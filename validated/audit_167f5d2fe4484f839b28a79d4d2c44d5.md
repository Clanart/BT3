Based on my investigation, this bug class (missing scope-binding field in an EIP-712 hash, allowing signature replay) does map onto the Kaia auction/searcher bid module.

### Title
Auction searcher bid EIP-712 signature can be replayed against a different `targetTxHash`/auctioneer package because `validateBid` never re-derives or binds the signed digest to the bid's pool-tracked identity beyond simple map lookup - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
The Biconomy report shows that `execTransaction`'s replay protection failed because the signed hash did not incorporate `batchId`, letting an attacker reuse a nonce from a different scope to replay a transaction. The analogous risk in Kaia's `kaiax/auction` module is that the EIP-712 struct that the searcher and auctioneer sign (`AuctionTx`) is only as strong as the set of fields baked into `EncodeData()`/`GetHashTypedData` [1](#0-0) , and the pool-level admission logic in `validateBid` treats a bid as unique purely by `bid.Hash()` (its RLP hash) rather than re-checking that the signed `nonce`/`blockNumber` still correspond to the current chain state at insertion time beyond a coarse future-block window [2](#0-1) .

### Finding Description
`Bid.GetHashTypedData` builds the EIP-712 digest from `TargetTxHash, BlockNumber, Sender, To, Nonce, Bid, CallGasLimit, Data` (and `MaxGasPrice` in v3) [3](#0-2) [1](#0-0) . `BidPool.validateBid` only rejects a bid if an *identical* bid hash already exists (`bp.bidMap[bid.Hash()]`) and if the sender already has a *different* winning bid at the same block number [4](#0-3) . It checks that `blockNumber` is in `[currentBlockNumber+1, currentBlockNumber+allowFutureBlock]` [5](#0-4) , bid > 0, data size, gas limit, and the two signatures [6](#0-5) . Notably, `validateBid`/`validateBidSigs` never checks `bid.Nonce` against any tracked on-chain/searcher-account nonce — the `Nonce` field only feeds into the signed hash and is otherwise unchecked at the p2p/pool layer.

The actual replay-prevention for `nonce` is expected to happen on-chain inside the `AuctionEntryPoint` system contract's `call()` function when the proposer executes the winning bid. However, the reference/testing implementation of that contract, `AuctionEntryPointMock.sol`, has its nonce-consumption and signature-verification logic entirely commented out (`_useNonce`, `_checkAndTakeBid`, `ValidateMember` recovery and `nonces(auctionTx.sender)` check are all disabled) [7](#0-6) . If the same disabled/incomplete nonce-check logic is present in the production `AuctionEntryPoint` contract deployed via the system-contract registry (referenced by `system.ReadActiveAddressFromRegistry(... system.AuctionEntryPointName ...)` in `kaiax/auction/impl/execution.go`) [8](#0-7) , then a validly-signed bid with a fixed `(sender, nonce)` pair could be replayed across multiple blocks/target transactions as long as the attacker resubmits it with an updated `blockNumber` (which only needs to satisfy the coarse "not yet used" check in `bidPool`, not an on-chain nonce increment).

I could not verify the real production `AuctionEntryPoint` contract's Solidity source in this index — only the auto-generated Go bindings (`contracts/bindings/auction/Kip249.go`, `contracts/bindings/auctionv3/Kip249V3.go`) and the commented-out mock are indexed, so I cannot confirm from the available code whether the deployed production contract actually enforces `nonce` consumption or replay protection at settlement time. This is the key missing piece to definitively confirm exploitability, analogous to how the original H-07 report required inspecting `SmartAccount.sol`'s `encodeTransactionData`.

### Impact Explanation
If the on-chain entry point does not consume/check the signed `nonce` (mirroring the disabled logic in the mock), a searcher's single signed bid could be reused to win and settle multiple auctions or be replayed by anyone who observed the bid over the p2p network, since `validateBid` does not enforce nonce monotonicity — leading to unauthorized repeated fee/bid settlement or state divergence between nodes that received the bid at different times with different `blockNumber` values accepted within the `allowFutureBlock` window.

### Likelihood Explanation
Likelihood is uncertain without visibility into the deployed production `AuctionEntryPoint` contract bytecode/source. The Go-side `bid_pool.go` validation logic alone does not prevent nonce reuse; it only prevents byte-identical duplicate bids and conflicting winners in the *same* block number. If replay protection lives solely in the on-chain contract and that logic mirrors the commented-out mock, likelihood would be high; if the production contract in fact enforces nonce consumption (unlike the mock), likelihood is low. This repo's indexed content does not include the full production contract source needed to confirm which is the case.

### Recommendation
Verify (and if necessary add) that the production `AuctionEntryPoint` contract's `call()` path actually calls `_useNonce(sender)`/`nonces(sender)` and increments a per-sender nonce tied to the signed `AuctionTx.nonce`, consistent with what is stubbed out in `AuctionEntryPointMock.sol`. Additionally, consider having `BidPool.validateBid` cross-check `bid.Nonce` against the searcher's current account/auction nonce (analogous to `state.GetNonce`) before admitting a bid to the pool, rather than relying solely on hash-based deduplication and the coarse future-block window.

### Proof of Concept
Not independently reproducible from the indexed code alone, because the deployed production `AuctionEntryPoint` contract source was not available for inspection — only the disabled-nonce mock (`contracts/testing/system_contracts/AuctionEntryPointMock.sol`, lines 54-108) and Go bindings are indexed. A full PoC would require: (1) confirming the production contract's `call()` implementation, (2) crafting a validly-signed `Bid` with fixed `sender`/`nonce`, (3) submitting it once to be won/settled, then (4) resubmitting the same signed bid with an updated `blockNumber` to see if `BidPool.validateBid` and the on-chain contract accept it a second time without nonce having advanced.

func (b *Bid) EncodeData() []byte {
	encoded := make([]byte, 0)
	encoded = append(encoded, b.TargetTxHash.Bytes()...)
	encoded = append(encoded, common.LeftPadBytes(common.Int64ToByteBigEndian(b.BlockNumber), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.Sender.Bytes(), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.To.Bytes(), 32)...)

func (bp *BidPool) validateBid(bid *auction.Bid) error {
	blockNumber := bid.BlockNumber

	bp.bidMu.RLock()

	// Check if the auction tx is already in the pool.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		bp.bidMu.RUnlock()
		return auction.ErrBidAlreadyExists
	}

	// 1. The `bid.Sender` must not be in the winner list of the same block number if the new bid isn't equal to the previous bid.
	if bp.senderHasDifferentWinner(bid) {
		bp.bidMu.RUnlock()
		return auction.ErrBidSenderExists
	}
	bp.bidMu.RUnlock()

	curBlock := bp.Chain.CurrentBlock()
	if curBlock == nil {
		return auction.ErrBlockNotFound
	}

	// 2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
	curNum := curBlock.NumberU64()
	if blockNumber <= curNum || blockNumber > curNum+allowFutureBlock {
		return auction.ErrInvalidBlockNumber
	}

	// 3. The `bid.Bid` must be greater than 0.
	if bid.Bid.Sign() <= 0 {
		return auction.ErrZeroBid
	}

	// 4. The data size must be less than the maximum limit.
	if uint64(len(bid.Data)) > BidTxMaxDataSize {
		return auction.ErrExceedMaxDataSize
	}

	// 5. The gas limit must be less than the maximum limit.
	if bid.CallGasLimit > BidTxMaxCallGasLimit {
		return auction.ErrExceedMaxCallGasLimit
	}

	// 6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.
	if err := bp.validateBidSigs(bid); err != nil {
		return err
	}

	return nil
}
