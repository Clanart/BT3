### Title
Unhandled `UnicodeDecodeError` on malformed NFT URI metadata halts wallet coin-set processing - ([File: chia/wallet/nft_wallet/nft_puzzle_utils.py])

### Summary
`get_nft_info_from_puzzle()` decodes attacker-controlled on-chain NFT metadata bytes (`u`, `mu`, `lu` key/value URI lists curried into an NFT puzzle) as strict UTF-8 without any error handling, unlike an analogous CAT-memo decode elsewhere in the codebase that explicitly catches `UnicodeError`. This mirrors the CVE's bug class of "incorrect string-decoding call on attacker-supplied bytes causing an out-of-bounds/invalid read that crashes the consumer" — here the Python analog is an unhandled decode exception raised while processing a spend a victim wallet did not choose the content of.

### Finding Description
`UncurriedNFT.uncurry()` extracts the `data_uris` (`u`), `meta_uris` (`mu`), and `license_uris` (`lu`) fields straight out of the curried NFT puzzle metadata program, with no validation of their byte content: [1](#0-0) 

`get_nft_info_from_puzzle()` then unconditionally decodes every URI atom as strict UTF-8: [2](#0-1) 

Because these URI bytes are simply curried CLVM atoms in the puzzle reveal of an NFT coin, any party who mints or transfers an NFT can set them to arbitrary byte sequences that are not valid UTF-8 (e.g., a lone `0x80` continuation byte). `str(uri, "utf-8")` will raise `UnicodeDecodeError` with no surrounding `try/except`.

This function is invoked from wallet-side NFT processing paths reachable by receiving/observing any NFT coin — e.g. `WalletStateManager.manual_nft_search()` calls it directly after uncurrying an arbitrary coin's puzzle reveal fetched from a peer: [3](#0-2) 
and it is also called from `wallet_rpc_api.py` NFT info/list RPC handlers. None of these callers wrap the call in exception handling for `UnicodeDecodeError`.

Notably, the codebase already recognizes this exact class of untrusted-string-decode risk and defensively handles it elsewhere for a similar attacker-controlled `CREATE_COIN` memo field: [4](#0-3) 
but the equivalent guard is missing for NFT metadata URIs.

### Impact Explanation
A malicious minter/sender can craft an NFT (or transfer an existing NFT they control) with non-UTF-8 bytes in the `u`/`mu`/`lu` metadata fields. Any full wallet client that subsequently processes that coin's puzzle reveal through `get_nft_info_from_puzzle` (via `manual_nft_search`, NFT listing/info RPCs, or NFT sync code paths that build `NFTInfo`) will hit an unhandled `UnicodeDecodeError`. Depending on the call site, this can abort an RPC call, crash a wallet-sync coroutine, or otherwise halt processing of that spend/coin for the victim wallet — a spend-triggered transaction-processing halt reachable from a single crafted coin spend, without requiring any privileged access.

### Likelihood Explanation
Likelihood is moderate-to-high for triggering the crash: constructing an NFT puzzle with arbitrary metadata bytes requires no special privilege — any wallet user can mint/transfer NFTs with attacker-chosen metadata atoms, and the vulnerable decode path executes automatically whenever a wallet inspects such a coin (e.g. via RPC `nft_get_info`/`nft_get_nfts`, or `manual_nft_search`). No signature bypass or consensus change is needed — only inclusion of a non-UTF-8 byte string in the URI KV list of the NFT metadata.

### Recommendation
Wrap the `str(uri, "utf-8")` conversions in `get_nft_info_from_puzzle()` (`chia/wallet/nft_wallet/nft_puzzle_utils.py`) in try/except for `UnicodeDecodeError` (or use `errors="replace"`/`"backslashreplace"` similar to the existing pattern in `chia/_tests/util/run_block.py`), so malformed/adversarial NFT metadata degrades gracefully (e.g., empty string or hex fallback) instead of raising an unhandled exception in wallet processing paths that operate on untrusted, attacker-supplied coin data.

### Proof of Concept
1. Construct an NFT-layer puzzle (`NFT_MOD` curried under `SINGLETON_TOP_LAYER_MOD`) whose metadata program includes a key/value pair `(b"u" . (0x80 ...))` — i.e., a "URI" atom containing an invalid UTF-8 byte sequence (e.g., a stray continuation byte `0x80`).
2. Mint or transfer this NFT to any address (no privileged access required — this is a standard, unsigned-by-victim on-chain object any user can create).
3. Have a wallet (victim) observe/sync this coin and call `manual_nft_search()` (or the `nft_get_info`/`nft_get_nfts` RPCs, which internally call `get_nft_info_from_puzzle`) on the coin id.
4. `UncurriedNFT.uncurry()` succeeds and returns `data_uris` containing the malformed atom; `get_nft_info_from_puzzle()` executes `str(uri, "utf-8")` on it in the loop at `nft_puzzle_utils.py:90-94`, raising an uncaught `UnicodeDecodeError` that propagates out of the RPC/sync call, halting processing for that request/coin.

Note: I could not fully trace every downstream call site's exception-handling wrapper (e.g., whether the RPC framework in `wallet_rpc_api.py` globally catches all exceptions before returning an error response, which would reduce this from a "halt" to a "failed RPC call"); this should be verified in a live/full-repo session to confirm the exact blast radius (single RPC failure vs. broader sync-loop disruption).
