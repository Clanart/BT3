### Title
Unbounded attacker-controlled element count in `SchnorrAggregate::read` enables CPU/memory exhaustion via expensive per-element point decompression - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` deserializes an aggregate Schnorr signature by first reading a little-endian `u32` count from attacker-controlled bytes, then looping that many times calling `C::read_G(reader)` — full elliptic-curve point decoding and validation — with no upper bound on the count and no pre-validation of remaining input length. An unprivileged party can feed this function a crafted buffer/stream whose declared count forces the maximum-possible number of expensive decompression operations plus proportional heap growth, a direct analog of CVE-2023-39327 (malicious input causing the program to enter a large loop / continuous work). The same attacker-controlled cardinality then drives `SchnorrAggregate::verify`'s `Vec::with_capacity(2 * len + 1)` and a `2n + 1`-term `multiexp_vartime`.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `read` reads `len` as a `u32` and iterates `0 .. u32::from_le_bytes(len)` unconditionally:

```rust
let mut len = [0; 4];
reader.read_exact(&mut len)?;

let mut Rs = vec![];
for _ in 0 .. u32::from_le_bytes(len) {
  Rs.push(C::read_G(reader)?);
}
Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
```

`C::read_G` for in-scope ciphersuites (e.g., Secp256k1 via k256, Ristretto/Ed25519/Ed448 via `crypto/dalek-ff-group` and `crypto/ed448`) performs full point deserialization — field-element decoding, quadratic-residue/sqrt recovery or torsion/validity checks — a constant-but-expensive operation per element. The declared count is never capped (no `MAX_AGGREGATE` bound, no check of remaining length before looping), so the loop bound and resulting `Vec<C::G>` growth are entirely attacker-determined, limited only by what the `Read` source yields. Because `read` takes any `R: Read`, an attacker supplying a large or lazily-produced byte stream (e.g., decompressed or streamed input, or simply a multi-MB buffer — trivially cheap to produce since valid or invalid 32-byte bodies cost the attacker ~zero CPU while each costs the victim a full decompression attempt) forces work disproportionate to attacker effort: each 32 attacker bytes induce one decompression plus a `push`/`Vec` reallocation.

The second stage is `verify` (same file, `aggregate.rs`): it checks `self.Rs.len() != keys_and_challenges.len()` early, but once lengths match it allocates `Vec::with_capacity((2 * len) + 1)`, calls the wide-reduction `weight()` once per signer, and feeds `2n + 1` `(scalar, point)` pairs into `multiexp_vartime` — so a large attacker-supplied aggregate also amplifies verification cost, with the allocation size attacker-controlled.

The codebase itself acknowledges this exact pattern as a live DoS concern elsewhere: `networks/ethereum/src/machine.rs` (`Call::read`) contains the comment "A valid DoS would be to claim a 4 GB data is present for only 4 bytes" and works around it by chunked reading — showing the project treats attacker-declared lengths in `Read` impls as in-scope threats — and `coordinator/src/tributary/transaction.rs` enforces `TRANSACTION_SIZE_LIMIT` on `commitments_len * each_commitments_len` for `DkgCommitments`. `SchnorrAggregate::read` has no such guard.

### Impact Explanation
This is reachable by an unprivileged party: `SchnorrAggregate::read` accepts arbitrary untrusted bytes via a generic `Read`, and the signature-aggregation protocol (eprint 2021/350) is inherently designed to consume signatures submitted by external signers — i.e., the aggregate is the message an unauthenticated counterparty produces. By sending an aggregate with a declared/actual element count of hundreds of thousands to millions, the attacker forces the victim to:

- execute that many `read_G` point decompressions (sqrt/validity work) during parsing,
- grow a `Vec` of group elements proportional to the count (each `C::G` is a full internal point representation, larger than the 32-byte wire form),
- and, on `verify`, allocate `2n + 1` multiexp pairs and run a variable-time multi-scalar multiplication plus `n` wide `weight()` reductions.

This stalls the parsing/verification thread for an extended period and can exhaust memory, degrading or halting the node's ability to process legitimate aggregates — mirroring the OpenJPEG impact (program forced into a large loop over malicious input, medium-severity availability loss). Severity is Medium: availability impact requiring the victim to parse attacker-supplied input.

### Likelihood Explanation
Likelihood is moderate. Exploitation requires only that the target calls `SchnorrAggregate::read` on bytes the attacker controls — the standard, documented entry point for this type (`pub fn read`, `serialize`/`write` round-trip). No privileges, valid keys, or cooperation are needed; the decompression cost is paid even for garbage points (the `?` on `read_G` still burns the decode attempt per element, and valid-but-meaningless compressed points are free to generate). The constraint keeping it at Medium rather than High: work is linear in supplied bytes (the loop exits early once the reader is exhausted), so the attacker must transmit/provide a proportionally large payload rather than achieving infinite loop from a few bytes — the amplification is the asymmetry between ~free attacker bytes and expensive victim-side per-element cryptography plus unchecked allocation, not an infinite loop.

### Recommendation
Bound the declared count before looping and fail fast on obvious length/count mismatches:

```rust
const MAX_AGGREGATE_SIGNATURES: u32 = /* protocol max, e.g. n-of-n signer cap */ u16::MAX as u32;

let mut len = [0; 4];
reader.read_exact(&mut len)?;
let len = u32::from_le_bytes(len);
if len > MAX_AGGREGATE_SIGNATURES {
  Err(io::Error::other("aggregate signature count exceeds limit"))?;
}
let mut Rs = Vec::with_capacity(len.min(4096) as usize); // don't trust len for preallocation
for _ in 0 .. len {
  Rs.push(C::read_G(reader)?);
}
```

Apply the same spirit in `verify`: cap `keys_and_challenges.len()` before `Vec::with_capacity(2 * len + 1)` and the multiexp. Alternatively enforce a serialized-size limit at a higher layer for any caller feeding network bytes into `read`.

### Proof of Concept
```rust
use std::io;
use frost::curve::{Ciphersuite, Secp256k1}; // or dalek_ff_group::Ed25519
use schnorr::SchnorrAggregate;

fn attack() {
  // 4-byte count, then a large run of valid compressed points.
  // Compressed Secp256k1 points with x = 1,2,3,... are cheap to fabricate;
  // even 0x02-prefixed garbage still costs a full decompression attempt each.
  let mut buf = (u32::MAX).to_le_bytes().to_vec();
  // Append N 32-byte bodies (e.g., valid encodings for maximum per-element cost).
  let point = {
    let p = <Secp256k1 as Ciphersuite>::generator();
    *p.to_bytes().as_ref()
  };
  for _ in 0 .. 1_000_000 {
    buf.extend_from_slice(&point);
  }

  // Victim: one unprivileged parse call burns ~1M decompressions + 1M-element Vec growth.
  // Each C::read_G performs field decoding + sqrt/validity checks.
  let agg = SchnorrAggregate::<Secp256k1>::read(&mut buf.as_slice()).unwrap();

  // Second-order amplification: matching-length keys_and_challenges triggers
  // Vec::with_capacity(2n+1) and a 2n+1-pair multiexp_vartime.
  // agg.verify(b"dst", &vec![(<Secp256k1 as Ciphersuite>::generator(), <Secp256k1 as Ciphersuite>::F::ONE); agg.Rs().len()]);
}
```

Observed effect: `read` alone performs ~1,000,000 point decompression/validation operations (the dominant cost per element for k256/dalek-ff-group/ed448 `read_G`) and grows `Rs` to a million `C::G` elements, from ~32 MB of attacker bytes that cost the attacker essentially nothing to produce — a sustained CPU/memory DoS per message, repeatable to continuously occupy the victim, directly analogous to the OpenJPEG large-loop warning-spam denial of service.
