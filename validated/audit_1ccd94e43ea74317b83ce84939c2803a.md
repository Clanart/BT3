### Title
Unbounded memory allocation when reading blob contents from an attacker-controlled repository (`git show`) causes Desktop OOM crash - (File: `app/src/lib/git/show.ts`)

### Summary
`getBlobContents` in `app/src/lib/git/show.ts` invokes `git show <commitish>:<path>` with `encoding: 'buffer'` and no `maxBuffer` override. In `app/src/lib/git/core.ts`, the default `maxBuffer` is computed as `options?.encoding === 'buffer' ? Infinity : kStringMaxLength` [1](#0-0) , meaning any `git` invocation using buffer encoding without an explicit `maxBuffer` is allowed to buffer an unbounded amount of data from the child process into memory.

### Finding Description
`getBlobContents` reads the full contents of a git blob (e.g. a file at a given commit/ref) with no size limit: [2](#0-1) 

Because `maxBuffer` is not passed, `core.ts` defaults it to `Infinity` when `encoding: 'buffer'` is used [1](#0-0) . This differs from the safer sibling function `getPartialBlobContentsCatchPathNotInRef`, which explicitly caps `maxBuffer: length` and gracefully handles `isMaxBufferExceededError` [3](#0-2) . `getBlobContents` has no such cap.

This function is used both directly and indirectly (`getResolutionDiff` calls it to read a merge-conflict stage blob via `git show :2:<path>` / `:3:<path>`) [4](#0-3) . The repository content (including the size of any blob at any ref/stage) is entirely attacker-controlled when the user clones or fetches a malicious/compromised repository — a huge blob (e.g. gigabytes) committed to a branch, tag, or present in a merge-conflict stage will be read in full into a Node.js `Buffer` with no upper bound.

Existing guards elsewhere in the codebase (the 70MB `MaxDiffBufferSize`/`isValidBuffer` check in `diff.ts` [5](#0-4) , and the 10MB check in `getFilesDiffText` [6](#0-5) ) are applied only *after* the full buffer has already been allocated by `git()`/`exec()` — they don't prevent the initial unbounded read, they just prevent rendering it. For `getBlobContents` specifically there is no post-hoc size check at all before consumers call `.toString()` on the buffer (e.g. `getResolutionDiff`'s `buffer.toString('utf-8')` at `app/src/lib/git/diff.ts:482`), so a sufficiently large blob will either exhaust process memory during the `exec` buffering stage or throw when converting an oversized buffer to a string.

### Impact Explanation
This is the closest local analog to the reported Nethermind P2P bug class: an attacker who controls content ingested by the client (there, P2P messages; here, a cloned/fetched git repository's blob content) can force the client to allocate unbounded memory, resulting in denial of service (renderer/main process OOM crash or unresponsiveness) for any Desktop user who opens/browses a malicious repository containing an oversized blob, or resolves a merge conflict against a commit/stage containing one. Per the reporting scope, this is a DoS-class primitive — the same class as the source report — with no code execution, file write, or credential exfiltration achieved. It should be evaluated as Medium consistent with the seed report's own severity rating, or discounted entirely if DoS-only findings are out of scope for this exercise.

### Likelihood Explanation
Triggering the path only requires normal, un-privileged user actions: cloning/fetching an attacker-supplied repository (or adding it as a remote), then interacting with a commit/ref/path that resolves to an oversized blob (viewing a commit diff, or resolving a merge conflict where `getResolutionDiff` reads a conflict-stage blob). No admin rights, local access, or social engineering beyond "open this repository" is required, matching the specified valid-impact criteria (attacker controls a cloned/fetched repository).

### Recommendation
Pass an explicit, bounded `maxBuffer` to the `git` call inside `getBlobContents` (mirroring `getPartialBlobContentsCatchPathNotInRef`'s pattern), and handle `isMaxBufferExceededError` by truncating or rejecting rather than allowing an unbounded buffer to be built. Consider changing the `core.ts` default `maxBuffer: options?.encoding === 'buffer' ? Infinity : kStringMaxLength` for buffer-encoded results to a sane finite ceiling for callers that don't override it, rather than defaulting to `Infinity`.

### Proof of Concept
1. Attacker creates and hosts a git repository containing a single blob of several GB in size (e.g. committed via `git commit` of a large binary file), or crafts a merge scenario where one conflict stage (`:2:<path>` / `:3:<path>`) resolves to such an oversized blob.
2. Victim clones or fetches this repository in GitHub Desktop and opens a commit/diff view that resolves to the oversized blob path, or attempts merge-conflict resolution (triggering `getResolutionDiff` → `getBlobContents`) at `app/src/lib/git/diff.ts:481` / `app/src/lib/git/show.ts:23-31`.
3. `git()` in `core.ts` executes `git show <ref>:<path>` with `maxBuffer: Infinity` (default for buffer encoding, `core.ts:234`), causing the process to buffer the entire blob content in memory with no bound.
4. Depending on available memory, this results in an out-of-memory crash of the Electron process or severe unresponsiveness — a DoS analogous to the Nethermind "evil client" OOM crash pattern, but scoped to Desktop's own git-object ingestion path rather than P2P networking.

Note: I was unable to execute this PoC in a live environment (no filesystem/terminal access); the analysis is based on static code review of the cited files, and the actual reachable maximum blob size / practical crash threshold would need to be validated with a live Desktop build.

```typescript
export async function getPartialBlobContentsCatchPathNotInRef(
  repository: Repository,
  commitish: string,
  path: string,
  length: number
): Promise<Buffer | null> {
  const args = ['show', `${commitish}:${path}`]

  return git(args, repository.path, 'getPartialBlobContentsCatchPathNotInRef', {
    maxBuffer: length,
    expectedErrors: new Set([GitError.PathExistsButNotInRef]),
    encoding: 'buffer',
  })
    .then(r =>
      r.gitError === GitError.PathExistsButNotInRef ? null : r.stdout
    )
    .catch(e =>
      isMaxBufferExceededError(e) ? coerceToBuffer(e.stdout) : Promise.reject(e)
    )
```
