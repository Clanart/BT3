### Title
NFT minters can forge an eve coin's DID-ownership field to impersonate arbitrary DID owners without their approval - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
`NFTWallet.generate_new_nft` documents, via an explicit code comment, that the DID "owner" value curried into a freshly-minted (eve) NFT coin's ownership layer can be set to any DID **without that DID's consent or any on-chain approval mechanism**, because the transfer-program/announcement enforcement that normally protects an owner-change (`-10` condition) only applies to *subsequent* spends of an established coin, not to the genesis/eve creation of the ownership-layer puzzle itself.

### Finding Description
Chia's NFT ownership model (`construct_ownership_layer` / `NFT_OWNERSHIP_LAYER`) stores a `current_owner` DID value curried directly into the puzzle. Legitimate owner changes on an already-existing coin are gated by the NFT transfer program requiring a puzzle announcement from the target DID's own coin spend (see `get_did_approval_info`, `chia/wallet/nft_wallet/nft_wallet.py:436-463`, and the enforced `ASSERT_ANNOUNCE_CONSUMED_FAILED` behavior demonstrated in `chia/_tests/wallet/nft_wallet/test_nft_lifecycle.py:314-339`).

However, for the very first ("eve") spend that creates the NFT, no such protection exists at the puzzle level. `generate_new_nft` explicitly acknowledges this: [1](#0-0) 

The code deliberately keeps the *curried* owner_did empty (`b""`) at eve-puzzle construction time specifically because, as the comment states, "eve coin DID can be set to whatever" and "wallets should always ignore DID value for eve coins as they can be set to any DID without approval." The actual owner assignment is only performed afterward through the `-10` change-owner condition in the eve spend itself: [2](#0-1) 

Because this is the *genesis* spend of a brand-new singleton (freshly launched via `SINGLETON_LAUNCHER_PUZZLE`), there is no pre-existing lineage or prior owner to protect, so nothing at the consensus/CLVM level stops an actor from crafting a raw eve spend bundle that sets `new_owner` to an arbitrary victim DID id (any `bytes32`) directly in the `-10` condition, without going through `get_did_approval_info` and without controlling or signing for that DID at all. The wallet-level `get_did_approval_info` call is merely a convenience helper for wallets that *do* own the target DID — it is not enforced by the puzzle for eve/genesis coins, and the comment confirms this gap is a known, accepted design quirk rather than a bug that's actually fixed anywhere in this code path.

Any node/wallet/indexer/marketplace that trusts the on-chain `owner_did` (or `minter_did`) field of a newly seen NFT coin — for example via `NFTWallet.identify()` (`chia/wallet/nft_wallet/nft_wallet.py:274-361`), which uses the parsed `new_did_id`/`owner_did` to decide which DID-linked NFT wallet a coin belongs to — can therefore be made to falsely associate an attacker-minted NFT with a victim's DID identity, purely by the attacker choosing what value to embed in the mint's `-10` condition.

### Impact Explanation
This is directly analogous to the Liferay bug class: an unprivileged actor (an NFT minter, i.e., anyone who can submit a spend bundle) can cause on-chain state to record them, or any DID, as the "owner" of an object without any actual authorization from that identity's key holder. Concretely:
- An attacker can mint NFTs that display an arbitrary, victim-controlled DID as `owner_did`, causing wallets/marketplaces/tools that key off DID ownership (e.g., `get_nft_wallet_by_did`, portfolio/ownership displays) to misattribute forged assets to a legitimate DID identity, enabling impersonation, reputation abuse, spam/counterfeit-collection attacks, and social-engineering (fake "verified owner" claims) against the victim's identity.
- Because the field is trusted at the wallet layer for indexing/sorting into DID-specific NFT wallets (`identify()`), a malicious NFT could get silently sorted into a victim's own local NFT-by-DID wallet view if the victim's own client scans it, without their consent, which is unexpected state mutation of the wallet's local view of their assets.

This is a Medium severity issue: it does not directly move funds or forge fungible-asset identity/supply, but it does forge coin/asset ownership metadata that other unprivileged parties and software reasonably treat as an authenticated attribute, matching the CWE-284 (Improper Access Control) pattern of the source advisory.

### Likelihood Explanation
Likelihood is high for exploitation feasibility (any wallet user can construct this spend bundle without special privileges — it only requires knowledge of a target DID's `launcher_id`, which is public), but the practical impact depends on downstream consumers (wallets, marketplaces, indexers) blindly trusting `owner_did`/`minter_did` fields on freshly seen coins instead of validating provenance/announcements, which the source code comment implies is an accepted risk that integrators must independently defend against.

### Recommendation
- Enforce, at the mempool/consensus or at minimum wallet-validation layer, that any `-10` (change owner) condition setting a non-empty DID on an eve/genesis NFT coin must be accompanied by a puzzle announcement from that DID's own coin (the same mechanism already used for post-mint transfers), removing the special-cased exemption for eve spends.
- Update all wallet-side consumers of NFT ownership data (`NFTWallet.identify`, RPC endpoints exposing `owner_did`/`minter_did`) to explicitly disregard or flag unverified DID ownership claims on freshly minted coins, and only treat DID association as "confirmed" once an on-chain announcement from that DID has been observed.
- Add a mempool/consensus level check (or clear user/developer facing documentation and stronger typed APIs) making this exemption explicit and unmissable, since currently it is only guarded by a source-code comment, not enforced code.

### Proof of Concept
1. Take any target DID's `launcher_id` (public information; the DID identity itself does not need to sign anything).
2. Construct a normal NFT-launch spend (launcher coin -> eve coin) as in `generate_new_nft`, but instead of legitimately calling `get_did_approval_info` for a DID you actually control, directly embed the victim's DID id in the `-10` change-owner condition of the eve spend's inner solution (mirroring the condition list built in `create_ownership_layer_transfer_solution`, `chia/wallet/nft_wallet/nft_puzzle_utils.py:214-231`), without any accompanying `CreatePuzzleAnnouncement`/`AssertAnnouncement` from the victim DID's coin.
3. Submit the resulting spend bundle to the mempool. Because it is a genesis/eve spend, and no announcement is asserted or required by the underlying puzzle logic for the initial ownership assignment (as documented in `nft_wallet.py:503-505`), the bundle is accepted, producing an NFT coin whose ownership-layer puzzle curries the victim's DID as `current_owner` even though the victim never approved this.
4. Query the resulting coin's ownership layer (or any indexer/wallet that surfaces `owner_did`) to observe that it now shows the victim DID as the "owner," despite no signature or announcement ever originating from that DID.

(Note: exact bytecode-level verification of the CLVM enforcement for the eve-spend path was not directly inspected beyond the cited Python driver code and accompanying test comments/behavior; the finding rests primarily on the explicit code comment/warning in `nft_wallet.py` and the observed test behavior in `test_nft_lifecycle.py` showing announcement-based enforcement only for non-genesis ownership changes.)
