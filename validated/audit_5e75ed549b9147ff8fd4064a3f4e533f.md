## Title
Silent conflict-marker-count corruption due to path quoting mismatch between `git diff --check` and `git status --porcelain=2 -z` - (File: `app/src/lib/git/diff-check.ts`)

### Summary
`getFilesWithConflictMarkers` in `app/src/lib/git/diff-check.ts` parses the plain-text (non-`-z`) output of `git diff --check` with a regex, while `getStatus` in `app/src/lib/git/status.ts` obtains file paths from `git status --porcelain=2 -z`, parsed byte-exactly by `parsePorcelainStatus` in `app/src/lib/status-parser.ts`. These two independently-derived path strings are used as the same lookup key in `conflictDetails.conflictCountsByPath.get(path)`.

### Finding Description
`getFilesWithConflictMarkers` runs `git diff --check` **without `-z`**: [1](#0-0) 
Without `-z`, Git applies its default path-quoting behavior (C-style quoting/escaping of unusual characters such as CR, LF, quotes, backslashes) to filenames in its human-oriented output, and the code makes no attempt to unquote/de-escape the captured value — it is used verbatim as the map key: `files.set(path, ...)`.

By contrast, `git status --porcelain=2 -z` is invoked with `-z`, which explicitly disables this quoting so that filenames are emitted as raw bytes delimited by `NUL`: [2](#0-1) 
`parsePorcelainStatus`/`parseUnmergedEntry` then extract `entry.path` directly from the raw token with no unescaping applied: [3](#0-2) 

These two independently-parsed path representations are then required to be byte-identical for a correct lookup: [4](#0-3) [5](#0-4) 

For a filename containing a special/control character such as an embedded or trailing CR, the porcelain `-z` path will contain the literal raw CR byte, while the `diff --check` output will quote/escape that same filename (wrapping it in double quotes and encoding the CR as an escape sequence, per Git's standard path-quoting rules), so the regex-captured string in `diff-check.ts` differs from the raw `entry.path` used as the lookup key. A search of the codebase confirms there is no unquoting/dequoting utility (`unquote`, `dequote`, `quotepath`) applied anywhere to reconcile this, and `core.ts`/the `git` wrapper does not pass `-c core.quotePath=false` to disable quoting for this call.

### Impact Explanation
When the keys mismatch, `conflictDetails.conflictCountsByPath.get(path)` returns `undefined`, and the code falls back to `0` via `|| 0`: [6](#0-5) 
A `conflictMarkerCount` of `0` is treated by `hasUnresolvedConflicts` as "no markers present," i.e., the file appears auto-resolved: [7](#0-6) 
This can mislead the user into believing a genuinely conflicted file (with real, unresolved `<<<<<<<`/`>>>>>>>` markers) has been fully resolved, potentially leading them to commit a file still containing conflict markers.

### Likelihood Explanation
This requires a specific, narrow precondition: a file path (in a merge/rebase/stash-conflict scenario) that contains a character Git considers "unusual" enough to trigger quoting in non-`-z` output (e.g., embedded CR, backslash, or double quote) — not something an attacker-controlled remote/repo can trivially and reliably exploit for a directly impactful outcome beyond a UI display/state discrepancy. It requires the attacker to have supplied such a filename in a repository/commit that the victim later merges/rebases against, which is a viable "attacker controls cloned/fetched repository content" scenario per the given scope. However, the practical exploitation is bounded to a display/state inconsistency (marking a file as resolved when it isn't) rather than direct code execution or credential exfiltration, and it depends on Git's actual default quoting behavior for the exact type of "unusual" character (this specific edge case around bare CR quoting was not verified against live Git source in this review — see caveat below).

### Recommendation
- Invoke `git diff --check` with `-z`-compatible parsing, or explicitly disable path quoting (`-c core.quotePath=false`) for this call so that the emitted paths are guaranteed to match the raw byte-exact paths used elsewhere (e.g., in `status.ts`).
- Alternatively, parse and unquote/de-escape any C-quoted (`"..."`) paths returned by `git diff --check` before using them as map keys.
- Add a regression test analogous to `app/test/unit/git/diff-check-test.ts` using a filename containing a CR/embedded newline/quote to confirm `getFilesWithConflictMarkers` and `parsePorcelainStatus` agree on the resulting path string.

### Proof of Concept
1. Create a repo, and via two branches, engineer a merge conflict on a file whose name contains a CR byte (e.g., `foo\r` — this can be done directly with low-level plumbing like `git update-index` using an escaped path, since normal filesystem APIs may reject CR on some platforms but Git's index does not).
2. Trigger the merge so the file is left with conflict markers.
3. Run `git status --porcelain=2 -z` and observe the raw path bytes (containing literal CR) reported for the unmerged entry — matching what `parseUnmergedEntry` extracts as `entry.path`.
4. Separately run `git diff --check` (no `-z`) on the same repo and observe that Git quotes the filename (e.g., wraps it in `"..."` and escapes the CR), which is what `getFilesWithConflictMarkers`'s regex captures as its map key.
5. Confirm the two strings are not equal, so `conflictCountsByPath.get(path)` misses, `conflictMarkerCount` falls back to `0`, and `hasUnresolvedConflicts` reports the file as resolved despite live conflict markers.

**Caveat:** I was not able to execute Git directly to confirm the exact quoting output for a bare/trailing CR character in this environment, so the precise escape form (and whether this specific control character reliably triggers quoting) should be empirically verified in a live Devin session before treating this as fully confirmed exploitable; the structural mismatch between quoted (`diff --check`) and raw (`status --porcelain -z`) path sources, however, is clearly present in the code as cited above.

export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

const unmergedEntryRe =
  /^u ([DAU]{2}) (N\.\.\.|S[C.][M.][U.]) (\d+) (\d+) (\d+) (\d+) ([a-f0-9]+) ([a-f0-9]+) ([a-f0-9]+) ([\s\S]*?)$/

function parseUnmergedEntry(field: string): IStatusEntry {
  const match = unmergedEntryRe.exec(field)

  if (!match) {
    log.debug(`parseUnmergedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for unmerged entry`)
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    path: match[10],
  }
}
