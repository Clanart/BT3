### Title
Malformed binary payload can escape as an uncaught `RuntimeException` from `GeneratedMessageLite.Builder.mergeFrom(CodedInputStream, ExtensionRegistryLite)` instead of the documented `InvalidProtocolBufferException` - (File: `java/core/src/main/java/com/google/protobuf/GeneratedMessageLite.java`)

### Summary
The Nextcloud report describes an Android application crashing because a value coming from an untrusted source triggers an uncaught exception that the app's exception handling doesn't expect — a class of bug that "invariant: public parsing/handling API must only surface documented, catchable exception types" is violated. The transferable invariant for Protobuf is: `MessageLite.parseFrom`/`Builder.mergeFrom` document that they only throw `InvalidProtocolBufferException` (a subclass of `IOException`) for malformed input, so calling code in a host application typically wraps these calls in `try { ... } catch (IOException e) { ... }`. If an unexpected unchecked `RuntimeException` (e.g. `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`) escapes instead, it will not be caught by that idiomatic handler and will crash the host application — the same failure mode as the Nextcloud bug, just relocated from Android application code into the protobuf-java "lite" runtime's stream-based merge path.

### Finding Description
`GeneratedMessageLite.Builder` has two different code paths for merging binary bytes, and they handle unexpected runtime exceptions inconsistently:

- The byte-array path (`mergeFrom(byte[] input, int offset, int length, ExtensionRegistryLite extensionRegistry)`) explicitly catches `IndexOutOfBoundsException` from the fast-path array schema decoder and converts it into a documented `InvalidProtocolBufferException.truncatedMessage()`: [1](#0-0) 

- The `CodedInputStream`-based path (used transitively by the public `parseFrom(InputStream)`, `parseFrom(CodedInputStream)`, and `mergeFrom(InputStream)` APIs) only catches `RuntimeException` and rethrows it as-is unless its *cause* happens to be an `IOException`: [2](#0-1) 

This means any `RuntimeException` thrown deep inside `Schema.mergeFrom` while decoding a malicious/malformed message via a `CodedInputStream` (e.g., a negative or corrupted length-delimited field length causing `NegativeArraySizeException`/`ArrayIndexOutOfBoundsException` while allocating or indexing byte buffers) is **not** normalized into `InvalidProtocolBufferException`, and instead propagates out of a method whose signature only declares `throws IOException`. Because `RuntimeException` is unchecked, the Java compiler permits this silently.

The generated `parseFrom` methods that route through this path are documented (and relied upon by callers) to only throw `IOException`/`InvalidProtocolBufferException`: [3](#0-2) [4](#0-3) 

By contrast, `AbstractParser.wrapAndThrowParseException` (used by the full, non-Lite runtime for the `CodedInputStream` path) does the same thing — it explicitly re-throws any `RuntimeException` unchanged rather than normalizing it — which is documented behavior but has the identical externally-visible effect: callers using `catch (IOException e)` around `parseFrom` will not catch such an exception: [5](#0-4) 

Extensive hardening elsewhere in the same codebase confirms this exact bug class is treated as a genuine, previously-fixed issue class in Protobuf: JSON/TextFormat parsers wrap `RuntimeException`s from Gson/tokenizers into `InvalidProtocolBufferException`/`ParseError` specifically "to distinguish between invalid protos vs. actual I/O errors" and to avoid leaking implementation-detail exceptions to callers: [6](#0-5) [7](#0-6) 
and Java's byte-array/array-decoder path was hardened to convert `IndexOutOfBoundsException` to a proper `InvalidProtocolBufferException`: [8](#0-7) 
but the `CodedInputStream`-based Lite merge path was not given the same normalization for generic `RuntimeException`s that are not wrapped `IOException`s.

### Impact Explanation
A consuming Java/Android application that calls `SomeLiteMessage.parseFrom(inputStream)` (or `mergeFrom(CodedInputStream, ...)`) inside a `try { ... } catch (IOException e) { ... }` block — the idiomatic pattern suggested by the public API's declared `throws IOException` — will not catch a `RuntimeException` that escapes from the fast decoder on a malformed/malicious payload. This directly reproduces the Nextcloud bug class: a value from an untrusted source (network payload, IPC extra, file) triggers an unhandled exception that crashes the process, because the actual exception type does not match what the documented contract and idiomatic exception handling expect. This is a denial-of-service/crash-only issue (no memory corruption, no RCE) — consistent with the Medium severity of the analog report.

### Likelihood Explanation
Likelihood is Medium: it requires (1) a genuinely malformed/malicious binary payload that trips an internal bounds/arithmetic bug deep in the Lite schema decoder (rather than a simple truncated field, which is already caught), and (2) an application using `parseFrom(InputStream/CodedInputStream)` rather than the byte-array overload. The byte-array overload is already hardened against `IndexOutOfBoundsException`, reducing exposure for the most common calling convention, but any Lite-generated message parsed from a stream (a common Android use case, e.g., reading from a socket or `ContentProvider`) is exposed to this path.

### Recommendation
Normalize exception handling in `GeneratedMessageLite.Builder.mergeFrom(CodedInputStream, ExtensionRegistryLite)` (and the analogous `AbstractParser`/full-runtime `CodedInputStream` path) so any `RuntimeException` thrown by the schema decoder that is not already an `InvalidProtocolBufferException`/wrapped `IOException` is converted into `InvalidProtocolBufferException` before leaving the public API, matching the treatment already given to `IndexOutOfBoundsException` in the byte-array overload. Add regression tests using crafted malformed lite messages (e.g., corrupted length-delimited fields via `CodedInputStream`) mirroring the existing `MapCrash`/`testMaliciousSGroupTagsWithMapField_fromInputStream` style tests to assert only `InvalidProtocolBufferException` (never a bare `RuntimeException`) escapes `parseFrom(InputStream)`.

### Proof of Concept
I was not able to construct or run an actual byte sequence in this environment that triggers a specific uncaught `RuntimeException` (as opposed to the already-handled `IndexOutOfBoundsException`/truncation cases) inside the fast-path schema decoder reached via `CodedInputStreamReader`; this would require exercising `ArrayDecoders`/`CodedInputStreamReader` with a debugger or fuzzer against a concrete generated Lite message type to find a specific malformed-length or malformed-varint input that raises, e.g., `NegativeArraySizeException`, rather than tracing this purely from static code reading. The code-level gap (inconsistent `RuntimeException` normalization between the byte[] and `CodedInputStream` merge paths in `GeneratedMessageLite.java`) is demonstrated above via direct citation; confirming an exact triggering payload would need dynamic testing, which is out of scope for this static analysis pass.

        throw new InvalidProtocolBufferException(e.getMessage(), e);
      }
    }
