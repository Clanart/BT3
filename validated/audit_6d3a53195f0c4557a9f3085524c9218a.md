### Title
Unauthenticated `internal_send_tx` aggregator RPC lets any caller drain the tx-sender's CPFP fee-payer wallet to broadcast arbitrary transactions - (File: `core/src/rpc/aggregator.rs`)

### Summary
The `ClementineAggregator::internal_send_tx` RPC accepts an arbitrary, already-signed Bitcoin transaction plus a fee-paying strategy and inserts it directly into the `tx_sender` queue for automated broadcasting, including CPFP fee-bumping funded by the aggregator's own wallet. Per the project's own documentation, the aggregator's gRPC server does not enforce client certificates, so this call is reachable by anyone, unlike the "internal" naming implies.

### Finding Description
`internal_send_tx` deserializes `raw_tx` from the request with no validation of its origin, structure, or relationship to any bridge transaction (deposit outpoint, kickoff, round, etc. are all `None`), and immediately calls `self.tx_sender.insert_try_to_send(..)` with `FeePayingType` chosen by the caller: [1](#0-0) 

Compare this to the sibling RPC `send_move_to_vault_tx`, which does perform strict structural validation (input/output counts, exact bridge amount, exact N-of-N/security-council script pubkeys) before queuing a tx: [2](#0-1) 

`internal_send_tx` has none of these checks. When `FeePayingType::CPFP` is chosen, `TxSender::send_cpfp_tx` will fund and sign a child transaction that spends the wallet's own "fee payer" UTXOs (created via `create_fee_payer_utxo`, funded from the tx-sender's Bitcoin Core wallet) to pay fees for the attacker-supplied parent transaction, and submits the resulting package with `submitpackage`: [3](#0-2) [4](#0-3) 

The reachability of this RPC without authentication is confirmed by the project's own documentation and server wiring: TLS client-certificate verification (`OnlyAggregatorAndSelf`) is only applied when `config.client_verification` is set, and the docs explicitly state the aggregator does not enforce client certificates: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any network-reachable, unauthenticated caller can submit their own fully-signed Bitcoin transaction (paying nothing towards fees, e.g. with a zero-fee anchor output) and force Clementine's automation to fund confirmation of that transaction using BTC held in the tx-sender's own fee-payer wallet - a wallet controlled by the bridge operator/aggregator, not by the attacker. Because there is no check binding the submitted transaction to any legitimate bridge operation (no deposit outpoint, no kickoff/round linkage, no structural constraint on outputs), the aggregator's own capital is repeatedly consumed as CPFP fees for transactions chosen entirely by the caller. This is a state-changing, fund-consuming action triggered by an unauthenticated request, which the grading rubric explicitly recognizes as High severity ("an unauthenticated state-changing or broadcasting call").

### Likelihood Explanation
The vulnerability requires no privileged role, no key compromise, and no social engineering - only network access to the aggregator's gRPC endpoint, which per the documented design is intentionally not gated by client certificates. Exploitation is a single unauthenticated RPC call with attacker-controlled parameters.

### Recommendation
Restrict `internal_send_tx` to be truly internal: enforce the same certificate-based access control used for verifier/operator internal methods, or remove/gate this RPC behind explicit authorization, and validate that any transaction submitted for CPFP funding is tied to a transaction type/metadata that the aggregator itself generated (mirroring the validation already done in `send_move_to_vault_tx`).

### Proof of Concept
1. Attacker connects (over TLS, without a recognized client certificate, since `client_verification` is not enforced on the aggregator per documentation) to the aggregator's gRPC endpoint.
2. Attacker calls `ClementineAggregator/InternalSendTx` with `raw_tx` set to any self-crafted, validly-signed Bitcoin transaction (e.g., one with a P2A anchor output and zero fee) and `fee_type = CPFP`.
3. `internal_send_tx` inserts this transaction into the `tx_sender` queue with no relation to any deposit/withdrawal.
4. The background tx-sender task calls `send_cpfp_tx`, which creates/funds a fee-payer UTXO from the tx-sender's wallet and submits a CPFP package that spends the bridge-controlled fee-payer funds to pay for the attacker's transaction, repeatable at will.

    async fn internal_send_tx(
        &self,
        request: Request<clementine::SendTxRequest>,
    ) -> Result<Response<Empty>, Status> {
        #[cfg(not(feature = "automation"))]
        {
            Err(Status::unimplemented("Automation is not enabled"))
        }
        #[cfg(feature = "automation")]
        {
            let send_tx_req = request.into_inner();
            let fee_type = send_tx_req.fee_type();
            let signed_tx: bitcoin::Transaction = send_tx_req
                .raw_tx
                .ok_or(Status::invalid_argument("Missing raw_tx"))?
                .try_into()?;
            tracing::warn!(
                "Internal send tx rpc called with feetype: {:?}, tx hex: {}",
                fee_type,
                bitcoin::consensus::encode::serialize_hex(&signed_tx)
            );

            let mut dbtx = self.db.begin_transaction().await?;
            self.tx_sender
                .insert_try_to_send(
                    &mut dbtx,
                    None,
                    &signed_tx,
                    fee_type.try_into()?,
                    None,
                    &[],
                    &[],
                    &[],
                    &[],
                )
                .await
                .map_to_status()?;
            dbtx.commit()
                .await
                .map_err(|e| Status::internal(format!("Failed to commit db transaction: {e}")))?;
            Ok(Response::new(Empty {}))
        }
    }

    async fn create_fee_payer_utxo(
        &self,
        bumped_id: u32,
        dbtx: Option<&mut TxSenderTransaction>,
        tx: &Transaction,
        fee_rate: FeeRateKvb,
        total_fee_payer_amount: Amount,
        fee_payer_utxos_len: usize,
    ) -> Result<()> {
        tracing::debug!(
            "Creating fee payer UTXO for txid {} with bump id {}",
            &tx.compute_txid().to_string(),
            bumped_id
        );
        let required_fee = Self::calculate_required_fee(
            tx.weight(),
            fee_payer_utxos_len + 1,
            fee_rate,
            FeePayingType::CPFP,
        )?;

        // Aggressively add 2x required fee to the total amount to account for sudden spikes
        // We won't actually use 2x fees, but the fee payer utxo will hold that much amount so that while fee payer utxo gets mined
        // if fees increase the utxo should still be sufficient to fund the tx with high probability
        // leftover fees will get sent back to wallet with a change output in fn create_child_tx
        let new_total_fee_needed = required_fee
            .checked_mul(2)
            .and_then(|fee| fee.checked_add(MIN_TAPROOT_AMOUNT));
        if new_total_fee_needed.is_none() {
            return Err(eyre!("Total fee needed is too large, required fee: {}, total fee payer amount: {}, fee rate: {}", required_fee, total_fee_payer_amount, fee_rate).into());
        }
        let new_fee_payer_amount =
            new_total_fee_needed.and_then(|fee| fee.checked_sub(total_fee_payer_amount));

        let new_fee_payer_amount = match new_fee_payer_amount {
            Some(fee) => fee,
            // if underflow, no new fee payer utxo is needed, log it anyway in case its a bug
            None => {
                tracing::debug!("create_fee_payer_utxo was called but no new fee payer utxo is needed for tx: {:?}, required fee: {}, total fee payer amount: {}, current fee rate: {}", tx, required_fee, total_fee_payer_amount, fee_rate);
                return Ok(());
            }
        };

        tracing::debug!(
            "Creating fee payer UTXO with amount {} ({} sat/kvB)",
            new_fee_payer_amount,
            fee_rate
        );

        let fee_payer_tx = Transaction {
            version: Version::TWO,
            lock_time: LockTime::ZERO,
            input: vec![],
            output: vec![TxOut {
                value: new_fee_payer_amount,
                script_pubkey: self.signer.address().script_pubkey(),
            }],
        };

        let fee_payer_bytes = crate::serialize_tx_for_fund_raw(&fee_payer_tx);

        let funded_fee_payer_tx = self
            .rpc
            .fund_raw_transaction(
                &fee_payer_bytes,
                Some(&FundRawTransactionOptions {
                    add_inputs: Some(true),
                    // for cpfp txs, the speed of tx inclusion is not that important, so we can not use unsafe utxos and wait for them to become safe. Also all cpfp fee payer tx's are safe (all wallet owned inputs), so wallet can already chain them
                    include_unsafe: Some(self.include_unsafe),
                    change_address: None,
                    change_position: None,
                    change_type: None,
                    include_watching: None,
                    lock_unspents: None,
                    fee_rate: Some(Amount::from_sat(fee_rate.to_sat_per_kvb())),
                    subtract_fee_from_outputs: None,
                    replaceable: Some(true),
                    conf_target: None,
                    estimate_mode: None,
                }),
                None,
            )
            .await
            .wrap_err("Failed to fund cpfp fee payer tx")?
            .hex;

        let signed_fee_payer_tx: Transaction = bitcoin::consensus::deserialize(
            &self
                .rpc
                .sign_raw_transaction_with_wallet(&funded_fee_payer_tx, None, None)
                .await
                .wrap_err("Failed to sign funded tx through bitcoin RPC")?
                .hex,
        )
        .wrap_err("Failed to deserialize signed tx")?;

        let outpoint_vout = signed_fee_payer_tx
            .output
            .iter()
            .position(|o| {
                o.value == new_fee_payer_amount
                    && o.script_pubkey == self.signer.address().script_pubkey()
            })
            .ok_or(eyre!("Failed to find outpoint vout"))?;

        self.rpc
            .send_raw_transaction(&signed_fee_payer_tx)
            .await
            .wrap_err("Failed to send signed fee payer tx")?;

        self.db
            .save_fee_payer_tx(
                dbtx,
                bumped_id,
                signed_fee_payer_tx.compute_txid(),
                outpoint_vout as u32,
                new_fee_payer_amount,
                None,
            )
            .await
            .map_to_eyre()?;

        Ok(())
    }

## RPC Authentication

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities
and to authenticate clients. Client certificates are verified and filtered by
the verifier/operator to ensure that:

1. Verifier/Operator methods can only be called by the aggregator (using
   aggregator's client certificate `aggregator_cert_path`)
2. Internal methods can only be called by the entity's own client certificate
   (using the entity's client certificate `client_cert_path`)

The aggregator does not enforce client certificates but does use TLS for encryption.
