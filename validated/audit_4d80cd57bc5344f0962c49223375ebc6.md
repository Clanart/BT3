### Title
Missing `msg.value` guard in ICS20 (and other) precompiles causes permanent, unrecoverable loss of native funds - ([File: precompiles/ics20/tx.go])

### Summary
The `Starklane::depositTokens` bug class (unchecked/unused `msg.value` leading to stuck funds) has a direct native analog in Cosmos EVM's precompile framework. The ERC-20 precompile explicitly rejects any call carrying `msg.value` because a precompile address has no owner key and no fallback/withdraw path, so any native value sent to it would be permanently lost [1](#0-0) . The **ICS-20 IBC-transfer precompile's `Transfer` method has no equivalent check** [2](#0-1) . Since the EVM call mechanism transfers `value` at the stateDB level independent of the precompile's own logic (as documented directly in the ERC20 guard's comment), any native coin sent as `msg.value` to the ICS-20 precompile is simply ignored by the handler and becomes permanently stranded at the precompile's account, which is also explicitly registered as a `BlockedAddress` in the bank module — preventing any future recovery via `bank.Send` [3](#0-2) .

### Finding Description
Cosmos EVM's precompile execution pipeline runs precompile logic via `RunNativeAction`, which is invoked from each precompile's `Run(evm, contract, readonly)` method [4](#0-3) . Before `Run` is invoked, the underlying `vm.Contract` already carries whatever `value` the caller attached to the `CALL` (this is standard EVM `Call` semantics: native balance is moved from caller to callee before the callee code — or precompile — executes). The ERC-20 precompile's own comments make this explicit:

> "ERC20 precompiles cannot receive funds because they are not managed by an EOA and will not be possible to recover funds sent to an instance of them... This check is a safety measure because currently funds cannot be received due to the lack of a fallback handler." [1](#0-0) 

This confirms that, absent an explicit guard, `msg.value` sent to a precompile is not consumed, not refunded, and is unrecoverable — the exact same defect described in the Starklane report ("if a user sends more ether than necessary, the excess will not be refunded, leading to a loss of funds").

The `ICS20I.transfer` Solidity interface is not marked `payable` [5](#0-4) , but this is only a compile-time restriction on well-behaved Solidity callers using the high-level interface; it does not prevent an EOA (or a low-level `call{value: x}(...)`) from sending a raw `MsgEthereumTx`/`eth_sendTransaction` directly to the precompile address `0x0000000000000000000000000000000000000802` with the `transfer(...)` calldata and a non-zero `value` field. The Go implementation of `Precompile.Transfer` performs no check on `contract.Value()` at all [2](#0-1) , unlike the ERC-20 precompile's `Execute` method which explicitly reverts the whole call (via `ReturnRevertError`) when `contract.Value().Sign() == 1` [1](#0-0) .

The stranded balance cannot be later recovered through ordinary bank operations because every static precompile address (including `0x802`, the ICS20 address) is explicitly added to the bank module's `BlockedAddresses()` set [3](#0-2) . Attempting to `bank.Send` funds out of a blocked address fails with `"... is not allowed to send funds: unauthorized"` per the analogous blocked-address behavior demonstrated for `x/precisebank` [6](#0-5)  and there is no withdraw/fallback code at the precompile since it is not a real contract account.

This differs from the intentional "payable precompile" pattern used by `gov`/`staking`, where `msg.value` sent along with `deposit`/`delegate` calls is deliberately tracked and moved into the operation amount via the `BalanceHandler`'s before/after event diffing [7](#0-6) ; ICS20's `Transfer` has no such mechanism to consume or account for `contract.Value()`.

### Impact Explanation
Any unprivileged user who sends a transaction with a non-zero native `value` directly to the ICS20 precompile (`0x...0802`) — whether by mistake (e.g., wallets/scripts that always attach a "safety" value, similar to the original Starklane bug pattern) or from a malicious contract performing a raw `call{value: X}` — permanently loses that value. It is neither used for the IBC transfer (which has its own separate `amount`/`denom` parameters) nor refunded, and it cannot be recovered afterward because the precompile address is a bank-module blocked address with no owner key or withdrawal logic. This satisfies the Critical "permanent freezing, locking, theft, or unauthorized extraction of user funds" impact category, since native EVM coin (backed 1:1 by the underlying bank denom via `x/precisebank`) becomes permanently unspendable/unrecoverable.

### Likelihood Explanation
The trigger requires nothing more than an ordinary EVM transaction from any unprivileged EOA (or a call from any contract) targeting the ICS20 precompile address with a non-zero `value` field — no special privileges, race conditions, or governance actions are required. The only mitigating factor is that well-formed dApps using the official `ICS20I.sol` interface (non-payable function signature) would not naturally attach value, somewhat reducing accidental triggering versus a fully "payable"-looking function; however, direct RPC calls, scripts, or malicious/careless contracts using low-level calls can trigger it trivially and deterministically.

### Recommendation
Add the same `contract.Value().Sign() == 1` guard (reverting the call, as done in the ERC-20 precompile) to the ICS20 precompile's `Execute`/`Transfer` entrypoint, and audit all other transaction-type precompile methods that are not already integrated with the `BalanceHandler`'s value-accounting flow (e.g., `bank`, and any other precompile without an intentional value-consumption mechanism) to ensure none of them silently swallow `msg.value`. Precompiles that are intentionally payable (`gov`, `staking`, `werc20`) should keep relying on the `BalanceHandler` pattern to ensure the value is fully accounted for or refunded.

### Proof of Concept
1. Deploy/observe the ICS20 precompile at address `0x0000000000000000000000000000000000000802`.
2. From any funded EOA, submit a `MsgEthereumTx` (or `eth_sendTransaction`) with:
   - `to = 0x...0802`
   - `value = 1000000000000000000` (1 native coin, or any positive amount)
   - `data` = ABI-encoded call to `transfer(sourcePort, sourceChannel, denom, amount, sender, receiver, timeoutHeight, timeoutTimestamp, memo)` with a valid, much smaller `amount` (or `0`) for the actual IBC transfer.
3. Observe: the transaction succeeds; the IBC transfer proceeds using only the `amount` parameter from calldata. `precompiles/ics20/tx.go`'s `Transfer` never inspects `contract.Value()` [2](#0-1) .
4. The sender's native balance is reduced by both the IBC `amount` and the attached `value`; the `value` portion is added to the stateDB balance of `0x...0802`.
5. Attempt to retrieve the stuck balance via any bank operation targeting `0x...0802` (bech32 form) — it fails because the address is in `BlockedAddresses()` [3](#0-2) , and there is no contract code or admin function to move the balance out, so it is permanently lost.

// Note, this includes:
//   - module accounts
//   - Ethereum's native precompiled smart contracts
//   - Cosmos EVM' available static precompiled contracts
func BlockedAddresses() map[string]bool {
	blockedAddrs := make(map[string]bool)

	maccPerms := GetMaccPerms()
	accs := make([]string, 0, len(maccPerms))
	for acc := range maccPerms {
		accs = append(accs, acc)
	}
	sort.Strings(accs)

	for _, acc := range accs {
		blockedAddrs[authtypes.NewModuleAddress(acc).String()] = true
	}

	blockedPrecompilesHex := evmtypes.AvailableStaticPrecompiles
	for _, addr := range corevm.PrecompiledAddressesPrague {
		blockedPrecompilesHex = append(blockedPrecompilesHex, addr.Hex())
	}

	for _, precompile := range blockedPrecompilesHex {
		blockedAddrs[cosmosevmutils.Bech32StringFromHexAddress(precompile)] = true
	}

	return blockedAddrs
}

// Run prepare the native context to execute native action for stateful precompile,
// it manages the snapshot and revert of the multi-store.
func (p Precompile) RunNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) ([]byte, error) {
	bz, err := p.runNativeAction(evm, contract, action)
	if err != nil {
		return ReturnRevertError(evm, err)
	}

	return bz, nil
}

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

	return bz, nil
}

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
