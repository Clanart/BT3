### Title
First-depositor reward theft in `DelegateVoteRewardPool` via zero-totalSupply queued rewards - ([File: rewards/DelegateVoteRewardPool.sol])

### Summary
`DelegateVoteRewardPool` accumulates bribe rewards into `queuedRewards` whenever `totalSupply == 0`, and folds the entire accumulated `queuedRewards` into `rewardPerTokenStored` the next time rewards are queued with `totalSupply > 0`, dividing only by the current (potentially tiny) `totalSupply`. An attacker who is first to re-stake (vote) after `totalSupply` drops to zero can capture the entire backlog of queued rewards with a negligible stake.

### Finding Description
`_queueNewRewardsWithoutTransfer` buffers rewards into `rewardInfo.queuedRewards` while `totalSupply == 0`, and on the next call with `totalSupply > 0` adds the full buffered amount into the reward-per-token computation, dividing by the current `totalSupply`: [1](#0-0) 

`totalSupply` for this pool tracks vlMGP delegated to the special `delegatedPool` entry inside `WombatBribeManager`. Any vlMGP holder can call `vote()`/`unvote()` on that pool, which routes into `DelegateVoteRewardPool.stakeFor`/`withdrawFor`: [2](#0-1) [3](#0-2) 

`stakeFor` runs the `updateRewards` modifier (which snapshots the caller's earned rewards against the *current* `rewardPerTokenStored`, unaffected by queued rewards) before bumping `totalSupply`: [4](#0-3) 

Exploit flow:
1. All existing voters call `unvote(delegatedPool)`, driving this pool's `totalSupply` to 0 while bribe rewards continue to be routed through `harvestAll()`/`_manageRewards`, which is fully permissionless: [5](#0-4) 
These rewards accumulate purely in `rewardInfo.queuedRewards` because `totalSupply == 0`.
2. Attacker calls `vote(delegatedPool, +1)` (needs only 1 wei of locked vlMGP voting power), triggering `stakeFor(attacker, 1)`; `totalSupply` becomes 1, and the modifier gives the attacker a starting `userRewardPerTokenPaid` unaffected by the still-buffered `queuedRewards`.
3. Attacker calls `harvestAll()` again (or any user does). `_queueNewRewardsWithoutTransfer` now sees `totalSupply = 1 > 0`, so it adds the entire backlog `queuedRewards` to the newly harvested amount and divides by `totalSupply = 1`, assigning essentially the whole reward backlog's `rewardPerTokenStored` to the attacker's single wei of stake.
4. Attacker calls `getReward`/`harvestAll` claim path to withdraw the full reward token balance that should have been shared pro-rata among future stakers.

None of `onlyOperator`, `updateRewards`, or the accounting checks in `BribeRewardPool`/`BaseRewardPoolV2` prevent this, because they correctly track shares given the state at each call, but the state transition (`totalSupply: 0 → 1`) is exactly what a first re-depositor can grab to convert a shared reward pool into a single-account payout.

### Impact Explanation
This is theft of unclaimed protocol yield: bribe rewards that should be distributed to whichever vlMGP holders eventually vote for `delegatedPool` are instead captured almost entirely by an attacker with a 1-wei stake. This matches the Immunefi "theft of unclaimed yield" impact class. The magnitude equals however much bribe reward accumulated in `queuedRewards` while the pool was empty, which is unbounded (depends on incoming bribes and how long the pool remains at `totalSupply == 0`).

### Likelihood Explanation
The precondition — `totalSupply == 0` for the delegated-vote pool while rewards are queued — is a state that can happen organically (e.g., all delegators unvoting) or be intentionally engineered by an attacker unvoting their own small stake and racing to be first to re-stake. The only capital required is 1 wei of locked vlMGP voting power and gas, well within reach of any unprivileged actor, and the attack is fully repeatable each time the pool's `totalSupply` returns to zero.

### Recommendation
Do not let `queuedRewards` be fully absorbed by whatever `totalSupply` happens to be immediately after a zero-supply period. Options: (a) require a minimum bootstrap stake/lock before allowing `_queueNewRewardsWithoutTransfer` to convert `queuedRewards` into `rewardPerTokenStored`, (b) distribute queued rewards gradually (e.g., a vesting/streaming schedule) rather than instantaneously crediting them to whatever `totalSupply` is at the moment of the next stake, or (c) snapshot/burn a virtual minimum share (similar to Uniswap V2's MINIMUM_LIQUIDITY) so a 1-wei staker cannot capture 100% of the backlog.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `DelegateVoteRewardPool` (as `delegatedPool`'s rewarder), a mock reward token, and a mock `IWombatBribeManager` bribe source.
2. Have two users lock vlMGP and vote for `delegatedPool`, causing `DelegateVoteRewardPool.totalSupply > 0`.
3. Simulate a bribe harvest (`harvestAll`) that queues, say, 1000 reward tokens while `totalSupply > 0` is irrelevant here — instead, first have both users `unvote(delegatedPool)` to drive `totalSupply` to 0.
4. Trigger `harvestAll()` (or directly call the reward-queueing path) with `totalSupply == 0`; assert `rewards[token].queuedRewards == 1000e18` and `rewardPerTokenStored` unchanged.
5. Attacker locks a minimal amount of vlMGP and calls `vote(delegatedPool, +1)` (delta = 1 wei), causing `DelegateVoteRewardPool.totalSupply == 1`.
6. Trigger another `harvestAll()` call (even with 0 new bribes); assert `rewardPerTokenStored` jumps by `queuedRewards * 1e(decimals) / 1`.
7. Attacker calls `getReward(attacker)`; assert attacker receives (approximately) the full 1000e18 reward tokens despite holding only 1 wei of the pool's `totalSupply`, while other users who return to vote afterward get none of that backlog.
