### Title
Any single state-machine processing error halts finalized-block processing for all deposits, blocking timeout/challenge/disprove duties for honest operators - ([File: core/src/states/mod.rs])

### Summary
`StateManager::process_block_parallel` in `core/src/states/mod.rs` aggregates all errors produced while advancing every `RoundStateMachine`/`KickoffStateMachine` for a finalized block, and if *any* machine reports an error it aborts the whole function with `Err(...)` instead of skipping only the offending machine. Because `SystemEvent::NewFinalizedBlock` only advances `next_height_to_process`/`last_finalized_block` when `process_block_parallel` returns `Ok`, one failing kickoff/round machine (which can be driven into an error state by data an unprivileged actor controls, e.g. a malformed watchtower challenge, kickoff, or blockhash-commit witness matched by the state machine) stops block ingestion for *every* deposit/kickoff/round the state manager tracks, not just the offending one. This is structurally the same bug class as the reported Berachain issue: a single invalid/adversarial input that should be rejected or skipped instead aborts the entire state-transition pipeline for all other participants.

### Finding Description
`process_block_parallel` calls `Self::update_machines` on all kickoff and round machines in parallel, then collects any errors captured via `StateContext::capture_error` into `ctx.errors` for each machine: [1](#0-0) 

If `all_errors` is non-empty for *any* single machine, the function returns immediately with a combined `Err`, discarding progress for all machines that were being processed in that same call: [2](#0-1) 

This function is only called from `SystemEvent::NewFinalizedBlock` handling, and `next_height_to_process`/`last_finalized_block` are only advanced when it succeeds: [3](#0-2) 

Errors are captured generically by `StateContext::capture_error`, which stores any `eyre::Report` raised inside a state handler's async closure without discriminating between "attacker-controlled malformed data" and "genuine internal bug": [4](#0-3) 

The kickoff/round state machines drive time-critical, deadline-bound duties (`WatchtowerChallenge`, `SendOperatorAsserts`, `VerifierDisprove`, `SendLatestBlockhash`, `CheckIfKickoff`, `NewReadyToReimburse`) defined in `Duty`: [5](#0-4) 

If a matcher-driven event for one kickoff machine (e.g., an operator's kickoff/challenge/assert transaction, or a watchtower challenge whose witness content is attacker/participant controlled) causes that specific machine's handler to error (via `unhandled_event`/`capture_error`, or any propagated `?` inside the closures), the aggregate error path in `process_block_parallel` returns `Err`. Because the whole call is atomic w.r.t. `next_height_to_process`, the state manager can never advance past that block height again until the operator/verifier process is manually fixed and restarted (state is reloaded via `reload_state_manager_from_db`, which resumes from the same stalled height). During the outage, **every** other kickoff/round state machine (belonging to honest operators, unrelated deposits) is also unable to progress, so their deadline-bound duties (`AssertTimeout`, `ChallengeTimeout`, `WatchtowerChallengeTimeout`, `Disprove`) cannot be dispatched in time by the affected verifier/operator instance.

This mirrors the reported bug's chain of events precisely:
1. Berachain: one Deposit with invalid signature → state-transition function errors → proposer cannot build the next block → every subsequent proposer is stuck.
2. Clementine: one kickoff/round machine hitting an unexpected/invalid on-chain event → `process_block_parallel` errors → the state manager for that node can never process the next finalized block → every other deposit/kickoff/round machine tracked by that node stalls, and none of their time-critical duties fire.

### Impact Explanation
If any input matched by a state machine (which, per the module doc, is populated from L1-scanned Clementine transactions such as kickoffs, watchtower challenges, and asserts — content largely under participant/attacker control) drives that machine into an unhandled/error branch, the entire per-node block-processing pipeline halts. Because deadline-bound challenge/disprove/timeout transactions (`AssertTimeout`, `ChallengeTimeout`, `Disprove`) are dispatched exactly through this pipeline via `Duty`, a stuck pipeline can make a deadline-bound challenge/disprove/timeout transaction unconfirmable for the affected verifier/operator instance, which falls under the defined High-severity impact category ("a deadline-bound challenge/disprove/timeout transaction made unconfirmable"). This can, in the worst case, prevent an honest operator from being reimbursed in time or prevent a malicious kickoff from being disproved/challenged in time by that node, while other honest operators unrelated to the triggering event are also blocked.

### Likelihood Explanation
Likelihood is moderate: the exact matcher/handler code paths that can be pushed into an error state (`kickoff.rs`, `round.rs`) were not fully enumerated in this pass (11+ `capture_error`/`Err(eyre)` sites exist in `kickoff.rs`, not individually audited here), so it is not proven with certainty that an unprivileged party can always reach one of these error branches purely by submitting valid-looking but semantically wrong on-chain data (e.g. a malformed challenge/kickoff transaction that still matches a `BlockMatcher` pattern). This requires further code-level verification of `core/src/states/kickoff.rs` and `core/src/states/matcher.rs` to confirm a concrete unauthenticated trigger; the architecture-level flaw (fail-everything error propagation from `process_block_parallel`) is confirmed, but a fully concrete unprivileged PoC input was not located in the time available.

### Recommendation
Do not let a single kickoff or round state machine's processing error abort the whole `process_block_parallel`/`NewFinalizedBlock` pipeline. Isolate errors per machine (as is already partially done via `capture_error`), log/quarantine the offending machine, and continue advancing `next_height_to_process` and processing all other machines, similar to the recommended Ethereum consensus-spec behavior of skipping invalid deposits instead of erroring the whole state transition.

### Proof of Concept
Not fully constructed — this analysis identifies the architectural flaw (`core/src/states/mod.rs` `process_block_parallel`, `core/src/states/event.rs` `NewFinalizedBlock` handling) and shows that any per-machine error aborts global progress, but a concrete unprivileged-attacker transaction/witness that reliably drives one of the `kickoff.rs`/`round.rs` state handlers into an unhandled error branch was not conclusively identified within the scope of this review. Confirming this requires deeper reading of `core/src/states/kickoff.rs` and `core/src/states/matcher.rs` (specifically all `capture_error`/`unhandled_event`/`Err(eyre::...)` call sites) to determine whether any of them can be triggered by malformed or adversarial on-chain data from an unprivileged party.
