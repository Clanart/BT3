Confirmed: `placeOrder` explicitly rejects **duplicate output tokens** (transient-storage dedupe loop, `IntentGatewayV2.sol:165-179`) but performs **no equivalent check on `order.inputs`** (loop at `IntentGatewayV2.sol:281-298` just transfers and records each input by index, with no dedupe). Escrow is then keyed only by `(commitment, token address)` and additively summed across input indices, so two same-chain output legs that happen to share an input token address share one flat escrow balance instead of two isolated ones.

### Title
Same-chain intent fills can drain a co-located output pair's dedicated escrow via shared per-token accounting - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntentsBase._orders[commitment][token]` tracks escrow as a flat balance per `(commitment, token)`, additively funded from every `order.inputs[i]` entry regardless of index (`IntentGatewayV2.sol:281-298`). `placeOrder` dedupes `order.output.assets` but never dedupes `order.inputs`, so an order can legally contain two output pairs (`i`, `j`) that are backed by the *same* input token. When `IntrinsicIntents._fillSameChain` fully completes pair `i`, it releases `escrowedAmount = _orders[commitment][token]` — the **entire remaining balance for that token**, not the amount proportionally owed to pair `i` — draining collateral that was meant to be isolated for pair `j`.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:116-121`):
```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```
On a *full* completion of output leg `i`, the code does not compute "the input amount reserved for leg `i`" — it reads whatever total balance currently sits in `_orders[commitment][token]`. If `order.inputs[i].token == order.inputs[j].token` for some other leg `j` (allowed, since only `order.output.assets` duplicates are rejected at placement — `IntentGatewayV2.sol:165-179`), the two legs' escrow was summed into one bucket at placement time (`_orders[commitment][token] += reducedInputs[i].amount` per input, additive across indices with the same token). A solver who fully satisfies only leg `i`'s output requirement collects the *combined* escrow of legs `i` and `j`, while leg `j` remains open with `_filled[commitment]` deleted (`IntrinsicIntents.sol:140`, since `isFullyFilled` is false). When leg `j` is later filled, `_orders[commitment][token]` is already zero, so its `WithdrawalRequest` token entry carries `amount: 0` and is silently skipped in `_withdraw` (`IntentsBase.sol:397-398`, `if (amount == 0) continue;`) — no revert, no signal that leg `j`'s backing collateral is gone. The order's own accounting (`_partialFills`) treats each output token independently and correctly, but the underlying `_orders` escrow ledger does not respect that same per-leg isolation, exactly mirroring the referenced report's core flaw: a value meant to be partitioned per "pool" (here, per output leg) is instead pooled and consumable by any party that satisfies just one leg's condition.

### Impact Explanation
This is a direct loss/misallocation of escrowed user funds inside `IntentGatewayV2`/`IntrinsicIntents`, a production bridge contract holding user collateral. A solver can construct or select an order (or collude with the placer) with two output legs sharing an input token, fully satisfy the cheaper/easier leg, and walk away with escrow that was reserved for the other, still-unfilled leg. The user is left with an order that can never be honestly completed for the second leg (its collateral is gone) while having received only partial value, and the "excess" escrow was moved to an unentitled beneficiary — matching the bounty's "stealing or loss of funds" / "transaction manipulation" impact classes, entirely through an unprivileged, public entry point (`placeOrder` + `fillOrder`) with no relayer, prover, or admin involvement.

### Likelihood Explanation
`order.inputs` is fully attacker/user-controlled at `placeOrder` time and is never checked for duplicate token addresses, unlike `order.output.assets` which explicitly is (`IntentGatewayV2.sol:165-179`). Any user (or a solver instructing a user, since solvers often construct orders for users in intent-based UX) can place such an order, and any solver filling same-chain orders can trigger the drain simply by choosing to complete one leg before the other in a normal `fillOrder` call — no special privileges, timing races, or malicious relayer/prover assumptions are required.

### Recommendation
Track escrow per output-leg index (or per `(commitment, token, legIndex)`), not merely per `(commitment, token)`, so that legs sharing an input token cannot cannibalize each other's reserved collateral. Alternatively, reject orders whose `order.inputs` contain duplicate token addresses at `placeOrder`, matching the existing dedupe already applied to `order.output.assets`, and add an explicit accounting invariant check in `_fillSameChain` that the amount released for a fully-completed leg never exceeds `order.inputs[i].amount` minus what has already been proportionally released for that specific leg.

### Proof of Concept
1. User calls `placeOrder` with:
   - `inputs = [ {token: USDC, amount: 1000}, {token: USDC, amount: 1000} ]` (same token, two legs, not rejected — only `output.assets` duplicates are checked).
   - `output.assets = [ {token: DAI, amount: 100}, {token: WETH, amount: 1} ]` (distinct output tokens, passes the dedupe check).
   - Result: `_orders[commitment][USDC] = 2000` (additive across both input indices, `IntentGatewayV2.sol:281-298`).
2. Solver calls `fillOrder` providing `options.outputs = [ {token: DAI, amount: 100}, {token: WETH, amount: 0} ]` — fully satisfies leg 0 (DAI), supplies nothing for leg 1 (WETH), which is legal (partial fill semantics, `IntrinsicIntents.sol:76-79`).
3. In the loop, leg 0 hits `amountFilled == totalRequired` (100 == 100), so `escrowedAmount = _orders[commitment][USDC] = 2000` — the solver is credited the **entire 2000 USDC**, not the 1000 USDC that leg 0 alone was meant to release.
4. `_orders[commitment][USDC]` is now `0`. `isFullyFilled = false` (leg 1 still pending), so `_filled[commitment]` is deleted and the order stays open (`IntrinsicIntents.sol:136-142`).
5. A later solver (or the same one) fills leg 1 (WETH) fully; `escrowedAmount = _orders[commitment][USDC] = 0`, so the `WithdrawalRequest` entry for USDC carries `amount: 0` and is silently skipped in `_withdraw` — the user's second leg is fulfilled by the solver providing WETH, but the solver receives none of the USDC that was supposed to back leg 1, because it was already drained in step 3.

This flow was not run against a live fork; it is derived directly from the escrow bookkeeping shown in `IntentGatewayV2.sol:165-298` and `IntrinsicIntents.sol:54-149`, and the lack of an input-token dedupe check contrasted with the explicit output-token dedupe at `IntentGatewayV2.sol:165-179`.
