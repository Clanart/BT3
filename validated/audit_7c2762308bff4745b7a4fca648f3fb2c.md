This is exactly the "price moves between quote and execution, no slippage check" bug class from the report. Every other caller path lets the actual user choose `_minimumLiquidity` (`WombatPoolHelperV2.deposit`, `.depositNative`, `WombatPoolHelper.deposit`), but `WombatPoolHelperV2.depositFor` hardcodes it to `0`.

### Title
`depositFor` hardcodes zero slippage protection, allowing sandwich attacks that steal value from depositors - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.depositFor` lets any unprivileged caller deposit tokens on behalf of another address, but it calls the internal `_deposit` helper with `_minimumLiquidity` hardcoded to `0` instead of exposing it as a caller-supplied parameter, unlike every sibling deposit entrypoint in the same contract.

### Finding Description
`depositFor` pulls `_amount` of `depositToken` from `msg.sender` and forwards it to `_deposit(_amount, 0, _for, address(this))`: [1](#0-0) 
`_deposit` in turn calls `IWombatStaking(wombatStaking).deposit(lpToken, _amount, _minimumLiquidity, _for, _from)`: [2](#0-1) 
`WombatStaking.deposit` passes that `_minimumLiquidity` straight through to the underlying Wombat AMM pool's `deposit()` call, which determines the LP amount minted based on the pool's current `cash`/`liability` ratio — a value that any other depositor or withdrawer on that same Wombat pool can move within the same block: [3](#0-2) 
Because `depositFor` forces `_minimumLiquidity = 0`, there is no way for the caller to protect against price movement in the underlying pool, exactly the class of bug described in the report (a state-dependent price with no slippage check on the "buy" transaction). All other deposit entrypoints in the same contract (`deposit`, `depositNative`) correctly forward a user-supplied `_minimumLiquidity`: [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker can sandwich a `depositFor` call: front-run it with a large deposit/withdrawal on the same Wombat pool to push the cash/liability ratio unfavorably, let the victim's `depositFor` mint LP at the worse ratio (accepted unconditionally since minimum is 0), then reverse their own position afterward. The victim (`msg.sender` of `depositFor`) pays the full `_amount` of deposit tokens but the `_for` address receives a reduced amount of staking/receipt tokens, resulting in a direct, quantifiable loss of value for the depositor with no recourse — this is a direct theft of user funds via sandwich attack, not merely a UX inconvenience.

### Likelihood Explanation
`depositFor` is a public, unprivileged, permissionless entrypoint that anyone can call for any `_for` address at any time; the sandwich requires no special access, only ordinary transactions on the underlying Wombat pool, making this readily and repeatably exploitable whenever `depositFor` is used.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` and forward the caller-supplied value instead of hardcoding `0`, mirroring the pattern already used by `deposit` and `depositNative` in the same contract.

### Proof of Concept
1. Attacker observes a pending `depositFor(amount, victimFor)` transaction (mempool or bundle) targeting a Wombat pool where cash/liability is currently favorable.
2. Attacker front-runs with a large `deposit`/`withdraw` on the same underlying Wombat pool (via any other pool helper or router) that shifts the cash/liability ratio unfavorably.
3. The victim's `depositFor` executes with `_minimumLiquidity = 0`, so `IWombatPool.deposit()` mints a reduced `lpReceived` amount that WombatStaking's `deposit()` computes and mints as receipt tokens 1:1 to `_for`: [6](#0-5) 
4. Attacker back-runs, reversing their own deposit/withdrawal and capturing the value difference, while the depositor/`_for` address is left with fewer staked tokens than the amount paid would have gotten absent the sandwich.
