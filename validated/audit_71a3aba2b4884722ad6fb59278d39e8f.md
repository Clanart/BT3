The reported bug class (fee-on-transfer tokens breaking accounting because the contract assumes the transferred amount equals the received amount) has a direct, reachable analog in `WombatStaking.sol`.

### Title
Fee-on-transfer LP tokens break receipt-token accounting and cause insolvency in `WombatStaking.depositLP` - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking.depositLP()` mints receipt tokens and stakes to Master Wombat based on the caller-supplied nominal `_lpAmount` instead of the amount actually received after `safeTransferFrom`, unlike the sibling `deposit()` function which correctly measures the balance delta.

### Finding Description
In `WombatStaking.depositLP` [1](#0-0) , the contract transfers `_lpAmount` of `poolInfo.lpAddress` from `_for`, but never verifies how much it actually received:

```solidity
IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);
_toMasterWomAndSendReward(_lpAddress, _lpAmount, true);
IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);
```

If `poolInfo.lpAddress` (the LP/staking token registered for a pool via `registerPool`) is a fee-on-transfer token, the actual balance increase in `WombatStaking` is less than `_lpAmount`, yet:
1. `_toMasterWomAndSendReward` attempts to stake the full nominal `_lpAmount` to `masterWombat` via `_stakeToWombatMaster`, which approves and deposits `_lpAmount` — more than the contract actually holds. [2](#0-1) 
2. The receipt token is minted for the full nominal `_lpAmount`, permanently over-representing the depositor's real backing.

This contrasts with the correctly implemented `deposit()` function in the same contract, which measures `lpReceived` via before/after balance diff before minting receipt tokens and staking: [3](#0-2) . `depositLP` omits this check entirely.

The call path is reachable by an ordinary wallet through `WombatPoolHelper.depositLP()` / `WombatPoolHelperV2.depositLP()`, which forward the user-specified `_lpAmount` straight to `WombatStaking.depositLP()`: [4](#0-3) .

### Impact Explanation
If a fee-on-transfer token is ever registered as a pool's `lpAddress`, either:
- the inflated stake to `masterWombat` reverts (denial of service for that pool), or
- if it succeeds (e.g., insufficient allowance edge cases aside), the minted receipt-token supply permanently exceeds the LP tokens actually custodied/staked, causing insolvency: later legitimate depositors/withdrawers of that pool cannot redeem their share because the underlying LP balance is short. This matches "protocol insolvency" / "permanent freezing of funds" criteria.

### Likelihood Explanation
Likelihood depends entirely on whether a fee-on-transfer token is ever whitelisted as an `lpAddress` by `registerPool` (owner-controlled), so this is a latent risk rather than an immediately exploitable path for a standard already-supported pool (WOM LP tokens are not fee-on-transfer today). It is only reachable if such a token is added to the pool registry in the future, consistent with the original report's framing as "should a fee-on-transfer token be added."

### Recommendation
Mirror the pattern already used in `deposit()`: measure the actual LP token balance delta after `safeTransferFrom` in `depositLP`, and use that measured amount (not the caller-supplied `_lpAmount`) for staking to Master Wombat and for minting receipt tokens.

### Proof of Concept
1. Owner registers a pool whose `lpAddress` is a fee-on-transfer token (e.g. via `registerPool`).
2. User calls `WombatPoolHelper.depositLP(_lpAmount)` → `WombatStaking.depositLP(_lpAddress, _lpAmount, _for)`.
3. `safeTransferFrom` moves `_lpAmount` nominally, but `WombatStaking` receives `_lpAmount - fee`.
4. `_toMasterWomAndSendReward` and `_stakeToWombatMaster` attempt to approve/deposit the full nominal `_lpAmount` to `masterWombat`, exceeding actual holdings.
5. `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` mints receipt tokens exceeding the real LP backing, breaking 1:1 redemption guarantees for subsequent withdrawers.
