### Title
Working-directory "Open File" action skips the `resolveWithin` symlink/traversal guard used elsewhere for repo-relative paths - (File: `app/src/ui/changes/sidebar.tsx`)

### Summary
Desktop hardened repo-relative path handling with a dedicated `resolveWithin()` helper that resolves a path against the repository root using `realpath` and rejects it if the resolved target escapes the root (guarding specifically against symlink-based traversal). This guard is deliberately applied to deep-link file opening (`openRepositoryFromUrl`) and to conflict-file reading (`buildConflictContext`), but the semantically identical "Open File" action for a working-directory change in the Changes sidebar builds the same kind of repo-relative path with a bare `Path.join` and no containment check before handing it to the shell to open.

### Finding Description
`resolveWithin()` is the invariant Desktop relies on to guarantee that a repository-relative path (which is attacker-influenced content coming from a cloned/fetched repository) cannot resolve, via `..` segments or a symlinked directory, to a location outside the repository working directory: [5](#0-4) 

This is used for the "open file from URL" deep-link flow: [2](#0-1) 

and for reading conflict file contents during Copilot conflict resolution: [6](#0-5) 

However, the "Open File" context-menu action in the Changes sidebar — which also derives its path from repo-relative, potentially attacker-controlled data (`file.path`, sourced from the working directory status of a cloned repository) — builds the full path with plain `Path.join` and passes it directly to `openFile`, with no `resolveWithin` (or any other containment) check: [3](#0-2) 

`openFile` then hands the resulting path straight to the OS shell as a `file://` URL: [4](#0-3) 

Because git working trees can contain symlinked directories (tracked as symlink blobs), a malicious repository can include a directory entry that is a symlink pointing outside the repository (e.g., to a sensitive folder or an executable elsewhere on disk). A file that appears to live inside that symlinked directory will still have a repo-relative `path` string like `evil-dir/payload.exe`, which `Path.join(repository.path, path)` will lexically resolve to something that *looks* contained under the repo root but that the OS/filesystem will actually resolve, through the symlink, to a location outside the repository. This is exactly the attack scenario the codebase's own test suite for `resolveWithin` documents and defends against: [7](#0-6) 

Since the sidebar's "Open File" path does not call `resolveWithin`, it does not benefit from that protection, breaking the invariant that all repo-relative, attacker-influenced paths are validated to stay within the repository before being touched by the shell — the same class of inconsistency as the `initiateBurn`/`initiateBurnBatch` bug, where one code path enforces a security-relevant check and a parallel, similarly-purposed code path omits it.

### Impact Explanation
An attacker who controls a cloned/fetched repository can plant a symlinked directory containing a file, causing Desktop's "Open File" action to invoke the OS shell (`shell.openExternal`) on a path that physically resolves outside the repository. Depending on the target and the OS's file-association handling, this can result in launching an arbitrary executable or opening files the user never intended to open, i.e., code execution or disclosure outside the intended repository boundary — squarely in the accepted impact category (cloned/fetched repo content leading to execution/file access outside the repo).

### Likelihood Explanation
Requires the victim to clone or fetch a malicious repository and then explicitly use the "Open File" context menu action on a changed file that lives under the attacker-planted symlinked directory — a normal, expected Desktop workflow (reviewing/opening changed files), not an unnatural user step. No admin rights, local access, or prior malware are needed; the trigger is entirely repository content plus a single ordinary click, making this a realistic (Medium) likelihood path, consistent with why the project already hardened the equivalent deep-link and conflict-file-read code paths with `resolveWithin` but missed this one.

### Recommendation
Route the working-directory "Open File" (and any sibling "Reveal in File Manager"/"Open With…" actions that build paths the same way) through `resolveWithin(repository.path, path)` exactly as `openRepositoryFromUrl` and `buildConflictContext` do, rejecting the action (with a log/error, mirroring the deep-link handler) whenever the resolved real path does not stay within the repository root.

### Proof of Concept
1. Attacker creates a git repository containing a symlink entry `evil` pointing to `/` (or to a directory holding a payload executable), and a change under `evil/payload.exe` recorded relative to the symlinked path (achievable because git tracks symlinks as blobs and will materialize them on checkout).
2. Victim clones/fetches this repository in GitHub Desktop; the working directory now contains the symlink `evil` -> `/`.
3. Desktop's Changes list shows `evil/payload.exe` as a file (e.g., untracked/new).
4. Victim right-clicks it and selects "Open File" (`onOpenItem` in `app/src/ui/changes/sidebar.tsx`), which does `Path.join(repository.path, 'evil/payload.exe')` and calls `openFile`.
5. `openFile` calls `shell.openExternal('file://' + fullPath)`; the OS resolves the symlink and opens/executes the file at the real, outside-of-repo target — with no `resolveWithin` check ever having run, unlike the equivalent deep-link and conflict-resolution code paths.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
