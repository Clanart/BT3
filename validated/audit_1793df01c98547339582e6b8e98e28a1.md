### Title
Generator promotion drops existing key scalar and offset - (crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` constructs the promoted `ThresholdKeys` from the original secret share, interpolation, and promoted verification shares, but creates a fresh `ThresholdKeys` object whose scalar and offset reset to `1` and `0`. Any ephemeral linear combination present on the input keys is therefore lost during promotion.

### Finding Description
`ThresholdKeys::scale` and `ThresholdKeys::offset` maintain current key-derivation state in the key object's `scalar` and `offset` fields. However, `GeneratorPromotion::complete` calls `ThresholdKeys::new` and supplies only the base parameters, interpolation, original secret share, and promoted verification shares. It does not reapply `base.current_scalar()` or `base.current_offset()`.

The proof itself is also bound to `base.original_group_key()` and `base.original_secret_share()`, not the tweaked group key/share. Consequently, promotion of a tweaked key silently produces keys for the untweaked group rather than preserving the previous derivation state.

Relevant code:

- `ThresholdKeys::scale` multiplies both scalar and offset: `crypto/dkg/src/lib.rs`
- `ThresholdKeys::offset` adds to the existing offset: `crypto/dkg/src/lib.rs`
- `ThresholdKeys::new` initializes `scalar` to `ONE` and `offset` to `ZERO`: `crypto/dkg/src/lib.rs`
- `GeneratorPromotion::complete` returns a fresh `ThresholdKeys` without restoring those values: `crypto/dkg/promote/src/lib.rs`

### Impact Explanation
This can silently change the effective group key after generator promotion. A caller promoting keys that were previously scaled or offset will obtain shares for a different group key than intended. If the promoted keys represent an externally derived account or wallet key, signatures are produced for the untweaked key instead of the expected tweaked key. Funds sent under the expected post-promotion tweaked identity may be unspendable by the promoted key set.

### Likelihood Explanation
The flaw is deterministic and reachable through the public `GeneratorPromotion::complete` API. Supplying valid proofs from all other participants triggers construction of the promoted key, while the input key's current scalar and offset are discarded. It only affects workflows that promote keys after applying a scale or offset, but such linear combinations are an explicitly supported feature of `ThresholdKeys`.

### Recommendation
Preserve the complete linear combination during promotion. After constructing the promoted `ThresholdKeys`, reapply the input key's `current_scalar()` and `current_offset()`, or construct an internal equivalent that retains them. Add a regression test that applies `.scale(...)` and `.offset(...)`, promotes the key, and verifies that `group_key()`, secret-share reconstruction, and signing use the same effective key before and after promotion.

### Proof of Concept
Conceptually:

1. Create `base: ThresholdKeys<C1>`.
2. Apply a nonzero tweak:
   ```rust
   let tweaked = base.offset(offset);
   let expected_group_key = tweaked.group_key();
   ```
3. Run `GeneratorPromotion::<C1, C2>::promote(rng, tweaked)`.
4. Complete promotion with valid proofs from every other participant.
5. Observe that the returned `ThresholdKeys<C2>` has scalar `ONE` and offset `ZERO`, so its `group_key()` corresponds to the original untweaked key rather than the generator-promoted equivalent of `expected_group_key`.

The concrete defect is the fresh construction in `GeneratorPromotion::complete`, where `ThresholdKeys::new` resets scalar and offset and no code restores `base.current_scalar()` or `base.current_offset()`.
