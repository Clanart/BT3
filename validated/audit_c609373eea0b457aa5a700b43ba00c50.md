### Title
`CallDispatcher` has a payable `receive()` but no withdraw/sweep function, permanently locking ETH left over from arbitrary calldata execution triggered by cross-chain messages - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a shared singleton used by multiple bridge apps (`IntentGatewayV2`/`IntentsBase`, `WrappedHyperFungibleToken`, `HyperFungibleToken`) to execute arbitrary attacker/solver/relayer-supplied calldata on behalf of orders and cross-chain messages. It accepts ETH via `receive()` and forwards `call.value` to target contracts during `dispatch()`, but the contract has **no withdraw, sweep, or owner-controlled recovery function at all**. Any native token that ends up sitting on the `CallDispatcher` balance (e.g. slippage refunds, dust, or a target contract returning native value to `msg.sender` instead of a specified recipient) is permanently unrecoverable, exactly matching the External Report's bug class (`TokenVesting`'s payable `receive`/`fallback` with no way to withdraw stuck ETH).

### Finding Description
`CallDispatcher.sol` defines: [1](#0-0) 

It has a `receive() external payable {}` to accept ETH transfers and a `dispatch()` function that loops over caller-supplied `Call[]` and forwards `call.value` to each target. There is no `withdraw`, `sweep`, `rescue`, or any privileged function anywhere in the contract to move out ETH (or ERC-20) that accumulates on its own balance.

Contrast this with `IntentsBase._execute`, which uses the same `CallDispatcher` for order-output calldata but explicitly accounts for and sweeps any residual dispatcher balance back to the calling gateway after every execution: [2](#0-1) 

That sweep (via a follow-up self-call routed back through `dispatch()`) is the only mechanism in the codebase that recovers ETH left in `CallDispatcher`, and it is bespoke to `IntentsBase`'s own call sites. Other consumers of the same singleton `CallDispatcher` do not replicate this pattern. `WrappedHyperFungibleToken.onAccept` and its upgradeable variant dispatch attacker/sender-controlled `message.data` through the dispatcher with no subsequent balance check or sweep: [3](#0-2) 

Because `CallDispatcher` is a single shared contract instance referenced by `_dispatcher`/`params.dispatcher` across `IntentGatewayV2`, `WrappedHyperFungibleToken`, and `HyperFungibleToken`, any native-value dust left on it by one app's calldata execution (e.g. a DEX route in an intent's `output.call` that returns unspent ETH to `msg.sender` == `CallDispatcher`, or a target contract that refunds excess value to the caller) sits on the dispatcher's balance forever if the executing app does not perform its own sweep. There is no owner, admin, or governance-gated function on `CallDispatcher` itself capable of recovering it — the contract has zero access control and zero withdrawal surface.

### Impact Explanation
Native token value belonging to users/solvers can become permanently locked with no recovery path, since `CallDispatcher` is a shared, stateless utility contract with no owner and no withdrawal function. Given it backs value-moving flows for intents (solver-provided arbitrary calldata routed through DEXes/lending protocols) and cross-chain token transfers with attached calldata, any accidental or protocol-level residual ETH is unrecoverable — a direct, permanent loss-of-funds condition matching the required "stealing or loss of funds" impact class.

### Likelihood Explanation
Low-to-moderate: it requires a calldata execution path (via `IntentsBase._execute` composability, or `WrappedHyperFungibleToken`/`HyperFungibleToken` message-attached calldata) where a downstream call returns native value to `msg.sender` (the `CallDispatcher`) rather than to the intended final recipient, or a direct mistaken ETH transfer to the dispatcher's address. This is plausible in real solver-routed DEX integrations (e.g., routers that refund excess ETH to caller) and does not require a malicious relayer, prover, or admin — only ordinary usage of the composable calldata-execution feature.

### Recommendation
Add an access-controlled `sweep`/`withdraw` function to `CallDispatcher` (or make it non-payable and remove `receive()` if ETH is never meant to rest there), so that ETH (and ERC-20 dust) sitting on its balance can always be recovered by the calling application or a governance-controlled beneficiary, mirroring the sweep logic already implemented in `IntentsBase._execute`/`_sweepDust` for every code path that routes value through the shared dispatcher.

### Proof of Concept
1. A cross-chain transfer arrives at `WrappedHyperFungibleToken.onAccept` with non-empty `message.data` encoding a `Call[]` that instructs `CallDispatcher` to call a DEX router contract, e.g. to swap part of the transferred tokens.
2. The router call executes; the router refunds unspent/leftover native ETH by sending it back to `msg.sender`, which from the router's perspective is `CallDispatcher` (since `CallDispatcher.dispatch()` is the direct caller).
3. `CallDispatcher`'s `receive() external payable {}` accepts this ETH silently; execution of `dispatch()` completes successfully.
4. `WrappedHyperFungibleToken.onAccept` returns without inspecting or sweeping `CallDispatcher`'s balance (unlike `IntentsBase._execute`, which performs an explicit dust-sweep call after every calldata execution).
5. The ETH now sits permanently on `CallDispatcher`. Because the contract exposes no `withdraw`/`sweep`/owner function anywhere in `evm/src/utils/CallDispatcher.sol`, it can never be recovered by the user, the app, or governance — permanent loss of funds.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
