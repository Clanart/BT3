### Title
`EnsureInstalled` resolves and exposes an installed shop's offline session/API access purely from the unauthenticated `shop` query parameter, allowing cross-shop data/action access - ([File: app/controllers/concerns/shopify_app/ensure_installed.rb])

### Summary
`ShopifyApp::EnsureInstalled#current_shopify_domain` derives the "authenticated" shop solely from the attacker-controllable `params[:shop]`, and `#installed_shop_session` looks up that shop's stored offline access-token session with no verification that the request actually originates from that shop (no HMAC, no session/ID token, no cookie). This session is not merely used for "install-check redirects" — it is actively used to make an authenticated Shopify Admin API call (`validate_non_embedded_session`) and is exposed to controller actions (e.g. via `@shop`/`current_shopify_domain`) as the documented "unauthenticated" boundary is explicitly acknowledged in the project's own docs, warning developers not to use this concern for data access — confirming the risk is real and left to the app author to avoid.

### Finding Description
The concern's before_action chain is: [1](#0-0) 

`current_shopify_domain` trusts `params[:shop]` directly (only sanitized for format, not verified for authenticity): [2](#0-1) 

`installed_shop_session` then fetches the victim's stored offline session purely by that unverified domain: [3](#0-2) 

`check_shop_known` assigns this victim session to `@shop`, which is then available to the actual controller action: [4](#0-3) 

Critically, `validate_non_embedded_session` uses that victim session to make a real, authenticated Shopify Admin REST API call (`GET /shop`) with the victim's access token whenever the request is not flagged as `loaded_directly_from_admin?` (i.e., `embedded=1` not present or app not configured as embedded): [5](#0-4) 

This is corroborated by the test suite, which explicitly asserts that an unauthenticated `GET` with only `shop=shop1.myshopify.com` results in `ShopifyAPI::Clients::Rest::Admin.new(session: session)` and `client.get` being invoked, returning `:ok`: [6](#0-5) 

No CSRF token, HMAC, session/ID token, or cookie is required to reach this path — `check_shop_domain` only requires a syntactically valid `shop` param: [7](#0-6) 

Once past these before_actions, the controller's own `index`/action code runs with `@shop`/`current_shopify_domain` set to the victim shop. The bundled generator template for a "home controller" using `EnsureInstalled` demonstrates the intended (safe) usage — only assigning `@shop_origin = current_shopify_domain` for frontend bootstrap, not for data access: [8](#0-7) 

However, the docs explicitly and prominently warn that this concern does **not** authenticate the request and must not be used to gate access to shop data or Shopify API calls — which is a strong signal that the maintainers are aware unsafe usage in a real app's action code (any override that calls Shopify APIs or renders shop data based on `current_shopify_domain`/`@shop`) would constitute exactly this vulnerability: [9](#0-8) 

### Impact Explanation
Scoped impact is cross-shop access-token misuse: an attacker who knows/guesses a victim's installed shop domain can force the app server to use the victim's stored offline access token to call the Shopify Admin API (`validate_non_embedded_session`), and can drive any `EnsureInstalled`-only controller action into operating in the victim shop's context (`@shop`, `current_shopify_domain`) without any proof of legitimate access. If any app code path built on top of `EnsureInstalled` (rather than `EnsureHasSession`) uses `installed_shop_session`/`current_shopify_domain` to fetch or render shop-specific data (a realistic and, per the docs' explicit warning, anticipated misuse), this results in unauthorized cross-shop data exposure or unauthorized use of the victim's access token — mapping to Shopify's "Authentication Bypass" / "Broken Access Control" impact class (cross-shop/cross-tenant data access via a mis-scoped session).

### Likelihood Explanation
Preconditions are minimal: the victim shop must have previously installed the app (very common), and the attacker needs only the shop's `myshopify.com` domain, which is often guessable/enumerable (shop names are frequently public storefront domain-derived) or discoverable via other channels. No secrets, tokens, or insider access are required — this is reachable by any anonymous HTTP client. The library ships `EnsureInstalled` as a public, documented concern for direct inclusion, and the bundled `unauthenticated_home_controller.rb` generator template demonstrates it is meant to be used in real apps' top-level entry controllers, exactly the surface reachable by attacker-controlled `shop` params. The remaining risk is contingent on individual app developers correctly restricting `EnsureInstalled` usage to non-data-serving actions, which the framework does not enforce.

### Recommendation
- Do not expose `installed_shop_session`/`current_shopify_domain` results for any purpose beyond install-check redirects; consider renaming/documenting them more strongly as "unverified" to discourage misuse (partially done in docs already).
- Ideally, `validate_non_embedded_session`'s API call using an unverified shop param's session should be reconsidered — an attacker can trigger arbitrary Admin API calls (`GET /shop`) against a victim's token merely by supplying `shop=victim` with no other credential, which itself is an unauthorized use of the token (rate-limit consumption, foot-printing) even absent a data-rendering action.
- Add a lint/runtime guard (e.g., raising if `EnsureInstalled`-only controllers attempt to instantiate `ShopifyAPI::Clients::Rest::Admin` inside action code) or require id_token/HMAC verification before allowing any Admin API call, even the internal validation ping.

### Proof of Concept
Using the existing test pattern in `test/controllers/concerns/ensure_installed_test.rb`, add an assertion that action code has access to victim session/API calls with zero auth material:

```ruby
test "attacker with only a shop param triggers Admin API call using victim's stored session" do
  victim_session = mock
  ShopifyApp::SessionRepository.stubs(:retrieve_shop_session_by_shopify_domain).returns(victim_session)

  client = mock
  ShopifyAPI::Clients::Rest::Admin.expects(:new).with(session: victim_session).returns(client)
  client.expects(:get).with(path: "shop") # attacker-triggered authenticated API call

  # No cookies, no HMAC, no id_token, no CSRF token supplied by "attacker"
  get :index, params: { shop: "victim-shop.myshopify.com" }

  assert_response :ok # controller action runs in victim shop's context
end
```

This mirrors the repo's own existing test [6](#0-5)  confirming that a bare `GET` with an attacker-supplied `shop` param for an already-installed victim causes an authenticated Admin API call using the victim's session and lets the controller action execute in that shop's context — validating the described attack path.

class HomeController < ApplicationController

    if ShopifyAPI::Context.embedded? && (!params[:embedded].present? || params[:embedded] != "1")
      embedded_app_url = safe_embedded_app_url(params[:host])
      redirect_url = embedded_app_url ? embedded_app_url + request.path : ShopifyApp.configuration.root_url
      redirect_to(redirect_url, allow_other_host: true)
    else
      @shop_origin = current_shopify_domain
      @host = params[:host]
    end
  end

## EnsureInstalled — Installation Check Only
Use this concern to verify that the app has been installed on a given shop. It is designed for unauthenticated entry points in embedded apps, such as serving the app shell or redirecting to OAuth.

> ⚠️ **This concern does not authenticate the request.** The shop is resolved from the `shop` query string parameter, which is user-controllable. Do not use this concern to gate access to shop data, access tokens, or Shopify API calls. For authenticated actions, use `EnsureHasSession`.

If the app is not installed for the provided `shop` parameter, the request will be redirected to login or the `embedded_redirect_url`.
