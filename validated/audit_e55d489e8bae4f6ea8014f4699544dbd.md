### Title
Argument injection via unsanitized GitHub API `clone_url` passed to `git remote add` / `git remote set-url` - (File: `app/src/lib/git/remote.ts`)

### Summary
`addRemote` and `setRemoteURL` build the git subprocess argv by directly splicing a caller-supplied URL string, with no `--` end-of-options marker and no check that the value doesn't start with `-`. `updateRemoteUrl` feeds this function with `apiRepo.clone_url` — a field taken verbatim from a GitHub API response object — after only checking protocol/hostname *equality*, never checking that the value is option-safe. This mirrors the smart-contract bug's pattern: a "safe" caller path exists, but the underlying primitive it calls performs no independent validation, so any caller (or attacker-controlled data reaching that caller) can smuggle option-like values straight into the git argv.

### Finding Description
`setRemoteURL` and `addRemote` construct git argv like this: [1](#0-0) [2](#0-1) 

Neither function inserts a `--` separator before the user-controlled `url` argument, and neither validates that `url` doesn't begin with `-`. This is inconsistent with other git wrappers in the same codebase area (`diff.ts`, `checkout.ts`, `reset.ts`, `apply.ts`, etc.) which explicitly insert `'--'` before untrusted path/ref arguments to prevent option injection — the same defensive pattern is simply missing here, just like `setParameter` in the original report bypassed the guard that `setCap` enforced.

`setRemoteURL` is reachable with attacker-influenced data through `updateRemoteUrl`, which is invoked whenever GitHub Desktop refreshes a repository's association with its GitHub API record: [3](#0-2) 

The only checks performed are: (1) the remote isn't null, (2) the URL protocol of the old and new URL match, and (3) the previously-stored clone URL for the GitHub repository still matches the current remote. None of these checks inspects the *content* of `apiRepo.clone_url` for characters like a leading `-` that would be interpreted by `git remote set-url` as a flag (e.g. `--delete`, `--push`) instead of a URL. The value `apiRepo.clone_url` originates from a GitHub API response object, which is attacker-influenced whenever the app is dealing with a repository hosted or forked from a source not fully controlled by the legitimate maintainer (e.g. via `_convertRepositoryToFork`, which passes `fork.clone_url` from an `IAPIFullRepository` directly into `setRemoteURL`): [4](#0-3) 

Because none of the call sites (`updateRemoteUrl`, `_convertRepositoryToFork`, `_setRemoteURL`) nor `remote.ts` itself sanitize or bound the URL string, a value such as `-o ProxyCommand=...`-style or a bare `--<flag>` string reaching `git remote add`/`git remote set-url` is passed through unfiltered as a raw argv element to the `git` subprocess.

### Impact Explanation
`git remote set-url`/`git remote add` accept flags like `--push`, `--add`, and `--delete` (`set-url`) or `-f`/`--tags`/`--mirror` (`add`). If the API-provided "clone URL" (or the last IPC-forwarded fork URL) is option-like rather than a real URL, git's option parser can interpret it as a flag instead of a positional URL argument, silently corrupting the resulting remote configuration (e.g., deleting a push URL, forcing an immediate fetch with unexpected flags, or setting the mirror/tags behavior) without any user-visible confirmation — corrupting what the user believes is being fetched/pushed, consistent with the "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
The trigger requires only that a GitHub API repository object (or fork object) returned to the client contain an attacker-influenced `clone_url` field, which the report's "Valid Impact" section explicitly allows ("attacker controls ... a GitHub API object"). No local access, admin rights, or social engineering is needed — the corruption happens automatically as part of the normal repository-refresh/fork-conversion flow whenever GitHub Desktop calls `updateRemoteUrl` or `_convertRepositoryToFork`.

### Recommendation
- In `app/src/lib/git/remote.ts`, insert a `'--'` separator before the `url` argument in both `addRemote` and `setRemoteURL` (matching the pattern already used in `diff.ts`, `checkout.ts`, etc.), or explicitly reject/escape URLs beginning with `-`.
- In `updateRemoteUrl` and `_convertRepositoryToFork`, validate that `apiRepo.clone_url`/`fork.clone_url` parses as a well-formed git URL before forwarding it to `setRemoteURL`.

### Proof of Concept
1. Simulate a GitHub API response (or a forked repository object) where `clone_url` is set to an option-like string, e.g. `--delete`, matching the protocol of the existing remote so `updateRemoteUrl`'s guard passes: [5](#0-4) 
2. Trigger a repository refresh (or fork conversion) so `updateRemoteUrl`/`_convertRepositoryToFork` calls `gitStore.setRemoteURL(name, '--delete')`.
3. `setRemoteURL` executes `git remote set-url <name> --delete`, which git interprets as the `--delete` flag rather than a URL, silently altering/removing the remote's configured URL(s) instead of setting a new fetch/push URL. [6](#0-5)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  public async _convertRepositoryToFork(
    repository: RepositoryWithGitHubRepository,
    fork: IAPIFullRepository
  ): Promise<Repository> {
    const gitStore = this.gitStoreCache.get(repository)
    const defaultRemoteName = gitStore.defaultRemote?.name
    const remoteUrl = gitStore.defaultRemote?.url
    const { endpoint } = repository.gitHubRepository

    // make sure there is a default remote (there should be)
    if (defaultRemoteName !== undefined && remoteUrl !== undefined) {
      // update default remote
      if (await gitStore.setRemoteURL(defaultRemoteName, fork.clone_url)) {
        await gitStore.ensureUpstreamRemoteURL(remoteUrl)
        // update associated github repo
        return this.repositoriesStore.setGitHubRepository(
          repository,
          await this.repositoriesStore.upsertGitHubRepository(endpoint, fork)
        )
      }
    }
    return repository
  }
