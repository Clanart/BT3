### Title
Out-of-bounds atom-length dereference in `is_atom_canonical`/`is_clvm_canonical` before bounds checking - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` and its caller `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` walk a submitter-controlled CLVM byte buffer (`puzzle_reveal`/`solution` bytes from a spend bundle) by repeatedly indexing `clvm_buffer[offset]` and incrementing `offset`, without ever checking `offset` against `len(clvm_buffer)` before dereferencing it. This mirrors the libdwarf `_dwarf_decode_s_leb128_chk()` bug class (CVE-2017-9054): a length-prefix/continuation-style decoder that dereferences the next byte before validating that the byte is actually within the buffer.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads the length-prefix bits from `clvm_buffer[offset]` and then, for `prefix_len` in `{0..5}`, does: [1](#0-0) 
```
atom_len = b & mask
for i in range(prefix_len):
    atom_len <<= 8
    offset += 1
    atom_len |= clvm_buffer[offset]

return 1 + prefix_len + atom_len, atom_len >= min_value
```
There is no check that `offset + prefix_len < len(clvm_buffer)` before `clvm_buffer[offset]` is dereferenced inside the loop. Its caller, `is_clvm_canonical()`, drives `offset` forward across the whole buffer in a `while True` loop and also indexes `clvm_buffer[offset]` at the top of every iteration without confirming `offset < len(clvm_buffer)`: [2](#0-1) 

Both functions rely purely on Python's built-in `IndexError` for `bytes` objects to stop out-of-range access — there is no explicit bounds check comparable to the length checks used elsewhere in the codebase (e.g. `skip_bytes`/`skip_list` in `chia/full_node/full_block_utils.py`, which explicitly compare `n > len(buf)` before slicing): [3](#0-2) 

For a Python `bytes`/`bytearray` object, `clvm_buffer[offset]` for out-of-range `offset` raises `IndexError` rather than reading adjacent heap memory, so in CPython this does not directly reproduce a memory-disclosure/heap-overread like the original libdwarf C bug. The dangerous pattern (dereference-before-bounds-check) is structurally identical, but its concrete impact here is an unhandled Python exception rather than memory corruption.

### Impact Explanation
If reachable with attacker-supplied buffers that are shorter than what the decoder expects (e.g. a truncated multi-byte atom-length prefix, or trailing high-bit bytes with no following pair/atom terminator), `is_atom_canonical`/`is_clvm_canonical` raise an uncaught `IndexError` instead of returning a controlled "not canonical" result. Depending on how/where these functions are invoked in mempool admission for dedup-eligible spends, this could cause an unhandled exception during spend-bundle processing — a mempool-manager crash/DoS path rather than any memory corruption, coin-set divergence, or asset-forgery impact. I was not able to fully confirm the exact call sites and exception-handling wrapper around `is_clvm_canonical()` from mempool admission (only definitions and test usages were found in the available index), so I cannot confirm whether callers already catch this exception, which would neutralize the impact entirely.

### Likelihood Explanation
An unprivileged spend-bundle submitter fully controls the raw puzzle_reveal/solution bytes passed into CLVM canonical-encoding checks, so triggering a malformed/truncated multi-byte atom length prefix is trivial to construct. However, whether this path is invoked unconditionally during mempool admission (vs. only for an optional/opt-in dedup check) is not confirmed from the available context, and it is plausible the call sites already wrap this in a try/except or validate buffer length beforehand.

### Recommendation
Add explicit length checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (verify `offset + prefix_len < len(clvm_buffer)` before the loop, mirroring the `n > len(buf)` pattern already used in `chia/full_node/full_block_utils.py`), and add an equivalent check at the top of the `while True` loop in `is_clvm_canonical()` before indexing `clvm_buffer[offset]`. Return `False`/raise a well-defined `ValueError` on truncated input rather than allowing an `IndexError` to propagate.

### Proof of Concept
Not able to fully confirm exploitability end-to-end without more visibility into the exact mempool-admission call path and any surrounding exception handling for `is_clvm_canonical()`. Conceptually:
```python
from chia.full_node.mempool_manager import is_clvm_canonical
# 0xf8 signals a 4-byte length prefix (5 total prefix bytes) but buffer is truncated
is_clvm_canonical(b"\xf8\x00\x00")  # expected to raise IndexError instead of returning False
```
This would need to be confirmed against the actual mempool_manager call sites (only 2 additional matches found beyond the definitions, not fully inspected) to determine if it's reachable from `push_tx`/spend-bundle admission without prior exception handling.

def skip_bytes(buf: memoryview) -> memoryview:
    if len(buf) < 4:
        raise ValueError(f"byte length prefix requires 4 bytes, remaining buffer {len(buf)}")
    n = int.from_bytes(buf[:4], "big", signed=False)
    buf = buf[4:]
    if n > len(buf):
        raise ValueError(f"byte length {n} exceeds remaining buffer {len(buf)}")
    return buf[n:]
