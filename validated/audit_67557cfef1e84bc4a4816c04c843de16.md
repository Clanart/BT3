### Title
Large-diff review-suppression threshold lets attacker-controlled content bypass commit/PR diff review, causing silent inclusion of unreviewed changes - (File: app/src/lib/git/diff.ts, app/src/ui/diff/index.tsx)

### Summary
The reported bug's underlying pattern is a "checked only above/below an attacker-tunable threshold" invariant: `GluexRouter.swap` only charges `routingFee` when `routeOutputAmount` exceeds `desc.effectiveOutputAmount`, so an attacker can set `effectiveOutputAmount` low and slip under the fee-triggering boundary. The closest real analog in GitHub Desktop is the diff-rendering size gate in `isDiffTooLarge`/`buildDiff` [1](#0-0) [2](#0-1) , which is a review/safety gate that a repository owner (attacker) fully controls the trigger for, and whose "safe" branch (suppressing diff rendering) silently removes the user's ability to review content before it's committed/pushed or acted on.

### Finding Description
`isDiffTooLarge` flips a diff to `DiffType.LargeText` the moment **any single line** in the diff exceeds `MaxCharactersPerLine` (5000 characters) [3](#0-2) [1](#0-0) . This check is per-line and applies to the *entire file's diff*, not just the offending hunk — so a single pathologically long line anywhere in a file is enough to collapse the whole file's diff into an unrendered placeholder.

When this happens, `buildDiff` returns an `ILargeTextDiff` instead of a normal `ITextDiff` [4](#0-3) , and the UI renders a placeholder panel instead of the actual diff content by default, requiring an explicit "Show Diff" click to reveal anything [5](#0-4) . Just like the `effectiveOutputAmount` threshold, this is a value (line length) that is entirely attacker-controlled when the "attacker" is the author of a branch, PR, or upstream commit the victim fetches/checks out/merges — the same "controls a cloned/fetched repository" primitive named in scope.

Crucially, staging/selection of changes for a file in Desktop's working directory model is independent of whether its diff was ever rendered/expanded: files are, by default, fully selected for commit (`DiffSelectionType.All`) the moment they appear as changed, regardless of whether the user opened/expanded the diff. This means an attacker who lands a change with one long line can smuggle unrelated, small, malicious edits into the same file — a config change, a build script tweak, a CI file edit — and the reviewer/committer will see only "The diff is too large to be displayed by default," never the actual line-level content, while the file is still fully staged and gets committed/pushed as-is if the user proceeds without clicking "Show Diff." This mirrors the report's core flaw precisely: an attacker-tunable value crossing a threshold silently short-circuits a safety/review mechanism, and the "else" branch (no fee / no visible diff) is the one that lets the bad outcome (fee evasion / unreviewed commit) through.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": a user reviewing incoming changes (e.g. before amending, cherry-picking, or during merge/rebase conflict review, or scanning a fetched branch before pushing it onward) can be made to believe a file has no meaningfully reviewable change, when in fact it contains attacker-chosen content that never gets rendered unless "Show Diff" is manually clicked. Since staging state is decoupled from diff visibility, the file's changes are committed/pushed in full regardless of whether the placeholder was expanded.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to actually proceed to commit/push without clicking "Show Diff" on a file flagged as too large, which is a plausible but not guaranteed workflow, especially for larger files/PRs where users are conditioned to skip past size warnings. The trigger (a single line > 5000 characters) is trivial for any attacker who controls a commit, branch, or fork the victim interacts with in Desktop, and it requires no special permissions, malware, or credentials.

### Recommendation
Only elide/collapse the specific hunk(s) containing overlong lines rather than suppressing the entire file's diff, or clearly enumerate which hunks are hidden versus shown so a small malicious change can't hide behind one long, unrelated line. Consider tying "Show Diff"/expansion state to a required acknowledgment before allowing a flagged file to be staged/committed at full selection, and audit other size/threshold gates (`MaxDiffBufferSize`, `MaxReasonableDiffSize`, `MaxHighlightContentLength`) for the same "whole file hidden by one outlier value" behavior.

### Proof of Concept
1. Attacker creates a commit/branch that modifies a target file with two changes: (a) a small malicious edit (e.g., in a script or config the victim will later run/trust), and (b) an unrelated line padded to > 5000 characters (e.g., a long comment or minified blob) anywhere else in the same file.
2. Victim fetches/checks out or merges this branch in GitHub Desktop and opens the file in the Changes view.
3. `isDiffTooLarge` detects the long line and `buildDiff` returns `DiffType.LargeText` for the whole file [2](#0-1) ; the UI shows only "The diff is too large to be displayed by default" with a "Show Diff" button [5](#0-4) .
4. The file remains fully selected for commit by default; the victim commits/pushes without clicking "Show Diff," never seeing the malicious edit (a) even though it is far below any actual size limit and would have been trivially visible in a normal diff.

```typescript
/** Is the diff too large for us to reasonably represent? */
function isDiffTooLarge(diff: IRawDiff) {
  for (const hunk of diff.hunks) {
    for (const line of hunk.lines) {
      if (line.text.length > MaxCharactersPerLine) {
        return true
      }
    }
  }

  return false
}
```
