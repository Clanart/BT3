### Title
Permanent, ownership-independent `safe.directory` trust exception allows silent code execution when a trusted path is later reoccupied by an attacker - ([File: app/src/lib/git/config.ts])

### Summary
Desktop's "Trust Repository" flow (`AddExistingRepository`, `MissingRepository`) calls `addSafeDirectory(path)` when a user opens a repository owned by another user, which permanently whitelists the *path* in the user's global `~/.gitconfig` via `safe.directory`. This exception has no expiration, no binding to the repository's identity/remote/commit history, and no revocation UI. Once granted, any future Git operation against that path is exempted from Git's ownership check — forever — even if the directory is later deleted and repopulated by a different, untrusted actor.

### Finding Description
`addSafeDirectory` in [1](#0-0)  writes the trusted path into the `safe.directory` global config entry, which git-for-windows/git itself only checks by path string, not by owner, remote URL, or repository identity. Desktop surfaces the trust prompt purely as a one-time decision:

- `AddExistingRepository.onTrustDirectory` [2](#0-1)  calls `addSafeDirectory(repositoryUnsafePath)` once the user clicks "add an exception for this directory".
- `MissingRepository.onTrustDirectory` [3](#0-2)  does the same when a previously-known repository path is re-detected as "unsafe".

There is no corresponding `removeSafeDirectory`/revocation call anywhere in the codebase, and no timestamp, remote fingerprint, or repository identity check is stored alongside the exception — only a bare path string in global git config.

This mirrors the reported bug class precisely: a one-time authorization (there, a signed `Credit`; here, a "trust this directory" click) is granted without any deadline or binding to the conditions that justified it (there, the NFT price; here, who currently owns/controls that filesystem path). Once granted, the exception silently persists and is reused automatically for all future git operations at that path, regardless of how drastically the underlying conditions have changed.

### Impact Explanation
Paths that get reused by different content are common: removable/USB drives, network shares, CI-mapped or synced folders (Dropbox/OneDrive), Docker/VM shared mounts, or simply a directory that was `rm -rf`'d and re-cloned by a different user or attacker with local access to the same environment. Once a user has trusted `/mnt/shared/project` (say, on a lab VM or shared machine) a single time, Desktop/Git will never re-check ownership for that path again. If an attacker subsequently gains control of that same path (recreates the repo there with a different owner), Git will treat the attacker's repository as fully trusted without any Desktop prompt, re-enabling the very risk the "unsafe" warning exists to prevent — including running that repo's local config-driven behavior (`core.hooksPath`, filters, `core.fsmonitor`, etc.) without ever alerting the user that ownership has changed. This can lead to code execution outside the user's expectation on their next git operation in that repository, matching the "silent corruption of what the user commits/executes" and "code execution" impact classes.

### Likelihood Explanation
Moderate. It requires the attacker to be able to place git-controlled content at a path the victim previously trusted (e.g. shared machines, removable media reused across users, restored backups, or synced folder race conditions) — this is a realistic multi-user/shared-storage scenario rather than requiring local malware already on the victim's own exclusive machine. The core weakness — an unconditional, non-expiring, identity-agnostic trust grant — is entirely attacker-independent of the initial trust decision being reasonable.

### Recommendation
- Do not persist safe-directory exceptions purely by path. Bind the trust decision to a stable repository identity (e.g., first-commit SHA, remote URL, or `.git` directory device/inode) captured at the time of trust, and re-validate it on each open.
- Provide a UI/settings surface to view and revoke previously granted `safe.directory` exceptions.
- Consider re-prompting when the underlying directory's owner or repository identity changes, even if the path itself was previously trusted.

### Proof of Concept
1. On a shared machine or removable/synced drive, user A clones a repo to `/shared/project` and, when adding it as an existing repository in Desktop, sees the "Git repository ... appears to be owned by another user" warning and clicks "Trust Repository". Desktop calls `addSafeDirectory('/shared/project')`, permanently adding the path to the user's global `safe.directory` config ( [2](#0-1) , [4](#0-3) ).
2. Later, the directory `/shared/project` is deleted (e.g., drive reformatted, folder recreated, user B recreates it) and repopulated by an attacker with a malicious repository at the same path, owned by a different account.
3. Because `safe.directory` matches by path only, Git no longer flags the directory as "unsafe" — Desktop performs no re-prompt (`getRepositoryType` returns `'regular'`, not `'unsafe'`), and the attacker's repository config/hooks are treated exactly as trusted content on the victim's next git operation there.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```
