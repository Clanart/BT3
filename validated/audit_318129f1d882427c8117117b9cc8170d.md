## Analog Found: NFT royalty fee aggregation bypasses per-royalty cap in `make_nft1_offer`

### Title
Per-NFT royalty cap check in `compute_royalty_amount` fails to bound the *aggregate* royalty fee across multiple requested NFTs, allowing royalty payments to consume nearly 100% of an offered fungible asset - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
The reported bug class is: individual fee components are each checked against a sane bound in isolation, but nothing bounds their *sum*, so the combined fee can consume nearly the entire value being transferred. The same pattern exists in Chia's NFT offer/royalty logic in `chia/wallet/nft_wallet/nft_wallet.py`. `compute_royalty_amount` only validates a single NFT's royalty against the full offered amount, but when an offer requests multiple royalty-bearing NFTs (`request_side_royalty_split > 1`), each NFT's royalty is computed and checked independently against the pre-split total, not against the actual remaining value after all other royalties are deducted.

### Finding Description
`compute_royalty_amount` guards a single royalty computation: [1](#0-0) 

In `make_nft1_offer`, when an offer requests `N` royalty-enabled NFTs (`request_side_royalty_split = N`), the fungible asset the maker is paying is looped over each `required_royalty_info` entry and `compute_royalty_amount(amount, request_side_royalty_split, percentage)` is invoked independently per NFT, with the *full, undivided* offered `amount` passed each time: [2](#0-1) 

Because `compute_royalty_amount` internally divides by `royalty_split` before computing the percentage (`abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`) and only rejects a *single* royalty that is `>= abs(offered_amount)` (the undivided total), each individual royalty can be pushed up to just under `offered_amount / royalty_split`. With `royalty_split = N` NFTs each carrying a royalty percentage near 100% (`percentage` up to `MAX_ROYALTY_BASIS_POINTS - 1`, i.e. 99.99%), every per-NFT check passes individually, yet the sum of the `N` royalty payments approaches the *entire* offered fungible amount: [3](#0-2) 

There is no aggregate check anywhere in `make_nft1_offer` that sums `royalty_payments[asset]` and compares it against the offered `amount` before constructing the trade. The only place the sum is computed is later, purely to determine `coin_amount_needed` for coin selection funding purposes, not for validation: [4](#0-3) 

This mirrors the report's exact bug class: flat + percentage fee are each unconstrained relative to each other, and only their sum determines whether the trade is economically viable — here, per-NFT royalty percentages are each capped against the full (undivided) amount, but the *sum* across multiple requested NFTs is never capped.

### Impact Explanation
A maker (or an offer-hosting third party) can construct an offer requesting multiple existing royalty-enabled NFTs (whose royalty percentage is fixed by the original minter and can be set arbitrarily up to 99.99% at mint time — see `MAX_ROYALTY_BASIS_POINTS` in `royalty_percentage_fraction` minting options) such that the cumulative royalty extracted from the fungible payment leg approaches 100% of the offered value. A counterparty who signs such an offer without independently re-deriving and summing all royalty percentages across all requested NFTs receives negligible or zero net proceeds relative to what they gave up, while the majority of value is diverted to third-party royalty addresses (which may be attacker-controlled, e.g. an NFT minted with a maximal royalty percentage then transferred/sold to an unwitting party). This is analogous to the reported "fee setup" flaw: individually-bounded fee components combine into an economically-void or near-total-value-extracting trade that passes all local checks.

### Likelihood Explanation
Exploitability requires the attacker to control (or induce use of) multiple NFTs with high royalty percentages within a single offer's `request_side_royalty_split`, which is straightforward since royalty percentage is minter-controlled at NFT creation time and unbounded up to just under 100% per NFT (`MintNftCMD.royalty_percentage_fraction`, `NFTMintNFTRequest.royalty_percentage`, checked only against `10000` disallowed). No privileged access or protocol bug is needed — only that a counterparty/taker signs an offer requesting several such NFTs without manually verifying the aggregate royalty impact, which the wallet's own logic does not compute or warn about prior to signing.

### Recommendation
In `make_nft1_offer`, after building `royalty_payments[asset]`, sum all royalty amounts per fungible asset and validate the aggregate against the offered `amount` (similar to the existing per-entry check in `compute_royalty_amount`), rejecting or clamping the offer construction if `sum(payment.amount for _, payment in royalty_payments[asset]) >= abs(amount)`. Additionally, surface the aggregate royalty percentage/amount prominently to the counterparty before they sign an offer (e.g., in `TradeManager`/offer summary flows) so a human reviewer can catch royalty-draining offers even if the aggregate check is bypassed.

### Proof of Concept
1. Mint two NFTs (`NFT_A`, `NFT_B`) each with `royalty_percentage_fraction = 9999` (99.99%) via `MintNftCMD`/`nft_mint_nft`, with `royalty_address` controlled by the "attacker."
2. Transfer or sell `NFT_A` and `NFT_B` to a victim (e.g., bundled with other legitimate-looking NFTs).
3. Construct an offer via `create_offer_for_ids` / `make_nft1_offer` requesting both `NFT_A` and `NFT_B` (`request_side_royalty_split = 2`) in exchange for a fungible asset amount `X` (e.g., 1000 XCH) offered by the maker.
4. Inside `make_nft1_offer`, for each NFT: `compute_royalty_amount(amount=-X, royalty_split=2, percentage=9999)` returns `≈ X/2 * 0.9999`, which individually is `< X`, so both individual checks in `compute_royalty_amount` pass.
5. The two `royalty_payments` entries sum to `≈ 0.9999 * X`, leaving the actual settlement payment (`requested_payments`) essentially untouched by any validation — the victim who takes this offer receives `X` fungible tokens into the trade, but ~99.99% of it is immediately re-routed via royalty payments to the attacker's `royalty_address` rather than the victim's own wallet, since royalty payouts are constructed from the same offered coin (`chia/wallet/nft_wallet/nft_wallet.py:927-934, 952-960`) before the counterparty's requested payment is settled.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
