### Title
Symlink-based path traversal in file context-menu actions bypasses the repo-boundary guard used elsewhere - (File: `app/src/lib/app-shell.ts`)

### Summary
GitHub Desktop has a dedicated, tested helper, `resolveWithin` (`app/src/lib/path.ts`), whose explicit purpose is to reject any repository-relative path that — after `realpath` resolution — escapes the repository root, including via a symlink planted inside the repo. This guard is correctly used for the "Open file from deep link" flow (`app/src/ui/dispatcher/dispatcher.ts`) and for Copilot conflict-context file reads (`app/src/lib/copilot-conflict-context.ts`). However, the much more commonly used "Reveal in File Manager" / "Open in External Editor" / "Open with default program" context-menu actions — reachable from Changes, History, Pull Request Files Changed, and Merge Conflict views — build the on-disk path with plain `Path.join(repository.path, path)` and never call `resolveWithin`, so a symlink tracked inside a malicious repository can redirect these actions to files anywhere on disk.

### Finding Description
`resolveWithin` is designed precisely to stop this class of bug: [1](#0-0) 

and is verified against symlink escapes in tests: [2](#0-1) 

It is used when opening a file from an `x-github-client://` deep link: [3](#0-2) 

and when reading conflicted files for Copilot ("Guard against path traversal and symlink escapes"): [4](#0-3) 

But the far more frequently used `revealInFileManager` helper — invoked from nearly every file-context menu in the app — does none of this: [5](#0-4) 

The same unguarded `Path.join(repository.path, path)` pattern is repeated at every call site that lets the user act on a file path taken from git status/log/diff output:
- Working directory context menu ("Reveal in File Manager"): [6](#0-5) 
- "Open in External Editor" from the main window: [7](#0-6) 
- Selected-commit file list ("Open with default program"): [8](#0-7) 
- Commit context menu (reveal / open in editor / open with default program): [9](#0-8) 
- Pull-request "Files Changed" context menu: [10](#0-9) 
- Merge-conflict file resolution menu: [11](#0-10) 
- Copilot-assisted conflict dialog overflow menu: [12](#0-11) 

The `path` value in all of these cases originates from git's own status/log/raw-diff parsers, which simply forward whatever path string appears in git's machine-readable output as-is: [13](#0-12) [14](#0-13) 

Git itself refuses to materialize `..`-containing tree entries on checkout, but it does allow ordinary symlinks to be committed and checked out as regular tracked objects. A malicious repository can therefore commit a symlink such as `link -> /` (or a relative equivalent), which git will happily check out as a normal working-tree entry. Any subsequently touched path that traverses through that symlink (e.g. `link/Users/victim/.ssh/id_rsa`) will be reported by `git status`/`git log --raw` as an ordinary file path string, with no `..` segments to trip up naive validation, yet `Path.join(repository.path, path)` combined with the OS's symlink resolution during file access will land on a location fully outside the repository. This is exactly the scenario `resolveWithin`'s `realpath`-based check exists to catch — but none of the `revealInFileManager` / `openInExternalEditor` / `onOpenItem` call sites use it.

### Impact Explanation
An attacker who gets a victim to clone or add a repository containing a tracked symlink can cause GitHub Desktop's "Open in External Editor" or "Open with default program" actions (triggered from an innocuous-looking file entry in Changes, History, or the Pull Request "Files Changed" view) to open an arbitrary file located outside the repository — for example configuration files, SSH keys, or other sensitive local files — displaying their contents to the user's editor/default handler, and "Reveal in File Manager" will disclose the existence/location of files outside the repo. This is a boundary violation of the same class described in the source report: a security control (`resolveWithin`) that protects one call path is silently absent on parallel call paths that perform logically equivalent operations, and the difference isn't documented or enforced by any shared access-control layer.

### Likelihood Explanation
Exploitation only requires the victim to open/clone an attacker-supplied repository (a normal, expected Desktop workflow) and right-click a file in any of the listed views — no admin rights, no local access, and no unnatural steps beyond interacting with the repository as intended. Git natively supports committing symlinks on macOS/Linux, so the malicious payload requires no exotic tooling.

### Recommendation
Route every path derived from tracked/working-tree file entries through `resolveWithin` (or an equivalent symlink-aware boundary check) before it is passed to `shell.showItemInFolder`, `openFile`, or `launchExternalEditor`/`launchCustomExternalEditor`. Centralize this in `revealInFileManager` and in the shared `onOpenItem`/`openInExternalEditor` dispatcher methods rather than re-implementing `Path.join` at each call site, and refuse the action (with a user-facing error, mirroring the `dispatcher.ts` deep-link handling) when the resolved path escapes the repository root.

### Proof of Concept
1. On macOS/Linux, create a malicious repository: `ln -s / evil-link`, `git add evil-link && git commit -m pwn`.
2. Publish/host this repository and have the victim clone it in GitHub Desktop.
3. In the working tree, create/modify a path that traverses the symlink, e.g. `evil-link/Users/<victim>/.ssh/id_rsa` (or ship it already committed pointing at a predictable sensitive path), so it shows up as a file entry in the Changes/History list with that path string.
4. Right-click the entry and choose "Open in External Editor" (or "Reveal in File Manager").
5. Observe that `Path.join(repository.path, path)` combined with OS symlink resolution opens/reveals the file at `/Users/<victim>/.ssh/id_rsa`, outside the repository, without ever going through `resolveWithin`'s symlink-escape check — unlike the equivalent, protected flow in `dispatcher.ts`'s `openRepositoryFromUrl`.
