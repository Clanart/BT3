### Title
Nested/Recursive Precompile Calls Cause Double-Processing of Bank Events in `BalanceHandler`, Corrupting EVM `StateDB` Balances - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
This is the same bug class as the reported ERC777 `tokensToSend` reentrancy: a hook that fires *mid-transfer*, before accounting is finalized, is used to reenter the system and cause balances to be computed/applied against a stale or already-consumed set of state changes. In Cosmos EVM, the analogous "hook" is a native ERC20 contract's `_beforeTokenTransfer` (or any nested EVM call) that reenters a stateful precompile (staking, distribution, bank, ICS20, ERC20) while an *outer* precompile call is still in progress. The `BalanceHandler` used to bridge Cosmos SDK bank events into the EVM `StateDB` records only a starting index (`prevEventsLen`) into the shared `ctx.EventManager()` event log, and reads to "now" when finalizing. Nested precompile calls consume and apply events from that same shared log independently, so when the outer call finalizes it can reprocess (and re-apply to `StateDB`) events that an inner nested call already applied — duplicating balance credits/debits in the EVM view while the Cosmos SDK bank keeper (source of truth) reflects the change only once.

### Finding Description
`BalanceHandler.BeforeBalanceChange` simply snapshots the event-log length: [1](#0-0) 

`AfterBalanceChange` then iterates every event from that snapshot index to the *current* end of the log and applies `AddBalance`/`SubBalance` to the `StateDB` for every `EventTypeCoinSpent`/`EventTypeCoinReceived`/precisebank fractional event found in that range: [2](#0-1) 

Every stateful precompile invocation goes through `Precompile.runNativeAction`, which creates a **new** `BalanceHandler` per call via the factory and calls `BeforeBalanceChange` right before executing the method, then `AfterBalanceChange` right after: [3](#0-2) 

The problem is that `ctx.EventManager()` here is shared/inherited across nested calls (the same underlying event manager keeps accumulating events regardless of nesting depth). If, while an outer precompile call's native action is executing (e.g., a `bank`/`erc20`/`ics20` transfer that internally emits `bank.MsgSend`), an ERC20 token contract's `_beforeTokenTransfer` hook or any other nested EVM call reenters and invokes *another* stateful precompile (e.g., `staking.delegate`, `distribution.claimRewards`, or even the same ERC20/bank precompile again), that nested call:
1. Starts its own `BalanceHandler` with `prevEventsLen = current length` (which is ≥ the outer's already-recorded starting length).
2. Emits its own bank events and, on completion, applies them to `StateDB` via its own `AfterBalanceChange`.
3. Returns control to the outer call, which then completes and calls **its own** `AfterBalanceChange`, iterating from the outer's original (earlier) `prevEventsLen` to the new end of the event log — a range that **overlaps and reprocesses** the events the inner call already consumed and applied.

This causes `StateDB.AddBalance`/`SubBalance` to be invoked twice for the same underlying bank movement, inflating (or corrupting) the EVM-visible balance of the affected address relative to the actual Cosmos SDK bank balance.

This exact scenario is explicitly exercised by the repository's own test suites, confirming the root cause is real and reachable through ordinary EVM contract execution (no privileged access required):
- A dedicated test suite states the bug directly: "recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [4](#0-3) 
- A full IBC/ICS20 integration test suite is dedicated to "recursive precompile calls," using a malicious ERC20 contract whose `_beforeTokenTransfer` hook reenters the staking/distribution precompiles mid-transfer — the direct on-chain analog of the ERC777 `tokensToSend` hook: [5](#0-4) [6](#0-5) 

### Impact Explanation
If the double-processing results in the `StateDB` crediting more balance than the bank keeper actually moved (e.g., an `AddBalance` applied twice for a receiver, or a `SubBalance` applied only once for a spender while credit is doubled), the attacker's EVM-visible balance becomes inflated relative to their true, backing Cosmos SDK bank balance. Since EVM balance is directly spendable (native token transfers, further precompile calls, contract calls with `value`), this is unauthorized duplication of spendable user value / accounting-invariant corruption between native bank balances and EVM balances, matching the repository's Critical impact gate ("unauthorized minting, burning, duplication, ... of spendable user value across native balances, EVM balances ... or precompile-mediated assets").

### Likelihood Explanation
The trigger requires only an ordinary, unprivileged user to deploy an ERC20 contract with a transfer hook (or any contract making a nested call) that is used as the token/asset for a precompile-mediated transfer (ERC20 precompile, ICS20 transfer precompile, bank precompile flows, or a contract that in turn calls the staking/distribution precompile mid-transfer), and then trigger a transfer of that asset through a precompile path. This requires no relayer, validator, or governance action — it is fully reachable via a standard EVM transaction, and the repository's own test files demonstrate that this exact call pattern (nested/recursive precompile invocation during a transfer hook) is a realistic, already-anticipated scenario.

### Recommendation
Do not rely on a length-delta over a shared, mutable event log across nested precompile invocations. Instead:
- Track and consume events using a strictly increasing, globally unique cursor that is only ever advanced (never re-read) once processed by any `BalanceHandler` instance (e.g., a single shared "high-water mark" stored on the `StateDB`/journal rather than per-call-local `prevEventsLen`), or
- Disallow/guard nested stateful-precompile reentrancy while a `BalanceHandler` pass is outstanding for the same EVM call stack (i.e., make the balance-handler window `nonReentrant` per transaction, similar to the recommended ERC777 mitigation), or
- Have `AfterBalanceChange` explicitly track already-processed event indices globally per transaction so that a nested call's finalize step permanently "claims" its event range and the outer call's finalize step skips those already-claimed indices.

### Proof of Concept
The repository already contains a proof-of-concept construction:
1. Deploy `ERC20RecursiveNonRevertingPrecompileCall` (or the reverting variant), whose `_beforeTokenTransfer` hook calls back into the staking/distribution precompiles via `try/catch` during a transfer: [6](#0-5) 
2. Route a transfer of this token through a precompile-mediated flow (e.g., ICS20 transfer precompile) so that the outer precompile call's `BeforeBalanceChange`/`AfterBalanceChange` window is open while the token's hook reenters other precompiles, exactly as exercised in: [7](#0-6) 
3. Compare the resulting `StateDB`/EVM-visible balance against the actual `x/bank` balance after the transaction — the existing test suite's own naming and description ("balance desync between native bank keeper and EVM stateDB") confirms this divergence is what the tests were built to detect.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
