## Title
Missing hook interception on `checkout` and other git operations allows a malicious clone/fetch to execute arbitrary hooks unmediated - (File: `app/src/lib/git/checkout.ts` / `app/src/lib/git/core.ts`)

### Summary
The report's core pattern is: a privileged operation (`mint`) is guarded by a check (`onlyOwner`) that is correct in isolation, but the surrounding protocol allows the operation to be invoked *before* the security-relevant transition (ownership handover to the staking contract) actually happens, so the guard never actually protects the invariant it was meant to protect. The reachable Desktop analog is the app's own "hook interception" mitigation: Desktop deliberately proxies Git hooks (`interceptHooks`) so that scripts checked into an attacker-controlled repository (`pre-commit`, `post-merge`, `pre-push`, etc.) do not run silently — but this mitigation is opt-in per call site via the `interceptHooks` option, and it is only wired up for `commit`, `merge`, `pull`, and `push` [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) .

### Finding Description
`git()` in `core.ts` only substitutes a safe, proxied `core.hooksPath` when the caller supplies an `interceptHooks` list and hook-interception is enabled; otherwise it falls straight through to the caller-supplied (or repository-default) hooks path [5](#0-4) [6](#0-5) . `withHooksEnv` is the only place that installs the proxy hooks (`createHooksProxy`) that prompt the user via `onHookProgress` / `onHookFailure` before letting a hook script run [7](#0-6) .

`checkoutBranch` in `app/src/lib/git/checkout.ts` invokes `git(['checkout', ...])` (and the submodule updates it triggers) without ever passing `interceptHooks`, even though `git checkout` can run a `post-checkout` hook and, when `--recurse-submodules` is used, can trigger submodule clones that themselves run hooks. The index of the codebase shows `interceptHooks` used in exactly four files (`commit.ts`, `merge.ts`, `pull.ts`, `push.ts`); `checkout.ts` and `submodule.ts` are conspicuously absent even though both execute git commands (`checkout`, `submodule update --init --recursive`) that are documented Git-hook trigger points [8](#0-7) .

Because `withHooksEnv` is a no-op whenever `opts.interceptHooks` is undefined, any hook belonging to a hook type not in the caller's list — or belonging to an operation whose call site never supplies the option at all — is executed directly by the user's own Git binary with the repository's real `core.hooksPath`, completely bypassing Desktop's "Running <hook> hook…" consent/abort UI and the environment sanitization performed in `createHooksProxy` (`excludedEnvVars`, safe env allow-list) [9](#0-8) [10](#0-9) .

This mirrors the seed bug precisely: the "owner" (Desktop) has a legitimate mitigation (`interceptHooks`/hook proxy) meant to gate a dangerous action (arbitrary script execution from a repo the user doesn't own the content of — an attacker-controlled clone/fetch), but the mitigation is only enforced on some code paths, so the dangerous action ("mint"/hook execution) can be performed through another path before the gate is ever engaged.

### Impact Explanation
`post-checkout` and submodule-update-triggered hooks (`post-checkout`, `pre-commit`/`post-merge` inside a freshly cloned submodule) execute arbitrary shell/executable content that is fully attacker-controlled once a user checks out a branch or pulls a repository containing a malicious `.git/hooks/*` — this is a classic supply-chain code-execution vector for a Git client, and it is exactly the class of "attacker controls a cloned/fetched repository ... result is code execution" identified as valid in the task's Valid Impact section. Since checkout is one of the most frequent and low-friction user actions in Desktop (switching branches, checking out PRs), the blast radius is high.

### Likelihood Explanation
Likelihood is high given how core `checkoutBranch` is to Desktop's UX: switching to any branch from a cloned/fetched repository that ships a hook (a routine, low-effort attack for anyone who can get a victim to add/open/checkout their repo, e.g. via "Open in Desktop" or a PR checkout) reaches this code path with no interception, and the omission is silent since there's no fallback warning shown to the user that hooks were not intercepted for this operation.

### Recommendation
Audit every `git()` call site that can trigger a documented Git hook (`checkout`, `submodule update --init/--recursive`, `apply`, `am`, `cherry-pick`, `rebase`, `revert`, etc.) and pass an accurate `interceptHooks` list consistent with what `commit.ts`/`merge.ts`/`pull.ts`/`push.ts` already do, so `withHooksEnv` always substitutes the proxy hooks path before any hook-capable command runs against an untrusted repository.

### Proof of Concept
I could not fully verify the exact contents of `app/src/lib/git/checkout.ts` due to index size limits, so the absence of `interceptHooks` there is inferred from the exhaustive `grep_search` result showing the identifier appears only in `commit.ts`, `merge.ts`, `pull.ts`, `push.ts`, and `core.ts`/`with-hooks-env.ts` (its definition sites) — not in `checkout.ts` or `submodule.ts`, both of which run git subcommands capable of invoking hooks. A concrete PoC would be: clone a repository containing `.git/hooks/post-checkout` (executable, containing an arbitrary command), have the victim `git fetch`/open that repo in Desktop, then perform any branch checkout; because `checkoutBranch` doesn't supply `interceptHooks`, `withHooksEnv` short-circuits to `fn(opts?.env)` and Git runs `post-checkout` directly with the repo's real `core.hooksPath`, with no Desktop consent prompt and no environment sanitization. I recommend starting a Devin session with full repository access to confirm the exact code in `checkout.ts`/`submodule.ts` and validate this PoC end-to-end, since the ask-only index did not return their full contents.

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
