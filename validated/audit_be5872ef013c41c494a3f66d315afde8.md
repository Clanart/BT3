### Title
Copilot conflict resolution silently mis-splices resolved content when a conflicted file contains decoy conflict-marker text - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The Lighthouse bug is a class of defect where two independently-driven pieces of async/derived state are correlated by *implicit position/order* instead of an explicit identity, so a mismatch between producer and consumer silently corrupts persisted data. GitHub Desktop's Copilot-assisted merge-conflict resolution feature has the same structural flaw: conflict hunks are extracted from a file and later re-located in that file by scanning for the same marker regex twice, independently, and are stitched back together purely by encounter order — with no identity check tying a specific model resolution to the specific marker block it was generated for.

### Finding Description
`extractConflictHunks` in [1](#0-0)  scans a conflicted file top-to-bottom for any text matching `<<<<<<<` / `=======` / `>>>>>>>` (via bare regexes `oursMarker`/`separatorMarker`/`theirsMarker`, not actual git conflict metadata) and produces an ordered list of "hunks" that is sent to the Copilot model. The model is documented to return resolutions "for each conflict hunk, in order" with no location anchor: [2](#0-1) .

When the user accepts the resolution, `reassembleResolvedFile` performs a **second, independent** scan of the raw on-disk content, again matching the same marker regexes, and splices `hunkResolutions[hunkIndex]` into each well-formed marker block it finds, incrementing `hunkIndex` once per block encountered: [3](#0-2) . Nothing ties `hunkResolutions[hunkIndex]` back to the specific block it was generated for — no line number, no hash of the original `oursContent`/`theirsContent`, no count-match assertion. `reassembleResolutions` (the bridge that produces the final file content used for writing) similarly matches purely by array order/path with no per-hunk validation: [4](#0-3) .

If a file (fully controlled by an attacker via a cloned/fetched repository or a branch merged from a fork) contains text that merely *looks like* a well-formed conflict-marker block — e.g. inside a code comment, string literal, or generated/vendored file — but is not an actual git conflict, `extractConflictHunks` will treat it as a real hunk and include it in the prompt sent to the model. If that decoy block appears earlier in the file than a real conflict, it consumes the model's first resolution slot, shifting every subsequent hunk-to-resolution correspondence by one position. `reassembleResolvedFile`'s validation only checks that a block is well-formed (has a separator and closing marker before EOF) — it does not verify the hunk count matches, nor that the spliced content corresponds to the block being replaced. The write path (`_applyCopilotConflictResolutions`) only skips overwriting a file when git reports **zero** remaining conflict markers — i.e. it assumes "fully resolved externally": [5](#0-4) . A file with the correct number of real conflicts plus one attacker-planted decoy block still reports as conflicted, so this guard never fires, and the misaligned splice is written to disk and staged unmodified: [6](#0-5) .

### Impact Explanation
The net effect is that content the model generated for one part of the merge gets written into an unrelated location (the decoy block, which was ordinary non-conflicted file text), while the real conflict may receive a resolution meant for a different hunk. This is written to disk and `git add`-ed without any warning to the user, who then commits it — a silent corruption of what the user commits, matching the impact criteria (attacker-controlled repository content causing silent corruption of committed content).

### Likelihood Explanation
This requires: (1) the user to have the Copilot conflict-resolution feature enabled and to click "Resolve with Copilot" / "Continue Merge" on a repository containing attacker-planted content, and (2) an attacker to plant marker-shaped text in a file that later also develops a real conflict in the same merge/rebase. This is a plausible but non-trivial scenario for a targeted supply-chain-style attack (e.g., a malicious PR branch merged by a maintainer using AI conflict resolution). I was not able to verify from the index whether there is any additional validation elsewhere (e.g., in the SDK response schema validation) that might reject a mismatched hunk count before reassembly — this should be confirmed by a background agent with full repo access.

### Recommendation
Add a hard count-match assertion between hunks sent to the model and blocks found during reassembly (fail/skip the file rather than splice on mismatch), and/or anchor each hunk resolution to its source block via a content hash or line-range captured at extraction time and verified at reassembly time rather than relying purely on ordinal position.

### Proof of Concept
1. Attacker crafts a text/code file containing `<<<<<<<`, `=======`, `>>>>>>>` as literal content (e.g., inside a fenced example in a markdown/doc file), not from an actual merge, and gets it merged into the target repo (e.g. via a PR).
2. Victim later performs a merge/rebase that produces one or more *real* conflicts in that same file, positioned after the decoy block.
3. Victim clicks "Resolve with Copilot"; `extractConflictHunks` extracts N+1 "hunks" (1 decoy + N real), and the model returns N+1 resolutions in order.
4. Victim clicks "Continue Merge"; `reassembleResolvedFile` re-scans the file and splices resolution[0] into the decoy block (corrupting previously-fine content) and shifts remaining resolutions into the real conflicts, potentially applying content generated for one conflict into the wrong one.
5. `_applyCopilotConflictResolutions`'s "externally resolved" skip check does not trigger (git still reports the file as conflicted because real conflicts remain), so the corrupted content is written and staged, then committed by the victim without any error being surfaced.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
