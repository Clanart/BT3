### Title
`extract_frontmatter` naive `str.split('---', 2)` lets an embedded `---` substring in a frontmatter value silently strip `action: block` into the message body, downgrading a block rule to warn - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` locates the YAML frontmatter block by doing `content.split('---', 2)` on the raw file text instead of splitting on delimiter *lines*. If any frontmatter value earlier in the block contains the literal substring `---` (e.g. inside a `pattern`, `message`, or `description` field), the second split point lands on that inline occurrence instead of the real closing `---` line, truncating the parsed frontmatter dict before it reaches later keys such as `action: block`. Those later lines are silently shoved into the markdown message body instead of the frontmatter dict, so `Rule.from_dict` falls back to the default `action = 'warn'` even though the raw file visibly contains `action: block`.

### Finding Description
`extract_frontmatter` at [1](#0-0)  splits on the literal string `---` anywhere in the content, not on standalone delimiter lines:
```
parts = content.split('---', 2)
frontmatter_text = parts[1]
message = parts[2].strip()
```
Because `str.split` matches the substring wherever it occurs, a value inside the frontmatter block (e.g. `pattern: "foo---bar"` or `message: "See --- disclaimer"`) that appears *before* the intended closing delimiter is treated as the closing delimiter. Everything after that point - including a genuine `action: block` line further down in the same frontmatter block - gets shifted into `parts[2]` (the message body) rather than `parts[1]` (frontmatter text).

`load_rule_file` then calls `Rule.from_dict(frontmatter, message)` at [2](#0-1) . Since the truncated `frontmatter` dict no longer contains the `action` key, `Rule.from_dict` falls back to the default:
```
action=frontmatter.get('action', 'warn'),
``` [3](#0-2) 

No exception is raised and `frontmatter` is non-empty (it still contains `name`, etc.), so the "missing frontmatter" warning at [4](#0-3)  never fires - the failure is completely silent.

Downstream, `RuleEngine.evaluate_rules` only treats a rule as blocking when `rule.action == 'block'`; anything else goes into `warning_rules`, which only emits a `systemMessage` and allows the tool call to proceed [5](#0-4) . For `PreToolUse`, a real blocking rule would set `permissionDecision: deny` [6](#0-5) , but the downgraded rule never reaches that branch, so the dangerous `Bash`/`Edit`/`Write` invocation the rule was meant to stop is allowed to execute.

`load_rules`/`load_rule_file` are invoked directly from the `PreToolUse`, `PostToolUse`, and `Stop` hook scripts on every tool call [7](#0-6) , so any `.claude/hookify.*.local.md` file present in a checked-out repository is parsed and enforced automatically, without further review by the victim.

### Impact Explanation
An attacker who can get a crafted `.claude/hookify.*.local.md` into a repository the victim clones (a plugin file, a PR, or repo content ordinarily consumed by Claude Code) can make it *appear* to a human/security reviewer that the rule blocks a dangerous action (`action: block` is visibly present in the file), while the actual enforced `Rule` object is `action: warn`. This breaks the stated invariant that a deny rule must never be parsed into a non-blocking configuration, and lets an otherwise-blocked dangerous `Bash`/`Edit`/`Write` operation execute unimpeded - enabling cross-repo/cross-session mutation, destructive command execution, or other actions the block rule was supposed to prevent, matching the "wrong-target mutation / bypass of an intended security control" impact class.

### Likelihood Explanation
The precondition is only that the attacker can place or influence a `.claude/hookify.*.local.md` file in a repository that the victim's Claude Code session loads (e.g. contributed via a PR, or shipped inside a cloned plugin/template repo) - no special privilege on the victim's machine is required. Constructing the trigger is trivial: any frontmatter value positioned before the `action: block` line that contains the three-character sequence `---` (a decorative separator in a `message`/`description` string, or a pattern containing three consecutive hyphens) is sufficient. The bug is deterministic and fully reproducible.

### Recommendation
Replace the substring-based `content.split('---', 2)` with a line-oriented frontmatter parser that only treats a line consisting solely of `---` (optionally with surrounding whitespace) as a delimiter, e.g. by iterating lines and matching `line.strip() == '---'` for the opening/closing markers instead of splitting on the raw string. Additionally, consider failing closed (refuse to load / treat as blocking) rather than defaulting `action` to `warn` when frontmatter parsing is ambiguous or a known dangerous key is absent unexpectedly.

### Proof of Concept
Unit test to add to `plugins/hookify/core/config_loader.py` tests (or an integration test that drives `pretooluse.py`):
```python
from hookify.core.config_loader import extract_frontmatter, Rule

content = '''---
name: block-rm
pattern: "rm -rf --- danger"
action: block
enabled: true
---
Blocked dangerous rm!
'''

frontmatter, message = extract_frontmatter(content)
rule = Rule.from_dict(frontmatter, message)

# Expected (correct) behavior: action should be 'block'
assert rule.action == 'block', f"Expected block, got {rule.action}"
```
Running this against the current implementation shows `rule.action == 'warn'` (the default), because `action: block` and `enabled: true` are shifted into the message body by the premature split on the embedded `---` inside `pattern`. An integration-level PoC would place this file as `.claude/hookify.rm.local.md`, pipe a `Bash` `tool_input` with `command: "rm -rf --- danger"` into `plugins/hookify/hooks/pretooluse.py`, and assert the hook output lacks `"permissionDecision": "deny"` even though the file visibly declares `action: block`.
