### Title
Unauthenticated panic via unknown `PointerType` in `MsgRegisterPointer` handler - (File: x/evm/keeper/msg_server.go)

### Summary
Any account can submit a `MsgRegisterPointer` transaction with a `PointerType` field set to an integer outside the defined enum range (e.g. 7, 100, -1). Because `ValidateBasic` does not validate the enum value and the message handler's `switch` statements have `default: panic("unknown pointer type")`, this causes the node to panic during transaction processing.

### Finding Description
The `RegisterPointer` message handler switches over `msg.PointerType` in three separate places, and each switch's default case calls `panic("unknown pointer type")` instead of returning an error: [3](#0-2) [4](#0-3) [5](#0-4) 

`MsgRegisterPointer.ValidateBasic` only checks the sender's bech32 address and that `ErcAddress` is a valid hex address; it performs no validation on `PointerType` at all: [1](#0-0) .

`PointerType` is a raw proto3 `int32` enum with defined values 0–6 [6](#0-5) . Protobuf/amino deserialization of a transaction does not enforce that an enum field only contain one of the named values — any `int32` is accepted into `m.PointerType` during unmarshaling. This is the same bug class as the reported zkSync issue: an externally-controlled numeric ID/group value is dereferenced without a bounds/existence check, leading straight to a panic path instead of a graceful error.

The message is routed to `EVMTransaction`/direct `MsgRegisterPointer` handling via the standard message router `NewHandler` [7](#0-6) , so it is fully reachable from a normal signed Cosmos transaction (or from `x/evm`'s own `MsgRegisterPointer` message type, not gated by any special permission).

### Impact Explanation
A panic inside message execution during `DeliverTx`/`FinalizeBlock` will be caught by Cosmos SDK's `runTx` panic recovery and converted into a failed transaction in most configurations, so this is not automatically a chain halt — but it depends on whether the panic occurs inside a code path protected by baseapp's recover wrapper. If it does propagate (e.g., if invoked from a context where recovery isn't installed, such as within the EVM's own precompile/ante flow or a code path that bypasses the standard recover), it can crash the validator process handling the block, resulting in a consensus-halting condition since all validators executing the same malicious transaction would panic identically. At minimum, this is a reliable, cheap, attacker-controlled panic trigger that should never occur in normal operation and violates fail-safe design (return-error, not panic, on invalid user input).

### Likelihood Explanation
Trivial and cheap to trigger: any account with enough balance to pay gas can construct a `MsgRegisterPointer` with `PointerType` set to any out-of-range int32 (e.g., 99) and broadcast it. No special privileges, precompile interaction, or contract deployment is required — this is a directly reachable Cosmos SDK message handler.

### Recommendation
Add an explicit range/allow-list check for `PointerType` inside `MsgRegisterPointer.ValidateBasic` (rejecting any value not in `{ERC20, ERC721, ERC1155}`, since those are the only pointer types this message currently supports per the switch statements), and additionally replace the `panic("unknown pointer type")` calls in `x/evm/keeper/msg_server.go`'s `RegisterPointer` with returned errors as defense in depth, consistent with the pattern already used elsewhere (e.g., `sdkerrors.Wrapf(sdkerrors.ErrUnknownRequest, ...)` as seen in `x/evm/handler.go`).

### Proof of Concept
1. Construct a `MsgRegisterPointer` with a valid signer/sender, a valid hex `ErcAddress`, but `PointerType` set to an integer not in `{0,1,2,3,4,5,6}` (e.g., `PointerType: 42`).
2. Sign and broadcast the transaction normally through the standard Cosmos tx flow.
3. `ValidateBasic` passes (it does not check `PointerType`) [1](#0-0) .
4. The message reaches `msgServer.RegisterPointer`, hits the first `switch msg.PointerType` block, matches none of the defined cases, and executes `panic("unknown pointer type")` [3](#0-2) .

func (msg *MsgRegisterPointer) ValidateBasic() error {
	_, err := sdk.AccAddressFromBech32(msg.Sender)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid sender address (%s)", err)
	}

	if !common.IsHexAddress(msg.ErcAddress) {
		return sdkerrors.ErrInvalidAddress
	}

	return nil
}
