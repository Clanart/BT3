## Analysis

`CallDispatcher.dispatch` has no caller restriction, and the contract is deployed once as a shared, persistent singleton whose address is wired into `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, and their upgradeable variants as `_params.dispatcher` / `_dispatcher`. [1](#0-0)  Both `receive()` and `dispatch()` are unauthenticated: [2](#0-1) 

Because it is a persistent singleton (not deployed/destroyed per call), any ETH or token balance that ends up in this contract survives across transactions and callers. The sweep logic used by `IntentsBase._execute` only reclaims balances for tokens explicitly listed in `order.output.assets` — if a solver's `order.output.call` causes native ETH to land in the dispatcher for a token/asset not enumerated in that list, it is never swept back and remains as a standing balance in the shared contract: [3](#0-2) 

Similarly, `IntentGatewayV2.execute`'s predispatch flow sweeps `address(dispatcher).balance` in full, meaning any un-related residual balance sitting in the dispatcher gets attributed to whichever order calls it next — but if no order calls it, it just sits there, claimable. [4](#0-3) 

Since `dispatch()` has no `onlyHost`/`onlyGateway`/`onlyOwner` modifier, any unprivileged address can directly call `dispatch()` with a `Call[]` targeting a contract they control (the `extcodesize` check only requires the target to *be* a contract, trivially satisfied by deploying a minimal receiver) and drain whatever ETH/ERC20 balance is currently sitting in `CallDispatcher`, regardless of who deposited it. ### Title
Unauthenticated `CallDispatcher.dispatch` allows draining any residual ETH/token balance left in the shared singleton dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is deployed once and shared across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` as a common relay for executing arbitrary calldata. Its `dispatch(bytes)` function has no access control and its `receive()` accepts ETH from anyone. Because several call flows transfer ETH/tokens into this shared contract and sweep only the assets they explicitly track (not the full balance for every possible token), residual balances can persist in the contract between transactions. Any unprivileged address can call `dispatch()` directly to move that residual balance to an attacker-controlled contract.

### Finding Description
`CallDispatcher.dispatch` [5](#0-4)  iterates over caller-supplied `Call[]` and executes each with `to.call{value: call.value}(call.data)`, with no restriction on `msg.sender`. The only check is that `to` must have code (`extcodesize > 0`), which is trivially satisfied by any attacker-deployed contract.

The contract is deployed exactly once as a long-lived singleton in `DeployIsmp.s.sol` [1](#0-0)  and its address is stored as `dispatcher`/`_dispatcher` in `IntentGatewayV2` and the `HyperFungibleToken` family. These consumers route ETH/ERC20 assets through the dispatcher mid-transaction (e.g., `IntentGatewayV2.execute`'s predispatch flow at [6](#0-5)  and `IntentsBase._execute` at [7](#0-6) ), then attempt to sweep the balance back out.

The sweep logic only reclaims balances for tokens present in the order's `assets` arrays — any balance generated for an untracked asset (e.g., dust ETH produced by an arbitrary solver-supplied `output.call`, or leftover balance not accounted for by the snapshot-diff logic) is left sitting in the dispatcher. Because the dispatcher is a persistent shared contract with a public, unauthenticated `dispatch()`, that leftover balance is not owned or claimable by anyone in particular — it becomes a race condition where any external, unprivileged address can call `dispatch()` first to redirect it to themselves.

### Impact Explanation
Any ETH (or ERC20, via a `transfer` call routed through `dispatch`) balance that is not atomically swept out of `CallDispatcher` within the same transaction it arrived in becomes stealable by an arbitrary unprivileged caller, since `dispatch()` performs no ownership/session tracking and no caller authentication. This is a "wrongful asset movement" impact against protocol/dust balances that legitimately belong to the depositing flow (IntentGatewayV2 fillers/orders or HyperFungibleToken bridging flows).

### Likelihood Explanation
The likelihood depends entirely on how frequently non-zero balances are left behind in the shared dispatcher across transaction boundaries. The sweep logic in `_execute` and `IntentGatewayV2.execute` only tracks assets explicitly enumerated by the order (`order.output.assets`, `order.inputs`), so any value generated outside those enumerated assets (e.g., native ETH change from a swap invoked via `order.output.call` when ETH isn't in `order.output.assets`) is a realistic, protocol-driven source of residual balance, not merely a hypothetical.

### Recommendation
Add a caller restriction to `dispatch()` (e.g., `onlyHost`, an allow-list of authorized gateways/tokens, or a per-call session/ownership check) so that only the contract that funded a given batch of calls can trigger their execution. Alternatively, redesign the pattern so `CallDispatcher` never custodies balances across transaction boundaries — e.g., require the funding and dispatch to happen atomically within a single call from the funder, and ensure every code path that can leave a balance on the dispatcher (not just the enumerated asset list) is swept back to zero before the transaction ends.

### Proof of Concept
1. Any flow (e.g., a solver's `order.output.call` in `IntentsBase._execute`) causes ETH to be sent into the shared `CallDispatcher` for an asset not listed in `order.output.assets`; the sweep loop only checks `order.output.assets[i].token`, so this ETH is never swept out and remains as `address(CallDispatcher).balance`.
2. An attacker deploys a minimal contract `AttackerSink` with a `payable` fallback (satisfies the `extcodesize` check in `dispatch`).
3. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: address(AttackerSink), value: address(CallDispatcher).balance, data: ""})]))` from any unprivileged address.
4. `dispatch()` executes `AttackerSink.call{value: balance}("")` successfully since there is no caller restriction, transferring the residual ETH to the attacker. [5](#0-4)

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
