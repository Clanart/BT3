### Title
`ManualCompound.compound` lacks reentrancy protection and uses shared-balance accounting, allowing an attacker with a hooked reward token to steal another user's already-claimed-but-unprocessed rewards - (File: `rewards/ManualCompound.sol`)

### Summary
`ManualCompound.compound()` claims **all** of the caller's pending rewards across every registered reward token in one shot via `multiclaimOnBehalf`, then sequentially converts/distributes each token type using `IERC20(_tokenAddress).balanceOf(address(this))` as the amount to process and routing the output to `msg.sender`. Because the function has no `nonReentrant` guard and the external calls in the distribution loop (`convertFor`, `lockFor`, `depositFor`) can trigger a transfer-hook on one of the reward tokens, an attacker can reenter `compound()` mid-loop and sweep another user's already-claimed-but-not-yet-processed reward token balances to themselves, using their own attacker-chosen `_minRec`/`_convertRatio`.

### Finding Description
`compound()` first claims every reward the caller specifies in one call: [1](#0-0) 

It then loops over all registered reward types and, for each, reads the **entire contract balance** of that token — not a per-call delta — and forwards the conversion output to `msg.sender`: [2](#0-1) 

`_minRec`/`_convertRatio` are raw caller-supplied parameters with no derivation from protocol state, and they gate the entire swept balance in `SmartWomConvert._convertFor`: [3](#0-2) 

The claiming step (`multiclaimOnBehalf` → `_multiClaim`) is `nonReentrant` on `MasterMagpie`, but that guard is released as soon as `_multiClaim` returns — i.e., before the reward-processing loop in `ManualCompound.compound()` even starts: [4](#0-3) 

Because a victim's single `compound()` call claims **multiple** reward token types at once into `ManualCompound`'s shared balance before any of them are distributed, and because `compound()` itself has no reentrancy guard, a hook fired during the `convertFor`/`safeTransferFrom` call for the *first* processed reward token (satisfying the stated precondition that a reward token has an attacker-controlled transfer hook) lets the attacker re-enter `compound()`. In the reentrant call the attacker passes empty `_lps`/`_rewards` (so `multiclaimOnBehalf` claims nothing new) and their own `_minRec`, but the loop still reads `balanceOf(address(this))` for the *next* not-yet-processed reward token — which still holds the victim's freshly claimed balance — and sends the converted proceeds to `msg.sender` of the reentrant call, i.e. the attacker. This is exactly the invariant violation described: the slippage floor (`_minRec`) and the swept amount are decoupled from whose funds they represent, because accounting is balance-based rather than delta/ownership tracked, and there is no reentrancy lock to prevent interleaving.

### Impact Explanation
An unprivileged attacker who controls (or can trigger a callback from) one registered reward token can steal any other reward token balance that a victim has already claimed into `ManualCompound` but not yet had processed within the same transaction. This is direct theft of user funds (Immunefi Critical), since the diverted tokens belong to the victim who initiated the `compound()` call, not the attacker.

### Likelihood Explanation
Exploitability depends entirely on the stated precondition — at least one registered reward token having a transfer hook that an unprivileged party can trigger to reenter. `addReward` is `onlyOwner`-gated, so this requires either a pre-existing reward token with hook/callback semantics (e.g., ERC-777-style or a token with `beforeTransfer`/blacklist callbacks that an attacker can weaponize) or another externally-called component (`_convertor`, `_locker`, `_helperAddress`) with reentrant callback surface. Given that precondition, the attack is fully repeatable and requires no special capital, just triggering a victim's or attacker's own `compound()` call while holding the hook-capable position.

### Recommendation
- Add a `nonReentrant` modifier to `ManualCompound.compound()`.
- Track reward amounts by delta (e.g., balance-before/balance-after around the claim, or have `multiclaimOnBehalf`/`_claimBaseRewarder` return exact claimed amounts) instead of relying on `balanceOf(address(this))`, so distribution is scoped strictly to the current caller's claimed funds.
- Do not let the caller supply `_minRec`/`_convertRatio` for a balance that is not provably 100% theirs; derive/validate against the just-claimed amount.

### Proof of Concept
Hardhat test outline:
1. Deploy `MasterMagpie`, `ManualCompound`, `SmartWomConvert`, and a mock "reward token B" plus a malicious WOM-like token `EvilWom` whose `transferFrom` hook calls back into `ManualCompound.compound()`.
2. Register both `EvilWom` (with `SmartWomConvert` as convertor) and reward token B (e.g., with a locker) via `addReward` (as owner, one-time setup — not attacker-controlled).
3. Victim stakes LP and accrues rewards in both `EvilWom` and token B.
4. Victim calls `compound([lp], [[EvilWom, tokenB]], ratio, minRec, false)`.
5. During processing of `EvilWom` (`convertFor` → `safeTransferFrom`), `EvilWom`'s hook calls `ManualCompound.compound([], [], 0, 0, false)` from the attacker's address.
6. Assert: the reentrant call's `IERC20(tokenB).balanceOf(address(this))` sweeps the victim's already-claimed token B balance and sends it (via `lockFor`/transfer) to the attacker, while the victim's original transaction completes and later sees a zero balance for token B — i.e., the victim's token B rewards end up owned by the attacker despite the victim never having interacted with the attacker.
7. Differential check: run the same claim as one `compound()` call vs. as split calls; show `_minRec` and `obtainedmWomAmount` reconciliation diverges only in the single-call (reentrant) scenario, confirming the shared-balance/no-reentrancy-guard flaw.
