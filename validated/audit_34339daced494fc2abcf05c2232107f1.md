### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` for fee-swap is refunded to the Host contract instead of the payer, permanently trapping funds - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and, when non-zero, forward it to `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. This is the same broken invariant as the reported `BridgeExecutorBase.sol` bug: whenever the exact required amount cannot be known in advance (fee/price fluctuation between quoting and execution), users naturally overpay, and the excess ends up unrecoverable in the contract with no withdrawal path back to them.

### Finding Description
Unlike `IntentGatewayV2`, `ExtrinsicIntents`, and `IntrinsicIntents` in this same repo — which all track `msgValue` explicitly and refund any leftover native token to `msg.sender` at the end of execution (e.g. [1](#0-0) , [2](#0-1) ) — `EvmHost` does not.

In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, the recipient of the Uniswap swap is `address(this)` (the host contract), not `_msgSender()`: [3](#0-2) [4](#0-3) [5](#0-4) 

Uniswap V2's `swapETHForExactTokens(amountOut, path, to, deadline)` computes `amounts[0]` (the exact WETH needed to swap for `to` recipient's `amountOut`), and refunds any dust ETH (`msg.value - amounts[0]`) via `TransferHelper.safeTransferETH(msg.sender, ...)`. Because `EvmHost` itself is the caller of the router (`msg.sender` from the router's perspective is `EvmHost`, `to` is also `address(this)`), **all dust refunded by the router lands back inside `EvmHost`'s own balance**, not the original transaction sender who supplied `msg.value` to `dispatch()`/`fundRequest()`.

There is no function in `EvmHost.sol` that lets a user reclaim this stranded native balance: no `receive()`/sweep-to-sender path, and the only privileged operations found are host-parameter/admin management (`restrict(...)`, `_hostParams.admin` checks) rather than a per-caller withdrawal mechanism. Once a caller sends more ETH than the swap actually consumes — which is unavoidable in practice because the exact swap input amount depends on live AMM reserves at execution time and cannot be predicted exactly off-chain (the report's "hard to hit an exact decimal amount" problem, here amplified by price/slippage drift) — that excess is permanently locked in the `EvmHost` contract with no path to recovery for the payer.

### Impact Explanation
This directly causes loss of funds for any app/user that dispatches a request or funds a pending request using native ETH instead of the fee token. Every overpayment (which will happen routinely since predicting the exact AMM input amount ahead of a state-changing transaction is not reliably possible) is siphoned into the host contract's balance instead of being returned to the payer, with no mechanism to reclaim it. This matches the "loss of funds" bounty category directly and is reachable by any unprivileged user calling public entry points (`dispatch`, `fundRequest`) — no malicious relayer, prover, or admin is required.

### Likelihood Explanation
High. `dispatch()` and `fundRequest()` are the primary, frequently-used entry points for paying relayer fees in native ETH across the entire Hyperbridge EVM app ecosystem (used directly by `IntentGatewayV2`'s cross-chain dispatch path and any third-party integrator calling `IDispatcher(host).dispatch{value: ...}(...)`). Given AMM price movement between fee-quote time and settlement, or callers intentionally sending a safety margin of ETH (as is standard practice and as explicitly tested for in `IntentGatewayV2`'s own overpayment-refund test suite), overpayment is an ordinary, expected occurrence, not an edge case.

### Recommendation
Change the `to` parameter of `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` to refund dust directly to `_msgSender()` (or explicitly capture and refund the leftover balance to `_msgSender()` after the swap, mirroring the pattern already used in `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents`). Alternatively, snapshot the host's ETH balance before/after the swap and forward any delta back to the caller in the same transaction.

### Proof of Concept
1. Attacker/user calls `IDispatcher(host).dispatch{value: 2 ether}(DispatchPost{ fee: 1000e18 feeToken units, ... })` where the actual WETH-in required by the current pool reserves to buy `1000e18` fee tokens is, say, `0.8 ether`.
2. `EvmHost.dispatch` forwards the full `2 ether` to `swapETHForExactTokens(1000e18, [WETH, feeToken], address(this), ...)`.
3. Uniswap V2 router consumes `0.8 ether`, and refunds the remaining `1.2 ether` dust via `safeTransferETH(msg.sender, 1.2 ether)` — but `msg.sender` here is `EvmHost`, so the `1.2 ether` lands in `EvmHost`'s own balance.
4. `dispatch()` returns normally with no error and no refund event; the caller's `1.2 ether` is now stuck in `EvmHost` with no function to withdraw it back to them.
5. Repeating step 1-4 across many callers accumulates locked ETH in `EvmHost` indefinitely.
