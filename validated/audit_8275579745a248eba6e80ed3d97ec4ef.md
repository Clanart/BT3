### Title
Missing HMAC header causes `hmac_valid?` to raise instead of failing closed - ([File: lib/shopify_app/controller_concerns/payload_verification.rb])

### Summary
`ShopifyApp::PayloadVerification#hmac_valid?` passes `shopify_hmac` (which is `nil` when the `X-Shopify-Hmac-Sha256` header is omitted) directly into `ActiveSupport::SecurityUtils.secure_compare`, which calls `.bytesize` on both arguments. An unprivileged attacker can POST to any controller mixing in this concern (`ShopifyApp::ExtensionVerificationController`, and any controller including `ShopifyApp::WebhookVerification`, e.g. `ShopifyApp::WebhooksController`) without the header and trigger a `NoMethodError`/`TypeError` instead of the intended `false` return.

### Finding Description
`hmac_valid?` is invoked from `before_action :verify_request` in both `app/controllers/shopify_app/extension_verification_controller.rb` and `lib/shopify_app/controller_concerns/webhook_verification.rb`. Both call `hmac_valid?(request.raw_post)` unconditionally, with no prior check that the `X-Shopify-Hmac-Sha256` header is present. `shopify_hmac` simply reads `request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]`, which returns `nil` if the attacker omits the header entirely. [1](#0-0) 

Inside `hmac_valid?`, `shopify_hmac` (potentially `nil`) is passed as the first argument to `ActiveSupport::SecurityUtils.secure_compare` alongside a computed Base64 digest string. `ActiveSupport::SecurityUtils.secure_compare` computes `a.bytesize == b.bytesize`, so calling it with `a = nil` raises `NoMethodError: undefined method 'bytesize' for nil` before any comparison happens. This exception is not caught anywhere in `PayloadVerification`, `WebhookVerification`, or `ExtensionVerificationController`; there is no `rescue_from` for this in these controllers. [2](#0-1) [3](#0-2) 

Both routes are public/unauthenticated by design (they exist specifically to validate incoming webhook/extension requests before any session exists), so an anonymous attacker can reach them with zero preconditions. The `secrets.any? { ... }` block will raise on the first secret evaluated, so the error is unconditional whenever the header is missing — it does not depend on knowledge of the app secret.

### Impact Explanation
This is an availability/robustness issue: an unauthenticated request reaching a fail-open exception (uncaught in the framework's request cycle) results in an unhandled exception on a public route. Depending on the app's exception-handling configuration (`config.consider_all_requests_local`, custom `exceptions_app`, etc. — not controlled by this gem), this can manifest as a 500 response, potentially with a backtrace disclosed if the host app runs with `consider_all_requests_local = true` (common misconfiguration, though the underlying code defect exists regardless of host configuration). Functionally, `hmac_valid?` should deterministically "fail closed" (return `false`) for any malformed/missing HMAC input; raising instead violates that invariant even if in most deployments Rails' default exception handling still results in a non-2xx response and does not itself grant unauthorized access. This maps most closely to a robustness/denial-of-service-adjacent defect (unhandled exception on unauthenticated input) rather than a direct auth-bypass, since a raised exception still blocks the webhook/extension action from being treated as verified.

### Likelihood Explanation
Trivial and 100% reproducible: any anonymous POST to a route using `ExtensionVerificationController` or a controller including `WebhookVerification` (e.g., the app's mounted `webhooks` route) without the `X-Shopify-Hmac-Sha256` header immediately raises. No secrets, tokens, or shop context are required.

### Recommendation
Guard against a missing/blank HMAC header before calling `secure_compare`, e.g.:
```ruby
def hmac_valid?(data)
  return false if shopify_hmac.blank?

  secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)
  secrets.any? do |secret|
    digest = OpenSSL::Digest.new("sha256")
    ActiveSupport::SecurityUtils.secure_compare(
      shopify_hmac,
      Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
    )
  end
end
```
This ensures `hmac_valid?` fails closed (`false`) without ever calling `secure_compare` with a `nil` argument.

### Proof of Concept
```ruby
# test/shopify_app/controller_concerns/payload_verification_test.rb (or webhooks_controller_test.rb)
test "missing HMAC header does not raise and fails closed" do
  ShopifyApp.configure { |c| c.secret = "secret" }

  post "/webhooks/orders_create", params: {}.to_json,
       headers: { "CONTENT_TYPE" => "application/json" } # no X-Shopify-Hmac-Sha256 header

  # Expected (post-fix): response.status == 401
  # Actual (current code): NoMethodError raised inside hmac_valid?,
  # propagating as an unhandled exception / 500 response instead of 401.
  assert_response :unauthorized
end
```
Running this against the current implementation raises `NoMethodError: undefined method 'bytesize' for nil` from within `ActiveSupport::SecurityUtils.secure_compare`, confirming the unhandled-exception path.
