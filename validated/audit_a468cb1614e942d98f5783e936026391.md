### Title
BalanceHandler `prevEventsLen` desync during recursive/nested precompile calls corrupts EVM StateDB balances relative to bank-module truth - ([File: precompiles/common/balance_handler.go])

### Summary
The H-26 root cause is a derived/cached value (borrowing rate) that is not recomputed when the underlying state it depends on (pool base amount) changes via a code path that bypasses the update hook. The Cosmos EVM analog is `BalanceHandler.prevEventsLen`, a single mutable cursor into `ctx.EventManager().Events()` that is used to translate native `x/bank`/`x/precisebank` events into `StateDB.AddBalance`/`SubBalance` calls after a precompile executes. When precompile calls recurse (a precompile call triggers another EVM call that invokes a second precompile, or a contract makes nested precompile calls), the same `BalanceHandler` instance's `prevEventsLen` is overwritten by the inner call's `BeforeBalanceChange`, so the outer call's `AfterBalanceChange` computes the wrong event-slice offset — mirroring exactly the "state changed but the dependent value not being kept in sync" bug class from H-26.

### Finding Description
`BalanceHandler` records an event-index cursor before a precompile executes: [1](#0-0) 

and later replays only the events appended after that cursor to update `StateDB` balances: [2](#0-1) 

This design assumes `BeforeBalanceChange`/`AfterBalanceChange` are called in strict, non-overlapping pairs for a single instance. The repository's own regression test explicitly documents that this assumption is violated for recursive precompile calls, which "share the same `BalanceHandler` instance, causing `prevEventsLen` to be overwritten," leading to "balance desync between native bank keeper and EVM stateDB": [3](#0-2) 

The test reproduces this via a debug precompile invoked recursively from a caller contract, asserting a specific count of `debug_precompile` events fired during the recursive call chain: [4](#0-3) 

If an inner precompile invocation's `BeforeBalanceChange` resets `prevEventsLen` to a higher index than the offset the outer invocation expects, the outer `AfterBalanceChange` will skip processing bank events that occurred between the outer's true starting point and the inner's reset point — meaning some `CoinSpent`/`CoinReceived`/`EventTypeFractionalBalanceChange` events never get applied to `StateDB.AddBalance`/`SubBalance`. Since actual coin movement in `x/bank`/`x/precisebank` has already occurred (and will be committed to the KVStore), while the EVM `StateDB` balance is left stale/incorrect for the addresses involved, the two balance views diverge. Because `StateDB` balances are what subsequent EVM opcodes (`BALANCE`, `SELFBALANCE`) and further transfers within the same or later transactions read and act on, this stale value can be leveraged to spend, transfer, or account for value that either does not exist in `StateDB` (permanent loss of EVM-visible funds) or exists in `StateDB` without a matching bank-side debit (duplication of spendable value), corrupting the money-supply invariant between native coin balances and EVM-visible balances that `x/precisebank`/`x/vm` are designed to preserve.

### Impact Explanation
This falls squarely under the "Critical unauthorized minting, burning, duplication, resurrection, or irreversible accounting corruption of spendable user value across native balances, EVM balances... or precompile-mediated assets" impact class, since the divergence is a direct 1:1 accounting break between `x/bank`/`x/precisebank` state and the EVM `StateDB` balance — the two systems that `x/vm`'s `SetBalance`/`BankWrapper` and `BalanceHandler` are explicitly responsible for keeping consistent, as documented in the precisebank invariant description: [5](#0-4) [6](#0-5) 

### Likelihood Explanation
Trigger requires only an unprivileged user deploying/calling a contract that performs nested precompile calls (e.g., a contract calling a precompile that itself invokes `CallEVM`/`CallEVMWithData` into another precompile, or reentrant precompile-to-precompile calls), a pattern reachable via ordinary transactions and already exercised by the repository's own regression test using recursive calls through a caller contract. I was not able to fully confirm, within the remaining investigation budget, whether the current `precompiles/common/precompile.go` `RunNativeAction` wrapper already scopes `BalanceHandler` per call-frame (e.g., via a stack, or by constructing a fresh handler per invocation) to fully close this gap, or whether the shared-instance issue described by the test comment is still exploitable end-to-end for value extraction (as opposed to only causing incidental event-count/log discrepancies as asserted in the test). This is a material uncertainty and should be verified directly against `precompiles/common/precompile.go` and the debug precompile's calling pattern before treating this as confirmed-exploitable in production.

### Recommendation
Ensure `BalanceHandler` state (`prevEventsLen`) is scoped per call-frame rather than shared across nested/recursive precompile invocations — e.g., by pushing/popping a stack of cursors, or by instantiating a new `BalanceHandler` for every `RunNativeAction` invocation and snapshotting/restoring the outer handler's cursor around nested calls — so that `AfterBalanceChange` always replays exactly the event slice produced by its own paired `BeforeBalanceChange`, regardless of call depth. Add invariant checks (e.g., reconciling total `StateDB` balance deltas against total bank-module event deltas for a transaction) to fail closed rather than silently desyncing.

// SetBalance update account's balance, compare with current balance first, then decide to mint or burn.
func (k *Keeper) SetBalance(ctx sdk.Context, addr common.Address, amount *uint256.Int) error {
	if amount == nil {
		return nil
	}
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	coin := k.bankWrapper.SpendableCoin(ctx, cosmosAddr, types.GetEVMCoinDenom())

	balance := coin.Amount.BigInt()
	delta := new(big.Int).Sub(amount.ToBig(), balance)
	switch delta.Sign() {
	case 1:
		// mint
		if err := k.bankWrapper.MintAmountToAccount(ctx, cosmosAddr, delta); err != nil {
			return err
		}
	case -1:
		// burn
		if err := k.bankWrapper.BurnAmountFromAccount(ctx, cosmosAddr, new(big.Int).Neg(delta)); err != nil {
			return err
		}
	default:
		// not changed
	}
	return nil
}
