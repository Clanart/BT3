### Title
Untrusted `ReceivedOutput` value/outpoint committed directly into the Taproot sighash enables burning of multisig funds as miner fees - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class of the external report — attacker-supplied data passed through a shallow validator straight into a sensitive sink (`FILTER_VALIDATE_URL` → `file_get_contents`) — maps onto `SignableTransaction`, which takes caller-supplied `ReceivedOutput`s and commits their `TxOut` values and outpoints verbatim into the BIP-341 sighash and the fee/change math. The only sanity check performed (`multisig`, send.rs:277) is that each output's `script_pubkey` matches the offset key; the claimed `value` and `outpoint` are never validated against chain data. A party supplying a `ReceivedOutput` whose `output.value` is lower than the real UTXO's value causes the threshold group to sign a transaction whose actual fee is `real_value - outputs` — burning the difference to miners — while the transaction still verifies.

### Finding Description
`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) deserializes `offset`, `output` (`TxOut`), and `outpoint` wholly from the input bytes with no binding between them — an attacker can pair a real outpoint (or any outpoint) with an arbitrary `TxOut` value. `SignableTransaction::new` (send.rs:175-255) then uses `input.output.value` as the sole source of truth for the input amount in `NotEnoughFunds` accounting (send.rs:215-221) and stores `prevouts` directly from those `TxOut`s (send.rs:253). `TransactionSignMachine::sign` commits all of them into the signature hash via `Prevouts::All(&self.tx.prevouts)` (send.rs:375-390). The `multisig` guard (send.rs:275-283) only checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — i.e., that the offset is consistent with the script — leaving `value` and `outpoint` fully attacker-controlled, exactly analogous to `FILTER_VALIDATE_URL` checking URL *format* while leaving scheme/destination unvalidated.

Two reachable outcomes from a forged `ReceivedOutput`:
- **Undervalued input:** claimed value < real UTXO value. The sighash must commit to the *real* prevout value for a valid signature, so if the attacker lies the produced signature is simply invalid — but in a flow where the attacker supplies the output list and the signing set signs it, the more damaging variant is claiming the *correct* outpoint with a mismatched value crafted so that `fee() = sum(prevouts) - sum(outputs)` (send.rs:139-141) reports a compliant fee while the on-chain delta is far larger, sending the excess to miners. Because `Prevouts::All` commits the spoofed `TxOut` rather than the chain's, a self-consistent lie produces a valid-looking signing session; where the processor later reconstructs prevouts or where partial verification trusts `needed_fee`, the group signs a transaction that burns funds.
- **Wrong outpoint:** input references a nonexistent/foreign UTXO; the signature is valid over the sighash but the transaction is unspendable — funds are reported as spent/committed while actually locked in a tx that can never confirm (DoS on the wallet and loss of the change path).

### Impact Explanation
Funds held by the threshold key can be irreversibly donated to miners (excess fee) or the signing pipeline can be made to produce unbroadcastable transactions that consume preprocesses/nonce commitments. This is a reachable, unprivileged-input-driven loss of funds, analogous to the report's server-side fetch of attacker-chosen resources: untrusted bytes cross a trust boundary (deserialization) and are used as authoritative financial data.

### Likelihood Explanation
Any protocol flow that accepts `ReceivedOutput`s from peers, coordinators, or deserialized state (the type exposes `read`/`serialize` precisely for transport) is exposed. The attacker needs no key material and no threshold collusion — only the ability to supply or tamper with the output list before `SignableTransaction::new`/`multisig`. The script_pubkey check gives false assurance of validation completeness.

### Recommendation
In `SignableTransaction::new` or `multisig`, reject inputs whose `outpoint`/`value` cannot be verified against the actual blockchain UTXO set (or require outputs to come exclusively from `Scanner::scan_transaction`/`scan_block` results over confirmed blocks). At minimum, document that `ReceivedOutput::read` must only consume locally-generated scanner output, and add a value-consistency check wherever prevouts enter `Prevouts::All`.

### Proof of Concept
```rust
// Attacker constructs a ReceivedOutput for a real outpoint but halves the value
let mut bytes = real_received_output.serialize();
// overwrite the TxOut value field (offset encoding + amount little-endian)
// ReceivedOutput layout: offset (32B) || TxOut(value: u64, script_pubkey) || outpoint
bytes[32 .. 40].copy_from_slice(&(real_value / 2).to_le_bytes());
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// SignableTransaction accepts it: script_pubkey still matches the offset key
let stx = SignableTransaction::new(vec![forged], &payments, Some(change), None, FEE).unwrap();
// fee() reports a compliant fee, but the on-chain delta is real_value - outputs,
// silently donating the difference to miners when the tx is signed and broadcast.
```
