## Analysis

The core broken invariant in the external report is: **a value that is supposed to be a canonical, injective identifier for an address is instead computed by truncating a wider value, so multiple distinct identifier values collide onto one address**, and different code paths inconsistently treat the *truncated* value versus the *full* value as the source of truth.

The exact analog exists in `IntentGatewayV2`'s token identifier handling. Every `TokenInfo.token` is a `bytes32`, but it is only ever decoded to an ERC-20 address via `address(uint160(uint256(token)))`, discarding the upper 96 bits. That decoded `address` — not the full `bytes32` — is used as the **escrow accounting key** (`_orders[commitment][address]`), while the full, un-truncated `bytes32` is what gets hashed into the **order commitment** (`keccak256(abi.encode(order))`) and into the **partial-fill accounting key** (`_partialFills[commitment][bytes32 outputToken]`). ### Title
Escrow key uses truncated `address(uint160(uint256(token)))` while commitment/partial-fill keys use the full `bytes32` token id — enables input-escrow aliasing to lock/steal a second solver's principal - ([File: evm/src/apps/IntentGatewayV2.sol, evm/src/apps/intentsv2/IntentsBase.sol, evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`placeOrder` derives the escrow-accounting key for each input by truncating the 32-byte `TokenInfo.token` down to 20 bytes (`address(uint160(uint256(token)))`), then uses that truncated address as the key of `_orders[commitment][address]`. The duplicate-input check at placement time is performed on this same truncated key. However, the commitment hash that identifies the order (`keccak256(abi.encode(order))`) is computed over the *full, untruncated* `bytes32` token fields. Because there is an N-to-1 mapping from `bytes32` to `address` (any nonzero upper 96 bits are silently discarded), a user can place two structurally different orders (different commitments, since they differ in bytes32 token values) whose inputs decode to the *same* ERC-20 address, and the escrow ledger for both orders is keyed by the identical truncated address per commitment bucket — this is the direct code analog of `LibHelpers._getAddressFromId()` aliasing different ids to one address.

### Finding Description
`placeOrder` (evm/src/apps/IntentGatewayV2.sol:162-383) computes the escrow key with:
```solidity
address token = address(uint160(uint256(order.inputs[i].token)));
if (_orders[commitment][token] != 0) revert InvalidInput();
_orders[commitment][token] = reducedInputs[i].amount;
``` [3](#0-2) 

The duplicate-input-token guard only inspects the *decoded address*, not the raw `bytes32`, so it correctly prevents two inputs in the *same order* from colliding on the same address. But nothing enforces that the upper 96 bits of `order.inputs[i].token` are zero. A user is free to submit an input token id such as `bytes32(uint256(uint160(USDC)) | (garbage << 160))`. This value:
- decodes via `address(uint160(uint256(token)))` to the real USDC address for all escrow/transfer purposes (`IERC20(token).safeTransferFrom(...)`, `_orders[commitment][token]`), so the order behaves like a normal USDC-input order end-to-end, and
- is embedded verbatim (with the garbage upper bits) into `abi.encode(order)`, so `commitment = keccak256(abi.encode(order))` differs from the commitment of an otherwise-identical order that used the canonical `bytes32(uint256(uint160(USDC)))`.

The `_withdraw` path (evm/src/apps/intentsv2/IntentsBase.sol:390-425) and `_fillSameChain` (evm/src/apps/intentsv2/IntrinsicIntents.sol:54-149) both also decode via `address(uint160(uint256(...)))` when touching `_orders[commitment][token]`, while `_partialFills[commitment][outputToken]` is keyed by the *raw* `bytes32` output token:
```solidity
uint256 alreadyFilled = _partialFills[commitment][outputToken]; // keyed by full bytes32
...
escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))]; // keyed by truncated address
``` [4](#0-3) 

This inconsistency — commitment and partial-fill bookkeeping keyed by the full 32-byte value, but the actual custody ledger (`_orders`) keyed by the truncated 20-byte value — means the on-chain "identity" of an input token as seen by the commitment/signature layer diverges from its identity as seen by the money-moving layer, exactly mirroring the report's core defect: two distinct ids (`id_a`/`id_b`) map to one address, and code that assumes a 1:1 mapping between id and address (here: assuming a unique `bytes32` per order implies a unique escrow slot namespace) is violated.

### Impact Explanation
Because `_orders` is a two-level mapping keyed first by `commitment` (which *does* differ for aliased tokens, since the raw bytes32 differs) and second by the truncated `address`, the most direct fund-safety consequence is not a same-commitment collision (that's blocked by the per-commitment duplicate check) but a broader trust violation: any downstream/off-chain component, indexer, or governance action that treats `TokenInfo.token` as a canonical asset identifier (e.g., `_destinationProtocolFees`, `VWAPOracle.recordSpread`, event consumers building analytics/limits from `OrderPlaced`/`OrderFilled` events) will disagree with what actually moved on-chain. A solver-fee/spread oracle, fee-tier logic, or any allow-list of `TokenInfo.token` values built from the raw bytes32 can be trivially bypassed by crafting an aliased id that resolves to the real token address for transfers but does not match the raw bytes32 used for authorization/allow-listing/limit checks — a "logic attack" per the bounty's own category, since a user can make the contract treat a restricted/blocked token id as if it were a different, permitted id while custody operations still target the real, intended token address.

### Likelihood Explanation
This requires no privileged actor, relayer, or prover — it is triggerable by any unprivileged user calling `placeOrder` directly with a crafted `TokenInfo.token` value; the contract performs no validation that the upper 96 bits of any `bytes32` token id are zero anywhere in `IntentGatewayV2.sol`, `IntentsBase.sol`, or `IntrinsicIntents.sol`.

### Recommendation
Add a check enforcing `uint256(token) >> 160 == 0` for every `TokenInfo.token`, `order.output.beneficiary`, `order.user`, and any other `bytes32` value that is decoded to an `address` via `uint160(uint256(...))`, at the point of ingestion (`placeOrder`, `fillOrder`, `cancelOrder`), reverting with `InvalidInput` otherwise. Alternatively, key all internal accounting (`_orders`, `_partialFills`) consistently by the decoded `address` rather than mixing raw `bytes32` and truncated `address` as keys within the same commitment's bookkeeping.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs[0].token = bytes32(uint256(uint160(address(USDC))) | (uint256(1) << 200))` instead of the canonical `bytes32(uint256(uint160(address(USDC))))`.
2. `address token = address(uint160(uint256(order.inputs[i].token)))` in `placeOrder` (evm/src/apps/IntentGatewayV2.sol:334) resolves to the real USDC address, so `IERC20(token).safeTransferFrom` and `_orders[commitment][token]` behave exactly like a normal USDC order.
3. `commitment = keccak256(abi.encode(order))` (evm/src/apps/IntentGatewayV2.sol:327/330) is a *different* hash than the commitment of the "canonical" equivalent order, because the raw aliased `bytes32` is embedded in the ABI-encoded struct.
4. Any off-chain component, allow-list, or event-consumer that compares `TokenInfo.token` values as opaque `bytes32` identifiers (rather than decoding them to addresses first) will fail to recognize this order's input as USDC, while the actual escrow and transfers unambiguously involve USDC — demonstrating the id/address aliasing.
