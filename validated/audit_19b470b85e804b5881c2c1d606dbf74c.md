### Title
Scanner::scan_block credits coinbase outputs that are not spendable for 100 blocks - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The audit issue describes a fallible operation (an ERC20 `transferFrom` that can return `false` instead of reverting) whose failure status is ignored, so the protocol credits/mints value for a deposit that never happened. The Serai analog is `Scanner::scan_block` in `networks/bitcoin/src/wallet/mod.rs`: it iterates `block.txdata` including `block.txdata[0]` (the coinbase transaction) and reports every output whose `script_pubkey` matches a registered script as a spendable `ReceivedOutput`, without checking the coinbase-maturity condition. Coinbase outputs are unspendable for 100 blocks, so funds are reported as received when they are not yet spendable.

### Finding Description
`scan_transaction` matches only on `output.script_pubkey` and immediately constructs a `ReceivedOutput` [1](#0-0) . `scan_block` applies this to every transaction including the coinbase [2](#0-1) . There is no flag on `ReceivedOutput` distinguishing coinbase-origin outputs, and `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs:150` consumes any `ReceivedOutput` as an input without a maturity check. The only mitigation is a doc comment telling callers to post-filter — the failure condition (immature coinbase) is silently ignored, exactly like the unchecked `transferFrom` return value.

### Impact Explanation
Any miner (an unprivileged party who controls coinbase transaction outputs) can pay to a Serai-scanned script in a coinbase. The scanner reports the output as received; downstream code can then build and threshold-sign a transaction spending it via `SignableTransaction::new`/`TransactionMachine`, producing a transaction that is invalid under consensus rules (immature coinbase spend) and will never confirm. This is "funds reported received that are not spendable" plus wasted signing sessions on an unspendable input — the same failure shape as crediting a deposit whose transfer silently failed.

### Likelihood Explanation
Requires a miner to target a Serai deposit script in their coinbase — feasible but requires mining a block. Impact is bounded: the output becomes spendable after 100 confirmations, and signing a premature spend fails at relay rather than losing funds. Medium.

### Recommendation
Track whether each `ReceivedOutput` originates from a coinbase transaction (e.g., a `coinbase: bool` field set in `scan_transaction`/`scan_block`, or have `scan_block` skip `block.txdata[0]` and expose a separate `scan_coinbase`). Reject or withhold coinbase-derived outputs in `SignableTransaction::new` until maturity rather than relying on callers to post-filter.

### Proof of Concept
1. A miner registers/learns a Serai deposit script (e.g., `p2tr_script_buf` of the group key or a registered offset via `Scanner::register_offset`).
2. The miner's coinbase transaction includes a `TxOut` paying that `script_pubkey`.
3. `Scanner::scan_block(&block)` returns a `ReceivedOutput` for it (`outpoint = OutPoint::new(coinbase_txid, vout)`).
4. Passing this output to `SignableTransaction::new` and through `TransactionMachine`/`TransactionSignMachine::sign` yields a fully signed transaction spending an immature coinbase output — invalid per consensus (COINBASE_MATURITY = 100) and rejected by the network, despite Serai having treated the funds as received and spendable.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
