### Title
Unhandled exception when decoding a malformed/incompatible offer file allows a spend-triggered processing halt in offer parsing - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.try_offer_decompression()`, which is on the path used to parse untrusted offer files/bech32 strings received from an offer counterparty (`Offer.from_bech32()`, `Offer.from_bytes()`), only guards against `TypeError` when attempting decompression. The underlying `decompress_object_with_puzzles()` can raise other, uncaught exception types (`CompressionVersionError`, `zlib.error`) when fed malformed or non-compressed input, exactly mirroring the branca advisory pattern: a decode routine that is expected to signal invalid input via a controlled error instead propagates an unexpected exception.

### Finding Description
`Offer.from_bech32()` decodes an attacker/counterparty-supplied bech32 string and immediately calls `try_offer_decompression()`: [1](#0-0) 

`try_offer_decompression()` attempts to treat the bytes as a compressed offer, but only catches `TypeError`: [2](#0-1) 

The decompression routine it calls, `decompress_object_with_puzzles()`, reads a 2-byte version prefix from the untrusted bytes and raises `CompressionVersionError` (a plain `Exception` subclass, not `TypeError`) if the version exceeds the known dictionary count, and otherwise feeds the remaining bytes into `zlib.decompressobj().decompress()`, which raises `zlib.error` on malformed/corrupt deflate streams: [3](#0-2) 

Because arbitrary attacker-controlled bytes almost always fail to decode as a valid zlib stream with the correct 2-byte version prefix, `try_offer_decompression()`'s fallback logic (`except TypeError: pass` then `cls.from_bytes(offer_bytes)`) is bypassed whenever the actual failure mode is `CompressionVersionError` or `zlib.error` — these propagate unhandled out of `Offer.from_bech32()`/`Offer.from_bytes()`/`Offer.from_compressed()`.

### Impact Explanation
Offer parsing (`from_bech32`, used by wallet CLI `take_offer`, and RPC endpoints that check/accept offer files) is a primary interface for interacting with untrusted offer files from third parties. A malformed or intentionally malicious offer string causes an unhandled `CompressionVersionError`/`zlib.error` instead of the intended, gracefully handled parse failure. This can crash the offer-processing code path or trade-manager task that expects only well-defined exceptions (e.g. `ValueError`) from offer parsing, producing a spend-triggered transaction-processing halt for the wallet/RPC caller handling that offer, consistent with the "unexpected panic on malformed decode input" bug class from the branca advisory. Severity is bounded by the fact that this affects local wallet/RPC error handling rather than causing fund loss or consensus divergence, so it maps to a Medium-severity denial-of-service-style processing halt rather than fund theft.

### Likelihood Explanation
Any offer counterparty or malicious file supplier can trivially trigger this by sending a bech32/byte string whose first two bytes decode to a version greater than `len(ZDICT)`, or whose remaining bytes are not valid zlib output — both are the overwhelmingly common case for arbitrary/corrupted input, making the unhandled path easy to hit unintentionally or intentionally.

### Recommendation
Widen the exception handling in `Offer.try_offer_decompression()` to catch `CompressionVersionError` and `zlib.error` (or catch a common base/tuple of expected decode-failure exceptions) alongside `TypeError`, and re-raise a well-defined `ValueError`/application-level error so callers (CLI, RPC, trade manager) can handle malformed offers gracefully instead of crashing on an unexpected exception type.

### Proof of Concept
1. Construct a byte string that is not a validly-compressed offer, e.g. `offer_bytes = b"\xff\xff" + b"not a valid zlib stream"` (version bytes `0xFFFF` far exceed `len(ZDICT)`).
2. Call `Offer.try_offer_decompression(offer_bytes)`.
3. Observe that `decompress_object_with_puzzles()` raises `CompressionVersionError`, which is not caught by the `except TypeError` clause in `try_offer_decompression`, so the exception propagates out uncaught instead of falling back to `cls.from_bytes(offer_bytes)` — unlike the intended graceful-failure behavior demonstrated for other malformed-input cases.

Note: I was unable to fully trace every downstream caller (e.g., exact exception-handling behavior inside `trade_manager.py` and the wallet RPC `take_offer`/`check_offer_validity` handlers) within the available search budget, so the ultimate observable effect (raw 500 error vs. process crash vs. silently dropped task) at each call site is not fully confirmed and would benefit from direct testing in a live environment.

class CompressionVersionError(Exception):
    def __init__(self, version_number: int):
        self.message = f"The data is compressed with version {version_number} and cannot be parsed. "
        self.message += "Update software and try again."


def zdict_for_version(version: int) -> bytes:
    summed_dictionary = b""
    for version_dict in ZDICT[0:version]:
        summed_dictionary += version_dict
    return summed_dictionary


def compress_with_zdict(blob: bytes, zdict: bytes) -> bytes:
    comp_obj = zlib.compressobj(zdict=zdict)
    compressed_blob = comp_obj.compress(blob)
    compressed_blob += comp_obj.flush()
    return compressed_blob


def decompress_with_zdict(blob: bytes, zdict: bytes) -> bytes:
    do = zlib.decompressobj(zdict=zdict)
    return do.decompress(blob, max_length=6 * 1024 * 1024)  # Limit output size


def decompress_object_with_puzzles(compressed_object_blob: bytes) -> bytes:
    version = int.from_bytes(compressed_object_blob[0:2], "big")
    if version > len(ZDICT):
        raise CompressionVersionError(version)
    zdict = zdict_for_version(version)
    object_bytes = decompress_with_zdict(compressed_object_blob[2:], zdict)
    return object_bytes
