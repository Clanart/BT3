I found a solid, locally-provable analog. The Tron variant of `IntentGatewayV2` deliberately switched from OpenZeppelin's strict `IERC20`/`SafeERC20` interface (used to avoid the exact bug class described in the external report) to raw low-level `.call()` for escrow payouts — but only checks the low-level call's `success` flag and never decodes/validates the returned `bool` payload. This reintroduces the very unchecked-transfer risk the external report warns about, in the opposite direction: instead of reverting on non-standard tokens, it now silently accepts failed transfers from standard tokens that return `false` instead of reverting.

### Title
Escrow withdrawal treats `transfer()` returning `false` as success, permanently burning escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` and the `SweepDust` handler in the Tron `IntentGatewayV2` pay out escrowed ERC20 tokens using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check the outer `success` boolean of the call, never inspecting the ABI-encoded return data. [1](#0-0) [2](#0-1) 

### Finding Description
Per EIP-20, `transfer` returns a `bool` indicating success; many compliant tokens return `false` on failure rather than reverting (e.g., insufficient allowance corner-cases, blacklist/pausable tokens, or custom fee/rebasing tokens). A low-level `.call()` only reports `success = true` when the callee did not revert — it does not verify the returned boolean. Because `withdraw()` and the `SweepDust` branch check only `success`/`!success` and ignore the returned bytes, a token call that executes without reverting but returns `abi.encode(false)` is treated as a successful transfer. [3](#0-2) 

Immediately after the "successful" transfer call, escrow accounting is unconditionally decremented: [4](#0-3) 

and `_filled[body.commitment]` is marked settled before the loop even begins: [5](#0-4) 

So if the underlying token silently fails (returns `false`) instead of reverting, the beneficiary never receives the tokens, but the protocol's internal ledger (`_orders[...]`) is decremented and the order is marked as filled/redeemed. The tokens remain custodied in the contract with no accounting entry pointing to them and no path to reclaim them for the intended beneficiary — the escrow is drained on paper while the actual asset stays stuck (loss of funds / bridge custody failure), and because `_filled` is already set, the associated `RedeemEscrow`/`RefundEscrow` request cannot be retried through this code path.

This is the direct inverse of the report's bug class: the report flagged reverting-when-it-shouldn't (breaking transfers for non-standard tokens like USDT); here the "fix" over-corrects by never reverting even when a standards-compliant token explicitly signals failure via `false`, because only call-success (not return-data) is checked. Unlike `SafeERC20.safeTransfer` (used elsewhere in the same file, e.g. for input escrow) which validates both call success and truthy return data (or absence of return data per EIP-20 optionality), the raw `.call()` pattern here validates neither. [6](#0-5) 

### Impact Explanation
This breaks the "bridged assets... must move exactly once and only to the rightful beneficiary and amount" invariant: escrow is debited from `_orders` and the order state is finalized in `_filled` while the actual token balance is never delivered to the beneficiary. This is unauthorized loss of user/solver funds during cross-chain intent settlement with no recovery path once `_filled` is set, since the withdrawal is treated as complete by the contract.

### Likelihood Explanation
No malicious peer, relayer, prover, or governance actor is required. Any ERC20 token integrated into the gateway (a normal, unprivileged token contract already whitelisted for use in orders) that returns `false` on failed transfer — a legitimate, EIP-20-compliant behavior — triggers this on the very first legitimate `RedeemEscrow`/`RefundEscrow`/`SweepDust` request that hits an edge case (e.g., paused token, blacklisted beneficiary, insufficient token-side balance due to fee-on-transfer interactions elsewhere in the same contract). Given the codebase already handles fee-on-transfer and other non-standard tokens elsewhere (see `FeeOnTransferToken` test fixture), the assumption that all payout tokens strictly revert on failure is not safe in this same protocol. [3](#0-2) 

### Recommendation
Replace the raw `.call()` payout pattern in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the same file (`using SafeERC20 for IERC20;`). `safeTransfer` correctly handles both non-standard tokens (no return value) and standard tokens that return `false`, reverting in the latter case instead of silently marking the escrow as settled. [7](#0-6) 

### Proof of Concept
1. Deploy an ERC20 token whose `transfer` function returns `false` (without reverting) when, e.g., the recipient is on an internal blacklist or a per-tx cap is exceeded — fully EIP-20 compliant behavior.
2. Use this token as an order input asset in `IntentGatewayV2` on Tron; it gets escrowed normally via `safeTransferFrom` at line 453/399 (which works fine on the input side).
3. Trigger a legitimate `RedeemEscrow` (fill settlement) or `RefundEscrow` (cancellation) request that calls `withdraw()` with the beneficiary address that the token will reject (return `false` for).
4. In `withdraw()` at lines 693-699, `token.call(...)` succeeds (no revert) but returns `abi.encode(false)`; `success` is `true` so no revert occurs.
5. `_orders[body.commitment][token] -= amount` executes at line 701, zeroing out escrow accounting, and `_filled[body.commitment]` was already set at line 684 — the order is now permanently marked settled.
6. The beneficiary's token balance never changed; the tokens remain stuck in the `IntentGatewayV2` contract with no on-chain accounting pointing to them, and the withdrawal cannot be retried since `_filled`/`_orders` already reflect completion. [8](#0-7)
