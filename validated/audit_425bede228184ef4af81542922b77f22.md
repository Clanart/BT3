The reported fee-on-transfer bug class has a direct analog in Kaia's service-chain bridge contracts, which are public system contracts reachable by any unprivileged token holder.

### Title
Bridge accounting for ERC20 fee-on-transfer tokens uses declared `_value` instead of actually received amount, enabling supply/value mismatch across chains - (File: contracts/service_chain/bridge/BridgeTransferERC20.sol)

### Summary
`BridgeTransferERC20.requestERC20Transfer` pulls tokens via `safeTransferFrom` using the caller-declared `_value + _feeLimit`, but all downstream accounting (fee bookkeeping, burn amount, and the emitted `RequestValueTransfer` event that the counterpart-chain relayer/operator trusts) uses the declared `_value` rather than the amount the bridge contract actually received. If `_tokenAddress` is a fee-on-transfer (deflationary) ERC20, the bridge receives less than `_value + _feeLimit`.

### Finding Description
`requestERC20Transfer` transfers tokens in with no balance-delta check: [1](#0-0) 

The internal `_requestERC20Transfer` then charges fee, optionally burns `_value`, and emits `RequestValueTransfer` carrying the full declared `_value`: [2](#0-1) 

On the counterpart chain, an operator later calls `handleERC20Transfer`, which mints (`modeMintBurn == true`) or transfers out (`modeMintBurn == false`) the exact `_value` from the `RequestValueTransfer` event, with no cross-check against the amount actually locked/burned on the source chain: [3](#0-2) 

Because the whole flow (fee accounting, burn, and cross-chain mint/unlock) is driven by the caller-declared `_value` and not by an actual balance-diff measurement of what the bridge contract received, a fee-on-transfer token breaks the 1:1 backing assumption between the two chains.

### Impact Explanation
- In `modeMintBurn = true` deployments, `ERC20Burnable(_tokenAddress).burn(_value)` burns the full declared value from the bridge's pooled balance. If the bridge holds enough tokens from other users' prior deposits, the burn silently succeeds even though this particular depositor's fee-on-transfer transfer delivered less than `_value` to the bridge. The counterpart chain still mints the full `_value`, so the destination-chain wrapped supply becomes under-collateralized, effectively socializing the shortfall across all other bridge depositors — this is unauthorized value/supply inflation on the destination chain.
- In lock/unlock mode, the bridge similarly emits/tracks more locked value than it actually holds, degrading the 1:1 backing and potentially causing insolvency when users try to redeem locked tokens later.
This matches the "Accept only concrete unauthorized value movement, supply inflation" criterion in the validation rules.

### Likelihood Explanation
Reachable via a single, unprivileged transaction: any ERC20 holder can call `requestERC20Transfer` (or the 1-step `onERC20Received`/`ERC20ServiceChain.requestValueTransfer` path) directly on the deployed bridge system contract with a whitelisted fee-on-transfer token. The only precondition is that the token is registered on the bridge (`onlyRegisteredToken`), which is a normal operational configuration rather than a privileged attacker capability — the vulnerability is triggered by the mismatch between `_value` bookkeeping and actual token semantics, not by any admin misbehavior.

### Recommendation
Measure the bridge's own token balance before and after `safeTransferFrom` in `requestERC20Transfer` (and in `onERC20Received`), and use that balance delta — not the caller-supplied `_value`/`_feeLimit` — for fee calculation, burn amount, and the value emitted in `RequestValueTransfer`. Alternatively, explicitly disallow non-standard (fee-on-transfer, rebasing) tokens from being registered via `onlyRegisteredToken`.

### Proof of Concept
1. Register a fee-on-transfer ERC20 token (e.g., one that deducts 10% on every `transfer`/`transferFrom`) on the bridge via governance/operator registration (`onlyRegisteredToken`).
2. User approves the bridge for `_value + _feeLimit` and calls `requestERC20Transfer(token, to, _value, _feeLimit, extraData)`.
3. `safeTransferFrom` moves `_value + _feeLimit` nominal tokens from the user, but due to the token's transfer fee the bridge contract's balance only increases by `(_value + _feeLimit) * (1 - fee%)`.
4. `_requestERC20Transfer` still burns `_value` (mint/burn mode) or keeps `_value` as the locked accounting figure (lock/unlock mode), and emits `RequestValueTransfer(..., _value, ...)`.
5. The counterpart-chain operator observes the event and calls `handleERC20Transfer(..., _value, ...)`, minting/unlocking the full `_value` on the destination chain — exceeding what was actually backed on the source chain, demonstrated by the balance accounting in the reference test suite for `BridgeTransferERC20`: [4](#0-3)

    function _requestERC20Transfer(
        address _tokenAddress,
        address _from,
        address _to,
        uint256 _value,
        uint256 _feeLimit,
        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        require(_value > 0, "zero ERC20 token amount");

        uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);

        if (modeMintBurn) {
            ERC20Burnable(_tokenAddress).burn(_value);
        }

        emit RequestValueTransfer(
            TokenType.ERC20,
            _from,
            _to,
            _tokenAddress,
            _value,
            requestNonce,
            fee,
            _extraData
        );
        requestNonce++;
    }

    async function expectSendERC20(fixture: BridgeFixture, tx: any) {
      const { bridge, token, feeReceiver, user1, user2 } = fixture;
      const modeMintBurn = await bridge.modeMintBurn();

      const expectTx = expect(await tx)
        .to.emit(bridge, "RequestValueTransfer")
        .withArgs(
          TokenType.ERC20,
          user1.address,
          user2.address,
          token.address,
          parseEther("1.0"),
          0,
          parseEther("0.3"),
          "0x",
        )
        .to.emit(token, "Transfer").withArgs(user1.address, bridge.address, parseEther("1.5")) // Send value + feeLimit
        .to.emit(token, "Transfer").withArgs(user1.address, feeReceiver.address, parseEther("0.3")) // Takeout fee
        .to.emit(token, "Transfer").withArgs(bridge.address, user1.address, parseEther("0.2")); // Refund (feeLimit - fee)
      if (modeMintBurn) {
        expectTx.to.emit(token, "Burn").withArgs(bridge.address, parseEther("1.0")); // Burn value
      } else {
        expectTx.to.not.emit(token, "Burn"); // No burn
      }

      expect(await bridge.requestNonce()).to.equal(1);
      expect(await token.balanceOf(user1.address)).to.equal(parseEther("3.7"));
      expect(await token.balanceOf(feeReceiver.address)).to.equal(parseEther("0.3"));
      if (modeMintBurn) {
        expect(await token.balanceOf(bridge.address)).to.equal(parseEther("0.0")); // Value is burned
      } else {
        expect(await token.balanceOf(bridge.address)).to.equal(parseEther("1.0")); // Bridge holds value
      }
    }
