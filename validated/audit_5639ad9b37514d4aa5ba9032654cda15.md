### Title
Missing reentrancy guard on Tron `IntentGatewayV2.cancelOrder`/`withdraw` allows double-refund/double-release of escrow via native-token callback - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The mainline EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) applies `nonReentrant` to `placeOrder`, `fillOrder`, and `cancelOrder`, and a dedicated regression suite (`evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`) proves that `_filled[commitment]` is set *before* any native-token `.call{value:}` transfer (CEI pattern) to stop a malicious beneficiary from re-entering during the ETH payout. The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the same escrow/withdraw logic but its `cancelOrder` function has **no `nonReentrant` modifier at all** [1](#0-0) , unlike its sibling on mainline EVM which is explicitly `nonReentrant` [2](#0-1) .

### Finding Description
`withdraw()` in the Tron contract sends native ETH/TRX directly to the beneficiary via a low-level `.call{value: amount}("")` before all bookkeeping is finished, and the order-level `_filled[commitment]` guard is the only protection against a repeated withdrawal [3](#0-2) . Because `cancelOrder` (the same-chain refund path, which calls `withdraw(body, true)` directly, and the destination cross-chain path, which sets `_filled[commitment]` then dispatches a message) is not `nonReentrant`, a beneficiary that is a smart contract can implement a `receive()`/fallback that re-enters `cancelOrder` (or `fillOrder`, similarly unprotected on Tron) mid-transfer.

The core broken invariant mirrors the Drippie bug class exactly: a state-mutating entry point permits more than one execution within the same call/transaction because the "only-once" guard (`_filled[commitment]`) is checked and set in a place that a reentrant call can bypass timing-wise, combined with the complete absence of the reentrancy lock that the equivalent mainline function already has. On the mainline contract this exact attack was found and fixed by moving `_filled[commitment] = msg.sender` to the very top of `_fillSameChain`/`_fillCrossChain` and adding `nonReentrant`; the Tron file was not patched to match.

### Impact Explanation
An attacker who places or is selected to fill/cancel an order with a malicious beneficiary contract can re-enter `withdraw`/`cancelOrder` during the native-token transfer callback. Depending on the exact reentrant call ordering (e.g., re-entering `cancelOrder` for a same-chain order before `_filled[commitment]` is written, since same-chain cancel routes straight into `withdraw` without first setting `_filled`), the escrowed input tokens for a single order can be paid out more than once, directly stealing bridge-held escrow — a direct loss-of-funds / double-settlement condition that matches the bounty's "stealing or loss of funds" and "replay/double-claim/double-settlement" categories.

### Likelihood Explanation
This requires no privileged actor, relayer, prover, or admin — only an unprivileged user placing an order with themselves (or a colluding "solver") as beneficiary, using a contract address that implements a reentrant `receive()`. The Tron file is presented as first-class production code (mirrors the audited/fixed mainline contract) and its `cancelOrder`/`withdraw` are public/external entry points reachable by any address, so likelihood is high once TRX/native-asset orders are used, and the class of bug is already proven exploitable against the un-fixed version of this exact logic (the mainline pre-fix code that the Foundry test suite exists specifically to regress-test).

### Recommendation
Port the same CEI fix applied to `evm/src/apps/IntentGatewayV2.sol`/`IntrinsicIntents.sol`/`ExtrinsicIntents.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: add `nonReentrant` to `cancelOrder`, `fillOrder`, and `placeOrder`, and ensure `_filled[commitment]` (or equivalent settlement marker) is written *before* any external call/native transfer inside `withdraw`. Add a Tron-specific regression test mirroring `IntrinsicIntentsReentrancyTest.sol`.

### Proof of Concept
1. Attacker deploys a malicious beneficiary contract with a `receive()` that calls back into `IntentGatewayV2.cancelOrder` (same-chain route) or `fillOrder` for the same `commitment`.
2. Attacker (as `order.user`) places a same-chain order with a native-token (TRX) input and sets `order.user`/beneficiary to the malicious contract.
3. Attacker calls `cancelOrder`, which is not `nonReentrant`, routes to `_cancelSameChain`/`withdraw(body, true)`, and sends native tokens via `.call{value: amount}("")` at [4](#0-3)  before `_orders[commitment][token] -= amount` fully drains every token in the loop.
4. During the callback, the malicious contract re-enters `cancelOrder`/`withdraw` for the same commitment before the first call unwinds and `_filled` guard from the first pass takes effect, draining the escrow a second time.
5. Compare against `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`, which demonstrates the identical attack is blocked on the mainline contract only because of the `nonReentrant` modifier plus CEI ordering that the Tron file lacks.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
