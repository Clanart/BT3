This confirms the critical detail: the wrap_err message explicitly documents the expected sighash type as "SinglePlusAnyoneCanPay" (`SIGHASH_SINGLE|ANYONECANPAY`) [1](#0-0) . This sighash type only commits to the single output at the same index as the signed input (the user's payout output), and leaves all other outputs — including the OP_RETURN output carrying `operator_xonly_pk` — completely unsigned. That means once the user broadcasts their signature off-chain (to allow racing operators to front the withdrawal), any party can attach an arbitrary `operator_xonly_pk` to the OP_RETURN output without invalidating the user's signature, since `ANYONECANPAY|SINGLE` does not cover that output.

Given the remaining unexplored piece — whether reimbursement crediting (`update_finalized_payouts`/`is_kickoff_malicious`/`send_asserts`) solely trusts this OP_RETURN-derived `operator_xonly_pk` with no additional binding to the actual broadcaster of the transaction (e.g., no check that the funding input of the payout tx, which pays the fee and funds the user's output, belongs to the claimed operator) — I was not able to fully verify the RBF/funding step (`fund_raw_transaction`) binds the additional inputs to `self.signer.xonly_public_key` on-chain in a way unforgeable by a third party. This is a meaningful gap in my analysis: without confirming that the *additional funding inputs* of the broadcast payout transaction are cryptographically tied to the operator identity claimed in OP_RETURN, I cannot be certain whether a third party could relay the user's SIGHASH_SINGLE|ANYONECANPAY-signed input, substitute a different `operator_xonly_pk` in OP_RETURN, and fund/broadcast it themselves to steal attribution of another operator's payout (or to attribute a payout to an operator that never actually fronted the funds).

### Title
Payout attribution in `update_finalized_payouts` trusts operator xonly pubkey from an unauthenticated OP_RETURN output that is not covered by the user's `SIGHASH_SINGLE|ANYONECANPAY` signature - (File: core/src/verifier.rs, core/src/operator.rs)

### Summary
The withdrawal-payout signature scheme uses `SIGHASH_SINGLE|ANYONECANPAY` [1](#0-0) , meaning the user's signature only commits to their own payout output and not to the transaction's OP_RETURN output that names the fronting operator. The verifier's bookkeeping then attributes the payout — and thus the right to reimbursement — solely by parsing that unsigned OP_RETURN field [2](#0-1) .

### Finding Description
`update_finalized_payouts` extracts `operator_xonly_pk` purely from the OP_RETURN output of the confirmed payout transaction with no other authentication [2](#0-1) , and persists it via `update_payout_txs_and_payer_operator_xonly_pk` [3](#0-2) . This value is later relied upon as ground truth to determine which operator is entitled to reimbursement (`get_first_unhandled_payout_by_operator_xonly_pk`, `validate_payer_is_operator`, `is_kickoff_malicious`, `send_asserts`) [4](#0-3) [5](#0-4) [6](#0-5) .

Because the underlying input signature explicitly uses `SinglePlusAnyoneCanPay` [7](#0-6) , the OP_RETURN output (added by `create_payout_txhandler`) is not covered by that signature's sighash commitment [8](#0-7) , so the identity written there is not cryptographically bound to whoever actually funds/broadcasts the transaction.

### Impact Explanation
If an unauthenticated third party can relay/rebroadcast the payout transaction with a substituted `operator_xonly_pk` while reusing the user's off-chain signature, they could misattribute a real fronted withdrawal to an operator that did not pay it (an operator reimbursed for a payout it never funded), or block the legitimate fronting operator from claiming reimbursement — both fall under the Critical impact bucket ("an operator reimbursed for a payout it never funded", "an honest operator permanently unable to be reimbursed").

### Likelihood Explanation
Confirmed root cause (sighash type documented in code) but likelihood of successful exploitation is unverified — I could not confirm whether the transaction-funding step (`fund_raw_transaction`, RBF inputs) independently binds the broadcasting operator's identity to the OP_RETURN pubkey, which would neutralize the issue in practice. This gap is explicitly noted above as unresolved.

### Recommendation
Bind the OP_RETURN `operator_xonly_pk` field to the funding inputs actually contributed by the claiming operator (e.g., require the operator to sign over the OP_RETURN output with their own key, or verify additional payout tx inputs are spent from the claimed operator's known UTXOs) before crediting attribution in `update_finalized_payouts`.

### Proof of Concept
Not fully constructible without confirming the funding/RBF binding step; the sighash-type gap itself is demonstrated directly in the code path cited above (`core/src/operator.rs:630-637`, `core/src/builder/transaction/operator_reimburse.rs:407-436`, `core/src/verifier.rs:2312-2342`).

            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
