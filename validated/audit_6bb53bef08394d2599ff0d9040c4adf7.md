### Title
Bonus reward token double-counted with WOM reward when a two-address token is registered as a bonus token, causing over-distribution of rewards in `WombatStaking._toMasterWomAndSendReward` - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking._toMasterWomAndSendReward()` measures the harvested WOM reward via a `balanceOf` diff on the hardcoded `wom` token, and separately measures each registered bonus token's harvested amount via its own `balanceOf` diff. `addBonusRewardForAsset()` only guards against adding the exact same bonus-token address twice — it never checks that the new bonus token is not an alternate address of `wom` (or of another already-registered bonus token). A token implemented with two valid addresses (e.g. a `ProxyERC20`-style token, analogous to the report's sUSD/sETH case) that resolves to the same underlying balance as `wom` would let the same harvested balance increase be captured and sent to the rewarder twice: once as `womRewards` and once as `bonusBalanceDiff`.

### Finding Description [1](#0-0) 

`_toMasterWomAndSendReward` snapshots `womBeforeBalance` for `wom` and `beforeBalances[i]` for each `assetToBonusRewards[_lpToken][i]`, then after triggering the Wombat harvest, computes:
- `womRewards = IERC20(wom).balanceOf(address(this)) - womBeforeBalance`
- `bonusBalanceDiff = IERC20(bonusTokens[i]).balanceOf(address(this)) - beforeBalances[i]`

Both amounts are independently forwarded to the rewarder via `_sendRewards`, which calls `IBaseRewardPool(_rewarder).queueNewRewards(_amount, _rewardToken)` [2](#0-1) .

The only guard when registering a bonus token is a duplicate-address check: [3](#0-2) 
`addBonusRewardForAsset` never verifies `_bonusToken != wom` (or that it isn't an alias of any other already-registered bonus token/reward asset). If the harvested reward is a token that exposes two valid ERC20-interface addresses referencing the same underlying balance (the exact bug class in the referenced report), an admin-registered bonus token that is an alias of `wom` would cause the single real balance increase from the harvest to be read twice — once under `wom`'s address and once under the alias address — and queued to the rewarder as two separate reward amounts.

### Impact Explanation
This causes `queueNewRewards` to record inflated reward amounts for a given pool's `BaseRewardPool`/rewarder, effectively minting phantom yield that stakers of that pool can claim beyond what was actually harvested from Wombat. Because `WombatStaking` custodies pooled LP/reward tokens shared across all registered pools, this over-crediting drains real token balances belonging to other users/pools when claims are executed later, i.e., protocol insolvency / theft of funds from other participants.

### Likelihood Explanation
This requires the (trusted, but not "malicious admin" in the excluded sense) `onlyOwner` `addBonusRewardForAsset` call to register a token that happens to share an address alias with `wom`. This is a configuration-error-triggered class of bug identical in mechanism to the referenced report — it does not require a malicious admin, only the existence of such a two-address token being harvested as a bonus reward, which is realistic for reward tokens like synthetix-style assets. Given no in-code check exists to prevent it, likelihood is non-trivial whenever bonus tokens are added without this specific validation.

### Recommendation
In `addBonusRewardForAsset`, reject any `_bonusToken` equal to `wom`, and reject any bonus token whose underlying balance could double-count with another registered token address (e.g., disallow well-known proxy/alias patterns, or use a stricter check comparing total-supply/canonical address where feasible). More robust: track cumulative harvested amounts from a single authoritative source instead of relying on independent `balanceOf` diffs per token address when multiple tracked tokens could reference the same balance.

### Proof of Concept
1. Owner registers a bonus token `B` for pool `_lpToken` via `addBonusRewardForAsset`, where `B` is a two-address ERC20 whose second address is exactly `wom` (i.e., `B.balanceOf` and `wom.balanceOf` both reflect the same underlying ledger).
2. A harvest is triggered via `deposit`/`withdraw`/`harvest`, calling `_toMasterWomAndSendReward`.
3. `womBeforeBalance` and `beforeBalances[i]` (for bonus token `B`) are both read from the same underlying balance before the harvest.
4. After `_stakeToWombatMaster`/`withdraw` triggers the Wombat harvest and WOM is received, both `womRewards` and `bonusBalanceDiff` compute the identical increase.
5. `_sendRewards` is called twice with the same harvested amount — once tagged as `wom`, once tagged as `B` — doubling the rewards queued to `poolInfo.rewarder` for a single harvest event.

        address[] memory bonusTokens = assetToBonusRewards[_lpToken];
        uint256 bonusTokensLength = bonusTokens.length;

        uint256 womBeforeBalance = IERC20(wom).balanceOf(address(this));

        if(_isStake)

        uint256 womRewards = IERC20(wom).balanceOf(address(this)) - womBeforeBalance;
        _sendRewards(_lpToken, wom, poolInfo.rewarder, womRewards);

        for (uint256 i; i < bonusTokensLength; i++) {
            uint256 bonusBalanceDiff = IERC20(bonusTokens[i]).balanceOf(address(this)) - beforeBalances[i];
            if (bonusBalanceDiff > 0) {
                _sendRewards(_lpToken, bonusTokens[i], poolInfo.rewarder, bonusBalanceDiff);
            }
        }

        emit WomHarvested(womRewards);

    }
