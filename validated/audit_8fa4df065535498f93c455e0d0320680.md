### Title
Stale ERC-decimals precision check lets `saturating_sub` silently zero out the cross-chain scale factor in `hyper-fungible-token` - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_erc20`/`convert_to_balance` compute the cross-chain scale factor as `10 ** erc_decimals.saturating_sub(local_decimals)`. The invariant `erc_decimals >= local_decimals` is checked only once, at `register_token`/`update_token` time [1](#0-0) , but `decimals` for non-native assets is re-read live from `pallet-assets` metadata on every `send()`/`on_accept()`/`on_timeout()` call [2](#0-1) [3](#0-2) . If that live value later exceeds the `erc_decimals` recorded in `Precisions` (asset metadata decimals are mutable in `pallet-assets` via `set_metadata`, an action independent of the HFT pallet's `T::CreateOrigin`), the registration-time guarantee becomes stale, and `saturating_sub` clamps the now-negative exponent to `0` instead of erroring, producing a completely wrong 1:1 conversion factor.

### Finding Description
- `convert_to_erc20`/`convert_to_balance` scale amounts by `10u128.pow(erc_decimals.saturating_sub(local_decimals))`: [4](#0-3) 
- The only place that ever validates `erc_decimals >= local_decimals` is inside `register_token`/`update_token`, gated by `Error::ErcDecimalsBelowLocal`: [5](#0-4) [6](#0-5) 
- `local_decimals`/`decimals` at send/receive time are *not* the value that was checked at registration — they are fetched fresh via `fungibles::metadata::Inspect::decimals(asset_id)` in `send()`, `on_accept()`, and `on_timeout()`: [2](#0-1) [3](#0-2) [7](#0-6) 
- `pallet-assets` decimals metadata is not immutable — it is set/updated via `set_metadata`, callable by the asset's own `Owner`, a role entirely separate from the HFT pallet's `T::CreateOrigin` governance. Nothing in this pallet re-validates the `erc_decimals >= local_decimals` invariant after registration, and nothing prevents the asset owner from calling `set_metadata` to raise `decimals` above the `erc_decimals` value frozen in `Precisions` storage.
- Once `local_decimals > erc_decimals`, `erc_decimals.saturating_sub(local_decimals)` silently returns `0` rather than failing, so the scale factor becomes `10^0 = 1` instead of the mathematically required down-scale. This is exactly the bug class in the seed report: a decimal-precision term is dropped from the calculation instead of raising an error, producing a numerically wrong result rather than a controlled failure.

### Impact Explanation
When the scale factor collapses to `1` instead of the correct divisor:
- In `send()`, `convert_to_erc20(amount, erc_decimals, decimals)` will emit an ERC20-side `Message.amount` that is numerically equal to the raw local-chain balance units instead of being scaled up to erc-chain precision — the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract will mint/release an amount that is orders of magnitude too large relative to what was actually escrowed/burned on the Substrate side (e.g., local_decimals=20 vs erc_decimals=18 → the destination receives 100x the intended value).
- Symmetrically, on `on_accept()`/`on_timeout()`, `convert_to_balance` would fail to scale down correctly and could mint/refund far more (or, in the opposite decimals-drift direction, far less) of the local asset than corresponds to the value actually locked on the other chain.
This breaks the core bridge invariant that value moves "exactly once and only to the rightful beneficiary and amount" — it is a direct fund-creation/fund-mismatch bug on the custody/mint path, not merely a display or off-chain estimation issue.

### Likelihood Explanation
Exploitability depends entirely on whether the local asset's decimals metadata can actually be changed after `register_token`/`update_token` runs — I could not find, within index limits, any code in this pallet or a companion pallet that locks/freezes an asset's metadata once it is registered with `hyper-fungible-token`, nor could I confirm from the indexed source whether the runtime restricts `pallet-assets::set_metadata` origin to only the HFT pallet's `T::CreateOrigin`. If the asset `Owner` capable of calling `set_metadata` is a distinct, less-trusted party than the HFT/bridge governance (a normal and expected `pallet-assets` permission model), this is a genuine, non-privileged-relayer, non-governance attack path. Given the uncertainty about runtime-level metadata-locking, likelihood is assessed as **medium** rather than high — this should be verified directly against the runtime configuration that instantiates `hyper-fungible-token`'s `Config::Assets`.

### Recommendation
- Re-validate `erc_decimals >= local_decimals` at the point of use (in `send()`, `on_accept()`, and `on_timeout()`), returning a hard error (reusing `Error::ErcDecimalsBelowLocal` or a new `HftError` variant) instead of silently clamping via `saturating_sub`.
- Alternatively/additionally, snapshot and freeze the local asset's decimals at registration time (store it in `Precisions` alongside `erc_decimals`, or lock the asset's metadata) so a later `set_metadata` change cannot desynchronize the two pallets' assumptions.
- Replace `saturating_sub` with `checked_sub` in `convert_to_erc20`/`convert_to_balance`, propagating `None` as a hard `DecimalsNotConfigured`/conversion error rather than defaulting the exponent to `0`.

### Proof of Concept
1. Governance registers asset `X` (a `pallet-assets` asset with `Owner = O`, decimals = 6) for chain `EVM-1` with `ChainConfig { decimals: 18, token_contract: ... }` via `register_token` — passes the `ensure!(18 >= 6, ...)` check [1](#0-0) , and `Precisions[X][EVM-1] = 18`.
2. Asset owner `O` later calls `pallet-assets::set_metadata` (or `force_set_metadata`) to change `X`'s decimals from `6` to `20` — an action entirely outside the HFT pallet's control/knowledge.
3. A user calls `hyper-fungible-token::send` with `asset_id = X`, `amount = 100 * 10^20` (100 tokens at the new 20-decimal precision).
4. Inside `send()`, `decimals = Inspect::decimals(X) = 20` (live value) and `erc_decimals = Precisions::get(X, EVM-1) = 18` (stale). `convert_to_erc20` computes `erc_decimals.saturating_sub(local_decimals) = 18.saturating_sub(20) = 0`, so `erc20_amount = amount * 10^0 = amount` (unscaled) — instead of the correct down-scale by `10^2`.
5. The dispatched `Message.amount` sent to the EVM `HyperFungibleToken` contract is `100 * 10^20`, which that 18-decimal contract will mint/release as `100 * 10^20 / 10^18 = 10,000` tokens — 100x the intended/escrowed value — realizing an on-chain value-creation exploit across the bridge.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
