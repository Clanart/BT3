### Title
Persistent, path-scoped `safe.directory` trust grant has no expiry, no content binding, and enables automatic code execution once trust is (re)established - (File: `app/src/lib/git/config.ts`)

### Summary
The external report's underlying flaw is granting broad, indefinite trust to an entity with no cap on what that trust can later be used for. GitHub Desktop's Git-ownership "trust" mechanism has the same shape: when Desktop detects a repository owned by a different user (`getRepositoryType` returning `{ kind: 'unsafe' }`), the user is offered a one-time "Trust Repository" action. Clicking it calls `addSafeDirectory()`, which permanently and unconditionally adds the path to the **global** `safe.directory` Git config with no expiration, no re-verification, and no binding to the specific content that existed at trust time.

### Finding Description
`addSafeDirectory` in [1](#0-0)  writes the trusted path into the user's global `~/.gitconfig` via `addGlobalConfigValueIfMissing('safe.directory', path)`. This exception is:
- **Global**, not scoped to the Desktop session or to the specific repository instance the user reviewed.
- **Permanent**, with no expiry, no re-prompt, and no UI to review/revoke it from within Desktop.
- **Keyed only on filesystem path**, not on repository identity/content (e.g., no commit hash, no remote URL check). Once trust is granted for path `P`, any future content placed at `P` — by any process or by a different owner reusing that path — is silently treated as trusted by Git going forward.

The UI surfaces the exact risk being accepted — `add-existing-repository.tsx` and `missing-repository.tsx` both warn "Adding untrusted repositories may automatically execute files in the repository" [2](#0-1)  and [3](#0-2)  — yet the mitigation offered (`onTrustDirectory`) grants unlimited, indefinite trust rather than a narrowly-scoped, re-checked exception [4](#0-3) [5](#0-4) .

This is directly analogous to `token.approve(spender, type(uint256).max)`: the "spender" (the git repository path) is granted an unbounded, un-revocable capability (arbitrary future hook/config execution trust) instead of a scoped, single-use grant tied to the reviewed content.

### Impact Explanation
Once `safe.directory` contains a path, Git will honor repository-local configuration and hooks at that path without the "dubious ownership" guard that Desktop relies on as its sole gate against untrusted repos. If the underlying directory is later repopulated with attacker-controlled content — for example on a shared/multi-user machine, via a symlink swap, or because the path is reused after removal/recreation — Desktop and the underlying `git` CLI will operate on it as fully trusted, with no re-prompt to the user, enabling execution of arbitrary repository-supplied hooks/config in the context of the user's Git operations (commit, checkout, merge, push all run through `with-hooks-env.ts` / hook invocation paths referenced in `get-repo-hooks.ts`, `rebase.ts`, `commit.ts`, `merge.ts`, `pull.ts`, `push.ts`, `tag.ts`).

### Likelihood Explanation
This requires an unprivileged attacker who can place or later replace content at a path a victim previously trusted (e.g. a shared workstation, a synced/network folder, or a path reused for a differently-owned clone) — no local/physical access beyond what the underlying report class already assumes (attacker-controlled repository content) and no additional social engineering beyond the one legitimate "Trust Repository" click the current UX already asks users to perform. Because the grant is permanent and unscoped, the single click effectively authorizes all future content at that path, indefinitely.

### Recommendation
Do not grant unbounded, indefinite trust for a bare filesystem path. Instead:
- Scope the `safe.directory` exception to the specific verified repository/session and re-validate ownership/identity (e.g., re-check `git rev-parse` and possibly file ownership/inode) before relying on prior trust each time the repository is opened.
- Provide a way in Desktop settings to view and revoke previously trusted `safe.directory` entries.
- Consider re-warning the user if a previously trusted path's ownership or top-level tree signature changes materially since the trust was granted, rather than silently continuing to treat it as safe.

### Proof of Concept
1. On a shared machine, User A clones/creates a repository at path `P` owned by another OS user account and clicks "Trust Repository" (`onTrustDirectory` in `missing-repository.tsx` / `add-existing-repository.tsx`), which calls `addSafeDirectory(P)` and appends `P` to `safe.directory` in the global `~/.gitconfig` [6](#0-5) .
2. Later, the other OS user (or any process able to write to `P`, e.g. after the original repo is removed and `P` is reused) replaces the contents of `P` with a malicious repository containing hostile hooks/config.
3. User A reopens Desktop; `getRepositoryType(P)` no longer returns `unsafe` because `safe.directory` already contains `P` [7](#0-6) , so no warning is shown.
4. Any subsequent Desktop Git operation (commit/checkout/merge/pull/push) on `P` executes the attacker-controlled hooks with no re-prompt, because trust was granted unconditionally and indefinitely at step 1. [1](#0-0)

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```

```typescript
export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }
```
