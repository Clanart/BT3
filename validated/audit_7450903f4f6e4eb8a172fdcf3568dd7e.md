### Title
Attacker can permanently fill the gasless bundle-tx queue and block all legitimate gasless transactions - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The `AlchemistV2` bug shows a shared, capacity-limited resource (the mint-limit rate limiter) that an attacker can keep pinned at capacity by repeatedly performing a cheap mint→burn cycle, permanently denying legitimate users access to the resource. The `kaiax` gasless module in this repository has a structurally identical shared, capacity-limited resource — the bundle-tx queue counted by `knownTxs.numQueue()` — that is admitted to and evicted from on a timer, without any real cost or balance verification at admission time, allowing an attacker to keep the queue permanently full and block all other users' gasless (`ApproveTx`/`SwapTx`) bundle transactions.

### Finding Description
`GaslessModule.PreAddTx` is the tx-pool admission hook called for every incoming transaction that is a "module tx" for the gasless module (i.e., an `ApproveTx` or `SwapTx` bundle transaction) [1](#0-0) . It rejects a new bundle tx only if the current queue occupancy (`g.knownTxs.numQueue()`) is already at or above the configured `MaxBundleTxsInQueue` (default 200, or unlimited if set to a non-positive value via CLI) [2](#0-1) [3](#0-2) . Critically, `PreAddTx` performs no balance, allowance, or economic-cost validation before counting the transaction toward the shared queue slot — the balance/allowance checks (`checkBalanceForApprove`, `checkBalanceForSwap`) are wired through a separate `GetCheckBalance` callback that is invoked elsewhere in the promotion/execution pipeline, not during `PreAddTx` admission [4](#0-3) .

Each admitted bundle tx is tracked in the `knownTxs` map with a `TxStatusQueue` status and an `addedTime` [5](#0-4) , and is only evicted from queue-occupancy accounting after `QueueTimeout` (10 seconds) or when it is promoted/dropped by the pool's own reset/lifecycle hooks [6](#0-5) . A tx hash can only be resubmitted once its `elapsedPromotedOrAddedTime()` exceeds `KnownTxTimeout` (30 seconds) [7](#0-6) , but there is nothing stopping an attacker from generating a fresh set of syntactically-valid `ApproveTx` transactions (new nonces/new sender-signed payloads, which is cheap and does not require real token balances or allowance at admission time) to refill the queue as soon as older entries expire on their timers — precisely analogous to the mint→burn cycle in the reported bug, where the underlying limiter naturally "frees up" capacity that the same attacker immediately reoccupies before honest users can use it.

### Impact Explanation
Because the queue-occupancy check in `PreAddTx` is a hard gate (`return ErrBundleTxQueueFull`) shared across all senders, and because occupying a slot costs the attacker nothing beyond generating a syntactically valid, signed `ApproveTx` (no requirement to actually hold or approve the token, since that check runs later, not at admission) [1](#0-0) [8](#0-7) , a single attacker can continuously keep `numQueue()` at `MaxBundleTxsInQueue`, causing `ErrBundleTxQueueFull` to be returned for every other user's legitimate gasless bundle submission. This denies the gasless/fee-delegation-adjacent swap-and-repay feature to all other users on the node, effectively a persistent denial-of-service against the gasless subsystem reachable purely by submitting ordinary transactions to the public tx pool / RPC endpoint.

### Likelihood Explanation
The attack requires only the ability to submit transactions to the endpoint node's tx pool (an unprivileged, public-RPC-reachable capability), and unlike the original `AlchemistV2` case which required a "well financed attacker" with real capital or a flash loan to hit the mint limit, filling this queue requires no capital at all — `PreAddTx` does not validate token balance/allowance before counting a tx toward the queue, so the cost is limited to gas/transaction-generation overhead, and even that overhead can be minimized because rejected/queued bundle txs still occupy slots for up to `QueueTimeout`/`KnownTxTimeout` seconds before natural eviction, giving the attacker a continuously renewable griefing window.

### Recommendation
Add an economic or reputation-based admission cost to `PreAddTx` (e.g., require the balance/allowance pre-check used by `checkBalanceForApprove`/`checkBalanceForSwap` to run before a tx is counted toward `MaxBundleTxsInQueue`), and/or apply a per-sender cap on concurrently-queued bundle txs so that a single account (or a small number of accounts) cannot occupy the entire shared queue capacity. This mirrors the `Limiters.increase()` mitigation recommended in the original report — restoring shared capacity should not be free of cost or trivially repeatable by a single actor.

### Proof of Concept
1. Attacker crafts `N = MaxBundleTxsInQueue` (default 200) distinct, syntactically valid `ApproveTx` transactions (via `makeApproveTx`-style encoding as used in tests) from throwaway accounts/nonces, requiring no real token balance [9](#0-8) .
2. Attacker submits all `N` transactions to the endpoint node's tx pool; each passes `PreAddTx` and is added to `knownTxs` with `TxStatusQueue`, since no balance check gates admission [10](#0-9) .
3. `g.knownTxs.numQueue()` now equals `MaxBundleTxsInQueue`; any subsequent legitimate user's `ApproveTx`/`SwapTx` submission is rejected with `ErrBundleTxQueueFull` [11](#0-10) , matching the test assertion for this exact enforcement path [12](#0-11) .
4. As each queued tx expires after `QueueTimeout`/`KnownTxTimeout`, attacker resubmits a fresh batch of cheap `ApproveTx` transactions to keep `numQueue()` pinned at the maximum indefinitely, permanently denying gasless bundle-tx admission to all other users.

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}

func (g *GaslessModule) checkBalanceForApprove(approveArgs *ApproveArgs) error {
	token := approveArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(approveArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckToken() {
		tokenContract, err := sc_erc20.NewERC20(token, bc)
		if err != nil {
			return err
		}

		// tx.token.balanceOf(sender) > 0
		tokenBalance, err := tokenContract.BalanceOf(nil, approveArgs.Sender)
		if err != nil {
			return err
		}
		if tokenBalance.Sign() <= 0 {
			return fmt.Errorf("insufficient sender token balance: token=%s, have=%s, want=nonzero", token.Hex(), tokenBalance.String())
		}
	}
	return nil
}

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
