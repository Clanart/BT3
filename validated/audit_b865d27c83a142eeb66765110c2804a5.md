### Title
Silent `origin` remote hijack via attacker-controlled GitHub API `clone_url` field - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` automatically rewrites a tracked repository's `origin` remote URL to whatever `clone_url` value is returned by the account's GitHub API endpoint, with no user confirmation, whenever the repo is refreshed. This is the same bug class as the reported `vest()` issue: an unprivileged, externally-supplied value silently overwrites a security-relevant local state field (here, the git remote used for all future `push`/`fetch`/`pull` operations), and the app's own "guard" only checks that the previous remote matched previously-cached API data — it never re-validates that the new URL still points to the same repository the user believes they're working with.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` in `app/src/lib/stores/app-store.ts` (lines 4874-4914) is invoked on ordinary background/foreground repository refresh paths (e.g. `_refreshRepository`, account-change refresh via `refreshSelectedRepositoryAfterAccountChange`). It calls: [1](#0-0) 

`apiRepo` comes straight from `api.fetchRepository(owner, name)` [2](#0-1)  — a plain HTTP JSON response whose `clone_url` field is fully controlled by whatever server answers for `account.endpoint`. For GitHub Enterprise Server accounts, that endpoint is a self-hosted/attacker-influenced host, and the response can also be altered by any on-path proxy/MITM — squarely within the "git remote/proxy response" attacker model.

`updateRemoteUrl()` then decides whether to overwrite the local remote: [3](#0-2) 

The only checks performed are:
- `gitStore.defaultRemote !== null`
- URL scheme (`http`/`https`) of old vs new URL match (`protocolsMatch`)
- the *previous* remote still equalled the *previously cached* `gitHubRepository.cloneURL` (`remoteUrlUnchanged`) — i.e., "the user hasn't manually touched this remote"

None of these validate that the new `clone_url` still points at the same host/owner/repo the user originally added — that check (`urlMatchesRemote`, used elsewhere in `repositoryMatchesRemote`/`findUpstreamRemote`) is deliberately *not* applied here. If those three conditions hold, `gitStore.setRemoteURL()` is called, which shells out to `git remote set-url origin <attacker_url>` [4](#0-3)  — with zero user interaction.

This mirrors the `vest()` flaw exactly: a function meant to reconcile trusted metadata (`benRevocable` / the repo's remote) unconditionally overwrites the previous value based on caller/attacker-supplied input, without checking whether the target should even be allowed to change, and without any privileged gate.

### Impact Explanation
Once `origin` is silently repointed, every subsequent `git push`/`fetch`/`pull` the user performs in Desktop targets the attacker's server instead of the real one:
- Any credentials/tokens sent through the git credential helper for that remote's host are sent to the attacker (`envForAuthentication`/credential negotiation is host-scoped, so this can leak auth material to the attacker's endpoint).
- Fetches/pulls can pull in attacker-controlled objects/history, silently corrupting what gets merged into local branches.
- Pushes silently go to an attacker-controlled destination, i.e. "silent corruption of what the user commits or pushes," which is explicitly listed as a valid impact category.

### Likelihood Explanation
Requires only that the victim has added/authenticated a GitHub Enterprise Server account (or a dotcom/GHES connection subject to a proxy/MITM) whose API responses the attacker controls, and that the victim hasn't manually customized their `origin` URL (the common case, since `remoteUrlUnchanged` is the default state for most clones). No local access, no admin rights, and no unusual user action are needed — the rewrite fires automatically during routine repository refresh.

### Recommendation
- Do not silently rewrite the remote URL from API data. At minimum, re-validate with `urlMatchesRemote`/`urlsMatch` that the new `clone_url` still resolves to the same hostname+owner+name (allow only owner/name changes reachable via the same account/endpoint, e.g. legitimate renames), not an arbitrary host swap.
- Require explicit user confirmation before changing a configured remote URL, similar to the "Trust Repository" confirmation pattern already used for unsafe directories in `add-existing-repository.tsx`/`missing-repository.tsx`.
- Treat GHES/API-supplied `clone_url` as untrusted input and never let it silently mutate the git remote used for authenticated `push`/`fetch`.

### Proof of Concept
1. Victim adds a GitHub Enterprise Server account pointing at a server the attacker controls (or is positioned as a MITM/proxy for the connection), and has a repository cloned from `origin = https://ghes.example.com/real-org/real-repo.git`.
2. Desktop calls `matchGitHubRepository` → `api.fetchRepository('real-org', 'real-repo')`, and the attacker's server returns a JSON body identical to a normal repo object except `clone_url: "https://ghes.example.com/attacker-org/decoy-repo.git"` (same host/protocol to satisfy `protocolsMatch`).
3. Because the victim never manually edited `origin` (`remoteUrlUnchanged` is true) and `urlsMatch` is false, `updateRemoteUrl()` calls `gitStore.setRemoteURL('origin', 'https://ghes.example.com/attacker-org/decoy-repo.git')`.
4. `origin` is rewritten in `.git/config` with no prompt. The victim's next `git push`/`fetch` in Desktop silently targets `attacker-org/decoy-repo` instead of `real-org/real-repo`.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```

```typescript
export async function setRemoteURL(

}
```
