### Title
Permissionless pointer precompile lets any CW20/CW721/CW1155 contract spoof the `name`/`symbol` of a legitimate asset - (File: `precompiles/pointer/pointer.go`)

### Summary
The pointer precompile at `0x100b` lets anyone permissionlessly register an ERC20/ERC721/ERC1155 "pointer" contract for any CosmWasm contract address, using the `name`/`symbol` metadata reported by that contract itself, with no uniqueness or provenance check against already-registered pointers or well-known assets.

### Finding Description
`AddCW20`, `AddCW721`, and `AddCW1155` in `precompiles/pointer/pointer.go` take a caller-supplied CW contract address, query `token_info`/`contract_info` on it, and copy the returned `name`/`symbol` fields verbatim into the new EVM pointer contract's metadata via `UpsertERCCW20Pointer`/`UpsertERCCW721Pointer`/`UpsertERCCW1155Pointer`: [1](#0-0) [2](#0-1) 

There is no check anywhere in this flow that the `name`/`symbol` pair is unique, matches an allow-listed/canonical asset, or differs from an existing pointer's metadata. Because deploying a CW20/CW721/CW1155 contract on Sei is itself permissionless, any user can deploy a malicious contract whose `token_info`/`contract_info` reports the exact same `name` and `symbol` as a well-known asset (e.g. "USDC"), then call `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` on the precompile to mint a look-alike ERC20/ERC721/ERC1155 pointer contract at a different address, with identical displayed identity.

This mirrors the Rolla `QToken` finding's root cause class: an on-chain, protocol-emitted token identifier (there, a truncated year in the symbol; here, the full `name`/`symbol` string) can be made indistinguishable between two semantically different underlying assets, and downstream tooling (wallets, DEXes, aggregators) that key off `name`/`symbol` rather than contract address can be fooled into trading/approving/transferring against the wrong contract.

### Impact Explanation
A user or integrator that identifies tokens by `symbol`/`name` (the exact pattern the Rolla report warns about for DEX listings) can be led to interact with an attacker-deployed pointer contract believing it is the canonical asset's pointer. Approvals, transfers, or swaps directed at the spoofed pointer can result in direct loss of user funds, satisfying the "unauthorized transfer via precompile or pointer" / fund-loss criteria. Unlike the original Rolla bug (a display quirk from truncation), this variant grants the attacker full string control, making convincing spoofing trivial and with no mitigation available to users beyond manually verifying contract addresses.

### Likelihood Explanation
Both preconditions - deploying an arbitrary CW20/CW721/CW1155 contract and calling the pointer precompile - are fully permissionless single-transaction actions available to any wallet, with no admin/governance gate on `AddCW20`/`AddCW721`/`AddCW1155`. Any attacker can execute this today at minimal cost.

### Recommendation
Do not allow uncurated `name`/`symbol` fields from arbitrary CW contracts to populate pointer metadata without disambiguation: e.g., prefix/suffix pointer `symbol`/`name` with the underlying CW contract address (similar to how the native pointer path in `AddNative` derives from bank-module denom metadata rather than free-form user input, see `precompiles/pointer/pointer.go` lines 99-132), or require governance/allow-list approval before a pointer's displayed `symbol` can match an existing, already-pointed asset's `symbol`.

### Proof of Concept
1. Attacker deploys a CW20 contract whose `token_info` query returns `{"name":"USD Coin","symbol":"USDC", ...}` but is otherwise unrelated to genuine USDC.
2. Attacker (or anyone) calls `addCW20Pointer(cwAddr)` on precompile `0x100b`; `PrecompileExecutor.AddCW20` queries `token_info`, and calls `UpsertERCCW20Pointer` with `ERCMetadata{Name:"USD Coin", Symbol:"USDC"}` [3](#0-2) .
3. The resulting ERC20 pointer contract at a new address now reports `name()==USD Coin`, `symbol()==USDC`, indistinguishable by metadata from the legitimate USDC pointer.
4. Any wallet/DEX/aggregator that resolves tokens by symbol/name (rather than by address) can present this spoofed contract to a user as if it were genuine USDC, leading the user to approve/transfer/swap against the malicious contract and lose funds.

func (p PrecompileExecutor) AddCW20(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	cwAddr := args[0].(string)
	cwAddress, err := sdk.AccAddressFromBech32(cwAddr)
	if err != nil {
		return nil, 0, err
	}
	res, err := p.wasmdKeeper.QuerySmartSafe(ctx, cwAddress, []byte("{\"token_info\":{}}"))
	if err != nil {
		return nil, 0, err
	}
	formattedRes := map[string]interface{}{}
	if err := json.Unmarshal(res, &formattedRes); err != nil {
		return nil, 0, err
	}
	name := formattedRes["name"].(string)
	symbol := formattedRes["symbol"].(string)
	contractAddr, err := p.evmKeeper.UpsertERCCW20Pointer(ctx, evm, cwAddr, utils.ERCMetadata{Name: name, Symbol: symbol})
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
