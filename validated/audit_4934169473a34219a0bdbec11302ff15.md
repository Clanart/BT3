### Title
Forfeiture on early mWOMSV reward claims is permanently disabled, letting cooldown users keep 100% of rewards - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never applies any forfeiture because, unlike its sibling `vlMGPBaseRewarder._calExpireForfeit`, it never calls the locker's `getRewardablePercentWAD(_account)` to discount rewards for the amount/time a user's tokens are in cooldown. `mWomSV.sol` implements `getRewardablePercentWAD` (lines 181-206) specifically for this purpose, but `mWOMSVBaseRewarder` ignores it entirely, so any user (attacker or not) who starts an unlock (`mWomSV.startUnlock`) and then claims rewards retains the full `earned()` amount with zero forfeiture, contradicting the documented forfeiture mechanism mirrored in `vlMGPBaseRewarder`.

### Finding Description
`vlMGPBaseRewarder._calExpireForfeit` (rewards/vlMGPBaseRewarder.sol:386-400) computes:
```
uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
...
uint256 forfeitAmount = _amount - rewardableAmount;
``` [1](#0-0) 

The corresponding function in the mWOMSV rewarder, `mWOMSVBaseRewarder._calExpireForfeit` (rewards/mWOMSVBaseRewarder.sol:385-398), never fetches `mWOMSV.getRewardablePercentWAD(_account)`. It instead sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount` is always `_amount - _amount = 0`: [2](#0-1) 

`mWomSV.sol` does implement the analogous helper `getRewardablePercentWAD(_user)` (lines 181-206), which discounts the rewardable percentage based on how much of a user's balance is in a cooldown slot and for how long, exactly the signal `_calExpireForfeit` should be consuming: [3](#0-2) 

Because this call is missing, `_sendReward` (rewards/mWOMSVBaseRewarder.sol:362-376) always sends the user's full `userRewards[...]` balance and never routes anything to `_queueNewRewardsWithoutTransfer` for redistribution to remaining lockers: [4](#0-3) 

Regarding the specific "front-run `updateFor`" mechanism proposed in the question: it does not materially matter. `balanceOf(_account)` in the rewarder reads the user's staked-token balance from `MasterMagpie.stakingInfo(stakingToken, _account)` [5](#0-4) , and `mWomSV.startUnlock` does not reduce this staked balance in MasterMagpie — it only marks a slot as "in cool down" and calls `multiclaimFor` to flush rewards; the actual withdrawal from MasterMagpie (`withdrawMWomSVFor`) only happens in `unlock()`, not `startUnlock()` [6](#0-5) [7](#0-6) . So `_updateFor`/`earned` compute the same value whether or not the attacker calls `updateFor` immediately before `startUnlock`; the accumulator-style reward math (Synthetix-style `rewardPerTokenStored` checkpointing) is idempotent to extra `updateFor` calls, and no value is "banked" or protected by calling it early. `startUnlock` itself already triggers `multiclaimFor` which flows into the same forfeit-free `getReward`/`_sendReward` path.

The actual, reproducible root cause is simply: **forfeiture is unconditionally zero in `mWOMSVBaseRewarder`** regardless of cooldown state, call order, or whether `updateFor` was invoked beforehand. Any staker — not just one racing `updateFor` — who partially or fully starts unlocking and then claims rewards (via `MasterMagpie`'s claim path, which is `onlyMasterMagpie`-gated but reachable by any user claiming their own rewards) receives 100% of `earned()` with no forfeiture, when the intended design (mirroring `vlMGPBaseRewarder`) is to forfeit a time/amount-weighted portion to be redistributed to users who keep tokens fully locked.

### Impact Explanation
This is a "theft or permanent freezing of unclaimed yield" issue at the protocol level: remaining lockers who keep their `mWOMSV` fully staked are entitled (by design, per the mirrored `vlMGPBaseRewarder`/`getRewardablePercentWAD` mechanism) to receive the forfeited portion of rewards from users who enter cooldown. Because `_calExpireForfeit` never applies any discount, that redistribution never happens, and every user who starts unlocking still claims their full accrued rewards. This dilutes/denies the reward share that should accrue to long-term lockers — a systemic, quantifiable loss to that class of users, not merely a documentation or best-practice issue, since it changes actual token flows (`_queueNewRewardsWithoutTransfer` is never invoked for mWOMSV rewards).

### Likelihood Explanation
High feasibility and no special preconditions: any unprivileged holder of `mWOMSV` can trigger this simply by calling `mWomSV.startUnlock` (or partial cooldown) after having accrued rewards, then claiming through the standard `MasterMagpie` claim flow — this is normal user behavior, not an edge case requiring flash loans, reentrancy, or front-running. It is 100% repeatable for every claim and does not depend on the front-running/`updateFor` ordering described in the question (that specific mechanism has no material effect given the accumulator-style reward math and the fact that `startUnlock` doesn't change `balanceOf`).

### Recommendation
Fix `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit` by fetching and applying `mWOMSV.getRewardablePercentWAD(_account)`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount) revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;
    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
        rewardableAmount = _amount;
    }
    return forfeitAmount;
}
```
This restores the intended forfeiture/redistribution mechanism consistent with `vlMGPBaseRewarder`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `MasterMagpie`, and `mWOMSVBaseRewarder`; register a reward token.
2. Have two users, `A` (attacker) and `B` (remains fully locked), lock equal amounts of `mWOM` via `mWomSV.lock`.
3. Queue rewards via `queueNewRewards` so `rewardPerTokenStored` increases, giving both users equal `earned()`.
4. Have `A` call `mWomSV.startUnlock(fullAmount)` to enter cooldown, then immediately call the claim path (`MasterMagpie` claim → `mWOMSVBaseRewarder.getReward`).
5. Assert: `A`'s received reward == `earned(A, rewardToken)` computed before `startUnlock`, with `calExpireForfeit(A, rewardToken) == 0` even though `A` is fully in cooldown — demonstrating forfeiture never triggers regardless of cooldown state.
6. Compare against a modified/reference `_calExpireForfeit` that calls `getRewardablePercentWAD`, showing it would have forfeited a nonzero amount, proving the discrepancy and lost redistribution to `B`.

Note: the specific "call `updateFor` immediately before `startUnlock`" step from the question is not required to reproduce the loss — omitting it produces an identical result, confirming the front-run timing is not the actual root cause; the always-zero forfeiture in `_calExpireForfeit` is.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
