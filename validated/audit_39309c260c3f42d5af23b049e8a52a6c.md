### Title
`ThresholdKeys::new` derives `group_key` from only the first `t` verification shares and never checks share consistency, so deserialized keys can certify an inconsistent threshold state - (File: crypto/dkg/src/lib.rs)

### Summary
The referenced bug class is a check that computes a security-critical value from stale/incomplete state: `getDebtValue` uses `bank.totalDebt` without the accrued interest, so `isLiquidatable` underreports risk and green-lights positions that are actually unsafe. The analogous pattern in Serai lives in `crypto/dkg`: `ThresholdKeys::new` (also reached through `ThresholdKeys::read` on untrusted bytes) computes the committed `group_key` by interpolating only the verification shares of participants `1..=t`, and performs no consistency check whatsoever on the remaining `n - t` verification shares — nor on whether the supplied `secret_share` matches the caller's own verification share. The "risk" (the actual key structure the shares commit to) is thus underdetermined by the value the check produces.

### Finding Description
`ThresholdKeys::new` validates only the count and index range of `verification_shares`, then derives the group key exclusively from participants `1..=t`:

- crypto/dkg/src/lib.rs, `ThresholdKeys::new`, lines 355-378:
```rust
if verification_shares.len() != usize::from(params.n()) { ... }
for participant in verification_shares.keys().copied() {
  if u16::from(participant) > params.n() { ... }
}
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

Two consistency checks are missing:
1. Verification shares for participants `t+1..=n` are never verified to lie on the same polynomial (i.e., to interpolate to the same `group_key` for any `t`-subset). With Lagrange interpolation, a `t`-of-`n` key only commits to `n` share evaluations; nothing binds shares `t+1..=n` to the shared secret that `group_key` certifies.
2. `secret_share` is never checked against `verification_shares[params.i()]` — the holder's own claimed share is accepted blindly.

This is reachable from an unprivileged party: `ThresholdKeys::read` (lines 574-632) parses `t`, `n`, `i`, the interpolation vector, `secret_share`, and all `n` verification shares from a byte stream and feeds them straight into `ThresholdKeys::new`. Any consumer that loads keys from an input it does not fully trust (key-exchange between processors, recovery material, operator-supplied files) accepts attacker-crafted keys.

The consequence materializes in `ThresholdKeys::view` (lines 463-533) and FROST `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs, lines 283-313): `view` computes interpolated verification shares for the *included* signer set from the stored map, while `group_key` remains the value derived from shares `1..=t`. For any signing set not identical to `{1..=t}` that includes a corrupted share `j > t`, every individual signature share verifies against its (attacker-chosen) `verification_share(j)`, yet the aggregated signature fails — or worse, share verification passes locally so blame is attributed to honest participants (`FrostError::InvalidShare(p)` naming the wrong party, since the check compares against manipulated shares).

This mirrors the audit issue exactly: just as `isLiquidatable` uses `bank.totalDebt` (pre-`poke`) instead of `borrowBalanceCurrent` and thereby certifies positions as healthy, `ThresholdKeys` certifies a `group_key` and per-signer verification state using only a `t`-sized subset of the committed shares, treating the remaining `n - t` shares as irrelevant when they are part of the same security invariant.

### Impact Explanation
- **Incorrect verifier formula / inconsistent threshold state accepted**: `ThresholdKeys::new` succeeds on keys whose shares `t+1..=n` commit to a different effective secret than `group_key` encodes. The check that should bind all `n` shares to one polynomial silently evaluates a `t`-subset — the direct analog of evaluating un-accrued debt.
- **Wrong blame attribution and signing failure**: in `AlgorithmSignMachine::sign`/`complete`, an honest participant's share is verified against an attacker-supplied `verification_share`. Crafted keys can make honest shares fail (participant unjustly blamed via `FrostError::InvalidShare`) or produce signatures that fail aggregate verification despite all share-level checks passing.
- A holder at index `i > t` can be handed keys where `secret_share` is fully attacker-known while `group_key` presents as an honest threshold key — no secret leak of the victim's real key (they have none for that group), but a false certification of security guarantees, the same "false comfort" as underpriced liquidation risk.

### Likelihood Explanation
Reachability is real but bounded: exploitation requires an attacker to feed crafted bytes through `ThresholdKeys::read` (explicitly an untrusted-bytes entry point per scope) into a component that then signs or attributes blame. The injected inconsistency deterministically passes `ThresholdKeys::new` because no code path checks shares beyond index `t`. Effects (invalid aggregate signatures, misblamed honest participants) trigger on the next signing session — a deterministic logic flaw, not a race. Severity is bounded to Medium: it yields liveness/blame-integrity failures and false key-structure certification rather than direct secret recovery or signature forgery against an honest group.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs), after computing `group_key` from `1..=t`, verify consistency of the full share set:
- For `Interpolation::Lagrange`, check that every verification share lies on the degree-`t-1` polynomial through `group_key` — e.g., for each `j` in `t+1..=n`, evaluate the interpolation of the committed polynomial at `j` and compare to `verification_shares[j]` (equivalently, interpolate `group_key` over a subset containing `j` and confirm equality).
- Check `verification_shares[params.i()] == C::generator() * secret_share` so the holder's own share is bound to its verification share.
These checks are the analog of `poke`: refresh/verify the full committed state before certifying `group_key`, instead of certifying on a partial subset.

### Proof of Concept
1. Choose `t = 2`, `n = 3`, curve Ristretto. Pick scalars `a0, a1`; set `verification_shares[1] = G*(a0 + a1)`, `verification_shares[2] = G*(a0 + 2*a1)` — these interpolate at 0 to `group_key = G*a0`.
2. Set `verification_shares[3] = G*x` for a random `x` *not* equal to `G*(a0 + 3*a1)` (off-polynomial share).
3. Supply `i = 3`, `secret_share = x` (consistent with `verification_shares[3]` but inconsistent with the shared secret `a0`).
4. Serialize via the `ThresholdKeys::write` layout and parse with `ThresholdKeys::read` — `ThresholdKeys::new` returns `Ok` with `group_key = G*a0`.
5. Call `view(vec![Participant(2), Participant(3)])` and run FROST `sign` for that set. Participant 3's share verifies against `verification_share(3)` (interpolated attacker share), yet the reconstructed signature does not verify under `group_key` — share-level checks pass while the aggregate fails, and any `InvalidShare` blame is computed against the corrupted map, misidentifying honest signers.
