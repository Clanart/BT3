### Title
Publicly derivable internal offset addresses let any sender forge Branch/Change/Forwarded outputs, bypassing external-deposit handling - (File: processor/src/networks/bitcoin.rs)

### Summary
The IDOR class (restricted object reachable by an unvalidated reference, bypassing intended access) maps onto Serai's Bitcoin scanner: the `Scanner` classifies any on-chain output paying to a registered script by `script_pubkey` alone, and the offsets for the internal `Branch`, `Change`, and `Forwarded` output types are deterministic functions of public constants (`Secp256k1::hash_to_F(KEY_DST, b"branch"|"change"|"forward")`) and the publicly known group key. Any unprivileged party can compute these addresses and pay to them, causing the processor to emit internally-classified outputs the protocol never created.

### Finding Description
`scanner()` in `processor/src/networks/bitcoin.rs:308-347` derives `BRANCH_OFFSET`, `CHANGE_OFFSET`, and `FORWARD_OFFSET` via `Secp256k1::hash_to_F(KEY_DST, ...)` with a fixed public domain separator and fixed public messages. These offsets are registered into a `Scanner` keyed only by the resulting `script_pubkey` (`Scanner::register_offset`, `networks/bitcoin/src/wallet/mod.rs:180-196`). `scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) returns a `ReceivedOutput` for any output whose `script_pubkey` matches, with no provenance check.

In `get_outputs` (`processor/src/networks/bitcoin.rs:686-740`), scanned outputs are typed by looking up the offset in `kinds` (`kinds[offset_repr_ref]`, line 695). Only `OutputType::External` outputs receive the transaction's embedded Serai instruction `data` (lines 730-734). An output sent to a `Branch`/`Change`/`Forwarded` script by an external party is therefore classified as an internal protocol output and its instruction data is discarded.

### Impact Explanation
An attacker (or merely confused user) who deposits to the derivable Branch/Change/Forward address has their funds reported as an internal output rather than an external deposit. The deposit is not bound to any Serai instruction (`data` stays empty for non-External kinds), so the credited intent is lost while the multisig still reports spendable-looking outputs. This produces funds reported received that are not correctly spendable/accounted for under the intended classification, corrupting internal accounting — outputs the protocol believes it created itself can be fabricated externally. This is the direct analog of the BookWyrm IDOR: an object (internal-only offset output) reachable through an identifier (the publicly computable script) that was assumed reachable only by the authorized party.

### Likelihood Explanation
The offsets require no secret: `KEY_DST` and the labels `"branch"`, `"change"`, `"forward"` are hard-coded constants, and the group key is public. Constructing the address is `p2tr_script_buf(group_key + G * offset)`. Any party who can send a Bitcoin transaction can trigger this at negligible cost (they do lose the sent funds, but griefing/ordering attacks and accidental deposits are realistic, and the classification error may be weaponized where internal-kind outputs are treated as trusted, e.g., change assumed to be the protocol's own).

### Recommendation
Bind the internal offset scripts to contexts only the protocol can produce, e.g., include a rotating secret/per-session nonce in the `hash_to_F` message for `Change`/`Forwarded` offsets, or commit the script to a specific transaction/outpoint when registering it. Alternatively, require that non-External scanned outputs match outputs of transactions the multisig itself signed (checkable via known txids) before emitting them as Branch/Change/Forwarded.

use bitcoin_serai::{crypto::*, wallet::p2tr_script_buf};
