## Finding

**Title:** Stale manual conflict resolutions carry over across unrelated conflicts in the same rebase/cherry-pick, causing silent auto-acceptance of attacker-controlled content - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
This is a direct structural analog of the Augur `preemptiveDisputeCrowdsourcer` bug: a state value tied to a specific target (a resolved outcome / a resolved conflict) is not reset when the underlying target moves on to a new round (a new dispute round / the next commit in a multi-commit operation), and a later action that legitimately targets the *new* round ends up being silently and incorrectly satisfied using the *stale* value.

### Finding Description
When a rebase or cherry-pick hits a conflict, GitHub Desktop stores the user's per-file resolution choice ("ours"/"theirs") in `IChangesState.conflictState.manualResolutions`, a `Map<path, ManualConflictResolution>` keyed only by file **path**, with no association to which commit in the multi-commit sequence the resolution was made for.

`getConflictState` always seeds the new conflict state with whatever `manualResolutions` map was already present: [1](#0-0) 

`updateConflictState` is the function that decides what to carry forward each time `git status` is refreshed. It unconditionally reuses `prevConflictState.manualResolutions` for the freshly computed conflict state: [2](#0-1) 

The only "reset" logic that exists, `performEffectsForRebaseStateChange`, is purely a stats/telemetry function - it only fires side effects when `newConflictState == null` (the whole operation ended), never when moving from one commit's conflict to the next commit's conflict within the same rebase/cherry-pick: [3](#0-2) 

Consequently, once the user resolves a conflict on `path/to/file.txt` for commit N (e.g. by picking "theirs"), and the rebase/cherry-pick advances to commit N+1 which introduces a *new, unrelated* conflict on the exact same path, `manualResolutions` still contains the old entry for that path. Because file "resolved" status in the UI is derived purely from `manualResolutions.get(path)`: [4](#0-3) 

the new conflict on `file.txt` is treated as already resolved and never surfaced to the user for review. When the operation is continued, both `continueRebase` and `continueCherryPick` apply `manualResolutions` by path with no verification that the resolution corresponds to the conflict currently on disk: [5](#0-4) [6](#0-5) 

This mirrors the Augur bug precisely: `preemptiveDisputeCrowdsourcer` (a value bound to outcome X) is silently reused after a `disavowCrowdsourcers` reset event moved the "current round" to a different outcome; here, a `manualResolutions` entry (a value bound to commit N's conflict) is silently reused after the rebase/cherry-pick engine advances the "current round" to commit N+1's conflict on the same path.

### Impact Explanation
An attacker who controls the branch/commits being rebased or cherry-picked (e.g. a malicious fork, PR branch, or crafted history the victim fetches and rebases onto) can engineer two conflicting commits that both touch the same file path. If the victim resolves the first conflict manually, the tool will auto-apply that same resolution choice to the second, semantically unrelated conflict without ever showing it to the user. This lets attacker-authored content on the second commit get silently staged and committed as part of the victim's history, corrupting what the user actually commits/pushes without their knowledge - satisfying the "silent corruption of what a user commits or pushes" impact category.

### Likelihood Explanation
This requires a rebase or cherry-pick spanning at least two commits from an attacker-influenced range, both touching the same file path with conflicting content against the base - a realistic scenario for a crafted malicious branch/PR designed to be rebased or cherry-picked by a victim, and requires no local/physical access, no elevated privileges, and no prior compromise.

### Recommendation
Scope `manualResolutions` (or the resolved/unresolved determination) to the specific commit currently being applied instead of persisting by file path across the whole multi-commit operation. When `updateConflictState` detects that the rebase/cherry-pick has advanced to a different commit within the same operation (e.g. `currentTip`/rebase head changes even though `targetBranch`/`originalBranchTip` match), the `manualResolutions` map for paths whose conflict content changed should be cleared, or resolutions should be validated against the conflict markers currently on disk before being reused.

### Proof of Concept
1. Attacker prepares a branch with two commits: commit A modifies `shared.txt` to conflict with the victim's base branch, commit B (later in the same branch) also modifies `shared.txt` with different, malicious content that also conflicts with the base.
2. Victim rebases their branch onto/cherry-picks this attacker branch in Desktop.
3. Commit A's conflict on `shared.txt` appears; victim manually resolves it, picking "theirs" via `_updateManualConflictResolution` [7](#0-6) .
4. Desktop calls `continueRebase`/`continueCherryPick`, which stages the resolution and advances to commit B [5](#0-4) .
5. Commit B introduces a fresh conflict on `shared.txt`. `updateConflictState` recomputes conflict state but reuses the stale `manualResolutions` map from step 3 [8](#0-7) .
6. `getResolvedFiles`/`hasUnresolvedConflicts` treat `shared.txt` as already resolved (map still has the path key) [9](#0-8) , so the UI never prompts the victim to review commit B's conflict.
7. The rebase/cherry-pick auto-continues, silently accepting attacker-controlled content into `shared.txt` as part of the victim's rewritten history, which the victim later commits/pushes without ever seeing the second conflict.

function performEffectsForRebaseStateChange(
  prevConflictState: RebaseConflictState | null,
  newConflictState: RebaseConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
) {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.targetBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.targetBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the rebase must have been aborted
  if (branchNameChanged) {
    statsStore.increment('rebaseAbortedAfterConflictsCount')
    return
  }

  const { currentTip, currentBranch } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null &&
    currentBranch != null
  ) {
    const previousTip = prevConflictState.originalBranchTip

    const previousTipChanged =
      previousTip !== currentTip &&
      currentBranch === prevConflictState.targetBranch

    if (!previousTipChanged) {
      statsStore.increment('rebaseAbortedAfterConflictsCount')
    }
  }

  return
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  public _updateManualConflictResolution(
    repository: Repository,
    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })

    this.updateMultiCommitOperationStateAfterManualResolution(repository)

    this.emitUpdate()
  }
