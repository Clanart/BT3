Partial-commit staging re-reads the working-directory diff at commit time, letting the on-disk state diverge from the diff the user reviewed and silently changing what gets committed - ([File: app/src/lib/git/apply.ts])

### Summary
When a user stages only some lines of a modified file, GitHub Desktop records the selection as a set of *absolute line indices* into a diff object that was fetched and shown in the Changes view. When the commit is actually created, `applyPatchToIndex` does **not** reuse that reviewed diff — it independently re-fetches a brand-new diff from disk via `getWorkingDirectoryDiff` and then reapplies the old index-based selection to the new diff's hunks. If the file content on disk changes between the time the diff was rendered/selected and the time the commit executes, the old line indices no longer correspond to the same lines, so the wrong content is silently staged and committed, with no diff-changed warning to the user. This is the same broken invariant as the FeeCollector bug: data captured under one state (fee amounts / diff+selection) is combined with a different, later state (updated rates / re-fetched diff) without any reconciliation or re-validation.

### Finding Description
Two independent, disconnected steps exist in the partial-commit flow:

1. **Selection time** — the Changes view loads a diff via `updateOrSelectFirstFile`/`updateChangesDiffForCurrentSelection` in `app/src/lib/stores/app-store.ts` (around lines 3444–3497). Line selections (`DiffSelection`) are stored as absolute indices computed against `hunk.unifiedDiffStart + lineIndex` for *that specific diff snapshot*. There is a staleness check here (`selectableLines` is recomputed if the diff changed), but it only prunes indices that no longer exist — it does not detect that remaining indices might now map to *different* lines. [1](#0-0) 

2. **Commit time** — `_commitIncludedChanges` in `app-store.ts` passes the currently-selected `WorkingDirectoryFileChange` objects (carrying the old `DiffSelection`) straight to `createCommit` → `stageFiles` → `applyPatchToIndex`. [2](#0-1) 

`applyPatchToIndex` then **independently re-fetches** the diff from the current on-disk file state and formats a patch using the *old* selection object against these *new* hunks:
```
const diff = await getWorkingDirectoryDiff(repository, file)
...
const patch = await formatPatch(file, diff)
await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })
``` [3](#0-2) 

`formatPatch` walks the *new* diff's hunks and decides whether to include each line purely by asking `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` from the **new** diff: [4](#0-3) 

There is no comparison between the diff that produced the selection and the diff used to build the patch (no hash/etag/mtime/hunk-shape check). If the file was modified on disk between selection and staging — e.g. by a build tool, an editor autosave, a background formatter, or a `clean`/`smudge` filter or hook defined by an attacker-controlled cloned repository's `.gitattributes`/hooks that rewrites tracked files as a side effect of some other git operation — the hunk boundaries and line offsets shift. The old index-based selection then silently picks unrelated lines in the new diff. Because `git apply --unidiff-zero --whitespace=nowarn` applies a zero-context patch by line number, it can succeed even when the hunk content textually differs from what the user actually saw, without any user-visible warning.

This directly parallels the fee-collector flaw: `collectedFees` (≈ the user's line selection) is captured under one state (`feeTypes[i]` ≈ the reviewed diff) but distributed (≈ committed) using whatever state is current at distribution time (≈ the freshly re-fetched diff), with no snapshot consistency and no re-validation before use.

### Impact Explanation
The result is silent corruption of what the user actually commits and pushes: content the user explicitly deselected (e.g., a debug print, an unwanted change, sensitive data they meant to keep out of the commit) can be included, or content they meant to include can be dropped — without any error or diff-mismatch prompt. Because commits are then pushed to a remote (often a shared/public repository), this can leak unintended content or silently omit an intended fix, and the user has no indication that the committed diff differs from what they reviewed and approved in the UI.

### Likelihood Explanation
The window between diff rendering/selection and the actual `git apply --cached` call is not zero — the user must review the diff, choose which lines to include, optionally type a commit message, and click Commit; during this interval any process with write access to the working directory (editor auto-save, linter/formatter watch mode, a build step, a Git hook, or a malicious `clean` filter shipped in the cloned repository's `.gitattributes` that runs during another background git operation like a status refresh or checkout) can alter the file. Desktop performs frequent background status refreshes and diff reloads while the Changes view is open, so the race window recurs continuously, not as a one-off. No admin rights or local malware are required — only a file-content change on disk (which can originate from repository-defined filters/hooks or ordinary tooling) between two normal Desktop-driven reads of the same file.

### Recommendation
- Bind the `DiffSelection` to an immutable snapshot of the diff it was computed against (e.g. store the diff's hunk boundaries or a content hash alongside the selection).
- In `applyPatchToIndex` / `stageFiles`, re-validate that the diff used to build the selection still matches the diff currently on disk before formatting the patch; if it does not match, abort staging that file and force the UI to reload the diff and require the user to re-confirm their selection.
- Alternatively, capture and reuse the exact same diff object used for rendering the selection when generating the patch, only falling back to a fresh `getWorkingDirectoryDiff` when no prior diff/selection exists (e.g., "select all").

### Proof of Concept
1. In a cloned repository, modify a tracked file and open it in Desktop's Changes view; Desktop loads a diff and the user deselects a few sensitive lines (e.g., a secret) using partial line selection, leaving other lines selected.
2. Before clicking "Commit", trigger any process that rewrites the same file on disk with different line offsets (e.g., an editor auto-formatter, a file-watcher script, or — in the untrusted-repo threat model — a `clean` filter/hook defined by the repository that fires during a Desktop-triggered git operation such as a background `status`/`diff` refresh).
3. Click "Commit". `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff from the now-changed file and reapplies the stale `DiffSelection` indices from step 1 against the new hunks.
4. Inspect the resulting commit with `git show`: the committed content does not match what the user selected in the UI — previously deselected (sensitive) lines may now be included, or previously selected lines may be dropped, with no warning shown by Desktop.
