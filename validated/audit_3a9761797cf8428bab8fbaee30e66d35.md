### Title
Bribe protocol fee is burned if `bribeFeeCollector` is not set - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking::vote` transfers the bribe protocol fee to `bribeFeeCollector` without verifying that the address has been configured, so if `bribeFeeCollector` is still `address(0)` the fee is permanently burned instead of collected.

### Finding Description
`vote()` is called by `WombatBribeManager` on every voting round, and it computes `protocolFee` from harvested bribe rewards and unconditionally sends it to `bribeFeeCollector`: [1](#0-0) 
`bribeFeeCollector` is a plain state variable that is only assigned inside the owner-only `setBribe` function; until that call is made (or if it is later reset to the zero address) it defaults to `address(0)`: [2](#0-1) 
There is no check such as `if (bribeFeeCollector != address(0))` before the `safeTransfer`, so any time the protocol fee is non-zero and the collector address is unset, `protocolFee` tokens are sent to the zero address and burned rather than being kept for the protocol/stakers.

This `vote()` function is reachable by an ordinary, unprivileged user: `WombatBribeManager.castVotes()` / `castVotesAndClaimBribes()` are `external` with no access-control modifier, and they call into `WombatStaking.vote()` (gated only by `msg.sender == bribeManager`, which `WombatBribeManager` satisfies) as part of harvesting and forwarding bribe rewards. [3](#0-2) [4](#0-3) 

This mirrors the reported `GaugeProxy::distributeToken` bug class exactly: a fee recipient mapping/variable can be left unset (zero address), and normal, permissionless flow execution silently burns the fee instead of reverting or skipping the transfer.

### Impact Explanation
Any bribe protocol fee harvested while `bribeFeeCollector == address(0)` is irrecoverably burned, permanently freezing/losing that portion of harvested yield that should have accrued to the protocol/collector. This can happen any time an ordinary user triggers `castVotes`/`castVotesAndClaimBribes` before the collector is configured, or after it is reset, with no way to recover the burned tokens.

### Likelihood Explanation
Low-to-moderate: it requires the specific scenario where `bribeFeeCollector` has not yet been set (e.g., right after deployment/upgrade before `setBribe` is called) or has been reset to zero, while `bribeProtocolFee` is already non-zero and bribe rewards exist. This is a plausible operational sequencing gap rather than a routine occurrence, but since `castVotes` is permissionless, any user (not just the admin) can trigger the burn during that window.

### Recommendation
Guard the transfer with an explicit non-zero check, e.g.:
```solidity
if (protocolFee > 0 && bribeFeeCollector != address(0)) {
    IERC20(rewardTokens[i][j]).safeTransfer(bribeFeeCollector, protocolFee);
} else if (protocolFee > 0) {
    rewardAmount -= 0; // keep protocolFee with the rewarder / do not deduct if it can't be sent
}
```
More robustly, either revert `setBribe`/`vote` when `bribeFeeCollector` is zero and a non-zero `bribeProtocolFee` is configured, or fold the undistributed protocol fee back into `rewardAmount` sent to the rewarder instead of sending it to the zero address.

### Proof of Concept
1. Deploy `WombatStaking` and `WombatBribeManager`; do not call `setBribe` yet (or call it once and later call it again with `_bribeFeeCollector = address(0)`), leaving `bribeProtocolFee` non-zero from a prior configuration while `bribeFeeCollector` is `address(0)`.
2. Any unprivileged user calls `WombatBribeManager.castVotes()` (or `castVotesAndClaimBribes`).
3. This invokes `WombatStaking.vote()`, which harvests bribe rewards and computes `protocolFee = rewardAmount * bribeProtocolFee / DENOMINATOR`.
4. `IERC20(rewardTokens[i][j]).safeTransfer(bribeFeeCollector, protocolFee)` executes with `bribeFeeCollector == address(0)`, sending `protocolFee` tokens to the zero address, permanently burning them. [1](#0-0)
