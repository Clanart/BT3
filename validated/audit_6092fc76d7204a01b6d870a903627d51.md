Based on the code evidence, I found a locally-provable analog in the Tron variant of `IntentGatewayV2.placeOrder()`.

### Title
Sandwichable native-fee swap in `placeOrder()` permanently locks the user's overpaid ETH with no refund - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The core broken invariant in the external report is: a function that swaps native value for a required token amount must return unused native value to the payer, and the payer's balance must not silently absorb price-impact losses from front-running. In the canonical EVM `IntentGatewayV2.sol`, `placeOrder()` performs `swapETHForExactTokens{value: msgValue}(order.fees, ...)`, then explicitly does `msgValue -= amounts[0]` and later refunds any leftover `msgValue` to `msg.sender` [1](#0-0) . The Tron fork of the same contract performs the identical exact-output swap but drops both the `msgValue` decrement and the trailing refund block entirely [2](#0-1) .

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder()`, when `order.fees > 0` and the user pays with native value, the contract calls:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
```

`swapETHForExactTokens` only ever consumes `amounts[0] <= msgValue` of the attached ETH to obtain exactly `order.fees` fee-token units; the router keeps any leftover ETH does not send it back automatically — the caller (the gateway contract) is responsible for reclaiming and refunding it. The canonical EVM contract does this (`msgValue -= amounts[0]` plus a final `if (msgValue > 0) { msg.sender.call{value: msgValue} }`), but the Tron variant has neither step [2](#0-1) .

The corrupted value is the **residual native `msgValue`** after the exact-output swap: it is neither tracked nor returned, so it becomes permanently stranded inside the `IntentGatewayV2` contract, unrecoverable by the user who sent it. This directly instantiates the report's broken invariant — the price paid by an unprivileged, non-atomic on-chain swap has no cap/refund guarantee, and any user who (deliberately, per SDK guidance, or due to normal price movement / a sandwich) attaches more ETH than the exact-output swap consumes has that entire delta silently absorbed by the protocol rather than refunded. This is a public entry point (`placeOrder`, callable by anyone) causing unconditional fund loss with no attacker or privileged actor required — the loss occurs on every call where `msgValue` exceeds the swap's `amounts[0]`, which is normal/expected behavior according to the SDK's own comments about overpaying ETH for the fee swap ("Send 5 ETH for a fee swap that should cost much less" pattern used in EVM tests) [3](#0-2) .

### Impact Explanation
Every `placeOrder()` call on Tron that pays the relayer/protocol fee in native token and overshoots the exact amount needed (which is the expected usage pattern, since callers cannot predict the router's exact-output price in advance) results in permanent, unrecoverable loss of the surplus ETH/TRX to the ordinary end user. There is no admin, relayer, or malicious peer involved — this is unconditional fund loss triggered by the protocol's own public entrypoint, matching the bounty's "stealing or loss of funds" and "transaction manipulation" categories.

### Likelihood Explanation
Likelihood is high: any user who follows the documented/tested pattern of over-funding the native value for the fee swap (as explicitly exercised in the EVM test suite) will trigger this loss on the Tron deployment, since the code path is unconditionally reached whenever `order.fees > 0` and `msgValue > 0`.

### Recommendation
Mirror the canonical EVM `IntentGatewayV2.sol` logic in the Tron contract: capture `amounts` returned by `swapETHForExactTokens`, decrement `msgValue -= amounts[0]`, and add the trailing refund step (`if (msgValue > 0) { (bool sent,) = msg.sender.call{value: msgValue}(""); if (!sent) revert InsufficientNativeToken(); }`) at the end of `placeOrder()`.

### Proof of Concept
1. On the Tron deployment, a user calls `placeOrder(order, graffiti)` with `order.fees = X` (some fee-token amount) and attaches `msg.value = Y` native tokens where `Y` is intentionally or unavoidably greater than the ETH cost of acquiring exactly `X` fee tokens via the configured Uniswap V2 router (as recommended/tested for the EVM sibling contract to guard against price swings).
2. `swapETHForExactTokens{value: Y}(X, path, address(this), block.timestamp)` executes, consuming only `amounts[0] < Y` ETH from the attached value to obtain `X` fee tokens; the router does not auto-refund unspent value to `placeOrder`'s caller — the surplus `Y - amounts[0]` remains as native balance in `IntentGatewayV2`.
3. `placeOrder()` finishes (`emit OrderPlaced(...)`) without ever computing `Y - amounts[0]` or returning it to `msg.sender`.
4. Verify: `address(intentGateway).balance` increases by `Y - amounts[0]` relative to what it should retain (only escrowed order inputs), and the user's balance decreases by the full `Y` rather than by `amounts[0]` — the difference is unrecoverable through any subsequent contract call.
