### Title
`SignableTransaction::new` computes weight/vbytes (and thus `needed_fee`, the min-relay check, and `MAX_STANDARD_TX_WEIGHT` check) without the OP_RETURN data output, so transactions carrying `data` underpay the intended fee rate and can be built below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes functionality that cannot execute because the required value path is unreachable. The analog here is a Bitcoin transaction-construction defect: when `data` is supplied, `SignableTransaction::new` appends a real OP_RETURN `TxOut` but runs `calculate_weight_vbytes` only over `payments`, so every fee/size decision is computed on a smaller transaction than the one actually signed and broadcast. This is reachable through the documented `data` parameter of the public `SignableTransaction::new` API.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- The OP_RETURN output is pushed into `tx_outs` first when `data` is present:
```rust
// send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```
- But the weight/vbyte calculation only considers `payments`:
```rust
// send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```
`calculate_weight_vbytes` (send.rs:62-127) builds a template `Transaction` containing only the payment `TxOut`s (and optionally `change`), so the OP_RETURN output — up to 80 bytes of data plus ~9 bytes of output overhead — is excluded from both `weight` and `vbytes`.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) underestimates the fee required to achieve the requested feerate.
- The minimum-relay check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (send.rs:211) is evaluated against the smaller vbytes, so a transaction whose *actual* vsize requires a larger minimum fee can be constructed below the relay minimum.
- The same undercount applies to the change-enabled path (`calculate_weight_vbytes(..., Some(&change))` at send.rs:226) and to the `weight > MAX_STANDARD_TX_WEIGHT` guard at send.rs:241, both of which ignore the data output.

Since `fee()` (send.rs:139) is `sum(inputs) - sum(outputs)`, the transaction will still pay *some* fee, but it is not guaranteed to meet `fee_per_vbyte` on the real vsize, nor the network's minimum relay fee for the real size. The wallet test (`networks/bitcoin/tests/wallet.rs:269`) asserts `needed_fee == tx.vsize() * FEE`, but it constructs the transaction with `data: None`, so the discrepancy is never exercised.

### Impact Explanation
A `SignableTransaction` built with `data` set can:

- Achieve an effective feerate below the caller-requested `fee_per_vbyte` (by up to ~(80+9)*4/4 ≈ 90 vbytes worth of fee).
- In the worst case be constructed with a fee below Bitcoin's minimum relay fee for its actual size, producing a signed transaction that will not propagate — i.e., the value-moving action cannot execute, mirroring the reported bug class where a component is unable to perform value-carrying operations.

`data` is a caller-controlled field on the public constructor, so this path is reachable by anyone driving the wallet API (e.g., withdrawal/instruction flows that attach protocol data).

### Likelihood Explanation
Any call to `SignableTransaction::new` with `data.is_some()` triggers the miscalculation deterministically. Whether a produced transaction actually falls below relay minimum depends on the margin between `needed_fee` and the true minimum, but the feerate shortfall occurs on every such transaction. No attacker control of keys or peers is required — only that the constructed transaction carries data.

### Recommendation
Include the OP_RETURN output in the size estimate: either pass the fully assembled `tx_outs` (post-data, pre-change) into `calculate_weight_vbytes`, or add the fixed overhead of `Amount` + script length + `data.len()` to the computed weight/vbytes. Re-run the minimum-relay and `MAX_STANDARD_TX_WEIGHT` checks against the size of the final output set.

### Proof of Concept
```rust
// Conceptual: construct a transaction with data and compare needed_fee
// against the real vsize * fee_per_vbyte.
let tx = SignableTransaction::new(
    vec![input],            // one ReceivedOutput
    &payments,              // e.g. one payment
    None,                   // no change, to isolate the effect
    Some(vec![0xaa; 80]),   // max-size OP_RETURN data
    FEE_PER_VBYTE,
).unwrap();

// tx.needed_fee() was computed from a template tx lacking the OP_RETURN output.
// tx.transaction() includes the ~89-byte OP_RETURN output, so:
//   tx.transaction().vsize() * FEE_PER_VBYTE > tx.needed_fee()
assert!(tx.transaction().vsize() as u64 * FEE_PER_VBYTE > tx.needed_fee());
// With FEE_PER_VBYTE == 1 sat/vB the on-chain fee can also sit below the
// DEFAULT_MIN_RELAY_TX_FEE requirement for the actual size.
```

Root cause confirmed at `networks/bitcoin/src/wallet/send.rs:194-206` — the OP_RETURN `TxOut` is appended to `tx_outs` before `calculate_weight_vbytes` is invoked, yet the estimate is derived solely from `payments`, leaving `needed_fee`, the min-relay check, and the weight cap evaluated against a transaction smaller than the one actually signed.
