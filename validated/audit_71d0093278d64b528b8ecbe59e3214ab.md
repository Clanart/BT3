### Title
`SchnorrAggregate::verify` accepts an empty aggregate signature (missing non-empty invariant enforced on the creation path) - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
The bug class is an invariant bound enforced on one state-transition path but missing on a sibling path that can reach the same state. In Tokemak, `stake()` rejects `points + totalSupply() > u192::MAX` while `extend()` never re-checks the bound. In Serai's `crypto/schnorr`, `SchnorrAggregator::complete()` enforces the invariant "an aggregate signature contains at least one signature" by returning `None` when `self.sigs.is_empty()`, but `SchnorrAggregate::verify` — reachable with attacker-controlled bytes via `SchnorrAggregate::read` — never checks that `Rs` is non-empty. An aggregate with `Rs = []` and `s = 0` verifies successfully against an empty `keys_and_challenges` list.

### Finding Description
`SchnorrAggregator::complete` refuses to emit an aggregate over zero signatures:

```rust
if self.sigs.is_empty() {
  return None;
}
``` [1](#0-0) 

However, `SchnorrAggregate::verify` only checks that `self.Rs.len() == keys_and_challenges.len()`, which is satisfied when both are empty: [2](#0-1) 

With both empty, the `for` loop over `keys_and_challenges` pushes no `(z, R)` / `(z·challenge, key)` pairs, so `pairs` contains only `(-self.s, C::generator())`: [3](#0-2) 

If `s == 0`, `multiexp_vartime(&pairs)` evaluates to `0·G = identity`, and `.is_identity()` returns `true`. `SchnorrAggregate::read` places no lower bound on `Rs` (a `u32` length of `0` is accepted), so an attacker can deserialize `len = 0u32 || s = 0` into a "valid" `SchnorrAggregate` directly: [4](#0-3) 

### Impact Explanation
An unprivileged party can produce a byte string — `0x00000000` followed by the zero scalar encoding — that deserializes via `SchnorrAggregate::read` and passes `verify` whenever the verifier is invoked with an empty `keys_and_challenges` slice. Any protocol flow that asks "did this aggregate verify?" over a set of signers that may legitimately be empty (e.g., a batch with no items, an empty included set, or a filter that produced zero entries) will accept a forgery with no signature whatsoever. The protocol invariant "an aggregate signature attests to at least one real signature" — enforced on the honest construction path — is silently broken on the untrusted-bytes path, exactly paralleling the GPToke `extend()` bypass of the `stake()` bound.

### Likelihood Explanation
Exploitation requires the caller to invoke `verify` with an empty `keys_and_challenges`. Callers that gate on a non-empty set upstream are safe, but the API contract of `verify` (`#[must_use]`, returning `bool`) gives no indication that empty input is vacuous-true, and `read` accepts the trivial encoding. This is a Medium-severity correctness/forgery issue rather than a universally reachable one: it converts "no signatures required" states into "a forged aggregate was provided and accepted" states.

### Recommendation
Reject empty aggregates in `verify`, mirroring the creation-side check:

```rust
if self.Rs.is_empty() || (self.Rs.len() != keys_and_challenges.len()) {
  return false;
}
```

and/or reject `len == 0` in `SchnorrAggregate::read` so the invalid object cannot be constructed from untrusted bytes at all.

### Proof of Concept
```rust
// Aggregate over zero signatures, s = 0
let mut bytes = 0u32.to_le_bytes().to_vec();           // Rs.len() == 0
bytes.extend(<C as Ciphersuite>::F::ZERO.to_repr());   // s == 0

let agg = SchnorrAggregate::<C>::read(&mut &bytes[..]).unwrap();
assert!(agg.verify(b"some_dst", &[])); // returns true today; should be false
```
`verify` computes `pairs = [(-0, G)]`, `multiexp_vartime` yields the identity, and `.is_identity()` returns `true`.
