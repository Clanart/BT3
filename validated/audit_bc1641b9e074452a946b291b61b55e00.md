Based on the investigation, the closest verified analog in GitHub Desktop to the Sherlock M‑26 pattern ("a value/action is fetched from the wrong context because a loosely-matched identifier is trusted instead of an exact one") is the `x-github-client://openRepo` deep‑link handler, which resolves an *existing* local repository via a partial URL match and then automatically performs `fetch` + branch `checkout` driven entirely by attacker-controlled URL parameters.

### Title
Deep-link `openRepo` action silently fetches and checks out an attacker-controlled branch name into a loosely-matched existing repository - (`app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The M‑26 bug is a "wrong context" bug: a decimals lookup is performed against the wrong chain because the code trusts a loosely resolved address instead of verifying the exact chain context. The Desktop analog is `Dispatcher.openBranchNameFromUrl()`/`openOrCloneRepository()`, which resolves which local repository to operate on using only a coarse (owner/name/hostname) URL match, and then performs a live `fetch` + `checkout` using a branch name taken directly from an untrusted `x-github-client://` URL, with no user confirmation step.

### Finding Description
`openRepositoryFromUrl` dispatches based on fields parsed straight out of the incoming URL by `parseAppURL` (`branch`, `pr`, `filepath`), which only validates that the branch string has no "invalid ref chars" via `testForInvalidChars`: [1](#0-0) .

`openBranchNameFromUrl` resolves (or opens) a repository and immediately fetches and checks out that attacker-supplied branch name without any confirmation prompt: [2](#0-1) .

The repository used for this operation is picked by `openOrCloneRepository`, which finds any *already-open* Desktop repository whose GitHub URL loosely matches the URL in the deep link: [3](#0-2) . The match itself, `doesRepositoryMatchUrl`, only checks that the repo's `origin` or `upstream` `htmlURL` matches on hostname/owner/name (via `urlsMatch`) — not that it's the exact remote the user intended, not the protocol, and not any account/token binding: [4](#0-3) [5](#0-4) .

This mirrors the audited bug's broken invariant: a value (which vault/decimals to use, here which repository/branch to operate on) is resolved from a context that is only "close enough" (owner/name match) rather than the exact intended one, and the action (checkout, a working-directory-mutating git operation) is executed unconditionally on that resolution. Unlike the `filepath` handling in the same function, which is defensively checked with `resolveWithin` and `isAbsolute` guards [6](#0-5) , no equivalent guard exists before the branch checkout: the branch name is only checked for ref-syntax validity, not for whether checking it out is safe or expected by the user.

### Impact Explanation
A link the user clicks (e.g. embedded in a webpage, README, or chat message) using the `x-github-client://openRepo/...` scheme can cause Desktop to silently `fetch` and `git checkout` an attacker-chosen branch name into an already-open, trusted local repository, without any dialog asking the user to confirm. If that branch exists on the remote (or is created locally to track a remote ref of that name), the user's working directory is mutated as a side effect of clicking a link — this can silently change what the user is about to commit or push, and if the attacker controls the target repository/branch content, the checked-out tree can include hooks or files that affect subsequent git operations. This satisfies the "silent corruption of what the user commits or pushes" and "link the user clicks" categories in the valid-impact list.

### Likelihood Explanation
The `x-github-client://` (and legacy `github-mac`/`github-windows`) protocol handlers are registered by the app at startup for all platforms: [7](#0-6) , and URLs are routed straight from `open-url`/command-line parsing into `handleAppURL`/dispatcher with no additional user gating beyond focusing the window: [8](#0-7) . Any web page can trigger the custom scheme via a link click on a machine with Desktop installed, satisfying the "unprivileged, attacker controls a link the user clicks" precondition without any local access, malware, or leaked credentials.

### Recommendation
Before performing `fetch`/`checkout` in `openBranchNameFromUrl`, require exact remote-URL equality (not just owner/name/host) between the deep-link URL and the matched repository, and surface a confirmation dialog naming the target repository and branch before mutating the working directory, mirroring the safeguards already applied to the `filepath` branch of `openRepositoryFromUrl` (`resolveWithin`/`isAbsolute` checks) at [6](#0-5) .

### Proof of Concept
1. User has GitHub Desktop installed and has `owner/repo` open locally (origin matches `https://github.com/owner/repo`).
2. Attacker hosts a page (or sends a message) with a link: `x-github-client://openRepo/https://github.com/owner/repo?branch=malicious-branch`.
3. User clicks the link; the OS routes it to Desktop via the registered protocol handler (`app/src/main-process/main.ts:326-335`).
4. `parseAppURL` accepts the branch since it only checks ref-name syntax (`app/src/lib/parse-app-url.ts:98-124`).
5. `openRepositoryFromUrl` → `openBranchNameFromUrl` finds the already-open matching repository via the loose owner/name/host match (`dispatcher.ts:1920-1938`, `repository-matching.ts:137-148`) and, with no prompt, fetches and checks out `malicious-branch` in that repository's working directory (`dispatcher.ts:1975-1996`).

Note: the exact implementation of `checkoutLocalBranch` referenced at `dispatcher.ts:1993` (and how it decides to create vs. track the branch, and whether it can override local uncommitted changes) could not be located in the indexed content and would need to be reviewed directly in the repository to confirm the exact extent of working-directory mutation (e.g., whether uncommitted changes block the checkout). This limitation is due to index size limits — a full Devin session against the repository would be needed to inspect that function body directly.

  private doesRepositoryMatchUrl(
    repo: Repository | CloningRepository,
    url: string
  ): repo is RepositoryWithGitHubRepository {
    if (repo instanceof Repository && isRepositoryWithGitHubRepository(repo)) {
      const originRepoUrl = repo.gitHubRepository.htmlURL
      const upstreamRepoUrl = repo.gitHubRepository.parent?.htmlURL ?? null

      if (originRepoUrl !== null && urlsMatch(originRepoUrl, url)) {
        return true
      }

      if (upstreamRepoUrl !== null && urlsMatch(upstreamRepoUrl, url)) {
        return true
      }
    }

    return false
  }

export function urlsMatch(url1: string, url2: string) {
  const firstIdentifier = parseRepositoryIdentifier(url1)
  const secondIdentifier = parseRepositoryIdentifier(url2)

  return (
    firstIdentifier !== null &&
    secondIdentifier !== null &&
    firstIdentifier.hostname === secondIdentifier.hostname &&
    firstIdentifier.owner === secondIdentifier.owner &&
    firstIdentifier.name === secondIdentifier.name
  )
}

async function handleCommandLineArguments(argv: string[]) {
  const args = parseCommandLineArgs(argv, {
    boolean: ['protocol-launcher'],
  })

  // Desktop registers it's protocol handler callback on Windows as
  // `[executable path] --protocol-launcher "%1"`. Note that extra command
  // line arguments might be added by Chromium
  // (https://electronjs.org/docs/api/app#event-second-instance).

  if (__WIN32__ && args['protocol-launcher'] === true) {
    // On Windows we'll end up getting called with something like
    // `--protocol-launcher --allow-file-access-from-files x-github-client://..`
    // which minimist naturally interprets as
    // `--allow-file-access-from-files=x:/github-client`. This is due to
    // Chromium's hot take on parsing command line arguments, see:
    // https://github.com/electron/electron/issues/20322#issuecomment-534137321
    // So while we could add '--allow-file...' as a boolean we can't know for
    // sure that Chromium won't add more switches later on which is why we have
    // to resort to looking through all arguments looking for something that
    // appears to be an app url.
    const prefixes = Array.from(possibleProtocols, p => `${p}://`)
    const matchingUrl = argv.find(arg => {
      if (prefixes.some(p => arg.startsWith(p))) {
        try {
          new URL(arg)
          return true
        } catch (e) {
          log.error(`Unable to parse argument as URL: ${arg}`)
        }
      }
      return false
    })

    if (matchingUrl) {
      handleAppURL(matchingUrl)
    } else {
      log.error(`Encountered --protocol-launcher without app url`)
    }
    // If --protocol-launcher is present we always want to bail and not
    // risk a smuggled cli switch
    return
  }

  if (typeof args['cli-open'] === 'string') {
    handleCLIAction({ kind: 'open-repository', path: args['cli-open'] })
  } else if (typeof args['cli-clone'] === 'string') {
    handleCLIAction({
      kind: 'clone-url',
      url: args['cli-clone'],
      branch:
        typeof args['cli-branch'] === 'string' ? args['cli-branch'] : undefined,
    })
  }

  return
}

function handleCLIAction(action: CLIAction) {
  onDidLoad(window => {
    // This manual focus call _shouldn't_ be necessary, but is for Chrome on
    // macOS. See https://github.com/desktop/desktop/issues/973.
    window.focus()
    window.sendCLIAction(action)
  })
}
