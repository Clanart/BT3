### Title
Uncontrolled panic on untrusted DKG messages via `Decryption::register` assert and `enc_keys` indexing - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PyTorch report class is "crafted input bytes → memory corruption." Serai is memory-safe Rust, so the honest analog of reachable memory corruption is an uncontrolled abort (panic/OOB index) driven by untrusted bytes. In PedPoP's encryption layer, two panics are reachable from participant-controlled protocol messages: `Decryption::register` hard-`assert!`s that no participant registers an encryption key twice, and `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]`, which panics when the referenced decryptor has no registered key. An unprivileged DKG participant can hit both with bytes they send.

### Finding Description
`Decryption::register` inserts a participant's encryption public key and panics on a second registration for the same participant: `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")` [1](#0-0) . The caller-facing path `Encryption::register` forwards every received `EncryptionKeyMessage` (parsed via `EncryptionKeyMessage::read` over attacker-controlled bytes) directly into this asserting function [2](#0-1) .

Separately, `decrypt_with_proof` — used on the blame path to reveal a message's plaintext given an `EncryptionKeyProof` — verifies the PoP, then dereferences `self.enc_keys[&decryptor]` inside the DLEq verification pairs [3](#0-2) . `enc_keys` is only populated by successful `register` calls, so a `decryptor` index that never registered (or whose registration message failed to parse) causes `HashMap` index panic instead of a `DecryptionError`. The same pattern exists in `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`) [4](#0-3) .

The crate elsewhere treats "faulty" duplicates as a caller concern (see the `Commitments` doc note that the library "does not handle networking"), yet here the library itself aborts the host process rather than returning an error [5](#0-4) .

### Impact Explanation
A malicious or simply buggy DKG participant can crash every honest participant's process: broadcasting two `EncryptionKeyMessage`s (or re-delivering one, e.g., across a reconnect/dedup gap) trips the `assert!`. Submitting a blame/complaint referencing a `decryptor` whose key was never registered panics in `decrypt_with_proof` during blame resolution. In a threshold-signing deployment this aborts the key-generation/signing node — a remotely triggerable denial of service and the closest safe-Rust equivalent of the reported memory-corruption primitive (uncontrolled termination on adversary-supplied input). Medium severity: it requires participation in the protocol and causes availability loss only, not key compromise.

### Likelihood Explanation
The input is fully attacker-controlled: `EncryptionKeyMessage::read`/`EncryptedMessage::read` parse `read_G`, `SchnorrSignature::read`, and a params-bounded `E::read` [6](#0-5) [7](#0-6) . Nothing between the wire and `register`/`decrypt_with_proof` rejects duplicates or missing keys. Whether an integrator pre-dedupes registrations is unspecified; the panic in `decrypt_with_proof` needs no integrator mistake beyond calling the blame path for a `decryptor` lacking a key — reachable whenever a participant's registration was dropped, reordered, or malformed.

### Recommendation
Replace `assert!` in `Decryption::register` with a fallible API returning an error on duplicate registration, and replace `self.enc_keys[&decryptor]` / `enc_keys[&participant]` indexing with `.get(...).ok_or(DecryptionError::…)` so all malformed/unexpected protocol inputs surface as `io::Error`/`DecryptionError` rather than process aborts [8](#0-7) [9](#0-8) .

### Proof of Concept
1. Victim runs `Encryption::new(context, i, rng)` and accepts `EncryptionKeyMessage`s from participants.
2. Attacker (participant `j`) sends two valid `EncryptionKeyMessage`s. Second call reaches `Decryption::register`; `enc_keys.contains_key(&j)` is true → `assert!` panics, aborting the victim.
3. Alternatively, attacker `k` never registers an encryption key but participates in the complaint round; when the victim resolves blame via `decrypt_with_proof(from, decryptor = k, msg, Some(proof))`, `self.enc_keys[&k]` panics before `InvalidProof` can be returned — provided `msg.pop` verifies, which the attacker can satisfy since they generated the key/PoP themselves.

Caveat: I verified reachability at the source level; I did not confirm whether `pedpop/src/lib.rs`'s caller filters duplicate registrations before invoking `Decryption::register` (my grep for call sites returned no visible matches). If the caller already dedupes, the `register` assert reduces in reachability, but the `enc_keys[&decryptor]` panic on the blame path remains unconditionally reachable for any unregistered index.
