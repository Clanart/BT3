### Title
Wei-denominated EVM transfers can spend `LockedCoins`-restricted usei balance, bypassing the vesting/lock check enforced by `SubUnlockedCoins` - (File: sei-cosmos/x/bank/keeper/send.go)

### Summary
The `SubWei` function in the bank keeper's send logic falls back to directly reading and setting the raw `usei` balance (via `GetBalance`/`setBalance`) whenever a wei debit exceeds the account's current sub-usei wei balance, without ever consulting `LockedCoins`. This is the exact "convert bypasses lock check" bug class from the external report: a code path that moves funds derived from a balance that is supposed to be lock-protected, without checking the lock, while a sibling code path (`SubUnlockedCoins`) correctly enforces it.

### Finding Description
Every EVM value transfer (native `msg.value`, including any amount with wei-level precision below 1 usei) is processed by `DBImpl.SubBalance`, which splits the amount into a usei component and a wei component and debits each separately: [1](#0-0) 

The usei portion correctly goes through `SubUnlockedCoins`, which subtracts `LockedCoins` from the balance before allowing the debit: [2](#0-1) 

`LockedCoins` returns the non-spendable portion of a vesting account's balance: [3](#0-2) 

However, the wei portion is debited via `SubWei`, which — once the requested wei amount exceeds the account's tracked sub-usei "wei" remainder — reads the account's **total, lock-unaware** usei balance (`k.GetBalance`, not `SpendableCoins`/`LockedCoins`-adjusted), recomputes an aggregated usei+wei balance, and writes the new usei balance straight back with `k.setBalance(...)`, completely bypassing the `LockedCoins` check that `SubUnlockedCoins` performs: [4](#0-3) 

The same logic is duplicated in the `giga` fork of the bank keeper: [5](#0-4) 

Because `setBalance` writes the account balance unconditionally (it only validates the coin, not lock status): [6](#0-5) 

...an EVM address associated with a vesting/locked Cosmos account can trigger the `SubWei` fallback path (by sending any EVM transaction whose `value` requires drawing on the usei balance to satisfy a wei-denominated remainder — trivially achieved by sending a transaction with a non-usei-aligned `value`, e.g. `1 wei` when the account's wei remainder is `0`) and thereby transfer amounts that should be locked by vesting, entirely skipping the `LockedCoins` restriction.

### Impact Explanation
This breaks the vesting lock invariant enforced elsewhere in the bank module (`SendCoins`, `BurnCoins`, `UndelegateCoins`, etc. all route through `SubUnlockedCoins`). Any account holding locked/vesting `usei` that is also EVM-associated can move its locked tokens out via ordinary EVM value transfers, defeating vesting schedules and any invariant depending on `LockedCoins` (e.g., delayed/periodic vesting, or any future locking mechanism layered on the same `LockedCoins` API). This is an unauthorized transfer of funds that are supposed to be non-spendable — a direct violation of an accounting invariant that the bank module is designed to guarantee, and can be triggered by a single unprivileged EVM transaction from the account holder (or from anyone able to induce a value transfer out of that account, e.g. via an EVM call routed through it).

### Likelihood Explanation
High reachability: any address with an EVM/Sei association and a nonzero `LockedCoins` balance (e.g., genesis vesting accounts, delayed/periodic/continuous vesting accounts) can trigger this by simply sending a standard EVM transaction with a `value` whose wei remainder exceeds the account's current tracked wei dust — something achievable with a single, ordinary, unprivileged transaction, no special permissions or races required.

### Recommendation
`SubWei`'s fallback path should not read the raw usei balance and write it back directly. Instead, it should compute the spendable usei balance (subtracting `LockedCoins`) before allowing the aggregated usei+wei amount to be drawn down — mirroring what `SubUnlockedCoins` does — or the usei portion consumed by the fallback should be routed through `SubUnlockedCoins` (with the corresponding remaining wei tracked separately) so that the lock check is uniformly enforced regardless of whether the debit originates from the usei-denominated or wei-denominated leg of an EVM balance change.

### Proof of Concept
1. Create/observe a vesting (or otherwise `LockedCoins`-restricted) Cosmos account `A` whose entire `usei` balance is locked (e.g., a `DelayedVestingAccount` before `EndTime`), and associate it with an EVM address `A_evm`.
2. Ensure `A`'s tracked wei remainder is `0` (default state).
3. From `A_evm`, submit any ordinary EVM transaction that transfers a nonzero amount with a wei-level remainder to another address, e.g. `value = 1` (1 wei, far below 1 usei = 10^12 wei per `SplitUseiWeiAmount`), or any `value` not aligned to a whole usei.
4. `DBImpl.SubBalance` splits the amount into `usei=0, wei=1` and calls `SubWei(ctx, A, 1)`.
5. Since `currentWeiBalance (0) < amt (1)`, `SubWei` falls into the fallback: it reads `currentUseiBalance := k.GetBalance(ctx, A, "usei").Amount` — the **full locked balance**, not the spendable one — computes `currentAggregatedBalance = currentUseiBalance * 10^12 + 0`, subtracts `1`, and calls `k.setBalance(ctx, A, ...)` directly with the new usei value, one unit lower — bypassing `SubUnlockedCoins`'s `LockedCoins` check entirely.
6. Repeating/scaling this with larger `value` amounts lets the vesting account systematically drain its "locked" usei balance through EVM transfers even though `x/bank`'s own `SendCoins`/`MsgSend` path would reject the same transfer for insufficient spendable (unlocked) funds.

Note: I was not able to independently verify the exact `OneUseiInWei` numeric constant value in the indexed portion of the codebase (the grep for the exact declaration line did not return a match), but its usage in `SplitUseiWeiAmount`/`SubWei` is consistent across `sei-cosmos/x/bank/keeper/send.go` and `giga/deps/xbank/keeper/send.go`, confirming the usei/wei split logic and the described bypass path.

func (k BaseSendKeeper) SubUnlockedCoins(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Coins, checkNeg bool) error {
	if !amt.IsValid() {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidCoins, amt.String())
	}

	lockedCoins := k.LockedCoins(ctx, addr)

	for _, coin := range amt {
		balance := k.GetBalance(ctx, addr, coin.Denom)
		if checkNeg {
			locked := sdk.NewCoin(coin.Denom, lockedCoins.AmountOf(coin.Denom))
			spendable := balance.Sub(locked)

			_, hasNeg := sdk.Coins{spendable}.SafeSub(sdk.Coins{coin})
			if hasNeg {
				return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%s is smaller than %s", spendable, coin)
			}
		}

// setBalance sets the coin balance for an account by address.
func (k BaseSendKeeper) setBalance(ctx sdk.Context, addr sdk.AccAddress, balance sdk.Coin, checkNeg bool) error {
	if checkNeg && !balance.IsValid() {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidCoins, balance.String())
	}

	accountStore := k.getAccountStore(ctx, addr)

	// Bank invariants require to not store zero balances.
	if balance.IsZero() {
		accountStore.Delete([]byte(balance.Denom))
	} else {
		bz := k.cdc.MustMarshal(&balance)
		accountStore.Set([]byte(balance.Denom), bz)
	}

	return nil
}

func (k BaseSendKeeper) SubWei(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Int) (err error) {
	if amt.Equal(sdk.ZeroInt()) {
		return nil
	}
	defer func() {
		if err == nil {
			ctx.EventManager().EmitEvent(
				types.NewWeiSpentEvent(addr, amt),
			)
		}
	}()
	currentWeiBalance := k.GetWeiBalance(ctx, addr)
	if amt.LTE(currentWeiBalance) {
		// no need to change usei balance
		return k.setWeiBalance(ctx, addr, currentWeiBalance.Sub(amt))
	}
	currentUseiBalance := k.GetBalance(ctx, addr, sdk.MustGetBaseDenom()).Amount
	currentAggregatedBalance := currentUseiBalance.Mul(OneUseiInWei).Add(currentWeiBalance)
	postAggregatedbalance := currentAggregatedBalance.Sub(amt)
	if postAggregatedbalance.IsNegative() {
		return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%swei is smaller than %swei", currentAggregatedBalance, amt)
	}
	useiBalance, weiBalance := SplitUseiWeiAmount(postAggregatedbalance)
	if err := k.setBalance(ctx, addr, sdk.NewCoin(sdk.MustGetBaseDenom(), useiBalance), true); err != nil {
		return err
	}
	return k.setWeiBalance(ctx, addr, weiBalance)
}

// LockedCoins returns all the coins that are not spendable (i.e. locked) for an
// account by address. For standard accounts, the result will always be no coins.

func (k BaseViewKeeper) LockedCoins(ctx sdk.Context, addr sdk.AccAddress) sdk.Coins {
	acc := k.ak.GetAccount(ctx, addr)
	if acc != nil {
		vacc, ok := acc.(vestexported.VestingAccount)
		if ok {
			return vacc.LockedCoins(ctx.BlockTime())
		}
	}

	return sdk.NewCoins()
}
