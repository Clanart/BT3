## Analysis

The External Report's bug class is: an attacker-controlled callback/hook fires during a batched operation because a security check that should gate it was disabled/missing, letting the attacker hijack control flow and steal something the honest user was entitled to. The strongest Desktop analog is not a re-entrancy bug in JS logic, but an explicit disabling of Git's own upstream clone-hook protection in `clone.ts`.

### Title
Desktop disables Git's clone-time hook/submodule protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-enabling arbitrary code execution from a malicious cloned repository - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` unconditionally sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on every clone Desktop performs, including `--recursive` clones that also initialize submodules. [1](#0-0)  `GIT_CLONE_PROTECTION_ACTIVE` is the internal signal upstream Git uses (added as part of the CVE-2024-32002/32004 hardening) to tell nested Git processes invoked during a clone (checkout, submodule clone/update) that they are still inside an untrusted, just-fetched repository and must refuse operations that would let a hostile repo plant and execute hooks (e.g. via colliding `.git`/`.GIT` paths on case-insensitive filesystems, or via submodule hook directories) before the user has ever reviewed the content. By forcing this flag to `'false'`, Desktop actively opts every clone out of that protection.

### Finding Description
`clone()` builds the git invocation with `--recursive` and merges in `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the environment passed to the `git` command: [1](#0-0) 

This runs before the local `isClonePathSensitive` destination check even matters — the destination check only protects specific well-known host paths (home dir, `.ssh`, `.gnupg`, `.config`, etc.) [2](#0-1) ; it does nothing to constrain what the *content* of the cloned repository (including nested submodules pulled in via `--recursive`) is allowed to do once Git's own hook-protection is turned off for the duration of the clone.

The broken invariant is: "content fetched from an untrusted remote must not be able to execute code on the user's machine as a side effect of the clone operation itself." Git's own defense-in-depth for this (the clone-protection-active state machine) is the guard that exists specifically to preserve that invariant — Desktop removes the guard rather than relying on it.

### Impact Explanation
If a victim uses GitHub Desktop's "Clone repository" flow (URL, `x-github-client://openRepo/...` deep link parsed by `parseAppURL`, or "Open in Desktop" from github.com) against an attacker-controlled or attacker-modified repository, the clone is executed with hook protections deliberately disabled. A crafted repository with, e.g., a submodule pointing at content designed to collide with hook install locations, or a hook shipped in a submodule that gets checked out via the `--recursive` clone, can achieve code execution on the victim's machine at clone time — before the user ever inspects the repository. This is unprivileged, remote, attacker-controlled-repository code execution, matching the report's class of "attacker abuses execution reached during a compound git-driven operation to steal control from a legitimate flow."

### Likelihood Explanation
Cloning is a normal, expected, single-step user action (paste a URL, click "Open in Desktop" from GitHub, or follow a shared repo link) — no local access, admin rights, or unnatural steps are required. The disabling of the protection is unconditional and applies to every clone Desktop performs, so any attacker who can get a victim to clone a URL (including through the `open-repository-from-url` deep-link path handled in `dispatcher.ts`) [3](#0-2)  can attempt this.

### Recommendation
Remove the explicit override of `GIT_CLONE_PROTECTION_ACTIVE` in `clone()` and let Git manage this internal state itself, or at minimum only set it to `'true'`/leave it unset so Git's built-in clone-time hook/submodule protections remain active for all Desktop-initiated clones, especially recursive ones.

### Proof of Concept
1. Attacker publishes a repository with a submodule configured such that the recursive clone/checkout path can plant an executable file into a location Git will treat as a hook target (the exact primitive fixed by the upstream `GIT_CLONE_PROTECTION_ACTIVE` hardening).
2. Victim clones the repository through GitHub Desktop (via UI, `x-github-client://openRepo/...` link, or CLI `--cli-clone`) — `clone()` runs the underlying `git ... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` forced in the environment. [1](#0-0) 
3. Because Git's clone-time protection is explicitly disabled, the hostile content planted by the submodule/hook is allowed to execute as part of completing the clone, achieving code execution on the victim's machine without any further action.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
