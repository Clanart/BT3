### Title
Blame proof emitted before PoP verification reveals ECDH key for an attacker's replayed message key, decrypting an honest participant's secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP `KeyMachine::calculate_share` decrypts each incoming `EncryptedMessage` and immediately constructs an `EncryptionKeyProof` (which reveals the recipient's ECDH shared key for that message's ephemeral key `msg.key`) via `Encryption::decrypt`. The Schnorr proof-of-possession on `msg.key` is only *queued* into a `BatchVerifier` — it is not verified until `batch.verify_with_vartime_blame()` at the end of the loop. If the decrypted bytes fail `C::F::from_repr`, `calculate_share` returns early with `PedPoPError::InvalidShare { blame: Some(proof) }`, publishing the ECDH-revealing proof for a message whose PoP was never checked. This mirrors the curl STARTTLS flaw: data produced under a pre-authentication assumption (that `msg.key` is owned by the claimed sender) is used/emitted after the point where authentication should have gated it.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs` (`Encryption::decrypt`), the PoP is only scheduled via `msg.pop.batch_verify(...)` while `ecdh(&self.enc_key, msg.key)` is computed and the `EncryptionKeyProof { key, dleq }` is constructed unconditionally [1](#0-0) . The code comments explicitly acknowledge the danger of revealing `bX` for a key the sender doesn't own: the PoP exists precisely so Eve cannot claim Alice's `enc_key` and trick Bob into revealing the shared key that decrypts Alice's message [2](#0-1) .

However, in `KeyMachine::calculate_share`, the returned `blame` proof is attached to the error *before* the batch (which contains the PoP verification) is executed: the `from_repr` failure path at lines 479–482 returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` immediately, short-circuiting `batch.verify_with_vartime_blame()` at line 493 [3](#0-2) . The PoP challenge binds the ciphertext bytes (`msg`), so an attacker who malleates the ciphertext cannot reuse the honest sender's valid PoP — but the blame proof escapes before that failure is ever detected [4](#0-3) .

### Impact Explanation
An unprivileged participant Eve observes an honest `EncryptedMessage` from Alice to Bob with ephemeral key `K_a` and ciphertext `C_a` (encrypting Alice's valid share to Bob under `ecdh(bob_enc, K_a)`). Eve sends Bob a new `EncryptedMessage` reusing `key = K_a` with a malleated/invalid ciphertext and any PoP (it will not verify, since Eve doesn't know `dlog(K_a)` and the challenge binds the altered ciphertext). Bob's `calculate_share` decrypts under `ecdh(bob_enc, K_a)` — the same shared key as Alice's message — producing garbage that is non-canonical as a Ristretto scalar with overwhelming probability (the group order `l ≈ 2^252`, so a random 32-byte string is canonical only ~1/16 of the time). The function returns early with `blame: Some(EncryptionKeyProof)` containing `key = ecdh(bob_enc, K_a)` plus a DLEq linking it to Bob's registered `enc_key`. Once that accusation/blame is published, *anyone* can apply the revealed `key` as the ChaCha20 cipher key to `C_a` and recover Alice's secret share to Bob — a key-share recovery primitive the PoP was specifically designed to prevent [5](#0-4) . Although downstream blame adjudication (`decrypt_with_proof`) will correctly fault Eve for the invalid signature [6](#0-5) , the ECDH key has already been disclosed in the accusation, so the secret leak is irreversible.

### Likelihood Explanation
Any DKG participant (or anyone able to submit a share message attributed to a participant index) can trigger this with public inputs: replay a victim's observed `msg.key`, supply a garbage ciphertext, and wait for the victim's `calculate_share` to emit the `InvalidShare` error carrying the blame proof. No collusion, no key knowledge, and no control over the RNG is required; success probability per attempt is ~15/16 (probability the garbage decryption is non-canonical), and `EncryptedMessage::read`/`SecretShare` parsing places no additional gate before `decrypt` [7](#0-6) . The processor propagates this error and its blame payload outward (`ProcessorMessage::InvalidShare`-style handling in `processor/src/key_gen.rs`), making the leaked proof available to all observers.

### Recommendation
Do not release the `EncryptionKeyProof` until the PoP for that specific message has actually been verified. Concretely:

- In `Encryption::decrypt`, verify `msg.pop` synchronously (or split the API so the proof is computed only after the caller confirms the PoP passed), before computing/returning `ecdh(&self.enc_key, msg.key)` [8](#0-7) .
- Alternatively, in `calculate_share`, batch only the PoPs first and verify them in a dedicated pass; only for messages whose PoP is valid should decryption proceed and `blame` proofs be attached. A non-canonical decryption of a PoP-less message must yield `blame: None` (or blame the sender directly) rather than an `EncryptionKeyProof` [3](#0-2) .
- Additionally, treat an invalid PoP as `DecryptionError::InvalidSignature` → blame the sender with no key reveal, matching the semantics already enforced in `decrypt_with_proof` [9](#0-8) .

### Proof of Concept
```rust
// Bob runs calculate_share over received shares.
// Alice's honest message to Bob: EncryptedMessage { key: K_a, pop: P_a, msg: C_a }
// where C_a = share_bytes XOR chacha20(ecdh(bob_enc_priv, K_a)).

// Eve (participant l) constructs her message to Bob:
let mut evil = EncryptedMessage::<C, SecretShare<C::F>> {
    key: alice_msg.key,                    // replay K_a — Eve does NOT know dlog(K_a)
    pop: some_schnorr_signature,           // cannot be valid: pop_challenge binds msg bytes
    msg: Zeroizing::new(SecretShare([0xFF; 32])), // garbage ciphertext
};

// Inside Bob's calculate_share:
//   decrypt() queues evil.pop into `batch` (never yet verified)
//   key = ecdh(bob_enc_priv, K_a)          // identical to Alice's shared key
//   proof = EncryptionKeyProof { key, dleq(generator, K_a; bob_enc_priv) }
//   decrypted = garbage ^ keystream(key)   // non-canonical w.p. ~15/16
//   => Err(InvalidShare { participant: l, blame: Some(proof) })
//      returns BEFORE batch.verify_with_vartime_blame() checks evil.pop
//
// Bob's processor publishes `proof`. Any observer now computes:
//   chacha20_stream(proof.key) XOR alice_msg.msg = Alice's secret share to Bob
// recovering a share the PoP mechanism (encryption.rs lines 84-90) was designed to protect.
```
Root cause: `blame` is emitted at `crypto/dkg/pedpop/src/lib.rs:480-482` for a message whose authentication (`msg.pop`) is still only pending inside `batch` [10](#0-9) .

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}

    from: Participant,

    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,

      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),

      Err(DecryptionError::InvalidSignature)?;

      Ok(msg.msg)
    } else {
