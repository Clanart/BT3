### Title
`multisig` validates only the prevout `script_pubkey` while signing a sighash that commits to the entire attacker-controlled `TxOut` — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

Analogous to the SSRF redirect bypass (validate the URL at check-time, fetch an unvalidated target at use-time), `SignableTransaction::multisig` performs a partial check-time validation of each `ReceivedOutput` — verifying only that `prevouts[i].script_pubkey` equals `p2tr_script_buf(offset.group_key())` — and then, at use-time, feeds the *entire* `prevouts` vector (including the unchecked `value` field) into `taproot_key_spend_signature_hash` via `Prevouts::All`. Since `ReceivedOutput::read` accepts untrusted bytes (`TxOut::consensus_decode` of arbitrary `value`/`script_pubkey`/`outpoint`), a peer can supply an output whose script matches the threshold key but whose `value` does not match the real on-chain UTXO.

### Finding Description

- `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) deserializes `offset`, `output: TxOut`, and `outpoint` from raw bytes with no binding to chain state.
- `SignableTransaction::new` (`send.rs:175-185`) uses `input.output.value` for fee/funds accounting and `input.outpoint` for `TxIn` construction — both unchecked.
- `SignableTransaction::multisig` (`send.rs:273-285`) is the only validation point: it checks `p2tr_script_buf(offset.group_key()) == self.prevouts[i].script_pubkey`. The `value` inside `prevouts[i]` is never validated.
- `TransactionSignMachine::sign` (`send.rs:373-391`) then signs `taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), ...)`, which commits to each prevout's full `TxOut` including `value` (BIP-341 commits `amount` and `scriptPubKey` of all prevouts).

So the value that is *validated* (script ownership) differs from the value that is *used* (the full `TxOut` hashed into the sighash) — the same check-time/use-time split as `isSSRFSafeURL` vs `file_get_contents` following redirects.

### Impact Explanation

If a malicious participant/peer supplies a serialized `ReceivedOutput` whose `script_pubkey` matches the key but whose `value` differs from the real UTXO, the threshold signature produced over `Prevouts::All` commits to the false amount. Two consequences:

- The resulting transaction is invalid on-chain (BIP-341 sighash mismatch against actual prevout values), so an output that `scan_transaction`/deserialization reported as received and that passed `multisig`'s key check is not actually spendable by the produced signature.
- `fee()`/`needed_fee` accounting in `new` uses the forged `value`, so `NotEnoughFunds` checks and change computation are performed against phantom sats.

### Likelihood Explanation

Reachability requires feeding forged `ReceivedOutput` bytes (e.g., deserialized from an untrusted source rather than produced by `Scanner::scan_transaction`), which is within the accepted input surface (`ReceivedOutput::read`). The `multisig` key check is the natural place an integrator would rely on for validation, and it silently passes forged values through to the sighash.

### Recommendation

In `SignableTransaction::multisig` (or at `ReceivedOutput::read` consumers), re-validate the full `TxOut` — not just `script_pubkey` — against independently verified chain data (e.g., via the `outpoint` lookup through `rpc.rs`) before committing `prevouts` to `Prevouts::All`. At minimum, document that `multisig` only authenticates the script and that `value` must be verified out-of-band.

### Proof of Concept

1. On-chain UTXO at outpoint `O` pays `p2tr_script_buf(key + G*offset)` with value `V_real`.
2. Attacker serializes a `ReceivedOutput` with `offset`, `outpoint = O`, and `TxOut { script_pubkey: same, value: V_fake ≠ V_real }`; honest node calls `ReceivedOutput::read`.
3. `SignableTransaction::new` accepts it; `multisig()` passes since `script_pubkey` matches.
4. `sign()` computes the sighash committing `value = V_fake`; the completed transaction's witness signatures fail BIP-341 verification against `V_real` — the output is unspendable despite passing validation.
