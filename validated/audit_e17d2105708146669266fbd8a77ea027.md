### Title
Reward-forfeiture bypass via cancelUnlock/startUnlock timing manipulation before harvest - ([File: VLMGP.sol], [File: rewards/vlMGPBaseRewarder.sol])

### Summary
`_calExpireForfeit` in `rewards/vlMGPBaseRewarder.sol` determines a user's forfeitable reward share by reading the *live* state of `VLMGP.getRewardablePercentWAD(_account)` at the moment of `getReward`/`queueMGP`, rather than accruing forfeiture continuously per second. Because `VLMGP.cancelUnlock` lets a user unilaterally zero out an active cooldown slot with no penalty, an attacker can cancel their cooldown immediately before triggering a harvest (converting a partially-forfeitable "in cooldown" balance into a fully-locked 100%-rewardable balance), collect their pending MGP/bonus rewards in full, then call `startUnlock` again right after to re-open a fresh cooldown slot.

### Finding Description
`VLMGP.getRewardablePercentWAD` (VLMGP.sol:193-218) computes the rewardable share as `fullyInLock` plus, for each unlock slot: 0% if the slot is *still actively cooling down* (block.timestamp <= endTime), or a time-weighted partial credit if the slot has already passed `endTime`. [1](#0-0) 
This means any amount actively in cooldown contributes **zero** to the rewardable percentage while cooling down — the entire cooldown portion is meant to be forfeited to other lockers via `_calExpireForfeit`/`_queueNewRewardsWithoutTransfer` in `rewards/vlMGPBaseRewarder.sol`. [2](#0-1) 

`VLMGP.cancelUnlock(_slotIndex)` allows the user, unprivileged and penalty-free, to immediately zero out `slot.amountInCoolDown` and decrement `totalAmountInCoolDown`, with no time delay, no fee, and no forfeiture check: [3](#0-2) 

Because `getRewardablePercentWAD` is a spot read (not an accrual tracked over time), the exploit sequence is:
1. Attacker has an active cooldown slot from a prior `startUnlock` (currently contributing 0% rewardable share, so pending rewards would be forfeited).
2. Attacker calls `VLMGP.cancelUnlock(_slotIndex)` — the cooldown amount instantly becomes "fully locked" again, with `getRewardablePercentWAD` jumping to ~100%.
3. Attacker triggers `MasterMagpie.multiclaimFor`/`getReward`, which reaches `vlMGPBaseRewarder.getReward`/`queueMGP` → `_sendReward`/`_calExpireForfeit`, now computing `forfeitAmount = 0` since the account reads as fully locked. [4](#0-3) 
4. Immediately after, attacker calls `VLMGP.startUnlock(sameAmount)` to re-open a new cooldown slot for the same amount (note: `startUnlock` itself also triggers `multiclaimFor` at its start, but no new rewards have accrued in the interim, so this is harmless to the attacker). [5](#0-4) 

The only "cost" to the attacker is that the new cooldown slot restarts its timer from `block.timestamp`, losing prior cooldown progress toward actual withdrawal — but this is not a monetary or time-locked cost relevant to the reward-forfeiture invariant; the attacker can repeat this pattern before every harvest indefinitely, at zero capital cost beyond gas, fully defeating the intended forfeiture-to-other-lockers mechanism.

No existing modifier (`whenNotPaused`, `nonReentrant`, `onlyMasterMagpie`, `updateReward`) prevents this, since `cancelUnlock` is a fully public, permissionless, unrestricted state mutation with no cooldown-of-its-own or fee, and the forfeiture computation trusts the current on-chain cooldown state without any historical/accrued tracking.

### Impact Explanation
This breaks the "Conservation" invariant: a user in cooldown is supposed to forfeit the cooldown-weighted share of pending MGP/bonus rewards to other lockers via `_queueNewRewardsWithoutTransfer`. By gaming the spot-check timing, an attacker with a cooldown slot can harvest 100% of pending rewards that should have been partially/fully forfeited, repeatedly and indefinitely, at zero cost. This is a theft of unclaimed yield that should have been redistributed to other, fully-locked vlMGP holders — reducing rewards actually available to honest lockers who obey/respect the cooldown penalty design.

### Likelihood Explanation
- Requires only holding any amount of vlMGP with an active cooldown slot (attacker-controlled precondition, trivially achievable via `lock` + `startUnlock`).
- No special privileges, capital, or timing races against other users are needed — the attacker controls their own claim timing.
- Fully repeatable before every harvest cycle.
- The only friction is the extra gas for `cancelUnlock` + `startUnlock` around each claim and the need to restart their personal unlock timer, which is not a real deterrent for a rational actor optimizing yield extraction.

### Recommendation
Do not compute forfeiture based on a live, mutable snapshot of cooldown state at claim time. Instead:
- Track forfeiture continuously (e.g., accrue rewardable/forfeitable amounts per unit time as cooldown state changes, similar to a reward-per-token checkpoint), or
- Impose a minimum lock-in period after `cancelUnlock` before rewards can be claimed at the restored (fully-locked) rate, or
- Disallow `cancelUnlock` immediately before/within the same block as a `getReward`/`queueMGP` call (e.g., require a cooldown/delay on `cancelUnlock` itself, or checkpoint rewards at the state that existed at last accrual rather than at claim time).

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder`, MGP token, and bonus reward token per repo test harness.
2. Attacker locks MGP via `VLMGP.lock`, then `VLMGP.startUnlock(amount)` to open a cooldown slot (record `slotIndex`).
3. Queue/accrue MGP and bonus rewards into `vlMGPBaseRewarder` (via `queueMGP`/`queueNewRewards`) while attacker is mid-cooldown (`block.timestamp < slot.endTime`).
4. **Baseline run**: Advance time partially into cooldown, call `MasterMagpie.multiclaimFor`/`getReward` for attacker directly (without cancelling), and record `forfeitAmount` emitted/queued via `ForfeitRewardAdded`/`MGPHarvested` events — expect `forfeitAmount > 0` matching `_calExpireForfeit`.
5. **Exploit run**: Reset state (new fork/snapshot) to the same accrual point, but before harvesting, call `VLMGP.cancelUnlock(slotIndex)`, then call `MasterMagpie.multiclaimFor`/`getReward`, then `VLMGP.startUnlock(amount)` to reopen the same-size cooldown slot.
6. Assert: in the exploit run, `forfeitAmount == 0` (or reward received == full pending amount) despite identical reward accrual window and identical starting cooldown state, proving the trick zeroes out forfeiture that would otherwise apply in the baseline run.
7. Assert the attacker's total vlMGP balance and eventual unlock capability are unaffected except for cooldown timer reset, confirming zero monetary cost for the reward-forfeiture bypass.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
