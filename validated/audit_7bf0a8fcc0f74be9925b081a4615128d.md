### Title
Reward-share dilution via direct ERC20 donation to `_calLpSupply()` balance-based denominator - (File: `rewards/MasterMagpie.sol`)

### Summary
`_calLpSupply()` uses `IERC20(_stakingToken).balanceOf(address(this))` as the denominator for `accMGPPerShare` for every pool except `vlmgp`/`mWomSV`. Any unprivileged actor can `transfer()` staking tokens directly to `MasterMagpie` (bypassing `deposit()`), permanently inflating this balance without crediting any `UserInfo.amount`, so a fraction of the MGP emitted via `mgpPerSec` is never reflected into any user's claimable balance again.

### Finding Description
`updatePool()` computes `mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint` and then divides it by `lpSupply = _calLpSupply(_stakingToken)` to increment `pool.accMGPPerShare`: [1](#0-0) 

For any pool other than `vlmgp`/`mWomSV`, `_calLpSupply()` simply reads the raw token balance held by the contract rather than an internally tracked total of legitimately staked tokens: [2](#0-1) 

`_deposit()`/`_withdraw()` keep `user.amount` and `user.available` moving in lockstep for regular pools, and `user.rewardDebt` is always resynced against `pool.accMGPPerShare`: [3](#0-2) [4](#0-3) 

Because there is no internal accounting of `totalStaked` separate from `balanceOf`, any address can call the staking token's own `transfer(masterMagpie, amount)` — a plain, unprivileged ERC20 call requiring no allowance or role — to inflate `lpSupply` without ever calling `deposit()`. The very next `updatePool()` call (triggered from any `deposit`, `withdraw`, `depositFor`, `withdrawFor`, `multiclaim*`, since all of these call `updatePool` internally, e.g. inside `_deposit`/`_harvestAndUnstake`) divides the fixed `mgpReward` for that interval by the inflated denominator, permanently reducing the per-token increment of `accMGPPerShare`. This portion of the intended emission (`mgpReward - actualDistributableAmount`) is never credited to any `UserInfo.rewardDebt`/pending balance and can never be recovered, since the donated tokens sit in the contract without any corresponding `UserInfo.amount` entitling anyone to withdraw them and reduce `lpSupply` back down.

The `withdraw`/`_harvestAndUnstake` path itself does not create the inflation — the donation is a separate, direct `transfer()` call to the token contract — but every subsequent `withdraw()` (and `deposit()`) call locks in and realizes the diluted `accMGPPerShare` via its `updatePool()` call, permanently reducing the rewards distributable to legitimate stakers for that interval. Existing checks (`whenNotPaused`, `nonReentrant`, `user.available < _amount` checks) do not defend against this because they only validate the caller's own withdrawal amount against their own `UserInfo`, not against the global supply/balance discrepancy.

Note: contrary to the framing in the question, `withdraw()` is not itself the entry point that causes the inflation (a raw ERC20 `transfer` is), and the per-user `available` vs `amount` fields remain internally consistent for any single user's own storage (they are always updated together in `_deposit`/`_harvestAndUnstake`). The actual broken invariant is at the pool level: `lpSupply` (used as denominator) can exceed `sum(UserInfo.amount)` for that pool, permanently diluting `accMGPPerShare` growth for all real stakers.

### Impact Explanation
Once a pool becomes the sole allocation-point recipient (a plausible early-stage or single-pool configuration), an attacker can permanently and cheaply inflate `lpSupply` by donating staking tokens. This causes a fraction of every future MGP emission for that pool to be mathematically unreachable by any user's `rewardDebt`/`unClaimedMgp` accounting — that MGP is effectively permanently unclaimable by any staker, matching "Permanent freezing of unclaimed yield" (High). The magnitude scales with how large the donation is relative to genuine stake, and the effect is permanent because there is no mechanism to remove the donated balance or exclude it from `_calLpSupply()`.

### Likelihood Explanation
Low capital and no privileged role is required — buying or already holding the staking token and calling its standard `transfer()` function suffices. It requires the target pool to have a non-trivial allocation of `mgpPerSec` (best case: sole non-zero `allocPoint` pool) to maximize the diluted amount, but the mechanism works to some degree on any pool with `MPGRewardPool`/default accounting using `balanceOf`. The attack is repeatable indefinitely and requires no complex timing, flash loans, or reentrancy.

### Recommendation
Track staked supply internally (e.g., a `pool.totalStaked` incremented/decremented in `_deposit`/`_withdraw`/`emergencyWithdraw`) instead of relying on `IERC20(_stakingToken).balanceOf(address(this))` in `_calLpSupply()`. This decouples reward accounting from the token's raw balance, eliminating the donation-based dilution vector.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `MasterMagpie`, an ERC20 mock staking token, and set the pool's `allocPoint` as the only non-zero pool (so `totalAllocPoint == pool.allocPoint`).
2. User A calls `deposit(stakingToken, 100e18)` (legit stake).
3. Advance time by `T` seconds; record expected `mgpReward = T * mgpPerSec`.
4. Attacker (holding tokens bought on market, no special role) calls `stakingToken.transfer(masterMagpie, 900e18)` directly (no `deposit()` call).
5. Call `updatePool(stakingToken)` (or trigger via any `deposit`/`withdraw`) — assert `pool.accMGPPerShare` increment equals `mgpReward * 1e12 / 1000e18` instead of the correct `mgpReward * 1e12 / 100e18`.
6. Have User A call `withdraw(stakingToken, 100e18)` and claim; assert claimed MGP is roughly 1/10th of `mgpReward`, and the remaining ~90% of emitted `mgpReward` for that interval is unrecoverable by any `UserInfo` in the pool (no address's `unClaimedMgp`/pending sums to the full `mgpReward`).
7. Assert this shortfall persists across further deposit/withdraw cycles as long as the donated 900e18 balance remains, confirming permanent dilution/freezing of a portion of unclaimed yield.

        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
