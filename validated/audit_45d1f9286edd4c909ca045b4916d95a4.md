### Title
Swallowed conflict-detection errors mask real merge/rebase conflicts as "resolved" - ([File: app/src/lib/git/status.ts])

### Summary
`getStatus()` builds the conflict view of a repository by calling `getConflictDetails()`, which wraps the underlying git conflict-detail calls (`getFilesWithConflictMarkers`, `getBinaryPaths`) in a single `try/catch` and, on *any* error, silently discards it and returns an empty result set. This is structurally the same broken invariant as the NEAR bug: a fallible sub-operation is reduced to a default/optimistic value on failure, and that default is then trusted by downstream logic that assumes it means "no conflicts here," rather than "the check could not be completed."

### Finding Description
`getStatus` computes `conflictedFilesInIndex` from `git status --porcelain=2` output and then calls `getConflictDetails` to enrich each conflicted path with a conflict-marker count and whether it is a binary file: [1](#0-0) 

Any error thrown by `getMergeConflictDetails`, `getRebaseConflictDetails`, or `getWorkingDirectoryConflictDetails` (which shell out to git for `getFilesWithConflictMarkers`/`getBinaryPaths`) is caught, logged, and replaced with:
```
{ conflictCountsByPath: new Map(), binaryFilePaths: [] }
``` [2](#0-1) 

That masked value is then used per-file in `parseConflictedState`:
```
conflictMarkerCount: conflictDetails.conflictCountsByPath.get(path) || 0
``` [3](#0-2) 

A file whose conflict-marker scan genuinely failed (transient git error, malformed/huge diff, encoding issue, or any I/O failure triggered by content in an attacker-controlled clone) gets exactly the same `conflictMarkerCount: 0` as a file that git has *already reconciled with no markers*. Desktop's conflict UI and "manual conflict" classification (`app/src/models/status.ts`, `app/src/ui/lib/conflicts/unmerged-file.tsx`) key off `conflictMarkerCount` to decide whether a file needs the marker-based merge-conflict editor or can be treated as a simple binary/manual resolution. `doConflictedFilesExist` at the top level still reports `true` (it is derived independently from `conflictedFilesInIndex.length`), so the app still knows "a conflict exists," but the per-file detail that drives whether markers are shown/enforced is silently zeroed out — exactly analogous to `fetch_block_new_chunks` still knowing a chunk exists but mis-classifying it due to a masked `EpochError`.

The one inner exception (`getWorkingDirectoryConflictDetails`'s catch around `getBinaryPaths(..., 'HEAD', ...)`) is deliberately scoped to "HEAD doesn't exist" and is a narrower, more defensible case: [4](#0-3) 
but the outer `getConflictDetails` catch has no such narrowing — it swallows *any* error from any of the three conflict-detail helpers, including ones unrelated to "HEAD doesn't exist."

### Impact Explanation
If an attacker-controlled repository/branch content (e.g., pathological binary blobs, encoding that breaks the conflict-marker scan, or a git operation that fails transiently under load) triggers an error in `getFilesWithConflictMarkers` or `getBinaryPaths`, Desktop will present the affected file with `conflictMarkerCount: 0` instead of surfacing the failure. Depending on how the UI branches on that count, a user could be shown a file as having no unresolved markers or be routed through the "manual/binary conflict" path, and stage/commit the file without ever seeing the actual `<<<<<<<`/`=======`/`>>>>>>>` markers that git left in place. That is a silent corruption of what the user commits — conflict markers or unmerged content ending up in a commit that the user believed was clean — which matches the "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
The catch is unconditional and untyped — it does not check the specific `DugiteError`/exit code, so any transient failure (disk contention, huge diff timeout, non-UTF8 content in a hostile file) reaching `getFilesWithConflictMarkers`/`getBinaryPaths` degrades into the same "no markers" default as a legitimately resolved file. There is no retry, no distinguishing "check failed" from "check found nothing," and no propagation back to `getStatus`'s caller. Because `getStatus` is called continuously during Desktop's refresh cycle after every merge/rebase/cherry-pick/stash-pop step, a transient failure at exactly the moment the user is asked to resolve conflicts is enough to trigger the masked state — no admin rights, local access, or social engineering required beyond the user already interacting with an attacker-influenced repository (a fetched/merged branch), which is within the accepted attacker model.

### Recommendation
- Change `getConflictDetails` to only catch and default on the specific, expected error conditions (e.g., "HEAD/MERGE_HEAD/REBASE_HEAD does not exist yet"), and otherwise propagate the error so `getStatus` can surface it (similar to the nearcore fix returning `Err` instead of masking with `false`).
- Consider adding an explicit tri-state result (`ok | unknown | none`) for `conflictCountsByPath`/`binaryFilePaths` so downstream UI can distinguish "confirmed no markers" from "marker scan failed," and refuse to auto-resolve/allow commit in the latter case.
- Add a regression test that forces `getFilesWithConflictMarkers`/`getBinaryPaths` to throw during an active merge conflict and asserts that `getStatus` reports the failure (or at minimum keeps the file flagged for manual review) rather than defaulting `conflictMarkerCount` to 0.

async function getConflictDetails(
  repository: Repository,
  mergeHeadFound: boolean,
  conflictedFilesInIndex: ReadonlyArray<IStatusEntry>,
  rebaseInternalState: RebaseInternalState | null
): Promise<ConflictFilesDetails> {
  try {
    if (mergeHeadFound) {
      return await getMergeConflictDetails(repository, conflictedFilesInIndex)
    }

    if (rebaseInternalState !== null) {
      return await getRebaseConflictDetails(repository, conflictedFilesInIndex)
    }

    // If there's conflicted files in the index but we don't have a merge head
    // or a rebase internal state, then we're likely in a situation where a
    // stash has introduced conflicts
    if (conflictedFilesInIndex.length > 0) {
      return await getWorkingDirectoryConflictDetails(
        repository,
        conflictedFilesInIndex
      )
    }
  } catch (error) {
    log.error(
      'Unexpected error from git operations in getConflictDetails',
      error
    )
  }
  return {
    conflictCountsByPath: new Map<string, number>(),
    binaryFilePaths: new Array<string>(),
  }
}
