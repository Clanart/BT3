### Title
Malformed `ThresholdKeys` encoding triggers attacker-controlled pre-allocation denial of service - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` trusts the serialized participant count before validating the threshold parameters and uses it to pre-allocate the constant-interpolation coefficient vector. A malformed input can therefore request allocation for 65,535 field elements with only a small serialized header.

### Finding Description
`ThresholdKeys::read` reads attacker-controlled `t`, `n`, and `i` fields directly from the stream. It then reads the interpolation tag and, for `Interpolation::Constant`, executes `Vec::with_capacity(usize::from(n))` before calling `ThresholdParams::new(t, n, i)` or otherwise bounding `n` against the amount of data actually present. The subsequent scalar reads fail on a truncated input, but the oversized allocation has already occurred.

For a 32-byte scalar field, declaring `n = u16::MAX` causes an allocation of approximately 2 MiB from a message of roughly a dozen bytes after the curve ID. This is a deserialization-time memory amplification issue analogous to the referenced Jackson denial-of-service class.

### Impact Explanation
An unprivileged party that can supply serialized `ThresholdKeys` bytes to a service can force disproportionate heap allocations without providing a proportionate amount of input. Repeated malformed messages can increase allocator pressure, trigger swapping or out-of-memory termination, and deny service to other operations.

### Likelihood Explanation
Exploitation requires an exposed path that feeds untrusted bytes to `ThresholdKeys::read`. No valid key material, authentication bypass, malformed signature, or consensus-level condition is required. The malicious input only needs a matching curve ID, encoded parameters selecting `n = 65535`, interpolation tag `0`, and truncated data.

### Recommendation
Validate `t`, `n`, and `i` with `ThresholdParams::new` immediately after reading them, before performing any allocation. Additionally, avoid `Vec::with_capacity(n)` based solely on serialized input; incrementally collect elements with a protocol-defined maximum, or bound `n` against a caller-supplied expected participant count before allocation.

### Proof of Concept
```rust
use frost::curve::{Ciphersuite, Secp256k1};
use frost::ThresholdKeys;

fn malformed_threshold_keys() -> Vec<u8> {
    let mut bytes = Vec::new();

    // Expected ciphersuite identifier.
    bytes.extend_from_slice(
        &u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes()
    );
    bytes.extend_from_slice(Secp256k1::ID);

    // t = 1, n = 65535, i = 1.
    bytes.extend_from_slice(&1u16.to_le_bytes());
    bytes.extend_from_slice(&u16::MAX.to_le_bytes());
    bytes.extend_from_slice(&1u16.to_le_bytes());

    // Interpolation::Constant. No coefficient data follows.
    bytes.push(0);

    bytes
}

// Allocates capacity for 65,535 scalars, then fails while reading the first one.
let mut input = malformed_threshold_keys().as_slice();
let result = ThresholdKeys::<Secp256k1>::read(&mut input);
assert!(result.is_err());
```

The vulnerable ordering is the allocation at `crypto/dkg/src/lib.rs:607-613`, which occurs before parameter validation at `crypto/dkg/src/lib.rs:625-630`.
