## Title
Distribution precompile's `rewards()` accepts positive msg.value without validation, stranding wei sent by the caller - (File: precompiles/distribution/distribution.go)

### Summary
The Notional finding describes swap adapters that assume `msgValue == 0` but never assert it, so a caller-supplied positive value silently produces unexpected/unsafe behavior. The Sei distribution precompile exhibits the same bug class: every other view/transaction method on the precompile validates that `value` is zero (directly via `pcommon.ValidateNonPayable` or through `p.validateInput`), but the `rewards()` method is the sole exception that skips this check entirely.

### Finding Description
`PrecompileExecutor.Execute` dispatches to `p.rewards(ctx, method, args)` for `RewardsMethod` without passing `value` and without any `pcommon.ValidateNonPayable(value)` guard: [1](#0-0) 

Contrast this with every sibling view method (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`), which all route through `p.validateInput(value, args, N)`: [2](#0-1) 

`validateInput` calls `pcommon.ValidateNonPayable`, which reverts if `value` is non-zero: [3](#0-2) 

`rewards()` itself never inspects `value` at all — it only unpacks `args[0]` and queries `DelegationTotalRewards`: [4](#0-3) 

This is a known, deliberate quirk documented in the integration test suite: "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)": [5](#0-4) 

Because the distribution precompile address (`0x...1007`) is **not** in the `payablePrecompiles` allow-list used to suppress EVM transfer semantics for payable precompiles (only `bank`, `staking`, `gov`, `wasmd` are listed): [6](#0-5) 

...a plain `CALL` with non-zero `value` to `rewards()` still causes the EVM/StateDB to move usei/wei balance from the caller to the precompile's module account as part of standard `CALL` value-transfer semantics before/around precompile execution, exactly like any other EVM contract call. Since `rewards()` never checks or refunds that value (unlike `delegate()` in the staking precompile, which explicitly requires and consumes `value`, or the wasmd/bank precompiles, which call `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` to refund/route the value), the caller's usei/wei is transferred into the distribution precompile address with no code path that returns or accounts for it.

### Impact Explanation
A user (or, more likely, a contract/dApp integrator who mistakenly attaches value to a `rewards()` call, or a malicious frontend tricking a user's wallet into doing so) permanently loses the sent funds: they are debited from the caller and credited to the non-payable precompile's associated account with no withdrawal mechanism, since no logic in `rewards()` (or elsewhere) ever moves funds out of that address in response to this call. This is a fund-loss / freezing bug matching the "Accept only concrete fund loss or permanent freezing" bar. The blast radius is bounded to whatever value a caller attaches to this specific call, but it is directly triggerable by any public RPC client or contract with zero privilege.

### Likelihood Explanation
Reachable by any EVM transaction sender or contract making a direct `CALL` to precompile address `0x0000000000000000000000000000000000001007` with method `rewards(address)` and non-zero `value` — no special permissions, associations, or preconditions beyond calling the precompile (the delegator address argument doesn't even need to be the caller). The comment in the test suite confirms the maintainers are aware this specific method behaves differently from all its siblings, indicating it was an oversight (missing `ValidateNonPayable`) rather than an intentional payable design (since it isn't in the `payablePrecompiles` list and its output/semantics never handle a payment).

### Recommendation
Add `if err := pcommon.ValidateNonPayable(value); err != nil { return nil, 0, err }` to the `rewards()` case in `Execute` (or inside `p.rewards`), matching every other view method on this precompile, so that a value-bearing call to `rewards()` reverts instead of silently stranding funds.

### Proof of Concept
1. Associate an EVM address with a Sei account and delegate to a validator so it accrues rewards.
2. From that EVM account, issue a raw `CALL` (e.g., via `eth_sendTransaction` or a Solidity `.call{value: X}(...)`) directly to `0x0000000000000000000000000000000000001007` with calldata = `rewards(address)` selector + the delegator's EVM address, and `value = X` usei/wei.
3. Observe the transaction succeeds and returns the rewards data as normal (no revert), confirming `ValidateNonPayable` was never invoked.
4. Query the caller's balance before/after: it is debited by `X`, while the precompile's associated Sei account balance is credited by `X`, with no subsequent code path that ever returns that amount to the caller — the funds are stranded, matching exactly the "unexpected behavior when msgValue is not zero" pattern in the referenced report.

Note: I was unable to fully trace the exact low-level EVM/StateDB value-transfer call path (i.e., the specific `Call`/`Transfer` implementation in the customized `vm.EVM`/StateDB) to verify byte-for-byte whether value transfer happens unconditionally for all precompiles or is gated somewhere else outside `IsPayablePrecompile`; this would benefit from a full Devin session with repository access to trace `x/evm`'s EVM interpreter modifications end-to-end.

```go
func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
```
