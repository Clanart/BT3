### Title
Self-destructing a native ERC20 contract permanently freezes the coin-side value of its token pair - ([File: x/erc20/keeper/msg_server.go])

### Summary
`ConvertERC20` and `ConvertCoin` treat "contract has no code hash" (i.e., self-destructed) as sufficient reason to unilaterally delete the entire `TokenPair` record — including its ERC20↔denom mappings and allowances — with no check for outstanding native-coin circulation or escrowed ERC20 balance tied to that pair.

### Finding Description
In `x/erc20/keeper/msg_server.go`, both `ConvertERC20` and `ConvertCoin` perform the same guard before executing a conversion: [1](#0-0) [2](#0-1) 

If the ERC20 contract account is missing or has an empty code hash, the keeper immediately calls `DeleteTokenPair`, which erases the `ERC20Map`, `DenomMap`, and any stored `Allowance`s for that pair: [3](#0-2) 

This is functionally identical to the Nexus `_uninstallValidator` bug: a single, unprivileged action removes the last remaining "authorization/mapping" primitive (here, the `TokenPair`) with no fallback, leaving dependent state permanently unusable. For a native ERC20 pair (`OWNER_EXTERNAL`), the contract is deployed and controlled by an ordinary user, who can build in a `selfdestruct` path. Self-destructing the contract wipes its code and storage (including the module's escrowed ERC20 balance) via `DeleteAccount`: [4](#0-3) 

Once the pair is deleted:
- Any native bank coins of that pair's denom already minted and circulating (via prior `ConvertERC20` calls, see `convertERC20IntoCoinsForNativeToken`) remain spendable as bank coins, but the corresponding ERC20-side value backing them is destroyed and the denom→ERC20 mapping is gone.
- Any coin holder who calls `ConvertCoin` to redeem their native coin balance back into ERC20 tokens will fail permanently: the pair lookup (`GetTokenPairID`/`GetTokenPair`, used before `MintingEnabled` returns a pair) will never resolve again for that denom, since the denom is deterministically derived from the now-destroyed contract's address (`types.CreateDenom(strContract)`), and a new contract cannot realistically be deployed at the same address to "restore" the mapping.
- There is no governance or admin recovery path in the codebase to re-link the orphaned denom to a new ERC20 contract or to unwind the escrow.

This means an ordinary, unprivileged token-pair owner can unilaterally and permanently strand the ERC20-side value for every other holder of that native coin denom — not just their own — by self-destructing their own registered contract at any time after other users have converted into (or received via transfer) that coin denom.

### Impact Explanation
This matches the "Critical permanent freezing, locking ... of user funds ... or token-pair-backed balances" allowed-impact category. The affected value is not limited to the attacker: any account holding the affected native-coin denom (received via bank transfer from someone who legitimately converted ERC20→coin) loses the ability to ever convert back to the ERC20 representation, and the ERC20 tokens escrowed in the module account backing outstanding coin supply become permanently unreachable/uncollateralized. This is an irreversible accounting/redeemability corruption of the token-pair's backing.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: it requires the registrant of the token pair to deploy an ERC20 contract containing a reachable `selfdestruct`. Since `x/erc20` registration for `OWNER_EXTERNAL` pairs allows arbitrary user-supplied bytecode (unlike `OWNER_MODULE` pairs, which use the fixed bundled contract without a selfdestruct path), this is achievable by any user who registers their own token. Full state-clearing self-destruct is also constrained by EIP-6780 (only fully destructive within the same transaction as contract creation), which somewhat narrows — but does not eliminate — the practical attack window, since a wrapper/factory contract can perform creation and self-destruction within a single transaction. I could not fully verify within the available index whether `MsgRegisterERC20` permits registering arbitrary externally-owned contracts without additional governance gating (the exact `RegisterERC20` msg-server logic and any minimum-liquidity/verification requirements were not fully retrievable from the index); this affects the precise bar for exploitability and should be manually confirmed by an engineer with full repository access.

### Recommendation
Before calling `DeleteTokenPair` on selfdestruct detection, the keeper should:
- Verify there is no outstanding native-coin supply issued for that denom (e.g., check `bankKeeper.GetSupply(ctx, pair.Denom)` is zero) before deleting the mapping, or
- Instead of deleting the pair, mark it permanently disabled (`Enabled = false`) while preserving the denom→ID mapping, and provide a governance-gated path to re-link the denom to a replacement ERC20 contract or to trigger a supply-matching burn/redemption process for remaining coin holders, or
- Disallow self-destructible bytecode for `OWNER_EXTERNAL` registrations, or require a bytecode/proxy-immutability check at `RegisterERC20` time.

### Proof of Concept
Not independently executable within the current investigation; the flow is inferable from the code but I was unable to confirm the exact preconditions of `MsgRegisterERC20` (governance vs. permissionless) within the indexed context. Conceptual PoC:
1. User deploys a custom ERC20 contract with a `selfdestruct` function callable by the deployer, and registers it as a native ERC20 token pair (`OWNER_EXTERNAL`).
2. User mints tokens to themselves and calls `MsgConvertERC20` to escrow tokens into the erc20 module account and mint native coin to their own account.
3. User transfers a portion of the minted native coin to other accounts (now circulating value backed by escrow).
4. User calls `selfdestruct` on their contract (within the same tx as its creation to satisfy EIP-6780, e.g. via a factory contract).
5. Any subsequent `MsgConvertERC20`/`MsgConvertCoin` involving that pair triggers `DeleteTokenPair`, permanently removing the mapping.
6. All other holders of the coin denom can never redeem it back to ERC20; the escrowed ERC20 balance backing their coins is unreachable.

// DeleteTokenPair removes a token pair.
func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
}

// DeleteAccount handles contract's suicide call:
// - clear balance
// - remove code
// - remove states
// - remove the code hash
// - remove auth account
func (k *Keeper) DeleteAccount(ctx sdk.Context, addr common.Address) error {
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	acct := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	if acct == nil {
		return nil
	}

	// NOTE: only Ethereum contracts can be self-destructed
	if !k.IsContract(ctx, addr) {
		return errors.New("only smart contracts can be self-destructed")
	}

	// set account to a base account to set the whole balance as spendable
	baseAccount := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	k.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(cosmosAddr, baseAccount.GetPubKey(), baseAccount.GetAccountNumber(), baseAccount.GetSequence()))

	// clear balance
	if err := k.SetBalance(ctx, addr, new(uint256.Int)); err != nil {
		return err
	}

	var keys []common.Hash

	// clear storage
	k.ForEachStorage(ctx, addr, func(key, _ common.Hash) bool {
		keys = append(keys, key)
		return true
	})

	for _, key := range keys {
		k.DeleteState(ctx, addr, key)
	}

	// clear code hash
	k.DeleteCodeHash(ctx, addr)

	// remove auth account
	k.accountKeeper.RemoveAccount(ctx, acct)

	k.Logger(ctx).Debug(
		"account suicided",
		"ethereum-address", addr.Hex(),
		"cosmos-address", cosmosAddr.String(),
	)

	return nil
}
