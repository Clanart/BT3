### Title
Quadratic deserialization cost in `ThresholdKeys::read`/`ThresholdKeys::new` via attacker-controlled threshold `t` (unbounded Lagrange interpolation and per-participant group scalar multiplication) - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts `t` and `n` as attacker-controlled `u16`s (up to 65,535) from untrusted bytes, then calls `ThresholdKeys::new`, which unconditionally computes the group key as a sum over `t` participants where each term invokes `Interpolation::interpolation_factor` — an O(t) Lagrange loop including a field inversion — plus a group scalar multiplication. The result is O(t²) field operations and O(t) elliptic-curve scalar multiplications per deserialized blob: a ~2 MB input forces ~4.3 × 10⁹ field multiplications, 65,535 field inversions, and 65,535 scalar multiplications, with no comparison/computation budget and no cap on `t`/`n`. This is the same bug class as GHSA-fc86-6rv6-2jpm (CWE-407, unbounded O(n²) work from a small crafted input) mapped onto Serai's threshold-key deserialization path, which the engagement rules explicitly expose as a reachable surface (`ThresholdKeys::read`).

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, and `i` directly from the reader with no upper bound beyond `u16` range and the `t <= n` check in `ThresholdParams::new` (crypto/dkg/src/lib.rs:591-602, 166-179). It then reads `n` verification-share points and calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:620-631). Inside `new`, the group key is computed as:

```rust

let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

For `Interpolation::Lagrange` (byte value `1` at line 614), each `interpolation_factor` call iterates all `t` included participants performing field multiplications and one `invert()` (crypto/dkg/src/lib.rs:229-247). Total cost: `t` × `t` field multiplications + `t` inversions + `t` group scalar multiplications. With `t = n = 65,535` — which only requires the reader to supply 65,535 encoded points (~2 MB, and compresses extremely well since points may repeat; `read` does not check for duplicate or distinct shares before the expensive `new` call) — the deserialization alone burns ~4.3 × 10⁹ field multiplications plus ~65k inversions (~256 field muls each) plus 65,535 variable-base scalar multiplications. The identical quadratic pattern recurs in `ThresholdKeys::view`, which recomputes `interpolation_factor` for every included signer (O(|included|²), crypto/dkg/src/lib.rs:500-507), and in `ThresholdView::interpolation_factor` over a linear `included.contains` scan (crypto/dkg/src/lib.rs:657-662). There is no counter, budget, or early-exit analogous to the missing "comparison budget" in the reference advisory.

### Impact Explanation
An unprivileged party that can cause a Serai component to deserialize `ThresholdKeys` bytes (the rules explicitly allow `ThresholdKeys::read` as an attack surface) can pin a CPU core for tens of seconds to minutes per ~2 MB request, with zero cryptographic validity required — the cost is incurred before any signature or share check. Because the input is highly repetitive (the same point encoding repeated), it also compresses trivially, bypassing body-size limits exactly as in the referenced advisory. Repeated or parallel requests exhaust a worker pool. Additionally, the quadratic term is spent on *scalar field* work proportional to t², so even a modest `t` of a few thousand (input of a few hundred KB) produces quadratic degradation. This maps the CWE-407 "quadratic validation cost with no budget" class onto a real, reachable Serai code path.

### Likelihood Explanation
Likelihood depends on whether any deployed flow feeds untrusted bytes to `ThresholdKeys::read`/`serialize` (e.g., key material recovery, message-carried keys, or reshare data). The engagement scope explicitly lists `ThresholdKeys::read` among the reachable untrusted-input sinks, and the function performs no sanity bound on `t`/`n` before the expensive computation — `ThresholdParams::new` only enforces `t <= n <= 65535`. The `Lagrange` variant requires no per-participant data beyond the `n` points already read, so crafting the input is trivial (a 6-byte header + interpolation byte + one scalar + `n` repeated point encodings). Severity: Medium–High DoS (availability only; no secret leakage or forgery), matching the reference advisory's availability impact.

### Recommendation
- Cap `t`/`n` to a protocol-realistic bound (e.g., the maximum validator-set size actually supported) inside `ThresholdParams::new` or at the top of `ThresholdKeys::read` before `ThresholdKeys::new` is invoked — analogous to the advisory's "cap the flattened set" option.
- Compute the group key via a linear-time evaluation (e.g., precompute Lagrange denominators once, or use prefix/suffix products so all `t` coefficients cost O(t) total rather than O(t²)).
- Add a computation budget shared across `new`/`view`/`interpolation_factor` (analogous to the advisory's comparison-budget option), failing deserialization after a bounded number of field/group operations.
- Defer the group-key computation to first use (`group_key()`) so malformed-but-never-used keys do not trigger the quadratic path.

// Layout per ThresholdKeys::write (crypto/dkg/src/lib.rs:538-561):
//   u32 id_len || C::ID || u16 t || u16 n || u16 i || u8 interpolation

fn malicious_blob<C: Ciphersuite>() -> Vec<u8> {
    let t: u16 = u16::MAX;          // 65,535
    let n: u16 = u16::MAX;
    let mut buf = vec![];
    buf.extend(&(C::ID.len() as u32).to_le_bytes());
    buf.extend(C::ID);
    buf.extend(&t.to_le_bytes());
    buf.extend(&n.to_le_bytes());
    buf.extend(&1u16.to_le_bytes());          // participant i = 1
    buf.push(1);                              // Interpolation::Lagrange
    buf.extend(C::F::ZERO.to_repr().as_ref()); // secret_share (any canonical scalar)
    let point = C::G::generator().to_bytes();
    for _ in 0 .. n {
        buf.extend(point.as_ref());           // same point repeated — highly compressible
    }
    buf                                       // ~2.1 MB raw, a few KB gzipped
}

// ThresholdKeys::new -> t interpolation_factor calls, each O(t):

// Estimated cost: tens of seconds of CPU per request, scaling as O(t^2).
// Doubling t quadruples the cost — the same O(n^2) signature as GHSA-fc86-6rv6-2jpm.
let _ = ThresholdKeys::<Ed25519>::read(&mut malicious_blob::<Ed25519>().as_slice());

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
  }
