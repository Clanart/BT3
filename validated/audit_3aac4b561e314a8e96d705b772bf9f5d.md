### Title
`restrict-assets?`/`as-contract?` FT/NFT allowance checks conflate the literal asset name `"*"` with a wildcard sentinel, letting a single-asset allowance authorize movement of every asset in a contract - (File: clarity/src/vm/functions/post_conditions.rs)

### Summary
`check_allowances` implements the fungible- and non-fungible-token allowance matching for `restrict-assets?`/`as-contract?` by re-using the literal string `"*"` as an internal wildcard key, but `"*"` is also a syntactically valid Clarity asset name that a contract author can legitimately use with `with-ft`/`with-nft`. Because there is no separate representation for "wildcard" versus "asset literally named `*`", any `(with-ft <contract> "*" <amount>)` allowance is indistinguishable from a wildcard allowance and is applied to every fungible token defined in that contract, each up to `<amount>`, instead of being scoped to a single named asset.

### Finding Description
`eval_allowance` builds an `Allowance::Ft`/`Allowance::Nft` from whatever `ClarityName` string is passed to `with-ft`/`with-nft`, with no restriction against the literal value `"*"`: [1](#0-0) 

`check_allowances` then indexes allowances by `AssetIdentifier` (contract + asset name) in `ft_allowances`/`nft_allowances`, and when checking an actual asset movement it looks up both the exact `AssetIdentifier` and a synthetic identifier constructed with `asset_name: ClarityName::from_literal("*")` to merge in "wildcard" entries: [2](#0-1) [3](#0-2) 

Because the allowance map is keyed purely by `AssetIdentifier` equality, an allowance created via `(with-ft 'SP...my-contract "*" u100)` — which a contract author would reasonably read as "permit moving up to 100 units of the token literally named `*`" — is stored under the exact same key the wildcard-lookup code searches for. It is therefore merged into every other asset's `merged` allowance list in that contract, and each asset is checked independently (`for (index, allowance) in merged { if *amount_moved > allowance { ... } }`), so a limit intended for one named token ends up separately permitting up to `amount` for every fungible (or non-fungible ID set) asset defined in that contract, with no aggregate cap across them.

This mirrors the JBToken class of bug: a restriction meant to bound a single, specific asset/authority is silently broadened because the code re-uses an application-level value (`"*"`) as a privileged sentinel with no separate namespace, letting `restrict-assets?`/`as-contract?` protected code paths move far more value than the post-condition author authorized.

### Impact Explanation
This breaks the core equality that `restrict-assets?`/`as-contract?` is supposed to enforce: "assets moved within the protected scope must not exceed the declared allowances." A contract that computes an asset name dynamically (e.g., derived from user input, or simply named `"*"` as a legitimate token symbol) and passes it to `with-ft`/`with-nft` would unintentionally authorize movement of every other fungible/non-fungible asset defined in the same contract up to the same bound — an asset moving past its post-conditions. Per the rules, this is classified High/Critical territory ("an asset moving past its post-conditions").

### Likelihood Explanation
Requires a contract using `restrict-assets?`/`as-contract?` with a `with-ft`/`with-nft` allowance whose asset-name argument evaluates to the literal string `"*"` (a legal `ClarityName`, since `*` is a valid standalone Clarity identifier used for operators). This could occur intentionally by an attacker-authored contract that defines a token literally named `*` to smuggle a wildcard allowance, or unintentionally when the asset name is computed/passed through from user-controlled input. It does not require any signer/miner privilege — it is purely a Clarity-VM-level authorization logic bug reachable by any contract-calling transaction.

### Recommendation
Represent "wildcard" as a distinct enum variant (e.g., `Allowance::FtWildcard { contract, amount }`) rather than overloading `ClarityName::from_literal("*")` as a sentinel key that can collide with a real, user-suppliable asset name. Alternatively, reject `"*"` as an asset name in `eval_allowance` for `with-ft`/`with-nft`, or require an explicit wildcard syntax that cannot be produced from a normal asset-name string.

### Proof of Concept
1. Deploy a SIP-010-like contract `token-hub` in the same contract that defines two fungible tokens: one named `*` (a valid `ClarityName`) and one named `real-token`.
2. From within a `restrict-assets?`/`as-contract?` block, declare `(with-ft 'SP...token-hub "*" u100)` intending to allow moving up to 100 units of the token named `*`.
3. Inside the protected body, transfer 100 units of `real-token` (a completely different asset never explicitly allowed).
4. `check_allowances` builds the wildcard lookup key `AssetIdentifier { contract_identifier: token-hub, asset_name: "*" }`, finds the allowance from step 2 in `ft_allowances`, and merges it into `real-token`'s check — the transfer is incorrectly permitted even though only the `*`-named token was supposed to be authorized.
