### Title
Vote-locked MGP becomes permanently unwithdrawable when a pool is deactivated, because `WombatBribeManager.unvote()` only works on active pools - ([File: VLMGP.sol, wombat/WombatBribeManager.sol])

### Summary
`VLMGP.startUnlock()` refuses to start a cooldown for any amount that would push a user's locked balance below `WombatBribeManager.userTotalVotedInVlmgp(msg.sender)`. The only way to reduce that number is `vote()` or `unvote()`, but both of these functions revert with `PoolNotActive` unless `pool.isActive == true`. Once a pool a user voted for is deactivated, the user's committed vote to that pool can never be reduced or removed, permanently capping the amount of MGP they can ever put through `startUnlock()`/`unlock()` and freezing the difference forever.

### Finding Description

i.e. a user cannot cool down MGP that is still "backing" an outstanding vote tracked in `userTotalVotedInVlmgp`.

The only two functions that can change `userTotalVotedInVlmgp[msg.sender]` are `vote()` and `unvote()` in `WombatBribeManager.sol`. Both gate on pool activity: [2](#0-1) [3](#0-2) 

`unvote()`'s own doc comment states its purpose is the opposite of what the code does: *"Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing"* — yet the implemented check `if(!pool.isActive) revert PoolNotActive();` means `unvote()` succeeds only while the pool is still active, and reverts once it is deactivated. `vote()` has the identical restriction (`if (!pool.isActive) revert PoolNotActive();`), so it also cannot be used to zero out a stale vote against a deactivated pool.

Consequence: once a pool that a user voted for is deactivated, that user's `userVotedForPoolInVlmgp[msg.sender][pool]` / `userTotalVotedInVlmgp[msg.sender]` entry can never be reduced through any public function. Any subsequent `startUnlock()` call that would drop the user's `getUserTotalLocked` below this stale voted amount reverts with `NotEnoughLockedMPG` forever, since the vote can never be reconciled down. The user's MGP corresponding to that voted amount is permanently unreachable — it can never be moved into a cooldown slot nor ever be withdrawn via `unlock()`/`forceUnLock()`.

The additional `maxSlot` precondition raised in the question (attacker already occupies all unlock slots, forcing `getNextAvailableUnlockSlot` to reuse a zeroed slot) does not change or worsen this specific root cause — it is orthogonal slot-reuse behavior in `getNextAvailableUnlockSlot()` [4](#0-3)  and does not by itself desynchronize `totalPenalty`/MGP balance accounting; I did not find a `totalPenalty` state variable in `VLMGP.sol` in the indexed contents, so that specific accounting-equality assertion in the question could not be verified against the actual code.

### Impact Explanation
This is a genuine permanent freezing of user funds: the affected user's MGP tied to the deactivated pool's vote can never be unlocked through `startUnlock()`/`unlock()`/`forceUnLock()`, and no other public path exists to reduce `userTotalVotedInVlmgp`. This matches "Critical - Permanent freezing of funds" for the affected user's principal.

### Likelihood Explanation
The trigger precondition — a pool becoming inactive after a user has voted for it — is a normal, expected lifecycle event explicitly anticipated by the `unvote()` function's own doc comment (pool removal / rewarder change). It does not require any malicious admin behavior, only ordinary pool-list maintenance, which is a realistic and likely-to-occur event over the protocol's lifetime. Any user who voted for a pool that is later deactivated is affected with no further action needed on their part; the freeze is a direct consequence of the inverted `isActive` condition in `unvote()`/`vote()`, not of the `maxSlot` slot-reuse mechanic.

### Recommendation
Fix the boolean logic in `unvote()` (and add symmetric handling for `vote()`) so that unvoting from an *inactive* pool is exactly what is permitted, e.g. change the guard to allow unvote regardless of `isActive`, or explicitly allow it only when `!pool.isActive`, matching the documented intent. Ensure `vote()` still requires `isActive` for adding new votes, but `unvote()` (whose entire purpose per its comment is to release stale votes) must not be blocked by pool deactivation. Additionally, provide an owner/permissionless "force clear vote" path for pools that are deleted/deactivated so `userTotalVotedInVlmgp` can always be reconciled to zero for such pools.

### Proof of Concept
Hardhat plan:
1. Deploy `VLMGP`, `WombatBribeManager`, mock `MasterMagpie`, mock pool/rewarder.
2. User locks MGP via `VLMGP.lock()`, then calls `WombatBribeManager.vote()` allocating full locked balance to `poolA`.
3. Owner deactivates `poolA` (sets `isActive = false`) — a normal admin action.
4. User calls `WombatBribeManager.unvote(poolA)` — assert it reverts with `PoolNotActive`.
5. User calls `WombatBribeManager.vote([poolA], [negativeDelta])` — assert it also reverts with `PoolNotActive`.
6. User calls `VLMGP.startUnlock(fullLockedAmount)` — assert it reverts with `NotEnoughLockedMPG`, for any `_amountToCoolDown` that would drop `getUserTotalLocked` below `userTotalVotedInVlmgp`.
7. Assert there is no other public function that reduces `userTotalVotedInVlmgp[msg.sender]` for `poolA`, confirming the user's MGP is permanently stuck.

        Pool storage pool = poolInfos[_lp];
        uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
        if(!pool.isActive)
            revert PoolNotActive();
        
        pool.totalVoteInVlmgp -= uint256(currentVote);
        userTotalVotedInVlmgp[msg.sender] -= uint256(currentVote);
        userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] = 0;
