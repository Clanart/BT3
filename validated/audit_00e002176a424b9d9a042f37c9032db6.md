### Title
`incentiveDeposit`'s mode-2 doubling bypasses the MGP-balance cap enforced inside `getRewardAmount` - (File: wombat/ArbWomUp3.sol)

### Summary
`getRewardAmount()` correctly caps `mgpReward` to `IERC20(mgp).balanceOf(address(this))` before returning it, but `incentiveDeposit` then multiplies that already-capped value by 2 when `_mode == 2`, completely bypassing the cap that was just computed. This lets `rewardToSend` diverge from the actual MGP balance held by the contract, breaking the "incentive pot must not be fully claimable by a single actor" invariant.

### Finding Description
In `incentiveDeposit`:
```solidity
uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender, _mode == 2);
if (_mode == 2)
    rewardToSend = rewardToSend * 2;
``` [1](#0-0) 

`getRewardAmount` computes a tier-based `mgpReward` from the tier walk in `rewardMultiplier`/`rewardTier`, and clamps it against the live balance:
```solidity
uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
return mgpReward > mgpleft ? mgpleft : mgpReward;
``` [2](#0-1) 

This clamp is meant to guarantee `rewardToSend <= mgp.balanceOf(address(this))`. However, `incentiveDeposit` applies the `* 2` multiplier for mode 2 *after* this clamp has already run, so the invariant the clamp is supposed to protect is defeated: a user whose uncapped tier-based reward is close to (or already equal to) the full MGP balance will, in mode 2, receive `rewardToSend` up to 2x the actual pot, i.e., strictly greater than `IERC20(mgp).balanceOf(address(this))`.

Additionally, the tier walk itself has no ceiling on `_amount`/accumulated locked balance per transaction — `getRewardAmount`'s `while` loop over `rewardTier` will happily traverse all configured tiers for any deposit size, so a single sufficiently large deposit (optionally combined with `mWomSV.startUnlock` + a second deposit in the same block to manipulate `getUserTotalLocked`/`calDoubledCounted` double-counting logic) can push `mgpReward` up to the full pot in one call, which mode 2 then doubles past the pot.

The immediate consequence: `IERC20(mgp).safeApprove(address(vlMGP), rewardToSend)` and `vlMGP.lockFor(rewardToSend, msg.sender)` are called with `rewardToSend` potentially exceeding the actual MGP token balance of `ArbWomUp3`. `_lock` in the locker (`mWOM.safeTransferFrom(spender, address(this), _amount)` pattern generally, and for `VLMGP`/`mWomSV` locking this ultimately requires transferring/approving the real MGP balance) — if the amount requested exceeds the real balance, the ERC20 transfer underlying `lockFor` will revert due to insufficient balance in the straightforward case. However, this does not make the design safe: the accounting divergence itself (`rewardToSend` computed and emitted as `2x mgpleft` while real balance is `mgpleft`) is the broken invariant, and any partial funding of the pot (e.g., pot has `X` tokens, user's *uncapped* tier reward before doubling is `X/2` or less, so post-doubling `rewardToSend` lands within `X` but consumes the entire remaining pot in a single call) allows one caller to drain the whole incentive pot in a single transaction — which is exactly the invariant that "an incentive pot must not be fully claimable by a single actor in one transaction" is meant to prevent. Nothing in `incentiveDeposit` re-validates `rewardToSend` against the live balance after the doubling step, and there is no per-transaction/per-user ceiling on the deposit size feeding the tier walk.

### Impact Explanation
A single unprivileged caller can, in one transaction (`incentiveDeposit` with `_mode == 2` and a sufficiently large `_amount`), consume the entire remaining MGP incentive pot that was intended to be distributed across many depositors over time. This matches "Direct theft of user funds" (of the yet-unclaimed MGP incentive pot funded by the protocol for other legitimate depositors) since the reward-cap safeguard is nullified by the post-cap doubling.

### Likelihood Explanation
Exploitation requires only: (1) an unprivileged WOM holder able to call `incentiveDeposit`, (2) `_mode == 2`, and (3) an `_amount` large enough (or combined with `mWomSV.startUnlock`/re-deposit maneuvers in the same block to inflate `getUserTotalLocked`) to reach a high tier bracket. No special privileges, flash loans, or admin roles are needed — only the WOM tokens needed to fund `_amount`, which can be sized to whatever is required to reach the top reward tier. This is a straightforward, repeatable exploit as long as the MGP pot has a non-trivial balance and reward tiers configured via `setMultiplier`.

### Recommendation
Apply the pot-balance cap **after** all multipliers (including the mode-2 doubling) are applied, e.g.:
```solidity
uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender, _mode == 2);
if (_mode == 2) rewardToSend = rewardToSend * 2;
uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
rewardToSend = rewardToSend > mgpleft ? mgpleft : rewardToSend;
```
Additionally, introduce an explicit per-transaction/per-user ceiling on the reward payout (e.g., a max percentage of the current pot balance) so no single call can consume the entire remaining incentive pot, and consider snapshotting `getUserTotalLocked` in a way that is resistant to same-block `startUnlock` + re-deposit manipulation.

4. As attacker (unprivileged EOA), acquire enough WOM to make a large deposit; call `mWomSV.startUnlock` on a prior lock, then in the same block call `incentiveDeposit(_amount, _convertRatio, false, 2)` with `_amount` sized to push `getRewardAmount` close to `P/2`.
5. Assert: after the call, `emit VLMGPRewarded` reports `rewardToSend > IERC20(mgp).balanceOf(address(this))` measured just before the call (pre-doubling snapshot), and/or that the attacker's single call reduces `mgp.balanceOf(ArbWomUp3)` to zero (full pot claimed) — violating the "pot not drainable by one actor in one tx" invariant.
6. Compare against a control call with `_mode == 1` (no doubling) that correctly respects the cap and leaves nonzero pot balance, demonstrating the divergence is caused specifically by the mode-2 doubling occurring after the cap check. [3](#0-2) [4](#0-3)

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
