### Title
Out-of-range `Participant` in a PedPoP blame accusation panics via unchecked `HashMap` indexing — ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
Analogous to CVE-2024-8445 (server crash while processing malformed modification input), the PedPoP DKG's blame-resolution path trusts the `sender`/`recipient` `Participant` indexes carried in a remote accusation and indexes `self.commitments` with them via `HashMap`'s `Index` impl. Any nonzero `u16` is a valid `Participant`, but the commitments map only contains `1 ..= n`. A malformed accusation naming a participant index `> n` causes an unconditional panic, crashing the node processing blame.

### Finding Description
`Participant` is defined as any non-zero `u16`, and `Participant::new` only rejects `0`. It imposes no upper bound relative to the DKG's `n`. [1](#0-0) 

`AdditionalBlameMachine::new` builds `commitments` strictly for `1 ..= n`: [2](#0-1) 

`BlameMachine::blame` / `AdditionalBlameMachine::blame` pass the accusation's `sender` and `recipient` straight into `blame_internal` with no bounds check against `params.n` or map membership: [3](#0-2) 

`blame_internal` then indexes the map with the attacker-controlled `sender`: [4](#0-3) 

`self.commitments[&sender]` (line 599) uses `HashMap`'s `Index` impl, which panics on a missing key. The `EncryptedMessage<C, SecretShare<C::F>>` is well-formed (`EncryptedMessage::read` and `SecretShare::read` accept any bytes of the right length — `SecretShare::read` doesn't even require a canonical scalar), and `decrypt_with_proof` returns a structured `Err` on bad signatures/proofs, so execution reliably reaches line 599 whenever the sender index is out of range. The same unchecked pattern exists in `KeyMachine::calculate_share` (`self.commitments[&l]` at line 490), though there `validate_map` bounds `l` to `1 ..= n`, making the blame path the reachable one. Note `AdditionalBlameMachine` is explicitly designed to be usable by a non-participant third party evaluating blame, widening the reachable callers.

### Impact Explanation
An unprivileged participant (or any party able to submit a blame accusation naming an accused sender) can crash every node that processes the accusation, simply by claiming an accusation against `Participant(n + 1)` or any index up to `u16::MAX`. This aborts DKG completion / blame adjudication and causes a denial of service identical in shape to the reference bug: malformed but parseable input reaching an unchecked index. In a validator set, simultaneous crashes during blame resolution can stall key generation or force consensus-level fault handling.

### Likelihood Explanation
Blame accusations are inherently adversary-influenced: they exist precisely because a party claims another party misbehaved, so the `(sender, recipient, msg, proof)` tuple originates from potentially malicious counterparties. No authentication or range validation on `sender`/`recipient` exists in `blame_internal`. Triggering requires only a well-formed `EncryptedMessage` and an out-of-range `Participant` — trivially craftable.

### Recommendation
Validate `sender` and `recipient` against the participant set (`1 ..= n`, and presence in `commitments`) at the top of `blame_internal` — or in `BlameMachine::blame`/`AdditionalBlameMachine::blame` — and return an error (e.g., `PedPoPError::DkgError(DkgError::InvalidParticipant { n, participant })`) rather than indexing. Use `HashMap::get` with explicit error handling instead of the panicking `Index` impl for any attacker-influenced key.

### Proof of Concept
```rust
// Assume a completed AdditionalBlameMachine for n = 2
let machine: AdditionalBlameMachine<Ed25519> =
  AdditionalBlameMachine::new(context, 2, commitment_msgs).unwrap();

// Craft a syntactically valid EncryptedMessage (any bytes of correct length
// deserialize; SecretShare::read does not even check canonicity)
let msg: EncryptedMessage<Ed25519, SecretShare<_>> =
  EncryptedMessage::read(&mut crafted_bytes.as_ref(), params).unwrap();

// Accuse a participant that does not exist (3 > n = 2)
let sender = Participant::new(3).unwrap();
let recipient = Participant::new(1).unwrap();

// Panics at crypto/dkg/pedpop/src/lib.rs:599:
// `self.commitments[&sender]` -> HashMap index panic (key not found)
machine.blame(sender, recipient, msg, None);
```

The panic occurs before any validity check on `sender`, so any `sender` in `(n, u16::MAX]` triggers it. `BlameMachine::blame` (consumed path after `calculate_share`) is affected identically since it shares `blame_internal`.
