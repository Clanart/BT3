### Title
Shared-token escrow over-release across multiple output pairs in `_fillSameChain` — ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntrinsicIntents._fillSameChain` computes the escrow amount to release for a completed output pair by reading the *entire current balance* of `_orders[commitment][token]` instead of the portion attributable to that specific output pair. Because `_orders` is keyed only by `(commitment, token address)` — not by output-pair index — an order whose `inputs[]` array contains the same token at two different indices lets a solver who completes one output pair drain escrow that was reserved to fund a different, still-unfilled output pair.

### Finding Description
`_orders` is declared as a flat mapping keyed by token address per commitment: [1](#0-0) 

In `_fillSameChain`, each output asset `i` is processed independently and pulls its proportional input release from `order.inputs[i]`: [2](#0-1) 

When the fill for pair `i` completes it (`amountFilled == totalRequired`), the code does **not** compute "the amount still owed for pair `i`" — it fetches whatever is currently sitting in `_orders[commitment][token]`, i.e., the aggregate escrow for that token across *all* input entries that share the same address, including any portion still backing another, unrelated output pair `j` that uses the same token but hasn't been filled yet.

`_withdraw` then unconditionally decrements this shared slot by the released amount: [3](#0-2) 

There is no per-index accounting (no `_orders[commitment][i]` or reservation ledger) to prevent one output pair's completion from consuming funds earmarked for a sibling pair that shares the same input token. Nothing in `placeOrder`/`_fillSameChain` rejects orders whose `inputs[]` contains duplicate token addresses across different indices, so an attacker (acting simply as a normal solver, no privileged role needed) can:

1. Wait for (or construct via a colluding "user" self-order, or simply exploit any legitimate order with duplicate-token inputs) an order with two output pairs `i` and `j` where `order.inputs[i].token == order.inputs[j].token`.
2. Fill output pair `i` completely first. `_fillSameChain` releases `_orders[commitment][token]`'s **full current balance** to this solver, even though part of that balance was meant to pay whoever fills pair `j`.
3. When a second solver later attempts to fill pair `j`, `_withdraw` reads `_orders[commitment][token]` and finds it depleted (`escrowed == 0`), reverting with `UnknownOrder` — permanently stalling that leg of the order even though the user's counterpart output for `j` may already be undeliverable, or, if the escrow decrement leaves a partial residue, pair `j`'s solver receives less than their fair proportional share while pair `i`'s solver was overpaid.

This is a direct functional analog to the H-2 rounding-invariant bug: a numeric value that is supposed to represent "the amount owed for a specific accounting unit" is instead computed against shared/aggregate state that does not correctly isolate that unit, causing an incorrect release of value to the wrong party.

### Impact Explanation
This falls squarely within the bounty's fund-loss / wrong-beneficiary-or-amount category: an unprivileged solver can capture escrowed funds intended to back a different, unfulfilled leg of the same order, at the direct expense of the user (whose collateral was escrowed to guarantee delivery of *both* output pairs) and of whichever solver attempts to fill the remaining leg (who is blocked by `UnknownOrder` or shorted funds). No malicious relayer, prover, or admin is required — a same-chain intent order with duplicate input token addresses across output pairs is sufficient, and `fillOrder` is a fully public entrypoint.

### Likelihood Explanation
Likelihood depends on whether real-world orders place the same input token behind two output pairs (e.g., a user pays 600 USDC + 400 USDC as two separate `inputs[]` entries funding two different desired outputs). Nothing in `placeOrder` validation rejects duplicate token addresses in `inputs[]`, and the intent-order schema (`TokenInfo[] inputs`, `TokenInfo[] outputs` indexed in parallel) does not require input tokens to be unique. A solver monitoring the order book can identify and exploit such orders opportunistically.

### Recommendation
Track escrow release per output-pair index rather than aggregated by token address — e.g., store `_orders[commitment][i]` (or `_orders[commitment][keccak256(abi.encode(token, i))]`) so that the amount released when pair `i` completes is bounded strictly by what was escrowed for that specific pair, independent of any other pair sharing the same token. Alternatively, reject `placeOrder` calls where `inputs[]` contains duplicate token addresses mapped to independently-fillable output pairs, or compute the "full remaining" release for a completed pair as `order.inputs[i].amount - alreadyReleasedForPair[i]` instead of reading the raw shared balance.

### Proof of Concept
1. User places a same-chain order with:
   - `inputs = [{USDC, 600}, {USDC, 400}]`
   - `output.assets = [{DAI, 600e18}, {WETH, 1e18}]`
   (both input entries use USDC; `_orders[commitment][USDC] = 1000`)
2. Solver A fully fills output pair 0 (600 DAI) in one call. `amountFilled == totalRequired` for pair 0 triggers:
   `escrowedAmount = _orders[commitment][USDC]` → returns **1000 USDC** (the full aggregate, not the 600 USDC that funded pair 0), which is transferred to Solver A via `_withdraw`.
3. `_orders[commitment][USDC]` is now `0`.
4. Solver B attempts to fill output pair 1 (1 WETH). The corresponding `_withdraw` call reads `_orders[commitment][USDC] == 0` and reverts with `UnknownOrder`, permanently blocking pair 1 while Solver A has already taken funds that should have covered it. [2](#0-1) [4](#0-3) [5](#0-4)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
