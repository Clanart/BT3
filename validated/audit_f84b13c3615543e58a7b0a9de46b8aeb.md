### Title
Disabling Git's built-in clone protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) reopens the CVE-2024-32002 recursive-clone RCE path - (File: `app/src/lib/git/clone.ts`)

### Summary
GitHub Desktop's `clone()` helper explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment for every `git clone --recursive` invocation, unconditionally disabling the safety checks that upstream Git introduced specifically to stop malicious repositories from executing code during a recursive clone.

### Finding Description
`clone()` builds the environment for the clone subprocess like this: [1](#0-0) 

The `env` merges `envForRemoteOperation(url)` with a hard-coded `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, and the command line always includes `--recursive`: [2](#0-1) 

`GIT_CLONE_PROTECTION_ACTIVE` is a real upstream Git environment variable that gates the hardening added to `git clone` to defend against maliciously crafted repositories (and their submodules) that exploit symlinked/embedded `.git` directories or case-insensitive filesystem tricks to write attacker-controlled files into a directory that later gets treated as `core.hooksPath`/`.git/hooks` for a submodule, so that ordinary post-checkout/post-init hook execution runs attacker code. When left enabled (the default), Git aborts the clone if it detects such a hazardous condition; setting it to `'false'` disables that check entirely, so Desktop chooses to run every clone with this safety net turned off.

This is compounded by the fact that Desktop treats the on-disk hooks directory as trusted input elsewhere in the code — `getRepoHooks()` resolves `core.hooksPath` (or the default `.git/hooks`) from the repository being operated on and later executes any recognized hook found there via the hooks-proxy trampoline: [3](#0-2) [4](#0-3) 

So the specific corrupted value is the resolved `hooksPath`/hooks directory contents of the *victim's working copy* after a `clone --recursive`: it can end up containing attacker-supplied executable "hook" files placed there via a submodule during the very clone operation whose only defense (`GIT_CLONE_PROTECTION_ACTIVE`) Desktop turns off.

### Impact Explanation
If exploited, an attacker who controls a repository (and its submodules) referenced by a URL the victim clones through Desktop — e.g. from a link, an organization's repo listing, or a forked/cloned dependency — can achieve arbitrary code execution on the victim's machine as soon as the clone (and its automatic recursive submodule checkout) completes, without any further user action such as opening the repo or running a build. This maps directly onto the report's underlying theme: a privileged/administrative safety knob (there, the fee-cap; here, Git's own clone-protection flag) is set to the least-safe value, silently removing the guard that would otherwise stop attacker-controlled input from causing loss/damage to an unsuspecting user.

### Likelihood Explanation
Likelihood is high in the sense that it requires no unusual user behavior: Desktop's standard "Clone repository" flow (and any deep-link/CLI `--cli-clone` clone flow) always calls this same `clone()` function with `--recursive` and the protection disabled, so any attacker-controlled repo URL that reaches the clone path is affected. The only prerequisite is that the running Git version implements the CVE-2024-32002 mitigation (i.e., a modern Git shipped/bundled with Desktop) — Desktop actively opts out of that mitigation rather than merely lacking it.

### Recommendation
Do not disable `GIT_CLONE_PROTECTION_ACTIVE`. Leave it unset (or explicitly `'true'`) so Git's built-in protections against symlinked/embedded `.git` directories and malicious submodule layouts remain active during `--recursive` clones. If the flag was disabled to work around a specific compatibility issue, gate the opt-out narrowly (e.g., only for verified-safe, first-party remotes) rather than globally for every clone of arbitrary, untrusted URLs, and add a regression test asserting the flag is never set to `'false'` for user-supplied clone URLs.

### Proof of Concept
1. Attacker creates a public repository `evil/repo` containing a `.gitmodules` file that references a submodule using a crafted path/URL designed to trigger the case-insensitive/symlinked `.git` hazard mitigated by Git's clone-protection checks (the same repository layout described in the upstream Git advisory for CVE-2024-32002, e.g. a submodule path that collides with `.git` on case-insensitive filesystems, combined with a hook file such as `post-checkout` placed to land in the resolved hooks directory).
2. Victim clones `https://github.com/evil/repo` using GitHub Desktop's normal "Clone a repository" UI (or via an `x-github-client://openRepo` deep link that leads to a clone).
3. Desktop calls `clone(url, path, options, ...)` in [5](#0-4)  which runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set, so Git's normal abort-on-hazard behavior does not trigger.
4. During the recursive submodule checkout, the attacker's crafted hook file lands in the resolved hooks directory and is executed as part of normal Git plumbing (or subsequently picked up by Desktop's own hook execution/interception path in `getRepoHooks()`/`withHooksEnv()`), resulting in code execution on the victim's machine with no explicit consent step beyond the initial clone.

  path: string,
  options: CloneOptions,

    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }
