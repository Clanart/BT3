### Title
PedPoP blame proofs reveal the ECDH shared key for messages whose proof-of-possession is invalid, letting a relayer decrypt a victim's secret share - (File: crypto/dkg/pedpop/src/encryption.rs + crypto/dkg/pedpop/src/lib.rs)

### Summary
The Vault advisory concerns an unauthenticated party reading protected metadata. The Serai analog: an unauthenticated/attacker-relayed `EncryptedMessage` causes an honest recipient to emit an `EncryptionKeyProof` (the ECDH shared point `b·K`) before the message's Schnorr proof-of-possession is verified, because the PoP is only queued into a batch verifier while the blame proof is computed unconditionally. The PoP in `pop_challenge` binds the `sender` index, so a relayed message's PoP is invalid — yet the recipient still produced and may publish the ECDH key that decrypts the relayed ciphertext, leaking the victim's secret share.

### Finding Description
In `Encryption::decrypt` (`crypto/dkg/pedpop/src/encryption.rs:469-500`), the per-message key's Schnorr PoP is *queued* via `msg.pop.batch_verify(...)`, and the ECDH shared key `key = ecdh(&self.enc_key, msg.key)` plus a DLEq proof is computed and returned immediately — before the batch is ever verified. In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:474-499`), this blame proof is stored in `blames` and attached to `PedPoPError::InvalidShare { blame: Some(...) }` whenever deserialization fails or when the batch verifier returns `BatchId::Share(l)`.

The `pop` challenge (`encryption.rs:302-324`) binds `sender`, `key`, `nonce`, and the ciphertext. Consequently, when Eve relays Alice's `EncryptedMessage` (copying `key`, `pop`, and ciphertext verbatim) as if it were Eve's own message to Bob:

- Bob's `decrypt` computes `key = enc_key_bob · msg.key_alice` and constructs a full `EncryptionKeyProof` for it.
- The share bytes deserialize fine (Alice's share is canonical), so the error isn't hit at `from_repr`.
- The batch contains two failing statements for Eve: `BatchId::Decryption(Eve)` (the PoP, which is bound to sender=Alice) and `BatchId::Share(Eve)` (Alice's share does not satisfy Eve's commitments). `verify_with_vartime_blame` blames whichever is found; when it returns `Share(Eve)`, Bob's error carries `blame: Some(proof)` revealing `b·K_alice`.

Anyone holding that proof (it is meant to be published for blame adjudication, and `AdditionalBlameMachine::new` at `lib.rs:649-662` explicitly lets *non-participants* verify blame with only the public commitment messages) can run the same `cipher(context, proof.key)` keystream over the ciphertext, recovering `f_alice(bob)` — Alice's polynomial evaluated at Bob. This is precisely the attack the comments at `encryption.rs:84-90` claim the PoP prevents ("they'd reveal bX, revealing Alice's message to Bob"), but the reveal happens *before* PoP verification completes, so the protection is void for relayed messages.

### Impact Explanation
An unauthenticated relayer (any party able to copy a broadcast/relayed ciphertext and deliver it to the victim — no valid PoP, no key knowledge required) can cause the victim to disclose the ECDH shared point that decrypts a targeted honest participant's `SecretShare`. This leaks one polynomial share `f_victim_sender(recipient)`, a component of the recipient's `ThresholdCore.secret_share` (`crypto/dkg/src/lib.rs:263`), breaking the DKG's confidentiality guarantee. Repeated across senders whose messages the attacker can relay, multiple terms of a victim's secret share are exposed. Severity: Medium (partial secret-share disclosure; requires active relaying into the DKG channel).

### Likelihood Explanation
Requires a malicious DKG participant (or an active MITM on the assumed-authenticated channel) who copies an honest sender's `EncryptedMessage` and delivers it as their own — fully within the untrusted-bytes threat model (`EncryptedMessage::read`, `calculate_share`). Success depends on `verify_with_vartime_blame` surfacing the `Share` failure rather than the `Decryption` failure; both fail for a relayed message, so exploitation is ordering-dependent but repeatable across sessions. No collusion needed.

### Recommendation
Do not construct or return the `EncryptionKeyProof` until the message's PoP has been verified. Concretely: in `Encryption::decrypt`, verify `msg.pop` synchronously (or in a separate earlier batch) before computing `ecdh`/`cipher`/`DLEqProof::prove`, and return the blame proof only for messages with a valid PoP. Alternatively, return the ECDH key only inside a blame-adjudication path that first re-verifies the PoP via `decrypt_with_proof`, and ensure `calculate_share` never emits a proof for a `BatchId::Decryption` failure or for shares whose PoP failed.

### Proof of Concept
```rust
// Participants: Alice (honest sender), Bob (honest recipient), Eve (relayer).
// 1. Alice runs KeyGenMachine::generate_coefficients and generate_secret_shares,
//    producing EncryptedMessage<C, SecretShare> addressed to Bob. The wire bytes
//    (msg.key = K_a, pop bound to sender=Alice, ciphertext = share f_a(Bob))
//    are observable on the channel.

// 2. Eve reads Alice's EncryptedMessage bytes and re-sends them as Eve's own
//    share message to Bob:
let forged: EncryptedMessage<C, SecretShare<C::F>> =
    EncryptedMessage::read(&mut alice_msg_bytes.as_slice(), params).unwrap();
let mut shares_for_bob = HashMap::new();
shares_for_bob.insert(eve_index, forged); // keyed under Eve, contents are Alice's

// 3. Bob calls KeyMachine::calculate_share. Inside Encryption::decrypt
//    (encryption.rs:479-499) the invalid PoP is only *queued* in the batch,
//    while key = ecdh(bob_enc_key, K_a) and a DLEq proof are computed eagerly.

// 4. Alice's share deserializes (from_repr succeeds), but fails the share
//    verification statements under Eve's commitments, and the PoP fails under
//    sender=Eve. If verify_with_vartime_blame returns BatchId::Share(Eve),
//    Bob's error is:
//      PedPoPError::InvalidShare { participant: Eve, blame: Some(proof) }
//    where proof.key == bob_enc_key * K_a.

// 5. Anyone with the published proof runs:
//      cipher::<C>(context, &proof.key).apply_keystream(ciphertext)
//    over Alice's ciphertext (which Eve included verbatim), recovering
//    f_alice(Bob) -- Alice's secret share for Bob.
```

Note: I was unable to inspect `multiexp::BatchVerifier::verify_with_vartime_blame`'s blame-selection order, so whether the leaking `Share` blame (rather than the `Decryption` blame) is returned deterministically is unverified; the information-disclosure primitive (eager ECDH-key proof emission before PoP verification) is present regardless.
