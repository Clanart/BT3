### Title
Cross-chain `RedeemEscrow` requests the full (pre-fee) input amount while only the fee-reduced amount is escrowed, permanently locking solver payouts - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`placeOrder` escrows `order.inputs[i].amount` **minus** the protocol fee (`reducedInputs[i].amount`) whenever `protocolFeeBps > 0`, but `_fillCrossChain` builds the `RedeemEscrow` `WithdrawalRequest` using the **full**, un-reduced `order.inputs` array. On the source chain, `_withdraw` (`IntentsBase.sol`) decrements `_orders[commitment][token]` by the amount taken from the request body with only an `escrowed == 0` guard — it never checks `amount <= escrowed`. When the requested (gross) amount exceeds the escrowed (net) amount, Solidity 0.8's checked arithmetic reverts the subtraction, permanently bricking that `RedeemEscrow` message. This is the same class of bug as the external report: two quantities (`escrowed input` and `redeemed input`) that are supposed to agree are computed independently and never validated against each other.

### Finding Description
- **Escrow side (`placeOrder`)**: when a destination-specific or global `protocolFeeBps` is non-zero, the contract computes `reducedInputs[i].amount = originalAmount - protocolFee` and stores that reduced value in `_orders[commitment][token]`: [1](#0-0) [2](#0-1) 

- **Redeem side (`_fillCrossChain`)**: on the destination chain, the solver's `RedeemEscrow` message is built directly from `order.inputs` (the gross, pre-fee amounts), not from the reduced/escrowed amounts: [3](#0-2) 

- **Release side (`_withdraw`)**: the source-chain handler for `RedeemEscrow`/`RefundEscrow` blindly decrements escrow by the message's requested `amount`, checking only that the token has *any* escrow at all, not that it has *enough*: [4](#0-3) 

Because Solidity ≥0.8 performs checked subtraction, `_orders[body.commitment][token] = escrowed - amount` reverts whenever `amount > escrowed`. There is no fallback or "clamp to available balance" path, and no earlier validation that `stepsize`-style quantities (`order.inputs` used for redemption vs `reducedInputs` used for escrow) actually match.

The test suite itself only exercises this flow with `protocolFeeBps == 0`, at which point `order.inputs == reducedInputs` and the mismatch is masked, as explicitly noted in a test comment ("protocolFeeBps is 0 in setUp, so escrow == input"): [5](#0-4) 

### Impact Explanation
Any cross-chain order placed while `protocolFeeBps` (or the per-destination override) is non-zero will always fail its `RedeemEscrow` settlement. The solver has already delivered the full output amount to the beneficiary on the destination chain (per `_fillCrossChain`'s transfer logic) before the message is dispatched, so the solver is left having paid out real assets with no way to reclaim the source-chain escrow — the `onAccept` call reverts on the underflow every time it is retried, since the message body's amount is fixed. This is a direct loss/permanent lock of bridged funds for an unprivileged, ordinary user flow (fee configuration is a normal governance parameter, not an attacker-controlled or malicious-actor precondition), matching the "loss of funds" and "cross-chain escrow must move exactly once and only the rightful amount" impact classes.

### Likelihood Explanation
This triggers deterministically and unconditionally whenever `protocolFeeBps > 0` (global or destination-specific) is configured and a cross-chain order is filled — no malicious relayer, prover, or admin is required. It is a pure logic defect in amount bookkeeping between `placeOrder` and `_fillCrossChain`. Because the same-chain path correctly uses stored/reduced escrow amounts on redemption while the cross-chain path does not, the bug is isolated to cross-chain fills and any deployment that has ever set a non-zero protocol fee together with cross-chain intents is affected.

### Recommendation
- In `_fillCrossChain`, build the `WithdrawalRequest.tokens` array from the **actual escrowed (reduced) amounts** for the commitment (mirroring what `placeOrder` stored in `_orders[commitment][token]`), not from `order.inputs` directly.
- Defense-in-depth: `_withdraw`/`withdraw` should validate `amount <= escrowed` explicitly (returning a clear error) rather than relying on an implicit underflow revert, and ideally should release "whatever remains" for finalize-type withdrawals instead of a caller-supplied amount, closing off any future drift between escrow bookkeeping and withdrawal requests.
- Add a regression test with non-zero `protocolFeeBps`/destination fee that exercises the full cross-chain fill → `RedeemEscrow` → `onAccept` path end-to-end (the current suite only covers this with fee = 0).

### Proof of Concept
1. Governance sets `protocolFeeBps > 0` (or a destination-specific fee) via `UpdateParams`.
2. User calls `placeOrder` for a cross-chain order with `inputs[0].amount = 1000e6`. `placeOrder` escrows `reducedInputs[0].amount = 990e6` in `_orders[commitment][usdc]` (per lines 353-364/450-458 of `evm/tron/contracts/apps/IntentGatewayV2.sol`).
3. A solver calls `fillOrder` on the destination chain; `_fillCrossChain` delivers outputs to the beneficiary and dispatches a `RedeemEscrow` message whose `WithdrawalRequest.tokens[0].amount = order.inputs[0].amount = 1000e6` (full, pre-fee amount) — see `ExtrinsicIntents.sol` lines 140-147.
4. The message lands on the source chain; `onAccept` calls `_withdraw` with `amount = 1000e6` against `escrowed = 990e6`. The line `_orders[body.commitment][token] = escrowed - amount;` underflows and reverts (`IntentsBase.sol` lines 400-403).
5. The transaction — and every retry of the same commitment/body — reverts identically. The solver's output delivery on the destination chain is final and cannot be undone, but the source-side escrow release can never succeed: the solver's funds are permanently lost/locked.
