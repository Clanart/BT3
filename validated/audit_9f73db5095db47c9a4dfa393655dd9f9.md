### Title
Untrusted output values can overflow Bitcoin transaction totals and trigger a panic or produce an unintended transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` trusts the `u64` amounts and outpoints carried by caller-supplied `ReceivedOutput` values. It sums input and payment amounts with unchecked `u64` arithmetic, then multiplies the requested fee rate by the transaction size, also without overflow checks. A malformed input set can therefore abort transaction construction in checked builds or wrap in unchecked builds and bypass the funding test.

### Finding Description
`ReceivedOutput::read` accepts a scalar offset, a consensus-decoded `TxOut`, and an arbitrary `OutPoint`, but does not validate that the output represents a spendable UTXO or constrain the aggregate value to Bitcoin's money supply. [1](#0-0) 

`SignableTransaction::new` then computes `input_sat` and `payment_sat` using `sum::<u64>()`. [2](#0-1)  It also computes `fee_per_vbyte * vbytes` and evaluates `payment_sat + needed_fee` without `checked_mul` or `checked_add`. [3](#0-2) 

Overflow of any of these operations panics in checked builds. In unchecked builds, wrapping can make the apparent input total and required total satisfy `input_sat >= payment_sat + needed_fee`. The resulting `SignableTransaction` is later eligible for signing; `multisig` checks only that each supplied offset produces the claimed previous output's `script_pubkey`, not that the outpoint exists or is funded with that value. [4](#0-3) 

### Impact Explanation
An attacker able to supply malformed `ReceivedOutput` data or influence transaction-construction inputs can cause a deterministic panic, analogous to the invalid-request assertion in the reference report. In wrapping builds, the same overflow can cause the threshold signer to sign a transaction whose declared inputs do not actually fund the outputs. This creates a signature and transaction the caller did not legitimately have funds to construct, although consensus will reject the fabricated spend.

### Likelihood Explanation
The malformed values are fully attacker-controlled when `ReceivedOutput::read` is exposed to serialized wallet data or when transaction-construction arguments are supplied by a coordinator. Triggering the panic requires only enough outputs or payment amounts to overflow `u64` arithmetic. Reaching signing additionally requires controlling the transaction proposal and having the configured participants complete the normal threshold-signing protocol.

### Recommendation
Reject `ReceivedOutput` values unless they come from authenticated wallet state or verified blockchain data. In `SignableTransaction::new`:

- Use `try_fold`/`checked_add` for `input_sat` and `payment_sat`.
- Use `checked_mul` for `fee_per_vbyte * vbytes`.
- Use `checked_add` for `payment_sat + needed_fee` and equivalent fee/change calculations.
- Reject individual and aggregate amounts exceeding Bitcoin's `MAX_MONEY`.
- Treat overflows as `TransactionError`, not wrapping values or panics.

### Proof of Concept
Conceptually, deserialize or construct two `ReceivedOutput` values whose `TxOut.value` is `Amount::from_sat(u64::MAX)`, whose outpoints are arbitrary, and whose `script_pubkey` matches the threshold key under the supplied offsets. Then call `SignableTransaction::new` with a payment near `u64::MAX`.

```rust
let fake_inputs = vec![
  ReceivedOutput::read(&mut bytes_for_fake_input_1())?,
  ReceivedOutput::read(&mut bytes_for_fake_input_2())?,
];

let payments = [(script_pubkey, u64::MAX)];

// Checked build: panics while summing input/output totals.
// Wrapping build: can bypass the insufficient-funds check.
let tx = SignableTransaction::new(
  fake_inputs,
  &payments,
  None,
  None,
  fee_per_vbyte,
)?;
```

The vulnerable unchecked operations are the input/output summations and fee arithmetic in `SignableTransaction::new`. [5](#0-4)
