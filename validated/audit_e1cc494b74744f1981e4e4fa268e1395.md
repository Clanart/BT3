### Title
Balance-based reward sweep in `compound()` allows theft of any pre-existing/other-user token balance without real claim entitlement - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` calls `multiclaimOnBehalf(_lps, _rewards, msg.sender)` and then, in a separate loop over `rewards[]`, sweeps `IERC20(_tokenAddress).balanceOf(address(this))` unconditionally and sends/locks/converts the *entire* contract balance to `msg.sender`. Because the transfer amount is derived from the contract's total balance rather than the amount actually returned/attributable to the caller's `multiclaimOnBehalf` call, any unprivileged caller can pass empty or irrelevant `_lps`/`_rewards` arrays (which cause `multiclaimOnBehalf` to no-op for that caller) and still walk away with any token balance sitting in the contract at call time.

### Finding Description
In `compound()` [1](#0-0) , `multiclaimOnBehalf` is invoked with attacker-supplied `_lps`/`_rewards`. If these arrays are empty (or reference pools the attacker never staked in), the claim call is effectively a no-op and does not revert. Regardless, the second loop over the globally configured `rewards[]` array reads `IERC20(_tokenAddress).balanceOf(address(this))` and routes the *full balance* to `msg.sender` via `lockFor`, `convertFor`, `depositFor`, or a plain transfer [2](#0-1) .

Because `ManualCompound` is a single shared contract used by all callers (it holds no per-user accounting, only a shared `Reward[]` config), any token balance present in the contract at the moment `compound()` executes — regardless of source — is up for grabs by whoever calls `compound()` next with a favorable transfer path (e.g. `_lockMgp = true` routed through `lockFor`, or a plain `safeTransfer`). This includes:
- Residual/dust balances left over from `addReward`/locker setup or incomplete prior transactions.
- Legitimate rewards claimed by *another user's* pending `compound()` transaction, if an attacker front-runs the second half of that transaction is not applicable since it's atomic within one tx — but a genuine race exists if `multiclaimOnBehalf` and the sweep are not atomic against reentrancy/interleaving from other paths that deposit tokens into `ManualCompound` (e.g., direct transfers, or other reward-claim flows that route through the same address).

The critical root cause is that the sweep is **balance-based, not return-value-based**: there is no capture of the amount actually claimed by `multiclaimOnBehalf` for `msg.sender`, and no accounting ties the swept balance to the caller's own claim. Existing checks (`compoundableRewards` mapping, `validRewardIndex`, `onlyOwner` on config setters) only govern which tokens are eligible for conversion/locking — they do nothing to verify the caller is entitled to the specific balance being moved.

### Impact Explanation
Any token balance held by `ManualCompound` — whether from operational dust, misdirected transfers, or race conditions with legitimate reward flows — can be stolen by an unprivileged attacker calling `compound()` with a crafted empty/irrelevant `_lps`/`_rewards` array. This constitutes direct theft of funds/unclaimed yield that do not belong to the caller, matching the Immunefi impact class "theft of unclaimed yield" / "direct theft of user funds."

### Likelihood Explanation
Exploitation requires only a standard EOA transaction calling the public `compound()` function with empty or attacker-chosen `_lps`/`_rewards` arrays — no special privileges, capital, or complex setup needed beyond a nonzero balance existing in `ManualCompound` at call time. Since the contract is a shared pot with no per-caller accounting, any residual balance (dust, rounding remainders from token transfers, or unintended direct transfers) is immediately sweepable. This is a low-cost, repeatable attack: an attacker can simply monitor `ManualCompound`'s token balances and call `compound()` with empty arrays whenever a balance appears.

### Recommendation
Refactor `compound()` to compute the *delta* in balance caused specifically by the `multiclaimOnBehalf` call for `msg.sender` (snapshot balances before/after the claim call) and only route that delta amount, rather than sweeping the entire contract balance. Additionally, ensure `multiclaimOnBehalf` reverts or the outer function reverts when `_lps`/`_rewards` don't correspond to actual claimable stake for `msg.sender`, so pre-existing contract balances can never be attributed to an unrelated caller.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `ManualCompound(masterMagpie)`, a mock MGP ERC20, and a mock `ILocker`.
2. Call `addReward(mgpToken, address(0), address(0), lockerAddress)` as owner to register MGP with a locker.
3. Directly transfer MGP tokens to `ManualCompound` address (simulating leftover/stuck funds, e.g. dust from a prior op), without any staking by the attacker in `MasterMagpie`.
4. As attacker EOA (with zero stake in any pool), call `compound(emptyLpsArray, emptyRewardsArray, 0, 0, true)`.
5. Assert: `multiclaimOnBehalf` is a no-op (attacker had no stake), yet `IERC20(mgp).balanceOf(address(ManualCompound))` drops to 0 and `ILocker.lockFor` is invoked with the full previously-stuck balance credited to attacker, i.e., attacker's locked/vlMGP balance increases despite zero legitimate claim entitlement.
6. This confirms fund misattribution independent of `multiclaimOnBehalf`'s actual claim output.
