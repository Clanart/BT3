### Title
`ReceivedOutput::read` accepts an arbitrary `script_pubkey`/outpoint without checking it belongs to the expected key (path-traversal analog) - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The OpenRefine bug constructs a filesystem path from an untrusted `lang` parameter and never verifies the resolved path stays inside the intended directory — the input selects a resource outside the expected set. The Serai analog is `ReceivedOutput::read`: it deserializes `(offset, TxOut, outpoint)` from untrusted bytes and never verifies that the `TxOut`'s `script_pubkey` is actually the P2TR script the `offset` claims to describe (`p2tr_script_buf(key + G*offset)`), nor that the outpoint corresponds to a real scanned output. A `ReceivedOutput` is a claim that "the multisig received value V at outpoint O, spendable via offset". The deserializer lets an attacker forge that claim, escaping the constrained set of outputs `Scanner` would ever produce.

### Finding Description
`Scanner::scan_transaction` is the only legitimate producer of `ReceivedOutput`: it constructs one only when `output.script_pubkey` is found in `self.scripts`, i.e., only when the script is exactly `p2tr_script_buf(key + G*offset)` for a registered offset (`wallet/mod.rs:199-214`, `180-196`). `ReceivedOutput::read` (`wallet/mod.rs:122-134`) performs zero such binding:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ...
  output = TxOut::consensus_decode(&mut buf_r)...;
  outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

Any `TxOut` (any `script_pubkey`, any `value`) and any `OutPoint` are accepted as long as the scalar decodes. This is the traversal: the deserialized "path" (offset → implied script/outpoint) is never normalized back into the expected directory (the set of scripts owned by the scanner's key).

Downstream, `SignableTransaction::new` / `TransactionMachine` consume `ReceivedOutput`s to build inputs, compute fee/change (`networks/bitcoin/src/wallet/`), and the sighash commits to `output.script_pubkey` and `value` via `Prevouts::All`. A forged `ReceivedOutput` pointing at a real third-party UTXO with a fabricated `value` yields a fully signed transaction spending someone else's coins — invalid on-chain but internally consistent — while a forged output claiming inbound funds that were never scanned produces "funds reported received that are not spendable" (the real script pays elsewhere, or the outpoint doesn't exist / is already spent).

### Impact Explanation
- **Unspendable credited funds**: any component deserializing attacker-supplied `ReceivedOutput`s (or trusting serialized scan results from a tampered/ federated source) will report received funds that the multisig cannot sign for — the offset does not unlock the declared `script_pubkey`. In a bridge this corrupts accounting: deposits credited that cannot ever be spent or forwarded.
- **Signed spends of fabricated inputs**: `SignableTransaction` trusts `output.value()` and `outpoint()` for input construction and fee/change math, so a forged `ReceivedOutput` drives the multisig to sign an invalid or mis-valued transaction (change computed off a phantom input), enabling griefing/signature-oracle behavior against outputs the scanner never saw.
- The untrusted-bytes reachability criterion is satisfied directly: `ReceivedOutput::read` is explicitly listed as an attacker-reachable `read_*` API.

### Likelihood Explanation
`read` is exercised wherever `ReceivedOutput`s round-trip through serialization (DB persistence, network relay, `Output::read` in the processor which calls `ReceivedOutput::read` on decoded bytes — `processor/src/networks/bitcoin.rs:156`). There is no integrity/authenticity tag in the encoding (`write`/`serialize` at `wallet/mod.rs:136-148`), so any byte supplier controls all three fields. Exploitation requires an integrator that feeds non-self-generated bytes into `read`, which is the standard deserialization attack surface this report assumes.

### Recommendation
Do what the OpenRefine patch does — verify the normalized result lands in the expected set:
1. Make `ReceivedOutput` deserialization take/return the binding context: after reading, recompute `p2tr_script_buf(key + G * offset)` and reject if `output.script_pubkey` doesn't match; equivalently, authenticate serialized `ReceivedOutput`s (MAC/signature over `write` output) at the storage boundary.
2. Additionally validate the claimed outpoint against chain data before crediting (defense in depth: confirm `outpoint` exists, is unspent, and pays the recomputed script).

### Proof of Concept
```rust
// Take any valid scanned ReceivedOutput `legit` (offset = 0 to key K).
// Forge one claiming K's offset but an attacker-chosen script/outpoint/value:
let mut forged_bytes = vec![];
forged_bytes.extend(Scalar::ZERO.to_repr());           // offset => "owned by K"
let fake_out = TxOut {
  value: Amount::from_sat(50_000_000),                 // phantom 0.5 BTC
  script_pubkey: ScriptBuf::new_p2tr_tweaked(
    TweakedPublicKey::dangerous_assume_tweaked(attacker_xonly)),
};
forged_bytes.extend(serialize(&fake_out));
forged_bytes.extend(serialize(&victim_outpoint));      // real or fabricated outpoint

let forged = ReceivedOutput::read(&mut forged_bytes.as_slice()).unwrap();
// forged.value() == 50_000_000 is now "received by" the multisig,
// yet offset 0 does not unlock fake_out.script_pubkey.
// Feeding `forged` into SignableTransaction::new(vec![forged], ...) yields
// a signed tx whose input either doesn't exist or isn't spendable by K.
```

No Scanner path can emit such an object (`scan_transaction` requires `self.scripts.contains(script_pubkey)`), so the deserialized object demonstrably escapes the expected set — the exact confinement failure class of GHSA-qfwq-6jh6-8xx4.
