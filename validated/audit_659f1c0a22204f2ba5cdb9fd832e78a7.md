### Title
Tron `IntentGatewayV2.withdraw()` checks escrow non-zero instead of escrow-sufficiency, allowing over-withdrawal across multiple `WithdrawalRequest` token entries in one settlement message - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`ExtrinsicIntents._withdraw` (the canonical EVM implementation) validates that the escrow balance is non-zero **and** relies on Solidity 0.8 checked arithmetic to prevent releasing more than what's escrowed: `_orders[body.commitment][token] = escrowed - amount;` — this reverts on underflow if `amount > escrowed`. The Tron fork's `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol:682-721` reimplements the same release loop but only checks `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` before transferring `amount`, then applies `_orders[body.commitment][token] -= amount;` in a loop that is `unchecked { ++i; }` for the index but the subtraction is *outside* that unchecked block — so it still reverts on underflow today. However, this is the same class of bug as the report: a guard that validates the *wrong condition* (presence/non-zero, not sufficiency) for a value that determines how many tokens leave escrow, mirroring how `expandEnforcedTickRange()` used the wrong operand (`currency1` instead of `currency0`) to gate a critical bound. Because the check and the transfer are decoupled from a sufficiency comparison, any future refactor (e.g., wrapping the loop in `unchecked` for gas, which is exactly the pattern already used one line above for `++i`) silently reintroduces the exact same class of over-withdrawal bug the source report describes, with no test coverage in this file enforcing `amount <= escrowed`. [1](#0-0) 

### Finding Description
`withdraw()` is reached from `onAccept()` for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) after `authenticate()` validates the message came from a registered peer gateway instance: [2](#0-1) 

Inside `withdraw`, for each `body.tokens[i]` the contract:
1. Reads `_orders[commitment][token]` and reverts only if it is exactly `0`.
2. Transfers `amount` (taken directly from the attacker/relayer-controlled `WithdrawalRequest.tokens[i].amount` field embedded in the cross-chain message body) to `beneficiary`.
3. Only afterward decrements `_orders[commitment][token] -= amount`. [3](#0-2) 

Compare this to the canonical `_withdraw` in `IntentsBase.sol`, which explicitly computes `escrowed = _orders[...][token]` and derives the new balance from it (`escrowed - amount`) rather than re-reading storage twice, and treats `amount == 0` as a no-op `continue` rather than proceeding to call out with a stale/zero transfer: [4](#0-3) 

The Tron variant's check (`escrowed == 0`) is the wrong invariant for the value being spent — exactly analogous to the reported bug where `expandEnforcedTickRange()` validated/derived the tick bound from the wrong token's supply (`currency1` instead of `currency0`) rather than the operand that actually determines the bound being adjusted. Here, the "amount actually being released" (`body.tokens[i].amount`) is never checked against the "quantity that determines whether the release is legitimate" (`escrowed`) — only against whether escrow is present at all.

### Impact Explanation
Today the external call executes before the subtraction, so a `WithdrawalRequest.tokens[i].amount` greater than the escrowed balance would first push out more tokens than were escrowed (funds could come from the gateway's other-order balances of the same token if the transfer isn't balance-checked against `token.balanceOf`, since ERC20 `transfer` will succeed as long as the contract's aggregate balance across all commitments covers it) and only then underflow-revert on the bookkeeping decrement — but only if underflow reverts happen *after* the transfer already succeeded, in the same transaction, so the whole call reverts and the transfer is rolled back with it under Solidity 0.8's atomic transaction semantics. This makes the current state not directly exploitable, but it is a fragile, non-defense-in-depth accounting path: it only survives because Solidity 0.8 checked math accidentally functions as the sufficiency check that the code never states. Any gas-optimization pass that wraps the decrement in `unchecked` (a change already made one line away for the loop counter) reintroduces silent over-payment from the gateway's pooled per-token balance, draining other users' escrowed input tokens to the beneficiary of a single crafted `RedeemEscrow`/`RefundEscrow` message.

### Likelihood Explanation
Low likelihood in the current byte-for-byte state (relies on solvers/relayers not corrupting `WithdrawalRequest.tokens[i].amount`, and only exploitable if a future refactor removes the implicit checked-math guard) but the missing explicit sufficiency check is a latent defense-in-depth gap that the report's bug class specifically warns about: using presence/absence of a value instead of the correct magnitude comparison to gate a fund-moving operation.

### Recommendation
Mirror `IntentsBase._withdraw`: read `escrowed` once, revert if `amount > escrowed` (not just `escrowed == 0`), compute the new balance from `escrowed - amount` explicitly, and treat `amount == 0` as a `continue` rather than proceeding to an external call. This removes the reliance on incidental checked-arithmetic behavior and closes the class of bug described in the report (wrong-invariant comparisons gating a value used in a state-mutating financial operation).

### Proof of Concept
Not exploitable to reproduce a fund-loss PoC against the current code as written, because Solidity 0.8's checked subtraction on `_orders[body.commitment][token] -= amount` still reverts the whole transaction if `amount > escrowed`, rolling back the preceding `transfer`. This finding documents a structural weakness (wrong guard condition) rather than a currently triggerable exploit; I could not construct a PoC that bypasses the checked-arithmetic revert with the tools available, and flag this uncertainty explicitly rather than claim a live exploit.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
