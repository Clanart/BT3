### Title
Unauthenticated `InternalSendTx` RPC call reachable when aggregator runs with `client_verification=false` - ([File: core/src/rpc/interceptors.rs])

### Summary
`only_aggregator_and_self` in `core/src/rpc/interceptors.rs` is the only code path that enforces the binding "caller of an `Internal*` method == `our_cert` holder," and it is applied exclusively through the `Interceptors::OnlyAggregatorAndSelf` variant. When the aggregator is configured with `client_verification=false`, `core/src/servers.rs::create_grpc_server` selects `Interceptors::Noop` instead, which performs no certificate check at all, so any caller who can reach the aggregator's gRPC port can invoke `InternalSendTx`.

### Finding Description
The intended binding is: `peer_leaf_cert(InternalSendTx caller) == our_cert` (enforced by `only_aggregator_and_self` at [1](#0-0) ). This check is only reached when `req.peer_certs()` exists and `is_internal(&req)` is true, itself gated on the `Interceptors::OnlyAggregatorAndSelf` variant being installed [2](#0-1) .

`core/src/servers.rs::create_grpc_server` decides which interceptor variant to install based purely on `config.client_verification`: if false, it builds `ServerTlsConfig` without `.client_ca_root(...)` (no client cert required at the TLS layer) and installs `Interceptors::Noop`, which returns `Ok(req)` unconditionally [3](#0-2) . In that configuration there is no code path anywhere that re-checks the caller's identity for `InternalSendTx` — `is_internal`/`only_aggregator_and_self` are simply never invoked, so the "self-only" binding does not hold: `peer_leaf_cert(caller) == our_cert` becomes `∅ == our_cert`, i.e., no verification occurs at all.

Consequently, with `client_verification=false`, an attacker with plain TCP access to the aggregator's gRPC port can call `ClementineAggregator::internal_send_tx` directly, supplying an arbitrary `RawSignedTx` payload, and the call reaches `AggregatorServer`'s handler in `core/src/rpc/aggregator.rs` unauthenticated, which forwards it toward the tx-sender infrastructure for broadcast.

### Impact Explanation
This matches the "High - an unauthenticated state-changing or broadcasting call" category: an attacker can invoke a gRPC method that is designed to be restricted to the aggregator's own local caller (`our_cert`) without presenting any credential. Note that actually causing bridge-fund loss (e.g., spending a bridge UTXO) still requires a valid Schnorr signature over that UTXO's sighash; forging N-of-N signatures is out of scope (key compromise), so this finding does not by itself demonstrate BTC leaving a move-to-vault UTXO or an unauthorized N-of-N spend — the concrete, in-scope impact is the unauthenticated ability to make the aggregator's internal, self-only broadcasting endpoint execute a caller-supplied action, i.e., a broken access-control binding on a state-changing/broadcasting RPC. It is repeatable per request and applies to any deployment that runs with `client_verification=false`.

### Likelihood Explanation
The precondition is a specific deployment/config choice: the aggregator process must be started with `config.client_verification=false` (which also disables mTLS client-cert enforcement at the transport layer, per `core/src/servers.rs` lines 106-139). Under that configuration, exploitation costs the attacker nothing beyond network access to the aggregator's gRPC port and knowledge of the `InternalSendTx` protobuf schema — no BTC, no key material, no certificate. If `client_verification=true` (the presumably intended production setting, given the explicit `tracing::warn!` emitted when it's enabled — implying it can be, and by default may be, disabled), the `only_aggregator_and_self` check fully closes this path since `is_internal` correctly identifies the method and rejects any peer certificate other than `our_cert`.

### Recommendation
Do not rely solely on a boolean config toggle that disables authentication entirely for `Internal*` methods. Either (a) always enforce `only_aggregator_and_self`-style checks for methods whose gRPC path starts with `Internal`, independent of `client_verification`, or (b) require `client_verification=true` unconditionally for the aggregator's listener and fail to start otherwise, so `Interceptors::Noop` can never be selected for a production/network-exposed aggregator.
