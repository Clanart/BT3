## Finding: `clone()` explicitly disables Git's embedded-repository clone protection

### Title
`GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` for every recursive clone, disabling upstream's embedded-repository/hook-injection safeguard - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` runs `git clone --recursive` and unconditionally sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for the operation: [1](#0-0) 

Git upstream introduced `GIT_CLONE_PROTECTION_ACTIVE` as part of the fix for the embedded-repository/hooks-injection class of vulnerabilities (the family that produced GHSA/CVE-2024-32002-style clone-time code execution, where a malicious repository with crafted submodules/embedded `.git` directories can get a hook or config file written into the *superproject's* real `.git` directory during a recursive clone, later executed on any git operation). Git's own clone code checks this variable/flag to decide whether extra safety checks (rejecting suspicious embedded git dirs, case-insensitive/NTFS name collisions with `.git`, etc.) should run during the clone. By explicitly setting it to `'false'`, GitHub Desktop is telling Git the protection is *not* active, i.e. it opts back out of the very check upstream Git ships to stop this attacker-controlled-repository class of bug.

### Finding Description
The attacker primitive here matches the required impact profile exactly: **the user clones a repository the attacker controls** (e.g., via "Open in Desktop"/`x-github-client://openRepo/...`, which flows through `parseAppURL` → `openRepositoryFromUrl` → `openOrCloneRepository` → `clone()`, or by manually pasting a malicious clone URL). The corrupted invariant is: *"Git clone will refuse to write hook/config files outside the intended repository layout when cloning recursively."* GitHub Desktop's `clone()` function forces this invariant off for every single clone operation performed by the app.

Other layers of `clone.ts` add defense for a *different* threat (path traversal of the destination folder via `isClonePathSensitive`), but that only checks the destination directory string — it does nothing to stop a malicious repository's *content* (nested `.git` folders, submodule gitlinks, `.gitmodules` entries) from tricking Git into writing hook scripts or config into the superproject's `.git` during the `--recursive` clone, which is precisely what `GIT_CLONE_PROTECTION_ACTIVE` is meant to catch: [2](#0-1) [3](#0-2) 

The app does have a hook-execution interception mechanism (`withHooksEnv`/`getRepoHooks`) that redirects `core.hooksPath` to a proxied temp directory for operations like `pull`/`push`/`commit`, but `clone` is not among the operations wired through `interceptHooks`: [4](#0-3) 

So neither of the two existing guards (destination-path sensitivity check, hooks-proxy interception) covers the specific attack surface that `GIT_CLONE_PROTECTION_ACTIVE=false` reopens: a crafted repository/submodule tree that, during recursive clone, plants a hook or config file that will be silently executed the next time the user runs any git command (commit, checkout, etc.) in that repository — all without any unusual user action beyond cloning a link they were sent.

### Impact Explanation
If Git's embedded-repository protection is what stands between "clone a link" and "arbitrary hook execution on next git operation," disabling it converts a routine, expected user action (cloning a repository/opening a link) into a potential local code-execution vector once the victim performs any subsequent git operation in the freshly cloned tree. This satisfies the "Valid Impact" bar: attacker controls a cloned/fetched repository, and the result is code execution outside normal repo boundaries.

### Likelihood Explanation
Likelihood is high for the trigger (cloning is one of the most common actions in Desktop, and it can be reached purely by a link click via the `x-github-client://openRepo/` deep link or the CLI `--cli-clone` flag) but is bounded by the fact that I could not directly confirm, from the indexed code alone, the exact semantics of `GIT_CLONE_PROTECTION_ACTIVE` as consumed by the vendored Git binary Desktop ships (this is Git's own C code, not part of this repository, so I cannot verify the exact protected/unprotected code paths it toggles, nor pin an exact CVE without external confirmation). The variable name and its explicit, unconditional `'false'` value strongly indicate protection is being deliberately switched off rather than merely defaulted, which is the actionable/verifiable part.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. If it was set to disable protection for a specific compatibility reason, that reason should be documented in code, the setting should be conditional (e.g., only for trusted/local clone sources), and equivalent protections (e.g., blocking symlinked/embedded `.git` dirs, validating `.gitmodules` paths before recursive submodule init, keeping clone within the hooks-proxy sandbox used by other commands) should be added back for the recursive clone path.

### Proof of Concept
Exact end-to-end exploitation could not be fully constructed without executing the vendored Git binary to confirm what `GIT_CLONE_PROTECTION_ACTIVE=false` actually toggles in this Git version, so this is reported based on strong code-level evidence rather than a fully verified working exploit:
1. Attacker hosts a malicious Git repository containing a submodule/nested `.git` entry crafted to collide with or escape into the superproject's `.git` directory during `--recursive` clone.
2. Attacker sends the victim a link such as `x-github-client://openRepo/https://attacker.example/evil-repo` (parsed by `parseAppURL`, dispatched by `openRepositoryFromUrl`).
3. Victim clicks the link; Desktop calls `clone()` with `--recursive` and `GIT_CLONE_PROTECTION_ACTIVE=false` [1](#0-0) , bypassing Git's embedded-repo protection that would otherwise reject/neutralize the crafted submodule.
4. If a hook/config is planted, it executes on the victim's next ordinary git operation in that repository (not intercepted by `withHooksEnv`, since `clone` does not pass `interceptHooks`).

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
