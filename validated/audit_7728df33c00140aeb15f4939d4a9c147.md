### Title
Flash-deposit sandwich around `queueNewRewards`/`donateRewards` lets an attacker snipe a disproportionate share of freshly-queued rewards - ([File: rewards/BaseRewardPool.sol])

### Summary
`_provisionReward` (called by both `queueNewRewards` and the permissionless `donateRewards`) increases `rewardInfo.rewardPerTokenStored` using the instantaneous `totalStaked()` snapshot with no time-weighting. Because `MasterMagpie._deposit`/`_withdraw` checkpoint a user's reward debt (`updateFor`) using the balance held at call time and update `user.amount` only after, an attacker can flash-deposit `stakingToken`, wait for a manager's `queueNewRewards` (and optionally add their own `donateRewards`), then withdraw in the same transaction, capturing a reward share proportional to their inflated momentary balance rather than their real time-weighted stake.

### Finding Description
`queueNewRewards`/`donateRewards` both call `_provisionReward`, which does: [1](#0-0) 
i.e. `rewardPerTokenStored += amount * 1e_dec / totalStaked()`, where `totalStaked()` is simply `IERC20(stakingToken).balanceOf(operator)` read live at call time: [2](#0-1) 

In `MasterMagpie`, `_deposit` checkpoints the user's reward accounting (`_harvestBaseRewarder` → `rewarder.updateFor(_account)`) using the *pre-deposit* balance, then increases `user.amount`: [3](#0-2) 
Conversely, `_harvestAndUnstake` (called on withdraw) checkpoints/harvests using the *current, still-inflated* balance before decreasing `user.amount`: [4](#0-3) 

There is no cooldown, vesting, or minimum holding period between deposit and withdrawal, and no `nonReentrant`/time-lock prevents both actions from occurring in the same transaction. This lets an attacker do:
1. `deposit(stakingToken, huge)` — inflates `totalStaked()`.
2. Manager calls `queueNewRewards(A, token)` — `rewardPerTokenStored` increases by `A / (huge + existing)`, diluted by the attacker's inflated balance.
3. Attacker calls `donateRewards(B, token)` — same dilution effect, using the same inflated `totalStaked()`.
4. Attacker calls `withdraw(stakingToken, huge)` — `_harvestAndUnstake` checkpoints the attacker's earned rewards using the *huge, still-current* balance times the total `rewardPerTokenStored` delta accrued in steps 2–3, capturing nearly all of `A + B` because the attacker's temporary balance dominates `totalStaked()`.
5. `getReward()` transfers out the captured share.

Because `earned()` is a pure balance × rate-delta calculation with no time-weighting (`earned = balanceOf * (rewardPerToken - userRewardPerTokenPaid) / 1e_dec + userRewards`, see [5](#0-4) ), a single-block/transaction stake is treated identically to a long-term stake for the entire un-checkpointed reward delta. Existing checks (`onlyManager` on `queueNewRewards`, `isRewardToken` check on `donateRewards`) do not prevent this because the attack does not require calling `queueNewRewards` itself — it only requires timing a deposit/withdraw around it. `donateRewards` is not actually "bypassing" `onlyManager`; it is a separate, intentionally permissionless function, but combined with the flash-deposit sandwich it amplifies the reward-sniping effect and lets the attacker largely reclaim their own donation while also skimming part of the manager's legitimate `A` reward meant for genuine long-term stakers.

### Impact Explanation
This is a direct theft of unclaimed yield from legitimate long-term stakers: the attacker extracts a share of the manager-funded reward `A` proportional to a stake they held for only one transaction, diluting/stealing rewards that should have accrued to real stakers over time. This matches the "theft of unclaimed yield" / "direct theft of user funds" Immunefi impact classes.

### Likelihood Explanation
Requires: (1) the attacker be able to flash-borrow or otherwise transiently acquire a large amount of `stakingToken` (feasible for many ERC20 staking tokens via flash loans or DEX flash swaps), (2) ability to time their transaction to land in the same block/transaction context as a manager's `queueNewRewards` call, which is realistically achievable via mempool front-running/same-block bundling since `queueNewRewards` is a normal, non-time-locked, publicly-observable transaction. No special privileges are needed. This is repeatable every time a manager queues new rewards.

### Recommendation
Replace the instantaneous balance/`totalStaked()` snapshot reward model with a time-weighted accounting scheme (e.g., checkpoint `rewardPerTokenStored` continuously based on elapsed time and a reward rate, as in standard `StakingRewards`-style contracts), or add a minimum staking duration / withdrawal cooldown so that deposits cannot immediately withdraw and claim freshly queued rewards in the same transaction or block. At minimum, checkpoint user reward-debt using post-deposit balances only after a delay, and disallow `withdraw` in the same block as `deposit` for a given account/pool.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `BaseRewardPool` (or `BaseRewardPoolV2`), a mock ERC20 `stakingToken`, and a mock ERC20 reward token; register the pool and reward token, set up a manager.
2. Have a "legitimate" staker deposit a modest amount and let some time pass (irrelevant since no time-weighting exists, but establishes baseline stake).
3. In a single transaction (attacker's contract):
   a. `masterMagpie.deposit(stakingToken, HUGE)`.
   b. Impersonate/call `manager.queueNewRewards(A, rewardToken)`.
   c. `baseRewardPool.donateRewards(B, rewardToken)` (attacker-funded).
   d. `masterMagpie.withdraw(stakingToken, HUGE)`.
   e. `masterMagpie` triggers `getReward` (or call `multiclaim`).
4. Assert: attacker's claimed reward ≈ `(A+B) * HUGE/(HUGE+existing)`, which is disproportionate to a genuine time-weighted share (i.e., `attackerReward > B` plus more than a negligible/zero share of `A`, despite zero time-weighted exposure), while the legitimate staker's claimable share of `A` is diluted below what it should be absent the sandwich.
5. Compare against a control run without the flash sandwich, showing the legitimate staker receives the expected full share of `A` when no flash deposit occurs.

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
