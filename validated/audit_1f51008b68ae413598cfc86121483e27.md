## Title
Withdrawal-UTXO reuse across two Citrea indices lets one payout tx satisfy two `withdrawals` rows, crediting an operator twice - (File: core/src/database/verifier.rs)

## Summary
`get_payout_txs_for_withdrawal_utxos` (core/src/database/verifier.rs:170-196) joins `withdrawals` to `bitcoin_syncer_spent_utxos` solely on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, with no uniqueness constraint on that pair in the `withdrawals` table (core/src/database/schema.sql:269-281). If two Citrea withdrawal indices `i` and `j` are ever populated with the identical UTXO by `update_withdrawal_utxo_from_citrea_withdrawal` (called from `update_citrea_deposit_and_withdrawals`, core/src/verifier.rs:2248-2262), a single confirmed payout transaction spending that UTXO is matched to *both* rows by `update_finalized_payouts` (core/src/verifier.rs:2283-2353), and `update_payout_txs_and_payer_operator_xonly_pk` stamps the same `payout_payer_operator_xonly_pk` onto both rows.

## Finding Description
Binding that should hold: for each Citrea withdrawal index `idx`, the pair `(withdrawal_utxo_txid, withdrawal_utxo_vout)` uniquely identifies the on-chain spend event credited to `idx` — i.e. `spending_txid(idx_i's utxo) credits operator O for idx_i` should be independent of `spending_txid(idx_j's utxo) credits operator O for idx_j` whenever `idx_i ≠ idx_j`. This is broken because the join key is `(txid, vout)` alone (core/src/database/verifier.rs:175-181), not `(idx, txid, vout)`, and Bitcoin only allows a UTXO to be spent once, so if two rows reference the same UTXO, both rows deterministically receive the same `spending_txid` from `bitcoin_syncer_spent_utxos`.

The exact reachable path:
1. Citrea's Bridge contract records a withdrawal UTXO per index via its own `withdrawalUTXOs` mapping; Clementine simply trusts and stores whatever `collect_withdrawal_utxos` returns per index with no cross-index duplicate check (core/src/verifier.rs:2224-2262, core/src/citrea.rs:458-496).
2. `Verifier::update_finalized_payouts` looks up all `(idx, spending_txid)` pairs for a finalized block via the vulnerable join, parses the OP_RETURN operator xonly pk out of the single spending tx, and pushes `(idx, txid, operator_xonly_pk, block_hash)` for *every* matching idx (core/src/verifier.rs:2298-2343).
3. `update_payout_txs_and_payer_operator_xonly_pk` bulk-updates `withdrawals` rows by `idx`, so both `i` and `j` get `payout_txid`, `payout_payer_operator_xonly_pk = O`, `payout_tx_blockhash` set identically (core/src/database/verifier.rs:198-251).
4. `get_first_unhandled_payout_by_operator_xonly_pk` will then return `j` as payable to `O` once `i` is marked handled (core/src/database/verifier.rs:282-313), and the bridge circuit's storage-proof check (`verify_storage_proofs` + the `user_wd_txid`/`vout` assertions in circuits-lib/src/bridge_circuit/mod.rs:182-204) will also pass for `j`, because Citrea's storage for index `j` records the *same* UTXO that the single confirmed payout tx actually spent.

None of the listed guards catch this: `Verifier::is_deposit_valid`/`is_kickoff_malicious`, `SECP.verify_schnorr`, and `verify_storage_proofs` all validate that the payout tx's spent input matches the *registered* withdrawal UTXO for the deposit in question — but if two deposits/indices are registered with the same UTXO, that check is satisfied for both. The vulnerability is purely a Clementine-side data-modeling gap: the query and update functions never verify a 1:1 mapping between `idx`
