## Title
Line-selection state applies to a re-fetched diff at commit time, allowing silent corruption of partial-commit content when a fetched/checked-out tree changes between selection and commit - ([File: app/src/lib/git/apply.ts])

### Summary
The Burve report's root cause is a state-timing mismatch: a value/selection computed at time T (compounding based on out-of-range liquidity) is applied at time T+1 against a materially different underlying state (in-range liquidity), letting an attacker who controls the timing of the state transition capture value that should have been distributed against the original state. The Desktop analog is structurally the same class of bug: a user's line-level commit selection (`DiffSelection`) is computed against the diff that was on screen at selection time, but `applyPatchToIndex` in `app/src/lib/git/apply.ts` re-fetches a *fresh* working-directory diff at commit time and reapplies the old selection's line indices to it, rather than using the diff the user actually reviewed [1](#0-0) .

### Finding Description
`WorkingDirectoryFileChange.selection` is a `DiffSelection`, an index-based (not content-based) representation of which diff lines the user wants committed [2](#0-1) . When a user partially selects lines in the Changes view, Desktop tracks that selection against the diff hunks that were rendered at that moment. `updateChangesWorkingDirectoryDiff` explicitly acknowledges that the diff "might have changed dramatically since last we loaded it" and only prunes selection indices that fall outside the new set of selectable lines — it does not invalidate the selection or require re-confirmation [3](#0-2) .

At commit time, `_commitIncludedChanges` takes the currently cached `WorkingDirectoryFileChange` objects (with their stale, cached `selection`) and passes them straight to `createCommit` [4](#0-3) , which calls `stageFiles` → `applyPatchToIndex` for any partially-selected file [5](#0-4) . Crucially, `applyPatchToIndex` does **not** use the diff the UI showed the user; it calls `getWorkingDirectoryDiff` again, right before staging, to obtain a brand-new diff of the file on disk, and then applies the old `selection.isSelected(absoluteIndex)` bitmap against that new diff's line indices via `formatPatch` [1](#0-0) [6](#0-5) .

This is the same broken invariant as the Sherlock report: "selection/weights computed against state S₀ are executed against state S₁, and nothing forces S₀ == S₁ or re-validates the selection semantics against S₁." In Burve, the attacker times a deposit to exploit the gap between compounding calls. In Desktop, the trigger is any working-tree mutation that lands between the moment the diff is rendered/selected and the moment `git commit` actually runs — e.g., a `post-checkout`/`post-merge`/smudge filter from a fetched/pulled repository, a background `pull`/`fetch` that fast-forwards a branch and rewrites tracked file contents, or any external process touching the file — none of which invalidate or re-confirm the cached line selection before `createCommit` runs. Because `DiffSelection` is purely index-based with no content/hash binding to the reviewed hunk, the same line indices can now correspond to entirely different, unreviewed content.

Existing guards do not stop this: `lineSelectionDisabled` in the UI only blocks *interactive* selection changes while a commit is in progress [7](#0-6) ; it does nothing to protect against the diff itself changing underneath an already-made selection. `updateChangedFiles`'s `clearPartialState` option only clears selection *after* a commit completes, not before a new one starts [8](#0-7) . Nowhere in the commit path is the diff hash/content compared between the moment of selection and the moment of staging.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user could review and select specific, safe lines from a diff (e.g., deliberately excluding a secret or an unwanted change), and — if the working tree is mutated between that review and the click of "Commit" (by a git hook triggered from a fetched/cloned repository, a concurrent background fetch/pull that touches the same path, or any other process) — Desktop will silently apply the old line-index selection to the new file content and commit/push whatever now occupies those line positions. This can result in unintended secrets or malicious content being committed and pushed to a remote without any warning, or conversely intended content being silently dropped from the commit.

### Likelihood Explanation
Moderate-to-low but plausible in ordinary developer workflows: Desktop performs background fetches automatically, and users commonly leave partial-commit selections open in the UI while other git activity happens (background fetch → fast-forward, checkout of a linked worktree, a build tool, or a hook from a repository they cloned that includes a `post-checkout`/`post-merge`/smudge filter). No special privileges are needed beyond controlling the content of a repository the user has already cloned/added as a remote and getting a hook or filter to run around commit time; this fits the "attacker controls a cloned/fetched repository" primitive in the task's valid-impact list.

### Recommendation
Bind `DiffSelection` to the exact diff instance it was computed against (e.g., store a content hash or the diff object itself alongside the selection) and have `applyPatchToIndex`/`stageFiles` refuse to apply a selection whose bound diff no longer matches the on-disk diff, forcing a re-render/re-confirmation of the selection instead of silently re-indexing against new content.

### Proof of Concept
Not independently executable from the index alone; the interaction (background fetch/hook mutating a file between the user's line-selection and clicking Commit, followed by `applyPatchToIndex` re-fetching a fresh diff and reapplying stale indices) is derived directly from the code paths cited above: `app/src/ui/changes/changes.tsx` (selection UI, no protection against diff drift) → `app/src/lib/stores/app-store.ts:3376-3497` (diff refresh comment acknowledging drift) → `app/src/lib/stores/app-store.ts:3680-3761` (`_commitIncludedChanges` uses cached selection) → `app/src/lib/git/update-index.ts:163-168` → `app/src/lib/git/apply.ts:52-60` (re-fetches diff, applies old selection indices) → `app/src/lib/patch-formatter.ts:143-171` (line inclusion decided purely by absolute index).
