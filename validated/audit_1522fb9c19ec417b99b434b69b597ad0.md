### Title
`updateRemoteUrl` silently rewrites the git remote using a value validated against itself, not an independent trust anchor - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` decides whether to silently rewrite a repository's `origin` remote URL by checking `remoteUrlUnchanged`, but that check is computed by comparing the *current* remote URL against `gitHubRepository.cloneURL` — a value that was itself populated from a prior GitHub API response for the same repository/endpoint. Just as the `BondingTax` slippage check validated a swap output against a "minimum" derived from the very same untrusted price feed it was supposed to protect against, this code validates a remote-URL change against a reference value sourced from the same (potentially attacker-influenced) API channel that supplies the new value, so the guard cannot detect a hostile change originating from that channel.

### Finding Description
`updateRemoteUrl` is invoked from `app-store.ts` whenever fresh GitHub API repository metadata (`apiRepo`) is fetched for a locally tracked repository. It compares the new `apiRepo.clone_url` to the existing git remote, and if the git remote still matches the *previously cached* `gitHubRepository.cloneURL`, it treats the remote as "unchanged by the user" and silently calls `gitStore.setRemoteURL(...)` to rewrite it to the new value: [1](#0-0) 

The only checks performed are:
1. `protocolsMatch` – both URLs use the same scheme.
2. `remoteUrlUnchanged` – the *current* remote still equals the *last API-provided* clone URL (`gitHubRepository.cloneURL`), via `urlMatchesRemote`.
3. `!urlsMatch` – the new URL differs from the current remote. [2](#0-1) 

None of these checks validate the *new* `clone_url` against anything independent of the API endpoint that supplied it — `gitHubRepository.cloneURL` is itself just a cached copy of a prior API response for the same endpoint/account. If the GitHub Enterprise endpoint being used for that repository is attacker-influenced (compromised server, hostile DNS/MITM against a self-hosted GHE instance the user added an account for, or a malicious proxy sitting in front of it), the attacker controls both the cached `cloneURL` and the new `clone_url`, so `remoteUrlUnchanged` can always be made to evaluate however the attacker wants. This is structurally identical to the `BondingTax` bug: the "expected" value used to gate the write comes from the same untrusted source as the value actually being written, so the guard provides no real protection against a hostile value from that source.

### Impact Explanation
If exploited, the local git remote is silently repointed (`gitStore.setRemoteURL`) to an attacker-chosen origin URL without any user confirmation. Subsequent `git fetch`/`git pull`/`git push` operations, and any credential helper interaction Desktop performs for that remote, would then target the attacker's host. Because Desktop attaches stored GitHub credentials/tokens based on host matching for API and push operations, redirecting the remote can lead to credential exposure to an attacker-controlled endpoint and/or the user unknowingly pushing to (or pulling malicious content from) a host they did not intend to trust — matching the "corruption of what the user commits/pushes" and "credential/token exfiltration" categories in scope.

### Likelihood Explanation
This requires the user to have an account configured against an endpoint the attacker can influence (e.g., a GitHub Enterprise server that is later compromised, or a network position allowing MITM of that specific enterprise host), which is a real but non-trivial precondition — it does not require local access, admin rights, or pre-existing malware, and needs no unusual user action beyond Desktop's normal periodic repository metadata refresh. This makes it a plausible but endpoint-compromise-dependent path rather than a directly internet-exploitable one.

### Recommendation
Do not treat the previously cached API value as a trust anchor for auto-rewriting the remote. Require explicit user confirmation before changing a remote URL based on API-provided data, and/or independently verify the new host against the account's already-verified endpoint/certificate rather than against another value sourced from the same channel.

### Proof of Concept
1. User adds a GitHub Enterprise account pointing at `https://ghe.example.com`, and clones `org/repo`, whose `gitHubRepository.cloneURL` is cached as `https://ghe.example.com/org/repo.git`.
2. Attacker compromises/MITMs `ghe.example.com` (e.g., after DNS takeover or during the enterprise's server compromise window).
3. On next repository metadata refresh, the attacker-controlled server returns `clone_url: https://attacker.example.com/org/repo.git`.
4. `updateRemoteUrl` computes `remoteUrlUnchanged = urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)`, which is `true` since the user never manually changed the remote, and `protocolsMatch` is `true` since both are `https:`.
5. The guard passes and `gitStore.setRemoteURL('origin', 'https://attacker.example.com/org/repo.git')` is executed with no user prompt, per the logic in [3](#0-2) .
6. All future fetch/push operations for that repository now target the attacker's host.

  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
