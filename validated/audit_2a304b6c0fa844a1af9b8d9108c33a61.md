### Title
DoS in ManualCompound.compound() due to calling IMasterMagpie.multiclaimOnBehalf with wrong parameter count - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` with three arguments [1](#0-0) , but the `IMasterMagpie` interface it depends on declares `multiclaimOnBehalf` with only two parameters: `function multiclaimOnBehalf(address[] memory _stakingTokens, address user_address) external;` [2](#0-1) . This mirrors the exact bug class from the referenced report (M-23), where a caller invokes a contract through an interface whose parameter count does not match the call site, causing every invocation to always fail.

### Finding Description
`ManualCompound.compound()` is the entry point any unprivileged user calls to claim and auto-compound their rewards from `MasterMagpie` across multiple staking pools [3](#0-2) . Internally it forwards the call to `masterMagpie` typed as `IMasterMagpie`, passing `_lps`, `_rewards`, and `msg.sender` — three arguments. The `IMasterMagpie` interface used for this call site only exposes a two-argument `multiclaimOnBehalf(address[] memory _stakingTokens, address user_address)` [4](#0-3) . If the interface used by `ManualCompound.sol` does not declare an overloaded three-parameter version matching the real `MasterMagpie` implementation, the ABI-encoded call from `ManualCompound` will not match any function selector exposed by `MasterMagpie`, causing the call to always revert (or, worse, silently hit an unintended fallback/selector collision) — the same interface-mismatch root cause identified in the external report.

### Impact Explanation
If confirmed against the deployed `MasterMagpie` implementation, this would permanently break the `compound()` feature for all users who rely on `ManualCompound` to auto-compound their claimed rewards (MGP locking, mWOM conversion, and other reward routing performed later in the same function) [5](#0-4) . This constitutes a DoS of the compounding pathway, which can cause permanent freezing/misrouting of otherwise claimable yield for any ordinary staker using this contract instead of calling `MasterMagpie` directly.

### Likelihood Explanation
Likelihood is high for any user who interacts with `ManualCompound` normally — no privileged role or malicious actor is required, exactly as in the external report where a normal user's transaction to the leverage module always failed.

### Recommendation
Verify the exact signature of `multiclaimOnBehalf` in the deployed `MasterMagpie.sol` and reconcile it with the `IMasterMagpie` interface used by `ManualCompound.sol`. Either add/confirm the matching 3-parameter overload in `IMasterMagpie.sol`, or fix the call site in `ManualCompound.sol` to match the actual on-chain function signature of `MasterMagpie`.

### Proof of Concept
1. A user calls `ManualCompound.compound(_lps, _rewards, _convertRatio, _minRec, _lockMgp)`.
2. Internally, this executes `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` [6](#0-5) .
3. The `IMasterMagpie` interface only defines a 2-parameter `multiclaimOnBehalf(address[], address)` [2](#0-1) , so the encoded call does not match `MasterMagpie`'s actual function selector for claiming rewards, causing the transaction to revert every time `compound()` is invoked.

**Note:** I was unable to fully confirm the exact signature of `multiclaimOnBehalf` as implemented in `rewards/MasterMagpie.sol` (I could only confirm its existence via grep, not read its full parameter list, before running out of tool iterations) [7](#0-6) . If `MasterMagpie.sol` actually implements a 3-parameter overload of `multiclaimOnBehalf` matching the `ManualCompound.sol` call site, this finding would not apply. Confirming this requires reading the full `multiclaimOnBehalf` function definitions in `rewards/MasterMagpie.sol`.
