### Title
Incomplete conflict-marker "postCheck" lets stray conflict-marker fragments survive reassembly and be written into files the user commits - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The Solidity report describes a class of bug where a safety "post-check" that is supposed to gate what gets returned/committed can be structurally bypassed, letting unchecked data flow through. The closest verified analog in `desktop--010` is in the Copilot-assisted merge-conflict resolution pipeline: a narrow, co-occurrence-based regex check for leftover conflict markers is applied only to each raw per-hunk string emitted by the model, and the actual file content that gets written to disk (and later committed/pushed) is produced afterward by a separate reassembly function that never re-validates its output.

### Finding Description
`parseCopilotConflictResolution` validates each hunk's `resolvedContent` with: [1](#0-0) 
This only throws when a line matching `<{7}\s` (an opening marker) AND a separate line that is exactly `={7}` are *both* present in the same hunk string. It never independently checks for a residual `>>>>>>>` closing marker, and it requires both marker types to co-occur rather than treating any single marker line as disqualifying on its own.

The actual content that ends up in the file on disk is not this raw per-hunk string — it is produced later by `reassembleResolvedFile`, which splices `hunkResolutions[...].resolvedContent` verbatim into the original file: [2](#0-1) 
There is no re-scan of the fully reassembled file for residual conflict-marker text after splicing; the only marker check that exists (`parseCopilotConflictResolution`) has already run once, earlier, on the un-reassembled fragments, and cannot see the marker check function is not invoked again in `reassembleResolvedFile` or `reassembleResolutions`: [3](#0-2) 

Structurally this mirrors the reported bug class: a "postCheck" is expected to gate what is ultimately returned/used, but the check runs against an intermediate value, while the value that is actually persisted/returned to the caller (the reassembled full file, analogous to the raw `return()` in the Solidity `fallback()`) is produced by a later step that the check never reaches.

### Impact Explanation
If a hunk's `resolvedContent` contains a lone `>>>>>>>` line (no matching `<<<<<<<`/`=======` pair in that same string), or an unbalanced/partial marker sequence that doesn't satisfy the AND condition, it passes validation untouched and is spliced into the reassembled file. That file is what the dialog offers the user to accept via "Continue Merge," and once accepted becomes the content that is written to disk and committed. This matches the "silent corruption of what the user commits or pushes" impact category — the corrupted value is the reassembled file body flowing out of `reassembleResolvedFile`.

### Likelihood Explanation
This is lower-confidence/speculative because it depends on the LLM occasionally emitting a partial/lone marker fragment in a hunk (something LLMs can plausibly do when conflicts are complex or nested, e.g. nested conflict markers from a previous unresolved merge in the fetched repository), and because I was not able to confirm within budget whether `_applyCopilotConflictResolutions` in `app-store.ts` performs any additional full-file re-validation before writing — this is the key unverified gap in this analysis.

### Recommendation
Add a final, full-file marker re-scan (checking `<<<<<<<`, `=======`, and `>>>>>>>` independently, not just as a co-occurring pair) inside or immediately after `reassembleResolvedFile`/`reassembleResolutions`, before the resolved content is offered for write, so that the check runs against the actual data that reaches disk rather than only against pre-reassembly fragments.

### Proof of Concept

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
