### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers a large eager allocation from a tiny input - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` reads `n` as a `u16` directly from the untrusted byte stream and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` variant, before any element is actually read. A ~15-byte input prefix is sufficient to force an allocation of up to `65535 * size_of::<C::F>()` bytes (~2 MiB for 32-byte scalars, ~3.7 MiB for ed448 scalars), an amplification factor on the order of 10⁵–10⁶×. This is the direct Serai analog of CVE-2025-59375 (small document → large dynamic allocation in libexpat).

### Finding Description
The deserialization of `ThresholdKeys` proceeds as follows:

1. The curve `id` is read and checked against `C::ID` — this is cheap to satisfy since `C::ID` is a fixed public constant.
2. `t`, `n`, `i` are read as three `u16` values with no bound checks at read time.
3. A one-byte `interpolation` tag is read; when it is `0` (`Interpolation::Constant`), the code executes `Vec::with_capacity(usize::from(n))` and only then attempts `C::read_F` for each element. [1](#0-0) 

`Vec::with_capacity` performs the allocation eagerly: `n = 0xFFFF` reserves space for 65535 field elements immediately, from only 2 attacker-controlled bytes. The subsequent per-element reads fail on a truncated stream, but the allocation has already happened; an attacker sending just the prefix (`id_len || id || t || n=0xFFFF || i || 0x00`) and then stalling/aborting gets the full allocation per invocation. Repeating or parallelizing the calls (e.g., feeding many such payloads to any service that deserializes `ThresholdKeys` from network/RPC/storage bytes) multiplies memory pressure arbitrarily.

Note the contrast with `coordinator/tributary/src/transaction.rs`, which checks `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` before allocating [2](#0-1) , and `networks/ethereum/src/machine.rs`, which explicitly chunked reads because "a valid DoS would be to claim a 4 GB data is present for only 4 bytes" [3](#0-2) . `ThresholdKeys::read` has no equivalent guard.

### Impact Explanation
Unprivileged memory-allocation amplification: a handful of well-formed prefix bytes forces multi-megabyte allocations. An attacker able to submit serialized `ThresholdKeys` to a validator/processor endpoint (key import, backup restore, DKG-related API, or any path plumbing `ThresholdKeys::read` to `io::Read` over untrusted data) can exhaust memory or trigger OOM kills, denying service. The allocation is freed on parse error, but concurrent requests and allocator fragmentation make sustained pressure practical.

### Likelihood Explanation
Likelihood is moderate. The trigger requires a caller that deserializes `ThresholdKeys` from attacker-influenced bytes; `ThresholdKeys::read` is a public API in scope and the prefix (`C::ID`, tag byte) is trivially constructible since the curve ID is a public constant. `n` need only be ≤ `u16::MAX` at allocation time — the `ThresholdParams::new(t, n, i)` validation happens only after the allocation and reads. I could not exhaustively enumerate every call site of `ThresholdKeys::read` in this pass, so reachability depends on deployment surface, but the pattern is exactly the class the advisory describes.

### Recommendation
Do not size allocations from untrusted length fields before validating them. In `crypto/dkg/src/lib.rs`:

- Validate `t`, `n`, `i` first (e.g., call `ThresholdParams::new(t, n, i)` or enforce `n` against a protocol maximum such as `MAX_KEY_SHARES_PER_SET`) *before* the `Interpolation::Constant` branch.
- Replace `Vec::with_capacity(n)` with `Vec::new()`/`push` growth, or cap the eager capacity at a small constant — actual elements are read anyway, so capacity hints buy nothing.

### Proof of Concept
Conceptual byte stream for `C = Ristretto`-family or any `Ciphersuite` whose `C::ID` is known:

```rust
// Prefix-only payload: forces 65535 * size_of::<C::F>() bytes of allocation
// then the first C::read_F hits EOF — allocation already committed.
let mut payload = Vec::new();
payload.extend(&(C::ID.len() as u32).to_le_bytes());  // id_len
payload.extend(C::ID);                              // id (public constant)
payload.extend(&1u16.to_le_bytes());                // t
payload.extend(&u16::MAX.to_le_bytes());            // n = 65535  -> Vec::with_capacity(65535)
payload.extend(&1u16.to_le_bytes());                // i
payload.push(0);                                    // interpolation = Constant
// no further bytes needed; ~15 + C::ID.len() bytes total
let _ = ThresholdKeys::<C>::read(&mut &payload[..]); // Err(EOF) after ~2 MiB alloc
```

Spam N copies concurrently → N × ~2 MiB (or ~3.7 MiB for `ed448`) of churned heap from ~20 bytes each, matching the CVE-2025-59375 shape of tiny input / large allocation.
