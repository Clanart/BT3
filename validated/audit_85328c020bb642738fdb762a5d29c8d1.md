### Title
Unsanitized PR fork `clone_url` passed to `git remote add`, enabling `ext::` transport command execution on checkout - (File: `app/src/lib/git/remote.ts`)

### Summary
`addRemote` in `app/src/lib/git/remote.ts` passes an unsanitized URL straight to Git as a positional argument, with no scheme allow-listing performed by Desktop anywhere in the pull-request checkout path.

### Finding Description
`addRemote` simply forwards the caller-supplied `url` to Git: [1](#0-0) 

That `url` originates, unsanitized, from the GitHub API's pull-request payload. `storePullRequests` in `pull-request-store.ts` takes `pr.head.repo` (attacker-controlled when the PR is opened from a fork the attacker controls) and stores it as the head `GitHubRepository`'s `cloneURL` with no scheme/format validation: [2](#0-1) 

When the user clicks "Checkout this PR", `_checkoutPullRequest` → `_findPullRequestBranch` in `app-store.ts` looks for a matching remote and, if none exists, calls `addRemote(repository, forkRemoteName, headCloneUrl)` with that value verbatim, then fetches it: [3](#0-2) [4](#0-3) 

`urlMatchesRemote`/`parseRemote` (used to detect an existing remote) and `addRemote` itself perform no scheme validation — there is nothing in the codebase (`repository-matching.ts`, `remote.ts`, `environment.ts`) that rejects non-`http(s)`/`ssh`/`git` schemes such as `ext::` before the value reaches `git remote add` and later `git fetch`. `envForRemoteOperation`/`envForProxy` only special-case `http(s)` for proxy resolution and do nothing to restrict allowed transports: [5](#0-4) 

Because Desktop invokes Git as an argv array (via dugite, no shell), classic shell-metacharacter injection isn't possible, but Git's own `ext::` transport helper is itself a documented way to spawn an arbitrary command when Git connects to that "remote" — this is inherent to Git, not to Desktop's spawn mechanism. Whether this actually executes depends on Git's own `protocol.ext.allow` / `GIT_PROTOCOL_FROM_USER` policy, which historically defaults to allowing `ext::` for top-level, directly-invoked commands (as opposed to recursive submodule operations, which Git disables by default post CVE-2017-14867). Desktop does not set `GIT_PROTOCOL_FROM_USER=0` or `protocol.ext.allow=never` anywhere in `environment.ts`, `core.ts`, or the trampoline environment, so it relies entirely on the end-user's locally installed Git binary/version/config for this protection rather than enforcing it itself.

### Impact Explanation
If the resolved Git installation's protocol policy permits `ext::` for a directly invoked `fetch`/`remote add`, an attacker who opens a pull request from a fork (or otherwise causes `pr.head.repo.clone_url` to be an `ext::` URL) can achieve arbitrary command execution on the victim's machine once they use Desktop's "Checkout this PR" feature. This would be full local code execution.

### Likelihood Explanation
This requires the "Checkout this PR" action, which is a normal Desktop workflow. However, real-world exploitability depends entirely on the Git binary and its version/configuration on the victim machine (Git's own default protocol allow-list) — this is not something demonstrably enforced or broken purely within Desktop's TypeScript code. I could not find, within this repository, any explicit hardening (`protocol.ext.allow`, `GIT_PROTOCOL_FROM_USER`) either enforcing or disabling this, so it is uncertain whether current shipped Git versions/config used by Desktop actually permit `ext::` execution in this flow without further verification against the exact bundled/embedded Git version and its compiled-in defaults, which I don't have visibility into from the indexed source alone.

### Recommendation
- Validate/allow-list the scheme of any GitHub API-derived `clone_url`/`ssh_url` (accept only `https://`, `http://`, `ssh://`, `git://`, or `scp`-like `user@host:path` forms) before calling `addRemote`, rejecting anything else (in particular `ext::`, `fd::`, or values starting with `-`).
- Explicitly set `GIT_PROTOCOL_FROM_USER=0` (or `protocol.ext.allow=never`/`protocol.allow=never` with an explicit allow-list for `http`, `https`, `ssh`, `git`) in the environment used for all Desktop-initiated Git operations (`envForRemoteOperation`, `core.ts` git spawn options) so that Desktop does not rely on the ambient Git installation's default policy.

### Proof of Concept
1. Attacker forks a target repository and opens a pull request whose `head.repo.clone_url` (as returned by the GitHub API for that PR) is `ext::sh -c touch\ /tmp/pwned`.
2. Victim opens the PR in GitHub Desktop and clicks "Checkout this PR".
3. `_checkoutPullRequest` → `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, 'ext::sh -c touch\\ /tmp/pwned')`, adding the malicious URL as a remote, then calls `_fetchRemote`, causing Git to invoke the `ext::` transport helper and execute the attacker's command — contingent on the local Git's protocol policy allowing `ext::` for this invocation.

I could not fully verify this last contingency (Git's exact default `protocol.ext.allow` behavior for a top-level, non-submodule `fetch`/`remote add` versus its behavior for submodules) directly from the indexed source, since that policy lives in Git itself, not in this repository's code; a background Devin session with access to build/run the app against the actually-bundled Git binary would be needed to confirm real-world exploitability end-to-end.

export async function addRemote(

}
