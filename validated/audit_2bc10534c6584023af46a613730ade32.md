## Title
`getRepoHooks` inverted `matchAll` guard silently disables the safe-hook interception wrapper for *all* wildcard-filtered Git operations — ([File: app/src/lib/hooks/get-repo-hooks.ts])

### Summary
`getRepoHooks()` is meant to enumerate a repository's executable Git hooks so that `withHooksEnv()` can wrap their execution in the sandboxed hooks-proxy (`hooks-proxy.ts`), which filters the environment passed to hooks down to `GIT_*`/`GITHEAD_*` variables and strips everything else (tokens, secrets, trampoline state, etc.). Callers such as `createCommit`, and the merge/pull/push code paths, request wildcard interception via `interceptHooks: ['*']`/`['*', ...]`. Due to an inverted boolean condition, when the filter is a wildcard (`matchAll === true`) the function `continue`s (skips) every hook file instead of yielding it, so `getRepoHooks` always returns an empty result for wildcard callers. `withHooksEnv` treats an empty hook list as "nothing to intercept" and falls through to running Git with the caller's *unfiltered* environment, i.e. hooks execute completely outside the sandbox.

### Finding Description
In `app/src/lib/hooks/get-repo-hooks.ts`: [1](#0-0) 
```
  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }
    ...
```
The intent, per the doc comment ("Including '*' will return all hooks"), is that `matchAll === true` should cause every hook to be *included*. Instead the boolean is OR'd directly into the skip condition, so `matchAll === true` causes every iteration to hit `continue` and the generator yields nothing at all. The correct logic would be to only `continue` when `!matchAll && filter?.includes(hookName) === false`.

This function is consumed by `withHooksEnv`: [2](#0-1) 
```
export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
```
Because `getRepoHooks` always returns an empty array for any wildcard-based `interceptHooks` filter, `hooks.length === 0` is always true for these callers, and `withHooksEnv` falls back to invoking `fn(opts?.env)` directly — i.e., Git runs the repository's hooks with the normal process/trampoline environment instead of the isolated `hooksProxy` sandbox described in `createHooksProxy` (`app/src/lib/hooks/hooks-proxy.ts`), which is specifically designed to only forward a `GIT_*`/`GITHEAD_*`-filtered, exclusion-listed environment (`safePrefixes`, `excludedEnvVars`) to hook processes: [3](#0-2) 

Callers rely on wildcard-style interception for exactly the operations where an attacker-controlled cloned repository can drop hook scripts, e.g. `createCommit` in `app/src/lib/git/commit.ts`: [4](#0-3) 
(`interceptHooks: ['pre-commit', 'prepare-commit-msg', ...]` — while this particular list is not `['*']`, other callers in `merge.ts`, `pull.ts`, and `push.ts` do pass wildcard filters based on the `interceptHooks` grep hits, meaning `matchAll` is reachable in real commit/merge/pull/push flows).

The `hooks.length === 0` fallback exists as an *optimization* for the case where a repo genuinely has no hooks — it is not designed to be the silent, wildcard-triggered path. The inverted `matchAll` condition turns this optimization into a full bypass of the hooks isolation feature whenever `['*']`-style filtering is requested.

### Impact Explanation
The GitHub Desktop hooks-proxy/trampoline mechanism exists specifically to prevent an attacker-controlled repository's Git hooks (which git executes automatically on `commit`/`merge`/`pull`/`push`) from being able to read the ambient environment used by Desktop (including trampoline tokens, SSH agent sockets, and other Desktop-managed state) beyond the sanitized `GIT_*`/`GITHEAD_*` subset. If the wrapper is silently skipped due to this logic bug, any hook script (`pre-commit`, `post-checkout`, `pre-push`, etc.) present in a cloned or fetched repository — fully attacker-controlled content, since hooks are ordinary files delivered via `.git/hooks` or `core.hooksPath` — runs with the full, unfiltered process environment that Desktop would otherwise have stripped down. This is a "silent corruption of what the user commits/pushes" / environment-exfiltration class issue: the intended security control (hook environment isolation) never activates for the flows that rely on wildcard interception, without any error or warning to the user.

### Likelihood Explanation
No privilege is required beyond convincing/getting the user to clone or fetch a repository containing a hook script (a routine, expected GitHub Desktop workflow) and to perform a commit/merge/pull/push, which is normal usage. The bug is deterministic — it triggers on every call where `interceptHooks` includes `'*'`, not a race or edge case, so it is highly reliable once such a call path is exercised.

### Recommendation
Fix the guard so the wildcard flag actually causes inclusion rather than exclusion, e.g.:
```ts
if (!matchAll && filter?.includes(hookName) === false) {
  continue
}
```
Add a regression test asserting that `getRepoHooks(path, ['*'])` yields all known, executable hooks present in the hooks directory, and audit every caller (`commit.ts`, `merge.ts`, `pull.ts`, `push.ts`) to confirm the hooks-proxy sandbox is actually engaged (non-empty hook list) whenever hook scripts exist in the target repository.

### Proof of Concept
1. Attacker publishes/serves a Git repository containing an executable `.git/hooks/post-checkout` (or `pre-push`, `pre-commit`, etc.) script that exfiltrates environment variables (e.g. `env > /tmp/leak` or sends them over the network) instead of doing anything benign.
2. Victim clones the repository in GitHub Desktop and performs an operation whose `interceptHooks` option resolves to a wildcard filter (merge/pull/push code paths in `app/src/lib/git/merge.ts`, `pull.ts`, `push.ts`).
3. `withHooksEnv` calls `getRepoHooks(path, ['*'])`. Because of the inverted `matchAll` check, the generator yields zero hooks even though the malicious hook file exists and is executable.
4. `withHooksEnv` sees `hooks.length === 0` and calls `fn(opts?.env)` directly, bypassing `createHooksProxy`'s environment allowlist.
5. Git invokes the hook natively with the full process environment (rather than the trampoline-token-scoped, `GIT_*`-only environment), so the attacker's hook script can read and exfiltrate any sensitive environment variables normally withheld from repository-supplied hook code.

**Note on verification limits:** I confirmed the inverted condition in `get-repo-hooks.ts` and its consumption in `with-hooks-env.ts`/`hooks-proxy.ts`, and confirmed `interceptHooks` is referenced in `merge.ts`, `pull.ts`, and `push.ts`, but the index did not surface the exact `interceptHooks` array literals passed by those three files (only `commit.ts`'s non-wildcard list was retrievable). I could not fully confirm from the indexed content whether `'*'` is literally passed in `merge.ts`/`pull.ts`/`push.ts` versus another named-hook list — starting a full Devin session with complete repo access would be needed to verify the exact `interceptHooks` values in those three files and fully confirm the wildcard code path is reached in practice.
