## Title
Block-reward `stake > total_active_stake` clamp in `calculate_block_reward` distributes fewer/incorrect delegator shares during reward recalculation - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
The external report's bug class is a share/value calculation where the numerator ("addedBalance") and the denominator used for the pro-rata split ("cumulativeValue") are computed from inconsistent bases — the denominator implicitly double-counts or otherwise diverges from the numerator's basis, corrupting the payout ratio. The closest local analog is `calculate_block_reward` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, where the per-delegator numerator (`stake`, from `delegation_effective_stake`) and the shared denominator (`total_active_stake`, from `RewardEpochDelegatedStakes`) are drawn from two different snapshots of stake state that the code itself documents as capable of diverging.

### Finding Description
`calculate_block_reward` computes each delegator's share of `pending_delegator_rewards` as:
```
stake * pending_delegator_rewards / total_active_stake
```
`total_active_stake` is read from a fixed epoch-end snapshot (`RewardEpochDelegatedStakes`), while `stake` is computed live via `delegation_effective_stake(delegation, rewarded_epoch, stake_history, ...)`. The function's own comment acknowledges the two values can be inconsistent: "During recalculation, if stake account has already received rewards, it's possible to have `stake > total_active_stake`" [1](#0-0) .

This is structurally the same defect class as the report: a per-account "contribution" value (`stake`, analogous to `addedBalance`) is compared against a denominator (`total_active_stake`, analogous to `cumulativeValue`) that was not computed on a mutually consistent basis with the numerator. In the LP report, `cumulativeValue` wrongly included the depositor's own just-added balance, skewing the ratio; here, `stake` can already include reward lamports that were added to the delegation after the `total_active_stake` snapshot was taken, which skews the ratio in the opposite direction (numerator inflated relative to the fixed denominator), producing `stake/total_active_stake > 1`.

The existing "guard" is only a saturating cap:
```rust
(pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
    .try_into()
    .unwrap_or(u64::MAX)
    .min(pending_delegator_rewards)
``` [2](#0-1) 

This clamp only prevents `u64` overflow and prevents a single delegator from being paid more than the vote account's total `pending_delegator_rewards`; it does not restore a correct proportional split among the several delegators sharing that vote account's `pending_delegator_rewards`. If one delegation's `stake` is inflated relative to the fixed `total_active_stake` denominator (e.g., because it has already accrued rewards from a previous recalculation pass while other delegations under the same vote account have not), that delegation is over-paid relative to its true share, and since `pending_delegator_rewards` is a fixed pool being drawn down per-delegator without re-normalizing the denominator, the remaining delegators effectively receive less than their fair share out of the same pool — mirroring the "other users get less than they should" outcome in the original report.

The call comment itself flags this is exercised specifically "during recalculation" [3](#0-2) , i.e., whenever `calculate_block_reward` / `calculate_stake_rewards_and_commissions` is invoked more than once for the same `rewarded_epoch` against updated account state (e.g., epoch-boundary recomputation flows using `EpochRewardCalculateParamInfo`/`get_epoch_params_for_recalculation`), confirming this is a real, reachable code path rather than a purely theoretical one.

### Impact Explanation
If block-revenue-sharing reward distribution is recalculated for an already-partially-rewarded epoch, delegators under the same vote account can receive incorrect, non-proportional shares of `pending_delegator_rewards`: some get more than their fair share (bounded only by the total pool, not by their true proportion) and others correspondingly get less. This is a fund-accounting correctness bug within stake/runtime reward distribution — the class of issue explicitly in scope (accounts/runtime fund-loss/false-execution class).

### Likelihood Explanation
This requires the block-reward recalculation path to be exercised with a delegation whose live `stake` has already absorbed rewards while the `RewardEpochDelegatedStakes` denominator snapshot has not been correspondingly updated, a scenario the code comment explicitly anticipates ("during recalculation ... it's possible to have `stake > total_active_stake`"). The precise external trigger conditions (how/when `calculate_block_reward` is invoked twice for the same `rewarded_epoch`) could not be fully traced within the available tooling/time, so likelihood is assessed as at least plausible/moderate rather than fully proven end-to-end.

### Recommendation
Ensure `stake` and `total_active_stake` are always computed from the same consistent snapshot when calling `calculate_block_reward`, rather than mixing a live/possibly-already-rewarded `delegation_effective_stake` value with a stale `RewardEpochDelegatedStakes` denominator. If a mismatch is unavoidable across recalculation passes, cap `stake` at `total_active_stake` (not just cap the resulting payout at `pending_delegator_rewards`) so that the proportional split among all delegators of the same vote account remains fair, and add an explicit invariant/assertion that sum of per-delegator payouts under one vote account does not exceed `pending_delegator_rewards` in a way that silently redistributes the shortfall away from smaller/normal delegators.

### Proof of Concept
Could not be fully constructed/verified within the available time — the exact caller sequence that invokes `calculate_block_reward` twice for the same `rewarded_epoch` (the "recalculation" path referenced in the code comment) was not traced to a concrete external trigger in this session. This is noted as an open item requiring further code-path tracing (e.g., through `get_epoch_params_for_recalculation` / `calculate_stake_rewards_and_commissions` callers) to confirm exploitability end-to-end.
