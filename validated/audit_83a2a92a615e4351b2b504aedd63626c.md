## Title
Conflict markers inside legitimate hunk content cause silent mis-splicing of Copilot resolutions into committed file - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`extractConflictHunks` scans a conflicted file for `<<<<<<<` / `=======` / `>>>>>>>` markers using plain per-line regex matching with no escaping/validation of the surrounding content. If either side of a real conflict happens to contain a line that coincidentally matches one of these marker regexes (e.g. a Markdown/changelog divider of exactly seven `=` characters, or a pasted diff snippet with a `>>>>>>>` line), the parser terminates the "ours"/"theirs" collection early at the wrong line. The truncated/garbled hunk is what gets sent to the Copilot model, and the model's resolution is computed against that corrupted view. `reassembleResolvedFile` then splices the model's resolution back in purely by **positional order** (`hunkIndex`) against the *real* marker boundaries in the file, with no verification that the spliced-in content corresponds to what was actually replaced. The result is that legitimate lines from either side can be silently dropped from the final committed content, with no error, no skip reason, and no warning surfaced to the user.

### Finding Description
- `extractConflictHunks` collects "ours" content by scanning forward until it hits a line matching `baseMarker` or `separatorMarker`, and "theirs" content until it hits `theirsMarker` — with no check that these are actually the markers belonging to the current hunk vs. incidental text: [1](#0-0) 
- The marker regexes are extremely permissive (any line that is exactly 7 `<`, `|`, `=`, or `>` characters, optionally followed by whitespace/text): [2](#0-1) 
- The extracted hunks (based on this potentially mis-parsed boundary) are what get sent to the model in the prompt: [3](#0-2) 
- After the model responds, `reassembleResolvedFile` independently re-scans the *same raw file* for real marker blocks and splices in `hunkResolutions[hunkIndex]` purely by array order, trusting that the model's per-hunk resolution corresponds exactly to the true marker-delimited region it is replacing: [4](#0-3) 

Because extraction and reassembly do not use a shared, verified hunk-boundary representation (e.g. line offsets recorded once and reused), any content-level ambiguity introduced during extraction propagates invisibly: the model sees a truncated/garbled version of "ours" or "theirs," but reassembly still replaces the *entire real* marker-delimited block with the model's answer. Lines the model never saw (because extraction cut them off early) are silently discarded from the committed file, and the code review path documented in `copilot-conflicts-dialog.tsx` (which gates "Continue" on the presence/absence of conflict markers, not on content correctness) will treat this as a fully resolved file: [5](#0-4) 

### Impact Explanation
This directly maps to the "silent corruption of what the user commits or pushes" impact category. An attacker who controls one side of a merge (e.g. a malicious PR branch a maintainer merges, or a branch fetched from a shared/compromised remote) can craft file content that is guaranteed to conflict with the victim's branch and that contains an innocuous-looking line (e.g. a Markdown `=======` divider, a YAML front-matter fence, or a pasted diff/patch snippet with `>>>>>>>`-shaped lines) inside the conflicting region. When the victim uses the built-in Copilot conflict resolution feature to resolve the merge, the resulting commit can silently drop legitimate code/content from either side without any error, size-skip warning, or leftover conflict markers to alert the user — the file is reported as fully resolved.

### Likelihood Explanation
Exploitation requires the victim to (1) merge/rebase/cherry-pick a branch controlled by the attacker that produces a real conflict, and (2) use the Copilot "Resolve conflicts" feature on that merge — both of which are normal, expected Desktop usage. Crafting file content with an incidental `=======`/`>>>>>>>`/`|||||||`-matching line is trivial and doesn't require any unusual or suspicious-looking payload (common in Markdown/changelog files, ASCII dividers, pasted diffs, or POD/YAML documents), making the trigger condition realistic rather than contrived.

### Recommendation
- Track hunk boundaries as concrete line ranges (start/end indices) at extraction time and pass those same indices through to reassembly, instead of re-deriving/re-matching marker positions independently and correlating purely by array order.
- When scanning for `=======`/`>>>>>>>` while collecting "ours"/"theirs" content, require that the *very next* non-matching pattern after a candidate separator is a valid closing `>>>>>>>` before committing to the boundary; otherwise treat the candidate line as ordinary content and keep scanning (mirrors the "look-ahead" validation already implemented in `reassembleResolvedFile`, but currently missing from `extractConflictHunks`'s incremental collection loops).
- Add an invariant check before splicing: verify that concatenating `contextBefore + oursContent (+ baseContent) + theirsContent + contextAfter` for a given hunk reconstructs exactly the corresponding span of `rawContent`; if not, skip that file with a `skippedReason` rather than silently committing a possibly-corrupted resolution.

### Proof of Concept
1. Attacker pushes a branch where a file (e.g. `CHANGELOG.md`) modifies a section that will conflict with the victim's branch, and includes a line of exactly `=======` (7 equals) inside the *theirs* content of the conflicting hunk, e.g.:
```
<<<<<<< HEAD
victim's real content line A
victim's real content line B
=======
attacker line 1
=======
attacker line 2 (should be part of "theirs")
>>>>>>> attacker-branch
```
2. Victim merges the attacker branch, gets this conflict, and opens Desktop's "Resolve with Copilot" flow.
3. `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:200-237`) stops collecting "theirs" content-scanning logic no differently — but the *first* embedded `=======` is what actually terminates "ours"-collection at line 208-211 during the initial ours-scan pass, so `attacker line 1` becomes mis-classified as the start of "theirs" content while `attacker line 2` and the real trailing content are parsed incorrectly relative to what a human/model expects.
4. The model resolves conflicts based on this incorrect view of "ours" vs. "theirs" content.
5. `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:559-596`) finds the *real* `<<<<<<<` ... `>>>>>>>` block (using the correct/full boundary) and replaces the **entire** block with the model's resolution — which was computed from the mis-split data — silently dropping/altering content the model never actually saw as distinct from the other side.
6. The resulting file has no conflict markers left (`conflictMarkerCount === 0`), so the "Continue Merge" gate treats it as fully resolved, and the corrupted content is committed without any warning.
