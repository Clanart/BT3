Based on my research, I found a concrete analog to the report's bug class ("state persisted as a side effect of an operation, but the corresponding cleanup only fires on a narrow subset of failure paths, allowing stale/unvalidated state to be replayed later").

### Title
Stale SSH key passphrase can be permanently persisted to the OS keychain without confirmation the credential was ever valid - (File: `app/src/lib/trampoline/trampoline-askpass-handler.ts`)

### Summary
Similar to the reported IBC bug — where a commitment is written and consumed by a callback but only deleted on one of two code paths, allowing replay — GitHub Desktop's SSH askpass flow writes an entered SSH key passphrase to the OS keychain immediately when the user opts to "remember" it, but only deletes that entry on two specific dugite error codes (`SSHAuthenticationFailed`, `SSHPermissionDenied`). Any other failure mode of the underlying git/ssh process (e.g. connection reset, generic exit code, a malicious/MITM SSH remote that fails in a way dugite doesn't classify as those two errors) leaves the unvalidated passphrase permanently stored and later replayed to subsequent operations against the same key.

### Finding Description
When git needs an SSH key passphrase, `handleSSHKeyPassphrase` in `app/src/lib/trampoline/trampoline-askpass-handler.ts` (lines 55-109) is invoked as the askpass callback: [1](#0-0) 

If the user chooses to store the passphrase, `setSSHKeyPassphrase(operationGUID, keyPath, passphrase)` is called, which (via `ssh-credential-storage.ts`) writes it to the OS keychain immediately, before the git operation has completed or its result is known: [2](#0-1) 

Cleanup only happens in `withTrampolineEnv`'s `catch` block in `app/src/lib/trampoline/trampoline-environment.ts`, and only when the caught error matches `isSSHAuthFailure`, i.e. `SSHAuthenticationFailed` or `SSHPermissionDenied`: [3](#0-2) [4](#0-3) 

This mirrors the report's broken invariant exactly: an action is committed eagerly (store commitment / persist credential), and the corresponding "cleanup" (delete commitment / delete credential) is only implemented for one class of outcomes, not all of them. If a malicious or MITM'd SSH remote/proxy terminates the connection or returns an error that dugite maps to a `GitError` other than those two specific codes (e.g., a generic exit/connection error), the passphrase the user just entered is never removed from the keychain, even though it was never proven to be a valid credential for that host/key.

### Impact Explanation
The stale, unvalidated passphrase persists indefinitely in the OS keychain and will be transparently returned by `getSSHKeyPassphrase(keyPath)` on every subsequent SSH operation against that key file, without any further prompt to the user. This is a credential-state corruption bug: what the user believes is a validated, remembered secret is instead an artifact of a single failed/interrupted session with an attacker-influenced remote. Concretely, an attacker who controls a git remote/proxy endpoint (e.g. by MITM-ing an SSH clone/fetch, or hosting a repository whose SSH handshake is deliberately disrupted after eliciting the passphrase prompt) can trigger passphrase capture-and-store while causing the actual git operation to fail in a way that bypasses cleanup, leaving Desktop believing a specific keychain-stored value is the correct passphrase for that key going forward.

### Likelihood Explanation
This requires the user to have chosen to "remember" the passphrase for the given key at the time of the malicious/interrupted operation, and requires the failure to surface as something other than `SSHAuthenticationFailed`/`SSHPermissionDenied` (plausible for network-level MITM/proxy interference, since many SSH client failure modes are not authentication-specific). It does not require local access, admin rights, or social engineering beyond the normal act of cloning/fetching from an attacker-influenced remote, which is within the accepted attacker model.

### Recommendation
Align the cleanup logic with the report's recommendation: either (a) defer persisting the passphrase to the keychain until the overall git operation has definitively succeeded (matching the doc comment in `withTrampolineEnv`, which already claims this is the intended behavior), rather than writing it eagerly inside the askpass handler; or (b) broaden the `finally`/`catch` cleanup in `withTrampolineEnv` to delete the pending SSH credential on *any* non-success outcome, not just the two specific SSH auth error codes.

### Proof of Concept
1. Attacker hosts (or MITMs) an SSH git remote.
2. Victim runs a Desktop operation (clone/fetch/push) against a private key that requires a passphrase, and opts to "remember" the passphrase when prompted (`handleSSHKeyPassphrase`, `storeSecret: true`).
3. `setSSHKeyPassphrase` immediately persists the passphrase to the OS keychain.
4. The attacker's server aborts/resets the SSH connection in a way that produces a git/dugite error other than `SSHAuthenticationFailed`/`SSHPermissionDenied` (e.g., connection reset, generic protocol error).
5. `withTrampolineEnv`'s catch block's `isSSHAuthFailure(e)` check evaluates false, so `deleteMostRecentSSHCredential` is never called; only `removeMostRecentSSHCredential` (in-memory map, not keychain) runs in `finally`.
6. The unvalidated passphrase remains permanently in the OS keychain and is auto-supplied on all future operations against that key via `getSSHKeyPassphrase`.

Note: I was unable to fully verify every dugite error code path that could produce a non-`SSHAuthenticationFailed`/`SSHPermissionDenied` failure from a malicious SSH server within the indexed code, so the exact triggering error condition would need confirmation with a live git/ssh test; this assessment is based on the cleanup logic's narrow error-matching as shown in the cited code.
