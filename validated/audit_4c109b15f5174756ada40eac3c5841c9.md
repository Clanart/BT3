### Title
Missing panic recovery when a node processes an untrusted proposed block's transactions - ([File: blockchain/state_processor.go], [File: work/execution.go])

### Summary
IoTeX's fix (#4920) extended panic recovery from the block-minting path to the block-validation path (`ValidateBlock`), because a proposed block's transactions are untrusted input and a panic during their processing could crash the validating node. In this Kaia codebase, the exact asymmetry exists: the block-*proposing* path (`backend.SubmitTransactions`) is wrapped in a `recover()` that turns any panic into a safe "skip this round" outcome, but the block-*importing/validating* paths that execute an untrusted peer's transactions — `StateProcessor.Process` (via `BlockChain.insertChain`) and `DefaultExecutor.ExecuteTransactions` (the istanbul speculative-execution path for a received PRE-PREPARE) — have no panic recovery at all.

### Finding Description
`consensus/istanbul/backend/backend.go`'s `SubmitTransactions` wraps the whole propose/execute/finalize/seal pipeline in a goroutine with `recover()`: [1](#0-0) 

By contrast, when a node processes a block it did *not* propose — either while importing a block in `BlockChain.insertChain` (`bc.processor.Process(...)`, i.e. `StateProcessor.Process`) or while speculatively executing a received PRE-PREPARE proposal (`DefaultExecutor.ExecuteTransactions`) — there is no equivalent `recover()`: [2](#0-1) [3](#0-2) 

Both paths call `BlockChain.ApplyTransaction` per transaction in a block whose contents (calldata, gas parameters, account keys, etc.) are supplied by a remote proposer/peer, not by the local node. `insertChain` invokes `Process` directly with no panic guard: [4](#0-3) 

And the istanbul core's PRE-PREPARE handler calls `backend.Verify` (structural checks only — tx-root, gas price vs base fee, blob sidecar) but never runs full EVM execution before entering the `Prepared`/`Commit` phases; the actual transaction execution against `ApplyTransaction`/EVM happens via `ExecuteTransactions`, which is unguarded: [5](#0-4) 

If any transaction inside a maliciously-crafted or buggy proposed block triggers a panic somewhere in the deep call stack of `ApplyTransaction` → `TransitionDb` → EVM/precompile execution (e.g., a nil-pointer dereference, unexpected type assertion, or index-out-of-range in a rarely-exercised code path — the same class of Go runtime panics the upstream IoTeX fix was guarding against), that panic propagates uncaught out of `Process`/`ExecuteTransactions`.

### Impact Explanation
An uncaught panic here would crash the goroutine that is running block insertion or speculative pre-prepare execution. For `insertChain`, this happens under `bc.mu.Lock()`, called from the main chain-insertion path used by every full node syncing or importing new blocks; a crash here takes down the node process (a node-wide DoS triggerable by any adversarial proposer/peer able to get a malformed block accepted past header/body checks but not past state execution). This is a "single crafted block from an untrusted proposer crashes the receiving node" class bug, directly parallel to what #4920 fixed. Because Kaia is a validator/BFT chain, a proposer role is attainable by any staked validator, and the panic would occur on every honest validating node processing that block — a state-divergence/liveness risk (validators crash instead of rejecting the block with an error) rather than silent data corruption.

### Likelihood Explanation
Likelihood depends on the actual existence of a panic-triggering code path reachable from `ApplyTransaction`/state-transition/EVM execution with attacker-controlled inputs. I was not able to identify a concrete, provable panic trigger within the available indexed code (e.g., a specific nil dereference or type assertion reachable from an externally-crafted transaction) — the analog is architectural (missing `recover()` at the validation boundary) rather than a demonstrated crash. Given the codebase already treats this class of risk as real enough to guard the *minting* path with `recover()`, the omission on the *validating* path is a plausible, but unconfirmed without deeper fuzzing/code-path analysis, gap.

### Recommendation
Wrap `StateProcessor.Process` (or its caller in `BlockChain.insertChain` around `bc.processor.Process(...)`) and `DefaultExecutor.ExecuteTransactions` in `recover()` handlers that convert any panic into a returned error, exactly mirroring the pattern already used in `SubmitTransactions`. Ensure any partially-mutated `statedb`/`ExecutionResult` is discarded on panic (as it already is on ordinary error returns), so the block is rejected without leaking partial state, and the commit/write-block path remains fatal-on-error as before.

### Proof of Concept
Not established — this analog is based on structural/code-review evidence of the panic-recovery asymmetry between the propose path (`SubmitTransactions`, guarded) and the validate/import paths (`StateProcessor.Process`, `DefaultExecutor.ExecuteTransactions`, unguarded), not on a demonstrated concrete panic trigger from a crafted transaction. A working PoC would require identifying a specific runtime panic reachable via `ApplyTransaction`/`TransitionDb`/EVM execution from attacker-supplied transaction data, which was not found within the indexed code available to this analysis.

func (p *StateProcessor) Process(block *types.Block, statedb *state.StateDB, cfg vm.Config) (types.Receipts, []*types.Log, uint64, []*vm.InternalTxTrace, ProcessStats, error) {
	var (
		receipts         types.Receipts
		usedGas          = new(uint64)
		header           = block.Header()
		allLogs          []*types.Log
		internalTxTraces []*vm.InternalTxTrace
		processStats     ProcessStats
	)

	p.InitializeState(header, statedb)

	// Extract author from the header
	author, _ := p.bc.sealer.Author(header) // Ignore error, we're past header validation

	processStats.BeforeApplyTxs = time.Now()
	// Iterate over and process the individual transactions
	for i, tx := range block.Transactions() {
		statedb.SetTxContext(tx.Hash(), block.Hash(), i)
		receipt, internalTxTrace, err := p.bc.ApplyTransaction(p.config, &author, statedb, header, tx, usedGas, &cfg)
		if err != nil {
			return nil, nil, 0, nil, processStats, err
		}
		receipts = append(receipts, receipt)
		allLogs = append(allLogs, receipt.Logs...)
		internalTxTraces = append(internalTxTraces, internalTxTrace)
	}

func (e *DefaultExecutor) ExecuteTransactions(txs []*types.Transaction) (*consensus.ExecutionResult, error) {
	e.mu.Lock()
	defer e.mu.Unlock()

	if !e.initialized {
		return nil, ErrExecutorNotInitialized
	}

	// Pre-tx hooks (EIP-2935, kaiax module pre-hooks, etc.)
	e.chain.Processor().InitializeState(e.header, e.state)

	// Extract the block proposer from the header seal — must match
	// StateProcessor.Process so COINBASE and reward distribution are identical.
	// Using e.nodeAddr here would be wrong: the local validator is not
	// necessarily the proposer of this block.
	author, _ := e.chain.Sealer().Author(e.header)

	var (
		receipts types.Receipts
		allLogs  []*types.Log
		usedGas  = new(uint64)
	)

	for i, tx := range txs {
		e.state.SetTxContext(tx.Hash(), common.Hash{}, i)
		receipt, _, err := e.chain.ApplyTransaction(
			e.config, &author, e.state, e.header, tx, usedGas, &vm.Config{},
		)
		if err != nil {
			return nil, fmt.Errorf("tx %d (%s): %w", i, tx.Hash().Hex(), err)
		}
		receipts = append(receipts, receipt)
		allLogs = append(allLogs, receipt.Logs...)
	}
