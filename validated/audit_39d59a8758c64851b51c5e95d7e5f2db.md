### Title
Payout attribution trusts attacker-controlled OP_RETURN, letting a withdrawer credit any operator with a payout it never funded - (File: `core/src/verifier.rs`, `circuits-lib/src/bridge_circuit/mod.rs`, `core/src/task/payout_checker.rs`)

### Summary
The protocol attributes a payout transaction to an operator solely by parsing an unauthenticated OP_RETURN output of whatever transaction spends the registered `withdrawal_utxo`. Since the withdrawer's signature (`SinglePlusAnyoneCanPay`) only commits to the input and the output at the same index, the withdrawer (an unprivileged attacker) can self-fund the entire payout, satisfy their own committed output exactly, and stamp an arbitrary honest operator's real x-only pubkey into the OP_RETURN, causing that operator's automation to build and broadcast a Kickoff/reimbursement claim for a payout it never made.

### Finding Description
The binding the system relies on is: `withdrawals.payout_payer_operator_xonly_pk == operator whose own funds paid the withdrawer`. In practice, the value is set as: `withdrawals.payout_payer_operator_xonly_pk == XOnlyPublicKey parsed from the first OP_RETURN output of whichever tx spends withdrawal_utxo`, an equality with no cryptographic connection to the funding source.

Trace:
- `create_payout_txhandler` builds the payout tx with input = the withdrawer-owned `input_utxo` spent via `SpendPath::KeySpend` using the withdrawer's own `taproot::Signature` (`SinglePlusAnyoneCanPay`), output[0] = the withdrawer's committed payout output, and output[2] = an unauthenticated OP_RETURN containing an x-only pubkey [1](#0-0) .
- Because the sighash is `SinglePlusAnyoneCanPay`, only the input and the output at the same index (index 0) are covered by the withdrawer's signature; the OP_RETURN output and any extra funding inputs are completely unconstrained and can be added by *anyone* who has the withdrawer's public signature and outpoint [2](#0-1) .
- The withdrawer registers `withdrawal_id`, `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount` themselves via the `withdraw` gRPC path with no verifier/operator gatekeeping of who ultimately broadcasts the completed transaction [3](#0-2) .
- `bitcoin_syncer` records any spend of the tracked `withdrawal_utxo`, and `update_finalized_payouts` treats it as the canonical payout, extracting `operator_xonly_pk` purely from the first OP_RETURN output with no check that this pubkey corresponds to whoever actually supplied the extra value: `let operator_xonly_pk = op_return_output.and_then(...).and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());` [4](#0-3) .
- `get_first_unhandled_payout_by_operator_xonly_pk` then returns this withdrawal to whichever operator's background task polls with that xonly pubkey [5](#0-4) .
- `PayoutCheckerTask::run_once` unconditionally calls `Operator::handle_finalized_payout`, which allocates an unused kickoff connector and proceeds to build/send a Kickoff to claim reimbursement, with no verification that the named operator's own wallet ever funded the spend [6](#0-5) [7](#0-6) .
- Critically, the zk `bridge_circuit` used later for Kickoff/Disprove does not re-derive the funder either: it recomputes `deposit_constant` directly from `operator_xonlypk` parsed from the OP_RETURN of the actual on-chain payout tx that spends the storage-proof-verified withdrawal outpoint, with no funding-source check: `let operator_xonlypk = parse_op_return_data(&first_op_return_output.script_pubkey)...` feeding straight into `deposit_constant(...)` [8](#0-7) . Since `deposit_constant` is purely a function of `(operator_xonlypk, watchtower pubkeys, move_txid, round_txid, kickoff_round_vout, genesis_state_hash)`, if the attacker names the real victim operator's pubkey, this recomputed constant matches exactly what the victim operator's pre-committed kickoff graph expects — the circuit has no way to detect that the victim never actually funded the transaction.

Exploit flow: the withdrawer (attacker), who is also the only holder of the valid `SinglePlusAnyoneCanPay` signature for their own dust `input_utxo`, constructs and broadcasts the completed payout transaction themselves: they add their own extra input(s) supplying the full withdrawal value (satisfying their own committed output exactly, so they simply receive their own withdrawal), and place a targeted honest operator's real x-only pubkey in the OP_RETURN output instead of their own. No signature or fee-payer identity check ever validates that the named operator supplied that value.

### Impact Explanation
The victim operator's automation (`PayoutCheckerTask` → `handle_finalized_payout`) will consume one of its pre-signed kickoff connectors and drive a Kickoff/reimbursement claim for a withdrawal it never funded. Because the recomputed `deposit_constant` in `bridge_circuit` only depends on the OP_RETURN pubkey (which the attacker set to the real victim key) and other deposit-fixed values, the Disprove/challenge machinery cannot distinguish this from a legitimate payout, so the reimbursement can be validated and paid out of the round/collateral chain. This is "an operator reimbursed for a payout it never funded" (Critical), directly matching the impact category, and is repeatable against any deposit whose `withdraw` has been requested, for any operator whose x-only pubkey is public (all operator keys are public by protocol design).

### Likelihood Explanation
Preconditions are minimal and match the stated unprivileged attacker capability set exactly: the attacker only needs to be the withdrawer (calls `withdraw` on the Citrea Bridge contract and obtains the `input_outpoint`/`input_signature` for their own dust UTXO), have enough BTC to cover the committed withdrawal output plus fees (which they receive back to themselves), and be able to broadcast a Bitcoin transaction with a chosen OP_RETURN. No verifier, operator, or aggregator collusion, no key compromise, and no majority hashrate are required. The race is only against legitimate operators attempting to front the same withdrawal — the attacker only needs to be first to get their self-funded, mislabeled transaction confirmed.

### Recommendation
Do not derive payout attribution solely from an unauthenticated OP_RETURN. Bind the OP_RETURN operator pubkey to the actual funding source, e.g. by requiring the payout transaction's additional funding input(s) to be provably controlled by (or pre-committed to) the claimed operator (such as via a signature or a taproot key path proof over the funding input tied to the operator's registered key), and have `update_finalized_payouts`/`bridge_circuit` verify that binding before crediting `payout_payer_operator_xonly_pk`, rather than trusting arbitrary OP_RETURN bytes.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }

            .operator
            .handle_finalized_payout(

    pub async fn handle_finalized_payout<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        deposit_outpoint: OutPoint,
        payout_tx_blockhash: BlockHash,
    ) -> Result<bitcoin::Txid, BridgeError> {
        let (deposit_id, deposit_data) = self
            .db
            .get_deposit_data(Some(dbtx), deposit_outpoint)
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        // get unused kickoff connector
        let (round_idx, kickoff_idx) = self
            .db
            .get_unused_and_signed_kickoff_connector(
                Some(dbtx),
                deposit_id,
                self.signer.xonly_public_key,
            )
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        let current_round_index = self.db.get_current_round_index(Some(dbtx)).await?;
        tracing::info!(
            "Operator: Current round index: {}, round idx for kickoff: {}",
            current_round_index,
            round_idx
        );
        #[cfg(feature = "automation")]
        if current_round_index != round_idx {
            // we currently have no free kickoff connectors in the current round, so we need to end round first
            // if current_round_index should only be smaller than round_idx, and should not be smaller by more than 1
            // so sanity check:
            if current_round_index.next_round() != round_idx {
                return Err(eyre::eyre!(
                    "Internal error: Expected the current round ({:?}) to be equal to or 1 less than the round of the first available kickoff for deposit reimbursement ({:?}) for deposit {:?}. If the round is less than the current round, there is an issue with the logic of the fn that gets the first available kickoff. If the round is greater, that means the next round do not have any kickoff connectors available for reimbursement, which should not be possible.",
                    current_round_index, round_idx, deposit_outpoint
                ).into());
            }
            tracing::info!(
                "Operator: Starting next round to be able to get reimbursement for the payout"
            );
            // start the next round to be able to get reimbursement for the payout
            self.end_round(dbtx).await?;
        }
