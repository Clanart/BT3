### Title
Overpaid native ETH in `EvmHost.dispatch`/`fundRequest` is refunded to the host contract instead of the payer, permanently absorbing user funds - ([File: evm/src/core/EvmHost.sol])

### Summary
The external report's core defect is that a swap-router refund is sent with `_refundAddress = address(this)` instead of to the actual payer, so unspent native value accumulates in a contract that is never expected to hold a balance, and is later drainable/misappropriated. `EvmHost` in this repo reproduces the identical root cause: `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` all call `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The canonical Uniswap V2 router refunds any unspent ETH (`msg.value - amountIn`) to `msg.sender` of the swap call, which from the router's perspective is `EvmHost` itself — not the original caller (`_msgSender()`) who overpaid. `EvmHost` never sweeps or forwards this dust back to the payer.

### Finding Description
In all three fee-paying entrypoints of `EvmHost`: [1](#0-0) [2](#0-1) [3](#0-2) 

the pattern is:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```
`swapETHForExactTokens` in a standard `UniswapV2Router02` implementation performs `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])` at the end — refunding any unspent ETH to whoever called the router. Since `EvmHost` itself is the caller of the router (not the end user), that unspent dust ETH lands back in `EvmHost`'s own balance rather than being returned to `_msgSender()`, the account that actually supplied the excess `msg.value`. `EvmHost` has no code path that forwards this residual value back to the payer after the swap call returns — the functions simply proceed to emit their events and return the commitment.

This exactly mirrors the reported bug: a "swap router" style contract (`EvmHost` swapping native ETH → fee token) is architected to never hold a native balance, yet the refund destination is hardcoded to the contract itself (`address(this)`) instead of the party who is owed the refund (`msg.sender`/payer), so value silently accumulates in a place it was never meant to be.

### Impact Explanation
Every user who calls `dispatch()` or `fundRequest()` with more native value than the exact amount needed to cover `post.fee`/`get.fee`/`amount` permanently loses the difference — it is absorbed into `EvmHost`'s balance instead of being returned. This is a direct, unattended loss of user funds on every overpayment, requiring no malicious relayer, prover, or admin — it is triggered purely by normal usage patterns (slippage buffers, imprecise `getAmountsIn` quoting, front-end estimation error) that are explicitly anticipated by the SDK's `quoteNative`/`getAmountsIn` helpers used to size `msg.value`. Because `withdraw()` in `IHostManager` is the only way to move native/token balance out of `EvmHost`, and it is scoped to protocol governance revenue, any dust that accumulates this way is indistinguishable from legitimate protocol revenue and gets swept by governance — the payer has no recourse to reclaim it. This satisfies the bounty's "stealing or loss of funds" impact class: the refund is not moved "exactly once and only to the rightful beneficiary."

### Likelihood Explanation
High. Any caller of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest` who supplies `msg.value` even slightly larger than the exact `amounts[0]` computed by the router (which is common, since `getAmountsIn` quotes can shift between quote-time and execution-time due to AMM price movement) will lose the excess with 100% certainty and no attacker action required beyond a normal transaction.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, compute the actual native amount spent and forward any leftover `address(this).balance` delta back to `_msgSender()` via a low-level call (mirroring the pattern already used correctly in `IntentGatewayV2.sol` and `UniV4UniswapV2Wrapper.sol`, both of which explicitly refund unspent `msgValue`/`refundETH` back to `msg.sender`). Alternatively, use `getAmountsIn` to compute the exact `amountIn` beforehand and only forward that exact value with the swap call, reverting on any excess like `IntentGatewayV2` does elsewhere.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: X}(post)` where `X` is 1.5x the amount actually required to purchase `post.fee` fee-tokens via the configured `uniswapV2` router (a realistic scenario given price movement between quote and execution).
2. Internally, `swapETHForExactTokens{value: X}(post.fee, path, address(this), ...)` spends `amountIn < X` and refunds `X - amountIn` back to `msg.sender` of that call, i.e., `EvmHost`.
3. `dispatch` returns without forwarding the `X - amountIn` remainder to the user; it stays permanently in `EvmHost`'s native balance.
4. Repeating this across many callers accumulates protocol-held ETH that was never intended to sit in the router-like `EvmHost`, and is only recoverable via governance's `withdraw()` — never by the actual payers, i.e., an irreversible loss of the users' funds. [1](#0-0)
