## Title
Argument Injection via Unsanitized Remote Name in `push()` — (File: `app/src/lib/git/push.ts`)

### Summary
`push()` builds the `git push` argv as `['push', remote.name, ...]` without ever inserting a `--` separator or validating that `remote.name` cannot begin with `-`. Because `remote.name` originates from parsing `git remote -v` output in `getRemotes()`, and git's config-file syntax allows a remote's subsection name (its "name") to be almost any string (including one that starts with `-` and contains spaces, `=`, `;`, etc.), a repository whose `.git/config` defines such a remote will have that raw string pushed as a positional CLI argument. Since git's own option parser inspects each argv token for a leading `-` regardless of the caller's intent, this token can be reinterpreted as a git-push flag instead of a remote name.

### Finding Description
`getRemotes()` parses `git remote -v` output with a permissive regex and returns whatever string sits before the first tab as `name`, with no validation: [1](#0-0) 

`push()` then splices that untrusted `remote.name` directly into the argv array passed to `git`, with no `--` end-of-options marker separating it from flags: [2](#0-1) 

The same unguarded pattern (`remote.name` as a bare positional element with no `--`) is repeated in `fetch.ts`'s `fetchRefspec`, `branch.ts`'s `deleteRemoteBranch`, and `tag.ts`'s `fetchTagsToPush`: [3](#0-2) [4](#0-3) 

Because `git()` invokes the git binary directly (not through a shell), the semicolon in the example remote name would not act as a shell metacharacter — so the exploit primitive is not literally `--upload-pack=touch /tmp/pwned;` being shell-executed. It's also worth correcting the premise in the question: `--upload-pack` is a flag recognized by `git fetch`/`git clone`/`git ls-remote`, not by `git push`. `git push`'s equivalent dangerous option is `--receive-pack=<cmd>` (or its alias `--exec=<cmd>`), which tells git to invoke `<cmd>` as the remote-side receive-pack program. For local-path or `ssh://` remotes this is executed as a subprocess by the local git process (or by the remote host over ssh) — this is the same argument-injection class as the well-known submodule URL RCE (CVE-2017-1000117), applied here to a remote *name* rather than a URL.

I found no sanitization of remote names anywhere in the codebase (no `startsWith('-')` guard, no `--` separator usage before `remote.name`, and the app's UI does not appear to expose a "rename remote"/"add remote" dialog that would validate this — remotes are primarily created via `addRemote()` using a fixed name like `origin`) [5](#0-4) . The only sanitization utility present, `sanitizedRefName`, is used for branch/ref names, not remote names, and is not invoked anywhere in `remote.ts` or `push.ts` [6](#0-5) .

### Impact Explanation
If an attacker can get a GitHub Desktop user to open a repository whose `.git/config` already contains a remote section header starting with `-` (e.g., a repository distributed as a zip/tarball with `.git` included, a repository containing such a config via a malicious submodule with its own separate `.git`, or any other repository-content vector accepted under the review scope), then the first time the user pushes to that remote from Desktop, `git push` will parse the crafted "remote name" as an option rather than a repository/URL argument. Using `--receive-pack=<cmd>`/`--exec=<cmd>`, an attacker can cause an arbitrary local binary to be invoked as the "receive-pack" program when the transport is local or ssh-based, which is a code-execution primitive triggered purely by attacker-controlled repository content and a normal user action (clicking Push) — matching the "attacker controls a cloned/fetched repository ... resulting in code execution" criterion in Valid Impact.

### Likelihood Explanation
Exploitation requires:
1. The victim to open/clone a repository whose `.git/config` already contains a maliciously-named remote (not created through Desktop's own `addRemote`, which would need to itself survive `git remote add`'s own argument parsing — but a pre-existing config file bypasses that entirely).
2. The victim to click "Push" against that remote through Desktop's normal UI flow, which always routes through `push()` in `app/src/lib/git/push.ts`.

No special git server behavior or credentials are needed — the injection is purely local. However, it does depend on the specific value used (`--receive-pack=`/`--exec=`) and on the remote's transport being one where the "remote-side" program is actually invoked locally or where the attacker also controls the target host, which is a real but narrower condition than the question's literal `--upload-pack` premise.

### Recommendation
- Insert a literal `--` separator into the argv immediately before `remote.name` (and any other value derived from user/repo-controlled remote names) in `push.ts`, `fetch.ts` (`fetchRefspec`), `branch.ts` (`deleteRemoteBranch`), and `tag.ts` (`fetchTagsToPush`), so git always treats it as a positional argument.
- Alternatively/additionally, validate remote names returned by `getRemotes()` and reject or sanitize any name starting with `-` before it is ever surfaced to callers or used in a `git` invocation.

### Proof of Concept
1. Create/obtain a repository directory whose `.git/config` contains:
```
[remote "--receive-pack=touch /tmp/pwned"]
    url = https://example.com/some/repo.git
    fetch = +refs/heads/*:refs/remotes/--receive-pack=touch /tmp/pwned/*
```
2. Open this repository in GitHub Desktop (e.g., via "Add local repository").
3. Confirm `getRemotes()` returns `{ name: "--receive-pack=touch /tmp/pwned", url: "..." }` (verifiable by inspecting the repository's remotes list in Desktop or by running `git remote -v` manually and observing the regex in `remote.ts:23-25` would capture that exact string).
4. Trigger a push from Desktop; observe that `push()` builds `['push', '--receive-pack=touch /tmp/pwned', ...]` [2](#0-1)  and that `git` interprets `--receive-pack=touch /tmp/pwned` as an option rather than attempting to resolve a remote literally named that string, demonstrating the argument-injection primitive (full RCE demonstration depends on transport/target host configuration).
