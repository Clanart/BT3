### Title
Unauthenticated panic on duplicate/missing encryption-key registration crashes DKG participants - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
The ASP.NET Core DoS report (BIT-aspnet-core-2020-0602, "improperly handles web requests") maps onto Serai as "improperly handles untrusted protocol messages." In PedPoP's encryption layer, `Decryption::register` uses `assert!` instead of returning an error when a participant's `EncryptionKeyMessage` is registered twice, and both `encrypt` and `decrypt_with_proof` index `enc_keys[...]` directly, panicking when the participant was never registered. Any counterparty in a DKG session can therefore remotely panic an honest participant by sending a duplicate `EncryptionKeyMessage` (or by withholding one), aborting the process.

### Finding Description
`Decryption::register` (encryption.rs:351-362) contains:

```rust
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
```

`EncryptionKeyMessage` is a broadcast message deserialized from untrusted bytes via `EncryptionKeyMessage::read` → `M::read`/`C::read_G` (encryption.rs:57-59). The PedPoP `Commitments` documentation explicitly acknowledges that "this library does not handle networking" and a participant may send multiple sets of messages — yet when such a duplicate reaches `register`, the library panics rather than returning a `DkgError`.

The same class appears at:
- encryption.rs:388 — `self.enc_keys[&decryptor]` panics if `decrypt_with_proof` is invoked for a participant who never registered an encryption key.
- encryption.rs:466 — `self.decryption.enc_keys[&participant]` panics in `encrypt` if shares are encrypted to a participant whose `EncryptionKeyMessage` was never processed (e.g., they withheld it, or messages were reordered).

An attacker controlling one DKG index sends (or induces delivery of) two `EncryptionKeyMessage`s, or simply never sends one while the victim proceeds to encrypt shares. The honest node's process aborts on the `assert!`/index panic. Unlike every other malformed-input path in these crates — which return `io::Error`/`DkgError`/`FrostError` — these paths have no graceful failure, so a single crafted message kills the participant's DKG session (and any co-resident signing state in the same process).

### Impact Explanation
A single malicious participant can crash honest participants mid-DKG, denying service to the key-generation/signing process. Because the panic occurs inside library code processing a routine protocol message, any embedding node (processor/validator) running PedPoP aborts. Repeated across sessions, one faulty index can permanently prevent a threshold group from completing key generation or rotation. This is a reachable availability failure caused entirely by attacker-controlled message bytes — the same class as the advisory (remote request → improper handling → denial of service).

### Likelihood Explanation
The trigger is trivial: serialize two valid `EncryptionKeyMessage`s under one `Participant` index, or omit the message entirely while letting the protocol advance to `encrypt`/`decrypt_with_proof`. No cryptographic computation is required — only control of one of `n` DKG participant positions, which is the standard threat model for a threshold protocol (messages from other participants are exactly the "untrusted bytes fed to `EncryptedMessage::read`/`Commitments::read`" enumerated as in-scope). Any network that delivers duplicate broadcasts (relays, retries, gossip) can also trigger the panic path even from non-malicious senders.

### Recommendation
Replace the `assert!` in `Decryption::register` with a fallible check returning a `DkgError`/`io::Error`-style error (e.g., `DuplicatedParticipant`), propagated through `Encryption::register`. Replace `enc_keys[&participant]` and `enc_keys[&decryptor]` indexing with `get(...)` plus an explicit `InvalidParticipant`/`MissingEncryptionKey` error. This matches the error-propagation discipline used elsewhere (`ThresholdKeys::new`, `ThresholdView::view`, `SignMachine::sign`).

### Proof of Concept
```rust
// Conceptual: attacker participates in PedPoP as participant j.
// They broadcast their EncryptionKeyMessage to victim i twice
// (duplicate delivery, retry, or deliberate replay).

// Victim side (crypto/dkg/pedpop/src/encryption.rs):
let mut enc = Encryption::<C>::new(context, i, &mut rng);
let msg1 = EncryptionKeyMessage::<C, M>::read(&mut bytes1, params).unwrap();
enc.register(j, msg1);                       // ok
let msg2 = EncryptionKeyMessage::<C, M>::read(&mut bytes2, params).unwrap();
enc.register(j, msg2);                       // assert! panics -> process abort

// Variant: attacker withholds their EncryptionKeyMessage entirely;
// victim proceeds to encrypt a share for j:
enc.encrypt(&mut rng, j, share);             // enc_keys[&j] -> panic (encryption.rs:466)
```
