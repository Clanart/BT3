### Title
`open-external` IPC handler forwards arbitrary attacker-controlled link schemes to `shell.openExternal` with no real allowlist - (File: `app/src/main-process/main.ts`)

### Summary
The `_auth` bug in the report is a case where a check that *looks* like it restricts an action is actually a no-op / bypassable gate, letting untrusted input reach a sensitive operation. The same broken-invariant shape exists in the `open-external` IPC handler in Desktop's main process: the code inspects the URL string only to decide whether to *log* it, but performs no scheme allowlisting before handing the raw string to Electron's `shell.openExternal`, which is the trusted, elevated-context sink that actually opens/executes the target.

### Finding Description
```javascript
// app/src/main-process/main.ts:581-597
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (
    pathLowerCase.startsWith('http://') ||
    pathLowerCase.startsWith('https://')
  ) {
    log.info(`opening in browser: ${path}`)
  }

  try {
    await shell.openExternal(path)
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`)
    return false
  }
})
``` [1](#0-0) 

The `pathLowerCase.startsWith('http://') || startsWith('https://')` check has the *appearance* of a validation gate (mirroring the Aragon report's redundant/misleading `isGranted` check), but it is only used to decide whether to write an informational log line — the `if` block has no `else`/`return`, so every value of `path`, regardless of scheme, unconditionally reaches `shell.openExternal(path)`. This IPC channel is invoked from the renderer via `app/src/ui/main-process-proxy.ts`, which exposes an `openExternal` wrapper called from places such as `app/src/ui/lib/link-button.tsx` and other UI code that renders links coming from GitHub API content (PR/issue/commit markdown, release notes, etc.) or from user-clicked hyperlinks. Because none of the callers or the IPC handler itself restrict the *scheme* of the string before it reaches `shell.openExternal`, any link embedded in attacker-controlled GitHub content (a PR description, issue body, or commit message an attacker authored) that a user clicks in the Desktop UI is passed straight through to the OS shell-open API. [2](#0-1) 

This mirrors the report's broken-invariant pattern precisely: a scoping check exists syntactically, but it doesn't actually gate the dangerous operation — it only gates an unrelated side effect (logging vs. actual authorization in the original report).

### Impact Explanation
`shell.openExternal` is a well-known dangerous sink on Windows in particular: crafted non-`http(s)` URIs/paths (e.g., `file://` pointing at an executable, or OS-registered custom protocol handlers) can result in unintended program execution or local file access outside of anything the user explicitly typed. Since the trigger is a link inside content originating from the GitHub API (PR body, issue, commit message) which is attacker-authored, this satisfies the "attacker controls a GitHub API object ... result is code execution / file access outside the repo" impact class in scope.

### Likelihood Explanation
Requires only that the victim open a repository/PR/issue containing attacker-authored text and click a rendered link — a normal, expected user action, not a local-access or social-engineering-heavy scenario. No admin rights or pre-existing host compromise needed.

### Recommendation
Make the scheme check authoritative rather than cosmetic: reject (return `false`/throw) for any `path` whose scheme is not on an explicit allowlist (e.g., `http:`, `https:`, `mailto:`) *before* calling `shell.openExternal`, instead of only branching on it for logging purposes.

### Proof of Concept
1. Attacker opens a PR/issue on a public repo containing a markdown link with a non-http(s) URI, e.g. `[click me](file:///C:/Windows/System32/some.exe)` or a registered custom-protocol URI.
2. Victim opens that PR/issue inside GitHub Desktop and clicks the rendered link.
3. The renderer calls the exposed `openExternal` proxy, which invokes IPC channel `open-external` in `app/src/main-process/main.ts:581`.
4. The scheme check at lines 583-588 evaluates false (or true — it doesn't matter), and control falls through unconditionally to `shell.openExternal(path)` at line 591, executing/opening the attacker-chosen target with no restriction.

**Confidence note:** I confirmed the unconditional `shell.openExternal` call and the cosmetic-only scheme check directly in `app/src/main-process/main.ts`. I could not fully trace, within the available indexed code, the exact markdown-rendering component that turns PR/issue/commit body text into clickable elements invoking this specific `openExternal` proxy (only a partial reference to `app/src/ui/lib/link-button.tsx` was visible). Given index size limits, some file contents may not be available — a Devin session with full repository access would be needed to confirm the exact rendering path.
