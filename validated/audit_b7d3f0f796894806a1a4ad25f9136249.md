### Title
`ThresholdKeys::read` accepts identity verification shares, yielding an identity group key and unspendable outputs - (File: crypto/dkg/src/lib.rs)

### Summary
The external report concerns a "use of uninitialized value" reached by feeding crafted bytes to a decoder: a field is consumed as if valid when it was never actually populated. The Serai analog is a value that decodes to the group *identity* (the additive "zero") being accepted where a real public key is required. `ThresholdKeys::read` deserializes per-participant verification shares using `<C as Ciphersuite>::read_G`, which performs only canonical-encoding checks and does **not** reject the identity point. `ThresholdKeys::new` then interpolates those shares into `group_key` without any identity check, so a crafted serialization produces `ThresholdKeys` whose group key is the identity — the functional equivalent of a zero/uninitialized key.

### Finding Description
- `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) checks only that the encoding is canonical (`to_bytes == encoding`). The identity point has a canonical encoding (e.g., `01 00..00` on Ed25519/Ristretto), so it passes.
- FROST is aware of this hazard: `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) explicitly rejects identity. But `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:620-623`) uses `<C as Ciphersuite>::read_G`, not the identity-rejecting variant, for every entry in `verification_shares`:
  ```rust
  for l in (1 ..= n).map(Participant) {
    verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
  }
  ```
- `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:376-378`) computes the group key as `Σ verification_shares[i] * interpolation_factor(i, 1..=t)` with no check that any share is non-identity:
  ```rust
  let group_key =
    t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
  ```
- Consequences of accepting the encoding-equivalent of a "zero/uninitialized" share:
  1. If the first `t` verification shares are all identity, `group_key = identity`. `group_key()` (`crypto/dkg/src/lib.rs:445-447`) then returns `identity * scalar + G * offset`; with a fresh deserialization (scalar = 1, offset = 0), this is the identity point. Any downstream consumer that registers this key for scanning (bitcoin-serai `register_offset`/`Scanner`, Taproot tweak of the internal key) reports outputs to an address whose discrete log does not exist — funds are detected as received but can never be spent ("funds reported received that are not spendable").
  2. A single identity verification share `Y_j = identity` makes the FROST share-verification equation `s_j·G == R_j + c·λ_j·Y_j` reduce to `s_j·G == R_j`, i.e., it validates a *zero* secret share from participant `j`. A participant holding zero share contributes nothing to reconstruction while appearing fully validated, which corrupts `recover_key` and can silently downgrade the effective threshold set.
  3. `ThresholdKeys::read` is reachable on untrusted bytes per the threat model (deserialized key material restored from disk/backup or supplied by a counterparty in key-recovery flows such as `dkg/recovery`), and none of `Participant` bounds (`i ≤ n` checked, `t/n` sanity via `ThresholdParams::new`) catch identity points.

### Impact Explanation
- **Unspendable funds**: a key set whose `group_key()` is identity (or attacker-controlled via offset semantics) is used as the scan/receive key; payments to its derived addresses are irreversibly locked.
- **Incorrect verifier input**: identity verification shares make zero secret shares verify, so key-recovery / share-validation logic accepts a share polynomial inconsistent with the real group key — the deserialized "key" describes a secret that does not match what honest signers can produce, enabling share-set substitution during recovery.
- Severity: **High** under the report's CVSS context (integrity/availability of funds via crafted input bytes), conservative Medium-High given it requires the victim to consume attacker-influenced serialized key material.

### Likelihood Explanation
Triggering requires an attacker to cause crafted bytes to be fed to `ThresholdKeys::read` — the deserialization path is explicitly in scope as an untrusted-bytes entry point (key backups, recovery flows, or any peer-supplied `ThresholdKeys` blob). No key compromise, collusion, or protocol misbehavior is needed; the bug is purely a missing validity check in a decoder, matching the uninitialized-value class. Crafting the payload is trivial (standard identity encodings are fixed byte strings).

### Recommendation
In `ThresholdKeys::read` (and `ThresholdKeys::new` as defense-in-depth), reject identity:
- Replace `<C as Ciphersuite>::read_G` with an identity-rejecting read (or add `if point.is_identity() { Err(...) }`) for each verification share.
- After computing `group_key` in `ThresholdKeys::new`, reject `group_key.is_identity()`.
- Optionally also reject `secret_share == 0` on read, since a zero share should never be serialized by honest code.
- Audit other `C::read_G` call sites that bypass `Curve::read_G` (e.g., PedPoP `Commitments::read` in `crypto/dkg/pedpop/src/lib.rs:115-124`, which reads commitments via the same non-identity-rejecting path — an identity commitment `A_j[0] = identity` likewise passes the PoK verification equation `s·G == R + c·A` only if the signer knows the discrete log, so this is weaker, but shares/commitments should be uniformly identity-checked).

### Proof of Concept
```rust
// Crypto: ed25519 (dalek-ff-group), but applies to any PrimeGroup ciphersuite.
// Identity encoding on ed25519 is 0x01 followed by 31 zero bytes; on Ristretto it is 32 zero bytes.

let t: u16 = 2;
let n: u16 = 3;
let i = Participant::new(1).unwrap();

let mut buf = vec![];
// C::ID header
buf.extend((Ed25519::ID.len() as u32).to_le_bytes());
buf.extend(Ed25519::ID);
// t, n, i
buf.extend(t.to_le_bytes());
buf.extend(n.to_le_bytes());
buf.extend(i.to_bytes());
// Interpolation::Lagrange
buf.push(1);
// secret_share: any canonical scalar
buf.extend(Ed25519::F::ONE.to_repr());
// n verification shares, all identity encodings
let identity = <Ed25519 as Ciphersuite>::G::identity().to_bytes();
for _ in 1 ..= n {
  buf.extend(identity.as_ref());
}

// This succeeds today: no identity check in ThresholdKeys::read / ThresholdKeys::new
let keys = ThresholdKeys::<Ed25519>::read(&mut buf.as_slice()).unwrap();

// group_key = sum of (identity * lambda) = identity
assert!(bool::from(keys.original_group_key().is_identity()));
assert!(bool::from(keys.group_key().is_identity()));

// Downstream: scanner registers this key; every output it detects is unspendable.
// Variant: set only verification_shares[2] = identity. Then the FROST share-check
// s_2·G == R_2 + c·λ_2·Y_2 reduces to s_2·G == R_2, i.e. a zero secret share
// verifies for participant 2, corrupting recover_key / effective threshold.
```

Root cause: `ThresholdKeys::read` at `crypto/dkg/src/lib.rs:620-623` uses the canonical-encoding-only `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) rather than the identity-rejecting `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`), and `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:376-378`) consumes the shares into `group_key` without an identity check — accepting the serialized equivalent of an uninitialized (zero) group element as a valid public key.
