### Title
Unchecked satoshi arithmetic enables signing a Bitcoin transaction with outputs exceeding inputs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts caller-supplied `u64` payment amounts and performs unchecked `u64` summation, multiplication, and addition when calculating inputs, payments, and required fees. [1](#0-0)  In a release build, a `u64::MAX` payment wraps `payment_sat + needed_fee` to a small value, allowing the insufficient-funds check to pass. [2](#0-1) 

### Finding Description
The only validation applied to each payment is a lower-bound dust check; there is no maximum amount or checked accumulation. [3](#0-2)  Input and payment totals are calculated with `sum::<u64>()`, while `needed_fee` uses unchecked multiplication. [4](#0-3)  The solvency test then uses unchecked addition in `payment_sat + needed_fee`. [5](#0-4) 

For `payment_sat == u64::MAX` and any nonzero `needed_fee`, release-mode wrapping makes the sum equal `needed_fee - 1`, so an input worth only enough satoshis to cover the fee is treated as sufficient. [6](#0-5)  The constructor subsequently returns a `SignableTransaction` containing the oversized output. [7](#0-6)  Signing commits every input to `Prevouts::All` and to the Taproot sighash containing the transaction outputs. [8](#0-7) 

### Impact Explanation
An attacker who can cause a crafted payment amount to reach `SignableTransaction::new` can cause the threshold wallet to produce signatures for a transaction paying `u64::MAX` satoshis despite having only a small input. [9](#0-8)  The resulting transaction is consensus-invalid because its output exceeds both its inputs and Bitcoin’s monetary limit, so it should not steal confirmed UTXOs directly. [10](#0-9)  However, Serai has still signed an unintended transaction, and the invalid spend can stall withdrawal processing or make later fee accounting report a wrapped value. [11](#0-10) 

### Likelihood Explanation
The attacker-controlled boundary is the public `payments: &[(ScriptBuf, u64)]` argument and deserialized `ReceivedOutput` data accepted by `SignableTransaction::new`. [12](#0-11)  A single output amount of `u64::MAX` is sufficient, requiring neither numerous inputs nor a large transaction. [9](#0-8)  In debug builds the overflowing operation may panic instead; release builds without overflow checks exhibit the exploitable wraparound. [13](#0-12) 

### Recommendation
Use `checked_add`, `checked_mul`, and `checked_sub` for all satoshi totals, fees, and comparisons in `SignableTransaction::new` and `fee`. [14](#0-13)  Reject any individual payment exceeding Bitcoin’s maximum money supply before constructing `TxOut`, and return a new overflow-specific `TransactionError` instead of allowing a panic or wrap. [15](#0-14) 

### Proof of Concept
The following construction demonstrates the arithmetic bypass; `received_output` can be produced by serializing an offset, `TxOut`, and `OutPoint`, then passing those bytes through `ReceivedOutput::read`. [16](#0-15) 

```rust
// One small spendable input with a valid prevout script/outpoint.
let input: ReceivedOutput = received_output_with_value(1_000);

// A single public-payment output whose amount is accepted by the dust check.
let payments = [(ScriptBuf::new(), u64::MAX)];

// fee_per_vbyte is nonzero, so needed_fee is positive.
let signable = SignableTransaction::new(
  vec![input],
  &payments,
  None,
  None,
  1,
).unwrap();

// Release-mode arithmetic computes:
//   u64::MAX + needed_fee == needed_fee - 1
// so the insufficient-funds check passes despite a 1,000-satoshi input.
assert_eq!(signable.transaction().output[0].value.to_sat(), u64::MAX);
```

Passing that `signable` object into `multisig`, `preprocess`, and `sign` causes each FROST signer to sign the Taproot sighash for the oversized output. [17](#0-16) [8](#0-7)
