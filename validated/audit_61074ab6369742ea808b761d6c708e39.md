### Title
Gasless module trusts a stale, admission-time swap-router quote instead of verifying execution-time outcome, enabling fee-delegation gas theft from the CN lender - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The Foundation report shows a marketplace trusting the *declared* return value of an externally-controlled call (`mintCountTo`) instead of verifying the actual on-chain effect (`balanceOf` delta) before releasing funds. The reachable analog in Kaia is the Gasless module's `checkBalanceForSwap`, which authorizes a fee-delegated `swap` transaction to enter the pool/bundle based on a single, point-in-time view call to the `GaslessSwapRouter` (`GetAmountIn`), without any mechanism that re-verifies the promised swap outcome (`amountRepay` actually recoverable) at the moment the transaction is finally executed by the CN acting as gas lender.

### Finding Description
`checkBalanceForSwap` in [1](#0-0)  performs these checks once, when the transaction is admitted to the pool:
- `minAmountOut >= amountRepay` (declared values from the tx, not enforced on-chain elsewhere in Go code)
- `amountIn >= GetAmountIn(token, minAmountOut)`, where `GetAmountIn` is a **read-only call into the externally deployed `GaslessSwapRouter` contract**, reflecting the AMM reserves *at that instant* [2](#0-1) 
- token balance/allowance snapshots at admission time [3](#0-2) 

This is exactly the pattern in the report: the system asks an external, price-mutable component "will this be enough?" and takes the answer as proof, without any subsequent step that re-confirms the actual result once the transaction is genuinely executed. In the NFT case the untrusted party was a malicious `mintCountTo` implementation; here the untrusted, mutable input is the AMM reserve state read via `GetAmountIn`, which any unprivileged actor can move between admission time and inclusion time by submitting ordinary swap transactions against the same pool (front-running/back-running the gasless tx while it sits in `MaxBundleTxsInQueue`/`MaxBundleTxsInPending`, per [4](#0-3) ).

Because the gasless flow is a fee-delegation model where the CN (acting as "lender") fronts the gas cost and is repaid only if the bundled swap actually executes successfully on-chain (see `SwappedForGas`/`FinalUserAmount` verified in [5](#0-4) ), any gap between the admission-time quote and the execution-time AMM state can cause the on-chain `require(minAmountOut>=actualAmountOut)`-style checks inside the router (external, not in scope) to revert the swap. A reverted swap consumes the gas the CN already fronted but returns none of the promised repayment, i.e., the CN's "lent" gas is spent with no compensation — a direct parallel to Bob's "paid but didn't receive" scenario, except the victim here is the fee-delegation counterparty (the CN/lender) rather than the collector.

### Impact Explanation
An unprivileged transaction sender can repeatedly submit gasless approve+swap bundles priced to just barely pass `checkBalanceForSwap` at admission time, then use ordinary follow-on swaps (their own or coincidental market activity) to move the AMM reserves before the bundle is promoted/executed. Because there is no re-validation step between admission and inclusion, the CN can end up paying gas fees for transactions it has no way to prevent from reverting at inclusion time, resulting in fee/gasless-settlement value loss for the fee-delegation counterparty. This is a concrete instance of "gasless settlement theft" / fee-delegation abuse reachable purely from public transaction submission.

### Likelihood Explanation
Medium likelihood: exploitation requires only ordinary transactions (no special privileges) and knowledge of the gasless swap's queuing window (`MaxBundleTxsInQueue`/`MaxBundleTxsInPending`), both of which are public configuration values. The attacker does not need to control the `GaslessSwapRouter` contract itself — only to influence AMM reserves through normal trading, which is an inherent capability of any market participant.

### Recommendation
Re-validate the swap's economic viability (via `GetAmountIn`/reserve snapshot) immediately before promotion to the pending pool and again immediately before the bundle is placed into the block being built, not only once at initial admission. Alternatively, require the on-chain `GaslessSwapRouter` to guarantee atomicity between the fee-lending disbursement and the repayment collection (e.g., a single all-or-nothing call so a reverted swap never allows the gas advance to be finalized), and have the Gasless module treat a stale/expired quote (beyond a bounded number of blocks) as invalid, dropping the bundled transaction from the pool rather than letting it wait indefinitely for promotion.

### Proof of Concept
1. Attacker submits `approveTx` + `swapTx` (gasless bundle) with `amountIn` computed to satisfy `checkBalanceForSwap`'s `GetAmountIn` check against the current AMM state [2](#0-1) .
2. The bundle is accepted into `knownTxs` and queued, subject only to `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` limits [4](#0-3) .
3. Before the bundle is promoted and included, the attacker (or unrelated market activity) executes ordinary swaps against the same pool, shifting reserves so the true `amountOut` at execution time falls below `minAmountOut`.
4. When the CN finally executes the bundle as the gas lender, the swap fails the on-chain slippage check inside `GaslessSwapRouter` and reverts; the CN has already incurred the gas cost of processing/lending for that transaction with no repayment recovered, since the earlier admission-time check in `checkBalanceForSwap` never gets re-verified against the actual execution-time reserves.

Note: I could not fully confirm from the available index whether any additional re-validation of `GetCheckBalance` occurs immediately before final block inclusion (separate from `IsReady`); this is a gap in what the code index exposed and would need further confirmation in a live session (e.g., via `blockchain/tx_pool.go` promotion logic) to determine the precise window of exposure.

func (g *GaslessModule) checkBalanceForSwap(swapArgs *SwapArgs, swapNonce uint64) error {
	token := swapArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	g.gaslessInfoMu.RLock()
	swapRouter := g.swapRouter
	g.gaslessInfoMu.RUnlock()

	// tx.minAmountOut >= tx.amountRepay
	minAmountOut := swapArgs.MinAmountOut
	amountRepay := swapArgs.AmountRepay
	if minAmountOut.Cmp(amountRepay) < 0 {
		return fmt.Errorf("insufficient minAmountOut: minAmountOut=%s, amountRepay=%s", minAmountOut.String(), amountRepay.String())
	}

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(swapArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckSwapAmount() {
		// tx.amountIn >= gsr.getAmountIn(minAmountOut)
		routerContract, err := kip247.NewGaslessSwapRouterCaller(swapRouter, bc)
		if err != nil {
			return err
		}
		// Required token amountIn, given the current exchange rate and the declared minAmountOut.
		requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
		if err != nil {
			return err
		}
		if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
			return fmt.Errorf("insufficient amountIn: have=%s, want=%s", swapArgs.AmountIn.String(), requiredAmountIn.String())
		}
	}
