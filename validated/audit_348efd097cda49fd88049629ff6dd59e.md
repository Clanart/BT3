### Title
Unauthenticated deposits to deterministic internal offset scripts are reported as internal outputs, enabling fake Branch/Change/Forwarded deposits - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` reports any transaction output whose `script_pubkey` matches a registered script, with no check on provenance. All registered scripts are publicly derivable: the external script is `p2tr_script_buf(key)`, and the internal Branch/Change/Forwarded scripts are `p2tr_script_buf(key + G*offset)` where the offsets are `Secp256k1::hash_to_F(KEY_DST, b"branch" | b"change" | b"forward")` — constants anyone can compute. This is the direct analog of `depositToken` accepting any token: the "whitelist" of internal offsets is not actually restricted to protocol-generated activity, so an unprivileged party can create fake deposits of internal output kinds.

### Finding Description
The scanner maintains a `scripts: HashMap<ScriptBuf, Scalar>` map and reports a `ReceivedOutput` carrying the registered offset for *any* output paying to a matching script, purely on script equality — there is no whitelist of authorized depositors or distinction between "externally initiated deposit" and "internally generated output". [1](#0-0) 

Registration fills this map with scripts derived from deterministic, publicly computable offsets. [2](#0-1)  The concrete internal offsets are fixed hash-to-curve values over a constant domain separator, so every internal script is a known, reusable "address" any Bitcoin sender can pay to. [3](#0-2) 

Downstream, each scanned output is classified into `OutputType::{External, Branch, Change, Forwarded}` solely by which offset's script matched — an attacker-sent output to the Forwarded script is indistinguishable from a genuine protocol-produced forward output. [4](#0-3)  Notably, `get_outputs` explicitly skips the coinbase for maturity, demonstrating awareness of provenance issues — but performs no equivalent check on who created the output or which kind it legitimately is.

Separately, within the same file, `SignableTransaction::multisig` does verify `p2tr_script_buf(key.offset) == prevout.script_pubkey` before signing each input, so a `ReceivedOutput::read` blob with a mismatched offset cannot force signing — the vulnerability is specifically in the *scan/reporting* direction, not the spend direction. [5](#0-4) 

### Impact Explanation
An unprivileged sender can cause the system to report internal-kind outputs that the protocol never created:

- **Fake `Forwarded`/`Change`/`Branch` outputs**: outputs sent to those deterministic scripts are reported and classified as internal protocol artifacts. Downstream scheduling treats such outputs as funds to be aggregated/forwarded, causing the threshold multisig to construct and sign transactions (`SignableTransaction` → `TransactionMachine`) spending outputs whose existence and semantics were attacker-injected — i.e., the group signs transactions it never intended, driven entirely by transaction data an unprivileged party broadcast.
- **Misclassification of external deposits**: an external depositor (deliberately or through address reuse/collision) paying to a non-`External` offset script produces an output credited under the wrong kind, breaking the accounting invariant that `External` outputs carry user deposit data (`output.data` is only populated for `External` kind).

This fits the "fake token deposit" class: the scanner credits deposits purely by destination script ("any token accepted"), with no whitelist binding internal-kind outputs to legitimately generated protocol flows.

### Likelihood Explanation
The attack requires only publishing a standard Bitcoin transaction paying to a publicly computable P2TR script — no validator collusion, no key material, no race conditions. The offsets are deterministic constants (`hash_to_F("Serai Bitcoin Output Offset", b"branch"/"change"/"forward")`), and the group key is public, so any observer can derive all internal deposit scripts and fund them at any time. Severity is Medium: the injected outputs are real and key-path-spendable (so no direct theft of the injected amount), but they corrupt the output stream the processor acts on, inducing unintended multisig signatures and misclassified accounting.

### Recommendation
Bind internal output kinds to provable protocol provenance rather than script-match alone:

- Restrict `Scanner`/classification so that `Change` outputs are only recognized when produced as the change output of a transaction the multisig itself constructed, and `Forwarded`/`Branch` outputs only when accompanied by the expected in-band instruction data (or via `register_offset`-time marking of which offsets accept unsolicited deposits).
- Alternatively, derive forward/change addresses under a separate, non-public offset derivation (e.g., include a secret or per-session component) so external parties cannot fabricate internal-kind outputs.
- At minimum, document and enforce at the scan boundary that an `OutputType` other than `External` requires corroborating evidence (e.g., matching outpoint of a transaction the node itself broadcast) before being emitted as a `ReceivedOutput`.

assert_eq!(outputs.len(), 1);
