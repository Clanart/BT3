Based on the investigation, the closest structural analog to the Malt auction bug — a piece of accounting state that is *supposed* to reflect the current round's data but instead silently carries over stale values from a previous round, causing wrong values to be applied later — is the `manualResolutions` map used to drive conflict-resolution during multi-commit operations (rebase / cherry-pick).

### Title
Stale manual-conflict-resolution map silently reapplied across separate rebase/cherry-pick conflict rounds - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
Desktop tracks the user's manual conflict resolutions ("ours"/"theirs" per file path) in a single `Map<string, ManualConflictResolution>` that is carried forward across the *entire* multi-commit operation (a whole rebase or cherry-pick sequence), keyed only by file path, not by which commit/round produced the conflict.

### Finding Description
`updateConflictState` explicitly preserves the previous conflict state's `manualResolutions` map every time git status is re-read during an ongoing rebase/cherry-pick, only creating a fresh `Map` when there was no previous conflict state at all: [1](#0-0) 

The resolution map is then consumed purely by file path when continuing the operation, with no correlation to which commit or conflict round it was chosen for: [2](#0-1) [3](#0-2) 

This mirrors the structural flaw in the report: a value meant to represent "what applies to *this* unit of work" (userCommitment/userMaltPurchased per exit vs. per whole account; here, a resolution chosen for *this* conflict vs. the whole operation) is tracked at the wrong granularity and is silently reused/decremented incorrectly across repeated iterations of the same loop (`exitEarly` calls vs. successive rebase/cherry-pick conflict rounds on the same path).

A dedicated unit test explicitly documents and locks in this behavior as "preserves manual resolutions when a rebase is detected": [4](#0-3) 

### Impact Explanation
If a malicious/crafted upstream branch is rebased onto or cherry-picked into the user's branch such that the *same file path* conflicts in multiple successive commits (trivial for an attacker who controls the remote/fork being pulled in), the resolution the user picked for the first conflict (e.g., "theirs") will be silently reapplied to the second, unrelated conflict on that path without showing the new conflict markers for review, because the map entry for that path is never invalidated between rounds. This can result in **silent corruption of what the user commits** — content the user never reviewed or approved for that specific commit gets applied and pushed, satisfying the "silent corruption of what the user commits or pushes" impact class from an attacker-controlled repository/branch.

### Likelihood Explanation
Reaching this path only requires an attacker to control the branch/commits being rebased or cherry-picked (a normal, unprivileged git operation a user performs on a fetched/cloned branch), and to craft commits that conflict repeatedly on the same file path — no special user action beyond a normal rebase/cherry-pick with manual conflict resolution is needed. I was not able to fully verify within the available tool budget whether some other code path (e.g. inside `app-store.ts`'s `_updateManualConflictResolution` or the flow that advances to the next commit) explicitly deletes an entry from the map once it has been successfully staged for a given round; only two matches for map-clearing exist in `app-store.ts` and I could not confirm their exact trigger conditions. This is the main uncertainty in this finding and would need direct confirmation via a live rebase/cherry-pick reproduction.

### Recommendation
Scope `manualResolutions` per conflict round/commit rather than for the lifetime of the whole multi-commit operation: clear (or re-key) the map after each successful `continueRebase`/`continueCherryPick` call so that a resolution chosen for one commit's conflict cannot be silently reapplied to a different commit's conflict on the same path. Alternatively, key the map by `(commitSha, path)` instead of `path` alone.

### Proof of Concept
1. Attacker publishes/pushes a branch with commit A and commit B, both of which modify the same file path in a way that conflicts with the user's branch at that path.
2. User rebases their branch onto the attacker's branch in Desktop. Commit A conflicts on `config.yml`; user manually resolves by choosing "theirs" and continues.
3. `updateConflictState` carries the `manualResolutions` map (`config.yml -> theirs`) forward as the rebase advances to commit B's conflict on `config.yml`.
4. When commit B's conflict is processed, `continueRebase` (`app/src/lib/git/rebase.ts:448-462`) finds `config.yml` already has a resolution in the map and silently stages "theirs" for commit B's conflict too — without ever surfacing commit B's actual conflict markers to the user for review — potentially incorporating attacker content the user did not intend to accept for that commit. export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }
