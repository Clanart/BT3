### Title
Payout tx uses `SIGHASH_SINGLE|ANYONECANPAY`, letting anyone replace the operator-attribution output and steal or deny reimbursement credit - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The payout transaction that fronts a Citrea withdrawal is only partially signed by the user: the withdrawal signature uses `SinglePlusAnyoneCanPay` (SIGHASH_SINGLE|ANYONECANPAY), which commits only to input 0 and output 0 (the user payout). The transaction's other fields — the anchor output, the OP_RETURN output that records `operator_xonly_pk` (the field used everywhere downstream to decide *which operator* fronted the withdrawal and is therefore owed reimbursement), and any additional funding inputs — are not covered by that signature and can be freely substituted by whoever finishes constructing/funding/broadcasting the transaction.

### Finding Description
`create_payout_txhandler` builds the payout transaction with three outputs: the user payout (`output_txout`, index 0), an anchor for CPFP (index 1), and an OP_RETURN carrying `operator_xonly_pk` (index 2): [1](#0-0) 

`Operator::withdraw` verifies the user's signature against this handler and explicitly documents/requires the `SinglePlusAnyoneCanPay` sighash type: [2](#0-1) 

It then funds the transaction via `fund_raw_transaction` (adding extra inputs and a change output) and broadcasts it: [3](#0-2) 

Because SIGHASH_SINGLE|ANYONECANPAY only binds input 0 to output 0, the (outpoint, signature) pair extracted from any broadcast/observed payout tx remains valid in an arbitrary alternative transaction that:
- reuses the same withdrawal input/signature and output 0 (satisfying the committed sighash),
- supplies its own funding input(s) to cover fees/anchor,
- and sets the OP_RETURN’s `operator_xonly_pk` to whatever value the constructor chooses (a different operator, no valid operator, or an unrelated key).

This attribution field is exactly what downstream logic uses to bind "the operator credited" to "the party that paid":
- `update_finalized_payouts` parses the OP_RETURN of whichever payout tx actually confirms on-chain and stores that `operator_xonly_pk` as `payout_payer_operator_xonly_pk`: [4](#0-3) 
- `is_kickoff_malicious` and `PayoutCheckerTask`/`validate_payer_is_operator` then trust this stored attribution to decide which operator is expected to kick off and be reimbursed for the deposit's move-to-vault output: [5](#0-4) [6](#0-5) [7](#0-6) 
- The reimburse transaction later pays out the entire `DepositInMove` value to whichever operator's round/kickoff chain got recognized as the payer: [8](#0-7) 

Since the anchor output, change output, and OP_RETURN are unsigned, an unprivileged party who obtains the (outpoint, signature, output_script_pubkey, output_amount) tuple — data that is by design shared "off-chain" with (potentially multiple) operators, and observable once any operator broadcasts their version to the mempool — can construct a competing/replacement transaction that pays the same output-0 amount to the same user address (satisfying the only signed constraint) while writing an arbitrary `operator_xonly_pk` into the OP_RETURN. If this replacement is mined instead of a legitimate operator's version (e.g. via a higher-fee RBF replacement, since the tx is broadcast for confirmation and nothing pins the OP_RETURN), the protocol's payer/attribution binding for the withdrawal permanently diverges from the real payer relationship intended by the design.

### Impact Explanation
This breaks the "operator credited versus the party that paid" binding that the protocol's reimbursement accounting depends on:
- An operator that legitimately intends to front the withdrawal (and would sign/broadcast a correctly attributed payout tx) can have their transaction pre-empted/replaced by an unrelated payout tx whose OP_RETURN does not name them, permanently denying that operator the ability to be recognized as payer and thus to be reimbursed for a withdrawal they were prepared to (or did) fund — this matches the Critical category "an honest operator permanently unable to be reimbursed."
- Conversely, an attacker (no privileged role required) could set the OP_RETURN to name an operator that never funded or intended to front this specific payout, causing that operator's automation (`PayoutCheckerTask`) to treat the deposit as one they must service, entering them into the kickoff/reimbursement pipeline for a payout they did not control the terms of — a mismatch between "the operator credited" and "the party that actually funded the flow," consistent with the Critical category "an operator reimbursed for a payout it never funded."

### Likelihood Explanation
No verifier, operator, watchtower, or other privileged key/role is required by the attacker: any party capable of observing/obtaining the withdrawal `(outpoint, signature, output_script_pubkey, output_amount)` tuple (shared off-chain to operators and/or visible once any operator's version of the tx enters the mempool) and funding a competing transaction can perform the replacement. The exploit path is purely a consequence of using SIGHASH_SINGLE|ANYONECANPAY for the sole signed input while leaving the attribution-bearing OP_RETURN and other outputs unsigned.

### Recommendation
Bind the OP_RETURN/`operator_xonly_pk` output (and ideally the anchor output) to the same signature that covers the user payout, e.g. by having the user (or the protocol) sign with SIGHASH_ALL over a transaction template that fixes the operator-attribution output, or by moving attribution off of an unsigned OP_RETURN entirely (e.g., recording it in a covenant/committed script or requiring the funding operator's own signature over the whole transaction) so that no unsigned output can be swapped by a third party while the withdrawal-fulfilling output remains valid.

### Proof of Concept
1. User signs a withdrawal payout template `(input=dust_utxo, output0=payout_to_user)` with `SinglePlusAnyoneCanPay`, per `Operator::withdraw`'s signature verification (`core/src/operator.rs:630-637`) and `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`).
2. Operator A funds and broadcasts payout tx v1: inputs = [dust_utxo (sig), A's funding input], outputs = [payout_to_user, anchor, OP_RETURN(A's xonly_pk)].
3. Any third party observes this in the mempool (or obtains the off-chain signature/outpoint/amount independently) and constructs payout tx v2: inputs = [dust_utxo (same sig, still valid since only input0/output0 are committed), attacker's own funding input at higher fee], outputs = [payout_to_user (identical to satisfy the signed constraint), anchor, OP_RETURN(arbitrary xonly_pk, e.g. operator B's or garbage)].
4. Because sequence allows replacement and only output 0 is signature-committed, tx v2 can replace/out-race tx v1 in the mempool and confirm instead.
5. `update_finalized_payouts` records `operator_xonly_pk` from whichever tx confirmed (`core/src/verifier.rs:2312-2342`), permanently mis-attributing the payout — operator A (who actually intended/attempted to front it) is denied credit, while the attribution now points to whatever key the attacker chose.

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
}

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
