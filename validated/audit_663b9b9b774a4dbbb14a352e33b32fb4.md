### Title
Single depleted-bandwidth app can abort an entire batched `GetResponse` submission, causing valid state-proof responses for unrelated apps to fail and their requests to time out - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`handle_get_requests` verifies a batch of `GetRequest`s against a shared source-chain membership proof and a shared destination state proof, then iterates the batch a second time to build each `GetResponse` and charge it against the destination app's `pallet-bandwidth` allowance via `BandwidthGate::try_consume`. This charge call is `?`-propagated: if any single app in the batch has insufficient bandwidth, `Err` aborts the whole function before any response in the batch is stored or dispatched, discarding proof-verified responses for the other, unrelated apps in the same batch.

### Finding Description
The batch flow is:
1. `dedup_requests` and per-request checks (timeout, chain id matches, not already responded) - loop 1, lines 76-103.
2. `verify_membership` (source) and `validate_state_machine`/state root fetch for the destination - lines 111-124.
3. Loop 2 (lines 133-155): for each request, `verify_state_proof` builds the `GetResponse`, then:
```rust
<T as Config>::BandwidthGate::try_consume(&response.get.source, &response.get.from, bytes)
    .map_err(|err| Error::Custom(...))?;
```
`try_consume` (`modules/pallets/bandwidth/src/lib.rs:509-564`) returns `GateError::Insufficient`/`NoAllowance` for a specific `(source, app)` when that app's FIFO subscription list can't cover the bytes for its own response. This error is not caught per-item; it propagates out of the `for` loop via `?`, aborting `handle_get_requests` entirely.

Because the function is a single atomic unit (all-or-nothing, matching the pattern noted in `docs/content/protocol/ismp/responses.mdx:64-71` and the `IHandlerV2`/`HandlerV2.sol` batch handlers which document "if any call fails, the entire batch reverts" [1](#0-0) ), no receipt is stored and no `dispatch_get_response` runs for **any** response in the batch — not just the depleted app's. This is the same broken invariant as the external report's `fillOffchainOrders`: heterogeneous, independently-valid items are coupled into one failure domain by a bare `revert`/`?` inside a shared loop, so one malicious or merely under-funded participant can deny service to unrelated honest participants whose items had already passed their own validation (state-proof verification even completed before the abort).

Unlike a purely relayer-side inefficiency, this specific loop is on-chain pallet logic (`handle_get_requests`, called from the coprocessor's message-handling extrinsic), so it is not mitigated by relayer-side pre-simulation/filtering the way `HandlerV2.sol`'s per-message flows are (the relayer only dry-runs whole encoded calls, and here the batch composition and gating happen entirely inside one pallet call after proofs are already verified) [2](#0-1) .

### Impact Explanation
An attacker who controls or colludes with even one app whose `pallet-bandwidth` allowance is exhausted (trivial and cheap: any app can let its subscription lapse, or a griefer with a small app registration can deliberately never top up) can cause any batch that happens to bundle that app's `GetRequest` with other apps' requests to fail entirely. Because responses for GET requests must be delivered before the request's `timeout_timestamp` elapses (documented in `docs/content/protocol/ismp/timeouts.mdx:8-12`), repeatedly forcing batch aborts can push honest apps' `GetRequest`s past their timeout, causing:
- Legitimate cross-chain state queries to fail and require fallback timeout handling that the requesting app may not have anticipated for that specific interval.
- Delayed/failed reputation minting to the relayer for that batch, and wasted challenge-period-gated proof verification work, since state proofs are recomputed and discarded on abort.
- Insolvency-adjacent risk for apps built assuming near-guaranteed GET response delivery (analogous to the "Insolvency Risk" impact called out in the original report), since delivery can be silently blocked by an unrelated third party's bandwidth state.

This does not meet the bar of direct fund theft, but it is a genuine logic attack surface within the required categories ("transaction manipulation," "logic attacks") because an unprivileged app operator can deny cross-chain execution to unrelated honest apps purely by manipulating their own bandwidth balance.

### Likelihood Explanation
Likelihood depends on how the coprocessor groups `GetRequest`s into a single `GetRequestsWithProof` batch (that grouping logic was not directly located in this pass — batching may occur per-destination-height rather than mixing arbitrary apps, which would reduce but not eliminate exposure, since two different apps querying the same destination height are still plausible in one batch). This is the main open uncertainty: I was not able to fully trace the caller that constructs `GetRequestsWithProof.requests` to confirm whether cross-app batching is common in practice or rare/coincidental.

### Recommendation
Do not let `BandwidthGate::try_consume` failure for one request abort the whole batch. Either:
- Pre-check bandwidth availability for all apps in the batch (read-only, no mutation) before doing any state-proof verification/dispatch, and drop only the offending request(s) from the batch (mirroring the report's recommended try/skip pattern), or
- Move the bandwidth charge to occur independently for each response's dispatch path (`dispatch_get_response`) with its own try/catch-equivalent (`Result` handled per-item, not via `?` inside the shared loop), so a depleted app only forfeits its own response instead of the whole batch's.

### Proof of Concept
1. App A (attacker-controlled) registers a `(source, app)` bandwidth key and lets its subscription fully deplete (or never purchases one).
2. App B (honest) has ample bandwidth and dispatches a legitimate `GetRequest`.
3. A relayer/coprocessor batches App A's and App B's `GetRequest`s together into one `GetRequestsWithProof` (same destination height, same proof) and calls `handle_get_requests`.
4. Loop 2 processes App B's response successfully (would succeed), then reaches App A's response and `BandwidthGate::try_consume` returns `Err(GateError::NoAllowance)` [3](#0-2) .
5. The `?` at `modules/pallets/state-coprocessor/src/impls.rs:151` propagates this error out of `handle_get_requests`, so `store_response_receipt`/`dispatch_get_response` never execute for App B's already-computed response either.
6. If App B's `GetRequest` is close to its `timeout_timestamp`, repeating this whenever App A is included in a batch can cause App B's request to time out despite App B having valid bandwidth, correct proofs, and no fault of its own. [4](#0-3) [5](#0-4)

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
