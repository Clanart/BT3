## Analysis Result

### Title
Unsigned outputs of the payout transaction let anyone hijack operator-reimbursement attribution - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The `SIGHASH_SINGLE|ANYONECANPAY` signature that authorizes spending of a user's withdrawal UTXO in `create_payout_txhandler` only commits to input 0 and output 0 (the user payout). The anchor output and, critically, the `OP_RETURN` output that records **which operator's x-only pubkey gets credited for the reimbursement** are left completely unsigned. Any party that observes a broadcast/relayed withdrawal signature can therefore build a competing payout transaction that pays the same user output but substitutes a different (or no) operator pubkey in the `OP_RETURN`, hijacking the reimbursement credit away from the operator who actually fronted the payout — the exact "operator credited vs. party that paid" custody binding called out in the rules, and structurally analogous to the reported bug class where a value/attribution flow silently diverges from the party entitled to it.

### Finding Description
`create_payout_txhandler` builds the payout tx with: output 0 = user payout, output 1 = anchor (CPFP), output 2 = `op_return_txout` carrying the operator's x-only pubkey, and signs only the withdrawal input via `set_p2tr_key_spend_witness(&user_sig, 0)`: [1](#0-0) 

The signature's sighash type is enforced to be `SinglePlusAnyoneCanPay`: [2](#0-1) 

Under BIP341 `SIGHASH_SINGLE|ANYONECANPAY`, the signature commits **only** to the input being spent and the output at the same index (index 0). It explicitly permits anyone to add/replace other inputs and to change any output other than index 0. This means the anchor output and the `OP_RETURN` operator-attribution output are entirely unauthenticated by the withdrawing user's signature — anyone possessing the same user-signed input/output0 pair (which is distributed to all operators via the aggregator `Withdraw` RPC, or is visible once any operator broadcasts it) can construct their own version of the transaction, pay the identical user output, and put an arbitrary key (or no key at all) into the `OP_RETURN`.

Downstream, the verifier trusts this on-chain `OP_RETURN` value as ground truth for "who fronted the payout": [3](#0-2) 

This value is persisted and later used to gate reimbursement eligibility. `validate_payer_is_operator` rejects reimbursement whenever the payer recorded in the DB (i.e., the `OP_RETURN` pubkey of the tx that actually got mined) does not match the requesting operator's own key: [4](#0-3) 

and `is_kickoff_malicious` similarly treats any kickoff as malicious if the operator sending it does not match the `OP_RETURN`-derived payer: [5](#0-4) 

Since there is no other mechanism confirming that the entity named in `OP_RETURN` is the entity that actually supplied/funded the payout, the binding **`OP_RETURN pubkey == entity that funded the withdrawal`** can be broken by any unprivileged party who intercepts the signed withdrawal request and replaces the unsigned outputs before the honest operator's transaction confirms.

### Impact Explanation
If an attacker (or any third party, not necessarily a registered operator) races the honest fronting operator's payout transaction with a variant that pays the same user output but stamps a different/garbage pubkey (or omits `OP_RETURN` entirely) into the attribution output, and that variant confirms first:
- The honest operator who actually paid the user is permanently unable to be reimbursed, because `validate_payer_is_operator` and `is_kickoff_malicious` will find the DB's recorded payer (derived from the winning transaction's `OP_RETURN`) does not match the honest operator's key, and reject/flag as malicious any kickoff/reimbursement attempt from that operator.
- If the attacker's chosen `OP_RETURN` value happens to name a different real operator, that operator would be incorrectly credited for a payout it never funded.

Either case matches the Critical impact class: "an honest operator permanently unable to be reimbursed" / "an operator reimbursed for a payout it never funded."

### Likelihood Explanation
This requires no operator/verifier/aggregator role, no key compromise, and no majority hashrate — only the ability to observe a broadcast or relayed withdrawal payout transaction (or the withdrawal request itself, which is sent to potentially all operators via the aggregator `Withdraw` RPC) and win a fee/relay race with a modified copy of it before the honest transaction confirms. The cost to the attacker is limited to constructing and fee-bumping a competing transaction; no capital beyond transaction fees is required since the signed input/output already carries the value paid to the user.

### Recommendation
Bind the `OP_RETURN` operator-attribution output (and ideally the anchor/CPFP output) to the user's signature by using a sighash type that commits to all outputs (e.g. `SIGHASH_ALL` variants, or a covenant/script-path construction that hashes the operator pubkey into the spending condition) rather than `SIGHASH_SINGLE|ANYONECANPAY`. Alternatively, require operators to additionally co-sign or otherwise cryptographically commit to the specific `OP_RETURN` value before the withdrawal UTXO can be considered spent for reimbursement purposes, so that reimbursement attribution cannot be altered by a party who did not participate in constructing the original signed payout.

### Proof of Concept
1. User submits `WithdrawParams` (with `SinglePlusAnyoneCanPay` `input_signature`) to Operator A via the `Withdraw`/`InternalWithdraw` RPC, or the aggregator broadcasts it to multiple operators via `AggregatorWithdrawalInput`.
2. Operator A builds and broadcasts the payout tx via `create_payout_txhandler`/`Operator::withdraw` (`core/src/operator.rs:560-627`), with `OP_RETURN` = A's xonly pubkey.
3. Before A's transaction confirms, an unprivileged observer who has seen the same signed input/output-0 pair constructs an alternate transaction spending the same withdrawal UTXO, reproducing output 0 (user payout) exactly, but replacing the `OP_RETURN` output with an arbitrary pubkey (or omitting it), and broadcasts it with a competitive fee.
4. If the attacker's transaction confirms, `update_finalized_payouts` (`core/src/verifier.rs:2283-2350`) records the attacker-controlled `OP_RETURN` value as the payer.
5. Operator A later calls `get_reimbursement_txs`/`handle_finalized_payout`; `validate_payer_is_operator` rejects it because the DB-recorded payer no longer matches A's key, permanently denying A reimbursement for a payout A actually funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
