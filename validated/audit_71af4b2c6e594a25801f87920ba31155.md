### Title
Attacker-controlled `n` in `ThresholdKeys::read` forces a large speculative heap allocation from a handful of bytes - (File: crypto/dkg/src/lib.rs)

### Summary
The bug class in the external report is "an attacker supplies an unbounded list/count that is trusted, causing resource exhaustion." The strongest in-scope analog lives in `ThresholdKeys::read`, which trusts a 2-byte `n` field taken directly from untrusted input to size a `Vec::with_capacity` allocation for `Interpolation::Constant` coefficients before any validation or bound check, and also uses `n` to drive a loop of `read_G` calls into a `HashMap`. `n` is a `u16` supplied by the reader, so a ~9-byte input forces an allocation of up to `65535 * size_of::<C::F>()` (≈2 MiB for 32-byte fields) plus the setup for a 65535-iteration deserialization loop. `ThresholdKeys::read` is an explicitly-listed untrusted-byte sink. [1](#0-0) 

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), after checking the curve ID, the code reads `t`, `n`, and `i` as bare `u16`s straight from the reader (lines 591-602). It then reads the interpolation tag, and for tag `0` performs:

```rust
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n { res.push(C::read_F(reader)?); }
```

followed by a `HashMap` fill loop over `1 ..= n` calling `read_G` (lines 620-623). Only *after* all of this does `ThresholdParams::new(t, n, i)` validate `t <= n`, `n != 0`, `i <= n` (lines 166-179, invoked at line 626), and `ThresholdKeys::new` does not bound `n` against anything sane either — it only requires `t <= n <= 65535`.

The declared `n` therefore needs only to satisfy `t <= n <= u16::MAX`; nothing ties it to the actual number of bytes/elements present. The `Vec::with_capacity(n)` commits `n * size_of::<C::F>()` bytes of heap memory (and touches allocator slow paths) on the strength of a single attacker-controlled `u16`, and the subsequent loops attempt `n` field-element and group-element reads even when the input contains only a few bytes (each `read_exact` fails, but the loop and per-element error handling still run linearly in `n`).

The closest sibling readers are more careful: `Transaction::read` in `coordinator/src/tributary/transaction.rs` explicitly rejects when `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` before allocating, and `RrCodec::read_request` checks `len > MAX_LIBP2P_REQRES_MESSAGE_SIZE` before `vec![0; len]`. `ThresholdKeys::read` performs no equivalent total-size check.

### Impact Explanation
Any unprivileged party that can feed bytes to `ThresholdKeys::read` (a listed reachable sink) can, per invocation and with ~9 bytes of input, force a ~2 MiB speculative allocation and a 65535-iteration deserialize loop. Issued repeatedly (e.g., per-message or per-peer deserializations in an integration), this produces sustained allocator churn and CPU burn disproportionate to the attacker's bandwidth — the same resource-exhaustion-via-unbounded-count class as the GitLab report, here manifesting as memory/CPU exhaustion rather than database bloat. This is a performance-impacting denial of service reachable from public inputs, consistent with a Medium-severity analog.

### Likelihood Explanation
Reachability depends on the host application exposing `ThresholdKeys::read` to untrusted bytes (e.g., loading keys supplied by peers or from wire data); the prompt scope explicitly treats that sink as reachable. The amplification per call is bounded (≈2 MiB / 65k iterations per ~9-byte message) but trivially repeatable, requires no valid signature, no collusion, and no threshold of attackers — a single unprivileged sender suffices. Likelihood is therefore moderate: it needs a deployment that deserializes `ThresholdKeys` from remote input at a non-trivial rate.

### Recommendation
Bound `n` before allocating. After reading `t`, `n`, `i`, immediately run `ThresholdParams::new(t, n, i)` validation and additionally enforce a protocol-appropriate cap on `n` (realistic multisigs are far below 65535). Replace `Vec::with_capacity(n)` with incremental `push`es (the allocation then grows only as bytes are actually consumed), or first check `n * repr_size <= remaining_input_length`. Apply the same ordering to the `verification_shares` loop so that parameter validation precedes any length-dependent work, matching the pattern already used in `Transaction::read` and `RrCodec::read_request`.

### Proof of Concept
```rust
use std::io;
use dkg::{Participant, ThresholdKeys};
use ciphersuite::Ciphersuite;
use ciphersuite::Secp256k1; // or any in-scope curve

fn main() {
    let mut buf = vec![];
    // C::ID header (length-prefixed, must match)
    let id = Secp256k1::ID;
    buf.extend((id.len() as u32).to_le_bytes());
    buf.extend(id);
    // t = 1, n = 65535 (u16::MAX), i = 1
    buf.extend(1u16.to_le_bytes());
    buf.extend(65535u16.to_le_bytes());
    buf.extend(1u16.to_le_bytes());
    // interpolation = Constant -> Vec::with_capacity(65535) executed here,
    // ~2 MiB committed from ~9 bytes of attacker input
    buf.push(0u8);
    // No further bytes needed: read_F fails per element, but the allocation
    // and 65535-iteration loop already ran. Repeating this call in a loop
    // exhausts memory bandwidth/CPU far above the attacker's input rate.
    let _ = ThresholdKeys::<Secp256k1>::read(&mut buf.as_slice());
}
```

Caveat: per the indexing coverage limits I could not fully verify every other in-scope `read`/deserialization path (e.g., `multiexp`, `transcript`, `musig`, `bitcoin-serai` internals) for a stronger amplification primitive; `ThresholdKeys::read` is the clearest concretely-verified instance of the class, with byte-for-byte allocation amplification bounded by `u16::MAX`.
