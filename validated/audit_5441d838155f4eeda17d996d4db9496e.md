### Title
Block-revenue-sharing commission (`UpdateCommissionBps`/`CommissionKind::BlockRevenue`) can be set to 100% immediately before reward distribution, unlike inflation-rewards commission which is epoch-delayed — allowing a last-minute "commission rug" against delegated stakers - (File: `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
This is a direct analog of the Astaria "malicious refinancing" bug: a permissionless (from the delegator's perspective) parameter change made right before the value-realizing event (liquidation ↔ reward distribution) can strip value that the counterparty (borrower ↔ staker) reasonably expected, because the check that normally prevents this timing attack does not cover this new code path.

Agave has two commission-setting instructions on vote accounts. The legacy `VoteInstruction::UpdateCommission` is gated by `is_commission_update_allowed` (only allows increases in the first half of an epoch), and once `delay_commission_updates` is active, the effective commission used for **inflation reward** calculation is taken from a snapshot of vote-account state from a full epoch earlier, specifically to prevent "last minute commission rugs".

The newer `VoteInstruction::UpdateCommissionBps` (SIMD-0291), used for both `CommissionKind::InflationRewards` and `CommissionKind::BlockRevenue`, explicitly has "No commission update rule, per SIMD-0249 and SIMD-0291" — it can be called at any slot, any number of times. For `InflationRewards` this is safe because reward calculation still consults the epoch-delayed snapshot (`CachedVoteAccounts::snapshot_epoch_vote_accounts` / `rewarded_epoch_vote_accounts`). However, the block-revenue-sharing path (`calculate_block_reward`) is fed `cached_vote_accounts.distribution_epoch_vote_accounts`, which is described as "vote account state from the end of the rewarded epoch / beginning of the distribution epoch" — i.e., the *current, live* commission, not the epoch-delayed one.

### Finding Description
The withdrawer authority of a vote account can call `update_commission_bps` with `CommissionKind::BlockRevenue` and no timing restriction: [1](#0-0) 

The dispatch site enforces only the feature-gate, not any epoch-position check: [2](#0-1) 

Contrast this with the legacy commission path, which is explicitly comment-documented as designed to prevent last-minute rugs via a mandatory delay: [3](#0-2) [4](#0-3) 

For inflation rewards, `redeem_delegation_rewards` deliberately reads commission from the epoch-old snapshot when `delay_commission_updates` is set, specifically to neutralize a same-epoch commission change: [5](#0-4) 

But the block-revenue-sharing reward is computed from the *live/current-epoch* `distribution_epoch_vote_accounts`, not the delayed snapshot, per the field's own documentation and its use site: [6](#0-5) [7](#0-6) 

The corrupted/unprotected value is the vote account's `block_revenue_commission_bps` field as read at block-reward calculation time: it can be set to its maximum (10000 bps = 100%) by the withdrawer authority immediately before the reward-calculation snapshot is taken for a given epoch/slot range, diverting essentially all block revenue owed to delegators to the validator, then reset back to a normal value afterward — with no cooldown, no minimum-duration lock, and no epoch-delay guard analogous to the one protecting inflation-reward commission.

### Impact Explanation
Delegated stakers economically rely on the advertised commission rate when choosing to delegate, just as the Astaria borrower relied on `liquidationInitialAsk` when taking the loan. Because the block-revenue commission update path has no timing restriction and is not covered by the epoch-delay protection that the inflation-rewards path uses, a vote account operator can transiently spike the block-revenue commission to 100% for exactly the window during which block-revenue rewards are computed/distributed, capturing revenue that stakers were owed, then quietly restore the original rate. This is a fund-loss issue for delegators/stakers, arising purely from a gap in the runtime's reward-commission enforcement — not from any malicious peer/validator consensus assumption, since it is the vote account's own legitimately-signed instruction exploiting an inconsistency between two parallel commission mechanisms.

### Likelihood Explanation
Likelihood is high for any vote account operator who controls (or compromises) the authorized withdrawer key, since:
- No feature/permission beyond `block_revenue_sharing` + `commission_rate_in_basis_points` + `delay_commission_updates` is required to reach this code path.
- The instruction itself imposes zero timing restriction by design ("No commission update rule, per SIMD-0249 and SIMD-0291").
- The attack requires only knowledge of when block-revenue reward calculation occurs relative to slot height, which is derivable from public epoch/slot schedule data — no privileged information needed.

### Recommendation
- Apply the same epoch-delay protection used for inflation-rewards commission (`delay_commission_updates` snapshot mechanism) to the block-revenue-sharing commission field, so `calculate_block_reward` reads `block_revenue_commission_bps` from a snapshot at least one epoch old rather than from `distribution_epoch_vote_accounts`.
- Alternatively/additionally, reinstate a minimum-delay or epoch-half-style restriction specifically for `CommissionKind::BlockRevenue` updates in `update_commission_bps`/`vote_processor.rs`, so it cannot be changed and reverted within the same reward-calculation window.
- Add an invariant test asserting that block-revenue commission used at reward-calculation time cannot reflect a commission change made after the start of the block-reward accrual period.

### Proof of Concept
1. A vote account's withdrawer authority observes it is nearing the point at which `calculate_stake_rewards_and_commissions`/`calculate_block_reward` will be invoked for the current distribution window (public information from slot/epoch schedule).
2. It submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::BlockRevenue }`, signed only by the authorized withdrawer — accepted unconditionally per: [8](#0-7) 
3. Block-revenue rewards for that window are computed from `distribution_epoch_vote_accounts` (live/current commission), per: [9](#0-8) 
so nearly 100% of the block revenue for that period is attributed to the validator's commission rather than distributed to delegators.
4. After distribution, the withdrawer authority calls `UpdateCommissionBps` again to restore a normal-looking commission rate, with no on-chain penalty or delay preventing this cycle from repeating every distribution window.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)

    /// Get cached vote account state from the past few epochs so that some vote
    /// state configuration changes are delayed before being used in reward
    /// calculation.
    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }
