### Title
Partial (hunk/line) commits silently bypass Git clean/CRLF filters, letting Desktop commit different content than what the repository's own `.gitattributes` filters would produce - (File: `app/src/lib/git/apply.ts`, `app/src/lib/git/update-index.ts`)

### Summary
`stageFiles()` in [1](#0-0)  splits selected files into two staging paths: whole-file selections go through `updateIndex()`, which shells out to `git update-index --add` [2](#0-1) , and partially-selected files go through `applyPatchToIndex()` [3](#0-2) . `git update-index --add` reads the working-tree file and converts it into a blob via Git's normal "clean" pipeline (CRLF normalization, `.gitattributes` `filter=` clean scripts, etc.), while `applyPatchToIndex()` builds a hand-rolled unified diff from the previously rendered diff text and feeds it to `git apply --cached` [4](#0-3) . `git apply` never invokes Git's clean/smudge/attribute pipeline — it writes the literal patch text into the index. This means the same repository, with the same `.gitattributes`, produces different committed bytes for the identical file content depending on whether the user selected "all" lines or only some lines in Desktop's UI.

### Finding Description
The broken invariant is: *what Desktop's diff view shows the user as "about to be committed" should match what actually lands in the git object database*, and *the repository's declared content-processing rules (`.gitattributes` clean filters, EOL normalization) should apply uniformly regardless of which UI path was used to stage a change*. Desktop breaks this in the partial-selection path:

- `formatPatch()` in `app/src/lib/patch-formatter.ts` builds a patch verbatim from the lines returned by `getWorkingDirectoryDiff` (raw working-directory content, not clean-filtered) [5](#0-4) .
- `applyPatchToIndex()` applies that literal patch straight into the index with `git apply --cached --unidiff-zero --whitespace=nowarn -` [6](#0-5) , which does not run `.gitattributes`-declared `clean` filters or CRLF normalization.
- By contrast, whole-file selections staged via `updateIndex(repository, normal)` run `git update-index --add`, which does perform Git's normal clean-filter/CRLF conversion of the working-tree content before it becomes a blob.

A repository the user has cloned (attacker-controlled) can define a `.gitattributes` clean filter — e.g. a secret-redaction filter (`*.env filter=redact`), a formatting/normalization filter, or CRLF normalization rules (`* text=auto`). The repo owner/attacker can craft this so that any file staged in full is transformed (secrets stripped, line endings normalized), while relying on the fact that any *partial* selection made through Desktop bypasses that transform entirely. Desktop's own UI signals (the `DiffContentsWarning`/line-endings banner, `app/src/ui/diff/diff-contents-warning.tsx`) are derived from whole-diff line-ending detection and give no indication that the partial-commit code path behaves differently or that clean filters won't run [7](#0-6) . There is no code anywhere in `apply.ts` or `patch-formatter.ts` that re-applies attribute filters after `git apply --cached`, and no warning to the user that a partial selection skips filtering.

Existing guards do not stop this: the only content-type guard in `applyPatchToIndex` rejects binary/large/unrenderable diffs [8](#0-7) , but does nothing for ordinary text files governed by a clean filter or EOL attribute — those are exactly the diffs that proceed to `git apply --cached`.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A repository can be engineered so that its clean filters are the security/consistency boundary the maintainers rely on (e.g., a pre-commit-style secret scrubber implemented as a `.gitattributes` clean filter, or mandated EOL/line-ending normalization for cross-platform consistency). Any Desktop user who stages a file by selecting individual hunks/lines (a very common, encouraged workflow — Desktop advertises per-line/per-hunk staging as a feature) will have that content committed, and subsequently pushed, without the transformation the repository owner expects to always be applied. This can result in unredacted secrets, non-normalized/incompatible line endings, or other filter-mandated transformations reaching the remote history — a divergence between the "preview" (working-directory diff shown pre-commit) and the "actual" (filtered result the repo's rules were supposed to guarantee), mirroring the `previewRedeem`/`redeem` mismatch pattern in the seed report.

### Likelihood Explanation
Likelihood is moderate to high: partial staging via line/hunk selection is a first-class, everyday Desktop feature (exercised extensively in `app/test/unit/git/commit-test.ts`, e.g. [9](#0-8) ), and any cloned/fetched repository can ship a `.gitattributes` clean filter or EOL policy without any additional user action beyond a normal `git clone`. No elevated privileges, local access, or social engineering beyond "clone this repo and use Desktop's normal partial-staging UI" are required.

### Proof of Concept
1. Attacker publishes a repository containing `.gitattributes`: `secret.txt filter=redact` and a configured clean filter (`git config filter.redact.clean "sed -r 's/API_KEY=.*/API_KEY=REDACTED/'"`, distributed via repo setup docs/hook the victim is expected to configure, or simply relying on `* text=auto` for the CRLF-only variant which needs no filter config at all — pure `.gitattributes` is sufficient for EOL normalization).
2. Victim clones the repo in GitHub Desktop and edits `secret.txt`, adding a line containing a real key alongside unrelated changes.
3. Victim opens the Changes view, and — as normally encouraged — selects only some lines/hunks of `secret.txt` to include, leaving other lines/hunks out of this commit (a very common per-hunk review flow).
4. Desktop calls `stageFiles` → `applyPatchToIndex` for `secret.txt` since it has a partial selection [10](#0-9) , which invokes `git apply --cached` with the raw, unfiltered patch text [4](#0-3) .
5. The commit is created via `createCommit` [11](#0-10)  containing the raw `API_KEY=...` value, even though the same file staged in full (`git update-index --add`) would have gone through the `redact` clean filter and stripped it.
6. The victim pushes; the secret is now in the remote history despite the repository's own filter rules — a divergence never surfaced by Desktop's UI.

### Recommendation
Either (a) make `applyPatchToIndex` renormalize/filter content after applying the patch — e.g. run `git add --renormalize -- <path>` or equivalent post-processing so attribute-driven clean filters and EOL rules are applied consistently regardless of whole-file vs. partial selection — or (b) detect when a file governed by a `filter=`/`text` attribute is being partially staged and surface an explicit warning (similar to the existing `DiffContentsWarning`) informing the user that clean filters will not be applied to this commit, so the discrepancy is not silent.

async function updateIndex(
  repository: Repository,
  paths: ReadonlyArray<string>,
  options: IUpdateIndexOptions = {}

  if (paths.length === 0) {
    return
  }

  const args = ['update-index']

  if (options.add !== false) {
    args.push('--add')
  }

  if (options.remove !== false || options.forceRemove === true) {
    args.push('--remove')
  }

  if (options.forceRemove) {
    args.push('--force-remove')
  }

  if (options.replace !== false) {
    args.push('--replace')
  }

  args.push('-z', '--stdin')

  await git(args, repository.path, 'updateIndex', {
    stdin: paths.join('\0'),
  })
}

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

export async function createCommit(
  repository: Repository,
  message: string,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  options?: {
    amend?: boolean
    noVerify?: boolean
    signOff?: boolean
    allowEmpty?: boolean
  } & HookCallbackOptions
): Promise<string> {
  // Clear the staging area, our diffs reflect the difference between the
  // working directory and the last commit (if any) so our commits should
  // do the same thing.
  await unstageAll(repository)

  await stageFiles(repository, files)

  const args = ['-F', '-']

  if (options?.amend) {
    args.push('--amend')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  if (options?.signOff) {
    args.push('--signoff')
  }

  if (options?.allowEmpty) {
    args.push('--allow-empty')
  }

  const result = await git(
    ['commit', ...args],
    repository.path,
    'createCommit',
    {
      stdin: message,
      // https://git-scm.com/docs/githooks/2.46.1
      interceptHooks: [
        'pre-commit',
        'prepare-commit-msg',
        'commit-msg',
        'post-commit',
        ...(options?.amend ? ['post-rewrite'] : []),
        'pre-auto-gc',
      ],
      onHookProgress: options?.onHookProgress,
      onHookFailure: options?.onHookFailure,
      onTerminalOutputAvailable: options?.onTerminalOutputAvailable,
    }
  )
  return parseCommitSHA(result)
}
