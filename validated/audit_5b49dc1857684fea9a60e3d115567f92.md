### Title
`git submodule update --init --recursive` re-enables the disabled `file://` submodule protocol via `allowFileProtocol`, permitting attacker-controlled submodule URLs to clone arbitrary local paths into the working tree - ([File: app/src/lib/git/submodule.ts])

### Summary
Git hardened itself (fix for CVE-2022-39253) by disabling the `file://` transport for submodules by default, precisely because a malicious repository can declare a submodule whose URL is `file:///some/local/path` and have `git submodule update --init --recursive` clone that local path (potentially outside the intended repository, e.g. a sibling checkout, `~/.ssh`, or any directory readable by the user) directly into the working tree. GitHub Desktop's `updateSubmodulesAfterOperation` function keeps this protection off by default but exposes a callable `allowFileProtocol` flag that, when `true`, re-enables the historically-exploited behavior via `-c protocol.file.allow=always`.

### Finding Description
`updateSubmodulesAfterOperation` in [1](#0-0)  builds the `submodule update --init --recursive` args and conditionally injects `-c protocol.file.allow=always` when `allowFileProtocol` is `true`. This flag is threaded through `checkoutBranch` and `checkoutCommit` in [2](#0-1)  and [3](#0-2) , both of which default the parameter to `false` but accept `true` from callers.

The broken invariant is the same as the fToken/xToken report: a protective restriction (Git's default refusal to resolve `file://` submodule URLs, added specifically to stop this class of local-file exfiltration/read) was deliberately reintroduced as an opt-in bypass in application code, and the guard that decides *when* it's safe to bypass depends entirely on the caller's judgment rather than on the trustworthiness of the repository content itself. Just as `Market.mint()` no longer checks whether the system is in an unsafe state before allowing repeated minting, `updateSubmodulesAfterOperation` does not itself validate whether the submodule URLs in the checked-out tree are safe (e.g., reject `file://` URLs pointing outside the repo's already-cloned directories) before re-enabling the disabled protocol — it simply trusts the boolean passed down from the checkout call site.

### Impact Explanation
If `allowFileProtocol=true` is reachable for content originating from an untrusted/attacker-controlled remote (a cloned or fetched repository, or a checked-out PR branch), an attacker can commit a `.gitmodules` entry with a `file://` URL pointing at any path readable by the victim (e.g., another local repository, a directory containing SSH keys, or config files) and have Desktop's submodule update silently clone/copy that path's Git history contents into the visible working directory. This can lead to reading/writing outside the intended repository boundary, silent corruption of the tree that the user might subsequently commit and push (exfiltrating sensitive local data to the attacker's remote), which matches the report's core theme: a previously-mandatory safety restriction removed, permitting compounding damage when repeatedly triggered (each additional attacker-supplied submodule/checkout amplifies exposure the same way each extra `mint()` call amplifies undercollateralization).

### Likelihood Explanation
Medium, mirroring the original report's medium rating. Git's own maintainers judged this scenario serious enough to change the *default* upstream behavior, and Desktop's code deliberately reintroduces the disabled behavior in a helper that is called from branch/commit checkout flows tied to remote content (e.g., pull-request checkouts and branch switches, which do operate on remote-supplied data). I could not fully verify, within the current tool budget, every UI call site where `checkoutBranch`/`checkoutCommit` is invoked with `allowFileProtocol=true` versus `false` (grep found 8 references in `app-store.ts` but I did not inspect each argument value in this pass), so it remains unconfirmed whether the `true` path is reachable purely from opening/checking out an untrusted remote repository versus being restricted to trusted local-clone scenarios only.

### Recommendation
Do not thread a raw `allowFileProtocol` boolean from UI-level call sites into `updateSubmodulesAfterOperation`. Instead, validate submodule URLs before update: reject or require explicit user confirmation for `file://` submodule URLs that resolve outside the repository's own already-fetched objects, regardless of the caller-supplied flag, mirroring the recommendation to check system state before allowing an action rather than trusting caller-supplied intent.

### Proof of Concept
1. Attacker publishes a repository (or a PR branch) whose `.gitmodules` includes:
   ```
   [submodule "leak"]
     path = leak
     url = file:///Users/victim/.ssh
   ```
2. Victim clones/fetches and checks out this branch in GitHub Desktop.
3. If the checkout path that runs invokes `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true` (per [4](#0-3) ), `updateSubmodulesAfterOperation` executes `git -c protocol.file.allow=always submodule update --init --recursive` ( [5](#0-4) ), cloning `/Users/victim/.ssh` into the `leak/` directory of the working tree.
4. The victim's private key material now sits inside a tracked (or trackable) path in their repository; if committed/pushed, it is exfiltrated to the attacker's remote.

Given the unresolved uncertainty about which exact call site passes `true`, this should be treated as a concrete code-level candidate requiring confirmation of the calling context (background Devin session) rather than a fully proven end-to-end exploit chain.
