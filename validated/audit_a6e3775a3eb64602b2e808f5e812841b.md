### Title
ThresholdKeys::read accepts attacker-fully-controlled secret share and verification shares with no consistency check, letting a crafted key file install an attacker-known group key — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes the participant index `i`, the interpolation variant (including a fully attacker-chosen `Interpolation::Constant` coefficient vector), the secret share scalar, and all `n` verification shares, then hands them to `ThresholdKeys::new`. `ThresholdKeys::new` validates only counts, index ranges, and the `Constant`-interpolation `t == n` restriction; it never checks that the deserialized `secret_share` corresponds to `verification_shares[i]` (i.e. `G * secret_share == verification_shares[i]`), and never checks that the verification shares lie on a consistent polynomial. The group key is then computed solely as the interpolation of attacker-supplied `verification_shares[1..=t]`. This mirrors the reported bug class: a security mechanism (the PedPoP DKG's per-share verification in `crypto/dkg/pedpop/src/lib.rs`) is silently bypassed because serialized "internal" fields are trusted without re-validation.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` (lines 573-632) reads `t`, `n`, `i`, an interpolation tag (`0` = Constant with `n` free scalars, `1` = Lagrange), a `secret_share` scalar via `C::read_F`, and `n` verification-share points via `C::read_G`, then calls `ThresholdKeys::new`. `ThresholdKeys::new` (lines 349-391) performs only:

- `verification_shares.len() == n` and each participant index `<= n` (lines 355-365)
- `t == n` when `Interpolation::Constant` (lines 367-374)
- `group_key = Σ_{i in 1..=t} verification_shares[i] * interpolation_factor(i, 1..=t)` (lines 376-378)

It never verifies `self.secret_share * G == verification_shares[params.i()]`. In the honest protocol path, PedPoP's `calculate_share` verifies every received share against the sender's commitments before constructing `ThresholdKeys` (`crypto/dkg/pedpop/src/lib.rs` lines 487-499, `share_verification_statements`). The deserialization path skips all of this — the exact analog of a config field that bypasses `trust_remote_code`. A subsequent `view()` (`crypto/dkg/src/lib.rs` lines 463-533) interpolates the bogus `secret_share` and emits FROST signature shares on demand, while `group_key()` reports whatever key the attacker encoded.

### Impact Explanation
Two concrete impacts follow from an unprivileged party feeding crafted bytes to `ThresholdKeys::read`:

1. **Attacker-controlled group key / silent key substitution.** The attacker picks a secret `s`, sets `secret_share = s`, `verification_shares[i] = G*s`, and chooses the remaining verification shares as points on a degree `t-1` polynomial whose interpolated constant term is a key `K` they fully know. `ThresholdKeys::new` returns keys whose `group_key()` is `K`. Any integrator that loads these bytes (restored key file, replicated DB, imported share) will attribute incoming funds to `K` — a key the attacker can spend from unilaterally — while the victim node will also sign for `K` on request, making the theft indistinguishable from legitimate operation. Funds are reported received under a group key the attacker, not the presumed validator set, controls.

2. **False blame / slashing of the honest node.** If the attacker instead sets `verification_shares[i] != G*secret_share`, the node emits FROST signature shares that fail verification against `verification_share(i)`, so every other participant identifies this node as malicious — grounds for slashing — even though the node behaved honestly and merely loaded corrupted bytes.

### Likelihood Explanation
Exploitation requires the attacker to supply the serialized `ThresholdKeys` blob. In `processor/src/key_gen.rs` (`GeneratedKeysDb::read_keys`, lines 47-62) this path reads processor DB state, which is normally internally written; however the format is the documented serialization of `ThresholdKeys` and is consumed wherever key material is imported, restored, or replicated — precisely the untrusted-bytes-to-`ThresholdKeys::read` surface in scope. No DKG transcript, PoK, or PoP is consulted on this path, so a single crafted blob is sufficient; there is no interactive requirement. Severity is bounded to Medium-High because reachability depends on key-material import/restore flows rather than pure network messages.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), after constructing the keys, verify `C::generator() * secret_share == verification_shares[params.i()]` and return a `DkgError` on mismatch. This re-establishes the share/commitment binding that PedPoP guarantees during interactive key generation and closes the deserialization bypass.

### Proof of Concept
```rust
// crypto/dkg/src/lib.rs context: ThresholdKeys::read -> ThresholdKeys::new
// For Secp256k1 (or any C), attacker with known scalar `a`:

let a = Zeroizing::new(C::F::random(&mut OsRng));       // attacker's secret
let i = Participant::new(1).unwrap();

// verification_shares[1] = a*G (consistent share for ourselves)
// choose verification_shares[2..=t] such that interpolation over 1..=t
// yields a group key K = k*G for a k the attacker knows, e.g. for t = n = 2
// with Lagrange factors l1 = 2, l2 = -1:
//   K = 2*(a*G) + V2  =>  V2 = k*G - 2*a*G = (k - 2a)*G   (attacker knows k, a)
let k = Zeroizing::new(C::F::random(&mut OsRng));
let v1 = C::generator() * a.deref();
let v2 = C::generator() * (k.deref() - (C::F::from(2) * a.deref()));

// Serialize: C::ID, t=2, n=2, i=1, interpolation tag 1 (Lagrange),
// secret_share = a, verification_shares = [v1, v2]
// ThresholdKeys::read succeeds; group_key() == k*G, fully known to attacker.
let keys = ThresholdKeys::<C>::read(&mut crafted.as_slice()).unwrap();
assert_eq!(keys.group_key(), C::generator() * k.deref());
// Node will now sign under attacker-known key k as if it were the multisig key.
```

The read path performs no check tying `secret_share` to `verification_shares[1]` or to the interpolated group key, so the crafted file is accepted unconditionally.
