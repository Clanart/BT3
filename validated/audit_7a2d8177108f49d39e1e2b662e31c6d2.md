## Valid Finding

### Title
Unbounded memory growth in `Banlist::banned` via unauthenticated self-signed QUIC identities used for BLS certificate banning - (File: `net-utils/src/banlist.rs`)

### Summary
`Banlist<T>` stores banned entries in a plain `HashMap<T, Instant>` behind an `RwLock` with no maximum-size cap or LRU eviction. [1](#0-0)  The only cleanup mechanism is `prune()`, which removes an entry only once its ban `expires_at` timestamp has passed. [2](#0-1)  The caller (`SimpleQosBanlist` used by the BLS sig-verifier) schedules `prune()` once per `BANLIST_PRUNE_INTERVAL` (1 hour), but bans issued by the BLS sig-verifier use `BAN_TIMEOUT = 48 hours`. [3](#0-2) [4](#0-3)  Because `prune()` cannot remove any entry before its 48‑hour expiry, the map can only grow for the entire 48‑hour window regardless of how frequently `prune()` runs.

Crucially, in `bls_cert_sigverify.rs`, the pubkey used as the ban key for network-received certificates is taken directly from the QUIC connection's `remote_pubkey()` — the self-signed TLS/QUIC identity — with no cross-check against the validator/stake set before the ban call: [5](#0-4) 
This differs from the vote path (`keep_vote`), where `sender_identity_pubkey` is validated against `rank_map.node_pubkey_to_stake_entry` before the message is ever queued for verification/potential banning. [6](#0-5)  For certificates, no such stake check gates `add_certificate_to_group`, so any peer that can complete a QUIC handshake (even unstaked) and send one certificate packet that later fails `verify_cert` will have its self-chosen, unauthenticated `remote_pubkey` inserted into the shared `SimpleQosBanlist`/`Banlist` via `handle_cert_verify_error` → `banlist.ban(sender_identity_pubkey, BAN_TIMEOUT)`. [7](#0-6) 

### Finding Description
An unprivileged/unstaked peer can:
1. Establish a QUIC connection to the validator's simple-QoS server using a freshly generated, self-signed identity keypair (admitted into the unstaked connection table, which exists specifically to allow connections without stake).
2. Send a single malformed/invalid BLS certificate packet over that connection.
3. Have `verify_cert` fail, triggering `banlist.ban(sender_identity_pubkey, BAN_TIMEOUT)` with `BAN_TIMEOUT = 48 hours`, inserting a brand-new `Pubkey → Instant` entry into `Banlist::banned`.
4. Immediately drop/close the connection and repeat with a new random identity.

Because `Banlist::ban()` unconditionally inserts into the `HashMap` with no cap, and `prune()` cannot evict any entry until its 48-hour timeout elapses, the number of live entries is bounded only by how many distinct self-signed identities the attacker can churn through connections in 48 hours — not by any application-level limit. The unstaked connection admission control bounds concurrent connections, but not the cumulative count of connections/identities used over time, since each connection can be extremely short-lived (open, send one bad cert, disconnect).

### Impact Explanation
This is a non-RPC remote memory exhaustion vector against the validator process: an unprivileged, unstaked network peer can force sustained growth of an in-memory `HashMap` for up to 48 hours with no size ceiling, degrading validator memory and requiring operator intervention (restart) to recover, consistent with the "non-RPC remote exhaustion/crash" impact category.

### Likelihood Explanation
Exploitation requires only a network connection and the ability to construct/send an invalid BLS certificate — no stake and no valid identity are needed, since the banned key is the attacker's own self-chosen QUIC identity taken from `remote_pubkey()` prior to any stake validation. The rate is bounded by QUIC handshake cost (asymmetric crypto) rather than by any per-identity/global cap in `Banlist`, so a moderately resourced attacker could sustain a meaningful entry-growth rate over the 48-hour window before any pruning is possible.

### Recommendation
Add a maximum-size cap (e.g., LRU or bounded map) to `Banlist::banned` independent of the caller's prune cadence, and/or validate `sender_identity_pubkey` against the current stake/rank map (as already done for votes in `keep_vote`) before banning certificate senders in `bls_cert_sigverify.rs`, so that unauthenticated/unstaked self-signed identities cannot be used as ban keys.

### Proof of Concept
```rust
// net-utils/src/banlist.rs - conceptual PoC demonstrating unbounded growth
#[test]
fn test_banlist_has_no_cap() {
    let banlist = Banlist::<Pubkey>::default();
    for _ in 0..1_000_000 {
        // Each call simulates a distinct self-signed QUIC identity triggering
        // a ban via an invalid certificate/vote, as in bls_cert_sigverify.rs
        banlist.ban(Pubkey::new_unique(), Duration::from_hours(48));
    }
    // No cap enforced; map grows linearly with number of unique keys.
    assert_eq!(banlist.banned.read().unwrap().len(), 1_000_000);
}
```

#[derive(Default)]
pub struct Banlist<T> {
    banned: RwLock<HashMap<T, Instant>>,
}

impl<T: Eq + Hash> Banlist<T> {
    /// Ban the `id` for the specified `timeout`
    ///
    /// Returns `true` if the `id` was already banned else `false`.
    pub fn ban(&self, id: T, timeout: Duration) -> bool {
        debug_assert!(!timeout.is_zero());
        debug_assert!(Instant::now().checked_add(timeout).is_some());
        let Some(expires_at) = Instant::now().checked_add(timeout) else {
            return false;
        };
        let prev = self.banned.write().unwrap().insert(id, expires_at);
        debug_assert!(prev < Some(expires_at));
        prev.is_some()
    }
