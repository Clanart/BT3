### Title
Wrong participant's preprocess removed due to threshold-index/MuSig-index confusion, causing self-inflicted `InvalidPreprocess` errors and wrongful fatal-slash votes — (`coordinator/src/tributary/signing_protocol.rs`)

### Summary
`threshold_i_map_to_keys_and_musig_i_map` re-keys the preprocess map from threshold share indexes (`Participant` values in the DKG's per-share index space) to sequential MuSig indexes (`raw_i + 1` over the sorted validator list), but then removes the local validator's own empty placeholder using `our_threshold_i` — a value in the *threshold* index space — against the *MuSig*-keyed map. Whenever these index spaces diverge, the wrong participant's preprocess is deleted and our own empty entry is left behind. This is the Serai analog of the wolfSSL incomplete-fix pattern: an error/cleanup path operating on the wrong (already-consumed/mis-indexed) object after attacker-influenced state changes. A malicious validator who gets themselves removed mid-attempt shifts the index mapping for everyone, causing every honest validator's `complete()` to fail and publish a `RemoveParticipantDueToDkg` vote against an innocent validator.

### Finding Description
In `threshold_i_map_to_keys_and_musig_i_map` (`coordinator/src/tributary/signing_protocol.rs:208-250`):

- Our own threshold index is computed and an empty placeholder is inserted into the incoming map, which is keyed by threshold `Participant` indexes: `map.insert(our_threshold_i, vec![])` (line 219).
- The map is then rebuilt, assigning each validator a sequential MuSig index: `map.insert(Participant::new(musig_i).unwrap(), share)` where `musig_i = raw_i + 1` enumerates *validators* (lines 241-245).
- The cleanup step then runs `map.remove(&our_threshold_i)` (line 247). But `map` is now keyed by MuSig indexes, while `our_threshold_i` is a threshold share index obtained from `spec.i(removed, ...)` (line 216), whose `start` counts *shares*, not validators.

These two index spaces diverge whenever (a) any earlier validator controls multiple shares (`spec.i` returns `start..end` ranges, so share indexes outrun validator positions), or (b) any validator earlier in the ordering is listed in `removed`, shifting positions. In both cases `map.remove(&our_threshold_i)` deletes a *different* participant's preprocess bytes and leaves our own `vec![]` placeholder in the map.

Downstream, `SigningProtocol::share_internal` iterates the map and calls `machine.read_preprocess(...)` on each entry (lines 161-167). Our empty entry fails to parse, returning `Err(our_musig_i)`. In `DkgConfirmer::complete` (`coordinator/src/tributary/handle.rs:535-545`), an `Err(p)` triggers `self.spec.reverse_lookup_i(&removed, p)` — which maps `p` back through the *threshold* index space, yet `p` is a MuSig index — and publishes a signed `Transaction::RemoveParticipantDueToDkg` against whatever validator that mis-lookup returns.

### Impact Explanation
Two concrete impacts:

1. **Wrongful fatal slash of an honest validator.** Every validator executes `complete()` with identical inputs, so all honest nodes fail identically at `read_preprocess` on their own empty entry and emit `RemoveParticipantDueToDkg` votes naming the same (incorrectly resolved) participant. Per `handle.rs:276-283`, votes accumulate by the signer's share weight and `fatal_slash` fires at `t`. A coordinated-but-unintentional threshold of votes against an innocent validator is therefore achievable, causing loss of their bond — funds slashed for a party that did nothing wrong.
2. **DKG confirmation liveness failure.** `share()`/`generated_key_pair` (`handle.rs:47-60`) returns `Err` instead of a confirmation share, stalling `set_keys` publication and halting key rotation for the set.

### Likelihood Explanation
The trigger is attacker-influenced: `removed` for an attempt comes from `removed_as_of_dkg_attempt`, and a validator can get themselves removed (e.g., via DKG misbehavior/blame) — an action fully within an unprivileged validator's power — which shifts the MuSig ordering relative to threshold indexes for all subsequent validators in the set. The misfire also occurs naturally whenever the spec assigns multiple key shares to validators (the entire reason `spec.i` returns ranges and `check_sign_data_len` counts shares rather than validators). Because the code path is deterministic, once the index spaces diverge for an attempt, *every* honest validator hits it simultaneously, amplifying a single index shift into a threshold of wrongful slash votes. No memory unsafety is needed — the "freed/wrong object" is the mis-indexed map entry consumed by the cleanup `remove`.

### Recommendation
- Remove our own entry by our *MuSig* index, not the threshold index: compute our position in the sorted `participants` list (e.g., `sorted.iter().position(|(key, _)| *key == our_pubkey)`) and `map.remove(&Participant::new(pos + 1).unwrap())`, or skip inserting the placeholder into the rebuilt map entirely and drop it during the rekeying loop by comparing `threshold_i == our_threshold_i` before assigning `musig_i`.
- In `handle.rs`, when resolving `Err(p)` from `complete()`, map the participant back through the MuSig index space actually used by `share_internal` (the `raw_i + 1` enumeration), not `reverse_lookup_i` over threshold indexes — or better, have `share_internal` return the already-resolved validator key.
- Add a regression test with a validator set containing at least one multi-share validator and one mid-attempt removal, asserting `complete()` succeeds and blames the correct participant on failure.

### Proof of Concept
Concrete trace with `n = 3` validators where validator A holds shares `1..=2` (i.e., `spec.i(A) = 1..3`), B holds `3..4`, and C (us) holds `4..5`:

1. `our_threshold_i = 4` (C's `i.start`). Line 219 inserts `map[Participant(4)] = vec![]`.
2. Rekeying iterates sorted threshold indexes `{1, 3, 4}` → assigns `musig_i`: A→1, B→2, C→3. New map: `{1: A_pp, 2: B_pp, 3: vec![]}`.
3. `map.remove(&our_threshold_i)` removes `Participant(4)` — not present, so nothing is removed — **or**, with n=4 and C at threshold index 4 while musig position 3, it removes participant D's real preprocess. Either way our `vec![]` remains at key 3.
4. `share_internal` reads key 3's empty bytes → `read_preprocess` returns `Err` → `Err(Participant(3))`.
5. `complete()` catches `Err(3)`, calls `reverse_lookup_i(&removed, Participant(3))` → resolves threshold index 3 → **validator B**, not us.
6. All honest validators execute the identical computation and publish `RemoveParticipantDueToDkg` for B; B's accumulated votes reach `t` → `fatal_slash(B)` — an innocent validator slashed.

Attacker-controlled variant: D is a malicious validator who gets themselves removed during the attempt (deliberately, via a bad DKG share). C's threshold index stays `4`, but the sorted non-removed ordering shifts C's MuSig position, reintroducing the divergence and the same wrongful-slash cascade — triggered entirely by D's public, permitted actions.
