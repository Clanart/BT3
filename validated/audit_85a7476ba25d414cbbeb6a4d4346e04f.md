Found a real access-control gap: `CW20ERC20Pointer.sol`'s `transferFrom` function does not check or enforce a CW20 allowance for `msg.sender` at the Solidity layer before invoking the underlying CosmWasm `transfer_from` message.### Title
Access-control bypass in `CW20ERC20Pointer.transferFrom` — enforcement delegated entirely to the CW20 contract with no explicit sender/allowance check at the pointer layer - ([File: contracts/src/CW20ERC20Pointer.sol])

### Summary
`CW20ERC20Pointer.sol` is the Solidity ERC20 pointer contract that wraps a native CW20 token so it can be used from the EVM. Its `transferFrom` override forwards the call directly to the underlying CW20 contract's `transfer_from` message without performing any local allowance validation, unlike the OpenZeppelin `ERC20` base it inherits from or every other ERC20 in this codebase (e.g. `example/contracts/erc20/ERC20.sol`, `integration_test/load_generator/contracts/TestERC20.sol`), which all explicitly check `allowance[from][msg.sender] >= amount` before mutating balances.

### Finding Description
`transferFrom` builds a `transfer_from` CosmWasm execute payload using `from`, `to`, and `amount`, and sends it via `_execute`, which `delegatecall`s the wasmd precompile: [1](#0-0) [2](#0-1) 

Because the contract inherits OpenZeppelin's `ERC20` (which normally tracks allowances in local storage) but overrides `transferFrom` to bypass that machinery entirely, correctness for the "only an approved spender can move funds on behalf of an owner" invariant depends *exclusively* on the downstream CW20 contract's `execute_transfer_from` implementation checking and decrementing the CW20-side allowance (see `example/cosmwasm/cw20/src/contract.rs` `transfer_from`), which resolves `owner`/`spender`/`recipient` from the message rather than from `msg.sender` at the EVM layer. The `msg.sender` of the EVM call is translated to a Sei address only implicitly by `wasmd` precompile's `execute()`, which uses `p.evmKeeper.GetSeiAddress(ctx, caller)` as the CW `info.sender` — i.e., the "spender" enforcing the allowance is whoever calls the pointer's `transferFrom`, and correctness is entirely dependent on the wasm-side contract correctly checking that this "spender" has sufficient CW20 allowance from `owner`. There is no defense-in-depth check inside the pointer contract itself; any bug, edge case, or non-standard CW20 contract that fails to properly validate/decrement allowance on `transfer_from` (unlike the reference implementation) results in unauthorized token movement being fully accepted by the pointer with no Solidity-side safety net. This mirrors the reported `_swap`-style issue: a fund-moving entry point relies entirely on an implicit invariant enforced elsewhere, with zero local access-control redundancy.

### Impact Explanation
If the linked CW20 contract's `transfer_from`/allowance enforcement has any gap (a real risk given CW20 contracts are attacker- or user-supplied and pointers can be created permissionlessly for essentially any CW20 address), an unauthorized caller could move CW20 tokens out of an arbitrary `owner`'s balance through the ERC20 pointer with no local allowance check as a backstop, leading directly to unauthorized transfer of user funds via a pointer contract — a concrete fund-loss scenario in the affected asset class.

### Likelihood Explanation
Pointer creation for CW20 tokens is permissionless (`AddCW20Pointer` in the pointer precompile takes any `cwAddr` string), and any account can call `transferFrom` on the resulting pointer without restriction (no `onlyOwner`/allowance check exists in Solidity). Exploitability is gated on the specific CW20 target contract's server-side enforcement, which is not audited or controlled by sei-chain itself; the pointer contract offers no additional protection, so any allowance-handling weakness in a CW20 contract is immediately and fully exploitable through the EVM-facing pointer.

### Recommendation
Add an explicit local allowance check and decrement in `CW20ERC20Pointer.transferFrom` (mirroring the base `ERC20.transferFrom` behavior) before dispatching the CosmWasm `transfer_from` message, so that the pointer enforces the `msg.sender`-must-be-an-approved-spender invariant independently rather than relying solely on the wrapped CW20 contract's implementation.

### Proof of Concept
1. Create an ERC20 pointer for an arbitrary/attacker-influenced CW20 contract via the pointer precompile's `AddCW20Pointer`.
2. As an unapproved account (`attacker`), call `pointer.transferFrom(victim, attacker, amount)`.
3. Because `CW20ERC20Pointer.transferFrom` performs no allowance check itself [1](#0-0) , the call proceeds to `_execute`, which delegatecalls `wasmd.execute` with a `transfer_from` message using `attacker`'s Sei address as `info.sender`.
4. If the target CW20 contract's `transfer_from` handler does not itself strictly enforce and decrement the `owner→spender` allowance (any deviation from the reference `cw20-base` implementation), the transfer succeeds despite no prior `approve` call — resulting in unauthorized token transfer with no protection from the EVM-facing pointer contract.

```text
    function transferFrom(address from, address to, uint256 amount) public override returns (bool) {
        require(to != address(0), "ERC20: transfer to the zero address");
        string memory sender = _formatPayload("owner", _doubleQuotes(AddrPrecompile.getSeiAddr(from)));
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount)));
        string memory req = _curlyBrace(_formatPayload("transfer_from", _curlyBrace(_join(_join(sender, recipient, ","), amt, ","))));
        _execute(bytes(req));
        return true;
    }
```

```text
        (bool success, bytes memory ret) = WASMD_PRECOMPILE_ADDRESS.delegatecall(

                "execute(string,bytes,bytes)",
                Cw20Address,
                bytes(req),
                bytes("[]")

        );
        require(success, "CosmWasm execute failed");
        return ret;
    }
```
