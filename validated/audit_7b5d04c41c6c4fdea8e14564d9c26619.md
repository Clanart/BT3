### Title
`Scanner::scan_block` credits immature coinbase outputs as spendable received funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner::scan_block` iterates `block.txdata` unconditionally, including `txdata[0]` (the coinbase transaction). Any output in a coinbase paying the watched tweaked key is returned as a `ReceivedOutput` indistinguishable from a normal output. Coinbase outputs are immature for 100 blocks and cannot be spent, so the scanner reports funds as received that are not actually spendable — the same "value accepted but not usable/credited" shape as `_dontMint` silently dropping the payment from `creditsOf`.

### Finding Description
`scan_transaction` matches only `output.script_pubkey` against registered scripts (line 205) and emits a `ReceivedOutput { offset, output, outpoint }` carrying the output's claimed value. `scan_block` then calls `scan_transaction` on every transaction in the block, including the coinbase (lines 221–227). A miner — an unprivileged party producing a Bitcoin block — can include a coinbase output paying the multisig's P2TR script. The scanner reports it as received value, but any `SignableTransaction::new` built over it produces a transaction Bitcoin consensus rejects (BIP-34 coinbase maturity), and the contained `TxOut.value`/prevout data feed the sighash in `TransactionSignMachine::sign` (`Prevouts::All`, send.rs L373–390), so the attempted spend is invalid.

The only guard is a doc comment on `scan_block` stating a "post-processing pass is needed" — nothing in the type system or API prevents, marks, or filters the immature output; it is returned in the same `Vec<ReceivedOutput>` as valid outputs.

### Impact Explanation
Funds are reported received that are not spendable. Downstream consumers that treat every `ReceivedOutput` as immediately spendable will construct spends that are consensus-invalid (coinbase < 100 confirmations), causing the transaction (and any legitimate inputs bundled with it under `Prevouts::All`) to be rejected, or permanently tracking a "received" balance that can never resolve if the coinbase is later reorged.

### Likelihood Explanation
Any miner can pay the multisig address in a coinbase output at zero cost to themselves beyond forgoing fee redirection; mining pools occasionally send coinbase outputs to arbitrary addresses. No threshold, collusion, or privileged position is needed — only producing a block or paying a pool that does.

### Recommendation
In `scan_block`, skip `block.txdata[0]` (or return coinbase-derived outputs in a separate, explicitly-marked channel with the block height required for maturity). Alternatively, record a maturity flag on `ReceivedOutput` so consumers cannot conflate immature and spendable funds.

### Proof of Concept
```rust
// Construct a block whose coinbase pays the scanner's P2TR script.
let scanner = Scanner::new(group_key).unwrap();
let mut block = honest_block();
block.txdata[0].output.push(TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: p2tr_script_buf(group_key).unwrap(),
});

let received = scanner.scan_block(&block);
// `received` contains the coinbase output as a normal ReceivedOutput,
// indistinguishable from spendable outputs, despite 100-block maturity.
assert_eq!(received.last().unwrap().value(), 100_000);
```
