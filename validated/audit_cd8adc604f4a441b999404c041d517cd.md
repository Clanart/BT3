### Title
Attacker-supplied `ThresholdKeys` can advertise a group key that unanimous signers cannot reconstruct - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` and `ThresholdKeys::new` accept an independent verification share for every participant, but derive the advertised `group_key` only from participants `1..=t`. The code never proves that all `n` verification shares lie on the same threshold polynomial. An attacker can therefore provide a serialized key package whose individual shares are internally valid while different signing sets reconstruct different secrets. This mirrors the reported bug class: the aggregate value is calculated from a different quantity than the sum represented by the participants’ individual shares.

### Finding Description
`ThresholdKeys::read` deserializes a secret share and `n` verification shares, then calls `ThresholdKeys::new` without checking that the shares define one consistent threshold sharing. [1](#0-0) 

`ThresholdKeys::new` only checks the number and indexes of the verification shares. It then derives `group_key` exclusively from verification shares `1..=t`. [2](#0-1) 

For a `t = 2, n = 3` key, this means the advertised group key is the interpolation of participants 1 and 2. However, `ThresholdKeys::view` permits any signing set containing between `t` and `n` participants and calculates each participant’s secret and verification share using that selected set. [3](#0-2) 

Consequently, an attacker can choose arbitrary scalars `x1`, `x2`, and `x3`, publish `V_i = G * x_i`, and give participant `i` the corresponding secret `x_i`. Every participant’s own share matches its verification share, but the verification shares do not necessarily represent one degree-`t - 1` polynomial.

During FROST completion, all shares are summed and first verified as one signature against the advertised group key. [4](#0-3)  If that aggregate check fails, each share is separately checked against its interpolated verification share. [5](#0-4)  The crafted shares pass those individual checks because `G * x_i == V_i`, but their sum still does not equal the advertised group key.

### Impact Explanation
A system that imports `ThresholdKeys` through `ThresholdKeys::read` can report an attacker-controlled `group_key` whose advertised signing behavior is inconsistent with the shares supplied to participants.

For the `2-of-3` example:

- The advertised group secret is reconstructed from participants 1 and 2.
- Participants `{2, 3}` reconstruct a different secret.
- Even unanimous participants `{1, 2, 3}` generally reconstruct a third secret.
- Signature shares can pass individual verification while the final signature fails against the advertised key.

If this group key is used as a Bitcoin key, funds sent to it may be unspendable by the intended signing set. Because the attacker selected the underlying `x_i` values, the attacker may also know the scalar reconstructed by participants 1 and 2 and can sign for the advertised key independently.

### Likelihood Explanation
The attack requires an application to accept serialized `ThresholdKeys` or verification-share data from an untrusted party. That input path is explicitly exposed by `ThresholdKeys::read`, which accepts attacker-controlled field and group encodings before constructing the key object. [6](#0-5) 

No malicious validator, collusion, leaked honest key, or invalid curve encoding is required. All points and scalars can be canonical and individually well-formed; the vulnerability is that their aggregate semantic relationship is not validated.

### Recommendation
`ThresholdKeys::new` must reject semantically inconsistent key material:

1. Verify the local secret share matches its verification share:
   `C::generator() * secret_share == verification_shares[params.i()]`.
2. Verify all `n` verification shares lie on the same degree-`t - 1` polynomial. For Lagrange interpolation, reconstruct the polynomial implied by the first `t` shares and compare its evaluation at every participant index with the corresponding verification share.
3. Apply equivalent consistency validation to `Interpolation::Constant`.
4. Perform these checks in both `ThresholdKeys::new` and all deserialization paths, including `ThresholdKeys::read`.
5. Add tests where all encodings are canonical and every `V_i = G * x_i`, but the `x_i` values do not form a valid threshold sharing. Such keys must be rejected rather than produce a `group_key` reachable only by one privileged subset.

### Proof of Concept
The following deterministic construction uses `t = 2` and `n = 3`. It does not require malformed encodings; every verification share is a valid public key corresponding to its supplied secret share.

```rust
use core::ops::Deref;
use std::collections::HashMap;
use zeroize::Zeroizing;
use dalek_ff_group::Ed25519 as C;
use ciphersuite::{
  group::{ff::Field, Group, GroupEncoding},
  Ciphersuite,
};
use dkg::{ThresholdKeys, ThresholdParams, Participant, Interpolation};

fn keys_for(
  i: u16,
  secret: C::F,
  verification_shares: HashMap<Participant, C::G>,
) -> ThresholdKeys<C> {
  ThresholdKeys::new(
    ThresholdParams::new(2, 3, Participant::new(i).unwrap()).unwrap(),
    Interpolation::Lagrange,
    Zeroizing::new(secret),
    verification_shares,
  )
  .unwrap()
}

#[test]
fn inconsistent_verification_shares_create_unreachable_group_key() {
  let p1 = Participant::new(1).unwrap();
  let p2 = Participant::new(2).unwrap();
  let p3 = Participant::new(3).unwrap();

  // Arbitrary secrets, intentionally not generated as one degree-1 polynomial.
  let x1 = C::F::from(11);
  let x2 = C::F::from(17);
  let x3 = C::F::from(29);

  let verification_shares = HashMap::from([
    (p1, C::generator() * x1),
    (p2, C::generator() * x2),
    (p3, C::generator() * x3),
  ]);

  let keys1 = keys_for(1, x1, verification_shares.clone());
  let keys2 = keys_for(2, x2, verification_shares.clone());
  let keys3 = keys_for(3, x3, verification_shares);

  // group_key is reconstructed only from participants {1, 2}:
  // lambda_1 = 2, lambda_2 = -1.
  assert_eq!(
    keys1.group_key(),
    C::generator() * ((x1 * C::F::from(2)) - x2),
  );

  // Now use the unanimous set {1, 2, 3}.
  let included = vec![p1, p2, p3];
  let view1 = keys1.view(included.clone()).unwrap();
  let view2 = keys2.view(included.clone()).unwrap();
  let view3 = keys3.view(included.clone()).unwrap();

  // Each private share is valid against its interpolated public verification share.
  assert_eq!(
    C::generator() * view1.secret_share().deref(),
    view1.verification_share(p1),
  );
  assert_eq!(
    C::generator() * view2.secret_share().deref(),
    view2.verification_share(p2),
  );
  assert_eq!(
    C::generator() * view3.secret_share().deref(),
    view3.verification_share(p3),
  );

  // For x = 0, the three-party Lagrange factors are 3, -3, and 1.
  let unanimous_secret =
    (x1 * C::F::from(3)) - (x2 * C::F::from(3)) + x3;

  // With x1=11, x2=17, x3=29:
  // - advertised secret from {1,2}: 2*11 - 17 = 5
  // - unanimous reconstruction: 3*11 - 3*17 + 29 = 11
  assert_eq!(unanimous_secret, C::F::from(11));
  assert_ne!(
    C::generator() * unanimous_secret,
    keys1.group_key(),
  );
}
```

The same state is reachable through `ThresholdKeys::read` by serializing each participant’s `i`, secret `x_i`, the Lagrange marker, and the common `V_i` vector. Each resulting FROST share can satisfy `verify_share`, while `AlgorithmSignatureMachine::complete` cannot produce a valid aggregate signature for the advertised `group_key`.
