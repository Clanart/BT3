Found the core analog: the auctioneer signature in the Kaia auction module verifies only that *a* signature bytes-blob was co-signed by the auctioneer — it never re-derives or binds to the actual bid content (sender, amount, target tx, data, etc.). This is structurally the same CWE-347 class as the RADIUS bug: a value ("first UDP datagram" / "AuctioneerSig over the raw SearcherSig bytes") is accepted as authoritative proof without cryptographically binding it to the full context that must be authorized.

### Title
Auctioneer Signature Does Not Bind to Bid Content, Allowing MaxGasPrice/Version Field Substitution in Auction Bids - (File: kaiax/auction/bid.go, kaiax/auction/eip712.go)

### Summary
`Bid.ValidateAuctioneerSig` verifies the auctioneer's signature over `GetEthSignedMessageHash()`, which hashes only the raw `SearcherSig` bytes rather than any digest of the bid's actual field values [1](#0-0) . This means the auctioneer's cryptographic approval never has direct algebraic binding to the true content it is meant to authorize; it merely and blindly ratifies "some 65-byte string" that was passed to it. Whether this string genuinely resulted from a canonical, unambiguous encoding of the bid it's supposed to approve depends entirely on the searcher-signature digest generation (`GetHashTypedData`) being collision-free and unambiguous across the two EIP-712 versions it supports.

### Finding Description
`bp.validateBidSigs` requires both `ValidateSearcherSig` and `ValidateAuctioneerSig` to pass before a bid is admitted to the pool [2](#0-1) . `ValidateSearcherSig` recovers the sender from an EIP-712 digest chosen by `bp.auctionEntryPointVersion`, either the v2.1 struct (`auctionType`, no `maxGasPrice`) or v3.0 struct (`auctionTypeV3`, includes `maxGasPrice`) [3](#0-2) [4](#0-3) . Critically, when the active version is `AuctionVersionV2` (`"0.0.1"`), the `MaxGasPrice` field of `BidData` is completely excluded from the signed struct hash [5](#0-4) , yet `BidData.MaxGasPrice` is still present as a normal (optional) field on the wire `Bid` object [6](#0-5) .

`ValidateAuctioneerSig` then only checks that the auctioneer signed `keccak256("\x19Ethereum Signed Message:\n65" + SearcherSig)` — i.e., it authenticates "the auctioneer approved that this particular 65-byte SearcherSig blob exists," not "the auctioneer approved this bid's full field set" [7](#0-6) . Because `MaxGasPrice` (and any other field not included in the EIP-712 struct for the active version) is never covered by either signature, an attacker who obtains a valid `(SearcherSig, AuctioneerSig)` pair for a v2.1-signed bid can freely set/modify `bid.MaxGasPrice` (or fields outside the active struct hash) before submitting to `auction_submitBid`, and both signature checks will still pass, since `validateBidSigs` never re-derives or independently confirms that every wire field was actually part of what was cryptographically approved. This is directly analogous to the RADIUS flaw: a downstream consumer trusts an authentication artifact ("Access-Accept"/"AuctioneerSig") as proof of full-content integrity when the artifact only proves a narrower, decoupled fact.

### Impact Explanation
`MaxGasPrice` is intended to cap what gas price the winning bid tx will use; if it can be forged/tampered post-signature without invalidating either signature, an attacker-controlled bid could carry an unauthorized `MaxGasPrice` value into block-building and fee/settlement logic driven by `system.EncodeAuctionCallData`/`DecodeAuctionCallData`, which explicitly carries `MaxGasPrice` through the v3 ABI path [8](#0-7) . Depending on how the on-chain `AuctionEntryPoint` (whose real Solidity logic is only partially shown/stubbed in the mock contract, e.g. `_verifyInputIntegrity` in `AuctionEntryPointMock.sol` which has its real signature-check logic commented out) enforces `maxGasPrice` against actual execution price, this allows fee/priority abuse in the auction settlement flow: a searcher/attacker submits a bid whose signed searcher-approved parameters differ from what was actually authorized by the auctioneer's approval, undermining the auction's economic guarantees (a form of "acceptance of an invalid/unauthorized value" analogous to the report's "forged Access-Accept accepted as valid login").

### Likelihood Explanation
Exploitation requires the auction module to be running with `AuctionVersionV2` (i.e., `auctionEntryPointVersion == "0.0.1"`) and an attacker having captured or been given one valid `(SearcherSig, AuctioneerSig)` pair (e.g., their own legitimately-submitted bid, or one observed on the wire/p2p bid-gossip channel via `HandleBid`) [9](#0-8) . Any unprivileged auction participant/searcher who already interacts with `auction_submitBid` can attempt this tampering on their own bids without needing any additional secret. This is a Medium-to-High likelihood scenario for any deployment still running the v2.1 (`"0.0.1"`) struct, since the vulnerability is a straightforward missing-field-in-signature design gap, not a cryptographic break.

### Recommendation
Ensure every field carried in `BidData` (including `MaxGasPrice`) is part of the EIP-712 struct hash for every supported auction version, or reject/zero-force fields not covered by the active version's struct hash before use. Additionally, change `ValidateAuctioneerSig` to sign/verify over a digest of the full `BidData` (or the searcher's EIP-712 struct hash) rather than the raw `SearcherSig` bytes, so that the auctioneer's approval is directly and unambiguously bound to the bid's content rather than transitively/blindly trusting whatever the searcher-signature covers.

### Proof of Concept
1. Configure/observe an `AuctionEntryPoint` reporting `AUCTION_VERSION() == "0.0.1"` so `bp.auctionEntryPointVersion == AuctionVersionV2`.
2. As a searcher, submit a legitimate bid with `MaxGasPrice = X` via `auction_submitBid`; obtain the resulting `SearcherSig` and `AuctioneerSig` (self-observable, since the searcher is the one generating/submitting it).
3. Because `EncodeData()` for `AuctionVersionV2` never includes `MaxGasPrice` [5](#0-4) , the same `SearcherSig`/`AuctioneerSig` pair remains valid for the identical `BidData` with `MaxGasPrice` changed to any value `Y != X`.
4. Resubmit the bid with `BidData.MaxGasPrice = Y`; `bp.validateBidSigs` calls `ValidateSearcherSig` (passes, since the v2.1 digest doesn't depend on `MaxGasPrice`) and `ValidateAuctioneerSig` (passes, since it only checks the raw `SearcherSig` bytes) [10](#0-9) , so the tampered bid is accepted into the pool and forwarded to block building via `getBidTxGasLimit`/`system.EncodeAuctionCallData` [11](#0-10) .

**Uncertainty/limitations**: I was unable to inspect the real (non-mock, non-commented) on-chain `AuctionEntryPoint` Solidity contract logic that enforces `maxGasPrice` at execution time — only the test-only `AuctionEntryPointMock.sol` (with signature checks commented out) was found in the index. Whether `maxGasPrice` tampering translates into concrete value/fee theft depends on that contract's real enforcement logic, which the index may not fully contain; I recommend a full Devin session with repository access to confirm the production `AuctionEntryPoint` contract's use of `maxGasPrice` before treating impact severity as fully confirmed.

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}

func (bp *BidPool) getBidTxGasLimit(bid *auction.Bid) (uint64, error) {
	bp.auctionInfoMu.RLock()
	buffer := bp.bidTxGasBuffer
	bp.auctionInfoMu.RUnlock()

	data, err := system.EncodeAuctionCallData(bid, bp.auctionEntryPointVersion)
	if err != nil {
		return 0, err
	}

	rules := bp.ChainConfig.Rules(big.NewInt(int64(bid.BlockNumber)))
	intrinsicGas, err := types.IntrinsicGas(data, nil, nil, false, rules)
	if err != nil {
		return 0, err
	}
	floorDataGas := uint64(0)
	if rules.IsPrague {
		floorDataGas, err = blockchain.FloorDataGas(types.TxTypeEthereumDynamicFee, data, 0)
		if err != nil {
			return 0, err
		}
	}

	return max(intrinsicGas+bid.CallGasLimit+buffer, floorDataGas), nil

func (b *Bid) EncodeData() []byte {
	encoded := make([]byte, 0)
	encoded = append(encoded, b.TargetTxHash.Bytes()...)
	encoded = append(encoded, common.LeftPadBytes(common.Int64ToByteBigEndian(b.BlockNumber), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.Sender.Bytes(), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.To.Bytes(), 32)...)
	encoded = append(encoded, common.LeftPadBytes(common.Int64ToByteBigEndian(b.Nonce), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.Bid.Bytes(), 32)...)
	encoded = append(encoded, common.LeftPadBytes(common.Int64ToByteBigEndian(b.CallGasLimit), 32)...)

}

func (b *Bid) GetHashTypedData(chainId *big.Int, verifyingContract common.Address, version string) []byte {
	if chainId == nil {
		return nil
	}

	domain := EIP712Domain{
		EIP712DomainTypeHash: eip712TypeHash,
		NameHash:             auctionNameHash,
		VersionHash:          crypto.Keccak256Hash([]byte(version)),
		ChainId:              chainId,
		VerifyingContract:    verifyingContract,
	}

	domainSeparator := EncodeEIP712(domain)

	var structHash []byte
	if version == AuctionVersionV3 {
		structHash = EncodeEIP712(bidV3{b})
	} else if version == AuctionVersionV2 {
		structHash = EncodeEIP712(b)
	} else {
		// Unknown version: default to v2.1 typehash.
		structHash = EncodeEIP712(b)
	}

	return crypto.Keccak256([]byte{0x19, 0x01}, domainSeparator, structHash)
}
