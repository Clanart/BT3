### Title
`Scanner::scan_block` reports coinbase outputs as spendable received funds despite maturity lock - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over `block.txdata` including the coinbase transaction (`txdata[0]`) and returns matching outputs as ordinary `ReceivedOutput`s. A miner (unprivileged third party) can pay the multisig's registered script in a coinbase output, which Bitcoin consensus makes unspendable for 100 blocks. The scanner reports these funds as received, and nothing in the returned `ReceivedOutput` distinguishes them — they can be fed into `SignableTransaction::new` and signed, producing a transaction that will be rejected by the network.

### Finding Description
The Alchemix report's bug class is an unprivileged party using a public entry point to insert state that corrupts a later privileged/legitimate operation. The analog here is that any miner can, with only public data (the P2TR script pubkey, derivable from the well-known group key and the fixed `hash_to_F` offsets), deposit funds that `scan_block` reports as a normal received output but which are not yet spendable under consensus rules.

`scan_block` scans every transaction including the coinbase:

`networks/bitcoin/src/wallet/mod.rs:221-227`
```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

`scan_transaction` (lines 199-214) matches only `output.script_pubkey` against registered scripts and pushes a `ReceivedOutput` with no maturity marker. The only mitigation is a doc comment on `scan_block` stating "a post-processing pass is needed" — no enforcement. Notably, the downstream consumer in `processor/src/networks/bitcoin.rs:690-691` had to special-case this (`// Skip the coinbase transaction which is burdened by maturity`, `for tx in &block.txdata[1 ..]`), confirming the library function itself does not protect callers.

Any caller that uses `scan_block` directly (as the library's own test does at `networks/bitcoin/tests/wallet.rs:65`) will treat an immature coinbase output as available funds.

### Impact Explanation
A miner can grief the multisig wallet: the immature coinbase output is reported as received balance and can be selected as an input to `SignableTransaction`, causing a threshold signing ceremony to produce a transaction that is consensus-invalid until maturity. Worse, if an integrator credits deposits based on `scan_block` results, funds are reported received that are not spendable, matching the report's "incorrect index / corrupted received-state" impact shape. Repeated coinbase payments also inflate the UTXO set with unusable entries, degrading coin selection.

### Likelihood Explanation
Any miner who observes the protocol's P2TR address (public on-chain) can include an output paying to it in their coinbase transaction. This requires no privilege, no collusion, and no malformed input — only a valid Bitcoin block the miner already controls. The trigger is fully reachable with public inputs.

### Recommendation
In `Scanner::scan_block`, either skip `block.txdata[0]` or carry coinbase provenance into `ReceivedOutput` (e.g., an `immature: bool` / maturity height field) so callers cannot silently treat the output as spendable. At minimum, make the API fail-closed rather than relying on a doc-comment post-processing pass.
