### Title
Fee-on-transfer/deflationary LP tokens cause receipt-token over-minting in `WombatStaking.depositLP` - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.depositLP` transfers `_lpAmount` of the pool's `lpAddress` token from the caller and then mints exactly `_lpAmount` of `receiptToken` and forwards `_lpAmount` to `_toMasterWomAndSendReward`, without ever verifying how many tokens the contract actually received. This is the same root-cause pattern as the reported "non-standard tokens not properly accounted for" issue: any mismatch between the nominal transfer amount and the amount actually credited to the contract's balance results in over-minted receipt tokens backed by fewer real tokens.

### Finding Description
In `WombatStaking.deposit` (lines 242-270), the contract carefully measures the actual LP tokens received by taking a `beforeBalance`/`afterBalance` snapshot before minting receipt tokens: [1](#0-0) 

However, the sibling function `depositLP` (lines 272-287), which is reachable by any pool helper on behalf of an ordinary user, does not perform this check. It simply transfers `_lpAmount` and then mints `_lpAmount` of `receiptToken` directly: [2](#0-1) 

```
IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);
_toMasterWomAndSendReward(_lpAddress, _lpAmount, true);
IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);
```

If `poolInfo.lpAddress` for any registered pool is (or is later registered as) a token with fee-on-transfer, rebasing, or "transfer-max-means-whole-balance" semantics (the exact bug classes cited in the source report), the amount of tokens the contract actually receives can differ from `_lpAmount`. The receipt token, however, is minted 1:1 against the requested `_lpAmount`, not the amount actually held by the contract. This creates a permanent mismatch between the total receipt tokens in circulation (claims on staked LP) and the LP tokens the contract actually custodies, which are subsequently withdrawable through `WombatPoolHelper.depositLP` / `AnkrBNBPoolHelper.depositLP` public entry points that any wallet can call: [3](#0-2) [4](#0-3) 

This is reachable purely by an ordinary wallet calling `depositLP`/`withdraw` with no privileged role required — the vulnerability is in the accounting logic itself, not in any admin action.

### Impact Explanation
If the LP token accounted for in `depositLP` has any deflationary/rebasing/non-standard transfer behavior, users can mint more receipt tokens than the actual LP tokens deposited. Since receipt tokens are burned 1:1 for real LP tokens on withdrawal, over-minted receipt tokens allow a depositor to withdraw more LP tokens than they actually contributed, at the expense of other depositors — a direct theft/drain of pooled user funds and insolvency of the receipt-token/LP-token peg.

### Likelihood Explanation
Exploitability depends entirely on whether a pool is configured with such a non-standard `lpAddress` token; standard Wombat Asset LP tokens are not fee-on-transfer under normal operation. However, the code path itself performs no defensive `before/after` balance check (unlike the adjacent `deposit` function, which does), so the contract makes an implicit, undocumented trust assumption about the LP token's transfer behavior that is inconsistently enforced across its own deposit paths.

### Recommendation
Apply the same before/after balance accounting pattern already used in `deposit()` to `depositLP()`: measure `poolInfo.lpAddress` balance before and after the `safeTransferFrom` call, and mint/forward only the actual amount received (`afterBalance - beforeBalance`) instead of the nominal `_lpAmount`. Document that only standard, non-fee, non-rebasing ERC20 LP tokens should ever be registered via `registerPool`/`updatePoolHelper`.

### Proof of Concept
1. Assume a pool is registered (via `WombatStaking.registerPool`) whose `_lpAddress` implements a transfer fee or fee-on-transfer wrapper (or is later swapped via `updatePoolHelper`).
2. A user calls `WombatPoolHelper.depositLP(_lpAmount)` → `WombatStaking.depositLP(lpToken, _lpAmount, msg.sender)`.
3. `safeTransferFrom(_for, address(this), _lpAmount)` moves `_lpAmount` nominally, but the contract's actual balance only increases by `_lpAmount - fee`.
4. `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` mints the full nominal `_lpAmount` of receipt tokens regardless of the shortfall.
5. The user (or any user) can later call `withdraw` to redeem receipt tokens 1:1 for LP tokens, draining LP tokens contributed by other depositors since total receipt-token supply now exceeds actual LP token custody.
