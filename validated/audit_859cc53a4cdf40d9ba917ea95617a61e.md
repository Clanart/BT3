### Title
Payout attribution relies solely on unauthenticated OP_RETURN content, letting anyone attribute a payout to an arbitrary operator - (File: core/src/verifier.rs)

### Summary
`update_finalized_payouts` identifies the operator who fronted a withdrawal purely by parsing the first `OP_RETURN` output of the transaction that spends the withdrawal UTXO on-chain, via `get_first_op_return_output` + `parse_op_return_data` + `XOnlyPublicKey::from_slice`, with no check that the named operator actually constructed, signed, or funded that transaction. Because withdrawal UTXOs are spendable by whoever holds the withdrawer-provided signature (with attacker-chosen sighash flags such as `SIGHASH_ANYONECANPAY`), a third party can add its own funding input(s) and a forged `OP_RETURN` naming a victim operator's xonly public key, causing that operator to be falsely credited as the payer.

### Finding Description
The binding the code implicitly assumes is: `operator_xonly_pk recorded in DB == operator who actually funded/broadcast the payout tx`. In reality, the code only establishes: `operator_xonly_pk recorded in DB == whatever 32-byte value appears in the first OP_RETURN of the tx that happens to spend the withdrawal UTXO`, per [2](#0-1) . There is no signature check, no proof-of-funds check, and no reconciliation against the operator's own records at this point in the flow - the comment in the code even acknowledges the value can be `None` "if optimistic payout is used, or an operator constructed the payout tx wrong" [3](#0-2) , implicitly trusting whatever non-`None` value appears.

Because Bitcoin enforces single-spend, there is no literal "race" of two competing spends - whichever transaction actually spends the withdrawal UTXO becomes canonical. The attack surface is that the withdrawal UTXO's signature/sighash setup can permit a party other than the intended operator to construct and confirm the spending transaction (adding funding inputs and arbitrary extra outputs, including a forged OP_RETURN), depending on the sighash flags chosen when the withdrawal signature was created. Downstream, `PayoutCheckerTask::run_once` picks up the recorded `operator_xonly_pk` via `get_first_unhandled_payout_by_operator_xonly_pk` and immediately proceeds to `handle_finalized_payout`, `fetch_validate_and_store_lcp`, and `mark_payout_handled` for that operator [4](#0-3) , with no verification step in this path confirming operator involvement in constructing the payout transaction.

### Impact Explanation
If exploitable, this allows crediting an operator (or triggering its kickoff/reimbursement machinery) for a payout it never funded - matching the Critical impact category "an operator reimbursed for a payout it never funded." The blast radius could span any withdrawal/operator pair where the withdrawal UTXO's spending conditions permit third-party-constructed transactions.

### Likelihood Explanation
Exploitability is conditioned entirely on whether the withdrawal UTXO's signing/sighash setup (established at `withdraw()` time on the Citrea side) actually permits a non-operator party to construct the spending transaction with an attacker-chosen extra `OP_RETURN` output while still satisfying the signed output commitments. I was not able to fully verify within the available tool budget (1) the exact sighash flags enforced by the withdrawal/payout construction logic (whether `SIGHASH_ALL`/`SINGLE` commits the OP_RETURN output as part of the signed template, which would prevent attacker-injected OP_RETURN content), or (2) whether `Operator::handle_finalized_payout` performs any additional reconciliation against the operator's own payout records before committing state. Both of these directly determine whether the described attack is actually reachable, and I could not confirm or rule them out with certainty.

### Recommendation
Cannot be fully specified without confirming the sighash/template constraints above; if third parties can indeed inject/alter the OP_RETURN output on a withdrawal payout, the payout attribution should be cryptographically bound (e.g., requiring the OP_RETURN-named operator to co-sign or requiring the operator's own key to be provably one of the input signers) rather than trusting parsed OP_RETURN bytes alone.

### Proof of Concept
Not constructed - reproducing this requires confirming the exact withdrawal signature/sighash construction and `handle_finalized_payout` validation logic, which I could not fully trace within the available tool budget.

Given the incomplete verification of the two open items above (sighash-committed outputs and operator-side reconciliation in `handle_finalized_payout`), I cannot confirm this finding with the certainty required by the validation rules (the equality binding must be checked "before and after" and existing guards must be ruled out with certainty). I am not confident enough in the negative to assert "no vulnerability," but I also lack the ev idence to assert a confirmed vulnerability.

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;
