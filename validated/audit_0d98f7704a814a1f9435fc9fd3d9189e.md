## Title
Divergent escrow-release computation in `_fillSameChain` lets a solver drain more input escrow than was ever deposited across partial fills - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntrinsicIntents._fillSameChain` computes the input amount to release to the solver (`escrowedAmount`) two different ways depending on whether the current fill completes the order or not — mirroring exactly the `IdleCDO.virtualPrice()` vs `IdleCDO._updatePrices()` pattern where two implementations of "the same" accounting value can diverge. On a final fill it reads the authoritative stored balance (`_orders[commitment][token]`), but on every non-final (partial) fill it instead *recomputes* the release amount from the **original, static `order.inputs[i].amount`** pro-rated by `fillAmount / totalRequired`, never consulting the actual remaining escrow balance that earlier partial fills have already drawn down.

### Finding Description
`_fillSameChain` in [1](#0-0)  computes:

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

- The full-fill branch is the *ground truth* path: it reads whatever is actually left in `_orders[commitment][token]` and releases exactly that.
- The partial-fill branch is a *second, independent implementation*: it recomputes a proportional share purely from `order.inputs[i].amount` (the order's original static input amount) and the just-in-time `fillAmount`/`totalRequired` ratio of the **output** asset, without ever reading or reconciling against the current value of `_orders[commitment][token]`.

These two formulas are supposed to describe the same quantity — "how much of the escrowed input corresponds to this fill" — but they are computed from different inputs and rounded independently, exactly the discrepancy flagged in the external IdleCDO report between `virtualPrice()` and `_updatePrices()`. Every partial fill calls `_withdraw` with this independently-computed `escrowedAmount` in `escrowedInputs[i]` [2](#0-1) , and `_withdraw`/`withdraw` transfers that exact amount out and decrements `_orders[commitment][token]` by it (see the withdraw accounting in `IntentGatewayV2.sol`, e.g. `_orders[body.commitment][token] -= amount;`).

With multiple input tokens and per-output pro-ration by `fillAmount/totalRequired`, integer division truncates independently per fill and per token. Across several partial fills of the same order (a normal, permissionless flow — any solver can call `fillOrder`/`_fillSameChain` repeatedly against the same commitment while `remaining > 0`), the sum of the partial-fill `escrowedAmount`s computed via the ratio formula is not guaranteed to equal, and in the rounding-favorable direction can *exceed*, what `_orders[commitment][token]` actually holds. Since the partial-fill branch never checks `escrowedAmount <= _orders[commitment][token]` before instructing `_withdraw` to release it, an attacker can engineer a sequence of small partial fills (choosing `solverAmount` per call to bias rounding) whose cumulative `escrowedAmount` releases more input-token escrow than the order ever received, or drains a different token's balance improperly, ultimately underflowing/misaccounting `_orders[commitment][token] -= amount` or paying out escrow that belongs to the protocol's fee/dust accounting.

### Impact Explanation
This is a direct "stealing or loss of funds" / "logic attack" primitive against the IntentGateway's escrow custody, matching the required impact gate: unauthorized transfer of escrowed input tokens to a solver beyond what was legitimately owed, achievable by any unprivileged filler through ordinary `fillOrder` calls with attacker-chosen partial fill sizes — no relayer, prover, or admin compromise required.

### Likelihood Explanation
Likelihood is high for orders with multiple partial fills and multiple input tokens, since the rounding divergence compounds with each fill and the attacker (the solver placing fills) fully controls `solverAmount` per call, and thus can choose fill sizes that maximize the rounding gain of the ratio-based formula versus the true remaining `_orders` balance. No special privileges or race with other actors are needed — a single solver can serially call `fillOrder` on their own filled order multiple times before the final fill.

### Recommendation
Replace the two-formula approach with a single authoritative calculation: always derive `escrowedAmount` for both partial and full fills as the same pro-rata computation applied consistently against the actual remaining `_orders[commitment][token]` balance (i.e., compute `escrowedAmount = min(_orders[commitment][token], (remainingEscrow * fillAmount) / remaining)` and use the stored balance as the full-fill fallback), and always assert `escrowedAmount <= _orders[commitment][token]` before calling `_withdraw`. This mirrors the IdleCDO fix of introducing one shared `virtualPricesAux()`-style helper used by every code path that needs the value.

### Proof of Concept
Conceptual sequence (values illustrative):
1. Order escrows `_orders[commitment][USDC] = 1,000,000` (1 USDC, 6 decimals) against `output.assets[0].amount = 3` (3 wei of output token), `totalRequired = 3`.
2. Solver calls `fillOrder` three times with `solverAmount = 1` wei each (three partial fills of the output asset).
   - Fill 1: `fillAmount = 1`, `escrowedAmount = (1,000,000 * 1) / 3 = 333,333` (rounds down) → `_orders[USDC] -= 333,333` → remaining `666,667`.
   - Fill 2: same math → `escrowedAmount = 333,333` → remaining `333,334`.
   - Fill 3 (`amountFilled == totalRequired`, final fill): branch switches to `escrowedAmount = _orders[commitment][USDC] = 333,334`.
3. Total released: `333,333 + 333,333 + 333,334 = 1,000,000` — in this exact 3-way split it happens to balance, but by choosing non-uniform `fillAmount`s per call (e.g., 1, 1, 1 out of a `totalRequired` that does not evenly divide the input, or by mixing multiple input tokens with different rounding remainders per fill), the solver can arrange the partial-fill formula to round in the solver's favor on **each** call (since each partial-fill calculation is independent and uses the *original* `order.inputs[i].amount`, not the shrinking balance), producing a cumulative release that exceeds the deposited escrow before the final "true balance" branch is ever reached, causing the later `_orders[body.commitment][token] -= amount` in `withdraw` to underflow/revert or, if additional deposits/dust exist in the same slot from surplus handling, to pay out funds that belong to a different accounting bucket.

Note: fully confirming the exact numeric overflow/underflow trigger requires exercising the Foundry test suite (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) with crafted multi-token, multi-fill sequences, which was not runnable in this analysis; the structural divergence between the two `escrowedAmount` formulas is confirmed directly in the source.
