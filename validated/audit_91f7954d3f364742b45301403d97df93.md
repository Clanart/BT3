## Analysis

I looked for a Desktop analog of the core M-06 pattern: **an action finalizes a state transition using a cached/accumulated value that was never refreshed to reflect what has actually happened**, allowing a mismatch between what was "accounted for" and what actually gets applied.

The closest structural analog I found is in the **partial-commit staging pipeline**, where the diff used to build the commit patch is *not* the same diff object the user reviewed and used to select lines — it's re-fetched from disk at staging time.

### Title
Partial-commit line selections are re-applied to a freshly re-fetched diff instead of the reviewed diff, allowing silent corruption of committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user partially stages a file (selecting individual lines/hunks), Desktop stores a `DiffSelection` containing line indices computed against the diff that was fetched and rendered at that moment [1](#0-0) . At commit time, however, `applyPatchToIndex` re-runs `getWorkingDirectoryDiff` from scratch to build the patch and blindly applies the old `DiffSelection` line indices to this newly fetched diff [2](#0-1)  via `formatPatch`, which resolves selection purely by absolute line index (`hunk.unifiedDiffStart + lineIndex`) [3](#0-2) .

### Finding Description
The invariant that should hold is: *"the line-selection state used to build the commit patch must correspond to the same diff content the user reviewed when making that selection."* Nothing enforces this at commit time.

- The diff shown to the user and the `selectableLines` recorded on the file's `DiffSelection` are computed once, when `updateChangesWorkingDirectoryDiff` runs [4](#0-3) . The code comment there explicitly acknowledges the diff can go stale ("The diff might have changed dramatically since last we loaded it...") but only re-syncs `selectableLines`, and only when this function happens to be invoked again.
- `_commitIncludedChanges` does **not** call `updateChangesWorkingDirectoryDiff` before committing — it directly hands the cached `state.changesState.workingDirectory.files` (with their possibly-stale `DiffSelection`) to `createCommit` [5](#0-4) .
- `createCommit` unconditionally resets the index and calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex` [6](#0-5) .
- `applyPatchToIndex` re-fetches the diff independently (`getWorkingDirectoryDiff(repository, file)`) rather than reusing the diff object the UI displayed, then formats a patch by indexing into this *new* diff using the *old* selection's line numbers [2](#0-1) .

If the tracked file's on-disk content shifts between the time the diff was rendered (T1) and the time the commit patch is generated (T2) — e.g., due to filter-driven normalization (`.gitattributes` `text=auto`/`eol`/`ident` filters that are honored purely from repository-tracked attributes without extra local trust), Git LFS smudge re-materialization, or any other automated working-tree rewrite tied to repository content that a malicious/compromised remote can carry — the hunk/line layout at T2 no longer matches T1. `formatPatch` will then apply "line 12 selected" semantics to whatever text now occupies that offset, silently including or excluding different content than what the user actually reviewed and checked.

Existing guards do not stop this: the only staleness check in `updateChangesWorkingDirectoryDiff` guards against *selection of a different file*, not content drift of the *same* file between diff-render and commit-build time, and that function is not invoked again on the commit path at all.

### Impact Explanation
This directly matches the "silent corruption of what the user commits" impact category. A user could believe they are committing exactly the lines highlighted/checked in the diff viewer, while the actual committed patch (built from a re-fetched, divergent diff) contains different lines — potentially reintroducing secrets, malicious code, or unintended content that the user explicitly tried to exclude, or dropping content the user intended to include. Because the corruption is silent (no re-confirmation dialog, no diff re-render before commit), it can persist into the pushed history undetected.

### Likelihood Explanation
This requires the working-tree content of the selected file to change between diff-load and commit-build without another `updateChangesWorkingDirectoryDiff` call in between. This is a narrow, timing-dependent window and its exploitability by a fully remote/unprivileged attacker (vs. only being triggerable by benign local races, e.g. an external editor autosave) is not conclusively demonstrated by the code alone — I could not find a code path where a cloned/fetched repository's content deterministically forces this race without some additional local interaction. I'm flagging this as a real design weakness (missing re-validation before finalizing the commit, structurally identical to the M-06 "stale accumulated value" bug) rather than a fully proven remote-triggerable exploit.

### Recommendation
- Persist and reuse the exact `IDiff` object (not just line indices) that was rendered when the user made their selection, and pass it through to `applyPatchToIndex`/`formatPatch` instead of re-fetching a new diff at commit time.
- If a fresh diff must be fetched for staging, verify equality (e.g., via hunk headers/hashes) with the diff the selection was computed against before applying `formatPatch`; if they differ, abort and force a UI re-sync/re-confirmation instead of silently proceeding.

### Proof of Concept
1. Open a repository containing a tracked text file `foo.txt` and modify it, producing a diff with several hunks.
2. In the Changes view, deselect/select specific lines mid-file (creating a `DiffSelection` with concrete absolute line indices tied to the currently rendered diff) — see `updateChangesWorkingDirectoryDiff` [1](#0-0) .
3. Before clicking "Commit", cause the file's on-disk content/line layout to shift outside of Desktop's own diff-refresh path (e.g., an external process rewrites the file, or a git filter transforms it on the next `git diff`/`git apply` invocation).
4. Click "Commit". Observe that `applyPatchToIndex` re-fetches the diff and `formatPatch` applies the old line indices to the new hunks [3](#0-2) , producing a committed patch whose content differs from what was shown/selected in step 2, with no warning to the user.
