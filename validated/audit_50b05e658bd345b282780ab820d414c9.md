### Title
`internal_send_tx` is fully unauthenticated when `client_verification` is disabled, allowing broadcast of an attacker-chosen Bitcoin transaction - (`core/src/servers.rs`, `core/src/rpc/interceptors.rs`)

### Summary
The `Internal`-prefixed gRPC methods (e.g. `internal_send_tx`) are only restricted to the aggregator's own certificate holder via the `OnlyAggregatorAndSelf` interceptor, which is installed only when `config.client_verification == true`. When it is `false`, `Interceptors::Noop` is installed instead, which performs no authorization check whatsoever on any method, including `Internal*` ones. This breaks the intended binding "caller of `internal_send_tx` == aggregator's own cert holder" for any deployment running with `client_verification = false`.

### Finding Description
The binding the system is supposed to enforce is:
`peer_leaf_cert(request) == our_cert` for any request where `is_internal(request) == true`.

Tracing the code:
- `is_internal()` in [1](#0-0)  flags any gRPC method whose name is prefixed with `Internal`.
- `only_aggregator_and_self()` enforces the equality above, but only if it is actually invoked as the interceptor: [2](#0-1) .
- Whether `OnlyAggregatorAndSelf` (which calls `only_aggregator_and_self`) or `Noop` (no-op, `Ok(req)` unconditionally) is used is decided purely by `config.client_verification` in `create_grpc_server`: [3](#0-2) .
- When `client_verification` is `false`, the interceptor is `Noop`, so `is_internal()` is never even consulted and every method — internal or not — is accepted from any TCP peer that can complete the TLS handshake with just the server's identity (no client cert requirement, since `client_ca_root` is also skipped for the TLS config in that branch, line 106-112).

The root cause is that authorization for `Internal*` methods is implemented purely as an interceptor gated on a config flag, rather than being enforced unconditionally at the method level regardless of `client_verification`. This means the "only the aggregator's own cert can call `internal_send_tx`" guarantee silently disappears whenever an operator disables `client_verification`, and any unprivileged party with network access to the aggregator's gRPC port can call `InternalSendTx` with an arbitrary `SendTxRequest`, causing the aggregator to broadcast an attacker-supplied raw Bitcoin transaction through `internal_send_tx`. Existing guards (`SECP.verify_schnorr`, `Verifier::is_deposit_valid`, database uniqueness constraints, etc.) are not on this path at all — the TX-sender broadcast path is reached before any bridge-protocol-level validation, since `InternalSendTx` is designed to be trusted-caller-only, not content-validated.

### Impact Explanation
An attacker can force the aggregator to broadcast a transaction it did not itself construct, e.g., spending an operator's fee-bumping/anchor UTXO, potentially double-spending or invalidating operator-controlled infrastructure transactions the aggregator was tracking/rebroadcasting. This is an unauthenticated state-changing/broadcasting call, matching the "High" impact category explicitly listed in scope. It is repeatable for every `SendTxRequest` the attacker can craft and is not limited to a single deposit/operator — any transaction the tx-sender queue is willing to relay can be triggered this way, as long as `client_verification` is `false`.

### Likelihood Explanation
This requires the specific deployment configuration `client_verification = false` on the aggregator (the precondition explicitly listed in the question and confirmed to be a valid config toggle at [3](#0-2) , with an explicit warning log only for the *enabled* case at [4](#0-3) , implying the disabled mode is a supported/expected operating mode rather than a hardening path). Given that precondition, the attack requires no special privileges beyond network access to the aggregator's public gRPC port and the ability to craft a valid `SendTxRequest`/raw transaction — cost is limited to Bitcoin fees for the transaction being broadcast. It is fully repeatable.

### Recommendation
Enforce the `Internal*` method restriction independently of `client_verification`/TLS-based peer identity — e.g., reject all `Internal*`-prefixed calls outright when peer certificate verification cannot be performed (instead of falling back to `Noop`), or always install a lightweight interceptor that at minimum rejects `is_internal()` requests unless mTLS-based self-identity can be established, regardless of the `client_verification` flag's effect on other endpoints.

fn is_internal(req: &Request<()>) -> bool {
    // This normally doesn't exist but we add it in the AddMethodMiddleware
    let Some(path) = req.metadata().get("grpc-method") else {
        // No grpc method? this should not happen
        tracing::error!("Missing grpc-method header in request");
        return false;
    };
    path.as_bytes().starts_with(b"Internal")
}
