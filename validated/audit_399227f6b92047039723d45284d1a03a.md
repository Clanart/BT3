### Title
Early error return in `KeyMachine::calculate_share` leaks the recipient's ECDH shared key for attacker-reused message keys, bypassing the PoP check and exposing honest parties' secret shares — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP DKG decrypts each incoming `EncryptedMessage` and immediately derives a blame proof containing the recipient-side ECDH shared key `b·X` (`Encryption::decrypt` returns `(plaintext, EncryptionKeyProof)` where `key = ecdh(enc_key, msg.key)`). The message's proof-of-possession (PoP) Schnorr signature is only *queued* into a `BatchVerifier`; it is verified at the end of `calculate_share`. However, when the decrypted share bytes fail `C::F::from_repr` canonicality, `calculate_share` returns `PedPoPError::InvalidShare { blame: Some(blame) }` early — before `batch.verify_with_vartime_blame()` is ever called — so the blame proof is published even though the PoP was never checked. This defeats the exact mitigation documented in `EncryptedMessage`'s own comments and enables a malicious participant to reveal the shared ECDH key of *any* honest message, decrypting its secret share.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs:469-501`, `Encryption::decrypt`:
1. Queues `msg.pop` for batch verification under `batch_id` (not yet verified).
2. Computes `key = ecdh(enc_key, msg.key)` = `b·X` where `b` is the recipient's static session encryption key and `X = msg.key` is the per-message public key supplied by the sender.
3. Applies the ChaCha20 keystream to the ciphertext.
4. Returns the plaintext together with `EncryptionKeyProof { key, dleq }`, a publicly verifiable DLEq proof binding `key` to `(generator, msg.key)` and `enc_pub_key` — i.e., an undeniable broadcast of `b·X`.

In `crypto/dkg/pedpop/src/lib.rs:476-499`, `calculate_share` iterates over shares. At lines 479-483:

```rust
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
```

The `?` propagates the error **before** `batch.verify_with_vartime_blame()` (line 493) runs, so the queued PoP statement for this message is never evaluated. The caller in `processor/src/key_gen.rs:416-425` wraps this into `ProcessorMessage::InvalidShare { ..., blame: Some(blame.serialize()) }`, which is published.

The design comment at `encryption.rs:84-91` acknowledges this attack: "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X... they'd reveal bX, revealing Alice's message to Bob." The PoP was added so only someone knowing `x = dlog(X)` can claim key `X`. But because the early return emits the blame proof before the queued PoP is verified, the mitigation is void whenever the decrypted payload is non-canonical — which the attacker can guarantee with ~15/16 probability per attempt (a random 32-byte decryption exceeds the Ristretto scalar modulus `l ≈ 2^252` with overwhelming probability), and can retry indefinitely.

### Impact Explanation
An unprivileged participant (or anyone who can send a `Shares` message to a key-gen participant) can:

1. Observe the victim sender Alice's published `EncryptedMessage` to Bob and copy its `key` field `X_A` (a public value).
2. Submit to Bob `EncryptedMessage { key: X_A, pop: <any parseable signature>, msg: <arbitrary 32 bytes> }` — the PoP need not be valid, since it is never verified on this path.
3. Bob's `decrypt` computes shared key `b·X_A` (identical to the key protecting Alice's real share), decrypts garbage, `from_repr` fails, and Bob broadcasts a blame proof cryptographically attesting `b·X_A`.
4. Anyone can now apply the same keystream derivation (`cipher(context, b·X_A)`) to Alice's original ciphertext and recover her secret share to Bob.

Repeating for every sender's message key reveals *all* shares Bob received, i.e. Bob's summed secret share `b`'s contribution — full recovery of Bob's FROST secret share for that session from public/broadcast data alone. This is key-share recovery of an honest, non-faulty participant: analogous severity to the CVE's sensitive-information disclosure, but here the leaked material is threshold signing key material.

### Likelihood Explanation
- Reachability: the attacker only needs to deliver a malformed `EncryptedMessage` to a participant running `calculate_share` — exactly the untrusted-bytes-to-`EncryptedMessage::read`/`calculate_share` path in scope (`processor/src/key_gen.rs:409`).
- The attacker does not need to satisfy the PoP, know `dlog(X_A)`, or collude; Bob's honest implementation produces the revealing blame proof itself.
- Success probability per attempt is ~15/16 (probability a random 32-byte string is non-canonical for Ristretto/Ed25519-class moduli); failures are indistinguishable from ordinary faults and retryable within an attempt window.
- The only requirement is that the DKG session runs at all; blame publication is part of normal protocol flow.

### Recommendation
Verify each message's PoP **before** generating or releasing any `EncryptionKeyProof`. Concretely, in `KeyMachine::calculate_share` (crypto/dkg/pedpop/src/lib.rs:476-499):
- Do not return early on the `from_repr` failure; record the fault and continue so `batch.verify_with_vartime_blame()` runs. If the PoP (`BatchId::Decryption(l)`) is invalid, emit `blame: None`, never the `EncryptionKeyProof`.
- Alternatively, change `Encryption::decrypt` to return the proof only after a synchronous PoP check, or gate blame emission on the decryption-batch entry having passed.
- As defense-in-depth, reject `msg.key` points that are identity/low-order at `EncryptedMessage::read` (the ciphersuite `read_G` used at `encryption.rs:173` accepts identity, unlike `frost::Curve::read_G`), since identity `X` makes `b·X` known to the attacker and PoP trivially satisfiable with `x = 0`.

### Proof of Concept
1. Participants run PedPoP key gen with `ThresholdParams`; Alice produces `EncryptedMessage` `M_A` to Bob with per-message key `X_A` (public field in `M_A`).
2. Attacker Eve reads `X_A` from `M_A` and constructs `M_evil = EncryptedMessage::<Ristretto, SecretShare<F>>` bytes: `key = X_A` encoding, `pop =` any well-formed `SchnorrSignature` (e.g., a real signature under a key she knows, or any parseable `(R, s)` — it is never verified), `msg =` arbitrary 32 bytes.
3. Bob's processor calls `EncryptedMessage::read` then `machine.calculate_share(rng, shares)` (`processor/src/key_gen.rs:409-416`). `Encryption::decrypt` computes `key = b·X_A`, queues the PoP under `BatchId::Decryption(Eve)`, decrypts `msg` to pseudorandom bytes, and returns the `EncryptionKeyProof { key: b·X_A, dleq }`.
4. `C::F::from_repr(share_bytes.0)` fails (≈15/16 chance); `calculate_share` returns `Err(InvalidShare { participant: Eve, blame: Some(proof) })` at `lib.rs:480-482` **before** `batch.verify_with_vartime_blame()` at line 493, so the bogus PoP is never checked.
5. `handle_machine` emits `ProcessorMessage::InvalidShare { blame: Some(proof.serialize()) }` (`key_gen.rs:419-425`), broadcasting the DLEq-attested `b·X_A`.
6. Any observer derives `cipher(context, b·X_A)` (transcript `"DKG Encryption v0.2"`, `encryption.rs:101-133`) and XORs it with `M_A.msg` to recover Alice's secret share for Bob. Repeating for all senders' message keys yields Bob's complete secret share for the session.
