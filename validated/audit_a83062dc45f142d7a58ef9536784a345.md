## Finding

### Title
Git's clone-time protection against malicious repository content is explicitly disabled during clone (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment used to run `git clone --recursive ... -- <url> <path>` and unconditionally sets:

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
```

`GIT_CLONE_PROTECTION_ACTIVE` is the environment switch upstream Git introduced as part of the fix for the clone/submodule symlink hook-execution class of vulnerabilities (the family covered by GHSA-fkgr-h9x5-2gr4 / CVE-2024-32002 and related advisories), where a malicious repository (or, more commonly, a malicious nested submodule) ships a `.git` directory that is actually a symlink, or crafted case-collision paths, so that after a recursive clone/checkout Git ends up writing/executing hook files (e.g. `post-checkout`) outside the intended repository tree — resulting in arbitrary code execution on clone. Git's fix made this protection active by default; explicitly forcing it to `'false'` re-opens that attack surface for every clone Desktop performs. [1](#0-0) 

### Finding Description
`clone()` is Desktop's single entry point for `git clone`, always invoked with `--recursive`, meaning any submodules referenced by the remote (fully attacker-controlled if the user clones/opens a malicious or malicious-fork repository, e.g. via the `x-github-client://openRepo/...` deep link handled in `app/src/main-process/main.ts` → `parseAppURL`/`openOrCloneRepository`) are fetched and checked out automatically as part of a single user action. [2](#0-1) [3](#0-2) 

The vulnerability class this env var protects against relies on the attacker fully controlling the *contents* of the cloned repository/submodule tree (symlinked `.git`, colliding case-insensitive paths, crafted `.gitmodules`) — exactly the "attacker controls a cloned/fetched repository" primitive named in the report's valid-impact list. Desktop's `isClonePathSensitive()` check only validates the *destination directory* chosen by the user (e.g. not `~/.ssh`); it does nothing to validate the *repository content* being written during a recursive clone, so it provides no mitigation for this class of bug. [4](#0-3) 

This is the direct structural analog of H-20: in the smart-contract report, `_executeReduceMargin` computed a safety bound (`maxReduceMarginInUsd`) from stale/incomplete state (ignoring current PnL), so an existing guard silently failed to prevent an attacker from extracting more value than intended. Here, Desktop computes/derives a "safe" execution environment for `git clone` but explicitly strips out the specific guard Git upstream added to stop attacker-supplied repository content from escaping the intended checkout boundary — the guard exists, and is deliberately turned off, so the invariant "malicious repo content cannot write/execute outside the target clone directory" is broken exactly where it matters.

### Impact Explanation
If the local Git binary bundled/used by Desktop is a version where `GIT_CLONE_PROTECTION_ACTIVE=false` reopens the historical hook-symlink / case-collision write vulnerabilities, then simply cloning (or "Open in Desktop"-ing) a malicious repository — no additional user action beyond the normal clone flow — can result in:
- Arbitrary file write outside the intended clone directory (e.g. overwriting `~/.bashrc`, SSH config, or other hook files via a symlinked submodule `.git` directory).
- Execution of attacker-controlled hook scripts (e.g. `post-checkout`) as a consequence of the corrupted checkout, i.e. code execution under the user's account.

This matches the report's severity pattern: a security invariant ("checkout of untrusted repo content cannot escape repo bounds") is bypassed by omitting/disabling the exact check meant to enforce it, at exactly the trust boundary (attacker-controlled remote content) the invariant exists to protect. [1](#0-0) 

### Likelihood Explanation
Every `git clone` performed by Desktop — whether initiated from the Clone dialog, the CLI (`--cli-clone`), or the `x-github-client://openRepo/<url>` deep link — runs through this single `clone()` function with the protection disabled and `--recursive` enabled, so the exposure is on the default/common code path, not a rare corner case. [5](#0-4) [6](#0-5) 

Actual exploitability depends on the exact bundled Git version's behavior with this flag and on filesystem case-sensitivity/symlink support, which could not be fully verified from the indexed code alone (Git's own binary/version pinning is not visible in this index) — this should be validated against the specific Git version Desktop ships.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override (or set it to `'true'`/leave it unset so Git's default, protected behavior applies) unless there is a narrowly scoped, documented reason tied to a specific compatibility issue — in which case the override should be gated to only the specific failing scenario, not applied unconditionally to every clone, and should be paired with post-clone verification (e.g. rejecting symlinked `.git` paths inside checked-out submodules).

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
