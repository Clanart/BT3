### Title
Desktop re-enables `protocol.file.allow=always` for submodule updates during branch checkout, bypassing Git's local-path submodule protection (CVE-2022-39253 class) - ([File: app/src/lib/git/submodule.ts])

### Summary
Git added `protocol.file.allow=user` as a default-deny for local-path submodules after CVE-2022-39253, because a malicious repository can define a submodule pointing at an absolute or `../`-escaping local filesystem path, and letting Git treat that as a valid submodule source can copy arbitrary local files into the working tree. GitHub Desktop's `updateSubmodulesAfterOperation` explicitly re-opens this hole by passing `-c protocol.file.allow=always` when an `allowFileProtocol` flag is set, and `checkoutBranch`/`checkoutCommit` accept and forward that flag.

`app-store.ts` calls into `checkoutBranch`/`checkoutCommit` in several places (8 matches found), which is where this flag's gating condition is ultimately decided. I was not able to fully inspect every call site within the available tool budget to confirm precisely which user actions (e.g., switching to an untrusted branch fetched from a remote, checking out a PR, or opening a repository containing an attacker-crafted `.gitmodules`/`.git/modules` layout) set `allowFileProtocol` to `true`. That gap is the main remaining uncertainty in this analysis.

The broken invariant, analogous to the missing ERC-20 approval in the original report, is: Git's default protections assume `protocol.file.allow=user` unless the user explicitly opts in; Desktop's code path silently escalates this trust boundary on behalf of the user for the "uninitialized submodule" convenience feature, without restricting *which* submodule URLs are allowed to use the local file path (e.g., no check that the submodule URL stays within the already-cloned repository or a benign relative path).

### Impact Explanation
If an attacker crafts a repository (or a branch/PR within an otherwise-trusted repository) whose `.gitmodules` defines a submodule with an absolute path or path-traversal sequence targeting a sensitive local directory (e.g., SSH keys, cloud credential files, other repos on disk), and the user checks out that branch/commit in Desktop with `allowFileProtocol=true` in effect, Git will copy the contents of that local path into the submodule's working tree inside the (attacker-influenced) repository. This is a form of unauthorized local file read that lands inside a directory the user may subsequently `git add`/commit/push — i.e., silent corruption/exfiltration of what the user commits or pushes, directly matching the accepted impact categories (file read outside the repo scope, corruption of committed content).

### Likelihood Explanation
Likelihood depends entirely on which code paths set `allowFileProtocol=true`. The test suite indicates it is turned on specifically to support switching to a branch containing a not-yet-initialized submodule — a state that can be reached simply by fetching/checking out a branch or PR from an untrusted remote/fork, which is squarely within the "attacker controls a cloned/fetched repository" threat model in scope. Without a companion check that submodule URLs are safe (relative, non-escaping, HTTP(S)/SSH only) before re-enabling `protocol.file.allow=always`, any repository with such a branch can attempt the attack merely by being fetched and checked out — a normal, expected user action, not requiring unnatural steps.

### Recommendation
- Before passing `allowFileProtocol=true`/`protocol.file.allow=always` to `git submodule update`, validate each submodule's configured URL (from `.gitmodules`) to ensure it is not a `file://`/absolute/path-traversal reference, or restrict the local-path allowance to paths that are provably within the already-checked-out repository tree.
- Alternatively, avoid blanket re-enabling of `protocol.file.allow=always` and instead pass `protocol.file.allow=user` with an explicit, narrow allowlist mechanism, mirroring the intent of the upstream Git CVE-2022-39253 fix rather than bypassing it wholesale.
- Add regression tests asserting that a submodule pointing at an absolute path outside the repository (e.g., `/etc`, `~/.ssh`) is rejected even when `allowFileProtocol` is set for legitimate same-repo uninitialized-submodule scenarios.

### Proof of Concept
1. Attacker creates a public repository with a branch `evil` whose `.gitmodules` contains:
   ```
   [submodule "leak"]
     path = leak
     url = /home/victim/.ssh
   ```
   with the submodule left uninitialized (no corresponding commit content needed, just the config).
2. Victim, using GitHub Desktop, fetches the repository/PR and checks out branch `evil`.
3. Desktop's checkout flow detects the uninitialized submodule and calls `checkoutBranch(..., allowFileProtocol = true)`, which invokes: [5](#0-4) 
   with `-c protocol.file.allow=always`, permitting Git to clone from `/home/victim/.ssh` into the `leak/` submodule directory inside the repository working tree.
4. The victim's SSH keys (or other targeted local files) now exist inside the repository's working directory and, if the victim commits/pushes without noticing, are exfiltrated to the attacker-controlled remote.

*Note: I could not confirm from the indexed code exactly which `app-store.ts` call sites set `allowFileProtocol` to `true` in production (vs. purely in tests), so the exact trigger conditions for step 2–3 should be verified against the full source (e.g., via a Devin session with complete repository access) before treating this as a confirmed, exploitable path.*
