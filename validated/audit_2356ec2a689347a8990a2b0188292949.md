### Title
Delimiter-based `createEqualityHash` allows cross-repository state collisions - (File: app/src/models/equality-hash.ts)

### Summary
`createEqualityHash` builds the "hash" used to identify `Repository` and `GitHubRepository` objects by naively joining fields with a `+` separator and no escaping or length-prefixing — the exact bug class described in the Mimc report: concatenation of variable-length attacker-influenced fields without an unambiguous boundary marker, so structurally different inputs can produce the identical output string.

### Finding Description
`createEqualityHash` simply does `items.join('+')` with no escaping of `+` characters inside the individual fields and no length prefix to disambiguate field boundaries: [1](#0-0) 

This function is used to compute `Repository.hash` from `path`, `id`, `gitHubRepository?.hash`, `missing`, `alias`, `workflowPreferences.forkContributionTarget`, and `isTutorialRepository`: [2](#0-1) 

and `GitHubRepository.hash` from `name`, `owner.login`, `dbID`, `isPrivate`, `htmlURL`, `cloneURL`, `issuesEnabled`, `isArchived`, `permissions`, and `parent?.hash` — all joined the same unescaped way, and this hash is itself nested into `Repository.hash` via `gitHubRepository?.hash`: [3](#0-2) 

Because `+` is a legal character in file-system paths, URLs (`htmlURL`/`cloneURL`, which can be arbitrary for GitHub Enterprise remotes or repos discovered via API/deep links), and aliases, two field-value sets that place the delimiter at different offsets can produce byte-identical hash strings — the same "shift/collapse" ambiguity the Mimc report flags (different length-encoded inputs collapsing to the same digest).

This hash string is then used as the sole key into per-repository caches: [4](#0-3) [5](#0-4) 

The `git-store-cache.ts` module also keys per-repository `GitStore` instances (working directory status, diffs, history) off this same hash (confirmed present via `grep_search`, not fully read due to iteration limits).

### Impact Explanation
If two distinct `Repository`/`GitHubRepository` objects collide on `.hash`, `RepositoryStateCache.get`/`.update` (and the analogous `GitStoreCache`) will silently return/overwrite the cached state of one repository for the other. This state includes working-directory changes, the pending commit message, `commitToAmend`, and conflict state: [6](#0-5) 
A collision could cause a user's changes, commit message draft, or "amend" target intended for repository A to be silently attributed to repository B in the UI, leading to committing/pushing the wrong content to the wrong remote — squarely the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitability depends on an attacker being able to place a `+` at different offsets across two field sets that otherwise concatenate identically. The most attacker-reachable fields are `htmlURL`/`cloneURL` (populated from GitHub Enterprise/API responses or repos referenced via deep links) and `parent` (fork) metadata, since GitHub.com repo/owner names themselves disallow `+`. This narrows practical exploitation mostly to GitHub Enterprise or non-github.com remotes where URL contents are less constrained, making this a real but non-trivial-to-trigger collision path rather than a trivially forgeable one like the original Mimc bug (which required only crafted `calldata`).

### Recommendation
Do not build equality/cache keys via unescaped delimiter joining. Either:
- Escape the delimiter character within each field before joining (e.g., escape `+` to `\+`), or
- Use a length-prefixed or JSON-based encoding (e.g., `JSON.stringify(items)`), or
- Compute a real cryptographic hash (e.g., SHA-256) over a canonical, unambiguous serialization of the fields.

### Proof of Concept
Conceptually (illustrating the ambiguity in `createEqualityHash`, analogous to the Mimc `lastChunk` shift issue):
```ts
createEqualityHash('a', 'b+c', 1)   // -> "a+b+c+1"
createEqualityHash('a+b', 'c', 1)   // -> "a+b+c+1"  (collision)
```
Applied to `GitHubRepository`, if `htmlURL` for repo A is `https://ghe.example.com/x` and for repo B is crafted such that its `cloneURL`/`name` fields shift the `+`-joined boundaries to produce the same concatenation as A's field set (both feasible for GHES-hosted repos where URL/name constraints are looser than github.com), `Repository.hash` for A and B become identical, and `RepositoryStateCache`/`GitStoreCache` will conflate their cached working-directory/commit state.

  public update<K extends keyof IRepositoryState>(
    repository: Repository,
    fn: (state: IRepositoryState) => Pick<IRepositoryState, K>
  ) {
    const currentState = this.get(repository)
    const newValues = fn(currentState)
    const newState = merge(currentState, newValues)

    const currentTip = currentState.branchesState.tip
    const newTip = newState.branchesState.tip

    // Only keep the "is amending" state if the head commit hasn't changed, it
    // matches the commit to amend, and there is no "fixing conflicts" state.
    const isAmending =
      newState.commitToAmend !== null &&
      newTip.kind === TipState.Valid &&
      currentTip.kind === TipState.Valid &&
      currentTip.branch.tip.sha === newTip.branch.tip.sha &&
      newTip.branch.tip.sha === newState.commitToAmend.sha &&
      newState.changesState.conflictState === null

    this.repositoryState.set(repository.hash, {
      ...newState,
      commitToAmend: isAmending ? newState.commitToAmend : null,
    })
  }
