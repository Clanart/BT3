### Title
SSRF via unvalidated DataLayer mirror/subscription URLs in `http_download()` - (File: chia/data_layer/download_data.py)

### Summary
`chia/data_layer/download_data.py`'s `http_download()` issues an outbound HTTP GET directly against a caller-supplied `server_info.url`, with no validation of scheme, host, or IP range. These URLs originate from two reachable, unprivileged inputs: (1) the `subscribe` DataLayer RPC, where a local RPC caller supplies arbitrary `urls` [1](#0-0)  that are stored verbatim as `ServerInfo` records [2](#0-1) , and (2) on-chain DataLayer mirror advertisements, which the sync loop treats as "external trust inputs" and merges into the subscription URL set before fetching [3](#0-2) [4](#0-3) . This mirrors the CarrierWave SSRF pattern (CVE-2021-21288), where a "download" feature blindly fetched attacker-supplied URLs/IPs without restricting access to internal-only network ranges.

### Finding Description
`fetch_and_validate()` selects from the store's tracked server URLs and calls `insert_from_delta_file()` → `download_file()` → `http_download()` [5](#0-4) . `http_download()` performs:
```
async with session.get(server_info.url + "/" + filename, headers=headers, timeout=timeout, proxy=proxy_url) as resp:
``` [6](#0-5) 
There is no allowlist/denylist for private, loopback, or link-local addresses (e.g. `127.0.0.1`, `169.254.169.254`, RFC1918 ranges), no scheme restriction beyond what `aiohttp` itself enforces, and no check that the URL resolves to a legitimate, expected mirror host. The URL is fully attacker/user-controlled through the `subscribe` RPC (`urls` list, only trimmed with `rstrip("/")`) [7](#0-6)  and through on-chain DataLayer mirror records that the sync loop pulls in during `update_subscription()` before validating any downloaded data [3](#0-2) . Because a store can also be a subscribed (non-owned) store, any DataLayer client can subscribe to any store id and inject arbitrary mirror URLs that this node's background sync loop (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`) will later fetch automatically, without further user interaction.

### Impact Explanation
This lets an unprivileged DataLayer client force the victim node's server process to issue outbound HTTP requests to internal-only addresses (cloud metadata services, internal admin/RPC endpoints, loopback services on the node's host), enabling network reconnaissance and potential further attacks against internal infrastructure that is otherwise unreachable from the public network — matching the SSRF impact described in CVE-2021-21288's "gather information about the Intranet infrastructure" scenario. Severity is bounded because the response body is only used as delta-file content (subject to downstream validation such as `is_filename_valid()` and Merkle-root verification), so it does not directly grant a read primitive back to the attacker; the primary impact is SSRF-driven probing/side effects, consistent with Medium severity.

### Likelihood Explanation
Likelihood is moderate: the `subscribe` RPC is reachable to any local caller with DataLayer RPC access, and mirror-URL ingestion happens automatically in the background sync loop for any subscribed store id, requiring no admin privilege and no additional user confirmation once a store id is subscribed to.

### Recommendation
Validate and restrict mirror/server URLs before use in `http_download()` and before persisting them via `subscribe()`/mirror sync: enforce an allowed scheme set (e.g. `http`/`https` only), resolve and reject requests targeting loopback, link-local, and private/reserved IP ranges (unless explicitly configured for testing), and consider requiring an explicit user allowlist or confirmation for new mirror URLs pulled from on-chain mirror records, mirroring the mitigation CarrierWave applied in 1.3.2/2.1.1.

### Proof of Concept
1. As an unprivileged DataLayer RPC caller, call `subscribe` for an arbitrary `store_id` with `urls=["http://169.254.169.254"]` (or an internal service address) [1](#0-0) .
2. Wait for the periodic sync loop to invoke `update_subscription()` → `fetch_and_validate()` for that store, which selects the malicious URL from `get_available_servers_for_store()` [8](#0-7) .
3. `download_file()`/`http_download()` issues `GET http://169.254.169.254/<filename>` from the victim node's process [6](#0-5) , confirming SSRF against the internal target regardless of whether the response constitutes a valid delta file.

    async def subscribe(self, store_id: bytes32, urls: list[str]) -> Subscription:
        parsed_urls = [url.rstrip("/") for url in urls]
        subscription = Subscription(store_id, [ServerInfo(url, 0, 0) for url in parsed_urls])
        await self.wallet_rpc.dl_track_new(DLTrackNew(launcher_id=subscription.store_id))
        async with self.subscription_lock:
            await self.data_store.subscribe(subscription)
        self.log.info(f"Done adding subscription: {subscription.store_id}")
        return subscription
```

```markdown
- `update_subscription()` performs four ordered steps: sync subscription URLs from wallet mirrors, fetch/validate remote data, upload local files for owned/current data, then prune old full files. Reordering these affects mirror discovery and file availability.
- Wallet reachability failures are intentionally non-fatal. Subscription tracking stops early if the wallet RPC connection is unavailable and retries next cycle; per-subscription failures are logged without killing the loop.
- `fetch_and_validate()` uses wallet singleton history as the target generation/root sequence, randomizes eligible server URLs, tries plugin-specific or plain HTTP delta downloads, and marks mirror/server failures with backoff in the subscriptions table.
```
