### Title
Unbounded multi-byte atom-length-prefix parsing in `is_atom_canonical` can raise an unhandled `IndexError` when validating a submitted spend bundle - (File: `chia/full_node/mempool_manager.py`)

### Summary
`chia/full_node/mempool_manager.py` implements a hand-rolled CLVM serialization scanner, `is_atom_canonical()` / `is_clvm_canonical()`, that is used to reject non-canonical `puzzle_reveal`/`solution` bytes for every coin spend in every submitted `SpendBundle`. The multi-byte length-prefix decoding loop in `is_atom_canonical` advances `offset` and re-indexes the buffer without ever checking that `offset` stays within `len(clvm_buffer)`. A crafted, truncated buffer whose final byte declares a multi-byte atom-length prefix (0xC0–0xFF forms) with insufficient trailing bytes causes an out-of-range index access. This is analogous to CVE‑2016‑2120, where a record's declared content size was not validated against the actual remaining buffer before being consumed, causing a read past the buffer boundary and crashing the server.

### Finding Description
`is_atom_canonical` decodes the CLVM atom length-prefix format: [1](#0-0) 

For every prefix form other than the 1-byte "small atom" form, the function enters a loop `for i in range(prefix_len): ... offset += 1; atom_len |= clvm_buffer[offset]` — it never checks `offset < len(clvm_buffer)` before dereferencing. `is_clvm_canonical`, which drives the scan token-by-token over the whole buffer, has the same problem at its top-level `b = clvm_buffer[offset]` read once `tokens_left` still expects more data but the buffer has been exhausted mid-prefix: [2](#0-1) 

This scanner is invoked directly on attacker-controlled bytes from every coin spend in a submitted spend bundle, once per `puzzle_reveal` and once per `solution`, inside `validate_spend_bundle`: [3](#0-2) 

If a submitter (via `push_tx`/wallet RPC, peer `respond_transaction`, or any spend-bundle submission path) supplies a `puzzle_reveal` or `solution` whose serialized bytes end with a multi-byte atom-length prefix byte but omit the required continuation bytes, `clvm_buffer[offset]` walks past the end of the `bytes` object and Python raises an unhandled `IndexError`. Unlike C-based PowerDNS (silent OOB memory read), Python's bounds check turns this into an uncaught exception rather than memory corruption — but the exception is not caught anywhere along the `validate_spend_bundle` → `add_spend_bundle` call chain (only `ValueError`/`ValidationError` are handled elsewhere, e.g. in `pre_validate_spendbundle`), so it propagates out of the mempool-admission code path for that spend bundle.

### Impact Explanation
An unprivileged submitter can send a spend bundle where the last coin spend's `puzzle_reveal` or `solution` bytes are truncated right after a multi-byte atom-length-prefix marker. This bypasses the "canonical CLVM" pre-check with an unhandled exception instead of the intended graceful `Err.INVALID_COIN_SOLUTION` rejection (contrast with the well-formed non-canonical case tested in `test_mempool_requires_canonical_clvm`, which does return that error cleanly): [4](#0-3) 

An uncaught exception during mempool admission for a single spend bundle can halt that transaction's processing path; if the surrounding caller (full node request handler / RPC endpoint) does not defensively catch a generic `IndexError`, this becomes a repeatable, remotely-triggerable DoS against a single node's spend-bundle intake, satisfying the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Likelihood is limited by the fact I could not confirm from the available index whether the higher-level caller (`full_node.py`'s transaction/RPC handling) wraps `add_spend_bundle`/`validate_spend_bundle` in a broad exception handler that would downgrade this to a harmless rejected transaction rather than a crash or stuck task — the relevant file content for that verification was not available through the index. The underlying missing-bounds-check defect in `is_atom_canonical`/`is_clvm_canonical` is confirmed and trivially reachable by any spend-bundle submitter; whether it escalates to a real processing halt depends on exception handling one layer up that I was unable to fully verify.

### Recommendation
Add explicit bounds checks in `is_atom_canonical` before each `clvm_buffer[offset]` access (return "not canonical" / raise a handled `ValueError` if `offset >= len(clvm_buffer)`), and add the same check in the top-level loop of `is_clvm_canonical`. Additionally, wrap the call sites in `validate_spend_bundle` (and any other caller of `is_clvm_canonical`) to catch decoding exceptions and convert them into `Err.INVALID_COIN_SOLUTION` rather than allowing them to propagate.

### Proof of Concept
1. Construct a `puzzle_reveal` (or `solution`) byte string ending in a byte such as `0xF8` (5-byte length-prefix form) but with fewer than 5 trailing bytes, e.g. `b"\xf8\x01"` (declares a 4-byte continuation, only 1 byte present).
2. Wrap it in a `CoinSpend`/`SpendBundle` and submit it through the standard spend-bundle submission path (e.g., `push_tx` RPC or peer `respond_transaction`), reaching `MempoolManager.add_spend_bundle` → `validate_spend_bundle`.
3. `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` is invoked; `is_atom_canonical` walks past the end of the short buffer, raising `IndexError: index out of range` instead of returning a graceful canonical-form rejection, matching the class of "size-check bypass causes read past buffer boundary" vulnerability referenced by CVE-2016-2120.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
