### Title
Wallet DoS via unhandled AssertionError in CREATE_COIN condition parsing - (File: chia/wallet/util/compute_hints.py)

### Summary
`compute_spend_hints_and_additions()` parses `CREATE_COIN` conditions out of a `CoinSpend`'s CLVM output without validating that the first argument (the puzzle hash) is actually an atom before asserting on it. A crafted puzzle/solution can produce a `CREATE_COIN` condition whose first argument is a cons pair (or otherwise non-atom), which trips a bare `assert`, raising an uncaught `AssertionError` rather than a handled `ValidationError`.

### Finding Description
In `compute_spend_hints_and_additions()`, after identifying a `CREATE_COIN` condition, the code does:
```python
rf = condition.at("rf").atom
assert rf is not None
coin: Coin = Coin(cs.coin.name(), bytes32(rf), uint64(condition.at("rrf").as_int()))
``` [1](#0-0) 

`condition.at("rf")` returns whatever CLVM node is in that position; `.atom` is `None` when that node is a pair rather than an atom. Since the CLVM output is fully attacker-controlled (any coin owner can construct a puzzle that emits `(51 (a . b) amount ...)` as its `CREATE_COIN` condition — CLVM does not require condition arguments to be atoms at the interpreter level), this `assert` can be triggered by an ordinary, otherwise-valid spend. This mirrors the CVE's bug class: a maliciously-crafted-but-otherwise-parseable input field that is used without verifying its shape/type first, leading to a crash on a "conditional" check (`assert rf is not None`) rather than a controlled rejection.

The same unguarded pattern (`.atom` used with `bytes32(...)` conversion without a None/type check) appears in several sibling condition parsers in `chia/wallet/conditions.py` (e.g., `CreateCoin.from_program`, `CreateCoinAnnouncement.from_program`), but `compute_hints.py`'s bare `assert` is the most direct crash trigger because it has no surrounding `try/except`.

### Impact Explanation
This function is used by wallet-side coin/hint tracking code (`chia/wallet/wallet_state_manager.py`, `chia/wallet/cat_wallet/cat_wallet.py`, `chia/wallet/did_wallet/did_wallet.py`, `chia/wallet/trade_manager.py`, `chia/wallet/trading/offer.py`, `chia/wallet/vc_wallet/cr_cat_wallet.py`) to compute hints/additions for coin spends the wallet observes — including spends made by *other* parties (e.g., offer counterparties, or any coin whose puzzle hash matches something the wallet is tracking, such as a hint). An unhandled `AssertionError` propagating out of this path can abort the calling coroutine/task, disrupting wallet state-manager processing of new coin states, offer parsing, or trade management — i.e., a spend-triggered halt of wallet transaction processing for any wallet that observes or evaluates such a spend (for example while validating an offer or receiving a coin-state update). I could not fully verify every call site's exception-handling within the limited exploration performed (in particular I was unable to inspect the exact `wallet_state_manager.py` call sites' surrounding try/except before running out of iterations), so the precise blast radius (whether some callers already wrap this in `except Exception`) is not fully confirmed.

### Likelihood Explanation
Likelihood is Medium: constructing a puzzle whose `CREATE_COIN` argument is a cons pair rather than an atom is straightforward CLVM authoring, requires no privileged access, and can be delivered via an ordinary spend bundle, an offer file, or a coin the victim wallet is otherwise induced to inspect (e.g., through hinting). No node-level bytecode or timing tricks are needed—just a spend whose puzzle output doesn't conform to the assumed atom shape.

### Recommendation
Replace the bare `assert rf is not None` with an explicit type/shape check that raises `ValidationError`/`Err.INVALID_CONDITION` (consistent with other condition-validation code paths), and apply the same defensive check to `condition.at("rrf")` before calling `.as_int()`. Ensure all callers of `compute_spend_hints_and_additions()` treat malformed condition shapes as a handled validation failure rather than allowing an `AssertionError`/other unchecked exception to propagate and interrupt wallet processing.

### Proof of Concept
1. Construct a puzzle that, when run with an attacker-chosen solution, outputs a condition list containing `(51 (0x1122 . 0x3344) 100)` — i.e. a `CREATE_COIN` (opcode 51) condition whose puzzle-hash argument is a cons pair instead of a 32-byte atom.
2. Have this puzzle/solution included in a coin spend that is either: (a) submitted as part of an offer inspected via `Offer.conditions()`/`compute_spend_hints_and_additions()`, or (b) observed by the wallet as a coin-state update it needs to hint/process.
3. When the victim wallet calls `compute_spend_hints_and_additions()` on this spend, `condition.at("rf").atom` returns `None` for the cons pair, and `assert rf is not None` raises `AssertionError`, propagating out of the intended parsing path and disrupting the caller's processing flow instead of being rejected as an invalid condition.
