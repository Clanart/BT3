Based on my investigation, I found a concrete Desktop analog that maps to the same broken-invariant class as the Solidity report: an "owner"/identity value being derived from an untrusted, attacker-influenceable source and then silently trusted for a security-relevant action, without prompting the user who is actually supposed to control it.

### Title
Silent auto-rewrite of the local `origin` remote URL from an unverified GitHub API repository match enables repository-takeover redirection of pushes/fetches - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
When Desktop refreshes a repository's GitHub metadata, it derives the "owner/name" identity purely by regex-parsing the current `origin` remote URL string and matching its hostname against a configured account's endpoint, with no verification that the API-returned repository is actually the same repository the user originally cloned. If the API returns a repository at that owner/name (which can now belong to an entirely different, attacker-registered account/org after a rename/deletion/name-squat), Desktop automatically rewrites the local `origin` remote to point at that new `clone_url`, with no user prompt.

### Finding Description
`matchGitHubRepository` in [1](#0-0)  determines the "owner" and "name" solely by parsing the current default remote URL string and matching its hostname to a signed-in account's endpoint — it performs no cryptographic or identity verification tying the string to the actual repository the user originally trusted.

This match is used in `matchGitHubRepository` (app-store) at [2](#0-1) , which is called from `repositoryWithRefreshedGitHubRepository`: [3](#0-2) 

The `owner`/`name` pair is used to call `api.fetchRepository(owner, name)` — whatever repository currently exists at that owner/name slot on the host is accepted as authoritative, and its `clone_url` is fed into `updateRemoteUrl`: [4](#0-3) 

The guard logic only checks that (a) the git URL protocol hasn't changed and (b) the local remote URL still matches the *previously cached* `gitHubRepository.cloneURL` (i.e., the user hasn't manually edited the remote). If both hold and the new `apiRepo.clone_url` differs, `gitStore.setRemoteURL` is called immediately — silently rewriting `origin` — via [5](#0-4) .

This refresh path runs not just on manual "Repository Settings" edits but automatically as part of routine repository refresh/fetch flows, e.g. `_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository` at [6](#0-5) , and via background/user-initiated fetches that call `withRefreshedGitHubRepository` before `performFetch`, e.g. [7](#0-6) .

### Impact Explanation
The broken invariant: "the local `origin` remote should only ever be changed with the user's explicit awareness/consent" is violated. If a GitHub owner/org name is renamed, deleted, or otherwise becomes available and an attacker registers a new repository under the exact same owner/name on the same GitHub host, the next automatic background fetch or repository selection will make Desktop rewrite the user's `origin` remote to the attacker's `clone_url` with **no dialog, confirmation, or diff shown**. Because git credential helpers on the same host (github.com or the same GHES endpoint) will subsequently supply the user's GitHub credentials to that URL, and future `git push`/`git fetch` operations silently target the attacker-controlled repository, this results in:
- Silent corruption of what the user pushes (their commits/branches get pushed to an attacker's repo instead of the intended one).
- Potential credential/token exposure to the attacker-controlled endpoint (same-host credential helper reuse).
- Silent corruption of what the user fetches/merges (attacker content pulled in believing it is the original project).

This falls squarely within the in-scope impact category: "a GitHub API object... the result is... credential/token exfiltration... or silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires no local access, no admin rights, and no prior compromise. It only requires: the original owner/org name/repo slot to become reusable (a routine GitHub event — account renames, org deletions, and username squatting are known and previously-abused patterns on GitHub.com), and the attacker to register a repository at that slot. The victim's app performs this refresh automatically as part of normal, ordinary background operation (fetch/select-repository), so no unusual user action is needed beyond continuing to use the app normally. The existing guard (`remoteUrlUnchanged` check against previously cached `cloneURL`) does not stop this path — it is designed to detect *user*-initiated manual remote edits, not to verify the *authenticity* of the API-returned repository identity, so it does not defend against a hijacked owner/name slot.

### Recommendation
Do not trust owner/name string matching alone as proof of repository continuity. Before silently rewriting `origin`, verify a stable, non-reusable identifier (e.g., the GitHub repository's immutable numeric `id`, cached at first association) matches between the previously known `GitHubRepository` and the newly fetched `apiRepo`. If the IDs differ (i.e., the API returned an entirely different repository object at the same owner/name), do not auto-update the remote — instead surface an explicit prompt/banner asking the user to confirm the change, similar to how "unsafe repository" ownership changes already prompt for explicit trust in this codebase (see `MissingRepository`/`AddExistingRepository` trust-directory flows at [8](#0-7) ).

### Proof of Concept
1. Victim clones `https://github.com/some-org/project` in Desktop; Desktop stores `GitHubRepository` with `cloneURL` = that URL.
2. `some-org` is later deleted/renamed on GitHub.com (e.g., org disbanded, or a personal account renamed).
3. Attacker immediately registers organization/account name `some-org` and creates a repository named `project` under it, with a different `clone_url` host path (same hostname `github.com`, so `protocolsMatch` stays true).
4. Victim's Desktop performs a routine background fetch or reselects the repository, triggering `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository('some-org', 'project')`, which now resolves to the attacker's repo.
5. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (local remote still equals the old cached `cloneURL`), and `urlsMatch === false` (new `clone_url` differs) → calls `gitStore.setRemoteURL(...)`, silently rewriting `origin` to the attacker's repository, with no prompt shown to the victim.
6. Victim's next `git push` (or Desktop's built-in push) sends commits, and the GitHub credential helper for `github.com`, to the attacker-controlled repository.

```typescript
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
```

```typescript
  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }
```

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
