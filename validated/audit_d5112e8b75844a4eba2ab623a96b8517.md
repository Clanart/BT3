### Title
Webhook Shop Domain Not Bound to HMAC Signature Enables Cross-Shop Webhook Spoofing - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates only the HMAC of the raw request body, while the shop identity used downstream (`shop_domain`) is read directly from the `X-Shopify-Shop-Domain` request header, which is not covered by that signature. This mirrors the reported bug class: an identity/target parameter (`_for` in the report, `shop_domain` here) is trusted without being cryptographically bound to the value that was actually authenticated (`msg.sender` in the report, the HMAC-signed body here), letting a party who legitimately possesses one valid signed payload substitute a different tenant identity.

### Finding Description
`ShopifyApp::PayloadVerification#hmac_valid?` computes and compares an HMAC over `request.raw_post` only: [1](#0-0) 

`WebhookVerification#verify_request` gates the action solely on this body HMAC: [2](#0-1) 

but the shop tenant identity exposed to consuming code is taken straight from an unsigned header: [3](#0-2) 

The gem's own documentation instructs apps building custom webhook controllers to use this concern and pass `shop_domain` (from this header) directly into background jobs that act on a specific tenant's data: [4](#0-3) 

Because the `X-Shopify-Shop-Domain` header is excluded from the signed material, any party who can obtain one valid `(body, HMAC)` pair — for example a merchant who has the app installed on their own shop and therefore legitimately receives real, correctly-signed webhook deliveries — can replay that exact body/HMAC pair to the same endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` header. `hmac_valid?` will still pass because it never inspects the header, so `verify_request` allows the request through, and the controller/job layer will process the payload under the attacker-chosen shop identity instead of the one Shopify actually signed for.

This is the direct analog of the reported `depositFor` bug: the code authenticates one thing (the payload/body, analogous to the ERC20 transfer amount) but performs the sensitive attribution (which shop/tenant, analogous to `_for`) using an unauthenticated, attacker-controlled value instead of deriving it from the verified source.

### Impact Explanation
An app that follows the documented pattern (any custom `WebhooksController` built on `ShopifyApp::WebhookVerification`, or the generator-scaffolded declarative webhook controller) will accept and process webhook bodies attributed to a shop domain the attacker chooses, not the shop that actually owns the signed payload. This enables cross-shop data injection/confusion: background jobs keyed by `shop_domain` (e.g., `CartsUpdateJob`, `OrderUpdateJob`) can be triggered to write, update, or act on data associated with a victim shop using content the attacker fully controls (subject to being a real, previously-observed webhook body). Depending on job logic, this can corrupt another merchant's stored data, trigger unwanted side effects, or be leveraged for further attacks scoped to the victim shop — a cross-shop impact from an accepted forged (mis-attributed) signed request.

### Likelihood Explanation
Exploitation requires only that the attacker have legitimate access to at least one valid signed webhook (trivial for any merchant with the app installed, since Shopify sends them real webhooks routinely), plus the ability to send an HTTP POST to the app's public webhook endpoint with a modified header — no secret knowledge, no session, and no privileged access to the target shop is required. The built-in `ShopifyApp::WebhooksController` delegates to `ShopifyAPI::Webhooks::Registry.process`, which may perform additional binding checks, but the documented/generator-scaffolded custom-controller path relies solely on this concern's header-based `shop_domain`, making the issue directly reachable via the officially recommended integration pattern.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` (or any other header/param not included in the HMAC-signed data) as trusted tenant identity. Either include the shop domain in the material that is HMAC-verified, or cross-check the header value against an independently trusted source (e.g., an active, previously established session/shop record) before using it to select which tenant's data a job or handler acts on, and reject the request if they do not match — mirroring the fix pattern from the referenced report of deriving identity from the verified source rather than an unauthenticated caller-supplied value.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`, so the app's webhook endpoint legitimately receives a signed webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture this `(B, H)` pair.
3. Send a new POST to the same webhook endpoint with identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but replace the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `PayloadVerification#hmac_valid?` recomputes `HMAC(secret, B)` and compares it to `H` — this still matches since `B` is unchanged, per [1](#0-0) .
5. `verify_request` therefore allows the request through, and `shop_domain` resolves to `victim.myshopify.com` per [3](#0-2) , causing any downstream job enqueued with that value to operate under the victim's identity instead of the attacker's.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
```
