### Title
Silent Swallowing of Merge-Parse Failure Leaves Stale Extension Value in `LazyFieldLite.mergeFrom` - (File: `java/core/src/main/java/com/google/protobuf/LazyFieldLite.java`)

### Summary
The external report describes an oracle contract that can process an old (previously-failed) price update as if it were current, because the contract has no check that guarantees only the freshest successfully-processed data is used. The transferable invariant is: *"when an attempt to apply a new update fails, the system must not silently continue to expose the stale previous value as if the update had been correctly incorporated, without any signal to the caller."* Protobuf's `LazyFieldLite.mergeFrom(CodedInputStream, ExtensionRegistryLite)` violates an analogous invariant: when a second wire-format occurrence of an already-parsed lazy message field fails to parse, the exception is caught, the failure is swallowed with **no exception, no log, and no value update**, and the field silently keeps returning the **old, already-parsed value** from before the failed merge attempt [1](#0-0) .

### Finding Description
`LazyFieldLite` represents a lazily-parsed message field: bytes are decoded on first access and the decoded `value` is cached [2](#0-1) . When the wire format contains a duplicate occurrence of the same field tag (a normal, attacker-controllable pattern for any repeated-tag/message field), `FieldSet`/`ExtensionSchemaLite` calls `LazyFieldLite.mergeFrom` again on the existing field to merge the new occurrence into the already-parsed value.

If the field has already been materialized (`value != null`), the merge path tries to parse the *new* incoming bytes directly into the existing value's builder:

```java
try {
  setValue(value.toBuilder().mergeFrom(input, extensionRegistry).build());
} catch (InvalidProtocolBufferException e) {
  // Nothing is logged and no exceptions are thrown. Clients will be unaware that a proto
  // was invalid.
}
``` [3](#0-2) 

Because `setValue()` is only called on the success path, a failure in this second merge attempt leaves `this.value` referencing the value produced by the **prior**, already-completed merge — i.e., stale data from before the failed update. No flag is set (unlike the sibling `corrupted` flag used elsewhere, e.g. in `ensureInitialized(MessageLite)` where a failure explicitly resets to the default instance and marks the field `corrupted` [4](#0-3) ). Callers of `getValue()` on this field have no way to know that a subsequent update to this field was dropped; they simply continue to receive the earlier value as if it were the fully up-to-date result of the whole parse.

This is a direct structural analog to the oracle bug: the "old" data (from the earlier successful merge) continues to be silently treated as valid/current after a later update operation on the same field failed, with no timestamp/version/validity check exposed to the consumer to detect that the newest data was actually rejected.

### Impact Explanation
Any application that relies on `getValue()` of a lazily-parsed message-typed field (most commonly a lazy extension) to reflect the full content of an incoming Protobuf message can be misled into using a partially stale sub-message when an attacker crafts a message containing a valid occurrence of a lazy field followed by a second occurrence with corrupted bytes for the same field number. The overall top-level `parseFrom` call can still return successfully (or throw only for the corrupted segment depending on registry mode), while the specific lazy field silently reflects only the first occurrence's data, not the corrected/updated value the sender intended to send. In systems that treat the parsed message as authoritative "latest state" (e.g., configuration, permission, or pricing-like sub-messages carried in extensions), this can lead to stale/incorrect data being acted upon without any error being surfaced — mirroring the "stale oracle price silently used" impact class, scoped to application logic that trusts `LazyFieldLite` without independently verifying freshness.

### Likelihood Explanation
The corrupting condition requires only a bounded, attacker-supplied message with a repeated (duplicate-tag) lazy message/extension field where the second occurrence's bytes are invalid for that message type — a scenario fully within the ordinary-client, bounded-binary-input threat model, no special parser configuration or privileged access needed beyond having lazy-parsed extension fields defined in a trusted schema, which is common. The failure path is exercised whenever `value != null` at merge time (i.e., an application already accessed the field, or a prior merge succeeded and set it), so it is reachable but conditional on this usage pattern rather than universal to every parse.

### Recommendation
On failure of the merge in `LazyFieldLite.mergeFrom`, do not silently retain the previous `value`. At minimum, mark the field `corrupted` (as is already done in `ensureInitialized`) so subsequent accesses are forced to react to the invalid state rather than transparently returning stale data, and/or propagate the failure so callers using strict parsing APIis are made aware that part of the incoming message could not be merged.

### Proof of Concept
1. Define a message type with an extension field `msg` of message type `Foo` that supports being lazily parsed (lazy extension enabled).
2. Serialize a valid `Foo` instance with `field=1` for the extension tag, producing bytes `B1`.
3. Append a second occurrence of the same extension tag with a length-prefixed but structurally invalid payload `B2` (e.g., a length prefix followed by insufficient bytes) to produce combined bytes `B1 || B2`.
4. Parse the combined bytes with `TestMessageSet.parseFrom(data, extensionRegistry)` and immediately call `getExtension(...)` once (forcing initialization to occur via the first occurrence, setting `value != null`), then access again (triggering the internal merge path from the second occurrence).
5. Observe: no exception surfaces on the second occurrence's failure, and `getExtension(...)` continues to return the `Foo` value derived only from `B1`, even though the sender's second (corrupted) occurrence was silently dropped without any corruption/error indicator being set on the field — confirmed by the swallow-and-continue logic at [3](#0-2) , contrasted with the explicit `corrupted` handling used elsewhere in the same class [4](#0-3) .
