## Title
`_findPullRequestBranch()` checks out whatever local/remote-tracking ref already exists for a PR's branch name without verifying it matches the untrusted PR head SHA - ([File: app/src/lib/stores/app-store.ts])

### Summary
The 1inch report's root cause is a **check-on-final-state-only** pattern: instead of diffing the state actually produced by an operation against a baseline, the code inspects whatever satisfies the check *right now*, which can be pre-existing/attacker-influenced state unrelated to the operation just performed. The GitHub Desktop analog is `_findPullRequestBranch()` in `app-store.ts`, which resolves a pull request's checkout target by looking for any *already existing* local or remote-tracking branch whose name matches the PR's `head.ref`, and checks it out without ever comparing its tip SHA to the PR object's own `head.sha` returned by the GitHub API.

### Finding Description
`_findPullRequestBranch` [1](#0-0)  is invoked from `_checkoutPullRequest` [2](#0-1)  whenever a user (or a deep link via `x-github-client://openRepo?pr=...`, see `dispatcher.openPullRequestFromUrl`) [3](#0-2)  asks Desktop to check out a PR.

The function's resolution order is:
1. Compute `remoteRef = ${remote.name}/${headRefName}`.
2. Look for a **local branch already tracking** `remoteRef` in the cached `gitStore.allBranches` and, if found, return it immediately for checkout: [4](#0-3) .
3. Otherwise look for an existing **remote-tracking branch** named `remoteRef` in the cache: [5](#0-4) .
4. Only if neither is found does it fetch the remote: [6](#0-5) .

At no point is the resolved branch's tip SHA compared against `pullRequest.head.sha` — the SHA that was returned alongside `head.ref` in the same trusted-looking API object that triggered the checkout. The "check" here is "does *some* ref with this name exist / satisfy the name match", exactly like the 1inch bug's "does the balance now satisfy the threshold" — it validates a name-based final state, not that the value was produced by (or corresponds to) the specific operation/object being acted on.

This matters because `headCloneUrl`/`headRefName` come from an `IAPIPullRequest` (a GitHub API object) or from a `github-mac://openRepo` deep link (`IOpenRepositoryFromURLAction`), both of which are attacker-influenceable inputs per the threat model (a malicious/compromised fork owner controls their own PR's head ref name; a crafted deep link controls `branch`). If a locally cached branch or remote-tracking ref already exists under that same name — e.g., left over from a previous PR, a renamed/reused branch, or simply reused by coincidence — Desktop will silently check out that pre-existing ref's content instead of fetching/validating the actual current PR head, without any indication to the user that what's on disk doesn't correspond to `pullRequest.head.sha`.

### Impact Explanation
A user who clicks "Checkout" on what they believe is PR #N (as advertised by the API/UI) can end up with working-directory content that does not match that PR's actual head commit, because the name-based lookup short-circuits before any fetch/SHA verification occurs. This is analogous to the swap slippage check passing on stale/pre-existing balance rather than the actual swap output — the "checkout succeeded and points at the right-looking ref" signal doesn't guarantee the content is the one the trusted-looking object claims. Depending on repo history this can result in reviewing, building, or committing on top of unintended code.

### Likelihood Explanation
Likelihood is low: it requires a specific name collision between a pre-existing local/remote-tracking branch and the PR's `head.ref` inside the same remote namespace, which is a narrower precondition than the general TOCTOU/staleness pattern. It does not require local/physical access, admin rights, or social engineering beyond the normal "click checkout on a PR" or "click an Open-in-Desktop PR link" action a user is expected to naturally perform.

### Recommendation
After resolving `existingBranch` (whether from cache or after fetch), verify that its tip SHA matches `pullRequest.head.sha` before checking it out; if it doesn't match, force a fetch of the remote and re-resolve, or surface an explicit warning/error rather than silently checking out stale content. This mirrors the balance-diff fix recommended in the source report: validate the *actual result* against the *expected value from the same trusted call*, not just that some plausible-looking state currently exists.

### Proof of Concept
1. Desktop has previously fetched/created a local branch or remote-tracking ref named `origin/feature-x` (or `<fork-remote>/feature-x`) for unrelated reasons (e.g., an earlier PR, manual fetch, or a stale fork remote).
2. A new/different PR is opened whose `head.ref` is also `feature-x` (attacker or coincidental reuse), with a genuinely different `head.sha`.
3. User clicks "Checkout" for this PR (via UI list `pull-request-list.tsx` → `dispatcher.checkoutPullRequest` [7](#0-6) , or via the `openRepo?pr=` deep link).
4. `_findPullRequestBranch` finds the pre-existing `feature-x` local/remote ref by name match at [8](#0-7)  and returns it without ever fetching or comparing SHAs against `pullRequest.head.sha`.
5. Desktop checks out the stale/mismatched content while the UI still shows PR #N's metadata, exactly mirroring how the 1inch contract's slippage check passed against a stale/mismatched balance instead of the actual swap delta.

      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`

      return null

    // up-to-date before performing the "Clone in Desktop" steps

      return null
