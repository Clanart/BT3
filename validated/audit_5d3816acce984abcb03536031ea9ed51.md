### Title
Fee-on-transfer / non-standard ERC20 tokens cause bridge value-accounting mismatch, allowing token deposits smaller than the value requested for cross-chain transfer - (File: contracts/service_chain/bridge/BridgeTransferERC20.sol)

### Summary
`BridgeTransferERC20.requestERC20Transfer()` and `_requestERC20Transfer()` use the caller-supplied `_value` parameter to compute fees, burn tokens, and emit the `RequestValueTransfer` event that the counterpart chain trusts to mint/release the equivalent value, but the function never verifies that the bridge actually received `_value` (+ `_feeLimit`) worth of tokens. If a registered ERC20 token implements a transfer fee, rebase, or any other non-standard transfer semantics that reduce the amount actually delivered, the bridge's internal/on-chain balance will be less than the `_value` it commits to on the counterpart chain.

### Finding Description
`requestERC20Transfer` pulls tokens via `safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` and then calls `_requestERC20Transfer`, which:
- pays/refunds the fee using `_payERC20FeeAndRefundChange`, which moves tokens out of the bridge's own balance based on the nominal `_feeLimit`/`fee` values, not on what was actually received,
- burns `_value` from the bridge (in mint/burn mode) or leaves `_value` implicitly "reserved" in the bridge's balance (in lock/release mode),
- emits `RequestValueTransfer(..., _value, ..., fee, ...)`, which is the sole piece of data the bridge operators use to call `handleERC20Transfer` and mint/release `_value` on the counterpart chain. [1](#0-0) 

None of this logic checks the bridge's actual token balance before and after the `safeTransferFrom`. For a fee-on-transfer token, the bridge will receive `(_value + _feeLimit) - transferFee` tokens, strictly less than the amount it commits to in the emitted event and (in lock/release mode) less than what it will eventually release when a matching `handleERC20Transfer` request comes back from the counterpart chain (or when it burns `_value` in mint/burn mode, which can even revert due to insufficient bridge balance for the burn).

`onERC20Received` (the 1-step deposit path) has the same issue: it trusts the `_value` argument passed by the token/caller without validating actual balance movement. [2](#0-1) 

Token registration is restricted to the bridge owner (`onlyOwner`), but this does not prevent the class of bug: any legitimately registered ERC20 that has fee-on-transfer, deflationary/rebasing, or blacklist-style-deduction behavior (a known and common token category, not requiring malicious owner intent) will trigger the mismatch for every unprivileged bridge user who calls `requestERC20Transfer`. [3](#0-2) 

### Impact Explanation
In lock/release mode (`modeMintBurn == false`), the bridge's ERC20 reserve is a shared pool funded by all users' deposits. Because `RequestValueTransfer` emits the nominal `_value` rather than the actually-received amount, the counterpart chain's bridge will later be instructed (via `handleERC20Transfer`) to mint/release the full nominal `_value` to the recipient. The shortfall caused by the fee-on-transfer token is silently absorbed by the shared bridge liquidity pool, i.e., other users' deposited tokens are used to cover the deficit — this is unauthorized value movement / effective fund drain from the pooled bridge balance. In mint/burn mode, the deficit instead causes `ERC20Burnable(_tokenAddress).burn(_value)` to attempt burning more than the bridge actually holds, which can revert (denial of service) or, if the bridge holds excess balance from prior deposits, silently burn other users' tokens, again a state divergence between the nominal accounting (`_value` on both chains) and real token custody.

### Likelihood Explanation
Any unprivileged bridge user can trigger this simply by calling `requestERC20Transfer` (or via `onERC20Received`) for any bridge-registered ERC20 token that charges a transfer fee, applies a deflationary burn on transfer, or otherwise delivers less than the nominal amount — no special privileges beyond normal token approval/transfer are required. The bug is deterministic and reproducible on every such transfer, not a rare edge case, so likelihood is high once such a token is registered by the bridge owner (a realistic operational scenario, not requiring owner malice).

### Recommendation
Measure the bridge's actual token balance before and after `safeTransferFrom` in `requestERC20Transfer`/`onERC20Received` and use the delta (actual received amount) rather than the caller-supplied `_value` for fee computation, burning, and for the `_value` field emitted in `RequestValueTransfer`. Alternatively, explicitly document and enforce (e.g., via a registration-time check that transfers a probe amount and reverts on mismatch) that only tokens with standard, non-fee-charging transfer semantics may be registered.

### Proof of Concept
1. Bridge owner registers a fee-on-transfer ERC20 token `T` (e.g., 5% transfer fee) via `registerToken`.
2. User Alice approves the bridge for `1000 T` and calls `requestERC20Transfer(T, Bob, 1000, feeLimit, "")`.
3. `safeTransferFrom` attempts to pull `1000 + feeLimit` tokens, but due to the 5% fee, the bridge only receives `0.95 * (1000 + feeLimit)` tokens.
4. `_requestERC20Transfer` still pays/refunds fee based on nominal amounts and emits `RequestValueTransfer(..., 1000, ..., fee, ...)`.
5. Bridge operators on the counterpart chain observe the event and call `handleERC20Transfer` there, minting/releasing `1000 T`-equivalent value to Bob — more than the `950`-ish tokens actually custodied by the origin bridge, drawing down the shared pool/other depositors' balance to cover the shortfall.

    function _requestERC20Transfer(
        address _tokenAddress,
        address _from,
        address _to,
        uint256 _value,
        uint256 _feeLimit,
        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        require(_value > 0, "zero ERC20 token amount");

        uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);

        if (modeMintBurn) {
            ERC20Burnable(_tokenAddress).burn(_value);
        }

        emit RequestValueTransfer(
            TokenType.ERC20,
            _from,
            _to,
            _tokenAddress,
            _value,
            requestNonce,
            fee,
            _extraData
        );
        requestNonce++;
    }

    // onERC20Received function of ERC20 token for 1-step deposits to the Bridge.
    function onERC20Received(

        uint256 _feeLimit,
        bytes memory _extraData
    )
        public
    {
        _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
