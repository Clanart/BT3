## Analysis

The Cabal report reduces to: **two subsystems consume the same conceptual state (supply vs. balance) at different points in time, and only one of them refreshes.** The result is a silent, unnoticed mismatch used to corrupt an outcome the user trusts (reward accounting).

GitHub Desktop has a structurally identical pattern in its **partial-commit staging pipeline**: the diff a user reviews and selects lines from in the UI, and the diff actually used to build the `git apply` patch at commit time, are fetched independently, and only the line-*position* selection survives between them — not the diff content itself.

### Title
Partial-commit patch generation re-fetches a fresh working-directory diff, silently desyncing it from the reviewed line selection - (File: app/src/lib/git/apply.ts)

### Summary
`applyPatchToIndex` builds the patch used for a partial commit by calling `getWorkingDirectoryDiff` again at staging time and applying the user's previously computed line-index selection (`DiffSelection`) against it. The selection was computed against whatever diff was rendered in the UI at review time. If the tracked working-tree file content changes between the moment the user reviews the diff/selects lines and the moment `createCommit` actually stages the patch, the index-based selection (`absoluteIndex = hunk.unifiedDiffStart + lineIndex`) is applied to a structurally different diff, so `git apply --cached` stages/commits different content than what the user reviewed and approved — without any error or warning.

### Finding Description
`WorkingDirectoryFileChange.selection` (a `DiffSelection`) stores *line positions*, not diff content or hashes, as shown by `formatPatch`'s use of `file.selection.isSelected(absoluteIndex)` in [1](#0-0) . When the user actually commits, `_commitIncludedChanges` passes the in-memory `WorkingDirectoryFileChange` objects (with their stale selection) straight into `createCommit` in [2](#0-1) , which calls `stageFiles` → `applyPatchToIndex` for any partially-selected file [3](#0-2) .

Critically, `applyPatchToIndex` does **not** reuse the diff that was rendered when the user made their selection. It re-reads the working directory diff from disk at staging time: [4](#0-3) 

The reused `file.selection` line-index positions are then blindly applied to whatever diff shape exists *now* via `formatPatch` in [5](#0-4) . There is no check that the newly-fetched diff's hunk structure matches the one the selection was derived from — no hunk/line hash comparison, no re-validation beyond what's done for still-open selection panels elsewhere in the app (`updateChangesWorkingDirectoryDiff`'s `selectableLines` re-derivation only runs for the *currently displayed* file while its diff panel is open, not at commit time) [6](#0-5) .

This mirrors the Cabal bug exactly: one code path (`check_snapshot`/selection UI) records state at time T0, another code path (`burn`/`applyPatchToIndex`) consumes fresh state at time T1, and the two are combined as if they were consistent.

### Impact Explanation
If working-tree content for a file under active partial-selection review is altered between diff render and the user clicking "Commit" — e.g. by a build/watch/codegen/format-on-save tool that ships as part of the cloned repository's own tooling (npm scripts, VS Code tasks, webpack/tsc watch, husky-installed git filters) — the patch built for staging can select entirely different lines/hunks than what the user reviewed and checked. This is silent corruption of what the user commits and subsequently pushes: the commit UI shows one diff, the actual commit contains another, with no error surfaced by `git apply` as long as the patch context still applies cleanly.

### Likelihood Explanation
This requires only that some file-modifying process attributable to the repository's own tracked build/dev tooling runs during the window between diff review and clicking commit — a realistic occurrence for larger repos with watch-mode tooling, autoformatters, or code generators that a user would run as part of ordinary local development, not an "unnatural" step. No elevated privileges, no local secrets, and no direct user deception are required beyond normal use of a malicious/compromised repository's shipped tooling.

### Recommendation
Bind the patch generation to the exact diff snapshot the selection was computed against instead of re-fetching from disk in `applyPatchToIndex`: pass the diff (or its hunk fingerprints, e.g., a hash of `hunk.header`/line content) alongside the `WorkingDirectoryFileChange` through `createCommit → stageFiles → applyPatchToIndex`, and abort/re-prompt the user if the freshly-read diff's hunk structure has changed since the selection was made, rather than silently reapplying position-based selections to new content.

### Proof of Concept
1. Open a repository in Desktop with a tracked npm script (e.g. `postinstall` or a VS Code `tasks.json` "runOn": "folderOpen") that periodically rewrites `src/foo.ts` with attacker-chosen content while preserving a plausible diff shape.
2. User opens `src/foo.ts` in the Changes view, sees hunk A (lines reviewed and approved), and selects only specific lines within it for partial commit.
3. Before the user clicks "Commit," the background script rewrites the file so the same line offsets now correspond to different content/hunks (still valid enough for `git apply` context matching).
4. User clicks "Commit." `applyPatchToIndex` calls `getWorkingDirectoryDiff` fresh (`app/src/lib/git/apply.ts:60`), builds a patch from the new diff using the old `DiffSelection` indices (`app/src/lib/patch-formatter.ts:143-161`), and `git apply --cached` succeeds.
5. The resulting commit (and subsequent push) contains content the user never reviewed or explicitly approved, with the commit UI showing no discrepancy.

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  // If we get into this state we should never have been called in the first
  // place. Someone gave us a faulty diff and/or faulty selection state.
  if (!patch.length) {
    log.debug(`formatPatch: empty path for ${file.path}`)
    throw new Error(`Could not generate a patch, no changes`)
  }

  patch = formatPatchHeaderForFile(file) + patch

  return patch
}
