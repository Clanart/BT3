## Title
Authentication fallback in `IntentGatewayV2.authenticate` (Tron) accepts an unregistered source chain by matching against `address(this)`, letting a forged cross-chain message steal escrowed order funds — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's bug class is: a callback's "who sent this" check compares against a value that can coincide with an attacker-controlled input (`sender == address(this)`), instead of a hard-bound, unspoofable identity. The Tron deployment of `IntentGatewayV2` reproduces this exact pattern in its cross-chain settlement authentication. `instance()` silently falls back to `address(this)` for any state machine that has no registered gateway entry, and `authenticate()` accepts a message whenever the claimed sender module equals that fallback value — so any request whose `from` field resolves to `address(this)` is treated as coming from a "known instance," even when the source chain was never actually registered as an `IntentGateway` deployment.

### Finding Description
`instance()` and `authenticate()` in the Tron contract: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

`onAccept()` calls `authenticate()` for exactly the two request kinds that move escrowed funds — `RedeemEscrow` and `RefundEscrow`: [2](#0-1) 

`withdraw()` then unconditionally overwrites `_filled[commitment]` and transfers the escrowed tokens to whatever `beneficiary` is encoded in the (attacker-forgeable) `WithdrawalRequest` body: [3](#0-2) 

Compare this to the corresponding logic in the mainline EVM implementation, which reverts instead of falling back: [4](#0-3) 

The corrupted value is `module` matching the `instance()` fallback: for any `stateMachineId` that Hyperbridge's host can produce a valid consensus/state proof for (i.e., it is a supported, provable state machine) but for which `_addDeployment` has never been called on the Tron gateway (no `_instances[keccak256(stateMachineId)]` entry — a routine, expected state for any newly-connected or not-yet-onboarded chain), `instance(request.source)` returns `address(this)`. The check `instance(request.source) != module` then passes for any dispatch whose `from` equals `address(this)` — the gateway's own, publicly known address — instead of requiring the message to originate specifically from the one true, admin-registered peer `IntentGateway` deployment on that chain. This is the same broken invariant as the seed report: a supposedly-restricted callback path is gated only by an equality test against `address(this)`, and that equality can be satisfied by a value the caller effectively supplies (their own contract's address on the source chain), rather than a binding to an actually-authorized peer.

### Impact Explanation
An attacker who reaches this state can submit (via a normal relayer flow, since the proof itself is real ISMP data for a genuinely supported-but-unregistered chain) a `WithdrawalRequest` naming any existing, still-escrowed order `commitment`/`tokens` and setting `beneficiary` to themselves. `withdraw()` will transfer the victim's escrowed input tokens to the attacker and mark the order as filled/refunded, permanently blocking the legitimate solver/user from ever redeeming it. This is direct, unauthorized theft of bridge-custodied funds and a false-acceptance of a forged settlement message — squarely inside the bounty's "stealing or loss of funds" and "false proof/state acceptance" categories.

### Likelihood Explanation
Likelihood is tied to the operational reality of multi-chain rollout: Hyperbridge routinely supports proof verification for additional state machines before every app (including `IntentGatewayV2`) has been deployed/registered on every chain via `_addDeployment`. Any such chain leaves this authentication fallback live. The attacker does not need a malicious relayer, prover, or governance actor — they only need to control a contract at `address(this)` on a state machine that Hyperbridge can already produce valid proofs for but that has not yet been registered as an `IntentGateway` instance, then dispatch a message and let a normal relayer deliver the (legitimately provable) message.

### Recommendation
Make `instance()` behave like `IntentsBase._instance()`: revert with an explicit `UnknownInstance` (or equivalent) error when no gateway is registered for the given state machine, rather than silently returning `address(this)`. Authentication for `RedeemEscrow`/`RefundEscrow` must never succeed against an implicit self-match; it should only succeed against an explicitly admin/governance-registered peer address.

### Proof of Concept
1. Identify a state machine `X` for which Hyperbridge's Tron host can already verify consensus/state proofs, but for which `_instances[keccak256(X)]` has not been set on the Tron `IntentGatewayV2` (i.e., `NewDeployment` for `X` was never processed).
2. On chain `X`, deploy/control a contract at the address equal to the Tron gateway's own `address(this)` (or otherwise cause the dispatched request's `from` field to resolve to that value) and dispatch an ISMP POST request to the Tron gateway with body:
   `bytes.concat(bytes1(RequestKind.RedeemEscrow), abi.encode(WithdrawalRequest({commitment: <victim's real order commitment>, tokens: <victim's escrowed tokens/amounts>, beneficiary: <attacker>})))`.
3. Have a relayer submit the (real) proof to the Tron ISMP handler; `onAccept` invokes `authenticate(incoming.request)`, which calls `instance(X)` → returns `address(this)` (unregistered) → matches `module` → passes.
4. `withdraw()` transfers the victim's escrowed tokens to the attacker and marks the order as settled, as shown in: [3](#0-2)
