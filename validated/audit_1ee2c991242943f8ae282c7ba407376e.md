## Analysis

The HackerOne report's core pattern is: **a client-supplied field that should be validated against a privilege/authorization boundary is instead trusted directly by a downstream operation**, letting an attacker widen what an operation is allowed to do. In GitHub Desktop, the closest reachable analog is not around GitLab-style roles, but around **git command construction from attacker-influenced fields returned by the GitHub API** (an explicitly valid category per this task's Valid Impact list — "attacker controls…a GitHub API object").

`clone()` in `app/src/lib/git/clone.ts` defends against argument/URL confusion by inserting an explicit `--` separator before the untrusted `url`/`path` arguments: [1](#0-0) 

`addRemote()` in `app/src/lib/git/remote.ts`, used for PR-fork remotes, has no such separator — the attacker-influenced `url` is passed as a bare positional argument to `git remote add`: [2](#0-1) 

This function is invoked from `_findPullRequestBranch` with `headCloneUrl`, a value taken directly from a pull request's `head.repo.clone_url`/`head.repo.owner.login` — fields returned by the GitHub API for a PR that can originate from any fork, i.e., attacker-controlled data reaching Desktop without the kind of allow-list validation that `parseRemote`/`urlMatchesRemote` performs for *matching* purposes (but not for the value handed to `git remote add`): [3](#0-2) [4](#0-3) 

The remote is then immediately fetched via `_fetchRemote`, and `envForRemoteOperation`/`envForProxy` set up proxy/auth env vars but never restrict allowed git transports (no `GIT_ALLOW_PROTOCOL`/`protocol.*.allow` hardening): [5](#0-4) 

### Title
Unsanitized PR-fork `clone_url` passed to `git remote add` without option-terminator or protocol allow-list - (File: app/src/lib/git/remote.ts)

### Summary
`addRemote()` builds the argv `['remote', 'add', name, url]` and executes it via `git()`, without a `--` end-of-options marker before `name`/`url`, unlike `clone()` which explicitly guards with `--`. This function is called from `_findPullRequestBranch` with the `clone_url` and `owner.login` of a pull request's head repository — values sourced from the GitHub API for a PR opened by any external contributor against a repository the victim has open in Desktop.

### Finding Description
`_findPullRequestBranch` trusts `headCloneUrl` (PR head fork's `clone_url`) and passes it straight into `addRemote(repository, forkRemoteName, headCloneUrl)`, then fetches that remote and checks out a branch from it. Because `addRemote` never terminates option parsing with `--`, a value beginning with `-` could be interpreted by `git remote add` as a flag rather than a positional URL, altering the semantics of the invoked git subcommand (e.g. enabling `-f`/`--tags`/`--mirror`-style behavior) — a class of bug the project's own `clone()` implementation was hardened against but `remote.ts` was not. Additionally, no `GIT_ALLOW_PROTOCOL`/`protocol.*.allow=never` restriction is applied when fetching from Desktop-created fork remotes, so whatever transport `clone_url` specifies is used by git as-is once the remote exists.

### Impact Explanation
An unprivileged actor (anyone who can open a pull request against a public/forkable repository the victim has cloned in Desktop) supplies the `clone_url`/`owner.login` values consumed here. If those values can be coerced into an option-like or non-`https(s)`/`ssh` git transport string, the affected user's Desktop client will execute `git remote add`/`git fetch` with attacker-influenced argv against their own local clone, without the option-boundary protection Desktop applies elsewhere (`clone.ts`). This directly corrupts what remotes/refs the app operates on and, depending on what git accepts for `url` here, could induce silent corruption of the repository's remote configuration or unexpected network/transport behavior outside of what the intended "checkout PR from fork" invariant should allow.

### Likelihood Explanation
Medium: reaching this path requires no local access, admin rights, or social engineering beyond a user viewing/checking out a PR (an intended, common Desktop workflow) from an untrusted fork. The gap is that `remote.ts` does not apply the same `--` hardening `clone.ts` already applies to the same class of untrusted input, and `envForRemoteOperation` does not restrict allowed git protocols for these auto-created fork remotes.

### Recommendation
- Add an explicit `--` end-of-options separator in `addRemote()` (and `setRemoteURL()`) before `name`/`url`, mirroring `clone.ts`.
- Validate `headCloneUrl`/`headRepoOwner` against `parseRemote()`'s known https/ssh URL shapes before calling `addRemote`, rejecting anything that doesn't match.
- Set `GIT_ALLOW_PROTOCOL` (or equivalent `-c protocol.*.allow=never` config) for fetch/remote operations on Desktop-managed fork remotes to restrict transports to `http`, `https`, and `ssh`.

### Proof of Concept
Not independently exploitable end-to-end from the index alone: whether git's `remote add` argument parser actually treats a leading-`-` `url` as a flag (vs. rejecting it) and whether GitHub's API can be made to return a non-conforming `clone_url` for a fork are both details that require live testing against the actual `dugite`/git binary and GitHub API behavior, which is outside what static code inspection can confirm.

#### Uncertainty note
Because of index size limits, I could not fully trace every call site of `_fetchRemote`/`fetchRefspec` or confirm the exact git binary version's argv parsing behavior for `remote add`. A Devin session with full repo and a runnable git binary would be needed to confirm exploitability of the flag/protocol-injection primitive described above rather than just the missing-guard code pattern.

export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')

  return { url, name }
}
