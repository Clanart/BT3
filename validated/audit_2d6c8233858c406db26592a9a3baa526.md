### Title
Unchecked `upb_Decode` status in PHP `Message::mergeFrom()` allows silent partial/failed merges to appear successful - ([File: php/ext/google/protobuf/message.c])

### Summary
The Sherlock report's failed invariant is: *"a call that signals failure via a return value is not checked, so the caller treats a failed operation as successful, corrupting downstream state."* The direct analog in this checkout is `Message::mergeFrom()` in the PHP native extension, where the success/failure status of `upb_Decode()` is only checked through `PBPHP_ASSERT`, a macro that becomes a total no-op in the default (assert-disabled) production build. This lets a decode failure during merge be silently swallowed: the PHP call returns normally, with no exception and no signal, even though the merge did not fully apply.

### Finding Description
`Message::mergeFrom()` re-serializes the source message and re-decodes it into the destination message's `upb_Message`: [1](#0-0) 

Line 682 *does* check the encode status (`Message_checkEncodeStatus`), but the decode status on line 684-686 is only fed into `PBPHP_ASSERT(ok)` — never into a real error path, exception, or return value. The macro definition shows why this check is inert in production: [2](#0-1) 

`PBPHP_ENABLE_ASSERTS` is not defined by default, so `PBPHP_ASSERT(x)` expands to a `do {} while (false && (x))` — the condition `x` (i.e., `ok`) is never evaluated for its truth value due to short-circuiting, and the function simply falls through to its closing brace with no error reported. The same pattern also silently disables the class-match check at line 678 (`PBPHP_ASSERT(from->desc == intern->desc)`).

This mirrors the Cooler.sol bug precisely: an operation's boolean success indicator (`transferFrom`'s return / `upb_Decode`'s status) is computed but not acted upon, so failure is indistinguishable from success to the caller.

### Impact Explanation
When `upb_Decode` fails partway (e.g., recursion-depth limit exceeded, or any other structural decode error on the re-encoded bytes), `mergeFrom()` returns to PHP userland as if it succeeded. The destination message is left in a partially-merged, inconsistent state with no exception thrown. Application code that relies on `mergeFrom()` succeeding-or-throwing (the documented contract of virtually every other parse/merge API in this codebase, e.g. `MergeFromString` which does check and raise `GPBDecodeException`) will proceed with corrupted/incomplete data, silently. Because messages routinely encode authorization, validation, or state-transition fields, an application that merges attacker-influenced data into a trusted message object can end up trusting a merge that never fully happened — the same "fake success" integrity failure the report describes, just manifesting as silent data corruption rather than direct value theft.

### Likelihood Explanation
Reachability is real but narrower than the original ERC20 report: it requires (a) that the PHP protobuf extension is built without `PBPHP_ENABLE_ASSERTS` (the default/production configuration), and (b) a source message whose re-encoded bytes fail to fully decode into the destination's minitable — most plausibly via exceeding `upb_Decode`'s recursion-depth limit on a deeply-nested message tree that an application built or received. `mergeFrom()` is a standard, publicly documented PHP API (`$dest->mergeFrom($src)`), so no privileged access is needed; only that application code calls it with attacker-influenced message content, which is a normal and expected usage pattern for a serialization library consumed by an application.

### Recommendation
Check the boolean `ok` unconditionally (not just via `PBPHP_ASSERT`) and raise a PHP exception (e.g., a `GPBDecodeException` analogous to `parseFromString`'s error path) when `upb_Decode` does not return `kUpb_DecodeStatus_Ok`, mirroring the existing `Message_checkEncodeStatus` check already applied to the encode step. The same fix should apply to the `PBPHP_ASSERT(from->desc == intern->desc)` type-check at line 678, since it is also compiled out in production builds.

### Proof of Concept
Static analysis only (no execution performed in this environment):
1. In a production build (`PBPHP_ENABLE_ASSERTS` undefined, the default per `php/ext/google/protobuf/protobuf.h:61-75`), `PBPHP_ASSERT(ok)` at `php/ext/google/protobuf/message.c:686` compiles to a no-op that never evaluates `ok`.
2. Any code path where `upb_Decode(pb, size, intern->msg, l, NULL, 0, arena)` at lines 684-685 returns a status other than `kUpb_DecodeStatus_Ok` (e.g., the destination minitable rejects a structurally-deep re-serialization exceeding upb's default recursion depth limit) causes `ok = false`, but `mergeFrom()` still falls through to its closing brace and returns to PHP with no exception raised.
3. Contrast with the checked encode path immediately above it (line 682: `if (!Message_checkEncodeStatus(status)) return;`), confirming the decode status check was intentionally added for encode but omitted for decode — an asymmetric, unchecked-return-value bug consistent with the reported bug class.

I was not able to execute a live PHP extension build to force a concrete `upb_Decode` failure and observe the silent-success behavior at runtime; this assessment is based on static code and macro-expansion review only.

PHP_METHOD(Message, mergeFrom) {
  Message* intern = (Message*)Z_OBJ_P(getThis());
  Message* from;
  upb_Arena* arena = Arena_Get(&intern->arena);
  const upb_MiniTable* l = upb_MessageDef_MiniTable(intern->desc->msgdef);
  zval* value;
  char* pb;
  size_t size;
  bool ok;

  if (zend_parse_parameters(ZEND_NUM_ARGS(), "O", &value,
                            intern->desc->class_entry) == FAILURE) {
    return;
  }

  from = (Message*)Z_OBJ_P(value);

  // Should be guaranteed since we passed the class type to
  // zend_parse_parameters().
  PBPHP_ASSERT(from->desc == intern->desc);

  // TODO: use a temp arena for this.
  upb_EncodeStatus status = upb_Encode(from->msg, l, 0, arena, &pb, &size);
  if (!Message_checkEncodeStatus(status)) return;

  ok = upb_Decode(pb, size, intern->msg, l, NULL, 0, arena) ==
       kUpb_DecodeStatus_Ok;
  PBPHP_ASSERT(ok);
}
