### Title
Uncontrolled recursion in wallet outer-puzzle driver matching allows a malicious offer/coin to crash the wallet process - (File: `chia/wallet/outer_puzzles.py`, `chia/wallet/cat_wallet/cat_outer_puzzle.py`, `chia/wallet/nft_wallet/singleton_outer_puzzle.py`, `chia/wallet/vc_wallet/cr_outer_puzzle.py`, `chia/wallet/trading/offer.py`)

### Summary
The wallet's outer-puzzle "driver" matching system recursively descends through nested puzzle layers (CAT, singleton, ownership, credential-restricted, etc.) with no bound on nesting depth. `match_puzzle()` in `chia/wallet/outer_puzzles.py` dispatches to per-asset-type `match()` implementations (e.g. `CATOuterPuzzle.match`, `SingletonOuterPuzzle.match`, `CROuterPuzzle.match`) that each call `self._match(UnknownPuzzle(known_program=inner_puzzle))` on the discovered inner puzzle, recursing one Python stack frame — interleaved with Rust CLVM `uncurry()` calls — per layer. An attacker who controls a puzzle reveal (via an offer file or a coin sent to a wallet's tracked puzzle hash) can construct an arbitrarily deep chain of curried layers, driving unbounded recursion analogous to the mdex/Comrak AST-conversion bug (uncontrolled recursion across a language/native boundary with no depth check).

### Finding Description
`match_puzzle()` [1](#0-0)  loops over registered drivers and calls each driver's `.match()`. Each driver's `match()` implementation matches its own puzzle shape via `uncurry()` (a Rust CLVM boundary call) and then, if the shape matches, recurses into `self._match()` on the inner puzzle to keep unwrapping additional layers, e.g.:

- `CATOuterPuzzle.match` [2](#0-1) 
- `SingletonOuterPuzzle.match` [3](#0-2) 
- `CROuterPuzzle.match` [4](#0-3) 

None of these implementations, nor `match_puzzle()` itself, impose a maximum nesting/recursion depth. The number of recursive calls is bounded only by the number of curried layers present in the attacker-supplied puzzle reveal. Because each recursive step also invokes `Program.uncurry()` [5](#0-4)  which crosses into the Rust CLVM extension (`run_chia_program`), the Python interpreter's own recursion-depth guard does not cleanly bound the combined native+Python stack usage — the same "recursion crosses a language boundary without a depth limit" pattern described in the mdex/Comrak advisory (Python frames interleaved with native CLVM parser frames can exhaust the OS thread stack rather than triggering a catchable `RecursionError`).

The reachable trigger path is `Offer.from_spend_bundle()` [6](#0-5) , which is invoked whenever a wallet parses an offer (e.g. when a user runs `take_offer`/`get_offer_summary`, or a full/light wallet processes a `SpendBundle` it received). For every `coin_spend` in the bundle it calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` on attacker-supplied, unvalidated puzzle reveals, feeding directly into the unbounded recursive matcher. The same `match_puzzle` recursive path is also exercised whenever the wallet syncs a coin (any coin sent to a tracked puzzle hash) and tries to identify its asset type/driver.

### Impact Explanation
A single maliciously crafted offer file or a single coin sent to a wallet-tracked address with an extremely deep chain of curried puzzle layers (CAT-in-CAT-in-singleton-in-ownership-in-CR, repeated thousands of times) can drive `match_puzzle`'s recursive descent past safe stack limits. Depending on how deep the combined Python/Rust call stack goes, this manifests as either an uncaught `RecursionError` that aborts the wallet's spend/offer-processing task, or — if the native CLVM frames dominate stack usage per layer — a hard stack overflow that crashes the wallet process outright, halting all transaction processing for that wallet (a spend-triggered transaction-processing halt), consistent with the "coin/offer-triggered processing halt" impact class called out in the validation criteria.

### Likelihood Explanation
Likelihood is high for triggering the crash/exception: constructing a puzzle reveal with many nested curry layers is inexpensive for an attacker (pure CLVM construction, no signatures or fees required beyond what's needed to build a spendable/offerable puzzle skeleton), and delivering it either as an offer file to a counterparty or as a low-value coin to a victim's tracked puzzle hash is trivial and requires no special privilege — matching the "offer counterparty" / "wallet user" reachability criteria in scope.

### Recommendation
Add an explicit maximum recursion/nesting depth (e.g., a small constant bound like 32–64 layers) enforced in `match_puzzle()` in `chia/wallet/outer_puzzles.py`, threading a depth counter (or converting the recursive `match()`/`_match()` chain into an iterative loop) through all `DriverProtocol.match()` implementations (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`, `TransferProgramPuzzle`, `RevocationOuterPuzzle`). Reject (return `None` / raise a handled error) once the depth limit is exceeded instead of continuing to recurse, and apply the same bound to `Offer.from_spend_bundle()`'s per-coin-spend driver matching before further offer/spend processing.

### Proof of Concept
Not independently executed (no code-execution access in this session); the trigger construction, based on the code paths cited above, would be:
1. Build an innermost puzzle (e.g. `ACS`), then repeatedly wrap it N times (N in the thousands) using nested `construct_cat_puzzle` / singleton `curry` / `construct_cr_layer` calls to produce a puzzle reveal with N curried layers, analogous to the pattern already used for two-layer nesting in `chia/_tests/wallet/cat_wallet/test_cat_outer_puzzle.py` (`double_cat_puzzle = construct_cat_puzzle(CAT_MOD, tail, cat_puzzle)`) [7](#0-6) , but scaled to a very large N instead of 2.
2. Place this puzzle as the `puzzle_reveal` of a `CoinSpend` inside a `SpendBundle`/offer file, or send a coin whose puzzle hash matches this deeply-nested puzzle to a victim wallet's tracked address.
3. Have the victim wallet call `Offer.from_bytes()`/`from_spend_bundle()` (e.g., via `take_offer`) or let the wallet's coin-state sync path call `match_puzzle()` on the received coin's puzzle reveal, triggering N nested recursive `match()`/`uncurry()` calls with no depth check, exhausting the stack.

```python
    def uncurry(self) -> tuple[Program, Program]:
        def match(o: CLVMStorage, expected: bytes) -> None:
            if o.atom != expected:
                raise ValueError(f"expected: {expected.hex()}")

        try:
            # (2 (1 . <mod>) <args>)
            ev, quoted_inner, args_list = self.as_iter()
            match(ev, b"\x02")
            if TYPE_CHECKING:
                # this being False is presently handled in the TypeError exception handler below
                assert quoted_inner.pair is not None
            match(quoted_inner.pair[0], b"\x01")
            mod = quoted_inner.pair[1]
            args = []
            while args_list.pair is not None:
                # (4 (1 . <arg>) <rest>)
                cons, quoted_arg, rest = args_list.as_iter()
                match(cons, b"\x04")
                if TYPE_CHECKING:
                    # this being False is presently handled in the TypeError exception handler below
                    assert quoted_arg.pair is not None
                match(quoted_arg.pair[0], b"\x01")
                args.append(quoted_arg.pair[1])
                args_list = rest
            match(args_list, b"\x01")
            return Program.to(mod), Program.to(args)
        except ValueError:  # too many values to unpack
            # when unpacking as_iter()
            # or when a match() fails
            return self, self.to(0)
        except TypeError:  # NoneType not subscriptable
            # when an object is not a pair or atom as expected
            return self, self.to(0)
        except EvalError:  # first of non-cons
            # when as_iter() fails
            return self, self.to(0)
```

```python
    @classmethod
    def from_spend_bundle(cls, bundle: WalletSpendBundle) -> Offer:
        # Because of the `to_spend_bundle` method, we need to parse the dummy CoinSpends as `requested_payments`
        requested_payments: dict[bytes32 | None, list[NotarizedPayment]] = {}
        driver_dict: dict[bytes32, PuzzleInfo] = {}
        leftover_coin_spends: list[CoinSpend] = []
        for coin_spend in bundle.coin_spends:
            driver = match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))
            if driver is not None:
                asset_id = create_asset_id(driver)
                assert asset_id is not None
                driver_dict[asset_id] = driver
            else:
                asset_id = None
            if coin_spend.coin.parent_coin_info == bytes32.zeros:
                notarized_payments: list[NotarizedPayment] = []
                for payment_group in Program.from_serialized(coin_spend.solution).as_iter():
                    nonce = bytes32(payment_group.first().as_atom())
                    payment_args_list = payment_group.rest().as_iter()
                    notarized_payments.extend(
                        [NotarizedPayment.from_condition_and_nonce(condition, nonce) for condition in payment_args_list]
                    )

                requested_payments[asset_id] = notarized_payments
            else:
                leftover_coin_spends.append(coin_spend)

        return cls(
            requested_payments, WalletSpendBundle(leftover_coin_spends, bundle.aggregated_signature), driver_dict
        )
```
