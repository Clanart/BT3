### Title
Crash (panic) via preprocess commitments summing to the identity point causes R = ∞ and panics BIP-340 `Hram::hram` — ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
CVE-2021-2215 is an availability-only DoS: inputs under an attacker's control cause a hang or repeatable crash. The analog in Serai is a reachable panic in the Bitcoin Schnorr signing path. An attacker who supplies a FROST preprocess whose commitment points sum to the identity point forces the aggregate nonce `R` to be the point at infinity. `Hram::hram` unconditionally calls `x(R)`, which executes `expect("point at infinity")`, crashing the signer/aggregator with untrusted input alone.

### Finding Description
`x(key)` extracts the x-coordinate of a point via `to_encoded_point` and panics when the point is infinity:

`networks/bitcoin/src/crypto.rs`:
```rust
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
pub(crate) fn x_only(key: &ProjectivePoint) -> XOnlyPublicKey {
  XOnlyPublicKey::from_slice(&x(key))
    .expect("x_only was passed a point which was infinity or odd")
}
```

`Hram::hram` invokes `x(R)` on the aggregate nonce and documents the panic itself: "If either `R` or `A` is the point at infinity, this will panic."

The attacker-controlled `R` flows through `AlgorithmSignMachine::sign` in `crypto/frost/src/sign.rs`: preprocesses are read via `read_preprocess` → `Commitments::read`, combined into `Rs = B.nonces(&nonces)` (a `BindingFactor`-weighted sum of each participant's nonce commitments), and passed to `sign_share` and later `verify`. `Curve::read_G` rejects the identity *per commitment*, but nothing rejects a linear combination of valid non-identity points that is itself identity. An attacker contributing two preprocess commitments `[P, -P]` (or a commitment crafted to cancel the other participants' sums) makes the aggregate `R = ∞`. The next call into `hram(R, A, msg)` inside `sign_share`/`verify` panics on `expect("point at infinity")`.

The doc comment on `Schnorr` claims the infinity case has "negligible probability for a well-reasoned caller, even with malicious participants present" — this is incorrect: a malicious preprocess sender deterministically produces `R = ∞` by choosing commitments that cancel.

### Impact Explanation
Complete denial of service of the signing node. Any participant in a Bitcoin multisig signing session can crash every honest signer (or the coordinator aggregating shares) by broadcasting a maliciously crafted preprocess. Repeated attempts crash the node each time the session is retried — a "frequently repeatable crash" exactly matching the CVE's availability impact. Signing for Bitcoin outputs is halted, so funds cannot move.

### Likelihood Explanation
Preprocess messages are the expected untrusted input to the FROST state machine (`read_preprocess` accepts peer bytes), so an unprivileged participant fully controls the commitment points. Constructing `[P, -P]` costs nothing. No key material, collusion, or race is needed — a single malicious participant crashes the process deterministically.

### Recommendation
Reject aggregate nonces equal to the identity before invoking `hram`, or make `x`/`x_only` return `Option`/`io::Result` and propagate `FrostError` instead of panicking. Alternatively, check `R.is_identity()` after `B.nonces(&nonces)` in `sign()` and in `verify` before completing, returning `FrostError::InternalError`/blame rather than aborting.

### Proof of Concept
```rust
// Attacker-side: craft a preprocess for a Schnorr AlgorithmMachine with
// two required nonces (or one nonce where the scheme allows shaping the sum).
use frost::curve::{Curve, Secp256k1};
use k256::ProjectivePoint;

// Instead of committing to real nonces d, e, broadcast commitments:
//   D = P, E = -P   (P any valid non-identity secp256k1 point)
// Both pass Commitments::read since each is canonical and non-identity.
// With binding factor rho, the aggregate contribution is
//   P + rho*(-P) = (1 - rho)*P  -- choose instead D and E for two
// participants P_i and -P_i so the *sum* over all signers is identity.

// Victim-side flow (crypto/frost/src/sign.rs):
//   let preprocess = machine.read_preprocess(&mut attacker_bytes)?; // Ok
//   machine.sign(preprocesses, msg)
//     -> Rs = B.nonces(&nonces)  // R == identity
//     -> algorithm.sign_share(&view, &Rs, nonces, msg)
//        -> Hram::hram(&R, &A, msg)   // networks/bitcoin/src/crypto.rs
//           -> x(R) -> expect("point at infinity")  // PANIC
```

To hit the panic deterministically, the attacker first observes the honest participants' preprocesses (each contributes `D_j, E_j`), computes the expected weighted sum `S = Σ (D_j + rho_j·E_j)` for their own share of the set, and publishes commitments `D_a = -S + Q`, `E_a` chosen so that `D_a + rho_a·E_a = -S`. The aggregate `R = S + (-S) = ∞`, and `Hram::hram` panics inside `sign_share`/`verify` — no unwrap on attacker bytes is required, only valid canonical points.
