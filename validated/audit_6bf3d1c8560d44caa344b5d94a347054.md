### Title
`Scanner::scan_block` reports immature coinbase outputs as received, crediting funds that cannot be spent for 100 blocks - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Skale `ValidatorService` issue — where disabled validators retain delegated funds that stay locked until the delegation period ends — bitcoin-serai's `Scanner::scan_block` credits outputs from the coinbase transaction exactly like any other received output, even though coinbase outputs are consensus-locked for 100 blocks. Serai therefore reports funds as received that are not actually spendable, and there is no mechanism in the scanning API to handle the lock period — only a doc comment telling callers to filter manually.

### Finding Description
`Scanner::scan_block` iterates `block.txdata` in full, calling `scan_transaction` on every transaction including `txdata[0]` (the coinbase): [1](#0-0) . `scan_transaction` matches on `output.script_pubkey` only and emits a `ReceivedOutput` with no maturity or transaction-position awareness [2](#0-1) . A `ReceivedOutput` is treated downstream as a spendable UTXO: it carries only `offset`, `output`, and `outpoint`, with no marker that it is coinbase-locked [3](#0-2) .

The lock is invisible at the type level — the only mitigation is a doc comment stating "this will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed" [4](#0-3) . Notably, the other call site that *does* care (`get_outputs` in the processor) had to manually skip `block.txdata[1 ..]` [5](#0-4) , confirming the hazard is real enough that consumers must work around it; `scan_block` itself offers no safe variant.

Just as disabling a Skale validator leaves delegations silently locked for up to 12 months, spending to a Serai-watched script via a coinbase leaves the wallet reporting a balance that is consensus-unspendable for ~100 blocks, with the lock state not represented anywhere in `ReceivedOutput`.

### Impact Explanation
A `ReceivedOutput` obtained from an immature coinbase is indistinguishable from a normal spendable output. Any consumer that feeds scan results into transaction building (`SignableTransaction::new`) or accounting will treat the funds as available. Constructing a spend of an immature coinbase output produces a transaction that is invalid by consensus (BIP-30/COINBASE_MATURITY = 100) and will be rejected, while the wallet's books show the balance as received — "funds reported received that are not spendable". Under re-orgs the coinbase may also disappear entirely, making the reported output unspendable permanently rather than temporarily.

### Likelihood Explanation
Reachable by an unprivileged party: a miner (or a pool paying out via coinbase-like flows, or anyone influencing coinbase outputs on regtest-like setups) can direct a coinbase output to a Serai P2TR script — `scan_transaction` matches purely on `script_pubkey` [6](#0-5) . Any call to `scan_block` then credits it. The triggering input is ordinary on-chain transaction data, no privileged access required. Severity Medium: it requires a miner counterparty and primarily causes locked/misreported funds rather than direct theft.

### Recommendation
Have `scan_block` skip `block.txdata[0]` (mirroring the `txdata[1 ..]` workaround already used in `processor/src/networks/bitcoin.rs:691`), or extend `ReceivedOutput`/`scan_transaction` to carry a maturity flag so immature outputs are surfaced distinctly. Alternatively, mark coinbase-derived outputs and refuse to feed them into `SignableTransaction` until maturity.

### Proof of Concept
1. Create `Scanner::new(key)` for an even Serai group key.
2. Mine a block whose coinbase pays to `p2tr_script_buf(key)` (as the existing test does via `generatetoaddress` to that script — `networks/bitcoin/tests/wallet.rs:43-69` confirms the scanner picks up the coinbase output).
3. Call `scanner.scan_block(&block)` before mining 100 more blocks: it returns a `ReceivedOutput` for the coinbase output.
4. Feed that `ReceivedOutput` into `SignableTransaction::new` and sign — `send_raw_transaction` rejects it as immature, demonstrating the wallet credited unspendable funds.
