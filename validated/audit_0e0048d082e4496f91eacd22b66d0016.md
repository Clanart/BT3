### Title
Unbounded string/bytes offset in EVM `console.log` precompile causes node panic on crafted call data - (File: blockchain/vm/contracts.go)

### Summary
The Hardhat-style `console.log` precompiled contract decodes attacker-controlled `params` bytes using offsets derived from raw `big.Int` values without validating that those offsets are non-negative or within a sane range before slicing, analogous to CVE-2018-7320 where the SIGCOMP dissector failed to validate operand offsets before using them to index into a buffer.

### Finding Description
`consoleLog.Run` is a precompiled contract reachable by any EVM `CALL`/`STATICCALL` with fully attacker-controlled `input`, dispatched purely by a 4-byte selector match against `common.ConsoleLogSignatures`: [1](#0-0) 

The actual decoding for `StringTy`/`BytesTy` parameters computes an offset by converting an arbitrary 256-bit big integer to a Go `int` via `big.Int.Int64()`, whose result is explicitly documented as undefined when the value cannot be represented in an `int64`: [2](#0-1) [3](#0-2) 

Because `start` can become negative (attacker sets the high bits of the 32-byte word so the low 64 bits interpreted as signed produce a negative value), the bounds checks `len(params) < start+registerSize` and `len(params) < start+size+registerSize` do not reject negative offsets (a negative right-hand side is trivially less than `len(params)`). The subsequent slice expression `params[start : start+registerSize]` (or `params[start+registerSize : start+size+registerSize]`) with a negative `start` triggers a Go runtime panic ("slice bounds out of range"), not a returned `error`.

This mirrors the SIGCOMP bug class from the CVE: an offset taken directly from untrusted input is used to index a buffer without validating it is within `[0, len(buffer)]`, leading to an out-of-bounds access/crash instead of a graceful decode error.

### Impact Explanation
`consoleLog.Run`'s panic occurs during normal EVM contract execution reachable from a single, ordinary transaction (or `eth_call`) that targets the console.log precompile address with a crafted 4-byte selector plus a `string`/`bytes` parameter whose length-word encodes a value whose low 64 bits form a negative `int64`. Unless the Go runtime panic is recovered somewhere above the precompile dispatch layer (search for a `recover()` wrapping `RunPrecompiledContract`/`Contract.Run` calls in `blockchain/vm/evm.go` did not show a call-site recover in the reviewed code), this crashes the executing node process while processing a transaction/block, which is a state-divergence/DoS class impact (nodes that crash cannot validate/relay blocks; if unrecovered panics during block processing differ across otherwise-identical nodes it can also cause consensus/availability issues). This is a High-severity, single-transaction-reachable crash, matching the reachable, unprivileged-sender criteria of the report.

### Likelihood Explanation
Reaching this requires only an unprivileged transaction sender or `eth_call`/`eth_estimateGas` submitter, no special account key or on-chain privilege, and no cooperation from other parties. The selector lookup table `common.ConsoleLogSignatures` and the exact parameter layout needed to trigger a negative offset were not directly inspected due to index limits (see below), so it is not fully confirmed which concrete selector/type combination is required, but the vulnerable code path (`decode` for `StringTy`/`BytesTy`) is unconditionally exercised whenever a matching selector with such a parameter type is invoked with attacker data.

### Recommendation
- Replace `big.NewInt(0).SetBytes(...).Int64()` conversions in `consoleLog.decode` with a safe conversion that rejects values exceeding `math.MaxInt32` (or a reasonable bound relative to `len(params)`), returning an error instead of relying on undefined `Int64()` truncation.
- After computing `start`/`size`, explicitly check `start >= 0 && size >= 0` before performing any additional arithmetic or slicing.
- Wrap precompiled contract execution (or at least `consoleLog.Run`) in a `recover()` so any residual decoding panic is converted into an EVM execution error rather than crashing the process.

### Proof of Concept
Conceptual PoC (exact selector/layout requires confirming `common.ConsoleLogSignatures`, which the indexed code did not fully expose):
1. Craft `input = selector(4 bytes matching a StringTy/BytesTy signature) || wordWithHighBitPattern || ...` such that `big.NewInt(0).SetBytes(word).Int64()` yields a negative `int64` (e.g., a 32-byte word like `0x00000000000000010000000000000000000000000000000000000000000000` chosen so the low-8-byte view is negative when reinterpreted as signed, per `Int64()`'s documented undefined behavior for out-of-range values).
2. Send this as `data` in a transaction (or `eth_call`) whose `to` is the `console.log` precompile address.
3. During `consoleLog.decode`, `start` becomes negative; the bounds checks pass (comparing `len(params)` to a negative number), and `params[start : start+registerSize]` panics with "slice bounds out of range", crashing/aborting the transaction execution path unless recovered elsewhere.

Note: Due to indexing limits, the exact contents of `common.ConsoleLogSignatures`/`common/console_log.go` and whether `blockchain/vm/evm.go` wraps precompile calls in a `recover()` were not fully confirmed in this session; a Devin session with full repository access should verify these two points to finalize exploitability before treating this as fully confirmed.

// Hardhat console.log accepts format string, however we don't support it.
// Instead, we just join all the parameters with a space.
func (c *consoleLog) toLogString(input []byte) (string, error) {
	if len(input) < 4 {
		return "", errors.New("input too short")
	}
	selector := binary.BigEndian.Uint32(input[:4])
	params := input[4:]

	types, ok := common.ConsoleLogSignatures[selector]
	if !ok {
		return "", errors.New("unknown selector")
	}
	decoded, err := c.decode(params, types)
	if err != nil {
		return "", err
	}

	return strings.Join(decoded, " "), nil
}
