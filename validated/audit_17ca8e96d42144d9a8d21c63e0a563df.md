### Title
CosmWasm contract `BankMsg::Send` bypasses tokenfactory `DenomAllowList` enforced on native `MsgSend`/`MsgMultiSend` - (File: sei-wasmd/x/wasm/keeper/keeper.go)

### Summary
The bug class from the Traefik advisory is a security allowlist that is enforced on one entry path to a shared resource but omitted on a structurally sibling path that reaches the same resource. Sei-chain's bank module has the same pattern: the tokenfactory `DenomAllowList` restriction is enforced in `x/bank`'s native `MsgSend`/`MsgMultiSend` handlers, but the CosmWasm contract-originated bank-send path (reachable by any wasm contract execution) calls the low-level `BankKeeper.SendCoins` directly and never checks the allow list.

### Finding Description
`x/bank`'s message server enforces the tokenfactory denom allow list on both entry points that end users can reach directly:

- `MsgSend`: calls `k.IsInDenomAllowList` for both sender and receiver before calling `k.SendCoins`. [1](#0-0) 
- `MsgMultiSend`: same allow-list check applied to every input/output. [2](#0-1) 

However, the low-level `BaseSendKeeper.SendCoins`/`SendCoinsWithoutAccCreation` function itself does **not** perform the `IsInDenomAllowList` check — that check lives only in `msgServer`, one layer above. [3](#0-2) [4](#0-3) 

CosmWasm's `BankCoinTransferrer.TransferCoins` — used by the wasm module to move funds when a contract issues `BankMsg::Send`, and when a contract is instantiated/executed with attached funds — calls `keeper.SendCoins` directly, checking only `IsSendEnabledCoins` and `BlockedAddr`: [5](#0-4) 

The same low-level `k.bank.TransferCoins` call is also used directly inside contract `execute`/`instantiate` to move attached funds into the contract: [6](#0-5) 

This is invoked from the generic wasm SDK message dispatcher (`SDKMessageHandler`/`handleSdkMessage`), which is reachable by any CosmWasm contract emitting a `BankMsg::Send` submessage — confirmed working end to end in the wasmd test suite (a `ReflectHandleMsg` triggers a `BankMsg::Send`, moving funds without any allow-list gate): [7](#0-6) [8](#0-7) 

Crucially, the EVM surface also reaches this same unguarded path: the `wasmd` Cosmos precompile's `execute`/`executeBatch` methods (callable by any EVM contract or EOA, including via CW20/CW721/CW1155 ERC pointer delegatecalls) invoke `p.wasmdKeeper.Execute`, which funds the contract through the same `TransferCoins`/`SendCoins` path that skips `IsInDenomAllowList`. [9](#0-8) 

### Impact Explanation
Tokenfactory denom allow lists exist to let a denom creator restrict a regulated/permissioned token to a specific address set (e.g., compliance-gated stablecoins) — this is a documented, security-relevant primitive. [10](#0-9) [11](#0-10) 

Because CosmWasm's bank-send and funds-attachment paths bypass `IsInDenomAllowList`, any unprivileged wasm contract deployer/caller (or EVM caller reaching CosmWasm via the `wasmd` precompile) can move an allow-listed tokenfactory denom to or from an address that is explicitly not authorized to send/receive it — the exact "unauthorized transfer bypassing an authorization allowlist" impact class called out in the validation rules. This defeats the compliance/authority control the denom creator relies on and constitutes unauthorized transfer of a controlled asset.

### Likelihood Explanation
Any account can permissionlessly deploy a CosmWasm contract and issue `BankMsg::Send` submessages, or fund a contract via `instantiate`/`execute` — no special privilege is required beyond normal wasm/EVM tx submission. Because the vulnerable path is exercised by ordinary reflect-style dispatch tests, it is a normal, everyday code path, not an edge case, making exploitation straightforward for anyone who can identify an allow-listed tokenfactory denom (allow lists are queryable on-chain) and get any coins of that denom into a contract, or induce a contract holding such coins to forward them to a `BankMsg::Send`.

### Recommendation
Move the `IsInDenomAllowList` check (matching the logic already in `sei-cosmos/x/bank/keeper/msg_server.go`) into the shared low-level transfer path — either inside `BaseSendKeeper.SendCoins`/`sendCoinsWithoutAccCreation`, or explicitly inside `BankCoinTransferrer.TransferCoins` and the direct `k.bank.TransferCoins` call in `wasm/keeper/keeper.go`'s `execute`/`instantiate`, so every entry point (native `MsgSend`, `MsgMultiSend`, wasm `BankMsg::Send`, wasm funds attachment, and the `wasmd` EVM precompile) is uniformly gated.

### Proof of Concept
1. Create a tokenfactory denom `factory/{creator}/regulated` and call `SetDenomAllowList` restricting it to `{creator, allowedRecipient}` (mirrors `x/bank` test setup). [12](#0-11) 
2. Fund a CosmWasm contract with this denom (e.g., via `MsgSend` from an allow-listed account to the contract, or via `instantiate`/`execute` with `Funds`).
3. From the contract, execute a `wasmvmtypes.CosmosMsg{Bank: &BankMsg{Send: &SendMsg{ToAddress: <not-allow-listed-address>, Amount: [...regulated denom...]}}}` — mirroring the pattern already validated in `TestDispatchSubMsgSuccessCase`/`TestReflectCustomMsg`. [13](#0-12) 
4. Observe the transfer succeeds and funds land in the non-allow-listed address, whereas the equivalent native `MsgSend` from an EOA to that same address is rejected with `"... is not allowed to receive funds"`. [14](#0-13)

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

// TransferCoins transfers coins from source to destination account when coin send was enabled for them and the recipient
// is not in the blocked address list.
func (c BankCoinTransferrer) TransferCoins(parentCtx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amount sdk.Coins) error {
	em := sdk.NewEventManager()
	ctx := parentCtx.WithEventManager(em)
	if err := c.keeper.IsSendEnabledCoins(ctx, amount...); err != nil {
		return err
	}
	if c.keeper.BlockedAddr(toAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", toAddr.String())
	}

	sdkerr := c.keeper.SendCoins(ctx, fromAddr, toAddr, amount)
	if sdkerr != nil {
		return sdkerr
	}
	for _, e := range em.Events() {
		if e.Type == sdk.EventTypeMessage { // skip messages as we talk to the keeper directly
			continue
		}
		parentCtx.EventManager().EmitEvent(e)
	}
	return nil
}

func (h SDKMessageHandler) DispatchMsg(ctx sdk.Context, contractAddr sdk.AccAddress, contractIBCPortID string, msg wasmvmtypes.CosmosMsg, info wasmvmtypes.MessageInfo, codeInfo types.CodeInfo) (events []sdk.Event, data [][]byte, err error) {
	sdkMsgs, err := h.encoders.Encode(ctx, contractAddr, contractIBCPortID, msg, info, codeInfo)
	if err != nil {
		return nil, nil, err
	}
	for _, sdkMsg := range sdkMsgs {
		res, err := h.handleSdkMessage(ctx, contractAddr, sdkMsg)
		if err != nil {
			return nil, nil, err
		}
		// append data
		data = append(data, res.Data)
		// append events
		sdkEvents := make([]sdk.Event, len(res.Events))
		for i := range res.Events {
			sdkEvents[i] = sdk.Event(res.Events[i])
		}
		events = append(events, sdkEvents...)
	}
	return
}

func (h SDKMessageHandler) handleSdkMessage(ctx sdk.Context, contractAddr sdk.Address, msg sdk.Msg) (*sdk.Result, error) {
	if err := msg.ValidateBasic(); err != nil {
		return nil, err
	}
	// make sure this account can send it
	for _, acct := range msg.GetSigners() {
		if !acct.Equals(contractAddr) {
			return nil, sdkerrors.Wrap(sdkerrors.ErrUnauthorized, "contract doesn't have permission")
		}
	}

	// find the handler and execute it
	if handler := h.router.Handler(msg); handler != nil {
		// ADR 031 request type routing
		msgResult, err := handler(ctx, msg)
		return msgResult, err
	}
	// legacy sdk.Msg routing
	// Assuming that the app developer has migrated all their Msgs to
	// proto messages and has registered all `Msg services`, then this
	// path should never be called, because all those Msgs should be
	// registered within the `msgServiceRouter` already.
	return nil, sdkerrors.Wrapf(sdkerrors.ErrUnknownRequest, "can't route message %+v", msg)
}

Best practices dictate careful review of `bank` module code to ensure that
permissions are limited in the way that you expect.

## Blocklisting Addresses

The `x/bank` module accepts a map of addresses that are considered blocklisted
from directly and explicitly receiving funds through means such as `MsgSend` and
`MsgMultiSend` and direct API calls like `SendCoinsFromModuleToAccount`.

Typically, these addresses are module accounts. If these addresses receive funds
outside the expected rules of the state machine, invariants are likely to be
broken and could result in a halted network.

By providing the `x/bank` module with a blocklisted set of addresses, an error occurs for the operation if a user or client attempts to directly or indirectly send funds to a blocklisted account, for example, by using [IBC](http://docs.cosmos.network/master/ibc/).
