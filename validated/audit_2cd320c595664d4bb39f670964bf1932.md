### Title
Fork remote pruning can delete a remote that is still actively referenced, breaking the invariant that a "removed" remote is no longer needed - ([File: app/src/lib/stores/git-store.ts])

### Summary
`GitStore.pruneForkedRemotes` removes any `github-desktop-*` remote that is not currently referenced by an open pull request URL or a local branch's upstream, mirroring the `removeWrapping` pattern in the original report: an entity is torn down based on a point-in-time check that does not guarantee nothing still depends on it. Because the "still in use" check is a stale, string-based snapshot (`this.allBranches` and PR `head.gitHubRepository.cloneURL`) that is refreshed on a separate, PR-poller-driven cadence, an attacker who controls the pull request's head/fork state (closing/reopening a PR, renaming/transferring the fork, or making it private) can cause the check to falsely conclude the remote is unused while a checkout/fetch that depends on it is still in flight, exactly as `removeWrapping` could be invoked while wrapped tokens were still circulating.

### Finding Description
`pruneForkedRemotes` is invoked from `AppStore.onPullRequestChanged` every time the pull-request list for a repository changes (polled every up to 30 minutes, but re-triggered any time `PullRequestCoordinator.refreshPullRequests` fires): [1](#0-0) 

The pruning decision itself lives in `findForkedRemotesToPrune`: [2](#0-1) 

It keeps a `github-desktop-*` remote only if:
1. its URL exactly string-matches some open PR's `head.gitHubRepository.cloneURL`, or
2. its name is present in `branchRemotes`, built from `this.allBranches` (the `GitStore`'s in-memory/cached branch list) via `branch.upstreamRemoteName`.

Once a remote fails both checks, `pruneForkedRemotes` unconditionally calls `removeRemote`: [3](#0-2) 

Both inputs are attacker/timing-influenced and not guaranteed to reflect the true, current state of the local repository:

- **URL check is exact string equality.** `IRemote.url` was captured from Git config when the fork remote was added, while `pr.head.gitHubRepository.cloneURL` is re-fetched from the API on every poll. If the PR author renames or transfers their fork (something the fork owner - the "attacker controlling a GitHub API object" per the valid-impact criteria - fully controls), the newly-fetched `cloneURL` no longer matches the URL stored in the local remote, so `prRemoteUrls.has(r.url)` becomes `false` even though the PR is still open and the user may still have that fork checked out.
- **Branch check depends on `this.allBranches` being current.** The remote is only protected if a local branch's upstream already points at it. When a user checks out a PR from a fork, Desktop must first add the remote, then fetch, then create/track the local branch. Until that local branch exists (or until `git-store`'s cached branch list is refreshed to reflect it), `branchRemotes` won't contain the new remote's name. A `pruneForkedRemotes` pass triggered by an independent PR-list poll landing in that window - a race the app does not synchronize against - will treat the freshly-added, in-use remote as orphaned.
- **PR closing/reopening.** A PR author can close a PR to drop it from `openPRs` and force pruning of the remote next PR-poll cycle, then reopen it; if the user's checkout/fetch is in progress when the poll lands, the remote used by that in-flight git operation is deleted mid-flight.

No mitigation exists to check whether a fetch/checkout is currently using the remote before it is removed, and `removeRemote` silently succeeds/no-ops on missing remotes with no signal back to any in-flight consumer of that remote name.

### Impact Explanation
When the remote backing an in-progress or just-completed checkout of a forked PR branch is deleted:
- Any subsequent `git fetch`/`git push`/`git pull` against that remote name fails ("No such remote").
- If the deletion races with an active fetch (e.g. `performFetch`), the operation can fail or leave the local branch's upstream tracking pointing at a nonexistent remote, silently breaking the user's ability to sync or push their work on that branch, corrupting the expected state of "what the user can push/fetch" - which matches the accepted valid-impact category of "silent corruption of what the user commits or pushes" driven by attacker control of a GitHub API object (the fork/PR head repo).
- This is triggerable purely by the PR author's/fork owner's actions (rename, transfer, close/reopen) without any unusual step by the victim beyond normal PR-checkout usage, satisfying the "unprivileged... attacker controls a GitHub API object" bar.

Severity is moderate: it does not grant code execution, but it degrades git operation integrity/availability for the victim's fork-tracking branch, analogous to the confirmed Medium-severity impact in the original report (users permanently unable to unwrap tokens once the mapping is removed).

### Likelihood Explanation
The `PullRequestUpdater` refreshes PR state as often as every 2 minutes while the app is focused, and any state-changing webhook-driven refresh (close/reopen, fork rename) is trivially triggerable by the PR author at will: [4](#0-3) 
Combined with the fact that `pruneForkedRemotes` runs unconditionally on every such refresh with no coordination against in-flight fetch/checkout operations, the race window is real, though it requires the victim to be actively checking out/using the specific fork's PR at the unlucky moment, which lowers likelihood from "trivial" to "situational but realistic," consistent with a Medium-severity classification.

### Recommendation
- Do not rely on point-in-time, string-equal URL matching against the API's `cloneURL`; instead track, per checked-out fork remote, whether it currently backs a tracked local branch's upstream by re-querying git state (not a possibly-stale cache) immediately before deletion, and re-verify after fetching the latest branch list.
- Synchronize `pruneForkedRemotes` with any in-flight `performFetch`/checkout that references the same remote (e.g. via the existing "any fetches or pulls are currently in-progress" guard already used elsewhere in `app-store.ts`) so pruning is deferred while an operation using that remote is active.
- Treat the PR-open check as best-effort corroboration only and require confirmation from actual git state (e.g., `git branch --list '*upstream_remote*'` freshly queried) rather than the cached `allBranches` snapshot before calling `removeRemote`.

### Proof of Concept
1. Victim opens a PR list in Desktop for repo `origin`; a malicious/collaborating user has an open PR from fork `github-desktop-attacker` with head `cloneURL = https://github.com/attacker/repo.git`.
2. Victim checks out the PR branch: Desktop adds remote `github-desktop-attacker` pointing at that URL and begins fetching/creating the local tracking branch.
3. Before the local branch's upstream tracking is fully reflected in `GitStore.allBranches` (or before the next `refreshBranches` completes), the attacker renames their fork (or closes/reopens the PR) so that the PR API response no longer reports `cloneURL` matching the remote's stored URL, or `openPRs` temporarily excludes it.
4. The `PullRequestUpdater`'s next poll (within 2 minutes) fires `onPullRequestChanged` → `pruneForkedRemotes`; `findForkedRemotesToPrune` sees the remote matches neither `prRemoteUrls` nor `branchRemotes` and returns it for pruning; `removeRemote` deletes `github-desktop-attacker` from the victim's local git config while the checkout/fetch is still using it.
5. The victim's subsequent fetch/push on the PR branch fails with "remote not found," or silently leaves the branch untracked, breaking their ability to sync work on that branch. [2](#0-1) [3](#0-2) [1](#0-0)

```typescript
export function findForkedRemotesToPrune(
  remotes: readonly IRemote[],
  openPRs: ReadonlyArray<PullRequest>,
  allBranches: readonly Branch[]
) {
  const prRemoteUrls = new Set(
    openPRs.map(pr => pr.head.gitHubRepository.cloneURL)
  )
  const branchRemotes = new Set(
    allBranches.map(branch => branch.upstreamRemoteName)
  )

  return remotes.filter(
    r =>
      r.name.startsWith(ForkedRemotePrefix) &&
      !prRemoteUrls.has(r.url) &&
      !branchRemotes.has(r.name)
  )
}
```
