### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` allows spend-triggered wallet stack exhaustion - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()` and its helper `MofNHint.from_program()` recursively reconstruct a CHIP-0043 custody structure from an on-chain memo without any depth limit. A coin creator (e.g. an offer counterparty, custody co-signer, or any party who can put a hint/memo on a coin sent to the victim's wallet) can craft a deeply nested `MofN` memo that drives Python's call stack past its recursion limit, mirroring the "unbounded recursion on attacker-controlled input" bug class from CVE-2023-43786 (libX11 `PutSubImage()`).

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses a `Program` memo and, when the puzzle is an `MofN`, recurses into itself once per member: [1](#0-0) 

The nesting depth is entirely controlled by the memo's shape (`further_branching_prog`, `puzzle_hint_prog` parsed via `MofNHint.from_program()`): [2](#0-1) 

There is no cap on nesting depth, no iterative rewrite (unlike `sha256_treehash`, which the codebase explicitly made iterative to avoid Python recursion limits, per `chia/types/blockchain_format/tree_hash.py`), and no `sys.setrecursionlimit` guard anywhere in the repo: [3](#0-2) 

This mirrors the same bug class as the `libX11` CVE: an attacker-controlled, self-referential/recursive structure parsed by an unbounded recursive function leads to stack exhaustion and denial-of-service in the consuming process.

The project's own internal documentation confirms `from_memo()` is intended to be driven by untrusted on-chain data during wallet sync ("`from_memo()` must reconstruct unknown members/restrictions, including recursive `MofN`, so later wallet code can fill known puzzle implementations by puzzle hash" / "This is necessary functionality to sync an unknown inner puzzle from on chain."): [4](#0-3) [5](#0-4) 

### Impact Explanation
If a wallet process calls `PuzzleWithRestrictions.from_memo()` on a memo taken from a coin created by another party (offer counterparty, custody co-owner, or any coin sender putting a hint/memo the wallet later parses to recognize an unknown custody puzzle), a maliciously deep `MofN` nesting can raise a Python `RecursionError`, unhandled at the call sites shown in tests, crashing or hanging the wallet's coin-processing/sync path. This is a spend-triggered transaction-processing halt consistent with the validation criteria (denial of service against wallet operation without requiring privileged access).

### Likelihood Explanation
Constructing the malicious memo requires no special privilege: any party can create a coin whose memo/hint is shaped as `(CHIP-0043-namespace, [nonce, restriction_hints, 1, (m, [nested-MofN-memo, ...])])` nested arbitrarily deep, since `MofNHint`/`PuzzleWithRestrictions.memo()` places no limit on nesting when producing memos, and `from_memo()` places no limit on nesting when consuming them. The only prerequisite is that a victim's wallet code path calls `from_memo()` on attacker-supplied program data, which the codebase's own documentation states is the intended flow for recognizing custody puzzles synced from chain.

### Recommendation
Rewrite `PuzzleWithRestrictions.from_memo()` (and `MofNHint.from_program()`/`RestrictionHint.from_program()`) as an iterative parser using an explicit work-stack, following the same pattern used in `sha256_treehash()`, or impose and enforce a strict maximum nesting depth before recursing, raising a controlled `ValueError` instead of allowing unbounded Python-level recursion.

### Proof of Concept
```python
from chia.types.blockchain_format.program import Program
from chia.wallet.puzzles.custody.custody_architecture import PuzzleWithRestrictions

BUNCH_OF_ZEROS = bytes([0] * 32)
ANY_PROGRAM = Program.to(None)

def malicious_mofn_memo(depth: int) -> Program:
    # innermost leaf: an UnknownMember hint
    leaf = Program.to((1, [BUNCH_OF_ZEROS, ANY_PROGRAM]))
    memo = leaf
    for _ in range(depth):
        # wrap in an MofN hint with a single member, forcing recursive from_memo() calls
        memo = Program.to(("CHIP-0043", [0, [], 1, (1, [memo])]))
    return memo

# depth chosen to exceed Python's default recursion limit (~1000)
deep_memo = malicious_mofn_memo(5000)
PuzzleWithRestrictions.from_memo(deep_memo)  # raises RecursionError, crashing the parsing thread/process
```
Note: reachability into a live wallet process depends on which code path in wallet sync/offer processing feeds a network-supplied coin memo into `PuzzleWithRestrictions.from_memo()`; I was unable to locate a production (non-test) call site beyond `custody_architecture.py` itself and one unrelated `.from_memo(` occurrence in `chia/pools/plotnft_drivers.py`, so full end-to-end wiring from an arbitrary untrusted coin to this parser should be verified against the current wallet sync code before treating this as fully confirmed in production.

@dataclass(kw_only=True, frozen=True)
class MofNHint:
    m: int
    member_memos: list[Program]

    def to_program(self) -> Program:
        return Program.to([self.m, self.member_memos])

    @classmethod
    def from_program(cls, prog: Program) -> MofNHint:
        m, member_memos = prog.as_iter()
        return MofNHint(
            m=m.as_int(),
            member_memos=list(member_memos.as_iter()),

        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]

The custody tests exercise `wallet.puzzles.custody.*` as a small composable puzzle framework:

- `PuzzleWithRestrictions.memo()` is the on-chain/exported synchronization contract. `from_memo()` must reconstruct unknown members/restrictions, including recursive `MofN`, so later wallet code can fill known puzzle implementations by puzzle hash.
- `PuzzleWithRestrictions.puzzle_reveal()` layers `INDEX_WRAPPER`, optional restriction layer, and top-level `DELEGATED_PUZZLE_FEEDER`; `puzzle_hash()` uses precalculated hashes to match the reveal without materializing every layer.
- `solve()` must align member validator solutions, delegated-puzzle validator solutions, member solution, and optional delegated puzzle/solution in the exact order expected by the CLVM modules.
- `MofN` rejects impossible thresholds and duplicate member nodes. Its solve format differs across threshold shapes, so tests iterate combinations to catch proof-format regressions.

Concrete member puzzle tests cover BLS-with-taproot, singleton-backed membership, and fixed-puzzle membership. They intentionally check both success and escape paths: invalid hidden puzzle, wrong fixed delegated puzzle, missing singleton approval message, and constructor/solve misuse errors.
