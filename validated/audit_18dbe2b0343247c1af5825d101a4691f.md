### Title
Fee/weight checks in `SignableTransaction::new` are computed before the OP_RETURN output is accounted for, producing transactions that underpay their fee and may exceed the standard weight limit - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the `initiateWithdraw()` finding — where the collateralization check ran before the action that changed the account's collateral — `SignableTransaction::new` computes the transaction's weight, vbytes, required fee, funds sufficiency, and the `MAX_STANDARD_TX_WEIGHT` check from `payments` and `change` only, while the OP_RETURN `data` output pushed into `tx_outs` is never included in any weight/vbytes calculation. The resulting signed transaction is larger than what was checked.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` when `data` is specified: [1](#0-0) 

However, weight/vbytes are computed via `calculate_weight_vbytes(tx_ins.len(), payments, change)`, which builds the measurement transaction from `payments` plus an optional change output — the `data`/`tx_outs` OP_RETURN output is never passed in: [2](#0-1) 

Consequently:
- `needed_fee = fee_per_vbyte * vbytes` and the minimum-relay-fee check at line 211 are evaluated on a transaction missing the data output (up to ~83 bytes of pushdata + ~11 bytes of output overhead ≈ ~25+ extra vbytes unpaid).
- The change branch recalculates with `vbytes_with_change`, still omitting the OP_RETURN output, so `needed_fee` and the change value are computed against the wrong size.
- The final `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight`/`weight_with_change`, also excluding the OP_RETURN output, so a transaction can pass the check yet actually exceed the standardness weight limit. [3](#0-2) 

The checks are thus performed against a state (set of outputs) that is then mutated by the inclusion of the data output — exactly the "check before the action affecting what was checked" ordering bug.

### Impact Explanation
The transaction actually signed pays `input_sat - payment_sat - change` as fee, but that fee was sized for a smaller transaction, so the effective sat/vbyte rate is lower than `fee_per_vbyte` and can fall below `DEFAULT_MIN_RELAY_TX_FEE` — producing a signed, fee-committed transaction that will not relay. Worse, when the true weight exceeds `MAX_STANDARD_TX_WEIGHT` (400,000 WU), the resulting transaction is non-standard and unbroadcastable, yet the FROST signing flow in `TransactionSignMachine::sign`/`complete` will still produce a valid signature for it — signing an unintended, unspendable transaction and burning the inputs' UTXOs from the wallet's perspective until recovery. With many inputs and near-limit payments, the ~94-byte OP_RETURN output is enough to cross the weight boundary undetected.

### Likelihood Explanation
`data` is supplied by callers constructing payments via the Bitcoin network processor (e.g., instructions carrying OP_RETURN payloads). Any signable transaction carrying ≥ ~11 bytes of OP_RETURN data where the fee margin or weight margin is thin triggers the miscalculation. It requires no malicious validator — only a transaction request combining `data` with a size near the boundary or a tight fee rate.

### Recommendation
Include the OP_RETURN output in the size accounting: pass the fully built `tx_outs` (payments + OP_RETURN + change) into `calculate_weight_vbytes`, or add `data.len()` overhead to the measured transaction, before computing `needed_fee`, `NotEnoughFunds`, the change value, and the `MAX_STANDARD_TX_WEIGHT` check — i.e., perform all fee/size checks against the final output set, after all outputs are determined.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), fee_per_vbyte)` with `input_sat == payment_sat + needed_fee` (exactly sufficient).
2. The `NotEnoughFunds` check passes at line 215 because `needed_fee` omits the OP_RETURN output.
3. The returned `SignableTransaction` contains `payments + 1 OP_RETURN` output; its actual fee rate is `needed_fee / actual_vbytes`, lower than `fee_per_vbyte` and potentially below the relay minimum — yet `multisig`/`sign`/`complete` will still produce a fully signed transaction for it.
