### Title
Distribution precompile `rewards()` accepts native SEI value without a non-payable guard, permanently stranding funds at the precompile address - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards()` view method of the distribution precompile (`0x0000000000000000000000000000000000001007`) is dispatched without the `pcommon.ValidateNonPayable` check that every other precompile method enforces, and without any `HandlePaymentUsei`-style refund/consumption logic. A caller that submits an EVM transaction/call to `rewards()` with non-zero `msg.value` will have that value debited from their EVM state balance and (per EVM value-transfer semantics) credited to the precompile's own address, but no code path in `rewards()` ever moves it out again — permanently stranding SEI (usei/wei) at the precompile address, analogous to the WETH/USDC funds getting permanently stuck in `PerpDepository.sol` with no owner-only rescue function.

### Finding Description
In `precompiles/distribution/distribution.go`'s `Execute` dispatcher, most state-mutating methods call `pcommon.ValidateNonPayable(value)` to reject any `msg.value`, and the payable ones (`execute`/`send`-style flows elsewhere) explicitly consume the value via `pcommon.HandlePaymentUsei`, which debits the precompile's Cosmos account and credits the payer back (see the general pattern in `precompiles/common/precompiles.go` `HandlePaymentUsei`). However, the `RewardsMethod` case:
```
case RewardsMethod:
    return p.rewards(ctx, method, args)
``` [1](#0-0) 
does not check `ValidateNonPayable` nor process `value` at all, unlike `WithdrawValidatorCommissionMethod` in the same switch which does: [2](#0-1) 

This is explicitly documented as intentional/known behavior in the integration test suite: [3](#0-2) 
"Guard quirk worth knowing: `rewards()` is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds), so this spec deliberately has no 'view rejects value' test."

Because `rewards` is only a query (it reads `DelegationRewards` and returns them) and never calls `HandlePaymentUsei` or `bankKeeper.SendCoins` to route the attached value back to the caller, any usei/wei sent along with the call is never refunded. In the general EVM/precompile flow, `IsPayablePrecompile` determines whether transfer events are suppressed for a precompile address, and distribution is not in that payable set: [4](#0-3) 
meaning the underlying EVM value transfer to the precompile address still occurs at the StateDB level even though the precompile logic does nothing with it, and the distribution precompile has no owner/anyone-callable withdrawal function to recover such stranded value.

### Impact Explanation
Any funds (usei, expressed as wei value in an EVM call) sent to the distribution precompile via a `rewards()` call are permanently and irrecoverably locked at the precompile's address — there is no function that lets the sender, the protocol, or any address retrieve them. This is a concrete, permanent freezing of user funds triggerable by any unprivileged EVM transaction sender or public JSON-RPC client, matching the accepted-impact criteria (permanent freezing of funds).

### Likelihood Explanation
The bug is reachable by any unprivileged party: any EVM account can construct and submit a transaction (or a smart contract can make a CALL) to the distribution precompile at address `0x...1007` invoking `rewards(...)` with a non-zero `value`. No special privileges, association bypass, or complex preconditions are required beyond simply attaching value to the call, which is trivially possible from any EVM client (e.g., ethers.js `rewards(..., {value: ...})`). The only reason it hasn't been exploited/noticed is because it's a "quirk" acknowledged only in test comments, not guarded in production code.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check at the start of `rewards()` (and any other query-only precompile method that currently omits it) in `precompiles/distribution/distribution.go`, consistent with every other view method in the same file. This prevents value from ever being attached to a call that has no path to consume or refund it, eliminating the fund-stranding vector without requiring a separate rescue function.

### Proof of Concept
1. Associate an EVM account with a Sei address (any funded account).
2. Call the distribution precompile at `0x0000000000000000000000000000000000001007`, encoding `rewards(delegatorAddress, validatorAddress)`, and attach `msg.value = X` (some non-zero usei-equivalent wei amount) either via `eth_call`-backed transaction or a contract `CALL`.
3. Observe: the call succeeds and returns the rewards data (per `Execute`'s `RewardsMethod` case which never validates or consumes `value`), while the sender's EVM balance is debited by `X`.
4. Confirm no method exists on the distribution precompile (or elsewhere) that can transfer that `X` back out of the precompile's address — it remains stranded indefinitely. [5](#0-4) [3](#0-2)
