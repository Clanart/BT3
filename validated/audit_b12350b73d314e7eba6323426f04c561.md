### Title
Stale partial-selection state is silently reapplied to changed file content on `git status` refresh, allowing unreviewed content to be committed - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`FileChange.id` is derived only from `status.kind` and `path`, never from file content or blob OID. `updateChangedFiles()` uses this coarse identity to "preserve" the user's line-level (partial) commit selection across `git status` refreshes. If the underlying content of a tracked file changes between two status polls while its `AppFileStatusKind` and path stay the same, Desktop reuses the old selection object as-is for the new content, without ever re-validating that the selected line indices still correspond to what the user actually reviewed — unless that file happens to be the one currently open in the diff viewer.

### Finding Description
`FileChange`'s identity is computed purely from path/kind, not content: [1](#0-0) 

In `updateChangedFiles`, for every file returned by the new `git status`, if a file with the *same id* existed in the previous state, its existing `selection` (which may be `DiffSelectionType.Partial` with specific line indices selected) is carried over onto the new `WorkingDirectoryFileChange` unconditionally: [2](#0-1) 

The only place that re-validates a partial selection against the *actual current diff* is `updateChangesWorkingDirectoryDiff`, and it does so **only for the single currently-selected/open file**: [3](#0-2) 

Any other file in the working directory that keeps the same `id` (same path, same `AppFileStatusKind`) but whose content changed underneath Desktop (e.g., rewritten by a build tool, pre-commit hook, file watcher, or any process triggered from within the cloned/fetched repository) retains its stale line-based partial selection indefinitely, until the user happens to click into that specific file's diff. `clearPartialState` only clears selection when explicitly requested by specific flows (e.g., after commit) and is not tied to detecting that the diff itself changed: [4](#0-3) 

Since `isIncludedInCommit()`/staging logic is driven purely by `selection.getSelectionType()`/line indices and not by content hashing, a partial selection computed against one version of a file's diff can be silently applied against a structurally different diff for the same path the next time the user commits, without any warning that the reviewed lines no longer correspond to the current content.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": the user believes they have reviewed and selected specific lines for a commit, but Desktop can stage a different set of physical lines than what was actually reviewed, because the identity check (`kind+path`) does not capture content changes. In the worst case, this could cause unintended code to be committed or unreviewed lines to slip into a commit that the user believed only contained the lines they explicitly checked.

### Likelihood Explanation
Exploitation requires a background/automated process to modify a tracked file's content while the app is open and while a user has an outstanding partial line selection on a file they are not currently viewing (e.g. multi-file changesets with build/format scripts, pre-commit hooks, watch tasks — all of which are common developer workflows and can originate from tooling defined inside the cloned repository). No local/admin access beyond what an ordinary developer workflow already grants is required; the only requirement is background file modification of a path already tracked and dirty while Desktop is open.

### Recommendation
Tie selection validity to the actual diff content (e.g. a hash of the diff/hunks or the blob OIDs of the on-disk file vs. what was used to compute the selection) rather than only `status.kind + path`. When `updateChangedFiles` detects that the underlying diff for a file with a `Partial` selection has changed since the selection was captured, the selection should be reset (matching the `clearPartialState` "reset to none" behavior) instead of being blindly carried forward, for every affected file, not just the currently open one.

### Proof of Concept
1. Open a repository with two files, `a.txt` and `b.txt`, both modified.
2. Select `a.txt`, partially select a few lines (`DiffSelectionType.Partial`), then switch to viewing `b.txt` (so `a.txt`'s selection is not currently re-validated).
3. While Desktop is not actively viewing `a.txt`, run a script (e.g. from a pre-commit hook, watch task, or formatter — any process the repo's own tooling can trigger) that rewrites `a.txt` with substantially different content, keeping it tracked/modified.
4. Desktop's next background `getStatus()` call reports `a.txt` still as `Modified`, so `FileChange.id` (`Modified+a.txt`) is unchanged; `updateChangedFiles` reuses the old partial line selection verbatim onto the new `a.txt` content per [2](#0-1) .
5. The user commits without reopening `a.txt`'s diff; the lines actually staged correspond to line indices computed against the old content, not the lines the user actually reviewed in the new content.

export class FileChange {
  /** An ID for the file change. */
  public readonly id: string

  /**
   * @param path The relative path to the file in the repository.
   * @param status The status of the change to the file.
   */
  public constructor(
    public readonly path: string,
    public readonly status: AppFileStatus
  ) {
    if (
      status.kind === AppFileStatusKind.Renamed ||
      status.kind === AppFileStatusKind.Copied
    ) {
      this.id = `${status.kind}+${path}+${status.oldPath}`
    } else {
      this.id = `${status.kind}+${path}`
    }
  }
