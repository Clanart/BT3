This confirms the mechanism: `RuleEngine.evaluate_rules` treats `rule.action == 'block'` as blocking (sets `permissionDecision: deny`), and anything else falls into `warning_rules`, which only sets a `systemMessage` and allows the operation to proceed.### Title
`extract_frontmatter` naive substring split on `---` lets crafted frontmatter downgrade a `block` rule to `warn`, silently disabling PreToolUse/Stop enforcement - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` delimits YAML frontmatter using `content.split('---', 2)`, a raw substring split that is not anchored to line boundaries. If the frontmatter body contains the three-character substring `---` anywhere before the intended closing delimiter (e.g., inside a `pattern:` regex value), the split occurs at the wrong location, pushing the real `action: block` line (and any following lines up to the next `---`) out of the parsed frontmatter dict and into the rendered message body. Since `Rule.from_dict` defaults `action` to `"warn"` when the key is absent, the resulting `Rule` silently becomes non-blocking even though the visible file clearly reads `action: block`.

### Finding Description
`load_rule_file()` → `extract_frontmatter(content)` → `Rule.from_dict(frontmatter, message)` is the parse chain invoked by every hook executor (`pretooluse.py`, `posttooluse.py`, `stop.py`) via `load_rules()`. [1](#0-0) [2](#0-1) 

The frontmatter/body separation logic is:
```python
if not content.startswith('---'):
    return {}, content
parts = content.split('---', 2)
if len(parts) < 3:
    return {}, content
frontmatter_text = parts[1]
message = parts[2].strip()
``` [3](#0-2) 

`str.split('---', 2)` matches the literal substring `---` anywhere in the text, not only on lines that are exactly `---`. A rule author (or an attacker distributing a repository template containing a "safety" rule file) can write a pattern value that itself contains `---`, e.g. `pattern: rm\s+-rf|dd\s+if=---payload`. The second `---` occurrence inside that value is consumed as the closing frontmatter delimiter, so everything after it — including the real `action: block` line and the actual closing `---` — is shoved into `parts[2]`, which becomes the rendered warning message text instead of parsed YAML. `Rule.from_dict` then computes `action=frontmatter.get('action', 'warn')` [4](#0-3) , defaulting to `warn` because the `action` key was never captured.

Downstream, `RuleEngine.evaluate_rules` branches strictly on `rule.action == 'block'`: matching rules with any other action value fall into `warning_rules`, which only emit a `systemMessage` and allow the operation, whereas `blocking_rules` set `permissionDecision: "deny"` (PreToolUse/PostToolUse) or `decision: "block"` (Stop). [5](#0-4)  There is no validation anywhere in `load_rule_file`, `extract_frontmatter`, or `RuleEngine` that flags a frontmatter parse producing an unexpectedly missing/degraded `action` field, and all parse exceptions are swallowed with a warning printed to stderr and the file simply skipped or partially parsed — none of which alerts the user that their intended block rule silently became a warn rule. [6](#0-5) 

### Impact Explanation
This breaks the stated invariant that a deny (`block`) rule must never be parsed into a non-blocking configuration. A repository containing a `.claude/hookify.*.local.md` guard rule that a user believes blocks dangerous `Bash`/`Edit`/`Stop` actions (e.g., blocking `rm -rf`, blocking exfiltration of secrets, or requiring tests before stop) can be crafted so that it visually reads `action: block` yet is parsed by `extract_frontmatter` as `warn`. Combined with other repo content (prompt injection, malicious instructions) that induces Claude to run a dangerous command "since a safety rule will block it if wrong," the operation instead only produces a warning and proceeds, enabling unauthorized command execution, file mutation, or disclosure of code/secrets/diffs to a local or remote sink, matching the "Sensitive code, prompt, token, diff, or local file disclosure" impact category.

### Likelihood Explanation
Exploitation requires only crafting a plain-text markdown rule file with a specific substring placement — no privilege escalation, no admin access, and no changes to the trusted hookify code are needed. Any party who can influence the content of a `.claude/hookify.*.local.md` file that the victim's Claude Code session loads (e.g., a cloned repo/template containing such a file, or a rule generated by following attacker-supplied instructions/pattern text) can trigger this deterministically and repeatably; the bug is a straightforward, always-reproducible parsing defect (naive substring split vs. line-anchored delimiter), not a race condition or timing issue.

### Recommendation
Rewrite `extract_frontmatter` to identify the frontmatter delimiters on a line-by-line basis (e.g., require a line whose stripped content is exactly `---` to open/close frontmatter) rather than doing a raw substring `str.split('---', 2)`. Additionally, prefer using a real YAML parser (`yaml.safe_load`) for the frontmatter block instead of the hand-rolled indentation parser, and add a sanity check in `load_rule_file`/`Rule.from_dict` that rejects or loudly warns (rather than silently defaulting) when a rule's raw file text contains the string `action: block` outside of the parsed frontmatter dict, or more generally when parsed frontmatter keys diverge from what a straightforward YAML parse of the file would produce.
