### Title
Manual conflict resolutions are carried forward by file path across successive rebase steps without content revalidation - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
The external report describes a bug where a state variable (`balances`/`totalSupply`) is not refreshed after an operation (`rebase`), letting a caller keep acting on stale state across repeated calls. The closest Desktop analog is the `manualResolutions: Map<string, ManualConflictResolution>` that is preserved by `updateConflictState` across successive `_loadStatus` calls during a rebase, keyed only by file `path` — with no binding to the specific commit/content that produced the conflict.

### Finding Description
When `continueRebase` is invoked in `app/src/lib/git/rebase.ts:438-538`, it iterates `manualResolutions` and calls `stageManualConflictResolution` (`app/src/lib/git/stage.ts:22-62`), which in turn calls `checkoutConflictedFile(repository, file, resolution)` (`app/src/lib/git/checkout.ts:225-235`), running `git checkout --ours/--theirs -- <path>` purely based on the `path` key. [1](#0-0) [2](#0-1) 

The `manualResolutions` map lives in `ConflictState` and is explicitly preserved across status updates: `updateConflictState` in `app/src/lib/stores/updates/changes-state.ts:263-311` pulls `manualResolutions` forward from `prevConflictState` whenever the new status still reports a rebase in progress, regardless of whether the underlying `REBASE_HEAD` commit ("currentTip"/`rebaseCurrentCommit`) has changed to a different commit in the sequence. [3](#0-2) 

This is confirmed by the unit test `preserves manual resolutions when a rebase is detected`, which shows the same `manualResolutions` map surviving even though `currentTip` changes from `'old-sha'` to `'first-sha'` (i.e., moving to a new commit in the rebase sequence). [4](#0-3) 

**Attacker primitive**: an attacker who controls a cloned/fetched repository can craft a branch history where multiple consecutive commits touch the same file path, each producing a conflict when rebased against the user's branch. If the user resolves the first conflict on `path` with, say, "theirs" (choosing the attacker's content), that same choice is silently reapplied via `checkoutConflictedFile` to the *next* commit's conflict on the same path — which may contain entirely different, attacker-crafted content — without the UI re-prompting the user or the user reviewing that specific hunk.

**Corrupted value**: the `manualResolutions` Map entry for a given `path`, which is treated as durable across distinct conflict instances (distinct commits) instead of being scoped to the specific conflict/content it was chosen for.

**Why existing guards don't stop it**: `stageManualConflictResolution` only checks `isConflictedFileStatus` and whether conflict markers remain (`app/src/lib/git/stage.ts:29-39`) — it has no check that the resolution was made for *this* conflict's content/commit. The staleness-check comment in `applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7241-7256`) demonstrates the team is aware similar staleness issues exist for Copilot resolutions ("If the user resolved this file externally... skip it") but no equivalent guard exists for the manual `checkoutConflictedFile --ours/--theirs` path when moving between rebase steps. [5](#0-4) 

### Impact Explanation
If confirmed exploitable, this would let a malicious repository maintainer/collaborator cause Desktop to silently commit attacker-controlled content into the user's history during a rebase, without the user ever reviewing that specific diff — a silent corruption of what the user commits, matching the "Valid Impact" criteria (attacker-controlled cloned/fetched repository leading to silent corruption of what the user commits).

### Likelihood Explanation
**Uncertain / not fully verified.** I could not retrieve the earlier portion of `changes-state.ts` (lines 1–262, including `performEffectsForRebaseStateChange` and `getConflictState`) before running out of tool budget, so I cannot confirm whether there is an existing guard elsewhere (e.g., clearing `manualResolutions` whenever `rebaseCurrentCommit`/`REBASE_HEAD` sha changes, before `updateConflictState` is invoked) that would prevent this exact scenario. The test I did retrieve only demonstrates preservation across a `currentTip` change, not explicitly across a `REBASE_HEAD` (per-commit) change, so it is not conclusive proof of exploitability — only strong circumstantial evidence.

### Recommendation
- Scope `manualResolutions` entries to the specific conflict instance (e.g., key by `path` + the conflicting blob SHAs or by `REBASE_HEAD` commit SHA) rather than by `path` alone, so a resolution can't be silently replayed against a different commit's conflict.
- In `continueRebase`/`stageManualConflictResolution`, verify that the manual resolution being applied corresponds to the currently conflicted content for that path (similar to the staleness check already present in `applyCopilotConflictResolutions`).
- Clear or re-validate `manualResolutions` whenever `getRebaseInternalState`/`readRebaseHead` reports a different `REBASE_HEAD` commit than the one associated with the stored resolution.

### Proof of Concept
Not independently verified end-to-end due to incomplete file retrieval. Conceptual PoC:
1. Attacker crafts a fork/branch with two consecutive commits, both modifying `shared/file.txt` with different content, designed to conflict with the user's branch at the same path.
2. Victim rebases their branch onto the attacker's branch in Desktop; conflict dialog appears for commit 1 on `shared/file.txt`; user manually selects "theirs".
3. Desktop calls `continueRebase` → conflict resolved, rebase proceeds to commit 2, which also conflicts on `shared/file.txt` with different content.
4. If `manualResolutions` for `shared/file.txt` is still present in `conflictState` (per `updateConflictState`'s preservation logic), `continueRebase` re-applies "theirs" automatically via `checkoutConflictedFile`, silently accepting the attacker's second, unreviewed content into the user's commit.

Given the incomplete verification, I recommend this be validated with a live rebase test (spinning up two conflicting commits on the same path) before treating it as a confirmed vulnerability rather than a strong candidate.

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  if (
    (prevConflictState == null || isRebaseConflictState(prevConflictState)) &&
    (newConflictState == null || isRebaseConflictState(newConflictState))
  ) {
    performEffectsForRebaseStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }
