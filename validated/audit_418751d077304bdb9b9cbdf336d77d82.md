### Malformed FROST nonce commitments can panic Bitcoin transaction signing - ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary

A Bitcoin signing participant can provide nonce commitments that cause the aggregate FROST nonce `R` to be the point at infinity. `TransactionSignMachine::read_preprocess` accepts canonical identity points, `BindingFactor::nonces` sums attacker-controlled commitments into `R`, and the BIP-340 `Hram::hram` implementation panics when `x(R)` is called on infinity. This turns a syntactically valid preprocessing message into a signing-process panic.

### Finding Description

`TransactionSignMachine::read_preprocess` deserializes one FROST preprocess per transaction input using `AlgorithmSignMachine::read_preprocess`. Each preprocess contains attacker-controlled `(D, E)` nonce commitments read through `Secp256k1::read_G`; canonical group encodings are accepted without rejecting the identity point. [1](#0-0) [2](#0-1) [3](#0-2) 

During `AlgorithmSignMachine::sign`, all participants’ commitments are combined into the aggregate nonce commitments. Each participant contributes `D_i + rho_i * E_i` to `R`. [4](#0-3) 

The resulting `R` is passed to `Schnorr::sign_share`, which invokes `Hram::hram` on `nonce_sums[0][0]`. [5](#0-4)  The Bitcoin HRAM converts `R` to an x-coordinate through `x`, whose helper explicitly expects a non-infinity point and calls `expect("point at infinity")`. [6](#0-5) [7](#0-6) 

Thus, if the sum of the bound nonce commitments is identity, transaction signing panics instead of returning `FrostError::InvalidPreprocess`.

### Impact Explanation

An unprivileged signing participant can submit crafted preprocess bytes that terminate the signer’s transaction-signing operation. In a service that does not isolate each signing attempt, this can abort the process or task responsible for threshold Bitcoin signing, repeatedly preventing completion of a requested transaction.

### Likelihood Explanation

The attacker must participate in the signing set and choose commitments that make the aggregate bound nonce identity. Because each participant’s binding factor is transcript-derived from the complete commitment set, constructing the cancellation may require coordinating the attacker’s commitment after learning the other participants’ preprocesses or solving the resulting transcript-dependent relation. The affected input path is nevertheless reachable through `read_preprocess` and `sign`.

### Recommendation

Reject identity nonce commitments in `GeneratorCommitments::read` or reject an identity aggregate nonce before calling `sign_share`. The Bitcoin algorithm should also return a `FrostError::InvalidPreprocess`/verification failure rather than panicking when `R` or the group key is infinity. Add a regression test where a supplied preprocess causes the aggregate `R` to be identity.

### Proof of Concept

Conceptually, for a Secp256k1 `Schnorr` signing machine:

1. Begin a Bitcoin `TransactionSignMachine` signing session.
2. Supply a peer preprocess whose serialized `(D, E)` commitments are selected so that:
   ```text
   Σ_i (D_i + rho_i * E_i) = ProjectivePoint::IDENTITY
   ```
   where `i` ranges over the included participants and `rho_i` is the FROST binding factor calculated by `BindingFactor::calculate_binding_factors`.
3. Call `TransactionSignMachine::sign` with the parsed preprocess map.
4. `BindingFactor::nonces` returns `R = identity`, `Schnorr::sign_share` calls Bitcoin `Hram::hram`, and `x(R)` panics at `expect("point at infinity")`.
