### Title
Incorrect `getRewardablePercentWAD` quadratic/time-weighted formula lets users in cool-down retain full reward weight and manipulate vlMGP reward forfeits - ([File: VLMGP.sol])

### Summary
`VLMGP.getRewardablePercentWAD` is used by `vlMGPBaseRewarder._calExpireForfeit` to determine how much of a user's pending reward should be forfeited based on how much of their vlMGP balance is actively locked vs. in cool-down (unlocking). The formula implemented does not correctly discount reward weight for tokens that are mid-cool-down, and instead reduces weight only *after* the cool-down period has already elapsed, using an inverted time ratio. This diverges from what the forfeit mechanism is supposed to achieve (penalize users who are unlocking) and can be exploited to avoid reward forfeits entirely while a portion of the stake is unlocking. [1](#0-0) 

### Finding Description
`getRewardablePercentWAD` computes a WAD-scaled "rewardable percent" for a user made of two components:

1. The fraction of the user's vlMGP that is still fully locked: `percent = fullyInLock * 1e18 / userTotalVlmgp`.
2. For each cool-down slot:
   - If the cool-down period has **not yet ended** (`block.timestamp <= endTime`), the code adds the **full** weight of that slot's amount, unreduced: `percent += amountInCoolDown * 1e18 / userTotalVlmgp`.
   - If the cool-down period **has already ended** (`block.timestamp > endTime`, i.e., the tokens are already withdrawable and no longer contributing governance/lock power), the code adds a *reduced* weight computed as `amountInCoolDown * 1e18 * (endTime - startTime) / userTotalVlmgp / (timeNow - startTime)`. [2](#0-1) 

This is backwards relative to the evident intent of the forfeit mechanism (mirrored in `vlMGPBaseRewarder._calExpireForfeit`, which forfeits `_amount - _amount * rewardablePercentWAD / 1e18` of pending rewards): a user who is actively in the middle of cool-down (i.e., has taken action to reduce their locked commitment) is treated as if 100% of that slot is still "rewardable," identical to fully-locked tokens, while a user whose cool-down has already finished (and who could withdraw at any time, but hasn't) is penalized with a *decaying* weight the longer they wait to withdraw. This is the opposite of a sensible decay curve — cool-down should reduce reward weight progressively as it happens (as done with `VLMGP.expectedPenaltyAmount`'s explicit quadratic unlock schedule for MGP withdrawal, which does decay smoothly with elapsed time), but `getRewardablePercentWAD` does not apply any equivalent decay while cool-down is in progress. [3](#0-2) 

This closely matches the reported bug class in the Vader `calcAsymmetricShare` finding: the implemented arithmetic for a supposed "decay/weighting" curve does not correctly reflect the intended penalty/decay mathematics, causing miscalculated shares of value (here, reward-forfeit percentage) that a user can exploit.

### Impact Explanation
Because active cool-down amounts are counted at full (unreduced) weight in `getRewardablePercentWAD`, `_calExpireForfeit` in `vlMGPBaseRewarder` (and the analogous `mWOMSVBaseRewarder`, which relies on a different but structurally similar forfeit path) will forfeit less than intended for users who have started unlocking. This lets a user keep earning full boosted rewards on vlMGP even while all/most of their tokens are already scheduled to leave the lock, undermining the reward/forfeit incentive design and allowing unclaimed yield that should have been redirected (forfeited amounts are re-queued as rewards for other stakers via `_queueNewRewardsWithoutTransfer`) to instead be retained by users who are not maintaining a genuine long-term lock commitment. This constitutes theft/misdirection of yield that should accrue to other, genuinely-locked vlMGP holders. [4](#0-3) 

### Likelihood Explanation
Any unprivileged wallet holding vlMGP can trigger this by calling `startUnlock` to place a portion of their MGP into cool-down and then continuing to claim rewards through the normal reward-claim flow while the cool-down slot is active; the mismatch is deterministic and requires no special privileges or race conditions, only normal use of the public `startUnlock`/reward-claim functions. [5](#0-4) 

### Recommendation
Redefine `getRewardablePercentWAD` so that weight for amounts in cool-down decays progressively as the cool-down proceeds (e.g., mirroring the same quadratic/linear decay already used in `expectedPenaltyAmount`), rather than granting full weight during active cool-down and only decaying after the cool-down period has already ended. Clarify the intended forfeit-weighting spec first, then ensure the code matches it and add unit tests comparing expected vs. actual forfeit percentages across various cool-down states.

### Proof of Concept
1. User locks `1000 MGP` into vlMGP, becoming fully locked (`fullyInLock = 1000`).
2. User calls `startUnlock(900)`, moving 900 MGP into a cool-down slot with `startTime = now`, `endTime = now + coolDownInSecs`. Now `fullyInLock = 100`, `inCoolDown = 900`.
3. Immediately (or any time before `endTime`), user claims pending vlMGP-boosted rewards. `getRewardablePercentWAD` returns `(100*1e18/1000) + (900*1e18/1000) = 1e18` (100%) — i.e., **no forfeit at all**, even though 90% of the user's stake is actively being unlocked.
4. Compare to `expectedPenaltyAmount`, which for the same slot at `t=0` would apply a large penalty (only `amountInCoolDown/5` guaranteed, rest ramped quadratically) if the user withdrew MGP directly — showing the reward-forfeit path is inconsistent with the withdrawal-penalty path and is exploitable to retain full reward weight while abandoning lock commitment.         uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

            if (userUnlocking[i].amountInCoolDown > 0) {

                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;

            }
        }

        return percent;
