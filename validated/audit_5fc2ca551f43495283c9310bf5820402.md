## Title
Automatic, unconfirmed remote-URL rewrite based on trusted GitHub API `clone_url` allows silent push/fetch hijacking - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` silently rewrites a repository's `origin` remote URL whenever the GitHub API's `clone_url` for the associated `GitHubRepository` differs from what's currently configured, with **no user confirmation** and **no hostname validation** — only a same-protocol check. This is the same class of bug as the Livepeer `L1Escrow.approve` finding: a normally-trusted, powerful action (rewriting the destination of the user's git operations) is granted without any restriction on *who* that destination can be, so any entity that can influence the trusted data source (here, the `IAPIFullRepository.clone_url` returned by `api.fetchRepository`) can redirect the victim's push/fetch destination.

### Finding Description
`updateRemoteUrl` is invoked from `AppStore.repositoryWithRefreshedGitHubRepository`, which runs during routine background refreshes (e.g. on account change / periodic repo refresh): [1](#0-0) 

Inside `updateRemoteUrl`, the only safety checks performed before overwriting the remote are: (1) the URL protocol (http vs https vs ssh) hasn't changed, and (2) the *previously known* clone URL still matches the current git remote (i.e. the user hasn't manually customized it): [2](#0-1) 

Critically, `protocolsMatch` only compares the URL *scheme* (`https:` vs `https:`), never the hostname or owner/repo path. If the value returned for `apiRepo.clone_url` changes to any other `https://` URL — including one pointing at a completely different host — `gitStore.setRemoteURL(...)` is called immediately and unconditionally, with no dialog or opt-out shown to the user, unlike the analogous "upstream remote differs from expected" flow which explicitly prompts the user via `UpstreamAlreadyExists`: [3](#0-2) 

A closely related, even more direct sibling exists in `GitStore.updateExistingUpstreamRemote`, which sets the `upstream` remote straight from `gitHubRepository.parent.cloneURL` with zero validation of hostname: [4](#0-3) 

Both of these code paths trust the `clone_url`/`parent.clone_url` fields of the `IAPIFullRepository`/`IAPIRepository` API objects (`app/src/lib/api.ts`) as authoritative, without pinning them to the expected host of the account's endpoint. `_upsertGitHubRepository` likewise persists whatever `clone_url` the API returns verbatim into the local database: [5](#0-4) 

### Impact Explanation
If the attacker can influence the `clone_url`/`parent.clone_url` values returned by the API endpoint that Desktop trusts for a given account (e.g. a compromised or malicious GitHub Enterprise Server, a MITM'd/compromised API response, or any other channel that can taint the `IAPIRepository` object consumed here), Desktop will **silently** repoint the user's `origin` (or `upstream`) remote to an attacker-controlled host. Subsequent `git push` operations from that user then send their commits to the attacker's repository instead of the intended one, and subsequent `git fetch`/`pull` operations merge attacker-supplied history into the user's local branches — this is exactly "silent corruption of what the user commits or pushes," one of the explicitly accepted impact categories. Because credential lookup in the trampoline credential helper is keyed off the actual connection hostname (`getCredentialUrl`/`getEndpointKind` in `trampoline-credential-helper.ts`), GitHub.com/GHE tokens are not directly leaked to the new host, but the integrity of the user's git workflow (push/fetch destination) is fully compromised without any visible warning.

### Likelihood Explanation
This path fires automatically as part of routine background repository refresh (`repositoryWithRefreshedGitHubRepository`), not gated behind any explicit user action, and the existing guard (`protocolsMatch`) checks only the URL scheme rather than the host — so it does not stop a same-protocol, different-host redirection. The severity is bounded by the precondition that the attacker must be able to influence the trusted API's `clone_url` field for the relevant account/endpoint (e.g., via a malicious/compromised GitHub Enterprise instance), matching the report's own caveat that even a "well intended" but overly-permissive trusted actor creates reputational/rug risk.

### Recommendation
Restrict `updateRemoteUrl` (and `updateExistingUpstreamRemote`) so the new `clone_url` must match the same hostname/owner as previously known for that `GitHubRepository`'s endpoint before silently updating the remote; otherwise require explicit user confirmation, the same way `UpstreamAlreadyExists` already prompts users when the upstream remote doesn't match the expected parent URL. At minimum, compare hostnames (not just protocol) before auto-rewriting either remote.

### Proof of Concept
1. User has `Repository X` with GitHub repository record whose stored `cloneURL` is `https://github.com/owner/repo.git`, and local `origin` remote is exactly that URL (satisfies `remoteUrlUnchanged`).
2. The account's configured API endpoint (e.g. a GHE instance, or an intercepted/compromised `api.github.com` response) returns an `IAPIFullRepository` for `owner/repo` with `clone_url: "https://evil.example.com/owner/repo.git"`.
3. `AppStore.repositoryWithRefreshedGitHubRepository` runs (e.g. via `refreshSelectedRepositoryAfterAccountChange`), calling `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`.
4. `protocolsMatch` is `true` (both `https:`), `remoteUrlUnchanged` is `true`, `urlsMatch` is `false` → `gitStore.setRemoteURL('origin', 'https://evil.example.com/owner/repo.git')` executes with no user prompt.
5. The next `git push`/`git fetch` from Desktop silently targets `evil.example.com` instead of `github.com`. [6](#0-5)

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
