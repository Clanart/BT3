### Title
Malformed offer solution causes unhandled `TypeError` crash in `Offer.from_spend_bundle` — ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.from_spend_bundle()` parses attacker-supplied offer bytes (from `Offer.from_bech32`/`Offer.from_bytes`, reachable via `take_offer`, offer-summary/examine flows, and Data Layer offer verification) and blindly assumes the first element of each notarized-payment group is an atom. A crafted offer whose "requested payment" solution places a cons-pair (rather than an atom) as the nonce field causes `Program.as_atom()` to return `None`, which is then fed into `bytes32(None)`, raising an unhandled `TypeError` that propagates out of the parsing call — mirroring the GNU patch bug class where a malformed structural assumption (consecutive/absent markers) is not validated before being dereferenced, leading to a crash during processing of attacker-controlled input.

### Finding Description
When any wallet user (or Data Layer client) loads or examines an offer, the code path is:
`Offer.from_bech32` → `Offer.from_bytes` → `Offer.from_spend_bundle`. [1](#0-0) 

```
if coin_spend.coin.parent_coin_info == bytes32.zeros:
    notarized_payments: list[NotarizedPayment] = []
    for payment_group in Program.from_serialized(coin_spend.solution).as_iter():
        nonce = bytes32(payment_group.first().as_atom())
        ...
```

`payment_group.first()` is taken directly from the attacker-controlled `coin_spend.solution` CLVM program with no validation that it is an atom of the correct length. If it is a pair (list) instead of an atom, `Program.as_atom()` returns `None` (this mirrors the pattern seen elsewhere in the codebase, e.g. `chia/consensus/condition_tools.py` `parse_sexp_to_condition`, which explicitly checks `if a is None: break` before use — a check that is missing here). Passing `None` into `bytes32(...)` raises an unhandled `TypeError`, which is not caught anywhere in `from_spend_bundle`, `from_bytes`, or `from_bech32`.

By contrast, the `Offer.conditions()` property (used elsewhere in the same class) wraps similar per-coin-spend parsing in a `try/except Exception: continue` guard, showing the developers are aware such untrusted-data parsing can throw — but this protection was not applied to `from_spend_bundle`.

### Impact Explanation
Any counterparty offer file (shared as a bech32 string or raw bytes, as offers commonly are) can be crafted so that a benign-looking `chia wallet take_offer`, `get_offer_summary`, `examine_only` preview, or Data Layer `verify_offer`/`make_offer` call raises an unhandled exception the moment the offer is decoded — before any signature or puzzle-hash validation occurs. This is a crash-on-parse condition triggered purely by structuring the CLVM solution of a spend bundle, directly analogous to the reported GNU patch NULL-pointer dereference where malformed structural input corrupts an assumed-valid data field and crashes processing before any legitimate use of the data. Depending on how the calling context handles unexpected exceptions (RPC endpoint vs. bare asyncio task), this can fail the offer-processing request or, in less-guarded call paths, propagate further and disrupt wallet transaction-processing flow.

### Likelihood Explanation
High likelihood: constructing an offer with a solution whose payment-group "nonce" position holds a cons pair instead of a 32-byte atom requires no cryptographic material and no special privileges — any offer counterparty or file distributor can produce and share such a file, and the crash triggers on the very first parse (`Offer.from_bech32`/`from_bytes`), before signature checks.

### Recommendation
In `Offer.from_spend_bundle`, validate that `payment_group.first().as_atom()` returns a non-`None` 32-byte value before constructing `bytes32`, and raise a caught `ValueError`/offer-specific exception (consistent with the guarding pattern already used in `Offer.conditions()`) instead of allowing an unguarded `TypeError` to propagate. Apply the same defensive check to `NotarizedPayment.from_condition_and_nonce` and any other place that trusts the shape of attacker-supplied CLVM solutions inside offer files.

### Proof of Concept
1. Construct a `CoinSpend` with `coin.parent_coin_info == bytes32.zeros` (the offer "dummy" marker) and a `solution` program whose payment group is `((<cons-pair> <amount> <puzhash>))` instead of `((<32-byte-atom> <amount> <puzhash>))`, e.g. serialize `Program.to([[Program.to((1,2)), 1, bytes32.zeros]])` as the solution.
2. Wrap it in a `WalletSpendBundle` and serialize with `bytes(offer)`/`to_bech32()`.
3. Have a victim call `Offer.from_bech32(offer_str)` (e.g. via `chia wallet take_offer` or the `take_offer`/`get_offer_summary` RPC, or Data Layer `verify_offer`).
4. Observe `payment_group.first().as_atom()` returns `None`, and `bytes32(None)` raises `TypeError`, aborting offer parsing before any further validation.
