### Malformed FROST preprocess can panic Bitcoin transaction signing via an identity aggregate nonce - (File: networks/bitcoin/src/crypto.rs)

### Summary

`TransactionSignMachine::read_preprocess` accepts a vector of per-input FROST preprocesses from untrusted signing participants. `AlgorithmSignMachine::sign` converts those preprocesses into aggregate nonce points without rejecting an aggregate identity result. Bitcoin’s BIP-340 challenge implementation then unconditionally encodes that point with `x`, which panics on the point at infinity. A participant able to supply preprocess bytes can therefore crash a signing process instead of producing a `FrostError`.

### Finding Description

`TransactionSignMachine::read_preprocess` delegates directly to every per-input `AlgorithmSignMachine::read_preprocess`, making each preprocess part of attacker-controlled protocol input. [1](#0-0) 

Each preprocess’s commitment points are decoded with `Curve::read_G`, which rejects an identity point only at the individual encoding layer. [2](#0-1)  After parsing, `AlgorithmSignMachine::sign` computes binding factors and calls `BindingFactor::nonces` to combine all participant commitments. [3](#0-2)  `BindingFactor::nonces` sums `D` and each binding-factor-weighted `E`, but never checks whether the resulting aggregate nonce is identity. [4](#0-3) 

For Bitcoin’s `Schnorr` algorithm, `sign_share` immediately invokes `Hram::hram` on `nonce_sums[0][0]`. [5](#0-4)  The Bitcoin `Hram` calls `x(R)`, and `x` panics when asked for the x-coordinate of the point at infinity. [6](#0-5) [7](#0-6) 

Thus validation rejects identity only for each serialized commitment point, not for the algebraic aggregate produced from those non-identity points.

### Impact Explanation

This is a remotely reachable denial of service against transaction signing. A signing participant can provide syntactically valid preprocess bytes whose resulting aggregate nonce is the identity. When the victim reaches `TransactionSignMachine::sign`, the panic in `x` terminates the operation rather than returning an attributable `FrostError`. In a process that does not isolate signing state machines, this crashes the signer; in a retrying coordinator/cosigner path, repeated malicious preprocesses can repeatedly prevent transaction completion.

The impact matches the bug class suggested by CVE-2020-2686: attacker-controlled protocol input reaches an unchecked edge case in cryptographic processing and causes a repeatable crash/availability failure.

### Likelihood Explanation

Likelihood depends on whether an attacker can influence the signing quorum and supply a preprocess. Any quorum participant reaches `read_preprocess` with bytes they control. The individual points must merely be canonical non-identity points, so the usual malformed-encoding defenses do not stop this condition. The attack requires arranging the binding-factor-weighted commitment sum to equal identity, but there is no protocol-level check preventing that state from being constructed or explicitly detecting it before BIP-340 challenge generation.

The issue is more reachable for Bitcoin transaction signing than for algorithms whose challenge function can encode the identity without panicking.

### Recommendation

Reject non-viable nonce commitments and aggregate nonces before invoking `Hram`.

At minimum:

- In `BindingFactor::nonces`, return a `Result` and reject any aggregate nonce that `is_identity`.
- In `BindingFactor::bound`, reject each participant’s bound nonce if it is identity, so invalid preprocesses can be attributed to a participant.
- Convert `Algorithm::sign_share` or `Hram` usage to return an error instead of panicking when `R` is invalid.
- Add a regression test using valid canonical non-identity secp256k1 points that produce an identity aggregate and assert that `sign` returns `FrostError::InvalidPreprocess`, rather than panicking.

### Proof of Concept

Conceptually, for a 2-of-2 Bitcoin transaction signing session:

```rust
use frost::{
  Participant,
  curve::Secp256k1,
  sign::{PreprocessMachine, SignMachine},
};

// victim_machine and victim_preprocess are produced normally.
let (victim_machine, victim_preprocess) =
    AlgorithmMachine::new(Schnorr::new(), victim_keys).preprocess(&mut rng);

// Attacker supplies a serialized preprocess whose commitments decode to canonical,
// non-identity points, but whose bound aggregate contribution makes:
//
//   victim_bound_nonce + attacker_bound_nonce == identity
//
// The encoding itself therefore passes Curve::read_G.
let malicious_preprocess =
    victim_machine.read_preprocess(&mut malicious_bytes.as_slice()).unwrap();

let mut preprocesses = HashMap::new();
preprocesses.insert(Participant::new(2).unwrap(), malicious_preprocess);

// Panics inside Hram::hram -> x(R) when R is identity instead of returning
// FrostError::InvalidPreprocess.
let _ = victim_machine.sign(preprocesses, &sighash);
```

The decisive crash path is:

```text
TransactionSignMachine::read_preprocess
  -> AlgorithmSignMachine::sign
    -> BindingFactor::nonces
    -> Schnorr::sign_share
    -> Hram::hram(R = identity)
    -> x(R)
    -> panic!("point at infinity")
```
