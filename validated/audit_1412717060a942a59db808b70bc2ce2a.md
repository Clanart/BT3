Based on the investigation, the closest verifiable local analog to the `feeBips` validation gap is a discrepancy between the two `IntentGatewayV2` implementations in this repo: the canonical EVM contract validates governance-supplied basis-point fee values before persisting them, but the Tron variant does not.

### Title
Missing bounds validation on `protocolFeeBps`/`destinationFeeBps` in Tron `IntentGatewayV2.onAccept` UpdateParams path permanently bricks `placeOrder` via arithmetic underflow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder()` computes `protocolFee = (amount * protocolFeeBps) / 10_000` and then `reducedAmount = amount - protocolFee`. This subtraction is only safe if `protocolFeeBps < 10_000` (and equivalently for any per-destination override). The canonical EVM implementation enforces this invariant on every parameter update via `_validateParams`/`_updateParams` in `IntentsBase.sol`, which reverts if `protocolFeeBps >= 10_000` or a `destinationFeeBps >= 10_000`. The Tron port of the same contract applies `UpdateParams` messages directly with no such check.

### Finding Description
In `evm/src/apps/intentsv2/IntentsBase.sol`, `_updateParams` calls `_validateParams(update.params)` and additionally validates each destination override: [1](#0-0) 
`_validateParams` explicitly bounds `surplusShareBps <= 10_000` and `protocolFeeBps < 10_000`: [2](#0-1) 

In contrast, `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `onAccept` handles `RequestKind.UpdateParams` by writing `_params` and `_destinationProtocolFees` directly, with no call to any validation function: [3](#0-2) 

Because `placeOrder` on the Tron contract performs the exact same unchecked-arithmetic fee reduction as the audited path: [4](#0-3) 
any `protocolFeeBps` (global or per-destination) value `>= 10_000` makes `protocolFee >= originalAmount` for every order input, so `originalAmount - protocolFee` underflows and reverts under Solidity 0.8 checked arithmetic — for **every** `placeOrder` call to that destination, not just a single malicious order.

This is the same broken invariant as the `OracleLess.createOrder()` M-5 finding — a basis-points fee parameter with an implicit "must be < 10000" invariant that is enforced in some code paths but not others, and whose violation causes systemic transaction reversion rather than a contained per-order failure.

### Impact Explanation
Unlike the original OracleLess bug (a single attacker-created bad order clogging a queue), this analog is more severe in blast radius on the affected chain: once an out-of-bounds `protocolFeeBps`/`destinationFeeBps` value is stored, **all** future `placeOrder` calls to the affected destination on the Tron deployment revert, permanently denying new order placement (a protocol-wide DoS on that lane) until governance issues a corrective `UpdateParams`. Funds already escrowed prior to the bad update are not directly stolen, but the gateway becomes unusable, which matches the bounty's "unauthorized... transaction manipulation / logic attacks" category via false-invariant acceptance in state that should have been rejected.

### Likelihood Explanation
This path is only reachable via a `PostRequest` from Hyperbridge (source must equal `IDispatcher(host()).hyperbridge()`), not from an arbitrary unprivileged EOA: [5](#0-4) 
So triggering it requires the Hyperbridge coprocessor/governance to dispatch a malformed or miscalculated `ParamsUpdate` (e.g., a units/percentage mismatch bug in the intents-coprocessor pallet, or human error), which the EVM contract explicitly defends against via `_validateParams` but the Tron contract does not. This is a real, low-effort-to-fix gap and an inconsistency between two supposedly equivalent contracts in the same repo, but it is governance/pallet-input-driven rather than exploitable by a fully unprivileged attacker — this materially weakens confidence that it meets the "unprivileged attacker" bar strictly required by the Impact Gate.

### Recommendation
Add the same bounds checks used in `IntentsBase._validateParams`/`_updateParams` to the Tron `IntentGatewayV2.onAccept` `UpdateParams` branch: reject `params.surplusShareBps > 10_000`, `params.protocolFeeBps >= 10_000`, and any `destinationFees[i].destinationFeeBps >= 10_000` before writing to storage.

### Proof of Concept
1. Hyperbridge coprocessor (or a bug in it) dispatches a `PostRequest` with `body = RequestKind.UpdateParams || abi.encode(ParamsUpdate{params: {..., protocolFeeBps: 10000, ...}, destinationFees: []})` to the Tron `IntentGatewayV2`.
2. `onAccept` stores `_params.protocolFeeBps = 10000` with no validation (`evm/tron/contracts/apps/IntentGatewayV2.sol:635-651`).
3. Any user calls `placeOrder` with a non-zero-fee destination; inside the loop `protocolFee = (originalAmount * 10000) / 10000 = originalAmount`, then `reducedAmount = originalAmount - protocolFee = 0`... for `protocolFeeBps > 10000` the subtraction underflows and reverts, permanently blocking `placeOrder` for that destination.

**Caveat:** I could not fully verify within the available iterations whether the Tron gateway's `onAccept` truly lacks *all* paths to `_validateParams` (e.g., whether `initialize`/`setParams` calls elsewhere still perform validation, limiting exposure to only the cross-chain `UpdateParams` message path) — this is based on the code shown in `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 620-660 and should be confirmed against the full file if pursuing this further, since indexing limits may have truncated additional guard logic elsewhere in the contract.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }

            authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return withdraw(body, kind == RequestKind.RefundEscrow);

        // only hyperbridge is permitted to perfom these actions

            NewDeployment memory body = abi.decode(incoming.request.body[1:], (NewDeployment));
            _instances[keccak256(body.stateMachineId)] = body.gateway;

                    ++i;
