## Analysis

The Nouns `forkPeriod`/`forkThresholdBPS` bug is a governance-set-parameter-to-zero pattern: an authorized party can push a critical timing parameter to `0` (no `MIN_FORK_PERIOD` enforced), silently disabling a safety window that other participants rely on. The direct Hyperbridge analog is the **`challengePeriod`** host parameter, which gates when a submitted state commitment can be trusted for proof verification. [1](#0-0) 

`updateHostParamsInternal` validates `hostManager`, `handler`, `consensusClient`, `hyperbridge` id, `stateMachines` length, and enforces a **minimum of 1 day for `unStakingPeriod`** — but performs **no minimum/maximum bound check on `challengePeriod`**, which is copied straight into storage: [2](#0-1) 

On the Substrate side, `verify_delay_passed` treats a zero challenge period as an automatic pass, entirely bypassing the delay: [3](#0-2) 

### Title
Cross-chain governance can zero out `challengePeriod` to bypass the state-commitment dispute window and force acceptance of unchallenged state - (File: evm/src/core/EvmHost.sol, modules/ismp/core/src/handlers.rs)

### Summary
`updateHostParamsInternal` (and the mirrored Rust `EvmHostParam::update`) allow `challengePeriod` to be set to any value, including `0`, with no `MIN_CHALLENGE_PERIOD` enforced (unlike `unStakingPeriod`, which has an explicit `1 days` floor). `verify_delay_passed` in `modules/ismp/core/src/handlers.rs` treats `delay_period.as_secs() == 0` as "delay already elapsed," so a zeroed `challengePeriod` removes the entire window during which state commitments could be disputed/frozen before being relied upon by `validate_state_machine`. [4](#0-3) 

### Finding Description
The challenge period exists specifically to give the system time to detect and freeze a fraudulent consensus/state update before it is used to authorize requests, responses, or timeouts — this is the Hyperbridge equivalent of the fork-escrow window in the Nouns report. `HostParams.challengePeriod` is updated only through `updateHostParams`, which is restricted to the `hostManager` contract (i.e., cross-chain governance messages relayed from the Hyperbridge parachain via `HostManager.onAccept` -> `OnAcceptActions.SetHostParam`): [5](#0-4)  and on `EvmHost` itself: [6](#0-5) 

`updateHostParamsInternal` explicitly guards `unStakingPeriod` with `if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();` but has no equivalent guard for `challengePeriod` before it's written to `_hostParams.challengePeriod`. Once set to `0`, `verify_delay_passed` (used by `validate_state_machine`, which gates request/response/timeout processing) unconditionally returns `true` for that state machine, meaning any newly-submitted state commitment is immediately treated as final and safe to build proofs against — with no window left for fishermen/operators to observe and veto it.

### Impact Explanation
This maps directly onto the "Impacts" gate: it enables **false state/proof acceptance** — a state commitment can be accepted and immediately relied upon for message verification with zero delay, eliminating the intended fraud-detection window before Merkle/state proofs derived from that commitment are trusted for dispatching requests/responses on the destination. Because `challengePeriod` is a shared host parameter, this affects every request/response/timeout routed through that host, not a single user, making the blast radius broad (loss of the core safety guarantee "false remote state must never become trusted").

### Likelihood Explanation
The path requires the parameter-update flow to be triggered with `challengePeriod = 0`, which is only reachable via the authorized `hostManager` cross-chain governance channel — this is analogous to the "malicious majority" DAO actor in the seed report (a legitimate authorized governance path being misused/misconfigured), not a compromised relayer, prover, or leaked key. There is no local input validation stopping this specific value from being set, so the only barrier is off-chain review of the governance payload, exactly the gap the original Nouns report criticizes ("unless there is an automated impact review... such proposals... pose non-negligible risk").

### Recommendation
1. Enforce a `MIN_CHALLENGE_PERIOD` (and reasonable max) in `updateHostParamsInternal`, mirroring the existing `unStakingPeriod` check, e.g. `if (params.challengePeriod < MIN_CHALLENGE_PERIOD) revert InvalidChallengePeriod();`.
2. Apply the same lower-bound validation in the Rust `EvmHostParam::update`/`HostParam` pallet path so Substrate-side hosts can't be configured with a zero challenge period either.
3. Consider rejecting decreases to `challengePeriod` for state machines with commitments still inside their existing challenge window, analogous to preventing `forkPeriod` decreases during escrow.

### Proof of Concept
1. Cross-chain governance (via the Hyperbridge parachain) sends a `SetHostParam` post request with `HostParams.challengePeriod = 0` to `HostManager.onAccept`, which calls `IHostManager(_params.host).updateHostParams(hostParams)`.
2. `updateHostParamsInternal` passes all existing checks (no check exists for `challengePeriod`) and stores `_hostParams.challengePeriod = 0`. [2](#0-1) 
3. A new/malicious state commitment is submitted for that state machine.
4. Any subsequent request/response/timeout handling calls `validate_state_machine` -> `verify_delay_passed`, which returns `true` immediately because `delay_period.as_secs() == 0`, skipping the intended dispute window entirely. [7](#0-6) 

Note: I was not able to fully trace the EVM-side (`HandlerV2.sol`) challenge-period check function body within the tool-call budget (only confirmed via `grep_search` that it references `challengePeriod`/timestamp arithmetic), so I cannot state with certainty whether the Solidity handler has an equivalent independent minimum-period safeguard that the Rust path lacks; this would need direct inspection of `HandlerV2.sol`'s delay-check logic to fully close out cross-chain parity of this analog.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
