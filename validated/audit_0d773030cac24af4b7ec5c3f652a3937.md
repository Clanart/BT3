Based on the evidence gathered, I found a concrete local analog in the Hyperbridge intents settlement paths (`IntentsBase.sol` / `ExtrinsicIntents.sol` / `IntentGatewayV2.sol`), which mirror the exact "push-transfer to unchecked recipient blocks execution" pattern from the external report.

### Title
Push-based escrow withdrawal loops permanently lock order funds if any token/beneficiary transfer reverts (blacklist/reverting recipient) - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()` and its Tron counterpart `IntentGatewayV2.withdraw()` release escrowed order funds to a fixed `beneficiary` address using a **push** model inside a `for` loop over all escrowed tokens, with no `try/catch` isolation per token. If any single token transfer to `beneficiary` reverts — for example because `beneficiary` is blacklisted by a stablecoin like USDT/USDC, or is a smart-contract wallet whose `receive()`/fallback reverts — the entire withdrawal reverts, and because this function is invoked from the cross-chain `onGetResponse`/`onAccept` callback path, the failure is "retriable" by the host but will deterministically fail forever, permanently locking all escrowed inputs and fees for that order commitment.

### Finding Description
`_withdraw` in `IntentsBase.sol` iterates escrowed tokens and pushes funds directly to `beneficiary`: [1](#0-0) 
and forwards accumulated fees the same way: [2](#0-1) 

The Tron `IntentGatewayV2.withdraw()` has the identical unguarded loop pattern, reverting the whole function (`revert TransferFailed()`) if any single token push fails: [3](#0-2) 

This function is reached from the `onGetResponse` callback that the `EvmHost` invokes after verifying a cross-chain state proof (cancellation/refund flow) or from a fill/redeem flow. Crucially, `EvmHost.dispatchIncoming(GetResponse)` treats a reverting app callback as "retriable" and simply deletes the receipt so it can be resubmitted: [4](#0-3) 

But retrying does not help here: `beneficiary` is derived from immutable order data (`order.user` for refunds, or the filler/`msg.sender` for fills) baked into the commitment, so every retry hits the exact same reverting transfer. There is no pull-based fallback and no `try/catch` around any per-token transfer, so one non-transferable output blocks release of *all* other escrowed tokens and the fee balance for that order, exactly mirroring the `FeeHandler.handleFee()` bug class (single failing recipient blocking the whole batched transfer and blocking retries indefinitely).

### Impact Explanation
An order whose beneficiary/user address becomes blacklisted by an ERC-20 stablecoin used as an input/output/fee token (or is a contract with a reverting `receive()`), the escrowed funds for that commitment become permanently unrecoverable — the withdrawal can never succeed since the beneficiary is immutable and there is no alternate claim path (no pull/withdraw-by-owner override). This is a direct fund-lock impact under the "stealing or loss of funds" / bridged-asset-must-move-exactly-once category.

### Likelihood Explanation
No malicious relayer, prover, or admin is required — any ordinary user (or counterparty they interact with) whose address is later blacklisted by a stablecoin issuer, or who supplies a beneficiary/session contract with a reverting fallback, will trigger this permanently. Stablecoin blacklisting is a real, externally-triggerable event outside the protocol's control, making this readily reachable in production without any privileged actor.

### Recommendation
Replace the push model in `_withdraw` (`IntentsBase.sol`) and `withdraw` (`IntentGatewayV2.sol`, Tron) with a pull-based claim pattern, or wrap each token transfer in the loop with a low-level call whose failure credits an internal claimable balance instead of reverting the whole batch — so a single non-transferable token/beneficiary cannot block release of the remaining escrowed assets.

### Proof of Concept
1. User places a cross-chain intent order with `order.user` = address `A` (or a filler fills with `beneficiary` = `A`), escrowing USDC + another ERC-20 + protocol fee tokens.
2. Before settlement/cancellation completes, `A` is added to USDC's blacklist (e.g., via Circle/Tether compliance action) — a routine, externally-triggered event, no protocol compromise needed.
3. Cancellation via `_cancelFromDest`/GET-proof path invokes `IntentsBase._withdraw(body, isRefund=true, finalize=true)`, which loops through `body.tokens` and calls `IERC20(USDC).safeTransfer(A, amount)` per [5](#0-4) ; this reverts because `A` is blacklisted.
4. The revert propagates up through the `onGetResponse` callback to `EvmHost.dispatchIncoming(GetResponse)`, which only deletes the receipt for a retry per [6](#0-5)  — any resubmission of the same proof hits the identical revert.
5. All escrowed tokens (including the non-blacklisted ones and fees) for that commitment remain locked in the gateway forever, with no alternate recovery path.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

                if (!sent) revert InsufficientNativeToken();

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
