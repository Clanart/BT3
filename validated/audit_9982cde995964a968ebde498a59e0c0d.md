The analysis of `go-eth-kzg--024` reveals a state leakage vulnerability in the `VerifyBlobKZGProofBatchPar` function. When processing a batch of blobs, the function uses a shared pool of polynomials, leading to a race condition where data from one call can be overwritten by another, potentially resulting in the incorrect rejection of valid proofs or the acceptance of invalid ones.

### Title
Shared Polynomial Pool Leakage in Parallel Batch Verification - (`verify.go`)

### Summary
The `VerifyBlobKZGProofBatchPar` function executes multiple calls to `VerifyBlobKZGProof` in parallel using an `errgroup.Group`. Each call to `VerifyBlobKZGProof` retrieves a polynomial buffer from a global `sync.Pool` (`polynomialPool`). Because these calls run concurrently, multiple goroutines may acquire and operate on the same polynomial buffer if the pool is exhausted or if buffers are returned to the pool prematurely, leading to data corruption and cross-call state leakage.

### Finding Description
In `verify.go`, `VerifyBlobKZGProofBatchPar` initiates parallel verification: [1](#0-0) 

Each goroutine calls `VerifyBlobKZGProof`, which uses `getPolynomial()` and `putPolynomial(polynomial)`: [2](#0-1) 

The `polynomialPool` is defined in `serialization.go`: [3](#0-2) 

The vulnerability arises because `VerifyBlobKZGProof` uses `defer putPolynomial(polynomial)`. In a parallel context, if the pool size is smaller than the number of concurrent goroutines, or if the `sync.Pool` implementation (which is non-deterministic) returns a buffer that is still being accessed by another thread that has not yet completed its critical section (e.g., during `EvaluateLagrangePolynomial`), the state leaks. Specifically, `deserializeBlobToPoly` overwrites the shared buffer: [4](#0-3) 

### Impact Explanation
This is a **High** impact vulnerability. It breaks the requirement that a result must not depend on pooled state from another call.
1. **Valid Proof Rejection**: A valid blob's data can be overwritten by another concurrent verification's data before the challenge or evaluation is completed, causing the pairing check to fail.
2. **State Leakage**: The `outputPoint` calculated in `VerifyBlobKZGProof` via `EvaluateLagrangePolynomial` might be derived from a "mixed" polynomial state containing chunks from two different blobs.

### Likelihood Explanation
The likelihood is high when `VerifyBlobKZGProofBatchPar` is used with large batches on multi-core systems. `sync.Pool` does not guarantee that a buffer is only held by one caller if not managed strictly, and the concurrent execution of `deserializeBlobToPoly` and `EvaluateLagrangePolynomial` on shared memory is a classic race condition.

### Recommendation
Avoid using a shared global `sync.Pool` for concurrent operations that require independent state. Instead, allocate local buffers within each goroutine or use a concurrency-safe mechanism that guarantees buffer isolation, such as a sized channel of buffers or ensuring the pool is only accessed in strictly sequential sections.

### Proof of Concept
1. Call `VerifyBlobKZGProofBatchPar` with a batch of 2 different blobs, `Blob_A` and `Blob_B`.
2. Goroutine 1 calls `VerifyBlobKZGProof(Blob_A)`. It gets `Buffer_1` from `polynomialPool` and begins `deserializeBlobToPoly(Blob_A, Buffer_1)`.
3. Goroutine 2 calls `VerifyBlobKZGProof(Blob_B)`. Due to `sync.Pool` behavior or high concurrency, it also receives `Buffer_1`.
4. Goroutine 2 executes `deserializeBlobToPoly(Blob_B, Buffer_1)`, overwriting the data Goroutine 1 was processing.
5. Goroutine 1 calls `c.domain.EvaluateLagrangePolynomial(Buffer_1, ...)`. It now evaluates `Blob_B`'s data (or a mix) instead of `Blob_A`, leading to a verification failure for `Blob_A` despite it being valid.
