## Title
Malicious merge content can make Copilot's conflict-resolution reassembly mis-detect a conflict block's boundary, silently committing leftover conflict-marker debris and dropped code - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot "resolve conflicts" feature extracts conflict hunks from a conflicted file (`extractConflictHunks`), sends them to an LLM, and then splices the model's per-hunk output back into the *original on-disk content* by re-scanning for marker lines (`reassembleResolvedFile`). Both the extraction pass and the reassembly pass locate a conflict block's boundaries independently, using the same lightweight, non-nesting-aware marker regexes. Content coming from an attacker-controlled branch (the "theirs" side of a merge/rebase/cherry-pick, e.g. a malicious PR the user merges) can contain conflict-marker-*looking* lines embedded inside the real conflict's ours/theirs text. Both scanners latch onto the first embedded `>>>>>>>`-looking line as the "closing marker" instead of the real one, so the true trailing `=======`/`>>>>>>>` markers and the real trailing content are left outside the detected hunk and are copied through verbatim by `reassembleResolvedFile`. The result is written to disk and `git add`-ed without any check that the reassembled file no longer contains conflict-marker debris.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks a conflicted file collecting "ours" content until it sees a base or `=======` separator marker, then collects "theirs" content until it sees a `>>>>>>>` marker: [1](#0-0) [2](#0-1) 

Note that while collecting "ours" content, only `baseMarker`/`separatorMarker` terminate the loop - a stray `<<<<<<<`-looking line is simply pushed as ordinary text. Likewise, while collecting "theirs" content, only a `theirsMarker` line terminates the loop.

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) independently re-derives the conflict block boundary from the same raw content when splicing the model's resolution back in: [3](#0-2) 

It scans forward from a `<<<<<<<` line and stops at the *first* line matching `>>>>>>>`, tracking only whether a `=======` was seen anywhere in between - it has no concept of nested/embedded fake markers either.

Because both passes use the same "first closing marker wins" logic, a crafted "theirs" branch content that embeds a complete fake `<<<<<<< / ======= / >>>>>>>` triple *inside* the real conflict's ours/theirs text causes both the extraction and the reassembly to agree on a *truncated* hunk boundary that ends at the fake closing marker rather than the real one. The real trailing `=======` and `>>>>>>> branch` lines, along with whatever "theirs" content genuinely followed them, fall outside the detected hunk and are then copied through unchanged by the reassembly's default line-copy path: [4](#0-3) 

The only marker-related validation in the pipeline checks a *single hunk's* model-provided `resolvedContent` for stray `<<<<<<<`/`=======` pairs (i.e. it validates the model didn't parrot markers back), not that the fully reassembled file is free of the leftover real markers introduced by this boundary-detection mismatch: [5](#0-4) 

The reassembled content is then written straight to disk and staged with no further scan: [6](#0-5) [7](#0-6) 

### Impact Explanation
This lets an attacker who only controls the incoming ("theirs") side of a merge - e.g. a pull-request branch the victim merges locally - cause Desktop's AI conflict-resolution feature to silently produce and stage a corrupted file: genuine code from beyond the fake marker is dropped from the hunk sent to the model (so it's never resolved at all), while literal `=======`/`>>>>>>> branch`-style debris and the real trailing content are copied verbatim into the file that Desktop then `git add`s and offers up for commit. This is a silent corruption of what the user commits/pushes: the commit dialog and diff view will show this as the "resolved" content, and nothing in the pipeline flags that real conflict-marker text remains in the file or that trailing content was silently excluded from resolution.

### Likelihood Explanation
The trigger only requires that the attacker's branch content, when merged, produces a single git conflict region whose "ours" or "theirs" side happens to contain a well-formed nested marker triple (7 `<`, 7 `=`, 7 `>` at line start) - something an attacker can engineer deliberately (e.g. by adding documentation, example code, or an embedded diff/patch snippet that mimics conflict markers) in a file they know or expect will conflict with the victim's edits. No local access, elevated privileges, or social engineering beyond "the user merges/rebases this branch and uses the built-in Copilot conflict resolver" is required.

### Recommendation
Make `reassembleResolvedFile` and `extractConflictHunks` share a single, nesting-aware marker-parsing routine, and make the boundary detection reject (or fall back to skipping) any hunk whose ours/theirs region itself contains lines matching the marker regexes rather than treating them as regular content. Additionally, after reassembly, re-scan the produced file for any remaining lines matching the marker regexes and refuse to write/stage the file (surfacing an error to the user) if markers are still present, instead of relying solely on the per-hunk `resolvedContent` check.

### Proof of Concept
Given a conflicted file (attacker controls the "theirs" text merged in) containing:
```
<<<<<<< HEAD
real our content
<<<<<<< nested-fake
fake ours
=======
fake theirs
>>>>>>> nested-fake-end
=======
real their content
>>>>>>> branch
```
1. `extractConflictHunks` reports exactly one hunk, with `oursContent` = `"real our content\n<<<<<<< nested-fake\nfake ours"` and `theirsContent` = `"fake theirs"`, ending its scan at the `nested-fake-end` line (see loop logic at `app/src/lib/copilot-conflict-context.ts:200-242`). The trailing `=======`, `real their content`, and `>>>>>>> branch` lines are outside any detected hunk.
2. The model resolves the single reported hunk (it never sees the real trailing content, so cannot resolve it).
3. `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:559-596`) independently detects the same truncated boundary (first `>>>>>>>` line encountered), splices in the model's resolution for lines 1-7, then copies the remaining `=======`, `real their content`, `>>>>>>> branch` lines through verbatim as ordinary file content.
4. `_handleCopilotConflictResolutions` writes this reassembled content to disk and runs `git add` on it (`app/src/lib/stores/app-store.ts:7258-7267`), with no validation that the file still contains literal `=======`/`>>>>>>>` marker text.
5. The user commits, producing a commit containing corrupted source with residual conflict-marker text and silently dropped real content, with no warning from the app.
