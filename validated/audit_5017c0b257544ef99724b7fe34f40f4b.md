## Finding [1](#0-0) 

The application already has a purpose-built defense against exactly this class of bug: `resolveWithin`, which is explicitly documented and tested to reject paths that escape the repository root via `..` traversal *or* via a symlink planted inside the working tree [2](#0-1) . It is correctly used when reading working-directory file contents for the Copilot conflict-resolution feature, with an explicit comment "Guard against path traversal and symlink escapes (cross-platform)" [3](#0-2) .

However, `getWorkingDirectoryImage` — the function that reads working-directory image files for rendering diffs — bypasses this guard entirely, joining the raw `file.path` from git status directly onto `repository.path` and reading it with `readFile`: [1](#0-0) 

The same unguarded pattern also appears in the AI conflict-resolution diff builder, `getResolutionDiff`, which reads the working-tree file directly with `Path.join` + `readFile` instead of `resolveWithin`: [4](#0-3) 

### Title
Symlink escape in working-directory image diff rendering allows arbitrary file read outside the repository - (File: app/src/lib/git/diff.ts)

### Summary
`getWorkingDirectoryImage`, invoked whenever the Changes list renders a preview for a file with an image extension, reads the file via `readFile(Path.join(repository.path, file.path))` without calling the app's own `resolveWithin` traversal/symlink guard. If a cloned/fetched/merged branch introduces a tracked symlink whose name has an image extension (e.g. `logo.png`) and whose target points outside the repository (e.g. `~/.ssh/id_rsa`), selecting that entry in the Changes list — which Desktop auto-selects/previews — causes Desktop to read the symlink target and base64-embed its contents as a `data:` URI `<img>` in the renderer.

### Finding Description
`convertDiff` routes any file with a recognized image extension whose diff is `isBinary` to `getImageDiff`, which for working-directory files calls `getWorkingDirectoryImage` [5](#0-4) . That function performs a raw filesystem read:

```ts
const contents = await readFile(Path.join(repository.path, file.path))
```

Node's `fs.readFile` follows symlinks. `file.path` originates from git status parsing of the working tree; it can never contain `..` segments (git trees disallow them), but git *does* allow a tracked entry to be a symlink (mode `120000`). A malicious branch can therefore add/modify a symlink entry named with an image extension pointing at an arbitrary absolute path (e.g. the user's SSH key, `.git-credentials`, or `.aws/credentials`). This is precisely the scenario `resolveWithin` was built to stop, as shown by its dedicated symlink-escape test [6](#0-5) , and as applied in the conflict-context reader [7](#0-6) . `getWorkingDirectoryImage` and `getResolutionDiff` simply never call it, so the guard is inconsistently applied across the codebase — the same “protection exists but wasn’t wired into this specific code path” pattern as the external report’s missing `afterSwapReturnDelta` permission flag.

### Impact Explanation
A successful exploit reads the contents of any file on disk that the Desktop process can access (limited by OS file permissions of the logged-in user, not by repository boundaries) and exposes it in the renderer as base64 data embedded in the DOM. This is a repository-controlled arbitrary file read outside the repo root, matching the stated valid-impact category of "file ... read outside the repo" triggered by "a cloned/fetched repository." Secrets such as SSH private keys or credential files could be exfiltrated once rendered into the DOM (inspectable, copyable, or capturable by any other code with DOM/clipboard access).

### Likelihood Explanation
Triggering requires only that the victim pull/fetch/merge a branch (or open a repository) containing a tracked symlink with an image-like filename pointing outside the repo, then have Desktop preview that entry in the Changes view — something Desktop does automatically for the top/selected file. No local access, admin rights, or unnatural user steps are required beyond normal repository collaboration (cloning, fetching, merging a branch), which is squarely within the "attacker controls a cloned/fetched repository" threat model.

### Recommendation
Route `getWorkingDirectoryImage` (and `getResolutionDiff`'s direct `readFile` of working-tree files) through `resolveWithin(repository.path, file.path)` before reading, exactly as already done in `copilot-conflict-context.ts`, and skip/flag the file with a "skipped" reason if resolution fails. Additionally, consider refusing to render "image" diffs for tree entries whose git mode is a symlink (`120000`) rather than a regular file.

### Proof of Concept
1. Attacker creates a branch that adds a tracked symlink `logo.png` pointing to `../../../../.ssh/id_rsa` (or an absolute path via a Git server that allows it, or via a subsequent commit that reuses/renames an existing symlink).
2. Victim fetches/merges that branch into a local clone of the repository using GitHub Desktop.
3. Desktop's Changes list shows `logo.png` as a new/modified file and auto-previews it (or the user clicks it).
4. `convertDiff` → `getImageDiff` → `getWorkingDirectoryImage` calls `readFile(Path.join(repository.path, 'logo.png'))`, which follows the symlink and returns the contents of the victim's SSH private key, base64-encoded and rendered as an `<img>` `data:` URI in the diff viewer.

export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}
