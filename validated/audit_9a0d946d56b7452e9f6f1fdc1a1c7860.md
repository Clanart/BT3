## Analysis Summary

I was unable to fully verify all necessary preconditions for a confirmed Critical-severity finding before the tool budget was exhausted, but I found strong evidence pointing to a real analog bug class. I'll present it with explicit caveats about what remains unverified.

### Title
Shared `BalanceHandler` instance across nested/recursive precompile calls silently drops balance-changing events, desyncing StateDB balances from `x/bank` truth - (File: `precompiles/common/balance_handler.go`, `testutil/testdata/debug/debug.go`)

### Summary
The audited Symmetrical bug is a case where a multi-step process (liquidation) records an intermediate cutoff/checkpoint, but a later step's accounting incorrectly assumes that checkpoint is still valid after an intervening state change, silently dropping value that should have been credited to a legitimate party. The closest analog in this repository is the `BalanceHandler`'s `prevEventsLen` checkpoint mechanism used to translate `x/bank` `CoinSpent`/`CoinReceived` events into `StateDB` balance mutations around precompile execution [1](#0-0) .

### Finding Description
`BeforeBalanceChange` records `len(ctx.EventManager().Events())` as a checkpoint, and `AfterBalanceChange` only replays events emitted *after* that checkpoint into the `StateDB` via `AddBalance`/`SubBalance` [2](#0-1) . This design is only correct if `BeforeBalanceChange`/`AfterBalanceChange` calls are strictly paired per precompile invocation without an intervening call overwriting the checkpoint.

The `precompiles/common/precompile.go` `runNativeAction` path is safe: it creates a **fresh** `BalanceHandler` from `p.BalanceHandlerFactory.NewBalanceHandler()` on every call [3](#0-2) , so nested calls each get their own instance.

However, the test utility precompile at `testutil/testdata/debug/debug.go` instead calls `p.GetBalanceHandler()` directly in `Run()`, implying a single handler instance associated with the precompile rather than one instantiated fresh per call [4](#0-3) . An accompanying test, explicitly named to demonstrate this exact defect, confirms the bug: recursive precompile calls that share the same `BalanceHandler` instance cause the checkpoint to be repeatedly overwritten by inner invocations [5](#0-4) .

The mechanism, by trace of `AfterBalanceChange`'s window semantics: when a precompile call `A` records checkpoint `N`, then internally triggers a nested precompile call `B` (e.g., via `CallEVMWithData`/`CallEVM` re-entering a stateful precompile) that also calls `BeforeBalanceChange`, the checkpoint is advanced to `M > N`. When `B` returns and eventually `A`'s own `AfterBalanceChange` runs, it uses the shared handler's checkpoint, which is now `M`, not `N` — silently skipping all `CoinSpent`/`CoinReceived`/fractional-balance events emitted between `N` and `M`. Those events (i.e., real bank-ledger balance movements) never get mirrored into the EVM `StateDB`, per the parsing logic [6](#0-5) .

### Impact Explanation
If this pattern exists in any production, unprivileged-reachable precompile (staking, distribution, gov, ics20, erc20, slashing — each of which references `GetBalanceHandler` per `grep_search`, though I was unable to confirm within budget whether their `Run()` methods use the safe per-call `RunNativeAction`/factory pattern or the same shared-instance pattern as `debug.go`), the practical impact would be:
- `StateDB`-visible native balances (used for `BALANCE` opcode reads, `msg.value` semantics, and any subsequent EVM-level native transfer logic within the same transaction) diverge from the actual `x/bank`/`x/precisebank` ledger state.
- Because the discrepancy is a silent drop (not a revert), a contract could construct a call sequence that triggers a real bank-mediated debit/credit through one precompile call, then recursively invoke a second stateful precompile before the outer handler's `AfterBalanceChange` fires, causing the outer balance mutation to never be applied to `StateDB`. This can leave an account's EVM-visible balance permanently inflated (or deflated) relative to its actual spendable bank balance, i.e., irreversible accounting corruption of spendable user value between native and EVM-visible balances — matching the "Critical unauthorized … duplication … irreversible accounting corruption of spendable user value across native balances, EVM balances" impact category.

### Likelihood Explanation
The mechanism is deterministic and triggerable by an ordinary, unprivileged user constructing a contract that invokes a stateful precompile which internally re-enters another (or the same) stateful precompile — this is exactly the scenario the repository's own `TestRecursivePrecompileCallsWithDebugPrecompile` test was written to reproduce. The `contracts/solidity/ERC20RecursiveNonRevertingPrecompileCall.sol` / `ERC20RecursiveRevertingPrecompileCall.sol` test contracts further indicate this recursive-precompile-call scenario was specifically anticipated/tested for the ERC20 precompile family, suggesting it is a realistic, reachable pattern in production-adjacent code, not purely theoretical.

**What remains unverified (honesty disclosure):** I was not able to inspect the `Run()` implementations of the production precompiles (`precompiles/erc20/erc20.go`, `precompiles/staking/staking.go`, `precompiles/distribution/distribution.go`, `precompiles/gov/gov.go`, `precompiles/ics20/ics20.go`, `precompiles/slashing/slashing.go`) or the definition of `GetBalanceHandler()` on the base `Precompile` struct before the tool budget was exhausted. It is possible these production precompiles exclusively use the safe `RunNativeAction` path (fresh handler per call) and that only the explicitly-marked test-only `debug` precompile exhibits the unsafe shared-instance pattern, in which case this finding would be excluded per the Allowed Impact Gate (tests/fixtures are out of scope). I could not confirm this either way.

### Recommendation
Audit every precompile's `Run()`/`Execute()` implementation to confirm that `BalanceHandler` instances are always freshly created per top-level precompile invocation (as `RunNativeAction` already does), never stored as a reusable/shared field returned by a method like `GetBalanceHandler()`. If any production precompile follows the `debug.go` pattern, refactor it to use `BalanceHandlerFactory.NewBalanceHandler()` per call, and add a regression test analogous to `TestRecursivePrecompileCallsWithDebugPrecompile` against each production precompile capable of recursive/nested calls.

### Proof of Concept
The existing repository test already constitutes a proof of concept for the mechanism: [7](#0-6) . A full PoC against a production precompile would require: (1) confirming which production precompile(s) reuse a shared `BalanceHandler`, (2) deploying a contract that calls that precompile such that its execution triggers a nested call back into a stateful precompile (directly or via callback), and (3) asserting that a bank-ledger balance change from the outer call is not reflected in `StateDB.GetBalance()` after the full call returns — which I could not complete due to tool-call budget exhaustion.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
