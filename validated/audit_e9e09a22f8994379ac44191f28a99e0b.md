### Title
Recursive clone disables Git's built-in clone-protection safeguard, re-exposing users to submodule/hook-based RCE - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` in [1](#0-0)  always runs `git clone --recursive` with the environment variable `GIT_CLONE_PROTECTION_ACTIVE` explicitly set to `'false'`: [2](#0-1) 

`GIT_CLONE_PROTECTION_ACTIVE` is Git's own safeguard (added to mitigate the class of vulnerabilities behind CVE-2024-32002/CVE-2024-32004/CVE-2024-32465) that detects and refuses clones where a submodule's `.git` entry is a symlink or uses a case-/Unicode-confusable name that could smuggle a hook, config, or nested `.git` directory outside the intended submodule boundary and into the superproject's git directory. By force-disabling this protection on every clone (recursive by default via `--recursive`), GitHub Desktop removes Git's own defense-in-depth check against this exact attacker-controlled-repository primitive.

### Finding Description
The invariant that should hold is: "a cloned repository's submodules cannot place files (hooks, config, `info/attributes`, etc.) into a location that git or Desktop will later execute or trust as if it belonged to the top-level repository." Git enforces this invariant via `GIT_CLONE_PROTECTION_ACTIVE`/`clone.protectHFS`/`clone.protectNTFS` style checks introduced in the patched releases responding to the RCE class where a malicious repo ships a submodule whose `.git` file (or symlink) uses a case-insensitive-filesystem-confusable name such as `.git` vs `.GIT` (on HFS+/APFS/NTFS) or a symlink pointing outside the submodule, letting the checkout write attacker content (e.g. a post-checkout hook) into the real `.git/hooks` directory of the outer repository.

GitHub Desktop's `clone()` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and always passes `--recursive`, meaning any submodules referenced by a malicious remote are cloned with this protection turned off [3](#0-2) . The only other guard present, `isClonePathSensitive()`, only validates the destination directory chosen by the user (blocking clones into `~/.ssh`, `~/.gnupg`, etc.) [4](#0-3)  — it does not inspect the contents of the remote repository or its submodules, so it provides no protection against a malicious submodule structure inside the cloned tree.

### Impact Explanation
If a victim clones (or "clone again"s, via `MissingRepository.cloneAgain` / `AddExistingRepository`) a remote repository/gist/fork controlled by an attacker that contains a crafted submodule exploiting the case-confusion/symlink `.git` smuggling technique, the disabled protection allows the malicious submodule checkout to write files into the outer repository's real `.git` directory (e.g., hooks executed on next commit/checkout, or altered `core.fsmonitor`/`core.hooksPath` config). This is a direct code-execution primitive triggered purely by cloning an attacker-supplied repository URL, matching the "attacker controls a cloned/fetched repository ... result is code execution" impact class.

### Likelihood Explanation
Cloning a URL supplied by a link, a search result, an org invite, or a GitHub API repository listing is the primary, unavoidable workflow of GitHub Desktop (`clone.ts` is invoked from the standard clone dialog and from "Clone Again"). The vulnerable environment variable is set on every single clone call, with no opt-out and no per-repository trust decision, so any user who clones a hostile repository is affected without any additional unusual steps.

### Recommendation
Do not hardcode `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Let Git's own clone-protection remain active (the default, enabled behavior) for all clones, especially recursive ones that pull in third-party submodules. If protection must be disabled for a specific legitimate use case, gate it behind an explicit, narrowly-scoped condition and document why the safeguard is being bypassed, rather than disabling it unconditionally for every clone.

### Proof of Concept
1. Attacker publishes a public repository containing a submodule entry whose `.git` reference uses a symlink or case/Unicode-confusable name designed to escape the submodule checkout path and target the superproject's `.git/hooks` directory (the same technique behind CVE-2024-32002).
2. Victim opens the "Clone repository" dialog in GitHub Desktop and clones the attacker's URL (or clicks a `x-github-client://openRepo`/deep-link style clone flow, or uses "Clone Again" on a previously known GitHub repository whose contents changed).
3. `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` [2](#0-1) , so Git does not refuse the malicious submodule layout it would otherwise reject.
4. The malicious submodule checkout writes/overwrites a hook (e.g. `post-checkout`) in the outer repository's real `.git/hooks` directory.
5. The next Desktop-triggered git operation that runs hooks (checkout, commit, merge) executes attacker-controlled code in the context of the victim's user account.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
