### Title
Tokenfactory/Bank denom `Metadata.Name`/`Metadata.Symbol` allow Unicode Bidi control characters, enabling on-chain token-identity spoofing via the Bank precompile and CW/ERC pointer contracts - (`sei-cosmos/x/bank/types/metadata.go`)

### Summary
The reported CVE (ALPINE-CVE-2021-42574) is a "Trojan Source" class issue: Unicode Bidirectional control characters can be used to make displayed text differ from its logical byte content, misleading reviewers/users. sei-chain has a directly reachable analog of this bug class: the `Metadata.Name` and `Metadata.Symbol` fields used for tokenfactory/bank denoms are only checked for blankness, never sanitized against control/bidi characters, and are then surfaced verbatim to any EVM caller through the Bank precompile and baked immutably into ERC20/CW pointer contract metadata.

### Finding Description
`Metadata.Validate()` only verifies that `Name` and `Symbol` are non-blank strings; it applies no charset restriction to them (unlike `Base`/`Display`, which are checked with `sdk.ValidateDenom`, a strict alphanumeric regex): [1](#0-0) 

Any account can permissionlessly create a tokenfactory denom and later call `SetDenomMetadata`, which only performs this same blank-check "defense in depth" validation before persisting the metadata on-chain: [2](#0-1) 

This metadata is then:
1. Returned directly to any EVM caller through the Bank precompile's `name()`/`symbol()` view functions: [3](#0-2) 
2. Copied verbatim into the immutable `name`/`symbol` fields of the auto-generated ERC-native pointer contract when a pointer is created (`AddNative`): [4](#0-3) 

Because neither path filters out Unicode bidirectional override/embedding characters (U+202A–U+202E, U+2066–U+2069) or other invisible/format characters, an attacker can craft a `Name`/`Symbol` whose rendered form is deceptively similar to that of a well-known, high-value token (e.g., visually "USDC" or "USDT") while the underlying bytes/denom are entirely different, exactly mirroring the "Trojan Source" visual-vs-logical mismatch described in the CVE.

### Impact Explanation
Wallets, block explorers, and DeFi front-ends generally trust and display the `name()`/`symbol()` values returned by the Bank precompile and ERC pointer contracts to identify tokens for users. A spoofed display name/symbol can cause a user to approve, swap, or transfer funds to the attacker's counterfeit denom/pointer believing it is a legitimate, well-known asset — this is a fund-loss enabling issue via token/precompile-identity confusion, reachable purely through a public `MsgCreateDenom` + `MsgSetDenomMetadata` transaction and the public Bank/Pointer precompiles.

### Likelihood Explanation
Likelihood is high: tokenfactory denom creation is fully permissionless for any unprivileged transaction sender, `SetDenomMetadata` validation is trivially bypassed with any non-blank Unicode string, and the resulting metadata is automatically exposed on the public EVM JSON-RPC surface and baked into pointer contracts without any further review or gating.

### Recommendation
Extend `Metadata.Validate()` (and the tokenfactory `SetDenomMetadata`/`CreateDenom` validation paths) to reject `Name`/`Symbol`/`Description` fields containing Unicode bidirectional control characters and other invisible/format characters (per Unicode Technical Standard #39 guidance), or normalize/strip them before persisting and before propagating the values into ERC/CW pointer contract metadata.

### Proof of Concept
1. Attacker calls `MsgCreateDenom` to create `factory/{attacker}/spoof`.
2. Attacker calls `MsgSetDenomMetadata` with `Symbol` containing a Right-to-Left Override (U+202E) sequence crafted so the rendered text is visually indistinguishable from `"USDC"` while the raw bytes differ from the real USDC denom metadata; `Metadata.Validate()` accepts it because it is non-blank.
3. Attacker (or anyone) calls the Pointer precompile's `addNativePointer(denom)`, which copies `metadata.Name`/`metadata.Symbol` unmodified into the new ERC20 pointer contract's immutable name/symbol.
4. A wallet or block explorer querying `name()`/`symbol()` via the Bank precompile or the pointer ERC20 contract renders the spoofed token identically to the legitimate one, and a user is deceived into interacting with/transferring funds to the counterfeit token.
