Audit Report

## Title
`secp256r1_program` missing from `NON_MIGRATING_BUILTINS_COSTS` causes incorrect default compute-unit accounting - (File: `builtins-default-costs/src/lib.rs`)

## Summary
`BUILTIN_INSTRUCTION_COSTS`, built from `MIGRATING_BUILTINS_COSTS` chained with `NON_MIGRATING_BUILTINS_COSTS`, is the sole source of truth for classifying a program id as a "builtin" for default compute-unit-limit calculation and block-cost accounting. `secp256k1_program` and `ed25519_program` are registered in `NON_MIGRATING_BUILTINS_COSTS`, but `secp256r1_program` — which is fully supported as a first-class precompile in `precompiles/src/lib.rs::PRECOMPILES` and priced via `SECP256R1_VERIFY_COST` in the cost model — is absent, causing `secp256r1` verify instructions to be misclassified as non-builtin.

## Finding Description
`BuiltinProgramsFilter::check_program_kind` in `compute-budget-instruction/src/builtin_programs_filter.rs` classifies each instruction's program id using `MAYBE_BUILTIN_KEY` and `get_builtin_migration_feature_index`, both derived exclusively from `BUILTIN_INSTRUCTION_COSTS` in `builtins-default-costs/src/lib.rs`. Since `secp256r1_program::id()` is not present in `NON_MIGRATING_BUILTINS_COSTS`, `check_program_kind` returns `ProgramKind::NotBuiltin` for it. This classification feeds `ComputeBudgetInstructionDetails::try_from`, which increments `num_non_builtin_instructions` instead of `num_non_migratable_builtin_instructions` for secp256r1 instructions. When a transaction omits an explicit `SetComputeUnitLimit`, `calculate_default_compute_unit_limit` multiplies `num_non_builtin_instructions` by `DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` (200,000 CU) rather than `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT`, which is the treatment secp256k1/ed25519 instructions correctly receive. The module's own comment states this table is used both to calculate the compute limit for transactions without an explicit limit and to calculate the transaction cost used in replay to enforce block cost limits — confirming this is consensus-relevant accounting data. No existing guard corrects this, since the classification is purely table-driven and the table is simply missing the entry.

## Impact Explanation
Any unprivileged user can submit a transaction with a `secp256r1_program` verify instruction and no explicit `SetComputeUnitLimit`. The resulting `compute_unit_limit` computed by `sanitize_and_convert_to_compute_budget_limits` is inflated (using `DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` instead of `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` for that instruction) relative to an equivalent transaction using `secp256k1_program`/`ed25519_program`. Because this same default-limit calculation logic underlies the cost model used for block cost limit enforcement in replay, this is a deterministic, all-validators-agree miscalculation of a specific accounting value — the default/implicit compute-unit budget assigned to `secp256r1` transactions — rather than a consensus-divergence bug. It does not enable fund theft or false execution/rooting, and it is deterministic across all validators, so it does not cause consensus halt.

## Likelihood Explanation
Highly reproducible: any transaction containing a `secp256r1_program` instruction without an explicit compute-unit-limit instruction deterministically hits this path on every validator running this code, as shown by the direct code trace through `check_program_kind`, `ComputeBudgetInstructionDetails::try_from`, and `calculate_default_compute_unit_limit`.

## Recommendation
Add `(secp256r1_program::id(), BuiltinCost::NotMigrating)` to `NON_MIGRATING_BUILTINS_COSTS` in `builtins-default-costs/src/lib.rs`, update `TOTAL_COUNT_BUILTINS`, and add a feature-gated migration path if/when this must change post-activation, since the map is explicitly marked as consensus-sensitive and cannot be modified without a coordinated feature gate.

## Proof of Concept
1. Build a `SanitizedTransaction` containing one `secp256r1_program::id()` instruction and no `ComputeBudgetInstruction::SetComputeUnitLimit` instruction.
2. Call `ComputeBudgetInstructionDetails::try_from(...)` on its instruction iterator; observe `num_non_builtin_instructions` incremented (via `BuiltinProgramsFilter::check_program_kind` returning `ProgramKind::NotBuiltin` for `secp256r1_program::id()`) rather than `num_non_migratable_builtin_instructions`.
3. Call `sanitize_and_convert_to_compute_budget_limits`; observe the computed `compute_unit_limit` uses `DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` for that instruction rather than the smaller `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT`, unlike an equivalent transaction built with `secp256k1_program::id()` or `ed25519_program::id()`.

    fn calculate_default_compute_unit_limit(&self, feature_set: &FeatureSet) -> u32 {
        // evaluate if any builtin has migrated with feature_set
        let (num_migrated, num_not_migrated) = self
            .migrating_builtin_feature_counters
            .migrating_builtin
            .iter()
            .enumerate()
            .fold((0, 0), |(migrated, not_migrated), (index, count)| {
                if count.0 > 0 && feature_set.is_active(get_migration_feature_id(index)) {
                    (migrated + count.0, not_migrated)
                } else {
                    (migrated, not_migrated + count.0)
                }
            });

        u32::from(self.num_non_migratable_builtin_instructions.0)
            .saturating_add(u32::from(num_not_migrated))
            .saturating_mul(MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT)
            .saturating_add(
                u32::from(self.num_non_builtin_instructions.0)
                    .saturating_add(u32::from(num_migrated))
                    .saturating_mul(DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT),
            )
    }
