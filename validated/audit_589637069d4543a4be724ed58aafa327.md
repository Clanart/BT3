### Title
`ReceivedOutput::read` deserializes an attacker-supplied `TxOut`/`outpoint` pair without binding the claimed `TxOut` to the on-chain UTXO it names, letting untrusted bytes misstate the input's value and script - (`networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) deserializes three independent attacker-controlled fields — `offset`, `output` (a `TxOut`), and `outpoint` — and `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:175-185, 253) trusts the embedded `output.value` for fee/change arithmetic and the embedded `outpoint` as the spend target, with no verification that the `TxOut` actually matches the UTXO at `outpoint`. This is the analog of path traversal: a crafted identifier/record escapes its intended correspondence and causes the wallet to operate on a misrepresented object.

### Finding Description
`ReceivedOutput::read` performs only structural decoding:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-133
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

Nothing ties `outpoint` to `output`, nor `output.value`/`output.script_pubkey` to the real UTXO. Downstream, `SignableTransaction::new`:

- sums `input.output.value` into `input_sat` (send.rs:175) used for the `NotEnoughFunds` check and the change amount (`value = input_sat - payment_sat - fee_with_change`, send.rs:228-230);
- builds the `TxIn` from `input.outpoint` (send.rs:179-185);
- stores the claimed `TxOut` in `prevouts` (send.rs:253), which is committed by `Prevouts::All` in the BIP-341 sighash (send.rs:375, 386).

`SignableTransaction::multisig` (send.rs:273-282) does verify `prevouts[i].script_pubkey == p2tr_script_buf(key + offset*G)`, binding script to the signing key — but it never binds `outpoint` ↔ `TxOut` nor validates `value` against the chain.

Two exploitation shapes:

1. **Value understatement (fund burn).** Feed `ReceivedOutput::read` an `outpoint` for a real 0.01 BTC UTXO paying `key + offset·G`, but a `TxOut` claiming `value = 0.005 BTC` (with the correct script_pubkey so `multisig` passes). `input_sat` is understated; the constructed transaction is valid on-chain (BIP-341 commits the *claimed* prevout amounts only in the sighash — the real UTXO still satisfies the script), and the genuine surplus `0.005 BTC` is silently paid as a giant fee to miners.
2. **Value inflation / script mismatch (invalid signed tx).** Claim `value` higher than the real UTXO, or point `outpoint` at an unrelated UTXO while keeping a valid-looking `TxOut`. `SignableTransaction::new` then computes change for money that doesn't exist; the multisig produces a fully-signed but permanently invalid transaction (sighash commits the false prevout amounts), blocking the intended spend while consuming a FROST signing round.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` — the explicit threat surface here — can cause the threshold wallet to sign a transaction that either burns arbitrary amounts of the multisig's real UTXO value as fees (understated prevout value) or produces an unbroadcastable transaction while emitting a valid signature (overstated/mismatched prevout). The former is a direct, irreversible loss of funds; no key material is needed since the script_pubkey check passes with the attacker's forged `TxOut`.

### Likelihood Explanation
Medium. `ReceivedOutput::read`/`serialize` are the documented persistence/transport format for scanned outputs; any deployment that stores or relays scanned outputs over an attacker-influenceable channel (DB rows, RPC relays, coordinator messages) exposes this. Exploitation only requires choosing `value`/`outpoint` freely plus knowing the multisig's registered offset scripts (which are publicly derivable addresses). It does not require participating in the DKG or signing protocol.

### Recommendation
- In `ReceivedOutput`, do not deserialize a standalone `TxOut`/`outpoint` pair from untrusted bytes; instead store the `(outpoint, value)` claimed and have `SignableTransaction::new`/`multisig` re-fetch the prevout from the chain (or require the caller to supply chain-verified `TxOut`s), failing if the claimed `TxOut` differs from the on-chain output at `outpoint`.
- At minimum, document that `ReceivedOutput::read` input must be integrity-protected, and add a `verify_against_utxo(&self, rpc)`-style check before `SignableTransaction::new` consumes the value for fee/change math.

### Proof of Concept
```rust
// Attacker observes a real UTXO: outpoint P paying `key + offset*G` worth 10_000 sats.
// They craft bytes for ReceivedOutput::read:
//   offset = the registered offset (public derivation)
//   output = TxOut { value: 5_000 sats, script_pubkey: <real script> }  // understated
//   outpoint = P (the real outpoint)
let forged: ReceivedOutput = ReceivedOutput::read(&mut attacker_bytes).unwrap();

// Honest wallet path:
let tx = SignableTransaction::new(vec![forged], &payments, change_addr, None, fee_rate)?;
let machine = tx.multisig(&keys).unwrap(); // passes: script_pubkey matches
// ... FROST signing completes; the broadcast tx spends the real 10_000-sat UTXO
// while accounting only 5_000 sats of input — the extra ~5_000 sats become
// an unintended miner fee.
```
The symmetrical case (claiming `value` above the real UTXO, or an `outpoint` pointing to an output the multisig does not control) yields a transaction the network rejects, yet which consumed a signing attempt and whose signature was produced under attacker-influenced sighash parameters.
