### Title
Attacker-injected inconsistent verification shares in deserialized `ThresholdKeys` silently redirect the group key, so received funds are not spendable - (File: crypto/dkg/src/lib.rs)

### Summary
The Superset advisory is an authorization-bypass bug where attacker-controlled content in a parsed field (`sqlExpression`) evades the check meant to constrain it. Serai's analog is `ThresholdKeys::read` / `ThresholdKeys::new`: the parser performs only *structural* validation (parameter ranges, share count, canonical encodings) but never enforces the *semantic* invariant that binds the secret share to the verification shares — `C::generator() * secret_share == verification_shares[i]`. An unprivileged party who can feed bytes to `ThresholdKeys::read` can inject a verification-share set whose interpolated `group_key` is a key the attacker controls, while the victim's embedded `secret_share` does not correspond to it.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, `i`, an `Interpolation` method, a `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new` [1](#0-0) . `ThresholdKeys::new` checks only that the share count equals `n`, that participant indexes are `<= n`, and that `Constant` interpolation isn't used with `t != n` [2](#0-1) . It then computes `group_key` purely from the *attacker-controlled* `verification_shares` (indexes `1..=t` with interpolation factors) [3](#0-2)  and stores the supplied `secret_share` without ever checking `C::generator() * secret_share == verification_shares[params.i()]`. Note the code itself acknowledges this gap: `AlgorithmSignatureMachine::complete` comments that "the only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" [4](#0-3)  — i.e., semantically invalid keys are reachable through deserialization and are silently accepted.

### Impact Explanation
An attacker who supplies a `ThresholdKeys` serialization (e.g., a coordinator distributing/recovering key material, or any import path consuming untrusted bytes via `ThresholdKeys::read`, an API explicitly in scope) can choose `verification_shares` whose Lagrange/Constant interpolation at indexes `1..=t` sums to a group key for which the attacker — not the victim — knows the discrete log (e.g., `verification_shares[1] = G * x` with all factors arranged so the sum equals `G*x`). The victim's `group_key()` and any derived Bitcoin address report funds as received, but the victim's `secret_share` doesn't match: signing sessions produce shares that fail `verify_share`/aggregate verification, or worse, the attacker simply spends the outputs alone since they control the interpolated group key. Funds are reported received yet are not spendable by the victim — a direct analog of a row-level-security bypass granting access to data/funds the policy should have excluded.

### Likelihood Explanation
Reachability requires an attacker to cause a victim to deserialize attacker-influenced `ThresholdKeys` bytes. The format carries a curve-ID tag and self-describing `t`/`n`/`i`, so it is designed to cross trust boundaries (backup, transfer, coordinator-assisted setup). The attack needs only valid canonical encodings — trivially satisfiable — and interpolation factors over participants `1..=t` are public and computable by the attacker. No malicious validator, collusion, or leaked key is needed; the injected field (the verification-share list) simply evades a check that does not exist. Given the constrained reachability (a flow that imports foreign key bytes), Medium-to-High likelihood within such flows.

### Recommendation
In `ThresholdKeys::new`, verify the consistency invariant `C::generator() * secret_share == verification_shares[params.i()]` and return an error otherwise. Additionally, for `Interpolation::Constant`, sanity-check that interpolating the verification shares under the declared coefficients reproduces the same `group_key` for the `1..=t` subset the constructor uses. Ideally, treat any deserialized `ThresholdKeys` whose secret share is inconsistent with its verification shares as a hard deserialization error in `ThresholdKeys::read`.

### Proof of Concept
1. Attacker picks scalar `x`, computes `P = G * x` (key they control).
2. For a `t-of-n` encoding with `Lagrange` interpolation, the attacker solves for verification shares `V_1..V_n` such that `Σ_{i=1..=t} V_i * λ_i = P`, where `λ_i` are the public Lagrange factors over `{1..=t}` — e.g., set `V_1 = P * λ_1^{-1}` and `V_i = identity` handled via `λ_i`-weighted cancellation for `i ∈ {2..=t}` (all are valid canonical non-identity encodings except where identity is needed, which `<C as Ciphersuite>::read_G` — not `Curve::read_G` — accepts, since `ThresholdKeys::read` calls `<C as Ciphersuite>::read_G` [5](#0-4)  which does not reject identity [6](#0-5) ).
3. Attacker picks an arbitrary `secret_share` scalar `s` (they need not know it corresponds to anything) and writes: `id_len || C::ID || t || n || i || 0x01 (Lagrange) || s || V_1..V_n`.
4. Victim calls `ThresholdKeys::<C>::read(&mut bytes)`. All structural checks pass; `group_key = P`.
5. Victim derives the deposit address from `group_key()` and reports received funds — only the attacker (who knows `x`) can spend them; any `sign` the victim attempts fails at `complete` because `s` doesn't match `verification_shares[i]`, hitting the "semantically invalid FrostKeys" path [7](#0-6) .

**Uncertainty note:** I verified the missing consistency check in `ThresholdKeys::new` and the use of the non-identity-rejecting `Ciphersuite::read_G` in `ThresholdKeys::read`, but within the available iteration budget I could not confirm every upstream caller that feeds untrusted bytes into `ThresholdKeys::read` (e.g., coordinator/recovery paths in the wider workspace). The finding stands on the in-scope API surface per the rules, but severity should be weighed against how the consuming protocol obtains these bytes.
