### Title
Sybil self-referral via two attacker-controlled EOAs lets a user farm unearned referrer + referee bonus MGP - (File: rewards/ReferralStorage.sol)

### Summary
`ReferralStorage.useCode` only blocks a user from using a code they themselves registered (`codeOwners[_code] == msg.sender` check), but it does not stop an attacker from registering a code with one EOA and using it from a second EOA they also control. Because `trigger()` is invoked automatically by `MasterMagpie` on every reward claim and pays out both a referrer bonus and a referee bonus based purely on the referee's real, self-generated staking reward, an attacker can capture both bonuses with no genuine third-party referral.

### Finding Description
`registerCode` (rewards/ReferralStorage.sol:147-156) lets any EOA register an arbitrary code and become `codeOwners[_code]`. `useCode` (rewards/ReferralStorage.sol:134-145) only reverts with `Circled()` if `codeOwners[_code] == msg.sender`, i.e. it prevents literal same-address self-use, but performs no check that the caller is a distinct, unrelated economic entity from the code owner: [1](#0-0) 

An attacker deploys `EOA_A` and `EOA_B`. `EOA_A` calls `registerCode(codeA)`, then `EOA_B` calls `useCode(codeA)`, establishing `myReferer[EOA_B] = EOA_A` at zero cost.

`EOA_B` then stakes and calls `masterMagpie.claim`, which (once `totalReward > 0`) unconditionally calls `IReferralStorage(referral).trigger(_user, totalReward)`: [2](#0-1) 

`trigger()` computes `refererAmount` and `refereeAmount` as percentages of the referee's already-earned reward and credits both to `userInfos[...].rewardAmount`, with no check that referrer and referee are unrelated identities: [3](#0-2) 

Additionally, if `EOA_A` locks MGP into vlMGP, `updateTotalFactor` grants it a boost factor (`sqrt(lockedAmount)`) that increases its share of `totalBoostFactor`/`BoostPoint`, further amplifying `_calBoosted` and thus `refererAmount` on every subsequent trigger: [4](#0-3) [5](#0-4) 

Since `EOA_A` and `EOA_B` are both attacker-controlled, every real claim by `EOA_B` mints extra `rewardAmount` credit to both addresses that is redeemable via `claimReward()` (rewards/ReferralStorage.sol:158-168), even though no independent third party was ever referred. This is additive on top of the normal staking reward `EOA_B` already receives through `masterMagpie.claim`, so it constitutes protocol-funded bonus MGP obtained without the qualifying condition (a genuine, separate referred user) the referral program is meant to reward.

### Impact Explanation
This is theft of unclaimed yield: the attacker extracts referrer + referee bonus MGP (funded from the MGP balance held by `ReferralStorage`) proportional to their own staking activity, without ever bringing in real referred volume. Because the boost factor scales with locked vlMGP, an attacker with capital to lock can also increase this diverted share (`_calBoosted`) at the expense of legitimate referrers who share the same `totalBoostFactor` denominator, diluting genuine referrers' payouts as well.

### Likelihood Explanation
Feasibility is high and capital requirement is minimal: only two EOAs and normal staking/claiming activity through `masterMagpie` is required; `registerCode`/`useCode` are permissionless, unauthenticated, and free. The exploit is repeatable on every claim cycle and does not require any privileged role, oracle manipulation, or flash loan.

### Recommendation
Referral Sybil-resistance cannot be fully solved on-chain by address checks alone, but mitigations include: capping/removing the referrer-side boost bonus that scales with the referrer's own vlMGP lock size when the referrer and referee share related characteristics (e.g., same funding source can't be detected on-chain, but consider requiring a minimum bona fide interaction period, KYC/off-chain verification for high tiers, or restricting `registerCode`/tier assignment to vetted addresses via `setReferrerTier`), and/or funding referral bonuses from a portion of the referee's reward (rather than as pure additive protocol-funded bonus) so that self-referral does not create net-new emissions.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `VLMGP`, `ReferralStorage`, and a staking pool; fund `ReferralStorage` with MGP for payouts.
2. `EOA_A.registerCode(codeA)`.
3. `EOA_B.useCode(codeA)`.
4. `EOA_B` stakes into a `masterMagpie` pool and lets rewards accrue; call `masterMagpie.claim` for `EOA_B` multiple times over several blocks.
5. Assert after each claim that `referralStorage.userInfos(EOA_A).rewardAmount` and `referralStorage.userInfos(EOA_B).rewardAmount` both increase, and that `EOA_A.claimReward()` succeeds in withdrawing real MGP despite `EOA_A` never having a genuine independent referee.
6. Optionally have `EOA_A` lock MGP into `VLMGP` and call `updateTotalFactor`, then show `refererAmount` per claim increases further via `_calBoosted`, confirming the diverted share compounds with attacker-controlled capital.

    function useCode(bytes32 _code) external {
        if (_code == bytes32(0)) revert InvalidCode();
        if (codeOwners[_code] == address(0)) revert InvalidCode();
        if (codeOwners[_code] == msg.sender) revert Circled();
        if (myReferer[msg.sender] != address(0)) revert HasReferral();
        
        userInfos[msg.sender].codeIUsed = _code;
        myReferer[msg.sender] = codeOwners[_code];

    }

    function registerCode(bytes32 _code) external {
        if (_code == bytes32(0)) revert InvalidCode();
        if (codeOwners[_code] != address(0)) revert CodeOccupied();

        codeOwners[_code] = msg.sender;
        userInfos[msg.sender].myCode = _code;
        userInfos[msg.sender].tier = 1; // tier 1 as default

        emit RegisterCode(msg.sender, _code);
    }

    function trigger(address _referee, uint256 _amount) external _onlyMasterMagpie {
        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
