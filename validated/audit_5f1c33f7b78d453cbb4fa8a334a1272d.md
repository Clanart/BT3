### Title
Stale line-index reuse in partial-commit selection lets working-directory content drift silently corrupt staged/committed changes - (File: app/src/lib/stores/app-store.ts, app/src/lib/git/apply.ts, app/src/lib/patch-formatter.ts)

### Summary
`DiffSelection` (app/src/models/diff/diff-selection.ts) stores selected lines as a `Set<number>` of positional indices computed from `hunk.unifiedDiffStart + lineIndex`, not by any content-based identity. This selection object is retained in the `WorkingDirectoryFileChange` across the delay between the user visually selecting lines in one diff render and the actual commit, at which point `applyPatchToIndex` (app/src/lib/git/apply.ts) fetches a brand-new diff via `getWorkingDirectoryDiff` and reapplies the old, index-based selection to it in `formatPatch` (app/src/lib/patch-formatter.ts). If the file on disk changes between those two points — e.g., a build tool, editor autosave, git hook, IDE, or any concurrent process writes to the file, or a background repository refresh triggered by a git operation — the hunk boundaries and line indices shift, but the selection's index set does not shift with them.

### Finding Description
The comment at app/src/lib/stores/app-store.ts:3480-3485 explicitly documents that "the diff might have changed dramatically since last we loaded it" and that the app "ideally" should validate that selected lines still exist, but "for now" only filters selection by whether an index is still `selectable` (i.e., still exists as an includeable line at that position), not whether it's still the *same* line. This same weak invariant is present at the actual staging boundary: `applyPatchToIndex` recomputes the diff at commit time and blindly reapplies `file.selection.isSelected(absoluteIndex)` (app/src/lib/patch-formatter.ts:157) using the newly fetched hunk's `unifiedDiffStart` offsets. Nothing recomputes or invalidates the selection against the new hunk content — only against whether the index number is still in range/includeable.

This means the value that gets silently corrupted is the effective line-selection that determines what content is written into the git index/commit: an index that pointed to "line X: `deleteApiKeyCheck()`" at selection time can, after a shift, point to "line X: `unrelated comment`" at staging time, causing the wrong hunk lines to be included or excluded from what the user believes they are committing — without any error, warning, or diff re-confirmation shown to the user (`applyPatchToIndex` never re-renders the diff for user review before staging).

### Impact Explanation
This falls squarely in "silent corruption of what the user commits or pushes." A user reviewing a diff and selecting specific lines to include in a partial commit has no code-level guarantee that those same logical lines are what get staged if the underlying file content shifts before the commit executes (e.g., due to a fetch/checkout/rebase auto-triggering a background diff refresh, an editor/IDE autosave, a file-system watcher-driven build step, or another tool writing to the file). The result can be a commit that includes attacker- or tool-introduced lines the user never reviewed/selected, or excludes lines the user intended to commit, while the UI gives no indication that anything went wrong.

### Likelihood Explanation
Desktop refreshes working-directory diffs frequently (status polling, window focus, explicit refreshes) and there is an inherent async gap between diff computation, user interaction with `DiffSelection`, and eventual commit execution (`_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff again). Any legitimate concurrent file modification during that window (very plausible for actively-edited files, files touched by build tools/linters/formatters, or files in repos with pre-commit/post-checkout hooks that rewrite content) will trigger the described index misalignment. No malicious local access is required — only ordinary concurrent file writes during normal Desktop usage.

### Recommendation
Before applying a partial-commit patch, re-validate the `DiffSelection` against a fresh diff of the file taken immediately prior to `applyPatchToIndex`, and abort/re-prompt the user (rather than silently reusing possibly-mismatched indices) if the file's content hash/mtime has changed since the diff the selection was made against. Alternatively, key selection state by stable line content/hash rather than purely positional index, similar in spirit to the report's recommendation of correctly sequencing state mutations so that a stale, pre-shift quantity is never blindly reused post-shift.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file so it has multiple hunks.
2. In the Changes view, partially select specific lines from hunk 2 for a partial commit (do not click "Commit" yet).
3. While the commit UI is open, have another process (e.g., a script, editor autosave, or `git pull`/hook) insert/remove lines earlier in the same file, shifting hunk 2's line numbers.
4. Click "Commit selected lines." `applyPatchToIndex` (app/src/lib/git/apply.ts:60) fetches the new diff and `formatPatch` (app/src/lib/patch-formatter.ts:143-171) reapplies the old index-based `DiffSelection` to the shifted hunk.
5. Inspect the resulting commit: it contains different logical lines than what was visually selected in step 2, with no warning shown to the user.
