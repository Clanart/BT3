### Title
Fungible-token transfers can bypass post-condition enforcement when a contract defines a non-fungible token under the same asset name - ([File: clarity-types/src/effects/asset_map.rs])

### Summary
`AssetMap::to_table()` merges the fungible-token map (`token_map`) and the non-fungible-token map (`asset_map`) into a single `HashMap<AssetIdentifier, AssetMapEntry>` per principal, keyed only by `{contract_identifier, asset_name}` [1](#0-0) . Because `AssetIdentifier` does not encode whether the asset is fungible or non-fungible, and Clarity's `define-fungible-token` and `define-non-fungible-token` namespaces are tracked separately by the type checker (so a contract can define both a FT and an NFT with the identical name), a single principal can move both a fungible token and a non-fungible token that share the same `asset_name` within one transaction. When `to_table()` builds its merged view, the NFT entries are drained and inserted *after* the FT entries, and `HashMap::extend` overwrites on key collision, so the FT entry is silently replaced by the NFT entry for that `AssetIdentifier`. This causes `check_transaction_postconditions`'s "every moved asset must be covered" enforcement loop to see only the NFT movement and completely miss the FT movement for that identifier.

### Finding Description
`check_transaction_postconditions` in `crates/stacks-transactions/src/lib.rs` builds two independent tracking maps while iterating the transaction's post-conditions: `checked_fungible_assets` (populated only by `TransactionPostCondition::Fungible`/`STX` conditions) and `checked_nonfungible_assets` (populated only by `TransactionPostCondition::Nonfungible` conditions) [2](#0-1) .

After processing the declared post-conditions, the function enforces that *every* asset actually moved by the transaction (in Deny/Originator mode) is covered by some post-condition, by calling `asset_map.to_table()` and matching each `(principal, asset_identifier)` entry against the two tracking maps according to whether the merged entry is `AssetMapEntry::Asset` (NFT) or something else (FT/STX) [3](#0-2) .

The bug is in how `to_table()` builds that merged view: it drains `token_map` (FT transfers) into the table first, then later drains `asset_map` (NFT transfers) into the *same* table using `output.extend(...)` [4](#0-3) . `HashMap::extend` overwrites any existing entry with the same key, so if a principal transferred a fungible token and a non-fungible token that share the same `AssetIdentifier` (same contract, same `asset_name`), the resulting table only retains the NFT entry (`AssetMapEntry::Asset`) — the FT entry (`AssetMapEntry::Token`) for that identifier disappears entirely from the enforcement pass.

Clarity does not prevent a contract from defining a fungible token and a non-fungible token with the same name — `define-fungible-token` and `define-non-fungible-token` are tracked in separate namespaces by the type checker/analysis contexts. A malicious (or careless) contract author can therefore construct a contract with `(define-fungible-token foo)` and `(define-non-fungible-token foo uint)`, and a single public function that transfers both `foo` FT and `foo` NFT away from the caller in one call.

If a user signs a transaction against such a contract in `Deny` (or `Originator`) post-condition mode and adds only a `Nonfungible` post-condition covering the specific NFT they expect to move (believing this fully constrains what the contract can take from them), the `Fungible`/FT branch of the per-postcondition loop is never exercised, so `checked_fungible_assets` has no entry for that `AssetIdentifier`. Normally the "unchecked assets" enforcement loop would catch the un-covered FT transfer and reject the transaction. But because `to_table()` collapses the FT and NFT entries under the same key (NFT wins), the enforcement loop only observes the NFT entry, finds it covered by the user's NFT post-condition, and never inspects the FT transfer at all — the FT movement escapes any post-condition check.

### Impact Explanation
This breaks the exact equality guaranteed by post-conditions: "in Deny/Originator mode, every asset moved by a principal must be covered by an explicit post-condition." An attacker-controlled contract can move an arbitrary amount of a fungible token away from a signer whose transaction is protected by post-conditions in Deny mode, as long as the contract also emits an NFT transfer under the same `asset_name`/contract identifier that happens to be (or is made to be) covered by the user's declared NFT post-condition. This matches the report's "Impact must be... an asset moving past its post-conditions," which is classified High/Critical in the rules ("an asset moving past its post-conditions").

### Likelihood Explanation
Exploitation requires the victim to interact with a specific malicious contract (one deliberately crafted to define colliding FT/NFT names and to transfer both asset kinds together) and to rely on Deny/Originator-mode post-conditions covering only the NFT leg. This is fully reachable through ordinary user-signed transactions calling an arbitrary (attacker-deployed) contract — no miner, signer, or privileged party is required, and it is entirely under the control of the contract author who lures a victim into signing such a transaction (e.g., an NFT marketplace/swap contract that also silently drains a same-named FT).

### Recommendation
`AssetMap`'s internal table (and any consumer, such as `check_transaction_postconditions`'s enforcement pass) must not conflate fungible and non-fungible entries under the same `AssetIdentifier`. Either:
- Track FT and NFT entries under independently-keyed maps in `to_table()`'s output (e.g., return two separate maps, or wrap the key to include an asset-kind discriminant), so a collision in `asset_name` between a `define-fungible-token` and `define-non-fungible-token` in the same contract cannot cause one entry to silently overwrite the other; or
- Make `to_table()` merge FT/NFT entries for a colliding identifier by preserving both (e.g., use a `Vec<AssetMapEntry>` per key, or a composite key `(AssetIdentifier, AssetKind)`), and update the "unchecked assets" enforcement loop in `crates/stacks-transactions/src/lib.rs` to iterate over both kinds independently instead of assuming one `AssetMapEntry` per `(principal, asset_identifier)`.

### Proof of Concept
1. Deploy a contract `evil.clar` containing:
   ```
   (define-fungible-token foo)
   (define-non-fungible-token foo uint)
   (define-public (drain (id uint))
     (begin
       (try! (ft-transfer? foo 1000000 tx-sender 'SP...ATTACKER))
       (nft-transfer? foo id tx-sender 'SP...ATTACKER)))
   ```
2. Victim signs a transaction calling `evil.drain(u1)` with `TransactionPostConditionMode::Deny` and a single post-condition:
   `TransactionPostCondition::Nonfungible(Origin, AssetInfo{evil, "foo"}, Value::UInt(1), Sent)`.
3. During execution, `log_token_transfer` records `token_map[victim][AssetIdentifier{evil,"foo"}] = 1_000_000` and `log_asset_transfer` records `asset_map[victim][AssetIdentifier{evil,"foo"}] = [1]` [5](#0-4) .
4. `check_transaction_postconditions` processes the single `Nonfungible` post-condition and populates only `checked_nonfungible_assets`.
5. In the enforcement pass, `asset_map.to_table()` merges the two maps; because the NFT drain runs after the FT drain and overwrites the same key, the resulting table entry for `AssetIdentifier{evil,"foo"}` is `AssetMapEntry::Asset([1])` only — the `AssetMapEntry::Token(1_000_000)` entry is lost [6](#0-5) .
6. The enforcement loop sees `AssetMapEntry::Asset`, looks up `checked_nonfungible_assets`, finds NFT id 1 covered, and returns `Ok(None)` (pass) — despite the 1,000,000 `foo` FT transfer never being checked against any post-condition [7](#0-6) .

    pub fn to_table(mut self) -> HashMap<PrincipalData, HashMap<AssetIdentifier, AssetMapEntry>> {
        let mut table: HashMap<PrincipalData, HashMap<AssetIdentifier, AssetMapEntry>> =
            HashMap::with_capacity(self.token_map.len());
        for (principal, principal_map) in self.token_map.drain() {
            let output = table.entry(principal).or_default();
            output.extend(
                principal_map
                    .into_iter()
                    .map(|(asset, amount)| (asset, AssetMapEntry::Token(amount))),
            );
        }
        for (principal, amount) in self.stx_map.drain() {
            table
                .entry(principal)
                .or_default()
                .insert(AssetIdentifier::STX(), AssetMapEntry::STX(amount));
        }
        for (principal, amount) in self.burn_map.drain() {
            table
                .entry(principal)
                .or_default()
                .insert(AssetIdentifier::STX_burned(), AssetMapEntry::Burn(amount));
        }
        for (principal, principal_map) in self.asset_map.drain() {
            let output = table.entry(principal).or_default();
            output.extend(
                principal_map
                    .into_iter()
                    .map(|(asset, values)| (asset, AssetMapEntry::Asset(values))),
            );
        }
        table
    }
