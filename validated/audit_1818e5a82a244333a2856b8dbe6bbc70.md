Based on the investigation, the closest structural analog to the Weiroll “default value bypasses a required check” bug is in Desktop's `x-github-client://openRepo` deep-link handler, specifically how the `branch` parameter is validated before being fed into a Git checkout command.

### Title
Deep-link `branch` parameter validation omits leading-dash check, enabling Git argument injection - (File: `app/src/lib/sanitize-ref-name.ts`)

### Summary
`parseAppURL` validates the `branch` query parameter of an `openRepo` deep link using `testForInvalidChars`, which only tests against `invalidCharacterRegex`. That regex bans control characters, spaces, and several ref-format-illegal characters but does **not** flag a leading `-`/`+`. A dedicated stripping step for leading dashes/pluses only exists in the sibling function `sanitizedRefName`, which is never invoked for deep-link branch values.

### Finding Description
`parseAppURL` accepts `branch` from an untrusted `x-github-client://openRepo/...` URL and validates it with: [1](#0-0) 
This calls `testForInvalidChars`, which simply runs `invalidCharacterRegex.test(name)`: [2](#0-1) 
Note that `sanitizedRefName` (used elsewhere to create *new* branches) strips leading `-`/`+` in a second pass — `.replace(/^[-\+]*/g, '')` — but `testForInvalidChars` performs no equivalent check, so a string like `--upload-pack=/tmp/x` passes validation as a "valid" branch. The validated action is then handed to `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl`, which calls `checkoutLocalBranch` with the attacker-supplied string as `branchName`: [3](#0-2) 
This mirrors the reported bug's shape exactly: a guard exists (`fillAmount==0` check / `testForInvalidChars`) but it does not cover the specific "default/edge" value (`RewardStyle.Upfront==0` / a leading-dash ref) that lets attacker-controlled data flow past validation into a sensitive execution path.

### Impact Explanation
If the resulting branch string is ultimately passed as a literal `git checkout <branchName>` argument without a `--` separator ahead of it, Git will interpret a leading-dash value as an option/flag rather than a ref name. Depending on which flags are reachable this way, this is the classic "argument injection via user-controlled ref name" bug class, which can be leveraged to influence Git process behavior in ways the option wasn't designed for (e.g., forcing extra flags into the checkout invocation). This is a code-execution-adjacent primitive triggered purely by the user clicking a link — no local access, no malware, and no credentials required, matching the requested unprivileged/deep-link-triggered impact class.

### Likelihood Explanation
Likelihood depends on whether `checkoutLocalBranch`'s underlying git invocation places `branchName` before a `--` argument terminator. I was not able to fully confirm the exact argument assembly of `checkoutLocalBranch` (the shared git branch-checkout helper) within the indexed content available to me — the file implementing it (likely under `app/src/lib/git/checkout.ts`) was not returned by my searches in enough detail to verify the exact `args` array ordering. This is the key uncertainty: if that call site already inserts `--` before the ref (a common Git-wrapper mitigation), the injection is neutralized even though the deep-link validation gap still exists.

### Recommendation
- Make `testForInvalidChars`/`parseAppURL`'s branch validation reject (or `sanitizedRefName`-normalize) any ref beginning with `-` or `+`, consistent with the stripping logic already present in `sanitizedRefName`.
- Independently, audit all Git invocations that accept a caller/URL-supplied ref (including `checkoutLocalBranch`) to ensure a `--` separator always precedes the ref argument, as defense in depth against argument injection regardless of upstream validation.

### Proof of Concept
1. Register/trigger the `x-github-client://` protocol handler (e.g. via a webpage link) with:
   `x-github-client://openRepo/https://github.com/owner/repo?branch=--upload-pack=%2Ftmp%2Fevil`
2. `parseAppURL` parses this to `{ name: 'open-repository-from-url', branch: '--upload-pack=/tmp/evil', ... }` because `testForInvalidChars('--upload-pack=/tmp/evil')` returns `false` (no banned characters present) — confirmed by reading `app/src/lib/sanitize-ref-name.ts` and the test suite in `app/test/unit/parse-app-url-test.ts`, which never exercises leading-dash branch values.
3. Desktop calls `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl(url, branchName)` → `checkoutLocalBranch(repository, branchName)` with the unsanitized string.
4. If the underlying `checkoutLocalBranch` git invocation does not prepend `--` before the ref, Git treats the value as a flag rather than a ref, enabling argument injection.

**Caveat:** I could not verify step 4 against the actual implementation of `checkoutLocalBranch`/the Git command it issues within the indexed codebase content, so I cannot confirm exploitability end-to-end with full certainty — this should be verified directly against `app/src/lib/git/checkout.ts` (or wherever `checkoutLocalBranch` is implemented) before treating this as a confirmed, exploitable vulnerability rather than a validation-gap finding.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
