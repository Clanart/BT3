The Chainlink report's core defect is **trusting a bounded/stale value without validating it against expected freshness or range**, allowing an attacker to exploit outdated data as if it were current. The closest analog in `shopify_app` is the App Proxy HMAC verification, which validates only the *signature* of a query string but never validates the `timestamp` parameter's freshness, so a captured valid signed proxy request can be replayed indefinitely.

### Title
Missing Timestamp Freshness/Bounds Check in App Proxy Signature Verification Enables Indefinite Replay - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` verifies that the HMAC `signature` query parameter matches the recomputed signature of the remaining query parameters, but it never inspects or bounds-checks the `timestamp` parameter that Shopify includes in every app-proxy request.

### Finding Description
`verify_proxy_request` calls `query_string_valid?`, which deletes `signature` from the query hash, recomputes the HMAC over the remaining sorted parameters (including `timestamp`), and does a `secure_compare` against the supplied signature [1](#0-0) . Nowhere in this method — or anywhere else in the concern — is `timestamp` parsed and compared to `Time.now` to reject stale requests. As long as the signature matches the exact bytes of a previously-valid query string, the request is accepted regardless of how old the `timestamp` value is, similar to how the Chainlink aggregator keeps returning `minAnswer`/`maxAnswer` (a value that was once valid but no longer reflects reality) without any bound/freshness check causing it to be trusted.

### Impact Explanation
An attacker who observes or intercepts one valid app-proxy request URL (e.g., via logs, browser history, referrer leakage, or network capture over an unencrypted channel) can replay that exact query string against the app-proxy endpoint at any point in the future, and it will still pass verification because only the cryptographic signature — not the age of the request — is checked. This is a concrete "accepted forged/stale signed request" scenario: the endpoint accepts a request from an unrelated/anonymous requester (the analog does not require any own-shop session) as if it were a fresh, legitimate proxy call from Shopify.

### Likelihood Explanation
Reachable by any anonymous HTTP client that can obtain one previously valid signed proxy query string; no authentication, session, or privileged access is required to attempt replay against `verify_proxy_request` [2](#0-1) . The test suite confirms only signature correctness is asserted and never timestamp age [3](#0-2) .

### Recommendation
Parse the `timestamp` parameter and reject requests whose timestamp is outside an acceptable window (e.g., a few minutes) before performing the signature comparison, in addition to the existing HMAC check.

### Proof of Concept
1. Capture one legitimate app-proxy request URL (with valid `signature` and `timestamp`) sent by Shopify to a controller including `ShopifyApp::AppProxyVerification`.
2. Replay the identical URL (unmodified) against the same endpoint at any later time.
3. `query_string_valid?` recomputes the same HMAC over the same parameters and returns `true` via `ActiveSupport::SecurityUtils.secure_compare`, so `verify_proxy_request` allows the stale request through [4](#0-3) .

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
