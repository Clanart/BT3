### Title
Panic on unregistered participant index in blame decryption - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` directly, and `BlameMachine::blame_internal` indexes `self.commitments[&sender]` directly, without validating that the `recipient`/`sender` `Participant` values are members of the DKG set. A blame accusation naming an out-of-set participant causes a HashMap indexing panic, crashing the evaluating party — a reachable, repeatable denial of service analogous to the CVE-2023-22064 class (easily triggered crash/hang from crafted protocol input).

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take `sender: Participant` and `recipient: Participant` plus an `EncryptedMessage` and `Option<EncryptionKeyProof>`, all of which originate from an accusing party's protocol message (the blame API exists precisely to evaluate externally supplied, potentially false accusations). `Participant::new` only rejects zero — any nonzero `u16` is a valid `Participant`, including indexes greater than `n`.

In `decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:381-390):

```rust
if let Some(proof) = proof {
  proof
    .dleq
    .verify(
      &mut encryption_key_transcript(self.context),
      &[C::generator(), msg.key],
      &[self.enc_keys[&decryptor], *proof.key],   // panics if decryptor not registered
    )
```

`enc_keys` is only populated for participants `1..=n` (via `verify_r1` in crypto/dkg/pedpop/src/lib.rs:313-315 and `AdditionalBlameMachine::new` at crypto/dkg/pedpop/src/lib.rs:656-660). Indexing a missing key panics. The only gate before this is `msg.pop.verify` (encryption.rs:374-379), which an accuser can satisfy: the PoP challenge binds `context`, the attacker-chosen `msg.key`, `msg`, and the `from` (sender) index — but no secret of any real participant. The accuser picks an ephemeral scalar `k`, sets `key = k*G`, and Schnorr-signs the challenge, so the check passes for arbitrary `sender`/`recipient` labels. Similarly, `blame_internal` later evaluates `self.commitments[&sender]` (pedpop/src/lib.rs:599), which panics for any `sender` index not in the DKG set once the earlier checks pass.

`AdditionalBlameMachine` makes this worse: its documented purpose is to let *any* party (even non-participants) evaluate blame claims (pedpop/src/lib.rs:639-649), so feeding it a malicious accusation is an intended input path, not caller misuse — yet the function has no `Result` return and panics unconditionally.

### Impact Explanation
A party submitting a blame accusation can deterministically crash any node that evaluates it (each honest party arbitrating blame, or an `AdditionalBlameMachine` observer), by setting `recipient` (or `sender`) to a `Participant` index outside `1..=n` while supplying a self-consistent `EncryptedMessage`/`EncryptionKeyProof`. This is a repeatable, on-demand panic — a complete denial of service of the blame-arbitration path, and abort of any DKG relying on it, matching the "unauthorized ability to cause a hang or frequently repeatable crash" bug class.

### Likelihood Explanation
Triggering requires only that the accuser cause a blame evaluation to run with out-of-range indexes — inputs the API explicitly accepts from external accusations. Constructing a passing `pop` signature is trivial since the signing scalar is chosen by the attacker. No threshold collusion, leaked keys, or privileged position is needed.

### Recommendation
Replace indexing with fallible lookups: `self.enc_keys.get(&decryptor)` / `self.commitments.get(&sender)`, returning `DecryptionError::InvalidProof` (or a new `InvalidParticipant` error propagated through `PedPoPError`) when the named participant isn't part of the registered set. `blame_internal`/`blame` should return `Result<_, PedPoPError<C>>` or treat out-of-set accuser/accused labels as a defined fault rather than panicking.

### Proof of Concept
```rust
// Setup: n = 3 DKG completes normally, producing a BlameMachine or
// AdditionalBlameMachine::new(context, 3, commitment_msgs).

// Attacker crafts an EncryptedMessage with a self-consistent PoP:
let k = Zeroizing::new(C::random_nonzero_F(&mut OsRng));
let key = C::generator() * k.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(&mut OsRng));
let R = C::generator() * nonce.deref();
let msg_bytes = SecretShare::<C::F>(C::F::ZERO.to_repr()); // contents irrelevant
let pop = SchnorrSignature::sign(
  &k, nonce,
  pop_challenge::<C>(context, R, key, sender, msg_bytes.as_ref()),
);
let evil_msg = EncryptedMessage { key, pop, msg: Zeroizing::new(msg_bytes) };

// Any proof suffices; the panic occurs while constructing verify()'s args
// before the DLEq is ever checked.
let proof = Some(EncryptionKeyProof { key: Zeroizing::new(key), dleq: any_dleq });

// recipient = Participant(4) is not in {1,2,3}, so enc_keys has no entry:
machine.blame(sender, Participant::new(4).unwrap(), evil_msg, proof);
// => thread panics at encryption.rs:388: self.enc_keys[&decryptor]
```

Note: confidence is moderate. The panic site is unambiguous (`HashMap` `Index` impl panics on absent keys), and the PoP gate is attacker-satisfiable, but whether a given Serai deployment routes arbitrary accuser-supplied `sender`/`recipient` indexes into `blame` depends on the caller; the `AdditionalBlameMachine` API (explicitly for arbitrary blame evaluation by third parties) makes this path reachable regardless. I did not exhaustively audit `networks/bitcoin` for additional crash vectors within the iteration budget.
