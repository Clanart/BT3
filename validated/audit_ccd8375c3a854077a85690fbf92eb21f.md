## Analog identified: stale diff used to build a "discard changes" patch without re-validating against the current working-directory content

### Title
Discarding a partial selection applies a patch built from a **stale** in-memory diff instead of the file's current on-disk content - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/ui/changes/changes.tsx`)

### Summary
The `sell_market_seat` bug is a "stale value used for a state-changing action" bug: a cached price/funding value is used to compute an outcome instead of refreshing it first. The closest structural analog in GitHub Desktop is `discardChangesFromSelection`: when a user discards a *partial* line selection, Desktop builds a `git apply` patch from the `ITextDiff` object that was rendered in the UI (`diff` prop), not from a freshly recomputed diff of the file's current on-disk state, and applies that patch directly to the working tree.

### Finding Description
The discard-partial-selection flow is:
- `Changes.onDiscardChanges` receives `diff: ITextDiff` and `diffSelection: DiffSelection` straight from the diff viewer component and forwards them unchanged to the dispatcher: [1](#0-0) 
- `_discardChangesFromSelection` (via `git-store.ts`) calls `discardChangesFromSelection(repository, filePath, diff, selection)` in `app/src/lib/git/apply.ts`, which formats a patch **directly from the passed-in `diff`** and applies it with `git apply`: [2](#0-1) 

Contrast this with the *full-file* stage/apply path, `applyPatchToIndex`, which explicitly re-fetches the diff at call time via `getWorkingDirectoryDiff(repository, file)` right before formatting the patch: [3](#0-2) 

For the partial-discard path there is no equivalent refresh: the `ITextDiff` held in `changesState.selection.diff` (populated by `updateChangesWorkingDirectoryDiff`) can become stale relative to the file on disk, and there is no re-fetch or hash/mtime comparison performed immediately before `git apply` is invoked. `updateChangesWorkingDirectoryDiff` only reconciles the diff opportunistically when the *selection* changes or a refresh happens to run; it does not run synchronously right before a discard action commits the patch: [4](#0-3) 

The invariant that's broken is the same one broken in `sell_market_seat`: **an action that mutates persistent state (the working tree / the client's funds) is computed from a value that was correct at read time but is not guaranteed correct at write time**, and no re-validation step exists between read and write.

### Impact Explanation
If the file on disk changes between the moment the diff was rendered and the moment the user clicks "Discard selection" — e.g. an external editor autosave, a formatter/linter running on save, a build tool regenerating the file, or another concurrent Desktop operation (checkout, stash pop, pull) touching the same file — the unified diff patch generated by `formatPatchToDiscardChanges` no longer matches the file's real content. `git apply` is a context-based patcher: with unchanged surrounding context lines it can still apply "successfully" against the new content while discarding/reverting the wrong hunk offsets, silently corrupting parts of the file the user never intended to touch (data loss/corruption of uncommitted work, analogous to the report's "user receives more or less money than they should" — here the user loses or keeps different content than they intended). This is squarely inside the "silent corruption of what the user commits or pushes" impact class, since discarded/kept lines directly determine what subsequently gets staged and committed.

### Likelihood Explanation
This requires no privileged access, malware, or unnatural user steps — only a normal, foreseeable timing window between rendering a diff and clicking "Discard changes/selection" while some other process (editor autosave, linter, formatter, build watcher, or another Desktop background refresh) touches the same file, which is a common developer workflow. Because `git apply` tolerates some drift via surrounding context matching, the failure mode is silent rather than a hard error, making it more likely to go unnoticed by the user (no confirmation of what was actually discarded against the *current* file content). I could not find any hash/mtime freshness check, nor a re-fetch-and-diff-recompute step gating the `git apply` call in this path, unlike the full-file stage path (`applyPatchToIndex`) which does re-fetch.

### Recommendation
Before invoking `git apply` for `discardChangesFromSelection` (and the analogous partial-stage path if it doesn't already), re-fetch the current working-directory diff for the file (as `applyPatchToIndex` already does) and re-validate that the `DiffSelection` and hunks used to build the patch still correspond to the current file content (e.g., compare `diff` hunks/hash against a freshly computed diff, or pass the file's current stat/hash and abort/refresh-and-reprompt on mismatch) instead of trusting the diff object captured earlier by the UI.

### Proof of Concept
1. Modify a tracked file so it has a multi-hunk diff; select only part of the changes for inclusion.
2. Open the diff view so `changesState.selection.diff` is populated (per `updateChangesWorkingDirectoryDiff`), and choose to discard the unselected hunk(s) via `Changes.onDiscardChanges`.
3. Before clicking "Discard", have another process append/modify lines near the target hunk in the same file on disk (simulating an editor autosave/linter run) without Desktop re-rendering the diff in time.
4. Confirm the discard; `discardChangesFromSelection` in `app/src/lib/git/apply.ts` builds the patch from the old `diff` object and calls `git apply --unidiff-zero --whitespace=nowarn -`.
5. Inspect the file afterward: because the patch context no longer matches, either `git apply` fails outright (fail-safe but unhelpful) or, in offset-tolerant cases, ends up altering lines beyond what the user actually intended to discard, silently diverging from the user's real intent — verifying the absence of a freshness check that exists in the sibling `applyPatchToIndex` function (`getWorkingDirectoryDiff` re-fetch at line 60 of `apply.ts`).

**Note:** I was not able to execute this PoC against a live Desktop build (no filesystem/terminal access in this mode); this is a static code-path analysis based on the indexed source. If you need this validated dynamically, a Devin session with repo access could run the discard flow with a concurrent file mutation to confirm the exact `git apply` behavior (hard failure vs. silent partial corruption).

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}

  private async updateChangesWorkingDirectoryDiff(
    repository: Repository
  ): Promise<void> {
    const stateBeforeLoad = this.repositoryStateCache.get(repository)
    const changesStateBeforeLoad = stateBeforeLoad.changesState

    if (
      changesStateBeforeLoad.selection.kind !==
      ChangesSelectionKind.WorkingDirectory
    ) {
      return
    }

    const selectionBeforeLoad = changesStateBeforeLoad.selection
    const selectedFileIDsBeforeLoad = selectionBeforeLoad.selectedFileIDs

    // We only render diffs when a single file is selected.
    if (selectedFileIDsBeforeLoad.length !== 1) {
      if (selectionBeforeLoad.diff !== null) {
        this.repositoryStateCache.updateChangesState(repository, () => ({
          selection: {
            ...selectionBeforeLoad,
            diff: null,
          },
        }))
        this.emitUpdate()
      }
      return
    }

    const selectedFileIdBeforeLoad = selectedFileIDsBeforeLoad[0]
    const selectedFileBeforeLoad =
      changesStateBeforeLoad.workingDirectory.findFileWithID(
        selectedFileIdBeforeLoad
      )

    if (selectedFileBeforeLoad === null) {
      return
    }

    const diff = await getWorkingDirectoryDiff(
      repository,
      selectedFileBeforeLoad,
      this.hideWhitespaceInChangesDiff
    )

    const stateAfterLoad = this.repositoryStateCache.get(repository)
    const changesState = stateAfterLoad.changesState

    // A different file (or files) could have been selected while we were
    // loading the diff in which case we no longer care about the diff we
    // just loaded.
    if (
      changesState.selection.kind !== ChangesSelectionKind.WorkingDirectory ||
      !arrayEquals(
        changesState.selection.selectedFileIDs,
        selectedFileIDsBeforeLoad
      )
    ) {
      return
    }

    const selectedFileID = changesState.selection.selectedFileIDs[0]

    if (selectedFileID !== selectedFileIdBeforeLoad) {
      return
    }

    const currentlySelectedFile =
      changesState.workingDirectory.findFileWithID(selectedFileID)
    if (currentlySelectedFile === null) {
      return
    }

    const selectableLines = new Set<number>()
    if (diff.kind === DiffType.Text || diff.kind === DiffType.LargeText) {
      // The diff might have changed dramatically since last we loaded it.
      // Ideally we would be more clever about validating that any partial
      // selection state is still valid by ensuring that selected lines still
      // exist but for now we'll settle on just updating the selectable lines
      // such that any previously selected line which now no longer exists or
      // has been turned into a context line isn't still selected.
      diff.hunks.forEach(h => {
        h.lines.forEach((line, index) => {
          if (line.isIncludeableLine()) {
            selectableLines.add(h.unifiedDiffStart + index)
          }
        })
      })
    }

    const newSelection =
      currentlySelectedFile.selection.withSelectableLines(selectableLines)
    const selectedFile = currentlySelectedFile.withSelection(newSelection)
    const updatedFiles = changesState.workingDirectory.files.map(f =>
      f.id === selectedFile.id ? selectedFile : f
    )
    const workingDirectory = WorkingDirectoryStatus.fromFiles(updatedFiles)

    const selection: ChangesWorkingDirectorySelection = {
      ...changesState.selection,
      diff,
    }

    this.repositoryStateCache.updateChangesState(repository, () => ({
      selection,
      workingDirectory,
    }))
    this.emitUpdate()
