### Title
Identity (point-at-infinity) public key accepted into MuSig key aggregation and `ThresholdKeys`, creating a forgeable "phantom signer" slot in n-of-n sets — ([File: crypto/dkg/musig/src/lib.rs])

### Summary
The external report concerns a validation routine (`IsIPAddress`) that enforced only the *syntactic* range of each input component while letting a semantically reserved value (`0.0.0.0`) through, breaking a security boundary. The Serai analog is `check_keys` / `musig` / `musig_key_vartime` in `crypto/dkg/musig`, which validate that the key list is non-empty, fits in `u16`, and contains no duplicate *encodings* — but never reject the point at infinity. `Ciphersuite::read_G` only checks canonicality (`crypto/ciphersuite/src/lib.rs:91-101`), and the identity encoding is canonical, so an identity key flows all the way into `ThresholdKeys::new` as a legitimate participant whose verification share is `C::G::identity()`.

### Finding Description
`check_keys` (crypto/dkg/musig/src/lib.rs:46-63) iterates keys and only enforces uniqueness of `key.to_bytes()`. Neither it, `musig_key_multiexp` (:87-98), `musig` (:116-162), nor `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) check `key.is_identity()`. For the identity participant, `verification_shares.insert(i, identity)` (:149) is stored, and the group key picks up a `binding_factor * identity = identity` term (:146,:151), i.e. the slot contributes nothing to the group key while occupying a mandatory participant index (`t = n` at :128-130).

In FROST signing over the resulting `ThresholdKeys`, that participant's per-share verification equation degenerates: `verify_share` builds statements summing to `s_l·G − R_l − c·(verification_share_l)`, and with `verification_share_l = identity` this reduces to `s_l·G == R_l`. Since the same party (or *any* party — shares for that index need no secret) also chooses the nonce commitments `D_l, E_l`, they can output `s_l = d_l + ρ_l·e_l` and pass `verify_share` with `secret_share = 0`. The `musig()` entry point even accepts `Zeroizing(C::F::ZERO)` as `private_key` (`our_pub_key = identity` matches the identity key at :121-124), confirmed usable in tests (crypto/dkg/musig/src/tests.rs:28-36).

Downstream, substrate's `musig_key` reads validator keys with `Ciphersuite::read_G` (substrate/validator-sets/primitives/src/lib.rs:136-145), which accepts identity, and the coordinator builds FROST machines over these `ThresholdKeys` via `musig(...)` (coordinator/src/tributary/signing_protocol.rs:118-121). Notably, `Curve::read_G` in FROST does reject identity (crypto/frost/src/curve/mod.rs:124-131) — so nonce commitments and signature `R` values are protected, but the key set itself is not, mirroring the "insufficient fix" shape of the report.

### Impact Explanation
Any n-of-n MuSig set containing an identity key has its effective signing threshold reduced to n−1 real participants: the identity participant's share is satisfiable by anyone with no secret and no participation. Consequences:

- A validator set configured with an identity `Public` produces a group key indistinguishable in structure from an honest set, yet signatures can be completed without the nominal nth member — `complete()` will not detect it because `verify_share` passes.
- The phantom slot is unblamable-by-omission: its share is always forgeable, so the identity-key holder can neither be required to sign nor held accountable — the set's n-of-n accountability guarantee is silently void.
- Because the identity key's contribution to the group key is `identity`, the forged share is indistinguishable from a genuine share of a zero secret; detection is impossible post-hoc.

This is a forged-signature-share / threshold-reduction vulnerability reachable purely from a public key value supplied as input to `musig`/`musig_key`/validator registration.

### Likelihood Explanation
Exploitation requires getting an identity point registered as a member key. All code paths that ingest keys (`Ciphersuite::read_G`, `musig_key`, `musig`, `check_keys`) accept it — no gate exists. Whether validator-set registration upstream rejects identity is outside the in-scope crates; the DKG/aggregation layer itself, which is the documented security boundary for rogue-key resistance, does not defend it. Once included, producing the phantom share is trivial arithmetic, not a cryptographic break.

### Recommendation
Reject the identity point wherever a public key is accepted for aggregation or share verification:

- In `check_keys` (crypto/dkg/musig/src/lib.rs:46): add `if bool::from(key.is_identity()) { Err(...) }` alongside the duplicate check.
- In `musig` (lib.rs:121): reject `private_key == 0` / `our_pub_key.is_identity()`.
- In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:361-365): while iterating `verification_shares`, also reject identity shares — this defends Lagrange-mode keys constructed via `ThresholdKeys::read` (lib.rs:620-622 reads `C::read_G`, the non-identity-rejecting variant) as well.

### Proof of Concept
```rust
// Construct a MuSig validator set where one member's key is the identity.
use dalek_ff_group::Ristretto;
use ciphersuite::Ciphersuite;
use zeroize::Zeroizing;

let mut keys = honest_pubkeys.clone();               // n-1 honest Ristretto points
keys.push(<Ristretto as Ciphersuite>::G::identity()); // "0.0.0.0" of points

// All of these succeed today:
assert!(musig_key_vartime::<Ristretto>(CONTEXT, &keys).is_ok());
let tk = musig::<Ristretto>(CONTEXT, Zeroizing::new(<Ristretto as Ciphersuite>::F::ZERO), &keys)
  .unwrap(); // claims the identity slot with secret 0

// The identity participant's verification share is identity; in FROST's
// verify_share the check degenerates to s*G == D + rho*E, satisfiable by any
// party choosing the nonce commitments — no secret needed for that index.
```

Uncertainty note: I confirmed `verify_share` in `crypto/frost` delegates to Schnorr-style `batch_statements`-shaped checks (`s·G − R − c·share`), and that `musig`/`check_keys`/`read_G` contain no identity rejection; I did not trace every upstream caller of validator-key registration to confirm whether identity `Public` values are rejected earlier in the (out-of-scope) substrate pallets.
