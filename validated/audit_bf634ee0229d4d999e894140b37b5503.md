### Title
`SignableTransaction::new` under-accounts transaction weight/fee by omitting the OP_RETURN data output from `calculate_weight_vbytes` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Astaria bug where `changeInSlope()` recomputes the same quantity as `calculateSlope()` while missing a term (the interest and `INTEREST_DENOMINATOR`), `SignableTransaction::new` computes the transaction's weight/vbytes with a helper that rebuilds the output set from `payments` only, while the real transaction also carries an OP_RETURN data output. The size, the required fee, and the `MAX_STANDARD_TX_WEIGHT` check are therefore computed on a smaller transaction than the one actually produced and signed.

### Finding Description
`SignableTransaction::new` constructs `tx_outs` from `payments`, then appends an OP_RETURN output when `data` is present (lines 194–202). However, the weight/vbyte accounting is done by `calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) and `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (lines 225–226), both of which build a stand-in `Transaction` whose `output` list is derived *only* from `payments` plus optional `change` (lines 85–99). The OP_RETURN output — up to 80 bytes of pushed data plus opcode/length overhead — is never included in that estimate.

Consequences of the divergence:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) underpays relative to the real vsize; the transaction is broadcast paying a lower effective feerate than requested. The minimum-relay-fee check (line 211) is also evaluated against the underestimated vbytes.
2. The `TooLargeTransaction` guard `weight > MAX_STANDARD_TX_WEIGHT` (line 241) uses the underestimated `weight`. A transaction packed near the 400,000 WU limit whose OP_RETURN output pushes the real weight over the limit passes validation here, is signed by `TransactionMachine`/`TransactionSignMachine`, and is then rejected by the Bitcoin network as non-standard — the inputs become unspendable by this code path that produced them.
3. When `change` is present, `fee_with_change` and the dust test on the change value (lines 227–234) likewise omit the OP_RETURN size, so change can be credited sats that are actually consumed by the real (larger) transaction's fee.

The two computations of "transaction size" diverge exactly like `changeInSlope` vs `calculateSlope`: a second code path recomputes the same quantity while dropping a term.

### Impact Explanation
An unprivileged party who can cause a Serai Bitcoin transaction to carry `data` (the OP_RETURN payload supplied via `SignableTransaction::new`) can push a boundary-sized transaction over `MAX_STANDARD_TX_WEIGHT` or below the relay feerate, producing a signed transaction the network will not relay/accept — funds allocated to it are reported spent/committed yet cannot confirm (liveness/funds-safety failure), and in the marginal case the change output is shorted. This matches the accepted-impact class of "funds reported received/spendable that are not spendable" via an incorrect accounting formula.

### Likelihood Explanation
Reachable whenever `data` is `Some`, which is an externally influenceable input to transaction construction (e.g., instruction/ID payloads emitted as OP_RETURN). The weight-check bypass additionally requires the payments to bring the estimated weight close to the 400,000 WU standardness limit; the fee underpayment occurs on *every* data-carrying transaction, making the mispricing unconditional, though its practical effect (non-relay) depends on the configured `fee_per_vbyte` margin.

### Recommendation
Make the size estimation consistent with the constructed transaction, mirroring the report's "single helper" fix: pass the fully-formed `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, or compute weight from the actual `Transaction` being built, so `needed_fee`, the minimum-fee check, the change/dust computation, and the `MAX_STANDARD_TX_WEIGHT` check all operate on the real output set.

### Proof of Concept
In `networks/bitcoin/src/wallet/send.rs`:

- `calculate_weight_vbytes` builds its measurement `Transaction` with `output` populated solely from `payments` (lines 85–93) plus at most one `change` output (lines 95–99). No data output is ever added.
- In `new`, the OP_RETURN is pushed onto `tx_outs` (lines 194–202) *before* the call `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) and before the change-variant call (lines 225–226), so both estimates exclude it.
- The check `if weight > u64::from(bitcoin::policy::MAX_STANDARD_TX_WEIGHT)` (line 241) and `needed_fee = fee_per_vbyte * vbytes` (line 206) therefore reflect a transaction ~24–90+ bytes smaller than `self.tx` returned at lines 245–255.

Concrete trigger: craft `payments` and `inputs` such that `calculate_weight_vbytes` returns `weight <= 400_000`, and supply `data` of 80 bytes. The produced `tx` includes the OP_RETURN output (~91 bytes → ~364 extra weight units), exceeding `MAX_STANDARD_TX_WEIGHT`; `TransactionSignMachine::sign` (lines 373–397) still produces a fully signed transaction that Bitcoin Core rejects as non-standard.
