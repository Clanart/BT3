### Title
Unbounded recursive decoding of nested `AccountKeyRoleBased` values allows an unauthenticated tx submitter to crash any node parsing the transaction - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively invokes `rlp.DecodeBytes` on each sub-key blob via `AccountKeySerializer.DecodeRLP`, and that sub-key can itself again be of type `AccountKeyTypeRoleBased`. There is no depth limit or composite-type check performed during decoding — the only composite-type guard (`IsCompositeType`/`CheckInstallable`/`CheckUpdatable`) runs *after* the whole structure has already been decoded. A single crafted `TxTypeAccountUpdate` (or fee-delegated variant) transaction with a deeply self-nested `AccountKeyRoleBased` value therefore drives unbounded Go-level recursion while being RLP-decoded, before any size or composite-type validation is applied.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of raw byte blobs and, for every blob, constructs a fresh `AccountKeySerializer` and calls `rlp.DecodeBytes`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type and dispatches decoding to the concrete `AccountKey` implementation via `s.Decode(serializer.key)`: [2](#0-1) 

If `serializer.keyType == AccountKeyTypeRoleBased`, `s.Decode` calls back into `AccountKeyRoleBased.DecodeRLP`, which again iterates its sub-keys and calls `rlp.DecodeBytes` for each — a self-referential recursive chain with **no depth counter, no cycle/composite-type check** at decode time.

The only defense against nested `RoleBased` keys is `checkAccountKeyZeroValues`/`CheckInstallable`, which explicitly rejects a `RoleBased` key nested inside another `RoleBased` key — but this validation happens strictly *after* decoding completes: [3](#0-2) [4](#0-3) 

The transaction decode path itself has no such check. `Transaction.DecodeRLP` and `TxInternalDataSerializer.DecodeRLP` unconditionally dispatch to the concrete tx type decoder based on attacker-controlled `txType` bytes, which for `TxTypeAccountUpdate` eventually reaches `AccountKeySerializer.DecodeRLP` for the `Key` field: [5](#0-4) [6](#0-5) [7](#0-6) 

Crucially, the tx-size check (`MaxTxDataSize`) is enforced in `TxPool.validateTx` **after** the transaction has already been RLP-decoded (both when arriving over p2p via `handleTxMsg`/`msg.Decode(&txs)`, and when submitted via RPC/`rlp.DecodeBytes`): [8](#0-7) [9](#0-8) 

So the decode-time recursion is bounded only by the p2p/RPC transport message-size limit, not by `MaxTxDataSize`, and it occurs unconditionally for every transaction that reaches a node — whether via `eth_sendRawTransaction`, `TxPool.AddRemote`, p2p tx propagation, or block/header import that includes an `AccountUpdate` transaction.

This is structurally the same bug class as the reported Trapster issue: a per-message decoder recurses once per nested "pointer" (here, once per nested `AccountKeyRoleBased` level) with no depth bound and no cycle/structure check, and the exception/overflow happens on an unauthenticated, single-message attacker-controlled input path.

### Impact Explanation
In Go, unlike Python's recoverable `RecursionError`, exceeding the runtime's maximum stack size raises a **fatal, unrecoverable runtime error** (`runtime: goroutine stack exceeds ... - fatal error: stack overflow`) that terminates the entire process — it cannot be caught by `recover()`. Because the vulnerable decode path is reached by:
- any peer broadcasting the malicious transaction over p2p (`handleTxMsg`),
- any RPC caller submitting it via `eth_sendRawTransaction`/`SendRawTransaction`,
- any node importing a block containing the malicious `AccountUpdate` transaction,

a single unauthenticated transaction can crash every full node, validator, or RPC endpoint that attempts to decode it, causing a network-wide denial of service and potential chain liveness disruption (nodes crash while trying to validate/propagate/import the poisoned tx or block). This is a stronger impact than the referenced Trapster advisory (process-fatal crash vs. a recoverable per-packet exception).

### Likelihood Explanation
Likelihood is high for any attacker capable of submitting a transaction to the network:
- No special privileges, prior state, or victim interaction required — the transaction only needs a valid RLP shape (signature validity is not required for decode-time recursion to occur, since decoding happens before `ValidateSender`/signature checks in `TxPool.validateTx`).
- No transaction-size guard exists ahead of the recursive decode; the guard (`MaxTxDataSize`) fires only after decode.
- Depth achievable is bounded only by p2p/RPC payload-size limits, which are generally megabytes — comfortably enough to reach recursion depths that exhaust default goroutine stack limits, given each nesting level requires only a handful of bytes of RLP overhead.

### Recommendation
- Add an explicit recursion-depth (or composite-type) check inside `AccountKeyRoleBased.DecodeRLP` itself (not only in the post-decode `CheckInstallable`/`CheckUpdatable` paths), rejecting any nested `AccountKeyTypeRoleBased` sub-key immediately during decode.
- Alternatively/additionally, thread a decode-depth counter through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` and bound it to a small constant (e.g., 1, since nesting is never valid).
- Enforce transaction/message size limits (`MaxTxDataSize` or a dedicated pre-decode raw-byte length check) prior to invoking `rlp.Decode`/`DecodeRLP` on any raw, network-received transaction bytes, both in the p2p handler (`handleTxMsg`) and in RPC submission paths.

### Proof of Concept
Conceptual construction (cannot be executed in this environment, but follows directly from the cited code):
1. Build an innermost valid `AccountKeyPublic` (or `AccountKeyNil`) key, RLP-encode it via `AccountKeySerializer`.
2. Wrap it in an `AccountKeyRoleBased` value containing a single sub-key slot whose stored blob is the RLP-encoding of an `AccountKeySerializer{keyType: AccountKeyTypeRoleBased, key: <previous level>}`.
3. Repeat step 2 iteratively N times (each level adds only a few bytes of RLP list/string framing overhead), producing an `N`-deep self-nested `AccountKeyRoleBased` blob within the size budget of a single p2p/RPC transaction payload.
4. Set this nested key as the `Key` field of a `TxTypeAccountUpdate` transaction (`blockchain/types/tx_internal_data_account_update.go`), RLP-encode the transaction, and submit it via `eth_sendRawTransaction` or broadcast it over the p2p `TxMsg` channel.
5. Any recipient node calls `Transaction.DecodeRLP` → `TxInternalDataSerializer.DecodeRLP` → `TxInternalDataAccountUpdate.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP`, recursing `N` times before any size (`MaxTxDataSize`) or nested-composite-type (`CheckInstallable`) check is ever reached, exhausting the goroutine stack and crashing the process with a fatal (non-recoverable) runtime error.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}

func (serializer *TxInternalDataSerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.txType); err != nil {
		// fallback to the original transaction decoding.
		txd := newEmptyTxInternalDataLegacy()
		if err := s.Decode(txd); err != nil {
			return err
		}
		serializer.txType = TxTypeLegacyTransaction
		serializer.tx = txd
		return nil
	}

	if serializer.txType == EthereumTxTypeEnvelope {
		var ethType TxType
		if err := s.Decode(&ethType); err != nil {
			return err
		}
		serializer.txType = serializer.txType<<8 | ethType
	}

	var err error
	serializer.tx, err = NewTxInternalData(serializer.txType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.tx)
}
