## Analog Identified: Stale Partial-Commit Line Selection Applied Against a Freshly Regenerated Diff

### Title
Silent Commit Content Corruption via Stale `DiffSelection` Line Indices Reapplied to a Regenerated Diff - (File: `app/src/lib/stores/updates/changes-state.ts`, `app/src/lib/git/apply.ts`, `app/src/models/diff/diff-selection.ts`)

### Summary
The Quantstamp report's root cause is a classic "two independently-tracked pieces of state can desynchronize" bug: `UltraLRT`'s vault-level bookkeeping (`delegatorAssets`/`delegatorMap`) can diverge from the delegator's actual balance when the delegator is mutated through a path that bypasses the vault's accounting update. The Desktop analog is structurally the same pattern applied to the partial-commit ("stage selected lines") feature: a user's line-level selection (`DiffSelection`, a bitset of *absolute line indices*) is preserved across working-directory refreshes purely by file-identity matching, while the actual diff content used to interpret those indices is regenerated independently and later, at commit time. If the file's on-disk content shifts between when the selection was made and when the commit is staged, the stale index bitset is blindly reapplied to a diff with a different hunk layout, so the wrong lines get staged.

### Finding Description
`updateChangedFiles` re-merges the new `git status` result with the previous working-directory state and preserves a file's `DiffSelection` purely by matching the file's `id`: [1](#0-0) 

`DiffSelection` itself stores only a `Set<number>` of *absolute diff line indices* with no binding to the actual line content or hunk boundaries — `isSelected(lineIndex)` is a pure index lookup: [2](#0-1) 

When the user actually commits, `createCommit` → `stageFiles` → `applyPatchToIndex` does **not** reuse the diff the user was looking at. It independently re-fetches a brand-new diff from disk via `getWorkingDirectoryDiff` and feeds it, together with the (possibly stale) `file.selection`, into `formatPatch`: [3](#0-2) 

`formatPatch` walks the *newly fetched* diff's hunks and, for each line, asks `file.selection.isSelected(absoluteIndex)` — reinterpreting the old numeric indices against the new hunk layout with no validation that the diff hasn't changed shape: [4](#0-3) 

This mirrors the report's broken invariant exactly: `UltraLRT` kept `delegatorAssets` as an independent ledger that could desync from the delegator's real balance when the delegator was mutated by another path (`AffineDelegator.withdraw()` called directly). Here, `DiffSelection` is an independent "ledger" of *which lines the user wants staged*, expressed as raw indices into a diff snapshot, and it can desync from the diff that is actually used to build the patch, because nothing revalidates the selection against the new diff before staging.

### Impact Explanation
If the working tree content of a file changes between the moment the user makes a partial (line-level) selection and the moment `createCommit` runs — e.g., a `post-checkout`/`post-merge` hook, a `clean`/`smudge` filter defined in `.gitattributes`, or any other content mutation triggered by routine git operations in a hostile/cloned repository — the hunk boundaries in the newly fetched diff can shift. The stale selection's line indices then point at different lines than the ones the user visually reviewed and clicked on. `formatPatch` will silently select/deselect the wrong additions and deletions, so the resulting commit (and anything later pushed) can contain content the user never intended to commit and never saw in the diff view they approved. This is precisely the "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
Exploitation requires no local/physical access, no admin rights, no pre-existing malware, and no unnatural user steps beyond Desktop's normal usage pattern: opening/using a repository with attacker-controlled `.gitattributes` filters or hooks, letting Desktop's periodic background status refresh run (`_loadStatus`, called with `clearPartialState=false` from `_refreshRepository`) while the user has a pending partial line selection, and then committing. I could not fully verify from the indexed code every call path that triggers this refresh cadence in the background (e.g., exact timers/focus handlers), so the precise timing window and its reliability are not fully confirmed from local evidence alone — this is the main remaining uncertainty.

### Recommendation
Bind `DiffSelection` (or the cached diff) to a content fingerprint (e.g., diff hash or mtime/size) of the file at the time of selection. Before applying a stored selection in `applyPatchToIndex`/`formatPatch`, verify the freshly fetched diff matches the fingerprint the selection was computed against; if it doesn't, invalidate the partial selection (fall back to `withIncludeAll(false)` as already done via the `clearPartialState` path) rather than silently reapplying mismatched indices.

### Proof of Concept
1. Attacker publishes/serves a repository containing a `.gitattributes` `clean`/`smudge` filter (or a `post-checkout`/`post-merge` hook) that deterministically appends or removes lines from a tracked file as a side effect of normal git plumbing operations.
2. Victim clones/opens the repository in Desktop and, in the Changes view, partially selects specific lines of that file for commit (`DiffSelectionType.Partial`), per [5](#0-4) .
3. Before the victim clicks "Commit", Desktop's background repository refresh runs `_loadStatus`/`updateChangedFiles`, which re-fetches status and file identity but preserves the old `DiffSelection` object by `file.id`, per [1](#0-0) . Meanwhile the filter/hook has altered the file's on-disk content, shifting hunk boundaries.
4. The victim commits. `createCommit`/`applyPatchToIndex` regenerates the diff fresh from disk and applies the stale index-based selection to it, per [3](#0-2)  and [4](#0-3) .
5. The resulting commit contains lines the victim never selected/reviewed (silent corruption of committed/pushed content), even though the Changes view appeared to show a normal, reviewed partial selection.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

  public withRangeSelection(
    from: number,
    length: number,
    selected: boolean
  ): DiffSelection {
    const computedSelectionType = this.getSelectionType()
    const to = from + length

    // Nothing for us to do here. This state is when all lines are already
    // selected and we're being asked to select more or when no lines are
    // selected and we're being asked to unselect something.
    if (typeMatchesSelection(computedSelectionType, selected)) {
      return this
    }

    if (computedSelectionType === DiffSelectionType.Partial) {
      const newDivergingLines = new Set<number>(this.divergingLines!)

      if (typeMatchesSelection(this.defaultSelectionType, selected)) {
        for (let i = from; i < to; i++) {
          newDivergingLines.delete(i)
        }
      } else {
        for (let i = from; i < to; i++) {
          // Ensure it's selectable
          if (this.isSelectable(i)) {
            newDivergingLines.add(i)
          }
        }
      }

      return new DiffSelection(
        this.defaultSelectionType,
        newDivergingLines.size === 0 ? null : newDivergingLines,
        this.selectableLines
      )
    } else {
      const newDivergingLines = new Set<number>()
      for (let i = from; i < to; i++) {
        if (this.isSelectable(i)) {
          newDivergingLines.add(i)
        }
      }

      return new DiffSelection(
        computedSelectionType,
        newDivergingLines,
        this.selectableLines
      )
    }
