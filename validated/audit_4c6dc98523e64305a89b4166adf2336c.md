### Title
OP_RETURN data output excluded from fee/weight accounting, producing transactions which underpay the fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an OP_RETURN output onto `tx_outs` when `data` is provided, but both invocations of `calculate_weight_vbytes` only reconstruct the transaction from `payments` (and optional `change`). The data output's weight is therefore never included in `vbytes`, so `needed_fee` — and the change amount derived from it — are computed as if the output didn't exist. This mirrors the Elfi bug class: a term that is unconditionally present in the final aggregate (the OP_RETURN output in the signed transaction, like `lossAmount`/`uPnL` in the pool value) is skipped by the accounting because the computation iterates a different list guarded by an incomplete condition.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` appends the OP_RETURN output to `tx_outs` at lines 194–202:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}
```

Yet the fee is computed from `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) and later `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (line 225–226), whose reconstructed `Transaction` is built solely from `payments` (lines 85–93) plus an optional change output (lines 95–99). The OP_RETURN output — up to 80 bytes of data plus ~9 bytes of output overhead, roughly 90+ weight units / ~23+ vbytes — is absent from every fee calculation.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (line 206) is underestimated.
- The minimum-relay-fee check at line 211 passes against the underestimated size, so a transaction can be constructed whose actual fee rate is below `DEFAULT_MIN_RELAY_TX_FEE` once the OP_RETURN output is included.
- The change amount `input_sat - (payment_sat + fee_with_change)` (line 228) overestimates the true leftover by the omitted output's fee contribution, so the actual fee paid (`sum(inputs) - sum(outputs)`, per `fee()` at lines 138–141) equals the underestimated `needed_fee`, not the required fee for the real transaction size.
- `weight` used for the `MAX_STANDARD_TX_WEIGHT` check (line 241) is also understated, so an oversized transaction can pass the standardness check.

### Impact Explanation
`needed_fee` is the value the signing flow (`processor/src/networks/mod.rs::prepare_send`, via `needed_fee` → amortization → `signable_transaction`) uses to decide a plan is fulfillable and to amortize fees across payments. A `SignableTransaction` produced with `data` set will commit all threshold signers to a Taproot key-spend signature over a transaction whose fee rate is lower than requested — potentially below the minimum relay fee — yielding a fully signed transaction that the Bitcoin network will not propagate. The change output is simultaneously inflated by the missing fee contribution. Because `TransactionSignMachine::sign` sighashes `Prevouts::All` plus all outputs (including the OP_RETURN), the signature is valid for exactly this under-funded transaction; the error is undetectable at signing time. This is a concrete case of producing a transaction that cannot achieve its stated goal (relay/confirmation), analogous to Elfi minting shares on a mis-stated pool value — here the "pool value" is the fee budget and the omitted term is the data output's weight.

### Likelihood Explanation
Reachable by any caller able to influence the `data` argument to `SignableTransaction::new` — i.e., a payment/withdrawal path that attaches arbitrary OP_RETURN data (the `TooMuchData` bound at line 171 explicitly permits up to 80 attacker-controlled bytes). The maximum fee omission scales with data length: 80 bytes of data plus output overhead is ~23–25 vbytes, so at any `fee_per_vbyte` the fee is short by `~24 * fee_per_vbyte` sats. When `fee_per_vbyte` is at or near the relay minimum (e.g., a quiet mempool where `median_fee` returns `Fee(1)`), the resulting transaction falls below minimum relay fee and is dropped by every relaying node. No malicious validator, leaked key, or collusion is required — only control over the data field of a transaction the multisig is asked to produce.

### Recommendation
Include the OP_RETURN output in the weight calculation. Change `calculate_weight_vbytes` to accept the full output list (or a `data: Option<&[u8]>` parameter that appends an OP_RETURN `TxOut` inside the reconstruction), and call it with the same outputs that will actually appear in `tx_outs`, at both the no-change call site (line 204) and the with-change call site (lines 225–226). General principle (matching the upstream fix): compute the fee over the complete set of outputs, not just `payments`, so no present-but-unaccounted term is skipped.

### Proof of Concept
```rust
// networks/bitcoin context: key, output obtained as in tests/wallet.rs
let inputs = vec![output];                 // e.g. 10_000 sat input
let payments = vec![(addr(), 1000)];

// Baseline: no data. needed_fee covers the full transaction.
let tx_no_data = SignableTransaction::new(inputs.clone(), &payments, None, None, 1).unwrap();

// With 80 bytes of OP_RETURN data (max allowed by TooMuchData check).
let tx_data = SignableTransaction::new(
    inputs.clone(), &payments, None, Some(vec![0u8; 80]), 1,
).unwrap();

// The data-bearing transaction is ~24 vbytes larger, yet:
assert_eq!(tx_no_data.needed_fee(), tx_data.needed_fee());
// needed_fee ignored the OP_RETURN output entirely.
// Actual fee paid equals needed_fee (inputs - outputs), so the real fee rate is
// needed_fee / actual_vsize < requested fee_per_vbyte, and with fee_per_vbyte = 1
// the TX is below DEFAULT_MIN_RELAY_TX_FEE for its true size and won't relay.
```
