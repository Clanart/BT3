### Title
Unbounded iteration over expired governance proposals in EndBlock can stall block production - (File: sei-cosmos/x/gov/abci.go)

### Summary
`gov.EndBlocker` (and its `legacyEndBlocker` fallback) iterates the *entire* inactive-proposal queue for the current block time via `keeper.IterateInactiveProposalsQueue` with **no cap on the number of proposals processed**, unlike the adjacent active-proposal tally loop which is explicitly capped by `MaxVotesProcessedPerBlock`.

### Finding Description
`MsgSubmitProposal.ValidateBasic()` only requires that the `InitialDeposit` be non-negative and "valid" coins — a zero-value deposit passes validation (confirmed by the `coinsZero` test case). `SubmitProposalWithExpedite` in `sei-cosmos/x/gov/keeper/proposal.go` does not enforce any minimum deposit at submission time either; it unconditionally creates the proposal and inserts it into the inactive (deposit-period) queue keyed by `submitTime + MaxDepositPeriod` (a fixed, governance-set constant).

Because any unprivileged account can call `MsgSubmitProposal` with a zero (or near-zero) deposit for only the price of transaction gas, an attacker can submit an arbitrarily large number of proposals across one or more blocks. Since `MaxDepositPeriod` is fixed, proposals submitted around the same time will all have (nearly) the same `DepositEndTime`, causing them to collapse into the same `EndBlock` call's inactive-queue processing window.

`EndBlocker` in `sei-cosmos/x/gov/abci.go` then walks the entire inactive-proposal queue whose deposit period has expired via an unbounded `keeper.IterateInactiveProposalsQueue` callback that always returns `false` (never stops), performing per-proposal store deletes, deposit refund/burn bookkeeping, and event emission for every single expired proposal in that block — with no upper bound analogous to `MaxVotesProcessedPerBlock` used for the active-proposal tally path just below it.

### Impact Explanation
EndBlock/FinalizeBlock work is deterministic, consensus-critical, and not gas-metered per proposal the way a single transaction is. An attacker-inflated inactive-proposal queue collapsing into a single block forces every validator to perform O(N) state deletions and event emissions synchronously during block finalization. This can materially delay block production beyond acceptable thresholds (or, at extreme N, risk node resource exhaustion/timeouts), which maps to the "block delay beyond 2.5 seconds" / validator-halt impact class.

### Likelihood Explanation
Likelihood is high in the sense that the precondition (submitting many proposals with zero/near-zero deposit) requires no special privilege — any account with enough usei to pay gas fees can do it, and it can be done from a plain `MsgSubmitProposal` transaction (also reachable via the gov EVM precompile's `submitProposal`/`submitProposalWithAuthorization` methods). The only cost is transaction gas for each submission, not deposit capital, since zero deposits are valid.

### Recommendation
Apply the same bounded work-budget pattern used for `IterateActiveProposalsQueue`/`TallyIncremental` (i.e., a `MaxVotesProcessedPerBlock`-style limit) to `IterateInactiveProposalsQueue` processing in both `EndBlocker` and `legacyEndBlocker`, so that at most a fixed number of expired/failed-deposit proposals are cleaned up per block, deferring the remainder to subsequent blocks. Additionally consider enforcing a minimum non-zero initial deposit (e.g., a small fixed floor or fee) at `MsgSubmitProposal` time to raise the cost of queue-flooding.

### Proof of Concept
1. Attacker holds a funded account with only enough usei to cover gas fees.
2. Attacker submits N (e.g., 100,000) `MsgSubmitProposal` transactions, each with `InitialDeposit = sdk.NewCoins()` (empty/zero), across blocks within the same `MaxDepositPeriod` window — each call passes `ValidateBasic` per `sei-cosmos/x/gov/types/msgs.go:90-99` and is accepted by `SubmitProposalWithExpedite` in `sei-cosmos/x/gov/keeper/proposal.go:23-79`, each inserted into `InactiveProposalQueue` keyed by `submitTime + MaxDepositPeriod`.
3. Once block time reaches the shared `DepositEndTime`, `EndBlocker`'s `keeper.IterateInactiveProposalsQueue` call in `sei-cosmos/x/gov/abci.go:39-64` must delete, log, and emit an event for all N proposals in that single `EndBlock` invocation, with no per-block cap, delaying block finalization proportionally to N.
