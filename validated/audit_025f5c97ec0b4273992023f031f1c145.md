## Finding

### Title
Residual ERC20 allowance granted to attacker-controlled contract in IBC receive-callback is never revoked after arbitrary calldata execution - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
`ContractKeeper.IBCReceivePacketCallback` mirrors the LibSwap pattern almost exactly: it grants an ERC20 `approve()` for a fixed amount to an **attacker-controlled** `contractAddress`, then executes **attacker-controlled calldata** (`cbData.Calldata`, taken from the untrusted IBC packet memo) against that same untrusted contract, and only afterward checks that the isolated address's balance of the *specific* token is zero. There is no step that clears/reverts the allowance itself, and the state produced by the approve + external call is written back to the real context (`writeFn()`) *before* the post-condition check runs. [1](#0-0) 

### Finding Description
In `IBCReceivePacketCallback`:

1. An isolated address is deterministically derived from `(destChannel, sender)` — the same sender using the same channel will always resolve to the same isolated address across many separate IBC transfers. [2](#0-1) 

2. The keeper approves the packet-sender-chosen `contractAddr` (fully attacker-controlled, taken from the packet memo `dest_callback.address`) to spend `amountInt` of the received token, on behalf of the isolated address:
```go
res, err := k.evmKeeper.CallEVM(cachedCtx, erc20.ABI, receiverHex, tokenPair.GetERC20Contract(), true, remainingGas, "approve", contractAddr, amountInt.BigInt())
``` [3](#0-2) 

3. It then executes fully attacker-controlled calldata against that same untrusted contract, with `msg.sender` set to the isolated address:
```go
res, err = k.evmKeeper.CallEVMWithData(cachedCtx, receiverHex, &contractAddr, cbData.Calldata, true, remainingGas)
``` [4](#0-3) 

4. State changes from the cached context (including the `approve`) are committed via `writeFn()` **before** the invariant check runs:
```go
writeFn()

receiverTokenBalance := k.erc20Keeper.BalanceOf(ctx, erc20.ABI, tokenPair.GetERC20Contract(), receiverHex)
if receiverTokenBalance.Cmp(big.NewInt(0)) != 0 {
    return errorsmod.Wrapf(erc20types.ErrEVMCall, "receiver has %d unrecoverable tokens after callback", receiverTokenBalance)
}
``` [5](#0-4) 

This is structurally identical to the LibSwap finding: an approval is granted to a caller-specified address, arbitrary caller-specified calldata is then executed against that address, and the code never revokes the allowance afterward (the LibSwap fix was exactly "clear the allowance after the external call"). Here the situation is worse because:
- The approved spender (`contractAddr`) and the executed calldata are **both** attacker-supplied via the untrusted IBC packet memo, with no on-chain validation of what the contract does with the allowance.
- The isolated address is **deterministic and reusable** across many IBC packets from the same `(channel, sender)` pair, so any allowance that is not driven to zero by the callback contract persists and is available to be exploited by a later, differently-crafted calldata call in a subsequent packet using the same isolated address.
- Because `writeFn()` runs before the "zero balance" invariant check, the approve (and any effects of the calldata call) are committed to the real state even in the failure path where the function subsequently returns an error — the only rollback that occurs afterward is whatever the higher-level ibc-go callbacks middleware performs on the *outer* packet-processing context, not on the effects already written from `cachedCtx` into `ctx` inside this function.

### Impact Explanation
If the callback contract's calldata does not consume the entire approved allowance (e.g., a benign integrator contract has a bug, or an attacker deliberately crafts a contract/calldata pair that leaves a nonzero allowance while still trying to satisfy or intentionally fail the zero-balance check), a standing ERC20 allowance for the token-pair-backed asset remains against the deterministic isolated address. Because the isolated address is reusable by the same sender across multiple packets/callbacks, this residual allowance can later be drained by a subsequent unrelated call (from the same attacker-controlled contract, or any other flow that can reach `transferFrom` using that allowance), resulting in unauthorized extraction of token-pair-backed value that was intended only for the specific packet's callback. This matches the "unauthorized extraction of ... token-pair-backed balances" impact class.

### Likelihood Explanation
The IBC packet sender (an unprivileged, potentially malicious counterparty-chain actor) fully controls both the callback `contractAddress` and `cbData.Calldata` via the transfer packet's memo field, and no code path revokes the allowance to zero after the calldata call completes (successfully or not). Reaching this state does not require any privileged access — only crafting an ICS-20 transfer with a `dest_callback` memo pointing to an attacker-deployed contract. The main uncertainty is exactly how much of the state written by `writeFn()` is retained by the outer ibc-go v10 callbacks middleware if this function subsequently returns a non-nil error — this depends on ibc-go internal transaction/branching semantics that were not fully traceable within the available index, so the exact persistence guarantee of the leftover allowance in the error path is not fully confirmed.

### Recommendation
- After the calldata call to `contractAddr` completes (success or failure), explicitly reset the ERC20 allowance from the isolated address to `contractAddr` back to zero (`approve(contractAddr, 0)`), mirroring the LibSwap fix.
- Perform the zero-balance invariant check (and the allowance-zeroing step) *before* calling `writeFn()`, or perform both operations within the same cached context that is only committed once all invariants are confirmed, so that no approval/side effect is persisted unless the callback fully satisfies its contract.
- Consider deriving isolated addresses per-packet (e.g., including sequence number) rather than solely per `(channel, sender)`, to prevent allowance/state reuse across unrelated packets from the same sender.

### Proof of Concept
Conceptual PoC (exact confirmation of the commit/rollback boundary at the ibc-go middleware layer would require running the flow, which was not possible in this review):
1. Attacker controls a counterparty chain account `sender` and channel `destChannel`; the isolated address `isoAddr = GenerateIsolatedAddress(destChannel, sender)` is deterministic and known in advance.
2. Attacker deploys `EvilCallback` at `contractAddr` on the destination EVM chain.
3. Attacker sends an ICS-20 transfer of token `X`, amount `A`, with memo `{"dest_callback":{"address":"<contractAddr>",...}}` and calldata `D1` such that `EvilCallback` calls `transferFrom(isoAddr, attacker, A)` — this passes the zero-balance check as designed, but `EvilCallback`'s logic could instead call `transferFrom(isoAddr, attacker, A-1)` while otherwise causing the top-level check to still observe zero balance through unrelated means (e.g., by also burning or forwarding the last unit elsewhere it controls), leaving a residual allowance of `1` unit — or more generally, leaves any nonzero allowance while the transaction as a whole is still considered by the outer processing to have succeeded/committed.
4. In a later, unrelated ICS-20 packet from the same `sender`/`destChannel` (reusing the same `isoAddr`), the attacker's `contractAddr` still holds the previously granted allowance and can call `transferFrom` again to pull additional token `X` balance that legitimately belongs to the isolated address from that later packet, without a fresh, matching `approve` call being required.
