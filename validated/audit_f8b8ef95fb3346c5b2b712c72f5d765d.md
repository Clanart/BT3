### Title
Multi-token reward claim can be permanently DOS'd by a single blacklisting/reverting reward token — ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2.getReward`/`getRewards` loop over all registered `rewardTokens` and call `_sendReward`, which performs a bare `IERC20(_rewardToken).safeTransfer(_receiver, _amount)` with no try/catch and no code-length/failure isolation. If any single reward token in the loop reverts on transfer (e.g., a blacklist-capable token like USDC blacklists the receiver, or the token is paused/self-destructed), the entire claim transaction reverts, blocking the user from claiming **all** other legitimate reward tokens as well as their MGP reward in the same call.

### Finding Description
`_sendReward` in `BaseRewardPoolV2.sol` directly transfers reward tokens without any error isolation: [1](#0-0) 

This is called in a loop for every registered reward token inside `getReward`/`getRewards`: [2](#0-1) 

These functions are reachable from `MasterMagpie._claimBaseRewarder`, invoked from the user-facing claim flow (`_multiClaim`), which also bundles the user's MGP reward payout in the same transaction: [3](#0-2) [4](#0-3) 

Unlike the reference report's `VaultRewarderLib.sol` (which at least wraps the transfer in `try/catch` to isolate per-token failures, only missing the codesize check for the self-destruct edge case), `BaseRewardPoolV2._sendReward` has **no failure isolation at all**. Any revert from a single reward token's `transfer` (blacklist, pause, insufficient allowance/implementation quirks, or a self-destructed token with empty code) bubbles up and reverts the whole claim call, including the unrelated MGP payout and any other healthy reward tokens bundled in the same `_multiClaim`/`getReward(s)` invocation. The same unprotected pattern also exists in `mWOMSVBaseRewarder._sendReward` and `vlMGPBaseRewarder._sendReward`. [5](#0-4) [6](#0-5) 

Reward tokens are registered without restriction on their token type (any manager-approved token can be a common stablecoin like USDC, which has an admin-independent blacklist feature affecting arbitrary receivers) — this is not a malicious-admin scenario, since the failure trigger (a third-party token issuer blacklisting an address, or the token becoming non-functional) is an external condition unrelated to any privileged actor within this protocol.

### Impact Explanation
Because `userRewards[rewardToken][_account]` is zeroed out at the start of `_sendReward` before the transfer occurs, once the transaction reverts nothing is actually zeroed on-chain (the whole tx reverts), so no direct fund loss occurs on that attempt — but the user is permanently unable to claim **any** of their rewards (including MGP) through the normal claim path for as long as the problematic reward token continues to fail, since `getReward`/`getRewards` always iterate over the full `rewardTokens` array. This is a permanent freezing of the user's unclaimed yield/rewards until the token is somehow fixed (which for a self-destructed or externally blacklisted token can be indefinite), satisfying the "permanent freezing of unclaimed yield" bar.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires a specific reward token behavior (blacklist-style tokens like USDC/USDT freezing a specific receiver, a paused ERC20, or a self-destructed token) among the pool's registered reward tokens. This mirrors the exact "external condition/specific state" scenario that Sherlock judged as Medium in the referenced report, since such tokens (e.g., USDC) are commonly used as reward/bribe tokens in DeFi protocols.

### Recommendation
Wrap each reward token transfer in `_sendReward` (in `BaseRewardPoolV2.sol`, `mWOMSVBaseRewarder.sol`, and `vlMGPBaseRewarder.sol`) in a `try/catch`, and additionally check `rewardToken.code.length > 0` before attempting the call, so that a failure or removal of code for one reward token does not prevent the claim/accounting of the other reward tokens or the base MGP payout in the same transaction. On failure, emit an event to signal the failed transfer instead of reverting, similar to the pattern shown in the reference report.

### Proof of Concept
1. Manager registers a reward token `T` (e.g., a USDC-like blacklistable token) via `queueNewRewards` on a `BaseRewardPoolV2` instance used by a pool that a victim user has staked in.
2. `T`'s issuer blacklists the victim's `_receiver` address (an action entirely external to this protocol, e.g., regulatory compliance action on USDC) — no privileged action on this protocol is required.
3. Victim calls the claim path that eventually invokes `MasterMagpie._multiClaim` → `_claimBaseRewarder` → `IBaseRewardPool(rewarder).getReward(_account, _receiver)`.
4. Inside `getReward`, the loop reaches reward token `T` and calls `_sendReward`, which calls `IERC20(T).safeTransfer(_receiver, amount)`; this reverts because the receiver is blacklisted.
5. The entire `getReward` call reverts, which reverts the entire `_multiClaim` transaction — the victim cannot claim MGP or any other healthy reward token bundled in the call, and this remains true for every future claim attempt as long as `T` keeps reverting for that receiver.

                vlMGPPoolAmount += claimableMgp;

                mWOmPoolAmount += claimableMgp;
            } else {
                defaultPoolAmount += claimableMgp;

        }
