## Analog Identified: Silent Swallowing of ERC20-Conversion Failure Permanently Strands Refunded IBC Coins in the `x/erc20` Module Account

The reported bug class — an owner-controlled function that can silently divert user funds without proper safety checks — maps onto a Cosmos EVM analog in `x/erc20`'s IBC-refund-to-ERC20 conversion path, where a failed internal step is masked as success, permanently stranding user coins in a module account that has no withdrawal path back to the user.

### Title
Silent error-swallowing in `ConvertCoinToERC20FromPacket`/`ConvertCoinNativeERC20` permanently strands refunded IBC coins in the `erc20` module account - (File: `x/erc20/keeper/ibc_callbacks.go`, `x/erc20/keeper/msg_server.go`)

### Summary
`ConvertCoinNativeERC20` escrows the user's Cosmos coin into the `erc20` module account **before** attempting to move the corresponding ERC20 balance via an EVM call, and only burns the escrowed coin if the EVM call succeeds. When invoked from the IBC timeout/error-acknowledgement path (`ConvertCoinToERC20FromPacket`), any failure of that EVM call is caught, logged as an event, and the function returns `nil` — meaning the enclosing Cosmos SDK message (`MsgTimeout`/`MsgAcknowledgement`) is treated as **successful**, so the already-executed escrow of the user's refunded coin is never rolled back and never re-unescrowed.

### Finding Description
`ConvertCoinNativeERC20` performs the conversion in this order:
1. `SendCoinsFromAccountToModule` — escrow the Cosmos coin from `sender` into the `erc20` module account.
2. `CallEVM(... "transfer" ...)` — attempt to move ERC20 balance from the module's EVM address to the `receiver`.
3. Only if (2) succeeds and balance checks pass, `BurnCoins` the escrowed amount. [1](#0-0) 

If step (2) fails (e.g., `CallEVM` returns an error because the registered ERC20 contract reverts, is paused, blacklists the receiver, or has any other conditional revert logic), the function returns the error **without unwinding step (1)**: [2](#0-1) 

This function is invoked both from the normal `MsgConvertCoin` handler (where a returned error causes the whole Cosmos transaction to abort atomically, so no state actually persists) and from the IBC refund path `ConvertCoinToERC20FromPacket`, used by both `OnAcknowledgementPacket` (error-ack) and `OnTimeoutPacket`: [3](#0-2) 

Critically, in `ConvertCoinToERC20FromPacket`, a failure from `ConvertCoinNativeERC20` is caught and converted into a **successful** `nil` return, only emitting a `EventTypeFailedConvertERC20` event: [4](#0-3)

Because this function returns `nil`, the surrounding IBC message-processing transaction (delivering the timeout/ack packet) is treated by the SDK as fully successful, and the already-applied `SendCoinsFromAccountToModule` state mutation (step 1) is **not rolled back**. The function's own doc-comment claims "the user receives the corresponding bank token from the TokenPair instead," but that is only true if the escrow step had not already executed — which it has, by the time the EVM call fails. The net effect: the user's refunded IBC coin is moved into the `erc20` module account and left there permanently, with no burn, no re-credit to the user, and no governance or user-facing recovery mechanism to un-escrow it.

### Impact Explanation
This is a Critical, unauthorized-permanent-freezing-of-user-funds bug: coins that IBC's transfer module already refunded to the user upon timeout/error-ack are silently re-escrowed into the `erc20` module account and never returned, burned, or otherwise accounted for. The user has no way to reclaim them through any exposed message or precompile. Because the party controlling the native ERC20 contract registered in the `TokenPair` (which, depending on `PermissionlessRegistration`, may be any user) fully controls when `transfer` reverts (via pausability, blacklists, or other conditional logic in their own contract), a malicious or buggy token-pair owner can deterministically trigger this failure path against any counterparty using their token pair for IBC transfers, permanently trapping refunded escrow value belonging to unprivileged users — directly matching the "permanent freezing/locking of escrowed assets" allowed impact.

### Likelihood Explanation
Likelihood is high in any deployment allowing permissionless native ERC20 registration (`PermissionlessRegistration` param) combined with normal IBC usage: (1) attacker registers a native ERC20 with a pausable/blacklistable `transfer`, (2) a victim initiates an ICS20 transfer of the paired coin, (3) attacker pauses/blacklists at the moment of timeout or error-ack, (4) `ConvertCoinNativeERC20`'s EVM call reverts, (5) the coin is escrowed but never unescrowed, and the outer call returns success, permanently stranding the victim's refunded balance. No validator, governance, or admin privilege is required — this is triggerable purely through ordinary user transaction/IBC flow.

### Recommendation
`ConvertCoinToERC20FromPacket` should never allow a partial state change to persist when the conversion fails. Wrap the call to `ConvertCoinNativeERC20` in a cached/branched context (`ctx.CacheContext()`), and only commit (`write()`) if the entire conversion (escrow + EVM transfer + burn) succeeds; otherwise discard all state changes so the user's coin remains in their own account exactly as before the failed conversion attempt, consistent with the function's documented intended behavior.

### Proof of Concept
1. Enable `PermissionlessRegistration` (or use governance) to register a custom ERC20 contract `EvilToken` as a native ERC20 `TokenPair`, where `EvilToken.transfer` can be made to revert conditionally by the deployer (e.g., a `paused` flag or blacklist mapping toggle).
2. A victim converts native coin to `EvilToken` ERC20 balance and initiates an ICS20 transfer of the corresponding Cosmos coin to another chain.
3. The deployer pauses/blacklists `EvilToken` transfers.
4. The IBC packet times out (or the receiving chain returns an error acknowledgement).
5. `OnTimeoutPacket`/`OnAcknowledgementPacket` invoke `ConvertCoinToERC20FromPacket`, which refunds the coin to the victim via the transfer module, then attempts `ConvertCoinNativeERC20`: the coin is escrowed into the `erc20` module account, then `CallEVM("transfer", ...)` reverts due to the pause/blacklist.
6. `ConvertCoinNativeERC20` returns an error; `ConvertCoinToERC20FromPacket` catches it, emits `EventTypeFailedConvertERC20`, and returns `nil`.
7. The IBC timeout/ack transaction commits successfully. Verify on-chain: the victim's coin balance for that denom is now zero, the `erc20` module account holds the escrowed amount, and the victim's ERC20 balance for `EvilToken` was never restored — the funds are permanently stuck with no available user-facing recovery message. func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

// ConvertCoinToERC20FromPacket converts the IBC coin to ERC20 after refunding the sender
// This function is only executed when IBC timeout or an Error ACK happens.
func (k Keeper) ConvertCoinToERC20FromPacket(ctx sdk.Context, data transfertypes.FungibleTokenPacketData) error {
	// Sender is local (source) chain address; accept local bech32 or 0x-hex
	senderBz, err := k.addrCodec.StringToBytes(data.Sender)
	if err != nil {
		return err
	}
	sender := sdk.AccAddress(senderBz)

	pairID := k.GetTokenPairID(ctx, data.Denom)
	pair, found := k.GetTokenPair(ctx, pairID)
	if !found {
		// no-op, token pair is not registered
		return nil
	}

	coin := ibc.GetSentCoin(data.Denom, data.Amount)

	switch {

	// Case 1. if pair is native coin -> no-op
	case pair.IsNativeCoin():
		// no-op, received coin is a  native coin
		return nil

	// Case 2. if pair is native ERC20 -> unescrow
	case pair.IsNativeERC20():
		// use a zero gas config to avoid extra costs for the relayers
		ctx = ctx.
			WithKVGasConfig(storetypes.GasConfig{}).
			WithTransientKVGasConfig(storetypes.GasConfig{})

		params := k.GetParams(ctx)
		if !params.EnableErc20 || !k.IsDenomRegistered(ctx, coin.Denom) {
			// no-op, ERC20s are disabled or the denom is not registered
			return nil
		}

		// assume that all module accounts on Cosmos EVM need to have their tokens in the
		// IBC representation as opposed to ERC20
		senderAcc := k.accountKeeper.GetAccount(ctx, sender)
		if types.IsModuleAccount(senderAcc) {
			return nil
		}

		// Convert from Coin to ERC20
		if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(sender), sender); err != nil {
			// We want to record only the failed attempt to reconvert the coins during IBC.
			defer func() {
				telemetry.IncrCounter(1, types.ModuleName, "ibc", "error", "total")
			}()
			ctx.EventManager().EmitEvents(
				sdk.Events{
					sdk.NewEvent(
						types.EventTypeFailedConvertERC20,
						sdk.NewAttribute(types.AttributeCoinSourceChannel, pair.Denom),
						sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
						sdk.NewAttribute("error", err.Error()),
					),
				},
			)
			return nil
		}
