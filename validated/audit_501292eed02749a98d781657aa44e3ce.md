### Title
Payout tx's OP_RETURN operator-attribution is unauthenticated, letting anyone reassign reimbursement credit before confirmation — (`core/src/operator.rs`, `core/src/builder/transaction/operator_reimburse.rs`, `core/src/verifier.rs`)

### Summary
The user's payout signature only commits to input 0 and output 0 via `TapSighashType::SinglePlusAnyoneCanPay`; the OP_RETURN output naming the fronting operator (`output[2]`) is never covered. Because `Verifier::update_finalized_payouts` credits reimbursement eligibility purely from the OP_RETURN bytes of whichever transaction ends up mined spending the withdrawal UTXO, anyone who observes the honest operator's unconfirmed Payout tx can, before confirmation, replace it via RBF with a variant that keeps input 0 and output 0 identical (so the signature still verifies) but swaps the OP_RETURN to name a different, non-paying operator.

### Finding Description
Binding claimed and verified broken: `operator_credited_and_reimbursed(i) == operator_whose_funds_paid_output_0(i)`.

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the Payout tx with outputs `[0]=user payout, [1]=anchor, [2]=OP_RETURN(operator_xonly_pk)`.
- `Operator::withdraw` (`core/src/operator.rs:620-637`) verifies the user's signature only over input 0 / output 0 with `SinglePlusAnyoneCanPay`: [1](#0-0) 
- The operator then calls `fund_raw_transaction` with `add_inputs: true`, `replaceable: None` (defaults to wallet RBF-enabled) and `change_position: Some(1)`, meaning the honest operator's own wallet funds must cover the shortfall between the (dust) input 0 and the (large) output 0 value: [2](#0-1) 
- Because the sighash type is `SIGHASH_SINGLE | ANYONECANPAY`, the signature only binds input 0's own outpoint/amount/scriptPubKey and the output at the same index (output 0). It places **no constraint** on any other input or output, including the OP_RETURN at output 2. This is confirmed by `calculate_pubkey_spend_sighash`'s `Prevouts::One` handling for this sighash type: [3](#0-2) 
- An unprivileged attacker who observes the honest operator's broadcast mempool tx can copy input 0 (with its witness, satisfying signature verification) and output 0 verbatim into a new transaction, add their own funding inputs to cover output 0's value and a higher fee, and replace output 2's OP_RETURN with a *different* registered operator's xonly_pk. Since the original tx signaled RBF (bitcoind default `walletrbf=true`), a higher-fee conflicting tx is a valid BIP125 replacement and can be mined instead of the honest operator's version.
- Once mined, `Verifier::update_finalized_payouts` reads whichever tx actually spent the withdrawal UTXO and extracts the operator xonly_pk purely from its OP_RETURN, with no check of who funded the tx: [4](#0-3) 
- This is persisted via `update_payout_txs_and_payer_operator_xonly_pk` into `withdrawals.payout_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`), and later consumed by `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`), which the `PayoutCheckerTask` (`core/src/task/payout_checker.rs:39-79`) uses to invoke `Operator::handle_finalized_payout` for the named operator.
- The only anti-fraud check, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`), verifies that the kickoff's `operator_xonly_pk` matches the DB's `payout_payer_operator_xonly_pk` and that the committed blockhash matches — it never verifies that the named operator's own funds paid for output 0. Therefore an operator named via a maliciously rewritten OP_RETURN passes this check and is legitimately routed into the reimbursement flow (`Reimburse`/`ReimburseInKickoff`) for a withdrawal it never funded.

None of the listed guards (`is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, `is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`) check that the L1 funds actually came from the credited operator's wallet — they only check tx/OP_RETURN consistency, which the attacker fully controls for the winning transaction.

### Impact Explanation
- The falsely-named operator (`O_other`) becomes eligible for `Reimburse`, receiving `bridge_amount` from the deposit's move-to-vault reimbursement chain despite never fronting any L1 funds for that withdrawal — matching the Critical category "an operator reimbursed for a payout it never funded."
- The honest operator (`O_honest`), whose broadcast was replaced, permanently loses the ability to claim reimbursement for this withdrawal, since `withdrawals.idx` is a primary key and only one payout/operator attribution is recorded per withdrawal index — matching "an honest operator permanently unable to be reimbursed."
- The attack is repeatable per withdrawal that is broadcast but not yet finalized, and does not depend on which operator is targeted, so the blast radius spans any operator set and any withdrawal in flight.

### Likelihood Explanation
- No privileged role, key share, collateral, or TLS cert is needed — only the ability to observe the Bitcoin mempool/network and broadcast a competing RBF transaction, both of which are explicitly in-scope for an unprivileged attacker.
- Preconditions: a withdrawal index registered on Citrea; an operator broadcasting (not yet confirmed) a Payout tx with default wallet RBF signaling (`replaceable: None` defers to wallet default, which is RBF-enabled).
- Cost: the attacker must supply additional inputs covering the full output-0 value (near the withdrawal amount) plus a fee bump, since the signature fixes output 0 and input 0 but nothing else. This is a real capital cost, not free, but it is a pure BTC/fee cost with no need for protocol privileges — feasible for any sufficiently funded party, and the funds are recoverable in the sense they go to pay the legitimate user (not burned), so the attack's "cost" is capital lockup/loss risk, not consumption. Feasibility is bounded only by having liquid BTC and mempool visibility, and is fully repeatable across withdrawals/operators.

### Recommendation
Bind the OP_RETURN operator attribution to the signature. Options:
1. Have the user's signature cover all outputs (e.g., switch to `SIGHASH_ALL` or a covenant that commits to the full output set) so the operator identity cannot be swapped post-broadcast.
2. Alternatively, require the operator's own signature/commitment (separate from the user's) over the OP_RETURN output content, and have `update_finalized_payouts`/`is_kickoff_malicious` cross-check that the additional inputs funding output 0 are attributable to (i.e., signed/owned by) the credited operator, not merely that OP_RETURN names them.
3. As a mitigation, disable third-party RBF replacement eligibility for Payout transactions where feasible (e.g., don't signal opt-in RBF, or use presigned anti-fee-sniping/anchor outputs that require the operator's own key to bump fees), forcing any fee-bump/replacement to originate from the operator's own wallet.

### Proof of Concept
```
cargo test path: core/src/test/... (new test)

1. Set up two registered operators O_honest and O_other (already part of the operator/verifier set from `create_actors`), and a single withdrawal index i with a signed user payout (SinglePlusAnyoneCanPay over input0/output0), as in `generate_withdrawal_transaction_and_signature`.
2. Have O_honest call `withdraw` to build+broadcast its Payout tx (funded via `fund_raw_transaction`, RBF-enabled), but do NOT mine it.
3. Construct an attacker transaction: same input0 (with same witness copied from O_honest's broadcast tx) and output0 (byte-identical), add attacker-owned inputs sufficient to cover the output0 value plus a higher fee, and set output2's OP_RETURN to O_other's xonly_pk instead of O_honest's. Broadcast via `rpc.send_raw_transaction`.
4. Mine the block; assert the attacker's tx (not O_honest's) is the one confirmed spending the withdrawal UTXO.
5. Run the block sync path so `Verifier::update_finalized_payouts` processes the block, then assert via `db.get_payout_info_from_move_txid` that `payout_payer_operator_xonly_pk == O_other.xonly_pk` (not O_honest).
6. Assert `db.get_first_unhandled_payout_by_operator_xonly_pk(O_other.xonly_pk)` returns withdrawal i.
7. Run `PayoutCheckerTask`/`handle_finalized_payout` for O_other and assert it succeeds, producing a kickoff for O_other, and `mark_payout_handled` attributes handling to O_other — proving O_other becomes reimbursement-eligible for a payout it never funded, while O_honest's `get_first_unhandled_payout_by_operator_xonly_pk(O_honest.xonly_pk)` returns `None` for this withdrawal.
```
