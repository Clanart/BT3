I traced the external "stateless proxy trusts unverified balance" bug class to an Aptos analog in the package-verification tooling: the `aptos move verify-package` command claims to verify that on-chain code matches locally-built source, but its implementation never actually compares bytecode.

### Title
`aptos move verify-package` never compares on-chain module bytecode, so it falsely certifies deployed code as verified - (File: `aptos-move/cli/src/stored_package.rs`, `aptos-move/cli/src/commands.rs`)

### Summary
The Aptos CLI's `verify-package` subcommand is documented and marketed as downloading a package "and verifies the bytecode matches a local compilation of the Move code". In practice, `VerifyPackage::execute` fetches the on-chain `PackageRegistry` with `with_bytecode: false`, and the comparison routine `CachedPackageMetadata::verify()` only diffs self-reported `PackageMetadata` fields (name, deps, `ModuleMetadata` structs containing gzip source/source_map, manifest, upgrade_policy, source_digest, extension) — never the actual deployed module bytecode. Because none of these compared fields are independently derived from or checked against the real bytecode by the Move VM at publish time, a package can be published with metadata/source that looks legitimate while the actual executable bytecode differs arbitrarily, and `verify-package` will still report success.

### Finding Description
`VerifyPackage::execute` in [1](#0-0)  builds the package locally, extracts its metadata, then calls:
```
let registry = CachedPackageRegistry::create(client, self.account, false).await?;
...
package.verify(&compiled_metadata)?;
```
The `false` argument to `CachedPackageRegistry::create` disables bytecode download entirely [2](#0-1) .

`CachedPackageMetadata::verify()` then compares `name`, `deps`, `modules`, `manifest`, `upgrade_policy`, `extension`, and `source_digest` between the locally-built metadata and the on-chain `PackageMetadata` [3](#0-2) . None of these fields is the module bytecode: `ModuleMetadata` only carries `name`, gzip-compressed `source`, `source_map`, and `extension` — never bytecode bytes or a bytecode hash [4](#0-3) . `source_digest` itself is documented as a hash of the *source text*, not the bytecode [5](#0-4) .

Critically, at publish time the Move VM's `validate_publish_request` only checks that the compiled module names match the `expected_modules` declared in metadata and validates dependency/native constraints — it never checks that `ModuleMetadata.source` (or any other metadata field) is the actual source that compiles to the submitted bytecode [6](#0-5) . The `source`/`manifest`/`source_digest` fields are entirely publisher-supplied and unconstrained relative to the bytecode.

Combining these two facts: (1) publish-time validation never ties metadata to actual bytecode, and (2) `verify-package` never fetches or compares actual bytecode — the tool's core claimed guarantee ("verifies the bytecode matches a local compilation") is not implemented. `DownloadPackage` does support fetching bytecode via `--bytecode`/`get_bytecode()` [7](#0-6) , and `CachedPackageRegistry` even keeps a `bytecode: BTreeMap<String, Vec<u8>>` field for this purpose [8](#0-7) , but `verify()` simply never touches it.

### Impact Explanation
This is a code-safety/publish-verification invariant violation matching the "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" impact category. Any downstream consumer (auditor, dependency resolver such as `AptosPackageHooks::resolve_custom_dependency` in [9](#0-8) , or a user manually running `aptos move verify-package` before trusting a deployed contract) can be misled into believing the running on-chain bytecode is exactly what the published/reviewed source compiles to, when in fact a completely different (malicious or backdoored) bytecode blob is executing at that address. Since Aptos package dependencies and code-object trust decisions rely on this exact "verified" signal (e.g., the CLI package-download/dependency-resolution flow calls `get_package`/`save_package_to_disk` from the same untrusted metadata), this can lead to users building on top of, or depending on, code that is not what was represented, undermining code-safety guarantees for permissionless publish/upgrade flows.

### Likelihood Explanation
No privileged access is required — any account can publish a package with metadata whose `source`/`manifest`/`source_digest` correspond to an innocuous or previously-audited module while shipping different bytecode in the same transaction, since the VM never cross-validates them. Anyone relying on `aptos move verify-package` (the documented tool for exactly this purpose, see `third_party/move/documentation/book/src/cli-deploy.md` lines 70-83) would be silently misled every time, making this a systematic (not edge-case) gap in the verification tooling.

### Recommendation
Update `VerifyPackage::execute` to call `CachedPackageRegistry::create` with `with_bytecode: true`, and extend `CachedPackageMetadata::verify()` to additionally recompile the local package to bytecode and byte-for-byte compare each module's bytecode against `registry.get_bytecode(module_name)`, failing verification on any mismatch. This closes the gap between the tool's documented guarantee and its actual behavior.

### Proof of Concept
1. Compile a benign package locally (e.g. a simple `m::f()`), and separately hand-craft a `CompiledModule` bytecode blob with the same module name/signature but hidden malicious logic (e.g. draining a resource in an entry function not present in the visible source).
2. Publish using `code::publish_package_txn` with `PackageMetadata.modules[0].source` set to the benign source text but `code` (the actual bytecode bundle) set to the malicious bytecode — the VM's `validate_publish_request` only checks module names against `expected_modules`, not source-bytecode correspondence [10](#0-9) , so this succeeds.
3. Run `aptos move verify-package --account <addr>` pointing at the benign local source. Because `CachedPackageRegistry::create(client, account, false)` never downloads bytecode [11](#0-10)  and `verify()` never compares it [3](#0-2) , the command prints `"Successfully verified source of package"` even though the deployed bytecode is malicious.
