### Title
Unauthenticated `ReceivedOutput` deserialization accepts outputs outside the scanner allowlist - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes a scalar offset, `TxOut`, and `OutPoint` without checking that the output’s `script_pubkey` belongs to the `Scanner`’s registered script set or that the supplied offset is the one registered for that script. This is analogous to an incomplete disallowed-input list: the trusted path enforces an allowlist, but the deserialization path bypasses it.

### Finding Description
`Scanner` maintains an explicit allowlist of acceptable Taproot scripts in `scripts: HashMap<ScriptBuf, Scalar>` and `scan_transaction` only reports outputs whose `output.script_pubkey` is present in that map [1](#0-0) . `register_offset` additionally warns that arbitrary offsets may introduce a script path, allowing an output to be spent by satisfying a script rather than by the key signature [2](#0-1) . Despite those constraints, `ReceivedOutput::read` accepts `Secp256k1::read_F`, a consensus-decoded `TxOut`, and a consensus-decoded `OutPoint`, then returns `Ok(ReceivedOutput)` with no script, offset, or scanner binding [3](#0-2) . The returned object exposes `offset()`, `output()`, `outpoint()`, and `value()` as if it were a scanned spendable output [4](#0-3) .

### Impact Explanation
An attacker who can supply bytes to `ReceivedOutput::read` can inject an output that was never produced by `Scanner::scan_transaction`, including an output paying to an unregistered script, using an offset not associated with that script, or referencing a non-existent/immature outpoint. Downstream code receiving the deserialized object is given a struct that represents “a spendable output” [5](#0-4)  even though the security-critical allowlist check in `scan_transaction` was never applied [6](#0-5) . This can cause funds to be reported as received when they are not spendable by the threshold key, or cause wallet logic to attempt spending an invalid output.

### Likelihood Explanation
The vulnerable path is reachable wherever serialized `ReceivedOutput` values are accepted from storage, messages, or other untrusted input and then consumed as scanner results. The bypass is deterministic: the parser returns `Ok` for any syntactically valid scalar, `TxOut`, and `OutPoint`. The practical impact depends on whether callers treat deserialized `ReceivedOutput`s as authenticated scan results; the type itself provides no field distinguishing scanned outputs from deserialized assertions.

### Recommendation
Do not expose `ReceivedOutput::read` as an authentication boundary. Either make deserialization private to trusted storage, or require the `Scanner`/registered script context during decoding and reject inputs whose `TxOut.script_pubkey` is absent from `scripts` or whose supplied offset differs from `scripts[script_pubkey]`. For stronger binding, persist and verify the scan provenance (txid/block context and maturity status) rather than trusting an attacker-controlled `OutPoint`.

### Proof of Concept
Conceptually, the malicious input is:

```text
canonical_scalar ||
consensus_encoded_TxOut { value, script_pubkey = attacker_script } ||
consensus_encoded_OutPoint { txid = attacker_chosen, vout }
```

Feeding these bytes to `ReceivedOutput::read` reaches `Ok(ReceivedOutput { offset, output, outpoint })` without evaluating `attacker_script` against `Scanner.scripts` [7](#0-6) . By contrast, the same `TxOut` passed through `Scanner::scan_transaction` is ignored unless `self.scripts.get(&output.script_pubkey)` succeeds [6](#0-5) . The discrepancy demonstrates the incomplete input policy: the allowlist exists on the scan path but is absent on the public deserialization path.
