### Title
`GeneratorPromotion::complete` panics on a malformed-but-correctly-sized proof map — DoS via untrusted participant input - (File: crypto/dkg/promote/src/lib.rs)

### Summary
Analogous to CVE-2024-47522 (invalid attacker-controlled input aborts the process), `GeneratorPromotion::complete` in `crypto/dkg/promote/src/lib.rs` trusts that a `HashMap<Participant, GeneratorProof>` of length `n - 1` contains every required participant index. It only rejects keys `> n`, then unconditionally unwraps `proofs.get(&i)` for each `i in 1..=n`. A remote participant can supply a proof set with the correct length that substitutes an extraneous in-range key (including the caller's own index `params.i()`) for a missing required one, causing an `unwrap()` on `None` and aborting the host process.

### Finding Description
At `crypto/dkg/promote/src/lib.rs:125-136`, `complete` checks `proofs.len() == n - 1` and rejects only keys `> n`. It then iterates `i in 1..=n`, skipping `params.i()`, and executes `proofs.get(&i).unwrap()` at line 146:

```rust
let proof = proofs.get(&i).unwrap();
``` [1](#0-0) 

The length check guarantees count, not membership. For `n = 4`, `i = 1`, an attacker-provided map keyed by `{1, 2, 3}` (including the caller's own index, which is never rejected) passes both checks, yet `proofs.get(&Participant(4))` returns `None` and panics. `Participant` values and `GeneratorProof`s are deserialized from peer messages via `GeneratorProof::read` (`crypto/dkg/promote/src/lib.rs:72-77`), so the map contents are fully attacker-controlled; the keyset is the attacker-influenced portion.

### Impact Explanation
A single malicious or misbehaving participant in a generator-promotion round can crash every other participant's process by submitting a well-formed-looking proof map of the right size with the wrong membership. Because the panic escapes `complete`'s `Result`-based API, callers cannot gracefully attribute fault — the promotion session aborts mid-protocol. This is a remotely triggerable denial of service (availability loss of the threshold node), matching the bug class of the reference report.

### Likelihood Explanation
Triggering requires only that the attacker be one of the `n` DKG participants whose `GeneratorProof` map entries are fed to `complete`. No cryptographic break, timing, or collusion is needed — just a wrong key in a correctly-sized map. In Serai's validator sets, participants are exactly the parties the protocol is designed to not trust individually, so this is a realistic adversary.

### Recommendation
Validate membership, not just count: check `proofs.keys()` equals the expected set `1..=n` minus `params.i()` (or that it does not contain `params.i()` and has no missing required index) before indexing, and return `PromotionError::InvalidParticipant`/`IncorrectAmountOfParticipants` instead of unwrapping. Replace `proofs.get(&i).unwrap()` with `.get(&i).ok_or(PromotionError::InvalidParticipant { n: params.n(), participant: i })?` so the malformed-input path is an error, not a panic.

### Proof of Concept
```rust
// n = 4, our participant index = 1
let mut proofs = HashMap::new();
// Insert proofs keyed by our own index and two others, omitting participant 4
proofs.insert(Participant::new(1).unwrap(), proof_a); // our own i — never rejected
proofs.insert(Participant::new(2).unwrap(), proof_b);
proofs.insert(Participant::new(3).unwrap(), proof_c);
// proofs.len() == 3 == n - 1: passes length check
// All keys <= n: passes range check
// complete() then does proofs.get(&Participant(4)).unwrap() -> panic
promoting.complete(&proofs);
```
