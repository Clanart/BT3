### Title
Desktop silently rewrites a trusted git remote to whatever the GitHub API reports for owner/name, without validating the underlying repository identity - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
GitHub Desktop periodically "refreshes" the GitHub metadata associated with a local repository (e.g. on account refresh/sign-in, foreground activation, etc.) via `repositoryWithRefreshedGitHubRepository`. This flow looks up the local `origin` remote, re-resolves it against GitHub's API by **owner login + repository name text**, and — if the API's `clone_url` differs from the remote currently configured — **automatically rewrites the user's local git remote URL** with `git remote set-url`, with no user confirmation and no verification that the repository being pointed to is the *same* repository (by immutable id) as before.

### Finding Description
The refresh path is: [1](#0-0) 

1. `matchGitHubRepository` re-derives `owner`/`name` purely by parsing the **current local remote URL string** against the hostname of a signed-in account — it does not consult any previously stored, immutable repository id: [2](#0-1) 

2. The resolved `owner`/`name` pair is sent straight to `api.fetchRepository(owner, name)`, and whatever `IAPIFullRepository` comes back is trusted as "the same repository, possibly renamed": [3](#0-2) 

3. `updateRemoteUrl` then decides whether to auto-rewrite the local `origin` remote. Its only checks are: (a) the git URL protocol didn't change, and (b) the *previous* remote URL still textually matched the previously cached `gitHubRepository.cloneURL`: [4](#0-3) 

None of these checks compare the API response's persistent repository identity (`id`/`node_id`) against the `dbID` stored for the existing `GitHubRepository` record. Identity is tracked purely by `ownerID + name` in the local Dexie database as well: [5](#0-4) 

This mirrors the audited pattern exactly: `AirdropFactory.sol` updated a "locker" reference in one place (`AirdropList`) without propagating/validating identity in the dependent contract (`Airdrop.sol`'s `parentAirdropData`), so a changed locker silently broke or hijacked fund flow. Here, Desktop's `RepositoriesStore`/`GitStore` caches a "trusted" `origin` remote for a `GitHubRepository`, but when the API is asked to re-resolve `owner/name`, nothing ties the answer back to the original `dbID`/repository identity — the code implicitly assumes "same owner+name string" means "same repository," which is not guaranteed on GitHub. GitHub is well known to allow repository/owner-name recycling: once a repository is renamed/transferred or a user/org renames their login, the old `owner/name` combination becomes claimable by an unrelated third party (a documented "repo-jacking"/redirect-chain risk). If an attacker claims the now-freed `owner/name` slot and stands up their own repository there, the next Desktop refresh cycle will:
- Call `api.fetchRepository(owner, name)` and receive the **attacker's** repository data (different `id`, different `clone_url` if attacker uses a different final destination such as after a further rename or an org transfer chain).
- Because the *old* local remote URL still textually matched the previously cached `cloneURL` (the app never detected the underlying repo changed), `remoteUrlUnchanged` is `true`.
- Since the new `clone_url` differs and protocol matches, Desktop calls `gitStore.setRemoteURL(...)`, silently repointing the user's `origin` remote at the attacker-controlled destination — with no dialog, no diff, no confirmation.

### Impact Explanation
This is a silent corruption of what the user pushes to and pulls from. Once `origin` is rewritten:
- Future `git push` operations from Desktop will send the user's commits/branches to a repository the attacker controls, potentially exposing private code, or the attacker can accept/merge nothing while just harvesting pushed history.
- Future `git pull`/`fetch` will bring in attacker-controlled commits/tags that a user may believe originate from the legitimate upstream, since Desktop shows repository metadata (PRs, checks, branch protection) sourced from the same, now-attacker-owned, API-resolved `GitHubRepository`.
- Credentials: the trampoline credential helper resolves credentials by matching the `origin` URL/host, so subsequent authenticated operations will still use the legitimate account's token against the now-different remote target, since GitHub.com is still the host — the attacker doesn't need to phish credentials, they just need Desktop to trust their squatted repo.

This satisfies the "silent corruption of what the user commits/pushes" impact category without requiring local access, admin rights, or social engineering beyond passively claiming a freed GitHub `owner/name` slot.

### Likelihood Explanation
Requires: (1) a user has previously cloned/tracked a repository with Desktop such that `gitHubRepository.cloneURL` was cached, and (2) the original `owner/name` combination subsequently becomes available for a third party to claim on GitHub (via account rename, repository rename, org deletion, etc. — well documented in GitHub's own "repository namesquatting" advisories affecting many third-party integrations). Desktop's periodic refresh (`refreshSelectedRepositoryAfterAccountChange`, called on account/sign-in changes and other background repository refresh paths) means the vulnerable code path executes without any explicit user action. The existing guards (`protocolsMatch`, `remoteUrlUnchanged`, `urlsMatch`) are all textual/string-based and do not stop this path because none of them look at repository identity (`id`).

### Recommendation
- When refreshing GitHub metadata for a repository, verify the fetched `apiRepo.id` (or `node_id`) matches the persisted `GitHubRepository.dbID`'s underlying remote `id` before treating the API response as "the same repository, possibly renamed."
- If the ids differ, treat it as a *new* repository association candidate requiring explicit user confirmation (similar to how a fork conversion (`_convertRepositoryToFork`) is an explicit, user-initiated action) rather than silently calling `updateRemoteUrl`/`setRemoteURL`.
- Persist and check the original repository id fetched at initial association time so a "the underlying repository behind this owner/name has changed" case can be detected and surfaced to the user instead of auto-applied.

### Proof of Concept
1. User A owns and Desktop-tracks `github.com/alice/project` (origin remote = `https://github.com/alice/project`); Desktop caches `GitHubRepository.cloneURL = https://github.com/alice/project` with `dbID = 100`, matching remote API id `12345`.
2. Alice renames her GitHub account to `alice2` (freeing the `alice` login) or otherwise the `alice/project` slot becomes available (e.g., repo deleted).
3. Attacker registers the `alice` login (or otherwise reclaims the slot) and creates a new public repository named `project` — same URL string `https://github.com/alice/project`, but a different underlying API `id` (e.g., `99999`) and potentially with the repository set up to redirect `clone_url` elsewhere via a further rename chain, producing a different `clone_url` than the cached one.
4. On the victim's next Desktop refresh cycle (`repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` → `api.fetchRepository('alice','project')`), Desktop receives the attacker's repo data.
5. `updateRemoteUrl` sees `remoteUrlUnchanged === true` (old cache still equalled old remote) and `urlsMatch === false` if the attacker's `clone_url` differs (e.g. attacker further transferred the repo), and silently calls `gitStore.setRemoteURL('origin', <attacker clone_url>)`, repointing the victim's local `origin` without any prompt.   private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
