### Title
Aggregator's "Internal"-only gRPC methods are reachable by any unauthenticated caller because the Aggregator server does not enforce client certificates - (File: core/src/servers.rs, core/src/rpc/interceptors.rs)

### Summary
The bug class from the external report — a security control that exists in the code but is never wired up so that the party who is supposed to invoke it actually can, while everyone else is blocked — has a concrete analog in Clementine's RPC authorization model. Instead of OpenZeppelin's `Pausable`, Clementine uses an mTLS certificate interceptor (`Interceptors::OnlyAggregatorAndSelf`) that is supposed to restrict any RPC method whose name is prefixed `Internal` to be callable only by the entity's own client certificate. This gate, however, is explicitly not applied to the Aggregator's own gRPC server.

### Finding Description
The authorization logic lives in `only_aggregator_and_self`, which treats any gRPC method whose name starts with `"Internal"` as self-only: [1](#0-0) [2](#0-1) 

This interceptor is only installed when `config.client_verification` is `true`; otherwise the server is wired with `Interceptors::Noop`, which passes every request through unchecked: [3](#0-2) 

The project's own documentation states this is intentional for the Aggregator: "The aggregator does not enforce client certificates but does use TLS for encryption," while for the Verifier/Operator, "Internal methods can only be called by the entity's own client certificate": [4](#0-3) 

`create_aggregator_grpc_server` builds the Aggregator's `ClementineAggregatorServer` through the very same `create_grpc_server` path used for verifiers/operators, so it inherits the same `Noop`-when-unverified behavior instead of any Aggregator-specific gate: [5](#0-4) 

The `ClementineAggregator` service exposes multiple methods with the `Internal` prefix that are meant to be self-only per the naming convention used everywhere else in the codebase (e.g. `InternalSendTx`, which broadcasts a Bitcoin transaction, and `InternalGetEmergencyStopTx`, which produces an emergency-stop transaction): [6](#0-5) [7](#0-6) 

Because the Aggregator does not enforce client certificates, there is no code path in this repository that restricts these `Internal*` Aggregator methods to the aggregator process itself — the `is_internal()` check that would otherwise catch them is never reached (`Noop` interceptor).

The equality this breaks: "the caller reaching a signing or state-changing/broadcasting method" should equal "the party the method is meant for" (the aggregator's own internal process, per the `Internal` naming convention enforced everywhere else). On the public-facing Aggregator server, `attacker calling InternalSendTx` == `true`, even though `attacker == intended caller` is `false`.

### Impact Explanation
`InternalSendTx` accepts a `SendTxRequest` and broadcasts the transaction, and `InternalGetEmergencyStopTx` builds an emergency-stop transaction; both are state-changing/broadcasting operations reachable without any authentication when the Aggregator is deployed per its own documented, intended configuration (client verification not enforced). This directly matches the "unauthenticated state-changing or broadcasting call" category, which is explicitly called out as High impact. An unauthenticated attacker who can reach the Aggregator's gRPC port could invoke these internal-only surfaces meant exclusively for the aggregator's own automation.

### Likelihood Explanation
This is not a hypothetical misconfiguration to be excluded — it is the documented, default operating mode of the Aggregator ("The aggregator does not enforce client certificates"). Any deployment following the project's own documentation exposes these `Internal*` methods to the open network without further authentication, since no other authorization check exists on the Aggregator service for these RPCs.

### Recommendation
Apply an aggregator-specific interceptor that always rejects calls to methods whose gRPC method name starts with `Internal` unless they originate from the aggregator process itself (e.g., loopback/unix-socket-only binding, or a local shared secret), independent of the `client_verification` TLS setting used for public-facing methods like `NewDeposit`/`Withdraw`.

### Proof of Concept
1. Deploy the Aggregator per the documented configuration (`client_verification` not enforced for the Aggregator, as stated in `docs/usage.md`).
2. From an unauthenticated network client (no client certificate needed since the Aggregator interceptor is `Noop`), call `ClementineAggregator/InternalSendTx` with an attacker-chosen `SendTxRequest`.
3. Because `only_aggregator_and_self`'s `is_internal()` gate is never invoked (no `OnlyAggregatorAndSelf` interceptor is installed for the Aggregator), the request reaches `internal_send_tx` and the transaction is broadcast, confirming the method — intended to be self-only like every other `Internal*` RPC in the codebase — is reachable by any caller.

fn is_internal(req: &Request<()>) -> bool {
    // This normally doesn't exist but we add it in the AddMethodMiddleware
    let Some(path) = req.metadata().get("grpc-method") else {
        // No grpc method? this should not happen
        tracing::error!("Missing grpc-method header in request");
        return false;
    };
    path.as_bytes().starts_with(b"Internal")
}

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}

## RPC Authentication

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities
and to authenticate clients. Client certificates are verified and filtered by
the verifier/operator to ensure that:

1. Verifier/Operator methods can only be called by the aggregator (using
   aggregator's client certificate `aggregator_cert_path`)
2. Internal methods can only be called by the entity's own client certificate
   (using the entity's client certificate `client_cert_path`)
