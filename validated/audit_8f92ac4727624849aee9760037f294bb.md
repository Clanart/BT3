## Finding Confirmed

The attack path is valid: `on_accept` mutates custody state (mint/transfer to beneficiary) *before* validating the optional calldata against `BaseCallFilter`, and `pallet-ismp` core's receipt handling makes this partial-state failure exploitable for repeated/duplicate settlement, not merely a stuck receipt.

### Title
Custody funds are moved before `BaseCallFilter` validation in `on_accept`, and failed calls cause receipt deletion that enables replay-driven duplicate settlement — (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`HyperFungibleToken::on_accept` mints/transfers the bridged amount to the beneficiary at [1](#0-0)  before it decodes and validates any attached calldata's `RuntimeCall` against `BaseCallFilter::contains` at [2](#0-1) . If the call is filtered, `on_accept` returns `Err(HftError::CallFiltered)` after the balance mutation has already been committed.

### Finding Description
The ISMP core request handler in `pallet-ismp`/`modules/ismp/core` stores a request receipt *before* invoking the module callback, then explicitly deletes it if the callback errors: [3](#0-2) 

Critically, the enclosing `handle()` function always returns `Ok(MessageResult::Request { .. })` at the top level regardless of whether an individual request's `on_accept` failed [4](#0-3) . This means the surrounding extrinsic (e.g., `handle_unsigned`) does **not** itself return an error, so FRAME's automatic per-extrinsic storage rollback never triggers. The only compensating action taken by the core is the explicit `delete_request_receipt` call — there is no rollback of whatever storage mutations the module already performed (mint/transfer to beneficiary).

The project's own documentation confirms this is a known module responsibility, not something the framework protects against: [5](#0-4) 

`HftError::CallFiltered` at [6](#0-5)  is exactly the kind of post-mutation error this warning describes: the pallet violates the "maintain invariants before modifying state" rule by minting/transferring first and validating the call filter second.

Because the request receipt is deleted after such a failure, the *same* `PostRequest` (same commitment) is no longer recognized as processed by `host.request_receipt()`, and can be resubmitted by any relayer holding the original valid membership proof (a standard, unprivileged, permissionless action in the ISMP protocol — not "malicious infrastructure"). Each resubmission re-runs `on_accept`, remints/re-transfers the same amount to the beneficiary, and fails again at the same `BaseCallFilter` check, deleting the receipt again — an unbounded loop of duplicate settlement for a single locked/burned source-chain amount.

### Impact Explanation
An attacker who controls the `call_data` field of their own cross-chain transfer (or crafts calldata targeting an arbitrary `RuntimeCall` known to be filtered, e.g., during `SafeMode`/maintenance, or targeting `CollatorSelection::leave_intent`-style filtered calls as shown in [7](#0-6) ) can guarantee that `on_accept` mutates custody state and then errors deterministically. Each replay of the same request commitment duplicates the minted/transferred amount to the beneficiary while the source chain's escrowed/burned funds correspond to only a single transfer — resulting in unbounded fund duplication far beyond the originally locked amount. This matches "stealing or loss of funds" / "duplicate settlement."

### Likelihood Explanation
High. The trigger only requires an unprivileged sender to attach calldata containing any `RuntimeCall` variant blocked by the runtime's `BaseCallFilter`, then have any relayer (not necessarily malicious — this is the expected permissionless mechanism) submit/resubmit the request with the valid proof. No privileged operator or compromised infrastructure is required; the replay works simply because the deleted receipt makes the request indistinguishable from an un-processed one.

### Recommendation
Reorder `on_accept` so all validation (including `BaseCallFilter::contains` and calldata decode/signature checks) happens strictly before any custody-affecting mutation (mint/transfer). Alternatively/additionally, wrap the entire `on_accept` body in a storage transaction (`frame_support::storage::with_transaction`) so that any `Err` return atomically reverts all storage writes made during that call, consistent with the invariant the protocol documentation already assumes modules uphold.

### Proof of Concept
1. Register an asset and pair it with a destination contract as in the existing test setup [8](#0-7) .
2. Construct a `Message` whose `data` field encodes `SubstrateCalldata` with a `runtime_call` that decodes to a call blocked by `BaseCallFilter` (e.g. `CollatorSelection::leave_intent`).
3. Call `module.on_accept(post.clone())` — observe the beneficiary balance increases (mint/transfer succeeds) then the call returns `Err(HftError::CallFiltered)`.
4. Confirm via `pallet-ismp` core that `delete_request_receipt` removed the receipt for this commitment (per `modules/ismp/core/src/handlers/request.rs` lines 122-125).
5. Call `module.on_accept(post.clone())` again with the identical `PostRequest` — since no receipt exists, it is not rejected as a duplicate, and the beneficiary balance increases a second time from the same source-chain-locked amount, demonstrating duplicate settlement.
