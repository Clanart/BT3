## Title
Spoofed `WWW-Authenticate` realm header from a malicious git remote/proxy tricks Desktop into launching a trusted GitHub Enterprise sign-in flow against an attacker-controlled host - (`File: app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Sherlock finding's broken invariant is: a value that is meant to be provisional/attacker-influenceable (the UMA oracle's first-pass answer) is treated as authoritative via an `OR` check, instead of requiring the value from the actual trusted final authority (the neg-risk operator). The Desktop analog is `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts`, which classifies a git remote host as `'enterprise'` (a trusted first-party GitHub host) based on a `WWW-Authenticate` header value that is fully controlled by the remote server Desktop is talking to, rather than any cryptographic or pre-registered trust anchor.

### Finding Description
`getEndpointKind` decides how a credential request from git should be handled: [1](#0-0) 

```
for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
```

This "happy path" for detecting GitHub Enterprise hosts is explicitly documented as a shortcut to avoid a network probe: [2](#0-1) 

The `cred` map, including the `wwwauth[]` entries, is populated from Git's credential-helper protocol, which in turn is populated from the HTTP response headers returned by whatever remote (or a malicious HTTP proxy/MITM the URL points to) the user is fetching/pushing/cloning against. An attacker who controls the git remote (e.g., a repository hosted on an attacker's own server that the user is told to add/clone/fetch/push to) can simply respond to the credential negotiation with `WWW-Authenticate: Basic realm="GitHub"`. That is enough to make `getEndpointKind` return `'enterprise'` instead of `'generic'`, even though the actual host has nothing to do with github.com or any registered GHE instance.

In `getCredential`, once `endpointKind !== 'generic'` and no matching stored account exists for that host, Desktop calls: [3](#0-2) 

`ui.promptForGitHubSignIn(endpoint)` is invoked with `endpoint` set to the attacker's own host. That function then does: [4](#0-3) 

Because `hostname !== 'github.com'`, this calls `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` with `origin` being the attacker-controlled host, launching the full "Sign in to GitHub Enterprise" popup/browser OAuth flow pointed at that attacker origin (`SignInStore.setEndpoint` → `getEnterpriseAPIURL` → `getOAuthAuthorizationURL`), just as if it were a real GHE instance the user manages.

Just like the Sherlock bug — where a provisional/interim signal from an unreliable party (UMA oracle answer, which can still be overridden by the neg-risk operator) is trusted as if it were the final determination — here a value fully supplied by the untrusted remote party (`WWW-Authenticate` realm string) is trusted as if it were proof the host is a legitimate first-party GitHub endpoint, without any registration, TLS pinning, or actual `/meta` API confirmation. The `isGitHubHost(endpoint)` API-probe fallback (which does perform a legitimate check) is only reached when there's no `wwwauth[]` header at all, i.e. the spoofable path is checked and returns *before* the safe path.

### Impact Explanation
This is triggerable by any unprivileged remote server the user's Desktop client talks to (a hostile git host, a compromised/attacker-run mirror, or a MITM proxy on an insecure network) — matching the "attacker controls...a git remote/proxy response" criterion. The impact:
- The user is presented with GitHub Desktop's native "Sign in to GitHub Enterprise" dialog while actually being directed to authenticate against an attacker-controlled origin, which can serve a convincing enterprise-login-look-alike page and harvest credentials or an OAuth `code`/token flow tailored to look legitimate because it's initiated by Desktop itself rather than a suspicious external link (`beginEnterpriseSignIn` + `setSignInEndpoint`).
- Because the flow is triggered transparently as part of a normal git fetch/push credential negotiation, the user did not click a phishing link — Desktop itself decided the remote "looks like GitHub" and initiated the sign-in UI, increasing user trust in the prompt (classic unauthorized account-binding / phishing-amplification primitive).
- This can also serve as a building block for account confusion: if the user has an existing GHE account whose endpoint happens to collide in some edge case, or if the user is tricked into re-entering enterprise credentials, that materially satisfies "unauthorized OAuth or account binding."

### Likelihood Explanation
Likelihood is high for any user who adds/clones/pushes to a repository under attacker control (a common social/dev workflow, e.g. contributing to a fork, or being handed a "please clone this internal repo" URL) since the only requirement is that the server return a crafted `WWW-Authenticate` header during git's credential negotiation — trivially controlled by any HTTP server implementation. No admin rights, local access, or pre-existing compromise is required.

### Recommendation
Do not classify a host as `'enterprise'`/trusted based solely on the self-reported `WWW-Authenticate` realm string from the remote. Either:
- Always fall back to the authoritative `isGitHubHost(endpoint)` API probe (the same check already used as the final fallback) instead of trusting the `realm="GitHub"` shortcut, or
- Require the realm-based classification to still be corroborated by the `isGitHubHost` probe before invoking `promptForGitHubSignIn`, so that a spoofed header alone cannot trigger the GitHub Enterprise sign-in UI for an arbitrary attacker-controlled origin.

### Proof of Concept
1. Attacker stands up an HTTP git server at `https://attacker.example/evil.git` and configures it to respond to unauthenticated Git HTTP requests with `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote (or clones it) in GitHub Desktop and performs a fetch/push.
3. Git invokes Desktop's credential helper (`createCredentialHelperTrampolineHandler` → `getCredential`), which calls `getEndpointKind`; the `wwwauth[]` loop matches `realm="GitHub"` and returns `'enterprise'` for `attacker.example`. [3](#0-2) 
4. Since no account exists for `attacker.example`, `ui.promptForGitHubSignIn('https://attacker.example')` is called, and Desktop opens its native "Sign in to GitHub Enterprise" dialog pointed at `attacker.example`. [4](#0-3) 
5. The victim, believing this is a legitimate Desktop-initiated GHE sign-in (not an external phishing link), proceeds to authenticate, sending credentials/OAuth flow data to the attacker's origin.

Note: I was not able to fully trace every downstream branch of `SignInStore.setEndpoint`/enterprise validation (e.g., whether `validateURL` or the enterprise TLS/HTTPS requirement would add friction) within the indexed portion of the codebase, so the exact UX friction the victim would see before submitting credentials should be verified by a background agent with full repo access.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
