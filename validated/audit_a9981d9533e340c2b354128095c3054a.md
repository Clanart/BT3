### Title
Case-sensitive `knownHooks` allow-list bypass causes native (unintercepted) hook execution with leaked trampoline credential-helper environment - ([File: app/src/lib/hooks/get-repo-hooks.ts])

### Summary
`getRepoHooks` filters candidate hook filenames against a hard-coded, all-lowercase `knownHooks` array using exact, case-sensitive `Array.includes` comparison at [3](#0-2) . On case-insensitive filesystems (default on Windows and macOS), a repository-controlled hook file named with different casing (e.g. `Pre-Commit`) will still be resolved and executed by git's own hook lookup, but is silently skipped by this filter, since `hookName` is taken verbatim from `readdir` via `basename(file.name, '.exe')` at [4](#0-3)  without any case normalization.

### Finding Description
`withHooksEnv` only overrides `core.hooksPath` (redirecting git to the sandboxed/intercepting proxy directory) when `getRepoHooks` yields at least one recognized hook name: `if (hooks.length === 0) { return fn(opts?.env) }` at [5](#0-4) . If the only hook present in the repository's real hooks directory has a case-variant name that fails the exact-match check, `hooks` is empty and Desktop makes no attempt to intercept: it calls `fn(opts?.env)` unmodified, leaving `core.hooksPath` pointed at the repository's real (attacker-influenced) hooks directory.

Git itself performs hook lookup on the filesystem's native semantics, so on a case-insensitive filesystem a hook literally named `Pre-Commit` is found and executed by git for the canonical hook `pre-commit`, even though Desktop's own allow-list check rejected the name. This produces exactly the interception/reality divergence described: `hooks-proxy.ts` never gets a chance to run the hook through its sandboxed proxy, so none of its protections apply — most importantly the environment sanitization performed in `hooks-proxy.ts`, which strips sensitive variables (`GIT_CONFIG_PARAMETERS`, `GIT_ASKPASS`, `GIT_SSH_COMMAND`, `GIT_USER_AGENT`, `GIT_SYSTEM_CONFIG`, `GIT_EXEC_PATH`, `GIT_TEMPLATE_DIR`) before spawning a hook, per `excludedEnvVars` and the `safeEnv` filter at [6](#0-5)  and [7](#0-6) .

When the hook instead runs natively (because interception never engaged), it inherits the full environment that `withTrampolineEnv` sets up for the enclosing git command — including `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, `GIT_CONFIG_PARAMETERS` configuring `credential.helper=desktop`, `GIT_USER_AGENT`, and SSH environment variables — as constructed in [8](#0-7) . A malicious hook script can read `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from its own environment and connect directly to the local trampoline server socket. The server validates commands solely by token equality (`isValidTrampolineToken`) with no additional binding to the git subprocess or hook context, and dispatches to registered handlers (credential fill, SSH passphrase, etc.) per [9](#0-8) . This lets the malicious hook impersonate git's own credential-helper trampoline for the duration of the current operation and retrieve the credentials git would have used for that remote operation.

### Impact Explanation
If exploitable, this allows a hook that Desktop believes is "not a real/known hook" (and therefore doesn't intercept) to nonetheless execute via real git, with full access to Desktop's internal trampoline token/port that the interception path deliberately strips out. Using that token, the hook can query the trampoline server for the current operation's git credentials, resulting in credential exfiltration originating purely from cloned/fetched repository content (an attacker-controlled hooks directory) — matching the "credential/token exfiltration" impact category.

### Likelihood Explanation
This requires: (1) the target repository to have `interceptHooks` enabled for the git operation in question, (2) the repository/hooks directory containing only a case-variant (or otherwise not-exact-string-matching but filesystem-resolvable) hook name so `hooks.length === 0`, (3) the user's OS using a case-insensitive filesystem (default on Windows/macOS), and (4) the hook file being executable (or, on Windows, any file — since Desktop assumes any valid name is executable there, but the name still must be filesystem-resolvable as the real hook by git). The environment/token leak also depends on git's hook execution actually inheriting the process environment set up by `withTrampolineEnv`, which is consistent with git's normal hook-invocation semantics (child processes inherit the parent's environment) but was not directly re-verified beyond reading the source that constructs and passes this environment through `IGitExecutionOptions`/dugite. Because hook execution normally requires the repository to be cloned/checked out and a corresponding git command run (e.g., commit, push, pull, merge — wherever `interceptHooks` is passed, per `app/src/lib/git/commit.ts`, `push.ts`, `pull.ts`, `merge.ts`), this is reachable purely from repository content without additional user action beyond routine git operations in Desktop.

### Recommendation
Normalize/compare hook names against `knownHooks` case-insensitively (and reject or flag whitespace/alternate-stream variants) in `getRepoHooks`, so that any filesystem-resolvable variant of a known hook name is recognized and routed through interception rather than silently ignored. Additionally, consider treating "any file present in the hooks directory" as requiring interception (redirecting `core.hooksPath` even when 0 recognized hooks are found, but zero hooks are copied into the proxy dir) so that git never has an active `core.hooksPath` pointing at an attacker-influenced directory during operations where interception was intended.

### Proof of Concept
1. Configure a git operation (e.g. commit) with `interceptHooks` enabled and hook interception feature flag on.
2. Have a repository whose `.git/hooks` directory (or `core.hooksPath` target) contains a single executable file named `Pre-Commit` (case-variant of `pre-commit`), tested on a case-insensitive filesystem (default macOS APFS / Windows NTFS).
3. Observe that `getRepoHooks` yields no hooks because `knownHooks.includes('Pre-Commit')` is `false` — [3](#0-2)  — so `withHooksEnv` never overrides `core.hooksPath` — [5](#0-4) .
4. Confirm git still executes `Pre-Commit` natively (case-insensitive lookup resolves it as `pre-commit`), and that the hook process's environment contains `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` (which would have been stripped had interception engaged, since they don't match the `GIT_`/`GITHEAD_` `safePrefixes` filter in `hooks-proxy.ts`).
5. From within the hook, connect to `127.0.0.1:$DESKTOP_PORT` and issue a trampoline command using `$DESKTOP_TRAMPOLINE_TOKEN`, demonstrating that the token is accepted by `TrampolineServer.processCommand` and the credential-fill handler responds — [2](#0-1) .
