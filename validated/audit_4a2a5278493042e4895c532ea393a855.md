### Title
Unchecked slice access in `IsGzip`/`IsWasm` causes a panic (node crash) on short CosmWasm code payloads - (File: sei-wasmd/x/wasm/ioutils/utils.go)

### Summary
`IsGzip` and `IsWasm` in [1](#0-0)  slice their `input []byte` argument (`input[:3]` / `input[:4]`) without first checking `len(input)`. In Go, slicing beyond the length of a slice panics with `slice bounds out of range`. This is the direct Go analog of the reported graphviz bug class: a crafted/short file (here, wasm bytecode payload) is loaded and immediately triggers a memory-bounds fault in a low-level "sniff the format" routine (`lib/common/shapes.c` in graphviz vs. `ioutils.IsGzip`/`IsWasm` here) before any validation of the actual content occurs.

### Finding Description
`IsGzip` performs `bytes.Equal(input[:3], gzipIdent)` and `IsWasm` performs `bytes.Equal(input[:4], wasmIdent)` with no length guard. Any caller that passes fewer than 3 (or 4) bytes as `input` will cause an immediate Go runtime panic (index/slice out-of-range), not a handled error. This mirrors the CVE's root cause class — a fixed-size magic-byte/header read performed on attacker-supplied file/byte content without validating that the buffer is large enough, causing memory-safety failure at parse time rather than a graceful validation error.

These helpers are used across the codebase (per `grep_search` matches) in the wasm CLI/REST tx paths, `precompiles/wasmd/wasmd.go` and its `legacy/v*` copies, `x/evm/keeper/msg_server.go`, and `evmrpc/simulate.go` / `evmrpc/send.go` — i.e., code-path candidates that decide whether uploaded CosmWasm bytecode is gzip-compressed or a raw wasm binary before further processing (store-code flows reachable by ordinary CosmWasm/precompile users). Because these entry points accept externally supplied byte payloads (contract bytecode from an `MsgStoreCode`-equivalent call, or via the `wasmd` precompile invoked from an EVM transaction), a caller can supply a payload shorter than 3–4 bytes (including empty) to reach `IsGzip`/`IsWasm` before any length validation happens.

I was not able to fully trace, within the available iterations, the exact call site and its surrounding validation order in `precompiles/wasmd/wasmd.go`, `x/evm/keeper/msg_server.go`, and `evmrpc/simulate.go`/`evmrpc/send.go` to confirm whether a length check is performed by the caller immediately before invoking `IsGzip`/`IsWasm` in every one of these paths (my tool budget was exhausted before I could open and read those call sites). This uncertainty matters: if every call site already validates `len(payload) >= 4` (or larger, e.g. minimum wasm module size) before calling `IsGzip`/`IsWasm`, the panic is unreachable from external input and this would not be exploitable. Given the pattern shows up consistently unguarded in the function itself (the safety burden is pushed onto callers, and the doc comments give no such warning), and given the same helper is reused by many legacy precompile versions, this is a plausible but not fully confirmed reachable panic.

### Impact Explanation
If reachable with attacker-controlled length (e.g., via `MsgStoreCode`, the `wasmd` precompile's store-code method, or the JSON-RPC `eth_call`/`eth_sendRawTransaction` simulation path in `evmrpc/simulate.go`/`send.go`), an unprivileged CosmWasm user or EVM transaction sender could submit a store-code message with a bytecode payload of 0–3 bytes, causing a Go panic. Depending on where the panic is caught (module-level `recover()` in the wasm keeper/ante handler vs. an uncaught panic that reaches the top of the ABCI message-processing loop), the result ranges from a single failed transaction to a validator node crash/consensus halt if the panic escapes recovery during block processing — which would satisfy the "crash of default-configuration node" / "validator halt" impact bar.

### Likelihood Explanation
Likelihood is speculative without confirming call-site validation. `IsGzip`/`IsWasm` are called from many precompile version directories and from CLI/REST tooling, suggesting broad reuse of an unguarded helper, which increases the chance that at least one reachable call site lacks a preceding length check. However, without confirming the actual invocation order at `precompiles/wasmd/wasmd.go`, `x/evm/keeper/msg_server.go`, and `evmrpc/simulate.go`, this cannot be asserted as definitively exploitable from a live transaction today.

### Recommendation
Add explicit length checks at the top of both functions before slicing, e.g.:
```go
func IsGzip(input []byte) bool {
    if len(input) < 3 {
        return false
    }
    return bytes.Equal(input[:3], gzipIdent)
}

func IsWasm(input []byte) bool {
    if len(input) < 4 {
        return false
    }
    return bytes.Equal(input[:4], wasmIdent)
}
```
This makes the format-sniffing helpers safe regardless of caller discipline, removing reliance on every current and future call site independently enforcing a minimum length.

### Proof of Concept
Not independently verified end-to-end due to inability to confirm the exact reachable entry point within the remaining tool budget. Conceptually: submit a CosmWasm `MsgStoreCode` (or invoke the `wasmd` precompile's store-code method from an EVM transaction, or call `evmrpc`'s simulate/send path) with a `WASMByteCode`/bytecode field of length 0–2 bytes. If the call path reaches `ioutils.IsGzip`/`IsWasm` without a preceding length check, the node will panic with a slice-bounds-out-of-range runtime error while processing that transaction/RPC request.
