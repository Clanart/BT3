## Title
Path-confinement bypass via missing separator check in `resolveWithin()` allows deep-link-triggered access outside the intended repository directory - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is Desktop's core sandboxing primitive: every caller that needs to safely join an untrusted, attacker-influenced relative path onto a trusted root (a repository directory) relies on it to guarantee the result cannot escape that root. The confinement check is a plain string `startsWith()` comparison with no path-separator boundary check, so a resolved path that is a *sibling* directory whose name happens to have the root directory's name as a prefix (e.g. `/Users/victim/repo-secrets` vs root `/Users/victim/repo`) is incorrectly accepted as "inside" the root. This is structurally identical to the reported smart-contract bug class: a boundary validation that checks the wrong edge condition (here, "is a string prefix" instead of "is a path prefix followed by a separator or equal"), silently allowing a value that should have been rejected to pass validation.

### Finding Description
`_resolveWithin()` computes `realResolved` and `realRoot` via `realpath()` and then confines the result with: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a character-prefix comparison, not a path-segment comparison. If `realRoot` is `/Users/victim/repo` and the computed `realResolved` is `/Users/victim/repo-evil/secret.txt`, `realResolved.startsWith(realRoot)` returns `true` even though `repo-evil` is a completely different, sibling directory — not a subdirectory of `repo`. The same flaw affects Windows drive-relative paths and any realpath-resolved symlink target that happens to share the root's directory name as a prefix.

This function is the sole confinement guard used by every caller that needs to keep an attacker-influenced path inside the repository:
- `openRepositoryFromUrl()` in the dispatcher, which handles the `x-github-client://openrepo/...?filepath=...` deep link. The `filepath` query parameter comes directly from a URL that the user clicks (fully attacker-controlled), is only checked with `isAbsolute(filepath)` before being passed to `resolveWithin(repository.path, filepath)`: [2](#0-1) 
- `buildConflictContext()` in the Copilot AI conflict-resolution feature, which resolves per-file conflict paths against the working directory before reading file content: [3](#0-2) 
- The Copilot conflict-resolution *write-back* path in `app-store.ts`, which resolves the model's returned resolution path against the repository root and then writes the model-produced content to disk: [4](#0-3) 

The deep-link parser does no path-traversal filtering of `filepath` at all — it just extracts the raw query string value: [5](#0-4) 

Existing unit tests for `resolveWithin` only cover `..`-then-back-into-root and symlink-out cases; they do not cover the sibling-directory-name-prefix case, so this specific boundary gap is untested: [6](#0-5) 

### Impact Explanation
A path that is a sibling of the repository directory (not underneath it) can be misclassified as "inside" the repository whenever an attacker can arrange for the repository's realpath to be a prefix of another accessible directory name on disk (a very common real-world situation — e.g., `Desktop-old`, `Desktop.bak`, `Documents/GitHub/desktop` next to `Documents/GitHub/desktop-experimental`, `repo` next to `repo-2`, `repo` next to `repo.git`, etc., all common developer directory-naming patterns). Once `resolveWithin` wrongly returns a non-null path, downstream code treats it as safely confined and performs a file-system operation on it:
- Via the `openrepo` deep link, `shell.showItemInFolder(resolved)` is invoked on a path outside the intended repository — an attacker who convinces a user to click a crafted `x-github-client://` link can cause Desktop to reveal an arbitrary file outside the cloned repo in the file manager, an information-disclosure/path-confinement escape triggered purely by a link click, matching the accepted impact category "a link or deep link the user clicks."
- Via the Copilot conflict-resolution flow, `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` can write attacker/model-influenced content to a location outside the repository, i.e., silent corruption of files that are not part of what the user intends to commit — matching "file write ... outside the repo" / "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Exploitation of the deep-link path requires only that the victim click a malicious `x-github-client://openrepo/...` link (a normal Desktop-supported URL scheme) while having (or after cloning) a directory whose realpath is a prefix-match sibling of another directory reachable on disk — a condition that is common by accident (backup/versioned folder names) and can also be deliberately engineered by an attacker who also controls or suggests the clone target name (e.g., via a crafted repository name in combination with `sanitizeCloneName`). No local access, admin rights, or pre-existing malware is required — only a URL click and the OS's normal directory layout. The Copilot write-back path additionally requires the AI-assisted merge-conflict feature to be enabled and a resolution containing a path that resolves to a sibling directory, which is a narrower but still plausible condition given prompt-injectable conflict content from a malicious remote branch.

### Recommendation
Fix `_resolveWithin()` in `app/src/lib/path.ts` to check for an exact match or a prefix followed by the platform path separator, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
where `sep` is the appropriate separator for the `options` module in use (`Path.sep`, `Path.win32.sep`, or `Path.posix.sep`). Add regression tests for the sibling-directory-name case (e.g., root `/tmp/repo` vs. candidate `/tmp/repo-evil/file`) to prevent recurrence, mirroring how the original report recommended validating the exact boundary condition instead of an adjacent one.

### Proof of Concept
1. Create two sibling directories: `/Users/victim/Documents/GitHub/myrepo` (a real Desktop-managed repository) and `/Users/victim/Documents/GitHub/myrepo-secrets/ssh-key.txt` (any other directory/file the attacker wants to target).
2. Attacker sends the victim a link: `x-github-client://openrepo/octocat/myrepo?filepath=../myrepo-secrets/ssh-key.txt`.
3. Victim clicks the link. Desktop parses it via `parseAppURL` (no traversal filtering on `filepath`), opens/clones `myrepo`, then calls `resolveWithin(repository.path, '../myrepo-secrets/ssh-key.txt')`.
4. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/Documents/GitHub/myrepo-secrets/ssh-key.txt`; `realResolved.startsWith(realRoot)` evaluates `true` because `"...myrepo-secrets/ssh-key.txt".startsWith("...myrepo")` is `true` as a string, even though it is not a subpath.
5. `resolveWithin` returns the outside path instead of `null`, and `shell.showItemInFolder(resolved)` reveals the file outside the repository in the file manager — confirming the path-confinement guard is bypassed via a simple deep link.
