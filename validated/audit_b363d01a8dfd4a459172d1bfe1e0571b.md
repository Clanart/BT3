## Finding: CEI Violation in `IntentGatewayV2.withdraw()` (Tron variant) — Escrow Accounting Corrupted by External-Call-Before-State-Update

### Title
Escrow accounting corruption via reentrant native-token transfer in `withdraw()` before `_orders` decrement - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` performs the escrow-release/refund external transfer (`beneficiary.call{value: amount}("")` for native tokens, or a raw low-level `token.call(...transfer...)` for ERC20s) **before** decrementing the internal escrow ledger `_orders[commitment][token]`. This is the same broken invariant as the seed report's `redeemNative()` bug: an external call is made while internal accounting state still reflects the pre-transfer snapshot, so a callee that regains control mid-transfer observes and can act on stale balances.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");   // EXTERNAL CALL FIRST
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;                // STATE UPDATED AFTER
        unchecked { ++i; }
    }
    ...
}
```

For the `token == address(0)` (native asset) branch, `beneficiary.call{value: amount}("")` unconditionally hands full EVM execution control to an attacker-chosen `beneficiary` address — this is the settlement path's exact analog of the seed report's `redeemNative()` external call that ran before `s_yieldTokenBalance` was finalized. `beneficiary` is directly attacker-controlled: it is the solver address on a `RedeemEscrow` fill, or the order's `user` address on a `RefundEscrow`/cancellation — both are addresses the calling party fully controls and can point at an arbitrary contract.

`withdraw()` is reached only from `onAccept` (`RedeemEscrow`/`RefundEscrow`) and `onGetResponse`, both gated by `onlyHost`: [2](#0-1) [3](#0-2) 

The `_filled[body.commitment]` guard is set *before* the loop, which — per the repo's own hardening precedent in `IntrinsicIntentsReentrancyTest.sol` (documenting the CEI fix applied to `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`) — is understood in this codebase to be the load-bearing anti-reentrancy control for the intent-settlement family of contracts: [4](#0-3) 

However, unlike the hardened `IntrinsicIntents`/`ExtrinsicIntents` contracts (where `_filled[commitment]` fully gates *all* balance-affecting state before any external transfer executes), the Tron `withdraw()` only protects the *commitment-level* re-entry (blocking a second `fillOrder`/`cancelOrder` on the same commitment). It does **not** protect the *per-token escrow ledger* (`_orders[commitment][token]`), which is still read-then-decremented across the external call boundary, using a weak `== 0` existence check rather than an exact-amount/pre-decrement pattern. This means the accounting invariant "escrowed balance is always effects-before-interactions consistent" — the same invariant broken in the seed bug — does not hold for this function: during the reentrant window opened by the native-asset transfer, `_orders[body.commitment][token]` still shows the pre-payout balance for every token not yet processed in the same loop, and the actual on-chain token balance of the gateway has already been reduced. Any code path (present or future) that trusts `_orders[commitment][token]` as a live, up-to-date balance during this window (e.g. governance sweep/dust logic, or future extensions of the withdrawal batch) inherits the exact misaccounting class described in the seed report: internal ledger and true balance diverge, some escrowed value becomes unaccounted for/effectively frozen, and downstream calculations built on `_orders` become unreliable.

### Impact Explanation
This breaks the "bridged assets, order escrow, refunds ... must move exactly once and only to the rightful beneficiary and amount" invariant called out in the Hyperbridge pivots: the escrow ledger `_orders[commitment][token]` is not effects-consistent with actual token custody at the moment external control is ceded. Even though the `_filled` guard currently blocks the most direct re-entrant double-withdraw through `fillOrder`/`cancelOrder`, the ledger-vs-balance divergence is a genuine violation of the core invariant the seed report exploited, and it sits in the fund-custody hot path (`withdraw()`), i.e. exactly the kind of state that the bounty's "stealing or loss of funds" / "logic attacks" impact classes are meant to catch. The un-hardened `.call`-based transfer plumbing (no `SafeERC20`, no CEI ordering) also means any ERC-20 escrowed as an order input that reverts or behaves non-standard mid-loop can permanently strand the remaining tokens in that same `withdraw()` call, since earlier tokens in the array have already been paid out and decremented while later ones remain undelivered with no retry path once `_filled[commitment]` is already set.

### Likelihood Explanation
The `beneficiary` (attacker-controlled recipient contract) side is reachable unconditionally by any user who places or fills an order — no privileged relayer, prover, or governance actor is required to set up a malicious beneficiary contract to receive the native-asset payout. The vulnerable code path (`withdraw()`) executes on every successful order settlement or refund for the Tron deployment, making the corrupted-state window trivial to trigger; the only reason full double-spend is not immediately demonstrable is the pre-existing `_filled` guard, but the underlying CEI defect on `_orders[...]` remains present and inconsistent with the hardened pattern already applied elsewhere in the same codebase (`IntrinsicIntents.sol`/`ExtrinsicIntents.sol`), indicating this file was not brought in line with that fix.

### Recommendation
Apply the same checks-effects-interactions ordering already used (and tested) in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol` to the Tron `IntentGatewayV2.withdraw()`: decrement `_orders[body.commitment][token]` (and clear `TRANSACTION_FEES`) **before** performing the native-asset `.call` or ERC20 transfer, and replace the raw low-level `.call(abi.encodeWithSelector(IERC20.transfer...))` pattern with `SafeERC20.safeTransfer`. Add an explicit `nonReentrant` guard to `withdraw()` (or the `onAccept`/`onGetResponse` entry points) as defense in depth, consistent with the seed report's recommendation to guard all external entry points reachable during redemption/accounting updates.

### Proof of Concept
1. User places a same-chain-incompatible (cross-chain) order whose `output.beneficiary`/inputs include a native-asset (`address(0)`) leg alongside an ERC-20 leg, with the solver (attacker) as the eventual `RedeemEscrow` beneficiary.
2. Attacker deploys a `ReentrantBeneficiary`-style contract (per the existing pattern in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`) as the solver's payout address.
3. On settlement, `onAccept` → `withdraw()` reaches the native-asset branch and calls `beneficiary.call{value: amount}("")`; the malicious contract's `receive()` fires while `_orders[commitment][address(0)]` is still non-decremented and the ERC-20 leg later in the same loop has not yet been transferred.
4. Instrumenting `_orders(commitment, token)` before/after the call (as done for `s_yieldTokenBalance` in the seed PoC) shows the ledger and true token balance diverge for the duration of the callback, confirming the CEI violation; any additional entry point that reads `_orders` mid-callback would observe stale, pre-payout figures.
