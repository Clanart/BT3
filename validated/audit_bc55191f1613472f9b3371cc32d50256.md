### Title
Panic on out-of-range participant index in DKG blame evaluation causes denial of service - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame`, `AdditionalBlameMachine::blame`, and their shared helper `blame_internal` index `self.commitments[&sender]` without validating that `sender` is within the protocol's participant range. Since `Participant` only guarantees a non-zero `u16` (any value up to 65535), an untrusted blame statement naming a `sender` greater than `n` causes a `HashMap` index panic. This is an improper-input-handling denial of service reachable with bytes an unprivileged party can supply, analogous to the request-handling DoS class of CVE-2019-0548.

### Finding Description
`AdditionalBlameMachine::new` populates `commitments` exclusively for `Participant::new(1) ..= Participant::new(n)` [1](#0-0) . `blame_internal` then unconditionally indexes that map with a caller-supplied `sender`: `&self.commitments[&sender]` inside the `multiexp_vartime` share check [2](#0-1) . Both public entry points pass the attacker-influenced `sender` straight through: `BlameMachine::blame` [3](#0-2)  and `AdditionalBlameMachine::blame` [4](#0-3) . `Participant::new` rejects only zero, so `Participant(500)` is a legal value even when `n = 150` [5](#0-4) . The surrounding code acknowledges this fragility: `AdditionalBlameMachine::new` documents that invalid inputs "may cause everything from inaccurate blame to panics" [6](#0-5) , yet `blame` performs no range check itself.

### Impact Explanation
A malformed blame statement (sender index > n, or an index whose commitments were never registered) triggers a `HashMap` index-out-of-bounds panic inside `blame_internal`, aborting the thread evaluating blame. In deployments where a panic kills the process (Serai binaries install panic hooks that call `std::process::exit`), a single crafted blame message takes down the node performing fault attribution — precisely the availability loss the DKG blame mechanism exists to prevent an attacker from causing. Severity: Medium.

### Likelihood Explanation
Blame evaluation consumes authenticated but otherwise untrusted peer data: the accused `sender` index, the `EncryptedMessage`, and the optional `EncryptionKeyProof` all arrive from the accusing party. Crafting `sender = Participant(n + 1)` (or any index absent from `commitments`, e.g., a participant whose commitments were legitimately excluded from the session) requires no cryptography — just a two-byte field. The panic fires on the `self.commitments[&sender]` lookup once decryption/proof handling on the message completes, and additionally `self.encryption` lookups keyed on the same unvalidated index may panic earlier in `decrypt_with_proof` [7](#0-6) .

### Recommendation
Validate `sender` and `recipient` against the populated `commitments` map (i.e., `1 ..= n` and present) at the top of `blame_internal`, returning the accusing party as faulty (or a dedicated error) instead of indexing. Replace `self.commitments[&sender]` with `self.commitments.get(&sender)` and treat `None` as recipient-faulty/malformed input rather than panicking.

### Proof of Concept
```rust
// n = 3 DKG completed; build an AdditionalBlameMachine over the real commitments.
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker submits a blame statement naming participant index 4 (> n).
let sender = Participant::new(4).unwrap();
let recipient = Participant::new(1).unwrap();
// msg: any EncryptedMessage that passes decrypt_with_proof handling
// (e.g., a structurally valid message encrypted to recipient).
machine.blame(sender, recipient, msg, None);
// PANIC at crypto/dkg/pedpop/src/lib.rs:599 — `self.commitments[&sender]`
// indexes a HashMap that only contains keys 1..=3.
```

Caveat: the exact panic point depends on whether `decrypt_with_proof` indexes the sender's encryption key before the commitments lookup at line 599; in either ordering the root cause is the same missing range check on the attacker-supplied participant index.
