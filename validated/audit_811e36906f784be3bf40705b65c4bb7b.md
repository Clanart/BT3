Based on my investigation, the on-chain publish/upgrade/ownership invariants in `code.move`, `object_code_deployment.move`, and the new `init.move` lazy-initialization gate are all internally consistent and covered by explicit tests (ownership checks via `object::is_owner`, root-owner-based self-init gating in `assert_may_self_initialize`, upgrade-policy monotonicity in `check_upgradability`/`check_dependencies`). I could not find an unprivileged bypass there. However, I did find a concrete gap in the CLI-side bytecode-verification path that matches the "mismatch between verified bytes, package metadata... and committed module bytes" pivot.

### Title
`aptos move verify-package` never compares on-chain module bytecode, only self-reported metadata - (File: `aptos-move/cli/src/stored_package.rs`)

### Summary
`CachedPackageMetadata::verify` — the function backing the `aptos move verify-package` CLI command — only diffs `PackageMetadata` fields (`name`, `deps`, `modules` metadata, `manifest`, `upgrade_policy`, `extension`, `source_digest`). It never fetches or compares the actual on-chain module bytecode against the locally compiled bytecode, even though `CachedPackageRegistry` already has the machinery to fetch it (`with_bytecode` flag, `get_bytecode()`).

### Finding Description
`CachedPackageRegistry::create` can optionally fetch each module's raw bytecode via `client.get_account_module(...)` into a `bytecode: BTreeMap<String, Vec<u8>>` map [1](#0-0) . A `get_bytecode()` accessor exists to read this map [2](#0-1) .

However, `verify()` — the routine that actually implements "verify that the on-chain copy matches" — only compares `PackageMetadata` struct fields: `name`, `deps`, `modules` (which is `ModuleMetadata`, containing `name`/`source`/`source_map`/`extension`, not bytecode), `manifest`, `upgrade_policy`, `extension`, and `source_digest` (a hash computed over *source text*, not compiled bytecode) [3](#0-2) . It never touches `self.bytecode` or calls `get_bytecode()`.

All of the fields it does compare (`source`, `source_digest`, `manifest`) are self-reported by whoever published the package — they are attacker-controlled inputs baked into `PackageMetadata` at publish time (see `BuiltPackage::extract_metadata`, which computes `source_digest` from the same local source tree and packs it alongside the modules, all serialized client-side before submission) [4](#0-3) . There is no on-chain linkage enforced between the declared source/metadata and the actual verified/loaded module bytes at the framework level being checked by this specific tool; the `code::publish_package` flow performs bytecode verification for compatibility/loading purposes, but the CLI's "verify" tool does not independently confirm that the source underlying that bytecode matches what was actually deployed — it just trusts the metadata blob that was published.

### Impact Explanation
`aptos move verify-package` is documented as the mechanism to "Build the package locally and verify that the on-chain copy matches" [5](#0-4) . Third parties (auditors, wallets, indexers, or dependent-package authors relying on `is_policy_exempted_address`/dependency trust in `code::check_dependencies`) may use this command as a supply-chain trust anchor to confirm "the deployed module is exactly what this source produces." Because `verify()` only diffs self-declared metadata (name/digest/manifest text) and never diffs actual retrieved bytecode against locally recompiled bytecode, a malicious package owner can publish one set of bytecode while declaring metadata/source that "verifies" successfully against an innocuous local package, misleading anyone who relies on this CLI's PASS result as proof of code integrity.

### Likelihood Explanation
Likelihood of a package owner deliberately submitting mismatched metadata vs. bytecode is straightforward (metadata is passed as raw serialized bytes at publish time, entirely under the publisher's control, and the chain does not cross-check metadata against bytecode identity itself). The bar to trigger this is simply publishing normally; no special privilege beyond being able to call `publish_package_txn` is required.

### Recommendation
Extend `verify()` to always fetch (`with_bytecode = true`) and byte-compare each module's on-chain bytecode against `BuiltPackage::extract_code()` output for the same module name, failing verification on any mismatch, in addition to the existing metadata field checks.

### Proof of Concept
1. Build package `A` locally with source declaring benign logic; compute its metadata (`source_digest`, `manifest`, `modules[].source`).
2. Publish arbitrary/different bytecode under the same module name/package name via `code::publish_package_txn`, using the metadata blob from step 1 for `metadata_serialized` (metadata and code bundle are independent function args — `code::publish_package` never hashes `code` into `pack.source_digest` or otherwise ties them together at the Move layer beyond module names) [6](#0-5) .
3. Run `aptos move verify-package --account <addr>` using package `A`'s local source; `CachedPackageMetadata::verify` compares only metadata fields, all of which match by construction, and reports success — despite the deployed bytecode being different from what `A`'s source would compile to.

Note: this is a CLI/tooling-level trust gap, not a consensus or write-set state-mutation bug — I want to flag that explicitly since the confidence in this being a "high/critical" on-chain impact (as opposed to a supply-chain/tooling trust issue) is moderate, not high. I found no unprivileged bypass in the actual on-chain ownership/upgrade-policy/self-init invariants (`code.move`, `object_code_deployment.move`, `init.move`), which all appeared correctly enforced and test-covered.

        };
