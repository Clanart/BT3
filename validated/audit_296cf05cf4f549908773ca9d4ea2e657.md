### Title
Malformed/nested conflict markers are silently absorbed into a single hunk by `extractConflictHunks`, causing Copilot merge-conflict resolution to overwrite unrelated conflicting content - (File: `app/src/lib/copilot-conflict-context.ts`)

### Summary
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` scans a conflicted file for `<<<<<<<` / `|||||||` / `=======` / `>>>>>>>` markers using a simple linear state machine [1](#0-0) . While collecting the "ours" and "theirs" sections of a hunk, the loops only look for the specific marker that is expected to *close* the current section (`baseMarker`/`separatorMarker` while collecting ours, `theirsMarker` while collecting theirs) [2](#0-1) . Any other marker type encountered mid-collection (in particular a second, nested `<<<<<<<`/`=======` pair) is not recognized as a boundary and is pushed as plain text into `oursLines`/`theirsLines`. This lets an attacker-crafted conflicted file (from a malicious branch/remote merged, rebased, or cherry-picked into the user's repo) cause two logically separate conflicts to be silently collapsed into a single `IConflictHunk`, whose `oursContent`/`theirsContent` now contains an embedded, un-flagged second conflict.

### Finding Description
The function never validates that markers appear in the expected, non-overlapping order; it only reacts to the marker it happens to be looking for at each step, exactly like the audited `spend_order_inputs` recursion which only accounted for the outermost `PlaceOrder` and silently let a nested one ride along unprocessed. Here, a nested `<<<<<<<`/`=======` block occurring inside what should be the "theirs" region of an outer hunk is not rejected or split out — it's absorbed as literal content of the outer hunk:

```
<<<<<<< HEAD
line1
=======
line2
<<<<<<< HEAD      <-- nested marker, not checked for here
line3
=======
line4
>>>>>>> branch    <-- closes the OUTER hunk, swallowing the nested one
```

Tracing the state machine: the "ours" loop stops at the first `=======` (`line1` becomes `oursContent`), then the "theirs" loop only stops on `theirsMarker` (`>>>>>>>`), so it keeps consuming `<<<<<<< HEAD`, `line3`, `=======`, `line4` as plain lines until it hits the final `>>>>>>> branch`. The result is a single `IConflictHunk` whose `theirsContent` is `"line2\n<<<<<<< HEAD\nline3\n=======\nline4"` — two distinct, independently-resolvable conflicts have been merged into one opaque blob, with no `skippedReason` and no signal that anything unusual happened [3](#0-2) .

This hunk data, together with the raw file content, is what `buildConflictContext` hands off (`rawContent`/`hunks`) specifically so that "the resolved file" can later be reassembled "by splicing per-hunk resolutions into the original content" [4](#0-3) [5](#0-4) . The reassembly/splicing logic lives in `app/src/lib/copilot-conflict-resolution.ts`, which I confirmed references splicing/resolved-content logic, but I was not able to fully read its implementation before the iteration budget ran out, so I cannot show the exact byte-offset mechanics of how a single AI-generated resolution string gets written back over the merged region.

### Impact Explanation
Because the merged hunk is presented to the AI model, and to the user's review UI, as *one* conflict instead of two, the single resolution text returned by the model gets spliced over a region that actually corresponds to two independent conflicting changes. This can silently discard or corrupt one side's changes without the user (or the model) ever being told a second conflict existed in that span — matching the "silent corruption of what the user commits or pushes" impact category, since the file the user ultimately stages and commits no longer faithfully reflects either branch's real changes and the discrepancy is not surfaced anywhere in the UI (no `skippedReason`, no extra "Conflict N of M" entry for the swallowed inner block).

### Likelihood Explanation
Triggering this requires nothing more than the ordinary Desktop conflict-resolution flow: the attacker only needs to get a branch merged/rebased/cherry-picked such that the resulting conflicted file happens to contain content that itself resembles nested conflict markers (e.g., a file that legitimately contains conflict-marker-like strings, or an adversarial file specifically engineered with embedded `<<<<<<<`/`=======`/`>>>>>>>` sequences inside what will become one side of a real conflict). No local access, admin rights, or social engineering beyond a normal git merge/rebase/cherry-pick against attacker-influenced content is needed, and the existing size/length guards (`MAX_CONFLICT_FILE_READ_SIZE`, `MAX_CONFLICT_LINE_LENGTH`, `MAX_CONFLICT_CONTENT_SIZE`) do nothing to detect malformed marker nesting — they only bound size [6](#0-5) .

### Recommendation
In `extractConflictHunks`, while collecting `oursLines`/`baseLines`/`theirsLines`, check every line against **all** marker regexes, not just the one expected to close the current section. If any unexpected marker (e.g., a stray `oursMarker` while still inside an ours/base/theirs collection, or a `theirsMarker` encountered before a `separatorMarker`) is seen, treat the surrounding structure as malformed: abort hunk extraction for that region and surface it via `skippedReason` (as is already done for the "no closing marker" case at lines 240-242) rather than silently folding it into adjacent content. Long term, add fuzz/property tests with deliberately nested and malformed marker sequences (mirroring the recommendation in the original report to "expand the test suite to check execution of nested" structures) to `app/test/unit/copilot-conflict-context-test.ts`.

### Proof of Concept
1. Create two branches whose merge produces a conflicted file with the following content (attacker controls the branch that gets merged/rebased/cherry-picked):
```
<<<<<<< HEAD
keep-this-from-ours
=======
theirs-part-A
<<<<<<< HEAD
keep-this-from-ours-2
=======
theirs-part-B
>>>>>>> feature-branch
```
2. Trigger a merge/rebase/cherry-pick in Desktop that results in this conflict, then invoke the Copilot conflict-resolution feature.
3. `extractConflictHunks` returns a single hunk with `oursContent = "keep-this-from-ours"` and `theirsContent = "theirs-part-A\n<<<<<<< HEAD\nkeep-this-from-ours-2\n=======\ntheirs-part-B"`, instead of two separate hunks.
4. The Copilot prompt (`formatConflictContextForPrompt`) shows this as a single "Conflict 1 of 1" [7](#0-6) , and the model's single resolution is spliced back over the entire merged region — silently resolving/removing the second, un-signaled conflict along with the first.

  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

export function getHunkSkipReason(
  hunks: ReadonlyArray<IConflictHunk>
): string | null {
  let totalContent = 0

  for (const hunk of hunks) {
    const sides = [hunk.oursContent, hunk.theirsContent, hunk.baseContent ?? '']
    for (const side of sides) {
      totalContent += side.length
      for (const line of side.split('\n')) {
        if (line.length > MAX_CONFLICT_LINE_LENGTH) {
          return 'Conflict contains lines too long to resolve automatically'
        }
      }
    }
    if (totalContent > MAX_CONFLICT_CONTENT_SIZE) {
      return 'Conflict region too large to resolve automatically'
    }
  }

  return null
}
