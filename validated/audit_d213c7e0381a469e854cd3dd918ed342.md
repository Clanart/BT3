## Title
Reentrancy in `IntentGatewayV2.withdraw()` allows a solver-controlled beneficiary to double-claim escrowed order funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
On `onAccept` receipt of a `RedeemEscrow`/`RefundEscrow` cross-chain message, the Tron `IntentGatewayV2.withdraw()` function performs the token transfer to `beneficiary` **before** decrementing the `_orders[commitment][token]` escrow ledger, violating checks-effects-interactions. Since `beneficiary` is attacker-controlled (it is the solver's own address, taken directly from `order.user`/`msg.sender` at fill time), a malicious contract acting as solver/beneficiary can reenter during the native-token `.call` (or an ERC-777/callback-style token transfer) and withdraw the same escrowed amount multiple times before the ledger is updated.

### Finding Description
`withdraw()` is invoked from `onAccept` for both `RedeemEscrow` (paying the filler/solver after a cross-chain fill) and `RefundEscrow` (paying the original order user after cancellation): [1](#0-0) 

The `withdraw()` function itself checks only that the escrow is non-zero, then performs the external transfer, and only afterwards decrements the ledger: [2](#0-1) 

For the native-token branch, `beneficiary.call{value: amount}("")` hands full control-flow to `beneficiary` before `_orders[body.commitment][token] -= amount` executes. `beneficiary` is derived from `order.user` (refund path) or `msg.sender`-the solver-at fill time (redeem path), both of which are unprivileged, attacker-choosable addresses. A malicious beneficiary contract can, inside its `receive()`/`fallback()`, immediately call back into the ISMP delivery path for the *same commitment* (the request has not yet been marked delivered/consumed with respect to this specific ledger entry, since `_orders[commitment][token]` is still non-zero) and trigger `withdraw()` again for the same commitment/token before the first invocation's decrement runs, draining more than the amount escrowed for that order.

This is exactly the invariant broken in the BUIDL/Ondo report generalized: the contract assumes a redemption of a tracked/owed balance is atomic and safe to execute in one step, without protecting the ledger update against interaction with the external asset/beneficiary during the transfer. Here, instead of an external minimum-balance rule causing an unexpected revert, the unprotected order of operations causes an unexpected **double payout**.

By contrast, the canonical EVM (`evm/src/apps/intentsv2/IntentsBase.sol`) implementation of the equivalent `_withdraw()` logic correctly decrements the escrow **before** the external call: [3](#0-2) 

The Tron variant does not follow this same ordering, and does not appear to have any additional reentrancy guard (`onAccept` uses `onlyHost`, which only authenticates that the caller is the local Hyperbridge host relaying an ISMP message — it does not prevent the *beneficiary* from reentering during the payout).

### Impact Explanation
A successful reentrant call drains escrowed input tokens beyond what was committed for a single order, directly stealing funds belonging to the protocol/other orders' escrow pool. This falls squarely under "stealing or loss of funds" and "replay/double-claim/double-settlement" in the bounty's required impacts, since the same `WithdrawalRequest`/commitment effectively pays out more than once before its ledger entry reflects the first payout.

### Likelihood Explanation
The attack requires only that the attacker act as an unprivileged solver (fill an order and become its `beneficiary`) or as the order's original `user` on the refund path — both are ordinary, permissionless capabilities of any actor using the IntentGateway, no relayer/prover/admin compromise is needed. The only requirement is that the beneficiary address be a contract capable of reentering during the native-token `.call`, which is trivial to arrange.

### Recommendation
Apply checks-effects-interactions consistently in `IntentGatewayV2.withdraw()` (Tron variant): decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` balance) **before** performing the external `.call`/token transfer, mirroring the ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally consider adding an explicit reentrancy guard around `onAccept`/`withdraw` for defense in depth.

### Proof of Concept
1. Attacker deploys a malicious contract `Evil` with a `receive()` function.
2. Attacker (as solver) fills a cross-chain order via `fillOrder`, setting `msg.sender = Evil`, so `WithdrawalRequest.beneficiary = Evil` is dispatched in the `RedeemEscrow` request body to the source chain. [4](#0-3) 
3. When the `RedeemEscrow` message is delivered on the source chain, `onAccept` calls `withdraw(body, false)`.
4. Inside `withdraw()`, for a native-token entry, `beneficiary.call{value: amount}("")` transfers to `Evil` **before** `_orders[commitment][token] -= amount` executes: [5](#0-4) 
5. `Evil.receive()` reenters the host's message-delivery entrypoint for the same already-authenticated commitment/token (escrow not yet decremented, so the `_orders[...] == 0` check still passes), causing a second `.call{value: amount}` payout for the same order before the first call's decrement is applied.
6. Repeat until the contract's actual token/native balance is exhausted, having paid out multiples of the order's real escrowed amount.

Note: I could not fully trace whether ISMP's outer message-delivery layer (host contract) enforces its own single-delivery/receipt guard that would block re-entrant redelivery of the identical incoming request at the host level; if such a guard exists it may need to be bypassed via a second, distinct request or reentry into a different function that reaches `withdraw()` (e.g. by having multiple token entries in `body.tokens` for the same order, since the loop itself decrements per-iteration after each transfer, so a single request already contains a reenter-during-loop vector without needing to bypass any outer message-uniqueness check). This inner-loop path is the most directly provable primitive from the code shown.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
