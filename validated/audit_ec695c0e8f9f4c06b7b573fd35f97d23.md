## Analysis

The Olas report describes a pattern where an on-chain state transition (`unstake()`) performs an irreversible action (returning the NFT / clearing service state) *before* attempting a token transfer that can be blocked (blocklist/pause), and the two are bundled in a way that isn't safely separable, risking permanent lock of user assets.

The Cosmos EVM analog is in the `x/erc20` IBC middleware's automatic native-ERC20 conversion during `OnRecvPacket`, where the underlying ICS20 token movement (unescrow/mint) is committed to state **before** the auto-conversion into the ERC20 representation is attempted, and a failure of that conversion (via a paused/blocklisted/disabled token) still allows an error acknowledgement to be returned — without rolling back the already-committed ICS20 state change. ### Title
Native ERC20 auto-conversion failure in IBC `OnRecvPacket` commits the underlying token unescrow/mint while still returning an error acknowledgement, causing duplicated funds across chains - (File: x/erc20/ibc_middleware.go, x/erc20/keeper/ibc_callbacks.go)

### Summary
`IBCMiddleware.OnRecvPacket` first executes the standard ICS20 `OnRecvPacket` (which unescrows or mints the transferred coin to the receiver's bank balance, committing this change directly to the shared `ctx`), and only afterward calls `k.keeper.OnRecvPacket` to auto-convert that coin into its native ERC20 representation. If the conversion step fails — e.g. because the token pair's `SendEnabled` is disabled, the receiver is a `BlockedAddr`, or the underlying ERC20 contract itself reverts a transfer (paused/blocklisted, analogous to the Olas report) — the middleware returns a `channeltypes.NewErrorAcknowledgement`. Unlike other parts of the codebase (e.g. `x/ibc/callbacks` `IBCReceivePacketCallback`, which explicitly uses a cached context and only calls `writeFn()` on success specifically to avoid this problem), this path does **not** use a cached/discardable context for the initial ICS20 transfer. The bank-level state change therefore persists even though the acknowledgement reports failure.

### Finding Description
The relevant flow:
1. `IBCMiddleware.OnRecvPacket` calls `im.Module.OnRecvPacket(ctx, ...)`, the standard ICS20 handler, which unescrows (return-trip case) or mints tokens directly on `ctx` to the receiver's bank balance. [1](#0-0) 
2. If that step succeeds, it calls `k.keeper.OnRecvPacket(ctx, packet, ack)`, which for a native-ERC20 token pair calls `MintingEnabled` (checks `BlockedAddr`/`IsSendEnabledCoin`) and then `ConvertCoinNativeERC20` (an EVM call to `transfer` on the ERC20 contract). [4](#0-3) 
3. Any failure in `MintingEnabled` or `ConvertCoinNativeERC20` results in `channeltypes.NewErrorAcknowledgement(err)` being returned — **but the bank-level unescrow/mint from step 1 was already committed to `ctx` and is never rolled back.**
4. An error acknowledgement propagates back to the counterparty chain, which will treat the transfer as failed and refund the original sender (unescrow or re-mint the burned voucher).

The result: the receiving chain has already credited the receiver with spendable bank-coin value, while the sending chain independently refunds the sender — duplicating the transferred value across both chains.

This exact failure mode is demonstrated (without checking for the cross-chain duplication consequence) in the test suite, whose own comment confirms the funds are **not** returned to escrow when conversion fails: [5](#0-4) 

By contrast, the codebase already has a known-good mitigation pattern for exactly this class of problem elsewhere, confirming this is a real gap rather than accepted behavior: [6](#0-5) 

### Impact Explanation
This directly matches the "Critical unauthorized minting, burning, duplication ... of spendable user value ... across native balances ... IBC escrows" impact category. Coins are simultaneously: (a) present as a real, spendable bank balance on the receiving chain (unescrowed/minted, just not converted to the intended ERC20 form), and (b) refunded to the sender on the counterparty chain due to the error acknowledgement. This breaks the fundamental IBC/ERC20 escrow invariant and creates value out of nothing, corruptible by any account that is blocklisted, any token pair with `SendEnabled=false`, or (matching the original report's exact scenario) any native ERC20 contract that pauses/blocklists transfers.

### Likelihood Explanation
Triggering this requires only an ordinary, unprivileged IBC packet receive under any of several realistic conditions: the token pair's coin `SendEnabled` set to false, the receiver being on the bank module's `BlockedAddr` list, or (as in the Olas analog) the underlying native ERC20 contract owner pausing/blocklisting transfers — none of which requires special chain privileges, malicious relayers, or governance action. The token pair owner (an ordinary contract deployer) fully controls whether their ERC20 implements pause/blocklist logic, making this attacker/protocol-controllable.

### Recommendation
Wrap the ICS20 `im.Module.OnRecvPacket` call and the subsequent `k.keeper.OnRecvPacket` conversion attempt in a single cached context (`ctx.CacheContext()`), only calling `writeCache()` if the final acknowledgement (after attempting conversion) is successful — mirroring the pattern already used in `x/ibc/callbacks/keeper/keeper.go`. Alternatively, on conversion failure, do not return an error acknowledgement; instead fall back to leaving the coin in its bank representation (as `OnAcknowledgementPacket`/`OnTimeoutPacket` already do gracefully) and always return a success acknowledgement so the counterparty never issues a refund for value that was already delivered.

### Proof of Concept
1. Register a token pair for a native ERC20 token on evmChainA and IBC-transfer some amount to chainB (escrowing it on evmChainA).
2. From chainB, initiate a transfer of the token back to evmChainA (a "return trip" IBC packet for evmChainA's native denom).
3. Before the packet is relayed/received, disable transfers for the pair's denom (`SetSendEnabled(denom, false)`) or otherwise make `MintingEnabled`/`ConvertCoinNativeERC20` fail (blocklist the receiver, or pause/blocklist on the ERC20 contract side).
4. Relay the packet to evmChainA. `im.Module.OnRecvPacket` unescrows the coin to the receiver's bank balance (committed state change); `k.keeper.OnRecvPacket`'s conversion attempt fails and an error acknowledgement is returned/written.
5. This error acknowledgement is relayed back to chainB, which refunds the original sender (mints back the burned voucher).
6. Now check balances: the receiver on evmChainA holds the unescrowed native coin (real spendable value, confirmed not returned to escrow in the test at evmd/tests/ibc/ibc_middleware_test.go lines 728-754), AND the sender on chainB was refunded the equivalent amount — the same value now exists on both chains simultaneously.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}

func (k Keeper) OnRecvPacket(
	ctx sdk.Context,
	packet channeltypes.Packet,
	ack exported.Acknowledgement,
) exported.Acknowledgement {
	// If ERC20 module is disabled no-op
	if !k.IsERC20Enabled(ctx) {
		return ack
	}

	var data transfertypes.FungibleTokenPacketData
	if err := transfertypes.ModuleCdc.UnmarshalJSON(packet.GetData(), &data); err != nil {
		// NOTE: shouldn't happen as the packet has already
		// been decoded on ICS20 transfer logic
		err = errorsmod.Wrapf(errortypes.ErrInvalidType, "cannot unmarshal ICS-20 transfer packet data")
		return channeltypes.NewErrorAcknowledgement(err)
	}

	// use a zero gas config to avoid extra costs for the relayers
	ctx = ctx.
		WithKVGasConfig(storetypes.GasConfig{}).
		WithTransientKVGasConfig(storetypes.GasConfig{})

	// recipient (local chain address): accept hex or local bech32
	recipientBz, err := k.addrCodec.StringToBytes(data.Receiver)
	if err != nil {
		return channeltypes.NewErrorAcknowledgement(errorsmod.Wrap(err, "invalid recipient"))
	}
	recipient := sdk.AccAddress(recipientBz)

	receiverAcc := k.accountKeeper.GetAccount(ctx, recipient)

	// return acknowledgement without conversion if receiver is a module account
	if types.IsModuleAccount(receiverAcc) {
		return ack
	}
