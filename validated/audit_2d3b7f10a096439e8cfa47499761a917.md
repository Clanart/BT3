### Title
`SignableTransaction` excludes the OP_RETURN data output from weight/vsize fee calculation, signing transactions that pay a lower fee rate than intended - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an attacker-controlled `OP_RETURN` output to `tx_outs` (lines 194–202) but computes the transaction's weight, virtual size, and `needed_fee` via `calculate_weight_vbytes`, which is invoked with `payments` only — the data output is never included in the size calculation (lines 204, 225–226). Like CVE-2019-20089's size miscalculation in `GPMF_SeekToSamples`, an object present in the serialized artifact is omitted from its size accounting, producing a systematically wrong (too-small) size and fee.

### Finding Description
`calculate_weight_vbytes` builds a template `Transaction` whose `output` vector contains only `payments` plus an optional `change` output (send.rs lines 68–99). In `SignableTransaction::new`:

- The OP_RETURN output is pushed to `tx_outs` *before* the size call (lines 194–202).
- `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204 and `Some(&change)` at line 226 both receive `payments`, not `tx_outs`, so the OP_RETURN output (variable size, up to ~92 vbytes for the 80-byte data limit) contributes nothing to `weight` or `vbytes`.
- `needed_fee = fee_per_vbyte * vbytes` (line 206) is therefore computed against a smaller transaction than the one actually constructed and signed.
- The minimum-fee gate at line 211 and the `MAX_STANDARD_TX_WEIGHT` check at line 241 also use the undercounted `weight`/`vbytes`, so a transaction that actually exceeds the standardness weight bound can pass validation.

The `data` field originates from the `InInstruction` payload attached to deposits (`processor/src/networks/bitcoin.rs` `Self::extract_serai_data(tx)` populates `output.data` for `OutputType::External` outputs, lines 730–734), so its presence/length is controlled by an unprivileged depositor.

### Impact Explanation
The multisig signs a transaction whose true vsize exceeds the size used for fee computation. Consequences:

- The realized fee rate (`actual fee / actual vbytes`) is lower than the `fee_per_vbyte` requested and lower than the value `needed_fee()` reports. When the margin is thin, the signed transaction can fall below `DEFAULT_MIN_RELAY_TX_FEE` in real terms and be rejected by relay policy — a DoS on processing that deposit/withdrawal until re-signed, and the fee/dust accounting in `fee()` diverges from the intended policy.
- A transaction whose true weight exceeds `MAX_STANDARD_TX_WEIGHT` (400,000 WU) can pass the check at line 241 because the check is evaluated against the template without the OP_RETURN output, yielding a non-standard transaction the network will not relay.
- When change is present, the undercharged remainder accumulates into the change output rather than fee; when there is no change, the shortfall is silently absorbed — in both cases the "fee the transaction will use" reported by the API is computed on a transaction that does not exist.

No funds are stolen and the signature itself is correct, so this is a Medium-severity correctness/availability issue rather than key compromise.

### Likelihood Explanation
Triggering requires only an `InInstruction` carrying non-empty `data`, which any external depositor can include in a Bitcoin transaction to the Serai address — no validator status or collusion needed. Whether it causes a stuck/non-standard transaction depends on how close the requested fee rate and weight are to the policy limits, so the failure is conditional, but the miscalculation occurs on every data-bearing transaction.

### Recommendation
Include the OP_RETURN output in the template used by `calculate_weight_vbytes`. The cleanest fix is to pass the fully assembled `tx_outs` (payments + data, and later change) into the weight calculation rather than reconstructing outputs from `payments`, or add the data output to the template explicitly:

- In `calculate_weight_vbytes`, accept `data: Option<&[u8]>` (or a pre-built `Vec<TxOut>`) and push the `ScriptBuf::new_op_return` output before computing `tx.weight()`.
- Recompute `weight`/`vbytes` for the change branch with the data output included as well.

### Proof of Concept
In `SignableTransaction::new`, with `payments = []`, `change = None`, `data = Some(vec![0; 80])`:

1. `tx_outs` ends up with one OP_RETURN output (~11+80 bytes of base size, ~91+ vbytes of weight contribution).
2. `calculate_weight_vbytes(inputs, &[], None)` builds a template transaction with *zero* outputs — the OP_RETURN is absent — so `vbytes` excludes it.
3. `needed_fee = fee_per_vbyte * vbytes` is therefore `fee_per_vbyte * ~91` sats lower than the fee required for the transaction actually signed and broadcast.
4. `tx.weight()` on the final `self.tx` exceeds the checked `weight`, meaning a transaction near `MAX_STANDARD_TX_WEIGHT` (or near the min-relay-fee boundary) passes validation while the real signed transaction violates it.
