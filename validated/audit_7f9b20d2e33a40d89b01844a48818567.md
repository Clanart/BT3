### Title
Royalty payments miscalculated when bundling multiple differently-valued/differently-priced NFTs in a single offer - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`NFTWallet.make_nft1_offer` and its helper `compute_royalty_amount` split the fungible trade amount evenly across all royalty-enabled NFTs in a multi-NFT offer, instead of weighting each NFT's royalty payment by its actual price/value. This mirrors the reported Caviar bug class where royalties were divided equally among bundled assets regardless of their true relative value, producing misdistributed royalty payouts to the correct royalty recipients.

### Finding Description
When creating an NFT1 offer that bundles several royalty-enabled NFTs together with fungible assets (XCH/CAT), the wallet computes a single, uniform "trade price" per NFT by dividing the total fungible amount by the NFT count: [1](#0-0) 

and computes each NFT's royalty payment using this same even split via `compute_royalty_amount`, which divides `offered_amount` by `royalty_split` (the count of royalty NFTs on that side of the trade) before applying each individual NFT's own `percentage`: [2](#0-1) 

This is used directly in the royalty-payment construction loop: [3](#0-2) 

and in the equivalent summary/preview endpoint used by the wallet CLI/RPC before an offer is created (`royalty_calculation`), which divides `abs(amount)` by `len(royalty_assets_dict)` uniformly: [4](#0-3) 

The split-by-count logic implicitly assumes every NFT bundled in the trade carries the same fungible value. If the NFTs have different actual/implied prices (or different royalty percentages), each NFT's royalty payment is computed off of an equal share of the pooled fungible amount rather than its true proportional share, so royalty recipients whose NFT is priced higher relative to others in the bundle receive less royalty than they are entitled to, and recipients of the relatively cheaper NFT receive more than they are entitled to — exactly the misdistribution pattern in the referenced report.

### Impact Explanation
Any wallet user constructing (or accepting) an NFT1 offer that bundles multiple royalty-enabled NFTs with unequal implicit values, alongside a single fungible request/offer, will generate royalty payments that do not reflect the true value split. Royalty recipients (NFT creators) are underpaid or overpaid mojos/CATs depending on which side of the value skew their NFT falls on — a genuine misdistribution/loss-of-funds condition for the correct royalty beneficiaries, reachable purely through normal wallet offer-creation flow (`make_nft1_offer`) without any privileged access.

### Likelihood Explanation
This requires a wallet user (maker or taker) to bundle two or more royalty-enabled NFTs of differing value in a single offer alongside fungible assets — a scenario explicitly supported by the offer-building code path (`royalty_nft_asset_dict`, `offer_side_royalty_split`/`request_side_royalty_split` counters) and exercised in the test suite (`test_complex_nft_offer`), so it is a normal, easily triggered usage pattern rather than an edge case requiring privileged access.

### Recommendation
Weight each NFT's royalty payment by its actual/implied value relative to the other NFTs in the bundle instead of an even count-based split — e.g., require per-NFT trade prices to be specified explicitly in `offer_dict`/`driver_dict` when bundling multiple differently-priced royalty NFTs, and use those individual weights in `compute_royalty_amount` and `royalty_calculation` rather than dividing by `royalty_split`/`len(royalty_assets_dict)`.

### Proof of Concept
Using the existing royalty unit tests as a template: `test_royalty_split_across_multiple_nfts` in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py` (lines 24-26) shows `compute_royalty_amount(offered_amount=-2_000_000, royalty_split=2, percentage=1000)` returning `100_000`, i.e., each of the 2 NFTs is credited royalty on an even `1_000_000` share of the pooled `2_000_000` amount regardless of each NFT's real relative value. Constructing an offer via `NFTWallet.make_nft1_offer` with two royalty NFTs of very different real value (e.g., one worth 10x the other) bundled against one fungible request reproduces the same equal-split miscalculation end-to-end, analogous to the PoC in the original report where `user2` (10% royalty on the 10x-valued NFT) should receive 100x `user1`'s royalty but only receives 10x. def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
```python
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```

```python
                    }
                )
```
