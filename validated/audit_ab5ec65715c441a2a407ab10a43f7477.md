### Title
Missing upper-bound validation of `PackageMetadata.upgrade_policy.policy` permanently bricks package upgradability - (File: `aptos-move/framework/aptos-framework/sources/code.move`)

### Summary
`code::publish_package` only checks that `pack.upgrade_policy.policy` is greater than the "arbitrary" value (0), but never validates that it is one of the three well-defined enum values (`arbitrary = 0`, `compatible = 1`, `immutable = 2`). Because `PackageMetadata` (and its nested `UpgradePolicy`) is deserialized directly from raw, caller-supplied BCS bytes via `util::from_bytes` in `publish_package_txn`, any `u8` value can be placed into the `policy` field, bypassing the type-safe constructors `upgrade_policy_arbitrary/compat/immutable`. Any policy value `>= 2` is treated identically to `immutable` by `check_upgradability`, permanently locking the package from ever being upgraded again, even though the owner never intended to publish an immutable package.

### Finding Description [1](#0-0) : `publish_package` only enforces
```
assert!(pack.upgrade_policy.policy > upgrade_policy_arbitrary().policy, error::invalid_argument(EINCOMPATIBLE_POLICY_DISABLED));
```
i.e. `policy > 0`. There is no `assert!(pack.upgrade_policy.policy <= upgrade_policy_immutable().policy)` or equivalent enum-range check anywhere in the module. [2](#0-1)  shows that the entry point deserializes attacker/tool-supplied bytes directly into the `PackageMetadata` struct with `util::from_bytes`, which performs a raw BCS deserialization and does not go through the `upgrade_policy_arbitrary()/upgrade_policy_compat()/upgrade_policy_immutable()` constructors that are the *only* places in the module that produce "valid" enum values. Any `u8` (e.g. `250`) can therefore end up in `pack.upgrade_policy.policy`. [3](#0-2) : `check_upgradability`, which runs on every subsequent republish attempt, gates on
```
assert!(old_pack.upgrade_policy.policy < upgrade_policy_immutable().policy, error::invalid_argument(EUPGRADE_IMMUTABLE));
```
`upgrade_policy_immutable().policy == 2`, so any previously stored policy `>= 2` (not just the canonical `2`) fails this check identically to a genuinely immutable package. Once a package is published with e.g. `policy = 250`, `check_upgradability` will abort on every future upgrade attempt with `EUPGRADE_IMMUTABLE`, with no way to ever change it back (there is no "downgrade" path — `can_change_upgrade_policy_to` also only allows the policy to increase).

The Move spec for the module explicitly calls out this exact requirement as "Critical" and claims it is only manually audited, not code-enforced: [4](#0-3)  ("The arbitrary upgrade policy should never be used... Enforcement: Manually audited that it aborts if package.upgrade_policy.policy == 0.") — no analogous requirement/enforcement is stated (or exists) for the *upper* bound of the policy field.

### Impact Explanation
A package publisher (via a buggy SDK, a malformed offline-signed payload, a bug in tooling that serializes `PackageMetadata`, or bit-corruption while constructing the metadata bytes) can accidentally set `upgrade_policy.policy` to any value `>= 2`. The very first publish transaction succeeds (only the `> 0` check is enforced), but the package becomes permanently non-upgradable — indistinguishable in effect from `immutable`, yet the owner had no chance to review/confirm an immutability commitment (there is no distinct code path or confirmation for "immutable" vs. this accidental value). This is high impact: any bug in the published module (including security bugs) can never be patched at that address; for object-code deployments, `freeze_code_object`/`upgrade` in `object_code_deployment.move` inherit the same restriction, so funds/resources controlled by that code become effectively unmaintainable, mirroring the "almost permanently locked tokens" impact described in the seed report — except here it is *code* (and anything gated behind it) that is permanently locked rather than tokens directly.

### Likelihood Explanation
Low, matching the seed report's likelihood assessment: it requires a malformed/buggy metadata construction (fat-finger analog) rather than a directly exploitable attacker-controlled path, since normal Aptos CLI/SDK flows always go through `upgrade_policy_arbitrary()/compat()/immutable()`. However, since `publish_package_txn` accepts raw serialized bytes from any transaction sender for their own address, any third-party tool, custom script, or slightly corrupted BCS payload can trigger it without any privileged access.

### Recommendation
Add an explicit upper-bound / enum-membership check in `code::publish_package` (and ideally directly after BCS deserialization in `publish_package_txn`), e.g.:
```
assert!(
    pack.upgrade_policy.policy <= upgrade_policy_immutable().policy,
    error::invalid_argument(EINVALID_UPGRADE_POLICY)
);
```
so that only the three defined values (`0`, `1`, `2`) are ever accepted, consistent with how the CrowdSale report recommends adding both min and max bounds rather than only one side of the range.

### Proof of Concept
1. Craft a `PackageMetadata` BCS blob identical to a normal package except set the `upgrade_policy.policy` byte to `250` instead of `1` (compatible) — this bypasses `upgrade_policy_compat()`/`upgrade_policy_arbitrary()`/`upgrade_policy_immutable()` entirely since BCS deserialization does not call these constructors.
2. Submit `code::publish_package_txn(owner, metadata_serialized, code)` (or via `aptos_stdlib::code_publish_package_txn`) with this blob. The only current guard, `policy > upgrade_policy_arbitrary().policy` (i.e. `250 > 0`), passes, so the transaction succeeds and stores `upgrade_policy.policy = 250` in `PackageRegistry`.
3. Attempt to republish (upgrade) the same package with valid, compatible bytecode via `publish_package` again. `check_upgradability` evaluates `old_pack.upgrade_policy.policy < upgrade_policy_immutable().policy` → `250 < 2` → `false`, aborting with `EUPGRADE_IMMUTABLE`. The package can never be upgraded again, confirming the permanent lock, even though `250` was never intentionally chosen as "immutable".

Note: I was unable to fully verify from the index whether any additional guard exists in the Rust-side native `request_publish`/`request_publish_with_allowed_deps` implementation (`aptos-move/framework/natives/src/code.rs`) that might reject out-of-range policy bytes before they are persisted — the grep only found the `ARBITRARY_POLICY` constant reference without full context of its surrounding validation logic, so if further verification is needed, this file should be reviewed in full.
