### Title
`SchnorrAggregate::verify` accepts a forged signature for an empty signer set — missing validation lets an unauthenticated "aggregate signature" verify successfully - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The Gym Network exploit class is *crediting/accepting an action without verifying the party actually authorized it* (deposits credited with no payment due to a missing caller check). The direct analog in Serai's in-scope code is `SchnorrAggregate::verify`, which accepts an aggregate `SchnorrAggregate { Rs: [], s: 0 }` as valid when `keys_and_challenges` is empty — i.e., a completely unsigned, unauthenticated blob passes signature verification.

### Finding Description
`SchnorrAggregate::read` accepts a length-prefixed vector of `R` points with `len == 0` and any scalar `s` (crypto/schnorr/src/aggregate.rs:77-88). `verify` then only checks `self.Rs.len() != keys_and_challenges.len()`, computes transcript weights over the challenges, and queues the multiexponentiation `pairs`. When both are empty, `pairs` contains only `(-s, G)`; with `s == 0` the multiexp is the identity and `verify` returns `true` (crypto/schnorr/src/aggregate.rs:127-146).

There is no check that at least one signer/challenge is present — the exact analogue of Gym's "no caller verification": the verifier never requires any real authorization input, so a forged empty aggregate is accepted wherever an aggregate Schnorr signature gates a privileged action (e.g., attestation of received funds, batch approval).

### Impact Explanation
An unprivileged attacker can serialize `[0x00;4] ++ s(0)` via `SchnorrAggregate::read`/`serialize` and have it accepted by `verify` for an empty key set. Wherever the calling protocol interprets a passing aggregate as "the validator set approved X", this is a signature forgery enabling unauthorized state transitions — conceptually identical to Gym crediting deposits that were never paid.

### Likelihood Explanation
Requires a caller of `verify` to ever evaluate an empty `keys_and_challenges` list (e.g., a set that is populated from attacker-controlled data and can be empty). `read` places no lower bound on `Rs`, so attacker-supplied bytes can produce the empty aggregate. Whether any production caller can reach this state determines practical severity; the verifier itself makes no defense.

### Recommendation
Reject empty inputs in `SchnorrAggregate::verify`: return `false` when `self.Rs.is_empty()` or `keys_and_challenges.is_empty()`, and consider rejecting `len == 0` in `SchnorrAggregate::read`. Alternatively, have callers enforce a minimum signer count, but enforcing non-emptiness in the verifier removes the foot-gun.

### Proof of Concept
```rust
// crypto/schnorr/src/aggregate.rs semantics:
let agg = SchnorrAggregate::<C> { Rs: vec![], s: C::F::ZERO };
// Or equivalently: SchnorrAggregate::read(&[0,0,0,0, /* s = 0 */])
assert!(agg.verify(b"any dst", &[]));
// Rs.len() == keys_and_challenges.len() == 0 passes the length check;
// pairs = [( -0, G )] → multiexp_vartime == identity → verify returns true.
```
The forgery is 36 bytes of attacker-controlled data (`0x00000000` length prefix plus the zero scalar encoding) and requires no private key, no valid nonce, and no cooperation from any signer.
