## Title
Unbounded recursive RLP decoding of `AccountKeyRoleBased` allows stack-overflow DoS via a crafted `TxTypeAccountUpdate` transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each sub-key of a role-based account key by calling `rlp.DecodeBytes` on nested byte blobs, and each sub-key may itself be another `AccountKeyRoleBased`. There is no depth limit enforced during decoding — the only safeguard (`CheckInstallable`, which rejects composite/nested types) runs only *after* decoding fully succeeds. A crafted transaction containing deeply nested role-based keys can therefore drive unbounded Go call-stack recursion during RLP parsing, analogous to the CVE-2018-8002 PoDoFo bug class (unbounded recursive parsing of attacker-controlled structured input leading to stack exhaustion/DoS), but reachable here from an ordinary submitted transaction rather than a local file.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of byte strings and, for each element, invokes `rlp.DecodeBytes(b, &serializer)` where `serializer` is an `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type and dispatches to `NewAccountKey`, then decodes the concrete key (which can again be `AccountKeyRoleBased`): [2](#0-1) 

Because each nesting level uses a brand-new `rlp.DecodeBytes` call (a fresh `Stream`), any list-nesting bookkeeping internal to a single `rlp.Stream` (e.g. `stack []uint64` in `rlp/decode.go`) is reset at every level and provides no cross-call depth protection: [3](#0-2) 

The only rejection of nested composite keys, `IsCompositeType`/`CheckInstallable`, is applied only *after* the whole structure has already been fully decoded: [4](#0-3) 

This is invoked from `checkAccountKeyZeroValues`/tx validation flows, all of which occur only after `DecodeRLP` returns successfully — meaning a payload that never finishes decoding (because it crashes the goroutine first) never reaches this check: [5](#0-4) 

An attacker can build an `AccountUpdate` (or `FeeDelegatedAccountUpdate`) transaction whose account key is `AccountKeyRoleBased` containing another `AccountKeyRoleBased`, nested many thousands of times, each level adding only a few bytes of RLP framing overhead. Because `MaxTxDataSize` is 128KB, an attacker has ample headroom to nest deeply enough to exhaust the goroutine's growable stack: [6](#0-5) 

Unlike a Go panic, a genuine runtime stack-overflow (`morestack`/fatal error: stack overflow) is **not recoverable** and terminates the entire process, unlike an ordinary decode error which is caught and returned safely by callers such as `pool.validateTx`.

### Impact Explanation
Any unprivileged party able to submit a transaction to the mempool (`TxPool.AddRemote`) or include it in a block can trigger this path merely by crafting the RLP bytes directly (bypassing normal encode-side protections such as `CheckInstallable`, since `AccountUpdate`/`AccountKeyRoleBased` objects can be assembled programmatically and RLP-encoded without going through the installable-key validation that only runs post-decode). A successful trigger crashes the node process handling the transaction (mempool ingestion, RPC `eth_sendRawTransaction`, block/tx propagation, or block validation during sync) — a full denial of service, not just a resource-exhaustion warning, because it crashes rather than merely slows the process.

### Likelihood Explanation
Likelihood is high for any node that decodes attacker-supplied raw transaction bytes before running key-specific composite-type checks: this includes `eth_sendRawTransaction`/`kaia_sendRawTransaction` RPC handlers, p2p transaction gossip ingestion, and `TxPool.AddRemote`/`validateTx`. No special privileges, staking, or governance access are required — only crafting and submitting one oversized-but-within-limit RLP transaction.

### Recommendation
Enforce a maximum recursion/nesting depth for `AccountKeyRoleBased`/`AccountKeySerializer` decoding (e.g., pass a depth counter through `DecodeRLP` and reject with an error once a small limit such as 1–2 levels is exceeded), matching the semantic rule already enforced in `CheckInstallable` that role-based keys must not contain nested composite keys. This check must happen during decoding, not only afterward.

### Proof of Concept
1. Programmatically build nested Go values:
```go
key := accountkey.AccountKey(accountkey.NewAccountKeyPublicWithValue(pub))
for i := 0; i < N; i++ { // N large enough, e.g. tens of thousands
    key = accountkey.NewAccountKeyRoleBasedWithValues([]accountkey.AccountKey{key})
}
```
2. RLP-encode this key via `AccountKeySerializer`/`AccountKeyRoleBased.EncodeRLP` and embed it in an `AccountUpdate` transaction's key field, keeping total tx size under `MaxTxDataSize` (128KB) by using minimal sub-key content at the innermost level.
3. Submit the raw transaction bytes to a node's `TxPool.AddRemote`/RPC endpoint; `Transaction.DecodeRLP` → `TxInternalDataAccountCreation`/Update `DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recurse N times before any `CheckInstallable`/`IsCompositeType` rejection can occur, exhausting the goroutine stack and crashing the process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
```

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}

func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
```
