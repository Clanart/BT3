### Title
Attacker-controlled `WWW-Authenticate` realm header from a plain HTTP(S) remote spoofs GitHub host classification and redirects the OAuth/Enterprise sign-in flow to the attacker's endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's git credential helper decides whether a remote host is trusted as `github.com`/`enterprise` or treated as `generic` by inspecting a `WWW-Authenticate` header value that Git forwards verbatim from the remote server's HTTP response. This classification is attacker-controlled data used to select the destination of a security-sensitive action (which sign-in/credential flow to invoke), analogous to the Waterusdc bug where an untrusted/incorrect destination value was used for a fee transfer instead of validating the intended recipient.

### Finding Description
`getEndpointKind` in [1](#0-0)  classifies a remote endpoint as `'enterprise'` purely because the credential map contains a `wwwauth[...]` entry whose value includes `realm="GitHub"`: [2](#0-1) 

This header comes from the remote server's HTTP response and is passed through by git's credential protocol into `cred`, i.e., it is fully attacker-controlled if the user adds/fetches/pushes to any HTTP(S) remote under attacker control (a git remote or proxy response — one of the explicitly accepted attacker primitives).

When `getCredential` runs and this classification says `'enterprise'` (not `'generic'`) but no existing `Account` matches the endpoint, Desktop does not just decline — it actively invokes `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn` then starts an Enterprise sign-in flow *pointed at the attacker's origin* and shows a sign-in dialog to the user: [4](#0-3) 

The only gate preventing an untrusted host from reaching this path is the string match on the `realm="GitHub"` value inside a header the attacker's own server supplies — there is no verification (e.g., contacting the real GitHub API, checking TLS certificate identity beyond hostname, or requiring an out-of-band trust decision) before triggering the sign-in UI aimed at that host. The existing guard `isGitHubHost(endpoint)` (an actual network probe) is only reached later in the fallback path and is *bypassed entirely* once the `wwwauth[...]` shortcut matches.

### Impact Explanation
An attacker who controls (or can MITM/proxy) any HTTP(S) git remote can cause GitHub Desktop to:
1. Believe the remote is a "GitHub" host (`'enterprise'` classification) purely by returning a crafted `WWW-Authenticate: Basic realm="GitHub"` response.
2. Trigger `dispatcher.beginEnterpriseSignIn` / `setSignInEndpoint(origin)` against the attacker's origin and pop the "Sign in to GitHub Enterprise" dialog with that origin as the target.

If the victim proceeds with the resulting sign-in flow — believing it originates from a legitimate corporate/enterprise GitHub instance because the Desktop UI itself initiated it — any credentials or OAuth authorization completed against that flow are directed to the attacker's server rather than the real GitHub Enterprise/`github.com` endpoint. This mirrors the report's root cause: a value that should route a sensitive resource (fee → vault) is instead routed to an untrusted destination (real GitHub identity/session → attacker endpoint) because of insufficient validation of the destination selection logic.

### Likelihood Explanation
Likelihood is limited by the need for user interaction to complete the resulting sign-in dialog, but the trigger itself requires no user action beyond a normal git network operation (`fetch`/`pull`/`push`/clone) against an attacker-supplied remote URL — something Desktop performs automatically as part of routine background fetches. The `wwwauth[...]` shortcut is explicitly designed as a "happy path" to *avoid* the more rigorous `isGitHubHost` network check, which weakens the trust decision specifically for hosts that are not already `dotcom`/`ghe.com`.

### Recommendation
Do not treat the `wwwauth[...]` `realm="GitHub"` header as authoritative for classifying a host as a genuine GitHub/Enterprise endpoint before initiating a sign-in flow that targets that host. At minimum:
- Require the authoritative `isGitHubHost()` network probe (which validates against real GitHub API responses) before showing the sign-in prompt for any endpoint not already a known/trusted account endpoint.
- Surface the exact destination host prominently in the sign-in dialog and require explicit user confirmation that they intend to authenticate against that specific, unfamiliar host.
- Consider removing or restricting the `wwwauth[...]` heuristic to only *supplement* (never substitute for) the network-based verification.

### Proof of Concept
1. Attacker sets up an HTTP(S) git server (or a MITM proxy in front of a legitimate-looking URL) that, on an unauthenticated git-over-HTTP request, responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote in GitHub Desktop (or clones it) and performs a fetch/pull.
3. Git's credential protocol forwards the `wwwauth[...]` entry to Desktop's trampoline credential helper.
4. `getEndpointKind` matches the `realm="GitHub"` string and returns `'enterprise'` without any real verification of the host: [5](#0-4) 
5. Since no `Account` exists for this endpoint, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)`, which begins an Enterprise sign-in flow bound to the attacker's origin and shows the Desktop sign-in dialog: [6](#0-5) 
6. If the victim completes the sign-in believing it's a normal Enterprise authentication prompt from Desktop, their credentials/OAuth authorization are sent to the attacker-controlled origin instead of a legitimate GitHub host.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
