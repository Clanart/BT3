### Title
Inconsistent path-traversal/symlink validation lets a malicious repo's tracked symlink be opened/revealed outside the repository via "Reveal in Finder"/"Open with Default Program" - (File: app/src/lib/app-shell.ts)

### Summary
Desktop has a dedicated safe-path helper, `resolveWithin`, that resolves a repo-relative path and rejects it (returns `null`) if it escapes the repository root — including via symlinks, since it compares `realpath()` of the resolved path against `realpath()` of the root. [1](#0-0) 
This guard is explicitly applied when opening a file from a deep link (`openRepositoryFromUrl`) and when reading conflict file contents for Copilot (`buildConflictContext`), both annotated as protecting "against path traversal and symlink escapes." [2](#0-1) [3](#0-2) 

However, the much more commonly used `revealInFileManager` helper — and every UI action that calls it or `openFile` on repository/changed/conflicted file paths — builds the on-disk path with a plain `Path.join(repository.path, path)`/`join(repository.path, path)` and never runs it through `resolveWithin`, even though `IAppShell` itself documents that `openPath`/`showItemInFolder` must "not [be used] with non-validated paths." [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
`path` values reaching `revealInFileManager`/`openFile` come directly from git status entries for the working directory, conflicted merge files, and committed/PR files — all of which are derived from an attacker-controlled cloned/fetched repository:
- Merge-conflict UI: `join(repository.path, relativeFilePath)` then `revealInFileManager(...)`/`openFile(absoluteFilePath, ...)`. [7](#0-6) 
- Copilot conflict resolution overflow menu: `join(repository.path, path)`. [8](#0-7) 
- Changes list / PR files-changed / history file list context menus all call `revealInFileManager(repository, file.path)` and `Path.join(repository.path, file.path)` for "Open with Default Program"/copy-path actions. [9](#0-8) [10](#0-9) 

Git tracks and checks out symlinks (mode `120000`) verbatim as normal filesystem symlinks. A malicious repository can therefore commit a tracked path (e.g. `notes.txt`) that is a symlink pointing to an absolute location outside the working directory (e.g. a predictable sensitive file on the victim's machine, or an application bundle). After the victim clones/fetches and merges (creating a conflict, or simply viewing "Changes"/"Files changed"), that tracked symlink shows up as a normal file entry. Because `revealInFileManager`/`openFile` never route the path through `resolveWithin` (unlike the deep-link and Copilot-conflict-context code paths that do), the OS-level `shell.showItemInFolder`/`shell.openExternal('file://...')` call follows the symlink and reveals or opens whatever the symlink target is — a location entirely outside the cloned repository. This is the exact same class of bug as the report's root cause: two logically-equivalent "resolve/validate an untrusted repo-relative path before acting on it" decisions are implemented with different rigor, and the weaker one is reachable in practice (conflict resolution, changes list, PR review), defeating the intent of the stronger guard that exists elsewhere in the same codebase.

### Impact Explanation
This allows reading/opening a file (or listing/revealing a folder) outside the cloned repository, driven entirely by content the attacker fully controls (a tracked symlink target path in their repository) — matching the accepted impact category "file write or read outside the repo" triggered by cloning/fetching a malicious repository and performing ordinary, expected UI actions (viewing changes, resolving a conflict, reviewing a PR diff).

### Likelihood Explanation
The path is very short: any repository with a tracked symlink pointing outside the repo (a normal, one-line addition to any Git repo) will surface the symlinked entry in the Changes tab, PR "Files changed" view, or merge-conflict dialog. Right-clicking and choosing "Reveal in Finder"/"Show in Explorer" or "Open with Default Program" is a standard, expected interaction — no unusual steps are required, and `isSafeFileExtension` only restricts a handful of extensions on Windows, leaving macOS/Linux and most extensions unguarded. [11](#0-10) 

### Recommendation
Route every repository-relative path used by `revealInFileManager`, `openFile`, and their call sites (changed files, conflicted files, PR/commit files) through `resolveWithin` (as already done in `openRepositoryFromUrl` and `buildConflictContext`) before calling `shell.showItemInFolder`/`shell.openExternal`/`shell.openPath`, and refuse the action (with a user-facing error) when the resolved path escapes the repository root.

### Proof of Concept
1. Attacker creates a public repository containing a tracked symlink `notes.txt -> /Users/victim/Library/Application Support/GitHub Desktop/some-sensitive-file` (or any predictable absolute path), committed with `git add` after `ln -s` (mode `120000`).
2. Victim clones the repository in GitHub Desktop (or it appears as a conflicted/changed file after a fetch/merge).
3. Victim opens the Changes tab (or a PR's "Files changed" view / a merge conflict dialog), right-clicks `notes.txt`, and selects "Reveal in Finder" or "Open with Default Program".
4. `revealInFileManager`/`openFile` compute `Path.join(repository.path, 'notes.txt')` with no `resolveWithin` check [12](#0-11)  and hand it to `shell.showItemInFolder`/`shell.openExternal`, which the OS resolves through the symlink, revealing/opening the file outside the repository — unlike the deep-link handler, which would have rejected this path via `resolveWithin`. [13](#0-12)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
