### Title
KIP-160 Treasury Rebalancing Allows Unbounded KAIA Supply Inflation Due to Missing Zeroed/Allocated Balance Check - (File: blockchain/system/rebalance.go)

### Summary
`RebalanceTreasury` executes a hard-fork-triggered state transition that zeroes out a set of "retired" treasury addresses and reallocates arbitrary amounts to a set of "newbie" addresses. For KIP-103 rebalances, the code enforces `totalZeroedAmount >= totalAllocatedAmount` before executing, guaranteeing that any excess is burnt rather than minted. For KIP-160 rebalances this check is skipped entirely, and the corresponding on-chain contract (`TreasuryRebalanceV2`) also does not enforce this invariant at `finalizeApproval()` time (unlike the V1 `TreasuryRebalance` contract, which explicitly reverts if `treasuryAmount > sum of retired balances`).

### Finding Description
`RebalanceTreasury` reads the `TreasuryRebalanceV2` (KIP-160) or `TreasuryRebalance` (KIP-103) system contract at the target rebalance block and performs a state transition that sets all "zeroed" addresses' balances to zero and sets all "allocated" addresses' balances to the amounts recorded in the contract: [4](#0-3) 

The sufficiency check that guards against allocating more KAIA than was zeroed out is gated by `isKIP103`:
```go
if isKIP103 && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
    return result, ErrRebalanceNotEnoughBalance
}
``` [5](#0-4) 

For KIP-160, `caller` is `TreasuryRebalanceV2Caller`, whose `Allocateds()`/`amounts` are populated solely via `registerNewbie(address, uint256 amount)` and `testSetAll(...)`, with no cap tied to the sum of registered `zeroeds`' balances anywhere in `TreasuryRebalanceV2.sol`. `finalizeApproval()` only validates approver quorum via `checkZeroedsApproved()`; it performs no comparison between allocated amounts and zeroed balances [2](#0-1) . Compare this to the legacy V1 flow, which explicitly reverts `finalizeApproval()` in this scenario with `"treasury amount should be less than the sum of all retired address balances"` [1](#0-0) .

Consequently, once a KIP-160 `TreasuryRebalanceV2` contract reaches `Status.Approved` with `sum(allocated amounts) > sum(zeroed balances)`, the state transition in `RebalanceTreasury` will still execute successfully (the KIP-160 branch has no guard), zeroing the retired addresses and unconditionally crediting the newbie addresses with the registered (potentially inflated) amounts. The `Burnt` field computed by the code (`remainder := totalZeroedAmount - totalAllocatedAmount`) becomes negative, meaning net new KAIA is minted into circulation rather than burnt, exactly analogous to the reported vault bug class where a missing/absent guard around a computed "target" value (here, the zeroed/allocated balance delta) allows an operation to proceed into an invalid, value-creating state instead of being safely rejected or requiring remediation first.

### Impact Explanation
This is a supply-inflation vector: any KIP-160 rebalance approved by the contract owner/admin flow with `allocated > zeroed` mints net-new KAIA directly into arbitrary "newbie" addresses at the hardfork block, silently increasing total supply and diluting all holders — a direct, concrete violation of the "no unauthorized value movement/supply inflation" acceptance criterion. Because this executes as part of core state-transition logic tied to the block header (`IsKIP160ForkBlock`), it also creates state divergence risk between nodes if the underlying contract data differs from expectations, and would be accepted into canonical state by honest nodes running this code without any error being raised.

### Likelihood Explanation
The KIP-160 treasury rebalance mechanism is designed to be governed by contract owner-controlled registration/approval steps (`registerNewbie`, `approve`, `finalizeApproval`), which are the trust boundary the sherlock-analog concern is calling out: any code path where enforcement of an economic invariant is silently dropped for one enum/branch relative to a sibling branch is exactly the "order of operations / missing validation" pattern described in the analog report (rebalancing proceeding without properly bounding a target amount). Because the safety check is entirely absent for `isKIP160` (not merely misordered), and the contract itself provides no compensating validation, a single administrative rebalance execution — reachable at a network hardfork event without any additional protocol safeguard in the Go execution code — is sufficient to trigger inflation.

### Recommendation
Add the same sufficiency check for the KIP-160 branch as is enforced for KIP-103:
```go
if (isKIP103 || isKIP160) && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
    return result, ErrRebalanceNotEnoughBalance
}
```
Additionally, add an equivalent on-chain `require` in `TreasuryRebalanceV2.finalizeApproval()` (mirroring the V1 `TreasuryRebalance` contract's check) so the invariant is enforced at both the contract level and the core state-transition level, defense-in-depth.

### Proof of Concept
1. Deploy `TreasuryRebalanceV2` and register a zeroed address with balance `X` (e.g., 1,000,000 wei) and a newbie address with `amount = X * 1000` via `registerNewbie`.
2. Call `finalizeRegistration()`, have the zeroed address approve via `approve()`, then call `finalizeApproval()` — this succeeds because `finalizeApproval()` in V2 only checks approver quorum, not amount sufficiency.
3. At the configured `rebalanceBlockNumber`, the node executes `RebalanceTreasury(state, chain, header)`. Because `isKIP160` is true and `isKIP103` is false, the `totalZeroedAmount.Cmp(totalAllocatedAmount) < 0` guard at [5](#0-4)  is skipped.
4. Execution proceeds to zero the retired address and credit the newbie address with the full inflated `amount`, producing `result.Burnt` as a large negative number — i.e., net KAIA supply increase — with `result.Success = true` and no error returned, exactly as demonstrated by the existing "net mint" test case in the test suite for the KIP-103 path (`big.NewInt(-2987655)` burnt with `success: true`) [6](#0-5) , except for KIP-160 this negative-burn/mint scenario is reachable without any guard rejecting it first.

// RebalanceTreasury reads data from a contract, validates stored values, and executes treasury rebalancing (KIP-103, KIP-160).
// It can change the global state by removing old treasury balances and allocating new treasury balances.
// The new allocation can be larger than the removed amount, and the difference between two amounts will be burnt.
func RebalanceTreasury(state *state.StateDB, chain backends.BlockChainForCaller, header *types.Header) (*rebalanceResult, error) {
	var (
		err    error
		caller RebalanceCaller

		result   = newRebalanceReceipt()
		isKIP160 = chain.Config().IsKIP160ForkBlock(header.Number)
		isKIP103 = chain.Config().IsKIP103ForkBlock(header.Number)
	)

	if isKIP160 {
		caller, err = rebalance.NewTreasuryRebalanceV2Caller(chain.Config().Kip160ContractAddress, backends.NewBlockchainContractBackend(chain, nil, nil))
	} else if isKIP103 {
		caller, err = NewKip103ContractCaller(state, chain, header)
	} else {
		return nil, errors.New("rebalancing shouldn't be executed unless the block number is kip103 or kip160 hard fork")
	}
	if err != nil {
		return nil, err
	}

	// Retrieve 1) Get Zeroed
	if err = result.fillZeroed(caller, state); err != nil {
		return result, err
	}

	// Retrieve 2) Get Allocated
	if err = result.fillAllocated(caller, state); err != nil {
		return result, err
	}

	// Validation 1) Check the target block number
	if blockNum, err := caller.RebalanceBlockNumber(nil); err != nil || blockNum.Cmp(header.Number) != 0 {
		return result, ErrRebalanceIncorrectBlock
	}

	// Validation 2) Check whether status is approved. It should be 2 meaning approved
	if status, err := caller.Status(nil); err != nil || status != 2 {
		return result, ErrRebalanceBadStatus
	}

	// Validation 3) Check approvals from zeroeds
	if err = caller.CheckZeroedsApproved(nil); err != nil {
		return result, err
	}

	// Validation 4) Check the total balance of zeroeds are bigger than the distributing amount
	totalZeroedAmount := result.totalZeroedBalance()
	totalAllocatedAmount := result.totalAllocatedBalance()
	if isKIP103 && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
		return result, ErrRebalanceNotEnoughBalance
	}

	// Execution 1) Clear all balances of zeroeds
	for addr := range result.Before.Zeroed {
		state.SetBalance(addr, big.NewInt(0))
		result.After.Zeroed[addr] = big.NewInt(0)
	}
	// Execution 2) Distribute KAIA to all allocateds
	for addr, balance := range result.After.Allocated {
		// if an allocated has KAIA before the allocation, it will be burnt
		currentBalance := state.GetBalance(addr)
		result.Burnt.Add(result.Burnt, currentBalance)

		state.SetBalance(addr, balance)
	}

	// Fill the remaining fields of the result
	remainder := new(big.Int).Sub(totalZeroedAmount, totalAllocatedAmount)
	result.Burnt.Add(result.Burnt, remainder)
	result.Success = true
	return result, nil
}
