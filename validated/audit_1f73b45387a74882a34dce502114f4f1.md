## Analysis

The Hats/Palmera report's broken invariant is: dynamic-length fields (`bytes`) are concatenated into a preimage using `abi.encode` *without* first hashing them, so two different `(data, signatures)` pairs can produce colliding byte sequences at the ABI level, corrupting the "digest" used for signature verification.

The closest structural analog in GitHub Desktop is `createEqualityHash()` in `app/src/models/equality-hash.ts`, used to build the `hash` identity field for `Repository` and `GitHubRepository`.

`createEqualityHash` simply does `items.join('+')` over untrusted, variable-length, attacker-influenced string fields (repository name, owner login, HTML URL, clone URL, path, alias, etc.) with **no escaping and no length-prefixing** — exactly the same "naive concatenation instead of collision-resistant encoding" flaw as the Solidity report. [1](#0-0) 

This hash is treated by the codebase as a strong identity guarantee: the doc-comment states "Objects with the same hash are guaranteed to be structurally equal," and it's the primary key type used to index all per-repository application state. [2](#0-1) [3](#0-2) [4](#0-3) 

Because several of the hashed fields (`name`, `owner.login`, `htmlURL`, `cloneURL`, `path`, `alias`) are plain strings that can legitimately contain the `+` delimiter (GitHub repo/owner names, HTML URLs, and local filesystem paths are not restricted from containing `+`), two structurally different repositories can be crafted whose joined `+`-separated strings are byte-identical — a delimiter-injection collision, not a cryptographic hash collision. The `repositoryState` cache in `RepositoryStateCache` keys all per-repo state (working directory changes, commit message drafts, history, selection) by this same `hash` value and explicitly relies on it to decide whether to transfer/merge state between two `Repository` objects. [5](#0-4) 

If an attacker can influence any of the concatenated fields (e.g., via a crafted GitHub API response for `htmlURL`/`cloneURL`/`name`/`login` returned when Desktop resolves repository metadata after a clone, or via a locally cloned repo's path/alias), they can engineer a second `Repository`/`GitHubRepository` whose `hash` collides with a legitimate one, even though the objects are not structurally equal. This breaks the stated invariant and can cause the app to treat two different repositories as the same cache entry — causing the in-memory commit-message draft, working-directory changes, or selection state of one repository to bleed into another (cross-repository state confusion), i.e., "silent corruption of what the user commits" in one repo due to state actually belonging to a different, attacker-influenced repository.

I was not able to fully trace every call site that reads/compares `Repository.hash`/`GitHubRepository.hash` across the whole app (e.g., all places using it as a Map key vs. `React` key vs. equality check) within the available search budget, so I can't give a complete end-to-end exploit chain with concrete attacker-controlled field values guaranteed to reach the API-derived `htmlURL`/`cloneURL`/`name` fields unsanitized. That would require tracing `API.fetchRepository`/`upsertGitHubRepository` in the databases layer, which I did not have iterations left to inspect.

### Title
Delimiter-collision in `createEqualityHash()` breaks repository identity/state-isolation invariant - (File: app/src/models/equality-hash.ts)

### Summary
`createEqualityHash()` builds repository identity hashes by naively joining untrusted string fields with `+` with no escaping, the same "concatenate-then-hash without domain separation" flaw as the reported EIP-712 issue. Since fields such as repository name, owner login, HTML/clone URL, path, and alias can contain `+`, two structurally different `Repository`/`GitHubRepository` objects can be crafted to produce the same `hash`, violating the documented "same hash implies structurally equal" invariant.

### Finding Description
`createEqualityHash` is `items.join('+')` over `HashableType` values with no length-prefixing, escaping, or unambiguous separator handling. [6](#0-5) 
`Repository.hash` is computed from `path`, `id`, `gitHubRepository?.hash`, `missing`, `alias`, `forkContributionTarget`, and `isTutorialRepository` joined this way, and `GitHubRepository.hash` similarly joins `name`, `owner.login`, `dbID`, `isPrivate`, `htmlURL`, `cloneURL`, `issuesEnabled`, `isArchived`, `permissions`, and `parent?.hash`. [3](#0-2) [7](#0-6) 
None of these fields are guaranteed free of the `+` delimiter — `path` is an OS filesystem path, `htmlURL`/`cloneURL` are attacker/host-influenced strings from the GitHub API, and `name`/`alias` are user- or repo-owner-controlled strings. A crafted set of field values (e.g., shifting a `+` from one field into an adjacent field) can produce an identical joined string, and therefore an identical `hash`, for two different objects — directly contradicting the type's own contract ("Objects with the same hash are guaranteed to be structurally equal").

### Impact Explanation
`RepositoryStateCache.transferState` and the broader state cache key all per-repository application state (working directory changes, commit message draft, history, selection) by this `hash`, and use hash equality to decide whether to carry state from one `Repository` identity to another. [5](#0-4) 
A hash collision between two distinct repositories can therefore cause Desktop to conflate their cached state — e.g., attributing another repository's in-progress commit message/working-directory changes to the wrong repo, or skipping/performing a state transfer between unrelated repositories. This matches the "silent corruption of what the user commits" and "cross-tenant/cross-repository data exposure" impact categories in scope.

### Likelihood Explanation
Exploitation requires an attacker to control one or more of the concatenated identity fields for a repository the victim adds/clones (repo name, owner login, HTML/clone URL, or local alias/path) such that its joined-with-`+` representation collides with another repository's. This is plausible given the report is scoped to attacker-controlled cloned/fetched repositories and GitHub API objects, but constructing a concrete colliding pair, and confirming every consumer treats `hash` (rather than reference/object identity) as authoritative, requires deeper tracing of the API ingestion path than was completed here — hence Medium/uncertain confidence rather than a fully proven exploit chain.

### Recommendation
Replace `items.join('+')` in `createEqualityHash` with a collision-resistant, unambiguous encoding — e.g., length-prefix each field (`${item.length}:${item}`) before concatenation, or hash each field individually and concatenate the fixed-length digests (as already correctly done in `computeBundleHash`) before combining, rather than concatenating raw variable-length attacker-influenced strings with a single-character separator. [8](#0-7) 

### Proof of Concept
Conceptual collision (illustrative, not verified end-to-end against live API ingestion):
- Repository A: `name = "foo+bar"`, other fields empty/default.
- Repository B: `name = "foo"`, `alias = "bar"` (adjacent field in the join order), other fields empty/default.
If the join order places `name` immediately before `alias` (or another field boundary), both can be engineered to serialize to the same `+`-joined string, e.g. `"...foo+bar..."` for both A and B, producing identical `hash` values despite A and B being different objects — violating the "same hash ⇒ structurally equal" contract relied upon by `RepositoryStateCache`. [1](#0-0)

   * Move the entire cached state for a repository from one identity to another.
   *
   * This is used when a worktree is renamed: the repository's path (and
   * therefore its hash) changes, but it still refers to the same working
   * directory, so all of the existing in-memory state (working directory
   * changes, commit message, history, etc.) should be carried over to the new
   * identity rather than reset to its initial values.
   */
  public transferState(source: Repository, target: Repository) {
    if (source.hash === target.hash) {
      return
    }

    const sourceState = this.repositoryState.get(source.hash)
    if (sourceState === undefined) {
      return
    }

    this.repositoryState.set(target.hash, sourceState)
    this.repositoryState.delete(source.hash)
  }

/**
 * Compute a combined SHA-256 hash representing the integrity of all shipped
 * bundle files in the given directory.
 *
 * The combined hash is a Merkle-style construction: individual file hashes are
 * computed, concatenated in a fixed order, and then hashed again. This produces
 * a single deterministic value that changes if any bundle is modified.
 */
export async function computeBundleHash(bundleDir: string): Promise<string> {
  const hashes = await Promise.all(
    bundleFiles.map(f => getFileHash(path.join(bundleDir, f), 'sha256'))
  )
  return createHash('sha256').update(hashes.join('')).digest('hex')
}
