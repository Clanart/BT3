### Title
Silent, unconfirmed rewrite of a repository's `origin` remote URL based on unauthenticated GitHub API data - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
GitHub Desktop periodically refetches metadata about a repository's associated GitHub repo (`repositoryWithRefreshedGitHubRepository`) and, if the API's `clone_url` differs from the locally configured remote, silently rewrites the user's `origin` remote via `updateRemoteUrl` — with no user prompt, no diff shown, and no confirmation dialog. This mirrors the `PartyGovernanceNFT` rage-quit bug's core flaw: a value the user relies on as a stable, agreed-upon setting (here, "where my commits get pushed") can be unilaterally overridden by an external, less-trusted party (the upstream GitHub repository's owner/API response) with no guardrail beyond a loose heuristic.

### Finding Description
`updateRemoteUrl` compares the locally configured `origin` remote against `apiRepo.clone_url` returned by `api.fetchRepository(owner, name)`, and if the protocol matches and the remote "looks unchanged" from the last known GitHub clone URL, it calls `gitStore.setRemoteURL` to overwrite the remote — all without any UI confirmation: [1](#0-0) 

This is invoked automatically from `repositoryWithRefreshedGitHubRepository`, part of the routine background repository-refresh flow, not a user-initiated settings change: [2](#0-1) 

The only "guard" is `urlMatchesRemote`/`urlsMatch`, which check hostname/owner/repo-name structurally — they do not verify that the *content* behind that URL is the same repository the user originally trusted, nor do they require any user acknowledgment before the change takes effect: [3](#0-2) 

Contrast this with the manual repository-settings flow, where a remote URL change is staged in UI state and only committed via an explicit "Save" action (`onSubmit` → `dispatcher.setRemoteURL`): [4](#0-3) [5](#0-4) 

The background path has no equivalent confirmation step — it is the exact analog of the rage-quit bug: a security-relevant setting ("where does `origin` point") that the user believes is fixed/agreed-upon (set at clone time) can be silently altered by an external actor's data (the GitHub API response for that repo), overriding the user's existing configuration without notice, consent, or any rate limiting/cooldown.

### Impact Explanation
If an attacker can influence what `api.fetchRepository(owner, name)` returns for a `clone_url` that "matches" structurally (owner/name/hostname) per `urlMatchesRemote` — for example, via a compromised/malicious GitHub Enterprise Server instance the user has added as an account endpoint, or via a repository transfer/rename scenario where the reported `clone_url` no longer corresponds to the content the user expects — Desktop will silently repoint the user's `origin` remote. Because this happens transparently in the background, subsequent `git push` operations initiated by the user could send commits to a different endpoint than the one they configured, corrupting the destination of what the user pushes without their awareness. This satisfies the "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
Likelihood is constrained: for `dotcom` this requires GitHub's own API responses to be adversarial, which is out of scope for an unprivileged attacker without a MITM/compromise. The most realistic trigger is a self-hosted/Enterprise Server endpoint under attacker influence (network position, compromised GHES instance, or a malicious enterprise admin), where `api.fetchRepository` is the sole source of truth and there's no cross-check against the actual git remote's identity beyond structural URL matching. This is a narrower, more speculative path than a straightforward client-side bug, and I could not fully verify additional guard rails (e.g., certificate pinning or endpoint trust prompts) elsewhere in the codebase within the available tool budget — this should be treated as a probable but not fully confirmed condition.

### Recommendation
Apply the same category of safeguards suggested in the original report, adapted to this context:
1. Require explicit user confirmation (a dialog, similar to `UpstreamAlreadyExists`) before silently rewriting `origin`'s URL based on background-refreshed API data — never do it silently.
2. Only auto-update the remote if the repository's stable identifier (e.g., GitHub repo `id`) is unchanged, not just owner/name string matching, to avoid the case where `owner/name` textually matches a different underlying repository.
3. Rate-limit/cooldown this auto-update per repository to avoid repeated silent flips.
4. Log/notify the user distinctly when their `origin` remote is programmatically changed.

### Proof of Concept
1. User clones `github-enterprise.example.com/org/repo` into Desktop; `origin` is set to the corresponding `clone_url`, and `GitHubRepository.cloneURL` is stored matching it.
2. Attacker gains the ability to influence responses from the Enterprise Server API endpoint configured in Desktop's account settings (e.g., DNS hijack, malicious/compromised GHES instance, or an org owner renaming/transferring the repo such that `clone_url` now points to a repository they control under the same `owner/name`, e.g., after a rename-and-recreate).
3. During Desktop's next background refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository(owner, name)` and receives an `apiRepo.clone_url` differing from the current remote but still passing the `urlMatchesRemote`/`remoteUrlUnchanged`/`protocolsMatch` checks in `updateRemoteUrl`.
4. `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` is called automatically — the user is never shown any prompt or diff. [6](#0-5) 
5. The user's subsequent `git push` (through Desktop's UI, unaware of the change) now sends commits to the attacker-influenced remote.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
