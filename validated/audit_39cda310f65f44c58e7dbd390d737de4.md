### Title
Untrusted `ReceivedOutput` deserialization permits forged, unspendable inputs - ([File: networks/bitcoin/src/wallet/mod.rs](https://github.com/blackvul/serai--010/blob/master/networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts an offset, `TxOut`, and `OutPoint` as three independent fields without verifying that the claimed `OutPoint` identifies the embedded output on-chain. This lets an attacker serialize a fabricated wallet input whose script is controlled by the wallet but whose referenced outpoint or amount is false. Downstream transaction construction treats the forged value as spendable, and `SignableTransaction::multisig` only verifies that the embedded `TxOut` script matches the key plus offset, not that the referenced prevout exists or contains that output. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The authentic scanner path constructs `ReceivedOutput` by matching an observed transaction output and deriving `outpoint` from that transaction. [4](#0-3)  In contrast, the public deserializer accepts all three components directly from attacker-controlled bytes and performs only scalar and consensus-decoding checks. [5](#0-4) 

`SignableTransaction::new` copies the attacker-selected amount into `input_sat`, places the attacker-selected `outpoint` into the transaction input, and preserves the embedded `TxOut` as the alleged prevout. [6](#0-5) [7](#0-6)  During signing, the sole semantic validation is that `p2tr_script_buf(keys.offset(offset).group_key())` equals the supplied `prevouts[i].script_pubkey`; there is no validation binding `outpoint` to that script or amount. [3](#0-2) 

This is analogous to the referenced path traversal flaw because a caller-controlled identifier escapes its intended lookup boundary: `outpoint` is supposed to locate the chain object represented by `TxOut`, but the deserializer accepts an arbitrary location independently of the object.

### Impact Explanation
An attacker who can supply serialized `ReceivedOutput` records can cause the wallet to report received funds that do not exist or are not spendable under the encoded `OutPoint`. If the fabricated output uses a script matching `key + offset * G`, the wallet can construct and threshold-sign a transaction consuming the fake record, but the resulting transaction is unusable because its prevout commitment is not backed by the claimed UTXO. [8](#0-7) 

Depending on how the caller uses `value()` or `SignableTransaction::new`, this can inflate observed balances, authorize transfers based on nonexistent funds, exhaust fees in failed broadcast attempts, or deny wallet operation by poisoning the input set. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
Exploitation requires the application to deserialize `ReceivedOutput` from an attacker-controlled source rather than obtaining it solely from `Scanner::scan_transaction` or `Scanner::scan_block`. The constructor used by the scanner safely binds the output to the containing transaction, but `ReceivedOutput::read` does not preserve that invariant when loading serialized records. [4](#0-3) [1](#0-0) 

The attacker does not need a validator, key share, malicious peer implementation, or leaked secret. For the record to survive `multisig`, they only need to encode an arbitrary `Scalar` offset and a `TxOut` whose script is `p2tr_script_buf(wallet_key + offset * G)`, paired with any fabricated `OutPoint`. [11](#0-10) [3](#0-2) 

### Recommendation
Treat serialized `ReceivedOutput` values as untrusted claims and authenticate them against the chain before exposing or spending them. At minimum, lookup the encoded `OutPoint` and require the retrieved consensus `TxOut` to equal `ReceivedOutput::output()` before accepting the object. Prefer a constructor that accepts `(OutPoint, TxOut)` only after chain lookup, or store a locally generated authentication tag over scanner-produced records. Do not rely on `SignableTransaction::multisig` for this check because it validates only script ownership, not UTXO existence or value. [1](#0-0) [3](#0-2) 

### Proof of Concept

```rust
// From networks/bitcoin/src/wallet/mod.rs and send.rs.

let offset = Scalar::ONE;

// Select a script accepted by SignableTransaction::multisig.
let forged_output = TxOut {
    value: Amount::from_sat(100_000_000),
    script_pubkey: p2tr_script_buf(
        wallet.group_key() + ProjectivePoint::GENERATOR * offset
    ).unwrap(),
};

// This outpoint is fabricated and need not contain forged_output.
let forged_outpoint = OutPoint::new(Txid::all_zeros(), 0);

let mut serialized = Vec::new();
serialized.extend(offset.to_bytes());
serialized.extend(serialize(&forged_output));
serialized.extend(serialize(&forged_outpoint));

let forged = ReceivedOutput::read(&mut serialized.as_slice()).unwrap();
assert_eq!(forged.value(), 100_000_000);

let spend = SignableTransaction::new(
    vec![forged],
    &[(payment_script, 50_000_000)],
    None,
    None,
    fee_rate,
).unwrap();

// This succeeds because only output.script_pubkey is compared with
// wallet_key + offset * G.
let machine = spend.multisig(&wallet).unwrap();
```

The signed transaction references `Txid::all_zeros():0` while its witness is generated for the fabricated 1-BTC `TxOut`; full-node validation rejects the spend because no corresponding UTXO exists. The vulnerability is that `ReceivedOutput::read` allowed an unauthenticated object to cross the boundary between raw byte deserialization and wallet-owned received outputs. [1](#0-0) [8](#0-7)
