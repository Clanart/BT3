### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` in AccountUpdate transactions can crash the entire Kaia node via unrecoverable Go stack overflow - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively invokes `rlp.DecodeBytes` on each role's serialized key without any depth limit. Because `AccountKeyType` can itself be `AccountKeyTypeRoleBased`, an attacker can encode arbitrarily deep nesting of role-based keys inside a single `TxTypeAccountUpdate` (or `TxTypeFeeDelegatedAccountUpdate`) transaction. The composite-type rejection (`ErrNestedCompositeType`) is only enforced in `CheckInstallable`/`CheckUpdatable`, which run *after* the full recursive decode has already completed. A sufficiently deep nesting exhausts the goroutine stack during decode itself, which in Go is an unrecoverable fatal error that terminates the whole process — not just the request/goroutine — mirroring the "nested-array deserialization bypasses allowlist checks and crashes the whole process" bug class from CVE-2026-59275.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes into a slice of raw byte slices, then for each element calls `rlp.DecodeBytes` on a fresh `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the `keyType` tag, constructs the corresponding `AccountKey` via `NewAccountKey`, and recursively decodes into it: [2](#0-1) 

`NewAccountKey` allows `AccountKeyTypeRoleBased` to be constructed again with no restriction at this stage: [3](#0-2) 

If the decoded `keyType` is again `AccountKeyTypeRoleBased`, `s.Decode` re-enters `AccountKeyRoleBased.DecodeRLP`, which spawns another `rlp.DecodeBytes` call, recursing indefinitely with attacker-controlled depth. There is no depth/size guard anywhere in this call chain or in the generic `rlp` decoder (`rlp/decode.go`) that limits nesting depth — only the overall byte-size limit (`willRead`/`ErrValueTooLarge`, `ErrElemTooLarge`) applies, which bounds total bytes, not recursion depth. Because RLP list/string headers are extremely compact (as little as 1–2 bytes per level for very small nested items), a very large number of nesting levels can be packed into a transaction well under the pool's `MaxTxDataSize` limit enforced later in `TxPool.validateTx`: [4](#0-3) 

Crucially, the only place that rejects nested `AccountKeyRoleBased` values (`ErrNestedCompositeType` via `IsCompositeType`/`CheckInstallable`) executes only *after* decoding has fully materialized the nested structure — it is a post-decode allowlist check, exactly analogous to the Spring AMQP report's "allowlist bypass by nested structure before enforcement" pattern: [5](#0-4) 

A dedicated test even documents that nested `RoleBased` keys are supposed to be rejected only at the `CheckInstallable`/pool-validation stage, confirming decode happens first and unconditionally: [6](#0-5) 

`TxInternalDataAccountUpdate.DecodeRLP` (and the fee-delegated variant) is what triggers this chain when a raw transaction is RLP-decoded, e.g. from a submitted `eth_sendRawTransaction`/p2p-broadcast transaction, before any pool-level structural validation runs: [7](#0-6) 

In Go, a goroutine stack overflow (`runtime: goroutine stack exceeds ... limit`) is a fatal, unrecoverable runtime error — `recover()` cannot catch it, and it calls `runtime.fatalthrow`, terminating the entire process (all goroutines, not just the one handling the malicious transaction). This is architecturally equivalent to the reported Spring AMQP bug where a nested structure bypasses upstream checks, triggers a `StackOverflowError`, and results in whole-process termination.

### Impact Explanation
Any unprivileged transaction sender or public-RPC caller can submit a single `TxTypeAccountUpdate`/`TxTypeFeeDelegatedAccountUpdate` transaction (does not even need to be added to the pool successfully, since the crash occurs during RLP decoding itself, which happens on p2p transaction propagation and RPC ingestion before pool admission checks run) containing a deeply nested `AccountKeyRoleBased` payload. This can crash the entire Kaia node process, causing full denial of service for that node (and potentially cascading if the same crafted transaction propagates via p2p to other nodes before local decode-time crashes are contained), which is a Medium/High-severity availability impact matching the CVSS 6.6 profile of the source CVE.

### Likelihood Explanation
Likelihood is high for a single malicious actor with no special privileges: constructing a maliciously nested `AccountKeyRoleBased` RLP payload requires only client-side encoding using the same `AccountKeySerializer`/`AccountKeyRoleBased` encode logic (or manual RLP crafting) and does not require a valid signature to be decoded (decode happens as part of general RLP struct decoding regardless of signature validity, since `DecodeRLP` runs before `ValidateSender`/signature checks in `tx_pool.go`'s `validateTx`). The size of RLP overhead per nesting level is minimal, making very deep nesting achievable well within transaction size limits.

### Recommendation
Add an explicit recursion/depth limit check in `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., reject decoding if `keyType == AccountKeyTypeRoleBased` while already decoding a nested key, or track and cap a decode depth counter passed through the `rlp.Stream` context) so that nested composite types are rejected *during* decode, not only after decode completes in `CheckInstallable`. Alternatively, impose a global maximum RLP nesting depth in the shared `rlp` package (similar to Go's own protections against RLP DoS) that would generically bound this class of self-referential/recursive `DecodeRLP` implementations.

### Proof of Concept
1. Build an `AccountKeyRoleBased` value whose single role element is itself an `AccountKeyRoleBased` wrapping another, repeated to a depth of tens of thousands of levels (each level only requires a `keyType` byte + a short RLP list/string header, so payload stays well under `MaxTxDataSize`).
2. Wrap this nested key as the `Key` field of a `TxTypeAccountUpdate` transaction and RLP-encode the transaction (no valid signature needed to trigger decode).
3. Submit the raw transaction bytes via `eth_sendRawTransaction` or inject it into p2p transaction propagation.
4. `TxInternalDataAccountUpdate.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recurse for each nesting level; at sufficient depth the goroutine stack overflows, producing a fatal, unrecoverable Go runtime error that terminates the entire node process.

Note: I was unable to fully verify the exact byte-size cost of RLP overhead per nesting level against the precise numeric value of `MaxTxDataSize` (its exact constant value was not directly retrieved in this session, only its usage sites), so the exact maximum achievable nesting depth within a single transaction is not empirically confirmed — but even a conservative estimate leaves ample headroom for goroutine stack exhaustion (Go's default goroutine stack limit is 1 GB, but each recursion level here likely consumes multiple stack frames across `rlp.DecodeBytes` → `Stream.Decode` → `decodeDecoder` → `DecodeRLP`, so a few thousand nesting levels is plausible).

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}
