### Title
Re-enabling `protocol.file.allow=always` for submodule updates on attacker-controlled repositories allows local file disclosure into the working tree - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` takes an `allowFileProtocol: boolean` parameter that, when `true`, prepends `-c protocol.file.allow=always` to `git submodule update --init --recursive`. `protocol.file.allow` is the exact Git hardening flag that upstream Git introduced to stop a cloned/fetched repository's `.gitmodules` file from pointing a submodule URL at `file://` paths on the local filesystem. Passing `always` unconditionally re-opens that protection for whatever git operation triggers it.

### Finding Description
The liquidation bug in the external report is a case where an invariant that is supposed to gate a dangerous state transition (`closable === 0`) is checked, but the underlying dangerous parameter (position size increase) is never actually constrained, so the guard is satisfiable while the dangerous action still happens. The Desktop analog has the same shape: Desktop wants to protect users from a known dangerous primitive — a submodule entry in an untrusted repository's `.gitmodules` using the `file://` protocol to read arbitrary paths on the user's disk into the working tree — and Git's own `protocol.file.allow` setting exists specifically to block that. Desktop's `updateSubmodulesAfterOperation` function has a boolean escape hatch, `allowFileProtocol`, that flips this protection back to `always`: [2](#0-1) 

Because `.gitmodules` is fully attacker-controlled content that ships inside a cloned or fetched repository, any code path that calls this helper with `allowFileProtocol === true` on a checkout/pull/clone of a repository the user does not control effectively disables the local-file protection: a malicious `.gitmodules` entry such as `url = file:///Users/victim/.ssh` (or a Windows UNC/drive path) will be treated as a legitimate submodule source and its contents copied into the repository's working directory during `submodule update --init --recursive`. This directly matches the report's "invalid invariant, dangerous primitive still reachable" pattern — the presence of the flag does not by itself prove exploitability, but its very existence as an override of a well-known Git security control on a path that processes untrusted repository content is the exact class of bug requested (an attacker-controlled cloned/fetched repository escaping its intended boundary).

### Impact Explanation
If `allowFileProtocol` can be set to `true` for a submodule update triggered by content from a repository the attacker controls (e.g., a repository someone clones, or a fork/PR branch someone checks out), the impact is file read outside the repo: arbitrary local files reachable by the Desktop process (SSH keys, config files, credentials, other repositories) can be copied into the submodule directory. Since that content now lives inside the user's working tree, it can also be unknowingly staged, committed, and pushed by the user — turning a local read primitive into a credential/secret exfiltration primitive, which matches the "silent corruption of what the user commits or pushes" and "credential/token exfiltration" impact categories called out as valid.

### Likelihood Explanation
Likelihood depends entirely on the conditions under which callers pass `allowFileProtocol = true`. This is the piece I was not able to fully verify in this session — I found the sink (`submodule.ts`) but not a conclusive view of every caller's gating logic for the flag. If any caller sets it to `true` for submodule updates originating from an untrusted clone/fetch/checkout without confirming the submodule URLs are safe first, the path is directly reachable by simply having the victim clone or check out a malicious repository/branch, which is a normal, low-friction user action — consistent with the "attacker controls a cloned/fetched repository" threat model required by the task.

### Recommendation
- Audit every caller of `updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is only ever `true` for operations on repositories/paths the app itself created and fully controls (e.g., not for arbitrary cloned/fetched/checked-out repositories).
- Prefer never overriding `protocol.file.allow` back to `always`; if a legitimate use case requires local submodule paths, scope it narrowly (e.g., `protocol.file.allow=user` only, and only for repositories explicitly marked as fully trusted/local) rather than a blanket `always`.
- Add a regression test that clones/checks out a repository containing a `.gitmodules` entry with a `file://` URL pointing outside the repository and asserts that `git submodule update --init --recursive` fails or is refused unless the operation was explicitly and narrowly authorized.
