### Title
WERC20 precompile silently accepts and permanently locks native tokens sent alongside standard ERC20 method calls (transfer/approve/transferFrom) - (File: precompiles/werc20/werc20.go)

### Summary
The base ERC20 precompile explicitly guards against receiving native value on ERC20 methods, but the WERC20 precompile's `Execute` function bypasses that guard by routing ERC20 calls directly to `HandleMethod` instead of `erc20.Precompile.Execute`, allowing `msg.value` to be silently dropped and permanently stranded — the same root cause as the referenced `LineLib.receiveTokenOrETH` bug (dual-path logic where the ERC20 branch ignores `msg.value`).

### Finding Description
The plain ERC20 precompile explicitly protects against stray native-token transfers on ERC20 calls: [1](#0-0) 
This check reverts any call where `contract.Value()` is nonzero before dispatching to `HandleMethod`.

The WERC20 precompile wraps the ERC20 precompile and reimplements `Execute` itself, but its default branch for standard ERC20 methods calls `p.HandleMethod` directly — never going through `erc20.Precompile.Execute`, so the `ErrCannotReceiveFunds` value check is never applied to `transfer`, `transferFrom`, `approve`, or the ERC20 query methods on WERC20: [2](#0-1) 

Only `Deposit` (fallback/receive/`deposit()`) actually forwards `contract.Value()` back to the caller via `BankKeeper.SendCoins`: [3](#0-2) 

If a caller sends a low-level call to the WERC20 precompile address with both `value > 0` and calldata selecting `transfer`/`approve`/`transferFrom` (nonpayable in the ABI, but the precompile is Go code — not compiler-generated bytecode — so there is no automatic EVM-level "revert on value for nonpayable function" check), the EVM statedb will still credit the native balance to the precompile's account address as part of ordinary CALL-with-value semantics, while the WERC20 logic performs only the ERC20 accounting operation and never triggers any bank-keeper `SendCoins` to move that value anywhere. The `BalanceHandler.AfterBalanceChange` only reconciles `stateDB` balances based on `bank` events emitted during the precompile action [4](#0-3) ; since no bank event is emitted for a plain `Transfer`/`Approve` call, the value credited to the precompile address by the EVM call mechanics is never reflected/moved by any subsequent bank operation, and there is no other precompile method that will ever forward, spend, or refund an arbitrary balance sitting at the precompile address (its `Deposit` method only forwards `contract.Value()` for the *current* call, and `Withdraw` is a pure no-op that never transfers anything). The stranded amount is therefore permanently unreachable via any user-triggerable path.

### Impact Explanation
This causes irreversible loss/locking of native user funds with no privileged or asynchronous means to recover them, since the precompile has no owner/admin sweep function and the WERC20 precompile design explicitly documents "No Lock-up: Native tokens are never locked in the precompile" as a security invariant that this path violates [5](#0-4) . This matches the Critical "permanent freezing/locking of user funds" impact category.

### Likelihood Explanation
Trigger requires only an unprivileged EOA or contract issuing a low-level `call{value: x}(abi.encodeWithSignature("transfer(address,uint256)", ...))` (or `approve`/`transferFrom`) directly to the WERC20 precompile address — no special permissions, no relayer/validator collusion, and no reliance on any other module. This is easy to construct accidentally (e.g., a wallet/dApp that always attaches `msg.value` to a generic token call, or a contract composing a WERC20 transfer inside a payable function) or deliberately.

### Recommendation
Route all ERC20 method dispatch in `werc20.Precompile.Execute` through the same `contract.Value()` guard used in `erc20.Precompile.Execute` (or call `p.Precompile.Execute` instead of `p.HandleMethod` directly for the ERC20 branch), so that any nonzero `msg.value` attached to `transfer`/`transferFrom`/`approve`/query calls causes the whole call to revert instead of silently stranding native funds at the precompile address.

### Proof of Concept
1. Deploy/identify the WERC20 precompile for a given token pair at address `WERC20_ADDR`.
2. From an EOA/contract, construct a raw call: `WERC20_ADDR.call{value: 1 ether}(abi.encodeWithSignature("transfer(address,uint256)", recipient, 0))` (amount can be 0 or a real balance the caller holds).
3. Trace execution: `werc20.Precompile.Execute` [2](#0-1)  matches the default case and calls `p.HandleMethod` directly, with no check on `contract.Value()`, unlike `erc20.Precompile.Execute` [6](#0-5) .
4. The EVM `CALL` mechanics still transfer `1 ether` of native balance to the precompile's contract address at the state-transition level; the `Transfer` method performs the ERC20 bookkeeping but never calls `BankKeeper.SendCoins` for this value.
5. Confirm no follow-up call (`deposit`, `withdraw`, or any other) can retrieve this specific stranded value — `Withdraw` is a no-op [7](#0-6)  and `Deposit` only forwards `contract.Value()` of its *own* invocation, not any previously stranded balance.

Note: I was not able to execute this against a live node/test harness to directly observe the resulting balance discrepancy (e.g., via `eth_getBalance` on the precompile address vs. bank module balance) — this analysis is based on static code tracing of `precompiles/werc20/werc20.go`, `precompiles/erc20/erc20.go`, `precompiles/werc20/tx.go`, and `precompiles/common/balance_handler.go`. Confirming exact on-chain behavior (whether the EVM's `CALL`-with-value pathway for precompiles indeed credits `stateDB` balance without an accompanying bank-module operation) would require running the integration test suite or a live testnet trace.

func (p Precompile) Execute(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	// ERC20 precompiles cannot receive funds because they are not managed by an
	// EOA and will not be possible to recover funds sent to an instance of
	// them.This check is a safety measure because currently funds cannot be
	// received due to the lack of a fallback handler.
	if value := contract.Value(); value.Sign() == 1 {
		return nil, fmt.Errorf(ErrCannotReceiveFunds, contract.Value().String())
	}

	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	return p.HandleMethod(ctx, contract, stateDB, method, args)
}

func (p Precompile) Execute(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	var bz []byte

	switch {
	case method.Type == abi.Fallback,
		method.Type == abi.Receive,
		method.Name == DepositMethod:
		bz, err = p.Deposit(ctx, contract, stateDB)
	case method.Name == WithdrawMethod:
		bz, err = p.Withdraw(ctx, contract, stateDB, args)
	default:
		// ERC20 transactions and queries
		bz, err = p.HandleMethod(ctx, contract, stateDB, method, args)
	}

	return bz, err
}

// Deposit handles the payable deposit function. It retrieves the deposited amount
// and sends it back to the sender using the bank keeper.
func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}

// Withdraw is a no-op and mock function that provides the same interface as the
// WETH contract to support equality between the native coin and its wrapped
// ERC-20 (e.g. ATOM and WEVMOS).
func (p Precompile) Withdraw(ctx sdk.Context, contract *vm.Contract, stateDB vm.StateDB, args []interface{}) ([]byte, error) {
	amount, ok := args[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("invalid argument type: %T", args[0])
	}
	amountInt := math.NewIntFromBigInt(amount)

	caller := contract.Caller()
	callerAccAddress := sdk.AccAddress(caller.Bytes())
	nativeBalance := p.BankKeeper.SpendableCoin(ctx, callerAccAddress, evmtypes.GetEVMCoinDenom())
	if nativeBalance.Amount.Mul(types.ConversionFactor()).LT(amountInt) {
		return nil, fmt.Errorf("account balance %v is lower than withdraw balance %v", nativeBalance.Amount, amountInt)
	}

	if err := p.EmitWithdrawalEvent(ctx, stateDB, caller, amount); err != nil {
		return nil, err
	}
	return nil, nil

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
