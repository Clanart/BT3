## Title
Partial-commit staging applies zero-context patches (`--unidiff-zero`) with no verification that the working-tree file still matches the diff snapshot, silently corrupting staged content - (File: `app/src/lib/git/apply.ts`)

### Summary
The Transmuter bug is a case where an operation performs an irreversible state change based on stale/attacker-influenced external data with no bound or verification step to catch drift between the expected and actual state. GitHub Desktop's partial-commit (line/hunk selection) staging pipeline has the same broken invariant: `applyPatchToIndex` and `discardChangesFromSelection` build a patch from a diff snapshot captured earlier in the UI, then apply it to the index/working tree with `git apply --unidiff-zero`, a mode that deliberately removes the context-line verification Git would otherwise use to confirm the file hasn't changed since the diff was computed.

### Finding Description
`formatPatch` in `app/src/lib/patch-formatter.ts` builds a unified-diff patch purely from the previously-fetched `ITextDiff`/`selection` state and hardcoded hunk headers computed from that stale diff. [1](#0-0) 

That patch is then fed straight into `git apply --cached --unidiff-zero --whitespace=nowarn -` in `applyPatchToIndex`: [2](#0-1) 

and the same `--unidiff-zero` flag is used for `discardChangesFromSelection`: [3](#0-2) 

Normally `git apply` uses the surrounding context lines in a hunk to locate and verify the correct position in the target file, and refuses to apply if the context doesn't match (i.e., it detects that the file has drifted from what the patch expects). `--unidiff-zero` patches carry no context lines, so Git can only apply hunks by raw line-number offset and cannot detect that the underlying file content has changed between the moment the diff was generated for display in the Changes list and the moment the user commits/discards their selection. This is structurally identical to calling `depositUnderlying` with `minOut = 0`: the action is executed against a live, mutable resource without any bound/check that the actual outcome still matches what was reviewed.

### Impact Explanation
If the tracked file's content changes during that window (e.g., a build tool, formatter, linter auto-fix, git hook, or any other process the repository configures to run as part of the normal workflow such as file watchers or `prepare`/`post-checkout` scripts) between diff generation and patch application, `git apply --unidiff-zero` will still succeed and insert/remove lines purely by line number, without validating that those lines still contain what the user selected. The result is that the index/commit can silently contain different content than what the user reviewed and explicitly selected in the diff view — i.e., corruption of what the user commits, with no error surfaced to the user.

### Likelihood Explanation
This requires a time-of-check/time-of-use window between the diff being fetched (`getWorkingDirectoryDiff`) for UI display and the user completing the partial-stage/discard action — the same class of "unfavorable timing" the original report calls out for the keeper-bot buffer call. A cloned/fetched repository that ships tooling which mutates tracked files as part of a normal developer workflow (formatters, generators, watch tasks) can reliably create that window without requiring any local/admin access beyond what the user already grants when running the project's own tooling.

### Recommendation
Before applying the zero-context patch, re-verify that the current on-disk content for the affected hunks still matches the diff that was used to build the patch (equivalent to adding a "slippage bound"), and abort/re-diff if it does not, similar to how `_alchemistWithdraw`-style bounded calls are recommended in the original report. At minimum, avoid `--unidiff-zero` for cases where context verification would catch drift, or add an explicit content-hash/mtime check between diff generation and patch application.

### Proof of Concept
1. Open a file with local changes in Desktop and select only some lines/hunks for partial commit (the diff and `DiffSelection` are computed at this point via `getWorkingDirectoryDiff`).
2. Before confirming the commit, have an external process (e.g., a repo-configured formatter/watch script) modify the same lines of the file on disk.
3. Complete the commit. `stageFiles` → `applyPatchToIndex` builds the patch from the stale selection/diff and runs `git apply --cached --unidiff-zero` [4](#0-3) , which applies successfully because there is no context to validate against, silently staging content that no longer matches what the user saw and selected.
