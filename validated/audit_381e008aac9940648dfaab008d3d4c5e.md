### Title
Attacker-controlled participant count causes oversized allocation in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the serialized `n` value before validating the threshold parameters or confirming that the corresponding serialized data exists. A very short input can therefore force allocation of a `Vec` with capacity for up to 65,535 field elements.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from attacker-controlled bytes [1](#0-0) . If the interpolation byte selects `Interpolation::Constant`, it immediately calls `Vec::with_capacity(usize::from(n))` before reading any coefficients [2](#0-1) . `ThresholdParams::new` permits any nonzero `n` and only requires `t <= n` and `i <= n`, so `n = 65535` is valid [3](#0-2) . Parameter validation occurs only after the oversized allocation and after the encoded coefficients and verification shares are processed [4](#0-3) .

### Impact Explanation
An unprivileged party that can submit serialized `ThresholdKeys` bytes can trigger an allocation of roughly 2 MiB for a 32-byte field using only the header bytes needed to reach the interpolation branch. Repeating this operation, especially concurrently, can exhaust allocator capacity or abort the process on allocation failure, causing denial of service.

### Likelihood Explanation
The input does not need to contain the promised coefficients. The allocation happens before the first `read_F`, so a truncated buffer still reaches the vulnerable `Vec::with_capacity` call and then fails only when coefficient decoding begins [5](#0-4) .

### Recommendation
Validate `t`, `n`, and `i` through `ThresholdParams::new` before allocating interpolation storage. Avoid `Vec::with_capacity(n)` for untrusted serialized data; either push elements as they are successfully decoded or enforce a protocol-specific maximum participant count before allocation.

### Proof of Concept
```rust
// Conceptual input against crypto/dkg/src/lib.rs ThresholdKeys::read.
// For a 32-byte-field Ciphersuite, this requests ~2 MiB despite being
// far shorter than the serialized object it claims to contain.

let mut bytes = Vec::new();
bytes.extend_from_slice(&(C::ID.len() as u32).to_le_bytes());
bytes.extend_from_slice(C::ID);
bytes.extend_from_slice(&1u16.to_le_bytes());       // t
bytes.extend_from_slice(&u16::MAX.to_le_bytes());   // n = 65535
bytes.extend_from_slice(&1u16.to_le_bytes());       // i
bytes.push(0);                                      // Interpolation::Constant
// No coefficient bytes follow.

let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
```

The call reaches `Vec::with_capacity(65535)` before failing on the missing coefficient data.
