## Title
Unchecked ERC20 return value in Tron `IntentGatewayV2.withdraw()` allows escrow accounting to advance while beneficiary receives nothing — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases cross-chain escrow via `withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow`) using a raw low-level `.call()` to the token's `transfer` selector and only checks that the call did not revert (`success`), never decoding the returned boolean. This is the exact bug class from the referenced report (M-01, Visor `timeLockERC20`): non-reverting ERC20 tokens that return `false` on failure will make `success == true` even though no tokens moved, while the vault's internal accounting is unconditionally decremented as if the transfer succeeded. [1](#0-0) 

### Finding Description
`withdraw()` is the escrow-release path invoked by `onAccept` when a `RedeemEscrow` (solver fill payout) or `RefundEscrow` (user cancellation refund) request is authenticated and processed: [2](#0-1) 

Inside `withdraw()`, for ERC20 tokens the contract does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and then unconditionally executes `_orders[body.commitment][token] -= amount;` right after, regardless of what the call actually returned. [3](#0-2) 

The identical unchecked-return pattern is used for the transaction-fee payout in the same function: [4](#0-3) 

and again in `onAccept`'s `SweepDust` handling: [5](#0-4) 

This is the same broken invariant as the External Report: `success` from a low-level `.call()` only tells you the call didn't revert — it says nothing about the ABI-encoded `bool` return value. Standard-conforming ERC20s revert on failure and this pattern happens to work for them, but ERC20 (and especially TRC20/TRON token) implementations are not guaranteed to revert; many legacy or non-standard tokens return `false` instead of reverting on failed transfers (insufficient balance edge cases, paused/blacklisted recipients, etc.). Contrast this with the parallel EVM-side implementation, `IntentsBase._withdraw()`, which correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, decoding and enforcing the return value: [6](#0-5) 

The Tron gateway's `withdraw()` diverges from this safe pattern and reintroduces the exact class of bug the report describes, but on the payout side rather than the deposit side: the escrow bookkeeping (`_orders[commitment][token]`) is decremented and `_filled[commitment]` is set to the beneficiary even though the token transfer silently failed.

### Impact Explanation
Because `_filled[body.commitment] = beneficiary` is set and `_orders[body.commitment][token] -= amount` executes before/regardless of the actual transfer outcome, a failed-but-non-reverting `transfer()` causes:
1. The order commitment is marked as finalized (filled or refunded) — permanently, since `_filled` and `_orders` are not reversible once written.
2. The intended beneficiary (a solver who fulfilled the order, or a user requesting a refund) never receives their tokens for that leg.
3. The tokens remain physically locked inside the `IntentGatewayV2` contract with no accounting path left to reclaim them, because the escrow slot has already been zeroed out and the commitment marked filled — matching the report's "loss of funds" scenario, just on the withdrawal/settlement side of the bridge intent flow instead of the initial lock.

This falls squarely within the bounty's accepted impact categories: stealing/loss of funds and false state acceptance (the contract believes settlement/refund succeeded when it did not) for a public, unprivileged execution path (any solver/user triggering the cross-chain settlement flow with a non-standard ERC20/TRC20 as the order's input token).

### Likelihood Explanation
The path is reachable through the standard cross-chain settlement flow — `onAccept` is called by the host for any legitimately authenticated `RedeemEscrow`/`RefundEscrow` message, and `withdraw()` unconditionally executes this branch whenever the order's input token happens to be a non-reverting ERC20/TRC20. No malicious relayer, prover, or admin is required — the trigger condition is purely the choice of input token used when the order was originally placed (an ordinary user- or solver-controlled parameter in `placeOrder`), combined with that token entering a state where its `transfer` legitimately fails but returns `false` instead of reverting (e.g., an edge-case balance/allowance condition, or a token type common in the TRON ecosystem that does not strictly adhere to reverting semantics). This does not require a compromised peer or front-running; it is a straightforward function of token behavior on a public entry point.

### Recommendation
Replace the raw `.call()` + `success`-only check in `withdraw()` (lines 693–714) and in `onAccept`'s `SweepDust` branch (lines 665–666) with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the pattern already used correctly in `IntentsBase._withdraw()`:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
This decodes and enforces the ERC20 return value (when present) in addition to reverting on a reverted call, closing the gap for tokens that signal failure via a `false` return rather than a revert.

### Proof of Concept
1. Deploy (or use) a TRC20/ERC20-like token whose `transfer()` function does not revert on failure but instead returns `false` (a real, deployable pattern seen in numerous legacy/non-standard tokens, and explicitly the scenario cited in the source report).
2. A user places an order via `placeOrder` using this token as an input, escrowing `amount` tokens; `_orders[commitment][token] = amount`.
3. The order is filled (or cancelled) cross-chain, generating an authenticated `RedeemEscrow`/`RefundEscrow` request that reaches `onAccept` → `withdraw()` on the Tron gateway.
4. At the moment of payout, the token's `transfer(beneficiary, amount)` call returns `false` (e.g., due to a transient balance discrepancy or an implementation quirk) without reverting.
5. `success` is `true` (the call itself didn't revert), so execution proceeds: `_orders[body.commitment][token] -= amount` zeroes the escrow record, and `_filled[body.commitment] = beneficiary` finalizes the order — but the beneficiary's token balance never increased.
6. The tokens remain stuck in the `IntentGatewayV2` contract with no remaining accounting reference to recover them, while the protocol and beneficiary both believe settlement succeeded (per the emitted `EscrowReleased`/`EscrowRefunded` event).

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
