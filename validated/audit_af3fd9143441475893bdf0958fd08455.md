### Title
Symlink-based directory escape in Copilot conflict context via flawed prefix check in `resolveWithin()` - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin()` in `app/src/lib/path.ts` is the shared "is this path inside the repo root" guard used across the app. Its final containment check is a plain string-prefix test, `realResolved.startsWith(realRoot)`, with no path-separator boundary check. This lets a resolved path whose real (symlink-followed) location is a **sibling** directory that merely shares a name prefix with the repository (e.g. `myrepo-secrets` vs `myrepo`) pass the "is inside root" test. `buildConflictContext()` in `app/src/lib/copilot-conflict-context.ts` relies solely on this check (no extra `isAbsolute()`/normalization guard), reads the resolved file from disk, and feeds its full content into the Copilot conflict-resolution prompt shown in the UI.

### Finding Description
`_resolveWithin()` resolves `rootPath` and the joined path segments, calls `realpath()` on both to follow symlinks, and then does: [1](#0-0) 

There is no check that `realResolved` starts with `realRoot + path.sep` (or equals `realRoot`) — a purely lexical prefix match. This is the exact same class of bug as the report's broken invariant: a security check exists and looks correct in isolation, but the primitive it relies on (string containment) doesn't match the real invariant it's supposed to encode (directory containment).

`buildConflictContext()` calls this shared primitive directly on repository-relative conflict file paths that originate from the working tree of a merge/rebase/cherry-pick — content that can come from a branch fetched from an attacker-controlled remote/fork: [2](#0-1) 

If the attacker's branch/tree introduces (or the merge produces) a **symlink** at a conflicted path whose target resolves to a directory outside the repo that happens to share the repo's directory name as a prefix (e.g. repo at `/Users/victim/myrepo`, symlink target `/Users/victim/myrepo-backup/id_rsa` or `/Users/victim/myrepository/secrets.env`), `realpath()` resolves the symlink to that outside location, and `startsWith` incorrectly reports it as "inside" the root. The function then proceeds to `stat()` and `readFile()` that out-of-repo file and includes its contents in the Copilot prompt via `formatConflictContextForPrompt()`, which is both sent to the AI backend and rendered in the merge-conflict-resolution dialog: [3](#0-2) [4](#0-3) 

Notably, other call sites of the same primitive add an extra, independent guard the shared function itself doesn't provide — e.g. `dispatcher.ts` explicitly rejects absolute paths with `isAbsolute(filepath)` before calling `resolveWithin` for the "open file from deep link" flow: [5](#0-4) 

This shows the underlying `resolveWithin` containment check alone is known/treated as insufficient at at least one call site, but `buildConflictContext` does not apply an equivalent additional guard — mirroring the report's pattern where the invariant is properly enforced in one function (`withdrawERC20`'s `onlyUnblockedTokens`) but a sibling function operating on the same class of data (`withdrawLPToken`) lacks it.

### Impact Explanation
Successful exploitation lets a malicious remote/fork branch, once merged/rebased/cherry-picked by the victim (unprivileged, no special access needed beyond the user pulling in the attacker's ref, e.g. via a PR the user is reviewing/merging), cause Desktop to read an arbitrary file outside the repository whose real path shares a prefix with the repo directory name, and exfiltrate its contents into: (a) the Copilot AI backend as part of the prompt, and (b) the rendered conflict-resolution UI. This is a file-read-outside-the-repo / potential credential-exfiltration primitive, matching the "Valid Impact" criteria (attacker controls a fetched/merged repository content, result is file read outside the repo / credential exfiltration).

### Likelihood Explanation
Requires: (1) the victim to have a repository whose path has a sibling directory sharing a name prefix (realistic — cloned repos commonly live in a shared parent folder with similarly-named siblings, e.g. `project` and `project-secrets`, `project.bak`, `project2`), (2) the victim to merge/rebase/cherry-pick an attacker-influenced branch that introduces a conflicting path implemented as a symlink pointing outside the repo, and (3) the victim to use the Copilot conflict-resolution feature on that conflict. This is a plausible but not trivial chain — likelihood is Medium given it needs both a favorable filesystem layout and the victim opting into the AI-assisted conflict resolution flow.

### Recommendation
Fix `_resolveWithin()` in `app/src/lib/path.ts` to require a proper directory boundary, not a bare prefix match:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
This closes the sibling-directory bypass for every consumer of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` at once (including `copilot-conflict-context.ts`, `dispatcher.ts`, and `app-store.ts`), rather than requiring each call site to layer its own extra guard.

### Proof of Concept
1. Victim has repo at `/Users/victim/Documents/GitHub/myrepo` and an unrelated sensitive directory `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa`.
2. Attacker's fork/branch, when merged, produces a conflict on a file `link` where the "theirs" side is a symlink `link -> ../myrepo-secrets/id_rsa` (or an absolute equivalent) checked into the attacker's tree.
3. Victim opens the merge-conflict resolution UI and triggers Copilot-assisted resolution; `buildConflictContext()` calls:
   `resolveWithin('/Users/victim/Documents/GitHub/myrepo', 'link')`
4. `realpath()` resolves the symlink to `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa`; `realRoot` is `/Users/victim/Documents/GitHub/myrepo`. `realResolved.startsWith(realRoot)` evaluates `true` because of the shared prefix, even though the file is in a completely separate sibling directory.
5. `stat`/`readFile` succeed on the out-of-repo file, and its contents are embedded in the prompt sent to Copilot and displayed in the conflict dialog, per `formatConflictContextForPrompt()`.
