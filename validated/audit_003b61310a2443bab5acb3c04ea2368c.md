### Title
Silent truncation via unchecked `big.Int.Uint64()` when converting on-chain staking amounts to `StakingInfo.StakingAmounts` - (File: kaiax/staking/impl/getter.go)

### Summary
`kaiax/staking/impl/getter.go` converts staking-contract balances (read from the AddressBook / AddressBookV2 / CL registry via the MultiCall contract) from `*big.Int` (wei/kei, effectively `uint256`-range) into `uint64` using Go's `big.Int.Uint64()`, without first checking `IsUint64()`. Per Go's documented semantics, if the value does not fit in 64 bits, `Uint64()` silently returns an undefined/truncated result rather than erroring — an unchecked-downcast pattern directly analogous to the unsafe `int256(uint256)` cast flagged in the referenced PoolTogether finding, where a large source value silently wraps into a materially different destination value that then drives reward-distribution math.

### Finding Description
In `parseCallResult` and `parsePermissionlessCallResult`, staking amounts obtained from the AddressBook/MultiCall contract calls are divided by `params.KAIA` and truncated with `.Uint64()`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

None of these four call sites check `big.Int.IsUint64()` before calling `.Uint64()`. The resulting `uint64` `StakingAmounts`/`CLStakingAmount` values then flow directly into `kaiax/reward` consensus-level reward computations that determine minimum-stake eligibility and pro-rata reward shares: [5](#0-4) [6](#0-5) 

If a staking (or consensus-liquidity) contract's on-chain balance, expressed in KAIA units (wei/1e18), exceeds `math.MaxUint64` (~1.8446744e19 KAIA), the truncation silently wraps around and produces an arbitrary, much smaller (or larger, mod 2^64) `StakingAmount`, corrupting `minStake`/`threshold` eligibility checks and the proportional reward split across validators — the same class of effect the referenced report describes (drastically altered payout computed from a corrupted numeric value due to an unchecked cast).

### Impact Explanation
If triggered, this could corrupt `RewardModule.getDeferredRewardFull*`'s staking-reward allocation (`assignStakingRewards`/`assignStakingRewardsFlex`), causing reward mis-distribution among validators/consensus-liquidity pools computed and paid out during `FinalizeState`, i.e., unauthorized/incorrect value movement of minted+fee rewards at the protocol level. That places it in the "reward redirection" impact category called out in scope.

### Likelihood Explanation
Reachability requires a single staking (or CL) contract's reported balance, once divided by 1e18, to exceed `2^64` (~1.84e19 KAIA). Given KAIA's fixed, bounded total native-token supply is orders of magnitude below this threshold, and staking-contract balances are backed by real native-token transfers (not attacker-mintable), no unprivileged transaction sender can currently accumulate a balance anywhere near this bound through ordinary transactions. Because the precondition for triggering the silent wraparound is not reachable by a normal transaction/bundle/RPC caller under the current native-token supply constraints, likelihood is not demonstrated to be practically exploitable today, only latent/defense-in-depth.

### Recommendation
Replace the bare `.Uint64()` conversions in `kaiax/staking/impl/getter.go` (`parseCallResult`, `parsePermissionlessCallResult`, and the CL-staking-amount conversions) with a checked conversion, e.g. verify `IsUint64()` first (or clamp/saturate) and return an explicit error (`staking.ErrAddressBookResult`-style) instead of silently truncating, mirroring the OZ `SafeCast`-style fix applied in the referenced PoolTogether mitigation.

### Proof of Concept
Not constructible under current mainnet/network conditions: exploitation would require a staking or CL-registry contract to hold a native-token balance exceeding ~1.8e19 KAIA (post-division by 1e18), which exceeds the entire fixed KAIA supply and cannot be produced by any unprivileged transaction, bundle, or RPC call today.

// assignStakingRewardsFlex assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}
