### Title
Empty serialized aggregate signatures verify successfully - (File: crypto/schnorr/src/aggregate.rs)

### Summary

`SchnorrAggregate::read` permits an aggregate containing zero nonces, while `SchnorrAggregate::verify` accepts the resulting empty verification equation when `s == 0`. [1](#0-0) [2](#0-1) 

### Finding Description

`SchnorrAggregator::complete` explicitly refuses to produce an empty aggregate, establishing that an aggregate must contain at least one signature. [3](#0-2)  The deserializer bypasses that invariant: it accepts a zero nonce count and returns `SchnorrAggregate { Rs: [], s }` for any canonically encoded scalar `s`. [1](#0-0) 

During verification, zero `Rs` match an empty `keys_and_challenges` slice, so the challenge loop queues no weighted signature statements. [4](#0-3)  With `s == 0`, the only remaining statement is `0 * G`, which evaluates to identity and causes verification to return true. [5](#0-4) 

### Impact Explanation

An unprivileged party can provide serialized bytes representing an aggregate signature without any constituent signature and have `verify` report success for an empty statement set. [1](#0-0)  This bypasses the non-empty invariant enforced by the normal aggregation API and can produce an incorrect verifier result in callers which derive the verification list from attacker-controlled or otherwise empty signature metadata. [3](#0-2) 

### Likelihood Explanation

Exploitation requires a caller to invoke `verify` with an empty `keys_and_challenges` slice, which makes the issue context-dependent rather than a forgery against a specified nonempty public-key set. [6](#0-5)  When such an invocation is reachable, the required bytes are deterministic and consist only of a zero length followed by a canonical zero scalar. [1](#0-0) 

### Recommendation

Reject empty aggregates in both `SchnorrAggregate::read` and `SchnorrAggregate::verify`. [1](#0-0)  At minimum, `verify` should return false when `keys_and_challenges.is_empty()` before evaluating the multiexp, preserving the same non-empty invariant as `SchnorrAggregator::complete`. [2](#0-1) 

### Proof of Concept

For a ciphersuite with a 32-byte scalar encoding, such as `frost::curve::Secp256k1`, the serialized proof is four little-endian zero bytes for the nonce count followed by thirty-two zero bytes for `s`. [1](#0-0)  The transaction-signing module uses `frost::curve::Secp256k1` as its concrete Bitcoin ciphersuite. [7](#0-6) 

```rust
use schnorr::aggregate::SchnorrAggregate;
use frost::curve::Secp256k1;

let mut encoded = Vec::new();
encoded.extend_from_slice(&0u32.to_le_bytes());
encoded.extend_from_slice(&[0u8; 32]);

let forgery =
  SchnorrAggregate::<Secp256k1>::read(&mut encoded.as_slice()).unwrap();

assert!(forgery.verify(b"example-domain-separator", &[]));
```

The assertion succeeds because the empty nonce list matches the empty challenge list, and the sole generated term is zero times the generator. [2](#0-1)
