## Finding

The External Report's actual broken invariant is: **a value the code implicitly assumes is trustworthy/available is never validated, and the app proceeds as if it were valid — leading to complete failure/undesired behavior.** The closest security-relevant analog in GitHub Desktop is not a missing-value bug, but a *missing-trust-boundary* bug: Desktop's git credential helper classifies a remote host as a trusted GitHub endpoint based on a header **supplied by the remote server itself**, and then automatically kicks off a GitHub sign-in flow scoped to that attacker-controlled endpoint.

### Title
Credential helper trusts attacker-controlled `WWW-Authenticate` header to classify a git remote as GitHub, triggering an Enterprise sign-in flow against attacker's server - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git fails to authenticate against a remote, it forwards any `WWW-Authenticate` response headers to Desktop's credential helper. `getEndpointKind()` uses the content of that attacker-supplied header (`realm="GitHub"`) to decide the remote is an "enterprise" GitHub host, with no verification against a known/trusted account or TLS/identity check. [1](#0-0) 

### Finding Description
`getCredential()` first tries to resolve an existing stored GitHub account for the endpoint; if none is found, it calls `getEndpointKind()`. [2](#0-1) 

`getEndpointKind()` classifies the host as `'enterprise'` purely because a `wwwauth[...]` credential field contains the string `realm="GitHub"` — a value that is fully controlled by whatever server answers the git HTTP request (a malicious remote, or a MITM/malicious proxy sitting on the path of a `.git` clone/fetch/push URL): [3](#0-2) 

Once classified as non-generic (`'enterprise'`) and no matching account exists, `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)` where `endpoint` is the attacker's own remote URL: [4](#0-3) 

`promptForGitHubSignIn` then programmatically starts the Enterprise sign-in flow **using the attacker's origin**, bypassing the normal "Enterprise URL entry" step (and its `validateURL` check) that a user would otherwise go through manually: [5](#0-4) 

The subsequent `SignInStep.Authentication` step for that endpoint opens either an OAuth browser flow (`shell.openExternal(getOAuthAuthorizationURL(endpoint, csrfToken))`) or direct username/password entry, both scoped to the attacker-controlled `endpoint`: [6](#0-5) 

Because the endpoint was derived entirely from the malicious remote's response header rather than a value the user typed and had validated, the "GitHub Enterprise" sign-in dialog the user sees is legitimately generated by Desktop but is silently pointed at the attacker's server.

### Impact Explanation
A user who adds/clones from, or is redirected through a proxy to, a malicious git HTTP remote can have that remote's server respond with `401 WWW-Authenticate: Basic realm="GitHub"`. Desktop will then present what looks like a normal "sign in to GitHub" prompt, but the OAuth/PAT exchange and any credentials the user enters are sent to the attacker's endpoint — resulting in credential/token exfiltration under legitimate-looking Desktop UI, without the user ever manually typing a GHE URL (which is the only place `validateURL` normally applies).

### Likelihood Explanation
This requires only that the user perform an ordinary git network operation (clone/fetch/push) against a remote that is attacker-controlled or sits behind a malicious/compromised proxy — no local access, no prior malware, no leaked credentials, and no unnatural steps beyond the normal "authentication failed, please sign in" flow that already occurs today when talking to GHE instances.

### Recommendation
Do not rely on the server-supplied `WWW-Authenticate` realm string alone to classify a host as GitHub/Enterprise. Require this heuristic to be corroborated by an independent check (e.g., only trust it when the host also passes `isGitHubHost()`'s network-based verification, or when the account/endpoint was previously registered by the user through the validated Enterprise sign-in flow), and route any such sign-in prompt through the same `validateURL`-gated endpoint entry UI rather than auto-populating it from an unauthenticated header value.

### Proof of Concept
1. Host a git-over-HTTP server (or a MITM proxy in front of any HTTP git remote) that returns `401` with header `WWW-Authenticate: Basic realm="GitHub"` for any request.
2. In GitHub Desktop, clone/add this URL as a remote and perform a fetch/push.
3. Git invokes Desktop's credential helper; `getEndpointKind()` sees the spoofed header and returns `'enterprise'`. [7](#0-6) 
4. `getCredential()` finds no existing account for this endpoint and calls `ui.promptForGitHubSignIn(endpoint)`, which begins an Enterprise sign-in scoped to the attacker's origin. [8](#0-7) 
5. The user, believing this is a legitimate GitHub/GHE prompt, completes sign-in (OAuth or PAT), sending credentials/tokens to the attacker's server.

Note: I could not fully trace the exact PAT/basic-auth submission code path in `sign-in.tsx`/`app-store.ts` due to running out of tool iterations, so the OAuth-browser path is confirmed in detail while the direct username/password path is inferred from `IAuthenticationState`/`SignInStep.Authentication` but not fully verified line-by-line.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
