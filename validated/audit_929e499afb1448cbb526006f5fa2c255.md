### Title
Native-token fee swaps in `EvmHost.dispatch()`/`fundRequest()` use `block.timestamp` as the Uniswap deadline, providing no execution-time protection and permanently trapping user ETH in the contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all convert user-supplied native ETH into fee tokens via `IUniswapV2Router02.swapETHForExactTokens`, but each call hardcodes the `deadline` parameter to `block.timestamp` at execution time, exactly mirroring the ParaSpace analog where `deadline: block.timestamp` is passed to an AMM call. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`deadline: block.timestamp` is a no-op deadline: whatever block the transaction is finally mined in, `block.timestamp` at that time trivially satisfies the deadline check inside the AMM. This is the same broken invariant identified in the external report — the "deadline" never actually bounds *when* the swap can execute, so it cannot protect the user against unfavorable price movement while the transaction sits unmined (in a mempool, a private orderflow auction, or is simply delayed).

Unlike the codebase's own `UniV3UniswapV2Wrapper.swapETHForExactTokens`, which accepts a caller-supplied `deadline` parameter precisely to give "deadline protection" (as documented in its own comment), `EvmHost` does not expose a `deadline` field on `DispatchPost`/`DispatchGet`/`fundRequest` at all — it always uses `block.timestamp`, closing off the possibility of a caller ever enforcing a real deadline. [4](#0-3) 

Because this is an exact-output swap (`amountOut = post.fee`/`get.fee`/`amount`) funded with `msg.value`, the amount of ETH actually consumed depends on the pool price at execution time. UniswapV2Router02's `swapETHForExactTokens` refunds any unspent ETH to `msg.sender` of the router call — which is the `EvmHost` contract itself (`address(this)` calls the router with `{value: msg.value}`), not the end user. `EvmHost` has no function to sweep or forward this refunded ETH back to the caller, and no `receive()`/withdrawal path was found for stray native ETH. [1](#0-0) 

Combining these two facts: (1) the deadline provides no real time-bound protection, so the swap always executes at whatever price exists when eventually mined, and (2) any ETH not consumed by the swap (the difference between `msg.value` and the actual cost of `post.fee` fee-tokens) is retained by the `EvmHost` contract with no path back to the depositor. A user who overestimates `msg.value` to buffer for slippage, or whose transaction is delayed until price moves favorably, permanently loses the unspent portion of their ETH into the contract.

### Impact Explanation
This is a direct "loss of funds" impact under the bounty's required-impact list: unprivileged users calling `dispatch()`/`fundRequest()` with native ETH lose any ETH not consumed by the exact-output swap, since it is captured by the host contract with no recovery mechanism, and the meaningless `block.timestamp` deadline offers no protection against this outcome being made worse by execution-time price movement. This is not a "front-run-only" or "malicious relayer" scenario — the loss occurs purely because of the missing deadline parameter and the absent refund/sweep logic, triggerable by any ordinary user funding a request with native tokens.

### Likelihood Explanation
Every call to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with `msg.value > 0` goes through this exact-output swap path, so the exposure is present on every native-token-funded dispatch, not an edge case. The likelihood of measurable loss increases with mempool delay, gas-price volatility, or normal AMM price movement between transaction submission and inclusion — none of which require a malicious actor.

### Recommendation
- Add an explicit `deadline` field to `DispatchPost`, `DispatchGet`, and the `fundRequest` call signature, populated by the caller (e.g., `block.timestamp + userSuppliedWindow`), rather than hardcoding `block.timestamp` in `EvmHost`.
- After each `swapETHForExactTokens` call, check the actual ETH spent and refund any unspent `msg.value` directly to `_msgSender()` rather than leaving it in the `EvmHost` contract.
- Add a slippage/maximum-input check (e.g., revert if the eventual swap cost would exceed a user-specified `amountInMax`) to bound worst-case cost given deferred execution.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` with `msg.value = X` intending to cover `post.fee` in fee-tokens, expecting the extra ETH buffer to be refunded.
2. The router call `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` executes at whatever time it is actually mined; because the deadline equals the execution-time timestamp, it can never revert due to staleness — even if inclusion was delayed substantially. [1](#0-0) 

3. Suppose actual cost to acquire `post.fee` fee-tokens is `Y < X`. The router refunds `X - Y` ETH to `msg.sender` of the swap call, which is `EvmHost` itself.
4. `EvmHost` has no logic to forward this `X - Y` refund to the user and no admin/user-facing sweep function for native ETH, so the funds remain permanently stuck in the contract, unrecoverable by the depositor — confirmed by the absence of any `withdraw`/`sweep`/`rescue` function in `EvmHost.sol` from source inspection.

     * @notice Swaps ETH for exact amount of tokens through V3 with deadline protection.
     * @param amountOut The exact amount of tokens to receive
     * @param path Array of token addresses representing the swap path
     * @param recipient Address that will receive the output tokens
     * @param deadline Unix timestamp deadline by which the transaction must confirm
     * @return amounts Array of amounts [ethSpent, tokensReceived]
     */
    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory)
    {
        address weth = _params.WETH;
        if (path[0] != weth) revert InvalidWethAddress();

        (bool sent,) = weth.call{value: msg.value}("");
