## Title
Copilot conflict-resolution response can spoof `action` to silently discard a real hunk-level merge and pick the wrong side of an attacker-influenced conflict - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The report's bug class is: a computed, security-relevant value (`minPrimary`) is unconditionally overwritten to a fixed derivation, silently discarding another parameter (`oracleSlippagePercent`) that was supposed to modulate it — with no check that the override path was actually appropriate for the situation. The Desktop analog is in the Copilot "resolve conflicts" pipeline: when a model response for a file includes an `action` field, the app unconditionally discards that file's real per-hunk merge content and substitutes an empty-string placeholder, without ever verifying that the file is actually a delete-vs-modify conflict.

### Finding Description
`validateResolutionPaths` skips the hunk-count check for any resolution that carries an `action`: [1](#0-0) 
It never cross-checks that against `expectedFiles`/`IFileConflictContext.deleteConflict` — i.e. it never confirms the file is actually a delete-vs-modify conflict before accepting the `action` shortcut.

`reassembleResolutions` then unconditionally honors `raw.action`, discarding any hunks and never touching the file's real conflict-marker content: [2](#0-1) 
Compare this with the legitimate delete-conflict detection, which is based on `deletedSide` set during context gathering (only true delete-vs-modify conflicts get `deleteConflict`): [3](#0-2) 

The model prompt explicitly instructs the LLM to only use `action` for delete-vs-modify conflicts, but this is a soft, unenforced convention baked into the system prompt text, not a code-level invariant: [4](#0-3) 

The entire hunk/context/commit-message/PR-description input to the model is attacker-influenceable: it comes directly from conflict-marker content (ours/theirs/base) and commit metadata gathered from a fetched/merged branch (`app/src/lib/copilot-conflict-context.ts`), which an attacker fully controls if they authored the upstream branch, PR, or commits being merged/rebased. A prompt-injection payload embedded in a commit message, PR description, or the conflicting file content itself could induce the model to emit `"action": "keep"` (or `"delete"`) for a path that is a genuine three-way text conflict with real, security- or correctness-relevant hunks. Because neither `validateResolutionPaths` nor `reassembleResolutions` verifies the file's actual conflict shape before honoring `action`, the pipeline accepts it: the real hunk resolutions are silently dropped (`resolvedContent: ''`), and the file is instead resolved as a whole-side pick (`ManualConflictResolution`) — i.e. the wrong content is applied to a file that actually needed a real merge, and the corruption happens without any error, retry, or user-visible signal that hunks were discarded.

This mirrors the seed bug precisely: a would-be-configurable/validated input (`oracleSlippagePercent` ↔ real hunk resolutions) is discarded in favor of a hard-coded override (`balancerPoolSlippageLimitPercent`-only calc ↔ `action`-only calc) without checking that the override is actually applicable to the case at hand.

### Impact Explanation
This can cause silent corruption of what the user commits: the actual merged/resolved content for a genuinely conflicted file is thrown away and replaced by an entire "ours" or "theirs" side, chosen by attacker-influenced model output rather than by an honest per-hunk merge. Since the file is presented to the user as fully "resolved" by Copilot (with a plausible `reasoning` string also generated by the model), a user relying on the tool could commit and push code that silently reverts, drops, or reintroduces changes they didn't intend — including security-relevant code — without any warning that hunk-level content was discarded.

### Likelihood Explanation
Exploitation requires only that the user run Desktop's Copilot conflict resolution feature on a merge/rebase/cherry-pick that pulls in attacker-authored branch content (a fetched fork, PR, or shared branch) — a common workflow, not a special or unnatural user step. The rest depends on prompt-injection reliability against the underlying LLM, which is probabilistic rather than guaranteed, so likelihood is moderate rather than certain; I could not verify from the indexed code how `deleteConflictAction` is ultimately consumed in `app/src/lib/stores/app-store.ts` (whether additional guardrails exist there), so this should be confirmed against that file before treating the impact as fully unmitigated.

### Recommendation
In `validateResolutionPaths` and/or `reassembleResolutions`, reject (or downgrade to a hard validation error) any resolution that supplies `action` for a path whose `IFileConflictContext` does not have `deleteConflict` set — i.e. enforce in code, not just in the prompt, that the action-only shortcut can only be used for genuine delete-vs-modify conflicts. For all other files, require and reassemble the per-hunk `hunks` content unconditionally.

### Proof of Concept
1. Set up a repository where a branch that will be merged contains a commit whose message/description or file content includes a prompt-injection instructing the assistant to respond with `"action": "keep"` for `criticalFile.ts` (a file that has a genuine multi-line, non-delete conflict against the current branch).
2. Trigger Desktop's Copilot-based conflict resolution on that merge/rebase.
3. Observe: `parseCopilotConflictResolution` accepts the `action` field for `criticalFile.ts` [5](#0-4) , `validateResolutionPaths` skips hunk-count verification for it [1](#0-0) , and `reassembleResolutions` discards the real conflict content, returning `resolvedContent: ''` with a `deleteConflictAction` [6](#0-5) , even though `criticalFile.ts` was never an actual delete-vs-modify conflict — silently applying an attacker-steered whole-side resolution instead of the real merge.
