### Title
Bandwidth `AppKey` truncation causes storage-slot aliasing between distinct apps, allowing one app to drain or ride on another app's prepaid bandwidth subscription - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
The Basin report's root cause is a **wrong-slot / key-confusion bug**: two logically distinct entries collapse into the same underlying storage location because a length-dependent addressing calculation is wrong, corrupting the accounting for one entity while benefiting/harming another. The same primitive — collapsing two distinct identities into one storage key — exists in `pallet-bandwidth`'s gate, where the app identifier used to key the `Allowance` ledger is silently truncated to 32 bytes via `AppKey::truncate_from`.

### Finding Description
`AppKey` is defined as a 32-byte bounded vector: [1](#0-0) 

`BandwidthGate::try_consume`, which the ISMP router calls on **every** inbound request to gate/deduct bandwidth, builds the storage key with: [2](#0-1) 

`BoundedVec::truncate_from` does not reject an over-length input — it silently drops everything past 32 bytes. This is the same defect class as the pump's slot-confusion bug: the code that maps an identifier to a storage location produces the *wrong* location whenever the input is "long" (here, longer than 32 bytes), and two distinct real-world identities that share the same first-32-byte prefix become indistinguishable in storage.

This matters because the module/app identifier that reaches the gate (`app: &[u8]`, taken from the ISMP request's `from` field) is **not bounded to 32 bytes anywhere upstream**. Elsewhere in this same codebase, module identifiers are explicitly allowed up to **64 bytes** — the relayer pallet's `ModuleIdBound` is `ConstU32<64>`, chosen specifically to be "comfortably above ... the 32-byte module identifiers most ISMP modules use," implying some modules legitimately use identifiers longer than 32 bytes: [3](#0-2) 

By contrast, the relayer pallet's reward-claim path explicitly rejects (does not truncate) over-length module ids with `try_into().map_err(...)`: [4](#0-3) 

The bandwidth gate does the opposite — it truncates instead of rejecting — which is the exact asymmetry class the Basin report flags: one code path (`LibBytes`) does the slot math correctly, the other two (`LibBytes16`, `LibLastReserveBytes`) get it wrong, causing cross-entry corruption.

### Impact Explanation
Because `Allowance<T>` and `Allowlist<T>` are keyed by this truncated `AppKey`, any two distinct apps on the same source chain whose real identifiers agree on the first 32 bytes (e.g. a 64-byte module id vs. a crafted 32+-byte id sharing that prefix, or two contracts/pallets whose identifiers were padded/encoded to share a common 32-byte head) are treated as **the same app** by the gate:
- An attacker-controlled app can craft/choose an identifier whose first 32 bytes match a legitimate paying app, and then have its own inbound messages billed against — and pass the gate using — that app's prepaid `Subscription` list, consuming bandwidth the victim purchased.
- Symmetrically, the legitimate app's own messages can be silently gated/drained by traffic attributed to the colliding identifier, since `try_consume` mutates `Allowance<T>::mutate(source, &key, ...)` on the shared key regardless of which real app the bytes came from.

This is a direct "wrong beneficiary" / logic-attack outcome on a paid resource (bandwidth balances), matching the impact gate's requirement that bandwidth balances "move exactly once and only to the rightful beneficiary."

### Likelihood Explanation
The gate is on the **public, unprivileged path**: it runs on every non-purchase POST request from any registered source chain, and the `app` bytes are attacker-influenced (`request.from`), not admin-controlled. No relayer/prover/admin collusion is required — an ordinary user deploying/using an app whose identifier is engineered to share the same 32-byte prefix as a target is sufficient. The main uncertainty is whether any currently-registered module actually emits `from` identifiers longer than 32 bytes today; however, the protocol's own module-id bound elsewhere (64 bytes) and the truncate-vs-reject asymmetry show the bandwidth pallet was not defensively coded against this, and nothing in `try_consume` enforces or even checks the input length before truncating.

### Recommendation
Replace `AppKey::truncate_from(app.to_vec())` with a fallible conversion (`BoundedVec::try_from`) and reject the request (or fail closed, e.g. treat as `NoAllowance`) when `app.len() > 32`, mirroring the `outbound_request.rs` pattern that rejects rather than truncates over-length module identifiers. Apply the same fix consistently to whatever code credits subscriptions (`force_credit`, purchase `on_accept`) so both the write side and the read/gate side key on identical, non-lossy `AppKey` derivation.

### Proof of Concept
1. App `X` purchases bandwidth; its ISMP module identifier is `id_X` (32 bytes), stored/keyed as `AppKey = id_X`.
2. Attacker deploys/operates app `Y` whose module identifier is `id_X || <arbitrary suffix>` (>32 bytes, sharing `id_X` as prefix) — feasible wherever module ids up to 64 bytes are accepted (as the relayer pallet's `ModuleIdBound` confirms is a supported identifier length in this protocol).
3. Attacker's app `Y` sends a normal (non-purchase) request through the router; `BandwidthGate::try_consume(source, id_X||suffix, bytes)` runs `AppKey::truncate_from` and derives the same 32-byte key as `X`.
4. The gate drains from `X`'s FIFO `Subscription` list — `Y`'s traffic is billed against and passes using `X`'s paid allowance, and `BandwidthConsumed`/ledger state under key `id_X` is corrupted with `Y`'s consumption, exactly analogous to the pump writing a corrupted reserve value into the wrong (aliased) slot.
