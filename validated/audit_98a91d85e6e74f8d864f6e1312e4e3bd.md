## Title
Missing forfeiture check in `mWOMSVBaseRewarder._calExpireForfeit` lets in-cooldown/cycled mWomSV stakers keep 100% of rewards, permanently denying the forfeited yield that should flow back to genuine long-term lockers - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWomSV.getRewardablePercentWAD` computes a time-weighted "rewardable" percentage that should discount rewards for balance sitting in cooldown, exactly like the working analogue in `vlMGP`/`vlMGPBaseRewarder`. However, `mWOMSVBaseRewarder._calExpireForfeit` never calls it, so `rewardableAmount` is unconditionally set to the full claimed amount and `forfeitAmount` is always `0`. Any holder who moves mWOM into cooldown via `startUnlock` and then claims rewards keeps 100% of rewards with none of the intended penalty, and the forfeited portion that should be re-queued to remaining/long-term stakers via `_queueNewRewardsWithoutTransfer` is never generated.

### Finding Description
Compare the two forfeit implementations:

`rewards/vlMGPBaseRewarder.sol` (working, intended pattern): [1](#0-0) 
computes `rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account)` and scales `rewardableAmount` accordingly, so users mid-cooldown forfeit a portion of rewards, which is re-queued into `rewardPerTokenStored` for everyone else.

`rewards/mWOMSVBaseRewarder.sol` (broken): [2](#0-1) 
sets `rewardableAmount = _amount` directly and never references `mWOMSV.getRewardablePercentWAD(_account)`, even though that function is implemented and exported on `mWomSV`: [3](#0-2) 

Because `mWomSV.balanceOf` and the `mWOMSVBaseRewarder.balanceOf`/`totalStaked` accounting count cooldown amounts the same as fully-locked amounts (cooldown only reduces stake upon final `unlock`/`withdrawMWomSVFor`): [4](#0-3) [5](#0-4) 
a staker who calls `startUnlock` retains full reward accrual for the entire cooldown window and, on `getReward`, suffers zero forfeiture because `_sendReward`/`_calExpireForfeit` never invoke the percentage check: [6](#0-5) 

The reachable path is fully unprivileged: `SmartWomConvert.convert(..., _mode=2)` converts WOM to mWOM and locks directly into `mWomSV` via `mWomSV.lockFor`: [7](#0-6) 
then the public `lock`/`startUnlock`/`unlock` functions on `mWomSV` are callable by any EOA: [8](#0-7) [9](#0-8) [10](#0-9) 
and `getReward` on the rewarder is reachable through `MasterMagpie` (which is the only enforced access control, `onlyMasterMagpie`) with no `nonReentrant`/forfeit-aware guard beyond the (broken) `_calExpireForfeit`: [11](#0-10) 

### Impact Explanation
This is a "theft/permanent loss of unclaimed yield" class issue: the forfeited-reward pool that the design intends to redistribute to remaining/long-term mWomSV holders (via `_queueNewRewardsWithoutTransfer`, mirrored correctly in `vlMGPBaseRewarder`) never materializes for mWOMSV. Every staker who is ever in cooldown (not just a scripted attacker) keeps rewards that should have been partially forfeited and redistributed, meaning long-term lockers permanently lose the yield they were entitled to receive under the parallel, working vlMGP design. However, note this defect applies uniformly to any account with a cooldown position, not specifically amplified by "repeated cycling" — a single `startUnlock`→`getReward` already captures the full benefit, so there is no incremental advantage gained specifically from the multi-cycle sequence described versus a single cooldown pass.

### Likelihood Explanation
Trivial and fully unprivileged: only requires holding WOM/mWOM, calling `SmartWomConvert.convert`/`depositFor`, `mWomSV.lock`/`lockFor`, `startUnlock`, and claiming rewards through `MasterMagpie`. No special capital, timing, or race condition needed; the missing check is a permanent code defect, always exploitable while the cooldown mechanism is used at all.

### Recommendation
In `rewards/mWOMSVBaseRewarder.sol::_calExpireForfeit`, mirror `vlMGPBaseRewarder`: fetch `mWOMSV.getRewardablePercentWAD(_account)` (already implemented in `mWomSV`), scale `rewardableAmount = _amount * rewardablePercentWAD / 1e18`, and queue the resulting `forfeitAmount` back via `_queueNewRewardsWithoutTransfer` exactly as the vlMGP implementation does.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie`, `SmartWomConvert` per existing test harness/mocks.
2. Fund a reward token and call `_provisionReward`/equivalent to accrue `rewardPerTokenStored` over time.
3. User A ("long-term locker"): converts WOM→mWOM→locks into `mWomSV`, never calls `startUnlock`, holds for the full test period.
4. User B ("attacker"): converts equal principal, locks, immediately calls `startUnlock` for 100% of balance, waits for `coolDownInSecs`, calls `getReward` before or after `unlock`, then `unlock`s and relocks, repeating across the period.
5. Assert: `_calExpireForfeit` returns `0` for User B despite being fully in cooldown for the whole period (demonstrating the missing check), and that User B's total claimed reward equals User A's per-unit-staked reward with zero forfeiture difference — confirming no forfeiture is ever applied regardless of cooldown status, in contrast to an equivalent `vlMGP`/`vlMGPBaseRewarder` test where an in-cooldown staker's `_calExpireForfeit` returns a nonzero forfeit amount that gets requeued to `rewardPerTokenStored`.
6. Assert final invariant break: total `historicalRewards` distributed to cooldown-cycling accounts under mWOMSV exceeds what the `vlMGP` parallel mechanism would have allowed for an equivalent cooldown pattern, i.e., `_queueNewRewardsWithoutTransfer` for forfeited amounts is never invoked in the mWOMSV path.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;

            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

```text
    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
```
