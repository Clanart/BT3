### Title
`ReceivedOutput::read` accepts untrusted offset/output pairs without verifying the offset actually derives the output's `script_pubkey`, allowing unspendable outputs to be reported as received funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report's bug class is "a deserialized/processed field is never validated against the set of values (or the object) it must be consistent with, so an out-of-range/inconsistent value silently produces an unusable state." The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`, which deserializes an attacker-controlled `(offset, TxOut, OutPoint)` triple and returns it as a spendable received output without ever checking that `offset` actually maps the scanner's key to `output.script_pubkey`.

### Finding Description
`Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) is the only *trusted* constructor of `ReceivedOutput`: it looks up `output.script_pubkey` in `self.scripts` and attaches the registered `offset`, guaranteeing `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey`. However, `ReceivedOutput::read` (lines 122-134) — an explicitly in-scope untrusted-bytes entry point — reconstructs a `ReceivedOutput` from raw bytes by reading a scalar via `Secp256k1::read_F`, then consensus-decoding an arbitrary `TxOut` and `OutPoint`. No consistency check exists anywhere: `offset()`, `output()`, and `value()` (lines 100-118) return the fields verbatim, and there is no `verify`/re-derivation method on `ReceivedOutput`. Mirroring the audit finding (a status value outside {0..4} is written but never processed, leaving the recipient in a state that cannot advance), an offset/script pair that is mutually inconsistent is accepted but can never advance to a successful spend: signing under `key + offset·G` produces a key whose P2TR script does not equal `output.script_pubkey`, so the input can never satisfy the output's key-path spend.

### Impact Explanation
An unprivileged party that supplies `ReceivedOutput` bytes (e.g., a peer/coordinator path feeding serialized outputs into the wallet) can cause the wallet to report a specific Bitcoin output as received and spendable when it is not. Two failure modes:

1. **Phantom spendable output**: a crafted `offset` + `TxOut` whose `script_pubkey` is *not* `P2TR(key + offset·G)` is treated as a received output. Any downstream accounting that trusts `value()` credits funds that can never be spent — the acceptance criterion "funds reported received that are not spendable."
2. **Stuck state**: consistent with the source bug, the malformed entry is accepted into the set of spendable outputs and then permanently fails at spend time (signature verification against the wrong tweaked key), wedging coin selection rather than being rejected at deserialization.

### Likelihood Explanation
Reachable whenever serialized `ReceivedOutput`s cross a trust boundary (the structure has `serialize`/`read` precisely for transport/storage). The attacker needs only to control bytes fed to `read` — listed as an allowed attack surface. The bug is deterministic (no race/negligible probability) but requires an integrator path that consumes untrusted `ReceivedOutput` bytes, matching the source finding's Medium severity.

### Recommendation
Either bind the check into the type or expose an explicit validation step:

- Add a `verify(&self, key: &ProjectivePoint) -> bool` (or make `read` take the scanner key) asserting `p2tr_script_buf(key + ProjectivePoint::GENERATOR * self.offset) == Some(self.output.script_pubkey.clone())`, rejecting any `(offset, output)` pair that fails it — the analog of the report's "judge the range / reject unexpected status" recommendation.
- Alternatively, document and enforce that `ReceivedOutput` may only be constructed by `Scanner::scan_transaction`/`scan_block`, and gate `read` behind a validation pass before the value is used for accounting or coin selection.

### Proof of Concept
```rust
// Attacker crafts bytes: an offset that does NOT derive the TxOut's script.
let mut bytes = Vec::new();
// offset = 1
bytes.extend((Scalar::ONE).to_bytes());
// TxOut paying to P2TR of an unrelated key K' (or any attacker-chosen script)
bytes.extend(serialize(&TxOut { value: Amount::from_sat(50_000), script_pubkey: fake_p2tr }));
// any outpoint
bytes.extend(serialize(&outpoint));

// Wallet deserialization accepts it without any consistency check.
let ro = ReceivedOutput::read(&mut &bytes[..]).unwrap();
assert_eq!(ro.value(), 50_000); // reported as received funds

// Spending signs under key + 1·G, whose P2TR script != fake_p2tr,
// so the input can never be spent: funds reported, never spendable.
```
