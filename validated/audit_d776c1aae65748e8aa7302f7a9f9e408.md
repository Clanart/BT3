### Title
`ReceivedOutput::read` accepts a caller-supplied key-derivation `offset` instead of deriving it from the registered script, allowing misattributed/unspendable reported funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to CVE-2024-12125 (a field the UI marks read-only is accepted verbatim by the server), `ReceivedOutput` treats `offset` — a value that is fundamentally *derived state* (the script→offset mapping held only by the `Scanner`) — as attacker-controlled wire data. `ReceivedOutput::read` deserializes `offset`, `output` (TxOut), and `outpoint` directly from the byte stream with no consistency check between the `offset` and the `script_pubkey` contained in `output`. The correct value is only ever established inside `Scanner::scan_transaction`, which looks up the offset from the internally-registered `scripts` map.

### Finding Description
`Scanner::register_offset` builds the authoritative mapping `scripts: HashMap<ScriptBuf, Scalar>` and `scan_transaction` populates `ReceivedOutput.offset` from that map, guaranteeing `script_pubkey == p2tr(key + G*offset)`. However, `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122) simply reads a scalar from the reader and stores it, with no re-derivation:

- `offset` is read via `Secp256k1::read_F(r)` and trusted unconditionally (mod.rs:123).
- `output` and `outpoint` are consensus-decoded and trusted (mod.rs:128-131).
- Nothing checks that `output.script_pubkey` equals `p2tr_script_buf(key + G*offset)` — indeed `read` cannot, because it doesn't take the base key, so the invariant is silently delegated to whoever produced the bytes.

Downstream, the offset is load-bearing for key attribution and signing:
- `Output::key()` reconstructs the purported owning key as `scriptKey - G*offset` (processor/src/networks/bitcoin.rs:112-122), so a forged offset yields an *arbitrary* reported owner key.
- `SignableTransaction`/`multisig` applies `keys.offset(output.offset())` per input, so an incorrect offset causes the FROST multisig to produce signatures under `group_key + G*(tweaks + forged_offset)`, which will not correspond to the actual `script_pubkey` in the UTXO.

### Impact Explanation
An unprivileged party who can inject serialized `ReceivedOutput` bytes (a listed in-scope sink) can cause either:

1. Funds reported received that are not spendable: a `ReceivedOutput` pairing a real deposit's `script_pubkey`/`outpoint` with a wrong `offset` will be tracked as owned by `scriptKey - G*offset` (a key unrelated to the vault), and any spend attempt produces a signature valid for the wrong tweaked key — the UTXO can never be signed for correctly, locking deposited funds.
2. Misattribution of deposits: since `key()` is `scriptKey - G*offset`, crafted bytes make an arbitrary output report an arbitrary owning key, corrupting balance/key attribution.

This matches the report's class exactly: a server-side-derived value (the scanner-registered offset) is accepted from client-controlled wire data without revalidation.

### Likelihood Explanation
Reachability requires untrusted bytes to reach `ReceivedOutput::read`, which the task scope explicitly enumerates as an exposed deserialization sink (`ReceivedOutput::read` is listed among attacker-fed readers). No signature forgery or key recovery results — the impact is fund lockup/misattribution, fitting Medium severity, consistent with the "funds reported received that are not spendable" accepted-impact category.

### Recommendation
Make the derived nature of `offset` explicit: either (a) have `ReceivedOutput::read` take the expected base `key`/`Scanner` and verify `p2tr_script_buf(key + G*offset) == output.script_pubkey`, rejecting inconsistent inputs; or (b) re-derive the offset at the consumer: in `Output::key()`/signing setup, verify the computed key equals the expected group key before treating the output as owned/spendable.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet — conceptual PoC
// Victim vault key (even, taproot-tweakable), e.g. tweak_keys(...).group_key()
let key: ProjectivePoint = victim_key;
let scanner = Scanner::new(key).unwrap();

// A real deposit tx paying the vault's P2TR script
let real_outputs = scanner.scan_transaction(&deposit_tx);
let real = &real_outputs[0]; // offset == Scalar::ZERO, correct

// Attacker forges a serialized ReceivedOutput: same TxOut + OutPoint,
// but a "read-only"/derived field (offset) rewritten
let mut forged_bytes = real.output().clone(); // real script_pubkey
let mut buf = vec![];
// arbitrary wrong offset, e.g. Scalar::ONE instead of ZERO
buf.extend(Scalar::ONE.to_bytes());
buf.extend(serialize(real.output()));
buf.extend(serialize(real.outpoint()));

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // accepted, no check

// Reported owner key is now wrong:
//   key() = scriptKey - G*1  !=  vault group key
// Any SignableTransaction spending `forged` signs under group_key + G*(tweaks+1),
// producing a signature invalid for the actual script_pubkey -> funds locked.
```

Caveat: I verified the deserialization path and downstream offset usage, but the transport path that feeds untrusted bytes to `ReceivedOutput::read` lives outside the in-scope crates (`processor/`), so concrete end-to-end reachability rests on the task's explicit listing of `ReceivedOutput::read` as an attacker-reachable sink.
