### Title
Shared-outpoint withdrawal UTXOs let `get_payout_txs_for_withdrawal_utxos`/`update_finalized_payouts` credit one real payout to two withdrawal indices, letting an operator be reimbursed for a payout it never funded - ([File: core/src/database/verifier.rs], [File: core/src/verifier.rs])

### Summary
`get_payout_txs_for_withdrawal_utxos` joins the `withdrawals` table to `bitcoin_syncer_spent_utxos` solely on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, with no constraint preventing two different withdrawal indices from sharing that outpoint. Since a Bitcoin outpoint can only be spent once, if withdrawal index `i` and index `j` are both registered with the identical `withdrawal_utxo`, the single real payout transaction that spends it will be joined against both rows, and `update_finalized_payouts` will write the same `payout_txid` and `payout_payer_operator_xonly_pk` into both `withdrawals` rows.

### Finding Description
The broken binding is: `withdrawals.payout_payer_operator_xonly_pk` for index `j` == the operator that actually funded the specific output paying deposit `j`'s recipient. This binding is violated because attribution is keyed only by the shared `(withdrawal_utxo_txid, withdrawal_utxo_vout)` pair, not by `idx`.

- `withdrawal_utxo_txid/vout` for each withdrawal index is populated from `collect_withdrawal_utxos`, which reads the raw `txId`/`outputId` bytes an unprivileged user supplies to Citrea's `withdraw()` call [1](#0-0) . Nothing in this repository enforces that two different withdrawal indices cannot be registered with the same outpoint bytes.
- `get_payout_txs_for_withdrawal_utxos` joins `withdrawals w` to `bitcoin_syncer_spent_utxos bsu` purely `ON bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`, returning `(idx, spending_txid)` pairs [2](#0-1) . If two `idx` rows share the same outpoint, and that outpoint is spent exactly once (as any Bitcoin UTXO can only be), the join yields two rows: `(i, spending_txid)` and `(j, spending_txid)` for the same real payout transaction.
- `Verifier::update_finalized_payouts` iterates these pairs, parses the OP_RETURN operator key once per pair, and pushes `(idx, payout_txid, operator_xonly_pk, block_hash)` for both `i` and `j` [3](#0-2) , then commits both via `update_payout_txs_and_payer_operator_xonly_pk` [4](#0-3) [5](#0-4) . There is no dedup or "first authoritative registration wins" logic anywhere in this path.
- Downstream, `PayoutCheckerTask::run_once` pulls "unhandled payouts" per operator key and, for each, resolves a distinct `deposit_data` from `move_to_vault_txid` and calls `Operator::handle_finalized_payout` to release/reimburse that deposit's vault [6](#0-5) . Because both `i` and `j` now carry the same `payout_payer_operator_xonly_pk`, the task will process both indices as legitimate unhandled payouts for the same operator, even though only one real Bitcoin transaction ever paid out — satisfying only one of the two withdrawer's outputs.

None of the existing guards catch this: `SECP.verify_schnorr` validates the payout's individual signature but says nothing about cross-index outpoint uniqueness; `is_deposit_valid` and `verify_storage_proofs` validate a single deposit/withdrawal's storage proof, not the uniqueness of `withdrawal_utxo` across indices; there is no DB uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` enforced in the update/join queries reviewed.

### Impact Explanation
An operator that fronted exactly one payout (for index `i`) is automatically also marked and reimbursed for index `j`'s deposit by the automated `PayoutCheckerTask`, without ever separately funding `j`'s payout. This falls under the Critical category "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal," since deposit `j`'s vault collateral is released via `handle_finalized_payout` while its actual recipient was never separately paid on Bitcoin. This is repeatable per deposit pair the attacker chooses to alias, and the blast radius extends to any operator whose payout happens to spend a shared outpoint that an attacker deliberately registered against two withdrawal indices.

### Likelihood Explanation
The attacker only needs to call Citrea's `withdraw()` twice, supplying the identical `txId`/`outputId` bytes for two different withdrawal indices — a capability explicitly granted (choosing withdrawal UTXO bytes). No verifier/operator/aggregator privilege, key material, or majority hashrate is required. The only uncertainty is whether Citrea's Bridge contract itself rejects re-registering an already-used withdrawal UTXO across indices; that check, if it exists, lives entirely in the Citrea contract (out of this repository's index) and could not be verified from the code available here. Assuming the contract does not enforce global outpoint uniqueness (nothing in this repo's `collect_withdrawal_utxos`/schema suggests such a check is mirrored or re-validated on the Clementine side), the attack is cheap (Bitcoin fees for one real payout, plus two L2 `withdraw()` calls) and fully repeatable.

### Recommendation
Disambiguate payout attribution by tracking, per `withdrawal_utxo` outpoint, which specific `idx` registration is authoritative (e.g., first-registered-wins, or better, require the payout transaction's OP_RETURN/committed data to explicitly encode the withdrawal `idx` it is settling, and validate that against the join result instead of trusting outpoint equality alone). Add a uniqueness constraint or explicit conflict-detection in `get_payout_txs_for_withdrawal_utxos` so that when multiple `idx` rows share an outpoint, only the index whose withdrawal request was authoritative (per Citrea's own accounting) gets `payout_payer_operator_xonly_pk` set, and flag/reject the rest instead of silently double-crediting.

        &self,
        last_withdrawal_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, OutPoint)>, BridgeError> {
        let mut utxos = vec![];

        let mut start_idx = match last_withdrawal_idx {
            Some(idx) => idx + 1,
            None => 0,
        };

        loop {
            let withdrawal_utxo = self
                .contract
                .withdrawalUTXOs(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match withdrawal_utxo {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Withdrawal utxo not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            let withdrawal_utxo = withdrawal_utxo.expect("Failed to get withdrawal UTXO");
            let txid = withdrawal_utxo.txId.0;
            let txid =
                Txid::from_slice(txid.as_ref()).wrap_err("Failed to convert txid to Txid")?;
            let vout = withdrawal_utxo.outputId.0;
            let vout = u32::from_le_bytes(vout);
            let utxo = OutPoint { txid, vout };
            utxos.push((start_idx as u64, utxo));
            start_idx += 1;
        }
        Ok(utxos)
    }
