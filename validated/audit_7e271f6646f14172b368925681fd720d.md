### Title
Prompt injection via attacker-controlled merge conflict content leads to silent code injection when applying Copilot conflict resolutions - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop's Copilot-assisted conflict resolution feature sends the raw, unmodified content of conflicting hunks — which can originate entirely from an attacker-controlled branch fetched or merged into the user's repository — to an LLM, and then writes the model's freeform output directly to disk and stages it for commit, with only a narrow staleness guard that does not validate the content itself. This mirrors the reported bug pattern: a special-case guard exists on one path (skip if the user externally resolved the file) but the surrounding invariant (the written content must be attributable only to the two known conflict sides) is not enforced anywhere, leaving a gap an attacker can exploit through the untrusted input they control.

### Finding Description
When a merge/rebase/cherry-pick hits conflicts, `buildConflictContext` reads the raw file content containing conflict markers for every conflicted file and forwards it to the Copilot conflict-resolution model as context [1](#0-0) . This raw content is not restricted to structured hunks — it is the literal on-disk text between conflict markers, which is fully attacker-controlled if the "their" side comes from a cloned/fetched branch, a PR, or any remote the user merges from.

The model's response (`IRawFileResolution`) is reassembled into full file content via `reassembleResolutions`, which trusts the model's `raw.hunks`/`resolvedContent` to only replace conflicting regions, but there is no verification step confirming the reassembled content is actually derived solely from "ours"/"theirs" [2](#0-1) .

`_applyCopilotConflictResolutions` then writes this content straight to disk and `git add`s it once the user clicks "Continue Merge": [3](#0-2) 

The only safety check present is a staleness guard that skips a file if it was *externally* resolved by the user in their editor while the dialog was open: [4](#0-3) 

This guard — analogous to the `totalPending == 0` special case in the audited contract's `spin()` — only covers one narrow scenario (user already fixed the file manually) and is not paired with any content-level validation of what the model chose to write. There is no check that `resolution.resolvedContent` is a plausible combination of the "ours" and "theirs" hunks; the model output is trusted wholesale, just as `fulfillRandomness` in the report trusted `pendingCounts` without re-checking the same invariant `spin()` enforced.

Because merge-conflict text is inherently attacker-influenced (it is literally the diff between the user's branch and a branch the attacker controls), a crafted conflict block containing prompt-injection instructions (e.g., embedded within a comment or string literal that looks like part of the conflicting code) can manipulate the model into emitting `resolvedContent` containing attacker-chosen code unrelated to the actual conflict — while the separately generated `summary`/`reasoning` field shown to the user may not reflect this, since it is generated independently by the same manipulable model.

### Impact Explanation
If successful, this leads to silent corruption of what the user commits and pushes: attacker-chosen code is written into the user's working tree and staged via `git add` inside `_applyCopilotConflictResolutions`, without the file ever being diffed against a trustworthy source. The user's confirmation is based on Copilot's own possibly-manipulated summary rather than the actual bytes written. This can result in backdoored code entering a commit that a maintainer with push access unknowingly publishes.

### Likelihood Explanation
Exploitation requires: (1) the victim to use the opt-in "Resolve with Copilot" conflict feature, (2) a real merge/rebase/cherry-pick conflict against attacker-authored content (achievable simply by proposing or authoring a branch that conflicts with the target), and (3) a successful prompt injection against the underlying model, which is inherently probabilistic and not guaranteed. This keeps likelihood at Low-to-Medium, similar to how the original report was rated Low likelihood despite High impact — the precondition (feature usage + conflict with attacker content) is realistic but the injection success is not deterministic.

### Recommendation
- Do not trust model-generated `resolvedContent` verbatim. Validate that the reassembled hunks only replace the exact conflict-marker regions found in the original file and that content outside those regions is byte-identical to the original.
- Surface a real diff (original vs. resolved) to the user before writing/staging, rather than relying solely on the model's self-reported summary.
- Extend the existing staleness/safety guard in `_applyCopilotConflictResolutions` to also validate resolution provenance (i.e., reject any resolution whose content cannot be shown to derive from the two known sides), closing the same class of gap the report identified between `spin()` and `fulfillRandomness()` — a guard enforced in one code path must be enforced everywhere the same invariant matters.

### Proof of Concept
1. Attacker opens a PR / pushes a branch that intentionally conflicts with a file in the target repo, crafting the conflicting hunk to include text designed to hijack the LLM's instructions (indirect prompt injection embedded in code comments/strings).
2. Victim maintainer, using GitHub Desktop, merges/rebases and hits the conflict, then clicks "Resolve with Copilot" [5](#0-4) .
3. The conflicting content (including the injected instructions) is sent as-is via `buildConflictContext` [1](#0-0) .
4. The manipulated model returns `resolvedContent` containing attacker-chosen code framed as the "resolution."
5. Victim clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes and stages the file without validating that its content is a genuine merge of ours/theirs [6](#0-5) .
6. Victim commits and pushes, publishing attacker-controlled code that passed only a superficial "was this externally resolved?" check.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
