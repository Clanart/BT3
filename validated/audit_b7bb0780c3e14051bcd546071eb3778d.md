## Title
A malicious git remote can spoof a `WWW-Authenticate` realm header to redirect GitHub Desktop's OAuth sign-in flow (and client secret) to an attacker-controlled host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The reported WLFI bug is a class of "status bypass": a security state (`_excludedVotingPower`) is set on an account, but a secondary code path (`_delegate`/`_update`) fails to re-check that state, letting the excluded value flow to an unprotected destination (a delegatee/new owner) that the original guard never anticipated. The Desktop analog is `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts`: the classification of a remote as a trusted "enterprise"/GitHub endpoint is derived from attacker-controlled input (the `WWW-Authenticate` header value returned by the remote server itself), and that classification is then used, unchecked, to drive a privileged action (initiating GitHub's OAuth sign-in flow, including transmission of the app's `client_secret`) against whatever host the attacker supplied — with no independent verification that the host actually is a GitHub endpoint.

### Finding Description
When Git performs an HTTP(S) authentication attempt against a remote, it forwards any `WWW-Authenticate` response headers to Desktop's git credential helper as `wwwauth[...]` credential fields. `getEndpointKind()` treats this attacker-supplied header as authoritative evidence that a host is a GitHub host: [1](#0-0) 

If the value contains `realm="GitHub"`, the function returns `'enterprise'` — no additional check (such as calling the existing `isGitHubHost()` discovery request, which is only used as a *fallback* later) is performed to confirm the host is a real GitHub/GHE instance.

That classification then feeds `getCredential()`, which — for any endpoint classified as non-`'generic'` that has no existing matching `Account` — calls `ui.promptForGitHubSignIn(endpoint)`: [2](#0-1) 

`promptForGitHubSignIn` inspects only the hostname to decide between the dotcom flow and the enterprise flow, and for anything other than literal `github.com` it starts the enterprise sign-in flow pointed at the attacker's own origin: [3](#0-2) 

`authenticateWithBrowser()` in the sign-in store then opens the system browser at `getOAuthAuthorizationURL(endpoint, csrfToken)`, i.e. `https://<attacker-host>/login/oauth/authorize?client_id=...`: [4](#0-3) 

If the attacker's server captures the OAuth `code`/`state` round trip (e.g. by redirecting back through the app's registered `x-github-client://oauth` deep link, which the attacker fully controls since they control the callback content), `resolveOAuthRequest()` calls `requestOAuthToken(endpoint, code)`, which POSTs `client_id`, **`client_secret`**, and `code` directly to `${endpoint}/login/oauth/access_token` — i.e., to the attacker's host, since `endpoint` is the attacker-chosen origin, not `github.com`: [5](#0-4) 

The only state guard that exists in this subsystem — `hasRejectedCredentialsForEndpoint` — only tracks *rejected* prompts to avoid re-prompting/mis-reporting auth failures; it never validates that the endpoint being classified as GitHub-owned truly is one: [6](#0-5) 

This mirrors the WLFI bug precisely: a trust/classification value (`excludedVotingPower` ↔ `endpointKind === 'enterprise'`) is set based on one signal, but the function that acts on it (`_delegate`/`_update` ↔ `getCredential`/`promptForGitHubSignIn`/`requestOAuthToken`) doesn't re-derive or re-validate that signal from a trustworthy source before performing a sensitive operation, letting attacker-supplied input silently redirect the sensitive action (voting power / OAuth secret and sign-in flow) to an attacker-controlled recipient.

### Impact Explanation
An attacker who merely controls the HTTP responses of a git remote (their own server, or an MITM/malicious proxy the victim is pointed at) can:
- Trick GitHub Desktop into believing an arbitrary host is a legitimate GitHub Enterprise instance, purely via a spoofed `realm="GitHub"` WWW-Authenticate header.
- Cause Desktop to launch the OAuth "Sign in with browser" UX against that attacker host.
- Cause the app's OAuth `client_id`/`client_secret` to be sent to the attacker's `/login/oauth/access_token` endpoint during the token exchange if the attacker completes the redirect back via the app's own registered deep-link scheme.
- Have the resulting attacker-supplied "account"/token silently added to the user's Desktop account list (`fetchUser(endpoint, token)`), after which any subsequent Git operation against that host will transparently present that attacker-issued token as the user's credential.

This satisfies "unauthorized OAuth ... binding" and "credential/token exfiltration" from an attacker-controlled git remote — no local access, malware, or leaked credentials are required, and the only user action needed is a normal `git fetch`/`git clone`/`git pull` against a repository whose remote the attacker controls.

### Likelihood Explanation
Moderate-to-high. Triggering the header spoof requires nothing more than the victim adding/using a remote pointed at a server the attacker controls (a common social/engineering-light scenario already assumed valid per the task's rules, since it's the attacker's own remote/proxy responding, not user-installed malware). The remainder of the chain (OAuth code/state round trip via the desktop:// URL scheme) requires the attacker's server to also handle the redirect, which is fully under attacker control since they own the domain being authenticated against.

### Recommendation
- Do not trust the `WWW-Authenticate` realm value alone to classify a host as `'enterprise'`; require it to be corroborated by the existing `isGitHubHost()` network probe (which validates via the `x-github-request-id` response header from the actual host) before treating it as GitHub-owned.
- Before opening a browser-based OAuth flow or POSTing `client_id`/`client_secret` to `requestOAuthToken`, validate that the target `endpoint` was explicitly entered/approved by the user for GitHub Enterprise sign-in (e.g. via `validateURL`/an explicit "Add Enterprise account" step) rather than being silently derived from a remote's error response.
- Rate-limit or require explicit user confirmation naming the actual hostname before auto-triggering a GitHub sign-in dialog based on heuristics from git credential negotiation.

### Proof of Concept
1. Attacker sets up a Git HTTP server (`https://evil.example.com/attacker/repo.git`) that, on any credential challenge, responds with `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote and performs `git fetch` inside GitHub Desktop.
3. Desktop's credential helper (`createCredentialHelperTrampolineHandler`) invokes `getCredential`, which calls `getEndpointKind`; the spoofed header causes it to return `'enterprise'`. [7](#0-6) 
4. Because no `Account` exists for `evil.example.com`, `ui.promptForGitHubSignIn('https://evil.example.com')` is invoked, launching the enterprise OAuth flow against the attacker's own domain. [8](#0-7) 
5. `authenticateWithBrowser` opens `https://evil.example.com/login/oauth/authorize?client_id=<real_client_id>&state=<csrf>` in the system browser. [9](#0-8) 
6. Attacker's server redirects to `x-github-client://oauth?code=<attacker_code>&state=<csrf>`; Desktop calls `requestOAuthToken('https://evil.example.com', code)`, POSTing `client_id`/`client_secret`/`code` to `https://evil.example.com/login/oauth/access_token`. [10](#0-9) 

(Note: full exploitability of steps 5-6 in the current app build — e.g. whether any additional origin allow-list exists in the OS-level deep-link registration or in `dispatcher.beginEnterpriseSignIn` — could not be fully confirmed from the indexed code; a Devin session with full repo access would be needed to trace `handleAppURL`/deep-link dispatch end-to-end and to check for any missing corroborating checks not captured by this index.)

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}

const hasRejectedCredentialsForEndpoint = new Map<string, Set<string>>()

export const setHasRejectedCredentialsForEndpoint = (
  trampolineToken: string,
  endpoint: string
) => {
  const set = hasRejectedCredentialsForEndpoint.get(trampolineToken)
  if (set) {
    set.add(endpoint)
  } else {
    hasRejectedCredentialsForEndpoint.set(trampolineToken, new Set([endpoint]))
  }
}

export const getHasRejectedCredentialsForEndpoint = (
  trampolineToken: string,
  endpoint: string
) => {
  return (
    hasRejectedCredentialsForEndpoint.get(trampolineToken)?.has(endpoint) ??
    false
  )
}
