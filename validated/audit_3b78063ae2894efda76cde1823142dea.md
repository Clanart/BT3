### Title
Untrusted `ReceivedOutput` bytes let an attacker claim arbitrary Bitcoin outputs as owned by a multisig key, reporting funds that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes endpoints reachable by unauthenticated network actors that leak/abuse internal state (CWE-940, improper verification of the source of a communication). The analog in Serai is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122`, which deserializes an `offset`, a `TxOut`, and an `OutPoint` from untrusted bytes without ever verifying that `output.script_pubkey` actually corresponds to `key + G*offset` — the only thing that makes the output spendable by the multisig. A forged `ReceivedOutput` therefore reports an arbitrary on-chain output (anyone's UTXO, any value) as funds belonging to the group key, and the downstream scheduler plans/signals spends for outputs the multisig cannot spend.

### Finding Description
`Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) is the trusted construction path: it only produces a `ReceivedOutput` when `output.script_pubkey` is found in `self.scripts`, i.e., when the script is exactly `p2tr_script_buf(key + G*offset)` [1](#0-0) .

`ReceivedOutput::read` (`mod.rs:122-134`) reconstructs the same struct from raw bytes but performs no equivalent check — it cannot, because the key is not stored in the struct. It accepts any `(offset, TxOut, OutPoint)` triple [2](#0-1) .

The inconsistency is observable in the `Output::key()` accessor, which derives the owning key *from the untrusted fields themselves*: `read_G(script_pubkey key) - G*offset` [3](#0-2) . That derivation returns a coherent-looking key for any `(script, offset)` pair — it is self-consistent, not a verification. Nothing in `Output::read` (`processor/src/networks/bitcoin.rs:145-166`) or `ReceivedOutput::read` recomputes `p2tr_script_buf(derived_key + G*offset)` and compares it to `script_pubkey`, nor confirms the outpoint exists on-chain [4](#0-3) . The `assert_eq!(output.key(), key)` check exists only on the live scan path (`processor/src/multisigs/scanner.rs:562-563`), not on the deserialization path [5](#0-4) .

### Impact Explanation
An unprivileged party who can get crafted `ReceivedOutput`/`Output` bytes fed to the read path causes the wallet/scheduler to treat a UTXO paying an unrelated Taproot script (controlled by nobody the multisig trusts, or controlled by the attacker) as a balance of the multisig key. Consequences: funds are reported received that are not spendable by the threshold group; `SignableTransaction::new` will be asked to spend inputs whose prevout scripts are attacker-chosen, and since the sighash commits to prevouts, either signing fails/livelocks the scheduler or — if the attacker actually owns that script — the multisig signs a transaction consolidating the attacker's coin into its own accounting (deficit in the honest accounting). This matches the accepted impact class "funds reported received that are not spendable."

### Likelihood Explanation
Reachability requires a path where `ReceivedOutput`/`Output` bytes arrive from an untrusted source (relayed outputs, DB contents written via untrusted input, or an integrator feeding scanner-equivalent data through the deserialize API rather than `scan_transaction`). Within the shipped scanner the check exists, so the concrete exposure is on any path using `read`/`Output::read` on data not produced by `scan_transaction` — exactly the kind of "internal pod reachable without authentication" gap the reference advisory describes. Not exploitable purely by an on-chain transaction, hence Medium rather than High.

### Recommendation
Make the constructor the only way to bind fields: either (a) store the expected `key` inside `ReceivedOutput`/`Output` and, in `read`/`Output::key()`, verify `output.script_pubkey == p2tr_script_buf(key + G*offset)`, rejecting otherwise; or (b) have `read` return an unverified type that must be confirmed via `Scanner::scan_transaction`-equivalent logic before entering the scheduler. Additionally, remove the self-referential `Output::key()` derivation or gate it behind a `verified` flag set only by the scan path.

### Proof of Concept
```rust
// Attacker-controlled bytes handed to the deserialize path
// (e.g. via Output::read on relayed/stored data).
use bitcoin::{ScriptBuf, TxOut, OutPoint, Amount, Txid};
use ciphersuite::Ciphersuite;
use kp256::Secp256k1;

// Victim multisig group key, e.g. from the processor's registered key.
let group_key = Secp256k1::generator() * Scalar::random(&mut OsRng);

// Attacker picks an offset and a script paying *themselves*
// (any valid P2TR script NOT equal to p2tr(group_key + G*offset)).
let attacker_key = ProjectivePoint::random(&mut OsRng);
let fake_script = p2tr_script_buf(attacker_key).unwrap();

// A real on-chain outpoint paying fake_script (attacker's own UTXO),
// or any outpoint the victim will be told is theirs.
let forged = ReceivedOutput {
    offset: Scalar::ZERO,
    output: TxOut { value: Amount::from_sat(1_000_000), script_pubkey: fake_script },
    outpoint: OutPoint { txid: attacker_txid, vout: 0 },
};

// Serialization round-trips cleanly:
let bytes = forged.serialize();
let parsed = ReceivedOutput::read::<&[u8]>(&mut bytes.as_ref()).unwrap();

// Output::key() derives group_key-looking result from the forged fields:
//   read_G(attacker_key) - G*0  == attacker_key
// Nothing rejects this; balance() reports 1_000_000 sats as received.
// SignableTransaction will then plan a spend of attacker_txid:0,
// which is either unspendable by the multisig or spends the attacker's coin.
```
