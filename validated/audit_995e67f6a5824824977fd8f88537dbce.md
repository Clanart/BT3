Based on the investigation, the strongest and most concrete analog to the Nextcloud "narrow permission grant silently escalated via an object the attacker controls" bug class is the `allowFileProtocol` override in GitHub Desktop's submodule-update path, which deliberately re-enables `protocol.file.allow=always` — the exact Git setting that was locked down upstream (Git 2.38.1, CVE-2022-39253) specifically to stop malicious repositories from using `.gitmodules` `file://` submodule URLs to read/exfiltrate arbitrary host paths into the working tree.

I was not able to fully trace, within the remaining tool budget, every call site that passes `allowFileProtocol=true` into `checkoutBranch`/`checkoutCommit`, so I cannot confirm with certainty whether Desktop gates that flag on a trust boundary (e.g., only first-party/local-clone submodules) or whether it is reachable from a plain "check out branch from a cloned/fetched repository" flow. That is a genuine gap in my analysis — flagging it explicitly rather than guessing.

### Title
Submodule `protocol.file.allow=always` override re-enables file:// submodule exfiltration blocked by upstream Git (CVE-2022-39253) - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` conditionally injects `-c protocol.file.allow=always` into `git submodule update --init --recursive` when its `allowFileProtocol` parameter is `true`. [1](#0-0) 
This flag is threaded through `checkoutBranch` and `checkoutCommit`, both of which forward it straight into `updateSubmodulesAfterOperation` without any inspection of the submodule URLs that a checked-out commit's `.gitmodules` might contain. [2](#0-1) 

### Finding Description
Upstream Git hardened `git submodule update`/`clone --recursive` (CVE-2022-39253) by defaulting `protocol.file.allow` to `user`, which blocks recursive submodule operations from following `file://` URLs embedded in a repository's `.gitmodules`. That file is attacker-controlled content: it ships inside a cloned/fetched repository or a checked-out branch/commit, exactly like the Nextcloud report's "attacker controls the object that expresses trust" scenario — there the object was a link-share permission set; here it is `.gitmodules`.

Desktop's `updateSubmodulesAfterOperation` explicitly reverses that protection by passing `-c protocol.file.allow=always` whenever it is invoked with `allowFileProtocol: true`. Once that override is active, a submodule entry such as:
```
[submodule "x"]
  path = x
  url = file:///home/victim/.ssh
```
will be honored by `git submodule update --init --recursive`, causing Git to "clone" from an arbitrary local filesystem path (or a symlink target reachable via `file://`) into the working tree of the checked-out repository. The narrow "you may read/checkout this repository" permission is escalated into "read this repository AND read arbitrary paths on the checking-out user's disk," which then land inside tracked working-tree content the user may `git add`/commit/push — mirroring the Nextcloud bug's "read-only grant silently becomes write/exfiltration."

The `clone()` path itself does not add this override — a fresh `git clone --recursive` runs under Git's own default protections [3](#0-2) 
which is good, but the same protection is deliberately bypassed later in `checkoutBranch`/`checkoutCommit` whenever `allowFileProtocol` is `true`. [4](#0-3) 

### Impact Explanation
If the `allowFileProtocol=true` branch is reachable from a checkout of a branch/commit that originated in an untrusted, attacker-supplied repository (e.g., "Open PR from Desktop" or "open repository from URL" flows that clone/fetch and then check out a remote-supplied ref), an attacker who controls that repository's `.gitmodules` can cause Desktop to copy the contents of sensitive local paths (SSH keys, config files, arbitrary user files reachable via `file://` or symlink) into the victim's working tree. This satisfies the "file read outside the repo" and "silent corruption of what the user commits/pushes" impact categories called out as valid.

### Likelihood Explanation
This requires no local/physical access, no admin rights, and no pre-existing malware — only that the victim clone/fetch and check out a branch or PR from a repository the attacker controls, which is a normal, expected Desktop workflow. The only uncertainty is whether Desktop's call sites actually set `allowFileProtocol=true` for untrusted/remote-originated checkouts versus only for repositories the user has explicitly marked trusted (e.g., via the `safe.directory`/"unsafe repository" flow seen in `getRepositoryType`/`addSafeDirectory`). I could not verify the exact call sites that pass `true` within the available search budget, so likelihood cannot be confirmed as high without that additional evidence — this should be checked directly in the codebase (search all callers of `checkoutBranch(`, `checkoutCommit(`, and `updateSubmodulesAfterOperation(` for the boolean argument's provenance).

### Recommendation
Audit every caller of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is only ever `true` for repositories the user has explicitly and knowingly trusted (not merely "successfully cloned/fetched"), and in all other cases leave Git's default `protocol.file.allow=user` restriction intact so `file://` submodule URLs from untrusted content are rejected.

### Proof of Concept
1. Attacker publishes a public repository/branch/PR containing a `.gitmodules` entry with `url = file:///home/victim/.ssh` (or a Windows UNC/`file://` path to a sensitive directory).
2. Victim uses Desktop to open/clone that repository and check out the malicious branch or PR via a flow that invokes `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true`.
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, pulling the contents of `/home/victim/.ssh` into the submodule path inside the repo's working tree.
4. The victim, unaware, stages and commits/pushes, exfiltrating the sensitive files to the (attacker-visible) remote — an unprompted write/read outside the intended repository boundary, directly analogous to the Nextcloud report's silent escalation from a narrow, explicit grant.

export async function checkoutBranch(

  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  return true
