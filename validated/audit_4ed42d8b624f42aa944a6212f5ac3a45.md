### Title
`redelegateWithAuthorization` withdraws destination-validator rewards on behalf of the delegator without going through the granted `StakeAuthorization` check - (File: precompiles/staking/staking.go)

### Summary
`redelegateWithAuthorization` lets a grantee redelegate tokens "on behalf of" a delegator using a limited `StakeAuthorization` grant (validator allow-list + `maxTokens` budget) [1](#0-0) . Before the actual `MsgBeginRedelegate` is routed through `authzMsgServer.Exec` (which enforces the authorization's validator list and `maxTokens` budget), the precompile unconditionally calls `p.distributionKeeper.WithdrawDelegationRewards(ctx, delegator, dstValAddr)` directly against the keeper, completely outside of the authz/allowance check [2](#0-1) .

### Finding Description
`redelegateFor` (shared by `redelegate` and `redelegateWithAuthorization`) performs an unconditional pre-step: `p.distributionKeeper.WithdrawDelegationRewards(ctx, delegator, dstValAddr)` is invoked directly on the `distributionKeeper`, not through `execute(msg)`/`authorizedStakingExecutor` [2](#0-1) . Only afterwards is the actual `MsgBeginRedelegate` value-bearing message routed through the authorization-checked executor: `authorizedStakingExecutor` wraps `pcommon.ExecuteAuthorization`, which enforces `StakeAuthorization`'s validator allow-list and `maxTokens` accounting via the native authz `MsgExec` [3](#0-2) [4](#0-3) .

This mirrors the reported bug class exactly: the function validates/consumes the grantee's allowance for one value (the redelegated `amount`, checked against `maxTokens`) but performs a second, materially significant state-mutating action (`WithdrawDelegationRewards` against the destination validator) that is never checked against any authorization at all — it is called as a bare keeper method with no grant lookup, no message-type check, and no budget consumption.

### Impact Explanation
Unlike a typical "grantee steals funds" bug, the reward destination is the delegator's own configured withdraw address [5](#0-4) , so this specific call does not by itself redirect funds to the attacker. However, it demonstrates the exact analog root cause required by the report: a grantee holding *any* narrow `StakeAuthorization` (e.g., limited to one specific validator pair and a small `maxTokens`) can force `WithdrawDelegationRewards` to fire for *any* destination validator argument they choose, entirely bypassing the authorization's validator allow-list and `maxTokens` scope, because that particular state mutation is never routed through the checked `execute()` path. This resets the delegator's reward "starting info" for that validator (as the code comment itself states) as an unauthorized side effect triggered by presenting an authorization that was never scoped to include that validator or that action. Because this can alter delegator-controlled accounting state (reward starting info) for an arbitrary validator chosen by the grantee, outside the bounds of what the granter explicitly authorized, it is a real allowance-bypass/authorization-scope violation reachable by any grantee holding an unrelated staking grant on the token — matching the reported bug's root cause (checking allowance for one parameter while leaving a second, materially state-changing operation unchecked).

### Likelihood Explanation
Reachable by any account that holds *some* `StakeAuthorization` grant from a delegator (a normal, expected precompile usage pattern via `grantStakingAuthorization`) and simply calls `redelegateWithAuthorization` with an arbitrary `dstAddress` of their choosing, regardless of whether that validator or reward-withdrawal action was ever included in the grant. No special privileges beyond holding any staking authorization are required, and the call is a standard EVM transaction through the public precompile ABI [6](#0-5) .

### Recommendation
Route the destination-validator reward pre-withdrawal through the same `execute` callback used for the `MsgBeginRedelegate`, so it is subject to the same authorization/allow-list/`maxTokens` checks as the redelegation itself (e.g., wrap it as a `MsgWithdrawDelegatorReward` passed through `execute(...)` before issuing the redelegate message), rather than calling `p.distributionKeeper.WithdrawDelegationRewards` directly and unconditionally.

### Proof of Concept
Conceptual reproduction (cannot be executed without a live devnet, but the code path is directly verifiable by static inspection):
1. Delegator `A` grants grantee `B` a `StakeAuthorization` restricted to `allowedValidators = [V1]` and `maxTokens` covering only validator `V1`, via `grantStakingAuthorization` [7](#0-6) .
2. `A` has an existing delegation (and pending rewards) to an unrelated validator `V2` that was never included in the grant.
3. `B` calls `redelegateWithAuthorization(A, V1, V2, smallAmount)` — passing `V2` as `dstAddress`.
4. Before the authorization-checked `MsgBeginRedelegate` executes (and regardless of whether it ultimately succeeds/fails against the `V1`-only allow-list), `redelegateFor` has already called `p.distributionKeeper.WithdrawDelegationRewards(ctx, delegator, V2)` directly [8](#0-7) , mutating `A`'s reward starting info for `V2` — an action never covered by the grant.

	// WithdrawDelegationRewards reinitializes the delegation's starting info, so the

func ExecuteAuthorization(ctx sdk.Context, msgServer utils.AuthzMsgServer, grantee sdk.AccAddress, msg sdk.Msg) (*authztypes.MsgExecResponse, error) {
	if err := msg.ValidateBasic(); err != nil {
		return nil, err
	}
	exec := authztypes.NewMsgExec(grantee, []sdk.Msg{msg})
	if err := exec.ValidateBasic(); err != nil {
		return nil, err
	}
	return msgServer.Exec(sdk.WrapSDKContext(ctx), &exec)
}
