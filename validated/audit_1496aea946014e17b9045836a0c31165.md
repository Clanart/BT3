### Title
Panic (denial of service) via out-of-range participant index in PedPoP blame evaluation - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The bug class from the external report is a NULL-dereference denial of service: attacker-controlled input reaches a code path that dereferences/indexes data which does not exist, crashing the process. The analog in Serai is an unchecked `HashMap` index (`self.commitments[&sender]` / `self.commitments[&l]`) in the PedPoP blame-evaluation path, which panics when the accused `sender` participant index is not a member of the DKG set. A participant index is a `u16` in `Participant` and is only constrained to be non-zero (`Participant::new`, crypto/dkg/src/lib.rs:29-35); `blame`/`blame_internal` never bounds it against `n`.

### Finding Description
`BlameMachine::blame_internal` computes `share_verification_statements::<C>(recipient, &self.commitments[&sender], ...)` at crypto/dkg/pedpop/src/lib.rs:596-601. `self.commitments` is built only for `Participant` values `1 ..= n` — either by `KeyMachine::calculate_share` (which populates `commitments` for `self.params.all_participant_indexes()`, pedpop/src/lib.rs:512-521) or by `AdditionalBlameMachine::new` (pedpop/src/lib.rs:656-660). Neither `BlameMachine::blame` (lines 623-632) nor `AdditionalBlameMachine::blame` (lines 674-682) validates that `sender` (or `recipient`, used as the interpolation index) lies within `1 ..= n`.

`AdditionalBlameMachine` is explicitly intended for arbitrary third parties evaluating blame over commitment messages (`AdditionalBlameMachine::new`, lines 640-661), so `sender`/`recipient` are attacker-influenced values accompanying a blame claim and an `EncryptedMessage`. Passing `sender = Participant(n + 1)` (or any index > n, up to 65535) makes `self.commitments[&sender]` panic, crashing the caller — exactly the DoS shape of CVE-2021-35306. There is no `get`/`Option` handling; `HashMap`'s `Index` impl panics on a missing key.

Related unchecked-index sites reachable from the same data: `KeyMachine::calculate_share` indexes `self.commitments[&l]` at line 490, though there `validate_map` (lines 57-83) constrains `l` to `1 ..= n`, so it is safe; the blame path lacks this guard.

### Impact Explanation
A panic inside a Serai processor/validator evaluating a blame statement crashes the task/process (the codebase's own panic hook exits the process on task panics, as in networks/ethereum/relayer/src/main.rs:11-19). An attacker can abort DKG blame adjudication — and thereby the key-generation session — at will by submitting a blame request naming a non-existent participant index. This is a denial of service reachable purely through attacker-supplied values (`sender`, `recipient`, and the `EncryptedMessage`/`EncryptionKeyProof` bytes), matching the CVE's availability-only impact.

### Likelihood Explanation
Blame evaluation is a normal protocol path invoked when any participant claims a fault, so the code is reached during ordinary (adversarial) DKG operation. The malicious input is a single out-of-range `u16` participant index; `Participant::new` accepts any non-zero `u16` and `blame` performs no bounds check, so triggering the panic is trivial. The only mitigating factor is that the caller must route attacker-controlled indices into `blame` — but the API exists precisely to arbitrate claims between untrusted DKG parties, and `AdditionalBlameMachine::new` even documents that invalid inputs "may cause ... panics" (line 648) while placing the burden on callers, meaning any integrator that forwards peer-supplied indices is vulnerable.

### Recommendation
Validate `sender` and `recipient` in `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `blame_internal`: return the accusing party as faulty (or a dedicated error) when `u16::from(sender) > n` / `u16::from(recipient) > n`, or when `!self.commitments.contains_key(&sender)`. Replace `self.commitments[&sender]` with `.get(&sender)` and handle `None` gracefully rather than panicking.

### Proof of Concept
```rust
// Construct an AdditionalBlameMachine over a valid set of commitment
// messages for n participants, then submit a blame claim naming a
// participant index which does not exist.
let mut machine = AdditionalBlameMachine::<Ed25519>::new(context, n, commitment_msgs).unwrap();
let invalid_sender = Participant::new(n + 1).unwrap(); // non-zero, but > n
// Panics inside blame_internal at `self.commitments[&sender]`:
machine.blame(invalid_sender, Participant::new(1).unwrap(), msg, None);
```
The same panic occurs through `BlameMachine::blame` (which delegates to `blame_internal`, crypto/dkg/pedpop/src/lib.rs:575-632) whenever the `sender` index exceeds `n`.
