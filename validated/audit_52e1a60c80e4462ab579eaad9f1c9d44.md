### Title
Missing `nonReentrant` guard in `ManualCompound.compound()` combined with shared `balanceOf(address(this))` accounting allows reentrancy via attacker-controlled non-compoundable reward token, corrupting which `msg.sender` a harvested reward balance is credited to - ([File: rewards/ManualCompound.sol])

### Summary
`ManualCompound.compound()` has no `nonReentrant` modifier, and the "send back non-compoundable rewards" loop calls `IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance)` for **any attacker-supplied token address** that is not registered in `compoundableRewards` — this address is not validated to be an actual reward token of the claimed pools. Because this transfer happens before the loop that consumes real reward-token balances (MGP/mWOM) via `safeApprove` + `convertFor`/`lockFor`, an attacker can pre-fund the contract with a malicious ERC20 whose `transfer()` callback reenters `compound()`, causing the shared, balance-based accounting (`IERC20(_tokenAddress).balanceOf(address(this))`) to be read and consumed out of order relative to the outer call. [1](#0-0) 

### Finding Description
`compound()` is `external` with no reentrancy protection and no restriction on who can call it or what token addresses can be passed in `_rewards`: [2](#0-1) 

The first loop checks `!compoundableRewards[_rewards[i][j]]` — `compoundableRewards` is only populated by the owner via `addReward` — but `_rewards[i][j]` itself is an arbitrary, caller-supplied address, not validated against the real reward tokens actually claimed by `multiclaimOnBehalf` for the given `_lps`. If that address happens to hold a balance at `address(this)` (which the attacker can arrange simply by transferring their own malicious token to the `ManualCompound` contract beforehand), `safeTransfer(msg.sender, rewardBalance)` executes the malicious token's `transfer()` logic, which the attacker fully controls and can use to reenter `compound()` before the outer call proceeds to its second loop: [3](#0-2) 

The second loop reads `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))` for the real compoundable tokens (e.g. MGP) and then `safeApprove`s and calls `convertFor`/`lockFor` using `msg.sender` of whichever call is currently executing. Because there is no accounting of "how much was actually harvested by this specific call" (only a raw `balanceOf` snapshot) and no `nonReentrant` guard, a reentrant inner call can drain/process the shared balance before the outer call reaches this loop, or vice versa. Note that in a pure single-attacker reentrancy the inner call's `msg.sender` is the malicious token contract (since it is the token's code making the external call back into `compound()`), not the original EOA — so a simple self-reentry redirects funds to an attacker-controlled contract, which is still attacker-owned value, not by itself a cross-user theft. The scoped "theft of another user's funds" only materializes if the `ManualCompound` contract is holding another party's already-harvested-but-unswept balance at the moment of attack (e.g., overlapping/concurrent `compound()` calls in the same block, dust left from partial conversions, or a stuck balance from a prior call) — a condition-dependent but plausible scenario given the contract's shared, non-isolated balance-based bookkeeping. [4](#0-3) 
`multiclaimOnBehalf` and the internal `_multiClaim` do carry a `nonReentrant` modifier, but that guard only protects the `MasterMagpie` claim call itself, which fully completes and returns before `ManualCompound.compound()`'s subsequent sweep-back loop executes — so it does not protect the vulnerable section in `ManualCompound.compound()`. [5](#0-4) 

### Impact Explanation
The concrete, unconditionally reachable impact is reentrancy-driven corruption of the compounding flow: balances intended for one `compound()` invocation's `msg.sender` can be processed/locked/converted under a different call context due to the shared `balanceOf(address(this))` snapshot and lack of reentrancy protection. This matches "theft or permanent freezing of unclaimed yield" when the contract holds overlapping unswept balances from separate compounding operations at the time of the reentrant call.

### Likelihood Explanation
Preconditions: the attacker needs to (1) deploy a malicious ERC20 with a `transfer()` hook that reenters `compound()`, (2) pre-fund the `ManualCompound` contract with that token (a normal token transfer, requires no privilege), and (3) call `compound()` referencing that token address in `_rewards`. This requires no privileged role and only ordinary EOA capability plus deploying a contract, making it feasible and repeatable. However, turning this into a cross-user theft (rather than self-redirection) additionally depends on another user's harvested balance being present/unswept in the shared contract balance at that exact moment, which is a timing-dependent, opportunistic condition rather than guaranteed on every call.

### Recommendation
Add a `nonReentrant` modifier (OpenZeppelin `ReentrancyGuard`) to `compound()`. Additionally, do not rely on raw `balanceOf(address(this))` snapshots for accounting; instead measure the delta received specifically from `multiclaimOnBehalf` for the current call (e.g., record balance before/after the claim call only, or have `multiclaimOnBehalf`/rewarders return exact claimed amounts), and validate that `_rewards[i][j]` in the sweep-back loop corresponds to tokens actually returned by the claim for that specific call, not arbitrary caller-supplied addresses.

### Proof of Concept
Foundry test plan:
1. Deploy `ManualCompound`, `MasterMagpie` (or mocks), and register a `MaliciousToken` (attacker-controlled ERC20) that on `transfer()` calls back into `ManualCompound.compound()` with a second set of parameters.
2. Attacker transfers some `MaliciousToken` balance directly to the `ManualCompound` contract address.
3. Attacker calls `compound(lps, rewards, ratio, minRec, true)` where `rewards[i]` includes the `MaliciousToken` address (not registered via `addReward`, so `compoundableRewards[MaliciousToken] == false`).
4. Assert that during the `safeTransfer` sweep-back at line 134, the malicious token's callback triggers a nested call to `compound()` before the outer call's second loop executes.
5. Assert that `ILocker.lockFor` or `IConverter.convertFor` is invoked with a `receivedBalance` reflecting a state that differs from what the outer call alone would have harvested (e.g., combined/reduced balance) and that the credited `msg.sender` in the nested call differs from the original transaction sender (`tx.origin`), demonstrating out-of-order/cross-context balance consumption.
6. Repeat with a second legitimate user's harvested balance intentionally left in the contract (simulate via direct token transfer to `ManualCompound`) to show that balance can be swept into the attacker-triggered nested call's `lockFor`/`convertFor`, quantifying the diverted amount.

    function compound(address[] calldata _lps, address[][] calldata _rewards, uint256 _convertRatio, uint256 _minRec, bool _lockMgp) external {
        uint256 rewardTokensLength = rewards.length;        
        IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
        // send none compoundable reward back to caller
        for(uint256 i; i < _lps.length; i++) {
            uint256 rewardLength = _rewards[i].length;
            if (rewardLength > 0) {
                for (uint j; j < rewardLength; j++) {
                    if (!compoundableRewards[_rewards[i][j]]) {
                        uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
                        if (rewardBalance > 0)
                            IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
                    }
                }
            }
        }
        for (uint256 i; i< rewardTokensLength; i++) {
            address _tokenAddress = rewards[i].tokenAddress;
            address _helperAddress = rewards[i].tokenHelper;
            address _convertor = rewards[i].convertor;
            address _locker = rewards[i].locker;
            uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));

            if (receivedBalance > 0) {
                if (_convertor != address(0)) {
                    IERC20(_tokenAddress).safeApprove(_convertor, receivedBalance);
                    IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2);
                } else if (_locker != address(0) && _lockMgp) {
                    IERC20(_tokenAddress).safeApprove(_locker, receivedBalance);
                    ILocker(_locker).lockFor(receivedBalance, msg.sender);                        
                } else if (_helperAddress != address(0)) { 
                    IERC20(_tokenAddress).safeApprove(_helperAddress, receivedBalance);
                    ISimpleHelper(_helperAddress).depositFor(receivedBalance, msg.sender);
                } else {
                    IERC20(_tokenAddress).safeTransfer(msg.sender, receivedBalance);
                }
            }
        }

        emit Compounded(msg.sender, rewardTokensLength, _lockMgp);
    }
