## Title
Unbounded `getProgramAccounts` full scan when program-id is not in secondary account index causes single-request memory/CPU exhaustion - ([File: rpc/src/rpc.rs])

## Summary
`JsonRpcRequestProcessor::get_filtered_program_accounts` only applies the `scan_results_limit_bytes` byte cap when the `ProgramId` secondary account index is enabled and covers the queried key; otherwise it falls back to `bank.get_filtered_program_accounts` → `Accounts::load_by_program_with_filter`, which runs `AccountsDb::scan_accounts` with `ScanConfig::default()` and no abort/size mechanism. Since `--account-index program-id` is off by default, a single unauthenticated `getProgramAccounts` call against a program with many owned accounts (e.g. SPL Token) forces the node to materialize every matching account into an unbounded in-memory `Vec`.

## Finding Description
In `rpc/src/rpc.rs`, `get_filtered_program_accounts` branches on `self.config.account_indexes.contains(&AccountIndex::ProgramId)` [1](#0-0) . When indexed, it uses `get_filtered_indexed_accounts`, which forwards `self.config.scan_results_limit_bytes` into `Accounts::load_by_index_key_with_filter` [2](#0-1) . That function tracks accumulated result size via `accumulate_and_check_scan_result_size` and aborts the scan via `config.abort()`/`maybe_abort_scan` once the byte budget is exceeded [3](#0-2) .

When the program-id is NOT indexed — the default configuration unless an operator explicitly passes `--account-index program-id` (confirmed in `validator/src/commands/run/args/account_secondary_indexes.rs`, where `account_indexes` is empty unless explicitly supplied via CLI) [4](#0-3)  — the RPC layer takes the `else` branch, explicitly commenting "this path does not need to provide a mb limit because we only want to support secondary indexes," and calls `bank.get_filtered_program_accounts` with no size bound [5](#0-4) . That delegates to `Accounts::load_by_program_with_filter`, which calls `AccountsDb::scan_accounts` with a plain `ScanConfig::default()` (no abort flag ever set) and unconditionally pushes every matching account into an in-memory `Vec` via `load_while_filtering` [6](#0-5) . `load_by_program` (unfiltered) shares the identical unbounded pattern [7](#0-6) .

`AccountsDb::scan_accounts` walks the full accounts cache and accounts index/ancestors for every root and cached pubkey, and calls the given `scan_func` for every matching account, materializing full `AccountSharedData` (including account data bytes) with no early exit for size [8](#0-7) . Because the byte-limit machinery (`accumulate_and_check_scan_result_size`, `maybe_abort_scan`) is only wired into `load_by_index_key_with_filter`, and not into `load_by_program_with_filter`/`load_by_program`, there is no existing guard on the non-indexed path.

This runs inside `self.runtime.spawn_blocking(...)` [9](#0-8) , so it doesn't block the async I/O reactor, but it still occupies a blocking-thread-pool worker for the full scan duration and allocates memory proportional to the total size of every account owned by `program_id`.

## Impact Explanation
A single unauthenticated RPC client can send one `getProgramAccounts` request naming a widely-used program (e.g. SPL Token, which owns tens of millions of accounts on mainnet) and force the node to allocate memory proportional to the full set of that program's accounts, with no configurable or hardcoded byte limit on this path. Repeated/concurrent requests can exhaust node memory or saturate the shared blocking-thread pool used by many other RPC calls, degrading or crashing RPC service — matching the allowed "single-client low-rate RPC crash/degradation" / "non-RPC remote exhaustion" impact class. No stake, authentication, or special network position is required.

## Likelihood Explanation
Likelihood is high on any RPC node running `--full-rpc-api` without `--account-index program-id` enabled, which is the default configuration and a common real-world deployment (building/maintaining secondary indexes is itself resource-intensive, so many public RPC providers avoid enabling them). The exploit requires only a single ordinary, publicly reachable JSON-RPC POST request.

## Recommendation
Extend the same byte-budget/abort mechanism used in `Accounts::load_by_index_key_with_filter` (i.e., `accumulate_and_check_scan_result_size` + `ScanConfig::default().recreate_with_abort()` + `maybe_abort_scan`) to `Accounts::load_by_program_with_filter` / `load_by_program`, threading `scan_results_limit_bytes` through `bank.get_filtered_program_accounts` and the non-indexed branch of `get_filtered_program_accounts` in `rpc/src/rpc.rs`. Consider also enforcing a conservative default byte/time budget regardless of secondary-index configuration, and/or per-IP request throttling for RPC methods known to trigger full-database scans.

## Proof of Concept
1. Run a validator/RPC node with `--full-rpc-api` and without `--account-index program-id` (default).
2. Send: `{"jsonrpc":"2.0","id":1,"method":"getProgramAccounts","params":["TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA"]}` against a cluster where this program owns a very large number of accounts.
3. Observe execution takes the unindexed branch (`rpc/src/rpc.rs:2283-2307`) and `Accounts::load_by_program_with_filter` (`accounts-db/src/accounts.rs:338-358`) collects every matching account into memory with no size check, causing large memory allocation and prolonged blocking-thread occupation from the single request. This can be reproduced as a Rust integration test by populating `AccountsDb`/`Bank` with a large number of accounts owned by a test program id (no secondary index configured) and calling `bank.get_filtered_program_accounts` directly, observing unbounded `Vec` growth with no `ScanError::Aborted` regardless of size.
