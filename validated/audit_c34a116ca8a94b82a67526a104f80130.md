## Title
Partial-commit line selection is applied against a **stale diff snapshot**, allowing a changed working file to silently corrupt which lines get committed — (`File: app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user stage only some lines of a modified file. The user's selection is recorded as a set of **line indices** (`DiffSelection`) computed against the diff that was rendered in the UI. When the commit is actually created, `applyPatchToIndex` does **not** reuse that same diff — it independently re-runs `git diff` against the current on-disk file and then reinterprets the old, position-based selection against this brand-new diff. This is structurally the same bug class as the Zaros report: a value (mark price / diff-hunk-line-mapping) computed at one point in time is silently reused later on as if it still reflected current state, without recomputing it against the state that is actually acted upon.

### Finding Description
The staging flow is:

1. UI renders a diff and the user selects specific lines. This selection is stored purely as a `Set<number>` of line indices inside `DiffSelection` (`app/src/models/diff/diff-selection.ts:82-136`) — `isSelected(lineIndex)` only checks whether the *index* is a member of the diverging set, with no notion of the underlying line content. [1](#0-0) 

2. When the commit is created, `stageFiles` → `applyPatchToIndex` is invoked for any file with a partial selection. [2](#0-1) 

3. Crucially, `applyPatchToIndex` fetches a **fresh** diff straight from the working directory (`getWorkingDirectoryDiff`) right before formatting the patch, rather than reusing the diff the selection was created against: [3](#0-2) 

4. `formatPatch` then walks this **new** diff's hunks and, for every line, asks `file.selection.isSelected(absoluteIndex)` — using indices computed from the *old* diff — to decide whether to include it in the patch that gets `git apply --cached`'d into the index: [4](#0-3) 

There is no verification that the hunk layout, line count, or line content at a given index in the "new" diff is the same as in the diff the user actually reviewed and clicked checkboxes against. `withSelectableLines` in the app store only reconciles the selection against a re-fetched diff when the user is actively looking at the Changes view and a background diff refresh happens (`app-store.ts:3478-3497`), but this reconciliation is not part of the commit path itself — `applyPatchToIndex` performs its own independent diff fetch with no equivalent reconciliation. [5](#0-4) 

### Impact Explanation
If the tracked file's content on disk changes between the moment the user reviews/selects lines in the Changes view and the moment `Commit` is clicked (e.g., a build tool, file watcher, editor autosave, a Git smudge/clean filter, or a malicious script bundled in the cloned repository that touches files on `checkout`/`post-merge` hooks), the hunk boundaries and line offsets in the diff shift. Because the stored selection is keyed purely on line index rather than content, `formatPatch` will silently:
- Include unselected lines the user never intended to commit, or
- Exclude lines the user did intend to commit, or
- Apply the "keep as context" / "drop line" logic (lines 171-201 of `patch-formatter.ts`) to the wrong lines entirely, producing a patch whose semantics no longer match anything the user reviewed.

This is a silent corruption of what the user commits (and subsequently pushes), matching the "silent corruption of what the user commits or pushes" impact category. Because commits are then pushed to GitHub, unreviewed/unintended content (including content the user explicitly chose to exclude, e.g., secrets or debug code) can end up in the pushed history without any error or warning shown to the user.

### Likelihood Explanation
This requires a source of concurrent file modification between diff-render time and commit time that is plausible in real workflows: file watchers/build tools regenerating files, IDE auto-formatters, git attribute filters (`clean`/`smudge`), or repository-provided pre-commit/post-checkout hooks acting on a maliciously crafted repository the victim cloned. No admin rights, local access, or leaked credentials are required — the attacker only needs to control repository content/hooks/build tooling that runs in the user's normal workflow while they have a partial-commit selection pending. It is a race-condition-class bug so likelihood depends on timing, but the window (time between rendering the diff and clicking Commit) is often long enough in real usage.

### Recommendation
`applyPatchToIndex` (and `stageFiles`/`createCommit`) should not silently re-fetch a new diff and reinterpret a stale, position-based selection against it. Instead:
- Reuse the exact diff object the selection was validated against when building the patch, or
- Recompute/validate the selection against the freshly fetched diff (as is partially done in `updateChangesWorkingDirectoryDiff`) and fail/warn the user if the file has changed since the selection was made, rather than silently applying a potentially mismatched line-index selection.
- Consider hashing or content-anchoring selected line text (not just positional index) so a shifted diff can be detected instead of blindly trusted.

### Proof of Concept
1. Modify a tracked file, e.g. add 10 lines near the top.
2. Open the Changes view in GitHub Desktop; a diff is rendered and the user selects (checks) only a later, unrelated hunk to include in the commit — this selection is stored as `DiffSelection` line indices from `app/src/lib/stores/app-store.ts:3444-3497`.
3. Before committing, have an external process (simulating a build tool/hook/malicious repo script) append/insert additional lines at the top of the same file, shifting all hunk offsets.
4. Click Commit. `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) calls `getWorkingDirectoryDiff` again, obtaining a diff with shifted hunk boundaries.
5. `formatPatch` (`app/src/lib/patch-formatter.ts:143-171`) applies the old selection's indices to this new diff — because indices no longer align with the same lines, the resulting patch includes/excludes different lines than what the user selected, and `git apply --cached` stages content the user never reviewed.

      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
