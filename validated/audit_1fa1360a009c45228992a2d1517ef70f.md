Confirmed: pool state for the Uniswap V4 venue is read via `getSlot0` (instantaneous spot price), not a TWAP/observe-based oracle. Combined with the disabled overfill clamp in `calculateProfitability`, this produces a concrete, exploitable path.

### Title
Disabled overfill clamp lets an attacker drain Simplex filler funds via spot-price manipulation of the Uniswap V4 pricing venue - (File: sdk/packages/simplex/src/strategies/fx.ts)

### Summary
`FXFiller.calculateProfitability` in `sdk/packages/simplex/src/strategies/fx.ts` computes each leg's `policyMaxOutput` from `resolveLegRates`, which for venue-priced pairs pulls the price from `UniswapV4LiquidityState`, which in turn reads the pool's instantaneous `getSlot0()` price (spot price, no TWAP) via `UNISWAP_V4_STATE_VIEW_ABI` [1](#0-0) . The code that used to bound the resulting output to `(1 + maxOverfillBps) × user-requested amount` has been intentionally neutered: the ceiling is still computed, but only used to emit a warning log, and the filler pays out the full, unclamped `policyMaxOutput` regardless of how far it exceeds the safe ceiling [2](#0-1) .

### Finding Description
The historical safety design (documented in `docs/content/developers/evm/intent-gateway/simplex.mdx`) was that "the filler clamps its computed output to at most `(1 + maxOverfillBps) × user-requested amount`" specifically to bound "per-leg loss if the filler's internal pricing is wrong (bug, stale cache, manipulated venue)" [3](#0-2) . That protection is now dead code in practice: `overfillCeiling` is computed but `finalOutputAmount` is derived only from `policyMaxOutput`/`walletContribution`/`credited`, with no clamping against `overfillCeiling` anywhere in the leg loop [4](#0-3) . The in-code comment explicitly states: "the clamp is DISABLED, so the filler fills the full computed amount even when it exceeds (1 + maxOverfillBps) × user-requested — including venue-priced legs (e.g. Uniswap V4). NOTE: this removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price."

Since the venue price source is `getSlot0` — an instantaneous AMM price with no staleness/TWAP protection — an attacker can:
1. Flash-loan/trade against the specific Uniswap V4 pool the filler is configured to price from, moving the spot price so that `token1`/`token0` valuation is skewed in the attacker's favor.
2. Simultaneously (or immediately after) submit an IntentGatewayV2 order whose output leg is priced against that manipulated pool.
3. The filler's `calculateProfitability`/`executeOrder` path computes `policyMaxOutput` from the manipulated rate, which now legitimately exceeds the user-requested amount by more than `maxOverfillBps`, but since the clamp is disabled, the filler fills the order at the inflated (attacker-favorable) output amount instead of capping it.
4. The attacker reverts/unwinds their pool manipulation trade after the fill, pocketing the difference between what they should have received and the inflated amount actually paid by the filler's wallet/vault funds.

This is a genuine "loss of funds" / "logic attack" primitive: an unprivileged order-submitter (no malicious relayer, prover, or admin required) can force the filler to pay out more than the safe ceiling by manipulating a public, permissionless AMM pool that the filler's own pricing logic trusts without protection.

### Impact Explanation
The filler's on-chain wallet and any configured funding venues (vault treasury, Uniswap V4 LP positions) are drained proportional to the attacker's ability to move the venue pool's spot price and to the size of the order the filler is willing to fill. Because the loss-bound mechanism (`maxOverfillBps`) exists specifically to cap this kind of loss and is now disabled for all pairs, including venue-priced pairs, there is no other guard preventing an unbounded per-order loss up to the filler's available balance for that leg. This is fund loss directly attributable to logic in the repository, not to a compromised relayer or admin.

### Likelihood Explanation
Any user can submit an IntentGatewayV2 order; Uniswap V4 pools are permissionless and can be moved with a flash loan or large swap without needing any privileged access. The only precondition is that the filler operator has configured a venue-priced (Uniswap V4) pair, which the SDK explicitly supports and documents (`[vault.uniswapV4]` / HyperFX strategy) [5](#0-4) . The disabled clamp is unconditional (applies to every leg, not just misconfigured ones), so exploitability does not depend on rare conditions — only on attacker capital sufficient to move the target pool's spot price within a single block/transaction window before the filler fills.

### Recommendation
Re-enable the overfill clamp so `finalOutputAmount` (and the on-chain output the filler commits to) is capped at `overfillCeiling = output.amount * (1 + maxOverfillBps)`, exactly as documented, for all pricing sources including venue-priced (Uniswap V4) legs. If overfill beyond the ceiling is detected, either fill at the clamped amount or reject/skip the leg (as `computeLegPolicyOutput` already does for budget exhaustion) rather than only logging a warning. Additionally, switch the Uniswap V4 price source from instantaneous `getSlot0()` to a TWAP/`observe()`-based price, or add explicit staleness/deviation checks against a secondary oracle before using venue pricing for fill sizing.

### Proof of Concept
1. Configure a Simplex filler with a `[[pairs]]` entry priced via a Uniswap V4 pool (`priceSource: venue`), per `docs/content/developers/evm/intent-gateway/simplex.mdx`.
2. Attacker takes a large flash-loan swap against that pool to shift `sqrtPriceX96` such that the pool's implied `token1/token0` rate becomes favorable to a subsequent fill.
3. Attacker submits an IntentGatewayV2 order requesting `output.amount = X` on the corresponding leg.
4. `calculateProfitability` → `resolveLegRates` reads the manipulated `getSlot0()` price, computing `rawPolicyMaxOutput ≫ overfillCeiling` (i.e., `rawPolicyMaxOutput > X * (1 + maxOverfillBps)/10000`).
5. Because the clamp code only logs a warning (`sdk/packages/simplex/src/strategies/fx.ts:602-617`) and never reduces `policyMaxOutput`/`finalOutputAmount`, the filler fills the order at the inflated `rawPolicyMaxOutput`, transferring more value to the attacker's destination address than the safe ceiling permits.
6. Attacker reverses the pool-manipulating trade in the same or a following transaction, realizing profit equal to the excess amount paid by the filler.

Note: I was not able to fully trace `resolveLegRates`/`computeLegPolicyOutput`'s exact numeric derivation from the venue price in this pass (index truncation limited further reads); the exact multiplier/precision math should be verified directly in `sdk/packages/simplex/src/strategies/fx.ts` and `UniswapV4LiquidityState.ts` before remediation, but the core defect — disabled clamp plus unprotected spot-price venue source — is clearly evidenced in the cited lines.

### Overfill Protection

Bounds per-leg loss if the filler's internal pricing is wrong (bug, stale cache, manipulated venue). For every order, the filler clamps its computed output to at most `(1 + maxOverfillBps) × user-requested amount` — this ceiling applies to every strategy. After `maxConsecutiveClamps` consecutive orders where the clamp activated, the **HyperFX** strategy halts itself — a pattern that strongly suggests a systemic pricing error — and requires an operator restart. HyperFX additionally rejects any order where the total output USD value ≥ total input USD value.
