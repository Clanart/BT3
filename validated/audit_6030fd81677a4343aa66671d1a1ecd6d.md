## Title
Unbounded recursive parsing of on-chain memo data in `PuzzleWithRestrictions.from_memo()` allows a spend-triggered Python `RecursionError` denial of service in wallet/plotnft sync - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a custody/MofN puzzle tree from untrusted `Program` memo data taken from a coin's CLVM memo blob. Whenever the parsed puzzle hint indicates `MofN` ("further branching"), the function calls itself once per member, with no depth limit, directly mirroring the CWE-674 "unbounded recursion while parsing nested/recursive structures" bug class in the reported protobuf advisory (GHSA-8qvm-5x2c-j2w7 / CVE-2025-4565).

### Finding Description
`from_memo()` is a classmethod that recurses into itself for every `MofN` member found in the memo hint: [1](#0-0) 

```
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
    )
```

There is no bound on nesting depth, no maximum-recursion guard, and no bound on `len(m_of_n_hint.member_memos)` before recursing. Each `MofN` member is itself a `PuzzleWithRestrictions` memo which can again be `MofN`, so a memo blob can be crafted with arbitrarily deep `MofN` nesting (or an extremely wide + deep branching factor) to blow past CPython's default recursion limit (~1000 frames), raising `RecursionError`.

This is invoked from `chia/pools/plotnft_drivers.py` in `PlotNFTPuzzle.get_next_from_coin_spend()` when trying to recognize a singleton's next inner-puzzle state purely from the child coin's memo, i.e. it is exercised on data taken directly from a `CREATE_COIN` condition's memo, which is attacker-influenced content inside a spend: [2](#0-1) 

The project explicitly documents elsewhere (`chia/types/blockchain_format/tree_hash.py`, `.cursor/context/types.md`) that CLVM tree-walking code is deliberately made *iterative* specifically "to avoid Python recursion limits on deeply nested CLVM" — showing this is a known, previously mitigated risk class in this codebase, but `from_memo()` in the custody architecture does not follow that pattern and instead recurses per CLVM tree node/member. [3](#0-2) 

Contrast this with `chia/util/streamable.py`'s general parser, whose recursion is bounded by the fixed dataclass field schema (not by attacker-controlled input shape), and with the DataLayer merkle file loader, which has an explicit `chia_rs.datalayer.RecursionDepthExceededError` guard for deep untrusted trees: [4](#0-3) 

No equivalent depth guard exists for `PuzzleWithRestrictions.from_memo()`.

### Impact Explanation
A `RecursionError` raised deep inside `from_memo()` while a wallet is syncing/parsing a coin's memo (e.g., during plotnft/pool-wallet state recognition) can propagate up through wallet-sync code paths that are not universally prepared to catch it, since the codebase's existing exception handling around this call only catches `ValueError`: [5](#0-4) 

If `RecursionError` is not a subclass of a handled exception at every call site, an untrusted coin's memo can cause an unhandled exception during wallet sync of coins the wallet is trying to interpret, i.e. a "spend-triggered transaction-processing halt" for the affected wallet client. Because this is on the wallet-side sync/interpretation path (not consensus-critical block validation, and not gated by CLVM cost metering, since it is pure Python `Program.at()`/`as_iter()` recursion over memo data, not CLVM execution), it bypasses the mempool/consensus cost bounds described in `.cursor/context/clvm-execution.md`.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to get a coin with a crafted deep/wide `MofN` memo into a shape that the victim wallet's sync code attempts to interpret via `PuzzleWithRestrictions.from_memo()`/`PlotNFTPuzzle.get_next_from_coin_spend()`. This path is reached for singleton coins recognized as candidates for plotnft/pool-wallet tracking, which is a wallet-controlled, but externally-influenceable, code path (the coin creating the memo is part of a spend bundle that can be crafted by any spender). Exploitation does not require a leaked key, a malicious peer/node, or any privileged position — only a spend whose `CREATE_COIN` memo is shaped to trigger deep recursion.

### Recommendation
- Convert `PuzzleWithRestrictions.from_memo()` (and `MofN` construction it drives) to an iterative/explicit-stack algorithm, matching the pattern already used in `sha256_treehash()`.
- Alternatively/additionally, enforce an explicit maximum nesting depth and/or maximum member count before recursing, rejecting malformed/oversized memos with a `ValueError` rather than allowing unbounded Python-level recursion.
- Ensure all callers that parse untrusted memo data (e.g., `plotnft_drivers.py`) catch `RecursionError` alongside `ValueError`, or better, make the parser itself never raise `RecursionError` by imposing the depth cap above.

### Proof of Concept
Conceptually (cannot be fully validated without executing code in this environment):
1. Construct a `PuzzleWithRestrictions.memo()` Program where `puzzle` is `MofN` with `m=1`, and its single member is again a `PuzzleWithRestrictions` with an `MofN` puzzle, repeated to a nesting depth exceeding Python's recursion limit (e.g., 2000+ levels), matching the same recursive shape validated (at shallow depth) by the existing test: [6](#0-5) 

2. Place this crafted memo `Program` into the `memo_blob` of a `CREATE_COIN` condition for a coin whose parent is a singleton the target wallet is tracking (e.g., via `PlotNFTPuzzle.get_next_from_coin_spend()`'s memo-based recognition path at `chia/pools/plotnft_drivers.py:477-483`).
3. When the victim wallet processes this coin/spend, `PuzzleWithRestrictions.from_memo()` recurses once per nesting level and raises `RecursionError`, which is not caught by the existing `except ValueError` handler, propagating an unhandled exception into wallet sync processing.

Note: I was unable to execute this PoC or trace every downstream caller/exception boundary in wallet sync (e.g., `wallet_state_manager.py`, `plotnft_wallet.py`) within the scope of this investigation, so the exact severity of the resulting crash (process-wide sync halt vs. isolated coin-processing failure) is not fully confirmed from static review alone.

```python
@pytest.mark.anyio
@pytest.mark.parametrize("depth", [1000, 100_000])
async def test_insert_into_data_store_from_file_line_graph_depth(
    data_store: DataStore,
    store_id: bytes32,
    tmp_path: Path,
    depth: int,
) -> None:
    # Binary "line graph":
    #   1 -> leaf_1, 2
    #   2 -> leaf_2, 3
    #   ...
    #   depth -> leaf_depth, leaf_end
    #
    # This stresses depth/stack handling while staying strictly binary.
    #
    # Node IDs:
    # - internal nodes: 1..depth
    # - per-level leaf nodes: (depth+1)..(2*depth)
    # - final leaf: (2*depth+1)
    internal_first = 1
    internal_last = depth
    leaf_base = internal_last + 1
    leaf_end = (2 * depth) + 1

    edges: list[tuple[int, int]] = []
    for i in range(internal_first, internal_last):
        # Order matters: first edge is left child, second edge is right child.
        edges.append((i, leaf_base + (i - internal_first)))  # unique leaf for this internal node
        edges.append((i, i + 1))  # next internal node

    # last internal points to its leaf and a final leaf
    edges.append((internal_last, leaf_base + (internal_last - internal_first)))
    edges.append((internal_last, leaf_end))

    filename = tmp_path / f"line_graph_depth_{depth}.dat"
    root_hash = create_graph_util(filename, edges)

    with pytest.raises(chia_rs.datalayer.RecursionDepthExceededError):
        await data_store.insert_into_data_store_from_file(store_id, root_hash, filename)

```
