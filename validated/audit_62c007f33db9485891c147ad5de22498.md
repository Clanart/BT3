Found a clear analog: `onAccept` in `ExtrinsicIntents.sol` finalizes withdrawal (`_withdraw(..., finalize=true)`) for `RedeemEscrow`/`RefundEscrow` messages without ever checking `_filled[commitment]` before doing so, mirroring the `processAuction()` pattern where a state-changing action is gated only by external, replayable conditions rather than an internal one-shot guard.

### Title
Missing `_filled` finalization guard in `onAccept()` allows repeated `_withdraw` calls to drain order escrow beyond what was deposited - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`onAccept()` handles `RedeemEscrow` and `RefundEscrow` messages by calling `_withdraw(body, isRefund, true)` unconditionally, without first checking whether `_filled[commitment]` is already non-zero [1](#0-0) . This is structurally identical to the Knox `processAuction()` bug: the finalize action is executed based on an incoming-message condition (a valid, authenticated Hyperbridge POST) rather than an idempotent internal guard on the resource being finalized.

### Finding Description
`_withdraw` decrements `_orders[commitment][token]` per call and transfers out whatever `amount` is specified in the `WithdrawalRequest` body, checking only that `escrowed != 0`, not that `escrowed >= amount` correctly accounts for cumulative withdrawals beyond intended bounds since `escrowed - amount` will underflow/revert only if amount exceeds escrowed — but nothing prevents a second `RedeemEscrow`/`RefundEscrow` message with the same `commitment` from being dispatched and delivered on the source chain [2](#0-1) .

The dedup relied upon is `EvmHost.dispatchIncoming`'s `_requestReceipts[commitment]` replay protection, but that commitment is computed over the **ISMP PostRequest** (source, dest, nonce, body, timeout), not the **order commitment** [3](#0-2) . The destination-chain gateway is the one constructing and dispatching this PostRequest (in `_fillCrossChain` for RedeemEscrow, and `_cancelFromDest` for RefundEscrow) [4](#0-3) [5](#0-4) . Each such dispatch produces a **new, unique ISMP nonce**, so the resulting PostRequest commitment differs every time even though the embedded `WithdrawalRequest.commitment` (the order commitment) is identical. The `_requestReceipts` replay guard on `EvmHost` therefore does not prevent two distinct ISMP messages — both carrying the same order `commitment` in their body — from each independently reaching `onAccept()` and calling `_withdraw(..., finalize=true)`.

Concretely: if `_cancelFromDest()` is invoked twice for the same order commitment (e.g., once by the user before the deadline is exactly reached, and once permissionlessly by anyone after the deadline — the code explicitly allows both an authorized pre-deadline call and an unauthorized post-deadline call for the *same* order, and nothing in `_cancelFromDest` checks `_filled[commitment]` before setting it), two separate `RefundEscrow` PostRequests are dispatched to the source chain with the same order commitment. Each will arrive as an independently-committed ISMP message (different nonces ⇒ different `_requestReceipts` keys) and independently call `_withdraw(body, true, true)` on the source-chain gateway. `onAccept()` performs no check like `if (_filled[commitment] != address(0)) revert Filled();` before finalizing [1](#0-0) .

The corrupted values are `_orders[commitment][token]` (decremented a second time, potentially underflowing/reverting only once escrow is exhausted — but any residual dust or accumulated fees in `_orders[commitment][TRANSACTION_FEES]` can be drained twice) and `_filled[commitment]` (overwritten, breaking the "who received the funds" invariant used by off-chain status checks such as `OrderStatusChecker.isOrderRefunded`) [6](#0-5) . Because `_withdraw` re-checks `_orders[body.commitment][token]` per token and reverts only if `escrowed == 0`, a partially-drained order (e.g., after a first RedeemEscrow that only released some assets, or where `TRANSACTION_FEES` line item still holds a positive balance) allows the second finalize call to sweep the accumulated fee balance in `_orders[commitment][TRANSACTION_FEES]` again if it was not yet zeroed by the first call, or to succeed on assets that overlap only partially with what the first message covered.

### Impact Explanation
This matches the bounty's "duplicate settlement/double-claim" and "fund loss" categories: escrow funds meant to move exactly once to the rightful beneficiary can be dispatched and finalized more than once because `onAccept()` lacks an idempotency guard equivalent to Knox's missing `auctionProcessed` check. Unlike a pure replay of the identical ISMP message (which is blocked by `_requestReceipts`), this is a **new, valid, once-only-per-message but not once-only-per-order** message flow — the vulnerability is in the application-level state machine (`_filled`), not the ISMP transport layer.

### Likelihood Explanation
Reaching this requires no malicious relayer, prover, or governance action — `_cancelFromDest` is explicitly permissionless after `order.deadline` has passed for any caller, and can be invoked by any account at any time following expiry with the same `order` calldata, producing a fresh dispatch each time as long as `_filled[commitment]` was never checked to already be set. Any user/attacker holding the (public) `Order` struct can trigger this by calling `cancelOrder()` more than once before the first cross-chain `RefundEscrow` message is finalized on the source chain — the source-chain guard needed to reject the second one (`_filled[commitment] != 0`) is simply absent.

### Recommendation
Add an explicit one-shot guard in `onAccept()` before calling `_withdraw` with `finalize=true`:
```solidity
if (_filled[body.commitment] != address(0)) revert Filled();
```
Additionally, guard `_cancelFromDest` (and `_fillCrossChain`) on the destination chain so that a second call for an already `_filled` commitment cannot dispatch a second `RedeemEscrow`/`RefundEscrow` message at all, closing the vulnerability at the source of duplicate dispatch rather than relying solely on the destination-side check.

### Proof of Concept
1. User places a cross-chain order; solver never fills it, deadline passes.
2. Attacker (or anyone) calls `cancelOrder()` → `_cancelFromDest(order, options1, commitment)`. This sets `_filled[commitment] = order.user` and dispatches `RefundEscrow` PostRequest #1 (ISMP nonce N) to the source chain.
3. Before PostRequest #1 is relayed/finalized on the source chain, attacker calls `cancelOrder()` again with the same `order` and a new `options2` (different `relayerFee`/`msg.value`). Since `_cancelFromDest` never checks `_filled[commitment]` before proceeding, it dispatches a second `RefundEscrow` PostRequest #2 (ISMP nonce N+1) with the identical `WithdrawalRequest.commitment`.
4. Both PostRequest #1 and #2 are distinct ISMP messages (different nonces ⇒ different commitments in `EvmHost._requestReceipts`), so both pass replay protection and are independently delivered to `onAccept()` on the source chain.
5. Each delivery calls `_withdraw(body, true, true)`, which finalizes and attempts to move escrow twice; any assets or fees not already zeroed by the first call (e.g., `_orders[commitment][TRANSACTION_FEES]`) are paid out a second time, and `_filled[commitment]` is overwritten, corrupting the order's finalization record.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

	/**
	 * Checks if a V2 order has been refunded by reading the `_orders` mapping on the source chain.
	 *
	 * Calls `_orders(commitment, tokenAddress)` for each input token. When the order is placed the
	 * escrowed amounts are stored there. After a successful refund the contract zeroes them out.
	 * An order is considered refunded when all escrowed input amounts have been returned (i.e. are 0).
	 *
	 * @param order - The V2 order to check. `order.id` is used as the commitment; if not set it is computed.
	 * @returns True if all escrowed inputs have been returned to the user on the source chain, false otherwise.
	 */
	async isOrderRefunded(order: Order): Promise<boolean> {
		if (!order.inputs || order.inputs.length === 0) return false

		const commitment = (order.id ?? orderCommitment(order)) as HexString
		const sourceStateMachineId = isHex(order.source) ? hexToString(order.source as HexString) : order.source

		const intentGatewayV2Address = this.ctx.source.configService.getIntentGatewayAddress(sourceStateMachineId)

		for (const input of order.inputs) {
			const tokenAddress = bytes32ToBytes20(input.token)
			const escrowedAmount = await this.ctx.source.client.readContract({
				abi: IntentGatewayV2ABI,
				address: intentGatewayV2Address,
				functionName: "_orders",
				args: [commitment, tokenAddress],
			})

			if (escrowedAmount !== 0n) {
				return false
			}
		}

		return true
	}
