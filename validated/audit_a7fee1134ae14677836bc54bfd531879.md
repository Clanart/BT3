### Title
Unchecked ERC20 Transfer Return Value in Escrow Withdrawal Silently Locks Funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` releases escrowed intent tokens using a raw low-level `.call()` to the token's `transfer` selector and only checks that the call did not revert, never decoding the returned boolean. Non-standard ERC20 tokens that return `false` on failure instead of reverting will report `success == true` while transferring nothing, yet the escrow accounting is decremented and the order is marked finalized regardless.

### Finding Description
`withdraw()` is the internal handler invoked from `onAccept()` for both `RequestKind.RedeemEscrow` and `RequestKind.RefundEscrow` messages [1](#0-0) . For each escrowed token it performs:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [2](#0-1) 

The same unchecked pattern is repeated for the fee-token payout in the same function, and for dust sweeping in `onAccept`'s `SweepDust` branch [3](#0-2) [4](#0-3) .

A raw `.call()` only reports `success = false` when the callee itself reverts. A non-compliant ERC20 (e.g. one that returns `false` instead of reverting on insufficient balance/blocklist/paused states — this pattern is common enough that OpenZeppelin's `SafeERC20` exists specifically to guard against it) will make the call return `success = true` with `returnData = abi.encode(false)`. The code never decodes that return data, so the failure is swallowed. `token` here comes from `order.inputs[i].token`/`order.output` set by whoever called `placeOrder()` — the order creator fully controls which ERC20 contract is escrowed [5](#0-4) .

Elsewhere in the same repo the fix pattern is already applied correctly: the non-Tron mainline `IntentsBase._withdraw()` uses `SafeERC20.safeTransfer()` for the exact same escrow-release logic [6](#0-5) , confirming the Tron variant is the outlier missing the safe-transfer guard that the rest of the codebase relies on for this bug class.

### Impact Explanation
Because `_orders[body.commitment][token] -= amount` and `_filled[body.commitment] = beneficiary` both execute unconditionally once `success == true`, a false-returning token causes: (1) the destination beneficiary never actually receives the tokens, (2) the escrow slot is zeroed out so no retry or alternate recovery path exists (`UnknownOrder` guards future withdrawal attempts against the same commitment/token pair), and (3) the order is marked finalized, closing off any cancellation/refund path. The result is genuine, permanent loss of the escrowed funds with no remediation — tokens remain stuck in the contract while all bookkeeping says they were paid out. This satisfies the bounty's "stealing or loss of funds" and "false proof/state acceptance"-adjacent criteria (false settlement state is accepted as final).

### Likelihood Explanation
Exploitability requires no privileged role, relayer collusion, or governance action — an ordinary unprivileged user places an order (`placeOrder`) specifying a token contract they control (or a known non-compliant token deployed on the destination chain) as an input/output asset. When the counterpart gateway later dispatches the `RedeemEscrow`/`RefundEscrow` message and it reaches `onAccept` → `withdraw()`, the bug triggers deterministically on the first transfer attempt. The `authenticate()` call only checks the message's cross-chain source/module binding, not the token's transfer semantics, so it does not block this path [1](#0-0) .

### Recommendation
Replace the raw `.call()` + success-only checks in `withdraw()` (both the token loop and the fee-token payout) and in the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer()`, consistent with how `evm/src/apps/intentsv2/IntentsBase.sol` already handles this same operation.

### Proof of Concept
1. Deploy a minimal ERC20-like contract `EvilToken` whose `transfer()` always returns `false` without reverting (or reverts only on transfers above some threshold, mimicking real non-compliant tokens).
2. Call `placeOrder()` on the Tron `IntentGatewayV2` with `order.inputs[0].token = EvilToken`, escrowing some amount.
3. Trigger the cross-chain fill/cancel flow so the counterpart chain dispatches a `RedeemEscrow` (or `RefundEscrow`) `PostRequest` back to this gateway.
4. `onAccept()` routes to `withdraw()`; `EvilToken.transfer(beneficiary, amount)` returns `false`, but the low-level `.call()` reports `success = true` since the token didn't revert.
5. Observe: `_orders[commitment][EvilToken]` is decremented to 0, `_filled[commitment]` is set, `EscrowReleased`/`EscrowRefunded` is emitted — yet `EvilToken.balanceOf(beneficiary)` is unchanged and the tokens remain permanently stuck in the gateway contract with no further code path to recover them.
