### Title
`SchnorrAggregate::read` trusts an unvalidated 4-byte signature count, enabling connection hang / resource exhaustion on streamed deserialization - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The kafka-python advisory (CVE-2026-10142) describes a protocol parser that reads a 4-byte frame length and either allocates gigabytes or hangs the connection because the length is never bounds-checked. `SchnorrAggregate::read` in the in-scope `schnorr` crate has the same shape: it reads a little-endian `u32` count and loops that many times calling `C::read_G`, with no cap on the count and no check that the declared count is consistent with the actual data available.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregate::read` reads `len` as a `u32` and iterates `0 .. u32::from_le_bytes(len)` performing `Rs.push(C::read_G(reader)?)` for each element.

```rust
// crypto/schnorr/src/aggregate.rs
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
  let mut len = [0; 4];
  reader.read_exact(&mut len)?;
  let mut Rs = vec![];
  for _ in 0 .. u32::from_le_bytes(len) {
    Rs.push(C::read_G(reader)?);
  }
  Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

There is no bound on `len` (up to ~4.29 billion elements), no `Vec::with_capacity` sanity cap, and no check of the count against bytes remaining. The count alone dictates loop iterations. By contrast, other Serai readers are parameterized by protocol-fixed sizes (`Commitments::read` uses `params.t()`, `Commitments::read` in FROST uses the algorithm's `nonces()` layout, `MultiDLEqProof::read` takes an explicit `discrete_logs`), so the count is fixed by context rather than attacker bytes. `SchnorrAggregate::read` is the one in-scope parser where the attacker directly controls the element count over the wire.

Two consequences depending on the reader:

- On a blocking/streaming `io::Read` (the deployment shape when aggregate signatures are parsed off a P2P/RPC stream), declaring `len = u32::MAX` and then withholding bytes leaves the deserializer blocked in `read_exact` — the exact "connection hangs until restart" behavior of the advisory.
- On any reader, each successfully read element is pushed into `Rs`, and the caller proceeds to `verify`, which builds a `pairs` vector of `2 * len + 1` and runs `multiexp_vartime` — memory and scalar-multiplication work scale linearly with attacker-declared count, not with a protocol bound.

### Impact Explanation
An unprivileged party who can submit an aggregate signature (any path that feeds untrusted bytes to `SchnorrAggregate::read`) can hang a worker/connection indefinitely with a single 4-byte prefix, or force parsing/verification work proportional to a forged count of up to ~4 billion. This is a denial of service against the node processing the aggregate — same class and severity profile (High CVSS, CWE-789 uncontrolled memory allocation) as the reference advisory, mapped onto Serai's protocol parser.

### Likelihood Explanation
Reachable wherever serialized `SchnorrAggregate`s transit an `io::Read` that isn't a pre-sized slice (network codecs in Serai use exactly this `io::Read`/`ReadWrite` pattern). The attacker needs no keys, no threshold collusion, and no valid signature — only the ability to deliver 4 attacker-chosen length bytes. Against `&[u8]` inputs it degrades to a bounded loop that errors at EOF, so the full hang requires a streaming reader; the unbounded `Vec` growth and `verify` multiexp apply in both cases.

### Recommendation
Bound the count before iterating, e.g. reject `len` above a protocol maximum (the aggregate's expected participant/signature count is known to the caller — pass it in like `MultiDLEqProof::read`'s `discrete_logs`, or enforce a hard `MAX_AGGREGATE_SIGNATURES`), and/or verify `len` is consistent with remaining input length before allocating/pushing.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ristretto;
use schnorr::aggregate::SchnorrAggregate;

// A reader that never returns EOF and yields zeroed bytes slowly/never —
// models a peer that sends the length prefix then stalls the stream.
struct Stalling;
impl io::Read for Stalling {
  fn read(&mut self, _buf: &mut [u8]) -> io::Result<usize> {
    std::thread::park(); // blocks forever, as a withheld stream does
  }
}

// 1) On a blocking reader: declare 0xFFFFFFFF signatures, then stall.
//    SchnorrAggregate::read blocks in read_exact inside read_G ~forever.
let mut prefix_then_stall = u32::MAX.to_le_bytes().as_slice().chain(Stalling);
let _ = SchnorrAggregate::<Ristretto>::read(&mut prefix_then_stall); // hangs

// 2) On an in-memory reader: len = 0xFFFFFFFF followed by N valid points
//    still drives N read_G calls and N pushes into Rs, then verify()
//    builds a 2N+1 multiexp — work proportional to attacker-declared len
//    with no protocol bound.
```

Caveat: I verified the parsing code in `crypto/schnorr/src/aggregate.rs` directly, but did not enumerate every call site feeding it; the finding holds wherever untrusted bytes reach `SchnorrAggregate::read` via a non-bounded `io::Read`, consistent with the ReadWrite/codec pattern used across Serai's message parsing.
