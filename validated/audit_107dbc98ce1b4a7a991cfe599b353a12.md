## Analog Finding [1](#0-0) 

### Title
Git-remote-controlled `WWW-Authenticate` header spoofs "GitHub Enterprise" identity and triggers an unsolicited OAuth/account-binding flow - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The original report's broken invariant is that a value meant to bind an action to a specific, freshly-verified context (`block.chainid`) is instead derived once and trusted without independent re-verification, letting a replayed message be treated as valid on the wrong chain. The GitHub Desktop analog is `getEndpointKind()` in the credential-helper trampoline, which decides whether a remote host is a genuine GitHub/GitHub Enterprise endpoint by trusting an attacker-controlled HTTP response header (`WWW-Authenticate`) forwarded by git, instead of independently verifying the host's identity.

### Finding Description
When git needs credentials for an HTTPS remote, it invokes Desktop's credential helper trampoline (`GIT_CONFIG_PARAMETERS=... credential.helper=desktop`), forwarding any `WWW-Authenticate` headers returned by the remote server as `wwwauth[...]` fields in the credential request [2](#0-1) .

`getEndpointKind()` classifies the endpoint as `'enterprise'` purely because the value of that attacker-supplied header contains `realm="GitHub"`, without any cryptographic or network-level verification that the host is actually a GitHub Enterprise instance:
```
if (v.includes('realm="GitHub"')) {
  return 'enterprise'
}
``` [3](#0-2) 

That classification then feeds directly into `getCredential()`: since no existing account matches the attacker's host, Desktop calls `ui.promptForGitHubSignIn(endpoint)` for that endpoint [4](#0-3) . `promptForGitHubSignIn` unconditionally starts the full account-binding flow — `beginEnterpriseSignIn` + `setSignInEndpoint(origin)` (or `beginDotComSignIn` if the attacker also spoofs `hostname === 'github.com'` via a DNS/proxy trick) — using the attacker-chosen `origin` with no additional confirmation that this is a trusted GitHub host: [5](#0-4) .

This mirrors the oracle bug's structure: a security-relevant identity check (`block.chainid`/SALT vs. here, "is this a real GitHub host") is derived from data that is fully controlled/replayable by the untrusted counterparty (the forked chain vs. here, the malicious git remote's HTTP response), and the downstream trusted action (signature verification vs. here, launching the OAuth/enterprise sign-in and account-binding UI) proceeds on that unverified basis.

### Impact Explanation
A malicious or compromised git remote/HTTP proxy that a user clones or fetches from can force GitHub Desktop to spontaneously present its "Sign in to GitHub Enterprise" popup and initiate `setSignInEndpoint`/browser OAuth authorization against an arbitrary attacker-controlled origin — during what looks like a normal, non-interactive git operation (e.g. background auto-fetch, checkout, or `openRepositoryFromUrl` triggered by a deep link). This satisfies the "unauthorized OAuth or account binding" impact category: the account-binding flow is entered on the attacker's terms and endpoint, not the user's, and the resulting sign-in state (`credentialHelperUrl`, `oauthState.endpoint`) is bound to that attacker-chosen host. A user who is used to seeing GHE sign-in prompts from Desktop can be primed to complete an OAuth authorization or type an enterprise PAT into a dialog that is actually rooted in a hostile server's response header, not a host the user asked Desktop to trust.

### Likelihood Explanation
Moderate. It requires the attacker to control (or MITM/proxy) a git HTTP remote that the victim's Desktop instance will contact — which is within the report's accepted attacker model ("attacker controls ... a git remote/proxy response"). No local access, malware, or leaked credentials are needed; only a normal `git fetch/clone/pull` against the attacker's server with a crafted `WWW-Authenticate` header on a 401 response. `findGitHubTrampolineAccount()` (checked first) still requires exact origin match, so existing stored tokens for real GitHub/GHE accounts are not directly exfiltrated by this path — the exposure is limited to triggering the sign-in/account-binding UI itself, which is why this is reported as a trust/UX-boundary bypass rather than a token-theft primitive.

### Recommendation
Do not use the git-forwarded, remote-controlled `WWW-Authenticate` realm string as sufficient evidence that a host is a genuine GitHub/GHE endpoint. Require an independent verification step (e.g. only trust `isGitHubHost()`'s own network probe result, or require the endpoint to already be a configured/known GitHub Enterprise endpoint) before invoking `promptForGitHubSignIn`, and surface the actual remote origin prominently in the sign-in UI so users can detect a mismatch before authorizing.

### Proof of Concept
1. Host an HTTPS git server at `https://evil.example` that serves a normal-looking repository over `git://`/`https://` smart-HTTP protocol.
2. Configure the server to respond to unauthenticated requests with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. Victim runs `git clone https://evil.example/some/repo.git` inside GitHub Desktop (or opens an `x-github-client://openrepo/...` deep link pointing at that URL).
4. Git invokes Desktop's credential helper trampoline; `getEndpointKind()` sees the spoofed header and returns `'enterprise'` [3](#0-2) .
5. Since no account is registered for `evil.example`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example')`, which opens Desktop's `SignIn` popup and calls `beginEnterpriseSignIn` + `setSignInEndpoint('https://evil.example')` [6](#0-5) , presenting an unsolicited GitHub-branded sign-in/OAuth flow rooted at the attacker's domain.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}
```

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
