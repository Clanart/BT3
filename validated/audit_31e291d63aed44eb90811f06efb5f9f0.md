### Title
Spot AMM price used to size mWOM buyback swap allows sandwich-attack value extraction - (File: wombat/SmartWomConvert.sol)

### Summary
`SmartWomConvert` decides how much WOM to swap for mWOM on the Wombat AMM versus how much to mint 1:1, using the live spot price read directly from `IWombatRouter.getAmountOut`. The subsequent on-chain swap itself is executed with `amountOutMin = 0`, so the swap output is completely unprotected against price manipulation, exactly the pattern flagged in the referenced SponsorVault report (spot-price dependence + unprotected swap = sandwichable value leak).

### Finding Description
`currentRatio()` and `maxSwapAmount()` compute the current mWOM/WOM exchange rate and the WOM pool imbalance directly from the Wombat router's spot quote: [1](#0-0) [2](#0-1) 

`smartConvert()` uses this manipulable `currentRatio()`/`maxSwapAmount()` output to decide the `convertRatio` — i.e., how much of the incoming WOM is routed through the AMM swap (`buybackAmount`) versus minted 1:1 via `IMWom.deposit`: [3](#0-2) 

The actual swap in `_convertFor` is then executed against the router with **no minimum-out protection on the swap call itself** (`0` passed as `amountOutMin`): [4](#0-3) 

The only safety check is a single aggregate comparison of `convertAmount + amountRec` against `_minRec` at the end of `_convertFor`: [5](#0-4) 

Because `getAmountOut` reads the Wombat pool's current cash/liability ratio (spot state), an attacker can manipulate the WOM/mWOM pool immediately before the conversion transaction to (a) push `currentRatio()` above `buybackThreshold` so more WOM is routed into the unprotected AMM swap, and/or (b) directly sandwich the `swapExactTokensForTokens` call in `_convertFor`, extracting the price impact as MEV profit at the expense of the WOM being converted. This mirrors the SponsorVault flaw: a protocol contract sizes and executes a swap using a manipulable spot price rather than a robust oracle/TWAP, with no swap-level slippage protection.

### Impact Explanation
`smartConvert` is documented to be "mainly used by wombat staking upon sending wom" (comment at `wombat/SmartWomConvert.sol:132`), meaning it operates on protocol/reward WOM rather than a caller's freely-chosen personal funds in that flow. If invoked in that flow, any wallet able to trigger the conversion (or simply front-run/back-run whenever it naturally executes) can manipulate the WOM/mWOM Wombat pool to divert value from the protocol-held WOM into their own pocket via the unprotected swap, i.e., theft of protocol/yield-bearing funds that ultimately belong to mWOM/WOM stakers. This falls under "theft ... of unclaimed yield" for the affected user base.

### Likelihood Explanation
The attack requires only the ability to manipulate the Wombat WOM/mWOM pool's spot price around the block(s) in which `smartConvert`/`_convertFor` executes — a standard sandwich/flash-loan technique requiring no privileged role, governance action, or admin cooperation. The `swapExactTokensForTokens` call's `amountOutMin = 0` removes any built-in resistance at the swap level, and the aggregate `_minRec` check does not prevent value extraction as long as the manipulated outcome still clears the caller-supplied (potentially loose) minimum.

### Recommendation
Do not size or execute the buyback swap using the router's live spot quote. Either:
1. Enforce a per-swap minimum output derived from an independent, harder-to-manipulate price reference (e.g., a TWAP or oracle) rather than `0`, and
2. Compare the spot price used in `currentRatio()`/`maxSwapAmount()` against that oracle/TWAP reference, reverting or falling back to the oracle-derived ratio when they diverge beyond a safe threshold — consistent with the fix pattern applied to `SponsorVault` (PR 1595) in the reference report.

### Proof of Concept
1. Attacker observes/predicts an imminent call that will route protocol WOM through `SmartWomConvert.smartConvert` (or `convert`/`convertFor` with an insufficiently strict caller `_minRec`).
2. Attacker manipulates the Wombat WOM/mWOM pool's cash/liability balance via a large swap so that `currentRatio()` (spot quote from `getAmountOut`) reports a favorable-looking ratio, maximizing `buybackAmount` routed through the AMM in `smartConvert`.
3. When `_convertFor` executes `IWombatRouter(router).swapExactTokensForTokens(..., 0, ...)`, the attacker's manipulated pool state yields a bad execution price for the contract's WOM, while the attacker captures the price-impact spread.
4. Attacker reverses their initial manipulation swap in the same or following transaction, realizing profit extracted from the WOM that was meant to be converted/minted for stakers. [4](#0-3)

    // should mainly used by wombat staking upon sending wom
    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
