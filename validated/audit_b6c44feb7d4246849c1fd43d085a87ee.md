### Title
Unchecked payment and fee arithmetic can produce an unspendable oversized transaction for signing - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums attacker-influenced payment amounts with plain `u64` addition and compares the result against the total input value. If the payment sum or `payment_sat + needed_fee` wraps, the insufficient-funds check can pass even though the serialized outputs exceed the inputs and Bitcoin's consensus limit. The resulting `SignableTransaction` can be submitted to threshold signing, causing validators to sign a transaction with an unintended, consensus-invalid payment set.

### Finding Description
The constructor computes `input_sat`, `payment_sat`, `needed_fee`, and later the change allowance using normal `u64` addition and subtraction sites rather than consistently checked arithmetic. [1](#0-0) [2](#0-1) [3](#0-2) 

The direct solvency check is:

```rust
if input_sat < (payment_sat + needed_fee) { ... }
```

If `payment_sat` is `u64::MAX - 1`, then a small `needed_fee` wraps `payment_sat + needed_fee` to a tiny value. With ordinary inputs, the comparison therefore accepts the payment list even though the unsigned transaction contains outputs totaling nearly `2^64` satoshis.

This maps the external report's arithmetic-invariant bug onto Serai's Bitcoin transaction constructor: independent valid-looking numeric inputs cross a wrap boundary and leave the signed artifact inconsistent with the amount being authorized.

### Impact Explanation
An attacker able to influence requested payment amounts can cause a multisig to sign a transaction it never should have authorized. The transaction will not be consensus-valid if it spends more than its inputs, but this still represents signing of an unintended transaction and can consume the selected inputs/signing attempt, trigger blamed or failed completion paths, and stall the affected plan. In debug or overflow-checking builds, the same inputs panic during transaction construction, freezing processing rather than returning `TransactionError`.

### Likelihood Explanation
The vulnerable path is reachable through public transaction/payment data supplied to `SignableTransaction::new`; each individual amount only needs to pass the `DUST` check. [4](#0-3)  Exploitation requires the aggregate payment amount to overflow `u64`, so it depends on the calling protocol accepting very large requested amounts before balance validation. Impact is primarily transaction-construction denial of service and unintended signing rather than extraction of spendable funds.

### Recommendation
Use checked arithmetic for every monetary aggregation and comparison:

- `input_sat` should use `try_fold(..., u64::checked_add)`.
- `payment_sat` should use `try_fold(..., u64::checked_add)`.
- `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change` should use `checked_mul`.
- `payment_sat + needed_fee` and `payment_sat + fee_with_change` should use `checked_add`.
- Reject arithmetic overflow with a dedicated `TransactionError`, and preferably bound every payment to Bitcoin's `MAX_MONEY` before serializing it as an output.

### Proof of Concept

```rust
// Conceptual PoC for networks/bitcoin/src/wallet/send.rs

// Construct or scan one ordinary ReceivedOutput worth >= DUST.
let input: ReceivedOutput = ...;

// Publicly influenced payment amounts. Each payment individually passes
// `amount >= DUST`, but their sum overflows u64.
let payments = [
    (attacker_script_a(), u64::MAX),
    (attacker_script_b(), u64::MAX),
];

// With a normal nonzero fee:
//   payment_sat = u64::MAX - 1
//   payment_sat + needed_fee wraps to needed_fee - 2
// For needed_fee >= 3, this wrapped total can be <= input_sat.
let tx = SignableTransaction::new(
    vec![input],
    &payments,
    None,
    None,
    1, // fee_per_vbyte; still above the relay check after sizing
);

// Overflow-enabled build: panics.
// Wrapping release build: can return Ok(_) containing two u64::MAX outputs
// despite the input being far smaller.
assert!(tx.is_ok());
```

The relevant unchecked operations are the payment summation, fee multiplication, and solvency addition. [1](#0-0) [2](#0-1)
