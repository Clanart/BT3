## Analysis

The Notional bug reduces to a general pattern: **a data structure indexed/keyed by token address is assumed to be a set of *distinct* tokens correlated positionally with another array, but the code never enforces uniqueness on one side of that mapping — so a repeated token collapses two logically independent slots into one, breaking the accounting and locking or losing funds.**

I found a structurally identical pattern in Hyperbridge's `IntentGatewayV2` same-chain intent-fill/cancel logic.

`placeOrder` explicitly deduplicates **output** tokens with a transient-storage guard (and the code comment even calls out the exact class of bug: *"Regression test: same-chain partial fills prematurely finalize repeated output legs"*), but performs **no equivalent dedup check on `order.inputs`**: [1](#0-0) 

Escrow accounting in `placeOrder` is keyed purely by token address and correctly sums duplicate input legs: [2](#0-1) 

But `_fillSameChain` reads the input side **positionally**, pairing `order.inputs[i]` with `order.output.assets[i]`, and — for a fully-filled leg — pulls the *entire current* per-token escrow balance rather than a per-leg share: [3](#0-2) 

`_cancelSameChain` does the same positional, un-deduplicated read over `order.inputs`: [4](#0-3) 

Both then hand the resulting (possibly duplicated-token) list to `_withdraw`, whose per-entry guard (`_orders[commitment][token] == 0` → `UnknownOrder`, then `-= amount`) reads and writes the *same* storage slot across iterations when the token repeats: [5](#0-4) 

### Title
Duplicate input tokens in `IntentGatewayV2` same-chain orders permanently lock escrowed funds (Notional-style token-collision defect) - (evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`placeOrder` dedups `order.output.assets` but not `order.inputs`. `_fillSameChain`/`_cancelSameChain` assume `order.inputs[i]` maps 1:1 to a distinct per-token escrow bucket by array index. If the same input token appears at two indices (paired with two distinct, valid output legs), both indices read the *same, undecremented* `_orders[commitment][token]` balance, producing a `WithdrawalRequest.tokens` array with two entries for the same token carrying the full balance twice. `_withdraw`'s per-token zero-check then reverts on the second entry after the first has already zeroed the balance — because `_orders[commitment][token]` was already fully drained by entry 1.

### Finding Description
This is the exact class of bug described in the external report: a set of tokens that is required to be unique/ordered by position (there: pool tokens indexed 0..n; here: `order.inputs[i]` matched against `order.output.assets[i]`) is never validated for uniqueness on one side. When the "reward token equals a pool token" analog occurs here — an input token repeated across legs — both the fill path and the cancel path independently break:

- `_fillSameChain`, on a fully-filled leg, sets `escrowedAmount = _orders[commitment][order.inputs[i].token]`, i.e. the *entire remaining* escrow for that token, not the amount attributable to that specific leg. [6](#0-5) 
- `_cancelSameChain` likewise reads `_orders[commitment][token]` per input index without deduplication. [7](#0-6) 
- `_withdraw` decrements the shared storage slot in-loop and reverts with `UnknownOrder` once a duplicate entry finds the slot already zeroed. [8](#0-7) 

Because both `fillOrder` (full-fill path) and `cancelOrder` traverse the same duplicated-token list, **every settlement path for such an order reverts**, and the user's already-escrowed tokens become permanently unreachable in the contract — there is no other function to retrieve escrow.

### Impact Explanation
This is a direct, protocol-logic-caused loss/lock of user funds, matching the bounty's "stealing or loss of funds" category. Unlike the DoS-only carve-out in the impact gate, the outcome here is **permanent fund lock with no recovery path** (both fill and cancel revert), which is a genuine capital loss for the order creator, not a transient availability issue.

### Likelihood Explanation
Reachable by any unprivileged user through the ordinary, unprivileged `placeOrder` entry point — no relayer, prover, or admin involvement is required. It requires the order creator to supply `order.inputs` with a repeated token address across two legs paired with two distinct output tokens (a plausible construction, e.g. paying two output legs with the same input token split across amounts, which the contract does not reject at placement time although it explicitly rejects the symmetric case for outputs).

### Recommendation
Apply the same transient-storage duplicate-rejection check already used for `order.output.assets` to `order.inputs` in `placeOrder`, or refactor `_fillSameChain`/`_cancelSameChain` to aggregate escrow releases by unique token rather than assuming a positional 1:1 correspondence between `order.inputs[i]` and `order.output.assets[i]`.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [{USDC, 600}, {USDC, 400}]` and `order.output.assets = [{DAI, 500}, {WETH, 1}]` (distinct outputs pass the dedup check; `_orders[commitment][USDC]` accumulates to 1000).
2. Solver calls `fillOrder` fully filling both legs in one call.
3. In `_fillSameChain`, leg 0 (`DAI`) sets `escrowedInputs[0] = {USDC, 1000}` (full balance); leg 1 (`WETH`) also sets `escrowedInputs[1] = {USDC, 1000}` (still full balance, unchanged).
4. `_withdraw` processes `[{USDC,1000},{USDC,1000}]`: first entry transfers 1000 USDC and zeroes `_orders[commitment][USDC]`; second entry hits `_orders[commitment][USDC] == 0` and reverts `UnknownOrder`, aborting the whole `fillOrder` call.
5. `cancelOrder` on the same order independently constructs `remainingTokens = [{USDC,1000},{USDC,1000}]` from `order.inputs` and hits the identical revert in `_withdraw`.
6. Neither settlement path can ever succeed — the escrowed 1000 USDC is permanently stuck in `IntentGatewayV2`. [9](#0-8)
