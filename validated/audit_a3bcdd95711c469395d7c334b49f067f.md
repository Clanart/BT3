### Title
Unmetered full-cache scan on every same-tx contract self-destruct enables quadratic memory/CPU blowup from a single EVM transaction - (File: sei-cosmos/store/cachekv/store.go)

### Summary
The QEMU CVE describes an unbounded, unmetered resource cost triggered by repeating a cheap operation (device unplug) many times. The Sei analog is the EVM `SELFDESTRUCT` cleanup path: every time a contract created and destroyed in the same transaction (EIP‑6780 full removal) is cleared, the keeper scans the **entire** cachekv in-memory cache — not just the account's own key range — via `GetAllKeyStrsInRange`/`DeleteAll`. A transaction that repeatedly creates and same-tx-destroys child contracts (a pattern the codebase itself exercises via `SelfDestructFactory.createAndDestroy`) pays roughly linear gas per iteration but forces node-side work that grows with the size of everything already written in that transaction's cache layer, i.e. quadratically in the number of iterations.

### Finding Description
`x/evm/state/state.go` (`clearAccountState`) is invoked for every self-destructed account at `Finalize()`: [1](#0-0) 

It calls `Keeper.PurgePrefix`, which is a thin wrapper over `KVStore.DeleteAll(nil, nil)` scoped to the account's own state prefix: [2](#0-1) 

`prefix.Store.DeleteAll` narrows the byte range and forwards to the parent store's `DeleteAll`: [3](#0-2) 

The parent is ultimately a `cachekv.Store`. Its `DeleteAll`/`GetAllKeyStrsInRange` implementation does **not** perform a bounded range scan of the cache — it calls `store.cache.Range(...)` over the *entire* `sync.Map` cache (which holds every key written anywhere in this cache layer during the transaction, across all accounts, code, nonces, balances, etc.), filtering by byte comparison per key: [4](#0-3) 

The same unbounded-scan pattern exists in `giga`'s equivalent cachekv (`giga/deps/store/cachekv.go`) and other `DeleteAll`/`GetAllKeyStrsInRange` implementations across the store stack.

A contract can trivially chain many `create()` + `selfdestruct()` cycles in a single transaction (the codebase's own `SelfDestructFactory.createAndDestroy` and `EVMGigaTest.js` "Self-Destruct With Storage Cleanup" tests exercise exactly this same-tx create+destroy pattern): [5](#0-4) [6](#0-5) 

For each such contract destroyed in the same tx, `clearAccountStateIfDestructed` runs `clearAccountState` at `Finalize`, which re-scans the whole accumulated cache: [7](#0-6) 

Because the scan cost of each `PurgePrefix` call grows with the *total* number of keys already cached in the transaction (not with the size of the destroyed account's own storage), a loop of N create+destroy cycles, each writing k keys, costs O(k·N²) scanning work rather than O(k·N). Gas is charged per SSTORE/CREATE/SELFDESTRUCT operation (an EVM-level, roughly linear cost), not per byte scanned in the underlying Cosmos cache, so the actual CPU/memory cost paid by validating nodes is not proportional to the gas the attacker pays — the same "unmetered cost from repeated create/destroy" root cause as the QEMU CVE's device-unplug memory leak.

### Impact Explanation
A single crafted transaction from any unprivileged EVM sender (no special permissions needed — deploying and self-destructing contracts is a normal user-reachable EVM path) can force disproportionate CPU and transient memory allocation on every validating full node while executing/finalizing that one transaction, since the cache scan happens during `Finalize`/`DeleteAll` processing for each same-tx-destructed contract. Because this cost is not properly gas-metered relative to actual work performed, an attacker can construct a transaction that is gas-cheap to submit but expensive to process, risking block-processing delay beyond the 2.5-second target (all nodes must reproduce the same quadratic scan deterministically) or excessive memory churn from repeated `map[string]struct{}` / `[]string` allocations in `GetAllKeyStrsInRange`, which is a resource-exhaustion vector matching the report's accepted "block delay beyond 2.5 seconds" and "crash of default-configuration RPC/full nodes" impact categories.

### Likelihood Explanation
The trigger is a straightforward, already-tested EVM pattern (same-tx CREATE + SELFDESTRUCT, EIP-6780) that any contract deployer can construct without needing precompiles, governance, or validator access — the repository's own test suite (`SelfDestructFactory`, `EVMGigaTest.js`) demonstrates the exact code path that reaches `clearAccountState`/`PurgePrefix`. Scaling the number of create+destroy iterations within the per-block gas limit is a mechanical exercise, making this readily reachable by any public-RPC client submitting a transaction.

### Recommendation
Scope `cachekv.Store.GetAllKeyStrsInRange`/`DeleteAll` (and the equivalent `giga` and `storev2` implementations) to only inspect cache entries actually within `[start, end)` using a sorted/indexed structure (or by iterating the underlying `unsortedCache`/`sortedCache` structures already maintained) instead of a full `sync.Map.Range` filter over every key in the layer. Additionally, ensure the gas cost of `SELFDESTRUCT`/account-cleanup reflects the true amount of underlying store work performed (or cap/charge for the number of keys scanned) so that repeated same-tx create+destroy cycles cannot decouple gas paid from node-side processing cost.

### Proof of Concept
1. Deploy a factory contract exposing a loop that, in a single transaction, calls `new SelfDestructTester(...)` (seeding many storage slots) immediately followed by `selfdestruct()` on the child, repeated N times (extending the existing `SelfDestructFactory.createAndDestroy` pattern into a loop) — see: [5](#0-4) 
2. Submit one transaction invoking this loop with N large enough to fit under the block gas limit but produce a growing cachekv layer (many prior CREATE/SSTORE writes accumulate in `store.cache`).
3. At `Finalize()`, each of the N same-tx self-destructs triggers `clearAccountState` → `PurgePrefix` → `DeleteAll` → `GetAllKeyStrsInRange`, each scanning the full (and growing) `cache` map: [4](#0-3) 
4. Measure that per-transaction processing time/memory grows super-linearly with N despite the gas cost growing linearly, confirming the amplification.

Note: I was unable to fully verify actual production gas-limit feasibility for large N (i.e., whether a single block's gas limit permits enough same-tx create+destroy cycles to produce a measurable >2.5s delay) without running the code; this would need to be confirmed by a background agent with execution access to the full test/benchmark harness.

    function createAndDestroy(uint256 numKeys, address payable recipient)
