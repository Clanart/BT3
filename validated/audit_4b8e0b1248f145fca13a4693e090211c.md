### Title
Attacker-controlled `ThresholdKeys` deserialization never validates `secret_share`/verification-share consistency, allowing injection of an arbitrary group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) accepts untrusted bytes describing `t`, `n`, `i`, an `Interpolation`, a `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391). `ThresholdKeys::new` derives `group_key` purely as `sum(verification_shares[i] * interpolation_factor(i))` over participants `1..=t` and stores the supplied `secret_share` verbatim — it never checks that `C::generator() * secret_share == verification_shares[i]`, and it uses `<C as Ciphersuite>::read_G`, which does not reject the identity point (unlike `Curve::read_G`, crypto/frost/src/curve/mod.rs:125-131). An unprivileged party who can feed bytes to `ThresholdKeys::read` can therefore inject a fully inconsistent key: a `secret_share` whose discrete log they know, paired with attacker-chosen verification shares that yield an attacker-chosen `group_key`.

### Finding Description
The bug class of the external report — unsanitized input flowing into a security-sensitive operation — maps to Serai's deserialization path for threshold key material. The checks performed in `ThresholdKeys::new` are limited to share count (`verification_shares.len() == n`), participant index range (`<= n`), and the `Constant`-requires-`t == n` rule (crypto/dkg/src/lib.rs:355-374). Nothing binds the deserialized `secret_share` to `verification_shares[i]`, and nothing binds the interpolated `group_key` to any honest polynomial. With `Interpolation::Constant(vec![F::ONE; n])` (t = n enforced), `group_key` becomes the plain sum of the attacker-supplied verification shares — fully attacker-determined. `ThresholdView`/`view` (crypto/dkg/src/lib.rs:463-533) then builds `secret_share` and `verification_shares` from these poisoned values, and downstream FROST signing (`AlgorithmSignMachine::sign` in crypto/frost/src/sign.rs) produces signature shares under this injected material.

### Impact Explanation
The victim node is induced to treat an attacker-chosen `group_key` and an attacker-known secret share as its threshold key. Any signature produced under `Interpolation::Constant` with an attacker-consistent share set verifies under the attacker's chosen group key — i.e., the node produces signatures for a public key entirely controlled by the bytes an unprivileged party supplied, satisfying the "signing of an unintended message"/injected-state analog. Additionally, identity verification shares are accepted through `Ciphersuite::read_G`, enabling shares that interpolate to degenerate group keys.

### Likelihood Explanation
Exploitation requires reaching `ThresholdKeys::read` with adversarial bytes — the listed attack surface for this exercise. No secrets need to be leaked and no collusion is required; the attacker crafts the entire serialized blob offline (any scalar plus any points). The cost is trivial; the only constraint is the deployment actually deserializing key material from a peer-reachable source rather than local trusted storage.

### Recommendation
In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject identity/zero verification shares. Prefer a stricter `read` that re-derives consistency (e.g., require `C: Curve` and use `Curve::read_G` to reject identity), and document that `ThresholdKeys::read` must only consume authenticated bytes, or authenticate the serialized blob externally.

### Proof of Concept
```
// C: any Ciphersuite, e.g. Ristretto. Attacker picks:
let x = C::F::random(rng);                      // attacker-known secret
let t = n;                                      // satisfies Constant interpolation
let params_bytes = (t,n,i=1) + byte 0 + [F::ONE; n] // Interpolation::Constant(ones)
// verification_shares: any n points; group_key = sum of first t points
let shares_points = vec![G * x, identity, ...]; // sum = G*x
// serialize: id_len||ID||t||n||i||0||[ONE; n]||x||shares_points
let keys = ThresholdKeys::<C>::read(&mut blob.as_ref()).unwrap(); // accepted
assert_eq!(keys.group_key(), C::generator() * x); // attacker-chosen key bound to known secret
// keys.view(...)+FROST sign produces shares consistent with group_key = G*x
```
Root cause: crypto/dkg/src/lib.rs:376-378 derives `group_key` without ever checking the deserialized `secret_share` against `verification_shares[i]`, and crypto/dkg/src/lib.rs:622 uses the identity-accepting `Ciphersuite::read_G`.
