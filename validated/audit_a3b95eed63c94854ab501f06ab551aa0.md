### Title
Hard-coded UTF-8 decoding of raw diff buffers silently corrupts non-UTF-8 file content during partial commits - (File: `app/src/lib/git/diff.ts`)

### Summary
`diffFromRawDiffOutput` in `app/src/lib/git/diff.ts` unconditionally decodes the raw `git diff`/`git log` output buffer as UTF-8, and the resulting JavaScript string (with any invalid byte sequences already replaced by U+FFFD) is later used verbatim by `formatPatch`/`formatPatchToDiscardChanges` in `app/src/lib/patch-formatter.ts` to reconstruct a text patch that is fed back into `git apply --cached`. If a file in a cloned/fetched repository contains bytes that are not valid UTF-8 (e.g. Shift-JIS, Latin-1, UTF-16, or simply a byte sequence that happens to be invalid UTF-8), the decode step is lossy and irreversible, and the corrupted text gets written into the index/commit when the user performs a partial stage of that file.

### Finding Description
`diffFromRawDiffOutput` explicitly documents the assumption: [1](#0-0) 
```

  // we can try and convert this into other encodings in the future
  const result = output.toString('utf-8')
  ...
}
```
This is invoked from `buildDiff`, which is the shared entry point for both `getWorkingDirectoryDiff` and `getCommitDiff`, both of which request `encoding: 'buffer'` from `git()` specifically so they can access the raw bytes: [2](#0-1) [3](#0-2) 

The resulting `IRawDiff.contents`/hunks are strings that have already lost fidelity for any non-UTF-8 byte sequence in the file (JS's `Buffer.toString('utf-8')` replaces malformed sequences with U+FFFD, an irreversible, one-way transformation).

When the user performs a **partial commit** (selecting only some lines/hunks of a changed file), Desktop does not use `git add`/`update-index` on the whole file — it builds a synthetic unified diff from the already-decoded `DiffLine.text` strings via `formatPatch`: [4](#0-3) 
Context lines and unselected-but-retained lines (e.g. unselected deletions converted to context) are copied through `line.text` unchanged: [5](#0-4) 

This string patch is then piped as `stdin` to `git apply --cached`: [6](#0-5) 

Because the original buffer was already decoded lossily as UTF-8 before the diff was ever parsed, any content in a context line, an unselected/retained line, or the surrounding text of a hunk that contained non-UTF-8 bytes will have already been replaced with U+FFFD by the time it's re-serialized into the patch and applied to the index. `git apply --cached` will happily write this corrupted content into the Git object database as part of the commit — there is no re-validation against the actual working-tree bytes.

### Impact Explanation
This meets the "silent corruption of what the user commits" impact bar: a file whose content is not valid UTF-8 (which is entirely plausible for legacy text files, files authored on Windows-1252/Shift-JIS systems, or files deliberately crafted by a malicious repository author/maintainer to exploit collaborators who do partial-file staging) will have its bytes silently and irreversibly replaced with U+FFFD replacement characters in the portion of the file that ends up in the commit — without any error, warning, or diff-review indication that this transformation occurred (the existing `DiffContentsWarning` component only warns about hidden bidi characters and line-ending changes, not encoding loss). The user believes they are committing/pushing exactly what is in their working directory, but the object actually written to the repository (and later pushed) differs from the real file content.

### Likelihood Explanation
The path is triggered purely through normal use of the app's "partial commit" feature (selecting/deselecting some lines of a changed file before committing) on any file that isn't strictly UTF-8 — no local/admin access, no social engineering, no malware required. An attacker who controls a repository (or a file introduced via merge/checkout from a malicious remote) only needs to ensure the file's bytes aren't valid UTF-8 in a region a victim might leave unselected/as context when doing a partial stage. This is a plausible, naturally-occurring scenario (mixed encodings are common in real-world repos), which raises likelihood above purely theoretical.

### Recommendation
- Detect whether `output.toString('utf-8')` round-trips losslessly (e.g., by re-encoding and comparing byte length/content, or using a strict UTF-8 decoder) before treating a diff as text; fall back to a binary/"cannot show diff" treatment (similar to how oversized diffs already fall back to `Unrenderable`/`LargeText`) when the underlying bytes are not valid UTF-8.
- If encoding must be assumed, surface a clear, blocking warning (not just a passive banner) before allowing partial-line commits for such files, and disable line-level selection until content fidelity can be guaranteed.
- Prefer operating on the raw buffer for the parts of the file that are not touched by the user's selection, only reconstructing "changed" lines from the decoded diff, so unselected/context regions are round-tripped exactly.

### Proof of Concept
1. Attacker publishes/pushes a repository containing a tracked text file (e.g. `notes.txt`) whose bytes are valid Shift-JIS/Latin-1 but not valid UTF-8 (i.e., contain byte sequences like `0xA4 0xA2` that are invalid as UTF-8 continuation sequences).
2. Victim clones the repo in GitHub Desktop and modifies one line of `notes.txt`, then opens the diff view and selects only that one changed line for commit (leaving the rest of the file as unselected/context).
3. Desktop calls `getWorkingDirectoryDiff` → `buildDiff` → `diffFromRawDiffOutput`, which decodes the raw diff buffer with `output.toString('utf-8')` — replacing the non-UTF-8 bytes elsewhere in the file with U+FFFD in the in-memory `DiffLine.text` values.
4. `formatPatch` (`app/src/lib/patch-formatter.ts:129-161`) builds a synthetic patch using those already-corrupted `line.text` strings for the context/unselected lines.
5. `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-81`) pipes that patch to `git apply --cached`, writing the corrupted (U+FFFD-substituted) content into the Git index/object for the untouched portion of the file.
6. The resulting commit's blob for `notes.txt` now differs from the actual working-directory bytes — the corruption is silent and only detectable by diffing the raw bytes outside of Desktop. [1](#0-0) [4](#0-3) [6](#0-5)

  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        if (line.type === DiffLineType.Add) {
          return
