### Title
OP_RETURN Data Output Omitted From Fee Estimation, Producing Under-Paid Transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output carrying caller-supplied data to `tx_outs`, but computes the transaction weight/vbytes — and therefore `needed_fee` — using only `payments` and `change`. The data output is "left behind" by the fee logic exactly as the report's `saleToken` is left behind by the emergency-closure transfer logic: the transaction is built and signed for a larger actual size than was accounted for, so the realized fee rate is lower than the caller-requested `fee_per_vbyte`.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is pushed onto `tx_outs` at `send.rs:194-202` before any weight calculation, yet both calls to `calculate_weight_vbytes` pass only `payments` (`send.rs:204` and `send.rs:226`), never `tx_outs` or the data output. An `OP_RETURN` output adds roughly `8 (value) + 1 (script len) + 2 (OP_RETURN + push opcode) + len(data)` bytes — up to ~91 vbytes for the permitted 80-byte payload — none of which is counted.

Two consequences follow:

1. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`, `send.rs:227-232`) is underpriced. The change amount is then computed as `input_sat - (payment_sat + fee_with_change)` (`send.rs:228-230`), so the transaction commits to a fixed absolute fee that covers a smaller transaction than the one actually produced.
2. The minimum-relay-fee gate at `send.rs:211` compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes`, so a transaction at the boundary passes the check while its true fee rate sits below the relay minimum.

Since `fee()` is defined as `sum(prevouts) - sum(outputs)` (`send.rs:138-141`) and the outputs' values are fixed at construction, there is no mechanism to correct the shortfall — the multisig signs exactly this transaction via `taproot_key_spend_signature_hash` over `Prevouts::All` (`send.rs:373-390`).

### Impact Explanation
A `SignableTransaction` constructed with `data` pays a materially lower effective fee rate than requested (worst case ~91 unaccounted vbytes). At low `fee_per_vbyte` values the signed transaction can fall below the default minimum relay fee despite passing the `TooLowFee` check, so it will not propagate and the inputs are locked until the attempt is abandoned and re-signed — funds are committed to a transaction that cannot complete. Analogous to the report: an asset class that should be handled during the operation is silently omitted, leaving value stranded.

### Likelihood Explanation
The flaw triggers deterministically whenever `data` is `Some` — no adversary is required. Whether it causes a relay failure depends on how tight `fee_per_vbyte` is to the relay minimum and the data length, so the missed fee ranges from negligible to transaction-stalling. Reachability is through the public `SignableTransaction::new` API with caller-controlled `data`, matching the "untrusted inputs to a public API" model.

### Recommendation
Include the `OP_RETURN` output in the weight estimation — e.g., pass the fully-built `tx_outs` (or `payments` plus the data output) into `calculate_weight_vbytes` at `send.rs:204` and `send.rs:225-226` instead of only `payments`. Alternatively, compute `vbytes` after all outputs (payments, `OP_RETURN`, change) are assembled.

### Proof of Concept
```rust
// Conceptual: for inputs totaling input_sat, payments totaling payment_sat,
// a change script, and data = Some(vec![0u8; 80]):
//
//   vbytes_est = vbytes(inputs, payments, change)          // what the code measures
//   vbytes_real = vbytes_est + ~91                         // actual signed tx size
//
// Let fee_per_vbyte = 1 and input_sat = payment_sat + vbytes_est + DUST.
// SignableTransaction::new succeeds; change = DUST; needed_fee = vbytes_est.
// The broadcast tx is ~91 vbytes larger, so fee/vbyte < 1 sat/vB < min relay,
// and the transaction is rejected by the mempool while its inputs remain spent
// in the constructed (signed) transaction.
```
The mis-sizing is directly observable by comparing `tx.weight()` of `transaction()` after construction against the `vbytes` implied by `needed_fee / fee_per_vbyte`.
