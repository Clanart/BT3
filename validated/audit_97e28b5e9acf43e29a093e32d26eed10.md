### Title
Unbounded recursive memo parsing in `PuzzleWithRestrictions.from_memo()` allows a crafted CREATE_COIN memo to crash wallet/pool sync via Python stack exhaustion - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively parses a `CREATE_COIN` memo blob to reconstruct an on-chain custody/PlotNFT puzzle structure. When the memo encodes an `MofN` node, the function recurses once per member via a Python-level function call with no depth limit: [1](#0-0) . This is directly analogous to the CVE-2017-11624 QPDF bug class: a parser that recurses on attacker-controlled nested structure without a stack/depth guard, leading to stack exhaustion ("infinite loop"/DoS via crafted input) rather than memory-safety corruption.

### Finding Description
`from_memo()` is the reconstruction counterpart of `memo()`/`to_program()` used to synchronize an "unknown" on-chain inner puzzle back into wallet-side representations: [2](#0-1) . For an `MofN` branch, it calls itself recursively for every element of `m_of_n_hint.member_memos`, and each member can itself be an arbitrarily nested `MofN`, so recursion depth is bounded only by how deeply the memo's CLVM structure nests `MofN` hints — a value fully controlled by whoever creates the coin that carries the memo.

This memo is not a puzzle that must be *executed* to be nested — it is *literal output data* of a `CREATE_COIN` condition. Constructing a deeply nested list structure in CLVM (e.g., a chain of `(1, [...])` cons pairs representing nested `MofNHint`s) is cheap: CLVM's per-`cons`/quote cost is small and roughly linear in node count, so an attacker can build memo nesting depth far beyond Python's default recursion limit (~1000) while staying well within a single spend's cost budget.

The parsing path is reachable by any full-node/wallet process that decodes a `CREATE_COIN` memo through this code, notably PlotNFT pool-transition syncing: `PlotNFT.get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` directly on the memo of a coin created by an observed spend: [3](#0-2) . Any wallet or client following a PlotNFT/singleton chain that encounters a malicious spend with a crafted memo will attempt this recursive parse.

### Impact Explanation
A crafted, cheaply-constructed CREATE_COIN memo (attached to a coin that superficially matches the PlotNFT/custody singleton shape, or otherwise processed via `PuzzleWithRestrictions.from_memo`) triggers unbounded Python recursion in the parsing wallet/pool-sync client, raising `RecursionError`. Depending on how the caller handles exceptions, this can crash or hang the wallet's pool-sync/plotnft-following logic for any client attempting to derive PlotNFT/custody state from that spend — a spend-triggered processing halt for an unprivileged, single-attacker-controlled coin/spend. This satisfies the "spend-triggered transaction-processing halt" acceptance criterion; it does not itself grant unauthorized coin movement, inflation, or forged identity.

### Likelihood Explanation
Likelihood is moderate-to-high for any client that actively follows PlotNFT/custody singleton lineages using `get_next_from_coin_spend`/`from_memo` on untrusted, chain-observed memos: constructing the malicious memo requires only a single ordinary spend creating a coin with a deeply nested memo program, no privileged position, and no consensus-level malformation (the outer block/spend itself can be perfectly valid CLVM). The trigger condition depends on some client code path actually calling `from_memo()` on attacker-supplied data outside of a guarded try/except that only catches `ValueError` (as done at the top level in `get_next_from_coin_spend`, which only catches `ValueError`, not `RecursionError`): [4](#0-3) .

### Recommendation
Add an explicit maximum-depth counter (or iterative rewrite using an explicit work-list/stack, similar to the pattern already used in `sha256_treehash` for the same class of concern: [5](#0-4) ) to `PuzzleWithRestrictions.from_memo()` and reject memos whose `MofN` nesting exceeds a small, protocol-appropriate bound. Additionally, wrap calls such as `get_next_from_coin_spend()` to catch `RecursionError` (or pre-validate nesting depth before recursing) so a malformed/malicious memo cannot abort caller processing loops that walk many coins/spends.

### Proof of Concept
Conceptually (cannot be executed in this read-only environment):
1. Build a nested `MofNHint` program of depth N (e.g., N = 5000) using cheap CLVM cons construction: `MofN(m=1, members=[MofN(m=1, members=[... depth N ...])])`, each wrapped in the expected `PuzzleWithRestrictions` memo shape shown in `memo()` ( [6](#0-5) ).
2. Craft (or reuse) a puzzle whose `CREATE_COIN` condition emits this nested structure as its memo, spend it as an ordinary, valid transaction.
3. Have a wallet/pool client observe the resulting coin and invoke `PlotNFT.get_next_from_coin_spend()` (or any other caller of `PuzzleWithRestrictions.from_memo()`) on it, at which point the recursive parse in lines 282-286 raises `RecursionError`, uncaught by the surrounding `except ValueError` handler, crashing/aborting that processing path.

Note: I could not fully verify every call site's exception-handling behavior (e.g. `wallet_state_manager.py`, `cr_cat_drivers.py`, `vc_wallet.py` also reference `from_memo`/`from_program`), so the precise blast radius (which specific wallet sync loops would fully crash vs. skip-and-continue) is not fully confirmed within this read-only review.

    @classmethod
    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
            puzzle=puzzle,
            additional_memos=additional_memos,
        )
