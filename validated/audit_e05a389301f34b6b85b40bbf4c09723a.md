### Title
Missing lower-bound check on `Participant` index allows index 0 to reach `ThresholdView` / `verification_share`, causing a panic (denial of service) - (File: crypto/frost/src/sign.rs)

### Summary
The reference bug class is "mishandled input type → remote crash via crafted input." The analog in Serai's FROST signing path is a missing lower-bound validation on attacker-supplied `Participant` indexes: `sign()` rejects indexes `> n` but never rejects `0`, which is an invalid participant index (participants are `1..=n`). A participant 0 preprocess flows into `ThresholdView`/`verification_share`, which is built around `1..=n` indexing, producing an out-of-bounds/underflow panic — a remotely triggerable crash, and where wrapping arithmetic is used, an incorrectly computed Lagrange/verification-share mapping.

### Finding Description
`AlgorithmSignMachine::sign` builds `included` from the keys of the attacker-influenced `preprocesses: HashMap<Participant, Preprocess>` and validates only:

- `included.len() >= t` (crypto/frost/src/sign.rs:298)
- `included.last() <= n` (crypto/frost/src/sign.rs:302)
- no adjacent duplicates (crypto/frost/src/sign.rs:306-310)

There is no check that every `Participant` is `>= 1`. `Participant(0)` satisfies all three checks, so execution proceeds to:

- `self.params.keys.view(included.clone()).unwrap()` (crypto/frost/src/sign.rs:312) — `ThresholdView` is constructed over a set containing index 0, which has no corresponding key share.
- `validate_map` (crypto/frost/src/lib.rs:50-72) — only enforces presence of map keys for each included index; `Participant(0)` keyed data passes.
- In `complete()`, `self.view.verification_share(*l)` is called for each `l` in `included` (crypto/frost/src/sign.rs:475-479). Verification shares are stored for participants `1..=n` and are conventionally indexed as `shares[i - 1]`; `i = 0` underflows to index `u16::MAX`/`usize::MAX`, panicking on out-of-bounds access. Similarly, Lagrange interpolation over a zero index computes `x_j - 0` / `0 - x_j` factors, which panics in debug builds or produces a garbage coefficient in release builds.

The same gap exists on the second-round path: `complete()` calls `validate_map(&shares, self.view.included(), ...)` and then iterates `self.view.included()` calling `verification_share(*l)` — but shares are keyed by the same attacker-controlled `Participant` values that were accepted in round one.

Callers upstream (`batch_signer.rs`, `signer.rs`, `cosigner.rs`, `slash_report_signer.rs`) deserialize peer preprocess/shares and pass the `HashMap<Participant, _>` keys directly into `sign()`/`complete()`, mapping only `FrostError` variants — a `panic` propagates and kills the task/process rather than yielding an `InvalidParticipant` error.

### Impact Explanation
An unprivileged participant (or anyone able to inject a preprocess/share keyed under `Participant(0)` into the preprocess map) can crash a validator's signing routine during any signing session — the USB-dissector analog of "crafted packet → application crash." Because the panic occurs inside `sign()`/`complete()` rather than returning a `FrostError`, the blame/attribution path (`InvalidPreprocess`/`InvalidShare`) is bypassed: the malicious participant cannot be identified, and the signing attempt aborts. Repeated per attempt, this is a persistent denial of service against threshold signing (batch signing, cosigning, slash reports). In release builds with wrapping arithmetic, index 0 instead produces a wrong Lagrange coefficient / wrong verification share — an incorrect verifier formula rather than a clean rejection.

### Likelihood Explanation
Reachability is high: the preprocess map keys are fully attacker-controlled serialized `Participant` values, and no layer between the network deserialization and `view()`/`verification_share()` filters `0`. The check at sign.rs:302 only bounds the maximum (`included[included.len()-1]`), and the duplicate scan only compares adjacent sorted entries; `0` sorts first and escapes both. The only precondition is participation in (or injection into) a signing session's preprocess round, which any signer can do.

### Recommendation
Reject `Participant(0)` alongside the upper bound, e.g.:

```rust
// crypto/frost/src/sign.rs, in sign(), after sorting `included`
if included[0] == Participant::ZERO /* u16 == 0 */ {
  Err(FrostError::InvalidParticipant(multisig_params.n(), included[0]))?;
}
```

Equivalently, enforce `1 <= i <= n` inside `ThresholdParams`/`ThresholdView::new` and inside `dkg`'s `lagrange`/`verification_share` so all callers share the invariant, and make `validate_map` assert the key range. Return `FrostError::InvalidParticipant` (never panic) so upstream callers can attribute blame.

### Proof of Concept
Within a signing session for `ThresholdParams { t, n, i }`, a malicious signer broadcasts a preprocess message keyed under `Participant(0)` (valid encodings of `Commitments` so `read_preprocess` succeeds, since `Commitments::read` never inspects the map key — crypto/frost/src/sign.rs:276-281, crypto/frost/src/nonce.rs:133-139).

1. Honest signer collects preprocesses into `HashMap<Participant, Preprocess>` including key `0`.
2. `sign()`: `included = [0, ..., i]` sorted; `0 <= n` passes (line 302), no duplicate passes (306-310), `len >= t` passes.
3. `keys.view(included)` (line 312) constructs a view including participant 0; `validate_map` passes since the map contains key 0.
4. Signing produces a share; in `complete()`, `self.view.verification_share(Participant(0))` (line 477) indexes verification shares at `0 - 1` → panic (or wrapped OOB), crashing the caller — the crafted-input crash analog of CVE-2016-5354.

Uncertainty note: the exact panic site (`view()` vs. `verification_share()` vs. `lagrange()` inside `crypto/dkg`) could not be fully confirmed in this pass because the `dkg` internals weren't read in detail, but every index-0 path through `sign.rs` either panics or produces an incorrect coefficient rather than a clean `FrostError`. pub fn validate_map<T>(
  map: &HashMap<Participant, T>,
  included: &[Participant],
  ours: Participant,
) -> Result<(), FrostError> {
  if (map.len() + 1) != included.len() {
    Err(FrostError::InvalidParticipantQuantity(included.len(), map.len() + 1))?;
  }

  for included in included {
    if *included == ours {
      if map.contains_key(included) {
        Err(FrostError::DuplicatedParticipant(*included))?;
      }
      continue;
    }

    if !map.contains_key(included) {
      Err(FrostError::MissingParticipant(*included))?;
    }
  }

  Ok(())
