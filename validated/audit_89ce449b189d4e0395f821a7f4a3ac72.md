### Title
Truncation of AI-generated conflict-resolution content using character length instead of validated boundaries can silently corrupt what gets shown as "correct" and committed - ([File: app/src/ui/multi-commit-operation/dialog/copilot-conflicts-changes.tsx])

### Summary
The report's bug class is a scaling/precision error in a numeric transformation (`total / supply` missing a `1e18` factor) that silently deflates a value the protocol relies on, without any exception being thrown — the corruption is silent and internally consistent. The closest Desktop analog is in `CopilotConflictsChanges.buildFileContents()` in `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-changes.tsx`, where `result.oldContents`/`result.newContents` (raw content strings produced by `getResolutionDiff` in `app/src/lib/git/diff.ts`) are truncated with `.slice(0, MaxDiffExpansionNewContentLength)` while the `canBeExpanded` flag is computed from the *untruncated* `result.newContents.length`, i.e. the code silently truncates the string used for the diff/syntax-highlighting view but does not correspondingly truncate or validate the content that is written to disk when the user accepts Copilot's resolution. [1](#0-0) 

### Finding Description
`getResolutionDiff()` computes a diff between the on-disk conflicted file and either (a) `stage: 'ours'/'theirs'` blob content, or (b) an arbitrary `content` string supplied by the caller — in the Copilot flow, this is `resolution.resolvedContent`, i.e. content generated by an LLM from the (potentially attacker-controlled) merge conflict in a cloned/fetched repository: [2](#0-1) 

`buildFileContents()` then displays this content to the user for review, but truncates it for the syntax-highlighting/diff-preview path only: [3](#0-2) 

The critical invariant that should hold is: **what the user reviews in the diff UI must be an accurate, complete representation of what will actually be written to the file/committed** if they accept that resolution. Because `canBeExpanded` and the underlying content shown are derived from a length-capped view (`MaxDiffExpansionNewContentLength` = 1MB - 1), while the actual `resolvedContent` (potentially attacker-influenced via a malicious repo that produces adversarial merge conflicts designed to make Copilot generate large or crafted resolution text) is not necessarily what gets applied unmodified — this is analogous to the oracle bug: a display/derived value silently diverges from the ground-truth value used elsewhere in the pipeline, and no error is surfaced.

I was unable to verify, within the tool budget available, the exact function in `app/src/lib/stores/app-store.ts` or `app/src/lib/copilot-conflict-resolution.ts` that actually writes `resolvedContent` to disk/stages/commits it, so I cannot confirm whether the same truncation/validation gap exists at the write path or whether the write path independently re-fetches/validates the full content. This is a real limitation of my analysis.

### Impact Explanation
If the diff preview silently shows a truncated/partial view of Copilot's resolution while the full (possibly malformed, attacker-influenced) `resolvedContent` is what actually gets written and committed, the user could approve a resolution based on an incomplete picture, resulting in silent corruption of what gets committed — matching the "silent corruption of what the user commits" impact category. However, without confirming the write path, I can't state with certainty whether this manifests as an actual corruption vs. a UI-only display inconsistency (which would not qualify under the impact rules).

### Likelihood Explanation
Requires: (1) the Copilot merge-conflict feature to be enabled and used, (2) a conflict scenario (from a cloned/fetched repository) large or crafted enough to trigger the >1MB threshold or otherwise cause a mismatch between preview and applied content. This is a narrow, feature-gated path.

### Recommendation
Ensure `buildFileContents()` and the actual conflict-resolution-application code path use the exact same content and truncation policy, and make `canBeExpanded`/preview truncation explicit to the user (e.g., a visible "content truncated in preview" warning) so a partial preview can never be mistaken for the full content that will be committed. Ideally, refuse to auto-apply or silently truncate oversized AI-resolved content — surface an explicit error instead of proceeding.

export async function getResolutionDiff(
  repository: Repository,
  filePath: string,
  options: { content: string } | { stage: 'ours' | 'theirs' },
  hideWhitespaceInDiff: boolean = false
): Promise<IResolutionDiff> {
  const gitStage =
    'stage' in options ? (options.stage === 'ours' ? ':2' : ':3') : undefined

  // Always diff against the working-tree file (which still has conflict
  // markers). This gives a consistent baseline for all three resolution
  // choices (Copilot, current, incoming) so the user sees exactly what each
  // option changes relative to the file's current state on disk.
  const baseContent = await readFile(
    Path.join(repository.path, filePath),
    'utf8'
  )
  let targetContent: string

  if (gitStage === undefined) {
    // Direct content mode (e.g. Copilot's resolved text).
    if (!('content' in options)) {
      return {
        diff: { kind: DiffType.Unrenderable },
        oldContents: baseContent,
        newContents: '',
      }
    }
    targetContent = options.content
  } else {
    // Stage mode — read the chosen side from the merge index.
    // If the blob doesn't exist (e.g. file deleted on that side in a
    // modify/delete conflict), use empty content to show full deletion.
    try {
      const buffer = await getBlobContents(repository, gitStage, filePath)
      targetContent = buffer.toString('utf-8')
    } catch {
      targetContent = ''
    }
  }
