Based on my review, the exact attack framing in the question doesn't match the code's actual execution order (mint happens *before* the calldata dispatch, not after), but the code does contain a genuine non-atomicity bug in the opposite direction that produces a more serious result: **duplicate minting via replay**, in direct violation of the protocol's own documented invariant for `IsmpModule::on_accept`.

### Title
Non-atomic `on_accept`: irreversible token mint/transfer precedes fallible calldata dispatch, enabling duplicate settlement via message replay - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`Pallet::on_accept` credits the beneficiary (mint or escrow-release) **before** executing the optional `call_data` runtime call. [1](#0-0) 
If the subsequent signed dispatch of the attacker-supplied `runtime_call` fails for any reason (bad origin, insufficient balance, filtered call, decode error, etc.), the error propagates via `?` and the whole `on_accept` returns `Err`. [2](#0-1) 

### Finding Description
`pallet-ismp`'s own documentation states the exact invariant this code violates: *"if `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be replayed... the `IsmpModule` is responsible for maintaining all invariants before modifying its internal state to prevent partial state changes."* [3](#0-2) 
and again: *"you should ensure irreversible state changes occur only after a message effectively meets all success criteria."* [4](#0-3) 

The request handler explicitly deletes the receipt whenever a module's `on_accept` returns `Err`, and this happens per-message inside a `Vec` of results — an individual message failure does **not** make the enclosing `handle()` call return `Err` overall: [5](#0-4) 

Because the top-level extrinsic that invokes this batch handler still returns `Ok`, FRAME's automatic extrinsic-level storage-transaction rollback is never triggered — that rollback only fires when the dispatchable itself returns a `DispatchError`. I found no `with_transaction`/`storage_layer`/`#[transactional]` wrapping around the individual `cb.on_accept(...)` call in `modules/ismp/core/src/handlers/request.rs`, nor in `modules/pallets/ismp/src/lib.rs`. That means the mint/transfer performed inside `on_accept` before the failing call-data dispatch is **not rolled back**, while the request's receipt is deleted, making the identical request eligible for replay via `pallet-ismp`'s existing request-handling flow (same membership proof, since the request was never marked as delivered).

An attacker who is the beneficiary of a cross-chain `send()` (or who controls the destination `call_data` field, which is attacker/sender-supplied per `SendParams.call_data`) can craft `substrate_data.runtime_call` to be a call that is guaranteed to fail when dispatched under `RawOrigin::Signed(beneficiary)` — e.g. a call requiring `EnsureRoot`, or a `transfer` that will underflow, or simply garbage that still SCALE-decodes into some `RuntimeCall` variant but reverts at execution. Each time the relayer/attacker resubmits the same request:
1. `mint_into`/`transfer` to `beneficiary` executes and succeeds again (line 93-117).
2. The deliberately-failing `runtime_call.dispatch(...)` fails, `on_accept` returns `Err`.
3. `pallet-ismp` deletes the just-stored receipt, leaving the request re-deliverable.

Repeating this drains/duplicates the source-chain-locked or minted supply, since a single source-chain `send()` message can be "delivered" — and its beneficiary credited — an unbounded number of times before the request eventually times out.

### Impact Explanation
This is a **duplicate settlement / unauthorized token minting** bug matching the bounty's "duplicate/double-settlement" and "stealing or loss of funds" categories. A single locked/burned amount on the source chain can be minted/released to the beneficiary multiple times on the destination chain, directly inflating supply or draining escrow beyond what was ever locked.

### Likelihood Explanation
High: the `call_data` field is fully attacker-controlled (any sender of `send()` sets it, and the beneficiary is also attacker-controlled), no privileged access is required, and crafting a runtime call that reliably fails dispatch (e.g. targeting a filtered or root-only call, or one with a guaranteed-false precondition) is trivial. The only requirement is that message delivery/replay via `pallet-ismp` remains possible before the request times out — which is the documented behavior of the protocol for any failed `on_accept`.

### Recommendation
Perform all state-committing effects (mint/transfer to beneficiary) **atomically with** the optional calldata dispatch, or defer the mint until after the calldata dispatch succeeds. Concretely:
- Validate/dispatch `runtime_call` first, and only mint/transfer funds to `beneficiary` after the calldata dispatch succeeds, or
- Wrap the entire body of `on_accept` (mint + calldata dispatch) in an explicit `frame_support::storage::with_transaction` (or equivalent) so that any `Err` returned from the function guarantees all storage writes made within it — not just those after the failure point — are rolled back, consistent with the "all invariants before modifying internal state" requirement documented by `pallet-ismp`.

### Proof of Concept
1. Register a non-native asset and have `ALICE` `send()` `SEND_AMOUNT` to `beneficiary` on `StateMachine::Kusama(100)`, escrowing/burning funds on the source side (mirrors `should_receive_asset_with_calldata` test setup). [6](#0-5) 
2. Build a `Message` whose `data` is a `SubstrateCalldata` with `signature: None` (so origin is derived directly from `message.from`) and `runtime_call` set to a call that is guaranteed to fail under `RawOrigin::Signed(beneficiary)` (e.g. `EnsureRoot`-only call, or a `Balances::transfer_allow_death` with an amount that always underflows the account).
3. Call `module.on_accept(post.clone())` — observe: (a) it returns `Err`, but (b) `beneficiary`'s balance already reflects the minted/transferred `amount` (assert balance changed despite the `Err` return).
4. Call `module.on_accept(post.clone())` again with the identical `post` (since `pallet-ismp`'s handler deleted the receipt on the prior failure, per `modules/ismp/core/src/handlers/request.rs` lines 122-125) — observe the beneficiary's balance increases a second time from a single original locked amount, demonstrating duplicate settlement.
