### Title
Missing participant-index bounds check causes panic on crafted blame accusation - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
The hostapd CVE-2026-58374 is a missing bounds check: a wire-parsed `link_id` of 15 is used to index a table that only has valid entries for 0–14, corrupting memory / killing the process. The Serai analog is the same shape: a `Participant` parsed from attacker-controlled bytes is only validated as non-zero, then used as a direct map index in the PedPoP blame path. `BlameMachine::blame` / `AdditionalBlameMachine::blame` pass attacker-influenced `sender` and `recipient` values into `blame_internal`, which indexes `self.commitments[&sender]` (and, via `Decryption::decrypt_with_proof`, `self.enc_keys[&decryptor]`) with no check that the participant was actually registered. Any out-of-range index (e.g. `n+1` … `u16::MAX`, or simply a participant that never sent commitments) hits a `HashMap` index panic, terminating the process — the same "parsed index exceeds valid table → crash" failure as the hostapd bug.

### Finding Description
- `Participant::new` accepts **any** non-zero `u16`, so a parsed value of e.g. 15 (or 65535) is a perfectly valid `Participant` even when `n = 4`. [1](#0-0) 
- `BlameMachine::blame` takes `sender` and `recipient` from the caller (which feeds them from deserialized accusation messages) and calls `blame_internal` without verifying either is a member of the DKG. [2](#0-1) 
- `blame_internal` unconditionally indexes `self.commitments[&sender]` — an absent key panics. [3](#0-2) 
- Independently, `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]`, which panics when `decryptor` was never registered (any participant index outside the registered set). [4](#0-3) 

The accusation path is reachable with public inputs: the accuser submits an `InvalidDkgShare`-style message carrying arbitrary `sender`/`faulty`/`accuser` participant fields (Participant is deserialized from 2 raw bytes with only a non-zero check, see the `borsh`/`read` paths in `crypto/dkg/src/lib.rs:121-125`). Nothing between byte-parsing and the map indexing bounds the value to `1..=n` or to the registered set. Unlike the rest of the stack — `ThresholdParams::new` enforces `i <= n` and `ThresholdKeys::view`/`sign` check `included.last() <= n` — the blame path performs no equivalent check.

### Impact Explanation
A single crafted accusation containing an out-of-range `sender` (or a `decryptor`/`recipient` index not present in `enc_keys`) triggers a panic inside `blame_internal` / `decrypt_with_proof`, crashing the host process before the blame can be adjudicated. This is a pre-verification, unauthenticated-range denial of service of any node evaluating blame — mirroring the CVE's confirmed impact of process termination before the handshake completes.

### Likelihood Explanation
Any party able to submit a blame/accusation message (a DKG participant or an accuser relayed by the protocol) controls the two-byte participant fields. `Participant::new(u16)` only rejects `0`, so `n+1` through `65535` all pass parsing, and `blame` performs no membership check before indexing. Triggering it requires no credentials, collusion, or valid share — just one malformed index.

### Recommendation
Bounds-check participant indexes at the trust boundary, the same way `ThresholdParams::new` does: before `blame_internal`/`decrypt_with_proof` index their maps, verify `sender <= n`, `recipient <= n`, and that both keys exist (`commitments.get(&sender)`, `enc_keys.get(&decryptor)`), returning `Err`/a defined faulty-party result instead of panicking. Consider also enforcing `participant <= n` inside the deserialization path or at `blame()` entry.

### Proof of Concept
```rust
// After a PedPoP DKG completes for params n=4, t=3 (a BlameMachine or
// AdditionalBlameMachine exists), an accuser submits an accusation where the
// 'faulty'/'sender' field is a parsed Participant with index 15 (or 65535),
// which is never in `commitments` (only indexes 1..=4 were registered).

let sender = Participant::new(15).unwrap();      // parses fine: only 0 is rejected
let recipient = Participant::new(2).unwrap();

// EncryptedMessage::read'd from attacker-influenced bytes, or any stored msg:
// blame() -> blame_internal() -> self.commitments[&sender]
//   -> HashMap index panic: "no entry found for key" -> process abort
blame_machine.blame(sender, recipient, msg, proof);
// Similarly: a registered sender but recipient=15 reaches
// decrypt_with_proof -> self.enc_keys[&decryptor] -> panic.
```

Caveat: exploitability end-to-end depends on the coordinator/substrate layer forwarding attacker-supplied `Participant` values into `blame()`; the tributary transaction reader (`coordinator/src/tributary/transaction.rs`) does parse `accuser`/`faulty` from raw bytes with only the non-zero check, but the exact dispatch into `BlameMachine::blame` is outside the in-scope crates and was not fully verified.
