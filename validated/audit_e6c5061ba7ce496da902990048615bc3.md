### Title
Native-token relayer-fee overpayment is permanently trapped in `EvmHost` due to misuse of `swapETHForExactTokens` refund semantics - (`File: evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and the fee-increase path all convert user-supplied native token into the protocol `feeToken` via Uniswap V2's `swapETHForExactTokens`, using `msg.value` as the maximum spend and `post.fee`/`get.fee` as the exact output amount. This is the correct "exact-out" direction of the curve-pool misuse pattern described in the source report, but the code fails to account for the router's own refund semantics: `swapETHForExactTokens` refunds unspent ETH to its **caller**, which is `EvmHost` itself, not the end user who sent the transaction. There is no code path in `EvmHost` that forwards this refunded ETH back to `_msgSender()`/`post.payer`.

### Finding Description [1](#0-0) 
and [2](#0-1) 

Both dispatch functions do:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

`swapETHForExactTokens` computes the amount of ETH actually required to buy exactly `post.fee`/`get.fee` units of `feeToken`, spends that amount, and — per the standard Uniswap V2 router implementation — refunds any leftover `msg.value` to `msg.sender`. Here `msg.sender` (from the router's perspective) is `EvmHost`, because `EvmHost` is the contract that called the router with `{value: msg.value}`. The refunded ETH therefore lands back in `EvmHost`'s own balance rather than being returned to the original transaction sender (`_msgSender()`) or the `payer` recorded in `FeeMetadata`.

There is no accounting or sweep mechanism visible in these functions (or in the surrounding contract, per the code reviewed) that tracks this residual native balance and returns it to the user who overpaid. Since off-chain callers estimate the ETH needed for a target fee amount using a price quote that can drift between quoting and execution (the same "amount to send is not carefully bound to a swap outcome" class of bug as the reported curve-pool misuse), users routinely send `msg.value` slightly above what's strictly required as a safety margin — and that margin is silently absorbed by the contract instead of refunded.

This mirrors the root cause in the external report: the code treats the swap's input/output relationship as a black box and does not correctly handle the excess-value outcome of the swap call, producing predictable, permanent value loss for the caller.

### Impact Explanation
Any unprivileged user who calls `dispatch(DispatchPost)` or `dispatch(DispatchGet)` (or the fee-bump function following the same pattern) with `msg.value` greater than the exact ETH cost of the requested `feeToken` amount permanently loses the difference — it is not credited to their request, not refunded, and not recoverable through any user-facing function shown in this contract. Over time this accumulates unswept, unaccounted-for ETH inside `EvmHost`, representing a genuine "loss of funds, but doesn't lose value for the protocol" class of impact for every affected caller, with no privileged action required to trigger it — it happens on ordinary usage.

### Likelihood Explanation
High. Any dApp or SDK integration that pays relayer fees in native token and estimates `msg.value` off-chain (a normal, encouraged pattern per the "Payment Methods" documentation) will occasionally overshoot the exact swap requirement due to price movement between quote and execution. No attacker action or malicious actor is needed — this triggers under completely benign, expected usage of a public entrypoint.

### Recommendation
After calling `swapETHForExactTokens`, refund any leftover native balance attributable to the caller's overpayment back to `_msgSender()` (or `post.payer`/`get`'s payer) rather than allowing it to be retained by `EvmHost`. Alternatively, require `msg.value` to exactly match the router's precomputed input amount (via `getAmountsIn`) before executing the swap, rejecting any overpayment up front so users can retry with the exact figure.

### Proof of Concept
1. Off-chain, a caller quotes that `X` wei of ETH is needed to obtain `post.fee` units of `feeToken` via `uniswapV2.getAmountsIn`.
2. Due to normal price movement/slippage margin, the caller submits `dispatch(DispatchPost)` with `msg.value = X + delta` (delta as a safety buffer, e.g. 1-2%).
3. Inside `dispatch`, `swapETHForExactTokens{value: X + delta}(post.fee, path, address(this), block.timestamp)` executes, spending only the true required amount `X' <= X` and refunding `X + delta - X'` in ETH — but that refund is paid to `address(this)` (`EvmHost`), since `EvmHost` was the caller of the router.
4. `EvmHost` performs no further logic with this refunded balance; it is neither tracked, emitted, nor returned to the caller.
5. Repeated calls by any number of unprivileged users accumulate untracked ETH inside `EvmHost` that is unrecoverable by those users, confirming permanent fund loss without any privileged, relayer, or attacker involvement.
