### Title
Unchecked multi-byte length-prefix read in CLVM canonical-encoding check causes out-of-bounds read on attacker-supplied spend bundle — (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` decodes a CLVM atom's variable-length size prefix (1–6 bytes) by repeatedly indexing into the raw `clvm_buffer` for `prefix_len` additional bytes, with no check that those bytes actually exist within the buffer before reading them [1](#0-0) . This mirrors the CVE-2024-32620 bug class: a length-decoding routine (`H5F_addr_decode_len`) that advances a cursor and dereferences bytes for a multi-byte length field without first validating that the underlying buffer has enough remaining bytes, causing an over-read.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` inspects the tag byte at `offset` to determine how many additional length-prefix bytes (`prefix_len`, 0–5) follow, then loops `prefix_len` times incrementing `offset` and reading `clvm_buffer[offset]` each iteration [2](#0-1) . There is no bounds check comparing `offset + prefix_len` against `len(clvm_buffer)` before or during this loop. The caller, `is_clvm_canonical()`, walks an entire serialized CLVM program (puzzle reveal or solution) byte-by-byte using the same unchecked pattern, advancing `offset` by the atom length returned from `is_atom_canonical` without verifying it stays within the buffer [3](#0-2) . If a submitted CLVM buffer ends with a truncated multi-byte atom-length tag (e.g., the final byte is `0xFC`/`0xF8`/`0xF0`/`0xE0`/`0xC0` indicating a 2–6 byte prefix, but fewer trailing bytes actually remain), the read loop indexes past the end of `clvm_buffer`.

This function is used by the mempool manager to determine DEDUP eligibility of coin spends (`eligible_for_dedup`) referenced throughout `chia/full_node/mempool_manager.py` and `chia/types/mempool_item.py` [4](#0-3) , meaning it processes puzzle-reveal/solution bytes taken directly from spend bundles submitted by any unprivileged network participant during mempool admission.

In Python, indexing a `bytes` object past its end raises an unhandled `IndexError` rather than corrupting adjacent heap memory the way the C-based HDF5 bug does — there is no memory-safety/RCE equivalent in this managed-runtime context. The concrete effect is a crash of whatever code path invoked the canonical-encoding check on an untrusted, truncated CLVM buffer.

### Impact Explanation
If `is_clvm_canonical`/`is_atom_canonical` is invoked on attacker-controlled puzzle-reveal or solution bytes without the caller catching `IndexError`, a single malformed spend bundle can raise an unhandled exception during mempool processing. Depending on where this exception propagates, it could disrupt spend-bundle admission processing for the full node handling it — a spend-triggered transaction-processing halt, which is one of the explicitly accepted impact categories. This is a Denial-of-Service class issue, not a coin-theft, inflation, or consensus-divergence issue, since Python's memory safety prevents the "corruption of the instruction pointer" outcome described in the original HDF5 CVE.

### Likelihood Explanation
Likelihood depends on whether any call site of `is_clvm_canonical` lacks exception handling around untrusted spend-bundle bytes. I was only able to confirm the function's definitions and their use in `eligible_for_dedup` bookkeping within `chia/full_node/mempool_manager.py`; I was not able to fully trace whether the exact call site that invokes `is_clvm_canonical(bytes(spend.puzzle_reveal))` on freshly-submitted, unvalidated spend bundles is wrapped in exception handling, due to the limited number of tool iterations available. This is a meaningful gap: without confirming an unguarded call path, I cannot assert the crash is definitely reachable in production versus already caught elsewhere.

### Recommendation
Add explicit bounds checks in `is_atom_canonical` before each `clvm_buffer[offset]` access inside the `prefix_len` loop (and in the initial `clvm_buffer[offset]` read in `is_clvm_canonical`), returning "not canonical" or raising a handled `ValueError` when the buffer is too short — mirroring the defensive pattern already used in `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list` functions, which check `len(buf)` before consuming length-prefixed fields [5](#0-4) . Additionally, verify that any call site processing untrusted spend-bundle bytes wraps calls to `is_clvm_canonical` in a try/except that treats malformed input as "not canonical" / rejects the spend, rather than letting exceptions propagate.

### Proof of Concept
```python
from chia.full_node.mempool_manager import is_clvm_canonical

# 0xFC tag byte declares a 6-byte-prefix atom (5 additional length bytes required),
# but the buffer is truncated to only 2 bytes total.
truncated_buf = bytes([0xFC, 0x01])
is_clvm_canonical(truncated_buf)  # raises IndexError instead of returning False
```
Submitting a spend bundle whose puzzle reveal or solution ends in such a truncated multi-byte atom tag would trigger this unhandled `IndexError` wherever `is_clvm_canonical` is invoked on it during mempool eligibility checks [6](#0-5) .

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value


def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)

def skip_bytes(buf: memoryview) -> memoryview:
    if len(buf) < 4:
        raise ValueError(f"byte length prefix requires 4 bytes, remaining buffer {len(buf)}")
    n = int.from_bytes(buf[:4], "big", signed=False)
    buf = buf[4:]
    if n > len(buf):
        raise ValueError(f"byte length {n} exceeds remaining buffer {len(buf)}")
    return buf[n:]
