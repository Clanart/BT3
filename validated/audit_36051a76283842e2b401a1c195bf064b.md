## Analysis

The bug-class seed (SWC "unchecked return value on `transfer`/`transferFrom`") maps directly onto `evm/tron/contracts/apps/IntentGatewayV2.sol`, the Tron variant of the EVM `IntentGatewayV2` contract. Its EVM/mainline sibling (`evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`) consistently uses `SafeERC20.safeTransfer`/`safeTransferFrom`, which reverts unless the token's return data explicitly decodes to `true` (or the call has no return data at all, per OZ semantics). ### Title
Unchecked ERC20/TRC20 transfer return value in escrow withdrawal permanently burns beneficiary funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` releases escrowed intent funds to the `beneficiary` using `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only checks the low-level `success` flag, not the ABI-decoded boolean the ERC20 standard specifies as the actual transfer result.

### Finding Description
Solidity's low-level `.call` returns `success = true` as long as the target contract does not revert — it says nothing about the semantic outcome encoded in the return data. Many real-world TRC20/ERC20 tokens (including several non-standard tokens historically deployed on Tron) return `false` on a failed `transfer` instead of reverting. In `withdraw()`, that `false` is silently discarded: `success` is still `true`, so the `if (!success) revert TransferFailed();` guard never triggers [5](#0-4) . Immediately after, the function unconditionally mutates settlement state as if the transfer succeeded: `_orders[body.commitment][token] -= amount;` and, at the top of the function, `_filled[body.commitment] = beneficiary;` [6](#0-5) . The same unchecked-boolean pattern appears in the `sweepDust`-style path that pays out via `req.beneficiary` [4](#0-3) , and in the transaction-fee payout at the end of `withdraw()` [3](#0-2) .

This is precisely the bug class from the external report: `transfer`/`transferFrom` results are not validated, so a token that signals failure via a `false` return (rather than a revert) leaves the intended recipient without funds while the protocol's internal books mark the obligation as settled. The sibling non-Tron contracts (`evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`) already use `SafeERC20.safeTransfer`, which does perform this check — confirming this is a local regression/divergence rather than an inherent design constraint.

### Impact Explanation
Once `withdraw()` runs against a token that returns `false` on transfer failure, `_orders[body.commitment][token]` is decremented and `_filled[body.commitment]` is set to the beneficiary, marking the order as fully and successfully redeemed. No follow-up path in the contract allows retrying or reclaiming an escrow once `_filled`/`_orders` has been updated. The escrowed tokens remain stranded in the contract with no beneficiary ever receiving them — permanent loss of bridged/escrowed user funds, triggered purely by normal (non-adversarial) execution against a token with non-reverting failure semantics. This satisfies the bounty's "stealing or loss of funds" and "false state acceptance" impact categories without requiring any malicious relayer, prover, or admin — an ordinary token behavior during a resolvable business flow (e.g., an allowance/balance edge case in the token that yields `false` rather than reverting) is enough.

### Likelihood Explanation
No privileged actor or malicious peer is required — the only precondition is that the escrowed/fee token used in an order returns `false` on transfer failure instead of reverting, a documented and known category of ERC20/TRC20 tokens (some TRC20 tokens on Tron notoriously deviate from strict EIP-20 semantics). The path is reached on every ordinary `RedeemEscrow`/`RefundEscrow` withdrawal and every dust sweep, i.e. the core, frequently-executed settlement flow of the gateway, making the likelihood of encountering an affected token nontrivial in production given open, permissionless token listing for intents.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` and the dust-sweep path with `IERC20(token).safeTransfer(beneficiary, amount)` (the `SafeERC20` library is already imported and `using SafeERC20 for IERC20;` is already declared in this file), mirroring the pattern already used in `IntentsBase.sol` and the non-Tron `IntentGatewayV2.sol`. This ensures both call-revert and boolean-return failures cause the whole withdrawal to revert before `_orders`/`_filled` state is mutated.

### Proof of Concept
1. An order escrows Token X (a TRC20 that returns `false`, not a revert, on failed `transfer`, e.g. due to a paused state, a per-tx transfer cap, or blacklist condition applied to the gateway or beneficiary).
2. The relevant response/timeout path calls `withdraw(body, isRefund)`.
3. Inside `withdraw()`: `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes; Token X's internal logic returns `abi.encode(false)` without reverting.
4. `success` is `true` (the call itself did not revert), so `if (!success) revert TransferFailed();` at line 698 does not fire.
5. `_orders[body.commitment][token] -= amount;` executes, and `_filled[body.commitment]` was already set at function entry — the order is now permanently marked settled.
6. `beneficiary` never received the tokens; the tokens remain locked in the `IntentGatewayV2` contract with no remaining code path to recover them.
