### Title
JSON parser recursion-depth check is performed with an off-by-one comparison, allowing one extra level of nesting beyond `RecursionLimit` - (File: `csharp/src/Google.Protobuf/JsonParser.cs`)

### Summary
The Sherlock report describes a "check-then-mutate" ordering/boundary defect: `LiquidityBorrowingManager.sol` checks `allUserBorrowingKeys.length > MAX_NUM_USER_POSOTION` *before* pushing a new entry, so the guard is evaluated against the pre-mutation count with a strict `>` rather than `>=`, letting one extra element through before the limit takes effect. The same class of defect — a guard checked with the wrong boundary before the counter is incremented, permitting exactly one unit of overshoot — exists in the C# ProtoJSON recursion-depth guard in `JsonParser.Merge`.

### Finding Description
`JsonParser.Merge` enforces the JSON recursion limit like this: [1](#0-0) 

`tokenizer.RecursionDepth` is a plain `int` property, defaulting to `0`, that is only mutated by this method: [2](#0-1) 

The check `if (tokenizer.RecursionDepth > settings.RecursionLimit)` is evaluated on the *current* depth (before the `++`), using a **strict `>`**. Tracing an actual nested call sequence with `RecursionLimit = N`:
- At the call where `RecursionDepth == N` (i.e., the parser has already descended `N` levels), the check evaluates `N > N` → `false`, so the guard does **not** fire.
- The method then executes `tokenizer.RecursionDepth++`, bringing the depth to `N + 1`, and proceeds to parse yet another nested object/array at that depth.
- Only on the *next* call, when `RecursionDepth == N + 1`, does `N + 1 > N` become `true` and the exception fire.

This is structurally identical to the Sherlock finding's failed invariant: the enforcement check is evaluated against the pre-increment state with a boundary condition (`>` instead of `>=`) that lets the guarded counter cross the intended limit by exactly one before the check can reject it. In the Solidity report, `allUserBorrowingKeys.length > MAX_NUM_USER_POSOTION` should have been `>=` (or the push should have preceded the check); here, `RecursionDepth > settings.RecursionLimit` should have been `>=` (or the increment should have preceded the check), for the same reason — the mutation that the check is meant to gate happens strictly after the check reads the stale value.

By contrast, other recursion guards in the same codebase correctly avoid this off-by-one: e.g. the C++ `CodedInputStream`/`ParseContext` and TextFormat parsers decrement/consume the budget *before* comparing to the terminal boundary (`--recursion_limit_ < 0`, `--depth_ < 0`), so the exact configured limit is enforced with no slack: [3](#0-2) [4](#0-3) 

The C# ProtoJSON path instead performs the comparison strictly before mutating, on the wrong side of the boundary, producing the overshoot.

### Impact Explanation
An attacker who controls a bounded ProtoJSON payload sent to a public `JsonParser.Parse`/`Merge` API can nest one JSON level deeper than the configured `RecursionLimit` (default is a fixed value used by all callers of `Settings.Default`) before `InvalidProtocolBufferException.JsonRecursionLimitExceeded()` is thrown. This is a pure boundary/off-by-one defect: the parser's recursion-depth accounting undercounts by one relative to the actual call-stack depth reached, so the enforced limit is effectively `RecursionLimit + 1`, not `RecursionLimit`. It does not by itself cause unbounded resource exhaustion or stack overflow (per the analog rules, unbounded-allocation/resource-exhaustion analogs are excluded and this is only a one-unit overshoot, not an unbounded one), but it is a genuine correctness/security-invariant violation: the API contract of `RecursionLimit` (the maximum nesting depth the caller has decided is safe) is silently violated by exactly one level for every parse, which can matter for callers that rely on the documented limit as a hard security boundary (e.g., depth-sensitive validation, defense-in-depth against stack exhaustion at a precisely tuned limit).

### Likelihood Explanation
High likelihood of triggering: any ProtoJSON input with nesting depth of `RecursionLimit + 1` (attacker-controlled, ordinary bounded JSON, no privileged access needed) deterministically reaches the one-level overshoot before the exception fires. The condition is purely a function of nesting depth in the JSON text, which is fully attacker-controlled via the public JSON parsing API (`JsonParser.Parse`).

### Recommendation
Change the check in `JsonParser.Merge` (`csharp/src/Google.Protobuf/JsonParser.cs`) from:
```csharp
if (tokenizer.RecursionDepth > settings.RecursionLimit)
```
to:
```csharp
if (tokenizer.RecursionDepth >= settings.RecursionLimit)
```
so the guard fires before the depth is allowed to exceed the configured limit, matching the pattern used elsewhere in the codebase (`--depth_ < 0`, `--recursion_limit_ < 0`) where the check and the mutation are consistent and no off-by-one slack exists.

### Proof of Concept
Given `JsonParser.Settings.Default.RecursionLimit = N`, construct a JSON document consisting of `N + 1` nested objects, e.g. (conceptually) `{"a":{"a":{"a": ... N+1 times ... }}}` mapped onto a self-referential message schema, and call:
```csharp
JsonParser.Default.Parse<MyMessage>(jsonWithNPlusOneNestedLevels);
```
Tracing `Merge` calls: at nesting level `N` (i.e., the `N`-th recursive call to `Merge`), `tokenizer.RecursionDepth == N` when the check runs, `N > N` is `false`, so parsing proceeds into level `N + 1` before the exception is finally raised on the following call. This demonstrates that the parser permits recursion depth `N + 1` even though `RecursionLimit` was set to `N`, confirming the off-by-one bypass. Full execution/verification of this trace would require running the C# test suite (e.g., extending `JsonParserTest.cs`), which was not performed in this static analysis — the control-flow read above is what supports the claim.
