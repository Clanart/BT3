Looking at the full validation path in `send_move_to_vault_tx` and the aggregator's access control.

**Key finding: the input outpoint is never checked against `deposit_outpoint`.**

The validation in `send_move_to_vault_tx` checks:
- `movetx.input.len() != 1 || movetx.output.len() != 2` [1](#0-0) 
- Output amounts (bridge_amount + 0-sat anchor) [2](#0-1) 
- Output script pubkeys (vault + anchor) [3](#0-2) 

There is **no check** that `movetx.input[0].previous_output == deposit_outpoint`. The `deposit_outpoint` from the request is only stored in `TxMetadata` — it is never compared against the actual transaction input. [4](#0-3) 

**Access control on the aggregator server:** The docs explicitly state "The aggregator does not enforce client certificates but does use TLS for encryption." The `create_grpc_server` function applies `OnlyAggregatorAndSelf` only when `config.client_verification` is true; for the aggregator it uses `Noop`. [5](#0-4) [6](#0-5) 

So `SendMoveToVaultTx` is reachable by any network client, not just self.

**Attack path:**
1. Attacker makes a real deposit (UTXO A) and calls `new_deposit` to obtain a validly MuSig2-signed `movetx_A` (spending UTXO A).
2. Attacker calls `send_move_to_vault_tx(raw_tx=movetx_A, deposit_outpoint=B)` where B is a victim's deposit outpoint.
3. All structural checks pass (movetx_A has correct output count, amounts, and script pubkeys).
4. `movetx_A` is queued for broadcast — it spends UTXO A on-chain correctly.
5. The bridge's DB records `deposit_outpoint=B` as the processed deposit in `TxMetadata`. [7](#0-6) 

**Impact:** The bridge's internal state records deposit B as having been moved to vault, while deposit B's UTXO is still unspent on Bitcoin. Depending on how downstream deposit-tracking logic uses `TxMetadata.deposit_outpoint`, this can permanently prevent deposit B from being processed — locking the victim's BTC in the deposit address. This is a metadata-binding failure, not direct theft, but it constitutes a liveness/permanent-lock impact on bridged BTC.

**Limitation of the claim:** The question's framing that "the wrong deposit UTXO is moved to vault" is slightly imprecise — the attacker's own UTXO A is moved to vault (correctly), while victim's UTXO B is only corrupted in metadata. Direct theft of victim's BTC is not possible through this path alone.

### Title
Missing Input Outpoint Binding in `send_move_to_vault_tx` Allows Deposit Metadata Corruption — (`core/src/rpc/aggregator.rs`)

### Summary
`send_move_to_vault_tx` validates move transaction outputs but never verifies that the transaction's single input spends the declared `deposit_outpoint`. An attacker with any valid signed move transaction can submit it with an arbitrary `deposit_outpoint`, corrupting the bridge's deposit tracking state.

### Finding Description
In `AggregatorServer::send_move_to_vault_tx`, after deserializing `movetx` and `deposit_outpoint`, the code performs three output-side checks (count, amounts, script pubkeys) but performs zero input-side checks. Specifically, `movetx.input[0].previous_output` is never compared to `deposit_outpoint`. The `deposit_outpoint` is only used to populate `TxMetadata` before being stored in the tx-sender queue alongside the actual transaction. [8](#0-7) 

### Impact Explanation
An attacker who possesses any legitimately signed move transaction (obtained by making their own deposit and calling `new_deposit`) can submit it with a mismatched `deposit_outpoint` pointing to a victim's deposit. The bridge records the victim's deposit as processed while the victim's UTXO remains unspent, potentially permanently blocking the victim's deposit from being finalized.

### Likelihood Explanation
The aggregator server applies `Noop` interceptor (no client certificate enforcement), so any network-reachable client can call `SendMoveToVaultTx`. The attacker only needs to have made one real deposit to obtain a valid signed move transaction. [9](#0-8) 

### Recommendation
Add an explicit check immediately after the output validations:
```rust
if movetx.input[0].previous_output != deposit_outpoint {
    return Err(Status::invalid_argument(
        "movetx input does not spend the declared deposit_outpoint"
    ));
}
```

### Proof of Concept
Construct a `SendMoveTxRequest` where `raw_tx` is a validly signed move transaction spending UTXO A, but `deposit_outpoint` is set to UTXO B. Call `send_move_to_vault_tx`. Observe that the call succeeds and the tx-sender DB records `deposit_outpoint=B` while the broadcast transaction spends UTXO A. Assert that `movetx.input[0].previous_output != deposit_outpoint` — the mismatch is never detected. [10](#0-9)
