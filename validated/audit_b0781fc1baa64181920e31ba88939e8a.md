## Title
Stale line-index based partial-commit selection is silently reapplied to a changed diff, causing GitHub Desktop to stage/commit different content than what the user selected - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
The reported Sushi bug is a case of a cached accounting value (`reserve0`/`reserve1`) being carried forward without being kept consistent with the real underlying state (`balance`) after an operation (`burn`) mutates that state, so later operations (`mint`/`swap`) trust the wrong value and the end result silently diverges from what the user actually intends/pays. The closest structural analog in GitHub Desktop is the partial-commit line-selection tracking: `DiffSelection` records *which absolute line indices* the user (de)selected in a diff, and this index set is carried forward across refreshes of the working directory by matching on file id, without verifying that the diff content underlying those indices is still the same. When the diff is later recomputed for staging, the same stale indices are blindly reapplied against the new diff, so the set of lines the user actually excluded/included can silently diverge from what gets staged and committed.

### Finding Description
`DiffSelection` tracks selection purely by integer line index (`divergingLines: Set<number>`), with no binding to the actual line content: [1](#0-0) 

When the working directory status is refreshed (e.g. after any git operation, background poll, or focus event), `updateChangedFiles` re-attaches the *old* selection object onto the new `WorkingDirectoryFileChange` purely by matching file id — with no validation that the line indices still refer to the same lines: [2](#0-1) 

The one place that does attempt to reconcile selection state after a diff reload, `updateChangesWorkingDirectoryDiff`, explicitly documents that it does *not* verify selected lines are unchanged — it only prunes indices that are no longer "selectable" (i.e., out of range or turned into context), not indices whose underlying text has shifted or changed: [3](#0-2) 

At commit time, `applyPatchToIndex` re-fetches a fresh diff from disk/git (`getWorkingDirectoryDiff`) — independent from whatever diff was shown when the user made their selection — and then calls `formatPatch`, which stages exactly the lines whose **absolute index** is marked selected in the (possibly now-stale) `DiffSelection`: [4](#0-3) [5](#0-4) 

Because selection is index-based rather than content-based, any change to the file's diff shape between the moment the user deselects/selects lines and the moment `Commit` triggers staging (e.g. hunks shifting due to added/removed lines earlier in the file, line-ending/`ident`/`$Id$` keyword-expansion normalization governed by an attacker-supplied `.gitattributes`, an editor auto-save/format-on-save, or any other process touching the working tree) causes the *same numeric indices* to now point at different lines. The existing guard (`withSelectableLines`) only removes indices that are no longer valid positions in the new diff — it performs no equality check on line content, so it does not stop indices that still land on a "selectable" line, just a different one than the user actually reviewed.

### Impact Explanation
This breaks the fundamental invariant that "what the user visually selected/deselected in the diff view is what gets committed." A shift in the underlying diff between selection and staging can cause content the user explicitly excluded (e.g., a malicious or unwanted line an attacker seeded in the tracked file) to be silently included in the commit, or vice versa — content the user intended to commit gets dropped. This matches the "silent corruption of what the user commits or pushes" impact category: the corruption is invisible to the user because Desktop shows no re-confirmation of the actual staged diff before committing.

### Likelihood Explanation
The trigger does not require local/physical access or malware: it only requires the working-tree content backing a file's diff to change between when the user makes a partial selection and when they click Commit, which can be caused by content originating from an attacker-controlled repository (e.g., built-in git normalization filters declared in a repository's own `.gitattributes`, which are applied automatically on checkout with no external configuration needed) combined with the normal periodic/background status refresh Desktop performs (`updateChangedFiles`) while a commit dialog with partial selections is open. This is a narrower race than a guaranteed one-click exploit, but it is reachable purely through unprivileged interaction with a crafted repository plus Desktop's own background refresh behavior.

### Recommendation
Bind `DiffSelection` state to line content (e.g., a hash or stable identity of the hunk/line text) rather than raw absolute indices, or invalidate/re-map the entire selection (not just prune indices) whenever the underlying diff for a file changes between load and staging. At minimum, `applyPatchToIndex`/`stageFiles` should diff the currently selected lines' content against what was originally shown to the user and refuse to stage (or force a UI re-confirmation) if a mismatch is detected.

### Proof of Concept
1. Clone a malicious repository containing a tracked file with a `.gitattributes` entry that mutates the file on checkout (e.g., `ident` keyword expansion or EOL normalization), plus other lines including a payload line the user is likely to want excluded (e.g., a suspicious dependency addition).
2. In GitHub Desktop, open the changes view for that file and manually deselect the payload line's index while selecting other legitimate changes, per `DiffSelection.withLineSelection` (`app/src/models/diff/diff-selection.ts:205`).
3. Trigger a working-directory status refresh before hitting Commit (e.g., switch away/back to the app, wait for periodic background refresh, or let an editor/save-on-format touch the file) — `updateChangedFiles` (`app/src/lib/stores/updates/changes-state.ts:32`) reuses the old `DiffSelection` object by file id without validating the new diff shape.
4. If the refresh shifted hunks (line insertion/removal/normalization earlier in the file), the previously-deselected index now points to a different line in the diff fetched fresh by `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`), so `formatPatch` (`app/src/lib/patch-formatter.ts:157`) stages a different set of lines than what the user visually reviewed and intended, including possibly the payload line, silently committing content the user tried to exclude.
