### Title
Attacker-controlled `n` in `ThresholdKeys::read` forces a large upfront allocation, enabling repeated-input memory exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the serialized `n` field (a raw `u16` read straight from the wire) and immediately executes `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` variant, before any bound check against `t`/`i` and before confirming the corresponding bytes actually exist. An unprivileged party feeding crafted bytes to `ThresholdKeys::read` can therefore force an allocation of up to `65535 * size_of::<C::F>()` (≈2 MB for a 32-byte scalar, more for wider curves) with a message of only ~9 bytes — an allocation-amplification DoS directly analogous to CVE-2022-42316 (a peer causes the daemon to allocate vast amounts of memory from small inputs). [1](#0-0) 

### Finding Description
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs):

- `t`, `n`, and `i` are read as raw `u16`s from the reader with no sanity checks (lines 591–602). [2](#0-1) 
- If the next byte is `0` (`Interpolation::Constant`), the code does `Vec::with_capacity(usize::from(n))` where `n` can be up to `u16::MAX` (line 608). This reserves the full `n * size_of::<C::F>()` buffer immediately, before a single scalar is read (lines 607–613). [3](#0-2) 
- A further `n` verification shares are then read into a `HashMap` (lines 620–623), but each iteration does `read_exact`/`read_G`, so the bounded case is input-proportional — the dangerous part is specifically the speculative `with_capacity` on the unchecked `n`. [4](#0-3) 
- Only at the very end does `ThresholdParams::new(t, n, i)` validate consistency (lines 625–631), i.e., after the oversized allocation already happened. [5](#0-4) 

The crafted input is just: curve-ID length + curve ID, then `t`, `n = 0xFFFF`, `i`, and tag byte `0x00`. The reader can even be an empty/truncated stream afterward — the allocation already occurred and the subsequent `read_exact` failure does not undo it. Repeated invocations (e.g., an integrator reading `ThresholdKeys` from peer-supplied/DB-supplied bytes, which `ThresholdKeys::read`/`serialize` are explicitly designed for per the docs at lines 565–574) accumulate these transient-but-synchronous multi-megabyte allocations, mirroring the xenstored pattern of a remote party driving large allocations with tiny messages. [6](#0-5) 

### Impact Explanation
Each ~9-byte malicious input forces a synchronous heap reservation of up to ~2 MB (curve-dependent; `Vec::with_capacity` commits the full capacity immediately). An attacker who can repeatedly cause a node to deserialize `ThresholdKeys` from untrusted bytes amplifies their bandwidth into disproportionate memory pressure, degrading or OOM-killing the victim process — a cross-scope availability impact matching the CVE's CVSS profile (C:N/I:N/A:H).

### Likelihood Explanation
Reachability requires an application to call `ThresholdKeys::read` (or `ThresholdKeys::<C>::read`-equivalent deserialization) on bytes influenced by an untrusted party — the API is explicitly public and documented for reading keys from an `io::Read`. The attack needs no valid key material, no threshold position, and no protocol participation — only a few crafted bytes. Likelihood is gated on an integrator deserializing these bytes from an unauthenticated source, so it is rated Medium rather than High.

### Recommendation
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs), validate `n` before allocating: call `ThresholdParams::new(t, n, i)` first (rejecting `n == 0`, `t > n`, `i > n`), then either cap `n` to a sane maximum or replace `Vec::with_capacity(n)` with incremental `push` so allocation stays proportional to bytes actually present — the same chunked-read approach already used in `Call::read` in networks/ethereum/src/machine.rs (lines 51–60) for the identical bug class.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;
use ciphersuite::Ed25519; // any Ciphersuite

fn main() {
  // Serialized prefix of a ThresholdKeys::<Ed25519>:
  //   u32 id_len || id || u16 t || u16 n || u16 i || u8 interpolation_tag
  let mut buf = vec![];
  buf.extend((Ed25519::ID.len() as u32).to_le_bytes());
  buf.extend(Ed25519::ID);
  buf.extend(1u16.to_le_bytes());        // t
  buf.extend(u16::MAX.to_le_bytes());    // n = 65535 -> with_capacity(65535)
  buf.extend(1u16.to_le_bytes());        // i
  buf.push(0);                           // Interpolation::Constant
  // No scalar bytes follow at all.

  // Each call reserves 65535 * 32 B (~2 MB) synchronously before erroring.
  for _ in 0 .. 1000 {
    let _ = ThresholdKeys::<Ed25519>::read(&mut buf.as_slice()); // ~2 GB cumulative pressure
  }
}
```
The function returns `Err` quickly, but the ~2 MB `Vec` allocation is performed first; in a loop over attacker-triggered deserializations this exhausts memory with negligible attacker bandwidth.

Caveat: I verified the allocation site and reachability of `ThresholdKeys::read`, but did not fully trace every caller that feeds untrusted bytes into it; if no in-scope integration point deserializes `ThresholdKeys` from unauthenticated input, the practical severity is lower. Other in-scope readers I checked (PedPoP `Commitments::read`, `EncryptedMessage::read`, `EncryptionKeyProof::read`, `DLEqProof::read`, `SecretShare::read`) are bounded by `params.t()` or fixed-size encodings rather than attacker-controlled lengths.
