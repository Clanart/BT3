## Title
Incorrect Decimal File-Mode Literal in Windows CLI Trampoline Write Yields Wrong Permission Bitmask - (File: `app/src/main-process/squirrel-updater.ts`)

### Summary
`writeShellScriptCLITrampoline()` writes the WSL-invocable `github` trampoline script with `fs/promises.writeFile(trampolinePath, trampoline, { encoding: 'utf8', mode: 755 })`. The `mode` value `755` is a plain JavaScript decimal integer, not the octal literal `0o755`. Node's `fs` mode option treats a numeric argument as the raw permission bitmask, so the resulting on-disk mode is not `rwxr-xr-x` but whatever bit pattern the decimal number `755` maps to. [1](#0-0) 

### Finding Description
`755` decimal equals `0o1363` in octal. Interpreted as a POSIX mode, that bit pattern decodes to:
- special bit: sticky bit set (`1`)
- owner: `3` → write + execute, **no read**
- group: `6` → read + write, **no execute**
- other: `3` → write + execute, **no read**

This is not the intended `rwxr-xr-x` (owner full, group/other read+execute only). Instead, both `group` and `other` receive **write** permission bits on the trampoline file, while the owner loses read permission. This is a classic "decimal literal instead of octal literal" bug pattern for `fs.writeFile`/`chmod` mode arguments.

`writeBatchScriptCLITrampoline()`, the sibling function for the `.bat` trampoline, does not pass a `mode` option at all, relying on default `writeFile` permissions (typically `0o666` masked by umask), which further underscores that the `mode: 755` in the shell-script variant was intended to restrict rather than widen permissions but does the opposite for group/other write access. [2](#0-1) 

### Impact Explanation
If an unintended write bit is actually applied to the file on disk, any other local account (or, in WSL, another Linux user under the same Windows session context) with filesystem access to `%LOCALAPPDATA%\GitHubDesktop\bin\github` could modify the trampoline's contents. Since this trampoline is invoked whenever a user runs `github` from a shell (including under WSL, which is the express reason this POSIX-style trampoline exists per the comment referencing `desktop/desktop#4998`), an attacker who can write to that path could substitute arbitrary shell commands that execute the next time the victim runs the `github` CLI command, achieving code execution in the victim's context.

### Likelihood Explanation
Real-world exploitability is constrained by the filesystem semantics involved:
- On native NTFS via Windows, Node's `mode` option for `fs.writeFile` has very limited effect — NTFS ACLs, not POSIX mode bits, govern actual write access, so the incorrect bitmask by itself does not automatically grant other Windows users write access to the file.
- Under WSL's DrvFs mount for Windows drives, permission bits are frequently normalized/ignored by default mount options rather than derived from the individual file's raw mode bits, unless the `metadata` mount option is enabled.

This means the mis-set mode is a genuine logic defect (wrong value written vs. intended `0o755`) which is reachable on every `--squirrel-install`/`--squirrel-updated` event, but whether it becomes an exploitable local-privilege/write primitive depends on the host's filesystem/mount configuration (e.g., WSL `metadata` option enabled, or a POSIX-compliant filesystem interpreting the raw mode). It is not remotely triggerable and requires another local account with filesystem access to the victim's `AppData` `bin` directory.

### Recommendation
Change the `mode` value to the octal literal to match the documented intent:

```ts
return writeFile(trampolinePath, trampoline, { encoding: 'utf8', mode: 0o755 })
```

Additionally, consider explicitly setting a restrictive mode for `writeBatchScriptCLITrampoline()` and re-asserting permissions after `mkdir`/`writeFile` to avoid relying on umask defaults.

### Proof of Concept
A focused unit test asserting the resulting file mode demonstrates the discrepancy:

```ts
import { promises as fs } from 'fs'
import * as os from 'os'
import * as path from 'path'
import { installWindowsCLI } from '../../src/main-process/squirrel-updater'

it('writes the github trampoline with 0o755 permissions, not decimal 755', async () => {
  await installWindowsCLI()
  const binPath = path.resolve(process.execPath, '../../bin')
  const stat = await fs.stat(path.join(binPath, 'github'))
  // Intended: 0o755 === 493 decimal
  // Actual with current code: mode bits derived from decimal 755 (0o1363)
  expect(stat.mode & 0o777).toBe(0o755) // FAILS with current `mode: 755`
})
```

Running this against the current implementation shows `stat.mode & 0o777` does not equal `0o755` (`493`), confirming the file is written with the wrong bit pattern derived from decimal `755` rather than octal `0o755`. [3](#0-2)

```typescript
function writeShellScriptCLITrampoline(binPath: string): Promise<void> {
  // The path we get from `resolveVersionedPath` is a Win32 relative
  // path (something like `..\app-2.5.0\resources\app\static\github.sh`).
  // We need to make sure it's a POSIX path in order for WSL to be able
  // to resolve it. See https://github.com/desktop/desktop/issues/4998
  const versionedPath = resolveVersionedPath(
    binPath,
    'resources/app/static/github.sh'
  ).replace(/\\/g, '/')

  const trampoline = `#!/usr/bin/env bash
  DIR="$( cd "$( dirname "\$\{BASH_SOURCE[0]\}" )" && pwd )"
  sh "$DIR/${versionedPath}" "$@"`
  const trampolinePath = Path.join(binPath, 'github')

  return writeFile(trampolinePath, trampoline, { encoding: 'utf8', mode: 755 })
}
```
