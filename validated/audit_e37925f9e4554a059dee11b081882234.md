### Title
Decoy transaction spending a registered `withdrawal_utxo` is recorded as its payout with no validation it paid the withdrawer, letting an outside attacker frame a real operator into automatically claiming an unfunded reimbursement - ([File: core/src/database/verifier.rs])

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` joins the `withdrawals` table to `bitcoin_syncer_spent_utxos` purely on `(txid, vout)` and `Verifier::update_finalized_payouts` blindly trusts the first OP_RETURN of whatever transaction spent that outpoint to populate `payout_payer_operator_xonly_pk`. Neither function - nor the downstream `is_kickoff_malicious` check used to decide whether to challenge a kickoff - verifies that the spending transaction actually paid the withdrawer's `output_script_pubkey`/`output_amount`. An unprivileged withdrawer can therefore sweep their own registered `withdrawal_utxo` with a decoy transaction carrying an arbitrary OP_RETURN, and if that OP_RETURN happens to decode as a real operator's x-only pubkey, that operator's own automation (`PayoutCheckerTask`) will believe it fronted the payout and autonomously start the kickoff/reimbursement flow for a withdrawal it never funded.

### Finding Description
The claimed binding is: `withdrawals.payout_txid` (and `payout_payer_operator_xonly_pk`) recorded for withdrawal `idx` == the txid of a transaction that actually paid `withdrawals.output_script_pubkey`/`output_amount` to the withdrawer.

- `Database::get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) selects `bsu.spending_txid` by matching only `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`. It has no join or predicate on the spending tx's outputs, amounts, or OP_RETURN.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) takes whatever tx spent the outpoint, looks for the first OP_RETURN, and if it parses as a valid `XOnlyPublicKey`, stores it as `payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk` - again with zero validation of the transaction's actual payment outputs against the withdrawal's committed `output_script_pubkey`/`output_amount`.
- `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`), which decides whether verifiers challenge a kickoff, only checks that (a) the DB's `payout_payer_operator_xonly_pk` equals the kickoff's operator, and (b) the committed payout blockhash matches. It never re-derives or checks that the recorded payout tx pays the withdrawer.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:31-111`) queries `get_first_unhandled_payout_by_operator_xonly_pk` filtered on the operator's *own* xonly pubkey and, if a row exists, unconditionally calls `Operator::handle_finalized_payout` (`core/src/operator.rs:839-916`) to start the kickoff process and eventually `mark_payout_handled`, without any check that the operator itself broadcast the recorded `payout_txid`.

Exploit flow: the attacker (an ordinary user) calls `withdraw()` on the Citrea bridge contract specifying their own UTXO as `input_outpoint` (this becomes `withdrawal_utxo_txid`/`vout` in `withdrawals`). Before any operator fronts the payout, the attacker broadcasts a decoy transaction spending that same UTXO with a single crafted OP_RETURN output whose 32 bytes happen to parse as a valid x-only public key equal to a real, honest operator's public `xonly_pk` (public information; ~50% of random 32-byte values are valid x-coordinates, so this is free and trivially repeatable off-chain). Once this decoy transaction is finalized, `update_finalized_payouts` writes `payout_txid = <decoy>`, `payout_payer_operator_xonly_pk = <victim operator>` into `withdrawals`. The victim operator's own `PayoutCheckerTask` then discovers this "payout" tagged with its own key and autonomously drives the kickoff/round/reimbursement flow for a withdrawal it never funded, while verifiers' `is_kickoff_malicious` sees a self-consistent (attacker-fabricated) DB record and does not flag/challenge it.

The zk `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs`) does independently re-derive the withdrawal outpoint from Citrea storage proofs and cross-checks it against the payout SPV transaction, but this stronger validation is only exercised if a challenge/dispute is raised. Since `is_kickoff_malicious` (based on the same unguarded DB fields) determines whether verifiers challenge at all, an honest operator's kickoff sails through unchallenged and reaches the `Reimburse` transaction, at which point the operator is paid from the bridge's collateral/round funds for a withdrawal it never actually paid.

### Impact Explanation
This breaks custody: an operator can end up reimbursed (Reimburse tx paid out of protocol round funds) for a withdrawal it never fronted, while the withdrawer received nothing from that operator and the deposit's BTC is effectively drained without a matching fronted payment. This matches the Critical category "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." It is repeatable per withdrawal against any operator whose x-only pubkey is public (all operators' pubkeys are public), and the attacker only needs to control their own withdrawal UTXO and fee for one small decoy transaction - no key compromise, no privileged role, no majority hashrate.

### Likelihood Explanation
Preconditions: any unprivileged user who withdraws via Citrea and supplies their own UTXO as the withdrawal UTXO can perform this at will, at the cost of a single low-fee Bitcoin transaction, with no cooperation from any operator, verifier, or aggregator required. Producing an OP_RETURN payload matching a specific target operator's x-only pubkey requires no brute force at all (the attacker directly writes that operator's real, public xonly_pk bytes as OP_RETURN data) - success is not probabilistic, it is deterministic. The only requirement for the attack to fully cash out is that the targeted operator runs automation (`PayoutCheckerTask`) and that no verifier independently notices the discrepancy before the challenge-timeout window elapses; nothing in the current code performs that independent check.

### Recommendation
`Database::get_payout_txs_for_withdrawal_utxos`/`update_finalized_payouts` (and `is_kickoff_malicious`) must validate that the transaction spending the registered `withdrawal_utxo` actually pays the withdrawal's committed `output_script_pubkey` and `output_amount` (as stored/derived at withdrawal-registration time) before recording it as the withdrawal's `payout_txid`/`payout_payer_operator_xonly_pk`. If no output of the spending transaction matches the committed script_pubkey/amount, the row should not be treated as a valid payout (and ideally flagged so verifiers challenge any kickoff attempting to claim it).

### Proof of Concept
`cargo test` plan (no mainnet, no live Citrea):
1. In a test harness similar to `core/src/database/verifier.rs` tests (`update_get_payout_txs_from_citrea_withdrawal`), register a withdrawal via `upsert_move_to_vault_txid_from_citrea_deposit` + `update_withdrawal_utxo_from_citrea_withdrawal` with a specific `output_script_pubkey`/`output_amount` intent (store this in the deposit/withdrawal fixture data).
2. Construct a "decoy" transaction that spends the registered `withdrawal_utxo_txid`/`vout` with: no output paying the withdrawer's `output_script_pubkey`, and one OP_RETURN output containing a target operator's real `xonly_pk` bytes.
3. Insert this decoy as the spending tx via `insert_spent_utxo`, then call `Verifier::update_finalized_payouts` (or directly `Database::get_payout_txs_for_withdrawal_utxos` + `update_payout_txs_and_payer_operator_xonly_pk`).
4. Assert (LEFT side of the binding): `db.get_payout_info_from_move_txid(...)` returns `payout_txid == decoy_txid` and `payout_payer_operator_xonly_pk == Some(target_operator_xonly_pk)`.
5. Assert (RIGHT side of the binding, which should be false): the decoy transaction's outputs do NOT contain a `TxOut` equal to `(output_amount, output_script_pubkey)` for the withdrawer.
6. Show these two sides mismatch (decoy recorded as payout despite paying nothing to the withdrawer), and optionally call `Operator::handle_finalized_payout` for the target operator to show it proceeds to build/sign a kickoff without error, confirming the automation would act on the false record.
