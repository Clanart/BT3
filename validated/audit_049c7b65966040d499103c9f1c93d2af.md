Based on my research, the strongest analog for the reported off-by-one/boundary bug class in Desktop is in the "Preview Pull Request" diff-rendering path, where the commit range used to render the diff a user reviews before merging is built with a fixed `shas[0]^..shas.at(-1)` boundary that does not account for non-linear/merge history — a structural boundary mismatch conceptually parallel to the Tracer bug's `currentGlobalFundingIndex` vs `currentGlobalFundingIndex - 1` mismatch, but here it can cause the *reviewed* diff to silently diverge from what actually gets merged/pushed.

### Title
Diff shown for a fork/PR preview can omit attacker-controlled changes from unreachable merge-commit ancestry - ([File: app/src/lib/git/diff.ts])

### Summary
`getCommitRangeDiff` and `getCommitRangeChangedFiles` compute the review diff for a range of commits using only `shas[0]^..shas.at(-1)`, i.e. a straight two-endpoint `git diff`. This boundary calculation is documented by Desktop itself to be unsound whenever the selected range contains a merge commit, since `git diff X..Y` only follows the *first* ancestral path and can silently exclude entire branches of changes reachable through a merge.

### Finding Description
`getCommitRangeDiff` picks `oldestCommitRef = ${commits[0]}^` and `latestCommit = commits.at(-1)` and runs a plain `git diff oldestCommitRef latestCommit` for a single file: [1](#0-0) 
`getCommitRangeChangedFiles` does the same for the full changed-file list used to populate the PR preview's file list: [2](#0-1) 
This is used directly to populate the "Preview Pull Request" review UI (`PullRequestFilesChanged`/`open-pull-request-dialog.tsx`) that a user relies on before merging a branch that may include commits from a fork or externally fetched branch: [3](#0-2) 
Desktop's own documentation explicitly states that a two-endpoint `git diff` over a merge-containing range only follows the ancestral path of the *last* commit, and can miss changes from merged-in commits that are otherwise part of the visible, chronologically-ordered commit list: [4](#0-3) 
The regular local commit-selection code path (`_changeCommitSelection`/`getShasInDiff` in `app-store.ts`) is aware of this and explicitly walks parent links to compute the correct `shasInDiff` set before diffing, specifically to avoid this class of bug: [5](#0-4) [6](#0-5) 
However `getCommitRangeDiff`/`getCommitRangeChangedFiles`, used for the pull-request preview flow, do not perform this same ancestral-path correction — they always use only the first and last SHA of the range as the diff boundary, regardless of merge commits in between.

### Impact Explanation
If an attacker crafts a branch/fork (e.g. one the victim fetches or is asked to preview as a PR) that contains a merge commit where the "hidden" branch introduces malicious file changes, the two-endpoint diff can present an incomplete/misleading view of the actual file changes to the user reviewing the PR in Desktop's "Preview Pull Request" screen, while the full content is nonetheless part of the commit range that will be merged/pushed if the user proceeds. This matches "silent corruption of what the user commits or pushes" in that what is displayed for review does not match what is actually being merged.

### Likelihood Explanation
This requires the attacker to control a fetched/forked branch with a merge commit shape that Desktop's own documentation confirms produces incorrect diffs, and requires the victim to be using the Preview Pull Request flow. It does not require local access, malware, or leaked credentials — only a specially crafted, attacker-supplied git history reachable via a normal clone/fetch/fork-review workflow. Likelihood is moderate: it depends on the specific commit-graph shape and on the reviewer trusting the file list/diff without independently verifying via `git log --graph` or the GitHub web UI.

### Recommendation
Apply the same ancestral-path-aware computation used for the local commit-selection diff (`getShasInDiff`) before calling `getCommitRangeDiff`/`getCommitRangeChangedFiles` for pull-request previews, or otherwise ensure that merge commits inside a previewed range are expanded to include all reachable branches, not just the first-parent path between the two endpoint SHAs.

### Proof of Concept
1. Attacker creates a fork/branch history: `A -> B -> C`, then branches off `B` to add `D` (malicious payload file), merges `D` into `C` producing merge commit `M` (`C` and `D` both parents of `M`), so the linear/chronological commit list shown by Desktop is `A, B, C, D, M`.
2. Victim opens "Preview Pull Request" for this branch in Desktop; the commit range passed to `getCommitRangeDiff`/`getCommitRangeChangedFiles` is `[A, B, C, D, M]`, producing `oldestCommitRef = A^`, `latestCommitRef = M`.
3. Per Desktop's own `docs/learn-more/unreachable-commits.md` example, `git diff A^..M` only follows `M -> C -> B -> A`, and the changes introduced by `D` alone (before being merged) can be omitted/misrepresented in the reviewed diff and file list, even though `D`'s content is part of the branch that will be merged if the user proceeds.
4. This is unverified end-to-end (no live repro was executed against a running Desktop build); confirmation would require constructing the exact commit graph in a test repository and comparing `getCommitRangeChangedFiles` output against `git diff A..M --stat` / the actual merged tree.

  /**
   * When multiple commits are selected, the diff is created using the rev range
   * of firstSha^..lastSha in the selected shas. Thus comparing the trees of the
   * the lastSha and the first parent of the first sha. However, our history
   * list shows commits in chronological order. Thus, when a branch is merged,
   * the commits from that branch are injected in their chronological order into
   * the history list. Therefore, given a branch history of A, B, C, D,
   * MergeCommit where B and C are from the merged branch, diffing on the
   * selection of A through D would not have the changes from B an C.
   *
   * This method traverses the ancestral path from the last commit in the
   * selection back to the first commit via checking the parents. The
   * commits on this path are the commits whose changes will be seen in the
   * diff. This is equivalent to doing `git rev-list firstSha^..lastSha`.
   */
  private getShasInDiff(
    selectedShas: ReadonlyArray<string>,
    isContiguous: boolean,
    commitLookup: Map<string, Commit>
  ) {
    if (selectedShas.length <= 1 || !isContiguous) {
      return selectedShas
    }

    const shasInDiff = new Set<string>()
    const selected = new Set(selectedShas)
    const shasToTraverse = [selectedShas.at(-1)]
    let sha

    while ((sha = shasToTraverse.pop()) !== undefined) {
      if (!shasInDiff.has(sha)) {
        shasInDiff.add(sha)

        commitLookup.get(sha)?.parentSHAs?.forEach(parentSha => {
          if (selected.has(parentSha) && !shasInDiff.has(parentSha)) {
            shasToTraverse.push(parentSha)
          }
        })
      }
    }

    return Array.from(shasInDiff)
  }
