### Title
Cached FROST preprocess seed is never deleted after signing, enabling deterministic nonce reuse and private key share recovery on re-execution - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` persists the ChaCha20 seed backing a FROST preprocess in `CachedPreprocesses` keyed only by `context` and never removes it. Every subsequent call to `share_internal`/`complete` under the same context deterministically regenerates the identical nonce pair `(d, e)`. The file's own header admits the safety of this scheme rests entirely on never re-signing under distinct inputs — yet `DkgConfirmer::share` and `DkgConfirmer::complete` each re-enter `share_internal`, and the documented on-chain consistency check that would make reuse safe is an unimplemented TODO. The "incomplete cleanup" (the consumed seed remaining live in the DB) is exactly the bug class of ALPINE-CVE-2020-24489 mapped onto Serai's FROST state machine.

### Finding Description
In `coordinator/src/tributary/signing_protocol.rs:123-147`, the coordinator encrypts a freshly generated preprocess seed with `Blake2s256("Cached Preprocess Encryption Key" || context || key)` and stores it via `CachedPreprocesses::set`. On every later invocation, `CachedPreprocesses::get` is read back and fed to `AlgorithmSignMachine::from_cache` — there is no `remove`/`delete` anywhere after `sign()` consumes it. `seeded_preprocess` in `crypto/frost/src/sign.rs:127-132` then derives the same `ChaCha20Rng` and therefore the same nonces via `Commitments::new` → `Curve::random_nonce` (`crypto/frost/src/curve/mod.rs:94-121`).

`share_internal` (`signing_protocol.rs:150-181`) always begins by calling `preprocess_internal`, so `DkgConfirmer::share` (lines 304-310) and `DkgConfirmer::complete` (lines 312-327, which calls `share_internal` again at line 322) reuse the same nonce material for the context `(b"DkgConfirmer", attempt)`. The header comment (lines 25-54) explicitly states nonce reuse leaks the secret share and that safety is only assumed because BFT should never deliver distinct commitment sets — while simultaneously acknowledging two TODOs: the check that "the commitments generated from the decided nonces are in fact its commitments on-chain" and "we also need to review how we're handling Processor preprocesses." Those checks do not exist; the stale seed remains usable indefinitely.

A FROST share is `s = d + ρ·e + λ·x·c`. If `share_internal` executes twice under the same context with identical remote preprocesses but a different message `msg` (e.g., a re-executed confirmation over a different `key_pair` / `set_keys_message`, or a partial rebuild that re-runs `share` after `complete` already consumed the machine — a scenario the header concedes is possible since "partial rebuilds" retain the DB state), `d`, `e`, and `ρ` are identical, giving `r = d + ρ·e` reused across two challenges. Anyone observing both published shares solves `x = (s1 − s2) / (λ·(c1 − c2))`, recovering the validator's MuSig secret share — the root-of-trust key the header says must never leak.

### Impact Explanation
Recovery of a validator's private key share. Since these MuSig shares confirm DKG results on-chain and the validators are the root of trust, leaked shares allow forging set-key confirmations and, combined with threshold participation, control of the rotating validator set's signing authority. This is secret-key leakage reachable through the normal `share`/`complete` API with public preprocess/share data — matching the documented consequence in `spec/cryptography/FROST.md:51-55` ("reusing preprocesses would enable a third-party to recover your private key share").

### Likelihood Explanation
Triggering requires `share_internal` to run a second time under the same `(b"DkgConfirmer", attempt)` context with a differing `msg` or participant set — e.g., a coordinator rebuild mid-attempt, or `share` followed by a `complete` path where the confirmed `key_pair`/preprocess set differs from the first execution. The code provides no defense: the seed is never invalidated, the attempt-boundary consistency checks are TODOs, and the FROST library itself cannot detect reuse because `from_cache` is a legitimate API. Likelihood hinges on coordinator re-execution paths in `handle.rs` that I could not fully verify; the latent primitive (permanent seed reuse) is unconditional.

### Recommendation
Delete the `CachedPreprocesses` entry (or mark it consumed) inside `share_internal`/`preprocess_internal` before returning, and refuse to sign if a consumed context is revisited. Additionally, implement the two TODOs: before publishing a share, verify on finalized chain data that the preprocess commitments correspond to the decided nonces, and bind the `context` to the full signing statement (set + key_pair hash + attempt) so any change produces a fresh, never-before-used seed.

### Proof of Concept
1. Coordinator runs `DkgConfirmer::share` for attempt `a` → stores seed `S` under `CachedPreprocesses[(b"DkgConfirmer", a)]`, publishes share `s1 = d + ρ·e + λ·x·c1` over `msg1 = set_keys_message(set, removed, key_pair_A)`.
2. After a partial rebuild or a second confirmation round under the same attempt, `share` (or `complete`, which re-enters `share_internal`) is invoked with the same remote preprocesses but `msg2 = set_keys_message(set, removed, key_pair_B)` — `S` is reloaded, identical `(d, e)` regenerated, identical `ρ` (binding factors depend on the remote commitments, not `msg`), but different challenge `c2` since the message is transcripted.
3. Observer computes `x = (s1 − s2) / (λ · (c1 − c2)) mod q` — the validator's secret share — and can produce valid shares/confirmations impersonating that validator.

Note: I could not fully inspect `coordinator/src/tributary/handle.rs` callers within the iteration budget, so the exact public path that supplies a divergent `key_pair`/preprocess set under one attempt context is inferred from the header's own safety analysis rather than confirmed end-to-end; the missing-cleanup primitive itself (seed never deleted at `signing_protocol.rs:134-147`) is fully verified.
