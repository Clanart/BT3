### Title
Untrusted `ReceivedOutput` bytes bind an arbitrary scalar offset to any `script_pubkey`, producing unspendable “received” funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes three independent fields — a scalar `offset`, a `TxOut`, and an `OutPoint` — from untrusted bytes with no binding between them. The scanner's `scan_transaction` only ever produces `ReceivedOutput`s where `output.script_pubkey == p2tr_script_buf(key + offset * G)`, but `read` never re-establishes that invariant. A crafted blob pairs a victim-owned `script_pubkey` (one of the scanner's registered addresses) with an arbitrary offset (or vice versa). The resulting `ReceivedOutput` is treated as a spendable input, yet the spend key derived as `key + offset * G` does not match the output's actual key, so any transaction consuming it produces an invalid BIP-340/Taproot signature.

### Finding Description
`ReceivedOutput` is the wallet's unit of spendable funds, defined at `networks/bitcoin/src/wallet/mod.rs:90-97` as an `offset` scalar plus a `TxOut`/`OutPoint`. The read path at `networks/bitcoin/src/wallet/mod.rs:120-134` reads `offset` via `Secp256k1::read_F`, then `consensus_decode`s the `TxOut` and `OutPoint`, and returns the struct unconditionally — there is no check that `output.script_pubkey` equals the P2TR script for `key + offset * G`.

The honest constructor, `Scanner::scan_transaction` at `networks/bitcoin/src/wallet/mod.rs:199-214`, only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` yields a registered offset, guaranteeing `script_pubkey = p2tr_script_buf(self.key + offset * G)` (`register_offset` at lines 180-196 builds exactly that map). `read` reintroduces these bytes without that guarantee.

Downstream, spending relies on the offset being the discrete-log difference between the base key and the output key: `SignableTransaction`/the FROST multisig tweak the `ThresholdKeys` by `output.offset()` (the `ThresholdKeys::offset` mechanism at `crypto/dkg/src/lib.rs:409-417` adds the offset to `included[0]`'s secret share, and `view` at lines 518-521 adds `G * offset` to the verification share). The math is only correct if `key + offset * G` is actually the output's key. An attacker-injected `ReceivedOutput` violates this: the produced signature verifies under a different tweaked key than the one committed in the UTXO, so the spend is invalid on-chain.

This is the deserialization-side analog of the report's injection class: untrusted bytes supply a field (`offset`) that is later interpreted as a trusted statement ("this offset spends this output") that the parser never validated.

### Impact Explanation
Any consumer that loads `ReceivedOutput`s from a source an unprivileged party can influence (serialized output lists, blame/recovery payloads, or any integration persisting scanner results across trust boundaries) will credit funds that cannot actually be spent. The malformed output is indistinguishable from a real deposit — `value()`, `outpoint()`, and `id()` all look valid — so it enters coin selection. Every transaction built over it is invalid and the affected wallet/processor keeps selecting the poisoned input, burning fee budget in retries and creating a liveness failure for the affected funds. The scanner only matches `script_pubkey`, so the attacker can point a *real* victim-owned script at a false offset without knowing any private keys.

### Likelihood Explanation
Medium. Exploitation requires attacker-controlled bytes to reach `ReceivedOutput::read`, which the stated reachability model permits. No secret material, signatures, or on-chain cooperation are needed — the payload is just `scalar || TxOut || OutPoint` bytes. The impact is bounded to unspendable-input DoS rather than key recovery, since the offset can only decouple the claimed spend key from the real output key.

### Recommendation
In `ReceivedOutput::read`, or in a `verify(key)`/`new` constructor that becomes mandatory, recompute `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset)` and reject the input if it does not equal `output.script_pubkey`. Alternatively, store only the `OutPoint`/`TxOut` plus the script and re-derive the offset via the `Scanner` script map at load time, so the offset can never diverge from the script.

### Proof of Concept
```rust
// networks/bitcoin context; attacker crafts bytes for ReceivedOutput::read
let key: ProjectivePoint = /* scanner's base key (even) */;
let real_offset = Scalar::ZERO; // script pays to the base key
let evil_offset = Scalar::from(7u64); // attacker-chosen mismatch

let mut buf = vec![];
buf.extend(evil_offset.to_bytes());                       // offset field
buf.extend(serialize(&TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: p2tr_script_buf(key).unwrap(),         // victim's real script
}));
buf.extend(serialize(&OutPoint::new(Txid::all_zeros(), 0)));

// Accepted unconditionally — no script/offset consistency check
let poisoned = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(poisoned.offset(), evil_offset);

// Downstream: signing tweaks keys by evil_offset, producing a signature for
// key + 7*G, while the UTXO commits to key + 0*G -> invalid spend.
```
