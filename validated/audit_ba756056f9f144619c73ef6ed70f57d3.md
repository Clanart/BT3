### Title
Attacker-controlled Bitcoin fee samples can permanently discard multisig inputs - (File: processor/src/networks/bitcoin.rs)

### Summary
Serai estimates Bitcoin transaction fees using the median fee rate of only the single finalized block selected for plan preparation. [1](#0-0)  Because every non-coinbase transaction in that public block contributes to the sorted sample and the upper median is selected, an attacker who places enough high-fee transactions into the sampled block can arbitrarily raise Serai's fee rate. [2](#0-1)  If the resulting fee exceeds the plan's inputs, no transaction is produced and the already-drained inputs are not restored, making the affected funds unusable by normal scheduler flow. [3](#0-2) [4](#0-3) 

### Finding Description
`Bitcoin::make_signable_transaction` retrieves `block_number`, computes `median_fee` over that block, and passes the resulting rate directly to `BSignableTransaction::new`. [5](#0-4)  `median_fee` reconstructs each transaction's total fee from its public inputs and outputs, divides by transaction vsize, sorts all fee rates, and returns `fees[len / 2]`. [2](#0-1)  There is no cap, historical smoothing, outlier rejection, or sanity bound; the adjacent comment explicitly notes that the estimate should use several blocks but currently does not. [1](#0-0) 

The sampled block number comes from the latest finalized external-network block supplied in the Substrate context. [6](#0-5)  Once the malicious block is finalized at that position, every processor independently derives the same inflated fee because the calculation is deterministic over public block contents. [7](#0-6) 

`SignableTransaction::new` rejects construction when `input_sat < payment_sat + needed_fee`. [8](#0-7)  The Bitcoin adapter maps `NotEnoughFunds` to `Ok(None)`, and `Network::needed_fee` propagates that result. [9](#0-8) [10](#0-9)  `prepare_send` then returns `PreparedSend { tx: None, .. }` rather than retrying with a different fee market. [3](#0-2) 

The scheduler had already drained its UTXO set into the plan being prepared. [11](#0-10)  After a `None` transaction, the caller explicitly lacks logic to restore the plan's inputs to the scheduler. [4](#0-3) 

### Impact Explanation
An attacker can make a selected plan unbuildable by choosing a median fee rate greater than `total_input_value / transaction_vbytes`. [8](#0-7)  The discarded plan's inputs remain absent from the scheduler's UTXO set, so later calls do not automatically regain or spend them. [11](#0-10) [4](#0-3)  This can strand aggregation, payment, refund, forwarding, or rotation transactions that depend on the discarded inputs, making the issue a permanent funds-availability failure absent manual recovery or a code fix. [3](#0-2) 

The impact is Medium: it causes loss of availability of multisig-controlled funds and can stall required wallet operations, but stealing those funds is not shown and sustaining the attack is costly. [2](#0-1) 

### Likelihood Explanation
The attack is reachable solely by publishing ordinary Bitcoin transactions because the oracle consumes public transactions from the selected block without filtering. [12](#0-11)  To set the median to an attacker-chosen rate, the attacker must cause more than half of the sampled non-coinbase transactions to carry that rate; for a block with `n` such transactions, `floor(n / 2) + 1` malicious transactions are sufficient. [13](#0-12)  Each malicious transaction must actually pay its advertised fee, so making the target plan unaffordable generally costs at least the value of the targeted inputs multiplied by the number of malicious samples needed, making the attack economically irrational in ordinary conditions but viable for griefing or timing-critical rotation/withdrawal disruption. [8](#0-7) 

### Recommendation
Do not derive transaction fees from the median of a single external block. [1](#0-0)  Use a bounded estimator over a multi-block window or node fee estimation, clamp it to documented minimum and maximum rates, and treat a still-unaffordable estimate as retryable rather than final. [2](#0-1)  Separately, when `prepare_send` returns `tx: None`, restore the plan's inputs to the scheduler or persist them in an explicitly recoverable state. [3](#0-2) [4](#0-3) 

### Proof of Concept
1. Let the finalized block selected as `block_number` contain `n` ordinary non-coinbase transactions. [6](#0-5) 
2. Publish `floor(n / 2) + 1` valid Bitcoin transactions whose fee rate is `F`, choosing `F` so `F * target_vbytes` exceeds the target plan's `input_sat`. [2](#0-1) [8](#0-7) 
3. Once that block is finalized, `median_fee` sorts the transaction fee rates and returns `F` from index `fees.len() / 2`. [14](#0-13) 
4. `needed_fee` calls `BSignableTransaction::new` with the target inputs and receives `NotEnoughFunds`, which the adapter converts to `None`. [9](#0-8) [10](#0-9) 
5. `prepare_send` emits no transaction, while the plan's inputs remain drained because the caller only has a TODO to restore them. [3](#0-2) [4](#0-3)

  async fn median_fee(&self, block: &Block) -> Result<Fee, NetworkError> {
    let mut fees = vec![];
    if block.txdata.len() > 1 {
      for tx in &block.txdata[1 ..] {
        let mut in_value = 0;
        for input in &tx.input {
          let mut input_tx = input.previous_output.txid.to_raw_hash().to_byte_array();
          input_tx.reverse();
          in_value += self
            .rpc
            .get_transaction(&input_tx)
            .await
            .map_err(|_| NetworkError::ConnectionError)?
            .output[usize::try_from(input.previous_output.vout).unwrap()]
          .value
          .to_sat();
        }
        let out = tx.output.iter().map(|output| output.value.to_sat()).sum::<u64>();
        fees.push((in_value - out) / u64::try_from(tx.vsize()).unwrap());
      }
    }
    fees.sort();
    let fee = fees.get(fees.len() / 2).copied().unwrap_or(0);

    // The DUST constant documentation notes a relay rule practically enforcing a
    // 1000 sat/kilo-vbyte minimum fee.
    Ok(Fee(fee.max(1)))
