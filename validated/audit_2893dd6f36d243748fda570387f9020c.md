### Title
Unvalidated `AccountInfo.data` pointer lets a legacy-path CPI caller redirect the fixed-offset "length write" during `update_caller_account`, corrupting arbitrary VM-writable memory - (File: `program-runtime/src/cpi.rs`)

### Summary
The External Report's bug class is: code assumes a fixed structural relationship between a data pointer and a length word that precedes it (e.g. "the word at `offset - 32` is always the array length"), but that assumption breaks when the pointer has been repositioned (via slicing or manual construction) so it no longer points to the true start of the structure — causing the wrong memory to be read/written as "length". Agave's CPI account-data synchronization path in `program-runtime/src/cpi.rs` embeds the exact same assumption: it hard-codes that the serialized account length lives at `vm_data_addr - size_of::<u64>()`, and — outside the `syscall_parameter_address_restrictions` feature-gated path — never verifies that `vm_data_addr` (derived from the caller-supplied `AccountInfo::data` pointer) actually still points at the runtime-constructed serialization region.

### Finding Description
`CallerAccount::from_account_info` derives `vm_data_addr` directly from the pointer stored in the BPF program's own `AccountInfo::data` slice: [1](#0-0) 

The pointer validity check that ties `data.as_ptr()` back to the trusted `account_metadata.vm_data_addr` (`check_account_info_pointer`) is only performed `if syscall_parameter_address_restrictions`: [2](#0-1) 

When that feature flag is not active for the executing transaction (legacy ABI path), `vm_data_addr` is accepted as-is — i.e. it is whatever pointer value the BPF program currently has stored in its own `AccountInfo::data` field, which the program is free to overwrite/move (this exact capability is exercised by the test harness in `programs/sbf/rust/invoke/src/lib.rs`, `TEST_FORBID_LEN_UPDATE_AFTER_OWNERSHIP_CHANGE_MOVING_DATA_POINTER` / `TEST_FORBID_LEN_UPDATE_AFTER_OWNERSHIP_CHANGE`, which deliberately move `account.data`'s pointer past a manually placed `RcBox` before invoking CPI): [3](#0-2) 

Later, at CPI exit, `update_caller_account` unconditionally recomputes the location of the "serialized length" word purely by subtracting a fixed 8-byte offset from `caller_account.vm_data_addr`, then performs a translated *write* to that address: [4](#0-3) 

This is structurally identical to the reported bug: the code assumes "the length always lives at `pointer - N`" without re-validating that `pointer` still denotes the start of the object the runtime originally serialized. In the Solidity report, an attacker-controlled calldata slice pointer breaks that assumption and causes a bad length to be copied. Here, an attacker-controlled (BPF-program-controlled) `AccountInfo::data` pointer breaks the same assumption, and instead of merely reading a bad length, the runtime performs a **translated store of `post_len` to `vm_data_addr - 8`**, i.e. an attacker-influenced write target inside the VM's mapped memory region set.

`translate_type_mut_for_cpi` only checks that the address is mappable/aligned within the VM's memory regions — it does not know or check that the target address is actually the length field belonging to *this* account: [5](#0-4) 

### Impact Explanation
This is an unprivileged path: any BPF program (the deployed/invoked program itself, not a "malicious validator/peer") can manipulate its own `AccountInfo::data` pointer before performing CPI and trigger `update_caller_account`'s fixed-offset write. Because the write address is `caller_account.vm_data_addr - 8` and `vm_data_addr` is unauthenticated on the legacy (non-`syscall_parameter_address_restrictions`) path, the 8-byte write of `post_len` can land inside adjacent account regions, the realloc padding, or other VM-mapped memory rather than the true serialized-length slot — corrupting account data length bookkeeping used to reconstruct account state after the transaction. Corrupted length metadata feeding into `deserialize_parameters_for_abiv1`/`abiv0` (which trust the stored length field, cf. `program-runtime/src/serialization.rs` lines 612-698) can result in the wrong account data being committed back to the ledger, i.e. false execution/state acceptance for account data. This matches the "false execution/acceptance" and potential "fund loss" impact categories for unprivileged CPI/runtime issues.

### Likelihood Explanation
Likelihood is limited by the fact that this behavior is only reachable when `syscall_parameter_address_restrictions` is **not** active for the transaction/feature-set in effect. The test suite (`programs/sbf/tests/programs.rs`, `TEST_FORBID_LEN_UPDATE_AFTER_OWNERSHIP_CHANGE_MOVING_DATA_POINTER`) explicitly documents that when the flag is enabled the runtime fails earlier (`ProgramFailedToComplete`), but when disabled it still lets CPI "write into the account data" and only catches the resulting inconsistency afterward via `ExternalAccountDataModified`: [6](#0-5) 

I could not determine from the indexed code whether `syscall_parameter_address_restrictions` is already activated on mainnet-beta (fully rolled out) or still pending/optional in this snapshot — the feature is defined in `feature-set/src/lib.rs` but its activation-epoch/status wasn't retrievable via search. If it is already universally active, this specific path is effectively dead/mitigated already (the tests suggest defenses ["FORBID..."] were added specifically for this scenario), which would reduce this to a documented, already-tested corner case rather than a live vulnerability. This uncertainty should be resolved before treating this as a live, exploitable issue.

### Recommendation
- Make the `check_account_info_pointer` validation of `data.as_ptr()` against `account_metadata.vm_data_addr` unconditional (not gated behind `syscall_parameter_address_restrictions`), so `vm_data_addr` can never diverge from the value the runtime itself established during serialization, regardless of feature-set state.
- In `update_caller_account`, before computing `serialized_len_ptr = vm_data_addr - size_of::<u64>()`, assert/verify that `vm_data_addr` equals the region start recorded in `SerializedAccountMetadata` (as already done defensively in `update_caller_account_region`'s `debug_assert_eq!(region_start_vm_addr, caller_account.vm_data_addr)` at cpi.rs:1201-1203) and turn that debug assertion into a hard runtime check on all paths.
- Add fuzz/property tests that construct `AccountInfo::data` pointers at arbitrary offsets (not just "moved past an RcBox") to confirm no legacy-path write can escape the intended account/length slot, mirroring the External Report's recommendation to test with "randomly created calldata pointers."

### Proof of Concept
Conceptual PoC (cannot be executed here, no sandbox access):
1. Deploy an SBF program (legacy ABI, `syscall_parameter_address_restrictions` inactive for the transaction) mirroring `TEST_FORBID_LEN_UPDATE_AFTER_OWNERSHIP_CHANGE_MOVING_DATA_POINTER` in `programs/sbf/rust/invoke/src/lib.rs`.
2. Overwrite `AccountInfo.data`'s inner slice pointer to point past the natural serialization start (as done via `RcBox<RefCell<&mut [u8]>>` construction in the referenced test), without going through the runtime's serializer.
3. Perform CPI to a callee that changes the account's data length (`resize`).
4. On CPI return, `update_caller_account` computes `serialized_len_ptr` from the tampered `vm_data_addr` and writes `post_len` at `vm_data_addr - 8`, landing outside the true length slot.
5. Observe corrupted serialized-length metadata; depending on adjacent memory layout, this can affect subsequent deserialization/account commit behavior instead of being uniformly caught as `ExternalAccountDataModified`.

This PoC sketch is derived directly from the existing (currently-passing, defense-oriented) test in the repo; verifying whether an *undetected* corruption variant exists (rather than the currently-caught `ExternalAccountDataModified` case) requires actual execution/fuzzing in a Devin session with full repository and toolchain access, which was not available here.
