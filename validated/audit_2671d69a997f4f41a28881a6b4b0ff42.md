Based on my investigation, `PlotNFT2Wallet.identify()` calls `PlotNFT.get_next_from_coin_spend()` on **every** singleton spend recognized during wallet sync (`chia/wallet/plotnft_wallet/plotnft_wallet.py:539-544`), before any ownership or key-matching check happens (that check occurs afterward, at lines 551-558). ### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` allows attacker-controlled memo to crash wallet sync (Python `RecursionError`) - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs nested `MofN` custody structures from a CLVM memo blob, with no depth limit. This memo originates from the `memo_blob` attached to a `CREATE_COIN` condition inside a singleton coin spend, and is parsed by wallet PlotNFT sync logic (`PlotNFT.get_next_from_coin_spend()` → `PlotNFTPuzzle`/`PlotNFT2Wallet.identify()`) before any signature, ownership, or puzzle-hash validation takes place.

### Finding Description
`PuzzleWithRestrictions.from_memo()` at `chia/wallet/puzzles/custody/custody_architecture.py:271-296` recursively calls itself for every member of a hinted `MofN` structure:
```python
puzzle: MIPSComponent = MofN(
    m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
)
```
There is no recursion-depth or size limit. This mirrors the GeoDjango bug class in the report: a WKT/WKB-style nested-structure parser (`GEOMETRYCOLLECTION` there, nested `MofN` memo hints here) that recurses proportionally to attacker-supplied nesting depth, with no bound, leading to stack exhaustion (Python `RecursionError`, which can also corrupt process state depending on where it's caught) instead of GEOS's C-level segfault.

Crucially, this parser is invoked on **untrusted, attacker-supplied data**: `singleton_create_coin.memo_blob` is populated by whoever creates the coin via a `CREATE_COIN` condition's optional memo list — a plain CLVM value with no consensus-level structural constraints (`chia/pools/plotnft_drivers.py:477-483`):
```python
if singleton_create_coin.memo_blob is None:
    raise GetNextPlotNFTError("Invalid memoization of PlotNFT")
try:
    unknown_inner_puzzle = PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())
except ValueError:
    raise GetNextPlotNFTError("Invalid memoization of PlotNFT")
```
This call happens for any coin spend recognized as a plausible singleton/PlotNFT shape during sync, and the resulting exception (`ValueError`) is the only one caught — a `RecursionError` is not a `ValueError` and will propagate out of `get_next_from_coin_spend()`.

The reachable path is `PlotNFT2Wallet.identify()` (`chia/wallet/plotnft_wallet/plotnft_wallet.py:539-544`), invoked by the wallet's coin-state sync/hint-matching pipeline whenever it observes a hinted singleton spend. This call happens **before** the ownership check (`user_key_is_owned`, lines 551-558), meaning any third party can craft a singleton spend (or even just a coin creation with a matching hint/puzzle shape and a deeply nested memo) to have this code path exercised against an arbitrary wallet syncing the chain, since sync processes all hinted/matching coin spends observed on-chain, not just the user's own.

### Impact Explanation
An uncaught `RecursionError` raised deep inside wallet sync coin-processing can abort the sync task/coroutine, and depending on how the surrounding async task and error handling is structured, this can repeatedly disrupt wallet state-manager sync processing for any wallet observing the malicious spend, causing a spend-triggered, repeatable transaction/sync-processing halt — a legitimate Medium DoS analogous to the GeoDjango GEOS segfault-DoS. This qualifies under the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
Likelihood is Medium: the attacker needs to create a coin (any spendable coin they own) with a `CREATE_COIN` condition carrying a maliciously deep, nested `MofN` memo blob and a puzzle hash/hint that causes the wallet's sync/hint matching to route it into `PlotNFT.get_next_from_coin_spend()`. Constructing the CLVM memo blob is straightforward and requires no special privileges — any spend bundle submitter can include arbitrary memos in `CREATE_COIN` conditions. The main uncertainty is confirming exactly how deep sync-time hint routing must match to trigger `identify()`/`get_next_from_coin_spend()` on an arbitrary third party's coin (this appears gated on hint/hash matching, not on the wallet already owning the singleton), which I could not fully trace end-to-end within available context.

### Recommendation
Add an explicit recursion-depth (or total-node-count) limit to `PuzzleWithRestrictions.from_memo()` and reject memos exceeding it with a caught, expected exception type (e.g. `ValueError`), and ensure calling code (`PlotNFT.get_next_from_coin_spend()`, `PlotNFT2Wallet.identify()`) treats any parsing failure — including recursion-limit or malformed-structure errors — uniformly as an invalid/unrecognized PlotNFT memo rather than letting a `RecursionError` propagate uncaught.
