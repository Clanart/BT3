## Title
Unauthenticated OP_RETURN operator-attribution in payout transactions allows permanent freezing of a deposit's vault UTXO - (File: core/src/builder/transaction/operator_reimburse.rs)

## Summary
The external report's bug class is that a value transfer (a validator withdrawal) was attributed to the wrong bookkeeping state because the classification tag (`WithdrawalDone`) was not actually bound to whether the transfer had happened. The same class of bug exists in Clementine's payout attribution: the `OP_RETURN` output that names "the operator who fronted this peg-out" is not cryptographically bound to who actually supplied the payout funds, because the only signature protecting the payout transaction (`SIGHASH_SINGLE|ANYONECANPAY`) does not cover that output. This lets an unprivileged party who controls a withdrawal request construct and broadcast the Bitcoin payout transaction themselves, stamping an unclaimable operator key into the `OP_RETURN`, permanently freezing the corresponding vault UTXO.

## Finding Description
`create_payout_txhandler` builds the payout transaction with a single signature-protected input — the user's withdrawal UTXO — and separately appends an `OP_RETURN` output carrying an arbitrary `operator_xonly_pk` parameter that is supposed to identify the operator that funded the payout: [1](#0-0) 

The withdrawal input is signed with `SIGHASH_SINGLE|ANYONECANPAY`, which the code itself documents as required: [2](#0-1) 

`SIGHASH_SINGLE|ANYONECANPAY` only commits to input #0 and the output at the matching index; it does **not** authenticate the `OP_RETURN` output, the anchor output, or any additional funding inputs added later (e.g. via `fund_raw_transaction` with `add_inputs: Some(true)`): [3](#0-2) 

Because Bitcoin transaction construction/broadcast requires no special protocol role, any party who controls a Citrea withdrawal request's authenticating signature (the withdrawing user themselves) can independently build and broadcast this exact transaction shape outside of the normal operator `withdraw()`/`Withdraw` RPC path, and set the `OP_RETURN` to any xonly public key — including one for which no registered operator holds the private key.

When this transaction confirms, `update_finalized_payouts` parses the `OP_RETURN` and persists whatever key it finds as the credited operator for that withdrawal/deposit index, without checking that it corresponds to who actually funded the transaction: [4](#0-3) 

This value is later used as the sole authorization check for reimbursement:
- `PayoutCheckerTask` only auto-claims a payout if it matches the operator's own key, so a bogus key is never picked up automatically: [5](#0-4) 
- Any operator that manually attempts a Kickoff for this deposit will be judged malicious because the on-chain-committed key doesn't match theirs: [6](#0-5) 

Since no operator can ever pass this check for a bogus/unclaimable key, the pre-signed `Reimburse` transaction that spends this deposit's `MoveToVault` `DepositInMove` output can never be safely broadcast by anyone: [7](#0-6) 

The binding this breaks is exactly the one the analog rules call out: **the operator credited (via the `OP_RETURN`) must equal the party that actually paid** — but nothing enforces that equality, so an attacker can set the credited party to a value nobody controls, permanently orphaning the deposit's vault UTXO.

## Impact Explanation
Critical — this matches the explicitly listed impact "a vault UTXO permanently frozen." Once the withdrawal UTXO for a given deposit index is spent by a payout transaction whose `OP_RETURN` key cannot be claimed by any registered operator, that deposit's `MoveToVault` output can never be reimbursed: automation never picks it up, and any manual attempt is flagged malicious and risks the attempting operator's collateral. The depositor's BTC in that vault UTXO is permanently locked with no recovery path.

## Likelihood Explanation
The attack requires no verifier/operator/aggregator/watchtower privilege — only the ability to be (or act as) the withdrawing party for a Citrea withdrawal request, which is an ordinary, unprivileged user action. The attacker does not need to observe or race anyone else's transaction; they can construct and fund the malicious payout transaction themselves from the start, at essentially no net cost (they are simply paying out their own withdrawal with a corrupted `OP_RETURN` instead of letting an operator front it).

## Recommendation
Bind the `OP_RETURN` operator attribution cryptographically to the actual funding of the payout transaction, e.g., by requiring the operator's signature to cover the `OP_RETURN` output and all additional funding inputs (extend the signed message/sighash scope, or require a separate operator signature over the committed pubkey and transaction template), so that the credited operator key can only be set by whoever actually supplies the funding inputs. Additionally, consider rejecting/ignoring as "the payout" any transaction spending the withdrawal UTXO whose `OP_RETURN` key does not correspond to a currently registered operator, rather than treating it as a valid (if unclaimed) payout that locks the vault slot.

## Proof of Concept
1. Attacker submits (or is) a normal Citrea withdrawal request, receiving withdrawal index `i` with a registered `(input_outpoint, output_script_pubkey, output_amount)` and their own signature over it (`SIGHASH_SINGLE|ANYONECANPAY`).
2. Instead of relying on an operator's `withdraw()`/`Withdraw` RPC, the attacker independently builds a raw Bitcoin transaction: input #0 = the withdrawal UTXO + their own valid signature (as in `create_payout_txhandler`), output #0 = the exact user payout output, output #1 = anchor, output #2 = `OP_RETURN` containing an xonly public key for which no registered operator has the private key, plus additional inputs (their own funds) to cover the payout amount and fees.
3. Attacker broadcasts and confirms this transaction.
4. `update_finalized_payouts` records this bogus key as `payout_payer_operator_xonly_pk` for deposit/withdrawal index `i`.
5. No operator's `PayoutCheckerTask` ever matches this key, so nobody automatically claims reimbursement; any operator manually attempting Kickoff is flagged malicious by `is_kickoff_malicious` due to the key mismatch.
6. The `Reimburse` transaction for this deposit's `MoveToVault` output can never be safely broadcast — the vault UTXO is permanently frozen.

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
}

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
