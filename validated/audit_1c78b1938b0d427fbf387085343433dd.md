## Title
Anyone can permissionlessly trigger `WombatStaking.harvest()` after front-running with a large deposit to steal a share of freshly distributed rewards from `BaseRewardPool` - (File: `wombat/WombatStaking.sol`, `rewards/BaseRewardPool.sol` / `rewards/BaseRewardPoolV2.sol`)

### Summary
`BaseRewardPool`/`BaseRewardPoolV2` distribute rewards using a `rewardPerTokenStored` accumulator that is bumped instantly, in full, based on the pool's *current* `totalStaked()` whenever new rewards are queued. Since `WombatStaking.harvest()` is a **permissionless** function that anyone can call, and deposits/withdrawals into the corresponding `MasterMagpie` pool have no cooldown or vesting, an attacker can deposit a large stake immediately before calling `harvest()`, capture a full pro-rata share of the newly harvested WOM/bribe rewards, and withdraw right after — diluting/stealing yield from genuine long-term stakers, mirroring the Covalent `OperationalStaking.rewardValidators()` new-stake dilution bug class.

### Finding Description
`_provisionReward()` in `BaseRewardPool.sol` (and the analogous function in `BaseRewardPoolV2.sol`) updates the reward accumulator based on the pool's current total stake at the moment new rewards are queued: [1](#0-0) 

`rewardPerTokenStored` is incremented by `_amountReward * 10**decimals / totalStaked()` — using whatever `totalStaked()` is *at that instant*, with no time-weighting or checkpointing of prior stake duration. A user's earned rewards is `balanceOf(user) * (rewardPerToken - userRewardPerTokenPaid[user])`, calculated in `earned()`: [2](#0-1) 

Crucially, `queueNewRewards`/reward injection is not gated to only the reward manager's off-chain-computed timing — the actual trigger for harvesting/queuing pool rewards, `WombatStaking.harvest()`, is a public, permissionless function that anyone can call at any time: [3](#0-2) 

Deposits (`WombatStaking.deposit`/`depositLP`, exposed via `WombatPoolHelper.deposit`/`depositLP`) mint receipt tokens and immediately stake them into `MasterMagpie` via `depositFor`, with no lock or cooldown: [4](#0-3) [5](#0-4) 

When a user deposits into `MasterMagpie`, `_harvestBaseRewarder` calls `rewarder.updateFor(_account)`, which sets `userRewardPerTokenPaid[account]` to the *current* (pre-harvest) `rewardPerTokenStored`: [6](#0-5) [7](#0-6) 

So the attack sequence is:
1. Attacker calls `WombatPoolHelper.depositLP()`/`deposit()` with a large amount, staking receipt tokens into `MasterMagpie`. This sets the attacker's `userRewardPerTokenPaid` at the pre-harvest baseline.
2. Attacker (or anyone observing the mempool) calls the permissionless `WombatStaking.harvest(_lpToken)`, which internally calls `queueNewRewards` on the `BaseRewardPool`, bumping `rewardPerTokenStored` based on `totalStaked()` that now includes the attacker's fresh, un-time-weighted stake.
3. Attacker's `earned()` now reflects a full pro-rata share of the just-harvested reward, despite having staked for a single block.
4. Attacker immediately withdraws via `WombatPoolHelper.withdraw()` → `WombatStaking.withdraw()` → `MasterMagpie.withdrawFor()`, which also calls `_harvestBaseRewarder`/`updateFor`, locking in the accrued `userRewards[token][attacker]` balance before removing the stake.
5. Attacker can later claim the accrued reward via the standard claim path, having paid no meaningful cost (no lock, no fee, no cooldown) beyond gas.

This directly parallels the reported bug class: unpredictable timing of reward injection is irrelevant here because the triggering function itself (`harvest()`) is permissionless, so the attacker doesn't need to front-run a manager's transaction — they control the timing entirely and can repeat the attack every time meaningful WOM/bribe rewards accumulate for a pool.

### Impact Explanation
This constitutes direct theft of yield from legitimate long-term stakers in a `BaseRewardPool`/`WombatStaking` pool. Every time an attacker executes this deposit→harvest→withdraw sequence, they dilute the reward-per-token increment (since it's now divided across a larger `totalStaked()`) and simultaneously capture a share of the full harvested amount proportional to their now-inflated stake, despite contributing none of the underlying LP/duration that generated the WOM emissions or bribes. This can be repeated indefinitely with the same capital since there is no cooldown on `recoverUnstaking`-equivalent deposit/withdraw cycles in `WombatStaking`/`WombatPoolHelper`.

### Likelihood Explanation
High. `WombatStaking.harvest()` is unrestricted (`_onlyActivePool` only checks the pool is registered, not caller identity) and callable by any address at any time. Deposits and withdrawals into the receipt-token/`MasterMagpie` flow have no minimum staking duration or cooldown. An attacker needs only capital (which can be sized to dominate `totalStaked()` for a target pool) and does not need privileged access, oracle manipulation, or governance — an ordinary wallet can execute the full sequence.

### Recommendation
Adopt a checkpoint-based or time-weighted share accounting model as suggested in the referenced report: either (a) require newly deposited stake to accrue for a minimum period before being eligible for the next reward distribution (e.g., snapshot eligible balances prior to `queueNewRewards`/`harvest` execution), or (b) restrict who/when `harvest()` can trigger `queueNewRewards`, combined with (c) a minimum staking duration / cooldown on deposit-then-withdraw cycles in `WombatStaking`/`WombatPoolHelper`/`MasterMagpie`, similar to the cooldown fix referenced in the original report's discussion for `recoverUnstaking`.

### Proof of Concept
1. Existing depositors have staked LP receipt tokens into `MasterMagpie` for pool `P`, accumulating pending WOM/bribe rewards not yet harvested (`WombatStaking` still holds unharvested WOM in the underlying Wombat pool/voter).
2. Attacker calls `WombatPoolHelper(P).depositLP(largeAmount)` (or `deposit`), receiving receipt tokens and staking them via `MasterMagpie.depositFor`, which calls `_harvestBaseRewarder` → `rewarder.updateFor(attacker)`, pinning `userRewardPerTokenPaid[attacker]` at the current (pre-harvest) value — see [6](#0-5) .
3. Attacker calls `WombatStaking.harvest(P)` (permissionless) — see [3](#0-2)  — which routes to `queueNewRewards` on the pool's `BaseRewardPool`, bumping `rewardPerTokenStored` using `totalStaked()` inflated by the attacker's fresh deposit — see [1](#0-0) .
4. Attacker's `earned()` now reflects `attackerBalance * (newRewardPerToken - pinnedRewardPerToken) / 1e_decimals`, a full share of the just-harvested reward despite one block of staking — see [2](#0-1) .
5. Attacker calls `WombatPoolHelper(P).withdraw(largeAmount, minOut)`, which triggers `MasterMagpie.withdrawFor` → `_harvestBaseRewarder`/`updateFor`, locking the ill-gotten `userRewards` balance into `userRewards[token][attacker]` before removing the stake — see [8](#0-7) .
6. Attacker later claims the accrued reward token balance normally, having diluted/stolen yield from genuine stakers who held their position through the full accrual period.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
