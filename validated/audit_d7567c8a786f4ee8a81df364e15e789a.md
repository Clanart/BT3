### Title
`SignableTransaction::new` computes `needed_fee` from a weight that omits the OP_RETURN output, so the reported/required fee understates the true cost and the achieved feerate is lower than requested - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the IdleProvider finding — where an accounting primitive (`exchangeRate`) ignores a cost component (performance fees), so `balanceUnderlying()`/`calcShares()` report figures that don't match what is actually obtained — `SignableTransaction::new` derives the transaction's required fee from a weight/vbytes calculation that omits the OP_RETURN output already appended to `tx_outs`. The resulting `needed_fee` and the change amount are computed against an understated vsize, so the constructed transaction achieves a lower feerate than the `fee_per_vbyte` the caller requested.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output carrying the caller-supplied `data` is pushed onto `tx_outs` before the weight and vbytes are measured. However, `calculate_weight_vbytes` is invoked with `payments` only — it rebuilds a scratch `Transaction` from `payments` and an optional `change` script, never including the OP_RETURN output. The measured `weight`/`vbytes` therefore exclude up to ~83+ bytes (1-byte OP_RETURN/ pushdata overhead plus up to 80 bytes of data, plus the 8-byte value and script-length fields). [1](#0-0) 

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) });
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

The same omission applies to the change path, where `fee_with_change` is also computed without the OP_RETURN output: [2](#0-1) 

`calculate_weight_vbytes` builds its scratch transaction strictly from `payments` and `change`, so the data output is structurally invisible to the fee formula: [3](#0-2) 

Additionally, the `weight` used for the `MAX_STANDARD_TX_WEIGHT` check comes from the same understated measurement, so a transaction can be accepted whose real weight exceeds the standardness limit: [4](#0-3) 

The committed fee is `sum(inputs) - sum(outputs)` (`fee()`), which is correct in absolute sats once outputs are fixed, but `needed_fee()` — the accessor documented as "the fee necessary for this transaction to achieve the fee rate specified at construction" — reports a number that does not achieve that rate: [5](#0-4) 

### Impact Explanation
Just as IdleProvider's `tokenPrice()` overstates balance and understates shares-needed because it ignores the fee deducted at withdrawal, `needed_fee` understates the sats required to reach the requested feerate because it ignores the vbytes contributed by the OP_RETURN output. When a `data` payload is present, the signed transaction broadcasts at a lower effective feerate than `fee_per_vbyte` — the gap grows with the data length (up to ~90 vbytes of uncounted size on a transaction whose typical size is only a few hundred vbytes, a materially large relative error). A transaction intended to confirm promptly can be underpriced, delayed, or — at the extreme — exceed `MAX_STANDARD_TX_WEIGHT` while passing the check. This is reachable purely from public input: `data` is an untrusted byte vector supplied to `SignableTransaction::new` (the "transaction data they cause to be signed" surface), and no internal state or key material is needed to trigger the miscalculation.

### Likelihood Explanation
Any construction path that passes a non-empty `data` payload hits the discrepancy deterministically; it does not depend on adversarial timing or validator behavior. The error is proportional to payload size, so the worst case (full 80-byte OP_RETURN) is fully attacker/integrator-controlled. The consequence is a feerate/accounting mismatch rather than direct theft, mirroring the original report's "skewed amounts, no funds lost" classification — Medium severity.

### Recommendation
Pass the fully-assembled output set (including the OP_RETURN output) into the weight calculation, e.g. compute `calculate_weight_vbytes` over `tx_outs` rather than `payments`, or add the serialized size/weight of the data output to the measured weight before deriving `vbytes`. Apply the same correction to both the no-change and with-change fee paths and to the `MAX_STANDARD_TX_WEIGHT` check so `needed_fee` and the standardness gate reflect the real transaction.

### Proof of Concept
Conceptual: construct `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)` with `input_sat` sufficient for change. The returned `needed_fee()` equals `fee_per_vbyte * vbytes` where `vbytes` was measured without the ~90-vbyte OP_RETURN output. The final `transaction()` contains that output, so `fee() / actual_vbytes < fee_per_vbyte` — the reported/required figure understates the true requirement exactly as `tokenPrice()` understates the shares needed once Idle's performance fee is applied.
