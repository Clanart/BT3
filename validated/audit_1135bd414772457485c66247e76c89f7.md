## Finding: Valid

### Title
Binary File Diff "Open in External Program" Bypasses `isSafeFileExtension` and Can Trigger Script Execution on macOS - (File: `app/src/ui/diff/binary-file.tsx`)

### Summary
The `BinaryFile` component's "Open file in external program" link calls `onOpenBinaryFile` directly, with **no extension check of any kind** — it never calls `isSafeFileExtension`. This is different from every other "Open with Default Program" entry point in the app (the Changes list context menu, rebase context menu, commit-history context menu, and PR files-changed context menu), all of which gate the action on `isSafeExtension`. Because a git repository can contain a tracked file that git classifies as binary (e.g., via `.gitattributes`, a `-diff` marker, or NUL bytes) while also carrying the executable bit and shell-script content/shebang, a malicious repository can cause Desktop to hand such a file straight to the OS shell for opening.

### Finding Description
`BinaryFile.open` builds the full path and calls `onOpenBinaryFile(fullPath)` unconditionally: [1](#0-0) 

That callback is wired (in `repository.tsx`, and similarly in the copilot-conflicts view) to `openFile()`: [2](#0-1) 

`openFile()` calls `shell.openExternal('file://' + fullPath)` with **no extension validation at all**: [3](#0-2) 

Contrast this with every other place in the codebase that exposes "Open with Default Program" — they all check `isSafeFileExtension(extension)` before enabling the action: [4](#0-3) [5](#0-4) [6](#0-5) 

`isSafeFileExtension` itself only blocks `.cmd/.exe/.bat/.sh` on Windows and unconditionally returns `true` everywhere else: [7](#0-6) 

Even where this check *is* applied, it is designed around the Windows threat model (a `.exe`/`.bat`/`.cmd`/`.sh` file being handed directly to `ShellExecute`). On macOS, Finder/Launch Services' `open` behavior for a script file with the executable bit set and a shebang is to launch it via Terminal rather than opening it in a text editor — the same class of risk the Windows-only `RestrictedFileExtensions` list was meant to prevent, just not accounted for on macOS. `Electron`'s `shell.openExternal('file://...')` on macOS delegates to `NSWorkspace`/Launch Services, which is the same "open" mechanism.

The BinaryFile diff view is reachable purely from attacker-controlled repository content: any file that `git diff`/`git status` treats as binary (e.g., via `.gitattributes` `-diff`, embedded NUL bytes, or a custom diff driver) will render the `BinaryFile` panel instead of a text diff, and the "Open file in external program" link is always active there, independent of `isSafeFileExtension`.

### Impact Explanation
If the attacker crafts a tracked file that (a) git treats as binary so `BinaryFile` is rendered, and (b) has the executable bit set and shell-script content, a user who clicks "Open file in external program" on macOS can have that script launched/executed by Launch Services/Terminal instead of being safely displayed, resulting in arbitrary code execution under the user's own privileges — sourced entirely from a cloned/fetched repository the user did not otherwise need to run.

### Likelihood Explanation
Requires the victim to open the Changes or History diff for the malicious file and click the "Open file in external program" link — a single, plausible, in-product UI action that the file's binary status invites (Desktop shows no diff, so opening externally is the natural next step). No admin rights, no prior malware, and no unnatural steps beyond normal repository review are required.

### Recommendation
- Apply `isSafeFileExtension` (or an equivalent, platform-aware safelist) to the `BinaryFile`/`openFile()` path exactly as is done for the context-menu "Open with Default Program" actions, so it isn't bypassed via the diff-view link.
- Extend the restricted-extension/behavior check to macOS and Linux — not just `__WIN32__` — including consideration of the executable bit (files with the execute permission set should not be opened via `shell.openExternal`/Launch Services regardless of extension).
- Consider using a non-executing "reveal in Finder" style default for binary files instead of directly invoking the OS open handler.

### Proof of Concept
1. Create a repository, add a file `payload.sh` containing a shebang plus a NUL byte or `.gitattributes` entry marking it `binary`/`-diff`, and `chmod +x payload.sh`; commit it.
2. Clone this repository with GitHub Desktop on macOS and select the file in the Changes or History view — it renders via `BinaryFile` (per `renderBinaryFile` in `app/src/ui/diff/index.tsx`). [8](#0-7) 
3. Click "Open file in external program." This invokes `BinaryFile.open` → `onOpenBinaryFile` → `openFile()` → `shell.openExternal('file://.../payload.sh')`, with no `isSafeFileExtension` gate applied at any point in this call chain, causing macOS Launch Services to launch/execute the script.

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
