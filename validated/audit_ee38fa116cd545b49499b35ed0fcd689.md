### Title
Unvalidated CLVM Atom Length Prefixes in `is_clvm_canonical`/`is_atom_canonical` Cause an Unhandled Crash During Spend-Bundle Admission - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` runs `is_clvm_canonical()` directly on the raw, attacker-controlled `puzzle_reveal` and `solution` bytes of every coin spend in a submitted `SpendBundle`, before any other length sanity-checking of those buffers happens in Python. `is_clvm_canonical()` and its helper `is_atom_canonical()` walk the buffer using CLVM's variable-length atom-size prefix without ever checking that enough bytes remain in the buffer to satisfy a declared prefix length or atom body, mirroring the exact bug class in CVE-2015-7975 (NTP's `nextvar` not validating the length of its input before consuming it, crashing the process).

### Finding Description
`is_atom_canonical()` reads the size-prefix control byte and then blindly walks `prefix_len` additional bytes forward: [1](#0-0) 
There is no bound check comparing `offset` (or `offset + prefix_len`) against `len(clvm_buffer)` before each `clvm_buffer[offset]` access.

`is_clvm_canonical()` calls this in a loop and also directly indexes `clvm_buffer[offset]` on every iteration with no bounds check against the buffer length: [2](#0-1) 

Both functions are invoked unconditionally on attacker-supplied bytes inside the mempool admission path, `MempoolManager.validate_spend_bundle()`, for every coin spend in a newly submitted spend bundle, with no `try`/`except` around the calls: [3](#0-2) 

Because a CLVM atom's byte-length prefix can declare 1–5 extra prefix bytes (`0xF8`/`0xFC` forms) or the pair token `0xFF` can advance `tokens_left` without any corresponding bytes remaining, a spend-bundle submitter can craft a `puzzle_reveal` or `solution` blob that is truncated relative to what its leading control byte promises. When `is_atom_canonical()`/`is_clvm_canonical()` then try to read past the end of the (short) `bytes` object, Python raises an uncaught `IndexError`, since nothing in this call chain catches it before it propagates out of `validate_spend_bundle()`.

### Impact Explanation
This is a spend-triggered transaction-processing halt: an unprivileged actor who can submit a `SpendBundle` to a full node's mempool (via RPC `push_tx`, wallet broadcast, or P2P `new_transaction`/`respond_transaction` handling that funnels into `MempoolManager.add_spend_bundle` → `validate_spend_bundle`) can supply a coin spend whose `puzzle_reveal` or `solution` is a truncated CLVM atom encoding. This raises an unhandled `IndexError` inside mempool admission logic that governs whether every subsequent spend bundle is accepted, matching the "spend-triggered transaction-processing halt" impact category called out as valid for this scan.

### Likelihood Explanation
Likelihood is high for triggering the crash condition itself: constructing a `SerializedProgram`/`Program` with a size-prefix byte (e.g. `0xF8`, `0xFC`) declaring a longer body/prefix than the actual buffer contains is trivial and requires no privileged access, signing keys, or coordination — only a syntactically-arbitrary puzzle reveal/solution byte string attached to any coin spend the submitter references in the `SpendBundle`. No other validation step in `validate_spend_bundle()` runs before the `is_clvm_canonical()` calls at lines 723–726, so the crafted buffer reaches the vulnerable code on the very first spend-bundle-processing pass.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` and `is_clvm_canonical()` before every buffer index/slice — verify `offset < len(clvm_buffer)` prior to reading `clvm_buffer[offset]`, and verify `offset + prefix_len < len(clvm_buffer)` before the prefix-length loop in `is_atom_canonical()` — returning `False` (non-canonical) or raising a handled `ValueError`/`ConsensusError` instead of allowing a raw `IndexError` to propagate. Additionally, wrap the `is_clvm_canonical()` calls in `validate_spend_bundle()` in a `try/except` that treats any parsing failure as `Err.INVALID_COIN_SOLUTION`, consistent with how other malformed-input paths in this codebase (e.g. `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list`) explicitly validate lengths and raise catchable `ValueError`s rather than depending on implicit bounds checking.

### Proof of Concept
1. Construct a `CoinSpend` whose `solution` (or `puzzle_reveal`) is the raw bytes `b"\xf8"` — a valid start-of-atom control byte declaring a 5-byte length prefix (`0xF8` matches the `(b & 0b11111110) == 0b11111100`... actually `0xF8` matches the 4-prefix-byte case) — but supply no further bytes after it.
2. Wrap it in a `SpendBundle` with an arbitrary/empty aggregated signature and submit it through the node's spend-bundle admission path (`MempoolManager.add_spend_bundle` → `validate_spend_bundle`).
3. Execution reaches: [4](#0-3) 
which calls `is_clvm_canonical(bytes(coin_spend.solution))`, which calls `is_atom_canonical(clvm_buffer, 0)`, which attempts to read `clvm_buffer[offset]` for `offset` beyond the 1-byte buffer, raising an unhandled `IndexError` out of the admission pipeline.
