### Title
`ThresholdKeys::read` / `ThresholdKeys::new` accept a secret share inconsistent with the verification shares, letting attacker-supplied key bytes silently redefine the signing identity - (File: crypto/dkg/src/lib.rs)

### Summary
The CVAT bug class is "state-mutating/deserializing endpoints that accept attacker-controlled fields without validating them against the resource's authority model." The Serai analog is `ThresholdKeys::read`, which ingests fully attacker-controlled `t, n, i`, an interpolation blob, a `secret_share`, and a map of `verification_shares`, and then constructs `ThresholdKeys` via `ThresholdKeys::new`. `new` validates counts and participant bounds, but never checks the one relation that binds the secret to the public state: `G * secret_share == verification_shares[i]`. The deserialized object is therefore a self-inconsistent "key" whose every derived property (group key, views, produced shares) is attacker-defined.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses `t`, `n`, `i`, `Interpolation`, `secret_share`, and `n` verification shares entirely from the input stream, then delegates to `ThresholdKeys::new`. `new` (crypto/dkg/src/lib.rs:349-391) only enforces:

- `verification_shares.len() == n` and every participant index `<= n` (lines 355-365),
- `t == n` for constant interpolation (lines 367-374),
- and derives `group_key` by interpolating `verification_shares[1..=t]` (lines 376-378).

At no point does it verify that `C::generator() * secret_share == verification_shares[i]` — the standard Pedersen-VSS consistency check that PedPoP itself performs during key generation (`verify_share` in crypto/dkg/pedpop). The honest-DKG path guarantees this invariant by construction; the deserialization path does not. `view()` (lines 463-533) then blindly interpolates whatever `secret_share` was supplied and reports `group_key` derived from the attacker-chosen verification shares.

Two concrete outcomes from crafted bytes:

1. **Signing under an attacker-defined group key.** The attacker sets `verification_shares` to shares of a polynomial whose constant term is an attacker-known secret `x` (so `group_key = x*G`), and sets `secret_share` to the corresponding share for `i`. `view()` yields a self-consistent key set under `x*G`; FROST `sign`/`complete` executed on this view produces valid signatures under `x*G` — a group key that was never generated by the threshold set. If these bytes reach a participant through any provisioning/recovery/migration channel that consumes `ThresholdKeys::read`, the participant signs for a key the attacker fully controls.

2. **Silent share corruption / wrongful blame.** The attacker keeps the honest `verification_shares` (real group key `K`) but supplies a `secret_share` that is not the honest share. `view()` interpolates a wrong share; the FROST signature share it produces fails verification against `verification_shares[l]`, so `complete` aborts and — in any deployment with blame attribution — the holder of the tampered keys is identified as the faulty/malicious signer. An attacker who can write one party's serialized keys converts them into a permanently "malicious" participant, a direct analog of CVAT's unauthorized modification of resource-associated state.

### Impact Explanation
Any consumer that loads `ThresholdKeys` from bytes it did not itself write in the same trusted session — restore-from-backup, key import, coordinator-distributed key material — inherits an unvalidated assertion of *which* secret corresponds to *which* group key. The result is either signatures issued under an attacker-chosen group key (integrity of every downstream signature-verifying system is broken) or denial-of-service plus misattributed blame for the victim participant. This matches the Medium-severity profile of the source bug: it requires the attacker to reach the input channel but no collusion, no leaked key, and no malicious validator in the honest threshold.

### Likelihood Explanation
Medium-low: exploitation needs a deployment path where serialized `ThresholdKeys` cross a trust boundary (backup/restore or import), which is plausible but integrator-dependent. The defect itself is unconditional — a missing invariant check on a public `read`/`new` path explicitly exposed to untrusted bytes.

### Recommendation
In `ThresholdKeys::new`, after the existing parameter checks, verify `C::generator() * secret_share.deref() == verification_shares[&params.i()]` (returning a `DkgError` on mismatch). This binds the deserialized secret to the committed public state and closes both the key-substitution and share-corruption variants at the single construction chokepoint shared by `read`, PedPoP, and promotion/recovery.

### Proof of Concept
```rust
// Conceptual, Secp256k1 ciphersuite
let n = 3u16; let t = 2u16;
// Attacker polynomial f(0) = x (attacker-known), shares s1..s3
let x = Scalar::random(&mut OsRng);
let mut shares = poly_shares(x, t, n); // any degree-1 poly with f(0)=x
let vshares: HashMap<_, _> =
    (1..=n).map(|l| (Participant::new(l).unwrap(), G::generator() * shares[l])).collect();

// Craft bytes with i=1, secret_share=shares[1]
let mut buf = vec![];
// id_len, ID, t, n, i, interpolation=1 (Lagrange), secret_share, vshares[1..=n]
let keys = ThresholdKeys::<Secp256k1>::read(&mut buf.as_slice()).unwrap(); // accepted
assert_eq!(keys.group_key(), G::generator() * x); // group key fully attacker-controlled

// Any FROST AlgorithmMachine built on keys.view(...) produces valid
// signatures under x*G despite x never arising from a threshold keygen.
```

Variant 2: serialize honest `vshares` with a random `secret_share`; `read` succeeds, `view(i)` produces a share that fails `complete`, and the victim is blamed as the faulty signer.
