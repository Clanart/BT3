Audit Report

## Title
No vulnerability found: `calculate_block_reward()`'s per-delegation clamp does not actually permit aggregate over-payment beyond `pending_delegator_rewards` under the codebase's real invariants - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

## Summary
The claim asserts that `calculate_block_reward()` can pay out, in aggregate across all delegations to one vote account, more than that vote account's `pending_delegator_rewards`, because the `.min(pending_delegator_rewards)` clamp is applied per-delegation rather than to a running total. Investigation of the actual denominator source (`RewardEpochDelegatedStakes`) and how it is computed/persisted shows the premise that `sum(stake_i) > total_active_stake` is a realistic, reachable condition is not supported by the code as written; the denominator is derived from, and is consistent with, the same per-delegation effective-stake computation used at payout time.

## Finding Description
`calculate_block_reward()` divides `pending_delegator_rewards` proportionally by `stake / total_active_stake` and clamps the individual result to `pending_delegator_rewards`, as the claim correctly quotes. [1](#0-0) 

However, `total_active_stake` (`RewardEpochDelegatedStakes::delegated_stakes`) is not an independently-drifting value. It is computed once, at the reward epoch boundary, as the sum over **all** stake delegations to a vote account of `delegation_activation_status(delegation, self.epoch, &self.stake_history, ...).effective` — i.e., built from the exact same activation/effective-stake math (`delegation_effective_stake` / `delegation_activation_status` in `runtime/src/stake_delegation.rs`) that `calculate_block_reward()` later uses per-delegation. [2](#0-1)  This value is then persisted on-chain via `RewardEpochDelegatedStakes::set()`. [3](#0-2) 

On recalculation (after partial distribution or snapshot restore), the code explicitly re-fetches the *persisted* `RewardEpochDelegatedStakes` rather than recomputing it from current, possibly-mutated stake state: `RewardEpochDelegatedStakes::get(self)`. [4](#0-3)  The codebase has a dedicated regression test, `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`, whose explicit purpose is to prove that recalculation after partial distribution "must use the same AG delegated stake denominator as the original epoch-boundary calculation" even when a stake delegation's on-chain state has since changed due to a distributed reward. [5](#0-4)  This test asserts the unpaid delegation's reward is identical before and after the mutation, which directly contradicts the claim's exploit scenario (that `stake_i` values used at redemption can diverge upward from the frozen `total_active_stake` in a way that inflates aggregate payout).

The code comment cited by the claim ("During recalculation, if stake account has already received rewards, it's possible to have `stake > total_active_stake`") describes a bounded, already-acknowledged edge case that the author explicitly judged "harmless in practice" and defensively clamped per-delegation — not an unbounded aggregate-overpay vector. The claim does not identify any code path where `sum(stake_i)` computed with `delegation_effective_stake(delegation, rewarded_epoch, stake_history, ...)` at the *same* `rewarded_epoch` and *same* historical `stake_history` snapshot can exceed the `total_active_stake` that was computed by summing that identical function over the identical delegation set. The claim's own "Likelihood Explanation" concedes uncertainty ("I was not able to fully trace whether ... clamps the sum before it is ever stored... is inconclusive") and its PoC is explicitly "not independently reproduced," relying entirely on an extrapolation from a defensive comment rather than a demonstrated code path or failing test.

## Impact Explanation
Not applicable — no reachable aggregate over-payment path was found. The existing clamp, the frozen/persisted nature of `RewardEpochDelegatedStakes`, and the regression test guarding recalculation consistency together contradict the claimed divergence mechanism.

## Likelihood Explanation
Not applicable. The claim itself acknowledges it could not confirm the absence of a masking/aggregate check and did not produce a working reproduction; the available evidence (denominator construction and the dedicated recalculation-consistency test) indicates the asserted divergence condition is not actually reachable in the current implementation.

## Recommendation
No action required based on current evidence. If further investigation is desired, it should focus on constructing a concrete Rust unit test with multiple stake delegations to a single vote account and asserting `sum(calculate_block_reward(...)) <= pending_delegator_rewards` across a real recalculation cycle (extending `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`-style scenarios to multiple delegations) — but the current per-delegation-consistent denominator construction found in `runtime/src/stakes.rs` provides no evidence this would fail.

## Proof of Concept
Not established. The claim's own PoC section states the scenario was "not independently reproduced against a live cluster from local code alone," and this audit found no test or code path demonstrating `sum(stake_i) > total_active_stake` under the actual denominator-construction and recalculation-consistency logic in `runtime/src/stakes.rs:449-502` and `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:1038-1095`.
