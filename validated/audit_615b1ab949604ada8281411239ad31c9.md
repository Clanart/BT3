### Title
Duplicate `ReceivedOutput` inputs are counted twice, producing an unspendable Bitcoin transaction - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` accepts multiple `ReceivedOutput`s representing the same Bitcoin outpoint. It sums each supplied output’s claimed value and creates a transaction input for every entry without checking whether `previous_output` is unique. An attacker who can supply crafted bytes to `ReceivedOutput::read`, or otherwise influence the input list, can make one UTXO count multiple times. The resulting transaction is signed but is consensus-invalid because it contains duplicate inputs.

### Finding Description
`ReceivedOutput` stores `offset`, `output`, and `outpoint` independently, and its deserializer accepts those fields without establishing that the outpoint is unique in any later input set. [1](#0-0) 

`SignableTransaction::new` computes total available funds by summing `input.output.value` over the entire vector. [2](#0-1) 

It then converts every supplied `ReceivedOutput` into a `TxIn` using `input.outpoint`, with no `HashSet`, `BTreeSet`, ordering check, or other duplicate-outpoint rejection. [3](#0-2) 

The duplicated accounting also propagates into `prevouts` and `fee()`: each duplicate contributes its claimed `TxOut` to the reported input amount. [4](#0-3) [5](#0-4) 

During multisig construction, every input is independently assigned the corresponding offset and checked only for whether the derived key matches that supplied `TxOut` script. Duplicates therefore pass this check as well. [6](#0-5) 

### Impact Explanation
A caller can represent one spendable UTXO as two or more inputs. `input_sat`, `prevouts`, and the transaction’s input list all count the same coin repeatedly, so the wallet may believe a payment is funded when it is not.

The generated transaction cannot actually spend the duplicated amount. Bitcoin consensus permits each transaction input to reference a distinct outpoint; repeating the same `previous_output` makes the transaction invalid regardless of the signatures. This can turn an accepted withdrawal or consolidation plan into an unexecutable transaction and incorrectly report its funding/fee capacity.

### Likelihood Explanation
The ordinary `Scanner` path derives each `ReceivedOutput` from an actual transaction output, so scanner-produced lists are unlikely to naturally contain identical outpoints. [7](#0-6) 

However, `ReceivedOutput::read` accepts serialized `offset`, `TxOut`, and `OutPoint` fields directly, and `SignableTransaction::new` trusts the resulting vector without checking chain authenticity or uniqueness. Any integration that accepts, restores, relays, or merges attacker-influenced `ReceivedOutput` records can reach the flaw. [8](#0-7) 

### Recommendation
Reject duplicate `ReceivedOutput::outpoint`s in `SignableTransaction::new` before summing inputs or constructing `tx_ins`. Track observed outpoints in a `HashSet<OutPoint>`/`BTreeSet<OutPoint>` and return a new `TransactionError::DuplicateInput`.

At minimum, the invariant should be enforced before:

- `input_sat` is calculated;
- `offsets` and `tx_ins` are built;
- `prevouts` is stored.

### Proof of Concept
Conceptually, duplicate one valid scanned output and ask the wallet to spend slightly less than twice its value:

```rust
// One real spendable output obtained from Scanner::scan_transaction.
let first = scanned_output.clone();
// A byte-level duplicate, as could arrive through untrusted serialization.
let second =
  ReceivedOutput::read(&mut first.serialize().as_slice()).unwrap();

let tx = SignableTransaction::new(
  vec![first, second],
  &[(payment_script, (2 * scanned_output.value()) - sufficient_fee)],
  None,
  None,
  fee_per_vbyte,
).unwrap();

assert_eq!(
  tx.transaction().input[0].previous_output,
  tx.transaction().input[1].previous_output,
);
```

`SignableTransaction::new` accepts because the duplicated output’s value is included twice in `input_sat`, and it emits two transaction inputs for the same `previous_output`. [9](#0-8) 

`multisig` also accepts the duplicated input because both entries have the same offset and matching Taproot script, so signing proceeds over a transaction that Bitcoin nodes must reject. [10](#0-9)

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Returns None if the wrong keys are used.
  pub fn multisig(self, keys: &ThresholdKeys<Secp256k1>) -> Option<TransactionMachine> {
    let mut sigs = vec![];
    for i in 0 .. self.tx.input.len() {
      let offset = keys.clone().offset(self.offsets[i]);
      if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
        None?;
      }

      sigs.push(AlgorithmMachine::new(Schnorr::new(), keys.clone().offset(self.offsets[i])));
    }

    Some(TransactionMachine { tx: self, sigs })
  }
