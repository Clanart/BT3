### Title
Predictable/weak hash seed enables algorithmic-complexity (hash-flooding) attack on upb `map<string,...>` fields — (`upb/hash/common.c`)

### Summary
CVE-2021-41119 describes a JSON hash-flooding DoS: an attacker sends a crafted object whose keys collide in the server's hash table, driving parsing/lookup from O(n) to O(n²). The transferable invariant is: *any hash table populated from attacker-controlled keys during parsing must use a hash function whose seed is unpredictable to the attacker (or otherwise resistant to collision construction), or the attacker can force worst-case bucket-chaining behavior.* In this Protobuf checkout, upb's `upb_strtable` (backing all `map<string, V>` / `map<bytes, V>` fields decoded from binary wire format via `upb/wire/decode.c:_upb_Decoder_DecodeToMap` → `upb/message/internal/map.h:_upb_Map_Insert` → `upb_strtable_insert`) uses `_upb_Hash_NoSeed`, which is explicitly documented as providing weak, non-cryptographic randomization.

### Finding Description
`upb/hash/common.c` (mirrored verbatim in the generated `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`) defines: [1](#0-0) 
`_upb_Seed()` returns the address of a static process-global variable, explicitly commented as "does not provide high-quality randomness... provided that ASLR is enabled." This seed is fixed for the lifetime of the process (not per-table, not per-parse-call) and is combined with a fixed, compile-time constant salt array `kWyhashSalt`: [2](#0-1) 
Every `map<string,...>` or `map<bytes,...>` field parsed from binary wire format goes through this exact hash: `upb/wire/decode.c` builds the map via `_upb_Decoder_CreateMap`/`_upb_Decoder_DecodeToMap`, then calls `_upb_Map_Insert`, which for string-keyed maps calls `upb_strtable_insert` using `_upb_Hash_NoSeed`: [3](#0-2) [4](#0-3) 
Because the seed derives only from ASLR entropy of a single process-wide address (not re-randomized per message, not a CSPRNG), it is far weaker than the per-process high-entropy seeding used by, e.g., Python's `str` hash (SipHash with `PYTHONHASHSEED`) or Go/Abseil's `absl::Hash` with dynamic per-process seeds sourced from OS randomness at multiple points. If ASLR is disabled/limited (common in some container/hardened-kernel/32-bit configurations, or when the attacker can infer/leak a single heap/text address via a side channel), the seed becomes predictable, and an attacker who knows (or brute-forces offline) the fixed `kWyhashSalt` and Wyhash construction can precompute a large set of string keys that collide into the same bucket chain of `upb_strtable`'s linked hash table. Note by contrast that the equivalent C++ core `Map` implementation salts using `absl::HashOf` combined with the *table pointer* rotated by key size (`src/google/protobuf/map.h:696-703`), which is arguably similarly weak (also ASLR-derived, not cryptographic) — so this weakness is systemic across upb and core `Map`, not isolated to one binding.

### Impact Explanation
An attacker who can submit a bounded-size binary Protobuf (or JSON via upb's JSON decoder, which also funnels map string keys through `upb_strtable_insert`) message containing a `map<string, V>` field with many keys that collide under the predictable/weak Wyhash-with-ASLR-seed can force the internal singly-linked bucket chains in `upb_strtable` to degrade to O(n) per insertion, yielding O(n²) total parse time for n keys — the same class of impact as CVE-2021-41119 (quadratic-time DoS via crafted keys), scoped to a single bounded message rather than requiring huge/unbounded input. This affects the upb-based Python, Ruby, and PHP language bindings (all of which link the identical `upb_strtable`/`_upb_Hash_NoSeed` code shown above) whenever application code parses attacker-supplied bytes into a message containing a string/bytes-keyed map field.

### Likelihood Explanation
Exploitability hinges on the seed being predictable enough to precompute a large colliding key set offline. This requires either (a) ASLR being disabled/weak in the target environment, or (b) an address-leak side channel — reducing likelihood versus a pure algorithmic flaw with no seeding at all. The comment in the source explicitly acknowledges the seed is not high-quality and is only "enough to prevent unit tests from relying on a deterministic map ordering," which is a materially weaker security bar than "resistant to a motivated attacker constructing collisions." Given schemas/registries here are trusted and the payload is bounded, this is a Medium-likelihood, not Critical, condition — it is preserved per the prompt's guidance to keep eligible Medium findings only if impact is proven, which here is architecturally plausible but not proven without ASLR bypass, so it should not be forced to High/Critical.

### Recommendation
Replace `_upb_Seed()`'s ASLR-address-based seed with a proper per-process cryptographically-strong random seed sourced from the OS CSPRNG at process/library-init time (as `absl::flat_hash_map` and modern SipHash-based containers do), and consider re-seeding or adding a secondary collision-count fallback (e.g., converting long bucket chains to a balanced structure, as Java's `HashMap` does via treeification) for `upb_strtable`. Apply the same fix to the C++ core `Map`'s `Hash()` function in `src/google/protobuf/map.h`, which has the analogous ASLR-derived salt.

### Proof of Concept
A concrete PoC requires computing Wyhash collisions offline against the fixed `kWyhashSalt` constant and a guessed/leaked ASLR seed value, then serializing a binary Protobuf message with a `map<string, int32>` field containing thousands of such colliding keys, and measuring parse time via `upb_Decode`/language-binding `ParseFromString`. This trace establishes the reachable code path and the weak-seed root cause; timing measurements to confirm quadratic blowup were not run in this review and would need to be executed against a built binary with a fixed/known ASLR seed (e.g., `setarch -R` or ASLR disabled) to demonstrate the worst-case degradation empirically.
