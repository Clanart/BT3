### Title
Truncated 128-bit `ModuleId` hash in `aptos_framework::init` allows cross-module collision to bypass the object-ownership-change self-init guard - (File: `aptos-move/framework/aptos-framework/sources/init.move`)

### Summary
The lazy module self-initialization gate (`aptos_framework::init`) is supposed to guarantee that a module deployed to an object can only self-initialize (rerun `init_module`-style privileged setup via `internal_maybe_initialize`) while the object's transitive root owner is unchanged since that specific module's last publish. This guarantee is enforced by storing a per-module `deploy_owner` keyed by a `ModuleId` that is derived from a SHA3-256 hash of the module's name **truncated to 16 bytes (128 bits)**. Because the key space is reduced to 128 bits, an attacker who controls the source module names inside their own package (which is normal, unprivileged capability for anyone publishing code to an object they own) can find two distinct module names whose truncated hashes collide, and use a later publish of the colliding-name module to silently overwrite the `deploy_owner` record of an unrelated module at the same address — reviving self-init eligibility for a module whose owner actually did change, defeating the documented invariant.

### Finding Description
`aptos_framework::init` records, per object address, a map from `ModuleId` to `ModuleState { only_once, deploy_owner }`: [1](#0-0) 

`ModuleId` is computed purely from the module's *name*, by hashing it with SHA3-256 and then truncating to 16 bytes: [2](#0-1) 

`code::publish_package` calls `init::record_deploy_owner(addr, module_name, owner)` for every module name in the package being (re)published to an object, recording the object's current transitive root owner: [3](#0-2) [4](#0-3) 

At call time, `internal_maybe_initialize` derives the caller's `(addr, module_id)` from the real calling module (via the native `get_caller_address_and_module_id`), and gates the signer grant on `assert_may_self_initialize`, which compares the **recorded** deploy owner against the **current** root owner of the object: [5](#0-4) 

Since `ModuleId` only depends on the module name (not on the module's full identity/bytecode) and the hash is truncated to 128 bits, two *different* module names can produce an identical `ModuleId` with roughly 2^64 hash trials (a classic birthday-bound collision search that can be done completely offline, with no on-chain interaction, before ever publishing anything). Module name uniqueness is only enforced textually within a package (`EMODULE_NAME_CLASH` compares literal names, not truncated hashes), so nothing prevents a package from containing (or later adding, via upgrade) a module whose name happens to collide, under the truncated hash, with an existing module already recorded in `InitializationState` at the same address.

Exploit path:
1. Attacker deploys an object-hosted package (`object_code_deployment::publish`) containing module `A`, owned by the attacker. `record_deploy_owner(O, "A", attacker)` is stored under `ModuleId = H`.
2. Offline, the attacker precomputes a second valid Move identifier `"B"` such that `module_id_from_name("B") == H` (a ~2^64-effort SHA3-256 birthday search — computationally significant but not out of reach, comparable in cost to the real-world SHAttered SHA-1 collision, which was produced for roughly $110K of cloud compute in 2017).
3. Attacker transfers the object `O` to a new owner (e.g., relinquishing control, or to simulate a legitimate ownership transfer). Per the documented invariant, module `A` should now be permanently blocked from self-initializing under the new owner (`EOWNER_CHANGED_SINCE_DEPLOY`).
4. Attacker (while they still control publishing rights, or via `upgrade`) republishes/upgrades the package to add module `B` at the same object address `O`. `code::publish_package` calls `record_deploy_owner(O, "B", new_owner)`, which — because `ModuleId("B") == ModuleId("A") == H` — **overwrites** the `ModuleState` entry that module `A` actually uses, setting its recorded `deploy_owner` to `new_owner`.
5. Module `A`'s (unmodified) code later calls `internal_maybe_initialize`; the native resolves its true `ModuleId = H`, `assert_may_self_initialize` now finds `recorded == new_owner == current root owner`, and incorrectly authorizes self-initialization — even though module `A`'s own record should reflect the *attacker's* original ownership, not the new owner's.

This directly breaks the invariant stated in the module's own documentation ("A module on an object cannot self-initialize once the object changed owner... since that module's code was last published") via a code-safety verifier gap: the identity used to gate privileged initialization is not injective over module names.

### Impact Explanation
This is a code-ownership/authorization bypass in the on-chain module self-initialization mechanism gating privileged `init_module`-style logic for object-hosted code. It lets an unprivileged package author (attacker) resurrect self-init eligibility for a module after an ownership change that was specifically designed to revoke it, potentially allowing re-execution of privileged initialization code (capability minting, signer capability re-acquisition, resource re-creation, etc.) under conditions the framework was built to forbid. This falls squarely under "unauthorized... code-object ownership change" and "verifier/module-init... write-set-publish failure that reaches protected state mutation" in the publish impact gate.

### Likelihood Explanation
The root cause (module name is fully attacker-controlled, and hash truncation to 128 bits) is exploitable by any unprivileged account able to publish/upgrade object code — no special permissions needed. The limiting factor is the offline SHA3-256 birthday-collision search (~2^64 hash evaluations), which is expensive but has real-world precedent at comparable cost (e.g., the SHAttered SHA-1 collision, ~2^63.1 operations, produced for roughly $110K of cloud compute in 2017). This is a design flaw (unnecessary hash truncation reducing collision resistance from a 256-bit security level to a 64-bit birthday-bound) rather than a purely theoretical concern, and 128-bit output hashes are explicitly discouraged by modern security guidance for exactly this reason.

### Recommendation
- Do not truncate the SHA3-256 hash when deriving `ModuleId`; use the full 256-bit hash (or otherwise ensure the identifier space has full 256-bit/128-bit-collision-resistant security), eliminating the birthday-bound collision.
- Alternatively/additionally, key `ModuleState` by the full module name (or a domain-separated hash covering the whole name plus package/address context) instead of a truncated digest, so no two distinct module names can ever alias to the same state slot.
- Add an explicit invariant/test asserting that `record_deploy_owner` never overwrites an existing `ModuleState` entry whose associated module name differs from the one currently being recorded (defense-in-depth even if the hash algorithm changes later).

### Proof of Concept
A full PoC requires an offline SHA3-256 birthday search (feasible per the cost analysis above but impractical to execute in this review), followed by a straightforward Move e2e test using the pattern already present in the framework's own tests (`self_init_blocked_when_owner_transferred` in `init.move`):

1. Publish object package with module named `A` (attacker-owned object).
2. Transfer the object to `new_owner`.
3. Republish/upgrade the object package to add a module whose name `B` collides (`module_id_from_name("B") == module_id_from_name("A")`), which calls `record_deploy_owner(O, "B", new_owner)` and overwrites `A`'s slot.
4. Call an entry function that triggers `A::init_module` via `internal_maybe_initialize`; observe that `assert_may_self_initialize` now succeeds for `A` (comparing `new_owner == new_owner`) instead of aborting with `EOWNER_CHANGED_SINCE_DEPLOY`, contrary to the guarantee demonstrated by `republished_sibling_does_not_rearm_transferred_module` in the same file, which the collision defeats: [6](#0-5) 

The existing test explicitly checks that republishing a *different, non-colliding* sibling module does not re-arm the transferred one — this finding shows that guarantee no longer holds when the sibling module name is chosen (via the offline collision search) to alias the same `ModuleId`.

    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
    /// publish, so a transfer of the object or an ancestor, or its deletion, blocks self-init; an
    /// object with no record is fail-closed. Account addresses authorize their own code by publishing.
    fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
        let recorded = recorded_deploy_owner(addr, module_id);

            object::is_object(addr)

            !object::is_object(addr)
        };
