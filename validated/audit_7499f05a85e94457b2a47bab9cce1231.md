Audit Report

## Title
Permissionless `DepositDelegatorRewards` griefing permanently blocks vote-account closure/withdrawal for un-delegated vote accounts - (File: `programs/vote/src/vote_state/mod.rs`)

## Summary
`deposit_delegator_rewards` allows any signer to transfer an arbitrary amount (as little as 1 lamport) into any V4 vote account, unconditionally incrementing `pending_delegator_rewards` via `add_pending_delegator_rewards`, with no relationship to the vote account's authorities required. [1](#0-0)  The `withdraw` instruction refuses to fully close a vote account, or to withdraw below `rent_exempt_minimum + pending_delegator_rewards`, whenever `pending_delegator_rewards > 0`. [2](#0-1)  The only mechanism that decrements this field is `calculate_block_reward`, which returns `0` (i.e., redeems nothing) when `total_active_stake` for the vote account is `0`, since that value is looked up per-delegation from `reward_epoch_delegated_stakes`. [3](#0-2)  Because a vote account with zero delegated stake has no stake-delegation entries pointing at it, the redemption loop never executes for it, leaving any griefed `pending_delegator_rewards` balance permanently stuck.

## Finding Description
`add_pending_delegator_rewards` in `programs/vote/src/vote_state/handler.rs` performs an unconditional `checked_add` on `v4.pending_delegator_rewards` with no cap or minimum-threshold check. [4](#0-3)  `deposit_delegator_rewards` only requires the *sender* to sign the transfer (`verify_authorized_signer(&source_address, signers)`); it does not check any relationship between the sender and the target vote account's authorized voter/withdrawer, making the call fully permissionless with respect to the target vote account. [5](#0-4)  The instruction is only gated by three feature flags (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`), not by any permission check on the caller. [6](#0-5) 

`withdraw()` treats `pending_delegator_rewards` as an untouchable reserve: it unconditionally rejects full closure (`remaining_balance == 0`) with `InstructionError::InsufficientFunds` if `pending_delegator_rewards > 0`, and for partial withdrawals requires the remaining balance to be at least `rent_exempt_minimum + pending_delegator_rewards`. [2](#0-1)  There is no other guard or escape hatch in this function for the case where the reserved amount can never be redeemed.

The only reduction path is `calculate_block_reward`, invoked once per stake delegation targeting the vote account during epoch reward distribution; it explicitly returns `0` when `total_active_stake == 0` for that vote account. [3](#0-2)  Since this function is only invoked in the context of an existing stake `Delegation` pointing at the vote account, a vote account with zero delegated stake has no invocations of this function at all — it is not merely a no-op, the reward computation loop for that vote account simply never runs. I found no other code path in `programs/vote/src/vote_state/handler.rs`, `programs/vote/src/vote_state/mod.rs`, or `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` that decrements or clears `pending_delegator_rewards` outside this per-delegation epoch-reward flow.

This confirms the claimed exploit path: an attacker calls `DepositDelegatorRewards` on a vote account currently lacking delegated stake, permanently setting `pending_delegator_rewards > 0` with no mechanism to ever reduce it, thereby permanently blocking that vote account's authorized withdrawer from closing the account or withdrawing below the (now-inflated) minimum balance.

## Impact Explanation
This is an unprivileged, negligible-cost (deposit as low as 1 lamport plus transaction fee) fund-lock/DoS against a specific validator's vote account. The authorized withdrawer's legitimate `withdraw()` calls to reclaim the rent-exempt reserve or fully close the account will permanently fail with `InstructionError::InsufficientFunds` for any vote account that has no active delegated stake at the time of the griefing deposit and never subsequently attracts stake sufficient to trigger reward redemption of that exact residual amount. This falls under "fund theft/loss" style impact in the accounts/runtime/built-ins scope, as it permanently locks lamports (the reserved `pending_delegator_rewards` amount plus, in the full-closure case, the entire account balance) away from their rightful owner (the authorized withdrawer), with the exact corrupted value being the vote account's `pending_delegator_rewards` field.

## Likelihood Explanation
High. The attack requires only a signer able to pay a transfer of an arbitrary (even trivial) amount and a transaction fee; no special permissions, timing, or relationship to the target vote account are needed beyond the three feature flags being active. [6](#0-5)  Any vote account that is newly created, mid-way through deactivating all delegated stake, or otherwise has zero active delegated stake at a given time is a viable, repeatable target, and the attack can be repeated cheaply against any number of vote accounts.

## Recommendation
- Bound accepted `DepositDelegatorRewards` deposits to a computed expected-reward amount, or restrict the caller to the runtime/an authorized party, rather than allowing arbitrary unprivileged deposits from any signer.
- Provide a mechanism (e.g., available to the authorized withdrawer) to reclaim, burn, or redistribute a stranded `pending_delegator_rewards` balance when the vote account has zero active delegated stake, so the withdrawal reserve implemented in `withdraw()` (`programs/vote/src/vote_state/mod.rs:1084-1122`) cannot become permanently unspendable.

## Proof of Concept
1. Attacker (any signer) submits `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` targeting a vote account with zero currently-delegated stake, per `deposit_delegator_rewards` (`programs/vote/src/vote_state/mod.rs:936-988`), which requires only the source account to sign.
2. `add_pending_delegator_rewards` increments the vote account's `pending_delegator_rewards` field to `1` (`programs/vote/src/vote_state/handler.rs:196-209`).
3. Because no `Delegation` currently targets this vote account, `calculate_block_reward` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-231`) is never invoked for it during epoch reward distribution, so `pending_delegator_rewards` is never reduced.
4. The authorized withdrawer later calls `withdraw()` attempting to fully close the vote account; the call fails with `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0` (`programs/vote/src/vote_state/mod.rs:1084-1122`), and this failure persists indefinitely unless stake happens to be delegated to the account and enough epochs pass to redeem exactly that residual amount.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
