### Title
`ReceivedOutput::read` accepts an arbitrary scalar offset not bound to the output's `script_pubkey`, letting attacker-supplied bytes misattribute received funds to a nonexistent key - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The CVE-2018-10928 bug class is "an attacker-supplied reference resolves to a target outside the intended domain" (symlink destinations escaping the volume). The analog in Serai is the `offset` field of `ReceivedOutput`: it is a reference that resolves which group key can spend a scanned Bitcoin output (`attributed key = script_pubkey_key - offset*G`). `ReceivedOutput::read` deserializes `offset` via `Secp256k1::read_F` with no check that `offset` is one of the offsets the `Scanner` actually registered for that script. Only `Scanner::scan_transaction` enforces the script → offset binding; `read` drops that binding entirely.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` where each entry is a registered, validated offset (`Scalar::ZERO` for the base key, plus securely-generated offsets from `register_offset`) (`networks/bitcoin/src/wallet/mod.rs:153-196`). `scan_transaction` only emits a `ReceivedOutput` when `output.script_pubkey` matches a registered script, so the emitted `offset` is always the correct inverse for that script (`networks/bitcoin/src/wallet/mod.rs:199-213`).

`ReceivedOutput::read`, however, reads `offset` and `output` independently:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-133
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ...
  output = TxOut::consensus_decode(&mut buf_r)...;
  outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

Nothing verifies `output.script_pubkey == p2tr_script_buf(scanner_key + offset*G)`, or that `offset` is in the registered set. The downstream consumer trusts the field: `Output::key()` computes the attributed multisig key as `script_pubkey_key - GENERATOR * offset` (`processor/src/networks/bitcoin.rs:112-122`), and `get_outputs`/scanner code classifies and attributes the output using that derived key (`processor/src/networks/bitcoin.rs:686-699`). Spending re-keys the `ThresholdKeys` via `ThresholdKeys::offset(offset)` so that `group_key() = key + offset*G` (`crypto/dkg/src/lib.rs:414-446`).

### Impact Explanation
An attacker who can feed bytes to `ReceivedOutput::read` (it is a documented untrusted-bytes sink in scope) can take a real on-chain output paying to a registered script `S = (K + o_real*G)` and pair it with a different offset `o'`. The output is then attributed to key `K' = K + (o_real - o')*G` — a group key for which no `ThresholdKeys`/shares exist (or a key belonging to a different multisig/session). The funds are real on-chain but are credited under a key that cannot produce a valid spend: the signer set for `K'` doesn't exist, and honest participants signing under key `K` with offset `o'` would produce `K + o'*G ≠ S`, failing to spend. This yields "funds reported received that are not spendable" — deposits become stranded or misrouted between multisig sessions, matching the CVE pattern of an attacker-controlled reference escaping its intended domain.

### Likelihood Explanation
Exploitation requires an attacker to reach a deserialization path for `ReceivedOutput` outside the `Scanner`-produced flow (e.g., relayed/forwarded output data, DB entries populated from external input, or cross-service messages). It does not require collusion, a malicious validator, or any secret knowledge — the offset is a plain public scalar and the script_pubkey can be copied from the chain. No discrete-log or hash-preimage work is needed because the attacker is corrupting the binding between two already-valid fields, not forging a key.

### Recommendation
Bind the offset to the script at decode/validation time: either make `ReceivedOutput::read` take the owning `Scanner` (or the base key plus registered-offset set) and reject outputs whose `p2tr_script_buf(key + offset*G) != output.script_pubkey`, or add a `ReceivedOutput::verify(&self, key) -> bool` that consumers must call before trusting `offset()`/`key()`. At minimum, `Output::key()` in `processor/src/networks/bitcoin.rs` should cross-check `self.output.output().script_pubkey` against the expected script for `(key(), offset())` rather than trusting the serialized pair.

### Proof of Concept
1. From the chain, take a confirmed deposit output `O` with `O.script_pubkey = p2tr(K + o_real*G)` and outpoint `P` (public data).
2. Craft bytes: `offset' = o_real + 1` (canonical `Scalar`), followed by consensus-encoded `O` and `P`.
3. `ReceivedOutput::read` accepts this (all fields individually well-formed).
4. `Output::key()` returns `K + o_real*G - o'*G = K - G` — a valid point attributed as the owning multisig key.
5. The processor records the deposit under `K - G` instead of `K`. No `ThresholdKeys` exist for `K - G`; signing under `K` offset by `o'` produces `K + (o_real+1)*G ≠ S`. The confirmed deposit is reported received yet is unspendable.

Note: I verified the decode path, `Output::key()` derivation, and the offset application in `ThresholdKeys`/`Scanner` directly; I did not fully trace every call site that feeds attacker bytes into `ReceivedOutput::read` within the remaining iteration budget, so the reachability claim rests on `ReceivedOutput::read` being an in-scope untrusted-bytes sink per the scan rules.
