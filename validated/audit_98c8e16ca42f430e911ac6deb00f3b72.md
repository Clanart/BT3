### Title
`getWorkingDirectoryDiff` silently omits already-staged changes for renamed files, allowing attacker-controlled content to be committed/pushed without appearing in the diff - (File: `app/src/lib/git/diff.ts`)

### Summary
For files whose status is `Renamed`, `getWorkingDirectoryDiff` deliberately diffs the working tree against the **index**, not against `HEAD`, as it does for every other file status. The code's own comment acknowledges this is wrong: staged content that differs from `HEAD` is invisible in the diff the user reviews before committing. [1](#0-0) 

### Finding Description
In `getWorkingDirectoryDiff`, the argument construction branches on file status:
- New/Untracked files: diff against `/dev/null` via `--no-index`.
- Renamed files: diff **without** a target ref, which makes `git diff` compare the working tree to the **index** only.
- Everything else (Modified, Deleted, Copied, etc.): diff explicitly against `HEAD`. [2](#0-1) 

The in-code comment explains the consequence directly: "By diffing against the index we won't show any changes already staged to the renamed file which differs from our other diffs," and that the correct fix (diff `blob <-> blob` via `hash-object`) was not implemented "because that seems a bit excessive." [3](#0-2) 

This matters because the index can be manipulated by sources outside of direct user typing — e.g. a merge/rebase/cherry-pick that resolves a rename with attacker-controlled content from a fetched branch, a Git LFS/merge driver, a pre-commit hook, or any git-porcelain interaction that stages content into the index. If a rename lands in the index with content that already differs from `HEAD` (e.g. malicious content merged in via a crafted incoming branch during a rename conflict resolution), and the user's working tree matches the index (i.e., they haven't made further edits), `getWorkingDirectoryDiff` will show an **empty diff** for that file (as literally demonstrated by the test `is empty for a renamed file`), even though the committed blob differs substantially from `HEAD`. [4](#0-3) 

Even in the "renamed and modified" case, the diff view only shows the delta between what's staged and what's on disk — never the delta between what's staged and `HEAD`. So any content that entered the index via a source other than the visible working-tree edit (fetched merge content, conflict resolution, filters/attributes, hooks) is committed/pushed with zero visual review, because `getWorkingDirectoryDiff` is what the Changes view (`stageFiles`/commit flow) uses to render what the user is about to commit. [5](#0-4) 

The upstream project attempted to address a related symptom via changelog item "#17467 Inform user when a staged renamed file has changes," but no corresponding banner/guard code (`hasStagedChanges`, warning banner, etc.) could be found anywhere in the current source tree — only the changelog entry itself references it, and the `diff.ts` implementation and its explanatory "technically incorrect" comment remain unchanged in this codebase. This strongly suggests the underlying broken-invariant path (diff against index instead of HEAD for renames) is still present and unguarded in this snapshot.

### Impact Explanation
This falls into "silent corruption of what the user commits or pushes": the Desktop diff view is the sole gate the user relies on before clicking Commit, and for renamed files it can display no changes (or only partial changes) while the actual blob staged for commit differs from `HEAD`. A malicious/crafted upstream branch merged during a rename-conflict resolution, or any tool that stages content into the index outside of the visible working-directory edit, can cause a user to unknowingly commit and push attacker-influenced content. This is a genuine "what you see is not what you commit" integrity bug, not a crash or hardening issue.

### Likelihood Explanation
The rename path is common (any `git mv`/detected rename, including during merges of externally-fetched branches), and the bug is structural, not a rare edge case — the code path is always taken for `AppFileStatusKind.Renamed`, and the repository's own test suite confirms the empty-diff behavior (`is empty for a renamed file`). No unusual local access or social engineering is required beyond normal repository interactions (fetch/merge/rename-conflict resolution), which fits the "attacker controls a fetched repository" threat model.

### Recommendation
Implement the diff for renamed files as `git diff <blob@HEAD:oldPath> <blob@index:newPath>` (via `hash-object`/`--no-index` on temp blobs, or `git diff HEAD -- oldPath newPath` restructured to include staged deltas) so that any content in the index that differs from `HEAD` is always shown, matching the behavior used for Modified/Deleted files. At minimum, surface an explicit warning banner when a renamed file's staged content differs from what's shown in the working-directory diff, verifying it is actually wired up (the changelog references such a fix, but no corresponding code was found in this snapshot).

### Proof of Concept
Adapted from the existing unit test that demonstrates the empty-diff behavior: [4](#0-3) 

1. Commit `foo` with content `foo\n`.
2. Simulate an attacker-influenced merge/rebase that resolves a rename of `foo` -> `bar` and stages `bar` with malicious content `malicious payload\n` (differing from `HEAD`'s `foo\n`) directly into the index (e.g., via `git mv` + `git add` inside a merge, or a merge driver).
3. Do **not** touch the working tree further (working tree matches index).
4. Call `getWorkingDirectoryDiff(repo, files[0])` — per the existing test pattern, this returns a diff with `hunks.length === 0`, i.e., no visual indication of the malicious content.
5. User reviews an empty/innocuous diff, clicks Commit, and pushes — the malicious content is committed and pushed without ever being shown to the user.
