### Title
Permissionless `donateRewards` trusts caller-supplied amount instead of actual tokens received, allowing reward accounting corruption for non-standard ERC20 tokens - (File: rewards/BaseRewardPool.sol, rewards/BaseRewardPoolV2.sol, rewards/mWOMSVBaseRewarder.sol, rewards/BribeRewardPool.sol)

### Summary
`BaseRewardPool.donateRewards` is an unprivileged, permissionless external function (no `onlyManager`/`onlyOwner` check) that any wallet can call for any token that is already registered as a reward token [1](#0-0) . It forwards straight to `_provisionReward`, which trusts the caller-supplied `_amountReward` for all internal accounting instead of measuring the actual balance change resulting from the `safeTransferFrom` call [2](#0-1) . The identical pattern exists in `BaseRewardPoolV2._provisionReward` [3](#0-2)  and `mWOMSVBaseRewarder._provisionReward` [4](#0-3) , and `rewards/BribeRewardPool.sol` also exposes this pattern (a `donateRewards`-style function was found there but its full body was not retrieved before the tool budget was exhausted).

### Finding Description
This is the same bug class as the external report: a reward-deposit function updates internal reward-per-token accounting using the *intended* transfer amount rather than the *actually received* amount. The original report focuses on `type(uint256).max`-special-cased tokens like cUSDCv3, but the root cause is broader — it also affects fee-on-transfer or deflationary/rebasing ERC20 tokens, which the reported fix explicitly notes it also resolves ("This mitigation also resolves the issue related to incorrect accounting for fee-on-transfer tokens.").

In `_provisionReward`:
```solidity
IERC20(_rewardToken).safeTransferFrom(msg.sender, address(this), _amountReward);
Reward storage rewardInfo = rewards[_rewardToken];
rewardInfo.historicalRewards += _amountReward;
...
rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / totalStaked();
``` [5](#0-4) 

There is no balance-before/balance-after check, so if the actual amount received by the contract is less than `_amountReward` (fee-on-transfer token, deflationary token, or a `transferFrom` that silently caps the amount like Compound's cToken `type(uint256).max` semantics), `rewardPerTokenStored` is inflated relative to the tokens actually held by the pool.

Critically, `donateRewards` has **no access control beyond `isRewardToken[_rewardToken]`** [6](#0-5) , meaning any ordinary wallet — not just a manager — can trigger this corrupted accounting path for any token that has already been registered as a reward token in that pool (registration itself happens via the manager-only `queueNewRewards`, but once a token is registered any wallet can call `donateRewards` for it repeatedly).

### Impact Explanation
If `rewardPerTokenStored` becomes inflated beyond the pool's actual token balance, subsequent legitimate reward claims via `getReward`/`getRewards` (`IERC20(rewardToken).safeTransfer(_receiver, reward)`) will attempt to pay out more tokens than the contract holds [7](#0-6) . Once the shortfall exceeds the remaining balance, transfers for other stakers will revert, permanently freezing already-accrued, unclaimed reward tokens for all users of that pool/reward-token pair. This constitutes protocol insolvency / permanent freezing of unclaimed yield for the affected reward token.

### Likelihood Explanation
Exploitability depends on whether a registered reward token behaves non-standardly (fee-on-transfer, deflationary/rebasing, or capped-transfer semantics). This is plausible for pools where reward tokens are not curated to be "plain vanilla" ERC20s (e.g., bribe reward tokens submitted for third-party incentive campaigns via the bribe/rewarder registration flow), and the attack requires only calling the already-public `donateRewards` function — no privileged role needed. Likelihood is moderate: it requires a specific non-standard token to be an already-registered reward token, but the code contains no defense (no balance-diff check) regardless of which token is used.

### Recommendation
Adopt the same fix pattern verified by Cyfrin for the referenced report: measure the actual token balance delta after `safeTransferFrom` and use that measured amount (not the caller-supplied `_amountReward`) for all downstream accounting (`historicalRewards`, `queuedRewards`, `rewardPerTokenStored`) in `_provisionReward` across `BaseRewardPool.sol`, `BaseRewardPoolV2.sol`, `mWOMSVBaseRewarder.sol`, and `BribeRewardPool.sol`:
```solidity
uint256 balBefore = IERC20(_rewardToken).balanceOf(address(this));
IERC20(_rewardToken).safeTransferFrom(msg.sender, address(this), _amountReward);
uint256 actualAmount = IERC20(_rewardToken).balanceOf(address(this)) - balBefore;
// use actualAmount in place of _amountReward for all subsequent accounting
```

### Proof of Concept
1. Governance/manager registers a reward token `T` for a `BaseRewardPool` via `queueNewRewards` (sets `isRewardToken[T] = true`).
2. `T` has non-standard transfer semantics — e.g., a fee-on-transfer token that deducts 2% on every transfer, or a Compound-style cToken that caps `transferFrom(from, to, type(uint256).max)` to the sender's actual balance.
3. Attacker (any wallet) calls `donateRewards(largeAmount, T)`. `safeTransferFrom` only moves the actual (smaller) amount into the pool, but `_provisionReward` still increments `rewardInfo.historicalRewards` and `rewardInfo.rewardPerTokenStored` using the full `largeAmount` parameter [5](#0-4) .
4. `rewardPerTokenStored` for token `T` is now inflated beyond the pool's real `T` balance.
5. As legitimate stakers call `getReward`, later claimants' `safeTransfer(_receiver, reward)` calls revert due to insufficient contract balance, permanently locking their already-accrued `T` rewards [7](#0-6) .

        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
