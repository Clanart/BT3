### Title
Attacker-controlled file paths from tracked repository content bypass path-traversal guards used elsewhere and reach filesystem-revealing/editor-launch sinks - ([File: app/src/lib/app-shell.ts])

### Summary
`revealInFileManager` in [1](#0-0)  and multiple UI call sites (`app/src/ui/changes/sidebar.tsx`, `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/ui/app.tsx`) build a filesystem path with `Path.join(repository.path, path)` using a `path` value that originates from Git-reported file paths (working directory status, commit diffs, PR diffs) without ever validating that the resulting path stays inside the repository. This is the same broken-invariant pattern as the Astaria bug: a value (`lien.last` / here, the repo-relative `path`) is trusted to satisfy an invariant (bounded within `[lien.start, lien.start+duration]` / here, "inside the repository") purely because of where it came from, and it is then fed unchecked into a sensitive downstream operation (a subtraction that can underflow / here, `shell.showItemInFolder` or the external editor spawn).

Elsewhere in the same codebase this exact class of risk is explicitly recognized and mitigated: `buildConflictContext` in `app/src/lib/copilot-conflict-context.ts` uses `resolveWithin(workingDirectory, file.path)` specifically to "guard against path traversal and symlink escapes" before reading a Git-reported conflict path [2](#0-1) , and `resolveWithin` itself is tested against `..`-escaping and symlink-escaping paths [3](#0-2) . However, the sinks in `app-shell.ts`, `sidebar.tsx`, `selected-commits.tsx`, `pull-request-files-changed.tsx`, and `app.tsx`'s `onOpenInExternalEditor` do not apply the same `resolveWithin` check before joining and using the path [4](#0-3) [5](#0-4) [6](#0-5) .

### Finding Description
`Path.join(repository.path, path)` does not prevent `..` segments in `path` from escaping `repository.path`; on POSIX and Windows, `path.join('/repo', '../../etc/passwd')` legitimately resolves outside `/repo`. The `path` value passed to these join calls comes from `WorkingDirectoryFileChange.path` / `CommittedFileChange.path`, which in turn is populated from `git status --porcelain` or `git diff` output (see `status-parser.ts` referenced in `app/src/lib/git/status.ts` line 182-184 for how status codes/paths are parsed) — i.e., ultimately from tree entries that can originate from a cloned or fetched repository under attacker control (a maliciously crafted tree with a path containing `../` sequences, or a symlinked directory entry checked out into the working copy).

Once such a path exists in the working directory or a commit diff, the resulting `fullyQualifiedFilePath` / `fullPath` is handed to:
- `shell.showItemInFolder(fullyQualifiedFilePath)` (`revealInFileManager`) — reveals/selects an arbitrary filesystem path outside the repo in the OS file manager.
- `dispatcher.openInExternalEditor(fullPath)` / `launchExternalEditor` — spawns the user's configured editor with an arbitrary absolute path as an argument [7](#0-6) .
- `openFile(fullPath, dispatcher)` (open with default program).

None of these call sites re-derive or re-validate the path the way `buildConflictContext` does with `resolveWithin`, so the invariant "this path is inside the repository working directory" — which the UI assumes because it displays paths as repo-relative — is not actually enforced at the point of use, exactly mirroring how `lien.last` is trusted to be within `[lien.start, end]` without re-validation at the point where `end - lien.last` is computed.

### Impact Explanation
An attacker who controls a cloned/fetched repository (a git remote or a repository a victim opens/clones) can craft tree entries or working-directory content whose reported path contains traversal segments or resolves via a symlink to a location outside the repository. When the user interacts with GitHub Desktop's context menus (Reveal in Finder/Explorer, Open in external editor, Open with default program) for such an entry, the app operates on a path outside the intended repository sandbox. This can result in: launching an arbitrary local file/editor process against an attacker-chosen path, or revealing/selecting arbitrary filesystem locations — a "file read/operate outside the repo" class of impact enabled purely by attacker-controlled repository content, consistent with the valid-impact criteria (attacker controls a cloned/fetched repository, no local/prior-access or social engineering required beyond normal repo browsing).

### Likelihood Explanation
Likelihood is moderate: it requires the user to right-click a specific file entry and choose "Reveal in File Manager" / "Open in external editor" / "Open with default program", which is a normal, expected user action (not an unnatural step), triggered by simply browsing changes/commits/PR diffs in a repository the attacker controls. The application already recognizes this exact risk class internally (the `resolveWithin` guard exists and is unit-tested), which indicates the gap in the unguarded call sites is a genuine oversight rather than an accepted risk.

### Recommendation
Route every `Path.join(repository.path, path)` (or equivalent) construction that originates from Git-reported paths (working directory status, commit diffs, PR diffs, conflict files) through the existing `resolveWithin` guard (already used in `copilot-conflict-context.ts`) before passing the result to `shell.showItemInFolder`, `launchExternalEditor`/`launchCustomExternalEditor`, or `openFile`. Reject or surface an error for any path that resolves outside `repository.path`, consistent with how `buildConflictContext` currently handles this.

### Proof of Concept
1. Attacker creates/publishes a repository whose tree contains a path such as `foo/../../../../tmp/evil` or a working-tree entry that is a symlink pointing outside the repo (POSIX) reported by `git status` as a tracked/untracked file path.
2. Victim clones/fetches this repository into GitHub Desktop and opens the "Changes" or "History" view, where the malicious path appears as a file entry (`WorkingDirectoryFileChange`/`CommittedFileChange`).
3. Victim right-clicks the entry and selects "Reveal in File Manager", "Open in external editor", or "Open with default program".
4. `Path.join(repository.path, path)` in `app/src/ui/changes/sidebar.tsx` (or the analogous call sites) resolves to a path outside `repository.path` because `path.join` does not sanitize `..` traversal, and this un-validated path is passed to `shell.showItemInFolder` / `launchExternalEditor`, operating on a filesystem location the user did not intend to expose, in contrast to the protected path in `app/src/lib/copilot-conflict-context.ts` which would reject the same input via `resolveWithin`.

    const root = process.cwd()

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
      assert((await resolveWithin(root, 'foo\0bar')) === null)
    })

    it('succeeds for absolute relative paths as long as they stay within the root', async () => {
      const parent = resolve(root, '..')
      assert.equal(await resolveWithin(parent, root), root)
    })

    if (!__WIN32__) {
