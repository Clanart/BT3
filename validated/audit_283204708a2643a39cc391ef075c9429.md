## Analog Found

### Title
CR-CAT payments become permanently stuck if the recipient never obtains an authorized VC (no reclaim path from the "pending approval" state) - (File: `chia/wallet/vc_wallet/cr_cat_drivers.py`)

### Summary
The reported bug is that `SolverVaults.requestWithdraw()` irrevocably burns the caller's SVT before the collateral transfer is attempted, so if the `receiver` is (or becomes) blocklisted, the burned value is permanently unrecoverable. The chia analog is Credential-Restricted CATs (CR-CATs): a sender can move a CR-CAT to any inner puzzle hash, but if the recipient's wallet is not already tracked, the coin is committed to a hard-coded "pending approval" puzzle. That coin can only ever be spent by presenting a valid VC proof satisfying the CR-CAT's `proofs_checker`/`authorized_providers`. If the intended recipient never has (or loses/never obtains) such a VC — the functional equivalent of being "blocklisted" from the credential-restriction perspective — the coin is permanently unspendable, exactly like the burned-SVT/blocklisted-receiver scenario.

### Finding Description
`construct_pending_approval_state()` curries a fixed output condition (`CREATE_COIN puzzle_hash amount [puzzle_hash]`) into `PENDING_VC_ANNOUNCEMENT` [1](#0-0) . When a CR-CAT is spent to a puzzle hash the sending wallet doesn't recognize as its own, the receiving wallet records the coin as `CoinType.CRCAT_PENDING` rather than `CoinType.CRCAT` [2](#0-1) .

The only way to move this coin out of the pending state is `claim_pending_approval_balance()`, which requires locating a VC in the local wallet whose provider is in `self.info.authorized_providers` and which has valid proofs matching `self.info.proofs_checker.flags`: [3](#0-2) 
If no such VC exists, the call raises `RuntimeError("No VC exists that can approve spends for CR-CAT wallet ...")` [4](#0-3) . There is no alternative unlock path, no sender-side reclaim/timelock, and no way to reroute the coin to a different, VC-holding recipient, because the destination puzzle hash and amount are hard-curried into the pending puzzle at creation time.

This mirrors the SolverVaults flaw structurally: the sender's asset-transfer step (`CATWallet`/`CRCATWallet` spend) is finalized on-chain unconditionally (analogous to the SVT burn) before the "authorization/allowlist" check (the VC/proofs-checker match, analogous to the blocklist check) is satisfied. If the recipient's credential status is or becomes non-compliant (revoked DID, expired/insufficient proofs, no VC at all), the previously-committed CAT value is permanently locked with no recovery mechanism.

### Impact Explanation
Any CR-CAT sender can unknowingly (or a malicious counterparty can deliberately, e.g. in an offer, via `add_vc_authorization`'s "pending state" carve-out [5](#0-4) ) cause CAT value to be sent to a puzzle hash whose owner can never produce a satisfying VC. That value becomes permanently frozen — no burn event, no supply loss accounting, but a real, unrecoverable loss of usable funds for a legitimate user, which is a High-severity fund-lock condition reachable from a single wallet-issued spend/offer.

### Likelihood Explanation
This can be triggered by any wallet user sending a CR-CAT (a spend type explicitly supported by the wallet and offer flows) to a recipient whose VC eligibility is unknown, revoked, or never granted. Because the recipient's credential status can change after the transfer is broadcast (VC revocation is a normal, expected operation for CR-CATs), this is a realistic operational scenario, not a contrived edge case.

### Recommendation
Provide a recovery path for coins stuck in the CR-CAT "pending approval" state — e.g., allow the original sender (or a timelocked fallback) to reclaim the payment if it is never approved within a bounded period, similar to the clawback mechanism already used for XCH transfers [6](#0-5) . Alternatively, require wallets constructing CR-CAT payments to verify the recipient currently holds a valid, matching VC before finalizing the spend, rather than optimistically routing to the fixed pending-approval puzzle.

### Proof of Concept
1. Wallet A holds a CR-CAT restricted to `authorized_providers = [DID_X]` with a given `proofs_checker`.
2. Wallet A sends an amount to `puzzle_hash_B` (owned by user B) via the normal CR-CAT spend path; because B's wallet is not recognized locally, `add_crcat_coin` records the output coin as `CoinType.CRCAT_PENDING` bound to `construct_pending_approval_state(puzzle_hash_B, amount)`.
3. Before or after this spend confirms, the DID `DID_X` revokes B's VC (a supported, intended VC operation), or B simply never acquires a VC from any `authorized_providers`.
4. B calls `crcat_approve_pending` → `claim_pending_approval_balance()`; `vc_wallet.get_vc_with_provider_in_and_proofs` returns `None`, raising `RuntimeError("No VC exists that can approve spends for CR-CAT wallet ...")`.
5. The coin remains forever in the `CRCAT_PENDING` state: A cannot reclaim it (no such API/puzzle path exists) and B cannot claim it (no valid VC). The transferred value is permanently stuck.

def construct_pending_approval_state(puzzle_hash: bytes32, amount: uint64) -> Program:
