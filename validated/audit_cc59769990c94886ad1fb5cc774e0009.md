### Title
Unbounded, non-cancellable native precompile execution can stall block production past the block time limit - ([File: blockchain/vm/evm.go])

### Summary
The reported OpenComputers CVE (CVE-2024-31446) is a class of "native call cannot be interrupted, blocking the host thread" DoS: a Lua native library call ignores `xpcall`/interrupt signals, so a single user script can hang a whole server thread that only cooperative-yield checks can normally interrupt. The closest reachable analog in this Kaia codebase is the fact that the EVM's cancellation/time-limit mechanism (`evm.abort`) is only checked *between* opcodes in the interpreter's main loop and inside a couple of jump opcodes, but is **never checked while a precompiled contract's native `Run()` is executing**.

### Finding Description
The interpreter's main loop explicitly polls the abort flag on every opcode step: [1](#0-0) 

and jump-family opcodes additionally check `interpreter.evm.Cancelled()` so that tight `JUMP`/`JUMPI` loops can be aborted quickly: [2](#0-1) 

However, when a `CALL`-family opcode targets a precompiled contract address, execution takes a completely different path: `run()` looks up the precompile and calls `RunPrecompiledContract`, which charges gas once and then invokes the native `Run(...)` method to completion, with no abort/cancel check at all: [3](#0-2) [4](#0-3) 

The abort flag (`evm.abort`) and the `CancelByTotalTimeLimit`/`CancelByCtxDone` reasons are the mechanism the block-proposer worker uses to stop a running EVM once the per-block time budget is exhausted: [5](#0-4) 

That watchdog goroutine calls `evm.Cancel(vm.CancelByTotalTimeLimit)` when the timer fires, expecting the currently executing EVM to notice and abort promptly, exactly like the interpreter's opcode loop does. But because `RunPrecompiledContract`/native `Run()` never inspects `evm.abort`, any precompile whose native computation time is large relative to its declared gas/computation cost will run to completion regardless of the timeout signal, blocking the worker goroutine that is producing the block — analogous to OpenComputers' native Lua call ignoring the interrupt and blocking the server thread.

The gas/computation-cost values charged for each precompile (e.g., `EcrecoverComputationCost`, `Bls12381PairingBaseComputationCost`, `Bls12381G2MulComputationCost`, `P256VerifyComputationCost`, MODEXP's `berlinModexpGas`/`osakaModexpGas`) are static estimates: [6](#0-5) [7](#0-6) 

If the real wall-clock cost of any precompile's `Run()` implementation is under-priced for some crafted input (e.g. a MODEXP overflow-adjacent input, or a BLS12-381 pairing/multi-exp call sized near the discount-table boundary), the caller pays comparatively little gas/computation-cost budget yet the goroutine executing it cannot be preempted mid-call. This directly negates the `params.OpcodeComputationCostLimit` / `BlockGenerationTimeLimit` safety nets that the rest of the EVM relies on for bounding per-transaction and per-block wall-clock execution time.

### Impact Explanation
Any unprivileged transaction sender can submit an EVM `CALL` to a precompiled contract address with attacker-chosen input. If that precompile's native implementation has a real execution time not proportional to the gas/computation cost charged, the sender can consume the block proposer's/validator's execution goroutine for longer than intended, and — unlike normal opcode execution — this cannot be aborted by the `CancelByTotalTimeLimit`/`CancelByCtxDone` mechanisms once the native `Run()` call has started. Repeated or crafted such calls could delay or stall block assembly on the proposer, a state-divergence/availability risk reachable purely by submitting transactions.

### Likelihood Explanation
Exploitability depends entirely on finding a specific precompile input where measured CPU time is disproportionately larger than its charged gas/computation cost (the pricing formulas for MODEXP, BLS12-381 operations, and P256VERIFY are the natural places to look). I was not able to fully verify, within the tool budget, whether any of the currently priced precompiles (MODEXP, BLS12-381 family, P256VERIFY, ECRECOVER, SHA256/RIPEMD160/IDENTITY) actually contain such a mispriced worst case in this codebase's implementation — the gas formulas for MODEXP in particular are the standard, previously-audited EIP-2565/EIP-7883 formulas designed to prevent exactly this. Without confirming a concrete underpriced input, this should be treated as a structural gap (missing cancellation check inside precompile execution) rather than a confirmed exploitable timing mismatch.

### Recommendation
- Add periodic abort/cancellation checks inside any precompile whose `Run()` performs a data-dependent loop (e.g., MODEXP's big-integer exponentiation loop, BLS12-381 multi-exp loops), similar to the `in.evm.abort.Load()` check in the interpreter loop, so a timed-out or cancelled EVM cannot be blocked by native precompile execution.
- Alternatively/additionally, re-audit each precompile's `GetRequiredGasAndComputationCost` against actual worst-case CPU time on the deployed hardware to ensure computation cost tracks real time closely enough that `OpcodeComputationCostLimit`/`BlockGenerationTimeLimit` remain effective upper bounds even without in-call cancellation.

### Proof of Concept
Not fully constructible from static analysis alone: exploitation requires an empirically-verified precompile input (e.g., a MODEXP or BLS12-381 call) whose native `Run()` wall-clock time is disproportionate to its charged gas/computation cost, submitted via a normal transaction's `CALL` to the precompile address, while the block proposer's `BlockGenerationTimeLimit` watchdog is active (`work/worker.go` `ApplyTransactions`). I could not confirm such an input within the available investigation, so this finding is reported as a structural gap in the cancellation mechanism (missing abort checks in `RunPrecompiledContract`/native `Run()`) rather than a demonstrated end-to-end timing exploit.

// RunPrecompiledContract runs and evaluates the output of a precompiled contract.
func RunPrecompiledContract(p PrecompiledContract, input []byte, contract *Contract, evm *EVM) (ret []byte, computationCost uint64, err error) {
	gas, computationCost := p.GetRequiredGasAndComputationCost(input)
	if contract.UseGas(gas) {
		ret, err = p.Run(input, contract, evm)
		return ret, computationCost, err
	}
	return nil, computationCost, kerrors.ErrOutOfGas
}

// GetRequiredGasAndComputationCost returns the gas required to execute the pre-compiled contract
// and the computation cost of the precompiled contract.
func (c *bigModExp) GetRequiredGasAndComputationCost(input []byte) (uint64, uint64) {
	// Parse input lengths
	baseLenBig := new(uint256.Int).SetBytes(getData(input, 0, 32))
	expLenBig := new(uint256.Int).SetBytes(getData(input, 32, 32))
	modLenBig := new(uint256.Int).SetBytes(getData(input, 64, 32))

	// Convert to uint64, capping at max value
	baseLen := baseLenBig.Uint64()
	if !baseLenBig.IsUint64() {
		baseLen = math.MaxUint64
	}
	expLen := expLenBig.Uint64()
	if !expLenBig.IsUint64() {
		expLen = math.MaxUint64
	}
	modLen := modLenBig.Uint64()
	if !modLenBig.IsUint64() {
		modLen = math.MaxUint64
	}

	// Skip the header
	if len(input) > 96 {
		input = input[96:]
	} else {
		input = input[:0]
	}

	// Retrieve the head 32 bytes of exp for the adjusted exponent length
	var expHead uint256.Int
	if uint64(len(input)) > baseLen {
		if expLen > 32 {
			expHead.SetBytes(getData(input, baseLen, 32))
		} else {
			expHead.SetBytes(getData(input, baseLen, expLen))
		}
	}

	// Choose the appropriate gas calculation based on the EIP flags
	if c.eip7883 {
		gas := osakaModexpGas(baseLen, expLen, modLen, expHead)
		return gas, gas/100 + params.BigModExpBaseComputationCost
	} else if c.eip2565 {
		gas := berlinModexpGas(baseLen, expLen, modLen, expHead)
		if gas == math.MaxUint64 {
			// Contract: Kaia doesn't divide computation cost by 100 for backward compatibility
			return math.MaxUint64, math.MaxUint64
		}
		return gas, gas/100 + params.BigModExpBaseComputationCost
	} else {
		gas := byzantiumModexpGas(baseLen, expLen, modLen, expHead)
		if gas == math.MaxUint64 {
			// Contract: Kaia doesn't divide computation cost by 100 for backward compatibility
			return math.MaxUint64, math.MaxUint64
		}
		return gas, gas/100 + params.BigModExpBaseComputationCost
	}
