## Analog Found

### Title
Forged `WWW-Authenticate` realm lets an attacker-controlled git host impersonate a GitHub Enterprise endpoint and hijack the sign-in/credential flow - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Hats finding is a classic "self-declared identity trusted without verification" bug: `IncentivesController.handleAction()` trusts `msg.sender`'s claim to be a registered `aToken` instead of checking it against a real registry. The same broken-invariant pattern exists in GitHub Desktop's git credential trampoline: `getEndpointKind()` classifies a remote host as a trusted "GitHub"/"enterprise" endpoint based on a **self-reported, attacker-controlled `WWW-Authenticate` header value**, rather than any cryptographic or registry-based verification. That misclassification then drives the credential-helper into launching a full GitHub sign-in/OAuth flow scoped to the attacker's endpoint.

### Finding Description
When Git needs credentials for an HTTPS remote, it forwards any `WWW-Authenticate` response headers it received from the server to Desktop's credential helper as `wwwauth[...]` fields [1](#0-0) . `getEndpointKind()` treats a header containing `realm="GitHub"` as proof that the remote is a "GitHub Enterprise" host: [2](#0-1) 

This value comes entirely from the remote server's HTTP response — a value under full control of whoever operates the git remote (or a MITM/malicious proxy in front of it), analogous to `msg.sender` in the Hats report being an unverified claim of identity. Nothing in this code path checks that the host is actually a real GitHub/GHE instance (the `isGitHubHost()` network probe is only used as a last resort, and is bypassed entirely once the forged header matches).

Once `getEndpointKind()` returns `'enterprise'` for a host with no matching stored account, `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)` [3](#0-2) . That, in turn, calls `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` using the **attacker-controlled origin** taken straight from the credential URL, then shows a "Sign in to GitHub Enterprise" popup: [4](#0-3) 

This entire chain can be triggered without any explicit user action beyond a normal git operation (`fetch`/`push`/`pull`/`clone --recursive`) against a remote that the attacker controls — e.g. a malicious `origin` in a shared/forked repository, or a malicious submodule URL pulled in via `.gitmodules` during `updateSubmodulesAfterOperation()` [5](#0-4) , both of which are exactly the "attacker controls a cloned/fetched repository / git remote or proxy response" scenario called out as in-scope.

### Impact Explanation
Desktop presents the user a "Sign in to GitHub Enterprise" prompt whose target host/endpoint is fully attacker-chosen, purely because the attacker's server echoed a fake `WWW-Authenticate: realm="GitHub"` header. A user who has been conditioned to trust Desktop's native sign-in UI has no reliable way to tell that the endpoint being signed into is not a legitimate GitHub instance — this is an account-binding/phishing surface directly triggered by an untrusted git remote, matching the "unauthorized OAuth or account binding" impact class. I was not able to fully trace, in the remaining time, whether the subsequent OAuth code/token exchange (`requestOAuthToken` in `app/src/lib/api.ts`) sends any Desktop OAuth secret material to the attacker-supplied endpoint versus only ever talking to hardcoded GitHub OAuth URLs — that would determine whether this escalates from a UI-trust/phishing bug to actual credential exfiltration, and should be verified directly in `app/src/lib/stores/sign-in-store.ts` (`beginEnterpriseSignIn`/`resolveOAuthRequest`) and `app/src/lib/api.ts` (`requestOAuthToken`).

### Likelihood Explanation
High. No local access, no elevated privileges, and no unusual user behavior are required — a normal `git fetch`/`push`/`clone --recursive` against any repository whose remote (or submodule) the attacker controls is enough to reach `getCredential()` and trigger the classification. Setting a spoofed `WWW-Authenticate` header on an HTTPS git server is trivial for an attacker who controls that server.

### Recommendation
Do not classify a remote as a trusted "GitHub"/"enterprise" endpoint based solely on a self-reported `WWW-Authenticate` header. At minimum, require the independent `isGitHubHost()` verification (network probe for `x-github-request-id`) before trusting an unknown host enough to launch the GitHub Enterprise sign-in UI, and clearly surface the actual hostname being authenticated against in the sign-in popup so users can detect a mismatch.

### Proof of Concept
1. Attacker stands up an HTTPS git server at `https://attacker.example.com/evil.git` that responds to unauthenticated requests with `WWW-Authenticate: Basic realm="GitHub"`.
2. Attacker shares a repository whose `origin` remote (or a `.gitmodules` submodule) points at that URL, or gets the victim to add/fetch it.
3. Victim runs an ordinary Desktop operation that needs to authenticate against that remote (push/fetch/`updateSubmodulesAfterOperation`).
4. `getEndpointKind()` sees the forged `wwwauth[...]` header, returns `'enterprise'` [6](#0-5) .
5. `getCredential()` finds no matching account for that endpoint and calls `ui.promptForGitHubSignIn('https://attacker.example.com')` [3](#0-2) .
6. Desktop opens the native "Sign in to GitHub Enterprise" popup with the sign-in endpoint set to the attacker's origin [7](#0-6) , despite the victim never having entered that host.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
