## Title
`WombatStaking.depositLP` mints receipt tokens and stakes based on the input parameter instead of the actual LP tokens received - (`wombat/WombatStaking.sol`)

### Summary
`WombatStaking.depositLP()` transfers LP tokens via `safeTransferFrom` and then uses the caller-supplied `_lpAmount` parameter — rather than the contract's actual balance increase — to stake into the Wombat master and to mint receipt tokens. This is exactly the bug class flagged in the referenced report: any deviation between the amount requested and the amount actually received (fee-on-transfer, deflationary, or otherwise non-standard LP token behavior) causes the protocol to over-mint receipt tokens relative to what it actually custodies.

### Finding Description
In `wombat/WombatStaking.sol`, the sibling function `deposit()` correctly guards against this issue by snapshotting the LP balance before and after the external Wombat pool deposit and using the delta (`lpReceived`) for downstream accounting: [1](#0-0) 

However, `depositLP()` does not apply the same pattern. It transfers `_lpAmount` from `_for` and then immediately uses the raw `_lpAmount` value — not a measured balance delta — both to stake into the master Wombat contract and to mint the receipt token: [2](#0-1) 

This function is reachable by any ordinary wallet through the public pool helpers (`WombatPoolHelper.depositLP`, `WombatPoolHelperV2.depositLP`, `AnkrBNBPoolHelper.depositLP`), which forward the user-supplied `_lpAmount` straight through: [3](#0-2) 

If the actual amount received by `WombatStaking` after `safeTransferFrom` (line 281) is less than `_lpAmount` (e.g., a fee/tax on the LP token, or any nonstandard `transferFrom` behavior), `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` (line 284) still mints receipt tokens for the full nominal `_lpAmount`, and `_toMasterWomAndSendReward` (line 283) is told the wrong staked amount as well.

### Impact Explanation
Because receipt-token supply is minted 1:1 based on the unverified `_lpAmount` rather than the verified balance increase, the total receipt tokens outstanding can exceed the LP tokens actually custodied/staked by `WombatStaking`. Since `withdraw()`/`burnReceiptToken()` rely on this same LP accounting to return `depositToken`/LP back to users, this creates a shortfall where not all receipt-token holders can be made whole — a protocol insolvency / permanent freezing-of-funds condition for some depositors, consistent with the accepted-impact criteria.

### Likelihood Explanation
Any unprivileged wallet holding a supported LP token can call `depositLP` through any of the deployed pool helpers, so the code path is fully reachable without any privileged role. The likelihood of the bug manifesting is dependent on whether any currently or future whitelisted LP token deviates from standard, non-fee ERC20 transfer semantics; the vulnerable code pattern itself, however, exists unconditionally today and diverges from the safer pattern already implemented in the neighboring `deposit()` function in the same contract.

### Recommendation
Mirror the pattern already used in `deposit()`: snapshot `IERC20(poolInfo.lpAddress).balanceOf(address(this))` before the `safeTransferFrom` call in `depositLP`, compute the actual received amount as the post-transfer balance delta, and use that measured amount (not the caller-supplied `_lpAmount`) for `_toMasterWomAndSendReward` and for `IMintableERC20(poolInfo.receiptToken).mint(...)`.

### Proof of Concept
1. A pool is configured in `WombatStaking` whose `lpAddress` deviates from standard ERC20 transfer semantics (e.g., applies a transfer fee).
2. A user calls `PoolHelper.depositLP(_lpAmount)`, which calls `WombatStaking.depositLP(lpToken, _lpAmount, msg.sender)`.
3. `IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount)` (line 281) transfers less than `_lpAmount` into `WombatStaking` due to the fee.
4. `_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)` (line 283) stakes/accounts for `_lpAmount`, and `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` (line 284) mints `_lpAmount` receipt tokens, both exceeding what was actually received.
5. Over repeated deposits, receipt-token supply outstrips actual LP custody, so later withdrawers cannot be fully repaid, causing insolvency for the pool's receipt-token holders.

        address _lpAddress,
        uint256 _lpAmount,
        address _for
    ) nonReentrant whenNotPaused _onlyActivePoolHelper(_lpAddress) external {

        // Transfer lp to this contract and stake it to wombat

    }
