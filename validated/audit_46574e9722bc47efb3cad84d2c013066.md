## Title
Stale line-index diff selections are blindly re-applied to a freshly re-diffed working file at commit time, silently corrupting partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
The Dopex report describes a "quote vs. execution" mismatch: a value (bond discount) is computed for the user at "review time," but the actual on-chain execution recomputes it from mutable state, so what the user pays no longer matches what they approved. GitHub Desktop has a structurally identical pattern in its **partial-commit ("stage selected lines")** flow: the diff a user reviews and hand-selects lines from is snapshotted once in the Changes view, but at commit time Desktop re-reads the file from disk, re-generates a brand-new diff, and blindly re-applies the *old* line-index selection to that *new* diff structure — with no check that the selection still refers to the same lines the user actually approved.

### Finding Description
When a user partially stages a file, the UI computes a diff via `updateChangesWorkingDirectoryDiff` and stores absolute line indices (`unifiedDiffStart` + offsets) that the user toggles on/off in `DiffSelection`, e.g. in `app/src/lib/stores/app-store.ts`: [1](#0-0) 

Desktop itself acknowledges that the diff and the underlying file can change between renders — but only guards against this when it happens to *re-run this specific refresh path*, and even then only clears indices that literally no longer exist, without verifying the surviving indices still map to the lines the user thought they selected: [2](#0-1) 

Critically, this stale-diff hazard is **not** re-checked in the actual commit path. When the commit is executed, `stageFiles` → `applyPatchToIndex` is called for every partially-selected file: [3](#0-2) 

`applyPatchToIndex` re-reads the file from disk and computes a **brand new diff** (`getWorkingDirectoryDiff`) at commit time, independent of whatever diff the UI last rendered: [4](#0-3) 

It then hands this freshly-computed diff, together with the `file.selection` object (holding the old absolute-index selection from the UI), straight to `formatPatch`, which decides what to keep purely by `absoluteIndex` lookup against the new hunk structure: [5](#0-4) 

`formatPatch`/`applyPatchToIndex` never compares the new diff against the diff that produced the selection, and never verifies the file's content/hash is unchanged since the selection was made. There is no equivalent of the "slippage protection" the report recommends (i.e., no check that "what will be staged" still equals "what was reviewed").

### Impact Explanation
If the working-tree file is modified between the moment the user selects specific lines/hunks in the diff view and the moment `Commit` actually runs `applyPatchToIndex` — e.g. by a file watcher, an auto-formatter/linter task, an editor auto-save, a build step, or (per the valid-impact scope) content introduced via a cloned/fetched repository triggering local tooling — the hunk boundaries and `unifiedDiffStart` offsets shift. The stale absolute-index selection then silently lands on different lines in the new diff: lines the user never reviewed can be staged and committed, while lines the user did approve can be silently dropped. This is a **silent corruption of what the user commits/pushes**, one of the explicitly valid impact classes, without any error or warning surfaced to the user — the commit simply succeeds with unintended content.

### Likelihood Explanation
Partial/line-level staging is a core, everyday Desktop feature (extensively covered by `app/test/unit/git/commit-test.ts` "createCommit partials" and `app/test/unit/patch-formatter-test.ts`), so the code path is always reachable. The window between "user finishes selecting lines" and "commit executes" is attacker-influenceable time (auto-save, formatters, file watchers, background tools acting on repo content) rather than requiring local/physical access or malware, and Desktop's own comments confirm the developers are aware such races can occur ("...race condition when someone rapidly modifies the file on disk", `app/src/ui/diff/syntax-highlighting/index.ts`) — yet no integrity check exists on the actual commit-time path (`apply.ts`/`patch-formatter.ts`).

### Recommendation
Before calling `applyPatchToIndex`, verify that the working-directory file's content (or a checksum captured at selection time) is unchanged relative to the diff the user's `DiffSelection` was built against; if it has changed, abort the partial-stage/commit for that file and force Desktop to re-diff and require the user to re-confirm their selection, mirroring the "slippage protection" mitigation recommended in the report (fail closed on stale state rather than silently reusing an outdated selection against new content).

### Proof of Concept
1. Modify a tracked file with several distinct hunks; open it in Desktop's Changes view so the diff and `DiffSelection` are computed for the current on-disk content.
2. Select only lines within hunk B and leave hunk A unselected.
3. Before clicking "Commit", have an external process (e.g., a formatter/watcher acting on the cloned repo) rewrite the file such that line counts shift within/above hunk A (changing `unifiedDiffStart` offsets for later hunks) but the file remains "dirty" so Desktop still shows it as staleable.
4. Click "Commit". `applyPatchToIndex` re-diffs the now-changed file and `formatPatch` reapplies the old absolute-index selection (originally meant for hunk B) against the new hunk layout, producing a patch that includes/excludes different lines than the user selected.
5. Inspect the resulting commit: it contains content the user never visually reviewed/approved, or omits content the user intended to include — demonstrating silent corruption of the committed diff.
