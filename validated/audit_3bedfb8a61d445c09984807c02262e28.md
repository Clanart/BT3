### Title
`ReceivedOutput::read` accepts an offset/output pairing it never verifies, letting attacker-supplied bytes register unspendable funds as received - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary

`Scanner::scan_transaction` is the only code path that *correctly* binds a scalar `offset` to an output: it derives the offset from `self.scripts[&output.script_pubkey]`, a map populated by `Scanner::new`/`register_offset` only for scripts of the form `p2tr_script_buf(key + G * offset)` (`networks/bitcoin/src/wallet/mod.rs:199-214`, `:180-196`, `:80-86`). However, `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) deserializes `offset`, `output`, and `outpoint` as three independent fields and performs **no check that the declared offset actually generates the output's `script_pubkey`**, nor that the outpoint corresponds to any real payment to the wallet. This is the same bug class as GHSA-8579-rgg5-ph2m: an acceptance decision ("this output is spendable by key+offset") is taken on a message that is not bound to the thing it claims to authorize.

### Finding Description

`ReceivedOutput` is the wallet's representation of a spendable received output, and its correctness invariant is `output.script_pubkey == p2tr(key + G*offset)`. That invariant holds by construction when the object comes from `Scanner::scan_transaction`/`scan_block`, because `scripts` maps each script to exactly the offset registered for it (`mod.rs:155-165`, `:185-191`, `:205-210`). `ReceivedOutput::read` bypasses the scanner entirely: it reads a scalar via `Secp256k1::read_F`, then consensus-decodes a `TxOut` and an `OutPoint`, and returns the triple unconditionally (`mod.rs:122-133`). There is no `key` context, no recomputation of `p2tr_script_buf(key + G*offset)`, and no comparison against `output.script_pubkey` — the analogue of the missing `message_reference`/approver check in the Discord backend.

The wallet's spend path then trusts `offset()`/`output()`/`outpoint()` (`mod.rs:99-118`): the signer produces a BIP-340 signature under `key + G*offset` for the prevout/txout as deserialized. For any pairing where `offset` does not derive `output.script_pubkey`, the signature cannot be valid for the real script, so the input is unspendable on-chain even though the wallet reports it as a received, spendable output — precisely the "funds reported received that are not spendable" validation criterion.

### Impact Explanation

Any component that feeds serialized `ReceivedOutput`s into `ReceivedOutput::read` from a channel an unprivileged party can influence (relayed scan results, coordinator/processor messages, or stored data) can inject arbitrary `(offset, TxOut, OutPoint)` triples:

- An output paying someone else's script is reported as wallet funds, corrupting the wallet's balance and UTXO set with entries that can never be signed for.
- A real wallet output can be paired with the wrong offset (e.g., an offset registered for a different payment), producing a deterministic signing failure and misattributing which payment was received — breaking the offset-per-payment accounting the `Scanner`'s `register_offset` design relies on (`mod.rs:168-179`).
- Since `register_offset` returns `None` on script collisions and offsets are explicitly surjective (`mod.rs:174-175`), caller-side deduplication cannot detect the forgery either; only the cryptographic binding in `scan_transaction` can, and `read` skips it.

### Likelihood Explanation

Medium. Exploitation requires serialized `ReceivedOutput` bytes to cross a trust boundary — plausible where scan results are transmitted or persisted between components — and the impact is integrity/availability of funds accounting (unspendable reported funds, poisoned UTXO set, stuck spends) rather than direct theft, since a forged pairing yields no valid signature. The defect itself is unconditional: `read` performs zero semantic validation, so any untrusted byte stream reaching it succeeds.

### Recommendation

- Make `ReceivedOutput` deserialization binding-aware: require the wallet's `key` (or the `Scanner`) at read time and verify `p2tr_script_buf(key + G*offset) == Some(output.script_pubkey)`, rejecting on mismatch — the equivalent of binding the approval message to the request/approver.
- Prefer serializing the offset alongside the script it was derived from (rather than a free-standing `TxOut`), or store/transfer `Scanner`-produced values in a type that cannot be constructed except via `scan_transaction`/`scan_block` (`mod.rs:199-227`).
- Add a regression test: feed `ReceivedOutput::read` a triple where `offset` derives a different script than `output.script_pubkey` and assert rejection.

### Proof of Concept

```rust
use bitcoin::{OutPoint, TxOut, ScriptBuf, Amount, Txid, hashes::Hash};
use k256::{ProjectivePoint, Scalar};
use serai_bitcoin::wallet::{ReceivedOutput, Scanner};

// Wallet key the scanner was built for
let key = ProjectivePoint::GENERATOR * Scalar::from(7u64);
let mut scanner = Scanner::new(key).unwrap();
let real_offset = scanner.register_offset(Scalar::from(42u64)).unwrap();

// Attacker supplies bytes: a valid offset for the wallet,
// paired with an output paying a script the wallet does NOT control
let attacker_script = ScriptBuf::new_p2tr_tweaked(/* someone else's tweaked key */);
let forged = {
    let mut buf = vec![];
    buf.extend(real_offset.to_bytes());           // offset: honest-looking
    // TxOut paying attacker_script, and an outpoint for a tx paying the attacker
    // consensus-serialized here
    ReceivedOutput::read(&mut buf.as_slice()).unwrap()   // accepted unconditionally
};

// forged.output().script_pubkey != p2tr(key + G*real_offset), yet the wallet
// treats `forged` as a spendable received output: value() is credited and the
// send path signs under key + real_offset, which can never satisfy
// attacker_script -> funds reported received that are not spendable.
```

The vulnerability is visible directly in the code: `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-133`) returns `Ok` for any well-formed triple, while the only place the offset↔script binding is ever established is the `scripts` map lookup inside `Scanner::scan_transaction` (`mod.rs:205`) — a check the deserialization path never performs.
