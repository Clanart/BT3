### Title
A single invalid DKG share forces O(n·t) batch verification plus blame re-computation on every honest participant — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` queues a PoP signature statement and a full Pedersen share-verification statement for *every* participant into one `BatchVerifier`, then calls `verify_with_vartime_blame`. A participant who submits one malformed `EncryptedMessage` (read via `EncryptedMessage::read`) causes each honest node to run a full multiexp over all `n` statements (`multiexp` over a flattened `n × t`-ish pair list), and — because the batch fails — a `blame_vartime` binary search that re-runs `log2(n)` additional multiexps each over roughly half the batch. One ~100-byte message from the attacker therefore triggers roughly 2–3× the cost of an entire honest `n`-party share-verification workload on every honest participant. This mirrors CVE-2025-49643's class: a low-privilege, low-cost request inducing disproportionate server CPU.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `KeyMachine::calculate_share` (lines 463–499):

- For each `(l, share_bytes)` in the attacker-influenced `shares` map, it calls `self.encryption.decrypt(...)`, which (a) computes an ECDH scalar multiplication, (b) applies a ChaCha20 keystream, and (c) queues the sender's Schnorr PoP into the shared `BatchVerifier` (`encryption.rs:469-501`).
- It then queues `share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share)` — a `t`-length multiexp statement — into the same batch.
- `batch.verify_with_vartime_blame()` first runs `verify()` — a constant-time `multiexp` over the flattened `n × (t + PoP)` pair list (`batch.rs:93-95`) — and on failure runs `blame_vartime()`, a binary search performing `log2(n)` extra `multiexp_vartime` calls over halved slices (`batch.rs:108-123`), totaling approximately another full multiexp.

An attacker who sends a single `EncryptedMessage` with a corrupted ciphertext (so `C::F::from_repr` fails at `lib.rs:480`, or the share-verification statement doesn't sum to zero) forces every honest participant to execute the full O(n·t) batch verification plus the O(n·t) blame search, when the honest-path cost for that attacker is merely serializing ~t+3 point encodings. The decryption itself also performs `key * enc_key` ECDH and a keystream before the failure is detected. If the attacker further corrupts the PoP, `blame_vartime` still walks the whole tree. There is no cheap pre-check (e.g., per-message PoP verification before queuing, or early rejection) that bounds the cost per message to O(t).

### Impact Explanation
Unavailability of honest DKG participants' CPU. Every faulty 32–200 byte message causes work proportional to the entire session's verification cost (`n` participants × `t` coefficients of scalar multiplications, run ~2–3× due to verify + blame binary search). A coalition of `f` faulty senders — or one sender repeated across `attempt` retries of the DKG — multiplies this per attempt. Since the DKG runs on the critical path for key generation and resharing, sustained invalid shares stall consensus-adjacent key operations and burn validator CPU at a large attacker amplification ratio (~n·t group operations per attacker message). Consistent with Medium severity (AV:N/AC:L/PR:L, A:H, no C/I impact).

### Likelihood Explanation
Any DKG participant — an authenticated but low-privilege party, analogous to the "Guest" user in the Zabbix advisory — can reach this path with only public protocol messages: a syntactically valid `EncryptedMessage`/`SecretShare` ciphertext that fails `from_repr`, or a valid scalar whose share-verification multiexp is nonzero. No secret knowledge, collusion, or protocol deviation beyond sending garbage bytes is needed. The cost lands on all honest participants simultaneously, and repeats each attempt the attacker can trigger.

### Recommendation
Verify each share's PoP and share-verification statement incrementally and short-circuit on the first failure, or use `verify_vartime` then `blame_vartime` only on the cheap subset. Consider verifying the Schnorr PoP per-message *before* queuing it into the shared batch (a 3-term multiexp) so a PoP failure costs O(1) instead of contaminating the whole batch. Bound or rate-limit `calculate_share` invocations per `attempt`, and consider blame-token accounting so a participant that repeatedly triggers the blame path is excluded before the expensive search runs.

### Proof of Concept
1. Honest node runs `KeyMachine` for `n` participants, threshold `t` (`crypto/dkg/pedpop/src/lib.rs:463`).
2. Attacker `Participant l` calls `EncryptedMessage::<C, SecretShare<C::F>>::read` output with ciphertext bytes `0xFF..FF` (a non-canonical scalar), or encrypts `C::F::ONE` instead of the correct share — both paths exercised by `invalidate_share_serialization`/`invalidate_share_value` in `encryption.rs:218-256`.
3. `calculate_share` performs the ECDH mult + keystream + queues statements for all `n` shares, then `verify_with_vartime_blame` (`lib.rs:493`) executes `multiexp` over the full `n·(t+1)`-pair batch and, on failure, `log2(n)` additional `multiexp_vartime` passes in `blame_vartime` (`multiexp/src/batch.rs:108-123`) before returning `InvalidShare`.
4. Attacker cost: one serialized message. Defender cost: ~2–3× the full-session verification multiexp, per attempt, on every honest node.
