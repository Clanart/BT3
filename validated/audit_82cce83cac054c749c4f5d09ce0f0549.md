### Title
Hookify block rules matched by exact `tool_matcher` string miss equivalent `MultiEdit` mutations - (File: plugins/hookify/core/rule_engine.py)

### Summary
`RuleEngine._matches_tool` performs a case-sensitive, exact-string match against a pipe-delimited list of tool names, with no normalization or aliasing between semantically equivalent tools. A block rule authored with `tool_matcher: "Edit|Write"` to protect a file/pattern from dangerous content will never fire for the same mutation performed via the `MultiEdit` tool, even though `_extract_field` explicitly supports `MultiEdit` for `file_path`/`new_text`/`content` extraction, proving the engine treats `MultiEdit` as a first-class file-mutation vector elsewhere but not in the matcher.

### Finding Description
`_matches_tool` implements matching as: [1](#0-0) 
This is a literal `tool_name in patterns` check after splitting `matcher` on `|`. There is no wildcard expansion for related tools, no case folding, and no concept that `Edit`, `Write`, and `MultiEdit` are three distinct `tool_name` values that can all produce the same net effect (writing attacker-influenced content to a target file). `_check_condition`/`_extract_field` acknowledge this equivalence for content extraction — `MultiEdit` is handled explicitly for `file_path` and concatenated `new_text`/`content` fields: [2](#0-1) 
but `_matches_tool` has no equivalent normalization step, so a rule author following the documented pattern of writing `tool_matcher: "Edit|Write"` (as shown in `plugins/hookify/skills/writing-rules/SKILL.md` and `plugins/hookify/README.md`) unintentionally excludes `MultiEdit`. Additionally, `pretooluse.py` classifies `Edit`, `Write`, and `MultiEdit` under the same `'file'` event bucket for rule loading purposes: [3](#0-2) 
meaning file-protection rules are loaded and evaluated for all three tool names, but the individual rule's `tool_matcher` string ultimately decides applicability via the exact-match logic in `_matches_tool`. If the assistant (potentially steered by prompt injection embedded in repository content, issue/PR text, or other externally supplied content that Claude Code ordinarily ingests) chooses to perform the same disallowed edit using `MultiEdit` instead of `Edit`/`Write`, the block rule silently does not match, and `evaluate_rules` returns `{}` (no block, no warning), allowing the operation to proceed.

### Impact Explanation
Any hookify block rule intended to prevent dangerous file mutations (e.g., blocking edits to CI config, protected paths, or cross-repo/cross-session artifacts) that is scoped via `tool_matcher: "Edit|Write"` can be bypassed by routing the identical mutation through `MultiEdit`. This breaks the stated invariant that "a matching block rule must reliably deny the protected operation," resulting in unauthorized file mutation that the rule author explicitly intended to prevent — matching the "wrong-target mutation with real security impact" bounty category, since the same class of dangerous edit that would be denied via `Edit`/`Write` silently succeeds via `MultiEdit`.

### Likelihood Explanation
This requires only that a block rule uses `tool_matcher` values enumerating specific tool names without including all functionally-equivalent tools (`MultiEdit` alongside `Edit`/`Write`), which is exactly the pattern shown in the plugin's own documentation/skill examples. No special privileges are needed — any flow that causes the assistant to issue a `MultiEdit` call instead of `Edit`/`Write` for the same target (e.g., due to normal tool selection, or content that nudges tool choice) triggers the bypass. This is fully deterministic and repeatable given a fixed rule set and tool call.

### Recommendation
Normalize tool-name matching in `_matches_tool` so that file-mutation tools are matched as a class unless explicitly narrowed — e.g., treat `Edit`, `Write`, and `MultiEdit` as aliases when a rule's `tool_matcher` includes any of them, or require rule authors to use an explicit group like `tool_matcher: "FileWrite"` that internally expands to `Edit|Write|MultiEdit`. At minimum, update `config_loader`/`SKILL.md` guidance and add a lint/validation step that warns when a rule matches `Edit`/`Write` but omits `MultiEdit` (or vice versa), and add regression tests asserting equivalent block behavior across all three tool names for the same logical file-mutation content.

### Proof of Concept
Unit test in `plugins/hookify/core/rule_engine.py` test harness:
1. Define a block rule: `tool_matcher="Edit|Write"`, condition `field="new_text"`, `operator="regex_match"`, `pattern=r"DANGEROUS_PAYLOAD"`.
2. Case A: `input_data = {"tool_name": "Edit", "tool_input": {"file_path": "x", "new_string": "DANGEROUS_PAYLOAD"}}` → `evaluate_rules` returns a `deny`/block result. Assert blocked.
3. Case B: `input_data = {"tool_name": "MultiEdit", "tool_input": {"file_path": "x", "edits": [{"new_string": "DANGEROUS_PAYLOAD"}]}}` → `evaluate_rules` returns `{}` (no block). Assert this currently succeeds, demonstrating the same payload is denied under `Edit` but allowed under `MultiEdit`, violating the "reliably deny" invariant.

```python
    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
```
