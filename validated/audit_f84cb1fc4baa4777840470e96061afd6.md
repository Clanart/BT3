## Finding: `listSubmodules` regex requires an optional `git describe` suffix, silently dropping submodule status lines that lack one

### Summary
`listSubmodules` in <cite repo="Kirstentat/desktop--016" path="app/src/lib/git/submodule.ts" start="158,190,192" end="163,190,194" /> parses the output of `git submodule status --` with the regex `/^.([^ ]+) (.+) \((.+?)\)$/gm`. Two things are silently thrown away here:

1. **The leading status character is consumed but never captured.** Git prefixes each line with `' '` (no change), `-` (uninitialized), `+` (checked-out SHA doesn't match the index), or `U` (merge conflict). The `.` in the regex matches and discards this character, so `SubmoduleEntry` [1](#0-0)  never carries this information — every submodule looks identical to the caller regardless of whether it's clean, dirty, uninitialized, or conflicted.

2. **The `(describe)` group is mandatory in the regex but optional in git's actual output.** Git only appends `(<describe output>)` when `git describe` succeeds for the submodule's checked-out commit; per git's `git-submodule.sh` status implementation, when describe fails (e.g., the commit isn't reachable from any tag/branch — trivially achievable by an attacker who controls the submodule's fixed commit), the line is emitted as just `<prefix><sha> <path>` with no parentheses. Because the regex anchors on `\((.+?)\)$`, such lines never match `statusRe`, and the entire submodule entry is silently omitted from the returned array — it never reaches `submodules.push(...)` at [2](#0-1) .

### Finding Description
An attacker who controls a submodule commit (e.g., a cloned repository with a submodule pinned to a detached commit unreachable by any tag/branch) can produce a `git submodule status` line without a trailing `(describe)` clause. `listSubmodules` will fail to match that line at all, meaning that submodule is dropped from the returned list as if it didn't exist or had no changes, rather than being reported (even with an empty describe string).

### Impact Explanation
`listSubmodules`'s output is the source of truth GitHub Desktop uses to determine submodule state for status/commit purposes. Silently dropping an entry means a modified/dirty submodule (`+` prefix) with no resolvable describe output would not be represented at all, rather than at least appearing with its `sha`/`path` and an empty describe — this can hide a submodule modification from the state the app builds for committing or discarding changes.

### Likelihood Explanation
This is a naturally-occurring case, not merely a synthetic corner case: any submodule commit that git cannot describe (missing tags/annotated references reachable from it) is enough. It requires no crafted/malformed byte content, delimiters, or binary trickery — just a plain, valid submodule pointing to an undescribable commit, which is fully within the "attacker controls a cloned/fetched repository" threat model.

### Recommendation
Make the `(describe)` portion of the regex optional and capture the status prefix character explicitly, e.g. `/^(.)(\S+) (.+?)(?: \((.+)\))?$/gm`, and propagate the status flag (or at least default `describe` to `''` when absent) into `SubmoduleEntry` so no line is unconditionally dropped.

### Proof of Concept
1. Create a repository with a submodule pointing at a commit that has no reachable tag or branch (so `git describe` fails for it).
2. Run `git submodule status --` manually in that repository — observe the output line has no trailing `(...)`, e.g. `+abcdef1234... foo/submodule`.
3. Call `listSubmodules(repository)` — the returned array is empty (or missing that entry), even though the submodule exists and is out of sync with the index (`+` prefix).

I was not able to fully trace every downstream consumer of `listSubmodules` in `app/src/lib/stores/git-store.ts` within the available iterations to confirm the exact user-visible commit/discard/push consequence beyond "the submodule entry disappears from Desktop's internal state" — that final linkage would benefit from further tracing in a full session, e.g. via Devin, since index size limits may also be hiding parts of `git-store.ts`.   // entries are of the format:
  //  1eaabe34fc6f486367a176207420378f587d3b48 git (v2.16.0-rc0)
  //
  // first character:
  //   - " " if no change
  //   - "-" if the submodule is not initialized
  //   - "+" if the currently checked out submodule commit does not match the SHA-1 found in the index of the containing repository
  //   - "U" if the submodule has merge conflicts
  //
  // then the 40-character SHA represents the current commit
  //
  // then the path to the submodule
  //
  // then the output of `git describe` for the submodule in braces
  // we're not leveraging this in the app, so go and read the docs
  // about it if you want to learn more:
  //
  // https://git-scm.com/docs/git-describe
  const statusRe = /^.([^ ]+) (.+) \((.+?)\)$/gm

  for (const [, sha, path, describe] of stdout.matchAll(statusRe)) {
    submodules.push(new SubmoduleEntry(sha, path, describe))
  }
