### Title
`check_session_expiry_date` defaults to disabled, so expired online-token sessions are silently treated as valid - ([File: lib/shopify_app/configuration.rb])

### Summary
This is the closest analog to the reported "TimeLockUpgrade timeLockPeriod remains default post-deployment" bug class: a security-critical gate is protected by a boolean configuration flag that defaults to `nil`/false and is never set to a safe value by the standard deployment path (the `shopify_app:install` generator), so the protection is effectively a permanent no-op unless a developer manually opts in.

### Finding Description
`ShopifyApp::Configuration#initialize` never assigns a value to `check_session_expiry_date`, leaving it `nil` (falsy) by default [1](#0-0) [2](#0-1) . Both `LoginProtection#activate_shopify_session` and `TokenExchange#should_exchange_expired_token?` gate the expiry check behind this flag, using the exact "if disabled, skip enforcement" pattern seen in the `timeLockUpgrade` passthrough (`if timeLockPeriod == 0 { return; }`):

```ruby
if ShopifyApp.configuration.check_session_expiry_date && current_shopify_session.expired?
``` [3](#0-2) [4](#0-3) 

Crucially, the "deployment script" for this gem — `lib/generators/shopify_app/install/install_generator.rb`, which writes `config/initializers/shopify_app.rb` — never sets `check_session_expiry_date` in the generated initializer template, unlike `reauth_on_access_scope_changes`, which the template explicitly sets to `true` [5](#0-4) . This is a direct parallel to `2_core.js` deploying `Core` (which inherits `timeLockUpgrade`) without ever calling `setTimeLock`.

The gem's own docs confirm this is a known, security-relevant opt-in: "You should also enable the [check for session expiry]... so that a new access token can be fetched before being used" [6](#0-5) , and that when the flag is off, expired sessions are simply accepted without re-auth [7](#0-6) .

### Impact Explanation
When `check_session_expiry_date` is left at its default (unset/false), a session whose `expires` timestamp has passed (particularly online/user access tokens, which cannot be refreshed and must be re-authorized via OAuth per the docs [8](#0-7) ) is never rejected by `activate_shopify_session`. `current_shopify_session.expired?` is simply never evaluated, so a session that should have been terminated continues to authenticate requests indefinitely as long as the underlying stored session record exists. This weakens the intended lifetime bound on user sessions/tokens — effectively unbounded session validity contrary to the documented security control — which is analogous to the white paper's expected "time-locked" enforcement never taking effect.

### Likelihood Explanation
This requires no attacker action beyond normal use of the default, generator-produced configuration; the gap exists for every app that follows the standard `rails generate shopify_app:install` flow and does not separately discover and set `check_session_expiry_date = true` (a step called out only in prose documentation, not enforced anywhere in code). Exploitation likelihood depends on an attacker separately obtaining/reusing a session identifier/cookie whose token has expired; the flag's default state does not by itself create theft, but it removes the intended backstop that would otherwise invalidate such a session.

### Recommendation
- **Short term:** Set `config.check_session_expiry_date = true` in the generator's `shopify_app.rb.tt` template so newly generated apps enforce expiry checks by default, matching the treatment already given to `reauth_on_access_scope_changes`.
- **Long term:** Change the default in `ShopifyApp::Configuration#initialize` to `true` (secure-by-default), or require an explicit affirmative choice during install (similar to how `shop_session_repository` is required) rather than silently allowing a `nil`/false fallback that bypasses the check entirely.

### Proof of Concept
1. Run `rails generate shopify_app` (or `shopify_app:install`) to scaffold a new app; do not add `config.check_session_expiry_date = true` to `config/initializers/shopify_app.rb` (it is absent from the generated file by default) [5](#0-4) .
2. Configure user/online session storage as documented, then obtain a valid session whose `expires` timestamp is in the past (e.g., wait for token expiry, or directly manipulate the stored `expires_at` in a test session store).
3. Send an authenticated request (e.g., hitting a controller including `ShopifyApp::LoginProtection`/`EnsureHasSession`) using that expired session's identifier/cookie.
4. Observe that `ShopifyApp.configuration.check_session_expiry_date` evaluates to `nil`/false, so `current_shopify_session.expired?` is never checked in `activate_shopify_session` [3](#0-2) , and the request is processed as authenticated rather than being redirected to login.
