### Title
Unhandled `AssertionError` on duplicate coin spends in `MempoolManager.validate_spend_bundle` crashes spend-bundle processing - ([File: chia/full_node/mempool_manager.py])

### Summary
`chia/full_node/mempool_manager.py`'s `validate_spend_bundle()` assumes that the number of coin spends in a submitted `SpendBundle` always equals the number of unique coin IDs derived from the CLVM-computed `SpendBundleConditions`. This invariant is enforced only via a bare `assert`, not a proper `Err` return, and the code explicitly documents the assumption as something that "shouldn't happen" rather than validating it defensively — the same "unexpected internal state → assertion failure on crafted input" bug class as CVE-2017-9500 (`ResetImageProfileIterator` assertion failure from crafted files).

### Finding Description
In `validate_spend_bundle`, conditions are turned into a coin-ID-keyed dict and then compared in size against the caller-supplied `coin_spends` list: [1](#0-0) 

```python
spend_conditions = {bytes32(spend.coin_id): spend for spend in conds.spends}

# if this happens, the SpendBundle doesn't match the
# SpendBundleConditions.
assert len(new_spend.coin_spends) == len(spend_conditions)
...
spend_conds = spend_conditions.pop(coin_id)
```

`conds.spends` is a plain list (one entry per processed coin spend, produced by the Rust CLVM condition evaluator); building `spend_conditions` via a dict comprehension collapses any entries that share the same `coin_id` into a single dict key. If a submitted `SpendBundle.coin_spends` contains the exact same coin spent twice (i.e., the identical `Coin`/`CoinSpend` entry duplicated in the list — trivially constructible by any unprivileged submitter building their own spend bundle), `len(new_spend.coin_spends)` will be larger than `len(spend_conditions)`, and the `assert` fails with a raw `AssertionError` instead of returning a well-formed `Err` (e.g. `Err.INVALID_SPEND_BUNDLE` or `Err.DOUBLE_SPEND`, as used elsewhere in this same function for comparable "malformed bundle" conditions, see the sibling `Err.INVALID_SPEND_BUNDLE` returns just below).

This path is reached directly from `add_spend_bundle()`, which is invoked for every spend bundle submitted over the wallet/RPC/protocol surface via `pre_validate_spendbundle` + `add_spend_bundle`: [2](#0-1) 

Unlike the many other malformed-bundle checks in this function that gracefully return `(Err, None, [])` tuples (e.g., the `INVALID_SPEND_BUNDLE` checks for fast-forward duplication just below this block), this particular consistency check is a bare `assert`, meaning any code path that hits it raises instead of returning a handled validation error.

### Impact Explanation
An `AssertionError` raised out of `validate_spend_bundle` is not caught and converted to a `ValidationError`/`Err` the way `ValueError`s from `pre_validate_spendbundle` are handled; it propagates as an unhandled exception out of the spend-bundle admission path. This is a spend-triggered transaction-processing halt: a single unprivileged submitter can construct a `SpendBundle` (no valid signature required to reach this code path, since signature/CLVM execution happens earlier and does not itself reject the duplicate-spend case) that crashes the mempool admission logic for that request, disrupting full-node transaction processing — directly matching the required "spend-triggered transaction-processing halt" impact category. This mirrors the ImageMagick CVE's essence: a state-consistency assumption enforced only by an assertion, triggerable by crafted/untrusted input, causing denial of service rather than memory corruption or fund theft.

### Likelihood Explanation
Likelihood is high for triggering the crash path itself (constructing a `SpendBundle` with a duplicated identical `CoinSpend` entry requires no special privilege, signature, or coordination — any wallet user or spend-bundle submitter can build such a list locally). The main uncertainty (not verifiable from the indexed Python sources alone, since the CLVM condition evaluator is implemented in the `chia_rs` Rust extension which is not part of this repository's indexed contents) is whether the Rust-side condition parser already rejects or normalizes duplicate coin-spend entries before `conds.spends` is returned to Python. The Python code's own comment ("if this happens, the SpendBundle doesn't match the SpendBundleConditions") indicates the developers did not consider this case fully validated/rejected upstream, which is why the defensive `assert` exists here at all — but it is not converted to a normal `Err`, so if the condition is ever reachable, it fails hard rather than failing safe.

### Recommendation
Replace the bare `assert len(new_spend.coin_spends) == len(spend_conditions)` with an explicit check that returns `Err.INVALID_SPEND_BUNDLE` (or a new dedicated error) instead of raising, consistent with how the surrounding code already returns `Err` tuples for other malformed-bundle conditions in the same function. Additionally, explicitly detect and reject spend bundles containing duplicate `coin_id`s in `coin_spends` as early as possible (e.g., in `pre_validate_spendbundle` or immediately upon iterating `new_spend.coin_spends`) so the ambiguity between "duplicate coin" and "coin/condition mismatch" is handled deterministically and does not depend on assertion-based invariants over externally influenced input.

### Proof of Concept
1. Construct a `SpendBundle` whose `coin_spends` list contains the same `CoinSpend` object (same `Coin`, same `puzzle_reveal`, same `solution`) twice, e.g.:
   ```python
   cs = make_spend(TEST_COIN, IDENTITY_PUZZLE, SerializedProgram.to([[ConditionOpcode.CREATE_COIN, IDENTITY_PUZZLE_HASH, 1]]))
   sb = SpendBundle([cs, cs], G2Element())
   ```
2. Submit it via `mempool_manager.pre_validate_spendbundle(sb)` followed by `mempool_manager.add_spend_bundle(sb, sbc, sb.name(), height)` (the same path used by `respond_transaction`/RPC transaction submission in `chia/full_node/full_node.py`).
3. If the Rust condition evaluator does not itself dedupe/reject the duplicate coin spend (unverifiable from this index due to `chia_rs` being an external/compiled dependency), `spend_conditions` ends up with one fewer entry than `new_spend.coin_spends`, and the `assert len(new_spend.coin_spends) == len(spend_conditions)` statement at [3](#0-2)  raises an unhandled `AssertionError`, aborting spend-bundle processing for that request instead of returning a clean `MempoolInclusionStatus.FAILED` / `Err` result.

**Note on confidence:** I was unable to inspect the `chia_rs` Rust implementation of `get_name_puzzle_conditions`/`validate_clvm_and_signature` (compiled dependency, not indexed in this repository), so I cannot fully confirm whether duplicate coin-spend entries are already rejected before reaching this Python assert. This should be verified directly against the `chia_rs` source or by running the PoC above before treating this as fully exploitable.
