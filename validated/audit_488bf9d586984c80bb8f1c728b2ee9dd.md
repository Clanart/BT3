### Title
Gasless swap repayment amount is computed from `swapTx.GasPrice()` instead of the LendTx's actual effective gas price, allowing the proposer/lender's fee advance to go unrepaid - ([File: kaiax/gasless/impl/getter.go])

### Summary
The KIP-247 gasless flow computes the amount a user must repay to the block proposer using a static value derived from the *user's declared* legacy gas price (`swapTx.GasPrice()`), rather than the *actual* effective gas price the proposer's `LendTx` (a dynamic-fee tx) will pay at inclusion time. This is directly analogous to the Ion Protocol `Liquidation.liquidate` bug: a settlement amount (`rate`/repay amount) is computed from a value that is not re-derived at the moment of actual execution, so the value used for accounting can diverge from the value actually charged/paid on-chain.

### Finding Description
In `repayAmount`, the repay owed by the user is computed as: [1](#0-0) 

```go
func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))
	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}
```

The comment itself states the intent: `R1` is supposed to equal `LendTx.Fee()`. However, `LendTx` is built as a `TxTypeEthereumDynamicFee` transaction whose `GasFeeCap`/`GasTipCap` are copied from the swap transaction: [2](#0-1) 

The actual fee `LendTx` pays at inclusion is not `swapTx.GasPrice() * TxGas` in general — a dynamic-fee transaction's paid gas price is `min(GasFeeCap, baseFee + GasTipCap)`, which is determined by the KIP-71/Magma base fee at the time the transaction is executed, not by the value cached in `repayAmount` when the swap/repay amount is fixed inside the swap transaction's calldata (`amountRepay`, checked via `VerifyExecutable`/`SP4`): [3](#0-2) 

Because `repayAmount` is used only to validate that `SwapTx.amountRepay` matches this statically-derived value (rather than the fee actually deducted from the proposer for `LendTx`), any scenario where the effective gas price of the dynamic-fee `LendTx` differs from `swapTx.GasPrice()` (e.g., base fee changes between when the bundle/tx was formed and validated versus the block in which it is finally included, or edge cases where `GasTipCap`/`GasFeeCap` derived from a legacy `GasPrice()` interact non-trivially with a fluctuating `baseFee`) causes the on-chain repay amount enforced by `swapForGas` to be computed from a stale/inaccurate fee estimate instead of the value actually charged for `LendTx`. This mirrors the root cause of the reported bug: a value that changes based on system state (interest `rate` in Ion; base fee in Kaia) is used without being recomputed against the state at actual settlement time.

### Impact Explanation
If `LendTx`'s actual effective gas price ends up lower than `swapTx.GasPrice()` at inclusion (possible when base fee moves between bundle formation and inclusion, given KIP-71's per-block base fee dynamics), the proposer advances less KAIA for gas than the fixed `R1` amount encoded in `amountRepay`, yet the swap contract still collects the full precomputed `amountRepay` from the user's swapped tokens. This results in the proposer being over-repaid (systematically extracting value from users) or, in the reverse direction, under-collecting relative to what was actually lent, causing the lender's balance to be silently drained over many gasless transactions. Either direction constitutes unauthorized value movement between the gasless-swap counterparties (user vs. block-proposer/lender) enabled purely by a single submitted gasless bundle.

### Likelihood Explanation
Every gasless swap transaction goes through this exact code path (`VerifyExecutable` → `repayAmount` → `GetLendTxGenerator`), and base fee (KIP-71) recalculates every block based on network gas usage, so it is highly likely for effective gas price to diverge from `swapTx.GasPrice()` under normal, permissionless network conditions — no privileged access or malicious peer/validator behavior is required, only submitting a gasless approve/swap transaction pair as an ordinary unprivileged user.

### Recommendation
Compute `R1` (the LendTx repayment component) using the LendTx's actual effective gas price at the block in which it will be included — i.e., `min(GasFeeCap, header.BaseFee + GasTipCap)` — rather than the static `swapTx.GasPrice()`, mirroring how the LendTx transaction's real fee will be computed by `TransitionDb`/`buyGas`. Alternatively, settle repayment based on the LendTx's post-execution actual fee (analogous to accruing "rate" before use in the Ion fix) instead of a value fixed before the base fee affecting the LendTx is known.

### Proof of Concept
1. Construct a `GaslessApproveTx`/`GaslessSwapTx` pair where `swapTx` is a legacy transaction with `GasPrice = P`, and encode `amountRepay` per `repayAmount()` = `P * TxGas + ApproveTx.Fee() + SwapTx.Fee()`.
2. Have the KIP-71 base fee shift (e.g., due to prior block traffic) between when the bundle's `amountRepay` was fixed (client-side, matching `repayAmount()`) and the block where the bundle (`LendTx`, `ApproveTx`, `SwapTx`) is actually included, such that `min(LendTx.GasFeeCap, header.BaseFee + LendTx.GasTipCap) != P`.
3. Observe that `LendTx.Fee()` actually deducted from the proposer differs from the `R1` component baked into `amountRepay`, while `swapForGas` still collects the full (stale) `amountRepay` from the user — producing a mismatch between value lent and value repaid.

Note: I was unable to fully trace how `GasFeeCap()`/`GasTipCap()`/`GasPrice()` resolve for a legacy `swapTx` versus how `buyGas`/effective gas price is computed inside `state_transition.go` (the file's `buyGas`/effective-price logic was not retrieved before running out of iterations), so the exact numeric conditions under which the divergence is non-zero could not be fully confirmed and would need to be validated with a live Devin session against `blockchain/state_transition.go` and `blockchain/types/transaction.go`.
