### Title
Missing duplicate-input-token guard in the Tron `IntentGatewayV2.placeOrder()` silently merges escrow buckets that the canonical EVM contract explicitly rejects - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core defect is: a mapping keyed by an identifier that is supposed to be one-to-one with a single logical transaction can be silently **overwritten/merged** by a second write with the same key, with no uniqueness check, breaking the guarantee that later code (lookups, withdrawals) relies on. The same broken-invariant class is reproducible in Hyperbridge's Tron deployment of `IntentGatewayV2`: `_orders[commitment][token] += reducedInputs[i].amount` merges escrow amounts for repeated `token` entries in a single order with no duplicate check, whereas the canonical EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was patched to explicitly `revert` on this exact condition after it was identified as an over-release vector, with a regression test literally titled *"same-chain partial fills over-release repeated input escrow."* The Tron contract implements the identical `_orders`/`_filled`/`WithdrawalRequest` escrow-accounting model but does not carry the fix forward.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol`, `placeOrder()` explicitly guards against duplicate input tokens before crediting escrow: [1](#0-0) 

and against duplicate output tokens using transient storage: [2](#0-1) 

Both guards exist specifically because merging same-token legs in the `_orders[commitment][token]` escrow map (or in `_partialFills`) breaks the per-leg accounting invariant that fill/withdraw logic depends on. This is proven by the maintainers' own regression tests: [3](#0-2) [4](#0-3) 

The Tron deployment of the same module (`evm/tron/contracts/apps/IntentGatewayV2.sol`) uses the identical escrow data model (`_orders`, `_filled`, `WithdrawalRequest`, `RedeemEscrow`/`RefundEscrow` request kinds) but its `placeOrder()` has **no duplicate-token rejection at all** — it accumulates escrow with `+=` unconditionally: [5](#0-4) [6](#0-5) 

There is also no transient-storage check rejecting duplicate output-asset entries anywhere in the Tron `placeOrder()` implementation (contrast with lines 165-189 of the canonical contract). This means the exact bug class that upstream engineers identified and fixed for over-release/partial-fill accounting on the primary EVM deployment was never back-ported to the Tron deployment, leaving the escrow bookkeeping for that chain in the same unguarded, pre-fix state — mirroring the seed report's core flaw: a value meant to be tracked per unique key is instead merged/overwritten with no uniqueness validation, and downstream logic (withdrawal, fill, cancellation) that assumes distinct per-leg entries operates on merged state instead.

### Impact Explanation
Per Hyperbridge's own regression-test commentary, allowing duplicate input/output token legs to merge into a single escrow bucket is the exact condition that previously enabled **over-release of escrowed funds** during partial/same-chain fills, and premature finalization of orders with repeated output legs. Any Hyperbridge chain still running this unpatched Tron `IntentGatewayV2` contract is exposed to the same fund-loss class: unauthorized/incorrect transaction execution against escrowed user funds, i.e. a `Discard`-excluded-but-`Accept`-listed impact ("stealing or loss of funds," "logic attacks" against bridged-asset escrow).

### Likelihood Explanation
`placeOrder()` is a fully public, unprivileged entrypoint — any caller can submit an `Order` with intentionally duplicated `TokenInfo` entries in `inputs` or `output.assets`. No relayer, prover, admin, or leaked key is required; the attacker only needs to control the order they place, which is the normal, expected caller capability. The vulnerability is a straightforward code-divergence bug (missing guard present elsewhere in the same codebase), which is a high-confidence, directly reproducible condition rather than a speculative one.

### Recommendation
Port the exact protections from the canonical `evm/src/apps/IntentGatewayV2.sol::placeOrder` into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`:
1. Revert when `_orders[commitment][token] != 0` is about to be overwritten/merged for a duplicate input token (replace `+=` accumulation with a strict duplicate check + `=` assignment, as in the fixed EVM version).
2. Add the transient-storage (or equivalent) duplicate-output-token rejection loop before escrowing.
3. Add the same regression tests that exist in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` (`testRevert_PlaceOrder_DuplicateInputTokens`, `testRevert_PlaceOrder_DuplicateOutputTokens`, and their fee-enabled variants) against the Tron contract to prevent future re-introduction.

### Proof of Concept
1. On the Tron deployment, call `placeOrder` with `order.inputs = [ {token: USDC, amount: 600}, {token: USDC, amount: 400} ]`.
2. `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 444-463 iterate both legs and execute `_orders[commitment][USDC] += reducedInputs[i].amount` twice, silently merging into a single bucket of `1000` with no revert, unlike the canonical contract which reverts with `InvalidInput()` at this exact step (`evm/src/apps/IntentGatewayV2.sol:337`).
3. This confirms the Tron contract lacks the invariant the rest of the codebase (including its own regression-test suite) proves is required to prevent escrow-accounting corruption during fill/partial-fill/withdrawal flows on this shared code path.

Note: I was not able to locate a `fillOrder`/partial-fill implementation inside `evm/tron/contracts/apps/IntentGatewayV2.sol` itself within the available search budget (only `placeOrder`, `cancelOrder`, and `onAccept`/`withdraw` were confirmed), so I cannot fully trace the same-chain partial-fill over-release mechanics for the Tron contract end-to-end. This is a gap in my verification — if a background engineering session is available, it should specifically confirm whether Tron's fill/withdraw logic (wherever it lives) has the same reliance on per-leg escrow uniqueness as the canonical EVM version before finalizing severity.
