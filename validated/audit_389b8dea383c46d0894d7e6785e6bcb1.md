### Title
Dust-value deposits to the vault's P2TR address are accepted as spendable inputs, letting anyone force the wallet to sign inputs worth less than the fee they consume — (`networks/bitcoin/src/wallet/send.rs`)

### Summary
The external report describes a minimum-value constraint (min deposit) that is enforced at one entry point but silently bypassed by a second code path, allowing an attacker to leave residual state below the enforced minimum and spam the system with dust. The direct analog exists in Serai's Bitcoin wallet: the `DUST` minimum (546 sats) is enforced only on outputs the wallet *creates* (`payments` and `change`), while the wallet *accepts* arbitrary `ReceivedOutput`s — which the scanner attributes to the vault based on `script_pubkey` match alone, with no value filter — as spendable inputs with no minimum-value check. An unprivileged party can therefore fund the vault address with dust outputs that are reported as received yet are not economically spendable, and can force weight/fee inflation when the wallet does try to spend them.

### Finding Description
In `SignableTransaction::new`, the dust minimum is applied exclusively to outgoing payments:

```rust
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```
`networks/bitcoin/src/wallet/send.rs:165-169`

and to the change output, which is only appended when `value >= DUST` (`send.rs:228-234`).

The *input* side has no corresponding check. All provided `ReceivedOutput`s are summed and turned into `TxIn`s unconditionally (`send.rs:175-185`), and the only validation is the aggregate solvency check `input_sat < payment_sat + needed_fee` (`send.rs:215-221`). A `ReceivedOutput` of e.g. 1 sat — or anything below ~57× the fee rate, i.e. less than the ~58 vbytes an additional Taproot input contributes to weight (`calculate_weight_vbytes`, `send.rs:66-127`) — is included as a net-negative input. `multisig()` then blindly builds a signing machine for every such input, keyed by its per-input offset (`send.rs:273-285`), so once the scanner has attributed the dust output to the vault, it must either be ignored forever (funds reported received but never spendable) or consumed at a loss.

This mirrors the report exactly: the minimum bound is enforced on the outgoing side (`DustPayment` for payments, the `value >= DUST` gate for change) but has no enforcement on the incoming/accepted side, so the effective minimum is bypassed by depositing through the path the check doesn't cover — just as the report's users bypassed `minDeposit` via `requestWithdrawDeposit`.

### Impact Explanation
- **Funds reported received that are not spendable**: dust sent to the vault's `p2tr_script_buf(group_key)` script_pubkey is attributed as vault funds, yet spending an input whose value is below the fee cost of its ~58-byte weight contribution loses money; ignoring it permanently reports unspendable funds as holdings.
- **Fee/weight griefing**: if dust inputs are swept together with legitimate inputs, each dust input increases `vbytes`, hence `needed_fee` (`send.rs:204-213`), by more than the value it contributes — an attacker can drain vault value into miner fees at a cost of only a few hundred sats per output plus their own transaction fee.
- **Spam**: identical to the report's impact — unbounded dust outputs can be created toward a single fixed address, inflating the UTXO set the signer must track and potentially pushing transactions over `MAX_STANDARD_TX_WEIGHT` handling edge cases.

### Likelihood Explanation
Any unprivileged party who learns the vault's P2TR script_pubkey (publicly derivable/observable on-chain once the vault receives or spends funds, and required by depositors anyway) can create arbitrary numbers of dust outputs paying to it. No validator, peer, or collusion is needed — only a standard Bitcoin transaction. Cost is bounded by the attacker's own spend, but a few cents per output buys permanent unspendable-looking balance entries or forced fee burn. Medium likelihood: the attack is cheap, requires no special position, and the vulnerable path is the normal deposit flow.

### Recommendation
Enforce the same `DUST` minimum symmetrically on accepted inputs:

- In `SignableTransaction::new`, filter or reject `ReceivedOutput`s whose `output.value.to_sat()` is below `DUST` (or more precisely below `fee_per_vbyte * input_vbytes`, the input's marginal fee cost), and exclude such outpoints at the scanner/processor layer so they are never queued for signing.
- Alternatively, only consolidate sub-economic inputs in dedicated sweep transactions where the aggregate recovered value exceeds the incremental fee, and explicitly skip inputs that are net-negative at the target fee rate.

### Proof of Concept
1. Attacker derives/observes the vault's P2TR script_pubkey (`p2tr_script_buf(offset.group_key())`, `send.rs:277`) and broadcasts transactions sending e.g. 100 outputs of 300 sats each (< `DUST` = 546, `send.rs:32`) to it.
2. The scanner attributes each output to the vault by `script_pubkey` match; each becomes a `ReceivedOutput` with an offset — none of which carries a value check anywhere in `signable transaction` construction (`send.rs:175-185`).
3. When the vault builds a transaction including these inputs, `calculate_weight_vbytes` adds ~58 vbytes per input (`send.rs:71-99`), so at any fee rate ≥ ~5 sat/vB each 300-sat input is net-negative; the aggregate check `input_sat < payment_sat + needed_fee` (`send.rs:215`) still passes since `input_sat` grows by 300 while `needed_fee` grows by more.
4. Result: the signed transaction pays more in fees than the dust contributes (silent value leak), or the coordinator must permanently exclude the outputs — i.e. funds recorded as received are never spendable. Both outcomes bypass the `DUST` minimum the code enforces on every output it creates.
