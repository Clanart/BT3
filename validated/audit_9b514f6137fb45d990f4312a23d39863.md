### Title
ThresholdKeys accepts attacker-asserted verification shares without ever checking the secret share matches — deserialized group key is whatever the writer claims (File: crypto/dkg/src/lib.rs)

### Summary
The `ipns` bug class is "public-key verification not performed, so any key is valid". Serai's analog lives in `ThresholdKeys::new` / `ThresholdKeys::read` in `crypto/dkg`: the set of `verification_shares` (the public keys of every participant) and the resulting `group_key` are taken entirely on faith. The constructor checks only the count and index range of the shares (`crypto/dkg/src/lib.rs:355-365`), derives `group_key` by interpolating `verification_shares[1..=t]` (`:376-378`), and never verifies that `C::generator() * secret_share == verification_shares[params.i()]` nor that the resulting `group_key` is non-identity / not attacker-known. `ThresholdKeys::read` (`:574-632`) accepts all of this data from raw untrusted bytes — an explicitly reachable sink — so an attacker who supplies a serialized `ThresholdKeys` blob fully dictates the group key that downstream FROST code believes is the validator-set key.

### Finding Description
`ThresholdKeys::new` performs the following validation only:
- `verification_shares.len() == n` and all participant indexes `<= n` (`:355-365`)
- `Interpolation::Constant` requires `t == n` (`:367-374`)

It then computes `group_key = Σ verification_shares[i] * interpolation_factor(i, [1..=t])` (`:376-378`) and stores everything without:
- checking `verification_shares` values are non-identity or otherwise "real" keys,
- checking that the local `secret_share` is consistent with `verification_shares[i]` (`G * secret_share` is never computed in `new` — the PedPoP/dealer paths only happen to produce consistent inputs; `debug_assert_eq!(keys.group_key(), group_key)` exists only in the dealer, `crypto/dkg/dealer/src/lib.rs:64`),
- binding the shares to any prior transcript/context.

Because `ThresholdKeys::read` (`:620-631`) feeds attacker-controlled points into `new`, the `group_key` returned by `group_key()` (`:445-447`, used as the verification key in `crypto/frost/src/algorithm.rs:214-217` and in share verification via `ThresholdView::verification_share`, `:680-682`) is under complete attacker control: the attacker picks `verification_shares` so that the interpolated `group_key` equals `G * x` for a scalar `x` they know (e.g., set `verification_shares[1] = G * x / λ_1` and the rest to identity).

### Impact Explanation
Any consumer that reads `ThresholdKeys` from untrusted bytes and then relies on `keys.group_key()` (or a FROST `ThresholdView` built from it) to authenticate the validator set's signatures will accept signatures for a key whose discrete log the attacker chose. Concretely, a FROST `SchnorrSignature` for the attacker-chosen group key verifies successfully (`SchnorrSignature::verify`, `crypto/schnorr/src/lib.rs:108-110`), so the attacker can forge "threshold" signatures that appear to come from the supposed validator set — equivalent to the ipns "any key is valid" failure. Even absent key-choice, a mismatched `secret_share`/`verification_shares[i]` pair silently produces a `ThresholdKeys` whose own signatures can never verify, or which attributes a different public share to the holder than their secret warrants.

### Likelihood Explanation
Requires an attacker to supply (or corrupt) the serialized `ThresholdKeys` consumed by a node — i.e., the `ThresholdKeys::read` sink with untrusted bytes, which the scope explicitly enumerates as reachable. No malicious threshold of validators, broken consensus, or leaked key is needed; a single attacker-controlled blob suffices. Within the honest DKG flows (dealer/PedPoP/MuSig) the inputs are internally consistent, so the exposure is specifically through deserialization and any other caller that constructs `ThresholdKeys::new` from unauthenticated verification shares.

### Recommendation
In `ThresholdKeys::new`, verify `C::generator() * *secret_share == verification_shares[&params.i()]` and error otherwise; reject identity `group_key` and identity verification shares; and document that `ThresholdKeys` bytes must be integrity-protected/authenticated (e.g., signed or committed in a transcript) since the group key is derived from claimed shares. At minimum, `ThresholdKeys::read` should enforce the same consistency check so a forged share map cannot alias an attacker-chosen group key.

### Proof of Concept
1. Attacker picks scalar `x`, computes target `Y = G * x`.
2. Build `params = ThresholdParams::new(t, n, i)` with `t = n = 1` (simplest): interpolation is `Constant(vec![F::ONE])` or `Lagrange`; with `t = n = 1`, `group_key = verification_shares[1] * λ` where `λ = 1` (Lagrange over a singleton set yields `num * denom⁻¹ = 1`, `crypto/dkg/src/lib.rs:229-247`).
3. Serialize `ThresholdKeys` bytes with `verification_shares[1] = Y` and any `secret_share` (the share/`G*share` consistency is never checked, `:349-391`).
4. Feed the bytes to `ThresholdKeys::read` (`:574-632`) — it succeeds, and `keys.group_key() == Y`.
5. Attacker signs any message with `x` via `SchnorrSignature::sign` and it verifies against `keys.group_key()` — a forged signature under a key the attacker chose, accepted as the threshold group's key.

Relevant code: `crypto/dkg/src/lib.rs` `ThresholdKeys::new` (`349-391`), `ThresholdKeys::read` (`574-632`), `group_key` (`445-447`); `crypto/frost/src/algorithm.rs:214-217` (verification against the attacker-derived `group_key`); `crypto/schnorr/src/lib.rs:108-110`.
