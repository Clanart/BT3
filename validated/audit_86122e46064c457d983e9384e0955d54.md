### Title
Force-push safety warning trusts stale/attacker-controlled remote-tracking refs, enabling silent loss of remote commits during rebase/squash/reorder - ([File: app/src/ui/dispatcher/dispatcher.ts])

### Summary
The original report is about a value-affecting operation (`BackingManager._manageTokens`) running against stale state because a dependent update (`claimRewards`) hadn't been applied first, letting an attacker front-run and cause loss. The Desktop analog is `Dispatcher.warnAboutRemoteCommits`, which decides whether to show the "this will require a force push and may discard remote commits" warning by reading purely local, previously-fetched remote-tracking refs instead of freshly-verified remote state. A malicious/compromised git remote (or a MITM proxy sitting in front of it) can shape what Desktop's last `fetch` recorded locally so that this safety check computes "no remote-only commits exist," silently skipping the warning, and the following `--force-with-lease` push gives no additional protection because the same untrusted server also arbitrates the lease check.

### Finding Description
`warnAboutRemoteCommits` in [1](#0-0)  determines whether a rebase/squash/reorder operation will discard commits that exist on the remote by:
1. Reading the local remote-tracking ref via `getBranches(repository, refs/remotes/${targetBranch.upstream})`.
2. Computing `getCommitsBetweenCommits(repository, oldestCommitRef, targetBranch.upstream)` — again against the local, cached remote-tracking ref, not a live query of the actual remote.

This function is invoked before every history-rewriting, force-push-requiring operation (`startRebase` at [2](#0-1) , `reorderCommits` at [3](#0-2) , and `squash` at [4](#0-3) ) to decide whether to interrupt the flow with `MultiCommitOperationStepKind.WarnForcePush`.

The remote-tracking ref used here (`refs/remotes/<upstream>`) is only as current as Desktop's last `git fetch`, and the *content* of that ref is entirely dictated by whatever the remote (or a proxy terminating/relaying the git protocol) chooses to advertise. If that remote is attacker-controlled — a scenario explicitly in scope ("git remote/proxy response") — it can simply omit or hide certain refs/commits during the fetch that populates `refs/remotes/<upstream>`, causing `getCommitsBetweenCommits` to return an empty/short result. `warnAboutRemoteCommits` then returns `false` and the destructive operation proceeds without any user confirmation.

Once the local rewrite (rebase/squash/reorder) completes, Desktop performs the actual push with `--force-with-lease` and no explicit expected value in [5](#0-4) . Without an explicit `<expect>` value, `--force-with-lease` validates the push against the server's *current* advertised ref state at push time — supplied by the same remote that already lied during the fetch used to build the local warning check. Because the attacker controls both the fetch-time advertisement and the push-time lease negotiation, the "safety net" that force-with-lease is supposed to provide against overwriting unexpected remote history is not an independent guard here: the same untrusted party is both hiding the commits from the warning logic and approving the very push that discards them.

### Impact Explanation
This lets a malicious/compromised remote (or MITM proxy) cause GitHub Desktop to silently rewrite and force-push history without ever surfacing the "Are you sure? This may discard remote commits" dialog to the user, discarding commits that genuinely exist on the remote and belong to other collaborators. This matches the "silent corruption of what the user commits or pushes" impact class — the user believes they safely rebased/squashed/reordered, but real remote history (potentially other people's work) is destroyed without their informed consent, and the built-in `--force-with-lease` guard offers no real protection because it is being arbitrated by the same adversarial remote.

### Likelihood Explanation
Requires the user to be operating against an attacker-controlled or MITM'd remote/proxy — no local access, no admin rights, no prior malware, and no unnatural user steps beyond normal repository work (fetch, then rebase/squash/reorder + force push), which is a common Desktop workflow. The "Show confirmation dialog before force pushing" setting is enabled by default per [6](#0-5) , and this issue defeats exactly that safeguard by manipulating the data it relies on.

### Recommendation
- Do not base `warnAboutRemoteCommits` solely on cached remote-tracking refs; perform (or require having just performed) a verified fetch immediately before evaluating remote-ahead state, and treat fetch/transport errors as "assume commits could be lost" rather than silently proceeding.
- When calling `push` with `forceWithLease`, supply an explicit `--force-with-lease=<refname>:<expected-oid>` captured at the moment the warning check ran, so the lease is validated against a value that was itself trust-checked, rather than deferring entirely to the remote's live advertisement.
- Consider treating a lease mismatch or an untrusted/changed remote fetch result as cause to re-show the force-push warning rather than silently failing/succeeding.

### Proof of Concept
1. Attacker stands up a git server (or transparent proxy) for a repository the victim has cloned, or compromises the existing remote/proxy.
2. Victim's collaborator pushes commit `C` to the tracked branch on the real remote.
3. Victim runs Desktop; Desktop's next `fetch` goes through the attacker-controlled remote/proxy, which advertises the tracked branch ref as if `C` doesn't exist (omits it from the ref advertisement/pack).
4. Victim starts a rebase/squash/reorder in Desktop that would normally trigger `warnAboutRemoteCommits` → `getCommitsBetweenCommits(oldestCommitRef, upstream)` finding `C`; because the local `refs/remotes/<upstream>` never recorded `C`, the function returns `false` and the `WarnForcePush` dialog is skipped ( [2](#0-1) ).
5. Desktop performs the rewrite and issues `git push --force-with-lease` ( [7](#0-6) ); since the same attacker-controlled remote arbitrates the lease check, it accepts the push and `C` is discarded from the remote without the victim ever having been asked to confirm.

  private async warnAboutRemoteCommits(
    repository: Repository,
    targetBranch: Branch,
    oldestCommitRef: string | null
  ): Promise<boolean> {
    if (targetBranch.upstream === null) {
      return false
    }

    // if the branch is tracking a remote branch
    const upstreamBranchesMatching = await getBranches(
      repository,
      `refs/remotes/${targetBranch.upstream}`
    )

    if (upstreamBranchesMatching.length === 0) {
      return false
    }

    // At this point, the target branch has an upstream. Therefore, if the
    // rebase goes up to the root commit of the branch, remote commits that will
    // require a force push after the rebase do exist.
    if (oldestCommitRef === null) {
      return true
    }

    // and the remote branch has commits that don't exist on the base branch
    const remoteCommits = await getCommitsBetweenCommits(
      repository,
      oldestCommitRef,
      targetBranch.upstream
    )

    return remoteCommits !== null && remoteCommits.length > 0
  }
