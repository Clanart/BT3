## Title
Clone-time protections against malicious repository config/hooks are explicitly disabled (`GIT_CLONE_PROTECTION_ACTIVE: 'false'`) - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` performs a `git clone --recursive` against an attacker-controlled URL and explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment passed to the git process: [1](#0-0) 

This is the same class of issue as the CBI report: a security-relevant guard that normally protects a trusted operation is turned off during an operation whose input (the clone URL / the resulting repository content) is fully attacker-controlled, letting a hostile payload reach code that assumed the guard was in place.

### Finding Description
Recent Git releases hardened `git clone` (and its recursive submodule handling) against repositories that ship a malicious `.git/config`, `.gitmodules`, or hook-adjacent files that could otherwise be used to smuggle configuration or hooks into the clone destination (the class of fixes around CVE-2024-32002/32004/32020/32021, shipped as Git's "clone protection" / `protectNTFS`/`protectHFS`-adjacent hardening). Git exposes `GIT_CLONE_PROTECTION_ACTIVE` as the internal signal for whether that protection path is engaged during the clone.

Desktop's `clone()` builds the environment for every clone with:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
```
and then runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` [2](#0-1) . Since `url` is attacker-controlled (a link the user clicks, a value from the "Clone repository" dialog, or a `x-github-client://openRepo/...` deep link handled by `parseAppURL`/`openOrCloneRepository` in the dispatcher [3](#0-2) ), the attacker fully controls both the remote content and, through `--recursive`, the submodule graph fetched during the same operation.

By forcing the protection env var off, Desktop is deliberately bypassing whatever safety checks upstream Git ties to `GIT_CLONE_PROTECTION_ACTIVE`, on a code path whose only real defenses elsewhere in the codebase are the destination-path checks (`isClonePathSensitive`, `sanitizeCloneName`) — none of which inspect the *content* of the cloned repository (e.g., its `.gitmodules`, embedded hook files, or nested `.git` directories). Those existing guards only stop path-traversal in the destination folder name; they do nothing about what upstream Git's own clone-protection mechanism was designed to catch inside the fetched tree.

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` disables a check that would otherwise reject or neutralize a malicious repository/submodule layout (e.g., one engineered to plant executable content where Git would later run it, or to overwrite files outside the intended working tree via crafted paths in `.gitmodules`/`.git/config` during the recursive submodule init), then simply cloning an attacker's public repo or following a malicious deep link/website "Open in Desktop" link could result in file writes outside the intended repository directory or subsequent code execution once submodules are initialized — matching the "attacker controls a cloned/fetched repository ... result is code execution, file write ... outside the repo" criteria.

### Likelihood Explanation
High likelihood of reachability: cloning is a core, unprivileged, one-click user action (Clone dialog, CLI `--cli-clone`, or the `x-github-client://openRepo/...` protocol handler), and it always runs with `--recursive`, so any malicious submodule reference in the target repo is fetched and initialized in the same flow, all while the protection flag is off for the entire operation.

### Recommendation
- Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` unless there is a well-documented, tested reason it must be disabled (e.g., a specific Git-for-Windows/dugite compatibility bug) — and if so, gate it narrowly and re-enable it as soon as that compatibility issue is resolved.
- If the flag must stay disabled, compensate by not using `--recursive` blindly: enumerate and vet `.gitmodules` entries (reject `ext::`, disallow arbitrary URLs/protocols via `protocol.ext.allow=never` and `protocol.file.allow=never` unless explicitly requested) before running `submodule update --init --recursive`, consistent with the `allowFileProtocol` gating already present in `updateSubmodulesAfterOperation` (`app/src/lib/git/submodule.ts`).
- Add regression tests asserting the clone/submodule-init commands run with Git's built-in clone/config protections active by default.

### Proof of Concept
1. Publish a public repository whose `.gitmodules`/nested `.git` layout is crafted to exploit the class of issues Git's clone-protection mechanism (tied to `GIT_CLONE_PROTECTION_ACTIVE`) is designed to block (e.g., a submodule path or config entry that would otherwise be rejected during a protected clone).
2. Get a victim to open the repository in GitHub Desktop via any of: the Clone dialog with the malicious URL, `desktop --cli-clone <url>`, or a hosted link using the `x-github-client://openRepo/<url>` deep-link scheme (parsed in `app/src/lib/parse-app-url.ts` and handled by `openOrCloneRepository` in `dispatcher.ts`).
3. Desktop calls `clone()` in `app/src/lib/git/clone.ts`, which executes `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'` for the whole operation, so the payload that upstream Git's protection would normally have blocked is processed unguarded, both for the top-level clone and every recursively-initialized submodule.

Note: I could not confirm from the indexed source alone the exact upstream Git semantics/version this flag maps to, or find any comment/commit message in this repo explaining why it is disabled — only that it is unconditionally set to `'false'` for every clone. A Devin session with full repository history (git log/blame) and access to the vendored Git/dugite binary version would be needed to confirm precisely which protection is bypassed and whether it is exploitable end-to-end in the currently vendored Git version.
