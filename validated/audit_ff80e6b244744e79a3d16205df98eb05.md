## Title
Attacker-crafted `git status` output can permanently break repository status refresh via unhandled parser exception - (File: `app/src/lib/status-parser.ts`)

### Summary
The reported Voter.sol bug is fundamentally about untrusted, attacker-influenced data reaching a strict validation (`require`) inside a loop that is executed by a recurring "refresh"/"poke" mechanism, causing that refresh mechanism to permanently fail for that specific state (an "unpokeable" NFT). The closest analog in the GitHub Desktop codebase is the porcelain status parser: repository content (fully attacker-controlled once a user clones/opens a malicious repository) is fed into `parsePorcelainStatus` and its field parsers, which `throw` a hard `Error` instead of skipping or gracefully degrading when a status line doesn't match the expected regex. Because this parser sits directly in the path of the recurring status-refresh flow (`getStatus` → `_refreshRepository` / `refreshIndicatorForRepository` / background fetch cycles), a single unparsable entry can make status refresh throw every single time it runs for that repository.

### Finding Description
`parsePorcelainStatus` in `app/src/lib/status-parser.ts` tokenizes the buffer produced by `git status --porcelain=2 -z` and dispatches to per-entry-type parsers: [1](#0-0) 

Each of these per-entry-type parsers (`parseChangedEntry`, `parsedRenamedOrCopiedEntry`, `parseUnmergedEntry`) validates the field against a strict regex and `throw`s a plain `Error` if the regex fails to match, rather than skipping the malformed/unexpected entry: [2](#0-1) [3](#0-2) [4](#0-3) 

This parser is invoked unconditionally by `getStatus()` in `app/src/lib/git/status.ts` on every status computation: [5](#0-4) 

`getStatus()` is, in turn, the backbone of the app's repeating "poke"-equivalent mechanisms: `_refreshRepository` (called after every fetch/pull/push and repository selection) and `refreshIndicatorForRepository` (called by the periodic `RepositoryIndicatorUpdater` background loop): [6](#0-5) [7](#0-6) 

Just as the Voter.sol bug relies on an attacker crafting input (a "dust vote") that later causes a rounding edge case that the `require` check cannot tolerate, an attacker who controls the content of a cloned/fetched repository (filenames, path characters, submodule state combinations, unusual byte sequences) can craft a working tree whose `git status --porcelain=2` output does not match Desktop's hand-written regexes (e.g. `changedEntryRe`, `renamedOrCopiedEntryRe`, `unmergedEntryRe`). Because the regexes assume ASCII structure and fixed field counts/ordering, any deviation git itself is capable of emitting (or that a corrupted/edge-case index state produces) causes `parsePorcelainStatus` to throw synchronously inside `getStatus`.

### Impact Explanation
If this exception is not caught somewhere up the call chain (verification of every call site could not be completed within the available tool budget — see Uncertainty below), it would propagate out of `getStatus`, and by extension out of `_refreshRepository` / `refreshIndicatorForRepository`. Since these are the very mechanisms responsible for keeping the Changes tab, ahead/behind counters, and sidebar status indicators up to date — the "poke" equivalent for Desktop — a persistently malformed status line makes the repository's status view permanently stale/unrefreshable as long as the offending file/state remains in the working tree, mirroring the "unpokeable" impact: outdated state is served indefinitely instead of being corrected. In the worst case (uncaught exception escaping to `onUncaughtException` in the renderer), this could also destabilize the whole application session rather than only one repository's view.

### Likelihood Explanation
Likelihood is High for the same reason as the original report: no privileged access is required, only that a user clones/opens or fetches into a repository containing attacker-chosen content, and the status computation runs automatically and repeatedly (background fetcher, indicator updater, manual refreshes) without any user action needed to trigger the parsing path.

### Recommendation
Make `parsePorcelainStatus`'s entry parsers resilient to unexpected/malformed porcelain lines: log and skip the offending entry (similar to how `IgnoredEntryType` lines are already skipped) instead of throwing, or catch parsing errors around individual entries in `parsePorcelainStatus`'s loop so that one malformed entry doesn't abort the entire status computation and doesn't recur on every refresh cycle.

### Proof of Concept
Conceptual PoC (not fully verified end-to-end due to inability to trace every call site of `getStatus`/`loadStatus` in this session):
1. Clone or open a repository whose working tree/index can be manipulated to produce a `git status --porcelain=2 -z` entry line that does not match `changedEntryRe`, `renamedOrCopiedEntryRe`, or `unmergedEntryRe` (e.g., unusual submodule status combination or byte sequence in a path that breaks field parsing assumptions).
2. Open the repository in Desktop; `getStatus()` is invoked, `parsePorcelainStatus` throws inside `parseChangedEntry`/`parsedRenamedOrCopiedEntry`/`parseUnmergedEntry`.
3. Observe that every subsequent automatic refresh cycle (fetch, indicator updater, manual "Refresh") hits the same code path and throws again, leaving repository status indicators/Changes tab permanently stale until the user manually repairs the working tree outside of Desktop.

### Uncertainty
I was not able to fully confirm, within the tool budget available, whether `getStatus`/`loadStatus` calls are wrapped in try/catch at every call site (e.g., inside `git-store.ts`'s `loadStatus`), which would determine whether the thrown error is silently swallowed (lower severity — stale-but-safe) versus propagating and crashing the refresh flow (higher severity). This should be verified directly in `app/src/lib/stores/git-store.ts` and `app/src/lib/stores/app-store.ts` before treating this as a confirmed high-severity finding.

function parseChangedEntry(field: string): IStatusEntry {
  const match = changedEntryRe.exec(field)

  if (!match) {
    log.debug(`parseChangedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for changed entry`)
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    path: match[8],
  }
}

function parsedRenamedOrCopiedEntry(
  field: string,
  oldPath: string | undefined
): IStatusEntry {
  const match = renamedOrCopiedEntryRe.exec(field)

  if (!match) {
    log.debug(`parsedRenamedOrCopiedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for renamed or copied entry`)
  }

  if (!oldPath) {
    throw new Error(
      'Failed to parse renamed or copied entry, could not parse old path'
    )
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    oldPath,
    renameOrCopyScore: parseInt(match[8].substring(1), 10),
    path: match[9],
  }
}
