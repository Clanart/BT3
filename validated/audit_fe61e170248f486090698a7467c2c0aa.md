### Title
Unauthenticated `InternalSendTx` allows arbitrary transaction broadcast through the aggregator's fee-paying pipeline - (File: core/src/servers.rs)

### Summary
The `Interceptors::Noop` variant, selected whenever `config.client_verification` is `false`, unconditionally returns `Ok(req)` for every RPC without ever calling `is_internal`, so the "Internal"-prefixed method convention that is supposed to restrict `internal_send_tx` to self/aggregator callers is never enforced. Any unauthenticated caller reaching the aggregator's public gRPC port can therefore invoke `InternalSendTx` directly and have an attacker-chosen raw transaction forwarded to the tx-sender/broadcast pipeline.

### Finding Description
The binding that should hold is: `caller_of_Internal*_method == aggregator_itself_or_self_cert_holder`, enforced by `is_internal()` + leaf-certificate comparison inside `only_aggregator_and_self` [1](#0-0) [2](#0-1) .

This check is only reached through `Interceptors::OnlyAggregatorAndSelf`; the alternate `Interceptors::Noop` variant bypasses it entirely and returns `Ok(req)` unconditionally [3](#0-2) . Which variant is installed on the aggregator's gRPC server is decided purely by the `config.client_verification` flag in `create_grpc_server`: when it is `false`, `Noop` is used instead of `OnlyAggregatorAndSelf` [4](#0-3) . Notably, `create_aggregator_grpc_server` only emits a warning when `client_verification` is *enabled* ("Client verification is enabled on aggregator gRPC server") [5](#0-4) , rather than when it is disabled, which is the security-relevant (insecure) branch — indicating the codebase treats verification-off as the normal/expected posture for the aggregator's port rather than flagging it as risky.

Under this configuration, an unprivileged network client can call `InternalSendTx` on the aggregator's public port with an attacker-chosen `raw_tx`, and the request reaches `AggregatorServer::internal_send_tx` with no certificate-based (or any other) authorization check, because `is_internal` is never invoked by `Noop`.

### Impact Explanation
This matches the "High - an unauthenticated state-changing or broadcasting call" category: an unauthenticated party gains the ability to submit arbitrary transactions into the aggregator's broadcast/fee-bumping infrastructure. This can be used to interfere with the aggregator's own pending protocol transactions (e.g., conflicting spends of inputs the aggregator's fee wallet controls), and is repeatable for as long as the misconfiguration/default persists, across any number of calls, independent of deposits or operators.

### Likelihood Explanation
The only precondition is `config.client_verification == false` on the aggregator's server, which is a deployment-time configuration switch rather than a per-request secret; the code's own warning logic treats "enabled" as the noteworthy state, suggesting disabled is the common/default operational mode. If that is indeed how the aggregator is run, the attack requires no special privileges, keys, or certificates — only network reachability to the aggregator's public gRPC port and the ability to craft a `SendTxRequest`.

### Recommendation
Enforce the "Internal" method authorization independent of `client_verification`/TLS mode — e.g., reject any RPC whose `grpc-method` starts with `Internal` when the interceptor is `Noop`, or split internal-only methods onto a separate, non-public listener (e.g., a loopback-only Unix socket) rather than gating them solely behind an optional client-certificate check on the public TCP port.

fn is_internal(req: &Request<()>) -> bool {
    // This normally doesn't exist but we add it in the AddMethodMiddleware
    let Some(path) = req.metadata().get("grpc-method") else {
        // No grpc method? this should not happen
        tracing::error!("Missing grpc-method header in request");
        return false;
    };
    path.as_bytes().starts_with(b"Internal")
}

                our_cert,
                aggregator_cert,
