### Title
Consensus reward misattribution: `on_executed` credits the entire batch's `StateMachineUpdated` reward to only the first message's signer - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::on_executed` derives a single `relayer_account` from `messages.get(0)` only, then pays that one relayer the reward for **every** `StateMachineUpdated` event in the whole batch, regardless of which consensus message actually produced each event. Because `pallet-ismp` can process a batch containing multiple independent `Message::Consensus` entries (each carrying its own valid signature) in one call, any two-message batch whose first entry is attacker-signed pays 100% of both chains' rewards to the attacker.

### Finding Description
`FeeHandler::on_executed(messages, events)` is called once per processed batch with the full list of messages and the full list of emitted events [1](#0-0) .

`pallet-consensus-incentives`'s implementation only inspects `messages.get(0)` to recover a signer, and if it decodes to a valid signature it becomes "the" `relayer_account` for the whole call: [2](#0-1) 

It then iterates over **all** `StateMachineUpdated` events in the batch (already deduplicated per state machine to its highest height, but not filtered by which message/signer produced it) and pays out a reward for each one to that single `relayer_account`: [3](#0-2) 

The reward for each state machine is `blocks_advanced * block_cost`, transferred from the treasury and additionally minted as reputation: [4](#0-3) 

Consensus proofs are, by protocol design, public artifacts that "can be generated by anyone" once finality is reached [5](#0-4) . This means an attacker does not need any relayer's private key to observe a valid, still-unprocessed consensus message for chain B (e.g. from the public mempool/gossip or by watching Hyperbridge's offchain storage) and repackage it into their own batch, prepended with a message they signed themselves for a cheap/no-op chain A. Since the batch's relayer identity is taken from `messages[0]` alone, all reward for advancing chain B's height is paid to the attacker rather than to whoever actually incurred the cost of producing/relaying it — a wrong-beneficiary payout of protocol treasury funds. The comment at lines 124-133 shows the author was aware of and fixed the "same state machine repeated in one batch" duplicate-payment case, but the fix does not address "different state machines from different signers combined in one batch."

### Impact Explanation
This lets an unprivileged, uncooperative caller redirect real relayer/treasury reward flows to themselves without doing the corresponding cross-chain proof-verification work for the state machines whose reward they collect — a direct "wrong beneficiary and amount" fund-movement bug against the treasury (`T::TreasuryAccount`) as required by the impact gate ("stealing or loss of funds", "logic attacks" causing "unauthorized ... execution" of a payout that should have gone elsewhere). Each successful batch drains `blocks * block_cost` per state machine improperly attributed, and since `StateMachinesCostPerBlock` and reward baselines only move forward (`LastRewardedHeight`), the true relayer of the stolen-credit chain is permanently unable to re-claim that span's reward.

### Likelihood Explanation
The attack requires only: (1) the ability to submit an unsigned/permissionless `handle` extrinsic containing multiple `Message::Consensus` entries in one call (this is the documented purpose of the ISMP consensus message batch), and (2) access to any already-valid, publicly available consensus proof/message for a second chain, which the documentation explicitly states is producible/observable by "anyone." No relayer, prover, admin, or governance compromise is required — only ordinary access to Hyperbridge's public consensus-message stream, which any user of the protocol has. This is a logic/ordering bug in first-message attribution, not a front-running race, since the attacker's own transaction atomically bundles both messages.

### Recommendation
Attribute each `StateMachineUpdated` reward to the signer of the specific `Message::Consensus` entry that produced it (e.g., by recovering a signer per-message and mapping each state-machine id back to the message/signer that generated its `StateMachineUpdated` event), rather than assuming a single relayer for the whole batch from `messages[0]`.

### Proof of Concept
1. Relayer R legitimately observes finality proof `P_B` for chain B (any observer can construct/relay this, per protocol design).
2. Attacker A crafts a batch `[Message::Consensus(signed_by_A, proof_A_for_chain_A), Message::Consensus(copied_message, proof_P_B_for_chain_B)]` and submits it via the unsigned `handle` extrinsic before R submits `P_B` alone.
3. `pallet-ismp` processes both consensus messages successfully, producing `StateMachineUpdated` events for both chain A and chain B.
4. `pallet-consensus-incentives::on_executed` is called once with `messages = [msg_A, msg_B]`, `events = [Updated(A), Updated(B)]`.
5. `maybe_relayer_account` is derived solely from `messages[0]` → A's account [2](#0-1) .
6. The loop over `highest_per_state_machine` pays A the reward for **both** chain A's and chain B's height advance [6](#0-5) , even though A did not independently produce or discover proof `P_B`.
7. `LastRewardedHeight` for chain B is now watermarked, so R (or any other future submitter) can never claim that span's reward again.
