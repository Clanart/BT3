### Title
Chia wallet accepts plaintext HTTP pool endpoints when joining a pool via RPC, bypassing the CLI-only HTTPS enforcement - ([File: chia/wallet/wallet_rpc_api.py])

### Summary
The Cryptomator advisory (CVE-2026-32309) describes a vault-metadata-driven unlock flow that trusts attacker/config-controlled endpoint URLs and never enforces HTTPS at the point where the sensitive network exchange actually happens, only elsewhere (or not at all), letting a network attacker intercept/tamper with the traffic. Chia has an analogous pattern in the plotnft/pool-join flow: HTTPS-on-mainnet enforcement for `pool_url` is implemented only in the CLI helper `chia/cmds/plotnft_funcs.py` (`create()` at lines 99-102, `join_pool()` at lines 366-369) and, separately and non-blockingly, in the farmer's periodic `update_pool_state()` loop (`chia/farmer/farmer.py:685-688`). The actual wallet RPC endpoint that creates the on-chain pool-join transaction — `pw_join_pool` (`PWJoinPool`) served by `chia/wallet/wallet_rpc_api.py` and implemented in `chia/pools/pool_wallet.py` / `chia/wallet/plotnft_wallet/plotnft_wallet.py` — performs **no scheme validation** on `pool_url` before it is persisted into on-chain `PoolState`/`PlotNFT` data and used by the farmer to contact the pool for authentication and partial submission.

### Finding Description
`join_pool()` in `chia/cmds/plotnft_funcs.py:345-414` is the only place that checks:
```python
enforce_https = wallet_info.config["selected_network"] == "mainnet"
if enforce_https and not pool_url.startswith("https://"):
    raise CliRpcConnectionError(f"Pool URLs must be HTTPS on mainnet {pool_url}.")
``` [1](#0-0) 

This check lives entirely in the CLI convenience wrapper, not in the RPC server. Any caller that talks to the wallet RPC directly (`pw_join_pool` / `PWJoinPool`, or the pool-wallet creation RPC with `initial_target_state.pool_url`) can submit an `http://` (or any other unvalidated scheme) `pool_url` on mainnet without hitting this guard. The RPC/wallet code that actually persists and later drives on-chain behavior (`PoolWallet`/`PlotNFT2Wallet.join_pool`, `chia/wallet/plotnft_wallet/plotnft_wallet.py:228-291`) accepts `pool_url` as an opaque string and embeds it into the spend/announcement (`url_remark = Remark(rest=Program.to(pool_url))`) with no scheme check at all. [2](#0-1) 

The only other enforcement point is the farmer's background loop, which is separate from the RPC/transaction path and merely skips/logs and does not stop the pool_url from having been committed on-chain:
```python
enforce_https = config["full_node"]["selected_network"] == "mainnet"
if enforce_https and not pool_config.pool_url.startswith("https://"):
    self.log.error(f"Pool URLs must be HTTPS on mainnet {pool_config.pool_url}")
    continue
``` [3](#0-2) 

Because RPC endpoints are meant to be programmatically callable (not only via the bundled CLI), a local RPC caller (any process with access to the wallet RPC port/keys — the same trust boundary explicitly listed as reachable in scope) can drive a mainnet plot-NFT into `FARMING_TO_POOL` state with an `http://` pool endpoint. Once that pool_url is committed on-chain via the singleton spend, the farmer's authentication (`AuthenticationPayload`), `PostFarmerPayload`/`PutFarmerPayload` (containing payout instructions), and partial submissions are transmitted to that endpoint. If the farmer instance ever reaches this endpoint before the (separate, best-effort) HTTPS gate is hit — or if the gate is bypassed by pointing `pool_url` at a URL that momentarily starts with `https://` then 301/307/308-redirects to `http://` (the redirect-following logic in `update_pool_state()` explicitly follows 301/308 redirects to a "new_pool_url" without re-validating scheme, see `chia/farmer/farmer.py:704-710`) — bearer/auth tokens, owner-key–derived authentication signatures, and payout instructions are exposed to network interception/tampering, mirroring the Cryptomator issue.

### Impact Explanation
An attacker who can either (a) call the wallet RPC directly (a local RPC caller, in-scope) or (b) control a pool endpoint that a user's plot-NFT is configured against, can force pool-authentication traffic (owner-public-key–bound signatures, payout instructions, farmer difficulty/points state) onto plaintext HTTP or through an HTTPS→HTTP redirect chain that the farmer's redirect-following logic doesn't re-validate. This allows on-path tampering with payout instructions or authentication data en route to the pool, and interception of farmer/pool protocol data, without any explicit warning surfaced by the RPC layer that is supposed to be the authoritative validation point.

### Likelihood Explanation
Medium-High: the missing validation is in the primary RPC/transaction path (`pw_join_pool` and pool-wallet creation), while the only protections are CLI-only and farmer-loop-only. Any tool, script, or third-party wallet/mobile client that talks to the RPC directly (bypassing `chia plotnft` CLI) will have no HTTPS enforcement whatsoever for pool joins on mainnet. Additionally, the redirect-handling code in `update_pool_state()` follows `new_pool_url` from pool responses without any scheme check, allowing an already-onboarded HTTPS pool to silently downgrade a farmer to HTTP via a redirect.

### Recommendation
Move the HTTPS-on-mainnet validation for `pool_url` into the RPC layer itself (`wallet_rpc_api.py`'s `pw_join_pool` handler and pool-wallet creation path) and into `PoolWallet`/`PlotNFT2Wallet.join_pool()`, so it is enforced regardless of caller. Also re-validate the scheme of any `new_pool_url` learned via redirect in `Farmer.update_pool_state()` before persisting/using it (`chia/farmer/farmer.py:704-710`), rejecting any downgrade from `https://` to `http://`.

### Proof of Concept
1. Start a mainnet-configured wallet/farmer.
2. Call the wallet RPC `pw_join_pool` (or `create_new_wallet` with `initial_target_state.pool_url`) directly via HTTP/RPC client (bypassing `chia plotnft join` CLI) with `pool_url="http://attacker.example.com"`.
3. Observe that no HTTPS check exists in `chia/wallet/wallet_rpc_api.py`/`chia/pools/pool_wallet.py`/`chia/wallet/plotnft_wallet/plotnft_wallet.py`; the transaction is created and pushed, committing the plaintext endpoint into on-chain `PoolState`.
4. Once the farmer picks up this pool_url (or a pool controlled by attacker sends a 301/308 redirect from an initially-HTTPS URL to an HTTP one), farmer authentication/payout traffic is sent in plaintext, observable/tamperable by a network attacker — the analog of the Cryptomator Hub HTTP/endpoint-validation bug. [4](#0-3)
