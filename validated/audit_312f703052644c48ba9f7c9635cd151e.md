### Title
`filter_preexisting_from_diff` uses stripped-text set matching without positional correspondence, letting attackers hide newly added malicious lines from the automated review agent - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`filter_preexisting_from_diff` reclassifies any added diff line as "pre-existing context" whenever its `.strip()`ed text matches *any* removed line's `.strip()`ed text anywhere in the same file's diff, with no positional/contextual correspondence check. An attacker who fully controls a file's content via Write/MultiEdit can therefore introduce a genuinely new, semantically different line (e.g., moved into a dangerous new scope/conditional) that is textually identical after whitespace-stripping to an unrelated pre-existing line being removed, causing the automated reviewer (invoked per `plugins/plugin-dev/skills/agent-development/SKILL.md`-style review workflows and the Stop-hook LLM review in `security_reminder_hook.py`) to never see it as a change.

### Finding Description
The filter builds two collections from the raw diff text: [1](#0-0) 

`removed_lines` is a `set`, and matching is purely by stripped string equality — there is no requirement that the added line replace *that specific* removed line, or that it appear at a similar position, or that the surrounding block/indentation context match. The rewrite step then converts any `+` line whose stripped content is in `removed_lines` into a context (space-prefixed) line: [2](#0-1) 

Because matching is set-based and global to the file, an attacker who rewrites a file (Write tool, or MultiEdit producing a full-content diff) can:
1. Delete an old, benign line whose stripped text is `X` (e.g., a comment, a harmless statement, or even a line from unrelated dead code).
2. Insert a **new** line whose stripped text is also `X`, but placed in a different, dangerous scope (different indentation, different conditional branch, inside a newly introduced function, etc.), where its actual semantic effect is entirely different from the original.

The diff will show `-X` and `+X` in unrelated positions; the filter matches them by stripped text alone and rewrites the `+X` line to a context line. The downstream LLM review agent (whether the Stop-hook `agentic_review` pipeline or a review skill/agent consuming this diff) is explicitly instructed to focus only on changed (`+`) lines and to ignore pre-existing/context content — e.g. `pr-review-toolkit/agents/code-reviewer.md` scores "Pre-existing issues" as false positives, and `code-review/commands/code-review.md` step 4 says agents should focus "only on the diff itself" and not flag pre-existing content. Once the malicious line is downgraded to context, it is invisible to this review gate.

The code's own comment acknowledges the imprecision and claims a backstop exists ("the diff-review prompt's previous-findings recheck"), but that mechanism (`PREVIOUS_FINDINGS_TTL_SEC`, `_record_fire`-based dedup in `security_reminder_hook.py`/`diffstate.py`) only re-checks issues that were *previously flagged* across turns — it does nothing for a vulnerability that was never flagged in the first place because the filter hid it as context on its very first pass. There is no other validation, allowlist, or positional check that would catch this.

### Impact Explanation
An attacker with control over file content in a Write/MultiEdit-driven rewrite can smuggle a malicious code change past the automated code-review agent entirely, because the diff shown to the reviewing LLM no longer marks the malicious line as added. This defeats the review gate described in the code-review skill/plugin workflow, allowing a backdoor, logic change, or malicious payload to be merged/accepted without ever being surfaced to the reviewer — a direct trust-boundary/review-integrity bypass (the diff shown to the automation does not faithfully represent the actual change).

### Likelihood Explanation
Feasible and repeatable: the attacker only needs to control the edited file's before/after content (already a stated precondition — full-file Write/MultiEdit rewrite) and craft one colliding stripped-line pair. No privilege escalation, no exploitation of a separate bug, and no reliance on timing is required; the collision is deterministic given the `.strip()`-only normalization and global set semantics.

### Recommendation
Replace the global stripped-text set matching with positional/contextual matching, e.g.:
- Use a proper line-level diff/LCS (or unified-diff hunk correlation) to pair each removed line with the added line it was actually replaced by, rather than any line sharing stripped text anywhere in the file.
- At minimum, require exact match (not `.strip()`-normalized) or require matching indentation/leading-whitespace plus a bounded proximity window between the removed and added line's positions before reclassifying as context.
- Cap how many "pre-existing" reclassifications can occur per matched string (currently a single removal can mask unlimited additions of the same stripped text) and log/flag when reclassification collapses a meaningfully sized diff, so it can be independently audited.

### Proof of Concept
Unit test for `filter_preexisting_from_diff` (in `plugins/security-guidance/hooks/gitutil.py`):

1. Construct an old file version containing a benign line at top-level scope, e.g. `x = 1` immediately followed by a comment line `run_check()` (harmless, unreachable/no-op stub).
2. Construct a new file version that removes that comment line but inserts a new line with identical stripped text `run_check()` inside a newly added `if is_admin_bypass:` block that actually calls a dangerous function aliased as `run_check` in the new scope (i.e., same text, different semantic effect due to new surrounding context).
3. Generate the raw unified diff between old and new (as `git diff` would produce for a full-file Write rewrite).
4. Call `filter_preexisting_from_diff([(path, diff)], cwd, baseline_sha)`.
5. Assert that the resulting diff for the malicious line is a context line (leading space), **not** a `+` line — demonstrating the bypass.
6. Additional invariant/fuzz variant: generate many (old, new) pairs where a single removed line's stripped text collides with N distinct newly-added lines placed in different dangerous contexts, and assert that the filter reclassifies all N as context (masking N distinct changes from a single deletion) — matching the documented "one removal can mask N additions" trade-off, confirmed as exploitable rather than merely theoretical.

    filtered = []
    for file_path, diff_content in diff_files:
        lines = diff_content.split('\n')

        # Collect removed and added lines (stripping the +/- prefix)
        removed_lines = set()
        added_lines = []
        for line in lines:
            if line.startswith('-') and not line.startswith('---'):
                removed_lines.add(line[1:].strip())
            elif line.startswith('+') and not line.startswith('+++'):
                added_lines.append(line[1:].strip())

        if not removed_lines:
            # New file, no pre-existing content to filter
            filtered.append((file_path, diff_content))
            continue

        # Check what fraction of added lines were pre-existing
        preexisting_count = sum(1 for l in added_lines if l in removed_lines)
        if preexisting_count == 0:
            filtered.append((file_path, diff_content))
            continue
