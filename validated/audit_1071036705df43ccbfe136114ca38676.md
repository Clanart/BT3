### Title
Inconsistent HTML/JS-unsafe character escaping across ProtoJSON emitters (PHP/Ruby upb backend and Python) - (File: `upb/json/encode.c`, `php/ext/google/protobuf/php-upb.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, `python/google/protobuf/json_format.py`)

### Summary
The upstream CVE is about a UI template failing to HTML-escape attacker-controlled text before embedding it in a page, enabling script injection when later rendered by a browser. The closest transferable Protobuf analog is in ProtoJSON serialization: several official language bindings deliberately over-escape `<`, `>`, and certain Unicode separator/format characters in string field values specifically to defend downstream consumers that later embed ProtoJSON output into HTML/`<script>` contexts (a documented, intentional defense-in-depth measure, see comments in `src/google/protobuf/json/internal/writer.cc:233-238` and `java/util/.../JsonFormat.java:1583-1591`). The PHP and Ruby native bindings (via the shared upb `jsonenc_put_escaped_char` routine) and the pure-Python `json_format.py` path do not perform this extra escaping, so identical string content serializes differently (and less defensively) across officially supported bindings.

### Finding Description
`jsonenc_put_escaped_char` in `upb/json/encode.c:268-301` (duplicated in the generated `php/ext/google/protobuf/php-upb.c:6807-6840` and `ruby/ext/google/protobuf_c/ruby-upb.c:5560-5593`) only special-cases `\n \r \t \" \f \b \\` and bytes `< 0x20`; every other byte, including `<` (0x3C) and `>` (0x3E), is emitted verbatim via `jsonenc_putbytes`. Python's `_Printer.ToJsonString` (`python/google/protobuf/json_format.py:224-228`) builds a plain dict/string and hands it to the standard library `json.dumps`, which likewise does not escape `<`/`>`. By contrast, the C++ `JsonWriter::WriteEscapedUtf8`/`MustEscape` (`src/google/protobuf/json/internal/writer.cc:198-269`), Java `JsonFormat.TextGenerator.getReplacementOrNull`/`replacementChars` (`java/util/.../JsonFormat.java:1568-1613`), and C# `JsonFormatter.WriteString`/`CommonRepresentations` (`csharp/src/Google.Protobuf/JsonFormatter.cs:61-83`, `686-748`) all explicitly convert `<` and `>` (and `&`, `=`, `'` in Java's case) to `\uXXXX` escapes, with comments stating this is done "to prevent security bugs in JavaScript" and a dedicated regression test `testHtmlEscape` (`java/util/.../JsonFormatTest.java:2016-2035`) verifying `</script>` is escaped to `\u003c/script\u003e`.

### Impact Explanation
This is a cross-implementation consistency/hardening gap, not a parser vulnerability: an attacker who controls a string field value (via a supported public parse API filling that field, or an application constructing a message from user input) and whose value is later embedded verbatim by the consuming application into an HTML page or inline `<script>` block, can break out of a `<script>` context when the message is serialized to ProtoJSON via the PHP, Ruby, or Python bindings, whereas the same message serialized via Java, C#, or C++ would be defensively escaped. The impact assumes an external application does unsafe embedding of ProtoJSON text into HTML — the same "consuming application must not blindly trust output" caveat noted for Java's `getReplacementOrNull` comment which explicitly says this is not "html escaping" but a defense measure for a specific (mis)use pattern. It is a genuine analog of the missing-escaping invariant in CVE-2019-15700, but the exploitability is entirely dependent on unsafe application-side use of ProtoJSON output as raw HTML, which is not a guaranteed or documented Protobuf public contract.

### Likelihood Explanation
Moderate to low. Reaching this requires (1) an application that renders ProtoJSON directly into HTML/script context without its own escaping — an anti-pattern — and (2) use of the PHP, Ruby, or Python bindings specifically, since Java/C#/C++ already defend against it. The bug is a genuine behavioral inconsistency reachable through the standard public `MessageToJson`/`to_json`/JSON encode paths with a fully trusted schema and bounded string input, with no memory-safety or crash implications.

### Recommendation
Align the upb JSON encoder (`upb/json/encode.c`, and its generated copies bundled into the PHP and Ruby extensions) and Python's `json_format.py` with the C++/Java/C# behavior: escape `<`, `>`, and the additional characters/Unicode ranges identified in `MustEscape` (`src/google/protobuf/json/internal/writer.cc:239-267`) when writing JSON string values, so all official ProtoJSON implementations provide the same defense-in-depth guarantee regardless of language binding.

### Proof of Concept
Using the Python binding (or PHP/Ruby via upb):
```python
from google.protobuf import json_format
msg = SomeProto3Message(string_value="</script><script>alert(1)</script>")
print(json_format.MessageToJson(msg))
# -> {"stringValue": "</script><script>alert(1)</script>"}   # '<' and '>' NOT escaped
```
Compare to the equivalent Java call `JsonFormat.printer().print(msg)` on a message with `optionalString="</script>"`, which per `JsonFormatTest.testHtmlEscape` (`java/util/.../JsonFormatTest.java:2016-2021`) produces `"optionalString": "\u003c/script\u003e"` — demonstrating the cross-binding inconsistency.     private static final String[] replacementChars;

    static {
      replacementChars = new String[128];
      for (int i = 0; i <= 0x1f; i++) {
        replacementChars[i] = String.format("\\u%04x", i);
      }
      replacementChars['"'] = "\\\"";
      replacementChars['\\'] = "\\\\";
      replacementChars['\t'] = "\\t";
      replacementChars['\b'] = "\\b";
      replacementChars['\n'] = "\\n";
      replacementChars['\r'] = "\\r";
      replacementChars['\f'] = "\\f";

      // These characters are fully legal in JSON, but are escaped to prevent XSS risks. Notably
      // this topic is not like 'html escaping' where these would be replaced with something like
      // `&lt;`. The escaped or not ways of writing it are verbatim 2 exactly equivalent
      // ways to represent the same exact value in JSON: consumers should never do any manual
      // unescape to round trip the intended value. This replacement is only be semantically
      // observable if someone tries to handle it raw textually and not as JSON.
      for (int i : "<>&='".toCharArray()) {
        replacementChars[i] = String.format("\\u%04x", i);
      }
    }

    /**
     * If a character needs to be escaped, returns the replacement string. Otherwise, returns null.
     */
    private static String getReplacementOrNull(char c) {
      if (c < 128) {
        return replacementChars[c];
      }

      // \u2028 and \u2029 are paragraph whitespace characters that had mismatch between the
      // JSON spec and the browser JavaScript object literal spec. It is extremely unlikely
      // this topic matters now, but for parity with GSON we escape them.
      if (c == '\u2028') {
        return "\\u2028";
      }
      if (c == '\u2029') {
        return "\\u2029";
      }

      return null;
    }
