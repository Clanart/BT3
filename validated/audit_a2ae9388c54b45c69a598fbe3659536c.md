### Title
Unvalidated single-source remote HEAD drives automatic destructive branch pruning - ([File: app/src/lib/stores/helpers/branch-pruner.ts])

### Summary
GitHub Desktop determines a repository's "default branch" from a single, unvalidated data source: the git remote's self-advertised `HEAD` symref, fetched via `git remote set-head -a`. That single value is later used, without any cross-validation or confirmation, by an unattended background task (`BranchPruner`) to silently `git branch -D` local branches it believes are "merged." A malicious or compromised remote (or a MITM'd git transport) can manipulate this single source to trigger permanent, silent deletion of local branches/commits — the git-world analog of "off-chain worker trusts one Ethereum source and an attacker manipulates it to corrupt state."

### Finding Description
Whenever Desktop fetches, it runs `git remote set-head -a <remote>`, which blindly trusts whatever the remote server reports as its default branch over the git protocol (the `HEAD` capability advertisement during ref negotiation): [1](#0-0) 

That locally cached symref is then read back and used, unmodified, as the *sole source of truth* for the default branch name: [2](#0-1) 

`findDefaultBranch` has no fallback validation against a previously-known default branch, no anomaly detection if the remote's HEAD suddenly changes, and no confirmation step — it just accepts the remote-reported value: [3](#0-2) 

This value flows into `GitStore.refreshDefaultBranch` and into `RepositoryStateCache`'s `branchesState.defaultBranch`: [4](#0-3) 

`BranchPruner` — a fully automatic background process that runs on a 4-hour timer without any user interaction or confirmation — reads `defaultBranch` straight from that cache and uses it as the base ref for `git branch --merged`: [5](#0-4) [6](#0-5) 

Any local branch whose tip is deemed an ancestor of that (attacker-influenced) ref, and that isn't a reserved name, wasn't checked out in the last two weeks, isn't in a worktree, and has no matching upstream, is permanently deleted with `git branch -D`: [7](#0-6) [8](#0-7) 

The existing "guards" (`ReservedRefs`, recently-checked-out set, worktree set, upstream-must-be-gone check) only filter *which* branches are candidates for pruning — none of them validate the *default branch reference itself*. There is no cross-check against a second source (e.g., the previously cached default branch, the GitHub API's `default_branch` field which Desktop already fetches elsewhere via `fetchRepository`/`fetchRepositoryCloneInfo`), so a single corrupted remote-protocol response is sufficient to poison the base ref used for a destructive, unattended operation.

### Impact Explanation
If an attacker controls the git remote (a malicious/compromised upstream, a repo the user was tricked into adding as a remote, or a MITM'd git-over-HTTP/SSH proxy), they can manipulate the advertised `HEAD` and remote branch graph so that Desktop computes a "default branch" whose ancestry happens to include commits/branch tips the user has not actually merged (e.g., because the attacker's server can construct a commit graph with the user's known feature-branch SHA as an ancestor of the advertised default ref). Because `BranchPruner` runs unattended every 4 hours and directly executes `git branch -D` on the resulting "merged" set, this results in silent, irreversible loss of local branches and any commits reachable only from them once git garbage collection runs — a direct instance of "silent corruption of what the user commits" caused entirely by an attacker-controlled remote/proxy response, satisfying the stated valid-impact class.

### Likelihood Explanation
The attack requires the victim to fetch from a remote the attacker controls or can MITM (a plausible, unprivileged scenario — cloning a malicious/compromised open-source fork, or an upstream that becomes compromised later), and requires the attacker to be able to predict or influence the SHAs of the victim's local branches (feasible if those branches were previously pushed to, or forked from, the same server). This is a moderate-likelihood but high-impact path since it needs no local access, no admin rights, and no social engineering beyond a normal `fetch`/`clone`+background app usage — pruning happens automatically without any explicit user action once the poisoned HEAD is cached.

### Recommendation
**Short term:** Do not treat the remote-advertised `HEAD` as an unconditionally authoritative single source for a destructive operation. Before pruning, cross-validate `defaultBranch` against a second source (e.g., the GitHub API's `default_branch` field already retrieved via `fetchRepository`), and refuse to prune (or prompt the user) if the two sources disagree or if the remote's default branch changes unexpectedly between fetches.

**Long term:** Avoid deriving inputs to irreversible local operations (branch deletion) from a single externally-controlled protocol response. Consider requiring the default branch used for pruning to be confirmed once via the GitHub API and cached, only updating it when both the git-protocol HEAD and the API's `default_branch` agree, and log/notify users when the default branch changes so silent divergence is visible before any deletion occurs.

### Proof of Concept
1. Set up a malicious/compromised git server as `origin` for a test repository.
2. Have the victim create local branch `feature-x` at commit `A` (not pushed, or previously pushed and known to the attacker).
3. On the malicious server, construct a branch `main` whose tip commit `B` has `A` as an ancestor (e.g., server creates `B` as a descendant of `A` even though the real project's `main` never actually incorporated `A`), and advertise `HEAD -> refs/heads/main` for that ref.
4. Victim runs a normal `fetch` in Desktop; `updateRemoteHEAD` (`app/src/lib/git/remote.ts:95-112`) runs `git remote set-head -a origin`, caching the attacker's `main` as the tracked default.
5. `findDefaultBranch` (`app/src/lib/find-default-branch.ts:21-35`) reports `main` as the default branch with no validation.
6. Within the next background prune cycle (`app/src/lib/stores/helpers/branch-pruner.ts:73-105`, every 4 hours or on repo load), `getMergedBranches(repository, 'main')` finds `feature-x` merged (since `A` is an ancestor of `B`), and — if `feature-x` isn't a reserved name, hasn't been checked out in 2 weeks, isn't in a worktree, and its upstream tracking branch was removed on the malicious remote — it is silently deleted via `deleteLocalBranch` (`app/src/lib/git/branch.ts:101-107`), with no user prompt or confirmation.

    env: await envForRemoteOperation(remote.url),
    isBackgroundTask,
  }

    repository.path,
    'updateRemoteHEAD',
    options
  )
}

export async function getRemoteHEAD(
  repository: Repository,
  remote: string
): Promise<string | null> {
  const remoteNamespace = `refs/remotes/${remote}/`
  const match = await getSymbolicRef(repository, `${remoteNamespace}HEAD`)
  if (
    match != null &&
    match.length > remoteNamespace.length &&
    match.startsWith(remoteNamespace)
  ) {
    // strip out everything related to the remote because this
    // is likely to be a tracked branch locally
    // e.g. `main`, `develop`, etc
    return match.substring(remoteNamespace.length)
  }

  return null
}

  private async findBranchesMergedIntoDefaultBranch(
    repository: Repository,
    defaultBranch: Branch
  ): Promise<ReadonlyMap<string, string>> {
    const gitStore = this.gitStoreCache.get(repository)
    const mergedBranches = await gitStore.performFailableOperation(() =>
      getMergedBranches(repository, defaultBranch.name)
    )

    if (mergedBranches === undefined) {
      return new Map<string, string>()
    }

    const currentBranchCanonicalRef = await getSymbolicRef(repository, 'HEAD')

    // remove the current branch
    if (currentBranchCanonicalRef) {
      mergedBranches.delete(currentBranchCanonicalRef)
    }

    return mergedBranches
  }
