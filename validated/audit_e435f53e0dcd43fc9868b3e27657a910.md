### Title
One dust-sized or oversized payment bricks the entire batched Bitcoin multisig transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` validates every payment in the batch and aborts construction of the whole transaction if any single payment is invalid (below the dust limit, or large enough via its `script_pubkey` to push the transaction over the standard weight limit). This is the Serai analog of the Sablier `_cancel()` bug: a transfer to one "recipient" that fails reverts the entire operation, letting an unprivileged party (anyone who can cause a payment entry to be included, e.g. via a burn/OutInstruction) permanently block all other payments and the spending of all inputs in that batch.

### Finding Description
In `SignableTransaction::new`, the constructor iterates over all `payments` and returns `TransactionError::DustPayment` if any payment amount is below `DUST` (546 sats):

```rust
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

It then builds a single transaction containing every input and every output, and rejects the entire batch if the aggregate weight exceeds `MAX_STANDARD_TX_WEIGHT` (`TooLargeTransaction`). There is no mechanism to drop or split out a single offending payment: one bad entry causes `new` to return `Err`, and since plan/batch construction is deterministic, every retry fails identically. The inputs committed to the plan (the multisig's `ReceivedOutput`s) cannot be spent through this transaction, mirroring how the Sablier recipient's reverting `safeTransfer` bricks the sender's portion of the cancel.

An attacker-controlled payment (amount `< 546`, or a `script_pubkey` large enough to exceed the weight cap) therefore poisons the batch for all other recipients.

### Impact Explanation
All payments in the affected batch, and all multisig inputs selected for it, become unspendable through that plan: the signing transaction can never be constructed, so the threshold ceremony never starts. If the multisig scheduler retries with the same plan, it fails deterministically and indefinitely — funds remain locked until external intervention rewrites the plan. This matches the Sablier impact: one party's failing leg bricks the counterparty's (and here, every other recipient's) funds.

### Likelihood Explanation
Payments are derived from user-submitted burn/withdrawal instructions, so any unprivileged user can submit a sub-dust withdrawal amount or an oversized destination script. No privileged position, collusion, or validator misbehavior is required — a single malformed withdrawal request is sufficient to halt the batch containing it.

### Recommendation
Instead of erroring on the whole batch, filter out or quarantine invalid payments before constructing the transaction: drop payments below `DUST` (or emit them into a separate dedicated plan), enforce a maximum `script_pubkey` size per payment, and cap the number of outputs so a single poisoned entry cannot abort unrelated transfers — the same "split into separate transactions" fix Sablier applied to `_cancel`.

### Proof of Concept
```rust
use bitcoin::script::ScriptBuf;
use bitcoin::OutPoint;
use networks::bitcoin::wallet::{SignableTransaction, ReceivedOutput, TransactionError};

// `honest_output` is a ReceivedOutput previously scanned by the Scanner.
let inputs = vec![honest_output];

// An attacker causes a dust-valued payment to be included alongside
// a legitimate user's withdrawal in the same plan/batch.
let payments = vec![
  (honest_scriptbuf, 100_000),  // legitimate withdrawal
  (attacker_scriptbuf, 100),    // < DUST (546)
];

let res = SignableTransaction::new(inputs, &payments, None, None, 10);
assert_eq!(res.unwrap_err(), TransactionError::DustPayment);
// The entire transaction fails to build: neither the attacker's dust
// payment nor the legitimate 100k-sat withdrawal — nor any other input
// committed to this plan — can ever be spent via this batch.
```

Alternatively, the attacker supplies a payment whose `script_pubkey` is large enough that `calculate_weight_vbytes`/`tx.weight()` exceeds `bitcoin::policy::MAX_STANDARD_TX_WEIGHT`, yielding `TransactionError::TooLargeTransaction` — again aborting the whole batch deterministically on every retry.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
