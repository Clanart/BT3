### Title
`git submodule update` re-enables `file://` submodule cloning, allowing an attacker-controlled `.gitmodules` to read files from outside the repository - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  conditionally injects `-c protocol.file.allow=always` into the `git submodule update --init --recursive` invocation whenever the caller passes `allowFileProtocol: true`. This flag is threaded through from `checkoutBranch`/`checkoutCommit` in [2](#0-1)  and [3](#0-2) .

### Finding Description
Modern Git defaults `protocol.file.allow` to `user` specifically to stop a cloned/fetched repository's `.gitmodules` from silently pulling in `file://` URLs that point at arbitrary local paths (the fix for the "submodule can escape the repo via local file protocol" class of issue). Desktop's `updateSubmodulesAfterOperation` deliberately re-widens this to `always` whenever `allowFileProtocol` is `true`:

```
const args = [
  ...(allowFileProtocol ? ['-c', 'protocol.file.allow=always'] : []),
  'submodule', 'update', '--init', '--recursive',
]
``` [4](#0-3) 

The broken invariant is: Git's own `protocol.file.allow=user` guard exists precisely to distinguish trustworthy top-level URLs from attacker-supplied submodule URLs, but Desktop's boolean flag collapses that distinction into a blanket "always allow" for the *entire* recursive submodule update. `.gitmodules` content is fully attacker-controlled — anyone can craft a repository whose `.gitmodules` declares a submodule with `url = file:///Users/<user>/.ssh` (or any other local path). If any code path reaches `updateSubmodulesAfterOperation`/`checkoutBranch`/`checkoutCommit` with `allowFileProtocol = true` while operating on such a hostile repository, `git submodule update --init --recursive` will happily clone the local filesystem path into the submodule directory inside the working tree, regardless of the fact that the URL has nothing to do with the actual remote host.

### Impact Explanation
This is a file-read-outside-repo-intent primitive: the content of an arbitrary local directory the git process can access gets copied into the working tree as the contents of a "submodule." Once materialized on disk it is indistinguishable from normal repo content — it will show up in Desktop's file list/diff view and, if the user stages/commits it (which is easy to do inadvertently on "Add submodule"/commit-all flows), the previously-local, non-repo files get pushed to the attacker's remote, resulting in credential/config exfiltration. This matches the "silent corruption of what the user commits or pushes" and "file read outside the repo" categories called out as valid impact for this analysis.

### Likelihood Explanation
The exploitability hinges entirely on which call sites pass `allowFileProtocol = true`. Both `checkoutBranch`/`checkoutCommit` default this parameter to `false`, so by default the guard is intact and Git's `protocol.file.allow=user` default applies. The risk is limited to whatever caller(s) opt into `allowFileProtocol = true` for a repository whose trust boundary includes attacker-controlled `.gitmodules` content (e.g., any flow that treats "this operation is safe for file:// submodules" based on a condition broader than "the top-level remote itself is a local/file:// remote initiated by the user"). I was not able to enumerate every call site of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` with the remaining tool budget, so I cannot confirm with certainty that a caller passes `true` for network-origin repositories rather than only for local test/tutorial fixtures (the test suite in `app/test/unit/git/pull/pull-test.ts` and `rev-parse-test.ts` only exercises this via direct `-c protocol.file.allow=always` in local fixture setup, not via the app's real dispatcher flow). This is the key open question a follow-up investigation (e.g., grepping `dispatcher.ts`/`git-store.ts` for `allowFileProtocol`) would need to resolve before treating this as confirmed-exploitable rather than a latent design risk.

### Recommendation
- Never set `protocol.file.allow=always` globally for `git submodule update`. If local-repository submodules must be supported (e.g., for Desktop's own test fixtures or intentionally local-cloned repos), scope the allowance per-submodule URL by validating that the `file://` path is not attacker-influenced, or use `protocol.file.allow=user` combined with an explicit allow-list rather than `always`.
- Audit every caller of `checkoutBranch`, `checkoutCommit`, and `updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is only ever `true` when the top-level repository itself was opened via a local/file path chosen directly by the user (mirroring Git's own `protocol.file.allow=user` semantics), never for repositories cloned/fetched from a remote/attacker-influenced source.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitmodules` file:
   ```
   [submodule "evil"]
     path = evil
     url = file:///Users/victim/.ssh
   ```
2. Victim clones/fetches this repository in Desktop and performs an operation that reaches `updateSubmodulesAfterOperation` with `allowFileProtocol = true` (exact trigger path unconfirmed — see Likelihood section).
3. `git -c protocol.file.allow=always submodule update --init --recursive` executes, cloning `/Users/victim/.ssh` into `evil/` inside the working tree.
4. The victim's SSH keys now appear as ordinary tracked files in the repository; if committed and pushed, they are exfiltrated to the attacker-controlled remote.

Because I could not fully verify (within the remaining tool budget) which production call sites set `allowFileProtocol = true` against non-local repositories, this should be treated as a **high-confidence design-level risk requiring verification** rather than a fully proven end-to-end exploit chain.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
