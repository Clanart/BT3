### Title
Payout `OP_RETURN` operator attribution is not signature-bound, allowing SIGHASH-malleability/RBF substitution of the credited operator - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the `payout_tx`'s `OP_RETURN` output directly from the `operator_xonly_pk` argument supplied by the calling operator, with no cryptographic binding between that value and the withdrawer's `user_sig`, which only authorizes the `SpendPath::KeySpend` of the withdrawal input. [1](#0-0)  Because the user-provided signature is generated off-chain and only needs to authorize the spend of the funding input/output pair (per the documented design of giving the operator flexibility over fee/anchor outputs), the `OP_RETURN` output that names "who fronted the payout" is not itself covered by any commitment tying it to the actual broadcaster of the transaction.

### Finding Description
The binding that should hold is: `operator_xonly_pk embedded in payout_tx's OP_RETURN == identity of the operator whose signing/broadcast process produced that specific payout_tx`. In `create_payout_txhandler`, the `op_return_txout` is constructed purely from the function argument `operator_xonly_pk` [2](#0-1)  while the only cryptographic authorization present on the transaction is `user_sig` applied via `set_p2tr_key_spend_witness` to the single withdrawal input [3](#0-2) . The withdrawer's signature is generated off-chain (per the function's own doc comment: "committed in Citrea side, with the signature given to operators off-chain") and, per the audit's stated precondition, uses `SIGHASH_SINGLE | ANYONECANPAY` for this input — a sighash flag that commits only to the current input and the output at the same index, leaving the anchor output and the `OP_RETURN` output unsigned and freely mutable by anyone holding the broadcast transaction bytes.

Consequently, once an operator broadcasts `payout_tx` to the mempool (unconfirmed), any party — including another operator or an unprivileged attacker who observes the mempool — can reconstruct a variant transaction that reuses the same witness/signature on the same input, keeps the withdrawer-facing output unchanged (to remain valid under the signed sighash), but replaces the `OP_RETURN`'s `operator_xonly_pk` with an arbitrary value, and rebroadcasts it as an RBF fee-bump (per `TransactionType::Payout` being RBF-enabled in `tx_sender_queue.rs`). If this replacement confirms first, the on-chain record used by downstream attribution logic (`update_finalized_payouts` in `core/src/verifier.rs`, and operator-side reconciliation via `is_utxo_spent`/`get_reimbursement_txs` in `core/src/operator.rs`) will observe a payout transaction spending the withdrawal UTXO whose `OP_RETURN` names a different operator than the one who actually built and broadcast the original.

### Impact Explanation
I was not able to fully confirm, within the available investigation budget, how `update_finalized_payouts` (core/src/verifier.rs) and `get_reimbursement_txs`/`is_utxo_spent` (core/src/operator.rs) consume the `OP_RETURN` value downstream — specifically, whether this attribution is enforced on-chain (e.g., checked against the kickoff's operator identity by verifiers or the disprove/bridge circuit) or is purely informational bookkeeping. This distinction is decisive: if the OP_RETURN operator field is load-bearing for deciding who is entitled to reimbursement, the described attack would match the "honest operator permanently unable to be reimbursed" Critical category, since the honest operator's own `is_utxo_spent(withdrawal_utxo)` would report the UTXO as spent by a transaction not naming them, blocking their reimbursement path, while an arbitrary named party is credited instead. If, however, the actual on-chain reimbursement claim (kickoff → challenge → disprove → reimburse_tx) is gated by the operator's own presigned kickoff/round sequence rather than by the payout `OP_RETURN` content, this field may only affect off-chain bookkeeping/UI without a path to fund misdirection.

### Likelihood Explanation
The technical primitive (SIGHASH_SINGLE|ANYONECANPAY malleability plus RBF fee-bump replacement) is plausible given the code as read and the documented off-chain signature design, and requires no privileged role — only mempool visibility and fee capital, consistent with the unprivileged attacker model. However, without confirming the downstream consumption of the `OP_RETURN` field in `update_finalized_payouts`/`get_reimbursement_txs`/the bridge circuit, I cannot confirm the sighash type actually used for `user_sig`, nor whether existing guards (e.g., `is_kickoff_malicious`, `lc_proof_verifier`, or the presigned transaction graph) already prevent this divergence from having economic consequence.

### Recommendation
Given the incomplete verification of the downstream binding, no fix is prescribed here. A background engineer should confirm (a) the exact sighash flags used to produce `user_sig` for `payout_tx`, and (b) whether `update_finalized_payouts`, `get_reimbursement_txs`, or the bridge/disprove circuit enforce that a confirmed payout's `OP_RETURN` operator matches the operator submitting reimbursement/kickoff. If the OP_RETURN is load-bearing and the sighash indeed excludes it, the payout `OP_RETURN` (and anchor) outputs should be brought under the signed commitment (e.g., via `SIGHASH_ALL` or an explicit additional commitment covering all outputs), or attribution should be derived from a source independent of the mutable output.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
