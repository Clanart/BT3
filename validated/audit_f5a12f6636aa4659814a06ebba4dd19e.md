### Title
CLI `verify-package` reports false positive because it never compares deployed bytecode to source-derived metadata - (File: `aptos-move/cli/src/commands.rs`, `aptos-move/cli/src/stored_package.rs`)

### Summary
The `VerifyPackage` CLI command is the Aptos-native analog to "callers trusting a value that was never actually validated." It is meant to let a user confirm that the code running on-chain at an address matches a given source tree. In practice it only compares self-reported `PackageMetadata` fields against a locally rebuilt copy of the same self-reported metadata, and never fetches or diff-checks the actual on-chain module bytecode. A publisher can therefore make `verify-package` print "Successfully verified source of package" while the bytecode actually executing on-chain is arbitrary and unrelated to the declared/verified source.

### Finding Description
`code::publish_package` / `object_code_deployment::publish` / `object_code_deployment::upgrade` accept `metadata_serialized` (a `PackageMetadata`, containing per-module `name`, gzipped `source`, `source_map`) and `code: vector<vector<u8>>` (the actual compiled modules) as two entirely independent parameters [1](#0-0) . Nothing in `publish_package`, `check_dependencies`, `check_upgradability`, or the native `request_publish`/`request_publish_with_allowed_deps` path ties the declared `ModuleMetadata.source` to the `code` bytes being published — the on-chain validation in `AptosVM::validate_publish_request` only checks module name registration, dependency allow-lists, and native/metadata-for-publishing rules, never the relationship between source text and bytecode [2](#0-1) . `ModuleMetadata` itself carries no bytecode hash to bind the two together [3](#0-2) .

The CLI's `VerifyPackage::execute` is the only tool meant to close this gap for end users/auditors. It builds the package locally to obtain `compiled_metadata`, fetches the on-chain `PackageMetadata` via `CachedPackageRegistry::create(client, self.account, false)` — note `with_bytecode: false`, meaning the actual deployed module bytes are never downloaded — and then calls `package.verify(&compiled_metadata)` [4](#0-3) . `verify()` only compares `name`, `deps`, `modules` (metadata objects: name/source/source_map/extension — not bytecode), `manifest`, `upgrade_policy`, and `source_digest`, and never touches actual bytecode bytes [5](#0-4) . Since `source_digest` is computed purely from the declared source files by the packaging tool, and the on-chain `ModuleMetadata.source`/`source_map` are just whatever bytes the publisher chose to write into the metadata parameter at publish time, a publisher can submit a `PackageMetadata` whose `source`/`source_digest`/`manifest` fields describe innocuous code while submitting completely different, malicious `code` bytes in the same transaction. The `verify-package` command will locally recompute the same "innocuous" metadata from the innocuous source shown to the auditor, compare it field-by-field to the identical self-reported innocuous metadata on chain, find a match, and declare success — despite the live bytecode being unrelated.

### Impact Explanation
This directly produces the "mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" condition called out as an acceptable publish-path impact. Users, dependents, or auditors who rely on `aptos move verify-package` (or the analogous `DownloadPackage`/source-review workflow) to confirm what code is actually running at a package address receive a false assurance. This can mask a malicious upgrade or an initial malicious deployment disguised as benign, reviewed source — a supply-chain trust bypass on a code-safety-critical publish/verification flow that current mainnet tooling relies on.

### Likelihood Explanation
High likelihood of occurrence whenever it's exploited intentionally: the mismatch requires no special privilege beyond being the package owner, who already controls both the `metadata_serialized` and `code` transaction arguments passed to `code::publish_package_txn`. No race condition or front-running is needed — a single publish/upgrade transaction with mismatched metadata/bytecode suffices, and the verification gap is deterministic (the CLI never fetches bytecode by design, `with_bytecode: false`).

### Recommendation
Change `VerifyPackage::execute` to fetch actual on-chain module bytecode (`CachedPackageRegistry::create(client, self.account, true)` and `get_bytecode`) and compare it byte-for-byte (or via hash) against modules recompiled from the same local source tree, rather than only comparing self-reported metadata objects. Consider also binding a bytecode hash into `ModuleMetadata`/`PackageMetadata` (or an on-chain event) at publish time, verified against actual `compiled_module` bytes, so downstream tools can cryptographically confirm source-to-bytecode correspondence without needing to trust the publisher's self-reported source blob.

### Proof of Concept
1. Compile package A with benign source `S_benign` producing `PackageMetadata_benign` (source, source_digest, manifest) and bytecode `B_benign`.
2. Compile a second, malicious module `B_evil` (e.g., with a hidden backdoor entry function), but do not include this source in the metadata.
3. Publish on-chain via `code::publish_package_txn(signer, metadata_serialized = bcs(PackageMetadata_benign), code = [B_evil])`. Aptos VM's compatibility/verifier checks pass because they only validate `B_evil` as a standalone module (address, verifier, compat, deps) — they never validate `B_evil` against `PackageMetadata_benign.modules[0].source`.
4. Run `aptos move verify-package --account <addr>` pointing at the local project containing `S_benign`. `VerifyPackage::execute` rebuilds `PackageMetadata_benign` locally, fetches `PackageMetadata_benign` from chain (bytecode not fetched), calls `.verify()`, all fields match, and the CLI prints "Successfully verified source of package" — while `B_evil` is what actually executes at `<addr>`.

    async fn execute(self) -> CliTypedResult<&'static str> {
        // First build the package locally to get the package metadata
        let build_options = BuildOptions {
            install_dir: self.move_options.output_dir.clone(),
            bytecode_version: fix_bytecode_version(
                self.move_options.bytecode_version,
                self.move_options.language_version,
            ),
            ..self.included_artifacts.build_options(&self.move_options)?
        };
        let w = self.env.writer();
        let pack = BuiltPackage::build_to(&w, self.move_options.get_package_path()?, build_options)
            .map_err(|e| CliError::MoveCompilationError(format!("{:#}", e)))?;
        let compiled_metadata = pack.extract_metadata()?;

        // Now pull the compiled package
        let client = self.rest_options.client(&self.profile_options)?;
        let registry = CachedPackageRegistry::create(client, self.account, false).await?;
        let package = registry
            .get_package(pack.name())
            .await
            .map_err(|s| CliError::CommandArgumentError(s.to_string()))?;

        // We can't check the arbitrary, because it could change on us
        if package.upgrade_policy() == UpgradePolicy::arbitrary() {
            return Err(CliError::CommandArgumentError(
                "A package with upgrade policy `arbitrary` cannot be downloaded \
                since it is not safe to depend on such packages."
                    .to_owned(),
            ));
        }

        // Verify that the source digest matches
        package.verify(&compiled_metadata)?;

        Ok("Successfully verified source of package")

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
                package_metadata.upgrade_policy,
                self_metadata.upgrade_policy
            )
        } else if self_metadata.extension != package_metadata.extension {
            bail!(
                "Extensions doesn't match {:?} : {:?}",
                package_metadata.extension,
                self_metadata.extension
            )
        } else if self_metadata.source_digest != package_metadata.source_digest {
            bail!(
                "Source digests doesn't match {:?} : {:?}",
                package_metadata.source_digest,
                self_metadata.source_digest
            )
        }

        Ok(())
    }
