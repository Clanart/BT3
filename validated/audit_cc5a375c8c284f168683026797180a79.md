### Title
Automatic remote URL rewrite from unvalidated GitHub API `clone_url` allows silent push/fetch redirection - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` silently rewrites a repository's local `origin` remote URL to whatever `clone_url` the GitHub API (or a GitHub Enterprise / proxy endpoint) returns for the matched owner/name, as long as the URL scheme (`https`/`ssh`) matches and the previously known clone URL matched the current remote. [1](#0-0)  Crucially, it never checks that the new `clone_url`'s **hostname** matches the account/endpoint that was actually queried — only that the *protocol* matches. [2](#0-1)  This is invoked automatically, with no user prompt, every time Desktop refreshes GitHub repository metadata (repository selection, fetch, etc.), via `repositoryWithRefreshedGitHubRepository`. [3](#0-2) 

### Finding Description
This is the "bad oracle" pattern applied to Desktop's trust model: an external, potentially attacker-influenceable data source (the GitHub/GHES REST API response for `repos/{owner}/{name}`) is treated as ground truth and used to overwrite a security-relevant local value — the git `origin` remote URL — without validating that the returned value is consistent with the identity of the endpoint being queried.

The flow:
1. `repositoryWithRefreshedGitHubRepository` matches the repository to an account by comparing the *current* remote's hostname against a signed-in account's endpoint hostname, then calls `api.fetchRepository(owner, name)` against that endpoint. [4](#0-3) 
2. The raw `IAPIFullRepository` response (specifically `apiRepo.clone_url`) is passed straight into `updateRemoteUrl`. [3](#0-2) 
3. `updateRemoteUrl` checks only: (a) `protocolsMatch` — do the URL *schemes* match (`https` vs `https`, or both null implying ssh), and (b) `remoteUrlUnchanged` — did the previously cached GitHub `cloneURL` still match the working remote. If both hold and the new URL differs, it calls `gitStore.setRemoteURL(...)` to rewrite `origin`. [5](#0-4) 
4. At no point is the *hostname* of the new `clone_url` compared to the hostname of the account/endpoint that produced it, nor to the previous remote's hostname. `urlMatchesRemote` (used elsewhere for hostname+owner+name comparisons) is available in the codebase [6](#0-5)  but is not used here to gate the hostname of the *new* URL — it's only used to detect whether the URLs already match (which is expected to be false, since that's the update trigger).

The unit tests only exercise benign scenarios (repo renamed within `github.com`, protocol mismatches blocking, and locally customized remotes blocking) — none of the tests cover a scenario where the new `clone_url` points to a completely different, attacker-controlled hostname while keeping the same scheme. [7](#0-6) 

### Impact Explanation
If an attacker can influence the `clone_url` field returned for a repository lookup — e.g. via a compromised/malicious GitHub Enterprise Server instance the user has added as an account, a MITM/rogue proxy sitting in front of that GHES endpoint, or any GitHub API response tampering reachable to the client — Desktop will **silently** rewrite the user's `origin` remote to an attacker-controlled host with a matching scheme (e.g. `https://attacker.example/owner/repo`), with no confirmation dialog. Subsequent `git fetch`/`git push` operations, and any credential helper interaction tied to that URL, are directed at the attacker's server, matching the requested impact categories: credential/token exfiltration (via HTTP Basic/credential-helper prompts against the wrong host) and silent corruption of what the user pushes (pushing commits to an attacker-controlled remote instead of the real repository, or fetching attacker-supplied refs believed to be from `origin`).

### Likelihood Explanation
This requires the attacker to control (or MITM) a GitHub Enterprise Server / API endpoint that the victim has already added as an authenticated account in Desktop — this is within the valid impact scope ("attacker controls...a git remote/proxy response") and does not require local/physical access, existing malware, or leaked credentials. The rewrite is fully automatic and silent, triggered on ordinary use (selecting a repo, fetching), which raises likelihood once such an endpoint is reachable. This is not exploitable purely by a hostile GitHub.com repository owner, since dotcom's real API is presumably trustworthy; the practical vector is a rogue/compromised self-hosted GHES instance or a network position that can tamper with responses from one.

### Recommendation
In `updateRemoteUrl`, require that the new `clone_url`'s hostname matches the hostname of the account/endpoint being queried (or the hostname of the previous remote) before calling `setRemoteURL`, in addition to the existing protocol check. Reuse `parseRemote`/`urlMatchesRemote`-style hostname comparison to reject cross-host rewrites, and consider surfacing a confirmation prompt to the user before silently repointing `origin` to a different host.

### Proof of Concept
1. User adds a GitHub Enterprise account whose endpoint is (or is later MITM'd/compromised to be) attacker-influenced.
2. User has a local repository with `origin` pointing to `https://ghe.example.com/owner/repo.git`, associated with that GHES account.
3. On the next repository refresh (e.g., selecting the repo or performing a fetch), Desktop calls `api.fetchRepository(owner, name)` against that endpoint. [8](#0-7) 
4. The (compromised/malicious) server responds with `clone_url: "https://evil.example.com/owner/repo.git"` — same `https` scheme, different host.
5. `updateRemoteUrl` sees `protocolsMatch === true` and `remoteUrlUnchanged === true` (previous cached cloneURL still matches current remote) and `urlsMatch === false` (different host), so it calls `gitStore.setRemoteURL('origin', 'https://evil.example.com/owner/repo.git')`, rewriting the user's `origin` remote with no prompt. [9](#0-8) 
6. The user's next `git push`/`git fetch` on `origin` now targets `evil.example.com`, exposing credentials to that host and/or silently substituting fetched content.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

  it("updates the repository's remote url when the github url changes", async t => {
    const { gitHubRepository, gitStore } = await createRepository(
      t,
      apiRepository
    )
    assert(gitStore.currentRemote !== null)

    const originalUrl = gitStore.currentRemote.url
    const updatedUrl = 'https://github.com/my-user/my-updated-repo'
    const updatedApiRepository = { ...apiRepository, clone_url: updatedUrl }
    await updateRemoteUrl(gitStore, gitHubRepository, updatedApiRepository)
    assert.notEqual(originalUrl, updatedUrl)
    assert.equal(gitStore.currentRemote.url, updatedUrl)
  })

  it("doesn't update the repository's remote url when the github url is the same", async t => {
    const { gitHubRepository, gitStore } = await createRepository(
      t,
      apiRepository
    )
    assert(gitStore.currentRemote !== null)
    const originalUrl = gitStore.currentRemote.url
    assert.notEqual(originalUrl.length, 0, 'Expected originalUrl to be empty')
    await updateRemoteUrl(gitStore, gitHubRepository, apiRepository)
