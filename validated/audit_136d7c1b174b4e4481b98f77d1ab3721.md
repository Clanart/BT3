### Title
IBC-received value is duplicated when `erc20` middleware overturns a successful ICS20 receipt into an error acknowledgement - (File: x/erc20/ibc_middleware.go, x/erc20/keeper/ibc_callbacks.go)

### Summary
The `x/erc20` IBC middleware wraps the ICS20 transfer app and, after the inner transfer app has *already* credited/unescrowed coins to the receiver, runs additional ERC20 registration/conversion logic. If that additional logic fails, the middleware discards the already-successful acknowledgement and substitutes an `ErrorAcknowledgement`, even though the underlying balance mutation from the inner transfer is not rolled back. This breaks the ICS20 atomicity invariant (state change ⇔ acknowledgement outcome must match) and lets an unprivileged user duplicate spendable value across chains.

### Finding Description
`erc20.IBCMiddleware.OnRecvPacket` first calls the wrapped ICS20 transfer module and only afterwards runs the erc20-specific logic: [1](#0-0) 

The inner call `im.Module.OnRecvPacket(...)` is the standard `transfer.IBCModule.OnRecvPacket`, which performs the actual bank state mutation (minting a voucher denom, or unescrowing a previously-escrowed native-ERC20-backed coin) and returns a *successful* acknowledgement. Only if that succeeds does execution proceed to `im.keeper.OnRecvPacket(ctx, packet, ack)`.

Inside `keeper.OnRecvPacket`, two branches can still fail and replace the already-successful `ack` with an `ErrorAcknowledgement`:

- Case 1 (new IBC denom): `RegisterERC20Extension` → `CreateNewTokenPair`/`SetToken` can return `ErrTokenPairAlreadyExists` if the denom or the deterministic ERC20 address is already registered.
- Case 2 (native ERC20 round-trip): `MintingEnabled` or `ConvertCoinNativeERC20` can fail (e.g. `ErrBalanceInvariance`, EVM call failure, or unexpected `Approval` events) and the middleware returns `channeltypes.NewErrorAcknowledgement(err)`. [2](#0-1) 

Crucially, none of these failure branches undo the state changes already committed by `im.Module.OnRecvPacket` (the bank credit/unescrow to the receiver). In the Cosmos SDK / ibc-go packet-processing flow, the Acknowledgement bytes written to the channel store are informational for the relayer/counterparty chain; they do not cause a rollback of state mutations already applied by the module during `OnRecvPacket`. Contrast this with `OnAcknowledgementPacket`/`OnTimeoutPacket`, which explicitly document a fallback design ("if conversion fails ... the user receives the corresponding bank token instead") — that graceful degradation is missing from `OnRecvPacket`.

The result: the receiving chain keeps the credited/unescrowed coin balance for the recipient, while the sending chain, upon seeing the resulting error acknowledgement, refunds (mints/unescrows) the original amount back to the sender. The same value now exists on both chains simultaneously — a duplication of spendable user value.

### Impact Explanation
This falls squarely under the "Critical unauthorized minting/duplication of spendable user value across native balances/IBC escrows" allowed impact. An unprivileged party (a token owner controlling an ERC20 contract registered as a native token pair, or anyone able to reach a state where `SetToken`/`MintingEnabled`/`ConvertCoinNativeERC20` deterministically fails post-credit) can trigger a chain state where:
1. The receiver's bank balance is credited/unescrowed by the inner ICS20 transfer (unconditional success), and
2. The counterparty chain independently refunds the sender due to the substituted error acknowledgement,
producing two spendable copies of the same value across the two chains — an irreversible accounting corruption, not merely a griefing/DoS as in the referenced report.

### Likelihood Explanation
Reaching Case 1's failure (colliding deterministic ERC20 address for a brand-new IBC denom) requires an address collision that is hard for an attacker to engineer directly (CREATE2 preimage search is infeasible), so that specific sub-case is low likelihood in isolation. Case 2, however, is directly reachable by any user who controls the underlying ERC20 contract of a *native* token pair (e.g., a token owner who deploys a contract with pausable/blacklist/fee-on-transfer/mint-guard logic, or whose contract self-destructs or reverts under specific conditions) and performs a round-trip IBC send of that token. Because `MintingEnabled`/`ConvertCoinNativeERC20` execute arbitrary EVM calls against a contract the "victim" (here, the same or a colluding party) controls, the failure condition is fully attacker-controllable, making exploitation practical without any privileged access, front-running, or validator collusion — matching the "unprivileged trigger" requirement.

### Recommendation
- Make `keeper.OnRecvPacket`'s post-processing atomic with respect to the acknowledgement it produces: execute the ERC20 registration/conversion logic (and the underlying transfer receipt) within a single cached context that is only committed if the overall result is a success acknowledgement; otherwise discard all changes (including the inner transfer module's mutation) before writing the error acknowledgement.
- Alternatively, mirror the design already used in `OnAcknowledgementPacket`/`OnTimeoutPacket`: never return an `ErrorAcknowledgement` from `keeper.OnRecvPacket` once the inner ICS20 transfer has succeeded. Instead, on registration/conversion failure, leave the recipient holding the plain bank coin (log/emit an event) and still return the original success acknowledgement, so the two chains' states remain consistent.
- Add invariant/integration tests asserting that whenever `OnRecvPacket` returns an error acknowledgement, no bank balance mutation persists from the same packet-processing call.

### Proof of Concept
1. Chain A deploys and registers (via `MsgRegisterERC20`, permissionless registration enabled) a native ERC20 contract whose `transfer` function can be made to revert or return `false` under attacker control (e.g., a pausable/blacklistable token), yielding a `TokenPair` with `ContractOwner = OWNER_EXTERNAL` — see registration flow: [3](#0-2) 
2. Attacker converts native coin to ERC20 and back is not required; instead, attacker sends the native-ERC20-backed coin out over IBC to chain B (escrowed on chain A), then sends it back to chain A via chain B (or times out/gets it returned), producing an incoming packet on chain A whose `coin.Denom` matches the already-registered native ERC20 pair's denom, hitting Case 2 in `OnRecvPacket`: [4](#0-3) 
3. Before the packet is relayed back, attacker pauses/blacklists the contract (or otherwise makes `transfer`/`Approval` checks fail) so that `k.ConvertCoinNativeERC20` returns `ErrBalanceInvariance` or an EVM error.
4. `im.Module.OnRecvPacket` (the inner ICS20 call) has already unescrowed/credited the bank coin to the receiver's account on chain A before `keeper.OnRecvPacket` runs and returns `ErrorAcknowledgement`.
5. Chain B, upon receiving the error acknowledgement, refunds the sender the original amount. Chain A's receiver now separately holds the unescrowed bank coin. The same value is now spendable on both chains.

Note: I was not able to fully trace the exact ibc-go v10 packet-handling code path in this repository confirming that `RecvPacket` never reverts a module's state changes purely based on the returned Acknowledgement’s success/failure content (this is standard ibc-go behavior but the specific vendored version's behavior was not directly inspected here due to tool budget). This should be verified in a live/testnet PoC before treating the severity as fully confirmed.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
