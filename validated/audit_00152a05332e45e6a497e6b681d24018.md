### Title
Silent, unconfirmed repointing of the `origin` remote URL from GitHub API data — no "confirm new destination" step ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The Solidity finding is about a single-step, unvalidated critical-state transfer: `Ownable.transferOwnership()` writes a new owner value with no secondary confirmation and no sanity check, so a bad value silently becomes authoritative. The GitHub Desktop analog is `updateRemoteUrl()`, which silently rewrites the local `origin` remote's URL to whatever `clone_url` the GitHub API returns for the tracked repository — with no user prompt, no diff review, and no confirmation step — unlike the equivalent flow for the `upstream` remote which explicitly asks the user via a dialog.

### Finding Description
`updateRemoteUrl()` in [1](#0-0)  compares the repository's current default remote URL against `apiRepo.clone_url` from a freshly fetched `IAPIFullRepository`. If the protocol matches and the current remote still matches the *previously* stored `gitHubRepository.cloneURL` (i.e., the user hasn't manually customized it), the function calls `gitStore.setRemoteURL(...)` and silently executes `git remote set-url origin <new-url>` [2](#0-1)  — with no user-facing confirmation of any kind.

This is invoked automatically from `repositoryWithRefreshedGitHubRepository()`, which fetches `api.fetchRepository(owner, name)` and immediately calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` [3](#0-2) . This refresh path runs during ordinary background operations: adding a repository, refreshing the selected repository after account switch, and other periodic refreshes — the user never explicitly asked to change the remote.

The validation logic (`urlMatchesRemote` in [4](#0-3) ) only checks that hostname/owner/name of the *current* remote pattern-match; it does nothing to validate the *new* value being written except a same-protocol string comparison (`parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol`) in [5](#0-4) . There is no host allow-list, no check that the new host is a known/trusted account endpoint, and no user confirmation — the exact "no transfer ownership pattern" broken invariant: a critical destination value can be overwritten in one step based on external (API-supplied) input, with only superficial format checks and no explicit acceptance step by the value's true owner (the user).

Contrast this with the deliberately-designed **two-step, user-confirmed** pattern Desktop already uses elsewhere for a very similar remote-URL change: `UpstreamAlreadyExists` shows the current and proposed URL and requires the user to click "Update" or "Ignore" before `setRemoteURL` is invoked [6](#0-5) . No equivalent confirmation exists for the `origin` remote update path.

### Impact Explanation
`origin`'s URL determines where the user's future `git push`/`git fetch` operations go. If the attacker can influence the GitHub API's `clone_url` field for the tracked repository (e.g., a compromised/malicious GHES instance, a man-in-the-middle on the API connection for that account's endpoint, or an API response manipulated through a proxy), Desktop will silently rewrite `origin` to point at an attacker-controlled host on the next automatic refresh — without any dialog, diff, or opportunity for the user to notice or reject the change. Subsequent pushes would silently ship the user's commits to the attacker's server instead of the real repository (data exfiltration of source code, and platform for further attacks like serving malicious content in future fetches).

### Likelihood Explanation
The refresh path is triggered routinely and automatically (repo add, account-switch refresh, `_publishRepository`, etc.) via `repositoryWithRefreshedGitHubRepository()` [7](#0-6) , so no unusual user action is required — the user just needs to have the affected repository open/tracked in Desktop while pointed at an account whose API responses the attacker can influence (GHES/proxy/MITM scenario, which is within the stated "attacker controls a git remote/proxy response" scope). The existing guard (`protocolsMatch` + `remoteUrlUnchanged` + `!urlsMatch`) narrows *when* it fires but does not validate *what* it writes, so it does not stop a malicious but well-formed `clone_url`.

### Recommendation
Require explicit user confirmation before rewriting an existing `origin` remote URL sourced from API data, mirroring the `UpstreamAlreadyExists` dialog pattern (show current vs. proposed URL, require an explicit "Update" click). Additionally, validate that the new host corresponds to the same trusted endpoint/account the repository was already associated with before allowing an automatic rewrite, rather than relying solely on protocol-string equality.

### Proof of Concept
1. Add/track a repository in Desktop whose GitHub association's account endpoint is a GitHub Enterprise Server the attacker can influence (e.g., via a compromising proxy sitting on the network path used for API requests to that endpoint, or a malicious/compromised GHES instance).
2. Ensure the local `origin` remote currently matches the previously-known `gitHubRepository.cloneURL` (default state for anyone who cloned normally).
3. Have the attacker-controlled API response for `GET repos/{owner}/{name}` return an `clone_url` field pointing to an attacker-controlled `https://` host (matching protocol) with a different hostname.
4. Trigger any background refresh (adding the repo, switching accounts, or Desktop's periodic refresh) which calls `repositoryWithRefreshedGitHubRepository()` → `updateRemoteUrl()`.
5. Observe that `git remote set-url origin <attacker-url>` executes silently with no dialog, and the user's next push/fetch goes to the attacker's server.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
