# Finding: ProtoJSON duplicate-key detection in the Python binding accepts semantically-duplicate keys under alternate spellings, letting the last value silently smuggle past the intended anti-ambiguity check

## Summary
CVE-2023-46846 is a case of a parser being too *lenient* about ambiguous/duplicate framing input (chunked-encoding), letting distinct frontend/backend interpretations diverge and enabling smuggling. The transferable invariant is: **a parser explicitly designed to reject ambiguous/duplicate keys must catch every encoding of the same logical key, not just byte-identical ones.** In this checkout, Python's `json_format.Parse` implements exactly such a check for ProtoJSON object keys, but it only detects *exact string* duplicates. It does not canonicalize alternate spellings (`camelCase` vs `original_name`, or `json_name` vs default name) that both resolve to the *same* protobuf field, so two differently-spelled but field-equivalent keys are silently accepted with "last one wins" instead of raising the intended `ParseError`. This is acknowledged in-repo as a bug (not a design choice) in `python/google/protobuf/internal/json_format_test.py` [1](#0-0) .

## Finding Description
Protobuf's ProtoJSON spec requires unique keys and treats duplicate keys targeting the same field as invalid input — this is enforced (with varying strictness) across backends: the Java implementation explicitly tracks a `SeenState` per field/oneof and rejects re-use of an already-seen field [2](#0-1) , and the C++ `internal::json` parser has the same `RecordAsSeen`/`SeenState` machinery [3](#0-2) .

The Python binding (`python/google/protobuf/json_format.py`) implements its own duplicate-key rejection on top of the stdlib `json` loader. Its check is confirmed by test to work only on **byte-identical key strings**:

- `testDuplicateField` shows that `{"int32Value": 1, "int32Value": 2}` correctly raises `'Failed to load JSON: duplicate key int32Value.'` [4](#0-3) .
- `testDuplicateFieldAlternateNames` shows that `{"int32Value": 1, "int32_value": 2}` — two *different strings* that both resolve to the exact same protobuf field via the field-name/`json_name` lookup — is **accepted**, and the parser silently keeps the last value (`int32_value: 2`) instead of raising an error. The test's own comment states: *"this behavior is non-spec and an oversight bug in the implementation, but would be a breaking change to fix. The duplicate field checker intends [to] reject inputs with duplicate key names, but it only catches keys that are exact matches and not alternate spellings that correspond to the same field."* [5](#0-4) 
- The same gap exists for map keys: `testDuplicateFieldAlternateNamesMap` with `{"int32Map": {"1":2}, "int32_map": {"3":4}}` silently resolves to `{3: 4}` with no error [6](#0-5) .

This is the same class of defect as the Squid CVE: a decoder that is supposed to reject ambiguous framing (Squid: chunked boundaries; protobuf: which JSON key wins for a given field) instead applies a **lenient, incomplete equivalence check**, so two representations that a spec-compliant, strict validator would flag as conflicting are silently merged with "last wins" semantics. Anywhere the failed uniqueness check is treated as a security boundary — e.g., a gateway/policy layer that inspects the *first* occurrence of a named field (`int32Value`) for authorization while the actual protobuf `Parse()` call resolves the value from the *last*, alternately-spelled occurrence (`int32_value`) — the two systems will disagree about which value is authoritative, exactly mirroring the request-smuggling pattern of "front-end sees one framing, back-end sees another."

## Impact Explanation
This is a parsing-correctness/robustness issue, not itself a memory-safety or RCE bug: it manifests as silent divergence between the intended validation (reject ambiguous duplicate keys) and actual behavior (last-alternate-spelling wins with no error). Where consuming application code relies on ProtoJSON's documented duplicate-key rejection as an integrity/consistency guarantee (e.g., detecting tampering, ensuring a single unambiguous value per field before authorization decisions elsewhere in a request pipeline), an attacker-controlled ProtoJSON payload with two different spellings of the same field can bypass that guarantee. This matches the CVE's "Medium" severity class — an integrity/logic bypass reachable in a bounded, ordinary-client input, not memory corruption.

## Likelihood Explanation
High likelihood of reachability: this is triggerable via the fully public `google.protobuf.json_format.Parse()` API with a bounded, valid-JSON payload and a trusted, ordinary schema containing any singular scalar or map field — no special schema features, extensions, or privileged access are required. The bug is deterministic and already demonstrated by first-party tests in this checkout.

## Recommendation
Extend the Python `json_format` duplicate-key detector to canonicalize each incoming key to its resolved `FieldDescriptor` (as Java/C++ already do via `SeenState`/`RecordAsSeen`) before comparing for duplicates, rather than only comparing raw key strings, so that `json_name`/`camelCase`/`snake_case` aliases of the same field are correctly flagged as conflicting. Cross-reference the Edition-Zero JSON handling design doc, which frames this exact class of conflict and proposes a `json_format` feature (`ALLOW`/`DISALLOW`/`LEGACY_BEST_EFFORT`) to make this behavior consistent and well-defined across runtimes [7](#0-6) .

## Proof of Concept
Using the existing, unmodified test in this checkout as the reproduction:
```python
# python/google/protobuf/internal/json_format_test.py:1203-1205
parsed_message = json_format_proto3_pb2.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', parsed_message)
assert parsed_message.int32_value == 2  # no ParseError raised, "last-alternate-spelling wins"
``` [5](#0-4) 

Compare to the exact-match case, which correctly raises:
```python

                 'Failed to load JSON: duplicate key int32Value.')
