### Title
Missing caller authorization check in `CW721ERC721Pointer.transferFrom`/`approve` allows unauthorized NFT theft - (File: `contracts/src/CW721ERC721Pointer.sol`)

### Summary
`CW721ERC721Pointer` overrides OpenZeppelin's `ERC721.transferFrom` and `ERC721.approve` but drops the caller-authorization check that the base implementation normally performs (`_isAuthorized(owner, msg.sender, tokenId)`). The overridden functions only validate that the `from` parameter matches the actual token owner on the underlying CW721 contract — they never verify that `msg.sender` is that owner, an approved spender, or an approved operator. Any unprivileged EVM account can therefore call `transferFrom(realOwner, attacker, tokenId)` (or `approve(attacker, tokenId)`) for any pointer-wrapped CW721 token and it will succeed.

### Finding Description
In `contracts/src/CW721ERC721Pointer.sol`: [1](#0-0) 

```solidity
function transferFrom(address from, address to, uint256 tokenId) public override {
    if (to == address(0)) {
        revert ERC721InvalidReceiver(address(0));
    }
    require(from == ownerOf(tokenId), "`from` must be the owner");
    string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
    string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
    string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
    _execute(bytes(req));
}

function approve(address approved, uint256 tokenId) public override {
    string memory spender = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(approved)));
    string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
    string memory req = _curlyBrace(_formatPayload("approve", _curlyBrace(_join(spender, tId, ","))));
    _execute(bytes(req));
}
```

`transferFrom` checks only `from == ownerOf(tokenId)` — a fact anyone can know/observe from public state — and never checks `msg.sender`. This is exactly the class of bug described in the external report: reliance on a weak/absent caller-identity check instead of explicit ownership/authorization validation for a transfer-type function. Here it is strictly worse than the report's example, because there is no authorization check at all (not even a mis-scoped one via `_msgSender()`), rather than merely using the wrong sender-resolution function.

The `_execute` call forwards the request via the `WASMD_PRECOMPILE_ADDRESS` delegatecall to execute a `transfer_nft` message against the underlying CW20/CW721 contract on behalf of the pointer contract (which is presumably the registered owner/operator on the CW721 side, or otherwise has rights sufficient to move the token), so the CosmWasm-side call succeeds regardless of who invoked the EVM-side `transferFrom`. [2](#0-1) 

By contrast, the analogous ERC-20 pointer's `transferFrom` correctly relies on the CW20 contract's own `transfer_from` message, which validates allowance server-side via `_spendAllowance`-equivalent CosmWasm logic keyed on the executing account (the pointer contract) — but the CW721 pointer never establishes or checks any spender/approval relationship for `msg.sender` before submitting the `transfer_nft` message.

### Impact Explanation
Any unprivileged EVM account can steal any NFT wrapped by `CW721ERC721Pointer` by simply calling `transferFrom(currentOwner, attackerAddress, tokenId)` — no approval, ownership, or operator status is required. This is a direct unauthorized-transfer/fund (NFT) loss primitive reachable by any public-RPC client submitting a single transaction, satisfying the "unauthorized transfer via precompile or pointer" impact category.

Additionally `approve` has the same gap: any account can grant themselves (or any address) approval for any token ID they don't own, which can be chained with marketplaces or other integrations that trust `getApproved`/`isApprovedForAll` results.

### Likelihood Explanation
High. Exploitation requires only a single EVM transaction calling a public, unauthenticated function (`transferFrom`) on any deployed `CW721ERC721Pointer` instance, with no special privileges, front-running, or governance access needed. Any CW721 collection that has an ERC721 pointer created for it (a permissionless, user-triggered operation elsewhere in the pointer-registration flow) is affected.

### Recommendation
Restore the standard ERC721 authorization check before performing the transfer/approval, e.g.:
```solidity
function transferFrom(address from, address to, uint256 tokenId) public override {
    if (to == address(0)) {
        revert ERC721InvalidReceiver(address(0));
    }
    require(from == ownerOf(tokenId), "`from` must be the owner");
    require(
        msg.sender == from ||
        isApprovedForAll(from, msg.sender) ||
        getApproved(tokenId) == msg.sender,
        "ERC721: caller is not token owner or approved"
    );
    ...
}

function approve(address approved, uint256 tokenId) public override {
    address owner_ = ownerOf(tokenId);
    require(
        msg.sender == owner_ || isApprovedForAll(owner_, msg.sender),
        "ERC721: approve caller is not token owner or approved for all"
    );
    ...
}
```
This mirrors the exact remediation pattern from the external report (explicit sender/ownership verification before allowing transfer-type state changes), applied to the pointer contract's precompile-forwarding path.

### Proof of Concept
1. Alice owns CW721 token `#1`, wrapped by a deployed `CW721ERC721Pointer` instance `P`.
2. Attacker (no approval, no relationship to Alice) calls `P.transferFrom(alice, attacker, 1)` from their own EOA.
3. `require(from == ownerOf(tokenId), ...)` passes because `from == alice` is indeed the real owner (this is a public read, not an authorization proof).
4. No check exists on `msg.sender`, so execution proceeds to `_execute`, which submits `transfer_nft` to the CW721 contract via the wasmd precompile.
5. Token `#1` is transferred from Alice to the attacker without Alice's consent or any prior approval.
