### Title
Sub-dust Bitcoin deposits to the multisig external address are silently dropped by the scanner and become unspendable protocol funds - (File: processor/src/multisigs/scanner.rs)

### Summary
`Bitcoin::get_outputs` scans every non-coinbase transaction for outputs paying to the multisig key (`processor/src/networks/bitcoin.rs:686-700`), but the processor's scanner discards any output whose value is below `N::DUST` before emitting it (`processor/src/multisigs/scanner.rs:564`). The discarded output is still locked to the threshold key, yet no `ReceivedOutput`/plan is ever produced for it, so the protocol can never spend it — the exact shape of `donateETH`: a reachable deposit path that permanently strands funds in the contract/multisig.

### Finding Description
`get_outputs` returns every scanned output to `Scanner::run`, which filters with:

```rust
// processor/src/multisigs/scanner.rs:562-567
for output in network.get_outputs(&block, key).await {
  assert_eq!(output.key(), key);
  if output.balance().amount.0 >= N::DUST {
    outputs.push(output);
  }
}
```

Any deposit under the dust threshold is neither emitted in `ScannerEvent::Block` nor persisted via `save_outputs`. Downstream, the scheduler (`SignableTransaction::new` at `networks/bitcoin/src/wallet/send.rs:150`) can only spend outputs it is handed as `inputs: Vec<ReceivedOutput>`; since the dropped output never becomes a `ReceivedOutput`, no plan, refund, or forward can ever reference its outpoint. There is also no refund path — `burns_to_payments`/refund plans only operate on outputs that were scanned and acknowledged. The bitcoins remain under the FROST group key with no protocol-level way to construct a spending transaction, making them as unrecoverable as ETH donated to `OptimismPortal.donateETH` (which cannot be routed to the yield manager).

### Impact Explanation
An unprivileged sender deposits e.g. 500 satoshis (or any amount in `0 < v < N::DUST`) to the Serai Bitcoin external address (`external_address`/`p2tr_script_buf(key)`, `networks/bitcoin/src/wallet/mod.rs:80`). The deposit confirms on-chain, but the processor never credits, forwards, or refunds it. The funds are permanently locked under the validator set's threshold key — a direct loss of user funds. The parallel class also applies to the deterministic branch/change/forward addresses derived in `processor/src/networks/bitcoin.rs:333-344`.

### Likelihood Explanation
Deposit addresses are public and anyone can create a transaction paying to one. Sub-dust deposits occur through user error, dusting activity, or fee-precise sends; the code path is unconditional and requires no privileged position. The same outcome occurs for any scanned output below `N::DUST` at `OutputType::Branch`/`Change`/`Forwarded` offsets, which are predictable constants (`hash_to_F(KEY_DST, ...)`), so a third party can also deliberately strand funds into those addresses.

### Recommendation
Either spend sub-dust outputs (drop the `>= N::DUST` gate and let the scheduler decide whether to consolidate them at fee-economical times), or treat them explicitly: emit an event recording the stranded output and expose a documented recovery/forward path, analogous to forwarding `donateETH` funds to the yield manager. At minimum, reject these deposits on the Serai side (e.g., not acknowledging the outpoint while documenting the loss) rather than silently discarding them.

### Proof of Concept
1. Compute the multisig P2TR address via `p2tr_script_buf(group_key)` (`networks/bitcoin/src/wallet/mod.rs:80-86`).
2. Broadcast a transaction with an output of value `N::DUST - 1` to that script.
3. After confirmation, `Bitcoin::get_outputs` returns the `Output`, but `scanner.rs:564` drops it since `output.balance().amount.0 < N::DUST`.
4. The output never reaches `save_outputs`, `ScannerEvent::Block`, or any `Plan`; it cannot appear in `SignableTransaction::new`'s `inputs`, so it can never be spent by the multisig — funds permanently stuck.

Note: I could not fully trace the `PlanFromScanning::Forward` handling path (a second potential stuck-fund/panic analog where unsolicited sends to the deterministic forward address hit `expect("supposed to forward an output yet no forwarding plan")` at `processor/src/multisigs/mod.rs:598-600`); its preconditions were not fully verified within the available iterations, so the dust-filter finding is the cleaner, fully-supported analog.
