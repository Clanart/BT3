I found a concrete analog to the reported bug class: the `hookify` plugin's `PreToolUse` hook executor explicitly and unconditionally fails open on error, discarding blocking decisions the same way the Solidity bug discarded a revert.### Title
Hookify PreToolUse/PostToolUse/Stop hooks fail open on rule-engine errors, silently bypassing user-configured blocking rules - ([File: plugins/hookify/hooks/pretooluse.py])

### Summary
The `hookify` plugin's hook executors (`pretooluse.py`, `posttooluse.py`, `stop.py`) wrap all rule evaluation in a `try/except`, and unconditionally call `sys.exit(0)` in a `finally` block regardless of whether an exception occurred. This is the same bug class as the reported `SwapCallLib.call()` issue: when the underlying operation (rule evaluation) fails, the code discards the failure and returns a "success/allow" signal instead of propagating a blocking failure. Any exception in the hookify rule engine (malformed rule file, bad regex, `RuleEngine` bug, encoding error, etc.) causes a user's configured `block` rule (e.g., "block `rm -rf`") to be silently skipped, and the potentially dangerous tool call proceeds unimpeded.

### Finding Description
`pretooluse.py` is a `PreToolUse` command hook that Claude Code invokes before every Bash/Edit/Write/MultiEdit tool call when the `hookify` plugin is enabled. It loads user-defined `.claude/hookify.*.local.md` rules and evaluates them via `RuleEngine.evaluate_rules()`. On success it prints the JSON decision (which may include `{"decision": "deny", ...}` for `action: block` rules) [1](#0-0) .

Critically, any exception during `load_rules`/`evaluate_rules` is caught, logged only as a `systemMessage`, and the `finally` block always calls `sys.exit(0)`: [2](#0-1) 

Exit code `0` from a `PreToolUse` command hook is documented as "Success — stdout shown in transcript," i.e., no block/deny is applied [3](#0-2) . Because the hook always exits 0 on error — even though the comment explicitly says "never block operations due to hook errors" — a rule engine crash silently discards whatever block/deny decision would otherwise have been produced. This is functionally identical to the reported Solidity bug: a failure path that should propagate as a rejection (`revert`) instead falls through to a success signal (`return`), while the "state" (here, tool execution) proceeds unchecked.

The same pattern exists in `posttooluse.py` [4](#0-3)  and `stop.py` [5](#0-4) , meaning `Stop`-event block rules (e.g., "require tests before stopping") and `PostToolUse` warnings can also be silently dropped on any internal error.

### Impact Explanation
Hookify's documented purpose is to let an unprivileged user author blocking guardrails, e.g. "Block Dangerous Commands" (`rm -rf`, `dd`, `mkfs`, `format`) [6](#0-5) . If the rule engine throws for any reason (a corrupted rule file, an unexpected regex, an encoding issue, a future code change introducing a bug in `RuleEngine`), the `PreToolUse` hook fails open instead of failing closed: the destructive command the user explicitly configured to be blocked is allowed to execute. This is a concrete hook-bypass / local compromise scenario — the user's own safety net silently disengages exactly when something goes wrong, without any visible denial (only a `systemMessage`, which per the exit-0 contract is shown in the transcript as informational, not as a blocking rejection).

### Likelihood Explanation
Likelihood is moderate: it requires (a) the `hookify` plugin to be enabled with at least one `block` rule, and (b) an exception during rule loading/evaluation (malformed `.local.md` frontmatter, invalid regex pattern supplied by the user or generated by the `/hookify` command flow, or any latent bug in `hookify.core.rule_engine`/`config_loader`). Given that rules are user-authored markdown/YAML with regex patterns, malformed input is a realistic and easily-triggered condition, and the code path is explicitly designed (per its own comment) to swallow all such errors rather than fail closed.

### Recommendation
Change the fail-open `finally: sys.exit(0)` behavior to fail closed for blocking-capable hooks: on an unhandled exception, emit a blocking decision (exit code `2` with a clear `stderr` message, or `{"decision": "deny"/"block", "reason": "hookify internal error"}`) so tool execution is not silently permitted when the safety check itself is broken. At minimum, distinguish "no rules matched" (safe to allow) from "rule engine crashed" (should not silently allow) so a broken hook cannot masquerade as a passing one.

### Proof of Concept
1. Enable the `hookify` plugin and create `.claude/hookify.block-rm.local.md` with `event: bash`, `pattern: rm\s+-rf`, `action: block`.
2. Introduce (or trigger) a runtime error in the rule evaluation path — e.g., corrupt the rule file with invalid YAML frontmatter that `load_rules`/`RuleEngine` fails to parse and raises an unhandled exception (any exception not caught inside `evaluate_rules` itself bubbles up to `pretooluse.py`'s `try/except`).
3. Ask Claude to run `rm -rf /some/path`.
4. Observe that `pretooluse.py` catches the exception, prints only a `systemMessage` about the hookify error, and exits `0` [2](#0-1)  — the `rm -rf` command executes despite the user's explicit `block` rule, with no deny decision ever surfaced.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
```
