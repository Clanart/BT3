### Title
Self-referral via two attacker-controlled addresses drains the ReferralStorage MGP reward pool without genuine third-party recruitment - (File: rewards/ReferralStorage.sol)

### Summary
`useCode()` only guards against `codeOwners[_code] == msg.sender`, i.e. it prevents a single address from referring itself, but does nothing to prevent one person from registering a code on address A and calling `useCode` from a second address B they also control. Because `trigger()` then credits both a referer share and a referee share on top of the referee's own claimed emissions, the attacker collects both halves of the referral bonus using only their own capital, draining the finite MGP balance held by the contract for `claimReward()`.

### Finding Description
`registerCode()` lets any address register an arbitrary unused code and become `codeOwners[_code]` [1](#0-0) . `useCode()` binds `msg.sender` to that code as long as `codeOwners[_code] != msg.sender`, with no check that the caller is economically distinct from the code owner [2](#0-1) .

An attacker:
1. Registers a code from address A (`registerCode`).
2. Calls `useCode(_code)` from address B, a second wallet the same attacker controls. This passes the only self-referral check because `codeOwners[_code] == A != B`.
3. Stakes/claims normally from B. `MasterMagpie` calls `trigger(B, amount)`, which computes `refererAmount` (credited to A) and `refereeAmount` (credited to B) based on `tiers[tierId].rewardPercentage` and `_calBoosted(A)`, and adds both to `userInfos[A].rewardAmount` / `userInfos[B].rewardAmount` [3](#0-2) .
4. Both A and B call `claimReward()` and pull MGP out of the contract's balance [4](#0-3) .

`claimReward()` performs a plain `safeTransfer` with no check that the contract's actual MGP balance covers `rewardAmount`; the accounting variable `rewardAmount` is incremented purely from `trigger()` with no cap tied to the funded balance. Since referral percentages (`basic + boostesd`) are only ever validated against `DENOMINATOR` in isolation (in `setTier`/`_calBoosted`), nothing in the contract enforces that the referer and referee be distinct economic actors — the invariant "a referral bonus rewards genuine third-party recruitment" is not encoded anywhere in code, only implied by product intent.

### Impact Explanation
Every self-referral doubles the incentive rate an attacker effectively earns on their own emissions claim (referer share + referee share) versus a normal user with no referral, extracted from the same finite MGP pool used to pay legitimate referrers/referees. If enough attackers do this, `sum(userInfos[*].rewardAmount)` can exceed the contract's actual MGP balance, causing later, legitimate `claimReward()` calls to revert (`InsufficientRewardBalance` / transfer revert) — i.e., permanent loss/freezing of yield for honest users, and unjust enrichment for the attacker. This matches "High – Theft of unclaimed yield" since the loss is of protocol-held referral incentive funds, not attacker capital.

### Likelihood Explanation
Trivial and fully repeatable: requires only deploying/using two normal EOAs, no special role, and no capital beyond gas and whatever stake/lock the attacker would already be doing for their own emissions. It can be done by any user and repeated across arbitrarily many wallet pairs, scaling the drain linearly with the number of self-referral pairs and the volume of emissions each claims.

### Recommendation
On-chain identity/Sybil resistance cannot be perfectly enforced, but the specific "same-controller, two-address" case here is exacerbated by unbounded, unfunded accounting. Recommendations:
- Track and enforce that `rewardAmount` accrual cannot exceed the contract's actual MGP balance (or require the reward pool to be pre-funded/escrowed per referral event), so `claimReward` failures cannot be caused by uncollateralized `rewardAmount` growth.
- Consider requiring a minimum bonding/vesting period, KYC-free heuristics (e.g., minimum unlock history, address age), or a cap on referral bonus per referrer/referee pair to reduce the profitability of wallet-splitting.
- At minimum, make the referral reward budget owner-capped and monitored so a systemic self-referral campaign cannot exceed the funded amount and starve genuine referrers.

### Proof of Concept
Hardhat test plan:
1. Deploy `ReferralStorage`, `VLMGP`/`MGP` mock, and `MasterMagpie` mock; fund `ReferralStorage` with a fixed MGP balance (e.g., 1000 MGP).
2. From address A, call `registerCode(codeA)`.
3. From address B (different EOA, same test signer set representing "attacker"), call `useCode(codeA)` — assert it succeeds (no `Circled` revert since `codeOwners[codeA] != B`).
4. Simulate `MasterMagpie` calling `trigger(B, amount)` for a large `amount` repeatedly (or via multiple B-like addresses) until `userInfos[A].rewardAmount + userInfos[B].rewardAmount + ... > actual MGP balance`.
5. Have A and B call `claimReward()`; assert that a later, honest referrer/referee (address C with a genuine distinct referral) cannot successfully call `claimReward()` because `MGP.safeTransfer` reverts due to insufficient balance — demonstrating the pool has been drained by the self-referral pair before legitimate claims occur.
6. Assert `tiers[tierId].rewardPercentage + _calBoosted(A)` sums correctly against `DENOMINATOR` per referral event (confirming the split math is not itself broken, only the identity assumption behind it), while the net effect is A+B collectively receive `refererAmount + refereeAmount` funded from a shared, undercollateralized pool.

    function trigger(address _referee, uint256 _amount) external _onlyMasterMagpie {
        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
