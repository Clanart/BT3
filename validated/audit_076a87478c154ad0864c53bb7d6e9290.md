### Title
Payout OP_RETURN operator attribution is not covered by the user's `SinglePlusAnyoneCanPay` signature, letting an unprivileged party hijack reimbursement credit for a withdrawal it never funded - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The user's withdrawal-authorization signature for the operator payout transaction is required to use `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) , which under BIP-341/342 only commits to the single input being spent and the output at the same index. The payout tx has three outputs — user payout (index 0), CPFP anchor, and an OP_RETURN carrying the fronting operator's x-only pubkey [2](#0-1) . Because `SIGHASH_SINGLE|ANYONECANPAY` only binds output 0, the OP_RETURN output (and any other outputs/inputs) is unsigned and freely malleable by anyone who obtains the user's signature.

### Finding Description
`create_payout_txhandler` builds the payout transaction with the withdrawal UTXO as the sole signed input (key-spend, single signature) and appends an OP_RETURN output that records `operator_xonly_pk`, described in the docstring as "the operator's x-only pubkey that fronts the peg-out" [3](#0-2) . The user's signature is verified only against `SinglePlusAnyoneCanPay` sighash [4](#0-3) [5](#0-4) , and the proto/RPC documentation explicitly states this sighash type is expected [6](#0-5) .

Under this sighash type, the produced signature is a valid, standalone token that authorizes spending the withdrawal UTXO to a fixed output-0 (amount+script), but places **no constraint whatsoever on the OP_RETURN output that attributes credit to an operator**, nor on which additional inputs/fee structure accompany the transaction. Once such a payout transaction (or just the bare signature, e.g. relayed via gRPC to multiple operators, or observed in the mempool once the intended operator broadcasts it) becomes visible, any party who can reconstruct the transaction with the *same* signed output 0 can substitute an arbitrary OP_RETURN operator pubkey — including their own, or an unrelated honest operator's — and attach it to a competing transaction they get confirmed instead (via better fee/CPFP on the anchor output, which itself is unsigned).

Downstream, this OP_RETURN value is trusted as ground truth for "who fronted the payout": `update_finalized_payouts` parses it directly from the confirmed on-chain transaction and stores it as `payout_payer_operator_xonly_pk` [7](#0-6) . `PayoutCheckerTask`/`handle_finalized_payout` then look up unhandled payouts *by that stored operator key* and proceed to build and sign a kickoff so that operator can claim reimbursement from the vault [8](#0-7) [9](#0-8) . Verifiers independently validate a kickoff's legitimacy by comparing `kickoff_data.operator_xonly_pk` against this same DB-derived `payout_payer_operator_xonly_pk` [10](#0-9) .

The binding that should hold is:
`operator credited for reimbursement == operator whose own capital actually delivered/funded output 0`

Because the OP_RETURN is unauthenticated by the only signature present, an attacker can break this equality: confirm a transaction that still correctly pays the withdrawing user (satisfying the signed output 0) while attributing the fronting credit to an arbitrary registered operator xonly-pubkey of the attacker's choosing, without that operator's involvement or consent.

### Impact Explanation
This directly breaks the "operator credited versus the party that paid" custody binding called out as Critical impact:
- An attacker (unprivileged, no signing role) can cause an **honest, uninvolved operator to be attributed as the payer** for a withdrawal it never fronted. That operator's automation (`PayoutCheckerTask`) will then autonomously spend one of its unused kickoff connectors and initiate a real on-chain kickoff/reimbursement claim for a payout it did not make, consuming that operator's kickoff slot and eventually attempting to draw reimbursement from the vault for money it never sent to the user.
- Alternatively, an attacker who is itself a registered operator can hijack the OP_RETURN to credit itself for a payout actually intended for/paid out under another operator's flow, obtaining reimbursement entitlement for a withdrawal payment for which it fronted no capital (matching the impact category "operator reimbursed for a payout it never funded").
- Because the withdrawal UTXO/output-0 payment is unaffected, the user is not harmed and the attack is invisible until reimbursement/verification stages, at which point it manifests as misattributed vault reimbursement.

### Likelihood Explanation
The signature is explicitly required and documented to be `SinglePlusAnyoneCanPay` (comments in `WithdrawParams` proto and enforcement in `parse_withdrawal_sig_params`) [11](#0-10) , so this is not a misconfiguration — it is the intended, documented signing scheme. Any party who can observe a submitted/broadcast payout transaction (mempool visibility, or via the `Withdraw` aggregator RPC which fans the same `WithdrawParamsWithSig` out to multiple operator clients [12](#0-11) ) obtains everything needed to reconstruct a substitute transaction with a different OP_RETURN. No privileged role, key compromise, or majority stake is required — only network-level transaction observation and standard fee-bumping capability, which is well within an unprivileged attacker's reach.

### Recommendation
Bind the operator-attribution OP_RETURN to the same signature that authorizes the withdrawal spend, e.g., by requiring/verifying `TapSighashType::All` (or `SinglePlusAnyoneCanPay` is dropped in favor of a scheme that commits to all outputs), or by having the operator co-sign/commit to the specific OP_RETURN value as part of a covenant, so that no unsigned output can alter who receives reimbursement credit. At minimum, the protocol should require the user's off-chain authorization to be scoped per-operator (i.e., signed once specifically for the intended operator, non-transferable), and reject on-chain confirmations whose OP_RETURN operator key wasn't part of what was actually authorized/witnessed off-chain.

### Proof of Concept
1. User signs a `SinglePlusAnyoneCanPay` signature over the withdrawal UTXO and gives it (via the `Withdraw`/`InternalWithdraw` RPC flow) to operator O1, targeting output 0 = (amount, user's script pubkey).
2. O1 (or the aggregator, per `withdraw` at `core/src/rpc/aggregator.rs:1812`) constructs and broadcasts `create_payout_txhandler(input_utxo, output_txout, O1_pubkey, user_sig, network)`, with OP_RETURN = O1's xonly pubkey.
3. Attacker (unprivileged) observes this transaction/signature (e.g., in mempool, or because the same signed `WithdrawParamsWithSig` was broadcast to all operators per the aggregator's fan-out) and constructs a new transaction spending the same withdrawal UTXO with the identical `user_sig`/output 0, but OP_RETURN = attacker-chosen operator xonly pubkey (their own, or a targeted honest operator's), and gets it confirmed via a higher-fee CPFP spend of the (unsigned) anchor output before O1's version.
4. `update_finalized_payouts` parses the confirmed transaction's OP_RETURN and stores the attacker-chosen pubkey as `payout_payer_operator_xonly_pk` [7](#0-6) .
5. That operator's `PayoutCheckerTask` finds this "unhandled payout" attributed to them and calls `handle_finalized_payout`, initiating a real kickoff to claim vault reimbursement for a payout they never funded [8](#0-7) , while verifiers' `is_kickoff_malicious` check passes because it only compares against the same (attacker-controlled) DB value [10](#0-9) .

/// Creates a [`TxHandler`] for the `payout_tx`.
///
/// This transaction is sent by the operator to front a peg-out, after which operator will send a kickoff transaction to get reimbursed.
///
/// # Inputs
/// 1. UTXO: User's withdrawal input (committed in Citrea side, with the signature given to operators off-chain)
///
/// # Outputs
/// 1. User payout output
/// 2. OP_RETURN output (with operators x-only pubkey that fronts the peg-out)
///
/// # Arguments
/// * `input_utxo` - The input UTXO for the payout, committed in Citrea side, with the signature given to operators off-chain.
/// * `output_txout` - The output TxOut for the user payout.
/// * `operator_xonly_pk` - The operator's x-only public key that fronts the peg-out.
/// * `user_sig` - The user's signature for the payout, given to operators off-chain.
/// * `network` - The Bitcoin network.
///
/// # Returns
/// A [`TxHandler`] for the payout transaction, or a [`BridgeError`] if construction fails.
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
