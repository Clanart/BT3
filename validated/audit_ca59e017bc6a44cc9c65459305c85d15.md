## Title
Deep-link `branch` parameter bypasses ref-name validation via leading dash, enabling git argument injection - (File: `app/src/lib/sanitize-ref-name.ts`, `app/src/lib/parse-app-url.ts`)

## Summary
The Sherlock bug is a class of "guard exists but covers less than what the consumer actually needs" — `EverclearBridge.sendMsg` approves `params.amount` but the `FeeAdapter` pulls `amount + fee`, so the guard (the approval) silently fails to cover the real requirement. The Desktop analog is `testForInvalidChars` in `app/src/lib/sanitize-ref-name.ts`, which is used as the sole gate on the `branch` query parameter of an attacker-controlled deep link (`x-github-client://openRepo/...&branch=...`) in `app/src/lib/parse-app-url.ts`, but the regex it uses does not reject a leading `-`, even though a leading `.` is explicitly rejected. That "approved" (validated) value is then passed on to the git `checkout` invocation as a bare CLI token, where the intended protection (the guard) doesn't cover the real requirement of git's argument parser: any token starting with `-` is interpreted as an option regardless of position.

## Finding Description
`parseAppURL` in [1](#0-0)  extracts `branch` from the URL query string of an `openrepo` deep link and validates it only with:

```
if (branch != null && testForInvalidChars(branch)) {
  return unknown
}
```

`testForInvalidChars` is defined in [2](#0-1)  using the regex `/[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g`. This regex explicitly guards against a *leading dot* (`^\.`) but has no equivalent guard against a *leading dash*. A branch value like `--upload-pack=/tmp/evil.sh` or `-o` passes this validation untouched.

This validated `branch` is then forwarded through `IOpenRepositoryFromURLAction.branch` to `Dispatcher.openRepositoryFromUrl` / `openBranchNameFromUrl`, which calls `this.checkoutLocalBranch(repository, branchName)` with the raw string, as seen in [3](#0-2) . Eventually the branch name is spliced into the argument array for `git checkout` in `getBranchCheckoutArgs`, which places the branch name *before* the `--` separator: [4](#0-3) . Because `--` only stops option parsing for arguments that come *after* it, a branch string beginning with `-` is still interpreted as a git option, not as a literal ref name — the same class of guard/requirement mismatch as the Sherlock bug (the safeguard was sized/scoped incorrectly relative to what the downstream consumer actually requires).

## Impact Explanation
If the string reaches `git checkout` as a leading argument, it enables git argument/option injection. Depending on which option is smuggled, this can range from unexpected repository state changes to more serious outcomes (e.g., options that make git read arbitrary config or template paths). This matches the requested impact classes: "attacker controls ... a link or deep link the user clicks" and "silent corruption of what the user commits / [state]", potentially escalating toward file writes outside the intended scope.

## Likelihood Explanation
The `branch` parameter originates entirely from an external, attacker-supplied URL (`x-github-client://openRepo/<url>?branch=...`) that only requires the victim to click a link — no local access, admin rights, or pre-existing malware needed. The validation gap is a straightforward regex omission (missing `^-` equivalent to the existing `^\.` check), so crafting a bypassing payload is trivial. The main uncertainty is whether `Dispatcher.checkoutLocalBranch` (not available for inspection in this pass) performs an additional existence check against real branches before invoking `git checkout`, which could neutralize the injection by refusing to proceed for a non-existent ref. I was unable to confirm the internals of `checkoutLocalBranch` within the available context/index, so this should be verified before treating the issue as confirmed end-to-end exploitable.

## Recommendation
Extend `invalidCharacterRegex` (or add a dedicated check) in `app/src/lib/sanitize-ref-name.ts` to reject ref names beginning with `-`, mirroring the existing `^\.` guard, and/or ensure every place that turns a user/URL-supplied ref name into a git CLI argument (e.g., `getBranchCheckoutArgs` in `app/src/lib/git/checkout.ts`) inserts `--` *before* the ref name (or otherwise defends against option-like arguments) rather than only after it.

## Proof of Concept
1. Attacker crafts a deep link: `x-github-client://openRepo/https://github.com/some/repo?branch=--upload-pack%3D%2Ftmp%2Fevil.sh`
2. Victim clicks the link; `parseAppURL` extracts `branch = "--upload-pack=/tmp/evil.sh"`.
3. `testForInvalidChars` returns `false` (no match) because the regex does not flag a leading `-`.
4. `openBranchNameFromUrl` clones/opens the repo and calls `checkoutLocalBranch(repository, "--upload-pack=/tmp/evil.sh")`.
5. If this string is passed unchecked into the `git checkout` argument array as shown in `getBranchCheckoutArgs`, git parses it as an option rather than a ref name, since it appears before the `--` terminator.

Note: step 4→5 assumes `checkoutLocalBranch` does not otherwise validate the branch against real repository refs before calling git; I could not verify that function's implementation in this session, so confirm this before treating the chain as fully exploitable end-to-end.

```typescript
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```
