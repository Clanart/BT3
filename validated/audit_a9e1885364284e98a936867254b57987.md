### Title
Unsanitized access to CREATE_COIN condition fields in NFT transfer parsing can crash wallet sync on a malicious NFT spend - (File: `chia/wallet/nft_wallet/nft_puzzle_utils.py`)

### Summary
`get_metadata_and_phs()` in `chia/wallet/nft_wallet/nft_puzzle_utils.py` iterates over CLVM conditions output by an NFT's inner puzzle and, for a `CREATE_COIN` (opcode `51`) condition, unconditionally does `condition.rest().rest().first()` after only checking `condition.list_len() < 2`. This mirrors the Fort CVE-2024-45236 pattern: code accesses a nested element of a CLVM/ASN.1-like structure without verifying the structure actually contains that many elements, so an attacker-crafted, minimally-sized value can trigger an exception deep in element access.

The guard `condition.list_len() < 2` only ensures the condition has an opcode and one argument. A standard `CREATE_COIN` condition requires 3 elements `(51 puzzle_hash amount [memo...])`, but the code proceeds to call `.rest().rest().first()` regardless — i.e., it reaches for the third element of a list that could have only two (or, depending on `list_len()` semantics, could be an atom/nil after two `.rest()` calls). This is the same bug class as the Fort issue: the code trusts that a signed/attacker-influenced structure has a minimum shape and indexes into it without validating length first, so a crafted, undersized input causes an unhandled exception during element access.

The input this function processes — the output of `unft.p2_puzzle.run(...)` against the inner solution of an NFT coin spend — is fully attacker-controlled: any party can create/spend an NFT coin (including in offer/trade flows and DID/ownership transfer flows) with an inner puzzle that emits a truncated `CREATE_COIN` condition (e.g., `(51 puzzle_hash)` with no amount). Because NFT syncing is triggered automatically by a wallet observing a coin-state update for a tracked/owned NFT coin (via `nft_wallet.py`/`wallet_state_manager.py`, which call this same code path when processing incoming NFT spends), an attacker does not need direct RPC access to the victim wallet — they only need to get such a spend accepted on-chain (e.g., transferring an NFT to the victim, or spending an NFT the victim already tracks/co-observes, such as in an offer negotiation) for the victim's wallet to run this parsing code and crash while syncing.

### Impact Explanation
A malformed/truncated `CREATE_COIN` condition from an untrusted NFT inner puzzle causes an unhandled exception in `get_metadata_and_phs()`. Because this function is invoked during NFT coin-state syncing in the wallet (from `nft_wallet.py`), an unhandled exception here can abort processing of that wallet sync callback, denying the victim wallet's ability to correctly track/update NFT ownership and metadata for the affected coin, and potentially the batch of coin updates being processed. This is a spend-triggered wallet-side processing halt for a specific, attacker-reachable code path (NFT ownership/metadata update parsing) — a Data/Availability-type impact rather than fund loss, consistent with the "spend-triggered transaction-processing halt" impact category the reviewers are scoped to accept.

### Likelihood Explanation
Likelihood is fairly high given the required action is simply broadcasting/accepting a coin spend that a normal user's wallet will subsequently sync (e.g., completing an NFT transfer to the victim, or being a counterparty in an NFT trade). No privileged position, no malicious peer/node role, and no key compromise is needed — only crafting the inner puzzle solution to emit a `CREATE_COIN` condition with fewer than 3 arguments while still passing the `list_len() < 2` guard.

### Recommendation
In `get_metadata_and_phs()` (and any similarly structured condition-parsing helpers in the NFT/DID/offer code paths), validate that a `CREATE_COIN` condition has at least 3 program elements (`condition.list_len() >= 3`) before calling `.rest().rest().first()`, and skip/ignore conditions that do not meet this minimum shape instead of assuming well-formedness. Apply the same length-check discipline anywhere else in the wallet puzzle drivers that reach multiple levels into a CLVM condition (`.at("rrf")`, `.rest().rest().first()`, etc.) based on attacker-supplied inner-puzzle output, wrapping parsing in defensive length checks or try/except around syncing so a single malformed NFT spend cannot abort broader wallet sync processing.

### Proof of Concept
1. Attacker mints/curries an NFT ownership-layer inner puzzle (or crafts an NFT transfer solution) such that running the p2 inner puzzle against its solution yields a condition list containing `(51 <puzzle_hash>)` — i.e., opcode `51` with only one argument (no amount), which still satisfies `list_len() < 2` being false (list_len == 2) and thus is not skipped.
2. Attacker sends/transfers this NFT coin (or otherwise causes it to be spent) so that a victim wallet tracking the NFT (e.g., as recipient, DID owner, or offer counterparty) observes the coin spend during sync.
3. The wallet's NFT sync path calls `get_metadata_and_phs()` on the new coin's solution; upon reaching `condition_code == 51`, `condition.rest().rest().first()` is invoked on a program that lacks a third element, raising an exception (e.g., `EvalError`/`ValueError` from the underlying CLVM `Program` implementation) that is not caught by callers in `nft_wallet.py`, aborting that portion of wallet-state-manager sync processing.

def get_metadata_and_phs(unft: UncurriedNFT, solution: SerializedProgram) -> tuple[Program, bytes32]:
    conditions = unft.p2_puzzle.run(unft.get_innermost_solution(Program.from_serialized(solution)))
    metadata = unft.metadata
    puzhash_for_derivation: bytes32 | None = None
    for condition in conditions.as_iter():
        if condition.list_len() < 2:
            # invalid condition
            continue
        condition_code = condition.first().as_int()
        log.debug("Checking condition code: %r", condition_code)
        if condition_code == -24:
            # metadata update
            metadata = update_metadata(metadata, condition)
            metadata = Program.to(metadata)
        elif condition_code == 51:
            atom = condition.rest().rest().first().as_int()

            if atom == 1:
                # destination puzhash
                if puzhash_for_derivation is not None:
                    # ignore duplicated create coin conditions
                    continue
                memo = bytes32(condition.at("rrrff").as_atom())
                puzhash_for_derivation = memo
                log.debug("Got back puzhash from solution: %s", puzhash_for_derivation)
    assert puzhash_for_derivation
    return metadata, puzhash_for_derivation
