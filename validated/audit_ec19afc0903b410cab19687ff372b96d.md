### Title
`validate_non_embedded_session` skips offline-token liveness check via attacker-controlled `embedded=1` query param, letting a revoked session be treated as valid - (File: `app/controllers/concerns/shopify_app/ensure_installed.rb`)

### Summary
`validate_non_embedded_session` decides whether to call the Admin API to verify the cached offline token is still valid based solely on `loaded_directly_from_admin?`, which is derived only from `ShopifyApp.configuration.embedded_app?` and the request query parameter `params[:embedded]`. Since `params[:embedded]` is fully attacker-controlled and unauthenticated, any request can set `embedded=1` to bypass the liveness check, so a revoked/uninstalled shop's session set by `check_shop_known` is never re-validated.

### Finding Description
`before_action :check_shop_known` loads `@shop = installed_shop_session` from `SessionRepository` purely by the sanitized `shop` param [1](#0-0) . The subsequent `before_action :validate_non_embedded_session` is supposed to catch the case where the stored offline access token has since been revoked by Shopify (uninstall/re-auth), by calling `client.get(path: "shop")` and redirecting to `shop_login` on a 401 [2](#0-1) .

However, this API call is skipped entirely when `loaded_directly_from_admin?` returns true: [3](#0-2) 
This method only checks `ShopifyApp.configuration.embedded_app?` (an app-wide static config, not attacker-influenced) and `params[:embedded] == "1"` — a raw, unsigned, unauthenticated query parameter that any HTTP client can set on any GET request. There is no HMAC, session-token/JWT verification, or Referer check involved (contrary to the question's premise about "Referer" — the actual code path only inspects `params[:embedded]`, which is even easier to forge).

Exploit flow:
1. Shop `victim.myshopify.com` installs the app; app stores an offline token.
2. Merchant/attacker uninstalls the app or otherwise causes Shopify to revoke the offline token (this would normally cause `client.get(path: "shop")` to 401).
3. Attacker (or anyone, including the uninstalling merchant re-triggering old bookmarked links, or any unauthenticated caller who knows/guesses the shop domain) sends `GET /some_ensure_installed_route?shop=victim.myshopify.com&embedded=1`.
4. `check_shop_known` still finds and caches the stale `@shop` session (SessionRepository still has it, since no explicit revocation cleanup happens on the app side).
5. `validate_non_embedded_session` calls `loaded_directly_from_admin?` → `true` (since `embedded_app?` is true for the app and `params[:embedded]=="1"`), returns immediately without calling the Admin API.
6. The revoked session is treated as valid for the rest of the request, and the controller action executes using `@shop`/`installed_shop_session`.

This bypasses the only liveness/re-validation check present in this concern; there is no other check (ID token verification, HMAC, CSRF) in `EnsureInstalled`'s embedded branch that would independently catch a revoked offline token, since `EnsureInstalled` (as opposed to `EnsureHasSession`/`TokenExchange`) is the legacy, non-`use_new_embedded_auth_strategy` path guarding controllers directly with an offline session.

### Impact Explanation
Concrete impact: a shop whose Shopify install/offline access has been revoked continues to be treated by the app as "installed" and "session-valid," allowing controller actions gated by `EnsureInstalled` to execute with a stale/revoked session for the remainder of the request (and any code path caching `@shop`/`installed_shop_session` for that request). This corresponds to the Shopify HackerOne impact class of "Improper authentication/session validation leading to continued unauthorized use of a revoked authorization" — a stale-session/authorization-bypass issue rather than direct data exfiltration, since actual API calls made using the stale token would themselves fail (return 401) once actually invoked by application code downstream, limiting practical severity to bypassing the "redirect to reinstall" UX/guard rather than granting the attacker actual access to shop data (because the underlying token is genuinely revoked at Shopify).

### Likelihood Explanation
Trivial and fully attacker-controlled: no secrets, tokens, or valid session are needed — just appending `embedded=1` to the query string of any route protected by `EnsureInstalled`. It only requires `ShopifyApp.configuration.embedded_app?` to be `true`, which is the default/common configuration for embedded Shopify apps using this legacy (non token-exchange) flow. Repeatable on every request.

### Recommendation
Do not rely on an unauthenticated request parameter as the sole gate for skipping the offline-token liveness check. Either always perform the `client.get(path: "shop")` liveness check (accepting the extra API call cost), or require a signed indicator of “loaded from Admin” such as a verified Shopify session token (JWT) / `id_token` check, or verify the request via HMAC before treating `embedded=1` as trustworthy. At minimum, apps using the legacy embedded flow should not skip revocation checks based solely on `params[:embedded]`.

### Proof of Concept
Extend the existing test suite pattern (`test/controllers/concerns/ensure_installed_test.rb`) with:
```ruby
test "embedded=1 param bypasses liveness check even for a revoked session" do
  session = mock
  ShopifyApp::SessionRepository.stubs(:retrieve_shop_session_by_shopify_domain).returns(session)

  # Admin API client should NEVER be constructed/called because embedded=1 causes early return
  ShopifyAPI::Clients::Rest::Admin.expects(:new).never

  get :index, params: { shop: "shop1.myshopify.com", embedded: "1" }

  # Expected (secure) behavior would be a redirect to shop_login due to revoked token,
  # but actual behavior is:
  assert_response :ok
end
```
This mirrors the existing test "does not perform a session validation check if coming from an embedded" [4](#0-3) , demonstrating that simply supplying `embedded=1` — with no signature or authentication — is sufficient to skip the check that would otherwise redirect a revoked/uninstalled shop to `shop_login`, as shown by the 401 test at [5](#0-4) .

    def validate_non_embedded_session
      return if loaded_directly_from_admin?

      client = ShopifyAPI::Clients::Rest::Admin.new(session: installed_shop_session)
      client.get(path: "shop")
    rescue ShopifyAPI::Errors::HttpResponseError => error
      ShopifyApp::Logger.info("Shop offline session no longer valid. Redirecting to OAuth install")
      redirect_to(shop_login) if error.code == 401

    end
