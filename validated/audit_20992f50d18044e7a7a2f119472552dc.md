### Title
Reward pool `totalStaked()` uses raw `balanceOf(operator)` instead of internally tracked stake total, allowing donation-based dilution/permanent freezing of reward tokens - (File: rewards/BaseRewardPool.sol / rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPool` (and `BaseRewardPoolV2`) compute the reward-per-token denominator from the **raw token balance** of the `MasterMagpie` operator contract, while each user's individual share is computed from a **separately, internally tracked** value (`MasterMagpie.stakingInfo`). Because these two numbers can be desynchronized by a plain, unprivileged ERC20 transfer directly to the operator, an attacker can inflate the denominator used for reward-per-token accounting without increasing anyone's actual claimable share — permanently diluting/locking a portion of every subsequent reward distribution.

### Finding Description
`totalStaked()` in the reward pool contracts returns the staking token's `balanceOf` the `MasterMagpie` operator, not an internally tracked total: [1](#0-0) [2](#0-1) 

Per-user shares, however, are computed from `MasterMagpie.stakingInfo`, which is driven purely by the internal `UserInfo.amount`/`available` accounting updated in `_deposit`/`_withdraw`, and is *not* affected by raw token transfers into the contract: [3](#0-2) [4](#0-3) 

When new rewards are queued, the increment to `rewardPerTokenStored` is divided by `totalStaked()`: [5](#0-4) 

Because `totalStaked()` reads the operator's raw balance rather than the sum of tracked `user.amount` values, anyone can call `IERC20(stakingToken).transfer(masterMagpie, amount)` directly (bypassing `deposit`) to inflate `totalStaked()` without crediting any user. This mirrors the root cause pattern in the referenced report: relying on `balanceOf` for a weighting/denominator calculation that is meant to reflect internally-tracked accounting, which is trivially manipulable by direct token donation from any unprivileged wallet.

### Impact Explanation
Every subsequent `_queueNewRewardsWithoutTransfer` call computes `rewardPerTokenStored += amountReward * 1e18 / totalStaked()` using an artificially inflated `totalStaked()`. Since actual claimable amounts (`earned()`) are computed against the real, unmanipulated per-user tracked balances (which sum to less than the inflated `totalStaked()`), the sum of all users' claimable rewards will permanently fall short of the reward tokens actually transferred into the pool. The shortfall is not recoverable by any existing mechanism (it isn't re-queued like the zero-totalStaked case), resulting in a **permanent freezing/loss of a portion of legitimate stakers' yield** — proportional to how much the attacker donates relative to genuine stake.

### Likelihood Explanation
The attack requires only a plain ERC20 `transfer` to the `MasterMagpie` contract address by any unprivileged wallet holding the staking token — no special permissions, timing, or governance access needed. It can be executed at any time rewards are queued and stakers are actively earning, making it straightforward to trigger repeatedly.

### Recommendation
Track `totalStaked()` via an internal accumulator (e.g., a running total updated in `_deposit`/`_withdraw`) rather than reading the operator's raw `balanceOf`, so external token transfers cannot influence reward-per-token accounting. Alternatively, sweep/rescue any excess balance that doesn't correspond to tracked stake so it cannot silently corrupt the reward math.

### Proof of Concept
1. Users A and B each stake 1000 tokens of `stakingToken` in a pool via `MasterMagpie.deposit`, so `MasterMagpie`'s tracked total is 2000 and its real token balance is 2000 (`totalStaked() == 2000`).
2. Attacker (no special role) calls `stakingToken.transfer(masterMagpie, 8000)` directly, without calling `deposit`. `MasterMagpie`'s real balance becomes 10000, so `totalStaked()` (raw `balanceOf`) is now 10000, while tracked user amounts remain 2000 total.
3. A reward of 1000 reward tokens is queued: `rewardPerTokenStored += 1000 * 1e18 / 10000` instead of `/2000`, distributing only 20% of the intended reward-per-token rate.
4. Users A and B's `earned()` (computed from their real tracked `balanceOf`, 1000 each) will only reflect the diluted rate — the remaining ~80% of the 1000 reward tokens sit permanently unclaimable in the contract, since nothing corresponds to the attacker's "phantom" 8000 in tracked accounting.
