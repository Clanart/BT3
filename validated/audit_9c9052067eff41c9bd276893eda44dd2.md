### Title
A single sub-dust payment aborts construction of the entire withdrawal transaction, DoS-ing all pending payments - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Frankencoin `end()` bug class is "one failing transfer reverts the whole multi-party payout, with no pull-based fallback." In Serai, the same shape exists in `SignableTransaction::new`: all payments destined for a single Bitcoin transaction are validated up front, and if *any one* payment is below the dust threshold the constructor returns `TransactionError::DustPayment` and no transaction is built at all. Every other valid payment bundled into that transaction is blocked with no per-payment recovery path.

### Finding Description
`SignableTransaction::new` takes the full `payments: &[(ScriptBuf, u64)]` list for the transaction being constructed and rejects the entire transaction if a single payment is below `DUST` (546 sats):

```rust
// networks/bitcoin/src/wallet/send.rs:165-169
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

Because the `Err` is returned before `tx_outs`, fee calculation, and input selection are completed (`send.rs:175-255`), a single undersized payment poisons the whole batch — identical in shape to one reverting `zchf.transfer` aborting `end()` and locking all other parties' funds. Payments originate from user-initiated burns of `sriBTC`, so the payment amount is attacker/public-influenced input, not internal-only data.

Additionally, the scheduler's consumption loop stops at the first unsatisfiable payment (`processor/src/multisigs/scheduler/utxo.rs:399-409`), so a permanently un-fulfillable front-of-queue payment can compound the head-of-line DoS, though that scheduler code is outside the strict in-scope crates.

### Impact Explanation
An unprivileged user who can trigger a Bitcoin payment of less than 546 sats (e.g., burning a tiny amount of sriBTC) forces `SignableTransaction::new` to fail for the entire transaction. All other payments bundled into the same plan are never signed or broadcast. Like the Frankencoin report, the failure is atomic — there is no mechanism to skip just the offending output and still pay the rest — so one bad payment stalls the whole withdrawal batch. Depending on how the caller handles the `TransactionError` (I could not fully verify the error path in `processor/src/networks/bitcoin.rs`, which is out of scope), the plan may be retried indefinitely or the multisig's signing pipeline stalls, constituting a persistent DoS of withdrawals.

### Likelihood Explanation
Reachable whenever a payment under 546 sats enters the payments list for a Bitcoin plan — burns are permissionless user actions, so no privileged role or validator collusion is needed. Impact is a Medium DoS (temporary or persistent blocking of unrelated withdrawals), not fund theft, matching the severity profile of the source report.

### Recommendation
Filter or clamp dust payments before constructing the transaction rather than aborting the whole batch: drop sub-dust payments (crediting/refunding them or folding them into fees via documented policy) so remaining payments still proceed. Alternatively, catch per-payment failures and exclude only the offending output, providing a recovery path analogous to the recommended "pull funds later" mitigation.

### Proof of Concept
1. An attacker burns `sriBTC` for an amount that yields a payment below `DUST = 546` sats (`send.rs:32`).
2. The scheduler enqueues the payment alongside legitimate payments (`utxo.rs:340`) and pops it into `executing` for the next plan (`utxo.rs:399-403`).
3. `SignableTransaction::new` iterates all payments and hits `*amount < DUST` → `Err(TransactionError::DustPayment)` (`send.rs:165-168`).
4. The entire transaction is never constructed: no `tx_outs`, no `TransactionSignMachine`, no signature shares (`send.rs:321-395`). All bundled payments are blocked atomically — the same one-failure-fails-all pattern as `MintingHub.end()`.

Open uncertainty: whether `processor/src/networks/bitcoin.rs` drops the offending plan on `TransactionError` or retries it indefinitely could not be confirmed since that file is outside the indexed in-scope set; the in-scope defect — the all-or-nothing batch construction — is confirmed in `send.rs`.
