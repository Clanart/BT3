### Title
SignableTransaction omits the OP_RETURN data output from weight/fee calculation, producing underpriced transactions — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying user-supplied `data` to `tx_outs`, but computes the transaction weight/vbytes — and therefore `needed_fee` — via `calculate_weight_vbytes(tx_ins.len(), payments, None)`, where `payments` does not include the OP_RETURN output. The fee formula uses the wrong denominator/output set, analogous to the Surge fee-share bug: a derived quantity is computed from a value that excludes a term it must include, so the resulting fee is always less than intended and the change output retains more than it should.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- `tx_outs` is built from `payments` and then the OP_RETURN output is pushed at `send.rs:194-202`.
- The weight/vbytes used for `needed_fee` is computed at `send.rs:204` as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — passing `payments`, not `tx_outs`, so the data output's bytes are never counted.
- `needed_fee = fee_per_vbyte * vbytes` at `send.rs:206` therefore under-charges, and the `TooLowFee` minimum-relay check at `send.rs:211` is evaluated against this same underestimated vbytes, so it cannot catch the discrepancy.
- The change path repeats the same omission: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at `send.rs:225-226`, again without the OP_RETURN.
- The final transaction emitted at `send.rs:245-251` does include the OP_RETURN output, so the signed TX's real vsize is strictly larger than the vbytes used for fee computation.

The OP_RETURN `data` is attacker-controlled: it originates from untrusted in-instruction data associated with deposits/forwards, and is only bound by the `PushBytesBuf`/`TooMuchData` size checks, not by the fee computation.

### Impact Explanation
Every transaction carrying a data payload pays a lower fee rate than the caller/protocol specified via `fee_per_vbyte`, while the change output (or fee accounting) is computed as if the data output weighed nothing. For payloads approaching the pushdata limit the underestimate is meaningful. In the worst case the produced transaction's true fee rate falls below the mempool minimum relay fee despite passing the `TooLowFee` check, so the multisig-signed transaction is unbroadcastable and the inputs/plan are stuck — the signature still completes and spends the intended inputs, but the transaction cannot confirm. This is a concrete incorrect-formula bug (fee/share computed without accounting for all newly added outputs), reachable purely through public deposit data.

### Likelihood Explanation
Triggered whenever a non-`None` `data` payload is attached to a send — a routine protocol path for forwarded outputs carrying `InInstruction` data, which any depositor can cause to be set. Severity of outcome depends on how close the underestimated fee rate lands to the relay minimum; the formula error itself is unconditional and deterministic.

### Recommendation
Include the OP_RETURN output in the weight calculation. Either pass the full `tx_outs` into `calculate_weight_vbytes` (changing its signature to accept `&[TxOut]` or the data length), or add the OP_RETURN's serialized size to the computed weight before deriving `vbytes` and `needed_fee`. Apply the same fix to both call sites (the no-change estimate at `send.rs:204` and the with-change estimate at `send.rs:225-226`), and ideally compute weight once on the final `tx.output` set. Additionally, consider re-checking the real fee (`fee()` at `send.rs:138-141`) against the required minimum after construction.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, &payments, change, Some(data), fee_per_vbyte)` with `data` of length ~80 bytes.
2. Observe `needed_fee() == fee_per_vbyte * vbytes`, where `vbytes` excludes the OP_RETURN output because `calculate_weight_vbytes` is given `payments` (`send.rs:204`) while `tx_outs` — the actual outputs placed in the signed transaction (`send.rs:195-202`, `send.rs:250`) — contains an extra `TxOut` with the data-bearing `script_pubkey`.
3. `tx.fee()` (real fee, `send.rs:138-141`) equals `needed_fee`, but `tx.vsize()` of the produced `Transaction` exceeds `vbytes` by the OP_RETURN output's serialized size, so the effective fee rate is strictly below `fee_per_vbyte`. With `fee_per_vbyte` chosen at the minimum relay boundary, the resulting transaction is below `DEFAULT_MIN_RELAY_TX_FEE` per actual vbyte and is rejected by Bitcoin nodes.
