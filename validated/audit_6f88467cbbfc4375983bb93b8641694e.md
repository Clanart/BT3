## Title
Reachable exception via attacker-controlled commit identity string in `CommitIdentity.parseIdentity` — ([File: app/src/models/commit-identity.ts])

## Summary
The nimiq bug is a class of "attacker supplies data that violates an unstated invariant the code silently assumes, then the code calls an infallible unwrap/assert against that data." The closest verified analog in this Desktop codebase is `CommitIdentity.parseIdentity`, which throws a raw `Error` if a git author/committer identity string does not match a strict regex, and is fed directly with commit data coming from a cloned/fetched repository's log output.

## Finding Description
`getCommits()` in `app/src/lib/git/log.ts` requests `%an <%ae> %ad` / `%cn <%ce> %cd` formatted fields from `git log` and passes them unconditionally into `CommitIdentity.parseIdentity`: [1](#0-0) 

`parseIdentity` assumes the string always matches `NAME <EMAIL> DATE (+/-)HHMM` and throws if it doesn't, or if the parsed date is `NaN`: [2](#0-1) 

This is structurally the same defect shape as the nimiq issue: the code assumes a specific well-formed shape for attacker-influenced data (a commit's author/committer identity, which is fully attacker-controlled in any cloned/fetched repository — a user can craft a commit with arbitrary raw author/committer lines using low-level plumbing such as `git commit-tree` with a custom `GIT_AUTHOR_NAME`/`GIT_AUTHOR_DATE`, e.g. embedding a literal newline, omitting the timezone, or using non-ASCII control bytes that break the regex) and then calls a function that throws/"panics" instead of degrading gracefully, with no validation before the unwrap-equivalent.

Several call sites consume `getCommits`/`getCommit` without an intervening try/catch that is visible in the file itself, e.g. `app/src/lib/copilot-conflict-context.ts` and `app/src/lib/stores/notifications-store.ts` call these functions directly: [3](#0-2) [4](#0-3) 

By contrast, the main history-loading path in `GitStore` wraps `getCommits`/`getCommit` calls in `performFailableOperation`: [5](#0-4) [6](#0-5) 

**I was not able to locate and inspect the definition of `performFailableOperation` in the time available**, so I cannot confirm whether it swallows all exceptions (including those thrown synchronously inside the `.map()` callback in `getCommits`) or only catches process/exec-level failures. This is a real gap in my verification, and it matters: if `performFailableOperation` only wraps the `git()` exec call and not the subsequent synchronous `parse`/`.map()` step, then even the "protected" call sites in `git-store.ts` are exposed, since the throw happens inside the `.map()` callback in `getCommits`, which is *inside* the async function `performFailableOperation` awaits, so it would still be caught by any `try { await fn() } catch` pattern — but I could not verify this pattern is actually used.

## Impact Explanation
If the exception is not caught somewhere in the async chain, it surfaces as an unhandled promise rejection. In Electron, unhandled rejections in the renderer are non-fatal by default (they log to console) unless the app has configured `process.on('unhandledRejection')` to crash, but the practical impact is a broken feature: repository history, notifications, and Copilot conflict-context generation for the poisoned commit would fail every time it's accessed, degrading to a persistent, repeatable failure state whenever the user interacts with that repository (opens history, fetches, views a check-suite notification tied to that commit, etc.) — analogous to a repeatable reachable-assertion DoS, just realized as a JS exception rather than a native panic.

## Likelihood Explanation
Medium-low confidence without confirming the catch behavior. The attacker primitive (an unprivileged party crafting a commit with a malformed author/committer identity string in a repository the victim later clones or fetches) is realistic and matches the "attacker controls a cloned/fetched repository" criterion. However, I could not confirm from local code alone that this path is unguarded end-to-end — the presence of `performFailableOperation` around the two most commonly used call sites suggests the Desktop team already anticipated failures in this area, which weakens confidence that this is currently exploitable versus already mitigated.

## Recommendation
- Make `CommitIdentity.parseIdentity` non-throwing (return `null`/a sentinel identity) for the two call sites in `getCommits`, and have `getCommits` substitute a safe fallback identity instead of letting a single malformed commit take down history/notification loading for the whole repository.
- Explicitly wrap all remaining direct call sites of `getCommit`/`getCommits` (`copilot-conflict-context.ts`, `notifications-store.ts`) in `performFailableOperation` or an equivalent try/catch, so a single malformed commit degrades gracefully rather than raising an unhandled exception.

## Proof of Concept
Because I could not fully confirm the exception is unguarded through every call path, I cannot state with certainty this is exploitable as shipped; the following describes the mechanism to test rather than a confirmed working exploit:
1. Attacker creates a repository and uses `git commit-tree` with a `GIT_AUTHOR_NAME`/`GIT_AUTHOR_DATE` environment combination that produces an author line not matching `NAME <EMAIL> DATE (+/-)HHMM` (e.g., omit timezone offset or embed a raw `\0`/control character that survives the `-z`/`%x00` delimiter parsing in `git-delimiter-parser.ts` but breaks the identity regex).
2. Victim clones/fetches this repository into Desktop.
3. Desktop calls `getCommits` (directly via `copilot-conflict-context.ts`/`notifications-store.ts`, or indirectly via `GitStore`), which calls `CommitIdentity.parseIdentity` on the malformed string and throws.
4. Observe whether the throw is caught anywhere in the chain; if not, the corresponding feature (history view, notification, conflict context) fails/breaks whenever that commit is touched. [7](#0-6)

```typescript
  public static parseIdentity(identity: string): CommitIdentity {
    // See fmt_ident in ident.c:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L346
    //
    // Format is "NAME <EMAIL> DATE"
    //  Markus Olsson <j.markus.olsson@gmail.com> 1475670580 +0200
    //
    // Note that `git var` will strip any < and > from the name and email, see:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L396
    //
    // Note also that this expects a date formatted with the RAW option in git see:
    //  https://github.com/git/git/blob/35f6318d4/date.c#L191
    //
    const m = identity.match(/^(.*?) <(.*?)> (\d+) (\+|-)?(\d{2})(\d{2})/)
    if (!m) {
      throw new Error(`Couldn't parse identity ${identity}`)
    }

    const name = m[1]
    const email = m[2]
    // The date is specified as seconds from the epoch,
    // Date() expects milliseconds since the epoch.
    const date = new Date(parseInt(m[3], 10) * 1000)

    if (isNaN(date.valueOf())) {
      throw new Error(`Couldn't parse identity ${identity}, invalid date`)
    }
```
