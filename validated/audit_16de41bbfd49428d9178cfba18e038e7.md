### Title
WebSocket JSON-RPC transport bypasses HTTP-only method access controls (deny-list and legacy `sei_*` gating) - ([File: evmrpc/rpcstack.go])

### Summary
`evmrpc`'s HTTP JSON-RPC listener enforces two method-level access controls — a configurable per-method deny list and the `sei_*` legacy-API allowlist gate — but neither control is applied to the WebSocket JSON-RPC listener, which registers the exact same API namespaces. Any method an operator intends to block network-wide via `deny_list`, or any gated `sei_*` legacy method not enabled in `enabled_legacy_sei_apis`, remains fully callable by simply connecting over `ws://`/`wss://` instead of HTTP. This mirrors the GitLab class of bug: an access-control check bound to one transport (HTTP request path) is silently absent on an alternate transport (WebSocket) that reaches the identical server-side methods.

### Finding Description
`HTTPServer.EnableRPC` builds the HTTP JSON-RPC handler and applies two method-level gates before requests reach the inner `rpc.Server`:
- it calls `srv.RegisterDenyList(method)` for every entry in `config.DenyList`, and
- it wraps the handler with `wrapSeiLegacyHTTP(base, config.SeiLegacyAllowlist, ...)`, which centrally enforces `[evm].enabled_legacy_sei_apis` for `sei_*` methods. [1](#0-0) 

`HTTPServer.EnableWS`, by contrast, only calls `RegisterApis(apis, config.Modules, srv)` (a namespace-level allowlist) and wraps the resulting handler with `NewWSHandlerStack(srv.WebsocketHandler(config.Origins), config.JwtSecret)` — there is no `RegisterDenyList` call and no `wrapSeiLegacyHTTP`-equivalent gate anywhere in the WS path. [2](#0-1) 

This is not an oversight limited to a single call site — the `WsConfig` struct itself has no `DenyList` or `SeiLegacyAllowlist` field, unlike `HTTPConfig`, which carries both: [3](#0-2) 

Both listeners register the same underlying `rpc.API` set via `RegisterApis`, which only filters by `Namespace` against the configured `Modules` list — it performs no per-method filtering, so any method exposed to HTTP under a namespace is also exposed to WS under that namespace unless explicitly denied (HTTP-only) or gated (HTTP-only, `sei_*` only). [4](#0-3) 

The project's own test for the deny list (`TestHttpDenyList`) only exercises the HTTP path and confirms the deny-list mechanism exists solely to block specific methods over HTTP — with no corresponding WS test, since no WS enforcement exists to test. [5](#0-4) 

### Impact Explanation
`deny_list` and `enabled_legacy_sei_apis` are the two mechanisms sei-chain operators have to disable specific JSON-RPC methods on a running node without disabling an entire namespace (e.g., disabling a specific heavy/unsafe `debug_`/`eth_` method while keeping the rest of that namespace available, or keeping deprecated `sei_getCosmosTx`/`sei_getEVMAddress`/`sei_getSeiAddress` off by default). Because these gates are only wired into the HTTP handler stack and any node that also has `EnableWS` turned on (a standard, commonly-enabled EVM WebSocket JSON-RPC configuration) exposes the identical namespaces without them, an unprivileged public-RPC client can defeat the operator's intended method-level restriction simply by issuing the same JSON-RPC call over the WebSocket endpoint instead of HTTP. Depending on what an operator has deny-listed (e.g., resource-heavy trace/debug calls meant to protect node stability, per `evmrpc/AGENTS.md`'s discussion of tracer gating), this can result in denial-of-service against the RPC node or unauthorized use of a legacy/deprecated method path the operator explicitly turned off.

### Likelihood Explanation
High reachability: this requires no privileged access — any client capable of opening a WebSocket connection to a node's public EVM RPC endpoint (the default and encouraged configuration for `eth_subscribe`/log/newHeads support) can trivially invoke a denied method by simply targeting the WS listener with the identical JSON-RPC method name. No race condition, no special crafting beyond picking the transport is needed.

### Recommendation
Apply the same method-level access controls to the WebSocket listener as the HTTP listener in `HTTPServer.EnableWS` (`evmrpc/rpcstack.go`): call `srv.RegisterDenyList(method)` for `config.DenyList` entries, and add an equivalent `SeiLegacyAllowlist` field to `WsConfig` with the same `wrapSeiLegacyHTTP`-style enforcement (or a websocket-compatible equivalent) applied before dispatch. Add a `WsConfig`-based deny-list/legacy-gate test mirroring `TestHttpDenyList` to prevent regression.

### Proof of Concept
1. Start a node with EVM JSON-RPC and WebSocket both enabled, and configure `deny_list` (or leave `enabled_legacy_sei_apis` empty) to block a specific method, e.g. `sei_getCosmosTx` or any `debug_`/`eth_` method the operator disabled.
2. Confirm over HTTP that the method is rejected:
   `curl -d '{"jsonrpc":"2.0","id":1,"method":"sei_getCosmosTx","params":[...]}' http://<node>:8545` → HTTP-gated error (`errSeiLegacyNotEnabled` / deny-list `-32601`), per `wrapSeiLegacyHTTP`/`RegisterDenyList` enforcement in `EnableRPC`. [6](#0-5) 
3. Open a WebSocket connection to `ws://<node>:8546` and send the identical JSON-RPC request. Because `EnableWS` never registers a deny list and has no legacy allowlist gate, the call is dispatched normally to the same registered `Service` and succeeds. [7](#0-6)

// EnableWS turns on JSON-RPC over WebSocket on the server.
func (h *HTTPServer) EnableWS(apis []rpc.API, config WsConfig) error {
	h.mu.Lock()
	defer h.mu.Unlock()

	if h.wsAllowed() {
		return fmt.Errorf("JSON-RPC over WebSocket is already enabled")
	}
	// Create RPC server and handler.
	srv := rpc.NewServer()
	srv.SetBatchLimits(config.batchItemLimit, config.batchResponseSizeLimit)
	readLimit := effectiveMaxRequestBodyBytes(config.readLimit)
	srv.SetReadLimits(readLimit)
	// maxConcurrentRequestBytes is passed through raw; rpc.Server.recomputeWSConcurrentBudget
	// raises it to readLimit when smaller, matching
	// newRequestSizeLimiter's max(budget, maxBody) rule on the HTTP protocol.
	srv.SetWSConcurrentRequestBytes(config.maxConcurrentRequestBytes)
	srv.SetWSAdmissionTimeout(config.wsAdmissionTimeout)
	srv.SetWSAdmissionEventHook(func(reason string) {
		// Hook carries no request context, and the fork's own connCtx is context.Background() too.
		recordWSAdmissionRejected(context.Background(), reason)
	})
	logger.Info("Registering apis for evm websocket")
	if err := RegisterApis(apis, config.Modules, srv); err != nil {
		return err
	}
	h.WsConfig = config
	h.wsHandler.Store(&rpcHandler{
		Handler: NewWSHandlerStack(srv.WebsocketHandler(config.Origins), config.JwtSecret),
		server:  srv,
	})
	return nil
}

// RegisterApis checks the given modules' availability, generates an allowlist based on the allowed modules,
// and then registers all of the APIs exposed by the services.
func RegisterApis(apis []rpc.API, modules []string, srv *rpc.Server) error {
	if bad, available := checkModuleAvailability(modules, apis); len(bad) > 0 {
		logger.Error("Unavailable modules in HTTP API list", "unavailable", bad, "available", available)
	}
	// Generate the allow list based on the allowed modules
	allowList := make(map[string]bool)
	for _, module := range modules {
		allowList[module] = true
	}
	// Register all the APIs exposed by the services
	for _, api := range apis {
		if allowList[api.Namespace] || len(allowList) == 0 {
			if err := srv.RegisterName(api.Namespace, api.Service); err != nil {
				return err
			}
		}
	}
	return nil
}
