### Title
Daemon WebSocket message routing spoofs sender identity via unauthenticated `origin` field - ([File: chia/daemon/server.py])

### Summary
The local daemon (`chia/daemon/server.py`) relays JSON messages between registered service websockets based solely on the client-supplied `destination`/`origin` fields, without ever verifying that the sending websocket is actually registered under the `origin` it claims. Any local client able to open a websocket to the daemon can forge the `origin` field to impersonate a trusted service (e.g. `chia_full_node`, `wallet`) when pushing a message to another subscriber (e.g. `wallet_ui`), which is directly analogous to CVE-2024-34397 (GDBus signal spoofing where an unprivileged local peer on the shared bus can impersonate a trusted service to another subscriber).

### Finding Description
`WebSocketServer.handle_message()` treats any message whose `destination` is not `"daemon"` as pure forwarding traffic: [1](#0-0) 

The forwarded payload is the attacker-controlled JSON dict, serialized verbatim (`dict_to_json_str(message)`), including whatever `origin` value the sender chose — there is no check that the sending websocket is itself registered under `self.connections[origin]`.

`register_service()` allows any connected websocket to register under any arbitrary service name string, with no restriction tying a connection to a particular privileged service identity: [2](#0-1) 

Message construction/parsing in `chia/util/ws_message.py` confirms `origin` and `destination` are just free-form strings supplied by the sender, and `format_response()` blindly swaps them from the incoming message without any authentication step: [3](#0-2) 

Downstream consumers of relayed messages — RPC service loops (`RpcServer.connection`/`safe_handle` in `chia/rpc/rpc_server.py`), the wallet/full-node/GUI subscribers registered as `wallet_ui`, and `KeychainProxy`, which logs and processes responses keyed by `request['origin']` — implicitly trust that `origin` reflects the actual sending service, because in the legitimate flow only the real service would be registered under that name. Since `register_service` performs no authorization check on the requested name, and `handle_message` performs no origin-vs-registration cross-check when forwarding, any local process that can complete the daemon's mutual-TLS handshake (i.e., any local RPC caller sharing the daemon's private cert/key material, which every locally-installed Chia service and CLI tool does) can:
1. Register itself under an arbitrary or colliding service name, or simply omit registration and directly forge `origin`/`destination` on any message it sends.
2. Send a crafted message with `destination="wallet_ui"` (or any other real subscriber) and `origin="chia_full_node"`/`"chia_wallet"`, which the daemon will relay unmodified to every websocket registered as `wallet_ui`.
3. The receiving subscriber (a GUI, RPC bridge, or automation script) processes the message believing it originated from the trusted full node/wallet service, exactly mirroring the GDBus CVE's "spoofed signal wrongly interpreted as sent by the trusted system service" scenario.

### Impact Explanation
This is scoped under the "daemon/keychain/RPC authorization" reachable category. An unprivileged/local RPC caller can spoof push notifications (`state_changed`, `keyring_status_changed`, or arbitrary relayed commands/responses) as if they came from the trusted full-node or wallet service, causing another local client (e.g. wallet UI, automation, or any RPC bridge) to act on forged application state. Depending on what the receiving consumer does with `state_changed` payloads (e.g., balance/transaction/offer notifications), this can mislead a wallet-adjacent client into displaying or acting on forged coin/transaction state, satisfying the "coin-set divergence between honest [local] nodes" / unauthorized-state-influence bar for a Medium-severity local-authorization flaw.

### Likelihood Explanation
Any process capable of connecting to the daemon websocket (holding the shared private daemon TLS cert, as any local Chia CLI/service/GUI component does) can trivially construct and send a JSON message with forged `origin`/`destination` fields — no cryptographic proof of sender identity is required beyond the shared TLS handshake, and `register_service` places no restriction on which name a connection may claim. This requires no race condition or timing tricks, only a single crafted message.

### Recommendation
Bind message `origin` to the registered identity of the sending websocket rather than trusting the client-supplied field: in `handle_message()`, verify the sending `websocket` is a member of `self.connections[origin]` (or otherwise cryptographically attest identity) before relaying, and reject/rewrite `origin` for messages whose sender is not registered under the claimed name. Consider requiring `register_service` requests to include proof of the calling process/service identity (e.g., a per-service token minted by `Service.manage()` at start time) rather than an arbitrary string.

### Proof of Concept
1. Start the daemon and let the real wallet RPC service register under `chia_wallet` and a GUI subscriber register under `wallet_ui` (both via normal `register_service`).
2. From an unrelated local client with only the shared daemon TLS cert, open a websocket to the daemon and send, without ever registering as `chia_wallet`:
   ```json
   {"command":"state_changed","ack":false,"data":{"state":"coin_added"},"request_id":"...","destination":"wallet_ui","origin":"chia_wallet"}
   ```
3. `handle_message()` sees `destination="wallet_ui" != "daemon"`, finds `wallet_ui` in `self.connections`, and relays the message verbatim to the real `wallet_ui` websocket(s) — which observe `origin == "chia_wallet"` even though the message never touched the real wallet service, matching `chia/_tests/core/daemon/test_daemon.py` patterns that already assert `message["origin"]` is trusted as sender identity by receivers.

        self, websocket: WebSocketResponse, message: WsRpcMessage
    ) -> tuple[str, set[WebSocketResponse]] | None:
        """
        This function gets called when new message is received via websocket.
        """

        command = message["command"]
        destination = message["destination"]
        if destination != "daemon":
            if destination in self.connections:
                sockets = self.connections[destination]
                return dict_to_json_str(message), sockets

            return None

        service = request.get("service")
        if service is None:
            self.log.error("Service Name missing from request to 'register_service'")

def format_response(incoming_msg: WsRpcMessage, response_data: dict[str, Any]) -> str:
    """
    Formats the response into standard format.
    """
    response = {
        "command": incoming_msg.get("command", ""),
        "ack": True,
        "data": response_data,
        "request_id": incoming_msg.get("request_id", ""),
        "destination": incoming_msg.get("origin", ""),
        "origin": incoming_msg.get("destination", ""),
    }

    json_str = dict_to_json_str(response)
    return json_str


def create_payload(command: str, data: dict[str, Any], origin: str, destination: str) -> str:
    response = create_payload_dict(command, data, origin, destination)
    return dict_to_json_str(response)


def create_payload_dict(command: str, data: dict[str, Any] | None, origin: str, destination: str) -> WsRpcMessage:
    if data is None:
        data = {}

    return WsRpcMessage(
        command=command,
        ack=False,
        data=data,
        request_id=bytes32.secret().hex(),
        destination=destination,
        origin=origin,
    )
