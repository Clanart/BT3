## Analysis: Aptos `verify-package` never checks actual on-chain bytecode against the source it claims to verify

I traced the external report's core invariant — *"the mechanism that's supposed to prove/attest what's on-chain must actually check the thing users rely on, not just a self-reported side value"* — to Aptos's package publish/verification flow.

### Candidate paths considered
1. `code::publish_package` ownership/upgrade-policy checks — sound: uses `object::is_owner` / `signer::address_of` correctly, matches spec requirements in `code.spec.move`.
2. `object_code_deployment::upgrade`/`freeze_code_object` — sound: correctly checks `object::is_owner(code_object, publisher_address)` before generating the extending signer.
3. `native_request_publish` module-name/dependency enforcement in `aptos-move/framework/natives/src/code.rs` — sound: enforces `expected_modules` and `allowed_deps` against actual `CompiledModule` contents in `validate_publish_request` (`aptos-move/aptos-vm/src/aptos_vm.rs`).
4. **`aptos move verify-package` CLI command / `CachedPackageMetadata::verify`** — this is the strongest candidate: it never compares actual on-chain bytecode to the locally built bytecode.

### Root cause [1](#0-0) 

`VerifyPackage::execute` builds the package locally, fetches the on-chain `PackageMetadata` via `CachedPackageRegistry::create(client, self.account, false)` (bytecode fetch disabled), and calls `package.verify(&compiled_metadata)`. [2](#0-1) 

`verify()` only compares `name`, `deps`, `modules` (which store gzipped **source text**, not bytecode), `manifest`, `upgrade_policy`, `extension`, and `source_digest` (a hash of the *source*, per the doc comment in `code.move`: "constructed by first building the sha256 of each individual source... sorting them alphabetically, and sha256 them again"). At no point does it fetch or diff the actual `.mv` bytecode stored on-chain (`CachedPackageRegistry::get_bytecode`, only populated when `with_bytecode=true`, which `VerifyPackage` never requests). [3](#0-2) 

The on-chain `PackageMetadata.modules[].source` field is purely descriptive/attested data supplied by the publisher — the Move VM's `request_publish`/`request_publish_with_allowed_deps` natives and `validate_publish_request` never check that this source text actually compiles to the bytecode bundle being published; only module names and dependencies are cross-checked against the real `CompiledModule`s. [4](#0-3) 

### Impact
A publisher can submit honest-looking source text in `PackageMetadata.modules[].source` while the accompanying `code` (actual bytecode bundle) implements different, malicious logic. Since nothing links source metadata to the real bytecode on-chain, and `aptos move verify-package` never downloads/diffs bytecode, running `verify-package` against such an account reports **"Successfully verified source of package"** even though the deployed executable code differs from the verified source. Any user, auditor, or integrator relying on this CLI command's success as a source-code attestation is misled about what code is actually live — this is a direct mismatch between "verified bytes," package metadata, and committed module bytes reaching a trust decision, matching the Publish Impact Gate's third bullet.

### Likelihood
High from an exploitability standpoint (no privileged access needed — any account can publish arbitrary source-vs-bytecode combos since metadata authenticity toward bytecode is never enforced on-chain), though the actual damage depends on downstream consumers trusting `verify-package` output as a security signal.

### Recommendation
`verify-package` (and `CachedPackageMetadata::verify`) should additionally fetch the on-chain compiled module bytes (`get_account_module`) for every module and re-verify that these bytes match a fresh local compilation output (byte-for-byte, or via a bytecode hash), not merely metadata/source text equality. Alternatively, document prominently that `verify-package` only attests source-metadata self-consistency, not code identity, until bytecode verification is added. [5](#0-4) 

---

Note: this is a trust/attestation gap in an off-chain developer/auditor CLI tool (`aptos move verify-package`), not an on-chain unauthorized-publish, upgrade-authority, or write-set-mutation bug — on-chain ownership and compatibility invariants in `code.move` and `object_code_deployment.move` are correctly enforced. If the intended scope was strictly on-chain state-mutation bypasses, this finding would fall outside it; I'm flagging it because it's the only candidate with a concrete, provable "verification says X but reality is Y" gap analogous to the seed report.

        // First build the package locally to get the package metadata
        let build_options = BuildOptions {
            install_dir: self.move_options.output_dir.clone(),
            bytecode_version: fix_bytecode_version(
                self.move_options.bytecode_version,
                self.move_options.language_version,
            ),
            ..self.included_artifacts.build_options(&self.move_options)?
        };
        let w = self.env.writer();
        let pack = BuiltPackage::build_to(&w, self.move_options.get_package_path()?, build_options)
            .map_err(|e| CliError::MoveCompilationError(format!("{:#}", e)))?;
        let compiled_metadata = pack.extract_metadata()?;

        // Now pull the compiled package
        let client = self.rest_options.client(&self.profile_options)?;
        let registry = CachedPackageRegistry::create(client, self.account, false).await?;
        let package = registry
            .get_package(pack.name())
            .await
            .map_err(|s| CliError::CommandArgumentError(s.to_string()))?;

        // We can't check the arbitrary, because it could change on us
        if package.upgrade_policy() == UpgradePolicy::arbitrary() {
            return Err(CliError::CommandArgumentError(
                "A package with upgrade policy `arbitrary` cannot be downloaded \
                since it is not safe to depend on such packages."
                    .to_owned(),
            ));
        }

        // Verify that the source digest matches
        package.verify(&compiled_metadata)?;

        Ok("Successfully verified source of package")
    }

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
                package_metadata.upgrade_policy,
                self_metadata.upgrade_policy
            )
        } else if self_metadata.extension != package_metadata.extension {
            bail!(
                "Extensions doesn't match {:?} : {:?}",
                package_metadata.extension,
                self_metadata.extension
            )
        } else if self_metadata.source_digest != package_metadata.source_digest {
            bail!(
                "Source digests doesn't match {:?} : {:?}",
                package_metadata.source_digest,
                self_metadata.source_digest
            )
        }

        Ok(())
    }
