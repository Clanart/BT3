### Title
Missing minimum-value validation on `Kip71GasTarget` governance parameter allows division-by-zero panic in KIP-71 base fee calculation - (File: `params/kip71_config.go`)

### Summary
`Kip71BaseFeeDenominator` has a `FormatChecker` in `kaiax/gov/param.go` that rejects `0` (`v != 0`), and `params/kip71_config.go`'s `NextMagmaBlockBaseFee` even has a defensive fallback for a zero `BaseFeeDenominator`. However, `Kip71GasTarget` uses `noopFormatChecker` (no validation at all) and is not cross-checked in `checkConsistency` in `kaiax/gov/headergov/impl/header.go`. If governance votes `Kip71GasTarget` to `0`, `NextMagmaBlockBaseFee` performs `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`, which panics on `*big.Int` division by zero. This is the same bug class as the reported issue: a percentage/ratio-like governance parameter lacking a bounds/non-zero check, whose faulty value is only caught deep inside consensus-critical fee-calculation logic, causing a halt.

### Finding Description
`Kip71GasTarget` is defined with `FormatChecker: noopFormatChecker` in `kaiax/gov/param.go` (around lines 324-334), meaning any `uint64` value, including `0`, passes format validation for a governance vote. [1](#0-0) 

`checkConsistency` in `kaiax/gov/headergov/impl/header.go` only cross-validates `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` against each other; `Kip71GasTarget` falls into the default "no more checks" bucket alongside other params. [2](#0-1) 

The consumer of this parameter, `NextMagmaBlockBaseFee` in `params/kip71_config.go`, divides by `gasTarget` twice (in both the gas-used-above-target and below-target branches) without any zero check on `gasTarget` itself, unlike the explicit zero-guard that exists for `BaseFeeDenominator`: [3](#0-2) 

If `parentHeaderGasUsed != 0` (essentially any produced block) and `GasTarget == 0`, `parentGasUsed` will always be `> gasTarget`, hitting the branch `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` at line 102, which is a division by the zero big.Int — this panics in Go's `math/big`.

### Impact Explanation
`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is invoked on the base-fee-critical path for every block: in block validation (`blockchain/block_validator.go`), block assembly (`work/worker.go`), the tx pool (`blockchain/tx_pool.go`), and gas price estimation (`node/cn/gasprice/gasprice.go`, `feehistory.go`). A panic here on all nodes attempting to validate or produce the next block after the faulty `GasTarget=0` vote takes effect would halt block production/validation network-wide (chain halt), matching the "Vault halt" impact pattern of the original report — a governance-parameter misconfiguration with no bounds check causing the core pricing/consensus path to become permanently stuck (since KIP-71 parameters, once voted, are only updatable via further governance votes on a chain that can no longer produce blocks).

### Likelihood Explanation
Reaching this requires a single governance vote setting `Kip71GasTarget = 0` to be included and accepted by `checkConsistency`, which currently performs no validation preventing it (`noopFormatChecker` and no consistency check against zero or against `MaxBlockGasUsedForBaseFee`). Unlike a hostile external tx-sender action, this requires a governance vote to be accepted on-chain (via the governing node/council under the "single" or "none" governance mode) — the same trust assumption as the original Sherlock report ("Sherlock trust in admin set correct variable... impact is locked fund in case of lost admin key" or an operational error). Given the value is a plain governance parameter (in scope per the analog rules for "governance parameters"), and the resulting effect is a full chain halt rather than a benign no-op, this is a valid Medium-severity analog.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`) in `kaiax/gov/param.go` rejecting `0`, mirroring the existing `Kip71BaseFeeDenominator` check (`v != 0`). Additionally, add a defensive zero-guard for `gasTarget` inside `NextMagmaBlockBaseFee` in `params/kip71_config.go`, consistent with the existing fallback logic already present for `BaseFeeDenominator == 0`, to prevent a panic even if an invalid value slips through consensus validation.

### Proof of Concept
1. Governance votes to set `kip71.gastarget = 0` (a `PartialParamSet` value passed through `ParamSet.Set` / header vote, which is not blocked by `Kip71GasTarget`'s `noopFormatChecker` and not cross-checked in `checkConsistency`).
2. Once the vote takes effect at the target block, any subsequent block with `parentHeaderGasUsed > 0` triggers `NextMagmaBlockBaseFee`.
3. Because `gasTarget == 0`, `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)` is `> gasTarget`, taking the "gas used above target" branch.
4. `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` executes `big.Int.Div` with divisor `0`, which panics per Go's `math/big` documentation ("Div implements Euclidean division... panics if `m == 0`" for `Div`/`Mod`-style zero-denominator operations).
5. This panic occurs inside `VerifyMagmaHeader`/`NextMagmaBlockBaseFee`, called from block validation and block assembly paths (`blockchain/block_validator.go`, `work/worker.go`), halting block production/validation on every node processing that block height.
