### Title
DkgConfirmer re-executes `sign` on a cached FROST preprocess with no "consumed" flag, enabling nonce reuse and validator key recovery - (coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a deterministic FROST preprocess seed in `CachedPreprocesses` keyed only by `context` (e.g., `(b"DkgConfirmer", attempt)`). Every subsequent call — `preprocess()`, `share()`, and crucially `complete()` (which internally calls `share_internal` → `preprocess_internal` → `machine.sign` a second time) — rebuilds a signing machine from the *same* seed and therefore the *same* nonces. The code checks whether the cache entry exists *after the fact* only to decide whether to create it; it never marks the nonce as consumed or binds the cache to the message/preprocess-set actually signed — the exact "is it already terminating" check-too-late pattern. The header comment (lines 25–54) acknowledges that safety depends entirely on all later `sign` executions seeing identical inputs, and admits a missing check: the on-chain preprocesses are never verified against the presumed ones before shares are published.

### Finding Description
- `preprocess_internal` derives nonces deterministically: if `CachedPreprocesses::get(txn, &context)` is `None`, it creates a machine, stores `machine.cache()`; otherwise it decrypts the stored seed and calls `AlgorithmSignMachine::from_cache`, regenerating identical nonces (signing_protocol.rs:123–147).
- `share_internal` then calls `machine.sign(preprocesses, msg)` with those nonces (line 170).
- `DkgConfirmer::share` (line 304) is invoked from `generated_key_pair` (handle.rs:57–59), publishing a `DkgConfirmed` share on the public tributary.
- `DkgConfirmer::complete` (lines 312–327) re-executes `share_internal` — a second `sign` under the same cached nonce — to rebuild the machine for `complete_internal`.
- `generated_key_pair` unconditionally overwrites `DkgKeyPair::set`/`KeyToDkgAttempt::set` (handle.rs:54–55) with no guard against a second `GeneratedKeyPair` for the same attempt. If a second report carries a different `key_pair`, `set_keys_message` (and thus the FROST challenge message) differs while the nonce stays fixed — and the confirmation share is published publicly again.
- The file's own safety argument (lines 29–51) rests on "received nonce commitments (or the message) would have to be distinct and sign called again" being impossible — yet `sign` *is* called again by construction in `complete`, and the durable DB cache survives rebuilds, contradicting the claim that "upon any complete rebuild, we'd re-decide nonces."

### Impact Explanation
FROST/Schnorr nonce reuse across two distinct challenges yields `s₁ = k + e₁·x`, `s₂ = k + e₂·x` → `x = (s₁ − s₂)/(e₁ − e₂)`. Because `DkgConfirmed` shares are published on the tributary, any observer recovering two shares signed under context `(b"DkgConfirmer", attempt)` over differing `msg`/`preprocess` sets recovers that validator's MuSig secret key — the root-of-trust key used for `set_keys`. This is key share recovery, reachable without privileged access (the shares are public transaction data; the trigger is any duplicated `GeneratedKeyPair`/re-execution path, including rebuilds the comments already contemplate).

### Likelihood Explanation
Each of `share`, `complete`, and any repeated `generated_key_pair` is a distinct `sign` execution on the same nonce. No flag prevents or detects the second execution — the cache is only checked for existence, mirroring the upstream bug where the work item was scheduled before the terminating check. Divergent inputs arise if `DkgKeyPair` is overwritten between calls, `ConfirmationNonces`/`removed` state differs on re-execution, or a partial rebuild replays the protocol — none of which are guarded (the file's TODO at lines 53–54 concedes the preprocess-match check is unimplemented).

### Recommendation
Record a per-context "share produced for digest H(msg, preprocesses)" entry when `share_internal` first signs; on any subsequent `sign` for the same context, assert the digest matches and refuse (or return the previously produced share) rather than re-signing. Delete/invalidate `CachedPreprocesses` once the confirmation completes. Implement the TODO check: verify the accumulated on-chain preprocesses equal the machine's presumed preprocess before producing or publishing any share. Add a dedup guard in `generated_key_pair` so a second `GeneratedKeyPair` for the same attempt cannot overwrite `DkgKeyPair` or trigger a re-sign.

### Proof of Concept
1. During DKG attempt `N`, coordinator generates nonces via `dkg_confirmation_nonces` → `CachedPreprocesses` stores seed under `(b"DkgConfirmer", N)`.
2. Processor reports `GeneratedKeyPair` with `key_pair_A` → `share()` signs `set_keys_message(..., key_pair_A)` under nonce `k`; share `s₁` is published in a `DkgConfirmed` transaction.
3. A second `GeneratedKeyPair` arrives for the same attempt with `key_pair_B ≠ key_pair_A` (unconditional overwrite at handle.rs:54–55 permits this) → `share()` signs a *different* message under the same `k`; `s₂` is published.
4. Any observer computes `x = (s₁ − s₂) · (e₁ − e₂)⁻¹`, recovering the validator's secret key. The same reuse occurs silently inside `complete` (signing_protocol.rs:322) whenever its inputs diverge from those used at `share` time. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
