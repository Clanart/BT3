### Title
OP_RETURN data is omitted from fee and change calculations, causing underpriced signed transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output to `tx_outs`, but calculates both the no-change and with-change transaction weight using only `payments`. [1](#0-0) [2](#0-1)  The final signed transaction nevertheless contains the additional output. [3](#0-2) 

### Finding Description
When the `data` argument is supplied, `SignableTransaction::new` adds an `OP_RETURN` output before estimating the transaction's weight and virtual size. [1](#0-0)  However, `calculate_weight_vbytes` is called with `payments`, not `tx_outs`, so the `OP_RETURN` output is absent from the estimated transaction. [4](#0-3) [5](#0-4) 

The same omission occurs when calculating `fee_with_change`, meaning the change amount is derived from an understated fee. [2](#0-1)  `TransactionSignMachine::sign` then signs Taproot sighashes for the final transaction, including the omitted `OP_RETURN` output. [6](#0-5) 

### Impact Explanation
An unprivileged caller who can supply transaction data to `SignableTransaction::new` can cause the threshold wallet to sign a transaction whose actual fee rate is lower than the requested `fee_per_vbyte`. [7](#0-6) [8](#0-7)  Because the change output is calculated using the understated fee, the actual fee remains understated after change is added. [2](#0-1) 

For transactions intended to use the minimum relay fee rate, an up-to-80-byte `data` payload can make the signed transaction fail relay policy despite the constructor's `TooLowFee` check succeeding. [9](#0-8) [8](#0-7) 

### Likelihood Explanation
The bug is deterministic whenever `data` is present: the additional output is always excluded from both fee estimates. [1](#0-0) [2](#0-1)  The effect is largest with the maximum permitted 80-byte payload and a fee rate near the relay minimum. [9](#0-8) 

### Recommendation
Calculate weight and virtual size from the complete output list, including the `OP_RETURN` output. For example, pass `tx_outs` or an equivalent `payment` representation including the zero-value data output to `calculate_weight_vbytes`, both with and without change. [1](#0-0) [2](#0-1) 

### Proof of Concept
```rust
// Conceptual PoC for networks/bitcoin/src/wallet/send.rs

let tx = SignableTransaction::new(
    vec![input],
    &[(payment_script, 546)],
    Some(change_script),
    Some(vec![0xaa; 80]),
    1, // intended fee: 1 sat/vbyte
).unwrap();

// The OP_RETURN output is present in the transaction being signed.
assert_eq!(tx.transaction().output.len(), 3);

// The estimated fee was calculated without that output.
let needed = tx.needed_fee();
let actual_vsize = tx.transaction().vsize() as u64;

// The commitment/signature will commit to a fee rate below 1 sat/vbyte.
assert!(tx.fee() < actual_vsize);
assert_eq!(tx.fee(), needed);
```

The root cause is that `tx_outs` already contains the `OP_RETURN` output, while `calculate_weight_vbytes` is invoked with `payments`. [1](#0-0)
