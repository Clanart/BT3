### Title
Algorithmic-complexity DoS via attacker-controlled participant count in `ThresholdKeys::read` / `ThresholdKeys::new` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts a 2-byte `n` (and `t`) field from untrusted input and performs `n` point decompressions plus an O(t²) Lagrange interpolation before validating `t <= n` or bounding the parameter against any sane maximum. The cost is driven entirely by two attacker-chosen `u16` values, not by input length — the same bug class as CVE-2018-18898 (a length/count field controlling super-linear work).

### Finding Description
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:591-623) the deserializer reads `t`, `n`, and `i` as raw `u16`s, then:

- allocates `Vec::with_capacity(usize::from(n))` and calls `C::read_F` `n` times for `Interpolation::Constant` (lines 607-613),
- calls `C::read_G` — a full point decompression/validation — once per participant for `l in (1 ..= n)` (lines 620-623),

and only *after* all of that work calls `ThresholdParams::new(t, n, i)` and `ThresholdKeys::new` (lines 625-631). Inside `ThresholdKeys::new` (lines 376-378), `group_key` is computed as a sum over `t` participants, each term calling `interpolation.interpolation_factor(*i, &t)`. For `Interpolation::Lagrange` this evaluates a product over the `t`-element participant set, giving O(t²) field multiplications plus `t` scalar multiplications.

Because `t`/`n` are `u16`, a single call with `t = n = 65535` forces ~65k point decompressions during read, then ~4×10⁹ field multiplications plus 65k group scalar multiplications during `group_key` derivation — minutes of CPU pinned per call, with no bound tied to the actual byte length consumed and no cap like the 150-participant bound applied elsewhere in the codebase. Repeated calls amplify this trivially.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (explicitly an in-scope sink) can pin a victim CPU for minutes per call. In a deployment where threshold keys are deserialized from externally supplied data (key ceremony tooling, recovery shares, RPC-relayed key material), this is a remote denial of service against the processor/coordinator, stalling signing and scanning. Severity: Medium-High (availability loss only, no secret leakage).

### Likelihood Explanation
The attack requires only that the victim deserialize attacker-influenced `ThresholdKeys` bytes. The reader performs no sanity cap on `n` before the expensive loops, and `ThresholdParams::new` validation runs *after* the decompression loop and is followed by the O(t²) group-key computation — so even inputs that ultimately fail validation still burn the work. Any periodic endpoint or retry path accepting such bytes turns a trivial request into sustained CPU exhaustion.

### Recommendation
- Validate `t`, `n`, `i` (including an upper bound such as the protocol's 150-participant maximum) immediately after reading them, before any `read_F`/`read_G` loops.
- Reject `n` exceeding a protocol constant in `ThresholdKeys::read` rather than relying on `ThresholdParams::new`.
- Consider deferring `group_key` computation or bounding the interpolation work.

### Proof of Concept
```rust
use std::io;
use serai_dkg::{ThresholdKeys, Participant}; // crypto/dkg/src/lib.rs
use ciphersuite::Secp256k1;

// Crafted ThresholdKeys bytes with t = n = u16::MAX, i = 1, Lagrange interpolation.
// Curve ID must match C::ID; then u16 t, u16 n, u16 i, u8 interpolation tag.
let mut buf = vec![];
buf.extend((<Secp256k1 as ciphersuite::Ciphersuite>::ID.len() as u32).to_le_bytes());
buf.extend(<Secp256k1 as ciphersuite::Ciphersuite>::ID);
buf.extend(u16::MAX.to_le_bytes()); // t = 65535
buf.extend(u16::MAX.to_le_bytes()); // n = 65535
buf.extend(1u16.to_le_bytes());     // i = 1
buf.push(1);                        // Interpolation::Lagrange -> skips the n*read_F loop
buf.extend([1u8; 32]);              // secret_share scalar (non-canonical still costs a parse)
// reader.read_exact fails only *after* ThresholdParams check? No:
// the read_G loop needs n point bytes; even a truncated stream costs the
// with_capacity alloc + per-point reads until EOF, and supplying 65535 compressed
// points (~2.1 MB) yields 65535 decompressions then an O(t^2) Lagrange group_key
// derivation in ThresholdKeys::new before any participant-count bound is enforced.
buf.extend(vec![0x02; 33 * 65535]); // compressed-point-shaped filler
let res = ThresholdKeys::<Secp256k1>::read(&mut buf.as_slice()); // CPU pinned
```

Caveat: I could not fully verify whether an unprivileged network path delivers raw bytes directly into `ThresholdKeys::read` in the deployed processor (the call sites appear to be within `processor/src/multisigs/` DB restore paths). The complexity flaw itself in `crypto/dkg/src/lib.rs` is confirmed; the finding's severity depends on the reachability of that deserializer to untrusted input, which the rules' allowed-sink list treats as in-scope.
