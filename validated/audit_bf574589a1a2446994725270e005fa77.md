### Title
Reward-tier accumulator desync in `incentiveDeposit(_mode=2)` allows repeated double-bonus reward theft via mWomSV under-crediting - ([File: wombat/ArbWomUp3.sol])

### Summary
In `ArbWomUp3`, `mode=2` (the doubled-bonus path) computes the marginal MGP reward assuming the *entire* `_amount` will be added to the caller's `mWomSV.getUserTotalLocked()`, but `_deposit()` actually locks only half of `_amount` (`_amount/2`) into `mWomSV`, with the other half being converted/swapped instead. This creates a permanent gap between the tier baseline used for reward accounting (`_amountToConvert + getUserTotalLocked`) and the baseline actually reflected after the call (`getUserTotalLocked += _amount/2`), letting an attacker split conversions across multiple `mode=2` calls to get the same reward tier segment rewarded (and doubled) more than once.

### Finding Description
`incentiveDeposit` computes the reward before depositing: [1](#0-0) 
```
uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender, _mode == 2);
if (_mode == 2) rewardToSend = rewardToSend * 2;
_deposit(msg.sender, _convertRatio, _amount, _mode);
```

`getRewardAmount` (for `_lock == true`) projects the tier baseline as if the *full* `_amountToConvert` will be locked: [2](#0-1) 

But `_deposit` for `_mode == 2` only locks half the amount into `mWomSV`: [3](#0-2) 
```
uint256 toDeposit = _amount / 2;
...
IERC20(mWom).safeApprove(address(mWomSV), mWomBal);
ILocker(mWomSV).lockFor(mWomBal, _account); // mWomBal == toDeposit == _amount/2
```

`calDoubledCounted` (the "already-rewarded" baseline subtracted to prevent double counting) reads `mWomSV.getUserTotalLocked(_account)` — the *actual* locked balance, not the amount that was already used to compute a prior reward: [4](#0-3) 

Because only `_amount/2` (not `_amount`) is reflected in `getUserTotalLocked` after a `mode=2` call, the next call's `calDoubledCounted` baseline is *lower* than the tier range already paid out in the previous call. Concretely, with an empty starting position:
- Call 1, amount `a`: `accumulated = a + 0 = a`; reward is computed over range `[0, a]` and doubled. Actual locked afterward: `a/2`.
- Call 2, amount `a`: `accumulated = a + a/2 = 1.5a`; `calDoubledCounted` baseline is `a/2` (not `a`), so the marginal reward is computed over range `[a/2, 1.5a]`, which overlaps `[a/2, a]` — a segment *already paid and doubled* in call 1.

Repeating `mode=2` calls thus lets the attacker re-earn (and re-double) overlapping tier segments, causing `vlMGP.lockFor` to mint strictly more MGP for the attacker than a single equivalent conversion of the same total WOM would produce. Neither `nonReentrant` nor `whenNotPaused` prevents this, since it requires only sequential unprivileged transactions, not reentrancy.

### Impact Explanation
This is a theft of unclaimed MGP yield: the reward pool held by `ArbWomUp3` (`IERC20(mgp).balanceOf(address(this))`) is depleted faster than intended by the reward-tier schedule, and the attacker's `vlMGP` locked balance is inflated relative to the real WOM they converted, at the expense of the remaining reward pool available to other legitimate depositors. This falls under theft of unclaimed yield / protocol insolvency of the reward-distribution pool.

### Likelihood Explanation
Fully attacker-controlled and repeatable: the attacker only needs WOM tokens and the ability to call the public `incentiveDeposit` function multiple times with `_mode == 2`, with `rewardTier`/`rewardMultiplier` configured with more than one band (a normal production configuration, not a misconfiguration). No special privileges, oracle manipulation, or governance control are required. The exploit is bounded only by the remaining MGP balance held by the contract, and can be repeated across many small deposits to systematically drain the reward pool.

### Recommendation
Make the reward-accounting baseline track the actually-locked amount rather than the nominal `_amountToConvert`. Specifically, in `_mode == 2`, compute `getRewardAmount`/`calDoubledCounted` using the *actual* amount that will be passed to `mWomSV.lockFor` (i.e., `_amount/2`), not the full `_amountToConvert`; or alternatively, restructure so that `getRewardAmount` is called after `_deposit` completes and mWomSV state is updated, with the marginal computation strictly based on before/after `getUserTotalLocked` deltas of the actual locked amount.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3` with `rewardTier = [0, T1, T2]`, `rewardMultiplier = [m0, m1, m2]` (multi-band), fund it with sufficient MGP, and set up `mWom`, `mWomSV`, `vlMGP`, `smartWomConvert` mocks/real contracts.
2. Path A (single shot): attacker calls `incentiveDeposit(a1 + a2, ratio, false, 2)` once. Record `vlMGP` locked amount for attacker as `lockedSingle`.
3. Path B (split): a fresh attacker address calls `incentiveDeposit(a1, ratio, false, 2)` then `incentiveDeposit(a2, ratio, false, 2)`. Record cumulative `vlMGP` locked amount as `lockedSplit`.
4. Assert `lockedSplit > lockedSingle` for the same total WOM converted (`a1 + a2`), demonstrating that splitting the conversion into multiple `mode=2` calls yields strictly more MGP reward than a single equivalent call — confirming the double-counting/over-minting bug.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
