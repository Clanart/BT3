### Title
Payout transaction's `SIGHASH_SINGLE|ANYONECANPAY` witness allows front-running of operator reimbursement attribution - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The `payout_tx` that operators broadcast to front a Citrea withdrawal only commits, via the user's `SinglePlusAnyoneCanPay` signature, to the withdrawal input and the user's payout output [4](#0-3) . The OP_RETURN output that records which operator's `xonly_pk` should later be credited with reimbursement is *not* covered by any signature or authorization check on the Bitcoin side — it is simply appended by whichever party builds and successfully mines the transaction [3](#0-2) . Because `ANYONECANPAY` explicitly allows additional inputs to be spliced onto a partially-signed transaction, any party holding the (mempool-visible) user signature can build a competing version of the same payout with a different fee, a different funding input, and an arbitrary `operator_xonly_pk` in the OP_RETURN, and win the race by paying a higher fee — exactly the class of bug described in the external report, where the "reporter" identity recorded on-chain is not bound to the party whose transaction is included first.

### Finding Description
`create_payout_txhandler` builds a transaction that spends the withdrawal UTXO using only a `SpendPath::KeySpend` witness signed by the user with `SinglePlusAnyoneCanPay` [3](#0-2) . The `operator_xonly_pk` who is meant to receive credit for having fronted the withdrawal is placed in output #3 as raw OP_RETURN data, which is entirely unauthenticated with respect to the signer [5](#0-4) .

The operator's `withdraw()` handler verifies the user's Schnorr signature against sighash type `SinglePlusAnyoneCanPay` (`in_signature.sighash_type`) [1](#0-0) , and then funds the transaction using the Bitcoin Core wallet via `fund_raw_transaction`, adding the operator's own inputs to cover the payout amount, and sends it via RBF [2](#0-1) . `ANYONECANPAY` inputs are, by design, meant to allow additional funding inputs to be appended without invalidating the user's signature — this is explicitly relied upon by the RBF/fee-bumping machinery, which preserves `SinglePlusAnyoneCanPay` witnesses while adding new inputs/outputs [6](#0-5) .

Because the withdrawal UTXO's outpoint and the user's presigned signature are visible on-chain (in the mempool, once any operator broadcasts a candidate payout tx, or via whatever off-chain channel first delivers it), any party — not necessarily a registered operator — can:
1. Copy the user's `SinglePlusAnyoneCanPay` witness and the fixed user-payout output.
2. Add their own funding input(s) to cover the payout amount.
3. Replace the OP_RETURN's `operator_xonly_pk` with an arbitrary value (their own key, or any bytes at all — the Bitcoin script does not validate that this key belongs to a bridge operator).
4. Broadcast with a higher fee, causing their version to confirm before the honest operator's.

Downstream, verifiers key the entire reimbursement/challenge machinery off this OP_RETURN value: `update_finalized_payouts` records whatever `operator_xonly_pk` is parsed from the confirmed payout's OP_RETURN as `payout_payer_operator_xonly_pk` [7](#0-6) , and `is_kickoff_malicious` requires this stored key to equal the actual kickoff's operator key or else the kickoff is treated as malicious/challenged [8](#0-7) . Likewise `validate_payer_is_operator` requires the stored payer key to equal the local operator's own key before it will proceed with reimbursement [9](#0-8) . If the confirmed OP_RETURN key is an arbitrary/attacker key that matches no registered operator, no legitimate operator can ever satisfy `validate_payer_is_operator`, and any operator's kickoff for that deposit is permanently flagged as malicious by `is_kickoff_malicious` (since the OP_RETURN key will never equal any real `kickoff_data.operator_xonly_pk`).

### Impact Explanation
This breaks the custody/attribution binding: `payer_xonly_pk (embedded, unauthenticated OP_RETURN) == operator who actually fronted the withdrawal`. An unprivileged party who observes the withdrawal signature can:
- Take over the "fronting credit" for a withdrawal that a legitimate, registered operator was in the process of paying, using their own funds and an arbitrary key, or
- Simply corrupt the attribution field with a non-operator key, orphaning the deposit's reimbursement path forever.

In the latter case, this matches the Critical-severity criterion "an honest operator permanently unable to be reimbursed": `validate_payer_is_operator` will always fail for every real operator on that deposit, and `is_kickoff_malicious` will always flag every real operator's kickoff for that deposit as malicious, since the stored `payer_xonly_pk` never matches an actual operator key [9](#0-8) [8](#0-7) .

### Likelihood Explanation
Exploitation requires: (1) visibility of an unconfirmed/pending payout transaction (or the underlying presigned user signature) before it confirms, and (2) enough capital to fund the payout output as a replacement input. Both are plausible for any party monitoring the Bitcoin mempool for Clementine payout transactions, since `SinglePlusAnyoneCanPay` is specifically designed to permit exactly this kind of input-splicing, and the protocol already anticipates multiple operators racing for the same withdrawal (the aggregator's `Withdraw` RPC explicitly fans the same request out to all operators) [10](#0-9) . Nothing in the Bitcoin-level protocol restricts the OP_RETURN attribution field to a value belonging to a registered operator, so the same race is exploitable by non-operator actors as well.

### Recommendation
Bind the OP_RETURN attribution to the signer of the transaction, e.g. by requiring the operator to additionally provide a signature (over the tx or over `operator_xonly_pk` plus the withdrawal id) that verifiers check against a registered operator set before accepting a payout as the deposit's canonical fronting event; alternatively, use a covenant/script commitment (verified at the Bitcoin script level, e.g. a script-path spend requiring the operator's own signature over the full transaction including the OP_RETURN) rather than an unauthenticated `SinglePlusAnyoneCanPay` witness plus free-form OP_RETURN data. At minimum, verifiers should reject/ignore (rather than treat as a permanent malicious-kickoff signal) any payout tx whose OP_RETURN key does not correspond to a currently registered operator, and provide a recovery path for the deposit to be reassigned to a legitimate operator in that case.

### Proof of Concept
1. Operator A calls `withdraw()`; the resulting payout tx (per `create_payout_txhandler`) has: input = withdrawal UTXO with `user_sig` (`SinglePlusAnyoneCanPay`), output[0] = user's payout, output[2] = OP_RETURN(`operator_A_xonly_pk`) [3](#0-2) .
2. Operator A's node funds this via `fund_raw_transaction`/RBF and broadcasts it at fee rate `f1` [11](#0-10) .
3. Before it confirms, an attacker (or a competing operator B) observes the transaction in the mempool, extracts `user_sig` and the fixed output[0], and constructs an alternate transaction reusing that witness/output but replacing the funding input with their own UTXO and OP_RETURN with `attacker_xonly_pk`, at a higher fee rate `f2 > f1`.
4. The attacker's version confirms first, spending the withdrawal UTXO.
5. `update_finalized_payouts` records `payout_payer_operator_xonly_pk = attacker_xonly_pk` for this withdrawal [7](#0-6) .
6. Any legitimate operator subsequently calling `validate_payer_is_operator`/`get_reimbursement_txs` for this deposit receives an error because `payer_xonly_pk != self.signer.xonly_public_key` for every real operator [9](#0-8) , and any legitimate operator's kickoff for the deposit is flagged malicious by `is_kickoff_malicious` because `operator_xonly_pk != kickoff_data.operator_xonly_pk` will always hold true [8](#0-7)  — permanently orphaning reimbursement for this deposit.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
