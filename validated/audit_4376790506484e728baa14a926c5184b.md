## Analysis

The `BridgeRoles` report's broken invariant is: **a security-critical binding (who controls contract state) is silently rewritten based on a single unauthenticated/unverified signal, with no user confirmation and no ability to detect or roll back the change.**

The closest real Desktop analog is the automatic **git remote URL rewrite driven by GitHub/GHES API data**, in `updateRemoteUrl`.

### Title
Unconfirmed, Automatic Rewrite of Git Remote URL from GitHub/GHES API Response — (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
Whenever Desktop refreshes GitHub metadata for a repository (on every fetch, push, pull, and periodic background/indicator refresh), it silently calls `git remote set-url` on the user's `origin` remote if the `clone_url` returned by the GitHub/GHES API differs from the currently stored one, with no user prompt, diff, or confirmation step — mirroring the report's "Direct Role Transfer" flaw where a critical binding is changed immediately with no verification/acceptance step.

### Finding Description
`repositoryWithRefreshedGitHubRepository` fetches repository metadata from the API for the account/owner/name matched to the local remote, then unconditionally feeds that response into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` performs a same-hostname/owner/name check (`urlMatchesRemote`) and a protocol check, then — if those pass and the *previously cached* `cloneURL` matched the remote — calls `gitStore.setRemoteURL(...)` to rewrite the remote, with no user interaction: [2](#0-1) 

`GitStore.setRemoteURL` and the underlying `setRemoteURL` git helper perform the change directly via `git remote set-url`, with no confirmation dialog, diff, or audit trail exposed to the user: [3](#0-2) [4](#0-3) 

This code path is exercised on virtually every network operation — user-initiated fetch, remote fetch, and the periodic repository-indicator background fetch — none of which are actions a user would associate with "changing my remote": [5](#0-4) [6](#0-5) 

The trust anchor for "same repository" is only hostname + owner + name string matching (`urlMatchesRemote`/`urlsMatch`), not any stable repository identifier: [7](#0-6) 

Because GitHub Enterprise Server endpoints are user-configurable and the API client trusts whatever `clone_url` the configured endpoint's `/repos/:owner/:repo` response contains, a malicious or compromised GHES instance (or a network position capable of tampering with responses to that endpoint — e.g., a corporate TLS-terminating proxy scenario already acknowledged elsewhere in the codebase's `known-issues.md`) can return an API repository object with an attacker-chosen `clone_url` (same protocol, same owner/name string) that Desktop will apply to the user's real `origin` remote automatically, with no acceptance step and no way to detect the swap short of manually reviewing repository settings.

### Impact Explanation
Silent redirection of `origin` means the next `git push` from the user sends commits (potentially proprietary or credential-bearing) to an attacker-controlled server, and the next `git fetch`/`git pull` pulls history/objects from an attacker-controlled server into the user's working repository — matching the "silent corruption of what the user commits or pushes" impact class. There is no two-step acceptance or recovery mechanism, exactly the deficiency called out in the source report ("Direct Role Transfer" / "Lack of Recovery Mechanism").

### Likelihood Explanation
This requires the attacker to control (or MITM) the API responses of a GitHub Enterprise Server endpoint the user has already added an account for — this is within the stated valid-impact scope ("a git remote/proxy response") and does not require local access, admin rights, or prior malware. The rewrite runs automatically on background/periodic fetches without any user action beyond having previously added the account/repository, so it is triggered passively rather than needing unnatural user steps.

### Recommendation
- Require explicit user confirmation (a dialog showing old vs. new URL) before rewriting an existing remote URL based on API data, rather than doing it silently.
- Anchor the "is this the same repository" check to a stable API-provided repository ID (already available in `IAPIRepository`) rather than string-matching hostname/owner/name, which an attacker who controls the API response fully governs.
- Log/notify the user when a remote URL is changed automatically so the change is auditable, and offer an easy way to revert.

### Proof of Concept
1. User adds a GitHub Enterprise Server account in Desktop pointing at `ghes.example.com`, and has a repository cloned from `https://ghes.example.com/owner/name.git` set as `origin`.
2. Attacker compromises `ghes.example.com` (or sits on a path able to tamper with its API responses) and modifies the JSON returned for `GET /api/v3/repos/owner/name` so that `clone_url` is `https://ghes.example.com/owner/name-mirror.git` (same hostname/owner/name-derived match under `urlMatchesRemote`, same `https` protocol).
3. On the next background fetch/indicator refresh (`fetchForRepositoryIndicator` → `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`), Desktop calls `gitStore.setRemoteURL('origin', 'https://ghes.example.com/owner/name-mirror.git')` with no prompt.
4. The user's next push/fetch silently targets the attacker-controlled `name-mirror` repository instead of the original one.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
