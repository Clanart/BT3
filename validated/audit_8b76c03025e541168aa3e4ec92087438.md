## Title
Bridge circuit accepts operator total work equal to (not strictly greater than) a watchtower's proven total work — ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
The bridge circuit's watchtower-vs-operator proof-of-work check uses a non-strict comparison (`total_work < max_total_work` triggers failure) where the protocol's own specification requires operator total work to be *strictly greater than* the maximum valid watchtower total work. This is the same bug class as the referenced Allora finding (M-6): a strict inequality mandated by spec is implemented as a non-strict one in code, silently changing the boundary at which the check passes.

### Finding Description
`bridge_circuit` in [1](#0-0)  computes `max_total_work` from the highest-work, Groth16-verified watchtower challenge via `total_work_and_watchtower_flags`, then checks:

```rust
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
```

This means the check only fails (panics) when `total_work < max_total_work`; it passes whenever `total_work >= max_total_work`, i.e. it accepts equality.

However, the protocol documentation explicitly states the required relationship is strict: [2](#0-1)  "Asserts that the Operator's `total_work` from their HCP is greater than the `max_total_work` from the Watchtowers," and the function's own doc-comment repeats this: [3](#0-2)  "Validates that the computed `max_total_work` does not exceed the `total_work`... " and [4](#0-3)  "If `max_total_work` given by watchtowers is greater than `hcp.chain_state.total_work`" is the only panic condition documented — no panic is documented (nor coded) for the equal-work case, even though the design intent ("Operator must provide a HCP with more work") is strict.

The watchtower's total work comes from an independently Groth16-verified Work-Only proof over the watchtower's own claimed chain [5](#0-4) , while the operator's total work is the cumulative work in their own HCP chain state [6](#0-5) . Because Bitcoin block work is quantized (a function of difficulty bits), it is possible for two distinct chains of the same length under the same difficulty epoch to have identical cumulative work. The intended binding is: "the operator's claimed canonical chain must be strictly heavier than any chain a watchtower can independently prove," ensuring the operator's fronting-transaction chain is unambiguously the canonical one. Allowing equality breaks this binding — the circuit would accept the operator's proof even when a watchtower has proven an equally-heavy competing chain, meaning canonicity of the operator's claimed chain is not actually established.

### Impact Explanation
This falls under the Critical impact category "a false circuit claim proved... made unprovable/proved" for the bridge circuit's soundness. If total work can tie, the circuit's core soundness claim — that the operator followed the canonical (unambiguously heaviest) chain — is not actually enforced at the boundary, potentially allowing a disprove-resistant claim for a payout tied to a non-provably-canonical chain, or conversely making a legitimate operator's proof spuriously accepted/rejected depending on off-by-one framing, undermining the guarantee described in the docs that a work tie already implies the operator "did not follow the canonical chain."

### Likelihood Explanation
Exploitability requires an actual proof-of-work tie between the operator's HCP chain and the best watchtower Work-Only proof, which is a narrow but not impossible condition (equal number of blocks at equal difficulty). This is a real, unprivileged-attacker-reachable boundary condition in the on-chain-verifiable disprove path — no special role is required to construct the two competing chains/proofs, only mining effort, matching the report's own root cause (loop/comparison boundary using non-strict operator where spec requires strict).

### Recommendation
Change the check to reject on equality as well, consistent with the documented requirement that operator work be strictly greater:
```rust
if total_work <= max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
```

### Proof of Concept
1. Construct a watchtower Work-Only Groth16 proof for a chain with cumulative work `W`.
2. Construct/mine an operator HCP chain, of the same length under the same difficulty, that also accumulates exactly `W` total work (a tie), containing the operator's payout inclusion.
3. Submit both to `bridge_circuit`; the check at [7](#0-6)  passes because `total_work < max_total_work` is `false` when `total_work == max_total_work`, even though the spec requires strict inequality.
