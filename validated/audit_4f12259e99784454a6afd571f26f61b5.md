### Title
Referral reward split can exceed 100% of the claimed amount, causing over-crediting of referral rewards and insolvency of the reward pool - (File: `rewards/ReferralStorage.sol`)

### Summary
`ReferralStorage.trigger()` splits an incoming reward `_amount` between a referrer and a referee using two independently-configured percentage sources — a per-tier `rewardPercentage` (`basic`) and a boosted share (`boostesd`) derived from `BoostPoint` and the caller's proportion of `totalBoostFactor`. Neither of these two values, nor their sum, is ever checked against the `DENOMINATOR` (10000 = 100%). This is the exact same bug class as the reported Nayms issue: two independently bounded (but not jointly bounded) commission/percentage sources can sum to more than 100%, causing more value to be credited than was actually received.

### Finding Description
In `trigger()`: [1](#0-0) 

`basic = tiers[tierId].rewardPercentage` is individually capped at `DENOMINATOR` in `setTier()`: [2](#0-1) 

`boostesd = _calBoosted(_referer)` is computed as `BoostPoint * factor / totalBoostFactor`: [3](#0-2) 

`BoostPoint` is set once in the initializer with **no upper-bound check at all** (unlike `sharePercent`, which is checked against `DENOMINATOR`): [4](#0-3) 

Because `totalBoostFactor` is the sum of `sqrt(vlMGPLockedAmount)` over only the users who have activated the referral feature, an individual referrer's `factor` can be a large fraction of (or, with few referral participants, nearly equal to) `totalBoostFactor`. In that case `boostesd` approaches `BoostPoint` itself — a value that was never bounded to be ≤ `DENOMINATOR`. Combined with a `basic` tier percentage that can independently be set up to `DENOMINATOR` (100%), the sum `basic + boostesd` can exceed `DENOMINATOR`, meaning:

```
refererPercentage + refereePercentage = (basic + boostesd) > DENOMINATOR
```

so `refererAmount + refereeAmount > _amount`, i.e. more reward is credited to the two `userInfos[...].rewardAmount` ledgers than the actual `_amount` that was routed in from `MasterMagpie`. This is reachable purely through ordinary, unprivileged user activity: any user calls `registerCode()`/`useCode()` to join the referral program (unprivileged), locks `vlMGP` (unprivileged), and has their referee claim rewards via `MasterMagpie`, which calls `trigger()` — no admin action is required at exploitation time; only that `BoostPoint` and the tier percentages were configured (at init/via governance) without an invariant tying `basic + boostesd ≤ DENOMINATOR` together, which the contract itself never enforces even in principle since `boostesd` is dynamic based on participation.

### Impact Explanation
Because `rewardAmount` is an internal accounting ledger that is later paid out 1:1 via `claimReward()` (`MGP.safeTransfer(msg.sender, userInfo.rewardAmount)`), over-crediting inflates the sum of all outstanding claims beyond the actual MGP balance funded into the contract by `MasterMagpie`. This leads to:
- Insolvency of the referral reward pool: the sum of all pending `rewardAmount` balances can exceed the MGP tokens actually available in the contract.
- Permanent freezing of funds for honest referrers/referees: once the over-credited amounts are claimed by early claimants, later legitimate `claimReward()` calls will revert (`safeTransfer` failing due to insufficient balance), permanently locking out other users' rightfully earned referral rewards.

This matches the "protocol insolvency" / "permanent freezing of funds" categories.

### Likelihood Explanation
No privileged action is needed to trigger the overflow condition at claim time — it only requires normal user participation (registering/using referral codes and locking vlMGP) combined with a `BoostPoint`/tier configuration that was set once and never re-validated against `totalBoostFactor` dynamics. Because `totalBoostFactor` naturally shrinks/grows with participation, the invariant `basic + boostesd ≤ DENOMINATOR` can be violated at any time without any single "bad" transaction — it emerges from ordinary protocol usage combined with the missing bound on `BoostPoint`.

### Recommendation
1. Bound `BoostPoint` at initialization (and if ever made settable) to ensure `BoostPoint ≤ DENOMINATOR`, mirroring the check already done for `sharePercent`.
2. In `trigger()`, explicitly cap or check that `basic + boostesd ≤ DENOMINATOR` before computing `refererPercentage`/`refereePercentage`, e.g. clamp the sum to `DENOMINATOR` or revert if it would exceed it.
3. Consider tracking cumulative issued `rewardAmount` against actual MGP received by the contract, and assert solvency invariants before crediting new rewards.

### Proof of Concept
1. Deploy `ReferralStorage` with `BoostPoint = 6000` (60%) — this passes initialization since there is no upper-bound check.
2. Admin calls `setTier(1, 5000)` for tier 1 (50%), which is valid since `5000 ≤ DENOMINATOR`.
3. User A calls `registerCode()` (default tier 1) and locks `vlMGP` so their `factor` is computed via `updateTotalFactor`. Since A is the only (or dominant) referral participant, `totalBoostFactor ≈ factor_A`, so `_calBoosted(A) ≈ BoostPoint = 6000` (60%).
4. User B calls `useCode()` referencing A's code, then claims a MasterMagpie reward of `_amount = 1000` MGP, which triggers `ReferralStorage.trigger(B, 1000)` from `MasterMagpie`.
5. Inside `trigger()`: `basic + boostesd = 5000 + 6000 = 11000 > DENOMINATOR (10000)`, so `refererAmount + refereeAmount = 1000 * 11000 / 10000 = 1100 > 1000` — 100 MGP more than the actual `_amount` transferred in is now credited across the two `rewardAmount` ledgers.
6. Repeating this over multiple claims accumulates ledger entries beyond the MGP actually funded into `ReferralStorage`, so eventually some user's `claimReward()` call reverts due to insufficient contract balance, permanently freezing that user's legitimate referral rewards.
