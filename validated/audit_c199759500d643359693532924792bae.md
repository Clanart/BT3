### Title
Automatic `git remote set-url` from an attacker-controlled GitHub API `clone_url` field silently redirects origin to a malicious host - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
When GitHub Desktop refreshes the GitHub metadata for a repository, it calls `updateRemoteUrl()` to compare the cached repository's `clone_url` against the local git remote and, if they diverge, rewrites the local `origin` remote to the new URL returned by the API — without verifying the new URL's hostname belongs to the same GitHub endpoint/account the repository is associated with.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` fetches fresh repository data from the API (`api.fetchRepository(owner, name)`) and, whenever a `gitHubRepository` is already associated with the local repo, feeds the API's `clone_url` straight into `updateRemoteUrl()`: [1](#0-0) 

`updateRemoteUrl()` only checks that the *protocol* (https vs ssh) of the old and new URLs match and that the currently-stored remote URL still matches the previously cached `cloneURL`. It never validates that the new URL's *hostname* corresponds to the account's endpoint (e.g. `github.com` or the specific GHES host the user authenticated against): [2](#0-1) 

`urlMatchesRemote()`/`parseRemote()` only compare `hostname`, `owner`, and `name` between the two URLs being compared for equality — they do not enforce that the new hostname is on any allow-list tied to the signed-in account's endpoint: [3](#0-2) [4](#0-3) 

Because `fetchRepository()` simply parses whatever JSON the configured API endpoint returns into an `IAPIFullRepository`, and that JSON's `clone_url` field is attacker-controlled if the endpoint is a malicious/compromised GitHub Enterprise Server (a "GitHub API object" per the valid-impact criteria), the returned `clone_url` can point to `https://attacker.example/owner/repo` (same protocol, different host) with no rejection: [5](#0-4) 

If the conditions `protocolsMatch && remoteUrlUnchanged && !urlsMatch` hold — which is the common case when a user has not manually edited their remote — Desktop calls `gitStore.setRemoteURL(...)`, which shells out to `git remote set-url origin <attacker-url>` with no further confirmation: [6](#0-5) 

This refresh path is triggered silently and repeatedly in the background: on repository selection (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`), on account changes, and via `withRefreshedGitHubRepository` used by background fetch/pull/push flows — the user does not need to take any explicit "trust this server" action beyond having previously signed in to the (compromised) endpoint: [7](#0-6) [8](#0-7) 

### Impact Explanation
Once `origin` is silently repointed to an attacker-controlled host, subsequent `git fetch`/`git pull`/`git push` operations from Desktop resolve credentials by matching the *new* URL's origin. If the new host doesn't match a known GitHub account endpoint, Desktop's credential trampoline falls back to generic-git-auth and will prompt the user to enter credentials for that host — a classic path to credential exfiltration — or, for SSH remotes, may attempt authentication with the user's real SSH key against the attacker's server. Even absent explicit credential prompts, all future pushes are silently redirected: what the user believes they are pushing to `github.com/org/repo` actually goes to the attacker's server, and pulled/fetched content originates from the attacker rather than the legitimate repository, corrupting the user's view of "what they are pushing/pulling" without any visible warning.

### Likelihood Explanation
The remote rewrite requires an attacker who controls the API responses of an endpoint the user has authenticated to (e.g., a malicious or compromised GitHub Enterprise Server, or a MITM able to tamper with API responses under a broken/misconfigured TLS setup) — this squarely matches the allowed "attacker controls...a GitHub API object" primitive. No local access, no leaked credentials, and no unusual user action are required: the repository refresh path runs automatically in the background whenever Desktop syncs GitHub metadata (repository selection, account refresh, background fetch). The only guard (`protocolsMatch`) is trivially satisfiable by keeping the same scheme and only changing the host.

### Recommendation
In `updateRemoteUrl()` (and more generally wherever an API-provided `clone_url`/`ssh_url` is used to mutate a local git remote), validate that the new URL's hostname matches the hostname of the account's API endpoint (or the existing remote's hostname) before calling `setRemoteURL`. Any hostname change should require explicit user confirmation (e.g., a prompt similar to fork-conversion flows) rather than being applied silently, and should be logged/surfaced in the UI so users can detect unexpected remote-URL changes.

### Proof of Concept
1. Add a GitHub Enterprise Server account in Desktop pointing to a server the attacker controls or can tamper with (server is otherwise indistinguishable from a legitimate GHES instance the user was told to add).
2. Add/clone a repository `owner/repo` from that server; Desktop stores `gitHubRepository.cloneURL = https://ghe.example.com/owner/repo`.
3. On a subsequent background refresh (e.g., selecting the repo again, or Desktop's periodic background fetch), the malicious server responds to `GET repos/owner/repo` with `clone_url: "https://ghe.example.com.attacker.tld/owner/repo"` (same `https` scheme, attacker-controlled host).
4. `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` finds `protocolsMatch = true`, `remoteUrlUnchanged = true` (local remote still equals the previously cached, legitimate URL), `urlsMatch = false` → calls `gitStore.setRemoteURL('origin', 'https://ghe.example.com.attacker.tld/owner/repo')`.
5. `git remote -v` now shows `origin` pointing at the attacker's host; the next `git push`/`fetch` from Desktop silently talks to the attacker's server instead of the legitimate one.

Note: this analysis is based on static code review of the indexed files; I was not able to execute the flow end-to-end or fully inspect `GitStore.setRemoteURL`'s complete implementation (only the underlying `app/src/lib/git/remote.ts:setRemoteURL` helper) due to tool/query limits, so runtime confirmation of the exact background-refresh cadence and any additional guard code inside `GitStore` should be verified in a live session.

  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}
