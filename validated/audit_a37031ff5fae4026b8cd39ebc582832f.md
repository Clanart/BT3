## Finding: Underflow-Revert Permanently Locks Refunds When Cancel Requests Use Pre-Fee `order.inputs` Against Post-Fee Escrow

### Title
Cross-chain order refund permanently reverts due to unsigned underflow from escrow/amount mismatch - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2.withdraw()` function guards escrow debits with `if (_orders[commitment][token] == 0) revert UnknownOrder()` instead of checking `escrowed >= amount`. Escrow is credited at placement time with the *fee-reduced* amount (`reducedInputs[i].amount`), but `_cancelFromDest` builds the refund `WithdrawalRequest` from the *pre-fee* `order.inputs[i].amount`. Whenever `protocolFeeBps` (or a destination fee override) is non-zero, `order.inputs[i].amount > escrowed`, so the on-chain checked subtraction `_orders[body.commitment][token] -= amount` underflows and the whole transaction reverts — this is a direct structural analog of the Perennial `BalancedVault` M-7 bug, where `claimAmount` exceeding `_totalAssetsAtEpoch` caused an unconditional revert on `0 - claimAmount`. [1](#0-0) 

### Finding Description
1. **Escrow credited post-fee.** When inputs go through the predispatch/call-dispatcher path, the escrow ledger is incremented with `reducedInputs[i].amount` (the amount left after protocol-fee deduction), not the full `order.inputs[i].amount`: [2](#0-1) 

2. **Refund request built pre-fee.** `_cancelFromDest` (destination-initiated cancellation) constructs the `WithdrawalRequest` sent back to the source chain using the *original* `order.inputs`, not the fee-reduced amount that was actually escrowed: [3](#0-2) 

3. **No sufficiency check before subtraction.** `withdraw()` only checks that the escrow slot is non-zero, then unconditionally executes `_orders[body.commitment][token] -= amount` using the (possibly larger) requested `amount`: [4](#0-3) 

Because Solidity ≥0.8 uses checked arithmetic by default, `escrowed - amount` with `amount > escrowed` reverts the entire call. Since the transfer to `beneficiary` happens *before* the subtraction in the same function, the revert also unwinds that transfer — so the net effect is not a silent fund drain but a **permanent inability to settle the refund**: every retry of the ISMP delivery for that `RefundEscrow` commitment hits the same underflow and reverts, exactly mirroring the BalancedVault `claim()` failure mode. The user's principal is locked in the `_orders[commitment][token]` mapping with no code path that can ever complete the withdrawal, because the corrupted value being compared (`order.inputs[i].amount`, fixed forever by the order's hash/commitment) can never be reduced to match the escrow record post-fee.

### Impact Explanation
This falls squarely within "loss of funds" / "unauthorized... transaction manipulation" per the bounty's asset-custody pivot: bridged input tokens must "move exactly once and only to the rightful beneficiary and amount." Here they cannot move at all once a non-zero fee is configured, because the on-chain refund path is unconditionally broken by construction — not by any relayer, prover, or governance misbehavior, but by mismatched accounting between the placement-time escrow credit and the cancellation-time debit request, both fully determined by protocol logic and immutable order fields.

### Likelihood Explanation
This triggers deterministically, with no attacker or malicious party required, any time:
- `protocolFeeBps` or a per-destination fee override is configured non-zero (the documented, expected production configuration — the main EVM `IntentGatewayV2` explicitly tests fee-adjusted commitments, confirming fees are a normal operating mode), and
- a cross-chain order is cancelled from the destination chain (`_cancelFromDest`) rather than filled.

Any ordinary user cancelling an order under a fee-enabled deployment hits this path.

### Recommendation
In `withdraw()`, replace the `== 0` guard with a sufficiency check (`if (amount > _orders[body.commitment][token]) revert InsufficientEscrow();`) and, more fundamentally, make `_cancelFromDest` (and any other refund/redeem builder) source the withdrawal amount from the *actual escrowed balance* (`_orders[commitment][token]`) rather than re-deriving it from `order.inputs`, mirroring the same-chain `_cancelSameChain` path which already reads `_orders[commitment][token]` directly instead of the order's nominal input amount.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `protocolFeeBps > 0`.
2. User places a cross-chain order with `inputs[0].amount = 1000e6`; at placement, escrow is credited with `reducedInputs[0].amount = 995e6` (after fee deduction), matching the pattern shown at lines 431-440.
3. Before the deadline expires (or after), the order is cancelled from the destination chain via `cancelOrder()` → `_cancelFromDest()`, which dispatches a `RefundEscrow` `WithdrawalRequest` with `tokens[0].amount = order.inputs[0].amount = 1000e6` (line 590).
4. The message lands on the source chain; `onAccept()` invokes `withdraw(body, isRefund=true)`.
5. Inside `withdraw()`, `_orders[commitment][token] == 995e6` (non-zero, passes the guard), the token transfer of `1000e6` is attempted, then `_orders[commitment][token] -= 1000e6` underflows `995e6 - 1000e6` and reverts.
6. The transaction — and therefore the entire refund — reverts. Every re-delivery of the same `RefundEscrow` commitment reproduces the identical underflow, permanently locking the user's `995e6` escrowed principal with no code path to release it.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
