### Title
DID ownership transfer preserves stale recovery/backup authorization, letting previously-designated backup DIDs seize the DID after a sale/transfer - (File: chia/wallet/did_wallet/did_wallet.py)

### Summary
`DIDWallet.transfer_did()` reassigns a DID singleton to a new owner's puzzle hash but does not clear the DID's `backup_ids` / `recovery_list_hash`. Because DID recovery authorization is checked purely from data curried into the DID inner puzzle (independent of who currently controls the p2 key), a backup DID that was authorized by the *previous* owner remains capable of forcing a recovery spend on the DID even after it has been sold/transferred to a new owner - directly mirroring the report's pattern of "a previously granted authorization surviving object re-creation/transfer and being usable against the new state."

### Finding Description
`transfer_did()` builds the new DID inner puzzle hash while explicitly re-using the unmodified backup list: [1](#0-0) 

and the sibling helper `get_innerpuz_for_new_innerhash()` documents this exact issue in its own comment: the recovery list is intentionally kept across an ownership change, and it is up to the *seller* to remember to clear it beforehand: [2](#0-1) 

The recovery/backup mechanism (`recovery_list`, `num_of_backup_ids_needed`, `recovery_list_hash`) is curried directly into the DID inner puzzle and enforced purely on-chain: [3](#0-2) [4](#0-3) 

This is structurally identical to the reported ERC-721 flaw: an entity (`nftMapping`/backup DID) that was granted authority over an asset while it was in one state continues to hold that authority after the asset is transferred/"recreated" for a new owner, because the code path responsible for the transfer never invalidates the old grant. Just as `transferShortRecord` never checks whether the NFT still points at the *current* `ShortRecord`, `transfer_did` never checks/clears whether the currently-curried `backup_ids` still reflect parties the *new* owner trusts.

### Impact Explanation
If a user sells/transfers a DID (e.g., via an offer/marketplace flow) without first explicitly resetting its recovery list, any address previously designated as a backup DID by the seller retains standing on-chain authority to execute a recovery spend and redirect the DID coin to an address of its choosing - taking the singleton away from the new, legitimate owner. This is an unauthorized coin-ownership takeover of a transferred asset, reachable purely through a wallet-level action (buying/receiving a DID) combined with a spend the attacker (former owner's backup) can construct and broadcast unilaterally. This matches the accepted impact class of "concrete unsigned/unauthorized coin movement."

### Likelihood Explanation
Exploitability requires an external precondition, mirroring the original report's medium-severity rationale: the DID must have been created/configured with a non-empty backup/recovery list, and the seller must fail to clear it before transferring ownership (the seller-side code comment itself concedes this is a real, expected failure mode - "In a selling case, the seller should clean the recovery list then transfer to the new owner"). Because the wallet does not enforce or warn about this at transfer time, and DID marketplace/offer transfers commonly go through `transfer_did`, a normal, non-malicious sequence of user actions (configure backups → later sell the DID without remembering to clear them) is sufficient to expose the DID to takeover by the old backup DID holder(s).

### Recommendation
- Before or during `transfer_did()`, require/force clearing of `backup_ids`/`recovery_list_hash` (i.e., default to an empty recovery list unless the new owner explicitly re-establishes one), rather than silently carrying forward the seller's list.
- Surface a hard warning/failure in wallet RPC/CLI DID-transfer flows when a non-empty recovery list is detected, so sellers cannot accidentally transfer a DID with live backup authorizations intact.
- Consider making `did_wallet_puzzles.create_innerpuz`/`get_inner_puzhash_by_p2` calls from `transfer_did` default `recovery_list_hash` to the "empty" hash rather than passing through `self.reset_recovery_list()`/existing state without an explicit, opt-in override.

### Proof of Concept
1. Alice creates a DID wallet with `backup_ids = [Mallory's DID]`, `num_of_backup_ids_needed = 1` via `generate_new_decentralised_id`.
2. Alice sells the DID to Bob using `transfer_did(new_puzhash=Bob's puzzlehash, ...)` (e.g., through an offer). The resulting inner puzzle still curries in `backup_ids = [Mallory]` because `transfer_did` passes `self.did_info.backup_ids` unchanged.
3. Bob now believes he fully owns/controls the DID.
4. Mallory, still holding the private key corresponding to her backup DID, constructs a recovery spend against the DID coin using the on-chain recovery branch of `DID_INNERPUZ_MOD` (satisfying `recovery_list_hash`/`num_of_backup_ids_needed`), redirecting the DID to an address she controls - without any signature or consent from Bob.
5. The full-node mempool/consensus accepts this spend because it is valid according to the currently-curried puzzle, which still contains Mallory's stale authorization.

```python
def create_innerpuz(
    p2_puzzle_or_hash: Program | bytes32,
    recovery_list: list[bytes32],
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list_hash: Program | None = None,
) -> Program:
    """
    Create DID inner puzzle
    :param p2_puzzle_or_hash: Standard P2 puzzle or hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :param recovery_list_hash: Recovery list hash
    :return: DID inner puzzle
    Note: Receiving a standard P2 puzzle hash wouldn't calculate a valid puzzle, but
    that can be useful if calling `.get_tree_hash_precalc()` on it.
    """
    backup_ids_hash: Program | bytes32 = Program.to(recovery_list).get_tree_hash()
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash
    singleton_struct = Program.to((SINGLETON_TOP_LAYER_MOD_HASH, (launcher_id, SINGLETON_LAUNCHER_PUZZLE_HASH)))
    return DID_INNERPUZ_MOD.curry(
        p2_puzzle_or_hash, backup_ids_hash, num_of_backup_ids_needed, singleton_struct, metadata
    )
```

```python
def get_inner_puzhash_by_p2(
    p2_puzhash: bytes32,
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list: list[bytes32] | None = None,
    recovery_list_hash: Program | None = None,
) -> bytes32:
    """
    Calculate DID inner puzzle hash based on a P2 puzzle hash
    :param p2_puzhash: P2 puzzle hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :return: DID inner puzzle hash
    """

    if recovery_list is None and recovery_list_hash is None:
        raise ValueError("Cannot construct DID inner puzzle without information about recovery list")

    # Allow both recovery_list and recovery_list_hash to be provided but
    # in that case the list is ignored and the hash is used
    # this matches the behaviour of create_innerpuz
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash.as_atom()
    else:
        assert recovery_list is not None
        backup_ids_hash = shatree_atom_list(recovery_list)

    # singleton_struct = (MOD_HASH . (LAUNCHER_ID . LAUNCHER_PUZZLE_HASH))
    singleton_struct = shatree_pair(
        SINGLETON_TOP_LAYER_MOD_HASH_TREE_HASH,
        shatree_pair(shatree_atom(launcher_id), SINGLETON_LAUNCHER_PUZZLE_HASH_TREE_HASH),
    )

    return curry_and_treehash(
        DID_INNERPUZ_MOD_HASH_QUOTED,
        p2_puzhash,
        shatree_atom(backup_ids_hash),
        shatree_int(num_of_backup_ids_needed),
        singleton_struct,
        metadata.get_tree_hash(),
    )
```
