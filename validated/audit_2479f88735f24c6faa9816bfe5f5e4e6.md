### Title
Stale working-directory snapshot lets Copilot's earlier conflict resolution silently overwrite a user's freshly-resolved file - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The Copilot conflict-resolution flow's "safety check" that is supposed to prevent overwriting a conflict the user has since resolved by hand is evaluated against a `state` snapshot taken once at the *start* of the apply routine, not against the file's live on-disk/status at the moment each file is actually written. This mirrors the report's underlying invariant break — a downstream value (`resolvedContent`) is applied without re-validating it against the current, possibly-changed state, so what actually lands in the commit can silently diverge from what the user believes they approved.

### Finding Description
`_applyCopilotConflictResolutions` fetches the working-directory state a single time: [1](#0-0) 

For each Copilot resolution it then decides whether it's safe to overwrite the file using that same, un-refreshed `state` object: [2](#0-1) 

The comment at line 7241 explicitly documents the intended protection ("skip it and let their resolution stand") but the check reads `state.changesState.workingDirectory.files` — a cache populated before this function began, not the file's actual current status — before doing `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and staging it with `git add`. `resolution.resolvedContent` itself was produced earlier by the AI resolution run, whose duration is explicitly tracked for taking over 60–120+ seconds: [3](#0-2) 

During that window (and the additional time the user spends reviewing the result dialog before clicking "Continue Merge"), the user may resolve the same conflicted file manually and save it — but `_applyCopilotConflictResolutions` never re-reads git status right before writing, so the guard can pass on stale data and Copilot's older `resolvedContent` overwrites the user's real resolution without any diff-vs-current-disk re-check at write time. This is structurally the same broken invariant as the report: a value that should be validated at the moment of use (here, "is `resolvedContent` still safe to write") is instead validated against an earlier snapshot, and nothing forces re-verification before the corrupting write occurs.

### Impact Explanation
If exploited, the commit ends up containing content the user did not actually approve — a large, complex, or slow-to-resolve conflict (which an attacker fully controls by crafting the conflicting branches/files) widens the race window, increasing the odds that Copilot's stale resolution silently clobbers a user's manual fix (e.g., reintroducing vulnerable code, secrets, or reverting a security-relevant fix) right before commit. This falls under "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires a user to actively use the (still Copilot-specific, comparatively new) AI conflict-resolution flow, and to manually resolve the same file externally during the resolution/review window, which is a real but not the most common workflow. I could not verify from static code review alone whether `refreshChangesSection`/status polling runs frequently enough in practice to keep `state` fresh in most cases, so the actual exploit window in a running app is uncertain without dynamic testing.

### Recommendation
- Before writing `resolution.resolvedContent` for a given path, re-fetch that file's current git status/content directly (not from the cached `state` snapshot) and re-verify it still has unresolved conflict markers.
- Consider diffing the live on-disk content against the content that existed when the resolution was generated, and abort/re-prompt the user if it changed, analogous to an optimistic-concurrency/ETag check.

### Proof of Concept
Not independently executable from static analysis; the flow would need to be exercised end-to-end (start a merge with a conflict, trigger Copilot resolution, manually resolve the same file externally during the multi-second/minute resolution+review window, then click "Continue Merge") to confirm whether `state` is stale enough in practice for the overwrite to occur. I flag this as **unverified dynamically** — the code path and the absence of a live re-check are confirmed by inspection, but I did not have the ability to run the application to prove the race is reliably triggerable.
