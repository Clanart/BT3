### Title
Same-chain partial-fill progress is keyed only by output token address, not by output-leg index, allowing cross-contamination between order legs sharing a token — (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` tracks partial-fill progress per `(commitment, outputToken)` via `_partialFills[commitment][outputToken]` [1](#0-0) , and computes the escrow to release per output leg with `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` [2](#0-1) . This is the same structural pattern the external report warns about: a value meant to represent progress/price for one specific pair is combined with (or substituted into) the accounting of a different pair as if they were commensurate, because the storage key does not distinguish which leg the fill applies to.

### Finding Description
In `_fillSameChain`, the loop iterates output legs by index `i`, reading `order.output.assets[i].token` and `order.inputs[i].amount`/`order.inputs[i].token` as a matched pair [3](#0-2) . However, the "already filled" progress used to compute `remaining` and `fillAmount` is read and written through `_partialFills[commitment][outputToken]`, keyed **only by the output token's address**, not by leg index [4](#0-3) .

If an order's `output.assets` array contains two (or more) legs that specify the **same output token address** but are paired with **different input tokens/amounts** (e.g., leg 0: pay 100 DAI to get 100 USDC-input released, leg 1: pay 100 DAI to get 500 WETH-input released), the shared key means that a fill against leg 0 advances `alreadyFilled` for the token globally. When leg 1 is subsequently processed (even within the same transaction, since the loop runs over all `outputsLen` entries), `remaining = totalRequired - alreadyFilled` for leg 1 is computed using progress that was actually paid against leg 0's `totalRequired`, not leg 1's. Because `escrowedAmount` for a non-final fill is `(order.inputs[i].amount * fillAmount) / totalRequired` — where `totalRequired` is leg 1's requirement but `fillAmount` was derived from cross-contaminated `alreadyFilled`/`remaining` state — the input-token payout for leg 1 can be computed using a `fillAmount` that does not correspond to output actually delivered for leg 1's specific input pairing. In the worst case, a solver can drive `amountFilled == totalRequired` for leg 1 (fully filled) without providing proportionally correct output for the leg 1's paired input, then hit the full-release branch `escrowedAmount = _orders[commitment][token]` [2](#0-1) , releasing an entire escrow balance for an input token disproportionate to what was actually paid for that specific leg.

Existing guards do not stop this: there is no per-leg duplicate-token check visible in the fill path, and the `TokenInfo`/`Order` structures (`evm/src/apps/IntentGatewayV2.sol`) do not appear (from what I could inspect) to enforce uniqueness of `output.assets[].token` across legs of the same order. `_orders[commitment][token]` (escrow balance) is aggregated per token across all input legs at placement time [5](#0-4) , so a global per-token escrow pool exists that a mis-keyed partial-fill accounting can misallocate between legs.

**Caveat / what I could not verify:** I ran out of tool iterations before confirming (a) whether `placeOrder` validation explicitly rejects orders whose `output.assets` contains duplicate token addresses, and (b) whether `order.inputs[i]`/`order.output.assets[i]` are guaranteed 1:1 unique-token pairings elsewhere in `IntentGatewayV2.sol`. If such a uniqueness check exists at order placement, this specific path is not exploitable and the finding should be discarded. I could not locate such a check via `grep_search` for `duplicate`/`InvalidInput` patterns restricted to the intents directory before the session ended, but this does not conclusively prove its absence.

### Impact Explanation
If duplicate output-token legs are not rejected at placement, a solver could manipulate the shared `_partialFills` key to claim escrowed input tokens disproportionate to the output actually delivered for a specific leg — a direct case of "wrong beneficiary or amount" / fund loss from escrow, matching the bounty's core impact categories (unauthorized execution/transaction manipulation, fund loss).

### Likelihood Explanation
Likelihood is **conditional and unverified**: it depends entirely on whether the `Order` struct or `placeOrder` enforces uniqueness of output tokens across legs. If no such check exists, the exploit requires only a normal user placing an order with a crafted (but structurally valid) `output.assets` array and a colluding/self-controlled solver — no privileged actor, relayer, or prover involvement, which is consistent with the bounty's "unprivileged attacker" requirement. If such a uniqueness check does exist, likelihood is zero and this analog does not hold.

### Recommendation
- Confirm whether `Order` placement validates uniqueness of `output.assets[].token`; if not, add that check, or
- Re-key `_partialFills` by `(commitment, outputLegIndex)` instead of `(commitment, outputToken)` so progress can never be shared across legs with coincidentally identical token addresses, mirroring the external report's recommendation to never combine values from different "denominations" (here, different logical legs) as if they were fungible.

### Proof of Concept
Conceptual reproduction (pending confirmation of the missing duplicate-token guard):
1. User places a same-chain order with two output legs, both requiring token `DAI` as output: leg 0 pairs with input `USDC` (small `totalRequired`), leg 1 pairs with input `WETH` (large `totalRequired`, disproportionately large escrow).
2. Solver calls `fillOrder` supplying `outputs[0].amount = totalRequired[0]` (fully satisfying leg 0) in the same or a prior call, advancing `_partialFills[commitment][DAI]` to `totalRequired[0]`.
3. On the call processing leg 1, `alreadyFilled` reads the same `_partialFills[commitment][DAI]` value already advanced by leg 0's payment, causing `remaining`/`fillAmount` for leg 1 to be computed incorrectly relative to leg 1's actual `totalRequired`.
4. Depending on the exact values chosen, the solver can reach `amountFilled == totalRequired[1]` for leg 1 without paying the corresponding DAI amount for leg 1 specifically, triggering the full-release branch and draining the WETH escrow tied to leg 1.

This PoC could not be executed or fully validated against the live contract/tests in this session; a Devin session with repository/test access would be needed to confirm exploitability and the presence or absence of the duplicate-token guard.
