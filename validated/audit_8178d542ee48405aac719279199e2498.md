## Analysis

The Ion Protocol report's core issue is: a value used to move funds/state (an oracle price) is consumed without any validation of correctness, and no fallback ensures the counterparty is made whole. The closest real, fund-affecting analog in Hyperbridge is not in proof verification (which is heavily guarded — see `HeaderImpl.stateCommitment` [1](#0-0) , `GrandpaConsensusClient::verify_consensus` [2](#0-1) , and `SimplexPaymaster._getOraclePrice`, which explicitly checks staleness/non-positivity [3](#0-2) ). It is in `EvmHost`'s native-fee dispatch path, which uses an on-chain AMM spot price as an implicit "oracle" with no output/refund validation.

### Title
Unrefunded native-token overpayment in `EvmHost` dispatch/fundRequest permanently strands user funds - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` accept `msg.value` and swap it via Uniswap V2 (`swapETHForExactTokens`) to obtain an exact amount of fee token. Because callers must send `msg.value` ≥ the amount required at execution time (the price can move between the off-chain `quote()` estimate and on-chain execution), any native token sent in excess of what the swap actually consumes is refunded by the router to `msg.sender` — which is the `EvmHost` contract itself, not the original caller. `EvmHost` never forwards or accounts for this refunded dust, so it is permanently and silently absorbed by the contract with no recovery path for the payer.

`IUniswapV2Router02.swapETHForExactTokens` is documented to require `msg.value >= amounts[0]`, execute the swap for the exact requested output, and refund `msg.value - amounts[0]` to its caller. Here the caller is `EvmHost`, so the standard Uniswap refund lands inside `EvmHost`'s own balance rather than being returned to `_msgSender()`. None of the three call sites capture or forward this refund back to the payer.

The protocol's own documentation confirms this AMM spot price is inherently volatile and only safe to use off-chain: "`quote()` ... uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks. Only use it off-chain for frontend fee estimation" [7](#0-6) . Because the actual price at execution can differ from the quoted price, any rational caller must send `msg.value` with margin above the quoted amount to avoid reverts from insufficient input — and that margin is exactly the amount that gets trapped in `EvmHost` instead of being returned. `quote()` itself confirms this reliance on the unguarded spot price with no slippage bound: [8](#0-7) 

This differs from the Ion Protocol case only in mechanism (missing zero/staleness check vs. missing refund-of-excess check), but the broken invariant is the same class: a market/price value is consumed to move funds without a guard that keeps the depositor whole when that value is unfavorable or moves.

### Impact Explanation
Every unprivileged, ordinary user who pays for a dispatch/fundRequest with native token and provides any margin above the exact quoted amount (which is unavoidable given price movement between quote and execution, and explicitly warned about by the docs) loses that margin permanently — it is not returned, not tracked as protocol revenue, and not attributable to any request. This is direct, non-consensual loss of user funds via a public entrypoint, with no privileged actor, relayer, or prover involved. It also does not need an active attacker: it manifests on every native-token dispatch/fundRequest call where sent value exceeds swap consumption.

### Likelihood Explanation
High. `dispatch()` and `fundRequest()` are the standard, expected way for any `HyperApp` (i.e., any Hyperbridge-integrated dApp) to pay for a cross-chain message with native token, per the documented pattern [9](#0-8) . Since `quote()` is explicitly unsafe to call on-chain and price can shift between estimation and execution, any caller sending exact-quoted `msg.value` risks a revert, so realistic integrations pad the value sent — guaranteeing dust loss on every such call, with the loss magnitude scaling with padding and market volatility.

### Recommendation
After the Uniswap swap in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, check `address(this).balance` (or capture the swap's actual token cost) and refund any leftover native token to `_msgSender()`/`post.payer` before returning. Alternatively, switch to `swapExactETHForTokens` with a caller-specified `amountOutMin` and always refund unspent `msg.value`.

### Proof of Concept
1. Deploy `EvmHost` and configure it with a live Uniswap V2 router.
2. A caller estimates required native cost off-chain via `quote()` (per docs), then adds a safety margin and calls `dispatch{value: quotedAmount + margin}(post)` — this is the documented, expected usage pattern.
3. Inside `dispatch()`, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes: it consumes only what is needed to obtain exactly `post.fee` fee-tokens and refunds the difference to `msg.sender`, i.e., `EvmHost` itself (per `IUniswapV2Router02` semantics) [4](#0-3) .
4. `dispatch()` returns without transferring any ETH back to the original caller — the margin remains locked in `EvmHost`'s balance, unassociated with any commitment or accounting structure, confirmed by the absence of any refund logic in the function body [10](#0-9) .
5. Repeat for any number of calls: `EvmHost`'s native balance accumulates unaccounted dust taken from ordinary users with no mechanism for them to reclaim it.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(

            );

            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();

            to: abi.encodePacked(request.to),
            nonce: request.nonce,
            timeoutTimestamp: request.timeoutTimestamp,
            body: request.body,
            fee: post.fee
        });
    }

contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
