### Title
Unchecked u64 amount arithmetic in `SignableTransaction` panics/wraps on out-of-range output values - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The ImageMagick flaw (CVE in `MagickCore/statistic.c`) is an integer-range violation: accumulated statistics produce values outside the range of `unsigned long`, yielding undefined behavior and crashing the process on crafted input. The Serai analog is the unchecked `u64` satoshi arithmetic in `SignableTransaction::new` / `SignableTransaction::fee`, which operates directly on `TxOut.value` decoded from untrusted bytes via `ReceivedOutput::read`. Summing output values with `.sum::<u64>()` and adding `payment_sat + needed_fee` can exceed `u64::MAX`, and `fee()` performs a plain subtraction that underflows — producing a panic (availability loss) reachable purely from attacker-controlled serialized bytes.

### Finding Description
`ReceivedOutput::read` decodes a `TxOut` with `TxOut::consensus_decode` without bounding `value` to `Amount::MAX_MONEY` (21M BTC); any `u64` up to `u64::MAX` is accepted into `ReceivedOutput.output` (networks/bitcoin/src/wallet/mod.rs:122-133). These values then feed unchecked arithmetic in `SignableTransaction`:

```rust
// send.rs:175
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
// send.rs:206
let mut needed_fee = fee_per_vbyte * vbytes;
// send.rs:215
if input_sat < (payment_sat + needed_fee) { ... }
// send.rs:139-141
pub fn fee(&self) -> u64 {
  self.prevouts.iter().map(|p| p.value.to_sat()).sum::<u64>() -
    self.tx.output.iter().map(|p| p.value.to_sat()).sum::<u64>()
}
```

Three distinct range violations, all from crafted `ReceivedOutput` bytes (or crafted payment lists):

1. `input_sat` summation wraps modulo 2^64. Two outputs each claiming `~u64::MAX` wrap to a small value; the solvency check at line 215 (`input_sat < payment_sat + needed_fee`) and the `checked_sub` change computation at line 228 then operate on a wrapped total, producing a `SignableTransaction` whose bookkeeping (`needed_fee`, `fee()`, `prevouts`) is inconsistent with the real inputs.
2. `payment_sat + needed_fee` (line 215) and `fee_per_vbyte * vbytes` (line 206) can themselves overflow, causing the solvency check to pass when it should fail.
3. Whenever the constructed tx's output sum exceeds the wrapped prevout sum, `fee()`'s unchecked subtraction at lines 139-141 underflows and panics. In release builds without `overflow-checks`, the wraps in `sum`/`+` are silent; the subtraction panic (debug builds, or any caller asserting `fee() == needed_fee()`) kills the task. This is exactly the ImageMagick pattern: an aggregate statistic (`sum` of untrusted `unsigned long` values) escapes the type's range and the process aborts.

The same class appears in `processor/src/networks/mod.rs:579-583`, where `sum(inputs) - sum(payments) - tx_fee` is computed with plain subtraction, but the in-scope instance is `send.rs`.

### Impact Explanation
An unprivileged party who can feed crafted bytes to `ReceivedOutput::read` (or otherwise inject outputs with inflated `value` fields into a signing flow) can: (a) crash the process during transaction construction or when `fee()`/`needed_fee()` consistency is asserted — direct availability loss matching the ImageMagick advisory; (b) obtain a `SignableTransaction` whose reported `needed_fee`/`fee` disagree with `sum(inputs) - sum(outputs)`, causing the coordinator's fee accounting and the eventual signed transaction's change output to be computed from a wrapped total — i.e., funds bookkeeping corrupted by attacker-chosen values. No secret material is needed; only malformed serialized `TxOut` values.

### Likelihood Explanation
`ReceivedOutput::read` is a listed untrusted-bytes entry point and performs no range check on `TxOut.value`. The overflow requires only a `value` near `u64::MAX` in two decoded outputs, or `payment_sat`/`fee_per_vbyte` products large enough to wrap — all attacker-encodable in a byte stream. Triggering the `fee()` underflow additionally requires reaching a state where wrapped totals make outputs exceed inputs, which follows directly from case (1). Exploitation does not require validator status, collusion, or leaked keys.

### Recommendation
- In `ReceivedOutput::read`, reject `TxOut` values exceeding `Amount::MAX_MONEY` (`output.value > Amount::MAX_MONEY` → error).
- In `SignableTransaction::new`, use `checked_sum`/`checked_add`/`checked_mul` for `input_sat`, `payment_sat`, `needed_fee`, and the change computation; return a `TransactionError` instead of wrapping.
- In `fee()`, use `checked_sub` and return `Option<u64>`/`Result` rather than panicking.
- Apply the same treatment to the mirrored subtraction in `processor/src/networks/mod.rs:579-583`.
