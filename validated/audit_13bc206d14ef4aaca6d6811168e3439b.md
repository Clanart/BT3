## Analysis

The external report's core theme — "a component can look valid/verified while actually being outdated and exploitable" — maps to a genuine local issue in Hyperbridge's GET-timeout path: **a stale (but individually valid) non-membership proof height can be used to force a false timeout even though the request already has a live, later response**, because the handler never checks the *current* state of the request/response, only a caller-chosen historical height.

### Title
GET request timeout can be forced with a stale non-membership proof height, bypassing the "response already delivered" check present on the Substrate side - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handleGetRequestTimeouts` accepts a caller-supplied `StateMachineHeight` and proves non-membership of the response receipt at that specific height, then unconditionally calls `dispatchTimeOut` if the request is "known" and `request.timeout() > state.timestamp` is false. [1](#0-0) 

Unlike the Rust ISMP core, which explicitly rejects a timeout once a response has actually been received: [2](#0-1) 

the Solidity handler has no equivalent check against the *live* state. It only checks non-membership at an arbitrary, caller-chosen past height. Because `stateMachineCommitment` entries for old heights are never pruned (`handleConsensus` only tracks/advances the "latest" height, it never deletes historic commitment entries), an attacker can always find/reuse an older, still-stored height `H1` — timestamped past the request's `timeoutTimestamp` — at which the response genuinely didn't exist yet, even though a legitimate response has since been produced and is pending delivery (or already delivered under a different, later height).

### Finding Description
`handleGetRequestTimeouts` derives its correctness from a non-membership proof anchored at `message.height` (an arbitrary `StateMachineHeight` chosen by the caller): [1](#0-0) 

There is no requirement that `message.height` be the *latest* known height for that state machine, and no check of the local `responseReceipts` state that `handleGetResponses` itself relies on for its own duplicate protection: [3](#0-2) 

Since `EvmHost.dispatchTimeOut(GetRequestTimeout, ...)` unconditionally deletes the request commitment and invokes the module's `onGetTimeout`, and refunds the sender's fee, this can happen even when the response for that exact request has already been computed (and possibly already delivered under a fresher, later-height proof, or about to be delivered): [4](#0-3) 

Once `dispatchTimeOut` deletes `_requestCommitments[commitment]`, any subsequent legitimate `handleGetResponses` delivery for that same request permanently reverts with `UnknownMessage`, because the "known request" check reads `_requestCommitments`: [5](#0-4) 

The bound value corrupted here is the *effective liveness state of the GET request*: the handler treats an old, no-longer-current non-membership fact as proof of "still not answered," when the true canonical state (a later height, or the local `responseReceipts` mapping already populated by an earlier `handleGetResponses` call) says otherwise.

### Impact Explanation
This is a "false proof/state acceptance" bug: an unprivileged caller (no relayer/prover/admin collusion needed — anyone who can construct/replay a previously-valid non-membership proof for an old, still-retrievable height) can force a GET request to be treated as timed out even though it has a real, later, already-committed response. Consequences:
- The requesting application's `onGetTimeout` callback fires with false information (e.g. releasing escrow, refunding a fee, or unwinding an intent) while the real answer is silently discarded.
- The genuine response, if delivered afterward, is permanently rejected (`UnknownMessage`), so the intended recipient never gets the correct query result.
- Protocol-level fee refund to the original sender happens based on a fabricated timeout rather than the real outcome, which is a fund-movement decision driven by stale/false state.

This directly threatens fund/state correctness in any HyperApp built on GET queries (e.g., cross-chain balance/price checks feeding escrow release logic), fitting "false proof/state acceptance" and "logic attack" in the bounty's impact gate.

### Likelihood Explanation
Likelihood is high for any long-lived GET request where multiple state-machine heights get finalized between the request's timeout deadline and the actual response delivery — a normal, expected occurrence given relayer latency. No special relayer/prover compromise, governance action, or front-running is required; the attacker only needs to obtain (or reconstruct) a valid non-membership proof at an older height, something any honest relayer already produces routinely as part of normal operation, and resubmit/race it via the permissionless `handleGetRequestTimeouts` entrypoint.

### Recommendation
Add a live-state check mirroring the Rust implementation and `handleGetResponses`'s own duplicate-response check: before calling `dispatchTimeOut`, verify `host.responseReceipts(commitment).relayer == address(0)` (i.e., no response has already been recorded locally), and/or require `message.height` to be at or above the latest known height for that state machine so stale proofs cannot be reused to contest already-superseded state.

### Proof of Concept
1. App on chain A dispatches a `GetRequest` with `timeoutTimestamp = T`.
2. Hyperbridge (or the queried chain) finalizes state at height `H1` with `timestamp = T+1`, at which the response has genuinely not yet been produced — a valid non-membership proof exists for `RESPONSE_RECEIPTS_STORAGE_PREFIX || commitment` at `H1`.
3. Shortly after, the response is actually produced and finalized at a later height `H2 > H1`.
4. Attacker (anyone) calls `HandlerV2.handleGetRequestTimeouts` with `message.height = H1` and the (still valid, still stored) non-membership proof from step 2. All checks pass: challenge period elapsed, `state.stateRoot` for `H1` still exists (`host.stateMachineCommitment` never prunes old heights), `request.timeout() > state.timestamp` is false, request is "known," non-membership proof at `H1` verifies.
5. `EvmHost.dispatchTimeOut(GetRequestTimeout, ...)` executes: deletes `_requestCommitments[commitment]`, refunds the fee to the original sender, and calls the module's `onGetTimeout`.
6. The relayer who actually delivers the real response at `H2` via `handleGetResponses` now fails at the "known request" check (`meta.sender == address(0)`) with `UnknownMessage`, permanently losing the true response while the app has already acted on the false timeout.

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
