### Title
Attacker-primed `session[:return_to]` enables post-OAuth open redirect to arbitrary external domain - (File: app/controllers/shopify_app/callback_controller.rb)

### Summary
`ShopifyApp::SessionsController#copy_return_to_param_to_session` copies the unauthenticated `params[:return_to]` into `session[:return_to]` before OAuth begins, and `CallbackController#redirect_to_app` later redirects the victim's browser to that value verbatim (with `allow_other_host: true`) whenever `fully_formed_url?` recognizes it as an absolute URL. `RedirectSafely.make_safe` only guards against empty/blank values here, not scheme/host confinement, so an attacker who gets a victim to start the OAuth flow with a crafted `return_to` (e.g. via a phishing link to the app's `/login` route) can redirect the victim post-auth to an attacker-controlled domain.

### Finding Description
The attack surface begins at `ShopifyApp::SessionsController#authenticate` → `#start_oauth` → `#copy_return_to_param_to_session`, which runs on unauthenticated requests to `/login` (or `create`): [1](#0-0) 
`RedirectSafely.make_safe(params[:return_to], "/")` is invoked with a fallback of `"/"`, but nothing in this code path restricts `params[:return_to]` to same-host/relative values before it is written into `session[:return_to]`.

After the victim completes the OAuth dance, `CallbackController#redirect_to_app` reads back that session value: [2](#0-1) 
If `fully_formed_url?` (which only checks `Addressable::URI` scheme+host presence) returns true, `return_to` is used verbatim as the redirect target with `allow_other_host: true`, bypassing Rails' `redirect_to` external-host protections. The only host check performed (`deduced_phishing_attack?`) validates the **`host` query param** against the myshopify domain, not the `return_to` value at all — so a benign/valid `host` param combined with a malicious `return_to` sails through unblocked.

This exact behavior is already codified as "expected" in the test suite: [3](#0-2) 

### Impact Explanation
This is a **post-authentication open redirect** (Shopify HackerOne class: Open Redirect / Sensitive data exposure via redirect). Because the embedded redirect happens immediately after OAuth completes, the redirected URL/browser context can carry query-string state, referrer data, and potentially the `host` fragment used for embedded app bootstrapping to the attacker's domain. It does not directly leak the access token (which is stored server-side/in encrypted cookies), but it can be used for phishing (displaying a fake Shopify-embedded login page), session/state exfiltration via query params, or chaining with other vulnerabilities that rely on trusted redirect targets.

### Likelihood Explanation
Exploitability requires only that the host app exposes the default `ShopifyApp::SessionsController#new`/`#create` (`/login`) route with `return_to` accepted as a query parameter — this is the gem's default behavior, not a custom misconfiguration, since `copy_return_to_param_to_session` runs unconditionally on `params[:return_to]` presence. The attacker sends the victim a link such as `https://merchant-app.example.com/login?shop=victim-shop.myshopify.com&return_to=https://evil.com/phish`; the victim (already logged into Shopify admin or clicking from the Shopify admin app list) completes OAuth normally, and the gem's own logic performs the final redirect to `evil.com`. This is fully reproducible with no secrets, tokens, or insider access required.

### Recommendation
- In `login_protection.rb`/`sessions_controller.rb`, sanitize `return_to` to only allow relative paths (or paths on the app's own configured domain) before storing it in `session[:return_to]`, e.g. reject any value where `Addressable::URI.parse(return_to).host` is present and doesn't match the app's own host.
- In `CallbackController#fully_formed_url?`/`#redirect_to_app`, when `return_to` is fully-formed, validate that its host equals `decoded_host`'s host (or another explicitly trusted domain) before honoring it with `allow_other_host: true`; otherwise fall back to `decoded_host`.

### Proof of Concept
```ruby
test "return_to primed by unauthenticated login request redirects victim to attacker domain after OAuth" do
  # Step 1: attacker-crafted request to /login with return_to pointing to evil.com
  get :new, params: { shop: SHOP_DOMAIN, return_to: "https://evil.com/phish" }
  # session[:return_to] is now "https://evil.com/phish" (RedirectSafely.make_safe only checks blank/"/","")

  # Step 2: victim completes OAuth; callback runs with the primed session
  mock_oauth
  get :callback, params: @callback_params

  # Vulnerable behavior (confirmed by existing test at callback_controller_test.rb:185-192):
  assert_redirected_to "https://evil.com/phish"
  # Expected secure behavior: redirect should be confined to app's own/trusted host,
  # e.g. assert_redirected_to "https://#{@host}/admin/apps/key" instead.
end
```

      if ShopifyAPI::Context.embedded?
        return_to = session.delete(:return_to)
        redirect_to = if fully_formed_url?(return_to)
          return_to
        else
          "#{decoded_host}#{return_to}"
        end

        redirect_to = ShopifyApp.configuration.root_url if deduced_phishing_attack?
        redirect_to(redirect_to, allow_other_host: true)
      else
        redirect_to(return_address)
      end
    end

    def fully_formed_url?(return_to)
      uri = Addressable::URI.parse(return_to)
      uri.present? && uri.scheme.present? && uri.host.present?
    end
