## Title
AddressBook `registerCnStakingContract` does not enforce uniqueness of `cnStakingContractAddress`, allowing a validator to double-count a single staking-contract balance across two `NodeId` entries and inflate `StakingInfo.StakingAmounts` used for reward distribution and proposer weighting - (File: `contracts/testing/reward/AddressBookMock.sol`, `kaiax/staking/impl/getter.go`, `kaiax/staking/staking_info.go`)

### Summary
`registerCnStakingContract` in the AddressBook system contract only checks uniqueness of `cnNodeId`; it never validates that `cnStakingContractAddress` (or `cnRewardAddress`) is not already registered under a different `NodeId`. `kaiax/staking` (`getter.go`) parses the AddressBook's flat list into `StakingInfo.{NodeIds, StakingContracts, RewardAddrs, StakingAmounts}` verbatim, and `StakingInfo.consolidateNodes()` only merges entries that share an identical `RewardAddr` [1](#0-0) . If the same physical staking-contract address is registered under two distinct `NodeId`/`RewardAddr` pairs, its native-token balance is queried and summed twice, inflating the validator's effective stake.

### Finding Description
`registerCnStakingContract` only guards against duplicate `cnNodeId`: [2](#0-1) 

There is no check that `_cnStakingContractAddress` (or `_cnRewardAddress`) has not already been registered by another `cnNodeId`. This mirrors exactly the pattern in the external report: uniqueness is enforced for one identifier (`cnNodeId` ~ `location` uniqueness inside a single call) but not for the other field that actually determines whether a balance gets double-counted.

`kaiax/staking/impl/getter.go` (`parseCallResult`/`parsePermissionlessCallResult`) reads the AddressBook/MultiCall results and builds parallel arrays `NodeIds`, `StakingContracts`, `RewardAddrs`, `StakingAmounts` directly from the on-chain lists without any de-duplication of `StakingContracts`: [3](#0-2) 

Each `StakingAmounts[i]` is derived from the actual native balance of `StakingContracts[i]` (see test fixtures binding staking contract balances 1:1 to `StakingContracts` entries) [4](#0-3) .

`StakingInfo.consolidateNodes()` only consolidates entries sharing the same `RewardAddr`; it does not detect or merge entries that reuse the same `StakingContracts[i]` address under a different `RewardAddr`: [1](#0-0) 

Consequently, if a CN operator registers two `NodeId`s (e.g. `N1` with `RewardAddr R1`, and `N2` with `RewardAddr R2`) that both point to the same `StakingContract S`, the resulting `consolidatedNodes` will contain **two independent** entries, `CN1={[N1],[S],R1,A_S}` and `CN2={[N2],[S],R2,A_S}`, each carrying the **full** balance `A_S` of the single staking contract `S`. The same underlying collateral is counted twice.

### Impact Explanation
`ConsolidatedNodes()` output feeds directly into reward allocation (`assignStakingRewards`/`assignStakingRewardsFlex` in `kaiax/reward/impl/getter.go`, which computes `totalExcessInt` and per-CN proportional reward using `cn.StakingAmount`) [5](#0-4) , and into validator-set/committee selection (`collectStakingAmounts` and weighted-random proposer selection in `kaiax/valset/impl/getter_demote.go`) [6](#0-5) . Duplicating a single collateral balance across two council entries:
- Redirects a disproportionate share of the staking-reward pool to the operator controlling both reward addresses (fee/reward redistribution abuse), and
- Inflates the operator's weight in weighted-random proposer selection and Gini-based validator demotion thresholds, letting a single collateral amount count as if it were staked twice — a form of stake-weight inflation analogous to balance double counting from unchecked duplicate "locations".

This is a concrete, consensus-relevant value-redirection bug (not merely cosmetic), matching the required "reward redirection" / unauthorized value movement criteria.

### Likelihood Explanation
Registering CN entries in AddressBook is restricted to the AddressBook's governance/admin workflow (not an arbitrary EOA), so this requires a validator/CN operator with registration rights — the same class of actor implicated in the original report (a permissioned but error-prone action). Given that `registerCnStakingContract` never validates uniqueness of the staking-contract or reward address across different node IDs, this can happen either through operator error (registering the same staking contract twice under different node identities) or deliberate action by a validator seeking extra reward weight. Because Kaia's council registration process does not appear to cross-check `StakingContracts`/`RewardAddrs` uniqueness anywhere downstream (`getter.go`, `staking_info.go`), nothing in the pipeline would catch or reject such a duplicate before it affects reward math and proposer weighting.

### Recommendation
Add duplicate checks for `_cnStakingContractAddress` and `_cnRewardAddress` in `registerCnStakingContract` (and its production AddressBook equivalent), rejecting registration if the staking-contract address (or reward address, if that is not an intentional many-to-one design) is already associated with a different `cnNodeId`. As defense-in-depth, `kaiax/staking` (`parseCallResult`/`parsePermissionlessCallResult`) and/or `StakingInfo.consolidateNodes()` should also detect and reject (or safely dedupe) repeated `StakingContracts` entries across different `RewardAddrs`, since a single native-token balance being represented as stake for multiple validators is invalid input regardless of how it arose on-chain.

### Proof of Concept
1. Deploy/activate AddressBook (as in `contracts/testing/reward/AddressBookMock.sol`).
2. Call `registerCnStakingContract(N1, S, R1)` — succeeds (unique `N1`).
3. Call `registerCnStakingContract(N2, S, R2)` with the same staking contract `S` but a different node id `N2` and different reward address `R2` — succeeds, because only `cnNodeIdList` uniqueness is checked [2](#0-1) .
4. Fund `S` with balance `A`.
5. `kaiax/staking.GetStakingInfo` returns `StakingContracts=[S,S]`, `StakingAmounts=[A,A]`, `RewardAddrs=[R1,R2]`.
6. `StakingInfo.consolidateNodes()` produces two separate consolidated nodes, each carrying stake amount `A` (total `2A` counted from a single collateral of `A`) [1](#0-0) .
7. This inflated total feeds `assignStakingRewards`, doubling the effective reward share attributable to the colluding operator relative to actual collateral locked [5](#0-4) .

Note: I was unable to locate the production (non-mock, non-test) `AddressBook.sol` source file in the indexed codebase (only `AddressBookMock.sol` and generated bindings were found); the analysis above assumes the production contract's `registerCnStakingContract` follows the same uniqueness-check pattern shown in the mock and reflected by the downstream `kaiax/staking` parsing logic. Confirming the exact production contract logic would require a full repository session, since the index may not include all Solidity system-contract sources.

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]
		} else {
			cmap[r] = &consolidatedNode{
				NodeIds:          []common.Address{n},
				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}

func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining

func collectStakingAmounts(nodes []common.Address, si *staking.StakingInfo) map[common.Address]float64 {
	cns := si.ConsolidatedNodes()
	stakingAmounts := make(map[common.Address]float64, len(nodes))
	for _, node := range nodes {
		stakingAmounts[node] = 0
	}
	for _, cn := range cns {
		for _, node := range cn.NodeIds {
			if _, ok := stakingAmounts[node]; ok {
				stakingAmounts[node] = float64(cn.StakingAmount)
			}
		}
	}
	return stakingAmounts
}
