### Title
Permissionless `BandwidthManager.purchase()` Lets an Attacker Evict a Victim's Prepaid Bandwidth via FIFO-Cap Spam - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` stores each `(app_chain, app)` bandwidth balance as a fixed-capacity (1024) FIFO list of `Subscription` entries. `push_subscription()` unconditionally evicts the **oldest** entry — regardless of its remaining value — whenever a new purchase arrives on a full list [1](#0-0) . Because `BandwidthManager.purchase()` on the EVM side is fully permissionless — any caller can target an arbitrary `app` identifier with the cheapest configured tier and `months = 1` — an attacker can pay for 1024 trivial purchases against a victim's `app` to force-evict the victim's legitimately-paid, unconsumed, higher-value subscription before it is ever drained by the gate. This is the direct analog of the reported bug class: spamming many small, low-value entries into an ordered/queued on-chain structure to force out or starve a legitimate high-value entry.

### Finding Description
`purchase()` in `evm/src/apps/BandwidthManager.sol` performs no ownership or rate-limiting check on the `app` parameter — it is caller-supplied `bytes`, validated only for non-emptiness [2](#0-1) . Any address can dispatch a `BandwidthPurchaseMsg` crediting bandwidth to *any* `(chain, app)` pair, as documented for the sponsorship feature [3](#0-2) .

On the Hyperbridge side, `on_accept` in `pallet-bandwidth` processes every valid purchase message by calling `push_subscription`, which appends to the `(app_chain, app)` list [4](#0-3) . The append logic is:

```rust
let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
    let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
        Some(list.remove(0))
    } else {
        None
    };
    let _ = list.try_push(new_sub);
    evicted
});
``` [5](#0-4) 

This eviction is purely positional (index 0 = oldest by insertion time), with **no check on `remaining_bytes`, `expires_at`, or the paid value of the entry being evicted**. The documentation explicitly frames this as expected only under "pathological repeat-buy behavior" [6](#0-5) , but nothing prevents a third party — not the app owner — from triggering that behavior against someone else's `app` key.

The gate (`try_consume`) also only drains from the head and has no way to recover an evicted subscription — once popped, its `remaining_bytes` are gone, only recorded via a best-effort `SubscriptionEvicted` event [7](#0-6) .

**Attack path:**
1. Victim (a legitimate app) purchases a large tier (e.g. `TierFour`, $1000 for 8MB over a long duration) for `app = victimApp` on `chain = X`. This becomes the sole/oldest entry in `Allowance[X][victimApp]`.
2. Attacker, with no privileged role, repeatedly calls `BandwidthManager.purchase(victimApp, TierOne, 1, "EVM-X")` — the cheapest configured tier — 1023 more times (or fewer, if other purchases already exist), filling the FIFO list to the 1024 cap.
3. On purchase #1025 (any further purchase, even a tiny one from the attacker or an innocent third party), `push_subscription` evicts index 0 — the victim's large, unconsumed, legitimately-paid subscription — deleting its `remaining_bytes` permanently.
4. The victim's app, which had already paid for and expected to use that bandwidth, now has none, while dispatches continue to be metered and rejected by the gate `NoAllowance`/`Insufficient` [8](#0-7) .

No existing guard stops this: `purchase()` has no per-caller cap, no minimum tier-to-evict-value check, and `push_subscription` performs positional eviction with no value-aware ordering.

### Impact Explanation
This causes a genuine, permanent **loss of prepaid funds** for a legitimate protocol user: bandwidth that was purchased and paid for in real fee-tokens is destroyed on-chain with no refund path, purely by a third party's unrelated purchase transactions targeting the same `app` identifier. This falls within the bounty's "stealing or loss of funds" and "logic attack" categories — it does not require a malicious relayer, prover, or admin; it is reachable by any unprivileged EVM account calling a public entrypoint.

### Likelihood Explanation
The `app` field is public information (typically a known contract/module address), so an attacker can trivially target any specific victim. The attack requires no privileged role, no race condition, and no protocol collusion — only repeated calls to `purchase()` paying the cheapest configured tier price. The cost to the attacker is bounded and known in advance (≈1024 × cheapest tier price), while the value destroyed can be arbitrarily larger (any unconsumed higher tier balance), making this economically viable as a targeted griefing/sabotage tool against competitors or as leverage in a dispute.

### Recommendation
- Track the `Allowance` list by *value-weighted* rather than purely positional FIFO, or refuse to evict an entry that is not the smallest/oldest-relative-to-value, or refuse new pushes past the cap rather than silently evicting (fail purchase with an error instead, forcing the caller to wait for natural expiry/drain).
- Alternatively, restrict `push_subscription`'s implicit eviction to entries that are already substantially drained, or add an owner-gated/rate-limited purchase path (e.g., require `msg.sender == app` or an authorized sponsor list) so unrelated addresses cannot inflate a victim's own subscription queue.
- At minimum, cap purchase frequency per `(chain, app)` per block/timeframe, and emit a governance-actionable alert well before 1024 entries are reached (early-warning threshold) so victims can react before eviction occurs.

### Proof of Concept
1. Governance configures `TierOne` (cheap) and `TierFour` (expensive) via `set_tier` + `dispatch_set_tiers`.
2. Victim calls `BandwidthManager.purchase(victimApp, TierFour, 12, "EVM-X")`, crediting a large, long-lived subscription as entry #1 in `Allowance["EVM-X"][victimApp]`.
3. Attacker scripts 1023 calls to `BandwidthManager.purchase(victimApp, TierOne, 1, "EVM-X")`, filling the list to `MAX_SUBSCRIPTIONS = 1024`.
4. Attacker (or anyone) issues one more `purchase(victimApp, TierOne, 1, "EVM-X")`. `push_subscription` executes `list.remove(0)`, evicting the victim's `TierFour` entry (`SubscriptionEvicted { lost_bytes: <TierFour bytes> }` is emitted) even though it had not expired and had full `remaining_bytes`.
5. Victim's subsequent dispatches through the ISMP router now hit `BandwidthGate::try_consume` against depleted/absent allowance and fail with `GateError::NoAllowance` / `Insufficient`, despite having paid in full. [9](#0-8) [2](#0-1)

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```
