## Title
`StakesCache::check_and_store` fails to evict stale vote/stake delegation entries when an account's owner changes away from the Vote/Stake program - (File: `runtime/src/stakes.rs`)

### Summary
The HydraDX report describes a bug class where a "removed" entity's historical data survives in a derived cache/oracle, and later gets blended with fresh data once the entity is re-established, producing an incorrect aggregate value. The closest verified Agave analog is `StakesCache::check_and_store` in `runtime/src/stakes.rs`, which is the bank-level cache of vote accounts and stake delegations used to compute stake weights, leader schedules, and rewards. This function only evicts a cached vote/stake entry when the account's lamports go to zero, or when the account is still owned by the vote/stake program but fails to deserialize. If the account's owner changes away from the vote or stake program while lamports remain non-zero, neither branch fires, and the previous (now-stale) `VoteAccount`/`StakeAccount` entry is left in the `Stakes<StakeAccount>` cache indefinitely.

### Finding Description
`StakesCache::check_and_store` contains an explicit, acknowledged TODO documenting this gap: [1](#0-0) 

```rust

    // and so should be removed from cache as well.
    if account.lamports() == 0 {
        ...
        return;
    }
    ...
    if solana_vote_program::check_id(owner) { ... }
    else if stake_program::check_id(owner) { ... }

``` [2](#0-1) 

This is called on every processed transaction from `Bank::update_stakes_cache`: [3](#0-2) 

The gap is directly exercised by an existing regression test that documents the exact broken invariant (with `check_owner_change` deliberately left disabled): [4](#0-3) [5](#0-4) 

In that test, after `vote_account.set_owner(bogus_vote_program)` (and non-zero lamports), `bank.vote_accounts().len()` is still `1` — i.e. the stale, previously-cached `VoteAccount`, corresponding to a pubkey that is *no longer* actually a valid vote account on-chain, is still returned by the cache. The corrupted value is the in-memory `Stakes<StakeAccount>.vote_accounts` / `stake_delegations` map held by `StakesCache`, which the runtime treats as ground truth for stake-weighted computations (`Bank::vote_accounts()`, `_load_vote_and_stake_accounts`, leader-schedule/epoch-stakes derivation) without re-validating against the live account each time — exactly analogous to the Oracle in the HydraDX report continuing to serve stale price data after the underlying asset's on-chain state changed.

The existing guard (`check_and_store`'s zero-lamport branch) only stops the "clean removal via draining to zero lamports" path; it does not stop the "owner changed while non-zero-lamports" path, which is precisely the gap the TODO calls out.

### Impact Explanation
If a pubkey previously registered as a vote or stake account can have its owner changed away from the vote/stake program while retaining non-zero lamports, and this owner change is not observed by `check_and_store`, the `StakesCache` will continue reporting on-chain-stale vote/stake data. Because bank-level `Stakes` feed directly into consensus/reward-relevant computations (stake weighting, `EpochStakes`, leader schedule derivation via `_load_vote_and_stake_accounts`), a persistently stale entry can misrepresent real stake distribution — the exact "value leak / incorrect state used" impact the judge in the HydraDX report attributed Medium severity to. `InvalidCacheEntryReason::WrongOwner` in the same file confirms the runtime is aware such "wrong owner but still cached" entries can exist and must be filtered defensively elsewhere (`_load_vote_and_stake_accounts` does check `vote_account.owner() != &solana_vote_program`), but that defensive check is not present everywhere the cache is consumed (e.g. plain `stakes.vote_accounts()` reads elsewhere in the codebase), so any consumer that trusts the cache without an owner re-check inherits the stale value.

### Likelihood Explanation
I was not able to fully verify, given the remaining tool budget, whether a permissionless/unprivileged transaction path exists in current Agave to change a vote or stake account's owner field away from the vote/stake program while the account retains non-zero lamports (normal Solana runtime semantics restrict owner-field mutation to the current owning program, and neither the vote nor stake program appears to expose a "reassign owner" instruction in the code I inspected). The existing test in `runtime/src/bank/tests.rs` constructs this scenario only via direct `bank.store_account()` (test-only bypass of instruction processing), not via a submitted transaction, so I cannot confirm this is reachable by an ordinary user-submitted transaction/CPI today. This uncertainty is the main open question for confirming exploitability; the code-level gap and the developers' own acknowledgment (TODO + `evict_invalid_stakes_cache_entries` feature flag referenced in `feature-set/src/lib.rs`) are, however, clearly documented in the codebase.

### Recommendation
- Confirm whether any current instruction path (system program `Assign`/`AssignWithSeed`, CPI-based reassignment, or a future loader) can change a vote/stake-owned account's owner field while lamports remain non-zero.
- If such a path exists (or could exist via a future program), extend `StakesCache::check_and_store` to explicitly evict the cached entry whenever the current owner is neither the vote program nor the stake program, regardless of lamport balance, rather than only on the zero-lamports path.
- Ensure every direct consumer of `Stakes::vote_accounts()` / `stake_delegations()` re-validates account owner (as `_load_vote_and_stake_accounts` already does) until the cache itself is hardened, and consider fully enabling/relying on the `evict_invalid_stakes_cache_entries` feature-gated behavior referenced in `feature-set/src/lib.rs` as the authoritative fix.

### Proof of Concept
Local evidence (not a fully-verified live-transaction exploit, but a code-level demonstration of the stale-cache condition): [6](#0-5) 

`check_stake_vote_account_validity` sets `vote_account.set_owner(bogus_vote_program)` while lamports remain at `original_lamports` (non-zero) and stores it via `bank.store_account`. Subsequent calls confirm `bank.vote_accounts().len()` still reports the stale entry as valid (count `1` rather than `0`), demonstrating that `StakesCache::check_and_store`'s owner-independent eviction path is the only thing preventing this, and it is not triggered for non-zero-lamport owner changes — mirroring the HydraDX Oracle bug where stale historical data persisted in a cache after the underlying entity's real state diverged.

    /// a bank-level cache of vote accounts and stake delegation info
    fn update_stakes_cache(
        &self,
        txs: &[impl SVMMessage],
        processing_results: &[TransactionProcessingResult],
    ) {
        debug_assert_eq!(txs.len(), processing_results.len());
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();
        txs.iter()
            .zip(processing_results)
            .filter_map(|(tx, processing_result)| {
                processing_result
                    .processed_transaction()
                    .map(|processed_tx| (tx, processed_tx))
            })
            .filter_map(|(tx, processed_tx)| {
                processed_tx
                    .executed_transaction()
                    .map(|executed_tx| (tx, executed_tx))
            })
            .filter(|(_, executed_tx)| executed_tx.was_successful())
            .flat_map(|(tx, executed_tx)| {
                let num_account_keys = tx.account_keys().len();
                let loaded_tx = &executed_tx.loaded_transaction;
                loaded_tx.accounts.iter().take(num_account_keys)
            })
            .for_each(|(pubkey, account)| {
                // note that this could get timed to: self.rc.accounts.accounts_db.stats.stakes_cache_check_and_store_us,
                //  but this code path is captured separately in ExecuteTimingType::UpdateStakesCacheUs
                self.stakes_cache.check_and_store(
                    pubkey,
                    account,
                    new_warmup_cooldown_rate_epoch,
                    use_fixed_point_stake_math,
                );
            });
    }

fn check_stake_vote_account_validity<F>(check_owner_change: bool, load_vote_and_stake_accounts: F)
where
    F: Fn(&Bank) -> StakeDelegationsMap,
{
    let validator_vote_keypairs0 = ValidatorVoteKeypairs::new_rand();
    let validator_vote_keypairs1 = ValidatorVoteKeypairs::new_rand();
    let validator_keypairs = vec![&validator_vote_keypairs0, &validator_vote_keypairs1];
    let GenesisConfigInfo { genesis_config, .. } = create_genesis_config_with_vote_accounts(
        1_000_000_000,
        &validator_keypairs,
        vec![LAMPORTS_PER_SOL; 2],
    );
    let bank = Arc::new(Bank::new_from_genesis(
        &genesis_config,
        Arc::<RuntimeConfig>::default(),
        Vec::new(),
        None,
        ACCOUNTS_DB_CONFIG_FOR_TESTING,
        None,
        None,
        Arc::default(),
        None,
        None,
    ));
    let vote_and_stake_accounts = load_vote_and_stake_accounts(&bank);
    assert_eq!(vote_and_stake_accounts.len(), 2);

    let mut vote_account = bank
        .get_account(&validator_vote_keypairs0.vote_keypair.pubkey())
        .unwrap_or_default();
    let original_lamports = vote_account.lamports();
    vote_account.set_lamports(0);
    // Simulate vote account removal via full withdrawal
    bank.store_account(
        &validator_vote_keypairs0.vote_keypair.pubkey(),
        &vote_account,
    );

    // Modify staked vote account owner; a vote account owned by another program could be
    // freely modified with malicious data
    let bogus_vote_program = Pubkey::new_unique();
    vote_account.set_lamports(original_lamports);
    vote_account.set_owner(bogus_vote_program);
    bank.store_account(
        &validator_vote_keypairs0.vote_keypair.pubkey(),
        &vote_account,
    );

    assert_eq!(bank.vote_accounts().len(), 1);

    // Modify stake account owner; a stake account owned by another program could be freely
    // modified with malicious data
    let bogus_stake_program = Pubkey::new_unique();
    let mut stake_account = bank
        .get_account(&validator_vote_keypairs1.stake_keypair.pubkey())
        .unwrap_or_default();
    stake_account.set_owner(bogus_stake_program);
    bank.store_account(
        &validator_vote_keypairs1.stake_keypair.pubkey(),
        &stake_account,
    );

    // Accounts must be valid stake and vote accounts
    let vote_and_stake_accounts = load_vote_and_stake_accounts(&bank);
    assert_eq!(
        vote_and_stake_accounts.len(),
        usize::from(!check_owner_change)
    );
}
