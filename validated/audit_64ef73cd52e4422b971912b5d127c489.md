This confirms it: `GetParamSet(blockNum)` always resolves to the ParamSet as of `prevEpochStart` — i.e., it never reflects votes cast earlier in the *same* epoch [1](#0-0) . Every `KIP71LowerBoundBaseFee`/`KIP71UpperBoundBaseFee` vote's consistency check therefore compares the *new* voted value only against the stale, epoch-start snapshot of the paired bound, not against any other vote for the paired parameter that lands in the same epoch.

### Title
Insufficient KIP-71 bound consistency validation allows lowerBoundBaseFee > upperBoundBaseFee within a single epoch - (File: kaiax/gov/headergov/impl/header.go)

### Summary
`checkConsistency()` validates a `kip71.lowerboundbasefee` or `kip71.upperboundbasefee` vote against the *currently active* `ParamSet` (i.e., the value fixed at the start of the current epoch), not against the pending/new value of the counterpart parameter that may be voted on within the same epoch. This mirrors the ZNSCurvePricer bug class: a boundary/invariant check is performed against the wrong reference point (an outdated value analogous to checking `maxLength-1` instead of `maxLength`), letting an individually-valid vote combine into a governance state that violates the intended invariant `lowerBoundBaseFee <= upperBoundBaseFee`.

### Finding Description
In `checkConsistency`, the two relevant cases are: [2](#0-1) 

Both checks call `h.GetParamSet(blockNum)`, which is defined to search back to `PrevEpochStart(blockNum, ...)` [3](#0-2)  — the parameter snapshot from the beginning of the *current* epoch, before any votes cast in this same epoch have taken effect. Governance votes accumulate throughout an epoch and are only aggregated and applied together at the next epoch boundary via `getExpectedGovernance()` [4](#0-3) .

Consequently, two different validator votes cast in different blocks of the same epoch — one lowering `upperBoundBaseFee` and one raising `lowerBoundBaseFee` — are each checked independently against the epoch-start values, and each can pass individually even though their *combination* produces `lowerBoundBaseFee > upperBoundBaseFee` once both are aggregated into governance at the epoch boundary.

### Impact Explanation
The resulting KIP-71 config is consumed directly by `NextMagmaBlockBaseFee` to compute the next block's base fee [5](#0-4) . An inverted bound configuration (`lowerBoundBaseFee > upperBoundBaseFee`) breaks the clamp logic's assumptions (parent-baseFee clamping and the increase/decrease branches), which can yield inconsistent or diverging base-fee calculations across nodes reconstructing the same header, or a governance state that is nonsensical and inconsistent with the on-chain fee mechanism's intended monotonic bound invariant — a state-divergence/DoS-adjacent governance-parameter integrity issue reachable purely by two validator votes submitted within one epoch (no privileged/off-chain access required beyond normal validator voting rights).

### Likelihood Explanation
Requires two governance votes (or a single voter changing votes) within the same epoch targeting `kip71.lowerboundbasefee` and `kip71.upperboundbasefee` in a specific order — this is achievable by any council member entitled to vote, using the standard `governance_vote` / `PrepareHeader` vote flow, and does not require compromising consensus or exploiting a separate bug elsewhere. However, it does require validator/council voting rights, and unintentional occurrence would only happen if governance operators pick conflicting values; there's no indication of additional exploitation value beyond breaking the base-fee bound invariant.

### Recommendation
When validating a `Kip71LowerBoundBaseFee` or `Kip71UpperBoundBaseFee` vote, incorporate any pending vote for the counterpart parameter already cast earlier in the same epoch (e.g., via `GetPartialParamSet`/`groupedVotes` for the current epoch) rather than only the epoch-start `ParamSet`, so the final aggregated pair is validated for `lowerBoundBaseFee <= upperBoundBaseFee` before either vote is accepted.

### Proof of Concept
1. Epoch starts with `LowerBoundBaseFee = 25e9`, `UpperBoundBaseFee = 750e9` (in the active `ParamSet`).
2. In block N (within the epoch), a validator submits vote `kip71.lowerboundbasefee = 700e9`. `checkConsistency` compares `700e9 > params.UpperBoundBaseFee (750e9)` → false → vote accepted.
3. In block M > N (same epoch), a validator submits vote `kip71.upperboundbasefee = 650e9`. `checkConsistency` compares `650e9 < params.LowerBoundBaseFee (still 25e9, unaffected by the block-N vote)` → false → vote accepted.
4. At the next epoch boundary, `getExpectedGovernance` aggregates both votes into `PartialParamSet{LowerBoundBaseFee: 700e9, UpperBoundBaseFee: 650e9}`, producing a config where `LowerBoundBaseFee (700e9) > UpperBoundBaseFee (650e9)`, violating the intended KIP-71 invariant, despite each individual vote having passed validation.

func PrevEpochStart(blockNum, epoch uint64, isKore bool) uint64 {
	if blockNum <= epoch {
		return 0
	}
	if !isKore {
		blockNum -= 1
	}
	return blockNum - blockNum%epoch - epoch

func (h *headerGovModule) getExpectedGovernance(blockNum uint64) headergov.GovData {
	prevEpochIdx := calcEpochIdx(blockNum, h.epoch) - 1
	prevEpochVotes := h.getVotesInEpoch(prevEpochIdx)
	govs := make(gov.PartialParamSet)

	sortedVoteBlocks := slices.Collect(maps.Keys(prevEpochVotes))
	slices.Sort(sortedVoteBlocks)

	for _, voteBlock := range sortedVoteBlocks {
		vote := prevEpochVotes[voteBlock]
		govs.Add(string(vote.Name()), vote.Value())
	}

	// assert(len(headergov.NewGovData(govs).Items()) == len(govs))
	return headergov.NewGovData(govs)
}
