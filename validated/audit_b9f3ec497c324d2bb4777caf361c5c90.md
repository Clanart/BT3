### Title
FROST IetfTranscript drops all names, labels, and domain separation — signatures carry no context binding and are replayable across protocols - ([File: crypto/frost/src/algorithm.rs](crypto/frost/src/algorithm.rs))

### Summary
The bug class is "signed data lacks context/origin binding, so the signer cannot tell what the signature commits to." Serai's analog is concrete: the `IetfTranscript` used by `IetfSchnorr` (and therefore by the Bitcoin `Schnorr` algorithm in `networks/bitcoin/src/crypto.rs`) discards the transcript name, ignores every label, makes `domain_separate` a no-op, and returns the raw concatenated message bytes as the "challenge". The resulting Schnorr/BIP-340 signature challenge binds only `(R, A, m)` — never the protocol, purpose, or origin that requested the signature.

### Finding Description
`IetfTranscript` implements `Transcript` as a flat byte buffer:

- `Transcript::new(_)` discards the name (`IetfTranscript(vec![])`), at `crypto/frost/src/algorithm.rs:107-109`.
- `domain_separate(_)` is a no-op, at `crypto/frost/src/algorithm.rs:111`. This means the `domain_separate(b"FROST")` call in `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:317`) silently does nothing under this algorithm.
- `append_message` extends the buffer with only the message value, dropping the label (`crypto/frost/src/algorithm.rs:113-115`), and `challenge(_)` returns the raw concatenation (`algorithm.rs:117-119`).

Consequently the `rho_transcript` built in `sign` (`crypto/frost/src/sign.rs:362-368`) has no domain separation either — its challenge is just `group_key_bytes || hash_msg(msg) || hash_commitments(...)`, and the "merge" of it back into the global transcript is again raw concatenation. The final signature challenge `c = H::hram(R, A, msg)` (`crypto/frost/src/algorithm.rs:208`) binds nothing except the raw `msg` bytes supplied by the caller of `SignMachine::sign` (`crypto/frost/src/sign.rs:237-241`), which can be arbitrary attacker-controlled bytes.

For the Bitcoin instantiation, `networks/bitcoin/src/crypto.rs:56-74` defines `Hram` as a pure BIP-340 tagged hash of `R || A || m`, and `Schnorr::new()` (`crypto.rs:89-91`) wraps `FrostSchnorr::ietf()`. Any FROST signing session therefore emits a canonical BIP-340 signature valid in *every* context that accepts a BIP-340 signature of the threshold key over those bytes — there is no mechanism to bind the signature to a network, transaction type, session ID, or requesting party.

### Impact Explanation
A coordinator or any party able to supply the `msg` argument to `sign` can obtain a signature that is valid far beyond the context the signer intended. Because nothing in the transcript or the HRAm binds a domain/purpose:

- A signature requested for protocol A (e.g., an internal attestation over 32 bytes) is a valid BIP-340 Schnorr signature under the group key in protocol B (e.g., a Taproot key-path spend or a DLC adaptor context) whenever `A` can be induced to sign bytes that `B` accepts. This is a cross-protocol signature replay enabled by missing domain separation — the signer cryptographically commits to opaque bytes with no origin/context, exactly the "user cannot identify what they are signing" defect generalized to machine signers.
- Two distinct logical signing sessions (different `IetfTranscript` names, different domain separators the caller may attempt) produce identical challenges when participants, preprocesses, and `msg` collide, since names and separators are discarded — an undocumented transcript collision class introduced by this transcript implementation.

This meets the bar of "signing of an unintended message" + "undocumented transcript collision": the signature's semantic scope is unrestricted despite the `Transcript` API advertising `new(name)`/`domain_separate` as safety mechanisms (`crypto/transcript/src/lib.rs:32-35`).

### Likelihood Explanation
Medium. The attacker needs to influence the `msg` passed to `sign`, which is the normal role of the session coordinator / whichever component constructs the signing payload — an unprivileged party in the threat model ("messages or transaction data they cause to be signed"). The prerequisite is a second protocol accepting BIP-340/Schnorr signatures of the same group key over attacker-chosen bytes, which is realistic for a threshold-key wallet (the same key signs transactions and arbitrary `sign`-requests). Exploitation requires no malicious validators, no collusion, and no leaked keys — only a chosen-message signing oracle, which the API inherently provides.

### Recommendation
- In `IetfTranscript`, honor the contract of `Transcript`: incorporate `name` on construction, include labels in `append_message` (with length framing), and make `domain_separate` a real delimiter. If IETF-draft compatibility forbids changing the rho hash, document loudly that `IetfSchnorr` produces context-free signatures.
- At the `SignMachine::sign` API surface, require a caller-supplied `context`/`domain` byte string that is appended to the algorithm transcript before participants are committed (`crypto/frost/src/sign.rs:315-318`), so every signature is bound to its requesting purpose.
- For the Bitcoin algorithm, consider prefixing `msg` in `Hram::hram` with an application domain tag when the session is not strictly a BIP-340 spend, preventing raw-byte signatures from being valid outside the intended purpose.

### Proof of Concept
Conceptual trace:

1. A coordinator runs `AlgorithmSignMachine::sign` with `Schnorr::new()` (Bitcoin), submitting `msg = X` where `X` is a byte string valid as a message in an unrelated BIP-340-accepting protocol (e.g., a `sha256` digest of an external statement, or a `Sighash` from a different, attacker-constructed transaction).
2. In `sign`, `domain_separate(b"FROST")` no-ops (`algorithm.rs:111`), the rho transcript name `"FROST_rho"` is discarded (`algorithm.rs:107-109`), so all challenges are functions of raw concatenated bytes only.
3. `sign_share` computes `c = hram(R, A, X)` = tagged `sha256(R || A || X)` (`crypto.rs:59-69`) — identical to a standalone BIP-340 challenge for `X`.
4. `verify` returns a 64-byte BIP-340 signature (`crypto.rs:139-149`) that verifies under the group key for `X` in any context — including ones the signing nodes never saw or authorized, since neither the transcript nor the challenge binds the request's origin or purpose.

The signature is byte-for-byte identical to what a context-binding protocol would have produced only if the context were part of `msg`; the library places that obligation entirely on the caller while the `Transcript` API's name/label/domain parameters — which exist precisely for this binding — are silently discarded.
