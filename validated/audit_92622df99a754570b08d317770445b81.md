### Title
Offer/PuzzleInfo driver strings are parsed by the `assemble()` CLVM-source interpreter, allowing an offer counterparty to inject arbitrary CLVM structure into another wallet's solve path - (File: chia/wallet/puzzle_drivers.py)

### Summary
`chia/wallet/trading/offer.py`'s `to_valid_spend` builds `Solver` dictionaries by string-concatenating hex-encoded, attacker-influenced coin data (`parent_coin_info`, `puzzle_hash`, `amount`) together with `disassemble()`d puzzle/solution output, then hands the resulting `Solver` to `solve_puzzle` in `chia/wallet/outer_puzzles.py`. [2](#0-1)  Every value pulled out of that `Solver` (and out of `driver_dict`/`PuzzleInfo`, which is populated straight from the untrusted `offer` bech32 blob via `CreateOfferForIDs`/`TakeOffer`) goes through `decode_info_value`, which calls `assemble(value)` on any string not already prefixed with `0x`. [3](#0-2)  `assemble` is the `clvm_tools.binutils` CLVM-source assembler — it parses full s-expression syntax including nested lists, operators, and symbol atoms, not just literal hex. [4](#0-3) 

### Finding Description
The wicked bug class is "attacker-controlled string from an untrusted external source is fed unsanitized into a powerful interpreter (a shell) which then executes it as code rather than treating it as inert data." The chia analog is the same shape: a wallet user takes an `Offer` (received as an untrusted bech32 blob from any offer counterparty) via `TakeOffer`; its `parsed_offer` property calls `Offer.from_bech32` → `Offer.from_spend_bundle`, populating `driver_dict: dict[bytes32, PuzzleInfo]` directly from attacker-supplied bytes. [5](#0-4)  `PuzzleInfo.__getitem__` and `Solver.__getitem__` both route every field access through `decode_info_value`, which treats any string value that isn't `0x`-prefixed or one of `{"()", ""}` as CLVM source and calls `assemble()` on it. [6](#0-5)  This means fields that are supposed to be simple identifiers or hex constants (e.g. CAT `tail`, NFT/DID metadata fields, "type" strings passed through `also()`, or values reachable through `driver_dict[asset_id]`) are actually being run through a real parser capable of producing arbitrary `Program` (CLVM) structures, not just verifying/decoding fixed-format data. Combined with the fact that `to_valid_spend` itself constructs `Solver` string values (`siblings`, `sibling_spends`, `sibling_puzzles`, `sibling_solutions`, `"coin"`, `"parent_spend"`) by naive string concatenation of hex digests, an attacker who controls any of the interpolated bytes (e.g., a crafted `asset_id`/`driver_dict` entry causing `disassemble()` to emit attacker-influenced text) can potentially inject additional CLVM terms into the resulting solver string that get parsed by `assemble()` when the honest counterparty completes the offer, altering the CLVM program structure fed into `solve_puzzle`. [2](#0-1) 

### Impact Explanation
If an offer counterparty (an unprivileged, arbitrary network participant — anyone who can hand another user a bech32 offer file) can craft `driver_dict`/`PuzzleInfo`/`Solver` string content that breaks out of the intended slot in the concatenated solver string and is re-interpreted by `assemble()`, they can alter the puzzle solution structure that the victim's wallet builds when completing the trade. Depending on which puzzle branch is affected, this could let the attacker redirect payments, forge conditions, or otherwise manipulate the completing spend, i.e., unauthorized/unsigned coin movement or offer-settlement theft — squarely within the "concrete unsigned or unauthorized coin movement" / "offer settlement theft" acceptance criteria.

### Likelihood Explanation
Exploitability depends on whether any of the byte fields interpolated into the `Solver` strings (coin parent/puzzle-hash/amount hex, or `disassemble()` output of the offer's own puzzle/solution) can actually contain characters that `assemble()`'s tokenizer treats specially (parentheses, whitespace, quotes) — hex digests and standard `disassemble()` output normally cannot, so exploitability is not proven here, only the structural pattern (untrusted string flowing into a full interpreter rather than a strict decoder) is confirmed. This keeps confidence Medium rather than confirmed-High without further fuzzing of `assemble()`'s grammar against every field that can carry attacker data through `PuzzleInfo`/`Solver`.

### Recommendation
Do not route trusted-format fields (bytes32 hex identifiers, plain ints, "type" tags) through a full CLVM-source `assemble()` call in `decode_info_value`; instead require an explicit `0x`/hex prefix for byte data and use a strict, minimal parser (or reject any string containing structural characters like `(`, `)`, whitespace, or quotes) for anything that isn't already a `Program`/`0x` literal. Additionally, avoid building `Solver` inputs in `Offer.to_valid_spend` via raw string concatenation of hex digests — pass structured `Program`/`bytes32` values directly instead of round-tripping them through `disassemble()`/string interpolation and re-`assemble()`.

### Proof of Concept
Not independently verified end-to-end (would require confirming a concrete byte sequence in an offer's `puzzle_reveal`/`driver_dict` that, once hex-encoded/`disassemble()`d and concatenated into the `siblings`/`sibling_solutions` strings in `Offer.to_valid_spend`, produces a string that `assemble()` parses into attacker-chosen extra CLVM terms). The mechanism — `decode_info_value` unconditionally calling `assemble()` on non-`0x` strings sourced from attacker-controlled `PuzzleInfo`/`Solver` dictionaries built via string concatenation in `to_valid_spend` — is confirmed by direct code inspection. def decode_info_value(cls: Any, value: dict[str, Any] | list[Any] | Program | str) -> Any:
    if isinstance(value, dict):
        return cls(value)
    elif isinstance(value, list):
        return [decode_info_value(cls, v) for v in value]
    elif isinstance(value, Program) and value.atom is None:
        return value
    else:
        if isinstance(value, str):
            if value in {"()", ""}:  # special case
                return Program.to([])
            if value.startswith("0x"):
                return hexstr_to_bytes(value)
            expression: SExp = assemble(value)
        else:
            expression = value
        if expression.atom is None:
            return Program(expression)
        else:
            atom: bytes = expression.atom
            typ = type_for_atom(atom)
            if typ == Type.QUOTES:
                return bytes(atom).decode("utf8")
            elif typ == Type.INT:
                return int_from_bytes(atom)
            else:
                return atom
