### Title
Scanner reports same-block spent Bitcoin outputs as received funds - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`Scanner::scan_transaction` identifies received funds solely by matching each transaction output's `script_pubkey` and records the resulting `OutPoint`, without checking whether another transaction in the same block spends that output. [1](#0-0)  `Scanner::scan_block` similarly accumulates every matching output across all transactions and never removes outputs consumed by later transactions. [2](#0-1)  The Bitcoin network adapter then converts each matched output directly into a protocol `Output`, with no UTXO or same-block-spend check. [3](#0-2) 

### Finding Description
The bug class maps to Serai's Bitcoin deposit-recognition path: an unprivileged party can submit two transactions in one block, where the first pays a scanned Serai address and the second immediately spends that output. `scan_transaction` examines only `tx.output`, derives `ReceivedOutput` from the matching script and `(txid, vout)`, and ignores `tx.input` across the block. [4](#0-3)  Consequently, the scanner reports an output that is already spent and cannot later be used as a `SignableTransaction` input.

The Bitcoin integration skips only the coinbase transaction for maturity purposes; it does not compensate for regular transaction spends in the same block. [5](#0-4)  Each reported `ReceivedOutput` is intended to be spendable, as `SignableTransaction::new` converts its outpoint and output value directly into a transaction input. [6](#0-5) 

### Impact Explanation
An attacker can cause Serai to report funds as received even though the funds are no longer spendable. The resulting deposit may trigger downstream accounting or execution based on a UTXO that cannot actually be spent by the threshold wallet. This matches the accepted impact of funds reported received that are not spendable.

### Likelihood Explanation
The attack only requires publishing two ordinary Bitcoin transactions in the same block: one paying a registered Serai script and one spending that output. The scanner's matching logic is deterministic and has no condition preventing this sequence. Confirmation depth does not prevent the issue because both transactions remain in the same confirmed block. [7](#0-6) 

### Recommendation
Track all spends within each scanned block and remove received outputs whose outpoints are consumed by any transaction in that block. Before emitting an output, additionally verify its current UTXO status against the Bitcoin node or otherwise account for spends observed at the accepted confirmation depth. The scanner should record received funds only when the corresponding outpoint remains unspent according to the finalized chain view.

### Proof of Concept
1. Register or identify a scanned P2TR script using `Scanner::new` or `register_offset`. [8](#0-7) 
2. In one Bitcoin block, include:
   - `tx_fund`, whose output `vout=0` pays that scanned script.
   - `tx_spend`, whose input references `OutPoint(tx_fund.txid, 0)` and sends the funds elsewhere.
3. Call `Scanner::scan_block` on the block. The loop reaches `tx_fund`, matches its output script, and appends `ReceivedOutput { offset, output, outpoint }`. [9](#0-8) 
4. When the loop reaches `tx_spend`, only its outputs are inspected; its input spending the previously reported outpoint is ignored. [4](#0-3) 
5. `get_outputs` then emits the stale `ReceivedOutput` as a received output despite it already being spent. [3](#0-2)

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
