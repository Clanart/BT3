### Title
mWOMSVBaseRewarder never applies mWomSV's cooldown/forfeit penalty, letting every mWOMSV locker claim full rewards during cooldown - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never calls `mWomSV.getRewardablePercentWAD`, unlike its sibling `vlMGPBaseRewarder._calExpireForfeit` which does wire the percentage into the forfeit calculation. As a result, `mWOMSVBaseRewarder` always treats 100% of a user's accrued rewards as rewardable and always computes a forfeit amount of `0`, regardless of whether the user is fully locked, mid-cooldown, or holds fully-unlocked (expired) mWom in a cooldown slot.

### Finding Description
`mWomSV.getRewardablePercentWAD` [1](#0-0)  computes a time-weighted percentage of a user's mWomSV balance that should still be considered "rewardable," decaying as tokens sit in cooldown or become fully unlocked. The intended design (matching `vlMGP`/`vlMGPBaseRewarder`) is that when a locked-token holder claims rewards while some of their balance is in cooldown/unlocked, only the `rewardablePercentWAD` fraction of the accrued reward is paid out and the rest is forfeited back into the pool for other stakers, via `_queueNewRewardsWithoutTransfer`.

`vlMGPBaseRewarder._calExpireForfeit` correctly implements this: [2](#0-1) 
It calls `vlMGP.getRewardablePercentWAD(_account)` and scales `_amount` by it to derive `rewardableAmount`, so `forfeitAmount = _amount - rewardableAmount` is a real, non-zero forfeiture whenever the user is not 100% rewardable.

`mWOMSVBaseRewarder._calExpireForfeit`, by contrast, is dead code: [3](#0-2) 
It sets `rewardableAmount = _amount` unconditionally (no call to `mWOMSV.getRewardablePercentWAD` at all), so `forfeitAmount = _amount - rewardableAmount` is always `0`, and the `if (rewardableAmount > _amount) revert` branch is unreachable.

This function is invoked from `_sendReward`, which is reached from `getReward`/`getRewards`, both callable only by `masterMagpie` but ultimately triggered by any user calling MasterMagpie's public claim functions for their own stake: [4](#0-3) 
No modifier, `nonReentrant` guard, or reward-index accounting compensates for this — the forfeiture math itself is simply broken, independent of access control.

### Impact Explanation
Governance's design intent (evidenced by the parallel, correctly-implemented `vlMGPBaseRewarder` and by `mWomSV.getRewardablePercentWAD` existing specifically for this purpose) is that a locker who starts unlocking (cooldown) or lets a cooldown slot fully expire should forfeit a pro-rata share of pending bonus rewards, which is redistributed to remaining lockers via `_queueNewRewardsWithoutTransfer`. Because `mWOMSVBaseRewarder` never applies this penalty, every mWOMSV locker who calls `startUnlock` (or does nothing and simply accrues fully-unlocked cooldown balances) still collects 100% of their accrued bonus rewards on every claim. This is a direct, ongoing misallocation of yield: users who should forfeit yield keep it, and users who remain fully locked (and are supposed to receive the forfeited yield) are permanently denied it. This falls under "theft or permanent freezing of unclaimed yield" — the redistribution mechanism is completely non-functional, and the loss accrues continuously and irreversibly for every reward distribution cycle.

### Likelihood Explanation
No special privileges or capital are needed — any unprivileged mWOMSV holder benefits automatically just by using the protocol normally (`lock`, optionally `startUnlock`, then claiming rewards through the standard MasterMagpie flow). The bug triggers on every single reward claim by every user with any cooldown/unlocked balance, making it 100% reliable and repeatable, not a one-off edge case.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`: call `mWOMSV.getRewardablePercentWAD(_account)` and scale `_amount` by that percentage (`rewardableAmount = _amount * rewardablePercentWAD / 1e18`) before computing `forfeitAmount`, so cooldown/expired balances correctly forfeit yield back into the pool.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `MasterMagpie`, and `mWOMSVBaseRewarder`; deploy `VLMGP` and `vlMGPBaseRewarder` with equivalent parameters for comparison.
2. Have User A lock `1000e18` tokens in each system, then call `startUnlock` for `500e18` (putting half in cooldown) in both `mWomSV` and `VLMGP`.
3. Queue identical reward amounts (e.g., `100e18`) into both `mWOMSVBaseRewarder.queueNewRewards` and `vlMGPBaseRewarder.queueNewRewards`.
4. Advance time partially into the cooldown period (before `endTime`) so `getRewardablePercentWAD` for both should return < 100%.
5. Call `getReward`/equivalent claim for User A on both rewarders (through their respective MasterMagpie flows).
6. Assert: `vlMGPBaseRewarder` pays User A less than the full `100e18 * userShare` (a nonzero forfeit is queued via `ForfeitRewardAdded`), while `mWOMSVBaseRewarder` pays User A the full un-forfeited amount and emits no meaningful forfeiture (`forfeitAmount == 0` from `calExpireForfeit`), proving the mWOMSV path systematically over-pays relative to the intended, correctly-implemented vlMGP path.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
