### Title
Hookify PreToolUse rule matching uses a hardcoded exact-string tool_name allowlist, silently bypassing `block` rules for any tool not in {Bash, Edit, Write, MultiEdit} - (File: `plugins/hookify/hooks/pretooluse.py`, `plugins/hookify/core/rule_engine.py`)

### Summary
`pretooluse.py` and `posttooluse.py` derive the rule-matching `event` bucket from `tool_name` using a hardcoded, case-sensitive equality check against only `'Bash'` and `['Edit', 'Write', 'MultiEdit']` before loading rules. `RuleEngine._matches_tool` similarly performs exact `tool_name in patterns` string comparison with no normalization. Any tool invocation whose `tool_name` is not one of these four exact strings (e.g. a different file-editing tool, or any casing variant) causes file/bash-oriented `block` rules to never be evaluated against the correct field data, because `_extract_field` also only special-cases `Bash`, `Write`/`Edit`, and `MultiEdit`.

### Finding Description
The enforcement pipeline is:
1. `pretooluse.py` reads the hook JSON (`tool_name`, `tool_input`) from stdin and computes `event` via a hardcoded mapping [1](#0-0) .
2. `load_rules(event=event)` filters which `.claude/hookify.*.local.md` rule files are even considered; if `event` doesn't match `rule.event` (and isn't `'all'`) the rule is skipped [2](#0-1) .
3. `RuleEngine._rule_matches` performs an additional exact tool_matcher check (`tool_name in patterns`, case-sensitive, no trimming) [3](#0-2) .
4. `_extract_field` extracts the field to test against the regex/condition, but only has explicit branches for `tool_name == 'Bash'`, `tool_name in ['Write','Edit']`, and `tool_name == 'MultiEdit'` [4](#0-3) .

A rule author writing a `event: file` block rule (e.g. "block any edit that adds an API key/secret pattern") reasonably expects it to cover *any* file-mutating tool call. However, because the tool_name→event mapping and the field extractor both hardcode only `Bash`/`Edit`/`Write`/`MultiEdit`, any other file-mutating tool representation (for example a notebook-editing tool, or any tool name that doesn't exactly equal one of these four strings byte-for-byte) falls through: `event` stays `None`, `load_rules(None)` loads all rules unfiltered, but `_extract_field` returns `None` for the relevant field because there is no branch handling that tool's input schema, so `_check_condition` returns `False` and the rule silently never triggers. The `block` decision path in `evaluate_rules` [5](#0-4)  is therefore never reached even though the operation is functionally identical to the one the rule intended to block.

The failure is silent: `pretooluse.py` always prints a JSON response and always `sys.exit(0)` [6](#0-5) , so there is no error or warning indicating that the rule was skipped due to the tool representation mismatch.

### Impact Explanation
A repository-embedded workflow (e.g. content that steers Claude toward using a file-editing tool other than the four hardcoded names, or any tool_name casing difference) can cause a user-authored `block` rule intended to prevent sensitive-file disclosure/mutation to be silently ignored, allowing secrets/tokens/credentials to be written, or dangerous content to reach disk/commit, without the protection the user configured. This matches the "Sensitive code, prompt, token, diff, or local file disclosure" impact category, since a diff/edit that should have been denied is instead allowed to proceed.

### Likelihood Explanation
This requires: (1) the user to have opted into hookify and defined a `block` rule for `event: file` or `event: bash`, and (2) an attacker-influenced automation flow that causes Claude to invoke a tool whose `tool_name` isn't exactly `Bash`, `Edit`, `Write`, or `MultiEdit` to perform an equivalent sensitive operation. Since hookify is an optional, community/example plugin that fails open by design (`# ALWAYS exit 0 - never block operations due to hook errors`), and the exact set of tool names is controlled by the Claude Code harness rather than free-form attacker text, this is a real logic gap in the plugin's coverage rather than a high-reliability exploit primitive; it is best characterized as a coverage/robustness bug in an advisory guardrail plugin rather than a bypass of Claude Code's core permission system.

### Recommendation
- Make tool-to-event classification and field extraction driven by rule metadata/config rather than a hardcoded 4-string allowlist; support a generic fallback (e.g. scan all string values of `tool_input` for file/bash-like rules) so unknown tool names don't silently skip evaluation.
- Normalize `tool_name` comparisons (case-insensitive, trimmed) in `_matches_tool`.
- Log/emit a `systemMessage` when a `block`-action rule's `event` cannot be resolved for the current `tool_name`, so failures are visible instead of silent.

### Proof of Concept
Unit test on `RuleEngine`/`load_rules`:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-secret-edit",
    enabled=True,
    event="file",
    action="block",
    conditions=[Condition(field="new_text", operator="contains", pattern="API_KEY")],
    message="secret leak"
)
engine = RuleEngine()

# Case 1: recognized tool -> correctly blocked
result_edit = engine.evaluate_rules([rule], {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {"file_path": "a.py", "new_string": "API_KEY=123", "old_string": ""}
})
assert result_edit.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# Case 2: equivalent file-mutation via an unrecognized tool_name -> silently NOT blocked
result_other = engine.evaluate_rules([rule], {
    "hook_event_name": "PreToolUse",
    "tool_name": "NotebookEdit",
    "tool_input": {"new_source": "API_KEY=123"}
})
assert result_other == {}   # demonstrates the bypass: no deny issued despite equivalent sensitive content
```
Expected assertion failure/success demonstrates that the identical sensitive payload is denied under `Edit` but silently allowed under any tool name outside the hardcoded `{Bash, Edit, Write, MultiEdit}` set, confirming the tool-matching coverage gap in `RuleEngine._rule_matches` / `_extract_field` and the hook scripts' `tool_name`→`event` mapping.

```python
    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
```
