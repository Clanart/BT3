## Summary

Helm's `chartutil` bug is a recursive parser that panics on adversarial nested structured input, crashing the process. The closest reachable analog in this codebase is the wallet's **puzzle-driver matching recursion**, which walks an untrusted `CoinSpend.puzzle_reveal` layer-by-layer with unbounded Python recursion. An offer counterparty (or any local RPC caller who submits/loads a crafted offer/spend bundle) can supply a `puzzle_reveal` whose curried structure nests a recognized driver shape (e.g. `CAT_MOD`, singleton, ownership, metadata, or CR layers) arbitrarily deeply, driving the wallet's puzzle-matching code into deep/unbounded Python recursion.

## Finding Description

`chia.wallet.outer_puzzles.match_puzzle()` iterates registered drivers and calls `driver.match(puzzle)` [1](#0-0) . Each driver is constructed with `function_args = (match_puzzle, construct_puzzle, solve_puzzle, get_inner_puzzle, get_inner_solution)`, so `self._match` inside every driver **is** `match_puzzle` itself [2](#0-1) .

`CATOuterPuzzle.match()`, `SingletonOuterPuzzle.match()`, `OwnershipOuterPuzzle.match()`, `MetadataOuterPuzzle.match()`, and `CROuterPuzzle.match()` all recurse into their puzzle's `inner_puzzle` via `self._match(UnknownPuzzle(known_program=inner_puzzle))` with no depth limit, purely following how deeply the supplied puzzle is curried [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) .

The structural check that decides whether a layer "matches" is shallow — e.g. `match_cat_puzzle()` only checks `puzzle.mod == CAT_MOD and puzzle.curried_args is not None`, with no requirement that the deeper structure be semantically valid or bounded [8](#0-7) . An attacker can therefore construct a `puzzle_reveal` that is `CAT_MOD` curried around another `CAT_MOD`-shaped inner puzzle, repeated thousands of times, purely to satisfy the shallow shape check at every level — it never needs to actually execute correctly.

This recursive matcher is exercised on attacker-controlled data whenever an offer is parsed: `Offer.from_spend_bundle()` calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` for every `CoinSpend` in a `WalletSpendBundle`, which is how `Offer.from_bytes()` / offer-taking / offer-summary code paths derive `driver_dict` from an offer file supplied by an offer counterparty [9](#0-8) .

## Impact Explanation

A deeply/pathologically nested `puzzle_reveal` inside an offer file (or a spend bundle passed to `create_offer_for_ids`/`respond_to_offer`/offer-validity checks) forces unbounded Python-level recursion in `match_puzzle`/driver `.match()`. This mirrors the Helm bug's root cause: a recursive parser walking attacker-supplied nested structure with no depth bound. In CPython, exceeding the recursion limit ordinarily raises `RecursionError`, but deep recursion combined with the additional C-stack frames used by property access, `uncurry()`/`as_iter()` calls, and nested `try/except` blocks in this code path can exhaust the real OS thread stack before Python's own recursion-limit check fires, producing a native stack overflow that is not catchable by any Python `except Exception:` handler and can crash the whole wallet process — exactly the "unrecoverable panic" failure mode described in the Helm advisory. Even in the milder case where a clean `RecursionError` is raised and caught by the RPC layer, it still represents a spend/offer-triggered halt of the specific transaction-processing operation (offer parsing/validation), which is unacceptable input handling for untrusted, counterparty-supplied data.

## Likelihood Explanation

Any wallet user who receives/opens an offer file from an untrusted counterparty, or a local RPC caller who submits a `driver_dict`/spend bundle through `create_offer_for_ids`/`respond_to_offer`, exercises this path. Constructing the malicious `puzzle_reveal` requires only crafting nested CLVM cons-structures satisfying a shallow curry-shape check (mod hash + argument count) at each level — no valid signatures, real cost accounting, or mempool admission is required to reach this parser, since it runs client-side during offer summarization/validation before any chain submission.

## Recommendation

Add an explicit recursion-depth (or iterative rewrite) guard to `match_puzzle()`/each outer-puzzle driver's `.match()`/`.get_inner_puzzle()`/`.solve()` chain, similar to the deliberate iterative design already used for `sha256_treehash()` [10](#0-9) . Reject or bound puzzle layer-matching depth before invoking driver recursion on any externally supplied `CoinSpend.puzzle_reveal` (offer files, RPC-submitted spend bundles/driver dicts).

## Proof of Concept

1. Build an inner puzzle `P0` (arbitrary atom).
2. Repeat N times (e.g. N = 5,000–50,000, bounded only by CLVM program byte-size limits): `Pi = CAT_MOD.curry(<tail-hash-atom>, Pi-1)` so each layer's mod hash equals `CAT_MOD_HASH` and has the 3-arg curried shape `match_cat_puzzle()` expects.
3. Place the resulting deeply nested `PN` as the `puzzle_reveal` of a `CoinSpend` inside a `WalletSpendBundle`, with `coin.parent_coin_info == bytes32.zeros` so it is treated as a requested-payment coin spend by `Offer.from_spend_bundle()`.
4. Serialize this as an offer file (`Offer(...).to_bech32()`), send it to a victim wallet, or pass an equivalent `driver_dict`/spend bundle to `create_offer_for_ids`/`respond_to_offer`.
5. When the victim wallet calls `Offer.from_bytes()` (or the RPC endpoint parses the offer/driver_dict), `match_puzzle()` recurses N levels deep through `CATOuterPuzzle.match()` → `self._match` → `match_puzzle` → ..., exceeding the interpreter's safe recursion depth and triggering a `RecursionError` or native stack overflow, halting or crashing the wallet's offer-processing path.

**Note on residual uncertainty:** I was not able to fully verify, within the tool budget, whether `chia/rpc/rpc_server.py`'s outer exception handling for RPC endpoints reliably catches `RecursionError` before it can crash the process (versus the interpreter hitting a hard native stack overflow first). The severity of this finding (Medium DoS, matching the Helm CVSS) assumes the native-crash variant is achievable given the additional C-stack depth per recursion level in this code (property access, `uncurry()`, nested `try/except`); if the RPC layer's blanket exception handling proves fully robust, the impact would be reduced to a caught, per-request failure rather than a process crash.

def match_cat_puzzle(puzzle: UnknownPuzzle) -> Iterator[Program] | None:
    """
    Given the curried puzzle and args, test if it's a CAT and,
    if it is, return the curried arguments
    """
    if puzzle.mod == CAT_MOD and puzzle.curried_args is not None:
        return iter(puzzle.curried_args)
    else:
        return None
