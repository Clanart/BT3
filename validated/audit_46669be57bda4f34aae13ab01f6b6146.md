Based on my research, I found a genuine analog in the codebase, but I could not fully verify a complete attacker-controlled trigger path in the remaining iterations, so I'll present what is solidly supported and flag the unverified part.

### Title
`checkoutBranch`/`checkoutCommit` accept caller-supplied `allowFileProtocol` flag that re-enables `protocol.file.allow=always` for submodule updates - ([File: app/src/lib/git/checkout.ts], [File: app/src/lib/git/submodule.ts])

### Summary
`checkoutBranch` and `checkoutCommit` in `app/src/lib/git/checkout.ts` take an `allowFileProtocol` boolean parameter (default `false`) which is forwarded to `updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts`. When `true`, the submodule update is executed with `-c protocol.file.allow=always` [1](#0-0) , overriding Git's own hardening (Git disables `file://` submodule URLs by default specifically to mitigate local-file-disclosure/RCE-adjacent submodule attacks). This is architecturally the same "safety gate exists but call sites can bypass/disable it" pattern as the reported `LootSystem` `whenNotPaused` gap: a protective control is present in the code but its enforcement is optional and controlled by the caller rather than being an invariant.

### Finding Description
`updateSubmodulesAfterOperation` conditionally injects `protocol.file.allow=always` based on the `allowFileProtocol` argument passed all the way from `checkoutBranch`/`checkoutCommit` [2](#0-1) . This means the safety of submodule updates after a checkout is not a fixed guarantee of the checkout function — it depends on what each caller decides to pass. I confirmed at least one test exercising this with `allowFileProtocol = true` to auto-initialize an "uninitialized submodule" scenario [3](#0-2) , showing the flag is deliberately used in real (non-test-only) checkout flows, not just disabled by default everywhere.

### Impact Explanation
If a code path that checks out attacker-influenced content (e.g., a pull-request branch from a fork, or a branch reached via deep link `x-github-client://openPullRequest` handled in `openPullRequestFromUrl`/`_checkoutPullRequest` in `app/src/ui/dispatcher/dispatcher.ts`) passes `allowFileProtocol = true`, a malicious `.gitmodules` entry with a `file://` URL could point the submodule init at an arbitrary local path, potentially exfiltrating or aliasing local repository/config content into the checked-out tree during submodule init. This aligns with the "Valid Impact" criteria: attacker controls a fetched/cloned repository's content and the result could be file read/write outside the intended repo scope.

### Likelihood Explanation
I was **not able to conclusively verify**, within the remaining tool budget, that any of the currently-reachable `checkoutBranch`/`checkoutCommit`/`_checkoutPullRequest` call sites in `app-store.ts` or `dispatcher.ts` actually pass `true` for `allowFileProtocol` on attacker-influenced (fork/PR/deep-link) checkouts — my last grep for the call sites and `true`-argument usages in `app-store.ts` returned matches but I ran out of iterations before inspecting which specific calls set the flag and under what trigger. This is the critical missing link: if `allowFileProtocol` is only ever `true` for known/trusted local recovery scenarios (like the uninitialized-submodule fixup test), the analog is much weaker (impact/likelihood roughly matching the original report's low score). If it is `true` on any PR/fork/deep-link checkout, likelihood is materially higher.

### Recommendation
Audit all call sites of `checkoutBranch`, `checkoutCommit`, and `_checkoutPullRequest` to confirm `allowFileProtocol` is never `true` for checkouts of remote/fork/PR-supplied refs. Convert `allowFileProtocol` from a caller-supplied boolean into an invariant enforced inside `updateSubmodulesAfterOperation` (e.g., only allow it when the submodule URL is verified to reside within the already-trusted local working copy, never as a blanket override), rather than trusting each caller to reason about untrusted-input paths correctly — the same class of fix the original report requested for `LootSystem`'s pausability guarantee (make the guard an invariant, not an opt-in).

```typescript
export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
```
