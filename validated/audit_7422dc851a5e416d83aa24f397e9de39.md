### Title
Assertion-crash DoS via mempool item eviction race between `peak_post_processing()` and unlocked `peak_post_processing_2()` broadcast - ([File: chia/full_node/full_node.py])

### Summary
`FullNode.peak_post_processing()` runs under `blockchain.priority_mutex` and returns a `PeakPostProcessingResult` containing `mempool_peak_added_tx_ids` — transaction IDs that were just (re-)admitted to the mempool while draining the pending/conflict caches during `new_peak()` processing [1](#0-0) . The corresponding `mempool_item` lookup and broadcast happen later, in `peak_post_processing_2()`, which is explicitly documented and called **without** holding the blockchain lock [2](#0-1) . Between the unlock at the end of the locked phase and the unlocked iteration in `peak_post_processing_2()`, another concurrently-processed transaction can legitimately evict the very same mempool item (e.g. via mempool conflict resolution in `MempoolManager.add_spend_bundle()`, which calls `self.mempool.remove_from_pool(remove_items, MempoolRemoveReason.CONFLICT)` before re-adding a competing spend) [3](#0-2) . When that happens, `self.mempool_manager.get_mempool_item(transaction_id)` returns `None`, and the code immediately hits `assert mempool_item is not None` [4](#0-3) .

### Finding Description
This is structurally the same bug class as CVE-2026-10656: a transfer/event is queued from one synchronized context (interrupt / locked block-acceptance phase) and consumed later in an unsynchronized context (driver thread / unlocked `peak_post_processing_2`), and in between, a legitimate, attacker-triggerable action (new SETUP packet draining the FIFO / a second conflicting spend bundle evicting the mempool item) invalidates the object the consumer assumes is still present. The Zephyr fix added a NULL check and returned an error instead of dereferencing; Chia's equivalent code instead performs an unguarded `assert`, which — unlike a handled `None`-check path elsewhere in the same function (see `MempoolManager.get_mempool_item()` returning `Optional[MempoolItem]` by design [5](#0-4) ) — has no recovery path and raises an `AssertionError`.

The identical unguarded pattern also exists in `FullNode.add_transaction()`: after releasing the low-priority `priority_mutex` following a successful `add_spend_bundle()` call, the code re-fetches the item and asserts it is not `None` before broadcasting [6](#0-5) . Any concurrently processed higher-priority block acceptance (which drives `MempoolManager.new_peak()` and can evict/replace mempool items via FF rebase, double-spend eviction, or expiration in `new_tx_block()` [7](#0-6) ) can remove the same item in the gap between the lock release and this `assert`, again defeating the intended admission-then-confirmation flow with no NULL/None handling.

### Impact Explanation
An unhandled `AssertionError` raised inside these coroutines is not caught by any surrounding exception handler visible in the reviewed code paths (`peak_post_processing_2` and `add_transaction` have no try/except around the assert). Depending on how the enclosing task is scheduled, this can terminate the peak-processing or transaction-processing task, disrupting mempool broadcast/wallet-notification flow and, in the worst case, crash the full node process — a denial-of-service condition triggerable purely by submitting one or more spend bundles, without any special privilege.

### Likelihood Explanation
The race requires a mempool item that is admitted (present in `mempool_peak_added_tx_ids` or freshly added in `add_transaction`) to be evicted by a second, concurrently-processing transaction or block before the deferred lookup executes. Both `MempoolManager.add_spend_bundle()`'s conflict-eviction path and `new_peak()`'s eviction/expiration paths are reachable by ordinary wallet users submitting competing or double-spending transactions; no elevated access or malicious peer/farmer behavior is required — only ordinary concurrent transaction submission, which is a normal and expected usage pattern on a busy mempool.

### Recommendation
Replace the bare `assert mempool_item is not None` in both `FullNode.peak_post_processing_2()` and `FullNode.add_transaction()` with an explicit `None` check that skips/logs the broadcast for that transaction ID instead of crashing, mirroring the defensive-check style already used by `MempoolManager.get_mempool_item()`'s callers elsewhere in the codebase.

### Proof of Concept
1. Node processing a new peak drains its pending/conflict caches and re-admits transaction `A`, recording its ID in `mempool_peak_added_tx_ids` (still under lock) [1](#0-0) .
2. Lock is released; `peak_post_processing_2()` begins iterating `mempool_peak_added_tx_ids` unlocked [4](#0-3) .
3. Concurrently, a wallet/attacker submits transaction `B`, which conflicts with/supersedes `A` on the same coin; `add_transaction()` acquires the low-priority lock and calls `add_spend_bundle()`, which evicts `A` via `remove_from_pool(..., MempoolRemoveReason.CONFLICT)` before adding `B` [3](#0-2) .
4. `peak_post_processing_2()` reaches `get_mempool_item(A)`, which now returns `None` since `A` was just evicted, triggering `assert mempool_item is not None` and raising an unhandled `AssertionError` [8](#0-7) .

Note: I could not fully trace, within the available index, whether the asyncio task hosting `peak_post_processing_2()`/`add_transaction()` has an outer exception handler that would contain the `AssertionError` short of crashing the node process (e.g., in `create_referenced_task` wrappers) — this would need direct verification in a full checkout, since the index may not include every call-site/wrapper.

    def get_mempool_item(self, bundle_hash: bytes32, include_pending: bool = False) -> MempoolItem | None:
        """
        Returns the MempoolItem in the mempool that matches the provided spend bundle hash (id)
        or None if not found.

        If include_pending is specified, also check the PENDING cache.
        """
        item = self.mempool.get_item_by_id(bundle_hash)
        if not item and include_pending:
            # no async lock needed since we're not mutating the pending_cache
            item = self._pending_cache.get(bundle_hash)
        if not item and include_pending:
            item = self._conflict_cache.get(bundle_hash)

        return item
