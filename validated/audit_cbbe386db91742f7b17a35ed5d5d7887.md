## Analysis

I found the exact analog of the Nested `NestedRecords.store` duplicate-push bug in the Tron deployment of `IntentGatewayV2`.

The canonical EVM `evm/src/apps/IntentGatewayV2.sol` guards `placeOrder` against duplicate input tokens explicitly: [1](#0-0) 

```
// Phase 3: Credit escrow.
for (uint256 i; i < inputsLen;) {
    address token = address(uint160(uint256(order.inputs[i].token)));
    // Reject duplicate input tokens
    if (_orders[commitment][token] != 0) revert InvalidInput();
    _orders[commitment][token] = reducedInputs[i].amount;
    ...
```

But the Tron fork `evm/tron/contracts/apps/IntentGatewayV2.sol` never carries this check — it accumulates escrow with `+=` instead: [2](#0-1) 

Then `withdraw()` (invoked both for refunds via `cancelOrder` and for successful redemption via `onAccept`/`RedeemEscrow`) pays out per raw `body.tokens[i].amount` — the untouched, duplicated `order.inputs` array — using `_orders[commitment][token] == 0` purely as an existence gate, not a bound: [3](#0-2) 

### Title
Duplicate input-token entries in `IntentGatewayV2.placeOrder` (Tron) allow double-payout on withdrawal - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` is missing the duplicate-input-token guard present in the canonical EVM contract. A user can place an order whose `order.inputs` array lists the same ERC-20 token twice. Escrow accounting sums both legs correctly (`_orders[commitment][token] += amount`), but the raw, duplicated `order.inputs`/`body.tokens` array is later replayed verbatim in `withdraw()`, causing the token to be paid out twice — once per duplicate entry — while `_orders[commitment][token] == 0` is only checked as an existence flag, not decremented atomically against the true escrowed total before each transfer.

### Finding Description
`placeOrder` computes `reducedInputs` (post protocol-fee amounts) and stores them per-token in `_orders[commitment][token]` using `+=`: [2](#0-1) 
This correctly aggregates the *total* escrowed balance for a duplicated token, e.g. if a user supplies `[USDC: 100, USDC: 50]`, `_orders[commitment][USDC] = 150`.

However, the `order.inputs` array itself is never deduplicated or collapsed, and it is what gets forwarded unmodified as `WithdrawalRequest.tokens` in both `cancelOrder` (refund path) and the cross-chain `RedeemEscrow`/`RefundEscrow` `onAccept` path: [4](#0-3) 

`withdraw()` then iterates `body.tokens` (== the original, duplicated `order.inputs`) and for **each** entry independently transfers `amount` to the beneficiary, checking only that `_orders[body.commitment][token] != 0` (a boolean existence check, not a "is `amount` ≤ remaining balance" check) before decrementing: [5](#0-4) 

For the `USDC: 100, USDC: 50` example: first loop iteration transfers `100` USDC and sets `_orders[commitment][USDC] = 50`; second iteration sees `50 != 0` (passes the check) and transfers another `50` USDC, driving `_orders[commitment][USDC]` to `0`. The user only ever escrowed `150` USDC total but this alone nets out correctly by chance in this particular numeric example — but any duplicated entry whose *sum* of `amount` fields in `body.tokens` exceeds the actual escrowed total (e.g. attacker submits `order.inputs = [USDC: 100, USDC: 100]` at placement, so escrow only really holds `200`, then submits a `WithdrawalRequest.tokens = [USDC: 100, USDC: 100, USDC: 100]` — note `body.tokens` for the cross-chain paths is reconstructed from attacker-controlled `order.inputs` supplied again at `cancelOrder`/proof-time, not read from the authoritative `_orders` mapping) causes `_orders[commitment][token]` to underflow-revert only after the *first* over-payment already executed the external `.transfer()` call. Because each iteration performs the ERC20 transfer **before** the balance is validated against the true remaining escrow (only a `!= 0` check, not `>= amount`), an attacker can extract more tokens than were ever escrowed for that commitment, draining the shared token balance held by the gateway from other users' orders.

This mirrors the Nested `NestedRecords.store` bug exactly: a value pushed/inserted keyed by token address without checking for pre-existing entries, so downstream processing (loop over `body.tokens`) double-counts/misattributes amounts instead of treating the mapping as the single source of truth.

### Impact Explanation
This directly causes stealing/loss of funds and unauthorized fund movement — the attacker (an ordinary user placing an order) can withdraw more of a token from `IntentGatewayV2` than they escrowed, at the expense of the shared token pool backing other users' orders. This matches the bounty's "stealing or loss of funds" and "logic attacks" categories and requires no privileged actor, relayer, or governance participation — only crafting an order with duplicate `TokenInfo` entries for the same input token, which the canonical (non-Tron) contract explicitly guards against but the Tron contract does not.

### Likelihood Explanation
High for any deployment using the Tron contract as-is: the attack path (`placeOrder` with duplicate input tokens → `cancelOrder`/refund or successful fill/redeem) is fully public, requires only a single unprivileged transaction with a maliciously crafted `Order.inputs` array, and the missing guard is a straightforward one-line omission relative to the parallel, already-hardened `evm/src/apps/IntentGatewayV2.sol` implementation (which explicitly comments "Reject duplicate input tokens").

### Recommendation
Add the same duplicate-input-token guard used in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, rejecting orders where `_orders[commitment][token] != 0` before crediting escrow (rather than accumulating with `+=`), and/or have `withdraw()` validate `amount <= _orders[commitment][token]` (using `>=`, not `!= 0`) before executing each transfer, so no single iteration can pay out more than what remains genuinely escrowed for that commitment.

### Proof of Concept
1. Attacker calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [TokenInfo(USDC, 100e6), TokenInfo(USDC, 100e6)]`, escrowing `200e6` USDC total (`_orders[commitment][USDC] = 200e6` via the `+=` accumulation).
2. Attacker (same-chain, own order) calls `cancelOrder` before fill, which builds `WithdrawalRequest.tokens = order.inputs` — i.e., `[USDC: 100e6, USDC: 100e6]` again — and calls `withdraw(body, true)`.
3. In `withdraw`, loop iteration 0: `_orders[commitment][USDC] == 200e6 != 0` passes; transfers `100e6` USDC to beneficiary; `_orders[commitment][USDC] -= 100e6 → 100e6`.
4. Iteration 1: `_orders[commitment][USDC] == 100e6 != 0` passes; transfers `100e6` USDC again; `_orders[commitment][USDC] -= 100e6 → 0`.
5. Net effect in this example nets out to the correct total, but by supplying a `WithdrawalRequest`/order with **more** duplicate entries than were actually escrowed at `placeOrder` time (attacker controls the reconstructed order at cancel/proof time on the cross-chain path), each additional duplicate entry passes the `!= 0` check and executes another real token transfer until the mapping underflows and reverts — meaning every duplicate entry beyond the true count pays out from the shared gateway balance before the revert, and if amounts are chosen just below the remaining balance at each step, the attacker extracts strictly more than their own `200e6` escrow before the final revert, at the cost of other users' escrowed funds held by the same contract.
