## Finding: Git's Own Anti-RCE Clone Protection Is Explicitly Disabled During Clone

### Title
Disabling Git's `GIT_CLONE_PROTECTION_ACTIVE` Safeguard Re-opens Recursive-Clone RCE (CVE-2024-32002 class) - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` builds the environment for the underlying `git clone --recursive` invocation and explicitly forces `GIT_CLONE_PROTECTION_ACTIVE: 'false'` [1](#0-0) , while the app-level guard added right above it (`isClonePathSensitive`) only validates the *top-level destination path* the user chose, not what happens inside the recursive submodule checkout [2](#0-1) . This mirrors the reported pattern exactly: a security invariant ("don't allow this dangerous action") is enforced through one narrow gate (path-string comparison of the clone destination) while the actual attacker-controlled primitive (a malicious repository's submodules/hooks during `--recursive` clone) travels through a different, unguarded path — and here Desktop doesn't just fail to add a second guard, it actively turns off Git's own built-in one.

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is the internal switch Git uses to enable the hardening that was added upstream to remediate the class of clone-time RCE issues (symlinked/case-colliding `.git`/hooks directories reachable via crafted submodules on case-insensitive filesystems such as macOS/Windows, which allowed hook execution during `git clone --recursive`). Desktop's `clone()` function sets this to `'false'` for every clone it performs:

```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c', `init.defaultBranch=${defaultBranch}`,
  'clone', '--recursive',
]
...
args.push('--', url, path)
await git(args, __dirname, 'clone', opts)
``` [3](#0-2) 

The only mitigation actually present, `isClonePathSensitive`, is a *destination path* allow/deny check comparing the resolved clone path against a fixed list (`~`, `~/.ssh`, `~/.gnupg`, `~/.config`, `~/.gitconfig`, `%APPDATA%`) [4](#0-3) . It says nothing about, and cannot protect against, writes that occur *inside* the (legitimate) destination directory as a side effect of recursively checking out a malicious repository's submodules — exactly the scenario `GIT_CLONE_PROTECTION_ACTIVE` exists to stop. By forcing it off, Desktop removes Git's own defense-in-depth for that scenario and relies solely on the narrower, differently-scoped path check, the same "guard bound to the wrong identity/primitive" flaw as the Solidity report (a modifier keyed to `msg.sender` while the actual resource — the shares — could move to another address).

### Impact Explanation
If an attacker gets a victim to clone a crafted repository (fits the report's threat model: "attacker controls a cloned/fetched repository"), the disabled protection can allow the recursive submodule checkout to place files (including executable hooks) in locations that would otherwise be blocked by Git's upstream fix, potentially resulting in hook execution during clone — i.e., code execution on the victim's machine purely by cloning a repository through Desktop. This is a high-impact, unprivileged path exactly matching the accepted impact criteria (code execution via a malicious cloned repository).

### Likelihood Explanation
Likelihood is high: every clone performed through Desktop's `clone()` uses `--recursive` and unconditionally disables the protection, with no opt-out or conditional re-enable, and no equivalent replacement check exists for submodule/hook content. No unusual user action beyond a normal "Clone repository" (the primary use case of the app) is required.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Either omit the variable entirely (letting Git's default protection apply) or explicitly set it to `'true'`. If some other portion of the clone flow depends on the protection being off, the actual attacker-controlled primitive it interferes with should be identified and a check performed against *that* primitive (e.g., validating submodule paths/URLs before recursive checkout), not by disabling the upstream safeguard wholesale — the same fix pattern the report recommends (hook the check to the real point where the invariant can be violated, `_afterTokenTransfer`, rather than only at `deposit`/`withdraw`).

### Proof of Concept
1. An attacker creates and publishes a public repository containing a submodule whose configuration is crafted for a case-insensitive filesystem collision/hook-execution technique of the kind the upstream Git advisory addressed with `GIT_CLONE_PROTECTION_ACTIVE`.
2. A victim on macOS or Windows uses GitHub Desktop's "Clone a repository" feature to clone the attacker's repository to any normal, non-sensitive path (so `isClonePathSensitive` never triggers).
3. Desktop invokes `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` injected into the environment [1](#0-0) .
4. Because the protection Git normally applies for this scenario is disabled, the recursive submodule checkout proceeds without the upstream hardening, exposing the victim to the underlying hook-execution/arbitrary-write primitive that `GIT_CLONE_PROTECTION_ACTIVE` was designed to prevent.

Note: I could not find any code path in the indexed portion of the repository that re-enables or conditionally restores this protection elsewhere (e.g., in `envForRemoteOperation` or callers of `clone()`); if such logic exists in files not covered by the index, a Devin session with full repository access should verify this before treating the finding as final.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
```
