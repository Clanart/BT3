### Title
Partial commit selection is applied against a re-fetched diff, silently committing lines the user never selected - (File: `app/src/lib/git/apply.ts`)

### Summary
The external report's broken invariant is: a value is computed once (spot price at claim time) and applied to a quantity (staked balance) that was actually accumulated under a different, earlier state (the historical prices) — the two states are never reconciled, so the result silently diverges from what the user actually did. The same pattern exists in GitHub Desktop's partial-commit path: the user's line-level selection (`DiffSelection`, an index-based bitmask) is built against one diff snapshot shown in the UI, but at commit time `applyPatchToIndex` silently re-fetches a brand-new diff and applies the *old* selection indices to the *new* hunk structure, with no check that the two diffs are still consistent.

### Finding Description
When a user partially stages a file in Desktop, the UI computes a diff via `getWorkingDirectoryDiff` and lets the user toggle inclusion of individual lines. This selection is stored as a set of absolute line indices (`DiffSelection.divergingLines`), which only have meaning relative to the specific hunk layout (`hunk.unifiedDiffStart`) of the diff that was on screen when the selection was made: [1](#0-0) 

At commit time, `createCommit` → `stageFiles` → `applyPatchToIndex` does **not** reuse the diff/selection pairing that was validated in the UI. Instead it independently re-fetches the diff from disk right before building the patch: [2](#0-1) 

`formatPatch` then walks this freshly-fetched diff's hunks and asks `file.selection.isSelected(absoluteIndex)` — using the *old* absolute indices from the UI-time diff — to decide which lines to keep: [3](#0-2) 

If the file on disk changes between the moment the user reviews/selects lines in the Changes view and the moment they click "Commit" (e.g. a watch-mode build tool, formatter-on-save, linter, or a repository-provided git hook/npm script rewrites the file), the hunk layout returned by the second `getWorkingDirectoryDiff` call shifts. The old `divergingLines` indices no longer refer to the same logical lines, so `formatPatch` silently constructs a patch that stages a different set of additions/deletions than the ones the user visually selected. There is no re-validation step analogous to the "average price" fix recommended in the report — Desktop trusts the stale selection against the newly recomputed diff exactly the way `_earnedASugar` trusted the stale `stPrice` snapshot for the whole staking duration.

Existing guards elsewhere in the codebase (e.g. `_changeFileSelection`'s "something has changed... bail" check, or `updateChangesStashDiff`'s discard-on-mismatch check) explicitly compare before/after state to avoid using stale results: [4](#0-3) 
No equivalent check exists in `applyPatchToIndex`/`stageFiles`/`createCommit` — the re-fetched diff is used unconditionally with the old selection.

### Impact Explanation
This results in "silent corruption of what the user commits" — one of the explicitly valid impact categories. A user who has carefully reviewed and hand-picked lines to include in a commit (e.g. deliberately excluding a secret, a debug statement, or unfinished code) may end up committing content they never selected, or omitting content they intended to include, without any warning, if the working tree file is modified concurrently by any external process between selection and commit. Because commits are then pushed, this can also propagate unreviewed/unintended content to a shared remote.

### Likelihood Explanation
This requires the file to change between UI-diff computation and clicking Commit — a realistic condition for developers running file watchers, formatters, linters, or build tools in the background (a common, natural workflow, not an "unnatural user step"). No local/admin access or leaked credentials are needed; the attacker-controlled input is simply the content of a cloned/fetched repository combined with normal developer tooling that mutates tracked files. Likelihood is moderate — it depends on timing and an external process touching the same file — but the code path itself provides zero protection against it, unlike other parts of the codebase that explicitly guard against stale-state races.

### Recommendation
Before applying the patch in `applyPatchToIndex`, verify that the diff used to build the patch is the same diff the selection was made against (e.g. by comparing blob hashes/hunk fingerprints, or by re-deriving `selectableLines` from the freshly fetched diff and rejecting/re-validating any selection state that doesn't map 1:1 onto the new hunks, the way `_changeFileSelection` already bails when state changes underneath it). If the diff has changed, the commit operation should surface a conflict/refresh prompt to the user rather than silently applying a mismatched selection.

### Proof of Concept
1. Open a repository in Desktop containing a tracked file `foo.txt` with several distinct hunks of change.
2. In the Changes view, deselect specific lines (e.g. only stage the first hunk) — Desktop computes a diff via `getWorkingDirectoryDiff` and stores line-level `DiffSelection` indices for that diff.
3. Before clicking "Commit", run any background process that rewrites `foo.txt` such that the number of context/changed lines above the originally-selected hunk changes (e.g. a formatter reflows earlier lines, or a watch-mode build script regenerates part of the file) — this shifts subsequent hunks' `unifiedDiffStart` values.
4. Click "Commit". `applyPatchToIndex` re-runs `getWorkingDirectoryDiff` and calls `formatPatch` with the *original* selection indices against the *new* hunk layout.
5. Inspect the resulting commit (`git show HEAD`): it contains lines the user did not visually select (or omits lines they did select), with no warning shown by Desktop.
