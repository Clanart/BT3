## Finding

### Title
Relayer receipt attribution trusts an unverified embedded public key, enabling relayer-fee theft - (File: `modules/pallets/ismp/src/host.rs`)

### Summary
`pallet-ismp`'s `IsmpHost` implementation records the delivering relayer for every request/response by calling `extract_signer()` on the `signer` bytes carried in the incoming `Message`. That function decodes the bytes as a `crypto_utils::verification::Signature` enum and returns whichever `address`/`public_key` field is embedded in it — **without ever verifying the accompanying signature bytes actually sign anything**. This receipt is later read by `pallet-ismp-relayer`'s fee-accumulation path to decide who gets paid the relayer fee for delivering a message, so an unverified "signer" field directly controls fund distribution — the exact bug class in the referenced report, where a message field meant to identify a signer carries no cryptographic binding.

### Finding Description
`store_request_receipt` / `store_response_receipt` in `pallet-ismp`'s host implementation call `extract_signer`: [1](#0-0) 

```rust
fn extract_signer(signer: &[u8]) -> Result<Vec<u8>, Error> {
	if signer.len() > 32 {
		Signature::decode(&mut signer.as_ref())
			.map(|sig| sig.signer())
			.map_err(|_| Error::SignatureDecodingFailed)
	} else {
		Ok(signer.to_vec())
	}
}
``` [2](#0-1) 

`Signature::signer()` merely returns the embedded `address`/`public_key` field of whichever variant was decoded — it performs no cryptographic check:
```rust
pub fn signer(&self) -> Vec<u8> {
    match self {
        Signature::Evm { address, .. } => address.clone(),
        Signature::Sr25519 { public_key, .. } => public_key.clone(),
        Signature::Ed25519 { public_key, .. } => public_key.clone(),
    }
}
``` [3](#0-2) 

`Signature::decode` is a plain SCALE decode of attacker-controlled bytes (`Signature::Evm { address, signature }` — `signature` is `Vec<u8>` and its length/content is never validated by `decode`). Because the ISMP message-handling extrinsic that ultimately calls `store_request_receipt`/`store_response_receipt` is submitted as an **unsigned extrinsic** (`Ismp::handle_unsigned`, as used by the honest relayer client), any caller can submit a batch containing an arbitrary `signer` field: [4](#0-3) 

Contrast this with `pallet-messaging-incentives`, which correctly performs cryptographic verification before crediting a relayer:
```rust
fn relayer_for(message: &Message) -> Option<T::AccountId> {
    let (signer, signed) = match message { ... };
    Signature::decode(&mut &signer[..]).ok()?
        .verify_and_get_sr25519_pubkey(&signed, None).ok()
        .map(T::AccountId::from)
}
``` [5](#0-4) 

`store_request_receipt`/`store_response_receipt`, however, use `extract_signer`, which has no equivalent `.verify(...)` call — it never checks the `signature` bytes against the message hash, it just extracts the identity field.

This receipt is precisely what the fee-claim path later trusts: `decode_receipt_relayer` in `pallet-ismp-relayer` reads the stored receipt bytes from a state-proven `RequestReceipts`/`ResponseReceipts` entry and, for the substrate branch, applies the exact same unauthenticated `Signature::decode(...).signer()` pattern to determine the payee address for relayer fees: [6](#0-5) 
and the resulting `address` is credited via `Fees::<T>::try_mutate` in `accumulate()`: [7](#0-6) 

### Impact Explanation
Because the "signer" identity that ends up permanently recorded in `RequestReceipts`/`ResponseReceipts` (and later state-proven and paid out by `accumulate()`) is taken from an unverified embedded field rather than a validated signature, an attacker submitting (or racing) the unsigned `handle_unsigned` message-delivery extrinsic can set the `signer` bytes to decode as `Signature::Evm { address: <attacker or arbitrary address>, signature: <any 65 bytes> }`. This misattributes delivery credit and lets the attacker redirect relayer fees to an address of their choosing instead of the account that actually incurred delivery costs — a direct "wrong beneficiary" / fund-theft outcome matching the bounty's impact gate (unauthorized transaction/execution causing loss of funds to the rightful relayer).

### Likelihood Explanation
The path requires only an unprivileged actor able to submit an unsigned ISMP message extrinsic with a crafted `signer` field — no relayer key, prover collusion, or governance access is needed, since `extract_signer`/`Signature::signer()` never validates the signature payload. The only mitigating factor is that the underlying request/response content must still pass consensus-proof verification to be accepted at all (this analysis did not fully trace whether `ismp/core/src/handlers.rs` performs any independent signature check on `msg.signer` prior to invoking `store_request_receipt`/`store_response_receipt`; no such check was found in the searched call sites, but this could not be exhaustively confirmed within the available search).

### Recommendation
Before persisting a receipt in `store_request_receipt`/`store_response_receipt`, cryptographically verify the `signer` signature against the request/response content hash (mirroring the pattern already implemented correctly in `pallet-messaging-incentives::relayer_for`), rather than trusting the embedded `address`/`public_key` field returned by `Signature::signer()`. Alternatively, bind receipt attribution to the extrinsic's actual submitter (`ensure_signed`) rather than an unauthenticated in-payload field.

### Proof of Concept
1. Attacker crafts an ISMP `Message::Request` (or `Response`) with a valid consensus/state proof for a legitimate cross-chain request, but sets `signer = Signature::Evm { address: <attacker_address>, signature: [0u8; 65] }.encode()`.
2. Attacker submits this via the unsigned `Ismp::handle_unsigned` extrinsic (as the relayer client does in `tesseract/messaging/substrate/src/provider.rs`).
3. `store_request_receipt` calls `extract_signer(signer)`, which SCALE-decodes the bytes successfully and returns `attacker_address` via `Signature::signer()` — no signature math is performed.
4. `RequestReceipts::<T>` now records `attacker_address` as the delivering relayer.
5. When fee accumulation runs, `decode_receipt_relayer` reads this same unauthenticated field from the proven receipt and `accumulate()` credits `attacker_address` in `Fees::<T>`, letting the attacker withdraw fees that should belong to whoever actually delivered/paid for the message.

	/// Recover the relayer's account from the sr25519 signature on a

	fn relayer_for(message: &Message) -> Option<T::AccountId> {

				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),

			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
