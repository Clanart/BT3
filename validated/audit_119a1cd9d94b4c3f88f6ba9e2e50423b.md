### Title
Cross-contract tier desync between `BandwidthManager.tierPrice` and `pallet-bandwidth`'s `TierConfig` allows underpaid bandwidth purchases - (File: evm/src/apps/BandwidthManager.sol, modules/pallets/bandwidth/src/types.rs)

### Summary
The bandwidth subscription system splits a single logical SKU ("tier") across two independently-updated, asynchronously-synchronized contracts, exactly mirroring the FIVA `storage::index` desync bug: the EVM-side `BandwidthManager.tierPrice[tier]` holds the price, while the Hyperbridge-side `pallet-bandwidth::TierConfig` (bytes + duration) holds what the buyer actually receives. Governance updates these two values via two separate transactions (`set_tier` on the pallet, then a `SetTiers` cross-chain dispatch to the manager), with no atomicity or version binding between them.

### Finding Description
`purchase()` in [1](#0-0)  reads only the local `tierPrice[tier]` to compute the amount charged, then dispatches a `BandwidthPurchaseMsg{tier, months, app, chain}` carrying just the tier discriminant — no price or version field — to `pallet-bandwidth`. On the Hyperbridge side, the pallet's inbound handler looks up its own `TierConfig` (bytes/duration) for that same discriminant and credits `bytes × months` regardless of what price was actually charged by the EVM contract, as described in the docs: "The pallet owns the bytes-and-duration side of each tier; the manager owns the price side. Governance keeps the two in sync by dispatching a `SetTiers` message from the pallet to each registered manager whenever prices change" [2](#0-1) .

Just as in the FIVA report, where the Pool and YTMinter each store an independent `storage::index` that must stay synchronized across two async messages (`update_pool_index` / `update_minter_index`), here `TierConfig` (pallet) and `tierPrice` (manager) are two independently-mutable state variables tied only by the shared `tier` discriminant, updated by two separate governance actions with no ordering guarantee or shared version/nonce:

- Pallet-side: `set_tier` mutates `TierConfig` for a tier directly.
- Manager-side: `SetTiers` is a cross-chain dispatch from the pallet that must be relayed and separately applied via `onAccept` in [3](#0-2) .

If governance re-prices a tier upward (raises `tierPrice`) while simultaneously increasing the tier's `bytes`/`duration_secs` allowance (a routine "raise the bytes and the price together" governance action), there exists a window where the pallet's `TierConfig` has already been bumped (new, larger allowance) but the `SetTiers` message has not yet landed on the manager (old, smaller price is still active). Any unprivileged user can call `purchase()` during that window and pay the **stale, lower price** while receiving credit for the **new, larger `bytes`/`duration_secs`** allowance once the purchase message reaches `pallet-bandwidth`'s `on_accept`. This is functionally identical to the FIVA scenario where the YTMinter index was bumped before the Pool index, causing the Pool to under-account minted PT tokens relative to what was actually minted.

Nothing in `purchase()` or the pallet's purchase-credit path binds the price paid to the allowance granted — the only shared key is the bare `tier` discriminant, and the docs explicitly acknowledge the two sides are "kept in sync" only by best-effort sequential governance dispatch, not by any atomic or versioned update, exactly the unguarded assumption flagged by the FIVA report ("the report recommends... validate these syncing assumptions").

### Impact Explanation
This directly causes fund loss for the protocol treasury: the buyer receives more bandwidth allowance (bytes × duration) than what they paid for, i.e., a wrong-amount settlement between what is charged (EVM fee-token pull) and what is credited (Substrate subscription ledger). Under the bounty's impact categories this is a "loss of funds" / "transaction manipulation" case — a legitimate unprivileged caller obtains a state result (bandwidth credit) that is inconsistent with, and worth more than, the value actually transferred, purely by racing a routine two-step governance re-pricing operation. No malicious relayer, prover, or governance actor is required — this only requires an ordinary user submitting `purchase()` during the natural latency window between two sequential, otherwise-legitimate governance transactions.

### Likelihood Explanation
Governance updates that jointly change price and allowance are a normal, expected operational action for this system (the docs list per-tier bytes/duration/price adjustments as ordinary governance calls). The desync window is bounded by ordinary cross-chain message relay latency (the `SetTiers` dispatch must be picked up by a relayer and delivered), which is a routine, non-adversarial delay of at least one block round-trip — not a rare or attacker-engineered race. Any user who happens to submit `purchase()` in that interval (or watches for the `TierSet`/tier-update events and times their call) benefits automatically.

### Recommendation
- **Short term:** Bind price and allowance together at purchase time by including a price (or a monotonically increasing tier version/nonce) in the `BandwidthPurchaseMsg`, and have `pallet-bandwidth` reject or reprice purchases whose embedded price/version does not match the currently configured `TierConfig` version. Alternatively, source both price and allowance from a single atomic update path (e.g., have the pallet be the sole source of truth and have the manager query it synchronously, or freeze purchases on a tier while a `SetTiers` update for that tier is in flight).
- **Long term:** Audit all cross-contract/cross-chain "kept in sync" invariants in the codebase (similar dual-state patterns may exist elsewhere in fee/paymaster logic) and add explicit versioning or two-phase commit so config updates that must land atomically across chains cannot be independently observed mid-update by user-facing entry points.

### Proof of Concept
1. Governance decides tier `TierTwo` should now grant 2× the bytes for the same or higher price (a normal capacity increase). It calls `pallet-bandwidth::set_tier(TierTwo, { bytes: 600_000, duration_secs: X })`, updating `TierConfig` immediately on Hyperbridge [4](#0-3) .
2. Governance then calls `dispatch_set_tiers` to push the corresponding (possibly repriced) `tierPrice` to `BandwidthManager` on the EVM chain; this message must be relayed and is not yet applied.
3. During this window, an attacker (or any regular user) calls `BandwidthManager.purchase(app, TierTwo, 1, chain)` in [1](#0-0) . `tierPrice[TierTwo]` is still the old (lower) price, so the user pays the old amount.
4. The `BandwidthPurchaseMsg` is relayed to `pallet-bandwidth`, whose purchase handler credits a `Subscription` using the already-updated `TierConfig` (the new, larger `bytes`/`duration_secs`), giving the user the upgraded allowance for the old, lower price.
5. Result: the treasury under-collects fee-token revenue relative to the bandwidth actually granted — a direct value loss caused solely by the unsynchronized two-step, cross-chain tier update, with no privileged or malicious actor beyond ordinary governance and an ordinary user racing the relay latency.

```text
    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );
```
