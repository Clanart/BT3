### Title
Silent remote-URL rewrite on repository rename uses inconsistent protocol/identity checks that ignore protocol on one side and use a weak legacy parser on the other - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` decides whether to automatically rewrite a user's local git remote to a new URL supplied by the GitHub API (`apiRepo.clone_url`) after detecting a repository rename/transfer. Like the OHM/PRICE.sol finding, the function combines two guards that are supposed to express the *same* invariant ("this URL still refers to the remote I expect") but implement it with two different, inconsistent parsers/semantics — one (`protocolsMatch`) is scheme-only and computed with Node's legacy, permissive `URL.parse()`, the other (`urlMatchesRemote`/`remoteUrlUnchanged`) is computed with the app's own regex-based `parseRemote()` and **completely ignores protocol**. Because the two checks don't agree on what "the same URL" means, the combined guard can be satisfied even though the semantic intent (only rewrite the remote when we're sure nothing user- or attacker-controlled has diverged) is not actually met, allowing the stored git remote to be silently repointed based on API data.

### Finding Description [1](#0-0) 

```
const remoteUrl = gitStore.defaultRemote.url
const updatedRemoteUrl = apiRepo.clone_url
const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

const parsedRemoteUrl = URL.parse(remoteUrl)
const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
const protocolsMatch =
  parsedRemoteUrl.protocol !== null &&
  parsedUpdatedRemoteUrl.protocol !== null &&
  parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

const remoteUrlUnchanged =
  gitStore.defaultRemote &&
  urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
  await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
}
```

`urlMatchesRemote` (used for both `urlsMatch` and `remoteUrlUnchanged`) is implemented purely with the app's `parseRemote()` regex table and only compares `hostname`/`owner`/`name`, case-insensitively — it never inspects protocol: [2](#0-1) 

`protocolsMatch`, by contrast, is derived from Node's deprecated `url.parse()` legacy API, which behaves inconsistently with the app's own `parseRemote()` scp-style/ssh detection (per the comment in the file itself, `url.parse` returns `protocol === null` for scp-style `git@host:owner/repo.git` URLs even though `parseRemote()` classifies these as valid `ssh` remotes): [3](#0-2) 

This mirrors exactly the structure of the M-18 bug: two guards intended to jointly enforce "don't touch the remote unless we're sure it's safe" are built on two different notions of URL equivalence (one strict on scheme, blind to identity nuance beyond exact string match; the other strict on owner/name/hostname, completely blind to scheme). The combined `if` statement is only as safe as the *weaker* of the two checks for any given input, and any GitHub API response containing a `clone_url` for the repository (a value that is influenced by repository owner/name, i.e. by transfers/renames — actions an attacker with sufficient collaborator/admin rights on a shared repository can trigger) is trusted to rewrite the user's local remote as long as the two independently-computed checks happen to both pass.

### Impact Explanation
If an attacker with write/admin capability on a repository the victim has cloned (e.g., a malicious collaborator, or a takeover of a low-privileged co-maintainer account) renames/transfers the repository so that the GitHub API's `clone_url` for that repository ID now points at an attacker-controlled owner/name, and the victim's Desktop client happens to satisfy the two inconsistent identity checks (`protocolsMatch` via `URL.parse` and `remoteUrlUnchanged` via `parseRemote`), Desktop will silently call `gitStore.setRemoteURL` and repoint the user's `origin` remote to the attacker's fork — without any user confirmation dialog. Subsequent `git push` from the user will silently commit/push code and history to the attacker-controlled destination, meeting the "silent corruption of what the user commits or pushes" impact category. Because this is done automatically as a background sync operation (triggered on repository refresh, via `app-store.ts` call sites of `updateRemoteUrl`), the user has no visual indication their remote has changed.

### Likelihood Explanation
Exploitability requires that the two independent guard computations happen to agree despite modeling the invariant differently — this makes the exact conditions narrower than a full validation bypass, similar to how the OHM/PRICE.sol staleness mismatch only manifests under specific timing. The most reliable trigger is the common, everyday case (both remotes are `https://` URLs, which is Desktop's default clone protocol), where `protocolsMatch` reduces to a trivial `'https:' === 'https:'` and `remoteUrlUnchanged`/`urlsMatch` reduce entirely to `parseRemote()`'s hostname/owner/name comparison. In that common case, the feature *always* applies whenever a repo the victim has cloned changes owner/name via the GitHub API, since there is no additional confirmation step and no protocol-aware sanity check tying the update back to the same underlying repository ID.

### Recommendation
- Base both the "protocol changed" and "identity changed" checks on a single, consistent parser (e.g., extend `parseRemote()`/`IGitRemoteURL` to carry protocol and use it everywhere instead of mixing in Node's legacy `url.parse()`).
- Do not silently rewrite `origin` based on `apiRepo.clone_url` alone; tie the update to the numeric GitHub repository ID (which `IAPIRepository`/`GitHubRepository` already track) rather than relying purely on string-based URL comparisons, and prompt the user before changing an existing remote.
- Add explicit tests asserting that `protocolsMatch` and `urlMatchesRemote`/`remoteUrlUnchanged` agree on protocol handling for scp-style, `ssh://`, and `https://` URLs, closing the gap the way the mitigation for M-18 unified the two staleness thresholds.

### Proof of Concept
1. Victim clones `https://github.com/legit-owner/legit-repo.git` in Desktop; `gitHubRepository.cloneURL` is cached as this same URL.
2. Attacker (a collaborator/admin on `legit-repo`, or an account that gains such access) transfers/renames the repository so that its canonical URL becomes `https://github.com/attacker-owner/legit-repo.git`, while GitHub preserves the same repository ID.
3. On Desktop's next background repository refresh, `updateRemoteUrl` is invoked with `apiRepo.clone_url = 'https://github.com/attacker-owner/legit-repo.git'`.
4. `protocolsMatch` is `true` (both `https:`), `remoteUrlUnchanged` is `true` (victim never manually edited the remote, so `urlMatchesRemote(gitHubRepository.cloneURL, defaultRemote)` still matches on owner/name/hostname prior to the rename), and `urlsMatch` is `false` (the API URL now differs).
5. Desktop calls `gitStore.setRemoteURL('origin', 'https://github.com/attacker-owner/legit-repo.git')` without prompting the user.
6. The victim's next `git push` silently pushes to the attacker's repository.

```typescript
export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```
