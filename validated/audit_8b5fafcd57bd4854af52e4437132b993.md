### Title
ReceivedOutput deserialization does not bind the offset to the output's script_pubkey, allowing an output to be reported as spendable when it is not — ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` deserializes three independent fields — a scalar `offset`, a `TxOut`, and an `OutPoint` — with no consistency check that `output.script_pubkey` is actually the P2TR script for `group_key + G * offset`. `Scanner::scan_transaction` guarantees this invariant by construction, but `read` does not. Any `ReceivedOutput` materialized from untrusted bytes (rather than from the scanner) can therefore carry a mismatched `offset`/`script_pubkey` pair. When the protocol later tries to spend it, `SignableTransaction::multisig` detects the mismatch and returns `None`, so the output can never be signed for — the funds are treated as received yet are unspendable, mirroring the "stuck funds with no recovery path" class of the reference report.

### Finding Description
`ReceivedOutput::read` reads the fields independently and returns them verbatim:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output;
  let outpoint;
  {
    let mut buf_r = BufReader::with_capacity(0, r);
    output = TxOut::consensus_decode(&mut buf_r)...
    outpoint = OutPoint::consensus_decode(&mut buf_r)...
  }
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

Contrast with `Scanner::scan_transaction` (mod.rs:199-214), which only produces a `ReceivedOutput` after looking up `output.script_pubkey` in the registered `scripts` map, so `offset` is *proven* to match the script.

The spend path enforces the invariant and refuses to sign on mismatch:

```rust
// networks/bitcoin/src/wallet/send.rs:273-285
pub fn multisig(self, keys: &ThresholdKeys<Secp256k1>) -> Option<TransactionMachine> {
  ...
  let offset = keys.clone().offset(self.offsets[i]);
  if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
    None?;
  }
```

So a deserialized `ReceivedOutput` whose `script_pubkey` doesn't equal `p2tr_script_buf(group_key + G*offset)` is accepted as an input but produces no signing machine. Additionally, `Output::key()` in `processor/src/networks/bitcoin.rs` (lines 112-122) recomputes the key as `script_key - G*offset`; a mismatched pair yields a wrong key there too (and would trip `assert_eq!(output.key(), key)` in `processor/src/multisigs/scanner.rs:563` if it flowed through the scanner path).

### Impact Explanation
An output that the processor records/reports as received cannot be spent: `multisig` returns `None`, no `TransactionMachine` is produced, and there is no alternate recovery path — the same "funds reported received that are not spendable" impact as the reference issue where non-`pool.token` balances could never be withdrawn. If such an output is included among inputs, the entire transaction construction/signing fails, halting use of all co-spent inputs.

### Likelihood Explanation
Severity Medium. The corruption requires untrusted bytes reaching `ReceivedOutput::read`/`Output::read` (e.g., serialized outputs propagated between processors/coordinator rather than produced by the local `Scanner`), which is narrower than an on-chain-only trigger, but requires no secret material and no collusion.

### Recommendation
Either verify the binding inside `ReceivedOutput::read` — recompute `p2tr_script_buf(key + G*offset)` given the expected group key — or, since `read` lacks the group key, push verification to consumers: have `SignableTransaction::new` (not just `multisig`) reject inputs where `output.script_pubkey` isn't a registered scanner script, and have the processor drop/reject scanned outputs whose `Output::key()` doesn't equal the expected key instead of asserting after the fact.

### Proof of Concept
```rust
// Conceptual: craft bytes with a valid offset but an arbitrary script_pubkey
let mut buf = Vec::new();
buf.extend(Scalar::ZERO.to_bytes()); // claims "no offset"
let fake = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_p2tr_tweaked(
    TweakedPublicKey::dangerous_assume_tweaked(attacker_xonly) // not our key
  ),
};
buf.extend(serialize(&fake));
buf.extend(serialize(&OutPoint::new(some_txid, 0)));

let ro = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// ro is accepted; SignableTransaction::new(vec![ro], ...) builds fine,
// but multisig(&keys) returns None — funds are recorded yet can never be signed for.
```

Two notes on scope: `scan_block` returning immature coinbase outputs (mod.rs:216-227) is documented behavior with a stated mitigation, so it was not used; the `expect("offset collision")` in `processor/src/networks/bitcoin.rs:325` involves fixed `hash_to_F` constants and isn't attacker-reachable, so it was also excluded.
