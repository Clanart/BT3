Based on the investigation, I've found a strong analog to the GitLab "UI misrepresentation of critical information" bug class within the offer summary/heuristic parsing code in the Chia wallet.

## Analog Found

The GitLab bug class involves a business-logic error where the UI displays incorrect identity information (branch name) that a user relies on to make a security/confidentiality decision. The Chia analog is in `Offer._get_offered_coins()` in `chia/wallet/trading/offer.py`, which is explicitly documented as heuristic ("It's also a little heuristic, but it should get most things") and used to build the human-facing `Offer.summary()` that CLI/RPC callers (`take_offer`, `print_offer_summary`, `get_offer_summary`) display to a counterparty before they decide whether to accept a trade. [1](#0-0) 

The heuristic first tries to match offered coins to an `asset_id` purely by **amount** (`matching_spend_additions = [a for a in additions if a.amount in offered_amounts]`), only falling back to puzzle-hash matching if the amount-based match count doesn't line up. If a malicious offer-maker crafts a multi-asset offer where two different assets happen to share coin amounts, this heuristic can attribute settlement coins to the wrong `asset_id` in `get_offered_coins()` / `get_offered_amounts()` / `Offer.summary()`, without violating any consensus-level check. [2](#0-1) 

This summary is exactly what a wallet user or CLI operator (via `print_offer_summary` in `chia/cmds/wallet_funcs.py`, or `get_offer_summary` RPC in `chia/wallet/wallet_rpc_api.py`) uses to decide whether to `take_offer`. The actual settlement, by contrast, is driven independently by `driver_dict` and `requested_payments` in `to_valid_spend()`, so the *effective* asset flow used for signing/consensus can differ from what the human-facing summary claims — a direct parallel to GitLab's branch-name confusion, where the UI shows one identity while the backend acts on another, tricking a user relying on the display into an action (accepting a trade) they wouldn't take if shown accurate information. ### Title
Offer summary asset-identity misattribution via amount-based coin-matching heuristic - (File: chia/wallet/trading/offer.py)

### Summary
`Offer._get_offered_coins()` (invoked by `get_offered_amounts()`, `Offer.summary()`, and ultimately by `print_offer_summary`/`get_offer_summary` RPC used before `take_offer`) attributes settlement coins to asset IDs primarily by matching coin **amount**, not puzzle identity. A crafted offer with colliding amounts across different assets can cause the human-facing summary to display an incorrect asset breakdown to the counterparty.

### Finding Description
`_get_offered_coins()` filters additions first by `a.amount in offered_amounts` and only falls back to puzzle-hash matching when the amount-based count fails to reconcile (`chia/wallet/trading/offer.py:242-303`). This is explicitly acknowledged in code comments as "a little heuristic." Because the summary derived from this method (`get_offered_amounts`, `Offer.summary()`) is the primary trust signal shown to a human before accepting an offer (`take_offer` in `chia/cmds/wallet_funcs.py:816-840`, `get_offer_summary` RPC in `chia/wallet/wallet_rpc_api.py:1985-2009`), a maker can construct an offer bundling multiple assets with overlapping coin amounts such that the displayed offered/requested asset totals do not match the assets that are actually transferred by the underlying `driver_dict`/`requested_payments`-driven settlement (`to_valid_spend`, `offer.py:501-596`). The summary and the consensus-enforced settlement are computed from independent code paths, so they can diverge without any validation error.

### Impact Explanation
A victim who inspects the offer summary before calling `take_offer` may approve a trade believing they are receiving/giving a different asset mix than what actually settles, since acceptance decisions in both the CLI and any GUI/RPC client built on `get_offer_summary`/`print_offer_summary` rely on this heuristic output. This can lead to an offer counterparty being tricked into an asset-for-asset trade they did not intend, i.e., economic loss through offer settlement misrepresentation — while the resulting spend is technically valid per consensus (since actual movement is governed by `driver_dict` and puzzle solutions), the attacker exploits the UI/summary layer as the deception vector.

### Likelihood Explanation
Requires only the ability to construct and share an arbitrary offer file/spend bundle (any wallet user, no special privilege) with intentionally colliding coin amounts across multiple asset types; no consensus rule violation or wait-for-confirmation is needed to trigger the display mismatch, only crafting of the offer's coin amounts to make the heuristic misfire.

### Recommendation
Strengthen `_get_offered_coins()` to always resolve asset identity via puzzle-hash correspondence (`construct_puzzle(puzzle_driver, OFFER_MOD).get_tree_hash()`) rather than amount-first matching, or raise a `ValueError` whenever amount-based and puzzle-hash-based matches could disagree (ambiguous cases), instead of silently trusting amount matching when counts coincidentally align.

### Proof of Concept
Construct an `Offer` whose `_bundle` contains settlement-payment children for two distinct CAT asset types where coins for asset A and asset B share the same amount value; call `offer.summary()` / `get_offered_amounts()` and observe that the heuristic in `_get_offered_coins()` (`chia/wallet/trading/offer.py:266-291`) can attribute an addition to the wrong `asset_id` bucket purely because `a.amount in offered_amounts` matched before puzzle-hash disambiguation was needed, producing a summary that misrepresents which asset is actually being offered/requested to a human reviewing the trade via `take_offer`.

    def _get_offered_coins(self) -> dict[bytes32 | None, list[Coin]]:
        offered_coins: dict[bytes32 | None, list[Coin]] = {}

        cost_left = INFINITE_COST
        for parent_spend in self._bundle.coin_spends:
            coins_for_this_spend: list[Coin] = []

            parent_puzzle: UnknownPuzzle = UnknownPuzzle(known_program=parent_spend.puzzle_reveal)
            parent_solution = Program.from_serialized(parent_spend.solution)
            additions: list[Coin] = self._additions[parent_spend.coin]

            puzzle_driver = match_puzzle(parent_puzzle)
            if puzzle_driver is not None:
                asset_id = create_asset_id(puzzle_driver)
                inner_puzzle: Program | None = get_inner_puzzle(puzzle_driver, parent_puzzle, parent_solution)
                inner_solution: Program | None = get_inner_solution(puzzle_driver, parent_solution)
                assert inner_puzzle is not None and inner_solution is not None

                # We're going to look at the conditions created by the inner puzzle
                puzzle_cost, conditions = inner_puzzle.run_with_cost(cost_left, inner_solution)
                assert cost_left >= puzzle_cost
                cost_left -= puzzle_cost
                expected_num_matches: int = 0
                offered_amounts: list[int] = []
                for condition in conditions.as_iter():
                    if condition.first() == 51 and condition.rest().first() == OFFER_MOD_HASH:
                        expected_num_matches += 1
                        offered_amounts.append(condition.rest().rest().first().as_int())

                # Start by filtering additions that match the amount
                matching_spend_additions = [a for a in additions if a.amount in offered_amounts]

                if len(matching_spend_additions) == expected_num_matches:
                    coins_for_this_spend.extend(matching_spend_additions)
                # We didn't quite get there so now lets narrow it down by puzzle hash
                else:
                    # If we narrowed down too much, we can't trust the amounts so start over with all additions
                    if len(matching_spend_additions) < expected_num_matches:
                        matching_spend_additions = additions
                    matching_spend_additions = [
                        a
                        for a in matching_spend_additions
                        if a.puzzle_hash == construct_puzzle(puzzle_driver, OFFER_MOD).get_tree_hash()
                    ]
                    if len(matching_spend_additions) == expected_num_matches:
                        coins_for_this_spend.extend(matching_spend_additions)
                    else:
                        raise ValueError("Could not properly guess offered coins from parent spend")
            else:
                # It's much easier if the asset is bare XCH
                asset_id = None
                coins_for_this_spend.extend([a for a in additions if a.puzzle_hash == OFFER_MOD_HASH])

            # We only care about unspent coins
            coins_for_this_spend = [c for c in coins_for_this_spend if c not in self._bundle.removals()]

            if coins_for_this_spend != []:
                offered_coins.setdefault(asset_id, [])
                offered_coins[asset_id].extend(coins_for_this_spend)
        return offered_coins

    def summary(self) -> tuple[dict[str, str], dict[str, str], dict[str, PuzzleInfo], ConditionValidTimes]:
        offered_amounts: dict[bytes32 | None, int] = self.get_offered_amounts()
        requested_amounts: dict[bytes32 | None, int] = self.get_requested_amounts()

        def keys_and_amounts_to_strings(dic: dict[bytes32 | None, int]) -> dict[str, str]:
            new_dic: dict[str, str] = {}
            for key, val in dic.items():
                if key is None:
                    new_dic["xch"] = str(val)
                else:
                    new_dic[key.hex()] = str(val)
            return new_dic

        driver_dict: dict[str, PuzzleInfo] = {}
        for key, value in self.driver_dict.items():
            driver_dict[key.hex()] = value

        return (
            keys_and_amounts_to_strings(offered_amounts),
            keys_and_amounts_to_strings(requested_amounts),
            driver_dict,
            self.absolute_valid_times_ban_relatives(),
        )
