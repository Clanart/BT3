## Title
Permissionless `purchase()` lets anyone evict a victim app's paid bandwidth via cheap FIFO-eviction spam - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
Just like Aleo's `split` transaction charged a fixed 10-credit fee that never scaled with congestion and thus let an attacker cheaply flood blocks, Hyperbridge's `pallet-bandwidth` subscription model lets an *unrelated, unprivileged caller* pay the cheapest tier price and target **any** victim `(app_chain, app)` bucket, repeatedly appending throwaway subscriptions until the 1024-slot FIFO cap evicts the victim's real, unconsumed, higher-value subscription. The "cost" of griefing a victim's bandwidth purchase is fixed and trivial (cheapest tier × 1 month, no ownership check on `app`), while the victim's loss is the full unused byte-balance they already paid for.

### Finding Description
`BandwidthManager.purchase()` on EVM takes an arbitrary `app` and `chain` argument with no binding to `msg.sender`: [1](#0-0) 

This is intentional for the "sponsorship" feature (a payer on one chain can credit an app on another chain), documented explicitly: [2](#0-1) 

On the Hyperbridge side, `pallet-bandwidth::on_accept` decodes the purchase message and calls `push_subscription` keyed purely by `msg.chain` + `msg.app` from the message body — never checked against the actual payer: [3](#0-2) 

`push_subscription` enforces a hard cap of `MAX_SUBSCRIPTIONS = 1024` per `(chain, app)` key. When the list is full, the **oldest** entry is evicted regardless of its remaining byte balance or value — an FIFO cap-and-evict with no value-aware ordering: [4](#0-3) [5](#0-4) 

Because:
1. `purchase()` is fully permissionless and unauthenticated with respect to the target `app`/`chain` pair,
2. the cheapest tier (`TierOne`, $50/100KB) costs a fixed, small, non-scaling amount regardless of how full the victim's subscription queue is,
3. the FIFO eviction discards the oldest entry unconditionally — even a large, mostly-unused, expensive subscription,

an attacker can call `purchase(app=victim_app, tier=1, months=1, chain=victim_chain)` 1024 times (paying only `1024 × TierOne price`, a small, fixed, non-scaling cost) to fully displace a victim's real subscriptions from the FIFO queue. The victim's paid-for, unconsumed bandwidth (e.g., an $1000/8MB annual plan) is evicted and reported via `SubscriptionEvicted { lost_bytes }` — permanently lost, with no recourse, since eviction is silent and irreversible: [6](#0-5) 

This mirrors the H-2 pattern precisely: a transaction/message type (`split` / bandwidth `purchase`) has a **fixed cost that never increases** regardless of the harm it can inflict, and lacks any binding (fee-market pressure in H-2; ownership/ACL binding here) that would make the attack economically or logically infeasible. The "existing guard" — the 1024-slot cap meant to bound unbounded storage growth — is exactly what the attacker leverages, since eviction is oldest-first and value-blind.

### Impact Explanation
This is a direct, permissionless loss-of-funds vector: a victim app that legitimately prepaid for bandwidth (potentially a large annual/high-tier purchase) can have that paid allowance evicted and destroyed by any third party spending a comparatively trivial, fixed amount on the cheapest tier repeated up to 1024 times. Once evicted, the bytes are unrecoverable (`SubscriptionEvicted` is a one-way audit event, not a refund), and the victim app's dispatches subsequently get rejected by the `BandwidthGate` (`GateError::NoAllowance`/`Insufficient`), causing denial of legitimate cross-chain messaging on top of the direct financial loss. This satisfies the bounty's "stealing or loss of funds" and "logic attack" impact categories, executed entirely through a public entrypoint with no relayer/prover/admin/governance actor needed.

### Likelihood Explanation
High. `purchase()` requires no special permission — any address can call it with an arbitrary `app`/`chain` pair as long as it pays the (fixed, cheap) tier price for the purchase. The attacker doesn't need to know anything about the victim beyond their public `app` identifier and `app_chain`, both of which are visible on-chain via `BandwidthCredited`/`BandwidthPurchased` events. 1024 purchases at the cheapest tier is economically trivial compared to, e.g., a victim's $1000-tier purchase, making this a cheap, repeatable griefing/theft primitive.

### Recommendation
- Bind `purchase()` targeting to the payer, or require an explicit authorization/allow-list from the target `app` before crediting to it (opt-in sponsorship rather than fully open write access to any `(chain, app)` bucket).
- Change eviction policy to be value-aware (e.g., evict smallest-remaining-value or nearest-to-expiry entries) rather than strict FIFO, or reject new pushes once the cap is reached instead of silently evicting.
- Consider a minimum tier-price floor per evicting purchase relative to the entries being displaced, or rate-limit/cost-scale repeated purchases against the same `(chain, app)` key from third parties to prevent cheap queue-flooding.

### Proof of Concept
1. Victim purchases `TierFour` (8MB, 12 months) for `(chain=EVM-8453, app=Victim)` via `BandwidthManager.purchase(app=Victim, tier=4, months=12, chain="EVM-8453")`. This is credited on Hyperbridge as subscription #1 in `Allowance[EVM-8453][Victim]`.
2. Attacker (any unrelated address, no relationship to Victim) repeatedly calls `BandwidthManager.purchase(app=Victim, tier=1, months=1, chain="EVM-8453")` 1024 times, each dispatching a `BandwidthPurchaseMsg{app: Victim, tier: 1, months: 1, chain: "EVM-8453"}` to `pallet-bandwidth`.
3. Each `on_accept` call appends a new cheap `TierOne` subscription via `push_subscription` to `Allowance[EVM-8453][Victim]`; once the list hits `MAX_SUBSCRIPTIONS = 1024`, subsequent pushes evict the oldest entry — eventually evicting Victim's `TierFour` subscription entirely (see `modules/pallets/bandwidth/src/lib.rs:404-437`).
4. `SubscriptionEvicted { app_chain: EVM-8453, app: Victim, tier: TierFour, lost_bytes: <remaining 8MB*12> }` fires — Victim's paid bandwidth is gone.
5. Victim's subsequent legitimate dispatches through the `BandwidthGate` (`try_consume`) now see only attacker's low-value `TierOne` remnants (or none), causing `GateError::Insufficient`/`NoAllowance` and rejecting Victim's cross-chain messages — denial of service plus the direct loss of the prepaid credits.

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
