### Title
Fail-open exception handling in Hookify `PreToolUse`/`Stop` hooks allows attacker-controlled tool input to silently bypass "block" rules — (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
This is analogous to the reported `ArbitrumBranchBridgeAgent._performCall()` bug: a component that is supposed to propagate a failure/deny signal instead swallows it and lets the caller proceed as if everything succeeded. In Hookify, `RuleEngine.evaluate_rules()` is meant to return a `"permissionDecision": "deny"` when a `block` rule matches attacker/user-controlled tool input (e.g. a `Bash` command). However, `pretooluse.py` and `stop.py` wrap the entire evaluation in a broad `try/except Exception` and unconditionally `sys.exit(0)` in a `finally` block regardless of whether evaluation raised an exception mid-way through condition checking — before a matching `block` rule could be recorded and returned.

### Finding Description
`pretooluse.py` reads the tool call, loads rules, and calls `RuleEngine.evaluate_rules(rules, input_data)`: [1](#0-0) 

Inside `evaluate_rules`, each rule is checked via `_rule_matches`, which iterates over `rule.conditions` and calls `_check_condition` → `_extract_field`, only accumulating a rule into `blocking_rules` after `_rule_matches` returns `True` for the *entire* condition set: [2](#0-1) [3](#0-2) 

If evaluating any earlier rule's condition throws an unhandled exception (e.g., `_extract_field` string operations on non-string `tool_input` values, or condition operators like `.startswith(pattern)`/`.endswith(pattern)` called on a field value that isn't guaranteed to be a string in all code paths, or a `KeyError`/`TypeError` from malformed but user-writable rule files or crafted `tool_input`), the exception propagates out of `evaluate_rules` before a later `block` rule (e.g. `block-dangerous-rm` matching `rm -rf`) is ever reached and returned.

Critically, `pretooluse.py`'s outer handler does not distinguish "hook infrastructure failure" from "mid-evaluation crash that skipped a `block` verdict" — both are treated identically: [4](#0-3) 

The `finally: sys.exit(0)` always signals "allow" to Claude Code's `PreToolUse` gate, since no `hookSpecificOutput.permissionDecision: "deny"` was ever emitted. This mirrors the Solidity bug exactly: the intended failure/deny signal (`permissionDecision: "deny"`) is computed only on the "happy path", and any exception thrown partway through evaluation causes the caller to silently proceed as if the check had passed — just as `ArbitrumBranchBridgeAgent._performCall()` ignored `anyExecute()`'s `success == false` and let execution continue.

### Impact Explanation
A user (or a crafted rule/tool-input combination) that triggers an exception during condition evaluation of *any* loaded rule causes **all** rules — including unrelated `block` rules meant to stop dangerous operations like `rm -rf` — to be silently skipped for that invocation, and the tool call proceeds unblocked. This is a genuine command-approval bypass: the explicit design goal of Hookify's `block` action ("Prevents operation from executing") is defeated by an unrelated crash. The same fail-open pattern exists in `stop.py`, allowing an agent to bypass a `block` rule intended to prevent premature session stop (e.g., "must run tests first").

### Likelihood Explanation
Likelihood is moderate: the rule-loading and field-extraction code already anticipates several failure modes (`config_loader.load_rules` catches `IOError`/`ValueError`/generic `Exception` per rule file), but `RuleEngine._check_condition`/`_extract_field` has no equivalent per-condition exception isolation — only `_regex_match` catches `re.error`. Any operator (`contains`, `starts_with`, `ends_with`) applied when `field_value` is unexpectedly non-string, or a condition dict with unexpected types from a manually/AI-authored `.claude/hookify.*.local.md` file, would raise and abort evaluation for the whole rule set, not just the offending rule.

### Recommendation
- In `RuleEngine.evaluate_rules`/`_rule_matches`, wrap per-rule (or per-condition) evaluation in its own `try/except`, so an exception in one rule cannot suppress evaluation of the remaining rules — especially `block` rules.
- In `pretooluse.py`/`stop.py`, distinguish "hook crashed before producing any verdict" from "no rule matched": on crash, either fail closed for rules that could not be evaluated, or at minimum surface a clear warning rather than silently defaulting to full allow.
- Add defensive type coercion in `_extract_field`/`_check_condition` so operators never receive non-string values unexpectedly.

### Proof of Concept
Not independently executed (index-only investigation); conceptual PoC based on code inspection:
1. Create `.claude/hookify.dangerous-rm.local.md` with `event: bash`, `action: block`, `pattern: rm\s+-rf` (a legitimate, common Hookify rule from the plugin's own README).
2. Additionally load a second, earlier-iterated rule file with a condition whose `field`/`operator` combination causes `_check_condition` to raise (e.g. an `ends_with`/`starts_with` operator against a `tool_input` field that resolves to a non-string, or a condition referencing a field that `_extract_field` returns as something other than `str`/`None`).
3. Invoke the `Bash` tool with `rm -rf /important/path`.
4. Because rule iteration in `evaluate_rules`/`_rule_matches` has no per-rule exception isolation, the exception raised while evaluating the earlier rule propagates up through `evaluate_rules`, is caught by `pretooluse.py`'s outer `except Exception`, and `finally: sys.exit(0)` allows the `rm -rf` command to execute — despite the matching `block-dangerous-rm` rule that should have denied it. def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
