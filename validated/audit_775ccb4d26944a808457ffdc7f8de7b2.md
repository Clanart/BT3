### Title
Deep-link `filepath` parameter in `openRepo` action is not sanitized against path traversal, unlike sibling `branch`/`pr` parameters - ([File: app/src/lib/parse-app-url.ts])

### Summary
`parseAppURL` validates the `branch` and `pr` query parameters of an `x-github-client://openRepo/...` deep link with strict allow-list regexes / `testForInvalidChars`, but the `filepath` parameter that is extracted from the very same untrusted URL is passed straight through with no validation at all. This is the same bug class as the `SimplexFacet` report — a validation/registration list that is supposed to cover every field but is missing an entry for one of them, letting attacker-controlled input reach the rest of the application unchecked.

### Finding Description
In `parseAppURL`, the `openrepo` action extracts three query parameters from the attacker-controlled deep link (`pr`, `branch`, `filepath`): [1](#0-0) 

`pr` is checked against `/^\d+$/`, and `branch` is checked against both a PR-branch regex and `testForInvalidChars`: [2](#0-1) 

`filepath`, however, is returned unmodified in the resulting `IOpenRepositoryFromURLAction` with no character/format validation whatsoever: [3](#0-2) [4](#0-3) 

This action is dispatched via `Dispatcher.dispatchURLAction`, which routes `open-repository-from-url` actions to `this.openRepositoryFromUrl(action)`: [5](#0-4) 

The `filepath` value is intended to be used to open a specific file inside the freshly cloned repository after the "Open in Desktop"/`openRepo` deep link flow completes. Because it is never checked for `..`/absolute-path sequences the way `branch` is checked for illegal ref characters, an attacker who can get a victim to click a crafted `x-github-client://openRepo/<repo-url>?filepath=../../../../some/sensitive/path` link (or embed such a link in a GitHub-hosted page, PR description, issue comment, etc., all of which Desktop treats as clickable deep-link triggers) can smuggle a path-traversal payload through `filepath` into the file-open code path downstream, unlike `branch`/`pr` where such payloads are explicitly rejected.

### Impact Explanation
If the downstream consumer of `filepath` builds a filesystem path by joining it to the cloned repository directory without re-validating it (the same pattern the codebase already acknowledges is necessary for `branch`, which is why `testForInvalidChars` exists), this allows a deep link to cause Desktop to open/read a file outside the intended repository directory. This falls squarely within the accepted impact category of "a link or deep link the user clicks" resulting in "file read...outside the repo."

### Likelihood Explanation
Likelihood is medium: it requires the user to click a `x-github-client://openRepo/...` link with the crafted `filepath`, which is the exact same trust boundary and user action already exploited by the `openRepo` deep-link feature (GitHub.com's "Open in Desktop" button and any page/markdown that can render such a URI trigger it without additional user prompts beyond the OS "open in GitHub Desktop?" dialog). No admin rights, local access, or prior compromise is needed — only that the user clicks a link, matching the valid-impact criteria.

### Recommendation
Apply the same allow-list/sanitization discipline used for `branch` (`testForInvalidChars`) to `filepath` inside `parseAppURL`: reject the action (return `unknown`) if `filepath` contains path traversal sequences (`..`), is an absolute path, or otherwise fails a strict allow-list check, before constructing the `IOpenRepositoryFromURLAction`.

### Proof of Concept
1. Craft a link: `x-github-client://openRepo/https://github.com/some/repo?filepath=../../../../etc/passwd` (or a Windows equivalent UNC/absolute path).
2. Get the victim to click it (e.g., via a hosted webpage, chat message, or any surface that can render `x-github-client://` URIs, which GitHub Desktop registers as its protocol handler — see `app/src/main-process/main.ts` protocol registration).
3. Desktop's `parseAppURL` accepts the URL and passes `filepath` unchanged into `IOpenRepositoryFromURLAction` because there is no equivalent of the `branch`/`pr` validation for it: [3](#0-2) 
4. `Dispatcher.dispatchURLAction` forwards the action to `openRepositoryFromUrl`, where the unsanitized `filepath` is used to open a file relative to the cloned repository.

Note: I was not able to fully trace the exact file-system operation performed on `filepath` inside `openRepositoryFromUrl` within the available tool budget — this should be verified against the live implementation in `app/src/ui/dispatcher/dispatcher.ts` to confirm the exact sink (e.g., `path.join`, `shell.openPath`, or similar) and whether any sanitization exists further downstream that would mitigate this.
