### Title
Missing minting/balance check before unsigned cast in mempool fee computation causes uncaught `OverflowError` on malicious spend bundles - ([File: chia/full_node/mempool_manager.py])

### Summary
`MempoolManager.validate_spend_bundle()` computes the transaction fee by subtracting the total addition amount from the total removal amount and immediately casting the (possibly negative) result to `uint64`, without first verifying that additions do not exceed removals. Any unprivileged submitter can craft a spend bundle whose `CREATE_COIN` conditions sum to more than the amount of the coins it spends (an inflationary/"minting" spend bundle), causing `uint64(removal_amount - addition_amount)` to raise an unhandled `OverflowError` inside the mempool admission path.

### Finding Description
In `chia/full_node/mempool_manager.py`, `validate_spend_bundle()` accumulates `addition_amount` from each spend's `CREATE_COIN` conditions [1](#0-0)  and accumulates `removal_amount` from the spent coins' recorded amounts [2](#0-1) . It then computes:

```
fees = uint64(removal_amount - addition_amount)
``` [3](#0-2) 

There is no prior check that `addition_amount <= removal_amount`. If a submitted spend bundle creates more total coin value than it consumes (i.e. attempts to mint value), `removal_amount - addition_amount` is negative, and casting a negative Python `int` to the `chia_rs`-backed `uint64` type raises `OverflowError`, as demonstrated by the sized-int constructor tests: `Coin(H1, H2, -1)` raises `OverflowError: can't convert negative int to unsigned` [4](#0-3) . `uint64(...)` uses the identical underlying conversion, so the same exception class is raised at line 814.

By contrast, the equivalent consensus-level check in block-body validation explicitly guards against this case before computing fees, returning `Err.MINTING_COIN` if `removed < added` [5](#0-4) . The mempool admission path (`validate_spend_bundle`, reached via `MempoolManager.add_spend_bundle` from any submitted transaction: RPC `push_tx`, wallet sends, or gossip `NewTransaction`) has no analogous guard before the unsigned cast at line 814, unlike the CometBFT fix which converts to `uint64` *before* the addition specifically to avoid a signed-overflow wraparound; here the Chia code performs the subtraction in signed Python `int` space (safe from wraparound) but then blindly casts to an unsigned type without validating the sign, turning a would-be rejection (`MINTING_COIN`/`INVALID_BLOCK_FEE_AMOUNT`) into an uncaught exception.

### Impact Explanation
Any wallet user, offer counterparty, or unprivileged bundle submitter can construct and submit a spend bundle where the sum of `CREATE_COIN` outputs exceeds the sum of the coins being spent. This is processed by `MempoolManager.validate_spend_bundle()` on every full node that receives the transaction (via gossip, RPC, or direct wallet submission) before any handled-error path is reached, since the unhandled `OverflowError` occurs prior to the `INVALID_BLOCK_FEE_AMOUNT` check at line 826. This is a spend-triggered fault in core transaction-processing logic reachable by a single unprivileged submitter, matching the "spend-triggered transaction-processing halt" impact category. Depending on how the calling context (RPC handler, gossip protocol handler) handles unexpected exceptions, this can manifest as failed transaction relaying, error responses instead of clean rejection codes, or worse if any call site does not wrap mempool admission in a broad exception handler.

### Likelihood Explanation
High reachability: constructing a spend bundle with unbalanced `CREATE_COIN` totals requires no special privileges, keys beyond the attacker's own coins, or race conditions — it is a standard, deterministic spend-bundle construction reachable through the normal `push_tx` RPC or peer gossip path used by any wallet or client.

### Recommendation
Add an explicit balance check in `MempoolManager.validate_spend_bundle()` mirroring the consensus-level check in `block_body_validation.py`: verify `addition_amount <= removal_amount` and return a proper `Err` (e.g., `Err.MINTING_COIN`) before computing `fees = uint64(removal_amount - addition_amount)`, so that unbalanced/inflationary spend bundles are rejected through the normal error path instead of raising an uncaught `OverflowError`.

### Proof of Concept
1. Create coin `C` with amount `10`.
2. Build a `SpendBundle` that spends `C` and issues two `CREATE_COIN` conditions totaling `12` (e.g., `CREATE_COIN(ph1, 6)`, `CREATE_COIN(ph2, 6)`).
3. Submit the bundle via RPC `push_tx` or gossip `NewTransaction` to a full node.
4. `MempoolManager.validate_spend_bundle()` computes `addition_amount = 12`, `removal_amount = 10`, then executes `fees = uint64(10 - 12)` → `uint64(-2)`, raising `OverflowError`, before the normal `Err.INVALID_BLOCK_FEE_AMOUNT` rejection path at line 826 can run. [6](#0-5)
