### Title
Data race on `auctionEntryPointVersion` in `BidPool.getBidTxGasLimit` bypasses the mutex that protects it elsewhere - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
`BidPool` guards `auctioneer`, `auctionEntryPoint`, `auctionEntryPointVersion`, and `bidTxGasBuffer` with `auctionInfoMu`, and `updateAuctionInfo` correctly takes the write lock before mutating all four fields together. However, `getBidTxGasLimit`, which runs on every `AddBid` call from an external bidder, only takes `auctionInfoMu.RLock()` to read `bidTxGasBuffer` and then reads `bp.auctionEntryPointVersion` **after releasing the lock**, with no synchronization at all. This is the same bug class as the reported ALSA `input_dev` issue: a field that is nominally protected by a mutex is read through a code path that doesn't actually hold that mutex while another goroutine can concurrently mutate it.

### Finding Description
`BidPool` declares:
```go
auctionInfoMu            sync.RWMutex
auctioneer               common.Address
auctionEntryPoint        common.Address
auctionEntryPointVersion string
bidTxGasBuffer           uint64
``` [1](#0-0) 

`updateAuctionInfo` (invoked from the auction module's block-processing/execution path whenever the on-chain auctioneer/entry-point config changes) takes the full write lock and updates all of `auctioneer`, `auctionEntryPoint`, `auctionEntryPointVersion`, and `bidTxGasBuffer` together:
```go
func (bp *BidPool) updateAuctionInfo(auctioneer common.Address, auctionEntryPoint common.Address, auctionEntryPointVersion string, bidTxGasBuffer uint64) {
	bp.auctionInfoMu.Lock()
	defer bp.auctionInfoMu.Unlock()
	...
	bp.auctioneer = auctioneer
	bp.auctionEntryPoint = auctionEntryPoint
	bp.auctionEntryPointVersion = auctionEntryPointVersion
	bp.bidTxGasBuffer = bidTxGasBuffer
	...
}
``` [2](#0-1) 

But `getBidTxGasLimit`, called from `AddBid` for every incoming bid, releases the lock before touching `auctionEntryPointVersion`:
```go
func (bp *BidPool) getBidTxGasLimit(bid *auction.Bid) (uint64, error) {
	bp.auctionInfoMu.RLock()
	buffer := bp.bidTxGasBuffer
	bp.auctionInfoMu.RUnlock()

	data, err := system.EncodeAuctionCallData(bid, bp.auctionEntryPointVersion)
	...
``` [3](#0-2) 

`AddBid` — the entry point directly reachable by any auction bidder submitting a bid — calls this unguarded function:
```go
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	...
	gasLimit, err := bp.getBidTxGasLimit(bid)
	...
``` [4](#0-3) 

Because Go strings are two-word headers (pointer + length), a concurrent unsynchronized read of `bp.auctionEntryPointVersion` while `updateAuctionInfo` is writing it can observe a torn value (e.g., new pointer with old length or vice versa), which can lead to reading out-of-bounds/garbage memory when the string is subsequently used, or otherwise using a stale/inconsistent version identifier in `system.EncodeAuctionCallData`. This mirrors the CVE's root cause: a resource nominally protected by a lock is accessed on a specific path without holding it, opening a TOCTOU/race window between the unregistration (here: `updateAuctionInfo`) and the use (here: `getBidTxGasLimit`).

### Impact Explanation
`auctionEntryPointVersion` determines how `EncodeAuctionCallData` encodes the auction settlement call data (e.g., which EIP-712 version/format is used to build the on-chain call to the auction entry point). A torn/incorrect read of this field can cause the bid pool to compute call data using a mismatched version, which can result in:
- Bid transactions being built/gas-limited against the wrong auction entry-point calling convention, causing bid settlement transactions to revert or be executed with incorrect parameters.
- In the worst case (data race producing a corrupted string header), a runtime panic/crash of the node process handling bid submissions, which is a liveness/DoS impact on the node's bid-processing path.
Given the auction module handles value-bearing bids and their eventual on-chain settlement, corruption in the encoded call data can also affect fee/settlement correctness for auction winners. This is rated Medium, matching the CVE's severity, since it is a genuine, unprivileged-reachable data race, but exploitation requires precise timing (bid submission racing with an on-chain auctioneer/entry-point config change).

### Likelihood Explanation
`AddBid` is called for every bid submitted by any external searcher/bidder via `HandleBid`/RPC-facing bid ingestion, so the racy read happens on a very hot, externally triggered path. `updateAuctionInfo` runs whenever the auction system contract's auctioneer/entry-point/version changes are detected during block processing — an event that is infrequent but entirely plausible in production once governance or the system contract owner rotates the auctioneer or entry-point version. Any bid submitted in the same instant as such an update can hit the race; the `-race` detector would flag every `AddBid` call as racy relative to `updateAuctionInfo`, meaning this is a genuine, reproducible correctness bug rather than a purely theoretical one.

### Recommendation
Read `auctionEntryPointVersion` under the same `auctionInfoMu.RLock()` critical section that already protects `bidTxGasBuffer` in `getBidTxGasLimit`, e.g.:
```go
bp.auctionInfoMu.RLock()
buffer := bp.bidTxGasBuffer
version := bp.auctionEntryPointVersion
bp.auctionInfoMu.RUnlock()

data, err := system.EncodeAuctionCallData(bid, version)
```
More broadly, audit all direct field reads of `auctioneer`, `auctionEntryPoint`, and `auctionEntryPointVersion` in `bid_pool.go` to ensure every access goes through `auctionInfoMu`, consistent with the pattern used for `GetAuctionEntryPoint`/`GetAuctionEntryPointVersion`.

### Proof of Concept
1. Run `go test -race ./kaiax/auction/impl/...` with a test that concurrently:
   - Repeatedly calls `bp.updateAuctionInfo(newAuctioneer, newEntryPoint, "v2-changed", newBuffer)` from one goroutine.
   - Repeatedly calls `bp.AddBid(bid)` (which internally calls `getBidTxGasLimit`) from another goroutine.
2. The Go race detector will report a data race between the write to `bp.auctionEntryPointVersion` in `updateAuctionInfo` (bid_pool.go:209) and the unguarded read in `getBidTxGasLimit` (bid_pool.go:490), confirming the unsynchronized access analogous to the ALSA `input_dev` mutex-bypass bug.

func (bp *BidPool) updateAuctionInfo(auctioneer common.Address, auctionEntryPoint common.Address, auctionEntryPointVersion string, bidTxGasBuffer uint64) {
	bp.auctionInfoMu.Lock()
	defer bp.auctionInfoMu.Unlock()

	if bp.auctioneer == auctioneer && bp.auctionEntryPoint == auctionEntryPoint && bp.auctionEntryPointVersion == auctionEntryPointVersion && bp.bidTxGasBuffer == bidTxGasBuffer {
		return
	}

	// Clear the existing auction pool since the auctioneer or auction entry point address is changed.
	bp.clearBidPool()

	bp.auctioneer = auctioneer
	bp.auctionEntryPoint = auctionEntryPoint
	bp.auctionEntryPointVersion = auctionEntryPointVersion
	bp.bidTxGasBuffer = bidTxGasBuffer

	logger.Info("Update auction info", "auctioneer", auctioneer, "auctionEntryPoint", auctionEntryPoint, "auctionEntryPointVersion", auctionEntryPointVersion, "bidTxGasBuffer", bidTxGasBuffer)
}

func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)
