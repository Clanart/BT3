## Analysis

The seed bug's core invariant is: **a "this-is-the-last-one" completion branch substitutes the live aggregate balance for the tracked per-unit owed amount**, letting whoever triggers the completion branch harvest the pooled balance rather than only their fair share — starving the next legitimate claimant.

The exact structural analog exists in Hyperbridge's same-chain Intent Gateway fill logic.

### Root cause

`_orders` is a `mapping(bytes32 => mapping(address => uint256))` keyed only by `(commitment, tokenAddress)` — not by output-pair index: [1](#0-0) 

`placeOrder` explicitly rejects **duplicate output tokens** using transient-storage dedup, but performs **no equivalent check on `order.inputs`**: [2](#0-1) 

So a user can construct an order with two (or more) `output.assets[i]` entries mapped by index to two `inputs[i]` entries that share the **same input token address**. Because escrow is accumulated by token address, both legs' escrowed amounts land in the same `_orders[commitment][token]` slot.

In `_fillSameChain`, when a fill causes a given output-index pair to reach `amountFilled == totalRequired` (i.e., "this pair is now fully done"), the code does **not** compute the proportional amount owed for that specific pair — it instead reads the entire current pooled balance for the token: [3](#0-2) 

This is the same shape as `LogarithmVault.claim`'s `isLast` branch reading `idleAssets()` (the whole current balance) instead of the tracked `requestedAssets` — a "completion" special-case that trusts the aggregate balance rather than the owed amount.

### Exploit path

1. User places one order with two output legs (e.g. `output.assets[0] = 100 DAI`, `output.assets[1] = 900 DAI`) whose paired inputs are **the same token** (`inputs[0].token = inputs[1].token = USDC`, amounts 100 and 900 respectively). `placeOrder`'s dedup only checks `output.assets`, so this is accepted; `_orders[commitment][USDC]` accumulates to `1000`.
2. A solver (can be the user's own colluding solver, or any solver racing to fill the cheap leg first) fully fills only the small leg (`output[0]`, 100 DAI) in a single call.
3. Inside `_fillSameChain`, for index 0, `amountFilled == totalRequired` is true, so `escrowedAmount = _orders[commitment][USDC]` reads **1000**, not the ~100 actually earned for that leg.
4. `_withdraw` transfers the full 1000 USDC to this solver and zeroes `_orders[commitment][USDC]`.
5. Any subsequent solver trying to fill the remaining `output[1]` (900 DAI) delivers real tokens to the beneficiary but `_withdraw` finds `escrowed == 0` and reverts with `UnknownOrder()` — rolling back their fill entirely, and permanently stranding the order (the user's `900 DAI` leg can never be filled by anyone since the backing escrow is gone).

This is unauthorized fund extraction (wrong amount to the beneficiary, sourced from escrow that belongs to a *different, unrelated* order leg) reachable by any public, unprivileged caller (the order-placing user and a cooperating/racing solver) — no relayer, prover, or admin compromise needed, matching the bounty's "unauthorized transaction/execution" and "wrong beneficiary or amount" categories.

### Recommendation
- Reject orders whose `inputs[]` contain duplicate token addresses at different indices, mirroring the existing output-token dedup in `placeOrder`.
- Independently, `_fillSameChain`'s "last fill" branch should not fall back to reading the raw `_orders[commitment][token]` balance; it should use the exact residual amount owed for that specific index (`order.inputs[i].amount - alreadyReleased[i]`), tracked per-pair rather than derived from the pooled per-token escrow.

### Proof of Concept (conceptual)
```solidity
// Order: two legs sharing the same input token
inputs[0] = {token: USDC, amount: 100e6};
inputs[1] = {token: USDC, amount: 900e6};
output.assets[0] = {token: DAI, amount: 100e18};
output.assets[1] = {token: DAI, amount: 900e18};
// placeOrder succeeds — output tokens differ, dedup check on inputs is absent.
// _orders[commitment][USDC] == 1000e6

// Solver fully fills leg 0 only:
fillOrder(order, {outputs: [{token: DAI, amount: 100e18}]});
// -> amountFilled == totalRequired for index 0
// -> escrowedAmount = _orders[commitment][USDC] == 1000e6 (not 100e6)
// -> solver receives all 1000 USDC for delivering only 100 DAI worth of output

// Any later attempt to fill leg 1 (900 DAI) reverts UnknownOrder() — order permanently stuck,
// remaining 900 USDC economically lost from the intended backing.
```

**Uncertainty**: I confirmed the dedup check exists only for `order.output.assets` in `placeOrder` (`evm/src/apps/IntentGatewayV2.sol`) and not for `order.inputs`, and confirmed the raw-balance read in `_fillSameChain` (`IntrinsicIntents.sol:116-121`), which the repo's own tests label "Finding #4" and frame as a rounding-dust fix rather than a duplicate-input-token exploit — so this specific attack combination has not been exercised by the existing test suite. I did not find a Foundry test that places an order with duplicate input tokens across indices, so the exact runtime revert path in `_withdraw` for the stranded second leg is inferred from the code (`escrowed == 0 → revert UnknownOrder()`) rather than observed in a passing/failing test.

        if (order.inputs.length == 0) revert InvalidInput();
