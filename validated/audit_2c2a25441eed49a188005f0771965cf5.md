### Title
External deposits to reserved offset addresses are misclassified as internal outputs and never credited - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` classifies every scanned output by looking up its registered scanner offset in a `kind` map. The offsets for `OutputType::Branch`, `OutputType::Change`, and `OutputType::Forwarded` are deterministic, publicly derivable `hash_to_F` constants (`Secp256k1::hash_to_F(KEY_DST, b"branch"|"change"|"forward")`). Because `Scanner::scan_transaction` matches only `script_pubkey`, any third party can send Bitcoin to one of these reserved P2TR scripts, and the processor will tag the output as an internal `Branch`/`Change`/`Forwarded` output rather than an `External` deposit.

### Finding Description
The offset constants are computed in `scanner()` at `processor/src/networks/bitcoin.rs:308-347`:

```rust
register(OutputType::Branch,   Secp256k1::hash_to_F(KEY_DST, b"branch"));
register(OutputType::Change,   Secp256k1::hash_to_F(KEY_DST, b"change"));
register(OutputType::Forwarded,Secp256k1::hash_to_F(KEY_DST, b"forward"));
```

Anyone knowing the group key (public) can compute `key + offset*G`, build the script via `p2tr_script_buf`, and pay to it — the `forward_address` helper itself derives such an address from the public key (`processor/src/networks/bitcoin.rs:671-674`).

In `get_outputs` (`processor/src/networks/bitcoin.rs:686-739`), scanned outputs are typed purely by offset:

```rust
let kind = kinds[offset_repr_ref];
let output = Output { kind, presumed_origin: None, output, data: vec![] };
```

and Serai data (the deposit instruction / `InInstruction` payload extracted via `extract_serai_data`) is only attached to `OutputType::External` outputs (`processor/src/networks/bitcoin.rs:731-735`).

### Impact Explanation
An unprivileged depositor — or a griefer — can send BTC to the `Forwarded`/`Change`/`Branch` scripts. The resulting `Output` is reported to the coordinator as an internal-kind output, so:

- The deposited funds are not treated as a user deposit: no `data` is attached (`data` is only cloned onto `External` outputs), so no `InInstruction` is processed and no credit is issued to the sender.
- The output lands in the wrong handling lane (e.g., `Forwarded` outputs are meant for outputs the protocol itself created to forward to processors), meaning the funds may be ignored by the scheduler or spent under an incorrect assumption, effectively becoming stuck/unaccounted — analogous to the Wallet contract crediting a user with tokens it cannot handle.
- The `presumed_origin` of `tx.input[0]` is attached to these outputs as well (`processor/src/networks/bitcoin.rs:731-736`), letting an attacker set arbitrary origin metadata on internally-typed outputs.

### Likelihood Explanation
The scripts are fully derivable from the public group key and fixed `hash_to_F` constants; no internal state is needed. Any party that can send a Bitcoin transaction can trigger the misclassification. The classification path (`scanner.scan_transaction` → `kinds[offset]`) runs on every non-coinbase transaction in every scanned block with no authentication of the sender.

### Recommendation
Do not classify outputs solely by registered offset for transactions the protocol did not create. Options:

- Only attach `OutputType::Branch`/`Change`/`Forwarded` to outputs in transactions that the coordinator itself constructed (match by expected `txid`/internal record), and treat any other payment to a reserved script as `External` (or reject/ignore it with an explicit alert).
- Alternatively, reserve only the external deposit script for scanning and handle change/branch/forward bookkeeping internally rather than by offset lookup over arbitrary on-chain transactions.

### Proof of Concept
1. Obtain the current group key `key` (public) and compute `forward_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")`, incremented per `register_offset` parity rules until `p2tr_script_buf(key + forward_offset*G)` returns `Some`.
2. Send a Bitcoin transaction paying `p2tr_script_buf(key + forward_offset*G)` with an `InInstruction`-style OP_RETURN payload.
3. `get_outputs` scans the block: `scan_transaction` matches `script_pubkey`, `kinds[offset_repr]` returns `OutputType::Forwarded`, and because `kind != External`, the deposit data is dropped (`processor/src/networks/bitcoin.rs:731-735`). The output is reported as a `Forwarded` internal output and the depositor is never credited — the funds are received by the wallet but not spendable/credited as a deposit.   pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
