### Title
Payout attribution can be forged by any third party via unsigned OP_RETURN, letting an operator claim reimbursement for a payout it never funded - ([File: core/src/task/payout_checker.rs])

### Summary
The `payout_payer_operator_xonly_pk` column that `PayoutCheckerTask::run_once` relies on (`get_first_unhandled_payout_by_operator_xonly_pk`) is populated purely from an OP_RETURN output in the confirmed payout transaction [1](#0-0) , but that OP_RETURN output is not covered by the only signature present on the payout transaction. Since the user's withdrawal signature uses `SinglePlusAnyoneCanPay` and is verified only over input 0 / output 0, anyone can take a broadcast-but-unconfirmed payout transaction, replace its funding input(s) and its OP_RETURN operator key, and get their own version mined — causing the DB (and ultimately the operator whose key ends up in OP_RETURN) to be credited for a payout it never funded.

### Finding Description
The claimed binding is: `withdrawals.payout_payer_operator_xonly_pk == the operator whose own funds actually paid output 0 of the payout tx`. Tracing the code shows this binding is never established.

- In `Operator::withdraw`, the user's signature is verified with `payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` and the sighash type is enforced to be `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:174-187`, `core/src/operator.rs:630-637`). `SIGHASH_SINGLE | ANYONECANPAY` commits **only** to input 0 (the user's dust UTXO) and to output 0 (the user's payout amount/script). It commits to nothing else: not to any other input, not to the anchor output, and not to the OP_RETURN output that carries the operator attribution. [2](#0-1) 

- The operator then funds the transaction via `fund_raw_transaction` with `add_inputs: Some(true)` (ANYONECANPAY explicitly allows arbitrary extra inputs to be added without invalidating the user's signature) and broadcasts it. [3](#0-2) 

- `create_payout_txhandler` places the OP_RETURN with the claiming operator's xonly pubkey as an *unsigned* output (`op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()))`), outside the sighash commitment of the only signature in the transaction. [4](#0-3) 

- On confirmation, `Verifier::update_finalized_payouts` blindly trusts whatever OP_RETURN ends up in the mined transaction and writes it as the payer attribution with no cross-check against which UTXOs (i.e., whose wallet) actually funded the transaction. [5](#0-4) 

- `PayoutCheckerTask::run_once` then simply looks up "first unhandled payout attributed to *my* xonly key" and, upon finding one, calls `self.operator.handle_finalized_payout(...)`, `end_round`, and `mark_payout_handled` — advancing on-chain state (consuming a kickoff connector, potentially ending the round) purely based on that DB attribution. [6](#0-5) 

- The bridge circuit itself inherits the same weakness: it derives `operator_xonlypk` for the `deposit_constant` straight from the OP_RETURN of the payout transaction with no independent verification of who funded the transaction. [7](#0-6) 

**Exploit flow:** Operator A (or any innocent funder) constructs and broadcasts a valid payout tx with OP_RETURN = A's xonly pubkey, using their own extra inputs for fees/value (via `fund_raw_transaction`/RBF). Because ANYONECANPAY and SIGHASH_SINGLE leave everything except input 0/output 0 unsigned, an attacker who observes this transaction (e.g., in the mempool prior to confirmation) can rebuild an alternative transaction with: the same input 0 and output 0 (preserving the valid user signature), the attacker's own funding input(s) instead of A's, and an OP_RETURN naming operator B instead of A. The attacker then gets this version mined (e.g., by paying a higher fee and winning a mempool/replacement race, or submitting directly to a mining service) before A's original version confirms. No hashpower majority or key compromise is required — only broadcasting a transaction and paying fees, both explicitly within the attacker's allowed capability set.

Once mined, `update_finalized_payouts` records `payout_payer_operator_xonly_pk = B`. Operator B's `PayoutCheckerTask` then picks this up as an "unhandled payout" that B never funded, and drives `handle_finalized_payout` → kickoff → eventual `Reimburse` transaction, crediting B from the deposit's collateral/round funds for a withdrawal B never paid for.

None of the existing guards catch this: `is_deposit_valid`/`is_profitable` only run at the time operator A calls `withdraw` (before the malleation happens); `SECP.verify_schnorr` only verifies the user's signature over input0/output0, which remains valid in the malleated transaction; the bridge circuit's `deposit_constant`/journal computation reads the same unauthenticated OP_RETURN; and `verify_additional_disprove_conditions`/`is_kickoff_malicious` verify the operator's *kickoff commitments* (payout block hash, watchtower flags) against on-chain data, but never independently verify that the operator's own wallet funded the payout transaction's inputs.

### Impact Explanation
This directly matches the Critical impact category "an operator reimbursed for a payout it never funded." Operator B (or a colluding attacker who forges the credit onto B, or even onto themselves if they control an operator key) obtains a `Reimburse` transaction payout from the deposit's move-to-vault funds without having spent their own money to satisfy the user's withdrawal. Symmetrically, the honest operator (A) who actually funded the payout is left unable to claim reimbursement for that deposit, since the DB/attribution and hence `get_first_unhandled_payout_by_operator_xonly_pk` and the on-chain OP_RETURN both point to a different operator — matching "an honest operator permanently unable to be reimbursed." This is repeatable for every payout transaction broadcast by any operator, across every deposit and every operator in the round-robin set, as long as the attacker can win the confirmation race against the original broadcaster.

### Likelihood Explanation
Preconditions: the attacker must observe an operator's payout transaction before it is mined (via mempool visibility, which is standard) and be able to construct and broadcast a competing version with the same input0/output0 but different additional inputs/OP_RETURN, at an equal or higher fee to win the race. This requires no special privilege — only the ability to build and broadcast Bitcoin transactions and pay fees, which is explicitly within the defined attacker capability. The transaction uses `NON_STANDARD_V3` versioning, which may affect default mempool relay policy on some nodes, so in the least favorable case the attacker may need to submit directly to a mining pool or via a node/policy that accepts it; this doesn't require majority hashrate, just one block's inclusion, and is a realistic capability for a motivated single attacker. Given BTC withdrawal amounts (which can be sizable "move-to-vault" amounts), the attacker's cost (fees to win a mempool race, potentially none if they simply omit funding entirely and let their own transaction dominate) is small relative to the payoff (reimbursement of a whole deposit amount for the credited operator, or denial of reimbursement to a competitor operator).

### Recommendation
Bind the operator attribution cryptographically to the entity that actually funds/broadcasts the payout tx:
- Require the payout transaction's user-signed sighash to cover the OP_RETURN output (e.g., use `SIGHASH_ALL` semantics for the outputs that matter, or have the operator additionally co-sign a commitment — e.g., sign a message binding `(withdrawal_id, operator_xonly_pk, txid template)` — that is checked before the DB/attribution and before `handle_finalized_payout`/kickoff can proceed).
- Alternatively/additionally, when parsing OP_RETURN in `update_finalized_payouts`, verify that the operator named in OP_RETURN actually controls (signed) one of the additional inputs funding the transaction (e.g., check that at least one non-user input's scriptPubkey/witness corresponds to the claimed operator's known wallet/xonly key), rather than trusting the OP_RETURN bytes alone.
- Consider committing to the operator identity within the same sighash as the user's signature by restructuring the payout transaction (e.g., moving OP_RETURN before the anchor and constraining its position/content via `SIGHASH_SINGLE` semantics differently, or switching the user signature to `SIGHASH_ALL|ANYONECANPAY` if compatible with fee-bumping needs) so OP_RETURN cannot be altered without invalidating the user's signature.

### Proof of Concept
`cargo test` plan (regtest, no mainnet, no live Citrea — using the existing mock-Citrea harness as in `core/src/test/deposit_and_withdraw_e2e.rs`):
1. Set up two operators A and B and a mock Citrea client, register a deposit and a withdrawal UTXO (as in `mock_citrea_run_truthful`).
2. Have operator A call `withdraw(...)` to build and broadcast its payout tx (`Operator::withdraw`), capturing the raw hex before it confirms.
3. Programmatically construct a malleated version of A's transaction: keep input 0 (dust UTXO) and output 0 (user payout) byte-identical (preserving `in_signature`'s validity under `SinglePlusAnyoneCanPay`), replace A's additional funding input with a fresh attacker-controlled UTXO funded from the regtest faucet, and rewrite the OP_RETURN output to contain operator B's `xonly_public_key` instead of A's.
4. Broadcast the malleated tx and mine it (ensuring it is the one that gets included, e.g., by never broadcasting A's original, or using `prioritisetransaction`/an RBF-style replace).
5. Run the block sync so `Verifier::update_finalized_payouts` processes the block; assert `withdrawals.payout_payer_operator_xonly_pk == B` even though B never funded anything (query via `db.get_payout_info_from_move_txid` or the `withdrawals` table directly).
6. Run operator B's `PayoutCheckerTask::run_once` and assert it returns `Ok(true)`, that `handle_finalized_payout` was invoked (kickoff txid produced), and `mark_payout_handled` set `is_payout_handled = true` for that withdrawal index — proving B advanced state (and will eventually be reimbursed) for a payout it never funded, while A's payout attempt is permanently orphaned (assert operator A's own `PayoutCheckerTask` for the same withdrawal index finds nothing, i.e., `get_first_unhandled_payout_by_operator_xonly_pk(A)` returns `None` for that withdrawal).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;
