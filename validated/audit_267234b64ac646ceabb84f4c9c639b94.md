### Title
Desynchronization of `git log -z` NUL-delimited fields via attacker-controlled commit message causes silent commit metadata corruption - (File: `app/src/lib/git/git-delimiter-parser.ts`)

### Summary
`BatchDeposit2.sol`'s bug was a permissive boundary check on a flat, fixed-record-length byte string: because the check tolerated extra bytes, an attacker could inject bytes that shifted field boundaries and silently overwrote the *next* depositor's data. The same broken invariant — "assume clean, unbroken record boundaries in a delimiter-separated blob, with no validation that a record doesn't itself contain the delimiter" — exists in Desktop's `createLogParser`, which parses `git log -z --format=...%x00...` output by blindly splitting on NUL and re-grouping in fixed strides.

### Finding Description
`createLogParser` in [1](#0-0)  builds a format string joining fields with `%x00` and then parses the resulting output by splitting the whole stdout buffer on `\0` and re-assembling entries in fixed strides of `keys.length`:

```
for (let i = 0; i < records.length - keys.length; i += keys.length) {
  const entry = {} as { [K in keyof T]: V }
  keys.forEach((key, ix) => (entry[key] = records[i + ix]))
  entries.push(entry)
}
```

This is used by `getCommits()` in [2](#0-1)  to parse `sha (%H)`, `shortSha (%h)`, `summary (%s)`, `body (%b)`, `author`, `committer`, `parents (%P)`, `trailers`, and `refs (%D)` for every commit in one `git log` invocation over a possibly-attacker-controlled (cloned/fetched) repository.

The parser assumes each field value never itself contains a `\0` byte. Git's commit object format does not NUL-terminate or forbid NUL bytes inside the free-form commit message text (it's a length-prefixed, zlib-compressed blob) — a commit crafted with low-level plumbing (`git hash-object -w --stdin -t commit`) can contain a literal `0x00` byte inside its subject/body. When Desktop runs `git log -z --format=%H%x00%h%x00%s%x00%b%x00...` over such a commit, git emits that raw NUL byte in the middle of the `%b` (body) field's text, in addition to git's own `%x00` field separators. `splitBuffer`/`String.split('\0')` (used inside `createLogParser`, see [3](#0-2)  and [4](#0-3) ) cannot distinguish this embedded byte from a real field separator, producing one extra token. Because the loop consumes tokens in fixed strides with no re-synchronization or validation that the record boundaries are still aligned (analogous to the permissive `argv.length / 0xd0 == values.length` check), every subsequent commit's fields are shifted by one position for the remainder of the batch: `sha` for commit N+1 may actually hold what was `shortSha`, `summary` may hold a SHA, etc.

### Impact Explanation
`getCommits()` output feeds the commit history list and, critically, `reorder.ts`, which writes a `git rebase -i` todo file directly from the parsed `commit.sha` and `commit.summary` values: [5](#0-4)  `pick ${commit.sha} ${commit.summary}`. If the SHA field has been silently shifted/corrupted due to an embedded NUL earlier in the log stream, Desktop can construct a `pick` line for the *wrong* commit object, causing the interactive rebase machine to squash/reorder/drop a different commit than the one the user selected in the UI. This is exactly the class of impact called out as valid: "silent corruption of what the user commits or pushes," triggered purely by cloning/fetching a malicious repository — no local access, no admin rights, no social engineering beyond the normal act of opening/browsing a repo in Desktop.

### Likelihood Explanation
Exploitation requires only that the victim clone or fetch a repository containing one attacker-crafted commit whose message contains an embedded NUL byte (trivial to construct with `git hash-object`/`git commit-tree`), and that Desktop subsequently loads history (which happens automatically when opening the repository). No unusual interaction is required beyond normal repository browsing, and the corrupted parsing silently affects an entire `git log` batch (default `CommitBatchSize = 100`, see [6](#0-5) ), so a single crafted commit can desynchronize many subsequent legitimate commits' metadata.

### Recommendation
- Do not assume field values are free of the chosen delimiter. After splitting, validate that `records.length` is an exact multiple of `keys.length` (reject/log otherwise, rather than silently truncating or grouping misaligned records) — the direct analog of "use a strict length check" from the report.
- Prefer field-level escaping/quoting (e.g., percent-encoding via `git log --format` combined with a custom unescape step) or parse using a self-describing structure (e.g., emit an explicit record-count/length header per record) instead of relying purely on a delimiter that isn't guaranteed to be absent from arbitrary attacker-supplied commit content.
- Add a defensive check in `createLogParser`/`createForEachRefParser` that throws (rather than silently emitting misaligned entries) whenever leftover/misaligned tokens are detected, and add a regression test with a commit message containing a literal NUL byte.

### Proof of Concept
1. In a scratch repo, create a commit whose message contains a raw NUL byte using plumbing commands, e.g.:
   ```
   printf 'tree %s\nauthor A <a@a> 0 +0000\ncommitter A <a@a> 0 +0000\n\nfoo\x00bar\n' "$(git write-tree)" | git hash-object -w -t commit --stdin
   git update-ref refs/heads/evil <sha-from-above>
   ```
2. Create several ordinary commits after it.
3. Have the victim clone/fetch this repository into GitHub Desktop and open the History view (triggers `getCommits()` → `createLogParser`).
4. Observe that `sha`/`summary`/`author` fields for commits following the malicious one are shifted/misattributed (verifiable by comparing Desktop's displayed SHA/summary pairs against `git log` output).
5. Use "Reorder commits" (drag-and-drop) on the affected range; `reorder.ts` writes the corrupted `commit.sha`/`commit.summary` pairing into the rebase todo file, causing the interactive rebase to act on the wrong commit. [1](#0-0) [2](#0-1) [5](#0-4)

export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }

  return { formatArgs, parse }
}

export function splitBuffer(buffer: Buffer, delimiter: string): Buffer[] {
  const result = []
  let start = 0
  let index = buffer.indexOf(delimiter, start)
  while (index !== -1) {
    result.push(buffer.subarray(start, index))
    start = index + delimiter.length
    index = buffer.indexOf(delimiter, start)
  }
  if (start <= buffer.length) {
    result.push(buffer.subarray(start))
  }
  return result
}
