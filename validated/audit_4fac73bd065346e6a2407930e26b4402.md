### Title
Cached FROST seed is regenerated and signed with before the participant set is finalized, enabling nonce reuse across differing preprocess sets - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The reference bug is an ordering hazard: a state value (reserves) is read before a pending update (reward distribution) is applied, producing an operation over stale state. The analog in Serai is in `SigningProtocol::preprocess_internal` / `share_internal` (`coordinator/src/tributary/signing_protocol.rs:99-181`): a FROST preprocess seed is cached once per `context` and deterministically regenerated via `AlgorithmSignMachine::from_cache` on *every* call, before the final participant/preprocess set or the final message is necessarily fixed. Because the same seed is reused across all invocations for a context, any two `share_internal` executions that observe different `preprocesses` maps or different `msg` values emit two signature shares built on the same base nonces `d, e` — the classic FROST/ROS share-reuse failure that leaks the signer's secret share.

### Finding Description
`preprocess_internal` (lines 123–147) stores `CachedPreprocesses[context]` only if absent, then always loads it and calls `from_cache`, which runs `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`) deriving `nonces` and `commitments` from `ChaCha20Rng::from_seed(seed)`. The seed is never consumed or invalidated. `share_internal` (line 156) calls `preprocess_internal` again, so each call to `DkgConfirmer::share` (line 304) and `DkgConfirmer::complete` (line 312, which re-invokes `share_internal` at lines 321–324) regenerates the identical base nonces and produces a fresh share against whatever `preprocesses`/`key_pair` map the caller supplies at that moment. The share equation is `s = λ·x·c + d + ρ·e` where `ρ` is the binding factor over the preprocess set. Two executions with different participant sets (different `ρ`) yield `s₁ − s₂ = e·(ρ₁ − ρ₂)`, recovering nonce `e`; with the same set but a different `msg` (different challenge `c`) it yields `s₁ − s₂ = λ·x·(c₁ − c₂)`, recovering the MuSig/FROST secret share `x` directly.

### Impact Explanation
Recovery of the signer's private key share. For `DkgConfirmer`, `x` is the coordinator's MuSig key over the tributary validator set; for the same pattern applied to threshold `ThresholdKeys`, it is the FROST secret share of the network multisig — enabling forgery of threshold signatures and theft of vault funds.

### Likelihood Explanation
Reachability hinges on the coordinator invoking `share()`/`complete()` twice under one `(b"DkgConfirmer", attempt)` context with divergent inputs. `share()` returns `Err(Participant)` identifying a malicious preprocess submitter; if the coordinator retries the same attempt after dropping that participant, or if `complete()` is driven with a preprocess map that differs from the one used at `share()` time, the divergence is triggered by an unprivileged participant submitting a malformed preprocess. I could not fully verify within handle.rs whether retries re-key the context (incrementing `attempt` would be safe); the code itself contains no guard — the seed is unconditional reused whenever the context key matches, and nothing records that the seed was already consumed for signing.

### Recommendation
Delete or mark `CachedPreprocesses[context]` as consumed the first time `share_internal` produces a share, and refuse to sign a second time under the same context — mirroring the fix of applying `distributeRewards()` before reading reserves, the consumed-once invariant must be enforced in code rather than by caller discipline. Alternatively, mix the finalized participant set and `msg` into the seed (`seed' = H(seed || participants || msg)`) so differing inputs yield independent nonces.

### Proof of Concept
1. As a tributary validator in a DKG attempt, submit an invalid preprocess causing `share()` to return `Err(self_i)`; observe the coordinator's emitted share under set A.
2. Trigger a retry under the same `attempt` with the corrected participant set B.
3. Collect the second share; solve `s₁ − s₂ = e·(ρ_A − ρ_B)` for nonce `e`, then recover the secret share from either equation, or if the `KeyPair`/`msg` differed, recover `x` directly from `λ·x·(c₁ − c₂)`.
