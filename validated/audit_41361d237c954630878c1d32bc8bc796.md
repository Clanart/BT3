### Title
Path-traversal guard `resolveWithin` uses substring `startsWith` instead of a path-boundary check, allowing file read/write outside the repository root - ([File: app/src/lib/path.ts])

### Summary
`resolveWithin` (and its `resolveWithinPosix`/`resolveWithinWin32` wrappers) is the app-wide security boundary used to guarantee that a user- or attacker-influenced relative path stays inside a given root directory. It is relied on by the deep-link file-open handler in `dispatcher.ts` and by the Copilot merge-conflict-resolution pipeline to decide whether a path is safe to touch. The final check compares the resolved real path against the real root using plain string `startsWith`, with no trailing path-separator boundary. This is the classic "prefix confusion" bug: any sibling path whose name has the root directory's name as a string prefix (e.g. root `/Users/victim/repo` vs. sibling `/Users/victim/repo-secrets`) is incorrectly treated as "inside" the root.

### Finding Description
`_resolveWithin` computes the candidate path and validates containment like this: [1](#0-0) 

`realResolved.startsWith(realRoot)` is true whenever `realResolved` begins with the literal characters of `realRoot`, regardless of whether the next character is a path separator. If `rootPath` is `/Users/victim/Documents/GitHub/repo` and an attacker-supplied relative segment resolves (via `..` traversal, which the function otherwise permits as long as the *string comparison* passes — see the doc comment and the passing test `succeeds for paths that traverse out, and then back into, the root`) to `/Users/victim/Documents/GitHub/repo-secrets/id_rsa`, the check passes because `"...repo-secrets/id_rsa".startsWith("...repo")` is `true`, even though `repo-secrets` is a completely different directory. The existing unit tests in `app/test/unit/path-test.ts` only cover exact-root and symlink-escape cases; they never test the sibling-prefix scenario, so this bypass is unguarded and unnoticed by the test suite: [2](#0-1) 

This broken primitive is consumed in at least two attacker-reachable paths:

1. **Deep link file-open** — `x-github-client://` URL handling ultimately calls `openRepositoryFromUrl`, which takes an attacker-controlled `filepath` from the URL and passes it straight to `resolveWithin(repository.path, filepath)` before revealing it in the OS file manager: [3](#0-2) 
If the user's repository directory name is a prefix of a sibling directory (e.g. `repo` next to `repo-backup`, `project` next to `project-old`, a very common naming pattern), a crafted deep link with a `..`-traversal filepath escapes the intended repository and reveals/opens a file in the sibling directory instead of being rejected.

2. **Copilot conflict-resolution file I/O** — the same guard gates both reading conflicted file content into the AI context and later writing AI-resolved content back to disk: [4](#0-3) [5](#0-4) 
A conflicted-file path that traverses into a sibling directory sharing the root's name as a prefix would bypass the "path is outside the repository" rejection, letting file content outside the repo be read (and potentially exfiltrated to the Copilot service) or overwritten with resolved content on write-back.

### Impact Explanation
This breaks the fundamental invariant the function is documented to guarantee ("the resolved path is guaranteed to reside at, or underneath this path"). Concretely it can lead to file read outside the repository (contents sent off to an external AI service in the Copilot path) or file write outside the repository (overwriting an unrelated file's content), both of which are explicitly in-scope impacts. The write path is particularly severe because it silently corrupts a file the user never intended to touch, without any confirmation.

### Likelihood Explanation
Exploitability depends on the victim having a sibling directory whose name is a superstring of the repository directory's basename (e.g. `repo` / `repo-old`, `project` / `project2`, `app` / `app.bak`) — a common but not universal real-world layout. The deep-link vector requires the user to click an attacker-supplied `x-github-client://openRepo` link with a crafted `filepath` query parameter, which fits the in-scope "link/deep link the user clicks" attacker model. The Copilot vector requires the attacker to control the conflicting repository content/paths presented for AI resolution. Likelihood is therefore medium: the code path is real and reachable without any local/admin access, but successful exploitation is conditioned on directory-naming coincidence rather than being universally triggerable.

### Recommendation
Fix the containment check to enforce a real path-separator boundary instead of a raw string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(with the platform-appropriate separator for the `win32`/`posix` variants), and add a regression test covering the sibling-prefix case (`root = /a/repo`, candidate resolves to `/a/repo-evil/file`) to `app/test/unit/path-test.ts`.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdtemp, mkdir, writeFile } from 'fs/promises'
import { join } from 'path'
import { tmpdir } from 'os'

// Set up sibling directories: /tmp/xxxx/repo and /tmp/xxxx/repo-secrets
const base = await mkdtemp(join(tmpdir(), 'poc-'))
const root = join(base, 'repo')
const sibling = join(base, 'repo-secrets')
await mkdir(root)
await mkdir(sibling)
await writeFile(join(sibling, 'id_rsa'), 'SECRET KEY MATERIAL')

// Attacker-controlled relative path traverses out of root into the sibling
const escaped = await resolveWithin(root, '../repo-secrets/id_rsa')

console.log(escaped)
// Expected (safe): null
// Actual (buggy):  "<base>/repo-secrets/id_rsa"  -- treated as "inside" root
```
This demonstrates that `resolveWithin` fails to reject a path that resolves outside the intended root when the root's directory name is a string prefix of the escaped sibling directory's name — the same condition that gates both `openRepositoryFromUrl`'s `shell.showItemInFolder` call and the Copilot conflict read/write paths.
