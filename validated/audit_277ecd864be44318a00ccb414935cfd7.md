Audit Report

## Title
Unbounded, permissionless growth of the live `vote_accounts` map degrades `getVoteAccounts` and other full-map iterations over `Bank::vote_accounts()` - (File: `runtime/src/stakes.rs`, `runtime/src/bank.rs`, `rpc/src/rpc.rs`)

## Summary
Vote account creation only requires paying the rent-exempt minimum for a `VoteStateV4`-sized account; unlike stake *delegation* (gated by `get_minimum_delegation`), creating and keeping a vote account registered in the bank's live `Stakes`/`StakesCache` carries no minimum-stake or count requirement. This unfiltered map is returned unbounded by `Bank::vote_accounts()` and fully iterated by the `getVoteAccounts` RPC handler (and other bank-wide scans), so an unprivileged actor can permanently grow the collection the RPC path must iterate on every call, at a cost proportional only to rent-exempt lockup per account, not stake.

## Finding Description
`get_minimum_delegation` in `runtime/src/stake_utils.rs` enforces a minimum-stake gate only for *delegations*, not for vote-account creation or registration. Every successfully processed transaction touching a vote/stake-owned account runs `Bank::update_stakes_cache` [1](#0-0) , which calls `StakesCache::check_and_store` [2](#0-1) . That function unconditionally upserts any vote-program-owned account with non-zero balance into the live `vote_accounts` map — there is no stake or count check, only a size/initialization check.

The only mechanism that removes an entry from this map is when the account's lamport balance is driven to exactly zero [3](#0-2) . The VAT ("Validator Admission Ticket") burn mechanism, `Bank::maybe_burn_vat_from_staked_accounts`, only drains lamports from the epoch's VAT-filtered, capped (`MAX_ALPENGLOW_VOTE_ACCOUNTS`) distribution snapshot, and `clone_and_filter_for_vat` explicitly filters that snapshot down to accounts with non-zero delegated stake, a BLS pubkey, and sufficient balance [4](#0-3) [5](#0-4) . A vote account created with zero delegated stake is excluded from this filter (`has_stake = *stake != 0u64`) and is therefore never VAT-burned, so its balance stays at the rent-exempt minimum forever and it is never evicted from the live map by the zero-lamport path.

`Bank::vote_accounts()` exposes this raw, unfiltered, uncapped map [6](#0-5) , and the `getVoteAccounts` RPC handler fully iterates it on every invocation with no pagination or size cap on the input set (filters like `vote_pubkey`, `keep_unstaked_delinquents` only reduce the *output*, applied after iterating the whole map) [7](#0-6) [8](#0-7) . Other bank-wide scans such as `SnapshotMinimizer::get_vote_accounts` and `Stakes::highest_staked_node`/`VoteAccounts::find_max_by_delegated_stake` similarly iterate the same unbounded structure. The `MAX_ALPENGLOW_VOTE_ACCOUNTS` cap referenced in `maybe_burn_vat_from_staked_accounts` only bounds the epoch-stakes/leader-schedule *distribution* snapshot, not `stakes_cache.stakes().vote_accounts()`, so it provides no protection for the code paths this claim targets.

## Impact Explanation
This matches the allowed "single-client low-rate RPC crash/degradation" impact category: any legitimate client (or validator/RPC node itself) calling `getVoteAccounts`, or any code path relying on `Bank::vote_accounts()`, pays a cost that scales with the total number of vote accounts ever created network-wide with non-zero balance, regardless of whether that balance is backed by any real stake. An unprivileged actor can inflate this cost by creating many zero-stake vote accounts, each permanently occupying a slot in the live map for the price of one rent-exempt lockup, with no on-chain limit on how many such accounts a single identity can create.

## Likelihood Explanation
Likelihood is moderate: the only barrier is the rent-exempt balance for a `VoteStateV4`-sized account (smaller than the 1 SOL minimum stake delegation) plus ordinary transaction fees, and there is no cap on the number of distinct vote accounts. The existing VAT/SIMD-357 filtering mechanism does not apply to zero-stake vote accounts, so it does not mitigate this specific growth vector, leaving the live-map iteration cost unbounded and attacker-controllable over time.

## Recommendation
Cap the size of, or add pagination to, the collection returned by `Bank::vote_accounts()` and consumed by `getVoteAccounts`, or require a minimum stake/balance for a vote account to remain in the live-iterated set (extending the existing VAT-style filter used for the epoch-stakes distribution snapshot to the live cache, or evicting zero-stake vote accounts after a grace period). Alternatively, add server-side rate limiting/pagination to `getVoteAccounts` so a single call's cost does not scale with the total number of on-chain vote accounts.

## Proof of Concept
1. Submit repeated `create_account_with_config`/`VoteInit` transactions (see `cli/src/vote.rs::process_create_vote_account`) to create N vote accounts, each funded only with the rent-exempt minimum for `VoteStateV4::size_of()` and no stake delegation.
2. Each account is unconditionally inserted into the bank's live `vote_accounts` map via `Bank::update_stakes_cache` → `StakesCache::check_and_store` on transaction success, and — because it has zero delegated stake — is excluded from VAT filtering/burning and never evicted.
3. Call `getVoteAccounts` against a node and measure latency/CPU as N grows; observe iteration cost scales with the full unfiltered `bank.vote_accounts()` map size.
4. Write a Rust integration test in `runtime/src/stakes.rs`/`rpc/src/rpc.rs` test harness that creates a large number of zero-stake vote accounts via `check_and_store`, then times `Stakes::vote_accounts()` iteration and/or the `get_vote_accounts` RPC handler to demonstrate linear cost growth with account count.

    fn update_stakes_cache(
        &self,
        txs: &[impl SVMMessage],
        processing_results: &[TransactionProcessingResult],
    ) {
        debug_assert_eq!(txs.len(), processing_results.len());
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();
        txs.iter()
            .zip(processing_results)
            .filter_map(|(tx, processing_result)| {
                processing_result
                    .processed_transaction()
                    .map(|processed_tx| (tx, processed_tx))
            })
            .filter_map(|(tx, processed_tx)| {
                processed_tx
                    .executed_transaction()
                    .map(|executed_tx| (tx, executed_tx))
            })
            .filter(|(_, executed_tx)| executed_tx.was_successful())
            .flat_map(|(tx, executed_tx)| {
                let num_account_keys = tx.account_keys().len();
                let loaded_tx = &executed_tx.loaded_transaction;
                loaded_tx.accounts.iter().take(num_account_keys)
            })

                    use_fixed_point_stake_math,
