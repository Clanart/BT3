### Title
Attacker-injectable leading OP_RETURN output lets `get_first_op_return_output` misattribute payout credit - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`get_first_op_return_output` returns the first `OP_RETURN` output of a transaction with no check on its index, while `create_payout_txhandler` always places the operator's real `xonly_pk` OP_RETURN at output index 2 (after the payout output and the anchor). If a transaction spending the committed withdrawal outpoint can be produced with more than one `OP_RETURN` output, whichever one appears first is what gets parsed as the "operator that fronted the payout," regardless of which output the protocol actually designates.

### Finding Description
The binding claimed by the protocol is: `xonly_pk parsed by get_first_op_return_output(payout_tx) == operator_xonly_pk.serialize()` as placed at output index 2 by `create_payout_txhandler`.

`create_payout_txhandler` builds the payout transaction with a fixed output layout: output 0 = user payout, output 1 = anchor, output 2 = `OP_RETURN` carrying `operator_xonly_pk.serialize()`: [1](#0-0) 

`get_first_op_return_output` performs a linear scan and returns the *first* matching `OP_RETURN`, with no verification that it is at the expected index or that there is exactly one such output in the transaction: [2](#0-1) 

Because Bitcoin transactions can contain an arbitrary number of `OP_RETURN` outputs and nothing in this function enforces uniqueness or position, any transaction that (a) still spends the exact committed withdrawal outpoint with a valid signature, and (b) contains an extra `OP_RETURN` output placed before the legitimate one, will cause this function to return attacker-chosen bytes instead of the real operator's serialized `xonly_pk`.

I was not able to fully trace `Verifier::update_finalized_payouts` in `core/src/verifier.rs` in the remaining tool budget, nor confirm what sighash-type constraints (if any) are enforced on the withdrawal/payout signature (`user_sig`) that would prevent an attacker from altering the output set of a transaction spending the withdrawal UTXO. That is the critical missing piece of the trace: if the signature covering the withdrawal input commits to the entire output set (e.g. `SIGHASH_ALL`/`SIGHASH_DEFAULT`), no alternate transaction with an injected OP_RETURN can be validly signed, and the described attack is not exploitable. If any permissive sighash flag (`SIGHASH_NONE`, `SIGHASH_SINGLE`, or an `ANYONECANPAY` variant) is accepted for this signature, the attack becomes feasible.

### Impact Explanation
Unresolved without confirming the sighash-commitment guard on the withdrawal payout signature — I could not verify whether existing constraints in `Verifier::update_finalized_payouts` or elsewhere already prevent an attacker from broadcasting an alternative valid transaction with an added `OP_RETURN` for the same withdrawal outpoint.

### Likelihood Explanation
Not determined — likelihood depends entirely on whether the withdrawal/payout signature (`user_sig` in `create_payout_txhandler`) is constrained to a fixed sighash flag that commits to the full, fixed 3-output template. This dependency could not be confirmed within the available investigation.

### Recommendation
Regardless of the sighash dependency, `get_first_op_return_output` should not be positionally naive: harden it to require the `OP_RETURN` to be at a fixed, protocol-defined index (index 2, matching `create_payout_txhandler`'s layout) and/or to reject transactions containing more than one `OP_RETURN` output, rather than trusting "first match wins."

### Proof of Concept
Not completed — a definitive `cargo test` proof requires first confirming (in `Verifier::update_finalized_payouts` and the signature-verification path for the withdrawal payout signature) whether a permissive sighash flag can be used to produce a validly-signed alternate transaction with an injected leading `OP_RETURN` for the same withdrawal outpoint. Without that confirmation, a test that merely constructs a 4-output `CircuitTransaction` and asserts `get_first_op_return_output` returns the first one only demonstrates the (real) lack of positional validation in the parsing function itself, not a demonstrated end-to-end attribution exploit.

/// Retrieves the first output of a transaction that is an OP_RETURN script. Used in various
/// contexts to extract metadata or constants from transactions.
pub fn get_first_op_return_output(tx: &CircuitTransaction) -> Option<&TxOut> {
    tx.output
        .iter()
        .find(|out| out.script_pubkey.is_op_return())
}
