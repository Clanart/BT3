### Title
`resolveWithin`'s directory-boundary check uses `startsWith` without a separator, allowing deep-link `filepath` values to escape the repository root - ([File: app/src/lib/path.ts])

### Summary
`_resolveWithin` (the sole guard behind the public `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` helpers) validates that a resolved path stays inside a root directory by doing `realResolved.startsWith(realRoot)`. Like the `>=` vs `>` off-by-one in the smart-contract report, this is a boundary check that is subtly wrong: it doesn't require a path separator (or exact match) after the prefix, so a resolved path that lands in a *sibling* directory whose name merely starts with the root directory's name passes the check.

### Finding Description [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

If `realRoot` is `/Users/victim/Documents/GitHub/foo` and `realResolved` is `/Users/victim/Documents/GitHub/foobar/secret.txt`, `realResolved.startsWith(realRoot)` is `true` even though `foobar` is a completely different directory from `foo` — there is no check for a trailing separator or exact equality after the prefix match. This is functionally the same class of bug as the reported `nextId + amount >= MAX_SUPPLY` check: an inclusive/boundary comparison that silently accepts one input class it was meant to reject.

This helper is reached from an attacker-influenced entry point: `openRepositoryFromUrl`, which handles the `x-github-client://openRepo/...` deep link (`IOpenRepositoryFromURLAction`) that a user can be lured into clicking. [2](#0-1) 

```
private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
  ...
  if (filepath !== null) {
    if (isAbsolute(filepath)) {
      log.error(`Refusing to open absolute path: ${filepath}`)
      return
    }
    const resolved = await resolveWithin(repository.path, filepath)
    if (resolved !== null) {
      shell.showItemInFolder(resolved)
    } else {
      log.error(...)
    }
  }
}
```

The `isAbsolute(filepath)` guard only blocks absolute payloads; it does nothing against a relative traversal payload such as `../foobar/secret.txt`. Once `resolveWithin` mis-validates that path as "inside" `repository.path`, `shell.showItemInFolder(resolved)` is invoked on a path outside the intended repository.

Existing unit tests for `resolveWithin` (`app/test/unit/path-test.ts`) cover `..`, null bytes, and symlink traversal, but never test the "sibling directory with a shared name prefix" case, which is exactly the scenario the flawed `startsWith` check fails to catch. [3](#0-2) 

### Impact Explanation
The immediate exploitable sink here is `shell.showItemInFolder`, which reveals/selects a file outside the intended repository boundary in the OS file explorer — a genuine "read outside the repo" boundary violation caused purely by the attacker crafting the deep link's `filepath` parameter and having the victim click it (no local access, no malware, no admin rights required). The severity depends on which sibling directories happen to exist next to a given repository's clone folder (a very common layout, since Desktop by default clones many repositories from the same organization/owner under one parent directory, e.g. `.../GitHub/foo` and `.../GitHub/foo-internal`), but the underlying primitive — `resolveWithin` returning a path that is provably outside `rootPath` — is a shared building block used elsewhere in the codebase (e.g. Copilot-conflict-resolution file writes in `app-store.ts`), so any future or existing caller that doesn't independently re-validate the returned path inherits this boundary bug.

### Likelihood Explanation
High for the specific vector shown: the deep-link handler is reachable with just a URL click, the `isAbsolute` guard is trivially bypassed with a `../` relative payload, and the flawed boundary check in `_resolveWithin` does nothing to stop it as long as a same-prefixed sibling directory exists on disk. The main precondition — a sibling directory sharing a name prefix with the target repository folder — is common but not guaranteed for every victim, which is why this is rated "High" for the boundary-check flaw itself and situational for full exploitation depending on the victim's folder layout.

### Recommendation
Fix the comparison in `_resolveWithin` to require an exact match or a path-separator boundary, e.g.:
```diff
- return realResolved.startsWith(realRoot) ? resolved : null
+ return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
+   ? resolved
+   : null
```
(with the appropriate `join`/`sep` for the win32/posix variant passed in via `options`). Add a regression test asserting that `resolveWithin('/foo', '../foobar/x')` (or the platform equivalent) returns `null` even when `/foobar` exists on disk.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdirSync, rmSync } from 'fs'
import { join } from 'path'
import { tmpdir } from 'os'

const base = mkdtempSync(join(tmpdir(), 'poc-'))
const repoFoo = join(base, 'foo')
const repoFoobar = join(base, 'foobar')
mkdirSync(repoFoo)
mkdirSync(repoFoobar)
writeFileSync(join(repoFoobar, 'secret.txt'), 'sensitive')

// Simulates dispatcher.ts's handling of a deep-link filepath that is NOT
// absolute, so the isAbsolute() guard does not block it.
const escaped = await resolveWithin(repoFoo, '../foobar/secret.txt')

// BUG: escaped !== null even though it resolves to a sibling directory,
// not underneath `repoFoo`.
console.log(escaped) // -> `${base}/foobar/secret.txt`
```
In the real app this is triggered by a user clicking a link such as `x-github-client://openRepo/https://github.com/owner/foo?filepath=../foobar/secret.txt`, after which `shell.showItemInFolder` is called on the escaped path.
