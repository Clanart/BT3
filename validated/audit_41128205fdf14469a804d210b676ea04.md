### Title
`open-external` IPC handler and `shell.openExternal` proxy trust arbitrary URI schemes without validating the protocol - ([File: app/src/main-process/main.ts])

### Summary
The Chainlink report's broken invariant is: *"trust an externally-supplied value without validating it is safe/fresh before acting on it."* The closest Desktop analog is the `open-external` IPC channel: the main-process handler and its renderer-side proxy accept any string and hand it directly to Electron's `shell.openExternal`, only inspecting the string to decide whether to *log* it as `http(s)`, never to gate what is actually executed. Any code path that funnels an attacker-influenced string (a GitHub API field, a markdown-rendered link, an OAuth/enterprise sign-in URL, etc.) into this channel can cause the OS to invoke an arbitrary registered URI-scheme handler.

### Finding Description
The main-process handler for `open-external` is: [1](#0-0) 

It only uses the `http://`/`https://` prefix check for a log statement; it does **not** reject or otherwise gate non-http(s) schemes before calling `shell.openExternal(path)`. The renderer-side proxy that feeds this channel performs no validation either: [2](#0-1) 

`shell.openExternal` (used by `LinkButton`, release-notes dialog, editor-error dialog, and the sign-in OAuth flow) is called with values that originate, directly or indirectly, from external/API-controlled data: [3](#0-2) [4](#0-3) 

Some call sites do add a scheme allow-list before invoking the callback — e.g. the sandboxed markdown iframe's link interceptor requires `/^https?:/` on the anchor's `protocol` before firing `onMarkdownLinkClicked`: [5](#0-4) 

However, this validation is local to that one component and is not enforced centrally at the IPC boundary or inside `shell.openExternal`/`openExternal` proxy itself. Any other renderer code path (current or future) that passes a URI to `LinkButton`, `dispatcher.openInBrowser`, or the `open-external` IPC channel — including `IAPIComment.html_url`, `IAPIPullRequestReview.html_url`, or other GitHub-API-supplied URL fields surfaced in notification/PR UI — bypasses the http(s)-only check because the enforcement point (`main.ts`'s handler) does not itself validate the scheme. This mirrors the Chainlink flaw: the "last known value" (URL string) is consumed and acted upon without a freshness/sanity check at the point where it actually matters (the trust boundary between renderer and OS shell).

### Impact Explanation
Electron's `shell.openExternal` invokes whatever the OS has registered for a given URI scheme. If a scheme other than `http(s)` reaches this function unfiltered (e.g., `file://`, a custom app-registered protocol, or an OS-specific search/handler protocol on Windows), it can result in launching arbitrary local applications or file handlers with attacker-influenced arguments — this is a well-known Electron/`shell.openExternal` code-execution vector when the argument isn't restricted to `http`/`https`. Because GitHub Desktop surfaces GitHub-API content (issue/PR bodies, comments, reviews) that an attacker fully controls by opening a PR or issue against a repo the victim has cloned/added, and because several UI components call `shell.openExternal`/`LinkButton` on API-sourced or link-derived strings without a centralized scheme allow-list, this is a plausible code-execution-adjacent primitive that satisfies the "attacker controls a GitHub API object or a link the user clicks, result is code execution/file access outside the repo" impact bar.

### Likelihood Explanation
Likelihood is **uncertain/moderate** rather than confirmed: the sandboxed markdown renderer (the primary path for rendering untrusted PR/issue/comment bodies) does enforce an `https?:` filter before dispatching `onMarkdownLinkClicked`, which mitigates the most obvious exploitation path. What remains unverified from the available index is whether every other call site that ultimately reaches `shell.openExternal`/`open-external` (e.g., avatar links, other `html_url` fields, notification deep-links) is equally filtered, or whether any of them pass raw, unsanitized API-derived strings. The lack of validation at the actual trust boundary (`main.ts:581` and `main-process-proxy.ts:146`) means the safety of the whole system currently depends on every caller remembering to filter first — a fragile, defense-in-depth-violating pattern, consistent with the "extra validation not performed at the authoritative point" theme of the Chainlink bug.

### Recommendation
Move the `https?:`-only (or explicit protocol allow-list) validation into the `open-external` IPC handler in `app/src/main-process/main.ts` itself (and/or into the `openExternal` proxy/`shell.openExternal` wrapper in `app/src/lib/app-shell.ts`), rejecting/no-oping any URL whose scheme is not on an explicit allow-list, rather than relying on individual call sites like `sandboxed-markdown.tsx` to filter beforehand.

### Proof of Concept
Could not be fully constructed from the indexed code alone — a concrete PoC would require confirming a specific unfiltered call site that forwards attacker-controlled `html_url`/API data directly to `LinkButton`/`shell.openExternal` without the `https?:` guard seen in `sandboxed-markdown.tsx`. This requires access to the full call graph (not fully covered by the code index) to enumerate every consumer of `IAPIComment.html_url`, `IAPIPullRequestReview.html_url`, and similar fields; a Devin session with full repository access would be needed to trace all such usages and build a working repro (e.g., a PR/issue body or review containing a `file://` or Windows `search-ms:`/custom-scheme link rendered outside the sandboxed markdown path).

    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
