### Title
Crafted `ThresholdKeys` deserialization decouples group key from any valid secret share — funds reported received that are unspendable - (File: crypto/dkg/src/lib.rs)

### Summary

CVE-2022-45771 describes privilege escalation via a crafted file uploaded to a deserialization endpoint. The analog in Serai is a crafted serialized `ThresholdKeys` object fed to `ThresholdKeys::read`: the deserialization path and `ThresholdKeys::new` accept arbitrary `verification_shares` and an arbitrary `secret_share` without ever checking that they are mutually consistent, that is, that `C::generator() * secret_share == verification_shares[i]` or that the shares interpolate to a well-formed group key. The resulting object reports an attacker-chosen `group_key()` while no quorum can ever produce a valid signature for it.

### Finding Description

`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses the curve ID, `t`, `n`, `i`, the interpolation variant, the `secret_share` scalar, and `n` verification-share points, then passes everything to `ThresholdKeys::new`. `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) checks only:

- `verification_shares.len() == n` and each key `<= n` (lines 355-365),
- `t == n` when `Interpolation::Constant` is used (lines 367-374),

and then computes `group_key` by interpolating the verification shares of participants `1..=t` (lines 376-378):

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

Nothing binds `secret_share` to `verification_shares[i]`, and nothing binds the `n` verification shares to a common polynomial/secret. A crafted byte stream therefore produces a `ThresholdKeys` whose `group_key()` (crypto/dkg/src/lib.rs:445-447) is fully attacker-controlled while `secret_share` is some unrelated scalar.

When `view(included)` is later called, the interpolated secret share (`interpolation_factor(i, included) * secret_share`, line 495-498) will not match the interpolated verification share (`verification_shares[i] * interpolation_factor(i, included)`, lines 500-507), so `verify_share` rejects every share the holder produces. Downstream, `Scanner::new`/`register_offset` (networks/bitcoin/src/wallet/mod.rs:162-196) register P2TR scripts derived from `group_key()`, and `scan_transaction` (lines 199-214) reports any Bitcoin output paying to those scripts as a `ReceivedOutput` owned by the "multisig".

### Impact Explanation

Two concrete failures, both reachable purely through crafted bytes:

1. **Funds reported received that are not spendable.** If the crafted verification shares interpolate to a group key whose discrete log nobody knows, deposits sent to addresses derived from `group_key()` are scanned, credited, and reported as multisig outputs, yet can never be signed — the BTC is burned while Serai's accounting treats it as held.
2. **Attacker-controlled key reported as the multisig key.** If the crafted shares interpolate to a group key `G * a` for an attacker-known `a`, deposits are reported as multisig funds while the attacker can spend them directly on Bitcoin — an effective privilege escalation mirroring CVE-2022-45771: attacker-supplied bytes cause the system to treat attacker-controlled state as privileged state.

### Likelihood Explanation

`ThresholdKeys::read` is the canonical deserialization path for key material (used e.g. in FROST test vector import at crypto/frost/src/tests/vectors.rs:131 and by any persistence/import flow). Any deployment that loads or imports serialized `ThresholdKeys` from storage or another party is exposed; the malformed input is trivially constructible — it requires only writing valid encodings of inconsistent scalars/points, all of which pass `read_F`/`read_G` canonicality checks (crypto/ciphersuite/src/lib.rs:74-101). No cryptographic break is needed. Likelihood is gated by whether an integration loads keys from an untrusted source rather than generating them via `dealer::key_gen`/`pedpop`, which do produce consistent keys.

### Recommendation

In `ThresholdKeys::new` (and hence `ThresholdKeys::read`), add an integrity check that the loaded secret share matches its claimed verification share:

```rust
if C::generator() * secret_share.deref() != verification_shares[&params.i()] {
  Err(DkgError::...)?;
}
```

This does not defend against a fully crafted set of verification shares (which are arbitrary points by design), so additionally document — or enforce via type separation — that `ThresholdKeys::read` output must not be used as authoritative `group_key` material unless the source is trusted, or compare `group_key()` against an externally known/expected key before registering it with `Scanner`/`register_offset` (networks/bitcoin/src/wallet/mod.rs:162-196).

### Proof of Concept

Conceptual reproduction against `ThresholdKeys::<Secp256k1>::read`:

```rust
// Crafted buffer: valid curve ID, t=2, n=2, i=1, Lagrange.
// secret_share = s (arbitrary), verification_shares = {1: G*a1, 2: G*a2}
// chosen so that Lagrange interpolation of shares {1,2} yields an
// attacker-known group key G*a (e.g. pick a1, solve a2).
// ThresholdKeys::read succeeds: no consistency check exists.
let keys = ThresholdKeys::<Secp256k1>::read(&mut crafted.as_slice()).unwrap();
// keys.group_key() == G*a — attacker knows `a`
// keys.original_secret_share() == s where G*s != G*a1
// -> Scanner::new(keys.group_key()) registers attacker-spendable P2TR
//    scripts; scan_transaction credits deposits that the multisig
//    can never cosign (every sign() share fails verify_share) or that
//    the attacker can unilaterally spend on-chain.
```

The test-vector importer (crypto/frost/src/tests/vectors.rs:118-131) demonstrates the serialization format required to construct the crafted buffer.
