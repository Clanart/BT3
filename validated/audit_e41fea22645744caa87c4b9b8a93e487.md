## Title
GitHub token exfiltration via malicious repo Git hooks/filters abusing the inherited trampoline credential-helper - (`File: app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Sherlock finding describes `initialize()` functions that trust the *caller* rather than verifying *who* is entitled to call them, letting an attacker race in and bind themselves as admin. The GitHub Desktop analog is `findGitHubTrampolineAccount()` in the trampoline credential helper: it trusts the *credential request content* (a `url=`/`host=` value) rather than verifying that the request actually originates from the Git operation Desktop intended to authenticate, and it returns the user's real GitHub OAuth token to whatever process can reach the trampoline socket with a valid (but non-repo-scoped) token.

### Finding Description
When Desktop performs any remote Git operation it wraps the invocation with `withTrampolineEnv`, which mints a short-lived `DESKTOP_TRAMPOLINE_TOKEN` and sets `GIT_CONFIG_PARAMETERS` to register `credential.helper=desktop` and `GIT_ASKPASS=''` for that git process [1](#0-0) . These environment variables (`DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, `GIT_CONFIG_PARAMETERS`) are set specifically so that "commands invoked by filters (i.e. Git LFS)" also pick up the configuration — the comment explicitly says this is intentional so that child processes spawned by the git operation inherit it [2](#0-1) . Git hooks, submodule commands, and clean/smudge filters run as child processes of that same `git` invocation and therefore inherit the same environment, including the still-valid trampoline token, for the whole duration of the operation.

The trampoline server only checks that the token is a member of the currently-active set (`isValidTrampolineToken`) — it does not scope the token to a specific repository, remote, or credential domain [3](#0-2) [4](#0-3) . Any command carrying that token can call the `get` credential-helper command with an arbitrary `url`/`host` field of its choosing.

`getCredential()`/`getGitHubCredential()` then resolve the credential purely from the `url` field supplied in the request, independent of the repository or remote that legitimately triggered the git process: `findGitHubTrampolineAccount` just matches origins and returns the account's real `token` [5](#0-4) [6](#0-5) [7](#0-6) . There is no correlation between the URL/remote of the actual git command that triggered `withTrampolineEnv` (stored only as a repo *path* via `trampolineEnvironmentPath`, used solely for SSH-passphrase bookkeeping) [8](#0-7)  and the endpoint a client requests credentials for.

Consequently, a malicious repository that Desktop clones/fetches/checks out can define a Git hook (e.g. `post-checkout`, `post-merge`) or a clean/smudge filter that runs during that same operation and simply invokes `git credential fill` (or speaks the trampoline TCP protocol directly using the inherited `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN`) with `url=https://github.com`. Because the token is valid for the whole git invocation and is not bound to the actual remote being operated on, the trampoline will happily hand back the user's real `github.com` OAuth token to a process that is entirely under attacker control.

### Impact Explanation
This results in exfiltration of the user's real GitHub account credential/OAuth token from an unprivileged attack surface — a hook or filter defined inside a repository that the victim merely clones or fetches, with no interaction beyond a normal Git operation Desktop already performs. That token can be used to access private repositories, push to other repos the user can write to, or otherwise act as the user on GitHub — a clear "credential/token exfiltration" outcome matching the requested impact class.

### Likelihood Explanation
Likelihood is high once the invariant is understood: any repository Desktop clones or updates can ship a hook/filter, and Desktop is the one setting up the environment that makes the credential helper reachable by that hook process. No local/admin access or pre-existing malware is required — the "malware" is simply committed inside the repository content itself, and the trigger is a normal `git clone`/`fetch`/`checkout` performed by Desktop through its trampoline wrapper. The only unresolved uncertainty (not fully confirmed via the index) is which specific Desktop-triggered git operations execute hooks by default (e.g. whether `core.hooksPath`/hook execution is otherwise disabled for clone operations) — verifying that requires reading `app/src/lib/git/core.ts`, `app/src/lib/git/clone.ts`, and any hook-suppression flags, which the index did not fully surface.

### Recommendation
Bind trampoline credential requests to the specific remote/host Desktop is actually authenticating against for a given operation (store the expected endpoint alongside `trampolineEnvironmentPath`/`isBackgroundTaskEnvironment`, keyed by token) and refuse `get` requests for hosts that don't match the operation's expected remote unless it's a generic (non-GitHub) credential. Consider disabling arbitrary hook execution (or hooks path) for repositories being cloned/fetched for the first time, and never let filter/hook subprocesses inherit `DESKTOP_TRAMPOLINE_TOKEN` unless strictly required for LFS-style filter use cases.

### Proof of Concept
1. Attacker publishes a repository containing `.git/hooks/post-checkout` (or a `.gitattributes` clean/smudge filter, which is more directly reachable since hooks aren't cloned by default — but submodule hooks/`.gitmodules` update hooks and LFS smudge filters *are* content that ships with the repo and execute during clone/fetch):
   ```sh
   #!/bin/sh
   # runs as a child of the git process Desktop spawned via withTrampolineEnv
   printf 'get\x00' | nc 127.0.0.1 "$DESKTOP_PORT" # (schematic - actual protocol per trampoline-command-parser)
   # or simply:
   printf "protocol=https\nhost=github.com\n\n" | git credential-desktop get
   ```
2. Victim clones/fetches this repository in GitHub Desktop; Desktop calls `withTrampolineEnv` which sets `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and `credential.helper=desktop` for the git subprocess [1](#0-0) .
3. During that operation the filter/hook subprocess (inheriting the same environment) issues a `get` request for `host=github.com`.
4. `createCredentialHelperTrampolineHandler` → `getCredential` → `getGitHubCredential` resolves and returns the victim's real GitHub account token because the token is valid and no remote/endpoint binding is enforced [9](#0-8) .
5. The hook/filter exfiltrates the returned credential (e.g., via an outbound HTTP request also permitted from within the same child process).

export const createCredentialHelperTrampolineHandler: (
  store: AccountsStore
) => TrampolineCommandHandler = (store: Store) => async command => {
  const firstParameter = command.parameters.at(0)
  if (!firstParameter) {
    return undefined
  }

  const { trampolineToken: token } = command
  const input = parseCredential(command.stdin)

  if (__DEV__) {
    debug(
      `${firstParameter}\n${command.stdin
        .replaceAll(/^password=.*$/gm, 'password=***')
        .replaceAll(/^(.*)$/gm, '  $1')
        .trimEnd()}`
    )
  }

  try {
    if (firstParameter === 'get') {
      const cred = await getCredential(input, store, token)
      if (!cred) {
        const endpoint = `${getCredentialUrl(input)}`
        info(`could not find credential for ${endpoint}`)
        setHasRejectedCredentialsForEndpoint(token, endpoint)
      }
      return cred ? formatCredential(cred) : undefined
