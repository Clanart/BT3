### Title
`ReceivedOutput::read` accepts an attacker-specified offset/script pairing with no ownership check, letting untrusted bytes register unspendable outputs as spendable inputs — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to CVE-2022-28137 (a missing check letting a low-privileged party supply an attacker-chosen endpoint/parameters which are then acted on), `ReceivedOutput::read` deserializes an arbitrary `offset`, `TxOut`, and `OutPoint` and returns them as a fully-formed "spendable output" without verifying that `output.script_pubkey` is the P2TR script of `key + offset·G` or that the output was ever observed by a `Scanner`. Any consumer that later trusts this `ReceivedOutput` (e.g. passes it to `SignableTransaction`/`multisig`) treats attacker-specified bytes as legitimate funds.

### Finding Description
`Scanner::scan_transaction` constructs `ReceivedOutput`s only for `script_pubkey`s present in its registered `scripts` map, so a legitimately-scanned output is guaranteed to be spendable with `offset`. However, `ReceivedOutput::read` bypasses this invariant entirely:

- It reads a scalar `offset` via `Secp256k1::read_F`, a `TxOut`, and an `OutPoint` via `consensus_decode`.
- It performs **no** check that `output.script_pubkey == p2tr_script_buf(key + G·offset)` — it doesn't even have access to the group key — and no check that the script was a registered scanner offset.

So the security-critical link between `offset` and `output.script_pubkey` established by `Scanner` (`register_offset`/`scan_transaction`, `networks/bitcoin/src/wallet/mod.rs:180-214`) is silently dropped on deserialization (`mod.rs:122-134`). This is the same bug class as the Jenkins advisory: an attacker-chosen input (there a URL+credentials, here an offset+TxOut+outpoint) is accepted and acted on without a check that the requester is entitled to make it.

### Impact Explanation
A `ReceivedOutput` produced by `read` with a mismatched `script_pubkey` (e.g. paying to an attacker key, or to a script never registered) is indistinguishable from a genuinely scanned deposit. Downstream, the offset is used to derive the signing key (`key + offset·G` via `ThresholdView` offset semantics), while the `outpoint`/`TxOut` are committed as a prevout in `SignableTransaction`. Consequences:

- **Funds reported received that are not spendable**: an output accepted under an offset whose script doesn't match cannot be spent by the group key — the spend attempt produces an invalid input, and any accounting built on `value()` (`mod.rs:116-118`) is wrong.
- **Concrete signing of an unintended message**: the sighash commits to the attacker-chosen `TxOut`/`outpoint` pair, so the threshold signs over an attacker-specified prevout set that never corresponded to a real deposit.

This matches the accepted impact classes (unintended message signing; funds received that are not spendable).

### Likelihood Explanation
Reachability requires untrusted bytes to reach `ReceivedOutput::read` — i.e., a peer/remote component that supplies serialized outputs to be spent rather than outputs derived locally from `scan_transaction`/`scan_block`. In deployments where outputs are relayed between components (scanner → scheduler → signers), an unprivileged party who can inject or corrupt those bytes controls the full `(offset, TxOut, outpoint)` triple. The fix cost is low, and the attacker's cost is only the ability to supply bytes — consistent with the CVSS "low privilege, low complexity" profile of the reference advisory.

### Recommendation
Either make `ReceivedOutput::read` require the scanning context and re-derive the script (verify `self.scripts.contains(&output.script_pubkey)` and that `scripts[script] == offset`), or add a `ReceivedOutput::verify(&Scanner)`/`verify(key)` method that checks `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` before the output is accepted for scheduling/signing. Documentation should also state the type is only safe when constructed via `Scanner`.

### Proof of Concept
```rust
// Deserialize an attacker-crafted ReceivedOutput claiming funds under offset `o`,
// with a script_pubkey that does NOT correspond to key + o*G.
let mut bytes = Vec::new();
// offset = 0 (claims to be spendable by the raw group key)
bytes.extend(Scalar::ZERO.to_bytes());
// TxOut paying to an attacker-controlled P2TR script, value = large
bytes.extend(serialize(&TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: attacker_script,
}));
bytes.extend(serialize(&fake_outpoint));

let output = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(output.value(), 1_000_000);          // accepted as "received"
// output.offset() = 0 ⇒ consumers believe it's spendable by group key,
// but script_pubkey belongs to the attacker; any spend attempt fails
// or signs a prevout that was never a deposit.
```

Note: I was unable to fully trace every downstream consumer of `ReceivedOutput::read` within the available iterations; the finding holds to the extent that serialized `ReceivedOutput`s cross a trust boundary (network/peer messages, DB rows populated from remote sources), which is the usage pattern `read`/`serialize` exist for.
