## Analysis

This is a real structural analog to the Rigor `Community.sol` APR bug. In `pallet-consensus-incentives`, relayer rewards for delivering consensus proofs are computed as `(latest_height - baseline) * cost_per_block`, where `cost_per_block` is a **currently-stored** parameter that governance can update at any time via `update_cost_per_block`, and the reward span is **retroactive** — it covers every block since the last-rewarded watermark, which can be arbitrarily far in the past.

Exactly like Community.sol, the rate parameter is overwritten in place with no settlement of the outstanding "debt" (unpaid block span) at the old rate first.

## Title
Stale block-span rewarded entirely at the new `cost_per_block` after a mid-span rate update - (File: `modules/pallets/consensus-incentives/src/lib.rs`)

## Summary
`update_cost_per_block` overwrites `StateMachinesCostPerBlock[state_machine_id]` unconditionally, with no check of whether blocks have already accrued (unrewarded) under the old rate. `calculate_reward` in `impls.rs` then prices the *entire* unrewarded span — from `LastRewardedHeight` (or `previous_commitment_height`) up to `latest_height` — using whatever rate is currently stored at claim time, regardless of which rate was in effect for each portion of that span.

## Finding Description [1](#0-0) 

`calculate_reward` computes `blocks = latest_height - baseline` and multiplies by whatever `block_cost` was passed in, which is read fresh from `StateMachinesCostPerBlock` in `process_message`: [2](#0-1) 

`update_cost_per_block` simply overwrites the map entry with no interaction with `LastRewardedHeight` or any pending-reward settlement: [3](#0-2) 

Because `LastRewardedHeight` only advances when a reward is actually paid out (i.e., when a `StateMachineUpdated` consensus message is processed), any gap between consensus deliveries for a given `state_machine_id` is a pending, unpriced block-span. If governance changes `cost_per_block` while such a gap exists — a completely ordinary operational event, not requiring a malicious actor — the next relayer to submit a consensus proof for that chain collects (or the treasury pays) the reward for the *entire* backlog at the *new* rate, not the rate(s) that were actually in effect while those blocks were pending. This is structurally identical to Community.sol's flaw: a rate is updated in place while a stale, unsettled balance (there: `lentAmount`; here: unrewarded block span) still exists, and the new rate is wrongly applied retroactively to the old balance.

## Impact Explanation
This directly causes fund loss from the `TreasuryAccount` (or underpayment to the relayer, depending on rate direction):
- If governance raises `cost_per_block` while a backlog exists, the treasury pays out reward for old, already-priced-lower blocks at the new higher rate — an unbounded overpayment scaled by however long the relaying gap was (`blocks_as_balance.saturating_mul(block_cost)` in `calculate_reward`, `impls.rs:94-97`).
- Any relayer (an ordinary, unprivileged actor — no compromised/malicious relayer assumption needed) that simply happens to be the first to deliver a consensus proof after a rate increase collects this inflated payout via `T::Currency::transfer` from the treasury (`impls.rs:53-59`).
- This falls under "loss of funds" and "logic attacks" in the accepted impact categories — real BRIDGE/reputation-asset value moves incorrectly and irrevocably (transfer + mint are executed unconditionally once `calculate_reward` returns a non-zero value).

## Likelihood Explanation
Likelihood is high in practice: relaying of consensus proofs for a given remote state machine is not synchronized with governance's `update_cost_per_block` calls. Any operational rate adjustment (e.g., to react to gas cost changes, as in the original APR-adjustment scenario) that lands while a chain has gone even briefly un-relayed will misprice the entire pending span. No attacker collusion, malicious relayer, or malicious governance intent is required — this occurs from the normal, expected operation of the two independent code paths (governance rate updates and periodic relaying) not being reconciled.

## Recommendation
Before applying a new `cost_per_block`, settle any outstanding reward for the currently pending block span at the *old* rate (mirroring the C4 recommendation for Community.sol): in `update_cost_per_block`, if `StateMachinesCostPerBlock` already has a value and `latest_height > LastRewardedHeight`, either (a) reject the update until the pending span is claimed, or (b) record a rate-change checkpoint (height + rate) so `calculate_reward` can price each sub-span at the rate that was actually in effect, summing across all applicable rate regimes instead of applying a single flat multiplier to the whole span.

## Proof of Concept
1. Governance calls `update_cost_per_block(sm_id, cost=1)` for state machine `sm_id`. `LastRewardedHeight[sm_id]` is unset; `previous_commitment_height` is at height 100.
2. No consensus messages are relayed for `sm_id` for a long period; `latest_commitment_height` for `sm_id` advances (via other means, e.g. periodic state updates) to height 100,000 while `cost=1` was nominally in effect.
3. Governance calls `update_cost_per_block(sm_id, cost=100)` (e.g., reacting to increased infra costs) — `StateMachinesCostPerBlock::mutate` in `lib.rs:140-142` overwrites the value with no check of the pending 99,900-block backlog.
4. A relayer submits any consensus message for `sm_id`, triggering `on_executed` → `process_message` → `calculate_reward`. `baseline` resolves to `previous_commitment_height` = 100 (no watermark set yet), `blocks = 100,000 - 100 = 99,900`, and `block_cost` is read as the *new* value `100`.
5. `reward = 99,900 * 100 = 9,990,000`, instead of the correct `99,900 * 1 = 99,900` that should have applied to blocks accrued under the old rate. The treasury transfers the inflated amount via `T::Currency::transfer` (`impls.rs:53-58`) and mints a matching reputation amount (`impls.rs:67-68`), both unconditionally executed once `calculate_reward` returns non-zero. 	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
