### Title
Race between `BidPool.AddBid` and `BidPool.stop()` causes a send-on-closed-channel panic, crashing the node - (File: `kaiax/auction/impl/bid_pool.go`)

### Summary
`BidPool.AddBid` only guards on the `running` flag before enqueueing a bid to `newBidCh`, but the flag check and the channel send are not atomic with respect to `BidPool.stop()`, which flips `running` to 0 and then `close()`s the same channel. An unprivileged auction bidder can trigger this race on every block boundary where the auction info is refreshed, causing a Go runtime panic ("send on closed channel") that crashes the consensus node process — a direct DoS analog of the gve XSK bug, where an operation (enable/disable of a resource) was not properly guarded against the resource ceasing to exist while the operation was in flight.

### Finding Description
`BidPool.stop()` performs, without holding any lock that serializes against `AddBid`: [1](#0-0) 

- clears `running` to 0,
- clears the pool,
- and if not already stopped, `close(bp.bidMsgCh)` / `close(bp.newBidCh)`.

`AddBid` checks `running` at entry, then later unconditionally sends to `newBidCh`: [2](#0-1) 

Because the `running` load in `AddBid` (line 253) and the channel send (line 271) are two separate, non-atomic operations, a goroutine can observe `running == 1`, proceed through `validateBid`/`insertBid` (which involves signature verification and lock acquisition — non-trivial latency), and then perform `bp.newBidCh <- bid` at the exact moment another goroutine has already executed `stop()` and closed `newBidCh`. Sending on a closed channel panics in Go and is unrecoverable by a `select`/`default` guard, unlike `HandleBid`'s send which uses `select { case bp.bidMsgCh <- bid: default: }` (which is itself also unsafe against a closed channel — sending on a closed channel panics regardless of `default`).

This mirrors the gve XSK bug class: the driver enabled/disabled queues without synchronizing against concurrent operations that assumed the queue's continued existence, causing a NULL dereference. Here, `AddBid`/`HandleBid` assume the channel exists/is open based on a stale `running` read, while `stop()` can destroy that assumption concurrently.

The `running` flag is not just toggled at node shutdown — `PostInsertBlock` (in `kaiax/auction/impl/execution.go`) recomputes and toggles `running` on every new block depending on whether valid auctioneer/entry-point info is present (confirmed via `TestUpdateAuctionInfo`, which shows `running` transitioning 0→1→0 across `PostInsertBlock` calls). This means the stop path executes routinely during normal chain operation, not only during node shutdown, giving an attacker many per-block windows to win the race.

### Impact Explanation
A successful race triggers an unrecovered Go panic in the `handleNewBid`/`AddBid` call path, which crashes the entire node process (denial of service on a consensus node, since the auction module is only enabled on CNs). This is a High/Medium-severity availability impact reachable without any special privilege — any external actor invoking the `auction_submitBid` RPC (`SubmitBid` in `kaiax/auction/impl/api.go`) repeatedly around block boundaries can attempt to win the race.

### Likelihood Explanation
Exploitation requires winning a timing race between an RPC-submitted bid's validation/insertion path and the module's per-block `stop()`/info-refresh cycle. This is not guaranteed on a single attempt, but the window recurs every block and an attacker can flood `SubmitBid` calls with bids timed near block insertion to increase the chance of hitting the race, making repeated attempts practically effective over time.

### Recommendation
Serialize `stop()` against `AddBid`/`HandleBid` channel operations — e.g., hold `bidMu` (or a dedicated state mutex) across both the `running` check and the channel send in `AddBid`, and across the flag clear + channel close in `stop()`, or replace direct channel closes with a `context`/`done`-channel pattern so sends never race with close. Alternatively, avoid closing channels that producers write to at all; use a `select` on a separate stop-signal channel to gate sends.

### Proof of Concept
1. Node runs with the auction module enabled and `running == 1`.
2. Attacker issues a burst of valid `auction_submitBid` RPC calls just as a new block is about to be inserted.
3. One call enters `AddBid`, passes the `running == 1` check (line 253), and proceeds through `validateBid`/`insertBid`.
4. Concurrently, `PostInsertBlock` invalidates the auction info (e.g., auctioneer changes) and calls `bp.stop()`, which sets `running = 0` and `close(bp.newBidCh)`.
5. The in-flight `AddBid` call reaches `bp.newBidCh <- bid` (line 271) on the now-closed channel, causing `panic: send on closed channel` and crashing the node. [3](#0-2) [2](#0-1) [4](#0-3)

func (bp *BidPool) start() {
	// Start the bid pool.
	// running will be set 1 once it's ready in the PostInsertBlock.

	// If channels are closed, recreate them
	if atomic.CompareAndSwapUint32(&bp.stopped, 1, 0) {
		bp.bidMsgCh = make(chan *auction.Bid, bidChSize)
		bp.newBidCh = make(chan *auction.Bid, bidChSize)
	}

	bp.wg.Add(2)
	go bp.handleBidMsg()
	go bp.handleNewBid()
}

func (bp *BidPool) stop() {
	// Stop the bid pool.
	atomic.CompareAndSwapUint32(&bp.running, 1, 0)
	bp.clearBidPool()

	// Only close channels if they haven't been closed before
	if atomic.CompareAndSwapUint32(&bp.stopped, 0, 1) {
		close(bp.bidMsgCh)
		close(bp.newBidCh)
	}
	bp.wg.Wait()
}

func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}

func (bp *BidPool) HandleBid(peerID string, bid *auction.Bid) {
	if atomic.LoadUint32(&bp.running) == 0 || bid == nil {
		return
	}

	// Check rate limit for this peer
	if !bp.checkRateLimit(peerID) {
		logger.Trace("Rate limit exceeded for peer", "peerID", peerID)
		return
	}

	select {
	case bp.bidMsgCh <- bid:
	default:
		logger.Trace("Bid queue is full, dropping bid", "peerID", peerID)
	}
}
