## Title
Prefix-based path containment check in `resolveWithin` allows escape to sibling directories - (File: app/src/lib/path.ts)

## Summary
`resolveWithin` (and its POSIX/Win32 variants) is the central guard GitHub Desktop uses to ensure an attacker- or model-influenced relative path stays inside a repository root before the app opens, reads, or writes it. The final containment check uses a raw string-prefix comparison (`realResolved.startsWith(realRoot)`) instead of a boundary-aware check, so any resolved path whose string happens to start with the root path — even a sibling directory like `myrepo-secrets` when the root is `myrepo` — is treated as "inside" the repository.

## Finding Description
The containment decision is made here: [1](#0-0) 

```
// Resolve to an absolute path...
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`startsWith` performs a pure character-prefix comparison with no separator boundary check. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo` and a crafted relative segment resolves to `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa`, the latter string literally starts with the former string (`myrepo` is a prefix of `myrepo-secrets`), so the function incorrectly returns the resolved path instead of `null`. This is the same class of defect as the Swivel `allowance` bug: a comparison operator meant to gate an authorization/boundary decision is subtly wrong, silently defeating the intended invariant ("resolved path must be *inside* root") in an edge case the author didn't consider.

This primitive is depended on by multiple attacker-reachable call sites that treat a `null` return as "safe" and any non-`null` return as "verified inside the repo":

- Deep-link file opening, driven entirely by a URL the user clicks (`x-github-client://openLocalRepo/...&filepath=...`): [2](#0-1) 

- Copilot merge-conflict context building, where `file.path` originates from git conflict status of a cloned/fetched repository: [3](#0-2) 

- Copilot conflict resolution file writing, which uses the same guard before calling `writeFile`: [4](#0-3) 

The existing unit tests for `resolveWithin` only cover `..`/`../..` traversal and symlink escape, never a same-prefix sibling directory, so this gap is unexercised: [5](#0-4) 

## Impact Explanation
Any code path that relies on `resolveWithin(repository.path, attackerControlledSegment)` to confirm "this path is safely inside the repo" can be tricked into operating on a directory outside the repo whose name merely shares the repository directory name as a prefix (a very plausible situation for GitHub Desktop, since clone destinations are commonly siblings under the same parent, e.g. `~/Documents/GitHub/<repo>` and `~/Documents/GitHub/<repo>-old`, `<repo>-backup`, `<repo>2`, etc.). Depending on the call site this enables:
- File-write outside the intended repository (`writeFile(absolutePath, resolution.resolvedContent, ...)` in the Copilot conflict-resolution flow), i.e. silent corruption of files the user did not intend to touch, if a sibling directory with a prefix-matching name exists.
- Disclosure/exposure of files outside the repo via `shell.showItemInFolder` when a crafted deep-link `filepath` is clicked.

## Likelihood Explanation
Exploitation requires only that (a) the user has a directory next to their repository whose name is prefixed by the repository's directory name (common in practice — backup/duplicate clone folders), and (b) the attacker supplies the relative path via a deep link click or via content in a cloned/fetched repository that flows into these APIs. No local access, admin rights, or pre-existing malware is required — this fits squarely in the reachable "link the user clicks" / "cloned repo content" attack surface the guard was specifically built to defend against.

## Recommendation
Fix the boundary check to require an exact match or a match followed by the path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add a regression test asserting that `resolveWithin('/tmp/foo', '../foo-secret')` (and equivalent same-prefix sibling paths) returns `null`.

## Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdir, rmdir } from 'fs/promises'
import { join } from 'path'
import { tmpdir } from 'os'

const base = await mkdtemp(join(tmpdir(), 'repo'))       // e.g. /tmp/repo-AbC123
const sibling = base + '-secret'                          // /tmp/repo-AbC123-secret
await mkdir(sibling)

// Attacker-controlled relative path escaping to the sibling directory
const escapePath = join('..', require('path').basename(sibling), 'secret.txt')
const result = await resolveWithin(base, escapePath)

// BUG: result is NOT null even though it resolves outside `base`
console.log(result) // -> /tmp/repo-AbC123-secret/secret.txt
```
This demonstrates that `resolveWithin` fails to reject a path that traverses into a sibling directory whose name is prefixed by the root directory's name, confirming the broken invariant described above.
