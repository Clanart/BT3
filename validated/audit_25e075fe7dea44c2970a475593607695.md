Found a genuine, still-open analog: `pallet-relayer::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` reads and dispatches `available_amount` from `Fees` *before* zeroing that storage entry, and the dispatch call goes through `dispatcher.dispatch_request(...)` — an external module boundary — prior to the balance being cleared.

### Title
Relayer fee double-withdrawal via re-entrant `dispatch_request` before `Fees` is zeroed - (modules/pallets/relayer/src/withdrawal.rs)

### Summary
`Pallet::withdraw` reads the relayer's accrued balance into `available_amount`, calls `T::IsmpHost::dispatch_request(...)` to send the withdrawal-triggering POST request, and only *after* that call zeroes the `Fees` storage entry with `Fees::<T>::insert(..., U256::zero())` [1](#0-0) . This mirrors the H-8 pattern exactly: read balance → external call → clear balance, instead of the safe read → clear → external call ordering.

### Finding Description
`available_amount` is fetched from `Fees::<T>::get(dest_chain, address)` at line 116 [2](#0-1) . The nonce is incremented (line 127) before the dispatch, which protects the *signature* from replay, but the `Fees` balance itself is not cleared until line 177, after `dispatcher.dispatch_request(...)` runs at lines 170-175 [3](#0-2) . `dispatch_request` is a call into `IsmpDispatcher`/`pallet-ismp`, an external module boundary relative to `pallet-relayer`, e.g. it enqueues the request, computes/writes commitments, may invoke router or metadata hooks, and could — depending on the concrete `IsmpHost`/`IsmpDispatcher` implementation and any hooks registered on the request/commitment path — call back into pallet-relayer's own dispatchables (`withdraw`, `accumulate_fees`) within the same host callstack before `Fees` is zeroed. Because Substrate transactions guard against re-entrancy at the *extrinsic* boundary (via `frame_system`'s call-stack) but not necessarily inside a single dispatchable's internal cross-pallet call graph, if any code reachable from `dispatch_request` re-invokes `Pallet::<T>::withdraw` for the same `(address, dest_chain)` before the outer call reaches line 177, `available_amount` is read again unchanged, and a second withdrawal-triggering POST is dispatched for the same full balance — a double-claim of the same relayer fee balance.

The existing nonce increment at line 127 only protects a *signature* from being reused for the specific signed message (line 89's `message(nonce, ...)`) — it does not gate `Fees` itself, and a re-entrant call which supplies a *fresh* signature with the incremented nonce (i.e., an attacker relayer controlling their own signing key can pre-sign the next nonce ahead of time, since nonces are deterministic and public via `Nonce::<T>::get`) would pass signature verification on the second call even though `Fees` has not yet been cleared.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds" and "replay/double-claim/double-settlement" categories: an attacker-controlled relayer could cause `pallet-relayer` to dispatch two (or more) withdrawal-triggering POST requests for the same accrued fee balance to a destination host manager, each instructing the destination to disburse `available_amount` to the beneficiary — resulting in the relayer being paid out multiple times against a balance that should only be spent once, draining more from the destination-side fee pool than was actually earned.

### Likelihood Explanation
This is reachable by any relayer address with a nonzero `Fees` balance calling the unsigned `withdraw_fees` extrinsic themselves — no privileged actor, malicious peer, or off-chain relayer/prover assumption is required; the attacker is simply the beneficiary of their own accrued fees. The likelihood is gated on whether `IsmpDispatcher::dispatch_request`/`pallet-ismp`'s dispatch path can be made to call back into `pallet-relayer::withdraw` (or another mutator of `Fees`) within the same call stack — I was not able to fully trace `pallet-ismp`'s dispatcher internals within the available context to confirm or rule out such a callback path exists today (e.g. via a request/commitment hook, a `Router` callback, or fee-metadata handler). This is the key open unknown, and it should be verified against `pallet-ismp`'s dispatcher implementation before treating this as confirmed-exploitable.

### Recommendation
Apply checks-effects-interactions: zero (or decrement) the `Fees::<T>` entry for `(dest_chain, address)` **before** calling `dispatcher.dispatch_request(...)`, matching the safe ordering already used elsewhere in the same file (e.g. `RequestCommitments` claimed-marking happening after computation in `accumulate.rs`, though that path has no external call in between). Concretely, move the `Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());` line to immediately after reading `available_amount` and before the `dispatcher.dispatch_request(...)` call.

### Proof of Concept
Conceptual reentrancy trace (exact reachability of the callback leg is unverified given available context):
1. Attacker relayer accrues `Fees[dest_chain][attacker] = X` via normal `accumulate_fees`.
2. Attacker calls `withdraw_fees` with a validly-signed `WithdrawalInputData` for `nonce = N`.
3. Inside `Pallet::withdraw`: `available_amount = X` is read (line 116); `Nonce` is bumped to `N+1` (line 127); `dispatcher.dispatch_request(...)` is invoked (line 170).
4. If any code reachable from that dispatch call re-enters `Pallet::withdraw` (or another entry point) for the same `(attacker, dest_chain)` before control returns to line 177, the attacker supplies a second signature over `nonce = N+1` (pre-computable since nonces are deterministic and public), passing verification; `Fees` is still `X` (not yet zeroed by the outer call), so a second `X`-sized withdrawal POST is dispatched.
5. Control returns to the outer call, which now sets `Fees[dest_chain][attacker] = 0` — but two withdrawal requests for `X` each have already been dispatched to the destination host manager, resulting in `2X` disbursed against a balance of `X`.
