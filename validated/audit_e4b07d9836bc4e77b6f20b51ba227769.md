### Title
Same-chain partial-fill escrow release reads the full pooled token balance instead of the per-output share, allowing over-withdrawal when an order has repeated input tokens - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntrinsicIntents._fillSameChain` computes the escrow to release for a completed output by reading the *entire* remaining balance of `_orders[commitment][token]` rather than the amount specifically allocated to that output/input pair. Because `_orders` is keyed only by `(commitment, token address)` — not by input index — an order whose `inputs[]` array references the same token for more than one input/output pair lets a solver complete the cheapest output and drain the whole pooled escrow for that token in a single call, while the transaction is recorded as a non-finalizing partial fill (the rest of the order remains "open" but with its backing collateral already gone).

### Finding Description
`_orders` is declared as a flat mapping: [1](#0-0) 

In `_fillSameChain`, for each output index `i` the code pairs `order.output.assets[i]` with `order.inputs[i]` by index, and once that output's cumulative fill (`amountFilled`) reaches `totalRequired`, it sets the escrow to be released as: [2](#0-1) 

This is meant to sweep any rounding dust on the last chunk of a specific output/input pair. However, the read `_orders[commitment][token]` is not scoped to input index `i` — it is the aggregate balance for that token across the *entire order*. If two different entries in `order.inputs[]` (backing two different outputs) use the same token address, the pooled `_orders[commitment][token]` holds the sum of both. Completing only the output tied to the smaller input while leaving the other output unfilled (`solverAmount == 0` for that index) still triggers the `amountFilled == totalRequired` branch for the first output, and `escrowedAmount` for that branch is the **full pooled balance**, including the second output's untouched collateral.

The subsequent `_withdraw` call is executed once per `fillOrder` invocation over all computed `escrowedInputs`, with `finalize = isFullyFilled`: [3](#0-2) 

Since the other output is unfilled, `isFullyFilled` is `false`, so this executes as a "partial fill" (`finalize = false`), releasing the entire pooled token amount to `msg.sender` (the solver) via `_withdraw`, decrementing `_orders[commitment][token]` to zero: [4](#0-3) 

The order is left `_filled[commitment]` unset (deleted, since not fully filled) — appearing open for a future filler on the still-unmet output — yet with zero escrow left to pay them.

### Impact Explanation
This is a genuine escrow-accounting break, not a UX gap: a solver can pay for and complete only the cheaper leg of a multi-output same-chain order while unilaterally seizing the escrow reserved for the other, unfilled leg. The result is stolen/lost user funds — the user's remaining collateral disappears without the corresponding output ever being delivered, and the order cannot later be honestly filled or fully refunded because its backing balance is already gone. This falls squarely under "stealing or loss of funds" / "logic attacks" in the bounty's impact gate, exercised entirely through the public `fillOrder` entrypoint by an ordinary (no special privilege) solver.

### Likelihood Explanation
Exploitability depends only on a user (or an attacker crafting an order on their own behalf, e.g. to later grief a bona fide solver, or a solver colluding with a malicious "order" it constructs itself via `predispatch`/self-placed orders) creating or encountering an order whose `inputs[]` array repeats a token address across two or more input/output pairs. Nothing in the visible fill/placement logic enforces per-input uniqueness of token addresses, and the intent-gateway design explicitly supports multi-asset orders with independent input/output pairs, so such orders are a normal, reachable configuration rather than a contrived edge case. I was not able to fully inspect `placeOrder` in `evm/src/apps/IntentGatewayV2.sol` within the available tool budget to confirm whether duplicate-token inputs are explicitly rejected there — this is a limitation of my search, and directly reading that function (and the `Order`/`TokenInfo` struct definitions) is necessary to fully confirm or rule out this path before treating it as conclusively exploitable.

### Recommendation
Track escrow per `(commitment, inputIndex)` rather than per `(commitment, token)`, or explicitly disallow duplicate token addresses across `order.inputs[]` at `placeOrder` time. Alternatively, when computing `escrowedAmount` for a completed output, cap it at the *proportional* remaining amount for that specific input index (tracked independently) rather than reading the shared token-keyed balance, and only fall back to "sweep the remainder" logic once it is confirmed that no other pending output shares the same input token.

### Proof of Concept
1. User places a same-chain order with two outputs: output A (cheap, e.g. 1 USDC) and output B (expensive, e.g. 1000 USDC worth of a target token), both backed by `inputs[]` entries denominated in the **same** escrowed token (e.g. WETH): `inputs[0] = 0.001 WETH` (for output A) and `inputs[1] = 1 WETH` (for output B). Total escrow: `_orders[commitment][WETH] = 1.001 WETH`.
2. A solver calls `fillOrder` providing `options.outputs[0].amount = 1 USDC` (fully completing output A) and `options.outputs[1].amount = 0` (skipping output B).
3. In the loop, `i = 0`: `amountFilled == totalRequired` triggers `escrowedAmount = _orders[commitment][WETH]` = **1.001 WETH** (the full pool, not the 0.001 WETH allocated to output A).
4. `i = 1`: `solverAmount == 0` and `remaining > 0`, so `isFullyFilled = false`, and `escrowedInputs[1]` stays 0.
5. `_withdraw` is called once with `escrowedInputs = [1.001 WETH, 0]`, `finalize = false`. The solver receives the full 1.001 WETH for the price of just the 1 USDC output, and `_orders[commitment][WETH]` is now 0.
6. The order remains open (`_filled[commitment]` cleared) for output B, but there is no escrow left to pay any future filler of that leg — the user's 1 WETH earmarked for output B is gone.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
