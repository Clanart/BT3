## Title
OAuth sign-in `state` nonce is never invalidated after a failed/timed-out token exchange, allowing replay of the callback deep link to hijack an in-progress sign-in - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
The external report's broken invariant is: a request is fired with a piece of user data that is deleted up front, the request can time out/fail, and there is no mechanism to invalidate that pending request or safely re-associate it with a fresh attempt — so stale request state stays "live" and exploitable/lost. In GitHub Desktop's browser-based OAuth flow, the analogous broken invariant is that the CSRF `state` nonce generated for a sign-in attempt is *never consumed or rotated* after it's used (or after the token exchange fails/times out), so the same `x-github-client://oauth?code=…&state=…` deep link can be replayed, or a new deep link bearing the same `state` value can be delivered again, and `SignInStore.resolveOAuthRequest` will happily process it as long as the store is still parked in the `Authentication` step.

### Finding Description
`SignInStore.authenticateWithBrowser` generates a single `csrfToken` via `crypto.randomUUID()` and stores it in `oauthState.state`, then opens the authorize URL in the external browser [1](#0-0) .

When the OS protocol handler later delivers `x-github-client://oauth?code=…&state=…`, it is parsed by `parseAppURL` (which only checks that `code` and `state` are present strings, with no single-use tracking) [2](#0-1)  and routed to `Dispatcher.dispatchURLAction` → `AppStore._resolveOAuthRequest` → `SignInStore.resolveOAuthRequest` [3](#0-2) .

`resolveOAuthRequest` only checks that a sign-in session is still active and that `action.state` matches `this.state.oauthState.state`; it never clears or rotates `oauthState` after processing, whether the call succeeds or fails: [4](#0-3) 

Crucially, if `requestOAuthToken` fails — including on a network timeout, exactly the failure mode described in the external report — it swallows the error and resolves to `null` rather than throwing: [5](#0-4) . Back in `resolveOAuthRequest`, a `null` token calls `onAuthError`, which is handled by the `.catch()` in `authenticateWithBrowser`. That handler only sets `error`/`loading` on the existing state — it does **not** clear `oauthState` or rotate `csrfToken`: [6](#0-5) 

The corrupted/stale value is `IAuthenticationState.oauthState.state` (the CSRF nonce): it remains valid and comparably "live" for the entire duration the sign-in dialog stays open in the `Authentication` step, regardless of how many times `resolveOAuthRequest` has already been invoked or failed. There is no single-use flag, no expiry, and no PKCE `code_verifier` binding the callback to the specific browser session that initiated it [1](#0-0) .

### Impact Explanation
Because the `state` value is not invalidated after first use or after a failed exchange, any subsequent deep link carrying the same `state` (e.g., replayed by a malicious local app registered for the same custom protocol, a stale browser tab reload, or a crafted link sent to the user while the Desktop sign-in dialog is open) will still be accepted by `resolveOAuthRequest` and will exchange whatever `code` it carries for a token via `requestOAuthToken`, then call `fetchUser` and complete the sign-in with **whatever account that code belongs to** [7](#0-6) . This is an unauthorized OAuth account-binding primitive: an attacker who can get a second `x-github-client://oauth?...&state=<captured>` URL invoked (e.g., via `--protocol-launcher` handling in the main process) while the victim's sign-in dialog is still open can bind their own attacker-controlled account/token into the victim's Desktop instance, or replay a previously-successful callback again since nothing marks it as consumed.

### Likelihood Explanation
The window is bounded by how long the sign-in dialog remains in the `Authentication` step (until the user closes it, which calls `SignInStore.reset()` and clears state) [8](#0-7) . That window is attacker-friendly precisely in the failure/timeout case the external report describes: a slow or failing `requestOAuthToken` call leaves the user staring at an error in the dialog without resetting the flow, during which the stale `state` is still accepted. Reaching this path requires the attacker to get a second protocol-URL invocation delivered to the running Desktop process — a capability Desktop already exposes to any triggerable `x-github-client://` link (browser click, malicious page performing the OS protocol handoff, or command-line `--protocol-launcher` invocation) rather than physical/local access.

### Recommendation
Treat `oauthState.state` as single-use: clear/rotate it immediately after `resolveOAuthRequest` is invoked (success or failure) rather than only on `Success` or explicit `reset()`. Consider adding PKCE (`code_verifier`/`code_challenge`) so a captured `code`+`state` pair cannot be redeemed without material that never leaves the process, and add expiry to the pending `oauthState` so a stalled/timed-out exchange cannot be revived by a later replayed callback.

### Proof of Concept
1. Start GitHub Desktop sign-in (`Dispatcher.beginBrowserBasedSignIn` → `SignInStore.authenticateWithBrowser`), which generates `state = S` and opens the browser to `.../login/oauth/authorize?...&state=S` [1](#0-0) .
2. Simulate the token exchange failing/timing out: `requestOAuthToken` returns `null` [5](#0-4) , which surfaces as `onAuthError` in `resolveOAuthRequest`, leaving `this.state.oauthState.state` still equal to `S` and the dialog showing an error [9](#0-8) .
3. Without the user restarting the flow, invoke the protocol handler again with a second, attacker-supplied `x-github-client://oauth?code=<attacker_code>&state=S`. Because `this.state.oauthState.state === S` still holds, `resolveOAuthRequest` proceeds, exchanges `attacker_code` for a token, fetches the corresponding user, and completes the sign-in as that account [10](#0-9) .

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
