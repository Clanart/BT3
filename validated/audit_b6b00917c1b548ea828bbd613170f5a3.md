### Title
Submodule `file://` protocol allowed during automatic branch/PR checkout can read/exfiltrate local files - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  conditionally adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation whenever its caller passes `allowFileProtocol=true`. `checkoutCommit` in [2](#0-1)  exposes this same `allowFileProtocol` flag (default `false`) and forwards it straight through to the submodule update call after checking out a commit. The unit test at [3](#0-2)  demonstrates a normal "checking out a branch with an uninitialized submodule" flow being invoked with `allowFileProtocol = true`, i.e. this is not an obscure/manual code path — it is the mechanism Desktop uses to make sure branches with newly-added submodules are usable immediately after checkout.

### Finding Description
This mirrors the broken-invariant pattern from the H-10 report: an operation (`creatorClaimSoldTokens`) mutates real state (moves tokens) without updating the bookkeeping variable that a later, security-relevant calculation (`recoverTokens`) depends on, so the later logic operates on stale/incorrect assumptions and its guard fails silently.

Here, the "bookkeeping" is the assumption baked into modern Git (and CVE-2022-39253) that `protocol.file.allow` must default to `user`/`refuse` because a **repository’s `.gitmodules` file is attacker-controlled content** — a submodule URL of `file:///home/user/.ssh` or any other local path is exactly the kind of untrusted "GitHub API/remote-controlled object" the valid-impact criteria call out. Desktop deliberately re-enables the unsafe `always` mode for a specific, legitimate UX reason (freshly-added submodules need to be cloned immediately after checkout), but doing so at the same call site that runs for *any* branch checkout (including a branch fetched from an untrusted fork, e.g. via the PR-checkout / `openRepositoryFromUrl` deep-link flow at [4](#0-3) ) means the "trust" bookkeeping (should this checkout be allowed to touch `file://` submodules) is not tied to whether the branch content is trusted — it's tied only to "is a submodule new". An attacker who controls the fetched branch's `.gitmodules` can add a submodule entry pointing at a local path, and if that checkout path is reached with `allowFileProtocol=true`, `git submodule update --init` with `protocol.file.allow=always` will "clone" arbitrary local directories into the working tree.

### Impact Explanation
If reachable from an attacker-controlled repository/branch (e.g. a forked PR checked out via the deep-link `openrepo` action or `_checkoutPullRequest`), this allows:
- Reading files/directories outside the intended repository (local file disclosure) by pulling them in as a "submodule".
- Silent corruption of what the user later commits/pushes, since the disclosed content becomes part of the working directory and could be staged/committed/pushed to the attacker's remote, exfiltrating local file contents.

This satisfies the "file read outside the repo" / "silent corruption of what the user commits or pushes" categories in the valid-impact list.

### Likelihood Explanation
Medium-to-uncertain. I confirmed the vulnerable primitive exists (`allowFileProtocol` flag threaded from `checkoutCommit`/`checkoutBranch` into `protocol.file.allow=always`) and that ordinary branch-checkout code exercises it with `true` in a test scenario that is not gated by trust of the branch's origin. However, I was not able to fully trace, within the available tool budget, every production call site of `checkoutBranch`/`checkoutCommit` to confirm whether the PR/fork checkout flow (`_checkoutPullRequest`) passes `allowFileProtocol=true` versus `false`, or whether some other trust gate exists upstream that I didn't locate. This should be verified directly in `app/src/lib/stores/app-store.ts` around `_checkoutPullRequest`/`_checkoutBranch` before treating this as confirmed-exploitable.

### Recommendation
- Never pass `allowFileProtocol=true` for checkouts of branches/commits whose provenance is not fully trusted (i.e., not the user's own already-cloned remote), especially PR/fork checkouts reached via `openRepositoryFromUrl`/CLI actions.
- Prefer explicitly allow-listing submodule URLs (scheme = `https`/`ssh`) rather than blanket-enabling `protocol.file.allow=always`, mirroring how `resolveWithin`/`sanitizeCloneName` were hardened elsewhere in this codebase for other attacker-controlled path/URL inputs.
- Add a regression test asserting that checking out a branch from an untrusted/forked remote with a `file://` submodule URL does not create or populate the submodule directory.

### Proof of Concept
1. Attacker forks a public repository and pushes a branch that adds a `.gitmodules` entry: `url = file:///path/to/sensitive/local/dir` (or a plausible per-OS sensitive path).
2. Victim opens the PR / deep link in GitHub Desktop, which triggers `openPullRequestFromUrl` → `_checkoutPullRequest` ( [4](#0-3) ), ultimately reaching `checkoutCommit`/`checkoutBranch` ( [2](#0-1) ).
3. If that code path supplies `allowFileProtocol=true` (as demonstrated feasible by the existing test at [5](#0-4) ), `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive` ( [6](#0-5) ), causing Git to clone the attacker-specified local path into the working directory as a submodule, disclosing its contents inside the victim's repository.

Because I could not conclusively verify step 2's exact `allowFileProtocol` argument for the PR-checkout code path within the available search budget, this should be validated with a Devin session that traces every caller of `checkoutBranch`/`checkoutCommit` in `app/src/lib/stores/app-store.ts`.

export async function checkoutCommit(
  repository: Repository,
  commit: CommitOneLine,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out ${__DARWIN__ ? 'Commit' : 'commit'}`
  const target = shortenSHA(commit.sha)
  const opts = await getCheckoutOpts(
    repository,
    title,
    target,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, commit.sha]

  await git(args, repository.path, 'checkoutCommit', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    target,
    allowFileProtocol
  )

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }
