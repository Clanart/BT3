### Title
Reward-per-token dilution via zero-`totalStaked()` window in `_provisionReward` allows theft of queued rewards - (File: `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool._provisionReward` checks `this.totalStaked() == 0` to decide whether to add incoming rewards to `rewardInfo.queuedRewards` or to immediately update `rewardPerTokenStored`. Because `totalStaked()` reads the live staking-token balance held by `MasterMagpie` (i.e., depends entirely on unprivileged deposit/withdraw calls), an attacker who can transiently drain the pool's stake to zero can force a reward-queuing event, then re-stake a dust amount and trigger the deferred distribution themselves via the unguarded `donateRewards` function, capturing nearly all queued rewards with negligible principal.

### Finding Description
`totalStaked()` in `BaseRewardPool.sol` is a live view over `MasterMagpie`'s token balance for that staking token: [1](#0-0) 

`_provisionReward` branches on this value: if zero, the incoming reward amount is stashed into `rewardInfo.queuedRewards` instead of being reflected in `rewardPerTokenStored`; otherwise it is fully distributed proportionally to `totalStaked()` at that instant, including any previously queued amount: [2](#0-1) 

`rewardPerToken` and `earned` are based purely on this stored accumulator and the caller's live `balanceOf` (i.e., current stake in `MasterMagpie`), with no protection for the size of stake at the time rewards accrued: [3](#0-2) 

Exploit flow:
1. Attacker (either sole staker of that pool, or via flash-loan/front-running when they can transiently dominate stake) calls `MasterMagpie.withdraw` for their full balance, driving `totalStaked() == 0`.
2. A `queueNewRewards` call by any legitimate `manager` (this does not require malicious intent — it's a normal reward-distribution operation) executes while `totalStaked()==0`, so the entire reward amount goes into `rewardInfo.queuedRewards` rather than being distributed to the (now zero) stakers who actually earned it.
3. Attacker deposits a dust amount (e.g., 1 wei) back into the pool via `MasterMagpie.deposit`, becoming ~100% owner of the now-tiny `totalStaked()`.
4. Attacker triggers realization of the queued reward themselves — critically, `donateRewards` is **not** gated by `onlyManager` (unlike `queueNewRewards`), so any unprivileged address can call it: [4](#0-3)  — with `_amountReward = 0` (many ERC20s permit zero-value transfers) or any small amount, entering the `else` branch of `_provisionReward` and folding the full stashed `rewardInfo.queuedRewards` into `rewardPerTokenStored`, computed against the attacker-dominated dust `totalStaked()`.
5. Attacker calls `getReward` and receives essentially the entire queued reward that was meant to accrue to the pool's real stakers.

No existing check prevents this: `queueNewRewards`/`donateRewards` have no minimum-stake or time-weighted safeguard, `_updateFor`/`updateReward` only checkpoint per-account state and don't protect against a globally-manipulated `rewardPerTokenStored`, and there is no `nonReentrant`/pause gate relevant to this state-manipulation path.

### Impact Explanation
This is direct theft of unclaimed/queued yield: rewards intended for legitimate stakers at the time they accrued are instead diverted to an attacker who re-enters with negligible capital (dust deposit) right before triggering the deferred distribution. This matches the Immunefi "theft of unclaimed yield" / "direct theft of user funds" impact class.

### Likelihood Explanation
Feasibility depends on the attacker being able to drive `totalStaked()` for a given pool to exactly zero, which is realistic for low-TVL pools, newly-launched pools, or via flash-loan-assisted withdrawal in the same block/transaction bundle as (or immediately before) a manager's `queueNewRewards` call. The second half of the attack (`donateRewards` call from a dust position) is fully unprivileged, permissionless, and repeatable every time a `queueNewRewards` occurs during a zero-stake window. The main precondition — no competing stakers at the moment of queuing — narrows applicability but is realistic for smaller/newer reward pools, and coordinated timing (front-running the manager's queuing transaction) increases feasibility further.

### Recommendation
Do not let the distribution decision depend on the instantaneous `totalStaked()` at `_provisionReward` time. Options: (1) snapshot/checkpoint reward-per-token accrual using a time-weighted mechanism so rewards can't be attributed to a stake size that didn't exist during the accrual period; (2) require `donateRewards`/`queueNewRewards` to check `totalStaked()` immediately before and after a reasonable staleness window, or restrict `donateRewards` to `onlyManager` as well, removing the fully-permissionless trigger; (3) when releasing `queuedRewards`, distribute over an average/minimum stake observed since queuing rather than the current instantaneous stake.

### Proof of Concept
Foundry test plan:
1. Deploy `BaseRewardPool` wired to a `MasterMagpie` mock and a reward token; register `attacker` as the only staker with balance `X`.
2. `attacker` calls `MasterMagpie.withdraw(X)` making `totalStaked() == 0`.
3. `manager` calls `queueNewRewards(1000e18, rewardToken)`; assert `rewards[rewardToken].queuedRewards == 1000e18` and `rewardPerTokenStored` unchanged.
4. `attacker` calls `MasterMagpie.deposit(1)` (1 wei), making `totalStaked() == 1`.
5. `attacker` (unprivileged) calls `donateRewards(0, rewardToken)`; assert `rewardPerTokenStored` jumps by `1000e18 * 10**decimals / 1`.
6. `attacker` calls `getReward(attacker, attacker)` via `MasterMagpie`; assert attacker receives (approximately) the full `1000e18` reward token despite having contributed 1 wei of stake and no time-weighted exposure to the reward period.
7. Assert this violates conservation: total rewards paid to the dust staker (`~1000e18`) vastly exceeds their pro-rata share based on actual stake-time contribution (expected ~0).

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
