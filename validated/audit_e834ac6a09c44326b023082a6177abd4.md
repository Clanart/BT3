### Title
Cross-transaction overwrite of `data`/`presumed_origin` lets any sender spoof or replace the Serai instruction on another party's Bitcoin deposit — (File: processor/src/networks/bitcoin.rs)

### Summary

CVE-2025-12435 is an incorrect-security-UI / spoofing bug: attacker-controlled content causes the system to present or act on the wrong security-relevant identity. The Serai analog is in `Bitcoin::get_outputs` (`processor/src/networks/bitcoin.rs:686-740`), which decides which Serai instruction (`data`, e.g. a mint destination) and which origin address (`presumed_origin`) are attributed to each received output.

The `outputs` vector accumulates across every transaction in the block, but the "populate the outputs" block runs once per transaction and iterates the *entire accumulated* vector. Once the first matching output exists, `outputs` is never empty again, so every later transaction in the block — even one paying Serai nothing — triggers `Address::new` from `tx.input[0]` and `extract_serai_data(tx)`, and unconditionally overwrites `presumed_origin` on all prior outputs and `data` on all prior `OutputType::External` outputs (`processor/src/networks/bitcoin.rs:701-736`).

### Finding Description

```rust
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) { ... outputs.push(output); }
  if outputs.is_empty() { continue; }          // cumulative, not per-tx
  let presumed_origin = { let input = &tx.input[0]; ... };   // this tx's input[0]
  let data = Self::extract_serai_data(tx);                   // this tx's data
  for output in &mut outputs {                 // ALL outputs seen so far
    if output.kind == OutputType::External { output.data.clone_from(&data); }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
```

Two reachable defects:

1. **Cumulative overwrite**: `outputs.is_empty()` never re-empties within a block, so transaction `tx_j` (j > i) rewrites `data` and `presumed_origin` for outputs produced by an unrelated earlier transaction `tx_i`. An attacker who gets *any* transaction into the same block after a victim's deposit replaces the victim's `External` output `data` with the attacker's own `extract_serai_data` result — either an OP_RETURN payload of their choosing or a witness-embedded `InInstruction` (`extract_serai_data`, `processor/src/networks/bitcoin.rs:493-524`). The same flaw mis-attributes the origin of victim outputs to the attacker's `tx.input[0]` prevout address.

2. **First-input origin spoofing**: even without cross-tx bleed, `presumed_origin` is derived solely from `tx.input[0]` (`processor/src/networks/bitcoin.rs:715`), so a multi-input deposit lets the sender put any input first to make the deposit appear to come from an arbitrary address.

The attacker is an unprivileged Bitcoin user sending ordinary transactions — no validator, peer, or RPC compromise required.

### Impact Explanation

For `OutputType::External` outputs, `data` is the Serai instruction attached to the deposit (the mechanism tests attach a `Shorthand::transfer` to a Serai address, `processor/src/tests/literal/mod.rs:88-118`). Overwriting it lets an attacker swap a victim's attached instruction for their own (e.g., redirecting the minted funds' destination) or wipe it entirely. Overwriting `presumed_origin` mis-attributes the source of funds for every scanned output in the block — the direct analog of the Chrome UI-spoofing primitive, applied to Serai's attribution of deposit metadata instead of a browser omnibox.

### Likelihood Explanation

The attacker only needs a transaction positioned later in the same block as the victim's deposit — obtainable by watching the mempool for deposits to a known multisig address and fee-bribing for inclusion, or via any miner cooperation. No threshold collusion or key material is needed. The overwrite is deterministic given ordering. Cost is one ordinary transaction plus fees; impact is theft/misattribution of deposit instructions, consistent with Medium severity.

### Recommendation

Scope the population loop to the outputs produced by the current transaction:

```rust
let start = outputs.len();
for output in scanner.scan_transaction(tx) { ... outputs.push(output); }
if outputs.len() == start { continue; }
...
for output in &mut outputs[start ..] { ... }
```

Additionally, `presumed_origin` should be computed per-output (or documented as best-effort across all inputs) rather than trusting `tx.input[0]` alone, and `data` should only be attached to the `External` output(s) of the transaction that actually carried it.

### Proof of Concept

1. Victim broadcasts `txV` depositing to the Serai external address, embedding an OP_RETURN `InInstruction` crediting their Serai account. It confirms in block `B` at index `i`.
2. Attacker crafts `txA` with (a) an OP_RETURN carrying their own serialized Serai instruction and (b) a first input spending an output whose script_pubkey maps to a "clean"/chosen address. `txA` confirms in `B` at index `j > i` and pays nothing to the scanner.
3. `get_outputs(B, key)` scans `txV`, pushes the `External` output, sets correct `data`/`presumed_origin`. When `txA` is reached, `outputs` is still non-empty, so `presumed_origin` is recomputed from `txA.input[0]` and `data = extract_serai_data(txA)`, then `for output in &mut outputs` overwrites the victim's `External` output fields.
4. The scanner emits `txV`'s output carrying the attacker's instruction and the attacker's `input[0]` address as `presumed_origin` — attacker-attributed metadata attached to victim funds.

Note: the exact downstream handling of `Output.data`/`presumed_origin` in `processor/src/multisigs/mod.rs` could not be fully inspected in this pass; the overwrite itself in `get_outputs` is confirmed by the code cited.
