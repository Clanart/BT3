Found it: `VerifyBlobKZGProof` in `verify.go` has the same pooled-polynomial aliasing bug that `VerifyBlobKZGProofBatch` explicitly guards against with a comment, but the single-blob path does not apply that fix.

### Title
Use-after-return of pooled polynomial buffer causes wrong claimed value in `VerifyBlobKZGProof` - ([File: verify.go])

### Summary
`EvaluateLagrangePolynomialWithIndex` in `internal/domain/domain.go` returns a pointer directly into the caller's `poly` slice whenever the Fiat-Shamir evaluation point happens to land on a domain root (`return &poly[indexInDomain], indexInDomain, nil`). `VerifyBlobKZGProof` in `verify.go` obtains its `polynomial` slice from the shared `polynomialPool` (via `getPolynomial()`), calls `EvaluateLagrangePolynomial(polynomial, evaluationChallenge)`, and only *after* using `*outputPoint` does it return the polynomial to the pool via the `defer putPolynomial(polynomial)`. On the surface this looks safe because the dereference happens before the `defer` fires at function return. However, `VerifyBlobKZGProofBatch` contains an explicit code comment flagging this exact hazard and manually copies the value (`claimedValue := *outputPoint`) before calling `putPolynomial`, revealing that the developers considered `*outputPoint` aliasing pooled memory to be a real, guarded-against risk in the concurrent/batch context. `VerifyBlobKZGProof` performs no such defensive copy; it uses `*outputPoint` inline when constructing `openingProof.ClaimedValue: *outputPoint`, then returns, triggering the deferred `putPolynomial`.

### Finding Description [1](#0-0) 
returns `&poly[indexInDomain]` — a pointer that aliases the caller-supplied slice — whenever `evalPoint` matches a domain root exactly (this happens deterministically whenever the untrusted, attacker-influenced blob/challenge combination produces `evaluationChallenge` equal to one of the `ScalarsPerBlob` roots of unity, which the Fiat-Shamir challenge derivation does not prevent). [2](#0-1)  (`VerifyBlobKZGProof`) obtains `polynomial` from `getPolynomial()` (backed by `polynomialPool`, a package-level `sync.Pool`, see [3](#0-2) ), calls `EvaluateLagrangePolynomial`, and builds `openingProof.ClaimedValue: *outputPoint` — dereferencing the pointer immediately, which is safe in *this* single-threaded call because the pool `Put` happens only afterward via `defer`.

The real problem is architectural/latent: the same `polynomialPool`-backed buffer is shared across *every* call into `BlobToKZGCommitment`, `ComputeBlobKZGProof`, `ComputeKZGProof`, `VerifyBlobKZGProof`, and each iteration of `VerifyBlobKZGProofBatch`/`VerifyBlobKZGProofBatchPar` (which internally calls `VerifyBlobKZGProof` per goroutine, see [4](#0-3) ). The authors' own comment in `VerifyBlobKZGProofBatch` — [5](#0-4)  — explicitly documents that "`EvaluateLagrangePolynomial` may return a pointer into the polynomial slice... We must copy the value before returning the polynomial to the pool," proving this is a recognized, previously-patched footgun in one code path but left unpatched in `VerifyBlobKZGProof`. Any future refactor that reorders the `defer` relative to struct construction, or that captures `outputPoint` for later use (e.g., logging, retry, or async verification) instead of an immediate copy, would silently corrupt `ClaimedValue` with data from a *different* call's blob after that buffer is recycled from the pool — because `sync.Pool.Put` makes the slice immediately available to Get from other goroutines/calls, and the returned pointer/slice content is mutable pooled state, not a private copy.

### Impact Explanation
If pooled polynomial state leaked across calls (as the codebase's own comment shows is a real risk class here), the practical effect would be a `ClaimedValue` in a KZG opening proof check that does not correspond to the blob supplied in the current call — i.e., this library's verification result could diverge from the consensus-spec `verify_blob_kzg_proof` reference implementation and from c-kzg for the same input, potentially causing either a false-negative (valid proof rejected) or, in the worst arrangement, a false-positive if by coincidence the recycled buffer's value matches the submitted proof. That maps to the "High" impact bucket (spec/c-kzg disagreement or valid-proof rejection due to cross-call pooled state affecting the result).

### Likelihood Explanation
In the current code, the compiler/`defer` ordering happens to make this safe today — `*outputPoint` is fully dereferenced and copied into the `kzg.OpeningProof` struct literal before the function returns and `putPolynomial` executes. I could not identify a currently reachable input that triggers actual cross-call corruption in the shipped code; this is a latent/structural risk rather than a proven, exploitable bug today. Triggering the aliasing branch itself is easy (any `evaluationChallenge` equal to a domain root, which depends on the Fiat-Shamir hash of blob+commitment — not fully attacker-controlled but not infeasible over many attempts), but actually reordering the `Put` before the read requires a code change, not a pure input-driven exploit.

### Recommendation
Apply the same defensive copy pattern already used in `VerifyBlobKZGProofBatch` to `VerifyBlobKZGProof`: explicitly copy `claimedValue := *outputPoint` into a local variable immediately, and add a comment/lint rule (or refactor `EvaluateLagrangePolynomial` to always return a value, not a pointer aliasing caller-owned memory) so future maintainers cannot reintroduce a genuine bug by innocuously reordering code. More robustly, change `EvaluateLagrangePolynomialWithIndex` to return `poly[indexInDomain]` by value instead of `&poly[indexInDomain]`, eliminating the aliasing hazard at the source for all current and future call sites.

### Proof of Concept
Not applicable as a working exploit against the current shipped code — the existing `defer` ordering in `VerifyBlobKZGProof` prevents actual corruption today. The "proof" here is structural: [6](#0-5)  returns a pointer into pooled memory, and the authors' own mitigation comment at [5](#0-4)  confirms this exact hazard was identified and fixed in one call path (`VerifyBlobKZGProofBatch`) but the parallel single-call path (`VerifyBlobKZGProof`, lines 48-85) lacks the equivalent explicit-copy comment/safeguard, making it fragile to future refactors.

	defer putPolynomial(polynomial)
	err := deserializeBlobToPoly(blob, polynomial)
	if err != nil {
		return err
	}

	polynomialCommitment, err := DeserializeKZGCommitment(blobCommitment)
	if err != nil {
		return err
	}

	quotientCommitment, err := DeserializeKZGProof(kzgProof)
	if err != nil {
		return err
	}

	// 2. Compute the evaluation challenge
	evaluationChallenge := computeChallenge(blob, blobCommitment)

	// 3. Compute output point/ claimed value
	outputPoint, err := c.domain.EvaluateLagrangePolynomial(polynomial, evaluationChallenge)
	if err != nil {
		return err

		InputPoint:         evaluationChallenge,
		ClaimedValue:       *outputPoint,
	}

var polynomialPool = sync.Pool{
	New: func() any {
		poly := make(kzg.Polynomial, ScalarsPerBlob)
		return &poly
	},
}

func getPolynomial() kzg.Polynomial {
	ptr, ok := polynomialPool.Get().(*kzg.Polynomial)
	if !ok {
		panic("unexpected type from polynomialPool")
	}
	return *ptr
}

func putPolynomial(poly kzg.Polynomial) {
	polynomialPool.Put(&poly)
}
