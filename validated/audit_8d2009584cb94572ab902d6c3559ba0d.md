### Title
`ReceivedOutput::read` accepts a scalar offset that does not correspond to the output's `script_pubkey`, producing unspendable "received" funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

The external report describes a silent-failure class: a call returns an error code instead of reverting, and the caller proceeds on the false assumption of success, creating a divergence between perceived and actual state. The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`: it deserializes three independently-supplied fields (`offset`, `output`, `outpoint`) and returns `Ok(ReceivedOutput)` without ever checking that the claimed scalar `offset` actually derives the Taproot `script_pubkey` contained in `output`. A malformed `ReceivedOutput` is therefore silently accepted, and downstream wallet code treats the output as spendable under that offset when it is not.

### Finding Description

`Scanner::scan_transaction` (mod.rs:199-214) is the only honest producer of `ReceivedOutput`: it looks up `output.script_pubkey` in `self.scripts` and attaches the `Scalar` offset that was registered for that exact script via `register_offset` (mod.rs:180-196). The offset-to-script binding is the security-critical invariant — the offset is what re-keys the threshold key so the output can be signed for.

`ReceivedOutput::read` (mod.rs:122-134) reconstructs the same struct from a byte stream:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

It performs canonical scalar decoding (`read_F`) and consensus decoding of the `TxOut`/`OutPoint`, but never re-derives `p2tr_script_buf(key + G * offset)` nor compares it against `output.script_pubkey`. The consistency check that the scanner enforces by construction is silently dropped on deserialization — the exact analog of ignoring `mToken.mint()`'s error code: the failure condition (offset does not match script) produces a structurally valid, `Ok`-wrapped object instead of an error.

`ReceivedOutput` is in the listed untrusted-read surface, so these bytes can be attacker-influenced wherever serialized outputs cross a trust boundary (e.g., relayed/indexed data fed back into a wallet).

### Impact Explanation

The reader obtains a `ReceivedOutput` that reports `value()` satoshis as received and spendable under `offset()`, but whose `output.script_pubkey` is not the P2TR script of `key + G*offset`. When the wallet later builds a spend, the signer applies the stored offset to the threshold key; the resulting Taproot internal key does not match the output's script, so any produced signature fails BIP-341 verification — the funds are reported received but are not spendable. Alternatively, an attacker can supply an offset corresponding to a *different* registered script, causing the wallet to attempt spending under the wrong key entirely. This satisfies the "funds reported received that are not spendable" acceptance criterion, mirroring the report's "imbalance between perceived balance and actual supply."

### Likelihood Explanation

Reachability requires attacker-controlled bytes to reach `ReceivedOutput::read`. The struct is explicitly designed for serialization (`serialize`, `write`, `read` — mod.rs:120-148) for storage/transport, which is precisely where untrusted or corrupted data enters. No signature, key material, or validator collusion is needed; only control over serialized bytes. Likelihood is moderate: it depends on an integrator deserializing outputs from a non-trusted source, but no other preconditions exist — every `ReceivedOutput` read is silently trusted once decoded.

### Recommendation

`ReceivedOutput` should not be deserializable into an inconsistent state. Either:

- Store the `Scanner`'s key (or the script map) and have `read`/`write` record only the `outpoint` + `TxOut`, re-deriving the offset via `scan_transaction`-equivalent lookup on load; or
- Add a `ReceivedOutput::verify(key: &ProjectivePoint) -> bool` that recomputes `p2tr_script_buf(key + G*offset)` and compares it to `output.script_pubkey`, and mandate it after `read`.

This makes the failure explicit (an `Err`/`false`) rather than silently constructing a struct whose fields contradict each other — the same fix pattern as adding return-value validation to `mToken.mint()`.

### Proof of Concept

```rust
// Attacker crafts bytes for ReceivedOutput::read
let mut bytes = vec![];
// offset = arbitrary scalar, e.g. 1
bytes.extend(Scalar::ONE.to_bytes());
// TxOut paying to the wallet's REAL registered script for a different offset
bytes.extend(serialize(&TxOut { value: Amount::from_sat(50_000), script_pubkey: victim_script }));
bytes.extend(serialize(&real_outpoint));

let ro = ReceivedOutput::read(&mut &bytes[..]).unwrap(); // Ok — silently accepted
assert_eq!(ro.offset(), Scalar::ONE);
// ro.value() == 50_000 reported as received/spendable,
// but signing with offset=1 yields a Taproot key != victim_script's key:
// any spend attempt produces an invalid BIP-340 signature.
```

Uncertainty: whether an in-scope call path feeds truly attacker-controlled bytes to `ReceivedOutput::read` (rather than local DB storage) is not fully verified within the indexed code; the finding holds wherever that read boundary is untrusted, which the task's reachability rules stipulate.
