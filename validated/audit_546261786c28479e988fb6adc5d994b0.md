## Consuming-application exposure assumption

A client application embeds a `.proto` schema with a packed, repeated extension field, and calls the public Objective-C parsing API (`GPBMessage parseFromData:`/`mergeFromCodedInputStream:extensionRegistry:`) on attacker-supplied, bounded binary protobuf bytes. The schema, generated code, and extension registry are trusted; only the wire bytes are attacker-controlled.

### Title
Negative packed-extension length bypasses `CheckFieldSize`, causing integer wraparound in `GPBCodedInputStreamPushLimit`/`BytesUntilLimit` - (File: objectivec/GPBMessage.m)

### Summary
`ExtensionMergeFromInputStream` in `objectivec/GPBMessage.m` reads the length prefix of a packed extension field with `GPBCodedInputStreamReadInt32`, an operation that returns a signed 32-bit value and — unlike every other length-delimited read path in the Objective-C runtime — never calls `CheckFieldSize()`. A crafted varint whose top bit is set decodes to a negative `int32_t`. That negative value is passed directly into `GPBCodedInputStreamPushLimit`, whose parameter is `size_t` (unsigned), producing an integer underflow/wraparound analogous to the SPF macro-parsing underflow in ALPINE-CVE-2023-42118: an unvalidated attacker length is used in unsigned pointer/limit arithmetic before any range check can reject it.

### Finding Description
Compare the packed-extension path to every sibling length-delimited path in the same file/module:

- `readMessage:` / `readMapEntry:` / `GPBCodedInputStreamReadRetainedBytes` / `GPBCodedInputStreamReadRetainedString` all read the length with `GPBCodedInputStreamReadUInt64` and immediately call `CheckFieldSize(size)`, which rejects any value `> 0x7fffffff` (there is no negative case because the value is already `uint64_t`). [1](#0-0) [2](#0-1) 

- The packed extension path instead does:
```
int32_t length = GPBCodedInputStreamReadInt32(state);
size_t limit = GPBCodedInputStreamPushLimit(state, length);
while (GPBCodedInputStreamBytesUntilLimit(state) > 0) { ... }
``` [3](#0-2) 

`GPBCodedInputStreamReadInt32` simply casts the raw varint to `int32_t` with no sign/size validation: [4](#0-3) 

If the wire bytes encode a varint such as `0x80808080F8`-style value with the top bit of the 32-bit result set (e.g., value `0xFFFFFFFF` = `-1` as `int32_t`), `length` becomes negative. This negative `int32_t` is passed as the `size_t byteLimit` parameter of `GPBCodedInputStreamPushLimit`:
```
size_t GPBCodedInputStreamPushLimit(GPBCodedInputStreamState *state, size_t byteLimit) {
  byteLimit += state->bufferPos;
  size_t oldLimit = state->currentLimit;
  if (byteLimit > oldLimit) { GPBRaiseStreamError(...); }
  state->currentLimit = byteLimit;
  return oldLimit;
}
``` [5](#0-4) 

Converting `int32_t -1` to `size_t` sign-extends to a huge unsigned value (`SIZE_MAX`). Adding `state->bufferPos` to `SIZE_MAX` wraps back around to a *small* value, which is highly likely to be `≤ oldLimit`, so the bounds check `byteLimit > oldLimit` — the only safety net in this function — is bypassed. `state->currentLimit` is then set to this small, wrapped value, which can end up **smaller than the current `bufferPos`**.

The invariant that fails is exactly the SPF-CVE class: an attacker-controlled quantity that should be validated as non-negative/bounded before being used in unsigned arithmetic is instead trusted, and the subsequent addition/subtraction underflows. Here the corrupted invariant propagates into `GPBCodedInputStreamBytesUntilLimit`:
```
size_t GPBCodedInputStreamBytesUntilLimit(GPBCodedInputStreamState *state) {
  return state->currentLimit - state->bufferPos;
}
``` [6](#0-5) 

If `currentLimit < bufferPos` (a state reachable only through this unchecked path), this unsigned subtraction itself underflows to a near-`SIZE_MAX` value, making the packed-loop condition `GPBCodedInputStreamBytesUntilLimit(state) > 0` in `ExtensionMergeFromInputStream` permanently true. The loop then keeps invoking `DecodeSingleValueFromInputStream`, driving the parser to read far past the field's intended length, corrupting the state machine's notion of the current limit/position (`state->bufferPos` can even be forced backwards by `CheckSize`'s "fast forward to end of currentLimit" logic, since `currentLimit` is now bogus).

### Impact Explanation
This is a genuine invariant violation reachable from ordinary binary-protobuf parsing of a trusted schema containing a packed repeated extension field — no privileged access or hostile schema required. The immediate, demonstrable consequences are: (1) bypass of the length-limit safety check that every other length-delimited decode path in this file enforces via `CheckFieldSize`, and (2) an unsigned-subtraction underflow that corrupts the parser's stream-position bookkeeping (`bufferPos`/`currentLimit` can go inconsistent, with `bufferPos` potentially forced backward by the `CheckSize` "fast forward" branch). Depending on how deeply the corrupted limit/position state is exploited by subsequent reads within the same buffer, this can manifest as parser state corruption, incorrect field values, or a crash from the eventual `GPBRaiseStreamError` — comparable in bug-class (unchecked attacker length feeding unsigned arithmetic that underflows a bounds check) to the underflow in the reported CVE, though I could not fully trace whether the corrupted state alone yields memory writes outside `state->bytes` (all raw byte accesses still ultimately funnel through `CheckSize`, which compares against `state->bufferSize`, the actual buffer bound) — so I state this uncertainty explicitly: the OOB-write potential is not proven, but the check-bypass and unsigned-underflow themselves are concretely demonstrated by the code.

### Likelihood Explanation
High likelihood of reachability: any protobuf schema with a packed extension field, parsed via the Objective-C runtime's `mergeFromCodedInputStream:extensionRegistry:`, hits `ExtensionMergeFromInputStream` for that field. Producing a 5-byte varint whose decoded low 32 bits have the sign bit set is trivial for an attacker crafting the wire bytes. The bug requires no cooperation from the schema author and no non-default configuration.

### Recommendation
In `objectivec/GPBMessage.m`, read the packed-extension length the same way every other length-delimited field is read: use `GPBCodedInputStreamReadUInt64` (or `ReadUInt32`) and call `CheckFieldSize(size)` before calling `GPBCodedInputStreamPushLimit`, rejecting negative/too-large values exactly as `readMessage:`/`readMapEntry:`/`readBytes`/`readString` already do. Additionally, harden `GPBCodedInputStreamPushLimit` and `GPBCodedInputStreamBytesUntilLimit` to defensively reject/clamp cases where the computed `currentLimit` would be less than `bufferPos`, so a single missed call site cannot corrupt global stream invariants.

### Proof of Concept
Construct a serialized message containing one packed extension field whose wire bytes are:
```
tag (length-delimited wiretype for the packed extension field)
varint length bytes: 0xFF 0xFF 0xFF 0xFF 0x0F   // decodes low 32 bits to 0xFFFFFFFF == -1 as int32_t
```
Feed this into `[SomeMessage parseFromData:extensionRegistry:...]` where `SomeMessage` has a packed repeated extension registered in `extensionRegistry`. Tracing the code:
1. `ExtensionMergeFromInputStream` reads `length = GPBCodedInputStreamReadInt32(state)` → `-1` (no validation). [7](#0-6) 
2. `GPBCodedInputStreamPushLimit(state, -1)` implicitly converts `-1` to `SIZE_MAX`, `byteLimit += bufferPos` wraps to a small number, bypassing `byteLimit > oldLimit`. [5](#0-4) 
3. `state->currentLimit` is now smaller than (or inconsistent with) `state->bufferPos`.
4. `GPBCodedInputStreamBytesUntilLimit` computes `currentLimit - bufferPos`, which underflows to a huge `size_t`, keeping the `while` loop in `ExtensionMergeFromInputStream` from terminating correctly. [6](#0-5)
