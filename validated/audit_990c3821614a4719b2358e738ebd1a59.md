### Title
Uncaught assertion / undefined-behavior crash on unvalidated `Duration`/`Timestamp` fields consumed by `TimeUtil::*ToNanoseconds/Microseconds/...` after a normal `ParseFromString` - (File: `src/google/protobuf/util/time_util.cc`)

### Summary
`TimeUtil::DurationToNanoseconds` (and its `Microseconds`/`Milliseconds`/`Seconds` siblings, plus the `Timestamp` equivalents) assume as a precondition that the `Duration`/`Timestamp` message is already range-valid, and only assert this with `ABSL_DCHECK`, not an always-on check. A `Duration`/`Timestamp` obtained from a normal, bounded `ParseFromString`/`MergeFrom` call on attacker-controlled bytes can freely contain out-of-range `seconds`/`nanos` values, because the wire parser performs no semantic validation on these plain `int64`/`int32` fields. Feeding such a message into `TimeUtil::DurationToNanoseconds` violates the function's documented precondition: in debug/assertion-enabled builds this aborts the process (fatal `ABSL_DCHECK`), and in `NDEBUG` builds the subsequent `seconds() * kNanosPerSecond + nanos()` computation is signed-integer overflow, which is undefined behavior. This mirrors the analog invariant failure in the reported `boojum` bug: a numeric result derived from attacker-influenced input is fed into an operation that silently assumes it fits an expected range, and the "safety net" (`unwrap()` there, `ABSL_DCHECK` here) only turns the violation into a crash rather than preventing it.

### Finding Description
`Duration` and `Timestamp` are ordinary generated messages with unconstrained `int64 seconds` / `int32 nanos` fields [1](#0-0) . Nothing in `ParseFromString`/wire decoding enforces `IsDurationValid`/`IsTimestampValid` bounds — those are utility-level helpers, not decoder-level checks. `TimeUtil::DurationToNanoseconds` explicitly documents that behavior is undefined if its precondition doesn't hold, and only guards it with a `ABSL_DCHECK`, not a `ABSL_CHECK`: [2](#0-1) 

The same pattern repeats for `DurationToMicroseconds`, `DurationToMilliseconds`, and the corresponding `Timestamp` conversions, all layered on top of `DurationToSeconds`'s `ABSL_DCHECK` [3](#0-2) . The header itself states the precondition and its consequence in plain terms: [1](#0-0) 

The project's own tests confirm that violating this precondition is fatal in assertion-enabled builds (`EXPECT_DEATH`), i.e. that the check is real but only conditionally compiled in: [4](#0-3) 

This is structurally identical to the reported `boojum` bug: `q` is computed from attacker-influenceable `a, b, m` and assumed (but not proven) to fit `U256`; here, `seconds`/`nanos` are directly attacker-controlled via the wire and assumed (but not enforced by the parser) to fit `Duration`'s documented valid range before an unchecked arithmetic operation is performed on them.

### Impact Explanation
- In any build where Abseil's `ABSL_DCHECK` is active (which includes many non-`NDEBUG` builds, sanitizer builds, and any service compiled with assertions/DCHECK-always-on for extra safety — a common production hardening choice), a single out-of-range `Duration`/`Timestamp` field parsed from attacker-controlled bytes and later passed to a `TimeUtil::*To*` conversion aborts the process, which is a remote denial-of-service against any consuming application that performs this exact common composition ("parse a proto containing a `Duration`/`Timestamp`, then convert it with `TimeUtil`").
- In pure `NDEBUG` release builds, the same input causes signed-integer-overflow UB in the multiply/add, which is a correctness/integrity issue (silently wrong nanosecond/millisecond values feeding into downstream logic such as deadline or rate calculations) and, per the C++ standard, technically undefined behavior a compiler is free to miscompile around.

### Likelihood Explanation
`Duration`/`Timestamp` fields have no wire-level range restriction, so any client using the standard, bounded public `ParseFromString`/`MergeFrom` API can trivially set `seconds` to `INT64_MAX` or any other out-of-range value. Any application that parses such a message and calls a `TimeUtil` conversion helper (a very common, documented, first-party pattern for consuming Well-Known Types) reaches this code path without any additional preconditions, elevated privileges, or malicious schema/plugin involvement.

### Recommendation
Make the precondition check in `TimeUtil::DurationToNanoseconds`/`TimestampToNanoseconds`/etc. an always-on `ABSL_CHECK`, or better, return an `absl::StatusOr`/failure instead of asserting, so out-of-range attacker-supplied `Duration`/`Timestamp` values are rejected uniformly across build configurations rather than relying on `NDEBUG`-gated `ABSL_DCHECK`, which either crashes (debug) or silently overflows (release).

### Proof of Concept
1. Construct a `Duration` message with `seconds = INT64_MAX` (or any value outside `[kDurationMinSeconds, kDurationMaxSeconds]`) using a normal serializer/`SetInt64Field`-equivalent, i.e. exactly what an attacker can produce and transmit as bounded binary protobuf bytes.
2. A receiving application calls `Duration d; d.ParseFromString(attacker_bytes);` via the public parse API — this succeeds because the wire format has no semantic bound on `int64 seconds`.
3. The application then calls `TimeUtil::DurationToNanoseconds(d);`, exactly mirroring the documented usage pattern and the test fixture at [5](#0-4) , which shows this call `EXPECT_DEATH`s ("outside of the valid range") for an out-of-range `Duration` — demonstrating the crash is real and reachable, not merely theoretical, whenever `ABSL_DCHECK` is compiled in; when it is compiled out, the same call performs an unchecked `seconds() * kNanosPerSecond + nanos()` on attacker-chosen `int64_t` values, i.e. signed overflow UB [2](#0-1) .

int64_t TimeUtil::DurationToNanoseconds(const Duration& duration) {
  ABSL_DCHECK(IsDurationValid(duration))
      << "Duration is outside of the valid range";
  return duration.seconds() * kNanosPerSecond + duration.nanos();
}

int64_t TimeUtil::DurationToMicroseconds(const Duration& duration) {
  return DurationToSeconds(duration) * kMicrosPerSecond +
         RoundTowardZero(duration.nanos(), kNanosPerMicrosecond);
}

int64_t TimeUtil::DurationToMilliseconds(const Duration& duration) {
  return DurationToSeconds(duration) * kMillisPerSecond +
         RoundTowardZero(duration.nanos(), kNanosPerMillisecond);
}

int64_t TimeUtil::DurationToSeconds(const Duration& duration) {
  ABSL_DCHECK(IsDurationValid(duration))
      << "Duration is outside of the valid range";
  return duration.seconds();
}
