### Title
Disabling Git's built-in clone-protection guard (`GIT_CLONE_PROTECTION_ACTIVE=false`) during recursive clone can let a malicious repository execute hooks/config on the victim's machine - (File: `app/src/lib/git/clone.ts`)

### Summary
The external report's bug class is: a privileged/trusted code path deliberately turns off a validation guard that upstream (circuit/rolling-hash) logic relies on to reject attacker-controlled data, letting untrusted input be accepted as if verified. GitHub Desktop's `clone()` function reproduces this pattern at the git level: it explicitly sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` for every `git clone --recursive` invocation, unconditionally disabling git's own built-in protection that git itself introduced to stop repository content from triggering unwanted local file writes/hook execution during clone and submodule checkout.

### Finding Description
`clone()` builds the clone environment as: [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is the actual upstream git safety switch (default `'true'` since the git 2.45.x security releases) that aborts a clone/recursive-submodule checkout when the resulting working tree would place files in unexpected/sensitive locations (e.g. via crafted nested `.git`, symlinked directories, or hook paths surfaced through recursive submodules) — the class of issue behind the 2024 git clone/submodule advisories. Desktop force-disables this guard on every clone (`--recursive` is always passed, so submodules belonging to an attacker-controlled remote are always fetched and checked out), and the app-level mitigations that exist elsewhere in this codebase (`isClonePathSensitive`, `sanitizeCloneName`) only validate the *top-level destination path* chosen by the user/URL — they do nothing to validate content written by git itself while checking out nested submodules, which is precisely what `GIT_CLONE_PROTECTION_ACTIVE` guards against.

This mirrors the report's broken invariant exactly: a lower-level validation (`batchReceptionIndices` verification / `unchecked` counter guard in the L2MessageManager) is bypassed by a trusted caller, letting attacker-supplied data (arbitrary anchored messages) be accepted without the check the system was designed to enforce. Here, the "message setter" is whichever code path calls `clone()`/`updateSubmodulesAfterOperation` with `allowFileProtocol` for a repository URL fully controlled by the attacker (a link the user clicked via `x-github-client://openrepo/...`, parsed in `parse-app-url.ts`, or a manually entered clone URL), and the "arbitrary anchoring" is git being told to skip its own content-safety check while materializing that attacker's repository (including recursive submodules) onto disk. [2](#0-1) 

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE` exists specifically to stop git from writing/overwriting files outside the intended checkout in certain crafted-repository scenarios (the scenario the upstream flag was created for), unconditionally disabling it for every clone means Desktop reintroduces exactly the class of bug git patched: cloning or fetching an attacker-controlled repository (including one reached through submodules, forks, or an "Open in Desktop" deep link) can result in file writes outside the intended repository directory or unexpected local state corruption, entirely under the attacker's control and without any user action beyond cloning/opening the link. This satisfies the "attacker controls a cloned/fetched repository ... result is code execution, file write ... outside the repo" impact bar.

### Likelihood Explanation
Every clone Desktop performs goes through this code path (`clone()` is the single implementation used by the Clone dialog, CLI `--cli-clone`, and the `open-repository-from-url` protocol action), and `--recursive` submodule handling is always enabled, so the disabled guard is on the hot path for any attacker who can get a victim to clone or open a link to a malicious/malicious-fork repository — no local access, admin rights, or pre-existing compromise needed.

### Recommendation
Do not blanket-disable `GIT_CLONE_PROTECTION_ACTIVE`. Only disable it (if at all) after confirming the specific git version/behavior requiring the workaround, and prefer a scoped, minimal-risk configuration (e.g. only affecting the top-level clone destination validation already covered by `isClonePathSensitive`) rather than removing the guard for the whole recursive clone/submodule tree. At minimum, gate the override behind an explicit understanding of what the flag protects against, and add regression tests analogous to `clone-path-safety-test.ts` that assert files cannot be written outside the destination tree during a recursive clone of a crafted repository.

### Proof of Concept
1. Attacker crafts a repository containing a submodule (or nested `.git` structure) engineered to exploit the class of clone-time path issue that `GIT_CLONE_PROTECTION_ACTIVE=true` is designed to block (equivalent to the upstream git clone-protection advisories).
2. Attacker distributes the repo URL via a normal clone link or an `x-github-client://openrepo/<url>` deep link, handled by `parseAppURL`/`dispatchURLAction` → `openRepositoryFromUrl`. [3](#0-2) 
3. Victim opens the link or clones normally; Desktop calls `clone()` with `--recursive` and `GIT_CLONE_PROTECTION_ACTIVE=false`. [4](#0-3) 
4. Because the protection env var is forced off, git performs the checkout without the safety check it would otherwise apply, allowing the crafted repository/submodule content to be materialized in a way the disabled guard was meant to prevent.

Note: I could not find in-repo documentation or a changelog entry explaining *why* `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` here (searches for `CVE-2024`/`CLONE_PROTECTION` in `changelog.json` and commit history returned no explanatory context beyond the raw string match in `clone.ts`), so the specific upstream git advisory this flag maps to and the exact exploit primitive it guards against should be confirmed against the installed `dugite`/git version bundled with this app before treating this as fully confirmed exploitable — the code-level fact (protection explicitly and unconditionally disabled on every recursive clone) is verified from local code.
