### Title
`internal_withdraw` RPC bypasses the aggregator-authenticity check enforced by `withdraw` - (File: core/src/rpc/operator.rs)

### Summary
The reported bug class is a missing sender-identity check that lets a caller reach privileged behavior meant only for a specific counterparty (aliasing applied to EOAs that should never be aliased). The closest reachable analog in this repository is `ClementineOperator::internal_withdraw`, which triggers the exact same privileged, signing operation as `ClementineOperator::withdraw` but omits the verification-signature check that binds the request to the aggregator.

### Finding Description
`withdraw` in `core/src/rpc/operator.rs` requires, when `self.operator.config.aggregator_verification_address` is configured, that the caller supply a `verification_signature`, recovers the signer address via `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` (core/src/rpc/ecdsa_verification_sig.rs), and rejects the request unless the recovered address equals `address_in_config`: [1](#0-0) 

`internal_withdraw`, however, parses the same withdrawal parameters and calls `self.operator.withdraw(...)` directly — the same state-changing/signing call that produces a signed payout transaction — with no verification-signature check, no `aggregator_verification_address` comparison, and unlike the sibling `internal_finalized_payout` method (which explicitly gates itself with `if !cfg!(test) { return Err(...) }`), it carries no such test-only guard: [2](#0-1) [3](#0-2) 

This is structurally the same class of defect as the address-aliasing report: a security check meant to bind "the party that is supposed to trigger the withdrawal" (the aggregator, proven via ECDSA signature recovery) to "the party that actually can trigger it" is applied inconsistently across equivalent code paths, so a second method reaches the privileged operator-signing logic without the intended attribution check.

### Impact Explanation
If `internal_withdraw` is reachable on the operator's gRPC surface the same way `withdraw` is, any caller who can supply a valid `input_signature`/`input_outpoint`/`output_script_pubkey`/`output_amount` for a real withdrawal can obtain an operator-signed payout transaction without proving the request was routed through the aggregator — the exact authorization boundary `withdraw` was built to enforce. This is an unauthenticated state-changing/signing call, matching the "unauthenticated state-changing or broadcasting call" High-impact category.

### Likelihood Explanation
Likelihood depends entirely on whether `internal_withdraw` is reachable by anything other than the aggregator over the deployed transport (e.g., if operator/aggregator gRPC communication additionally relies on network-level or mTLS restriction outside this repository's application logic). This repository's application-level code does not gate `internal_withdraw` the way it gates `internal_finalized_payout` or the way `withdraw` gates itself, so purely from the code in `core/src/rpc/operator.rs`, the check is missing on one of two functionally equivalent entry points.

### Recommendation
Apply the same `aggregator_verification_address` / `verification_signature` check present in `withdraw` to `internal_withdraw`, or remove/guard `internal_withdraw` behind the same test-only restriction used for `internal_finalized_payout`.

### Proof of Concept
1. Configure `aggregator_verification_address` on the operator (the documented configuration intended to restrict payout triggering to the aggregator).
2. As an unprivileged caller with a valid withdrawal's `input_signature`/`input_outpoint`/`output_script_pubkey`/`output_amount` (data that is public/derivable from the withdrawal on Citrea), call `ClementineOperator::internal_withdraw` instead of `withdraw`.
3. Observe that `internal_withdraw` (core/src/rpc/operator.rs:168-190) skips the `address_from_sig != address_in_config` check performed in `withdraw` (core/src/rpc/operator.rs:209-238) and returns a valid `RawSignedTx` payout, despite no proof the request came from the aggregator.

                input_outpoint,

            )
            .await?;

        Ok(Response::new(RawSignedTx::from(&payout_tx)))
    }
