Given the evidence gathered, the strongest and most defensible analog is a **TOCTOU integrity gap in Desktop's partial-commit ("select lines to commit") pipeline**, which mirrors the core defect in the report: a value (there, `encryptedOutputs`; here, the diff a user's line-selection indices refer to) is consumed later **without being cryptographically/structurally bound to the state it was derived from**, so it can silently diverge and cause the wrong content to be committed.

### Title
Stale line-selection indices are re-applied to a freshly re-fetched diff during partial commits, allowing silent commit of unintended content - ([File: app/src/lib/git/apply.ts])

### Summary
Desktop lets users stage individual lines/hunks of a file for commit. The UI records the user's choice as absolute line indices (`DiffSelection`) computed against the specific `ITextDiff` object that was rendered when the user made the selection. When the commit is actually created, `applyPatchToIndex` re-fetches a brand-new diff from disk/git rather than reusing the diff the user reviewed, and then reapplies the old index-based selection to the new hunk layout.

### Finding Description
The commit flow is: `createCommit` → `stageFiles` → `applyPatchToIndex` for any file with a partial selection. [1](#0-0) 

Inside `applyPatchToIndex`, the diff used to build the patch is fetched fresh at staging time, independent of whatever diff the user actually looked at in the UI: [2](#0-1) 

That fresh diff is then run through `formatPatch`, which decides what to keep/drop purely by testing `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` is a positional index into whatever hunk layout the *new* diff happens to have: [3](#0-2) 

The `DiffSelection` object itself carries no content hash or identity binding it to the specific diff it was derived from — it is a pure index/bitmask structure. The only mitigating logic that exists, `app-store.ts`'s selection refresh, merely prunes indices that no longer correspond to an "includeable" line; it does **not** verify that a surviving index still refers to the same line content the user selected: [4](#0-3) 

If the working-directory content for a file changes between the moment the user reviews/selects lines and the moment `stageFiles`/`applyPatchToIndex` runs (e.g., because a git `clean`/`smudge` filter or `git-lfs`-style content filter declared in a **tracked, attacker-controlled `.gitattributes`** rewrites the file's on-disk representation when git re-reads it, or because of any other process racing with the commit), the hunk boundaries in the newly fetched diff shift. The old `absoluteIndex`-based selection is then silently reinterpreted against the new hunks, so `formatPatch` can select/deselect completely different lines than the ones the user actually reviewed and approved — with no error, since `git apply --cached --unidiff-zero` will happily apply a structurally valid but semantically wrong patch.

### Impact Explanation
This breaks the fundamental invariant the report's finding also breaks: **the user's approval is not cryptographically/structurally tied to what actually gets persisted.** Here, the user could unknowingly commit and push content they never selected or reviewed — e.g., text they explicitly excluded gets included, or a partially-reviewed sensitive change is committed in full. Because this happens silently (no error dialog, `git apply` succeeds), the user has no signal that the commit doesn't match their reviewed selection, and could push corrupted/incomplete changes to a shared remote.

### Likelihood Explanation
The precondition — repository content changing between diff-render and stage time — is attacker-influenceable through a malicious/fetched repository's tracked `.gitattributes` filter declarations combined with any locally configured filter driver (a common real-world setup, e.g. `git-lfs`), or through ordinary races with other tooling. It does not require local/physical access, admin rights, prior malware, or leaked credentials — only that the victim open/interact with a hostile or compromised repository, which is squarely in scope. That said, it is a race-window bug rather than a deterministic single-request exploit, so reliability depends on timing/filter configuration.

### Recommendation
Bind the `DiffSelection` to the exact diff it was computed against (e.g., store a hash/identity of the diff text or the hunk header set alongside the selection) and validate that identity in `applyPatchToIndex`/`formatPatch` before applying the patch. If the diff has changed since the selection was made, fail loudly and force the user to re-review and re-select rather than silently remapping indices onto new hunk content — analogous to including `encryptedOutputs` in `callDataHash` so a changed value can never be silently substituted.

### Proof of Concept
1. Open a repository in Desktop and make a multi-hunk modification to a tracked file.
2. In the Changes view, select only specific lines within one hunk (not "select all") — this fixes a `DiffSelection` bound (in the user's mind) to the currently rendered diff.
3. Before clicking "Commit," cause the working file's on-disk content to shift lines (e.g., a background process appends/removes a line earlier in the file, or a `clean`/`smudge` filter configured via the repo's `.gitattributes` rewrites the file when git next reads it).
4. Click "Commit." `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff, and `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) reapplies the old absolute line indices to the new hunk layout.
5. Inspect the resulting commit: it contains different line content than what was highlighted/selected in the UI at commit time, with no warning shown to the user.
