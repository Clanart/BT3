### Title
Attacker-Controlled Solver Dict Override in Offer Settlement Merge Enables Forged CR-CAT/Offer Solve Context - (File: chia/wallet/trade_manager.py)

### Summary
`TradeManager.respond_to_offer` builds the final settlement spend by merging two `Solver` dictionaries with `Solver({**valid_spend_solver.info, **solver.info})`, where `solver` is the caller/taker-supplied `Solver` passed straight into `respond_to_offer` from the RPC/CLI (`take_offer`), and `valid_spend_solver` is the output of `check_for_final_modifications`, which is meant to hold trust-critical data (e.g. VC authorization proofs for CR-CATs, or DL graftroot resolution data). Because plain Python dict unpacking is used with the attacker-supplied dict applied *last*, any key names that coincide with the ones the wallet's own trusted logic populates (such as `vc_authorizations` consumed by `chia/wallet/vc_wallet/cr_outer_puzzle.py`'s `CROuterPuzzle.solve`) are silently overwritten by attacker data before being handed to `Offer.to_valid_spend`, which itself does another unguarded merge (`**solver.info`) into the per-coin solving context in `chia/wallet/trading/offer.py`. ### Finding Description
This is the closest reachable analog to the `lutils-merge` prototype-pollution bug class: an unvalidated, attacker-supplied key/value object (`solver.info`, structurally similar to a JS object passed to `merge()`) is spread into a dictionary that already contains security-relevant, wallet-computed values, with the untrusted side taking override precedence. In JS prototype pollution, the danger is that a merge() function fails to reject reserved keys (`__proto__`) so attacker input silently redefines properties used elsewhere in the app. Here, `Solver({**valid_spend_solver.info, **solver.info})` and `Solver({..., **solver.info})` in `offer.py` have the analogous flaw: there is no allow-list or rejection of reserved/security-sensitive keys (e.g. `vc_authorizations`, `coin`, `siblings`, `sibling_puzzles`, `sibling_solutions`, `proofs_of_inclusion`) before merging attacker data on top. Any outer-puzzle driver relying on `solver["<reserved-key>"]` (see `CROuterPuzzle.solve` at `chia/wallet/vc_wallet/cr_outer_puzzle.py:83-86`, `CATOuterPuzzle.solve` at `chia/wallet/cat_wallet/cat_outer_puzzle.py:83-100`, and `DataLayerWallet.finish_graftroot_solutions` at `chia/data_layer/data_layer_wallet.py:1137-1206`) can be tricked into consuming attacker-forged data instead of the wallet's own validated computation, because the taker's `solver` argument to `respond_to_offer` is fully attacker-controlled from the RPC (`take_offer`). ### Impact Explanation
If a counterparty crafts a `Solver` containing a `vc_authorizations` key when responding to/accepting a CR-CAT offer, the taker-supplied value silently wins over any `valid_spend_solver` value produced by `VCWallet.add_vc_authorization`, potentially letting the local wallet build a spend using attacker-chosen credential-restriction proofs/authorization data rather than data validated by the wallet's own VC/authorization flow — undermining the credential restriction (CR-CAT) settlement guarantee that is supposed to prevent unauthorized transfer of CR-CATs. This is a coin-identity/authorization integrity issue reachable purely through the offer-taking RPC path (`take_offer` → `respond_to_offer`), i.e., from a local/offer counterparty supplied value, not a privileged operator action.

### Likelihood Explanation
Medium likelihood: exploitation requires the wallet operator to accept an offer for a CR-CAT (or other Solver-consuming asset type) using a `Solver` argument they don't fully control/understand — a normal usage pattern for the `take_offer` RPC since callers are expected/allowed to pass a `solver` to satisfy dependency data. The override only affects the local wallet's own solve-context construction (not consensus directly), so severity is bounded to the local wallet's constructed spend, but no key allow-listing exists to prevent an attacker (e.g., an offer file crafted by a counterparty, or a malicious dApp/wallet-connect frontend) from smuggling override keys through the `solver` parameter.

### Recommendation
Do not blindly `{**trusted, **untrusted}` merge `Solver.info` dictionaries. Instead, explicitly allow-list which keys the caller-supplied `solver` may add/override (e.g. reject any key already present in `valid_spend_solver.info`, or maintain a fixed set of caller-overridable keys), and raise an error if the untrusted solver attempts to supply a reserved/security-relevant key such as `vc_authorizations`, `coin`, `parent_spend`, `siblings*`, or `proofs_of_inclusion`.

### Proof of Concept
1. Call the `take_offer` wallet RPC to accept a CR-CAT offer, passing `solver={"vc_authorizations": {"<coin_name_hex>": [<attacker chosen proof tuple>]}}` in the request body alongside the offer.
2. `WalletRpcApi` → `TradeManager.respond_to_offer` computes `valid_spend_solver` via `check_for_final_modifications` → `VCWallet.add_vc_authorization`, which is expected to populate the legitimate `vc_authorizations`.
3. At `chia/wallet/trade_manager.py:889-891`, `Solver({**valid_spend_solver.info, **solver.info})` overwrites the wallet-computed `vc_authorizations` with the attacker-controlled value from step 1.
4. `Offer.to_valid_spend` merges this solver again (`**solver.info` in `chia/wallet/trading/offer.py:578`) into the per-coin solve context, and `CROuterPuzzle.solve` (`chia/wallet/vc_wallet/cr_outer_puzzle.py:83-86`) reads `solver["vc_authorizations"][coin_name]`, consuming the attacker-forged tuple instead of the wallet-validated one.
