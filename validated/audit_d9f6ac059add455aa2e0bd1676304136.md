### Title
Untrusted `ReceivedOutput` deserialization accepts unsatisfiable outputs as wallet funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without proving that the output script corresponds to the wallet’s base key plus that offset, or even that it is a spendable Taproot output. [1](#0-0)  This is an untrusted-object injection analogous to accepting an uploaded file without validating that it conforms to the object’s security invariant.

### Finding Description
A genuine `ReceivedOutput` is created by `Scanner::scan_transaction` only after the transaction output’s `script_pubkey` matches a registered P2TR script and the associated offset is recovered from `self.scripts`. [2](#0-1)  That script/offset relationship is the critical ownership invariant: the output is spendable only because its Taproot key equals the wallet key plus the registered scalar offset. [3](#0-2) 

`ReceivedOutput::read` bypasses that scanner-derived invariant. It deserializes `offset` with `Secp256k1::read_F`, then independently deserializes any consensus-valid `TxOut` and `OutPoint`, returning `Ok(ReceivedOutput { offset, output, outpoint })` with no P2TR or key-relation check. [1](#0-0) 

The spending path consumes the untrusted fields as authoritative: `SignableTransaction::new` reads each input’s value and outpoint and preserves each supplied offset for signing, without checking that `input.output.script_pubkey` belongs to the threshold wallet. [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who can supply serialized `ReceivedOutput` bytes can cause the wallet to report an attacker-controlled or permanently unspendable output as received funds. For example, a `TxOut` containing an OP_RETURN script decodes successfully even though no signature can spend it. If the value and outpoint refer to an existing chain output—or are otherwise trusted by the surrounding accounting flow—the resulting balance can be treated as available even though the threshold wallet cannot authorize its spend.

This meets the “funds reported received that are not spendable” impact directly. It can also poison downstream input selection: `SignableTransaction::new` counts the forged output’s value toward spendable inputs and builds a transaction around the supplied outpoint and offset. [4](#0-3)  The result is false balance reporting and failed/invalid spends; severity is High where persisted scanner or wallet state can be supplied by an untrusted party.

### Likelihood Explanation
Exploitation does not require a validator, peer consensus failure, leaked key, malformed curve point, or invalid scalar. The scalar only needs a canonical field encoding, and the remaining objects only need consensus-valid encodings accepted by `TxOut::consensus_decode` and `OutPoint::consensus_decode`. [6](#0-5) 

The attacker needs a reachable path that feeds controlled bytes to `ReceivedOutput::read`. The scanner itself creates safe objects, but the separate public deserializer reconstructs them without re-establishing the scanner’s ownership check, making serialized storage/import/sync boundaries the dangerous surface.

### Recommendation
Do not treat deserialized `ReceivedOutput` values as trusted wallet outputs. Either:

1. Make `ReceivedOutput::read` private to trusted serialization boundaries, or rename/document it as lossy persistence decoding rather than ownership validation.
2. Preferably, revalidate every decoded output against the scanner: check that `output.script_pubkey` is the exact P2TR script generated from `base_key + offset * G` and that the outpoint/value match a confirmed chain output.
3. Reject any decoded `TxOut` whose script is absent from the scanner’s registered script map before inserting it into wallet state or passing it to `SignableTransaction::new`.
4. Consider storing the scanner’s expected script alongside the output and comparing it during `read`, rather than serializing an arbitrary `TxOut`.

### Proof of Concept
```rust
use bitcoin::{
  Amount, OutPoint, ScriptBuf, TxOut,
  consensus::Encodable,
};
use bitcoin_serai::wallet::ReceivedOutput;
use k256::Scalar;
use std::io::Write;

let mut bytes = Vec::new();

// Canonical scalar offset.
bytes.extend_from_slice(&Scalar::ONE.to_bytes());

// Consensus-valid TxOut, but provably unspendable: OP_RETURN.
TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_op_return(&[]),
}
.consensus_encode(&mut bytes)
.unwrap();

// Consensus-valid outpoint. The deserializer does not verify that it
// exists or that its script belongs to this wallet/offset.
OutPoint::default().consensus_encode(&mut bytes).unwrap();

// This succeeds despite the output being unspendable and unrelated to
// any Scanner-registered offset.
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 100_000);
assert!(forged.output().script_pubkey.is_op_return());
```

`ReceivedOutput::read` accepts this forged object because its implementation ends immediately after decoding the three fields, with no check against `Scanner::scripts`, no P2TR assertion, and no proof that `offset` authorizes spending the `TxOut`. [6](#0-5)
