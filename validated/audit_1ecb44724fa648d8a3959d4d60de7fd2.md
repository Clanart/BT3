## Analysis

The reported bug class—reward-rate emissions accruing while `totalSupply == 0`, causing that period's rewards to be permanently lost because they are never re-queued on the next reward notification—has a direct analog in `wombat/WomUp.sol`.

Unlike the other reward-distribution contracts in this codebase (`BaseRewardPool`, `BaseRewardPoolV2`, `vlMGPBaseRewarder`, `mWOMSVBaseRewarder`, `DelegateVoteRewardPool`), which all explicitly detect `totalStaked() == 0` and push the incoming reward into a `queuedRewards` bucket to be rolled into `rewardPerTokenStored` on the next non-zero-supply provisioning [1](#0-0) , `WomUp.sol` uses the exact vulnerable Synthetix-style `StakingRewards` pattern with no such safeguard.

### Root cause

`rewardPerToken()` simply returns the unchanged `rewardPerTokenStored` whenever `totalSupply() == 0`, silently discarding the elapsed-time reward for that period instead of accounting for it: [2](#0-1) 

`initializeRewards()` sets `rewardRate` once as `rewardsAvailable / duration` and starts `lastUpdateTime`/`periodFinish` immediately, guarded so it can never be called again once `rewardRate > 0`: [3](#0-2) 

Since `stake()` is the only way `_totalSupply` becomes non-zero, and it is a normal unprivileged entrypoint, any gap between `initializeRewards()` and the first `stake()` call causes `rewardRate * gap` worth of MGP reward to never enter `rewardPerTokenStored`. There is no `queuedRewards` mechanism and no second `notifyRewardAmount`-equivalent call to recover it — `rescueReward()` is only usable *before* `rewardRate` is set (`if (block.timestamp >= startTime || rewardRate > 0) revert AlreadyStarted();`) [4](#0-3) . Once `rewardRate` is initialized, the MGP corresponding to any zero-supply window is permanently stuck in the contract with no owner or user recovery path.

### Title
Rewards accrued while `totalSupply == 0` in `WomUp` are permanently lost and never rolled over - (File: `wombat/WomUp.sol`)

### Summary
`WomUp.initializeRewards()` starts a fixed 7-day reward-rate emission schedule for MGP rewards distributed to WOM stakers, but `rewardPerToken()` does not account for the interval where `_totalSupply == 0`. Any elapsed time with zero total stake causes a portion of the pre-funded MGP reward to be permanently unclaimable, because there is no queued-reward carry-forward like the one implemented in `BaseRewardPool`/`vlMGPBaseRewarder` elsewhere in the repo.

### Finding Description
`rewardPerToken()` returns `rewardPerTokenStored` unchanged when `totalSupply() == 0` [2](#0-1) . Because `lastUpdateTime` is set to `block.timestamp` at `initializeRewards()` time (or at each subsequent `updateReward` call) regardless of whether anyone is staked [5](#0-4) [3](#0-2) , the reward that would have accrued during any zero-stake window (`rewardRate * elapsed`) is dropped from the accounting entirely once a user eventually calls `stake()`. There is exactly one call to `initializeRewards()` allowed per contract lifetime (`if(rewardRate > 0) revert MustZero();`), so this lost reward can never be re-queued for distribution — unlike the codebase's other reward pools, which explicitly capture this case via `rewardInfo.queuedRewards`.

### Impact Explanation
The MGP tokens funding the reward schedule are transferred into the `WomUp` contract prior to `initializeRewards()`. Any portion of the schedule that elapses before the first ordinary user calls `stake()` (an unprivileged, permissionless action) results in that MGP becoming permanently unrecoverable and unclaimable by anyone — `rescueReward()` can no longer be invoked once `rewardRate > 0`. This is a permanent freezing/loss of yield that was meant for stakers.

### Likelihood Explanation
`initializeRewards()` is a normal, expected one-time admin setup action (not a malicious-admin scenario), and any real-world delay between funding/initializing the schedule and the first user's `stake()` transaction — even a short one — triggers the loss. Given `duration = 7 days`, even modest gaps (e.g., due to deployment/rollout timing, or brief post-withdrawal periods where `_totalSupply` returns to 0 before new stakers arrive) directly and deterministically cause partial, permanent reward loss.

### Recommendation
Mirror the pattern already used in `BaseRewardPool`/`vlMGPBaseRewarder`: when `totalSupply() == 0`, instead of silently dropping the reward-per-second accrual, either (a) reset `lastUpdateTime` only up to the point where supply was last non-zero and track the pending amount in a `queuedRewards`-like variable to fold into the next `rewardPerTokenStored` update, or (b) extend `periodFinish` by the zero-supply duration so undistributed rewards remain claimable once staking resumes.

### Proof of Concept
1. Owner funds `WomUp` with MGP and calls `initializeRewards()`, setting `rewardRate = balance/7 days`, `lastUpdateTime = block.timestamp`, `periodFinish = block.timestamp + 7 days`.
2. No user calls `stake()` for `N` seconds (e.g., due to deployment lag or all existing stakers withdrawing so `_totalSupply` returns to 0).
3. A user then calls `stake()`, entering `updateReward(msg.sender)`, which calls `rewardPerToken()`; since `totalSupply() == 0` was true for the preceding `N` seconds, `rewardPerTokenStored` is left unchanged and `lastUpdateTime` jumps to the current timestamp.
4. The `rewardRate * N` MGP that should have accrued during that gap is now unaccounted for in `rewardPerTokenStored` and can never be distributed to any staker, nor rescued by the owner (`rescueReward()` reverts once `rewardRate > 0`), permanently locking that portion of MGP in the contract.

    function initializeRewards() external onlyOwner returns (bool) {
        if(rewardRate > 0) revert MustZero();

        uint256 rewardsAvailable = IERC20(mgp).balanceOf(address(this));
        if(rewardsAvailable == 0) revert MustNotZero();

        rewardRate = rewardsAvailable / (duration);

        lastUpdateTime = block.timestamp;
        periodFinish = block.timestamp + (duration);

        emit RewardAdded(rewardsAvailable);

        return true;
    }
