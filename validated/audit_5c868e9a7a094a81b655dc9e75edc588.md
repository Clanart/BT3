## Analysis

Tracing the reward/refund logic in `evm/src/core/EvmHost.sol`, I found an asymmetry in how GET request fee-escrow (`_requestCommitments[commitment]`) is cleared between the two terminal outcomes of a GET request: response delivery vs. timeout. [1](#0-0) [2](#0-1) 

### Title
Double payout of escrowed GET-request fee via response delivery followed by timeout refund - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming(GetResponse, relayer)` pays the escrowed fee in `_requestCommitments[commitment].fee` to the delivering relayer but never clears `_requestCommitments[commitment]`. `EvmHost.dispatchTimeOut(GetRequestTimeout, meta, commitment)` explicitly treats deletion of `_requestCommitments[commitment]` as "replay protection" and, on a successful `onGetTimeout` callback, refunds `meta.fee` to `meta.sender`. Because the response path never deletes the entry, the same escrowed fee can be paid out twice for the same GET request commitment: once to the relayer on response, and again to the original payer on a subsequently-submitted timeout.

### Finding Description
`dispatchIncoming(GetResponse memory response, address relayer)` is restricted to the handler and reads `_requestCommitments[commitment].fee`, transferring it to `relayer` — but the function only deletes `_responseReceipts[commitment]` on failure, and never touches `_requestCommitments[commitment]` on success: [3](#0-2) 

By contrast, `dispatchTimeOut(GetRequestTimeout ...)` labels the deletion of `_requestCommitments[commitment]` explicitly as "replay protection," and on a successful timeout callback refunds `meta.fee` to `meta.sender`: [4](#0-3) 

`HandlerV2.handleGetRequestTimeouts` (called permissionlessly by anyone submitting a timeout proof) gates on the state commitment/challenge period and the timed-out timestamp, but the presence check for "known request" is `meta.sender == address(0)` against `_requestCommitments` — which, because the response path never clears that mapping, remains satisfied even after a valid `GetResponse` has already been delivered and paid out: [5](#0-4) 

The duplicate-delivery guard used for POST requests/GET responses (`requestReceipts`/`responseReceipts` checks in `HandlerV2.handlePostRequests` / `handleGetResponses`) has no equivalent counterpart preventing a timeout from firing on a GET request whose response was already delivered, because `_requestCommitments` — the storage slot that both paths rely on as the "is this request still live" gate — is only ever cleared by the timeout path itself, not by the response path.

### Impact Explanation
This is a direct fund-loss/double-payout bug in the ISMP host's fee-escrow accounting. For a single fee amount escrowed at GET-request dispatch time, the host can be made to pay it out twice: once to the relayer via `dispatchIncoming(GetResponse)` and again to the payer via `dispatchTimeOut(GetRequestTimeout)`. Repeated across many requests this drains the fee token balance held by `EvmHost`, effectively minting free money for either the colluding relayer/payer pair or the payer alone at the relayer's/protocol's expense — the same "no verification of correct one-time settlement" class of bug the external report describes (an actor extracting value the protocol never intended to pay).

### Likelihood Explanation
Both `dispatchIncoming(GetResponse)` and `dispatchTimeOut(GetRequestTimeout)` are called by the permissionless `IHandler` (`handleGetResponses` / `handleGetRequestTimeouts`), restricted only to `restrict(_hostParams.handler)` at the host level, meaning any user who can construct a valid state/consensus proof for either path (a normal, permissionless relayer action, not requiring any privileged role) can trigger both legs sequentially on the same commitment once the request's `timeout_timestamp` has elapsed relative to the state machine commitment timestamp — a condition that is trivially reachable if the relayer waits, or if the response is delivered late relative to the timeout window while `_requestCommitments` is still populated.

### Recommendation
Delete (or mark settled) `_requestCommitments[commitment]` inside `dispatchIncoming(GetResponse, ...)` immediately after it is used to compute the relayer fee (mirroring the "replay protection" pattern already used in the timeout paths), so that a subsequent `dispatchTimeOut(GetRequestTimeout, ...)` for the same commitment fails the `meta.sender == address(0)` "known request" check in `handleGetRequestTimeouts` and cannot pay out a second time.

### Proof of Concept
1. Dispatch a GET request from the source `EvmHost`, escrowing `fee` under `_requestCommitments[commitment]`.
2. Before or shortly after the request's `timeout_timestamp`, submit a valid `GetResponseMessage` via `handleGetResponses` → `EvmHost.dispatchIncoming(GetResponse, relayer)`. This pays `fee` to `relayer` from `_requestCommitments[commitment].fee`, but leaves `_requestCommitments[commitment]` populated.
3. Submit a `GetTimeoutMessage` for the same commitment via `handleGetRequestTimeouts` → `EvmHost.dispatchTimeOut(GetRequestTimeout, meta, commitment)`. Since `_requestCommitments[commitment]` was never cleared in step 2, the `meta.sender == address(0)` known-request check still passes; if `onGetTimeout` succeeds on the source module, `meta.fee` is refunded a second time to `meta.sender`.
4. Net result: the same escrowed `fee` has been paid out twice from the host's fee-token balance for a single GET request.

Note: I was unable to view the full body of `handleGetRequestTimeouts` beyond the header shown (lines 293–300 in the retrieved snippet) to confirm there is no additional, unseen check elsewhere in that loop that independently blocks this sequence; this is flagged as the one piece of the flow I could not fully verify with the available tool budget.

```text
    /**
     * @dev Dispatch an incoming GET response to source module
     * @param response - get response
     */
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

```text
    /**
     * @dev Dispatch an incoming GET timeout to the source module.
     * @notice Does not refund any protocol fees.
     * @param timeout - timed-out get request bundled with the relayer that submitted the timeout proof
     * @param meta - fee metadata for the original request
     * @param commitment - request commitment
     */
    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```

```text
    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
```
