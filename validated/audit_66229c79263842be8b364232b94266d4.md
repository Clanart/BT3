### Title
Division-by-zero panic in `consolidatedNode.Split` during Prague/flex reward distribution when proposer has zero CN and CL staking - (File: kaiax/staking/staking_info.go)

### Summary
`consolidatedNode.Split` divides by `totalAmount = StakingAmount + CLStakingInfo.CLStakingAmount` without checking whether that sum is zero, analogous to the ERC-4626 `_convertToShares` division-by-zero identified in the referenced report. This function is invoked unconditionally for the block proposer's consolidated node whenever it has a non-nil `CLStakingInfo`, regardless of whether the proposer's staking amounts meet minimum-stake eligibility.

### Finding Description
`consolidatedNode.Split` performs: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount) // divides by totalAmount, no zero-check
	...
}
```

`Split` is called from `specWithProposerAndFundsFlex`/`specWithProposerAndFunds` for the block proposer's `consolidatedNode`, found by matching `cn.RewardAddr == config.Rewardbase`, with only a nil-check on `cn.CLStakingInfo`: [2](#0-1) 

Unlike `assignStakingRewards`/`assignStakingRewardsFlex`, which only call `Split` for stakers whose `StakingAmount >= minStake` (a nonzero governance parameter, guaranteeing `totalAmount > 0`), the proposer path in `specWithProposerAndFunds(Flex)` performs no such eligibility check before calling `Split`. `consolidateNodes()` attaches a `CLStakingInfo` to any node found via `nToR` mapping regardless of its `StakingAmount`: [3](#0-2) 

If the current block proposer's consolidated node has `StakingAmount == 0` (e.g., it does not hold minimum CN stake, or is a non-committee CN transiently selected due to policy/edge behavior) and its associated consensus-liquidity pool also currently has `CLStakingAmount == 0` (e.g., all CL depositors withdrew, or CL pool was just registered with no deposits yet), then `totalAmount = 0 + 0 = 0`. `big.Int.Div` with a zero divisor **panics** in Go (unlike Solidity's revert, this is a hard runtime panic), unlike EIP-4626's mandated non-reverting behavior for `maxRedeem`.

### Impact Explanation
A panic inside `getDeferredRewardFullKore`/`getDeferredRewardFullFlex` (called from `GetDeferredReward`, used during `FinalizeState`/block reward computation and `kaia_getReward` RPC) crashes the node process. If this occurs during block finalization on all honest nodes deterministically (same StakingInfo/CLStakingInfo state), it would halt block production network-wide — a chain liveness failure. If reachable only via the `kaia_getReward`/`kaia_getRewardsAccumulated` public RPC, an unprivileged RPC caller could crash any full/RPC node by querying reward info for a block whose proposer meets the zero/zero condition, which is a public-RPC crafted request achieving denial of service on a public system component in-scope of this class of finding (staking/reward distribution, public RPC).

### Likelihood Explanation
Requires a specific but not implausible state: the block proposer of a given block has `StakingAmount == 0` and has a `CLStakingInfo` entry with `CLStakingAmount == 0` for the same block. This state is reachable through legitimate use of the consensus-liquidity/staking system without any privileged action — e.g., all liquidity providers withdraw from a CL pool right when its associated CN also has zero CNStaking, or a newly registered CL pool has 0 deposits. Since `assignStakingRewards`'s eligibility-gated call path (`StakingAmount >= minStake`) already demonstrates the developers were aware of this same division and guarded it there, the ungated call in `specWithProposerAndFunds(Flex)` for the proposer's own share is an overlooked asymmetric case — directly analogous to the missing `_totalAssets == 0` guard in the referenced bug.

### Recommendation
Add a zero-check in `consolidatedNode.Split` before dividing, mirroring how ERC-4626's fix handled the `_totalAssets == 0` special case:
```go
if totalAmount.Sign() == 0 {
    return big.NewInt(0), big.NewInt(0) // or return (amount, 0) as before, depending on intended semantics
}
```
This guarantees the reward/getter computation (and any RPC endpoint exposing it) never panics regardless of the proposer's CN/CL staking state, consistent with the non-reverting expectations enforced elsewhere in the codebase (e.g., `assignStakingRewards`'s eligibility gate).

### Proof of Concept
Conceptual reproduction (cannot execute in this environment):
1. Configure a Prague-enabled chain where `istanbul.policy == 2`.
2. Register a validator `V` in AddressBook with `StakingAmount = 0` (below `minStake`), so `V` is a `consolidatedNode` with `StakingAmount = 0`.
3. Register a `CLStakingInfo` for `V`'s `CLNodeId` via the CL registry, with `CLStakingAmount = 0` (e.g., pool created but currently has 0 total deposits after all withdrawals).
4. Have `V` become the block proposer for a block (`config.Rewardbase == V`).
5. Call `GetDeferredReward`/`GetBlockReward` (or the `kaia_getReward` RPC) for that block. In `specWithProposerAndFundsFlex`/`specWithProposerAndFunds`, the code finds `cn` with `cn.RewardAddr == V` and `cn.CLStakingInfo != nil`, then calls `cn.Split(proposer)`, computing `totalAmount = big.NewInt(0).Add(big.NewInt(0), big.NewInt(0)) = 0`, and `clAmount.Div(clAmount, totalAmount)` panics with "division by zero".

This mirrors the referenced report's proof-of-concept pattern (deposit → make `totalAssets` reach 0 → call the vulnerable view function → revert), here reproduced as: register CN with 0 stake + CL pool with 0 stake → become proposer → query deferred reward → panic.
