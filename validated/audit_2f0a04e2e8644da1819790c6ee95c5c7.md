### Title
Silent remote-URL rewrite to attacker-controlled host via unvalidated GitHub API `clone_url` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` automatically rewrites a repository's `origin` remote URL using the `clone_url` field returned by a GitHub/GHES API response, but it never verifies that the new URL still points to the same host/endpoint that the account is associated with. It only checks that the URL *protocol* (`https`/`ssh`) is unchanged, that the previous remote exactly matched the last cached `cloneURL`, and that the new URL differs from the current remote. This is directly analogous to the PoolTogether report's pattern of trusting an external, "approximately correct" value without an exact/complete validation step, allowing it to silently produce an incorrect (here, attacker-controlled) result.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository()` [1](#0-0)  every time Desktop refreshes GitHub metadata for a repository (e.g. on account change, periodic repository refresh). It calls `api.fetchRepository(owner, name)` [2](#0-1)  against the account's configured `endpoint`, and passes the resulting `apiRepo` straight into `updateRemoteUrl`.

Inside `updateRemoteUrl`, the validation logic is: [3](#0-2) 

The only checks performed before calling `gitStore.setRemoteURL(...)` are:
1. `protocolsMatch` — compares `URL.parse(remoteUrl).protocol === URL.parse(updatedRemoteUrl).protocol`, i.e. both are `https:` or both are unparsable SSH strings.
2. `remoteUrlUnchanged` — the *current* remote must still equal the last known `gitHubRepository.cloneURL` (via `urlMatchesRemote`, which itself only compares hostname/owner/name parsed from the URL, not against the account endpoint).
3. `!urlsMatch` — the new URL differs from the current one.

Nowhere is the new `updatedRemoteUrl`'s **hostname** checked against the account's actual GitHub/GHES endpoint (`account.endpoint`). If the API response — obtained over the network from the configured endpoint — returns a `clone_url` pointing to a completely different host but with the same protocol (e.g., `https://attacker.example/owner/name.git`), the guard conditions above are still satisfiable, and Desktop will call `gitStore.setRemoteURL('origin', updatedRemoteUrl)` [4](#0-3) , silently repointing the user's `origin` remote.

The existing unit tests confirm this exact behavior is accepted as "working as intended" — a `clone_url` change is applied without any host-pinning check: [5](#0-4)  shows the remote URL is updated to `https://github.com/my-user/my-updated-repo` purely because the API says so, and the only negative test cases relate to protocol mismatch or the previous remote already having diverged from the cached clone URL — not to the new URL pointing to an unexpected host: [6](#0-5) .

This differs from other remote/URL-handling code paths in the same codebase which are host-aware, e.g. `matchGitHubRepository` explicitly compares parsed hostnames against the account's endpoint [7](#0-6) , and `sanitizeCloneName`/clone path checks defend against traversal [8](#0-7) . `updateRemoteUrl`, by contrast, has no equivalent host-pinning guard for the *destination* of an automatic remote rewrite.

### Impact Explanation
`git()` operations (`fetch`, `push`, `pull`) resolve credentials and proxy behavior based on `remote.url`, via `envForRemoteOperation(remote.url)` [9](#0-8) . If `origin` is silently repointed to an attacker-controlled host with the same protocol, subsequent `git push` operations issued by the user through the Desktop UI would push code (potentially proprietary/private) to the attacker's server, and subsequent `git fetch`/`pull` would pull attacker-supplied content into the user's working copy — all without any visible warning, since the UI reads the remote URL from the git store and shows no diff/prompt for this automated change. Depending on the credential helper in use, this could also result in credentials or tokens being sent toward the attacker-controlled host during authentication attempts. This satisfies the "silent corruption of what the user commits or pushes" and "credential/token exfiltration" impact categories.

### Likelihood Explanation
The attacker precondition is a compromised/malicious response from the endpoint that the account authenticates against — e.g., a GitHub Enterprise Server instance under attacker influence, a MITM/rogue proxy sitting between Desktop and the API endpoint, or a compromised reverse proxy in front of self-hosted GHES — which matches the "attacker controls ... a git remote/proxy response" scope of this task. No local access, admin rights, or user action beyond normal use of Desktop (which periodically refreshes GitHub repository metadata) is required, satisfying the "unprivileged" bar. The condition `remoteUrlUnchanged` requires the current remote to match the last cached `cloneURL` exactly, which is the common case for repositories that haven't been manually re-pointed by the user, so likelihood of triggering the vulnerable path in a normal Desktop session is realistic.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that the new `updatedRemoteUrl`'s hostname matches the hostname of the associated `account.endpoint` (the same check `matchGitHubRepository` already performs), not merely that the protocol string matches. Reject/ignore API-provided `clone_url` values whose host differs from the expected GitHub/GHES host, and surface a warning to the user rather than silently rewriting `origin`.

### Proof of Concept
1. User has an account configured against `https://ghe.corp.example` and a repository whose `origin` remote and cached `gitHubRepository.cloneURL` both equal `https://ghe.corp.example/owner/repo.git`.
2. An attacker who can influence the network path/response from that endpoint (compromised proxy, malicious GHES admin, DNS/MITM) causes `api.fetchRepository(owner, name)` to return `clone_url: "https://attacker.example/owner/repo.git"`.
3. `repositoryWithRefreshedGitHubRepository` runs (e.g., triggered by periodic refresh or account-change refresh) and calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)`.
4. `protocolsMatch` is true (both `https:`), `remoteUrlUnchanged` is true (cached `cloneURL` equals current remote), `urlsMatch` is false (different owner/host) → `gitStore.setRemoteURL('origin', 'https://attacker.example/owner/repo.git')` executes silently.
5. The next `git push`/`fetch` from the Desktop UI targets `attacker.example` without any user-visible warning.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
