Based on the code I found, there's a legitimate analog in how GitHub Desktop validates deep-link branch names using a **stateful global regex object shared across two different validation call sites**.

### Title
Deep-link branch validation bypass via shared stateful global RegExp (`invalidCharacterRegex`) enables git ref/argument injection - ([File: app/src/lib/sanitize-ref-name.ts])

### Summary
`testForInvalidChars()` in [1](#0-0)  is used by `parseAppURL()` in [2](#0-1)  to gate whether an attacker-supplied `branch` query-string value from a `x-github-client://openrepo` deep link is safe to pass through to `openBranchNameFromUrl` in the dispatcher. The regex used, `invalidCharacterRegex`, is declared with the global (`g`) flag and is a module-level singleton object shared between `sanitizedRefName()` (uses `.replace()`) and `testForInvalidChars()` (uses `.test()`) [1](#0-0) . Because `RegExp.prototype.test` with a global-flagged regex mutates and reuses `lastIndex` across calls (only resetting to `0` on a failed match), a prior invocation that matched near the end of one input string leaves `lastIndex` pointed past the length of a subsequent, shorter input string. The next `.test()` call on that shorter string then immediately fails to find any match (since `lastIndex` exceeds the string length), returns `false`, and the caller treats the branch name as "clean" even though it actually contains disallowed control characters, `~^:?*[\|"<>` or other unsafe sequences.

### Finding Description
The broken invariant is: *"`testForInvalidChars(branch)` must reliably report `true` whenever `branch` contains any character matched by `invalidCharacterRegex`."* This invariant silently breaks whenever the regex's `lastIndex` was left in a non-zero state by an earlier successful match on a longer string, because the same regex *object* (not a fresh instance) is reused across invocations [3](#0-2) . `parseAppURL` relies exactly on this check before constructing an `open-repository-from-url` action carrying the raw branch string [4](#0-3) :

```
if (branch != null && testForInvalidChars(branch)) {
  return unknown
}
```

If `testForInvalidChars` produces a false negative, the unsanitized branch string flows straight into the dispatcher's `openBranchNameFromUrl` handling reached from `openRepositoryFromUrl` [5](#0-4) , unlike the `filepath` parameter which is independently hardened with `isAbsolute()` and `resolveWithin()` checks [6](#0-5) . There is no equivalent secondary guard for `branch` downstream — the regex check is the only line of defense.

### Impact Explanation
An attacker who controls a web page (or chain of links) can trigger the OS-level `x-github-client://` protocol handler twice in quick succession — first with a long, crafted branch/pr value engineered to leave `invalidCharacterRegex.lastIndex` non-zero, then with a short malicious branch value containing unsafe characters (e.g., a leading `-` to smuggle a git CLI flag, or embedded control characters). The second value is treated as validated and passed into whatever git ref/checkout logic backs `openBranchNameFromUrl`, potentially resulting in git argument injection or ref confusion during automated checkout triggered purely by the user clicking a link — matching the "attacker controls ... a link or deep link the user clicks" impact category and resulting in silent corruption of the repository state Desktop operates on.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control the sequencing of two protocol-handler invocations (feasible via a web page issuing two `x-github-client://` navigations, or via `second-instance` handling on Windows/Linux which processes `argv` for `--protocol-launcher`), and requires crafting inputs that produce the specific `lastIndex` residue. This is a genuine, reproducible JavaScript regex statefulness bug rather than a hypothetical — `RegExp.prototype.test`'s behavior with the `g` flag is well defined and deterministic, so the bypass is reliably triggerable with the right two inputs.

### Recommendation
- Do not share a single stateful global-flagged `RegExp` instance across multiple validation call sites; either construct a fresh `RegExp` for each `.test()` call or strip the `g` flag from the instance used by `testForInvalidChars` (global flag is unnecessary for a boolean containment check).
- Add a defense-in-depth check on the `branch` value at the point of use in `openBranchNameFromUrl`/git invocation (mirroring the `resolveWithin` treatment given to `filepath`).

### Proof of Concept
```ts
import { testForInvalidChars } from '../../src/lib/sanitize-ref-name'

// First call: long string with an invalid char near the end advances lastIndex.
testForInvalidChars('a'.repeat(90) + '\x00') // returns true, but lastIndex is now > 0

// Second call: short malicious branch with an unsafe leading '-' or control char
// at an EARLIER position than the stale lastIndex is missed entirely because
// lastIndex (~91) exceeds the string length, causing an immediate non-match.
testForInvalidChars('-upload-pack=evil') // returns false (bypass)
```
Feeding the second value as the `branch` parameter of a `x-github-client://openrepo/...&branch=-upload-pack=evil` deep link immediately after a link containing the first payload demonstrates the bypass reaching `parseAppURL`'s guard in [7](#0-6) .

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
