## Title
Missing Result-Size Limiting in Full-Node RPC Coin-Query Endpoints Enables Resource-Exhaustion DoS - (File: `chia/full_node/coin_store.py`)

### Summary
The Liferay CVE describes a GraphQL endpoint that returns unbounded query results, letting a caller trigger disproportionate server-side work with a single request and exhaust resources. The chia full-node RPC service has an analogous bug class: several `CoinStore` query methods backing public full-node RPC endpoints execute unbounded SQL queries with no `LIMIT` clause and no caller-configurable/enforced cap, unlike sibling methods in the same file that were hardened with a `max_items` cap.

### Finding Description
`CoinStore.get_coin_records_by_puzzle_hash` and `CoinStore.get_coin_records_by_puzzle_hashes` build and execute a SQL `SELECT` with no `LIMIT` at all, materializing every matching row into a `set()` and returning the full list to the RPC caller: [1](#0-0) [2](#0-1) 

Likewise `get_coin_records_by_names` runs an unbounded query and returns every matching record: [3](#0-2) 

Contrast this with `get_coin_records_by_parent_ids`, which was explicitly capped with a `max_items` parameter and an SQL `LIMIT`, and `get_coin_states_by_puzzle_hashes`, which similarly enforces `max_items`: [4](#0-3) [5](#0-4) 

These unbounded methods are directly exposed as full-node RPC endpoints reachable by any local RPC caller (no size/limit validation is performed in the API layer either — it only validates presence of required fields and forwards the request straight to the store): [6](#0-5) [7](#0-6) 

These endpoints are registered in the route table without any pagination, limit, or rate-limiting wrapper: [8](#0-7) 

By comparison, the wallet-side `get_coin_records` RPC was hardened with explicit limits (`max_get_coin_records_limit`, `max_get_coin_records_filter_items`) that reject oversized requests: [9](#0-8) 

No equivalent limit exists for the full-node `get_coin_records_by_puzzle_hash(es)` / `get_coin_records_by_names` endpoints — a caller supplying a puzzle hash (or hint, via `get_coin_records_by_hint`, which also forwards into the unbounded `get_coin_records_by_names`) that matches a very large number of historical coin records (e.g. a heavily reused address, faucet, or high-throughput CAT/singleton puzzle) forces the full node to materialize and JSON-serialize the entire unbounded result set in a single request/response cycle.

### Impact Explanation
A single RPC call against `/get_coin_records_by_puzzle_hash`, `/get_coin_records_by_puzzle_hashes`, `/get_coin_records_by_names`, or `/get_coin_records_by_hint` targeting a puzzle hash/hint with a large historical coin count can force the node to scan and serialize potentially hundreds of thousands of rows with no cap, consuming significant CPU, memory, and I/O on the full node process. This matches the resource-exhaustion/DoS impact class of the reference CVE (CWE-400) and can degrade or stall the full node's transaction-processing capability for legitimate wallet/RPC callers sharing that node.

### Likelihood Explanation
The endpoints are part of the standard full-node RPC surface and require only local RPC access (the same trust boundary already accepted as in-scope per the analog rules — "local RPC caller"). No special privileges beyond standard RPC access are required, and any puzzle hash with a large coin history (easily achievable by an attacker reusing an address across many transactions, or targeting a well-known heavily-used puzzle hash) triggers the unbounded scan deterministically.

### Recommendation
Apply the same `max_items`/`LIMIT`-based capping already used in `get_coin_records_by_parent_ids` and `get_coin_states_by_puzzle_hashes` to `get_coin_records_by_puzzle_hash`, `get_coin_records_by_puzzle_hashes`, and `get_coin_records_by_names` in `chia/full_node/coin_store.py`, and surface a caller-facing limit/pagination parameter (mirroring `WalletRpcApi.max_get_coin_records_limit`) in the corresponding `FullNodeRpcApi` handlers so oversized requests are rejected or paginated rather than fully materialized.

### Proof of Concept
1. Start a full node and repeatedly reuse the same puzzle hash across many transactions (or pick an existing puzzle hash/hint known to have a very large number of historical coin records, e.g. via `get_coin_records_by_hint`).
2. Issue `POST /get_coin_records_by_puzzle_hash` with `include_spent_coins=true` and that puzzle hash.
3. Observe that `CoinStore.get_coin_records_by_puzzle_hash` executes an unbounded `SELECT ... WHERE puzzle_hash=?` (no `LIMIT`), materializes all matching rows into a Python `set`, and the RPC handler serializes every record to JSON in the response — with response size and processing cost scaling linearly and unboundedly with the number of historical coins for that puzzle hash, unlike the capped `get_coin_records_by_parent_ids`/`get_coin_states_by_puzzle_hashes` paths.

                    spent_index = uint32(0) if row[1] <= 0 else uint32(row[1])
                    coins.add(CoinRecord(coin, row[0], spent_index, row[2] != 0, row[6]))
                return list(coins)

    async def get_coin_records_by_puzzle_hash(self, request: dict[str, Any]) -> EndpointResult:
        """
        Retrieves the coins for a given puzzlehash, by default returns unspent coins.
        """
        if "puzzle_hash" not in request:
            raise RpcError.simple(RpcErrorCodes.PUZZLE_HASH_NOT_IN_REQUEST, "Puzzle hash not in request")
        kwargs: dict[str, Any] = {"include_spent_coins": False, "puzzle_hash": hexstr_to_bytes(request["puzzle_hash"])}
        if "start_height" in request:
            kwargs["start_height"] = uint32(request["start_height"])
        if "end_height" in request:
            kwargs["end_height"] = uint32(request["end_height"])

        if "include_spent_coins" in request:
            kwargs["include_spent_coins"] = request["include_spent_coins"]

        coin_records = await self.service.coin_store.get_coin_records_by_puzzle_hash(**kwargs)

        return {"coin_records": [coin_record_dict_backwards_compat(cr.to_json_dict()) for cr in coin_records]}

    async def get_coin_records_by_puzzle_hashes(self, request: dict[str, Any]) -> EndpointResult:
        """
        Retrieves the coins for a given puzzlehash, by default returns unspent coins.
        """
        if "puzzle_hashes" not in request:
            raise RpcError.simple(RpcErrorCodes.PUZZLE_HASHES_NOT_IN_REQUEST, "Puzzle hashes not in request")

            "puzzle_hashes": [hexstr_to_bytes(ph) for ph in request["puzzle_hashes"]],

        if "end_height" in request:

        if "include_spent_coins" in request:
            kwargs["include_spent_coins"] = request["include_spent_coins"]

        coin_records = await self.service.coin_store.get_coin_records_by_puzzle_hashes(**kwargs)

        return {"coin_records": [coin_record_dict_backwards_compat(cr.to_json_dict()) for cr in coin_records]}
