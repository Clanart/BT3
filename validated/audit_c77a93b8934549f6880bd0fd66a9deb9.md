## Analysis

I found a real analog to the "stale state used for a new calculation" bug class in `applyPatchToIndex()` (`app/src/lib/git/apply.ts`), which underlies `stageFiles()`/`_commitIncludedChanges()`.

### Title
Partial-commit line selection is applied against a freshly-fetched diff without re-validating that stored `DiffSelection` line indices still correspond to the same content - ([File: app/src/lib/git/apply.ts])

### Summary
When a user commits a file with only some lines selected (a "partial commit"), the app stores the user's choices as absolute line indices in a `DiffSelection` object attached to `WorkingDirectoryFileChange`, computed against whatever diff was loaded in the UI at selection time [1](#0-0) . At commit time, `applyPatchToIndex()` re-fetches a **new** diff of the file on disk via `getWorkingDirectoryDiff(repository, file)` [2](#0-1)  and then builds the patch by calling `file.selection.isSelected(absoluteIndex)` for each line of that **new** diff's hunks [3](#0-2) . The `selection` object itself, however, is unchanged since the moment the user made their selection - it has no knowledge of the new diff's hunk boundaries; it only maps raw integer line indices to a selected/unselected boolean.

### Finding Description
This is structurally the same class of bug as the ReserveLogic report: a value computed at time T0 (the line-index-to-selection mapping) is combined with fresh data computed at time T1 (the new diff/hunks), under the implicit assumption that nothing relevant changed between T0 and T1 — an assumption the code does not verify at the point of use.

There *is* a partial mitigation: `updateChangesWorkingDirectoryDiff()` in `app-store.ts` recomputes `selectableLines` and calls `withSelectableLines()` to drop selection state for lines that are no longer selectable whenever the working-directory diff is reloaded in the UI [4](#0-3) . But this reconciliation only runs when the diff is reloaded through the **UI's own refresh path** (`_selectWorkingDirectoryFiles` → `updateChangesWorkingDirectoryDiff`). It is not invoked from `applyPatchToIndex()`/`stageFiles()`/`createCommit()`. If the on-disk file changes (e.g., due to a `post-checkout`/background process, editor auto-format, or - relevant to the attacker-controlled-repo threat model - a file being externally touched by a symlinked working tree, a concurrent `git` operation, or content mutated by an untrusted script bundled in the repo and executed by the user before committing) *after* the UI last refreshed the diff but *before* the commit button is pressed, `applyPatchToIndex` will build a hunk from stale line indices against the new content without re-checking `selectableLines`.

Because `DiffSelection.isSelected()` operates purely on integer indices with no cross-check against hunk identity/content [5](#0-4) , an index that pointed at "line 42 = attacker-injected code" in the old diff can silently point at a *different, unrelated* line in the new diff (e.g., an unrelated context line becomes an addition, or vice versa) if hunk boundaries shift. `formatPatch()` then emits a syntactically valid patch reflecting the wrong set of lines, and `git apply --cached` stages it without complaint [6](#0-5) .

### Impact Explanation
This maps to the "silent corruption of what the user commits or pushes" impact category: a user could unknowingly commit and push content they never intended to include (or omit content they intended to include), based on a mismatch between the displayed diff and the diff actually staged. Because the corruption is silent - no error is thrown, and the UI has already moved past the stale render - the user has no obvious signal that the committed content differs from what they reviewed.

### Likelihood Explanation
Likelihood is constrained: it requires the working-directory file to change between the last UI diff refresh and the commit action, without the app performing a background refresh in between (Desktop typically refreshes fairly often, and most users commit shortly after reviewing). This narrows the practical window but does not eliminate it, particularly for larger repos/files where background refresh is throttled, or workflows where a repo-provided script (e.g., pre-commit-adjacent tooling, watch-mode formatters/linters) mutates the file after the user opens the diff but before they click "Commit." I could not confirm from the index whether `_commitIncludedChanges` (`app-store.ts`) performs a synchronous re-diff/re-validation of `selectableLines` immediately before calling `createCommit` — my search only found the reconciliation logic in the `updateChangesWorkingDirectoryDiff` UI-refresh path, not in the commit path itself.

### Recommendation
Before building the patch in `applyPatchToIndex`, re-derive `selectableLines` from the freshly-fetched diff and apply `withSelectableLines()` to the file's `DiffSelection` (mirroring what `updateChangesWorkingDirectoryDiff` already does), and abort/re-prompt the user if the reconciled selection differs meaningfully from what was last shown, rather than silently proceeding to stage whatever the reconciled selection computes to.

### Proof of Concept
Not independently executed against a live checkout; based on static code reading:
1. Open a modified file with multiple hunks in Desktop's Changes view; partially select some added lines (e.g., select only the addition in hunk 2), which stores a `DiffSelection` keyed by absolute line indices from the currently-displayed diff.
2. Without Desktop refreshing the working-directory diff again (e.g., is throttled or window not focused), externally modify the file so that hunk boundaries shift (add/remove lines earlier in the file), changing what content lives at the previously-selected indices.
3. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff [2](#0-1)  and calls `formatPatch` using the stale `DiffSelection` against the new hunks [3](#0-2) , producing a patch whose selected lines no longer correspond to what the user actually reviewed and approved in the UI.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
