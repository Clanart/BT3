### Title
Attacker-controlled `n`/`t` in `ThresholdKeys::read` triggers quadratic (O(t²)) Lagrange interpolation work and causes unauthenticated CPU-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts a fully attacker-controlled `u16` participant count `n` and threshold `t`, then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for each of `t` participants. Under the (attacker-selectable) `Interpolation::Lagrange` variant, each `interpolation_factor` call iterates over all `t` included participants, making `ThresholdKeys::new` O(t²) in field operations plus `t` field inversions and `t` point multiplications. With `t = n = 65535`, a single ~4 MB serialized blob forces ~4.3 billion field multiplications and 65535 field inversions — an algorithmic-complexity DoS directly analogous to the unbounded `p2c` iteration count in the SimpleJWT advisory.

### Finding Description
The deserialization path is:

- `ThresholdKeys::read` reads `t`, `n`, `i` as raw `u16`s with no sanity ceiling on `t`/`n` beyond `t <= n <= 65535`, reads `n` scalars and `n` points, then calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:591-631). [1](#0-0) 
- `ThresholdKeys::new` computes `group_key` by calling `interpolation.interpolation_factor(*i, &t)` for every participant in `1..=t` (crypto/dkg/src/lib.rs:376-378). [2](#0-1) 
- `Interpolation::Lagrange`'s `interpolation_factor` loops over the entire `included` slice (length `t`), performing field multiplications per element and one `denom.invert().unwrap()` per call (crypto/dkg/src/lib.rs:229-247). Total cost: O(t²) field ops + t inversions + t scalar-multiplies, all before any authentication or semantic validity check on the key material. [3](#0-2) 
- The attacker selects interpolation method byte `1` (Lagrange) to reach the quadratic path; `Constant` would be O(t) but is optional (crypto/dkg/src/lib.rs:604-616). [4](#0-3) 
- The same quadratic pattern reappears in `ThresholdKeys::view`, which calls `interpolation_factor` for each member of `included` (length up to `n`) (crypto/dkg/src/lib.rs:500-506), so a deserialized malicious `ThresholdKeys` also poisons subsequent `view` calls. [5](#0-4) 

Like the SimpleJWT flaw, the expensive computation (key "derivation" via interpolation) runs on unauthenticated input during deserialization; no proof of correctness of the verification shares is required to trigger it — `ThresholdKeys::new` only checks counts and participant bounds, never that the shares form a consistent polynomial.

### Impact Explanation
A single crafted input of `~n·(F::Repr + G::Repr) + O(1)` bytes (≈ 4 MB for ed25519/Ristretto-sized elements at `n = 65535`) forces ~t² ≈ 4.3·10⁹ field multiplications, 65535 field inversions, and 65535 variable-time scalar multiplications — orders of magnitude more CPU work than bytes supplied, exactly the amplification profile of the PBKDF2 `p2c` bug. Repeated submissions can exhaust CPU and block processing of legitimate traffic in any service that feeds untrusted bytes to `ThresholdKeys::read`. Additionally, `denom.invert().unwrap()` panics on duplicate `included` entries in `view`-adjacent flows, though `view` itself dedups; the primary impact is CPU exhaustion.

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization API intended for keys loaded from storage/messages; any deployment that reads threshold keys from data influenced by an unprivileged party (the threat model explicitly includes untrusted bytes fed to `ThresholdKeys::read`) reaches this path with a single message. No authentication, valid signature, or consistent key material is needed — the quadratic work happens inside `ThresholdKeys::new` before any verification. Maximum cost requires only setting `t = n = 0xFFFF` and choosing Lagrange interpolation, trivially within the format.

### Recommendation
- Enforce a sane upper bound on `n`/`t` in `ThresholdKeys::read` (and `ThresholdParams::new`), consistent with the protocol's actual maximum set size (e.g., `MAX_KEY_SHARES_PER_SET`-style limits used elsewhere), before performing interpolation.
- Alternatively/additionally, compute `group_key` via a single multiexp over precomputed Lagrange coefficients (compute all `t` denominators with a batch inversion / prefix-product trick), reducing cost to O(t) with one inversion.
- Consider deferring `group_key` derivation out of the deserialization path, or validating share consistency cheaply first.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::{ThresholdKeys, Participant};
use dalek_ff_group::{Ristretto, Scalar, EdwardsPoint};
use group::{GroupEncoding, ff::PrimeField};

fn main() -> io::Result<()> {
    let t: u16 = 0xFFFF; // 65535
    let n: u16 = 0xFFFF;

    let mut buf = vec![];
    // C::ID
    let id = <Ristretto as Ciphersuite>::ID;
    buf.extend((id.len() as u32).to_le_bytes());
    buf.extend(id);
    // t, n, i
    buf.extend(t.to_le_bytes());
    buf.extend(n.to_le_bytes());
    buf.extend(Participant::new(1).unwrap().to_bytes());
    // Interpolation::Lagrange
    buf.push(1);
    // secret_share
    buf.extend(Scalar::ONE.to_repr().as_ref());
    // n verification shares (any validly-encoded points)
    for _ in 0 .. n {
        buf.extend(EdwardsPoint::generator().to_bytes().as_ref());
    }

    // ~4 MB input -> ~4.3e9 field muls + 65535 inversions + 65535 scalar muls
    let _keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice())?;
    Ok(())
}
```

The call to `ThresholdKeys::new` inside `read` evaluates `interpolation_factor` 65535 times, each iterating over all 65535 participants — blocking the caller until completion, with no authentication or validity requirement on the supplied shares.
