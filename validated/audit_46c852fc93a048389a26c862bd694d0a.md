### Title
Stale cached FROST/MuSig preprocess seed reused across validator sets, enabling nonce reuse and secret key recovery - ([File: coordinator/src/tributary/signing_protocol.rs](blackvul/serai--002/coordinator/src/tributary/signing_protocol.rs))

### Summary
Analogous to CVE-2024-57951 — where CPU-hotplug state (`hres_active`, `cpu_base.online`, stale pointers) is not reset when a CPU transitions down partway and back to online — `SigningProtocol::preprocess_internal` in `coordinator/src/tributary/signing_protocol.rs` caches a FROST preprocess seed under a DB key that is never scoped to the tributary/genesis or validator set. When a new tributary (new genesis, new validator set) runs its first DKG-confirmation attempt, the stale seed from the *previous* set's confirmation is loaded, the identical nonce is regenerated deterministically, and it is used to sign a *different* `set_keys_message`. Two Schnorr-style shares over one nonce with different challenges leak the signing private key.

### Finding Description
`SigningProtocol::preprocess_internal` stores the preprocess seed in `CachedPreprocesses`, keyed solely by `self.context` [1](#0-0) . For `DkgConfirmer`, the context is `(b"DkgConfirmer", self.attempt)` — a static tag plus the attempt counter [2](#0-1) . Every other tributary DB table (`DataDb`, `AttemptDb`, `ReattemptDb`, `FatallySlashed`, …) is keyed by `genesis` precisely because the coordinator DB is shared across all tributaries [3](#0-2) ; `CachedPreprocesses` is the lone exception, carrying no genesis/session/set component.

If the cached key already exists, no fresh seed is drawn — the stored one is decrypted (XOR with a key derived from `context || self.key`) and fed to `AlgorithmSignMachine::from_cache` [4](#0-3) . `from_cache` rebuilds the machine via `seeded_preprocess`, which seeds `ChaCha20Rng` with the cache and regenerates the same nonces [5](#0-4) . The message being signed, however, is `set_keys_message(&self.spec.set(), &removed, key_pair)` — it binds the *new* set's keys and removed list [6](#0-5) .

The protocol's own safety argument (file docstring) is that nonce reuse is impossible because the cached seed is context-bound and BFT finalizes identical inputs per context — but that argument only holds while `context` uniquely identifies one signing session. It does not: `attempt` restarts at 0 for every new tributary's DKG, so `("DkgConfirmer", 0)` collides across set rotations. This is exactly the kernel bug shape: a prepare-phase artifact survives a transition back to the "online" state and is mistaken for freshly-initialized state.

### Impact Explanation
A Schnorrkel/MuSig share has the form `s = k + c·x`. With the same `k` and two different challenges `c`, `c'` (different message, different MuSig participant set, different binding factors), `x = (s − s') / (c − c')`. Both shares are published on-chain in `DkgConfirmation`/`set_keys` transactions. Recovery of `key` — the coordinator's validator secret used as root of trust for confirming DKG results on Substrate [7](#0-6)  — lets an attacker forge validator signatures on `set_keys` messages and any other validator-key-signed artifact, undermining the whole validator-set root of trust. The FROST docs explicitly classify this: reuse of a cached preprocess "enables recovery of your private key share" [8](#0-7) .

### Likelihood Explanation
The trigger is ordinary validator-set rotation: whenever a new tributary is stood up with a fresh genesis, its `DkgConfirmer` starts at `attempt = 0` and unconditionally reads the same `("DkgConfirmer", 0)` DB entry left by the prior set's confirmation. `share_internal` is invoked each time `share()`/`complete()` run [9](#0-8) , deterministically re-deriving and re-publishing shares over the stale nonce against the new message. No malicious validator, no race, and no user-controlled bytes are needed — the collision is structural, occurring on the first confirmation attempt of every subsequent set. Severity: High (secret key recovery under normal operation).

### Recommendation
Include the tributary genesis (or `self.spec.set()`/`session`) in the `CachedPreprocesses` key, e.g. `context = (b"DkgConfirmer", spec.genesis(), attempt)`, mirroring how every other tributary table is keyed by genesis. Additionally, delete the cached entry after `complete_internal` succeeds, and add a startup-style "reset on re-entry" guard: refuse to reuse a cached seed when the `ThresholdKeys`/`musig_context` derived for the current set differ from those the cache was created under (store a hash of the participant set alongside the seed and assert equality on load).

### Proof of Concept
1. Set `A` runs a DKG; at `attempt = 0` the coordinator calls `DkgConfirmer::share`, which executes `preprocess_internal` with `context = (b"DkgConfirmer", 0)`. A random seed `s_A` is stored in `CachedPreprocesses` and nonces `k` are generated; the share `s = k + c·x` over `set_keys_message(set_A, removed_A, kp_A)` is published.
2. Validator set rotates; tributary with genesis `B` performs its DKG. `DkgConfirmer::new(..., attempt: 0)` produces the identical `context`. `CachedPreprocesses::get` returns `s_A`; `from_cache` regenerates the identical `k`.
3. `share_internal` signs `set_keys_message(set_B, removed_B, kp_B)` — different bytes, different challenge `c'`. Share `s' = k + c'·x` is published.
4. Anyone reading the two tributaries' confirmation transactions computes `x = (s − s')/(c − c')`, recovering the coordinator's validator private key.

Uncertainty note: I did not fully trace whether each tributary uses an isolated `Db` instance or a truly shared one; however, all sibling tables take an explicit `genesis` key and `CachedPreprocesses` does not, which strongly indicates the DB namespace is shared and the collision is real.
