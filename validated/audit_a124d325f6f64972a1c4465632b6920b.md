### Title
`ReceivedOutput::read` trusts attacker-supplied outpoint/value, causing the multisig to sign transactions that burn funds to fees - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The SSRF bug class — a server acting on an attacker-supplied resource descriptor without verifying it against the authoritative source — maps onto `bitcoin-serai`'s `ReceivedOutput`. `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) deserializes an `offset`, a full `TxOut` (script + claimed value), and an `OutPoint` entirely from untrusted bytes, and `SignableTransaction::new` / `TransactionSignMachine::sign` then sign a Taproot key-spend committing to those claimed prevout values (`Prevouts::All`, send.rs:375) without ever checking that the outpoint resolves on-chain to an output with that script and value. The only consistency check is that the prevout's `script_pubkey` equals `p2tr_script_buf(offsetted group key)` (send.rs:277); the value and the outpoint itself are never validated.

### Finding Description
- `ReceivedOutput::read` accepts arbitrary `TxOut` and `OutPoint` bytes (mod.rs:122-134). There is no binding between `outpoint` and `output` — the struct claims "this UTXO exists and has this value" purely on the reader's say-so.
- `SignableTransaction::new` uses `input.output.value` as the input sum for payment/change/fee math (send.rs:175) and stores `input.output` as the prevout committed to by the sighash (send.rs:253).
- `multisig` only checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` (send.rs:276-279). A forged `ReceivedOutput` reusing the multisig's real script_pubkey passes this check with any attacker-chosen `outpoint` and any attacker-chosen `value`.
- `sign` then produces FROST signature shares over `taproot_key_spend_signature_hash(i, Prevouts::All(&prevouts), Default)` (send.rs:383-390), and `complete` assembles a fully-signed transaction spending those outpoints (send.rs:413-427).

Consequences of the mismatch:
- **Deflated value**: attacker supplies a real multisig UTXO outpoint but a `value` lower than the on-chain amount. The change/fee math uses the claimed value, so the signed transaction sends `actual - claimed` satoshis to miners as excess fee. The signature is consensus-valid (Taproot commits to the claimed prevout values, and Bitcoin enforces them — but the *output* side is computed from the same wrong number, so the difference is burned). Real funds are irrecoverably lost.
- **Inflated value or foreign outpoint**: attacker claims a UTXO that isn't the multisig's, or inflates the value. The multisig produces a broadcastable-looking signed transaction that consensus rejects — a repeatable signing DoS where each attempt consumes a fresh FROST signing session.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (e.g., any flow where a peer/relayer submits or mutates serialized inputs to a signer) can cause the threshold group to produce a valid signature on a transaction that either destroys multisig funds via inflated miner fees or locks the signing pipeline on permanently-invalid transactions. This is "funds reported spendable that are not" and "concrete signing of an unintended message" — a signature is emitted for inputs whose economic reality the signer never verified.

### Likelihood Explanation
The vulnerability requires an attacker to reach `ReceivedOutput::read` (or otherwise inject a `ReceivedOutput`) upstream of `SignableTransaction::new`. In honest use the `Scanner` produces these from chain data, but the type is explicitly serializable/deserializable (`read`/`write`/`serialize`, mod.rs:120-148), so any transport of scanned outputs between components is a trust boundary that is currently unauthenticated. Medium severity: secret keys are not exposed, but signed transactions destroying funds are achievable with a single corrupted message.

### Recommendation
Verify each `ReceivedOutput` before signing: fetch the transaction named by `outpoint.txid` via `Rpc::get_transaction` and check `output[vout]` equals the claimed `TxOut` (script and value), rejecting mismatches in `SignableTransaction::new` or `multisig`. Alternatively, treat `ReceivedOutput` as privileged: authenticate/harden its serialized form (MAC or trusted-channel-only deserialization) so untrusted parties cannot fabricate outpoint/value pairs.

### Proof of Concept
```rust
// Attacker observes a real multisig UTXO on-chain: outpoint P, value 1_000_000 sats,
// script_pubkey = p2tr_script_buf(group_key).
// They craft serialized bytes for ReceivedOutput::read:
//   offset  = Scalar::ZERO
//   output  = TxOut { value: 100_000 sats, script_pubkey: <real multisig script> }
//   outpoint = P  (real outpoint worth 1_000_000 sats)
let forged = ReceivedOutput::read(&mut attacker_bytes).unwrap();

// Signer builds the transaction
let tx = SignableTransaction::new(
    vec![forged],
    &[(payment_script, 90_000)],
    None, // no change: everything not paid out becomes fee
    None,
    fee_per_vbyte,
).unwrap();
// multisig() passes: script_pubkey check succeeds (send.rs:277)
// sign() produces shares over Prevouts::All with the *claimed* 100_000 sat prevout
// complete() yields a tx paying 90_000 sats and ~910_000 sats of miner fee
```
