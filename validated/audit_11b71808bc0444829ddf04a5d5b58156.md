## Analysis

The aria2c CVE's failed invariant: a value explicitly meant to stay out of a persisted debug artifact (HTTP Basic Auth credentials) leaks into that artifact because the logging code path never applies the redaction that other code paths respect. The transferable invariant for Protobuf is `debug_redact`: a schema author marks a field so that "the field value should not be printed out when using debug formats, e.g. when the field contains sensitive credentials" [1](#0-0) . Consuming applications rely on this annotation to keep secrets (tokens, passwords) out of debug/log output regardless of which built-in "debug format" API they call.

`TextFormat`/`DebugString` honors this: `TryRedactFieldValue` checks `GetRedactionState(field)` and substitutes `[REDACTED]` when `debug_redact` is set [2](#0-1) , and the Java `TextFormat.Printer.shouldRedact` does the analogous check [3](#0-2) .

`JsonFormat` (Java `com.google.protobuf.util.JsonFormat`) is a separate, equally-public serialization API commonly used to log/dump message contents, but its printer (`PrinterImpl.printField`/`printSingleFieldValue`) contains no reference to `debug_redact`, `RedactionState`, or any redaction marker at all [4](#0-3) [5](#0-4) . The Python `json_format._Printer._FieldToJsonObject` similarly has no redaction logic and prints all field values unconditionally [6](#0-5) . I found no `debug_redact`/`redact` references anywhere under the JSON printer code paths in either language.

This is a genuine, verifiable gap in this checkout: a schema owner who marks a credential field `debug_redact = true` — the exact scenario the option's own documentation calls out ("sensitive credentials") — is fully protected when the message is dumped via `TextFormat`/`DebugString`, but the same field is printed in cleartext if the same message is dumped via `JsonFormat.printer().print()` (Java) or `MessageToJson`/`MessageToDict` (Python), which are equally standard, documented, public "debug/log this message" entry points. An ordinary client can supply the sensitive value through a normal parse API, and any application code that assumes `debug_redact` is format-agnostic (a reasonable assumption given the field's schema-level, not-printer-specific declaration) will inadvertently write secrets into JSON logs — directly analogous to aria2c's `--log` writing Basic Auth credentials to a file that other components assumed would be redacted/scrubbed.

This is a real design/consistency gap, not proto3 optional. Whether it rises to a security *vulnerability* in this checkout (versus a documentation/consistency issue: `debug_redact` may be intentionally scoped only to `TextFormat`-family debug strings) is genuinely ambiguous — the descriptor.proto comment says "debug formats" generically, but Protobuf's own JSON printer was apparently never wired to honor it, and there is no test coverage anywhere in the repo asserting JSON redaction (only `TextFormat`/`DebugFormat` tests exist, e.g. `DebugFormatTest.java`, `redaction_metric_test.cc`).

### Title
Missing `debug_redact` enforcement in ProtoJSON printers (`JsonFormat`, `json_format.py`) — sensitive fields leak into JSON debug/log output - (File: `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`)

### Summary
`FieldOptions.debug_redact` is documented as a schema-level guarantee that a field's value "should not be printed out when using debug formats, e.g. when the field contains sensitive credentials." `TextFormat`/`DebugString` enforce this consistently across C++/Java, but the ProtoJSON printers (`JsonFormat.Printer` in Java, `_Printer` in `json_format.py`) never check `debug_redact` at all, so credentials marked sensitive by the schema author are printed in cleartext whenever a consuming application serializes the message to JSON for logging/debugging instead of using TextFormat.

### Finding Description
`TextFormat::Printer::TryRedactFieldValue` (C++) and `TextFormat.Printer.shouldRedact` (Java) consult `FieldDescriptor.debug_redact`/`RedactionState` before emitting a field value, substituting `[REDACTED]` when set [2](#0-1) [3](#0-2) . This is the only enforcement point for the invariant in the whole codebase.

`JsonFormat.PrinterImpl.printField`/`printSingleFieldValue`, the Java ProtoJSON printer, iterates all fields and prints their raw values with no redaction check whatsoever [4](#0-3) . The Python `json_format._Printer._FieldToJsonObject`/`_RegularMessageToJsonObject` behave identically, unconditionally converting and printing every field [7](#0-6) [6](#0-5) . Neither implementation references `debug_redact`, `RedactionState`, or `[REDACTED]`.

Because `debug_redact` is a single, schema-wide annotation (set once on a `.proto` field, independent of which printer will be used later), an application author who marks a `password`/`token`/`Authorization` field `debug_redact = true` reasonably expects that annotation to protect the field across all "debug output" surfaces exposed by the library. It only protects `TextFormat`-derived output.

### Impact Explanation
Applications frequently log protobuf messages as JSON (via `JsonFormat.printer().print(message)` or `json_format.MessageToJson`) for request/response tracing, structured logging, or error reporting. If such logging pipelines and the schema's `debug_redact` annotations were set up under the (reasonable, given the option's generic name and docs) assumption that redaction is format-agnostic, credentials or other sensitive fields end up written to plaintext logs/log files — the same class of local, at-rest sensitive-information disclosure described in CVE-2019-3500 (confidentiality impact, no privileged access needed to trigger the write, only to later read the resulting artifact).

### Likelihood Explanation
High for triggering the write (any client-controlled field value flowing into a message that is later JSON-logged reproduces it deterministically), moderate for real-world exploitability since it depends on the consuming application choosing to serialize via `JsonFormat`/`json_format` for logging while also relying on `debug_redact` — a plausible but not universal usage pattern. No parser bypass or malformed input is needed.

### Recommendation
Either (a) explicitly scope `debug_redact`'s documentation to `TextFormat`/`DebugString`-only and have `JsonFormat`/`json_format.py` refuse/ignore silently by design (documented limitation), or (b) implement the same `GetRedactionState`/`debug_redact` check in `JsonFormat.PrinterImpl` and `json_format._Printer` so the annotation is honored consistently across all "debug" serialization surfaces, matching the guarantee already given for TextFormat.

### Proof of Concept
Given `RedactedFields.optional_redacted_string` (marked `debug_redact = true` in `unittest.proto` [8](#0-7) ):
```java
RedactedFields msg = RedactedFields.newBuilder()
    .setOptionalRedactedString("super-secret-credential")
    .build();

// Protected: prints "[REDACTED]"
System.out.println(DebugFormat.multiline().toString(msg));

// NOT protected: prints the raw value "super-secret-credential"
System.out.println(JsonFormat.printer().print(msg));
```
The `DebugFormat` path calls `TextFormat.Printer.shouldRedact` and redacts [3](#0-2) ; the `JsonFormat.printer().print()` path has no equivalent check and serializes the raw string [9](#0-8) .
