## Analysis Result [1](#0-0) 

### Title
Incomplete Extension Denylist in "Open with Default Program" Enables Code Execution via Malicious Repository Content - (File: app/src/ui/lib/context-menu.ts)

### Summary
The `isSafeFileExtension` gate that decides whether GitHub Desktop's "Open with Default Program" menu item is enabled relies on a tiny, hardcoded denylist (`.cmd`, `.exe`, `.bat`, `.sh`) instead of a safe allowlist. Just as the WooCommerce report exploited a check that validated the *wrong* property of an attacker-supplied file (any extension could still smuggle a Phar stream), this Desktop analog validates only 4 out of dozens of Windows-executable-associated extensions before allowing the app to hand an attacker-controlled file straight to the OS's default-open handler.

### Finding Description
`isSafeFileExtension` in [1](#0-0)  defines:
```
const RestrictedFileExtensions = ['.cmd', '.exe', '.bat', '.sh']
...
export function isSafeFileExtension(extension: string): boolean {
  if (__WIN32__) {
    return RestrictedFileExtensions.indexOf(extension.toLowerCase()) === -1
  }
  return true
}
```
This function gates the `enabled` flag on the "Open with Default Program" context-menu item across every UI surface that renders repository content originating from attacker-controlled sources: the Changes list [2](#0-1) , commit history file list [3](#0-2) , and the pull-request "Files changed" view [4](#0-3) . When the menu item is invoked, `onOpenItem` joins the repository path with the attacker-controlled relative path and calls `openFile`, which invokes `shell.openExternal('file://' + fullPath)` [5](#0-4) , i.e., it asks the OS to launch the file with its registered default handler.

On Windows, dozens of extensions besides `.exe`/`.cmd`/`.bat` are directly executable or trigger code execution through their default handler — e.g. `.scr` (screensaver, run as PE), `.pif`, `.com`, `.msi`, `.msc`, `.jar`, `.vbs`, `.vbe`, `.js`/`.jse`, `.wsf`, `.wsh`, `.ps1`, `.hta`, `.cpl`, `.reg`, `.url`, `.lnk`, `.application`, `.gadget`. None of these appear in `RestrictedFileExtensions`, so `isSafeFileExtension` returns `true` for them and the menu item stays enabled.

### Impact Explanation
An attacker who controls the content of a repository (a public repo the victim clones, a branch/PR the victim fetches, or a file introduced via merge/checkout) can add a file such as `invoice.scr`, `readme.hta`, or `update.jar` to the working directory. If the victim opens the Changes/History/PR-files list, sees the unfamiliar file, and clicks "Open with Default Program" (a normal, expected action for reviewing an unknown file type since Desktop cannot render a diff/preview for it), Windows will execute the attacker's payload with the same privileges as the logged-in user — full code execution outside of any Git/Desktop sandboxing. This matches the required impact class: attacker controls cloned/fetched repository content, and the result is code execution, achieved via a natural, single user click rather than an unprompted or unnatural workflow.

### Likelihood Explanation
This requires the extension not to be one of the four blocked ones and the user to intentionally choose "Open with Default Program" on a file that piqued their curiosity (e.g., disguised as a document via icon/extension spoofing tricks like `invoice.pdf.scr` — Explorer hides known extensions by default). This is a normal single click already exposed prominently in three separate context menus, no admin rights, no pre-existing malware, and no credential leakage required — only a denylist gap.

### Recommendation
Replace the denylist in `isSafeFileExtension` with a maintained allowlist of known-safe, non-executable extensions (documents, images, text, media), or delegate the safety decision to the OS/Explorer's own "this file could harm your computer" Mark-of-the-Web prompt by not special-casing extensions at all, or expand `RestrictedFileExtensions` to a comprehensive, actively-maintained list of Windows executable-content extensions (`.scr`, `.pif`, `.com`, `.msi`, `.msc`, `.jar`, `.vbs`, `.vbe`, `.js`, `.jse`, `.wsf`, `.wsh`, `.ps1`, `.hta`, `.cpl`, `.reg`, `.url`, `.lnk`, `.application`, `.gadget`, etc.), consistent with the more complete `WindowsExecutableExtensions`-style curation already used elsewhere in the codebase for custom integrations [6](#0-5) .

### Proof of Concept
1. Attacker creates a public repository containing a file `important-notes.scr` (a renamed executable) and pushes it.
2. Victim clones or fetches this repository in GitHub Desktop and the file shows up as an untracked/new file in the Changes list, or as part of a PR's "Files changed" view.
3. Victim right-clicks the file; because `.scr` is not in `RestrictedFileExtensions`, `isSafeFileExtension('.scr')` returns `true`, so "Open with Default Program" is enabled [7](#0-6) .
4. Victim clicks it; `onOpenItem` → `openFile` → `shell.openExternal('file://<repo>/important-notes.scr')` [8](#0-7)  causes Windows to execute the attacker's binary.

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
