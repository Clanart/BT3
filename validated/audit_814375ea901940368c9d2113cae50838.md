### Title
Unvalidated participant indexes in PedPoP blame evaluation cause a remotely triggerable panic (DoS) - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs), [File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
Analogous to CVE-2020-2573 (network-reachable crash/hang of a client via untrusted data), Serai's PedPoP DKG blame path indexes `HashMap`s keyed by `Participant` with attacker-supplied indexes and panics on missing keys. Both `BlameMachine::blame` / `AdditionalBlameMachine::blame` pass the caller-provided `sender`/`recipient` straight into `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with no bounds check that they lie within `1 ..= n`. `Participant::new` only rejects zero, so any nonzero u16 (e.g., `n + 1`) is a valid `Participant` that is absent from those maps, producing a `HashMap` index panic — a crash of the evaluating party's process.

### Finding Description
`Participant` is defined as a non-zero `u16` wrapper; `Participant::new` returns `Some` for every value in `1 ..= 65535`, with no relation to the session's `n`. [1](#0-0) 

`AdditionalBlameMachine::blame` accepts `sender` and `recipient` as `Participant` arguments and forwards them to `blame_internal` without checking `<= n` or membership in the maps built by `AdditionalBlameMachine::new` (which only registers participants `1 ..= n`). [2](#0-1) [3](#0-2) 

Inside `blame_internal`, `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (panics when `recipient` was never registered), and later `self.commitments[&sender]` is indexed to build the share-verification statements (panics when `sender` is out of range). [4](#0-3) [5](#0-4) 

The early return on `DecryptionError::InvalidSignature` only occurs when the message's PoP fails to verify; a malicious `sender` (or an accuser referencing a valid sender message) can supply an `EncryptedMessage` with a correctly formed PoP, since `EncryptedMessage::read` deserializes attacker bytes and the PoP only proves knowledge of the ephemeral key the attacker chose. Once the PoP verifies and a `proof` is supplied, the unchecked `enc_keys[&decryptor]` lookup is reached. A `Participant` such as `Participant::new(n + 1).unwrap()` is trivially constructible.

### Impact Explanation
Any party that evaluates blame — either a `BlameMachine` holder processing an accusation, or an `AdditionalBlameMachine` operator (e.g., a coordinator/arbiter reconstructing the DKG commitment set to adjudicate `InvalidDkgShare`-style accusations) — crashes on a panic when the accusation names a `sender` or `recipient` outside `1 ..= n`. This is a complete, repeatable denial of service of the evaluating process triggered purely by attacker-chosen message fields (two u16 indexes plus an `EncryptedMessage`), matching the CVE class: unprivileged network input causing a crash/abort in a cryptographic client library. In a validator/processor deployment, the panic aborts the task evaluating blame, preventing DKG completion and any dependent signing.

### Likelihood Explanation
The trigger requires only that blame evaluation be invoked — no threshold cooperation, no valid share, no cryptographic break. The attacker must supply an `EncryptedMessage` whose Schnorr PoP verifies for the claimed `sender` (they can generate this themselves, as they possess the ephemeral key), or simply name an out-of-range `recipient` (`decryptor`) so the panic fires at `enc_keys[&decryptor]` before the commitment lookup is even reached. `Participant` admits any nonzero u16, so crafting the index is trivial. Medium likelihood: it requires reaching the blame flow, which occurs on any DKG dispute.

### Recommendation
In `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal`, replace indexing (`self.enc_keys[&decryptor]`, `self.commitments[&sender]`) with fallible lookups (`HashMap::get` → return an error / a defined blame outcome) and validate `sender`/`recipient` against `params` (or the registered key set) before use, e.g. `u16::from(p) <= n`. `AdditionalBlameMachine::new` should also store `n` and reject out-of-range participants in `blame`.

### Proof of Concept
```rust
// n = 2 session; attacker triggers blame evaluation with an out-of-range recipient.
let n = 2u16;
let context = [0u8; 32];

// commitment_msgs for participants 1 and 2, built from attacker-controlled bytes
// via EncryptionKeyMessage::read / Commitments::read.
let machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// An EncryptedMessage whose `pop` verifies (attacker knows the ephemeral key):
//   EncryptedMessage::read(key, pop, msg) -> valid SchnorrSignature over pop_challenge.
let msg: EncryptedMessage<Ristretto, SecretShare<_>> = attacker_msg_with_valid_pop;

// recipient = Participant(3) was never registered (enc_keys only has 1..=2).
// blame_internal -> decrypt_with_proof(from, decryptor=3, msg, Some(proof))
//   -> self.enc_keys[&Participant(3)]  => PANIC: "key not found"
machine.blame(Participant::new(1).unwrap(), Participant::new(3).unwrap(), msg, Some(proof));
```

The same panic is reachable via `sender = Participant(3)` at `self.commitments[&sender]` once the PoP check passes, and on participant-side `BlameMachine::blame` whenever an accusation references indexes outside `1 ..= n`. No bounds check exists anywhere along `blame` → `blame_internal` → `decrypt_with_proof` for either index.

  pub fn new(
    context: [u8; 32],
    n: u16,
    mut commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<Self, PedPoPError<C>> {
    let mut commitments = HashMap::new();
    let mut encryption = Decryption::new(context);
    for i in 1 ..= n {
      let i = Participant::new(i).unwrap();
      let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
      commitments.insert(i, encryption.register(i, msg).commitments);
    }
    Ok(AdditionalBlameMachine(BlameMachine { commitments, encryption, result: None }))
  }
