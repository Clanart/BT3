### Title
Race condition in `AccountsStore.refresh()` silently discards/reverts concurrent `addAccount`/`removeAccount` changes - (File: `app/src/lib/stores/accounts-store.ts`)

### Summary
`AccountsStore.refresh()` snapshots `this.accounts`, kicks off an async network call per account, and then unconditionally overwrites `this.accounts` with the resolved snapshot once all calls complete. This is the same "read into memory → mutate storage elsewhere during an async gap → blind overwrite of the whole state with the stale snapshot" pattern described in the Perennial V2 report, just applied to Desktop's account cache instead of Solidity storage.

### Finding Description
`refresh()` reads the current `this.accounts` array and maps each entry through `tryUpdateAccount`, which calls `fetchUser(account.endpoint, account.token)`: [1](#0-0) 

If, while this `Promise.all` is pending, another code path calls `addAccount()` or `removeAccount()` (both of which synchronously mutate `this.accounts` and persist immediately via `save()`): [2](#0-1) [3](#0-2) 

then when `refresh()` finally resolves, it does `this.accounts = await Promise.all(...); this.save()`, which blindly overwrites the array (and re-persists it to `dataStore`/keychain) with the value computed from the *original* pre-mutation snapshot, silently reverting whatever `addAccount`/`removeAccount` did in the interim — exactly analogous to `_storeContext` clobbering `_locals[account]` with a stale `context.local` after `_credit` had already mutated storage in `Market.sol`.

Because `updatedAccount()` performs an HTTP request to `account.endpoint` (a GitHub.com or GitHub Enterprise Server URL the account was configured with): [4](#0-3) 
a malicious or compromised Enterprise Server (or a network man-in-the-middle for that endpoint) fully controls how long the response is delayed, and therefore controls the width of the race window during which the in-memory snapshot goes stale relative to concurrent account operations.

### Impact Explanation
If a user removes an account (e.g. signs out of a compromised/leaked-token Enterprise account) while a slow/attacker-delayed `refresh()` call for that same account is still in flight, `removeAccount()` deletes the token from the secure keychain and drops the account from `this.accounts`, but the pending `refresh()` later overwrites `this.accounts` with its stale snapshot that still contains that account object holding its old token in memory, and `save()` re-persists the (tokenless-on-disk, but token-in-memory/re-derivable) account list. This silently undoes a security-relevant user action (revoking access to an account) without any error or indication to the user, effectively resurrecting an account/token binding the user explicitly removed.

### Likelihood Explanation
Exploitation requires only that the user has added an Enterprise/GitHub.com account whose server response Desktop trusts (the "attacker-controlled remote/API endpoint" scenario), and that `refresh()` is invoked around the same time the user removes or adds an account — both realistic, low-privilege, network-only conditions (a slow/hanging HTTP response from a malicious/compromised server is trivial for the endpoint owner to produce). No local access, admin rights, or pre-existing malware is required.

### Recommendation
Make `refresh()` update accounts by identity/merge rather than wholesale array replacement — e.g., re-read `this.accounts` after each `tryUpdateAccount` resolves and merge results by endpoint/id, or use a version/generation counter to detect and drop stale writes, mirroring the report's recommendation to update `context.local` in place rather than overwriting the account's full storage slot.

### Proof of Concept
1. User adds an Enterprise account pointing at a server the attacker (or a MITM) controls.
2. Desktop calls `refresh()`, which starts `fetchUser()` against the attacker's server for that account; the attacker holds the HTTP response open indefinitely.
3. While the request is pending, the user removes the (now suspected-compromised) account via Preferences → `removeAccount()`, which deletes the token from the keychain and updates/persists `this.accounts` without that entry.
4. The attacker finally lets the delayed response resolve. `refresh()`'s `Promise.all` completes with the pre-removal snapshot and executes `this.accounts = ...; this.save()`, restoring the removed account (with its cached token in memory) into the store and re-persisting it, silently reverting the user's removal.   /** Refresh all accounts by fetching their latest info from the API. */
  public async refresh(): Promise<void> {
    this.accounts = await Promise.all(
      this.accounts.map(acc => this.tryUpdateAccount(acc))
    )

    this.save()
    this.emitUpdate(this.accounts)
  }

  /**
   * Attempts to update the Account with new information from
   * the API.
   *
   * If the update fails for whatever reason this function
   * will return the old Account instance. Usually updates fails
   * due to connectivity issues but in the future we should
   * investigate whether we're able to detect here that the
   * token is definitely not valid anymore and let the
   * user know that they've been signed out.
   */
  private async tryUpdateAccount(account: Account): Promise<Account> {
    try {
      return await updatedAccount(account)
    } catch (e) {
      log.warn(`Error refreshing account '${account.login}'`, e)
      return account
    }
  }

  /**
   * Remove the account from the store.
   */
  public async removeAccount(account: Account): Promise<void> {
    await this.loadingPromise

    try {
      await this.secureStore.deleteItem(
        getKeyForAccount(account),
        account.login
      )
    } catch (e) {
      log.error(`Error removing account '${account.login}'`, e)
      this.emitError(e)
      return
    }

    this.accounts = this.accounts.filter(
      a => !(a.endpoint === account.endpoint && a.id === account.id)
    )

    this.save()
  }

async function updatedAccount(account: Account): Promise<Account> {
  if (!account.token) {
    return fatalError(
      `Cannot update an account which doesn't have a token: ${account.login}`
    )
  }

  return fetchUser(account.endpoint, account.token)
}
