### Title
Blocking hookify rules silently fail open when a condition's field is unset for the tool variant being used - (File: plugins/hookify/core/rule_engine.py)

### Summary
The Sherlock finding's root cause is that a return value (`amountToMint`/`amountMinted`) is never checked for the "null"/zero case, so a costly, irreversible side effect (transferring reserve funds) proceeds even though the compensating effect (minting tokens) silently produced nothing. The same defect shape — a value that can legitimately be `None`/absent is treated as a definitive negative signal rather than being explicitly validated, causing a security-relevant action to silently take the permissive path — exists in the `hookify` plugin's rule engine, which implements `PreToolUse`/`Stop` command-approval and blocking behavior for Claude Code.

### Finding Description
`RuleEngine._check_condition()` extracts a field from the tool call via `_extract_field()` and immediately treats a `None` result as "the condition does not match," which for a `block` rule silently converts a would-be `deny` into an allow: [1](#0-0) 

```python
field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
if field_value is None:
    return False
```

`_extract_field()` returns `None` whenever the requested field name isn't one of the small set of hardcoded `(tool_name, field)` pairs it recognizes: [2](#0-1) 

For example, a rule written to block dangerous content via `field: content` matches `Write`/`Edit`'s `content`/`new_string`, but returns `None` for `MultiEdit` unless the condition author also anticipated `MultiEdit`'s different field name (`edits[].new_string` is only merged when `field` is exactly `new_text` or `content`, not `content` for a rule authored using `new_text`/`old_text` naming used elsewhere, and not at all for a `NotebookEdit` or any other file-editing tool). Likewise, a `field: command` condition returns `None` for anything other than `tool_name == 'Bash'` — so the same logical rule silently never blocks equivalent operations invoked through a different tool (e.g., a custom/plugin Bash-like tool, or a script tool whose input uses a different key name than `command`).

Because a missing/mismatched field is indistinguishable from "field present and doesn't match the pattern," a rule author who defines a `block` rule intending to catch a dangerous command/content pattern across all tool variants gets a rule that is silently inert for any tool/field combination not explicitly hardcoded in `_extract_field`. There is no validation, warning, or error surfaced anywhere in the pipeline — `evaluate_rules()` simply returns `{}` ("no matches — allow operation") for the untouched tool call, exactly mirroring the Sherlock pattern where `mintFromInterest()` silently returns `0` and the caller proceeds as if nothing was wrong.

This is compounded by every hook entrypoint (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) wrapping the whole evaluation in `try/except` that also fails open on any exception: [3](#0-2) 

### Impact Explanation
A user (or a project maintainer relying on hookify to enforce guardrails, e.g. "block `rm -rf`", "block writing secrets into `.env`") believes a `block` rule is protecting all matching tool calls, but the rule only actually fires for the exact tool/field pairs `_extract_field` hardcodes (`Bash`+`command`; `Write`/`Edit`+`content`/`new_string`/`old_string`/`file_path`; `MultiEdit`+`file_path`/`new_text`/`content`). Any equivalent dangerous action reached through a tool not in that list (or a field name the rule author reasonably chose but that doesn't match the hardcoded name) bypasses the block entirely and is silently allowed — the exact "funds added without minting" asymmetry: the guardrail's enforcement side quietly no-ops while the risky action proceeds. This is a concrete tool-authorization/hook-bypass gap reachable by any user (or by content an unprivileged party influences, e.g. a crafted file edit routed through a less-common tool) without any privilege.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: hookify's own documentation encourages users to write conditions keyed on field names like `new_text`/`content` without tool-specific knowledge, and Claude Code exposes multiple file-editing tools (`Write`, `Edit`, `MultiEdit`, and others) with different input shapes. Any rule author who doesn't happen to pick the exact hardcoded field name for the exact tool in play will unknowingly ship a rule that never blocks — with zero error/warning surfaced, since `_check_condition` treats "field absent" identically to "field didn't match."

### Recommendation
Distinguish "field not applicable/not found for this tool" from "field found but pattern didn't match." When a condition's field cannot be resolved for the current `tool_name`, either (a) treat it as a rule-authoring error and surface a `systemMessage`/log warning (never a silent pass), or (b) for `block` actions, fail closed (`ask`/`deny`) rather than silently allowing, mirroring the Sherlock fix's guidance of reverting rather than proceeding on an unchecked null/zero. Additionally, extend `_extract_field` to generically fall back to any matching key inside `tool_input` rather than hardcoding per-tool field name, so field-name/tool coverage gaps don't silently defeat rules.

### Proof of Concept
1. A project defines a hookify blocking rule intended to prevent secrets from being written into files:
```markdown
---
name: block-secret-writes
enabled: true
event: file
action: block
conditions:
  - field: new_text
    operator: contains
    pattern: API_KEY
---
```
2. The rule works for `Edit` (maps `new_text`→`new_string`) but is silently inert for `MultiEdit`, because `_extract_field` only merges `edits[].new_string` when `field in ['new_text', 'content']` is checked against `MultiEdit`'s branch — verify: for `field == 'new_text'` and `tool_name == 'MultiEdit'`, the code does correctly hit `elif field in ['new_text', 'content']:` at line 249, so `MultiEdit` is actually covered in this specific case. However, any other tool that edits files (e.g. a plugin/MCP-provided file-write tool, or a future built-in tool) is NOT covered — `_extract_field` returns `None`, `_check_condition` returns `False` at line 159-160, and `evaluate_rules` returns `{}`, silently allowing the secret-containing write with no warning to the user or Claude.
3. An unprivileged user (or model acting on ambiguous instructions) can write the secret via any tool outside the hardcoded set and the "protective" rule never fires, while the write action itself proceeds — the same source-of-truth split between "the guarded state was consulted" and "the guard actually enforced anything" seen in the GoodDollar report.
