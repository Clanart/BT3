### Title
Quadratic-time Lagrange interpolation on attacker-controlled `t`/`included` enables CPU denial of service - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the fzf DoS (CVE-2026-53433), where a crafted request triggers O(n²) work on a single-threaded server, Serai's `Interpolation::interpolation_factor` performs an O(k) inner loop over the signing set, and it is invoked once per participant — once per `1..=t` share in `ThresholdKeys::new` and once per `included` signer in `ThresholdKeys::view`. Both `t` (via `ThresholdKeys::read`) and `included` (via the set of peers' preprocesses passed to `sign`) are attacker-influenced, producing O(t²) / O(k²) field multiplications from a small input.

### Finding Description
`interpolation_factor` iterates the entire `included` list for each evaluation [1](#0-0) . `ThresholdKeys::new` calls it for each of `t` participants to derive `group_key` [2](#0-1) , and `ThresholdKeys::view` calls it for every signer in `included` [3](#0-2) .

Both bounds come from untrusted bytes:

- `ThresholdKeys::read` reads `t` and `n` as attacker-controlled `u16`s, then calls `ThresholdKeys::new` — yielding up to ~4.3×10⁹ field multiplications plus 65,535 scalar multiplications for `t = n = 65535` [4](#0-3) .
- `AlgorithmSignMachine::sign` builds `included` from the participant keys of the peer-supplied `preprocesses` map (bounded only by `n ≤ 65535`) and then calls `view`, again O(k²) [5](#0-4) .

There is no caching of interpolation factors and no smaller cap on `t`/`n`, so the quadratic blowup is directly reachable.

### Impact Explanation
A single small malicious input (a crafted `ThresholdKeys` serialization, or a signing session advertising ~65k preprocesses) monopolizes a signer's CPU for an extended period. Since signing/DKG handling runs inline in the processor's message loop, this blocks all other signing work — a remote denial of service against the validator/processor, matching the Medium severity of the fzf advisory.

### Likelihood Explanation
`ThresholdKeys::read` and the preprocess map are explicitly reachable with untrusted bytes per the threat model (peer-supplied sign data is deserialized and fed to `read_preprocess`/`sign` in `processor/src/batch_signer.rs` and `processor/src/signer.rs`). The attacker needs only to transmit bytes; no key compromise, collusion, or protocol violation is required. Lagrange interpolation being inherently quadratic in a 65k-bound set is what makes a modest input translate into billions of field operations.

### Recommendation
Cache/compute Lagrange coefficients in O(k) total (standard prefix/suffix product trick) inside `view`/`new` instead of recomputing `interpolation_factor` per signer, and/or enforce a realistic upper bound on `t`/`n` and on the number of preprocesses accepted per signing session before invoking `view`.

### Proof of Concept
```rust
// Attacker-controlled bytes: t = n = 0xFFFF
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(0xFFFFu16.to_le_bytes()); // t
buf.extend(0xFFFFu16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes());      // i
buf.push(1);                          // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref()); // secret_share
for _ in 0 .. 0xFFFF { buf.extend(C::generator().to_bytes().as_ref()); }
// ThresholdKeys::read -> ThresholdKeys::new performs sum over t participants,
// each interpolation_factor looping over t entries: ~4.3e9 field muls.
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
```
Equivalently, a participant broadcasting a `preprocesses` map keyed by participants `1..=65535` forces every verifier's `sign()` → `view()` into the same O(k²) loop.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
