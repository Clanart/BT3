### Title
Cross-chain-replayable EIP-7702 SetCode authorizations can force-associate an unintended Sei identity, mirroring the Coinbase index/owner replay bug - (File: `utils/helpers/address.go`, `x/evm/ante/preprocess.go`, `app/ante/evm_checktx.go`)

### Summary
Sei's EVM supports EIP-7702 `SetCodeTx`, whose `SetCodeAuthorization` tuples are signed over `(chainId, address, nonce)`. Per spec (and mirrored here), an authorization with `chainId == 0` is valid on **every** chain, making it publicly replayable across all Sei-connected chains/environments exactly like Coinbase's `executeWithoutChainIdValidation`. The authority recovered from such an authorization is a distinct account from the transaction sender, and if naively associated to its "direct-cast" Sei address rather than its true pubkey-derived Sei address, a later legitimate association for that same person remaps the identity — splitting state (balances, staking/distribution records) across two different Sei addresses for what the user believes is one account, analogous to `removeOwnerAtIndex` silently acting on a different owner than intended across contexts.

### Finding Description
The code explicitly documents the root-cause class: `AuthorityToPreAssociate` in [1](#0-0)  must "mirror go-ethereum's `validateAuthorization`" and skip out-of-scope authorizations, because "the authorization sig hash is computed from the auth's own ChainID, so recovery and `auth.Authority()` succeed for an authorization signed for ANY chain" and "a publicly-visible authorization a user signed for another chain ... could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their direct-cast balance and orphaning staking/distribution state." This is the same fundamental class as the Coinbase bug: a signed message whose scope/target-identity binding is weaker than assumed can be replayed in a different context to act on unintended state.

The mitigation (`AuthorityToPreAssociate` + `associateAuthorizationAuthorities` in [2](#0-1)  and the legacyabci counterpart `AssociateAuthorizationAuthorities` in [3](#0-2) ) requires: chain-id match (or zero), nonce/account-state match, and — critically — skips authorities that are **already associated**, preventing remapping of an existing identity. Tests in `app/setcode_authority_test.go` and `x/evm/ante/preprocess_test.go` explicitly verify a foreign-chain authorization is *not* pre-associated.

### Impact Explanation
If this guard were absent or bypassed (e.g., via the OCC/giga execution path or another entry point that skips `AuthorityToPreAssociate`), an attacker could take a victim's publicly-broadcast EIP-7702 authorization (chainId=0 or matching) and replay it in a sponsored SetCode transaction to force-associate the victim's EVM authority address to the wrong (direct-cast) Sei address before the victim's real pubkey-derived association happens. This would split the victim's balance/staking state across two Sei addresses — a fund-loss/fund-freezing condition, and per the code comments could "halt the chain via the distribution validator-removal hook" if the orphaned identity held validator-linked state. This matches the accepted High-severity bar (fund loss/freezing, potential validator halt).

### Likelihood Explanation
Currently mitigated in both ante paths (`x/evm/ante/preprocess.go` and `app/ante/evm_checktx.go`) and in the giga executor (`app/app.go`'s `setCodeTxRequiresAuthorityAssociation`), with dedicated regression tests. Likelihood of exploitation today is low given the guard exists; the risk is regression if a new EVM execution path (e.g., a future OCC/giga fast-path) forgets to call `AuthorityToPreAssociate` before applying SetCode authorizations, exactly as the Coinbase root cause was a missing owner-binding check.

### Recommendation
Ensure every code path that can apply an EIP-7702 `SetCodeAuthorization` (ante handlers, giga/OCC executor, any future replay/import tooling) routes through `AuthorityToPreAssociate`/`AssociateAuthorizationAuthorities` before installing delegation code, and add a differential/fuzz test asserting no execution path can create a direct-cast mapping for an authority that will later receive a true pubkey-derived association. Keep the existing "already associated authorities are skipped" and "chain-id must be zero or match" invariants as hard preconditions, and add CI coverage that fails if a new transaction path is added without this check (e.g., via an interface requiring authorization pre-association to be called explicitly).

### Proof of Concept
1. Victim signs an EIP-7702 authorization with `chainId = 0` (valid anywhere) delegating their EOA to some code target, intending to use it on chain A.
2. Attacker observes this authorization (it's public once broadcast/signed) and, on Sei, submits a sponsored `SetCodeTx` embedding the same authorization before the victim ever transacts on Sei.
3. Without the `AuthorityToPreAssociate` guard, the naive path would associate the victim's authority EVM address to its **direct-cast** Sei address (`sdk.AccAddress(evmAddr[:])`), matching go-ethereum's SetCode application logic.
4. The victim later performs a normal Sei transaction, deriving their **true pubkey-based** Sei address, which is different from the direct-cast address, per `TestPreprocessAssociatesSetCodeAuthorities` in `x/evm/ante/preprocess_test.go` (asserting `victimCast.String() != victimTrueSei.String()`).
5. Any balance or staking/distribution state already attributed to the direct-cast identity becomes orphaned/inaccessible under the victim's real identity — fund loss/freezing, matching the Coinbase bug's "user loses access to funds due to identity/index mismatch across contexts."

// AuthorityToPreAssociate returns the authority of an EIP-7702 authorization that should be
// associated with its true (pubkey-derived) Sei address before execution, or ok=false.
//
// It mirrors go-ethereum's StateTransition.validateAuthorization (chain id, nonce overflow,
// authority code, and account-nonce checks) so that pre-association happens only for
// authorizations the EVM will actually apply, and additionally skips authorities that are
// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true

// associateAuthorizationAuthorities associates every EIP-7702 authorization authority in
// the transaction with its true (pubkey-derived) Sei address, so that a subsequent
// SetCode for the authority does not create a mutable direct-cast mapping. It is
// best-effort: authorities with invalid signatures (which EVM execution would also skip)
// or that are already associated are left untouched, and an association failure skips
// only that authority rather than rejecting the transaction, which go-ethereum would
// still accept.
func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}
