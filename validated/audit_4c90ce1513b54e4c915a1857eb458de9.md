### Title
Unauthorized DID Recovery Capability Retained by Former Backup Providers After DID Transfer to New Owner - (File: `chia/wallet/did_wallet/did_wallet.py`)

### Summary
`DIDWallet.transfer_did()` unconditionally carries the DID's existing `backup_ids` (recovery/backup DID list) and `num_of_backup_ids_needed` into the new owner's inner puzzle when a DID is sold or transferred to a new p2 puzzle hash. There is no parameter on this method to clear the recovery list, so the previous owner's designated "backup" DIDs retain the ability to execute a DID recovery/takeover of the singleton even after ownership has passed to a new, unrelated party — an analog of the reported bug class where a privileged role (here, recovery authority) is not revoked when the underlying entity changes context/ownership.

### Finding Description
A Chia DID is a singleton whose inner puzzle is curried with a `p2_puzzle_or_hash` (current owner key), a `recovery_list_hash` (hash of the list of backup DIDs authorized to help recover the DID), and `num_of_backup_ids_needed`. These are produced by `did_wallet_puzzles.create_innerpuz()`: [1](#0-0) 

When a DID owner sells/transfers the DID to a new owner via `DIDWallet.transfer_did()`, the new inner puzzle hash is computed with `did_wallet_puzzles.get_inner_puzhash_by_p2(...)`, but the call unconditionally passes `backup_ids=self.did_info.backup_ids` and `backup_required=self.did_info.num_of_backup_ids_needed` — the exact recovery configuration from before the transfer — with no option to reset it: [2](#0-1) 

The same pattern occurs in the lower-level helper `get_innerpuz_for_new_innerhash()`, whose own docstring/comment explicitly flags this as an issue that the *seller* must remember to handle manually: [3](#0-2) 

```
# Note: the recovery list will be kept.
# In a selling case, the seller should clean the recovery list then transfer to the new owner.
```

Because the DID recovery mechanism authorizes any DID in `backup_ids` (up to `num_of_backup_ids_needed` signatures) to execute a recovery spend that changes the DID's `p2_puzzle_or_hash` (i.e., seize control of the singleton, see the recovery flow and `find_lost_did`/recovery matching logic), any DID previously listed as a backup provider by the seller retains the capability to recover/take over the coin belonging to the new owner, unless the seller (a party who may be malicious, careless, or simply no longer trusted) explicitly clears the list before transferring: [4](#0-3) 

This mirrors the Palmera finding precisely: an identity (a "backup DID"/recovery role holder) that had a privileged capability over an object in one ownership context is not automatically stripped of that capability when the object changes hands into a new context, and the security burden is silently placed on the outgoing party ("the seller should clean the recovery list") rather than being enforced by the protocol/wallet code.

### Impact Explanation
If a DID is sold/transferred on a marketplace, the buyer receives what looks like exclusive ownership (new p2 puzzle hash), but any DID the previous owner had listed in `backup_ids` still has recovery authority over the singleton. A malicious seller can:
1. Add their own secondary DID (or a DID they still control) to the recovery list before selling.
2. Transfer/sell the DID to a buyer using `transfer_did`, which silently preserves the recovery list.
3. Later use the still-authorized backup DID to execute a recovery spend and reclaim/seize the DID coin from the new owner, since the recovery mechanism only checks the curried `recovery_list_hash`, not any notion of "current legitimate owner intent."

This results in unauthorized access control / coin takeover of an asset the victim believes they fully own — a concrete unauthorized coin-movement / ownership-theft scenario reachable purely by a wallet user's own DID transfer action combined with a subsequent spend bundle from the retained backup DID.

### Likelihood Explanation
This is reachable by any ordinary wallet/marketplace participant with no special privileges: a seller only needs to populate `backup_ids` on their own DID (a normal DID wallet feature) prior to selling it, and the vulnerability requires no additional cooperation, bug, or race condition from the buyer. The protocol code itself documents this as a known risk ("the seller should clean the recovery list") but does not enforce it — there is no warning, no default reset, and no separate opt-in parameter exposed on `transfer_did`.

### Recommendation
- Modify `DIDWallet.transfer_did()` to default to resetting `backup_ids`/`num_of_backup_ids_needed` to empty/zero unless the caller explicitly opts to preserve the recovery list (invert the current default), matching how `reset_recovery_list()` is already used elsewhere in the wallet.
- Surface this decision clearly in the RPC/CLI transfer commands (`DidTransferDidCMD`) with recovery preservation defaulting to `False`, and document the risk plainly to marketplace integrators.
- Consider adding wallet-level validation/warning when accepting a transferred DID whose recovery list is non-empty, so buyers are alerted that former backup DIDs retain recovery authority.

### Proof of Concept
1. Alice creates DID A and sets `backup_ids = [Alice_secondary_DID]`, `num_of_backup_ids_needed = 1` (a normal DID recovery configuration).
2. Alice calls `transfer_did(new_puzhash=Bob_p2_hash, ...)` to sell DID A to Bob. Per `chia/wallet/did_wallet/did_wallet.py:805-843`, the resulting coin's inner puzzle still curries `backup_ids=[Alice_secondary_DID]`.
3. Bob receives the DID and, from the wallet UI, sees it as his DID with a new owner key — with no indication that `Alice_secondary_DID` retains recovery rights.
4. Alice later initiates a DID recovery spend using `Alice_secondary_DID`'s signature against the recovery puzzle (satisfying `num_of_backup_ids_needed`), successfully changing the DID's owner puzzle hash back to one Alice controls — reclaiming the singleton out from under Bob.

```python
def create_innerpuz(
    p2_puzzle_or_hash: Program | bytes32,
    recovery_list: list[bytes32],
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list_hash: Program | None = None,
) -> Program:
    """
    Create DID inner puzzle
    :param p2_puzzle_or_hash: Standard P2 puzzle or hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :param recovery_list_hash: Recovery list hash
    :return: DID inner puzzle
    Note: Receiving a standard P2 puzzle hash wouldn't calculate a valid puzzle, but
    that can be useful if calling `.get_tree_hash_precalc()` on it.
    """
    backup_ids_hash: Program | bytes32 = Program.to(recovery_list).get_tree_hash()
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash
    singleton_struct = Program.to((SINGLETON_TOP_LAYER_MOD_HASH, (launcher_id, SINGLETON_LAUNCHER_PUZZLE_HASH)))
    return DID_INNERPUZ_MOD.curry(
        p2_puzzle_or_hash, backup_ids_hash, num_of_backup_ids_needed, singleton_struct, metadata
    )
```
