## Finding

### Title
Unvalidated commit-status `target_url` flows into `IRefCheck.htmlUrl` and is passed unfiltered to `shell.openExternal` - (File: `app/src/lib/ci-checks/ci-checks.ts`)

### Summary
`apiStatusToRefCheck` copies the API's `target_url` field verbatim into `IRefCheck.htmlUrl` with no scheme/protocol validation, and this value is later handed directly to `dispatcher.openInBrowser` / `shell.openExternal` when a user clicks to view a check.

### Finding Description
`apiStatusToRefCheck` builds an `IRefCheck` from a legacy commit-status API object and sets `htmlUrl: apiStatus.target_url` with no sanitization or scheme check: [1](#0-0) 

`IRefCheck.htmlUrl` is typed as a plain `string | null`, with no indication or enforcement that it must be `http(s)`: [2](#0-1) 

That value is consumed in `CICheckRunPopover.onViewCheckDetails`, which uses `checkRun.htmlUrl` as-is (falling back to the PR URL only when `htmlUrl` is `null`) and passes it straight to `dispatcher.openInBrowser(url)`: [3](#0-2) 

Similarly, `getCheckRunStepURL` concatenates `checkRun.htmlUrl` with a step fragment and returns it unmodified for `onViewJobStep`: [4](#0-3) 

I traced the client-side chain (`ci-checks.ts` → `ci-check-run-popover.tsx` → `dispatcher.openInBrowser` → `openExternal` IPC proxy) and found no protocol allow-list or validation at any of these layers: [5](#0-4) [6](#0-5) 

**Important caveat / unverified step:** I was not able to inspect the main-process handler that registers the `'open-external'` IPC channel (in `app/src/main-process/main.ts`) within the available iterations. That handler is the actual final sink that would call Electron's `shell.openExternal`, and it is possible — but not confirmed by what I reviewed — that protocol filtering exists there. Without seeing that code, I cannot conclusively state that a `file://` or `javascript:` URL reaches `electron.shell.openExternal` unfiltered. This should be verified directly in `app/src/main-process/main.ts` before treating this as fully confirmed.

Note also that the specific `onViewCheckExternally` callback referenced in the question (in `ci-check-run-list-item.tsx`/`ci-check-run-step-list-header.tsx`) is a prop that is not wired up by `CICheckRunPopover` in the code I reviewed — the popover instead uses `onViewCheckDetails`, which follows the vulnerable path described above.

### Impact Explanation
If the final IPC handler does not validate the URL scheme, an attacker who can set a commit status's `target_url` on a repository the victim has open in GitHub Desktop (e.g., via a malicious/compromised CI integration with `repo:status` write access) could cause `shell.openExternal` to be invoked with a `file://` URL, potentially exposing local files via the OS file handler, or otherwise abuse non-http(s) schemes registered on the victim's machine.

### Likelihood Explanation
Medium-to-Low. It requires an attacker-controlled source able to write commit statuses to the target repository (this generally requires a GitHub App/CI integration with status-write permission, not merely public read access), and it requires the user to actively click "View check"/"View job step" in the CI checks popover. This is within the stated scope (attacker-controlled GitHub API object) but is gated by the need for status-write access.

### Recommendation
- Add explicit `http:`/`https:` scheme validation (e.g., via `new URL(url).protocol`) in `apiStatusToRefCheck` before assigning `htmlUrl`, or centrally in `getCheckRunStepURL`/`onViewCheckDetails`/`onViewJobStep`, rejecting or nulling out non-http(s) URLs.
- Additionally (defense in depth), validate the URL scheme in the `openExternal` proxy (`app/src/ui/main-process-proxy.ts`) and/or in the main-process `'open-external'` IPC handler, so that no caller can trigger `shell.openExternal` with a non-http(s) URL regardless of source.

### Proof of Concept
```ts
// app/src/lib/ci-checks/ci-checks.ts
const maliciousStatus = {
  id: 1,
  state: 'failure',
  context: 'ci/build',
  target_url: 'file:///etc/passwd', // or 'javascript:alert(1)'
} as IAPIRefStatusItem

const check = apiStatusToRefCheck(maliciousStatus)
// check.htmlUrl === 'file:///etc/passwd'  -- unvalidated

// In CICheckRunPopover.onViewCheckDetails:
// url = check.htmlUrl ?? prUrl  -> 'file:///etc/passwd'
// this.props.dispatcher.openInBrowser(url) is called with the raw scheme
```

**Verification still needed:** inspect `app/src/main-process/main.ts`'s `'open-external'` handler to confirm whether it performs scheme filtering before calling Electron's `shell.openExternal`. If it does not, this finding is confirmed as exploitable; if it does, the vulnerability is mitigated at that layer and this report should be downgraded/rejected.

```typescript
export function getCheckRunStepURL(
  checkRun: IRefCheck,
  step: IAPIWorkflowJobStep,
  repository: GitHubRepository,
  pullRequestNumber: number
): string | null {
  if (checkRun.htmlUrl === null && repository.htmlURL === null) {
    // A check run may not have a url depending on how it is setup.
    // However, the repository should have one; Thus, we shouldn't hit this
    return null
  }

  const url =
    checkRun.htmlUrl !== null
      ? `${checkRun.htmlUrl}/#step:${step.number}:1`
      : `${repository.htmlURL}/pull/${pullRequestNumber}`

  return url
}
```

  private onViewCheckDetails = (checkRun: IRefCheck): void => {
    if (checkRun.htmlUrl === null && this.props.repository.htmlURL === null) {
      // A check run may not have a url depending on how it is setup.
      // However, the repository should have one; Thus, we shouldn't hit this
      return
    }

    // Some checks do not provide htmlURLS like ones for the legacy status
    // object as they do not have a view in the checks screen. In that case we
    // will just open the PR and they can navigate from there... a little
    // dissatisfying tho more of an edgecase anyways.
    const url =
      checkRun.htmlUrl ??
      `${this.props.repository.htmlURL}/pull/${this.props.prNumber}`

    this.props.dispatcher.openInBrowser(url)
    this.props.dispatcher.incrementMetric('viewsCheckOnline')
  }
