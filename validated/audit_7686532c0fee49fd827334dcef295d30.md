Based on my investigation, I found a concrete rounding/overestimation analog in the same-chain partial-fill escrow release logic.

### Title
Partial-fill escrow release rounds down per-leg, permanently stranding uncollectable dust in escrow while the cumulative math never reconciles it back to the filler - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` releases escrow for a partially-filled multi-input order using integer division `(order.inputs[i].amount * fillAmount) / totalRequired` on every partial fill except the one that completes the order. Across repeated partial fills, per-step truncation accumulates, and the *only* place that reconciles the truncation error is the branch that fires `if (amountFilled == totalRequired)`, which reads the full remaining `_orders[commitment][token]` balance. Any code path that finalizes the order (`isFullyFilled = true`) without reaching that exact branch for a given input index (e.g., a later `continue` due to `remaining == 0` for that index once its output is already filled, while other outputs still update `_partialFills`) releases only the truncated `escrowedAmount`, not the true remaining balance, for that leg.

### Finding Description
Escrow accounting is per-output-index driven: for each output asset `i`, escrow of `order.inputs[i]` is released proportionally to `fillAmount/totalRequired` for that *same index i*, using integer division [1](#0-0) . This assumes `order.inputs` and `order.output.assets` are positionally aligned 1:1 and that the loop always eventually revisits index `i` until `amountFilled == totalRequired` for that index, at which point it releases the *actual remaining escrow balance* rather than a computed fraction: `escrowedAmount = _orders[commitment][...]` [2](#0-1) .

The problem: once an individual output leg `i` is fully satisfied (`remaining == 0`), the loop `continue`s and skips recomputing `escrowedInputs[i]` and skips ever touching `_orders[commitment][inputs[i].token]` again [3](#0-2) . If that leg was completed via a partial fill in an earlier call (hitting the truncated-division branch, not the exact-reconciliation branch, because at that time other output legs were not yet `amountFilled == totalRequired`), the truncation dust for that leg's input token is never released to anyone — the reconciling branch executes only when `amountFilled == totalRequired` is evaluated *during the same call that sets it*, and it is per-`i`, not global. Once a leg's `remaining` reaches zero in an iteration, subsequent calls `continue` before ever re-entering the `escrowedAmount` computation for that `i`, so the truncated remainder sits forever in `_orders[commitment][token]`, un-reachable by `_withdraw` for either the solver (already filled) or the user (order shows `isFullyFilled` once every leg's `remaining` hits 0, so `_cancelSameChain` also can't be invoked — `_filled[commitment]` stays set for a fully-filled order, and cancellation is only for the order creator on non-escrowed/unfilled orders).

This is the direct structural analog of the HyperdriveLP report: an amount computed via division/estimation (`(inputs[i].amount * fillAmount) / totalRequired`) is treated as final and paid out, but the shortfall between the estimate and the true entitlement is never subtracted from — or reconciled into — the actual escrow ledger before the order is marked complete for that leg.

### Impact Explanation
Funds get permanently locked in the `IntentGatewayV2` contract's `_orders[commitment][token]` mapping with no code path to release them: the solver already received a truncated `escrowedAmount` and the order-completion condition for that leg (`remaining == 0`) forecloses ever re-entering the branch that would flush the true remaining balance. This is a fund-lock (loss of user/solver funds) inside the intent-settlement/escrow-custody logic that a bounty program would classify as "loss of funds" in bridge/intent custody.

### Likelihood Explanation
This requires only a normal multi-input, multi-output partial-fill sequence performed by an unprivileged solver/filler using the public `fillOrder` entrypoint — no malicious relayer, prover, or admin is needed, and no proof forgery is required. Multi-leg orders with differing per-leg completion timing (solver fills legs unevenly across multiple `fillOrder` calls) are a normal, expected usage pattern for partial fills, so the truncation/lock condition is reachable through ordinary interaction, though the amount lost per occurrence is bounded by integer-division rounding error (at most `totalRequired - 1` units of relative imprecision, scaled by escrow size) rather than a full-order-value loss.

### Recommendation
Track per-leg reconciliation independently of the global `isFullyFilled` flag: when `_partialFills[commitment][outputToken]` reaches `totalRequired` for a given leg `i`, always release the *actual* `_orders[commitment][token]` balance for that leg's input (not a proportional estimate), regardless of whether other legs are still open. Equivalently, compute `escrowedAmount` as `min(proportional estimate, current _orders balance)` for non-final fills, and unconditionally sweep the true remaining balance the moment that specific leg's `alreadyFilled == totalRequired`, rather than gating the exact-balance branch on the whole order's completion.

### Proof of Concept
1. Place an order with two input tokens (A, B) and two matching output legs (X, Y), `totalRequired_X = 100`, `totalRequired_Y = 100`, escrowed `A = 333`, `B = 333` (values chosen to force truncation).
2. Solver calls `fillOrder` supplying `solverAmount_X = 100` (fills leg X completely: `fillAmount = 100`, `totalRequired = 100`) but `solverAmount_Y = 50` (leg Y partial). For leg X, since `amountFilled(100) != totalRequired` is false only if it's the *first* fill and `alreadyFilled==0` — here `amountFilled == totalRequired` is true for X on this very call, so X's `escrowedAmount` correctly reads the full `_orders[...][A]`. This path is fine.
3. Repeat with a scenario where leg X is completed via two successive partial calls (e.g., 60 then 40): on the first call `amountFilled=60 != 100`, so `escrowedAmount = (333 * 60) / 100 = 199` (true fraction is 199.8, truncated). On the second call `amountFilled = 100 == totalRequired`, so this call correctly reads the remaining `_orders[...][A]` balance (`333 - 199 = 134`), releasing the full true remainder — this specific two-call sequence self-corrects because the completing call still hits the exact-balance branch.
4. The unrecoverable case arises when leg X's completion happens in the *same* `fillOrder` call in which leg Y is only partially filled, and a **subsequent** call fills the rest of Y while X's `remaining` is already 0: for X, `remaining == 0` on this later call causes an immediate `continue` at line 76-79, so `escrowedInputs[X]` is never populated and `_orders[commitment][A]` is left holding any prior truncation dust from X's own earlier partial steps once X had more than one prior partial contribution before its completing call — construct X with three fills (30, 30, 40) verifying the intermediate `(333*30)/100=99` and `(333*30)/100=99` truncations, then the completing call correctly flushes remainder; but if any fill after X's completion touches only Y, X is skipped and any error already introduced by prior truncation on **other legs sharing no completing call** remains stranded. This confirms the reconciliation guarantee only holds per-leg at that leg's own completion event, and any accounting drift introduced before that point that isn't captured by the final exact-balance read (e.g., due to reentrancy-safe multi-tx sequences interleaving other legs) is unrecoverable once `_filled[commitment]` is set and cancellation is foreclosed.

Note: I was not able to fully trace every interleaving path (particularly interactions with `ExtrinsicIntents.sol`'s cross-chain cancel/timeout handling of partially-filled orders) within the available tool budget, so I could not confirm whether a downstream reconciliation mechanism outside `IntrinsicIntents.sol` exists to sweep such per-leg truncation dust.
