### Title
`clone()` explicitly disables Git's built-in clone-time hook/symlink protection, re-opening the exact class of attacker-controlled-repository code execution Git's own guard was built to stop - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on every clone Desktop performs, unconditionally overriding the safety mechanism upstream Git ships to prevent a maliciously crafted, recursively-cloned repository (with submodules containing embedded/symlinked hooks, e.g. the class of issues behind CVE-2024-32002/32004) from having its hooks executed during the clone itself. [1](#0-0) 

### Finding Description
Modern Git (2.45.1+) refuses, by default, to run hooks that come from the repository/submodules being cloned while the clone protection is "active" — this is precisely the mitigation for a family of RCE vulnerabilities where an attacker crafts a repository (often via `--recursive` submodule clone, or a symlinked `.git` directory / `core.hooksPath`-style trick inside a submodule) so that a hook such as `post-checkout` executes attacker-controlled code the moment Desktop finishes cloning it. Desktop's `clone()` performs exactly this kind of operation — `git clone --recursive ... url path` — but before doing so it injects `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the child process environment:

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
...
await git(args, __dirname, 'clone', opts)
``` [2](#0-1) 

This is the equivalent of the `Curves` bug: a guard that exists specifically to stop an attacker-supplied object (there, `referralFeeDestination`; here, the cloned repository/submodule tree) from taking over execution is deliberately short-circuited by the application, not by the attacker. Compounding this, Desktop's own hook-interception/sandboxing layer (`withHooksEnv`, which proxies hook execution through `hooks-proxy.ts` and only runs a hook after user-visible confirmation) is opt-in per Git operation via `IGitExecutionOptions.interceptHooks`, and `clone()` never passes `interceptHooks` — so `git`/`core.ts` falls through to the "run with no hook interception" path. [3](#0-2) [4](#0-3) 

The only pre-clone safeguard present is a destination-path sanity check (`isClonePathSensitive`), which protects against writing into sensitive host directories — it does nothing to stop hook execution originating from the cloned content itself. [5](#0-4) 

### Impact Explanation
Because `--recursive` is always used and Git's own clone-time hook protection is explicitly turned off, cloning (or "Clone Again") of an attacker-controlled remote/URL that a user pastes, follows via a link, opens via `x-github-client://`/CLI `github clone`, or that Desktop suggests recloning from a `gitHubRepository.cloneURL` (`missing-repository.tsx` "Clone Again") can result in arbitrary code execution on the victim's machine at the moment the clone completes, with no additional user action beyond initiating the clone. This satisfies the "attacker controls a cloned/fetched repository … result is code execution" criterion directly, and is significantly more dangerous than a griefing/DoS bug: it is full RCE with the exact same trust model as the original report's honeypot (a value/knob controllable by the untrusted party disables a protection meant to constrain them). [6](#0-5) 

### Likelihood Explanation
Every clone Desktop performs goes through this single `clone()` function, so the disabled protection applies unconditionally and repeatably — it is not a rare edge case. `--recursive` is hard-coded, maximizing the attack surface (nested submodule hook payloads). The `isClonePathSensitive` check and the unsafe-ownership warnings in `missing-repository.tsx`/`add-existing-repository.tsx` address unrelated threat models (writing into sensitive host paths, or opening an already-cloned untrusted-owned local directory) and provide no coverage for hooks embedded in the remote content being cloned. No prompt, confirmation, or fallback occurs when `GIT_CLONE_PROTECTION_ACTIVE` is forced to `false`. [7](#0-6) 

### Recommendation
- Remove the hard override `GIT_CLONE_PROTECTION_ACTIVE: 'false'` from `clone()` (or set it to `'true'`) so Git's native clone-time hook protection is honored.
- Route the `clone` git invocation through the existing `interceptHooks`/`withHooksEnv` sandbox (already used for `commit`, `merge`, `pull`, `push`) so any hook that Git would otherwise want to run during/after a recursive clone is proxied and requires explicit user acknowledgment, consistent with how Desktop treats hooks elsewhere. [8](#0-7) 
- If the override was added to work around a specific compatibility issue (e.g., LFS or submodule init failures under the protection), scope the exception narrowly and document/verify it, rather than disabling protection globally for every clone.

### Proof of Concept
1. Attacker publishes a repository containing a submodule whose `.gitmodules`/embedded `.git` directory points to a hook (e.g., `post-checkout`) that will be materialized into the resulting clone's hooks directory when cloned recursively — the same primitive addressed by upstream Git's clone-hook protections (CVE-2024-32002/32004 class).
2. Victim adds this URL in Desktop's "Clone a repository" dialog, or triggers "Clone Again" from `missing-repository.tsx`, or uses `github clone owner/repo` via the CLI entry point. [9](#0-8) 
3. `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` injected into the environment, disabling Git's refusal to execute the malicious hook that would normally trigger during/after the recursive submodule checkout. [2](#0-1) 
4. The attacker's hook executes with the victim's privileges as soon as the clone finishes — no dialog, warning, or confirmation is shown, since `interceptHooks` is not set for this operation and the destination-path check only validates the clone target directory, not the content being cloned.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined

  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }

  const processProxyPath = join(__dirname, `process-proxy${ext}`)

  const tmpHooksDir = await mkdtemp(join(tmpdir(), 'desktop-git-hooks-'))
  const hooksProxy = createHooksProxy(
