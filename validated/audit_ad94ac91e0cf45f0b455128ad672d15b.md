## Analog Found: Git argument injection via misplaced `--` separator in branch checkout

### Title
Argument Injection via Attacker-Controlled Branch Names in `checkoutBranch` — ([File: app/src/lib/git/checkout.ts])

### Summary
The original report is about an admin failing to bound/validate numeric and structural inputs (`claimTimeout`, `withdrawTimeout`, fee sums, `startsAt`) in `LP.sol`, letting an out-of-range value break protocol invariants. The Desktop analog is the same class of bug — **missing/incomplete validation of an externally supplied value before it is used as a trusted, structural parameter** — but the untrusted input here is a **branch name coming from a deep link (`x-github-client://openRepo/...`) or a remote repository**, and the "invariant" broken is *"the branch name is always passed as a ref, never as a git option."*

### Finding Description
`parseAppURL` extracts a `branch` query parameter from an `x-github-client://openrepo/...` deep link and validates it only with `testForInvalidChars`: [1](#0-0) 

That regex rejects control characters, `~^:?*[\|"<>`, `@{`, leading/trailing dots, `.lock` suffix, and trailing `/` — but it **does not reject a leading `-`**, even though a leading dash is fully valid for `sanitizedRefName`'s stripping logic (`.replace(/^[-\+]*/g, '')`) elsewhere, meaning the codebase itself is aware that leading dashes are a hazard, just not everywhere it needs to be. [2](#0-1) 

This unsanitized `branch` value flows into `Dispatcher.openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch`, which eventually resolves/creates a `Branch` and calls `checkoutBranch`: [3](#0-2) 

`checkoutBranch` builds its git arguments via `getBranchCheckoutArgs`, which places `branch.name` **before** the `--` end-of-options marker instead of after it: [4](#0-3) 

Because `--` only protects arguments that come *after* it, `branch.name` is not shielded at all — it is the exact opposite pattern used correctly elsewhere in the same file for path arguments (e.g. `checkoutPaths` and `checkoutConflictedFile` put `--` before the untrusted values): [5](#0-4) 

If a ref name beginning with `-` reaches this code (Git itself permits refs to start with `-`; only `sanitizedRefName` — not `testForInvalidChars` — strips that prefix), `git checkout` will interpret it as a command-line flag instead of a ref, e.g. a branch literally named `--orphan` or `-f`/`--force` would silently change checkout semantics (force-discarding local changes, creating an orphan branch, etc.) instead of failing as "branch not found."

### Impact Explanation
This breaks the invariant that a ref-name value is always treated as data, never as an option, when handed to `git checkout`. An attacker who controls a remote/forked repository (e.g. creating a branch named `-f` or `--orphan`) combined with a crafted `x-github-client://openrepo/...?branch=...` link that an unprivileged victim clicks can cause Desktop to invoke `git checkout` with attacker-chosen flags instead of a plain ref argument. Depending on the flag, this can silently discard the user's uncommitted local changes (`-f`/`--force`), rewrite history state (`--orphan`), or otherwise corrupt what the user believes they are checking out — matching the "silent corruption of what the user commits" impact class. The path is reachable purely through remote content (branch name) and a link click, with no local access, admin rights, or prior compromise required.

### Likelihood Explanation
Moderate: it requires (1) an attacker to control a repository with an attacker-named branch, and (2) the victim to click a crafted `x-github-client://openrepo` deep link (or a CLI `--cli-clone`/`--cli-branch` invocation) referencing that branch/repo. Both are attacker-achievable without any elevated privileges, similar in spirit to the original report's "compromised/careless admin, low likelihood, high impact" framing — here it's "attacker-controlled repo + one user click, moderate likelihood, meaningful impact."

### Recommendation
- Extend `testForInvalidChars` (or add a dedicated check) in `app/src/lib/parse-app-url.ts` to reject branch names beginning with `-`, mirroring the stripping already done by `sanitizedRefName`.
- Fix `getBranchCheckoutArgs` in `app/src/lib/git/checkout.ts` to place `branch.name` **after** the `--` separator (or use `--` immediately preceding it) so Git can never interpret it as an option, consistent with `checkoutPaths`/`checkoutConflictedFile`.
- Apply the same audit to any other git-argument-building helper that accepts branch/ref names sourced from deep links, CLI args, or remote data (e.g. `getBranchCheckoutArgs`-style helpers for other commands).

### Proof of Concept
1. Attacker creates/pushes a branch literally named `--orphan` (or `-f`) to a repository they control.
2. Attacker sends the victim a link: `x-github-client://openrepo/https://github.com/attacker/repo?branch=--orphan`.
3. `parseAppURL` accepts `--orphan` as a valid branch because `testForInvalidChars` does not flag leading dashes.
4. `openBranchNameFromUrl` → `checkoutLocalBranch` → `checkoutBranch` runs `git checkout --orphan -- ` effectively, because `getBranchCheckoutArgs` returns `['--orphan', '--']` before the "checkout" args are combined — `git` parses `--orphan` as the `--orphan` option rather than a ref name, silently altering the checkout behavior instead of failing with "branch not found."

Note: I could not directly inspect the implementation of `Dispatcher.checkoutLocalBranch` (only its call site) within the available index, so I could not 100% confirm whether it always resolves to a matching, git-rules-compliant `Branch` before calling `checkoutBranch`, or whether it can also fall through to `git branch <raw-name>`/`git checkout -b <raw-name>` with the raw string. If it starts a Devin session, the engineer should trace `checkoutLocalBranch`'s full body to confirm the exact code path and adjust the PoC accordingly.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

export async function checkoutPaths(
  repository: Repository,
  paths: ReadonlyArray<string>
): Promise<void> {
  await git(
    ['checkout', 'HEAD', '--', ...paths],
    repository.path,
    'checkoutPaths'
  )
}
