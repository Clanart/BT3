Based on what I was able to verify, the strongest analog to the reported bug class ("attacker-controlled data used to reach a privileged operation while bypassing the intended validation gate") is the branch-name validation used for the `x-github-client://openRepo/...` deep link.

### Title
Deep-link `branch` parameter bypasses ref-name validation and reaches `git checkout` as a raw argument - (File: app/src/lib/parse-app-url.ts)

### Summary
The GitHub Desktop protocol handler accepts `x-github-client://openRepo/<url>?branch=<name>` deep links from any web page or link the user clicks. The `branch` value is treated as trusted input and validated only against `testForInvalidChars`, whose regex does not reject a leading `-`. This value is forwarded unmodified into the checkout pipeline reached from `openBranchNameFromUrl`.

### Finding Description
`parseAppURL` validates the `branch` query parameter using `testForInvalidChars`, which is backed by `invalidCharacterRegex` defined in `sanitize-ref-name.ts`: [1](#0-0) 

That regex blocks control characters, spaces, `~^:?*[\|"<>`, `@{`, consecutive dots, leading/trailing dots, and `.lock`/trailing-slash suffixes, but it does **not** reject a leading `-`/`--`. Contrast this with `sanitizedRefName`, used elsewhere for user-typed branch names, which additionally strips a leading `-`/`+` prefix via `.replace(/^[-\+]*/g, '')` — a mitigation that `testForInvalidChars` (used for the deep-link path) does not apply: [2](#0-1) 

The `branch` value that survives this check is passed to `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl`, which clones/opens the target repository, fetches it, and then checks the attacker-supplied string out directly: [3](#0-2) 

This mirrors the structure of the original report: a user-facing entry point (`deployAccount`'s `initializer` / here, the `branch` query parameter) is validated only superficially, and the unvalidated remainder is handed to a downstream privileged sink (`initialize` call / here, the `git checkout` invocation) whose behavior depends entirely on whether that value is treated as data or as a command option.

### Impact Explanation
If the value ultimately reaches a `git` invocation without an explicit `--` separator isolating it as a positional ref argument (a detail I could not confirm from `app/src/lib/git/checkout.ts` within this session), a value such as `--orphan=x` or other `git checkout` option flags supplied via the `branch` query parameter could alter checkout behavior in ways unintended by the user — this is the classic git argument-injection primitive. Even absent argument injection, this is at minimum a validation-gap in the deep-link path (missing leading-dash stripping present in the sibling `sanitizedRefName` function), which is the exact broken invariant described in the report: the "trusted" sanitizer for this attacker-reachable entry point is weaker than the sanitizer used elsewhere for the same kind of value.

### Likelihood Explanation
The `x-github-client://openRepo/...` protocol is registered as a default handler and triggered purely by the victim clicking a link (e.g., an "Open in Desktop" button on any web page), matching the required "attacker controls a link the user clicks" primitive with no local access, admin rights, or prior compromise needed. Whether it is fully exploitable for code execution depends on unverified downstream argument handling in `git/checkout.ts`.

### Recommendation
Apply the same leading `-`/`+` stripping used in `sanitizedRefName` to the `testForInvalidChars` validation path in `app/src/lib/parse-app-url.ts`, or reject any `branch` value beginning with `-` outright. Additionally, audit `app/src/lib/git/checkout.ts` and any other git command builders that consume deep-link-supplied ref names to ensure a literal `--` precedes user-supplied ref arguments, consistent with git's own recommended defenses against argument injection.

### Proof of Concept
1. Host a link: `x-github-client://openRepo/https://github.com/some/repo?branch=--orphan%3Dpwn`
2. Victim (with Desktop installed and registered as the protocol handler) clicks the link.
3. `parseAppURL` accepts `--orphan=pwn` as a "valid" branch name since `testForInvalidChars` does not flag a leading `-`.
4. `openBranchNameFromUrl` clones/fetches the repo and calls the checkout pipeline with this raw string, unlike the equivalent manually-typed-branch code path which strips leading dashes via `sanitizedRefName`.

Note: I could not confirm within this session the exact command-line construction in `app/src/lib/git/checkout.ts` (e.g., whether a `--` separator is present before the branch argument), so I cannot state with certainty that this specific PoC achieves code execution — only that the validation gap itself is confirmed and inconsistent with the sanitizer used for the equivalent manually-entered-branch code path.

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

  }
