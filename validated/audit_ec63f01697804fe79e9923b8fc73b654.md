## Analog Identification

The Sherlock finding is about an operation whose failure mode is not checked (`ERC20.transfer` returning `false` instead of reverting), so the caller assumes success and the invariant "asset actually moved" silently breaks, leaving stuck value. The closest Desktop analog is in the Copilot merge-conflict-resolution write path, where a safety check (`resolveWithin`) can legitimately return a "failure" sentinel (`null`) for a single file, but the code only logs it and keeps going — the caller (`onContinue`) is never told a file failed, and it unconditionally finalizes the merge/rebase/cherry-pick.

### Title
Silent skip of unsafe file write in Copilot conflict resolution lets unresolved conflict markers be committed - (File: app/src/lib/stores/app-store.ts)

### Summary
`AppStore._applyCopilotConflictResolutions` writes Copilot's resolved content back to each conflicted file before the app proceeds to finish a merge/rebase/cherry-pick. For every resolution it re-validates the target path with `resolveWithin(repository.path, resolution.path)` [1](#0-0)  . If that check fails (returns `null`, meaning the path resolves outside the repository, e.g. because the on-disk entry is/became a symlink), the function only calls `log.warn` and `continue`s to the next file — it does not abort, does not remove the file from the "resolved" set surfaced to the UI, and does not signal failure to its caller.

### Finding Description
`_applyCopilotConflictResolutions` iterates `copilotResolutions` and, for ordinary text conflicts, does:
```
const absolutePath = await resolveWithin(repository.path, resolution.path)
if (absolutePath === null) {
  log.warn(`Copilot resolution skipped: path outside repository: ${resolution.path}`)
  continue
}
...
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
``` [2](#0-1) 

Crucially, the calling UI code does not check whether every file was actually written — it treats the call as fire-and-forget and immediately continues the in-progress git operation:
```
await this.props.dispatcher.applyCopilotConflictResolutions(this.props.repository)
await this.props.onContinueAfterConflicts()
``` [3](#0-2) 

The broken invariant: the app's model of "the merge is fully resolved and safe to conclude" no longer matches reality once even one file's resolved content failed to be written. Unlike the original `buildConflictContext` step, which records a `skippedReason` that is surfaced back into the model prompt and dialog data [4](#0-3) , the *second*, apply-time `resolveWithin` check in `app-store.ts` has no equivalent user-visible signal — it is a bare `log.warn`. Since `resolveWithin` is re-evaluated at apply time (potentially long after the resolutions were computed and reviewed in the dialog), a path that was safe when the context was built can legitimately fail this second check (e.g. the working-tree entry for that path changed between build time and "Continue" click), causing that specific file's on-disk content — including the literal `<<<<<<<`/`=======`/`>>>>>>>` conflict markers — to remain untouched while the app proceeds to finish the merge/rebase/cherry-pick as if everything had been resolved.

### Impact Explanation
This is a silent corruption of what the user commits: the merge operation is marked complete and the user is taken past the conflict-resolution UI, but the actual file on disk for the skipped path still contains unresolved (or partially resolved) conflict-marker text. The user has no indication anything went wrong — only a debug log line is emitted — and can go on to `git add`/commit that file, baking raw conflict markers or unmerged content into the permanent history that gets pushed to the remote, exactly analogous to the ERC20 report's "transfer silently fails but the caller proceeds as if it succeeded, leaving stuck/corrupted state."

### Likelihood Explanation
The path is reachable any time a user resolves conflicts via the Copilot flow for merges/rebases/cherry-picks involving remote branches or PRs — content an attacker can fully control (a malicious "theirs" branch/PR). The severity is capped because it requires the on-disk state at the target path to differ between context-build time and apply time (e.g., a race with another process, or the conflicted entry being/becoming a symlink), so it is not trivially triggerable on every conflict, only medium-likelihood.

### Recommendation
Treat a `null` result from the apply-time `resolveWithin` check as a hard failure of the whole "apply resolutions" operation rather than a per-file `continue`: abort `_applyCopilotConflictResolutions`, surface an explicit error to `onContinue` (so `onContinueAfterConflicts()` is never invoked), and require the user to re-run/re-review conflict resolution for the affected file rather than silently finishing the git operation with stale conflicted content on disk.

### Proof of Concept
1. Trigger a merge/rebase/cherry-pick against an attacker-controlled branch/PR that produces a text conflict on `notes.txt`.
2. Run "Resolve with Copilot"; `buildConflictContext` successfully reads and resolves `notes.txt` (passes `resolveWithin` at build time) [4](#0-3) , and the result dialog shows it as resolved.
3. Before the user clicks "Continue Merge", something changes the on-disk entity at `notes.txt` to a symlink pointing outside the repository root (e.g. a background process, another tool, or a git hook triggered by the attacker's branch).
4. The user clicks "Continue Merge" → `_applyCopilotConflictResolutions` calls `resolveWithin(repository.path, 'notes.txt')`, which now returns `null` because the symlink resolves outside root; the function logs a warning and `continue`s, never writing `notes.txt` and never adding it to `pathsToStage` [2](#0-1) .
5. `onContinue` still calls `onContinueAfterConflicts()` unconditionally [3](#0-2) , finishing the merge as though all files were resolved, while `notes.txt` on disk retains its unresolved conflict-marker content, which the user then unknowingly commits and pushes.
