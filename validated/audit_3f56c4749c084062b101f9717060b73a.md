### Title
FROST per-nonce binding factors are all identical: the rho transcript is never advanced per nonce index, collapsing the intended per-nonce binding - (File: crypto/frost/src/nonce.rs)

### Summary
In `BindingFactor::calculate_binding_factors`, the code claims to derive a distinct binding factor (`rho`) for each nonce a participant commits to, analogous to how the reference bug's per-call update step was skipped in the "claim all" path. The iterator over nonce indexes maps every index to the *same* `transcript.challenge(b"rho")` output — the transcript is never appended to or advanced between iterations, so the "per nonce" differentiation silently collapses to a single shared rho per participant. This mirrors the finding's stale `lastUpdateTimestamp`: a value intended to be refreshed per step is computed once and reused, while downstream code (`BindingFactor::bound`, `BindingFactor::nonces`, and `AlgorithmSignMachine::sign` in `crypto/frost/src/sign.rs:385-396`) consumes the vector believing each entry independently binds its nonce.

### Finding Description
`calculate_binding_factors` (crypto/frost/src/nonce.rs:161-173) does:

```rust
binding.binding_factors = Some(
  (0 .. binding.commitments.nonces.len())
    .map(|_| C::hash_binding_factor(transcript.challenge(b"rho").as_ref()))
    .collect(),
);
```

The closure ignores the nonce index and calls `transcript.challenge(b"rho")` on an unmodified transcript clone each iteration. Any sane `Transcript` implementation returns the same challenge for the same state and label, so `binding_factors[i] == binding_factors[j]` for all `i, j` of a given participant. The comment ("This generates a binding factor per nonce just to ensure it never comes up as a question") shows per-nonce factors were intended — the per-step transcript update was simply never implemented, exactly the "update omitted in the aggregate path" class of the external report.

The bound group nonce is then computed as `R_n = Σ_l (D_{l,n} + rho_l · E_{l,n})` (`nonces`, nonce.rs:194-212), and each signer's scalar nonce is `d_n + rho_l · e_n` (sign.rs:388-395). For algorithms using `nonces() > 1` (the library's multi-nonce extension; e.g. algorithms embedding multiple Schnorr proofs per FROST session, per spec/cryptography/FROST.md:28-37), FROST's binomial-nonce argument requires each nonce position to be independently bound. With `rho` shared across positions, an adversary who submits their preprocess last — participant ordering lets a malicious signer observe honest `Preprocess` messages before broadcasting their own (they are collected into `preprocesses: HashMap<Participant, Preprocess>` and only then transcripted in `sign`, sign.rs:324-368) — can solve for their `E` commitments across nonce positions as one linear system in a single unknown `rho` instead of `n` independent systems. This restores the cross-nonce degrees of freedom that per-nonce binding factors exist to remove, enabling ROS-style grinding of the aggregate nonces `R_0, …, R_{n-1}` relative to each other (e.g., forcing `R_1 = R_0 + k·G` for chosen `k`), which collapses multi-challenge algorithms' challenges and yields forgeries of the composed signature for messages/keys the honest signers never agreed to.

### Impact Explanation
Threshold signature forgery / signing of an unintended message for any `Algorithm` with `nonces().len() > 1`. The adversary controls their `Commitments` (untrusted bytes read via `read_preprocess` → `Commitments::read`, sign.rs:276-281, nonce.rs:133-139) and can adapt them after seeing honest commitments, since `rho` only commits to the preprocess transcript *after* all are received. With a single shared `rho` per participant, the attacker's `n` nonce positions are bound by only `n` effective unknowns instead of `n` independent factors, preserving the linear-algebra attack surface the binomial binding is meant to eliminate.

### Likelihood Explanation
Reachable by any signing participant (unprivileged party submitting public `Preprocess` bytes). No collusion, broken BFT, or leaked keys are required — just the ability to pick one's own commitments after observing others', which the preprocess round inherently allows. Exploitation additionally requires the concrete multi-nonce algorithm's challenge structure to admit the ROS-style relation; the code defect (identical per-nonce rhos) is unconditional and verifiable directly from the source.

### Recommendation
Append the nonce index to the transcript before each challenge so each position gets an independent factor:

```rust
binding.binding_factors = Some(
  (0 .. binding.commitments.nonces.len())
    .map(|n| {
      let mut t = transcript.clone();
      t.append_message(b"nonce_index", u64::try_from(n).to_be_bytes());
      C::hash_binding_factor(t.challenge(b"rho").as_ref())
    })
    .collect(),
);
```

(Or advance a single cloned transcript cumulatively.) The same fix should be audited wherever "per-item" challenges are generated in a loop from a shared transcript.

### Proof of Concept
Unit-level demonstration of the collapsed factors:

```rust
let mut B = BindingFactor::<C>(HashMap::new());
let commitments = Commitments { nonces: vec![nc0, nc1] }; // two nonces
B.insert(Participant::from(1u16), commitments);
B.calculate_binding_factors(&rho_transcript);
let rhos = B.binding_factors(Participant::from(1u16));
assert_eq!(rhos[0], rhos[1]); // per-nonce binding factors are identical
```

`transcript.clone()` inside the per-participant loop is fresh for each participant, and within `.map(|_| …)` no message is appended between `challenge(b"rho")` calls, so for any deterministic transcript (e.g. `DigestTranscript`/`RecommendedTranscript`, which produce state||label hashes) every element of `binding_factors` is the same scalar. Caveat: I verified the divergence between intended and actual behavior and the attack surface it preserves; a full end-to-end forgery depends on the specific multi-nonce algorithm in use and was not constructed here.
