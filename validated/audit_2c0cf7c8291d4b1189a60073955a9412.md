## Title
Silent, unconfirmed rewrite of a repository's `origin` remote URL from GitHub API data can redirect future pushes - (`File: app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` silently rewrites a repository's default git remote URL whenever the GitHub API's `clone_url` for that repository no longer matches the locally configured remote, with no user confirmation. The check that gates this rewrite only compares hostname/owner/name and protocol — it does not verify that the change is something the user initiated or expects. This mirrors the report's broken invariant: a function acts on attacker/server-controlled input (there, `msg.value`; here, `apiRepo.clone_url`, a value returned by the GitHub API) without validating that the resulting side effect (loss of ETH / silent remote rewrite) is something the caller actually intended, and it takes effect without any confirmation step.

### Finding Description
`updateRemoteUrl` is invoked from `app-store.ts` when repository metadata is refreshed from the GitHub API. The function compares the current `git remote` URL to `apiRepo.clone_url` and, if they don't match but protocols do and the remote hadn't been "manually" diverged from the last-known `GitHubRepository.cloneURL`, it calls `gitStore.setRemoteURL()` to overwrite the remote: [1](#0-0) 

The only checks performed are:
- `urlMatchesRemote` — structural comparison of hostname/owner/name [2](#0-1) 
- `protocolsMatch` — same protocol (http/https) as before [3](#0-2) 
- `remoteUrlUnchanged` — the current remote still matches the previously cached `GitHubRepository.cloneURL` [4](#0-3) 

None of these checks confirm with the user that the destination of `git push` is being changed. The `clone_url` value comes directly from the GitHub API response (`IAPIRepository`), which for repositories on GitHub Enterprise or for renamed/transferred repos is a value Desktop trusts implicitly as authoritative. If a repository is renamed, transferred to a different owner, or a server returns a different `clone_url` (e.g., an Enterprise instance where an admin or an attacker with API access changes repository metadata, or a MITM/compromised endpoint returns a modified API response), Desktop will automatically repoint the user's `origin` remote to the new URL the next time repository state is refreshed — without ever showing the user a diff, prompt, or confirmation dialog like it does for other trust-affecting operations (e.g., unsafe/untrusted directory ownership in `add-existing-repository.tsx`) [5](#0-4) .

### Impact Explanation
Because the rewrite is silent, a user who is unaware that the remote changed will continue to `git push` and `git fetch`/`git pull` believing they're interacting with the same repository. If the new `clone_url` points to a repository under attacker control (achievable if the attacker can influence what `clone_url` Desktop's GitHub API client returns for that repository — e.g., via a compromised/malicious GitHub Enterprise server, a repository transfer to an attacker-controlled namespace, or a man-in-the-middle on the API endpoint), the victim's future pushes are silently redirected to a location chosen by the attacker. This is a "silent corruption of what the user commits or pushes" per the described impact class — the user's `push` target is changed underneath them with no visible indication in the UI.

### Likelihood Explanation
This code path runs automatically as part of routine repository/account data refresh (background API calls), not gated behind any explicit user action, so it fires whenever `apiRepo.clone_url` diverges from the current remote under the stated conditions. The likelihood of triggering it depends on an attacker's ability to control the `clone_url` value returned for a given `GitHubRepository` (most plausible against GitHub Enterprise Server deployments, or scenarios of repository transfer/rename where a malicious actor gains temporary control of the destination namespace), which is a real but not universal precondition — hence "requires attacker control of a GitHub API object" per the valid-impact scope, but does not require local access, malware, or leaked credentials.

### Recommendation
Do not silently call `gitStore.setRemoteURL()` from background metadata refreshes. At minimum:
- Prompt the user with an explicit confirmation dialog showing the old and new remote URL before changing `origin`, or
- Restrict automatic updates strictly to same-owner/same-name canonical redirects that GitHub's API explicitly flags as a repository rename (if such a signal is available), and
- Log/surface the change prominently in the UI so users notice their push destination changed.

### Proof of Concept
1. User adds/clones a repository in Desktop; `GitHubRepository.cloneURL` and `git remote origin` are both `https://github.com/victim/repo.git`.
2. The associated GitHub (Enterprise) API endpoint later returns an `IAPIRepository` object whose `clone_url` is `https://github.com/attacker/repo.git` (achievable if API responses can be influenced/spoofed for that endpoint, or the repo is transferred to an attacker-controlled account and back).
3. On the next background repository refresh, `updateRemoteUrl` runs: `urlsMatch` is `false` (different owner), `protocolsMatch` is `true` (both `https:`), and `remoteUrlUnchanged` is `true` (user never manually edited the remote).
4. `gitStore.setRemoteURL('origin', 'https://github.com/attacker/repo.git')` executes silently. [6](#0-5) 
5. The user, unaware of the change, runs `git push` from Desktop; the push now goes to the attacker's repository instead of the intended one, with no warning shown.

Note: I was unable to fully trace all call sites in `app-store.ts` that invoke `updateRemoteUrl` or confirm whether any additional UI-level confirmation exists further up the call chain (only 3 references were found in `app-store.ts` and I did not read their full surrounding context) — a Devin session with full file access should verify whether any gating UI exists before treating this as fully confirmed.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
