## Title
Missing already-filled check in `_cancelFromDest` allows destination-chain cancellation to race a legitimate fill, corrupting `_filled[commitment]` and dispatching a conflicting `RefundEscrow` message alongside an already-sent `RedeemEscrow` message - (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromDest` never checks the local `_filled[commitment]` slot before overwriting it and dispatching a `RefundEscrow` message. Because this function executes directly on the destination chain (where `_filled` already lives), it has trivial local access to the exact information that `_cancelFromSource` has to fetch via a cross-chain GET-proof, yet it skips the check entirely.

### Finding Description
`_filled` is documented as the one-time finalization marker: *"A non-zero value indicates the order has been finalized and cannot be filled again."* [1](#0-0) 

`_fillCrossChain` sets `_filled[commitment] = msg.sender` (the solver) immediately, then dispatches a `RedeemEscrow` post request to the source chain to pay the solver back out of escrow: [2](#0-1) [3](#0-2) 

`_cancelFromDest` allows *anyone* to call it once `order.deadline < _blockNumber()` (the `order.user` check at line 242 is only enforced pre-deadline): [4](#0-3) 

It then unconditionally overwrites `_filled[commitment]` back to `order.user` and dispatches a `RefundEscrow` message to the source chain — with **no check that `_filled[commitment]` is still `address(0)`**: [5](#0-4) 

Contrast this with `_cancelFromSource`, which is forced to use a Hyperbridge GET request specifically to remotely verify that `_filled` is empty on the destination chain before refunding — an explicit acknowledgment that this check is required for correctness: [6](#0-5) [7](#0-6) 

`_cancelFromDest` runs *on* the destination chain, so it can read `_filled[commitment]` locally with zero cost, yet it omits this same safety check that its sibling function goes out of its way to enforce cross-chain.

Because a solver can legitimately call `_fillCrossChain` up to and including the deadline block (`order.deadline >= _blockNumber()`), there exists a normal, attacker-controllable window: the very next block after a legitimate fill, `_cancelFromDest` becomes callable by *anyone* (no `order.user` gate), for the *same* order/commitment. This overwrites `_filled[commitment]` from the solver's address back to `order.user`, and dispatches a second, conflicting `RefundEscrow` message to the source chain — while the `RedeemEscrow` message from the legitimate fill is still in flight (or already delivered).

On the source-chain `onAccept`, both `RedeemEscrow` and `RefundEscrow` route to `_withdraw`, which decrements `_orders[commitment][token]` and reverts with `UnknownOrder` once the escrow for that commitment/token reaches zero: [8](#0-7) [9](#0-8) 

Cross-chain message delivery order between the `RedeemEscrow` (from fill) and `RefundEscrow` (from the attacker's cancel) is not guaranteed to match dispatch order. If the `RefundEscrow` message is delivered to the source chain *before* the `RedeemEscrow` message, the escrow is drained to `order.user` first, and the legitimate solver's subsequent `RedeemEscrow` withdrawal reverts (`UnknownOrder`) — even though the solver already paid out the full output amount to the beneficiary on the destination chain during `_fillCrossChain`. This is a genuine loss of funds for the solver and a broken one-time-settlement invariant, independent of whether the reverting message is ultimately treated as failed.

### Impact Explanation
- The one-time settlement invariant encoded by `_filled` is violated: a finalized (solver-filled) order can be overwritten back to "cancelled by user" state by an unprivileged caller with no ownership of the order.
- Two conflicting withdrawal messages (`RedeemEscrow` to the solver and `RefundEscrow` to `order.user`) are put in flight for the same escrowed commitment.
- Depending on message delivery order on the source chain, the solver who already fulfilled the order (transferred real output tokens to the beneficiary) can be denied reimbursement from escrow, since `_orders[commitment][token]` gets zeroed out by the winning message and the loser reverts with `UnknownOrder`. This is a direct loss of solver funds and a duplicate-settlement/race condition on escrow accounting.

### Likelihood Explanation
The race window is deterministic and attacker-triggerable: any account can call `_cancelFromDest` for any order once `_blockNumber() > order.deadline`, with no requirement to be the order owner and no requirement that the order remain unfilled. A solver filling near the deadline boundary (a normal, expected usage pattern) is automatically exposed to this race in the very next block.

### Recommendation
Add a check in `_cancelFromDest` that reverts with `Filled()` if `_filled[commitment] != address(0)` before allowing cancellation, mirroring the guarantee that `_cancelFromSource`/`onGetResponse` already enforce (but doing it as a cheap local read instead of a remote proof, since this function executes on the very chain where `_filled` lives):
```solidity
function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
    if (_filled[commitment] != address(0)) revert Filled();
    ...
}
```

### Proof of Concept
1. Solver calls `_fillCrossChain(order, options, commitment)` at block `order.deadline` (allowed since `order.deadline >= _blockNumber()`), which sets `_filled[commitment] = solver` and dispatches `RedeemEscrow` to the source chain.
2. At block `order.deadline + 1`, an unprivileged attacker calls `_cancelFromDest(order, cancelOptions, commitment)` for the same order — the `msg.sender == order.user` check is skipped since `order.deadline < _blockNumber()`, and there is no check that `_filled[commitment]` is already non-zero.
3. `_cancelFromDest` overwrites `_filled[commitment]` to `order.user` and dispatches `RefundEscrow` to the source chain.
4. On the source chain, whichever of `RedeemEscrow`/`RefundEscrow` is delivered first drains `_orders[commitment][token]` to zero via `_withdraw`; the second message reverts with `UnknownOrder`. If `RefundEscrow` wins the race, the solver — who already delivered output tokens on the destination chain — never receives their escrowed reimbursement.

     * @dev Initiates cancellation of a cross-chain order from the source chain.
     *
     * Only the order creator may cancel, and only after the order deadline has passed
     * (verified by `options.height > order.deadline`). Dispatches a Hyperbridge GET
     * request to the destination chain to verify that the `_filled` storage slot for
     * this commitment is empty (i.e., the order was never filled on the destination).
     *
     * The GET response is handled by `onGetResponse`, which refunds the escrow if
     * the slot is indeed empty.
     *
     * @param order The order to cancel.
     * @param options Cancel options including the proof height and relayer fee.
     * @param commitment The keccak256 hash of the ABI-encoded order.
     */
    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
