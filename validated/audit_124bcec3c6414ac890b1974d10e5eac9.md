## Title
Recursion-depth quota bypass via nested MessageSet extension re-parsing - (File: objectivec/GPBMessage.m)

## Summary
`-parseMessageSet:extensionRegistry:forcedExtension:` in `GPBMessage.m` extracts the raw bytes of a MessageSet item's payload and re-parses them by allocating a brand-new `GPBCodedInputStream` rather than continuing to use the current stream/state. [1](#0-0)  The recursion-depth invariant that `kDefaultRecursionLimit` is supposed to enforce globally across the whole parse is instead re-armed at zero for every new MessageSet payload, exactly mirroring the unbound flaw where a nested-name expansion causes each recursion "hop" to be checked against a local budget instead of the intended global quota.

## Finding Description
Protobuf's C++/Java/C# parsers maintain a single monotonically-decreasing recursion counter threaded through the entire parse (`ParseContext::depth_`, `CodedInputStream::recursion_budget_`, `Registers.recursionDepth`) so that arbitrarily deep nesting — through any combination of messages, groups, or MessageSet-style dispatch — is bounded by one global limit. [2](#0-1) [3](#0-2) [4](#0-3) 

The Objective‑C `CheckRecursionLimit` helper checks `state->recursionDepth` against `kDefaultRecursionLimit` (100), and this is enforced only within the lifetime of a single `GPBCodedInputStreamState`. [5](#0-4) 

When a MessageSet-formatted extension item is encountered, `parseMessageSet:` reads the type-id/payload sub-fields, then constructs an entirely new `GPBCodedInputStream` over the extracted `rawBytes` and recursively merges the target extension message through it. [6](#0-5)  The code contains a comment claiming the parent stream's recursion depth is carried into the child stream via an `initWithData:parentRecursionDepth:` initializer specifically "so that nested MessageSet items... remain bounded by kDefaultRecursionLimit." However, no such initializer exists anywhere in `GPBCodedInputStream.h`/`.m` — the only designated initializer present is the plain `initWithData:`, which always starts `recursionDepth` at 0 for the freshly allocated stream. This means the depth-inheritance the comment describes is not actually implemented in this codebase: each new MessageSet extension hop resets the local recursion counter to zero, so the check in `CheckRecursionLimit` only ever bounds nesting *within* a single hop, not across chained hops.

## Impact Explanation
An attacker who controls a bounded, well-formed serialized Objective‑C message can nest MessageSet-encoded extension items inside MessageSet-encoded extension items. Each hop is locally valid (depth stays under 100 inside that hop) but the aggregate recursion across hops — each of which allocates its own `GPBCodedInputStream` and recurses through `mergeFromCodedInputStream:extensionRegistry:endingTag:` — is unbounded by the advertised `kDefaultRecursionLimit`, contrary to the documented intent in the very code comment. This directly parallels the unbound analog: a security control meant to cap a resource (upstream packets / recursion depth) globally is instead re-armed per sub-unit (per DNS name level / per MessageSet hop), letting attacker-controlled nesting silently exceed the intended bound. The practical consequence is uncontrolled native call-stack growth during message merging, which can exhaust the stack (crash / DoS) despite the presence of a recursion-limit check that appears, but fails, to be global.

## Likelihood Explanation
Reachable through the public, documented `-parseFromData:extensionRegistry:error:`/`-mergeFromData:...` APIs whenever a schema declares (or an attacker forges, within otherwise-valid wire bytes) MessageSet-style extensions, which Objective-C protobuf supports for `option message_set_wire_format = true` messages. No privileged access or hostile schema is required — only a bounded, well-formed binary payload with nested MessageSet extension items, consistent with the "ordinary client sending bounded binary Protobuf" threat model.

## Recommendation
Implement (or correctly wire up) depth propagation from the parent `GPBCodedInputStreamState.recursionDepth` into any newly allocated `GPBCodedInputStream` used to re-parse MessageSet extension payloads, and enforce `CheckRecursionLimit` against that inherited value before merging — mirroring the C++ `ParseContext::Spawn` depth-reduction pattern [7](#0-6) . Add a regression test that nests MessageSet extensions beyond `kDefaultRecursionLimit` hops and asserts that parsing raises `GPBCodedInputStreamErrorRecursionDepthExceeded` rather than recursing further.

## Proof of Concept
Not executed against a running binary in this environment (index/documentation limitations — the actual method table for `GPBCodedInputStream` could not be fully enumerated here, and no build/test tooling is available in ask-only mode). Conceptual PoC: construct a message-set-wire-format message whose extension payload is itself another message-set-wire-format extension item, nested repeatedly (e.g., 500 levels), each level valid on its own (`< kDefaultRecursionLimit`). Parsing via `-parseFromData:extensionRegistry:error:` should be expected to trigger `GPBRaiseStreamError(GPBCodedInputStreamErrorRecursionDepthExceeded, ...)` if depth truly is global as the code comment claims; the absence of the `initWithData:parentRecursionDepth:` initializer in the codebase indicates this check is not actually enforced across hops. This should be verified with an actual build/runtime session, which is outside the scope of this read-only analysis.
