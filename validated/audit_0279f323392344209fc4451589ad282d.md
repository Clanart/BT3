## Title
Webhook HMAC verification does not bind the signature to the `shop_domain`/`topic` headers, allowing cross-shop replay of a legitimate webhook body - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
The reported ParaSpace issue is a signature-binding gap: a maker's signature over a `Credit` struct doesn't include a marketplace identifier, so a valid signature can be replayed in an unintended context (a different, worthless order) and still pass verification. The analogous gap in `shopify_app` is in webhook authentication: `WebhookVerification#verify_request` and the underlying `PayloadVerification#hmac_valid?` compute/verify the HMAC over the raw POST body only, never over the `X-Shopify-Shop-Domain` or `X-Shopify-Topic` headers. Any request whose body/HMAC pair is valid for the shared app secret will pass verification regardless of which shop or topic header accompanies it.

### Finding Description
`hmac_valid?` computes the digest strictly from `data` (the raw body) and the app's shared secret(s): [1](#0-0) 

`WebhookVerification#verify_request` only feeds `request.raw_post` into this check, and `shop_domain` is read directly and unauthenticated from a header: [2](#0-1) 

`WebhooksController#receive` builds the downstream `ShopifyAPI::Webhooks::Request` purely from `request.raw_post` and `request.headers.to_h` after `verify_request` has already passed: [3](#0-2) 

The `shop`/`topic`/`webhook_id` values consumed by the job handler come from headers, as confirmed by the test job signature `handle(topic:, shop:, body:, webhook_id:, api_version:)`: [4](#0-3) 

Because the app secret is shared across every shop that installs the app (it is the app's client secret, not a per-shop secret), an unrelated/unprivileged merchant who has legitimately installed the app on their own store can trigger an event on their own shop to obtain a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair. Since the signature never covers `X-Shopify-Shop-Domain` or `X-Shopify-Topic`, that attacker can resend the exact same body and HMAC to the webhook endpoint while substituting a victim's shop domain (and/or a different topic) in the headers. `hmac_valid?` still returns true because it only re-derives the digest from the untouched body, so `verify_request` lets the forged request through, and the enqueued job runs believing the webhook body originated from the victim shop.

### Impact Explanation
This is a forged/replayed signed request being accepted for the wrong tenant context — the same bug class as the report (missing binding field enabling signature reuse across unintended contexts). Depending on the app's webhook job logic (e.g., jobs that create/update shop records, sync data, or trigger business logic keyed by `shop_domain`), this enables cross-shop data injection/corruption: attacker-controlled webhook content can be attributed to and processed under a victim shop's identity.

### Likelihood Explanation
Exploitation requires only that the attacker install the app on their own shop (a standard, unprivileged action) and know/guess a victim shop domain — no secret leakage or privileged access is required. The header/body split is enforced consistently by both `PayloadVerification` and its consumer `WebhookVerification`, so this is a systemic default of the verification design rather than an edge case.

### Recommendation
Include the trust-critical headers (`X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and ideally `X-Shopify-Webhook-Id`) as part of the data that is authenticated, e.g. by having `hmac_valid?`/`verify_request` bind the computed digest to a canonicalized string that incorporates these header values, or by validating that the shop domain in the header matches an installation-scoped expectation before enqueuing the job. This mirrors the report's suggested fix of adding a binding identifier (`MarketplaceAddress`) to the signed structure.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a subscribed webhook topic (e.g. `orders/create`), causing Shopify to POST a body `B` with a valid `X-Shopify-Hmac-Sha256: H` (computed with the app's shared secret) to `/webhooks/orders_create`.
2. Attacker intercepts/records `(B, H)`.
3. Attacker crafts a new POST to the same endpoint using identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which only checks `B` against `H` and the shared secret — it succeeds. [5](#0-4) 
5. `WebhooksController#receive` forwards the request (with the forged shop header) to `ShopifyAPI::Webhooks::Registry.process`, which dispatches the corresponding job with `shop: "victim-shop.myshopify.com"` and the attacker's own webhook body `B`. [6](#0-5)

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
