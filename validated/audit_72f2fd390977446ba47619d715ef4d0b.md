## Analysis

The CVE describes a classic **missing output-encoding** bug class: attacker-controlled data (the `PATH_INFO` segment) flows into the application's response/DOM without HTML/JS-context escaping, letting an attacker break out of the intended context and inject script. The failed invariant is *"user-controlled string data that will be embedded in an HTML/JS context must be escaped before being emitted."*

Protobuf's ProtoJSON serializers are the closest legitimate analog: they are a public, supported serialization API (`MessageToJson`/`JsonFormat.print`/`serializeToJsonString`) that emits string field values that may originate from arbitrary application/user data, and Google's own C++ and Java implementations deliberately add **non-JSON-spec escaping of `<`, `>`, `&`, `=`, `'`** specifically to prevent script/HTML injection when the resulting JSON is later embedded inside a `<script>` tag or similar HTML context — this is proven by explicit code comments and a named regression test (`b/73832901`): [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The C# `JsonFormatter` implements the identical hardening (`\u003c`/`\u003e` for `<`/`>`): [5](#0-4) 

However, this same hardening is **absent** in three other officially supported implementations:

1. **Python** — `json_format.py` builds a plain dict via reflection and calls the stdlib `json.dumps()`, with no HTML-unsafe-character escaping layer at all, regardless of which native backend (pure-Python/C++/upb) is in use for parsing: [6](#0-5) 
The project's own test explicitly asserts `<`, `>`, and `&` are emitted **verbatim, unescaped**, unlike the Java/C++ test asserting the opposite: [7](#0-6) 

2. **PHP / Ruby (via upb)** — the shared upb JSON encoder's character-escaping routine only escapes JSON-spec-required characters (quote, backslash, control chars) and never touches `<`, `>`, `&`, `=`, `'`: [8](#0-7) [9](#0-8) [10](#0-9) 
PHP's pure-PHP fallback path (`GPBJsonWire::jsonNiceEscape`) has the same gap: [11](#0-10) 

### Title
Missing HTML/XSS-safety escaping (`<`, `>`, `&`, `=`, `'`) in Python/PHP/Ruby ProtoJSON string encoders - (File: `python/google/protobuf/json_format.py`, `upb/json/encode.c`, `php/src/Google/Protobuf/Internal/GPBJsonWire.php`)

### Summary
Protocol Buffers' C++ and Java ProtoJSON encoders deliberately escape `<`, `>`, `&`, `=`, and `'` (beyond what the JSON spec requires) specifically to defend against script-injection when serialized JSON is embedded in an HTML `<script>` context. The Python, PHP, and Ruby ProtoJSON encoders lack this same defense-in-depth escaping, emitting these characters verbatim.

### Finding Description
`json_format.py`'s `ToJsonString` produces a plain dict and hands it to Python's stdlib `json.dumps`, which only escapes what the JSON spec requires; it never escapes `<`/`>`/`&`. The upb JSON encoder (`jsonenc_put_escaped_char`, shared by the PHP and Ruby native extensions) and PHP's pure-PHP fallback (`GPBJsonWire::jsonNiceEscape`/`isJsonEscaped`) exhibit the identical gap — only quotes, backslashes, and control characters are escaped. By contrast, C++'s `JsonWriter::MustEscape` and Java's `JsonFormat.getReplacementOrNull` explicitly escape these characters "to prevent security bugs in JavaScript," with a dedicated regression test tied to an internal bug (`b/73832901`) proving this was a known, real-world risk that was intentionally fixed in those two implementations but never ported to Python/PHP/Ruby.

### Impact Explanation
If an application uses `MessageToJson`/`serializeToJsonString` (Python/PHP/Ruby) on a message containing an attacker-influenced string field and embeds the resulting JSON text directly inside an HTML `<script>` block (a common server-side-rendering / hydration pattern), a value such as `</script><script>alert(1)</script>` is emitted unescaped. This lets the attacker break out of the intended `<script>` element and inject arbitrary script into the page — the same DOM/script-injection class of impact as CVE-2019-12834, mediated through the ProtoJSON serializer rather than a raw template.

### Likelihood Explanation
Moderate. It requires (a) an application-level design where ProtoJSON output is inlined into HTML/`<script>` without its own additional escaping (a widely-documented anti-pattern but one the Java/C++ implementations were specifically hardened against because it happens in practice), and (b) an attacker-influenced string field reaching the serializer. No parsing corruption, memory, or resource-exhaustion primitive is needed — only reachability of the codepath, which is the default, public JSON serialization API.

### Recommendation
Port the same non-JSON-spec HTML-unsafe-character escaping (`<`, `>`, `&`, `=`, `'`, and the JS-whitespace/format characters already escaped in C++/Java) into Python's `json_format.py` string serialization path and into upb's `jsonenc_put_escaped_char` (covering PHP and Ruby), and into PHP's pure-PHP `GPBJsonWire::jsonNiceEscape`, so that all language implementations of ProtoJSON provide consistent script-injection hardening as documented for C++/Java/C#.

### Proof of Concept
Using the Python API (illustrative, matches the existing project test at `python/google/protobuf/internal/json_format_test.py:296-304` which currently asserts this exact unescaped behavior):
```python
from google.protobuf import json_format
msg = TestMessage()
msg.string_value = "</script><script>alert(1)</script>"
print(json_format.MessageToJson(msg))
# -> {"stringValue": "</script><script>alert(1)</script>"}
```
Compare with the Java/C++ equivalent, which produces `\u003c/script\u003e...` (see `JsonFormatTest.testHtmlEscape`, `JsonTest.HtmlEscape`), demonstrating the cross-implementation inconsistency and the missing hardening in Python (and analogously PHP/Ruby via upb).

```c
static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}
```

```c
static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
```
