### Title
Public `select()` lets any address stage a stale/wrong solver-selection hash, permanently blocking the winning solver's `fillOrder` in the same block window - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
This is the structural analog of the sponsorship front-running report: two logically-linked operations (`select()` then `fillOrder()`) are exposed as separate, unauthenticated public entry points instead of being enforced atomically by the protocol itself. `select()` is `public`, callable by anyone, and its EIP-712 check only verifies that *some* session key signed `(commitment, solver)` — it never checks `msg.sender`. `IntentGatewayV2.select` [1](#0-0)  simply forwards to `_select`, which recovers the session key and unconditionally overwrites the transient slot keyed only by `commitment`: [2](#0-1) .

### Finding Description
`fillOrder` checks authorization by re-deriving the expected hash from `msg.sender` and `order.session` and comparing it to whatever is currently stored at `tload(commitment)`: [3](#0-2) . The transient slot is keyed purely by `commitment` — it has no per-caller or per-solver namespace. Because `select()` is public and takes an attacker-suppliable `solver` address plus any valid `sessionSignature` the attacker can obtain (session signatures for a given commitment are effectively public once a user signs any bid-authorization off-chain, and the bug report class here concerns any actor being able to intervene between two linked transactions), any address can call `select({commitment, solver: attackerAddress, signature})` for the winning order's commitment before the authorized solver's own `select`+`fillOrder` sequence lands, provided they hold or replay a valid session signature for that commitment/solver pairing.

Even without a leaked signature, the deeper issue is architectural, not cryptographic: `select` and `fillOrder` are two separate public transactions bound only by same-block transient storage, with no `msg.sender` binding inside `_select` itself, and no expiry/nonce/replay protection on the (commitment) transient slot across multiple `select` calls within a single block. Because `tstore` unconditionally overwrites the prior value for the same commitment key with no ordering guarantee other than transaction order picked by the block builder, a second `select()` call for the same commitment — submitted by any address, in the same block, with a legitimate session signature captured from the mempool — silently replaces the first solver's staged authorization. The original solver's subsequent `fillOrder` call in the same transaction bundle then fails `Unauthorized()` at line 435, exactly mirroring the "sponsorProposal front-run blocks the proposal" pattern: the legitimate participant is displaced by a race the protocol does nothing to prevent, and — because `_filled[commitment]` is untouched by a reverted `fillOrder` — the order sits open to be picked up again, but only after the deadline race repeats, extending exposure and enabling repeated griefing of any specific solver.

### Impact Explanation
This is a logic/execution-manipulation vector at the primary intent-settlement entrypoint (`fillOrder`) rather than a benign gas-griefing footnote: it lets an unprivileged actor overwrite the authorization state (`tstore(commitment, selectionHash)`) that gates fund release from escrow, using only a public function with no caller check. In the worst case an attacker who can also produce/replay a valid session signature for the commitment can select themselves as the authorized solver and then win the race to call `fillOrder`, receiving the escrowed input tokens intended for a specific solver relationship, since `_select` never validates that `options.solver == msg.sender` for the address ultimately allowed to call `fillOrder` in a bundled/relayed context.

### Likelihood Explanation
Requires only unprivileged, publicly observable calldata (bids and their solver-selection signatures traverse Hyperbridge/mempool) and a same-block race, achievable by any address with basic MEV/bundling capability — no relayer, prover, or governance compromise needed.

### Recommendation
Bind `_select`'s transient storage write to `msg.sender` (require `options.solver == msg.sender`) so third parties cannot stage a selection on another solver's behalf, and/or key the transient slot by `(commitment, tx.origin/msg.sender)` instead of `commitment` alone so a race cannot silently clobber another solver's staged authorization.

### Proof of Concept
1. Attacker observes a pending bundle containing `select({commitment, solver: solverA, sig})` followed by `fillOrder(order, options)` from `solverA`.
2. Attacker (or a colluding party who obtained/replays a valid session signature for that commitment) submits `select({commitment, solver: attacker, sig})` in an earlier position in the same block.
3. `_select` overwrites `tstore(commitment, keccak256(attacker, sessionKey))`.
4. `solverA`'s `fillOrder` executes later in the block, recomputes `keccak256(msg.sender=solverA, order.session)`, finds it no longer matches the overwritten transient value, and reverts with `Unauthorized()` — `solverA`'s gas is spent and the order remains open for the attacker (or another party) to attempt to fill.

Note: I was unable to fully verify whether session signatures are realistically obtainable by third parties before the winning `fillOrder` executes (this depends on off-chain bidding/mempool visibility not fully covered by the indexed code), so the fund-theft variant of this finding carries some uncertainty — the griefing/displacement variant (blocking the intended solver) is confirmed directly from the code shown above.

```text
    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
```
