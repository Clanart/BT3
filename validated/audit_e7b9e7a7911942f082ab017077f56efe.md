### Title
Recursive clone explicitly disables Git's clone-time protection against malicious repos (`GIT_CLONE_PROTECTION_ACTIVE=false`) - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` performs a `git clone --recursive` while explicitly setting the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`, which disables Git's own built-in defense against maliciously crafted repositories/submodules that try to write files into a `.git` directory during clone (the class of clone-time attacks addressed upstream by Git, e.g. CVE-2024-32002-style symlink/case-confusable submodule tricks). This is the closest local analog to the reported "safety mechanism that the owner can permanently and intentionally disable, defeating the protection it was designed to provide" pattern: here, Desktop — not the user — disables a security guard on every single clone of an attacker-controlled repository.

### Finding Description
`clone()` in [1](#0-0)  builds the environment for the git process: [2](#0-1) 

`GIT_CLONE_PROTECTION_ACTIVE` is a Git-upstream safety switch introduced specifically to stop clone recursion from writing outside the intended working tree via crafted submodule/`.git` paths on case-insensitive or symlink-capable filesystems. Desktop unconditionally forces this to `'false'` for every `--recursive` clone, regardless of whether the remote/URL is trusted. The clone destination itself is validated against a short list of "sensitive locations" (`~/.ssh`, `~/.gnupg`, `~/.config`, `~/.gitconfig`, `%APPDATA%`) in `isClonePathSensitive()` [3](#0-2) , but that check only guards the top-level clone target directory chosen by the user — it does nothing to prevent a malicious remote from smuggling files elsewhere via recursive submodule checkout once Git's own clone-time protection has been switched off.

### Impact Explanation
The attacker primitive matches the "attacker controls a cloned/fetched repository" category explicitly allowed by scope. A malicious remote repository (public repo the user is enticed to clone, or a compromised/typosquatted repo) can embed submodules engineered to exploit the very class of clone-time write-outside-worktree bug that `GIT_CLONE_PROTECTION_ACTIVE` exists to stop. Because Desktop always clones with `--recursive` and always disables this protection, any such repository processed by Desktop loses the upstream Git safeguard, which can result in files being written outside the intended repository directory during the clone — i.e., file write outside the repo, matching the report's core theme of a security guard being deliberately (and here, silently to the user) disabled with harmful consequences.

### Likelihood Explanation
Every single clone operation performed through the app (the primary, everyday user action of adding a repository) exercises this code path with the protection disabled and `--recursive` set, so there is no additional user action required beyond cloning an attacker-supplied URL — a normal, expected workflow in GitHub Desktop. The `isClonePathSensitive` allow-list is narrow and unrelated to the submodule/protection bypass, so it provides no coverage for this specific mechanism.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE=false`. If this override was added to work around a specific benign scenario (e.g., legitimate submodule paths triggering false positives), scope the override narrowly (only for known-safe/local file:// sources, or only after confirming the resolved submodule paths stay within the clone target), and otherwise let Git's clone protection run with its default (enabled) behavior for all remote clones of untrusted repositories.

### Proof of Concept
1. Craft a Git repository with a submodule (or `.gitmodules` entry) designed to trigger the write-outside-worktree condition that `GIT_CLONE_PROTECTION_ACTIVE` is designed to block (the same class of payload used against vanilla `git clone --recursive` before the protection existed).
2. Have the victim clone this repository through GitHub Desktop's normal "Clone repository" flow, which calls `clone()` in [4](#0-3) .
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` in the child git process's environment, Git's own guard against the malicious submodule layout is bypassed during the `--recursive` clone, potentially resulting in files being written outside the chosen clone directory.

Note: I could not find any comment, commit message, or test in the indexed codebase explaining why `GIT_CLONE_PROTECTION_ACTIVE` is force-disabled (the repository only shows a single "Initial commit" in its history, so no prior rationale is available), so the intent behind this override is unconfirmed — it may be an unintentional workaround rather than a deliberate acknowledged trade-off, unlike the "intended behavior" acknowledgment in the original report.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
