### Title
Authorization header for GitHub asset/avatar requests is scoped only to origin, not to the account/repository that owns the resource - (File: `app/src/main-process/authenticated-image-filter.ts`)

### Summary
The ERC-7739 report describes a "wrong scope" bug: a value meant to bind an operation to one specific entity (the account) was instead bound to a shared, coarser identity (the SmartSession contract), defeating the isolation the scheme was designed to provide. The closest reachable analog in this GitHub Desktop codebase is `installAuthenticatedImageFilter`, which re-attaches the signed-in user's real GitHub access token to any request whose *origin* matches a signed-in account's endpoint and whose *path* matches a generic regex for avatar/asset URLs — without verifying that the specific resource (owner/repo/asset) is one the account is actually authorized for, or that the request originated from a context associated with that account.

### Finding Description
`installAuthenticatedImageFilter` builds a `Map<origin, token>` from the currently signed-in accounts [1](#0-0) . On every outgoing renderer request, it checks only two things: the request's `origin` and whether the `pathname` matches `isEnterpriseAvatarPath` or `isGitHubRepoAssetPath` [2](#0-1) . If both match, it unconditionally attaches `Authorization: token <token>` to the request [3](#0-2) .

The "verifying" scope here is the origin string (`https://github.com` or a GHE host) plus a loose path shape (`/owner/repo/assets/userID/guid` or `/user-attachments/assets/guid`) — not the specific repository, asset owner, or the document/context that requested the image. Any content rendered inside GitHub Desktop that can embed an `<img>` (or other subresource-fetching) tag pointing at a URL matching this shape on the trusted origin — e.g., a pull request/issue body, commit description, or README rendered from a cloned/fetched repository, all of which are attacker-influenced surfaces — will cause Desktop to silently attach the real signed-in user's token to that request, regardless of whether the referenced asset belongs to a repository the attacker (or the embedded content) has any business referencing.

This mirrors the reported bug class exactly: a security-relevant credential is bound to a coarse, shared scope (origin) instead of the fine-grained scope (specific repo/asset ownership) that the mechanism is meant to protect, enabling cross-context replay of that credential.

### Impact Explanation
Because the Authorization header is attached based purely on host+path-shape matching, an attacker who controls content rendered by Desktop (a PR/issue body, or a file in a cloned repository that Desktop renders as markdown, e.g. `README.md`) can embed asset/avatar URLs for *arbitrary* repos or enterprise avatar paths on the trusted origin. Desktop will then present the user's real token to GitHub for that resource. `same-origin-filter.ts` only strips auth headers on a *cross-origin* redirect hop [4](#0-3) ; it does nothing to prevent the initial same-origin request (to the attacker-chosen path under the legitimate github.com/GHE origin) from carrying the real token. This can be used as a confused-deputy oracle (e.g., probing private-repo asset existence/access via response codes) and, if the target host has any open-redirect behavior under matching paths, could be chained toward off-origin token exposure since only the *redirect hop* is filtered, not the origin/path validation on the initial request itself.

### Likelihood Explanation
The path is reachable without local access, malware, or social engineering: Desktop already renders untrusted markdown from PR/issue bodies and repository READMEs, and asset/user-attachment URLs of exactly this shape (`/user-attachments/assets/<guid>`, `/owner/repo/assets/<userid>/<guid>`) are the normal way GitHub embeds pasted images in those bodies — meaning the matching regexes are trivially satisfiable by content an attacker fully controls (a crafted PR, issue, or file in a repo the victim opens/clones). No unnatural user action beyond viewing such content in Desktop is required.

### Recommendation
Do not scope the Authorization attachment to origin + generic path shape alone. Require that the specific repository/owner embedded in the path is one the requesting account is actually entitled to access (via a authorization/ownership check against Desktop's known repositories/accounts, or a server-issued signed URL) before attaching the real token, so the credential is bound to the account-resource relationship rather than to a coarse per-origin scope.

### Proof of Concept
1. Attacker opens a pull request or issue (or contributes a `README.md`) containing:
   `<img src="https://github.com/some-private-org/some-private-repo/assets/12345/aaaa-bbbb-guid">`
2. Victim, signed in to GitHub Desktop with a token for `github.com`, views this PR/issue/README rendered inside Desktop.
3. `installAuthenticatedImageFilter`'s `onBeforeSendHeaders` handler matches the origin (`https://github.com`) against `originTokens`, and the pathname against `isGitHubRepoAssetPath`, and attaches `Authorization: token <victim's real token>` to the outgoing request [3](#0-2)  — without any check that the victim's session is meant to authorize access to `some-private-org/some-private-repo`.
4. The response (200 vs 404/403) can be observed by the attacker via side channels (e.g., load success/failure of the embedded image) as an access oracle, or the mechanism can be reused against other same-origin path variants to probe/leak token-gated resources the victim did not intend to authenticate against.

Note: I could not fully verify whether GHE/GHES environments expose any same-origin open-redirect under these matched paths that would let `same-origin-filter.ts`'s per-redirect stripping be bypassed for true off-origin exfiltration — that would need further investigation in a live/GHE environment, which is outside the scope of static code search.

```typescript
function isEnterpriseAvatarPath(pathname: string) {
  return pathname.startsWith('/api/v3/enterprise/avatars/')
}

function isGitHubRepoAssetPath(pathname: string) {
  // Matches paths like: /repo/owner/assets/userID/guid
  return (
    /^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/.test(pathname) ||
    // or: /user-attachments/assets/guid
    /^\/user-attachments\/assets\/[^/]+\/?$/.test(pathname)
  )
}
```
