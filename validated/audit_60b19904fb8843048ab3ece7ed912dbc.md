### Title
Missing Mismatch Check in `insert_operator_bitvm_keys_if_not_exist` Allows Silent Poisoning of Stored BitVM Winternitz Keys — (`File: core/src/database/operator.rs`)

### Summary

`insert_operator_bitvm_keys_if_not_exist` uses `ON CONFLICT DO NOTHING` and returns `Ok(())` without verifying that the incoming keys match what is already stored. Every other analogous "insert-if-not-exists" function in the same file performs an explicit mismatch check and returns a hard error on divergence. The omission means a malicious operator can permanently fix wrong BitVM Winternitz keys in a verifier's database, silently, with no error surfaced to the caller.

### Finding Description

`insert_operator_bitvm_keys_if_not_exist` stores the per-deposit BitVM assert Winternitz public keys for an operator:

```rust

Every peer function in the same file performs a post-conflict read-back and returns an error if the stored value differs from the incoming value:

`insert_operator_bitvm_keys_if_not_exist` is the sole exception: it silently discards the incoming keys when a row already exists, returning `Ok(())` regardless of whether the stored keys match.

The function is called from `Verifier::set_operator_keys`, which is invoked by the aggregator during `new_deposit` to distribute per-deposit operator keys to every verifier: [6](#0-5) 

### Impact Explanation

The BitVM Winternitz public keys stored here are used to construct the assert-UTXO scripts inside the kickoff transaction and, critically, to reconstruct the disprove transaction when a verifier needs to challenge a fraudulent operator. If the stored keys diverge from the keys the operator actually used on-chain, the verifier will build a disprove transaction whose script path does not match the on-chain UTXO, making it unspendable on Bitcoin.

A malicious operator can exploit this to permanently disable the disprove path for a specific deposit:

1. During `set_operator_keys` for a deposit, the operator sends syntactically valid but deliberately wrong Winternitz public keys to the aggregator.
2. The aggregator distributes them to all verifiers; each verifier calls `insert_operator_bitvm_keys_if_not_exist` and stores the wrong keys — no error is raised.
3. The deposit flow continues and the move-to-vault transaction is finalized (it does not use BitVM keys).
4. If the deposit is retried or `set_operator_keys` is called again with the correct keys, `ON CONFLICT DO NOTHING` silently discards the correct keys; the wrong keys remain.
5. The operator broadcasts a kickoff transaction whose assert UTXOs commit to the correct (operator-controlled) Winternitz keys.
6. When the operator submits a fraudulent assert, every verifier attempts to construct a disprove transaction using the poisoned stored keys. The resulting transaction cannot spend the on-chain UTXO.
7. The challenge window expires; the operator's fraudulent withdrawal is finalized and bridged BTC is stolen.

### Likelihood Explanation

The attack requires a malicious operator — an entity that has posted collateral and is explicitly within the BitVM threat model. The operator controls exactly what keys it sends to the aggregator. No external chain state, no privileged key compromise, and no honest-node misbehavior is required. The only prerequisite is that the operator sends wrong keys before correct keys for the same `(xonly_pk, deposit_id)` pair, which is entirely within the operator's control.

### Recommendation

Apply the same post-conflict mismatch check used by every other analogous function:

```rust
pub async fn insert_operator_bitvm_keys_if_not_exist(
    &self,
    mut tx: Option<DatabaseTransaction<'_>>,
    operator_xonly_pk: XOnlyPublicKey,
    deposit_outpoint: OutPoint,
    winternitz_public_key: Vec<WinternitzPublicKey>,
) -> Result<(), BridgeError> {
    let wpk = borsh::to_vec(&winternitz_public_key)...;
    let deposit_id = self.get_deposit_id(tx.as_deref_mut(), deposit_outpoint).await?;

    let query = sqlx::query(
        "INSERT INTO operator_bitvm_winternitz_public_keys
         (xonly_pk, deposit_id, bitvm_winternitz_public_keys)
         VALUES ($1, $2, $3)
         ON CONFLICT DO NOTHING;",
    )...;

    let result = execute_query_with_tx!(self.connection, tx.as_deref_mut(), query, execute)?;

    if result.rows_affected() == 0 {
        let existing = self.get_operator_bitvm_keys(tx, operator_xonly_pk, deposit_outpoint).await?;
        if existing != winternitz_public_key {
            return Err(BridgeError::OperatorBitvmKeysMismatch(operator_xonly_pk, deposit_outpoint));
        }
    }
    Ok(())
}
```

This mirrors the pattern already used by `insert_operator_kickoff_winternitz_public_keys_if_not_exist`. [7](#0-6) 

### Proof of Concept

1. Operator A registers for a deposit with `deposit_outpoint = X`.
2. During `set_operator_keys`, operator A sends `winternitz_pubkeys = [garbage_key_1, garbage_key_2, ...]` to the aggregator.
3. Aggregator calls `set_operator_keys` on each verifier; each verifier calls `insert_operator_bitvm_keys_if_not_exist` — garbage keys are stored, `Ok(())` returned.
4. Deposit finalization proceeds; move-to-vault transaction is broadcast and confirmed.
5. Operator A calls `set_operator_keys` again (e.g., deposit retry path) with the correct keys derived from its actual secret key.
6. Each verifier calls `insert_operator_bitvm_keys_if_not_exist` again — `ON CONFLICT DO NOTHING` fires, correct keys are discarded, `Ok(())` returned.
7. Operator A broadcasts a kickoff transaction whose assert UTXOs commit to the correct Winternitz keys.
8. Operator A submits a fraudulent assert.
9. Each verifier calls `get_operator_bitvm_keys` → receives garbage keys → constructs a disprove transaction with wrong script paths → transaction is rejected by Bitcoin.
10. Challenge window expires; fraudulent withdrawal is finalized. [8](#0-7) [9](#0-8)

    /// This function additionally checks if the BitVM setup data already exists in the db.
    /// As we don't want to overwrite BitVM setup data on the db, as maliciously overwriting

        latest_blockhash_root_hash: &[u8; 32],

            .get_deposit_id(tx.as_deref_mut(), deposit_outpoint)
            .await?;

        let query = sqlx::query(
            "INSERT INTO bitvm_setups (xonly_pk, deposit_id, assert_tx_addrs, root_hash, latest_blockhash_root_hash)
             VALUES ($1, $2, $3, $4, $5)
             ON CONFLICT (xonly_pk, deposit_id) DO NOTHING;",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk))
        .bind(i32::try_from(deposit_id).wrap_err("Failed to convert deposit id to i32")?)

                .iter()
                .map(|addr| addr.as_ref())
                .collect::<Vec<&[u8]>>(),

        .bind(root_hash.to_vec())
        .bind(latest_blockhash_root_hash.to_vec());

        let result = execute_query_with_tx!(self.connection, tx.as_deref_mut(), query, execute)?;

        // If no rows were affected, data already exists - check if it matches
        if result.rows_affected() == 0 {
            let existing = self
                .get_bitvm_setup(tx, operator_xonly_pk, deposit_outpoint)
                .await?;
            if let Some((existing_addrs, existing_root, existing_blockhash)) = existing {

                        operator_xonly_pk,
                        deposit_outpoint,
                    ));
                }

        }
