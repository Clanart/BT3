## Analysis Summary

I traced the "rounding truncation benefits the wrong party" bug class through Hyperbridge's proportional-release code in `IntrinsicIntents.sol`. The test suite (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol`, "Finding #4") shows the protocol already patched the classic dust-truncation problem for the single-input/single-output case by releasing the *exact remaining escrow balance* on the final fill instead of a truncated proportional share. However, that fix introduces a new, more serious accounting flaw when an order has multiple legs that escrow the **same input token address**.

### Title
Full-fill escrow release drains shared per-token escrow bucket across unrelated order legs - (evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` releases escrow per output-leg index `i`. When a leg's cumulative fill reaches `totalRequired`, the code no longer computes a proportional share — it reads and releases the *entire* current balance stored at `_orders[commitment][inputToken]`. Because `_orders` is keyed only by `(commitment, token address)` and not by leg index, this "exact balance" read is only safe if each input token address appears in exactly one leg of the order. If two legs of the same order use the same input token, completing any one of those legs pays out the whole shared bucket — including escrow that belongs to the other, still-unfilled leg.

### Finding Description
`IntentsBase.sol` declares: [1](#0-0) 

There is no per-leg/per-index escrow tracking — only a per-token aggregate. In `_fillSameChain`: [2](#0-1) 

When `amountFilled == totalRequired` for output leg `i`, `escrowedAmount` is set to the *full current balance* of `_orders[commitment][inputToken]` — not `order.inputs[i].amount` minus what's already been released for leg `i`. This was intentionally done to fix the rounding-dust lock demonstrated in the "Finding #4" test: [3](#0-2) 

That fix is correct only under the implicit assumption that each input token address is unique per order (one-to-one with its paired output leg). Nothing in `placeOrder`/`_orders` enforces that assumption — `_orders` is a flat `token => amount` map that aggregates whatever was escrowed under that token, regardless of how many legs contributed to it. `_withdraw` likewise decrements generically by token, not by leg: [4](#0-3) 

Consequently, an order with two legs both escrowing token `A` (e.g. `inputs[0].token == inputs[1].token == A`, paired with two different output tokens `X` and `Y`) will have `_orders[commitment][A]` equal to the *sum* of both legs' escrow. The first solver to fully complete either leg (say leg 0, output `X`) triggers `escrowedAmount = _orders[commitment][A]`, which equals the combined balance for **both** legs — paying that solver the escrow meant for leg 1 (output `Y`) as well, while leg 1 remains open and its output has not yet been delivered to the beneficiary.

### Impact Explanation
This is a direct loss/misallocation of escrowed user funds through the gateway's public, unprivileged `fillOrder` entrypoint — matching the bounty's "unauthorized transaction manipulation" / "false state acceptance of the intended payout" categories. A solver (or the user's own order, if a naive/generic order builder produces duplicate input tokens across legs) can:
1. Place (or observe) a same-chain order with two legs sharing the same input token.
2. Fill only the cheaper/easier leg first (satisfying its output requirement exactly).
3. Receive the entire aggregated escrow balance for that shared token, including the portion that should remain locked for the other unfilled leg.
4. The remaining leg is now under-collateralized: when a second solver later attempts to complete it, `_withdraw` will find `_orders[commitment][A]` insufficient (or zero) and revert with `UnknownOrder`, permanently stranding that leg — the user loses the input funds while receiving no output for the second leg, and the first solver received a windfall beyond what they were entitled to for their leg.

This is a genuine fund-loss and wrong-beneficiary/wrong-amount bug reachable by any solver with no relayer, prover, or governance compromise required.

### Likelihood Explanation
Exploitability depends on an order actually containing two legs with an identical input token address paired with distinct output tokens/bene+="0" amounts — nothing in the reviewed code (`_validateParams`, `placeOrder`) appears to reject such an order shape, though I was not able to fully inspect `IntentGatewayV2.sol`'s `placeOrder` validation path within the available tool budget to confirm there is no duplicate-input-token check. If such orders are permitted (which the flat per-token `_orders` mapping design suggests, since it has no natural way to disambiguate legs), the exploit requires no special privileges — any solver calling the standard `fillOrder` function can trigger it.

### Recommendation
- Track escrow per `(commitment, leg index)` rather than aggregated per `(commitment, token)`, or explicitly reject orders where the same input token address appears in more than one leg during `placeOrder` validation.
- If aggregation by token is intentional (to save storage), the full-fill release path must compute the leg's fair share as `order.inputs[i].amount - alreadyReleasedForLeg[i]` rather than reading the shared token-level balance, restoring the same "release only what this leg is owed" invariant the rounding-dust fix broke.

### Proof of Concept
Not independently executed (no terminal/build access in this mode). Conceptual PoC to validate on a testnet or in the existing Foundry harness (`IntentGatewayV2SameChainTest.sol`):
1. Construct an `Order` with `inputs = [{token: USDC, amount: 100e6}, {token: USDC, amount: 100e6}]` and `output.assets = [{token: DAI, amount: 100e18}, {token: WETH, amount: 0.05e18}]`.
2. `placeOrder` — verify `_orders[commitment][USDC] == 200e6` (aggregated).
3. Solver A calls `fillOrder` providing exactly `100e18` DAI for leg 0 only (`outputs[0].amount = 100e18`, `outputs[1].amount = 0`).
4. Assert Solver A receives `200e6` USDC (the whole bucket) instead of the expected `100e6` for leg 0.
5. Solver B then attempts to fill leg 1 with `0.05e18` WETH and observe `_withdraw` reverting with `UnknownOrder` because `_orders[commitment][USDC]` is now `0`, stranding the user's second leg permanently.
