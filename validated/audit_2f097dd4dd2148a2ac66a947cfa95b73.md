### Title
Unauthenticated `ReceivedOutput` deserialization can report nonexistent funds as spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts a scalar offset, transaction output, and outpoint entirely from untrusted bytes without authenticating that the outpoint exists or contains the claimed `TxOut`. The spending path subsequently trusts those fields: `SignableTransaction::new` uses the claimed value as available input and the claimed outpoint as the transaction input, while `multisig` validates only that the supplied offset derives the output's `script_pubkey`.

This is analogous to the reported missing-authorization issue because attacker-controlled input can define security-sensitive wallet state without proving that the state is legitimate.

### Finding Description
`ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122` performs only:

- canonical scalar decoding for `offset`;
- consensus decoding for `output`;
- consensus decoding for `outpoint`.

It does not verify that `outpoint` references an actual confirmed transaction or that the referenced output equals `output`.

The trusted constructor is `Scanner::scan_transaction`, which obtains the output from an actual transaction and computes its outpoint from `tx.compute_txid()` and its index. The deserializer bypasses that trusted construction path.

During spending:

- `SignableTransaction::new` sums `input.output.value` as spendable funds and uses `input.outpoint` as a transaction input.
- `SignableTransaction::multisig` checks only that `p2tr_script_buf(keys.offset(offset).group_key())` equals the decoded `script_pubkey`.
- The signing machine then signs a Taproot key-spend digest for the fabricated outpoint.

Thus, a caller can encode a zero offset, a valid base-key P2TR script, an arbitrary amount, and a nonexistent outpoint. The resulting object is treated as spendable until Bitcoin consensus rejects the transaction.

### Impact Explanation
An attacker able to supply serialized `ReceivedOutput` bytes can cause an application to report funds as received that are not spendable. If those records drive balance accounting, deposit crediting, forwarding, or transaction construction, the attacker can inflate apparent balances and induce the multisig path to produce signatures for transactions that cannot be accepted by Bitcoin.

This does not let the attacker spend Serai's real UTXOs: `multisig` still requires the decoded script to correspond to the threshold key and supplied offset. The concrete impact is fabricated wallet state and provably unspendable reported funds.

### Likelihood Explanation
Exploitation only requires control over bytes passed to `ReceivedOutput::read`. The attacker does not need a private key, validator position, or valid blockchain output. The base wallet script is public, and using offset zero makes the encoded object satisfy the later key/offset consistency check.

The precondition is that an application accepts `ReceivedOutput` objects from an unauthenticated storage, message, or synchronization boundary rather than obtaining them solely from `Scanner` and authenticated local storage.

### Recommendation
Do not treat `ReceivedOutput::read` as an authenticated constructor for spendable outputs.

- Require deserialized outputs to be validated against the chain before reporting them as received or spending them: resolve the outpoint and compare the returned `TxOut` exactly.
- Prefer an explicit `ReceivedOutput::read_unverified` name, followed by chain verification.
- Alternatively, include sufficient authenticated metadata to bind the object to a trusted scan result.
- At minimum, add a checked constructor that verifies the offset/script relationship and rejects non-P2TR outputs, while still requiring outpoint verification before use.
- Ensure persisted scanner records are authenticated and cannot be modified by lower-privilege writers.

### Proof of Concept
The following demonstrates the semantic bypass without needing a real UTXO:

```rust
use bitcoin::{
  Amount, OutPoint, ScriptBuf, TxOut,
  consensus::encode::serialize,
  hashes::Hash,
  Txid,
};
use k256::Scalar;
use serai_bitcoin::wallet::{p2tr_script_buf, ReceivedOutput};

// Let `group_key` be the wallet's even, tweaked group key.
let script: ScriptBuf = p2tr_script_buf(group_key).unwrap();

let mut encoded = Vec::new();

// Base-key output: offset zero.
encoded.extend(Scalar::ZERO.to_bytes());

// Claim the output pays 1 BTC to the wallet script.
encoded.extend(serialize(&TxOut {
  value: Amount::from_sat(100_000_000),
  script_pubkey: script,
}));

// Reference an outpoint which does not contain that TxOut, or does not exist.
encoded.extend(serialize(&OutPoint {
  txid: Txid::from_raw_hash(*Txid::all_zeros().as_raw_hash()),
  vout: 0,
}));

let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();

// The object reports one BTC as received despite no corresponding chain output.
assert_eq!(forged.value(), 100_000_000);
```

When passed to `SignableTransaction::new`, the fake amount contributes to `input_sat`, and the fake outpoint becomes a transaction input. `SignableTransaction::multisig` accepts the record if the encoded script is the base-key P2TR script, because its only ownership check is:

```rust
p2tr_script_buf(keys.offset(offset).group_key()) == prevout.script_pubkey
```

The resulting signed transaction references the fabricated outpoint and is rejected by Bitcoin consensus, proving the reported funds were not spendable.
