### Title
Unauthenticated `internal_withdraw` RPC bypasses aggregator EIP-712 authorization required by `withdraw` - (File: core/src/rpc/operator.rs)

### Summary
The `ClementineOperator::withdraw` gRPC method enforces an EIP-712 signature check (signed by the aggregator/Citrea-controlled key) before triggering a payout from the operator, when `aggregator_verification_address` is configured. The `internal_withdraw` method exposes the exact same underlying `Operator::withdraw` functionality but omits this authorization check entirely, and — unlike other `internal_*` handlers such as `internal_finalized_payout` — is not gated behind `cfg!(test)`.

### Finding Description
`ClementineOperator::withdraw` (`core/src/rpc/operator.rs:193-258`) parses withdrawal parameters and, if `self.operator.config.aggregator_verification_address` is set, requires a valid `verification_signature` recovered against `OperatorWithdrawalMessage`, matching the configured address, otherwise it returns `BridgeError::ECDSAVerificationSignatureMissing` or `InvalidECDSAVerificationSignature`. Only after this check does it call `self.operator.withdraw(...)`. [5](#0-4) 

`internal_withdraw` (`core/src/rpc/operator.rs:168-190`) parses the same `WithdrawParams` and calls the identical `self.operator.withdraw(...)` function, with zero authorization checks in between. [2](#0-1) 

`Operator::withdraw` (`core/src/operator.rs:560-627`) itself validates only that the input outpoint matches the withdrawal recorded from Citrea and that the payout is profitable for the operator (`is_profitable`) — it has no notion of "who called me," relying entirely on the RPC layer for authorization. [4](#0-3) 

This mirrors the RDNT bug class exactly: two entry points converge on the same privileged internal operation (`_send`/`_sendAndCall` in RDNT; `operator.withdraw` here), one path enforces the extra authorization/fee check, the other does not.

### Impact Explanation
If `internal_withdraw` is reachable by an unprivileged caller (i.e., not gated by transport-level ACL), it allows bypassing the aggregator-authorization binding that `withdraw` establishes: "party the payout was authorized for" = "party that requested it." An attacker could submit their own withdrawal request that satisfies only the profitability check, tricking the operator into funding a payout the aggregator never authorized. This falls under the High-impact class of "an unauthenticated state-changing or broadcasting call" since it triggers signing and broadcasting of a real Bitcoin payout transaction from the operator's funds.

### Likelihood Explanation
Likelihood depends entirely on whether `internal_withdraw` is exposed on the same network-reachable gRPC service as `withdraw` without additional transport-level restriction. Given the naming convention (`internal_*`) and the precedent of `internal_finalized_payout` being explicitly compiled out for non-test builds, it's plausible `internal_withdraw` is intended to be similarly restricted but the guard was omitted — this is the crux of the analog and could not be fully confirmed from the available index.

### Recommendation
Add the same `if !cfg!(test) { return Err(Status::permission_denied(...)) }` guard (or equivalent production-disabling mechanism) to `internal_withdraw` as is used in `internal_finalized_payout`, or otherwise enforce the identical EIP-712 verification-signature check inside `internal_withdraw` before calling `Operator::withdraw`.

### Proof of Concept
1. Deploy an operator with `aggregator_verification_address` configured (i.e., `withdraw` requires EIP-712 authorization).
2. As an unprivileged party with only network access to the operator's gRPC endpoint, craft `WithdrawParams` for a withdrawal outpoint recorded from Citrea, without any verification signature.
3. Call `internal_withdraw` (`core/src/rpc/operator.rs:169`) instead of `withdraw`.
4. Observe that `Operator::withdraw` (`core/src/operator.rs:560`) executes and signs/returns a payout transaction (`RawSignedTx`) without ever checking the EIP-712 signature that `withdraw` would have required, bypassing the intended aggregator-authorization gate.
