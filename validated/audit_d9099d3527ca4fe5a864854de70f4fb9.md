Challenge tx OP_RETURN (challenger EVM address) is unauthenticated due to `SIGHASH_SINGLE|ANYONECANPAY` operator signature, allowing attribution swap - ([File: core/src/builder/transaction/challenge.rs])

### Summary
The `Challenge` transaction's only input signature is an operator `CheckSig` signature computed with `TapSighashType::SinglePlusAnyoneCanPay`, which by BIP-341 rules commits only to the single input being spent and the single output at the same index (index 0, the operator reimbursement output). It never commits to output index 1, the OP_RETURN carrying the challenger's EVM address, nor to any other inputs added to the transaction. Consequently, anyone who observes this signature in a broadcast/mempool Challenge transaction can reuse it in a different transaction that spends the same Challenge UTXO with the identical output-0 payment to the operator, but with an arbitrary OP_RETURN of their own — swapping who is attributed as the challenger for Citrea reimbursement.

### Finding Description
Binding claimed: `EVM address embedded in Challenge OP_RETURN == evm_address of the party whose challenge is honored on Citrea`. Before/after: the OP_RETURN is set from `context.signer.map(|s| s.get_evm_address())` at `TxHandler` construction time [1](#0-0) , and the tx's single output-index for the challenger identity is `op_return_txout(challenger_evm_address.0)` at output index 1 in `create_challenge_txhandler` [2](#0-1) .

The Challenge input is spent via `SpendPath::ScriptSpend(0)` against the Kickoff's `Challenge` output, whose script-0 is `CheckSig(operator_xonly_pk)` [3](#0-2) . The signature kind used, `NormalSignatureKind::Challenge`, is mapped to `DepositSigKeyOwner::OperatorSharedDeposit(TapSighashType::SinglePlusAnyoneCanPay)` [4](#0-3) . This sighash flag is fed into the actual sighash computation and Schnorr signature check for the `CheckSig` script path in `Actor::tx_sign_and_fill_sigs` [5](#0-4) [6](#0-5) .

Per BIP-341/BIP-143, `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` restricts the committed data to: the single spent input's prevout/amount/scriptPubkey/sequence, and only the output at the same index as that input (index 0 here). It excludes all other inputs and all other outputs — specifically the OP_RETURN at output index 1. This means the operator's one-time signature (generated during deposit signing and cached/reused by verifiers, e.g. `create_operator_sighash_stream` / `get_signed_txs_for_kickoff` [7](#0-6) ) is valid for *any* transaction that: (a) spends the same Challenge UTXO with the same sequence, (b) pays the operator the same fixed `operator_challenge_amount` to the same fixed `operator_reimbursement_address` at output index 0, and (c) has arbitrary additional inputs (funded by the attacker, via ANYONECANPAY) and an arbitrary output 1 (the OP_RETURN).

Exploit flow: once any Challenge tx bearing this signature appears in the mempool or on-chain (a normal, public broadcast event — no privileged access needed), an unprivileged attacker can extract the valid Schnorr signature witness, rebuild a competing transaction spending the same Challenge outpoint (identical output-0), attach any funding input(s) they control to cover fees, and substitute their own OP_RETURN with an arbitrary EVM address. If this competing transaction is mined instead of (or before) the original, the operator's payment is unaffected but the recorded challenger identity used for reimbursement-crediting on Citrea is now the attacker's chosen address instead of the entity that actually detected the malicious kickoff — exactly the attribution mismatch the question describes. No script, MuSig2 session, or downstream Clementine code independently re-derives or cross-checks the challenger identity from any other source; `get_txhandler(&txhandlers, TransactionType::Kickoff)`-based flows (`kickoff_not_finalized`, `challenge_timeout`) only check whether the Challenge UTXO is spent, not by whom or with what OP_RETURN [8](#0-7) .

### Impact Explanation
The operator's reimbursement itself is unaffected (output 0 is fixed and signed), but the party credited with the challenge on Citrea — determined solely by this OP_RETURN, per the code's own documentation ("OP_RETURN output containing EVM address of the challenger, for reimbursement if the challenge is correct") [9](#0-8)  — can be redirected to an attacker-chosen address. This is a reimbursement-crediting/attribution bug: the entity that actually detected and paid for the malicious-kickoff challenge is denied the Citrea-side reimbursement it is owed, while an unrelated attacker who merely observed the mempool and paid a small fee is credited instead. This is repeatable for every deposit/operator/round where a Challenge tx is broadcast, since the same `SIGHASH_SINGLE|ANYONECANPAY` construction is used uniformly by `create_challenge_txhandler`.

### Likelihood Explanation
The precondition is simply that a legitimate Challenge transaction becomes visible (mempool or chain) before the attacker's replacement is mined — which always happens, since Bitcoin broadcast is public. The attacker needs only enough BTC to fund an additional input/fee (ANYONECANPAY permits arbitrary extra inputs) and does not need any key material belonging to the operator, verifier, or aggregator. This is fully unprivileged, cheap, and mechanically deterministic — no hashrate, no key compromise, no social engineering.

### Recommendation
Change the Challenge input's sighash type used for the operator's `CheckSig` signature from `SIGHASH_SINGLE|ANYONECANPAY` to `SIGHASH_ALL` (or `SIGHASH_DEFAULT` for Taproot), so the operator's signature commits to every output including the OP_RETURN carrying the challenger's EVM address, and to the full input set. If per-challenger flexibility is intentionally desired (letting different challengers reuse a pre-signed operator authorization), instead bind the OP_RETURN into the signed message directly (e.g., via a script commitment/hash check) rather than relying on sighash exclusion, or require a fresh operator co-signature per specific challenger identity.

### Proof of Concept
`cargo test` plan (regtest, no mainnet/live Citrea):
1. Set up a deposit/kickoff as in existing e2e tests, and obtain a signed `Challenge` transaction from `create_and_sign_txs`/`get_signed_txs_for_kickoff` with a legitimate challenger EVM address `E1` in its OP_RETURN.
2. Extract the witness signature from input 0 of that transaction.
3. Build a second, unsigned `Challenge`-shaped transaction via `create_challenge_txhandler` reusing the identical `kickoff_txhandler`/`operator_reimbursement_address` (so output 0 is byte-identical), but with `challenger_evm_address = Some(E2)` (attacker-controlled), and add an extra attacker-funded input for fees.
4. Manually insert the extracted signature (with `SinglePlusAnyoneCanPay` sighash flag) into the new transaction's witness and finalize it.
5. Assert `rpc.test_mempool_accept(&[tx])` returns `allowed = true` for the attacker's transaction (proving the operator's original signature validates against a tx with a different OP_RETURN and additional input).
6. Assert `parse_op_return_data` on the accepted attacker tx yields `E2`, not `E1`, while output 0 (operator payment) is identical to the legitimate tx — demonstrating the binding "OP_RETURN EVM address == entity actually owed reimbursement" is broken purely by observing and replaying a public signature.
