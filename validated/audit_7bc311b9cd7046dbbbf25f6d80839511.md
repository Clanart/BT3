## Analysis

The QPDF advisory concerns unbounded/infinite recursion in a document "unparse" routine leading to stack exhaustion on crafted input. Looking for an analogous reachable path in kaia, the closest structural match is the recursive RLP decoding of `accountkey.AccountKeyRoleBased`, which decodes nested account keys via mutually-recursive `DecodeRLP` calls without any depth limit — reachable from a single `TxTypeAccountUpdate` transaction submitted by an unprivileged sender.

`TxInternalDataAccountUpdate.DecodeRLP` decodes the transaction's `Key` field by calling `accountkey.NewAccountKeySerializer()` and `rlp.DecodeBytes(serialized.Key, serializer)`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a `keyType` tag and then calls `s.Decode(serializer.key)` on the concrete key type: [2](#0-1) 

When the type is `AccountKeyRoleBased`, `AccountKeyRoleBased.DecodeRLP` reads a list of byte-strings and, for **each element**, calls `rlp.DecodeBytes(b, &serializer)` again — recursively invoking `AccountKeySerializer.DecodeRLP` → potentially another `AccountKeyRoleBased.DecodeRLP`: [3](#0-2) 

Critically, nothing in this decode path enforces recursion depth or rejects an `AccountKeyRoleBased` nested inside another `AccountKeyRoleBased` at decode time. The only guard against nested role-based keys, `ErrNestedCompositeType`, is checked *after* decoding completes, in `AccountKeyRoleBased.CheckInstallable` (called from `CheckUpdatable`), which only inspects one level of nesting via `IsCompositeType()`: [4](#0-3) 

This means an attacker can construct a deeply nested chain (RoleBased → RoleBased → RoleBased → … ) as raw bytes and feed it as the `Key` field of an `AccountUpdate` transaction (or via the public `kaia_decodeAccountKey`/`kaia_encodeAccountKey`-adjacent path in `api/api_kaia.go`, `DecodeAccountKey`): [5](#0-4) 

Each nesting level costs multiple Go call frames (`rlp.DecodeBytes` → `Stream.Decode` → `decodeDecoder` → `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → recurse). With sufficient nesting depth, this recursion can exhaust the goroutine stack. In Go, stack overflow from unbounded recursion is a **fatal, unrecoverable runtime error** (not a `panic` catchable by `recover()`), so it crashes the entire node process — a far more severe outcome than the original qpdf bug's process crash.

This decode path is invoked:
1. During `TxPool.AddRemote`/block validation when any peer or user submits a raw `AccountUpdate` transaction that gets RLP-decoded (`Transaction.DecodeRLP` → `TxInternalDataSerializer.DecodeRLP` → `TxInternalDataAccountUpdate.DecodeRLP`): [6](#0-5) [7](#0-6) 
2. Via the public RPC `kaia_decodeAccountKey` call directly.

## Conclusion

This constitutes a valid, reachable analog: a single unprivileged transaction (or a public RPC call) can trigger unbounded recursive RLP decoding of a nested `AccountKeyRoleBased` structure, causing uncontrolled stack growth and a node crash — matching the "infinite recursion / stack consumption via crafted input" bug class from the qpdf advisory, but reachable through the standard transaction-submission and public-RPC surfaces rather than a local file parser.

I was not able to fully verify (within available tool budget) the exact maximum practical nesting depth achievable within kaia's transaction size limits (`MaxCodeSize`/tx size caps), nor whether `TxPool` enforces an overall transaction byte-size cap that could limit the achievable RLP nesting depth before the stack actually overflows. This would need to be confirmed by a Devin session that can build a PoC transaction and measure actual stack growth against Go's default goroutine stack limits.

### Title
Unbounded recursive RLP decoding of nested AccountKeyRoleBased causes node crash via stack exhaustion - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each role's key via `rlp.DecodeBytes`, with no depth limit, and the only "no nested RoleBased" check happens *after* decoding is complete. A crafted `AccountUpdate` transaction (or RPC payload) with deeply nested `AccountKeyRoleBased` values can drive Go's recursive `DecodeRLP` calls until the goroutine stack overflows, crashing the node.

### Finding Description
`TxInternalDataAccountUpdate.fromSerializable` calls `rlp.DecodeBytes(serialized.Key, serializer)` on an `AccountKeySerializer`, which dispatches to `AccountKeyRoleBased.DecodeRLP` when the type tag indicates a role-based key. That function loops over encoded sub-keys and calls `rlp.DecodeBytes` again for each — allowing a sub-key to itself be an `AccountKeyRoleBased`, recursing indefinitely. The compile-time protection against nesting (`ErrNestedCompositeType` in `CheckInstallable`/`CheckUpdatable`) only runs after the full (already recursively decoded) structure exists in memory, so it cannot prevent the decode-time recursion itself.

### Impact Explanation
Uncontrolled Go-level recursion leading to stack overflow is a fatal runtime error that cannot be recovered via `defer/recover`, crashing the entire node process. If exploitable via a standard transaction broadcast (mempool ingestion) or the public RPC (`kaia_decodeAccountKey`), this is a remotely triggerable denial-of-service against any node that processes the transaction or serves the RPC call.

### Likelihood Explanation
Constructing nested RLP-encoded `AccountKeyRoleBased` bytes requires no special privileges — any transaction sender or RPC caller can submit one. The likelihood of reaching the vulnerable decode path is high; the main uncertainty is whether transaction/RPC payload size limits cap achievable nesting depth below the threshold needed to actually overflow the stack.

### Recommendation
Add an explicit recursion/nesting depth counter (or reject any `AccountKeyRoleBased` sub-key whose type is also `AccountKeyRoleBased`) directly inside `AccountKeyRoleBased.DecodeRLP` / `AccountKeySerializer.DecodeRLP`, before recursing, rather than deferring the check to post-decode validation (`CheckInstallable`).

### Proof of Concept
Construct an RLP payload where an `AccountKeySerializer` of type `AccountKeyTypeRoleBased` contains one role entry that is itself an `AccountKeySerializer` of type `AccountKeyTypeRoleBased`, nested N times (e.g., tens of thousands of levels), each wrapped as its own self-contained RLP byte-string per `AccountKeyRoleBased.DecodeRLP`'s `[][]byte` encoding. Submit this as the `Key` field of a `TxTypeAccountUpdate` transaction via `AddRemote`, or pass the raw bytes to the `kaia_decodeAccountKey` RPC method, and observe the goroutine stack growth from the recursive `rlp.DecodeBytes` → `AccountKeyRoleBased.DecodeRLP` chain. 	// A zero-role key is not allowed.

		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.

		return kerrors.ErrLengthTooLong
	}

		}
		// If any key in the role cannot be initialized, return an error.

		}
	}
