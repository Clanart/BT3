## Analysis

The external report's core invariant is: **a value escrowed by a user-facing function has no reachable path back to the user once the system enters a protective "frozen" mode**, causing a portion of user funds to be permanently stuck. The Hyperbridge analog to this is the **relayer-fee escrow held by `EvmHost`**, whose only refund/payout paths are gated by the very same `FrozenStatus` freeze mechanism used to protect the bridge, with no dedicated fallback to release stuck fees.

### Title
Escrowed relayer fees become permanently unrecoverable while `EvmHost` is frozen with `FrozenStatus.Incoming`/`All` - (File: `evm/src/core/HandlerV2.sol`, `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch()` escrows the caller's relayer fee into `_requestCommitments[commitment]` and is only blocked when `_frozen == FrozenStatus.Outgoing || FrozenStatus.All`. However, every function capable of releasing that escrow — `handlePostRequestTimeouts`, `handleGetRequestTimeouts`, `handlePostRequests`, and `handleGetResponses` in `HandlerV2.sol` — is guarded by `modifier notFrozen(IHost host)`, which reverts with `HostFrozen()` whenever `FrozenStatus.Incoming` or `FrozenStatus.All` is set. This creates the same asymmetry as the reported bug: deposits/escrow can still be created, but the only mechanism to return them is disabled by the same emergency state.

### Finding Description
`EvmHost.dispatch()` is guarded only against `Outgoing`/`All`: [1](#0-0)  so a user can still call `dispatch()` — locking a relayer fee into escrow — while the host is set to `FrozenStatus.Incoming` [2](#0-1) .

The refund/payout side is gated the opposite way. `HandlerV2`'s `notFrozen` modifier blocks any call when the host is `Incoming` or `All`: [3](#0-2) . This modifier is applied to `handlePostRequestTimeouts` (refunds relayer fee to `payer` on timeout) [4](#0-3)  and to `handleGetRequestTimeouts` [5](#0-4) , as well as `handlePostRequests`/`handleGetResponses`, which pay out the relayer fee on successful delivery [6](#0-5) .

`setFrozenState` can only be reversed by the `admin` or `handler` [7](#0-6) , and freezing is documented as the legitimate, non-malicious response to a byzantine/eclipse consensus event, intended to persist "until the source chain recovers" [8](#0-7) . There is no dedicated "sweep escrow" or emergency-withdraw function for `_requestCommitments` funds — the ERC20 fee-token balance backing every pending commitment sits in the general `EvmHost` balance, and the only exit path (timeout/delivery processing) is exactly what the freeze disables. Once frozen under `Incoming`/`All`, any relayer fee escrowed for a request whose timeout proof (or delivery proof) hasn't yet been submitted is stuck for the entire duration of the freeze, which by design has no fixed end.

### Impact Explanation
This is a direct, local analog of the reported class: an escrowed value (`WITHDRAWAL_STAKE` there, relayer fee escrow here) that a normal operational path deposits, but for which the *only* release mechanism is disabled precisely during the protocol's own emergency/frozen mode — the same scenario `exodusMode` represents for the zkSync-style system in the original report. Funds already escrowed via `dispatch()` (and any new ones deposited while only `Outgoing` is not yet set) become non-refundable and non-payable for the freeze's duration, matching the "portion of user funds lost" impact class.

### Likelihood Explanation
Freezing is a documented, intended emergency response to consensus byzantine behavior, not a rare or purely hypothetical trigger [9](#0-8) . Because unfreezing requires admin/governance action with no committed timeline, any relayer fee escrow that is pending at freeze time (or created before `Outgoing` freeze is also applied) is exposed to this lock for as long as the freeze lasts.

### Recommendation
Decouple escrow release from the frozen-state gate: either (a) add a dedicated, always-available refund function that lets the `payer` reclaim their escrowed fee for requests whose timeout has passed, independent of `FrozenStatus`, or (b) scope `notFrozen` on the timeout-processing functions to only check proof-related freezes (e.g., disallow processing *new* incoming proofs) while still allowing timeout refunds tied to already-verified/expired state commitments to proceed.

### Proof of Concept
1. User calls `EvmHost.dispatch(post)` with `post.fee = X`; `X` fee tokens are pulled and recorded in `_requestCommitments[commitment]` [10](#0-9) .
2. Admin (or handler, in response to a detected byzantine consensus fork) calls `setFrozenState(FrozenStatus.Incoming)` [7](#0-6) .
3. The request times out. Relayer submits `handlePostRequestTimeouts(host, message)` to refund `X` to the `payer` — this reverts with `HostFrozen()` because `notFrozen(host)` sees `FrozenStatus.Incoming` [3](#0-2) [11](#0-10) .
4. Meanwhile `dispatch()` is still callable (only blocked by `Outgoing`/`All`), so more user fees continue accumulating in escrow with no way back out.
5. Until the admin explicitly unfreezes the host, `X` (and any further escrowed fees) remains locked in the `EvmHost` contract with no function available to reclaim it.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }

### Optimistic Bridging

To prevent the damage that can be done to our bridge in the event of a byzantine attack, **we must introduce a challenge window in the form of a time delay between when consensus proofs are verified by our consensus client and when state proofs associated with those headers can be used to process cross-chain messages.**

During this challenge window, consensus clients can detect byzantine attacks. Off-chain consensus clients can do this by participating in the P2P network. On-chain consensus clients, on the other hand, will need to rely on off-chain parties, which we'll call fishermen<sup>[3]</sup>, to provide the proofs of fraud to the client.

These fishermen will need some incentive to watch for byzantine attacks and report the fraud proofs which will safeguard the consensus client. As such, we will require relayers who submit consensus proofs to be staked, in the event of byzantine attacks, relayer’s stake can be used to incentivise fishermen to submit fraud proofs.

In the event of a byzantine attack, the fraud proofs will allow for the consensus client to go into a frozen state until the source chain recovers from this byzantine state, **The host chain can then unfreeze the consensus client through some kind of on-chain governance, allowing the bridge to resume operations safely and without any loss of funds ever having occurred.**
