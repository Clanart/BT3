### Title
Single global `max-confidence-ratio` applied to all Pyth-priced assets causes stale-price DoS on volatile assets and under-protection on stable ones - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Zest's oracle confidence check uses one protocol-wide `max-confidence-ratio` data-var to validate the Pyth confidence interval for every asset (STX, sBTC, stSTX, USDC, USDH), the same "one-size-fits-all cap" pattern flagged in the referenced MultiFlowPump finding, where a single hardcoded/global threshold is used to gate multiple assets with fundamentally different volatility profiles.

### Finding Description
`check-confidence` gates every Pyth price resolution against a single, asset-agnostic ratio: [1](#0-0) 

This ratio is stored as one global data-var, defaulting to 10% of price, with no per-asset dimension: [2](#0-1) 

It is invoked identically for every asset routed through `resolve-pyth`, regardless of which feed (BTC, STX, USDC, USDH) is being resolved: [3](#0-2) 

The DAO can adjust the value, but only as a single global number for the whole protocol - it cannot be tuned per asset type: [4](#0-3) 

This mirrors the reported MultiFlowPump defect exactly: a single hardcoded/global cap (`LOG_MAX_INCREASE`/`LOG_MAX_DECREASE` there, `max-confidence-ratio` here) is applied uniformly across assets whose normal confidence-interval-to-price ratios differ significantly by design (e.g., BTC/STX naturally have wider Pyth confidence intervals as a % of price than USDC/USDH). Note this is distinct from `max-staleness`, which the protocol correctly implements per-asset via the asset registry: [5](#0-4) 

### Impact Explanation
Because the ratio is tuned for a "typical" asset rather than per-asset:
- For higher-volatility assets (BTC/STX), a threshold generic enough to allow legitimate stablecoin updates can be too tight during real volatility spikes, causing `ERR-PRICE-CONFIDENCE-LOW` to reject legitimate price updates. Price resolution then continues to rely on the previously cached/last price (via `last-update`/`oracle-timestamp-fresh`) longer than intended, i.e. a stale price is used for collateral valuation, LTV, and liquidation checks feeding `price-resolve`/`price-multi-resolve`: [6](#0-5) 
- For lower-volatility assets (USDC/USDH), the same threshold may be too loose relative to their normal tight confidence bands, allowing a wide-confidence (i.e., low-quality/manipulated) price update to pass the check unchallenged and be used as the "true" price for collateral/debt valuation.

Either direction risks the protocol using an incorrect price for collateral/debt accounting, which can allow borrowing against overvalued collateral (theft / undercollateralized debt / potential insolvency) or block legitimate liquidations/updates on volatile collateral (temporary freezing of funds during the staleness window).

### Likelihood Explanation
This does not require any oracle manipulation or DAO misconfiguration - it is triggered by ordinary, expected market volatility differences between asset classes under the current, singleton `max-confidence-ratio` design. Every price resolution for every asset already passes through `check-confidence`, so the exposure is present on every price update, not a rare edge case.

### Recommendation
Make the confidence-ratio threshold per-asset, analogous to how `max-staleness` is already stored per-asset in the asset registry (`assets.clar`), rather than a single global data-var in `market.clar`. Pass/read the asset-specific confidence ratio in `check-confidence` and `resolve-pyth` the same way `max-staleness` is threaded through `price-resolve`.

### Proof of Concept
1. DAO sets `max-confidence-ratio` to 1000 (10%) as a reasonable value for STX/BTC volatility (`set-max-confidence-ratio`, `mainnet/contracts/market/v0-4-market.clar:995-1010`).
2. During normal Pyth reporting for USDC/USDH, confidence naturally sits well under 10% of price; a manipulated or degraded feed update reporting a much wider confidence interval (but still <10% of price) is accepted by `check-confidence`, even though it would be considered anomalously wide for a stablecoin.
3. Conversely, during a period of real BTC/STX volatility, Pyth's confidence interval legitimately exceeds 10% of price; `check-confidence` reverts with `ERR-PRICE-CONFIDENCE-LOW`, forcing the market to keep using the older cached price (via `oracle-last-update`/`last-update` map) for collateral/LTV/liquidation math until confidence narrows again, even though the underlying price may have moved substantially.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
