### Title
`GeneratorPromotion::complete` panics on a malformed proof map missing any participant index — (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the *count* (`n - 1`) and the upper bound (`<= n`) of the `proofs` map keys, but never checks that the map actually contains every other participant's index, nor that it excludes the local participant's own index. A malformed map — e.g. containing `params.i()` and omitting some other participant `j` — satisfies both checks and then hits `proofs.get(&i).unwrap()`, panicking the caller. This is the Serai analog of CVE-2017-7302: a missing validity check on attacker-influenced structured input leads to a crash rather than a clean error.

### Finding Description
In `complete`, the validation is:

```rust
// crypto/dkg/promote/src/lib.rs:125-136
if proofs.len() != (usize::from(params.n()) - 1) {
  Err(PromotionError::IncorrectAmountOfParticipants { .. })?;
}
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() {
    Err(PromotionError::InvalidParticipant { .. })?;
  }
}
```

Then every participant index `1 ..= n` except `params.i()` is dereferenced unconditionally:

```rust
// crypto/dkg/promote/src/lib.rs:140-146
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();
```

Because `Participant` values are only range-checked, a `HashMap` of size `n - 1` whose keys are `{params.i(), 1, ..., n} \ {j}` (i.e., includes the local participant and omits honest participant `j`) passes both checks. The loop then calls `proofs.get(&j).unwrap()` on the missing key and panics.

The `proofs` map is populated from bytes read via `GeneratorProof::read` (`share: C::read_G`, `proof: DLEqProof::read`, lib.rs:72-77), i.e., untrusted peer-supplied data keyed by claimed `Participant` index. A faulty participant can cause a coordinator/processor integrating this API to build such a map (e.g., by sending a proof attributed to the wrong index, or the integrator deduplicating on a colliding key), turning a routine `Err` path into a process-aborting panic — the same "missing check for unrecognised input → crash" shape as `swap_std_reloc_out`.

### Impact Explanation
Denial of service of the generator-promotion (key migration) flow. Any participant able to influence the construction of the `proofs` map — directly by submitting a `GeneratorProof` under an unexpected index — can crash the promoting node instead of receiving a clean `PromotionError`. Since promotion runs once per participant set and is on the critical path for generator/key rotation, a panic here halts the protocol for the victim. No secret material is leaked, so this maps to Medium/High availability impact (comparable to the CVE's A:H rating).

### Likelihood Explanation
Triggering requires a map of exactly `n - 1` entries with all keys `<= n` but a missing non-self index — achievable whenever a proof is filed under a duplicate or the victim's own `Participant` index. The proof bytes themselves are fully attacker-controlled (unprivileged DKG/promotion peer input), and the API contract ("proofs from all other participants") is not enforced by the callee, so any integrator that keys the map by a peer-claimed index is exposed.

### Recommendation
Replace the count-and-range checks with an explicit membership check, matching the style of `validate_map` used elsewhere in the codebase: verify `proofs.keys()` equals `all_participant_indexes() \ {params.i()}` (rejecting any key equal to `params.i()`), or at minimum return `Err(PromotionError::InvalidParticipant { .. })`/`IncorrectAmountOfParticipants` instead of `unwrap()`-ing `proofs.get(&i)` at crypto/dkg/promote/src/lib.rs:146.

### Proof of Concept

// Pseudo-PoC against crypto/dkg/promote/src/lib.rs
let (promotion, _proof) = GeneratorPromotion::<C, C2>::promote(&mut rng, base_keys);
let n = base_keys.params().n();
let me = base_keys.params().i();

// Build a map of n - 1 proofs, all with valid indexes <= n,
// but keyed under `me` instead of some other participant `j`.
let mut proofs: HashMap<Participant, GeneratorProof<C>> = HashMap::new();
for l in 1 ..= n {
  let l = Participant::new(l).unwrap();
  if l == Participant::new(n).unwrap() { continue; } // omit participant n
  proofs.insert(l, some_valid_proof);                // includes `me`, misses `n`
}
assert_eq!(proofs.len(), usize::from(n) - 1);        // passes the len check
// All keys <= n: passes the range check.
promotion.complete(&proofs); // panics at proofs.get(&n).unwrap()
