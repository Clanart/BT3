### Title
Unchecked addition overflow in the `NotEnoughFunds` guard lets an attacker craft payments whose total wraps past the balance check, producing a signed consensus-invalid transaction and burning the selected inputs - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` validates solvency with `input_sat < (payment_sat + needed_fee)`, but both `payment_sat` (a `u64` sum of attacker-influenced payment amounts) and the `payment_sat + needed_fee` addition use unchecked wrapping arithmetic. With two or more payments each passing the `DUST` check but summing above `u64::MAX` (or whose sum plus `needed_fee` overflows), the comparison wraps to a small value, the `NotEnoughFunds` check is bypassed, and a transaction whose outputs exceed its inputs is constructed and signed.

### Finding Description
The vulnerability class of the external report is "a quantity is checked, then used in arithmetic that can wrap/revert" (`gasleft()` checked once, then `gasleft() - _recoverGas` evaluated on a smaller second read). In `SignableTransaction::new` at `networks/bitcoin/src/wallet/send.rs:187` and `:215`:

```rust
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();          // line 187
...
if input_sat < (payment_sat + needed_fee) {                                       // line 215
  Err(TransactionError::NotEnoughFunds { ... })?;
}
```

`sum::<u64>()` wraps on overflow in release builds, and `payment_sat + needed_fee` is an unchecked `u64` addition. Each individual payment only has to satisfy `*amount >= DUST` (line 165-169); there is no upper bound per payment and no `checked_add`/`checked_sum`. An attacker supplying two payments of ~2^63 sats each makes `payment_sat` wrap to a small number, so `input_sat < wrapped_total` is false and the guard passes. The resulting `tx_outs` (lines 188-191) carry the huge `Amount::from_sat(payment.1)` values, so `sum(outputs) > sum(inputs)`. Later, `fee()` (lines 138-141) computes `prevouts_sum - outputs_sum`, which underflows/panics in debug builds and returns a meaningless wrapped value in release. The signed transaction is consensus-invalid (`bad-txns-out-bigger-than-in`), so it can never confirm.

Note the change-handling path at line 228 correctly uses `input_sat.checked_sub(...)`, showing the codebase knows this arithmetic needs checking — the solvency check itself was missed.

### Impact Explanation
The FROST `TransactionMachine` will produce valid Schnorr signatures for this malformed transaction (signing commits only to the sighash, which is computed over the invalid tx fine). Consequences:

- The honest inputs selected cannot be spent by this transaction; if any input were spent via a valid co-spend race or the attacker's goal is simply griefing, the threshold group's UTXOs are burned into an unspendable signed artifact and a signing attempt (fresh nonces) is consumed.
- `fee()` underflow panics crash any code path calling it on such a transaction (DoS of the signer/coordinator accounting).
- This mirrors the report's impact: a guard that should gracefully reject the operation is bypassed by wrapping arithmetic, and the failure surfaces later as a revert/panic/loss rather than a clean rejection.

### Likelihood Explanation
Payments amounts are attacker-influenced data (withdrawal instructions flowing into the transaction builder). No privileged position, collusion, or malicious validator is needed — only control over the `(ScriptBuf, u64)` payment list passed to `SignableTransaction::new`. Each payment only needs `>= DUST`, so arbitrary large values up to `u64::MAX` are accepted by all local validation. Medium severity: the output transaction is provably unspendable (bounded loss of signed-inputs/attempts and a reachable panic), rather than direct theft.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`:

```rust
let payment_sat = payments.iter().try_fold(0u64, |acc, p| acc.checked_add(p.1))
  .ok_or(TransactionError::NotEnoughFunds { inputs: 0, payments: u64::MAX, fee: 0 })?;
let total_needed = payment_sat.checked_add(needed_fee)
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: payment_sat, fee: needed_fee })?;
if input_sat < total_needed { ... }
```

Additionally, reject payments whose value exceeds the input total or a sane maximum, and make `fee()` use `checked_sub` (or `saturating_sub`) so an inconsistent transaction errors instead of panicking.

### Proof of Concept
```rust
let inputs = vec![received_output_with_value(1_000_000)]; // 0.01 BTC
let payments = vec![
  (script_a, u64::MAX - DUST),  // passes *amount >= DUST
  (script_b, u64::MAX - DUST),  // sum wraps
];
// payment_sat wraps to ~2^64 - 2*DUST mod 2^64 (small), or payment_sat + needed_fee wraps
let tx = SignableTransaction::new(inputs, &payments, None, None, 10);
// Expected: Err(NotEnoughFunds). Actual: Ok(tx) with outputs >> inputs.
// tx.fee() then underflows/panics; multisig(..).sign(..) signs an invalid tx.
```
