## Title
Argument injection into `git tag -d` via unsanitized tag name — (File: `app/src/lib/git/tag.ts`)

## Summary
`deleteTag` builds the git command as `['tag', '-d', name]` and passes `name` straight through to `git` without a `--` operand separator or leading-dash rejection. [1](#0-0) 

## Finding Description
The `git()` call in `core.ts` uses `dugite`'s `exec`, which spawns git via argv (no shell), so shell-metacharacter injection is not possible here — the risk is purely argument/option injection at the git-CLI level, i.e., a `name` value beginning with `-`/`--` being parsed by `git tag` as a flag rather than an operand.

Tag names that reach `deleteTag` originate from `getAllTags`, which parses `git show-ref --tags -d` output for the local repository — including tags fetched or cloned from an attacker-controlled remote. [2](#0-1)  This differs from tags created *inside* Desktop's own Create Tag dialog, whose names go through `RefNameTextBox`/`sanitizedRefName`, which strips leading `-`/`+` characters before the tag is created. [3](#0-2)  That sanitization is only applied at tag-creation time in the UI; it is not applied to tag names discovered from `getAllTags` (which can include refs the local repo learned about from a remote), and `deleteTag` itself performs no such check before invoking `git tag -d`.

`git`'s ref-name syntax rules (`check-ref-format`) do not categorically forbid a leading `-` in a ref name; that restriction is enforced by higher-level porcelain commands like `git branch`/`git tag` when *creating* a ref, not by the ref-storage format itself. This means a ref such as `refs/tags/-f` (or similar) can in principle exist in a fetched repository's ref namespace even though Desktop's own UI would never create it.

Given this, `deleteTag(repository, name)` will place such a name directly after `-d` with no `--` separator: `args = ['tag', '-d', name]`.

## Impact Explanation
`git tag`'s own option surface is comparatively small (`-d`, `-l`, `-n`, `-f`, `-m`, `-F`, `-a`, `-s`, `-u`, `--format`, `--sort`, etc.). Because `-d` is already fixed as the first flag and the command takes no other user-influenced arguments, an attacker-crafted `name` beginning with `-` would most likely be interpreted as an incompatible/duplicate action flag and cause `git tag` to error out (e.g., "only one action of -l, -d, or -v is allowed"), rather than achieve file read/write or code execution. I could not find a demonstrated path in this codebase turning this into the "Critical" impact described in the target text (arbitrary git/process option execution with file write/read or credential exfiltration) — that would require an option like `-F<file>`/`--file=<file>` to actually take effect alongside `-d`, which is not confirmed here and would need direct testing against the real `git tag` binary to verify whether git accepts the combination or hard-errors.

## Likelihood Explanation
An attacker who controls a remote/repository the victim clones or fetches from could plausibly create a ref under `refs/tags/` with a name starting with `-`, since normal Desktop-side tag-name sanitization does not apply to refs that arrive via fetch. The reachability of `deleteTag` itself requires the user to explicitly select "Delete Tag" from the UI, which is a genuine user action, not a passive/automatic trigger.

## Recommendation
- In `deleteTag` (and `createTag`), insert a `--` separator before the ref/name operand, e.g. `['tag', '-d', '--', name]`, so git treats `name` strictly as an operand regardless of its content.
- Apply the same leading-dash/invalid-character validation used in `sanitizedRefName`/`testForInvalidChars` to any tag name obtained from `getAllTags` (i.e., names originating from fetched refs) before it can be passed to `deleteTag`, not just to names entered via the Create Tag dialog.

## Proof of Concept
Not independently reproduced/confirmed against a live `git tag` binary in this review — the described mechanism (unsanitized ref name reaching `git tag -d` as a bare argv element without a `--` separator) is verified from the source, but the exact behavioral outcome of a specific hostile flag value (e.g., whether git errors out or partially executes a secondary action) needs to be validated by actually running `deleteTag(repository, '-F/some/file')`-style inputs against the real git binary, which was not done here. export async function getAllTags(
  repository: Repository
): Promise<Map<string, string>> {
  const args = ['show-ref', '--tags', '-d']

  const tags = await git(args, repository.path, 'getAllTags', {
    successExitCodes: new Set([0, 1]), // when there are no tags, git exits with 1.
  })

  const tagsArray: Array<[string, string]> = tags.stdout
    .split('\n')
    .filter(line => line !== '')
    .map(line => {
      const [commitSha, rawTagName] = line.split(' ')

      // Normalize tag names by removing the leading ref/tags/ and the trailing ^{}.
      //
      // git show-ref returns two entries for annotated tags:
      // deadbeef refs/tags/annotated-tag
      // de510b99 refs/tags/annotated-tag^{}
      //
      // The first entry sha correspond to the blob object of the annotation, while the second
      // entry corresponds to the actual commit where the tag was created.
      // By normalizing the tag name we can make sure that the commit sha gets stored in the returned
      // Map of commits (since git will always print the entry with the commit sha at the end).
      const tagName = rawTagName
        .replace(/^refs\/tags\//, '')
        .replace(/\^\{\}$/, '')

      return [tagName, commitSha]
    })

  return new Map(tagsArray)
}

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
