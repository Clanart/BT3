### Title
Deserialized `ThresholdKeys` accepts identity verification shares, yielding a forgeable identity group key - (File: crypto/dkg/src/lib.rs)

### Summary
The XXE advisory is about a parser consuming attacker-supplied input without disabling a dangerous class of values (external entities enabling secret exfiltration). The Serai analog is `ThresholdKeys::read`: it parses untrusted bytes into verification shares via `Ciphersuite::read_G`, which enforces canonical encoding but explicitly does **not** reject the identity point. `ThresholdKeys::new` then computes the group key by summing the first `t` verification shares, with no identity check on either the shares or the result. A crafted serialization whose first `t` shares are all identity produces `group_key == identity`, a public key whose discrete log is zero — trivially forgeable signatures and, for Bitcoin outputs, funds anyone can take.

### Finding Description
`Ciphersuite::read_G` validates canonicity (`to_bytes()` round-trip) but permits the identity element, unlike `Curve::read_G` in FROST which explicitly rejects identity [1](#0-0) [2](#0-1) . `ThresholdKeys::read` reads `n` verification shares using `<C as Ciphersuite>::read_G` — the identity-accepting variant — and passes them to `ThresholdKeys::new` [3](#0-2) . `ThresholdKeys::new` checks only the count and participant indexes, then derives `group_key` as the interpolated sum of shares `1..=t` with no identity check [4](#0-3) . The Schnorr verification equation `s·G == R + c·A` degenerates to `s·G == R` when `A` is the identity point, so any `(R = s·G, s)` pair verifies.

### Impact Explanation
Just as XXE let an attacker-controlled document cause the parser to resolve attacker-chosen entities, here attacker-chosen bytes cause the deserializer to construct a key the signer/verifier trusts but which is controlled by no one (discrete log 0). Consequences: forged threshold Schnorr/FROST signatures against the deserialized view, or a wallet registering an identity group key — deposits reported received are spendable by anyone (or effectively unspendable by the validator set), matching "funds reported received that are not spendable" / "forged signature" acceptance criteria.

### Likelihood Explanation
Requires an attacker to supply the serialized `ThresholdKeys` bytes a party loads (e.g., a crafted backup/restore, coordinated key blob, or any path feeding untrusted bytes to `ThresholdKeys::read`). It is not a malicious-DKG-participant attack — the DKG output is honest; the corruption happens purely at deserialization of externally supplied bytes. Rated Medium, mirroring the source advisory.

### Recommendation
In `ThresholdKeys::new` (or `ThresholdKeys::read`), reject any identity verification share and reject an identity `group_key`. Alternatively, read shares via an identity-rejecting helper equivalent to `Curve::read_G`.

### Proof of Concept
1. Build a byte string for `ThresholdKeys::<C>::read`: `C::ID` header, `t = n = i = 1` (or any `t, n`), `Interpolation::Lagrange` (`0x01`), any canonical `secret_share`, then `n` copies of `C::G::identity().to_bytes()`.
2. `read` succeeds; `group_key == identity`, `view(...)` yields `group_key = identity` (scalar=1, offset=0).
3. Forge: pick any `s`; set `R = s·G`; `SchnorrSignature { R, s }` verifies against the identity group key for any challenge.
