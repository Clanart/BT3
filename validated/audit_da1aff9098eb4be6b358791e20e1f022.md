### Title
Panic on identity aggregate nonce in BIP-340 `hram` via adversarially-crafted preprocess commitments — (`networks/bitcoin/src/crypto.rs`)

### Summary
The Bitcoin-specific `Hram` implementation calls `x(R)` / `x(A)`, which `expect()` that the point is not the point at infinity. A malicious signing participant can craft `Commitments` in their preprocess such that the aggregate nonce `R = Σ ρᵢ·(Dᵢ + Eᵢ …)` is the point at infinity, causing `Hram::hram` → `x()` to panic during `sign_share` — the exact analog of CVE-2019-8379 (crafted input reaching a dereference/unwrap on an invalid value, yielding a crash/DoS).

### Finding Description
`crypto.rs` defines helpers that unconditionally unwrap on the point at infinity:

- `fn x(key: &ProjectivePoint) -> [u8; 32]` — `key.to_encoded_point(true)` then `encoded.x().expect("point at infinity")` [1](#0-0) 
- `fn x_only(key: &ProjectivePoint)` — `XOnlyPublicKey::from_slice(&x(key)).expect(...)` [2](#0-1) 
- `Hram::hram` feeds attacker-influenced `R` into `x(R)` during challenge computation [3](#0-2) 

The `R` passed to `hram` is the aggregate nonce built inside `AlgorithmSignMachine::sign` from the `BindingFactor`-weighted sum of all participants' preprocess commitments: `B.nonces(&nonces)` produces `Rs`, which the algorithm's `sign_share` uses to compute the challenge via `hram(&R_sum, &group_key, msg)` [4](#0-3) . Each participant's preprocess (including their `Commitments` points) is read from untrusted bytes through `read_preprocess` → `Commitments::read` [5](#0-4) . The doc comments even acknowledge the panic surface: "If either `R` or `A` is the point at infinity, this will panic" [6](#0-5) , and "verify, verify_share MUST be called after sign_share … Otherwise, this library MAY panic" [7](#0-6) .

A single malicious participant in the signing set can compute the binding factors (ρ is derived from a transcript over all preprocesses, which are broadcast) and choose their own nonce commitments such that the weighted aggregate nonce `R` equals the identity. Even if `Commitments::read` rejects identity-encoded individual points, nothing prevents the *sum* of valid, non-identity points from being the identity — this is the standard rogue-key/cancellation degree of freedom, requiring no collusion beyond the attacker's own preprocess slot.

### Impact Explanation
When `sign_share` invokes `Hram::hram` on the identity `R`, `x(R)` executes `.expect("point at infinity")` and panics [1](#0-0) . This is a remotely-triggerable abort of the FROST signing session for Bitcoin (the crate used for Taproot/Schnorr signing in `networks/bitcoin`). Any unprivileged participant who can submit a preprocess (an in-scope "messages they cause to be signed" input) can crash the signing task of every honest participant that processes it — mirroring CVE-2019-8379's crafted-file → segfault DoS. In Serai deployments where panics propagate to process exit (the codebase sets exactly such a panic hook in coordinator/relayer binaries), this is a full node DoS that also halts the signing round, forcing a retry the attacker can grief again.

### Likelihood Explanation
High within a signing session: the attacker needs only one preprocess slot in the `included` set — no threshold collusion. They observe other participants' preprocesses (rushing/cancelling order is typical in these protocols, and even without rushing they can iterate), derive the binding factors from `FROST_rho` [8](#0-7) , and solve for commitments whose bound contribution negates the honest partial sum. The panic path is unconditional once `R` is identity — there is no `is_identity` guard around `x()`/`x_only()`/`hram` [9](#0-8) . The same panic is reachable in `Schnorr::verify` if the completed `sig.R` is identity (`needs_negation(&sig.R)` is safe but `sig.serialize()`/signature path aside, `verify` first routes through `hram`-style challenge logic in `FrostSchnorr`) — the documented "negligible probability" assumption is false under adversarially-chosen commitments rather than random nonces.

### Recommendation
- In `x`/`x_only`/`Hram::hram` (`networks/bitcoin/src/crypto.rs`), return a recoverable error (or map identity to a defined rejection) instead of `expect`/panic when `R` or `A` is the point at infinity.
- In `AlgorithmSignMachine::sign` / `BindingFactor::nonces` (`crypto/frost/src/sign.rs`), reject the signing set early if any aggregate `R` in `Rs` is identity — return `FrostError` rather than proceeding into an HRAm that panics.
- Additionally, have `Commitments::read` reject individual identity nonce commitments and have `verify`/`complete` check the final `sig.R`/`Rs` for identity before computing challenges, so a crafted preprocess yields `FrostError::InvalidParticipant`/blame rather than a crash.

### Proof of Concept
```rust
// Honest participants publish preprocesses for a Schnorr (BIP-340) signing
// session over Secp256k1. Malicious participant m waits, then computes:
//   rho_transcript = FROST_rho over (group_key, hash_msg(msg), all preprocesses)
//   rho_i = binding factor for each participant i
// Let S = sum over honest i of rho_i * D_i (and the E_i analogue).
// m chooses its commitments D_m, E_m such that
//   rho_m * (D_m + rho'_m * E_m)  ==  -S        // per FROST's bound-commitment form
// making aggregate R = identity.
//
// m then broadcasts preprocess = Commitments { nonces: [D_m, E_m, ...] }
// via AlgorithmSignMachine::read_preprocess (valid, non-identity points).
//
// When each honest signer calls:
//   machine.sign(preprocesses_including_m, msg)
// → B.nonces(&nonces) yields R = identity
// → FrostSchnorr::sign_share → Hram::hram(&R, &A, msg)
// → x(&R) → encoded.x().expect("point at infinity")
// → panic: "point at infinity"  (networks/bitcoin/src/crypto.rs:15)
//
// Result: signing task/process aborts; session can be re-griefed indefinitely.
```

Note: I could not fully verify within the available iterations whether `Commitments::read`/`B.nonces` already reject identity sums elsewhere in `crypto/frost/src/nonce.rs`; if such a guard exists, the panic path in `x()` remains reachable only via `verify`/blame paths or other algorithms' addenda, which would weaken but not eliminate the finding.
