### Title
First-staker-after-zero-stake can capture queued rewards accrued during a zero-`totalStaked` window - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2._provisionReward` queues incoming rewards into `rewardInfo.queuedRewards` whenever `totalStaked() == 0`, and only converts that queue into `rewardPerTokenStored` on the *next* call to `_provisionReward` (via `queueNewRewards`/`donateRewards`), using whatever `totalStaked()` is at that later time. Since `BribeRewardPool` inherits `_provisionReward` unmodified and only overrides `totalStaked()`/`balanceOf()` to use its own `totalSupply`/`_balances` bookkeeping, the same flaw applies: whoever is staked at the moment the queue is flushed captures the entire queued amount, regardless of whether they were staked while it accrued.

### Finding Description
`_provisionReward` in `rewards/BaseRewardPoolV2.sol` (lines 290-314) does:
- if `totalStaked() == 0`, add `_amountReward` to `rewardInfo.queuedRewards` and do nothing else (no `rewardPerTokenStored` change).
- otherwise, pull in any leftover `queuedRewards`, and distribute `(queuedRewards + _amountReward)` proportionally to `totalStaked()` **at the time this call executes**.

`BribeRewardPool.totalStaked()` returns `totalSupply` (line 48-50 of `rewards/BribeRewardPool.sol`), which is only mutated in `stakeFor`/`withdrawFor`, both `onlyOperator` (MasterMagpie). `_balances`/`totalSupply` accounting doesn't retroactively track *when* rewards were queued relative to a user's staked period — `userRewardPerTokenPaid` is stamped to the current `rewardPerTokenStored` at stake time (via the `updateRewards` modifier in `stakeFor`), which has not yet been advanced by the queued-but-unflushed reward. When the next `_provisionReward` call flushes the queue, the increase in `rewardPerTokenStored` is computed over the *current* `totalStaked()`, so any staker present at flush time — even one who staked after the reward accrued during the zero-supply window — receives their share (potentially 100% if they're the sole staker) of reward they had no economic claim to.

`donateRewards` is a fully permissionless external function (no access control beyond `isRewardToken` check), and `queueNewRewards` is normally called routinely by a reward manager/bot without regard to current `totalStaked()`. Neither function checks whether a "flush window" following zero-supply is fair game for whoever just staked.

### Impact Explanation
This is theft of unclaimed yield: rewards intended to compensate stakers who held the position while the reward-generating activity (bribes/incentives routed into `queueNewRewards`) occurred can instead be captured entirely by an unrelated party who stakes only after `totalStaked` returns from zero, immediately before/at the flush. This matches Immunefi's "theft of unclaimed yield" impact class.

### Likelihood Explanation
Preconditions are realistic and do not require any privileged action from the attacker: all it takes is (1) the pool's `totalStaked()` reaching zero — plausible for `BribeRewardPool`-backed pools that periodically empty between epochs or during low-TVL periods — and (2) a routine, permissionless/manager reward push (`donateRewards` or `queueNewRewards`) occurring during that window. The attacker only needs capital to be the (first) staker via a normal `MasterMagpie.deposit → stakeFor` call once the reward has been queued, requiring no special role. This is repeatable every time supply hits zero.

### Recommendation
Do not allow `rewardPerTokenStored` to be advanced using `totalStaked()` measured after the reward was queued while supply was zero without accounting for the elapsed period; instead, either revert/return the reward to sender when `totalStaked()==0` and don't allow silent queuing, or track a snapshot/timestamp so that queued rewards during a zero-supply window are distributed only to stakers who were active when the reward was generated (e.g., escrow to protocol treasury or refund to depositor instead of auto-crediting the first re-staker).

### Proof of Concept
Foundry test outline:
1. Deploy `BribeRewardPool` (via `BaseRewardPoolV2` constructor) with a mock `MasterMagpie` and a reward ERC20.
2. Have `userA` stake via `MasterMagpie.deposit` → `stakeFor`, generating `totalStaked() > 0`.
3. `userA` fully withdraws via `MasterMagpie.withdraw` → `withdrawFor`, driving `totalStaked() == 0`.
4. Call `donateRewards(1000e18, rewardToken)` (permissionless) or have the reward manager call `queueNewRewards` — assert `rewards[rewardToken].queuedRewards == 1000e18` and `rewardPerTokenStored` unchanged.
5. `attacker` (never previously staked) calls `MasterMagpie.deposit` → `stakeFor`, becoming sole staker.
6. Trigger a second `_provisionReward` flush (e.g., `donateRewards(0 or small amount, rewardToken)` from any caller, or the next scheduled `queueNewRewards`) causing `rewardPerTokenStored` to be updated over current `totalStaked()` (= attacker's balance only).
7. Assert `earned(attacker, rewardToken) ≈ 1000e18` (full previously-queued amount), despite attacker not being staked when the 1000e18 was donated/queued — confirming capture of yield accrued before attacker's stake existed. [1](#0-0) [2](#0-1)

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```
