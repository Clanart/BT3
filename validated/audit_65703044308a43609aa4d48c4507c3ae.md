The Team Finance incident maps to a missing-validation-of-supplied-parameters bug class: a routine derived the destination of funds from attacker-provided inputs instead of binding them to the expected configuration. The same shape exists in Serai's key deserialization path.

### Title
`ThresholdKeys::read`/`ThresholdKeys::new` derive the group key solely from attacker-controlled verification shares, with no check they correspond to the secret share - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::new` computes `group_key` by interpolating `verification_shares[1..=t]` supplied by the caller, and `ThresholdKeys::read` reconstructs both `verification_shares` and `secret_share` entirely from untrusted bytes. Neither function verifies that `C::generator() * secret_share == verification_shares[params.i()]`, nor that the shares are consistent with any previously agreed-upon key set. Any party who can feed crafted bytes into `ThresholdKeys::read` can make the victim's `group_key()` be a key whose discrete log the attacker knows.

### Finding Description
`ThresholdKeys::new` performs only structural checks: the count of verification shares equals `n`, participant indexes do not exceed `n`, and `Constant` interpolation requires `t == n` [1](#0-0) . It then computes `group_key` as the interpolated sum of the first `t` supplied verification shares [2](#0-1)  and stores everything verbatim [3](#0-2) . `read` parses `t`, `n`, `i`, the interpolation coefficients, the secret share, and `n` verification-share points straight from the byte stream, then calls `new` [4](#0-3) . There is no consistency check anywhere: the deserialized `secret_share` is never required to be the discrete log of `verification_shares[i]`, and for `Interpolation::Constant` the coefficients are never required to evaluate the shares to the group key. This is the same root cause as the Team Finance incident: a routine trusts user-supplied parameters to derive the destination/owner of funds rather than binding them to expected values.

### Impact Explanation
An attacker who can get a victim to load a crafted `ThresholdKeys` blob (key backup, key handoff, deserialized machine state) produces keys whose `group_key()` — the public key used to receive funds — is fully attacker-controlled: the attacker picks verification shares so the interpolated group key has a known discrete log, e.g. `G*x_1` for share 1 and shares `i>1` chosen so the interpolated sum lands on the attacker's key. Funds scanned/reported as received under `group_key()` are spendable by the attacker alone, while the victim's FROST shares either fail to verify or sign for the attacker's key. This is a direct redirect of custody, matching the "funds reported received that are not spendable [by the victim]" acceptance criterion — they are spendable, just by the attacker.

### Likelihood Explanation
`ThresholdKeys::read` is an explicitly in-scope sink for untrusted bytes, and serialized keys are designed to be transported/stored (the format omits the ephemeral scalar/offset but persists everything else) [5](#0-4) . Exploitation requires no threshold collusion, no malicious peer within a live protocol, and no leaked secrets — only delivery of a malicious serialized blob to a participant that subsequently uses `group_key()` as a deposit address or signing identity. Any tampering with keys in transit or at rest suffices, which is precisely the scenario `read`'s existence (with curve-ID checks but no consistency checks) contemplates.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `read`), verify the loaded key material is self-consistent before accepting it:
- Check `C::generator() * secret_share == verification_shares[&params.i()]` — noting the check must account for interpolation when `t != n` (the secret share for Lagrange keys is `f(i)`, and `verification_shares[i]` is `G*f(i)`, so equality still holds).
- For `Interpolation::Constant`, verify the constant coefficients actually reproduce each verification share: `sum_j c_j * verification_shares[j] ==` each expected share relationship the interpolator assumes, or at least that `group_key` derived two ways agrees.
- Prefer binding `group_key` derivation to shares `1..=n` consistency or to a transcript/PoK committed during key generation, rather than trusting `t` arbitrary points.

### Proof of Concept
```rust
// Secp256k1 ciphersuite; assumes Ciphersuite::read_G accepts arbitrary valid points.
use std::io::Write;
use rand_core::OsRng;
use ciphersuite::Ciphersuite;
use frost::curve::Secp256k1 as C;
use dkg::{ThresholdKeys, ThresholdParams, Interpolation, Participant};
use zeroize::Zeroizing;
use group::{ff::Field, Group};

// Attacker builds a blob where group_key interpolates to a key they know.
let attacker_scalar = <C as Ciphersuite>::F::random(&mut OsRng);
let attacker_key = <C as Ciphersuite>::generator() * attacker_scalar;

// t = n = 2, i = 1. With Lagrange, group_key =
//   V[1] * (2/(2-1)) + V[2] * (1/(1-2)) = 2*V[1] - V[2].
// Choose V[1] = G (victim-plausible), V[2] = 2*G - attacker_key
// => group_key = attacker_key.
let v1 = <C as Ciphersuite>::generator();
let v2 = (<C as Ciphersuite>::generator() * <C as Ciphersuite>::F::from(2)) - attacker_key;

// Serialize: curve ID, t, n, i, Lagrange tag, bogus secret_share, V[1], V[2].
let mut buf = vec![];
buf.write_all(&(C::ID.len() as u32).to_le_bytes()).unwrap();
buf.write_all(C::ID).unwrap();
buf.write_all(&2u16.to_le_bytes()).unwrap(); // t
buf.write_all(&2u16.to_le_bytes()).unwrap(); // n
buf.write_all(&1u16.to_le_bytes()).unwrap(); // i
buf.write_all(&[1u8]).unwrap();              // Interpolation::Lagrange
buf.write_all(<C as Ciphersuite>::F::random(&mut OsRng).to_repr().as_ref()).unwrap();
buf.write_all(v1.to_bytes().as_ref()).unwrap();
buf.write_all(v2.to_bytes().as_ref()).unwrap();

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
// group_key() returns the attacker's key; funds sent to it are the attacker's,
// and no consistency check ever compared secret_share to verification_shares[1].
assert_eq!(keys.group_key(), attacker_key);
```
