### Title
SSRF via unvalidated Data Layer mirror URLs used in `http_download` - (File: `chia/data_layer/download_data.py`)

### Summary
Data Layer wallet owners can publish arbitrary, attacker-controlled URL strings on-chain as "mirror" server locations for a store via `create_new_mirror`/`dl_new_mirror`. Any peer that subscribes to that store (a normal Data Layer client action) will later have its local `DataLayer` service fetch delta/full-tree files from that URL with no scheme or destination validation, mirroring the Vvveb `oEmbedProxy` SSRF pattern of piping a user-supplied URL straight into an HTTP client call.

### Finding Description
A wallet can create a mirror coin carrying arbitrary URL bytes with `DataLayerWallet.create_new_mirror`, which puts the caller-supplied `urls` directly into the coin memo with no format/scheme validation. [1](#0-0) 

These URLs are exposed via the `dl_new_mirror` RPC endpoint, again with no validation performed on `request.urls`. [2](#0-1) 

When another node tracks/subscribes to that store, the `DataLayer` service reads these mirror URLs and stores them (only trivially trimming a trailing slash) as candidate download servers. [3](#0-2) 

During `fetch_and_validate`, one of the stored mirror URLs is picked and passed as `server_info` into `insert_from_delta_file`, which ultimately reaches `http_download`. [4](#0-3) 

`http_download` concatenates the attacker-supplied `server_info.url` with a filename and issues an `aiohttp` GET request directly, with no scheme allow-list, no hostname/IP validation, and no protection against internal or loopback destinations: [5](#0-4) 

This is structurally identical to the Vvveb bug class: a URL parameter supplied by a lower-privileged actor (any user able to create a mirror coin / DL wallet operation) is passed unchecked into an HTTP client (`curl`/`aiohttp`) that performs the request and can be used to probe or interact with internal network services.

### Impact Explanation
A malicious Data Layer participant can set a mirror URL pointing at internal-only services (e.g. `http://127.0.0.1:<port>/...`, cloud metadata endpoints, other services on the operator's LAN) or unexpected ports. Whenever another node subscribes to that store and its `DataLayer.fetch_and_validate` loop selects that server, the victim's Data Layer service will issue outbound requests to the attacker-chosen destination. Response bytes are then treated as delta/full-tree file bytes and parsed by the data store, so, at minimum, this is SSRF (network reconnaissance/exfiltration against internal endpoints reachable from the DataLayer host); if the fetched content can be coerced into passing file validation, it could also cause resource abuse or unexpected data-store I/O. This is scoped to "Data Layer roots and proofs" reachable by a Data Layer client, matching the allowed analog categories.

### Likelihood Explanation
Any wallet able to create a mirror coin (`create_new_mirror`/`dl_new_mirror`) can set the URL to any string; there is no format or scheme check anywhere in the chain (`create_new_mirror` → `dl_new_mirror` RPC → `update_subscriptions_from_wallet` → `fetch_and_validate` → `http_download`). Reaching another node only requires that node to track/subscribe to the same store id, which is a normal, low-privilege Data Layer operation.

### Recommendation
Validate mirror URLs at creation time (`create_new_mirror`/`dl_new_mirror`) and again before use in `http_download`/`get_downloader`: enforce an `http://`/`https://` scheme allow-list, resolve and reject loopback/link-local/private-range/metadata-service destinations (unless explicitly opted into for local testing), and reject malformed or non-HTTP URLs before they are persisted as `ServerInfo` or dialed by `aiohttp`.

### Proof of Concept
1. Node A owns a Data Layer store `store_id` and calls `dl_new_mirror` (or `chia data add_mirror`) with `urls=["http://169.254.169.254"]` (or an internal service URL), which is accepted with no validation, per `chia/data_layer/data_layer_wallet.py` `create_new_mirror` and `chia/wallet/wallet_rpc_api.py` `dl_new_mirror`.
2. Node B tracks/subscribes to `store_id` (normal Data Layer client behavior) and calls `update_subscriptions_from_wallet`, storing the attacker URL as a `ServerInfo`.
3. When Node B's `DataLayer.fetch_and_validate` next runs, it selects that server and calls `insert_from_delta_file` → `download_file` → `http_download`, which issues `session.get("http://169.254.169.254" + "/" + filename, ...)` directly from Node B's host, demonstrating outbound SSRF to an attacker-chosen destination with no validation.

        request: DLNewMirror,

        """Add a new on chain message for a specific singleton"""
        if self.service.wallet_state_manager is None:

        dl_wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:

                request.launcher_id,
                request.amount,
                Mirror.encode_urls(request.urls),
                action_scope,
                fee=request.fee,
                extra_conditions=extra_conditions,
            )

        # tx_endpoint will take care of default values here
        return DLNewMirrorResponse(unsigned_transactions=[], transactions=[])

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
