### Title
`removePool` fails to deactivate the pool, permanently corrupting global vote-sum accounting (`totalVlMgpInVote`) - (File: wombat/WombatBribeManager.sol)

### Summary
`removePool` only removes a pool address from the `pools` array iterated by `castVotes`, but never sets `poolInfos[lp].isActive = false`. Because `vote()` only checks `poolInfos[_lp].isActive` (not membership in `pools`), ordinary users can keep voting for a "removed" pool, incrementing `pool.totalVoteInVlmgp` and the global `totalVlMgpInVote`, while `castVotes` will never again process that pool to reconcile its on-chain Wombat vote. This is the same class of bug as the `VoteWeighting.pointsSum.slope` issue: an aggregate sum (`totalVlMgpInVote`) is not kept in sync with the removal of an entity from the iterated set (`pools`), permanently corrupting the denominator used to compute every other pool's vote share.

### Finding Description
`removePool` swaps the target index with the last array element and pops it, shrinking `pools`: [1](#0-0) 

It does not touch `poolInfos[_lp].isActive`, which remains `true` forever since `addPool` set it and nothing else clears it: [2](#0-1) 

`vote()` only gates on `pool.isActive`, not on presence in the `pools` array, so any unprivileged user can still vote for the removed pool, increasing `pool.totalVoteInVlmgp` and the global `totalVlMgpInVote`: [3](#0-2) 

`castVotes`, however, only iterates the `pools` array to compute `targetVote = targetVoteInLMGP * totalVotes() / totalVlMgpInVote` for each remaining active pool and to send updated votes to `wombatStaking.vote(...)`: [4](#0-3) 

Since the removed pool is excluded from this loop, its `totalVoteInVlmgp` contribution to `totalVlMgpInVote` is never reconciled against an actual on-chain vote — exactly analogous to `pointsSum.slope` retaining a removed nominee's contribution forever in `VoteWeighting.sol`. `unvote()` also still succeeds for this "removed" pool because it only checks `isActive`, so users can still add/pull votes indefinitely, keeping the corruption ongoing.

### Impact Explanation
`totalVlMgpInVote` is the shared denominator for every active pool's `targetVote` calculation in `castVotes`. Once it is inflated by votes locked into an orphaned (removed-but-still-active) pool that is permanently excluded from `castVotes`, the computed `targetVote` for every legitimate remaining pool is permanently understated relative to `totalVotes()` (the real veWOM balance). This misallocates the protocol's actual Wombat governance votes across the remaining pools indefinitely — a governance voting-result manipulation that persists until manual owner intervention (there is no function to re-sync `totalVlMgpInVote` or force-clear the orphaned pool's contribution), satisfying the "governance voting result manipulation" / 24h+ freeze criteria.

### Likelihood Explanation
This requires only routine, non-malicious admin maintenance (calling `removePool` to retire an old LP/pool, which is an expected, ordinary operational action) followed by any unprivileged user voting (`vote()`) for the now-orphaned pool — a fully reachable path with no special privileges needed to trigger the corruption from the user side.

### Recommendation
In `removePool`, also set `poolInfos[pools[_index]].isActive = false` before removing it from the `pools` array (or alternatively, subtract `poolInfos[lp].totalVoteInVlmgp` from `totalVlMgpInVote` at removal time and zero it out), so that `vote()` immediately rejects new votes for removed pools and the aggregate `totalVlMgpInVote` is kept consistent with the active pool set used in `castVotes`.

### Proof of Concept
1. Owner calls `addPool(lpA, rewarderA, "A")`; users vote for `lpA`, incrementing `totalVlMgpInVote` and `poolInfos[lpA].totalVoteInVlmgp`.
2. Owner calls `removePool(indexOfA)`; `lpA` is removed from `pools`, but `poolInfos[lpA].isActive` stays `true`.
3. A user calls `vote([lpA], [positiveDelta])` — succeeds because `vote()` only checks `poolInfos[lpA].isActive`, incrementing `totalVlMgpInVote` and `poolInfos[lpA].totalVoteInVlmgp` further.
4. Owner calls `castVotes(...)`: the loop only iterates over the (now shorter) `pools` array, so `lpA`'s vote is never zeroed against actual Wombat votes, yet its contribution remains baked into `totalVlMgpInVote`, permanently skewing `targetVote` for every other active pool computed as `targetVoteInLMGP * totalVotes() / totalVlMgpInVote`.
