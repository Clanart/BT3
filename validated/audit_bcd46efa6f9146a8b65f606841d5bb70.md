### Title
Attacker-controlled participant count in `ThresholdKeys::read` forces large speculative allocation (memory amplification DoS) - (File: crypto/dkg/src/lib.rs)

### Summary
The GnuTLS advisory describes a DoS where a malicious input causes CPU/memory consumption disproportionate to its size. The same shape exists in `ThresholdKeys::read` in `crypto/dkg`: a 2-byte attacker-controlled `n` is used directly in `Vec::with_capacity(usize::from(n))` before any of the `n` scalars are actually read, letting a handful of input bytes force a ~2 MB allocation. The read then fails on the first missing scalar, but the allocation (and zeroing cost) has already been paid, once per malicious blob.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` as raw `u16`s, then reads the interpolation tag. For tag `0` (`Interpolation::Constant`) it executes:

```rust
// crypto/dkg/src/lib.rs
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n {
  res.push(C::read_F(reader)?);
}
``` [1](#0-0) 

`n` is fully attacker-controlled (max `0xFFFF` = 65535) and is only validated later inside `ThresholdParams::new(t, n, i)` / `ThresholdKeys::new`, i.e. *after* the allocation and read loop. `Vec::with_capacity` commits `65535 * size_of::<C::F>()` bytes (≈2 MB for 32-byte scalars) immediately, from a message that can be as short as the 7-byte header (`id_len`+`ID` prefix aside). The subsequent `read_F` fails on the first element because the input is truncated, returning an error — but the allocation cost is already incurred. Repeating the blob N times costs the attacker ~7–9 bytes each while the victim repeatedly allocates and frees ~2 MB.

The codebase itself recognizes this bug class: `networks/ethereum/src/machine.rs` comments "A valid DoS would be to claim a 4 GB data is present for only 4 bytes" and reads in 1 KB chunks to bound speculative allocation [2](#0-1) . The same consideration was not applied in `ThresholdKeys::read`. (Sister code `Payment::read` in `processor/src/plan.rs` has the same `vec![0; u32_len]` pattern — up to 4 GB claimed — but that crate is outside the in-scope list.) [3](#0-2) 

`ThresholdKeys::read` is an explicitly in-scope entry point for untrusted bytes, so an unprivileged party that can feed a serialized `ThresholdKeys` blob (e.g., key-material messages, backups, or protocol bytes routed to this deserializer) reaches the vulnerable path.

### Impact Explanation
Denial of service via memory amplification: each ~9-byte malicious input forces an immediate ~2 MB heap allocation plus allocation/zeroing work. A stream of such messages amplifies attacker bandwidth into victim memory pressure and allocator churn, potentially exhausting memory or degrading the signing/DKG service — the same "excessive consumption via crafted input" impact as ALPINE-CVE-2025-14831 (CVSS 5.3, availability-only).

### Likelihood Explanation
Reachability depends on untrusted bytes reaching `ThresholdKeys::read`; the function trusts `n` unconditionally with no bound check against `t`, protocol participant limits, or remaining input length. No cryptographic validity, authentication, or valid signature is required — the allocation happens before any check that could reject the input. Any deployment exposing this deserializer to peer-supplied data is triggerable with trivial cost.

### Recommendation
- Validate `n` before allocating: enforce `n >= t`, `i <= n`, and a sane protocol bound (e.g., the documented max participant count) immediately after reading the `u16`s, before the interpolation branch.
- Replace `Vec::with_capacity(n)` with incremental `Vec::push` (or `with_capacity` capped to a small constant), so allocation grows only with data actually present in the reader — mirroring the chunked-read approach already used in `ethereum/src/machine.rs`.
- Optionally bound the whole deserialization by first checking remaining input length (`n * F::repr_len()` bytes must exist before the loop).

### Proof of Concept
```rust
// Conceptual: feed a truncated blob with a huge participant count.
// Layout expected by ThresholdKeys::read (crypto/dkg/src/lib.rs:574-616):
//   [4B id_len][C::ID bytes][u16 t][u16 n][u16 i][u8 interpolation]
let mut blob = vec![];
blob.extend((C::ID.len() as u32).to_le_bytes());
blob.extend(C::ID);
blob.extend(1u16.to_le_bytes());      // t = 1
blob.extend(0xFFFFu16.to_le_bytes()); // n = 65535
blob.extend(1u16.to_le_bytes());      // i = 1
blob.push(0u8);                       // Interpolation::Constant -> Vec::with_capacity(65535)
// No scalar bytes follow.
// Each call allocates ~65535 * size_of::<C::F>() (~2 MB) then errors on the
// first read_F. Looping this in a stream amplifies ~13 bytes into ~2 MB
// allocation each iteration.
let _ = ThresholdKeys::<C>::read(&mut blob.as_slice()); // Err(..), but allocation already made
```

I was not able to fully inspect `crypto/dkg/pedpop/src/encryption.rs` (`EncryptedMessage::read`) within available iterations; if it applies the same `vec![0; claimed_len]` pattern it may constitute a second, possibly stronger instance of this class.
