### Title
Wildcard-allowance collision with real asset name `*` lets `restrict-assets?`/`as-contract?` allowances silently authorize other assets in the same contract - (File: clarity/src/vm/functions/post_conditions.rs)

### Summary
`check_allowances` implements per-contract wildcard allowances (`with-ft`/`with-nft` "all assets in contract X") by internally synthesizing a sentinel `AssetIdentifier` whose `asset_name` is `ClarityName::from_literal("*")`, then looking that sentinel up in the `ft_allowances`/`nft_allowances` maps alongside the exact-match asset. Because `"*"` is accepted by the `ClarityName` grammar as a genuine identifier, a contract can define a real fungible or non-fungible token literally named `*`. Any post-condition allowance written by the user for that specific asset (`with-ft '<contract>.* amount`) is keyed in the map under the exact same `AssetIdentifier` the wildcard-lookup code searches for, so it is indistinguishable from — and gets merged into — the wildcard bucket.

### Finding Description
`check_allowances` builds `ft_allowances`/`nft_allowances` keyed by `AssetIdentifier` from the allowances the user actually declared. Then, for each asset actually moved, it does an exact-match lookup plus a wildcard lookup using a synthetic key `AssetIdentifier { contract_identifier: asset.contract_identifier.clone(), asset_name: ClarityName::from_literal("*") }`, merging both into one list of `(index, amount)` pairs it checks against. [5](#0-4) 

The wildcard mechanism assumes no real asset can ever be named `*`, so the merged bucket is "the wildcard allowance, plus any allowance that happens to match this exact asset." But `*` is a syntactically legal Clarity identifier (confirmed by the `CLARITY_NAME_REGEX_STRING` and its accompanying test), so `define-fungible-token *` and `define-non-fungible-token *` are legal contract-asset names. When such a contract exists, an allowance the caller wrote specifically for `<contract>.*` (intending to cover only the literal `*`-named asset) is stored in the map under the identical key the wildcard code searches for, and is therefore also matched — and merged additively — for any other asset moved from the same contract, since the wildcard-search key and the real per-asset key collide.

This breaks the equality the allowance system is meant to enforce: "the sum of amounts sent for asset X must be ≤ the amounts explicitly allowed for X (or an explicit wildcard-all allowance for the contract)." With the collision, an allowance nominally scoped to the specific `*` asset is treated as if it were a genuine "allow all assets in contract" wildcard, inflating the allowed amount for a *different* asset (or vice versa: a real wildcard entry can be shadowed/merged incorrectly with a specific `*` asset entry), letting movement of one asset be authorized by an allowance amount the caller believed was scoped to a distinct asset.

### Impact Explanation
This is a post-condition/allowance escape: within a `restrict-assets?`/`as-contract?` block, the caller's declared allowances no longer bound asset movement the way the caller intended, because the allowance-merging logic conflates a real asset literally named `*` with the "allow-all" wildcard sentinel. An asset can move past what the specific post-condition line was meant to authorize, which matches the "asset moving past its post-conditions" high/critical impact category in this bug class.

### Likelihood Explanation
Requires a contract deployed with a fungible or non-fungible token explicitly named `*` (a legal but unusual name) and a caller writing an allowance for that specific asset inside a `restrict-assets?`/`as-contract?` clause alongside other assets from the same contract. This is a narrower trigger than a generic path-traversal analog, but it is fully reachable through ordinary Clarity contract deployment and post-condition allowance syntax — no privileged role or miner assumption is needed. The main mitigating factor is that a token author must intentionally (or accidentally) choose the name `*`.

### Recommendation
Do not overload a value in the legal `ClarityName` space as the wildcard sentinel. Represent "all assets in a contract" allowances with a separate, unambiguous enum variant/flag on the allowance record (e.g., `Allowance::FtAll(contract_id)`), rather than a magic `AssetIdentifier` whose `asset_name` is the string `"*"`, so lookups for wildcard allowances can never collide with a legitimately-named on-chain asset.

### Proof of Concept
1. Deploy a contract `token` that calls `(define-fungible-token * )` (legal per `ClarityName` grammar) and also mints/holds a second token `(define-fungible-token good-token)`.
2. Inside `restrict-assets?`, declare two allowances: `(with-ft 'SP...token.* u10)` (intended to cover only the `*`-named asset) and no allowance for `good-token`.
3. Have the protected code transfer `good-token` in an amount ≤ 10.
4. `check_allowances` computes the wildcard-lookup key for `good-token` as `AssetIdentifier{contract_identifier: token, asset_name: "*"}`, which is exactly the key under which the `with-ft '...token.*` allowance was stored, so the `good-token` transfer is merged into that allowance's bucket and passes the check — even though the caller never wrote an allowance for `good-token`.
