### Title
Unchecked u64 value arithmetic on a deserialized `ReceivedOutput` overflows and produces a signable transaction with forged economics — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`ReceivedOutput::read` accepts a `TxOut` via `consensus_decode`, which permits an output `value` anywhere in `0..=u64::MAX` — no `MAX_MONEY`/sanity bound is applied. When such an output reaches `SignableTransaction::new`, all of the economic checks are performed with plain u64 arithmetic (`sum::<u64>()`, `payment_sat + needed_fee`, `fee_per_vbyte * vbytes`, `input_sat - ...`). A value near `u64::MAX` wraps or underflows these computations, turning the "is this transaction funded / sane" question into the same class of bug as the TensorFlow advisory: an extreme numeric input silently converts into a meaningless value that downstream code treats as authoritative, here culminating in a threshold-signed transaction whose declared inputs do not fund its outputs.

### Finding Description
In `ReceivedOutput::read`, the output's satoshi value is decoded with no upper bound:

```rust
output = TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
``` [1](#0-0) 

`SignableTransaction::new` then sums input values and compares against `payment_sat + needed_fee` using unchecked `+`:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
...
if input_sat < (payment_sat + needed_fee) { Err(NotEnoughFunds ...) }
``` [2](#0-1) 

and computes change with `input_sat.checked_sub(payment_sat + fee_with_change)` — where the *inner* `payment_sat + fee_with_change` itself can overflow before `checked_sub` ever runs. With a crafted `ReceivedOutput` carrying `value = u64::MAX`, `input_sat` (or the addition) wraps, the `NotEnoughFunds` guard passes, and the change branch pushes a `TxOut` of ~`u64::MAX` sats to the change script:

```rust
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
  if value >= DUST {
    tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
``` [3](#0-2) 

The resulting `SignableTransaction` is then fed to `TransactionSignMachine::sign`, which computes the Taproot sighash over `Prevouts::All` and has every signer produce a signature share for it — i.e., the threshold group signs a transaction whose claimed input value is fabricated and whose outputs exceed any real input. Additionally, `fee()` subtracts `sum(outputs)` from `sum(prevouts)` with a plain `-`, so once `prevouts` holds the real (small) prevouts and `tx.output` holds the inflated outputs, it underflows and panics. [4](#0-3) [5](#0-4) 

### Impact Explanation
An unprivileged party who can get attacker-controlled bytes into `ReceivedOutput::read` (which the in-scope rules classify as an untrusted-bytes sink; `processor/src/networks/bitcoin.rs` `Output::read` deserializes a `ReceivedOutput` via that path at line 156) can cause the signing pipeline to:

1. Produce a threshold-signed transaction committing to inputs/outputs that do not correspond to real UTXO values — i.e., the multisig signs a message whose semantics (claimed funding) were never validated. In release builds the wraps are silent; in debug builds they panic, aborting the signing session (DoS).
2. Create a change output near `u64::MAX` sats. If the wrapped arithmetic makes the tx appear funded, signers sign it; the tx is consensus-invalid, so any plan built on it (e.g., a BTC payout for an already-burned SRI withdrawal) can never settle — the associated funds are stranded mid-protocol.

The panic in `fee()` (`prevouts_sum - outputs_sum` underflow) is a guaranteed crash whenever outputs exceed prevouts, reachable purely through crafted input values.

### Likelihood Explanation
Reachability requires attacker-influenced bytes flowing through `ReceivedOutput::read`/`Output::read` into `SignableTransaction::new`. Whether a production path feeds unauthenticated bytes to that deserializer is unverified from the indexed code — `processor/src/networks/bitcoin.rs:156` shows `ReceivedOutput::read` is used inside `Output::read`, but the index does not make clear whether that reader ever sees peer-supplied data versus only local DB state. If it is only local/DB data, likelihood drops substantially and the bug is a robustness gap rather than a remotely triggerable one. Medium confidence in the finding; severity aligned with the Medium source advisory.

### Recommendation
- In `ReceivedOutput::read` (or at `SignableTransaction::new` entry), reject `output.value > Amount::MAX_MONEY` — i.e., enforce consensus-valid value bounds on deserialization.
- Replace all `sum::<u64>()` and `+` arithmetic in `SignableTransaction::new` and `fee()` with `checked_add`/`checked_sub`/`checked_mul`, returning `TransactionError` on overflow instead of wrapping/panicking.
- Bound `fee_per_vbyte` and verify `sum(inputs) <= MAX_MONEY` before constructing the transaction.
