## Title
Live re-fetched local asset decimals let a self-created asset's owner inflate refunds/mints in `pallet-hyper-fungible-token` — (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The Solana report's core broken invariant is: a decimal-derived scaling rate is computed once from a mutable, externally-controlled decimals value, and nothing re-validates that the value hasn't changed by the time the rate is used to move funds. `pallet-hyper-fungible-token` reproduces the same broken invariant on Substrate: it never caches the local asset's decimals at `send()` time. Instead, `on_timeout`/`on_accept` re-read `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(local_asset_id)` live, while the ERC-side decimals (`Precisions`) stay fixed from registration. Because `pallet-assets` metadata (including `decimals`) is mutable at any time by the asset's owner and does not affect the asset's actual raw balance units, an attacker who owns the local asset can shift the decimals value between `send()` and the processing of the resulting timeout, corrupting the conversion math used to compute the refunded amount.

### Finding Description
`send()` locks/burns `params.amount` (raw local balance units) and encodes the outbound ERC20 amount using the local asset's decimals **at that instant**: [1](#0-0) 

That embedded `erc20_amount` becomes part of the dispatched `PostRequest` body and is immutable once dispatched. If the request later times out (a normal, publicly-triggerable ISMP outcome — anyone can submit a valid timeout proof), `on_timeout` decodes that same embedded amount and converts it back to a local balance using `Precisions` (fixed, from registration) together with the local asset's decimals **read live at refund time**: [2](#0-1) 

The conversion itself: [3](#0-2) 

`erc_decimals.saturating_sub(local_decimals)` — because it uses `saturating_sub` instead of a signed difference, once `local_decimals` exceeds `erc_decimals` the exponent floors at `0`, and the "scale down" step silently stops scaling. Conversely, if `local_decimals` is *raised* between `send()` and `on_timeout` while still `<= erc_decimals`, the divisor shrinks and the refunded amount becomes proportionally larger than what was actually escrowed/burned.

The only place `local_decimals` is validated against `erc_decimals` is at registration/update time: [4](#0-3) 

This check is a one-time gate; it is never re-enforced when `on_accept`/`on_timeout` later re-read decimals. Since asset metadata (`decimals`) in `pallet-assets` is a display-only field controlled by the asset's Owner (independent of `CreateOrigin`, the privileged origin that calls `register_token`), any account that owns the registered local asset can change its `decimals` at will with an ordinary `pallet-assets::set_metadata` call — and doing so does not touch the actual raw balance held by any account, only how this pallet's conversion functions interpret it.

### Impact Explanation
This breaks Hyperbridge's fund-custody invariant that bridged assets must move exactly once and only for the amount that was actually escrowed. By manipulating the local asset's `decimals` metadata between `send()` (escrow/burn) and the timeout refund, the asset owner can cause `on_timeout` to credit far more than was actually locked/burned, draining the pallet's escrow account (`pallet_account()`) or minting unbacked non-native asset supply. This is a direct "stealing/loss of funds" and "transaction manipulation" outcome reachable from an unprivileged, self-controlled asset — no relayer, prover, or governance compromise is required.

### Likelihood Explanation
Likelihood is **Low-to-Medium**: it requires the attacker to be the owner of the registered local asset (achievable for any non-native/self-issued asset a team registers on this pallet) and to force/wait for a timeout on their own outbound transfer (which is fully attacker-controllable — they can target an unconfigured or unresponsive destination contract, or simply let the configured timeout elapse). Both preconditions are within reach of an ordinary asset issuer without any privileged role, matching the bounty's requirement for a reachable, unprivileged, non-peer/non-relayer path.

### Recommendation
- Snapshot and store the local asset's `decimals` inside the dispatched message/commitment metadata at `send()` time (or otherwise persist the resolved exponent used for that specific transfer), and use that stored value — not a live re-read — in both `on_accept`/`on_timeout` for messages tied to that transfer.
- Replace `saturating_sub` with a checked/signed computation that fails closed (returns an error) rather than silently clamping to zero when `local_decimals > erc_decimals`.
- Alternatively, disallow post-registration mutation of decimals for any asset used by this pallet (e.g., require `pallet-assets::freeze_metadata` before/at `register_token`, and re-verify it remains frozen on every use), analogous to disabling `MintCloseAuthority` in the original report.

### Proof of Concept
1. Attacker creates asset `X` via `pallet-assets::create` (permissionless), decimals = 6, and becomes the asset's Owner.
2. Governance/`CreateOrigin` registers `X` with `register_token`, `chains = { EVM(1): { decimals: 18, contract } }` — passes the `config.decimals(18) >= local_decimals(6)` check: [5](#0-4) .
3. Attacker acquires real balance of `X` (1000 tokens = `1e9` raw units at 6 decimals) and calls `send()` to a destination that is guaranteed to time out (e.g., an EVM chain with no listening `token_contract`, or by exceeding the configured `timeout`). The asset is burned/escrowed for real: [6](#0-5) . The embedded ERC amount is computed at decimals=6: `erc20_amount = 1e9 * 10^(18-6) = 1e21`.
4. Before the timeout proof is submitted, attacker (as asset Owner) calls `pallet_assets::set_metadata(X, ..., decimals=12)`. This changes only the metadata field, not any account balances.
5. Attacker (or anyone) submits the ISMP timeout for the original request. `on_timeout` re-reads decimals live (now 12) and computes: `refund = convert_to_balance(1e21, erc_decimals=18, local_decimals=12) = 1e21 / 10^6 = 1e15` raw units — a refund 10^6× larger than the `1e9` units actually escrowed/burned in step 3: [7](#0-6) .
6. The pallet mints/transfers the inflated `1e15` to the attacker, draining escrow or minting unbacked supply — a concrete fund-theft/loss outcome from a fully unprivileged actor.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
