### Title
Path-containment check in `resolveWithin` uses unanchored `startsWith`, allowing deep-link `filepath` to escape the repository root - (File: `app/src/lib/path.ts`)

### Summary
The bug class in the ERC-712 report is a broken invariant caused by an encoding/string comparison that silently deviates from its intended semantics (an extra space breaks the exact-match hash comparison). The analogous invariant in GitHub Desktop is the "resolved path must be inside `rootPath`" check performed by `resolveWithin`, which is relied upon by the `x-github-client://openRepo/...?filepath=...` deep-link handler to decide whether it is safe to reveal a file to the user. That check uses a plain string `startsWith` comparison instead of a path-boundary-aware comparison, so it can be satisfied by a directory that merely shares a name prefix with the repository root, not one that is actually nested inside it.

### Finding Description
`_resolveWithin` computes the real, symlink-resolved paths of both the root and the candidate target and then does: [1](#0-0) 

`realResolved.startsWith(realRoot)` is a naive string-prefix test. It does not verify that `realRoot` is followed by a path separator (or that `realResolved === realRoot`), so any sibling path whose name has `realRoot` as a literal string prefix (e.g. root `/Users/x/Repos/project` vs. sibling `/Users/x/Repos/project-secrets`) satisfies the check even though the sibling is not "underneath" the root directory at all.

This function backs the only containment check used before revealing a file requested via the `filepath` query parameter of the `open-repository-from-url` deep-link action: [2](#0-1) 

The `filepath` value itself comes directly from an attacker-controlled URL that the app registers as a protocol handler (`x-github-client://`, `github-mac://`, etc.) and is parsed with only minimal validation (`isAbsolute` rejection) in `parseAppURL`: [3](#0-2) 

Because the containment guard is the only thing standing between an attacker-supplied `filepath` and `shell.showItemInFolder`, and that guard's string comparison is not anchored to a path boundary, a directory-naming coincidence between the cloned repository path and an adjacent directory on disk can defeat the guard.

### Impact Explanation
If exploitable, the practical outcome is that a maliciously crafted deep link (something a user could be induced to click from a webpage, chat message, or a GitHub "Open in Desktop" flow) could cause Desktop to reveal/open a file located outside of the intended repository directory via `shell.showItemInFolder`, even though the code explicitly attempts to "prevent attempt to open path outside of the repository root." This is a containment-check bypass — the exact bug class the external report calls out (a security-relevant string comparison that silently fails to enforce its stated invariant).

### Likelihood Explanation
Exploitability is directly conditioned on file-system layout: it requires a sibling path on the victim's disk whose name has the repository's absolute path as a literal prefix (no separator in between), which is not something the attacker fully controls remotely — this substantially limits real-world reach and is why the analogous ERC-712 finding is also rated Low impact/High likelihood-of-triggering-but-limited-severity. Within Desktop's own threat model (attacker controls a deep link, not the victim's filesystem layout), the likelihood of a specific victim having such a naming collision is comparatively low, but the check is unconditionally wrong regardless of layout, so any matching layout is exploitable with a single click.

### Recommendation
Anchor the prefix comparison to a path boundary instead of using a raw string `startsWith`, e.g.:
```diff
- return realResolved.startsWith(realRoot) ? resolved : null
+ const rootWithSep = realRoot.endsWith(Path.sep) ? realRoot : realRoot + Path.sep
+ return realResolved === realRoot || realResolved.startsWith(rootWithSep)
+   ? resolved
+   : null
```
This mirrors the fix pattern in the original report (correcting a string that almost—but not exactly—matches the intended, unambiguous format).

### Proof of Concept
1. Attacker sets up (or the user already has) two sibling directories under the same parent, e.g. `/Users/victim/Code/app` (the Desktop-cloned repo) and `/Users/victim/Code/app-secrets/creds.txt` (unrelated, sensitive).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/org/app?filepath=../app-secrets/creds.txt`.
3. `parseAppURL` accepts the URL and produces `{ name: 'open-repository-from-url', url, filepath: '../app-secrets/creds.txt' }` since `isAbsolute` is false for this relative traversal string (`app/src/lib/parse-app-url.ts:98-124`).
4. `openRepositoryFromUrl` calls `resolveWithin(repository.path, filepath)`; `resolve()` joins `app-secrets/creds.txt` under a normalized path, and because `/Users/victim/Code/app-secrets` starts with the string `/Users/victim/Code/app`, `realResolved.startsWith(realRoot)` returns `true`, defeating the intended containment check (`app/src/lib/path.ts:64-71`).
5. `shell.showItemInFolder(resolved)` reveals `creds.txt`, a file outside the cloned repository, in the OS file explorer (`app/src/ui/dispatcher/dispatcher.ts:1963-1966`).

Note: I was not able to execute this PoC in a live environment from the indexed code alone; the analysis is based on static reading of `path.ts`, `parse-app-url.ts`, and `dispatcher.ts`. A background Devin session with filesystem/terminal access would be needed to empirically confirm the exact directory-naming conditions required to trigger the bypass on macOS/Windows.
