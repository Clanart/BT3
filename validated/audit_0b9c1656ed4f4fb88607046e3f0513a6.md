### Title
State transition uses genesis-frozen `DeferredTxFee` instead of the live governance value, causing fee-recipient/burn divergence from `RewardModule` - (File: blockchain/state_transition.go)

### Summary
`StateTransition.TransitionDb()` decides whether to pay out (non-deferred) or defer transaction fees by reading `st.evm.ChainConfig().Governance.DeferredTxFee()`, which resolves the **genesis-time, hardcoded** chain config value, not the value produced by the live governance parameter store (`kaiax/gov`). The `reward.deferredtxfee` parameter is explicitly modeled as a votable governance parameter elsewhere in the codebase (`kaiax/gov/param.go`, `kaiax/reward/config.go`), so if governance ever votes to change `DeferredTxFee` mid-chain, the immediate per-transaction fee accounting in `state_transition.go` will diverge from the per-block reward accounting in `kaiax/reward/impl/getter.go`, which correctly reads the parameter from the current `ParamSet`.

### Finding Description
In `TransitionDb()`, the code comments and reads: [1](#0-0) 
which explicitly states: "DeferredTxFee has never been voted, so it's ok to use the genesis value instead of the latest value from governance," and branches solely on `st.evm.ChainConfig().Governance.DeferredTxFee()` — a static, genesis `ChainConfig` field, not the dynamic `ParamSet` value.

By contrast, the reward module treats `DeferredTxFee` as a normal, votable parameter: it is defined with a `Canonicalizer`/`FormatChecker`/`DefaultValue` in the parameter registry [2](#0-1) , is exposed through `ParamSet` [3](#0-2) , and is read fresh per-block via `GetParamSet(header.Number)` when building `RewardConfig` in `NewRewardConfig`: [4](#0-3) . `getExecFee`/`specWithNonDeferredFee`/`getDeferredRewardSimple` in `kaiax/reward/impl/getter.go` then branch on this live `config.DeferredTxFee` [5](#0-4) [6](#0-5) .

This is analogous to the reported Arrakis/Uniswap-V3 bug class: the vault math hardcodes an assumption ("protocol fee will always be zero") instead of reading the live, governance-controlled parameter, so if governance changes that parameter the two code paths (vault math vs. actual pool state) diverge and produce incorrect value transfers. Here, `state_transition.go`'s per-tx fee payout hardcodes the assumption "DeferredTxFee will never be voted" via a genesis-config read, while `kaiax/reward`'s per-block accounting correctly tracks governance votes on the same parameter through `ParamSet`.

If a governance vote changes `reward.deferredtxfee` after genesis:
- `TransitionDb()` will keep crediting `Coinbase`/`Rewardbase` immediately per-transaction (or not) based on the stale genesis flag, while `getDeferredRewardSimple`/`getDeferredRewardFull` in the reward module will compute end-of-block distribution based on the new voted flag.
- This produces double-crediting or missing-crediting of transaction fees (immediate payment plus deferred distribution, or vice versa), directly affecting account balances — a concrete "unauthorized value movement" / state divergence from the intended, single-source-of-truth governance parameter.

### Impact Explanation
If exploited (i.e., if the flag is ever actually voted, or if a chain configuration inconsistency between genesis-declared `Governance.DeferredTxFee` and the live governance value being enforced by the reward module occurs), transaction fees could be paid out twice (once non-deferred in `TransitionDb`, once again deferred in `FinalizeState`/reward getter) or fees could be silently lost/misburned relative to the officially voted policy, causing balance/supply divergence between what governance intended and what state actually holds. This is a Medium-severity fee-accounting/state-divergence class issue, matching the accepted "state divergence" / "fee abuse" impact categories.

### Likelihood Explanation
Likelihood depends entirely on whether `reward.deferredtxfee` is actually voted post-genesis. The code explicitly documents the assumption that it "has never been voted" and treats this as acceptable technical debt, but the parameter is fully wired into the general governance-voting machinery (`kaiax/gov/param.go`, `ParamSet`, `PartialParamSet.Add`) with no code-level guard preventing such a vote from being cast and accepted by `kaiax/gov`. Any governing node/council member using the standard governance/voting transaction flow could cast such a vote; no privileged off-chain access is needed beyond normal governance transaction submission.

### Recommendation
Read `DeferredTxFee` from the live `ParamSet`/`GovModule.GetParamSet(header.Number)` in `TransitionDb()` (matching how `NewRewardConfig` reads it), rather than from `st.evm.ChainConfig().Governance.DeferredTxFee()`, or, alternatively, explicitly disallow votes on `reward.deferredtxfee` in the parameter registry (e.g., mark it immutable/rejected in `kaiax/gov/param.go`) so the genesis-value assumption in `state_transition.go` is actually enforced at the governance layer instead of only documented in a comment.

### Proof of Concept
1. Deploy/operate a Kaia network where governance mode allows parameter voting (`GovernanceMode` = single/ballot as wired through `kaiax/gov`).
2. Submit a governance vote transaction proposing `reward.deferredtxfee` = the opposite of the genesis value (this is accepted since it is a registered, canonicalized/format-checked parameter per `kaiax/gov/param.go` lines 323-357, with no special-case rejection).
3. Once the vote is finalized and reflected in `ParamSet` at a future block height, `kaiax/reward/impl/getter.go`'s `NewRewardConfig` will pick up the new value for that block's end-of-block reward computation.
4. However, `blockchain/state_transition.go`'s `TransitionDb()` still branches on the frozen genesis `ChainConfig().Governance.DeferredTxFee()` for every transaction processed in that same block, causing the per-tx immediate payout logic and per-block deferred reward logic to use inconsistent flags for the same block, resulting in a fee-accounting mismatch (double payment or fee loss) versus the officially governed policy.

// specWithNonDeferredFee adds non-deferred fees to the reward spec.
func (r *RewardModule) specWithNonDeferredFee(spec *reward.RewardSpec, config *reward.RewardConfig, header *types.Header, execFee *big.Int) (*reward.RewardSpec, error) {
	if config.DeferredTxFee {
		return spec, nil // nothing to do under deferred mode
	}

	newSpec := spec.Copy()

	blobFee := getBlobFee(header)
	if config.Rules.IsMagma {
		burntFee := getBurnAmountMagma(execFee)
		distributedFee := new(big.Int).Sub(execFee, burntFee)
		newSpec.TotalFee.Add(newSpec.TotalFee, new(big.Int).Add(execFee, blobFee))
		newSpec.BurntFee.Add(newSpec.BurntFee, new(big.Int).Add(burntFee, blobFee))
		newSpec.Proposer.Add(newSpec.Proposer, distributedFee)

		// Since Magma, non-deferred fees are assigned to header.Rewardbase.
		newSpec.IncRecipient(config.Rewardbase, distributedFee)
	} else {
		distributedFee := new(big.Int).Set(execFee)

		newSpec.TotalFee.Add(newSpec.TotalFee, new(big.Int).Add(execFee, blobFee))
		newSpec.Proposer.Add(newSpec.Proposer, distributedFee)

		// Before Magma, non-deferred fees are assigned to evm.Coinbase which originates from the block author.
		coinbase, err := r.Chain.Sealer().Author(header)
		if err != nil {
			return nil, err
		}
		newSpec.IncRecipient(coinbase, distributedFee)
	}

	return newSpec, nil
}

// getDeferredRewardSimple is for Simple policy.
func getDeferredRewardSimple(config *reward.RewardConfig, execFee, blobFee *big.Int) (*reward.RewardSpec, error) {
	spec := reward.NewRewardSpec()
	minted := new(big.Int).Set(config.MintingAmount)

	// Non-deferred mode
	if !config.DeferredTxFee {
		var proposer *big.Int
		if config.Rules.IsMagma {
			// In non-deferred mode, no fees to distribute here at the end of block processing.
			// Just distribute the minting reward to the proposer and stop.
			proposer = new(big.Int).Set(minted)
			execFee = big.NewInt(0)
		} else {
			// But Simple policy had a bug where transaction fees were distributed to the proposer here at the end of block processing
			// despite configured to non-deferred mode. To keep the backward compatibility, the buggy behavior retains until Magma.
			proposer = new(big.Int).Add(minted, execFee)
		}
		spec.Minted = new(big.Int).Set(minted)
		// Both exec fees and blob fees are burned during state transition in non-deferred mode,
		// not at finalization. TotalFee/BurntFee are completed by specWithNonDeferredFee (GetBlockReward only).
		spec.TotalFee = execFee // Note that we've set it to 0 for non-deferred + Magma (see above).
		spec.BurntFee = big.NewInt(0)
		spec.Proposer = proposer
		spec.IncRecipient(config.Rewardbase, proposer)
		return spec, nil
	}
