Based on the investigation, the strongest local-code analog to the "guard mitigation" bug class (a security-relevant enforcement flag that, once toggled, removes protection universally rather than narrowly) is GitHub Desktop's `protocol.file.allow=always` toggle used for submodule operations.

### Title
Submodule `file://` protocol allowance permits attacker-controlled `.gitmodules` to read arbitrary local paths outside the repository - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` conditionally prepends `-c protocol.file.allow=always` to `git submodule update --init --recursive` whenever the caller passes `allowFileProtocol = true`. [1](#0-0) 
This flag is plumbed through `checkoutBranch` and `checkoutCommit`, both of which forward it, unmodified, into the submodule-update call that runs automatically after every checkout. [2](#0-1) 

### Finding Description
Git normally restricts the `file://` transport for submodules (`protocol.file.allow` defaults to `user`/`no` depending on version) specifically to prevent a repository from silently pulling in local filesystem content via a maliciously crafted `.gitmodules` entry such as `url = file:///home/victim/.ssh` or `file:///etc`. When Desktop passes `allowFileProtocol = true`, it globally overrides this protection for the entire `submodule update --init --recursive` invocation, meaning *every* submodule URL in the attacker-supplied `.gitmodules`, not just the one the feature was intended for (e.g. a same-machine relative submodule used in local testing/dev workflows), is permitted to use `file://`.

The broken invariant mirrors the ReNFT report's pattern exactly: a legitimate escape-hatch/allowance mechanism (there, whitelisted delegatecalls to fix a bricked guard; here, `protocol.file.allow=always` to support legitimate local-path submodules) is applied too broadly, at a scope boundary that an attacker fully controls (the `.gitmodules` file inside a repository they authored). Just as the Guard mitigation didn't scope the delegatecall allowance to only the specific upgrade path, Desktop's flag doesn't scope the file-protocol allowance to only the specific submodule/URL that legitimately needs it — it is an all-or-nothing switch applied per git invocation, over which the attacker has full content control via `.gitmodules`.

### Impact Explanation
If `allowFileProtocol` is enabled for any checkout/pull that touches an attacker-authored repository, `git submodule update --init --recursive` will happily treat a `file://` URL in `.gitmodules` as a valid submodule source and clone/copy the referenced local directory's tracked content into the victim's working tree — this is a file read outside the repository boundary, matching the report's accepted impact category ("file... read outside the repo"). Because submodule updates run automatically as part of ordinary checkout/pull flows, the victim does not need to take any unusual action beyond opening/using a cloned or fetched repository that contains such a `.gitmodules` entry, which satisfies the "attacker controls a cloned/fetched repository" threat model.

### Likelihood Explanation
This can only be fully assessed as remotely exploitable if `allowFileProtocol` is ever set to `true` for checkouts on repositories the app does not otherwise fully trust (e.g., for arbitrary/absolute `file://` submodule URLs rather than only same-origin relative ones). I was not able to inspect the `app-store.ts` call sites that decide the value of `allowFileProtocol` before running out of tool budget, so I cannot confirm here whether Desktop restricts this flag to relative-URL submodules only (which would substantially narrow the exploitable surface) or applies it uniformly regardless of URL shape. This is the key open question that determines whether the primitive is reachable by an untrusted repository author versus only usable in already-trusted local-clone scenarios.

### Recommendation
Confirm (in `app-store.ts`/`dispatcher.ts`, where `allowFileProtocol` is threaded through to `checkoutBranch`/`checkoutCommit`) that the flag is only ever set based on a per-submodule-URL check (i.e., only relative submodule URLs, never absolute `file://`/`file:///` paths) rather than as a blanket "allow always" for the whole checkout. If any code path derives `allowFileProtocol = true` from repository content or heuristics without validating each submodule URL, scope the `-c protocol.file.allow=...` override to the specific submodule path (e.g., via `git -c submodule.<name>.protocol.file.allow=always` semantics or pre-filtering `.gitmodules` entries) instead of applying it to the entire `submodule update --init --recursive` invocation.

### Proof of Concept
1. Attacker creates a repository containing a `.gitmodules` file with an entry such as:
```
[submodule "leak"]
    path = leak
    url = file:///Users/victim/.ssh
```
2. Victim clones/opens this repository in GitHub Desktop and performs any checkout or pull that triggers `updateSubmodulesAfterOperation` with `allowFileProtocol = true`. [3](#0-2) 
3. Git executes `submodule update --init --recursive` with `protocol.file.allow=always`, treats `file:///Users/victim/.ssh` as a valid submodule source, and materializes its tracked contents under `leak/` inside the checked-out repository, which is subsequently visible/committable by Desktop.

Unresolved uncertainty: without confirming the exact conditions under which `allowFileProtocol` is set to `true` in `app-store.ts`, I cannot state with certainty whether this path is reachable for arbitrary attacker-controlled repositories in the current build, or is scoped/gated in a way that prevents it. A follow-up session with full access to `app-store.ts`/`dispatcher.ts` call sites for `checkoutBranch`, `checkoutCommit`, and `updateSubmodulesAfterOperation` is needed to close this gap.
