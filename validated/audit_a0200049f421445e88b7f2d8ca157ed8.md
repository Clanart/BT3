### Title
Duplicate withdrawal-UTXO collision lets one payout tx double-credit reimbursement across two deposits - (File: `core/src/database/verifier.rs`)

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` purely on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, with no schema-level uniqueness on those columns and no idx-collision check in `update_withdrawal_utxo_from_citrea_withdrawal`. If two Citrea withdrawal indices are made to reference the identical Bitcoin UTXO, a single real payout transaction that spends that UTXO produces two joined rows, and `update_finalized_payouts`/`update_payout_txs_and_payer_operator_xonly_pk` writes the same `payout_txid`/`payout_payer_operator_xonly_pk` into both `withdrawals` rows. Since reimbursement authorization (`get_payout_info_from_move_txid`, used by `is_kickoff_malicious` and the operator's kickoff/assert flow) is keyed by each deposit's distinct `move_to_vault_txid`, this duplication lets the credited operator obtain a valid-looking kickoff/reimbursement for **two separate deposits' vault UTXOs** while having funded only one payout.

### Finding Description
The binding this breaks: **number of Bitcoin payout transactions that actually fronted funds == number of withdrawal `idx` rows credited with that reimbursement**. Concretely, it should hold that for a single spend of UTXO `U` (one `spending_txid`), at most one `withdrawals.idx` should be marked reimbursed by it. The code allows: `count(idx credited by spending_txid=T) > 1` for a single `T`.

Trace:
- `core/src/database/verifier.rs:108-135` `update_withdrawal_utxo_from_citrea_withdrawal` performs a bare `UPDATE ... WHERE idx = $1`, with no check against other rows already using the same `(withdrawal_utxo_txid, withdrawal_utxo_vout)`.
- `core/src/database/schema.sql:271-274` declares `withdrawal_utxo_txid`/`withdrawal_utxo_vout` with no `UNIQUE` constraint.
- `core/src/verifier.rs:2204-2262` `update_citrea_deposit_and_withdrawals` blindly loops over `new_withdrawals` from `collect_withdrawal_utxos` (Citrea) and calls `update_withdrawal_utxo_from_citrea_withdrawal` per idx with no cross-idx collision check.
- `core/src/database/verifier.rs:170-196` `get_payout_txs_for_withdrawal_utxos` JOINs `withdrawals w` to `bitcoin_syncer_spent_utxos bsu` on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`. If rows for `idx=i` and `idx=j` both carry the same `(txid, vout)`, and one spend of that UTXO is recorded in `bitcoin_syncer_spent_utxos` (via `bitcoin_syncer.rs:143-164` `save_transaction_spent_utxos`), the JOIN returns two tuples `(i, spending_txid)` and `(j, spending_txid)` for the same `spending_txid`.
- `core/src/verifier.rs:2283-2353` `update_finalized_payouts` consumes this result set and calls `update_payout_txs_and_payer_operator_xonly_pk` (verifier.rs:199-251), writing the same `payout_txid`, `payout_payer_operator_xonly_pk`, `payout_tx_blockhash` into **both** `withdrawals` rows.
- `core/src/database/verifier.rs:253-280` `get_payout_info_from_move_txid` is keyed by `move_to_vault_txid`, which is distinct per deposit (each deposit has its own real, presigned move-to-vault transaction id, not attacker-forgeable). So both deposit `i`'s and deposit `j`'s lookup will each independently return "reimbursed" info pointing at the same `payout_txid`/operator.
- `core/src/verifier.rs:1859-1915` `is_kickoff_malicious` and `core/src/operator.rs:1275-1296`/`1820-1835` (`send_asserts`, `get_next_txs_to_send`) both use `get_payout_info_from_move_txid` to authorize a kickoff/reimbursement for a given deposit's `move_to_vault_txid`, comparing operator pubkey and committed blockhash — neither of these checks detects that the underlying `payout_txid` was already used to satisfy a different deposit.

Attacker exploit flow: an unprivileged withdrawer calls Citrea's `withdraw()` twice (getting assigned withdrawal indices `i` and `j`), supplying identical UTXO bytes both times (a dust UTXO they own and can sign for with `SinglePlusAnyoneCanPay`, per `core/src/test/common/setup_utils.rs:430-543` semantics of the withdrawal UTXO used in `create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407-436`). An operator (possibly the attacker's own colluding operator, or unwittingly any operator who fronts the payout) constructs and broadcasts a single payout transaction spending that dust UTXO once. `bitcoin_syncer` records one spend; the DB join then duplicates the credit to both `idx=i` and `idx=j`.

Existing guards do not catch this: `Verifier::is_deposit_valid` and `SECP.verify_schnorr` validate the withdrawer's signature and profitability for each `withdraw` call individually, but nothing cross-references the UTXO against other outstanding withdrawal indices; `is_kickoff_malicious` only checks operator identity/blockhash match, not payout-uniqueness across deposits.

### Impact Explanation
An operator can be reimbursed from **two different deposits' vault UTXOs** (or a colluding operator + withdrawer pair can arrange this) while having funded only one payout transaction. This is a direct case of "an operator reimbursed for a payout it never funded" (Critical). The attack is repeatable across any number of withdrawal indices the attacker can register with colliding UTXO bytes, up to however many deposits/withdrawal slots are outstanding — each additional colliding idx yields one more fraudulent reimbursement per real payout. Blast radius: any deposit whose withdrawal slot is manipulated to collide loses its vault BTC to reimbursement collateral drain for the credited operator, without the corresponding withdrawer ever having been paid for that specific deposit index.

### Likelihood Explanation
Preconditions: (1) Citrea's `withdraw()` must not enforce that the UTXO argument is unique across withdrawal indices — this is asserted as a given precondition in the question and is consistent with the fact that this repo's database layer and update path (`update_withdrawal_utxo_from_citrea_withdrawal`, schema.sql) perform no independent validation either. (2) The attacker needs to control/trigger two withdrawal registrations (achievable if withdraw is permissionless/pool-based, requiring the attacker to have enough L2 balance for two withdrawals). (3) A payout transaction must actually spend the shared UTXO once (any operator, honest or colluding, triggers this by fronting the withdrawal normally). Attacker cost is modest: bitcoin fees for constructing/registering a dust UTXO and Citrea gas/L2 balance for two `withdraw()` calls; no verifier/operator privilege or key compromise is required. This is deterministic once the collision is set up — not probabilistic — and repeatable per additional colliding pair.

### Recommendation
- Add a database-level `UNIQUE` constraint on `withdrawals(withdrawal_utxo_txid, withdrawal_utxo_vout)` (where not null), and make `update_withdrawal_utxo_from_citrea_withdrawal` reject/short-circuit when the UTXO is already assigned to a different `idx`.
- Modify `get_payout_txs_for_withdrawal_utxos` to defensively enforce a 1:1 mapping (e.g., `DISTINCT ON (bsu.txid, bsu.vout)` ordered deterministically, or fail loudly if more than one `idx` maps to the same spent UTXO) rather than allowing silent fan-out.
- In `update_finalized_payouts`, detect and reject (or alert/no-op) when the same `spending_txid`/`payout_txid` would be assigned to more than one `idx`, and treat it as a malicious/duplicate condition rather than crediting both.

async fn duplicate_withdrawal_utxo_double_credits_payout() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();

    let move_txid_i = Txid::from_byte_array([0x11; 32]);
    let move_txid_j = Txid::from_byte_array([0x22; 32]);
    let idx_i = 1u32;
    let idx_j = 2u32;

    // Same colliding UTXO for both idx
    let shared_utxo = bitcoin::OutPoint {
        txid: bitcoin::Txid::from_byte_array([0x99; 32]),
        vout: 0,
    };
    let spending_txid = Txid::from_byte_array([0x77; 32]);
    let operator_pk = generate_random_xonly_pk();

    let mut dbtx = db.begin_transaction().await.unwrap();
    let block_id = db.insert_block_info(Some(&mut dbtx), &BlockHash::all_zeros(), &BlockHash::all_zeros(), 0).await.unwrap();
    db.insert_txid_to_block(&mut dbtx, block_id, &spending_txid).await.unwrap();

    // Two distinct deposits
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_i, &move_txid_i).await.unwrap();
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_j, &move_txid_j).await.unwrap();

    // Both idx registered with the SAME withdrawal_utxo (attacker-crafted collision)
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_i, shared_utxo, block_id).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_j, shared_utxo, block_id).await.unwrap();

    // Single real spend of the shared UTXO
    db.insert_spent_utxo(&mut dbtx, block_id, &spending_txid, &shared_utxo.txid, shared_utxo.vout.into()).await.unwrap();

    // BINDING CHECK: one spend should credit at most one idx
    let txs = db.get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id).await.unwrap();
    assert_eq!(txs.len(), 2); // VULNERABLE: returns 2 rows for 1 spend

    db.update_payout_txs_and_payer_operator_xonly_pk(
        Some(&mut dbtx),
        vec![
            (idx_i, spending_txid, Some(operator_pk), BlockHash::all_zeros()),
            (idx_j, spending_txid, Some(operator_pk), BlockHash::all_zeros()),
        ],
    ).await.unwrap();

    // Both deposits now independently show as "reimbursed" by the SAME payout
    let info_i = db.get_payout_info_from_move_txid(Some(&mut dbtx), move_txid_i).await.unwrap().unwrap();
    let info_j = db.get_payout_info_from_move_txid(Some(&mut dbtx), move_txid_j).await.unwrap().unwrap();
    assert_eq!(info_i.2, spending_txid);
    assert_eq!(info_j.2, spending_txid);
    assert_eq!(info_i.0, Some(operator_pk));
    assert_eq!(info_j.0, Some(operator_pk));
    // -> operator can now pass is_kickoff_malicious for BOTH deposit i and deposit j
    //    from a single funded payout, i.e., double reimbursement.

    async fn is_kickoff_malicious(

            .db
            .get_payout_info_from_move_txid(Some(dbtx), move_txid)

            tracing::warn!("No operator xonly pk found in payout tx OP_RETURN, assuming malicious");

            &[wt_derive_path],
            self.config.protocol_paramset(),

            if committed_blockhash != truncated_blockhash {

                return Ok(true);
            }
        } else {
            return Err(eyre::eyre!("Couldn't retrieve committed data from witness").into());

        Ok(false)

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())
    }

/// Creates a [`TxHandler`] for the `payout_tx`.
///
/// This transaction is sent by the operator to front a peg-out, after which operator will send a kickoff transaction to get reimbursed.
///
/// # Inputs
/// 1. UTXO: User's withdrawal input (committed in Citrea side, with the signature given to operators off-chain)
///
/// # Outputs
/// 1. User payout output
/// 2. OP_RETURN output (with operators x-only pubkey that fronts the peg-out)
///
/// # Arguments
/// * `input_utxo` - The input UTXO for the payout, committed in Citrea side, with the signature given to operators off-chain.
/// * `output_txout` - The output TxOut for the user payout.
/// * `operator_xonly_pk` - The operator's x-only public key that fronts the peg-out.
/// * `user_sig` - The user's signature for the payout, given to operators off-chain.
/// * `network` - The Bitcoin network.
///
/// # Returns
/// A [`TxHandler`] for the payout transaction, or a [`BridgeError`] if construction fails.
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
