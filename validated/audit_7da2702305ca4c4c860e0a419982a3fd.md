### Title
Index-space confusion in MuSig participant re-mapping drops the wrong signer's preprocess/share, causing DKG-confirmation signing failure and false blame attribution - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to the kernel bug (`smp_processor_id()` returning an ambient, context-dependent CPU identity instead of the pinned `raw_smp_processor_id()`), `threshold_i_map_to_keys_and_musig_i_map` removes "our" entry from the re-keyed map using an index from the *wrong index space* — the full non-removed validator ordering — after the map has been re-based onto positional indices over only the *submitting* signers. Whenever a proper subset of validators supplies preprocesses (the normal threshold case), the wrong entry is removed and our own empty placeholder is left behind.

### Finding Description
`DkgConfirmer::share`/`complete` receive preprocesses/shares keyed by each signer's `spec.i(removed, key).start` — their index in the ordering of *all non-removed* validators. `threshold_i_map_to_keys_and_musig_i_map` (`coordinator/src/tributary/signing_protocol.rs:208-250`) then:

1. Inserts `our_threshold_i` (our `spec.i(removed, ...).start`) into the map with an empty payload (line 219).
2. Sorts keys, then re-enumerates, assigning each submitter a fresh `musig_i = raw_i + 1` over the *submitted* set only (lines 241-245).
3. Calls `map.remove(&our_threshold_i)` (line 247) — but `our_threshold_i` is expressed in the full-set index space, while `map` is now keyed by subset-positional `musig_i`.

These only coincide when every non-removed validator submits. With any subset (e.g. a threshold `t` of `n`, or any signer below us absent), our real `musig_i` (`raw_i + 1`) is strictly less than `our_threshold_i`. The `remove` then either deletes a *different* participant's preprocess/share (whichever signer landed at position `our_threshold_i`), or is a no-op if `our_threshold_i` exceeds the map size. Either way, our own placeholder entry `our_threshold_i -> vec![]` survives and is fed to `read_preprocess`/`read_share`, which fails on empty bytes and returns `Err(Participant)` — misidentifying ourselves (or blaming the wrongly-removed peer) as the faulty participant.

### Impact Explanation
The MuSig/FROST machine in `share_internal` (`lines 150-181`) builds `included` from the preprocess map; the phantom empty entry causes `FrostError::InvalidPreprocess`/`InvalidParticipant` attribution, so no signature share is produced. Because `complete()` re-runs `share_internal` (line 322), the confirmation signing path deterministically fails for any signing session where the submitting set is a strict subset with a missing lower-indexed signer — i.e. ordinary threshold operation. This permanently stalls `set_keys` confirmation for that attempt (availability impact on DKG confirmation) and emits `InvalidParticipant` blame against an innocent validator ID, which upstream code treats as a malicious-participant signal.

### Likelihood Explanation
The inputs are `HashMap<Participant, Vec<u8>>` of preprocesses/shares deserialized from peer messages (`ProcessorMessage`-style gossip/BFT-ordered). Any honest or byzantine omission of a lower-indexed validator's preprocess — the expected case when only `t` of `n` sign — triggers the wrong removal on every coordinator executing this code. No special privileges are needed; a peer simply not submitting (or a subset being finalized) is sufficient. Deterministic once triggered.

### Recommendation
In `threshold_i_map_to_keys_and_musig_i_map`, compute our *subset-positional* index during the enumeration (record `raw_i` where `key == our_key`) and remove that `musig_i`, rather than reusing `our_threshold_i` from the full-set index space. Equivalently, track our position explicitly: `let our_musig_i = Participant::new(raw_i + 1)` captured during the sort/enumerate loop, then `map.remove(&our_musig_i)`. Add a test where a lower-indexed signer is absent to cover subset signing.

### Proof of Concept
Conceptual trace with `removed = []`, validators `v1..v4` (weights 1), us = `v3` (`our_threshold_i = 3`), and submitters `{v1, v3, v4}` (v2 abstains):

- Map after insert: `{1: p1, 3: [], 4: p4}`; sorted keys `[1, 3, 4]`; musig_i assignment: `v1→1, v3(us)→2, v4→3`; `participants = [v1, v3, v4]`; `map = {1: p1, 2: [], 3: p4}`.
- `map.remove(&our_threshold_i)` = `map.remove(&3)` deletes **v4's** preprocess and leaves `{1: p1, 2: []}`.
- `share_internal` reads `vec![]` for `Participant(2)` → `read_preprocess` fails → `Err(Participant(2))` — self-blame, no share produced; v4's preprocess silently discarded. Repeats identically in `complete()`, so the attempt can never confirm while v2 is absent.
