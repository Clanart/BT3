### Title
Hardcoded 40-character SHA regex silently drops commits for SHA-256 object-format repositories - (File: app/src/lib/git/rev-list.ts)

### Summary
`getCommitsInRange` in `app/src/lib/git/rev-list.ts` parses `git rev-list --oneline --no-abbrev-commit` output with a regex that hardcodes the legacy SHA-1 40-hex-character object id length, exactly analogous to the reported bug's hardcoded 165-byte SPL account size that ignores variable-length Token-2022 extension data. Just as the Solana fix needed to compute the actual account size instead of assuming the legacy fixed size, Git object ids are not universally 40 hex characters — Git's SHA-256 object format (`extensions.objectFormat = sha256`) produces 64-hex-character ids — and the parser here has no branch for that case.

### Finding Description
`getCommitsInRange` requests full, non-abbreviated commit ids via `--no-abbrev-commit` and then matches each output line with: [1](#0-0) 
```
const commitSummaryRe = /^([a-z0-9]{40}) (.*)$/
...
for (const line of lines) {
  const match = commitSummaryRe.exec(line)
  if (match !== null && match.length === 3) { ... }
}
```
The `{40}` quantifier is a fixed-length hardcoding of the legacy SHA-1 hex digest length, mirroring the bug class from the reported issue: a hardcoded legacy size (165 bytes / 40 hex chars) that fails to account for a valid, larger alternate format. If the repository's object database uses the SHA-256 object format, `rev-list` would emit 64-character hex ids, the regex would never match any line, and the loop silently produces an empty `commits` array rather than throwing or falling back — there is no error path here comparable to the `GitError.BadRevision` check above it. [2](#0-1) 

This function backs `getCommitsBetweenCommits`, which is documented to "emulate how `git rebase` initially determines what will be applied to the repository" and is consumed by `rebase.ts`, `cherry-pick.ts`, and `update-branch.ts` for rebase/cherry-pick operations. [3](#0-2) 

### Impact Explanation
If reachable, the practical effect is that Desktop's rebase/cherry-pick machinery would believe there are zero commits to replay between two revisions, silently corrupting the outcome of a rebase or cherry-pick operation (e.g., a rebase that should replay N commits onto a new base instead replays none, or a cherry-pick range appears empty) without surfacing any error to the user. This matches the "silent corruption of what the user commits or pushes" impact category rather than a crash.

### Likelihood Explanation
I could not confirm from the codebase that GitHub Desktop's bundled Git (via dugite) actually supports or interacts with SHA-256 object-format repositories in the wild, nor did I find any other code in the repo that is object-format aware (no `extensions.objectFormat` handling, no 64-char SHA regex variant anywhere in the codebase). This makes the likelihood of a real attacker-controlled trigger (a maliciously crafted SHA-256-format repo that a user clones/fetches) uncertain — it depends on the underlying Git binary's SHA-256 support being enabled/interoperable, which is outside this repository's control. I'm flagging this explicitly rather than asserting confirmed exploitability.

### Recommendation
Replace the fixed `{40}` length in `commitSummaryRe` with a variable-length hex pattern (e.g., `[a-f0-9]{40,64}`) or, more robustly, split each line on the first whitespace rather than assuming a fixed id length, so the parser is agnostic to object-id length regardless of the repository's `extensions.objectFormat`.

### Proof of Concept
Not independently verified end-to-end (requires a Git binary and repository actually using the SHA-256 object format, which I could not validate is supported/reachable in this environment). Conceptually:
1. Create or clone a repository initialized with `git init --object-format=sha256` (requires Git built with SHA-256 support).
2. Make several commits.
3. In Desktop, trigger a rebase or cherry-pick that internally calls `getCommitsBetweenCommits`/`getCommitsInRange`.
4. Because `git rev-list --oneline --no-abbrev-commit` emits 64-character object ids, `commitSummaryRe` never matches, and the returned commit list is empty, causing the rebase/cherry-pick to silently do nothing instead of replaying the expected commits.

Given the unresolved uncertainty about whether this path is reachable with Desktop's bundled Git, I present this as the closest local-code analog found, with the caveat above.

export async function getCommitsInRange(
  repository: Repository,
  range: string
): Promise<ReadonlyArray<CommitOneLine> | null> {
  const args = [
    'rev-list',
    range,
    '--reverse',
    // the combination of these two arguments means each line of the stdout
    // will contain the full commit sha and a commit summary
    `--oneline`,
    `--no-abbrev-commit`,
    '--',
  ]

  const options = {
    expectedErrors: new Set<GitError>([GitError.BadRevision]),
  }

  const result = await git(args, repository.path, 'getCommitsInRange', options)

  if (result.gitError === GitError.BadRevision) {
    return null
  }

  const lines = result.stdout.split('\n')

  const commits = new Array<CommitOneLine>()

  const commitSummaryRe = /^([a-z0-9]{40}) (.*)$/

  for (const line of lines) {
    const match = commitSummaryRe.exec(line)

    if (match !== null && match.length === 3) {
      const sha = match[1]
      const summary = match[2]

      commits.push({
        sha,
        summary,
      })
    }
  }
