## Title
Future-dated oracle price bypasses staleness check via zero-clamped delta - (File: `mainnet/contracts/market/v0-4-market.clar`)

## Summary
The oracle freshness gate in `oracle-timestamp-fresh` clamps the staleness delta to `u0` whenever the reported price `timestamp` is greater than `stacks-block-time`, instead of rejecting it. This mirrors the reported bug class: a time-bound value used to gate acceptance (here, an oracle price timestamp, analogous to `fundingStartBlock`/`fundingEndBlock`) is missing the precondition that it must not be *ahead of* the reference clock. Any price whose timestamp lands in the future is treated as maximally fresh forever, defeating the staleness protection that the rest of the design relies on.

## Finding Description
`oracle-timestamp-fresh` is the sole gate protecting `price-resolve` against stale data: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

When `ts > stacks-block-time` (the feed's reported timestamp is ahead of the chain's own current time), `delta` is forced to `u0`, and `u0 <= max-staleness` is always true. The intended purpose of this branch is presumably to avoid an underflow in `(- stacks-block-time ts)`, but the side effect is that any future-dated price is unconditionally accepted as fresh, with no ceiling on how far in the future it can be. This is the same missing-precondition pattern as the report: a value that should be bounded relative to "now" (there: `fundingStartBlock`/`fundingEndBlock` vs `block.number`; here: oracle `timestamp` vs `stacks-block-time`) has no upper-bound/ordering check, only a one-sided comparison that silently degrades into a no-op instead of failing closed.

This check is invoked directly in the core pricing path used for every collateral/debt valuation: [2](#0-1) 

The monotonicity guard `(>= ts prev)` (documented as the "Monotonic Timestamps" safety feature) does not help here since a future timestamp is still `>= prev` by definition, and once accepted it becomes the new `last-update-time`, permanently raising the floor for `prev` as well. [3](#0-2) 

## Impact Explanation
If a future-dated timestamp is ever recorded for a feed (Pyth publisher clock skew/misbehavior, DIA's reported timestamp, or any other feed source resolved through `resolve-price-feed`), the price attached to it can never be flagged stale again by `oracle-timestamp-fresh`, because `delta` stays `u0` for that feed until real chain time catches up to the false future timestamp — potentially indefinitely if the injected timestamp is far enough ahead. Since `price-resolve` feeds directly into collateral/debt valuation used for borrow, withdraw, and liquidation health checks, an unbounded stale/incorrect price being treated as always-fresh can allow borrowing against or defending an inflated/deflated valuation, i.e., a wrong health verdict driving theft or freezing of user funds. This lands in the Critical/High impact classes (protocol insolvency or theft of funds via mispriced collateral/debt) once the wrong price persists past its legitimate freshness window.

## Likelihood Explanation
Likelihood depends on how the flagged future timestamp gets recorded in the first place — it is not attacker-forgeable directly through this function alone, since `price-resolve` sources `timestamp` from `resolve-price-feed` (Pyth/DIA). However, the code path itself contains no defensive bound, so any anomalous or malicious upstream timestamp (clock skew, relayer bug, or a misbehaving/compromised feed publisher) is silently converted from "reject as stale in the future" into "always pass," which is strictly worse than failing closed. This is a real gap in the local validation logic regardless of how the anomalous timestamp arises.

## Recommendation
Change `oracle-timestamp-fresh` to reject (not clamp to zero) when `ts > stacks-block-time`, e.g.:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
This enforces that the oracle timestamp cannot be ahead of the chain's own clock, closing the unbounded-freshness window.

## Proof of Concept
1. A price update for a given `{type, ident}` feed is recorded with `timestamp > stacks-block-time` (e.g., due to publisher clock skew or a malformed but validly-signed update).
2. `price-resolve` calls `oracle-timestamp-fresh timestamp last-update-time max-staleness`.
3. Inside, `(> ts stacks-block-time)` is true, so `delta = u0`, and `(<= u0 max-staleness)` is trivially true; `(>= ts prev)` also holds since `ts` is the largest value seen.
4. `price-resolve` accepts the price as fresh and stores `timestamp` as the new `last-update-time` via `map-set last-update`.
5. Until real `stacks-block-time` advances past that future `timestamp`, every subsequent call to `oracle-timestamp-fresh` for this feed keeps hitting the `> ts stacks-block-time` branch, so the stale/incorrect price associated with that timestamp continues to be reported as fresh, feeding into collateral/debt valuation used by `process-collateral-asset`/health-factor computations.
