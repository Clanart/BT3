### Title
Fee-on-transfer / non-standard ERC20 tokens break the 1:1 backing invariant in `BridgeTransferERC20` lock/unlock bridging - ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
`requestERC20Transfer`/`onERC20Received` in `BridgeTransferERC20.sol` accept a nominal `_value` from the caller and emit a `RequestValueTransfer` event carrying that nominal `_value`, but never verify how many tokens the bridge contract actually received. For a fee-on-transfer (or otherwise non-standard) ERC20 token, the amount that actually lands in the bridge contract's balance can be less than `_value`. The operator-side counterpart bridge (`handleERC20Transfer`/`unlockToken` flow) still releases/mints the full nominal `_value`, so the bridge's real token holdings become under-collateralized relative to what has been promised/paid out on the other chain.

### Finding Description
In `requestERC20Transfer`, the contract pulls exactly `_value + _feeLimit` via `safeTransferFrom`, but for fee-on-transfer tokens the received amount is `< _value + _feeLimit`: [1](#0-0) 

`_requestERC20Transfer` then charges/refunds fee using the *nominal* `_feeLimit` (not the actual balance delta) via `_payERC20FeeAndRefundChange`, and emits `RequestValueTransfer` with the nominal `_value`, which is exactly what the operators will later use to call `handleERC20Transfer` on the counterpart chain to mint or unlock the "same" amount: [2](#0-1) 

`BridgeFee._payERC20FeeAndRefundChange` also blindly trusts the nominal `_feeLimit` figure to transfer fee/refund amounts rather than deriving them from an actual pre/post balance delta: [3](#0-2) 

On the receiving/counterpart side (non mint-burn mode), `handleERC20Transfer` releases the full nominal `_value` out of the bridge's locked token pool: [4](#0-3) 

This exactly matches the reported bug class: an accounting variable (here, the amount promised to the counterpart chain / total locked-token liability) is incremented by the *intended* transfer amount instead of the *actually received* amount. As users repeatedly bridge fee-on-transfer tokens, the aggregate amount promised (and later released) on the counterpart/return-trip side grows to exceed the bridge's real token balance, so eventually some legitimate `handleERC20Transfer`/unlock call reverts due to insufficient balance — the same "last withdrawer cannot withdraw" failure mode as in the original `Shelter.withdraw` report, but here manifesting as bridge insolvency/DoS for lock-and-release ERC20 bridging.

### Impact Explanation
This is reachable by any unprivileged token holder who calls the public `requestERC20Transfer`/`onERC20Received` entry points with a registered fee-on-transfer ERC20 token — no operator or admin privilege required to trigger the mis-accounting. The impact is a systemic under-collateralization of the bridge's ERC20 holdings relative to what it has committed to release on the counterpart chain: honest users bridging back or last-in-line "handle" calls will find the contract's actual token balance insufficient to fulfill `safeTransfer(_to, _value)`, causing transaction reverts (denial of service) and effectively causing early transferors' full nominal value to be honored at the expense of later users who cannot get their tokens released — a form of unauthorized value misallocation/loss for the bridge users and operators managing collateral 1:1 assumptions.

### Likelihood Explanation
Likelihood depends on the token registered via `registerToken` (an owner-only action) being a fee-on-transfer/rebasing/non-standard ERC20. Since `registerToken` does not restrict token behavior and this bridge is designed to support arbitrary registered ERC20 tokens across service chains, this is a plausible and directly triggerable scenario once such a token is registered — no low-level exploit sophistication needed, just a series of ordinary `requestERC20Transfer` calls with a fee-on-transfer token.

### Recommendation
In `_requestERC20Transfer`/`onERC20Received`, measure the actual amount received by comparing the bridge's token balance before and after the `safeTransferFrom` call, and use that measured delta (net of any bridge fee) as the value that is locked/emitted in `RequestValueTransfer`, rather than trusting the caller-supplied `_value`/`_feeLimit`. Apply the same before/after balance-delta pattern in `_payERC20FeeAndRefundChange` for computing the fee actually collected and the change actually refunded.

### Proof of Concept
1. Owner registers a fee-on-transfer ERC20 token `T` (e.g., taking a 5% fee on every `transfer`/`transferFrom`) via `registerToken(T, cT)`.
2. Alice calls `requestERC20Transfer(T, bob, value=100, feeLimit=0, "")`. The bridge calls `safeTransferFrom(alice, bridge, 100)`, but due to the 5% fee only 95 tokens actually land in the bridge; nonetheless, `RequestValueTransfer` emits `value=100`.
   - See [1](#0-0)  for the unchecked `safeTransferFrom`.
3. Operators observe the `RequestValueTransfer(value=100)` event and call `handleERC20Transfer` on the counterpart chain, releasing/minting 100 (nominal) tokens of `cT` to Bob — 5 more than what the source-chain bridge actually holds in reserve for `T`.
4. Repeating this pattern accumulates a growing gap between what has been promised on the counterpart chain and the real locked balance of `T` in the source bridge.
5. When a return-trip `handleERC20Transfer(..., T, value, ...)` is eventually processed on the source chain to release locked `T` tokens (in non-mint-burn mode) as in [5](#0-4) , the `safeTransfer(_to, _value)` call reverts because the bridge's actual `T` balance is insufficient — denial of service / loss for the affected user, and unrecoverable insolvency for the bridge's declared liabilities.

        internal

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
