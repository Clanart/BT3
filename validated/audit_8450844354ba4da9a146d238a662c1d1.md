### Title
Quadratic-cost Lagrange interpolation during `ThresholdKeys` deserialization enables CPU-exhaustion DoS from attacker-supplied bytes - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` accepts an attacker-controlled participant count `n` (u16) and interpolation selector, then calls `ThresholdKeys::new`, which computes the group key via Lagrange `interpolation_factor` for each of the first `t` participants. Each factor is `O(t)` field operations, making deserialization `O(t^2)`. A ~4 MB blob with `t = n = 65535` forces ~4.3 billion scalar multiplications plus 65535 field inversions and point multiplications — a classic CWE-400 resource-exhaustion primitive analogous to the `x/net` HTML parser CPU-blowup advisory, reachable purely from untrusted serialized bytes.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the reader, then reads `n` scalars (for `Interpolation::Constant`) and `n` verification-share points, before delegating to `ThresholdKeys::new`:

- `crypto/dkg/src/lib.rs:591-602` — `t`, `n`, `i` parsed from the stream with no cap beyond `u16::MAX`.
- `crypto/dkg/src/lib.rs:620-623` — `n` points read, so input size is linear in `n` (~2–4 MB at `n = 65535`).
- `crypto/dkg/src/lib.rs:376-378` — `ThresholdKeys::new` computes `group_key` by summing `verification_shares[i] * interpolation.interpolation_factor(i, &t)` for `i` in `1..=t`.
- `crypto/dkg/src/lib.rs:229-247` — the `Interpolation::Lagrange` branch of `interpolation_factor` loops over every element of `included` performing scalar multiplications and a field inversion.

So for Lagrange keys with `t = n = 65535` (valid per `ThresholdParams::new` since `t <= n`, `t`, `n` nonzero), `new` performs `t * t ≈ 4.3e9` scalar muls, `t` inversions, and `t` variable-time point multiplications to derive the group key — all inside a single `read` call on bytes an attacker supplied. The same quadratic factor recomputation occurs in `ThresholdKeys::view` (`crypto/dkg/src/lib.rs:500-507`), where `interpolation_factor` is re-evaluated per included signer, so every signing session re-pays `O(t^2)` against the deserialized keys.

### Impact Explanation
An unprivileged party able to feed bytes to `ThresholdKeys::read` (e.g., a corrupted/maliciously crafted key blob consumed by a processor, or any integrator that deserializes keys from untrusted input) causes the host to burn CPU quadratic in `n` — roughly `n^2` field multiplications plus `n` point multiplications — from an input of only `O(n)` bytes. At `n = 65535` this is billions of group/field operations per call, and repeated calls or `view()`/signing operations amplify it further. This is a denial of service against the node/processor performing the deserialization, matching the "parsing consumes excessive CPU time" class of GHSA-5cv4-jp36-h3mw.

### Likelihood Explanation
Severity Medium. The amplification factor is large (~65,000x CPU-per-input-byte), the check ordering means the expensive work happens during the `ThresholdKeys::new` validation inside `read` itself, and no size limit or early bound on `t`/`n` exists in the deserialization path. Likelihood is gated by an integrator actually deserializing `ThresholdKeys` from unprivileged input — in Serai itself these are normally locally-generated keys read from the node's own DB (`processor/src/key_gen.rs`), so exploitation requires either DB corruption by an attacker or an integrator exposing the parse path. `n` is capped at `u16::MAX` rather than truly unbounded, which bounds but does not eliminate the blowup.

### Recommendation
- In `ThresholdKeys::read`, enforce a sane maximum on `t`/`n` before performing interpolation work, or defer `group_key` derivation lazily.
- Precompute/cache Lagrange products incrementally in `ThresholdKeys::new` and `view` (compute `num`/`denom` products once over `included`, then per-signer correction), reducing `O(t^2)` to `O(t)`.
- Alternatively, bound `ThresholdParams` construction used for deserialization to the known validator-set size.

### Proof of Concept
```rust
// Pseudocode against crypto/dkg (e.g., C = Ristretto or Secp256k1 ciphersuite).
// Build a serialized ThresholdKeys blob with t = n = u16::MAX, i = 1,
// Interpolation::Lagrange.
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(u16::MAX.to_le_bytes()); // t
buf.extend(u16::MAX.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes());     // i
buf.push(1);                        // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref()); // secret_share
for _ in 1 ..= u16::MAX {
    buf.extend(C::generator().to_bytes().as_ref()); // verification_shares
}
// ~2 MB input; ThresholdKeys::read enters ThresholdKeys::new which performs
// ~65535^2 scalar multiplications + 65535 inversions + 65535 point muls.
let _keys = ThresholdKeys::<C>::read(&mut buf.as_slice()); // CPU exhaustion
```

The relevant code paths: `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), `ThresholdKeys::new` group-key derivation (`crypto/dkg/src/lib.rs:376-378`), `Interpolation::Lagrange` factor loop (`crypto/dkg/src/lib.rs:229-247`), and the identical quadratic pattern in `ThresholdKeys::view` (`crypto/dkg/src/lib.rs:500-507`).

Caveat: this relies on `ThresholdKeys::read` being reachable with attacker-controlled bytes, which the scan rules permit as an in-scope entry point; whether a given deployment exposes that path is integrator-dependent.
