## Title
Double-spend of escrowed order funds via missing `_filled` guard on cross-chain `RedeemEscrow`/`RefundEscrow` delivery - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core invariant is: *state that gates a payout must be committed before any external call/callback, otherwise the same payout path can be re-triggered.* In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the local same-chain cancellation path (`cancelOrder`) explicitly checks `_filled[commitment]` before releasing escrow, but the cross-chain delivery path (`onAccept` for `RedeemEscrow`/`RefundEscrow`) calls `withdraw()` directly with **no such check**. Because a fill and a cancellation are dispatched as two independently-valid cross-chain messages (each with its own unique ISMP request commitment), Hyperbridge's per-request replay protection does not stop both from being delivered for the *same order commitment*, letting `withdraw()` run twice and pay out the same escrow twice.

### Finding Description
`withdraw()` is the single function that releases escrowed funds for an order: [1](#0-0) 

`cancelOrder`'s same-chain branch defends against double release by checking `_filled` before calling `withdraw`: [2](#0-1) 

But the cross-chain delivery branch in `onAccept`, which handles both `RedeemEscrow` (fill payout, dispatched from the destination chain's `fillOrder`) and `RefundEscrow` (cancellation payout, dispatched from the destination chain's `cancelOrder`), calls `withdraw` unconditionally with no `_filled` check at all: [3](#0-2) 

Hyperbridge's replay protection operates on the **request commitment** (hash of the cross-chain message itself), not on the **order commitment** embedded in the message body: [4](#0-3) 

A `RedeemEscrow` message and a `RefundEscrow` message for the *same order* are two distinct requests (different `RequestKind` byte, different nonce/nonce-derived hash), so both pass replay protection independently. Once delivered, `withdraw()` runs to completion each time — decrementing `_orders[commitment][token]` and transferring tokens — without ever checking whether the order was already finalized by the other message.

### Impact Explanation
This is a direct double-settlement / duplicate-claim of bridged escrow funds: the same order's escrowed input tokens can be paid out once to the solver (via `RedeemEscrow` triggered by a legitimate fill) and a second time to the refund beneficiary (via `RefundEscrow` triggered by a legitimate cancellation), or vice-versa. Since the order owner and the solver can be the same attacker-controlled account, this results in unauthorized duplicate transfer of escrowed funds out of the gateway, directly matching the bounty's "double-claim/double-settlement" and "stealing or loss of funds" categories.

### Likelihood Explanation
No malicious relayer, prover, or governance actor is required. An attacker who places an order on the source (Tron) chain and also acts as (or colludes with) the solver on the destination chain can legitimately trigger both a fill (`fillOrder` → dispatches `RedeemEscrow`) and a cancellation (`cancelOrder` on the destination chain, once eligible → dispatches `RefundEscrow`) for the same order. Both are ordinary, protocol-permitted dispatches; delivery of each is independently valid under ISMP's per-request replay protection, so both reach `onAccept`/`withdraw` on the source chain.

### Recommendation
Add the same `_filled[commitment] != address(0)` guard in `onAccept`'s `RedeemEscrow`/`RefundEscrow` branch that already exists in `cancelOrder`, and set `_filled[commitment]` (or otherwise mark the order finalized) atomically before any external token transfer in `withdraw()`, consistent with checks-effects-interactions. Additionally, decrement `_orders[commitment][token]` before performing the external transfer/call inside `withdraw`'s loop, matching the correct ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` (lines 390-409), which decrements escrow before making the external call.

### Proof of Concept
1. Attacker places an order on the Tron (source) IntentGatewayV2 with themselves as `order.user`, escrowing input tokens.
2. Attacker (as solver) fills the order on the destination chain via `fillOrder`, which dispatches a `RedeemEscrow` POST request back to the Tron gateway.
3. Before or after that message is delivered, attacker also calls `cancelOrder` on the destination chain (eligible once expired, or immediately if unfilled from the destination's perspective in a race), dispatching a `RefundEscrow` POST request back to the Tron gateway for the same order commitment.
4. Both messages have distinct request commitments and each independently passes `EvmHost.dispatchIncoming`'s replay check.
5. Each delivery invokes `IntentGatewayV2.onAccept` → `withdraw(body, ...)` without any `_filled` check, so the escrowed tokens are transferred out twice for the same order commitment — once to the solver, once to the refund beneficiary.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }

        }

            // so that it can be retried

            return;
        }
