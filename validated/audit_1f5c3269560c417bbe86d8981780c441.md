## Analog Found

### Title
Incomplete daemon log redaction leaks wallet private-key entropy in cleartext debug logs - (File: `chia/daemon/server.py`)

### Summary
The Keycloak advisory describes verbose log formatting disclosing `Authorization`/`Cookie` credentials in cleartext because the logging layer did not sanitize sensitive request/response fields. Chia's local daemon has the equivalent protection point — `redact_sensitive_data()` — which is supposed to scrub credential material out of daemon websocket message logs before they hit disk, but its redaction trigger list is incomplete and misses the exact field name used to carry wallet seed material in the remote-keychain protocol.

### Finding Description
`chia/daemon/server.py` defines the single redaction gate for all daemon websocket traffic that gets logged at DEBUG level: [1](#0-0) 

The trigger set is `("pass", "key", "secret", "mnemonic")` — any dict key containing one of those substrings is redacted, everything else is logged verbatim. Per the module's own documented contract, *all* debug-level message logging (`WebSocketServer.handle_message()` and related logging of `WSMessage` contents) is required to pass through this function: [2](#0-1) 

The remote keychain protocol, however, transmits master-key material under a field literally named `entropy`, not `mnemonic` or `key`. `KeychainProxy.get_key_for_fingerprint()` requests a private key over the daemon connection and receives back `pk` and `entropy`, then reconstructs the mnemonic directly from that entropy: [3](#0-2) 

Because the string `"entropy"` does not contain `"pass"`, `"key"`, `"secret"`, or `"mnemonic"`, `redact_sensitive_data()` will not redact it. If DEBUG-level daemon logging is enabled (a supported, documented configuration — see the project's own acknowledgment of DEBUG-level key exposure risk), any `get_key_for_fingerprint` request/response containing `entropy` is written to the log file in cleartext. `bytes_to_mnemonic(bytes.fromhex(ent))` in the proxy shows this entropy is functionally equivalent to the wallet's mnemonic seed — recovering it is equivalent to recovering the full 24-word seed phrase and therefore every wallet, farmer, and pool key derived from it.

The project changelog already flags that DEBUG logging can leak the "local keyring passphrase" but explicitly claims the mnemonic itself is safe: [4](#0-3) 

That claim is false for the `entropy` field path, because the redaction trigger list was never updated to cover it — this is the same bug class as the Keycloak advisory: a verbose/debug logging path that "should" sanitize credentials but has an incomplete sanitizer, leading to cleartext credential/secret disclosure in log files (CWE-117).

### Impact Explanation
Anyone with read access to the daemon's DEBUG log file — a lower-privilege local user, backup/log-shipping process, or any other actor who can read Chia's log directory but is not supposed to have keychain access — can extract the raw entropy for a wallet fingerprint and reconstruct the full mnemonic/master private key. This grants full control of all wallet, farmer, and pool keys derived from that seed: theft of funds, farming rewards redirection, and pool identity takeover. This maps to "leaked-key" material exposure via a local daemon/keychain RPC path, which is explicitly in scope per the daemon/keychain/RPC authorization category.

### Likelihood Explanation
Exploitation requires (a) DEBUG-level daemon logging enabled — a supported and documented (if discouraged) configuration — and (b) a `get_key_for_fingerprint(private=True)` request/response traversing the daemon connection, which happens routinely for any local client using `KeychainProxy` in remote mode (GUI, CLI operations that touch private keys through a remote keychain). No malicious peer, network attacker, or elevated privilege is required — only log-file read access, which is a materially weaker requirement than keychain RPC access itself.

### Recommendation
Extend `redact_sensitive_data()`'s trigger set (or switch to an explicit field allowlist rather than substring denylist) to include `entropy`, `pk` (when it accompanies a private-key request), `ent`, and any other keychain-protocol field carrying seed/derivation material. Ideally, redact by known sensitive field name registered per-command rather than relying on fragile substring heuristics, and add a regression test analogous to `test_message_logging_redaction` that specifically exercises the `get_key_for_fingerprint`/`entropy` payload shape.

### Proof of Concept
1. Enable DEBUG logging for the daemon (`log_level: DEBUG` in config, a supported setting).
2. From a local client (e.g., `KeychainProxy` in remote mode, as used internally by CLI/GUI), issue a `get_key_for_fingerprint` request with `private=True` for an existing wallet fingerprint, per `chia/daemon/keychain_proxy.py:370-390`.
3. The daemon logs the received/sent websocket message content via the path documented in `.cursor/context/daemon.md:62-64`, running it through `redact_sensitive_data()` (`chia/daemon/server.py:69-79`).
4. Because the payload key is `entropy` and does not match any trigger substring, the raw entropy hex is written to the log file in cleartext.
5. Any reader of that log file computes `bytes_to_mnemonic(bytes.fromhex(entropy))` to obtain the full wallet mnemonic and derive all associated private keys.

```python
def redact_sensitive_data(obj: Any, redaction_triggers: Collection[str] = ("pass", "key", "secret", "mnemonic")) -> Any:
    """Recursively redact sensitive data from nested dictionaries."""
    if isinstance(obj, dict):
        return {
            key: "***<redacted>***"
            if any(trigger.casefold() in key.casefold() for trigger in redaction_triggers)
            else redact_sensitive_data(value, redaction_triggers)
            for key, value in obj.items()
        }
    else:
        return obj
```
