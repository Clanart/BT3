### Title
Attacker-controlled allocation amplification in `ThresholdKeys::read` enables memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to CVE-2017-9408 (a crafted input causing excessive memory consumption during deserialization in Poppler's `Object::initArray`), `ThresholdKeys::<C>::read` trusts an attacker-supplied `n` field to size an allocation before any of the corresponding bytes have been read. A few bytes of input force a multi-megabyte allocation, and the path is reachable by any unprivileged party feeding bytes to `ThresholdKeys::read`.

### Finding Description
`ThresholdKeys::read` reads three `u16` fields — `t`, `n`, `i` — directly from the reader. `n` is entirely attacker-controlled and can be up to 65535.

Immediately afterward, for `Interpolation::Constant` (tag byte `0`), it executes:

```rust
// crypto/dkg/src/lib.rs:607-612
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
``` [1](#0-0) 

`Vec::with_capacity(n)` allocates `n * size_of::<C::F>()` upfront. With `n = 65535` and a 32-byte field element, a single call allocates ~2 MiB, plus the subsequent `HashMap` of `n` verification shares read in the loop at lines 621–623. The input required to trigger this is only the curve-ID header (~40 bytes) plus `t || n || i || 0x00` (~7 bytes); the read then fails partway, but the allocation has already been committed and must be reclaimed.

There is no bound on `n` at parse time — validation via `ThresholdParams::new(t, n, i)` happens only in `ThresholdKeys::new` at line 626, *after* the allocation and the `O(n)` read loop have already run. A length/size-limit check comparable to the `TRANSACTION_SIZE_LIMIT` guard used for the commitments matrix elsewhere is absent here.

### Impact Explanation
An attacker who can submit `ThresholdKeys` bytes to a victim (e.g., a peer, coordinator-adjacent component, or any code path deserializing keys/config provided externally) can force repeated multi-megabyte allocations with a handful of input bytes per call. Repeated invocations — or many parallel sessions — exhaust available memory and deny service to the node, matching the CVE's denial-of-service-via-crafted-input impact. Since the allocation is proportional to a 16-bit field and occurs before input validation, the cost asymmetry (~50 bytes in → ~2–4 MiB allocated, plus the `O(n)` `read_G`/`HashMap` work attempted) is the vulnerability.

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization API expressly listed among the untrusted-byte entry points. Any component that deserializes `ThresholdKeys` from data influenced by an external party exposes the path. The trigger requires only setting `n` to a large value; no valid shares, signatures, or honest protocol state are needed. Impact is limited to memory exhaustion/DoS (Medium), not secret recovery or forgery.

### Recommendation
Validate `n` before allocating: check `ThresholdParams::new(t, n, i)` (or a hard upper bound on `n`) immediately after reading the header, before `Vec::with_capacity` and before the per-participant read loops. Additionally, avoid `with_capacity(n)` on unvalidated input — either push into an empty `Vec` so allocation tracks actually-read data, or read elements in bounded chunks as done for the chunked-read pattern used in `Call::read` (networks/ethereum/src/machine.rs:51-60) which caps the DoS amplification to 1 KiB per claim.

### Proof of Concept
Conceptual trigger against `ThresholdKeys::<C>::read`:

```rust
let mut bytes = vec![];
// Curve ID length + ID (must match C::ID to pass the header check)
bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(1u16.to_le_bytes());      // t = 1
bytes.extend(65535u16.to_le_bytes());  // n = 65535 -> ~2 MiB Vec::with_capacity + 65535-iteration loops
bytes.extend(1u16.to_le_bytes());      // i = 1
bytes.push(0);                         // Interpolation::Constant
// No further bytes needed: with_capacity already allocated ~2 MiB before read_F fails
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
// Loop the call in concurrent sessions to exhaust memory.
```

The failure to fully deserialize does not matter: the oversized allocation (and the `n`-iteration `HashMap`/`read_G` loop) is performed before the error is returned, which is precisely the crafted-file memory-consumption primitive from the referenced CVE.
