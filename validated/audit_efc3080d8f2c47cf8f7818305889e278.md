### Title
`collateral-remove` skips all health checks when a position's only debt lies in a disabled asset - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`collateral-remove` gates its entire health-check flow on `has-debt`, computed from `get-position`, which is documented as returning "enabled only" rows. `get-notional-evaluation` then also folds only over the enabled asset list. If a user's real debt sits in an asset the DAO has since disabled, `has-debt` reads `false`, the function takes the "NO DEBT: Skip price resolution entirely" branch, and collateral is removed with zero solvency check even though the account still carries real, uncollateralized debt.

### Finding Description
`get-position` is called with `mask = (get-enabled-bitmap)` and is annotated `;; enabled only` [1](#0-0) . `collateral-remove` uses this filtered position to derive `has-debt`: [2](#0-1) 

If `has-debt` is `false`, the function jumps straight to the vault call with no price resolution, no `get-notional-evaluation`, and no `is-healthy`/`is-healthy-with-mask` gate whatsoever: [3](#0-2) 

Separately, even in the has-debt branch, `get-notional-evaluation` folds strictly over `assets`, which is built from `get-assets(position-mask)` — itself intersected with the currently enabled bitmap via `user-safe-mask mask-user mask-enabled` — so any collateral or debt row whose asset id is not in that enabled list contributes `u0` to either total [4](#0-3) [5](#0-4) .

Chain of events:
1. User borrows an asset while it is enabled (correct configuration at that time).
2. DAO later disables that asset (a normal, intended lifecycle action, not a compromise).
3. User calls `collateral-remove` on a different, still-enabled collateral asset. `get-position` returns a `debt` list with zero enabled-debt rows, so `has-debt` is `false`.
4. The "NO DEBT" branch executes: `contract-call? .v0-market-vault collateral-remove` runs directly, with no computation of `collateral-value`, `debt-value`, or any `is-healthy` check at all [6](#0-5) .
5. The user extracts collateral while their real (disabled-asset) debt remains fully unbacked.

No later gate recovers this: the branch selection at line 1118 is the only bound, and once `has-debt` is `false` there is no subsequent price check, round-up, or slippage bound to catch the discrepancy.

### Impact Explanation
Direction: collateral is effectively valued at its full removable amount while real outstanding debt is treated as zero — debt is undervalued (to zero) rather than the required "valued high" bound. The withdrawing user profits directly by extracting collateral that should have been locked against their disabled-asset debt, leaving that debt unbacked. This is direct theft of user/protocol funds (the pool backing the disabled-asset debt becomes insolvent for that position), matching Critical - direct theft of funds at rest.

### Likelihood Explanation
Requires only: (1) the attacker borrows an asset while it is enabled, (2) the DAO disables that asset at some later point (an ordinary, expected governance action, not a bug or compromise), (3) the attacker calls the public `collateral-remove` on any other enabled collateral they hold. All three steps are reachable by an unprivileged principal without any oracle manipulation, flashloan, or DAO compromise. Repeatable for every position with debt exclusively in a disabled asset.

### Recommendation
Compute `has-debt` (and the entire evaluation feeding health checks) from the full, unfiltered position (`get-full-position`) rather than the enabled-only `get-position`, so that debt in disabled assets is always counted toward `debt-total` in `get-notional-evaluation` and never allows the health-check branch to be skipped.

### Proof of Concept
Clarinet/vitest simnet plan on a local fork:
1. Enable asset `A` (debt-eligible) and asset `B` (collateral) via DAO/admin setup.
2. Have `attacker` supply `B` as collateral and borrow `A` (creating a debt row for `A`).
3. As DAO, disable asset `A` (remove it from `get-enabled-bitmap`).
4. Call `get-position(attacker)` and confirm the returned `debt` list is empty (enabled-only filtering) while `get-full-position(attacker)` still shows the `A` debt row with nonzero `scaled`.
5. Call `collateral-remove` for asset `B` with a large `amount`, `receiver = none`, `price-feeds = none`.
6. Assert the call succeeds without reverting (`ERR-UNHEALTHY`/`ERR-INSUFFICIENT-COLLATERAL` never raised) and that `B` collateral is transferred to the attacker.
7. Confirm via `get-full-position`/`get-notional-evaluation` (constructed manually with the full position and full asset list) that the account is left with outstanding debt in `A` and no collateral in `B`, i.e., an unbacked position — demonstrating the health-check bypass.
