## Title
Desktop silently repoints a repository's Git remote based on unauthenticated-trust GitHub API data, redirecting future pushes without user confirmation - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The in3-server report's core theme is that a security-relevant parameter (`minBlockHeight`) is derived from an external/untrusted input and applied without validation or user confirmation, silently weakening a security guarantee (which blocks are safe to sign). The closest analog in GitHub Desktop is `updateRemoteUrl()`, which takes the `clone_url` field of a `GitHubRepository` object returned by the GitHub API — data controlled by whoever owns/administers that GitHub repository, not by the local user — and uses it to silently overwrite the local `origin` remote URL with `git remote set-url`, with no user prompt, warning, or opt-out.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` in `app/src/lib/stores/app-store.ts` runs periodically/on repository refresh. It resolves an `owner`/`name` pair from the current remote URL via `matchGitHubRepository()`, then calls `api.fetchRepository(owner, name)` to get a fresh `IAPIRepository` object [1](#0-0) . If the repository already has a `gitHubRepository` association, it immediately calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` [2](#0-1) .

Inside `updateRemoteUrl`, the only checks performed are: (1) the URL protocol (http/https/ssh) hasn't changed, and (2) the current remote still matches the *previously cached* `gitHubRepository.cloneURL`. If both hold and the new `apiRepo.clone_url` differs from the current remote, Desktop calls `gitStore.setRemoteURL(...)`, which runs `git remote set-url origin <new-url>` — with no dialog, toast, or any user-facing confirmation [3](#0-2) . This ultimately shells out via `setRemoteURL` in `app/src/lib/git/remote.ts` [4](#0-3) .

This is a documented, intentional feature ("Update the remote url when a repository's name changes on GitHub" — changelog #8590) [5](#0-4) , analogous to the in3-server maintainers' decision to keep `minBlockHeight` flexible with only soft (log) warnings instead of hard validation. The invariant broken here is: *the destination of a user's future `git push`/`git fetch` should not change without explicit user awareness or consent.* Just as `minBlockHeight` can silently drop to an unsafe value because it is sourced from unchecked user/config input, the local Git remote — a security-relevant trust boundary — can silently change because it is sourced from a mutable, attacker-influenceable API field (`clone_url`) that is only compared structurally (owner/name/hostname), never re-verified against the user's original intent or an immutable repository identifier.

### Impact Explanation
Any GitHub account owner who renames or transfers a repository that a Desktop user has cloned can cause Desktop to automatically retarget that user's `origin` remote to a different repository name/owner on the next background refresh — with zero user interaction. Because the check only compares parsed `hostname/owner/name`, not a stable repository ID, this reacts purely to attacker-controlled repository metadata. Once retargeted, subsequent `git push` operations from the user silently upload commits/branches to the new location; if the attacker has since granted (or later grants) the victim account write access to a similarly-named replacement repository, or if the victim doesn't notice the switch, the user's work — potentially containing sensitive code, credentials in commits, or private branches — is exfiltrated to a destination the user did not knowingly choose. This matches the "silent corruption of what the user commits or pushes" impact class explicitly called out as valid.

### Likelihood Explanation
The path requires only that the victim already have the (public or private, accessible) attacker-owned repository added as a remote and open in Desktop, and that the attacker performs a repository rename/transfer — both are ordinary, unprivileged GitHub actions available to any repository owner/admin, requiring no compromise of the victim's machine, credentials, or account. The refresh path (`repositoryWithRefreshedGitHubRepository`) runs automatically as part of normal repository background refresh, so no unusual user action is needed to trigger the check-and-rewrite.

### Recommendation
Do not auto-rewrite a Git remote based solely on `IAPIRepository.clone_url` comparison. Before calling `setRemoteURL`, prompt the user with an explicit confirmation dialog showing the old and new remote URLs, and/or gate the auto-update behind a stable, non-spoofable repository identifier (e.g., the GitHub repository's numeric `id`) fetched and compared out-of-band from the mutable name/owner fields, mirroring the in3-server resolution of moving safety-relevant values into an authoritative registry rather than trusting ad hoc, attacker-influenceable fields.

### Proof of Concept
1. Attacker creates/owns a public GitHub repository `attacker/foo` and gets a victim to clone it in GitHub Desktop (origin = `https://github.com/attacker/foo`).
2. Desktop links the local repo to a `GitHubRepository` record with `cloneURL = https://github.com/attacker/foo` (unchanged since clone).
3. Attacker renames the repository on GitHub to `attacker-2/bar` (or transfers it to another account they control), causing the GitHub API's `clone_url` for the same repo ID to change.
4. On Desktop's next background repository refresh, `repositoryWithRefreshedGitHubRepository` fetches the updated `IAPIRepository` and calls `updateRemoteUrl`; because `remoteUrlUnchanged` is true (user never manually edited origin) and `!urlsMatch` is true (new clone_url differs), `git remote set-url origin https://github.com/attacker-2/bar` executes silently, with no dialog shown, as reproduced by the existing test `"updates the repository's remote url when the github url changes"` [6](#0-5) .
5. The victim's next `git push` now targets `attacker-2/bar` without any notification.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}

  it("updates the repository's remote url when the github url changes", async t => {
    const { gitHubRepository, gitStore } = await createRepository(
      t,
      apiRepository
    )
    assert(gitStore.currentRemote !== null)

    const originalUrl = gitStore.currentRemote.url
    const updatedUrl = 'https://github.com/my-user/my-updated-repo'
    const updatedApiRepository = { ...apiRepository, clone_url: updatedUrl }
    await updateRemoteUrl(gitStore, gitHubRepository, updatedApiRepository)
    assert.notEqual(originalUrl, updatedUrl)
    assert.equal(gitStore.currentRemote.url, updatedUrl)
  })
