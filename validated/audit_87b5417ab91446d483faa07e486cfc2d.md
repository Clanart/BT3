## Analog Found

### Title
Gasless Approve/Swap Protocol Forces Users to Grant Unlimited (MaxUint256) Token Allowance to `GaslessSwapRouter`, Creating a Persistent Pull-Based Drain Surface - ([File: kaiax/gasless/impl/getter.go])

### Summary
The KIP-247 gasless transaction protocol requires every `GaslessApproveTx` to set the token allowance for the `GaslessSwapRouter` to exactly `MaxUint256`, rather than an amount scoped to the intended swap. This reproduces the exact "Plugin Approval vs Push and Call" risk pattern from the referenced audit: an unlimited, standing allowance is granted to a contract that later pulls funds via `transferFrom`-style access, instead of a bounded, single-purpose transfer. Once granted, the allowance remains valid on-chain indefinitely and is not limited to the paired `SwapTx`'s `amountIn`.

### Finding Description
`isApproveTx` enforces condition A4 that the approved amount must equal `abi.MaxUint256`: [1](#0-0) 

This means a gasless user's `ApproveTx` is only considered valid protocol input if it grants the `GaslessSwapRouter` unlimited spending rights over the user's ERC-20 balance — never a bounded approval tied to the specific `amountIn` of the accompanying swap.

The safety of the design then relies entirely on `checkBalanceForSwap`, which is a **mempool admission check**, not a consensus rule: [2](#0-1) 

These allowance/balance checks (`tokenContract.Allowance(...)`, `tokenContract.BalanceOf(...)`) only gate whether the txpool promotes/bundles the transaction; the actual token movement is performed by the `GaslessSwapRouter` contract's own EVM bytecode when `swapForGas` executes (confirmed by the deployed contract having a `SwapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` entry point that pulls tokens using the standing allowance): [3](#0-2) 

Because the allowance is `MaxUint256` and persists after the swap completes (ERC-20 `approve`/`transferFrom` semantics never auto-revoke non-max allowances, and Kaia's protocol mandates max allowance in the first place, see `IERC20`/`ERC20.transferFrom`): [4](#0-3) 

every gasless user who ever completes one approve+swap pair leaves a permanent unlimited allowance in place for the `GaslessSwapRouter` address. The router contract is a mutable system component identified through the KIP-149 `Registry` (as exercised in tests via `registry.Register(..., GaslessSwapRouterName, gsrAddr, targetBlockNum)`): [5](#0-4) 

If that registered router address is ever changed to a buggy or malicious implementation (compromised owner key, logic error, or governance-driven upgrade), any function it exposes that calls `transferFrom` can immediately drain the *entire* token balance of every user who has ever executed a `GaslessApproveTx`, not just the amount involved in their last swap. This is precisely the "push-and-call vs. unlimited pull allowance" risk described in the referenced audit: a wrongly-coded (or later replaced) contract with standing approval has access to funds far beyond what any single legitimate operation requires.

### Impact Explanation
Any account that has ever sent a `GaslessApproveTx` retains a `MaxUint256` allowance on the `GaslessSwapRouter` address indefinitely. A compromise or malicious redeployment of that router (reachable via the KIP-149 registry update mechanism that governs system contract addresses) turns this into a mechanism to drain the full ERC-20 balances of all past gasless users in a single transaction each — not bounded to the originally intended swap amount. This is a protocol-level design choice (enforced as a hard validity condition, A4) rather than an implementation bug in a single contract, so it affects every deployment of the gasless feature.

### Likelihood Explanation
Every legitimate use of the gasless-swap feature by an ordinary, unprivileged user necessarily creates this unlimited standing allowance — the condition is mandatory (`args.Amount.Cmp(abi.MaxUint256) == 0`), so the exposure accumulates passively over time with normal usage. The only additional trigger needed for exploitation is a change/compromise of the router contract referenced by the registry, which is a realistic single point of failure given it is the sole gatekeeper trusted with unlimited pull rights over every gasless user's tokens.

### Recommendation
Change the gasless protocol so `GaslessApproveTx` amounts are scoped to the exact `amountIn` required by the paired `GaslessSwapTx` (matching condition SP2's existing `approveArgs.Amount >= swapArgs.AmountIn` check) rather than requiring `MaxUint256`, and/or have the router explicitly revoke/reset the allowance to zero after consuming it in `swapForGas`, consistent with the audit's recommendation to prefer bounded, single-purpose token transfers over persistent unlimited allowances.

### Proof of Concept
1. User A sends `GaslessApproveTx` approving `GaslessSwapRouter` for `MaxUint256` of TokenX, satisfying the mandatory A4 rule in `isApproveTx` (`kaiax/gasless/impl/getter.go:79-86`).
2. User A's paired `GaslessSwapTx` executes successfully, swapping only a small `amountIn` of TokenX for gas repayment.
3. TokenX's on-chain `allowance(A, GaslessSwapRouter)` remains `MaxUint256` afterward (ERC20 semantics; `ERC20.sol:96-100` only decrements allowance by the amount actually transferred).
4. Later, governance/owner replaces the address registered under `GaslessSwapRouterName` in the `Registry` with a new (compromised or buggy) contract, per the same registration mechanism exercised in `tests/gasless_test.go:107-121`.
5. The new contract, still authorized by User A's un-revoked `MaxUint256` allowance, calls `transferFrom(A, attacker, balanceOf(A))` on TokenX, draining A's entire balance — far exceeding the value of the original swap.

// IsApproveTx checks following conditions:
// A1. tx.to is a whitelisted ERC20 token.
// A2. tx.data is `approve(spender, amount)`.
// A3. spender is a whitelisted SwapRouter contract.
// A4. amount is MaxUint.
func (g *GaslessModule) IsApproveTx(tx *types.Transaction) bool {
	args, ok := decodeApproveTx(tx, g.signer)
	return ok && g.isApproveTx(args)
}

func (g *GaslessModule) isApproveTx(args *ApproveArgs) bool {
	g.gaslessInfoMu.RLock()
	defer g.gaslessInfoMu.RUnlock()

	return g.allowedTokens[args.Token] && // A1
		g.swapRouter == args.Spender && // A3
		args.Amount.Cmp(abi.MaxUint256) == 0 // A4
}
