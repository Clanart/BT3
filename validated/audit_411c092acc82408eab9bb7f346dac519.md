## Title
`resolveWithin()` uses a bare `String.prototype.startsWith` prefix check instead of a path-boundary check, allowing traversal into sibling directories that share a name prefix with the repository root - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` are the app's single sanctioned guard against path traversal and symlink escapes when resolving attacker-influenced, repository-relative paths (e.g. conflicted-file paths fed to Copilot conflict resolution, and `filepath` from `x-github-client://openrepo` deep links). The containment check is implemented as a plain string prefix comparison rather than a path-segment-aware comparison, so it silently accepts paths that lie *outside* the intended root whenever the resolved path happens to start with the same characters as the root path.

### Finding Description
The core check is: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` treats `realRoot` as a literal character prefix, not a path segment boundary. If `realRoot` is `/Users/victim/Projects/app` and a resolved candidate is `/Users/victim/Projects/app-secrets/config.json`, the comparison `'/Users/victim/Projects/app-secrets/config.json'.startsWith('/Users/victim/Projects/app')` evaluates to `true`, even though `app-secrets` is a **sibling** directory, not a descendant of `app`. The function returns the escaped path as "safe" instead of `null`.

This is structurally the same bug class as the seed report: an implicit, unvalidated assumption (that "root" and "resolved" being compared via prefix equals "resolved is inside root") is baked into a security-relevant computation, and nothing downstream re-validates it. Just as the Tokemak code assumed `LMPVault` decimals were always 18 without checking, `resolveWithin` assumes `.startsWith()` prefix equivalence implies directory containment without checking for a following path separator.

The existing unit tests only cover the "traverse out via `..`" and "traverse out via symlink" cases, where the resolved path is genuinely shorter/unrelated to the root and therefore does not share the vulnerable prefix collision: [2](#0-1) 

None of the tests exercise the sibling-directory-with-shared-prefix scenario, so the bug is unguarded by the existing test suite.

The primary consumer that processes untrusted, repository-derived paths through this guard is the Copilot merge-conflict context builder: [3](#0-2) 

```
// Guard against path traversal and symlink escapes (cross-platform)
let absolutePath: string | null
try {
  absolutePath = await resolveWithin(workingDirectory, file.path)
} catch { ... }
if (absolutePath === null) {
  return { path: file.path, hunks: [], skippedReason: 'File path is outside the repository' }
}
```

`file.path` originates from conflicted file entries surfaced by `getStatus`/`status-parser.ts`, i.e. paths taken from a cloned/fetched, attacker-influenced repository's working tree/merge state. The code explicitly documents that `resolveWithin` is relied upon as the sole cross-platform defense against "path traversal and symlink escapes" here — meaning any weakness in `resolveWithin`'s containment logic directly undermines this guard.

### Impact Explanation
If an attacker can arrange a conflicted-file path (or, via `resolveWithin`, a `filepath` value from an `x-github-client://openrepo` deep link handled in `dispatcher.ts`/`app-store.ts`) whose resolution lands in a sibling directory sharing the root's name as a literal prefix (a common situation on multi-project checkouts, e.g. `repo` vs `repo-old`, `repo` vs `repo2`, `project` vs `project-backup`), the function will incorrectly treat that out-of-repo path as safe. Depending on the call site, this can lead to:
- Reading arbitrary files outside the intended repository (`readFile` in `buildConflictContext`, whose content is subsequently sent to the Copilot SDK as prompt context) — an out-of-repo file read/exfiltration primitive.
- Bypassing the "outside the repository" guard entirely for any other current or future caller of `resolveWithin` that performs a write, since the containment check is the same for all three exported variants (`resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`).

This satisfies the required impact class: an unprivileged, attacker-controlled repository/link object causes file read outside the intended repository boundary via a broken security invariant, without requiring local/physical access, admin rights, or pre-existing malware.

### Likelihood Explanation
Exploitability depends on the existence of a sibling path that literally starts with the root path's characters — a naming collision that is common in real developer environments (versioned/backup/duplicate folder names) but not guaranteed. The attacker does not need to create that sibling directory (that would require prior filesystem control); rather, the attacker needs to control the *value* passed to `resolveWithin` (the `file.path`/`filepath`) such that, when joined and resolved against a legitimate root that happens to have such a sibling on the victim's disk, the resulting path escapes. Because git normally disallows literal `..` path components in tracked blobs, the most direct trigger for `copilot-conflict-context.ts` (`file.path` sourced from git status) requires either a symlinked directory inside the working tree pointing at a sibling with the same prefix, or another current/future caller of `resolveWithin` that accepts a less-restricted path (e.g. deep-link `filepath`). The `startsWith` flaw itself, however, is deterministic and unconditionally present.

### Recommendation
Replace the prefix check with a path-boundary-aware comparison, e.g.:
```
return realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the platform-appropriate separator from the `options` passed into `_resolveWithin` (`Path`, `Path.posix`, or `Path.win32`), and add a regression test covering a sibling directory whose name is a prefix-superset of the root's basename (e.g. root `.../app`, candidate `.../app-secrets/file`).

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdir, rmdir, writeFile, unlink } from 'fs/promises'
import { join } from 'path'
import { tmpdir } from 'os'

// Simulate: root = <tmp>/app, sibling = <tmp>/app-secrets/secret.txt
const base = await mkdtemp(join(tmpdir(), 'poc'))
const root = join(base, 'app')
const sibling = join(base, 'app-secrets')
await mkdir(root)
await mkdir(sibling)
await writeFile(join(sibling, 'secret.txt'), 'top-secret')

// A "repository-relative" path that resolves, via join+normalize, to the sibling
const escapePath = join('..', 'app-secrets', 'secret.txt')

const result = await resolveWithin(root, escapePath)
console.log(result)
// BUG: result !== null and points to <tmp>/app-secrets/secret.txt,
// even though that file is NOT inside `root`.
```
This demonstrates that `resolveWithin` returns a non-null "safe" path for a location outside the given root whenever the root's path string is a literal prefix of the resolved path — the exact broken invariant that `buildConflictContext` in `app/src/lib/copilot-conflict-context.ts` relies on to prevent reading files outside the repository.
