## Title
Copilot merge-conflict reassembly silently splices attacker-controlled content and leaves stray conflict-marker text into the committed file - (File: app/src/lib/copilot-conflict-resolution.ts)

## Summary
The reported Saddle bug is a mismatch between an *assumed* invariant (amount sent == amount received) and reality, because an untrusted intermediary (a fee-charging token contract) can silently alter the value in transit, and the code never re-validates the post-transfer state before using it in further calculations. The Desktop analog is the same class of bug in the Copilot conflict-resolution pipeline: `extractConflictHunks` (used to build the hunk count sent to the model / used for validation) and `reassembleResolvedFile` (used to splice the model's resolutions back into the file that gets written to disk and committed) each independently re-parse the same untrusted, attacker-influenced raw file content with a naive first-match marker scan, and the code never verifies that the two parses agree on where a hunk boundary actually is. An attacker who controls a branch/PR/fetched ref that is merged locally can shape a "theirs" (or "ours") region so that its *content* — not an actual git conflict marker — matches the marker regexes (`^<{7}(?:\s|$)`, `^={7}$`, `^>{7}(?:\s|$)`). This desyncs what the model reviewed from what gets written to disk.

## Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) and `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) both scan the same raw on-disk file content line-by-line for the sequences `<<<<<<<`, `=======`, `>>>>>>>`, using the same regexes, but they are two entirely separate passes with no shared/authoritative parse tree: [1](#0-0) [2](#0-1) 

Both parsers stop at the *first* line that matches the theirs-marker/separator regex after an opening `<<<<<<<`. Neither parser validates that the matched marker is the "real" merge-generated marker versus a line of ordinary file content that happens to match the same 7-character pattern (a pattern with no game-theoretic reason to be rare — it's exactly the string a source file discussing/testing conflict markers, a diff/patch tool, or attacker-crafted payload can trivially contain).

Because the attacker fully controls the "theirs" content of the merge (a branch, PR, or fetched ref the user merges/rebases against — the exact "attacker controls a cloned/fetched repository" primitive called out as valid impact), they can embed a fake `>>>>>>> ...` (or `=======`) line inside what should be their own hunk content. This causes:
1. `extractConflictHunks` to truncate the hunk's `theirsContent` at the fake marker, and to stop counting hunks there — the *rest* of the theirs region (including the real closing marker and any trailing payload) is never included in any `IConflictHunk`, so it is never shown to the model and never scanned by `getHunkSkipReason`.
2. `reassembleResolvedFile`, parsing the same content independently, finds the same fake marker as the "closing" boundary, splices the model's `resolvedContent` there, and then resumes its main loop treating everything after — including the real leftover marker line and attacker payload lines — as ordinary non-conflict content that is copied through **verbatim** into the final file: [3](#0-2) 

The only sanity check applied to hunk content is on the model's own `resolvedContent` (rejecting embedded markers) and on hunk *counts* between context and response: [4](#0-3) [5](#0-4) 

Neither of these guards inspects the *leftover raw lines* that `reassembleResolvedFile` copies through untouched — they only ever operate on hunks that were actually detected by `extractConflictHunks`, and both `validateResolutionPaths` and the count check pass because `extractConflictHunks` and `reassembleResolvedFile` agree with each other on the (wrong) truncated boundary, even though that boundary is not the real end of the conflict. There is no verification that the reassembled file no longer contains conflict-marker syntax, and no re-diff/whole-file re-scan against the number of `<<<<<<<`/`>>>>>>>` occurrences in the final output.

## Impact Explanation
An attacker who supplies a branch, pull request, or remote ref that the victim merges/rebases locally can smuggle unreviewed content into the file that Desktop's Copilot-assisted conflict resolution writes to disk and that the user then commits/pushes, without that content ever being shown to the Copilot model or flagged by any validation step. This is a silent corruption of what the user commits: the resulting file can contain the attacker's un-vetted lines (potentially malicious code, secrets exfiltration snippets, or build-script tampering) spliced in as if it were "resolved" content, plus a leftover literal git conflict marker line that most users will not notice once the Desktop UI reports the conflict as auto-resolved. Because the feature's entire purpose is to let the user skip manual conflict review, this defeats the safety net a manual `git mergetool`/diff review would normally provide.

## Likelihood Explanation
Exploitation requires only that the victim run Desktop's Copilot conflict-resolution feature on a merge/rebase against a branch or PR the attacker controls (a normal, unprivileged workflow — e.g. merging a colleague's or contributor's branch). No local access, no leaked credentials, and no unusual user action beyond the feature's intended use ("resolve with Copilot") are required. The trigger condition (a line matching a 7-character marker sequence inside legitimate-looking content) is easy for an attacker to craft deliberately in a file they fully control.

## Recommendation
Replace the two independent, first-match-wins scans with a single authoritative parser that tags each marker occurrence with a nesting-aware or line-index-based identity, and have both `extractConflictHunks` and `reassembleResolvedFile` consume the same parsed hunk-boundary list (e.g. by index into the original array) rather than re-deriving boundaries by scanning raw text twice. Additionally, after reassembly, re-scan the final output for any residual `<<<<<<<`/`=======`/`>>>>>>>`-shaped lines and reject/flag the resolution rather than silently writing it, and assert that the total line count consumed by hunks (context + hunk regions) accounts for the entire original file so no attacker-controlled span can be dropped from model review yet still end up in the committed file.

## Proof of Concept
Given a file that, after `git merge`, contains a standard two-way conflict where the attacker-controlled "theirs" side embeds a line matching the closing-marker pattern:
```
before
<<<<<<< HEAD
victim's original line
=======
attacker line 1
>>>>>>> not-a-real-marker-but-matches-regex
attacker payload line (never reviewed by Copilot)
>>>>>>> feature/attacker-branch
after
```
- `extractConflictHunks` produces one hunk with `theirsContent = "attacker line 1"` (stopping at the fake `>>>>>>> not-a-real-marker...` line) — the model only ever sees `"attacker line 1"`.
- `reassembleResolvedFile`, splicing the model's resolution at the same fake boundary, copies `attacker payload line (never reviewed by Copilot)` and the real `>>>>>>> feature/attacker-branch` marker line straight through into the final committed file, unseen by the model and unvalidated by `validateResolutionPaths`/the marker-content check on `resolvedContent`.
- The user is shown a "resolved" conflict and commits a file containing attacker-injected content plus a stray leftover conflict marker.

This mechanism is directly supported by the code paths cited above; I was not able to trace further into `app-store.ts`'s write/commit call site within the remaining budget, so the exact UI wording shown to the user at commit time is not confirmed and should be verified in a Devin session with full file access.
