### Title
ProtoJSON duplicate-key validation is skipped for `null`-valued oneof/singular fields, allowing a client to bypass "already set" checks - ([File: src/google/protobuf/json/internal/parser.cc])

### Summary
In protobuf's ProtoJSON parser, when a JSON field value is `null`, the code takes an early "no-op" branch **before** calling `Traits::RecordAsSeen`, meaning the duplicate-field/oneof-conflict tracking is bypassed entirely for that occurrence. The code explicitly acknowledges this gap in a comment referencing an open bug (`b/519557203`), stating that spec behavior requires duplicate-key checking even for `null` values, but "this implementation currently does not" do it.

### Finding Description
The frourio advisory's failed invariant was: nested validators were not correctly invoked for specific request shapes, so some attacker-controlled inputs bypassed validation entirely (false negative validation). The transferable Protobuf analog is a structurally similar validation-bypass: the invariant "a field may only be set once (or once per oneof)" is supposed to be enforced uniformly by `ParseField`, but a specific input shape — a `null` JSON value — skips the enforcement path.

Looking at `ParseField` in `src/google/protobuf/json/internal/parser.cc`: [1](#0-0) 

The flow is:
1. If the JSON value is `null` and the field is not a `google.protobuf.Value`/`NullValue` special case, the parser returns early via `lex.Expect("null")` — **without ever calling `Traits::RecordAsSeen`**.
2. Only for non-null values does `RecordAsSeen` run and produce a `SeenState` (`kFirstSeen`, `kOneofAlreadySeen`, `kFieldAlreadySeen`) that is used to reject duplicate/oneof-conflicting keys.

The comment at lines 1244-1248 explicitly documents that this is a known conformance gap, not intentional design:
> "Note that spec behavior is that we should do duplicate key checking in the case of a null value, but this implementation currently does not (b/519557203)."

`RecordAsSeen` itself (in `ParseProto2Descriptor`/`ParseProto3Type` traits) is the sole place tracking `parsed_oneofs_indices_`/`parsed_fields_` sets used to detect duplicates: [2](#0-1) [3](#0-2) 

Because the `null` branch never reaches this bookkeeping, a JSON payload can present the same field key twice — once with a real value and once as `null` (or vice versa), or two different oneof members where one occurrence is `null` — and the second occurrence will not be flagged as `kFieldAlreadySeen`/`kOneofAlreadySeen`, even though ProtoJSON's default (non-legacy) mode is supposed to reject any duplicate key per the enforcement at: [4](#0-3) 

### Impact Explanation
This is a validation-integrity bug, analogous to frourio's "validator doesn't fire for specific input shapes." The consuming-application exposure assumption: any service that parses attacker-controlled ProtoJSON via `google::protobuf::json::MessageToJsonString`/`JsonStringToMessage` (or the internal `ParseField`/`JsonLexer` machinery) and relies on ProtoJSON's documented strict "no duplicate keys" semantics (default mode, not `allow_legacy_nonconformant_behavior`) could silently accept a payload it should have rejected. Concretely, a duplicate/conflicting key that should trigger an `Invalid` parse error instead succeeds, potentially letting a later `null` occurrence silently overwrite/no-op a field that a stricter validator would have rejected as malformed input, or letting two oneof members effectively co-exist across the last-write-wins path without the intended conflict error. This does not itself grant memory corruption or code execution — it is a correctness/validation gap (comparable in class to the "false negative" impact category of the frourio advisory), not a resource-exhaustion or memory-safety issue.

### Likelihood Explanation
High likelihood of being triggerable: any bounded ProtoJSON payload with a repeated key where one instance's value is the literal `null` reaches this code path deterministically; it requires no special schema, no privileged access, and works over the public `JsonStringToMessage` parsing API. The bug is already self-acknowledged and tracked by Google (`b/519557203`), which corroborates that it is real and reachable, not a theoretical construction.

### Recommendation
Move `Traits::RecordAsSeen(*field, msg)` (and the associated duplicate/oneof-conflict check) so it executes **before** the early-return `null` handling, so that a `null` occurrence of a field/oneof member is recorded and duplicate/conflict detection applies uniformly regardless of whether the value is `null` or a real value. This matches the "spec behavior" the existing comment already calls out as the correct target behavior.

### Proof of Concept
Given a proto3 message with a oneof `{ int32 a = 1; int32 b = 2; }`, and default (non-legacy) ProtoJSON parsing:
```json
{"a": 5, "b": null}
```
- Parsing `"a": 5"` calls `RecordAsSeen` → `kFirstSeen`, oneof index recorded.
- Parsing `"b": null` hits the `lex.Peek(JsonLexer::kNull)` branch in `ParseField` (`parser.cc:1249-1254`) and returns before ever calling `RecordAsSeen`, so the oneof-conflict check at lines 1261-1267 never executes for `"b"`.
- Result: the parser does not raise the `'b' has already been set ... as part of a oneof` error that spec/default-mode behavior requires, silently diverging from the intended "reject duplicate/oneof-conflicting keys" invariant.

This reasoning is based on static code/comment inspection only (no test harness was executed in this session); the actual runtime pass/fail behavior of this exact payload against `google::protobuf::json::JsonStringToMessage` should be confirmed by running it, which I did not do in this pass — the finding rests on the explicit code comment plus the control-flow ordering shown above.

  static SeenState RecordAsSeen(Field f, Msg& msg) {
    if (f->real_containing_oneof() != nullptr) {
      int oneof_index = f->real_containing_oneof()->index();
      bool oneof_inserted =
          msg.parsed_oneofs_indices_.insert(oneof_index).second;
      if (!oneof_inserted) {
        // Oneof takes precedent over Field in the case of "this is in a oneof
        // and the field is set"
        return SeenState::kOneofAlreadySeen;
      }
    }

    bool field_inserted = msg.parsed_fields_.insert(f->number()).second;
    if (!field_inserted) {
      return SeenState::kFieldAlreadySeen;
    }

    return SeenState::kFirstSeen;
  }
