### Title
Unauthenticated `dispatch()` allows anyone to drain native ETH held by the shared `CallDispatcher` - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.sol` is the shared execution utility used by every cross-chain messaging app in this repo (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`, etc.) to run destination-side calldata delivered via ISMP. It has a `receive()` function to accept native ETH [1](#0-0)  but its only spending function, `dispatch()`, has **no access control whatsoever** — it is `external` with no `onlyHost`/`restrict` modifier, so any address can call it directly and force it to send out the contract's own ETH balance to an arbitrary target. [2](#0-1) 

### Finding Description
`dispatch()` decodes an attacker-supplied `Call[]` and, for each entry, executes `to.call{value: call.value}(call.data)` using the CallDispatcher's *own* balance — not funds scoped to the caller or a specific request: [2](#0-1) 

The only checks are that `to` has code (`extcodesize(to) != 0`) and that the call succeeds; there is no verification that the caller is the `IsmpHost`, a registered `HyperApp`, or that `call.value` is bounded to value the caller actually contributed. This is a materially different trust model from every other value-holding contract in this codebase — `EvmHost.withdraw()` is `restrict(_hostParams.hostManager)` [3](#0-2) , and `HostManager.onAccept` is `restrict(_params.host)` [4](#0-3)  — but `CallDispatcher.dispatch()` is completely open.

By design, `CallDispatcher` is expected to transiently hold value/tokens mid-execution: the SDK docs explicitly warn that "the dispatcher contract holds tokens temporarily during execution" [5](#0-4) , and it also accepts stray/misdirected ETH via its bare `receive()`. Every `onAccept`/timeout handler across the fungible-token apps invokes `ICallDispatcher(_dispatcher).dispatch(message.data)` on this same shared instance [6](#0-5) [7](#0-6) . Any ETH that ends up sitting in the CallDispatcher between transactions — from a reverted/partial multi-call sequence, a mis-sent transfer to the `receive()` fallback, or leftover `call.value` from a prior batch — is not scoped to anyone. Because `dispatch()` has no caller restriction, any unprivileged address can immediately call it with a `Call[]` whose `to` is their own contract and whose `value` equals `address(CallDispatcher).balance`, sweeping out that balance before the legitimate flow (host → app → dispatcher) ever gets to use it.

This is the direct structural analog of the `MPROVesting` bug: a contract designed to receive/hold ETH (`receive() external payable {}`) with no protected withdrawal path — except here the "no protection" cuts the other way: the spend function exists but is unauthenticated, so instead of ETH being *permanently stuck*, it is *permanently exposed to theft* by any calling address.

### Impact Explanation
This meets the bounty's fund-loss / unauthorized-execution bar: any ETH balance the shared `CallDispatcher` accumulates (through its explicit `receive()`, or transiently during multi-call execution before a batch completes) can be executed against and drained by an unprivileged, unrelated third party via a direct call to `dispatch()`, bypassing the `IsmpHost` → `HyperApp.onAccept` authorization chain entirely. Because the same `CallDispatcher` address is shared by multiple apps (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`) and deployments, this is bridge-adjacent shared infrastructure, not an isolated per-user wallet.

### Likelihood Explanation
`dispatch()` is a plain public entrypoint requiring no proof, no relayer collusion, no admin/governance role, and no front-running — just a direct call once the contract holds any ETH. Given the contract explicitly implements `receive()` to accept ETH transfers and documentation itself acknowledges the contract "holds tokens temporarily during execution," the precondition (non-zero balance at some point) is not a hypothetical corner case but an anticipated operating state of the contract.

### Recommendation
Restrict `dispatch()` so it can only be invoked in the context intended (e.g., only by the registered `HyperApp`/`onAccept` caller, or require `msg.value == 0` and instead have callers `.call` with value pre-funded per-invocation and immediately swept, never resting in the CallDispatcher's balance). At minimum, either remove the bare `receive()` (forcing all value to arrive scoped to a specific `dispatch()` call in the same transaction) or add caller/allowlist authorization plus a sweep/withdraw function gated to the legitimate owner so no unscoped balance is ever exposed to arbitrary callers.

### Proof of Concept
1. Any actor sends ETH directly to the deployed `CallDispatcher` address (accepted unconditionally by `receive()`), or a prior `dispatch()` batch leaves residual `msg.value` in the contract (e.g., a partially executed but ultimately failed batch is retried and only part of the value is consumed by earlier calls before a later call reverts and is retried with fresh funding, or excess `value` fields sum higher than what downstream calls actually consume).
2. An attacker deploys a trivial contract `Sink` with a `receive()` function.
3. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: address(Sink), value: address(CallDispatcher).balance, data: ""})]))` directly (no ISMP proof, no host, no relayer needed).
4. `extcodesize(Sink) != 0` passes the only guard; `Sink.call{value: balance}("")` succeeds, and the entire ETH balance held by the shared `CallDispatcher` is transferred to the attacker's contract.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
```

```text
### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```
