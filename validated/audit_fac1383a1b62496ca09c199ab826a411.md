### Title
Unhandled `IndexError` from crafted CLVM atom length prefix during mempool canonical-encoding validation - ([File: chia/full_node/mempool_manager.py])

### Summary
`MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical()`/`is_atom_canonical()` on every submitted spend bundle's puzzle reveal and solution before it does any other bounds-checked parsing. These helper functions compute a variable-length atom-size prefix and advance an `offset` into the raw `bytes` buffer without first checking that enough bytes remain, then index into the buffer at that offset.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads the byte at `offset`, determines a `prefix_len` (0–5 continuation bytes) from the high bits, and then, in a loop, does: [1](#0-0) 
`offset += 1; atom_len |= clvm_buffer[offset]` for `prefix_len` iterations with no check that `offset` stays within `len(clvm_buffer)`. If the buffer is truncated right after a length-prefix byte that claims 1–5 continuation bytes, this indexing runs past the end of the buffer.

Additionally, `is_clvm_canonical()`'s main loop computes `atom_len` from `is_atom_canonical()` and does `offset += atom_len` unconditionally: [2](#0-1) 
before looping back to `b = clvm_buffer[offset]` at the top of the loop if `tokens_left != 0`. A crafted small buffer can produce a large `atom_len` (bounded only by the number of encoded prefix bits) that pushes `offset` far past `len(clvm_buffer)`, so the next iteration's `clvm_buffer[offset]` access again indexes out of bounds.

This is the same bug class as CVE-2019-17498 (bounds-check arithmetic on an attacker-controlled length/offset before a buffer read) — the difference is that Python's `bytes.__getitem__` is memory-safe, so instead of an out-of-bounds memory disclosure this manifests as an unhandled `IndexError` raised out of `is_clvm_canonical()`.

This code path is directly reachable by any unprivileged spend-bundle submitter: `validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` and `is_clvm_canonical(bytes(coin_spend.solution))` for every coin spend in a submitted `SpendBundle`, prior to any exception-safe validation: [3](#0-2) 

### Impact Explanation
An attacker who can submit a spend bundle (via RPC `push_tx`, gossip `RespondTransaction`, or offer/wallet flows that route through mempool admission) can craft a `puzzle_reveal` or `solution` blob whose bytes are otherwise a syntactically valid enough CLVM buffer to reach `is_clvm_canonical()`, but is truncated/short relative to an encoded atom length so that `is_atom_canonical()` or the `is_clvm_canonical()` loop indexes past the end of the buffer. This raises an unhandled `IndexError` inside the mempool admission code path (`validate_spend_bundle`), rather than the intended `Err.INVALID_COIN_SOLUTION` rejection path. Depending on how far up the call stack (RPC handler / message handler for `transaction` gossip) catches generic exceptions, this can abort mempool-item processing for that request/task, producing a spend-triggered transaction-processing halt for that request rather than a controlled rejection — this is a mempool admission robustness bug, not a memory-disclosure bug (Python bounds-checks indices), so the CVE's confidentiality impact does not carry over, but the availability-disruption bug class does.

### Likelihood Explanation
Likelihood is high for triggering the exception itself: constructing a `CoinSpend` with a puzzle_reveal/solution byte string that is short by design is trivial and doesn't require any signature or on-chain state — `is_clvm_canonical()` runs unconditionally on every coin spend as part of admission, before signature/cost checks. Whether this actually crashes node processing (vs. being caught by a broad `except Exception` somewhere between the RPC/gossip handler and `validate_spend_bundle`) could not be confirmed from the available index — the call chain between `full_node.py`'s transaction-handling entrypoints and `MempoolManager.validate_spend_bundle()` was not fully retrievable in this pass, so the ultimate severity (isolated per-request failure vs. broader halt) is uncertain.

### Recommendation
In `is_atom_canonical()`, validate `offset + prefix_len < len(clvm_buffer)` before entering the continuation-byte loop and raise/return a defined "not canonical"/error result instead of indexing unchecked. In `is_clvm_canonical()`, after computing `atom_len`/`offset`, check `offset <= len(clvm_buffer)` before continuing the loop and return `False` (non-canonical) rather than looping into an out-of-range index. Wrap `is_clvm_canonical()` calls in `validate_spend_bundle()` to treat any parsing exception as `Err.INVALID_COIN_SOLUTION` defensively.

### Proof of Concept
Construct a `CoinSpend` whose `solution` bytes are a single atom-length-prefix byte indicating a multi-byte length prefix (e.g. `0xC0`, signaling a 5+8 bit length prefix requiring 1 continuation byte) with no continuation byte following it — e.g. `bytes([0xC0])`. Passing this through `is_clvm_canonical(bytes([0xC0]))` reaches `is_atom_canonical(buffer, 0)`, which sets `prefix_len = 1`, then executes `offset += 1; atom_len |= clvm_buffer[offset]` with `offset == 1` against a 1-byte buffer, raising `IndexError: index out of range` instead of returning a controlled `False`/rejection. def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
```python
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
