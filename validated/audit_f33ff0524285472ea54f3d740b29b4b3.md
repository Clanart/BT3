### Title
Recursive/nested precompile calls cause double-processing of bank balance-change events, producing stateDB balance desync - (File: precompiles/common/precompile.go, precompiles/common/balance_handler.go)

### Summary
The Curve report describes an attacker abusing a *callback* mechanism (`Controller.liquidate_extended` invoking an arbitrary target/signature) to re-enter privileged accounting logic and duplicate a withdrawal. The Cosmos EVM analog is the `BalanceHandler` event-replay mechanism used by every stateful precompile (`distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`, `werc20`, `bank`, plus the debug precompile) via `Precompile.RunNativeAction`. When a precompile call recursively/nestedly triggers another precompile call (e.g. an ERC20 `_beforeTokenTransfer` hook that re-enters the EVM, or an ICS20 transfer whose underlying bank/distribution operations recursively invoke another precompile), the same Cosmos SDK bank events (`coin_spent`/`coin_received`) can be read and translated into `StateDB.AddBalance`/`SubBalance` calls more than once, because `BeforeBalanceChange`/`AfterBalanceChange` only record an event-slice offset (`prevEventsLen`) against a shared, monotonically growing `ctx.EventManager().Events()` list.

### Finding Description
`precompiles/common/precompile.go` implements `runNativeAction`, the entry point used by every stateful precompile's `Run`: [1](#0-0) 

Each call creates a `BalanceHandler` via the factory (`p.BalanceHandlerFactory.NewBalanceHandler()`), calls `BeforeBalanceChange(ctx)` to record `prevEventsLen = len(ctx.EventManager().Events())`, executes the precompile action, then calls `AfterBalanceChange(ctx, stateDB)` which iterates `events[bh.prevEventsLen:]` and converts `CoinSpent`/`CoinReceived`/precisebank fractional events into `stateDB.SubBalance`/`AddBalance` calls: [2](#0-1) 

The critical property is that `ctx.EventManager().Events()` is a single shared, append-only list for the entire transaction/cache context. If the `action(ctx)` executed for an outer precompile call itself performs an EVM call that re-enters another (or the same) precompile — e.g. a malicious ERC20 with a transfer hook, or ICS20 transfer flows that call into distribution/bank operations that in turn trigger further EVM calls — the *inner* precompile invocation captures its own `prevEventsLen`, processes (and consumes into stateDB) the events emitted during its own action, and returns. When control returns to the *outer* call, the outer `AfterBalanceChange` reads `events[outerPrevEventsLen:]`, which still includes the same bank events that were already applied to `stateDB` by the inner call. This causes those balance deltas to be re-applied to `stateDB`, i.e., the same coin_spent/coin_received event is translated into `AddBalance`/`SubBalance` twice, producing a state desync between the native bank keeper's true balance and the EVM `StateDB` balance visible to subsequent contract logic within the same transaction.

The repository's own test suite documents and reproduces this class of bug: [3](#0-2) [4](#0-3) 

The ICS20 recursive test specifically exercises a real production path: a malicious ERC20 contract overriding `_beforeTokenTransfer` to recursively re-enter the EVM while an ICS20 transfer (which internally triggers bank/distribution side effects) is in flight, and comments that "reverted distribution calls leave persistent bank events that are incorrectly aggregated." This is not merely a test-harness artifact — the vulnerable mechanism (`RunNativeAction` / `BalanceHandler`) is shared production code used by every stateful precompile shipped in `precompiles/`.

### Impact Explanation
If bank events are double-applied to `StateDB` within a single EVM transaction, an unprivileged user (via a crafted ERC20 token with reentrant hooks, or any contract that recursively triggers precompile calls, e.g., ICS20 transfer of an ERC20-backed token together with a distribution/staking side effect) can cause the EVM-visible balance of an account to diverge from the true bank-keeper balance. Because subsequent EVM opcodes/precompile calls within the same or later transactions read balances from `StateDB` (and the EVM `StateDB` is eventually what gets committed / is authoritative for balance transfers made purely at the EVM layer, e.g. native ETH-style value transfers, ERC20/`werc20` wrapped balances, or further precompile calls chained off of the inflated balance), this can allow duplication of spendable value — a Critical unauthorized "duplication of spendable user value across ... EVM balances ... precompile-mediated assets" per the impact gate. Concretely, an attacker-controlled balance in `StateDB` inflated beyond the true bank balance could subsequently be spent again via a normal EVM value transfer or via a wrapped-token withdraw path (`precompiles/werc20`) before the discrepancy is ever reconciled, effectively minting/duplicating value that is not backed by real bank coins.

### Likelihood Explanation
Reachability requires only deploying an ordinary ERC20-like contract with a reentrant hook (a fully permissionless, unprivileged action) and interacting with any stateful precompile whose native action internally performs additional EVM/precompile calls (ICS20 transfers of ERC20-registered tokens, distribution/staking flows triggered as a side effect, or explicit recursive precompile-to-precompile calls as demonstrated by the debug precompile test). The project's own test suite already implements working exploit scaffolding for this exact scenario (`ERC20RecursiveReverting`/`ERC20RecursiveNonReverting` contracts + ICS20 transfer), indicating the trigger path is realistic and already partially instrumented by the maintainers, which raises confidence that this is a genuine, reachable issue rather than a purely theoretical one. However, I could not fully trace whether other layered defenses (e.g., a final journal-based revert/commit reconciliation in `x/vm/statedb/statedb.go`'s `AddPrecompileFn`/`CommitWithCacheCtx` path) fully neutralize the double-application before the transaction is finally persisted — the index does not give complete visibility into `x/vm/statedb/statedb.go`'s handling of nested precompile snapshots, so it's possible the outer snapshot/commit logic silently corrects some of this drift. This uncertainty should be verified with a live reproduction.

### Recommendation
Track the event-list length globally per stateDB/cache-context (not per `BalanceHandler` instance) so that once a slice of events has been consumed by an inner `AfterBalanceChange`, it cannot be re-consumed by an outer one — e.g., store the "last processed event index" on the shared `statedb.StateDB` (or cache context) rather than on the per-call `BalanceHandler`, and have every `AfterBalanceChange` advance that shared pointer atomically. Alternatively, disallow/guard nested precompile-to-precompile re-entrancy from within a single `RunNativeAction` invocation, or have the outer call's `BeforeBalanceChange` re-read `prevEventsLen` immediately before its own `AfterBalanceChange` executes, based on the position *after* any nested calls' consumption rather than before the whole call began.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
