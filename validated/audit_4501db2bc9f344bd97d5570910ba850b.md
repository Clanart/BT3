### Title
Out-of-range `Participant` index in PedPoP blame handling panics instead of erroring, crashing the node - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to the Prysm `hex.Decode` panic (missing length check on attacker-influenced input leading to an index-out-of-bounds panic), `BlameMachine::blame` / `AdditionalBlameMachine::blame` index `self.commitments[&sender]` and `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with `Participant` values supplied as part of a blame accusation, without checking that they are members of the DKG set. A `HashMap` lookup via `Index` on an absent key panics, aborting the entire process instead of returning a `PedPoPError`.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `blame_internal` (lines 575-609) computes blame by dereferencing `self.commitments[&sender]` (line 599) and passes `decryptor` to `Decryption::decrypt_with_proof`, which dereferences `self.enc_keys[&decryptor]` in `crypto/dkg/pedpop/src/encryption.rs` (line 388). Both are `HashMap` `Index` accesses that panic on missing keys. The `sender`/`recipient` arguments are attacker-chosen `Participant` indexes taken from a blame accusation; `Participant::new` only enforces non-zero, so any value `> n` (or a registered-but-different index absent from the maps) reaches these lookups. The encrypted share message itself is deserialized via `EncryptedMessage::read` / `EncryptionKeyProof::read`, both listed as untrusted-byte sinks. Notably, `AdditionalBlameMachine::new` correctly errors with `PedPoPError::MissingParticipant` for absent commitment messages (line 658), but the per-blame paths skip the equivalent membership check on `sender`/`recipient`. The crate itself acknowledges this class: the `AdditionalBlameMachine::new` docs note invalid inputs "may cause everything from inaccurate blame to panics" (line 648), yet `blame`/`blame_internal` perform no validation.

### Impact Explanation
A single malformed blame accusation naming a non-member `Participant` index causes an index-out-of-bounds panic in the processing node, identical in effect to the reported Prysm crash: a tiny (<100 byte) unprivileged input aborts the host process. Since blame accusations are relayed protocol messages (and `AdditionalBlameMachine` exists explicitly so non-participants can evaluate blame), any observer or participant can trigger it; the panic takes down the validator/coordinator process rather than returning a blame verdict.

### Likelihood Explanation
Triggering requires only sending a `blame` call with `sender` or `recipient` set to a `Participant` not present in `self.commitments`/`self.enc_keys` (e.g., index `n+1`). No valid signature, threshold position, or protocol state is needed beyond delivering the accusation, mirroring the minimal-cost single-message DoS of the original report.

### Recommendation
Replace the panicking `HashMap` indexing with checked lookups: in `blame_internal` return the accusing party (or a new `PedPoPError::InvalidParticipant`) when `self.commitments.get(&sender)` is `None`, and in `decrypt_with_proof` return `DecryptionError::InvalidProof`/an error when `self.enc_keys.get(&decryptor)` is `None`. Alternatively, bound-check `sender` and `recipient` against `1 ..= n` at the top of `BlameMachine::blame` and `AdditionalBlameMachine::blame`.

### Proof of Concept
1. Complete (or simulate) a PedPoP DKG for `n` participants to obtain a `BlameMachine<C>` (or build `AdditionalBlameMachine::new(context, n, commitment_msgs)`).
2. Deserialize any `EncryptedMessage<C, SecretShare<C::F>>` via `EncryptedMessage::read` (arbitrary bytes suffice — the pop signature check happens later).
3. Call `machine.blame(sender, recipient, msg, proof)` with `sender = Participant::new(n + 1).unwrap()` (a valid `Participant`, not in the set).
4. `blame_internal` reaches `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`) — the `HashMap` `Index` impl panics on the absent key, aborting the process. Symmetrically, `recipient = n + 1` with `proof = Some(...)` panics at `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`).

Caveat: the panic sites are verified in the source (`pedpop/src/lib.rs:599`, `pedpop/src/encryption.rs:388`), and `sender`/`recipient` are unconstrained `Participant` arguments, but the exact transport-level entry point that feeds these values (e.g., the coordinator's blame-message handler) was not fully traced, so reachability is asserted at the library API level rather than an end-to-end network path.
