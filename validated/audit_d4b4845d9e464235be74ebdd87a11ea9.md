Based on my research, I found a concrete Desktop analog: an inconsistent, hardcoded disabling of a git submodule-protocol protection during clone, while the equivalent protection is treated as an explicit, defaulted-off opt-in everywhere else in the codebase.

### Title
Clone operation unconditionally disables Git's submodule/file-protocol clone protection - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` in `app/src/lib/git/clone.ts` sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for every clone, unconditionally, regardless of the source URL or trust level [1](#0-0) . This environment variable controls Git's built-in protection (added upstream to mitigate submodule-based clone attacks, e.g. CVE-2024-32002-class issues) against symlink/embedded-repository tricks encountered while recursively cloning submodules. Elsewhere in the same codebase (`checkout.ts` / `submodule.ts`), the analogous protection — allowing `file://` protocol for submodules — is treated as a narrow, explicit, default-`false` opt-in parameter (`allowFileProtocol: boolean = false`) that call sites must deliberately set to `true` [2](#0-1) [3](#0-2) . Cloning — the very entry point through which an attacker-controlled repository first enters the app, and which uses `--recursive` to fetch all submodules automatically [4](#0-3)  — is the one operation where this protection is turned off entirely, with no per-call trust check. This is the same "protections declared in one place but not honored/consistently applied in another" pattern the external report calls out for whitelist validation.

### Finding Description
`clone()` builds its execution environment as:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
``` [1](#0-0) 

and then always runs `git clone --recursive -- <url> <path>` [5](#0-4) . There is no branch on repository origin (GitHub-hosted vs arbitrary attacker-supplied URL/deep link) that would set this flag to `true` instead — every clone, whether initiated from a "Clone repository" URL the user typed, a `x-github-client://` deep link, or a "Clone Again" action derived from `IAPIRepository.clone_url` (`app/src/ui/missing-repository.tsx` line 175, `updateRemoteUrl` line 19), runs with the protection disabled.

Compare this to the deliberate design used for the same underlying risk (submodules resolving to `file://` paths that can read/traverse the local filesystem) elsewhere: `updateSubmodulesAfterOperation` only appends `-c protocol.file.allow=always` when its caller explicitly passes `allowFileProtocol: true`, and that parameter defaults to `false` in `checkoutBranch`/`checkoutCommit` [6](#0-5) [2](#0-1) . The codebase clearly recognizes that "trust the submodule protocol" is a decision that must be made per-call-site and default-denied — except at `clone`, the highest-risk entry point, where the analogous Git-native protection is unconditionally stripped.

The other existing guard in `clone.ts`, `isClonePathSensitive`, only validates the destination directory (blocking clones into `~/.ssh`, `~/.gnupg`, etc.) [7](#0-6)  — it does nothing to stop an attacker-controlled repository from abusing submodule entries once inside the (non-sensitive) destination directory, which is exactly the class of attack `GIT_CLONE_PROTECTION_ACTIVE` was designed to block.

### Impact Explanation
An attacker who controls a repository that a GitHub Desktop user clones (via a shared URL, an "Open with GitHub Desktop" deep link, a malicious fork used as an upstream/parent, etc.) can craft `.gitmodules`/submodule entries that rely on the very filesystem/protocol tricks `GIT_CLONE_PROTECTION_ACTIVE` exists to prevent. Because the flag is forced to `'false'` for every clone, the app is exposed to that class of Git submodule clone vulnerability even though a corresponding safeguard (default-deny for file-protocol submodules) is honored everywhere else in the codebase.

### Likelihood Explanation
Likelihood is high in terms of exposure — every clone in the app takes this path (`--recursive`, protection disabled) with no conditional logic to re-enable protection for untrusted sources. The precondition is simply that the user clones an attacker-supplied or attacker-influenced repository URL, which is a normal, expected Desktop workflow (cloning a fork, a link shared in an issue/PR, etc.) rather than requiring local access, admin rights, or social engineering beyond "clone this repo."

### Recommendation
- **Short term:** Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()`, or gate it the same way `allowFileProtocol` is gated in `checkout.ts`/`submodule.ts` — default to Git's built-in protection (`true`/unset) and only disable it for explicitly trusted flows, if any legitimate flow needs it disabled at all.
- **Long term:** Consolidate all submodule/file-protocol trust decisions (clone, checkout, pull, fetch) behind a single, consistently-applied policy/helper instead of independently deciding per operation, mirroring the report's recommendation to use one approach to validation across the whole codebase.

### Proof of Concept
1. Attacker publishes a public repository containing a submodule entry crafted to exploit the class of clone-time submodule vulnerability that `GIT_CLONE_PROTECTION_ACTIVE` mitigates in stock Git.
2. Victim clones the repository through GitHub Desktop (typed URL, "Clone repository" dialog, or `x-github-client://openLocalRepo`/clone deep link).
3. `clone()` runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment [8](#0-7) , so Git's protection against the crafted submodule is not applied, unlike what would happen with stock Git's default protections or with Desktop's own `allowFileProtocol=false` default used for post-checkout submodule updates.

Note: I was not able to fully trace every call site that ultimately determines `allowFileProtocol` at runtime (e.g., whether any UI flow passes `true` for untrusted repositories) due to tool-call limits; a Devin session with full repo access would be needed to confirm there is no compensating check elsewhere in `app-store.ts` before treating this as fully confirmed.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
