### Title
`incentiveDeposit()` reward-tier double-counting correction can be bypassed via `mWomSV.startUnlock()` to repeatedly claim top-tier MGP rewards - (File: wombat/ArbWomUp3.sol)

### Summary
`incentiveDeposit()` computes the reward tier from `mWomSV.getUserTotalLocked(msg.sender)` and subtracts an "already-rewarded" correction (`calDoubledCounted`) computed from the same view, both read consistently within a single call. However, `getUserTotalLocked()` in `mWomSV.sol` excludes any amount that is in a cool-down slot, so an attacker can call `mWomSV.startUnlock()` on their whole previously-locked balance right after a deposit, which instantly zeroes out `getUserTotalLocked()` while the tokens are still economically staked. A subsequent `incentiveDeposit(_mode=2)` call then treats the attacker as a brand-new depositor with zero prior lock, letting them re-earn the highest reward-tier multiplier on funds that were already rewarded, instead of the lower multiplier the declining tier schedule intends.

### Finding Description
`incentiveDeposit()` reads the reward via `this.getRewardAmount(_amount, msg.sender, _mode == 2)` before invoking `_deposit`: [1](#0-0) 

`getRewardAmount` (mode 2 branch) computes `accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)`, walks the tier ladder, then subtracts `calDoubledCounted(_account)`, which independently recomputes the tier reward for `mWomSV.getUserTotalLocked(_account)` alone: [2](#0-1) 

Both calls read `mWomSV.getUserTotalLocked(_account)` within the same external call/transaction, so within one `incentiveDeposit` call they are self-consistent. The actual bug is that `getUserTotalLocked` itself is not a stable measure of "amount the user has already been rewarded for" because it excludes cool-down balances: [3](#0-2) 

`startUnlock()` immediately increases `amountInCoolDown` for the chosen amount without withdrawing anything or reducing the user's actual stake in MasterMagpie — the tokens remain staked/locked economically, only flagged for future withdrawal after a cooldown: [4](#0-3) 

Exploit flow:
1. Attacker calls `incentiveDeposit(_amount1, ..., _mode=2)`. `getUserTotalLocked` is 0 pre-deposit, so `calDoubledCounted` returns 0 and the attacker earns the full top-tier-inclusive reward for `_amount1`. `_deposit` mode 2 locks the converted mWOM into `mWomSV`, raising `getUserTotalLocked(attacker)` to roughly `_amount1`.
2. Attacker calls `mWomSV.startUnlock(_amount1)` (or the full locked balance). This moves the whole balance into cool-down, making `getUserTotalLocked(attacker)` drop back to 0 while the mWOM is still staked in MasterMagpie/mWomSV (not actually withdrawn).
3. Attacker calls `incentiveDeposit(_amount2, ..., _mode=2)` again in the same block (or shortly after). `getRewardAmount` again sees `getUserTotalLocked(attacker) == 0`, so `calDoubledCounted` is 0 and the attacker is rewarded as though `_amount2` were their very first deposit, re-earning the top-tier multiplier instead of the diminished multiplier that should apply given their true cumulative locked position (`_amount1 + _amount2`).
4. This can be repeated (`startUnlock` can be reset/reused, per the function's own comment, "this function can also be used to reset or change a slot"), letting the attacker extract disproportionately more MGP per unit of WOM deposited than the tier schedule intends, up to the cap `mgpleft = IERC20(mgp).balanceOf(address(this))` per call — draining the finite MGP reward pool meant for the broader depositor base.

`nonReentrant` and `whenNotPaused` on `incentiveDeposit` do not prevent this because the attack is sequential across separate transactions/calls, not reentrancy. `calDoubledCounted` does not fail — it silently returns 0 because its input, `getUserTotalLocked`, is stale/manipulable rather than tracking true cumulative rewarded principal.

### Impact Explanation
An unprivileged attacker can systematically extract more MGP from `ArbWomUp3` than the intended declining-tier reward schedule allows, by cycling `startUnlock`/deposit to make the contract repeatedly treat their position as tier-zero. Because the MGP payout pool held by the contract is finite (`IERC20(mgp).balanceOf(address(this))`), this results in a measurable, repeatable over-extraction of MGP tokens at the expense of the reward pool intended for all depositors — matching Critical / Direct theft of user (protocol reward pool) funds.

### Likelihood Explanation
The precondition (deposit → `startUnlock` → deposit again) requires only calls to public, unprivileged functions (`incentiveDeposit` and `mWomSV.startUnlock`), no special role, and can be executed within the same block or across a few blocks. The attacker needs capital equal to the WOM amounts they wish to deposit at each step (which they get back, since it's simply routed into mWOM/mWomSV under their own control), making the exploit cheap and repeatable as many times as the MGP balance allows.

### Recommendation
Base `calDoubledCounted`/tier computation on a value that cannot be reduced by `startUnlock`, such as the user's total ever-locked-through-this-contract MGP-tier-rewarded principal (tracked in a dedicated `mapping(address => uint256)` updated only by `ArbWomUp3` itself on deposit), or use `mWomSV.balanceOf(_account)` (which includes cool-down amounts) instead of `getUserTotalLocked` for the tier/double-count logic, so that initiating an unlock cannot reset the perceived locked balance.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `MasterMagpie`, mock `mWOM`/`wom`/`mgp` tokens, and `SmartWomConvert`; configure `rewardTier = [0, 1000e18, 2000e18]`, `rewardMultiplier = [100, 50]` (top tier pays more per unit than higher brackets), fund `ArbWomUp3` with enough MGP.
2. Attacker calls `incentiveDeposit(1000e18, ratio, false, 2)`; record `mgpReward1` from `VLMGPRewarded` event and contract's remaining MGP balance.
3. Attacker calls `mWomSV.startUnlock(mWomSV.getUserTotalLocked(attacker))`.
4. Assert `mWomSV.getUserTotalLocked(attacker) == 0` even though `mWomSV.balanceOf(attacker)` (or MasterMagpie `stakingInfo`) still reflects the full prior stake.
5. Attacker calls `incentiveDeposit(1000e18, ratio, false, 2)` again in the same block; record `mgpReward2`.
6. Assert `mgpReward1 + mgpReward2` exceeds the reward that a single `incentiveDeposit(2000e18, ...)` call would have produced (i.e., the tier-degression is bypassed), and that `IERC20(mgp).balanceOf(address(this))` has been depleted by more than the amount intended for a correctly-tiered 2000e18 deposit — demonstrating the divergence between `rewardToSend` (per call, capped only by `mgpleft`) and the true amount owed under one consistent snapshot of cumulative locked principal.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }

    function calDoubledCounted(address _account) public view returns (uint256) {
        uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accuIn1 > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }

        rewardAmount += (accuIn1 - rewardTier[i - 1]) * rewardMultiplier[i - 1];
        return rewardAmount / DENOMINATOR;
    }
