## Analysis

The external report's core invariant is: *a single coarse authorization signal (one authorized account) gates every privileged action, with no finer-grained separation of duties* — so anyone who can satisfy that one signal gets full control. The Hyperbridge local analog is the same shape but on the message-authentication side: several EVM-side ISMP apps that receive governance actions (fund withdrawal, host-param updates, proxy upgrades, token registry changes) authenticate inbound `onAccept` calls using only the **source chain id** (`request.source == hyperbridge`) — they never check `request.from`, the actual module identifier of the pallet that dispatched the message on Hyperbridge.

### Title
Governance `onAccept` handlers authenticate only by source chain, not by sending module (`request.from`), letting any Hyperbridge-originated message trigger fund withdrawal/host reconfiguration - (File: `evm/src/core/HostManager.sol`)

### Summary
`HostManager.onAccept`, `BandwidthManager.onAccept`, and `SimplexPaymaster.onAccept` all validate an inbound governance `PostRequest` by checking only that `request.source` equals the Hyperbridge state-machine id [1](#0-0) , [2](#0-1) , [3](#0-2) . None of them verify `request.from` — the module identifier of the specific pallet on Hyperbridge that dispatched the request.

### Finding Description
Hyperbridge's own documentation establishes that the sending module identity (`from`) is a distinct, load-bearing piece of authorization information, separate from the source chain id: the outbound-reward system explicitly keys its allowlist by `request.from` because `request.source == hyperbridge` alone is *not* a sufficient identity check, since many different pallets legitimately dispatch requests from Hyperbridge (host-executive, intents-coprocessor, token-governor, relayer, bandwidth, and "any other pallet that ends up dispatching from hyperbridge") [4](#0-3) . The dispatcher primitive (`DispatchPost { dest, from, to, timeout, body }`) lets a dispatching pallet freely choose `to` (destination contract) and `body` (payload) [5](#0-4) , and the framework's own example shows this being wired directly to a signed, user-invocable extrinsic that forwards the caller-supplied `DispatchPost` (including `from`) straight into `dispatch_request` [6](#0-5) .

Given that pattern, `request.source == hyperbridge` is trivially true for *any* pallet-originated message from the coprocessor chain — it says nothing about which pallet sent it. Yet `HostManager.onAccept` uses exactly that single check to authorize a `Withdraw` action that transfers `WithdrawParams`-specified funds to an arbitrary `beneficiary`, or a `SetHostParam` action that rewrites the entire `HostParams` of the EVM host [7](#0-6) . `BandwidthManager.onAccept` similarly authorizes `Withdraw` (arbitrary ERC20/native transfer to `w.beneficiary`) and `SetTiers` price changes on the same single check [8](#0-7) . `SimplexPaymaster.onAccept` gates `UpgradeContract` (arbitrary UUPS implementation swap), `WithdrawAssets`, `RegisterToken`, and `DeactivateToken` on the identical check [9](#0-8) .

This mirrors the report's bug class precisely: instead of one over-privileged EOA, there is one over-broad authorization predicate (`source == hyperbridge`) that stands in for "this message is authentic governance," when the actual security-relevant identity is the specific dispatching module (`from`), which the protocol's own reward-allowlist design treats as the real authorization key. Any pallet on Hyperbridge capable of dispatching an outbound POST with attacker-influenced `to`/`body` — and the dispatch primitive is explicitly designed to let calling pallets set arbitrary `to`/`body` — can therefore impersonate the trusted host-executive/relayer-withdrawal/bandwidth-governance module and drive these EVM contracts' privileged code paths.

### Impact Explanation
If any Hyperbridge-side pallet (present or future) exposes a signed-user-triggerable path that dispatches an outbound POST to one of these contracts with attacker-chosen `to`+`body` (the documented dispatcher pattern permits exactly this), an attacker can:
- Drain `HostManager`'s and `BandwidthManager`'s escrowed bridge revenue/treasury funds to an attacker-controlled `beneficiary` via the `Withdraw` action.
- Rewrite `EvmHost`'s `HostParams` (admin, handler, consensus client, fee token, etc.) via `SetHostParam`, potentially seizing control of the host's trust configuration.
- Upgrade `SimplexPaymaster`'s implementation to arbitrary attacker-supplied bytecode via `UpgradeContract`, or register malicious token/oracle pairs.

This is unauthorized execution and direct fund loss/lock through a missing module-identity check on cross-chain governance messages — matching the "unauthorized transaction or execution" / "stealing or loss of funds" impact classes.

### Likelihood Explanation
Exploitability hinges entirely on whether any pallet in the live Hyperbridge (nexus) runtime exposes a permissionless (or under-restricted) extrinsic that lets a caller influence `to`/`body`/`from` of an outbound `DispatchPost` targeting these specific EVM contract addresses. The codebase's own documentation demonstrates this exact wiring pattern for pallet authors, and the reward-allowlist design confirms the maintainers are aware that `source == hyperbridge` does not identify the sending module — they solved that problem in the relayer-reward pallet by keying on `request.from`, but the governance-receiving EVM contracts were not updated with the same discipline. I could not fully confirm from the indexed code whether the currently deployed nexus runtime pallets restrict `to`/`body` tightly enough to close this gap for every dispatch path (this would require exhaustively auditing every pallet's dispatch call sites in the live runtime, which is not indexed here) — so likelihood should be treated as "verify against the exact runtime dispatch surface," but the missing defense-in-depth check on the EVM side is unambiguous and independent of that uncertainty.

### Recommendation
Add an explicit check on `request.from` in every governance `onAccept` handler (`HostManager.sol`, `BandwidthManager.sol`, `SimplexPaymaster.sol`), comparing it against a hardcoded/immutable expected module id (e.g., the host-executive or relayer-withdrawal pallet's `PalletId`, or `pallet-bandwidth`'s module id), in addition to the existing `request.source == hyperbridge` check — mirroring the module-id allowlist approach already used in the outbound-reward pallet. Reject any request whose `from` does not exactly match the single trusted governance module for that action type.

### Proof of Concept
1. Identify (or, per protocol design, any future) a pallet on Hyperbridge nexus with a signed extrinsic that forwards a caller-influenced `DispatchPost{ from, to, body }` into `pallet_ismp::dispatch_request` (the documented `send_message` pattern) [6](#0-5) .
2. Craft `body = abi.encodePacked(uint8(OnAcceptActions.Withdraw), abi.encode(Withdrawal{ token: feeToken, beneficiary: attacker, amount: contractBalance }))` and set `to = <HostManager or BandwidthManager address>`.
3. Submit the extrinsic from any signed account; the resulting `PostRequest` has `source = hyperbridge` (true by construction) regardless of which module actually dispatched it.
4. When relayed and delivered on the EVM chain, `onAccept` passes its only check (`request.source.equals(hyperbridge)`) [10](#0-9)  and executes the `Withdraw`, transferring funds to `attacker`.

```text
        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
```

```text
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));

                tierPrice[updates[i].tier] = updates[i].price;

                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);

        }
```

**File:** docs/outbound-request-incentivization.md (L16-19)
```markdown

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

This is structurally identical to the existing `claim_outbound_consensus_delivery_reward` (see `modules/pallets/relayer/src/outbound_consensus.rs`) on the consensus side. The request claim lives in its own `modules/pallets/relayer/src/outbound_request.rs` module that mirrors it: swap "consensus rotation delivered" for "request delivered," key the reward storage by `module_id`, and have the relayer ship the full `PostRequest` in the claim so the pallet can hash it on chain.
```
