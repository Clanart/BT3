## Finding

### Title
Missing reentrancy guard and checks-effects-interactions violation in `IntentGatewayV2.withdraw()` (Tron deployment) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2` (a full re-implementation of the intent-settlement/escrow contract, not a thin wrapper) omits `ReentrancyGuardTransient` entirely and performs external value/token transfers in `withdraw()` before decrementing the corresponding escrow accounting map `_orders[commitment][token]`. This is the exact bug class from the external report (external calls before state writes) reintroduced in a production contract path, while the canonical EVM version of the same contract has since been hardened with `nonReentrant` and CEI-ordered writes.

### Finding Description
`evm/tron/contracts/apps/IntentGatewayV2.sol` declares the contract as `contract IntentGatewayV2 is HyperApp, EIP712` with no `ReentrancyGuard`/`ReentrancyGuardTransient` inheritance and no `nonReentrant` modifier anywhere in the file [1](#0-0) . `placeOrder`, `cancelOrder` are declared `public payable` with no reentrancy modifier [2](#0-1) [3](#0-2) .

The internal `withdraw()` function, which releases escrowed order funds (used by both `onAccept` for `RedeemEscrow`/`RefundEscrow` and `onGetResponse` for cancel-from-source refunds), sets `_filled[commitment]` up front (good), but then loops over `body.tokens` and makes an external call (`beneficiary.call{value: amount}("")` for native tokens, or `token.call(...transfer...)` for ERC-20) **before** decrementing the per-token escrow balance `_orders[body.commitment][token]`: [4](#0-3) 

This mirrors precisely the bug class described in the external report: external calls (`.transfer()`/`.call()`) occurring before the write of the state variable that tracks whether/how much has been redeemed. The same file also performs unguarded external calls before/without effect-ordering protection in `_sweepDust`-equivalent logic inside `onAccept`'s `SweepDust` branch [5](#0-4) .

By contrast, the primary EVM `IntentGatewayV2.sol` inherits `ReentrancyGuardTransient` and marks `placeOrder`, `fillOrder`, and `cancelOrder` as `nonReentrant` [6](#0-5) [7](#0-6) [8](#0-7) , and a dedicated regression test suite (`IntrinsicIntentsReentrancyTest.sol`) exists specifically confirming a prior reentrancy bug in `_fillSameChain`/`_fillCrossChain` was fixed by moving `_filled[commitment] = msg.sender` to the top of the function (CEI) [9](#0-8) . The Tron contract received no equivalent hardening: it has neither the `nonReentrant` guards nor confirmed CEI ordering in the fund-release path.

### Impact Explanation
`_orders[commitment][token]` is the on-chain accounting of escrowed user/solver funds for intent settlement. `withdraw()` is the single code path that releases that escrow to a beneficiary for both order fill redemption and order cancellation refunds. Because the escrow-balance write trails the external transfer, and no reentrancy lock exists across the whole contract (`placeOrder`, `cancelOrder`, `onAccept`, `onGetResponse` are all unguarded), an attacker who controls the beneficiary address of their own order (fully permitted — beneficiaries are user-supplied) can install malicious receive/fallback logic that fires mid-loop, while `_orders[commitment][token]` for that (and any other not-yet-processed) token is still at its pre-withdrawal value. This falls squarely under "stealing or loss of funds" / "double-claim/double-settlement" for bridged escrow, matching the bounty's asset-custody pivot.

### Likelihood Explanation
Reachable by any unprivileged user: placing an order and specifying themselves (a contract they control) as beneficiary is a normal, permissionless action, no relayer/prover/admin collusion required. The trigger (a native-token or hook-capable ERC-20 transfer to an attacker-controlled beneficiary during escrow release) executes automatically as part of the intended redemption/cancellation flow.

### Recommendation
- Add `ReentrancyGuard`/`ReentrancyGuardTransient` to the Tron `IntentGatewayV2` and mark `placeOrder`, `fillOrder`, `cancelOrder`, `onAccept`, and `onGetResponse` as `nonReentrant`, matching the EVM version.
- In `withdraw()`, decrement `_orders[body.commitment][token]` (and the tx-fee entry) **before** making the external `.call`, following checks-effects-interactions for every token in the loop, not just the top-level `_filled` write.
- Add the same reentrancy regression coverage (`IntrinsicIntentsReentrancyTest.sol`-style) for the Tron contract.

### Proof of Concept
1. Attacker deploys a malicious beneficiary contract with a `receive()`/token-callback that, when it fires, attempts to trigger a second read of the still-inflated `_orders[commitment][token]` state (e.g., via a duplicated-token order construction, or by chaining a second entry point that reads `_orders` before the current `withdraw()` call has finished decrementing all its entries).
2. Attacker calls `placeOrder` with `order.inputs` containing multiple `TokenInfo` entries — e.g., two native-token (`address(0)`) entries — with the malicious contract's address encoded as `order.output.beneficiary`/`order.user`.
3. Attacker triggers a same-chain cancellation/fill flow that invokes `withdraw()`.
4. During the first native-token `.call{value: amount}("")` in the loop, `_orders[commitment][address(0)]` has **not yet** been decremented for that iteration; the malicious contract's fallback executes here.
5. Because the contract has no `nonReentrant` guard on any public function, this callback window is unprotected contract-wide, unlike the hardened EVM sibling contract, allowing state to be read/manipulated while `_orders` is stale — the concrete corrupted value is `_orders[commitment][token]`, and no guard (guard is entirely absent) stops the path.
