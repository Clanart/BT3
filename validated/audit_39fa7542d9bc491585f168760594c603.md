## Title
Excess Native-Token Fee Payment Permanently Locked in `EvmHost` During `dispatch()`/`fundRequest()` Swaps - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native-token payment and internally swap it for the exact `feeToken` amount needed via Uniswap V2's `swapETHForExactTokens`. None of these functions capture or forward back any leftover native token that the router refunds after the exact-output swap, unlike the `JBXBuybackDelegate` analog where the unused ETH from a partial/limited swap is never returned to the payer.

### Finding Description
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`: [1](#0-0) [2](#0-1) [3](#0-2) 

Each of these calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(feeAmount, path, address(this), block.timestamp)`. By the Uniswap V2 router's own semantics, `swapETHForExactTokens` only consumes the ETH actually required to produce `feeAmount` of the output token and refunds any surplus `msg.value` back to `msg.sender` of that call — which is `EvmHost` itself, not the original caller (`_msgSender()`) who funded the transaction. There is no code path in any of these three functions that captures this router refund and forwards it back to the actual payer. Any ETH sent above the amount strictly needed to acquire `feeAmount` of `feeToken()` is absorbed into the `EvmHost` contract's own balance rather than returned to the user.

This is the exact same broken invariant as the `JBXBuybackDelegate` report: a contract performs an exact-output/limited swap with `msg.value`, and the portion of `msg.value` not consumed by the swap is not refunded to the depositor, resulting in a silent, permanent value transfer from the user to the contract.

Unlike `IntrinsicIntents._fillSameChain` / `ExtrinsicIntents.fillOrder` in the same repository, which explicitly track `msgValue` and refund any unspent native token to `msg.sender` at the end of execution (`evm/src/apps/intentsv2/IntrinsicIntents.sol:144-148`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-168`), `EvmHost`'s three fee-payment entry points contain no equivalent refund logic.

### Impact Explanation
Any user who dispatches a POST/GET request or funds an existing request with native token overpays permanently loses the difference between `msg.value` and the ETH actually consumed by the swap (which itself is bounded by the AMM price at execution time — a value the caller cannot predict exactly on-chain, especially under price movement between quote and execution). Because `feeToken()` prices fluctuate and callers must send a `msg.value` buffer to guarantee the swap succeeds, essentially every native-token fee payment through these paths will overpay by some margin, and that margin is trapped in the `EvmHost` contract rather than returned to the payer. This constitutes unauthorized, silent loss of user funds — a direct violation of the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" pivot, reachable by any unprivileged caller with no relayer, prover, or admin involvement.

### Likelihood Explanation
This triggers on ordinary, expected usage — every native-token payment for `dispatch()`/`fundRequest()` requires the caller to send `msg.value` with some slippage/price buffer (since the exact ETH cost of acquiring `feeAmount` of `feeToken` cannot be known precisely at call time due to AMM price fluctuation between quoting and execution). There is no adversarial precondition required; it happens by default whenever a user doesn't send the exact minimal amount, which is the normal case. This is a high-likelihood, unprivileged, public-entrypoint issue.

### Recommendation
Track the ETH balance of `EvmHost` before and after the `swapETHForExactTokens` call (or capture the return value of the swap, which reports `amounts[0]` spent) in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amountSpent` back to `_msgSender()` at the end of each function, mirroring the pattern already used in `IntrinsicIntents._fillSameChain` and `ExtrinsicIntents.fillOrder`.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost{... fee: 100e18 feeToken ...})` sending `msg.value = 1 ether` to cover the swap, expecting the router to only use what's needed.
2. Inside `dispatch()`:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [1](#0-0) 
3. Suppose only `0.6 ether` is required to acquire `100e18` of `feeToken` at current pool price. The Uniswap V2 router internally refunds the remaining `0.4 ether` to its caller — `EvmHost` — via a low-level ETH transfer.
4. `EvmHost` has no logic anywhere in `dispatch()` to detect or forward this `0.4 ether` refund back to the user; it simply accrues to the contract's balance.
5. The user's transaction completes successfully (the POST request is dispatched, fee is paid), but `0.4 ether` that belonged to the user is now stuck in `EvmHost`, recoverable only through the privileged `IHostManager.withdraw()` path controlled by governance/host manager — not by the user who sent it.
