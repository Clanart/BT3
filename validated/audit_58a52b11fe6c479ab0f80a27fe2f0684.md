### Title
Fail-open exception handling in `pretooluse.py` allows TypeError from malformed `MultiEdit` `edits` to bypass block-action rules - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
`RuleEngine._extract_field` in `plugins/hookify/core/rule_engine.py` directly joins `new_string` values from `MultiEdit` `edits` entries without validating they are strings. A crafted `tool_input` with `edits=[{'new_string': None}]` raises an uncaught `TypeError` that propagates through `_check_condition` → `_rule_matches` → `evaluate_rules` into `pretooluse.py`'s catch-all exception handler, which always exits `0` and returns only a `systemMessage`, never a `deny` decision — silently bypassing any matching block rule.

### Finding Description
For `MultiEdit`, `_extract_field` builds the `new_text`/`content` field via: [1](#0-0) 
`e.get('new_string', '')` only applies the default `''` when the key is *absent*; if the key exists but its value is `None` (or another non-string), `e.get` returns that value unchanged, and `' '.join(...)` raises `TypeError: sequence item 0: expected str instance, NoneType found`.

This call happens inside `_check_condition`, invoked from `_rule_matches`, invoked from `evaluate_rules`: [2](#0-1) 
None of these functions catch exceptions, so the `TypeError` propagates all the way up to `pretooluse.py`'s `main()`: [3](#0-2) 
The generic top-level path in `_extract_field` (`if field in tool_input: ... return str(value)`) would normally coerce non-string values safely, but it only triggers when `field` itself is a literal key in `tool_input` (e.g. `field == 'new_string'`). Rules configured with `field == 'new_text'`/`'content'` for `MultiEdit` skip that generic coercion and fall into the unguarded tool-specific branch at line 252, so the type-confusion path is reachable specifically for rules targeting `new_text`/`content` on `MultiEdit`.

Once the exception is raised, `evaluate_rules` never returns its `{"hookSpecificOutput": {"permissionDecision": "deny"}}` payload for the matching block rule; instead `pretooluse.py` prints `{"systemMessage": "Hookify error: ..."}` and unconditionally calls `sys.exit(0)`, which Claude Code interprets as "allow" (no deny decision present). This violates the `DENY_MEANS_DENY` invariant: a configured block-action rule on `MultiEdit`/`new_text` is silently defeated by a malformed `edits` entry.

### Impact Explanation
Any hookify block rule intended to deny `MultiEdit` operations based on inspecting `new_text`/`content` (e.g. blocking writes containing secrets, dangerous code patterns, or protected paths) can be bypassed entirely by including one `edits` entry whose `new_string` is `None` (or another non-string). This is a security-control (deny) bypass of the plugin's own guardrail mechanism, matching a hook/permission-enforcement bypass impact.

### Likelihood Explanation
Triggering the bug requires only that `tool_input.edits` contains an entry with `new_string` set to `None`/non-string while a hookify rule targets `MultiEdit` with field `new_text` or `content` and `operator` in `{contains, starts_with, ends_with, equals}`. This is fully reproducible by feeding a crafted JSON payload to the hook's stdin (as `pretooluse.py` does no schema validation on `tool_input` before calling `evaluate_rules`) and requires no privileged access — only the ability to produce a `MultiEdit` call with that shape (e.g. via a manipulated/injected tool call or a non-conforming tool-call generator).

### Recommendation
In `_extract_field`, coerce all extracted values to strings defensively before returning, e.g. for MultiEdit: `' '.join(str(e.get('new_string') or '') for e in edits if isinstance(e, dict))`, and similarly guard the Write/Edit branches (`tool_input.get('new_string') or ''` cast to `str`). Additionally, wrap the `evaluate_rules` call in `pretooluse.py` with narrower exception handling that treats extraction/evaluation errors as "block-rule indeterminate" rather than defaulting to allow, or re-validate `tool_input` types before rule evaluation so malformed shapes cannot silently defeat block rules.

### Proof of Concept
Unit test in `plugins/hookify/core/rule_engine.py` test harness:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-secret",
    enabled=True,
    action="block",
    tool_matcher="MultiEdit",
    conditions=[Condition(field="new_text", operator="contains", pattern="SECRET")],
    message="Blocked: secret detected"
)

engine = RuleEngine()
input_data = {
    "hook_event_name": "PreToolUse",
    "tool_name": "MultiEdit",
    "tool_input": {
        "file_path": "/tmp/x",
        "edits": [{"old_string": "a", "new_string": None}]  # malformed edit
    }
}

result = engine.evaluate_rules([rule], input_data)  # raises TypeError, uncaught
```
Expected (secure) behavior: `evaluate_rules` should return a `deny`/indeterminate-block result or raise a caught, handled error that still results in a deny decision rather than allow. Actual behavior: `TypeError` raised and, when run through `pretooluse.py` end-to-end (feeding this `input_data` via stdin), the process prints `{"systemMessage": "Hookify error: ..."}` and exits `0` with no `deny` decision — confirming the fail-open bypass of the block rule.
