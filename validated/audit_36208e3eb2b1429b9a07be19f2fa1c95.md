### Title
Pointer contract redeploy-in-place upgrade path can create storage-layout collisions on the pointer address - (File: `x/evm/keeper/pointer_upgrade.go`)

### Summary
The Sei EVM module implements token "pointer" contracts (ERC20/ERC721/ERC1155/native wrappers around CW20/CW721/CW1155 tokens) that are versioned and can be upgraded via `MsgRegisterPointer`. When a pointer for a given token already exists but is out of date, `UpsertERCPointer` "upgrades" it not by deploying a fresh proxy/implementation pair, but by re-running the new version's deployment (constructor) bytecode against the **same existing contract address** and then overwriting only the runtime bytecode with `k.SetCode`, while any storage the old pointer version wrote at that address is left untouched. [1](#0-0) 

### Finding Description
`UpsertERCPointer` looks up whether a pointer already exists for the given token. If it does, instead of deploying a brand-new contract at a new address, it calls `evm.GetDeploymentCode(...existingAddr)` — running the new version's constructor logic against the pre-existing address — and then simply calls `k.SetCode(writeCtx, contractAddr, ret)` to swap in the new runtime bytecode, with no step that clears or resets the account's existing storage slots. [2](#0-1) 

Pointer contracts are explicitly versioned per type (e.g. `erc20.CurrentVersion`, `cw20.CurrentVersion`, `erc721.CurrentVersion`, `erc1155.CurrentVersion`), and `RegisterPointer` re-deploys when a stored pointer's version is lower than current, retaining the same contract address across the upgrade. [3](#0-2) [4](#0-3) 

The pointer implementation contracts themselves (e.g. `CW20ERC20Pointer`) are regular non-upgradeable Solidity contracts built on OpenZeppelin's `ERC20`, with state variables (`Cw20Address`, `WasmdPrecompile`, `JsonPrecompile`, `AddrPrecompile`) declared with no explicit storage-gap reservation and no assumption that they will ever be redeployed onto an address that already carries state from a prior, differently laid-out version of the same contract family. [5](#0-4) 

This is precisely the storage-clash class described in the external report: because the "upgrade" path re-uses the same account/address and only replaces code (never clears storage), any change to the pointer contract's state-variable layout between versions (e.g. bumping `CurrentVersion`, adding a new field, or reordering an inherited OpenZeppelin base's internal variables) causes the new implementation to read leftover storage slots written by the old version's layout — reading/writing state at the wrong slot, exactly analogous to the missing-storage-gap proxy collision in the original `YoloV2.sol` report.

### Impact Explanation
If a future pointer-contract upgrade changes storage layout (adding fields, changing inheritance order, or bumping OpenZeppelin's base contract version with a different internal layout) while the module keeps the same "redeploy in place, keep old storage" upgrade pattern, values such as ERC20 balances/allowances, decimals caching, or pointer metadata (`Cw20Address`) could be misread from stale slots left by the prior pointer version. Since pointer contracts back real token balances used for CW↔EVM interoperability, a layout collision can lead to balance/allowance corruption, incorrect token accounting, or unauthorized transfers — the class of fund-impacting outcomes called out as acceptable ("unauthorized transfer via precompile or pointer").

### Likelihood Explanation
`RegisterPointer` is a permissionless message any unprivileged transaction sender can submit, and the redeploy-in-place path is taken automatically whenever the currently registered pointer's version is behind `CurrentVersion`, which is the normal path for chain-level pointer upgrades, not a rare/operator-only trigger. [4](#0-3) 
The actual exploitability, however, depends on whether/when the pointer contract's Solidity source is modified to add or reorder state variables in a future `CurrentVersion` bump — this repo's current pointer contracts (as available in the index) do not yet show such a layout change, so this is a structural risk in the upgrade mechanism rather than a currently demonstrated storage corruption. I was not able to fully confirm within the available tool budget whether `evm.GetDeploymentCode` performs any implicit storage-clearing of the target account before running the constructor; if it does, this risk would be mitigated, but no such clearing call is visible in `UpsertERCPointer` itself.

### Recommendation
- Before re-running a pointer contract's deployment/constructor code against an existing address in `UpsertERCPointer`, explicitly clear all storage slots for that account (or use a fresh CREATE2 address per version and update the registry pointer instead of preserving the address).
- Require every pointer contract version to declare and respect a fixed storage layout/append-only schema (analogous to an explicit storage gap pattern), and add a check in the upgrade path (or in CI) that fails if a new pointer artifact's storage layout is incompatible with the prior version's layout at the same slots.
- Add unit tests that deploy pointer version N, mutate its storage (balances/allowances), upgrade to version N+1 with an intentionally different layout, and assert no stale-slot values leak into the new layout.

### Proof of Concept
1. Register a CW20→ERC20 pointer via `MsgRegisterPointer`; this deploys `CW20ERC20Pointer` at address `A` with `CurrentVersion` V1, storing `Cw20Address`, and inherited OZ `ERC20` internals at their respective slots.
2. Ship a future pointer artifact update that bumps `erc20.CurrentVersion` and changes the contract's state-variable set/order (e.g., adds a new `mapping` before `Cw20Address`, or changes the OZ ERC20 base version with different internal slot layout).
3. Any user resubmits `MsgRegisterPointer` for the same CW20 token; `RegisterPointer`/`UpsertERCPointer` detects the stale version and takes the `exists` branch in `pointer_upgrade.go`, running the new constructor against the same address `A` and overwriting only the code via `k.SetCode`. [2](#0-1) 
4. Because slots from the old contract's storage were never cleared, the new implementation's reads/writes at those slots reflect stale data from the old layout, producing incorrect balances/allowances or misrouted pointer metadata — the storage-clash impact described in the reference report.

func (k *Keeper) UpsertERCPointer(
	ctx sdk.Context, evm *vm.EVM, typ string, args []interface{}, getter PointerGetter, setter PointerSetter,
) (contractAddr common.Address, err error) {
	pointee := args[0].(string)
	evmModuleAddress := k.GetEVMAddressOrDefault(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName))

	var bin []byte
	bin, err = artifacts.GetParsedABI(typ).Pack("", args...)
	if err != nil {
		panic(err)
	}
	bin = append(artifacts.GetBin(typ), bin...)
	// GetDeploymentCode / Create take EVM snapshots that Freeze() Multistore layers.
	// Exists-lookup and commits must use the live unfrozen top (sdb.Ctx): cachekv
	// forbids writing a frozen layer, and same-tx readers that skip frozen-empty
	// parents would miss those writes. The precompile Prepare `ctx` is that top at
	// Prepare time, but is frozen once this Upsert snapshots. Always attach the
	// caller's gas meter (finite precompile meter in deliver) — sdb.Ctx() alone
	// carries the infinite EVM meter.
	sdb := state.GetDBImpl(evm.StateDB)
	liveCtx := func() sdk.Context {
		if sdb == nil {
			return ctx
		}
		return sdb.Ctx().WithGasMeter(ctx.GasMeter())
	}
	existingAddr, _, exists := getter(liveCtx(), pointee)
	suppliedGas := k.getEvmGasLimitFromCtx(ctx)
	var remainingGas uint64
	if exists {
		var ret []byte
		contractAddr = existingAddr
		ret, remainingGas, err = evm.GetDeploymentCode(evmModuleAddress, bin, suppliedGas, utils.Big0, existingAddr)
		if err != nil {
			return
		}
		// Only write on success: a failed GetDeploymentCode can leave ret as nil or
		// revert data, which must not clobber live pointer bytecode (even transiently).
		writeCtx := liveCtx()
		k.SetCode(writeCtx, contractAddr, ret)
		if sdb != nil {
			sdb.RefreshCodeCache(contractAddr, ret)
		}
	} else {
		_, contractAddr, remainingGas, err = evm.Create(evmModuleAddress, bin, suppliedGas, uint256.NewInt(0))
	}
