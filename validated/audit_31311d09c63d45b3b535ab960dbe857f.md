### Title
Precision loss in `BaseRewardPoolV2._provisionReward` permanently locks reward-token dust with every `donateRewards` call - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPoolV2` exposes a permissionless `donateRewards()` entry point that funnels into the same `_provisionReward()` routine used by the manager-only `queueNewRewards()`. That routine computes `rewardPerTokenStored += (_amountReward * 10**stakingTokenDecimals) / totalStaked()` using integer (floor) division. Just like the `MultiRewards._notifyRewardAmount()` bug referenced in the report, the remainder `(_amountReward * 10**stakingTokenDecimals) % totalStaked()` is silently discarded: the full `_amountReward` is pulled in via `safeTransferFrom`, but only the truncated portion is ever credited to `rewardPerTokenStored`, so the residual tokens become permanently stuck in the pool with no mechanism to recover or re-queue them for stakers.

### Finding Description
`_provisionReward()` in `rewards/BaseRewardPoolV2.sol` is: [1](#0-0) 

Unlike the `totalStaked() == 0` branch, which defers the whole `_amountReward` into `rewardInfo.queuedRewards` for later distribution, the `totalStaked() > 0` branch has no equivalent carry-over for the division remainder — the truncated fraction of `_amountReward * 10**stakingTokenDecimals` divided by `totalStaked()` is dropped forever, exactly the root cause pattern described for `MultiRewards._notifyRewardAmount()`.

This function is reachable by any unprivileged wallet through the permissionless `donateRewards()` wrapper: [2](#0-1) 

Any caller can pick an already-registered `_rewardToken` and a small `_amountReward` such that `_amountReward * 10**stakingTokenDecimals < totalStaked()`. In that case `rewardPerTokenStored` increases by `0`, meaning the entire donated amount is transferred into the contract yet never becomes claimable by any staker — the tokens are permanently frozen with no owner/manager sweep function for this residual balance in `BaseRewardPoolV2`.

### Impact Explanation
Funds transferred in via `donateRewards()` (or via the manager-driven `queueNewRewards()` path when the truncation occurs) become permanently unclaimable — an accumulating, irrecoverable loss of reward-token yield that would otherwise belong to stakers, matching the "permanent freezing of unclaimed yield" impact category. The magnitude depends on `totalStaked()` versus the reward amount and can be forced to 100% loss for a given call by choosing a small enough donation relative to the pool's `totalStaked()`.

### Likelihood Explanation
`donateRewards()` has no access control and can be called by any wallet holding the registered reward token, and the precision-loss condition (`_amountReward * 10**stakingTokenDecimals < totalStaked()`) is trivially satisfiable whenever the staking pool's `totalStaked()` balance is reasonably large relative to the decimals scaling factor, making the loss reproducible on demand.

### Recommendation
Track the truncated remainder (`(_amountReward * 10**stakingTokenDecimals) % totalStaked()`) in a per-reward-token accumulator (similar to `queuedRewards`) and fold it into the numerator of the next `_provisionReward()` call for that token, so residual dust is eventually credited to stakers instead of being permanently lost.

### Proof of Concept
1. Deploy a `BaseRewardPoolV2` pool where `stakingToken` has 18 decimals and register a reward token via `queueNewRewards`/constructor.
2. Have stakers deposit through `MasterMagpie` such that `totalStaked() = 1_000_000e18`.
3. Call `donateRewards(1, rewardToken)` (i.e., `_amountReward = 1`).
4. Observe `(1 * 1e18) / 1_000_000e18 == 0`, so `rewardPerTokenStored` is unchanged while the `1` wei of `rewardToken` is transferred into the contract via `safeTransferFrom` in `_provisionReward` and never becomes claimable — repeat calls accumulate stuck balance with zero benefit to stakers.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
