Found the analog: `buildSubmoduleDiff()` in `app/src/lib/git/diff.ts` computes a submodule's `fullPath` by joining the repository root with the raw `file.path` reported by `git status`/`git diff` for a gitlink entry, with no containment check comparable to `resolveWithin()`. That path is later handed to `Dispatcher.openOrAddRepository()`, which opens it as a brand-new Desktop repository without any confirmation that it is inside the original repo.

### Title
Submodule path from git status/diff is used to open an arbitrary directory as a repository, bypassing repo-root containment checks - ([File: app/src/lib/git/diff.ts])

### Summary
When Desktop renders a submodule change, it derives the submodule's `fullPath` by joining the repository root with the raw path string that `git status --porcelain=2` reports for the gitlink entry [1](#0-0) . Unlike other user-facing path resolutions in the codebase, this one does not use `resolveWithin()` and there is no check that the resolved path stays inside `repository.path`.

### Finding Description
The application already has an established guard, `resolveWithin()`, that resolves a repo-relative path and returns `null` if the resolved (and realpath-resolved, to catch symlinks) location escapes the given root [2](#0-1) . This is used for deep-link file opening (`openRepositoryFromUrl`) [3](#0-2)  and for Copilot conflict resolution writes [4](#0-3) .

However, `buildSubmoduleDiff()` builds the submodule `fullPath` with a plain `Path.join(repository.path, path)`, where `path` is `file.path` taken straight from the parsed `git status` porcelain-2 output (`IStatusEntry.path`) [1](#0-0) . That entry path is attacker-controlled: it comes from the index/tree of a cloned or fetched repository (the path where a `.gitmodules` entry or gitlink object is registered), and `Path.join()` will happily collapse `..` segments to point outside the working directory.

The resulting `fullPath` is stored on `ISubmoduleDiff` [5](#0-4)  and surfaced to the UI's "Open Repository" button for the submodule (`SubmoduleDiff.onOpenSubmoduleClick`) [6](#0-5) . Clicking it calls `onOpenSubmodule` in `Repository.tsx`, which forwards straight to `Dispatcher.openOrAddRepository(fullPath)` [7](#0-6) . `openOrAddRepository` does not validate that `path` is inside the parent repository — it directly opens an "Add Repository" popup pointed at that filesystem path [8](#0-7) .

This mirrors the report's broken invariant: a comment/expectation ("submodule path is always inside the checked-out repo") is not enforced by validating logic, so an attacker who controls the cloned repository content (a gitlink path) can supply an out-of-tree location.

### Impact Explanation
A malicious repository can register a submodule entry whose path traverses out of the working directory (e.g. `../../../../.ssh` style path components inside the tree that git reports for the gitlink). When the victim opens "Changes" for that entry and clicks "Open Repository" on the submodule diff card, Desktop will attempt to add/open an arbitrary directory outside the cloned repo as a new local Desktop repository, and (depending on `.git` state at that path) can be induced to run further Desktop operations (fetch/checkout/commit tooling) against that out-of-repo directory. At minimum, this breaks the file-system containment invariant that `resolveWithin()` exists to enforce elsewhere in the same codebase and lets a hostile repo redirect a "safe, local-repo-relative" action to a path of the attacker's choosing.

### Likelihood Explanation
The path is attacker-supplied purely through repository content (a gitlink/`.gitmodules` entry with a crafted path) — no local access, admin rights, or social engineering beyond "clone/open a malicious repository and view its changes/diff" is required, which matches valid-impact scope (attacker controls a cloned/fetched repository). Whether git itself would allow storing such a path in a gitlink and whether it survives status/diff parsing intact needs runtime verification, which I could not execute in this read-only environment — this is the main uncertainty.

### Recommendation
In `buildSubmoduleDiff()`, resolve `fullPath` with `resolveWithin(repository.path, path)` (the same helper already used in `dispatcher.ts` and `app-store.ts`) instead of a raw `Path.join`, and treat a `null` result (path escapes the repo) by refusing to render the "Open Repository" action for that submodule entry, logging the anomaly instead.

### Proof of Concept
1. Craft a malicious repository whose tree/index contains a submodule (gitlink) entry whose recorded path, when read back by `git status --porcelain=2`, resolves through `Path.join(repoRoot, path)` to a location outside `repoRoot` (e.g., containing `..` components).
2. Victim clones this repository in GitHub Desktop and opens the Changes view; the submodule entry is displayed via `SubmoduleDiff`.
3. Victim clicks "Open Repository" on the submodule card (`onOpenSubmoduleClick` → `onOpenSubmodule` → `Dispatcher.openOrAddRepository(fullPath)`).
4. Desktop opens the "Add Repository" popup pre-filled with the out-of-tree `fullPath`, which — unlike deep-link file opening — is never validated with `resolveWithin`, allowing the attacker to steer Desktop into treating an arbitrary host directory as an added repository.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
