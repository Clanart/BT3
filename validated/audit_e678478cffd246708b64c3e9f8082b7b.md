## Analysis

The external report's core invariant is: **when pulling untrusted ERC20 tokens into custody, code must credit internal accounting with the amount *actually received* (post-balance minus pre-balance), not the amount requested/transferred**, because fee-on-transfer, deflationary, or rebasing tokens can silently deliver less than requested.

I compared the two IntentGatewayV2 implementations in this repo. The primary EVM contract already fixes this class of bug — `placeOrder` snapshots `balanceOf` before `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual delta before crediting escrow [1](#0-0) . This behavior is explicitly documented and unit-tested for fee-on-transfer tokens [2](#0-1) .

However, the **Tron** deployment of the same contract dropped this protection entirely in its non-predispatch escrow path.

### Title
Untrusted-token escrow over-crediting via missing before/after balance check in Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the non-predispatch branch of `placeOrder` calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits the escrow ledger `_orders[commitment][token]` with `reducedInputs[i].amount` — the *requested* amount minus protocol fee — instead of the amount the contract actually received [3](#0-2) . This is the exact bug class from the external report: no post-balance vs. pre-balance-plus-amount check.

### Finding Description
The vulnerable block:
```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
``` [3](#0-2) 

There is no `balanceOf` snapshot before/after the `safeTransferFrom`, unlike the sibling EVM implementation which does:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [4](#0-3) 

Because `_orders[commitment][token]` is a shared per-token ledger that many different orders/commitments write into via `+=` [5](#0-4) , and `withdraw()` later pays out of that ledger by directly calling `token.call(transfer, beneficiary, amount)` and decrementing the ledger [6](#0-5) , any token whose `transferFrom` delivers less than the nominal amount (fee-on-transfer, deflationary, rebase-down, or any non-standard ERC20) causes the sum of ledger credits across all orders for that token to exceed the contract's real token balance. Because escrow accounting is a shared pool rather than per-order segregated custody, the shortfall is not contained to the order that used the lossy token — it silently reduces the pool backing every other user's escrowed position in that same token, so a later, unrelated `withdraw()` for a different (honest) order can fail or be under-collateralized, causing loss of funds/fund lock for that beneficiary while earlier withdrawers are paid in full (race-to-withdraw insolvency).

### Impact Explanation
This directly causes loss/lock of user or solver funds without any privileged actor, malicious relayer, or governance action — a normal user placing an order with an unprivileged, permissionless input token triggers permanent under-collateralization of the shared escrow ledger for that token. Any other legitimate order sharing that token can then be unable to fully honor its withdrawal, i.e. unauthorized-amount / loss-of-funds for whichever beneficiary is unlucky enough to withdraw after the pool is drained short.

### Likelihood Explanation
Requires only that the input token used in an order is fee-on-transfer, deflationary, or otherwise non-standard (delivers less than the nominal `transferFrom` amount) — a property entirely controlled by which token is listed/permitted as an input, not requiring any compromised participant. The parallel EVM contract's test suite shows this is an actively considered token class for this exact protocol [7](#0-6) , confirming it is a realistic, in-scope input type rather than a theoretical edge case.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before calling `safeTransferFrom` in the non-predispatch escrow loop of the Tron contract, compute the actual received delta, and credit `_orders[commitment][token]` (and the protocol-fee-reduced commitment hash) based on that actual received amount rather than the caller-declared `order.inputs[i].amount`.

### Proof of Concept
1. Admin/permissionless listing allows a fee-on-transfer ERC20 (e.g., 1% fee) as a valid input token on the Tron `IntentGatewayV2`.
2. User A calls `placeOrder` with `inputs[0].amount = 1000` of that token. `safeTransferFrom` delivers only 990 to the contract, but `_orders[commitmentA][token] += reducedInputs[0].amount` credits ~1000 (minus protocol fee), a 10-token overcredit versus actual balance held.
3. User B places a normal order using the same token, correctly funded 1:1 (contract now holds `990 + fundsB`, ledger records `~1000 + fundsB`).
4. When solver fills and settles order A first, `withdraw()` pays out based on the ledger amount, consuming part of User B's real backing tokens.
5. When order B is later settled, the ERC20 `transfer` in `withdraw()` reverts or short-pays because the contract's actual token balance is less than the sum of ledger entries, causing User B's (or the solver's) withdrawal to fail/lock or receive less than entitled — demonstrating fund loss caused solely by a normal, permissionless `placeOrder` call and no malicious relayer/admin involvement. This mirrors the exact test scenario already proven against the (patched) EVM sibling contract in `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` [8](#0-7) , but the Tron contract lacks the corresponding guard.

        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),

            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);

        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
