### Title
Duplicate signer entries allow one Schnorr signature to satisfy an aggregate - ([File: crypto/schnorr/src/aggregate.rs])

### Summary
`SchnorrAggregate::verify` accepts attacker-controlled `(public_key, challenge)` entries without rejecting duplicates. Because verification is a linear combination, two identical entries can be satisfied by replaying the same nonce and scaling the valid signature response by the sum of the two deterministic aggregation weights.

### Finding Description
`SchnorrAggregate::read` accepts a length, a list of nonces, and one scalar response without enforcing distinct signers or statements. [1](#0-0)  During verification, each supplied challenge contributes a deterministic weight `z_i`, producing the terms `z_i * R_i` and `z_i * c_i * A_i`. [2](#0-1)  A normal Schnorr signature satisfies `R + cA - sG = 0`. [3](#0-2)  Therefore, for duplicated `(A, c)` entries and duplicated `R`, submitting `s' = (z1 + z2) * s` makes the aggregate equation equal zero.

There is no uniqueness check before verification. [4](#0-3) 

### Impact Explanation
An unprivileged party can transform one valid Schnorr signature into an aggregate signature which verifies as two signatures for the same signer/challenge pair. Any protocol which interprets each `keys_and_challenges` entry as a separate authorization can count one authorization multiple times, producing a forged aggregate authorization.

### Likelihood Explanation
The attack only requires public knowledge of the original `(R, s)` signature, the aggregate DST, and the duplicated challenge. The weights are deterministic and derived entirely from public transcript data. [5](#0-4)  Exploitation requires the verifier to supply or accept duplicate signer/challenge entries; the API neither prevents nor documents that requirement.

### Recommendation
Reject duplicate `(public_key, challenge)` pairs in `SchnorrAggregate::verify`. Prefer rejecting duplicate public keys entirely if each aggregate entry is intended to represent a distinct signer. Alternatively, serialize signer uniqueness requirements into a higher-level API and document that callers must enforce them before invoking this verifier.

### Proof of Concept
Let `(R, s)` be one valid signature satisfying:

```text
sG = R + cA
```

Construct a serialized aggregate containing:

```text
length = 2
R_0 = R
R_1 = R
s' = (z_0 + z_1) * s
```

where `z_0` and `z_1` are the two deterministic weights generated by `aggregate.rs` for:

```text
keys_and_challenges = [(A, c), (A, c)]
```

Verification computes:

```text
z_0*R + z_0*c*A + z_1*R + z_1*c*A - s'*G
= (z_0 + z_1)(R + cA) - (z_0 + z_1)sG
= 0
```

Thus `SchnorrAggregate::verify` returns true even though only one underlying signature exists.
