## Title
NFT royalty fee can be bypassed via rounding-down division when a trade is split into small increments - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`compute_royalty_amount` and `NFTWallet.royalty_calculation` in `chia/wallet/nft_wallet/nft_wallet.py` compute the royalty owed to an NFT's royalty address using integer floor division (`//`) over basis points, exactly the rounding-down pattern described in the referenced report. Because the royalty is computed per-trade from a fungible amount that floor-divides toward zero, a party constructing/settling royalty-bearing NFT offers can split a large trade into many sufficiently small increments so that each individual increment's computed royalty rounds down to `0`, letting the aggregate trade evade the intended royalty entirely.

### Finding Description

and the batch-royalty helper used by both the RPC (`nft_calculate_royalties`) and offer machinery uses the same floor-division pattern: [2](#0-1) 

The unit tests explicitly confirm the rounding-to-zero behavior for small enough amounts/percentages: [3](#0-2) 

`compute_royalty_amount` is invoked from `make_nft1_offer` when constructing the royalty `CreateCoin` payments for an offer that includes a royalty-enabled NFT: [4](#0-3) 

Because `amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`, any single fungible amount smaller than `MAX_ROYALTY_BASIS_POINTS / percentage` (in the smallest mojo/CAT unit) produces `royalty == 0` for that increment. This mirrors the described `instantUnstake` bug class: instead of rounding the fee up (or applying it to the whole amount before subtraction), the code computes the fee/royalty directly via floor division on the (possibly small) traded amount, so an offer-maker can structure/repeat many small-value NFT-for-fungible-asset offers (each below the rounding threshold) to accumulate the same total fungible proceeds while the royalty due on each leg rounds to zero, instead of paying royalty on the equivalent single large trade.

### Impact Explanation
This lets any wallet user who is a party to NFT offers strip or drastically reduce the royalty revenue owed to the NFT's `royalty_address`/creator by fragmenting a trade into many small increments, each computed puzzle-side/wallet-side with a zero royalty due to floor-division truncation. This is a fee-avoidance/value-diversion issue affecting NFT creators' royalty income across offers/trades, matching the "concrete unsigned or unauthorized coin movement" bug class in spirit (funds that should move to the royalty address never do), reachable by any ordinary offer counterparty with no special privileges. Because chia mojo amounts are integers with no forced minimum granularity, and royalty percentages can be set arbitrarily low (or trades sized arbitrarily small, e.g., in CAT with small effective unit value), this is practically exploitable, though it requires many repeated transactions (transaction fees/mempool cost act as a natural friction, similar to the original report's caveat about "not feasible on mainnet" for larger fees but feasible for cheaper conditions/small-decimal assets).

### Likelihood Explanation
Medium likelihood: exploitation requires the attacker (any NFT offer maker/taker) to deliberately structure many small trades rather than one large trade, each incurring its own mempool/chain fee overhead, which reduces attractiveness on Chia mainnet but becomes practical for low/no fee-cost trading patterns, very small percentage royalties, or aggregation across many separate low-value NFT sales, mirroring the original finding's assessment that this attack is more relevant off of expensive-fee networks.

### Recommendation
Change the royalty computation to round up (or at minimum never round down to zero when a nonzero royalty is due), e.g. using `-(-numerator // denominator)` style ceiling division, or by computing `amount_minus_royalty = amount * (MAX_ROYALTY_BASIS_POINTS - percentage) // MAX_ROYALTY_BASIS_POINTS` and deriving royalty as `amount - amount_minus_royalty`, so the royalty is only exactly `0` when `percentage == 0`. Apply the same fix consistently to both `compute_royalty_amount` and `NFTWallet.royalty_calculation` in `chia/wallet/nft_wallet/nft_wallet.py`.

### Proof of Concept
1. Mint an NFT with a nonzero `royalty_percentage` (e.g., 100 basis points = 1%).
2. Instead of creating one offer trading the NFT for `1000` mojos of a fungible asset (which would yield `compute_royalty_amount(-1000, 1, 100) = 10`), create/settle 20 separate offers each trading a fractional interest for `50` mojos.
3. For each 50-mojo leg, `compute_royalty_amount(-50, 1, 100)` returns `0` (as directly demonstrated by `test_small_amount_truncates_to_zero` at `chia/_tests/wallet/nft_wallet/test_nft_royalty.py:42-44`), so no royalty coin is created for any leg.
4. The aggregate fungible proceeds received (`20 * 50 = 1000`) equal the single-trade case, but the total royalty paid across all legs is `0` instead of `10`, fully bypassing the intended 1% royalty.

Note: I was unable to locate/verify the exact on-chain CLVM (`.clsp`) source for `NFT_TRANSFER_PROGRAM_DEFAULT` within the indexed codebase to confirm whether the identical floor-division formula is also enforced at the puzzle level (only the Python driver/wallet-side `compute_royalty_amount`/`royalty_calculation` functions were found and verified). This may be due to index size limits; a full Devin session with complete repository access would be needed to inspect the CLVM puzzle source and confirm whether the on-chain enforcement path has the identical rounding behavior, which would raise this from a wallet-side royalty-computation issue to a fully puzzle-enforced, consensus-level bypass.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
