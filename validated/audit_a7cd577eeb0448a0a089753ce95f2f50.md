### Title
Deterministic `CachedPreprocess` reuse allows FROST nonce reuse across distinct signing invocations, enabling secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to the reference bug (where a front-run `retry()` causes two randomness draws to coexist, letting the attacker pick the favorable output), `SigningProtocol::preprocess_internal` deterministically re-derives the same FROST nonces from a DB-cached seed every time it runs for a given `context`. Both `DkgConfirmer::share` and `DkgConfirmer::complete` re-invoke `share_internal`, each time reconstructing the *same* nonce pair `(d, e)` and signing over whatever preprocess set was supplied. Since the attacker controls the preprocess bytes fed to `read_preprocess`, each distinct invocation produces one linear equation `s_i = d + rho_i·e + c_i·k` with attacker-known `rho_i`, `c_i`. Three invocations with distinct preprocess sets yield three equations in the three unknowns `d`, `e`, and the MuSig secret key share `k`.

### Finding Description
In `SigningProtocol::preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148), the preprocess seed is stored in `CachedPreprocesses` keyed only by `context` — for `DkgConfirmer` that is `(b"DkgConfirmer", self.attempt)` (line 275). Every call does `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`, which regenerates identical nonces via `ChaCha20Rng::from_seed(*seed.0)` in `seeded_preprocess` (crypto/frost/src/sign.rs:127-132). The seed is never deleted or rotated.

`share_internal` (lines 150-181) is invoked from both `DkgConfirmer::share` (line 304) and `DkgConfirmer::complete` (line 312, which calls `share_internal` again at line 322 to rebuild the signature machine). Each call signs attacker-supplied preprocess commitments parsed via `read_preprocess` (crypto/frost/src/sign.rs:276-281). In `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:283-398), the private nonce scalars `d, e` are identical across invocations, while the binding factor `rho` is derived from the transcripted preprocess set (sign.rs:362-371) and the challenge `c` from `Hram` over `(R, group_key, msg)` (crypto/frost/src/algorithm.rs:208). The emitted share is `s = d + rho·e + c·k` (sign.rs:390-398, algorithm.rs:210).

The file's own header (lines 25-54) acknowledges this hazard: fixed nonces are only safe because BFT ordering is assumed to prevent operating on "distinct received messages", and a TODO notes the missing check that on-chain commitments match the presumed preprocess before publishing shares. Unlike the classic FROST preprocess one-shot rule (documented in crypto/frost/src/sign.rs:84-87: reuse "will enable third-party recovery of your private key share"), nothing in `share`/`complete` enforces that the cached seed is consumed exactly once or that the signed-over preprocess set is identical to a previously signed one for the same attempt.

### Impact Explanation
Each signature share published for the same `attempt` with a different preprocess set leaks one linear relation over the validator's static secret share `k` (the substrate/MuSig key). With three distinct preprocess sets — which an attacker participant can produce by varying its own commitment bytes — the system `s_i = d + rho_i·e + c_i·k` is fully determined, recovering `k` directly. This is key-share recovery, not merely a fairness break, and it compromises the validator key that is the root of trust for DKG confirmation. Even two shares with `rho_1 = rho_2` (same preprocess set, or a rebuilt/partially-rebuilt node replaying) but different `c` would give `s_1 - s_2 = (c_1 - c_2)·k`, recovering `k` immediately.

### Likelihood Explanation
Exploitation requires `share_internal` to execute multiple times for the same `attempt` with differing inputs — via multiple share/complete transactions, a coordinator restart/partial rebuild replaying with a different preprocess map, or any acceptance path that doesn't pin the preprocess set to the first one signed. The code explicitly relies on BFT finality to prevent this rather than enforcing it locally (no consumed-flag on the cached seed, no preprocess-set pinning — the TODO at lines 50-54 admits the check is missing). Given that the unsafe condition is documented as an accepted-but-unenforced bound rather than cryptographically prevented, and the consequence is full key-share recovery, this rates High if any re-execution path is reachable; Medium under strict BFT assumptions.

### Recommendation
- Treat the cached preprocess as single-use: after `share_internal` signs, record the signed preprocess-set hash in the DB and refuse to sign again for the same `context` with a different set (implementing the TODO at signing_protocol.rs:50-54).
- Alternatively, mix the negotiated preprocess-set hash (or the `rho_transcript` output) into the nonce derivation so re-execution over a different set yields different nonces.
- Delete/rotate `CachedPreprocesses` entries after use instead of regenerating from the same seed indefinitely.

### Proof of Concept
1. A DKG confirmation attempt `A` begins; `DkgConfirmer::new` creates context `(b"DkgConfirmer", A)`.
2. Attacker (a validator participant) arranges for the coordinator's `share()`/`complete()` to be invoked three times for attempt `A` with preprocess maps differing in the attacker's own commitment bytes (each map is parsed from attacker-influenced serialized preprocesses via `read_preprocess`).
3. Each invocation calls `preprocess_internal` → `from_cache` → `seeded_preprocess` with the identical stored seed, so `(d, e)` are identical, while `rho_i` (from `B.calculate_binding_factors` over the transcripted set, sign.rs:362-371) and `c_i` differ.
4. Collect the three published shares `s_i = d + rho_i·e + c_i·k`. Solve the 3×3 linear system over the Ristretto scalar field for `k`, recovering the validator's MuSig secret key share.
