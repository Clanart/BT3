### Title
Fee and weight are computed on a transaction that omits the OP_RETURN output, so the actual transaction pays a lower fee rate than requested and can exceed the standard weight limit - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes a data-carrying `OP_RETURN` output into `tx_outs` but then calls `calculate_weight_vbytes(tx_ins.len(), payments, ...)` with `payments` — a slice that does not include the OP_RETURN output. The reported `weight` and `vbytes`, and therefore `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check, are computed on a smaller transaction than the one actually signed and broadcast. This mirrors the audited bug class: an amount is computed on one basis (the smaller payment set) while the obligation (the real transaction size/fee) is charged on a larger basis the payer never saw.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is appended to `tx_outs` at lines 194–202, *after* `payment_sat` is computed and *before* `calculate_weight_vbytes` is called at line 204:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62–127) builds its dummy transaction from `payments`, so the OP_RETURN output — up to 80 bytes of payload plus ~11 bytes of output overhead (8-byte value, script length, `OP_RETURN` push opcodes) — is absent from both the `weight` and `vbytes` results. The same omission occurs in the change path at lines 225–226.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) under-charges. The real transaction is up to ~93 vbytes larger than the `vbytes` used. Since no output value is reduced to compensate, `fee() == needed_fee` while the real fee rate is `needed_fee / (vbytes + op_return_size)`, strictly below the requested `fee_per_vbyte`.
2. The `TooLowFee` check at line 211 compares against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`. A caller requesting a fee rate at or near the minimum relay fee produces a transaction whose *actual* fee rate falls below 1 sat/vbyte, which default policy nodes will not relay or accept to mempool.
3. The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses the underestimated `weight`, so a transaction near the 400,000 WU limit can silently exceed it once the OP_RETURN output is added, again producing an unrelayable transaction.

### Impact Explanation
A `SignableTransaction` built with `data` set produces a signed Bitcoin transaction that is either under-priced relative to its real size or non-standard by weight. Outputs spent as inputs (`prevouts`) are committed in the sighash (`Prevouts::All`, line 375), so the threshold signature cannot be trivially rebound to a corrected transaction — the round must be re-run. In the worst case the broadcast transaction is rejected by relay policy, leaving the just-spent inputs' funds temporarily unspendable and requiring a full re-signing ceremony, i.e. funds reported sent/received that are not actually spendable — the same "received less than the accounting basis" harm as the reference finding.

### Likelihood Explanation
The trigger is any call to `SignableTransaction::new` with `data: Some(..)`, which is a documented public API input (`data` up to 80 bytes is explicitly supported). Any consumer of `bitcoin-serai` that attaches metadata to transactions hits the miscalculation deterministically; no malformed input or adversarial peer is required. The failure manifests whenever the requested fee rate or weight is near a policy boundary.

### Recommendation
Include the OP_RETURN output in the weight/vbytes computation. Either pass the already-built `tx_outs` (or `payments` plus a synthetic `data` output) into `calculate_weight_vbytes`, or compute the weight directly from the final `Transaction` before returning, and use that corrected `vbytes` for `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check.

### Proof of Concept
Conceptual: call `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` is chosen so `fee_per_vbyte * vbytes` just clears `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`. The constructed `tx` contains an extra ~93-byte OP_RETURN output not reflected in `vbytes`; `signable.fee()` equals `needed_fee` yet the transaction's real feerate is `needed_fee / (vbytes + ~93)` < 1 sat/vbyte, so Bitcoin Core relays reject it despite `TooLowFee` not firing. The underestimation is directly visible at send.rs lines 194–204: `data` output is pushed before `calculate_weight_vbytes` is invoked with only `payments`.
