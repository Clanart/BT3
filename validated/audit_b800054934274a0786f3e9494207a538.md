### Title
`SchnorrAggregate::verify` returns `true` for an empty aggregate (zero signers, `s = 0`) — ([File: crypto/schnorr/src/aggregate.rs])

### Summary
Analogous to CVE-2020-13895 (a verifier accepting degenerate/small-parameter signature inputs), `SchnorrAggregate::verify` accepts the degenerate empty aggregate: when `keys_and_challenges` is empty and the submitted `s` scalar is `0`, the verification equation reduces to `0·G == identity` and returns `true` with no signer bound to the statement at all.

### Finding Description
`SchnorrAggregate::read` parses a length-prefixed list of `R` points followed by a scalar `s` [1](#0-0) . A `len` of `0` is accepted, producing `Rs = []`.

In `verify`, the only length check is `self.Rs.len() != keys_and_challenges.len()`, which passes trivially when both are `0` [2](#0-1) . The pairing loop then pushes no terms, leaving only `(-self.s, C::generator())` [3](#0-2) . With `s = 0`, `multiexp_vartime` returns the identity and `verify` returns `true`.

This is reachable from untrusted bytes: `SchnorrAggregate::read` is listed as an in-scope public input sink, and `Validators::verify_aggregate` passes attacker-supplied aggregate bytes through `SchnorrAggregate::read` into `aggregate.verify` with a `signers` list derived from the same submitted message [4](#0-3) .

### Impact Explanation
The verifier accepts an aggregate signature that no key holder ever produced — a trivially forgeable "valid" result for the degenerate case. Wherever the caller's logic relies on `verify == true` to mean "the listed signers endorsed this message" (e.g., a path where the `signers`/`keys_and_challenges` list can be empty or is checked only for equality with `Rs.len()`), an attacker can submit `len = 0 || s = 0` and pass verification without any signature. This is an incorrect verifier formula: the equation being checked, `Σ z_i(R_i + c_i·A_i) − sG = 0`, is vacuously satisfiable at `n = 0, s = 0`, and the verifier never requires `n ≥ 1`.

### Likelihood Explanation
The forgery is deterministic and requires no secret material — only the ability to submit the crafted encoding to a `verify` path. Actual security impact is gated by callers: a consensus path that independently requires a non-empty quorum of weighted signers would reject the input before or regardless of this check, which is why this is rated Medium rather than High. Within this codebase the verifier itself provides no defense; correctness depends entirely on every caller separately enforcing non-emptiness.

### Recommendation
Return `false` early in `SchnorrAggregate::verify` when `self.Rs.is_empty()` (or `keys_and_challenges.is_empty()`), so the degenerate statement is never accepted as valid.

### Proof of Concept
```
// crypto/schnorr/src/aggregate.rs — verifier-side check for C = Secp256k1, Ed25519, etc.
let agg = SchnorrAggregate::<C>::read(&mut &[0u8; 36][..].as_ref()).unwrap();
// bytes: len = 0x00000000 (no R points), s = 0x00..00 (zero scalar)
assert!(agg.verify(b"any-dst", &[])); // returns true: empty statement, sG = 0
```
Correspondingly, via `Validators::verify_aggregate` (`coordinator/tributary/src/tendermint/mod.rs`), an `AggregateSignature` encoding of `0x00000000 || 0x00…00` with `signers == []` reaches `verify` and is reported as a valid aggregate signature.
