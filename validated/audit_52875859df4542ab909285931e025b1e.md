### Title
Out-of-range participant index in blame evaluation panics on HashMap indexing — denial of service (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The bug class in CVE-2021-46046 is a null/out-of-bounds dereference reachable from attacker-controlled input, causing a denial of service. The Serai analog is a reachable panic (Rust's equivalent crash) in `BlameMachine::blame` / `AdditionalBlameMachine::blame` / `Decryption::decrypt_with_proof`: attacker-chosen `sender`/`recipient`/`decryptor` `Participant` values are used as unchecked `HashMap` indices (`self.commitments[&sender]`, `self.enc_keys[&decryptor]`), panicking on any index not in `1..=n`.

### Finding Description
`Participant::new` accepts any non-zero `u16` (crypto/dkg/src/lib.rs:29-35), so values up to 65535 are constructible regardless of the DKG's `n`. In `blame_internal`, the `sender` argument indexes `self.commitments[&sender]` with no membership check (crypto/dkg/pedpop/src/lib.rs:599). Earlier, `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` when a proof is supplied (crypto/dkg/pedpop/src/encryption.rs:388). `AdditionalBlameMachine::new` only populates `commitments`/`enc_keys` for participants `1..=n` (crypto/dkg/pedpop/src/lib.rs:656-660), and `AdditionalBlameMachine::blame` forwards its caller-supplied `sender`/`recipient` straight to `blame_internal` (lib.rs:674-682). A blame accusation naming `sender = Participant(n+1)` (or any unregistered index) therefore hits `HashMap`'s `Index` impl and panics. Because `AdditionalBlameMachine` is explicitly designed to let *any* party — "regardless of if the caller was a member in the DKG protocol" (lib.rs:639-641) — evaluate blame proofs, the hostile index is an unprivileged public input.

### Impact Explanation
A single crafted blame message aborts the process/thread evaluating it. In a deployment where blame evaluation runs on validators or coordinator nodes (blame proofs are gossiped to resolve DKG faults), an unprivileged party can crash every node that evaluates the accusation — a context-dependent denial of service identical in shape and impact to the GPAC `gf_isom_box_size` dereference.

### Likelihood Explanation
Triggering requires only submitting a blame statement with an out-of-range participant index — no collusion, no valid keys, no threshold participation. `Participant` admits 65534 non-zero values while `n` is typically small, so nearly the entire index space panics.

### Recommendation
Replace unchecked indexing with lookups that return a blame/`PedPoPError`: use `self.commitments.get(&sender)` and `self.enc_keys.get(&decryptor)` and treat missing entries as the accusing party's fault (or an explicit `InvalidParticipant` error) rather than panicking. Validate `sender`/`recipient` against `1..=n` at the top of `blame_internal` and `AdditionalBlameMachine::blame`.

### Proof of Concept
```rust
// After an honest DKG with n participants produces `additional: AdditionalBlameMachine<C>`
// (constructed via AdditionalBlameMachine::new(context, n, commitment_msgs)):
let evil = Participant::new(n + 1).unwrap(); // valid non-zero Participant, not in the DKG
// Any EncryptedMessage that reaches decrypt_with_proof's DLEq branch, or for
// blame_internal's commitments lookup, a sender index > n:
additional.blame(evil, recipient, msg, Some(proof));
// -> panics at `self.enc_keys[&decryptor]` (encryption.rs:388) if `decryptor`/`recipient`
//    is unregistered, or at `self.commitments[&sender]` (lib.rs:599) — index out of bounds
//    for HashMap, unwinding/aborting the evaluator.
```
