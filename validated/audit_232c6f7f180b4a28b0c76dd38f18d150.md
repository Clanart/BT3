### Title
Payout tx attribution can be hijacked via SIGHASH_SINGLE|ANYONECANPAY malleability of the OP_RETURN operator tag - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` signs the withdrawal input with a user signature that (per the required `SinglePlusAnyoneCanPay` sighash flag) only commits to input 0 and output 0. The OP_RETURN output carrying `operator_xonly_pk` (the only source of the `payout_payer_operator_xonly_pk` DB field) is unsigned and thus fully malleable by anyone who observes the witness. An unprivileged attacker can copy that witness+output0 from a legitimate, profitable payout being broadcast by an honest operator, append their own fee-paying inputs, corrupt or redirect the OP_RETURN, and get their variant mined first, decoupling attribution from the operator that actually ran `Operator::is_profitable` and paid fees.

### Finding Description
The claimed binding: `payout_payer_operator_xonly_pk` recorded for a mined payout tx == the operator that ran `Operator::is_profitable` and funded/broadcast that payout.

- `Operator::withdraw` checks `is_profitable` and then calls `builder::transaction::create_payout_txhandler(input_utxo, output_txout, self.signer.xonly_public_key, in_signature, network)` [1](#0-0) , which builds outputs `[user payout, anchor, OP_RETURN(operator_xonly_pk)]` and finalizes the witness for input 0 with the **user-supplied** `in_signature` [2](#0-1) .
- The signature must use the `SinglePlusAnyoneCanPay` sighash type, as enforced by the wrap_err message on `SECP.verify_schnorr` [3](#0-2) . Under BIP341, `SIGHASH_SINGLE|ANYONECANPAY` only commits to input 0's prevout and to the single output at index 0 - it does **not** commit to the anchor output or to the OP_RETURN output (index 2), nor to any additional inputs the funder adds.
- Because the operator later calls `fund_raw_transaction` to add its own fee-paying inputs and only then signs+broadcasts [4](#0-3) , the base signed material (witness for input 0 + output 0) is reusable in a *different* transaction: an attacker who has seen this witness (e.g. via mempool, since the honest operator must broadcast to get it mined, or via Citrea's public withdrawal calldata) can build their own transaction reusing input 0’s witness and output 0, add their own funding inputs/fees, and substitute an arbitrary or corrupted OP_RETURN, then win the race to be mined (RBF/fee outbidding).
- Attribution is derived purely from whatever OP_RETURN ends up on-chain: `Verifier::update_finalized_payouts` parses the mined payout tx's OP_RETURN and writes `operator_xonly_pk` (or `None` if invalid/garbage) into `payout_payer_operator_xonly_pk` [5](#0-4) . Nothing here validates that the entity constructing/broadcasting the final mined transaction is the operator that ran `is_profitable`/paid the fee.
- Downstream, `Verifier::is_kickoff_malicious` treats any mismatch between the DB's `payout_payer_operator_xonly_pk` and the actual kickoff sender's `operator_xonly_pk` (or a `None`/missing value) as malicious [6](#0-5) , which triggers a Challenge tx against that kickoff sender [7](#0-6) .

Exploit flow:
1. Honest Operator O runs `is_profitable` and broadcasts a payout tx signed with the user's `SinglePlusAnyoneCanPay` signature, OP_RETURN = O's xonly pk.
2. Attacker A observes the witness for input 0 (via the mempool broadcast, or directly from the Citrea withdrawal calldata that carries `in_signature`/`in_outpoint` before O even broadcasts).
3. A constructs a new transaction reusing that witness and output 0, adds their own funding input(s)/fee, and sets output 2 (OP_RETURN) to garbage bytes (not a valid 32-byte xonly pk) or to a different real operator's pubkey.
4. A gets this variant confirmed first (double-spending O's `input_utxo`, e.g. via higher fee/RBF).
5. `update_finalized_payouts` now records `payout_payer_operator_xonly_pk = None` (or a different operator's pk) for this withdrawal.
6. When O later sends a kickoff to claim reimbursement for the deposit it actually funded, `is_kickoff_malicious` sees `operator_xonly_pk_opt == None` (or mismatched) and returns `true` → verifiers broadcast a Challenge against O, leading toward burning O's collateral, while O never gets reimbursed.

Existing guards do not stop this: `is_profitable` only gates O's own broadcast decision and is irrelevant to what actually gets mined; `SECP.verify_schnorr` only checks the input-0 signature validity under the (malleable) sighash, not tx-wide integrity; `is_kickoff_malicious` explicitly relies on the very OP_RETURN field that is unsigned and attacker-controllable.

### Impact Explanation
This breaks Critical-severity guarantees: an honest operator that fronted the withdrawal (paid the user, following a successful `is_profitable` check) can be permanently unable to be reimbursed (DB attribution becomes `None`), or worse, have its later kickoff flagged malicious and challenged, burning its collateral - both are listed Critical impacts ("an honest operator permanently unable to be reimbursed", "an honest operator's collateral burned"). The attacker gains nothing monetarily (funds still go to the withdrawer) but destroys the honest operator's ability to be reimbursed and can force collateral loss; the attack is repeatable against any withdrawal/operator pair, for the cost of a single competing on-chain transaction with adequate fee/RBF priority.

### Likelihood Explanation
Preconditions: an operator must actually attempt to service a withdrawal (this happens for every legitimate payout); the attacker only needs standard Bitcoin capabilities already granted to unprivileged actors (broadcast transactions, pay fees, observe mempool/Citrea calldata), and must win a fee/propagation race against the honest operator's own broadcast — a purely mempool-level condition, not requiring any protocol privilege, key share, or majority hashrate. The cost is limited to the attacker's own transaction fee to outbid the honest operator once, and it can be repeated for every withdrawal an operator handles, making the blast radius broad across all deposits/operators.

### Recommendation
Bind the OP_RETURN operator tag (and ideally all outputs/inputs) into the signature that the withdrawing user provides — e.g. require `SIGHASH_ALL` (or a custom sighash covering all outputs and disallowing extra inputs) instead of `SIGHASH_SINGLE|ANYONECANPAY`, or have the operator itself co-sign/commit to the exact final transaction (including OP_RETURN) before broadcasting, so that no output can be altered post-hoc by a third party without invalidating the witness.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
