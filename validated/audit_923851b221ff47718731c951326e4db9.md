### Title
Unbounded ReDoS in `security-patterns.yaml` custom regexes bypasses `_has_redos_structure()` heuristic and hangs all PostToolUse pattern checks - (File: plugins/security-guidance/hooks/extensibility.py)

### Summary
`_validate_pattern()` gates user-supplied regexes only through `_has_redos_structure()`, a narrow static heuristic matching two hardcoded shapes (`_REDOS_SHAPES`: nested `+`/`*` inside a group repeated by `+`/`*`/`?`, and `(.*)+`) plus an overlapping-alternation-under-repetition check (`_ALT_UNDER_REP`). A regex like `(a?){50}a{50}` is catastrophic-backtracking-prone (bounded optional repetition followed by a matching requirement is a classic ReDoS shape) but contains no `+`/`*` inside the inner group and its outer repetition uses a `{n}` count rather than `+`/`*`/`?`, so it matches neither `_REDOS_SHAPES` pattern, and it contains no alternation so `_ALT_UNDER_REP` never fires.

### Finding Description
The exploit path is: attacker commits `.claude/security-patterns.yaml` with a `regex` field set to a payload such as `(a?){50}a{50}` → `extensibility.load_for_session()` → `_load_user_patterns()` → `_read_config()` (YAML/JSON parses fine) → `_validate_pattern()` calls `_has_redos_structure(regex)` [1](#0-0)  which returns `False` because:
- `_REDOS_SHAPES[0]` = `\([^()]*[+*][^()]*\)[+*?]` requires a `+`/`*` *inside* the parenthesized group and a `+`/`*`/`?` immediately after it; `(a?){50}` has only `?` inside and `{50}` after, matching neither position.
- `_REDOS_SHAPES[1]` = `\(\.\*[^()]*\)[+*]` only matches literal `(.*` wildcard groups.
- `_ALT_UNDER_REP` only fires on `|` alternation inside a repeated group; `(a?){50}` has no alternation at all.

Since `_has_redos_structure()` returns `False`, `re.compile(regex)` succeeds (bounded quantifiers are syntactically valid) and the rule is merged into `user_patterns()`, which is combined with the built-in `SECURITY_PATTERNS` list defined in `plugins/security-guidance/hooks/patterns.py` [2](#0-1) . Every subsequent PostToolUse hook invocation runs the pattern list against edited file content; Python's backtracking `re` engine evaluates `(a?){n}a{n}`-style constructs with exponential worst-case time as `n` grows (the classic bounded-nested-optional ReDoS shape), so ordinary file content that fails to match at the tail (e.g. a string of `n-1` `a` characters, or any content lacking the trailing exact match) can drive the regex engine into combinatorial backtracking. The heuristic comment in the file itself acknowledges this is "not a proof — catches the common shapes," confirming the check is incomplete by design. There is no execution timeout, `signal.alarm`, subprocess sandbox, or `re2`-style engine wrapping the `re.search`/`re.compile` calls anywhere in the hook to bound this.

### Impact Explanation
Once the malicious rule is loaded, the pattern-checking step of the PostToolUse hook will hang (potentially indefinitely, bounded only by attacker-chosen `n`) on any file edit whose content triggers the backtracking blowup. Because pattern rules are evaluated together in one pass, this causes the hook to stop delivering *any* of the built-in reminders (`eval_injection`, `os_system_injection`, `pickle_deserialization`, etc.) in a timely fashion for the remainder of the session — a denial of the entire additive-and-built-in pattern enforcement layer triggered purely by a committed config file, which matches a fail-safe-isolation violation: an additive, low-trust extensibility surface degrading enforcement of unrelated, higher-trust built-in checks.

### Likelihood Explanation
The only precondition is committing a `.claude/security-patterns.yaml` file to the project, which is explicitly documented as an "allowed, additive" extensibility surface (see the module docstring in `extensibility.py` [3](#0-2) ). No special privileges are required beyond normal contribution access, and the payload is deterministic and reliably reproducible — the attacker fully controls `n` in `(a?){n}a{n}` to dial in the desired hang duration, and can further amplify by nesting multiple such rules (up to `PATTERN_MAX_RULES = 50`).

### Recommendation
Replace or supplement the static structural heuristic with a runtime-bounded validation step: compile and test-execute each user regex against a small set of adversarial probe strings (e.g., `"a" * n`, `"a" * (n-1)`, empty string) under a hard wall-clock/CPU timeout (via `signal.alarm`, a subprocess with `resource.setrlimit`, or a worker thread with `join(timeout=...)` that is killed on timeout) before accepting the rule; reject and log any regex that exceeds the timeout. Alternatively/additionally, execute user-supplied regexes at match time (in `check_patterns()`) via the `re2` engine (or Python's `regex` module in a non-backtracking mode) or wrap every `re.search`/`re.compile(...).search` call over user patterns with a per-call timeout so a single bad rule cannot stall the whole PostToolUse invocation. Also broaden the static heuristic to flag any group with a bounded quantifier `{m,n}`/`{n}` around an inner optional/quantified atom followed by a matching literal-repetition tail, since `_REDOS_SHAPES` currently only checks for `+`/`*`/`?` as the *outer* quantifier.

### Proof of Concept
Unit/fuzz test to add to the plugin's test suite (e.g., alongside existing `extensibility`/`patterns` tests):

```python
import re, time
from extensibility import _has_redos_structure

CATASTROPHIC_BUT_MISSED = [
    r"(a?){20}a{20}",
    r"(a?){30}a{30}",
    r"(a{0,1}){25}a{25}",   # equivalent bounded-optional shape
]

def test_has_redos_structure_misses_bounded_optional_repetition():
    for regex in CATASTROPHIC_BUT_MISSED:
        assert _has_redos_structure(regex) is False, (
            f"expected heuristic miss for {regex!r} (demonstrates gap)"
        )

def test_bounded_optional_repetition_actually_hangs():
    regex = re.compile(r"(a?){30}a{30}")
    content = "a" * 29  # one short of full match -> forces backtracking search
    start = time.monotonic()
    try:
        regex.search(content)
    finally:
        elapsed = time.monotonic() - start
    # Expect this to blow well past any reasonable PostToolUse hook latency
    # budget (e.g. > 2s), demonstrating a DoS-class regex.
    assert elapsed > 2.0
```

Expected result: the first test shows `_has_redos_structure()` returns `False` for the payload (heuristic bypass confirmed), and the second test shows `re.search` on ordinary content takes multiple seconds/hangs — demonstrating that an accepted rule can stall every subsequent `check_patterns()` invocation for the session. A full integration test would additionally drive `extensibility.load_for_session()` with a temp `.claude/security-patterns.yaml` containing this regex and assert that `check_patterns()` (called from `security_reminder_hook.py`) exceeds a timeout on ordinary file content.
