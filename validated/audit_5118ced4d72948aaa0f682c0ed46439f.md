### Title
Webhook shop-domain spoofing due to HMAC signature not covering the `X-Shopify-Shop-Domain` header - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` validates a webhook's authenticity by checking the HMAC signature over the raw request body only, but the shop identity that downstream code is told to trust (`shop_domain`) is read from an unsigned HTTP header. This mirrors the `address(0)` bug class: a value is implicitly treated as trustworthy/"in scope" by the security-relevant flow, but the enforcement mechanism (HMAC / balance check) never actually validates that specific value, so it can be manipulated independently of the check that is supposed to gate it.

### Finding Description
`verify_request` computes and checks the HMAC exclusively over `request.raw_post`: [1](#0-0) 

`hmac_valid?` only ever receives `data` (the raw body) and compares it against `HTTP_X_SHOPIFY_HMAC_SHA256`: [2](#0-1) 

The same module exposes a `shop_domain` helper that simply returns the unauthenticated `HTTP_X_SHOPIFY_SHOP_DOMAIN` header, with no cryptographic tie to the signed body: [3](#0-2) 

The library's own documentation instructs consumers building a custom webhook controller to use exactly this unauthenticated value to dispatch shop-scoped background work: [4](#0-3) 

Because the HMAC only covers the body, an attacker who can obtain one validly-signed webhook body+signature pair (e.g., by triggering a webhook-firing event on their own installed shop, which any merchant can do) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in `X-Shopify-Shop-Domain`. `verify_request` still passes because it never inspects that header, yet the application code (per the documented pattern) uses `shop_domain` to select which shop's records the job acts on — exactly analogous to how `address(0)` was accepted as a trusted "asset" without being covered by the downstream `IERC20` assumptions.

### Impact Explanation
Any app built following the documented `WebhookVerification`-only pattern (i.e., not using the `ShopifyAPI::Webhooks::Registry`/`WebhooksController` path that derives shop from the verified/parsed body) will process attacker-controlled webhook payloads under an attacker-chosen `shop_domain`. This allows a merchant with a legitimately installed instance of the app to forge webhook requests attributed to a different, victim shop, resulting in cross-shop data writes/actions (e.g., a job that updates or deletes records keyed by `shop_domain`) — a concrete cross-shop access/integrity violation caused by an accepted forged signed request.

### Likelihood Explanation
Exploitability requires only: (1) the app author following the officially documented `WebhookVerification` custom-controller pattern, and (2) an attacker who is a legitimate merchant able to trigger any webhook-firing event on their own shop (trivial, e.g., updating a cart/order) and replay it with a modified header to the app's public webhook endpoint. No secrets or privileged access are needed beyond normal merchant capability, making this reasonably likely wherever the documented pattern (rather than the `Registry`-based flow) is used.

### Recommendation
- Do not expose or document `shop_domain` (header-derived) as a trustworthy value in `WebhookVerification`; derive the shop identity from the verified/parsed webhook body (as `ShopifyAPI::Webhooks::Request` does) instead of `HTTP_X_SHOPIFY_SHOP_DOMAIN`.
- If the header must be supported for backward compatibility, include it in the HMAC-covered material or explicitly cross-check it against a shop value parsed from the verified body before use, and update `docs/shopify_app/webhooks.md`'s custom-controller example accordingly.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any subscribed event (e.g., updates a cart) so Shopify sends a legitimately HMAC-signed webhook to the app's `WebhookVerification`-protected endpoint.
2. Attacker intercepts/replays this request, keeping `raw_post` and `X-Shopify-Hmac-Sha256` identical, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `verify_request` recomputes the HMAC over the unchanged body and it matches, so the request is accepted: [1](#0-0) 
4. The custom controller (per documented usage) enqueues `SomeJob.perform_later(shop_domain: shop_domain, ...)` using the spoofed `victim.myshopify.com` value, causing the job to act on/against the victim shop's data with attacker-supplied payload content.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
