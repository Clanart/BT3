### Title
Silent Byte-Level Corruption of Partially-Committed File Content via Forced UTF-8 Decoding of Diff Output - (File: `app/src/lib/git/diff.ts`)

### Summary
GitHub Desktop's diff pipeline unconditionally decodes the raw `git diff` output buffer as UTF-8, discarding any byte sequence that is not valid UTF-8 by replacing it with the Unicode replacement character (U+FFFD). This decoded, lossy text (`line.text`) is later used verbatim by `formatPatch` to reconstruct a unified diff that is fed into `git apply --cached` when the user performs a **partial** (line-by-line) commit. This mirrors the reported bridge bug's root cause: an untrusted external value is reinterpreted under an unvalidated, hard-coded assumption (fixed "decimals" on the bridge vs. fixed "UTF-8" here) and re-emitted as if it were the same value, silently corrupting the artifact the user believes they are committing.

### Finding Description

``` [1](#0-0) 

This is invoked from `getWorkingDirectoryDiff` (and the commit/branch-diff variants), which run `git diff ... --patch-with-raw -z --no-color` with `encoding: 'buffer'` specifically so the raw bytes can be inspected before any string coercion: [2](#0-1) 

The only gate before this decoding is a binary/size check (`isValidBuffer`/`isBufferTooLarge`) that determines whether the diff is renderable at all — it does not validate that the *text* content is actually valid UTF-8. Files with non-UTF-8 byte sequences that git still treats as text (e.g., Latin-1/Windows-1252 encoded source files, Shift-JIS, or any file containing a handful of invalid UTF-8 byte runs) pass the binary check and get force-decoded, and any invalid byte sequence is silently replaced by `\uFFFD` (which itself re-encodes to different bytes, `EF BF BD`, than the original).

The corrupted `line.text` values become part of the `DiffHunk`/`DiffLine` model that both the UI renders **and** that `formatPatch` in `app/src/lib/patch-formatter.ts` uses to reconstruct a patch when the user selects only some lines/hunks for the commit: [3](#0-2) 

That patch is then piped directly into `git apply --cached` in `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-81`), which stages exactly the (already-corrupted) text as the new index content — it does not re-read the original working-tree bytes for the selected lines: [4](#0-3) 

For a **full-file** stage, Desktop instead runs `git add`/`update-index` directly against the working-tree file (`stageFiles` in `app/src/lib/git/update-index.ts:109-168`), which stages the real bytes and is unaffected: [5](#0-4) 

So the corruption is specific to the **partial/line-selection commit path**, where the value that actually gets written to the git object database is not what is in the working directory — it is the UTF-8-mangled reconstruction of it.

### Impact Explanation
When a user clones or fetches a repository (attacker-controlled) containing a text-classified file with non-UTF-8 byte sequences (e.g., a legacy source file, a config file, a `.txt` note, or a file crafted specifically with a few invalid UTF-8 byte runs interleaved with valid ASCII to avoid the binary heuristic) and the user performs a **partial commit** (select individual lines/hunks — a completely standard, everyday Desktop workflow, not an unusual action), any hunk touching the corrupted bytes will have those byte sequences permanently replaced by `U+FFFD` in the resulting commit — even though the file on disk is untouched and looks correct in most other editors/tools. This is silent corruption of exactly what the user commits, with no warning, diff-mismatch indicator, or confirmation step. It can subtly break builds, licensing/legal text, non-English content, or binary-adjacent text formats that were misclassified as text.

### Likelihood Explanation
This requires no privileges beyond the baseline "clone/open a repository and use Desktop's core commit feature." Partial commits (staging individual lines) are a first-class, heavily used Desktop feature. The attacker precondition is simply authoring or modifying a text file in the repository with byte sequences that are valid to git (and thus not flagged as binary) but invalid UTF-8 — an extremely low bar, achievable by anyone who can contribute a file that ends up in a repo the victim clones/fetches. No local access, admin rights, prior malware, or social engineering beyond "the victim uses Desktop normally on this repo" is required.

### Recommendation
Do not unconditionally assume UTF-8 for diff content. At minimum:
- Detect invalid UTF-8 byte sequences in `diffFromRawDiffOutput` and either fall back to treating the file as binary/unrenderable-for-partial-staging, or preserve/round-trip the raw bytes for hunks that need to be re-applied.
- For partial commits, avoid reconstructing a patch from re-encoded string content when the source bytes are not guaranteed to round-trip through UTF-8 decode/encode; instead operate on raw buffers or verify a decode→encode round trip is byte-identical before allowing `git apply` to run.
- Surface a clear warning/blocking state instead of silently staging content that differs from the working directory bytes.

### Proof of Concept
1. In a repository, create a file `notes.txt` whose bytes are ASCII except for one line containing an invalid UTF-8 byte sequence (e.g., a lone `0xFF` byte or a Windows-1252-encoded non-ASCII character such as `0xE9` for "é") interspersed with normal ASCII lines elsewhere, so `git diff --numstat`/binary heuristics still treat it as text.
2. Commit this file as the repo's initial state.
3. Modify `notes.txt`: add two new lines — one ordinary ASCII line and one line adjacent/containing the invalid-UTF-8 byte content — in the same or different hunks.
4. In GitHub Desktop, open the Changes view, and use line-selection to stage only the ordinary ASCII line for commit (partial commit), leaving the invalid-byte line for a later commit.
5. Commit. Inspect the resulting blob with `git show HEAD:notes.txt | xxd`.
6. Observe that the invalid byte sequence originally in the working directory (if it fell inside a hunk that had to be reconstructed via `formatPatch`, e.g. as unselected/context line converted from `line.text`) has been replaced with the 3-byte UTF-8 replacement character sequence `EF BF BD`, differing from the original working-directory bytes — demonstrating silent corruption of committed content relative to what the user intended and what is on disk.
