### Title
Unchecked `u64` arithmetic overflow in `SignableTransaction::new` lets oversized payments bypass the not-enough-funds check and produce a consensus-invalid signed Bitcoin transaction - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The integer-overflow bug class from the Lua report maps onto `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`, which performs unchecked `u64` addition and multiplication over attacker-influenced payment amounts and fee values. An unprivileged party who can cause a payment of a near-`u64::MAX` amount to be signed makes `payment_sat` / `payment_sat + needed_fee` wrap, defeating the `NotEnoughFunds` guard and the change calculation, so the threshold signer emits a Schnorr signature over a transaction that is invalid under Bitcoin consensus (an output exceeding `MAX_MONEY`, or fee math inconsistent with `needed_fee`).

### Finding Description
`SignableTransaction::new` accumulates and compares satoshi values with plain `u64` arithmetic:

- `payment_sat` is a wrapping sum of every `payment.1` [1](#0-0) 
- `needed_fee = fee_per_vbyte * vbytes` and `fee_with_change = fee_per_vbyte * vbytes_with_change` are unchecked multiplications [2](#0-1) [3](#0-2) 
- The funds check `input_sat < (payment_sat + needed_fee)` uses unchecked addition [4](#0-3) 
- The change arm uses `input_sat.checked_sub(payment_sat + fee_with_change)` — the `checked_sub` is undermined because `payment_sat + fee_with_change` itself wraps before the subtraction [5](#0-4) 

With a single payment of `u64::MAX` (or two payments summing past `u64::MAX`), `payment_sat + needed_fee` wraps to a small value, so `input_sat < (payment_sat + needed_fee)` is false even though the real obligation vastly exceeds `input_sat`. The wrapped sum also makes `checked_sub` return `Some(input_sat - small)`, so a nearly-full-value change output is appended alongside the `u64::MAX` payment output. The resulting `Transaction` is then passed to the Schnorr sign machine and signed.

`fee()` later does `sum(prevouts) - sum(outputs)`, which underflows in release builds for such a transaction [6](#0-5) .

### Impact Explanation
The threshold set signs a message (transaction preimage) that does not represent a valid Bitcoin transaction: an output of `u64::MAX` sats exceeds Bitcoin's `MAX_MONEY`, so the signed transaction can never confirm. This is concrete signing of an unintended/invalid message — a waste of a preprocess (a signing round) and a liveness failure where the plan's expected spend is produced but permanently unbroadcastable, stalling the affected funds/plan. Where the overflow instead lands on `needed_fee` (`fee_per_vbyte * vbytes` wrap), the transaction is signed with a fee far below the intended/median rate, producing a transaction the network will not relay.

### Likelihood Explanation
Reachable whenever a party can get an arbitrary `u64` amount into the payments list of a `SignableTransaction` — e.g., by triggering a withdrawal/branch payment whose amount field they control. Within the full Serai processor, payment amounts are nominally bounded by real minted supply (which makes the `u64::MAX` single-payment case hard in practice), but the library boundary in scope does not enforce any `MAX_MONEY`/`input_sat` sanity bound and the overflow is silent in release builds, so any upstream caller that forwards unvalidated amounts or fee rates hits it directly. Medium severity: reliable arithmetic flaw on the signing path, but impact is limited to an invalid/under-funded signed transaction rather than key recovery or forgery.

### Recommendation
Use `checked_add`/`saturating_add` when accumulating `input_sat`, `payment_sat`, and `payment_sat + needed_fee`/`payment_sat + fee_with_change`, use `checked_mul` for `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change`, and reject any payment/output amount exceeding `bitcoin::Amount::MAX_MONEY` (and each `Amount::from_sat` construction) before building `tx_outs`. Make `fee()` use `checked_sub` so inconsistent states error rather than wrap.

// networks/bitcoin context; `input` is any legitimately scanned ReceivedOutput
// worth e.g. 100_000 sats, `change` any valid ScriptBuf.
let huge_payment = (p2tr_script_buf(some_key).unwrap(), u64::MAX);
let tx = SignableTransaction::new(
  vec![input],
  &[huge_payment],
  Some(change_addr),
  None,
  fee_per_vbyte, // small honest fee

// payment_sat + needed_fee wraps mod 2^64, so the NotEnoughFunds check at
// send.rs:215 does not fire; checked_sub at send.rs:228 sees the wrapped sum
// and produces a large change output.
let stx = tx.unwrap();
// stx.tx.output[0].value == Amount::from_sat(u64::MAX) -> > MAX_MONEY,
// consensus-invalid, yet proceeds to the FROST Schnorr sign machine and is
// signed. It can never be broadcast/confirmed.
