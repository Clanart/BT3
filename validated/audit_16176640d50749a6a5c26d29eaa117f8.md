### Title
Windows shell-metacharacter injection via cloned-repository directory name in `launch()` - ([File: app/src/lib/shells/win32.ts])

### Summary
`app/src/lib/shells/win32.ts`'s `launch()` builds Windows shell/terminal-launch command lines by string-interpolating the repository's local folder path into a single argument, wrapped only in double quotes, and then spawns it with `shell: true` (i.e. via `cmd.exe`). The local folder name is derived from the attacker-controlled repository/URL name, and none of the sanitization functions applied to that name (`sanitizeCloneName` in `app/src/lib/remote-parsing.ts`, `safeDirectoryName` in `app/src/ui/lib/repository-path.tsx`) strip `cmd.exe` metacharacters such as `&`, `|`, `^`, `%`, which are all legal in Windows file/directory names. This mirrors the egg-scripts bug class: untrusted input reaches a shell-interpreting exec/spawn call without metacharacter sanitization.

### Finding Description
When a repository is cloned, the destination directory name is computed from the parsed repository name: [1](#0-0) 

`sanitizeCloneName` only guards against path traversal and separators (`/`, `\`, `:`) — it performs no filtering of shell metacharacters. The similar `safeDirectoryName` helper used for other repository-path flows only strips characters that are illegal in Windows filenames (`<>:"|?*`), explicitly leaving characters such as `&`, `%`, `^`, `(`, `)` untouched: [2](#0-1) 

These characters are all valid in NTFS file/directory names but are `cmd.exe` command separators/metacharacters. Later, when the user performs the ordinary, expected action "Open in \<Shell\>" on that repository, `Dispatcher.openShell` → `AppStore._openShell` → `launchShell`/`win32.ts`'s `launch()` is invoked with the repository's `path`: [3](#0-2) [4](#0-3) 

`launch()` embeds `path` into a single command-line string, quoting only the path itself, and spawns via `cmd.exe` (`shell: true`): [5](#0-4) [6](#0-5) 

For example, for Alacritty: `spawn(alacrittyPath, [`--working-directory "${path}"`], { shell: true, cwd: path })`. When `child_process.spawn` runs with `shell: true` on Windows, Node.js invokes `cmd.exe /d /s /c "<command>"`. Because the quoting here only wraps the path in `"`s inside one argv element (not through Node's own array-based escaping), and `cmd.exe`'s well-documented outer-quote-stripping behavior for `/c "..."` strings can un-protect embedded metacharacters, a folder name containing `&`, `|`, or `^` can break out of the intended single argument and be interpreted as additional shell commands. This is exactly the invariant the codebase itself warns about elsewhere: `script/sh.ts` explicitly documents "Do not pass unsanitized user input to this function! Any input containing shell metacharacters may be used to trigger arbitrary command execution" for its own `shell: true` helper, but `win32.ts`'s `launch()` performs the same unsafe pattern with a value (the repo-derived directory name) that is not guaranteed to be free of those characters.

### Impact Explanation
If a victim clones an attacker-controlled repository (or repository named via a malicious/crafted GitHub API `name`/URL, e.g. `evil&calc.exe&rem .git`) using the default clone path (a very common, expected flow — most users accept the auto-populated local path), the resulting local folder name is not sanitized against shell metacharacters. When the victim later performs "Open in Shell"/"Open in \<Terminal\>" from Desktop's Repository menu or the repository list context menu — an entirely ordinary and expected interaction — an attacker-chosen command embedded in the folder name can be executed via `cmd.exe`. This is code execution outside of any git operation, driven purely by attacker-controlled content (the repository name), matching the report's class of "does not sanitize input before passing to a shell-interpreting exec call."

### Likelihood Explanation
Likelihood is moderate: it requires (1) the attacker to control the repository/URL name that becomes the clone folder name, (2) the victim to clone using the default (unmodified) local path, and (3) the victim to subsequently click "Open in Shell" for that specific repository — all of which are normal, expected Desktop workflows requiring no unusual steps, elevated privileges, or pre-existing compromise. This is Windows-only (`cmd.exe`/`shell: true` quoting), since POSIX shells launched by `app/src/lib/shells/linux.ts`/macOS do not use `shell: true`.

### Recommendation
- Avoid `shell: true` entirely in `app/src/lib/shells/win32.ts`'s `launch()`; pass `path` as a discrete array argument to `spawn` without shell interpretation wherever the target program supports it directly.
- Where a shell wrapper is unavoidable (e.g. `START`, PowerShell `-Command`), apply the project's existing dedicated escaping utilities (`app/src/lib/hooks/shell-escape.ts`'s `cmdEscape`) to any interpolated path before building the command string, instead of only wrapping in double quotes.
- Extend `sanitizeCloneName`/`safeDirectoryName` to also reject or replace `cmd.exe`/PowerShell metacharacters (`&`, `|`, `^`, `%`, `!`, `(`, `)`) in derived directory names, consistent with the emoji/illegal-character stripping already done in `sanitizedRepositoryName`.

### Proof of Concept
1. Attacker hosts (or renames) a Git repository so that its parsed name (via `parseRepositoryIdentifier`) resolves, after `sanitizeCloneName`, to something like `repo & calc.exe & rem`.
2. Victim clones this repository via GitHub Desktop's Clone dialog using the default/auto-populated local path (`Path.join(basePath, safeName)`), producing a local directory literally named `repo & calc.exe & rem`.
3. Victim right-clicks the repository (or uses the Repository menu) and selects "Open in \<Shell\>" (`open-in-shell` menu event → `dispatcher.openShell(repository.path)`).
4. `win32.ts`'s `launch()` builds a `cmd.exe`-interpreted command line embedding the unescaped path, causing the injected `calc.exe` (or attacker's payload) to execute in place of / alongside the intended shell launch command.

```typescript
export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
```
