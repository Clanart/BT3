### Title
Unauthenticated OP_RETURN operator attribution in payout tx lets anyone assign reimbursement credit to an operator who never funded the withdrawal - (File: `core/src/builder/transaction/operator_reimburse.rs`, `core/src/operator.rs`)

### Summary
The payout transaction's OP_RETURN field (which names the operator entitled to reimbursement) is not signed or otherwise cryptographically bound to whoever actually supplies the funding input(s) for the payout output. Because the withdrawing user signs with `SinglePlusAnyoneCanPay`, which only commits to input/output index 0, anyone constructing and broadcasting the final transaction can freely set the OP_RETURN to name any operator's `xonly_pk`, regardless of who paid.

### Finding Description
The claimed binding is:
`payout_op_xonly_pk (parsed from OP_RETURN)` == `kickoff_data.operator_xonly_pk` **AND** == `xonly_pk of whoever funded payout output 0`.

`send_asserts` enforces only the first equality, by comparing the DB-stored `payout_op_xonly_pk` (populated from parsing the real, confirmed payout tx's OP_RETURN by `update_finalized_payouts`, `core/src/verifier.rs:2283-2352`) against `kickoff_data.operator_xonly_pk`: [1](#0-0) 

The OP_RETURN itself is created in `create_payout_txhandler` as a plain, unsigned output: [2](#0-1) 

The only input to this transaction is the registered withdrawal UTXO, signed by the withdrawing user with `TapSighashType::SinglePlusAnyoneCanPay`: [3](#0-2) 

`SIGHASH_SINGLE` only commits the signer to output index 0 (the user payout output) matching input index 0; `ANYONECANPAY` means additional funding inputs can be freely appended by whoever finishes and broadcasts the transaction. The anchor output and the OP_RETURN (outputs 1 and 2) are **not covered** by this signature at all. `Operator::withdraw` (`core/src/operator.rs:560-691`) only verifies that `in_outpoint == withdrawal_utxo` (the Citrea-registered outpoint) and that the user's signature is valid for that outpoint/output 0 — it never checks who supplies the extra funding inputs added by `fund_raw_transaction`, nor does anything bind the OP_RETURN's identity to the funder: [4](#0-3) [5](#0-4) 

Because `SIGHASH_SINGLE|ANYONECANPAY` and the OP_RETURN's malleability allow anyone (including the withdrawing user themselves, who legitimately controls the withdrawal UTXO's key and signature per the attacker capability list) to build and directly broadcast this transaction to Bitcoin — bypassing `Operator::withdraw`'s gRPC entirely — an attacker can construct a payout tx that: (1) spends the registered withdrawal UTXO with a valid signature they hold, (2) funds any shortfall with their own additional input(s), and (3) sets the OP_RETURN's xonly_pk to an arbitrary operator's key (e.g., `operator0.xonly_pk`).

Once mined, `update_finalized_payouts` parses this OP_RETURN and stores `operator_xonly_pk = operator0` against this payout in the DB: [6](#0-5) 

`operator0`'s own `PayoutCheckerTask` polls for unhandled payouts filtered by its own `xonly_public_key` (not by whether it actually funded the payout): [7](#0-6) 
and unconditionally calls `handle_finalized_payout`, which queues the kickoff and eventually drives `send_asserts`, whose only guard is the DB-vs-kickoff-data equality that was engineered by the attacker to match: [8](#0-7) 

`is_kickoff_malicious` (verifier side) exhibits the identical gap — it only compares `operator_xonly_pk != kickoff_data.operator_xonly_pk`, never checking who funded the payout: [9](#0-8) 

### Impact Explanation
`operator0` (an honest, uninvolved operator) is driven into performing kickoff/assert/eventually Reimburse for a withdrawal it never funded, and the bridge's Reimburse mechanism credits `operator0` with `bridge_amount` from vault-backed funds for work it did not do, while the actual funder of the payout output (the attacker) is never reconciled with the bridge accounting. This matches the Critical category "an operator reimbursed for a payout it never funded." It is repeatable per-withdrawal and can target any registered operator merely by writing their known public `xonly_pk` into the OP_RETURN; the attack requires no interaction with any operator's or verifier's private infrastructure, since the whole transaction can be built and broadcast directly to the Bitcoin network by the attacker.

### Likelihood Explanation
Preconditions are minimal and squarely within the stated attacker capabilities: the attacker must be the party requesting/holding a valid withdrawal (own the withdrawal UTXO's key, control the `SinglePlusAnyoneCanPay` signature and any additional funding UTXO), which is normal, unprivileged user behavior. No verifier/operator collusion, no majority hashrate, and no TLS/gRPC access is required — the attacker can build and submit the raw transaction directly via Bitcoin RPC/P2P. Cost is only the withdrawal amount plus fees the attacker would pay regardless of who is named in OP_RETURN.

### Recommendation
Bind the OP_RETURN operator attribution to the actual funding party cryptographically, e.g., require the operator's own signature (or a MuSig2/N-of-N commitment) over the full payout transaction (including OP_RETURN and all inputs), or have `send_asserts`/`is_kickoff_malicious`/`update_finalized_payouts` verify that at least one transaction input's scriptPubkey key-spend corresponds to `kickoff_data.operator_xonly_pk`, rather than trusting an unsigned OP_RETURN byte string as proof of who funded the payout.

### Proof of Concept
In `core/src/test/manual_reimbursement.rs`, add a test that:
1. Runs a deposit and registers a withdrawal (`insert_withdrawal_utxo`) exactly as in `generate_withdrawal_transaction_and_signature`, but do **not** call `operator0.withdraw`.
2. Manually build a `create_payout_txhandler`-equivalent transaction spending the withdrawal dust UTXO with the user's own `SinglePlusAnyoneCanPay` signature, add a second input funded from a locally-controlled (non-operator) key to cover `out_amount`, and set the OP_RETURN payload to `operator0.xonly_pk.serialize()`.
3. Broadcast this transaction directly via the regtest RPC (bypassing `Operator::withdraw`) and mine to finality.
4. Assert that `update_finalized_payouts`/DB sync stores `payout_op_xonly_pk == operator0.xonly_pk` for this payout even though `operator0` never signed or funded it (assert no operator-controlled UTXO appears among the tx's inputs).
5. Trigger `operator0`'s `PayoutCheckerTask`/`send_asserts` flow and assert it proceeds without error (`payout_op_xonly_pk == kickoff_data.operator_xonly_pk` passes) despite `operator0` never having funded output 0, demonstrating the missing binding to the actual funding key.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

fn sign_withdrawal_output(
    config: &BridgeConfig,
    dust_utxo: &UTXO,
    withdrawal_address: &bitcoin::Address,
    withdrawal_amount: bitcoin::Amount,
) -> (bitcoin::TxOut, taproot::Signature) {
    let signer = Actor::new(config.secret_key, config.protocol_paramset().network);
    let txin = builder::transaction::input::SpendableTxIn::new(
        dust_utxo.outpoint,
        dust_utxo.txout.clone(),
        vec![],
        None,
    );
    let txout = bitcoin::TxOut {
        value: withdrawal_amount,
        script_pubkey: withdrawal_address.script_pubkey(),
    };
    let unspent_txout = builder::transaction::output::UnspentTxOut::from_partial(txout.clone());

    let tx = builder::transaction::TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            builder::transaction::DEFAULT_SEQUENCE,
        )
        .add_output(unspent_txout.clone())
        .finalize();

    let sighash = tx
        .calculate_sighash_txin(0, sighash::TapSighashType::SinglePlusAnyoneCanPay)
        .expect("Failed to calculate sighash");

    let sig = signer
        .sign_with_tweak_data(sighash, builder::sighash::TapTweakData::KeyPath(None), None)
        .expect("Failed to sign");

    let sig = taproot::Signature {
        signature: sig,
        sighash_type: sighash::TapSighashType::SinglePlusAnyoneCanPay,
    };

    (txout, sig)
}
