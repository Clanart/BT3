## Title
Missing length validation on `message.from` in `on_accept` substrate branch causes panic-based DoS - (`modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
In the `on_accept` handler of the `hyper-fungible-token` pallet's `IsmpModule` implementation, when a `PostRequest` carries non-empty `message.data` with no `signature` field, and the request `source` is a non-EVM (substrate) chain, the code copies `message.from` into a fixed 32-byte buffer using `account.copy_from_slice(from_bytes)` without first validating that `from_bytes.len() == 32`. [1](#0-0) 

### Finding Description
`message.from` is a field of the ABI-decoded `Message` body, which is fully attacker-controlled data supplied by whoever constructs the cross-chain message on the source chain (bounded only by the arbitrary-length `bytes` ABI type). The pallet does validate `message.to` earlier with explicit length checks and typed errors: [2](#0-1) 

The `on_timeout` handler applies the same defensive pattern to `message.from`, explicitly checking for 32-byte or 20-byte lengths and returning `HftError::InvalidSenderLength` otherwise: [3](#0-2) 

However, in `on_accept`'s "no signature" branch for non-EVM sources, no equivalent guard exists before `account.copy_from_slice(from_bytes)`: [4](#0-3) 

`copy_from_slice` panics if the source and destination slice lengths differ. Since `from_bytes.len()` can be any value other than 32 (e.g., 0, 19, or 33 bytes), an attacker who controls the encoded `Message` body can trigger a Rust panic during extrinsic execution instead of a graceful, typed `HftError`.

### Impact Explanation
A panic during on-chain message processing (inside `on_accept`, invoked from the ISMP handler when processing an incoming `PostRequest`) is a logic/availability defect: rather than failing gracefully with `HftError` (which the runtime can catch as a dispatch error and revert state), an unhandled panic in a pallet call can abort block execution or extrinsic application in an uncontrolled way. This breaks the intended invariant — enforced everywhere else in this same file (`to_bytes`, and `from_bytes` in `on_timeout`) — that all attacker-supplied byte fields must be length-checked before fixed-size buffer operations. This is a genuine code defect, though its ultimate severity depends on how the runtime's executive/dispatch layer handles a panic inside `on_accept` (i.e., whether it aborts just the extrinsic or the whole block), which could not be fully confirmed from the pallet code alone.

### Likelihood Explanation
High: reaching this panic requires only that (1) `source.is_evm()` is false (a supported, non-privileged path — any registered substrate source chain), (2) `message.data` is non-empty, and (3) `substrate_data.signature` is `None`. Given that `message.from` originates from attacker-supplied ABI-encoded bytes, no privileged access is needed to construct a malformed `from` field.

### Recommendation
Apply the same length validation used for `to_bytes` (lines 65-71) and for `from_bytes` in `on_timeout` (lines 226-232) to the `from_bytes` used in `on_accept`'s no-signature substrate branch — checking `from_bytes.len() == 32` (or accepting 20 bytes with left-padding, consistent with the rest of the codebase) and returning a typed `HftError` (e.g., a new `HftError::InvalidSenderLength` reuse) instead of calling `copy_from_slice` unconditionally.

### Proof of Concept
Construct a `PostRequest` where `source` is a non-EVM `StateMachine`, `body` ABI-encodes a `Message` with non-empty `data` (a valid `SubstrateCalldata` with `signature: None`) and `from` set to a byte slice of length 5 (or 0, or 33). Call `Pallet::<T>::on_accept` with this request in a unit test; the call panics at `account.copy_from_slice(from_bytes)` (module.rs:184) instead of returning `Err(HftError::InvalidSenderLength(..))`.
