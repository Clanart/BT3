### Title
Cached FROST preprocess is never expired — repeated signing under one context reuses nonces and leaks the validator MuSig secret share - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
`SigningProtocol::preprocess_internal` stores a deterministic preprocess seed in `CachedPreprocesses` keyed only by `context` (`(b"DkgConfirmer", attempt)`), and every subsequent `share_internal`/`preprocess`/`complete` call for that context reconstructs the *same* sign machine via `AlgorithmSignMachine::from_cache`, regenerating identical FROST nonces. The cached "session" is never invalidated or rotated after a share is produced. If a second share is ever produced under the same context over a different message or different peer-preprocess set, the nonces are reused across two Schnorr equations, allowing recovery of the validator's MuSig private key share — the root-of-trust key used to confirm DKGs on Substrate. The file's own header acknowledges nonce reuse leaks the key, relies on BFT finality for safety, and notes the needed "on-chain commitments match presumed nonces" check is still a `TODO`.

### Finding Description
- `CachedPreprocesses` maps `context -> [u8; 32]` seed; the entry is created once (`is_none()` guard) and then read forever — it is never deleted or refreshed after `share_internal` produces a signature share. See `signing_protocol.rs` lines 123–145.
- `share_internal` calls `preprocess_internal`, so *every* call to `DkgConfirmer::share` and `DkgConfirmer::complete` (which internally calls `share_internal` again, line 322) rebuilds nonces from the same seed via `seeded_preprocess` (`crypto/frost/src/sign.rs` lines 121–144: `ChaCha20Rng::from_seed(*seed.0)` → identical `d, e`).
- `generated_key_pair` (`coordinator/src/tributary/handle.rs` lines 47–60) stores the `key_pair` with `DkgKeyPair::set` (an overwrite, not insert-once) and calls `share(...)`. Nothing prevents this path being executed twice for the same `attempt` with a *different* `key_pair`, producing a second share `s2 = d + ρ₂e + c₂·x` over a different `msg` while reusing `d, e`. Since `msg` enters the MuSig/Schnorrkel challenge (`set_keys_message` → `sign_share` → `hram`), `c₁ ≠ c₂` and the share `x` (the validator's MuSig secret key) is recovered as `(s₁ − s₂ − (ρ₁−ρ₂)e …)/(c₁ − c₂)`; with the same peer preprocess set, `s₁ − s₂ = (c₁ − c₂)·x` directly.
- Likewise, `complete()` re-executes `share_internal` with whatever `preprocesses`/`key_pair` are in the DB at that point; any divergence from the values used in the earlier `share` call yields a second distinct share under identical nonces.
- The safety argument in the file header (lines 25–48) explicitly concedes that re-execution with distinct received messages causes nonce reuse, and the mitigating check ("check the commitments generated from the decided nonces are in fact its commitments on-chain") is marked `(TODO)` — i.e., the "old session" remains valid with no expiry/verification, mirroring the CVE class (credentials/sessions not invalidated on re-use).

### Impact Explanation
Nonce reuse in Schnorr-family signatures is catastrophic: two shares over the same `(d, e)` nonces with different challenges linearly reveal the signer's secret share. Here that secret is the coordinator validator's MuSig key — the root of trust authorizing `set_keys` on Substrate, which installs the FROST group keys controlling all bridged funds. Recovery of this key lets an attacker forge validator signatures on key-setting and vote messages. This is a key-share recovery primitive reachable through protocol messages (key-pair reports / preprocess sets an unprivileged party can cause to differ), not merely a DoS.

### Likelihood Explanation
Triggering requires the same `attempt` context to sign twice with differing inputs. The most plausible routes: (a) `generated_key_pair` invoked a second time with a distinct `KeyPair` for the same attempt (the DB `set` permits overwrite and there is no completed/already-shared guard analogous to `AttemptDb`/`CompletedDb` used by the processor signers); (b) `complete()` re-deriving a share after `share()` when `ConfirmationNonces` or `removed`/`key_pair` state diverged between the two executions. The code's own comments admit the nonce-reuse hazard and that the consistency check is unimplemented, and the processor-side signers (`signer.rs`, `batch_signer.rs`) use `AttemptDb` guards precisely because reboots/re-execution are expected — the DKG confirmer lacks an equivalent "already shared" guard.

### Recommendation
- Delete or rotate `CachedPreprocesses` once a share has been produced for a context (write a tombstone), so `from_cache` can never rebuild the same nonces twice.
- Record the exact `(preprocesses hash, msg)` the share was produced over and refuse (or return the identical share) for any subsequent request under the same context — implementing the TODO's on-chain-commitment-matches-presumed check.
- Make `DkgKeyPair::set` insert-once for a given `(genesis, attempt)` so a second distinct `key_pair` cannot reach `share()`.

### Proof of Concept
1. Attempt `a` of the DKG for `spec` begins; `DkgConfirmer::new(key, spec, txn, a)` yields context `(b"DkgConfirmer", a)`. `preprocess()`/`share()` populate `CachedPreprocesses` and emit share `s₁` over `msg₁ = set_keys_message(set, removed, key_pair₁)`.
2. `generated_key_pair` is invoked again for the same `a` with `key_pair₂ ≠ key_pair₁` (`DkgKeyPair::set` overwrites silently). `share()` → `preprocess_internal` loads the *same* seed → same nonces `d, e` → emits `s₂` over `msg₂`.
3. Both shares are public on the tributary (`DkgConfirmed` / processor messages). With identical peer preprocesses, `x = (s₁ − s₂)·(c₁ − c₂)⁻¹` recovers the validator's MuSig secret; with differing peer preprocesses the standard two-nonce-reuse linear system still yields it.
4. The recovered key forges subsequent `set_keys`/vote signatures under the validator's identity.
