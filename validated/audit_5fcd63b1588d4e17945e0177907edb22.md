### Title
Path-prefix bypass in `resolveWithin()` allows escaping the intended repository root via sibling-directory names - ([File: app/src/lib/path.ts])

### Summary
The bug report's core defect is a boundary-check flaw: a comparison omits the exact-boundary case (`<` instead of `<=`), letting an attacker-influenced value slip past a guard that was meant to be authoritative. `_resolveWithin()` in `app/src/lib/path.ts` has the same class of flaw: it validates that a resolved path is "underneath the root" using a raw string `startsWith()` check with no path-separator boundary, so a sibling directory whose name happens to share the root path as a string prefix passes the check even though it is not actually contained within the root.

### Finding Description
`resolveWithin()` (and its `Posix`/`Win32` variants) is the app's designated guard for keeping attacker-influenced relative paths confined to a trusted root directory: [1](#0-0) 

The final check is:
```js
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`String.prototype.startsWith` performs a raw character-prefix comparison with no notion of path-segment boundaries. If `realRoot` is e.g. `/Users/victim/Documents/GitHub/repo` and the resolved candidate is `/Users/victim/Documents/GitHub/repo-secrets/config.json`, the check returns `true` even though `repo-secrets` is a completely different, sibling directory — not a subdirectory of `repo`. This is functionally identical to the report's broken invariant: the check silently accepts a value that sits exactly on/adjacent to the intended boundary and should have been rejected, because the guard is written without the extra condition needed to make the boundary strict (here, requiring a trailing separator character after `realRoot`, analogous to requiring `<=` instead of bare `<`).

This helper is used to validate the `filepath` parameter of the `x-github-client://openrepo` deep link, an attacker-controlled value delivered via a link the user clicks: [3](#0-2) 

The deep-link URL itself is parsed with only light validation (querystring extraction, branch/PR regex checks) — `filepath` is passed through essentially unchecked except for an absolute-path rejection: [4](#0-3) 

So the only thing standing between the attacker-supplied `filepath` and the filesystem is `resolveWithin(repository.path, filepath)`. Because `GitHub Desktop`'s default clone root (e.g. `~/Documents/GitHub/`) commonly holds multiple repositories side-by-side, and the current logged-in repository's name is very often a substring/prefix of other repos or folders in the same parent directory (forks, renamed clones, `repo`, `repo-backup`, `repo-old`, `repo.wiki`, etc.), an attacker who knows or guesses the victim's currently-open repository path can craft a `filepath` such as `../<sibling-dir-that-prefixes-root>/secret-file` that resolves outside the intended repository yet still passes the `startsWith` check.

### Impact Explanation
On success, `shell.showItemInFolder(resolved)` is invoked on the escaped path: [5](#0-4) 

This reveals/opens file-system content outside the boundary the guard is supposed to enforce (files belonging to a different, unrelated local repository or directory), i.e. a read/disclosure primitive triggered purely by the victim clicking an attacker-supplied deep link — matching the "file read... outside the repo" impact class named in the task's valid-impact list. The same `resolveWithin` primitive is reused elsewhere (`app/src/lib/stores/app-store.ts`, `app/src/lib/copilot-conflict-context.ts`), so any other caller relying on it for containment inherits the same weakness.

### Likelihood Explanation
Exploitation requires: (1) the victim to click/open an `x-github-client://openrepo?...&filepath=...` deep link, and (2) a filesystem layout where a sibling directory's name shares the repository root path as a string prefix. Condition (2) is common in practice because Desktop's default clone location groups all of a user's repos under one folder, and repo names frequently collide as prefixes (`repo` vs `repo2`, `repo-fork`, `repo.wiki`, case variants, etc.), or an attacker who previously got the victim to clone a maliciously-named repo can set this up deterministically. No local/physical access, admin rights, or leaked credentials are needed — only a link click, which matches the "link or deep link the user clicks" attacker model.

### Recommendation
Fix the boundary check to require a path-separator boundary (or exact equality) rather than a raw string prefix, e.g.:
```js
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the report's recommended fix pattern (correcting the comparison so the exact boundary is handled explicitly instead of being silently accepted/rejected by an imprecise operator).

### Proof of Concept
1. Victim has GitHub Desktop open with a repository cloned at `/Users/victim/Documents/GitHub/repo`.
2. A sibling directory exists at `/Users/victim/Documents/GitHub/repo-secrets` (e.g., another cloned repo, or one created by a previous malicious clone the attacker induced).
3. Attacker sends the victim a link:
   `x-github-client://openrepo?url=<repo-url>&filepath=..%2Frepo-secrets%2Fcredentials.json`
4. `parseAppURL` accepts `filepath` since it isn't absolute and contains no disallowed characters: [6](#0-5) 
5. `dispatcher.openRepositoryFromUrl` calls `resolveWithin('/Users/victim/Documents/GitHub/repo', '../repo-secrets/credentials.json')`.
6. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/Documents/GitHub/repo-secrets/credentials.json`; `realResolved.startsWith(realRoot)` evaluates `'/Users/victim/Documents/GitHub/repo-secrets/credentials.json'.startsWith('/Users/victim/Documents/GitHub/repo')`, which is `true` due to the missing separator check. [7](#0-6) 
7. The guard returns the escaped path as "resolved", and `shell.showItemInFolder(resolved)` reveals the unrelated file to the attacker-directed flow. [8](#0-7)
