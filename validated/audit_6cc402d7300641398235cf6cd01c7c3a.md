### Title
Verifier accepts `ReplacementDeposit` funded by a self-created UTXO with no proof the referenced `old_move_txid` vault was ever spent by the security council - (File: `core/src/verifier.rs`, `core/src/deposit.rs`)

### Summary
`Verifier::is_deposit_valid` and `DepositData::get_deposit_scripts` only check that the `deposit_outpoint`'s on-chain scriptPubKey matches the taproot template `ReplacementDepositScript(nofn_pk, old_move_txid) + Multisig(security_council)` and that its value equals `bridge_amount`. Neither function verifies that this UTXO was actually produced by a security-council-authorized spend of the real `old_move_txid` vault output; it only verifies the *shape* of the destination script, which any unprivileged party can reproduce because `security_council.pks` are public configuration values, not secrets.

### Finding Description
The binding that should hold is: `deposit_outpoint` funding the `ReplacementDeposit` == the actual UTXO produced by a security-council-signed spend of `old_move_txid`'s vault output (i.e. provenance of funds, not just destination-script equality).

`is_deposit_valid` (`core/src/verifier.rs:541-731`) implements this binding incorrectly:
- It compares `deposit_data.security_council` byte-for-byte with `self.config.security_council` (`core/src/verifier.rs:543-551`). Since `SecurityCouncil{pks, threshold}` contains only public keys, any depositor can trivially supply a struct that is byte-identical to the verifier's config — this is public information, not evidence of council control.
- It then computes `expected_scriptpubkey` from `deposit_data.get_deposit_scripts(...)` (`core/src/deposit.rs:206-217`), which for `DepositType::ReplacementDeposit` builds exactly `[ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid), Multisig::from_security_council(security_council)]` (`core/src/deposit.rs:207-216`).
- It fetches the actual on-chain tx at `deposit_outpoint` and checks only `value == bridge_amount` and `script_pubkey == expected_scriptpubkey` (`core/src/verifier.rs:688-705`), plus a block-height floor (`core/src/verifier.rs:706-730`).

At no point does the code check:
1. That `old_move_txid` is a `Txid` this bridge actually produced via `create_move_to_vault_txhandler` for some prior deposit, or
2. That the funding transaction of `deposit_outpoint` actually spends the output at `old_move_txid`'s vault (`UtxoVout::DepositInMove`) through the `CheckSig(old_nofn)+Multisig(security_council)` script path (the only path that requires genuine security-council signatures, per `create_replacement_deposit_txhandler`, `core/src/builder/transaction/mod.rs:404-446`).

Because `Multisig` is built purely from public keys (`Multisig::from_security_council`), an attacker with no security-council key share can construct the identical taproot address off-chain via `generate_replacement_deposit_address` (`core/src/builder/address.rs:89-103`), fund it directly from their own wallet with exactly `bridge_amount`, pick an arbitrary or even a real, unrelated `old_move_txid`, and submit it via the aggregator's public `new_deposit` gRPC call. `is_deposit_valid` will accept it, and verifiers will proceed to `deposit_sign`/`deposit_finalize` and co-sign the `move_to_vault_tx` that spends this attacker-funded UTXO into a fresh N-of-N vault (`core/src/builder/transaction/mod.rs:306-344`), exactly as it would for a legitimate remediation.

### Impact Explanation
This repo-level flaw allows an unprivileged attacker to obtain verifier co-signatures over a `ReplacementDeposit` that carries a fabricated (or misappropriated) `old_move_txid` binding, without ever needing security-council key material or performing the intended remediation spend. The resulting `move_to_vault_tx` moves only the attacker's own self-funded BTC into a new N-of-N vault — the attacker does not directly seize bridge funds through this repo's tx-signing path. However, the on-chain artifact this produces (a valid move-to-vault transaction whose predecessor commits to a chosen `old_move_txid`) is exactly what `register_replacement_deposit_to_citrea`/`replaceDeposit` (on the Citrea side) is later fed as proof of a legitimate replacement for a given `deposit_id`. Since this repo never verifies the provenance of the `old_move_txid` vault spend, it cannot prevent a real `old_move_txid` (pointing to a genuine, already-bridged deposit) from being cited by an attacker-created decoy vault. If the downstream Citrea `replaceDeposit` logic similarly trusts script-shape matching over spend-provenance verification, this repo-level gap is the entry point that lets an unprivileged party get verifiers to co-sign the transaction needed to hijack a `deposit_id`'s tracked vault, orphaning the real move-to-vault UTXO (a move-to-vault UTXO permanently frozen from the perspective of the honest depositor).

That said, I could not fully verify within this repo whether `replaceDeposit`/the Citrea contract's `deposit_id` reassignment logic performs any additional binding check (e.g., requiring the SPV-proven input side of the replacement tx to actually spend the recorded prior vault outpoint) that would block the ledger-level hijack — that logic lives in the Citrea smart contract, which is out of scope for this repo's audit, and I found no code in this repository that re-derives or checks the input-side provenance before or after `is_deposit_valid`.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only (a) the protocol's public `security_council` configuration (already public, part of `BridgeConfig`), (b) knowledge of a target `old_move_txid` (any move-to-vault txid is public on-chain), and (c) enough BTC to fund exactly `bridge_amount` to a taproot address they can compute themselves with public tools (`generate_replacement_deposit_address`), plus fees. No verifier, operator, or security-council collusion is required. The attack is repeatable for every deposit amount/paramset and every `old_move_txid` the attacker chooses to reference, since `is_deposit_valid` performs the same script/amount/height checks regardless of which `old_move_txid` is supplied.

### Recommendation
`is_deposit_valid` (or `get_deposit_scripts`) must verify the provenance of the `ReplacementDeposit` funding transaction, not merely its destination script shape. Specifically:
- Require that `old_move_txid` correspond to a move-to-vault transaction already known to this bridge (e.g., present in the verifier's DB as a completed deposit), and
- Require proof (e.g., by fetching and checking the funding transaction's input) that `deposit_outpoint`'s funding transaction actually spends `old_move_txid`'s vault output (`UtxoVout::DepositInMove`) via the `CheckSig(old_nofn)+Multisig(security_council)` script path with a valid security-council witness — not just that the resulting output's scriptPubKey matches a template that anyone can reproduce with public keys.
- Additionally enforce a DB-level uniqueness constraint so a given `old_move_txid` can only be replaced once, preventing repeated hijack attempts against the same deposit.
