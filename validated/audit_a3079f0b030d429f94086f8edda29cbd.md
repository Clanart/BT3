### Title
IBC Callback middleware allows any account to forge `onPacketAcknowledgement`/`onPacketTimeout` invocations on arbitrary contracts, enabling confused-deputy fund release - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
The `LeverageStrategy.receiveFlashLoan` bug (attacker-triggerable callback with no check that the contract itself initiated the flow) has a direct analog in the Cosmos EVM IBC-Callbacks module. `ContractKeeper.IBCSendPacketCallback` — the hook meant to authorize *which* address may register itself as an EVM contract's IBC callback target — is a no-op that unconditionally returns `nil`, and nothing downstream verifies that the `contractAddress` named in a packet's `src_callback` memo is actually owned/authorized by the account sending that packet. As a result, `IBCOnAcknowledgementPacketCallback` and `IBCOnTimeoutPacketCallback` will invoke `onPacketAcknowledgement`/`onPacketTimeout` on *any* deployed contract using attacker-controlled packet metadata, without that contract ever having sent (or consented to) the underlying packet.

### Finding Description
`x/ibc/callbacks/keeper/keeper.go` implements the `callbacktypes.ContractKeeper` interface consumed by ibc-go's callbacks middleware. The send-side authorization hook is explicitly stubbed out: [1](#0-0) 

The accompanying comment states this is intentional: *"This callback is currently not supported and always returns nil... contracts can implement custom logic before the send packet operation is called, making this callback redundant."* This pushes the entire authorization burden onto the callback-receiving contract — exactly the design flaw the external report describes: a callback surface trusts its caller-supplied context (`contractAddress`, `packetSenderAddress`, `data`) instead of verifying the flow was self-initiated.

On the ack/timeout path, the contract address and packet fields passed into the EVM call originate purely from the *sender's own* ICS-20 transfer memo (`src_callback.address`), which any account can set to reference someone else's already-deployed contract: [2](#0-1) 

Similarly for timeouts: [3](#0-2) 

Neither function checks that `contractAddress` was actually the sender of the referenced packet, nor that the contract ever agreed to receive callbacks tied to that `channelId`/`portId`/`sequence`. The only invariant enforced is that "the IBC module" is the caller of the resulting EVM message (as documented in `precompiles/callbacks/README.md`), which mirrors the flash loan bug's insufficient `msg.sender == flashLoanModule` check — the missing piece is validating that the *specific action being replayed* was legitimately initiated by the target itself.

### Impact Explanation
Any unprivileged user can craft their own outbound ICS-20 transfer with a `memo.src_callback.address` field pointing at a victim contract that implements `ICallbacks` (per `contracts/solidity/precompiles/callbacks/ICallbacks.sol`). When that attacker's own packet is acknowledged or times out, the victim contract's `onPacketAcknowledgement`/`onPacketTimeout` entrypoint is invoked with attacker-chosen `channelId`, `portId`, `sequence`, `data`, and (for acks) acknowledgement bytes — none of which correspond to any packet the victim contract actually sent. If the victim contract uses these callbacks to gate fund release, escrow accounting, or cross-chain swap completion (the exact use case the module's own README recommends), an attacker can spoof successful/failed delivery of a transfer the victim never made, causing unauthorized release/duplication of escrowed or contract-held value — matching the "Critical unauthorized extraction/duplication of escrowed assets" impact class.

### Likelihood Explanation
High: triggering the flow requires only sending a standard ICS-20 transfer with a crafted memo — no special privileges, relayer collusion, or validator control needed. The vulnerable authorization hook (`IBCSendPacketCallback`) is unconditionally a no-op for every transfer, so exploitation is always reachable whenever any contract on the destination/source chain implements the `ICallbacks` interface and relies on the callback's authenticity.

### Recommendation
Implement `IBCSendPacketCallback` to validate that `contractAddress` corresponds to `packetSenderAddress` (i.e., only a contract can register itself, not an arbitrary third party), and/or have `IBCOnAcknowledgementPacketCallback`/`IBCOnTimeoutPacketCallback` persist and check a store record created at send-time proving the named contract actually authorized/originated that specific `channelId/portId/sequence`, analogous to setting a `performingFlashLoan`-style flag before the async callback and validating it on receipt.

### Proof of Concept
1. Attacker deploys no special contract; attacker sends a standard `MsgTransfer` (ICS-20) with `memo = {"src_callback": {"address": "<victim_contract>", "gas_limit": "1000000"}}`.
2. Attacker intentionally causes the packet to time out (e.g., sends to a non-existent/unreachable channel) or lets it get acknowledged.
3. `IBCOnTimeoutPacketCallback`/`IBCOnAcknowledgementPacketCallback` in `x/ibc/callbacks/keeper/keeper.go` fires and calls `victim_contract.onPacketTimeout(sourceChannel, sourcePort, sequence, packetData)` using the attacker's own packet's channel/port/sequence/data — `victim_contract` never sent this packet nor consented to being named.
4. If `victim_contract`'s callback logic assumes "I only get called for packets I sent" (e.g., unlocking escrowed funds tied to a sequence number, marking a cross-chain swap as failed/refundable), the attacker can drive that logic into an inconsistent state to extract or duplicate value.

```go
func (k ContractKeeper) IBCOnAcknowledgementPacketCallback(
	ctx sdk.Context,
	packet channeltypes.Packet,
	acknowledgement []byte,
	relayer sdk.AccAddress,
	contractAddress,
	packetSenderAddress string,
	version string,
) error {
	data, err := transfertypes.UnmarshalPacketData(packet.GetData(), version, "")
	if err != nil {
		return err
	}

	cbData, isCbPacket, err := callbacktypes.GetCallbackData(data, version, packet.GetDestPort(), ctx.GasMeter().GasRemaining(), ctx.GasMeter().GasRemaining(), callbacktypes.SourceCallbackKey)
	if err != nil {
		return err
	}
	if !isCbPacket {
		return nil
	}

	// `ProcessCallback` in IBC-Go overrides the infinite gas meter with a basic gas meter,
	// so we need to generate a new infinite gas meter to run the EVM executions on.
	// Skipping this causes the EVM gas estimation function to deplete all Cosmos gas.
	// We re-add the actual EVM call gas used to the original context after the call is complete
	// with the gas retrieved from the EVM message result.
	cachedCtx, writeFn := ctx.CacheContext()
	cachedCtx = evmante.BuildEvmExecutionCtx(cachedCtx).
		WithGasMeter(evmtypes.NewInfiniteGasMeterWithLimit(cbData.CommitGasLimit))

	if len(cbData.Calldata) != 0 {
		return errorsmod.Wrap(types.ErrInvalidCalldata, "acknowledgement callback data should not contain calldata")
	}

	sender, err := utils.HexAddressFromBech32String(packetSenderAddress)
	if err != nil {
		return errorsmod.Wrapf(err, "unable to parse packet sender address %s", packetSenderAddress)
	}

	contractAddr := common.HexToAddress(contractAddress)

	// Check if the contract address contains code.
	// This check is required because if there is no code, the call will still pass on the EVM side,
	// but it will ignore the calldata and funds may get stuck.
	if !k.evmKeeper.IsContract(ctx, contractAddr) {
		return errorsmod.Wrapf(types.ErrCallbackFailed, "provided contract address is not a contract: %s", contractAddr)
	}

	abi, err := callbacksabi.LoadABI()
	if err != nil {
		return err
	}

	// Call the onPacketAcknowledgement function in the contract
	// NOTE: use the cached ctx for the EVM calls.
	res, err := k.evmKeeper.CallEVM(cachedCtx, *abi, sender, contractAddr, true, math.NewIntFromUint64(cachedCtx.GasMeter().GasRemaining()).BigInt(), "onPacketAcknowledgement",
		packet.GetSourceChannel(), packet.GetSourcePort(), packet.GetSequence(), packet.GetData(), acknowledgement)
	if err != nil {
		return errorsmod.Wrapf(types.ErrCallbackFailed, "EVM returned error: %s", err.Error())
	}
```
