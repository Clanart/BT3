### Title
Ed448 accepts low-order points as prime-group elements, enabling forged Schnorr proofs and signatures - (File: crypto/ed448/src/point.rs)

### Summary
`Point::is_torsion_free` always returns true because it computes `(-1 * P) + P`, which is the identity for every curve point. Consequently, `Point::from_bytes` accepts non-identity points of order 2 or 4 even though `Point` claims `PrimeGroup`. Untrusted Ed448 public keys, nonces, commitments, or proof points supplied through `Ciphersuite::read_G` can therefore contain torsion components that break Schnorr-style verification assumptions. [1](#0-0) [2](#0-1) 

### Finding Description
Ed448 has cofactor 4, so decoding must reject points outside the prime-order subgroup. The implementation defines torsion-freedom as `((*self * -1) + self).is_identity()`, which is algebraically true for every point and does not test membership in the scalar-order subgroup. [3](#0-2) 

`GroupEncoding::from_bytes` calls this ineffective check before returning a point, while `Ciphersuite::read_G` only checks that the canonical byte round-trip matches. Non-identity low-order points are therefore accepted. [4](#0-3) [2](#0-1) 

The generic Schnorr verifier accepts `R + cA - sG == identity`. If `A` is a low-order point accepted as a public key, an attacker can choose `R = kA - sG` and satisfy verification whenever `k + c = 0 mod 4`, without knowing a prime-subgroup discrete logarithm for `A`. [5](#0-4) 

### Impact Explanation
An attacker can create signatures or proofs accepted under a malformed Ed448 public key without knowing that key's discrete logarithm. This also affects proof-of-knowledge style uses such as PedPoP commitment verification, where the Schnorr equation is batch-verified against attacker-supplied commitment points. [6](#0-5) [7](#0-6) 

The root cause is not merely permissive decoding: treating a cofactor-component point as a prime-group element changes the verification equation's modulo-l scalar into an effective modulo-4 condition on the torsion component.

### Likelihood Explanation
The attacker only needs to supply a canonical encoding of a non-identity Ed448 torsion point and repeatedly choose `s` values until the challenge satisfies a modulo-4 condition. Expected work is only a small constant number of challenge evaluations because there are four possible residues. [4](#0-3) [8](#0-7) 

This is reachable wherever attacker-controlled Ed448 public keys or proof points are accepted through `read_G`, rather than being restricted to keys generated by the verifier.

### Recommendation
Implement a real prime-subgroup membership test, such as multiplying by the Ed448 prime subgroup order and requiring identity, or multiply by the cofactor and reject results not in the canonical prime-order encoding according to the intended Ed448 validation rule. Keep the negative-zero and canonical-encoding checks. [1](#0-0) 

Add test vectors for every non-identity low-order Ed448 encoding and assert `Point::from_bytes` rejects them.

### Proof of Concept
For a non-identity torsion point `T` of order 4, submit `T` as the public key `A`. For an arbitrary scalar `s` and torsion coefficient `k`, construct:

```text
R = kT - sG
signature = (R, s)
```

Verification computes:

```text
R + cA - sG
= (kT - sG) + cT - sG?  // pseudocode simplification: use R = kT + sG
```

With the construction `R = kT + sG`, the verifier computes `kT + cT`, so acceptance requires `k + c = 0 mod 4`. Repeatedly choose a fresh random `s`, derive `R`, evaluate the challenge, and retry until that congruence holds. The resulting signature verifies despite `A` having no known representation as `xG` in the prime-order subgroup. [5](#0-4) [1](#0-0)
