### Title
`current_shopify_domain` silently overridden by unauthenticated `params[:shop]` in `ShopAccessScopesVerification` - ([File: app/controllers/concerns/shopify_app/shop_access_scopes_verification.rb])

### Summary
The eMode report's root cause is a piece of code that is supposed to consult an "adjusted/authoritative" configuration but instead silently resolves to a "base/default" one due to calling the wrong accessor — with no error, just wrong data used downstream for security decisions. The closest analog in `shopify_app` is `ShopifyApp::ShopAccessScopesVerification`, which defines its own private `current_shopify_domain` method sourced from the raw, user-controllable `params[:shop]` query parameter, and this definition can silently shadow the authenticated `current_shopify_domain` that `TokenExchange`/`LoginProtection` (via `EnsureHasSession`) are documented to provide, for the entire including controller.

### Finding Description
`ShopifyApp::TokenExchange#current_shopify_domain` and `ShopifyApp::LoginProtection`'s equivalent are documented and implemented to resolve the shop from the verified ID token/session — i.e., the authenticated tenant identity: [1](#0-0) 

Separately, `ShopifyApp::ShopAccessScopesVerification` defines its *own* `current_shopify_domain`, sourced directly from the unauthenticated `params[:shop]` query string: [2](#0-1) 

In Ruby, when a class includes multiple modules that define the same method name, the module included *later* takes precedence in the ancestor chain (it sits closer to the class than earlier-included modules). The gem's own generator template creates exactly this composition — a controller inheriting from `AuthenticatedController` (which includes `EnsureHasSession` → `TokenExchange`/`LoginProtection`) and then including `ShopAccessScopesVerification` afterward: [3](#0-2) [4](#0-3) 

Because `ShopAccessScopesVerification` is included last, its `current_shopify_domain` (based on raw `params[:shop]`) overrides the authenticated one provided by `EnsureHasSession`/`TokenExchange` for the **entire controller**, not just inside its own `login_on_scope_changes` before_action. This directly parallels the eMode bug: code elsewhere in the system (and the gem's own documentation) assumes `current_shopify_domain` always reflects the verified, authenticated tenant — [5](#0-4) 
— but the actual value returned is silently swapped for an attacker-controlled, unauthenticated one whenever `ShopAccessScopesVerification` is combined with `EnsureHasSession` in the officially-generated pattern.

### Impact Explanation
Any controller/action code (custom application logic, or future gem code) that calls `current_shopify_domain` expecting the authenticated tenant — as explicitly promised by the gem's own documentation — will instead receive the value of the `shop` query parameter, which is fully attacker-controlled on an authenticated request. This breaks the tenant-scoping guarantee the method is documented to provide and can lead to shop-context confusion (e.g., incorrect shop identity used in authorization, redirect, or CSP frame-ancestors decisions) even though the underlying `current_shopify_session`/API access token itself remains correctly scoped to the authenticated shop. The severity mirrors the eMode issue in that a security-relevant accessor silently returns the wrong data source system-wide once the two officially-supported concerns are combined, rather than raising an error or being scoped to just its intended local use.

### Likelihood Explanation
This requires no unusual configuration — it occurs from the standard, gem-generated combination of `AuthenticatedController` + `include ShopifyApp::ShopAccessScopesVerification`, which is the exact pattern shown in the gem's own generator template and documentation. Any request to such a controller with an attacker-supplied `shop` query parameter will trigger the override; no special privileges are needed, only that the app has adopted this documented integration.

### Recommendation
Rename the private accessor in `ShopifyApp::ShopAccessScopesVerification` (e.g. `requested_shop_domain_for_scope_check`) instead of overloading `current_shopify_domain`, so it cannot shadow the authenticated method exposed by `EnsureHasSession`/`TokenExchange`/`LoginProtection`. Additionally, document/enforce (e.g., via a runtime check similar to the `EnsureInstalled`/`LoginProtection` incompatibility guard) that concerns must not redefine `current_shopify_domain` with a different trust level.

### Proof of Concept
1. Scaffold an app with the default generator, producing `HomeController < AuthenticatedController` with `include ShopifyApp::ShopAccessScopesVerification` (per `lib/generators/shopify_app/home_controller/templates/home_controller.rb`).
2. As an authenticated merchant (valid session/ID token for `shop-a.myshopify.com`), send `GET /?shop=shop-b.myshopify.com`.
3. Add any custom action code (or a future gem feature) in `HomeController` that calls `current_shopify_domain` expecting the authenticated shop per the documented contract in `docs/shopify_app/controller-concerns.md`.
4. Observe that `current_shopify_domain` resolves to `shop-b.myshopify.com` (from `params[:shop]`) instead of the authenticated `shop-a.myshopify.com`, because `ShopAccessScopesVerification#current_shopify_domain` (last included) shadows `TokenExchange#current_shopify_domain`/`LoginProtection`'s version.

Note: I was unable to complete final verification of the full contents of `lib/shopify_app/controller_concerns/login_protection.rb`, `lib/shopify_app/controller_concerns/frame_ancestors.rb`, and `lib/shopify_app/controller_concerns/ensure_billing.rb` due to a tool error in the last iteration, so I cannot confirm whether any in-gem code (e.g., CSP `frame-ancestors` generation) itself consumes the overridden `current_shopify_domain` value — that would strengthen the concrete exploit path beyond a documented-contract violation. ## ShopAccessScopesVerification
The `ShopifyApp::ShopAccessScopesVerification` concern helps merchants grant new access scopes requested by the app. The concern compares the current access scopes granted by the shop and compares them with the scopes requested by the app. If there is a mismatch in configuration, the merchant is redirected to login via OAuth and grant the net new scopes.

To activate the `ShopAccessScopesVerification` for a controller add `include ShopifyApp::ShopAccessScopesVerification`:
```ruby
class HomeController < AuthenticatedController
  include ShopifyApp::ShopAccessScopesVerification
```

## EnsureHasSession — Authenticated Requests
Use this concern for any controller action that needs to make authenticated Shopify API calls or access shop/user data. It verifies the requester's identity using either session tokens (embedded apps) or encrypted cookies (non-embedded apps), and works with both online (user) and offline (shop) access tokens. Prefer this concern over composing lower-level session concerns directly.

When using the token exchange auth strategy, `current_shopify_domain` resolves to the authenticated shop from the verified ID token/session. Missing or invalid ID tokens use the configured invalid-token response path to get a fresh token. Request shop context is validated against the authenticated context before the action runs. If your app needs the `shop` query string for pre-auth bootstrap or routing, use `requested_shopify_domain` or an installation-only concern; do not use requested shop context for authorization or tenant scoping.

In addition to session management, this concern handles localization, CSRF protection, embedded app settings, and billing enforcement.
