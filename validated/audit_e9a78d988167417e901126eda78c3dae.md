### Title
Rebase conflict resolution UI mislabels `ours`/`theirs` when resuming an in-progress rebase, risking silent discard of the user's own commits - (File: `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
`Dispatcher.launchRebaseOperation` (used to resume the multi-commit-operation conflicts UI for an in-progress rebase) initializes the conflict-state labels with `ourBranch: targetBranch, theirBranch: undefined`. This directly contradicts the documented git semantics for rebase used everywhere else in the codebase — during a rebase, git's real "ours" (merge-index stage 2) is the **base** branch, and "theirs" (stage 3) is the **target** branch being replayed. The mismatch is the same class of bug as the `directionMask` issue: a hardcoded assumption about which side is "ours" vs "theirs" instead of dynamically deriving it from the actual git state, causing the UI to present the inverse of what git will actually do.

### Finding Description
`app/src/lib/git/diff.ts` explicitly documents git's real semantics: [1](#0-0) 

> `stage: 'ours' | 'theirs'` ... These always refer to git's definition: `ours` = stage 2 (HEAD at merge time), `theirs` = stage 3 ... Note that during a rebase, git swaps these — the upstream branch is "ours" and the rebased commit is "theirs". The caller is responsible for mapping user-facing labels to the correct git side.

`app/src/lib/app-state.ts`'s `RebaseConflictState` codifies this: `targetBranch` is "the branch chosen by the user to be rebased" and `baseBranch` is "the branch chosen as the baseline for the rebase": [2](#0-1) 

Consistent with git's swap, `AppStore.getConflictLabelsAndRefs` maps rebase labels as `ourLabel: baseBranch`, `theirLabel: targetBranch`: [3](#0-2) 

and the same mapping is used for the "which branch triggered which conflict count" stat: [4](#0-3) 

However, `Dispatcher.launchRebaseOperation` — invoked when the app reloads/resumes and detects an in-progress rebase (`RebaseConflictState`) — builds the `ShowConflicts` step with the **opposite** mapping, assigning the base's role to `targetBranch` and leaving the base branch's name out entirely: [5](#0-4) 

This `ourBranch`/`theirBranch` pair flows straight into the manual-resolution dropdown labels shown to the user for each conflicted file: [6](#0-5) [7](#0-6) 

`ManualConflictResolution.ours`/`.theirs` are passed verbatim as `--ours`/`--theirs` to `git checkout` (this part is correctly tied to git's real stage semantics, not the display label): [8](#0-7) [9](#0-8) 

So the *mechanism* (checkout `--ours`/`--theirs`) is git-accurate, but the *label the user reads* ("Use current file from `<targetBranch>`" — their own feature branch) is inverted for this resume path: selecting what the UI calls "ours"/"current" actually invokes `git checkout --ours`, which resolves to stage 2 = the **base** branch content, not the user's own branch content the label implies.

### Impact Explanation
A user resuming a rebase conflict resolution (e.g., after reopening Desktop mid-rebase, or continuing a rebase paused externally) sees a dropdown/label claiming "Use current file from `<my-feature-branch>`" when choosing "ours." Clicking it actually stages the base branch's version of the file (via `git checkout --ours`), silently discarding the user's own feature-branch changes for that file while the UI implies the opposite. This is a silent corruption of what the user commits during a rebase — exactly the class of impact called out as valid (silent corruption of what the user commits/pushes), reached without any privileged access, malware, or unnatural steps — just resuming a normal rebase-conflict flow.

### Likelihood Explanation
The trigger path (`launchRebaseOperation`) is reached whenever the app needs to re-show the `ShowConflicts` step for an already in-progress rebase (e.g., app restarted, or navigating back into a stalled rebase), which is a routine, unprivileged, ordinary-user workflow — not a rare corner case. The inconsistency with the rest of the codebase's rebase-label mapping (`app-store.ts`) indicates this is a genuine oversight rather than an intentional design choice, increasing confidence this is a real latent bug and not dead code.

### Recommendation
In `Dispatcher.launchRebaseOperation`, mirror the mapping used in `AppStore.getConflictLabelsAndRefs`/`getMergeConflictsTheirBranch`: set `ourBranch: conflictState.baseBranch` and `theirBranch: targetBranch` (falling back to a generic label when `baseBranch` is undefined), matching git's documented "ours swaps to base during rebase" behavior. Add a regression test asserting that for a `RebaseConflictState`, all UI-facing `ourBranch`/`theirBranch` derivations agree with the `getResolutionDiff` stage-mapping comment in `diff.ts`, so future edits can't reintroduce the inversion in only one of the several call sites that independently compute this pair (`app-store.ts`, `dispatcher.ts`, `base-rebase.tsx`).

### Proof of Concept
1. Start a rebase in Desktop (`Branch feature` rebased onto `base`) that produces a conflict.
2. Quit/restart Desktop (or otherwise cause the app to re-detect the in-progress rebase and route through `launchRebaseOperation`).
3. Observe the `ShowConflicts` step conflict-state is built with `ourBranch: targetBranch (feature), theirBranch: undefined` per `dispatcher.ts:645-646`, contrary to the `baseBranch`/`targetBranch` mapping used elsewhere (`app-store.ts:6476-6483`).
4. In the conflict list, pick "Use current file from `feature`" for a conflicted file.
5. Inspect the staged content: because `ManualConflictResolution.ours` maps to `git checkout --ours` = merge-index stage 2 = `base`'s content (per `diff.ts:428-434` and confirmed by `checkout.ts:221-235`), the staged/committed result is the **base** branch's version, not `feature`'s, despite the UI label claiming otherwise — a mismatch between displayed intent and actual committed content.

Note: I was not able to fully trace `Dispatcher.processMultiCommitOperationRebaseResult`'s parameter semantics before running out of tool iterations, so I cannot confirm whether that specific call site (used at normal rebase completion, not the resume path) has the same inversion — the PoC and finding above rest solely on the confirmed, self-contained inversion in `launchRebaseOperation`.

/**
 * Returns the ours/theirs dropdown labels for a conflicted file, handling
 * both delete-vs-modify and regular text conflicts.
 */
export function getOursTheirsLabels(
  status: ConflictedFileStatus | undefined,
  ourBranch?: string,
  theirBranch?: string
): { readonly oursLabel: string; readonly theirsLabel: string } {
  if (status !== undefined && isDeleteConflictFile(status)) {
    return getDeleteConflictLabels(status, ourBranch, theirBranch)
  }

  const oursLabel = ourBranch
    ? `Use current file from ${ourBranch}`
    : 'Use current file'
  const theirsLabel = theirBranch
    ? `Use incoming file from ${theirBranch}`
    : 'Use incoming file'
  return { oursLabel, theirsLabel }
}
