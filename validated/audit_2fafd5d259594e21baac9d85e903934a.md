## Title
Clone operation explicitly disables Git's built‑in protection against malicious submodule hook execution (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: `app/src/lib/git/clone.ts`)

## Summary
The BCAP report's underlying concern is that a single, highly-privileged operation (control of the token issuer key) is left with no additional guard rail, so if that key/path is abused, the whole system is compromised. The analogous broken invariant in GitHub Desktop is that its `clone()` implementation always performs a **recursive** clone of a **fully attacker-controlled URL** while explicitly turning off the exact Git safety mechanism (`GIT_CLONE_PROTECTION_ACTIVE`) that upstream Git introduced to stop malicious repositories/submodules from executing hooks during clone (the class of issue fixed as CVE‑2024‑32004/CVE‑2024‑32465). Desktop unconditionally sets this variable to `'false'` for every clone, re‑enabling the vulnerable, protection‑disabled behavior for every user-supplied or API-provided clone URL.

## Finding Description
`clone()` builds the git invocation like this: [1](#0-0) 

```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c', `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git added to gate the fix for the "arbitrary code execution during recursive clone with submodules" class of vulnerabilities: a maliciously-crafted repository can embed a submodule whose on-disk layout (via symlinks / crafted `.git` paths / hardlinked object directories) causes Git, during a `--recursive` clone, to write or execute content (e.g. hook scripts) outside of the intended submodule working tree, in the host repository's real `.git` directory. Git ships this variable defaulting to a "protection active" state precisely so recursive clones of untrusted repositories are safe by default; setting it to `'false'` deliberately reverts to the pre-fix, exploitable behavior.

Desktop calls this code path from `_clone` in the app store for every "Clone repository" action (URL entry, GitHub repo picker, and `x-github-client://openRepo`/deep-link clone flows), meaning **every clone target is treated as if it is trusted**, including a URL typed by the user, chosen from search results, or supplied via a deep link/API object: [2](#0-1) 

The only defenses that exist around clone are unrelated to this: `isClonePathSensitive()` only checks the destination path for path traversal into sensitive local folders, it does nothing to validate the content of the remote repository or its submodules: [3](#0-2) 

Nothing else in the clone path re-enables or substitutes the disabled protection — the `git()` wrapper (`app/src/lib/git/core.ts`) just forwards the caller-supplied `env`, and `withHooksEnv`/`withTrampolineEnv` only manage credential/hook-interception env vars, they don't restore clone protections.

## Impact Explanation
If an attacker can get a Desktop user to clone (or the app to auto-clone, e.g. from a deep link or "Open in Desktop" flow) a repository they control, the disabled protection allows the attacker's crafted submodule layout to write/execute files outside the intended checkout directory during the `--recursive` clone — i.e., before the user ever inspects, commits, or pushes anything. This is code execution driven purely by content in a repository the attacker controls, which matches the "Valid Impact" criteria (attacker-controlled cloned repository → code execution/file write outside the repo) exactly, with no local/admin access, no leaked credentials, and no unnatural user interaction beyond the ordinary "Clone repository" action Desktop is built to perform.

## Likelihood Explanation
Every single clone performed by Desktop passes through this code path unconditionally — there is no per-repository trust decision, no prompt, and no opt-out. Any attacker who can get their repository URL in front of a user (a public repo link, a forked/typosquatted repo, an org invite, a deep link) reaches this vulnerable configuration deterministically. Because the mitigating Git behavior is explicitly turned off, whether it's exploitable end-to-end depends on the exact Git version bundled with Desktop's `dugite` and the specific crafted-repository technique used, which I could not verify further from the indexed code (I do not have visibility into the exact bundled Git version's patch level for this protection).

## Recommendation
- Remove `GIT_CLONE_PROTECTION_ACTIVE: 'false'` from `envForRemoteOperation`/clone's env so Git's default (protection-enabled) behavior is preserved for all clones.
- If this override was added to work around a specific benign scenario (e.g. cloning trusted local fixtures in tests), scope it narrowly (e.g., only for internal/test helpers) rather than the production `clone()` function used for arbitrary user- and API-supplied URLs.
- Audit `checkout.ts`/`submodule.ts` `allowFileProtocol` usage similarly, since `protocol.file.allow=always` is another Git protection (against `file://` submodule URLs, CVE‑2022‑39253) being force-enabled; confirm it is only used against repositories fully controlled by the local user (e.g., local fixture setup) and not reachable via `checkoutBranch`/`checkoutCommit` on attacker-supplied remote repos before considering it safe.

## Proof of Concept
1. An attacker publishes a public Git repository containing a submodule crafted per the CVE‑2024‑32004 technique (a submodule entry whose gitlink/`.git` structure is engineered so that, during `git clone --recursive` with clone protections disabled, Git writes/executes a hook file into the parent repository's real `.git/hooks` directory instead of the isolated submodule directory).
2. The attacker shares the clone URL (README link, "Clone in GitHub Desktop" button, or `x-github-client://openRepo/<url>` deep link).
3. The victim clicks "Clone" in GitHub Desktop, which invokes `AppStore._clone` → `clone()`: [1](#0-0) 
4. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` and `--recursive` is always passed, Git performs the recursive submodule clone with its protective check disabled, allowing the crafted hook to be written/executed as part of the clone, achieving code execution on the victim's machine without the victim ever opening the repository in an editor or running `git` commands manually.

Note: I could not verify from the indexed code which exact `dugite`/Git version ships with this build of Desktop, so I cannot confirm whether the underlying Git binary is otherwise patched in a way that would still block exploitation despite the environment variable override; this would need to be checked against `app/package.json`'s pinned `dugite` version and its bundled Git release notes.

```typescript
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
```
