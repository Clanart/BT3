### Title
System-wide liquidation freeze: `iter-price-multi`'s all-or-nothing accumulator + `get-assets`' unconditional pricing of every globally-enabled collateral asset lets a single asset's oracle fault brick liquidation for every unrelated position - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`get-liquidation-position`/`get-position` explicitly build the position's mask from "enabled collateral + all debt" rather than the account's actually-held assets, so `get-assets` always attempts to price every globally-enabled collateral asset for every account. `price-multi-resolve`'s fold accumulator (`iter-price-multi`) is strict all-or-nothing: one failing `price-resolve` call sets `valid: false`, which short-circuits every remaining element and causes `(asserts! (get valid response) ERR-ORACLE-MULTI)` to abort. Because `get-assets` reaches this via `unwrap-panic`, a single broken oracle feed for one globally-enabled asset panics/aborts pricing for every account's position, including accounts holding zero balance of that asset, freezing deposits/borrows/health-checks and liquidation protocol-wide.

### Finding Description
Tracing the path:

1. `get-liquidation-position`/`get-position` call `get-enabled-bitmap` and pass that mask into `v0-market-vault get-position`, and the code's own comment on `get-liquidation-position` states it returns "enabled collateral + all debt" [1](#0-0) . This means the mask/collateral list returned for ANY account includes every globally enabled collateral asset, not just the assets that account actually holds.
2. `get-assets` computes `mask-enabled` via `get-enabled-bitmap`, computes `user-safe-mask` by ANDing the user's collateral bits with the enabled bits [2](#0-1) , and since the position's collateral mask already equals the enabled-collateral set, `safe-mask` reduces to the full enabled-asset list. `get-assets` then unconditionally resolves prices for that full list via `price-multi-resolve` [3](#0-2) , using `unwrap-panic` on the result.
3. `price-multi-resolve` folds `iter-price-multi` over the oracle-data list with an initial `{valid: true}` accumulator [4](#0-3) .
4. `iter-price-multi` starts with `(skip? (asserts! valid acc))` — once `valid` becomes `false` for any single element, every subsequent fold step immediately short-circuits and returns the same `{valid: false}` accumulator unchanged, without attempting to resolve any further asset's price [5](#0-4) .
5. `price-multi-resolve` then asserts `(get valid response)` and returns `ERR-ORACLE-MULTI` for the WHOLE batch [6](#0-5) , which `get-assets` turns into a panic via `unwrap-panic` [7](#0-6) .

Root cause: (a) the mask construction deliberately forces pricing of every enabled collateral asset regardless of whether the specific account holds it, and (b) the fold accumulator has no per-asset isolation/fallback — a single asset's `price-resolve` failure (negative/zero price failing `oracle-price-legal`, stale timestamp failing `oracle-timestamp-fresh`, low confidence failing `check-confidence`, or a zero/missing `lindex` cache causing a divide/panic inside `resolve-ztoken`) propagates to abort pricing for every other, healthy asset and every other, unrelated account. There is no later gate that recovers from this: the abort happens before `get-notional-evaluation`, before `is-healthy`, and before the liquidation math ever runs, so the transaction simply reverts.

### Impact Explanation
Direction: this is not a mispricing but a denial-of-service — any account whose position evaluation reaches `get-assets` (deposit, borrow, health check, and critically `liquidate`) reverts as soon as one globally-enabled asset's oracle feed hits any single-asset freeze condition, even if that asset has zero balance in the position being evaluated. Since liquidation itself requires `get-assets`/`get-notional-evaluation` to compute health/LTV, a poisoned feed on one enabled asset freezes liquidation for every position in the protocol, including genuinely unhealthy, unrelated positions that hold none of the poisoned asset. Those positions continue to accrue bad debt while liquidators are unable to act, which is a protocol insolvency vector (Critical: permanent freezing of funds / protocol insolvency due to system-wide liquidation freeze).

### Likelihood Explanation
No special privilege is required to trigger the underlying single-asset fault (e.g., relying on a previously-identified single-asset freeze condition — negative price, extreme expo, or zero lindex cache — on any DAO-enabled asset); once that condition exists for any one enabled asset (via legitimate oracle publication of an edge-case value, or a scenario where the cached lindex for a rarely-touched ztoken has not been refreshed), every subsequent liquidation attempt on any position reverts automatically because `get-assets` is unconditionally invoked with the full enabled-asset mask. This is deterministic and repeatable as long as the faulty condition persists on the affected asset feed/cache; it does not require attacker capital beyond triggering or waiting for the underlying single-asset condition.

### Recommendation
Change `get-assets`/`get-liquidation-position` to price only the assets actually present (nonzero collateral or nonzero debt) in the specific position being evaluated, rather than intersecting with the full globally-enabled bitmap. Additionally, make `iter-price-multi`/`price-multi-resolve` isolate failures per-asset (e.g., only fail if a *needed* asset's price fails) instead of aborting the whole batch when an irrelevant asset's price fails, and avoid `unwrap-panic` in `get-assets` in favor of a recoverable error path so a single unrelated asset fault cannot brick unrelated positions' liquidation.

### Proof of Concept
Clarinet simnet test plan:
1. Enable two collateral assets globally in `v0-assets` (Asset A held by position P1 with healthy collateral/debt; Asset B held by no one, or held with zero balance by P1).
2. Create position P1 with only Asset A as collateral and enough debt to be unhealthy (e.g., collateral-usd * LTV < debt-usd).
3. Configure Asset B's oracle feed (Pyth or DIA) to return a negative/zero price, or configure its `max-staleness` such that `oracle-timestamp-fresh` fails, or leave its `lindex` cache at zero so `resolve-ztoken` div-down produces the failing case.
4. Call `liquidate` on P1 as an ordinary attacker/liquidator principal.
5. Assert the call reverts with `ERR-ORACLE-MULTI` (u400015) even though P1 holds zero balance of Asset B and is genuinely unhealthy on Asset A alone — demonstrating the liquidation freeze is system-wide rather than confined to holders of the faulty asset.

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))

(define-private (user-safe-mask (mask-user uint) (mask-enabled uint))
  (let ((enabled-collateral (bit-and mask-enabled MAX-U64))
        (user-collateral (bit-and mask-user MAX-U64))
        (user-debt (/ (bit-and mask-user DEBT-MASK) (pow u2 DEBT-OFFSET)))
        (collateral-match (bit-and user-collateral enabled-collateral)))
    (bit-or collateral-match user-debt)))
