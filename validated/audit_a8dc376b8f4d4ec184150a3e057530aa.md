### Title
Quadratic Lagrange interpolation during `ThresholdKeys` construction enables remote CPU-exhaustion DoS - ([File: crypto/dkg/src/lib.rs])

### Summary
The reported bug class (CVE-2018-18898) is an algorithmic-complexity denial of service: parsing crafted public input triggers work wildly disproportionate to the input size. `ThresholdKeys::read` accepts attacker-supplied `t`, `n` values (both `u16`, up to 65535) with `t <= n`, then `ThresholdKeys::new` computes the group key by running full Lagrange `interpolation_factor` over participants `1..=t`, where each factor computation is itself an `O(t)` loop containing a field inversion — yielding `O(t²)` field inversions/multiplications for a roughly `O(n)`-sized input.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` directly from the input, reading only `n` verification-share points plus the secret share — a linear amount of data [1](#0-0) . It then calls `ThresholdKeys::new` [2](#0-1) , which derives `group_key` as a sum over `1..=t` of `verification_shares[i] * interpolation_factor(i, &t)` [3](#0-2) . Each Lagrange `interpolation_factor` call iterates all `t` included participants and performs one `denom.invert()` per call — an expensive inversion per participant [4](#0-3) . `Interpolation::Constant` is only rejected when `t != n`, so the `Lagrange` path is always selectable by the attacker [5](#0-4) . The same quadratic pattern re-appears in `view()`, which calls `interpolation_factor` for every included signer [6](#0-5) .

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (or to `view` / any `calculate_share` path that constructs `ThresholdKeys` from public input) can supply `t = n = 65535`, `i = 1` — about 2 MB of encoded points — and force ~t² ≈ 4.3×10⁹ field inversions and multiplications in `ThresholdKeys::new`. This is a CPU-exhaustion DoS against a validator/processor node exactly analogous to the Request Tracker parsing blowup: linear input, quadratic (or worse, given per-term inversion cost) computation. It can stall a participant's event loop during key-load, share-calculation, or view construction, preventing timely signing participation.

### Likelihood Explanation
Reachability requires the application to deserialize `ThresholdKeys` or construct views from data influenced by external parties, which is a documented and reachable pattern for this library (key-share recovery / re-keying flows deserialize stored or received keys). The cost per byte is extreme since each of the 65535 factors performs a full field inversion (`denom.invert().unwrap()`) inside an O(t) loop [7](#0-6) . No authentication of `t`/`n` bounds exists beyond `t <= n` and `i <= n` [8](#0-7) .

### Recommendation
Cap `n` (and hence `t`) to the protocol's real maximum key-share count (e.g., `MAX_KEY_SHARES_PER_SET`) inside `ThresholdParams::new`/`ThresholdKeys::read`, and/or precompute Lagrange denominators once per signing set (single batch inversion via Montgomery's trick) so `interpolation_factor` is O(t) total rather than O(t) inversions per participant. Memoize factors in `view()` instead of recomputing per included signer.

### Proof of Concept
Craft a `ThresholdKeys` serialization: valid `C::ID`, `t = n = 65535`, `i = 1`, interpolation byte `1` (Lagrange), one scalar, then 65535 valid `read_G` encodings (e.g., repeated generator bytes). Feeding ~2 MB to `ThresholdKeys::read` reaches `ThresholdKeys::new`, which executes the `t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum()` line — performing 65535 × 65535 inner-loop iterations and 65535 field inversions before returning or erroring [9](#0-8) .
