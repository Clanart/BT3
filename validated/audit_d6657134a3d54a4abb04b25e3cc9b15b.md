## Finding

### Title
Denial of Service via Unbounded List Parameters in Full Node Coin Record RPC Endpoints - (File: `chia/full_node/full_node_rpc_api.py`)

### Summary
The full node RPC endpoints `get_coin_records_by_names`, `get_coin_records_by_puzzle_hashes`, and `get_coin_records_by_parent_ids` accept attacker/caller-controlled lists (`names`, `puzzle_hashes`, `parent_ids`) with no upper bound on their length. These lists are passed straight through to `CoinStore` methods that build a single SQL `IN (...)` clause sized to the exact length of the input list, without batching, unlike the sibling `get_coin_records()` method in the same file which correctly chunks lookups via `to_batches(names, SQLITE_MAX_VARIABLE_NUMBER)`. This mirrors the Discourse CVE-2024-27100 bug class: endpoints missing size limits on caller-supplied parameters, allowing a single request to trigger excessive resource consumption.

### Finding Description
`FullNodeRpcApi.get_coin_records_by_names()` reads `request["names"]`, hex-decodes every entry with no cap on count, and forwards the full list to `CoinStore.get_coin_records_by_names()`: [1](#0-0) 

`CoinStore.get_coin_records_by_names()` then builds the SQL statement by string-multiplying a placeholder for every element of `names` and binds all of them in one query, with no batching or length limit: [2](#0-1) 

The same unbounded pattern exists for `get_coin_records_by_puzzle_hashes`: [3](#0-2) [4](#0-3) 

and for `get_coin_records_by_parent_ids`, plus the hint-based lookup which also funnels into `get_coin_records_by_names`: [5](#0-4) 

Contrast this with the correctly-hardened `get_coin_records()` in the same file, which deliberately batches lookups to stay under SQLite's bound-parameter ceiling: [6](#0-5) 

and with the wallet RPC's `get_coin_records_by_names`, which is bounded indirectly by wallet-side coin-id filtering and a documented `max_get_coin_records_limit`/`max_get_coin_records_filter_items` class constant: [7](#0-6) 

Because the full node counterparts have no analogous limit, a caller can submit a request with an arbitrarily large `names`/`puzzle_hashes`/`parent_ids` array. Building the query string (`'?,' * (len(names) - 1)`) and the parameter tuple/list scales linearly with the array size in both CPU and memory, and the resulting single SQL statement is bound with as many parameters as elements supplied, well beyond SQLite's compiled `SQLITE_MAX_VARIABLE_NUMBER` bound-parameter ceiling referenced elsewhere in the same file as the correct batching threshold. This can stall the full node's single-writer/reader SQLite connection pool and its async event loop while constructing/parsing the oversized statement, degrading or halting the node's ability to process new blocks/transactions — the transaction-processing-halt class explicitly called out as in-scope impact.

### Impact Explanation
An RPC caller reachable via the full node's local RPC surface (as explicitly listed in the allowed attacker profile) can send a single crafted request to `get_coin_records_by_names`, `get_coin_records_by_puzzle_hashes`, or `get_coin_records_by_parent_ids` with a very large list, causing outsized CPU/memory consumption while building and executing the SQL statement. This can degrade the full node's responsiveness or cause a spend/RPC-triggered halt in servicing further requests, directly matching the "spend-triggered transaction-processing halt"/resource-exhaustion impact category. Severity is Medium, consistent with the analogous Discourse CVE, because it is a resource-exhaustion DoS bounded to the RPC-serving node rather than a fund-theft or consensus-divergence bug.

### Likelihood Explanation
No authentication logic beyond standard RPC transport is present in these handlers, and no size validation exists on the list-typed parameters, so any caller capable of reaching the full node RPC endpoint can trigger this with a single, easily constructed request (a large JSON array of hex-encoded 32-byte hashes). This makes the likelihood high for anyone with RPC reachability.

### Recommendation
Add an explicit maximum length check on `names`, `puzzle_hashes`, and `parent_ids` in the `full_node_rpc_api.py` handlers (mirroring `WalletRpcApi.max_get_coin_records_limit`), and update `CoinStore.get_coin_records_by_names` / `get_coin_records_by_puzzle_hashes` / `get_coin_records_by_parent_ids` to batch queries via `to_batches(..., SQLITE_MAX_VARIABLE_NUMBER)`, exactly as already done in `CoinStore.get_coin_records()`.

### Proof of Concept
1. Start a full node with RPC enabled and obtain RPC credentials (as any local RPC caller would).
2. Send a POST request to `/get_coin_records_by_names` with a `names` array containing e.g. 1,000,000 distinct 32-byte hex strings.
3. Observe `FullNodeRpcApi.get_coin_records_by_names()` hex-decode all one million entries, then `CoinStore.get_coin_records_by_names()` build a single SQL statement with one million `?` placeholders and bind one million parameters in one query — consuming significant CPU/memory and potentially exceeding SQLite's variable-count limits, stalling the node's DB connection during query construction/execution. The same can be repeated against `/get_coin_records_by_puzzle_hashes` and `/get_coin_records_by_parent_ids`.

    async def get_coin_records_by_puzzle_hashes(self, request: dict[str, Any]) -> EndpointResult:
        """
        Retrieves the coins for a given puzzlehash, by default returns unspent coins.
        """
        if "puzzle_hashes" not in request:
            raise RpcError.simple(RpcErrorCodes.PUZZLE_HASHES_NOT_IN_REQUEST, "Puzzle hashes not in request")
        kwargs: dict[str, Any] = {
            "include_spent_coins": False,
            "puzzle_hashes": [hexstr_to_bytes(ph) for ph in request["puzzle_hashes"]],
        }
        if "start_height" in request:
            kwargs["start_height"] = uint32(request["start_height"])
        if "end_height" in request:
            kwargs["end_height"] = uint32(request["end_height"])

        if "include_spent_coins" in request:
            kwargs["include_spent_coins"] = request["include_spent_coins"]

        coin_records = await self.service.coin_store.get_coin_records_by_puzzle_hashes(**kwargs)

        return {"coin_records": [coin_record_dict_backwards_compat(cr.to_json_dict()) for cr in coin_records]}

    async def get_coin_records(self, names: Collection[bytes32]) -> list[CoinRecord]:
        if len(names) == 0:
            return []

        coins: list[CoinRecord] = []

        async with self.db_wrapper.reader_no_transaction() as conn:
            cursors: list[Cursor] = []
            for batch in to_batches(names, SQLITE_MAX_VARIABLE_NUMBER):
                names_db: tuple[Any, ...] = tuple(batch.entries)
                cursors.append(
                    await conn.execute(
                        f"SELECT confirmed_index, spent_index, coinbase, puzzle_hash, "
                        f"coin_parent, amount, timestamp FROM coin_record "
                        f"WHERE coin_name in ({','.join(['?'] * len(names_db))}) ",
                        names_db,
                    )
                )

            for cursor in cursors:
                for row in await cursor.fetchall():
                    coin = self.row_to_coin(row)
                    spent_index = uint32(0) if row[1] <= 0 else uint32(row[1])
                    record = CoinRecord(coin, row[0], spent_index, row[2] != 0, row[6])
                    coins.append(record)

        return coins

                    spent_index = uint32(0) if row[1] <= 0 else uint32(row[1])
