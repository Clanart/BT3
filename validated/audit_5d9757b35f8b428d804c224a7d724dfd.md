### Title
`Scanner::scan_transaction` classifies outputs by `script_pubkey` alone, letting any sender's funds be consumed under reserved internal `OutputType`s instead of being credited as a deposit - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Trident M-06 bug class is: a single balance serves two purposes, and the consumer for one purpose (fee `collect()`) silently drains funds earmarked for another (incentive payouts), because the code distinguishes intent only by which balance the tokens sit in. Serai's Bitcoin scanner has the same shape. `Scanner` keys every received output solely by `script_pubkey` (`scan_transaction`, `networks/bitcoin/src/wallet/mod.rs:199-214`), and `register_offset` reserves three internal-purpose addresses derived from publicly computable offsets (`BRANCH_OFFSET`/`CHANGE_OFFSET`/`FORWARD_OFFSET` are `hash_to_F(KEY_DST, b"branch"|"change"|"forward")`, fixed constants in `processor/src/networks/bitcoin.rs:308-344`). Any unprivileged party who sends BTC to a Branch, Change, or Forwarded script_pubkey produces a `ReceivedOutput` that is indistinguishable from internally-created outputs. Downstream, the processor retains only `OutputType::External` outputs as deposit instructions, treats `Forwarded` outputs as completions of pending forward operations (consuming the stored `InInstruction` via `ForwardedOutputDb::take_forwarded_output` keyed by balance), and feeds `Branch` outputs into `Scheduler::add_outputs` where an amount-matching output pops and executes the queued payment plan (`processor/src/multisigs/scheduler/utxo.rs:276-295`). Funds sent to Change/Branch addresses are therefore classified as internal outputs and dropped from the deposit path — received, spendable only by the multisig's internal machinery, but never credited — exactly mirroring incentive tokens being consumed by fee collection.

### Finding Description
`Scanner::scan_transaction` performs `self.scripts.get(&output.script_pubkey)` with no distinction between an output Serai itself created (change it made, a branch it funded, a forward it executed) and an output an arbitrary third party created by paying to the same script. The offsets are not secret: `BRANCH_OFFSET`, `CHANGE_OFFSET`, and `FORWARD_OFFSET` are deterministic `hash_to_F` outputs over a fixed DST and fixed labels (`processor/src/networks/bitcoin.rs:308-344`), and `register_offset` only increments the offset to reach an even-Y point (`networks/bitcoin/src/wallet/mod.rs:180-196`), so anyone can recompute all four script_pubkeys from the public group key. The scanner's docstring even notes offsets "are surjective, not bijective" (`networks/bitcoin/src/wallet/mod.rs:170-175`) — there is no authentication of provenance at all. In `processor/src/multisigs/mod.rs:824-837`, `Forwarded` outputs cause `ForwardedOutputDb::take_forwarded_output(txn, output.balance())` — keyed only by amount — so an attacker-crafted forward-address output of the same value as a genuinely pending forward consumes the stored `InInstruction`, while `Change`/`Branch`-kinded attacker outputs are filtered out of the `External` deposit path and handled (or dropped) as internal artifacts, and a `Branch` output matching `self.plans[amount]` directly triggers execution of payments as if Serai's own branch had confirmed (`processor/src/multisigs/scheduler/utxo.rs:276-295`).

### Impact Explanation
As in M-06, value earmarked for one accounting purpose is consumed by another because the distinguishing feature is only "which bucket the coins sit in." Concretely: (1) external funds sent to the change/branch/forward script_pubkeys are never emitted as `External` outputs, so deposits are received but uncredited — the honest analog of `claimReward()` failing because the bento balance was drained by `collect()`; (2) an attacker-funded `Forwarded`-kind output with a matching amount can consume a `ForwardedOutputDb` `InInstruction` intended for Serai's own forwarded output, mis-attributing provenance; (3) a `Branch`-kind output with a matching amount prematurely executes a queued payment plan the scheduler believes its own confirmed branch is funding.

### Likelihood Explanation
The attacker needs only a standard Bitcoin transaction — no key material, no collusion. The reserved script_pubkeys are recomputable from the public group key and constant offsets, so crafting a matching output is trivial. Triggering the `Forwarded`/`Branch` paths additionally requires guessing the amount of a pending forward/branch, which is often inferable from the mempool or the payment set. The uncredited-deposit case requires no timing at all.

### Recommendation
Do not classify received outputs by `script_pubkey` alone, mirroring the M-06 recommendation to track reserved balances separately. Concretely: maintain an explicit registry of outpoints/script-uses Serai itself created (expected change, branch, and forward outputs) and only assign non-`External` `OutputType`s to outputs matching that registry; treat unexpected payments to reserved addresses as `External` (credited) or refuse to scan for them. At minimum, key `ForwardedOutputDb` entries by outpoint rather than by `balance()` so attacker-created forwards cannot consume stored instructions.

### Proof of Concept
1. Observe the multisig group key `K` (public). Compute `forward_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")`, increment until `K + G*o` is even, and derive `p2tr_script_buf(K + G*o)` — identically to `processor/src/networks/bitcoin.rs:324-344`.
2. Send a Bitcoin transaction paying `X` sats to that script. `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:205-211`) returns a `ReceivedOutput` whose `kinds` lookup in `get_outputs` (`processor/src/networks/bitcoin.rs:692-699`) labels it `OutputType::Forwarded`, not `External`.
3. In `scanner_event_to_multisig_event`, `ForwardedOutputDb::take_forwarded_output(txn, output.balance())` either consumes a pending legitimate forward instruction (if `X` matches) or the output is dropped by the `retain(External)` filter — in both cases the sender's deposit is never credited, despite the multisig provably receiving spendable funds. The same holds for the change and branch script_pubkeys, with the branch case additionally able to trigger `Scheduler::add_outputs` plan execution when `X` equals a queued branch amount.
