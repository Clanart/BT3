### Title
Blame proofs publish the ECDH shared key, exposing the accused participant's secret share in the `InvalidShare` error message - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG's blame mechanism embeds the raw ECDH shared key (`EncryptionKeyProof.key`) directly into the `PedPoPError::InvalidShare` / `ProcessorMessage::InvalidShare` error path. Because `cipher()` derives the ChaCha20 keystream solely from that ECDH point and a static IV, whoever sees the blame proof can decrypt the corresponding `EncryptedMessage<SecretShare>` — which is transmitted over the (publicly observable) channel and referenced by the accusation. The plaintext DKG secret share is thereby persisted inside error/blame data, the same class as the n8n advisory (decrypted secret written into error data, readable beyond the intended recipient).

### Finding Description
When a recipient claims a share is invalid, `KeyMachine::calculate_share` returns `PedPoPError::InvalidShare { participant, blame }` where `blame` is an `EncryptionKeyProof` containing `key: Zeroizing<C::G>` — the ECDH shared point `enc_key_recipient * msg.key` — plus a DLEq proving its correctness [1](#0-0) . `Decryption::decrypt_with_proof` explicitly uses that key to run `cipher(context, &proof.key).apply_keystream(...)` and recover the plaintext share, so the published key is by itself sufficient decryption material for the attached ciphertext [2](#0-1) . The cipher uses a fixed IV (`b"DKG IV v0.2\0"`), so no additional secret is needed [3](#0-2) . The processor serializes this proof into the outward-facing `ProcessorMessage::InvalidShare { id, accuser, faulty, blame }` sent to the coordinator for adjudication [4](#0-3) , and `BlameMachine::blame`/`blame_internal` is designed for any party to adjudicate the same `(sender, recipient, msg, proof)` tuple — meaning `msg` and `proof` must be, and are, publicly transportable [5](#0-4) .

The code comments acknowledge this side channel partially ("they'd reveal bX, revealing Alice's message to Bob") but only analyze a single reused-key case; the structural issue that every blame publication leaks the decrypted share to all observers remains [6](#0-5) .

### Impact Explanation
Each published blame proof leaks `f_sender(recipient)`, one evaluation of the accused sender's secret polynomial. A malicious participant `i` can maximize this: after `generate_secret_shares`, `i` submits an `InvalidShare` accusation (with a self-generated valid `EncryptionKeyProof`, since `i` knows `enc_key_i`) against *every* other participant `j`. Each published proof lets any observer decrypt `f_j(i)`. Since participant `i`'s threshold secret share is `Σ_j f_j(i)`, a malicious accuser causes its own secret key share to become fully recoverable by the public from error/blame data. With one participant's share public, the effective security of the threshold key drops by one share: an adversary compromising `t-1` other participants (instead of `t`) can forge signatures. This is concrete secret-key-share recovery from data any observer of the blame/error path can read.

### Likelihood Explanation
Exploitation only requires an unprivileged DKG participant crafting messages — an accusation costs nothing, needs no collusion, and the proof `i` must attach is honestly derivable from `i`'s own `enc_key` via `Encryption::decrypt` [7](#0-6) . The accuser is eventually blamed and the DKG aborts, but the leaked share of the *reused* validator set context (if shares/key material are ever retried or the participant set overlaps a future session) persists, and for the aborted session every `f_j(i)` is permanently public. The design intends blame messages to be relayed to all participants, so there is no confidentiality boundary containing the leak. Medium severity: real secret leakage, but it degrades rather than directly breaks the threshold.

### Recommendation
Do not place the raw ECDH key in the published proof. Have the accuser instead publish a DLEq-bound commitment and have blame adjudication performed as a keyed verification (e.g., a proof that `decrypt(msg)` fails the share-verification statements, evaluated against `proof.key` inside a zero-knowledge/verifiable-computation step), or publish only the decrypted share itself with a proof of correct decryption — which leaks `f_j(i)` identically, so the preferred fix is to keep `proof.key` and the adjudication off public transcripts: restrict `BlameMachine::blame` inputs so only an adjudicating committee or the sender sees the proof, or re-key per-blame so revealed material cannot decrypt other messages. At minimum, document that an accusation publicly reveals the accused share and bound each accuser to a single blame claim.

### Proof of Concept
1. Participants run PedPoP; malicious `i` completes `generate_secret_shares` honestly and receives `EncryptedMessage<C, SecretShare>` from each honest `j`.
2. `i` computes `key_j = ecdh(enc_key_i, msg_j.key)` and `EncryptionKeyProof { key_j, dleq }` for each `j` (normal `Encryption::decrypt` output).
3. `i` emits `ProcessorMessage::InvalidShare { id, accuser: i, faulty: j, blame: Some(proof_j.serialize()) }` for every `j` (processor emits exactly this on `PedPoPError::InvalidShare` [4](#0-3) ).
4. Any observer of the blame stream takes `(msg_j, proof_j)`, runs `cipher(context, &proof_j.key).apply_keystream(msg_j.msg)` — the identical operation in `decrypt_with_proof` [8](#0-7)  — and recovers `f_j(i)` for all `j`.
5. Observer computes `Σ_j f_j(i)`, recovering participant `i`'s full secret key share; the threshold key's security is reduced by one share.

Caveat: I verified the leak path in `encryption.rs`/`key_gen.rs`; I did not fully trace the coordinator's `handle.rs`/`transaction.rs` broadcast of `InvalidShare` to confirm exact propagation scope, but `BlameMachine` is explicitly built for third-party adjudication of the transported `(msg, proof)` tuple, so confidentiality of the proof is not part of the design.

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
