### Title
Out-of-bounds read / unhandled `IndexError` in `is_clvm_canonical()` / `is_atom_canonical()` on attacker-supplied puzzle reveal and solution bytes - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_clvm_canonical()` and its helper `is_atom_canonical()` walk a raw `bytes` buffer using an internally-tracked `tokens_left`/`offset` cursor without ever checking `offset` against `len(clvm_buffer)` before indexing into it. Both functions are invoked on every coin spend's `puzzle_reveal` and `solution` — fields fully controlled by whoever submits a spend bundle — during mempool admission in `validate_spend_bundle()`. A truncated/malformed CLVM buffer (e.g. a dangling cons pair with a missing second element, or a truncated multi-byte atom length prefix) drives `offset` past the end of the buffer, causing an unhandled `IndexError` from ordinary Python bytes indexing. This mirrors the CVE-2017-9472 bug class: a low-level byte-parsing routine that trusts internal length/type bookkeeping and reads past the buffer when fed a crafted, truncated input.

### Finding Description
`is_clvm_canonical()` is called unconditionally for every coin spend in a submitted `SpendBundle`: [1](#0-0) 

Its implementation reads `clvm_buffer[offset]` in a loop, advancing `offset` based on the pair/atom bookkeeping (`tokens_left`) without any bounds check against `len(clvm_buffer)`: [2](#0-1) 

For example, the buffer `b"\xff\x80"` encodes a cons pair (`0xFF`) that requires two child tokens, but only one atom (`0x80`) follows. After consuming the pair marker and the single atom, `tokens_left` is `1` (not `0`), so the loop reads `clvm_buffer[2]` on a 2-byte buffer, raising `IndexError`.

`is_atom_canonical()` has the same problem: it reads consecutive `clvm_buffer[offset]` bytes for `prefix_len` iterations (up to 5) to reconstruct a multi-byte atom length prefix, with no check that those bytes exist in the buffer: [3](#0-2) 

A crafted `puzzle_reveal` or `solution` ending exactly at (or before) a multi-byte length-prefix continuation byte (e.g. `0xC0` as the very last byte of the buffer) triggers the same class of out-of-bounds index access inside the `for i in range(prefix_len)` loop.

Because `Program`/`SerializedProgram` deserialization from raw bytes for a `CoinSpend` is permissive about buffer shape at this layer (the canonical-form check happens after CLVM execution, in `validate_spend_bundle()`), an attacker can submit a `SpendBundle` whose `puzzle_reveal`/`solution` bytes are syntactically incomplete CLVM (dangling pair or truncated atom length) yet still pass through to this canonical-form check.

### Impact Explanation
`validate_spend_bundle()` has no try/except around the `is_clvm_canonical()` calls, so the `IndexError` propagates out of mempool admission for that spend bundle. Depending on how far up the call stack exceptions are caught (full node RPC/API handlers vs. bare propagation into the mempool-processing task), this can abort mempool admission of the transaction and/or surface as an unhandled exception in the transaction-processing path invoked directly from network/RPC input, which matches the "spend-triggered transaction-processing halt" acceptance criterion — an unprivileged spend-bundle submitter can crash or interrupt the code path responsible for admitting further transactions with a single malformed submission, analogous to how a crafted file crashes `ytnef`'s parser via `SwapDWord`.

### Likelihood Explanation
High from a reachability standpoint: any unprivileged wallet user, offer counterparty, or RPC caller can submit a `SpendBundle` with a hand-crafted `puzzle_reveal`/`solution` byte string. No signature or additional validation on the raw byte shape happens before `is_clvm_canonical()` is invoked in `validate_spend_bundle()`, and the malformed patterns (dangling cons pair, truncated length-prefix continuation byte) are trivial to construct.

### Recommendation
Add explicit bounds checks in both `is_clvm_canonical()` and `is_atom_canonical()` before indexing into `clvm_buffer` (e.g., check `offset < len(clvm_buffer)` at the top of the main loop, and check remaining buffer length against `prefix_len` before the prefix-reconstruction loop), returning `False`/raising a well-defined `ValueError` instead of allowing Python's implicit `IndexError` to propagate. Ensure `validate_spend_bundle()` treats any such parse failure as `Err.INVALID_COIN_SOLUTION` rather than letting an unexpected exception escape mempool admission.

### Proof of Concept
1. Construct a `CoinSpend` whose `solution` (or `puzzle_reveal`) is the byte string `b"\xff\x80"` — a CLVM cons pair marker followed by a single small atom, omitting the second required child.
2. Wrap it in a `SpendBundle` and submit it through the normal transaction-submission path so it reaches `MempoolManager.validate_spend_bundle()`.
3. `is_clvm_canonical(bytes(coin_spend.solution))` is invoked at `chia/full_node/mempool_manager.py:723-726`; the loop in `is_clvm_canonical()` reads `clvm_buffer[2]` on a 2-byte buffer, raising `IndexError` instead of returning a controlled `False`/error, demonstrating the out-of-bounds-style read triggered by attacker-supplied, truncated CLVM bytes.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
