### Title
Race between `BidPool.stop()` closing `newBidCh`/`bidMsgCh` and concurrent `AddBid`/`HandleBid` sends causes a send-on-closed-channel panic - (File: `kaiax/auction/impl/bid_pool.go`)

### Summary
`BidPool.AddBid` and `BidPool.HandleBid` are reachable from an unprivileged bidder via the `auction_submitBid` RPC endpoint [1](#0-0) . Both functions check the `running` flag with `atomic.LoadUint32(&bp.running)` and then, without holding any lock that serializes against `stop()`, later write to `bp.newBidCh` / `bp.bidMsgCh` [2](#0-1) [3](#0-2) . `stop()`, invoked on every new block whenever the chain is syncing or the auctioneer/entry point becomes unset via `PostInsertBlock`, clears `running` and then unconditionally closes both channels [4](#0-3) [5](#0-4) . This is structurally the same bug class as CVE-2024-46803: a "check enabled, then act on a resource that another path may tear down concurrently" race, where the disable path proceeds without synchronizing with in-flight users of the resource.

### Finding Description
`AddBid` performs `atomic.LoadUint32(&bp.running)` as a guard, then does bid validation/insertion, and finally sends on `bp.newBidCh` at line 271 [2](#0-1) . Similarly `HandleBid` checks `running` and then sends into `bp.bidMsgCh` inside a `select`/`default` [3](#0-2) . Sending on a closed Go channel panics immediately, regardless of whether it's wrapped in a `select` with `default`.

Meanwhile, `stop()` toggles `running` to 0 and then closes both channels via `close(bp.bidMsgCh)` and `close(bp.newBidCh)` [5](#0-4) . There is no mutex or WaitGroup gate that prevents `AddBid`/`HandleBid` from being mid-flight (having already passed the `running` check, i.e., observed `running==1`) at the moment `stop()` executes `close(...)`. Since `AddBid` performs multiple non-trivial steps (signature verification, pool insertion under `bidMu`) between the atomic check and the channel send, there is a non-trivial window for `stop()` to run and close the channel before the send executes.

`stop()` is driven by `AuctionModule.Stop()` and, more importantly, by every call to `PostInsertBlock`, which is invoked on **every new block** when the node is synchronising or the on-chain auctioneer/auction-entry-point registry values become unset [4](#0-3) . Because these conditions are governed by on-chain registry state and downloader sync status, they can flip during normal chain progression while bid submissions are concurrently arriving through the public `auction_submitBid` RPC (guarded only by `Public: false`, but still reachable to a permitted unprivileged caller/bidder) [6](#0-5)  and via P2P bid gossip through `HandleBid`.

### Impact Explanation
A successful race causes a `panic: send on closed channel` in the goroutine executing `AddBid` (invoked synchronously from the RPC handler) or in `HandleBid` (invoked from the bid-gossip handler path). Depending on how these paths are wired into the node's panic recovery, this can crash the RPC-serving goroutine or the entire CN node process handling auction duties, terminating in-flight auction settlement for that block and potentially causing that node to diverge from peers in which blocks/bids it processes (e.g., missing an auction settlement it would otherwise have included), analogous to how the original CVE describes a NULL pointer dereference reached through the same "check disabled state, then still act on the resource" ordering flaw.

### Likelihood Explanation
`start()`/`stop()` toggling happens routinely on the auctioning node: `PostInsertBlock` calls `stop()` (via `atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)` plus the guarded channel closes) whenever downloader sync is in progress or the auction registry values are cleared, which can occur naturally as blocks are processed [4](#0-3) . A bidder submitting bids in a tight loop around block boundaries via `auction_submitBid` increases the probability of hitting the narrow window between the `running` check and the channel send in `AddBid`.

### Recommendation
Serialize the `running` check with the channel writes and the channel close under the same mutex (e.g., wrap `stop()`'s close under `bidMu`/a dedicated lock, and hold that same lock across the check-then-send in `AddBid`/`HandleBid`), or replace direct `close()` + `chan<- send` with a `select` guarded by a `done`/`quit` channel (similar to the pattern in `event/subscription.go`'s `quitWithError`) so a send can never race a close. Alternatively, avoid closing and recreating channels altogether and instead have `handleBidMsg`/`handleNewBid` exit via a distinct `stopCh` while `AddBid`/`HandleBid` use `select { case ch <- bid: case <-stopCh: }`.

### Proof of Concept
1. Node is running as CN with auction enabled and `bp.running == 1`.
2. Attacker (or any client) sends a burst of `auction_submitBid` RPC calls concurrently with block processing.
3. As a new block arrives, `PostInsertBlock` determines the auction registry values are unset (or sync begins) and calls `atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)` then `bp.stop()`, which executes `close(bp.newBidCh)`.
4. A concurrently-running `AddBid` call that already passed the `running` check at line 253 proceeds through validation/insertion and reaches `bp.newBidCh <- bid` at line 271 after the channel has been closed, causing an immediate panic.

Note: I was unable to execute this locally to confirm the panic occurs in practice (index provides read-only source access); the above is derived from static code-path analysis of the check-then-use ordering and the unsynchronized `close()` in `stop()`.

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)

func (bp *BidPool) stop() {
	// Stop the bid pool.
	atomic.CompareAndSwapUint32(&bp.running, 1, 0)
	bp.clearBidPool()

	// Only close channels if they haven't been closed before
	if atomic.CompareAndSwapUint32(&bp.stopped, 0, 1) {
		close(bp.bidMsgCh)
		close(bp.newBidCh)
	}
	bp.wg.Wait()
}

func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}

func (bp *BidPool) HandleBid(peerID string, bid *auction.Bid) {
	if atomic.LoadUint32(&bp.running) == 0 || bid == nil {
		return
	}

	// Check rate limit for this peer
	if !bp.checkRateLimit(peerID) {
		logger.Trace("Rate limit exceeded for peer", "peerID", peerID)
		return
	}

	select {
	case bp.bidMsgCh <- bid:
	default:
		logger.Trace("Bid queue is full, dropping bid", "peerID", peerID)
	}
}

func (a *AuctionModule) PostInsertBlock(block *types.Block) error {
	if a.Downloader.Synchronising() || !a.ChainConfig.IsRandaoForkEnabled(block.Number()) {
		atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)
		return nil
	}

	if !a.updateAuctionInfo(block.Number()) {
		logger.Debug("stop auction since auctioneer or auction entry point is not set")
		atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)
		return nil
	}
