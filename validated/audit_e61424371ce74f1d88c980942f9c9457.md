### Title
Daemon Logs Unredacted Sensitive Payload for Unknown Commands, Bypassing `redact_sensitive_data()` - ([File: chia/daemon/server.py])

### Summary
Chia's local daemon (`chia/daemon/server.py`) implements a redaction helper, `redact_sensitive_data()`, specifically to keep secrets such as passwords, private keys, mnemonics, and other credentials out of the debug log stream when it records incoming websocket messages. However, one logging call site in `WebSocketServer.handle_message()` bypasses this helper entirely and logs the raw message dictionary at `ERROR` level whenever the daemon receives an unrecognized command. This mirrors the CVE-2024-8365 bug class: a code path that is supposed to sanitize sensitive request fields before writing them to a log/audit trail has a regression/gap that allows plaintext secrets to reach the log file.

### Finding Description
`redact_sensitive_data()` recursively walks a message dict and replaces any key containing `"pass"`, `"key"`, `"secret"`, or `"mnemonic"` with a redacted placeholder before the daemon logs the raw inbound websocket payload: [1](#0-0) 

This helper is correctly applied at the primary ingestion point, where every incoming message is logged at `DEBUG` after being redacted: [2](#0-1) 

The dedicated test `test_message_logging_redaction` confirms this is the intended security control for the daemon's local RPC/keychain boundary: [3](#0-2) 

However, `handle_message()` has a second, independent log statement that logs the **original, unredacted** `message` object (not the redacted copy) whenever the `command` field does not match any entry in `keychain_commands`, `"ping"`, or `get_command_mapping()`: [4](#0-3) 

Because this branch is reached for any unrecognized `command` string, any local RPC/websocket caller can send a message whose `data` field contains arbitrary keys/values it wants captured — including values that look like passwords, keys, secrets, or mnemonics — paired with a bogus/unknown `command`. The daemon will then write the entire unredacted payload to the log at `ERROR` level (which is typically always enabled, unlike the `DEBUG`-gated redacted path).

### Impact Explanation
This is a `CWE-532: Insertion of Sensitive Information into Log File` issue analogous to the reported Vault CVE, where a regression caused audit logs to retain plaintext secrets that were supposed to be redacted. In Chia's daemon, sensitive data (e.g., keyring passphrases, private keys, mnemonics, or other credentials sent as part of any daemon message) can persist in plaintext in daemon log files if the request happens to use, or is crafted to use, a non-recognized `command` value. Log files are frequently collected for diagnostics/support or may be world/local-user readable depending on OS permissions, so this creates a credential-disclosure risk for anyone with access to the daemon's log files, without needing `DEBUG` logging enabled.

### Likelihood Explanation
Any local process able to open the daemon's TLS websocket (an operator tool, a compromised local wallet/CLI client, or a malicious local RPC caller with a valid client cert) can trigger this branch by sending a message with an unrecognized `command` and sensitive-looking fields in `data`. No special privilege beyond normal local-daemon connectivity is required, and the log call fires unconditionally at `ERROR` level rather than being gated behind `DEBUG`, making it easier to trigger than the primary redacted debug-log path.

### Recommendation
Route the `self.log.error(f"UK>> {message}")` statement through the same `redact_sensitive_data()` helper used for the primary message-received log (or log only the `command` name, not the full message/data), so unknown-command handling cannot leak sensitive payload fields into logs.

### Proof of Concept
1. Establish a local TLS websocket connection to the daemon (as any local client with a valid daemon certificate).
2. Send a JSON message with an unrecognized `command`, e.g.:
```json
{
  "command": "not_a_real_command",
  "ack": false,
  "data": {"password": "secret_password", "private_key": "sensitive_key_data"},
  "request_id": "1",
  "destination": "daemon",
  "origin": "test"
}
```
3. The daemon's `handle_message()` falls through to the `else` branch since `not_a_real_command` matches no entry in `keychain_commands` or `get_command_mapping()`, executing `self.log.error(f"UK>> {message}")` with the full, unredacted `message` dict — including `password` and `private_key` in plaintext — written to the daemon's `ERROR`-level log, in contrast to the `DEBUG`-level redacted log entry produced for the same connection at line 298.

```python
def redact_sensitive_data(obj: Any, redaction_triggers: Collection[str] = ("pass", "key", "secret", "mnemonic")) -> Any:
    """Recursively redact sensitive data from nested dictionaries."""
    if isinstance(obj, dict):
        return {
            key: "***<redacted>***"
            if any(trigger.casefold() in key.casefold() for trigger in redaction_triggers)
            else redact_sensitive_data(value, redaction_triggers)
            for key, value in obj.items()
        }
    else:
        return obj
```
