### Title
Division-by-zero panic in `consolidatedNode.Split` when a proposer's CN and CL staking amounts are both zero - (File: `kaiax/staking/staking_info.go`)

### Summary
`consolidatedNode.Split` divides by `totalAmount = StakingAmount + CLStakingInfo.CLStakingAmount` without checking that this sum is non-zero. This function is invoked unconditionally for the block proposer's consolidated node whenever a `CLStakingInfo` is attached to it (regardless of whether the proposer meets any minimum-stake eligibility threshold), during deferred reward distribution in `getter.go`. If a validator that becomes block proposer has both its CN staking amount and its consensus-liquidity (CL) staking amount reduced to zero while still having a registered `CLStakingInfo` entry, reward computation will divide by zero and panic.

### Finding Description
`consolidatedNode.Split` is defined as: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)   // <-- div by zero if totalAmount == 0
	...
}
```

There is no guard ensuring `totalAmount != 0`. `Split` is only safely invoked from `assignStakingRewards`/`assignStakingRewardsFlex` where the caller has already checked `StakingAmount > minStake`, but it is also invoked unconditionally for the **proposer's** node in `specWithProposerAndFundsFlex`, based solely on `cn.CLStakingInfo != nil`, without any staking-amount eligibility check: [2](#0-1) 

```go
cns := si.ConsolidatedNodes()
for _, cn := range cns {
	if cn.RewardAddr != config.Rewardbase {
		continue
	}
	if cn.CLStakingInfo == nil {
		break
	}
	cnAmount, clAmount := cn.Split(proposer)   // no minStake/zero check here
	...
}
```

If the proposer's CN stake (`StakingAmount`) has been withdrawn to zero (e.g., via CNStaking contract withdrawal) and its associated consensus-liquidity pool also has zero `CLStakingAmount` (e.g., all CL stakers withdrew via the public `CLPool` contract, an action reachable by unprivileged stakers), then `totalAmount` becomes `0`, and `Split` performs `big.Int.Div(x, 0)`, which panics in Go's `math/big` package. This function is exercised in `FinalizeState`/`GetDeferredReward`/`GetBlockReward` reward-computation paths on every full node processing that block.

### Impact Explanation
A panic inside block-reward computation during `FinalizeState` (or the `kaia_getReward`/`kaia_getRewardsAccumulated` RPC handlers, which call the same code path) would crash the node process or otherwise interrupt state-transition/consensus execution for that block on every node computing it, causing a chain halt / state divergence between nodes that crash versus recover — a consensus-availability failure. This satisfies "acceptance of an invalid transaction or block" / "state divergence between honest nodes" categories.

### Likelihood Explanation
Reaching the zero/zero condition requires: (1) a validator whose CN staking amount has dropped to (or started at) zero KAIA while still being included in the AddressBook consolidated node list, and (2) that same validator's registered consensus-liquidity pool (`CLStakingInfo`) also having zero staked amount, and (3) that validator being selected as the block proposer. Withdrawing CL stake down to zero is achievable by ordinary stakers (unprivileged public callers) interacting with the CL staking pool contract, and CN stake likewise can be withdrawn via the staking contract. This is a Prague-hardfork-only path (`CLStakingInfo` only exists since Prague) and requires a specific but plausible validator/staking configuration rather than a single crafted transaction, so likelihood is moderate rather than trivial.

### Recommendation
In `consolidatedNode.Split`, guard against `totalAmount.Sign() == 0` and return `(amount, big.NewInt(0))` (treat as CN-only) in that case, mirroring the `CLStakingInfo == nil` branch. Additionally, in `specWithProposerAndFundsFlex` (and the analogous non-flex `specWithProposerAndFunds`, which was not fully reviewed here but likely shares the same call pattern — this could not be fully verified due to tool-call limits), avoid calling `cn.Split` when both `StakingAmount` and `CLStakingInfo.CLStakingAmount` are zero.

### Proof of Concept
1. Configure a validator (proposer) in the AddressBook with `StakingAmount = 0` (withdraw all CN stake) but still registered.
2. Register/keep a `CLStakingInfo` entry for that validator's node with `CLStakingAmount = 0` (all CL stakers withdraw via the public CL pool).
3. Have this validator be elected/act as block proposer for a block (Prague active, non-Simple governance policy, deferred fee mode).
4. During `FinalizeState`/`GetDeferredReward` reward computation, `specWithProposerAndFundsFlex` calls `cn.Split(proposer)` for this proposer's consolidated node; since `CLStakingInfo != nil`, it computes `totalAmount = 0 + 0 = 0` and executes `clAmount.Div(clAmount, totalAmount)`, causing a `big.Int` division-by-zero panic that crashes the node/consensus routine processing that block.

Note: I was unable to view the body of `specWithProposerAndFunds` (non-flex path) with the remaining tool budget to confirm it has an identical unconditional call pattern; this should be verified in a follow-up review, but the vulnerable `Split` function and the unconditional Flex-path call site are directly confirmed in the code above.
