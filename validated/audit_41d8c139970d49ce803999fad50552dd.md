### Title
PedPoP leaks another sender's secret share through an unverified PoP blame proof - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` can return an `EncryptionKeyProof` before the encrypted message's Schnorr proof-of-possession is verified, allowing a participant to obtain the ECDH key for an arbitrary copied `msg.key` and decrypt another sender's secret-share ciphertext. [1](#0-0) [2](#0-1) 

### Finding Description
`EncryptedMessage::read` accepts attacker-controlled `key`, `pop`, and ciphertext fields without checking that the sender knows the discrete logarithm of `key`. [3](#0-2) 

During `calculate_share`, `Encryption::decrypt` only queues `msg.pop` for batch verification, then immediately computes `enc_key * msg.key`, decrypts the ciphertext, and constructs an `EncryptionKeyProof` for that ECDH point. [4](#0-3) [5](#0-4) [6](#0-5) 

If the decrypted plaintext is a non-canonical scalar, `calculate_share` returns `PedPoPError::InvalidShare` containing `Some(blame)` before `batch.verify_with_vartime_blame` can validate the queued PoP. [7](#0-6) [8](#0-7) 

The returned proof contains the raw ECDH point and a DLEq proof binding it to the recipient's registered encryption key and the attacker-selected `msg.key`. [9](#0-8) [10](#0-9) 

That proof is intentionally sufficient to decrypt the associated ciphertext, since `decrypt_with_proof` passes `proof.key` directly to `cipher` and applies the resulting keystream. [11](#0-10) 

### Impact Explanation
An expected DKG participant can copy the public `msg.key` from another participant's authenticated `EncryptedMessage` to the victim, place that key in a malformed share with an invalid PoP, and cause the victim's error path to disclose the victim's ECDH key for the copied `msg.key`. [12](#0-11) 

Because normal encryption derives the same ECDH point from the sender-selected `msg.key` and the recipient's encryption public key, the disclosed `proof.key` also decrypts the copied honest message's ciphertext. [13](#0-12) [14](#0-13) 

This exposes a secret share intended only for the victim, violating the confidentiality that PedPoP's per-message encryption and proof-of-possession are meant to provide. [15](#0-14) 

For a threshold of one, the leaked share is the sender's sole polynomial coefficient because `polynomial` returns `coefficients[0]` when `t == 1`. [16](#0-15) [17](#0-16) 

### Likelihood Explanation
The attacker needs only an expected participant slot, an observed serialized share containing the target `msg.key`, and the ability to submit a malformed `EncryptedMessage` to `calculate_share`. [18](#0-17) [3](#0-2) 

The malformed message does not require a valid PoP or knowledge of the copied key's discrete logarithm; it succeeds whenever the keystream-decoded plaintext fails `C::F::from_repr`, which is a realistic outcome for attacker-chosen ciphertext bytes. [1](#0-0) [5](#0-4) 

### Recommendation
Do not create or return an `EncryptionKeyProof` until the corresponding `msg.pop` has been successfully verified. [2](#0-1) 

The implementation should either synchronously verify `msg.pop` before deriving `proof.key`, or defer non-canonical-plaintext errors until after the queued PoP batch succeeds and only then disclose the proof. [19](#0-18) [20](#0-19) 

### Proof of Concept
Conceptually, for an honest Alice-to-Bob share `M_ab` with public ephemeral key `K_ab`, Eve submits an Eve-to-Bob `EncryptedMessage` containing `K_ab`, any canonically encoded invalid Schnorr PoP, and random ciphertext. [3](#0-2)

fn polynomial<F: PrimeField + Zeroize>(
  coefficients: &[Zeroizing<F>],
  l: Participant,
) -> Zeroizing<F> {
  let l = F::from(u64::from(u16::from(l)));
  // This should never be reached since Participant is explicitly non-zero
  assert!(l != F::ZERO, "zero participant passed to polynomial");
  let mut share = Zeroizing::new(F::ZERO);
  for (idx, coefficient) in coefficients.iter().rev().enumerate() {
    *share += coefficient.deref();
    if idx != (coefficients.len() - 1) {
      *share *= l;
    }
  }
  share
}
