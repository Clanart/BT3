### Title
Attacker-controlled `n` field drives eager `Vec` allocation in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` in `crypto/dkg/src/lib.rs` reads the participant count `n` as an unchecked `u16` from the input stream and immediately reserves `Vec::with_capacity(usize::from(n))` for `Interpolation::Constant` before any of the `n` scalars are confirmed present. This is the same bug class as CVE-2017-14165: allocation size decided solely by a header length field, independent of the actual data supplied. [1](#0-0) 

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574`), the fields `t`, `n`, and `i` are read as little-endian `u16`s directly from the attacker-supplied reader (`lib.rs:591-602`). If the next byte selects `Interpolation::Constant`, the code executes `Vec::with_capacity(usize::from(n))` and only then begins reading the `n` scalars (`lib.rs:607-613`). A ~10-byte input with `interpolation = 0` and `n = 0xFFFF` forces an immediate ~2 MiB heap reservation (`65535 × size_of::<C::F>()`) before the first `read_exact` on missing data returns an error. The same `n` then also drives `n` `read_G` calls into a `HashMap` (`lib.rs:620-623`).

The function is reachable per the engagement rules: `ThresholdKeys::read` is an explicitly listed sink for untrusted bytes. The only mitigating factor is the `u16` width, capping the forced allocation at ~2 MiB per call — but there is no check that `n <= actual params` and no correlation of `n` to bytes actually present before allocation.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` obtains a ~2000x memory amplification per call (≈10 bytes in → ~2 MiB allocated). Repeated invocations, or many parallel key-loading paths, exhaust memory and cause denial of service of the signing/key-management process — the same remote-DoS outcome as the reference GraphicsMagick bug, bounded at the `u16` ceiling rather than `u32`.

### Likelihood Explanation
Any code path that deserializes persisted or peer-delivered `ThresholdKeys` (the DKG/PedPoP/musig output type consumed across the codebase) exposes this. The trigger is a trivially craftable byte string; no valid points, signatures, or threshold participation are required to reach the allocation, since `with_capacity` executes before data validation.

### Recommendation
- Do not `with_capacity` from the untrusted `n`; push into `Vec::new()` so allocation tracks bytes actually read.
- Validate `t`/`n`/`i` via `ThresholdParams::new` *before* allocating the interpolation vector.
- Consider a hard cap (e.g., `MAX_PARTICIPANTS`) consistent with protocol limits.

### Proof of Concept
Feed `ThresholdKeys::read::<C>` a buffer containing: `id_len`/`C::ID` (valid), `t = 0x0001`, `n = 0xFFFF`, `i = 0x0001`, `interpolation = 0x00`, then EOF. The function allocates `Vec::with_capacity(65535)` (~2 MiB of `C::F`) at `crypto/dkg/src/lib.rs:608` and only then fails on the missing scalar bytes — reproducing the header-length-driven excessive allocation.

Note: the stronger unbounded variants of this pattern found in the tree (`Block::read` u32 tx count in `coordinator/tributary/src/block.rs:88-95`, `Payment`/`Plan`/`InInstruction` u32-length `vec![0; len]` in `processor/src/plan.rs`, `networks/ethereum/src/router.rs`, and `Transaction::read`/`SignData::read` in `coordinator/src/tributary/transaction.rs`) are outside the permitted scope, so this finding is reported at the `u16`-bounded magnitude reachable within the in-scope crates.
