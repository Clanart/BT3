### Title
Unprivileged caller can drain the entire contract balance of any registered reward token lacking a convertor/locker/helper via `compound()` - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` iterates over **all** registered `rewards` unconditionally (independent of the caller-supplied `_lps`/`_rewards`) and, for any reward whose `convertor`, `locker`, or `helper` is unset, transfers the contract's entire `balanceOf(address(this))` of that token to `msg.sender`. Because the amount sent is derived from the contract's total balance rather than the amount actually claimed for the caller in that transaction, any unprivileged caller can trigger this branch with a trivial/empty claim and sweep balances that belong to other users or accumulated dust.

### Finding Description
The second loop in `compound()` runs over `rewards.length` regardless of what the caller passed as `_lps`/`_rewards`: [1](#0-0) 

For each registered reward, `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))` is computed as a **global** balance snapshot, not a delta tied to what `multiclaimOnBehalf` just sent in for `msg.sender`. If `_convertor == address(0)`, `_locker == address(0) || !_lockMgp`, and `_helperAddress == address(0)` (i.e., the reward is "unconfigured" — the exact precondition stated in the question), the code falls to the final `else` branch and does `IERC20(_tokenAddress).safeTransfer(msg.sender, receivedBalance)` — the **entire** contract balance, not just what was claimed on behalf of `msg.sender`: [2](#0-1) 

Similarly, the first loop's sweep of non-compoundable tokens also relies on `balanceOf(address(this))` rather than a per-call delta: [3](#0-2) 

There is no registry check against what the caller actually claimed via `multiclaimOnBehalf` in the same transaction — only `compoundableRewards[token]` (a boolean set once via `addReward`) gates the first loop, and nothing gates the second loop's fallback `else` at all. Since `masterMagpie` routes claimed reward tokens to `address(this)` as an intermediate step (per `multiclaimOnBehalf` semantics) before this contract forwards them to `msg.sender`, any residual balance — from dust, rounding, partial conversions, or another user's claim still pending processing — sits in `address(this)` and is fully exposed to whichever caller invokes `compound()` next while that reward token lacks a convertor/locker/helper.

Regarding the specific invariant framed in the question (`_minRec` vs `obtainedmWomAmount` in `SmartWomConvert`): that reconciliation only applies to the `IConverter.convertFor(...)` branch, which requires `_convertor != address(0)`. Under the stated precondition ("no convertor ... configured"), that branch is never entered for the affected reward, so the `_minRec`/`SmartWomConvert` mismatch as literally phrased does not apply to this code path — the exploit here is instead the unconditional full-balance sweep in the final `else` branch shown above.

### Impact Explanation
Any unprivileged EOA can call `compound()` with minimal/dummy `_lps`/`_rewards` (or none at all, since the second loop is unconditional) and, for a registered reward token with no convertor/locker/helper set, receive the contract's **entire** balance of that token — including balances that logically belong to other users whose claims routed through the same contract. This is direct theft of user/protocol funds, matching Critical severity, contingent on the misconfiguration precondition (a registered reward with none of convertor/locker/helper set) and the contract holding a nonzero balance of that token at call time.

### Likelihood Explanation
Exploitability requires: (1) at least one registered reward in `rewards` with `convertor == address(0)`, and either `locker == address(0)` or `_lockMgp == false`, and `tokenHelper == address(0)`; and (2) a nonzero balance of that token sitting in the contract (plausible via dust/rounding from prior calls, or overlapping claims). No capital is required by the attacker — a single call with an empty or trivial `_lps` array suffices, since the drain loop does not depend on the caller's claimed amount. This is a misconfiguration-dependent precondition explicitly stated in the question, so likelihood is tied to that specific reward configuration state rather than being always exploitable.

### Recommendation
Track the actual amount claimed/received for `msg.sender` within the same transaction (e.g., via balance deltas captured immediately before/after `multiclaimOnBehalf`, or by having `multiclaimOnBehalf` return per-token amounts) and use that delta — not the contract's total `balanceOf`— for both the non-compoundable sweep and the registered-reward fallback transfer. Additionally, require that every registered reward have at least one of `convertor`/`locker`/`helper` set (or explicitly disallow the bare `safeTransfer` fallback) to eliminate the unconfigured full-balance-sweep path.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `ManualCompound` with a mock `masterMagpie` whose `multiclaimOnBehalf` is a no-op (simulating an empty/trivial claim).
2. Call `addReward(tokenX, address(0), address(0), address(0))` as owner to register `tokenX` with no convertor/locker/helper.
3. Simulate residual balance: transfer `1000` `tokenX` directly to the `ManualCompound` contract (representing dust/another user's stuck claim).
4. From an unprivileged attacker EOA (not owner, not `masterMagpie`), call `compound([], [], 0, 0, false)`.
5. Assert attacker's `tokenX` balance increased by `1000` and `ManualCompound`'s `tokenX` balance is now `0`, despite the attacker never having deposited/claimed anything — demonstrating full-balance theft via the unconditional fallback `else` branch at `rewards/ManualCompound.sol:156-158`.
