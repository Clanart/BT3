### Title
Trust granted via `safe.directory` is permanent and reusable by a different, untrusted repository at the same path - ([File: app/src/lib/git/config.ts])

### Summary
The external report describes a broken invariant: a privilege (the savior) is bound to a *resource identifier* (the SAFE) rather than to the *entity that was trusted when the privilege was granted* (the original owner), so the privilege silently carries over when the resource changes hands. GitHub Desktop has the same class of bug in its "unsafe repository" trust flow: trusting a directory adds the path to the global `safe.directory` git config permanently, and nothing in the codebase ever removes it — even when the repository is removed from Desktop. The trust is bound to a *path string*, not to the specific repository/content the user inspected and approved.

### Finding Description
When Desktop encounters a repository whose directory is owned by a different OS user than the current process, `getRepositoryType` reports `kind: 'unsafe'` [1](#0-0) . The UI then offers to "Trust Repository", which calls `addSafeDirectory(path)`, permanently appending the path to the global `safe.directory` git config via `addGlobalConfigValueIfMissing('safe.directory', path)` [2](#0-1) . This flow is wired up from two dialogs: `AddExistingRepository.onTrustDirectory` [3](#0-2)  and `MissingRepository.onTrustDirectory` [4](#0-3) .

Once added, this path is never removed. A codebase-wide search finds `addSafeDirectory` calls only in these two dialogs, with no corresponding "remove safe directory" function anywhere, and repository removal (`_removeRepository` in `app/src/lib/stores/app-store.ts`) does not touch `safe.directory` at all. So the trust decision is a permanent, global, path-keyed allow-list entry that outlives:
- the specific repository content the user reviewed,
- the Desktop-tracked `Repository` record itself (removing the repo from Desktop leaves the git config entry behind),
- and the OS-level ownership check `safe.directory` exists to enforce in the first place.

This mirrors the report's flaw exactly: `LiquidationEngine.protectSAFE()` binds a savior to the SAFE identifier rather than the owner at grant-time, so a transfer of the SAFE silently carries the privilege to a new, untrusted party. Here, `addSafeDirectory` binds "trusted" status to a filesystem path string rather than to the specific repository/owner the user vetted, so if that same path is later repopulated by different, untrusted content (e.g., a shared/multi-user machine, a mounted network share, `/tmp`, a Windows redirected profile folder, or any location an attacker can write to after the original repo is deleted), Git's core cross-user ownership protection is silently bypassed for the new content — with no re-prompt, no warning, and no way for the user to know the exception still applies.

### Impact Explanation
`safe.directory` exists specifically to stop an attacker who can write to a shared/multi-tenant path from planting a malicious `.git/config` (or repo-local hooks, `core.fsmonitor`, `core.pager`, etc.) that another user's Git client would otherwise refuse to honor due to ownership mismatch. Once a path is in the global exception list, all of Git's protections for that path are permanently disabled for every future occupant of that path — including a subsequent attacker-controlled repository. This can lead to arbitrary command execution when Desktop (or the bundled Git) subsequently operates on the path, satisfying the "unprivileged attacker controls a cloned/fetched repository ... resulting in code execution" impact category. The corrupted value is the global Git `safe.directory` multi-valued config entry, which persists independent of Desktop's own `Repository` bookkeeping and independent of the actual current owner/content at that path.

### Likelihood Explanation
Exploitation requires a scenario where: (1) a user once trusted a path (common on shared machines, network drives, redirected home directories, CI-shared workspaces, or after deleting/recreating a repo at the same location), and (2) an attacker can later write different, untrusted git content to that exact path. This is a realistic condition on multi-user systems, shared network shares, and environments where paths are reused (e.g., temp directories, mapped drives, container volumes) — exactly the situations `safe.directory` was invented to defend against. No admin rights, local pre-existing malware, or leaked credentials are needed beyond the attacker's pre-existing ability to write to the shared path, which is the same threat model Git's own unsafe-repository protection assumes.

### Recommendation
Do not treat directory trust as a permanent, global, path-only exception:
- Remove the `safe.directory` entry when the corresponding repository is removed from Desktop (in `_removeRepository`), or when Desktop later detects the directory has become unsafe again for a *different* identity (e.g., re-check ownership/`.git` object identity, not just the path string).
- Consider scoping the exception more narrowly (e.g., tie it to the repository's `.git` directory identity or a fingerprint captured at trust-time) rather than just the top-level working directory path, so that content-swap at the same path does not inherit prior trust.
- At minimum, prompt the user to re-affirm trust if the path is re-added to Desktop after having been removed, rather than silently reusing the existing `safe.directory` allow-list entry.

### Proof of Concept
1. On a shared machine/network share, User A clones a repo to path `P`, sees the "unsafe repository" warning (different owner) and clicks "Trust Repository" in `AddExistingRepository` or `MissingRepository`, which calls `addSafeDirectory(P)` [5](#0-4) .
2. User A later removes the repository from Desktop and deletes the directory at `P` (Desktop's removal path does not revoke the `safe.directory` entry — no such revocation code exists anywhere in the codebase).
3. Attacker, with write access to the same shared path `P` (e.g., another OS account on the same shared drive), places a malicious Git repository at `P`, owned by the attacker, containing hostile `.git/config` settings (e.g., `core.fsmonitor`, `core.hooksPath`) designed to execute code when Git operations run against it.
4. User A (or the same Desktop instance) re-adds/opens path `P` in Desktop. Because `P` is still listed in the global `safe.directory` config, `getRepositoryType` no longer reports `kind: 'unsafe'` (per the ownership-bypass logic tested in `app/test/unit/git/rev-parse-test.ts` lines 131-154), so no warning is shown and no re-trust step is required — Desktop and the embedded Git silently operate on the attacker-controlled repository with full trust, executing the attacker's planted hooks/config.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```
