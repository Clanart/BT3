## Finding

CVE-2021-28040 describes uncontrolled recursion in OSSEC's XML parser (`_ReadElem`): deeply nested open/close tags drive the parser into unbounded recursive descent until the process crashes. The closest reachable analog in this codebase is the **unbounded recursive puzzle-layer unwrapping in the wallet's outer-puzzle driver chain**, which is exercised whenever a wallet parses an untrusted offer or spend bundle.

### Title
Unbounded recursion when unwrapping nested outer-puzzle layers from an untrusted offer/spend bundle - (File: `chia/wallet/outer_puzzles.py`, `chia/wallet/trading/offer.py`)

### Summary
`match_puzzle()`, `get_inner_puzzle()`, `get_inner_solution()`, `construct()` and `solve()` in `chia/wallet/outer_puzzles.py` dispatch to per-asset-type driver objects (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`) that all recurse into themselves via `self._match(...)`, `self._construct(...)`, `self._get_inner_puzzle(...)`, `self._get_inner_solution(...)` once per detected "outer" puzzle layer, with no depth limit. [1](#0-0) 
Each of the drivers follows the same pattern of `next_constructor = self._match(UnknownPuzzle(known_program=inner_puzzle))`, recursing purely based on the shape of the puzzle passed in. [2](#0-1) [3](#0-2) 

This recursion is driven directly by `coin_spend.puzzle_reveal`, i.e., attacker/counterparty supplied CLVM bytes, when a wallet parses an offer: `Offer._get_offered_coins()` calls `match_puzzle(parent_puzzle)` on every `parent_spend` in `self._bundle.coin_spends`, where `parent_spend.puzzle_reveal` comes straight from the (possibly malicious) offer. [4](#0-3) 
`Offer.from_spend_bundle()` similarly calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` on every coin spend while parsing an offer taken from the network/counterparty. [5](#0-4) 

### Finding Description
A malicious offer-maker (or spend-bundle author reaching wallet-side driver code) can construct a puzzle reveal consisting of many nested "outer puzzle" layers (e.g., repeatedly curried CAT/singleton/ownership/metadata/CR wrappers around an inner puzzle). Because the driver's `match`, `construct`, `get_inner_puzzle`, `get_inner_solution`, and `solve` methods recurse once per layer with **no depth check or bound**, a sufficiently deep nesting chain drives unbounded Python recursion analogous to the unrestricted `_ReadElem` recursion in the reported CVE. Elsewhere in this same codebase, the project explicitly recognizes this bug class and defends against it — `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py` is deliberately implemented iteratively "to avoid Python recursion limits on deeply nested CLVM," and Data Layer file-import code documents the same concern and expects a bounded `RecursionDepthExceededError`. [6](#0-5) [7](#0-6) 
The outer-puzzle driver chain (`chia/wallet/outer_puzzles.py` and its per-asset drivers) has no equivalent iterative rewrite or depth cap, unlike these hardened peers.

### Impact Explanation
Reaching Python's recursion limit inside `match_puzzle()`/`get_inner_puzzle()`/etc. raises an uncaught `RecursionError` while a wallet is processing a received/countersigned offer or spend bundle. This halts offer/trade processing for that request and can propagate as an unexpected wallet-side failure while evaluating attacker-supplied puzzle data, matching the "spend-triggered transaction-processing halt" impact category. It does not by itself cause fund loss, but it is a denial-of-service against normal offer/trade handling triggered purely by data an untrusted counterparty controls.

### Likelihood Explanation
Any counterparty who can hand a wallet an offer file or spend bundle can control `puzzle_reveal` bytes for coins in that bundle. Building deep nesting only requires stacking the outer-puzzle layers the wallet already recognizes (CAT/singleton/ownership/metadata/CR), each adding a bounded number of bytes per layer, so an attacker can trade off puzzle size against recursion depth within normal transaction/offer size limits. No signature or on-chain validity is required to merely trigger the recursive `match`/`get_inner_puzzle` code paths during offer inspection.

### Recommendation
Rewrite the outer-puzzle driver recursion (`match_puzzle`, `construct_puzzle`, `get_inner_puzzle`, `get_inner_solution`, `solve_puzzle` in `chia/wallet/outer_puzzles.py` and the `also()`-based recursion in each driver/`PuzzleInfo`) as an iterative loop with an explicit, enforced maximum layer depth, mirroring the iterative design already used in `sha256_treehash()`. Reject or safely error out on puzzle structures exceeding that depth before recursing further.

### Proof of Concept
Construct an `Offer`/`WalletSpendBundle` whose `coin_spends` contain a `puzzle_reveal` built by repeatedly currying one outer-puzzle layer (e.g., `CAT_MOD.curry(..., CAT_MOD.curry(..., CAT_MOD.curry(..., inner_puzzle))...)`) to a depth near or above Python's default recursion limit, then call `Offer.from_spend_bundle(bundle)` or `offer._get_offered_coins()` / `offer.arbitrage()` on the resulting `Offer` object; observe an uncaught `RecursionError` originating from the recursive `match()`/`get_inner_puzzle()` chain in `chia/wallet/outer_puzzles.py` and its drivers.
