## Title
Weak "GitHub host" heuristic in the credential-helper trampoline lets an attacker-controlled remote trigger a branded "Sign in to GitHub" prompt that exfiltrates the user's real credentials/PAT to the attacker's server - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

## Summary
When Git needs HTTP credentials for a remote, Desktop's credential-helper trampoline decides whether to treat the target host as a first-party "GitHub"/"GitHub Enterprise" endpoint or a "generic" Git host. That classification is based on a best-effort hostname regex and an unauthenticated HTTP probe, not on any cryptographic or account-bound trust anchor. An attacker who controls the remote (or a proxy in front of it) can shape the hostname/response to be misclassified as "enterprise", causing Desktop to pop the GitHub-branded sign-in dialog and send whatever the user types directly to the attacker's host.

## Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts:137-179` classifies the credential URL's host using increasingly weak heuristics: [1](#0-0) [2](#0-1) 

- A hostname simply matching `/(^|\.)(github)\./` (i.e. any host with a `github.` label anywhere, such as `github.attacker.com` or `foo.github.evil.com`) is classified `'enterprise'`, with no verification that it belongs to a real GitHub Enterprise deployment.
- If that fails, `isGitHubHost()` (`app/src/lib/api.ts:2429-2491`) makes an unauthenticated `HEAD` request to the attacker's own server and trusts the response entirely: [3](#0-2)  — it just checks for an `x-github-request-id` response header, which any attacker-run server can trivially add.

In `getCredential` (`app/src/lib/trampoline/trampoline-credential-helper.ts:94-135`), if the endpoint is classified as non-`'generic'` and there's no existing account bound to that exact endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`: [4](#0-3) 

`TrampolineUIHelper.promptForGitHubSignIn` (`app/src/lib/trampoline/trampoline-ui-helper.ts:80-104`) then opens the standard GitHub sign-in flow, using `beginEnterpriseSignIn` and pointing `setSignInEndpoint` at the **attacker-controlled origin** whenever the hostname isn't literally `github.com`: [5](#0-4) 

The resulting popup is the same UI users see when legitimately signing into GitHub/GHE (`PopupType.SignIn`), so a user is asked to authenticate ("Sign in to GitHub") against a host that only had to superficially resemble GitHub and fake one header — not something that requires any privileged access, malware, or unnatural user action beyond adding/cloning from a malicious remote and completing an auth prompt Desktop itself surfaces.

The broken invariant mirrors the ZetaChain bug: a background classifier (`GetPendingCCTXInTransit` / `getEndpointKind`) treats a superficial, spoofable signal (an out-tx tracker entry / a hostname substring plus an unauthenticated header) as proof of a security-relevant fact (settlement / genuine GitHub identity), when the actual guarantee requires something stronger (on-chain execution confirmation / TLS-bound, account-verified identity). Existing guards don't stop this path: `findGitHubTrampolineAccount`/exact endpoint matching only protects *already signed-in* accounts from being leaked to the wrong host — it does nothing to stop the *initial* sign-in prompt from being routed to an attacker's endpoint, and `isGitHubHost`'s certificate-error suppression (`suppressCertificateErrorFor`) further weakens TLS validation for this same probe.

## Impact Explanation
A successful attack results in credential/token exfiltration: the user's GitHub.com/GHE username+password, personal access token, or SSO-flow can be delivered straight to the attacker's server, believing they are authenticating to GitHub. This matches the in-scope "credential/token exfiltration" and "unauthorized OAuth or account binding" impact categories. The attack is triggered purely by adding/cloning a repository from an attacker-controlled remote (or a MITM proxy answering the HTTP probe) — no local access, no prior malware, no leaked credentials, and no unnatural steps beyond the normal "add a remote and let Desktop authenticate" workflow.

## Likelihood Explanation
Likelihood is moderate-to-high for a targeted phishing scenario: the attacker only needs a domain containing a `github.` label (or to answer a HEAD request with one extra header) and an HTTPS remote requiring auth. Desktop performs this classification automatically as part of normal git credential negotiation, without any explicit user opt-in step that would flag the host as untrusted. The main mitigating factor is that the user must actually type real credentials into the resulting dialog, and sufficiently attentive users might notice the URL shown in the dialog — but Desktop's own branding and flow make it look like a legitimate GitHub sign-in.

## Recommendation
- Do not classify arbitrary hosts as `'enterprise'`/GitHub-trusted based on substring/regex matches on the hostname or an easily-spoofable response header.
- Require the credential URL's origin to exactly match a previously configured, user-added GitHub Enterprise account endpoint before showing the GitHub-branded sign-in flow; for genuinely new hosts, always fall back to the plain "generic Git credentials" prompt, which does not imply GitHub trust.
- If auto-detection of GHES instances is kept for UX convenience, gate it behind an explicit user confirmation ("This looks like a GitHub Enterprise Server — sign in with your GitHub Enterprise account?") that clearly displays the actual hostname, and avoid suppressing certificate errors for this discovery probe.

## Proof of Concept
1. Attacker stands up an HTTPS server at `https://github.totallylegit-mirror.com` (matches `/(^|\.)(github)\./`) requiring HTTP basic auth, or alternatively any host that returns an `x-github-request-id` header on a `HEAD /api/v3/meta` request.
2. Victim adds this URL as a remote in Desktop (e.g. clones a repo hosted there, thinking it's a legitimate mirror/fork host).
3. Desktop performs a `git fetch`/`clone`; Git requests HTTP credentials via the trampoline (`createCredentialHelperTrampolineHandler`).
4. `getEndpointKind` classifies the host as `'enterprise'` (regex match or spoofed header) — `app/src/lib/trampoline/trampoline-credential-helper.ts:149-179`.
5. Since no existing account is bound to that origin, `ui.promptForGitHubSignIn(endpoint)` is invoked — `app/src/lib/trampoline/trampoline-credential-helper.ts:118`.
6. `TrampolineUIHelper.promptForGitHubSignIn` opens the standard "Sign in" popup pointed at the attacker's origin via `beginEnterpriseSignIn` + `setSignInEndpoint(origin)` — `app/src/lib/trampoline/trampoline-ui-helper.ts:87-93`.
7. The victim, believing they're authenticating to GitHub, enters their real GitHub Enterprise credentials/PAT, which are submitted to the attacker's server.

Note: I was not able to fully trace `SignInStore._setSignInEndpoint`'s connectivity-validation logic (`app/src/lib/stores/sign-in-store.ts`) within the available search budget to confirm exactly what checks it performs before allowing credential entry; if it performs a similarly weak header-based check, the PoC path above holds unmodified. A Devin session with full file access would be needed to verify this remaining piece precisely.

    return new Promise<Account | undefined>(async resolve => {

        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)

        await this.dispatcher.setSignInEndpoint(origin)
      }

        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,

      })
