## Analysis

The bug-class from H‑5 is: **an unrelated, unchecked actor can push a shared resource past its cap through a code path the primary gating logic never validates, destroying value that a legitimate party already paid for, with no recovery mechanism.**

The local analog is in `pallet-bandwidth`'s subscription FIFO cap combined with the permissionless `purchase()` entrypoint on `BandwidthManager.sol`.

`purchase()` lets **any caller** credit bandwidth to **any arbitrary `app`** value — the caller never has to be, or be authorized by, the app it is crediting: [1](#0-0) 

The credit lands in `pallet-bandwidth::on_accept`, which appends a new `Subscription` to a `BoundedVec` capped at 1024 entries, keyed purely by `(app_chain, app)` taken from the message body — again with no relationship required between the payer and the app being credited: [2](#0-1) 

The cap-eviction rule is: pushing onto a full list silently evicts the **oldest** subscription — including one that still has unconsumed `remaining_bytes` that a legitimate buyer paid for — emitting `SubscriptionEvicted` but performing no restitution: [3](#0-2) [4](#0-3) 

This is exactly the H‑5 pattern: a path outside the victim's control (anyone calling `purchase()` against the victim's `app` value) mutates shared accounting state (the FIFO cap) in a way the victim's own top-up logic never anticipated, permanently destroying already-paid-for value.

### Title
Permissionless `purchase()` targeting an arbitrary `app` lets an attacker force-evict a victim's paid, undrained bandwidth subscriptions - (File: `evm/src/apps/BandwidthManager.sol`, `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`BandwidthManager.purchase()` accepts an arbitrary `app` parameter chosen entirely by the caller and never checks that the caller is, or is authorized by, that app. Every successful purchase appends a `Subscription` to a `BoundedVec` capped at `MAX_SUBSCRIPTIONS` (1024) keyed by `(app_chain, app)`. When the list is full, the oldest entry — regardless of how much `remaining_bytes` it still holds — is silently evicted. An attacker can therefore repeatedly call `purchase()` naming a victim `app`, each time buying the cheapest configured tier for the minimum `months`, until the victim's legitimately purchased, still-live subscription(s) age out of the FIFO window and are evicted, destroying bandwidth the victim already paid for.

### Finding Description
- `purchase()` takes `app` as raw caller-supplied `bytes` with no ownership check: [5](#0-4) 
- `on_accept` derives the storage key purely from the message body's `app`/`chain` fields, not from any authenticated relationship to the payer: [2](#0-1) 
- The `Allowance` storage is a `StorageDoubleMap<StateMachine, AppKey, BoundedVec<Subscription, MaxSubscriptions>>`, with pushes onto a full list evicting the oldest, unconditionally: [6](#0-5) 
- The `SubscriptionEvicted` event and documentation explicitly acknowledge that eviction destroys `lost_bytes` that were paid for but not consumed, and frame this as only a "pathological repeat-buy" edge case — implicitly assuming the account making 1024 purchases is the app's own owner topping itself up, not an unrelated attacker griefing someone else's `app` key: [7](#0-6) [8](#0-7) 

The gate that later consumes this allowance (`try_consume`) has no knowledge of who purchased what — it only sums `remaining_bytes` across whatever survives in the list: [9](#0-8) 

Nothing in this pipeline verifies that the account calling `purchase()` for a given `app` is that app, is its deployer, or holds any relationship to it. This mirrors H‑5's core flaw: the module responsible for enforcing the cap (`pallet-bandwidth`) never checks who is adding entries, so an entirely unrelated, unprivileged actor can push the count of entries associated with a victim's key past the cap through a path the victim's own top-up flow does not gate.

### Impact Explanation
This is a direct, permissionless loss of prepaid funds. A victim app purchases a large, long-duration tier (e.g., the $1000/8MB tier) expecting to draw it down over months. An attacker who knows the victim's `app` identifier (public — it's the app's own contract address, visible in `BandwidthCredited`/`AllowlistChanged` events and in the `try_consume` call chain from `ProxyModule::on_accept`) can spend a small amount on 1024 minimal-tier purchases targeting that same `(chain, app)` key, evicting the victim's subscription and destroying the unconsumed bandwidth allowance the victim paid real fee-token value for — with **no restitution path**: eviction only emits an event, it does not refund the fee token already pulled at purchase time. The app is left needing to re-purchase bandwidth it already paid for, or its dispatches get rejected via `GateError::NoAllowance`/`Insufficient` once its allowance is gone — a direct loss-of-funds and availability impact matching the bounty's "bandwidth balances must move exactly once and only to the rightful beneficiary and amount" pivot.

### Likelihood Explanation
High. `purchase()` is a fully public, unauthenticated entrypoint; the `app` argument is attacker-controlled `bytes` with zero validation against `msg.sender`. The victim `app` value is public knowledge (it must be, for anyone to sponsor bandwidth for it — the docs explicitly promote cross-chain sponsorship of arbitrary apps by arbitrary payers). The only cost to the attacker is the fee-token price of 1024 cheap-tier purchases (bounded by governance-set tier prices, which can be small), and the ISMP dispatch/relay cost of getting each purchase message delivered — no privileged role, relayer collusion, or governance action is required.

### Recommendation
Bind subscription accounting to the payer/app relationship the protocol actually intends to support, or otherwise decouple "who may add entries to a given app's queue" from "arbitrary permissionless attacker." Options:
- Require `purchase()` (and the pallet's `on_accept`) to record subscriptions per `(app_chain, app, payer)` rather than a single shared FIFO per `(app_chain, app)`, so unrelated purchasers cannot evict each other's entries.
- Alternatively, disallow eviction of unexpired subscriptions entirely — reject new purchases (or require the caller to be the app itself / an allowlisted sponsor) once the cap is reached, rather than silently destroying paid-for allowance.
- At minimum, refund (or credit back in fee-token terms) the pro-rated value of `lost_bytes` to whoever paid for the evicted subscription, rather than only emitting `SubscriptionEvicted`.

### Proof of Concept
1. Victim app `V` (or a sponsor on its behalf) calls `BandwidthManager.purchase(app=V, tier=TierFour, months=12, chain="EVM-8453")`, paying the $1000-tier price and receiving a subscription in `Allowance[chain][V]` with a full year's byte budget and 12 months' `expires_at`.
2. Attacker `A` (unrelated to `V`) repeatedly calls `BandwidthManager.purchase(app=V, tier=TierOne, months=1, chain="EVM-8453")` — 1024 times, each crediting a minimal, cheap subscription to the same `(chain, V)` key: [1](#0-0) 
3. Each purchase triggers `Pallet::on_accept`, which calls `push_subscription`, appending to the `BoundedVec`; once the list hits 1024 entries, subsequent pushes evict the oldest entry — which is `V`'s year-long, largely undrained subscription — via the documented eviction path: [10](#0-9) 
4. `V`'s subscription is now gone from `Allowance[chain][V]`; the fee tokens `V` paid for it are unrecoverable, and its future dispatches are rejected by `BandwidthGate::try_consume` with `GateError::NoAllowance`/`Insufficient` once the attacker's minimal entries are drained: [11](#0-10)

```rust
impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
```

```text
## Subscription Lifecycle

Each `(chain, app)` row holds a FIFO list of subscriptions, capped at **1024** entries. Every purchase appends a new subscription — same-tier repurchases don't stack, they queue.

A subscription is immutable across its lifetime:

| Field             | Behavior                                                                       |
| ----------------- | ------------------------------------------------------------------------------ |
| `tier`            | Recorded at purchase time. Used for events and analytics, not for gating.      |
| `remaining_bytes` | Drains as the gate consumes messages. Pops once it hits zero.                  |
| `expires_at`      | Fixed at purchase. Never extends — a repurchase is a _new_ row, not a renewal. |
| `purchased_at`    | Insertion timestamp. Fixes FIFO order under same-block buys.                   |

### Drain order

The gate drains from the **head** of the list. Once the head is fully consumed it pops and continues into the next. If the next entry is expired it's swept silently — what you paid for is yours only until it expires.

This matters when you queue multiple tiers: the cheapest/oldest entry is consumed first regardless of which tier it came from. Plan top-ups so a higher tier doesn't sit behind a soon-to-expire lower tier you'd rather burn last.

### Eviction

Pushing onto a full list (1024 entries) evicts the **oldest** entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain. In practice this only happens under pathological repeat-buy behavior — at the default of one purchase per cycle, 1024 buys is years of headroom.
```
