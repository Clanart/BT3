## Title
First depositor / new-depositor value theft when a fully-utilized pool's bad debt is socialized down to zero assets - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent vaults `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`)

### Summary
The Zest vault's share-conversion helper `convert-to-shares-preview` treats a total-assets value of zero specially: if `total-supply-preview` is non-zero but `total-assets-preview` is zero, it returns `u0` shares instead of a 1:1 mint. This is the same root cause described in the referenced report (allowing the pool to reach a state where `totalAssets == 0` while `totalSupply != 0` through bad-debt socialization) but the Zest implementation makes the outcome strictly worse: a subsequent depositor can be minted **zero shares** for a non-zero deposit, permanently transferring their funds to the existing shareholders instead of merely diluting them 1:1.

### Finding Description
`convert-to-shares-preview` in the vault contracts computes: [1](#0-0) 
```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```
This is called directly by `deposit`: [2](#0-1) 

`total-assets` is `assets + interest`, where `assets` is the vault's undeployed cash and `interest` is the (debt − borrowed) unrealized interest: [3](#0-2) 

When a fully-utilized pool's borrower goes bad and `socialize-debt` is invoked (via the market's `vault-socialize-debt`/liquidation flow), `assets` is reduced (floored at 0) and, if the loss is total, `lindex` is zeroed: [4](#0-3) 
```
(new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
               (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
               u0))
...
(var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
```
If a pool is at (or near) 100% utilization when its borrower's position is liquidated for bad debt (`system-repay`/`socialize-debt-asset` flow in `v0-4-market.clar`), `assets` can be driven to `u0` while `total-supply` (the outstanding `zft` shares held by existing lenders) remains non-zero — exactly the precondition described in the referenced Sentiment report. At that point `ta = 0`, `ts != 0`.

Under this condition `convert-to-shares-preview` returns `u0` for **any** deposit amount. In `deposit`, the only check on the minted amount is `(asserts! (>= inkind min-out) ERR-SLIPPAGE)`. A caller who supplies `min-out = 0` (the natural/default value when unaware of the zeroed pool state, or simply because they expect normal behavior) will pass this check with `inkind = 0`. The deposit then proceeds: `receive-underlying` pulls the depositor's real tokens into the vault, `ft-mint? zft inkind recipient` mints **zero** `zft` tokens, and `assets` is increased by the deposited amount: [5](#0-4) 

The depositor's underlying tokens are absorbed into the vault's `assets` balance (backing the still-outstanding shares of pre-existing lenders) while the depositor receives no `zft` shares at all in return.

### Impact Explanation
This is a direct theft of user funds at rest: the new depositor's principal becomes redeemable only by the pre-existing shareholders (who now recover value from a pool that had previously reached total loss), while the new depositor holds zero claim on the vault. This is strictly worse than the "diluted shares" scenario in the referenced report — it is a 100% loss of deposited funds for the victim, transferred entirely to existing token holders. This falls squarely under the Critical impact class: "direct theft of user funds at rest ... or protocol insolvency" is avoided for existing LPs precisely because the new depositor's funds cover it.

### Likelihood Explanation
The precondition (pool driven to 100% utilization, then bad debt on the sole/majority borrower socialized to `assets == u0` while `total-supply > 0`) requires the same conditions as the underlying report: high interest accrual, a fast collateral price drop, or a fast debt-asset price increase combined with delayed liquidation. This is an edge case rather than a routine occurrence, but it is directly reachable through normal protocol operation (deposit → borrow at 100% utilization → bad-debt liquidation → socialize-debt) without any DAO misconfiguration, oracle compromise, or privileged action. Any regular user who deposits afterward with a non-restrictive `min-out` is exposed.

### Recommendation
- In `convert-to-shares-preview` (and the analogous `redeem`/`convert-to-assets-preview` paths), never allow minting a non-zero deposit for `u0` shares; either revert deposits when `ta == 0` and `ts != 0` (pool insolvency state) until resolved via a dedicated recovery/re-basing mechanism, or preserve share value with a virtual-offset/dead-shares approach used by standard ERC4626-style vaults.
- Enforce a hard cap preventing 100% utilization (reserve a minimum available-liquidity buffer) so `assets` cannot legitimately reach zero via `socialize-debt` while `total-supply` remains non-zero.
- Require `min-out > 0` to be enforced at the protocol/UI level, or add a `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check to `deposit` (mirroring the existing check already present in `redeem`) so that any deposit that would round/clamp to zero shares reverts instead of silently minting nothing.

### Proof of Concept
1. Vault starts with `assets = A`, `total-supply = S` (S shares outstanding from existing lenders).
2. A borrower borrows the full `A` via `system-borrow`, driving utilization to 100%.
3. Interest accrues; the borrower's collateral value drops or debt value rises before liquidation occurs.
4. Bad debt is liquidated; `socialize-debt` is invoked with `scaled-amount` covering the entire outstanding debt, reducing `assets` to `u0` (per the floor logic) and zeroing `lindex`. `total-supply` (`S`) remains unchanged since `zft` is a fungible token unaffected by `socialize-debt`.
5. `total-assets-preview` now returns `0`; `total-supply-preview` returns `S != 0`.
6. A new depositor calls `deposit(amount, min-out=0, recipient)`. `convert-to-shares-preview(amount)` evaluates the `(is-eq ta u0)` branch and returns `u0`.
7. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes (`0 >= 0`). `receive-underlying` transfers the depositor's `amount` into the vault; `ft-mint? zft 0 recipient` mints zero shares; `assets` becomes `amount`.
8. The depositor now holds `0` `zft` shares while the vault's `assets` balance (`amount`) backs the pre-existing `S` shares — the depositor has lost 100% of their deposit to existing shareholders. [1](#0-0) [2](#0-1) [6](#0-5)
