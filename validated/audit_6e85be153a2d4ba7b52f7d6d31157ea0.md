### Title
`Offer.get_root_removal()` can infinite-loop (wallet hang) when a malicious offer's coin spends contain a parent-pointer cycle - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_root_removal()` walks a coin's `parent_coin_info` chain within the offer's own removal set to find the "root" (non-ephemeral) ancestor coin. It assumes this parent chain is acyclic, but `parent_coin_info` is an attacker-controlled data field on a `Coin` object supplied inside a spend bundle, not something cryptographically bound to a real ancestor. A malicious offer counterparty can construct an offer whose coin spends contain two (or more) coins whose `parent_coin_info` fields reference each other, creating a cycle that is never resolved to a non-ephemeral removal, causing the traversal to loop forever.

### Finding Description
`get_root_removal` computes the set of "non-ephemeral" removals (coins whose parent is *not* also a removal in the bundle) and then walks backward through `parent_coin_info` links, looking each step for a removal with `name() == coin.parent_coin_info`, until landing on a non-ephemeral removal: [1](#0-0) 

Nothing here validates that the `parent_coin_info -> name()` links form a DAG. Since `Coin.parent_coin_info` is simply a field chosen by whoever constructed the `CoinSpend`s of the offer (the value is only meaningful/enforced on-chain via a real spend of that parent coin, which is never checked at this stage), an attacker crafting an offer file can set up two coins A and B where `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`. Both A and B will then satisfy "parent is in the removal set", so neither is classified as non-ephemeral, and the `while coin not in non_ephemeral_removals: coin = next(...)` loop in `get_root_removal` alternates between A and B forever — an unconditional infinite loop with no cycle/visited-set detection, exactly analogous to the reported `noCircularLinkage()` flaw (a traversal that assumes cycles can only be found along the path from the starting node, not anywhere in the reachable structure).

This mirrors the same bug class as the external report: a graph-walk that trusts caller-supplied "parent" links to be acyclic and has no visited-node tracking, so a cycle anywhere in the relevant subgraph causes unbounded recursion/looping instead of being detected and rejected.

`get_root_removal` is used by `get_pending_amounts()` (to attribute change/pending coins to their primary offered coin) and by `get_primary_coins()`, both of which are invoked when a wallet displays or summarizes an *untrusted* offer (e.g., an offer file received from a counterparty), which is a standard "view offer" / "get offer summary" flow before the user decides whether to accept it: [2](#0-1) [3](#0-2) 

### Impact Explanation
Unlike the Solidity original (which reverts due to out-of-gas), this is pure Python running inside the wallet process, so the loop does not terminate on its own — it will spin the event loop / thread indefinitely, hanging the wallet's request handling for that call. Any RPC or CLI flow that summarizes/evaluates an untrusted offer sent by a counterparty (before the user has agreed to anything) can be turned into a denial-of-service against that user's wallet process just by having them load a maliciously crafted offer file. This fits the "spend-triggered transaction-processing halt" acceptance criterion, scoped to the offers/trades surface reachable by an offer counterparty.

### Likelihood Explanation
Constructing an offer's `SpendBundle` with two coins whose `parent_coin_info` fields point at each other is straightforward — these are just data fields on `Coin` objects included in the `coin_spends` of the offer; nothing prevents a spend bundle (which need not be broadcastable/valid on-chain, only decodable as an `Offer`) from containing such coins as long as the recipient never has to actually push it to the network before inspecting it. Since offer files are exchanged and inspected out-of-band before acceptance, this is directly reachable by any offer counterparty.

### Recommendation
Add cycle detection to `get_root_removal` (and any other parent-chain walker in `offer.py`) by tracking visited coin names and raising a `ValueError` (or otherwise rejecting the offer) if a coin is revisited, instead of looping unconditionally. This matches the report's own recommendation of recording visited nodes to detect a cycle rather than assuming the graph is acyclic.

### Proof of Concept
Conceptually (Python, using the `Offer` API):
1. Construct two `Coin` objects, `coin_a` and `coin_b`, each an "addition"-looking coin included as a spend in the offer's `SpendBundle`:
   - `coin_a = Coin(parent_coin_info=coin_b.name(), puzzle_hash=ph_a, amount=amt_a)`
   - `coin_b = Coin(parent_coin_info=coin_a.name(), puzzle_hash=ph_b, amount=amt_b)`
2. Build a `SpendBundle` whose `coin_spends` include `CoinSpend(coin_a, ...)` and `CoinSpend(coin_b, ...)` (puzzle reveals only need to be well-formed CLVM for `Offer` parsing to succeed — the loop in question runs long before any on-chain validity is checked).
3. Wrap it into an `Offer` (`Offer(driver_dict, bundle, old_requested_payments)`) and call `offer.get_pending_amounts()` or `offer.get_primary_coins()`.
4. `get_root_removal(coin_a)` is invoked internally; since `coin_a.parent_coin_info == coin_b.name()` and `coin_b.parent_coin_info == coin_a.name()`, both are excluded from `non_ephemeral_removals`, and the `while` loop in `get_root_removal` never terminates, hanging the calling wallet code.

Note: I was unable to fully trace every RPC/CLI entry point that calls `get_pending_amounts`/`get_primary_coins`/`get_root_removal` through `trade_manager.py` before running out of tool iterations, so the precise externally-triggerable call chain (e.g., `get offer summary` RPC vs. `take offer` flow) should be confirmed directly in the code before treating this as fully proven end-to-end.

```python
    # This returns the non-ephemeral removal that is an ancestor of the specified coin
    # This should maybe move to the SpendBundle object at some point
    def get_root_removal(self, coin: Coin) -> Coin:
        all_removals: set[Coin] = set(self.removals())
        all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
        non_ephemeral_removals: set[Coin] = {
            c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
        }
        if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
            raise ValueError("The specified coin is not a coin in this bundle")

        while coin not in non_ephemeral_removals:
            coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

        return coin
```
