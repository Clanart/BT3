### Title
Divergent conflict-marker parsers between hunk extraction and reassembly cause silent misapplication of Copilot conflict resolutions - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Teku report describes two independent code paths (frame decoding vs. stream-limit enforcement) disagreeing about how to interpret attacker-controlled data, with the mismatch silently discarding/misaligning payload instead of failing loudly. GitHub Desktop's AI conflict-resolution feature has a structurally identical flaw: the function that extracts conflict hunks to build the Copilot prompt, `extractConflictHunks` [1](#0-0) , and the function that splices the model's per-hunk resolutions back into the file, `reassembleResolvedFile` [2](#0-1) , implement two separately-written, non-equivalent marker-boundary scanners over the same file content.

### Finding Description
`extractConflictHunks` scans line-by-line and terminates the "ours" section on the first line matching `baseMarker` or `separatorMarker` only — it never checks for a `theirsMarker` while inside the ours section [3](#0-2) . It only declares a hunk malformed (and discards it) if no `theirsMarker` is ever found before EOF [4](#0-3) .

`reassembleResolvedFile`, in contrast, validates a hunk with a forward lookahead that scans for the first line matching `reassemblyTheirsMarker`, breaking as soon as it is found, and only separately tracking whether any `reassemblySeparatorMarker` line preceded it [5](#0-4) . Because this lookahead is not scoped to "the ours section" the way `extractConflictHunks`'s collection loop is, a line that merely *resembles* a closing marker (`>{7}` followed by whitespace or EOL) appearing anywhere inside the real "ours" content — before the genuine `=======` separator — is treated by `reassembleResolvedFile` as the block's closing marker. Since no separator has been seen yet at that point, `hasSeparator` is `false`, so the entire well-formed conflict block is classified as malformed and copied through **verbatim, including the literal `<<<<<<<`/`=======`/`>>>>>>>` marker lines**, without incrementing `hunkIndex` [6](#0-5) .

`extractConflictHunks`, however, counted this block as a legitimate conflict and included it in the hunk list sent to and expected from the model. `validateResolutionPaths` only checks that the *count* of hunks matches between what was extracted and what the model returned — it never re-validates hunk boundaries against `reassembleResolvedFile`'s independent parser [7](#0-6) . The result: `hunkIndex` in `reassembleResolvedFile` is now permanently offset by one relative to the resolutions array for every conflict that follows in the file, so `hunkResolutions[0]` (the model's answer intended for the corrupted/skipped hunk) gets spliced into the *next* real conflict block instead, and so on for the rest of the file.

### Impact Explanation
The corrupted value is the reassembled file content that GitHub Desktop writes to disk and stages for commit. The attacker only needs to control content on one side of a merge/rebase/cherry-pick (e.g. a branch, PR, or file containing an innocuous string that happens to match `>{7}` followed by whitespace/EOL — plausible in code comments, changelogs, git tutorials, or test fixtures describing conflict markers). When the victim triggers Copilot-assisted conflict resolution on a file containing such content:
- The genuinely conflicting hunk is left with live, unresolved `<<<<<<<`/`=======`/`>>>>>>>` markers baked directly into the file that GitHub Desktop presents as "resolved."
- A later, unrelated hunk in the same file silently receives the wrong resolution (content meant for a different conflict), which the user is likely to commit and push without noticing, since the UI reports success.

This matches the explicitly valid impact category "silent corruption of what the user commits or pushes," triggered purely by attacker-controlled repository content, with no local access, privileges, or social engineering required beyond a normal merge/rebase workflow.

### Likelihood Explanation
Requires: (1) the user has the Copilot conflict-resolution feature available and invokes it on a merge/rebase/cherry-pick, and (2) one side of the conflicting file contains a line matching the closing-marker regex (`^>{7}(?:\s|$)`) that is not an actual conflict marker. Because this regex only requires seven `>` characters followed by whitespace or end-of-line, and does not require a branch-name suffix like a real Git-generated marker (`>>>>>>> branchname`), such lines can occur incidentally in ordinary text (ASCII art, quoted diffs, changelogs, documentation about Git itself) or be deliberately planted by an attacker who controls a branch/PR that will later be merged. No existing guard (`MAX_CONFLICT_FILE_READ_SIZE`, `MAX_CONFLICT_CONTENT_SIZE`, `MAX_CONFLICT_LINE_LENGTH`, `validateResolutionPaths`'s count check) detects or prevents the boundary mismatch, since all of them operate on `extractConflictHunks`'s notion of hunks, not `reassembleResolvedFile`'s.

### Recommendation
Unify hunk-boundary detection into a single parser shared by both extraction and reassembly (e.g., have `extractConflictHunks` return hunk line-index ranges that `reassembleResolvedFile` consumes directly, rather than each re-deriving boundaries independently from raw text). At minimum, `reassembleResolvedFile`'s lookahead should mirror `extractConflictHunks`'s ordering rule exactly (stop "ours" collection strictly on `baseMarker`/`separatorMarker`, and only treat a `theirsMarker` as valid once a separator has already been consumed for that block). Additionally, after reassembly, assert that no `<<<<<<<`/`=======`/`>>>>>>>` marker lines remain in the output before it is presented as fully resolved, and fail loudly (falling back to manual resolution) rather than silently committing partially-corrupted content.

### Proof of Concept
1. Create a merge conflict in a file where the file contains two real conflicts, and the first conflict's "ours" side contains a line such as `>>>>>>> not-a-real-marker` (e.g., a code comment illustrating Git conflict syntax):
```
<<<<<<< HEAD
some code
>>>>>>> not-a-real-marker
=======
incoming code
>>>>>>> feature-branch
some unrelated line
<<<<<<< HEAD
second conflict ours
=======
second conflict theirs
>>>>>>> feature-branch
```
2. `extractConflictHunks` will correctly identify 2 hunks (the embedded `>>>>>>> not-a-real-marker` line is just consumed as part of "ours" content since it only breaks on base/separator markers) and send both to the model, expecting 2 resolutions.
3. `reassembleResolvedFile`, walking the same raw text, hits the first `<<<<<<<`, then scans forward and finds `>>>>>>> not-a-real-marker` as the first theirs-marker-looking line *before* any separator has been seen — `hasSeparator` is `false` — so it classifies this block as malformed and copies the `<<<<<<< HEAD` line through as plain content, without consuming the block or incrementing `hunkIndex`.
4. The engine continues scanning subsequent lines (including the real `=======`, `incoming code`, and `>>>>>>> feature-branch` lines) as plain content, leaving live conflict markers in the output.
5. When it reaches the second, well-formed conflict block, `hunkIndex` is still `0`, so `hunkResolutions[0]` (the model's answer meant for the first conflict) is spliced in instead of `hunkResolutions[1]`. The committed file now contains unresolved marker text from conflict 1 and the wrong resolved content for conflict 2 — silent corruption of the commit content that the UI reports as a successful automatic resolution. export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
