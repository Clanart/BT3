This confirms the analog: `GetParamSet(blockNum)` in [1](#0-0)  always returns the params effective as of the *previous* epoch — it never reflects other votes cast earlier within the *same* epoch that are still pending ratification. `checkConsistency` in [2](#0-1)  uses exactly this stale `params` when validating `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` votes, so two votes cast by the (single) governing node within the same epoch can each individually pass the check against the old, not-yet-updated bound, yet combine at ratification into a state where `LowerBoundBaseFee > UpperBoundBaseFee` — mirroring the Arcadia bug where a stale/inconsistent risk parameter (`minUsdValue`) is compared instead of validating the final combined state.

### Title
KIP-71 LowerBoundBaseFee/UpperBoundBaseFee vote consistency check uses stale (pre-epoch) ParamSet, allowing a ratified governance state where LowerBound > UpperBound - (File: kaiax/gov/headergov/impl/header.go)

### Summary
`checkConsistency()` validates `kip71.lowerboundbasefee` and `kip71.upperboundbasefee` votes by comparing the proposed value against `h.GetParamSet(blockNum)`, which always returns the parameter set effective as of the **previous** epoch [1](#0-0) . It never accounts for other votes for the *complementary* bound already cast (but not yet ratified) within the *current* epoch. Because both bounds can be changed independently by the sole governing node within the same epoch, and each vote is checked only against the stale value of the other bound, it is possible to ratify a combined state where `LowerBoundBaseFee > UpperBoundBaseFee`, violating the fundamental KIP-71 invariant.

### Finding Description
The vote validation logic is: [2](#0-1)  — each vote is checked only against `GetParamSet(blockNum)`, which resolves via `PrevEpochStart` to the ratified value from the epoch *before* the current one [3](#0-2) . Votes within the same epoch for `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` are collected independently, and only the *last* vote per parameter in the epoch is ratified (per `getExpectedGovernance`) [4](#0-3) . Consider current state `Lower=25e9, Upper=750e9`:
- Governing node casts vote A: `UpperBoundBaseFee = 20e9`. Check: `20e9 < params.LowerBoundBaseFee(25e9)` → fails, blocked. So the attacker instead orders it the other way:
- Vote 1: `LowerBoundBaseFee = 100e9`. Check: `100e9 > params.UpperBoundBaseFee(750e9)`? No → passes.
- Vote 2 (later block, same epoch): `UpperBoundBaseFee = 50e9`. Check: `50e9 < params.LowerBoundBaseFee`? `params` is still the *old* value `25e9` (pending Vote 1 not yet ratified) → `50e9 < 25e9` is false → passes.

At epoch boundary, both votes are ratified together (since `getExpectedGovernance` takes the last vote per parameter from the whole previous epoch), producing `LowerBoundBaseFee = 100e9 > UpperBoundBaseFee = 50e9`, an invalid, unvalidated combined state — directly analogous to the reported Arcadia issue where risk-parameter comparisons against a stale/different threshold silently produce an inconsistent, unchecked account state after the two-step change takes effect.

### Impact Explanation
Once ratified, this invalid `KIP71Config` state feeds `NextMagmaBlockBaseFee` [5](#0-4) , which is used by *every* node to compute the deterministic dynamic base fee via `VerifyMagmaHeader` in block validation [6](#0-5) . With `Lower > Upper`, the clamping logic (`if parentBaseFee >= upperBound: parentBaseFee = upperBound; elif parentBaseFee <= lowerBound: parentBaseFee = lowerBound`) can produce nonsensical or economically incorrect base-fee trajectories network-wide (e.g., base fee permanently stuck below the intended floor, or fee calculations that violate the documented monotonic bound invariants asserted in the KIP-71 tests) [7](#0-6) . Because the computation is deterministic, all honest nodes compute the same (wrong) result — so this is not node-divergence, but it is acceptance, at the protocol/consensus level, of an invalid governance parameter combination that corrupts the fee mechanism for all users/transactions on the chain (fee/pricing abuse impacting every sender).

### Likelihood Explanation
This requires control of the single governing node (in `single` governance mode) or a majority coalition (in `none` mode) to cast two votes within one epoch — the same actor who is already trusted to set these parameters, so it is a lower-privilege-escalation issue rather than an open unprivileged attack, but it is reachable purely through the standard `governance_vote` RPC transaction path with no additional protocol violation, and the consistency check that is supposed to prevent exactly this class of misconfiguration is bypassed due to the staleness bug.

### Recommendation
When validating `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` votes, also incorporate any pending (not-yet-ratified) vote for the complementary parameter already cast earlier in the same epoch (e.g., via `getVotesInEpoch(currentEpochIdx)`), not just the last-ratified `GetParamSet(blockNum)`. Alternatively, re-validate the fully merged, to-be-ratified `GovData` for internal consistency (`Lower <= Upper`) inside `VerifyGov` at the epoch boundary, rejecting ratification if the combined parameter set is invalid.

### Proof of Concept
1. Start chain with `Governance.GovernanceMode = "single"`, `GoverningNode = G`, KIP71 defaults `Lower=25e9, Upper=750e9`, `Istanbul.Epoch = E`.
2. At block `k*E + 1` (start of epoch k), have `G` propose a block with `header.Vote` = vote for `kip71.lowerboundbasefee = 100e9`. `checkConsistency` compares `100e9` to `params.UpperBoundBaseFee` from epoch `k-1` (`750e9`) → passes.
3. At block `k*E + 2`, same epoch, `G` proposes `header.Vote` = vote for `kip71.upperboundbasefee = 50e9`. `checkConsistency` compares `50e9` to `params.LowerBoundBaseFee` from epoch `k-1` (`25e9`, unchanged since Vote 1 is not yet ratified) → passes.
4. At block `(k+1)*E` (epoch boundary), `getExpectedGovernance` ratifies both last-votes-per-parameter from epoch `k`: `LowerBoundBaseFee=100e9`, `UpperBoundBaseFee=50e9`.
5. From block `(k+1)*E + 1` onward, `GetParamSet` returns `Lower=100e9 > Upper=50e9`, and `NextMagmaBlockBaseFee` operates on this inverted-bound config for all subsequent blocks, producing an unvalidated/incorrect deterministic base-fee schedule network-wide.

func (kc *KIP71Config) NextMagmaBlockBaseFee(parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) *big.Int {
	// governance parameters
	lowerBoundBaseFee := new(big.Int).SetUint64(kc.LowerBoundBaseFee)
	upperBoundBaseFee := new(big.Int).SetUint64(kc.UpperBoundBaseFee)
	makeEvenByCeil(lowerBoundBaseFee)
	makeEvenByFloor(upperBoundBaseFee)

	// If the parent is the magma disabled block or genesis, then return the lowerBoundBaseFee (default 25ston)
	if parentHeaderNumber.Cmp(new(big.Int).SetUint64(0)) == 0 || parentHeaderBaseFee == nil {
		return makeEvenByFloor(lowerBoundBaseFee)
	}

	var baseFeeDenominator *big.Int
	if kc.BaseFeeDenominator == 0 {
		// To avoid panic, set the fluctuation range small
		baseFeeDenominator = new(big.Int).SetUint64(64)
	} else {
		baseFeeDenominator = new(big.Int).SetUint64(kc.BaseFeeDenominator)
	}
	gasTarget := kc.GasTarget
	upperGasLimit := kc.MaxBlockGasUsedForBaseFee

	// check the case of upper/lowerBoundBaseFee is updated by governance mechanism
	parentBaseFee := parentHeaderBaseFee
	if parentBaseFee.Cmp(upperBoundBaseFee) >= 0 {
		parentBaseFee = upperBoundBaseFee
	} else if parentBaseFee.Cmp(lowerBoundBaseFee) <= 0 {
		parentBaseFee = lowerBoundBaseFee
	}

	// upper gas limit cut off the impulse of used gas to upper bound
	parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)
	if parentGasUsed == gasTarget {
		return makeEvenByFloor(parentBaseFee)
	} else if parentGasUsed > gasTarget {
		// shortcut. If parentBaseFee is already reached upperbound, do not calculate.
		if parentBaseFee.Cmp(upperBoundBaseFee) == 0 {
			return makeEvenByFloor(upperBoundBaseFee)
		}
		// If the parent block used more gas than its target,
		// the baseFee of the next block should increase.
		// baseFeeDelta = max(1, parentBaseFee * (parentGasUsed - gasTarget) / gasTarget / baseFeeDenominator)
		gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
		x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
		y := x.Div(x, new(big.Int).SetUint64(gasTarget))
		baseFeeDelta := math.BigMax(x.Div(y, baseFeeDenominator), common.Big1)

		nextBaseFee := x.Add(parentBaseFee, baseFeeDelta)
		if nextBaseFee.Cmp(upperBoundBaseFee) > 0 {
			return makeEvenByFloor(upperBoundBaseFee)
		}
		return makeEvenByFloor(nextBaseFee)
	} else {
		// shortcut. If parentBaseFee is already reached lower bound, do not calculate.
		if parentBaseFee.Cmp(lowerBoundBaseFee) == 0 {
			return makeEvenByFloor(lowerBoundBaseFee)
		}
		// Otherwise if the parent block used less gas than its target,
		// the baseFee of the next block should decrease.
		// baseFeeDelta = parentBaseFee * (gasTarget - parentGasUsed) / gasTarget / baseFeeDenominator
		gasUsedDelta := new(big.Int).SetUint64(gasTarget - parentGasUsed)
		x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
		y := x.Div(x, new(big.Int).SetUint64(gasTarget))
		baseFeeDelta := x.Div(y, baseFeeDenominator)

		nextBaseFee := x.Sub(parentBaseFee, baseFeeDelta)
		if nextBaseFee.Cmp(lowerBoundBaseFee) < 0 {
			return makeEvenByFloor(lowerBoundBaseFee)
		}
		return makeEvenByFloor(nextBaseFee)
	}
}
