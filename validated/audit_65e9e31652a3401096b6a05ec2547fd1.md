## Finding: Bandwidth purchase funds get pulled into `BandwidthManager` before the destination `pallet-bandwidth` validates the message — a rejection leaves the payment permanently stuck with no per-payer refund path

### Title
Funds locked in `BandwidthManager` when `pallet-bandwidth::on_accept` rejects a dispatched purchase - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.purchase()` pulls the fee token from the caller into the contract's own balance and *then* dispatches a cross-chain `BandwidthPurchaseMsg` to `pallet-bandwidth`, with no revert path if the destination rejects the message. `pallet-bandwidth::on_accept` independently validates the message against pallet-side state (`BandwidthManager` registry and `Tiers` config) that the EVM contract cannot see, and returns a plain `Err(...)` — not a state that ever refunds the payer — on several conditions that are reachable without any malicious relayer/admin. This reproduces the `Lock.claimGovFees` / `BondNFT.distribute` bug class: funds are moved into custody based on an operation whose downstream leg can silently fail, leaving the transferred asset stuck with no dedicated recovery mechanism for the original payer.

### Finding Description
`purchase()` in `evm/src/apps/BandwidthManager.sol` does: [1](#0-0) 

1. Validates only *local* state: `tierPrice[tier] != 0` (manager-side price).
2. `safeTransferFrom(msg.sender, address(this), amount)` — funds now sit in the manager contract.
3. Dispatches a `BandwidthPurchaseMsg` to `pallet-bandwidth` with `fee: 0`.

The destination-side handler, `pallet-bandwidth::on_accept`, independently re-checks conditions that the manager contract has no visibility into: [2](#0-1) 

- `BandwidthManager::<T>::get(&request.source)` must exist — i.e. governance must have called `set_manager` for that specific source chain (Step 3 of onboarding).
- `request.from` must match the registered manager address.
- `Tiers::<T>::get(tier)` must be configured on the pallet side (`TierConfig`), which is entirely independent from `tierPrice[tier]` on the EVM side — the docs explicitly call this out: *"A tier is unconfigured until both sides have set it. The pallet rejects purchases against a tier without a TierConfig; the manager rejects purchases against a tier with a zero price."* [3](#0-2) 

Any of these mismatches makes `on_accept` return `Err(...)` instead of crediting a subscription. This is a normal ISMP module rejection, not a panic — from the manager contract's point of view, the fee token it already pulled via `safeTransferFrom` simply sits in its balance forever. There is no `on_accept` failure callback into `BandwidthManager` that reverses the `transferFrom`, and no code path automatically returns the specific payer's tokens.

The only way funds ever leave the manager is a governance-initiated `Withdraw` message: [4](#0-3) 
which drains an arbitrary `amount` of `token` to an arbitrary `beneficiary` chosen by governance — it is not a per-payer refund mechanism, requires an off-chain/manual governance action to even notice the stuck funds (via the emitted `BandwidthPurchased` event correlating `payer` to `commitment`), and commingles the stuck payer's tokens with every other successful purchaser's collected fees sitting in the same contract balance.

This exactly mirrors the external report's broken invariant: **value transferred into an intermediary contract based on a downstream operation that can silently no-op**, with the only "fix" being an out-of-band admin sweep that isn't scoped to the specific victim.

### Impact Explanation
Any unprivileged caller of `purchase()` during a legitimate, non-malicious desync window — e.g. before governance finishes the five-step onboarding checklist for a new chain (`set_manager` not yet called), or after a `set_tier(tier, None)` revocation on the pallet side while the EVM-side `tierPrice[tier]` is still non-zero (or vice versa, before `dispatch_set_tiers` propagates a new tier) — pays real fee tokens and receives nothing in return, with the funds parked in the manager contract indefinitely. This is a direct loss-of-funds condition for ordinary users reachable through the public `purchase()` entrypoint, matching the bounty's "stealing or loss of funds" and "false proof/state acceptance"-adjacent categories (the manager accepts payment for a destination-side effect that the destination is not obligated, or able, to honor).

### Likelihood Explanation
No malicious actor, prover, relayer, or governance action is required — only ordinary operational skew between two independently-governed pieces of state (EVM-side `tierPrice` and Substrate-side `TierConfig`/`BandwidthManager` registry) that the protocol's own documentation acknowledges is a real, expected transient state during rollout ("Until every step lands, purchases from that chain are rejected"). Any user who calls `purchase()` during that window, or against a stale/desynced tier, loses funds. Given governance updates to tiers and manager registration happen asynchronously across chains, this window is not a theoretical edge case.

### Recommendation
- Make `on_accept` rejections observable and reversible: have the pallet's rejection path (or a timeout, since purchases currently dispatch with `timeout: 0`, making failures unresolvable) trigger a refund message back to the specific `payer` recorded in the purchase.
- Alternatively, do not pull funds via `transferFrom` until dispatch has been confirmed processed; or hold pulled funds in an escrow keyed by `commitment` + `payer` so a failed/timed-out purchase can be refunded to the exact address that paid, rather than relying on a governance-wide `Withdraw` sweep.
- At minimum, add a permissionless "reclaim" function on `BandwidthManager` that lets a payer reclaim funds tied to their own `commitment` if the corresponding purchase is provably not reflected on Hyperbridge after some deadline (mirrors the C4 report's suggestion to let assets be rescued rather than permanently trapped).

### Proof of Concept
1. Governance deploys `BandwidthManager` for a new source chain and calls `mgr.setHost(hostAddr)` (Step 2) but has not yet called `BandwidthPallet::set_manager(source, managerAddr)` (Step 3), or has set tier prices on the manager (`SetTiers` dispatched, or manually via a pre-Step-3 configuration) before the pallet's `Tiers` map has the corresponding `TierConfig`.
2. A regular user calls `BandwidthManager.purchase(app, tier, months, chain)`. The manager only checks `tierPrice[tier] != 0`, which passes; it pulls the fee token via `safeTransferFrom` and dispatches the purchase message. [1](#0-0) 
3. On Hyperbridge, `pallet_bandwidth::on_accept` looks up `BandwidthManager::<T>::get(&request.source)` (not yet set) or `Tiers::<T>::get(tier)` (not yet configured) and returns `Err(...)`. [5](#0-4) 
4. No subscription is credited (`push_subscription`/`BandwidthCredited` never execute), and no refund transaction is generated by the pallet or the manager.
5. The user's fee token remains in the `BandwidthManager` contract balance permanently; recovery requires governance to notice the mismatch and manually dispatch a `Withdraw` message to sweep the manager's balance to a beneficiary of governance's choosing — not an automated, user-triggered refund.
