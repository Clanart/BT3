### Title
Access-scope revocation check enforced in the legacy session path is skipped by `ShopifyApp::TokenExchange#activate_shopify_session`, allowing reuse of sessions with stale/insufficient scopes - ([File: lib/shopify_app/controller_concerns/token_exchange.rb])

### Summary
The oracle-deactivation bug class is "a state-invalidation check is enforced on one code path but omitted on an equivalent path, allowing the invalidated state to keep being used." In `shopify_app`, `ShopifyApp::LoginProtection#activate_shopify_session` forces re-authentication when `reauth_on_access_scope_changes` is enabled and the stored session's granted scopes no longer cover the app's configured scopes (`covers_scopes?`) [1](#0-0) . The functionally equivalent `ShopifyApp::TokenExchange#activate_shopify_session`, used when `use_new_embedded_auth_strategy?` is enabled, never performs this check [2](#0-1) .

### Finding Description
`EnsureHasSession` conditionally includes one of two session-activation strategies depending on `ShopifyApp.configuration.use_new_embedded_auth_strategy?` [3](#0-2) .

- Legacy strategy (`LoginProtection#activate_shopify_session`): after confirming a session exists and is not expired, it checks `ShopifyApp.configuration.reauth_on_access_scope_changes && !ShopifyApp.configuration.user_access_scopes_strategy.covers_scopes?(current_shopify_session)`, and if the session's scopes no longer cover the configured/required scopes it clears the session and forces re-login via OAuth [4](#0-3) .
- New strategy (`TokenExchange#activate_shopify_session`): it only re-exchanges the token when the session is blank or expired (`should_exchange_expired_token?`), then validates shop-domain match, then directly activates the session and yields — with no call to `covers_scopes?` or any scope-coverage check anywhere in the module [5](#0-4) .

`covers_scopes?` is defined in `ShopifyApp::AccessScopes::UserStrategy` (and the analogous shop strategy) to compare the session's granted `scope` against `ShopifyAPI::Context.scope` [6](#0-5) . This mechanism exists specifically so that when a merchant's/user's granted scopes fall out of sync with what the app currently requires (e.g., after the app or the shop changes its permission set), the stale session is invalidated and reauthorization is forced, per the gem's own documentation on handling access-scope changes [7](#0-6) . Under the token-exchange strategy this invalidation gate is simply never evaluated, so an app configured with `reauth_on_access_scope_changes = true` gets that protection only for non-embedded/legacy-cookie sessions, not for the modern embedded token-exchange flow that Shopify now recommends.

### Impact Explanation
This is directly analogous to the oracle report: a deactivation/staleness check ("oracle active" ↔ "session scopes cover configuration") is enforced on one operational path (vanilla option minting ↔ `LoginProtection`) but omitted on the semantically equivalent path (spreads minting ↔ `TokenExchange`), letting the stale/should-be-invalidated state continue to be used to perform authenticated actions. Concretely, for apps using the new embedded auth strategy, a session that should trigger reauthorization (because its granted scope set diverges from the app's currently configured scope set) will instead continue to be activated and used for API calls via `with_token_refetch` without ever being cleared or forced through OAuth, contrary to the app's own configured security policy. This is a real behavioral divergence between the two officially supported activation paths, not a hypothetical.

I was not able to fully verify from the indexed files whether Shopify's Admin API itself would independently reject requests made with out-of-sync scopes (i.e., whether server-side enforcement fully compensates for the missing client-side gate), so the ultimate blast radius depends on Shopify API-side scope enforcement behavior that is outside this repo's index.

### Likelihood Explanation
Likelihood is moderate: it requires (1) `use_new_embedded_auth_strategy?` to be enabled (the new/recommended token-exchange flow) and (2) `reauth_on_access_scope_changes` to be enabled, both realistic configurations that the docs actively encourage app developers to adopt. No attacker action is needed beyond the scope-change event occurring naturally (app scope requirements change, or the merchant edits granted scopes) — the gap is purely in `TokenExchange`'s omission of the check that `LoginProtection` performs.

### Recommendation
Add the same scope-coverage gate used in `LoginProtection#activate_shopify_session` to `TokenExchange#activate_shopify_session`: before activating/yielding with `current_shopify_session`, check `ShopifyApp.configuration.reauth_on_access_scope_changes && !ShopifyApp.configuration.user_access_scopes_strategy.covers_scopes?(current_shopify_session)` (and the shop-level equivalent), and if it fails, clear the session and re-trigger token exchange / redirect to reauth instead of activating the session, mirroring lines 37-41 of `login_protection.rb`.

### Proof of Concept
1. Configure the app with `config.new_embedded_auth_strategy = true`, `config.embedded_app = true`, and `config.reauth_on_access_scope_changes = true`.
2. Obtain a valid session via token exchange whose stored `scope` covers only a subset of scopes (e.g., app previously requested `read_products` and scopes were later expanded to `read_products,write_orders` in `config.scope`).
3. Make an authenticated request through a controller including `EnsureHasSession` (which resolves to `TokenExchange#activate_shopify_session`) [3](#0-2) .
4. Observe that `activate_shopify_session` proceeds straight to `ShopifyAPI::Context.activate_session(current_shopify_session)` and yields, with no `covers_scopes?` check performed anywhere in the method [2](#0-1) , whereas the same session under `LoginProtection#activate_shopify_session` would be cleared and redirected to login [1](#0-0) .

    def activate_shopify_session(&block)
      retrieve_session_from_token_exchange if current_shopify_session.blank? || should_exchange_expired_token?

      return if reject_mismatched_requested_shopify_domain

      ShopifyApp::Logger.debug("Activating Shopify session")
      ShopifyAPI::Context.activate_session(current_shopify_session)
      with_token_refetch(current_shopify_session, shopify_id_token, &block)
    rescue *INVALID_SHOPIFY_ID_TOKEN_ERRORS => e
      respond_to_invalid_shopify_id_token(e)
    ensure
      ShopifyApp::Logger.debug("Deactivating session")
      ShopifyAPI::Context.deactivate_session
    end

    def should_exchange_expired_token?
      ShopifyApp.configuration.check_session_expiry_date && current_shopify_session.expired?
    end

    def current_shopify_session

      @current_shopify_session ||= ShopifyApp::SessionRepository.load_session(current_shopify_session_id)
    end

## Requesting new scopes from merchants

The Shopify App gem will automatically request new scopes from merchants for both shop/offline and user/online tokens. To enable your app to reauth via OAuth on scope changes, you can set the following configuration flag in your `config/initializers/shopify_app.rb`:
```ruby
config.reauth_on_access_scope_changes = true
```

## ShopAccessScopesVerification
The `ShopifyApp::ShopAccessScopesVerification` concern helps merchants grant new access scopes requested by the app. The concern compares the current access scopes granted by the shop and compares them with the scopes requested by the app. If there is a mismatch in configuration, the merchant is redirected to login via OAuth and grant the net new scopes.
```
