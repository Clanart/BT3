## Title
Renderer crash / unhandled exception in `parseRawLogWithNumstat` when a malicious repository's commit diff produces mismatched raw/numstat entries - ([File: app/src/lib/git/log.ts])

### Summary
The lightningd bug is a crash caused by code that dereferences data assuming a fixed structural invariant (a block being present) that a remote/attacker-influenced input can violate. The analogous pattern in GitHub Desktop is `parseRawLogWithNumstat` in [1](#0-0) , which parses the output of `git diff`/`git log` with `--raw --numstat -z` and assumes the number of `:`-prefixed raw entries always matches the number of numstat entries, indexing `files[numStatCount]` without bounds checking.

### Finding Description
`parseRawLogWithNumstat` iterates the `-z`-split lines from git's raw/numstat output. For each `:`-prefixed raw entry it pushes a `CommittedFileChange` to `files`. For each subsequent numstat line it accesses `files[numStatCount]` to decide whether to skip extra rename/copy path lines: [2](#0-1) 
```
} else {
  const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
  const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
  ...
  if (isCopyOrRename(files[numStatCount].status)) {
    i += 2
  }
  numStatCount++
}
```
If `numStatCount` ever reaches or exceeds `files.length` — which happens whenever the raw and numstat sections become desynchronized (e.g., due to attacker-controlled paths/content in a cloned or fetched repository that break the expected line pairing, unusual rename/copy detection edge cases, or numstat lines that don't correspond 1:1 to raw entries) — `files[numStatCount]` is `undefined`, and `.status` throws a `TypeError: Cannot read properties of undefined`. This mirrors the lightningd crash: code assumes a companion data element ("block"/"file entry") is always present and dereferences it unconditionally, with no bounds/null check analogous to lightningd's missing block-availability guard before `fixup_scan_block`.

This function is invoked from two attacker-reachable code paths that operate on data controlled by a remote repository:
- `getChangedFiles` in [3](#0-2)  — called when a user selects a commit to view its diff.
- `getCommitRangeChangedFiles` in [4](#0-3)  — used for multi-commit diffs (e.g., squash/reorder previews).

Both are reached from `app-store.ts` (e.g. `_loadChangedFilesForCurrentSelection`), which is exercised simply by opening a cloned/fetched repository and browsing its commit history — a normal, unprompted user action, not requiring special interaction beyond viewing history that an attacker fully controls the content of (commit messages, file paths, renames).

### Impact Explanation
An attacker who controls a repository (via a crafted commit that a victim clones or fetches) can craft file paths/renames that desynchronize the raw/numstat line count, causing an unhandled `TypeError` inside async git-parsing code. Depending on how the promise rejection propagates, this can crash the Desktop renderer process or leave the app in an unrecoverable state while browsing history/diffs of an untrusted repository — a denial-of-service on the client triggered purely by attacker-controlled repository content. There is no code-execution path uncovered here (the crash is a thrown TypeError, not memory corruption), so the ceiling of this finding is a reliable renderer crash/DoS from opening or viewing a malicious repo's history, not remote code execution.

### Likelihood Explanation
Likelihood is uncertain: I was not able to find or exercise a concrete git raw+numstat output sequence (with real git semantics for `-M`/`-C` rename/copy detection) that provably desynchronizes `files.length` vs the numstat entry count within the given tool access. Git's own raw+numstat output format is normally self-consistent for legitimate diffs, so triggering the mismatch requires either an edge case in git's rename detection interacting with `-z` parsing, or corrupted/adversarial diff output that git itself would not normally produce. Without being able to run `git diff --raw --numstat -z` against a crafted commit to confirm a real desync, this remains a plausible-but-unconfirmed code-path weakness rather than a demonstrated exploit.

### Recommendation
Add bounds checking before indexing `files[numStatCount]` in `parseRawLogWithNumstat` ( [5](#0-4) ), and treat a raw/numstat count mismatch as a parse error (throw a descriptive error or skip gracefully) rather than allowing an unguarded property access on `undefined`. Wrap callers (`getChangedFiles`, `getCommitRangeChangedFiles`) so that parse failures on attacker-supplied repository data degrade gracefully (e.g., show "unable to parse diff") instead of raising an unhandled exception in the UI/store layer.

### Proof of Concept
Not independently verified — I could not execute git or construct a git raw+numstat output stream to confirm a real-world commit/rename/copy content sequence that causes `numStatCount` to exceed `files.length`. A concrete PoC would require running `git diff -C -M -z --raw --numstat` against a specially crafted repository (e.g., with chained/ambiguous rename+copy sequences or deliberately malformed diff output ingested via a compromised remote/proxy) and confirming the parser throws. This should be validated with actual git tooling before treating it as a confirmed, exploitable Desktop issue.

export async function getChangedFiles(
  repository: Repository,
  sha: string
): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)
  // this is equivalent to the user configuring 'diff.renames' to 'copies'
  // NOTE: order here matters - doing -M before -C means copies aren't detected
  const args = [
    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}

export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }

  return { files, linesAdded, linesDeleted }
}

export async function getCommitRangeChangedFiles(
  repository: Repository,
  shas: ReadonlyArray<string>,
  useNullTreeSHA: boolean = false
): Promise<IChangesetData> {
  if (shas.length === 0) {
    throw new Error('No commits to diff...')
  }

  const oldestCommitRef = useNullTreeSHA ? NullTreeSHA : `${shas[0]}^`
  const latestCommitRef = shas.at(-1) ?? '' // can't be undefined since shas.length > 0
  const baseArgs = [
    'diff',
    oldestCommitRef,
    latestCommitRef,
    '-C',
    '-M',
    '-z',
    '--raw',
    '--numstat',
    '--',
  ]

  const { stdout, gitError } = await git(
    baseArgs,
    repository.path,
    'getCommitRangeChangedFiles',
    {
      expectedErrors: new Set([GitError.BadRevision]),
    }
  )

  // This should only happen if the oldest commit does not have a parent (ex:
  // initial commit of a branch) and therefore `SHA^` is not a valid reference.
  // In which case, we will retry with the null tree sha.
  if (gitError === GitError.BadRevision && useNullTreeSHA === false) {
    const useNullTreeSHA = true
    return getCommitRangeChangedFiles(repository, shas, useNullTreeSHA)
  }

  return parseRawLogWithNumstat(stdout, latestCommitRef, oldestCommitRef)
