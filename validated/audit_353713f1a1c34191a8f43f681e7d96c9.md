### Title
`SignableTransaction::new` underestimates transaction vsize/fee because the OP_RETURN `data` output is excluded from `calculate_weight_vbytes` - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` accepts an optional `data` argument that is appended as an OP_RETURN output to `tx_outs` (send.rs:194-202), but both fee/size estimates call `calculate_weight_vbytes(tx_ins.len(), payments, ...)` with only the `payments` slice — the data output is never part of the estimated transaction (send.rs:204, 226). `needed_fee = fee_per_vbyte * vbytes` is therefore computed against a vsize smaller than the transaction actually signed and broadcast, mirroring the BCH bug class where the fee estimate is built on a different transaction than the one that materializes.

### Finding Description
`calculate_weight_vbytes` builds a mock transaction from `inputs` and `payments` (and optionally `change`) to derive `weight`/`vbytes` (send.rs:62-127). In `new`, the OP_RETURN output carrying up to 80 bytes of caller-supplied data is pushed to `tx_outs` (send.rs:194-202) but is absent from both `calculate_weight_vbytes` calls (send.rs:204 and 226). An 80-byte OP_RETURN output adds roughly 90–91 vbytes (8-byte amount, ~82-byte script_pubkey, output-count varint may also grow). The resulting `needed_fee` and the fee check at send.rs:211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) are evaluated against this underestimated size. The signed transaction — created at send.rs:245-255 with `tx_outs` including the data output and signed via `taproot_key_spend_signature_hash` (send.rs:386) — is strictly larger, so `fee()` (send.rs:138-141) divided by real vsize yields an effective fee rate below the requested `fee_per_vbyte`. The `weight` bound used for the `TooLargeTransaction` check (send.rs:241) is likewise underestimated, so a transaction may pass the check and still exceed `MAX_STANDARD_TX_WEIGHT` on the wire.

### Impact Explanation
Any caller-supplied `data` causes the produced transaction to pay a lower effective fee rate than requested — directly the "expected fee vs actual fee" divergence from the reference report. If the requested rate was marginally above minimum relay fee, the real transaction drops below 1 sat/vbyte and will be rejected/never relayed, leaving the intended payments unbroadcast and the consumed inputs' funds effectively unspendable via this path until a replacement is constructed. The underpayment also silently burns a higher sat/kwu weight than assumed, and the weight-limit check can be bypassed by the data output, producing a non-standard transaction that nodes refuse.

### Likelihood Explanation
`data` is a public, attacker-reachable parameter of `SignableTransaction::new` — it is arbitrary bytes "fed to" a sign API (FROST `TransactionMachine` signs whatever transaction was constructed). In the in-repo consumer (`processor/src/networks/bitcoin.rs:446-452`) `None` is passed, so the bug requires an integrator or protocol path that sets `data`; where it is set, the underpricing is deterministic, not intermittent. Impact is limited to a stuck/non-relayable transaction (recoverable by rebuilding with a correct fee), so severity is at most Medium.

### Recommendation
Include the OP_RETURN output in the size estimate: build the estimated outputs from `tx_outs` (payments + data output) rather than `payments` alone at send.rs:204 and 226, e.g. pass a combined `Vec<(ScriptBuf, u64)>` containing `ScriptBuf::new_op_return(...)` with value 0, or add the data output inside `calculate_weight_vbytes`. Also re-check `TooLowFee` and `MAX_STANDARD_TX_WEIGHT` against the size including all outputs that will be in the final transaction.

### Proof of Concept
From `networks/bitcoin/src/wallet/send.rs:204` and `226`:
```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
// ...
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```
Both calls omit the output pushed at lines 195-201:
```rust
tx_outs.push(TxOut {
  value: Amount::ZERO,
  script_pubkey: ScriptBuf::new_op_return(...),
})
```
Concrete divergence: call `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)`; the returned `needed_fee()` equals `fee_per_vbyte * vsize(tx_without_op_return)`, while `fee() / vsize(tx)` of the completed transaction is lower, and `vsize(tx)` exceeds the `vbytes` used for the `TooLowFee` check by ~91 vbytes — sufficient to push a marginally-priced transaction below the minimum relay fee.
