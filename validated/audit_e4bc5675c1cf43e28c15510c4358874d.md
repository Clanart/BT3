### Title
Automatic remote-URL rewrite trusts unauthenticated GitHub API `clone_url` field, allowing silent redirection of `origin` - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` automatically rewrites a repository's local git `origin` remote URL whenever the cached `GitHubRepository.cloneURL` differs from a fresh `clone_url` value coming from a GitHub/GitHub-Enterprise API response, as long as the URL "protocol" (scheme only) matches and the current remote hasn't been manually edited. This mirrors the audited `swapBorrowRateMode` pattern: a state-changing operation is executed without validating the full set of preconditions that should gate it — here, the new URL's hostname/owner/name is never verified to still resolve to the same, trusted repository host before the local git configuration is overwritten.

### Finding Description
The function only performs two checks before calling `gitStore.setRemoteURL`: [1](#0-0) 

1. `protocolsMatch` — compares only the URL scheme (`https:` vs `ssh:`) of the old and new URLs, via `URL.parse(...).protocol`.
2. `remoteUrlUnchanged` — confirms the *current* remote still matches the *previously cached* `gitHubRepository.cloneURL`, using `urlMatchesRemote`, which itself only compares hostname/owner/name using the app's own `parseRemote` regexes: [2](#0-1) .

Crucially, there is **no check that the incoming `apiRepo.clone_url` still points to the same host/owner** as the previous value, or to an expected GitHub host at all. As long as `urlsMatch` between old remote and new URL is `false` (i.e., "the API says the repo moved somewhere"), the code accepts the new URL verbatim and writes it into `.git/config` via `gitStore.setRemoteURL`. The test suite confirms this trust boundary explicitly — a `clone_url` change is accepted and written as-is: [3](#0-2) .

This is the same class of bug as the Aave `swapBorrowRateMode` finding: a downstream state mutation (rewriting the borrow-rate mode / rewriting the git remote) is permitted based on a partial/insufficient precondition check (only "does the mode differ" / only "does the scheme match"), rather than a full validation of whether the new state is actually one the system is supposed to allow (fixed-rate eligibility / trusted origin host).

### Impact Explanation
`clone_url` is a field returned by the configured GitHub.com or GitHub Enterprise API for a repository object. If that API response can be influenced — e.g., a compromised/malicious GitHub Enterprise Server the user has added as an account, a compromised or renamed upstream repository object, or a man-in-the-middle on an HTTP(S) GHE endpoint — Desktop will silently rewrite the user's `origin` remote to whatever URL is supplied, without any confirmation dialog, as long as the scheme matches. Subsequent `git push`/`git fetch`/credential-helper operations performed by Desktop then target the attacker-controlled remote, which can result in:
- Silent corruption/redirection of what the user pushes (their code goes to an attacker's server instead of the legitimate one).
- Leakage of push credentials/tokens to the attacker's server (Desktop's credential helper will authenticate against whatever host is now configured).

This matches the "silent corruption of what the user commits or pushes" and "credential/token exfiltration" impact classes.

### Likelihood Explanation
Exploitation requires the attacker to control a GitHub API object returned to the victim's Desktop client for a repository the user has already added (most plausible via a malicious/compromised GitHub Enterprise instance, which Desktop explicitly supports connecting to, or an API response substitution). This is not a purely local/physical-access or malware-on-host precondition — it fits within "the attacker controls ... a GitHub API object." However, it does require the attacker to control or intercept that specific API response channel, which is a narrower condition than a passively hostile git remote alone, so likelihood is moderate rather than trivial.

### Recommendation
Before calling `gitStore.setRemoteURL` in `updateRemoteUrl`, validate that the new URL's hostname is consistent with the account/endpoint that owns the cached `GitHubRepository` (e.g., compare against `account.endpoint`/`getHTMLURL(account.endpoint)` as done in `matchGitHubRepository`), not just that the scheme matches. Consider also surfacing a confirmation prompt to the user before silently changing `origin`, similar to how other destructive/consequential remote changes are handled elsewhere in the app (e.g., `_ignoreExistingUpstreamRemote` flows in `app-store.ts`).

### Proof of Concept
Using the existing test harness pattern in `app/test/unit/stores/updates/update-remote-url-test.ts`:
1. Set up a repository whose `GitHubRepository.cloneURL` and local `origin` both point to `https://github.com/my-user/my-repo`.
2. Simulate an API response (e.g., from a compromised GHE instance) where `clone_url` is changed to `https://evil-host.example/my-user/my-repo`.
3. Call `updateRemoteUrl(gitStore, gitHubRepository, updatedApiRepository)` exactly as `app-store.ts` does.
4. Because `protocolsMatch` (both `https:`) and `remoteUrlUnchanged` (origin still matches old cached clone URL) both hold, and `urlsMatch` is false (different host), `setRemoteURL` is invoked, silently rewriting `origin` to `https://evil-host.example/my-user/my-repo` with no hostname allow-listing and no user confirmation — mirroring the assertions already exercised in the "updates the repository's remote url when the github url changes" test: [3](#0-2) .

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
