Confirmed root cause: `query_string_valid?` at `lib/shopify_app/controller_concerns/app_proxy_verification.rb:17-27` validates only that the HMAC signature matches the current query params — it never checks the `timestamp` param's freshness against current time. ### Title
Missing timestamp freshness check in App Proxy signature verification permits indefinite replay of captured signed requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` verifies the HMAC-SHA256 signature over an App Proxy request's query parameters but performs no check on the `timestamp` parameter's age. Because the signature is a deterministic function of the (unordered, but sorted) query params and the shared app secret, a request that was valid once remains valid forever — there is no analog to the `block number` freshness check that Sherlock issue #142 required for the L1→L2 rebase message. This is the same bug class: a signed/permissioned message lacks any monotonicity/expiry enforcement, so an old-but-validly-signed payload can be replayed to force stale state.

### Finding Description
`verify_proxy_request` (`lib/shopify_app/controller_concerns/app_proxy_verification.rb:11-13`) calls `query_string_valid?`, which: [1](#0-0) 

This only recomputes the HMAC over the query hash (minus `signature`) and compares it to the supplied `signature` — the `timestamp` field is treated like any other opaque signed parameter, never compared against `Time.now` to reject stale requests. Any App Proxy-protected controller generated by `rails g shopify_app:app_proxy_controller` or any custom controller including this concern (`app/controllers/app_proxy/reviews_controller.rb` pattern documented in `docs/shopify_app/engine.md:52-71`) inherits this gap. [2](#0-1) 

Because App Proxy requests are proxied by Shopify from a storefront page (an unauthenticated, publicly reachable context), the full signed query string (including `signature` and `timestamp`) is exposed to anyone who can observe that network request — e.g., via browser devtools/network tab, browser history, a leaked URL, server access logs, or any client-side JS on the storefront that triggers the app-proxy call. An unrelated/anonymous actor who obtains one such observed request can resend the exact same query string to the app's App Proxy endpoint at any later time, and it will still validate as authentic, since nothing ties the signature's validity to a bounded time window.

### Impact Explanation
Any state-changing action exposed behind an App Proxy route (e.g., submitting a form, redeeming a code, writing a review, recording a loyalty/points action, or any POST-style side effect implemented in the app-proxy controller) can be replayed indefinitely by an attacker who captured a single legitimate signed request. This is a direct analog of the ECO rebase bug: the verification mechanism authenticates the payload's origin but not its freshness/order, allowing the "old" (stale) authenticated action to be re-applied and desynchronize application state — this maps to Sherlock's "accepted forged signed request" acceptance criterion.

### Likelihood Explanation
Exploitability requires the attacker to have observed one genuine App Proxy request/response exchange for the target shop (feasible without any special privilege — App Proxy traffic originates from public storefront pages and passes through the visitor's own browser, is visible in browser dev tools/history, and may be cached/logged by CDNs, proxies, or analytics tools). No secret key or account credential is needed; the attacker never needs to compute a valid signature themselves.

### Recommendation
Include and enforce a timestamp expiry check in `query_string_valid?`: parse `query_hash["timestamp"]`, reject the request if it's blank or if `Time.now.to_i - timestamp.to_i` exceeds a small tolerance window (matching Shopify's own admin/App Bridge guidance of a short validity window, e.g. a few minutes), in addition to the existing HMAC comparison. This mirrors the ECO fix of anchoring cross-domain messages to a monotonic block number to prevent replay of stale-but-validly-signed messages.

### Proof of Concept
1. Visit a storefront page for a shop with an app-proxy-enabled app (e.g., `https://shop.myshopify.com/apps/my-app?...&timestamp=1700000000&signature=<valid_sig>`), and capture the full request URL/query string via browser devtools network tab (no special access required — this traffic is visible to the visiting browser).
2. Days/weeks later, replay the exact same query string (unmodified) directly to the app's App Proxy endpoint.

## Verify HTTP requests sent via an app proxy

See [`ShopifyApp::AppProxyVerification`](/lib/shopify_app/controller_concerns/app_proxy_verification.rb).

The engine provides a mixin for verifying incoming HTTP requests sent via an App Proxy. Any controller that `include`s `ShopifyApp::AppProxyVerification` will verify that each request has a valid `signature` query parameter that is calculated using the other query parameters and the app's shared secret.

### Recommended usage of `ShopifyApp::AppProxyVerification`

The App Proxy Controller Generator automatically adds the mixin to the generated app_proxy_controller.rb
Additional controllers for resources within the App_Proxy namespace, will need to include the mixin like so:

```ruby
# app/controllers/app_proxy/reviews_controller.rb
class ReviewsController < ApplicationController
  include ShopifyApp::AppProxyVerification
  # ...
end
```
