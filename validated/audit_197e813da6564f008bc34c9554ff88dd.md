## Confirmed: `_calExpireForfeit` in `mWOMSVBaseRewarder` is dead code

Comparing `mWOMSVBaseRewarder._calExpireForfeit` against its sibling contract `vlMGPBaseRewarder._calExpireForfeit` confirms the bug is real and not a misread.

In `vlMGPBaseRewarder.sol`, the forfeit percentage is derived from the locker contract itself: [1](#0-0) 

In `mWOMSVBaseRewarder.sol`, the equivalent call to the locker (`mWOMSV.getRewardablePercentWAD(_account)` or similar) is missing — `rewardableAmount` is simply set equal to `_amount`, guaranteeing `forfeitAmount = _amount - rewardableAmount == 0` on every call, regardless of the account's lock/cooldown state: [2](#0-1) 

This feeds directly into `_sendReward`, which always forwards the account's full `userRewards` and never routes anything into `_queueNewRewardsWithoutTransfer`: [3](#0-2) 

### Title
Broken `_calExpireForfeit` permanently disables forfeiture redistribution to loyal lockers - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never queries the locker's rewardable-percent (unlike the parallel `vlMGPBaseRewarder` implementation which calls `vlMGP.getRewardablePercentWAD`), so `forfeitAmount` is unconditionally zero. As a result, early/partial unlockers always receive 100% of their accrued rewards through `getReward`/`_sendReward`, and `_queueNewRewardsWithoutTransfer` — the function meant to redistribute forfeited rewards to remaining fully-locked stakers — is never invoked with a non-zero amount.

### Finding Description
The intended design (mirrored by `vlMGPBaseRewarder`) is: a user who claims rewards while not fully "rewardable" (e.g., mid-cooldown/early-unlock) forfeits a portion of `userRewards`, and that forfeited portion is recycled into the pool via `_queueNewRewardsWithoutTransfer`, raising `rewardPerTokenStored` for all remaining stakers, including fully-locked ones like the attacker in this scenario. In `mWOMSVBaseRewarder._calExpireForfeit` (lines 385-398), `rewardableAmount` is hardcoded to `_amount` instead of being scaled by the account's actual rewardable percentage from `mWOMSV`. This makes `forfeitAmount` always `0`, so the `if(forfeitAmount > 0)` branch in `_sendReward` (line 374) is unreachable and `ForfeitRewardAdded`/`rewardPerTokenStored` bumps from forfeiture never occur. `updateReward`/`updateRewards` modifiers and `nonReentrant`/`onlyMasterMagpie` guards do not touch this logic at all — they don't stop the bug because the flaw is purely in the forfeit-percentage computation, not in access control or reentrancy.

### Impact Explanation
Any fully-locked mWomSV holder is permanently deprived of the forfeiture-redistribution share the contract's design promises whenever other participants unlock early and call `getReward`. Since `forfeitAmount` is always `0`, `rewardPerTokenStored` never increases from forfeiture events, so `earned()`/`_earned()` for the loyal locker never reflects any redistributed value — this yield is never generated at all (not merely delayed), which is a permanent loss of the redistribution the tokenomics model documents (`ForfeitRewardAdded` event exists specifically for this and never fires with nonzero value). This falls under "permanent freezing/loss of unclaimed yield" for long-term lockers, systemically, across the whole pool's lifetime.

### Likelihood Explanation
This requires no special capital or privileges — it triggers on the normal, permissionless flow of any user starting unlock/cooldown early and calling `getReward()`/`getRewards()` through `MasterMagpie` (both are `onlyMasterMagpie`-gated but reachable by any regular staker via the normal claim path). It happens 100% of the time, for every account and every reward token, with no edge case needed — it is deterministic dead code, not a probabilistic race.

### Recommendation
Fix `_calExpireForfeit` in `mWOMSVBaseRewarder.sol` to compute `rewardableAmount` from the actual rewardable percentage of the account, analogous to `vlMGPBaseRewarder._calExpireForfeit`'s `vlMGP.getRewardablePercentWAD(_account)` call — e.g. add and use `mWOMSV.getRewardablePercentWAD(_account)` (or the equivalent `ILocker` accessor) instead of assigning `rewardableAmount = _amount` directly.

### Proof of Concept
Foundry test plan:
1. Deploy `mWOMSVBaseRewarder` wired to a mock `ILocker`/`IMasterMagpie` that supports at least two accounts: `attacker` (fully locked, never unlocks) and `earlyUnlocker` (starts unlock/cooldown before claiming).
2. Queue rewards via `queueNewRewards` so `rewardPerTokenStored` > 0 for both stakers.
3. Have `earlyUnlocker` call `startUnlock`/enter cooldown on the mock locker, then call `getReward` through `masterMagpie`; assert `_sendReward`'s `forfeitAmount` is always `0` (add a view helper or check `ForfeitRewardAdded` is never emitted) even though the mock locker reports a reduced rewardable percentage for that account.
4. Assert `rewards[token].rewardPerTokenStored` is unchanged by `earlyUnlocker`'s claim (no forfeiture injected).
5. Have `attacker` call `getReward` and assert their `earned()`/received amount matches only their own linear share, with zero contribution from `earlyUnlocker`'s forfeiture — confirming `rewardPerToken` never increases from any forfeiture event, proving the redistribution promised by `_queueNewRewardsWithoutTransfer` never reaches the fully-locked holder.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
