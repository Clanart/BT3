## Title
Failed `git stash pop` is silently treated as success and the stash entry is deleted, permanently losing the user's uncommitted work - (File: `app/src/lib/git/stash.ts`)

### Summary
This is a structural analog of the GMX finding: in the audited contract, the *failure* branch of a two-branch flow (`_handleSwapError`) reused validation logic designed for the *success* branch, silently accepting an outcome the user never consented to. In GitHub Desktop, `popStashEntry` has the same shape: the failure branch of `git stash pop` assumes the operation actually succeeded and destroys the only record of the user's stashed data, with no verification that the working directory actually received those changes.

### Finding Description
`popStashEntry` calls `git stash pop --quiet` and, when it throws, applies this heuristic to decide whether the pop "really" succeeded: [1](#0-0) 

```
if (
  e instanceof GitError &&
  e.result.exitCode === 1 &&
  e.result.stderr.length === 0
) {
  log.info(...)
  // bye bye
  return dropDesktopStashEntry(repository, stashSha)
}
```

The comment in the source itself acknowledges the fragility: *"Not the greatest approach but stash isn't very communicative."* The only signal used to distinguish "pop applied but Git reported the well-known conflict exit code" from "pop actually failed for some other reason" is `exitCode === 1 && stderr.length === 0`. There is no check that the working directory actually contains the popped changes before `dropDesktopStashEntry` is invoked, which unconditionally runs `git stash drop` and permanently removes the entry.

This code path is reached from the "bring my changes to the new branch" checkout flow: [2](#0-1) 

Here Desktop creates a transient stash, checks out the target branch, then calls `popStashEntry` to restore the user's uncommitted changes on the new branch. If `git stash pop` fails for a reason other than a real conflict (e.g. a clean/smudge filter defined by `.gitattributes` in the checked-out branch failing during stash application, a partial/aborted apply, or any other exit-1-with-empty-stderr case not covered by the "MergeConflicts" `expectedErrors` set), Desktop's heuristic misclassifies it as a successful pop and immediately drops the stash — deleting the only backup of the user's uncommitted work with no error surfaced and no way to recover.

Because `.gitattributes`, hooks, and filter configuration are part of repository content that ships with a cloned/fetched repo, a branch authored by an attacker (e.g. a PR branch or remote branch the victim checks out) can define filters/attributes that are exercised precisely during the stash-apply step of this flow, deterministically triggering the exit-1/empty-stderr condition this heuristic misclassifies as success.

### Impact Explanation
The invariant broken is: "the user's stash entry is only deleted once its contents are verified restored to the working directory." Silent violation of this invariant results in **irrecoverable loss of the user's uncommitted work** — data that was never committed and now has no local backup, since Desktop's stash mechanism is the only safety net for `UncommittedChangesStrategy.MoveToNewBranch`. This is the desktop-app-native equivalent of "silent corruption of what the user commits or pushes": the user's local changes disappear without any error dialog, and the operation is reported as successful.

### Likelihood Explanation
The trigger condition (`git stash pop` returning exit code 1 with empty stderr for a reason other than a resolvable conflict) is plausible whenever repository content controls filter/hook behavior invoked during stash application. Because the branch being checked out is attacker-influenced content (a fetched/cloned branch), a crafted `.gitattributes`/clean-filter setup can reliably reproduce this condition on the victim's machine as part of a normal "checkout and bring my changes" workflow — no local access, admin rights, or social engineering beyond checking out an attacker's branch is required.

### Recommendation
After a `git stash pop` failure that isn't an expected/known conflict, verify the actual outcome before dropping the entry — e.g., re-check `git status`/working directory contents against the stash's file list, or only drop the stash when `git stash list` no longer contains the entry (i.e., Git itself dropped it), rather than inferring success purely from `exitCode === 1 && stderr.length === 0`.

### Proof of Concept
1. Attacker publishes a branch containing a `.gitattributes` entry wiring a `clean`/`smudge` filter for a file also present in the victim's stashed changes; the filter is crafted to exit non-zero without writing to stderr when invoked during `git stash apply`.
2. Victim has uncommitted changes on their current branch and checks out the attacker's branch using "Bring my changes to `<branch>`" (`UncommittedChangesStrategy.MoveToNewBranch`), which triggers `checkoutAndBringChanges` → `createStashEntry` → `checkoutIgnoringChanges` → `popStashEntry`.
3. `git stash pop` invokes the attacker-controlled filter during apply, filter fails, Git reports exit code 1 with no stderr content (not one of `expectedErrors`).
4. `popStashEntry`'s catch handler matches `exitCode === 1 && stderr.length === 0`, logs "a stash was popped successfully," and calls `dropDesktopStashEntry`, deleting the stash even though the working directory never received the changes.
5. Victim's uncommitted work is silently gone with no error shown and no recoverable stash entry.

    repository: Repository,
    branch: Branch,
    currentRemote: IRemote | null

    try {
      await this.checkoutIgnoringChanges(repository, branch, currentRemote)
    } catch (checkoutError) {
      if (!isLocalChangesOverwrittenError(checkoutError)) {
        throw checkoutError
      }

      const stash = (await this.createStashEntry(repository, branch))
        ? await getLastDesktopStashEntryForBranch(repository, branch)
        : null

      // Failing to stash the changes when we know that there are changes
      // preventing a checkout is very likely due to assume-unchanged or
      // skip-worktree. So instead of showing a "could not create stash" error
      // we'll show the checkout error to the user and let them figure it out.

        throw checkoutError
      }
