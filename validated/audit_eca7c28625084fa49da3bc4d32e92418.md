### Title
Internal `_multiClaim` Function's `nonReentrant` Modifier Causes Permanent Revert When Invoked From External `nonReentrant` Claim Functions - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie.sol` defines an **internal** function `_multiClaim` that itself carries the `nonReentrant` modifier [1](#0-0) . This function performs the core reward-claiming logic across multiple staking tokens, updating MGP accounting and routing MGP to vlMGP, mWOM, or default pools before delegating to `_claimBaseRewarder` for bonus tokens [2](#0-1) . Applying `nonReentrant` to an internal helper that is only ever reachable from other `MasterMagpie` functions is the same anti-pattern flagged in the external report for `_processVaultRewards`: OpenZeppelin's `ReentrancyGuardUpgradeable` uses a single shared lock (`_status`) per contract instance, so if any external entry point that itself is guarded with `nonReentrant` calls into `_multiClaim`, the second `nonReentrant` check will find the lock already engaged and revert the entire transaction with `ReentrancyGuard: reentrant call`.

### Finding Description
`ReentrancyGuardUpgradeable` (and its non-upgradeable counterpart) implements a single mutex per contract: entering any `nonReentrant`-guarded function sets `_status = _ENTERED`, and any nested call into another `nonReentrant` function in the same contract during that same call stack reverts. `MasterMagpie` already guards its primary user-facing entry points such as `deposit` and `withdraw` with `nonReentrant` [3](#0-2) , showing the pattern of protecting external functions used throughout the contract. `_multiClaim`, however, is marked `internal` yet also carries `nonReentrant` [1](#0-0) . Because it is `internal`, it can only be invoked from other functions inside `MasterMagpie` (e.g., wrapper "multiclaim" style external functions that harvest across multiple staking tokens for a user). If any such caller is itself protected by `nonReentrant` — consistent with the contract's established convention of guarding all state-mutating, fund-moving entry points — then every call to that wrapper will unconditionally revert, because the guard is already engaged by the outer function before `_multiClaim`'s own `nonReentrant` check executes.

This mirrors exactly the bug class described in the external report: a private/internal function's own reentrancy lock conflicts with the lock already held by its caller, rendering the function permanently non-executable rather than providing any real reentrancy protection.

### Impact Explanation
`_multiClaim` is the function responsible for crediting and distributing all pending MGP and bonus-token rewards across a user's staked positions (vlMGP-locked, mWOM, and default pools) [4](#0-3) . If its external wrapper is unconditionally revert-prone due to the nested `nonReentrant` guard, ordinary users lose the ability to claim/harvest already-accrued MGP and bonus rewards through that code path indefinitely. This constitutes a permanent freeze of unclaimed yield for every user relying on the multi-claim entry point, satisfying the "permanent freezing of unclaimed yield" impact bar.

### Likelihood Explanation
This is deterministic, not probabilistic: any ordinary wallet calling the guarded external wrapper around `_multiClaim` will always hit the revert, with no special conditions, privileged access, or timing required. The likelihood is effectively 100% whenever that specific call path is exercised, which is the primary intended use of `_multiClaim`.

### Recommendation
Remove the `nonReentrant` modifier from the internal `_multiClaim` function and rely solely on the `nonReentrant` guard applied at the external entry point(s) that invoke it, consistent with the pattern already used for `deposit`/`withdraw`. If additional protection is required for `_multiClaim` when it is reachable from multiple distinct external functions, ensure only one layer in the call chain applies the guard (i.e., either guard the outer functions only, or guard `_multiClaim` only and remove the modifier from its outer callers), rather than stacking `nonReentrant` on both.

### Proof of Concept
1. Confirm `_multiClaim` is declared `internal nonReentrant`: [1](#0-0) .
2. Identify the external "multiclaim"-style function(s) in `MasterMagpie.sol` that call `_multiClaim` — per the contract's established convention, fund-related external entry points such as `deposit`/`withdraw` are `nonReentrant` [3](#0-2) , and any external claim wrapper following the same convention would also be `nonReentrant`.
3. When such a wrapper is called by a user: the wrapper's `nonReentrant` modifier sets the lock, then calls `_multiClaim`, whose own `nonReentrant` modifier checks the lock, finds it already set, and reverts with `ReentrancyGuard: reentrant call is not allowed`.
4. Every call to that claim entry point therefore reverts, permanently blocking users from claiming already-accrued MGP/bonus rewards through this path.

**Note on verification limits**: due to tool/iteration constraints, I was able to directly confirm that `_multiClaim` is declared as an `internal nonReentrant` function, but I could not directly view the source of the external wrapper function(s) that call it to confirm they are also decorated with `nonReentrant` in this session. This should be verified by inspecting the full `MasterMagpie.sol` file (searching for all call sites of `_multiClaim(`) before treating this as fully confirmed.

    function _multiClaim(address[] calldata _stakingTokens, address _user, address _receiver, address[][] memory _rewardTokens) internal nonReentrant {
        uint256 length = _stakingTokens.length;
        if (length != _rewardTokens.length) revert LengthMismatch();

        uint256 vlMGPPoolAmount;
        uint256 mWOmPoolAmount;
        uint256 defaultPoolAmount;

        for (uint256 i = 0; i < length; ++i) {
            address _stakingToken = _stakingTokens[i];
            UserInfo storage user = userInfo[_stakingToken][_user];
            
            updatePool(_stakingToken);
            uint256 claimableMgp = _calNewMGP(_stakingToken, _user) + unClaimedMgp[_stakingToken][_user];

            if (_stakingToken == address(vlmgp)) {
                vlMGPPoolAmount += claimableMgp;
            } else if (MPGRewardPool[_stakingToken]) {
                mWOmPoolAmount += claimableMgp;
            } else {
                defaultPoolAmount += claimableMgp;
            }

            unClaimedMgp[_stakingToken][_user] = 0;
            user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
            _claimBaseRewarder(_stakingToken, _user, _receiver, _rewardTokens[i]);
        }

        if (vlMGPPoolAmount > 0) {
            _sendMGPForVlMGPPool(_user, _receiver, vlMGPPoolAmount);
        }

        if (mWOmPoolAmount > 0) {
            _sendMGP(_user, _receiver, mWOmPoolAmount);
        }

        if (defaultPoolAmount > 0) {
            _sendVlMGPFor(_user, _receiver, defaultPoolAmount);
        }

        uint256 totalReward = vlMGPPoolAmount + mWOmPoolAmount + defaultPoolAmount;

        if (totalReward > 0 && referral != address(0)) {
            IReferralStorage(referral).trigger(_user, totalReward);
        }
    }
