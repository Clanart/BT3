### Title
OP_RETURN data output is excluded from the transaction fee weight calculation - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Caviar report where one code path (`flashLoan`) escaped the protocol fee that all sibling paths charged, `SignableTransaction::new` adds an `OP_RETURN` output carrying up to 80 bytes of caller-supplied data to the transaction, but computes `needed_fee`/`vbytes` from `payments` and `change` only — the data output's weight is never charged for.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments`, then unconditionally appends a zero-value `OP_RETURN` output when `data` is supplied (lines 194–202). Both fee calculations then ignore it:

- `calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204 reconstructs a template transaction containing only `payments` (and optionally `change` at line 226). The `data` output is never passed in, so `vbytes` — and therefore `needed_fee = fee_per_vbyte * vbytes` at line 206 — omits the ~11–91+ vbytes the OP_RETURN adds.
- The change branch (lines 224–235) also uses `calculate_weight_vbytes(..., payments, Some(&change))`, again excluding the data output, so the change output is additionally credited the fee that should have been spent on the data output's weight.

Every other output (payments, change) is charged `fee_per_vbyte` for its weight; the `data` output rides for free — the same "one path doesn't pay" shape as the flashloan finding. [1](#0-0) [2](#0-1) 

### Impact Explanation
- The resulting transaction's effective fee rate is strictly lower than the `fee_per_vbyte` requested: `fee()` equals `needed_fee`, but the real vsize is larger than `vbytes` by the OP_RETURN's serialized size.
- The `TooLowFee` minimum-relay check at line 211 is evaluated against the under-counted `vbytes`, so a transaction can pass the check while its true fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` (a ~91-byte OP_RETURN on a small tx can push a borderline rate under the minimum), producing a transaction that won't relay/confirm.
- Any party that can attach `data` to a signed transaction (the processor passes user-supplied inscription data through this path) gets up to ~91 vbytes of block space unpaid, with the shortfall absorbed by the change output, i.e. by the multisig — funds are signed away at a lower fee rate than the scheduler accounted for.

### Likelihood Explanation
Reachable by an unprivileged user whenever `data` is `Some`: any output-bearing flow that attaches an OP_RETURN triggers it deterministically. The miscount is bounded (~83 bytes max pushdata overhead + output overhead), capping severity at Medium — consistent fee leakage per data-carrying transaction plus the relay-minimum edge case, not direct theft.

### Recommendation
Include the OP_RETURN output in the weight accounting: build a `TxOut` list containing payments, the data output (when present), and change, and pass that to `calculate_weight_vbytes` — or add the OP_RETURN output's serialized weight (`8 + compact_size(script_len) + script_len` weight units, value + scriptPubKey) to `weight`/`vbytes` before computing `needed_fee` and the minimum-fee check. Apply the same correction in the `change` recalculation at line 226.

### Proof of Concept
```rust
// Construct two otherwise-identical transactions, one with data.
let no_data = SignableTransaction::new(
    vec![output.clone()], &payments, Some(change.clone()), None, FEE,
).unwrap();
let with_data = SignableTransaction::new(
    vec![output], &payments, Some(change), Some(vec![0xaa; 80]), FEE,
).unwrap();

// The data-carrying TX reports the *same* needed_fee despite being ~90 vbytes larger.
assert_eq!(no_data.needed_fee(), with_data.needed_fee()); // BUG: should differ
// with_data.transaction().vsize() > vbytes used for its fee accounting,
// so its real sat/vbyte rate < FEE.
```
