### Title
Automatic, unconfirmed rewrite of a repository's git remote URL from GitHub API data allows attacker-controlled redirection of future pushes/fetches - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
The external report describes a class of bug where a value that determines a critical outcome (policy price/duration) is computed from external/mutable state at one point in time and then silently applied later, with no user-supplied hard limit or deadline to guard against the value having changed. The equivalent broken invariant in GitHub Desktop is `updateRemoteUrl()`, which silently rewrites a repository's configured git remote (`origin`) URL to whatever `clone_url` the GitHub API currently returns for the repository, with no user confirmation, no "hard limit" (e.g. requiring the new owner/host to match some trusted value), and no staleness/deadline check on the API-supplied value.

### Finding Description
`updateRemoteUrl` compares the repository's cached `GitHubRepository.cloneURL` against the freshly fetched `apiRepo.clone_url` and, if the protocol matches and the previously-stored URL still matches the local remote, blindly calls `gitStore.setRemoteURL` to point `origin` at whatever URL the API returned: [1](#0-0) 

This function is invoked automatically and silently as part of routine background operations — whenever the app refreshes the associated GitHub repository (on selecting a repository, on every fetch/push, and after an account change) — with no dialog, diff, or explicit user approval shown: [2](#0-1) [3](#0-2) 

The guard condition (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`) only checks that the *protocol* hasn't changed and that the user hasn't *manually* diverged from the previously cached URL — it performs no validation of the new destination itself (e.g., confirming the owner/organization is the one the user originally trusted). Because GitHub repository renames and ownership transfers are fully controlled by whoever owns/administers the repository, and because Desktop treats the API's `clone_url` as authoritative truth to silently reconcile the local git config, an attacker who controls the remote repository object (the one the victim has added as `origin`, e.g. their own public repo or fork used in a collaboration/PR workflow) can rename or transfer that repository to a destination of their choosing. On the victim's next background refresh, `setRemoteURL` will point `origin` at the new, attacker-chosen URL without any warning, changing where all subsequent `git push`/`git fetch` operations for that repository go: [4](#0-3) 

### Impact Explanation
If successful, the user's local `origin` remote is silently repointed to a destination fully controlled by the attacker. Because the redirection happens transparently in the background (no confirmation UI, no visual diff of the remote URL), the user will continue to commit and push exactly as before, but their pushes now go to wherever the attacker last renamed/transferred their repo to. This is a silent corruption of what the user pushes — code, and potentially secrets embedded in commits, can end up delivered to an attacker-controlled endpoint the user never explicitly consented to. This qualifies under "silent corruption of what the user commits or pushes," driven by an attacker-controlled GitHub API object (the repository's own metadata).

### Likelihood Explanation
The precondition is that the victim has a `GitHubRepository` association in Desktop pointing at a repository the attacker owns or administers (a very common scenario: cloning a public repo, working against a fork, or a repo where the attacker is later granted or already holds owner/admin rights). No compromise of the victim's account, host, or credentials is required — the attacker only needs to rename/transfer their own repository, which is standard GitHub functionality. The rewrite then happens automatically the next time Desktop refreshes repository metadata (selecting the repo, fetching, or pushing), which occurs routinely without any user action beyond normal usage.

### Recommendation
Do not silently rewrite the git remote URL based on API data. At minimum:
- Require explicit user confirmation (a dialog showing old vs. new URL) before changing `origin`'s URL due to an API-detected rename/transfer.
- Add a "hard limit"/allow-list check equivalent to the report's recommendation — e.g., only auto-update if the owner login is unchanged (only the repo name changed) and flag any change of owner/organization as requiring explicit approval.
- Consider adding a "trust anchor" check (e.g., compare repository IDs from the GitHub API rather than trusting `clone_url` string matching alone) so a renamed-then-reused name or a transferred repository cannot silently redirect the local remote.

### Proof of Concept
1. Attacker creates and shares/publicizes a repository `github.com/attacker/legit-project`; victim clones it in GitHub Desktop, so `origin` = `https://github.com/attacker/legit-project`.
2. Victim works normally; Desktop periodically calls `repositoryWithRefreshedGitHubRepository`, which calls `api.fetchRepository(owner, name)` and then `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`.
3. Attacker renames/transfers the repository (e.g., renames to `attacker/other-project`, or transfers ownership to a second attacker-controlled account `attacker2/legit-project`). GitHub's redirect means `api.fetchRepository` (called with the previously cached owner/name) still resolves and returns the new `clone_url`.
4. On the victim's next background refresh/fetch, `updateRemoteUrl` sees `protocolsMatch = true`, `remoteUrlUnchanged = true` (the local remote still matches the previously cached URL), `urlsMatch = false` (new clone_url differs) — and calls `gitStore.setRemoteURL('origin', <attacker-chosen URL>)` with no prompt.
5. The victim's next `git push` (via Desktop's push flow, which uses `gitStore.defaultRemote`/`currentRemote`) silently pushes to the attacker's newly chosen destination. [5](#0-4)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

export async function setRemoteURL(

  name: string,
  url: string

  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
