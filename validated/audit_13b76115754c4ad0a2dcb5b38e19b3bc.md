### Title
Reward-sniping via front-run deposit into MasterMagpie before WombatStaking.vote() queues bribe rewards - (File: wombat/WombatStaking.sol / rewards/BaseRewardPoolV2.sol)

### Summary
`WombatStaking.vote()` is triggered by the bribeManager (via `WombatBribeManager.castVotes`) and, for each pool, forwards harvested bribe/WOM rewards directly into the pool's `BaseRewardPool` with `IBaseRewardPool(_rewarders[i]).queueNewRewards(rewardAmount, rewardToken)` [1](#0-0) . That call is publicly visible in the mempool, and any unprivileged LP holder can front-run it by depositing a large amount of LP into `MasterMagpie`/`WombatPoolHelper` immediately before it lands, then withdraw right after, capturing a share of the reward proportional to their instantaneous stake rather than any real holding period.

### Finding Description
`BaseRewardPoolV2._provisionReward` (called from `queueNewRewards`) computes the reward index as a single snapshot update:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingTokenDecimals) / totalStaked();
``` [2](#0-1) 

This is not a per-second/continuous streaming accrual (unlike `MasterMagpie`'s MGP `accMGPPerShare` which uses a time `multiplier`, see `updatePool` at [3](#0-2) ) — it is a discrete, instantaneous distribution based on whatever `totalStaked()` happens to be at the exact block the reward is queued. Whoever holds a large balance of the receipt token in the rewarder at that single block captures a proportional slice of the entire reward, regardless of how long they've actually staked.

The reward-forwarding path is:
- `WombatBribeManager.castVotes()` → `wombatStaking.vote(_pools, votes, rewarders, msg.sender)` [4](#0-3) 
- `WombatStaking.vote()` harvests bribes from `voter.vote()` and calls `IBaseRewardPool(_rewarders[i]).queueNewRewards(rewardAmount, rewardToken)` for the pool's rewarder [5](#0-4) . The `_rewarders[i]` is the same `BaseRewardPool` created in `registerPool` that tracks receipt-token stakers in `MasterMagpie` [6](#0-5) .

Nothing in `MasterMagpie._deposit`/`_withdraw` [7](#0-6)  or `WombatPoolHelper.deposit`/`withdraw` [8](#0-7)  enforces a minimum holding period, cooldown, or vesting before a staker can claim their proportional share of a freshly queued reward. `queueNewRewards` itself is only gated by `onlyManager` (a manager role controlling *who can add rewards*, not who can *claim* them) [9](#0-8) ; it does nothing to prevent an ordinary staker from being present at the reward snapshot moment. Because `vote()` is an externally-observable transaction from the bribeManager, an attacker can:
1. Watch the mempool for the bribeManager's `castVotes()`/`vote()` transaction.
2. Submit a higher-gas transaction that deposits a large LP amount into `WombatPoolHelper`/`MasterMagpie` so it lands in the same block just before `vote()`.
3. Let `vote()` execute `queueNewRewards`, which computes `rewardPerTokenStored` using `totalStaked()` inflated by the attacker's fresh deposit — giving the attacker a large share of `rewardPerToken` credit despite zero holding duration.
4. Immediately withdraw (`WombatPoolHelper.withdraw` → `WombatStaking.withdraw` → `_unstake`/`burnReceiptToken`) and claim, realizing the reward with `getReward`/`_multiClaim`, which use `userRewardPerTokenPaid` snapshots updated on stake/unstake through the `updateReward`-style accounting in `BaseRewardPoolV2`/`BaseRewardPool` [10](#0-9) .

This dilutes the share that genuine long-term LP stakers would have received from that reward-queuing event, since the reward pie is fixed and distributed strictly by instantaneous balance ratio rather than time-weighted balance.

### Impact Explanation
This is a "theft of unclaimed yield from long-term stakers" style issue: capital that would have accrued proportionally to genuine long-duration LP stakers is redirected to a flash/JIT staker who bears essentially no capital-lockup risk. The magnitude of loss scales with (a) the size of the queued bribe/WOM reward at that call, and (b) the ratio of the attacker's flash deposit to the pre-existing `totalStaked()`. In pools with modest existing TVL and periodic large bribe payouts, an attacker with sufficient capital (borrowed or owned) could capture a disproportionate share in a single block.

### Likelihood Explanation
Feasibility depends on:
- The attacker being able to see the bribeManager's `vote()`/`castVotes()` transaction in the mempool and outbid it in the same block (standard front-running/MEV capability, not requiring any privileged role).
- The attacker needing enough deposit-token/LP-token capital to make a meaningful dent in `totalStaked()`, and being able to complete both deposit into the Wombat pool (`WombatStaking.deposit`/`depositLP`) and a subsequent withdrawal (`WombatStaking.withdraw`) without being blocked — both are unprivileged, permissionless functions with only `nonReentrant`/`whenNotPaused`/pool-helper-only checks, no time lock [11](#0-10) .
- Slippage/minAmount checks on Wombat pool deposit/withdraw and possible underlying-pool fees are the main friction, but these do not prevent the attack, they only affect net profitability, which is data-dependent (pool depth, bribe size) and cannot be conclusively ruled out from the code alone.
- The attack is repeatable every time `vote()`/`castVotes()` is called (an admin/bribeManager-triggered event that recurs periodically), making it a systemic rather than one-off issue.

### Recommendation
Change reward distribution for bribe/WOM rewards to a time-weighted streaming model (continuously accrue `rewardPerToken` over a duration, similar to Synthetix `StakingRewards`, rather than instantaneously dividing by `totalStaked()` at a single block), or add a minimum staking duration/cooldown before newly deposited stake becomes eligible for freshly queued rewards, or snapshot eligible stakers prior to the `vote()` call (e.g., based on a pre-vote block) so late deposits cannot retroactively claim a share of rewards queued in the same block.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `WombatStaking`, `WombatBribeManager`, a `BaseRewardPoolV2` for a test pool, and seed several "long-term" stakers with LP deposited well before the test's `vote()` call.
2. Simulate mempool ordering: in the same block, first execute attacker's `WombatPoolHelper.depositLP()` (large amount, e.g., 10x current `totalStaked()`), then execute `WombatBribeManager.castVotes()` → `WombatStaking.vote()` which calls `queueNewRewards` on the pool rewarder with a known bribe amount.
3. Immediately after, in the same or next transaction, have the attacker call `WombatPoolHelper.withdraw()` for their full deposited amount, followed by `MasterMagpie.multiclaim`/`claimBribe` for the reward token.
4. Assert: attacker's claimed reward / bribe amount ≈ attacker's deposit / new `totalStaked()` (i.e., near-instant snapshot share), and compare this to what the attacker's true time-weighted share should have been (≈0, since holding duration is 1 block) — demonstrate `attackerReward >> timeWeightedFairShare`.
5. Assert genuine long-term stakers' claimable reward for that same `queueNewRewards` event is correspondingly reduced versus a control run where the attacker's deposit/withdraw does not occur. [5](#0-4) [2](#0-1)

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }

        updatePool(_stakingToken);

        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][_account];

        if (user.amount > 0) {
            _harvestMGP(_stakingToken, _account);

        user.amount = user.amount + _amount;
        if (!_isVlmgp) {

        }

        if (_amount > 0)

                emit Deposit(_account, _stakingToken, _amount);

    }

    function _withdraw(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        _harvestAndUnstake(_stakingToken, _account, _amount, _isVlMgp);

        if (!_isVlMgp)

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
