### Title
Naive `content.split('---', 2)` delimiter counting in `extract_frontmatter` allows a `pattern`/value containing "---" to silently drop `action: block` into the message body, downgrading a deny rule to the default `warn` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` locates the YAML frontmatter block with a blind `content.split('---', 2)`, treating the third literal occurrence of the substring `---` anywhere in the file as the closing delimiter, with no quoting/escaping awareness. If a rule file's frontmatter contains a `pattern` (or any string value) that itself contains `---` positioned before the `action: block` line, the split boundary shifts so that `action: block` (and any fields after it) end up in the parsed "message body" instead of the `frontmatter` dict. `Rule.from_dict` then falls back to its default `action = frontmatter.get('action', 'warn')`, silently converting an intended blocking rule into a non-blocking `warn` rule.

### Finding Description
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` performs: [1](#0-0) 
It naively splits on the literal `---` substring with `maxsplit=2`, assuming the first two occurrences are the opening/closing YAML delimiters. This assumption breaks if any frontmatter value legitimately contains `---` (e.g., a Bash pattern such as `rm -rf ---force` or any regex/string with three consecutive dashes) placed before the `action:` key in field order.

`Rule.from_dict` reads the action with a default of `warn`: [2](#0-1) 
so any field that fails to land inside the recovered `frontmatter` dict (because the naive split truncated the frontmatter early) is silently lost, and `action` reverts to `warn` even though the file visually and semantically states `action: block`.

The rule-creation guidance in `plugins/hookify/commands/hookify.md` places `pattern` before `action` in the generated file template: [3](#0-2) 
and encourages regex patterns for dangerous Bash commands (e.g. `rm\s+-rf|chmod\s+777|dd\s+if=`), which are exactly the kind of user/LLM-authored strings that could plausibly contain a `---`-like substring (e.g., patterns matching `--force`, `---`, git-diff-style markers, or heredoc delimiters) without the author realizing this breaks the parser. Once the delimiter miscount happens, `action: block` (which appears after `pattern` in the template) is pushed into the "message" half of the split and never reaches the `frontmatter` dict, so `Rule.from_dict` defaults it to `warn`.

At enforcement time, `plugins/hookify/core/rule_engine.py`'s `evaluate_rules` only denies the tool call when `rule.action == 'block'`; anything else is downgraded to a mere `systemMessage` warning while the tool call proceeds: [4](#0-3) 
This is invoked directly from `plugins/hookify/hooks/pretooluse.py`'s `main()`, which loads rules and evaluates them for every `Bash`/`Edit`/`Write`/`MultiEdit` tool call: [5](#0-4) 
No validation step checks that the number of `---` occurrences in the file is exactly 2, nor that `action` was actually present as a top-level frontmatter key before falling back to `warn` — the code treats "field absent" and "field intentionally omitted" identically, silently weakening the security posture instead of failing safe (e.g., raising/rejecting the malformed file).

### Impact Explanation
A rule author (user or an LLM-authored rule via `/hookify`, whose generation is guided by `conversation-analyzer` output which explicitly recommends turning "High severity" issues into blocking rules) can end up with a `.claude/hookify.*.local.md` file that displays `action: block` in plain text but is silently parsed and enforced as `action: warn` due to an incidental `---` inside an earlier field value. Because `pretooluse.py` always exits 0 and never fails closed, and `evaluate_rules` treats non-`block` rules as pass-through warnings, the dangerous Bash/Edit/Write operation the user believed was hard-blocked is instead allowed to execute after only a warning message — a real bypass of a locally configured deny control, matching "Unauthorized local command execution that bypasses Claude Code approval or deny controls." The impact is scoped to whatever the rule was meant to prevent (e.g., `rm -rf`, writing secrets, dangerous `chmod`), executed without the intended block.

### Likelihood Explanation
This requires no privilege escalation and no direct file-write access beyond what an ordinary `/hookify` user (or LLM-generated rule content acting on conversation analysis) already has: any hookify rule whose `pattern`/string value happens to contain a `---`-like triple-dash sequence and is positioned before `action:` in the frontmatter block will trigger the downgrade deterministically and reproducibly — it is a pure parsing bug, not dependent on race conditions or timing. The likelihood of a rule author unknowingly choosing such a pattern (e.g. `--force`, `---`, or any dash-based flag/regex quantifier sequence like `-{3}`) is realistic given the freeform nature of regex patterns suggested for dangerous commands.

### Recommendation
Replace the ad-hoc `content.split('---', 2)` with a delimiter detector that only recognizes `---` when it appears alone on its own line (e.g. `re.match(r'^---\s*$', line)` scanning line-by-line, similar to the `^---$` anchoring used in the plugin's own bash reference scripts), so that `---` embedded inside quoted values or patterns cannot be misinterpreted as a frontmatter boundary. Additionally, make `Rule.from_dict`/`load_rule_file` fail closed (reject and refuse to load the rule, or default unspecified `action` to `block` for safety-relevant rules) rather than silently defaulting to `warn` whenever a security-relevant field is unexpectedly missing, and add a lint/validation step in the `/hookify` file-creation flow that re-parses the generated file and asserts the round-tripped `Rule.action` matches what was requested before confirming rule creation to the user.

### Proof of Concept
```python
# test_extract_frontmatter_delimiter_confusion.py
from plugins.hookify.core.config_loader import extract_frontmatter, Rule

malicious_content = '''---
name: block-dangerous-rm
enabled: true
event: bash
pattern: "rm -rf ---force"
action: block
---

This command is dangerous and must be blocked!
'''

frontmatter, message = extract_frontmatter(malicious_content)

# Because "pattern" contains a literal "---", the naive
# content.split('---', 2) treats that as the closing delimiter,
# pushing "action: block" and everything after it into `message`.
assert 'action' not in frontmatter, (
    f"Expected 'action' to be lost due to delimiter confusion, got: {frontmatter}"
)

rule = Rule.from_dict(frontmatter, message)

# The rule silently reverts to the non-blocking default despite the
# file visibly stating action: block.
assert rule.action == 'warn', (
    f"Expected downgraded action 'warn', got: {rule.action}"
)
print("Vulnerability confirmed: block rule silently downgraded to warn.")
```
Expected result: the assertions pass, demonstrating that `extract_frontmatter` misparses the file so that `Rule.action` becomes `"warn"` instead of the file's declared `"block"`. An integration-level PoC would place this file at `.claude/hookify.block-dangerous-rm.local.md` in a cloned repo, invoke `plugins/hookify/hooks/pretooluse.py` with a `Bash` tool call of `rm -rf /tmp/test`, and assert that the hook's JSON output contains only a `systemMessage` (warning) rather than `hookSpecificOutput.permissionDecision == "deny"`, confirming the command is allowed to execute despite the file stating `action: block`.
