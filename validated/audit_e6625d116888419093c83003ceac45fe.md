### Title
Stale `safe.directory` trust exemption is never revoked when a repository is removed, permitting silent re-exploitation of a reused path - (File: `app/src/lib/git/config.ts`)

### Summary
`GuardianRecoveryValidator.onUninstall` fails to purge `pendingRecoveryData`, so a stale trust/approval artifact survives a "disconnect" event and is later reused to skip a required security gate. The equivalent broken invariant exists in GitHub Desktop's directory-trust flow: once a user clicks "Trust Repository"/"add an exception" for a path Git considers unsafe (owned by a different user), Desktop calls `addSafeDirectory()`, which permanently appends that path to the **global** `safe.directory` git config. When the user later removes that repository from Desktop (`_removeRepository`), nothing revokes the `safe.directory` entry.

### Finding Description
`addSafeDirectory` in [1](#0-0)  permanently records a path into the user's global gitconfig via `addGlobalConfigValueIfMissing('safe.directory', path)`. This is invoked from the two "Trust Repository" UI flows: [2](#0-1) [3](#0-2) 

The removal path, `_removeRepository`, only deletes the repository record from Desktop's own database and optionally moves the folder to trash — it never calls any git-config cleanup to strip the path from `safe.directory`: [4](#0-3) [5](#0-4) 

There is no `removeSafeDirectory` counterpart anywhere in the codebase (confirmed via search — only `addSafeDirectory` call sites exist, in the two "Trust Repository" components).

This mirrors the report's broken invariant exactly: an approval/trust decision that is supposed to be scoped to a specific instance (the account's `pendingRecoveryData` in the report; a specific repository/clone in Desktop) is persisted in a durable store (`pendingRecoveryData` mapping vs. global `~/.gitconfig`) and is never cleared when that instance is disconnected/removed ("uninstall" vs. "remove repository"). Because git's ownership check is purely path-based (`safe.directory=<path>`), any future git repository that later occupies that same filesystem path — regardless of who owns/authored it — silently inherits the old trust decision and Git will no longer warn or block operations there.

### Impact Explanation
Git's "dubious ownership" check exists specifically to stop Git from executing repository-defined hooks/config for directories that could have been planted by another (potentially malicious) local account or process. Bypassing that check re-enables the attack it was designed to prevent — for example: a shared machine, a temp/scratch clone path, or a path that's recreated by another OS user or process later; if that path is repopulated with a malicious repository (attacker-controlled `.git` hooks/config), Desktop/Git will treat it as trusted without any prompt, because the stale `safe.directory` entry is still present. This does not require the user to click "Trust" again — the check is silently skipped, i.e. it is a silent removal of a security gate governing potential local code execution via git hooks/config. This lines up with the impact categories in scope (silent bypass of a security control tied to attacker-influenced repository content).

### Likelihood Explanation
Likelihood is moderate: it requires (1) the user to have trusted a path once (a legitimate, expected action for shared-owner scenarios), (2) removal of that repository from Desktop without corresponding revocation, and (3) the same path later being reused by different repository content. Reuse of paths is plausible in CI/build directories, `/tmp`-style scratch clone targets, shared multi-user machines, or Desktop's own re-clone-to-same-path flows (`_cloneAgain`/`Clone Again`, `Locate…`) which explicitly operate on the exact previous path. No admin rights or pre-existing malware are needed beyond the generic threat model that `safe.directory` protects against (a different local user/process controlling the directory contents at a later reuse).

### Recommendation
When a repository is removed from Desktop (`_removeRepository` / `repositoriesStore.removeRepository`), remove the corresponding entry from the global `safe.directory` config if Desktop was responsible for adding it (introduce and call a `removeSafeDirectory(path)` counterpart to `addSafeDirectory`, using `git config --global --unset safe.directory <path>`). Alternatively, track which paths were trusted due to Desktop's prompt (not pre-existing user config) so only Desktop-added trust exceptions are revoked on removal, avoiding removal of directories a user trusted outside of Desktop.

### Proof of Concept
1. On a machine where another OS user (or a synced/shared folder mechanism) can plant files at a known path, clone or copy a repository to `C:\Users\Shared\proj` (or similar) owned by a different user than the current one.
2. In Desktop, use "Add local repository" → Desktop reports "potentially unsafe" via `MissingRepository`/`AddExistingRepository` → click "Trust Repository", which calls `addSafeDirectory(path)` ( [6](#0-5) ), permanently adding the path to `~/.gitconfig`'s `safe.directory`.
3. Remove the repository from Desktop via `_removeRepository` ( [4](#0-3) ). Note that `safe.directory` in the global gitconfig still contains the path.
4. Have the attacker (a different local account/process with write access to that path, or a scheduled job that repopulates temp directories) replace the contents at that same path with a malicious `.git` repository containing hooks or `core.fsmonitor`/`core.hooksPath` config designed to execute code.
5. Re-add the same path in Desktop (or have it auto-detected via "Clone Again"/"Locate…" pointing back at the same path). Git and Desktop will treat the directory as trusted with no prompt, because `safe.directory` still lists it, silently skipping the ownership-mismatch warning that would otherwise have surfaced the malicious substitution.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

  public async _removeRepository(
    repository: Repository | CloningRepository,
    moveToTrash: boolean
  ): Promise<void> {
    try {
      if (moveToTrash) {
        try {
          await shell.moveItemToTrash(repository.path)
        } catch (error) {
          log.error('Failed moving repository to trash', error)

          this.emitError(
            new Error(
              `Failed to move the repository directory to ${TrashNameLabel}.\n\nA common reason for this is that the directory or one of its files is open in another program.`
            )
          )
          return
        }
      }

      if (repository instanceof CloningRepository) {
        this._removeCloningRepository(repository)
      } else {
        await this.repositoriesStore.removeRepository(repository)
      }
    } catch (err) {
      this.emitError(err)
      return
    }

    const allRepositories = await this.repositoriesStore.getAll()
    if (allRepositories.length === 0) {
      this._closeFoldout(FoldoutType.Repository)
    } else {
      this._showFoldout({ type: FoldoutType.Repository })
    }
  }
