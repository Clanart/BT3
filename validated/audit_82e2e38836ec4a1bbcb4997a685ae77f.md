### Title
Empty Schnorr aggregate signature verifies as valid when the verifier's statement set is empty - ([File: crypto/schnorr/src/aggregate.rs])

### Summary
`SchnorrAggregate::verify` accepts an aggregate containing zero signatures whenever the caller's `keys_and_challenges` slice is also empty, and neither `SchnorrAggregate::read` nor `verify` rejects the zero-length case. An attacker can therefore present a 36-byte "credential" (`u32` length `0` followed by a zero scalar) that `verify` returns `true` for — an empty credential that "authenticates" an empty/unknown statement set, the analog of PAM authenticating a non-existent user with an empty password.

### Finding Description
The PAM bug class is: a degenerate empty/absent credential presented for a non-existent account falls through the authentication path and succeeds. The same shape exists here.

- `SchnorrAggregate::read` reads a `u32` count and then that many `R` points; a count of `0` yields `Rs = []` with `s` read normally (`crypto/schnorr/src/aggregate.rs:77-88`).
- `verify` only checks `self.Rs.len() != keys_and_challenges.len()` before evaluating the multiexp (`crypto/schnorr/src/aggregate.rs:128-130`). With both empty, `pairs` contains only `(-self.s, generator())`. For `s = 0` the sum is the identity, so `multiexp_vartime(&pairs).is_identity()` is `true` (`crypto/schnorr/src/aggregate.rs:138-145`).
- The honest aggregation path (`SchnorrAggregator::complete`) explicitly refuses to produce an empty aggregate (`crypto/schnorr/src/aggregate.rs:175-178`), showing the library authors considered the empty case invalid — yet the verification path does not enforce the same invariant, letting an attacker bypass the intended check by serializing the aggregate directly.
- Because the weight transcript (`DigestTranscript::new(dst)` + `domain_separate(b"signatures")` + per-statement `challenge` messages, `aggregate.rs:132-136`) appends nothing for an empty statement set, there is also no domain-separated length commitment distinguishing "zero signatures" from a real aggregate.

### Impact Explanation
Any verifier that builds `keys_and_challenges` from attacker-supplied or attacker-influenced data — e.g., iterating over statements claimed by a prover, or verifying an aggregate over a set that ends up empty after filtering — will accept `Rs = []`, `s = 0` as a valid aggregate signature. The verifier's transcript of "verified signatures" then attests to nothing while reporting success, which is precisely the forged-verification outcome: a signature the signer never produced is reported as valid for a key/messages set the attacker reduced to nothing. This breaks the completeness guarantee the API contract implies (`verify` returning `true` ⇒ every queued statement held), enabling bypass of any gate that requires "all statements verified" when the attacker can empty the statement set.

### Likelihood Explanation
Exploitation requires the verifier to reach `verify` with an empty `keys_and_challenges`, which depends on the caller's logic — hence Medium rather than Critical/High. However, the vulnerable path is fully reachable by an unprivileged party: the attacker only needs to send the 36-byte encoding `00 00 00 00` + 32 zero bytes to `SchnorrAggregate::read` (or construct the object directly) in any context where they control or shrink the set of statements being verified. No keys, no threshold participation, and no protocol cooperation are needed.

### Recommendation
Reject the degenerate case in both places:

- In `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`), error when the decoded count is `0`.
- In `SchnorrAggregate::verify` (`crypto/schnorr/src/aggregate.rs:127-130`), additionally return `false` when `self.Rs.is_empty()` (or `keys_and_challenges.is_empty()`), matching the invariant already enforced by `SchnorrAggregator::complete` at `aggregate.rs:176`.
- Optionally append the statement count to the weight transcript so the aggregation weights also bind to the number of aggregated signatures.

### Proof of Concept
```rust
// crypto/schnorr context, e.g. C = Ristretto (dalek-ff-group)
use schnorr::aggregate::SchnorrAggregate;
use ciphersuite::Ciphersuite;

// Attacker-controlled bytes: count = 0, then a zero scalar s
let mut bytes = 0u32.to_le_bytes().to_vec();
bytes.extend(<C as Ciphersuite>::F::ZERO.to_repr().as_slice());

let agg = SchnorrAggregate::<C>::read(&mut bytes.as_slice()).unwrap();
assert!(agg.Rs().is_empty());

// Any verifier whose statement list is empty accepts the empty credential
assert!(agg.verify(b"some dst", &[]));
```

The call to `verify` returns `true` even though no signature — and no statement — was ever verified: the empty credential authenticates, exactly as the empty password did for a non-existent PAM user.
