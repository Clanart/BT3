### Title
Unbounded Recursive AccountKey Decoding Leads to DoS via Stack Exhaustion — (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes nested `AccountKeySerializer` values without any limit on nesting depth, mirroring the MaterialX `XInclude` bug class: an attacker who fully controls the *content* of a single field (here, the RLP-encoded `AccountKey` bytes inside an `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction) can force unbounded Go call-stack recursion during transaction decoding, before any "no nested composite type" validation ever runs.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` reads a list of raw byte strings and, for each one, immediately decodes it into a fresh `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a `keyType`, constructs the corresponding `AccountKey` via `NewAccountKey`, and then calls `s.Decode(serializer.key)` on that key — which, if the type is again `AccountKeyTypeRoleBased`, re-enters `AccountKeyRoleBased.DecodeRLP`: [2](#0-1) [3](#0-2) 

Because each level of `RoleBased` is itself just an RLP byte-string element inside the parent's list, an attacker can nest `RoleBased(RoleBased(RoleBased(...)))` to an arbitrary depth, and the decoder will recurse through Go function calls (`DecodeRLP` → `rlp.DecodeBytes` → `DecodeRLP` → ...) with no depth counter or limit anywhere in the chain, exactly analogous to the MaterialX `XInclude` chain that lacked an import-depth limit.

Critically, the only defense against nested composite types (`IsCompositeType()` / `ErrNestedCompositeType`) is enforced *after* full decoding completes, in `CheckInstallable`/`CheckUpdatable`: [4](#0-3) 
This means the recursive decode itself — the operation that can exhaust the stack — happens unconditionally before the nesting check has any chance to reject the structure.

This `Key` field is decoded as part of ordinary transaction deserialization for `TxInternalDataAccountUpdate` (and its fee-delegated variants), which is reachable from any unprivileged party submitting a raw transaction via public RPC (`eth_sendRawTransaction`/`SendRawTransaction`) or via p2p transaction propagation: [5](#0-4) 

### Impact Explanation
A crafted `AccountUpdate` (or `FeeDelegatedAccountUpdate`) transaction containing a deeply nested `AccountKeyRoleBased` structure can be broadcast or submitted to any Kaia node. When the node RLP-decodes the transaction (in the tx pool, RPC ingestion, or block/body decoding), it will recurse through `AccountKeyRoleBased.DecodeRLP`/`AccountKeySerializer.DecodeRLP` at a depth chosen entirely by the attacker, exhausting the goroutine stack and crashing the node process (`SIGSEGV`/fatal error: stack overflow). This is a network-wide, transaction-triggered Denial-of-Service: a single unprivileged sender can crash any node that decodes the transaction (mempool nodes, block-processing validators, and RPC nodes alike), potentially affecting availability and, if triggered during block validation, causing divergent node crash behavior across the network. This matches CWE-400 and is directly analogous to the referenced MaterialX advisory's root cause (unbounded recursive import/decode depth).

### Likelihood Explanation
Likelihood is high: constructing the payload requires no special privileges — only assembling nested RLP byte strings, each adding a small, bounded number of bytes (a keyType byte + a short nested list) per recursion level. Thousands of nesting levels can be encoded in a modest-sized transaction payload (well under typical tx size/gas limits), and the transaction only needs to be broadcast or submitted via `SendRawTransaction`/p2p for a receiving node to decode it and crash — no signature validity or execution is required to trigger the crash, since decoding happens before signature/other checks.

### Recommendation
Introduce an explicit recursion/nesting-depth counter (or iterative decode with an explicit stack and hard limit, e.g. depth ≤ 1) in `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP`, and reject decoding immediately once the limit is exceeded — mirroring the existing (but too-late) `IsCompositeType` check. Since `RoleBased` is documented to disallow nested composite keys entirely, decode-time depth enforcement should reject any nested `AccountKeyTypeRoleBased`/`AccountKeyTypeWeightedMultiSig`-inside-`RoleBased` structure at the first recursive call rather than after full recursive decoding completes. Additionally consider adding a general RLP nesting-depth limit at the `rlp.Stream` level for custom `Decoder` implementations, since this pattern (composable `Decoder.DecodeRLP` calling back into generic decode of attacker-controlled inner types) could recur elsewhere in the codebase.

### Proof of Concept
Conceptual construction (exact byte-level PoC would require a local build/test environment, which was not available in this investigation):
1. Build an `AccountKeySerializer` for `AccountKeyTypeRoleBased` whose single "role" entry is itself the RLP encoding of another `AccountKeyTypeRoleBased` serializer, and repeat this nesting N times (e.g., N = 100,000).
2. Wrap the innermost encoded bytes as the `Key` field of a `TxInternalDataAccountUpdate` transaction, sign it (or leave it unsigned since decode precedes signature validation), and RLP-encode the full transaction.
3. Submit the raw transaction via `eth_sendRawTransaction` to a Kaia node, or inject it via p2p transaction broadcast.
4. Observe that the node process crashes with a Go runtime "stack overflow" fatal error while decoding the transaction, before any account-key validation (`CheckInstallable`) is reached.

Note: I was not able to execute or compile this PoC directly (no code execution/build environment available); the analysis is based on static review of the decode/validation code paths cited above. If precise crash confirmation is needed, a Devin session with build/test access would be required to actually run the recursive-decode PoC against the RLP and accountkey packages.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

}
