## Analysis

The GammaProtocol bug's core invariant is: *"contract collects `msg.value`, performs sub-calls that only consume part of it, and never returns the unspent remainder to the original payer."* The closest verified local analog in Hyperbridge is in `EvmHost`'s native-fee dispatch path, which forwards `msg.value` to a Uniswap-V2-style router's `swapETHForExactTokens` but never captures or forwards back any unspent ETH to the caller who funded the transaction.

### Title
Unrefunded ETH overpayment in `EvmHost.dispatch`/`fundRequest` becomes permanently stuck in the host contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` accept `msg.value` and swap it for the exact `feeToken` amount needed via `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. [1](#0-0) [2](#0-1) [3](#0-2) 

Unlike `IntentGatewayV2`, which explicitly captures the router's return value and refunds the exact unspent delta back to `msg.sender`: [4](#0-3) 

`EvmHost.dispatch`/`fundRequest` **discard the return value of `swapETHForExactTokens` entirely** — they never compute `msgValue - amountSpent` and never issue any refund to `_msgSender()`. Any refund of unspent ETH that occurs is whatever the underlying router implementation does internally, and that refund is sent to the router's *caller*, which is `EvmHost` itself (since `EvmHost` is the one invoking `swapETHForExactTokens`), not to the original account that funded the `dispatch`/`fundRequest` transaction. This is directly visible in this repo's own router wrapper implementations, where the refund path is `msg.sender.call{value: refund}("")` — and `msg.sender` in that context is `EvmHost`: [5](#0-4) [6](#0-5) 

### Finding Description
`EvmHost` is the canonical `IDispatcher`/`IHost` implementation used by every app in this repo (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `HyperbridgeLzEndpoint`, `IntentGatewayV2`'s cross-chain cancel/redeem flows, and any third-party `HyperApp`) whenever they want to pay Hyperbridge's relayer/protocol fee in native token instead of `feeToken`. [7](#0-6) [8](#0-7) [9](#0-8) 

In every one of these call sites, the entire `msg.value`/available native balance is forwarded to `IDispatcher(_host).dispatch{value: msg.value}(request)` (or `dispatch{value: msgValue}`), on the assumption that unused native token gets returned. But `EvmHost.dispatch`/`fundRequest` perform:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

with **no post-call handling of leftover ETH**. Because `swapETHForExactTokens` only needs to spend enough ETH to buy exactly `post.fee` worth of `feeToken`, any router implementation that correctly implements the standard interface will refund the delta — but the refund target is *the caller of the swap function*, i.e. `EvmHost`. `EvmHost` has no mechanism visible in its dispatch/fundRequest functions to forward that ETH onward to the original transaction sender, and no public "sweep my leftover ETH" function analogous to `IntentGatewayV2`'s explicit refund lines. The unspent ETH balance is absorbed into `EvmHost`'s own contract balance permanently.

This exactly reproduces the "ETH could get trapped in the protocol" bug class: the caller sends more native value than strictly required for the fee swap (which is trivial to do — any caller supplying a native-token buffer for gas-price/slippage safety, exactly as the `IntentGatewayV2` fee-swap flow itself does by forwarding `msgValue` that can be many times larger than needed, e.g., the fee-swap test sends `5 ether` for a swap that costs a fraction of that), and the excess becomes unrecoverable inside `EvmHost`. [10](#0-9) 

### Impact Explanation
This is a direct, protocol-level, unauthorized loss/lock of user funds reachable by any unprivileged caller of a public entrypoint (`dispatch`, `fundRequest`) — no relayer, prover, governance, or malicious peer involvement is required. It matches the bounty's "stealing or loss of funds" and "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" criteria: native ETH paid by ordinary users/apps for a fee swap silently accrues in `EvmHost` instead of returning to them, with no recovery path exposed by the reviewed `EvmHost` code.

### Likelihood Explanation
High. Overpaying `msg.value` beyond the exact fee-swap requirement is the normal/expected usage pattern (callers cannot predict the exact AMM output needed and typically send a buffer), as demonstrated by this repo's own test suite deliberately sending `5 ether` against a swap costing "much less." [11](#0-10) 
No attacker action is required — this triggers on ordinary, honest usage of `dispatch`/`fundRequest` with native payment.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the `amounts` array returned by `swapETHForExactTokens` (mirroring `IntentGatewayV2`'s pattern), compute `msg.value - amounts[0]`, and refund the difference to `_msgSender()` via a checked low-level call before returning. Alternatively, expose an owner/permissionless sweep function that returns any stray ETH balance to the appropriate recorded payer.

### Proof of Concept
1. A `HyperApp` (e.g., `HyperFungibleToken.send`) or an EOA calls `EvmHost.dispatch{value: 5 ether}(post)` where `post.fee` only requires ~0.01 ETH worth of `feeToken` via the configured Uniswap V2 router. [1](#0-0) 
2. `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` spends only the ETH needed to buy `post.fee` in `feeToken` and refunds the remainder (~4.99 ETH) to its caller, `EvmHost`.
3. `EvmHost.dispatch` never reads the swap's return value nor forwards any leftover ETH back to the original caller; the ~4.99 ETH remains in `EvmHost`'s balance.
4. No function in the reviewed `EvmHost.sol` dispatch/fundRequest logic allows the original caller (or anyone) to reclaim that stranded ETH.

*Note: whether `EvmHost` contains a `receive()`/`withdraw` function elsewhere in the contract that could theoretically be repurposed to recover this stray balance was not fully confirmed within the available tool budget — grep matched several occurrences of `.balance`/`receive`/`withdraw` substrings in `EvmHost.sol` that could not be read in full before the session ended. If such a function exists and is restricted to governance/admin rather than the original payer, the fund-lock conclusion still holds (funds are not returned to the rightful beneficiary); if a permissionless refund path does exist there, it would need to be checked against this specific overpayment scenario to fully invalidate this finding.*

    /// @notice placeOrder with fee swap refunds unused ETH after swapETHForExactTokens.
    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;
