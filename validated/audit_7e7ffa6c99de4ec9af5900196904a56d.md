### Title
PedPoP encryption key registration accepts identity/non-possessed points, making encrypted secret shares world-decryptable - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`EncryptionKeyMessage` carries a participant-supplied `enc_key` group element that is used as the ECDH receiver key for every `EncryptedMessage` (secret share) sent to that participant. `EncryptionKeyMessage::read` parses it with `C::read_G` (the `Ciphersuite` implementation, not `Curve::read_G`), which enforces canonical encoding but does **not** reject the identity point, and `Decryption::register` stores it without any proof of possession or identity check. A malicious DKG participant can therefore register `enc_key = identity`. Every sender then computes `ecdh(key, identity) = identity`, so the ChaCha20 cipher key is derived from a publicly known shared point — anyone observing the ciphertext (in Serai, DKG shares are published via public tributary/coordinator messages) can decrypt the secret shares addressed to that participant index.

### Finding Description
- `EncryptionKeyMessage::read` reads `enc_key` via `C::read_G` at `crypto/dkg/pedpop/src/encryption.rs:57-59`. `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) checks only canonical encoding; unlike `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) it does not reject identity.
- `Decryption::register` (`crypto/dkg/pedpop/src/encryption.rs:351-362`) inserts the attacker-supplied `enc_key` into `enc_keys` with no PoP and no identity validation. It is invoked from `SecretShareMachine::verify_r1` (`crypto/dkg/pedpop/src/lib.rs:315`) on attacker-controlled commitment messages.
- `encrypt` (`encryption.rs:135-168`) computes `ecdh(&key, to)` where `to = enc_keys[participant]` (via `Encryption::encrypt`, `encryption.rs:466`). With `to = identity`, the shared point is `identity`, whose encoding is a fixed public constant. `cipher` (`encryption.rs:101-133`) derives the ChaCha20 key solely from `context || shared_key` with a static IV, so the keystream is reproducible by any observer.
- The accompanying `pop` Schnorr signature proves possession of the *per-message* key, not the registration key, so it provides no defense (`encryption.rs:299-324`; the code comments explicitly note per-message keys "have no root of trust"). A rogue participant can also make the round-1 PoK verify with `commitments[0] = identity`, since a Schnorr PoK for discrete log 0 is trivially producible.

### Impact Explanation
Every secret share `f_j(i)` encrypted to the malicious participant index `i` becomes decryptable by any passive observer of the wire/transcript data, not just the intended recipient. Serai permits a single validator to control multiple `Participant` indices (`processor/src/key_gen.rs:439-449` maps `i + m` indices to one validator). If an attacker registers identity encryption keys for `t` indices under their control, all `t` aggregated secret shares become publicly computable, and Lagrange interpolation of those `t` shares recovers the **full threshold group private key** for anyone watching the DKG — complete key compromise by an unprivileged, non-participating observer. Even below `t` indices, participant secret shares that must remain confidential are broadcast in the clear.

### Likelihood Explanation
The attack requires only submitting a well-formed `EncryptionKeyMessage`/`Commitments` in round 1 of PedPoP with `enc_key` set to the identity encoding — fully within normal, authenticated protocol flow, no collusion, no malformed encodings, and no deviation detectable by `verify_r1` since the PoK on `commitments[0]` can be satisfied independently of `enc_key`. Deterministic and trivially executable by any single DKG participant.

### Recommendation
- In `EncryptionKeyMessage::read` or `Decryption::register`, reject identity `enc_key` (use `Curve::read_G` semantics or an explicit `is_identity` check).
- Bind a proof of possession of `enc_key` into the round-1 `Commitments` signature (e.g., include `enc_key` in the PoK transcript or require a second Schnorr PoK over `enc_key`), so participants cannot register keys they do not control or degenerate keys.
- Optionally bind the recipient participant index into `pop_challenge` to harden the per-message proof against cross-participant replay.

### Proof of Concept
```
1. Attacker (Participant i, or validator controlling indices i..i+k) runs KeyGenMachine::generate_coefficients,
   then crafts EncryptionKeyMessage { msg: Commitments { commitments: [identity, ...], sig: PoK(0) },
   enc_key: identity } — serializes/publishes it normally.
2. Every honest sender j calls Encryption::encrypt(rng, j->i share):
   ecdh(per_msg_key, identity) = identity
   cipher = ChaCha20( key = H(context || identity.to_bytes()), iv = "DKG IV v0.2\0" )
   ciphertext = share_bytes XOR keystream
3. Observer recomputes the identical keystream from the public context and the known
   identity encoding, XORs the ciphertext, and recovers SecretShare<C::F> for index i.
4. If the attacker controls >= t indices (multiple key shares per validator), the observer
   interpolates the t leaked shares and recovers the group private key.
```
