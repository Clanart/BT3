### Title
Malformed MultiEdit `edits` entries crash rule evaluation and fail open, bypassing block rules - (File: plugins/hookify/core/rule_engine.py)

### Summary
`RuleEngine._extract_field` builds the `new_text`/`content` field for `MultiEdit` by joining `e.get('new_string', '')` over all entries in `tool_input['edits']` without validating that each entry is a dict with a string `new_string` value. If any edit entry is missing the required type (e.g. `new_string` is an int, list, or the entry itself is not a dict), the generator raises a `TypeError`/`AttributeError` during `' '.join(...)`, which propagates uncaught out of `_check_condition` and `_rule_matches` up to `evaluate_rules`.

### Finding Description
`_extract_field` for `MultiEdit` does: [1](#0-0) 
`e.get('new_string', '')` only supplies the default `''` when the key is absent; if `new_string` is present but not a string (or `e` is not a dict at all), calling `.get` or the subsequent `str.join` raises an exception. This exception is not caught anywhere inside `RuleEngine` — `_check_condition` calls `_extract_field` directly with no try/except, and `_rule_matches`/`evaluate_rules` likewise have no local exception handling.

The only exception handling in the call chain lives in the hook entrypoints, which wrap the entire rule evaluation in a blanket `try/except Exception` and always `sys.exit(0)`, emitting only a `systemMessage` (no `hookSpecificOutput.permissionDecision: deny`): [2](#0-1) 
Because the PreToolUse hook always exits 0 on any error and only returns a plain `systemMessage`, a crash inside rule evaluation is functionally equivalent to "no rule matched" — any configured block rule targeting `new_text`/`content` for `MultiEdit` is silently skipped for that call, breaking the "deny means deny" invariant.

### Impact Explanation
Any hookify rule configured to block dangerous file content via `new_text`/`content` matching on `MultiEdit` operations can be bypassed by supplying (or having the assistant supply, whether via prompt injection from repo content or a buggy/adversarial MCP/tool response) an `edits` array containing a non-string `new_string` value. This is a trust-boundary bypass of the plugin's own enforcement mechanism, since the intended deny action degrades into an allow with only a benign error message shown to the user.

### Likelihood Explanation
The bug is deterministic and requires no special privilege — only that a `MultiEdit` tool call reaches the hook with a malformed `edits` list. It is trivially reproducible via direct unit invocation of `RuleEngine._check_condition`/`evaluate_rules`, and every hook invocation using the shared `main()` fail-open pattern in `pretooluse.py`/`posttooluse.py` is equally affected.

### Recommendation
Harden `_extract_field` for `MultiEdit` to defensively coerce/validate each edit entry, e.g.:
```python
edits = tool_input.get('edits', [])
parts = []
for e in edits:
    if isinstance(e, dict):
        v = e.get('new_string', '')
        parts.append(v if isinstance(v, str) else str(v))
return ' '.join(parts)
```
Additionally, `evaluate_rules`/`_rule_matches` should catch exceptions per-rule and either fail closed (deny) or explicitly skip only the offending rule while still evaluating others, rather than relying on a top-level fail-open handler in the hook scripts.

### Proof of Concept
Unit test:
```python
from hookify.core.config_loader import Condition, Rule
from hookify.core.rule_engine import RuleEngine

engine = RuleEngine()
condition = Condition(field="content", operator="contains", pattern="malicious")
rule = Rule(name="block-malicious", enabled=True, event="file", action="block",
            conditions=[condition], message="blocked")

tool_input = {"file_path": "foo.py", "edits": [{"new_string": 12345}]}
input_data = {"tool_name": "MultiEdit", "tool_input": tool_input}

# Expect: no unhandled exception, and rule evaluation either raises a
# controlled error or safely coerces the value instead of crashing the join.
result = engine.evaluate_rules([rule], input_data)
```
Currently this raises `TypeError: sequence item 0: expected str instance, int found` from `_extract_field`, uncaught by `RuleEngine`, and only masked by the hook script's outer `try/except` returning an empty/allow decision — demonstrating the fail-open bypass.
