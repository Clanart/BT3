### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes an eager multi-megabyte allocation from a 9-byte input — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` deserializes the threshold parameters `t`, `n`, `i` directly from the input byte stream and then eagerly allocates `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector before reading a single byte of backing data. A 9-byte crafted buffer can therefore force an allocation of up to 65,535 scalars (~2 MB for 32-byte fields, ~4 MB for 64-byte Ed448-style fields), and additionally drives a `HashMap` insertion loop over `1 ..= n` point reads.

### Finding Description
The relevant code is in `ThresholdKeys::read`:

- `t`, `n`, and `i` are read as three little-endian `u16`s with no upper bound beyond `Participant::new` / `ThresholdParams::new` validation, which happens **after** the allocation.
- For interpolation tag `0` (`Constant`), the code executes `Vec::with_capacity(usize::from(n))` (`crypto/dkg/src/lib.rs`, around lines 604–613). `with_capacity` allocates immediately; `n` can be `0xFFFF`, so ~2–4 MB is committed per call before `read_F` ever runs.
- Independently, `for l in (1 ..= n)` inserts `n` entries into a `HashMap` of verification shares, each requiring a group element read (`crypto/dkg/src/lib.rs`, lines 620–623), so even valid streams force work proportional to attacker-chosen `n`.

This is the Serai analog of CVE-2023-31607: a crafted input causing disproportionate memory allocation in a deserialization path (`__libc_malloc` DoS there; length-controlled `Vec::with_capacity` here). `ThresholdKeys::read` is on the allow-listed untrusted-bytes surface, and callers such as coordinator tributary `Transaction::read` similarly deserialize signed transactions over the wire, so this pattern is reachable wherever `ThresholdKeys` bytes or any `n`-prefixed structure crosses a trust boundary.

### Impact Explanation
A malicious participant, or any party able to feed bytes to `ThresholdKeys::read`, can force repeated ~2–4 MB allocations per ~9-byte message — an amplification factor of roughly 10⁵. Repeated calls exhaust allocator/memory resources and crash or OOM the node, denying service. Severity is Medium: availability impact only, bounded per-call but trivially repeatable and requiring no privileges, keys, or valid signatures.

### Likelihood Explanation
Any peer in a DKG/signing session or any code path that reads `ThresholdKeys` from storage/network bytes before authentication reaches this code. The trigger is deterministic: set interpolation byte to `0` and `n = 0xFFFF`, then truncate the stream — the allocation still occurs before the first failed `read_F`.

### Recommendation
Validate `t <= n <= <protocol maximum>` and `i <= n` via `ThresholdParams::new` **before** allocating, and replace `Vec::with_capacity(n)` with `Vec::new()` (push-driven growth bounded by actual bytes present). Apply the same pattern to the `1 ..= n` verification-share loop — either bound `n` first or chunk reads so allocation scales with bytes actually supplied, matching the defensive chunked-read style already used in `networks/ethereum/src/machine.rs` for `Call::read`.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;
use frost::curve::Ristretto; // any Curve impl

fn poc() {
    let id = Ristretto::ID;
    let mut buf = vec![];
    buf.extend((id.len() as u32).to_le_bytes());
    buf.extend(id);                         // curve ID matches
    buf.extend(1u16.to_le_bytes());         // t = 1
    buf.extend(u16::MAX.to_le_bytes());     // n = 65535  <- attacker controlled
    buf.extend(1u16.to_le_bytes());         // i = 1
    buf.push(0);                            // Interpolation::Constant
    // No further bytes: Vec::with_capacity(65535) allocates ~2 MB,
    // then read_F fails. Repeat to exhaust memory.
    let _ = ThresholdKeys::<Ristretto>::read::<&[u8]>(&mut buf.as_ref());
}
```
Observed behavior: an eager `n`-element allocation occurs on every call regardless of the input actually containing `n` scalars; expected behavior is allocation bounded by validated parameters or by bytes present.
