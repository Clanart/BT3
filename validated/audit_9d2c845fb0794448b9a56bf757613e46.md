**Rationale:**

The claim conflates two independent things: (1) the API's request *encoding* format (JSON vs. raw BCS) and (2) the Move-level derivation of code-object ownership, which are unrelated.

- Both `SubmitTransactionPost::Json` and `SubmitTransactionPost::Bcs` variants are ultimately converted into the exact same `SignedTransaction` type before being forwarded to mempool/VM — `data.verify()` only validates request-shape invariants (e.g., hex encoding, field presence), not transaction semantics, and `SubmitTransactionPost::Bcs` intentionally has a no-op `verify()` since the wire format itself (a `SignedTransaction`) is self-describing and its signature is checked by the VM, not the API layer. [1](#0-0) 
- The signature over the raw transaction is verified identically regardless of which content-type was used to submit it; the "ownership" of the resulting code object is never derived from anything in the API layer at all. [2](#0-1) 
- Object-code ownership in `object_code_deployment::publish` is computed purely inside Move using `signer::address_of(publisher)`, where `publisher` is the cryptographically authenticated signer of the transaction (derived from the transaction's real sender/signature, checked by the VM's prologue, independent of API request format). The object address seed is `object_seed(publisher_address)` combined with the account's actual on-chain sequence number, and the `ManagingRefs`/`ExtendRef` are moved to the newly created object's own signer. [3](#0-2) 
- The `upgrade` function additionally re-checks `ENOT_CODE_OBJECT_OWNER` against the actual `object::owner` of the `code_object`, independent of anything the API forwarded. [4](#0-3) 
- E2E tests confirm this ownership check is enforced against the authenticated signer, not any API-supplied metadata: attempting to upgrade from a different account fails with `ENOT_CODE_OBJECT_OWNER`. [5](#0-4) 

There is no "ownership/upgrade metadata" carried by the API request at all — the API is a thin transport for an already-signed `SignedTransaction`/`RawTransaction`; whether that transaction was encoded as JSON-then-converted-to-BCS-and-signed, or submitted directly as a raw signed BCS blob, produces an identical `SignedTransaction` object that the VM executes the same way. Skipping `SubmitTransactionRequest`'s JSON-specific field validation does not skip signature verification, VM prologue account/sequence-number checks, or the Move-level owner derivation, none of which live in `api/src/transactions.rs` or depend on the request's wire format. The premise that the API "re-derives" or "forwards" ownership/upgrade metadata separately from the signed transaction itself is incorrect — no such derivation exists at the API layer to skip.
