### Title
Reward-forfeiture multiplier in `vlMGPBaseRewarder` is assessed only at claim time on the account's *current* lock state, letting a user avoid forfeiting rewards that accrued while their position was actually in a decayed/expired-unlock state - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder` accrues rewards for a vlMGP holder continuously via the standard `rewardPerToken`/`_earned` bookkeeping, but only applies the "forfeit" penalty (meant to claw back rewards from stale, past-cooldown, un-withdrawn vlMGP positions) once, at the moment `getReward`/`getRewards` is actually called, using the account's lock state **at that exact block**. Because the whole unclaimed, historically-accrued reward balance is multiplied by this single, point-in-time factor, a user can manipulate their lock state immediately before claiming to erase most or all of the forfeit that should have applied to the period during which their position was actually decayed, exactly mirroring the Union H-6 root cause: a "current-state multiplier" applied retroactively to a value that accrued over time.

### Finding Description
`_updateFor` snapshots `userRewards[token][account] = earned(...)` on every lock/unlock/claim action, based purely on `balanceOf(_account)` (the account's staked vlMGP amount in `MasterMagpie`), with no forfeiture applied at that point: [1](#0-0) 

The forfeiture is computed only later, inside `_sendReward`, which is invoked exclusively from `getReward`/`getRewards` (user-initiated claim functions): [2](#0-1) 

The forfeit percentage comes from `VLMGP.getRewardablePercentWAD`, which is a pure function of the account's **current** lock/cooldown state: currently fully-locked amounts always count at 100% (no time-based penalty at all), amounts still inside an active cooldown window also count at ~100%, and only amounts that are past their cooldown `endTime` and have not yet been withdrawn via `unlock()` decay toward 0% the longer they are left unclaimed: [3](#0-2) [4](#0-3) 

Because `_calExpireForfeit` is applied to `userRewards[_rewardToken][_account]` — the entire accumulated, not-yet-forfeited reward balance — in a single shot at claim time, the multiplier does not reflect the actual state the account was in while each portion of that reward was accruing. A holder can therefore let a large amount of vlMGP sit fully-expired/unclaimed (accumulating decay that is supposed to eventually zero out their claimable share, per the design intent visible in `getRewardablePercentWAD`), and then, in the same transaction sequence just before calling `getReward()`/`getRewards()`, re-lock a comparatively small amount of MGP (`lock`/`lockFor`) so that `fullyInLock` again dominates the `userTotalVlmgp` denominator, pushing `getRewardablePercentWAD` back toward 100% and defeating the intended forfeit on the bulk of the pending reward. This is structurally identical to the Union report's `_getRewardsMultiplier`, which is likewise computed from the account's current member/lock/frozen state and multiplies the entire elapsed reward differential, allowing risk-free multiplier maximization right before the value-realizing call.

### Impact Explanation
Forfeited rewards are not burned; they are re-queued into the pool for other vlMGP stakers via `_queueNewRewardsWithoutTransfer`: [5](#0-4) 

By gaming the point-in-time multiplier, an attacker extracts reward tokens that the protocol's own decay mechanism intended to redirect to honest, actively-locked stakers. This is a direct transfer of unclaimed yield away from other users of the system — the same class of harm ("theft ... of unclaimed yield," diluting/short-changing holders who don't game the timing) identified in the Union report.

### Likelihood Explanation
No privileged role is required — any vlMGP holder with an expired, unclaimed cooldown slot can perform the sequence (`lock`/`lockFor` a small top-up, then `getReward`/`getRewards`) using only the public, unprivileged `VLMGP` and `MasterMagpie`/`vlMGPBaseRewarder` interfaces. The precondition (holding an expired but not-yet-`unlock()`-ed cooldown slot with accrued pending rewards) arises naturally from normal usage and is fully within the attacker's control to engineer and time.

### Recommendation
Do not compute the forfeit multiplier from the account's state only at claim time against the entire historical unclaimed balance. Instead, checkpoint/realize the forfeit incrementally whenever the account's lock/cooldown state changes (i.e., call `_updateFor` combined with a forfeit-settlement step inside `lock`, `startUnlock`, `unlock`, `cancelUnlock`, and `forceUnLock` in `VLMGP.sol`, before the state that determines `getRewardablePercentWAD` is mutated), so that each portion of reward is forfeited according to the state that was actually in effect while it accrued, rather than being subject to a single value picked at the moment of `getReward()`.

### Proof of Concept
1. Attacker locks vlMGP and lets a `startUnlock` cooldown slot fully expire without calling `unlock()`, while `userRewards` continues to accrue via `_updateFor` at full (unforfeited) value based on `balanceOf` per [1](#0-0) .
2. Time passes well beyond `endTime`, so `getRewardablePercentWAD` for that slot has decayed toward a low percentage per the time-weighted formula in [6](#0-5) , meaning a claim now would forfeit most of the pending reward.
3. Immediately before claiming, the attacker calls `lock`/`lockFor` with a modest amount of MGP, increasing `fullyInLock` so that it again dominates `userTotalVlmgp` in `getRewardablePercentWAD`'s denominator, pushing the computed percent back near 100%.
4. The attacker then calls `getReward`/`getRewards` (via `MasterMagpie.multiclaimFor`/`multiclaimSpec`), triggering `_sendReward` → `_calExpireForfeit` with the now-inflated `rewardablePercentWAD`, per [2](#0-1) , resulting in little-to-no forfeiture despite the bulk of the reward having accrued while the position was in a decayed, expired state.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
