### Title
Payout attribution can be hijacked because `SinglePlusAnyoneCanPay` never commits the OP_RETURN operator-pubkey output or the funding inputs - (File: `core/src/operator.rs`, `core/src/builder/transaction/operator_reimburse.rs`, `core/src/verifier.rs`)

### Summary
`Operator::withdraw` verifies the user's signature with `TapSighashType::SinglePlusAnyoneCanPay`, which under BIP341 only commits input 0 (the withdrawal UTXO) and output 0 (the user payout output). It commits nothing about the other inputs added later by `fund_raw_transaction`, the anchor output, or the OP_RETURN output that encodes `operator_xonly_pk`. Any party who observes the signed input/output tuple (from a broadcast/mempool tx or the RPC request itself) can build and race a different payout transaction with a different funder and, critically, an arbitrary OP_RETURN payload, and `Verifier::update_finalized_payouts` will attribute the payout to whatever OP_RETURN happens to confirm.

### Finding Description
The claimed binding is: `payout_op_xonly_pk` (stored in `withdrawals.payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk`) `==` the operator whose funds actually paid for/fronted the confirmed payout transaction.

Tracing the code shows this binding never actually holds:

1. `Operator::withdraw` (`core/src/operator.rs:620-637`) builds `payout_txhandler` via `create_payout_txhandler`, computes `sighash = payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` and verifies it with `SECP.verify_schnorr`. `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:174-187`) enforces `sighash_type == SinglePlusAnyoneCanPay`.
2. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds exactly 3 outputs: `[0] user payout`, `[1] anchor`, `[2] OP_RETURN(operator_xonly_pk)`. Only input 0 (the user's UTXO) is present when the signature is produced/verified; `fund_raw_transaction` (`core/src/operator.rs:652-674`) adds further wallet inputs afterward, unsigned by the user.
3. Per BIP341, `SIGHASH_SINGLE | ANYONECANPAY` commits: (a) the single signed input's prevout/amount/scriptPubKey, and (b) the single output at the same index as that input (output 0, the user payout). It does **not** commit any other input, the anchor output, or - crucially - the OP_RETURN output that carries `operator_xonly_pk`. Nothing else in `withdraw()` re-checks or re-signs the OP_RETURN content against the funding wallet.
4. On the verifier side, `update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) determines `operator_xonly_pk` purely by reading whatever OP_RETURN happens to be present in the confirmed on-chain payout transaction (`get_first_op_return_output` / `parse_op_return_data`, lines 2312-2321) and stores it via `update_payout_txs_and_payer_operator_xonly_pk`. There is no check that the inputs of that confirmed transaction were actually funded by the operator named in the OP_RETURN.
5. Later, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1887-1890`) and `Operator::send_asserts` (`core/src/operator.rs:1284-1295`) only compare `payout_op_xonly_pk` (read from the DB, i.e., from the OP_RETURN of whichever tx confirmed) against `kickoff_data.operator_xonly_pk`. Neither checks who funded the transaction's non-committed inputs.

Because the OP_RETURN payload and the extra funding inputs are outside the signed message, any unprivileged observer of the `(in_signature, in_outpoint, out_script_pubkey, out_amount)` tuple — obtainable from a broadcast/mempool tx or from the RPC call itself — can construct their own transaction spending the same input 0 to the same output 0, but with:
- different additional funding inputs (their own UTXOs paying the fee),
- a different fee/change,
- an arbitrary OP_RETURN naming any operator's `xonly_pk` (public information from operator registration),

and broadcast it with a higher fee to win the race. `SECP.verify_schnorr` in the honest operator's own `withdraw()` call would still have validated the same signature under the same sighash, since the sighash calculation is identical regardless of which transaction eventually gets these unsigned bytes filled in.

Existing guards do not catch this: `is_profitable` only checks value/fee bounds at construction time, not after confirmation; `is_kickoff_malicious` and `send_asserts`'s equality check trust the on-chain OP_RETURN blindly; there is no signature or commitment tying `operator_xonly_pk` or the funding inputs to the user's authorization.

### Impact Explanation
Whichever payout transaction confirms first wins attribution in the DB (`withdrawals.payout_payer_operator_xonly_pk`), regardless of who actually paid the withdrawal fee/funded the transaction:
- The operator named in the winning OP_RETURN can later kick off and be reimbursed via `Reimburse`/`send_asserts` even though it never funded that specific payout — "an operator reimbursed for a payout it never funded" (Critical).
- The honest operator that constructed and broadcast the legitimate, correctly-funded payout loses the race (their transaction double-spends the now-already-spent withdrawal UTXO and fails), and can never be reimbursed for that withdrawal since the DB attribution now points elsewhere — "an honest operator permanently unable to be reimbursed" (Critical).
This is repeatable per withdrawal/deposit and is not limited to a single operator pair; it applies to every `withdraw()` call whose signed tuple becomes observable before its transaction confirms (i.e., essentially every withdrawal, since payout transactions must be broadcast to confirm).

### Likelihood Explanation
No special privilege is required: the attacker only needs to observe a broadcast/mempool payout transaction (or the withdrawal parameters submitted to any operator's public gRPC endpoint) and have Bitcoin funds to build a competing, higher-fee-rate transaction using the same signed input/output pair. This is a standard transaction-relay race requiring only fee-bumping capability, well within reach of an unprivileged BTC holder. The attack is deterministic given the described BIP341 sighash semantics and requires no cryptographic breaks.

### Recommendation
Bind the OP_RETURN operator attribution and the funding inputs to the user's authorization, e.g.:
- Require the withdrawal signature to cover the OP_RETURN output (do not use `SIGHASH_SINGLE`; use `SIGHASH_ALL` bound to a fully-specified transaction template, or have the user sign a message that separately commits to the intended operator's xonly pubkey and pass that commitment through the protocol).
- Alternatively/additionally, verify at attribution time (`update_finalized_payouts`/`is_kickoff_malicious`) that the operator claimed in the OP_RETURN can be cryptographically tied to the actual spending transaction (e.g., by requiring the operator's own signature over the full funded transaction, or by having the aggregator/verifier record and race-check the exact payout txid the operator submitted before it confirms, rejecting any other transaction spending the same withdrawal outpoint).

### Proof of Concept
`cargo test` (non-mainnet regtest, using existing e2e harness under `core/src/test/deposit_and_withdraw_e2e.rs`/`common/clementine_utils.rs` patterns, but for reproduction the actual test should be added outside `core/src/test` scope per rules — the plan below only sketches the logic, not the actual mandated file):
1. Perform a deposit and obtain a valid withdrawal (`withdrawal_utxo`, `sig` with `SinglePlusAnyoneCanPay`) as in existing test helpers.
2. Call operator A's `withdraw()` to build/sign payout tx A (funded by A's wallet, OP_RETURN = A's xonly_pk) but do not broadcast it yet (or intercept before confirmation).
3. Independently build payout tx B using the same `input_utxo`, `output_txout`, and `user_sig`, but funded with a different (attacker/operator B) wallet, and with OP_RETURN = operator B's xonly_pk, via `create_payout_txhandler`.
4. Assert both `SECP.verify_schnorr` calls (as done in `Operator::withdraw`) succeed for the identical `sighash` on both tx A and tx B, proving the signature does not distinguish them.
5. Broadcast tx B first and mine it; then attempt to broadcast tx A and confirm it fails as a double-spend.
6. Run the verifier's block sync to trigger `update_finalized_payouts`, then assert `db.get_payout_info_from_move_txid(...).0 == Some(operator_B_xonly_pk)` even though operator A funded/authored the original request — demonstrating the funder/attribution mismatch and that `send_asserts`'s `payout_op_xonly_pk != kickoff_data.operator_xonly_pk` check does not detect it for operator B, while operator A can never satisfy the check for that deposit.
