### Title
Missing minting-coin balance check before `uint64()` fee cast crashes mempool validation with an uncaught exception - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle` computes `fees = uint64(removal_amount - addition_amount)` without first checking that `removal_amount >= addition_amount`. If a submitted spend bundle creates coins whose total value exceeds the total value of the coins it spends, this subtraction is negative and the `uint64()` constructor raises an uncaught `ValueError`, instead of returning a clean `Err` result the way the block-validation path does.

### Finding Description
In `chia/full_node/mempool_manager.py`, `validate_spend_bundle` accumulates `addition_amount` from each spend's `create_coin` conditions and `removal_amount` from the spent coin records, then computes: [1](#0-0) 

There is no `if removal_amount < addition_amount: return Err.MINTING_COIN` guard before this line, unlike the equivalent and properly-guarded logic in `chia/consensus/block_body_validation.py`, which explicitly checks the invariant before computing fees: [2](#0-1) 

The CLVM condition engine (`chia_rs`) only validates conditions per-coin-spend (i.e., that a single coin's puzzle produces valid `CREATE_COIN` conditions); it does not enforce that the sum of all inputs in a spend bundle is greater than or equal to the sum of all outputs — that invariant is a bundle-level/block-level consensus rule, not a CLVM-execution-level one. This means a spend bundle that "mints" value (creates output coins whose total amount exceeds the total amount of the coins being spent) can pass CLVM execution and reach the `uint64()` cast in the mempool with a negative underlying value.

`uint64()` from `chia_rs.sized_ints` raises `ValueError` (message "does not fit into uint64") rather than wrapping or clamping when given a negative value, as confirmed by existing tests exercising the analogous `compute_block_fee`/`compute_fee_test` helpers: [3](#0-2) [4](#0-3) 

This is the direct analog of the reported Zaros bug: an unsigned-subtraction "underflow" (in Solidity terms) / negative-to-unsigned cast failure (in Python terms) occurring in a per-transaction "credit/fee delta" calculation that is reachable by any unprivileged submitter, without any preceding invariant check to prevent it.

### Impact Explanation
`validate_spend_bundle` is invoked from `MempoolManager.add_spend_bundle`, which is the core entry point exercised whenever a full node processes an incoming `transaction`/`respond_transaction`/RPC-submitted spend bundle: [5](#0-4) 
Any single unprivileged caller (wallet, spend-bundle submitter, or RPC client) can build a spend bundle whose declared `CREATE_COIN` outputs exceed the value of its inputs. Because the value-conservation check is missing here (compared to `block_body_validation.py`'s guarded version), the resulting `ValueError` is raised during mempool admission rather than being converted into a normal `Err.MINTING_COIN` rejection. If this exception is not caught by every caller in the transaction-processing chain, it can interrupt the transaction-admission pipeline for that request/connection, matching the "spend-triggered transaction-processing halt" impact class. I was not able to fully trace every calling context (e.g., `full_node.py`'s `add_transaction`, RPC handlers) within the available iterations to confirm whether a blanket `try/except` wraps every call site, so the exact blast radius (isolated request failure vs. broader service disruption) is not fully verified from the index alone.

### Likelihood Explanation
Likelihood is high for triggering the exception itself: constructing a spend bundle with `sum(created coin amounts) > sum(spent coin amounts)` requires no special privileges, no valid signature bypass, and no on-chain confirmation — it only needs to pass CLVM execution of the individual puzzles (e.g., a puzzle that unconditionally emits `CREATE_COIN` with an attacker-chosen large amount), which is trivial with a standard puzzle under attacker's own key. The actual DoS severity, however, hinges on unverified exception-handling behavior further up the call stack, which is why this is reported with an explicit caveat rather than certainty of a "protocol halt."

### Recommendation
Add an explicit minting/balance check in `chia/full_node/mempool_manager.py`'s `validate_spend_bundle`, mirroring `block_body_validation.py`'s pattern, before computing fees:
```python
if removal_amount < addition_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This converts the failure mode from an uncaught `ValueError` into the same clean `Err.MINTING_COIN` rejection already used by consensus-level block validation, keeping the two validation paths consistent and avoiding reliance on outer exception handlers to keep the node available.

### Proof of Concept
Conceptual reproduction (matching the existing test style in `chia/_tests/core/mempool/test_mempool_manager.py`):
1. Construct a standard-puzzle coin spend for a coin of amount `X`.
2. Have its solution instruct the puzzle to `CREATE_COIN` a new coin of amount `Y > X` (trivial for a puzzle spent by its own owner, e.g., a standard coin's `AGG_SIG_ME`-guarded solution with an inflated `CREATE_COIN` amount argument, which the owner is free to construct since it only affects their own spend, not signature validity).
3. Submit this single spend bundle (no other coins in the bundle) to `MempoolManager.add_spend_bundle`.
4. `addition_amount` (`Y`) exceeds `removal_amount` (`X`); at `fees = uint64(removal_amount - addition_amount)` a `ValueError: ... does not fit into uint64` is raised, unhandled by `Err`-based control flow, instead of the pipeline cleanly returning `Err.MINTING_COIN` as block validation does.

Note: I could not execute this PoC directly (no filesystem/test-runner access in this mode); the trace above is derived directly from reading `mempool_manager.py` lines 784–814 and comparing it against the guarded equivalent in `block_body_validation.py` lines 533–546, plus the `uint64()` negative-value behavior confirmed by existing repository tests. Confirming the exact downstream effect (whether the exception is caught by a broader handler in `full_node.py` or an RPC layer, thereby limiting impact to a single rejected request rather than a broader service interruption) would require deeper tracing than was possible in the remaining iterations.

def compute_fee_test(additions: Sequence[Coin], removals: Sequence[Coin]) -> uint64:
    removal_amount = 0
    addition_amount = 0
    for coin in removals:
        removal_amount += coin.amount
    for coin in additions:
        addition_amount += coin.amount

    ret = removal_amount - addition_amount
    # in order to allow creating blocks that mint coins, clamp the fee
    # to 0, if it ends up being negative
    ret = max(ret, 0)
    return uint64(ret)
