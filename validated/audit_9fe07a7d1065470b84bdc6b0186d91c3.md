### Title
Unchecked arithmetic overflow in fee/change calculation allows remote crash or silently wrong fee via attacker-influenced inputs - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/blackvul/serai--010/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` computes `needed_fee = fee_per_vbyte * vbytes`, `payment_sat = payments.iter().map(|p| p.1).sum::<u64>()`, and `input_sat < (payment_sat + needed_fee)` using plain `*`/`+`/`sum` arithmetic on `u64` [1](#0-0) . `fee_per_vbyte` is an externally-influenced value (in production it is derived from `median_fee` over transactions in a chain block [2](#0-1) ), and `payments`/`inputs` are attacker-influenced lists of satoshi amounts. An overflow either panics (denial of service, mirroring the CVE's crash class) or, in a release build without `overflow-checks`, wraps to a small value that defeats every subsequent sanity check.

### Finding Description
The analog to CVE-2017-13783 (crafted input → memory corruption / application crash) is a reachable arithmetic fault on untrusted numeric input rather than a memory-safety bug:

- `let mut needed_fee = fee_per_vbyte * vbytes;` — unbounded multiplication [3](#0-2) .
- `if input_sat < (payment_sat + needed_fee)` — unchecked addition [4](#0-3) .
- `fee()` uses `sum(inputs) - sum(outputs)` with a plain subtraction [5](#0-4) .

If `fee_per_vbyte * vbytes` wraps to a value below the real required fee but still above `(DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000`, the `TooLowFee` and `NotEnoughFunds` checks pass [6](#0-5) . When a change address is present, `input_sat.checked_sub(payment_sat + fee_with_change)` then folds the discrepancy into the change output, so the constructed transaction commits to paying only the wrapped (tiny) fee. Alternatively, with a `payment_sat + needed_fee` wrap, a transaction that cannot cover its outputs+fee is accepted. With `overflow-checks` enabled, every overflow is a hard panic — a remotely triggerable crash of the signing path.

The input vector is real: `median_fee` is computed from fees of transactions inside a fetched block [2](#0-1) , so an unprivileged party who mines or gets a high-fee transaction into a sampled block skews `fee_per_vbyte`; a caller-controlled payments list controls `payment_sat`. No trusted key material or validator privilege is needed — only the ability to get a transaction into a block used for fee estimation, and to induce payments.

### Impact Explanation
Two failure modes:

1. Denial of service: panic inside `SignableTransaction::new`/`fee()` aborts transaction construction for the multisig; the production wrapper escalates several `TransactionError`s into `panic!`s as well [7](#0-6) .
2. Incorrect financial commitment: a wrapped `needed_fee` produces a `SignableTransaction` whose real fee is far below the intended relay rate — the signed transaction will not confirm (or, for `payment_sat + needed_fee` wrap, an unpayable plan is approved for signing). The FROST machines then sign the malformed transaction; every honest cosigner contributes to signing an unintended transaction [8](#0-7) .

### Likelihood Explanation
`fee_per_vbyte` is median-of-block, so a single attacker-controlled transaction only moves the median if the attacker controls roughly half the sampled transactions or the block is sparse — moderate difficulty, but the multiply overflow only needs `fee_per_vbyte ≈ u64::MAX / vbytes` (~4×10^15 sat/vbyte, requiring absurd fees), making the multiplication path hard. The addition paths (`payment_sat + needed_fee`, `sum::<u64>` over payments) need payment sums near 2^64 sats — unreachable under Bitcoin's 21M BTC cap. The `fee()` subtraction is guarded by construction. Realistically this is a defense-in-depth panic/DoS reachable mainly when `fee_per_vbyte` is itself attacker-set or corrupted rather than median-derived — Medium at best, and arguably only a crash-class analog when overflow checks are enabled.

### Recommendation
Use `checked_mul`/`checked_add`/`checked_sub`/`checked_sum` throughout `SignableTransaction::new`, `fee()`, and the change calculation, mapping any `None` to a new `TransactionError::ArithmeticOverflow` variant. Also bound `fee_per_vbyte` and `payment_sat` against `MAX_MONEY` (21M BTC) before arithmetic so that even `checked_*` failures become clean, attributable errors instead of crashes reachable via peer/plan-supplied values.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs — debug build (overflow-checks on)
// Given a valid ReceivedOutput `output` worth e.g. 1 BTC:
SignableTransaction::new(
  vec![output],
  &[(script, 100_000_000 / 2)],
  Some(change_script),
  None,
  u64::MAX / 200,        // attacker-influenced fee_per_vbyte (e.g. via corrupted median fee)
);
// fee_per_vbyte * vbytes (~200-400) overflows u64 -> panic in debug,
// wraps to a tiny needed_fee in release -> change output absorbs the error,
// resulting TX pays a near-zero fee and never confirms.
```

Caveat: I could not fully confirm how `median_fee` bounds `fee_per_vbyte` upstream (processor code is out of scope); if the RPC-derived fee is clamped elsewhere, the externally-reachable overflow shrinks to the crash-under-overflow-checks configuration only.
