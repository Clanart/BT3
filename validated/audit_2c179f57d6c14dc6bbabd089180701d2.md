## Title
Incomplete conflict-marker validation lets malformed Copilot hunk resolutions be silently written and staged - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`parseCopilotConflictResolution()` is the only safety gate that stops a hunk resolution which still contains leftover git conflict markers from being written to the user's working tree. The check requires **both** a `<<<<<<<` marker line and a `=======` separator line to be present in the same `resolvedContent` string before it rejects the hunk, and it never checks for a stray `>>>>>>>` marker at all. A resolution containing only one of these marker types slips through validation, is spliced verbatim into the file by `reassembleResolvedFile()`, and is later written to disk and `git add`-ed by `_applyCopilotConflictResolutions()` without any further marker check.

### Finding Description
The relevant check is: [1](#0-0) 

```
const rc = hunkObj.resolvedContent
if (/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)) {
  throw new CopilotValidationError(
    `Copilot returned an invalid conflict resolution payload: hunk ${j} of file "${path}" still contains conflict markers`
  )
}
```

This is an **AND** of two partial marker patterns, and it omits the closing marker entirely:
- If `resolvedContent` contains a lone `<<<<<<<` (opening marker) without a `=======` line, validation passes.
- If it contains a lone `=======` without `<<<<<<<`, validation passes.
- If it contains a `>>>>>>>` (closing marker) alone, or together with only one of the other two markers, validation passes — `>{7}` is never tested.

Once `hunks` pass this check, `reassembleResolutions()` → `reassembleResolvedFile()` splices the (still possibly marker-containing) `resolvedContent` directly into the reconstructed file with no additional marker scanning: [2](#0-1) .

The reassembled content then flows unchecked through the store to disk: [3](#0-2) 

`writeFile(absolutePath, resolution.resolvedContent, 'utf8')` is called and the path is immediately queued for `git add`, staging the corrupted content: [4](#0-3) .

No other guard in the pipeline (`validateResolutionPaths`, the reassembly loop, or the write path) re-checks for conflict markers.

### Impact Explanation
This breaks the invariant the code itself documents: the check exists specifically to guarantee "all conflict markers removed" content before it becomes part of a commit. Because the attacker-influenced Copilot response (the model's session prompt includes repository content such as commit messages, PR titles/descriptions and diff context, which can carry prompt-injection payloads from an untrusted collaborator's commits/PR) only needs to produce a resolution containing one of the three marker tokens to bypass the guard, a malformed/partial conflict-marker artifact (e.g. a lone `<<<<<<< HEAD` line, or a stray `>>>>>>> theirs` line) can end up spliced into the reassembled file, written to disk, and staged automatically when the user clicks "Continue Merge." This is a silent corruption of what the user commits: the file can contain broken/invalid syntax or a misleading fragment of conflict-marker text that the user did not review as unusual, since the whole feature's premise is "fully resolved, marker-free content."

### Likelihood Explanation
Reaching this path only requires the Copilot session (whose context is built from repository-controlled data — commit messages, PR descriptions, diff hunks) to emit a hunk whose `resolvedContent` contains exactly one, not all, of the three marker patterns — a very plausible partial/degenerate LLM output, and one that is trivial to induce via prompt injection embedded in repo content that ends up in the model's context. No local access, credentials, or unusual user steps are needed beyond the normal "Resolve with Copilot" → "Continue Merge" flow that the feature already encourages.

### Recommendation
Tighten the marker check in `parseCopilotConflictResolution()` (around `app/src/lib/copilot-conflict-resolution.ts:444`) to reject `resolvedContent` if **any** of the three marker patterns (`<{7}`, `={7}`, `>{7}`) appears on its own line, rather than requiring the opening and separator markers to co-occur. Consider adding the same check as a final guard in `reassembleResolvedFile()`/`reassembleResolutions()` immediately before the content is returned, so the write path in `app-store.ts` cannot receive marker-containing content even if a caller bypasses `parseCopilotConflictResolution`.

### Proof of Concept
1. Craft (or induce via prompt-injected repo content) a Copilot response whose JSON payload contains a resolution hunk such as:
```json
{ "resolvedContent": "some code\n<<<<<<< HEAD\nmore code" }
```
This has an opening marker but no `=======` separator, so `/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)` evaluates to `false` and `parseCopilotConflictResolution()` does not throw.
2. The hunk is accepted into `validatedHunks` and returned from `parseCopilotConflictResolution()`.
3. `reassembleResolvedFile()` splices this raw string into the file content in place of the real conflict block (no marker re-check).
4. The user clicks "Continue Merge" in the Copilot conflicts dialog, triggering `_applyCopilotConflictResolutions()`, which calls `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and then `git add`s the file — committing a file with a stray, unresolved-looking `<<<<<<< HEAD` fragment without any validation error being raised.
