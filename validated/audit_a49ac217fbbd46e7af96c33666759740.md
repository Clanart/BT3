### Title
Reward-per-token distribution snapshot lets a flash-loaned "spot" share steal disproportionate BaseRewardPool bonus-token yield - (File: rewards/BaseRewardPoolV2.sol, wombat/WombatStaking.sol, wombat/WombatPoolHelper.sol)

### Summary
`BaseRewardPoolV2` (and the equivalent `BaseRewardPool`/`mWOMSVBaseRewarder`) distributes bonus reward tokens by bumping a single global `rewardPerTokenStored` accumulator each time new rewards are provisioned, using the **current spot value** of `totalStaked()` at that exact moment, exactly like the BathBuddy bug's "spot share of the pool" root cause. `WombatStaking.withdraw()` triggers this reward provisioning (`_toMasterWomAndSendReward`) *before* the withdrawing user's stake is removed from `MasterMagpie`, so a user who inflates their staked balance immediately before triggering a withdrawal-harvest captures an outsized share of that reward tranche relative to the actual time they contributed liquidity.

### Finding Description
`_provisionReward` in `BaseRewardPoolV2.sol` increases the accumulator proportionally to `totalStaked()` at the instant it is called: [1](#0-0) 

`totalStaked()` simply reads MasterMagpie's live balance of the staking (receipt) token: [2](#0-1) 

Every user's claimable amount is `(rewardPerToken - userRewardPerTokenPaid) * balanceOf(user)`, i.e., whoever holds the largest balance *at the moment `rewardPerTokenStored` increases* captures the largest share of that particular reward injection, regardless of how long they actually held the position: [3](#0-2) 

Critically, `WombatStaking.withdraw()` calls `_toMasterWomAndSendReward` (which harvests pending WOM and queues it into the `BaseRewardPool` via `_provisionReward`) **before** the pool helper unstakes the user from `MasterMagpie`: [4](#0-3) 

The corresponding `WombatPoolHelper.withdraw()` confirms the sequence: `WombatStaking.withdraw` (harvest+queue) executes first, then `_unstake` removes the user's stake from MasterMagpie afterward: [5](#0-4) 

So a wallet can: (1) deposit/flash-swap a large amount of the underlying deposit asset into the Wombat pool via `WombatPoolHelper.deposit`/`depositLP` to obtain an outsized share of the receipt token staked in `MasterMagpie`, (2) call `withdraw`, which harvests all currently pending WOM rewards and queues them into `BaseRewardPool` while `totalStaked()` still includes the attacker's inflated balance, then (3) complete the unstake/burn in the same transaction. The attacker's `earned()` for that reward tranche is computed against their momentarily-huge balance, diluting genuine long-term stakers who should have earned proportionally to their sustained share of the pool over the accrual period — the same "spot share vs. time-weighted share" flaw as BathBuddy's `release()`.

### Impact Explanation
This results in theft of unclaimed/pending bonus-token yield (WOM and other reward tokens routed through `BaseRewardPool`/`BaseRewardPoolV2`/`mWOMSVBaseRewarder`) from genuine long-term LPs/stakers, who receive a smaller share of each harvested reward tranche than their actual time-weighted contribution warrants, while the flash-depositor captures a disproportionate cut in a single atomic transaction. This matches the accepted impact category of theft of unclaimed yield.

### Likelihood Explanation
The path is reachable by any unprivileged wallet through the standard, unprivileged `WombatPoolHelper.deposit`/`depositLP` and `withdraw` functions — no admin or governance action is required. The only precondition is access to enough of the pool's deposit asset (or LP token) for one transaction, which is readily obtainable via a flash loan for common stablecoin/LP assets used by Wombat pools. The attack is atomic (single transaction), requiring no timing risk beyond standard MEV execution.

### Recommendation
Do not compute reward-per-share distribution against the instantaneous `totalStaked()`/user balance. Either (a) checkpoint total-staked and user balances *before* the current transaction's stake-affecting side effects (e.g., snapshot balances prior to harvest-and-queue, or perform harvest/queue strictly after removing the withdrawing user's stake, and require unstaking to fully settle before any new reward accrues to the remaining/incoming balance), or (b) adopt a time-weighted or minimum-holding-period based accrual model (e.g., Synthetix-style continuous `rewardRate`/`periodFinish` with per-second linear accrual) so that a single-block change in stake cannot capture a full reward tranche instantaneously.

### Proof of Concept
1. Pool P has legitimate long-term stakers with pending unharvested WOM rewards accruing in `MasterWombat`.
2. Attacker takes a flash loan of the pool's deposit asset and calls `WombatPoolHelper.deposit()`/`depositLP()`, minting a large receipt-token balance and staking it into `MasterMagpie` for pool P via `depositFor` [6](#0-5) , becoming the majority holder of `totalStaked()` in `BaseRewardPoolV2` for that staking token.
3. Attacker immediately calls `WombatPoolHelper.withdraw()`, which invokes `WombatStaking.withdraw()`; this calls `_toMasterWomAndSendReward(_lpToken, _liquidity, false)`, harvesting all pending WOM and calling `queueNewRewards`/`_provisionReward`, which bumps `rewardPerTokenStored` using `totalStaked()` that still includes the attacker's large stake [7](#0-6) .
4. `_unstake` then removes the attacker from `MasterMagpie` and the receipt token is burned, and the attacker repays the flash loan, having already banked a share of the just-harvested reward proportional to their momentary balance rather than to any real holding duration, diluting genuine stakers' entitlement to that WOM harvest.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
