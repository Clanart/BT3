Missing `PopLimit()` on error paths in `ParseDelimitedFromCodedStream` leaves stale wire-format boundary state on a reused `CodedInputStream`, corrupting/leaking subsequent-message parsing - ([File: src/google/protobuf/util/delimited_message_util.cc])

### Summary
The Tomcat advisory's failed invariant is: an object-recycling routine can exit through an error path that skips part of its cleanup, so stale per-request state survives into the next reuse of the object, corrupting/leaking data across otherwise-independent operations (CWE-459). The public helper `ParseDelimitedFromCodedStream()` in `google::protobuf::util` has the same structural flaw: it calls `CodedInputStream::PushLimit()` to bound one delimited sub-message, but on **every** failure branch it `return`s `false` without calling the matching `PopLimit()`. Because `CodedInputStream` is explicitly designed to be reused across sequential reads of multiple delimited messages from the same stream (this is literally what `ParseDelimitedFromCodedStream`/`ParseDelimitedFromZeroCopyStream` are for), an attacker-controlled malformed delimited message leaves the stream's internal limit/`bufferSizeAfterLimit_` bookkeeping in the state of the *previous, failed* message, silently corrupting the boundary computation for whatever is parsed next from that same stream.

`CodedInputStream::PushLimit`/`PopLimit` maintain `current_limit_` and derive `buffer_size_after_limit_` from it (`CodedInputStream::ExpectAtEnd`/`ConsumedEntireMessage` at `src/google/protobuf/io/coded_stream.h:1516-1576` depend on this bookkeeping being consistent). `PushLimit()` computes the new limit relative to the *previous* `current_limit_`; `PopLimit()` is the only call that restores it. `CodedInputStream::SetRecursionLimit`/`RecursionBudget` documentation and `resetSizeCounter()` (Java equivalent, `CodedInputStream.java:544-546`) both confirm the documented, supported usage pattern of reading "several messages from a single `CodedInputStream`" — i.e., the stream object is intentionally recycled across message boundaries, exactly analogous to Tomcat recycling `Request`/`Response`/`Processor` objects across HTTP requests on a connection.

If a client sends a delimited message whose declared size does not match the bytes actually consumed, or that fails `MergeFromCodedStream` (e.g., malformed field within the sub-message, or a message that leaves unconsumed trailing bytes so `ConsumedEntireMessage()` is false), the function returns `false` with the previous `PushLimit()` still in effect. If the caller (as is idiomatic for this exact API — reading a stream of delimited messages, e.g. in a loop, tolerating and logging per-item parse failures rather than tearing down the whole stream) continues calling `ParseDelimitedFromCodedStream()`/`ParseDelimitedFromZeroCopyStream()` on the same `CodedInputStream`/`ZeroCopyInputStream`, the next call's `ReadVarint32()`/`PushLimit()` operate under the stale, narrower `current_limit_` inherited from the aborted message rather than the true stream boundary. This is a direct wire-parsing invariant violation: the "boundary of message N" leaks into "the boundary computation of message N+1", i.e. the incomplete-cleanup pattern from the Tomcat advisory transferred onto CodedInputStream's public delimited-message API.

### Impact Explanation
Once `current_limit_` is left inconsistent, the next parse on the same stream can:
- Falsely report `ConsumedEntireMessage()`/hit the stale limit early, truncating or silently dropping trailing bytes of the next legitimate message (data loss / corruption of the next request's payload), or
- Cause `PushLimit()` for the next message to throw `TruncatedMessage` even though the new message is well-formed and within the real stream bounds (denial of parsing / availability for the next unrelated logical message on that connection).

This is a data-integrity/availability defect confined to a single shared stream/connection between sequential delimited messages — it does not itself leak bytes between different network sockets/arenas the way Tomcat's Request/Response recycling could leak response bytes between distinct client sockets, so the severity is lower than the Tomcat CVE. There is no memory-safety violation and no unbounded resource growth; the impact is bounded to corrupted parsing state for subsequently-read messages on the same, already-attacker-influenced stream. Impact is best characterized as Medium-Low: correctness/availability corruption within a single connection's message sequence, not cross-session confidentiality disclosure.

### Likelihood Explanation
Reaching this requires only a single attacker-controlled malformed delimited message (wrong prefix length vs. actual message bytes, or a message triggering `MergeFromCodedStream` failure) sent through the ordinary public `ParseDelimitedFromCodedStream`/`ParseDelimitedFromZeroCopyStream` entry points — no privileged access, hostile schema, or internal API misuse is needed. The likelihood that this manifests as an observable bug for an application depends on whether the application reuses the same `CodedInputStream`/`ZeroCopyInputStream` for multiple delimited reads after a `false` return (a common and, per the API's own documentation about `resetSizeCounter()`/multi-message streams, explicitly supported usage pattern) rather than discarding the stream on any parse failure. This is plausible but application-dependent, so likelihood is Medium.

### Recommendation
Wrap the parse body in a scope guard / RAII (or explicit `PopLimit(limit)` on every early-return path) so the pushed limit is always released regardless of which check fails, e.g.:
```cpp
struct LimitGuard {
  io::CodedInputStream* input;
  io::CodedInputStream::Limit limit;
  ~LimitGuard() { input->PopLimit(limit); }
};
```
and use it immediately after `PushLimit()` so `ParseDelimitedFromCodedStream` restores stream state on every return path, matching the guarantee CVE-2023-42795's fix gave Tomcat's recycling paths.

### Proof of Concept
1. Build a byte buffer: `VarintEncode(10) + <9 bytes of valid-looking prefix> + <corrupt/truncated tail>` such that `MergeFromCodedStream` fails partway (e.g. a required field missing or a malformed varint) while some bytes of the declared 10-byte length have already been consumed.
2. Append a second, fully valid, delimited message directly after it in the same buffer.
3. Wrap the whole buffer in one `ZeroCopyInputStream`, call `ParseDelimitedFromZeroCopyStream(&msg1, &stream, nullptr)` — observe it returns `false` (as expected) but note `PopLimit` was never invoked internally on `CodedInputStream`'s state (verifiable by instrumenting `CodedInputStream::PopLimit` call counts, or by constructing the call through `ParseDelimitedFromCodedStream` directly with the same `CodedInputStream` object retained across two calls).
4. Call `ParseDelimitedFromCodedStream(&msg2, &input, nullptr)` again on the *same* `input` for the second, valid message — observe that its `ReadVarint32`/`PushLimit` computations are performed against the still-stale `current_limit_` from step 3, producing either an unwarranted `TruncatedMessage` failure or a `ConsumedEntireMessage()` mismatch for a message that is otherwise wire-valid, confirming the leaked boundary from message 1 corrupts parsing of message 2 on the same stream.

bool ParseDelimitedFromCodedStream(MessageLite* message,
                                   io::CodedInputStream* input,
                                   bool* clean_eof) {
  if (clean_eof != nullptr) *clean_eof = false;
  int start = input->CurrentPosition();

  // Read the size.
  uint32_t size;
  if (!input->ReadVarint32(&size)) {
    if (clean_eof != nullptr) *clean_eof = input->CurrentPosition() == start;
    return false;
  }

  // Get the position after any size bytes have been read (and only the message
  // itself remains).
  int position_after_size = input->CurrentPosition();

  // Tell the stream not to read beyond that size.
  io::CodedInputStream::Limit limit = input->PushLimit(static_cast<int>(size));

  // Parse the message.
  if (!message->MergeFromCodedStream(input)) return false;
  if (!input->ConsumedEntireMessage()) return false;
  if (input->CurrentPosition() - position_after_size != static_cast<int>(size))
    return false;

  // Release the limit.
  input->PopLimit(limit);

  return true;
}
