### Title
PedPoP `blame` adjudicates an arbitrary caller-supplied `recipient` as faulty without proof the accuser is that recipient — forged blame against honest participants - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take `sender` and `recipient` `Participant` indexes plus an optional `EncryptionKeyProof`, and return which party is "faulty". This mirrors the H-01 confused-deputy pattern: the adjudicator acts on a caller-supplied principal (`recipient`) with no binding that the accusation actually originates from, or is authorized by, that participant. Because `proof` is optional, any party can submit `(sender, victim, msg, None)` and the function deterministically returns `victim` as faulty whenever the message's proof-of-possession signature is valid.

### Finding Description
`blame_internal` resolves blame as follows [1](#0-0) :

- `DecryptionError::InvalidSignature` (bad PoP) → `sender` blamed.
- `DecryptionError::InvalidProof` (missing or invalid `EncryptionKeyProof`) → `recipient` blamed.
- Valid decryption but non-canonical/invalid share → `sender` blamed.

In `decrypt_with_proof`, `proof: None` unconditionally yields `DecryptionError::InvalidProof` [2](#0-1) , and a `Some(proof)` DLEq-verified against `enc_keys[&decryptor]` fails unless the prover knows the victim's private encryption key — which also yields `InvalidProof` → `recipient` blamed.

Crucially, the `EncryptedMessage` PoP challenge binds only `context`, `nonce`, `key`, `sender`, and `msg` — it does **not** bind the intended recipient [3](#0-2) . So any authentically-signed `EncryptedMessage` from `sender` (e.g., one addressed to the attacker, or any such message the attacker can present to the adjudicator) passes `pop.verify` regardless of which `recipient` index the accuser claims. Nothing in `blame`/`blame_internal`/`AdditionalBlameMachine::new` checks that the accusation was issued by `recipient` or that `msg` was ever sent to `recipient` [4](#0-3) [5](#0-4) .

`AdditionalBlameMachine::new` is explicitly designed to evaluate blame "regardless of if the caller was a member in the DKG protocol" — it reconstructs `Decryption` solely from public commitment messages [6](#0-5) . This is the direct analog of a whitelisted contract executing operations on an arbitrary `data.user`: the `recipient` field is attacker-controlled input the verifier acts on without authorization.

### Impact Explanation
An accuser submits `(sender, victim, authentic_msg, proof: None)` to the blame adjudicator. The adjudicator returns `victim` (the honest participant) as the faulty party — an incorrect blame verdict equivalent to a forged accusation. In any deployment where the blame result drives slashing/removal of a participant (as `InvalidDkgShare` handling does downstream), an unprivileged accuser can get honest participants declared faulty purely by choosing their index as `recipient`, with no cooperation, signature, or decryption-key disclosure from the victim. This also inverts the intended accountability: the "guilty by silence" rule (`InvalidProof` → accuser at fault, because a real accuser refusing to reveal the ECDH key is lying) is weaponized against third parties who never accused anyone.

### Likelihood Explanation
Any party able to submit a blame evaluation with a well-formed `EncryptedMessage` (which every DKG participant possesses for the shares sent to them, and which the documentation expects to be relayed through an authenticated channel) can trigger this with zero secret knowledge. The only requirement — a PoP-valid `EncryptedMessage` from the accused `sender` — is satisfied by ordinary protocol traffic, since the PoP is not bound to a recipient.

### Recommendation
In `decrypt_with_proof`/`blame_internal`, do not return `recipient` as faulty for a bare `InvalidProof` unless the accusation is cryptographically bound to `recipient` — e.g., require a signature/PoK under the recipient's encryption key (or the recipient's registered identity) over `(sender, msg)` attesting the accusation, and reject `proof: None` submissions that cannot show such authorization. Additionally, consider binding the intended recipient into `pop_challenge` so a message cannot be repointed at a different `recipient` index during adjudication.

### Proof of Concept
```rust
// Any party (participant or external adjudicator caller) holding one
// authentic EncryptedMessage from `sender` — e.g. the share message
// legitimately sent to the *attacker* — can frame an honest `victim`:

let machine = AdditionalBlameMachine::<C>::new(context, n, all_commitment_msgs).unwrap();

// msg: any EncryptedMessage whose PoP verifies for `from = sender`
// (the PoP challenge does not include the recipient).
// proof: None  ->  decrypt_with_proof returns InvalidProof
//              ->  blame_internal returns `recipient`
let faulty = machine.blame(sender, victim, msg, None);
assert_eq!(faulty, victim); // honest participant declared faulty
```

Root cause chain: `blame` accepts caller-chosen `recipient` [5](#0-4)  → `blame_internal` maps `InvalidProof` to `recipient` [7](#0-6)  → `decrypt_with_proof` returns `InvalidProof` for `None`/wrong proof [2](#0-1)  → `pop_challenge` omits the recipient, so the supplied message needs no relation to `victim` [3](#0-2) .

  pub fn new(

    n: u16,
    mut commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<Self, PedPoPError<C>> {
    let mut commitments = HashMap::new();
    let mut encryption = Decryption::new(context);
    for i in 1 ..= n {
      let i = Participant::new(i).unwrap();
      let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
      commitments.insert(i, encryption.register(i, msg).commitments);
    }
    Ok(AdditionalBlameMachine(BlameMachine { commitments, encryption, result: None }))
  }

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
