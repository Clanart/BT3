### Title
`SignableTransaction::new` computes the transaction weight/fee without the OP_RETURN output, systematically underpaying the fee for any transaction carrying data - (File: `networks/bitcoin/src/send.rs`)

### Summary
The launchpad bug is a value-credit computation — `amount = balance − reserve` — that omits a component already carved out of the balance (accrued fees), letting a caller claim value they never provided. The same class appears in `SignableTransaction::new`: the transaction weight used to derive `needed_fee` is computed from `payments` only, while the real transaction also includes an attacker-influenced OP_RETURN output that was pushed to `tx_outs` beforehand. The size of the OP_RETURN output is never accounted for in the fee formula, so the signed transaction pays `fee_per_vbyte * vbytes(payments)` instead of `fee_per_vbyte * vbytes(payments + OP_RETURN)`.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` *before* the weight is calculated, but `calculate_weight_vbytes` is invoked with `payments`, which does not contain the data output:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds a template `Transaction` whose outputs come solely from `payments` (plus an optional change output), so the OP_RETURN's `8 + scriptPubKey` bytes (~`data.len() + 11` bytes) are excluded from `weight`/`vbytes`. The same omission occurs in the change branch, which calls `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` — again without the data output.

Consequences:

1. **Underpaid fee.** The actual fee paid is `needed_fee = fee_per_vbyte * vbytes_without_data`. The broadcast transaction is `~data.len() + 11` bytes larger, so the effective fee rate is below the requested `fee_per_vbyte` — by up to ~91 vbytes worth of fee per transaction (data is capped at 80 bytes).
2. **Minimum-relay check bypassed.** The `TooLowFee` check compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the *understated* `vbytes`. A transaction can pass this check while its true on-chain feerate is below 1 sat/vbyte, making it non-relayable by standard nodes.
3. **Dust-threshold change accounting.** Whether change is emitted, and the value assigned to it, are decided with `fee_with_change` derived from the same understated size — the change output absorbs the same missing-fee delta.

The OP_RETURN `data` is attacker-influenced: it carries the protocol's `InInstruction`/transfer shorthand ultimately derived from user-initiated messages on the Serai side, so an unprivileged user controls its length (up to the 80-byte cap) and can maximize the discrepancy.

### Impact Explanation
Every Bitcoin transaction Serai produces that includes a data output pays a lower feerate than the network layer requested and recorded in `needed_fee`. In the worst case (max-size data, fee rate near the minimum), the resulting transaction's true feerate can fall below the minimum relay fee and be rejected by Bitcoin Core's mempool entirely, leaving the plan's inputs un-spendable via that transaction until it is reconstructed — a liveness failure for user/protocol funds. At higher feerates the transaction still consistently underpays, degrading confirmation reliability. This maps to the same impact shape as the source report: an accounting formula silently drops a component, transferring/losing value relative to what was intended.

### Likelihood Explanation
The bug triggers deterministically whenever `SignableTransaction::new` is called with `data: Some(_)` — no race or adversary coordination is needed. The shortfall is bounded (~91 vbytes of fee), so it is not exploitable to drain funds; the realistic impact is underpriced/non-relayable transactions, i.e., a Medium-severity correctness/liveness issue rather than direct theft.

### Recommendation
Include the data output in the weight template. Either pass the already-built `tx_outs` (or a `payments + op_return` composite) into `calculate_weight_vbytes`, or add a `data_len` parameter so the OP_RETURN output is represented in the template transaction for both the no-change and with-change invocations. Additionally, perform the `TooLowFee` minimum-relay check against the final transaction's true vbytes.

### Proof of Concept
```rust
// networks/bitcoin/src/send.rs
let data = vec![0xaa; 80]; // max permitted
let tx = SignableTransaction::new(
  vec![output],                    // some ReceivedOutput
  &payments,
  None,
  Some(data.clone()),
  fee_per_vbyte,
).unwrap();

// needed_fee was computed against vbytes of a tx with NO OP_RETURN output
assert_eq!(tx.needed_fee(), fee_per_vbyte * vbytes_without_op_return);

// The real transaction includes the OP_RETURN output and is ~91 bytes larger
let real_vsize = tx.transaction().vsize() as u64;
// True effective feerate:
//   tx.fee() == tx.needed_fee()  (no change), but
//   tx.fee() / real_vsize < fee_per_vbyte
assert!(tx.needed_fee() < fee_per_vbyte * real_vsize);
```
