Based on my research, I found a concrete local analog. Both the original report and this Hyperbridge finding share the same root cause: **using an unguarded, externally-influenceable value (a contract's raw balance, moved by an unauthenticated entrypoint) as the basis for a security-critical accounting decision, instead of a value strictly tracked and attributable to the specific operation.**

### Title
`CallDispatcher.dispatch()` has no caller restriction, letting anyone drain tokens/ETH stranded in the shared dispatcher used by IntentGatewayV2's predispatch/postdispatch flows - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, persistent contract referenced by `Params.dispatcher` in `IntentGatewayV2`, used to execute attacker/user-supplied calldata during order placement (`predispatch`) and fulfillment (`postdispatch`/output calldata). Its `dispatch()` function is fully public with no access control, and it can hold real token/ETH balances between the moment assets are moved into it and the moment the gateway sweeps them back out.

### Finding Description
`CallDispatcher.dispatch()` accepts an arbitrary ABI-encoded `Call[]` and executes each with the dispatcher itself as `msg.sender`, with zero caller restriction: [1](#0-0) 

`IntentGatewayV2.placeOrder` uses this same shared `dispatcher` address to receive predispatch assets, run the order's arbitrary predispatch call, and then sweep the dispatcher's balance back into the gateway using the **full balance** of the dispatcher, not a value strictly attributable to only this order's assets: [2](#0-1) 

The "received" amount that becomes `order.inputs[i].amount` — which is baked into the order commitment and dictates how much escrow is later released to the filling solver — is derived from this dispatcher-balance-delta measurement: [3](#0-2) 

Because `order.predispatch.call` is attacker-controlled and can trigger arbitrary DeFi interactions (documented use case: "unwrapping LP tokens"), any predispatch flow that produces token types not declared in `order.inputs`, or leaves excess dust after a swap/unwrap, leaves those assets sitting in the `CallDispatcher` contract's persistent balance after the transaction completes — the gateway only sweeps tokens it explicitly listed in `order.inputs`. Since `dispatch()` has no `onlyGateway`/access-control modifier, any unprivileged address can later call `CallDispatcher.dispatch()` directly with `Call({to: strandedToken, data: transfer(attacker, strandedBalance)})` (or a plain ETH-sweeping call) to seize any balance that has accumulated in the dispatcher from any user's prior order, with the dispatcher's own identity authorizing the transfer.

This mirrors the AuctionHouse root cause precisely: the settlement/accounting value (`order.inputs[i].amount` / the auction's accepted funds) is derived from a contract's **raw balance** rather than a properly attributed, access-controlled internal state, and that balance can be reached/manipulated through an unauthenticated path (`dispatch()` here; `selfdestruct` donation there).

### Impact Explanation
This is a public-entrypoint, unprivileged path to permanent loss of user/protocol funds: any ETH/ERC20 dust or misrouted output from a predispatch/postdispatch calldata execution accumulated in the shared `CallDispatcher` can be swept by any third party, with no relayer, prover, admin, or governance compromise required. This satisfies the "stealing or loss of funds" and "transaction manipulation" impact categories in scope.

### Likelihood Explanation
Likelihood is high for any deployment where predispatch/postdispatch calls interact with external protocols (swaps, unwraps) that can produce more token types or dust than explicitly declared in the order — a documented, intended use case of the feature. The attack requires only a single public transaction calling `dispatch()`; no special conditions, timing, or privileged access are needed.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by authorized gateway contracts (e.g., an `onlyGateway`/allowlist modifier set at deployment), and additionally have `IntentGatewayV2`'s predispatch flow sweep based on a strictly tracked delta (balance immediately after predispatch execution minus balance immediately before, scoped to that single call) rather than raw full-balance reads that can be inflated by any funds unrelated to the current order.

### Proof of Concept
1. A user places an order with `predispatch.call` that unwraps an LP position or performs a swap through `CallDispatcher.dispatch()`, producing 100 units of Token B in addition to the 100 units of Token A declared in `order.inputs`.
2. `IntentGatewayV2.placeOrder` sweeps only Token A (per `order.inputs`); the 100 units of Token B remain in the `CallDispatcher` contract's balance after the transaction completes: [4](#0-3) 
3. Any unrelated attacker calls `CallDispatcher.dispatch()` directly with `Call({to: TokenB, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, 100e18)})`. Because `dispatch()` has no caller restriction, the call succeeds with `CallDispatcher` as `msg.sender` for the `transfer`, and the 100 Token B units are sent to the attacker: [5](#0-4)

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
