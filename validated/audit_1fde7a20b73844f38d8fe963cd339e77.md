### Title
`ReceivedOutput::read` fails to verify the stored offset actually derives the output's `script_pubkey`, silently accepting unspendable outputs — (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` deserializes three independent attacker-controlled fields — an offset scalar, a `TxOut`, and an `OutPoint` — but never checks the consistency invariant that makes the output spendable: `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)` and `key` even-Y. Analogous to `executeLowLevelCall` not checking `msg.value == msgValue` and that `target` is a contract, the reader accepts bytes where the claimed offset does not correspond to the claimed output, producing a `ReceivedOutput` that reports received value which no derived key can spend.

### Finding Description
`ReceivedOutput::read` reads an arbitrary `Secp256k1` scalar as `offset`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, returning `Ok(ReceivedOutput { offset, output, outpoint })` unconditionally [1](#0-0) . The only place `offset` and `script_pubkey` are ever bound together is inside `Scanner::scan_transaction`, which inserts into `scripts` only scripts produced by `p2tr_script_buf(self.key + GENERATOR * offset)` — the check that returns `None` for odd-Y keys [2](#0-1) [3](#0-2) . A deserialized `ReceivedOutput` bypasses that construction entirely: any `script_pubkey` (e.g. someone else's address, a bare P2WSH, or the P2TR script of `key + G*offset'` for a different `offset'`) can be paired with any `offset`. The processor's `Output::read` wraps `ReceivedOutput::read` directly, again with no consistency check [4](#0-3) , and `Output::key()` derives the spend key by *assuming* the binding, subtracting `G * offset` from whatever key the script encodes [5](#0-4) . The value is then reported via `balance()` from the unvalidated `TxOut` [6](#0-5) .

### Impact Explanation
Funds reported received that are not spendable. A `ReceivedOutput` claiming `offset` and a `TxOut` whose `script_pubkey` pays to an unrelated key yields an output the scanner/accounting credits `output.value` for, while the implied spend key (`script key - G*offset`, in `Output::key()`) does not correspond to the actual output key and has no usable scalar relationship to the multisig key. Feeding an `offset` that makes `key + G*offset` odd-Y yields a key with no valid P2TR encoding at all (`p2tr_script_buf` returns `None`) — the equivalent of the "silent failure on invalid target" half of the reference bug. Signing against such an output either produces an invalid transaction or attributes the input to the wrong key.

### Likelihood Explanation
Any path that feeds untrusted bytes into `ReceivedOutput::read`/`Output::read` (network relays, imported rescan data, replication) can craft the mismatch with ordinary consensus-valid encodings; no cryptographic hardness is required. The check omission is deterministic, so exploitability depends only on reachability of the read path with attacker-influenced bytes.

### Recommendation
Bind `offset` to `output.script_pubkey` at read/deserialization time, mirroring `Scanner`'s invariant:

```rust
pub fn read<R: Read>(r: &mut R, key: ProjectivePoint) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  // ... decode output and outpoint ...
  let expected = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * offset))
    .ok_or_else(|| io::Error::other("offset yields non-P2TR key"))?;
  if output.script_pubkey != expected {
    Err(io::Error::other("offset does not derive output script_pubkey"))?;
  }
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

If the base `key` is unavailable at read time, verify the binding on first use (e.g. inside `multisig`/`key()`), and additionally reject outputs whose implied key is odd-Y.

### Proof of Concept
```rust
// Any two independent, consensus-valid fields are accepted:
let mut buf = vec![];
buf.extend(Scalar::ONE.to_bytes());                    // offset = 1
buf.extend(serialize(&TxOut {
  value: Amount::from_sat(50_000),
  script_pubkey: ScriptBuf::new_p2sh(&ScriptHash::all_zeros()), // pays to someone else
}));
buf.extend(serialize(&OutPoint::null()));

let output = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(output.value(), 50_000);   // reported as received
assert_eq!(output.offset(), Scalar::ONE); // ...yet 1·G + key has no relation to the script
```
Under `Scanner`-produced outputs this is impossible — `register_offset`/`scan_transaction` only ever store script-matched pairs — but `read` admits the mismatch silently, matching the "missing equality/validity check → silent acceptance" class of the reference finding.
