Based on my investigation, I found a concrete analog: `MaxGasPrice` is defined as a searcher-supplied "price bound" field on an `auction.Bid` (analogous to a slippage/price limit in the sandwich-attack report), but it is never enforced by the Kaia client when generating and submitting the bid execution transaction.

### Title
Searcher-supplied `MaxGasPrice` bid bound is never enforced by the auction module, allowing fee-delegation/gas-price extraction beyond the searcher's agreed limit - (File: kaiax/auction/impl/getter.go)

### Summary
In the KIP-249 auction flow, a searcher's `Bid` (v3.0) includes an optional `MaxGasPrice` field [1](#0-0) , which is signed as part of the EIP-712 typed data (`auctionTypeV3`) [2](#0-1)  and included in the on-chain `AuctionTx` payload via `EncodeAuctionCallData` [3](#0-2) . This field is clearly intended to act as the searcher's slippage/price bound — the maximum gas price the searcher is willing to have the bid transaction executed at (analogous to `oppositeAmountBound`/`sqrtPriceLimit` in the reported Perp bug, which bound the acceptable execution price).

### Finding Description
When the Kaia client builds the actual bid execution transaction via `GetBidTxGenerator`, it copies `GasFeeCap`/`GasTipCap` directly from the target transaction rather than validating or capping them against `bid.MaxGasPrice`: [4](#0-3) 

Nowhere in `BidPool.AddBid`/`validateBid`/`insertBid` (bid admission) or in `GetBidTxGenerator` (bid tx construction) is `bid.MaxGasPrice` compared against the actual gas price/fee cap that will be paid: [5](#0-4) . The `MaxGasPrice` value is only ever encoded/decoded for signature verification purposes (`EncodeAuctionCallData`/`DecodeAuctionCallData`), never read back to enforce a bound on gas pricing during bundling or execution [6](#0-5) .

This mirrors the reported bug class precisely: a price-bound field exists and is propagated/signed, but the code path that actually executes the priced operation (`_placePerpOrder` in the original report / `GetBidTxGenerator` here) ignores it, using an unconstrained value (`oppositeAmountBound=0` in the report / target-tx-derived gas price here) instead of enforcing the bound.

### Impact Explanation
Because the block proposer (via the `worker`/`builder` module) controls block assembly and ultimately sets `GasFeeCap`/`GasTipCap` for the bid tx from the target transaction's values rather than the searcher's signed `MaxGasPrice`, a searcher's economic assumption ("I will never pay more than X gas price for this bid execution") is not mechanically enforced by the client. If gas pricing conditions between bid signing and bid execution change (e.g., base fee moves, or a malicious/careless proposer selects a target tx with a higher fee cap than the searcher intended), the searcher's bid can be executed and settled at a gas price/fee cost the searcher never authorized, resulting in fee-delegation/gas cost abuse against the searcher (unauthorized value extraction from the searcher beyond their signed intent).

### Likelihood Explanation
This is reachable by any unprivileged auction participant (searcher) submitting a bid through `auction_submitBid` — no special privilege required beyond being a bidder — and is triggered automatically whenever the proposer's block-building logic processes their bid via `ExtractTxBundles`/`GetBidTxGenerator`. Because `MaxGasPrice` is `omitempty` and not validated anywhere, this occurs in the normal/default code path, not just an edge case.

### Recommendation
In `GetBidTxGenerator` (and/or in `BidPool.validateBid`), when `bid.MaxGasPrice` is non-nil and non-zero, cap/validate the generated bid transaction's `GasFeeCap` (and `GasTipCap`) against `bid.MaxGasPrice`, rejecting or clamping bid tx construction if the resulting gas price would exceed the searcher-signed bound, consistent with how `oppositeAmountBound`/`sqrtPriceLimit` should have been enforced in the original report.

### Proof of Concept
1. A searcher signs and submits a v3.0 `Bid` with `MaxGasPrice = X` via `auction_submitBid`, matching `BidInput.MaxGasPrice` [7](#0-6) .
2. The bid is accepted into the pool by `BidPool.AddBid`/`insertBid`, which never inspects `MaxGasPrice` [5](#0-4) .
3. During block building, `GetBidTxGenerator` constructs the actual bid execution transaction using the target transaction's `GasFeeCap()`/`GasTipCap()`, ignoring `bid.MaxGasPrice` entirely [4](#0-3) .
4. If the target transaction's fee cap exceeds `X`, the bid tx executes and pays a gas price above what the searcher signed as their maximum, with no rejection or clamping anywhere in the pipeline.

func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}
