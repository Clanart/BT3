## Finding

`Rule.from_dict` in `plugins/hookify/core/config_loader.py` hard-codes the field used for legacy `pattern:` rules on `file` events to `new_text`, with no way to override it, while the explicit `conditions:` form lets the author pick any field, including `content`. Combined with `RuleEngine._extract_field` in `plugins/hookify/core/rule_engine.py`, this creates a real block-rule bypass for the `Write` tool.

### Root cause

For legacy simple-pattern rules, the field is inferred purely from `event`, never from the actual tool that will be used: [1](#0-0) 

For `event: file` this always resolves to `field = 'new_text'`, regardless of whether the triggering tool is `Edit`/`MultiEdit` (which carry `old_string`/`new_string`) or `Write` (which carries `content` and has no `new_string` key at all).

`RuleEngine._extract_field` then resolves `new_text` for `Write`/`Edit` tools via: [2](#0-1) 

For a `Write` call, `tool_input` has no `new_string` key, so `tool_input.get('new_string', '')` returns `''`. `_check_condition` then runs the regex/contains check against an empty string, which reliably fails to match any non-trivial pattern: [3](#0-2) 

So any block rule authored with the simple/legacy `pattern:` format for `event: file` (the format `/hookify` documents and generates as the default, simpler option) silently never fires when Claude uses the `Write` tool — only `Edit`/`MultiEdit` are actually checked. An explicit `conditions:` rule using `field: content` instead correctly matches both `Write` and `Edit` (`_extract_field` resolves `content` from `tool_input.get('content') or tool_input.get('new_string', '')`), so the two rule authoring styles produce different effective security semantics for the identical intended policy. [4](#0-3) [5](#0-4) 

### Exploit flow

1. A repo-shipped or `/hookify`-generated block rule uses the legacy format, e.g. `.claude/hookify.no-secrets.local.md` with `event: file`, `pattern: API_KEY`, `action: block`.
2. `load_rule_file` → `Rule.from_dict` silently locks the check to `field='new_text'`.
3. An unprivileged agent/session simply asks Claude to write the forbidden content using the `Write` tool instead of `Edit` (both are standard, always-available tool calls, no privilege needed).
4. `RuleEngine._rule_matches` extracts `''` for `new_text` on a `Write` call, the condition never matches, `blocking_rules` stays empty, and the operation is allowed with no warning at all — the block silently never engages for `Write`.
5. The same policy expressed via explicit `conditions:` with `field: content` would have correctly blocked the `Write` call, demonstrating the differential.

### Why existing checks don't stop it

There is no validation anywhere that legacy-inferred fields are actually resolvable for every tool that can trigger the given `event`; `load_rule_file`/`load_rules` only catch I/O and parsing exceptions, not semantic field-coverage gaps, and `_rule_matches` treats a `None`/empty extracted field as a normal non-match rather than flagging misconfiguration. [6](#0-5) 

### Impact

Security-control bypass: a block rule that the operator/plugin believes protects `event: file` operations (e.g. blocking secrets/dangerous patterns) is silently inert for `Write`-tool edits, letting Claude write disallowed content without any warning or blocking message — routing around the intended permission/review boundary.

### Recommendation

- In `Rule.from_dict`, do not hard-code a single inferred field for legacy `pattern` rules on `file` events; either generate multiple conditions covering all relevant fields (`content`, `new_text`, `old_text`) combined with OR semantics, or require rule authors/`/hookify` generation to specify `field` explicitly.
- In `RuleEngine._extract_field`, treat an unresolved/empty field value distinctly from "field genuinely empty in this tool call" (e.g., log a warning when a configured field cannot be resolved for the active tool) so misconfigured legacy rules fail loudly instead of silently.
- Add a validation/lint step (e.g., in `load_rule_file`) that warns when a legacy `pattern` rule's `event` can be triggered by a tool for which the inferred field cannot be extracted.

### Proof of Concept (test plan)

```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

engine = RuleEngine()

# Legacy-style block rule (as generated by /hookify or docs examples)
legacy_rule = Rule.from_dict(
    {"name": "block-secret", "enabled": True, "event": "file",
     "pattern": "API_KEY", "action": "block"},
    "Secret detected"
)

# Explicit-style equivalent rule targeting the same intent
explicit_rule = Rule.from_dict(
    {"name": "block-secret-explicit", "enabled": True, "event": "file",
     "conditions": [{"field": "content", "operator": "contains", "pattern": "API_KEY"}],
     "action": "block"},
    "Secret detected"
)

write_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Write",
    "tool_input": {"file_path": "config.py", "content": "API_KEY=secret123"}
}

# Legacy rule fails to block the Write call (bug)
assert engine.evaluate_rules([legacy_rule], write_input) == {}

# Explicit rule correctly blocks the same Write call
result = engine.evaluate_rules([explicit_rule], write_input)
assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
```

This demonstrates that identical security intent, expressed via the two supported rule formats, produces divergent enforcement outcomes for `Write` operations — the legacy format is silently bypassable.

    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True
