### Title
Discard-changes-from-selection applies a stale diff to the working tree without re-validating file content, allowing silent corruption of unrelated changes - (File: `app/src/lib/git/apply.ts`)

### Summary
The original Mover finding is a broken "check-then-act" invariant: the fee is computed from a before/after balance comparison, but the "before" snapshot can become stale by the time the "after" balance is read because an attacker interleaves state changes in between. GitHub Desktop's discard-selection flow has the same broken invariant: the diff (the "before" state used to build a `git apply` patch) is captured once when the discard dialog opens, but the patch is applied to whatever the working-tree file contains at click time, with no re-check that the file is unchanged in between.

### Finding Description
`_discardChangesFromSelection` in `app-store.ts` takes a `diff: ITextDiff` and `selection: DiffSelection` supplied directly by the caller and forwards them unmodified to `gitStore.discardChangesFromSelection`, which calls `discardChangesFromSelection` in `app/src/lib/git/apply.ts`: [1](#0-0) 

That function builds a patch purely from the diff object it was given via `formatPatchToDiscardChanges`, then applies it with `git apply --unidiff-zero --whitespace=nowarn`: [2](#0-1) 

The diff itself is loaded once when the working-directory file is selected/rendered (`updateChangesWorkingDirectoryDiff`), and that same diff/selection object is threaded through the UI into `DiscardSelection`'s `discard()` handler and only invoked when the user clicks "Discard Changes" — there is no re-fetch or re-validation of the diff immediately before the `git apply` call: [3](#0-2) 

`updateChangesWorkingDirectoryDiff` does re-validate the diff whenever it *reloads* it for display purposes (checking that selection hasn't changed since the load started), but this guard only protects the diff-loading path, not the discard-apply path, which uses whatever diff snapshot happened to be passed into the dialog: [4](#0-3) 

`--unidiff-zero` patches are built with full context lines from the stale diff and applied against the live file by line offset. Just as in the Mover bug — where the "before" balance became inconsistent with the "after" balance because of an interleaved operation — here the "before" diff (rendered/approved by the user) can become inconsistent with the actual on-disk file if the file changes between dialog-open and discard-click, e.g. via:
- the app's own background fetch/fast-forward path, which runs concurrently while a dialog is open and can update tracked files via `fastForwardBranches`/`_refreshRepository` (`performFetch`) triggered by a remote controlled by the attacker; [5](#0-4) 
- content/smudge filters, hooks, or LFS operations from an attacker-controlled cloned/fetched repository that rewrite working-tree bytes asynchronously.

Because `git apply` is not re-validating the file against the exact content it saw when the diff was generated (there's no `--check` against a freshly loaded diff, and no hash/mtime comparison), a patch built from a stale diff can be applied on top of different actual content, silently discarding or reintroducing lines the user never approved — i.e., silent corruption of what the user's working tree (and subsequently what they might stage/commit) contains.

### Impact Explanation
This can result in the user's working directory being modified (lines re-added, removed, or corrupted) in ways inconsistent with what was shown and approved in the discard dialog, without any error being surfaced (or with a partial/garbled apply). Since the working tree feeds directly into what the user stages and commits next, this is a silent corruption of what the user commits, matching the "silent corruption of what the user commits or pushes" impact category. It does not require local/physical access, admin rights, or leaked credentials — only an attacker-controlled repository/remote whose fetch/checkout activity races with a legitimate user interaction.

### Likelihood Explanation
Exploitability requires precise timing: the attacker-influenced write to the working tree (via background fetch, hook, or filter) must land in the window between diff capture and the user clicking "Discard." Desktop performs background fetches and fast-forwards periodically and automatically while a repository is selected, which creates a real, non-contrived window for this race, but the user must have a partial-discard dialog open and the malicious content change must happen to overlap that window — making this a real but timing-dependent (medium-to-low likelihood) issue rather than a straightforward, always-exploitable one.

### Recommendation
Before applying a discard/partial-commit patch, re-load the diff for the target file immediately prior to calling `git apply`/`applyPatchToIndex` and abort (with a user-facing error) if the file's on-disk content or hash differs from what was used to build the patch, mirroring the staleness check already implemented in `updateChangesWorkingDirectoryDiff` for the diff-loading path but currently missing from the diff-consuming (discard/apply) path.

### Proof of Concept
1. Open GitHub Desktop against a repository with a remote controlled by the attacker (or with a smudge filter/hook that can rewrite tracked files, e.g. via LFS or a `post-checkout`/`clean` filter).
2. User modifies a tracked file locally and opens the Changes view; Desktop loads and renders the diff (`updateChangesWorkingDirectoryDiff`), and the user opens the "Discard changes" selection dialog for a partial hunk — the `diff`/`selection` objects are now fixed in the dialog's props (`discard-selection-dialog.tsx`).
3. While the dialog is open, Desktop's periodic background fetch (`performFetch` → `fastForwardBranches`) — driven by the attacker-controlled remote — updates the same tracked file on disk (e.g., a fast-forward that changes file content, or an asynchronous filter rewrite).
4. The user clicks "Discard Changes." `discardChangesFromSelection` (`app/src/lib/git/apply.ts:102-120`) builds a patch from the *stale* diff/selection and applies it with `git apply --unidiff-zero` against the *new* file content, with no re-validation, silently corrupting the file relative to what the user saw and approved.

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
