### Title
Blame proof discloses the ECDH key for a message whose proof-of-possession was never verified, leaking the victim's encrypted secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP DKG encrypts each secret share under a per-message ECDH key. A blame proof (`EncryptionKeyProof`) reveals that ECDH shared key so third parties can decrypt an accused message. To prevent an attacker from replaying someone else's ciphertext and thereby tricking a recipient into publishing the ECDH key for a message the attacker could not otherwise read, every `EncryptedMessage` carries a Schnorr proof-of-possession (`pop`) over the per-message key. However, `KeyMachine::calculate_share` returns an `InvalidShare` error carrying a fully-formed blame proof when the decrypted share fails scalar deserialization *before* the queued PoP/`pop` batch verification is ever executed. An attacker can copy an honest sender's `EncryptedMessage` (valid `pop` bound to the original ciphertext), flip ciphertext bytes so `from_repr` fails, and the honest recipient will emit a blame proof revealing `bX` — the ECDH key that also decrypts the *original, unmodified* message — to everyone.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `calculate_share` queues `msg.pop.batch_verify` inside `encryption.decrypt` (encryption.rs:479-485), but the actual `batch.verify_with_vartime_blame()` runs only after the loop at lib.rs:493. Inside the loop, if `C::F::from_repr(share_bytes.0)` fails, the code early-returns `Err(PedPoPError::InvalidShare { participant: l, blame: Some(blame) })` at lib.rs:480-482 — before the batch verifier runs, so the `pop` is never checked.

The blame object is an `EncryptionKeyProof { key, dleq }` built in `Encryption::decrypt` at encryption.rs:487-499, where `key = ecdh(enc_key, msg.key)` — the shared point that feeds `cipher()` to decrypt `msg`. The code comments at encryption.rs:83-90 explicitly describe this exact attack (Eve reusing Alice's key X so Bob's blame reveals `bX`, exposing Alice's message) as "a massive side effect," and the `pop` exists solely to stop it. The early return reintroduces it: Eve copies Alice's honest `EncryptedMessage` addressed to Bob (key `X`, valid `pop` over the original ciphertext), corrupts the ciphertext so the plaintext is not a canonical scalar, and delivers it as her share to Bob. Bob's `calculate_share` emits a blame proof containing `bX` — and since `blame` is serialized and broadcast in `ProcessorMessage::InvalidShare` (processor/src/key_gen.rs:419-425), all participants can now decrypt Alice's original share to Bob.

Note the `pop` binds the ciphertext bytes (`pop_challenge` includes `msg` at encryption.rs:302-323), which is why the attack requires a path that skips `pop` verification — the deserialization early-return is exactly that path.

### Impact Explanation
Secret-share disclosure. Repeating the attack with each dealer's message to a victim reveals every ECDH key for shares addressed to that victim, recovering the victim's full threshold secret share publicly. A public leaked share reduces the effective threshold: any `t-1` other shares (or compromise of `t-1` participants, or shares recovered via another path) reconstruct the group key. Even a single disclosed share is secret material the protocol guarantees is only ever visible to its intended recipient.

### Likelihood Explanation
Reachable by any DKG participant (or anyone able to deliver a message attributed to a participant index in the authenticated channel) using only copied public ciphertext bytes — no collusion, no malicious validator assumptions beyond a single faulty sender, which the blame protocol explicitly exists to handle. The trigger is deterministic: any non-canonical scalar plaintext causes the early return.

### Recommendation
Verify the `pop` (and the rest of the queued batch for that participant) before returning a blame proof, or don't attach `Some(blame)` when the message's `pop` cannot be confirmed. Simplest fix: perform a synchronous `msg.pop.verify(...)` inside `Encryption::decrypt` before computing/returning `EncryptionKeyProof`, returning a blame-free error if it fails — mirroring `decrypt_with_proof`, which correctly returns `DecryptionError::InvalidSignature` (blaming the sender) before revealing anything.

### Proof of Concept
1. DKG with participants Alice (1), Bob (2), Eve (3). Alice sends `m = EncryptedMessage { key: X, pop, msg: enc(share_to_bob) }` to Bob; Eve observes the serialized bytes on the authenticated channel.
2. Eve copies `m`, flips a byte of `msg` (ciphertext is a ChaCha20 keystream XOR, so any flip malleates the plaintext; with overwhelming probability the result is a non-canonical scalar), and submits the mutated message as her round-2 share to Bob.
3. Bob's `KeyMachine::calculate_share` calls `encryption.decrypt`, queuing `pop.batch_verify` under `BatchId::Decryption(Eve)` — never executed — then `C::F::from_repr` fails at lib.rs:480 and returns `InvalidShare { participant: Eve, blame: Some(EncryptionKeyProof { key: bX, dleq }) }`.
4. `processor/src/key_gen.rs` serializes `blame` into `ProcessorMessage::InvalidShare`, broadcasting `bX` to all participants.
5. Any observer computes `cipher(context, bX)` and applies the keystream to Alice's *original* `msg` ciphertext, recovering the secret share Alice sent to Bob — disclosure of threshold key material that the `pop` was designed to prevent.
