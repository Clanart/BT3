### Title
Hunk-count desync between `extractConflictHunks` and `reassembleResolvedFile` causes silent deletion/misplacement of merge-conflict content - (File: `app/src/lib/copilot-conflict-context.ts` / `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
This is the same bug class as the Sublime `H-02` finding: a value computed under one interpretation (the hunk **count/order** produced by `extractConflictHunks`, which becomes the authoritative index space for the LLM's response and for `validateResolutionPaths`) is later treated as if it were computed under an equivalent, but actually independent, interpretation (the hunk boundaries `reassembleResolvedFile` re-derives by re-scanning the same raw file). The two parsers use non-identical state machines, so on attacker-crafted repository content they can disagree on how many real conflict blocks the file contains. Because reassembly is purely positional/order-based ("matched by order, not by line number" per its own doc comment) with no cross-check against the extraction pass, a desync causes conflict regions to be silently dropped or filled with the wrong model output when Copilot writes the "resolved" file to disk.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks the file once, and whenever a `<<<<<<<` marker is found without a matching `=======`/`>>>>>>>` before EOF, it aborts the current hunk via `continue` at line 240-242. Critically, at that point the inner `while (i < lines.length)` loops used to collect the ours/base/theirs sections have already advanced `i` all the way to `lines.length` (they only stop on a marker match or EOF). The outer `while (i < lines.length)` loop therefore also terminates — any well-formed conflict blocks that exist **after** a single malformed/stray `<<<<<<<`-looking line are never extracted, silently shrinking `hunks.length` for that file. [1](#0-0) 

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) performs an independent re-scan of the same raw content. For each `<<<<<<<` it finds, it does its own bounded lookahead for a separator/closing marker; if that particular block is malformed it copies it through as plain text and simply continues (`i++`) to the *next* line — it does **not** stop scanning the rest of the file the way `extractConflictHunks` effectively does. [2](#0-1) 

As a result, on a file where a stray/unclosed `<<<<<<<`-shaped line precedes a real, well-formed conflict block further down (plausible in documentation, ASCII-art banners, code that itself teaches/quotes git conflict-marker syntax, or minified/generated content), `extractConflictHunks` under-counts the hunks sent to the model, while `reassembleResolvedFile` still finds and tries to splice **all** the real conflict blocks in the file. The only integrity check in between, `validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`), only compares `resolution.hunks.length` against `expectedHunkCounts` derived from the (already under-counted) extraction pass — so it cannot detect the desync. [3](#0-2) 

The consequence surfaces in `reassembleResolvedFile`'s splice loop: for any conflict block beyond `hunkResolutions.length`, `hunkIndex < hunkResolutions.length` is false, so nothing is pushed for that block — the block's entire span (its true "ours"/"theirs" content) is deleted from the reassembled file with no error, warning, or model awareness. [4](#0-3) 

This reassembled content is then written directly to disk and staged via `_applyCopilotConflictResolutions` without any diff review gate other than the user clicking "Continue Merge": [5](#0-4) 

### Impact Explanation
The attacker (author of a branch/PR that the victim merges, rebases, or cherry-picks with GitHub Desktop's Copilot conflict-resolution feature) can craft file content that triggers the extraction/reassembly desync. The result is silent corruption of the committed file: an entire section of legitimate code (potentially a security check, validation, or business logic on either "ours" or "theirs" side) can be deleted from the merge result without the user seeing it flagged as unresolved, and without the model ever being asked to resolve it. This falls squarely under "silent corruption of what the user commits or pushes," since the file is written and staged automatically once the user accepts the dialog.

### Likelihood Explanation
Exploitability requires the attacker to control content that will conflict with the victim's local changes and to place an unclosed/stray 7-character marker sequence (`<<<<<<<`, or embedding real-looking `=======`/`>>>>>>>` sequences) ahead of an actual conflicting region in the same file — plausible in documentation files, changelogs, or code/comments that quote git conflict syntax. It requires no local access, no credentials, and no unnatural steps beyond the normal Desktop workflow of merging a branch and invoking the Copilot-assisted resolution feature and accepting its result, which is the intended feature flow.

### Recommendation
Make `reassembleResolvedFile` reuse the exact same hunk-boundary list produced by `extractConflictHunks` (e.g. have extraction return line offsets for each hunk, or have reassembly call `extractConflictHunks` internally and iterate over its result) instead of independently re-deriving conflict boundaries with a different state machine. Additionally, `validateResolutionPaths`/`reassembleResolutions` should hard-fail (rather than silently skip) whenever the number of conflict blocks encountered during reassembly does not exactly match the number of hunks that were sent to and returned by the model, rather than trusting order-based positional matching alone.

### Proof of Concept
1. Attacker pushes a branch that modifies a file such that, when merged with the victim's local branch, git leaves two real conflict regions in the file, with an unrelated line consisting of exactly seven `<` characters (e.g. from an ASCII banner or a code comment quoting conflict-marker syntax) placed between them but with no matching `=======`/`>>>>>>>` for that stray line before EOF.
2. Victim runs the merge, `getStatus`/`getConflictDetails` reports the conflicted file, and the victim opens the Copilot conflict-resolution dialog.
3. `buildConflictContext` → `extractConflictHunks` scans the file: it finds the first real conflict, then hits the stray unclosed `<<<<<<<`-looking line and, per `hunkEnd === -1` handling, aborts scanning the rest of the file — the second real conflict is never added to `hunks`.
4. Copilot is prompted with only 1 hunk for the file and returns exactly 1 `resolvedContent`; `validateResolutionPaths` sees `1 === 1` and passes.
5. `reassembleResolutions` → `reassembleResolvedFile` independently re-scans `rawContent` from scratch, correctly identifies **both** real conflict blocks (since its per-block lookahead doesn't get stuck on the stray marker), splices the model's single resolution into the first block, and for the second real conflict block finds `hunkIndex (1) < hunkResolutions.length (1)` false — so it discards that entire block's content when writing the final file.
6. `_applyCopilotConflictResolutions` writes this reassembled content to disk and stages it; the victim commits code that is silently missing a whole legitimate section from the merge, without ever having reviewed it as an unresolved conflict. [6](#0-5) [7](#0-6)
