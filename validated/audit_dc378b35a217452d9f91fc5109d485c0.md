## Title
Missing timeout re-check + disjoint receipt namespaces in `HandlerV2` allow a GET request to be both timed-out and responded-to, driving double dispatch to `IsmpModule::onGetTimeout` and `onGetResponse` - ([File: evm/src/core/HandlerV2.sol])

### Summary
The External Report's core defect is a **check performed against a cached/derived value that is trusted to have been validated elsewhere, with no re-verification at the point of use**, letting a downstream consumer act on stale state. The Hyperbridge analog is in `HandlerV2.sol`'s two independent GET-request completion paths — `handleGetResponses` and `handleGetRequestTimeouts` — which each maintain their **own** receipt namespace (`responseReceipts` vs. the timeout dispatch path) and neither cross-checks the other before calling into the destination `IsmpModule`. `handleGetResponses` explicitly skips the timeout check with the comment "don't check for timeouts because it's checked on Hyperbridge," trusting a validation that happened on a different chain, at a different (earlier) point in time, against a different clock.

### Finding Description
In `evm/src/core/HandlerV2.sol`: [1](#0-0) 

`handleGetResponses` never checks `leaf.response.request.timeout()` against `block.timestamp`. Its only anti-replay guard is:
```
if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
```

Separately, `handleGetRequestTimeouts` checks the timeout and non-membership proof, then dispatches the timeout: [2](#0-1) 

These are two disjoint code paths writing to two disjoint markers (`responseReceipts` populated by `dispatchIncoming` for responses vs. whatever `dispatchTimeOut` marks for timeouts). Nothing in `handleGetResponses` checks whether the *same request* has already had `handleGetRequestTimeouts` executed for it, and nothing in `handleGetRequestTimeouts` checks whether a response has already been delivered. Both paths are permissionless and callable by anyone holding a valid Hyperbridge-side proof.

The trust assumption baked into the "don't check … it's checked on Hyperbridge" comment is the same class of bug as the Evoq report: a critical invariant (has this GET request already reached a terminal state?) is assumed to hold based on a check performed in a different execution context (Hyperbridge's own timeout validation at response-construction time) rather than being re-verified against the actual current state of the consuming chain at dispatch time. Once Hyperbridge constructs a `GetResponse` (valid at Hyperbridge's timestamp), that response remains deliverable to the EVM destination indefinitely and independently of whatever happens locally on that destination chain afterward — including a local timeout having already fired.

### Impact Explanation
Any `IsmpModule` on an EVM host that performs state changes (fund release, refund, escrow settlement) in **both** `onGetTimeout` and `onGetResponse` for the same class of GET query is exposed to two independent execution attempts against the same underlying request — a logic/double-settlement pattern. The Intent Gateway's cancel-from-source flow is exactly this shape: it dispatches a `GetRequest` (`DispatchGet`) to check the destination's fill status, and depending on which result arrives (timeout vs. non-membership response) drives a refund path. Because `handleGetResponses` performs no timeout check and uses a receipt namespace independent from the timeout path's completion marker, a relayer can potentially get a request processed on the timeout path and, before/after, also successfully deliver a valid Hyperbridge-signed response for the same request, invoking the module's response handler a second time. This falls squarely in the "replay/double-claim/double-settlement" and "unauthorized transaction/execution" bounty categories — funds could be released twice or state transitioned inconsistently, depending on whether the specific module's own bookkeeping (e.g., an internal `_filled`/`claimed` flag) happens to catch the second call. This is a protocol-level gap in the shared `Handler`, not a module implementation bug, so any current or future `IsmpModule` that doesn't defensively re-derive completion state is at risk.

### Likelihood Explanation
Both `handleGetResponses` and `handleGetRequestTimeouts` are explicitly permissionless entry points (`external`, no access control beyond `notFrozen`), and both only require a relayer to submit a valid Merkle/trie proof they can obtain from Hyperbridge's own indexed/offchain data — no malicious peer, prover, or admin action is needed. The race only requires ordinary network conditions (proof for one path becoming available before/after the other), which is realistic given Hyperbridge's asynchronous relayer model.

### Recommendation
- In `handleGetResponses`, re-check `request.timeout()` against `block.timestamp` before dispatching, consistent with `handlePostRequests`'s explicit `MessageTimedOut()` check, rather than relying on Hyperbridge's earlier validation.
- Unify the completion marker for a GET request's lifecycle: `handleGetRequestTimeouts` and `handleGetResponses` should consult and set the **same** commitment-keyed receipt so that whichever path executes first permanently forecloses the other (`DuplicateMessage`/`MessageAlreadyTimedOut`-style mutual exclusion), mirroring the "one-time receipt handling" principle already applied to POST requests via `requestReceipts`.

### Proof of Concept
Exact reproduction requires tracing `IntentGatewayV2`'s specific `withdraw()`/`_filled` guard interaction with `onGetTimeout`/`onGetResponse`, which I was not able to fully verify within the available context (I confirmed the `HandlerV2.sol` dual-path gap directly, but did not fully read `IntentGatewayV2.sol`'s internal dedup logic to confirm whether its own state guard independently closes this gap for that specific module). At the `Handler` level, the concrete sequence is:
1. A GET request is dispatched from an EVM app expecting a state check on another chain (e.g., cancel-from-source fill-status query).
2. Its `timeout_timestamp` elapses on the source/destination chain.
3. A relayer submits `handleGetRequestTimeouts` with a valid non-membership proof — the module's `onGetTimeout` fires (e.g., refund).
4. Separately (before or after), Hyperbridge had already (or later) constructed a valid `GetResponse` for the same request (valid per Hyperbridge's own clock at construction time). A relayer submits this via `handleGetResponses`, which does not re-check the timeout and only guards against replaying the *same* response commitment — this succeeds because it's the first response delivery, and the module's `onGetResponse` fires (e.g., a second refund path), since `handleGetResponses` never checked whether the request had already been finalized via the timeout path.

Given the significant uncertainty about whether `IntentGatewayV2`'s own commitment-marking (`_filled[commitment]`) independently prevents the double payout in this specific module, this should be treated as a **protocol-level gap requiring confirmation against each consuming `IsmpModule`**, not a proven exploit against a named module.

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }

    /**
     * @dev Check the provided Get request timeouts, then dispatch to modules
     * @param host - Ismp host
     * @param message - batch get request timeouts
     */
    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }
}
