### Title
Attacker-controlled interpolation tag and coefficients in `ThresholdKeys::read` decouple the reported group key from the loaded secret share - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a 1-byte interpolation tag and, when the tag is `0` (`Interpolation::Constant`), reads `n` fully attacker-controlled field coefficients directly from the input. `ThresholdKeys::new` then computes `group_key` as a linear combination of the (also attacker-supplied) verification shares weighted by these coefficients, without ever checking that the coefficients are consistent, that the secret share corresponds to its verification share, or that the resulting group key is actually reconstructible by the declared threshold of shares. This mirrors the advisory's bug class: a parameter in attacker-influenced data selects an unsafe interpretation path (arbitrary "class" of interpolation with attacker-supplied behavior-defining values).

### Finding Description
`ThresholdKeys::read` reads a discriminant byte and dispatches on it:

```rust
// crypto/dkg/src/lib.rs:604-616
let mut interpolation = [0];
reader.read_exact(&mut interpolation)?;
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
  1 => Interpolation::Lagrange,
  _ => Err(io::Error::other("invalid interpolation method"))?,
};
```

The `Constant` variant carries a coefficient vector used verbatim as interpolation weights:

```rust
// crypto/dkg/src/lib.rs:226-229
Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
```

The group key is then derived directly from those attacker-chosen coefficients and attacker-chosen verification shares:

```rust
// crypto/dkg/src/lib.rs:376-378
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

The only validations performed are:
- `verification_shares.len() == n` and participant indexes `<= n` (lines 355-365),
- `t == n` when `Constant` is used (lines 367-372).

There is **no check** anywhere that `C::generator() * secret_share` equals the interpolated verification share for `params.i`, nor that the coefficients produce a group key consistent with what the shares interpolate to under any standard rule. A well-formed honest serialization only ever emits `Constant` coefficients matching the DKG output, but the deserializer accepts arbitrary ones.

### Impact Explanation
An unprivileged party who can get a `ThresholdKeys` blob loaded (the scan's threat model explicitly includes untrusted bytes passed to `ThresholdKeys::read`) can craft a blob where:

1. `group_key` — the key the node reports, registers, and receives funds to — is an arbitrary point, e.g. set all coefficients to `0` except one and choose `verification_shares` so `group_key` equals a key the attacker controls, or a key nobody controls.
2. The loaded `secret_share` is inconsistent with the node's own `verification_share`. When the node later calls `view(...)` and produces a FROST signature share, `interpolation_factor` returns the attacker's coefficient `c[i-1]`; the share either fails verification (blame attributed to this node) or, if the attacker constructed the shares consistently, produces signatures for a group key whose discrete log the honest node never actually held a share of.

Concretely this yields the "funds reported received that are not spendable" impact class: the processor/scanner derives the deposit address from `group_key()` (line 445-447), while the loaded shares cannot produce a valid signature under an honest interpolation, so outputs to that address are unspendable — or spendable only by the attacker if they arranged `group_key` to be their own key. With `read_G` accepting any encoded point, combined with arbitrary `c[i]`, the attacker has full control of the reported group key.

### Likelihood Explanation
Reachability requires getting a crafted serialization to `ThresholdKeys::read`, which is the explicitly in-scope untrusted-input sink for this audit (e.g. keys restored/imported from external data rather than produced by the local PedPoP DKG). The exploit needs no collusion, no valid shares, and no knowledge of any secret — all fields in the blob (tag, coefficients, `t`/`n`/`i`, share, verification shares) are attacker-chosen, constrained only by `t == n` for the `Constant` path. Since `Lagrange` blobs are also fully attacker-defined except the tag byte, the variant merely widens the degree of freedom rather than being required. Likelihood is bounded by how `ThresholdKeys::read` is exposed to untrusted input in deployment, so this is a **High** (not Critical) analog: the cryptographic flaw (unvalidated behavior-defining parameters selecting an interpretation path) is direct, but exploitation requires the import path to be attacker-influenced.

### Recommendation
- In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&params.i] * interpolation_factor(params.i, &[all participants 1..=n])` (the share must actually be a consistent share of the computed group key).
- Consider rejecting `Interpolation::Constant` on deserialization unless the deployment explicitly uses non-Lagrange DKG, or at minimum reject coefficient vectors that are all-zero / produce an identity `group_key` (reject `group_key == identity`).
- Reject `read` blobs whose recomputed properties are inconsistent rather than trusting serialized parameters, the same way `C::ID` is already checked at lines 578-588.

### Proof of Concept
Conceptual, for any in-scope `C: Ciphersuite` (e.g. `Secp256k1` / `Ristretto`):

```rust
// Attacker chooses their own key k_att, and wants victim's node to report
// group_key = k_att * G while holding an unrelated share.
let n: u16 = 2; // t == n required for Constant
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(n.to_le_bytes());           // t
blob.extend(n.to_le_bytes());           // n
blob.extend(1u16.to_le_bytes());        // i = 1
blob.push(0);                           // <-- Constant interpolation tag

// Coefficients: c[0] = 1, c[1] = 0 -> group_key = verification_shares[1] * 1
blob.extend(C::F::ONE.to_repr().as_ref());
blob.extend(C::F::ZERO.to_repr().as_ref());

// Victim's share (arbitrary; never validated against verification share)
let share = C::random_F(&mut rng);
blob.extend(share.to_repr().as_ref());

// verification_shares[1] = attacker pubkey; verification_shares[2] = anything
blob.extend((C::generator() * k_att).to_bytes().as_ref());
blob.extend((C::generator() * C::random_F(&mut rng)).to_bytes().as_ref());

let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
assert_eq!(keys.group_key(), C::generator() * k_att); // attacker-controlled key reported
// Node now scans for/receives funds to k_att*G which it cannot sign for,
// while believing it holds share `share` of a 2-of-2 it never agreed to.
```

The construction passes every check in `ThresholdKeys::new` and `ThresholdParams::new`, demonstrating that the tag byte plus coefficient vector function as an attacker-controlled dispatch into arbitrary interpolation behavior, directly analogous to URL parameters triggering loading of arbitrary classes.
