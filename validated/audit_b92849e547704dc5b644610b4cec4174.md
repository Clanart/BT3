### Title
Fee calculation omits the OP_RETURN data output, so transactions with data underpay the intended fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` is designed to build a transaction paying `fee_per_vbyte * vbytes` as its fee. However, the weight/vbyte estimate used to derive `needed_fee` is computed only over `payments` (and optionally `change`), never over the OP_RETURN output carrying `data`. As a result, transactions that embed data are assigned a fee calculated for a smaller transaction than the one actually signed — analogously to the wagmi report, the intended charge is computed from an incomplete base, so part of it is never collected.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` before the weight is estimated:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds a mock `Transaction` containing only `payments` (plus an optional `change` output) — it has no parameter for the data output, so the OP_RETURN output's ~11–92 bytes are excluded from `vbytes` in both the no-change call (line 204) and the change call (lines 225–226). The final transaction therefore pays `fee_per_vbyte * (vbytes_without_op_return)`, i.e., strictly less than the caller-requested fee rate, exactly mirroring "the user is charged fewer fees than required."

The same omission also means the `NotEnoughFunds` check (`input_sat < payment_sat + needed_fee`) and the change-vs-dust decision (`input_sat.checked_sub(payment_sat + fee_with_change)`) are evaluated against an understated fee.

### Impact Explanation
Any `SignableTransaction` created with `data: Some(..)` pays a fee rate below `fee_per_vbyte`. The shortfall is up to ~80 vbytes × `fee_per_vbyte`. At best this is an accounting discrepancy between the intended and actual fee rate; at worst, the produced transaction falls under the network's minimum relay fee or sits unconfirmed, since `TooLowFee` is checked against the underestimated `needed_fee`. This is a reachable, deterministic formula error in an incorrect-fee-verifier class: reachable via the public `SignableTransaction::new` API with attacker/integrator-supplied `data`.

### Likelihood Explanation
Deterministic: every call that passes `Some(data)` underpays. The only mitigating case is the no-change path where the entire leftover is burned as fee anyway — but whenever a `change` output is created (the normal wallet flow), the change amount absorbs the remainder and the effective fee is exactly the underestimated `fee_with_change`.

### Recommendation
Include the OP_RETURN output in the weight estimate. Either pass the full output list (payments + data + change) to `calculate_weight_vbytes`, or add a `data_len`/`has_data` parameter so the mock transaction includes the `TxOut` with the OP_RETURN script before computing `weight`/`vbytes`. Both call sites (lines 204 and 225–226) must account for it, or the helper should be restructured to take `&[TxOut]` directly.

### Proof of Concept
```rust
// Conceptual, against networks/bitcoin/src/wallet/send.rs
let data = vec![0u8; 80];
let tx_with_data = SignableTransaction::new(
  inputs.clone(), &payments, Some(change_addr.clone()), Some(data.clone()), FEE,
).unwrap();
let tx_without_data = SignableTransaction::new(
  inputs, &payments, Some(change_addr), None, FEE,
).unwrap();

// needed_fee is identical despite the ~90-byte OP_RETURN output
assert_eq!(tx_with_data.needed_fee(), tx_without_data.needed_fee());
// => effective fee rate of tx_with_data < FEE sats/vbyte
```
