## Finding: `testForInvalidChars` does not reject leading `-`/`--`, unlike its sibling `sanitizedRefName`

### Summary
`testForInvalidChars` in `app/src/lib/sanitize-ref-name.ts` reuses the same `invalidCharacterRegex` as `sanitizedRefName`, but that regex only rejects git's disallowed ref characters (control chars, space, `~^:?*[\|"<>`, `@{`, `..`, leading/trailing `.`, `.lock` suffix, trailing `/`). [1](#0-0) 

Crucially, `sanitizedRefName` additionally strips any leading `-`/`+` after applying the regex (`.replace(/^[-\+]*/g, '')`), but `testForInvalidChars` does not perform this extra step — it purely tests the raw regex. [2](#0-1) 

### Finding Description
`testForInvalidChars` is the validator used on the `branch` query parameter of the `x-github-desktop://openRepo/...` deep link handler in `parseAppURL`: if it returns `true` the whole action is discarded, otherwise the raw string is accepted as-is (no sanitization applied) and placed into `IOpenRepositoryFromURLAction.branch`. [3](#0-2) 

Because the regex does not include `-`, a value such as `--orphan`, `--detach`, `-b`, or any other string beginning with `-`/`--` passes validation untouched and is forwarded downstream as `branch`. In `dispatcher.ts`, that value flows into `openBranchNameFromUrl` → `checkoutLocalBranch(repository, branchName)` after a clone/fetch. [4](#0-3) 

Elsewhere in the codebase, values ultimately used as git argv operands (e.g. `checkoutBranch`'s `getBranchCheckoutArgs`) place the ref name as a **bare, un-prefixed positional argument before the terminating `--`** [5](#0-4) , which means a dash-leading string reaching that point would be parsed by `git checkout` as an option rather than an inert ref operand — exactly the "argv/flag injection" pattern the invariant is testing for.

### Impact Explanation
I was not able to fully trace `checkoutLocalBranch`'s implementation (only its two call sites in `dispatcher.ts` were found within my exploration budget) to confirm whether it re-validates/sanitizes the branch string, or constructs a `Branch` object with the raw attacker string that then reaches `getBranchCheckoutArgs` as a bare positional argument. This is a real gap and worth closing regardless, but I could not confirm a concrete path to **Critical** impact (arbitrary code execution or file read/write outside the repo): `git checkout` has no known flag equivalent to `--upload-pack=<cmd>` (which is the classic git-argument-injection RCE primitive for `clone`/`fetch`); the worst confirmed-reachable outcomes from a leading-dash branch name here would be checkout behavior being reinterpreted as an unrecognized/different flag (e.g. `--orphan`, `--detach`), most likely causing an error rather than code execution.

### Likelihood Explanation
The gap is real and easily demonstrated: `testForInvalidChars('--evil')` returns `false` (no invalid chars detected), while `sanitizedRefName('--evil')` strips the leading dashes to `'evil'` — i.e. the two functions disagree on what's "safe", and only the weaker one gates the deep-link branch parameter. [2](#0-1)  This is confirmed by existing tests only exercising invalid *characters* (e.g. `<>`), not leading dashes. [6](#0-5) 

### Recommendation
Make `testForInvalidChars` reject (or `sanitizedRefName`-equivalent-strip) any value beginning with `-`/`+`/`--`, consistent with `sanitizedRefName`'s trailing `.replace(/^[-\+]*/g, '')` step, so both functions enforce the same invariant. Additionally, audit every call site that passes a `testForInvalidChars`-validated string into a `git` argv (`checkoutLocalBranch` and its downstream `getBranchCheckoutArgs`) to ensure attacker-controlled ref/branch names are always passed after a literal `--` separator or as the explicit value of a flag, never as a bare leading positional argument.

### Proof of Concept
```ts
import { testForInvalidChars, sanitizedRefName } from '../../src/lib/sanitize-ref-name'

testForInvalidChars('--orphan')   // false — treated as a "valid" ref name
sanitizedRefName('--orphan')      // 'orphan' — dash stripped by the sibling function
```
A deep link such as `x-github-desktop://openRepo/https://github.com/org/repo?branch=--orphan` passes the `testForInvalidChars` gate in `parseAppURL` [7](#0-6)  and is forwarded unmodified as `action.branch` to `openBranchNameFromUrl`. [8](#0-7) 

**Caveat:** I could not verify, within the available exploration, that `checkoutLocalBranch` places this string as an unguarded positional argv token to `git`. Without that confirmation, I can validate the *input-side* flaw (inconsistent validation vs. `sanitizedRefName`) but cannot confirm the full argv-injection chain reaches a Critical-impact sink. This would need to be verified in a live/Devin session by reading `checkoutLocalBranch`'s full implementation and any intermediate `Branch` construction logic.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
