### Title
`VerifyBlame` swaps sender/recipient, letting an accuser choose which participant gets blamed via a self-authored share message — ([File: processor/src/key_gen.rs](processor/src/key_gen.rs))

### Summary
The PedPoP blame API is `blame(sender, recipient, msg, proof)`, where `sender` is the author of the encrypted share and `recipient` is the decryptor whose registered encryption key is used to verify the `EncryptionKeyProof` DLEq. The `VerifyBlame` handler in `key_gen.rs` invokes it as `.blame(accuser, accused, ...)`, passing the *accuser* as `sender` and the *accused* as `recipient` — the reverse of the real message direction (the accused sent the share; the accuser received it). Because the blamed party is derived from whichever role fails the checks, and the caller controls the `accused` field, an attacker can pin blame on an arbitrary participant — the same privilege-escalation shape as Strimzi's attacker-controlled `watchedNamespace` granting authority over a foreign scope.

### Finding Description
In `processor/src/key_gen.rs:504-564`, `CoordinatorMessage::VerifyBlame { accuser, accused, share, blame }` builds `AdditionalBlameMachine`s and calls `.blame(accuser, accused, substrate_share, substrate_blame)` / `.blame(accuser, accused, network_share, network_blame)`. [1](#0-0) 

But `AdditionalBlameMachine::blame`/`BlameMachine::blame` take `(sender, recipient)` — sender = the participant whose `EncryptedMessage` this is, recipient = the decryptor. [2](#0-1) 

`blame_internal` then does two things with these swapped roles:
1. `decrypt_with_proof(sender, recipient, msg, proof)` verifies the message PoP with `from = sender` — i.e., it expects the PoP challenge bound to the *accuser's* index. A genuine message from `accused` to `accuser` has `from = accused`, so an honest accusation fails `pop.verify` → `InvalidSignature` → returns `sender` = **accuser is blamed**, punishing the honest reporter. [3](#0-2) 
2. The proof path uses `self.enc_keys[&decryptor]` where `decryptor = recipient = accused`. [4](#0-3)  An accuser cannot produce the DLEq proving the shared ECDH point for the accused's encryption key (they don't know the accused's `enc_key` scalar), so any `InvalidProof` → returns `recipient` = **accused is blamed**. [5](#0-4) 

Attack path: a malicious participant authored a valid `EncryptedMessage` share to victim `V` during the DKG (its `pop` is bound to `sender = attacker`). The attacker submits `VerifyBlame { accuser: attacker, accused: V, share: <attackers own msg to V>, blame: <garbage/None> }`. `pop.verify` succeeds because `from = accuser` matches the PoP's bound sender (the message genuinely is the attacker's). The DLEq then fails because the proof must demonstrate `proof.key == V_enc_priv * msg.key`, unknown to the attacker → `InvalidProof` → `blame_internal` returns `recipient` = `V`. `key_gen.rs` sees `substrate_blame == accused` and emits `ProcessorMessage::Blame { participant: V }`, blaming an honest validator. [6](#0-5) 

The PoP does bind the sender index into the challenge via `pop_challenge::<C>(context, nonce, key, sender, msg)` — so the attacker cannot replay *V's* messages, only their own — but that is exactly sufficient here. [7](#0-6) 

### Impact Explanation
`VerifyBlame` exists to arbitrate `InvalidShare` accusations; a `Blame` result against a participant is the mechanism used to slash/fault validators for DKG misconduct. A malicious DKG participant can cause an arbitrary honest participant to be recorded as faulty — an unprivileged party gaining authority (punishment) over a participant outside their own scope, matching the cross-scope escalation class. The converse direction also breaks honest use: a truthful accuser reporting a genuinely invalid share is themselves blamed, since `pop.verify` fails under `from = accuser` and the code returns `sender` = accuser. Both outcomes destroy the accountability the blame protocol is supposed to provide, at cost of the victim's stake/reputation.

### Likelihood Explanation
Reachability requires only that the attacker participated in a key generation (holding a valid `EncryptedMessage` they authored) and can trigger a `VerifyBlame` arbitration — a routine protocol message, not a privileged operation. The exploit needs no cryptographic break: one malformed/absent `EncryptionKeyProof` plus one correctly-signed-by-them share message. The swapped-argument defect is deterministic, not probabilistic.

### Recommendation
Swap the arguments in `key_gen.rs` to `.blame(accused, accuser, share, blame)` so `sender = accused` (the share's real author) and `recipient = accuser` (the decryptor who produced the proof). Additionally, as defense in depth, `blame_internal` could verify that `msg`'s authenticated sender actually equals the `sender` parameter before attributing fault — the PoP already binds `sender` into the challenge, but nothing checks that the claimed `sender`/`recipient` roles correspond to a real share flow between those parties; a missing-proof `InvalidProof` should arguably fault the accuser (bad proof), not blanket-blame `recipient`.

### Proof of Concept
1. Attacker `A` and victim `V` participate in a PedPoP key generation. `A` produces shares; `A`'s share to `V` is `msg_A→V`, whose `pop` was signed with `pop_challenge(context, R, key, sender=A, msg)`. [8](#0-7) 
2. `A` sends `VerifyBlame { accuser: A, accused: V, share: msg_A→V, blame: None }`.
3. Processor reads `msg_A→V` via `EncryptedMessage::read`, builds `AdditionalBlameMachine`, calls `blame(sender=A, recipient=V, msg_A→V, None)`.
4. `decrypt_with_proof(from=A, decryptor=V, msg, None)`: `pop.verify` succeeds (challenge uses `sender=A`, matching the PoP); `proof is None` → `Err(InvalidProof)`.
5. `blame_internal` returns `recipient` = `V`; both `substrate_blame` and `network_blame` equal `V`.
6. `substrate_blame == accused` → `ProcessorMessage::Blame { participant: V }` — `V` is recorded faulty despite doing nothing wrong.

The same shape is reproduced in the crate's own blame test where `blame(ONE, TWO, ...)` relies on `sender=ONE` being the true author — `key_gen.rs` violates that precondition by passing `accuser` in the `sender` position. [9](#0-8) 

Caveat: I could not fully trace the coordinator-side message flow (`coordinator/src/tributary/handle.rs` matched but wasn't read) to confirm how `VerifyBlame` is dispatched and whether the coordinator performs an additional ordering check before the processor call; the mis-ordered invocation itself at `key_gen.rs:543-556` is confirmed in the code above.
