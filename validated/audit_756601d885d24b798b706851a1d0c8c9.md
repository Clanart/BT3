Based on my research, the strongest local analog to the ZetaChain "aborted CCTX / no refund" bug-class is in Hyperbridge's IntentGatewayV2 cross-chain settlement path, where the escrow-withdrawal finalization logic can be driven into a state where a legitimate `RedeemEscrow` settlement message permanently reverts, leaving the party owed funds (the solver) unable to ever collect them, while the counterparty message can already have released the same escrow.

### Title
Cross-chain escrow settlement race lets a fill and a cancel both target the same escrow, permanently reverting the losing message and stranding solver funds - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_fillCrossChain` and `_cancelFromDest` are two independent, unprivileged entry points that each unconditionally dispatch a settlement `PostRequest` (`RedeemEscrow` / `RefundEscrow`, both with `timeout: 0`, i.e. never expiring) targeting the same order `commitment` on the source chain [1](#0-0) [2](#0-1) . Both messages are independently authenticated on the source chain and routed to the shared `_withdraw()` finalizer [3](#0-2) . `_withdraw()` zeroes `_orders[commitment][token]` and reverts with `UnknownOrder()` for any subsequent call once escrow reaches zero [4](#0-3) . Whichever of the two settlement messages lands first on the source chain wins the entire escrow; the second message becomes permanently unprocessable — mirroring the ZetaChain report's core defect: once a competing/erroring execution path claims or reverts the settlement, there is no fallback to make the rightful party whole.

### Finding Description
On the destination chain, a solver calls the fill path which immediately delivers output tokens to the beneficiary and marks `_filled[commitment] = msg.sender`, then dispatches a `RedeemEscrow` message to the source-chain gateway with `timeout: 0` [5](#0-4) . Separately, `_cancelFromDest` — reachable by the order owner before the deadline, or by anyone after it — marks `_filled[commitment] = user` and dispatches a `RefundEscrow` message to the same source-chain gateway, also with `timeout: 0` [2](#0-1) . Neither of these destination-side functions references the other's `_filled` write before proceeding to build and dispatch its own settlement message.

On the source chain, `onAccept()` treats `RedeemEscrow` and `RefundEscrow` identically at the authentication layer — it only checks that the message came from the registered gateway instance for the declared source chain (`_authenticate`), not that it is the *first or only* settlement message for that commitment [3](#0-2) . Both message kinds funnel into `_withdraw(body, isRefund, true)`, which decrements the per-token escrow (`_orders[commitment][token] -= amount`) and transfers to whichever `beneficiary` is encoded in that particular message [4](#0-3) . The escrow accounting has no compare-and-lock against `_filled`: it is guarded purely by `if (escrowed == 0) revert UnknownOrder()`.

Because both messages are dispatched with `timeout: 0` (never expiring), both are guaranteed to eventually reach the source chain and be delivered via the permissionless `handlePostRequests()` path [6](#0-5) . Whichever lands first fully drains the escrow to its own beneficiary. The second one — corresponding to the party who did *not* win the race — hits `UnknownOrder()` and reverts every time it is resubmitted, exactly like ZetaChain's aborted CCTX: the transaction is rejected after the point where an off-chain party already acted on the expectation of settlement (the solver already handed over output tokens to the user's beneficiary on the destination chain), and there is no automatic mechanism to make the solver whole once the competing `RefundEscrow` claims the escrow first.

I was not able to fully verify, within the available context, whether the public `fillOrder`/`cancelOrder` wrapper functions gate `_fillCrossChain`/`_cancelFromDest` on a fresh check of `_filled[commitment] == address(0)` immediately before dispatch (only the internal functions' bodies were inspected). If such a check exists and is race-free, the window narrows to same-block/same-mempool front-running of the two destination-chain calls; if it does not fully close the window (e.g., a fill transaction and a cancel transaction from an already-expired order both pass their local guards in the same block), the race described above is directly exploitable by an unprivileged solver or order owner with no relayer, prover, or admin collusion required.

### Impact Explanation
If the race is realizable, this results in exactly the loss/misdirection-of-funds impact required by the bounty: the solver delivers real output tokens to the order beneficiary and never receives the escrowed input tokens it was promised, because the second-arriving settlement message reverts permanently and non-recoverably (`UnknownOrder()` on every retry, since escrow is already zero). Depending on which message wins, the *user* can additionally take back the escrowed inputs via `RefundEscrow` after already receiving the solver's output tokens — a wrong-beneficiary, double-payout outcome. This is a direct instance of "stealing or loss of funds" and "wrong beneficiary or amount" from the impact gate.

### Likelihood Explanation
Both settlement dispatches use `timeout: 0`, so there is no time pressure forcing a particular ordering — an attacker (a malicious order owner) only needs to submit a cancel transaction that reaches the destination chain in the same block/near-simultaneously as a solver's fill transaction, or immediately after a fill but exploiting any latency/ordering gap in the guard check on the destination chain, to create two competing in-flight cross-chain messages. Given `_cancelFromDest` becomes callable by *anyone* once `order.deadline < block.number`, and fills of near-deadline orders are common, the race window is realistic without needing a compromised relayer, prover, or governance actor — satisfying the "unprivileged attacker" requirement.

### Recommendation
Make settlement finalization idempotent and race-safe end-to-end:
1. On the destination chain, require both `_fillCrossChain` and `_cancelFromDest` to atomically check-and-set `_filled[commitment]` from `address(0)` in one guarded step immediately before dispatch, with no daylight between the check and the state write within the same call, so a fill and a cancel cannot both be dispatched for the same commitment.
2. On the source chain, make `_withdraw` reject or safely no-op a second settlement message that arrives for the same commitment once it has already been finalized by tracking a per-commitment "settled" flag distinct from the per-token escrow balance, rather than relying solely on `escrowed == 0`.
3. Add a recovery path so that if a `RedeemEscrow`/`RefundEscrow` message ever reverts because the commitment was already settled by the competing message, the losing party (typically the solver) has an on-chain mechanism to reclaim value, instead of the message permanently reverting into a stuck, unrecoverable state — analogous to fixing ZetaChain's missing abort-refund mechanism.

### Proof of Concept
1. User places a cross-chain order on chain A with `deadline = D`.
2. At block `D+1`, a solver on chain B calls the fill path: it delivers output tokens to the user's beneficiary address on chain B, sets `_filled[commitment] = solver`, and dispatches `RedeemEscrow{commitment, beneficiary: solver}` to chain A with `timeout: 0` [5](#0-4) .
3. In the same block window (deadline already passed, so anyone may cancel), a third party or the user calls the cancel-from-destination path, which sets `_filled[commitment] = user` and dispatches `RefundEscrow{commitment, beneficiary: user}` to chain A with `timeout: 0` [2](#0-1) .
4. Both messages are permissionlessly relayed and delivered to chain A's `onAccept()`, which does not enforce any commitment-level exclusivity beyond source-module authentication [3](#0-2) .
5. Whichever message is delivered/proven first calls `_withdraw()`, decrements `_orders[commitment][token]` to zero, and pays out its `beneficiary` [4](#0-3) . If `RefundEscrow` wins, the user receives both the solver's output tokens (from step 2) and the refunded input escrow (from step 5) — the solver is left with nothing and the still-pending `RedeemEscrow` message will revert with `UnknownOrder()` forever on retry.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
