### Title
Unbounded allocation driven by attacker-controlled `n` in `ThresholdKeys::read` enables memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the serialized `n` field (a `u16` read directly from untrusted bytes) and immediately performs `Vec::with_capacity(usize::from(n))` and a `HashMap` insert loop sized by `n`, before the stream has been shown to contain the corresponding `n` scalars and `n` points. This is the same bug class as CVE-2017-17885 (a crafted input causing excessive memory consumption / denial of service): a short, crafted buffer forces a multi-megabyte allocation per call, and repeated calls exhaust memory.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` deserializes `(t, n, i)` from the reader, then:

```rust
// crypto/dkg/src/lib.rs:607-613
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
```

and later:

```rust
// crypto/dkg/src/lib.rs:620-623
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
```

`n` is entirely attacker-controlled (up to 65535). When `interpolation == 0`, `Vec::with_capacity(n)` allocates `65535 * size_of::<C::F>()` (~2–4 MB) before a single byte of scalar data has been read. Even when the stream is truncated, the capacity allocation has already occurred. Additionally, the `HashMap` growth and the `ThresholdParams::new(t, n, i)` validation happen *after* the reads and allocations, so invalid parameters still cost the full allocation.

An attacker only needs to supply the fixed header (curve ID, `t`, `n = 0xffff`, `i`, interpolation tag `0`) — a handful of bytes — to force each call to allocate several megabytes and iterate up to 65535 times performing `read_G`/`read_F` decode work before erroring.

### Impact Explanation
`ThresholdKeys::read` is in the set of functions explicitly exposed to untrusted bytes (per the engagement's reachability model). Repeated invocations with crafted inputs let an unprivileged party force sustained multi-megabyte allocations and O(n) deserialization work per tiny message, exhausting process memory or starving the allocator — a denial of service identical in class to the upstream `ReadPICTImage` memory-leak DoS. Allocated-but-uninitialized memory and the `HashMap` may also persist in error paths/caches depending on the caller.

### Likelihood Explanation
Any code path that calls `ThresholdKeys::read` on bytes influenced by an external party (e.g., key material passed across process boundaries, recovered key blobs, or inputs forwarded by peers) is triggerable with a ~15-byte payload. The cost asymmetry (bytes sent vs. memory allocated) is roughly three orders of magnitude per call, making amplification trivial. It does not require a valid signature, proof, or participant index — the allocation precedes all validation in `ThresholdParams::new`/`ThresholdKeys::new`.

### Recommendation
- Validate `n` against `ThresholdParams::new(t, n, i)` (or at minimum `t <= n <= MAX_PARTICIPANTS`) *before* any `with_capacity` or read loop.
- Replace `Vec::with_capacity(usize::from(n))` with incremental `push` (no upfront capacity), so allocation tracks bytes actually present in the stream — mirroring the chunked-read mitigation already used in `networks/ethereum/src/machine.rs` `Call::read` for the identical bug class.
- Apply the same ordering to the `verification_shares` loop, and bound it by the validated `n`.

### Proof of Concept
```rust
use std::io;
use frost::curve::Ristretto; // any Ciphersuite
use frost::ThresholdKeys;

fn main() {
  // Minimal crafted buffer: curve ID, t=1, n=0xffff, i=1, interpolation=0 (Constant)
  let mut buf: Vec<u8> = vec![];
  let id = <Ristretto as frost::curve::Ciphersuite>::ID;
  buf.extend(u32::try_from(id.len()).unwrap().to_le_bytes());
  buf.extend(id);                       // matches C::ID check
  buf.extend(1u16.to_le_bytes());       // t
  buf.extend(u16::MAX.to_le_bytes());   // n = 65535 -> attacker-chosen
  buf.extend(1u16.to_le_bytes());       // i
  buf.push(0);                          // Interpolation::Constant -> with_capacity(65535)
  // No further bytes needed: the ~2-4MB capacity allocation happens immediately,
  // then read_F fails on the empty remainder.

  let _ = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
  // Loop this call in a harness; each iteration allocates multiple MB before erroring.
}
```
