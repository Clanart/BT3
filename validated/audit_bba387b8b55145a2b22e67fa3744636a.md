### Title
Explicit disabling of Git's embedded-`.git`-directory clone protection via `GIT_CLONE_PROTECTION_ACTIVE: 'false'` - (File: `app/src/lib/git/clone.ts`)

### Summary
The `clone()` function hardcodes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment passed to `git clone --recursive`, explicitly turning off Git's built-in defense against embedded/symlinked `.git` directories being planted by a malicious repository or submodule during a recursive clone.

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself uses to signal that its clone-time protections against symlinked/embedded `.git` directories (the class of issue fixed upstream as CVE-2024-32002/CVE-2024-32004-adjacent hardening) are in effect while recursing into submodules. In `clone()` the code builds: [1](#0-0) 

Here `env` is spread from `envForRemoteOperation(url)` and then the code unconditionally overrides/sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, and the args always include `--recursive`. There is no code path where this value is conditionally computed — it is a static override applied to every clone GitHub Desktop performs. `envForRemoteOperation` itself only adds authentication and proxy env vars and has no relation to this flag: [2](#0-1) 

There is no other check elsewhere in the file, or in `isClonePathSensitive`, that substitutes for Git's own embedded-directory protection — that function only guards against the *destination* path being a sensitive directory (e.g. `~/.ssh`), which is an unrelated, orthogonal control: [3](#0-2) 

Because Git's own protection is the only mechanism that prevents a malicious submodule (nested inside an attacker-controlled remote repository) from writing files that collide with or land inside the parent `.git/hooks` directory during a recursive clone, disabling it via this env var removes that safety net for every clone GitHub Desktop performs.

### Impact Explanation
If a user clones (or Desktop performs a recursive clone of, e.g., when opening a repo with submodules) an attacker-controlled or attacker-influenced repository containing a submodule engineered to collide with the parent working tree's `.git` directory, Git's normal protections would refuse or sanitize such a clone. With the protection explicitly disabled, a crafted hook file (e.g., `post-checkout`, `pre-commit`) could be written into `.git/hooks` outside the intended worktree boundary. That hook would then execute native code on the next Git invocation in that repository (e.g., subsequent commit/checkout operations performed by Desktop or the user), yielding local code execution — this matches the "Critical" scope description in the question (attacker-controlled repository content leading to code execution on next invocation).

### Likelihood Explanation
Likelihood is high for any user who clones a public/untrusted repository with submodules through GitHub Desktop, since `--recursive` is always used and the protection-disabling env var is unconditional — no special user action beyond a normal clone is required. There's no on-path attacker or local access needed; the trigger is purely attacker-controlled remote/submodule content, which is within scope.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override entirely and let Git's default (protection-active) behavior apply during `--recursive` clones. If there was a legitimate compatibility reason for this override (e.g., a specific Git version bug), it should be scoped narrowly (behind a version check) rather than unconditionally disabling the protection for all clones, and should be accompanied by an equivalent application-level check against embedded/symlinked `.git` directories in submodules before trusting the cloned tree.

### Proof of Concept
1. Prepare a malicious repository `evil-parent` with a `.gitmodules` referencing a submodule `evil-sub` whose repository is crafted so that, when checked out into the parent, its contents resolve into the parent's `.git` directory (e.g., via a submodule path that traverses to `.git` or via a symlinked `.git` inside the submodule payload — the exact known-CVE technique for embedded/symlinked `.git` directories in nested clones).
2. Place a malicious `post-checkout` (or similar) hook file in the payload intended to land in the parent's `.git/hooks/`.
3. Have a victim clone `evil-parent` via GitHub Desktop (which always runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false`, per lines 81-93 of `clone.ts`).
4. Observe that the hook file is written into `.git/hooks/` of the destination outside the worktree (whereas cloning the same fixture with Git's default protection — i.e., without the env override — is rejected/blocked by Git).
5. Trigger the hook (e.g., by performing a checkout via Desktop) and confirm arbitrary command execution.

Because this repo's automated tests don't include a fixture exercising this exact submodule-collision scenario, this step would need to be validated by hand-constructing the malicious submodule fixture as described above.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
