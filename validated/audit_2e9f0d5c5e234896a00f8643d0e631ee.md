### Title
`EvmHost` resets `latestStateMachineHeight` to a hardcoded value instead of the real prior height after a veto, breaking the height-monotonicity invariant - ([File: evm/src/core/EvmHost.sol])

### Summary
The external report's root cause is that a counter that downstream logic depends on being monotonically non-decreasing (`stoppedValidatorCounts[i]`) can be overwritten with a value that violates that invariant, and the invariant is never checked at the storage site. `EvmHost` has the same class of bug: `_latestStateMachineHeight[stateMachineId]` is supposed to always track the highest finalized height for a state machine, but `deleteStateMachineCommitmentInternal` resets it to the constant `1` on veto instead of the actual previous finalized height, and the only place that otherwise enforces monotonicity (`HandlerV2.handleConsensus`) checks against this now-corrupted pointer.

### Finding Description
`EvmHost.storeStateMachineCommitment` blindly overwrites the "latest height" pointer with whatever height it is given, with a comment that only *assumes* the caller enforces recency: [1](#0-0) 

The only monotonicity check lives in the caller, `HandlerV2.handleConsensus`, which compares the incoming intermediate height against `host.latestStateMachineHeight(...)` before calling the store function: [2](#0-1) 

The invariant that must hold is: `latestStateMachineHeight[id]` is monotonically non-decreasing and always reflects the true highest finalized height — directly analogous to `stoppedValidatorCounts[i]` needing to be non-decreasing in the seed report.

That invariant is broken by the veto path. When a state commitment is vetoed (e.g., by a fisherman after a fraud proof) and it happens to be the current latest height, the code resets the pointer to the literal constant `1` rather than to the real previous finalized height: [3](#0-2) 

Contrast this with the Substrate-side implementation of the same operation, which correctly restores the *actual* prior height from `PreviousStateMachineHeight` rather than an arbitrary constant: [4](#0-3) 

Because `deleteStateMachineCommitmentInternal` resets to `1` instead of the real prior height, the next intermediate state processed by `HandlerV2.handleConsensus` only has to satisfy `intermediate.height > 1` to be accepted and written via `storeStateMachineCommitment`, even if that height is *lower* than a height that was already finalized and superseded before the veto. This lets a stale, already-superseded state commitment become "the latest" again, updating `_latestStateMachineHeight` and its associated `_stateCommitmentsUpdateTime`, both of which gate challenge-period timing and root selection for subsequent request/response processing in `HandlerV2.handlePostRequests`/`handleGetResponses`: [5](#0-4) 

### Impact Explanation
`latestStateMachineHeight` and its update time are load-bearing for challenge-period gating (`stateMachineCommitmentUpdateTime`) used before dispatching incoming requests/responses. Reintroducing a stale height as "latest" resets the effective challenge-period clock for a superseded/older state root and lets it be treated as current, which can let previously-untrusted or already-rolled-back state data drive request/response acceptance — i.e., false state acceptance, matching the bounty's "false proof/state acceptance" category. This falls squarely within the accepted impact classes (unauthorized execution / false state acceptance) rather than a peer/relayer-compromise scenario, since the veto mechanism itself is a normal, permissionless dispute path in the protocol.

### Likelihood Explanation
Medium: it requires the normal sequence of (1) a state commitment being vetoed while it is the current latest height, then (2) a subsequent, otherwise-legitimate consensus update proving any intermediate height `> 1`. Both are ordinary protocol flows (fisherman veto + relayer consensus submission), not privileged/admin/compromised-actor actions, so it is reachable without any of the excluded assumptions (no malicious relayer, admin, or leaked key needed). The main uncertainty is how often a vetoed height coincides with the tracked "latest" pointer in production usage; this depends on operational conditions I could not fully verify from the indexed code alone.

### Recommendation
On veto, restore `_latestStateMachineHeight[stateMachineId]` to the actual previous finalized height rather than the constant `1`, mirroring the Substrate implementation's `PreviousStateMachineHeight` bookkeeping. Additionally, enforce the height-monotonicity invariant inside `storeStateMachineCommitment` itself (reject/no-op if `height.height <= _latestStateMachineHeight[height.stateMachineId]` except during controlled resets), rather than relying solely on the caller (`HandlerV2`) to pre-check it.

### Proof of Concept
1. Relayer submits consensus proof finalizing state machine `S` at height `H2 > H1`; `HandlerV2.handleConsensus` calls `storeStateMachineCommitment`, setting `_latestStateMachineHeight[S] = H2`.
2. A fisherman successfully vetoes the commitment at `H2` via `deleteStateMachineCommitment` → `deleteStateMachineCommitmentInternal`; since `H2 == latest`, `_latestStateMachineHeight[S]` is reset to `1` (not `H1`).
3. Any subsequent consensus proof presenting an intermediate state at height `Hx` where `1 < Hx < H1` (a height that would have failed the monotonicity check against the true prior latest `H1`) now passes `intermediate.height > latestHeight` (`Hx > 1`) in `HandlerV2.handleConsensus` and gets stored as the new "latest" state commitment, updating the challenge-period clock and root used by `handlePostRequests`/`handleGetResponses`.      * @dev Store the state commitment at given state height alongside relevant metadata.
     * Assumes the state commitment is of the latest height.

    function storeStateMachineCommitment(StateMachineHeight memory height, StateCommitment memory commitment)
        external
        restrict(_hostParams.handler)
    {
        _stateCommitments[height.stateMachineId][height.height] = commitment;
        _stateCommitmentsUpdateTime[height.stateMachineId][height.height] = block.timestamp;
        _latestStateMachineHeight[height.stateMachineId] = height.height;

        emit StateMachineUpdated({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId), 
            height: height.height
        });
    }

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }
