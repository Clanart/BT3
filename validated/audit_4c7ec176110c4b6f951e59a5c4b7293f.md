### Title
Spoofed `WWW-Authenticate: realm="GitHub"` header from an untrusted git remote causes the credential-helper to misclassify the host as GitHub Enterprise and leak the user's real GitHub token to it - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The git credential-helper trampoline decides which "vault" of credentials to use (GitHub-managed account token vs. generic per-host password) based on a classification (`getEndpointKind`) that is partly derived from data returned by the remote server itself. A malicious/compromised git server that the user clones/fetches/pushes to can trick Desktop into treating it as a legitimate GitHub Enterprise host, and, once that classification sticks, the origin-only account-matching logic (`findGitHubTrampolineAccount`) will hand the user's real GitHub OAuth token to that arbitrary host on every subsequent credential request — mirroring the ELFI bug pattern where a boolean/flag determines which fund source is drawn from, but the flag can be set to select the wrong (unintended) source.

### Finding Description
`getEndpointKind` classifies a git remote endpoint using several heuristics, one of which trusts unauthenticated data the remote itself sends back: [1](#0-0) 

If Git captures a `WWW-Authenticate` header containing `realm="GitHub"` from the remote's HTTP response, the endpoint is classified as `'enterprise'`, regardless of whether the host has any real relationship to GitHub Enterprise. This header is fully attacker-controlled: any HTTP(S) git server the user is pointed at (via a manually-added remote, a cloned repository's origin URL, or a crafted `x-github-client://`/`github-desktop://` clone deep link) can emit it.

Once classified `'enterprise'`, `getCredential` takes the GitHub-specific path: [2](#0-1) 

If no existing account matches that endpoint's API origin, the user is prompted with `ui.promptForGitHubSignIn(endpoint)` — a legitimate-looking "sign in to GitHub" dialog, but keyed to the attacker's arbitrary endpoint string rather than to `github.com`/a real enterprise API host.

After that (or if the user already has a matching account, e.g. if the attacker's host happens to have the same origin as one the user is already signed into, such as a self-hosted mirror at the same domain, or after the phishing sign-in above creates an account bound to the attacker endpoint), every future `get` request for that same origin resolves the credential purely by **origin string equality**, with no verification that the origin is actually a genuine, trusted GitHub host: [3](#0-2) 

`credWithAccount` then places the account's real token directly into the credential handed back to git, which git sends to that server over the git protocol: [4](#0-3) 

This is the same broken-invariant shape as the ELFI report: a source-selection flag (`isExecutionFeeFromLpVault` / here, `endpointKind === 'enterprise'`) is set based on attacker-influenced input and later consulted, unconditionally, to decide which "vault" (the GitHub-managed token store vs. the ordinary generic-per-host credential store) funds are drawn from — sending the asset (execution fee / OAuth token) to the wrong destination.

### Impact Explanation
If the classification is tricked into `'enterprise'` and an account becomes associated with the attacker's endpoint (via the phishing-style sign-in prompt, or via an origin collision), the user's genuine GitHub personal-access/OAuth token is transmitted as an HTTP Basic credential to a server the user does not intend to trust with it. This is a credential/token exfiltration primitive: the token can then be used by the attacker to access the victim's real GitHub account (repos, org data, etc.), i.e., full account compromise, without the user ever knowingly entering their token anywhere but a dialog they believe is GitHub's own sign-in.

### Likelihood Explanation
The attacker only needs to control the response of a git-over-HTTP(S) server that the victim is induced to clone/fetch/push to (a plausible/realistic vector: a project README/setup instructions telling a victim to add a malicious remote, or a crafted clone URL/deep link opened by GitHub Desktop). No local access, admin rights, or pre-existing malware is required — this fits the "attacker controls a git remote/proxy response" primitive called out as in-scope. The main uncertainty (not independently verified from the index) is the exact downstream behavior of `ui.promptForGitHubSignIn` / `trampoline-ui-helper.ts` — specifically whether the resulting `Account` gets persisted with `endpoint` set to the attacker's arbitrary host string (making the leak persistent across sessions) or is scoped more narrowly. That downstream code path (`app/src/lib/trampoline/trampoline-ui-helper.ts`, `app/src/lib/stores/app-store.ts` sign-in flow) could not be fully traced within the available tool budget, so likelihood should be treated as **medium** pending that confirmation.

### Recommendation
- Do not classify an endpoint as GitHub/enterprise based solely on an unauthenticated `WWW-Authenticate` header supplied by the remote; require an independent, verifiable check (e.g., an authenticated API probe with a known GitHub response shape/certificate, or an explicit user-confirmed enterprise-host allowlist) before treating a host as GitHub-managed.
- In `findGitHubTrampolineAccount`, do not match purely by origin string; cross-check that the endpoint was explicitly registered as a signed-in GitHub/Enterprise account through the normal sign-in flow (not one created reactively from a credential-helper prompt for an arbitrary remote), and warn the user prominently when signing in for a host that isn't a recognized GitHub Enterprise instance.

### Proof of Concept
1. Attacker sets up a plain HTTP(S) git server at `https://attacker.example/victim/repo.git`.
2. Attacker gets the victim to add it as a remote or clone it in GitHub Desktop (e.g., via README instructions or a crafted clone deep link).
3. When Desktop performs a `fetch`/`push`, git contacts the server; the server responds with `401` plus header `WWW-Authenticate: Basic realm="GitHub"`.
4. Desktop's credential helper (`getEndpointKind`, `app/src/lib/trampoline/trampoline-credential-helper.ts:153-165`) sees the `realm="GitHub"` substring and classifies `attacker.example` as `'enterprise'`.
5. Because no existing account origin matches `attacker.example`, `getCredential` (lines 93-135) calls `ui.promptForGitHubSignIn('https://attacker.example')`, presenting what looks like a normal "Sign in to GitHub" flow to the victim.
6. If the victim completes sign-in (using their real GitHub credentials/OAuth), and the resulting account is stored keyed to `attacker.example`'s origin, then on this and all future git operations against that origin, `findGitHubTrampolineAccount` (`app/src/lib/trampoline/find-account.ts:20-29`) matches by origin and `credWithAccount` returns the victim's real token, which git delivers to `attacker.example` as Basic-Auth credentials — completing the exfiltration.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
