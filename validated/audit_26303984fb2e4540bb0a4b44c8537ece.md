### Title
Unsanitized submodule path from untrusted repository allows path traversal when building the "open submodule" full path - (File: `app/src/lib/git/diff.ts`)

### Summary
`buildSubmoduleDiff` derives the on-disk path for a changed submodule directly from the tracked path reported for the file (`file.path`), which originates from git's status/diff machinery on a repository that can be entirely attacker-controlled (a cloned or fetched repo). This value is joined to the repository root with `Path.join` and no check is performed to ensure the resulting path stays inside the repository.

### Finding Description
In `buildSubmoduleDiff`, the submodule's path is taken as-is from `file.path` and combined with the repository root: [1](#0-0) 
There is no validation that `path` is a single, traversal-free path component before it is passed to `Path.join(repository.path, path)`, and no bounds check that `fullPath` remains inside `repository.path`. This mirrors the broken invariant in the original report: an externally influenced value (there, `WETH_TRANSFER_GAS_UNITS`; here, the submodule tracked path) is fed unchecked into a security-relevant computation (there, the WETH gas-cost deduction; here, the filesystem path used to open/manage a repository) with no sanity/bounds guard at the point of use.

The resulting `fullPath` is surfaced to the UI in `ISubmoduleDiff` and rendered by `SubmoduleDiff`, whose "Open Repository" action forwards it verbatim via `onOpenSubmodule(fullPath)`: [2](#0-1) 

Note: `sanitizeCloneName` in `app/src/lib/remote-parsing.ts` exists to prevent traversal in a different flow (deriving a folder name from a *clone URL*), showing the project is aware of this class of bug, but that helper is not invoked in `buildSubmoduleDiff`'s path construction: [3](#0-2) 

### Impact Explanation
If a submodule path containing `..` segments can reach `buildSubmoduleDiff` (e.g., via a crafted `.gitmodules`/tree entry in a repository the victim clones or fetches, historically exploitable in git itself — CVE-2017-1000117/CVE-2018-11235-class issues — or via any status/diff code path that doesn't itself reject such paths), `Path.join(repository.path, path)` would resolve to a location outside the repository. Depending on what the downstream `onOpenSubmodule` handler does with that path (adding/opening it as a Desktop-managed repository), this could let a malicious repository author point GitHub Desktop at an arbitrary directory on the victim's filesystem outside the cloned repo — a boundary violation matching the "read/write outside the repo" impact class.

### Likelihood Explanation
Exploitability depends on whether anything upstream (git itself, or Desktop's status/diff parsing) already strips or rejects `..`-containing submodule paths before they reach `buildSubmoduleDiff`; modern git has hardened against the classic submodule-path CVEs, which reduces likelihood. I was not able to fully verify, within the available iterations, whether Desktop's own consumer of `fullPath` (the `onOpenSubmodule` handler wired up in `app/src/ui/repository.tsx`) performs an additional containment check before acting on the path — this is the key remaining uncertainty for confirming end-to-end exploitability.

### Recommendation
- In `buildSubmoduleDiff` (`app/src/lib/git/diff.ts`), validate that `path` is a normalized, single relative path with no `..` segments before computing `fullPath`, and reject/ignore the diff (or drop the "open" action) if it isn't.
- Add an explicit containment check (e.g., resolve `fullPath` and confirm it starts with `resolve(repository.path)` plus a path separator) before it is ever passed to any handler that opens/adds it as a repository.

### Proof of Concept
Not independently reproduced end-to-end due to tool-iteration limits; the concrete corrupted-value path is:
1. A malicious repository is crafted so that a tracked submodule's reported path (`file.path`) contains `..` segments.
2. Victim clones/fetches this repository in GitHub Desktop and views the change in the Changes/Diff view, triggering `buildSubmoduleDiff`.
3. `fullPath = Path.join(repository.path, path)` (line 805 of `app/src/lib/git/diff.ts`) resolves outside `repository.path`.
4. The victim clicks "Open Repository" in `SubmoduleDiff`, invoking `onOpenSubmodule(fullPath)` with the escaped path.

Confirming whether step 4's downstream handler enforces containment (and whether current git versions still allow crafting such a submodule path) requires further investigation with full repository/file access, which I could not complete in this session.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
