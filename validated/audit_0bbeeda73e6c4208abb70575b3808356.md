## Title
CPI Compute-Cost Bypass via Reliance on Deprecated `is_executable()` Flag Instead of Ownership Check - (File: program-runtime/src/cpi.rs)

## Summary
The external report describes a class of bug where a contract distinguishes between two account types (EOA vs. contract) using a runtime-mutable/unreliable indicator (`isContract`/code presence) instead of a stable authorization signal, and that indicator can be manipulated (via EIP-7702) to force the wrong verification branch, causing legitimate signatures to be wrongly rejected. The closest reachable analog in agave is `translate_and_update_accounts` in `program-runtime/src/cpi.rs`, which branches CPI account handling logic on the deprecated, caller-controllable `executable` account flag rather than the account's owner/loader identity.

## Finding Description
In `program-runtime/src/cpi.rs`, the account-translation path taken during a cross-program invocation branches on `callee_account.is_executable()`: [1](#0-0) 

If the flag is `true`, the code treats the account as an already-known/immutable program account and skips translating it from the caller-supplied `account_infos`, only charging a CPI byte cost based on the account's current data length. If the flag is `false`, it falls through to the branch that looks up the account among the caller's `account_infos` and performs full translation/synchronization logic (`update_callee_account`), which is the path meant for regular, caller-controlled accounts.

This mirrors the reported bug class exactly: the runtime is using a boolean "is this a program" proxy (`executable`) to select between two structurally different code paths — one trusting the account as immutable/system-known, and one requiring full translation of caller-provided data — instead of relying on the account's actual owner/loader identity, which is the stable, protocol-enforced signal of "programness." The codebase itself acknowledges this flag is unreliable: `BorrowedInstructionAccount::is_executable()` is explicitly deprecated in favor of checking ownership: [2](#0-1) 

The protocol has already had to introduce a dedicated feature gate to remove reliance on this exact flag from account-loading logic because it does not reliably indicate whether an account is "code": [3](#0-2) 

Test harnesses in the codebase even demonstrate that the `executable` flag on `AccountInfo` structures passed across CPI boundaries can be freely set by the caller and is explicitly documented as ignored by the runtime for provenance purposes ("Test that is_executable and rent_epoch are ignored"): [4](#0-3) 

However, the `cpi.rs:1014` check reads this flag directly off the on-chain `BorrowedInstructionAccount` (the transaction-context copy, not the caller-supplied `AccountInfo`), so it is not attacker-forgeable in the same direct way as the `AccountInfo.executable` field in serialized memory — but it is exactly the same kind of unreliable, non-ownership-based signal that SIMD-0162 was created to eliminate elsewhere in the codebase, indicating this is a known-fragile pattern still present in the CPI hot path.

## Impact Explanation
If the "is program account" determination in this CPI cost-accounting branch can be desynchronized from the true owner/loader-based determination (e.g., an account's `executable` flag being stale relative to its `owner`, similar in spirit to how EIP-7702 desynchronizes "has code" from "is an EOA"), the code takes the wrong branch: either skipping the caller-account synchronization logic entirely for what should be treated as a regular account, or performing unnecessary/incorrect translation for what should be treated as a program account. This falls into "materially underpriced compute" and potential CPI account-state confusion territory referenced in the validation criteria, since the compute charged and the data-synchronization path differ materially between the two branches.

## Likelihood Explanation
This is a low-to-moderate likelihood finding. It requires demonstrating a concrete scenario where an account's `executable` bit and its owner/loader status diverge within an instruction's lifetime such that this branch selects the wrong code path with real consequences (e.g., stale CPI account view, incorrect compute charge). The `#[expect(deprecated)]` annotation and the existence of SIMD-0162 confirm the code owners are aware `is_executable()` is not a trustworthy signal in general, but I could not fully verify within the available tool budget whether this specific CPI branch has a concrete exploitable divergence scenario (e.g., whether `set_executable()`'s rent-exemption/ownership guardrails at `transaction-context/src/instruction_accounts.rs:286-311` fully prevent such a divergence during CPI). This is flagged as uncertain and would need deeper tracing of `translate_and_update_accounts` call sites and program cache interaction to confirm exploitability to the level of an accepted forged/underpriced outcome.

## Recommendation
Replace the `callee_account.is_executable()` check at `program-runtime/src/cpi.rs:1014` with an owner/loader-based check (e.g., verifying the account's owner is one of the loader program IDs, consistent with the direction taken by SIMD-0162 and the `ProgramCacheEntryOwner` classification used elsewhere), so that CPI account-handling branch selection is not dependent on the mutable/deprecated `executable` flag.

## Proof of Concept
Not established. I was unable to construct a concrete transaction/CPI sequence within the available investigation to demonstrate the `executable` flag and the account's owner-based "is this a program" status diverging in a way that is externally triggerable and produces a security-relevant outcome (rather than a benign, already-guarded state). This would require deeper analysis of `set_executable()`'s guard conditions and all call sites of `translate_and_update_accounts` to confirm reachability.
