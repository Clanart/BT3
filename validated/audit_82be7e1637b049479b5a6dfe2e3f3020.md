## Title
Unhandled `StopIteration` when accepting a malformed/adversarial Offer causes wallet spend-processing to crash - (File: chia/wallet/trading/offer.py)

## Summary
CVE-2020-6795 is a null-pointer dereference triggered when Thunderbird processes a message containing multiple S/MIME signature parts that don't line up with the code's single-signature assumption, causing an unhandled crash. The structurally analogous bug class in chia-blockchain is code that walks attacker-supplied "message" data (an `Offer`) and uses `next()` on a filter/generator **without a default**, assuming a matching item always exists. If a counterparty crafts an `Offer` whose internal structure doesn't satisfy that assumption, `next()` raises an uncaught `StopIteration`, crashing the code path that processes the offer — the same "unexploitable crash triggered by processing untrusted multi-part input" pattern as the CVE.

## Finding Description
`Offer.to_valid_spend()` iterates over `get_offered_coins()` and, for every offered coin, looks up its parent spend inside the bundle with: [1](#0-0) 

```python
parent_spend: CoinSpend = next(
    filter(lambda cs: cs.coin.name() == coin.parent_coin_info, self._bundle.coin_spends)
)
```

This `next()` call has no default value. If no `CoinSpend` in `self._bundle.coin_spends` has a `coin.name()` equal to `coin.parent_coin_info`, Python raises `StopIteration`, an unhandled exception at this call site. The `offered_coins` used here are computed heuristically in `_get_offered_coins()` — a method whose own docstring says "It's also a little heuristic, but it should get most things" — from CLVM-condition-derived amounts/puzzle-hash matches against `additions()`: [2](#0-1) 

An `Offer` object is built directly from untrusted, externally supplied bytes via `Offer.from_bytes` / the bech32/compressed offer file format and is not otherwise re-validated against strict consensus rules before this code runs. `to_valid_spend()` is invoked from the offer-acceptance path in `TradeManager.calculate_tx_records_for_offer()`: [3](#0-2) 

This mirrors the CVE's bug class: code assumes a corresponding "part" (here, a matching `CoinSpend` for an offered coin) always exists in attacker-controlled multi-part input, and an unhandled exception fires when the counterparty crafts input that violates that assumption.

## Impact Explanation
A malicious offer counterparty (or a malformed/corrupted offer file) can potentially trigger this crash the moment a victim's wallet attempts to inspect/accept the offer (`get_offered_coins()`/`to_valid_spend()` execution), halting that spend-processing call for the offer with an unhandled exception. This matches the "spend-triggered transaction-processing halt" category in the validation rules — no funds theft or supply inflation results, but a wallet-side denial-of-service against the specific offer-processing routine is plausible if `_get_offered_coins()`'s heuristics can be driven to disagree with the actual coin_spend parentage in a crafted bundle.

## Likelihood Explanation
This requires the attacker to construct a syntactically valid but internally inconsistent `Offer`/`WalletSpendBundle` (bypassing `Offer.__post_init__`'s duplicate-payment and driver-presence checks, which do not verify offered-coin/parent-spend consistency) such that the heuristic offered-coin detection in `_get_offered_coins()` selects a coin whose `parent_coin_info` is not present among `self._bundle.coin_spends`. I was not able to fully confirm within the available exploration whether `_get_offered_coins()`'s matching logic can actually be forced into this mismatched state by adversarial `coin_spends`/conditions (its own comments acknowledge it is heuristic and can raise `ValueError` in some mismatch cases, but the exact conditions to bypass those checks and still reach the `next()` without a match were not exhaustively verified against the CLVM puzzle-matching code in `chia/wallet/util/puzzle_compression*`/`match_puzzle` helpers).

## Recommendation
Add an explicit default/error handling to the `next()` call in `Offer.to_valid_spend()` (e.g., `next(..., default=None)` followed by a clear `ValueError`/`ValidationError` raise), and audit other similar unguarded `next()`/first-match assumptions in offer processing (e.g., `nft_wallet.py` lines 1095–1099 and 1134–1136) for the same failure mode. Additionally, add a construction-time or acceptance-time check that every coin returned by `get_offered_coins()` has a `parent_coin_info` matching some `coin_spend.coin.name()` in the bundle, rejecting the offer early with a descriptive error rather than allowing an uncaught exception deep in transaction-record calculation.

## Proof of Concept
Conceptual (not fully verified end-to-end within this investigation):
1. Attacker constructs a `WalletSpendBundle` for an `Offer` where a settlement-puzzle coin spend produces an addition that superficially matches the offered-coin heuristic (`_get_offered_coins()`, amount/puzzle-hash matching against `OFFER_MOD_HASH`/`construct_puzzle(...).get_tree_hash()`), but is not spendable back to a coin whose `coin.name()` appears in `self._bundle.coin_spends` (e.g., by aggregating in an unrelated, non-consuming coin spend or manipulating cost-limited condition parsing so `_additions` and true chain state diverge).
2. Attacker serializes this as a standard offer file/bech32 blob and sends it to the victim.
3. Victim wallet calls `TradeManager.respond_to_offer` → `calculate_tx_records_for_offer(offer, validate=True)` → `offer.to_valid_spend()`.
4. `next(filter(...))` at `chia/wallet/trading/offer.py:528` finds no matching `CoinSpend` and raises `StopIteration`, which is not caught anywhere in this call chain, crashing/aborting offer processing for that request.

    def _get_offered_coins(self) -> dict[bytes32 | None, list[Coin]]:
        offered_coins: dict[bytes32 | None, list[Coin]] = {}

        cost_left = INFINITE_COST
        for parent_spend in self._bundle.coin_spends:
            coins_for_this_spend: list[Coin] = []

            parent_puzzle: UnknownPuzzle = UnknownPuzzle(known_program=parent_spend.puzzle_reveal)
            parent_solution = Program.from_serialized(parent_spend.solution)
            additions: list[Coin] = self._additions[parent_spend.coin]

            puzzle_driver = match_puzzle(parent_puzzle)
            if puzzle_driver is not None:
                asset_id = create_asset_id(puzzle_driver)
                inner_puzzle: Program | None = get_inner_puzzle(puzzle_driver, parent_puzzle, parent_solution)
                inner_solution: Program | None = get_inner_solution(puzzle_driver, parent_solution)
                assert inner_puzzle is not None and inner_solution is not None

                # We're going to look at the conditions created by the inner puzzle
                puzzle_cost, conditions = inner_puzzle.run_with_cost(cost_left, inner_solution)
                assert cost_left >= puzzle_cost
                cost_left -= puzzle_cost
                expected_num_matches: int = 0
                offered_amounts: list[int] = []
                for condition in conditions.as_iter():
                    if condition.first() == 51 and condition.rest().first() == OFFER_MOD_HASH:
                        expected_num_matches += 1
                        offered_amounts.append(condition.rest().rest().first().as_int())

                # Start by filtering additions that match the amount
                matching_spend_additions = [a for a in additions if a.amount in offered_amounts]

                if len(matching_spend_additions) == expected_num_matches:
                    coins_for_this_spend.extend(matching_spend_additions)
                # We didn't quite get there so now lets narrow it down by puzzle hash
                else:
                    # If we narrowed down too much, we can't trust the amounts so start over with all additions
                    if len(matching_spend_additions) < expected_num_matches:
                        matching_spend_additions = additions
                    matching_spend_additions = [
                        a
                        for a in matching_spend_additions
                        if a.puzzle_hash == construct_puzzle(puzzle_driver, OFFER_MOD).get_tree_hash()
                    ]
                    if len(matching_spend_additions) == expected_num_matches:
                        coins_for_this_spend.extend(matching_spend_additions)
                    else:
                        raise ValueError("Could not properly guess offered coins from parent spend")
            else:
                # It's much easier if the asset is bare XCH
                asset_id = None
                coins_for_this_spend.extend([a for a in additions if a.puzzle_hash == OFFER_MOD_HASH])

            # We only care about unspent coins
            coins_for_this_spend = [c for c in coins_for_this_spend if c not in self._bundle.removals()]

            if coins_for_this_spend != []:
                offered_coins.setdefault(asset_id, [])
                offered_coins[asset_id].extend(coins_for_this_spend)
        return offered_coins
