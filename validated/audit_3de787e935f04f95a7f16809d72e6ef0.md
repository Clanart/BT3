I have confirmed the core finding: `DataLayerWallet.coin_added()` at [1](#0-0)  tracks mirror coins for *any* `launcher_id` as long as it's already tracked locally (owned or subscribed), with no restriction on who created the mirror coin. `create_new_mirror()` similarly places attacker-supplied `urls` into memos with no format/scheme validation [2](#0-1) , and `get_mirror_info()` extracts the launcher_id/urls purely from spend conditions [3](#0-2) . These URLs flow unmodified into `DataStore.update_subscriptions_from_wallet()` [4](#0-3)  and are then fetched via `http_download()`'s `aiohttp` GET with no host/scheme allow-listing [5](#0-4) .

### Title
Unauthenticated Mirror-Coin URL Injection Causes SSRF in DataLayer Subscription Fetch - (File: chia/data_layer/data_layer_wallet.py, chia/data_layer/download_data.py)

### Summary
Any wallet holder can spend a standard coin to the `MIRROR_PUZZLE_HASH` puzzle, embedding an arbitrary `launcher_id` (any DataLayer store id, including one the attacker does not own) and arbitrary URL strings in the coin's memos. Any node that already tracks that `launcher_id` (owner or subscriber) will ingest this mirror via `DataLayerWallet.coin_added()`, propagate the attacker URLs into its subscription table, and its `DataLayer.periodically_manage_data()` background loop will subsequently issue outbound HTTP requests to those URLs without any validation of scheme, host, or destination IP range.

### Finding Description
`create_mirror_puzzle()` / `MIRROR_PUZZLE_HASH` defines a puzzle that anyone can spend into with a `CREATE_COIN` condition carrying `(launcher_id, *urls)` in the memo list [6](#0-5) . `DataLayerWallet.create_new_mirror()` is the standard way to build such a spend, and it passes `urls` straight into the coin memos without any URL/format validation [2](#0-1) . The DataLayer service's `add_mirror()` RPC handler also only checks that the URL list is non-empty — no scheme or host checks — before submitting the spend [7](#0-6) .

On the receiving side, `DataLayerWallet.coin_added()` recognizes any coin sent to `MIRROR_PUZZLE_HASH`, decodes the `launcher_id` and `urls` from the parent spend, and — critically — only checks `is_launcher_tracked(launcher_id)`, not whether the *local wallet* created or owns this mirror or whether the sender is authorized in any way:
```python
if coin.puzzle_hash == create_mirror_puzzle().get_tree_hash():
    ...
    launcher_id, urls = get_mirror_info(parent_spend.puzzle_reveal, parent_spend.solution)
    if not urls:
        return
    if await self.wallet_state_manager.dl_store.is_launcher_tracked(launcher_id):
        ...
        await self.wallet_state_manager.dl_store.add_mirror(Mirror(...))
``` [1](#0-0) 

Any node tracking a given `launcher_id` — because it owns that store, is subscribed to it, or is simply syncing DL launcher creations — will therefore accept and store mirror URLs supplied by a third party who has no relationship to that store. `DataLayer.update_subscriptions_from_wallet()` pulls these mirror URLs from the wallet and inserts them into the local `subscriptions` table with no validation [8](#0-7) , and `DataStore.update_subscriptions_from_wallet()` persists them verbatim [4](#0-3) .

The background sync loop `periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()` iterates these server URLs and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs an unauthenticated `aiohttp.ClientSession().get(server_info.url + "/" + filename, ...)` [5](#0-4) . There is no validation restricting the URL to `http`/`https`, no blocklist for loopback/link-local/private ranges, and no confirmation that the URL was set by the local operator. This exactly matches the reported bug class (unvalidated URL fetch driven by attacker-controlled data), except here the attacker-controlled input is delivered on-chain via a standard, unauthenticated coin spend rather than an application-layer field.

### Impact Explanation
An attacker with no relationship to a DataLayer store can force any node syncing/subscribing/owning that store to make outbound HTTP requests to attacker-chosen destinations, including cloud metadata endpoints (`169.254.169.254`), internal services, or other local-network hosts reachable from the DataLayer host. Because `insert_from_delta_file()`/`download_file()` write the response body to disk and attempt to parse it as delta-tree data, response content and timing/error behavior can leak information about internal service reachability (port scanning / internal recon), and repeated fetches consume node resources. This is reachable purely through a low-cost, unprivileged on-chain spend bundle (a mirror coin creation), fitting the "Data Layer client" and "spend-bundle submitter" reachable actor classes.

### Likelihood Explanation
Likelihood is Medium-High: creating the mirror coin only requires XCH to cover the coin amount plus fee (mirror amount can be zero, per `test_datalayer_reorgs`), and no permission over the target `launcher_id` is required. Any DataLayer node subscribed to or owning a targeted store will automatically process the malicious mirror during its normal periodic sync loop without operator interaction.

### Recommendation
Before persisting/fetching mirror URLs, validate that they use `http`/`https` scheme and are not pointed at loopback, link-local, or private/reserved address ranges (mirroring the fix pattern in the referenced PDFME advisory). Consider requiring mirror URLs to be validated/allow-listed by the local operator (e.g., via config) before `DataLayer.fetch_and_validate()`/`http_download()` will use them, and/or bound outbound DL fetches with the same SSRF protections generally recommended for any user-influenced network resource.

### Proof of Concept
1. Attacker (any funded wallet) calls `dl_new_mirror` on their own wallet targeting a victim's `launcher_id` (a store the attacker does not own):
```python
await client.dl_new_mirror(
    DLNewMirror(
        launcher_id=<victim_store_launcher_id>,
        amount=uint64(0),
        urls=["http://169.254.169.254/latest/meta-data/"],
        fee=uint64(1),
        push=True,
    ),
    DEFAULT_TX_CONFIG,
)
```
(as exercised in `chia/_tests/wallet/rpc/test_dl_wallet_rpc.py:281-292`)
2. Once the spend is confirmed, any node that tracks `victim_store_launcher_id` (owner or any subscriber) will, via `DataLayerWallet.coin_added()`, add this URL as a `Mirror` regardless of who created it.
3. The victim's `DataLayer.periodically_manage_data()` loop calls `update_subscriptions_from_wallet()` then `fetch_and_validate()`, which will attempt `http_download()` against the attacker-supplied URL, causing the victim node to issue the SSRF request.

def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```

                "SELECT * FROM subscriptions WHERE from_wallet == 1 AND tree_id == :tree_id",
                {
                    "tree_id": store_id,
                },
            )
            old_urls = [row["url"] async for row in cursor]
            cursor = await writer.execute(
                "SELECT * FROM subscriptions WHERE from_wallet == 0 AND tree_id == :tree_id",
                {
                    "tree_id": store_id,
                },
            )
            from_subscriptions_urls = {row["url"] async for row in cursor}
            additions = {url for url in new_urls if url not in old_urls}
            removals = [url for url in old_urls if url not in new_urls]
            for url in removals:
                await writer.execute(
                    "DELETE FROM subscriptions WHERE url == :url AND tree_id == :tree_id",
                    {
                        "url": url,
                        "tree_id": store_id,
                    },
                )
            for url in additions:
                if url not in from_subscriptions_urls:
                    await writer.execute(

                        "VALUES (:tree_id, :url, 0, 0, 1)",
                        {
                            "tree_id": store_id,
                            "url": url,
