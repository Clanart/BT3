### Title
`restrict-assets?` / `as-contract?` "*" wildcard allowance sentinel collides with the legal Clarity asset-name grammar, letting one narrow allowance silently authorize movement of *every* fungible/non-fungible asset in a contract - ([File: clarity/src/vm/functions/post_conditions.rs])

### Summary
`check_allowances` in `clarity/src/vm/functions/post_conditions.rs` implements the `with-ft`/`with-nft` "match every asset in this contract" wildcard feature by using the literal string `"*"` as a sentinel `AssetIdentifier.asset_name` and unconditionally merging any allowance keyed with that sentinel into every other asset lookup for the same contract: [1](#0-0) 

The sentinel `"*"` is not a value that is excluded from the legal namespace of Clarity asset/token names. `CLARITY_NAME_REGEX_STRING` explicitly accepts the single-character token `"*"` as a valid Clarity name (branch `^[-+=/*]$`), meaning a contract can legitimately `define-fungible-token`/`define-non-fungible-token` an asset literally named `*`: [2](#0-1) 

Because `eval_allowance` accepts any ASCII string that passes `ClarityName::try_from` as the asset name argument to `with-ft`/`with-nft`, an allowance written as `(with-ft contract "*" amount)` — which a caller may write intending an *exact-match* restriction on the literal token named `*` — is stored under exactly the same `AssetIdentifier` key that `check_allowances` treats as the "match-any-asset-in-this-contract" wildcard: [3](#0-2) [4](#0-3) 

There is no distinct, reserved representation for "wildcard" versus "the real asset literally named `*`" — the equality `asset_name == "*"` is used to decide both semantics.

### Finding Description
`restrict-assets?`/`as-contract?` are Clarity's asset-post-condition primitive: they bound, via `Allowance` entries, exactly what STX/FT/NFT/staking/PoX actions a protected principal is permitted to perform within a body. `check_allowances` enforces those bounds against the actual `AssetMap` produced by executing the body: [5](#0-4) 

For fungible tokens, when checking whether a moved asset is covered, the code always looks up two keys for the same contract: the exact `AssetIdentifier` of the asset that moved, and the sentinel `AssetIdentifier{contract, asset_name:"*"}`, merging both sets of allowances: [6](#0-5) 

The identical pattern exists for NFTs: [7](#0-6) 

The root cause is the same class as the reported ExifTool bug: a security-relevant check treats two syntactically distinct-looking inputs as identical downstream (there, `File:FileName` normalized to `FileName` after the blocklist ran; here, a real, legally-defined asset named `*` is indistinguishable from the internal "any asset" wildcard token). The equality that should hold — "an allowance for token `T` bounds only movements of `T`" — is broken whenever `T`'s name is the single character `*`, which `ClarityName`'s grammar permits.

Concretely: a contract can be deployed that defines a fungible token (or NFT asset class) literally named `*` alongside other, unrelated fungible/non-fungible tokens in the same contract. Any Clarity code (a DeFi router, wallet contract, DAO treasury contract, etc.) that writes `(with-ft 'SP...TOKEN-CONTRACT "*" u100)` intending to authorize moving up to `100` units of the specific token named `*`, will — due to `check_allowances`'s wildcard lookup — also authorize *unbounded* (up to the same `100` cap, but for every other FT in that contract simultaneously, and for NFTs, no cap at all beyond the id list) movement of every other fungible/non-fungible asset defined in that contract, because every other asset's lookup in `check_allowances` will also match the `"*"`-keyed allowance entry.

### Impact Explanation
This breaks the "asset moving past its post-conditions" invariant that `restrict-assets?`/`as-contract?` exist to enforce: assets that were never authorized by the caller-supplied allowance list can move within the protected scope, purely because of an unprivileged party's choice of an asset name that collides with the internal wildcard sentinel. Any contract relying on `restrict-assets?`/`as-contract?` to scope third-party contract calls (the entire purpose of the feature) can have its allowance silently widened by a token-contract author who is not privileged in any way relative to the caller. This matches the Critical class "an asset moving past its post-conditions" in scope for this analysis.

### Likelihood Explanation
Exploitation requires only that some fungible or non-fungible asset in a contract that a victim contract interacts with be named the single character `*` — a fully valid Clarity identifier under the existing name-validation grammar, requiring no protocol-level privilege, and trivially achievable by any contract deployer. The victim need only use the wildcard-capable `with-ft`/`with-nft` allowance syntax against that contract (a documented, expected usage pattern), at which point the collision is deterministic, not probabilistic. The likelihood of a caller specifically intending to name-restrict `"*"` is lower than the likelihood of an attacker naming a token `"*"` to deliberately exploit the wildcard-merge behavior against victims who use `with-ft`/`with-nft` for *other* tokens in the same contract — since the merge happens unconditionally for every asset in the contract whenever *any* allowance entry keyed `"*"` exists, regardless of whether the caller intended a wildcard.

### Recommendation
Reserve the wildcard semantics behind a value that is provably outside the legal namespace of `ClarityName`/asset names (e.g., a distinct `Allowance` variant such as `Allowance::FtAny{contract}` / `Allowance::NftAny{contract}` set via a separate parse path, rather than overloading the `asset_name` string space with `"*"`), or explicitly reject `"*"` as a valid `define-fungible-token`/`define-non-fungible-token`/asset name so the sentinel cannot collide with a real, user-defined asset identifier.

### Proof of Concept
1. Deploy a contract `attacker.token` that defines two fungible tokens: `(define-fungible-token * )` (the literal name `*`, which passes `ClarityName`/`CLARITY_NAME_REGEX_STRING` validation) and `(define-fungible-token real-token)`.
2. A victim contract calls, inside `as-contract?`/`restrict-assets?`:
   `(with-ft 'SP...attacker.token "*" u100)`
   intending to authorize movement of up to 100 units of the token literally named `*`.
3. Inside the protected body, the victim contract calls into `attacker.token`, which transfers `real-token` (a completely different fungible token) out of the protected principal.
4. `check_allowances` (clarity/src/vm/functions/post_conditions.rs:600-613) looks up the exact `AssetIdentifier` for `real-token` (no match) and then additionally looks up `AssetIdentifier{contract: attacker.token, asset_name: "*"}` (match, because the caller's allowance was stored under that same key), merges its `100`-unit cap, and treats the `real-token` transfer as authorized — even though the caller never wrote an allowance mentioning `real-token`.
