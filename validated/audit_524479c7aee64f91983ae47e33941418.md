### Title
Missing pointer-version authorization check allows unprivileged callers to overwrite (re-`CREATE`/`DROP`) existing ERC pointer contracts - (File: `x/evm/keeper/pointer_upgrade.go`)

### Summary
The current pointer precompile (`precompiles/pointer/pointer.go`) and its `UpsertERCPointer` backend (`x/evm/keeper/pointer_upgrade.go`) removed the version-gate that earlier pointer implementations enforced. Any unprivileged EVM caller invoking `addNativePointer`, `addCW20Pointer`, `addCW721Pointer`, or `addCW1155Pointer` for a token/CW address that already has a registered pointer will cause the keeper to redeploy bytecode at the existing pointer's contract address, without verifying that the caller is entitled to modify/upgrade that specific pointer or that the operation represents an actual version bump.

### Finding Description
`UpsertERCPointer` fetches only `exists` from the pointer getter and ignores the version return value entirely: [1](#0-0) 

If a pointer already exists, it unconditionally regenerates the deployment bytecode via `evm.GetDeploymentCode` using the artifact bytecode for the pointer type (`native`/`cw20`/`cw721`/`cw1155`) baked into the binary, and overwrites the code at the existing pointer contract address with `k.SetCode`. There is no check comparing the caller-visible operation to the currently stored pointer version, unlike the analogous legacy code paths (v552, v555, v562, v605, v606, v610) which explicitly reject the call when `existingVersion >= CurrentVersion`: [2](#0-1) 

This mirrors the Hive `CREATE`/`DROP` authorization gap: an operation that mutates/recreates an existing "function" (here, a pointer contract's on-chain bytecode) is no longer gated by the check that previously enforced who/when this recreation is allowed, so any caller can trigger the recreation path repeatedly.

### Impact Explanation
Because the artifact bytecode compiled into the pointer type (`native`, `cw20`, `cw721`, `cw1155`) is fixed and not attacker-supplied, this does not let an attacker inject arbitrary malicious bytecode the way the Hive bug allowed pointing UDFs at malicious jars. However, the missing version gate means the "upsert" (redeploy) path can be re-triggered by any unprivileged caller on every call, silently re-running `SetCode` on the existing pointer contract address at unconstrained frequency and consuming EVM `Create`/deployment gas cycles without any guard that the redeploy is a genuine upgrade. Since I could not find any code path elsewhere that reintroduces the version check for the current pointer precompile (only pointer_upgrade.go and pointer.go were available for inspection), I cannot confirm with full certainty whether this is exploitable for fund loss beyond redundant/wasteful redeployments — the impact is bounded by the fact that the pointer constructor arguments and bytecode are keeper/artifact-controlled, not attacker-controlled.

### Likelihood Explanation
High: any account holding a small amount of gas can call `addNativePointer`/`addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` against an already-pointered token/CW address through the public EVM JSON-RPC surface, exercising this path on every transaction.

### Recommendation
Reinstate the version check inside `UpsertERCPointer` (or its callers in `precompiles/pointer/pointer.go`) so that pointer redeployment for an already-registered pointer only proceeds when `existingVersion < CurrentVersion` for the given pointer type, matching the legacy behavior in `precompiles/pointer/legacy/v562/pointer.go` and siblings.

### Proof of Concept
1. Call `addNativePointer(token)` on the pointer precompile (`0x...100b`) for a token with bank metadata — this deploys a pointer contract and calls `SetERC20NativePointer`.
2. Call `addNativePointer(token)` again for the same token. In the current implementation, `UpsertERCPointer` sees `exists == true` and unconditionally re-executes `evm.GetDeploymentCode` + `k.SetCode` at the existing pointer address, with no version check preventing or gating the repeat call — contrasted with the legacy precompile, which would reject this second call with `"pointer at %s with version %d exists..."`.
