### Title
Attacker-controlled `ReceivedOutput` terms let an untrusted party make the group sign arbitrary messages under arbitrarily offset keys — (`File: networks/bitcoin/src/wallet/mod.rs` / `networks/bitcoin/src/wallet/send.rs`)

### Summary
The marketplace bug is that the *terms* under which a purchase executes (price, payment token, duration) are re-read at execution time and are not pinned to what the buyer expected. The same shape exists in `bitcoin-serai`'s signing path: a `SignableTransaction` derives the key it signs under, the prevout it claims to spend, and the sighash entirely from a `ReceivedOutput` whose fields (`offset`, `output.script_pubkey`, `outpoint`) are deserialized from untrusted bytes via `ReceivedOutput::read`. The only consistency check — that `p2tr_script_buf(group_key + offset·G)` equals `prevouts[i].script_pubkey` — compares two attacker-controlled values to each other, so it is vacuous. The threshold group will therefore produce a valid BIP-340 signature over an attacker-chosen sighash, under `group_key + offset·G` for an attacker-chosen `offset`, i.e. a related-key signing oracle for terms the group never committed to.

### Finding Description
`ReceivedOutput::read` trusts three attacker-supplied fields with no binding to on-chain reality:

- `offset` is read directly as a scalar via `Secp256k1::read_F(r)` (`networks/bitcoin/src/wallet/mod.rs:122-133`).
- `output` (the claimed `TxOut`, including `script_pubkey` and value) and `outpoint` are consensus-decoded from the same byte stream (`mod.rs:127-132`).

`SignableTransaction::new` then stores these as `self.offsets` and `self.prevouts` (`send.rs:176,253`). In `multisig`, the signing key is re-keyed per input with the supplied offset, and the sole validation is `p2tr_script_buf(offset.group_key()) == self.prevouts[i].script_pubkey` (`send.rs:273-281`). Since the attacker picks both `offset` and `script_pubkey`, they can always satisfy this by setting the script to the P2TR script of `group_key + offset·G`. `TransactionSignMachine::sign` then computes `taproot_key_spend_signature_hash(i, Prevouts::All(&self.tx.prevouts), Default)` — committing to the attacker-declared prevouts and attacker-declared outpoint — and produces a FROST signature under the attacker-chosen offset key (`send.rs:373-395`).

Nothing pins the expected terms of signing (which offset/key, which real outpoint, which prevout value) before the signature is produced — exactly the missing "term commitment" the external report recommends for `buyAccess`.

### Impact Explanation
The threshold signer acts as a signing oracle for *related* keys: for any scalar `δ` and any message `m` shaped as a taproot key-spend sighash (which the attacker fully controls, since they choose the outpoint, prevout contents, and all transaction outputs/fees), the group emits a valid BIP-340 signature under `X + δ·G`. This is "concrete signing of an unintended message": the signatures verify against keys the group never agreed to sign for. Because the offset key-space includes every derived key in the BIP-341 tweaked-key family, a signature under a colliding/attacker-selected offset can authenticate spends or authorizations for addresses outside the registered scanner offsets, and related-key signatures can be cross-used anywhere the tweaked-key construction is relied upon (the same `tweak_keys`/offset machinery reuses `group_key + δ·G` for Branch/Change/Forwarded paths in `processor/src/networks/bitcoin.rs:333-344`).

### Likelihood Explanation
Reachability requires only feeding crafted bytes to the documented untrusted surface `ReceivedOutput::read` and getting the resulting `SignableTransaction` signed — the rules explicitly list `ReceivedOutput::read` and `sign`/`complete` as attacker-reachable. No malicious validator, key leak, or curve misuse is needed; the attacker merely chooses field values, analogous to a token owner calling `updateTerms()`. Exploitation into direct fund theft additionally requires the forged related-key signature to be meaningful for some real output/authorization (e.g., an offset colliding with a registered/derived address), so the concrete signature-forgery primitive is certain while the monetary payoff is context-dependent — consistent with a Medium/High rating rather than guaranteed Critical.

### Recommendation
Bind the signing terms instead of trusting the serialized `ReceivedOutput`:

1. In `SignableTransaction::new` / `multisig`, validate `input.outpoint` and `input.output` against actual chain data (or at minimum against the `Scanner`'s registered script→offset table) rather than trusting the deserialized tuple — the scanner already records legitimate outputs via `scan_transaction`, so `multisig` should reject inputs whose `offset`/`script_pubkey`/`outpoint` combination was never observed on-chain.
2. Have the caller commit to the expected key per input (e.g., pass the expected `ProjectivePoint` or the registered `Scalar` offset) and verify `offset.group_key()` equals it, instead of deriving the signing key from untrusted bytes and self-checking it against equally-untrusted prevout bytes.
3. Treat `offset` as authenticated data: if `ReceivedOutput`s cross a trust boundary, carry a MAC or store them keyed by outpoint so `read` cannot inject arbitrary `(offset, output, outpoint)` triples.

### Proof of Concept
```rust
// Attacker-controlled bytes -> ReceivedOutput::read
let delta = Scalar::random(&mut OsRng);            // arbitrary related-key offset
let fake_prevout = TxOut {
    value: Amount::from_sat(100_000),
    // self-consistent with the offset key, so the multisig() check passes vacuously
    script_pubkey: p2tr_script_buf(even(group_key + GENERATOR * delta)).unwrap(),
};
let fake_outpoint = OutPoint::new(Txid::from_byte_array([0xAA; 32]), 0);
let malicious = ReceivedOutput { offset: delta, output: fake_prevout, outpoint: fake_outpoint };

// Any payment shape the attacker wants, any fee -> sighash fully attacker-chosen
let tx = SignableTransaction::new(
    vec![malicious],
    &[(attacker_script, 50_000)],
    None, None, 1,
).unwrap();

// Honest signers run this; the check at send.rs:277 passes because
// p2tr_script_buf(group_key + delta*G) == fake_prevout.script_pubkey by construction
let machine = tx.clone().multisig(&keys).unwrap();
let signed = run_frost(machine); // TransactionSignMachine::sign -> complete

// `signed.input[0].witness` is a valid BIP-340 signature under key `group_key + delta*G`
// over a sighash the attacker fully chose — an unintended-message signature.
```
The crucial lines: `ReceivedOutput::read` trusts `offset`/`output`/`outpoint` (`mod.rs:122-133`); `multisig` re-keys by the untrusted offset and only cross-checks two untrusted fields (`send.rs:276-281`); `sign` commits `Prevouts::All` to the untrusted prevouts and signs (`send.rs:373-390`).
