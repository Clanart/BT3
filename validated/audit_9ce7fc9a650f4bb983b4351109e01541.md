### Title
Silent hunk-index desync in Copilot conflict resolution splices AI resolutions into the wrong conflict blocks, corrupting committed file content - (File: app/src/lib/copilot-conflict-context.ts, app/src/lib/copilot-conflict-resolution.ts)

### Summary
The report's core pattern — a "safe" fallback that swallows an underlying inconsistency instead of failing loudly, causing the wrong value to be silently used — has a structural analog in GitHub Desktop's Copilot-assisted merge-conflict resolution feature. Two independent passes walk the *same* raw file content with *different* tolerance for malformed conflict markers: `extractConflictHunks` (used to build the prompt and the expected hunk count) and `reassembleResolvedFile` (used to splice the model's per-hunk output back into the file). Their marker-recovery behavior differs, so the two passes can disagree on how many/which conflict blocks exist. Resolutions are spliced back purely **by ordinal index**, not by matching content, so a desync causes AI-generated content for one conflict to be written into a different, unrelated location in the file — silently, with no integrity check between the two passes.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) parses a file for conflict hunks. When it encounters an ours-marker (`<<<<<<<`) but never finds a matching `>>>>>>>` before EOF, it discards the current attempt via `continue` — but only *after* its inner while loops have already advanced `i` all the way to `lines.length`: [1](#0-0) 
This means a single malformed/incomplete marker sequence causes the parser to consume the rest of the file searching for a closing marker, then give up — silently dropping any genuine, well-formed conflict hunks that occur later in the file. The resulting hunk count (`file.hunks.length`) becomes the "expected" count baked into the prompt and later enforced by `validateResolutionPaths`.

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`), which later splices the model's `resolvedContent` back into the *same* raw file content, uses a different recovery strategy: on an unmatched marker it advances only one line and resumes scanning: [2](#0-1) 
Because it resyncs after a single line instead of abandoning the rest of the file, it can find a different set/ordering of "well-formed" marker blocks than `extractConflictHunks` did for the same content, whenever a spurious marker-like sequence exists earlier in the file (e.g. a string literal such as `<<<<<<< something` embedded in ordinary code with no matching `=======`/`>>>>>>>`, which is entirely valid content for an attacker to include in a file on a branch they control).

Splicing is done purely by **hunk order**, not by content matching: [3](#0-2) 
There is no cross-check that the number or location of blocks found by `reassembleResolvedFile` matches what `extractConflictHunks` reported (`validateResolutionPaths` only compares hunk *counts*, and it compares against the count computed at context-gathering time, not a fresh parse at reassembly time — but both derive from the same flawed extraction, so a desync is silently possible). The reassembled `resolvedContent` is then written straight to disk by `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7169-7269`) once the user clicks "Continue Merge," and staged with `git add`: [4](#0-3) 

The result dialog (`copilot-conflicts-dialog.tsx`) surfaces the model's textual "reasoning" and a markdown summary, but does not appear to render a line-level diff of the actual `resolvedContent` against the original file for user verification, so a misaligned splice is not something the user is positioned to catch before continuing.

### Impact Explanation
An attacker who controls a branch/PR that the victim merges, rebases, or cherry-picks (a standard, unprivileged Git/GitHub interaction) can craft a file containing an incomplete conflict-marker-like line sequence positioned before a genuine conflicting hunk. This can desynchronize the two marker-parsing passes, causing GitHub Desktop's "Resolve with Copilot" feature to splice AI-generated resolution text into the wrong location of the file. The corrupted content is written to disk, staged, and — once the user clicks "Continue Merge" and commits — becomes part of what the user commits and potentially pushes, all without an explicit warning that the splice may be misaligned. This matches the "silent corruption of what the user commits or pushes" impact class from valid-impact criteria, since the code compiles/looks plausible but its structure may not match either side's intent.

### Likelihood Explanation
This requires: (1) the victim to have the Copilot conflict-resolution feature enabled and to click "Resolve with Copilot" (an opt-in but ordinary user action already built into the merge/rebase/cherry-pick conflict flow), and (2) a file with an attacker-crafted conflict scenario merged from an untrusted branch. No local access, credentials, or social engineering beyond a normal collaborative merge is required. I was not able to fully verify from the index alone whether other guards elsewhere (e.g., a stricter shared marker-parsing utility used consistently) prevent this in practice, or whether `validateResolutionPaths`'s indirect re-derivation of `expectedHunkCounts` from the same `extractConflictHunks` call effectively closes the gap in all cases — the two functions being distinct implementations with differing marker-recovery logic is what raises the concern, but reproducing an end-to-end desync would require constructing a concrete malformed-marker fixture and tracing it through both parsers, which exceeds what static reading confirms with certainty.

### Recommendation
Use a single, shared conflict-marker parser/validator for both prompt-building (`extractConflictHunks`) and reassembly (`reassembleResolvedFile`), with identical malformed-marker recovery semantics. Additionally, have `reassembleResolvedFile` (or a wrapper) re-derive the hunk count from the raw content at splice time and assert it exactly matches the count used when the prompt was built (not just when validating the model's returned count), failing loudly (skipping the file, surfacing it in `skippedFiles`) rather than silently splicing on any mismatch or ambiguity. Consider also rendering an explicit diff of `resolvedContent` vs. original content in the result dialog so users can visually verify what will be written before confirming.

2. In GitHub Desktop, merge/rebase/cherry-pick this branch so the file has a real conflict.
3. Click "Resolve with Copilot." `extractConflictHunks` (`copilot-conflict-context.ts:186-242`) hits the spurious marker, consumes the rest of the file searching for a closing `>>>>>>>`, finds none, and discards — potentially reporting 0 hunks (file skipped) or a hunk count that omits the real conflict depending on marker placement.
