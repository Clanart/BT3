### Title
Front-running `queueNewRewards` with `VLMGP.lock()` to steal proportional yield from long-term lockers - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder` distributes rewards as a single lump-sum bump to `rewardPerTokenStored` inside `queueNewRewards`, calculated against the *current* `totalStaked()` at the moment the reward is queued. Because `earned()`/`_earned()` weight a user's share purely by their instantaneous `balanceOf()` and not by staking duration, an attacker can front-run a pending `queueNewRewards` transaction with `VLMGP.lock(largeAmount)` to inflate their share of that exact reward distribution, then back-run with a claim to extract a disproportionate amount of yield that should have accrued to existing long-term lockers.

### Finding Description
The reward math lives in `_earned`:
```
_userVlmgpShare * (rewardPerToken(_rewardToken) - userRewardPerTokenPaid[_rewardToken][_account]) / 1e18 + userRewards[...]
``` [1](#0-0) 

`rewardPerTokenStored` is bumped by `queueNewRewards` in one shot, using `totalStaked()` (= `vlMGP.totalSupply()`) at call time:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 1e18) / totalStaked();
``` [2](#0-1) 

`balanceOf(_account)` in the rewarder simply reads the live staked amount from `MasterMagpie.stakingInfo`, with no time-weighting: [3](#0-2) 

The exploit path:
1. Attacker observes a `queueNewRewards` transaction (from an `onlyManager` reward source) pending in the mempool.
2. Attacker front-runs with `VLMGP.lock(largeAmount)` → `_lock` → `MasterMagpie.depositVlMGPFor` → `MasterMagpie._deposit`, which calls `_harvestBaseRewarder` (i.e. `updateFor` → `_updateFor`) **before** increasing `user.amount`: [4](#0-3) 
   This syncs `userRewardPerTokenPaid` to the *current* `rewardPerTokenStored` using the attacker's *old* (small/zero) balance, then immediately increases the attacker's staked balance to `largeAmount`. Both `balanceOf()` and `totalStaked()` (vlMGP's `totalSupply`) now reflect the new large stake.
3. The victim's `queueNewRewards` tx executes, bumping `rewardPerTokenStored` by `amountReward * 1e18 / totalStaked()` — `totalStaked()` already includes the attacker's newly locked amount.
4. Attacker calls `MasterMagpie.multiclaim` → `_claimBaseRewarder` → `getReward`/`getRewards`, triggering `_updateFor`/`updateReward` modifier, which computes `_earned` using the attacker's **large** `balanceOf` against the **entire** `rewardPerToken` delta since step 2, i.e., the whole newly-queued reward chunk, despite the attacker having held that large balance for zero time before the reward was added. [5](#0-4) [6](#0-5) 

The only forfeiture mechanism present, `_calExpireForfeit`/`getRewardablePercentWAD`, penalizes MGP payouts based on how much of a user's stake is in/expired cooldown slots — it has nothing to do with how recently a lock was created relative to a reward distribution, so it does not mitigate this attack. [7](#0-6) [8](#0-7) 

Existing guards (`onlyMasterMagpie`, `updateReward`, `nonReentrant`, `whenNotPaused`) don't prevent this because the exploit doesn't rely on reentrancy or bypassing access control — it relies purely on transaction ordering (MEV/front-running) around a legitimate public `lock()` call and a legitimate reward-funding call.

### Impact Explanation
This is theft of unclaimed yield: existing long-term `vlMGP` lockers who should have received a larger proportional share of a reward distribution (since they held their stake for the full accrual period) instead see their share diluted by a staker who joined an instant before the distribution and exits shortly after. This matches the Immunefi impact class "theft of unclaimed yield."

### Likelihood Explanation
- Requires only unprivileged capital: attacker needs enough MGP tokens to lock, and public mempool visibility of `queueNewRewards` transactions from reward managers (compounders, harvesters, bribe distributors, etc., which call `queueNewRewards` regularly).
- No special permissions, reentrancy, or governance/admin access needed — only calling public `lock()`/`lockFor()` and then `multiclaim()`.
- Repeatable every time a sizable `queueNewRewards` call is queued and visible pre-confirmation (public mempool chains) or via searcher/builder relationships.
- Capital is not fully free — the attacker must actually lock MGP (subject to VLMGP's cooldown mechanics to eventually withdraw principal), which somewhat limits frequency/capital efficiency but does not prevent repeated extraction of large one-off reward events, especially bribe/incentive lump-sum deposits.

### Recommendation
Move to a time-weighted / streamed reward-rate model (e.g., Synthetix-style `rewardRate` accrued per second over a fixed duration) instead of an instantaneous lump-sum bump to `rewardPerTokenStored`, so that a deposit occurring immediately before a reward event cannot capture a share proportional to instantaneous balance rather than elapsed staking time. Alternatively, apply a minimum holding-period / vesting requirement (similar in spirit to `getRewardablePercentWAD`) directly to reward-token earnings based on time since last balance increase, not just to MGP payouts based on cooldown status.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder` and a reward token; set up an existing "long-term locker" LP with `lockAmount` locked well before any reward event, and let some time pass.
2. Prepare a `queueNewRewards(rewardAmount, rewardToken)` call from an authorized manager but do not yet mine it (simulate mempool visibility).
3. Front-run: attacker calls `VLMGP.lock(largeAmount)` where `largeAmount >> lockAmount`, executed and mined before the `queueNewRewards` tx.
4. Mine the `queueNewRewards` tx.
5. Back-run: attacker calls `MasterMagpie.multiclaim([vlMGPAddress])` (or reads `earned(attacker, rewardToken)`).
6. Assert:
   - `earned(attacker, rewardToken)` ≈ `rewardAmount * largeAmount / (largeAmount + lockAmount)`, i.e., the attacker captures a share proportional to instantaneous balance, not to the (near-zero) time they've held it.
   - Compare against `earned(longTermLocker, rewardToken)`, showing the long-term locker's share is diluted below what it would have been absent the attacker's front-run (i.e., below `rewardAmount * lockAmount / lockAmount` == full `rewardAmount` had attacker not front-run).
   - Confirm attacker's `earned()` exceeds any reasonable time-weighted allocation (e.g., zero, since attacker held the new balance for 0 blocks before the reward event).

        uint256 fullyInLock = getUserTotalLocked(_user);

        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
