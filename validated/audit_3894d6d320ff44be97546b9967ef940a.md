### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s — funds counted as received that cannot be spent (networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class is "assets counted toward available balances that are not actually available/spendable, leading the system to promise redemptions (here: signed spends) it cannot fulfill." In `bitcoin-serai`, `Scanner::scan_block` scans every transaction in a block — including `txdata[0]`, the coinbase — and returns matching outputs as `ReceivedOutput`s indistinguishable from immediately spendable ones. A `ReceivedOutput` from a coinbase cannot be spent until 100 blocks of maturity, yet nothing in the type carries a maturity flag. A downstream signer fed these outputs into `SignableTransaction::new` will construct and FROST-sign a transaction that consensus rejects. [1](#0-0) 

### Finding Description
`Scanner::scan_block` iterates `block.txdata` in full:

```rust
for tx in &block.txdata {
  res.extend(self.scan_transaction(tx));
}
```

`scan_transaction` (wallet/mod.rs:199-214) emits a `ReceivedOutput` for any output whose `script_pubkey` matches a registered script — including the block's coinbase transaction. Coinbase outputs are unspendable for 100 blocks, yet are returned identically to normal outputs.

The consumer-facing code is aware of the trap: `processor/src/networks/bitcoin.rs` `get_outputs` explicitly skips `block.txdata[1 ..]` boundary with the comment "Skip the coinbase transaction which is burdened by maturity" [2](#0-1) , and `scan_block`'s own doc comment notes a post-processing pass is required. However, the in-scope `networks/bitcoin` wallet API itself enforces nothing: `ReceivedOutput` has no maturity marker, and `SignableTransaction::new` (wallet/send.rs:150-256) will happily take the coinbase `ReceivedOutput` as an input, compute fees against it, and produce a signable transaction spending an immature coinbase. The resulting transaction is invalid under consensus rules — the multisig completes a FROST signing round producing a transaction the network rejects.

This mirrors the Unitas bug directly: the "reserve" (scanned balance) includes assets (coinbase rewards / portfolio funds) that are not actually usable, so the reported/acted-upon balance overstates what can be spent, and redemption (the spend) fails despite apparently sufficient funds.

### Impact Explanation
An unprivileged party — any miner — can reach this with public inputs: mine a block whose coinbase pays to the multisig's external/branch/forwarded script (the script is public). Any consumer of `Scanner::scan_block` that does not implement the documented-but-unenforced filtering will treat the immature output as received, schedule it as a UTXO, and burn a threshold signing round on a transaction that can never confirm. For forwarded/refund flows this can wedge automated spend pipelines until the output is manually excluded, and payments sized against the "full balance" (including the immature output) will fail — the exact "reserve ratio above 100% yet redemption fails" shape of the source report. Impact is availability/accounting correctness rather than direct theft, consistent with Medium.

### Likelihood Explanation
Requires a miner to pay the multisig script in a coinbase (a donation-style attack costing block subsidy to the multisig itself — attacker gains no funds, only DoS), plus a consumer that uses `scan_block` without the maturity filter. The in-tree processor already filters coinbases, so only external integrators of the wallet API are exposed. The code documents the caveat, which weighs against severity; the finding stands because the API returns a type that silently conflates spendable and unspendable outputs and the failure only manifests post-signing.

### Recommendation
Give `scan_block` maturity awareness: either skip `block.txdata[0]` by default (matching `get_outputs` in `processor/src/networks/bitcoin.rs:691`), or record a `is_coinbase`/confirmation-depth flag on `ReceivedOutput` and have `SignableTransaction::new` reject immature coinbase inputs. At minimum, expose a `scan_block` variant that returns only immediately-spendable outputs so the safe behavior is the default rather than a documented footnote.

### Proof of Concept
1. Register a `Scanner` for multisig key `K` via `Scanner::new(K)`.
2. Miner produces a block whose coinbase `txdata[0]` has an output paying `p2tr_script_buf(K)` (or a registered offset script).
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` for that coinbase output, indistinguishable from a normal deposit (verified in `networks/bitcoin/tests/wallet.rs:40-77`, where the test itself relies on this behavior and mines 100 blocks before spending).
4. Construct `SignableTransaction::new(vec![received], payments, change, None, fee)` — succeeds, since no maturity check exists in wallet/send.rs:150-256.
5. `TransactionMachine::preprocess`/`sign`/`complete` produce a fully signed transaction; broadcasting it fails consensus validation (`bad-txns-premature-spend-of-coinbase`), proving the reported output was not spendable.
