### Title
Unbounded aggregate-signature deserialization enables remote resource exhaustion - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` trusts a 32-bit count and then deserializes that many group elements into a `Vec`, without enforcing an aggregate-size, expected-signer-count, or remaining-input bound. [1](#0-0) 

### Finding Description
The serialized format begins with an attacker-controlled four-byte little-endian `Rs` length. The reader iterates up to `u32::MAX` times, calling `C::read_G` and storing every successfully decoded point in memory. [2](#0-1) 

If parsing succeeds, `verify` creates a multiexponentiation containing two pairs per supplied nonce plus the final generator term, causing additional allocation and CPU consumption proportional to the attacker-controlled count. [3](#0-2) 

Unlike bounded callers, this primitive gives the untrusted input itself authority over the loop count. [4](#0-3) 

### Impact Explanation
An unprivileged party supplying aggregate-signature bytes can force a host to perform expensive point decoding, grow `Rs` to attacker-controlled size, and subsequently allocate and evaluate an attacker-sized multiexponentiation. [5](#0-4) [6](#0-5) 

Because the count permits up to `4,294,967,295` entries, a sustained input stream can exhaust memory or consume enough CPU time to make the verifying/signing service unavailable. [7](#0-6) 

### Likelihood Explanation
The required capability is only control of bytes passed to `SchnorrAggregate::read` or an aggregate-signature verification path. [8](#0-7) 

No private keys, malformed internal state, collusion, or invalid curve implementation is required; the length field is sufficient to control the amount of attempted work. [9](#0-8) 

### Recommendation
Add an explicit maximum aggregate length before allocation or iteration, preferably derived from the validator/participant set when available. [2](#0-1) 

Change the API to accept an expected signer count or deserialization context, reject values greater than that count, and consider rejecting trailing bytes after the final scalar. [10](#0-9) [11](#0-10) 

### Proof of Concept
A conceptual PoC supplies a large encoded count followed by repeatedly encoded valid group elements:

```rust
use std::io::{self, Read};

use frost::curve::Ristretto;
use ciphersuite::group::GroupEncoding;
use schnorr::SchnorrAggregate;

struct RepeatedPoint {
  encoded: Vec<u8>,
}

impl Read for RepeatedPoint {
  fn read(&mut self, out: &mut [u8]) -> io::Result<usize> {
    out.copy_from_slice(&self.encoded[.. out.len()]);
    Ok(out.len())
  }
}

let mut encoded = Vec::new();
encoded.extend(1_000_000_u32.to_le_bytes());

let point = RepeatedPoint {
  encoded: Ristretto::generator().to_bytes().as_ref().to_vec(),
};

let mut input = encoded.chain(point);
let aggregate = SchnorrAggregate::<Ristretto>::read(&mut input).unwrap();
assert_eq!(aggregate.Rs().len(), 1_000_000);
```

This declares one million nonces and causes the parser to perform one million point decodes and stores all of them before the caller can reject the aggregate as too large. [1](#0-0)
