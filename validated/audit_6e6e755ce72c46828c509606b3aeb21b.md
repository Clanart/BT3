## Finding [1](#0-0) 

### Title
Unchecked ERC-20 return value in escrow release lets `withdraw()` silently "succeed" while beneficiary receives no funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` (Tron variant) escrows arbitrary, unvalidated ERC-20 tokens supplied by the order creator (`order.inputs[i].token`) using the safe pattern (`IERC20(token).safeTransferFrom`), but releases that same escrow using a raw low-level `.call` that only checks whether the call reverted, not the ABI-decoded boolean it returns. This is precisely the unchecked-transfer pattern the external report warns about, except here it sits on the *outgoing* leg of custody (escrow release / refund / dust sweep) rather than a routine transfer, so a non-reverting `false` return silently finalizes escrow accounting while leaving the beneficiary unpaid.

### Finding Description
Deposits into escrow use the safe wrapper: [2](#0-1) 

But the internal `withdraw()` function, which is the sole path that actually pays out escrowed input tokens to the beneficiary (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` and from `onGetResponse`), uses a raw `.call` and treats a non-reverting call as sufficient proof of a successful transfer: [3](#0-2) 

The same pattern repeats for the transaction-fee payout inside `withdraw()`: [4](#0-3) 

and again in the admin-driven `SweepDust` branch of `onAccept`: [5](#0-4) 

In all three spots, `success` only reflects whether the target contract call reverted — it says nothing about the decoded return value of `transfer()`. A token that returns `false` (instead of reverting) on a failed transfer — a well-known and common ERC-20/TRC-20 non-compliance pattern, and one an order creator can deliberately choose since `order.inputs[i].token` is an arbitrary, unvalidated address at order-placement time — causes:
1. `success == true` (the low-level call didn't revert),
2. `_orders[body.commitment][token] -= amount` executes anyway,
3. `EscrowReleased`/`EscrowRefunded`/`DustSwept` is emitted,
4. but the beneficiary receives zero tokens.

Since `_orders[...]` is now decremented to zero (or reduced) and `_filled[body.commitment]` is already set, there is no remaining code path to retry or recover the payout — the escrowed tokens are permanently stranded in the contract while the protocol's own bookkeeping asserts the payout already happened. Notably, this contradicts the pattern used in the parallel, non-Tron implementation `IntentsBase.sol`, which correctly uses `IERC20(token).safeTransfer(...)` for the equivalent release path: [6](#0-5) 

This shows the Tron variant is a regression/divergence from the safer pattern used elsewhere in the same codebase.

### Impact Explanation
This causes real loss of funds: escrow accounting is finalized (state says "paid"/"refunded") without the corresponding token transfer actually completing, for any token whose `transfer()` implementation returns `false` on failure rather than reverting. Because token addresses in `order.inputs` are attacker/user-supplied at order-creation time with no allowlist, this is directly reachable without needing a malicious relayer, prover, or admin — only a token contract with non-standard-but-legal ERC-20 semantics (which the intents system does not restrict against).

### Likelihood Explanation
The likelihood is moderate: it requires that one of the escrowed input tokens is a non-standard ERC-20 implementation that can return `false` instead of reverting under some condition (blacklist/pause/insufficient-balance-race, etc.). Given the protocol accepts arbitrary token addresses for `order.inputs`, and Tron's TRC-20 ecosystem specifically is known for inconsistent return-value semantics (this is why the wider codebase deliberately uses `SafeERC20`), this is a realistic condition rather than a purely theoretical one.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with the rest of the contract (which already imports and uses `SafeERC20` for deposits) and consistent with `IntentsBase.sol`'s `_withdraw`. This ensures a `false` return value reverts the transaction instead of silently finalizing escrow state.

### Proof of Concept
1. Order creator places an order via `placeOrder` with `order.inputs[0].token = MaliciousToken`, a contract implementing standard `transfer()`/`transferFrom()` except that `transfer()` returns `false` (no revert) once a configurable condition is met (e.g., after a certain block, or via an owner-toggled flag) — this passes the escrow deposit step because `safeTransferFrom` succeeds normally.
2. Order is filled/cancelled normally; Hyperbridge host relays a valid, correctly proven `RedeemEscrow`/`RefundEscrow` `PostRequest` to `onAccept`.
3. `onAccept` → `withdraw(body, ...)` executes; for the malicious token, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` but with encoded `false` payload (transfer silently failed).
4. `withdraw()` does not decode/check the returned boolean, so it proceeds to `_orders[body.commitment][token] -= amount;` and emits `EscrowReleased`/`EscrowRefunded`.
5. Beneficiary's on-chain balance of the token is unchanged; the escrowed tokens remain locked in the `IntentGatewayV2` contract with no code path left to retry the payout, since escrow accounting already shows the funds as disbursed.
