### Title
`ThresholdKeys::read`/`ThresholdKeys::new` accepts semantically inconsistent key material — secret share and verification shares are never validated against each other or a common polynomial - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, an interpolation method, a `secret_share`, and `n` verification shares from untrusted bytes, then forwards them to `ThresholdKeys::new`. `ThresholdKeys::new` performs only structural checks — share count, participant index bounds, and interpolation applicability — but never verifies that `secret_share * G == verification_shares[i]`, nor that the `n` verification shares are mutually consistent (i.e., lie on a common degree `t-1` polynomial). The group key is derived solely from `verification_shares[1..=t]` ( [1](#0-0) ), so shares at indexes `t+1..=n` are accepted without any consistency check at all. Analogous to the CGI parameter-injection report, attacker-controlled input slips past a validation routine that checks form but not semantics, and downstream code (`view`, FROST signing, blame) consumes the result as if it were trusted, consistent key material.

### Finding Description
`ThresholdKeys::read` parses the curve ID, threshold parameters, `Interpolation` (Constant reads `n` scalars; Lagrange reads none), the secret share, and `n` verification shares via `read_G`, then calls `ThresholdKeys::new` [2](#0-1) . `ThresholdKeys::new` only checks `verification_shares.len() == n` and `participant <= n` [3](#0-2) , then computes `group_key = Σ_{i=1..=t} share[i] * λ_i` [1](#0-0) . Missing checks:

1. `secret_share * G == verification_shares[i]` — the holder's own share is never bound to its verification share. Every legitimate constructor guarantees this (`dealer::key_gen` inserts `G * secret_share` [4](#0-3) ; PedPoP derives shares from verified commitments [5](#0-4) ), but `read` bypasses that invariant.
2. Verification shares `t+1..=n` never influence `group_key` and are never checked for polynomial consistency, so two different serialized blobs can yield the same `group_key` yet disagree on `verification_share(l)` for `l > t`.
3. For `Interpolation::Constant`, only `t == n` is enforced; the `n` binding-factor scalars are read from the wire [6](#0-5)  with no check that they correspond to the MuSig binding factors for the supplied keys.

### Impact Explanation
A party able to supply bytes to `ThresholdKeys::read` produces a `ThresholdKeys` object that passes every validation gate yet violates the core invariant binding secret share, verification shares, and group key. Concretely:

- The caller can be made to operate under a `group_key()` the attacker chose (by choosing shares `1..=t`) while the holder's `secret_share` does not correspond to it — every signing session then produces shares that fail verification, or, if the attacker also sets `verification_shares[i]` consistently with a known scalar, the "multisig" key is effectively solo-controlled by the attacker while the victim believes it participates in a threshold scheme. Deposits/outputs attributed to `group_key()` are unspendable by the honest threshold.
- Because shares `t+1..=n` are unchecked, signing sets that include those indexes interpolate verification shares inconsistent with the group key: `verify_share` in FROST uses `view.verification_share(l)` [7](#0-6) , so honest participants get blamed as `InvalidShare`, or completion falls through to `InternalError` [8](#0-7) , enabling targeted share misattribution and liveness/signing-failure attacks.
- With `Interpolation::Constant`, attacker-chosen binding factors combined with attacker-chosen verification shares produce a `group_key` that is not the MuSig aggregate of the shares, breaking the rogue-key resistance the DKG guarantees.

This maps to the accepted impact classes: funds reported received under a key that is not spendable by the claimed threshold, and shares verified against an incorrect verifier formula.

### Likelihood Explanation
Reachability depends on a path feeding untrusted serialization into `ThresholdKeys::read` (backup/restore, key import, or any peer-supplied key blob — the function is `pub` and explicitly designed for reading externally supplied encodings, and the codebase's own test vectors exercise it with externally generated data [9](#0-8) ). No cryptographic break is needed; the attacker merely crafts a byte string that satisfies the checked length/bounds constraints. Since `new` is also `pub`, any consumer constructing keys from mixed sources (e.g., `promote`, recovery flows, or integrators assembling shares) inherits the same gap — `GeneratorPromotion::complete` even unwraps `ThresholdKeys::new` on assembled shares [10](#0-9) . Severity: High where attacker-supplied key blobs are accepted; Medium as a defense-in-depth failure otherwise.

### Recommendation
In `ThresholdKeys::new` (so `read` and all constructors benefit):

- Reject if `C::generator() * *secret_share != verification_shares[&params.i()]`.
- For `Interpolation::Lagrange`, verify the full set of verification shares is consistent with a degree `t-1` polynomial — e.g., check that for every `l`, `share[l]` equals the evaluation implied by any fixed `t`-subset, or equivalently that the shares lie on a common polynomial (a multiexp over all `n` shares against Lagrange-style check coefficients suffices).
- For `Interpolation::Constant`, verify the supplied binding-factor scalars actually derive `group_key` from the verification shares as `Σ b_i * share[i]` (recomputing the MuSig aggregate rather than trusting the encoded factors).
- Document that `ThresholdKeys::read` is only safe for authenticated/trusted storage until these checks exist.

### Proof of Concept
For any `C`, let the attacker pick scalar `x` (known secret) and scalars `v_{t+1}..v_n` arbitrarily:

1. Set `verification_shares[i] = G * x_i` for `i = 1..=t` where the `x_i` are attacker-known values on a polynomial — e.g., `n = t = 1`, `verification_shares[1] = G * x`.
2. Set `secret_share = y` with `y != x` (violating the share↔verification-share binding).
3. Serialize per `ThresholdKeys::read`'s format: `u32 C::ID.len() || C::ID || t || n || i=1 || 0x01 (Lagrange) || repr(y) || bytes(verification_shares[1])`.
4. `ThresholdKeys::read` succeeds — all structural checks pass — yielding keys with `group_key() = G*x` (attacker-known discrete log) while `original_secret_share() = y`. Any FROST session initiated by the holder signs shares of `y` that fail `verify_share` against `G*x`, and `complete` yields `InternalError`; meanwhile any scanner/address derivation using `group_key()` attributes funds to an attacker-controlled key.

For the multi-share variant (`n > t`), setting `verification_shares[t+1..=n]` to random points leaves `group_key` unchanged but makes any signing set containing those participants produce shares that are blamed or fail — a per-subset liveness/misattribution oracle, exactly mirroring "crafted input passes the filter and poisons downstream interpretation."
