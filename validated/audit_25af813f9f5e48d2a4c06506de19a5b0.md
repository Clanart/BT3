### Title
Out-of-range participant index in PedPoP blame handling panics on unauthenticated index, crashing the node — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2015-5158 is a crash caused by an invalid opcode byte in an attacker-supplied command block — i.e., an attacker-controlled value used as an unchecked index/dispatch selector. The analog in Serai is PedPoP's blame path: `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` indexes `self.commitments[&sender]`, where `sender`/`recipient` are `Participant` values supplied alongside attacker-controlled bytes (`EncryptedMessage::read`, `EncryptionKeyProof::read`). `AdditionalBlameMachine::new` only registers participants `1..=n`, so any index `> n` causes a HashMap-index panic — a reachable crash, exactly the invalid-selector → crash class of the QEMU bug.

### Finding Description
`AdditionalBlameMachine::new` populates `encryption.enc_keys` and `commitments` only for `Participant::new(i)` with `i in 1..=n` (`crypto/dkg/pedpop/src/lib.rs:656-660`). When `blame(sender, recipient, msg, proof)` is invoked, `blame_internal` first calls `decrypt_with_proof`, which — once the attacker-provided `msg.pop` Schnorr signature verifies and a `proof` is supplied — evaluates `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`). A `decryptor`/`recipient` `Participant` not in `1..=n` (e.g. `n+1`, or any nonzero u16) panics via HashMap indexing. Similarly, if decryption succeeds, `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`) panics for an out-of-range `sender`. There is no bounds check of `sender`/`recipient` against `params.n()` anywhere in the blame path — the invalid "opcode" (participant index) is trusted blindly.

### Impact Explanation
An attacker who can trigger a blame evaluation — supplying a syntactically valid `EncryptedMessage` (its PoP is self-signed under the attacker's chosen ephemeral key, so always satisfiable), a well-formed `EncryptionKeyProof` byte string, and an out-of-range accused/accuser index — causes a panic in the executing validator. This aborts the VerifyBlame handling (processor/src/key_gen.rs:504-563 calls `blame` without validating `accuser`/`accused` against `params.n()`), crashing the processor task — a denial of service analogous to the QEMU instance crash. CVSS-class: Medium, availability-only.

### Likelihood Explanation
Reachable with public inputs: the `EncryptedMessage`/`EncryptionKeyProof` bytes and both participant indices are attacker-influenced message fields. The only gating check is `msg.pop.verify`, which the attacker trivially satisfies since they choose the key. Caveat: full end-to-end reachability assumes the `accused` field in `CoordinatorMessage::VerifyBlame` is not constrained to `1..=n` upstream — I could not fully verify the message-validation layer before this index reaches `blame`.

### Recommendation
Validate `sender` and `recipient` against `1..=n` in `AdditionalBlameMachine::blame`/`BlameMachine::blame` before use, and replace `enc_keys[&decryptor]` / `commitments[&sender]` indexing with `.get()` returning an error/blame verdict rather than panicking.

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }

  pub fn new(
    context: [u8; 32],
    n: u16,
    mut commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<Self, PedPoPError<C>> {
    let mut commitments = HashMap::new();
    let mut encryption = Decryption::new(context);
    for i in 1 ..= n {
      let i = Participant::new(i).unwrap();
      let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
      commitments.insert(i, encryption.register(i, msg).commitments);
    }
    Ok(AdditionalBlameMachine(BlameMachine { commitments, encryption, result: None }))
  }
