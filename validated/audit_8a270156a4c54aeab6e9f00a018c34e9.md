## Title
Order-based (not position-verified) splicing of AI conflict-resolution content allows attacker-crafted marker-like content in a merged/rebased branch to silently corrupt committed file content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The external report's bug class is: a piece of state that should be advanced by *the actual number of elapsed units* is instead advanced by a fixed, naive counter increment, letting an attacker exploit the mismatch between "counter position" and "real position" to get the wrong value applied. The closest verified analog in this GitHub Desktop codebase is `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts`, which reconstructs a fully-resolved file after Copilot-assisted conflict resolution by re-scanning the raw on-disk file for conflict-marker blocks with a simple line-by-line regex walk and splicing in the Nth model-produced hunk resolution using a bare incrementing `hunkIndex` counter — explicitly "matched by order, not by line number" — rather than any structural correlation to the specific conflict hunk the model actually resolved.

### Finding Description
`reassembleResolvedFile` walks the raw conflicted file content and, whenever it finds a line matching `^<{7}(?:\s|$)` (an "ours" conflict marker), looks ahead for a `=======` separator and a `>>>>>>>` closer: [1](#0-0) 

Each time a well-formed marker block is found, the code takes `hunkResolutions[hunkIndex]` — the Nth resolution returned by the LLM — and splices it in, then increments `hunkIndex`: [2](#0-1) 

The function's own doc-comment concedes the fragility of this design: resolutions are "matched by order, not by line number," and a malformed/stray marker is silently treated as ordinary content instead of aborting reassembly: [3](#0-2) 

The only safety check performed elsewhere is a *count* check — that the number of hunks the model returned matches the number of hunks that were extracted for the prompt (`validateResolutionPaths`): [4](#0-3) 

This check validates *quantity*, not *identity/position* of each hunk. If the file content that produced the conflict (which is fully attacker-controlled, since it comes from the branch/commits/PR the user is merging, rebasing, or cherry-picking from — i.e., a fetched/cloned repository object) contains any additional lines that coincidentally match the marker regexes (`<{7}`, `={7}`, `>{7}` — 7+ of a character followed by whitespace/EOL, which is trivial to place inside a code comment, string literal, markdown document, or even a leftover unresolved marker from a prior, different merge captured verbatim in file history), the number and boundaries of "marker blocks" found by this walker can diverge from the number/boundaries of hunks that were shown to the model when building the prompt (in `copilot-conflict-context.ts`, which was not fully re-verified in this session — see Likelihood/uncertainty note below). When that divergence happens while the *total hunk count* still matches by coincidence (e.g., an extra spurious block offsets a missing real one, or ordering shifts by one), `hunkIndex` will pull the wrong `IHunkResolution` for a given marker block and splice unrelated content into a different part of the file than the one the model actually reasoned about — all without any error, warning, or user-visible signal, since the write path (`_applyCopilotConflictResolutions`) directly writes `resolution.resolvedContent` to disk once the count check passes: [5](#0-4) 

### Impact Explanation
This is silent corruption of what the user commits/pushes: the reassembled file — with content misattributed to the wrong location in the file — is written to disk and staged (`git add`) as part of completing the merge/rebase/cherry-pick, then committed and potentially pushed, without the user being shown any discrepancy (the diff review UI would show *some* diff, but a user reviewing an AI-merged file has no ground truth to detect that resolution N landed on hunk M). Depending on what content collides into what location, this can silently drop, duplicate, or splice unrelated code/config across files, potentially reintroducing vulnerable code, dropping security-relevant lines, or corrupting build/dependency files, sourced entirely from a hostile branch the victim never reviewed line-by-line before triggering AI-assisted resolution.

### Likelihood Explanation
Exploitability requires only that the attacker control content the victim merges (a very ordinary attacker capability for a public PR/branch), and that the malicious file contain marker-like text that isn't a real conflict marker. This is a plausible occurrence in real repositories (documentation about Git conflicts, embedded diff/patch examples, previously-committed unresolved markers, or crafted strings deliberately matching `/^<{7}(?:\s|$)/`, `/^={7}$/`, `/^>{7}(?:\s|$)/`). I was not able to fully cross-reference `app/src/lib/copilot-conflict-context.ts`'s hunk-extraction logic in this session (the tool budget was exhausted before completing that comparison), so I cannot confirm from code alone that a discrepancy between context-building and reassembly is currently reachable in practice, or whether upstream validation (e.g., stricter hunk boundary detection during context construction) already prevents it. This is the main open uncertainty for this finding.

### Recommendation
Do not correlate LLM output to conflict-marker blocks purely by ordinal position. Instead:
- Tag each hunk with a stable identifier (e.g., a start/end line index or a hash of the exact original marker-block content) when building the prompt context in `copilot-conflict-context.ts`, and require the model's response to echo that identifier.
- In `reassembleResolvedFile`, validate that the located marker block's original content matches the corresponding hunk's known original content, and refuse to splice (falling back to manual resolution) if any structural mismatch is detected — rather than only checking total hunk counts.
- Treat any residual/malformed marker or unexpected extra marker-like line as a hard failure of AI-assisted resolution for that file, not as "regular content" to pass through silently.

### Proof of Concept
Conceptual PoC (not fully verified end-to-end due to inability to inspect `copilot-conflict-context.ts` in this session):
1. Attacker opens/maintains a branch or PR containing a file, e.g. `notes.md`, with content:
   ```
   Example of a conflict marker:
   <<<<<<< example
   some text
   =======
   other text
   >>>>>>> example
   ```
   placed inside a region that will end up on one side of a real merge conflict with the victim's branch (e.g., adjacent to a genuinely conflicting line).
2. Victim merges/rebases this branch in GitHub Desktop and invokes "Resolve with Copilot".
3. The prompt-construction step counts N real conflict hunks based on its own hunk-splitting logic; the reassembly step (`reassembleResolvedFile`) independently re-scans the same raw file for marker-shaped lines and may count/segment blocks differently because of the attacker's embedded look-alike marker text.
4. If the totals coincidentally still agree (or the mismatch is off-by-one within a file with multiple hunks), `hunkResolutions[hunkIndex]` is spliced into the wrong location, and `_applyCopilotConflictResolutions` writes and stages this corrupted content without any error: [6](#0-5) 

Further verification of step 3 (confirming an actual divergence between `copilot-conflict-context.ts`'s hunk splitter and `reassembleResolvedFile`'s marker walker) is recommended before treating this as a confirmed, fully-reproducible vulnerability rather than a design-level risk clearly acknowledged in the code's own comments.
