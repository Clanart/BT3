### Title
Unhandled overflow exception when casting negative fee in `validate_spend_bundle` can crash mempool processing - (File: `chia/full_node/mempool_manager.py`)

### Summary
The Fuel Labs commit fixed an unguarded arithmetic overflow in resource/coin selection totals by switching to saturating arithmetic. The chia-blockchain analog is in `MempoolManager.validate_spend_bundle`, where the transaction fee is computed as `fees = uint64(removal_amount - addition_amount)` at [1](#0-0) , with `removal_amount` and `addition_amount` accumulated as plain Python `int`s from coin amounts [2](#0-1) [3](#0-2) .

### Finding Description
`addition_amount` is the sum of every `CREATE_COIN` amount across all coin spends in the submitted `SpendBundle` [2](#0-1) , and `removal_amount` is the sum of the amounts of the coins actually being spent [3](#0-2) . Nothing in the code path prior to line 814 asserts that `addition_amount <= removal_amount`. If a spend bundle's puzzles create coins whose total value exceeds the value of the coins spent (i.e. attempted value creation / negative fee), `removal_amount - addition_amount` is negative, and casting that negative Python `int` to `uint64` raises an `OverflowError` per `chia_rs`'s sized-int semantics (confirmed by `Coin(H1, H2, -1)` raising `"OverflowError: can't convert negative int to unsigned"`, [4](#0-3) , and by the block-fee helper explicitly documenting/handling this case with `pytest.raises(ValueError, match="does not fit into uint64")` [5](#0-4) ).

Unlike `compute_block_fee` in `chia/consensus/block_creation.py` (which is tested for and presumably guards this exact negative case), `validate_spend_bundle`'s `fees = uint64(removal_amount - addition_amount)` line has no equivalent guard or try/except before it. `validate_spend_bundle` is invoked from `add_spend_bundle`, which is reached whenever any unprivileged peer/RPC caller submits a new `SpendBundle` to the mempool [6](#0-5) . `add_spend_bundle` itself has no try/except around the call to `validate_spend_bundle` [7](#0-6) , so an `OverflowError` raised deep inside would propagate up uncaught through the mempool add path.

### Impact Explanation
If this exception is not caught by an outer layer (e.g. the full node's RPC/message handler), a single malicious spend bundle that spends less value than it creates could throw an unhandled exception during mempool admission, which — depending on how the calling code (full-node transaction processing queue / RPC handler) manages exceptions — could disrupt processing of that specific submission or, in the worst case, destabilize the mempool-manager's spend-bundle validation coroutine (a spend-triggered transaction-processing halt scenario), rather than being cleanly rejected with a well-defined `Err` code the way `INVALID_BLOCK_FEE_AMOUNT`/`BLOCK_COST_EXCEEDS_MAX` are (as seen immediately after this line at [8](#0-7) ).

### Likelihood Explanation
I could not confirm within the available index whether an upstream consensus/CLVM rule (enforced by the Rust-side condition parser that produces `conds`/`SpendBundleConditions`) already guarantees `addition_amount <= removal_amount` for any bundle that reaches this point, nor could I locate the exact exception-handling wrapper (if any) around `MempoolManager.add_spend_bundle`'s caller in the full node's transaction-processing queue. Without confirming these two points, I cannot be certain this path is actually reachable with attacker-controlled input reaching an unguarded `uint64()` cast, or that any resulting exception is not already caught and converted into a normal rejection elsewhere.

### Recommendation
Given the above uncertainty, add an explicit, defensive check before the fee computation — e.g. `if addition_amount > removal_amount: return Err.MINTING_COIN, None, []` (mirroring the style of the subsequent `cost`/`fees` checks) — or wrap the `uint64()` cast so any overflow degrades to a normal `Err` return value instead of an uncaught exception, analogous to how `compute_block_fee` documents/handles the negative case.

### Proof of Concept
Not constructed — I was unable to verify (a) whether upstream consensus/CLVM validation already forbids `addition_amount > removal_amount` before `conds` is produced, and (b) whether `add_spend_bundle`'s caller already catches exceptions from `validate_spend_bundle`. Both would need to be confirmed with a live Devin session (full test execution / tracing through the Rust binding and the full-node's RPC/transaction-queue exception handling) to determine actual reachability and severity before treating this as a confirmed vulnerability rather than a hardening gap.
