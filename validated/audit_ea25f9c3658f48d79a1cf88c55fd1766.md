The strongest local analog to the Lido point-in-time balance bug is in the `IntentGatewayV2` escrow ledger, which records fixed nominal token amounts per order at `placeOrder()` time but never reconciles those nominal amounts against the contract's actual token balance when releasing escrow on fill, cancel, or refund.

### Title
Escrow ledger over-credits early withdrawals against a shared token balance that can shrink independently of `_orders` accounting - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`IntentsBase` tracks escrowed input tokens per order in `_orders[commitment][token]`, a nominal amount fixed at `placeOrder()` time [1](#0-0) . Withdrawal (fill settlement, same-chain/cross-chain cancel, and cross-chain refund) all route through `_withdraw`/`withdraw`, which transfers exactly the recorded nominal amount out of the contract's pooled balance for that token, without ever re-measuring the contract's actual current balance against the sum of outstanding nominal escrow for that token [2](#0-1) .

### Finding Description
The contract already demonstrates awareness of the "recorded amount vs. actual balance" hazard: `placeOrder` explicitly measures `balanceOf` before and after `transferFrom` and mutates `order.inputs[i].amount` to the actually-received amount for fee-on-transfer tokens, precisely to keep the ledger consistent with what the gateway holds [3](#0-2) [4](#0-3) .

That reconciliation happens only at deposit time, however. All tokens escrowed for every order of a given input token address share one pooled `balanceOf(gateway)` for that token. `_orders[commitment][token]` is only ever decremented by the exact nominal amount recorded at deposit; there is no step anywhere in `_withdraw`/`withdraw` that checks the contract's live balance against the sum of all outstanding escrow entries for that token before paying out [2](#0-1) [5](#0-4) .

If the escrowed input token is a rebasing/yield-bearing asset (e.g. an stETH-like token, an aToken, or any token whose `balanceOf` can decrease independently of an explicit `transfer` — a negative rebase, slashing event, or any yield-bearing wrapper), the pool backing all outstanding orders in that token shrinks below the sum of the nominal `_orders[...][token]` entries recorded before the rebase. `_withdraw` does not detect this: it keeps handing out full nominal amounts to whichever order is processed (filled, cancelled, or refunded) first. Each of these paths is reachable by unprivileged actors — same-chain cancel by the order's own user [6](#0-5) , cross-chain refund/redeem triggered by ordinary solver fills or destination-side cancellations that any relayer can carry through `onAccept` [7](#0-6) . The first orders processed after the balance shrinks are paid their full stale nominal amount — effectively over-credited against the asset's post-rebase real value — while the pool is depleted for whoever is left; the last order(s) sharing that token then have their withdrawal `safeTransfer` revert for insufficient balance, permanently reverting that transaction and leaving their escrow un-redeemable through the normal path.

This is the exact same broken invariant as the reported Lido bug: a point-in-time nominal balance is recorded at deposit, a rebase/negative-yield event occurs before redemption, and the contract keeps crediting withdrawals against the stale nominal figure instead of the token's live balance — causing over-crediting of earlier claimants at the expense of later ones sharing the same pool.

### Impact Explanation
This breaks the pivot that "order escrow, refunds... must move exactly once and only to the rightful beneficiary and amount." For any input token whose balance can drop after deposit without an explicit `transfer` call, users who withdraw first extract more value than their fair share of the shrunk pool, while later legitimate order holders using the same token find their escrow effectively locked (transaction reverts on insufficient balance), a fund loss/lock for the disadvantaged party and an unentitled over-credit for the advantaged one — all without any privileged actor, malicious relayer, or governance action required.

### Likelihood Explanation
Likelihood is bounded by whether a rebasing/yield-bearing/slashable ERC-20 is ever used as an intent input. The codebase already explicitly tests and supports fee-on-transfer tokens as inputs (proving arbitrary ERC-20s, not just "vanilla" tokens, are an anticipated input class) [4](#0-3) , but the deposit-time reconciliation logic that protects against fee-on-transfer tokens has no counterpart at withdrawal time, so the gap only manifests for tokens whose balance can move after deposit independent of transfers (rebasing/slashable tokens), which is a plausible but non-default token choice.

### Recommendation
At withdrawal time (`_withdraw`/`withdraw`), either (a) cap the transferred amount to `min(recorded nominal amount, actual contract balance)` and account/emit any shortfall rather than reverting on the last claimant, or (b) track escrow in a rebase-resistant unit (e.g., shares, analogous to the Lido team's own suggested fix) so nominal accounting always matches the token's live balance regardless of rebases between deposit and redemption.

### Proof of Concept
1. Deploy `IntentGatewayV2` with a mock rebasing ERC-20 (balances scale down on a `rebase(-x%)` call, independent of `transfer`).
2. User A places order A with 1000 units of the rebasing token as input; User B places order B with 1000 units of the same token. `_orders[commitmentA][token] = 1000`, `_orders[commitmentB][token] = 1000`; gateway holds 2000 tokens.
3. Trigger a 50% negative rebase on the token; gateway's `balanceOf` for that token drops to 1000, while `_orders` accounting for both A and B is untouched (still 1000 each).
4. User A cancels (same-chain) first: `_withdraw` transfers the full nominal 1000 to A, draining the gateway's remaining balance to 0.
5. User B cancels next: `_withdraw` attempts to transfer B's nominal 1000, but the gateway's balance is 0 — the `safeTransfer` reverts, and B's escrow is stuck/un-redeemable through the normal cancel path, while A extracted a full share of a pool that had actually shrunk by half.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

                if (!sent) revert InsufficientNativeToken();

        assertEq(
