Confirmed vulnerability. `UserSessionStorage.store` keys the row solely on `shopify_user_id`, and `session_shop_conflicts_with_params`/session loading trust whatever `shopify_domain` is currently on that row without re-validating it against the domain that originally created it.

### Title
Cross-shop session/token confusion due to user sessions keyed only on `shopify_user_id` instead of hash(shop, user_id) - (File: lib/shopify_app/session/user_session_storage.rb)

### Summary
This mirrors the reported class of bug where a canonical asset should be keyed on `hash(domain, id)` but is instead keyed on `id` alone, allowing distinct domain-scoped records to collide. In `shopify_app`, online (user) sessions are persisted keyed only by `shopify_user_id`, with no combination of the originating shop domain in the lookup/storage key.

### Finding Description
`ShopifyApp::UserSessionStorage.store` looks up the user record using only the Shopify user id, then overwrites `shopify_domain` and `shopify_token` unconditionally: [1](#0-0) 

`retrieve_by_shopify_user_id` likewise fetches solely by `shopify_user_id`: [2](#0-1) 

The generated migration enforces this at the DB level with a *global* unique index on `shopify_user_id`, with no compound uniqueness on `(shopify_domain, shopify_user_id)`: [3](#0-2) 

Because a single Shopify user (id) can be a staff/collaborator on multiple shops, the same `shopify_user_id` legitimately produces sessions for different shops over time. Each time `store` runs for that user id, `find_or_initialize_by(shopify_user_id: user.id)` finds the *same row* regardless of which shop authenticated, and overwrites `shopify_domain`/`shopify_token` in place — the old shop's row is silently repointed to the new shop.

Session retrieval during a normal authenticated request loads by user id extracted from the session/JWT identifier, not by an id keyed to the specific shop: [4](#0-3) 

The only guard that could catch a mismatch, `session_shop_conflicts_with_params`, compares the *retrieved* session's shop to `params[:shop]` — but since the row itself was overwritten, `current_shopify_session.shop` now legitimately reflects the last shop that authenticated for that user id, so no conflict is detected: [5](#0-4) 

### Impact Explanation
If the same Shopify user id is associated with two different shops (e.g., a Partner/collaborator account or staff member with access to multiple stores using this app), the older shop's stored access token becomes silently overwritten with the newer shop's token/domain. Any subsequent lookup by that `shopify_user_id` (e.g., background flows, webhooks tied to the old shop, or stale JWTs still referencing the old shop context) returns the wrong shop's access token/session, resulting in cross-shop access-token confusion — the exact "unintended id collision" bug class described in the report, applied to session storage rather than canonical asset registries.

### Likelihood Explanation
This requires a real Shopify-issued user id shared across two shop installations (not an arbitrary attacker-forged value, since `shopify_user_id` comes from the OAuth-verified `AssociatedUser`), so it is not exploitable by a fully anonymous/unrelated party forging requests. It is a realistic occurrence in normal multi-shop collaborator/staff usage patterns supported by Shopify, and the bug fires automatically without any malicious intent — making it a latent, moderate-likelihood data-integrity/session-confusion issue rather than a directly attacker-triggerable exploit.

### Recommendation
Key the `users` table lookup/storage on the combination of `shopify_domain` and `shopify_user_id` (e.g., a compound unique index and `find_or_initialize_by(shopify_domain: auth_session.shop, shopify_user_id: user.id)`), analogous to using `keccak256(domain, id)` for canonical asset keys, so that sessions for the same real user across different shops are stored as distinct rows rather than overwriting one another.

### Proof of Concept
1. User `U` (shopify_user_id = 42) installs/authenticates the app on Shop A → `UserSessionStorage.store` creates a row: `{shopify_user_id: 42, shopify_domain: "shop-a.myshopify.com", shopify_token: "token-A"}`.
2. The same real user `U` (same shopify_user_id = 42, valid on Shopify's side because they are staff on both stores) authenticates on Shop B → `store` runs `find_or_initialize_by(shopify_user_id: 42)`, finds the existing row, and overwrites it to `{shopify_domain: "shop-b.myshopify.com", shopify_token: "token-B"}`.
3. Any code path that later calls `retrieve_by_shopify_user_id(42)` (e.g. `SessionRepository.load_session` for a lingering/valid JWT still bound to Shop A) now returns Shop B's domain and access token instead of Shop A's, per [2](#0-1) , resulting in Shop A's request context operating with Shop B's credentials.
