## Finding: Confirmed — unguarded operand injection is present in the merge() argv construction

### Title
Contribution-target branch name is passed to `git merge` as an unguarded trailing operand, allowing an attacker-controlled fork/upstream default-branch name to be interpreted as a Git option — (File: `app/src/lib/git/merge.ts`)

### Summary
`updateBranchWithContributionTargetBranch` in `app/src/ui/app.tsx` resolves the branch to merge via `findContributionTargetDefaultBranch`, which — for a forked GitHub repository — returns `upstreamDefaultBranch` computed from the remote's HEAD symref (mirroring the parent/fork's `default_branch`, which is attacker-controlled if the attacker owns the fork/parent relationship being contributed to). That `Branch.name` string is passed unmodified all the way down to `git(['merge', ..., branch], ...)` with no `--` end-of-options marker and no character/prefix sanitization.

### Finding Description
- `app/src/ui/app.tsx:670-701` (`updateBranchWithContributionTargetBranch`) obtains `contributionTargetDefaultBranch` from `findContributionTargetDefaultBranch` and passes it straight into `dispatcher.mergeBranch`. [1](#0-0) 
- `findContributionTargetDefaultBranch` returns `upstreamDefaultBranch` for forked GitHub repos, which is populated from the *remote's* HEAD (i.e., driven by whatever branch the fork/parent has configured as default on the server). [2](#0-1) 
- `upstreamDefaultBranch` is computed in `git-store.ts` `refreshDefaultBranch` from `getRemoteHEAD(repository, UpstreamRemoteName)` and matched against branches enumerated from `for-each-ref`, i.e., the value literally reflects the remote's HEAD branch name, not a value that Desktop generates or validates itself. [3](#0-2) 
- `Dispatcher.mergeBranch` → `AppStore._mergeBranch` → `GitStore.merge` → `merge()` in `app/src/lib/git/merge.ts`, which builds argv as `['merge', ...optionalFlags, branch]` and pushes the branch name as the last operand with **no `--` separator**: [4](#0-3) 
- By contrast, other branch-name-accepting code paths in this codebase (e.g. `createBranch`, rename-branch UI) run the *user-typed* name through `sanitizedRefName`, which explicitly strips a leading `-`/`+` specifically to avoid this class of argument-injection issue: [5](#0-4) [6](#0-5) 
  That sanitization function is never applied to `upstreamDefaultBranch`/`defaultBranch` values flowing through `findContributionTargetDefaultBranch` → `mergeBranch` → `merge()`.

So the "Name the wrong value exactly" answer: the wrong value is `branch` (i.e. `contributionTargetDefaultBranch.name`) being appended as `args.push(branch)` in `app/src/lib/git/merge.ts` without a preceding `--` operand-terminator or without going through `sanitizedRefName`/an equivalent leading-hyphen check, unlike the equivalent user-facing branch-creation/rename code paths.

### Impact Explanation
If the resolved branch name begins with `-` (e.g. `--abort`, `--continue`, or a crafted `--upload-pack=...`/similar flag-like string), it would be interpreted by `git merge` as an option rather than a ref, causing the "Update from default branch" action to silently do something other than merge the intended upstream branch (e.g. abort an in-progress merge, or fail/behave in an option-dependent way) — i.e., silent corruption of what the user intends to merge into their current branch, matching the bounty's "silent corruption of what the user commits/pushes" impact category.

### Likelihood Explanation
Exploitation requires the attacker to control the `default_branch` of a repository in a fork/upstream relationship that GitHub Desktop is contributing to (fully within the "unprivileged, API-controlled object" scope described), and for that branch name to actually exist as a ref with a leading `-` on the remote. I could not verify from the code in this repository whether GitHub.com's server-side ref/branch-name validation (which is external to this codebase) permits creating and setting as default a branch literally named e.g. `--abort`, since `git-check-ref-format` does not, as far as could be confirmed here, strictly forbid a leading hyphen (this is only enforced defensively by this app's own `sanitizedRefName`, applied elsewhere but not on this path). This external/server-side constraint is the main uncertainty affecting real-world exploitability and could not be resolved via codebase search alone.

### Recommendation
Apply the same defensive measures used elsewhere in the codebase to the contribution-target/default branch path: reject or strip leading `-`/`+` characters (via `sanitizedRefName`/`testForInvalidChars`) before using a remote-derived branch name in any `merge`, `rebase`, or `checkout` invocation, and/or insert a `--` end-of-options marker before the branch operand in `app/src/lib/git/merge.ts` (and audit `rebase.ts`, `checkout.ts` and any other git subcommands that append `branch.name` as a trailing bare argument).

### Proof of Concept
Not independently executed against a live GitHub fork; based on static code tracing:
1. Attacker owns Fork F with parent P; sets F's GitHub `default_branch`/relevant ref such that `upstream/HEAD` symref resolves to a branch literally named `--abort` (server-side feasibility unverified).
2. Victim clones/contributes to F with `forkContributionTarget = Parent`; Desktop runs `git remote set-head -a upstream`, which sets `refs/remotes/upstream/HEAD` to `--abort`. [7](#0-6) 
3. Victim triggers the `update-branch-with-contribution-target-branch` menu action → `updateBranchWithContributionTargetBranch()` → `dispatcher.mergeBranch(repository, Branch{name: '--abort'}, ...)`. [1](#0-0) 
4. `merge()` constructs `args = ['merge', '--abort']` and executes it via `git(args, ...)`, instead of merging the intended branch. [8](#0-7)

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

export async function updateRemoteHEAD(
  repository: Repository,
  remote: IRemote,
  isBackgroundTask: boolean
): Promise<void> {
  const options = {
    successExitCodes: new Set([0, 1, 128]),
    env: await envForRemoteOperation(remote.url),
    isBackgroundTask,
  }

  await git(
    ['remote', 'set-head', '-a', remote.name],
    repository.path,
    'updateRemoteHEAD',
    options
  )
}

export async function getRemoteHEAD(
  repository: Repository,
  remote: string
): Promise<string | null> {
  const remoteNamespace = `refs/remotes/${remote}/`
  const match = await getSymbolicRef(repository, `${remoteNamespace}HEAD`)
  if (
    match != null &&
    match.length > remoteNamespace.length &&
    match.startsWith(remoteNamespace)
  ) {
    // strip out everything related to the remote because this
    // is likely to be a tracked branch locally
    // e.g. `main`, `develop`, etc
    return match.substring(remoteNamespace.length)
  }

  return null
}
