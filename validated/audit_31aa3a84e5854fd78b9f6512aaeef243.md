### Title
Missing `chain_id` in EIP-712 Domain Separator Enables Cross-Network Replay of Aggregator Authorization Signatures - (File: `core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

`CLEMENTINE_EIP712_DOMAIN` is defined with only `name` and `version`, omitting `chain_id` and `verifying_contract`. This means aggregator ECDSA authorization signatures for `OptimisticPayoutMessage` and `OperatorWithdrawalMessage` are valid across all EVM networks and bridge deployments. A signature captured on one network (e.g., Citrea testnet, chain_id=5655) is cryptographically identical to one on another (e.g., Citrea mainnet, chain_id=5115), enabling cross-network replay that bypasses the aggregator authorization gate on the optimistic payout and operator withdrawal paths.

---

### Finding Description

In `core/src/rpc/ecdsa_verification_sig.rs`, the static EIP-712 domain is:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

EIP-712 specifies that `chain_id` and `verifying_contract` are standard domain fields that bind a signature to a specific network and contract. Both are absent here.

This domain is used in two production authorization gates:

**1. Verifier optimistic payout authorization** (`verifier.rs:1602–1617`): [2](#0-1) 

**2. Operator withdrawal authorization** (`operator.rs:210–233`): [3](#0-2) 

In both cases, `recover_address_from_ecdsa_signature` recomputes the EIP-712 hash using `CLEMENTINE_EIP712_DOMAIN` and compares the recovered address to `aggregator_verification_address` from config: [4](#0-3) 

Because `chain_id` is absent from the domain, the hash — and therefore the recovered address — is identical regardless of which EVM chain the signature was produced for. The config already tracks `citrea_chain_id` (e.g., `5655` in `.env.example`, `5115` in `run.sh`) but it is never fed into the domain: [5](#0-4) 

---

### Impact Explanation

When `aggregator_verification_address` is configured (the production security posture described in the module doc), the ECDSA signature is the sole authorization gate preventing an unauthorized party from triggering optimistic payouts or operator withdrawals. Removing domain binding means:

- **Cross-network replay**: A valid aggregator signature obtained from a testnet deployment (same aggregator key, same withdrawal params) passes verification on mainnet. The operator then executes `withdraw()`, spending its own Bitcoin UTXO to pay out the withdrawal — a direct loss of operator BTC collateral/funds.
- **Cross-deployment replay**: Two bridge deployments on the same Citrea chain (e.g., a v1 and v2 deployment sharing an aggregator key) allow a signature from one to authorize actions on the other.

The concrete corrupted value is the recovered `address_from_sig`: it matches `address_in_config` for a replayed cross-network signature, causing the authorization check to pass when it should fail, and the operator's `withdraw()` to execute an unauthorized payout.

---

### Likelihood Explanation

The same aggregator key being used across testnet and mainnet is a realistic operational pattern during staged rollouts. The withdrawal params (`withdrawal_id`, `output_script_pubkey`, `output_amount`) are attacker-controlled in the RPC call; only `input_outpoint` (the Bitcoin UTXO the operator fronted) is independently constrained. An attacker who can observe a valid testnet signature (e.g., a malicious operator or verifier node on testnet) and construct a matching withdrawal request on mainnet can trigger the replay. The check is optional (`Option<Address>`), so deployments without it configured are unaffected, but those that rely on it as a security gate are fully exposed.

---

### Recommendation

Bind the domain to the Citrea chain ID and bridge contract address. Since `chain_id` is already present in `BridgeConfig` as `citrea_chain_id`, and the bridge contract address is a known constant, the domain should be constructed at runtime rather than as a `static`:

```rust
pub fn clementine_eip712_domain(chain_id: u64, contract_address: Address) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
        verifying_contract: contract_address,
    }
}
```

Pass `config.citrea_chain_id` and the bridge contract address wherever `CLEMENTINE_EIP712_DOMAIN` is currently used in `recover_address_from_ecdsa_signature`, `sign_optimistic_payout`, and `withdraw`.

---

### Proof of Concept

1. Aggregator signs an `OptimisticPayoutMessage` on Citrea testnet (chain_id=5655) for withdrawal_id=42, producing signature `S`.
2. Attacker submits the same withdrawal params plus `S` to a mainnet verifier's `optimistic_payout_sign` RPC.
3. Verifier calls `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>(...)` with `CLEMENTINE_EIP712_DOMAIN` (no chain_id). The hash is identical to the testnet hash, so the recovered address equals `aggregator_verification_address`.
4. The check at `verifier.rs:1616` passes. The verifier signs the optimistic payout partial signature.
5. Aggregator aggregates partial signatures and broadcasts the payout transaction, spending the operator's Bitcoin UTXO without a legitimate mainnet withdrawal having been authorized. [1](#0-0) [6](#0-5) [7](#0-6)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
