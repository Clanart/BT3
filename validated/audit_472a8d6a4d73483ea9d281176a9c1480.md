### Title
`_calExpireForfeit` is a permanent no-op, allowing expired-but-unclaimed cooldown positions to claim 100% of bonus rewards forever, denying the forfeiture redistribution owed to non-cooling stakers - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` is supposed to forfeit a portion of a user's accrued bonus rewards when their cooldown/unlock position has expired but the user has not finalized `unlock()`, redistributing the forfeited amount to other stakers via `_queueNewRewardsWithoutTransfer`. The function's logic is broken: it sets `rewardableAmount = _amount` before comparing it to `_amount`, so the "forfeit" branch is mathematically unreachable and `forfeitAmount` is always `0`, regardless of the account's actual lock/cooldown state.

### Finding Description
`_calExpireForfeit(address _account, uint256 _amount)` is defined as: [1](#0-0) 

The logic does the following:
- `rewardableAmount = _amount;` — set equal to input.
- `if (rewardableAmount > _amount) revert ...;` — this condition can never be true since they were just set equal, and the guard is dead code.
- `forfeitAmount = _amount - rewardableAmount;` — always evaluates to `0` because `rewardableAmount == _amount` always.
- The `_account` parameter is never used to look up any lock/cooldown state (e.g., `getFullyUnlock`, cooldown end time) from `mWOMSV`/`ILocker`. There is no call into the locker to check whether the account's cooldown slot has expired without finalizing `unlock()`.

This function is invoked from `_sendReward`, which is called from `getReward` (line 233) and `getRewards` (line 249), both gated only by `onlyMasterMagpie` and reachable by any unprivileged staker through `MasterMagpie.claimBaseRewarder` / `multiclaim` for their own account: [2](#0-1) 

Since `forfeitAmount` is always `0`, `toSend` always equals the full `userRewards[...]` amount, and the `forfeitAmount > 0` branch that would call `_queueNewRewardsWithoutTransfer` (redistributing the forfeited portion to other, presumably non-cooling, stakers) is never executed. There is no other mechanism in the contract that checks lock/cooldown expiry before paying `getReward`. Neither `onlyMasterMagpie`, `updateReward`, nor `nonReentrant` address this — they gate caller identity and reentrancy, not economic eligibility for full/forfeited rewards.

### Impact Explanation
This constitutes a permanent loss of the intended forfeiture-redistribution yield: stakers who let their cooldown expire without calling `unlock()` continue to receive full bonus-reward accrual as if they were still fully locked, in perpetuity, and the amount that should have been redistributed to non-cooling stakers (via `_queueNewRewardsWithoutTransfer`) is never generated. This falls under "theft or permanent freezing of unclaimed yield" since honest, still-locked/non-cooling stakers permanently lose the extra yield share they were entitled to receive from forfeited rewards, while any staker exploiting an expired cooldown slot captures a disproportionate, un-forfeited share indefinitely.

### Likelihood Explanation
This requires no privilege and no capital beyond having any locked position that can enter cooldown (`startUnlock`). The attacker simply calls `startUnlock`, waits past `endTime`, never calls `unlock()`, and repeatedly calls `MasterMagpie.claimBaseRewarder`/`multiclaim` to harvest full rewards every reward epoch, indefinitely. This is trivially repeatable and requires no special conditions beyond time passing, making it a certainty given the code as written (100% of accounts hitting this path will always avoid forfeiture).

### Recommendation
Fix `_calExpireForfeit` to actually compute forfeiture based on the account's lock/cooldown state from `ILocker`/`mWOMSV` (e.g., query the account's cooldown end time / `getFullyUnlock`; if expired and not yet finalized via `unlock()`, apply the intended forfeiture percentage to `_amount` instead of always returning `rewardableAmount == _amount`). Ensure the comparison/guard logic isn't tautological, and add a test verifying non-zero forfeiture for a known expired-but-unfinalized cooldown slot.

### Proof of Concept
Foundry test plan:
1. Deploy `mWOMSVBaseRewarder` wired to a mock/real `mWOMSV`/`ILocker` and `MasterMagpie`.
2. Stake MGP for `mWomSV`/`vlMGP`, call `startUnlock(amount)` to begin cooldown.
3. Warp time past the cooldown's `endTime` (i.e., past `coolDownInSecs`) without calling `unlock()`.
4. Have `rewardManager` queue bonus rewards via `queueNewRewards` across multiple epochs.
5. Call `earned(account, rewardToken)` and `calExpireForfeit(account, rewardToken)` — assert `calExpireForfeit` returns `0` regardless of elapsed cooldown-expired time.
6. Call `MasterMagpie.claimBaseRewarder` (routing to `getReward`) and assert the user receives 100% of `earned()` with zero amount routed to `_queueNewRewardsWithoutTransfer` (check `ForfeitRewardAdded` event is never emitted and `queuedRewards`/`rewardPerTokenStored` show no forfeiture-driven redistribution).
7. Repeat over multiple reward epochs to show the behavior persists indefinitely, confirming the forfeiture mechanism never activates.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
