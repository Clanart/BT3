### Title
Incorrect decimal-difference scaling in `convert_to_balance`/`convert_to_erc20` causes mis-minted/mis-refunded bridge amounts - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`hyper-fungible-token` converts amounts between the ERC20-side precision (`erc_decimals`) and the local Substrate asset precision (`local_decimals`) using `10u128.pow(erc_decimals.saturating_sub(local_decimals))`. This mirrors the reported `getRate()` flaw exactly: a fixed/one-directional scaling exponent is applied without checking which side actually has more decimals, so whenever `local_decimals > erc_decimals` the exponent silently saturates to `0` and **no scaling is applied at all**, producing a value that is off by up to `10^(local_decimals - erc_decimals)`.

### Finding Description
`convert_to_balance` and `convert_to_erc20` in [1](#0-0)  compute the scaling factor with `erc_decimals.saturating_sub(local_decimals)`. This is only correct when `erc_decimals >= local_decimals`. When the local asset is configured with *more* decimals than the source ERC20 token (a completely normal configuration — e.g. a 6-decimal ERC20 like USDC bridging into an 18-decimal local asset), `saturating_sub` returns `0`, so the multiplier/divisor becomes `10^0 = 1` instead of the correct `10^(local_decimals - erc_decimals)`.

This function is used directly in the custody-critical mint/transfer path:
- `on_accept` (inbound message from a remote chain) computes `amount = convert_to_balance(value, erc_decimals, decimals)` and then mints/transfers that `amount` to the beneficiary via `NativeCurrency::transfer` or `Assets::mint_into`. [2](#0-1) 
- `on_timeout` (refund path releasing escrowed funds back to the original sender) performs the identical conversion and transfer/mint. [3](#0-2) 

Both paths trust `erc_decimals` from `Precisions::<T>::get(local_asset_id, source)` and `decimals` from the local asset's metadata (or `T::Decimals::get()` for the native asset), but neither validates the *direction* of the decimal difference before exponentiating — the `saturating_sub` silently discards the correct signed exponent instead of dividing/multiplying appropriately.

### Impact Explanation
When `local_decimals > erc_decimals`, every inbound bridge message and every timeout refund mints/transfers `10^(local_decimals - erc_decimals)` times *less* than the correct amount. Concretely, bridging a token with 6 ERC20 decimals into a local asset configured at 18 decimals causes the beneficiary (or the refunded sender) to receive only `10^-12` of the intended amount — the remainder is permanently unminted/unrecovered even though the corresponding value was escrowed/burned on the source chain. This is a direct, systemic loss of bridged funds (falls squarely in "stealing or loss of funds" / wrong amount to the rightful beneficiary), triggered by ordinary, non-malicious cross-chain transfers whenever this common decimal configuration exists, with no privileged actor, relayer misbehavior, or malformed proof required.

### Likelihood Explanation
Likelihood is Medium-to-High: this is not an edge case requiring an attacker — it fires deterministically for any asset pair where the local asset precision exceeds the source ERC20 precision, which is a routine configuration (many Substrate assets use 18 decimals while common ERC20s use 6 or 8). Every regular user bridging or being refunded through such a pair is affected, and the wrong amount is computed unconditionally inside `on_accept`/`on_timeout` with no additional guard.

### Recommendation
Replace the one-directional `saturating_sub` scaling with a signed comparison that scales in the correct direction:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        (value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))).to_string()
    } else {
        (value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))).to_string()
    };
    dec_str.parse::<B>()
}
```
Apply the mirrored fix to `convert_to_erc20`, and add unit tests covering both `local_decimals > erc_decimals` and `local_decimals < erc_decimals` configurations.

### Proof of Concept
1. Configure a local asset `X` with `decimals = 18` and register `Precisions::<T>::insert(X, source_contract, 6)` (source ERC20 token has 6 decimals — e.g. USDC).
2. A user bridges `1_000_000` raw units (i.e., `1.0` USDC) from the EVM side; the ISMP `PostRequest` carries `message.amount = 1_000_000`.
3. In `on_accept`, `erc_decimals = 6`, `decimals = 18`. `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18) = 0`, so `convert_to_balance` returns `1_000_000` unscaled instead of the correct `1_000_000 * 10^12 = 1_000_000_000_000_000_000`.
4. The beneficiary is minted/transferred `1_000_000` planck of the 18-decimal asset — i.e., `0.000000000001` tokens — instead of `1.0` token, permanently losing `~99.9999999999%` of the bridged value. The identical shortfall occurs on refund via `on_timeout` for timed-out messages. [4](#0-3) [5](#0-4)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
