### Title
Forged `ReceivedOutput` amounts make threshold signers produce invalid Bitcoin transactions - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary

`ReceivedOutput::read` accepts an arbitrary serialized `TxOut` amount and `OutPoint`, while `SignableTransaction::new` uses that caller-supplied amount as the authoritative input value. During multisig setup, Serai validates only that the supplied `script_pubkey` corresponds to the offset group key; it does not verify that the referenced outpoint actually contains that amount. The resulting Taproot sighash commits to the forged prevout through `Prevouts::All`, causing honest signers to produce a transaction Bitcoin consensus will reject.

### Finding Description

`ReceivedOutput::read` deserializes a scalar offset, a consensus-encoded `TxOut`, and an outpoint without authenticating either the amount or the output against the chain. It returns the caller-controlled representation directly. [1](#0-0) 

`SignableTransaction::new` then treats `input.output.value` as the real UTXO value when calculating spendable funds and change. It also copies the caller-controlled `OutPoint` into the unsigned transaction. [2](#0-1) 

The only input-validation performed by `multisig` is a check that the prevout's `script_pubkey` equals the Taproot script for the offset group key. There is no check that the outpoint exists, is unspent, or contains the supplied amount. [3](#0-2) 

During signing, the fabricated `prevouts` are committed into every Taproot key-spend sighash with `Prevouts::All`. A signature over a prevout whose amount differs from the actual UTXO cannot satisfy Bitcoin's Taproot sighash verification for the real output. [4](#0-3) 

### Impact Explanation

An unprivileged caller who can supply `ReceivedOutput` bytes can make Serai generate and threshold-sign a transaction for an unintended sighash message. If the encoded amount is lower than the real UTXO amount, the resulting signature commits to the wrong prevout and is invalid. If it is higher, the transaction may additionally create payments or change that the real inputs cannot fund. Either way, the completed transaction is rejected by Bitcoin nodes.

This can waste a signing attempt and repeatedly stall withdrawals or other wallet operations if forged serialized outputs are reintroduced. The vulnerability is a state-authentication failure rather than an arithmetic overflow: the signing machinery correctly commits to the supplied prevout, but nothing proves that the supplied prevout is the observed chain output.

### Likelihood Explanation

The attacker only needs a public outpoint paying to a Serai-controlled Taproot script and the ability to feed modified `ReceivedOutput` bytes to a consumer of the API. `ReceivedOutput::read` is a public parser, and its encoding exposes the attacker-controlled `TxOut` amount. [5](#0-4) 

The attack does not require access to validator keys, malicious peers, malformed curve points, or control of the Bitcoin network. It does require a caller to accept untrusted `ReceivedOutput` values rather than exclusively using objects produced by `Scanner::scan_transaction` from a verified block. [6](#0-5) 

### Recommendation

Do not treat a deserialized `ReceivedOutput` as authenticated chain state.

Before constructing or signing a `SignableTransaction`:

1. Resolve each `OutPoint` against a trusted Bitcoin view.
2. Require the resolved UTXO's full `TxOut`, including `value` and `script_pubkey`, to equal the supplied `output`.
3. Require the output to be unspent and sufficiently confirmed.
4. Only then pass the canonical chain-observed `TxOut` to `SignableTransaction::new`.

Prefer making `ReceivedOutput` construction private and exposing it only from scanner/authenticated-provider APIs. If deserialization is required for persistence, provide a separate validation method or constructor that receives the resolved UTXO and rejects mismatched amounts.

### Proof of Concept

The encoding accepted by `ReceivedOutput::read` is:

```text
offset: 32-byte Secp256k1 scalar
output: consensus-encoded TxOut
outpoint: consensus-encoded OutPoint
```

`TxOut` contains the attacker-controlled `value`, and `OutPoint` identifies a real deposit. [7](#0-6) 

Conceptual reproduction:

```rust
// From networks/bitcoin/src/wallet/mod.rs and wallet/send.rs.

// `real` is a chain-observed output paying to a Serai key.
let real: ReceivedOutput = scanner.scan_transaction(&funding_tx).remove(0);

// Modify only the TxOut amount in its serialized representation.
let mut forged_bytes = real.serialize();
let value_position = 32; // offset is 32 bytes; TxOut starts with its 8-byte value
forged_bytes[value_position .. value_position + 8]
  .copy_from_slice(&(real.value() - 1).to_le_bytes());

// The parser accepts the forged amount without checking the UTXO.
let forged = ReceivedOutput::read(&mut forged_bytes.as_slice()).unwrap();
assert_eq!(forged.outpoint(), real.outpoint());
assert_eq!(forged.value(), real.value() - 1);

// Build the transaction using the forged input representation.
let signable = SignableTransaction::new(
  vec![forged],
  &[(payment_script, payment_amount)],
  Some(change_script),
  None,
  fee_per_vbyte,
).unwrap();

// This check passes because the script still corresponds to the offset key.
let machine = signable.multisig(&threshold_keys).unwrap();

// Each participant signs a sighash committing to `real.value() - 1` rather than
// the actual prevout amount. Completing and broadcasting this transaction yields
// a consensus-invalid Taproot input.
```

The script check succeeds because it compares only `prevouts[i].script_pubkey` with the offset group key's script. [8](#0-7)  The forged amount is nevertheless included in `Prevouts::All`, so it becomes part of the signed message. [9](#0-8)
