## Title
Spoofable `WWW-Authenticate` / `x-github-request-id` "GitHub host" detection lets an attacker-controlled remote impersonate a GitHub Enterprise endpoint and trigger a credential-helper sign-in flow - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind()` decides whether a git remote should be treated as a trusted `github.com`/GitHub Enterprise endpoint purely from unauthenticated signals that the remote server itself supplies (an HTTP `WWW-Authenticate` header, or an `x-github-request-id` response header). There is no cryptographic or out-of-band verification of this claim, so any attacker who controls the server behind a git remote URL can make Desktop classify their host as `'enterprise'`. This is the same class of bug as the reported `requireInterface` issue: a trust decision is made by trusting a self-declared property of an untrusted target instead of verifying it robustly, so an "unrelated" (attacker) endpoint can pass validation it should never pass.

### Finding Description
`getEndpointKind()` in [1](#0-0)  classifies a credential URL by walking down a series of checks. After the safe, hard-coded checks for `github.com`/`.ghe.com`, it falls back to two attacker-influenceable signals:

1. It scans the credential's forwarded `wwwauth[...]` fields — captured verbatim from the target server's HTTP response by git — and if any value contains `realm="GitHub"` it immediately returns `'enterprise'`: [2](#0-1) 
2. Failing that, it calls `isGitHubHost(endpoint)`, which performs a `HEAD` request to `${endpoint}/meta` and considers the host a GitHub host purely because the response contains an `x-github-request-id` header — again, a header the target server fully controls: [3](#0-2) 

Neither check verifies anything the attacker cannot forge (no signature, no pinned certificate/fingerprint, unlike the hard-coded GitHub SSH key fingerprint check used elsewhere: [4](#0-3) ). Notably `isGitHubHost` even suppresses certificate errors for its own probe request, further weakening the already-spoofable check: [5](#0-4) 

The consequence of a wrong `'enterprise'` classification flows directly into `getCredential()`: if no existing account matches the endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)` [6](#0-5) , which begins a full "Enterprise Sign In" flow rooted at the attacker's endpoint: [7](#0-6) . The sign-in dialog is shown with only a generic description "Git requesting credentials to access `<attacker URL>`" [8](#0-7) , with no indication that Desktop's own host-classification heuristic (not the user) decided this was an "enterprise" GitHub instance.

### Impact Explanation
An attacker who controls the server backing a git remote the user clones/fetches/pushes to (fully within the allowed threat model of "attacker controls... a git remote/proxy response") can force Desktop to treat their arbitrary host as a GitHub Enterprise endpoint. This: 
- Triggers Desktop's own GitHub Enterprise OAuth/browser sign-in flow pointed at the attacker's `origin`, normalizing what is effectively an unrequested authentication flow to an attacker-chosen domain (unauthorized OAuth/account binding).
- Bypasses the "generic credential" path entirely for that host (`storeCredential`/`eraseCredential`/`getGenericCredential` are all short-circuited whenever `getEndpointKind` is not `'generic'`), so credential handling and helper behavior silently diverge from what a legitimate non-GitHub server would receive.
- Relies on a check that is trivially bypassable server-side, so it provides no real security boundary despite being used as one to gate whether Desktop-managed GitHub accounts/sign-in are involved.

### Likelihood Explanation
Any HTTP(S) git server the attacker controls can add a `WWW-Authenticate: Basic realm="GitHub"` response header to a 401 challenge, or serve any response containing `x-github-request-id` on a `HEAD /meta` request, both of which are single-line, trivial server configurations. No MITM, local access, or leaked credentials are required — only that the victim add/use an attacker-supplied remote URL (a normal, expected Desktop workflow: cloning/adding a remote).

### Recommendation
Do not rely on unauthenticated, server-supplied signals (`WWW-Authenticate` realm text, arbitrary response headers) to classify a remote as a trusted GitHub/Enterprise host. Only trust `'github.com'`/`'.ghe.com'` matches and hosts that already correspond to accounts the user explicitly configured (`isDotCom`/`isGHE`/existing account lookup). If heuristic detection is kept for UX purposes, it must not be sufficient on its own to launch a sign-in flow or otherwise alter trust-sensitive behavior — require explicit user confirmation that clearly states the actual hostname is not a previously trusted GitHub Enterprise instance, and/or drop the `x-github-request-id`/`WWW-Authenticate` heuristics from `getEndpointKind` in favor of only endpoints the user has manually added as an Enterprise account.

### Proof of Concept
1. Attacker stands up an HTTPS git server at `https://evil.example`.
2. Victim adds it as a remote and runs `git fetch`/`git clone` in GitHub Desktop.
3. The server responds to the git HTTP auth probe with `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this header to Desktop's credential helper trampoline; `getEndpointKind()` returns `'enterprise'` solely from this header (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`).
5. Since the victim has no account configured for `evil.example`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example/...')`, which calls `dispatcher.beginEnterpriseSignIn()` and `setSignInEndpoint('https://evil.example')` (`app/src/lib/trampoline/trampoline-ui-helper.ts:87-93`), presenting a "Sign in" dialog whose only context is "Git requesting credentials to access evil.example".
6. If the victim proceeds with sign-in, Desktop's enterprise OAuth/browser-auth flow is carried out entirely against the attacker's domain.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

    return new Promise<Account | undefined>(async resolve => {

        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
