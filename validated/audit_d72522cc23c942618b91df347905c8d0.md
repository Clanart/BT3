### Title
Broken forfeiture logic in `mWOMSVBaseRewarder._calExpireForfeit` always returns zero forfeit, letting users claim full unvested MGP rewards - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` is supposed to withhold ("forfeit") a portion of a user's reward based on how much of their mWomSV position is still locked vs. unlocking/cooled-down, exactly as the analogous `vlMGPBaseRewarder._calExpireForfeit` does by querying `getRewardablePercentWAD`. Instead of calling `mWOMSV.getRewardablePercentWAD(_account)`, the function assigns `rewardableAmount = _amount` directly, making the subsequent sanity check `rewardableAmount > _amount` structurally unable to fail and the resulting `forfeitAmount` always `0`, regardless of the user's actual lock/cool-down state.

### Finding Description
Compare the two sibling reward contracts:

`vlMGPBaseRewarder.sol` (correct pattern) computes the forfeit from the locker's actual rewardable percentage: [1](#0-0) 

`mWOMSVBaseRewarder.sol` (buggy) never queries `mWOMSV.getRewardablePercentWAD(_account)` at all; it sets `rewardableAmount` equal to the input `_amount`, so `forfeitAmount = _amount - rewardableAmount` is always `0`: [2](#0-1) 

The `mWOMSV` locker (`wombat/mWomSV.sol`) does implement `getRewardablePercentWAD`, which computes the fraction of a user's balance that is fully locked versus in cool-down/unlocking, exactly mirroring `VLMGP.sol`'s implementation: [3](#0-2) 

This is the same bug class as the reported "majority proposal group will always satisfy minimum size requirement" issue: a guard/derived value is computed *from* the very quantity it is meant to validate against, so the comparison is a tautology that can never trigger the intended restriction. Here, `rewardableAmount` is derived to be identically equal to `_amount`, so the "forfeit unvested/cooling-down rewards" mechanism is dead code — `_sendReward` in `mWOMSVBaseRewarder.sol` always pays out the user's full accrued reward with zero forfeiture: [4](#0-3) 

### Impact Explanation
The forfeiture mechanism exists so that MGP/reward accrued while a user's mWomSV position is unlocking (cooling down, not fully committed) is partly redirected back into the reward pool (`_queueNewRewardsWithoutTransfer`) for other, fully-locked stakers, rather than paid out in full to the unlocking user. Because `_calExpireForfeit` in `mWOMSVBaseRewarder.sol` never applies any forfeit, any ordinary mWomSV holder who starts unlocking/cools down can still claim 100% of their accrued MGP/bonus rewards via `getReward`/`getRewards` (routed through `MasterMagpie`), permanently depriving the remaining fully-locked stakers of the forfeited-yield redistribution they are entitled to. This is a direct, unprivileged-wallet-reachable theft of unclaimed yield from other honest stakers in the mWOMSV reward pool.

### Likelihood Explanation
Any wallet holding mWOMSV and any amount in cool-down/unlocking can trigger this simply by calling the normal claim flow (`MasterMagpie` → `mWOMSVBaseRewarder.getReward`/`getRewards`) — no privileged role, governance action, or special conditions are required. This makes the issue trivially and repeatedly reachable by an ordinary user.

### Recommendation
- **Short term:** Fix `mWOMSVBaseRewarder._calExpireForfeit` to compute `rewardableAmount` from `mWOMSV.getRewardablePercentWAD(_account)`, mirroring `vlMGPBaseRewarder._calExpireForfeit`:
```solidity
uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
```
- **Long term:** Add unit tests asserting that partially-unlocked/cooling-down mWomSV positions incur a non-zero forfeit proportional to their unlocked/cool-down share, and add invariant tests across all `BaseRewardPool`/locker-reward implementations to catch tautological or dead validation logic.

### Proof of Concept
1. User locks mWom into `mWomSV` and accrues MGP rewards via `mWOMSVBaseRewarder`.
2. User calls `startUnlock`/cool-down on part of their mWomSV balance (position now partially "in cool down", not fully locked) — per `mWomSV.getRewardablePercentWAD`, this should reduce the rewardable percentage below 100%.
3. User calls `MasterMagpie`'s claim path, which invokes `mWOMSVBaseRewarder.getReward`/`getRewards` → `_sendReward` → `_calExpireForfeit`.
4. Because `_calExpireForfeit` sets `rewardableAmount = _amount` unconditionally, `forfeitAmount` computed is `0` and the user receives their entire accrued reward via `toSend = userRewards[...] - 0`, despite holding an unlocking/partially-vested position — no forfeit is ever queued back via `_queueNewRewardsWithoutTransfer`, unlike the equivalent `vlMGPBaseRewarder` flow.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
