## Analog Found

### Title
Forfeit calculation in `mWOMSVBaseRewarder` is hardcoded to always return zero, unconstrained bypass of early-exit reward forfeiture - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` unconditionally instead of computing it from the user's actual lock/vesting status, meaning `forfeitAmount` is always `0`. This mirrors the reported bug class: a value that is supposed to be constrained/derived from a real on-chain state check is instead left unconstrained (hardcoded to the "always valid" / "always full" case), silently disabling the intended forfeit mechanism.

### Finding Description
In the sibling contract `vlMGPBaseRewarder.sol`, `_calExpireForfeit` correctly derives the rewardable portion of a user's accrued reward from the locker's real state: [1](#0-0) 

It calls `vlMGP.getRewardablePercentWAD(_account)` and scales `_amount` by that live percentage, so a user who has not maintained/renewed their lock forfeits the un-rewardable portion of their pending rewards, and that forfeited amount is re-queued as rewards for remaining stakers via `_queueNewRewardsWithoutTransfer`.

`mWOMSVBaseRewarder.sol`, which shares the exact same reward/forfeit plumbing (`_sendReward`, `_queueNewRewardsWithoutTransfer`, `getReward`), instead does this: [2](#0-1) 

```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
}
```

`rewardableAmount` is set equal to `_amount` with no reference to `mWOMSV` lock state at all, so `forfeitAmount` is mathematically always `0` (`_amount - _amount`). The `revert InvalidRewardableAmount()` guard and the "ignore dust forfeit" branch are dead code that can never fire in a way that forfeits anything, because there is no real state-derived computation feeding into `rewardableAmount` — the constraint that should tie forfeiture to the account's mWomSV lock/cooldown status has effectively been dropped, just as the `IsZeroGadget::eval` constraint line was dropped in the original report, leaving the "gadget" (here, the forfeit check) structurally present but functionally unconstrained.

This is called from `_sendReward`, which is invoked by `getReward`/`getRewards` — both callable via `MasterMagpie` on behalf of any ordinary wallet holding `mWomSV`-linked reward positions: [3](#0-2) 

### Impact Explanation
Because `forfeitAmount` is always `0`, users who should be penalized for not maintaining eligible lock status (per the intended design mirrored in `vlMGPBaseRewarder`) instead receive 100% of their accrued `mWomSV` rewards unconditionally. The forfeited share, which under the correct design is redistributed to remaining/compliant stakers via `_queueNewRewardsWithoutTransfer`, is never generated — meaning:
- Non-compliant users receive rewards they should have forfeited (unmerited yield extraction from an ordinary wallet's transaction path, no privileged role needed).
- Remaining/compliant stakers permanently lose the yield that should have been redistributed to them, since it is never queued back into the reward pool.

This is a direct impact on unclaimed/forfeitable yield accounting reachable purely through `getReward`/`getRewards`, called by any wallet with a position, without any admin or governance involvement.

### Likelihood Explanation
High likelihood: this triggers on every single `getReward`/`getRewards` call for `mWomSV` positions — no special preconditions, race conditions, or privileged actions are required. Any ordinary user harvesting rewards through the normal flow is affected, and any user who should be subject to forfeiture will simply never be.

### Recommendation
Mirror `vlMGPBaseRewarder._calExpireForfeit`: derive `rewardableAmount` from the actual eligibility/lock state exposed by `mWOMSV` (e.g., an equivalent `getRewardablePercentWAD`-style view on `ILocker`/`mWomSV`) rather than hardcoding `rewardableAmount = _amount`.

### Proof of Concept
1. A wallet accrues `userRewards[token][account]` in `mWOMSVBaseRewarder` while its `mWomSV` lock becomes non-compliant/expired (per intended design, analogous to `vlMGP`'s rewardable-percent mechanism).
2. Wallet calls `getReward` (via `MasterMagpie`), which invokes `_sendReward` → `_calExpireForfeit(_account, userRewards[...])`. [4](#0-3) 
3. `_calExpireForfeit` returns `0` unconditionally regardless of the account's actual lock/eligibility state, so `toSend == userRewards[...]` in full.
4. The wallet receives 100% of rewards with no forfeiture, and no forfeited amount is ever queued back for other stakers via `_queueNewRewardsWithoutTransfer`, permanently depriving compliant stakers of that yield.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
