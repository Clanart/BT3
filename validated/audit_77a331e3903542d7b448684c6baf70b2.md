### Title
OOB indexing panic in `TransactionSignMachine::sign` on truncated per-participant preprocess vector — ([networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
CVE-2017-15045 is a heap buffer over-read in `fill_buffer` reachable purely by untrusted input length fields. The Serai analog is `TransactionSignMachine::sign`, which indexes each co-signer's `Vec<Preprocess>` by input index without checking its length, letting any unprivileged cosigner crash the signer with a truncated preprocess blob.

### Finding Description
`read_preprocess` deserializes one `Preprocess` per transaction input: `self.sigs.iter().map(|sig| sig.read_preprocess(reader)).collect()` — the returned `Vec<Preprocess>` length is entirely controlled by the sender's byte stream (`io::Result` on `read_exact`). [1](#0-0) 

In `sign`, each participant's vector is then indexed by input index `c` over `0 .. self.sigs.len()` with no length validation: [2](#0-1) 

If a participant supplies a `Preprocess` vector shorter than the number of inputs (e.g., an empty vector, or one parsed from a prematurely EOF'd buffer), `commitments[c]` panics on index-out-of-bounds. The same unchecked shape assumption exists in `complete`, where `shares.remove(0)` panics on an empty per-participant share vector. [3](#0-2) 

### Impact Explanation
A malicious or faulty cosigner can crash any signer's `TransactionSignMachine::sign`/`complete` by sending a syntactically valid `read_preprocess`/`read_share` output whose inner vector is shorter than `tx.input.len()`. In the processor this aborts the Bitcoin spend signing session mid-round; repeated across signers it stalls execution of pending `OutInstruction`s, leaving received outputs unspendable until operators intervene. Availability-only, matching the CVE's A:H profile — analogous to LAME reading past the heap buffer on attacker-controlled length data.

### Likelihood Explanation
Reachable by any participant in a FROST signing set for a Bitcoin spend: they only need to submit a truncated/malformed preprocess or share serialization. No key material, collusion, or privileged position is required. The panic is deterministic once `self.sigs.len() > sender_vec.len()`, which holds for any multi-input transaction against a short vector.

### Recommendation
In `sign`, validate `commitments.len() == self.sigs.len()` for every participant before indexing (return `FrostError::InvalidPreprocess(l)` on mismatch), and in `complete` check each `shares` vector is non-empty before `remove(0)` (return `FrostError::InvalidShare(l)`).

### Proof of Concept
```rust
// Two-input SignableTransaction => sigs.len() == 2.
// Malicious participant serializes a single Preprocess (or zero bytes after
// a valid first element), so read_preprocess yields vec![p0] of len 1.
let commitments: HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>> = ...;
// honest signers: vec![p0, p1]; attacker: vec![p0]
let (machine, _) = tx_machine.sign(commitments, b"");
// sign() computes c over 0..2; attacker entry commitments[1] -> index out of bounds panic
```
Concretely: build a `SignableTransaction` with ≥2 inputs, run `preprocess`, have one participant transmit only `n_inputs - 1` serialized preprocesses, then call `TransactionSignMachine::sign`; it panics at `send.rs:368` (`commitments[c]`).
