Based on the investigation, the strongest analog I can support with direct code evidence is in the submodule-update path, not a smart-contract-style "one-time setting" issue but the same *broken invariant* shape: a single coarse-grained trust decision (`allowFileProtocol`) is computed once and then propagated with `--recursive` to an entire, attacker-controlled submodule tree without being re-validated per submodule URL.

### Title
Recursive `protocol.file.allow=always` propagation lets attacker-controlled nested submodules read local files outside the repo - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` takes a single boolean `allowFileProtocol` and, if `true`, prepends `-c protocol.file.allow=always` to a `git submodule update --init --recursive` invocation. [1](#0-0)  This mirrors the HSG bug pattern: a trust/permission decision is made once (analogous to `maxSigners` being fixed at setup) and then applied broadly to a state that can change/differ at every nesting level (analogous to the safe's owner set changing after wiring), without re-validating the invariant (here: "is this specific submodule URL safe to fetch via `file://`?") at each point it matters.

### Finding Description
`checkoutBranch` and `checkoutCommit` accept an `allowFileProtocol` flag that is forwarded unchanged into `updateSubmodulesAfterOperation`. [2](#0-1)  When set, the resulting git invocation is:
```
git -c protocol.file.allow=always submodule update --init --recursive
``` [3](#0-2) 

Because `protocol.file.allow=always` is passed as a top-level `-c` config value and the update is `--recursive`, the permission is not scoped to the specific submodule/context that justified enabling it (e.g., a locally-cloned parent repository) — it is inherited by every nested submodule at every depth, each of whose URL is declared in that repository's own (attacker-authored) `.gitmodules` file. A malicious or compromised repository the user clones/fetches can therefore declare nested submodules with `url = file:///arbitrary/local/path`, and once the top-level decision to allow the `file://` protocol has been made anywhere in the operation, git will happily clone/fetch every nested `file://` submodule URL regardless of whether that specific submodule is "trusted."

This is exactly the class of bug in the report: a boolean/threshold decision that is valid at the moment/scope it was computed, but is later applied to a broader and dynamically/attacker-controlled scope (the full recursive submodule graph) where the original justification no longer holds — with no per-item re-check.

### Impact Explanation
If a local git repository elsewhere on disk exists at a path the attacker can guess or has otherwise learned (e.g., another checked-out project under the user's normal GitHub Desktop clone root, or a path leaked via prior telemetry/config), an attacker-controlled repository can declare a nested submodule pointing at that path via `file://`. Once `allowFileProtocol` is true for the operation, git will clone that local repository's *entire history* into the attacker's repo tree as a submodule. This is a "file read outside the repo" primitive: local file/history content the user did not intend to share ends up copied into the working tree of the attacker's repository, where it can subsequently be added and pushed by the (unsuspecting) user — i.e., "silent corruption of what the user commits or pushes," since the user is generally not shown a diff review step that calls out newly-materialized submodule content as a security-relevant change.

### Likelihood Explanation
Exploitation depends entirely on `allowFileProtocol` being `true` for the current checkout/update operation and on the attacker being able to control or guess a `file://` path of interest on the victim's machine. I was not able to fully trace, within the available search budget, the exact call sites in `app-store.ts`/dispatcher that decide when `allowFileProtocol` is passed as `true` (e.g., whether it's tied to the top-level remote being a `file://` URL, a local clone, or a test-only fixture path). This materially affects likelihood: if the flag is only ever `true` for genuinely local-only workflows (e.g., internal test fixtures, or repositories the user explicitly cloned via `file://`), real-world exploitability by a remote/GitHub-hosted attacker-controlled repo is much lower. I flag this as an open verification item.

### Recommendation
- Do not propagate a single `allowFileProtocol` decision recursively across the whole submodule graph. Instead, resolve `.gitmodules` per level and only allow `file://` for submodule URLs that are provably within the trust boundary that justified the flag (e.g., same repository root, or explicitly matching the top-level remote's own local path).
- Consider validating that any `file://` submodule URL resolves to a path within the already-cloned repository's own local clone source, rejecting arbitrary absolute paths.
- Add explicit UI disclosure/confirmation when a submodule update introduces content sourced from `file://` URLs, analogous to the existing "untrusted repository" ownership warnings already present in `add-existing-repository.tsx`/`missing-repository.tsx`. [4](#0-3) 

### Proof of Concept
1. Confirm (requires source access not fully verified in this session) a code path where `checkoutBranch`/`checkoutCommit` is invoked with `allowFileProtocol = true`. [2](#0-1) 
2. Craft/host a repository whose `.gitmodules` includes a nested submodule (a submodule of a submodule) with `url = file:///Users/victim/Documents/GitHub/some-other-private-repo`.
3. Have the victim clone/checkout this repository under conditions that trigger `allowFileProtocol = true`.
4. Observe that `git -c protocol.file.allow=always submodule update --init --recursive` clones the victim's local `some-other-private-repo` into the attacker's repo tree, materializing its full history/content inside the checked-out working directory. [5](#0-4) 

**Note on confidence**: I was unable, within this session's tool budget, to locate and confirm the exact caller-side conditions that set `allowFileProtocol = true` in `app-store.ts`/dispatcher code. This is necessary to fully confirm real-world reachability from an attacker-controlled repository versus a purely local/dev-only code path, so this finding should be treated as a strong lead requiring one more verification step (grep for `allowFileProtocol` call sites in `app-store.ts`) rather than a fully confirmed end-to-end exploit.
