### Title
Deposits below `N::DUST` to the multisig external address are silently dropped, locking user funds while leaving them spendable by the validator set - (File: processor/src/multisigs/scanner.rs)

### Summary
The bug class in the reference report is "user funds accepted but never credited, recoverable only by a privileged party." Serai's Bitcoin path exhibits the same shape: the scanner unconditionally discards any scanned output whose amount is below `N::DUST` before emitting it as a deposit. A depositor who sends a below-dust amount to the multisig's external P2TR address loses the funds from Serai's accounting entirely — no `ScannerEvent` is emitted, no instruction is created, and there is no refund path — while the underlying UTXO is still a normal key-spend to the threshold group key, spendable by the validator set at will.

### Finding Description
In `processor/src/multisigs/scanner.rs`, the scan loop filters outputs by amount before recording them:

```rust
for output in network.get_outputs(&block, key).await {
    assert_eq!(output.key(), key);
    if output.balance().amount.0 >= N::DUST {
      outputs.push(output);
    }
}
``` [1](#0-0) 

Outputs surviving this filter are what get saved via `save_outputs` and emitted as `ScannerEvent::Block { outputs }`, which downstream becomes `OutputType::External` deposits and `InInstruction`s. [2](#0-1) [3](#0-2) 

There is no check anywhere that prevents or warns about a user sending a below-dust amount to the external deposit address. `external_address` is just the P2TR script for the group key (offset `Scalar::ZERO`), so any output paying to it is detected by `Scanner::scan_transaction` — which matches purely on `script_pubkey` — but is then thrown away by the dust comparison. [4](#0-3) [5](#0-4) 

The dropped output is not unspendable: it is a key-path spend under `key + G*0`, and `SignableTransaction`/FROST signing can spend it like any other `ReceivedOutput` — it is simply never surfaced to the scheduler. This mirrors the Cudos `withdrawERC20` asymmetry: the user's funds are lost to them but remain recoverable/spendable by the privileged party (here, the validator set controlling the threshold key, rather than the depositor).

### Impact Explanation
A user who deposits a below-dust amount of BTC to their Serai deposit address permanently loses the credited value: the deposit is never reported, no `InInstruction` is processed, and no refund mechanism exists. The funds remain locked under the multisig key and can only ever be moved by the validator threshold — same "users lose funds, privileged party gains them" asymmetry as the reference finding. Per-deposit loss is bounded by `N::DUST` (~546–2940 sats for standard output types), which caps individual impact and is why this rates Medium rather than higher.

### Likelihood Explanation
Standard Bitcoin relay policy refuses sub-dust transactions, so the loss requires either a direct miner submission, a non-standard policy node, or a user/deposit flow that miscalculates the amount (e.g., a wallet deducting fees from a fixed dust-level payment, or an integrator computing a deposit that lands below the cutoff). It does not require any malfunction of Serai itself — only that a user broadcast such a transaction, which is externally reachable with public inputs (anyone can send BTC to the deposit address). Mistaken/edge-case deposits are a realistic occurrence on bridges, consistent with the sponsor-confirmed Cudos report.

### Recommendation
Mirror the Cudos mitigation ("check against a supported token list") on the deposit side: reject or handle below-dust outputs rather than silently dropping them. Concretely, in the scan loop at `processor/src/multisigs/scanner.rs:562-566`, emit below-dust `OutputType::External` outputs as a distinct event (or log-and-store them) so they can be refunded, or have `external_address`/deposit-amount validation in the UI/scheduler enforce a minimum deposit above `N::DUST + fee estimate`. At minimum, save dropped outputs to the DB so an operator can identify and refund them, rather than discarding them without record.

### Proof of Concept
1. A user obtains the multisig external address (`external_address(key)` → P2TR script for `key`, offset `Scalar::ZERO`).
2. The user constructs and broadcasts a transaction paying, e.g., 500 sats (< `N::DUST`) to that `script_pubkey`, arranging miner inclusion (e.g., direct submission).
3. `Scanner::scan_transaction` matches the output's `script_pubkey` and produces a `ReceivedOutput` with `offset == Scalar::ZERO`. [6](#0-5) 
4. `Bitcoin::get_outputs` wraps it as `OutputType::External`. [7](#0-6) 
5. In `processor/src/multisigs/scanner.rs`, `output.balance().amount.0 >= N::DUST` is false, so the output is dropped — never saved, never emitted, no instruction created. The user is never credited on Serai.
6. The 500-sat UTXO remains spendable only via the threshold group key, i.e., recoverable solely by the validator set — not by the depositor.

Uncertainty note: I could not re-read the exact `scanner(key)`/`kinds` helper and `N::DUST` constant definition in `processor/src/networks/bitcoin.rs` before the iteration limit, so the precise dust threshold value and kind-mapping details are inferred from the call sites shown above rather than the definitions themselves.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
