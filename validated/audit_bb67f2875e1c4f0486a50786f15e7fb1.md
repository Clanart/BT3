Confirmed: `purchase()` in `BandwidthManager.sol` is a fully permissionless entrypoint, and `app`/`chain` are attacker-controlled with no ownership check tying `app` to `msg.sender`. Combined with pallet-bandwidth's uncapped-cost, unbounded FIFO push/evict path, this reproduces the external report's core invariant break (an attacker cheaply grows a list the protocol must operate on, and this growth silently destroys a legitimate party's already-paid state) but with actual fund loss instead of gas DoS.

### Title
Permissionless bandwidth purchases let an attacker force-evict a victim's prepaid subscription for a fraction of its cost - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`BandwidthManager.purchase()` on any EVM source chain accepts an arbitrary `app` and `chain` argument from any caller, with no check that the caller is affiliated with the target app. `pallet-bandwidth::on_accept` credits the resulting `BandwidthPurchaseMsg` into the `(app_chain, app)` `Allowance` FIFO list, which is a `BoundedVec` capped at `MAX_SUBSCRIPTIONS = 1024`. Once at cap, every additional push evicts the single oldest entry via `push_subscription`. Because the eviction key is only `(app_chain, app)` and purchases are permissionless and cheap (lowest configured tier), any address can flood a victim's bucket with 1024 minimum-tier, 1-month purchases to evict all of the victim's real, larger/longer-duration subscriptions before they are consumed.

### Finding Description
`purchase()` in `evm/src/apps/BandwidthManager.sol` has no access control tying the caller to the `app` being credited — `app` and `chain` are pure calldata: [1](#0-0) 

The pallet's credit path stores subscriptions keyed by `(app_chain, app)` in an FIFO `BoundedVec` capped at 1024, evicting only the single oldest entry per push regardless of who paid for it or how much bandwidth it carries: [2](#0-1) [3](#0-2) 

The gate that drains the list also treats all entries interchangeably by insertion order, with no per-payer isolation: [4](#0-3) 

The docs confirm the eviction is "auditable" but treat it as a benign edge case reachable only "under pathological repeat-buy behavior," implicitly assuming the purchaser and the victim are the same economic actor: [5](#0-4) 

That assumption is false: `app`/`chain` are attacker-controlled, so anyone can target a victim app's bucket. There is no minimum purchase-price floor relative to what's already queued, no per-payer sub-limit, and no protection preventing a cheap tier-1/1-month purchase from evicting a victim's tier-4/12-month purchase that may be worth orders of magnitude more in prepaid bandwidth.

### Impact Explanation
This is a direct loss-of-funds / logic attack on the bandwidth escrow: a victim app that legitimately prepaid for bandwidth (e.g., a multi-month, high-tier subscription costing hundreds or thousands of dollars) can have that entire entitlement wiped from the FIFO list by an attacker who spends only 1024 × (cheapest tier price) to churn the queue — potentially far less than the value destroyed. Once evicted, the tokens paid to `BandwidthManager` are already held by the contract/treasury (no refund mechanism exists), so the victim has paid and receives nothing, while the attacker pays only the incremental cost needed to push the victim's specific entries out of the FIFO window. This falls squarely under "loss of funds" / "logic attacks" per the bounty's impact gate, and requires no relayer, prover, or admin compromise — only a normal, permissionless call to `purchase()`.

### Likelihood Explanation
Likelihood is moderate-to-high for any bandwidth-paying app that is a known, valuable target (address/appKey is public via `BandwidthCredited`/`BandwidthPurchased` events). The attack is entirely permissionless, requires no privileged role, and its cost is bounded and predictable (number of pushes needed × cheapest tier price on that chain). It is economically rational whenever `cost_to_evict(victim's entries) < value_of_victim's_remaining_bandwidth`, which is true whenever a victim buys higher tiers/longer durations while a cheap tier exists on the same manager.

### Recommendation
- Scope subscription eviction/isolation per payer as well as per `(app_chain, app)`, or require that `purchase()` calls crediting an `app` the caller does not control go through a separate, rate-limited/governance-gated path.
- Alternatively/additionally, disallow FIFO eviction of unexpired subscriptions whose remaining value exceeds some threshold, or require `force_evict`-style purchases to refund/compensate the evicted entry's remaining value to its original payer.
- Consider capping how much bandwidth-value a single purchase transaction may evict, or making eviction fail (reverting the purchase, refunding the payer) rather than silently destroying a live, higher-value entry.

### Proof of Concept
1. Victim calls `BandwidthManager.purchase(app=VICTIM_APP, tier=4 /* largest */, months=12, chain=CREDIT_CHAIN)`, paying a large fee-token amount; pallet credits a `Subscription` with large `bytes`/`expires_at` into `Allowance[CREDIT_CHAIN][VICTIM_APP]`.
2. Attacker repeatedly calls `BandwidthManager.purchase(app=VICTIM_APP, tier=1 /* cheapest */, months=1, chain=CREDIT_CHAIN)` from any address, paying only the tier-1 price each time — see the unrestricted signature: [6](#0-5) 
3. Each relayed purchase invokes `push_subscription`, and once `Allowance[CREDIT_CHAIN][VICTIM_APP]` reaches 1024 entries, each further attacker purchase evicts the oldest entry: [7](#0-6) 
4. After enough attacker purchases (up to 1024, bounded and predictable), the victim's tier-4/12-month subscription is evicted and emits `SubscriptionEvicted` with the victim's `lost_bytes`, while the victim's fee-token payment is already irretrievably held by `BandwidthManager`.
5. Test scaffolding for direct manipulation of `MAX_SUBSCRIPTIONS`-bound eviction already exists and confirms the mechanics (used here only to show the eviction is deterministic and attacker-triggerable, not that it is benign): [8](#0-7)

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
