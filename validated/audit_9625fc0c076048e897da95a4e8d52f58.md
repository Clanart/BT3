## Finding [1](#0-0) 
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow using the client-supplied `order.inputs[i].amount` (only reduced by the protocol-fee bps) rather than measuring the actual token balance received via `safeTransferFrom`, unlike the mainline EVM contract which explicitly snapshots balances before/after transfer to capture the real received amount for exactly this reason.

### Title
Deflationary/fee-on-transfer input tokens cause escrow over-crediting and pooled-fund drain in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` on the Tron deployment escrows tokens by calling `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally records `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived from the caller-specified `order.inputs[i].amount` minus only the protocol fee — never from the contract's actual measured balance delta. The sibling EVM implementation deliberately avoids this by measuring `balanceOf` before and after the transfer and mutating `order.inputs[i].amount` to the real received amount before computing fees/escrow/commitment, precisely to defend against fee-on-transfer/deflationary tokens.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder`'s no-predispatch branch: [1](#0-0) 
transfers `order.inputs[i].amount` via `safeTransferFrom` and then credits `_orders[commitment][token] += reducedInputs[i].amount` using the requested amount (minus protocol fee), not the amount actually received by the contract. If `token` applies a transfer fee or burn (deflationary/fee-on-transfer token), the contract's real balance increase is smaller than the amount recorded in `_orders`.

Because `_orders` is a shared per-token ledger across all orders in the same contract (all orders' escrowed tokens sit in one pooled contract balance), this discrepancy is not self-contained to the depositor's own order — it creates a shortfall that is paid out of the balance contributed by other, unrelated orders using the same token.

When the order is later filled or refunded, `withdraw` pays out exactly the recorded `_orders` amount: [2](#0-1) 
`amount = body.tokens[i].amount` comes from `order.inputs[i].amount`, i.e. the original (or fee-reduced-only) requested amount reconstructed by the filler/relayer from the emitted `order.inputs`/`OrderPlaced` — never the true received balance. This mirrors the corresponding pattern in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `IntrinsicIntents.sol` where withdrawal amounts are taken from `order.inputs`/`_orders[commitment]` rather than re-measured balances.

The corrupted value is the per-commitment, per-token escrow ledger entry `_orders[commitment][token]`: it is set higher than the tokens the contract actually custodies for that order.

### Impact Explanation
Any user can place an order using a deflationary/fee-on-transfer ERC20 as an input token. The contract records more tokens in `_orders[commitment][token]` than it actually received. When this order is filled/redeemed, the beneficiary (solver/filler) is paid the full recorded amount, which is funded from the pooled balance of that token held by the contract on behalf of other, unrelated orders — causing under-collateralization and eventual inability of legitimate order owners/fillers to redeem their rightful escrow (loss/lock of funds for other users). This is a direct fund-accounting break in bridge custody/escrow logic, not merely a griefing or DoS issue.

### Likelihood Explanation
No privileged actor, relayer, or prover assumption is required — any unprivileged user can call `placeOrder` with an arbitrary ERC20 token address, including a deflationary token they control or a known fee-on-transfer token, and immediately create an under-collateralized order in the shared pool. The mainline EVM `IntentGatewayV2.sol` and its test suite (`IntentGatewayV2SameChainTest.sol`, `FEE-ON-TRANSFER TOKEN TESTS`) explicitly acknowledge and test for this exact class of token, confirming it is an anticipated real-world input, while the Tron variant lacks the corresponding balance-delta guard.

### Recommendation
Mirror the mainline EVM fix in the Tron contract: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` in `placeOrder` (and any predispatch/dispatcher sweep paths), and use that measured delta — not the caller-supplied `amount` — both for computing `reducedInputs`/the commitment hash and for the `_orders[commitment][token]` escrow credit, exactly as done in `evm/src/apps/IntentGatewayV2.sol` lines 198-298.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g. 5% burn on transfer) and mint tokens to `user`.
2. `user` calls Tron `IntentGatewayV2.placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000}` and `order.output` targeting some other token/beneficiary.
3. Contract receives only 950 tokens (5% burned in transfer) but records `_orders[commitment][FOT] += 1000` (minus protocol fee, still based on the requested 1000, not the 950 actually received).
4. A separate, unrelated user places a legitimate order also escrowing the same `FOT` token, contributing to the same pooled contract balance.
5. When the first order is filled/redeemed via `withdraw`, the contract pays out 1000 `FOT` (or the fee-reduced-only figure) to the beneficiary using `token.call(transfer, beneficiary, amount)`, drawing on the pooled balance that includes the second, unrelated user's escrowed tokens.
6. The second user's order can no longer be fully redeemed because the pooled `FOT` balance is now insufficient — demonstrating fund loss/lock caused solely by the escrow-accounting mismatch, with no relayer/prover/admin involvement.
