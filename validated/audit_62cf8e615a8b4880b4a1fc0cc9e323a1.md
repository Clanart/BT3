### Title
Withdrawal UTXO can be spent by anyone with SinglePlusAnyoneCanPay + arbitrary OP_RETURN, letting an attacker credit any operator with an unfunded payout - (File: core/src/verifier.rs, core/src/rpc/parser/operator.rs, core/src/builder/transaction/operator_reimburse.rs)

### Summary
The withdrawal signature accepted by `parse_withdrawal_sig_params` only commits (via `TapSighashType::SinglePlusAnyoneCanPay`) to input 0 and output 0 of the payout transaction; nothing else — additional inputs, fee funding, and the OP_RETURN operator-attribution output are entirely unconstrained. Since the withdrawal UTXO belongs to the withdrawing user (the attacker), the attacker can build and broadcast this transaction themselves — funding the fee/output from their own wallet and writing an arbitrary operator's `xonly_pk` into the OP_RETURN — completely bypassing any operator's gRPC/wallet. The verifier's `update_finalized_payouts` then attributes the payout solely from that OP_RETURN, with no check that the named operator funded anything.

### Finding Description
The binding this exploits is:
`attributed_operator_xonly_pk (from payout_tx OP_RETURN, parsed in update_finalized_payouts) == fee_paying_operator's xonly_pk (whoever funded/signed the payout tx's non-user inputs)`

In the intended flow this holds because a single actor, the operator responding to a `withdraw`/`internal_withdraw` RPC, both (a) hardcodes its own key into the OP_RETURN via `create_payout_txhandler(..., operator_xonly_pk=self.signer.xonly_public_key, ...)` [1](#0-0)  and (b) funds/signs the rest of the transaction from its own bitcoind wallet via `fund_raw_transaction` / `sign_raw_transaction_with_wallet` in `Operator::withdraw` [2](#0-1) .

`parse_withdrawal_sig_params` normalizes a `Default` (64-byte) signature to `SinglePlusAnyoneCanPay` and only enforces that the final sighash type is `SinglePlusAnyoneCanPay`: [3](#0-2) . That sighash type commits **only** to input 0 and output 0 of the transaction it is embedded in — any other inputs/outputs (fee-funding inputs, change, and critically the OP_RETURN attribution output) are unconstrained by the signature and can be supplied by anyone.

The attacker is the withdrawing user, so they legitimately hold the private key for the withdrawal UTXO (per the rules: "choose the bytes of a withdrawal UTXO, a Schnorr signature and its sighash flag"). Instead of calling any operator's `withdraw`/`internal_withdraw` RPC, the attacker can directly construct and broadcast to Bitcoin a transaction that:
- Spends the withdrawal UTXO as input 0 with a valid `SinglePlusAnyoneCanPay` signature.
- Sets output 0 to exactly the committed user script/amount (required by the sighash commitment and by the Citrea storage proof binding vout/amount).
- Adds their own funding input(s) to cover the payout amount and fee (paid entirely by the attacker, not by any operator).
- Adds an OP_RETURN output containing an arbitrary operator's `xonly_pk` (public information) of the attacker's choosing.

The chain-level scanner tracks spends of the tracked `withdrawal_utxo` via `bitcoin_syncer` (`insert_spent_utxo`/`save_transaction_spent_utxos`) regardless of who broadcasts the spending transaction [4](#0-3) , and `get_payout_txs_for_withdrawal_utxos` simply joins on `withdrawal_utxo_txid`/`vout` [5](#0-4) . `Verifier::update_finalized_payouts` then extracts the OP_RETURN content and blindly attributes the payout to whatever xonly_pk is embedded, with no verification of who funded the other inputs: [6](#0-5) .

Once attributed, `PayoutCheckerTask::run_once` for the named operator picks up this "unhandled payout" purely by matching `operator_xonly_pk` [7](#0-6)  and drives `handle_finalized_payout`/kickoff/reimburse — none of which re-check that the operator actually funded the payout transaction's non-input-0 parts. The bridge circuit (`circuits-lib/src/bridge_circuit/mod.rs`) also only checks that the OP_RETURN pubkey is consistent between the payout tx and the kickoff tx via `deposit_constant`, not that the operator funded the payout [8](#0-7) .

No existing guard (`SECP.verify_schnorr` in `Operator::withdraw`, `is_profitable`, `validate_payer_is_operator`, or the bridge circuit's storage-proof/SPV checks) inspects who supplied the non-input-0 funding of a payout transaction; they all assume the payout tx was produced by the attributed operator's own RPC/wallet flow, which is not enforced on-chain.

### Impact Explanation
An unprivileged attacker (the withdrawing user) can self-fund their own withdrawal payout in full while embedding any operator's `xonly_pk` in the OP_RETURN. This causes the presigned-transaction-graph reimbursement flow (`handle_finalized_payout` → kickoff → `Reimburse` tx) to credit that operator with reimbursement drawn from the operator's round-tx pool for a payout the operator never fronted — exactly "an operator reimbursed for a payout it never funded" (Critical). This is repeatable per withdrawal and per operator (any operator's public xonly_pk can be targeted), and does not require the targeted operator's cooperation, collateral, or knowledge — only their normal automation (`PayoutCheckerTask`) to be running.

### Likelihood Explanation
Feasibility is high: the attacker only needs to be the depositor/withdrawer (fully within the unprivileged-attacker capability set), needs no verifier/operator/aggregator privileges, and pays only the Bitcoin fee plus the withdrawal payout amount itself (which they would have needed to fund anyway, just via a different path). No mainnet or live Citrea integration is required to demonstrate the DB/attribution logic in a `cargo test`, since `update_finalized_payouts`, `get_payout_txs_for_withdrawal_utxos`, and `update_payout_txs_and_payer_operator_xonly_pk` can be exercised directly with a synthetic block/transaction.

### Recommendation
Do not rely solely on the OP_RETURN of the spending transaction to attribute payer identity. Either (a) require the payout transaction to be fully committed by the withdrawal signature (e.g. use `SIGHASH_ALL`/`SIGHASH_SINGLE` without `ANYONECANPAY`, or otherwise cryptographically bind all inputs/outputs of the payout tx before accepting it as "the" payout), or (b) require an additional operator-signed commitment (e.g., a signature over the full payout tx from the operator whose collateral/round funds will be used) that verifiers check before marking `payout_payer_operator_xonly_pk` and before `handle_finalized_payout`/kickoff proceeds, so that the reimbursed operator provably authorized and funded the specific transaction.

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    let input_outpoint: OutPoint = params
        .input_outpoint
        .ok_or_else(error::input_ended_prematurely)?
        .try_into()?;

    let users_intent_script_pubkey = ScriptBuf::from_bytes(params.output_script_pubkey);

    Ok((
        params.withdrawal_id,
        input_signature,
        input_outpoint,
        users_intent_script_pubkey,
        Amount::from_sat(params.output_amount),
    ))
}

            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
