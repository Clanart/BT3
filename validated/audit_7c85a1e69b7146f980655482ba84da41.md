### Title
Untrusted deserialization of `ReceivedOutput` accepts a substituted output record — claimed offset/script/outpoint are never bound together, enabling misattributed or unspendable "received" funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes three independently attacker-controllable fields — `offset` (a scalar), `output` (a `TxOut` with value and `script_pubkey`), and `outpoint` — and returns them as a coherent "spendable output" without ever checking that the fields are consistent: i.e., that `output.script_pubkey == p2tr(key + GENERATOR * offset)` for the scanner's key, or that `outpoint` actually references `output`. This is the structural analog of the pam_usb symlink flaw: a security-critical object is reconstructed from a location the attacker can influence, and the code trusts the referenced contents instead of verifying the resolved object's identity. Anyone who can feed bytes to `ReceivedOutput::read` (the in-scope untrusted-read surface) can substitute a record for a different output — exactly the "redirect a trusted reference to an attacker-chosen object" primitive the symlink bug provides.

### Finding Description
The scanner produces `ReceivedOutput` values whose fields are internally consistent by construction: `scan_transaction` only emits an output when `output.script_pubkey` is found in `self.scripts`, and it sets `offset` to the registered scalar and `outpoint` to `(txid, vout)` of the transaction actually containing the output. [1](#0-0) 

However, the serialized form is just `offset || TxOut || OutPoint`, and `read` reconstructs the struct verbatim with no binding between the fields and no authentication of the blob: [2](#0-1) 

Because `Scanner.key` is not part of the encoding, deserialization cannot detect that:
- the `script_pubkey` does not correspond to `key + G*offset` (offset/script substitution — like a pad file replaced by a symlink target),
- the `outpoint` refers to a different transaction output than `output` (record swapped wholesale),
- the `value` inside `TxOut` is arbitrary (inflated balance claim).

Downstream, these fields are trusted as ground truth: `offset()` is used to derive the signing tweak for spending, `outpoint()` is used as the unique identifier of the claimed coin, and `value()`/`output()` feed balance and transaction-construction logic. [3](#0-2) 

### Impact Explanation
A forged or substituted `ReceivedOutput` produces two concrete failure modes allowed by the acceptance criteria:

- **Funds reported received that are not spendable.** An entry pairing a real `script_pubkey`/`outpoint` with a wrong `offset` (or vice versa) causes the wallet to treat the output as spendable under `key + G*offset` when it is not — the resulting FROST signing session would produce a signature for a key that doesn't control the UTXO, i.e., permanently locked funds attributed as received.
- **Balance/integrity corruption of privileged state** (the analog of root file corruption): an arbitrary `TxOut`/`OutPoint` with inflated `value` deserializes cleanly, so any consumer crediting balances from deserialized outputs accepts attacker-chosen amounts and identifiers.

The parallel to CVE-2026-44711 is structural: pam_usb trusted a path that an unprivileged user could redirect to another file; here the deserializer trusts a byte record whose components an unprivileged party can mix-and-match to point at other outputs/amounts, and no consistency check (the analogue of `O_NOFOLLOW`/ownership verification) is performed.

### Likelihood Explanation
Likelihood is moderate. Exploitation requires write influence over a byte stream later consumed via `ReceivedOutput::read` — the same class of local, low-privilege prerequisite as the pam_usb symlink attack (AV:L, PR:L). It does not require defeating any cryptographic check because there is none to defeat: the encoding contains no key commitment, no checksum over the triple, and no proof the outpoint resolves to the claimed `TxOut`. Where these records are persisted or relayed between components of differing trust (e.g., scanner → scheduler → signer pipeline), a single substituted record is sufficient to corrupt the accounting of the threshold wallet.

### Recommendation
Bind the fields cryptographically at serialization time:

1. Include the scanner's base `key` in the encoding (or a keyed tag) so `read` can verify `output.script_pubkey == ScriptBuf::new_p2tr_tweaked(TweakedPublicKey::dangerous_assume_tweaked(x_only(key + GENERATOR * offset)))`, rejecting records whose `offset` doesn't match the script — mirroring how `read_G` rejects non-canonical points in `Ciphersuite::read_G`. [4](#0-3) 
2. Authenticate stored output records (e.g., MAC keyed like the `Cached Preprocess Encryption Key` construction used for cached preprocesses in the coordinator) so swapped records are detected rather than silently adopted.
3. At minimum, re-derive and compare the expected `script_pubkey` on read and reject mismatches, and treat `outpoint`/`value` as claims to be re-validated against the chain, not as trusted fields.

### Proof of Concept
```rust
use bitcoin::{Transaction, TxOut, OutPoint, Amount, ScriptBuf, consensus::encode::serialize};
use ciphersuite::{Secp256k1, Ciphersuite};
use k256::Scalar;
use networks_bitcoin::wallet::{Scanner, ReceivedOutput, p2tr_script_buf};
use std::io::Read;

// 1. Build a legitimate scanner and register an offset.
let key = k256::ProjectivePoint::GENERATOR * Scalar::from(7u64);
let mut scanner = Scanner::new(key).unwrap();
let offset = scanner.register_offset(Scalar::from(42u64)).unwrap();

// 2. Take a real ReceivedOutput, then tamper: keep the outpoint,
//    swap in a TxOut with an inflated value or a foreign script_pubkey.
let legit = /* scan a tx paying to key + G*offset */;
let mut bytes = legit.serialize();

// Forge: overwrite the TxOut region with value = 21_000_000 BTC equivalent
// and an arbitrary script_pubkey. `ReceivedOutput::read` performs no
// consistency check between offset, output, and outpoint, so the forged
// record deserializes successfully and is reported as received/spendable.
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// forged.value() returns the attacker-chosen amount;
// forged.offset() claims spendability the script does not grant.
```

The essential demonstration: `ReceivedOutput::read` (wallet/mod.rs:122) accepts the spliced record because nothing binds `offset` → `script_pubkey` → `outpoint`, so a substituted record — the exact primitive a symlink provides — passes as authentic.

    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;

      outpoint =

    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
