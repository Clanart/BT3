### Title
Address (re-)association migrates spendable balances but silently orphans staking/distribution state left under the "cast address" identity - (File: `utils/helpers/associate.go`)

### Summary
The Shopware advisory is about an identity-normalization flaw: two distinct-looking inputs are treated as the same underlying identity by one part of the system but not by another, letting state accumulate under an identity that can no longer be reliably reached/controlled. Sei-chain has a structurally analogous flaw in the EVM⇄Sei address-association flow: the "cast address" `sdk.AccAddress(evmAddr[:])` is treated as a legitimate, usable Cosmos identity everywhere in the codebase (bank transfers, staking delegation, etc.) until the real pubkey owner performs an `associate`/`associatePubKey` call or sends a normal EVM tx, at which point `AssociateAddresses`/`MigrateBalance` reconciles only bank balances and then deletes the cast account — without checking whether other modules (staking, distribution) still hold state keyed to that same address bytes.

### Finding Description
`AssociationHelper.AssociateAddresses` and `MigrateBalance` in [1](#0-0)  perform the following when a Sei address is associated to an EVM address for the first time:
1. Compute `castAddr := sdk.AccAddress(evmAddr[:])`.
2. Move `SpendableCoins` and wei balance from `castAddr` to `seiAddr`.
3. If `LockedCoins(castAddr)` is zero, call `p.accountKeeper.RemoveAccount(ctx, ...)` to delete the cast account entirely.

`LockedCoins` only reports vesting-related locked coins [2](#0-1) ; it does **not** account for tokens that have been moved out of the account's balance into the staking bonded/unbonding pools via delegation, nor for any distribution state (outstanding rewards, starting-period info) keyed to `castAddr` as delegator/withdraw address. Those staking/distribution records live in separate module stores keyed directly by the address bytes and are never touched by `MigrateBalance`.

This exact hazard is explicitly acknowledged in the ante-handler code for one specific sub-case — EIP-7702 `SetCode` authorities — where the developers added `associateAuthorizationAuthorities` specifically to pre-associate authorities *before* a mutable cast mapping is created, citing the risk of "orphaning any staking/distribution state created under the direct-cast identity (which can then halt the chain via the distribution validator-removal hook)" [3](#0-2) . However, the general/common association path — reached whenever *any* new EOA sends its first normal EVM transaction, or calls the `addr` precompile's `associate`/`associatePubKey` methods [4](#0-3)  — still funnels through the same unguarded `AssociateAddresses`/`MigrateBalance` call [5](#0-4) , with no equivalent protection for ordinary accounts.

Because `castAddr = sdk.AccAddress(evmAddr[:])` is 20 raw bytes (not `hash(pubkey)`), it is not an address any standard Cosmos secp256k1 key can ever sign for. Any state left under `castAddr` after the account entry is deleted (e.g. an active delegation created by someone who sent funds to that address and delegated before the EVM owner ever associated) becomes permanently uncontrollable — nobody holds a private key whose canonical Cosmos address equals those raw bytes, and the account object needed for sequence/pubkey-based signing has just been removed.

### Impact Explanation
Funds bonded via staking (or accrued distribution rewards) under a cast-address identity that gets reconciled through `AssociateAddresses` can become permanently unclaimable: the account is deleted, and no key can ever produce a valid signature for the literal 20 raw EVM-address bytes as a Cosmos `AccAddress`. This is a permanent freezing-of-funds condition, matching the "Validate" criteria (permanent freezing) for this exercise. It is also the same failure mode the maintainers already flagged as capable of "halting the chain via the distribution validator-removal hook" for the EIP-7702 sub-case, suggesting the same hook can be triggered generally, not only through `SetCode`.

### Likelihood Explanation
Reachable by any unprivileged party: an attacker (or unaware user) sends `usei` to the cast address of a target EVM address (a plain bank `Send`, no privileges needed), delegates from that cast address to a validator, and waits for the EVM address owner to submit any ordinary EVM transaction or call `associate`/`associatePubKey`. The association path is automatically triggered on every first EVM transaction from a new address [6](#0-5) , making the trigger condition common and outside the attacker's control-timing requirements (i.e., it will eventually happen for any active EVM user).

### Recommendation
Before calling `RemoveAccount` in `MigrateBalance`, check for the presence of staking delegations, unbonding delegations, and outstanding distribution rewards/starting periods keyed to `castAddr`, and either migrate that state to `seiAddr` as well (mirroring the balance migration) or refuse to delete/repurpose the account until such state is cleared, extending the same protective approach already applied to EIP-7702 authorities to the general association path.

### Proof of Concept
1. Derive `evmAddr` for a fresh EOA (no on-chain activity yet) and compute `castAddr = sdk.AccAddress(evmAddr[:])`.
2. From an unrelated account, `bank send` `usei` to `castAddr`, then submit `MsgDelegate` from `castAddr` to any validator (no signature needed by the EOA owner — this is a normal Cosmos tx signed by whoever controls `castAddr`'s spendable funds path... note: actually requires a pubkey on file for signing `MsgDelegate`; alternatively, funds/delegation-equivalent state can be pre-seeded through any module operation that credits `castAddr`, e.g. contract/precompile flows that don't require `castAddr` itself to sign).
3. Have the EOA owner submit a standard EVM transaction (any value transfer) using their private key; the ante handler's `EVMPreprocessDecorator.AnteHandle` runs the "not associatedTx and not already associated" branch and calls `AssociateAddresses`, which migrates spendable `usei`/wei but leaves the delegation record referencing `castAddr` untouched.
4. Confirm via `x/staking` queries that the delegation record still exists under `castAddr`, while `x/auth`'s account entry for `castAddr` has been deleted and `castAddr` can never sign a transaction (no private key exists that hashes to those exact raw bytes under Cosmos's derivation scheme).

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
