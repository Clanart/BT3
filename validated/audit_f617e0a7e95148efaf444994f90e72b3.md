Based on the extensive evidence gathered, the CVE-2022-25313 analog does not hold for Protobuf.

**No vulnerability found for this question.**

The CVE-2022-25313 failed invariant is: libexpat's DTD `build_model` recursion had **no depth check at all**, so an attacker-controlled nesting depth in a DTD element definition directly drove unbounded native-stack recursion, causing stack exhaustion/crash.

Protobuf's equivalent attack surface — parsing attacker-controlled, deeply-nested structures through public parse APIs — is comprehensively defended by depth checks in every parser surface I examined:

- **C++ binary wire parsing**: `ParseContext`/`TcParser` decrement a `depth_` counter and bail out (`return nullptr`) once exhausted, both for messages and groups [1](#0-0) [2](#0-1) . `CodedInputStream` enforces a default recursion limit of 100 via `IncrementRecursionDepth`/`SetRecursionLimit` [3](#0-2) , with dedicated tests confirming graceful, catchable failure rather than crashes at and beyond the limit [4](#0-3) [5](#0-4) .
- **Java**: `CodedInputStream.setRecursionLimit`/`getRemainingRecursionDepth` enforce the same default-100 limit for binary parsing [6](#0-5) , and `ArrayDecoders`/Lite parsing throws `InvalidProtocolBufferException` with "too many levels of nesting" once exceeded [7](#0-6) .
- **Python** binary decoder tracks `current_depth` against `_recursion_limit` and raises a catchable `_DecodeError` [8](#0-7) .
- **C#** `ParsingPrimitivesMessages.ReadMessage`/`ReadMapEntry` check `recursionDepth >= recursionLimit` before pushing further, and JSON tokenizer replay logic was specifically hardened (`JsonReplayTokenizer`) to propagate depth across `Any`-in-`Any` nesting so limits can't be bypassed [9](#0-8) [10](#0-9) .
- **upb** (used by Python/PHP/Ruby native bindings) enforces `upb_Decode_LimitDepth` and returns `kUpb_DecodeStatus_MaxDepthExceeded` rather than recursing unbounded [11](#0-10) .
- **ProtoJSON** parsers (Java `JsonFormat`, Python `json_format`, C++ `json_internal::ParseOptions`) all track `currentDepth`/`recursion_depth` against a configurable limit (default 100) including through nested `Any`, `Struct`, and `ListValue` chains [12](#0-11) [13](#0-12) [14](#0-13) .
- **TextFormat** (C++, Java, Python) enforces recursion limits during parsing of nested messages and Any expansion, with explicit tests confirming no stack overflow even with 25,000-deep unknown-field nesting [15](#0-14) [16](#0-15) .
- **Proto file parsing** (`.proto` schema, not attacker payload data) also has a nesting-depth cap that fails gracefully without crashing regardless of depth [17](#0-16) .

Every parsing surface analogous to expat's DTD `build_model` — binary, ProtoJSON, and TextFormat, across all supported language runtimes — enforces a depth check that throws a catchable, bounded exception well before native call-stack exhaustion. The one exception is Python/C++ TextFormat's default of *no* depth limit, but this is explicitly documented as intentional (TextFormat is treated as a trusted-configuration format, not an untrusted wire-protocol input) and the API exposes `max_recursion_depth`/`SetRecursionLimit` for callers handling untrusted TextFormat, plus the deep-unknown-field print path is verified crash-free even at extreme depths [18](#0-17) [19](#0-18) . This does not transfer as a valid CVE-2022-25313 analog under the report's scope (bounded binary/ProtoJSON input through a public parse API) — it is a documented, opt-in trust assumption for a different format, not a missing invariant on the binary/JSON parsing surface the CVE targets.
