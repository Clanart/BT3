Based on my research, I found a legitimate structural analog to the reported "multiply-before-divide causing interest to round to zero" bug class within the NFT royalty computation logic. I was unable to locate the compiled `.clsp` source for the on-chain NFT transfer program puzzle in the indexed codebase (it may not be included due to index size limits), so I cannot fully confirm whether the on-chain puzzle performs the identical floor-division arithmetic as the wallet-side driver code — but the wallet-side logic that decides which royalty conditions get asserted on-chain is confirmed and is sufficient to establish the root cause.

### Title
NFT royalty amount computation truncates to zero for small trade prices, allowing structured trades to bypass royalty payment entirely - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
The royalty amount owed to an NFT creator is computed using integer floor division of `amount * percentage // MAX_ROYALTY_BASIS_POINTS` (basis points scale = 10000). When the per-trade fungible amount is small enough relative to the royalty percentage, this computation truncates to zero. The wallet additionally uses this same zero-check to decide whether to *even include* the royalty price requirement in the on-chain `trade_prices_list` that is asserted by the settlement/transfer-program puzzle. This mirrors the reported bug class where multiplying a rate by an amount before dividing by a large scale constant systematically rounds to zero for small inputs/short durations, letting a party structure many small operations to accumulate zero total accrual/fee/royalty even though a single larger operation would not.

### Finding Description
`compute_royalty_amount` performs the royalty math as pure floor-division: [1](#0-0) 

`royalty_calculation` (used by both the wallet CLI/RPC royalty preview and various tests) performs the same style of truncating computation: [2](#0-1) 

Critically, when building an actual NFT1 offer, the wallet uses this same "does it round to zero" check to decide whether to include the corresponding price at all in the `trade_prices_list` supplied to `generate_signed_transaction`, which becomes part of the on-chain solution/condition set enforced by the ownership-layer transfer program: [3](#0-2) 

Because the check `price[0] * offered_royalty_percentages[asset] // MAX_ROYALTY_BASIS_POINTS != 0` is evaluated per individual trade price component, a counterparty can split what would otherwise be one large purchase (which would produce a non-zero, correctly-rounded royalty) into many smaller settlement payments, each below the rounding threshold. Each smaller trade legitimately computes and asserts a royalty of `0`, and the corresponding royalty payment CreateCoin is simply skipped: [4](#0-3) 

This is the same root-cause pattern as the referenced report: `amount * rate / SCALE` performed with integer/floor semantics, where `SCALE` (10000 basis points here, versus `365 days * 1e9` in the original) dominates for small per-operation amounts, and repeatedly performing many small operations lets the actor avoid ever paying the accrued value that a single large operation would have required.

### Impact Explanation
An NFT with a nonzero configured royalty (e.g. 1%–5%) is supposed to guarantee the royalty address receives a percentage of every settlement trade price. By repeatedly trading in small enough fungible increments (via many sequential offers/take-offers, each below the rounding threshold for that NFT's percentage), a taker/maker pair can transfer arbitrarily large cumulative value for an NFT while the on-chain enforced royalty consistently computes and requires `0`, systematically denying the royalty holder their designed economic entitlement. This is an economic/value-transfer defect (Medium severity), not a corruption of consensus state, matching the classification given to the original report (BetaFinance rated this class of issue Medium/acknowledged-limitation rather than High/Critical).

### Likelihood Explanation
Exploiting this requires only a cooperating offer maker and taker (or a single actor controlling both sides via linked wallets), both unprivileged participants who can freely construct and exchange Chia offer files — no special network position or protocol privilege is needed. The threshold amount at which royalty rounds to zero is deterministic and easily computed as `floor(10000 / percentage)` minus one, making the structuring strategy straightforward to automate.

### Recommendation
Avoid combined multiply-then-integer-divide-by-basis-points patterns that truncate for small values, or, at minimum, disallow/flag NFT offers whose computed royalty would round to zero rather than silently omitting the payment from `trade_prices_list`. As BetaFinance's response noted for the original bug, a full precision fix may not be practical; documenting the minimum trade price required to guarantee non-zero royalty per given percentage (as Chia already does implicitly via `MAX_ROYALTY_BASIS_POINTS`) and warning NFT creators/wallet UIs when royalty rounds to zero would mitigate the structuring exploit.

### Proof of Concept
1. Mint an NFT with `royalty_percentage = 100` (1%, i.e. basis points out of 10000).
2. Threshold amount below which royalty rounds to zero: any fungible trade price `p` such that `p * 100 // 10000 == 0`, i.e. `p < 100` mojos.
3. Construct N offers (maker offering the NFT, requesting `p = 99` mojos each), and have the taker fulfill all N sequentially instead of a single offer for `N * 99` mojos.
4. For each individual offer, `nft_wallet.py:1030` computes `99 * 100 // 10000 == 0`, so the trade price is excluded from `trade_prices_list`, and `royalty_payments` for the asset sums to `0`, skipping the royalty CreateCoin entirely (`nft_wallet.py:1044-1046`).
5. Over N trades the NFT changes hands N times for a cumulative price of `N * 99` mojos with `0` total royalty paid, whereas a single trade of `N * 99` mojos (for `N*99 >= 100`) would have correctly required a nonzero royalty payment.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
