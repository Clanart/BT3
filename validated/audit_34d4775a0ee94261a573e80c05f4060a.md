### Title
Unbounded HashMap indexing on attacker-controlled Participant indexes panics the PedPoP blame/decryption path - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2020-14777 is a remotely-triggered, repeatable crash (complete DoS) caused by malformed input reaching the optimizer. The Serai analog is an unprivileged-party-reachable panic in the PedPoP blame machinery: `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` indexes `self.commitments[&sender]` with `Participant` values that are never validated against `params.n()`. `Participant::new` only rejects zero, so any nonzero `u16` — including indexes greater than `n` or indexes for participants who never registered — reaches these `HashMap` `Index` impls, which panic on a missing key, crashing the executing validator/processor.

### Finding Description
`Decryption::register` asserts on re-registration but nothing bounds-checks lookups. `enc_keys` is only populated for participants `1 ..= n` via `AdditionalBlameMachine::new`, which iterates `Participant::new(i)` for `i in 1 ..= n` [1](#0-0) . Later, `blame(sender, recipient, msg, proof)` flows into `decrypt_with_proof`, which evaluates `self.enc_keys[&decryptor]` while building the DLEq verification statement — before any validity check on `recipient` [2](#0-1) . A `recipient` not in `1 ..= n` (or who never registered a key) causes an unconditional `HashMap` index panic. Likewise, once a message decrypts to a canonical scalar, `blame_internal` indexes `self.commitments[&sender]` for share verification, panicking on an out-of-set `sender` [3](#0-2) .

The inputs are entirely attacker-shapable: `EncryptedMessage::read` accepts arbitrary bytes (`read_G`, `SchnorrSignature::read`, share bytes) [4](#0-3) , and `sender`/`recipient` are plain `Participant` values supplied by the caller (in the coordinator these are read straight from the `InvalidDkgShare`/`VerifyBlame` transaction bytes via `Participant::new`, which permits any nonzero index). The blame transaction handler consumes these values and calls `.blame(accuser, accused, share, proof)` without a membership check [5](#0-4) .

### Impact Explanation
A single crafted blame/accusation naming a `recipient` (or `sender`, on the share-verification path) outside the registered set panics every node that evaluates it — a "hang or frequently repeatable crash" equivalent, matching the CVE's availability impact. It aborts DKG blame adjudication and crashes the processor handling `VerifyBlame`, denying service to the key-generation/signing pipeline.

### Likelihood Explanation
Reaching it requires submitting a blame transaction referencing a non-registered or out-of-range participant plus a deserializable `EncryptedMessage` (and an `EncryptionKeyProof`-shaped blob for the `enc_keys` path, since the panic fires while constructing the verify arguments, independent of proof validity). Any party able to submit a blame message — not just a threshold participant — can trigger it; the only gate is transaction authentication, which the panic precedes semantically (blame evaluation happens on the signed message's contents, and the panic occurs inside `blame_internal` before concluding who is at fault).

### Recommendation
In `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal`, replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with fallible lookups (`get(&decryptor).ok_or(...)` / `get(&sender)`) that map to a well-defined outcome (e.g., treating an unknown `recipient`/`sender` as the faulty party or an `Err`). Alternatively, validate `sender`/`recipient` against `params.n()`/`all_participant_indexes` at the top of `blame()`/`blame_internal()` and error before any indexing.

### Proof of Concept
Conceptually:
```rust
// n = 3; context, commitments registered for participants 1..=3
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();
// Attacker supplies a blame naming participant 7 as the recipient (decryptor),
// a well-formed EncryptedMessage, and any deserializable EncryptionKeyProof.
machine.blame(sender, Participant::new(7).unwrap(), msg, Some(proof));
// -> panics at crypto/dkg/pedpop/src/encryption.rs:388 on enc_keys[&Participant(7)]
```
Similarly, `blame_internal` reaches `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599` for any `sender` not among the registered commitment senders once the supplied message decrypts to a canonical scalar.
