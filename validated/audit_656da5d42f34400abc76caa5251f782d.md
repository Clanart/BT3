### Title
Offer parsing infinite loop via crafted cyclic coin lineage in `Offer.get_root_removal` — ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.get_root_removal()` walks a coin's ephemeral parent chain within an untrusted offer's `SpendBundle` to find its non-ephemeral ancestor. The loop trusts the `parent_coin_info` fields of attacker-supplied `Coin` objects without verifying that the chain is acyclic. A malicious offer file can declare a set of "ephemeral" removals whose `parent_coin_info` values reference each other in a cycle, with none of them qualifying as non-ephemeral, causing the `while` loop to iterate forever. [1](#0-0) 

### Finding Description
`get_root_removal` computes `non_ephemeral_removals` as coins whose `parent_coin_info` is not the name of any other removal in the same bundle, then walks: `while coin not in non_ephemeral_removals: coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)`. [2](#0-1) 

`Coin.parent_coin_info` is just a plaintext field set by whoever constructs the `SpendBundle`; nothing in `Offer.from_bytes`/`Offer.from_spend_bundle` cryptographically ties it to a real, on-chain parent before this function runs — that link is only enforced later, when the bundle is actually spent on chain and the puzzle/singleton rules are checked. An attacker crafting an offer file can therefore build two (or more) coins A and B where `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`, both present in `self.removals()`, and neither present in `additions()` from a "real" ancestor — making both ephemeral relative to each other and forming a closed cycle with no exit into `non_ephemeral_removals`. Once `get_root_removal` is called on such a coin, the `while` loop never terminates because it keeps bouncing between A and B, neither of which is ever a member of `non_ephemeral_removals`.

This function is reachable purely from parsing/inspecting an offer — it is invoked by `get_primary_coins()` (used to summarize offers, e.g., for display or trade-record building) and by pending-payment summary logic, both of which run on offer objects supplied by an offer counterparty without requiring the local node to first accept/spend the offer. [3](#0-2) [4](#0-3) 

This mirrors the PeerTube CVE-2025-32947 bug class: untrusted, attacker-controlled crawlable/graph-like data (there: ActivityPub actor/objects; here: a chain of coin parent references) is walked with an unbounded loop that assumes well-formedness, letting a remote party trigger a permanent hang by supplying a cyclic structure.

### Impact Explanation
A wallet user who receives or inspects a maliciously crafted offer (via `chia wallet take_offer`, `get_offer_summary`, RPC endpoints that call into `Offer` parsing, or any UI that previews offers before acceptance) can have the calling thread/task hang indefinitely in this loop. Because `WalletStateManager`/RPC handling in Chia often serializes access via shared locks, a single crafted offer can block wallet responsiveness for the affected wallet client — a spend-triggered transaction-processing halt without requiring the user to ever actually accept/spend the offer.

### Likelihood Explanation
Likelihood is high for any user-facing flow that parses/summarizes an untrusted offer file before the user decides to accept it, since that is the intended, exposed use case of the `Offer` class (offers are explicitly meant to be shared with untrusted counterparties and inspected before being taken). Constructing the crafted `SpendBundle` requires no special privileges or signatures for the purpose of this parsing bug, because the offending code path runs before final signature/consensus validation.

### Recommendation
Harden `get_root_removal` (and the related `get_cancellation_coins` double `while True` loops) against cycles:
- Track visited coin names in a set while walking the parent chain and raise `ValueError`/`ValidationError` immediately if a coin is revisited.
- Alternatively, bound the loop by `len(all_removals) + 1` iterations, failing safe if that bound is exceeded.
- Apply the same cycle-detection principle to `get_cancellation_coins`'s dependency-removal loops, which have similar unbounded-iteration patterns over attacker-suppliable dependency/announcement maps. [5](#0-4) 

### Proof of Concept
1. Construct two `Coin` objects `A` and `B` (arbitrary puzzle hash/amount) such that `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`.
2. Build `CoinSpend`s for `A` and `B` (with any parseable puzzle reveal/solution) and combine into a `WalletSpendBundle`; wrap into an `Offer` via `Offer.from_spend_bundle(...)`.
3. Call `offer.get_primary_coins()` (or any code path that calls `get_root_removal(A)`), e.g., through offer-summary RPCs invoked when a peer shares this offer file for review.
4. Observe the call never returns: `non_ephemeral_removals` excludes both `A` and `B` (each one's parent is the other, which is itself in `all_removals`), so the `while coin not in non_ephemeral_removals` loop cycles between `A` and `B` forever.

    # This returns the non-ephemeral removal that is an ancestor of the specified coin
    # This should maybe move to the SpendBundle object at some point
    def get_root_removal(self, coin: Coin) -> Coin:
        all_removals: set[Coin] = set(self.removals())
        all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
        non_ephemeral_removals: set[Coin] = {
            c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
        }
        if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
            raise ValueError("The specified coin is not a coin in this bundle")

        while coin not in non_ephemeral_removals:
            coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

        return coin
