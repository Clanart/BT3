### Title
SignableTransaction fee/weight estimate omits the OP_RETURN output, producing undersized `needed_fee` and a transaction paying less than the intended feerate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` to `tx_outs`, but computes `needed_fee` via `calculate_weight_vbytes`, which is only ever passed `payments` (and optionally `change`) — never the data output. Analogous to the XFS bug where an undersized fixed roundoff value (512) was used in place of the actual required size (4096), the fee calculation uses an undersized transaction-size value, so the constructed transaction's real vsize exceeds the estimated one while the fee budget does not.

### Finding Description [1](#0-0)  `tx_outs` gains an OP_RETURN output for `data` (validated to ≤80 bytes at line 171), yet at line 204 `calculate_weight_vbytes(tx_ins.len(), payments, None)` only expands a template transaction containing `payments` — the OP_RETURN output is absent from the template, so `weight`/`vbytes` (lines 68–101) are undersized by roughly 90+ weight units (~11 vbytes base + ~80 script bytes ≈ 90 vbytes worst case). `needed_fee = fee_per_vbyte * vbytes` (line 206) is therefore undersized, and the `TooLowFee` minimum-relay check at line 211 is evaluated against the underestimated vbytes.

When `change` is provided, the change output is set to `input_sat - payment_sat - fee_with_change` (lines 224–233), so the actual fee paid equals the underestimated `fee_with_change`. The broadcast transaction's true feerate is `fee_with_change / actual_vsize`, which is strictly below `fee_per_vbyte` and can fall below `DEFAULT_MIN_RELAY_TX_FEE` whenever `fee_per_vbyte` was chosen at or near the minimum — even though the line-211 check passed. The same underestimation feeds `needed_fee()`, which `processor/src/networks/bitcoin.rs:433-452` relies on via `make_signable_transaction`/`amortize` logic (comments there assume fee math is correct and `panic!` on `TooLowFee`).

A second instance of the same class: the flat `DUST = 546` check at lines 165–168 uses a fixed minimum regardless of the payment's `script_pubkey` size, while Bitcoin's real dust threshold scales with output size — a payment to a large script with value ≥546 can still be dust/non-standard, again an undersized constant applied to input-dependent requirements.

### Impact Explanation
An unprivileged party who can cause a withdrawal plan carrying `data` (or payments with large scripts) causes the threshold network to produce and sign a transaction whose effective feerate is lower than the requested/median rate — potentially below the mempool minimum relay feerate despite passing the `TooLowFee` guard. Result: a signed, broadcast transaction that will not relay or confirm promptly, locking UTXOs the scheduler considers spent, and misreporting `needed_fee`/`fee()` upward relative to reality. The `NotEnoughFunds`/amortization checks also pass on the undersized fee, so change outputs can be created with less value reserved for fees than intended.

### Likelihood Explanation
Reachable whenever a `data`-bearing send is constructed: the underestimation is deterministic and grows with `data` length (up to ~90 vbytes ≈ 15%+ error on small transactions). It requires no timing, collusion, or privileged position — only that the caller supply `data` and a low `fee_per_vbyte` to cross the relay threshold. Exploitation degrades to degraded/unrelayable transactions rather than theft, placing it at Medium severity.

### Recommendation
Include the OP_RETURN output in the weight template: pass the full output set (payments + data output + optional change) into `calculate_weight_vbytes`, or add `ScriptBuf::new_op_return(...)`-equivalent size to the template before computing `vbytes`. Also compute the per-payment dust threshold from the actual `script_pubkey` size (e.g., `dust_relay_fee`-based calculation per output) instead of the flat `DUST` constant in `SignableTransaction::new`.

### Proof of Concept
```rust
// Construct a SignableTransaction with data and a change output at the
// minimum relay feerate (1 sat/vbyte).
let tx = SignableTransaction::new(
  vec![input],                      // one ReceivedOutput
  &[(payment_script, 10_000)],      // one payment
  Some(change_script),              // change absorbs the leftover
  Some(vec![0u8; 80]),              // max-size OP_RETURN
  1,                                // fee_per_vbyte = 1 sat/vb (minimum relay)
).unwrap();

// needed_fee passes the TooLowFee check against the underestimated vbytes.
let needed = tx.needed_fee();
// The real transaction contains the OP_RETURN output (~90 extra vbytes),
// so the actual fee == needed is spread over a larger vsize:
//   actual_feerate = needed / real_vsize < 1 sat/vb
// The signed transaction is below DEFAULT_MIN_RELAY_TX_FEE and will not
// relay, while SignableTransaction::new reported success.
```
