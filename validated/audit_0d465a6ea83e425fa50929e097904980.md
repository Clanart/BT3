### Title
Panic on untrusted decryptor index in PedPoP blame decryption (`Decryption::decrypt_with_proof`) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2021-3411 is an out-of-bounds memory access triggered while the kernel scanned attacker-influenced bytes (int3 padding detection in the linker path). The analogous defect class in Serai is an unchecked index into protocol state driven by attacker-supplied bytes. In PedPoP, `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with the panic-on-missing `HashMap` `Index` implementation, where `decryptor` is a `Participant` value derived from a blame/accusation message that an unprivileged DKG participant can submit. If the named participant never registered an `EncryptionKeyMessage`, every honest node evaluating the blame panics.

### Finding Description
`decrypt_with_proof` verifies the accused's `EncryptionKeyProof` and then unconditionally dereferences the decryptor's registered encryption key:

```rust
// crypto/dkg/pedpop/src/encryption.rs:381-390
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],
  )
```

`enc_keys` is only populated via `Decryption::register`, which is called when an `EncryptionKeyMessage` for a participant is processed [1](#0-0) . There is no check that `decryptor` is present in `enc_keys`; the `HashMap` `Index` impl panics on a missing key. The `msg` and `proof` arguments are deserialized from wire bytes via `EncryptedMessage::read` / `EncryptionKeyProof::read` [2](#0-1) [3](#0-2) , and `decryptor` is the participant index carried by the accusation in the PedPoP blame flow.

The same panic-on-untrusted-index pattern exists in two neighboring spots: `Encryption::encrypt` uses `self.decryption.enc_keys[&participant]` [4](#0-3) , and `Decryption::register` `assert!`s on duplicate registration, so a participant who resends an `EncryptionKeyMessage` also crashes the receiver [5](#0-4) .

### Impact Explanation
A panic in Rust unwinds and, inside a validator's DKG/blame handling, crashes the task or process evaluating the accusation. A malicious DKG participant can therefore (a) crash honest nodes processing a blame transaction, and (b) sabotage blame resolution itself — e.g., submit an accusation naming a decryptor who skipped the registration round so every verifier panics instead of confirming or rejecting the accused dealer. This maps to the CVE's confidentiality/integrity/availability threat with availability being the concrete effect here: an unrecoverable abort of threshold key generation / share-blame processing driven purely by attacker-chosen bytes.

### Likelihood Explanation
The attacker only needs to be a DKG participant able to emit an accusation (the same unprivileged reach as bytes fed to `EncryptedMessage::read` / `EncryptionKeyProof::read`, which are explicitly in-scope). Two simple triggers exist: accuse while the named decryptor never submitted an `EncryptionKeyMessage` (a participant can withhold or lose its registration), or duplicate a registration to hit the `assert!`. The code performs no membership guard before indexing — `enc_keys` is a plain `HashMap` built opportunistically from received messages, so absence of a key is a realistic state, not a theoretical one. Residual uncertainty: whether upstream PedPoP code pre-validates that the accuser/decryptor completed registration before invoking `decrypt_with_proof`; nothing in this file enforces it, and the defensive `assert!` in `register` shows the authors expected caller discipline that isn't documented.

### Recommendation
Replace infallible `HashMap` indexing/asserts on protocol-derived values with checked lookups returning a `DecryptionError`:

```rust
let Some(dec_key) = self.enc_keys.get(&decryptor) else {
  Err(DecryptionError::InvalidProof)?
};
```

Apply the same treatment to `Encryption::encrypt` (`enc_keys.get(&participant)` → error instead of panic) and convert the duplicate-registration `assert!` in `Decryption::register` into an ignorable/error outcome, since a duplicated `EncryptionKeyMessage` is an attacker-reachable condition, not an invariant violation.

### Proof of Concept
1. Participant A joins the DKG but never broadcasts an `EncryptionKeyMessage`, so `decryption.enc_keys` on honest nodes has no entry for A.
2. A (or a colluding-free second path: an accusation naming A as decryptor, since `decryptor` is read from the accusation) submits a blame message against dealer D containing an `EncryptedMessage` deserialized via `EncryptedMessage::read` and D responds with an `EncryptionKeyProof` deserialized via `EncryptionKeyProof::read`.
3. Each verifier calls `Decryption::decrypt_with_proof(from: D, decryptor: A, msg, Some(proof))`. After `dleq.verify` is reached, `self.enc_keys[&A]` executes `HashMap`'s `Index`, which panics with "key not found", aborting blame verification on every honest node.

The direct trigger is one line: `&[self.enc_keys[&decryptor], *proof.key]` in `crypto/dkg/pedpop/src/encryption.rs` [6](#0-5) .
