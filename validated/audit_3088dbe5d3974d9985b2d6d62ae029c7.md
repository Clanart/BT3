## Analog Identified

This maps to the **asset-representation invariant** (native coin ↔ ERC20 1:1 accounting across escrow) rather than a literal Solidity `call()` in a smart contract, but the root cause is the same class of bug as the Meson report: **a low-level EVM call (`CallEVM`) to a token contract is trusted to have performed the transfer, and when it silently no-ops (self-destructed/non-existent contract), the code path that detects the failure does not roll back the escrow it already performed.**

### Title
Silent swallowing of failed native-ERC20 unescrow permanently locks user funds on IBC ack-error/timeout - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
`ConvertCoinNativeERC20` in [1](#0-0)  escrows a user's Cosmos coin into the `erc20` module account **before** verifying that the corresponding low-level `transfer` call on the paired ERC20 contract actually moved tokens. The only verification that the call did something is `validateTransferEventExists`, which checks for a `Transfer` log [2](#0-1) . If the paired ERC20 contract has been self-destructed (exactly the Meson `_unsafeDepositToken` scenario — a low-level call to an address with no code trivially "succeeds" with empty return data and no logs), this check correctly returns an error — but by then the coin has already been irreversibly pulled from the user into the module account via `SendCoinsFromAccountToModule` [3](#0-2) .

The direct `MsgConvertCoin` path guards against this by checking contract existence **before** calling `ConvertCoinNativeERC20` [4](#0-3) . However, the IBC failure-recovery path, `ConvertCoinToERC20FromPacket` (invoked from `OnAcknowledgementPacket`/`OnTimeoutPacket`), has no such guard and additionally **deliberately swallows the error**: [5](#0-4) 

### Finding Description
When an IBC transfer times out or is acknowledged with an error, `ConvertCoinToERC20FromPacket` attempts to opportunistically re-wrap the refunded Cosmos coin into its native ERC20 representation by calling `ConvertCoinNativeERC20`. That function:
1. Reads the current token balance (no state change).
2. Calls `bankKeeper.SendCoinsFromAccountToModule` to escrow the coin — this **executes and persists**.
3. Calls `evmKeeper.CallEVM(... "transfer" ...)` on the paired ERC20 contract to move tokens out of the module account to the receiver.
4. If the contract has no code (self-destructed, or was never really deployed), the EVM call returns success trivially with empty `Ret` and no logs — the same low-level-call behavior called out in the Meson report.
5. `validateTransferEventExists` correctly detects the absence of a `Transfer` log and returns an error.
6. This error propagates back into `ConvertCoinToERC20FromPacket`, which does **not** return it — it only emits a `types.EventTypeFailedConvertERC20` event and returns `nil` [6](#0-5) .

Because step 2's `SendCoinsFromAccountToModule` already committed against the live `ctx` (there is no `ctx.CacheContext()`/`write()` pattern around the call in `ConvertCoinToERC20FromPacket`), and because the caller ultimately returns `nil` (success) for the whole operation, the escrowed coins are never burned (the `BurnCoins` step at the end of `ConvertCoinNativeERC20` is never reached) and are never refunded to the user. The coins are permanently stranded in the `erc20` module account with no code path that recovers them.

### Impact Explanation
This is a Critical **permanent freezing/locking of user funds** through an ordinary, unprivileged flow: any account can register an arbitrary ERC20 contract as a "native ERC20" token pair via permissionless registration, then trigger an IBC send of that denom that later fails (timeout or error ack) after the paired contract has been self-destructed (or is otherwise codeless, e.g. a `CREATE2`-based contract intentionally destroyed by its deployer between registration and packet failure). Every such failure permanently burns the refunded coin amount into the module account with no possibility of recovery for the affected user — satisfying the in-scope "permanent freezing, locking ... of user funds" criterion.

### Likelihood Explanation
Requires: (1) permissionless (or governance) registration of a native ERC20 token pair for an attacker-controlled contract capable of self-destructing, (2) an IBC transfer of that denom that times out or errors, which an attacker fully controls the timing of via relayer behavior or channel/timeout manipulation, and (3) self-destructing the contract before/at the time of the failed-packet recovery attempt. All of these are reachable by an ordinary, unprivileged user without relying on validator, relayer, or governance misbehavior.

### Recommendation
- In `ConvertCoinNativeERC20`, perform the contract-existence check (the same `acc == nil || !acc.HasCodeHash()` guard used in `ConvertCoin`/`ConvertERC20`) before escrowing coins, or wrap the escrow + unescrow sequence in a `ctx.CacheContext()` and only call `write()` on full success.
- In `ConvertCoinToERC20FromPacket`, do not silently discard errors from `ConvertCoinNativeERC20` when a prior state mutation (escrow) has already occurred; either avoid the escrow attempt entirely when the contract is not verifiably present, or ensure the escrow is rolled back on failure before returning `nil`.
- Apply the same defensive pattern (existence check before any state-mutating step, or atomic cache-and-commit) consistently to all call sites that perform low-level `CallEVM`/`CallEVMWithData` transfers on user-registered ERC20 contracts, since the Solidity-documented "call to non-existent account returns success" behavior is directly reachable through this Go code path.

### Proof of Concept
1. Permissionlessly register a self-destructible ERC20 contract as a native ERC20 token pair via `MsgRegisterERC20` (assuming `PermissionlessRegistration` is enabled, or via a governance proposal otherwise).
2. Convert some native coin into the ERC20 representation normally (`MsgConvertCoin` succeeds since the contract still has code) — user now holds ERC20 tokens; then convert back or otherwise obtain the underlying denom via IBC send-out, such that the account will be receiving a refund of the bank-side denom on failure.
3. Initiate an IBC transfer of the paired denom that will time out (e.g., use a short timeout with no counterparty relay) or induce an error acknowledgement.
4. Before the timeout/ack-error is processed on this chain, self-destruct the paired ERC20 contract.
5. When `OnTimeoutPacket`/`OnAcknowledgementPacket` fires, `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20` executes `SendCoinsFromAccountToModule` (debiting the refunded coin from the user into the `erc20` module account), then the low-level `transfer` call to the now-codeless contract returns success with no logs, `validateTransferEventExists` fails, the error is caught and swallowed, and the function returns `nil`.
6. The user ends the flow with neither the bank coin nor the ERC20 token — the amount is permanently stuck in the `erc20` module account, verifiable by querying the module account balance for `pair.Denom` before and after the sequence.

*Note: I was not able to fully verify from the indexed code whether the outer IBC packet-receive path (`OnRecvPacket`, case 2) is wrapped in an ibc-go core `ctx.CacheContext()` that would auto-discard state on an error acknowledgement — that would make the direct-receive case (not the ack/timeout case) potentially self-healing. However, the `ConvertCoinToERC20FromPacket` path (`OnAcknowledgementPacket`/`OnTimeoutPacket`) unconditionally returns `nil` after catching the internal error regardless of any outer caching, so the fund-locking impact described above holds independent of that uncertainty.*

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

// validateTransferEventExists returns an error if the given transactions logs DO NOT include
// an expected `Transfer` event from the expected address
func validateTransferEventExists(logs []*types.Log, tokenAddress common.Address) error {
	if len(logs) == 0 {
		return errors.Wrapf(
			types2.ErrExpectedEvent, "expected Transfer event",
		)
	}
	found := false
	for _, log := range logs {
		if log.Topics[0] == logTransferSigHash.Hex() {
			if log.Address != tokenAddress.Hex() {
				return errors.Wrapf(
					types2.ErrUnexpectedEvent, "Transfer event from unexpected address",
				)
			}
			if found {
				return errors.Wrapf(
					types2.ErrUnexpectedEvent, "duplicate Transfer event",
				)
			}
			found = true
		}
	}

	if !found {
		return errors.Wrapf(
			types2.ErrExpectedEvent, "expected Transfer event",
		)
	}

	return nil
}
