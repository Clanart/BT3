## Cosmos EVM Analog Found

### Title
Balance-change event window in precompile `BalanceHandler` can desync EVM `StateDB` balances from the native `x/bank` ledger on recursive/nested precompile calls - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
The external report's bug class is "a critical decision made from a stale/unsynced state value instead of a freshly recomputed one." In Cosmos EVM, the analogous pattern is `BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange`, which records an event-list offset (`prevEventsLen`) *before* executing a precompile action and later slices `ctx.EventManager().Events()[bh.prevEventsLen:]` to decide which bank events to replay onto the EVM `StateDB`. On recursive/nested precompile invocations this offset bookkeeping can become stale/incorrect, causing bank-originated balance deltas to be mis-applied (double-applied or skipped) to `StateDB`, breaking the 1:1 invariant between native bank balances and EVM-visible balances.

### Finding Description
`BalanceHandler` tracks state purely via an integer index into the shared `sdk.Context` event log: [1](#0-0) 

and later replays only the events appended after that recorded index to update `StateDB` balances: [2](#0-1) 

In the production call path (`precompiles/common/precompile.go`), each precompile invocation via `RunNativeAction` is intended to get a *fresh* handler and its own event window: [3](#0-2) 

However, the repository's own test-only reference precompile does not follow this "new instance per call" discipline — it holds and reuses a single `BalanceHandler` instance across recursive precompile calls via `p.GetBalanceHandler()`, and the test explicitly documents the resulting bug: [4](#0-3) 

A second, more concerning test targets real production precompiles (ICS20 transfer that internally triggers distribution-precompile-style calls) and is explicitly named/commented as reproducing the same class of bug in a live IBC transfer flow: [5](#0-4) 

The root cause pattern mirrors the external report precisely: a decision (which bank events represent "this precompile call's" balance deltas) is made using a cached/offset value (`prevEventsLen`) that is not correctly re-derived relative to the *current* nested execution context, so on re-entrant/recursive precompile calls the event-window boundaries used to update `StateDB` can shift — causing balance-changing bank events from an inner (possibly reverted or already-processed) call to be either replayed twice onto `StateDB` or dropped entirely.

### Impact Explanation
If the event-window bookkeeping is corrupted during nested/recursive precompile execution (achievable by any unprivileged user calling a contract that recursively invokes a stateful precompile, e.g., through an ICS20 transfer that triggers distribution-style callbacks, as the checked-in test demonstrates), the EVM `StateDB` balance for an account can diverge from the actual `x/bank`/`x/precisebank` balance. Because `StateDB.AddBalance`/`SubBalance` calls driven by `AfterBalanceChange` are irreversible from the EVM's perspective within that transaction (they represent the EVM's view of spendable value), a mismatch here constitutes duplication or unauthorized creation/destruction of spendable EVM balance relative to the bank-backed reserve — i.e., breaking the `x/precisebank` 1:1 accounting invariant between native `uatom`/`aatom` and EVM-visible balances described in `x/precisebank/README.md`. This falls squarely under the allowed "Critical unauthorized minting/duplication/accounting corruption of spendable user value across EVM balances / precompile-mediated assets" impact category.

### Likelihood Explanation
Likelihood is moderate to high for the specific mechanism to be *triggerable*: the repository ships dedicated integration tests (`balance_handler_test.go`, `ics20_recursive_precompile_calls_test.go`) purpose-built to reproduce recursive-precompile-call event misattribution, indicating the underlying re-entrancy/event-window issue is a known, reachable code path (via contract calls chaining precompiles, or ICS20 transfers that invoke distribution logic). However, I was unable to fully confirm — within the remaining investigation budget — whether the *production* precompiles (`staking`, `distribution`, `gov`, `slashing`, `erc20`, `ics20`) exclusively use the safe "new BalanceHandler per `RunNativeAction` call" path shown in `precompile.go`, or whether any of them retain a persistent/shared handler field analogous to the debug fixture's `GetBalanceHandler()`. This distinction determines whether the vulnerability is live in production or already mitigated by the factory pattern for real precompiles. This is a material open question that requires direct inspection of the `Precompile` struct embedding and each precompile's call path (particularly whether `RunNativeAction` is invoked once per top-level EVM call or once per nested precompile re-entry, and whether cache-context commit/revert correctly re-bases the event index on each nested invocation).

### Recommendation
- Verify that every production precompile invokes `RunNativeAction`/`runNativeAction` (which creates a fresh `BalanceHandler` per call) for **every** nested/recursive invocation, not just the outermost call.
- Ensure `prevEventsLen` is computed against the event log of the *current* nested cache context, not a log that persists across reverted sub-calls, so that events from reverted inner calls are never replayed onto `StateDB`, and events already consumed by an inner call are never re-consumed by an outer call.
- Add an explicit invariant check (e.g., in integration tests or as a runtime assertion) that after any EVM transaction touching precompiles, `Σ StateDB balances == Σ (bank balance × conversion factor) + fractional balances` for all touched accounts, to catch such desyncs deterministically.

### Proof of Concept
The repository already contains a reproducible PoC demonstrating the mechanism:
- `evmd/tests/integration/balance_handler/balance_handler_test.go` — deploys `DebugPrecompileCaller.sol`, which recursively calls a debug precompile (`contracts/solidity/DebugPrecompileCaller.sol`), and asserts on the resulting event/balance-handler bookkeeping being incorrect.
- `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` — drives an ICS20 transfer that recursively triggers precompile-mediated distribution logic and checks for "reverted distribution calls leave persistent bank events that are incorrectly aggregated."

Both are cited above; I could not execute them in this environment, so exploitability against the *current* production precompile wiring (as opposed to the debug fixture) should be confirmed by running these tests and tracing whether `staking`/`distribution`/`ics20` precompiles share a `BalanceHandler` instance across nested calls in any real user-reachable flow.
