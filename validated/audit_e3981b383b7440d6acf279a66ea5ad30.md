## Title
Zero `GasTarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee`, halting block processing on all nodes - (File: `params/kip71_config.go`)

### Summary
Kaia's KIP-71 dynamic base fee calculation, `NextMagmaBlockBaseFee`, divides by the governance-controlled `GasTarget` parameter without checking it for zero. Unlike the sibling parameter `Kip71BaseFeeDenominator`, whose format checker explicitly rejects zero, `Kip71GasTarget`'s format checker is `noopFormatChecker`, which accepts any `uint64` value including `0`. A governance vote setting `GasTarget=0` therefore passes all format/consistency checks and, once ratified, causes every node computing the next block's base fee (both while verifying headers and while preparing new blocks) to panic on integer division by zero.

### Finding Description
`NextMagmaBlockBaseFee` computes the delta of the base fee using the block's gas target as a divisor: [1](#0-0) 
When `parentGasUsed > gasTarget` (true for essentially any nonzero gas usage once `gasTarget == 0`), the code executes `x.Div(x, new(big.Int).SetUint64(gasTarget))`, which is `big.Int.Div(x, 0)` — this is a Go runtime panic ("division by zero"), not a graceful error return. The same pattern exists in the decreasing-baseFee branch: [2](#0-1) 

The only defense against a zero divisor is for `BaseFeeDenominator`, which has an explicit `v != 0` format check and even a fallback (`64`) inside `NextMagmaBlockBaseFee` itself: [3](#0-2) [4](#0-3) 

In contrast, `Kip71GasTarget`'s parameter definition uses `noopFormatChecker`, which unconditionally returns `true`, so no value — including `0` — is rejected: [5](#0-4) [6](#0-5) 

Vote-level validation in `checkConsistency` (`kaiax/gov/headergov/impl/header.go`) also does not add any extra restriction for `Kip71GasTarget` beyond the generic no-op path shared with several other parameters: [7](#0-6) 

`NextMagmaBlockBaseFee` is invoked both when verifying a candidate header's `BaseFee` field (`VerifyMagmaHeader`, called by every node validating a proposed block) and when computing `nextBaseFee` for the fee-history RPC: [8](#0-7) [9](#0-8) 

Once a `GasTarget=0` governance change is ratified and takes effect at the epoch boundary, every full node (including the block proposer building the next block and every peer verifying it) will panic in this arithmetic, since the parent block's `GasUsed` will exceed `0` for essentially all non-empty blocks.

### Impact Explanation
This is reachable purely through the standard governance voting path (`governance_vote` RPC/API), which any council/governing node can invoke — no privileged node-internal or p2p access is required beyond the ordinary governance mechanism explicitly listed as an allowed reachable surface. Once ratified, the resulting panic in `NextMagmaBlockBaseFee` is triggered deterministically by ordinary block production/verification, causing a chain-wide halt (every honest node panics attempting to build or verify the next block after the parameter takes effect) rather than a single reverted transaction. This is a Medium-to-High severity consensus/liveness bug: unlike the reported Solidity issue where only a single liquidation call reverts, here the entire network's block processing pipeline can crash.

### Likelihood Explanation
Requires a governance vote to set `kip71.gastarget` to `0` and have it ratified (same mechanism used for other legitimate governance changes such as `basefeedenominator`, which already receives a zero-value guard, implying zero was anticipated as an invalid input for these fee-tuning parameters but the guard was only added for one of the two divisors). Given `Kip71GasTarget` has no format check at all, any governing node (or majority of council members in "none" mode) proposing/voting this value would trigger it — accidental misconfiguration (e.g., copy-paste error setting it like `BaseFeeDenominator`) is plausible, and no additional confirmation step exists.

### Recommendation
Add a `v != 0` (or `v > 0`) `FormatChecker` to the `Kip71GasTarget` parameter definition in `kaiax/gov/param.go`, mirroring the existing check for `Kip71BaseFeeDenominator`. As defense in depth, also guard `NextMagmaBlockBaseFee` in `params/kip71_config.go` to short-circuit (e.g., treat `gasTarget == 0` similarly to `BaseFeeDenominator`'s fallback, or return the current/lower bound base fee) rather than performing an unguarded division.

### Proof of Concept
1. Governing node calls `governance_vote("kip71.gastarget", 0)`. `NewVoteData` canonicalizes `0` to `uint64(0)` and calls `Kip71GasTarget.FormatChecker`, which is `noopFormatChecker` and returns `true` — the vote is accepted. [10](#0-9) 
2. `checkConsistency` performs no additional validation for `Kip71GasTarget`, so `VerifyVote` succeeds. [7](#0-6) 
3. At the next epoch boundary, the vote is ratified into `header.Governance`, updating `ParamSet.GasTarget = 0`.
4. On the following block, `parentGasUsed` (any nonzero value, e.g. from a simple transfer) is `> gasTarget (0)`, entering the branch that computes `x.Div(x, new(big.Int).SetUint64(0))`, which panics with "division by zero" inside `NextMagmaBlockBaseFee`. [11](#0-10) 
5. This function is called both by the block proposer preparing the header's `BaseFee` and by every verifying node's `VerifyMagmaHeader`, so the panic occurs network-wide, halting block production/verification.

	}
	return nil
}

func NewVoteData(voter common.Address, name string, value any) VoteData {
	param, ok := gov.Params[gov.ParamName(name)]
	if !ok {
		param, ok = gov.ValidatorParams[gov.ParamName(name)]
		if !ok {
			logger.Error("Invalid vote name", "name", name)
			return nil
		}
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		logger.Error("Canonicalize error", "name", name, "value", value, "err", err)
		return nil
	}

	if !param.FormatChecker(cv) {
		logger.Error("Format check error", "name", name, "value", value)
		return nil
	}
