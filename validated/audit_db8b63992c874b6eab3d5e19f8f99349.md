## Binding under test

`stored_operator_xonly_pk == true_funder_xonly_pk`, where `true_funder_xonly_pk` is the x-only pubkey of the operator who actually fronted the withdrawal payout (by supplying the additional funding inputs and their own valid `OP_RETURN` push in `create_payout_txhandler`), and `stored_operator_xonly_pk` is the value written to `withdrawals.payout_payer_operator_xonly_pk` by `update_finalized_payouts`.

## Trace

`create_payout_txhandler` at [1](#0-0)  builds the payout tx with three outputs: user payout (0), anchor (1), `OP_RETURN` with the operator's 32-byte x-only pubkey (2), and signs only input 0 with the user-supplied signature via `set_p2tr_key_spend_witness`.

The withdrawal signature's sighash type is force-normalized/enforced to `SinglePlusAnyoneCanPay` in `parse_withdrawal_sig_params`: [2](#0-1) . `SIGHASH_SINGLE|ANYONECANPAY` commits only to input 0 and the output at the same index (output 0); it commits to neither the anchor output nor the `OP_RETURN` output. This is confirmed again in `Operator::withdraw`, where the same sighash is checked against `calculate_sighash_txin(0, ...)` [3](#0-2) .

Consequently, once the honest operator's payout tx (with the valid witness) is broadcast/visible, a third party can lift the witness+input0 and output0 and construct a conflicting transaction that supplies its own additional funding inputs and substitutes any `OP_RETURN`, including one whose push is exactly 32 bytes but is not a valid curve x-coordinate.

`update_finalized_payouts` parses whatever `OP_RETURN` ends up confirmed on-chain: [4](#0-3) , using `parse_op_return_data` (which only checks push-opcode structure, not curve validity) [5](#0-4)  chained with `XOnlyPublicKey::from_slice(bytes).ok()`. A syntactically 32-byte but non-curve payload passes `parse_op_return_data` but fails `from_slice`, yielding `operator_xonly_pk = None`, persisted via `update_payout_txs_and_payer_operator_xonly_pk` [6](#0-5) .

`is_kickoff_malicious` then unconditionally treats a `None` payer pubkey as malicious: [7](#0-6) , triggering a `Challenge` against the honest operator's kickoff regardless of the fact that they genuinely funded the payout.

Downstream, `deposit_constant`/`host_deposit_constant` used by the bridge circuit to prove a valid payout also require a valid x-only pubkey parsed from the same `OP_RETURN` and will fail (`.expect("Invalid operator xonlypk")`) [8](#0-7) [9](#0-8) , so the operator cannot produce a disprove-resistant assertion either, exposing them to losing their `Disprove` challenge and collateral.

### Title
Third-party malleability of the payout tx's uncommitted `OP_RETURN` output permanently denies honest operator reimbursement - (File: core/src/builder/transaction/operator_reimburse.rs / core/src/verifier.rs)

### Summary
The user's withdrawal signature is forced to `SIGHASH_SINGLE|ANYONECANPAY`, which never commits to the payout tx's `OP_RETURN` output carrying the operator's x-only pubkey. Anyone who observes the signed input+output0 can construct a conflicting transaction (fronting the same payout amount themselves) with a corrupted `OP_RETURN`, e.g. a syntactically-32-byte but non-curve payload, causing `XOnlyPublicKey::from_slice` to fail and `operator_xonly_pk` to be recorded as `None`.

### Finding Description
The broken binding is `stored_operator_xonly_pk == true_funder_xonly_pk`. Because the enforced sighash (`SinglePlusAnyoneCanPay`, [10](#0-9) ) leaves the `OP_RETURN` output uncommitted in `create_payout_txhandler` [1](#0-0) , a competing transaction that reuses the honest operator's input0/output0 but replaces the `OP_RETURN` push with an invalid-but-32-byte payload can be raced into confirmation instead. `update_finalized_payouts`'s `.and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok())` chain [11](#0-10)  then stores `None` for `payout_payer_operator_xonly_pk`, and `is_kickoff_malicious` treats any `None` payer as malicious [7](#0-6) , permanently flagging the honest operator's kickoff even though they genuinely funded the withdrawal payout.

### Impact Explanation
The honest operator who fronted the withdrawal is flagged malicious and challenged; because the same corrupted `OP_RETURN` also breaks `deposit_constant` computation used by the bridge circuit (`.expect("Invalid operator xonlypk")` in [8](#0-7)  and [9](#0-8) ), the operator cannot generate a valid assertion/disprove-resistant proof, risking losing the ensuing Disprove challenge and having their collateral burned. This matches "an honest operator permanently unable to be reimbursed" / "an honest operator's collateral burned."

### Likelihood Explanation
Exploitation requires the attacker to win a mempool race against the operator's own broadcast and to front the full payout amount themselves (since the user-signed input alone typically does not cover the payout value; the remainder comes from additional funding inputs supplied by whoever broadcasts the winning transaction), with zero compensation to the attacker (they hold no operator collateral/kickoff path to claim reimbursement). This makes the attack a costly, targeted griefing action against a specific operator/withdrawal rather than a cheap, freely repeatable exploit, but it remains technically feasible for a well-funded adversary and is deterministic once the race is won.

### Recommendation
Require the withdrawal signature to use a sighash type that commits to all outputs (e.g. `SIGHASH_ALL`) or otherwise cryptographically bind the `OP_RETURN` operator-pubkey output to the same signature/commitment that authorizes the payout, so the `OP_RETURN` cannot be substituted by a third party without invalidating the user's authorization.

### Proof of Concept
`cargo test` plan:
1. Build a payout tx via `create_payout_txhandler` with a valid operator pubkey `OP_RETURN`, sign input 0 with `SinglePlusAnyoneCanPay`.
2. Construct a second, conflicting transaction reusing the same input0 witness and output0, adding attacker-supplied funding inputs, and replacing the `OP_RETURN` push with a fixed 32-byte value known to be an invalid x-coordinate (well-known invalid values exist).
3. Mine the second transaction (regtest) in place of the honest one.
4. Run `update_finalized_payouts` against the block containing it; assert `get_payout_info_from_move_txid` returns `operator_xonly_pk = None`.
5. Call `is_kickoff_malicious` for the honest operator's real kickoff data; assert it returns `true`, matching the asserted permanent-denial outcome of the missing-`OP_RETURN` case.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

/// Parses the OP_RETURN data from a Bitcoin script. It retrieves the first data push after an OP_RETURN.
pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
