Based on my research, I could not find a Protobuf analog that reproduces the specific failure mode of the AuctionHouse bug (an unsigned/wraparound subtraction of a timestamp minus a duration that causes valid operations to unexpectedly revert/DoS). Protobuf's core wire-format and length-limit arithmetic (`CodedInputStream::isBeyondLimit`, `ReadSizeFallback`, `EpsCopyInputStream::BytesUntilLimit`/`IsRequestedLessThanOrEqualTo`, PHP's `pushLimit`, C#'s `ValidateCurrentLimit`) is consistently written with explicit overflow/underflow-conscious checks [1](#0-0) , so the underflow class the report describes does not transfer to the binary parsing paths.

The closest analog I found is a missing range-validation gap in the ProtoJSON Timestamp parser, but its impact is different in kind (silent data corruption, not a DoS/underflow revert), so I present it with that caveat rather than as a strict match.

### Title
Missing calendar-field range validation in ProtoJSON Timestamp parsing produces silently incorrect epoch seconds - (File: src/google/protobuf/json/internal/parser.cc)

### Summary
`ParseTimestamp` in the C++ JSON parser decodes an RFC3339-like timestamp string into year/month/day/hour/minute/second components and feeds them directly into a Howard-Hinnant-style days-from-civil arithmetic formula, without validating that month ∈ [1,12], day ∈ [1,31], hour ∈ [0,23], minute ∈ [0,59], or second ∈ [0,60] [2](#0-1) .

### Finding Description
`TakeTimeDigitsWithSuffixAndAdvance` only enforces a digit-count limit and a non-zero check for year/month/day; it never bounds month to ≤12, day to ≤31, or hour/minute/second to their calendar-valid ranges [3](#0-2) . The parser then computes:
```
uint32_t m_adj = *mon - 3;
uint32_t carry = m_adj > *mon ? 1 : 0;
...
secs = int64_t{epoch_days} * 86400 + *hour * 3600 + *min * 60 + *sec;
``` [4](#0-3) 

The `m_adj = *mon - 3` unsigned subtraction wraparound is *intentionally* relied upon for `mon` in [1,3) as part of the days-from-civil algorithm (analogous to how AuctionHouse relied on unchecked subtraction, except here the wraparound is deliberate and self-corrected by the `carry` term for valid months). However, for attacker-supplied `mon` values outside [1,12] (e.g., "13" through "99", since the field only enforces "at most 2 digits + literal '-'", not calendar validity), the same formula silently produces an internally consistent but semantically wrong epoch-seconds value — no error is returned. The same absence of an upper bound applies to `day`, `hour`, `minute`, and `second`. Unlike the CodedInputStream/EpsCopyInputStream paths, which use `isBeyondLimit`-style checks to reject invalid lengths (a value-relationship invariant enforced everywhere else in this codebase) [5](#0-4) , this Timestamp-specific arithmetic path lacks the equivalent invariant checks on its attacker-controlled inputs.

I could not find any downstream call to `IsTimestampValid`/`TimeUtil` validation invoked from within `ParseTimestamp` itself — those exist only in `time_util.cc`'s independent `TimeUtil::FromString` code path, which is not used by this JSON parser [6](#0-5) .

### Impact Explanation
Applications that parse untrusted ProtoJSON messages containing `google.protobuf.Timestamp` fields (e.g., an expiry, an issued-at time, or an access-control timestamp) could receive a `Timestamp` message whose `seconds`/`nanos` do not correspond to the string the client claims to have sent, without any parse error being raised. This is a data-integrity/type-confusion issue (unvalidated field values silently accepted into arithmetic), not a memory-safety or DoS bug, and the severity depends heavily on how the consuming application uses the resulting value (e.g., for authorization decisions). This differs materially from the original report's DoS-via-revert impact, so I flag it as a plausible but lower-confidence Medium candidate rather than a confirmed high-severity issue.

### Likelihood Explanation
Any client using the public ProtoJSON parsing API (`google::protobuf::json::JsonStringToMessage` or equivalent) against a message containing a `Timestamp`/`Duration` well-known-type field can trigger this by simply supplying an out-of-range but well-formed-looking date component (e.g., `"2024-13-01T00:00:00Z"` or `"2024-01-01T99:99:99Z"`). No special privileges are required, matching the "ordinary client, bounded ProtoJSON input" threat model.

### Recommendation
Add explicit range checks in `ParseTimestamp` (and the analogous `ParseDuration`/nanos-parsing helpers) rejecting `mon > 12`, `day > days_in_month(mon, year)`, `hour > 23`, `min > 59`, and `sec > 60` (allowing for leap seconds if desired), returning `str->loc.Invalid(...)` as is already done for the zero-value checks, consistent with the strict validation pattern used elsewhere for length/limit fields in this codebase.

### Proof of Concept
I was not able to execute this in the current environment (no code execution tool available), so this is a static-analysis-based finding, not a verified runtime reproduction. A minimal manual reproduction would be:
1. Build a message with a `google.protobuf.Timestamp` field.
2. Call the C++ JSON parser (`google::protobuf::json::JsonStringToMessage`) with input `{"ts": "2024-13-40T25:99:99Z"}`.
3. Observe that `TakeTimeDigitsWithSuffixAndAdvance` accepts `mon=13`, `day=40`, `hour=25`, `min=99`, `sec=99` (all pass the "≤2 digits + non-zero" checks), and `ParseTimestamp` returns `absl::OkStatus()` with an incorrect `seconds` value rather than an `Invalid` status.

Given the substantial uncertainty about whether this rises to the severity/likelihood bar the report describes, and that I could not confirm it against upstream's issue tracker/SECURITY.md for a prior fix, I present this as the best available analog rather than a confirmed strong match.

absl::optional<uint32_t> TakeTimeDigitsWithSuffixAndAdvance(
    absl::string_view& data, int max_digits, absl::string_view end) {
  ABSL_DCHECK_LE(max_digits, 9);

  uint32_t val = 0;
  int limit = max_digits;
  while (!data.empty()) {
    if (limit-- < 0) {
      return absl::nullopt;
    }
    uint32_t digit = data[0] - '0';
    if (digit >= 10) {
      break;
    }

    val *= 10;
    val += digit;
    data = data.substr(1);
  }
  if (!absl::StartsWith(data, end)) {
    return absl::nullopt;
  }

  data = data.substr(end.size());
  return val;
}
