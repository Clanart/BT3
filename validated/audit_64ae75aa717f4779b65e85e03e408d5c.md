### Title
Cached FROST preprocess seed reused across `share`/`complete` calls produces deterministic nonce reuse, enabling secret share recovery - (coordinator/src/tributary/signing_protocol.rs)

### Summary
The Tigris bug is a check-effect-interaction violation: external interaction (`_safeMint` callback) runs while protocol state (`initId`, `_limitOrders`) is still unset, letting the attacker re-enter and double-use the stale state. In Serai, the analogous shape is a secret-bearing state object — the FROST preprocess seed — that is reconstructed and "re-spent" on every call without ever being marked consumed. `SigningProtocol::preprocess_internal` loads the `CachedPreprocesses` seed keyed only by `context`, rebuilds an `AlgorithmSignMachine` via `from_cache`, and `seeded_preprocess` deterministically re-derives the same nonces (`ChaCha20Rng::from_seed(*seed.0)` feeding `Commitments::new`). `DkgConfirmer::share` and `DkgConfirmer::complete` each invoke `share_internal` — hence `machine.sign(...)` — over attacker-supplied preprocess maps, with no consumption/deletion of the cached seed in between. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
- `preprocess_internal` only *writes* a seed when none exists (`CachedPreprocesses::get(...).is_none()` → `set`), and never deletes or rotates it; every subsequent call under the same `context` reloads the identical seed. [4](#0-3) 
- `from_cache` → `seeded_preprocess` makes nonces a pure function of the seed (`ChaCha20Rng::from_seed(*seed.0)`, `Commitments::new(&mut rng, ...)`), so two `sign()` invocations under one context reuse the exact same nonce scalars `(d, e)`. [5](#0-4) [6](#0-5) 
- `share_internal` is called twice per signing flow: once from `share()` and again inside `complete()` (`self.share_internal(preprocesses, key_pair)`), each time with a freshly parsed, externally supplied `HashMap<Participant, Vec<u8>>` of serialized preprocesses. [7](#0-6) [8](#0-7) 
- The FROST share equation mixes the nonce with the per-participant binding factor `rho` and the Lagrange coefficient for the `included` set; both are derived from the submitted preprocess set inside `sign` (`included` built from `preprocesses.keys()`, `B.calculate_binding_factors(&rho_transcript)` over the transcripted commitments). Two `sign` executions with the same nonces but different included sets or different commitment bytes yield two linearly independent shares over the same nonce scalars — the standard nonce-reuse equation that recovers the signer's secret key share. The library's own docs confirm this: "A preprocess MUST only be used once. Reuse will enable third-party recovery of your private key share." [9](#0-8) [10](#0-9) [11](#0-10) 

### Impact Explanation
Key share recovery. If any two `share_internal` executions under one context differ in the effective signing set — e.g., `share()` is evaluated over one preprocess map and `complete()` over a map containing an extra/different participant or different commitment bytes — the honest node emits two signature shares `s₁ = d + e·ρ₁·λ₁·k_share ...` and `s₂` built from identical `(d, e)` with distinct binding factors/Lagrange coefficients. All public values (commitments, ρ, λ, group key) are known, so the observer solves for the secret key share directly. This is precisely the forbidden state the spec warns about ("Reusing preprocesses would enable a third-party to recover your private key share"), and it is reached through sanctioned code paths rather than integrator misuse. [12](#0-11) 

### Likelihood Explanation
The seed is never consumed: `preprocess_internal` unconditionally reuses `CachedPreprocesses::get`, and `complete()` re-enters `share_internal` rather than caching the post-`sign` `AlgorithmSignatureMachine` from the `share()` phase. The preprocess maps fed to each call are independently parsed from untrusted bytes via `read_preprocess`, so divergence between the two sets requires only that the data sources differ (different participant coverage or commitment bytes in the collected preprocesses). A co-signing participant who can influence the preprocess set presented at `complete` (or cause `share`/`complete` to run over different attempt views) triggers the reuse. Residual uncertainty: I could not fully verify the upstream call sites in `coordinator/src/tributary/handle.rs` to confirm the two maps can diverge under attacker control; the code-level reuse of an unconsumed seed across two `sign` executions is, however, concretely present and matches the "parallel-session / ROS-style share reuse; CachedPreprocess determinism" class. [13](#0-12) [14](#0-13) 

### Recommendation
- Delete (or rotate) `CachedPreprocesses[context]` immediately after it is first loaded in `preprocess_internal`, so any second `share_internal` call under the same context cannot regenerate the same nonces — the equivalent of writing `initId`/`_limitOrders` before the external interaction in the Tigris fix.
- Better: persist the `AlgorithmSignatureMachine` (post-`sign` state) produced by `share()` and have `complete()` reuse that machine instead of re-running `share_internal`; `complete` currently discards the `share` machine and re-signs from scratch.
- Enforce consistency between the preprocess sets used in `share` and `complete` (e.g., hash/commit to the exact `preprocesses` map at share time and require byte-identical input at complete time).

    let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap(); // never deleted
    let (machine, _) = AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));

}

    self.share_internal(preprocesses, key_pair).map(|(_, share)| share)

    // -> solve for key share: s1 - s2 = e*(rho1*lam1 - rho2*lam2) -> e, then d, then share

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
