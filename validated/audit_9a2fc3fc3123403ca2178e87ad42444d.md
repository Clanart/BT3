## Title
Tron `IntentGatewayV2` cross-chain order fill is missing the duplicate-output-token guard present in the main EVM contract, permitting under-payment of order beneficiaries and stranded escrow — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The main EVM `IntentGatewayV2.sol` was patched to reject duplicate tokens in an order's `output.assets` list, using per-transaction transient storage (`tload`/`tstore`) in `placeOrder`, precisely because downstream fill logic keys per-leg fill/escrow state by *token address*, not by leg index. [1](#0-0)  The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does not contain this check anywhere in `placeOrder`. [2](#0-1)  This is the exact bug class from the external report: a list (here, `order.output.assets`) is iterated and per-item state is looked up/updated keyed by an identifier (token address) that can repeat, so a user/solver can supply duplicate entries and the shared per-token bucket causes some legs to be under-serviced while escrow is drained as if they were fully independent.

### Finding Description
On the canonical EVM contract, `placeOrder` explicitly defends against duplicate output tokens:
```solidity
// evm/src/apps/IntentGatewayV2.sol:165-179
for (uint256 i; i < outputsLen_;) {
    bytes32 token = order.output.assets[i].token;
    assembly ("memory-safe") {
        if tload(token) revert(...)   // InvalidInput
        tstore(token, 1)
    }
    ...
}
``` [1](#0-0) 

This exists because the fill implementations (`IntrinsicIntents._fillSameChain`, `ExtrinsicIntents._fillCrossChain`) track per-leg progress in a mapping keyed by `outputToken`:
```solidity
// IntrinsicIntents.sol:74
uint256 alreadyFilled = _partialFills[commitment][outputToken];
uint256 remaining = totalRequired - alreadyFilled;
``` [3](#0-2) 

Regression tests explicitly document that this dedup check exists to stop “same-chain partial fills [from] prematurely finaliz[ing] repeated output legs”:
```solidity
// IntentGatewayV2SameChainTest.sol:2054-2088
function testRevert_PlaceOrder_DuplicateOutputTokens() public { ... }
``` [4](#0-3) 

The Tron contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) is a separate, non-inheriting reimplementation of the same protocol for the TVM (it doesn't reuse `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents`), and its `placeOrder` only loops over `order.inputs` to escrow tokens — there is no loop over `order.output.assets` at all, so no duplicate-output check exists:
```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:332-497
function placeOrder(Order memory order, bytes32 graffiti) public payable {
    if (order.inputs.length == 0) revert InvalidInput();
    ...
    // only order.inputs are validated/escrowed; order.output.assets is never inspected
    ...
    emit OrderPlaced({ ..., outputs: order.output.assets });
}
``` [2](#0-1) 

Because this file is used as the canonical multi-chain contract (Tron is one of the supported destinations for `IntentGatewayV2` orders in the SDK), an order whose `output.assets` list contains the same token twice (e.g., `[USDC: 400, USDC: 600]`) will be accepted by `placeOrder` unmodified. If the fill-side logic on this Tron deployment also tracks fill/escrow progress per output token (as the canonical EVM implementation does via `_partialFills[commitment][outputToken]`), a solver filling the first leg for the first `USDC` amount will mark that token's bucket as satisfied, and the second identical-token leg will be treated as already-filled/zero-remaining even though the order's `output.assets` array says two separate amounts are owed. This is structurally identical to the RelayerV2 report: iterating a list with duplicate keys and applying "unstake all remaining balance"/"escrow release" logic per unique key rather than per list entry, so a user receives less than intended while the contract's internal accounting believes the order was correctly and fully filled/escrowed.

### Impact Explanation
This falls squarely within the accepted impact categories: **loss of funds for the order beneficiary** (they receive only one leg's worth of a duplicated-token output instead of the sum of both legs) and **wrong-beneficiary/wrong-amount settlement**, reachable by any unprivileged user constructing an `Order` with duplicate `output.assets` entries and calling the permissionless `placeOrder`/fill path — no relayer, prover, or admin collusion required. It is a genuine bridge-escrow/settlement correctness bug, not a peer/relayer trust issue.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires a user or integrator to construct an order with duplicate output tokens (something the canonical EVM contract now explicitly guards against, indicating this was already exploited/found as a real construction pattern, per the regression-test comments referencing "same-chain partial fills over-release/-finalize repeated ... legs"). Because Tron is a distinct, separately-maintained contract copy, the fix landed on the primary EVM contract was not backported, so any order flow that reaches this Tron contract remains exposed.

### Recommendation
Port the exact duplicate-token guard from `evm/src/apps/IntentGatewayV2.sol::placeOrder` (the `tload`/`tstore` based check over `order.output.assets`, and confirm the existing `_orders[commitment][token] != 0` duplicate-input check semantics match) into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`. Since Tron/TVM support for transient storage opcodes should be verified, an equivalent in-memory dedup loop (e.g., nested loop or sorting check) can be used if `tload`/`tstore` are unavailable/unreliable on Tron. Add the same regression tests (`testRevert_PlaceOrder_DuplicateOutputTokens`, `testRevert_PlaceOrder_DuplicateInputTokens`) against the Tron contract build.

### Proof of Concept
1. A user submits an `Order` on the Tron `IntentGatewayV2` deployment with `output.assets = [{token: USDC, amount: 400}, {token: USDC, amount: 600}]` and appropriate `inputs`.
2. `placeOrder` accepts the order without reverting (no duplicate-output check exists in this file), escrows the inputs, and emits `OrderPlaced` with the duplicated output list intact.
3. A solver fills the order. If the fill/redeem logic on this chain tracks per-leg progress keyed by output token address (mirroring the canonical `_partialFills[commitment][outputToken]` pattern used elsewhere in the protocol), the second `USDC` leg collapses into the same bucket as the first.
4. The beneficiary ends up receiving only `400` USDC (or some single-leg amount) instead of the intended `1000` USDC, while the contract's internal state considers the order fully filled/escrow correctly released — funds are lost/misdirected exactly as in the external RelayerV2 report's `[T1, T1]` duplicate-token walkthrough.

*Note: I could not directly view the Tron contract's fill/redeem functions (`fillOrder`/`withdraw` completion beyond line ~700) within the available tool budget to confirm whether Tron's fill path uses an identical per-token-keyed accounting structure as `IntrinsicIntents.sol`. The core, directly-verified vulnerability is the confirmed *absence* of the duplicate-output-token guard that the canonical EVM contract added specifically to prevent this bug class — a background engineer should verify Tron's fill-side accounting keys before finalizing severity, but the missing guard itself is a verified regression versus the patched EVM contract.*
