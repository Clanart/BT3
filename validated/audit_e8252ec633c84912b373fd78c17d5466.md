## Title
Symlink escape in merge-conflict "Open in editor" bypasses repository scope, disclosing files outside the repo — (File: `app/src/ui/lib/conflicts/unmerged-file.tsx`)

## Summary
`renderUnmergedFile`'s `onOpenEditorClick` builds the target path with a plain `join(props.repository.path, props.path)` and hands it directly to the external editor launcher, with no `lstat`/`realpath` containment check. `props.path` comes from git's unmerged/conflict status for a file that is part of an attacker-controlled merge/rebase (a fetched branch). If that path is checked out as an actual filesystem symlink whose target points outside the repository root, Desktop will still treat it as an in-scope "conflicted file" and open the editor against the resolved symlink target.

## Finding Description
`renderUnmergedFile` computes the "Open in editor" click handler as: [1](#0-0) 

and the equivalent context-menu handler used for the dropdown/"Open with default program" builds the same unguarded path: [2](#0-1) 

Both simply call Node's `join(repository.path, relativeFilePath)`, which is a pure string operation — it does not follow or validate symlinks, and does not check that the final path stays within `repository.path`. The resulting absolute path is passed to `openFileInExternalEditor` / `dispatcher.openInExternalEditor`, which flows to `AppStore._openInExternalEditor` → `launchExternalEditor` → `launchEditor`: [3](#0-2) 

`launchEditor` only verifies that the *editor binary* (`editorPath`) exists via `pathExists`; it performs no existence/containment check on the *target file path* being opened — the target is simply passed as an argv element to the spawned editor process. If `repository.path/props.path` is a symlink whose target lies outside the repository (e.g. `../../.git/config` of a sibling repo, an absolute path to `~/.ssh/id_rsa`, etc.), the spawned editor will open/follow that symlink and display the external target's content.

This is notable because the same codebase already recognizes and mitigates this exact class of issue elsewhere: the Copilot conflict-resolution context builder explicitly guards against "path traversal and symlink escapes" using `resolveWithin`, which performs `realpath` on both the root and the resolved path and rejects anything that escapes the root: [4](#0-3) [5](#0-4) 

The "Open in editor" / "Open with default program" / "Reveal in File Manager" code paths in `unmerged-file.tsx` (and the analogous `copilot-conflicts-dialog.tsx` overflow menu) do not use `resolveWithin` or any equivalent check, and therefore lack the containment guarantee that the rest of the codebase treats as necessary for exactly this input (attacker-influenced conflicted file paths). [6](#0-5) 

## Impact Explanation
An attacker who controls a branch the user fetches/merges/rebases can introduce a conflicted path that resolves, on checkout, to a working-tree symlink pointing outside the repository. When the user opens the merge-conflicts dialog and clicks "Open in <editor>" for that file (a normal, expected step of conflict resolution), Desktop launches the user's configured editor against the resolved symlink target rather than a file confined to the repository. This satisfies the "file read... outside the repo" impact category: the editor is opened for and displays content that lives outside the intended repository scope (e.g., another repository's `.git/config`, credentials files, or other sensitive local files the OS user account can read). The same unguarded `join()` pattern also affects "Reveal in File Manager" and "Open with Default Program" for the conflict-dropdown menu.

## Likelihood Explanation
Exploitation requires: (1) the attacker crafts a branch/commit where the relevant path is (or becomes, via the merge machinery) an actual on-disk symlink targeting outside the repo, and (2) the user, in the normal course of resolving conflicts, clicks the "Open in editor" (or dropdown) button for that specific file. No unnatural steps are required beyond the ordinary use of the conflict-resolution UI, but it does depend on git/OS-specific behavior for how symlink conflicts are materialized on disk, which is not verified against real git merge output. This is a plausible but not fully proven precondition; confirming it requires an actual filesystem-level test with a crafted repository (as the question's proof idea suggests) rather than pure code inspection.

## Recommendation
Route the path used by `onOpenEditorClick`, `makeMarkerConflictDropdownClickHandler`, and the Copilot conflicts dialog's `onOverflowMenuClick` through `resolveWithin` (already used in `copilot-conflict-context.ts`) before passing it to `openFileInExternalEditor`, `openFile`, or `revealInFileManager`. If the resolved path is `null` (i.e., outside the repository root), refuse to open it and surface an error instead.

## Proof of Concept
Not independently executed against a live checkout; the analysis is based on static code tracing. A focused repository-level test would: (1) create a repo with a merge conflict where the conflicted file `path` is checked out as a real symlink pointing to a sibling path outside the repo root (e.g., `../outside/secret.txt`), (2) render `renderUnmergedFile`/invoke the dropdown's "Open with Default Program"/`onOpenEditorClick` handler, and (3) assert that `openFileInExternalEditor`/`openFile` is invoked with a path that `realpath`s outside `repository.path`, confirming no containment check occurs before the editor/file launch.

async function launchEditor(
  editorPath: string,
  args: readonly string[],
  editorName: string,
  spawnAsDarwinApp: boolean
) {
  const exists = await pathExists(editorPath)
  const label = __DARWIN__ ? 'Settings' : 'Options'
  if (!exists) {
    throw new ExternalEditorError(
      `Could not find executable for ${editorName} at path '${editorPath}'. Please open ${label} and select an available editor.`,
      { openPreferences: true }
    )
  }

  return new Promise<void>((resolve, reject) => {
    const opts: SpawnOptions = {
      // Make sure the editor processes are detached from the Desktop app.
      // Otherwise, some editors (like Notepad++) will be killed when the
      // Desktop app is closed.
      detached: true,
      stdio: 'ignore',
    }

    const child = spawnAsDarwinApp
      ? spawn('open', ['-a', editorPath, ...args], opts)
      : spawn(editorPath, args, opts)

    child.on('error', reject)
    child.on('spawn', resolve)
    child.unref() // Don't wait for editor to exit
```

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
