I found a persistence-based analog: `getEndpointVersion`/`updateEndpointVersion` in `endpoint-capabilities.ts` cache a host's "is this a GitHub Enterprise server" verdict in `localStorage` **forever**, with no timestamp, TTL, or re-validation, and `isGitHubHost` in `api.ts` treats any hit in that cache as sufficient proof the host is a trusted GitHub endpoint. This is the same broken-invariant class as the Switchboard bug: a value (price / "is-GitHub-host" verdict) derived from a remote response is trusted indefinitely with no recency check, and that stale trust decision then gates a security-relevant action (attaching a GitHub identity/credential-helper classification to the host).

### Title
Permanent, unbounded-lifetime caching of "is this a GitHub host" verdict allows credential-helper trust decisions to go stale - (File: app/src/lib/endpoint-capabilities.ts)

### Summary
`getEndpointVersion`/`updateEndpointVersion` cache the `x-github-enterprise-version` response header per endpoint in `localStorage` with no expiry, timestamp, or re-validation logic. `isGitHubHost` in `app/src/lib/api.ts` short-circuits to `true` if `getEndpointVersion(endpoint) !== null`, without re-checking the network. `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` relies on `isGitHubHost` to classify a credential request as `'enterprise'` (a GitHub host, whose credentials come from the signed-in account store) versus `'generic'` (any other host, which triggers the generic-git-auth password prompt/storage). A verdict recorded once — potentially from a single successful `/meta` probe — is trusted for the lifetime of the installation.

### Finding Description
`getEndpointVersion` (`app/src/lib/endpoint-capabilities.ts:70-86`) reads/writes a raw version string in `localStorage`; nothing in this path records *when* the value was captured, and there is no code path that invalidates or re-verifies it. `isGitHubHost` (`app/src/lib/api.ts:2435-2491`) treats a cache hit as conclusive: [1](#0-0) 
skipping the live `HEAD /meta` probe (which is otherwise the only integrity check — it inspects `x-github-request-id`) entirely for any endpoint that has ever been classified this way. `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:137-179`) uses this classification as the deciding factor for how Git-credential requests are handled — GitHub-classified endpoints route through the internal account store (`findGitHubTrampolineAccount`), while `'generic'` endpoints go through the separate generic-auth flow. There is no code analogous to the missing timestamp check the report calls out for Switchboard: the cache never expires and is never revalidated against the current state of the remote/proxy.

### Impact Explanation
If a host's classification is captured once while it legitimately answered as GHES/dotcom (e.g., a proxy or network path returned a plausible `x-github-enterprise-version` header, or the endpoint temporarily matched dotcom/GHE naming), that verdict is pinned in `localStorage` indefinitely, even if the remote or the machine's proxy configuration later changes (attacker-controlled remote takeover of a previously-legit hostname, DNS/proxy change, or a malicious proxy answering the initial `/meta` probe as described in the "attacker controls ... git remote/proxy response" allowed impact). Because the classification feeds directly into which credential path is used, a stale/poisoned verdict could cause Desktop to treat a now-different endpoint as a trusted GitHub host for credential-helper purposes rather than falling back to the safer generic flow.

### Likelihood Explanation
The likelihood is limited by the fact that establishing the initial poisoned entry still requires the attacker to control or influence the `/meta` response for that endpoint at least once (via a compromised remote/proxy answering the discovery probe), which is within the stated valid-impact scope but is not trivially exploitable by an unprivileged repository owner alone — it needs an on-path or server-side capability for the target endpoint. I could not verify from the index whether there is any additional mitigating check downstream (e.g., account-endpoint equality) that would prevent misuse of a poisoned `'enterprise'` classification when no matching signed-in account exists; the code in `getCredential` does check `accounts.some(a => a.endpoint === apiEndpoint)` before prompting sign-in, which limits (but does not eliminate) the practical blast radius.

### Recommendation
Store a timestamp alongside the cached version/verdict in `endpoint-capabilities.ts` and require `isGitHubHost`/`getEndpointVersion` to treat entries older than a defined TTL as absent, forcing re-validation via the live `/meta` probe. This mirrors the fix pattern in the reported bug: add an explicit recency check before trusting cached data used in a security-relevant decision, and fail closed (fall back to `'generic'`) when the cached verdict is stale.

### Proof of Concept
Not independently verifiable from the indexed code alone (requires live network/proxy control), but the trust path is directly reproducible by inspection:
1. `updateEndpointVersion(endpoint, version)` is called once (e.g. via `tryUpdateEndpointVersionFromResponse` in `api.ts`) and persists to `localStorage` with no timestamp: [2](#0-1) 
2. Any later call to `isGitHubHost(endpoint)` for that same endpoint returns `true` purely because the cache is non-null, regardless of how long ago it was set or whether the endpoint's ownership/routing has changed since: [1](#0-0) 
3. `getEndpointKind` uses that cached-forever verdict to route credential handling: [3](#0-2) 

I was not able to confirm within the indexed files whether this exact scenario has a compensating control elsewhere in the account-matching flow beyond the `accounts.some(...)` guard already cited, so the severity should be treated as moderate/uncertain pending a live-repro session.

export function updateEndpointVersion(endpoint: string, version: string) {
  const key = endpointVersionKey(endpoint)

  if (rawVersionCache.get(key) !== version) {
    const parsed = semver.parse(version)
    localStorage.setItem(key, version)
    rawVersionCache.set(key, version)
    versionCache.set(key, parsed)
  }
}
