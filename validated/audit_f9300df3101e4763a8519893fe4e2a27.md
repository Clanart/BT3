## Valid Analog Found

The reported bug class in `op-eco`'s `L2ECO.sol` `updateTokenRoleAdmin()` — a privileged admin address being reassigned in a single, unchecked transaction with no acceptance step — has a direct structural analog in the `x/tokenfactory` module's `MsgChangeAdmin` handler.

### Title
Tokenfactory `ChangeAdmin` is a single-step, unverified admin transfer that can permanently lock a denom's administrative capabilities - (File: `x/tokenfactory/keeper/msg_server.go`)

### Summary
The tokenfactory module lets any account become the "admin" of a denom simply by creating it, and that admin can reassign adminship to any other address via `MsgChangeAdmin`. The transfer is a single irreversible step: the new admin address is written directly into state with no acceptance/claim step from the new admin, and no validation beyond a generic bech32 address check.

### Finding Description
`msgServer.ChangeAdmin` verifies the caller is the current admin and that the new admin differs from the current one, then immediately commits the change via `setAdmin`: [1](#0-0) 

`setAdmin` unconditionally overwrites `AuthorityMetadata.Admin` in the same transaction with no pending/claim mechanism: [2](#0-1) 

`MsgChangeAdmin.ValidateBasic` only checks that `NewAdmin` parses as a valid bech32 address — it does not verify the address is controllable (e.g., has a known public key, is not a module account, etc.), and permits setting `NewAdmin` to any syntactically valid address in one shot: [3](#0-2) 

This mirrors exactly the audited pattern in `updateTokenRoleAdmin()`: a privileged, single-step admin reassignment reachable by an unprivileged transaction sender (here, the tokenfactory denom's own admin/creator, which is explicitly an in-scope actor), with no two-step accept/claim process and no protection against fat-fingering the destination address.

### Impact Explanation
If the current denom admin submits `MsgChangeAdmin` with an incorrect address (typo, wrong key, an address whose private key is not held, or a contract address that cannot originate transactions), all administrative capability over that denom — minting, burning, and any further `ChangeAdmin` calls — is **permanently and irrecoverably lost**. There is no way to "undo" the change since only the (now-unreachable) new admin can call `ChangeAdmin` again. This matches the "permanent freezing" impact criterion, since the denom's mint/burn/admin functionality freezes forever.

### Likelihood Explanation
Likelihood is non-trivial because `ChangeAdmin` is a normal, permissionless, frequently-used operation available to every tokenfactory denom admin (any account creating a denom becomes an admin, per `x/tokenfactory/README.md`), and the only validation performed is a syntactic bech32 check — not an ownership/liveness proof of the destination address. Unlike a governance-gated action, this requires no special privilege beyond already being a denom admin, which any user can obtain by creating their own denom, making the error surface broad across many independently-created denoms on chain.

### Recommendation
Convert `MsgChangeAdmin` into a two-step process:
1. Current admin calls `ChangeAdmin`/`ProposeAdmin` to set a `pendingAdmin` field in `DenomAuthorityMetadata` rather than overwriting `Admin` directly.
2. A new `MsgAcceptAdmin` (or similar) message, signed by the `pendingAdmin` address, finalizes the transfer by copying `pendingAdmin` into `Admin`.

This ensures an admin transfer only completes once the destination address demonstrably controls a private key capable of signing a transaction, eliminating the risk of irrecoverable loss of denom administration due to an incorrect address.

### Proof of Concept
1. Account `A` creates denom `factory/A/foo` via `MsgCreateDenom`, becoming its admin.
2. `A` calls `MsgChangeAdmin{Sender: A, Denom: "factory/A/foo", NewAdmin: B}` where `B` is a syntactically valid but uncontrolled bech32 address (e.g., a typo of the intended address, or an address for which no private key exists).
3. `ChangeAdmin` succeeds (passes `ValidateBasic` and the keeper's authorization/duplicate checks) and writes `B` as the new admin as shown in `x/tokenfactory/keeper/admins.go` lines 40-49.
4. No account can now call `Mint`, `Burn`, `SetDenomMetadata`, or `ChangeAdmin` for `factory/A/foo` ever again — administrative control of the denom is permanently frozen.

func (server msgServer) ChangeAdmin(goCtx context.Context, msg *types.MsgChangeAdmin) (*types.MsgChangeAdminResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	// Validate new admin we change to should be different from current admin
	if msg.NewAdmin == authorityMetadata.GetAdmin() {
		return nil, types.ErrAdminAlreadyExists
	}

	err = server.setAdmin(ctx, msg.Denom, msg.NewAdmin)
	if err != nil {
		return nil, err
	}
	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgChangeAdmin,
			sdk.NewAttribute(types.AttributeDenom, msg.GetDenom()),
			sdk.NewAttribute(types.AttributeNewAdmin, msg.NewAdmin),
		),
	})

	return &types.MsgChangeAdminResponse{}, nil
}

func (k Keeper) setAdmin(ctx sdk.Context, denom string, admin string) error {
	metadata, err := k.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return err
	}

	metadata.Admin = admin

	return k.setAuthorityMetadata(ctx, denom, metadata)
}

func (m MsgChangeAdmin) ValidateBasic() error {
	_, err := sdk.AccAddressFromBech32(m.Sender)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid sender address (%s)", err)
	}

	_, err = sdk.AccAddressFromBech32(m.NewAdmin)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid address (%s)", err)
	}

	_, _, err = DeconstructDenom(m.Denom)
	if err != nil {
		return err
	}

	return nil
}
