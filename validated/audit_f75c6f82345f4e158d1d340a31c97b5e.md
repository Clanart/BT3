### Title
Forfeiture check in `mWOMSVBaseRewarder._calExpireForfeit` is a tautology, so expired-reward forfeiture never triggers - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
The reported Cover Protocol bug is a self-referential/incorrect boundary check (`_newTimeWindow > 3 days` instead of `>= 3 days`) that silently fails to enforce the intended constraint. The same bug class — a check written against a value compared to itself, making the branch permanently dead — exists in `mWOMSVBaseRewarder._calExpireForfeit`, which is reachable by any ordinary staker through `getReward`/`getRewards`.

### Finding Description
`_calExpireForfeit` is meant to compute the portion of a user's accrued reward that should be forfeited (and redistributed to remaining stakers) versus the portion that is actually rewardable: [1](#0-0) 

```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
    return forfeitAmount;
}
```

`rewardableAmount` is assigned directly from `_amount`, so `rewardableAmount > _amount` can never be true, and `forfeitAmount = _amount - rewardableAmount` is always `0`. There is no time-based, account-based, or any other condition determining what should actually be forfeited — the guard is a dead/tautological check exactly analogous to `ClaimConfig`'s incorrect `timeWindow` comparison in the external report: a comparison that is structurally present in the code but can never fail (or in the analog, can never meaningfully evaluate), nullifying the intended business logic.

This function is invoked from `_sendReward`, which every unprivileged staker triggers when claiming rewards via `getReward`/`getRewards`: [2](#0-1) 

Because `forfeitAmount` is always `0`, the `_queueNewRewardsWithoutTransfer` redistribution path (meant to return forfeited/expired yield to the remaining pool of stakers) is never executed: [3](#0-2) 

### Impact Explanation
Any staker who claims rewards always receives 100% of their accrued `userRewards`, and the forfeiture/redistribution mechanism intended to route a portion of that yield back to other mWomSV stakers is permanently disabled. This permanently deprives the remaining staker pool of the forfeited-yield share they were designed to receive — a permanent misallocation/loss of unclaimed yield for other, unprivileged users, triggered purely by ordinary reward-claim transactions with no admin or governance involvement.

### Likelihood Explanation
High. This code path executes on every normal call to `getReward`/`getRewards` by any staker in the `mWomSV` reward pool — no special conditions, privileged roles, or unusual state are required to trigger it. It is the default behavior of the deployed contract, not an edge case.

### Recommendation
Replace the tautological check with the actual intended condition for forfeiture (e.g., based on lock/cool-down expiry, similar to the time-window based unlock calculations used elsewhere such as `VLMGP.expectedPenaltyAmount`), so `rewardableAmount`/`forfeitAmount` are derived from real time or eligibility data rather than being self-referential.

### Proof of Concept
1. Deploy `mWOMSVBaseRewarder`, register a reward token, and have `queueNewRewards` distribute rewards.
2. Any user calls `getReward`/`getRewards` through `MasterMagpie`.
3. Observe `_calExpireForfeit` always returns `0` regardless of account or timing, confirmed by inspecting `rewardableAmount = _amount` making `rewardableAmount > _amount` unsatisfiable.
4. `_sendReward` therefore always transfers the user's full `userRewards[...]` and never calls `_queueNewRewardsWithoutTransfer`, so no forfeited yield is ever redistributed to other stakers — verifiable purely by reading the contract logic (no external state manipulation required).

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
