### Title
Loose "is this a GitHub host" heuristic lets an attacker-controlled git remote trigger an Enterprise OAuth flow that leaks Desktop's OAuth client secret - (File: app/src/lib/api.ts)

### Summary
GitHub Desktop decides whether an unknown git remote host should be treated as a GitHub Enterprise (GHE) endpoint using a naive substring/regex heuristic rather than a canonical, verified identity check. An attacker who controls a git remote hostname (e.g. by creating a `github.` subdomain on a domain they own) can get this heuristic to misclassify their server as "GitHub Enterprise," causing Desktop to walk the user through its normal Enterprise sign-in flow against the attacker's host. That flow ends with Desktop POSTing the authorization code **and the app's shared OAuth `client_secret`** to the attacker-chosen origin.

### Finding Description
`isGitHubHost` classifies a URL as GitHub-owned using: [1](#0-0) 
`/(^|\.)(github)\./.test(hostname)` matches any hostname where "github" is a DNS label immediately followed by a dot — trivially satisfied by `github.attacker-domain.com` (attacker only needs to control any domain and add a `github` subdomain, no impersonation of the real `github.com` needed). This same class of loose matching (equating semantically different identifiers because a cheap syntactic check "looks" the same) is exactly the invariant broken in the NodeRegistry report, just applied to hostname trust instead of URL/deposit uniqueness.

This heuristic feeds `getEndpointKind` in the git-credential-helper trampoline: [2](#0-1) 
When Desktop needs credentials for a fetch/push/clone against an unrecognized host, and `isGitHubHost` (called at line 178) returns true, `getEndpointKind` returns `'enterprise'`. Back in `getCredential`, since no existing account matches that made-up API endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn` then unconditionally starts the Enterprise sign-in flow for any non-`github.com` hostname, with no verification that the host is actually a GHE server: [4](#0-3) 

`SignInStore.setEndpoint`/`authenticateWithBrowser` and `requestOAuthToken` then use the attacker-controlled `endpoint` directly as the OAuth authorize/token-exchange base URL, without ever confirming it is a legitimate previously-known GHE instance: [5](#0-4) [6](#0-5) 

The `client_id`/`client_secret` used here are Desktop's single, shared production OAuth credentials embedded in every install: [7](#0-6) 

Because `requestOAuthToken` builds its POST target from `getHTMLURL(endpoint)` where `endpoint` was derived from the attacker's hostname, the token-exchange request — including the app's real `client_secret` and the freshly-issued authorization `code` — is sent straight to the attacker's server.

### Impact Explanation
The value corrupted is the trust decision "this host is a legitimate GitHub Enterprise server," made via a cheap regex/substring test instead of any cryptographic or previously-established identity binding (an allow-list of known accounts, TLS-pinned identity, or a verified `/meta` roundtrip that isn't itself trivially spoofable by any HTTPS host). No existing guard stops the path: `isKnownThirdPartyHost` only blocks a hardcoded set of unrelated hosts, and there is no check that the "enterprise" endpoint was ever previously added by the user via Preferences. Exploitation exfiltrates the shared Desktop OAuth `client_secret` plus a live authorization `code`, letting the attacker complete the OAuth exchange themselves and potentially mint tokens or otherwise abuse Desktop's OAuth app identity.

### Likelihood Explanation
Attacker requirements match the "valid impact" bar exactly: they only need to control a git remote/repository the victim clones or fetches (e.g., a submodule or fork with a remote pointing at `https://github.<attacker-domain>/...`). No admin rights, no prior malware, no leaked credentials, and no unnatural steps — from the user's perspective this looks like Desktop's completely normal "sign in to continue" flow, which they routinely see for legitimate GHE remotes and would not obviously find suspicious since the hostname literally contains "github".

### Recommendation
Do not use substring/regex matching on hostnames to decide GitHub identity. Only treat an endpoint as "GitHub Enterprise" if it matches an account the user has explicitly added via the sign-in flow (with real verification, e.g. a successful, redirect-free `/meta` API response as already implemented later in `isGitHubHost`), and never auto-launch the Enterprise OAuth flow against an arbitrary, previously-unknown host purely because of a name heuristic. At minimum, `promptForGitHubSignIn`/`getEndpointKind` should require the discovery/verification step (the `/meta` check with `x-github-request-id`) to succeed before offering enterprise sign-in, rather than short-circuiting on the regex.

### Proof of Concept
1. Attacker registers any domain and creates a subdomain `github.<attacker-domain>`, serving a normal git-over-HTTPS repository that requires authentication (returns 401).
2. Attacker shares a repository (or a submodule/fork) whose remote is `https://github.<attacker-domain>/foo/bar.git`.
3. Victim clones/fetches it in GitHub Desktop. Git invokes Desktop's credential helper; `isGitHubHost` matches the regex and classifies the host as `enterprise`.
4. Desktop shows its standard "Sign in" popup (`promptForGitHubSignIn`), routing through `beginEnterpriseSignIn` → `setSignInEndpoint(origin)` with `origin = https://github.<attacker-domain>`.
5. Victim clicks "Continue with Browser"; `authenticateWithBrowser` opens `https://github.<attacker-domain>/login/oauth/authorize?client_id=<real client id>&...` — attacker's server, controlling the callback, captures the `code`.
6. Desktop's `resolveOAuthRequest` calls `requestOAuthToken(endpoint, code)`, which POSTs `client_id`, **`client_secret`**, and `code` to `https://github.<attacker-domain>/login/oauth/access_token` — fully exfiltrating Desktop's shared OAuth secret and the authorization code to the attacker.
