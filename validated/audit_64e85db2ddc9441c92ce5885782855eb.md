The `evm/tron/contracts/apps/IntentGatewayV2.sol` `placeOrder` predispatch branch is exactly analogous to the Gearbox bug: escrow accounting (`_orders[commitment][token] += reducedInputs[i].amount`) is accumulated inside the per-token loop, but the actual token movement (`ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`) happens only once, after the loop, for the entire batch. This differs from the main `evm/src/apps/IntentGatewayV2.sol`, which measures actual balances received after the sweep and only credits escrow with the measured amount — the Tron variant skips that "actual received" verification and instead credits the pre-computed `reducedInputs[i].amount` unconditionally before the sweep is executed and before the balance is confirmed.

### Title
Escrow credited with unconfirmed/unverified amount in Tron IntentGatewayV2 predispatch path, decoupled from actual tokens received - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the predispatch branch of `placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, escrow (`_orders[commitment][token]`) is incremented by the pre-computed `reducedInputs[i].amount` inside the per-token accounting loop (line 435), *before* the actual token-sweep transfer calls are executed against the `CallDispatcher` (line 443). This mirrors the Gearbox bug class: accounting values are accumulated ahead of, and independent from, the confirmation that the underlying transfer actually delivered the credited amount. [1](#0-0) 

### Finding Description
The Tron `IntentGatewayV2.placeOrder` predispatch flow:
1. Transfers predispatch assets to the `CallDispatcher` and executes the predispatch call.
2. Loops over `order.inputs`, checks `IERC20(token).balanceOf(dispatcher) >= requiredAmount`, builds a `transferCalls[i]` entry to sweep the dispatcher's *entire* balance back to the gateway, computes `dust = balance - requiredAmount`, and **credits escrow with `reducedInputs[i].amount` right there in the loop** — before any transfer has actually executed.
3. Only after the loop finishes does it call `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` to actually perform the sweep. [1](#0-0) 

Compare this to the primary EVM `IntentGatewayV2.sol`, which explicitly snapshots `balancesBefore[i]` before the sweep, executes the sweep, then computes `received = balanceOf(this) - balancesBefore[i]` and only escrows the amount **actually received**, emitting dust for any excess and mutating `order.inputs[i].amount` to the true received value: [2](#0-1) 

The Tron variant has no such "before/after" balance reconciliation for the escrow amount — it trusts `balanceOf(dispatcher)` read at loop time to still be accurate when the sweep executes later, and uses `reducedInputs[i].amount` (the fee-adjusted requested amount) directly as the escrow credit rather than a measured "actually swept" amount. For a fee-on-transfer, rebasing, or otherwise balance-mutating token used as a predispatch/input asset, or for any token whose `balanceOf(dispatcher)` can be reduced between the loop's read and the later `dispatch(transferCalls)` execution (e.g., a token with a callback/hook triggered by the earlier `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — which is fully attacker-controlled calldata operating with the dispatcher's assets), the escrow bookkeeping (`_orders[commitment][token]`) can end up crediting the order with more than the gateway actually receives on the final sweep transfer.

### Impact Explanation
If escrowed accounting (`_orders[commitment][token]`) exceeds the tokens actually swept into the gateway, later withdrawal/redemption paths (`withdraw`, `onGetResponse`-triggered refund) will pay out beneficiaries or refund users based on the inflated escrow ledger rather than the contract's real token balance — draining tokens belonging to other orders/users, i.e. fund loss for the protocol/other order owners. This falls under "stealing or loss of funds" per the bounty gate. [3](#0-2) 

### Likelihood Explanation
The attacker fully controls `order.predispatch.call`, which is dispatched to the `CallDispatcher` with the predispatch assets already sitting on it, before the balance is read for the sweep-calls construction. This gives an unprivileged, permissionless `placeOrder` caller a window to manipulate `dispatcher`'s ERC-20 balance (via a malicious/fee-on-transfer token contract, or a token with transfer hooks) between the balance check/escrow-credit and the actual sweep execution — all attacker-orchestrated in a single transaction, no privileged actor or relayer collusion required.

### Recommendation
Mirror the main `evm/src/apps/IntentGatewayV2.sol` pattern: snapshot dispatcher/gateway balances before constructing sweep calls, execute the sweep, then measure `received = balanceOf(this) - balanceBefore` and credit `_orders[commitment][token]` only with the actually-received (post-fee-reduction) amount — never with a value computed before the transfer executes.

### Proof of Concept
1. Deploy a malicious/fee-on-transfer ERC-20 token registered as both a `predispatch.assets` token and an `order.inputs` token.
2. Craft `order.predispatch.call` so that, when executed by `CallDispatcher`, the token's `balanceOf(dispatcher)` reflects a value that will still pass the `balance < requiredAmount` check at read time, but reduces further afterward, or use a token whose `transfer()` (invoked later in the batched `transferCalls`) delivers less than the balance read earlier.
3. Call `placeOrder` with such an order: the loop credits `_orders[commitment][token] += reducedInputs[i].amount` using the balance-at-read-time, but the subsequent `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` moves less than that amount into the gateway.
4. Later, initiate a fill/withdraw for that commitment — the withdrawal path pays out `_orders[commitment][token]`, exceeding what the gateway actually holds for that order, draining balance meant for other users' escrowed tokens. [4](#0-3)
