### Title
GitHub repository identity resolved by mutable owner/name strings instead of GitHub's immutable repository ID, enabling repo-squatting confusion - ([File: app/src/lib/repository-matching.ts])

### Summary
The Otter Audits finding is about `bluefin_vault` trusting a `BankV2` object solely by "it was passed in" rather than validating its unique identifier (UID) against the identifier the vault actually expects, allowing a different (attacker-controlled) `BankV2` instance to be silently substituted. The structural analog in GitHub Desktop is that a local `Repository`'s association to a GitHub-hosted repository is (re)established purely by matching mutable, attacker-influenceable strings — hostname + owner login + repository name — never by GitHub's immutable numeric repository id. `GitHubRepository.dbID` is explicitly documented as "no relation to the API ID" [1](#0-0) , and every comparison used to decide "is this the same GitHub repository" (`urlMatchesRemote`, `urlsMatch`, `matchGitHubRepository`) is a case-insensitive string comparison of hostname/owner/name [2](#0-1) [3](#0-2) [4](#0-3) .

### Finding Description
When Desktop refreshes a repository's association with a GitHub account (e.g. after a fetch/pull/push or on repository selection), `repositoryWithRefreshedGitHubRepository` calls `matchGitHubRepository`, which returns an `owner`/`name` pair derived purely from parsing the remote URL string and matching the URL's hostname to an account's endpoint hostname [5](#0-4) . That `owner`/`name` pair is then used to call the GitHub API (`api.fetchRepository(owner, name)`) and the resulting `apiRepo` is upserted and attached to the local `Repository` via `setGitHubRepository`/`upsertGitHubRepository` [6](#0-5) . At no point is a stable GitHub repository ID compared between the previously-cached `GitHubRepository` and the newly-fetched one — only the owner/name/hostname strings.

Separately, `updateRemoteUrl` will silently rewrite the user's local git `remote.origin.url` to whatever `apiRepo.clone_url` currently is, gated only on the *old* cached clone URL still textually matching the current remote and the URL protocol staying the same [7](#0-6) . This can happen automatically as part of routine `_push`/refresh flows via `withRefreshedGitHubRepository` [8](#0-7) , without any additional confirmation that the "same" owner/name repository the API returns is actually the object the user originally cloned.

Because GitHub allows repository renames, ownership transfers, and — critically — the freeing/reuse of a `owner/name` after a rename or account deletion, an attacker can register a repository under the exact same `owner/name` that a legitimate repository previously occupied. Since Desktop's identity check is textual (owner login + repo name + hostname) rather than based on GitHub's immutable numeric repository ID, Desktop's refresh/match logic has no way to detect that the "same-named" repository returned by the API is not the originally intended instance — this mirrors the audit's core defect: trusting an object by role/position instead of by verified unique identifier.

### Impact Explanation
If exploited, this could cause Desktop to: (1) silently rewrite a user's push remote (`updateRemoteUrl`) to the attacker's repository's `clone_url`, causing the user's next push to send code/history to an attacker-controlled repository; (2) reattach cached UI/permission state (branch protection, rulesets, "can push" assumptions) associated with the old `dbID` record to what is now a different underlying GitHub repository, potentially bypassing warnings that were previously valid for the legitimate repo. This falls into the "silent corruption of what the user commits/pushes" and unauthorized data flow categories called out as valid impact.

### Likelihood Explanation
This requires no local access, malware, or credential theft: it only requires (a) a repository being renamed/transferred/deleted on GitHub (a naturally occurring, common event) and (b) an attacker registering the freed `owner/name` combination — both are attacker-reachable, unprivileged actions. However, the practical exploitation window depends on timing (the rename/free event must occur while a Desktop user still has the old repo cloned and the app performs a refresh against the reused name), and it is unclear from the available code how frequently `repositoryWithRefreshedGitHubRepository` is invoked in practice or whether upstream GitHub API behavior (e.g., redirects for renamed repos, 404 on deleted ones) provides an additional layer of protection not visible in this client-side code — this could not be fully verified with the tools available.

### Recommendation
Store and compare GitHub's immutable numeric repository `id` (not just `dbID`, which is local-only, or owner/name strings) whenever validating that a previously-known `GitHubRepository` still refers to the same remote entity. `matchGitHubRepository`, `urlMatchesRemote`/`urlsMatch`, and `updateRemoteUrl` should require that the API-returned repository's immutable `id` matches the one already cached before reusing cached permissions/branch-protection state or silently rewriting the remote URL; if the ID differs (or is unknown, e.g. on first association), Desktop should treat it as a new repository association and require explicit user confirmation before altering the local remote configuration.

### Proof of Concept
1. User clones `https://github.com/owner/repo.git` with Desktop; Desktop stores a `GitHubRepository` row keyed by owner-login/name/hostname strings, with `cloneURL`/`htmlURL` and cached `permissions` [9](#0-8) .
2. The `owner` account is later renamed or the `repo` is deleted/transferred on GitHub, freeing the `owner/repo` name.
3. Attacker creates a new GitHub repository using the exact same freed `owner/repo` name.
4. On the victim's next fetch/pull/push, Desktop calls `matchGitHubRepository`/`repositoryWithRefreshedGitHubRepository`, which parses the still-configured local remote URL string, matches it to the account by hostname only, and calls `api.fetchRepository(owner, name)` — returning the attacker's new repository object, since only strings are compared, not any stable ID [5](#0-4) [6](#0-5) .
5. If protocol/URL heuristics line up, `updateRemoteUrl` may silently update `remote.origin.url` to the attacker repo's `clone_url` [7](#0-6) , and the victim's subsequent push sends commits to the attacker-controlled repository without any warning.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export function urlsMatch(url1: string, url2: string) {
  const firstIdentifier = parseRepositoryIdentifier(url1)
  const secondIdentifier = parseRepositoryIdentifier(url2)

  return (
    firstIdentifier !== null &&
    secondIdentifier !== null &&
    firstIdentifier.hostname === secondIdentifier.hostname &&
    firstIdentifier.owner === secondIdentifier.owner &&
    firstIdentifier.name === secondIdentifier.name
  )
}

  private async matchGitHubRepository(
    repository: Repository
  ): Promise<IMatchedGitHubRepository | null> {
    const gitStore = this.gitStoreCache.get(repository)

    if (!gitStore.defaultRemote) {
      await gitStore.loadRemotes()
    }

    const remote = gitStore.defaultRemote
    return remote !== null
      ? matchGitHubRepository(this.accounts, remote.url)
      : null
  }
