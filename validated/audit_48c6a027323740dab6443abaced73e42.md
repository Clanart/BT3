### Title
ReDoS in hookify's `_regex_match` via attacker-controlled `pattern` field in repo-tracked rule files causes PreToolUse hook to hang, risking fail-open bypass - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
Hookify loads regex `pattern` values directly from repo-tracked `.claude/hookify.*.local.md` files without any complexity/length validation, compiles them with `compile_regex`, and applies them via `re.search` in `_regex_match` against attacker-influenced fields (`command`, `new_text`, `content`). A committed rule with a catastrophic-backtracking pattern combined with a crafted `command`/file content can make `re.search` hang indefinitely inside the PreToolUse hook process, since there is no timeout, length cap, or safe-regex check anywhere in the pipeline.

### Finding Description
The flow is: `plugins/hookify/hooks/pretooluse.py` reads stdin JSON, calls `load_rules()` (from `plugins/hookify/core/config_loader.py`) which globs `.claude/hookify.*.local.md` files in the repo and parses YAML frontmatter with a hand-rolled parser (`extract_frontmatter`), producing `Condition.pattern` / `Rule.pattern` strings taken verbatim from the file [1](#0-0) . These rules are then evaluated by `RuleEngine.evaluate_rules` → `_rule_matches` → `_check_condition`, which for `operator == 'regex_match'` calls `self._regex_match(pattern, field_value)` [2](#0-1) . `_regex_match` compiles the pattern via the `lru_cache`-wrapped `compile_regex` (plain `re.compile(pattern, re.IGNORECASE)`, no safety checks) and calls `regex.search(text)` with no timeout, length limit, or backtracking guard [3](#0-2) [4](#0-3) . `field_value` (e.g. `command` for Bash, `new_text`/`content` for Edit/Write) is derived directly from the tool call parameters that Claude (or the user) is about to execute, so it is attacker-influenceable at hook-evaluation time [5](#0-4) . There is no per-pattern static analysis (e.g. rejecting nested quantifiers), no `signal`/`multiprocessing`-based timeout, and no regex engine substitute (e.g. `regex` module with timeout, or RE2) anywhere in `rule_engine.py`. `pretooluse.py` only catches generic `Exception` around the whole `main()` body and always calls `sys.exit(0)` in a `finally` block, but this only helps if the call *returns* — a hanging `re.search` call never returns, so the `try/except/finally` cannot save the process from hanging [6](#0-5) .

### Impact Explanation
If an attacker (e.g. via a pull request or committed file in a repo that a victim later checks out and runs Claude Code against) plants a `.claude/hookify.<name>.local.md` rule file with a catastrophic-backtracking `pattern` (e.g. `(a+)+$`-style pattern matched against `command` or `new_text`), then any subsequent Bash/Edit/Write tool call whose corresponding field can be steered to contain a crafted "poison" string (which is often within the attacker's control, e.g. as part of file content being edited, or partially controllable via a crafted PR description that Claude might echo into a command) will cause `_regex_match` to hang. Since hookify is the mechanism enforcing `block`-action rules (including security-relevant ones like the `sensitive-files`/`api-key-in-typescript` examples that block hardcoded credentials from being written), an indefinite hang in the PreToolUse evaluation causes the hook process to never emit a decision. Depending on how Claude Code's outer hook-timeout/error-handling treats a non-responding hook process, this can result in the blocking rule failing to be enforced (fail-open), allowing an unreviewed/dangerous operation (including one that could leak secrets or run a destructive command) to proceed without the intended block.

### Likelihood Explanation
Preconditions: (1) the victim's repo/workspace must contain a hookify rule file with attacker-supplied `pattern` (achievable via a committed file in a repo, or a rule added through a PR that is later merged/checked out without the victim inspecting the regex for ReDoS), and (2) a subsequent tool call must supply/trigger text against which the vulnerable field is matched. Both conditions are realistic under the stated threat model of "ordinary repository content" since hookify explicitly documents and encourages arbitrary user-supplied regex `pattern` fields in `.claude/hookify.*.local.md` for legitimate use (see `plugins/hookify/README.md` and `plugins/hookify/skills/writing-rules/SKILL.md`), and there is no review/sanitization step for these patterns before they are compiled and executed. The bug is fully deterministic and reproducible with any known ReDoS pattern (e.g. `^(a+)+$`, `(a|aa)+$`) matched against a crafted long input.

### Recommendation
- Add a hard timeout around regex evaluation in `_regex_match` (e.g. via a worker process/thread with `concurrent.futures` and a bounded `timeout=`, or the `regex` module's `timeout` parameter) and fail closed-safely (treat as non-match, log a warning) if exceeded.
- Alternatively/additionally, validate patterns at load time in `config_loader.py`/`Rule.from_dict` using a static ReDoS heuristic (reject nested unbounded quantifiers) or compile with a linear-time engine (e.g. Google's `re2` bindings) instead of Python's backtracking `re`.
- Cap the length of `field_value` passed into `_regex_match` (e.g. truncate `command`/`new_text`/`content` to a reasonable size) to bound worst-case backtracking cost.
- Ensure `pretooluse.py`/`posttooluse.py`/`stop.py`/`userpromptsubmit.py` hook executors themselves enforce a wall-clock timeout on the whole `evaluate_rules` call so a stuck regex cannot hang the hook process indefinitely.

### Proof of Concept
Add a unit/perf test in the hookify test suite:
```python
import time
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

def test_regex_match_redos_bounded():
    # Catastrophic backtracking pattern, as could be committed in
    # .claude/hookify.evil.local.md's `pattern` field
    evil_pattern = r"^(a+)+$"
    poison_command = "a" * 40 + "!"  # fails to match, forces backtracking

    rule = Rule(
        name="evil-rule", enabled=True, event="bash",
        conditions=[Condition(field="command", operator="regex_match", pattern=evil_pattern)],
        message="triggered"
    )
    engine = RuleEngine()
    input_data = {"tool_name": "Bash", "tool_input": {"command": poison_command}}

    start = time.monotonic()
    engine.evaluate_rules([rule], input_data)
    elapsed = time.monotonic() - start

    # Expect a bounded timeout/guard; currently this assertion fails
    # because re.search hangs for exponential time as len(poison_command) grows.
    assert elapsed < 1.0, f"_regex_match took {elapsed:.2f}s - no ReDoS guard present"
```
Run with increasing lengths of `poison_command` (e.g. 30, 40, 50 `a`s) to demonstrate exponential growth in `_regex_match`/`compile_regex` → `re.search` latency, confirming absence of any bounded timeout/guard in `plugins/hookify/core/rule_engine.py`.

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
