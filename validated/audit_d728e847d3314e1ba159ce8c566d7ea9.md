## Analysis

**Binding claimed:** `operator_xonly_pk` recorded as payer for withdrawal `i` (`withdrawals.payout_payer_operator_xonly_pk`) `==` the operator whose own funds actually paid for/broadcast payout `i`.

**Trace:** The withdrawal UTXO created by the payout transaction (`create_payout_txhandler`) is a plain Taproot key-spend output owned by the **withdrawing user**, not by any operator. Its only Bitcoin-consensus-enforced spending condition is a valid Schnorr signature from the user's own key [1](#0-0) . Nothing in the script or transaction structure binds any specific operator's key to this input — the OP_RETURN output carrying `operator_xonly_pk` is pure unauthenticated data with no signature requirement over it by design (it exists purely so operators can flexibly front payouts with their own extra funding inputs) [2](#0-1) .

When a verifier ingests a confirmed payout, it blindly trusts this OP_RETURN content: [3](#0-2) 

That value is persisted as `payout_payer_operator_xonly_pk` [4](#0-3) , with **no verification that any of the transaction's inputs are owned by, signed by, or otherwise attributable to that operator**.

Downstream, an operator's own node trusts this DB column completely to decide whether it should claim reimbursement: [5](#0-4) 

And the verifier-side "is this kickoff legitimate" check only cross-references the OP_RETURN value against the kickoff sender's declared key plus a committed block hash — it never checks that the claimed operator actually funded the payout inputs: [6](#0-5) 

Since the withdrawing user is the attacker (per the threat model — they call `withdraw` on Citrea and control the withdrawal outpoint/signature), the attacker can fully construct and broadcast the payout transaction themselves outside of any operator or aggregator RPC, fronting any shortfall with their own BTC, sending the correct output to the correct destination/amount (satisfying Citrea's SPV check later), and stamping an arbitrary victim operator's x-only pubkey into the OP_RETURN. No operator signature, RPC call, or private key is ever required for this — the whole flow is a raw Bitcoin transaction the attacker signs and broadcasts with their own key.

Once mined, `update_finalized_payouts` credits the forged operator as payer, that operator's automation (`validate_payer_is_operator`) will consider itself the legitimate payer and proceed to kick off / claim reimbursement of the full deposit amount from `create_reimburse_txhandler`'s move-to-vault output, even though it contributed nothing.

### Title
Unauthenticated OP_RETURN operator attribution in payout transactions allows crediting/reimbursing an operator that never funded the payout - (File: core/src/verifier.rs)

### Summary
`update_finalized_payouts` trusts the OP_RETURN output of a mined payout transaction as authoritative proof of which operator funded the payout, but the OP_RETURN output and the payout transaction's funding inputs are not cryptographically bound together or to any operator key. Any party that controls the withdrawal UTXO's user signature (including the withdrawing user/attacker themselves) can construct and broadcast a payout transaction that pays the correct destination/amount while stamping an arbitrary victim operator's x-only pubkey into the OP_RETURN, with zero operator involvement.

### Finding Description
The broken binding: `payout_payer_operator_xonly_pk stored for withdrawal i == the operator whose funds paid payout i`. Before: true only if the honest flow (`Operator::withdraw`, which funds and signs via the node's own wallet) is followed. After the attack: the DB column contains an attacker-chosen operator pubkey with no relationship to who actually funded the transaction, yet nothing detects the mismatch.

Root cause: `create_payout_txhandler` makes the withdrawal UTXO spendable via a plain key-spend by the withdrawing user's own key [1](#0-0) ; the OP_RETURN output carrying the operator's pubkey has no signature-based binding to any operator identity at the Bitcoin script level. `Verifier::update_finalized_payouts` parses this OP_RETURN and stores it as ground truth [3](#0-2) . `Operator::validate_payer_is_operator` and `Verifier::is_kickoff_malicious` only compare this stored value against the kickoff sender's own key and a committed block hash — neither validates that the claimed operator's wallet actually contributed funds to the payout transaction's inputs [7](#0-6) [8](#0-7) .

Exploit flow: attacker calls `withdraw` on the Citrea bridge contract for their own withdrawal, obtaining/creating the withdrawal UTXO and its user signature; attacker then builds the Bitcoin payout transaction directly (bypassing any operator's `withdraw` RPC and `fund_raw_transaction`/`sign_raw_transaction_with_wallet` path entirely), funding any shortfall with their own BTC, and inserts victim Operator B's x-only pubkey into the OP_RETURN output before broadcasting. No signature from Operator B, nor any other operator, is required anywhere in this transaction.

### Impact Explanation
Once the forged payout is finalized, Operator B's node (falsely believing it is the payer per `validate_payer_is_operator`) proceeds to kick off and eventually calls `create_reimburse_txhandler`, receiving the full deposit value from the `MoveToVault` UTXO [9](#0-8)  — reimbursement for a payout it never funded. This matches the Critical category "an operator reimbursed for a payout it never funded." It is repeatable per withdrawal/deposit and can target any registered operator, since every operator has a presigned kickoff/reimburse graph per deposit.

### Likelihood Explanation
The attacker only needs to be the withdrawing user (a Citrea account) and be able to construct/sign/broadcast a standard Bitcoin transaction — capabilities explicitly granted to the unprivileged attacker in this threat model. The attacker must front the shortfall in BTC themselves (their own capital, not stolen funds) to get their withdrawal paid, but the reward is that an arbitrary, uninvolved operator is credited with reimbursement for the full deposit amount. This requires no operator, verifier, or aggregator compromise, and no majority hashrate.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically to the operator's actual participation, e.g., by requiring the operator's key to sign over the OP_RETURN output (and the whole transaction) using a fixed sighash type that a verifier can check was produced by that operator's registered key, or by requiring verifiers/`is_kickoff_malicious` to independently confirm that a UTXO known to belong to the claimed operator was consumed as an input of the payout transaction (e.g., cross-reference operator collateral/registered funding addresses) rather than trusting unauthenticated OP_RETURN bytes.

/// Creates a [`TxHandler`] for the `payout_tx`.
///
/// This transaction is sent by the operator to front a peg-out, after which operator will send a kickoff transaction to get reimbursed.
///
/// # Inputs
/// 1. UTXO: User's withdrawal input (committed in Citrea side, with the signature given to operators off-chain)
///
/// # Outputs
/// 1. User payout output
/// 2. OP_RETURN output (with operators x-only pubkey that fronts the peg-out)
///
/// # Arguments
/// * `input_utxo` - The input UTXO for the payout, committed in Citrea side, with the signature given to operators off-chain.
/// * `output_txout` - The output TxOut for the user payout.
/// * `operator_xonly_pk` - The operator's x-only public key that fronts the peg-out.
/// * `user_sig` - The user's signature for the payout, given to operators off-chain.
/// * `network` - The Bitcoin network.
///
/// # Returns
/// A [`TxHandler`] for the payout transaction, or a [`BridgeError`] if construction fails.
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

                Ok((
