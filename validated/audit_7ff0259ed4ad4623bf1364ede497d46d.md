### Title
Reward forfeiture is never applied in `mWOMSVBaseRewarder`, permanently diverting yield away from long-term mWomSV lockers - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit()` is supposed to compute the portion of a claiming user's accrued reward that should be forfeited (because the user is unlocking/cooling down rather than remaining fully locked) and redistribute that forfeited amount back into the reward pool for remaining, fully-locked stakers. In this contract the forfeit calculation is stubbed out so that it always returns zero, meaning users always receive 100% of accrued rewards regardless of lock status, and the forfeiture redistribution to loyal stakers never happens.

### Finding Description
`mWOMSVBaseRewarder._sendReward()` computes `forfeitAmount` via `_calExpireForfeit(_account, userRewards[_rewardToken][_account])` and sends `userRewards - forfeitAmount` to the user, while any `forfeitAmount` is supposed to be re-queued into the pool for other stakers via `_queueNewRewardsWithoutTransfer` [1](#0-0) .

However, `_calExpireForfeit` in this contract sets `rewardableAmount = _amount` unconditionally, which makes `forfeitAmount = _amount - rewardableAmount` always equal `0`: [2](#0-1) 

This is in stark contrast to the sibling contract `vlMGPBaseRewarder`, which correctly computes `rewardableAmount` from the user's actual lock-weighted share via `vlMGP.getRewardablePercentWAD(_account)`, so that users who are unlocking/cooling down genuinely forfeit part of their reward: [3](#0-2) 

The companion locker contract `mWomSV.sol` does implement an equivalent `getRewardablePercentWAD()` function that computes the correct lock-weighted rewardable percent (fully-locked amount plus a decayed portion for cooling-down amounts): [4](#0-3)  But `mWOMSVBaseRewarder` never calls it, so the mechanism designed to penalize users who begin unlocking (and to redistribute that penalty to users who remain fully locked) is completely inert for the mWomSV/mWOM reward pool.

### Impact Explanation
This is directly analogous to the referenced report's root cause: a value (interest/fee in the original report, forfeited yield here) that is correctly calculated and accrued in one code path (`vlMGPBaseRewarder`, and the `interestAccrued`/treasury split in the original bug) but is silently dropped/bypassed in a sibling code path (`mWOMSVBaseRewarder`) that should apply the same accounting rule. Any unprivileged wallet holding mWomSV can start an unlock (`startUnlock`) and then claim full, un-forfeited rewards through `MasterMagpie`/`mWOMSVBaseRewarder.getReward`/`getRewards`, capturing yield that the reward-forfeiture design intended to redistribute to users who keep their tokens fully locked. This is a permanent loss of unclaimed yield for loyal, fully-locked mWomSV stakers, since the forfeiture that should flow into `rewardPerTokenStored` for their benefit never occurs.

### Likelihood Explanation
High likelihood: no privileged role is required. Any holder of mWomSV can call `startUnlock()` (an ordinary user action) and subsequently call `getReward`/`getRewards` through `MasterMagpie` while still holding a claim on rewards, and will always receive the full, non-forfeited reward amount because `_calExpireForfeit` is a no-op in this contract for every account and every reward token.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit()` to mirror `vlMGPBaseRewarder`'s implementation by querying the actual rewardable percentage from the locker, e.g.:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
}
```

### Proof of Concept
1. A user locks mWOM into `mWomSV` and accrues reward via `mWOMSVBaseRewarder` (rewards accrue proportional to `balanceOf`, which includes cooling-down amounts) [5](#0-4) .
2. The user calls `startUnlock()` to begin cooling down their entire balance, which under the intended design (per `getRewardablePercentWAD`) should reduce their rewardable share over the cool-down period [6](#0-5) .
3. The user then claims rewards via `MasterMagpie` → `mWOMSVBaseRewarder.getReward`/`getRewards`, which calls `_sendReward` → `_calExpireForfeit` [7](#0-6) .
4. Because `_calExpireForfeit` always returns `0`, the user receives 100% of `userRewards[_rewardToken][_account]` even though they are mid-unlock, and no forfeited amount is ever queued back for fully-locked stakers via `_queueNewRewardsWithoutTransfer`.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
