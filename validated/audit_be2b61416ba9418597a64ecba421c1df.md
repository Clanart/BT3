### Title
Deserialization of attacker-supplied `ThresholdKeys` accepts inconsistent share material, yielding attacker-controlled threshold keys - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation method (including `n` arbitrary `Interpolation::Constant` scalars), the `secret_share`, and all `n` `verification_shares` from untrusted bytes, then passes them to `ThresholdKeys::new`, which only validates counts and participant index bounds. It never checks that `generator() * secret_share == verification_shares[i]` (nor that the shares are internally consistent with the claimed parameters). A crafted byte blob therefore materializes as a fully valid `ThresholdKeys` whose group key and secret share are entirely attacker-chosen. [1](#0-0) 

### Finding Description
The deserialization is structurally canonical (scalars via `read_F` reject non-canonical encodings, points via `read_G` reject non-canonical/non-prime-order points, `Participant::new` rejects index 0, `ThresholdParams::new` validates `t <= n` and `i <= n`), but performs no *semantic* validation:

- `Interpolation::Constant` reads `n` scalars directly from the input; these scalars are later used verbatim as interpolation factors when computing `group_key` in `ThresholdKeys::new` (`t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum()`). [2](#0-1) 
- `ThresholdKeys::new` checks only `verification_shares.len() == n` and that no participant index exceeds `n`. It never binds `secret_share` to `verification_shares[i]`, and never binds the claimed `group_key` to any externally expected value. [3](#0-2) 

Consequently, an attacker who can supply the bytes fed to `ThresholdKeys::read` (key import/restore/migration path, or any RPC/peer-delivered blob) can fabricate keys where:

1. `verification_shares` are `G * a_j` for attacker-known `a_j`, making `group_key` a key whose discrete log the attacker knows;
2. `secret_share` is whatever the attacker wants the victim to believe it holds.

Downstream, `Scanner::new(group_key)` / `register_offset` (`networks/bitcoin/src/wallet/mod.rs`) causes the system to treat deposits to this attacker-known key as treasury funds, and FROST `sign`/`complete` will operate under the attacker's parameters. Notably, `AlgorithmSignatureMachine::complete` even contains an explicit acknowledgement of this failure mode: "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys". [4](#0-3) 

This is the direct analog of the Laravel `__destruct` deserialization flaw: a deserialization routine reconstructs a security-critical object from untrusted bytes without enforcing the invariants the rest of the system assumes, letting the attacker's input drive security-sensitive behavior (which key controls the funds / which share signs).

### Impact Explanation
If any in-scope consumer accepts remotely supplied serialized `ThresholdKeys` (key recovery, share import, coordinated re-keying), the attacker obtains a group key whose discrete log they know. All outputs scanned to that key via `Scanner`/`register_offset` are spendable by the attacker unilaterally — funds reported as received by the threshold are not actually controlled by the threshold. Alternatively, with `secret_share` inconsistent with `verification_shares[i]`, every FROST signing session the victim joins produces invalid shares/signatures (availability loss) or, in adversarial combinations, lets the attacker dictate `group_key` independently of the victim's real share via crafted `Constant` interpolation factors.

### Likelihood Explanation
Exploitation requires the attacker to supply the serialized key blob to a deserialization sink, which the audit rules explicitly classify as reachable (`ThresholdKeys::read` on untrusted bytes). The primitives themselves correctly reject malformed encodings, so no canonicalization trick is needed — the flaw is purely the missing consistency check, which is trivially constructible: pick a scalar `a`, emit `verification_shares[j] = G * a_j` for known `a_j`, pick a Constant interpolation so the interpolated combination of the first `t` shares yields a chosen group key, emit any `secret_share`. No cryptographic hardness is involved.

### Recommendation
In `ThresholdKeys::new` (which `read` delegates to), add `debug_assert`-style hard validation that `C::generator() * secret_share == verification_shares[&params.i()]`, returning a `DkgError` on mismatch. Additionally, for `Interpolation::Constant`, document or enforce that the supplied factors correspond to a known derivation (e.g., recompute MuSig binding factors from context when applicable), rather than trusting wire-supplied scalars.

### Proof of Concept
```rust
// Attacker constructs a blob for ThresholdKeys::<Secp256k1>::read:
//   id_len || ID || t=1 || n=1 || i=1 || interpolation=0 (Constant)
//   || n=1 scalar: factor = 1 || secret_share = a (attacker-known)
//   || verification_shares[1] = G * a
// Result: ThresholdKeys whose group_key = G*a — fully attacker-controlled,
// accepted with Ok(..) since all bound checks pass.
// Feeding group_key() into Scanner::new / tweak_keys registers attacker-
// spendable P2TR outputs as treasury-received funds.
```

All structural validation in `read`/`ThresholdKeys::new` passes; the resulting object is semantically fraudulent yet indistinguishable to callers.

  pub fn read<R: io::Read>(reader: &mut R) -> io::Result<ThresholdKeys<C>> {
    {
      let different = || io::Error::other("deserializing ThresholdKeys for another curve");

      let mut id_len = [0; 4];
      reader.read_exact(&mut id_len)?;
      if u32::try_from(C::ID.len()).unwrap().to_le_bytes() != id_len {
        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res
      }),
      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

    let secret_share = Zeroizing::new(C::read_F(reader)?);

    let mut verification_shares = HashMap::new();
    for l in (1 ..= n).map(Participant) {
      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )
    .map_err(io::Error::other)
  }
