### Title
Recursive precompile calls share a single `BalanceHandler` instance, causing `prevEventsLen` to be overwritten and producing StateDB/bank balance desync - ([File: precompiles/common/balance_handler.go])

### Summary
The stNXM bug is a class of "stateful snapshot invariant broken by reentrant/nested calls that share mutable snapshot state." The `BalanceHandler` in this repository implements the exact same pattern that Cosmos EVM precompiles use to reconcile native bank-module balance changes into the EVM `StateDB`: it records `prevEventsLen` in `BeforeBalanceChange`, then in `AfterBalanceChange` replays only the bank events emitted *after* that recorded index to apply `AddBalance`/`SubBalance` on the `StateDB`. This is structurally identical to `stNXM`'s `lastBalance`/`lastStaked` snapshot-then-diff pattern in the `update` modifier that the auditors found exploitable when a nested/out-of-order call re-executed the modifier during an unexpected phase (pause boundary).

The repository itself contains a dedicated regression test, `evmd/tests/integration/balance_handler/balance_handler_test.go`, explicitly documented as reproducing "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB" [1](#0-0) .

### Finding Description
`BalanceHandler.BeforeBalanceChange` snapshots the current event count on the context's `EventManager`: [2](#0-1) 

`AfterBalanceChange` then slices `events[bh.prevEventsLen:]` to determine which bank events belong to this call and mutates the EVM `StateDB` balances accordingly (`AddBalance`/`SubBalance`) based on `CoinSpent`/`CoinReceived`/precisebank fractional events: [3](#0-2) 

If a precompile call recursively invokes another precompile (e.g. via a caller contract that calls into the debug/erc20/staking/distribution precompiles reentrantly), and both invocations end up using the same `BalanceHandler` instance (as opposed to a fresh instance per call as intended by `BalanceHandlerFactory.NewBalanceHandler()` in the normal `runNativeAction` path [4](#0-3) ), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` to a later index. When the inner call finishes and the outer call's `AfterBalanceChange` executes, it now slices from the wrong (advanced) `prevEventsLen`, silently dropping the accounting for bank events that occurred between the outer call's start and the inner call's start. This causes the EVM `StateDB` balance to diverge from the actual bank-module balance — exactly analogous to `stNXM`'s `lastBalance` being read/written at the wrong point in a call sequence and corrupting the fee/balance accrual.

### Impact Explanation
If native bank balance changes are dropped from `StateDB` reconciliation, an attacker can construct a contract that triggers nested precompile calls (the repo's own test uses a `callback` contract driving 10 nested debug-precompile calls) such that certain `CoinSpent`/`CoinReceived` events are "lost" from the EVM's view. Depending on which side under/over-counts, this can let a user's `StateDB` balance diverge upward from their true bank balance (spendable-value duplication) or the reverse — permanent balance corruption which is unauthorized value creation/loss and irreversible accounting corruption across native/EVM balance representations, matching the "Critical unauthorized minting/duplication or irreversible accounting corruption of spendable user value across native/EVM balances" impact gate.

### Likelihood Explanation
The repository already has a test suite (`BalanceHandlerTestSuite`) purpose-built to reproduce this exact bug via an ordinary, unprivileged EVM contract call (`callback(0)`) that triggers recursive precompile invocations [5](#0-4) . This indicates the underlying condition is reachable through normal, unprivileged transaction flow (any user deploying/calling a contract that makes nested precompile calls), not through a privileged or malicious-validator path.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)

			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
