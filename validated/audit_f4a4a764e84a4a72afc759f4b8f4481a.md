### Title
Payout OP_RETURN operator attribution is unsigned, letting an unprivileged withdrawal-fronter misattribute reimbursement credit to an arbitrary xonly public key - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The `payout_tx` that fronts a Citrea withdrawal commits, via the user's `SinglePlusAnyoneCanPay` signature, only to the withdrawal input and the user's payout output. The `OP_RETURN` output that records which operator "fronted" the withdrawal (and is later used as the sole binding between "who actually paid the user" and "who gets reimbursed") is **not covered by that signature**, so whoever assembles/broadcasts the final `payout_tx` can put any x-only public key into it.

### Finding Description
`create_payout_txhandler` builds the payout transaction with:
- input 0: the withdrawal UTXO, spent with `SpendPath::KeySpend` using the user's `taproot::Signature` (`SinglePlusAnyoneCanPay` sighash type, per the proto doc comment) [1](#0-0) 
- output 0: the user's payout (amount/script pubkey fixed by the signature)
- output 1: anchor
- output 2: `op_return_txout(operator_xonly_pk.serialize())` — the credited operator's key [2](#0-1) 

Because `SIGHASH_SINGLE | ANYONECANPAY` only commits the signature to input index 0 and the *matching* output index 0, outputs 1 and 2 (anchor and OP_RETURN) are **not signature-committed**. Any party who can broadcast a valid payout tx for that UTXO (i.e. holds/observes the withdrawal input and the corresponding `user_sig`) can freely choose the bytes placed in the OP_RETURN, independent of which key's Bitcoin actually funds/pays the withdrawal output.

This OP_RETURN value is later trusted as ground truth for attribution: `update_finalized_payouts` extracts `operator_xonly_pk` straight from the OP_RETURN of the on-chain payout tx and stores it as `payout_payer_operator_xonly_pk` in the `withdrawals` table [3](#0-2) . That value then:
- gates which operator is authorized to submit a kickoff / claim reimbursement (`is_kickoff_malicious` flags kickoffs from operators whose xonly_pk doesn't match the OP_RETURN value) [4](#0-3) 
- gates `send_asserts`, which errors if `payout_op_xonly_pk != kickoff_data.operator_xonly_pk` [5](#0-4) 
- is used by `PayoutCheckerTask`/`validate_payer_is_operator` to decide which own-operator's flow should process the payout and start the round advancement/reimbursement pipeline [6](#0-5) 

Because the binding "OP_RETURN operator pk == entity that actually fronted BTC to the user" is never cryptographically enforced (no signature covers it, and nothing checks that the credited key's own funds paid the fee/CPFP for the payout), the equality the protocol relies on — *fronting party == credited operator* — can be broken by whoever finalizes the transaction.

### Impact Explanation
This breaks the "operator credited versus the party that paid" binding. Concretely, whoever assembles/broadcasts the final payout transaction chooses which xonly public key is recorded as having fronted the withdrawal, regardless of whose Bitcoin actually reached the user. Consequences:
- A withdrawal can be permanently mis-credited to an operator's xonly pk that never fronted anything, poisoning `withdrawals.payout_payer_operator_xonly_pk` and blocking the legitimate reimbursement path: `is_kickoff_malicious` will treat kickoffs from the true operator as malicious (mismatch), and `send_asserts`/`validate_payer_is_operator` will reject or misdirect the reimbursement flow, potentially leaving an honest operator unable to be reimbursed for BTC it actually fronted.
- Because the OP_RETURN is not signed and only the user's own output is committed, this is not merely an operator-vs-operator dispute inside the trusted role set; it is a property of the transaction format itself — any entity capable of constructing/relaying the final payout tx (which is a normal Bitcoin broadcast, not a privileged RPC call) can set this field arbitrarily.

### Likelihood Explanation
The withdrawal `user_sig` with `SinglePlusAnyoneCanPay` is explicitly designed to be shareable/usable by whichever operator fronts first (that is the whole point of ANYONECANPAY here), so by design multiple parties may hold a valid signature for the same UTXO. The vulnerable gap is that the OP_RETURN attribution piggybacks on this same signature without being covered by it, so the same "race to front" mechanic that is intentional for the input/output pair extends unintentionally to the attribution field, which was assumed to reliably identify the funder.

### Recommendation
Bind the OP_RETURN operator attribution to the transaction's economic effect rather than trusting an unsigned data push:
- Change the sighash type used for the payout input (or add a second commitment) so that the OP_RETURN output is covered by a signature tied to the actual funding operator (e.g., require the operator to also sign an output containing their own pubkey, or use `SIGHASH_ALL`/`SIGHASH_ANYONECANPAY_ALL` variants that commit to all outputs).
- Alternatively/additionally, verify at the protocol layer that the address/fee-payer of the CPFP anchor or the txin(s) funding replacement/RBF match the xonly pk recorded in the OP_RETURN before trusting `payout_payer_operator_xonly_pk` for reimbursement decisions in `update_finalized_payouts`, `is_kickoff_malicious`, and `send_asserts`.

### Proof of Concept
Conceptual (not a full runnable exploit given index limitations, but derivable from the cited code paths):
1. Obtain the withdrawal's `input_outpoint`, `output_script_pubkey`/`output_amount`, and the user's `SinglePlusAnyoneCanPay` `taproot::Signature` (shared to fronting parties per protocol design, see the proto message `WithdrawParams`) [1](#0-0) .
2. Construct a payout transaction identical to what `create_payout_txhandler` would produce for output 0 (so the user signature remains valid), but substitute an arbitrary x-only public key (e.g., a legitimate but uninvolved operator's key, or a non-operator key) into output 2's OP_RETURN, instead of the fronting operator's own key [7](#0-6) .
3. Broadcast it — the signature check only validates input/output index 0 under `SinglePlusAnyoneCanPay`, so the transaction is valid on-chain regardless of the OP_RETURN content.
4. When `update_finalized_payouts` scans the confirmed block, it reads the OP_RETURN verbatim and stores the (now misattributed) operator xonly pk as `payout_payer_operator_xonly_pk` [8](#0-7) , causing downstream reimbursement-authorization logic (`is_kickoff_malicious`, `send_asserts`, `validate_payer_is_operator`) to bind future kickoff/reimbursement legitimacy to the wrong key.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
