## Title
`handleGetResponses()` skips the destination-chain timeout re-check that `handlePostRequests()` performs, letting late `GetResponse`s be force-accepted after the app-visible timeout — ([File: evm/src/core/HandlerV2.sol])

## Summary
`HandlerV2.handleGetResponses()` explicitly omits any timeout validation at the point of delivery to the source chain, relying entirely on a timeout check performed earlier and elsewhere (on Hyperbridge, using Hyperbridge's own clock). This mirrors the M-14 pattern: a timing invariant is enforced inconsistently across two code paths that are supposed to agree, so by the time the message reaches its final destination the "already checked" assumption no longer holds. Unlike `handlePostRequests()`, which re-validates `timestamp >= leaf.request.timeout()` right before dispatch, `handleGetResponses()` has no equivalent guard.

## Finding Description
`handleGetResponses()` in `evm/src/core/HandlerV2.sol` processes each `GetResponseLeaf` with an explicit comment stating the timeout is intentionally not checked: [1](#0-0) 

```solidity
function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
    ...
    for (uint256 i = 0; i < responsesLength; ++i) {
        GetResponseLeaf memory leaf = message.responses[i];
        // don't check for timeouts because it's checked on Hyperbridge
        ...
    }
    ...
    for (uint256 i = 0; i < responsesLength; ++i) {
        ...
        host.dispatchIncoming(leaf.response, _msgSender());
    }
}
```

Compare this with `handlePostRequests()` in the *same contract*, which does re-check timing at the point of delivery: [2](#0-1) 

The "checked on Hyperbridge" assumption refers to the Rust-side response handler, which only validates the GET request's timeout against **Hyperbridge's own clock at the moment the response is constructed**: [3](#0-2) 

```rust
for get in &msg.requests {
    let req = Request::Get(get.clone());
    if req.timed_out(host.timestamp()) {
        Err(Error::RequestTimeout { meta: (&req).into() })?
    }
    ...
```

Once this passes, the `GetResponse` commitment is stored on Hyperbridge and must still be finalized (challenge period), relayed, and proven against the source chain's `IHost` before `handleGetResponses()` ever runs — a multi-step, multi-chain path with no upper bound tied to the original request's `timeout_timestamp`. Nothing on the EVM side re-derives or re-checks `request.timeout()` against `block.timestamp` before calling `host.dispatchIncoming(...)`, which invokes the application's `onGetResponse()` callback.

Meanwhile, the *only* other path that can resolve this request — `handleGetRequestTimeouts()` — requires a **non-membership** proof that no response exists in Hyperbridge's state at the relevant height: [4](#0-3) 

Once Hyperbridge has already constructed and stored the `GetResponse` (which happens strictly before the app-visible timeout, from Hyperbridge's clock), that non-membership proof becomes permanently unobtainable, so `handleGetRequestTimeouts()` can never succeed for this request. The application is left with exactly one resolution path: accepting whatever `GetResponse` arrives, no matter how late relative to its own `timeout_timestamp` and its own chain's clock.

## Impact Explanation
This breaks the timing invariant the timeout mechanism is supposed to guarantee to applications: "if my `timeout_timestamp` has elapsed and I haven't received a response, I can safely revert my pre-request state changes." Because `handleGetResponses()` never re-checks the timeout, and `handleGetRequestTimeouts()` is provably blocked once Hyperbridge has stored the response, an application relying on GET-request timeouts for state consistency (e.g. releasing an escrow, rolling back a provisional action, or unlocking funds via `onGetTimeout`) can be forced down the `onGetResponse()` path arbitrarily late — even long after the request timed out on the source chain — with no alternative outcome available. Any relayer (an unprivileged, permissionless caller of `handleGetResponses`) can choose to delay submission until after the app's local timeout window, deliberately steering execution into `onGetResponse()` when the application's own invariants assumed a timeout would occur instead. This is a logic/timing manipulation of a public entrypoint that can force unintended execution paths in application contracts that branch behavior between "response" and "timeout" (e.g. releasing funds on success vs. refunding on timeout).

## Likelihood Explanation
Likelihood is meaningful: the code path is permissionless (`handleGetResponses` has no access control beyond `notFrozen`), and the divergence between Hyperbridge's construction-time check and the destination's delivery-time check grows naturally with challenge periods and relay delay — conditions that exist on every deployment, not an edge case requiring an adversarial relayer, though an adversarial relayer amplifies the impact by choosing delivery timing intentionally.

## Recommendation
Add an explicit timeout re-check in `handleGetResponses()` mirroring `handlePostRequests()`/`handleGetRequestTimeouts()`, e.g. reverting with `MessageTimedOut()` if `block.timestamp >= leaf.response.request.timeout()` at the point of delivery, so the destination chain's own clock is authoritative for what the application actually observes, rather than trusting a stale check made on a different chain at an earlier point in time.

## Proof of Concept
1. App on `EVM-A` dispatches a `GetRequest` with `timeout_timestamp = T`.
2. Hyperbridge's consensus/finality for the queried chain lands just before Hyperbridge's local time reaches `T`; the relayer submits the `ResponseMessage`, and `modules/ismp/core/src/handlers/response.rs::handle` accepts it (`req.timed_out(host.timestamp())` is false) and stores the `GetResponse` + receipt.
3. Time passes — consensus proof finalization, challenge period on `EVM-A`, and message relay delay — such that by the time the relayer submits `handleGetResponses()` to `EVM-A`, `block.timestamp` on `EVM-A` is now `> T` (the request is timed out from the app's perspective).
4. `handleGetResponses()` performs no timeout check (per the code comment) and calls `host.dispatchIncoming(leaf.response, relayer)`, invoking `onGetResponse()` on the app.
5. Separately, no one can ever successfully call `handleGetRequestTimeouts()` for this request, because the non-membership proof required at `evm/src/core/HandlerV2.sol` lines 293-321 will always find the response commitment present in Hyperbridge's state trie — `entry.value.length != 0` reverts with `InvalidProof()`.
6. Result: the application executes `onGetResponse()` logic well after its own `timeout_timestamp`, with no ability to instead resolve via `onGetTimeout()`, even though its own local clock indicates the request should have timed out.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }
