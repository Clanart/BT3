### Title
Missing timestamp freshness/deadline check in HMAC-signed request verification allows unlimited replay of captured App Proxy and Webhook requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`, `lib/shopify_app/controller_concerns/payload_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` and `ShopifyApp::PayloadVerification#hmac_valid?` (used by `ShopifyApp::WebhookVerification`) accept any request whose HMAC/signature matches the shared secret, but neither checks the freshness of the `timestamp` query parameter (App Proxy) or verifies any time-bound claim for the webhook payload. This mirrors the analog reported bug class: a signed operation is executed with no deadline/expiry enforcement, so a captured, validly-signed request can be replayed indefinitely by anyone who obtains it, long after it was intended to be acted upon.

### Finding Description
`query_string_valid?` computes the HMAC over the sorted query parameters (including `timestamp`) and compares it to the supplied `signature`; if they match, the request is accepted with no check that `timestamp` is recent: [1](#0-0) 

Similarly, `verify_request` in `WebhookVerification` only checks `hmac_valid?(data)` on the raw payload body, with no timestamp/nonce or expiry validation of any kind: [2](#0-1) 

Because `timestamp` is just another signed field (not an enforced expiry), any request that was ever validly signed by Shopify (or leaked/logged/cached) remains permanently valid from the gem's perspective — there is no "deadline" after which the signature is rejected, exactly analogous to the reported issue's core defect: a signed operation (swap) executed with no deadline parameter, permitting arbitrarily delayed/stale execution.

### Impact Explanation
An App Proxy or webhook request that is captured once (e.g., via browser history/referrer leakage for App Proxy GET requests, a compromised or misconfigured proxy/CDN log, or network capture) can be replayed by an unrelated, unauthenticated party at any later time and will still be accepted as legitimate by the app, since only the HMAC (not request freshness) is checked. This can cause stale/duplicate state-changing actions to be executed against the app on behalf of a shop or customer well after the original request's intended validity window, which is the CSRF-like "accepted forged/stale signed request" impact class relevant here.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to first obtain a previously-valid signed query string or webhook payload (via logs, caching proxies, browser history, or accidental exposure), which is a realistic but non-trivial precondition. Once obtained, replay succeeds unconditionally since there is no time-window enforcement in `query_string_valid?` or `hmac_valid?`.

### Recommendation
Enforce a maximum age for the `timestamp` parameter in `AppProxyVerification#query_string_valid?` (reject if `Time.now.to_i - timestamp.to_i` exceeds a small window, e.g. a few minutes) before/alongside the HMAC comparison. For webhooks, additionally validate the `X-Shopify-Webhook-Id`/delivery uniqueness or timestamp header where available and reject stale/duplicate deliveries, rather than relying solely on HMAC correctness with no deadline.

### Proof of Concept
1. A shop's storefront issues an App Proxy request such as `shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid-hmac>`.
2. This exact query string is captured (e.g., from a shared/cached URL, browser history, or an access log) as shown to be independently reproducible by the test's `query_string_valid?` check: [3](#0-2) 
3. Because `query_string_valid?` only re-derives the HMAC and compares it, an attacker (any anonymous party who obtained the query string) can replay it verbatim to the same App Proxy endpoint at any later date/time and it will be accepted (`assert_response :ok` behavior in [4](#0-3) ), with no deadline enforcement ever applied by [5](#0-4) .

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
