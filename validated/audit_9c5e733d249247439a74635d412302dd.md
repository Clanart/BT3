### Title
`updateRemoteUrl()` silently rewrites the origin remote from an unauthenticated GitHub API field, redirecting future pushes/fetches - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` compares the current `git remote` URL against `apiRepo.clone_url` returned from a GitHub API (or GitHub Enterprise Server) response, and — if the protocol matches and the remote "looks unchanged" from the last cached API value — silently overwrites the repository's origin remote with the new API-supplied URL, without any user confirmation. [1](#0-0) 

### Finding Description
This is structurally the same broken-invariant pattern as the Balancer report: a value that should be treated as attacker-influenceable (the "spot price" in the report; here, the `clone_url` field of an API response) is used both as (a) the thing being validated and (b) the baseline the validation is checked against, and the update path that moves the trusted baseline is not gated by any user-facing confirmation.

The check `remoteUrlUnchanged` only verifies that the *previously cached* `gitHubRepository.cloneURL` (itself derived from a prior, unauthenticated API fetch) still matches the current git remote — it does not verify that the *new* `apiRepo.clone_url` is legitimate or expected: [2](#0-1) 

If the value comes from a GitHub Enterprise Server endpoint the user has configured, or from any actor able to influence the API/proxy response for that endpoint (matching "a git remote/proxy response" in scope), `apiRepo.clone_url` is fully attacker-controlled. As long as the URL scheme (http/https/ssh) matches the existing remote and the user hasn't manually customized the remote away from the last-seen API value, `setRemoteURL()` is invoked automatically and silently — no dialog, no diff shown to the user: [3](#0-2) 

This path is reached from `repositoryWithRefreshedGitHubRepository()`, which is Desktop's routine background repository-refresh flow (fetches `apiRepo` via `API.fromAccount(account).fetchRepository(owner, name)` and then calls `updateRemoteUrl`), i.e. it runs periodically/automatically without any explicit user action analogous to the permissionless `updatePrice()` in the report: [4](#0-3) 

The only guard rails are: (1) protocol must match, and (2) the remote must not already have diverged from the last API-known clone URL. Neither of these validates the *new* target host/owner/repo against anything the user actually trusts — they only protect against Desktop clobbering a remote the user manually retargeted. Existing helpers like `urlMatchesRemote`/`urlsMatch` in `app/src/lib/repository-matching.ts` only compare hostname/owner/name structurally between two untrusted strings; they provide no authentication of the source. [5](#0-4) 

### Impact Explanation
A successful attack silently redirects where the victim's `git push`/`git fetch`/`git pull` operations go for a tracked repository, without any user-visible warning or confirmation dialog. This is a "silent corruption of what the user commits or pushes" scenario: subsequent pushes could go to an attacker-controlled remote (potentially leaking commits, credentials embedded in the URL, or code), and fetches could silently pull attacker-controlled history into the user's local repository.

### Likelihood Explanation
Exploitation requires the attacker to control (or MITM) the API response for the specific `owner/repo` the victim has added to Desktop — realistic for GitHub Enterprise Server users pointed at an attacker-influenced/compromised on-prem instance, or any network position able to tamper with API responses for a configured endpoint (the report's "git remote/proxy response" primitive). No local access, admin rights, or pre-existing malware is required; the update fires automatically during Desktop's normal background repository refresh cycle. The dependency on protocol matching and "unchanged" cached state narrows the window somewhat but does not require any unusual user interaction.

### Recommendation
Never silently rewrite a configured git remote based on API data. At minimum:
- Require explicit user confirmation (a dialog showing old vs. new remote URL) before changing `origin`'s URL.
- Do not treat "matches the last cached API value" as proof the new API value is legitimate; instead pin/verify the endpoint identity (e.g., only allow this auto-update for github.com with certificate-pinned settings, never for user-added GHES endpoints without confirmation).
- Log and surface remote-URL changes prominently, and consider disabling automatic remote rewriting entirely in favor of an explicit "Repository was renamed — update your remote?" prompt.

### Proof of Concept
1. Victim adds a GitHub Enterprise Server account/endpoint that is attacker-influenced (e.g., attacker has some control over that server's API responses, or intercepts/proxies traffic to it).
2. Victim clones/opens a repository tracked via that endpoint; Desktop calls `repositoryWithRefreshedGitHubRepository()` during normal background refresh [6](#0-5) .
3. The API returns `apiRepo.clone_url` pointing to an attacker-controlled host with the same protocol scheme as the current remote (e.g., `https://attacker.example/owner/repo.git`).
4. Because the current remote still matches the previously cached `gitHubRepository.cloneURL` (i.e., the user never manually customized it) and protocols match, `updateRemoteUrl()` calls `gitStore.setRemoteURL(...)` automatically [3](#0-2) .
5. All subsequent `git push`/`fetch` operations for that repository silently target `attacker.example` with no dialog shown to the user.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
