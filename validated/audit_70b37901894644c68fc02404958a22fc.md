## Title
Attacker-controlled tag names from a fetched/cloned repository are passed unsanitized as `git push` arguments, allowing option/argument injection - (File: `app/src/lib/git/push.ts`)

### Summary
GitHub Desktop's push flow assembles the `git push` argument list by concatenating the local branch name with a list of tag names (`tagsToPush`) with no `--` separator and no validation that a tag name doesn't begin with `-`. Tag names are sourced from `getAllTags()`, which lists *all* local tags via `git show-ref --tags -d` [1](#0-0) . Because tags fetched from a remote (e.g. after cloning or fetching an attacker-controlled repository) become local tags, an attacker who controls a cloned/fetched repository can plant a tag whose name looks like a CLI flag. That name is later appended verbatim to the `git push` argument vector.

### Finding Description
`push()` in `app/src/lib/git/push.ts` builds the push arguments as:
```
const args = ['push', remote.name, remoteBranch ? `${localBranch}:${remoteBranch}` : localBranch]
if (tagsToPush !== null) { args.push(...tagsToPush) }
``` [2](#0-1) 

There is no `--` end-of-options marker before these dynamically supplied values, and no check that entries in `tagsToPush` do not start with `-`. This array is populated from `gitStore.tagsToPush`, which is originally read from `getAllTags()` (all `refs/tags/*` present on disk) [1](#0-0)  and reconciled against local storage in `GitStore.refreshTags()` [3](#0-2) . Tags present in a cloned or fetched repository (i.e., defined by the remote/attacker) become part of this local tag set, and any that are not yet known to the remote are treated as "unpushed" and included as `tagsToPush` when the user performs a routine push (`app-store.ts` `performPush`) [4](#0-3) .

The broken invariant is: **values that end up on the git-push command line (as if they were `<ref>`/`<tag>` positional arguments) are never checked to ensure they cannot be interpreted as command-line options**, and no `--` separator isolates them. This is the structural analog of the reward-report's core defect - a piece of state (`s_clientOnlyClRewards` / here, "trusted, sanitized tag list") is used downstream as though it had already been validated/committed, when in fact its provenance (an attacker-influenced source) was never checked before being consumed by a security-sensitive operation (a shell/subprocess invocation instead of a monetary transfer).

Existing guards do not stop this path:
- `createTag()` client-side UI restricts *user-created* tag names via `RefNameTextBox`, but this only restricts tags created through Desktop's own UI, not tags that already exist in a repository the user clones or fetches from [5](#0-4) .
- `getAllTags()` performs no filtering of tag names beyond stripping the `refs/tags/` prefix and the `^{}` peel suffix [6](#0-5) .
- `push()` itself performs no sanitization of `tagsToPush` before appending them to the argument array [7](#0-6) .

### Impact Explanation
If an attacker crafts a repository with a tag name that git's `dugite`/execa argv-based invocation would interpret as an option to `git push` (rather than a ref), a victim who clones or fetches that repository and later performs an ordinary push could unknowingly have Desktop invoke `git push` with attacker-chosen flags. Depending on which git-push options are reachable this way, outcomes range from altering the push behavior (e.g., forcing an unintended `--repo=<attacker-url>`-style behavior, if such an option exists and is exploitable via positional injection) to unexpected data disclosure or silently corrupting what gets pushed (e.g., pushing to an unintended destination or with unintended flags), which matches the "silent corruption of what the user commits or pushes" impact class explicitly called out as in-scope.

### Likelihood Explanation
Likelihood depends on git's actual `check-ref-format` restrictions on tag names beginning with `-`. I was not able to conclusively verify from the codebase alone whether git universally forbids ref names starting with a hyphen (this would need to be confirmed against `git check-ref-format` behavior, which was not present or testable in the indexed code). If git does permit tag names beginning with `-`, the path is directly and trivially reachable by any user who clones/fetches an attacker's repository and pushes — no unusual steps are required beyond normal Desktop usage. If git rejects such ref names outright at the storage layer, this specific vector is not exploitable and the report should be treated as unconfirmed.

### Recommendation
- Insert a literal `--` separator into the `git push` argument array immediately before the branch refspec and any interpolated tag names in `app/src/lib/git/push.ts`, so that no value derived from repository data can be interpreted as an option.
- Validate/reject any tag name that begins with `-` (or otherwise looks option-like) before including it in `tagsToPush`, both in `getAllTags()` and in `fetchTagsToPush()` (`app/src/lib/git/tag.ts`).
- Apply the same `--` separator hardening to other git subprocess invocations in the codebase that interpolate ref/tag/branch names sourced from a possibly attacker-controlled repository.

### Proof of Concept
Conceptual (not verified end-to-end due to inability to confirm git's ref-name restrictions in this environment):
1. Attacker creates a bare repository and adds a tag using low-level plumbing (bypassing `git tag`'s own CLI validation) named e.g. `--upload-pack=/tmp/evil.sh`, directly via `git update-ref refs/tags/'--upload-pack=/tmp/evil.sh' <sha>` if such a ref name is accepted by the on-disk ref format.
2. Victim clones or fetches this repository in GitHub Desktop; `refreshTags()`/`getAllTags()` picks up this tag into local state [3](#0-2) .
3. Victim makes an unrelated commit and clicks "Push" in the toolbar; `performPush()` gathers `gitStore.tagsToPush` (which includes the malicious tag name, since it hasn't been pushed to any remote yet) and calls `pushRepo()` → `push()` [4](#0-3) .
4. `push()` appends the malicious string directly into `args` with no `--` separator [2](#0-1) , so the underlying `git` invocation is `git push origin master --upload-pack=/tmp/evil.sh` (or similar), instead of pushing the tag as a ref.

Because I could not execute git locally to confirm whether `refs/tags/-...` is accepted by git's ref-format validation, this should be verified in a live Desktop/Devin session before treating it as a confirmed, exploitable finding.

export async function getAllTags(
  repository: Repository
): Promise<Map<string, string>> {
  const args = ['show-ref', '--tags', '-d']

  const tags = await git(args, repository.path, 'getAllTags', {
    successExitCodes: new Set([0, 1]), // when there are no tags, git exits with 1.
  })

  const tagsArray: Array<[string, string]> = tags.stdout
    .split('\n')
    .filter(line => line !== '')
    .map(line => {
      const [commitSha, rawTagName] = line.split(' ')

      // Normalize tag names by removing the leading ref/tags/ and the trailing ^{}.
      //
      // git show-ref returns two entries for annotated tags:
      // deadbeef refs/tags/annotated-tag
      // de510b99 refs/tags/annotated-tag^{}
      //
      // The first entry sha correspond to the blob object of the annotation, while the second
      // entry corresponds to the actual commit where the tag was created.
      // By normalizing the tag name we can make sure that the commit sha gets stored in the returned
      // Map of commits (since git will always print the entry with the commit sha at the end).
      const tagName = rawTagName
        .replace(/^refs\/tags\//, '')
        .replace(/\^\{\}$/, '')

      return [tagName, commitSha]
    })

  return new Map(tagsArray)
}
```

  public async refreshTags() {
    const previousTags = this._localTags
    const newTags = await this.performFailableOperation(() =>
      getAllTags(this.repository)
    )

    if (newTags === undefined) {
      return
    }

    this._localTags = newTags

    // Remove any unpushed tag that cannot be found in the list
    // of local tags. This can happen when the user deletes an
    // unpushed tag from outside of Desktop.
    for (const tagToPush of this._tagsToPush) {
      if (!this._localTags.has(tagToPush)) {
        this.removeTagToPush(tagToPush)
      }
    }

    if (previousTags !== null) {
      // We don't await for the emition of updates to finish
      // to make this method return earlier.
      this.emitUpdatesForChangedTags(previousTags, this._localTags)
    }
  }
