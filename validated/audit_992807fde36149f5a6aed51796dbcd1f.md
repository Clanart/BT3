### Title
Path-containment check in `resolveWithin` uses a bare `startsWith`, allowing sibling-directory escape when opening a `filepath` from an `x-github-client://openRepo` deep link - (File: `app/src/lib/path.ts`)

### Summary
The external report's broken invariant is "a security-critical ratio/comparison is computed the wrong way, so a check that is supposed to bound a value silently accepts the wrong range." The closest analog in GitHub Desktop is `_resolveWithin` in `app/src/lib/path.ts`, which is meant to guarantee a user/attacker-supplied path stays inside a trusted root directory, but implements that guarantee with a bare string-prefix comparison instead of a path-boundary comparison.

### Finding Description
`_resolveWithin` computes the real, symlink-resolved root and target paths and then checks containment with: [1](#0-0) 

`realResolved.startsWith(realRoot)` is a classic path-boundary bug: it treats any path whose *string* begins with the root's string as "inside" the root, even when the actual path is a sibling directory that merely shares the root's name as a prefix (e.g. root `/Users/alice/Documents/GitHub/app` vs. `/Users/alice/Documents/GitHub/app-secrets/creds.txt`). There is no check that the character immediately following `realRoot` in `realResolved` is a path separator (or that the strings are exactly equal), so `"…/app-secrets/creds.txt".startsWith("…/app")` returns `true`.

This function is reachable from an attacker-controlled deep link. `Dispatcher.openRepositoryFromUrl` handles the `open-repository-from-url` action produced by `parseAppURL` (registered for the `x-github-client://`, `github-mac://`, etc. custom protocols in `app/src/main-process/main.ts`): [2](#0-1) 

The code does reject absolute `filepath` values with `isAbsolute(filepath)`, which stops naive `/etc/passwd`-style paths, but a relative path containing `..` segments is still passed to `resolveWithin(repository.path, filepath)`. Because the final safety gate is the broken `startsWith` check, a crafted `filepath` such as `../<repoName>-something/secret.txt` can resolve outside `repository.path` while still passing the containment check, as long as a sibling directory whose name starts with the repository's directory name exists on disk (a very plausible layout, since GitHub Desktop clones repos side-by-side under a common parent folder, e.g. `~/Documents/GitHub/<repo>`).

### Impact Explanation
If the bypass succeeds, `shell.showItemInFolder(resolved)` is called on a path outside the intended repository, opening the OS file manager focused on an arbitrary file/folder chosen by the link author (as long as they can guess or know a sibling directory name on the victim's disk, e.g. another commonly-cloned repo name). This is an unprivileged, attacker-controlled-link primitive resulting in file-system disclosure/read outside the repository root, matching the report's "value computed the wrong way defeats a security check" bug class — here the check is supposed to keep the resolved path bounded to `repository.path` but the prefix comparison lets it escape.

### Likelihood Explanation
Exploitation requires only that the victim click an `x-github-client://openRepo/...&filepath=...` link (no local access, no admin rights, no pre-existing malware, no leaked credentials — this is exactly the "link the user clicks" primitive called out as in-scope). The attacker needs to guess a plausible sibling directory name, which is realistic given Desktop's convention of cloning all repositories into one parent folder, but exact success is data-dependent, so likelihood is moderate rather than guaranteed for arbitrary victims.

### Recommendation
Replace the prefix check in `_resolveWithin` (`app/src/lib/path.ts:71`) with a boundary-aware comparison, e.g.:
```ts
return realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the platform-appropriate separator for the `options` module passed in (`Path.sep`/`Path.win32.sep`/`Path.posix.sep`), so a sibling directory whose name merely shares a prefix with the root can never satisfy containment.

### Proof of Concept
1. Victim has GitHub Desktop with two repositories cloned side by side: `~/Documents/GitHub/app` and `~/Documents/GitHub/app-secrets` (the latter containing a sensitive file `creds.txt`).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/org/app?filepath=..%2Fapp-secrets%2Fcreds.txt`.
3. `parseAppURL` parses this into an `open-repository-from-url` action with `filepath = "../app-secrets/creds.txt"` [3](#0-2) .
4. `Dispatcher.openRepositoryFromUrl` opens/selects the `app` repository, `isAbsolute(filepath)` is `false` so it proceeds to `resolveWithin(repository.path, filepath)` [4](#0-3) .
5. Inside `_resolveWithin`, `resolved` becomes `~/Documents/GitHub/app-secrets/creds.txt`, and `realResolved.startsWith(realRoot)` evaluates `true` because `"…/app-secrets/creds.txt"` starts with `"…/app"` [5](#0-4) .
6. `shell.showItemInFolder(resolved)` opens the OS file explorer on `creds.txt`, outside the intended repository — confirming the path-containment guard can be bypassed by a link the user simply clicks.

(Note: I could not execute this PoC in a live environment — this analysis is based on static reading of `app/src/lib/path.ts`, `app/src/ui/dispatcher/dispatcher.ts`, and `app/src/lib/parse-app-url.ts`. A Devin session with filesystem/terminal access would be needed to actually run Desktop and confirm the runtime behavior end-to-end.)
