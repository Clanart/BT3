### Title
Unvalidated `PostRequest.source` field in `HandlerV2.handlePostRequests()` allows source-chain impersonation - ([File: evm/src/core/HandlerV2.sol])

### Summary
The external report's core broken invariant is: an identity field (`ProposerIndex`) embedded in message data is *implicitly* validated only through a downstream, unrelated check (RANDAO signature), rather than being explicitly bound to the actual claimed source of the message. This lets an attacker's message pass validation while spoofing an identity it doesn't own. The same class of bug exists in `HandlerV2.handlePostRequests()`: the `source` field of a `PostRequest` is never explicitly checked against the state machine identified by the supplied proof (`request.proof.height.id.stateMachineId`), unlike the equivalent Substrate/Rust core handler which performs this check explicitly.

### Finding Description
In the Rust ISMP core handler `modules/ismp/core/src/handlers/request.rs`, incoming POST requests are explicitly checked so that a request's declared `source_chain` must equal the state machine identified by the proof used to verify membership (or be an authorized proxy): [1](#0-0) 

This check ensures that a request claiming `source = ChainA` can only be accepted if the membership proof was actually generated against `ChainA`'s state commitment.

However, `HandlerV2.handlePostRequests()` on the EVM side performs no equivalent check. It only validates the request's `dest`, its timeout, and duplicate-delivery status, then verifies MMR membership against the root for `request.proof.height`: [2](#0-1) 

Nowhere in this loop is `leaf.request.source` compared against `request.proof.height.id.stateMachineId` (the chain whose overlay root the proof is verified against). The `source` field is just attacker-controlled request data hashed into the leaf — it is not cryptographically bound to the chain that actually produced the MMR the proof was checked against. As with the RANDAO example, an unrelated implicit check (membership of the *hash*, which merely proves *some* chain included this exact leaf in its own outgoing-request tree) is mistaken for validation of the *claimed identity* (`source`) inside that leaf.

An attacker who controls a dispatching contract on `ChainX` (any registered, low-trust state machine) can dispatch a `PostRequest` whose `source` field is forged to equal a different, higher-trust chain identifier (e.g., Hyperbridge's own state machine ID, or another chain a destination `IsmpModule` uses for privileged trust decisions). The MMR proof will correctly and honestly prove that this exact request (including its forged `source` field) is a genuine leaf in `ChainX`'s own outgoing request tree, since the attacker legitimately dispatched it there. `handlePostRequests` verifies this membership against `ChainX`'s root (matching `request.proof.height`), which succeeds — nothing checks that `leaf.request.source` should equal `ChainX`.

### Impact Explanation
Downstream, `dispatchIncoming` routes the request to `router.module_for_id(request.to)`(destination-selected module), and the destination `IsmpModule.on_accept` callback frequently make trust/authorization decisions keyed on `request.source` (e.g., "only accept privileged instructions if `source == Hyperbridge` or a specific whitelisted chain," a common ISMP application pattern, e.g. IntentGateway/BandwidthManager cross-chain admin instructions). If a module trusts the `source` field for such decisions without additional binding, an attacker on any registered but untrusted state machine can impersonate a trusted source chain and trigger unauthorized execution, false state acceptance, or fund-moving logic gated on source-chain identity — a direct violation of the "Cross-chain admin or host-management effects must not be reachable through malformed proofs, wrong module bindings" pivot.

### Likelihood Explanation
Likelihood is high for any deployment where multiple state machines are registered with the same `HandlerV2`/`EvmHost` and any destination application distinguishes trust level by `source` chain (which is standard ISMP design intent, as proven by the Rust core explicitly enforcing this binding). No relayer, prover, or admin collusion is required — the entire exploit path is reachable by any unprivileged actor deploying a contract on one permissioned-but-lower-trust chain and calling the permissionless `handlePostRequests` entrypoint.

### Recommendation
Add an explicit check in `HandlerV2.handlePostRequests()` (and equally `handleGetResponses`/related GET/timeout EVM handlers where relevant) mirroring the Rust core's proxy-aware source binding: require `leaf.request.source` to equal `request.proof.height.id.stateMachineId`, unless the host is configured to allow proxying from that state machine (analogous to `host.is_allowed_proxy`/`check_state_machine_client` in `modules/ismp/core/src/handlers/request.rs:75-83`).

### Proof of Concept
1. Attacker deploys a dispatching contract on `ChainX` (a chain registered with Hyperbridge but that the destination app does not intend to trust for privileged calls).
2. Attacker calls `dispatch()` on `ChainX`'s host with a `PostRequest` where `source = <spoofed trusted chain id>`, `dest = <victim chain>`, `to = <victim module address>`, and a malicious `body`.
3. This request is legitimately included as a leaf in `ChainX`'s own outgoing-request MMR.
4. Relayer (or attacker themselves, since `handlePostRequests` is permissionless) submits `PostRequestMessage{ proof: { height: {id: {stateMachineId: ChainX, ...}}, ...}, requests: [leaf] }` to `handlePostRequests` on the victim chain.
5. `handlePostRequests` verifies MMR membership against `ChainX`'s root — succeeds, since the leaf really is in `ChainX`'s tree. No check compares `leaf.request.source` to `ChainX`.
6. `host.dispatchIncoming(leaf.request, msgSender)` is called, invoking the destination module's `on_accept` with `request.source` falsely reporting the spoofed trusted chain, potentially triggering privileged logic gated on that source. [3](#0-2) [4](#0-3)

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
