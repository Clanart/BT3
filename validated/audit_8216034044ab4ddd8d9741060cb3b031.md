### Title
Identity public key enables universal Schnorr signature forgery - (File: crypto/schnorr/src/lib.rs)

### Summary
`SchnorrSignature::verify` accepts the group identity as a public key and does not reject the identity nonce. `Ciphersuite::read_G` only checks that an encoding decodes canonically; it does not reject the encoded identity. As a result, an attacker can submit `(R = identity, s = 0)` and satisfy verification for the identity public key under any challenge.

### Finding Description
`SchnorrSignature::read` parses attacker-controlled `R` and `s` through `C::read_G` and `C::read_F` without semantic restrictions [1](#0-0) . `Ciphersuite::read_G` accepts any canonical group encoding, including the canonical encoding of the identity [2](#0-1) . Verification computes `R + cA - sG == 0` through `batch_statements` and `multiexp_vartime` [3](#0-2) . If `A`, `R`, and `s` are respectively the identity, identity, and zero, the equation is `0 + c·0 - 0·G == 0`, which is true for every challenge.

### Impact Explanation
Any verifier that accepts an attacker-supplied Schnorr public key and signature through these APIs accepts a universal forged signature for the identity public key. This is a signature-verification correctness failure, not merely a malformed-input rejection issue: the forged signature remains valid regardless of the message because the challenge term is multiplied by the identity public key.

### Likelihood Explanation
The attack requires only canonical public input bytes and no private state. For Ristretto, the public key and `R` can both be the 32-byte canonical identity encoding (`00 * 32`), and `s` can be the canonical zero scalar (`00 * 32`). No malformed encoding is necessary. The impact depends on an application permitting identity as a public key; the primitives do not prevent that.

### Recommendation
Reject identity public keys in Schnorr verification, either inside `SchnorrSignature::verify`/`batch_statements` or at the point where caller-controlled public keys are accepted. Also consider rejecting `R = identity` during signature validation unless a consuming protocol explicitly permits it. If identity rejection is intentionally left to callers, document it prominently; enforcing it in `verify` provides safer API behavior.

### Proof of Concept
For `Ristretto`, attacker-controlled bytes can decode as:

```text
public_key = 00 * 32      // canonical Ristretto identity
R          = 00 * 32      // canonical Ristretto identity
s          = 00 * 32      // canonical zero scalar
```

These parse successfully with `Ristretto::read_G` and `SchnorrSignature::<Ristretto>::read` because canonicality is the only encoding check [2](#0-1) . Verification then queues the equation `R + cA - sG` [4](#0-3)  and accepts because all three terms are identity/zero [5](#0-4) .

```rust
use zeroize::Zeroizing;
use dalek_ff_group::Ristretto;
use ciphersuite::Ciphersuite;
use schnorr::SchnorrSignature;

let identity_bytes = [0u8; 32];
let public_key =
  Ristretto::read_G(&mut identity_bytes.as_slice()).unwrap();
let signature = SchnorrSignature::<Ristretto> {
  R: public_key,
  s: Zeroizing::new(<Ristretto as Ciphersuite>::F::ZERO).to_owned(),
};

// Any challenge accepted by the API verifies.
let challenge = <Ristretto as Ciphersuite>::F::ONE;
assert!(signature.verify(public_key, challenge));
```
