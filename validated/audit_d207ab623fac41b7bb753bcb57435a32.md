## Suspended validators retain staking-reward eligibility because reward distribution never checks the `Suspended` flag - (File: kaiax/staking/impl/getter.go)

### Summary
The external advisory describes an authorization function (`Server.IsAuthorized`) that validates several credential attributes (format, expiry, secret, deleted/system-user) but never checks whether the underlying account has been suspended, letting a suspended principal keep drawing paid resources through a still-"valid" credential. Kaia's validator-suspension mechanism has the same class of gap: a validator that the consensus layer (`kaiax/valset`) has explicitly `Suspended` (and therefore excludes from the committee) is still treated as fully reward-eligible by the staking/reward pipeline, because reward eligibility is computed from a completely different, coarser signal (`NodeState == ValActive`) that never looks at `Suspended`.

### Finding Description
`valset.Node` tracks two independent authorization-relevant attributes: the on-chain `State` (`ValActive`, `ValPaused`, etc., mirrored from AddressBookV2/MultiCall) and an in-memory `Suspended` boolean set by the epoch/violation transition logic (`kaiax/valset/impl/transition_context.go`, exercised e.g. in `TestApplyViolationTransition_SuspendedNotExempt`) and consulted via `MarkSuspended` / `ExcludeSuspended` [1](#0-0) .

The consensus-committee selection path correctly excludes suspended validators: `committeeWithFallback` computes `Committee = {ValActive} - {Suspended}` [2](#0-1) .

However, `NodeState.IsRewardEligible()` — the single predicate used to decide who gets staking rewards — checks only `State == ValActive` and has no notion of `Suspended` at all: [3](#0-2) 

This predicate is used directly by the staking module when building the `StakingInfo` that the reward module later pays out from: [4](#0-3) 

`kaiax/reward` consumes exactly this `StakingInfo` (via `GetStakingInfo`) to compute `GetRewardAddress` and to allocate KIP-82 staker rewards (`assignStakingRewards`) — neither of which re-derives or consults the valset module's `Suspended` set: [5](#0-4) 

So the two subsystems that should agree on "is this validator currently authorized to participate/benefit" diverge: the consensus/committee subsystem revokes access (excludes from block production duty) the moment `Suspended` is set, but the reward subsystem's authorization check (`IsRewardEligible`) never re-validates against that same suspension state — exactly the pattern in the external report where one authorization path checks account status and a parallel path (the AI Bridge proxy) does not, letting the suspended entity keep collecting value.

### Impact Explanation
A validator that has been suspended by the valset module (e.g., for PFS/CFS violations or minimum-stake violations under KIP-286/287, per `TestApplyViolationTransition_SuspendedNotExempt`) is removed from the active committee and stops performing consensus duties, yet it remains `State == ValActive` until (and unless) the slower violation-transition machinery eventually demotes it to `ValExiting`. During that window the reward module still counts it as a fully qualified, reward-eligible validator/staker and pays it its full share of minting/fee rewards (`GetDeferredReward` → `assignStakingRewards`), even though it contributed nothing to block production. This is a concrete reward-redirection/value-leak: KAIA that should be reallocated (or withheld) from a validator that has been penalized/excluded from consensus is instead paid out to that same suspended validator, diluting honest, actively-participating validators' and funds' shares.

### Likelihood Explanation
This requires no attacker action beyond becoming eligible for suspension (e.g., failing performance/fork-score checks, or violating minimum stake) — a condition that is entirely reachable by any registered staker/validator operating normally on the permissionless network. Because `Suspended` is deterministically computed by all honest nodes from the same on-chain data (staking amounts, CFS/PFS scores), every node will independently suspend and independently continue rewarding the same validator, so the reward leak is fully deterministic and reproducible every epoch that the validator remains suspended-but-`ValActive`.

### Recommendation
Make `IsRewardEligible` (or the staking module's eligibility filter in `parsePermissionlessCallResult`) consult the same `Suspended` state that the committee/getter path uses, e.g. by threading the valset module's suspension set into `GetStakingInfo`/`assignStakingRewards`, or by excluding `Suspended` node IDs from `StakingInfo.NodeIds` before rewards are computed, so that a validator excluded from the committee for suspension is also excluded from reward distribution for the same period.

### Proof of Concept
1. Let validator `V` be `State: ValActive` and, in a given epoch, get marked `Suspended: true` by the violation-transition logic (as in `TestApplyViolationTransition_SuspendedNotExempt`, `kaiax/valset/impl/transition_context_test.go:358-375`).
2. `committeeWithFallback` computes `Committee = {ValActive} - {Suspended}`, so `V` is excluded from the consensus committee for that epoch (`kaiax/valset/impl/getter_permissionless.go:33-45`) — `V` produces no blocks and validates nothing.
3. At the same block height, `kaiax/staking.GetStakingInfo` calls `parsePermissionlessCallResult`, which keeps `V` in `NodeIds`/`RewardAddrs` because `valset.NodeState(p.State).IsRewardEligible()` only checks `State == ValActive`, ignoring `Suspended` (`kaiax/staking/impl/getter.go:196-209`).
4. `FinalizeState` → `GetDeferredReward` → `assignStakingRewards` distributes staking rewards proportionally to all `NodeIds` returned by `GetStakingInfo`, so `V`'s `RewardAddrs` entry receives its full staking-reward share despite being suspended from the committee (`kaiax/reward/impl/blockstate.go:46-56`, `kaiax/reward/impl/getter.go:334-368`).

Note: I was unable to fully trace the exact code path where `Suspended` is asserted at consensus block-finalization time relative to `FinalizeState` (i.e., confirm the precise ordering/timing guarantee that `Suspended` is active in the same block where rewards are computed) due to running out of search iterations; a Devin session with full repository access would be needed to confirm this timing and produce an end-to-end runnable PoC test.

// committeeWithFallback returns the committee at the given block.
// Committee = {VA} - {Suspended}.
//
// Safety fallback: when len(committee)=0 due to {ValActive} ⊆ SuspendedSet, fallback to all VA.
func committeeWithFallback(nodes valset.NodeMap) (committee valset.NodeMap, fellBack bool) {
	committee = nodes.Committee()
	if len(committee) > 0 {
		return committee, false
	}

	// ignore SuspendedSet
	return nodes.FilterByState(valset.ValActive), true
}

func (r *RewardModule) GetRewardAddress(num uint64, nodeId common.Address) common.Address {
	sInfo, err := r.StakingModule.GetStakingInfo(num)
	if err != nil {
		return common.Address{}
	}

	for idx, id := range sInfo.NodeIds {
		if id == nodeId {
			return sInfo.RewardAddrs[idx]
		}
	}
	return common.Address{}
}
