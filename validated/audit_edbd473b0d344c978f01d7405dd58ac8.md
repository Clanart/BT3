### Title
Loss of pending MGP rewards when `totalSupply()` drops to zero in `WomUp` - ([File: wombat/WomUp.sol])

### Summary
`WomUp` implements a Synthetix-style staking/reward accrual scheme for migrating WOM stakers into `mWom`/`vlMGP`. Like the reported `AbstractRewarder::_updateReward()` bug, its `rewardPerToken()`/`updateReward` logic does not account for reward accrued while `totalSupply()` is zero, causing MGP rewards generated during that window to be permanently stranded in the contract with no recovery path.

### Finding Description
`rewardPerToken()` short-circuits and returns the stale `rewardPerTokenStored` whenever `totalSupply() == 0`: [1](#0-0) 

The `updateReward` modifier unconditionally advances `lastUpdateTime` to `lastTimeRewardApplicable()` on every `stake`/`withdraw`/`migrate`/`getReward` call, regardless of whether `totalSupply()` was zero during the elapsed interval: [2](#0-1) 

Because `rewardRate` and `periodFinish` are fixed once via `initializeRewards()` (a linear, time-based schedule independent of any staking activity), any interval in which `_totalSupply == 0` still "consumes" reward-rate time, but that reward is never captured into `rewardPerTokenStored` nor queued anywhere: [3](#0-2) 

When the last staker calls `withdraw()`/`migrate()` and reduces `_totalSupply` to `0`, and later a new staker calls `stake()`, the modifier sets `lastUpdateTime = lastTimeRewardApplicable()` for that empty-supply gap without adding the corresponding `rewardRate * elapsedTime` amount to `rewardPerTokenStored`. This exactly mirrors the root cause described in the external report (`rewardPerTokenStored` failing to capture reward accrued when supply is 0), except here it manifests via unconditional advancement of `lastUpdateTime` in the modifier rather than a guarded update in `_updateReward()`. Unlike `BaseRewardPool`/`BaseRewardPoolV2` in this same codebase, which already implement the recommended fix (routing rewards into `queuedRewards` when `totalStaked() == 0`, see `_provisionReward`), `WomUp` has no `queuedRewards` mechanism at all: [4](#0-3) 

### Impact Explanation
MGP reward tokens allocated for the zero-supply window are permanently unrecoverable: they are not credited to any user's `rewards[]`, and `rescueReward()` can only be called before `rewardRate` is set (i.e., before `initializeRewards()`), so the owner cannot reclaim them afterward. This is a permanent freezing/loss of unclaimed yield that reduces payouts to legitimate stakers relative to the total reward pool funded, and is triggered purely by ordinary user actions (withdrawing to zero supply and re-staking later).

### Likelihood Explanation
This requires only that all stakers withdraw/migrate out at some point during the fixed 7-day reward `duration` (leaving `_totalSupply == 0`) before a subsequent `stake()` call — a plausible scenario for a migration-helper contract with potentially few participants, especially near the start/end of the window or during low participation periods. No privileged role is needed to trigger it.

### Recommendation
Track reward accrued during zero-supply periods (e.g., a `queuedRewards` accumulator similar to `BaseRewardPoolV2::_provisionReward`) and fold it back into `rewardPerTokenStored` once `totalSupply()` becomes positive again, instead of unconditionally advancing `lastUpdateTime` in the `updateReward` modifier when `totalSupply() == 0`.

### Proof of Concept
1. Owner calls `initializeRewards()`, setting `rewardRate = R`, `periodFinish = now + 7 days`, `lastUpdateTime = now`.
2. Alice calls `stake(100)` at `t=0`.
3. Alice calls `withdraw(100, false)` at `t=5` → `_totalSupply` becomes `0`; `rewardPerTokenStored` updated to reflect `t=0..5`, `lastUpdateTime = 5`.
4. No one is staked between `t=5` and `t=10`.
5. Bob calls `stake(100)` at `t=10` → modifier computes `rewardPerToken()` which returns the stale `rewardPerTokenStored` (since `totalSupply()==0` at the start of this call), and sets `lastUpdateTime = 10`, silently discarding `R * 5` reward-seconds of MGP that were never distributed to anyone and can never be reclaimed (`rescueReward()` is blocked once `rewardRate > 0`).         if (totalSupply() == 0) {
            return rewardPerTokenStored;
        }
