## Title
Path Traversal via Unsanitized Committed File Path in `parseRawLogWithNumstat` Leads to Arbitrary File Open/Reveal Outside Repository — (File: `app/src/lib/git/log.ts`)

### Summary
`parseRawLogWithNumstat` extracts file paths directly from `git log --raw --numstat -z` output and places them into `CommittedFileChange.path` without any normalization or containment check against `repository.path`. Several UI consumers of `CommittedFileChange`/history file lists then build a filesystem path via naive `Path.join(repository.path, file.path)` and pass the result to OS-level "open"/"reveal" primitives. If a malicious tree entry name contains `../` segments, `Path.join` can resolve the final path outside the repository root, and Desktop will happily reveal/open that arbitrary path.

### Finding Description
`parseRawLogWithNumstat` reads the parsed path straight from git's raw output and stores it verbatim: [1](#0-0) 

There is no `path.normalize`/`path.isAbsolute`/containment check performed here or in `getChangedFiles`, which feeds this function directly from `git log ... --raw --numstat -z` on attacker-controllable commit content: [2](#0-1) 

Downstream, multiple UI code paths take `CommittedFileChange.path` and join it with `repository.path` using plain Node `path.join`, then hand the result to shell-level primitives that open or reveal the file:

- `revealInFileManager` in `app-shell.ts` joins and calls `shell.showItemInFolder`: [3](#0-2) 

- History "Open with Default Program" / context menu in `selected-commits.tsx`: [4](#0-3) [5](#0-4) 

- Pull request file list context menu (`pull-request-files-changed.tsx`), and stash/conflict dialogs use the identical unguarded `Path.join(repository.path, file.path)` pattern: [6](#0-5) [7](#0-6) 

By contrast, Desktop already has a hardened pattern for untrusted paths elsewhere: `openRepositoryFromUrl` (handling deep-link file paths) explicitly rejects absolute paths and uses `resolveWithin` to enforce containment before calling `shell.showItemInFolder`: [8](#0-7) 
This containment check is conspicuously **not** applied to paths sourced from `parseRawLogWithNumstat`.

Crucially, the *write*-oriented consumers of committed/working file paths (`checkoutPaths`, `checkoutIndex`, `checkoutConflictedFile`) delegate to `git checkout`/`git checkout-index`, which invoke git's own `unpack-trees`/`verify_path()` machinery — git itself rejects `..`, `.git`, and similar dangerous path components during checkout operations: [9](#0-8) [10](#0-9) 
That protection, however, does not apply to `git log --raw`/`--numstat`, which is a pure read/enumeration path that does not call `verify_path()` — it simply echoes tree entry names, so a crafted tree entry containing `../` segments (constructible via low-level plumbing such as `git mktree`, which does not validate entry names) will be printed verbatim and captured by `parseRawLogWithNumstat`.

Since `fetch.fsckObjects`/`transfer.fsckObjects` are **not** enabled by default in git, a client fetching/cloning from an attacker-controlled remote (self-hosted server, proxy, or MITM) will not reject such malformed tree objects on ingestion, so the payload can reach the local object database and subsequently `git log`.

### Impact Explanation
An attacker who controls a repository the victim clones/fetches (in-scope per the review's "Valid Impact": "attacker controls a cloned/fetched repository ... and the result is ... file write or read outside the repo") can craft a commit whose changed-file entry name is a traversal string (e.g. `../../../../some/known/path`). When the victim opens that commit in History (or a PR file list, stash view, or conflict dialog) and chooses "Reveal in Finder/Explorer" or "Open with Default Program"/"Open in External Editor", Desktop will resolve and open/reveal a path outside the repository — an out-of-repo file read/disclosure/open primitive. If the resolved path happens to reference an executable already present on the victim's machine, "Open with Default Program" could cause that pre-existing binary to run via the OS's default handler.

Note: this is a read/open/reveal primitive, not an arbitrary-write/corruption primitive — the write-side consumers (`checkoutPaths`/`checkoutIndex`) are protected by git's own `verify_path()` enforcement during actual checkout operations, so committing/pushing/pulling this content does not itself corrupt files outside the repo.

### Likelihood Explanation
Requires the victim to (a) clone/fetch a malicious remote (not necessarily hosted on github.com, since GitHub's server-side fsck would likely reject such trees on push, but a self-hosted server/proxy/MITM would not) and (b) manually interact with the specific commit/file (double-click, or explicitly choose Reveal/Open from the context menu) — this is plausible attacker-influenced but requires some user interaction, and the target path must be guessed/known in advance (blind traversal), limiting practical exploitation to disclosure of predictable file locations.

### Recommendation
- In `parseRawLogWithNumstat` (or immediately when constructing `CommittedFileChange`), reject or sanitize any path containing `..` path segments, leading `/`, absolute-path indicators, or resolving outside `repository.path` (mirroring the `resolveWithin` containment check already used in `dispatcher.ts`'s `openRepositoryFromUrl`).
- Apply the same containment check centrally at the point paths are turned into filesystem operations (`revealInFileManager`, `openFile`, `openInExternalEditor`, and the various `Path.join(repository.path, file.path)` call sites) rather than relying on git's checkout-time validation, since read-only git log/diff/status output is not subject to `verify_path()`.

### Proof of Concept
1. Create a scratch repo; use `git hash-object -w --stdin` to write a blob, then craft a tree line manually and feed it to `git mktree` with an entry name such as `../../../../tmp/evil` (mktree does not validate entry names).
2. `git commit-tree` the resulting tree to create a commit referencing this malformed tree, and set it as the tip of a branch in a bare repo served over `file://`/a custom git-daemon/HTTP server (no `receive.fsckObjects` enforcement).
3. In GitHub Desktop, clone/fetch that repository (client-side `fetch.fsckObjects` is off by default, so the object is accepted).
4. Run the equivalent of `getChangedFiles(repository, sha)` (e.g. select the commit in History) and confirm `CommittedFileChange.path` equals the raw `../../../../tmp/evil` string, unmodified.
5. Right-click the file in History and choose "Reveal in Finder/Explorer" or "Open with Default Program"; observe that `Path.join(repository.path, file.path)` resolves to `/tmp/evil` (or another out-of-repo location depending on nesting depth) and that path is opened/revealed by the OS shell.

export async function getChangedFiles(
  repository: Repository,
  sha: string
): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)
  // this is equivalent to the user configuring 'diff.renames' to 'copies'
  // NOTE: order here matters - doing -M before -C means copies aren't detected
  const args = [
    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}

export async function checkoutIndex(
  repository: Repository,
  paths: ReadonlyArray<string>
) {
  if (!paths.length) {
    return
  }

  const options = {
    successExitCodes: new Set([0, 1]),
    stdin: paths.join('\0'),
  }

  await git(
    ['checkout-index', '-f', '-u', '-q', '--stdin', '-z'],
    repository.path,
    'checkoutIndex',
    options
  )
}
