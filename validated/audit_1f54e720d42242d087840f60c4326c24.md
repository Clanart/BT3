### Title
`load_rules()` resolves `.claude/hookify.*.local.md` relative to process cwd instead of a session-bound project root, allowing cross-repo rule confusion - ([File: plugins/hookify/core/config_loader.py])

### Summary
`load_rules()` builds its glob pattern with a bare relative path `os.path.join('.claude', 'hookify.*.local.md')` and calls `glob.glob()` without anchoring to a fixed session/project directory. Since the hook process's working directory is whatever the Claude Code session's shell cwd currently is (which can change during a session, e.g. via a prior `Bash(cd ...)` tool call), the rule set loaded on each `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` invocation is bound to "whatever `.claude` directory happens to be under the current cwd" rather than to the originally-approved repository.

### Finding Description
`load_rules()` in `plugins/hookify/core/config_loader.py` does:
```python
pattern = os.path.join('.claude', 'hookify.*.local.md')
files = glob.glob(pattern)
``` [1](#0-0) 

This is a relative-path glob with no anchoring via `CLAUDE_PROJECT_DIR`, `os.environ`, or any session-fixed root. Every hook script (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) calls `load_rules()` directly with no cwd normalization: [2](#0-1) 

The codebase does define a `CLAUDE_PLUGIN_ROOT` environment variable used only to fix up `sys.path` for importing the `hookify` package itself, not to scope rule-file discovery to the project being worked on: [3](#0-2) 

I was not able to find any use of `CLAUDE_PROJECT_DIR` (or an equivalent session-root environment variable) inside `plugins/hookify/` itself — grepping the repo shows it is only referenced in documentation/skill files (`plugins/plugin-dev/skills/hook-development/*`) and in an unrelated plugin (`plugins/security-guidance/hooks/security_reminder_hook.py`), not in the hookify hook scripts or `config_loader.py`. This means there is no existing workspace guard, session-binding, or repo-scoping check that would prevent `load_rules()` from reading files outside the intended project when cwd drifts.

Because the hook subprocess inherits whatever cwd the parent Claude Code session process currently has, and Bash tool invocations within the same session can change that cwd (or a user/attacker-influenced `.claude` path could be a symlink into another checked-out repo), a subsequent hook invocation's `glob.glob('.claude/hookify.*.local.md')` can silently resolve to a completely different repository's rule files than the one the user believes is being governed.

### Impact Explanation
If the rule files that are supposed to enforce safety/policy guardrails (e.g., blocking `rm -rf`, blocking access to secrets, warning on dangerous commands) are silently swapped out for a different repository's rule set — or a repo with weaker/absent rules — the effective policy enforcement for the session becomes decoupled from the repo the user is actually operating on. This can cause a dangerous command that would have been blocked/warned under repo A's rules to pass through un-flagged because repo B's rules (loaded due to cwd drift) don't cover it, or conversely cause confusing/incorrect warnings. This matches a trust-boundary/session-binding bypass class of impact: automation state (hook enforcement) is not reliably bound to the approved session/repo.

### Likelihood Explanation
This requires only two things reachable through completely ordinary session activity: (1) a `Bash` tool call in the same Claude Code session that does `cd` into a different directory (a mundane, extremely common operation, not requiring any special privilege), and (2) the target directory containing (or being reachable from) another `.claude` directory with `hookify.*.local.md` files, or `.claude` being a symlink. No admin privilege, no exploit of parsing, no leaked keys are needed — this is a straightforward consequence of using a relative path and `os.getcwd()`-relative globbing with no session anchoring. This makes it a fairly practical/repeatable condition in real multi-repo, monorepo, or worktree-heavy workflows.

### Recommendation
Anchor rule discovery to a fixed, session-bound project root rather than the live process cwd:
- Use `os.environ.get('CLAUDE_PROJECT_DIR')` (or equivalent Claude Code-provided project root variable) to build the `.claude` glob path, falling back to a value captured once at hook-process startup, not to `os.getcwd()` re-evaluated per hook call.
- Reject or resolve symlinked `.claude` directories only if they point within the recognized project root (e.g., verify `os.path.realpath(claude_dir).startswith(os.path.realpath(project_root))`).
- Optionally cache/pass the project root explicitly as an argument to `load_rules(project_root=...)` so callers cannot accidentally rely on ambient cwd state.

### Proof of Concept
Unit test plan:
1. Create two temporary directories `repo_a/.claude/hookify.a.local.md` and `repo_b/.claude/hookify.b.local.md`, each with distinct `name:` frontmatter values (e.g., `rule-a` vs `rule-b`).
2. `os.chdir(repo_a)`; call `load_rules()`; assert the returned rules contain `rule-a` and not `rule-b`.
3. Simulate the mid-session drift by calling `os.chdir(repo_b)` (representing a prior `Bash(cd repo_b)` tool call) without restarting the hook process/session.
4. Call `load_rules()` again in the same process; assert it now returns `rule-b` instead of `rule-a`, demonstrating that the loaded policy silently switched repos despite the user-facing session still being "about" `repo_a`.
5. Expected (fixed) behavior: `load_rules()` should continue returning `rule-a` regardless of cwd changes when anchored via `CLAUDE_PROJECT_DIR`/explicit project root, proving the vulnerability is closed once anchoring is added.
