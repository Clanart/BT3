### Title
Zero-value/dust outputs counted as spendable funds, inflating transactions past the standard weight limit - (File: networks/bitcoin/src/wallet/mod.rs, networks/bitcoin/src/wallet/send.rs)

### Summary
The Covalent bug class is: entries that have been emptied (amount set to 0) still occupy slots in a bounded collection, so a bounded operation (`setValidatorAddress` moving at most 300 unstakings) can be permanently bricked by zero-value entries. In Serai's bitcoin wallet, the analog is `Scanner::scan_transaction`, which reports every output paying to a registered `script_pubkey` as a `ReceivedOutput` — including zero-value and sub-dust outputs — and `SignableTransaction::new`, which never filters inputs by value. Such outputs are "empty" inputs: they contribute nothing to `input_sat` but each occupies a fixed ~41-vbyte input slot in the transaction weight budget, and a single `MAX_STANDARD_TX_WEIGHT` overflow or fee exhaustion bricks the spend.

### Finding Description
`Scanner::scan_transaction` matches only `output.script_pubkey` against the registered scripts and unconditionally pushes a `ReceivedOutput` for every match, with no `output.value` check: [1](#0-0)  A `ReceivedOutput` wraps `offset`, `output`, `outpoint` with no validity gate on value: [2](#0-1) 

On the spend side, `SignableTransaction::new` rejects dust *payments* (`*amount < DUST` → `DustPayment`) and rejects dust *change*, but performs no minimum-value check on `inputs` — a 0-sat input is accepted into `input_sat`, `tx_ins`, and `prevouts`: [3](#0-2)  Every input adds a fixed-size `TxIn` to the weight computation via `calculate_weight_vbytes`, and the transaction is rejected with `TooLargeTransaction` once `weight > MAX_STANDARD_TX_WEIGHT`: [4](#0-3) [5](#0-4)  Because signing commits to `Prevouts::All`, all counted inputs are bound into every sighash — there is no way to drop the empty inputs inside the machine once they're in the `inputs` vector: [6](#0-5) 

### Impact Explanation
Any unprivileged party who observes a registered script_pubkey (which is a public Taproot address) can send low/zero-value outputs to it. Each is reported as a received fund. When the wallet sweeps its UTXO set, each empty input consumes ~57.5 WU (~41 non-witness bytes + ~16.5 witness bytes) of the 400,000 WU standard weight budget and raises `needed_fee`, while contributing 0 sats. Sufficient dust padding either (a) pushes the transaction over `MAX_STANDARD_TX_WEIGHT` causing `TooLargeTransaction` and blocking the spend, or (b) inflates `needed_fee` until `NotEnoughFunds` fires, forcing manual input curation outside the API — the same "empty entries occupy the bounded operation's slots and brick it" failure as the original report.

### Likelihood Explanation
Medium likelihood. The attacker's cost is one dust transaction per pad output (or many pad outputs in one transaction); no collusion, no validator role, and no leaked key is required — only knowledge of the public address, which `Scanner` is designed around. Zero-value and sub-dust non-OP_RETURN outputs are nonstandard on default relay but consensus-valid, so a miner-assisted or directly-submitted transaction suffices; ordinary dust (546+ sats) is trivially relayable.

### Recommendation
Mirror the report's fix — exclude empty entries rather than counting them: in `Scanner::scan_transaction`, skip outputs with `output.value.to_sat() == 0` (and optionally `< DUST`, since they can never be spent profitably). Additionally, in `SignableTransaction::new`, filter or reject `inputs` whose value cannot cover the marginal fee their input weight adds (compare each input's value against `fee_per_vbyte * marginal_input_vbytes`), so worthless inputs are never counted toward `input_sat` or the weight budget.

### Proof of Concept
1. Call `Scanner::new(group_key)`; the base `p2tr_script_buf(key)` script is registered automatically with `Scalar::ZERO` offset (`wallet/mod.rs:162-166`).
2. Attacker broadcasts a transaction containing hundreds/thousands of outputs paying that `script_pubkey` with value 0 or 546 sats (546 sats relays fine; only the spent amount is griefed, not blocked).
3. `scan_transaction` returns every one as a `ReceivedOutput` (`wallet/mod.rs:205-211`).
4. The wallet feeds all received outputs as `inputs` to `SignableTransaction::new`. `input_sat` grows only by real value, but `tx_ins.len()` — and hence `calculate_weight_vbytes` output (`send.rs:204`) — grows by the padded count.
5. At ~6,900 pad inputs the weight check `weight > MAX_STANDARD_TX_WEIGHT` (`send.rs:241`) fires, returning `TooLargeTransaction` for any spend built over the full UTXO set — the zeroed-entry-counted analog of the 300-unstaking limit.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
