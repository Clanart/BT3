## Analysis: Predictable Isolated-Address Poisoning Breaks IBC Callback Strict-Balance Check (DoS analog of DEPU-1)

### Title
Attacker-Griefable Strict Zero-Balance Check in `IBCReceivePacketCallback` Permanently DoSes ICS-20 Destination Callbacks - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
`IBCReceivePacketCallback` enforces a strict equality check (`receiverTokenBalance.Cmp(big.NewInt(0)) != 0`) requiring the deterministic, attacker-predictable "isolated address" to hold *exactly zero* ERC20 tokens after the destination callback executes. This mirrors the DEPU-1 bug class: a third party can pre-load a small amount of the same ERC20 into that address before the legitimate packet arrives, permanently breaking the equality invariant and denying the intended recipient's callback forever, since the callback contract can only transfer the amount it received (not the attacker-donated dust).

### Finding Description
`IBCReceivePacketCallback` derives a deterministic "isolated address" for the token receiver via `types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)` [1](#0-0) . This address is a function only of the public destination channel ID and the packet sender's bech32 string, both known in advance to anyone observing the source chain or simply guessing a sender address that plans to use the callback feature.

After the destination contract's callback finishes executing, the keeper enforces:
```go
receiverTokenBalance := k.erc20Keeper.BalanceOf(ctx, erc20.ABI, tokenPair.GetERC20Contract(), receiverHex)
if receiverTokenBalance.Cmp(big.NewInt(0)) != 0 {
    return errorsmod.Wrapf(erc20types.ErrEVMCall, "receiver has %d unrecoverable tokens after callback", receiverTokenBalance)
}
``` [2](#0-1) 

This is a strict equality (must be exactly zero), analogous to GMX's strict `executionFee` equality that DEPU-1 flagged as griefable. Because the isolated address is:
1. Deterministic and predictable ahead of time, and
2. Reusable across multiple packets (keyed only by channel + sender, not by sequence/nonce),

an attacker can pre-fund the same ERC20 token (the one backing the token pair for the transferred denom) to that isolated address with a trivial dust amount (e.g., `1` unit) via a normal ERC20 `transfer`, *before* the legitimate IBC packet with a callback is received. The destination callback contract only ever transfers the amount it was allotted from the packet (via `approve`/`transferFrom` for `amountInt`, see the `approve` call at [3](#0-2) ), so it cannot know about or move the attacker's pre-existing dust. As a result, `receiverTokenBalance` will never return to exactly zero, and the check at line 236 will fail on every subsequent packet destined to that same isolated address, permanently.

### Impact Explanation
Because the isolated address is reusable and deterministic per (channel, sender) pair, this is not a one-off failure but a **permanent DoS** for that sender's destination-callback packets on that channel: every future receive callback to the same isolated address will revert with `ErrEVMCall`, causing the packet's receive-side application state to be reverted and an error acknowledgement returned (per the module's stated behavior for malformed callback packets) [4](#0-3) . This blocks legitimate cross-chain callback-based flows (e.g., swap/execute-on-receive patterns) indefinitely, and the code comment itself acknowledges the underlying danger this check was meant to prevent — "funds getting stuck in the isolated address, since they would become irretrievable" [5](#0-4)  — the exploit weaponizes the very invariant meant to protect against fund lock-up into a permanent lock-up/DoS vector for anyone the attacker targets. This qualifies under the "critical permanent freezing/locking of user funds or unauthorized extraction" and DoS-of-fund-flow impact classes, since a legitimate depositor's tokens intended for a contract flow will forever fail to be delivered via callback once the isolated address is poisoned.

### Likelihood Explanation
Likelihood is high: triggering the condition requires only a standard ERC20 `transfer` call to a publicly computable address, no special privileges, no front-running/race condition, and no cost beyond gas plus a dust amount of the target token. The attacker does not even need to know a specific pending packet — they can proactively poison isolated addresses for popular senders/channels ahead of time.

### Recommendation
Do not use a strict `== 0` post-condition on a deterministic, externally-fundable address to validate callback completion. Alternatives:
- Track and compare the *delta* introduced by the packet itself (snapshot balance before minting/crediting the isolated address, compare only the packet-specific increase was consumed), rather than requiring the absolute balance to be exactly zero.
- Make the isolated address single-use / unpredictable (e.g., derive from packet sequence number as well as sender+channel) so it cannot be pre-funded ahead of a specific packet, and sweep any pre-existing residual balance out before comparing.
- If a nonzero leftover balance is detected that predates the current packet, treat it as pre-existing dust to be swept/burned rather than an unconditional callback failure, so unrelated donations cannot indefinitely block the receiver's legitimate flow.

### Proof of Concept
1. Attacker observes (or picks) a target destination channel ID `C` and a Cosmos sender address `S` on the source chain that is expected to (or could) send ICS-20 transfers with destination callbacks.
2. Attacker computes `isolatedAddr = GenerateIsolatedAddress(C, S)` locally (function is exported/deterministic) [6](#0-5) .
3. Attacker acquires 1 unit of the native ERC20 token underlying the token pair that will back the transferred denom on the destination chain, and calls `transfer(isolatedAddr, 1)` directly against that ERC20 contract on the destination EVM chain.
4. Sender `S` later sends a legitimate ICS-20 transfer with a `dest_callback` memo targeting a contract; the packet is relayed and `IBCReceivePacketCallback` runs: it mints/credits the transferred amount to `isolatedAddr`, runs the contract callback which correctly `transferFrom`s the full packet amount out.
5. The post-check `k.erc20Keeper.BalanceOf(ctx, erc20.ABI, tokenPair.GetERC20Contract(), receiverHex)` now returns `1` (the attacker's leftover dust) instead of `0`, so the function returns `ErrEVMCall: "receiver has 1 unrecoverable tokens after callback"` [2](#0-1) , causing the receive callback (and thus the intended contract execution / fund delivery) to fail — and this failure recurs for every subsequent packet to the same isolated address, since the dust can never be cleared by the legitimate flow.

---
Note: I was unable to fully trace whether a failed `IBCReceivePacketCallback` also rolls back tokens already minted to the isolated address earlier in `OnRecvPacket` (i.e., whether tokens become truly stuck vs. refunded via error-ack on the source chain) due to index/context limits on the full `x/erc20/keeper/ibc_callbacks.go` `OnRecvPacket` flow and the caller that invokes `IBCReceivePacketCallback`. This affects whether the ultimate impact is "repeated DoS of the callback feature" (confirmed) or additionally "permanent fund loss" (unconfirmed) — starting a full Devin session with complete repository access would allow tracing this precisely.
