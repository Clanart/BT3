### Title
Missing rate limiting on `auction_submitBid` JSON-RPC endpoint allows unauthenticated DOS via signature-verification/tx-forwarding spam - (File: kaiax/auction/impl/api.go, kaiax/auction/impl/bid_pool.go)

### Summary
The `auction_submitBid` RPC method is reachable by any unauthenticated public-RPC caller and, unlike the P2P bid-gossip path, has no per-caller/per-IP rate limiting before performing expensive work (RLP decode, transaction forwarding, and dual ECDSA signature recovery). This mirrors the reported `settleFundingFees` bug class: a publicly callable, unprivileged entry point with no gating on repeated invocation, enabling resource-exhaustion DOS.

### Finding Description
`AuctionAPI.SubmitBid` is exposed as a public JSON-RPC method (`auction_submitBid`, see `console/web3ext/web3ext.go` binding) and is callable by any RPC client without authentication: [1](#0-0) 

Before any cost-limiting check occurs, the handler:
1. Decodes the raw target transaction via RLP (`toTx`) — attacker-controlled bytes.
2. Forwards the decoded transaction into the node's transaction pool via `api.a.Backend.SendTx(ctx, targetTx)`.
3. Constructs a `Bid` and calls `bidPool.AddBid`, which runs `validateBid`, performing two ECDSA signature recoveries (`validateBidSigs`) and other checks, before any pool-size or dedup rejection can short-circuit repeated attempts cheaply.

Compare this to the P2P bid-gossip path in `BidPool`, which explicitly implements a per-peer rate limiter to bound how often a single peer can push bids into this same expensive validation pipeline: [2](#0-1) 

The `AddBid`/`validateBid` pipeline that performs the RLP decode, signature checks, and locking is the same expensive path for both P2P messages and RPC calls, but only the P2P path is rate-limited by `bidsPerSecondPerPeer`/`peerRateLimiter`: [3](#0-2) 

The only "protection" for the RPC path is the global `maxBidPoolSize` check inside `insertBid` (executed only after `validateBid`'s signature checks already ran) and a duplicate-bid check, neither of which is a rate limiter and defaults to effectively unlimited (`DefaultMaxBidPoolSize = math.MaxInt64`): [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker can call `auction_submitBid` at an arbitrary rate directly over public RPC (bypassing the P2P `peerRateLimiter` entirely), forcing the node to repeatedly: RLP-decode arbitrary payloads, push decoded transactions into `SendTx`/the tx pool, and perform CPU-bound signature recovery — all while holding `bidMu` locks during `insertBid`/`validateBid`. Sustained spam degrades auction-module responsiveness and consumes CPU/lock contention on the consensus node (CN) running the auctioneer-adjacent module, potentially delaying legitimate bid processing and block-building for the auction/MEV path. This is a resource-exhaustion Denial-of-Service against a public-RPC-reachable module, matching the "unpriviledged caller can DOS a publicly reachable settlement/validation function due to missing throttling" bug class from the source report.

### Likelihood Explanation
High likelihood: `auction_submitBid` requires no special privileges, no proof-of-work, and no stake — only a syntactically well-formed `BidInput` (an attacker doesn't even need a *valid* bid; sufficient calls with garbage-but-well-formed sigs will still walk through decode + `SendTx` + `validateBidSigs` before being rejected). The RPC surface is reachable by any client with node RPC access, and nothing in `api.go`'s `SubmitBid` throttles call frequency the way the P2P ingestion path does.

### Recommendation
Apply the same (or a JSON-RPC-appropriate) per-caller rate limiting to `AuctionAPI.SubmitBid` that already exists for P2P bid messages (`peerRateLimiter`/`bidsPerSecondPerPeer`), ideally keyed by RPC client/IP or API key, and perform cheap validation (bid > 0, block-number range, data/gas-limit bounds) before the costly `SendTx` and signature-recovery steps so invalid/spam requests are rejected as early as possible.

### Proof of Concept
1. Obtain public RPC access to a CN running the auction module (`auction.disable=false`).
2. Repeatedly invoke `auction_submitBid` with syntactically valid but arbitrary `BidInput` payloads (valid-length signatures, arbitrary `TargetTxRaw`) in a tight loop, bypassing any P2P-level rate limiting since the call goes directly through the RPC endpoint.
3. Observe that each call triggers `toTx` (RLP decode), `Backend.SendTx`, and `bidPool.AddBid` → `validateBid` → `validateBidSigs` (ECDSA recovery), consuming CPU/lock time on every request regardless of ultimate rejection, with no throttling comparable to `bidsPerSecondPerPeer` applied to this RPC path.

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)

func (bp *BidPool) validateBid(bid *auction.Bid) error {
	blockNumber := bid.BlockNumber

	bp.bidMu.RLock()

	// Check if the auction tx is already in the pool.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		bp.bidMu.RUnlock()
		return auction.ErrBidAlreadyExists
	}

	// 1. The `bid.Sender` must not be in the winner list of the same block number if the new bid isn't equal to the previous bid.
	if bp.senderHasDifferentWinner(bid) {
		bp.bidMu.RUnlock()
		return auction.ErrBidSenderExists
	}
	bp.bidMu.RUnlock()

	curBlock := bp.Chain.CurrentBlock()
	if curBlock == nil {
		return auction.ErrBlockNotFound
	}

	// 2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
	curNum := curBlock.NumberU64()
	if blockNumber <= curNum || blockNumber > curNum+allowFutureBlock {
		return auction.ErrInvalidBlockNumber
	}

	// 3. The `bid.Bid` must be greater than 0.
	if bid.Bid.Sign() <= 0 {
		return auction.ErrZeroBid
	}

	// 4. The data size must be less than the maximum limit.
	if uint64(len(bid.Data)) > BidTxMaxDataSize {
		return auction.ErrExceedMaxDataSize
	}

	// 5. The gas limit must be less than the maximum limit.
	if bid.CallGasLimit > BidTxMaxCallGasLimit {
		return auction.ErrExceedMaxCallGasLimit
	}

	// 6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.
	if err := bp.validateBidSigs(bid); err != nil {
		return err
	}

	return nil
}
