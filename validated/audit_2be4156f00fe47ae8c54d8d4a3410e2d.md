## Title
First reward computed for a newly-onboarded state machine treats an uninitialized `previous_commitment_height` of `0` as the reward baseline, causing massive over-payment of relayer rewards from the treasury - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`Pallet::calculate_reward` in `pallet-consensus-incentives` computes a relayer's reward as `(latest_height - baseline) * block_cost`, where `baseline` falls back to `previous_commitment_height` when no watermark has been recorded yet. `previous_commitment_height` is backed by `PreviousStateMachineHeight`, which pallet-ismp seeds via `unwrap_or_default()` (i.e. `0`) on the very first `store_latest_commitment_height` call for any state machine. Consequently, the first-ever reward paid for a newly onboarded chain is computed as `latest_height - 0`, i.e. the relayer is rewarded for every block from genesis height `0` up to the chain's actual (possibly very large) initial height, instead of the real span of the single consensus update being processed. This directly mirrors the Gearbox `_timestampLU == 0` class of bug: an uninitialized/default value silently substitutes for a real "last update" reference and corrupts a financial calculation.

### Finding Description
`calculate_reward` reads: [1](#0-0) 

`previous_commitment_height` is implemented as a plain storage read with no "unset" guard beyond `Option`: [2](#0-1) 

But `PreviousStateMachineHeight` is populated as soon as the *first* commitment height is ever stored for a state machine, using `unwrap_or_default()` on the previously-empty `LatestStateMachineHeight`: [3](#0-2) 

This means that by the time `process_message` / `calculate_reward` runs for the very first `StateMachineUpdated` event of a state machine (the consensus handler stores the commitment height before the reward code runs), `previous_commitment_height` already returns `Some(0)` rather than `None`. Since `LastRewardedHeight` is also unset on the first reward, `baseline` resolves to `0`: [4](#0-3) 

`blocks = latest_height.saturating_sub(0) = latest_height`, so the relayer is paid `latest_height * block_cost` — the entire historical height of the chain being onboarded — for submitting a single consensus proof, rather than the intended per-block cost of the actual update span.

### Impact Explanation
This is a direct loss-of-funds bug against the protocol treasury. `T::Currency::transfer` moves `reward` from `TreasuryAccount` to the relayer: [5](#0-4) 

For any state machine onboarded at a non-trivial height (which is the normal case — a new L1/L2 client is typically registered starting from whatever height the chain is currently at, often in the hundreds of thousands or millions of blocks), the very first relayer to submit a valid consensus proof receives a reward sized to the entire chain history instead of one update's worth of blocks. This can drain or substantially deplete the treasury in a single extrinsic, with no admin/governance/malicious-relayer assumption required — any relayer who is first to deliver the (legitimate) consensus proof for a newly configured `StateMachinesCostPerBlock` entry triggers it.

### Likelihood Explanation
This fires deterministically, not as an edge case: every time governance configures a new state machine for consensus incentives (a routine onboarding operation) and the first legitimate `StateMachineUpdated` event is processed, `LastRewardedHeight` and the "true previous height" are both effectively `0`/absent, so the bug is guaranteed to trigger on that first payout. No race condition, malicious actor, or rare timing is needed — only a normal relayer submitting the first honest consensus update after onboarding.

### Recommendation
Distinguish "no prior commitment recorded" from "prior commitment height was 0" instead of overloading `unwrap_or_default()`. Concretely:
- Change `previous_commitment_height` (and/or `calculate_reward`) to treat a genuinely first-ever update (no `LastRewardedHeight` and no real previous height) as rewarding a bounded/zero span, e.g. by tracking an explicit "first commitment height" separate from `PreviousStateMachineHeight`, or by seeding `LastRewardedHeight` with `latest_height` (not `previous_height`) whenever the state machine is first registered for incentives, so the first reward pays only for blocks that arrive *after* registration.
- Alternatively, cap `baseline` at `latest_height.saturating_sub(reasonable_max_span)` to bound any single payout regardless of how storage was initialized.

### Proof of Concept
1. Governance registers a new state machine and calls `set_state_machine_cost_per_block(state_machine_id, block_cost)` (populating `StateMachinesCostPerBlock`).
2. A relayer submits the first-ever valid consensus proof for that state machine, whose light client reports the chain currently at height `H` (e.g. `H = 2_000_000`, a normal onboarding height for an existing chain).
3. `pallet-ismp`'s consensus handler calls `store_latest_commitment_height({id, height: H})`, which reads `LatestStateMachineHeight::get(id) = None → unwrap_or_default() = 0`, then sets `PreviousStateMachineHeight::insert(id, 0)` and `LatestStateMachineHeight::insert(id, H)`.
4. `on_executed` → `process_message` → `calculate_reward` runs: `latest_height = H`, `previous_height = previous_commitment_height(id) = Some(0)`, `baseline = LastRewardedHeight::get(id).unwrap_or(0) = 0`.
5. `blocks = H - 0 = H`; `reward = H * block_cost`, transferred from the treasury to the relayer in one call — instead of the intended reward for a single update.

	fn store_latest_commitment_height(&self, height: StateMachineHeight) -> Result<(), Error> {
		let previous_height = LatestStateMachineHeight::<T>::get(height.id).unwrap_or_default();
		PreviousStateMachineHeight::<T>::insert(height.id, previous_height);
		LatestStateMachineHeight::<T>::insert(height.id, height.height);
		Ok(())
	}
