### Title
Missing wallet-ownership check on `target_coin_id` in `FungibilityManager.split_coins()` allows coin selection across wallets - ([File: chia/wallet/fungibility_manager.py])

### Summary
`FungibilityManager.split_coins()` looks up the coin to split purely by `target_coin_id`, with no filter tying that coin to the `wallet` the caller specified, unlike the sibling `combine_coins()` path which explicitly scopes its coin lookup with `wallet_id=wallet.id()`.

### Finding Description
`split_coins()` resolves the target coin with: [1](#0-0) 

This call to `self.coin_store.get_coin_record(target_coin_id)` has no `wallet_id` predicate — it will return any coin record present in the local `WalletCoinStore`, regardless of which `wallet_id` owns it, as long as the hex id matches. The returned coin is then used directly as the input to `wallet.generate_signed_transaction(...)` for whatever `wallet` object the RPC layer resolved from `get_fungible_wallet(wallet_id)`: [2](#0-1) [3](#0-2) 

Contrast this with `combine_coins()` in the same class, which correctly binds the coin lookup to the calling wallet: [4](#0-3) 

The BBB bug class is exactly this shape: an identifier (`presentationId` / here `target_coin_id`) is accepted and used to fetch/act on an object without checking that the object actually belongs to the caller-specified parent scope (`meetingId` / here `wallet_id`). `RemovePresentationPubMsgHdlr.scala` skipped the meeting-ownership check before deletion; `split_coins()` skips the wallet-ownership check before selecting the coin to spend.

### Impact Explanation
If a `target_coin_id` belonging to a different wallet (e.g. a CAT wallet's coin, or another standard wallet under the same key ring) is supplied while `wallet_id` points at an unrelated wallet, `split_coins()` will still accept the coin as a spend input for that unrelated wallet's `generate_signed_transaction()` call, mixing coin selection state (`interface.side_effects.selected_coins`) and fee/output accounting across wallets that the caller did not actually authorize for that operation. This breaks the invariant — relied on throughout `combine_coins()`, RPC coin-selection filtering (`HashFilter`, `wallet_id=wallet.id()`), and the wallet's balance/coin-selection bookkeeping — that coin lookups performed on behalf of one wallet are scoped to that wallet's own coin set.

### Likelihood Explanation
Any RPC caller who can invoke the wallet's split-coins action (a wallet user/local RPC caller reaching `FungibilityManager.split_coins`) can trivially trigger this by passing a `target_coin_id` that exists in the coin store under a different `wallet_id` than the one specified. No special privileges beyond normal wallet RPC access are needed, and the mismatch is not caught anywhere before the coin is committed to `generate_signed_transaction`.

### Recommendation
Scope the coin lookup in `split_coins()` the same way `combine_coins()` does, e.g. by fetching through `get_coin_records(wallet_id=wallet.id(), coin_id_filter=HashFilter.include([target_coin_id]))` (or otherwise validating `coin_record.wallet_id == wallet.id()`) before using the coin, and reject the request if the coin does not belong to the specified wallet.

### Proof of Concept
1. Have two wallets under the same key (`wallet_id=1` standard, `wallet_id=2` CAT/standard) each with confirmed coins.
2. Call the split-coins RPC with `wallet_id=1` but `target_coin_id` set to the coin name of a coin actually owned by `wallet_id=2`.
3. Observe that `FungibilityManager.split_coins()` (`chia/wallet/fungibility_manager.py:41-51`) successfully fetches the coin via `coin_store.get_coin_record(target_coin_id)` with no ownership check, then proceeds to select/spend it as if it belonged to wallet 1 — confirming the missing scope check that `combine_coins()` otherwise enforces.
