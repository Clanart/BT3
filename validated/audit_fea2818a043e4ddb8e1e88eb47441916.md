### Title
Malformed blame accusation can panic PedPoP blame resolution - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` accepts `Participant` identifiers that are not verified to be within the DKG's `1..=n` participant set. A participant can submit a blame accusation naming a nonexistent sender such as `n + 1`; after proof verification, `blame_internal` indexes `self.commitments[&sender]` without checking membership, causing a panic. This mirrors CVE-2017-8891's malformed-input crash class, applied to Serai's participant-index handling.

### Finding Description
`Participant::new` rejects zero but permits every other `u16` value. `AdditionalBlameMachine::new` registers commitments only for participants `1..=n` and stores them in `commitments`. Neither `blame_internal` nor its public callers validate that `sender` and `recipient` are registered participants. When a valid recipient and proof are supplied, execution reaches `self.commitments[&sender]`, which panics if the accused sender is outside the registered set. ### Impact Explanation
A malicious or faulty DKG participant can cause an honest participant or external blame evaluator to crash while processing an accusation. In a validator, relayer, or wallet process that evaluates blame messages, this provides a remotely reachable denial of service against the DKG recovery/blame path.

### Likelihood Explanation
The attacker controls the `sender`, `recipient`, encrypted message, and optional `EncryptionKeyProof` arguments to `blame`. They can choose a valid recipient, name an unregistered sender such as `Participant::new(n + 1).unwrap()`, and provide a proof/message pair that passes the earlier checks; the subsequent unchecked map access then panics.

### Recommendation
Validate that both `sender` and `recipient` are registered participants before decrypting or evaluating the share. Because `blame` returns a `Participant` rather than an error, an out-of-range sender should be treated as faulty or the API should be changed to return a dedicated `InvalidParticipant` error. The equivalent lookup for `decryptor` in `decrypt_with_proof` should also use `get` and return `DecryptionError` instead of indexing unconditionally.

### Proof of Concept
Conceptually, for a DKG with `n` participants:

```rust
let bogus_sender = Participant::new(n + 1).unwrap();
let valid_recipient = Participant::new(1).unwrap();

// `machine` is an AdditionalBlameMachine initialized for participants 1..=n.
// `msg` carries a valid PoP for `bogus_sender`, and `proof` is a valid
// EncryptionKeyProof for `valid_recipient`'s registered encryption key.
machine.blame(
    bogus_sender,
    valid_recipient,
    msg,
    Some(proof),
);
```

Execution passes the proof path and reaches `self.commitments[&bogus_sender]`, causing an out-of-bounds `HashMap` indexing panic because `AdditionalBlameMachine::new` populated only `1..=n`.
