### Title
Type-change (`T`) git status codes are unhandled and silently mis-classified as ordinary "modified" changes - (File: `app/src/lib/status-parser.ts`)

### Summary
`mapStatus()` in `app/src/lib/status-parser.ts` maps the two-character `XY` status code Git reports for a path to Desktop's internal `FileEntry` representation using a long chain of `if (statusCode === '...')` checks, ending in an unconditional fallback that always treats any *unrecognized* code as an ordinary modification. Git's porcelain v2 format allows `T` (type-change) as one of the valid status characters, and Desktop's own parsing regex explicitly permits it, but `mapStatus` never has a branch for `T.`, `.T`, `MT`, `TM`, or any other combination containing `T`. This is structurally the same bug class as the reported `numElements` issue: a lookup/dispatch table that is complete for the "known" initial cases but silently defaults for a legitimate case the author didn't enumerate, and that default is treated as safe/normal rather than being rejected or flagged.

### Finding Description
`app/src/lib/status-parser.ts:102-103` shows the regex Desktop uses to parse `git status --porcelain=v2 -z` output for ordinary changed entries: [1](#0-0) 
`T` (typechange) is explicitly part of the accepted character class, confirming Desktop expects Git to be able to emit it (e.g. when a tracked file changes from a regular file to a symlink, or from a regular file/directory to a submodule gitlink, or vice versa).

`mapStatus()` (`app/src/lib/status-parser.ts:201-426`) then enumerates every combination it knows how to handle — `.M`, `M.`, `.A`, `A.`, `.D`, `D.`, `R.`, `.R`, `C.`, `.C`, `AD`, `AM`, `RM`, `RD`, `DD`, `AU`, `UD`, `UA`, `DU`, `AA`, `UU` — but no combination involving `T` is present anywhere in that function: [2](#0-1) 

When none of the explicit checks match, execution reaches the fallback: [3](#0-2) 
`// as a fallback, we assume the file is modified in some way` — this silently discards the actual semantics of the status code (that the file's *type* changed, not just its content) and returns a generic `OrdinaryEntry` with `type: 'modified'`. Downstream, `convertToAppStatus()` in `app/src/lib/git/status.ts` (lines 129-152) reads `entry.type` and, for `'modified'`, produces `{ kind: AppFileStatusKind.Modified, submoduleStatus }` — a completely ordinary "Modified" label in the Changes list, with no indication that the underlying object type differs (e.g. a plain file becoming a symlink, or becoming a submodule pointer).

### Impact Explanation
A type change is one of the more security-sensitive kinds of git change: converting a tracked file into a symlink can be used to make Desktop/Git write into or read from an unexpected filesystem location on checkout, and converting a path into a submodule gitlink changes what remote/commit gets fetched. Because the type-change status codes fall into the generic "modified" bucket:
- The user sees only "Modified" in the Changes list, with no differentiation from a normal content edit, and it is included by default under Desktop's "select all" staging behavior.
- If the user commits and pushes without noticing (nothing in the UI singles out the type-change nature of the diff), they silently commit/propagate the type change — this is exactly "silent corruption of what the user commits or pushes."
- Because a real security-relevant transition (file → symlink, file → submodule) is mislabeled as ordinary content modification, a user reviewing a PR branch or a fetched fork in Desktop has reduced ability to notice something unusual is happening to the file's nature.

### Likelihood Explanation
Triggering this requires nothing beyond ordinary Desktop workflows: an attacker only needs to have the victim clone/fetch a repository or check out a branch/PR (a completely standard, unprivileged interaction) that contains a commit converting a tracked path's type (e.g. replacing a regular file with a symlink, or turning a directory into a submodule gitlink). Git will then report `T`-bearing status codes for that path, and Desktop's status-parsing logic reaches the fallback deterministically — there is no error, exception, or guard that stops this path; it is a silent default.

### Recommendation
Add explicit handling for all `T`-containing status codes (`T.`, `.T`, `MT`, `TM`, and any others Git's docs define) in `mapStatus()`, mapping them to a distinct, clearly surfaced status (e.g. a `TypeChanged` `AppFileStatusKind` or an explicit flag on `OrdinaryEntry`) rather than falling through to the generic "modified" fallback. The UI (`changed-file.tsx`, `file-list.tsx`, `diff-header.tsx`, etc.) should visually call out type changes so users are not misled into treating them as benign content edits. More generally, the final fallback in `mapStatus` should log/warn on genuinely unrecognized codes instead of silently normalizing them to "modified," so future unhandled Git status combinations fail loudly rather than corrupting classification.

### Proof of Concept
1. Attacker creates/controls a repository (or a branch/fork a victim will fetch or check out in Desktop) containing:
   - Commit A: a regular tracked file `payload.txt`.
   - Commit B: `payload.txt` deleted and replaced by a symlink of the same name pointing to an arbitrary path (or the path converted into a submodule pointing to an attacker-controlled remote).
2. Victim uses Desktop to fetch/checkout the branch containing commit B, then reverts/edits locally such that Git reports a `T`-bearing porcelain v2 status line for `payload.txt` (e.g. `1 .T N... 100644 100644 120000 <hash> <hash> payload.txt`, or `1 MT ...` if also staged and altered).
3. `parsePorcelainStatus`/`parseChangedEntry` in `app/src/lib/status-parser.ts` parses this into `statusCode: '.T'` (allowed by the regex at line 103).
4. `mapStatus('.T', ...)` checks every branch from lines 208-418, none matches `.T`, and control falls through to the lines 420-425 fallback, returning `{ kind: 'ordinary', type: 'modified', submoduleStatus }`.
5. `convertToAppStatus` in `app/src/lib/git/status.ts` labels this `AppFileStatusKind.Modified` with no special marker, so the file shows in Desktop's Changes list as a normal "Modified" file, selected by default for commit, giving the victim no visual signal that they are about to commit a file-type change (e.g. a symlink or submodule swap) potentially crafted by the attacker.

Note: I could not find any unit test in the repository specifically covering `T`-containing status codes (search of `status-utils-test.ts` and related tests turned up no matches for `MM`/`MT`/`TM` scenarios), which is consistent with this path being unexercised/unhandled rather than intentionally rejected elsewhere in the codebase.
