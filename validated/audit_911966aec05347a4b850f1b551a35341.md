### Title
Hardcoded STX price feed used to price BTC-denominated `stSTXbtc`/`zstSTXbtc` assets — ([File: mainnet/contracts/utility/v0-1-data.clar])

### Summary
`get-asset-price` in `mainnet/contracts/utility/v0-1-data.clar` prices the `stSTXbtc` and `zstSTXbtc` assets by calling `get-pyth-price PYTH-STX` (the STX/USD feed) while the surrounding code, comments, and variable names (`btc-price`) all indicate the intent was to fetch the BTC/USD feed (`PYTH-BTC`). This is a "price attached to the wrong asset" defect, directly analogous to the undocumented/uninspected math class the external Augur report flags — an unreviewed, undocumented pricing calculation hid an asset/feed mismatch.

### Finding Description
`get-asset-price` resolves prices per asset id via a chain of `if` branches: [1](#0-0) 

Both the `stSTXbtc` branch and the `zstSTXbtc` branch call `(get-pyth-price PYTH-STX)`, even though the comments explicitly say "BTC price" and the local binding is named `btc-price`. Every other BTC-denominated asset in the same function (`sBTC`, `zsBTC`) correctly calls `PYTH-BTC`: [2](#0-1) [3](#0-2) 

This function feeds directly into the position-valuation and health-verdict logic of the same contract: [4](#0-3) [5](#0-4) 

which are then consumed by `get-user-position` to compute `total-collateral-usd`, `total-debt-usd`, `current-ltv`, `health-factor`, and `is-liquidatable`: [6](#0-5) 

Since BTC/USD (tens of thousands of dollars) is orders of magnitude larger than STX/USD (roughly $0.50–$2), any position holding `stSTXbtc` or `zstSTXbtc` as collateral will be valued at a tiny fraction of its real USD value by this function, and any such debt would similarly be understated by orders of magnitude.

### Impact Explanation
The bug produces a materially wrong health verdict (`health-factor`, `current-ltv`, `is-liquidatable`) for any account holding `stSTXbtc`/`zstSTXbtc`. If this data path is consumed to gate borrowing, withdrawal, or liquidation decisions (e.g., by front-end tooling or off-chain liquidator bots that trust `get-user-position`), it could cause: (a) legitimately liquidatable BTC-collateralized positions to be reported as healthy (permanent/temporary freezing of the ability to liquidate undercollateralized debt, i.e., protocol insolvency risk), or (b) healthy positions with `stSTXbtc` debt being flagged as unhealthy. I was not able to fully confirm, within the available indexed code, whether any state-changing function in `mainnet/contracts/market/v0-4-market.clar` itself calls into this `v0-1-data.clar` helper for on-chain enforcement, or whether this contract is purely a read-only reporting/analytics layer separate from the market's own price-resolution path (which is driven by the per-asset oracle config in the assets registry rather than these hardcoded constants). This distinction materially affects severity — if consumed only by off-chain tooling, the impact is limited to incorrect information rather than fund loss; if any on-chain logic trusts this contract's health/price output, the impact rises to Critical (protocol insolvency / theft via mispriced collateral).

### Likelihood Explanation
Likelihood is high that this exact miscalculation triggers on any mainnet position involving `stSTXbtc` or `zstSTXbtc`, since the wrong constant is unconditionally used whenever those asset ids are queried — no special attacker action is required to trigger the wrong computation itself.

### Recommendation
Change both branches to use `PYTH-BTC` instead of `PYTH-STX`:
```clarity
(if (is-eq aid stSTXbtc) (default-to u0 (get-pyth-price PYTH-BTC))
(if (is-eq aid zstSTXbtc)
    (let ((btc-price (default-to u0 (get-pyth-price PYTH-BTC)))
          (lindex (get-vault-liquidity-index stSTXbtc)))
      (mul-div-down btc-price lindex INDEX-PRECISION))
```
Additionally, confirm (and document) whether `get-user-position`/`get-asset-price` in `v0-1-data.clar` is consumed by any state-changing contract logic; if so, add tests asserting parity between this helper's computed price and the market contract's own `price-resolve` output for every registered asset, to prevent silent divergence between the two pricing implementations.

### Proof of Concept
1. Register `stSTXbtc` and `zstSTXbtc` per the mainnet asset registry (as done in `mainnet/contracts/proposals/mainnet/v0-init.clar`).
2. Have a user deposit `stSTXbtc` as collateral and/or borrow it as debt.
3. Call `get-user-position` (or `get-asset-price` directly) for that account.
4. Observe the returned USD notional for the `stSTXbtc`/`zstSTXbtc` leg uses the STX/USD Pyth price (~$0.50–$2) rather than the BTC/USD Pyth price (tens of thousands of dollars), producing a `total-collateral-usd`/`total-debt-usd`, `current-ltv`, and `is-liquidatable` verdict that is wrong by orders of magnitude relative to the asset's real value.
