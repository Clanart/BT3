### Title
Deep-link `filepath` parameter is never validated for path traversal while sibling `branch`/`pr` parameters are - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` in `app/src/lib/parse-app-url.ts` parses the `x-github-client://openRepo/...` and `github-mac://openRepo/...` deep-link scheme that Desktop registers as its default handler. It applies targeted validation to some of the attacker-controlled query parameters (`branch`, `pr`) but leaves `filepath` completely unvalidated before returning it as part of the `IOpenRepositoryFromURLAction`, which is later consumed to open a file after cloning/opening the target repository. This mirrors the bug class in the referenced report: the function accepts several untrusted parameters as part of one action, validates some (tokenOut/minOut-equivalent: `branch`, `pr`), but omits validation for another (receiver-equivalent: `filepath`) that ultimately controls where an operation resolves to.

### Finding Description
`parseAppURL` explicitly sanitizes two of the four action parameters coming from an attacker-controlled deep link: [1](#0-0) 

- `pr` must match `/^\d+$/`.
- `branch` is checked with `testForInvalidChars`.

But `filepath` is read straight from the query string with no format, character, or path-traversal check and passed through untouched: [2](#0-1) 

This action is dispatched from `dispatchURLAction` directly to repository-opening logic: [3](#0-2) 

Because the entire `url`, `branch`, `pr`, and `filepath` bundle originates from a link an attacker can get a victim to click (e.g., a "Open this project in GitHub Desktop" link with `filepath=..%2F..%2F..%2F.ssh%2Fid_rsa` or similar traversal payload), and only `branch` gets a character-class check (via `testForInvalidChars`, intended for git ref names, not filesystem paths), the `filepath` value can contain `../` segments, absolute-path-like segments, or other characters that a naive `Path.join(repositoryPath, filepath)` downstream would not neutralize. This is analogous to `preSign` accepting an unvalidated `orderUid`/`receiver` while only informally checking other order fields — some inputs in the same trust boundary get scrutiny, others don't, and the omitted one is the one that determines the ultimate target of a sensitive operation (file resolution/opening vs. fund destination).

### Impact Explanation
If the code path that consumes `filepath` (post-clone "open this file" step wired through `dispatchURLAction`/`openRepositoryFromUrl`) joins it onto the repository's working directory without canonicalizing and verifying it remains inside the repo root, an attacker-crafted deep link can cause Desktop to open/reveal a file outside the intended repository directory — a path-traversal read/disclosure or unintended-file-open primitive triggered purely by a link click, matching the "attacker controls a link the user clicks" and "read outside the repo" impact categories in scope.

### Likelihood Explanation
Likelihood is elevated because: (1) the URL protocol handler is the officially registered Desktop deep-link scheme and requires only a user click, no prior local access; (2) the parser demonstrates the developers are already aware attacker-supplied query parameters need sanitization (they did it for `branch` and `pr`), which increases confidence that `filepath` was simply missed rather than intentionally left permissive; (3) unlike `branch`, which is constrained to valid git ref syntax, there is no equivalent structural constraint on a filesystem path that would incidentally block traversal sequences.

### Recommendation
Apply the same defensive posture used for `branch`/`pr` to `filepath`: reject any value containing `..` path segments, drive-letter/absolute-path prefixes, null bytes, or other path-control characters, and independently re-verify (at the consumption site) that `Path.resolve(repoPath, filepath)` still starts with `repoPath` before performing any file-system operation — do not rely solely on the parser-level check.

### Proof of Concept
1. Attacker hosts a link (e.g., on a webpage or in a README) of the form:
   `x-github-client://openRepo/https://github.com/attacker/public-repo?branch=main&filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
2. Victim, who has GitHub Desktop installed and registered as the handler for `x-github-client://`, clicks the link.
3. `parseAppURL` accepts the request because `branch=main` passes `testForInvalidChars` and `filepath` is not checked at all: [4](#0-3) 
4. `dispatchURLAction` routes the resulting `open-repository-from-url` action to the repository-opening flow: [3](#0-2) 
5. If the downstream consumer resolves `filepath` relative to the freshly cloned repository directory without bounds-checking, the traversal sequence escapes the repo directory.

Note: I was unable to retrieve the exact implementation body of `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` (the specific line range containing the file-open sink) within the available tool budget, so the precise consumption of `filepath` (and whether any additional bounds-check exists there) is not fully confirmed from the index. This should be verified directly in a full Devin session before treating the impact severity as final.
