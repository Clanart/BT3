### Title
Removing a repository leaves its `GitStore` and `IRepositoryState` cached under the reused path hash, causing stale git state to be reused by a subsequently added repository at the same path - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`AppStore._removeRepository()` deletes the repository record from `RepositoriesStore` but never evicts the corresponding entries from `GitStoreCache` or `RepositoryStateCache`, both of which are keyed by `repository.hash` (derived from the repository path). If the user later adds/clones a different repository at the same filesystem path, Desktop will reuse the stale in-memory `GitStore`/`IRepositoryState` instead of loading fresh state from the new repository, mirroring exactly the reported bug class: an entity is removed from one collection but a parallel, keyed cache retains a stale entry that later gets misattributed to a new entity sharing the same key.

### Finding Description
`_removeRepository` only touches the persistent store and cloning-repository bookkeeping: [1](#0-0) 

`RepositoriesStore.removeRepository` deletes the DB row and clears the `localStorage` "tags to push" entry, but this is a different store than the in-memory caches: [2](#0-1) 

Meanwhile `GitStoreCache` keeps a `Map<string, GitStore>` keyed by `repository.hash`, and only evicts an entry when `.remove()` is explicitly called - which `_removeRepository` never does: [3](#0-2) [4](#0-3) 

Likewise `RepositoryStateCache` keeps a `Map<string, IRepositoryState>` keyed by `repository.hash`, and exposes no delete/remove method at all - the only mutation resembling removal is `transferState`, used for worktree renames, not for repository deletion: [5](#0-4) [6](#0-5) 

Because `repository.hash` is derived from the repository's path (not a fresh UUID per add), if the underlying directory at that path is later populated with a different git repository (e.g. the user removes the Desktop entry without moving the folder to trash, then clones or opens a new/attacker-supplied repository into the exact same directory), a call to `gitStoreCache.get(repository)` or `repositoryStateCache.get(repository)` for the "new" `Repository` object will return the **stale `GitStore`/`IRepositoryState` instance from the previous repository** rather than constructing fresh state, because the cache still has an entry for that hash key that was never evicted.

This is the direct analog of the `AggregateStablePrice.remove_price_pair()` bug: removing an entity from the primary collection (`repositories` table / `price_pairs`) without removing the associated entry in a parallel keyed collection (`gitStores` / `repositoryState` maps ↔ `last_tvl` array), leaving stale data that gets silently reused against the wrong entity later.

### Impact Explanation
If stale `GitStore` state (branches, tip, tags-to-push, history, commit lookups) from a previously removed repository is served for a new repository that a user opens/clones at the same path, Desktop's UI can present branch/tip/history information that does not correspond to the actual on-disk git content. Operations that trust this cached state - e.g., determining the current branch tip before a push, showing "ahead/behind," or fast-forwarding branches - could act on incorrect assumptions, resulting in the user unknowingly pushing, committing, or fast-forwarding relative to the wrong reference state. This matches the "silent corruption of what the user commits or pushes" impact category, since none of it is visible to the user as an error - the stale cache is simply served transparently.

### Likelihood Explanation
This requires a specific but realistic workflow: the user removes a repository from Desktop (the default "Remove" flow does not move the folder to trash), and then adds/clones a different repository into the exact same local path - either intentionally or because an attacker-controlled repository is fetched/cloned into a path previously used by Desktop. There is no explicit guard in `_removeRepository` or in `gitStoreCache.get`/`repositoryStateCache.get` that detects a path/hash reuse and forces a cache invalidation, so nothing in the existing code stops the stale-state reuse once the same hash recurs.

### Recommendation
In `AppStore._removeRepository` (`app/src/lib/stores/app-store.ts`), call `this.gitStoreCache.remove(repository)` and add/expose a corresponding removal method on `RepositoryStateCache` (`app/src/lib/stores/repository-state-cache.ts`) and invoke it, mirroring the existing `clearTagsToPush` cleanup already performed in `RepositoriesStore.removeRepository`. This ensures that removing a repository fully purges all keyed caches associated with its `hash`, so any later repository added at the same path always starts from freshly loaded git state.

### Proof of Concept
1. Open repository `R1` at path `/Users/x/project` in Desktop; this populates `GitStoreCache` and `RepositoryStateCache` entries keyed by the hash of `/Users/x/project`.
2. Remove `R1` from Desktop via `_removeRepository(repository, moveToTrash: false)` - the folder on disk is left intact, and neither cache is cleared: [7](#0-6) 
3. Delete/replace the contents of `/Users/x/project` on disk with a different repository `R2` (e.g., by removing the old `.git` and cloning `R2` into the same path, or having a colluding/compromised process do so).
4. Add `/Users/x/project` (now containing `R2`) back to Desktop. Since `repository.hash` depends on path, `gitStoreCache.get(repository)` and `repositoryStateCache.get(repository)` return the previously cached `GitStore`/`IRepositoryState` for `R1` instead of building fresh state for `R2`, per: [8](#0-7) [9](#0-8) 
5. Desktop displays stale branch/tip/history data from `R1` for what is actually `R2`'s working directory, and any push/fetch/fast-forward action performed while this stale state is in effect operates against incorrect assumptions about the current tip.

import { GitStore } from './git-store'
import { Repository } from '../../models/repository'
import { IAppShell } from '../app-shell'
import { IStatsStore } from '../stats'

export class GitStoreCache {
  /** GitStores keyed by their hash. */
  private readonly gitStores = new Map<string, GitStore>()

  public constructor(
    private readonly shell: IAppShell,
    private readonly statsStore: IStatsStore,
    private readonly onGitStoreUpdated: (
      repository: Repository,
      gitStore: GitStore
    ) => void,
    private readonly onDidError: (error: Error) => void
  ) {}

  public remove(repository: Repository) {
    if (this.gitStores.has(repository.hash)) {
      this.gitStores.delete(repository.hash)
    }
  }

  public get(repository: Repository): GitStore {
    let gitStore = this.gitStores.get(repository.hash)
    if (gitStore === undefined) {
      gitStore = new GitStore(repository, this.shell, this.statsStore)
      gitStore.onDidUpdate(() => this.onGitStoreUpdated(repository, gitStore!))
      gitStore.onDidError(error => this.onDidError(error))

      this.gitStores.set(repository.hash, gitStore)
    }

    return gitStore
  }

  /**
   * Move the entire cached state for a repository from one identity to another.
   *
   * This is used when a worktree is renamed: the repository's path (and
   * therefore its hash) changes, but it still refers to the same working
   * directory, so all of the existing in-memory state (working directory
   * changes, commit message, history, etc.) should be carried over to the new
   * identity rather than reset to its initial values.
   */
  public transferState(source: Repository, target: Repository) {
    if (source.hash === target.hash) {
      return
    }

    const sourceState = this.repositoryState.get(source.hash)
    if (sourceState === undefined) {
      return
    }

    this.repositoryState.set(target.hash, sourceState)
    this.repositoryState.delete(source.hash)
  }
