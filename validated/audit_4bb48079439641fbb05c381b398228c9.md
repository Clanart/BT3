## Title
`EvmHost.dispatch()`/`fundRequest()` permanently trap unspent native-token change instead of refunding the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
Every place in the Hyperbridge apps layer (`IntentGatewayV2.sol`, `ExtrinsicIntents.sol`, `IntrinsicIntents.sol`) that performs a `swapETHForExactTokens` for fee payment explicitly tracks the leftover `msgValue` and refunds it to the caller. `EvmHost.sol`, the core protocol contract, performs the exact same pattern but never refunds the leftover ETH, so it accumulates in the host contract and is only reachable through the governance-gated `hostManager`/`WithdrawAssets`-style flow, not by the payer who overpaid.

### Finding Description
`dispatch(DispatchPost memory post)`, `dispatch(DispatchGet memory get)`, and `fundRequest(bytes32 commitment, uint256 amount)` in `evm/src/core/EvmHost.sol` all follow this pattern when `msg.value > 0`: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
}
```

The same code shape repeats for `dispatch(DispatchGet)` [2](#0-1)  and `fundRequest` [3](#0-2) .

Standard `UniswapV2Router02.swapETHForExactTokens` refunds any unspent `msg.value` to its immediate caller (`safeTransferETH(msg.sender, ...)`). Because `EvmHost` itself is the caller of the router (the router is invoked from inside `EvmHost`, not by the original transaction sender), any dust refund from the swap is sent back to `address(EvmHost)`, not to `_msgSender()` — the actual user who sent the over-provisioned `msg.value`. This is structurally identical to the reported `SwapRouter` bug: the contract computes/requests an exact amount but the caller must send ETH up front, and slippage/exact-output mechanics leave unspent ETH stuck in the contract rather than returned to the payer.

Unlike the app-layer contracts, which explicitly compute `msgValue -= amounts[0]` and issue `msg.sender.call{value: msgValue}("")` at the end (see `IntentGatewayV2.sol` [4](#0-3) , `ExtrinsicIntents.sol` [5](#0-4) ), `EvmHost.sol` has no equivalent refund step anywhere in `dispatch()` or `fundRequest()`.

The only party that could ever recover this trapped native balance is the privileged `hostManager` (a governance-controlled `IApp` that receives cross-chain admin requests to withdraw host revenue), per `HostParams.hostManager` in the struct comment: "receives governance requests from the Hyperbridge chain to ... withdraw revenue from the host" [6](#0-5) . There is no unprivileged path for the original payer to reclaim their own overpaid ETH.

### Impact Explanation
Any unprivileged user or app calling `dispatch()` with a native `msg.value` slightly greater than the exact amount the swap consumes (which is unavoidable in practice, since callers must estimate `swapETHForExactTokens`'s input requirement off-chain before the transaction, and Uniswap price movement between estimation and execution is normal) permanently loses the difference — it is swept into `EvmHost`'s balance and effectively becomes host/protocol revenue, extractable only by governance. This is a direct loss of user funds on every native-fee POST/GET dispatch or `fundRequest` call that isn't perfectly priced, which matches the bounty's "stealing or loss of funds" category.

### Likelihood Explanation
This triggers on ordinary, permissionless usage — no malicious relayer, prover, or admin is required. Any caller of `dispatch()`/`fundRequest()` paying with native token instead of the fee token, and providing any `msg.value` slack (which is the norm, since exact swap input is generally over-estimated to guard against slippage), will lose the excess. Given that this is the primary payment path documented for POST/GET requests using native tokens [7](#0-6) , exposure is broad and routine, not an edge case.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the pre/post native balance (or the swap's actual amount-in) around the `swapETHForExactTokens` call and refund any unspent `msg.value` back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.sol`, `ExtrinsicIntents.sol`, and `IntrinsicIntents.sol`.

### Proof of Concept
1. Deploy/use a live `EvmHost` with `uniswapV2` router configured and `feeToken()` set.
2. Caller A calls `dispatch(DispatchPost{ fee: 100 feeTokenUnits, ...})` sending `msg.value = 1 ether` (more than needed to buy 100 feeToken units at current pool price).
3. Inside `dispatch`, `swapETHForExactTokens{value: 1 ether}(100, path, address(this), block.timestamp)` is invoked; suppose only 0.01 ETH is actually needed.
4. The router refunds `1 - 0.01 = 0.99 ether` — but to `msg.sender` of the router call, which is `EvmHost`, not caller A.
5. `address(EvmHost).balance` increases by 0.99 ETH; caller A's transaction returns with no refund logic executed, and caller A has no unprivileged way to reclaim the 0.99 ETH.
6. Repeat for `fundRequest` and `dispatch(DispatchGet)` to show the same trapped-value pattern.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
