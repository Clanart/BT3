### Title
SimplexPaymaster Accepts Any Chainlink Answer That Passes Staleness/Sign Checks, With No Deviation Bound — A Bad-But-"Fresh" Oracle Price Lets Any UserOp Sender Drain Gas Subsidy From the Paymaster's EntryPoint Deposit - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
The external report's core defect is: an emergency mechanism trusts "the last price returned by the oracle" and bakes it irreversibly into a financial settlement, with no check that the price is *actually correct* — only that it exists. `SimplexPaymaster._getOraclePrice` reproduces the identical pattern: it validates a Chainlink answer only for positivity and freshness (`answer <= 0`, `updatedAt` staleness), then feeds it directly into `_tokenPrice()`, which is used every block by the fully permissionless `_fetchDetails()` path to price ERC-20 gas payments against the paymaster's EntryPoint deposit. There is no sanity/deviation bound on the reported price itself, so any Chainlink round that is fresh and positive but wrong (misreport, degraded liquidity round, depeg, compromised/buggy upstream feed) is blindly trusted and used to compute how much token an unprivileged UserOp sender must pay for real gas consumed from the paymaster's deposit.

### Finding Description
`_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol:428-442`) is the sole gate on oracle data: [1](#0-0) 

It only rejects `answer <= 0` and answers older than `maxOracleAge` (up to `MAX_ORACLE_AGE = 7 days`, `evm/src/utils/SimplexPaymaster.sol:103`). It performs no comparison against a reference price, no deviation cap, no circuit breaker — exactly the gap the external report calls out ("these prices will be recorded... and it would negatively impact the settlement... as the coverage calculation would provide incorrect values").

This unchecked value flows straight into `_tokenPrice()`: [2](#0-1) 

`_tokenPrice()` is called from `_fetchDetails()` (`evm/src/utils/SimplexPaymaster.sol:374-393`), which `PaymasterERC20` invokes on **every UserOperation**, permissionlessly, to determine `tokenPrice` and thus `erc20Cost = weiCost * tokenPrice / 1e18` charged to the sender and drawn from the paymaster's EntryPoint deposit. Any address holding the registered ERC-20 (in PERMIT or pre-approved APPROVE mode) can submit a UserOp — no governance, relayer, or admin role is required.

Unlike the LendingMarketController case, where a wrong price corrupts an *irreversible* one-time termination settlement, here a wrong-but-fresh oracle answer corrupts *every* gas-payment calculation for as long as that bad round stands (up to `maxOracleAge`, capped at 7 days by governance-set config, but a chain could configure it near that cap). Since `tokenPrice` directly sets how many token units are pulled per unit of real gas cost, an underpriced native/overpriced-token round lets attackers pay far less token than the real gas value, draining the paymaster's EntryPoint deposit (funded by governance/treasury) at a loss to the protocol on every transaction during the bad-price window. The doc comment at `evm/src/utils/SimplexPaymaster.sol:52-59` only reasons about a "malicious oracle" draining *solver allowances* (bounded because solvers keep allowances small) — it does not address protocol-side loss through the EntryPoint deposit, which has no comparable per-tx cap.

### Impact Explanation
This is a direct "loss of funds" / "false price acceptance" primitive against a production bridge contract (`SimplexPaymaster`, administered by Hyperbridge governance and holding a funded EntryPoint deposit). Any unprivileged UserOp sender can exploit a bad-but-fresh Chainlink round to systematically underpay for gas, draining the paymaster's deposited native balance — funds that ultimately come from protocol treasury/fee-recycling (`swapAndDeposit`, `evm/src/utils/SimplexPaymaster.sol:299-330`). Because there is no deviation bound, the contract cannot distinguish a legitimate price move from a misreporting round, so it cannot "pause" or fail safe the way the reporter recommended for the lending protocol's emergency path.

### Likelihood Explanation
Requires an anomalous-but-passing oracle round (not attacker-controlled manipulation of Hyperbridge itself, not a compromised relayer/prover/admin — purely an upstream Chainlink data-quality event, the same trigger class as the original report). Given real-world precedent of Chainlink round anomalies/degraded liquidity reporting and stablecoin depeg events, and that exploitation requires nothing more than submitting ordinary UserOps during the bad window, likelihood is non-trivial for a contract intended to run continuously across many chains with heartbeats up to 24h (`evm/src/utils/SimplexPaymaster.sol:85`).

### Recommendation
Add a sanity/deviation bound in `_getOraclePrice` (or `_tokenPrice`) — e.g., compare against a secondary oracle, a TWAP, or a configurable max-deviation-per-update — and revert or fail safe (disable the token via the existing `active` kill switch) when a round moves outside the bound, mirroring the reporter's recommendation to adapt the mechanism so a single bad oracle read cannot be blindly trusted for consequential fund-moving math. Consider also capping per-block/per-window token-cost exposure for the EntryPoint deposit independent of a single price read.

### Proof of Concept
1. Governance registers `nativeOracle` and a token's Chainlink feed as usual via `RegisterToken`/`UpdateParams`.
2. The token's Chainlink feed reports a fresh, positive, but erroneous answer (e.g., a stablecoin round misreporting $0.10 instead of $1.00 due to an upstream data fault) — `_getOraclePrice` accepts it because it passes both checks at `evm/src/utils/SimplexPaymaster.sol:431-434`.
3. `_tokenPrice()` now returns a `tokenPrice` ~10x too low relative to real value.
4. Attacker (any address holding/approving the token) submits UserOps through the paymaster in APPROVE or PERMIT mode; `_fetchDetails` charges `erc20Cost = weiCost * tokenPrice / 1e18`, ~10x under the real gas cost.
5. Repeated submission drains the paymaster's EntryPoint deposit at a fraction of real cost until the bad round ages past `maxOracleAge` or governance intervenes — no on-chain guard stops this during the window. [3](#0-2)

```text
    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }
```

```text
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
