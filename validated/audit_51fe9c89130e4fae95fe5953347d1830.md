### Title
Recursive precompile calls share a single `BalanceHandler` instance, causing `prevEventsLen` desync and duplicated/dropped balance credits between `x/bank` and the EVM `StateDB` - ([File: precompiles/common/precompile.go])

### Summary
`precompiles/common/precompile.go`'s `runNativeAction` creates a new `BalanceHandler` per top-level precompile call via `p.BalanceHandlerFactory.NewBalanceHandler()` [1](#0-0) , but several precompiles (`distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`) instead hold and reuse a single `BalanceHandler` instance across calls via `GetBalanceHandler()` [2](#0-1) . The handler records `prevEventsLen` in `BeforeBalanceChange` and replays only the events emitted after that index in `AfterBalanceChange` to credit/debit the EVM `StateDB` [3](#0-2) . When a contract makes recursive/nested precompile calls (e.g., a precompile call within a callback that itself triggers another precompile call), each nested invocation calls `BeforeBalanceChange` again on the *same* handler instance, overwriting `prevEventsLen`. This breaks the invariant that each precompile invocation processes exactly the bank events it caused, since the outer call's window gets truncated/expanded incorrectly, leading to either double-counting or dropping of `StateDB.AddBalance`/`SubBalance` adjustments relative to the actual `x/bank` ledger movements.

### Finding Description
This directly maps to the Cosmos EVM invariant that "VM state path: statedb, journal, snapshot, nested-call... must keep balances... consistent across recursive execution," and to the "Asset-representation path" invariant that EVM-visible balances must stay 1:1 with underlying `x/bank` balances.

The repository itself contains a dedicated regression test, `evmd/tests/integration/balance_handler/balance_handler_test.go`, whose doc-comment explicitly states the bug being reproduced: *"BalanceHandlerTestSuite tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [4](#0-3) 

The mechanics mirror the original report's bug class precisely: just as `PreMarkets::abortAskOffer` and `DeliveryPlace::closeBidTaker` are two independently-triggerable code paths that both mutate/rely on the same collateral accounting without checking for prior state transitions - causing a double payout - here `BeforeBalanceChange`/`AfterBalanceChange` are two independently-triggerable entry points (once per precompile call) that share one mutable `prevEventsLen` field without any nesting-awareness or stack/counter discipline. A nested precompile call re-arms `prevEventsLen` at `BeforeBalanceChange`, so when the *outer* call's `AfterBalanceChange` finally runs, it processes an event window that no longer corresponds to the balance changes it is responsible for - either re-processing events already credited by the inner call (double credit into `StateDB` for one `x/bank` transfer) or skipping events that should have been credited (under-crediting an account, effectively freezing/erasing spendable value it should have received).

Because `AfterBalanceChange` directly invokes `stateDB.AddBalance`/`stateDB.SubBalance` [5](#0-4) , any double-processing of the same `EventTypeCoinReceived`/`EventTypeCoinSpent` events results in the EVM-visible balance of an account diverging upward or downward from its true `x/bank` balance - i.e., unauthorized minting/duplication or freezing of spendable value in the EVM balance view, which is inconsistent with the underlying bank ledger.

The regression test's assertions capture the symptom concretely: after one funded transaction that triggers a `callback(0)` (which recursively invokes the debug precompile), the resulting event set is checked to contain exactly `10` `debug_precompile` events out of `15` total events [6](#0-5)  - the kind of exact-count check used specifically to pin down a miscounting/duplication defect during recursive calls.

### Impact Explanation
If triggered, this breaks the "1:1 accounting between native coins... and precompile-visible balances" invariant that is explicitly in the Critical impact gate for this repo. A malicious contract deployer can deliberately construct a contract that calls a precompile (e.g., distribution, staking, erc20, gov, ics20, or slashing - all of which reuse a persistent `BalanceHandler` per the `GetBalanceHandler()` call sites) recursively/nested within a single EVM transaction to intentionally desynchronize `prevEventsLen`. Depending on call ordering, this can:
- Cause the EVM `StateDB` to credit an address with more native/wrapped balance than was actually moved in `x/bank` (duplication of spendable value visible to subsequent EVM operations within the same transaction, e.g. transferring out the phantom balance before the transaction/journal reconciles), or
- Cause `x/bank` funds to be moved (e.g., withdrawn rewards, unbonded stake, ICS20 transferred coins) while the EVM `StateDB` never reflects the corresponding balance increase for the recipient, effectively freezing/losing the value from the EVM-visible ledger.

Either outcome is an unprivileged-user-triggerable, irreversible-in-effect accounting corruption between native balances and EVM-visible balances, satisfying the "Critical unauthorized minting/duplication ... or permanent freezing... of spendable user value" bar.

### Likelihood Explanation
The precondition (a Solidity/EVM contract calling a stateful precompile recursively within a single transaction) is fully reachable by any unprivileged user - no privileged keys, validators, or relayers are required. The repository's own test suite demonstrates that such recursive precompile calls are a supported/exercised code path (`RunNativeAction` / `precompileCallsCounter` with `MaxPrecompileCalls` [7](#0-6)  exists specifically to bound recursive precompile calls, confirming nesting is an expected scenario, not an edge case). The bug is already isolated and named by the project's own engineers in a dedicated test file, indicating it is a known, real, reproducible condition rather than a purely theoretical one.

### Recommendation
Make `BalanceHandler`'s before/after tracking re-entrant-safe:
- Replace the single `prevEventsLen int` field with a stack (e.g., `[]int`) pushed in `BeforeBalanceChange` and popped in `AfterBalanceChange`, so that nested precompile calls do not clobber the outer call's starting index.
- Alternatively (and more robustly, matching the fix pattern in the source report - "check state before permitting the second path to act"), ensure each precompile invocation creates its own `BalanceHandler` instance (as `runNativeAction` already does via `BalanceHandlerFactory.NewBalanceHandler()`), and audit/refactor `distribution`, `erc20`, `gov`, `ics20`, `slashing`, and `staking` precompiles that currently call `GetBalanceHandler()` to obtain a shared/cached handler instead of a fresh one per call.
- Extend the existing `evmd/tests/integration/balance_handler` test suite with assertions that directly compare the final `x/bank` balance of every touched address against the final `StateDB` balance after a recursive-call transaction, to catch any residual desync beyond event counts.

### Proof of Concept
The repository already contains a working proof of concept demonstrating the reachability of the recursive-call condition: `evmd/tests/integration/balance_handler/balance_handler_test.go::TestRecursivePrecompileCallsWithDebugPrecompile` [8](#0-7) . It deploys a "DebugPrecompileCaller" contract that invokes `callback(0)` on a debug precompile registered with a `BalanceHandlerFactory`, causing recursive precompile invocations within one EVM transaction, and asserts specific counts of `debug_precompile` events to characterize the miscounting behavior.

Note: I was not able to fully trace, within the available indexing, the exact production call graph inside `precompiles/distribution/distribution.go`, `precompiles/erc20/erc20.go`, `precompiles/gov/gov.go`, `precompiles/ics20/ics20.go`, `precompiles/slashing/slashing.go`, and `precompiles/staking/staking.go` for their `GetBalanceHandler()` call sites (only 1 match per file was surfaced, without full function bodies), nor the exact quantitative before/after `x/bank` vs `StateDB` balance divergence produced by the existing test. A Devin session with full repository access should be used to confirm the precise duplicated/dropped amount and whether a fix has already landed elsewhere in the codebase before finalizing severity.

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()

// AddPrecompileFn adds a precompileCall journal entry
// with a snapshot of the multi-store and events previous
// to the precompile call.
func (s *StateDB) AddPrecompileFn(snapshot int, events sdk.Events) error {
	s.journal.append(precompileCallChange{
		snapshot: snapshot,
		events:   events,
	})
	s.precompileCallsCounter++
	if s.precompileCallsCounter > types.MaxPrecompileCalls {
		return fmt.Errorf("max calls to precompiles (%d) reached", types.MaxPrecompileCalls)
	}
	return nil
}
