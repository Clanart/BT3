## Finding: Confirmed — Unanchored `issueUrl()` regex lets `getAnchorDescription()` slap trusted labels like `(review)`/`(commits)` on arbitrary non‑GitHub redirect links

### Title
Unanchored issue-URL regex in `IssueLinkFilter` lets attacker-controlled anchors produce trusted "(review)"/"(commits)" labels for non-GitHub links - (File: `app/src/lib/markdown-filters/issue-link-filter.ts`)

### Summary
`issueUrl()` builds a regexp from `escapeRegExp(gitHubURL)` with no `^` start anchor, and it is applied with `.test()`/`.match()` (substring search, not full-string match) both when deciding an anchor is a GitHub issue/PR/discussion link (`isGitHubIssuePullDiscussionLink`) and when extracting `refNumber`/`anchor` for the replacement label (`filter`, `getConsistentIssueReferenceText`, `getAnchorDescription`). Because the match is unanchored, a URL such as `https://evil.example/redirect?u=https://github.com/owner/repo/pull/123#pullrequestreview-456` contains the GitHub URL pattern as a *substring* and is treated as a legitimate GitHub PR link, while the actual host/origin is `evil.example`. [1](#0-0) [2](#0-1) 

### Finding Description
The tree walker only requires `el.href === el.innerText` before calling `isGitHubIssuePullDiscussionLink` and `filter()` [3](#0-2) , so an attacker fully controls both the href and displayed text as long as they are identical raw strings (trivial in an autolinked markdown URL from repo/issue/PR content).

`isGitHubIssuePullDiscussionLink` runs `issueUrl(this.repository).test(anchor.href)` [4](#0-3) . Since the regexp has no `^`, `.test()` succeeds if the GitHub URL pattern appears *anywhere* in `anchor.href`, not just as the actual origin/prefix of the URL. The other guard checks (`isPullRequestTab`, `isURlCustomFormat`) don't constrain the position of the host either [5](#0-4) .

Then in `filter()`, the same unanchored regex is matched against `node.textContent` (== the crafted href) and the captured `anchor` group (e.g. `#pullrequestreview-456`) is passed to `getConsistentIssueReferenceText` → `getAnchorDescription` purely for pattern classification, not validation of trust [6](#0-5) [7](#0-6) . `getAnchorDescription` maps `#pullrequestreview-*` → `(review)` and `#commits-pushed-*` → `(commits)`, so the resulting visible text becomes e.g. `#123 (review)`, while `newNode` retains the original (attacker-controlled) `href` via `node.cloneNode(true)` [8](#0-7) .

The click handler in the sandboxed markdown renderer does not perform any GitHub-origin validation before forwarding the href to the app — it only checks that the protocol is `http(s)` before invoking `onMarkdownLinkClicked` [9](#0-8) . There is no additional host allowlist anywhere in the filter pipeline (`buildCustomMarkDownNodeFilterPipe`) [10](#0-9)  that would catch this before rendering or navigation.

So the anchor-group classification does exactly what the question suspects: it doesn't merely reduce a spoofed link to a bare `#N`, it actively adds a specific, trust-conferring category label (`(review)`, `(commits)`, `(diff)`, `(reference)`) derived from attacker-supplied fragment text on a link whose real destination was never validated to be `github.com`.

### Impact Explanation
This is a link/text spoofing bug: an attacker who controls repository content consumable as markdown (issue/PR/commit comment body) can make an arbitrary external URL render with authoritative-looking text such as `#123 (review)`, strengthening a phishing pretext (e.g., luring the victim to a fake GitHub sign-in page believing they are opening a genuine PR review). It does not by itself grant code execution, file access outside the repo, or IPC/sandbox escape — the resulting `href` is opened as a normal external link, gated by the `https?:` protocol check, not directly loaded in a privileged context. Its severity is limited to increasing the credibility of a phishing/social-engineering vector.

### Likelihood Explanation
High feasibility for a low-privilege attacker: any user who can create an issue comment, PR comment, or commit message visible to a Desktop user (public repo, comment on shared PR, etc.) can embed the crafted URL as plain autolinked text, satisfying the `href === innerText` precondition with no interaction beyond viewing the comment in the app.

### Recommendation
Anchor `issueUrl()`'s regexp to match starting at the beginning of the URL host (e.g. use `^` plus proper `URL`/`origin` parsing of `anchor.href` and compare `url.origin === new URL(gitHubURL).origin`) instead of doing an unanchored substring search. Validate the parsed URL's origin equals the expected GitHub host before treating any part of the href (including the `anchor` fragment) as trustworthy input for label generation.

### Proof of Concept
Markdown/autolinked comment content (href === innerText, satisfying the tree-walker filter):
```
https://evil.example.com/login?next=https://github.com/owner/repo/pull/123#pullrequestreview-456
```
Trace:
1. `el.href === el.innerText` passes since both are that literal string.
2. `isGitHubIssuePullDiscussionLink` calls `issueUrl(repo).test(anchor.href)`, which matches the embedded `https://github.com/owner/repo/pull/123#pullrequestreview-456` substring anywhere in the string → returns `true`.
3. `filter()` matches the same substring in `textContent`, extracts `refNumber="123"`, `anchor="#pullrequestreview-456"`.
4. `getAnchorDescription` matches `/pullrequestreview/` → `(review)`.
5. Rendered anchor text becomes `#123 (review)`, but `href` remains `https://evil.example.com/login?next=...`, and clicking it (protocol is `https:`) is forwarded via `onMarkdownLinkClicked` without any GitHub-origin check.

Uncertainty: I could not fully trace what `onMarkdownLinkClicked` does downstream (e.g., whether `shell.openExternal` shows any additional URL confirmation before navigating) since that consumer wasn't inspected in this pass; if a further host-confirmation dialog exists downstream it could reduce (but not eliminate) impact since the spoofed label itself is still shown in the rendered comment.

export function issueUrl(repository: GitHubRepository): RegExp {
  const gitHubURL = getHTMLURL(repository.endpoint)
  return new RegExp(
    escapeRegExp(gitHubURL) +
      '/' +
      /** A regexp that searches for the owner/name pattern in issue href */
      /(?<nameWithOwner>\w+(?:-\w+)*\/[.\w-]+)/.source +
      '/' +
      /(?:issues|pull|discussions)/.source +
      '/' +
      /** A regexp that searches for the number and #anchor of an issue reference */
      /(?<refNumber>\d+)(?<anchor>#[\w-]+)?\b/.source
  )
}

  private isGitHubIssuePullDiscussionLink(anchor: HTMLAnchorElement) {
    const isIssuePullOrDiscussion = /(issue|pull|discussion)/.test(anchor.href)
    if (!isIssuePullOrDiscussion) {
      return false
    }

    const isPullRequestTab = /\d+\/(files|commits|conflicts|checks)/.test(
      anchor.href
    )
    if (isPullRequestTab) {
      return false
    }

    const isURlCustomFormat = /\.[a-z]+\z/.test(anchor.href)
    if (isURlCustomFormat) {
      return false
    }

    return issueUrl(this.repository).test(anchor.href)
  }

  public async filter(node: Node): Promise<ReadonlyArray<Node> | null> {
    const { textContent: text } = node
    if (!isElement(node, 'a') || text === null) {
      return null
    }

    const match = text.match(issueUrl(this.repository))
    if (match === null || match.groups === undefined) {
      return null
    }

    const { refNumber, anchor } = match.groups
    const newNode = node.cloneNode(true)
    newNode.textContent = this.getConsistentIssueReferenceText(
      refNumber,
      anchor
    )

    return [newNode]
  }

  private getAnchorDescription(anchor: string | undefined) {
    if (anchor === undefined) {
      return ''
    }

    switch (true) {
      case /discussion-diff-/.test(anchor):
        return '(diff)'
      case /commits-pushed-/.test(anchor):
        return '(commits)'
      case /ref-/.test(anchor):
        return '(reference)'
      case /pullrequestreview/.test(anchor):
        return '(review)'
      // Note: On dotcom, there is an additional case
      // /discussioncomment-/.test(anchor): and a check for threaded that
      // returns '(reply in thread)' as opposed to '(comment)', but this would
      // require an api call to determine.
    }

    return '(comment)'
  }

export const buildCustomMarkDownNodeFilterPipe = memoizeOne(
  (options: ICustomMarkdownFilterOptions): ReadonlyArray<INodeFilter> => {
    const { emoji, repository, markdownContext } = options
    const filterPipe: Array<INodeFilter> = []

    if (repository !== undefined) {
      /* The CloseKeywordFilter must be applied before the IssueMentionFilter or
       * IssueLinkFilter so we can scan for plain text or pasted link issue
       * mentions in conjunction wth the keyword.
       */
      if (
        markdownContext !== undefined &&
        isIssueClosingContext(markdownContext)
      ) {
        filterPipe.push(new CloseKeywordFilter(markdownContext, repository))
      }

      filterPipe.push(
        new IssueMentionFilter(repository),
        new IssueLinkFilter(repository)
      )
    }

    filterPipe.push(new EmojiFilter(emoji))

    if (repository !== undefined) {
      filterPipe.push(
        // Note: TeamMentionFilter was placed before MentionFilter as they search
        // for similar patterns with TeamMentionFilter having a larger application.
        // @org/something vs @username. Thus, even tho the MentionFilter regex is
        // meant to prevent this, in case a username could be encapsulated in the
        // team mention like @username/something, we do the team mentions first to
        // eliminate the possibility.
        new TeamMentionFilter(repository),
        new MentionFilter(repository),
        new CommitMentionFilter(repository),
        new CommitMentionLinkFilter(repository)
      )
    }

    filterPipe.push(new VideoTagFilter(), new VideoLinkFilter())

    return filterPipe
  }
)
