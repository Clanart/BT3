## Title
Python message wrapper caches stale sub-message pointer across `MergeFrom`, enabling use-after-free-style dangling-object access - (File: `python/google/protobuf/pyext/message.cc`)

## Summary
The libxslt CVE (BIT-java-2025-10911 / CVE-2025-10911) is a use-after-free where key/value data cached in one runtime-variable-table context outlives the document/pointer it references, so later dereference touches freed memory. The closest legitimate Protobuf analog is the Python C-extension's handling of cached sub-message wrapper objects (`composite_fields`) across `MergeFrom`/`ParseFromString`: a Python `CMessage` wrapper for a nested message is created lazily and cached; when the underlying C++ message is merged/mutated (in particular oneof switches that `delete` and replace the underlying `MessageLite*`), the cached Python wrapper's underlying pointer can become stale unless explicitly fixed up. The code contains deliberate, but narrow, mitigation logic (`MaybeReleaseOneofBeforeMerge` / `FixupMessageAfterMerge`) specifically because "preventing use-after-free bugs" was a known risk here [1](#0-0) .

## Finding Description
`CMessage` objects keep a `composite_fields` map from `FieldDescriptor*` to previously-returned Python wrapper objects for singular message fields, so that `msg.sub_field` returns the same Python object on repeated access [2](#0-1) . When merging (`ParseFromString`/`MergeFromString`, and by extension `MergeFrom`), if a `oneof` switch occurs in the destination message, the underlying C++ generated code will delete the old union member and construct a new one in its place (`ChangeOneof` in the tc-table parser explicitly deletes the old field object before creating the new one) [3](#0-2) ; the C++-generated `MergeImpl` for a oneof field similarly calls `clear_$name$()` (destroying the old object) before re-initializing the new member [4](#0-3) .

The Python extension therefore proactively guards against exactly this hazard: `MaybeReleaseOneofBeforeMerge` walks the `composite_fields` cache before merging and, if the *other* message will cause a different oneof branch to become active, calls `InternalReleaseFieldByDescriptor` to detach/neutralize the cached Python wrapper before the underlying object is destroyed [5](#0-4) . Similarly, `FixupMessageAfterMerge` re-syncs any cached wrapper whose underlying instance transitioned from a shared default instance to a genuinely-owned message after merge [6](#0-5) .

Crucially, this mitigation is applied on the `ParseFromString`/`MergeFromString` code path, which parses into a *temporary* message first specifically "to detect oneof switches before modifying the target message... preventing use-after-free bugs" [7](#0-6) , and only then calls `MaybeReleaseOneofBeforeMerge` / `FixupMessageAfterMerge` around the actual `message->MergeFrom(*temp_message)` call [8](#0-7) . This confirms the underlying invariant-failure mode (cached Python object referencing a C++ object that gets destroyed underneath it during a merge-triggered oneof switch) is a real, previously-identified bug class in this codebase — the same "key data stored across a lifetime boundary that is later invalidated" pattern as the libxslt UAF, just mapped onto Python-wrapper/C++-object lifetime instead of xsl-node/document lifetime.

The C++ core itself explicitly documents that holding a raw pointer to a sub-message across an operation that can destroy it (`Clear()`, oneof switch) is unsupported/UB by design — see the arena test comments: "Referring to a saved pointer to a child message is never guaranteed to work. IOW, protobufs do not guarantee pointer stability" [9](#0-8) , and there is a hardening mode (`DebugHardenClearOneofMessageOnArena`) that poisons memory specifically to catch this at the C++ level [10](#0-9) . The Python layer's `composite_fields` cache is the one place in the trusted, public-facing binding surface where this C++-level "pointer instability" invariant is turned into an actual Python-level dangling-object risk that ordinary application code (via `msg.sub_field` then `msg.MergeFrom(other)`) can trigger without any awareness that it is doing anything unusual.

## Impact Explanation
If the mitigation logic (`MaybeReleaseOneofBeforeMerge`/`FixupMessageAfterMerge`) fails to cover a call path or a corner case (e.g., nested oneof-in-oneof paths, or a merge that goes through a different C API entry point than `MergeFromStringImpl`), an application that has cached a reference to `msg.sub_field` (a Python wrapper over a C++ submessage) prior to merging in attacker-controlled bytes could end up holding a Python object whose underlying `Message*` pointer refers to freed/reused memory. Subsequent attribute access on that stale Python object would read or write through a dangling C++ pointer — a use-after-free reachable purely by parsing an attacker-supplied bounded ProtoJSON/binary payload via the public `MergeFrom`/`ParseFromString`/`MergeFromString` APIs, consistent with the assumption that the attacker is an ordinary client sending bounded Protobuf through a supported parse API. Severity is Medium: it requires a specific application usage pattern (holding a live reference to a submessage wrapper across a merge) and depends on whether any path evades the existing fixup logic — the code otherwise contains dedicated defenses against exactly this class of bug, and I did not find or execute a concrete case where the defense is bypassed in this checkout.

## Likelihood Explanation
Likelihood is limited by the fact that this exact hazard is explicitly acknowledged and defended against in the code (`MaybeReleaseOneofBeforeMerge`, `FixupMessageAfterMerge`, and the temp-message parse-then-merge pattern with an explicit "preventing use-after-free bugs" comment) [7](#0-6) . I was not able to fully verify, within the remaining investigation budget, whether the direct `Message.MergeFrom(other_message)` Python API (as opposed to `MergeFromString`) invokes the same `MaybeReleaseOneofBeforeMerge`/`FixupMessageAfterMerge` guards, or whether nested/repeated composite field paths are fully covered. That gap is a genuine unknown in this analysis, not a confirmed bypass.

## Recommendation
- Audit every Python `CMessage` code path that can trigger a C++-side oneof switch or `Clear()` on a submessage that has a live `composite_fields` cache entry (not just `MergeFromString`), and ensure `MaybeReleaseOneofBeforeMerge`/`FixupMessageAfterMerge`-equivalent guards are applied uniformly, including for the plain `Message.MergeFrom(other_message)` entry point and for `CopyFrom`.
- Add regression tests that hold a Python reference to `msg.sub_field` (a message-typed oneof field) prior to `msg.MergeFrom(other)` where `other` sets a different oneof branch, then access the held reference afterward, across all merge entry points (`MergeFrom`, `MergeFromString`, `CopyFrom`, `ParseFromString`), verifying it either raises or reflects updated state rather than reading freed memory.
- Consider enabling memory-poisoning hardening (`DebugHardenClearOneofMessageOnArena`) equivalents for the CPython extension build to make any residual dangling-wrapper access fail loudly (crash/`use-after-poison`) rather than silently corrupt.

int MaybeReleaseOneofBeforeMerge(CMessage* self, const Message& other) {
  CMessage::CompositeFieldsMap* composite_fields =
      self->composite_fields.TryGet();
  if (!composite_fields) {
    return 0;
  }

  Message* message = AssureWritable(self);
  if (message == nullptr) return -1;
  const Reflection* reflection = message->GetReflection();
  PyMessageFactory* factory = GetFactoryForMessage(self);
  std::vector<const FieldDescriptor*> fields_to_release;
  std::vector<std::pair<const FieldDescriptor*, ScopedPyObjectPtr>>
      nested_message_fields;
  composite_fields->ForEach([&](const void* key, PyObject* value) {
    const FieldDescriptor* descriptor =
        reinterpret_cast<const FieldDescriptor*>(key);
    if (descriptor->cpp_type() == FieldDescriptor::CPPTYPE_MESSAGE &&
        // For normal repeated message, MergeFrom will append the messages.
        // For message map with same keys, it is overwrite
        !descriptor->is_repeated() &&
        reflection->HasField(*message, descriptor)) {
      if (reflection->HasField(other, descriptor)) {
        Py_INCREF(value);
        nested_message_fields.emplace_back(descriptor, value);
      } else {
        // Release oneof message if the other message has set a different oneof
        const OneofDescriptor* oneof = descriptor->containing_oneof();
        if (oneof && reflection->HasOneof(other, oneof)) {
          fields_to_release.push_back(descriptor);
        }
      }
    }
  });

                           const TcParseTableBase::FieldEntry& entry,

  // The _oneof_case_ value offset is stored in the has-bit index.
  uint32_t* oneof_case = &TcParser::RefAt<uint32_t>(msg, entry.has_idx);

  *oneof_case = field_num;
