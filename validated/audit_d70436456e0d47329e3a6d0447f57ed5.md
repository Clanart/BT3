### Title
Out-of-range `Participant` index in a blame accusation panics `BlameMachine::blame` / `AdditionalBlameMachine::blame` via `HashMap` indexing — remote DoS - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
The PedPoP DKG blame path dereferences the commitments map with `self.commitments[&sender]` and `self.commitments[&recipient]` without validating that the supplied `Participant` indexes are within `1 ..= n`. `Participant::new` only rejects `0`, so any nonzero `u16` — e.g. `n + 1` up to `65535` — is a syntactically valid `Participant` but is absent from the `commitments` `HashMap`. Indexing a missing `HashMap` key panics, aborting the caller. This is the direct analog of CVE-2020-13848: an unchecked, attacker-controlled identifier used as a lookup key causing a crash (NULL pointer dereference in libupnp; unchecked `HashMap` index panic in Serai).

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept `sender` and `recipient` as `Participant` values supplied by the caller (in Serai's deployment, derived from `Transaction::InvalidDkgShare` accusations, whose reader only enforces `Participant::new(...) != None`, i.e. nonzero). `blame_internal` then does:

```rust
if !bool::from(
  multiexp_vartime(&share_verification_statements::<C>(
    recipient,
    &self.commitments[&sender],   // panics if sender ∉ 1..=n
    ...
``` [1](#0-0) 

The `commitments` map only contains entries for `1 ..= n` — it is populated per `all_participant_indexes()` in `verify_r1` / `calculate_share` [2](#0-1)  or for `1 ..= n` in `AdditionalBlameMachine::new` [3](#0-2) . Neither `blame()` nor `blame_internal` checks `u16::from(sender) <= n` or `recipient <= n` before indexing [4](#0-3) . By contrast, the signing code carefully validates participant bounds before map lookups (`included[last] > n` → `InvalidParticipant`) [5](#0-4) , and `dkg` itself defines `DkgError::InvalidParticipant` for exactly this condition [6](#0-5)  — the PedPoP blame path simply omits the check. Similarly, `Participant(u16)` deserialization permits any nonzero value [7](#0-6) .

The same unguarded indexing also exists at `self.commitments[&l]` inside `KeyMachine::calculate_share` [8](#0-7) , though there `validate_map` constrains keys to `1 ..= n`; the blame path has no equivalent guard.

### Impact Explanation
An unauthenticated-content input (a blame/accusation message naming a `sender`/`recipient` index outside the DKG's participant set) causes an unconditional panic in every node that evaluates the accusation — including via `AdditionalBlameMachine`, which is explicitly designed for use by parties who are *not* DKG members [9](#0-8) . Depending on deployment, this crashes the processor/coordinator task evaluating blame, denying service during the DKG fault-handling phase and potentially stalling key generation or rotation. Severity: Medium–High availability impact, no integrity/confidentiality loss (analogous to the 7.5 CVSS availability-only libupnp bug).

### Likelihood Explanation
Reaching the code requires only that the caller route an accusation with attacker-influenced `sender`/`recipient` fields into `blame()`. The panic trigger is trivial: any `u16` in `(n, 65535]` — e.g. `faulty = n + 1`. No cryptographic work, valid proofs, or threshold collusion is needed; the message itself does not need to be a valid secret share since the panic occurs on map lookup before or regardless of share verification.

### Recommendation
Validate `sender` and `recipient` against the participant set (e.g. `u16::from(p) <= params.n()` / `commitments.contains_key(&p)`) at the top of `blame()`/`blame_internal` and `AdditionalBlameMachine::blame`, returning a `Result` with `DkgError::InvalidParticipant` or defaulting blame to the accuser, instead of indexing the map unconditionally. Replace `self.commitments[&sender]` with `.get(&sender)` and handle the `None` case.

### Proof of Concept
```rust
// Assume a completed DKG with n = 3, producing `blame_machine: BlameMachine<C>`
// (or AdditionalBlameMachine::new(context, 3, commitment_msgs)).

let bogus_sender = Participant::new(4).unwrap();      // > n, still a valid Participant
let bogus_recipient = Participant::new(1).unwrap();

let msg: EncryptedMessage<C, SecretShare<C::F>> = /* any bytes, even garbage */;

// Panics: "no entry found for key" at pedpop/src/lib.rs (self.commitments[&sender])
let (_machine, _faulty) = blame_machine.blame(bogus_sender, bogus_recipient, msg, None);
```

The panic fires regardless of `msg` validity because the `commitments` map lookup occurs inside `share_verification_statements(..., &self.commitments[&sender], ...)` during evaluation of the blame statement [10](#0-9) .

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
