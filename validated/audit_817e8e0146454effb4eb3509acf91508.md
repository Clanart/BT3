This confirms the core mechanism: `calculate_pubkey_spend_sighash` uses `sighash_cache.taproot_key_spend_signature_hash(txin_index, &prevouts, sighash_type)` via rust-bitcoin's standard BIP-341 implementation, which for `TapSighashType::SinglePlusAnyoneCanPay` commits only to input 0 (via `Prevouts::One`) and the single corresponding output (index 0) — never the OP_RETURN output (index 2). The `create_payout_txhandler` at [1](#0-0)  builds the OP_RETURN with the caller-supplied `operator_xonly_pk` as an extra unsigned output, and the signature verification in `Operator::withdraw` at [2](#0-1)  only checks the sighash over input0/output0 — so the OP_RETURN content is fully unconstrained by the user's signature.

### Title
Unauthenticated OP_RETURN payer attribution lets anyone forge a registered operator as the funder of a withdrawal it never paid - (File: core/src/verifier.rs, core/src/builder/transaction/operator_reimburse.rs)

### Summary
The withdrawal payout transaction's OP_RETURN output (which encodes the operator's x-only pubkey used to attribute reimbursement) is not covered by the user's `SinglePlusAnyoneCanPay` signature, because that sighash flag commits only to input 0 and output 0. Anyone who can obtain a valid user withdrawal signature (as the withdrawal requester themselves, since the user creates and controls this signature) can build and broadcast their own payout transaction reusing that signature, paying the correct user output, but writing an arbitrary registered operator's x-only pubkey into the OP_RETURN. `update_finalized_payouts` blindly parses this OP_RETURN as ground truth for "who funded this withdrawal," and the operator's own `PayoutCheckerTask` automatically initiates a kickoff/reimbursement claim for any unhandled payout matching its key — with no verification that the operator itself broadcast or funded the transaction.

### Finding Description
The broken binding: `payout_payer_operator_xonly_pk` (DB attribution recorded by `update_finalized_payouts`) is claimed by the protocol to equal "the operator who fronted/funded withdrawal i," but the code only guarantees it equals "whatever bytes appear in the first OP_RETURN output of whichever transaction first spends withdrawal UTXO i."

Trace:
1. `create_payout_txhandler` builds output2 as an OP_RETURN containing `operator_xonly_pk` supplied by the transaction constructor, with no cryptographic binding to the withdrawal signature: [3](#0-2) .
2. The user's `in_signature` (`SinglePlusAnyoneCanPay`) is verified via `calculate_sighash_txin(0, ...)` / `calculate_pubkey_spend_sighash`, which for this sighash flag uses `Prevouts::One(txin_index, ...)` and BIP-341's `taproot_key_spend_signature_hash`, committing only to input 0 and output 0 — never output 2 (the OP_RETURN): [4](#0-3) , [5](#0-4) .
3. On-chain, `update_finalized_payouts` scans the confirmed payout tx, extracts the first OP_RETURN output, and parses it directly as an `XOnlyPublicKey` to attribute the payout, with no check that this key belongs to any registered operator or that the entity broadcasting the tx controls that key: [6](#0-5) .
4. `PayoutCheckerTask::run_once` polls `get_first_unhandled_payout_by_operator_xonly_pk` for the operator's own key and, if a match is found, automatically calls `handle_finalized_payout` to build and queue a kickoff/reimbursement — with no check that this operator's wallet or gRPC service ever created that specific payout transaction: [7](#0-6) .

Exploit flow: the attacker, acting as the withdrawal's own requester on Citrea (they legitimately control the dust withdrawal UTXO's private key and choose their own withdrawal output), self-signs `in_signature` with `SinglePlusAnyoneCanPay`. Instead of submitting it through an operator's `Withdraw`/`InternalWithdraw` RPC, they directly construct their own transaction spending the withdrawal UTXO (input0), fund the required user payout (output0, using their own BTC, so no net loss besides fees since the payout goes to their own chosen address), and append an OP_RETURN naming an arbitrary registered operator's x-only pubkey. They broadcast this directly to Bitcoin, bypassing all Clementine services entirely. Because the signature never commits to the OP_RETURN, `verify_schnorr` cannot detect any tampering, and once mined, `update_finalized_payouts` records the named (victim) operator as the payer. That operator's `PayoutCheckerTask` will then autonomously kick off the reimbursement process for a payout it never funded.

Existing guards do not catch this: `SECP.verify_schnorr` in `Operator::withdraw` only validates a specific transaction template an operator itself constructs before broadcasting — it provides no protection once a conflicting/alternate transaction using the same signature is built and broadcast by a third party directly to the Bitcoin network. `handle_finalized_payout`/`PayoutCheckerTask` trust the DB-derived attribution unconditionally.

### Impact Explanation
This allows any unprivileged party (a normal user requesting their own withdrawal) to force the bridge's reimbursement machinery (`handle_finalized_payout` → kickoff → `Reimburse` tx) to award a specific operator's collateral-round the "credit" for a withdrawal that operator never funded — matching the Critical category "an operator reimbursed for a payout it never funded." This is repeatable across any withdrawal and any registered operator whose x-only pubkey is public (operator keys are broadcast/discoverable), and does not require deposit, collateral, or any privileged role — only the ability to be a normal withdrawal requester who signs their own payout input.

### Likelihood Explanation
The attacker only needs to be a legitimate Citrea withdrawal requester (no deposit needed beyond what any user already does to withdraw) and enough BTC to fund their own withdrawal output plus fees — money that returns to an address they control, so the marginal cost is near-zero (transaction fees only). No mempool-scraping or race condition against an honest operator is strictly required, since the attacker legitimately creates their own signature; they simply never submit it to any operator's RPC and instead broadcast their own crafted transaction. This is straightforward to reproduce on regtest.

### Recommendation
Bind the OP_RETURN operator attribution to the signature: either (a) have the user's withdrawal signature use `AllPlusAnyoneCanPay` (or a full-output-commit sighash) so all outputs including the OP_RETURN are covered, requiring the OP_RETURN operator key to be fixed at signature-creation time and agreed with the user/aggregator beforehand, or (b) require a separate operator-authenticated commitment (e.g., an operator signature over the specific withdrawal index + payout tx template) that `update_finalized_payouts` and `PayoutCheckerTask` must validate before treating a payout as "funded by" that operator, rather than trusting unsigned OP_RETURN bytes alone.
