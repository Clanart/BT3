### Title
Deposits between the P2TR dust limit (330 sats) and `N::DUST` (546 sats) are silently dropped by the scanner, permanently freezing spendable funds in the multisig address - (File: processor/src/multisigs/scanner.rs)

### Summary
The analog of "`transferFrom()` sending an NFT to a contract that cannot handle ERC721" is Serai delivering funds to a subsystem that does not account for them. `Scanner::scan_transaction` correctly detects every output paying to a registered script, but `processor/src/multisigs/scanner.rs` then filters out any output whose value is below `N::DUST` before the output is ever recorded or acknowledged. Because Bitcoin's dust limit for P2TR (SegWit v1) outputs is 330 sats while `bitcoin_serai::wallet::send::DUST` is hard-coded to 546 sats, a standard, consensus-valid, fully spendable output of 330–545 sats sent to a Serai deposit/branch/change/forwarded address is detected-then-discarded. The coins remain locked under the multisig key, yet no `ReceivedOutput` is ever emitted, so `SignableTransaction::new` will never include them as inputs and the multisig can never spend them.

### Finding Description
- `Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs:199-214` returns a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script — including low-value outputs — since `ReceivedOutput` is defined as "a spendable output" (line 88).
- The processor-level scan loop in `processor/src/multisigs/scanner.rs:562-567` calls `network.get_outputs(&block, key)` and only pushes an output into `outputs` if `output.balance().amount.0 >= N::DUST`. Outputs failing the check are not emitted in the `ScannerEvent::Block`, not written by `ack_block`, and never revisited because the block is marked scanned in the same transaction.
- `N::DUST` resolves to `bitcoin_serai::wallet::send::DUST = 546` (`networks/bitcoin/src/wallet/send.rs:32`), taken from Bitcoin Core's generic `DUST_RELAY_TX_FEE`-based policy. That constant is correct for *constructing* payments, but for *crediting* received funds the relevant bound is the output-type-specific dust threshold. For P2TR outputs, Bitcoin Core computes dust as 330 sats (98-byte input × 3 sat/vB + output serialization), so the network accepts and relays transactions creating 330–545 sat outputs to Serai addresses.
- The result mirrors the audit issue: an asset is delivered into the custody of a component that structurally cannot process it. The output is spendable on-chain (the multisig key controls the P2TR key path), but Serai's pipeline has already discarded the only artifact (`ReceivedOutput` + offset) needed to sign a spend.

### Impact Explanation
Any user (or attacker sending on a victim's behalf) can create a valid 330–545 sat P2TR output to a Serai `external_address`, `branch_address`, `change_address`, or `forward_address`. The deposit is never credited to the sender's Serai account, never enters the multisig's spendable UTXO set, and cannot be recovered by any documented mechanism — the scanner has permanently marked that block as processed and `SignableTransaction::new`/`multisig` only operate on `ReceivedOutput`s produced by the scanner. Funds are frozen under the threshold key, exactly the "NFT stuck in a contract that doesn't support ERC721" outcome: delivery succeeded, handling did not. Repeatable per output.

### Likelihood Explanation
An unprivileged party needs only to broadcast a standard Bitcoin transaction; the reachable path is `get_outputs` → `scan_transaction` → the `>= N::DUST` gate. No malicious validator, collusion, or leaked material is required — the trigger is ordinary transaction data on the public chain. The frozen amount per instance is bounded (≤545 sats), which caps severity at Medium rather than High, but deposits being silently lost is a correctness violation of the credited-funds invariant.

### Recommendation
Use the output-type-aware dust threshold for the receive-side filter — for P2TR scripts, 330 sats — or remove the value filter entirely and let `SignableTransaction::new` decide spendability at input-selection time (it already enforces `DUST` on the payments it creates). If a minimum is retained for economic reasons, emit the dropped outputs in an event/log so they can be recovered by an explicit sweep rather than being permanently unaccounted.

### Proof of Concept
1. A coordinator registers a multisig key; `Bitcoin::external_address` yields a P2TR address (`processor/src/networks/bitcoin.rs` uses `scanner(key)` offsets for External/Branch/Change/Forwarded kinds).
2. An external user broadcasts a standard transaction paying 400 sats to that address. 400 ≥ 330 passes Bitcoin Core's P2TR dust relay check; the tx confirms.
3. The processor scans the containing block: `get_outputs` calls `Scanner::scan_transaction`, which matches the `script_pubkey` and yields a `ReceivedOutput` with the registered offset (`networks/bitcoin/src/wallet/mod.rs:205-211`).
4. Back in `processor/src/multisigs/scanner.rs:564`, `output.balance().amount.0 = 400 < N::DUST = 546`, so the output is dropped before `outputs.push`. The block is still committed as scanned (`ScannerDb::save_block` / `ack_block`), so it is never rescanned.
5. The 400 sats are now frozen: they are real, confirmed, key-path-spendable funds under the multisig key, but no `ReceivedOutput` exists, so `SignableTransaction::new` can never reference the outpoint and `multisig` can never produce a signature for it — the multisig received an asset it cannot spend, with no refund path to the depositor.
