## Title
Single invalid message poisons an entire ISMP batch and forces legitimate, fund‑bearing requests/responses/timeouts into failure — (`modules/pallets/ismp/src/impls.rs`)

### Summary
The seed report's broken invariant is: *"a single invalid item in a batch causes a hard error instead of being skipped, silently blocking every other, valid item bundled with it."* Hyperbridge's `pallet-ismp` message-execution path (`Pallet::execute`) reproduces this exact pattern for ISMP `Request`/`Response`/`Timeout` batches: any one message that fails validation (bad proof, duplicate, timed‑out, wrong destination, etc.) causes the whole batch to error out and roll back atomically, instead of the invalid message simply being skipped/ignored the way Ethereum's `apply_deposit()` (the recommendation in the seed report) does for a single bad deposit.

### Finding Description
`Pallet::<T>::execute` collects the results of `handle_incoming_message` over every message in the batch using `collect::<Result<Vec<_>, _>>()`: [1](#0-0) 

If **any single message** fails (e.g. `Error::RequestTimeout`, `Error::DuplicateRequest`, `Error::UnknownRequest`, `Error::InvalidRequestDestination` from the per-item validation loops in the request/response/timeout handlers), the whole `Result` is `Err`, and `execute` returns `Error::<T>::InvalidMessage` for the **entire batch**: [2](#0-1) [3](#0-2) [4](#0-3) 

This propagates to two enforcement points that make the failure absolute rather than partial:

1. `handle_unsigned` is `#[frame_support::transactional]`, so a batch failure reverts **all** state changes for every message in the call, even the valid ones: [5](#0-4) 

2. `validate_unsigned` (the mempool gate for this permissionless, unsigned call) itself calls `Self::execute(messages.clone())` and rejects the **entire transaction** with `InvalidTransaction::BadProof` if any single message in it is invalid — the whole bundle never even enters a block: [6](#0-5) 

This is the same broken invariant as the seed report: instead of skipping the one bad element (as the recommended Ethereum-spec fix does for deposits), the code treats "one item failed validation" as "the whole batch is invalid," rejecting or reverting the other, unrelated, legitimate items bundled in the same batch/transaction.

### Impact Explanation
ISMP request/response/timeout delivery is batched by design for gas efficiency (see `submit_batch_messages`/`batchCall` on the EVM side, and multi-message `handle_unsigned` calls on the Substrate side). Because validation of every message in a batch happens together, and any single invalid message poisons the entire batch:

- An attacker who controls even one ISMP message destined for the same chain/height as a batch of legitimate, fee-paying, fund-bearing requests (e.g., by dispatching a request designed to time out almost immediately, or by getting a duplicate delivered ahead of an honest relayer's batch) can cause **every other legitimate request/response/timeout bundled with it to be rejected**, since `execute` short-circuits and `validate_unsigned` blocks the whole unsigned extrinsic from even reaching a block.
- Legitimate `PostRequest`s that escrow relayer fees via `IsmpDispatcher::dispatch_request` remain undelivered while this poisoning persists; if delivery is withheld long enough, they hit their `timeout_timestamp` and must go through the timeout/refund path instead of normal settlement — this is state manipulation of cross-chain message settlement outcomes (forced timeout instead of successful delivery) driven entirely by an unprivileged attacker's own message, not by a malicious relayer/prover/operator.
- Because this failure mode requires no special relayer/prover/admin privilege and no front-running — only a normal dispatch of an ISMP message that predictably fails one of the existing checks — it is reachable by any ordinary, unprivileged actor with access to any application module that can dispatch ISMP requests.

### Likelihood Explanation
High. Dispatching an ISMP request/response that will be timed out or duplicated by the time a relayer batches it is a cheap, permissionless, everyday action (any module using `IsmpDispatcher::dispatch_request`). Relayers batch messages for efficiency by construction (`submit_batch_messages`, `handle_unsigned` with multiple messages), so the "poisoned batch" condition is the normal operating mode, not an edge case that requires special coordination.

### Recommendation
Mirror the recommended fix from the seed report: don't let one invalid message error out the whole batch. In `Pallet::execute` (and in `handlers/request.rs`, `response.rs`, `timeout.rs`), validate and dispatch each message independently — skip/record failures for individual invalid messages (emitting an event/error per message, as `Event::Errors` already supports) instead of using `collect::<Result<Vec<_>, _>>()` semantics that abort the entire batch. `validate_unsigned` should likewise not reject an entire submitted transaction because one message inside it is invalid; it should validate only that at least one message in the batch is deliverable, or restructure per-message unsigned submission so a single bad message cannot censor unrelated ones.

### Proof of Concept
1. Attacker (or any user of a module with dispatch access) dispatches Request A on the source chain with `timeout_timestamp` set to expire almost immediately, alongside/around the time honest users dispatch Requests B, C, D bound for the same destination chain.
2. A relayer builds a `handle_unsigned` batch (or destination-chain `batchCall`) containing `[A, B, C, D]` for gas efficiency, all sharing one state/consensus proof height.
3. On submission, `validate_unsigned` calls `Self::execute([A,B,C,D])`; validating A triggers `Error::RequestTimeout` in `handlers/request.rs`, so the entire call returns `Err`, and the transaction is rejected with `InvalidTransaction::BadProof` before it even enters a block — `B`, `C`, `D` are never delivered by this batch.
4. If a relayer instead gets the batch included as `handle_unsigned` directly, the `#[frame_support::transactional]` attribute on `handle_unsigned` rolls back the whole call, so `B`, `C`, `D` still fail to be delivered even though they are individually valid.
5. Repeating step 1 lets the attacker indefinitely deny delivery for any batch it can insert itself into, forcing legitimate pending requests toward timeout/refund instead of normal settlement.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;
