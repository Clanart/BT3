## Title
Missing domain separator lets a relayer's `accumulate_fees` beneficiary-redirect signature double as a valid `withdraw_fees` signature, enabling nonce-collision griefing of fee settlement - (File: `modules/pallets/relayer/src/accumulate.rs`, `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`pallet-relayer` has two independent signed actions that consume the *same* per-`(address, state_machine)` nonce counter (`Nonce<T>`), but the signed payloads for both actions hash to **identical bytes** for the same `(nonce, chain, beneficiary)` triple. There is no domain separator (function selector, purpose tag, or similar) distinguishing "authorize a fee withdrawal" from "authorize a beneficiary redirect during fee accumulation." This is the same broken invariant as the `FluidLocker::claim()` report: a signed, nonce-bound authorization meant for one code path can be consumed through a sibling path that shares the nonce space, causing the intended call to silently fail signature verification and revert, denying the relayer/beneficiary their fee credit.

### Finding Description
`withdraw()` builds its signed message as: [1](#0-0) 

```rust
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
    if let Some(beneficiary) = beneficiary {
        return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
    }
    sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
```

`accumulate()`'s beneficiary-redirect path builds its signed message as: [2](#0-1) 

```rust
pub fn beneficiary_message(nonce: u64, state_machine: StateMachine, beneficiary: &[u8]) -> [u8; 32] {
    sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
}
```

Both functions SCALE-encode the identical tuple shape `(u64, StateMachine, Vec<u8>)` and keccak256 it — there is no selector, purpose string, or pallet call-index mixed in. For the same `(address, chain)` pair, `message(nonce, chain, Some(beneficiary))` and `beneficiary_message(nonce, chain, beneficiary)` produce the exact same hash, so a signature valid for one is cryptographically valid for the other.

Both consumers read and advance the **same** storage item, keyed identically: [3](#0-2) [4](#0-3) [5](#0-4) 

`withdraw_fees` is dispatched unsigned (`ensure_none` origin per `lib.rs`), and `accumulate_fees` is likewise submitted unsigned via `validate_unsigned`, so both are public mempool submissions — anyone observing pending or historic on-chain payloads can extract the `(nonce, chain, beneficiary, signature)` tuple. Because the two functions share the nonce sequence with no domain tag, whichever of the two conflicting requests lands first on-chain silently invalidates the other: the second call's `signature.verify(&msg, ...)` fails `Error::InvalidSignature` (in `accumulate()`, this aborts the *entire* extrinsic, including the unrelated `total_fee` credit for that batch of proven commitments) or `Error::InvalidPublicKey`/`InvalidSignature` in `withdraw()`. This is structurally identical to the report's root cause: "a critical function that consumes a nonce may be triggered directly/out-of-band, bypassing the wrapper's other side effects," letting an unprivileged party deny the legitimate actor their credited funds.

### Impact Explanation
When `accumulate_fees`'s beneficiary-redirect signature check fails, the whole extrinsic reverts — the relayer loses the fee credit (`Fees::try_mutate` never runs) for that entire batch of already-proven, already-verified deliveries, and the affected `RequestCommitments` are not marked claimed, so the relayer must re-derive fresh state proofs and resubmit with an advanced nonce. This is unauthorized denial of a rightful fee credit / settlement caused purely by an unprivileged actor exploiting a missing domain separator in the signed-message construction shared between two unrelated pallet entry points — a logic flaw in how one-time authorizations are bound, not merely generic transaction-ordering noise.

### Likelihood Explanation
Both extrinsics are unsigned and their parameters (including the raw signature bytes) are visible in the public mempool/finalized blocks before/as they land. Any address with an accumulated `Fees` balance above `MinimumWithdrawalAmount` (visible in storage) triggering an `accumulate_fees` beneficiary redirect is a target; the attacker only needs to copy the intercepted signature bytes into a `withdraw_fees` call with matching `(dest_chain, beneficiary)` and submit it with priority. No relayer collusion, governance, or leaked keys are required — only public on-chain data.

### Recommendation
Add a purpose/domain tag distinguishing the two signed message constructions, e.g. include a constant discriminator (`b"WITHDRAW"` vs `b"ACCUMULATE_BENEFICIARY"`) or the pallet call index in both `message()` and `beneficiary_message()` before hashing, so a signature crafted for one action can never validate for the other even when `(nonce, chain, beneficiary)` coincide.

### Proof of Concept
1. Relayer R has `Fees[chain, R] = F ≥ MinWithdrawal` and wants to redirect a newly-proven batch's fee credit to beneficiary `B` via `accumulate_fees` with `beneficiary_details = Some((B, sig))`, where `sig` signs `beneficiary_message(nonce=N, chain, B)`.
2. R broadcasts the `accumulate_fees(withdrawal_proof)` extrinsic; `sig`, `N`, `chain`, `B` are visible in the mempool.
3. Attacker copies `sig` and submits `withdraw_fees(WithdrawalInputData { signature: sig, dest_chain: chain, beneficiary: Some(B) })` with higher priority/fee.
4. `withdraw()` computes `Nonce::get(R, chain) == N`, `message(N, chain, Some(B))` matches `sig` (identical hash to `beneficiary_message`), passes verification, increments `Nonce` to `N+1`, and dispatches the withdrawal.
5. R's original `accumulate_fees` now executes with `Nonce::get(R, chain) == N+1`; `beneficiary_message(N+1, chain, B)` no longer matches `sig`, so `signature.verify` fails, `Error::InvalidSignature` propagates via `?`, and the entire extrinsic reverts — R's newly proven fee batch is not credited and must be resubmitted with a fresh nonce/signature.
