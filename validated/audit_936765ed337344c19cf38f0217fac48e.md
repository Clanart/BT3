### Title
Unguarded `updateEndRemainingAllocation()` allows repeated resets of the bonus denominator, letting an attacker over-extract `totalBonus` and cause `InsufficientBalance()` freezes for later claimants - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is `public`, callable by anyone at any time after `periodsEndTime[4]`, and unconditionally overwrites `totalEndRemainingAllocation` with the *current* `totalRemainingAllocation` every time it is called, instead of only snapshotting it once. Since `getBonusAmount` divides `userAllocation * totalBonus` by `totalEndRemainingAllocation`, an attacker can call this public function again after other users have already claimed (shrinking `totalRemainingAllocation`), which re-normalizes the bonus share for the remaining claimants against a smaller denominator while `totalBonus` stays fixed — causing the sum of bonuses paid out across all users to exceed the actual `totalBonus` pool, and ultimately exceed the token balance held by the contract.

### Finding Description
- `totalBonus` accumulates forfeited allocation from early claimers (`claim()`, lines 165-168 of `rewards/Airdrop.sol`) and is meant to be split pro-rata among users who are still unclaimed at `periodsEndTime[4]`, using the one-time snapshot `totalEndRemainingAllocation` (`getBonusAmount`, lines 127-143).
- The snapshot is supposed to be taken exactly once: `claim()` only calls `updateEndRemainingAllocation()` when `totalEndRemainingAllocation == 0` (line 154-156). However, `updateEndRemainingAllocation()` itself (lines 146-150) has no such guard and is `public`:
```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
```
Any unprivileged address can call this directly, any number of times, after `periodsEndTime[4]`.
- Exploit: Let `D0` be `totalRemainingAllocation` at `periodsEndTime[4]` (sum of all unclaimed allocations). A first batch of users claim normally, each receiving `userAlloc_i * totalBonus / D0`, and `totalRemainingAllocation` shrinks by the sum `x` of their allocations to `D0 - x`. The attacker then calls `updateEndRemainingAllocation()` again, resetting `totalEndRemainingAllocation` to `D0 - x`. Remaining claimants (including the attacker) now receive `userAlloc_i * totalBonus / (D0 - x)`, which sums to `totalBonus` again for just that remaining group. Total bonus paid out becomes `totalBonus * (1 + x/D0) > totalBonus`.
- Since `totalBonus` is never decremented as it's paid, and the excess payout must be funded from the same token balance that also backs other users' still-unclaimed base allocations, the pool held in `aidropToken` (deposited by admin to exactly cover `Σ allocations`) becomes insufficient. Later legitimate claimants calling `claim()` hit `if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();` (line 160), permanently reverting their claim since no further deposits are made.
- No modifier (`onlyOwner`, `nonReentrant`, etc.) protects `updateEndRemainingAllocation()` from repeat invocation; this is purely a public-function/state-machine bug reachable by any EOA.

### Impact Explanation
This breaks the backing invariant of the Airdrop contract: total token liabilities (`Σ getClaimableAmount()`) can exceed `aidropToken.balanceOf(address(this))`. Legitimate users who claim after the attacker's manipulation are permanently unable to claim their rightful allocation (funds frozen indefinitely, well beyond 24 hours, since there is no mechanism to top up the pool). This matches Immunefi's "permanent freezing of funds" / "protocol insolvency" impact class, and effectively lets the manipulating claimant steal a disproportionate share of the shared `totalBonus` pool at the expense of other airdrop recipients.

### Likelihood Explanation
- Fully permissionless: requires only calling the public `updateEndRemainingAllocation()` function, which any address can invoke with no special capital or role.
- Requires only that `block.timestamp >= periodsEndTime[4]` and that at least one other user has already claimed (reducing `totalRemainingAllocation`) before the attacker calls the reset and then claims.
- Trivially repeatable by any of the remaining claimants racing to call `updateEndRemainingAllocation()` right before their own `claim()`.

### Recommendation
Guard `updateEndRemainingAllocation()` so it can only set `totalEndRemainingAllocation` once (e.g., add `if (totalEndRemainingAllocation != 0) return;` inside the function itself, not only in `claim()`), or restrict the function to be called automatically/internally only, removing public re-invocation entirely.

### Proof of Concept
Foundry test plan:
1. Deploy `Airdrop` with `startTime = block.timestamp + 1`, deploy a mock ERC20 as `aidropToken`.
2. `register()` 3 users (A, B, C) with equal allocations (e.g., 100e18 each); fund the contract with exactly `300e18` tokens (matching total allocation, no over-collateralization).
3. Warp time to before `periodsEndTime[4]` but after `periodsEndTime[0]`; have a 4th user D (allocation 100e18, registered too, total funded 400e18) claim early so that `totalBonus` becomes nonzero (forfeited remainder).
4. Warp to `periodsEndTime[4]`.
5. User A calls `claim()` — this internally calls `updateEndRemainingAllocation()` for the first time, snapshotting `totalEndRemainingAllocation = D0` (sum of B, C's remaining allocations, e.g., 200e18), and A receives its share of `totalBonus`.
6. Attacker (user B) directly calls `updateEndRemainingAllocation()` again — this resets `totalEndRemainingAllocation` to the now-smaller `totalRemainingAllocation` (100e18, just C's allocation), since A already claimed.
7. B calls `claim()`, receiving `100e18/100e18 * totalBonus = totalBonus` (100% of the bonus pool), in addition to A's earlier share — total bonus paid out now exceeds `totalBonus`.
8. Assert: `getClaimableAmount(C)` (base allocation, no bonus needed) plus previously paid amounts exceeds `aidropToken.balanceOf(address(this))` before C claims.
9. C calls `claim()` and assert it reverts with `InsufficientBalance()`, proving funds are frozen due to the manipulation. [1](#0-0)

```text
    /// @notice This will store the ending remaining amount for the bonus.
    function updateEndRemainingAllocation() public {
        if (block.timestamp >= periodsEndTime[4]) {
            totalEndRemainingAllocation = totalRemainingAllocation;
        }
    }

    /// @notice Claim MGP and forfeit remaining allocation
    function claim() external {
        if (totalEndRemainingAllocation == 0) {
            updateEndRemainingAllocation();
        }
        uint256 claimableAmount = getClaimableAmount(msg.sender);
        
        if(claimableAmount == 0) revert NothingToClaim();
        if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
```
