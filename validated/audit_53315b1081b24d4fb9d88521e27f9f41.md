Key fact confirmed directly in the codebase: sharded execution is explicitly marked as benchmark/perf-test only, not part of the production consensus path.`No Vulnerability found for this question.`

**Reasoning:**

The sharded block executor (`aptos-move/aptos-vm/src/sharded_block_executor/`) is explicitly documented as a benchmark-only execution path, not part of the mainnet consensus-critical execution flow. This is confirmed directly in the code: `ExecutableBlock::new` states "the sharded executor is only for benchmark purpose right now" [1](#0-0) , and the default `VMBlockExecutor::execute_block_sharded` trait method is `unimplemented!("sharded not supported")` unless explicitly overridden [2](#0-1) .

Even setting aside production relevance, the described mechanism does not create an attacker-controlled bypass:

1. Cross-shard dependency edges (which govern what `CrossShardStateView` waits on before allowing a global-round transaction to read a key) are computed by the **block partitioner's static conflict analysis** of read/write locations before any execution occurs [3](#0-2) , not by attacker-supplied transaction content directly influencing what the executor waits for.

2. `CrossShardStateView::get_state_value` only special-cases keys pre-registered from `required_edges_iter()`; any key not in that dependency set falls through to `base_view` (the pre-block canonical state), meaning the module compatibility check would see the genuinely committed on-chain bytecode, not a "stale" writer's local buffer [4](#0-3) .

3. `GlobalExecutor::execute_global_txns` (the file in question) only forwards to `ShardedExecutorService::execute_transactions_with_dependencies` with `GLOBAL_ROUND_ID` [5](#0-4) ; it contains no independent logic for module publish, compatibility checking, or write-set application — those all happen inside `AptosVMBlockExecutorWrapper::execute_block` using the exact same VM/verifier/loader code path as non-sharded execution [6](#0-5) .

4. Even in a hypothetical scenario where the partitioner mis-declared a dependency (a partitioner correctness bug, not an "unprivileged input" attack), any resulting divergence in write sets would produce a different state root than the deterministic, non-sharded reference execution used by all other validators, causing the block/output to be rejected by consensus rather than allowing unauthorized code to land on chain. This is a potential internal correctness/liveness bug class, not a code-ownership, compatibility-bypass, or unauthorized-publish vulnerability as scoped by the Publish Impact Gate.

No unprivileged package, bytecode, or write-set input changes what code is verified, published, or committed through this path — the finding assumes an internal partitioner dependency-tracking flaw in a non-mainnet benchmarking subsystem, which is out of scope per the review's decision standard.

    pub fn create_cross_shard_state_view(
        base_view: &'a S,
        transactions: &[TransactionWithDependencies<AnalyzedTransaction>],
    ) -> CrossShardStateView<'a, S> {
        let mut cross_shard_state_key = HashSet::new();
        for txn in transactions {
            for (_, storage_locations) in txn.cross_shard_dependencies.required_edges_iter() {
                for storage_location in storage_locations {
                    cross_shard_state_key.insert(storage_location.clone().into_state_key());
                }
            }
        }
        CrossShardStateView::new(cross_shard_state_key, base_view)
    }
