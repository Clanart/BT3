### Title
Unchecked u64 overflow in payment/fee arithmetic lets crafted payment amounts bypass the insufficient-funds check and produce a consensus-invalid transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to CVE-2022-28737 (trusting an attacker-controlled size/amount field in arithmetic without bounds checks), `SignableTransaction::new` sums untrusted `u64` payment amounts and adds fee terms using unchecked `+` operators. Overflow wraps the solvency check, yielding a transaction whose outputs exceed its inputs — consensus-invalid — and `SignableTransaction::fee()` later underflows on `sum(inputs) - sum(outputs)`.

### Finding Description
In `SignableTransaction::new`, the input total, payment total, and required fee are computed with plain `u64` arithmetic:

- `input_sat` and `payment_sat` are unchecked sums: `inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>()` and `payments.iter().map(|payment| payment.1).sum::<u64>()` (send.rs:175, 187). `payment_sat` itself can wrap if the cumulative payment amounts exceed `u64::MAX`.
- The solvency gate uses unchecked addition: `if input_sat < (payment_sat + needed_fee)` (send.rs:215). `payment_sat + needed_fee` can wrap to a small value, so the `NotEnoughFunds` error is bypassed even when the true required amount vastly exceeds the inputs.
- The change path repeats the pattern: `input_sat.checked_sub(payment_sat + fee_with_change)` (send.rs:228) — `payment_sat + fee_with_change` wraps before the `checked_sub`, so the subtraction succeeds and produces a huge `value` pushed as a change `TxOut` at line 230 (`Amount::from_sat(value)` accepts any `u64`).
- Later, `fee()` computes `prevouts_sum - outputs_sum` with a bare `-` (send.rs:139-140); since outputs exceed inputs, this underflows — panic in debug builds, wrap to a near-`u64::MAX` "fee" in release.

Each individual payment only needs `*amount >= DUST` (send.rs:165-169), so e.g. two payments of ~`u64::MAX/2 + 546` sats pass per-output validation while their sum wraps. The resulting `SignableTransaction` is then signed by `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` (send.rs:355-428), which faithfully produce Taproot signatures over a transaction that no Bitcoin node will accept (outputs exceed inputs). The shim CVE's pattern — "field controls arithmetic, overflow corrupts the result" — maps directly: here the untrusted `u64` amounts control saturating-free arithmetic deciding whether the spend is solvent.

### Impact Explanation
A party able to influence the payment list passed to `SignableTransaction::new` (payment amounts are untrusted input to this public API) can drive the threshold group to produce a fully signed yet permanently unbroadcastable transaction, and/or panic the caller via `fee()` underflow. That burns a signing attempt and can stall/lock the affected inputs' spending flow (availability loss, Medium-class per the report's severity). It does not directly steal funds, since the overspending transaction is consensus-invalid.

### Likelihood Explanation
Exploitation requires the attacker to control payment amounts summing near `u64::MAX` — feasible wherever amounts are carried as raw `u64` without an upstream 21M-satoshi bound (the in-scope crate performs no such check). Reach is limited to availability/invalid-output outcomes, matching Medium.

### Recommendation
Use `checked_add`/`checked_sum` for `input_sat`, `payment_sat`, `payment_sat + needed_fee`, and `payment_sat + fee_with_change`, and `checked_sub` in `fee()`; also cap each payment amount at `MAX_MONEY` (21M BTC in sats) alongside the existing `DUST` lower bound.

### Proof of Concept
Call `SignableTransaction::new` with a single funded input (e.g. 1_000_000 sats) and two payments of `9_223_372_036_854_775_807 + 546` sats each. `payment_sat` wraps to ~1090; `payment_sat + needed_fee` stays small, so the `input_sat < (payment_sat + needed_fee)` check passes, and a change output is pushed with value near `u64::MAX` — a transaction paying out more than it consumes, which `TransactionSignatureMachine::complete` will nonetheless sign, and `fee()` will subsequently underflow/panic on.
