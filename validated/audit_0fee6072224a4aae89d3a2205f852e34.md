## Title
Missing zero-amount validation on predispatch order inputs permanently locks escrowed funds via `withdraw()`'s zero-balance guard - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) validates that every order input amount is non-zero at four separate points in `placeOrder` — including inside the predispatch branch. The Tron port of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reproduces the non-predispatch zero-check but **omits it entirely from the predispatch branch**, allowing a user to place an order whose `order.inputs` array contains a zero-amount leg. That zero-amount leg is later fatal in `withdraw()`, whose per-token guard treats a `0` escrow balance as "unknown token" and reverts — permanently blocking settlement/refund for the *entire* order, including its legitimately-escrowed non-zero legs.

### Finding Description
In the reference implementation, every code path that builds `order.inputs` enforces a non-zero amount: [1](#0-0) [2](#0-1) [3](#0-2) 

The Tron variant's predispatch branch does the equivalent balance/transfer bookkeeping but never checks `order.inputs[i].amount == 0`: [4](#0-3) 

Only the non-predispatch branch retains the check: [5](#0-4) 

Because `requiredAmount` can be `0`, the guard `if (balance < requiredAmount) revert InvalidInput();` is always satisfied (balance is `uint256`, never negative), so the loop accepts a zero-required leg unconditionally and records `_orders[commitment][token] += reducedInputs[i].amount` = `0` for that token.

This corrupted state (`_orders[commitment][token] == 0` for a token that is nonetheless part of a valid, committed order) collides with the guard used later in `withdraw()`, which is invoked from both the `RedeemEscrow` (successful fill) and `RefundEscrow` (cancel/timeout) paths: [6](#0-5) 

`withdraw()` iterates every token in `body.tokens` and reverts the *entire* call with `UnknownOrder()` if any single token's escrow balance reads `0` — which is exactly the state a zero-amount predispatch leg produces. Since `withdraw()` processes all of an order's tokens atomically before any transfer happens, one deliberately zero-valued leg is enough to make the whole withdrawal (and hence the entire settlement or refund message) permanently un-processable, trapping every other, legitimately-escrowed token in that same order.

### Impact Explanation
This is a fund-lock vulnerability reachable from the unprivileged, public `placeOrder()` entrypoint. Any user who (deliberately or accidentally) includes a zero-amount token in `order.inputs` while using the predispatch path creates an order whose cross-chain settlement (`RedeemEscrow`) and cancellation (`RefundEscrow`) messages will deterministically revert forever in `withdraw()`. All non-zero, legitimately escrowed tokens tied to that commitment become permanently unrecoverable — matching the bounty's "loss/lock of funds" class. Because the flaw is in production settlement-path bookkeeping (not a peer/relayer/prover trust assumption), it is in scope.

### Likelihood Explanation
The path only requires calling the public `placeOrder()` function with a predispatch order containing one input whose `amount` is `0` — no privileged role, relayer collusion, or malformed proof is needed. The bug is a straightforward parity gap between the audited/guarded EVM contract and the Tron port, making it easy to trigger and highly likely to be hit either by an attacker seeking to grief solvers/users or by a legitimate integrator whose order-construction logic doesn't defensively filter zero amounts (since the reference contract silently accepts this in its own contract instance without the check that Solidity mainline enforces).

### Recommendation
Add the same `if (order.inputs[i].amount == 0) revert InvalidInput();` check to the predispatch branch of `placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (mirroring `evm/src/apps/IntentGatewayV2.sol` line 233), so that zero-amount legs are rejected at order creation time regardless of whether predispatch is used. As defense-in-depth, `withdraw()` should also distinguish "token not part of this order" from "token present with legitimately-zero escrowed amount" (e.g., by tracking known tokens in a separate set/bitmap) so a single zero-value leg cannot brick settlement of the whole order.

### Proof of Concept
1. Attacker (or naive integrator) calls `placeOrder(order, graffiti)` on the Tron `IntentGatewayV2` with `order.predispatch.call.length > 0` and `order.predispatch.assets.length > 0`, and `order.inputs` containing two entries: one legitimate (e.g., 1000 USDC) and one with `amount = 0` for some token `T`.
2. In the predispatch loop (`evm/tron/contracts/apps/IntentGatewayV2.sol:410-440`), `requiredAmount = 0` for token `T` passes the `balance < requiredAmount` check unconditionally; `_orders[commitment][T] += 0` leaves the escrow record at `0`, while the legitimate USDC leg is escrowed normally.
3. Order proceeds to be filled cross-chain; the destination gateway dispatches a `RedeemEscrow` message with `body.tokens` including token `T`.
4. On the source chain, `onAccept` calls `withdraw(body, false)` (`evm/tron/contracts/apps/IntentGatewayV2.sol:682-705`); the loop hits `if (_orders[body.commitment][T] == 0) revert UnknownOrder();` and reverts the whole transaction.
5. The message can be resubmitted indefinitely and will always revert identically, so the escrowed 1000 USDC (and any other legs) can never be released to the solver, nor can the order later be refunded via the same `withdraw()` path on cancellation — funds are permanently locked in the gateway.
