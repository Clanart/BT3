### Title
Unbounded `u32` length prefix in `SchnorrAggregate::read` enables memory/CPU exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to the BigBlueButton `answerIds` DoS (CVE-2025-61601), where a single untrusted length field drove unbounded work, `SchnorrAggregate::read` trusts a 4-byte little-endian count read directly from attacker-controlled bytes and then loops `u32::from_le_bytes(len)` times performing an elliptic-curve point deserialization (`C::read_G`) per iteration — with no cap, no sanity bound, and no check that the claimed count is plausible for the remaining input.

### Finding Description
At `crypto/schnorr/src/aggregate.rs:77-88`, `SchnorrAggregate::read` does:

```rust
let mut len = [0; 4];
reader.read_exact(&mut len)?;
let mut Rs = vec![];
for _ in 0 .. u32::from_le_bytes(len) {
  Rs.push(C::read_G(reader)?);
}
```

The attacker fully controls `len` (up to 4,294,967,295). Each iteration executes `C::read_G`, which performs a full group-element decoding (field parsing, on-curve/decompression work, and depending on the ciphersuite a subgroup/torsion check — e.g., Ed25519/Ed448 via `dalek-ff-group`, secp256k1 via `kp256`) and pushes the resulting point into `Rs`. There is no relationship enforced between `len` and the actual size of the input; the only limit is the reader running out of bytes.

This is exactly Serai's shape of the reported bug class: a single untrusted length field causes work and memory consumption linear in bytes the attacker supplies, with a large constant factor (a curve point decode + allocation per ~32–57 bytes of input), up to a protocol-legal maximum of ~4 billion entries (~130+ GB of input and comparable heap) — far exceeding any legitimate aggregate size.

The matching write path (`write`, lines 93-104) and `verify` (lines 127-146) confirm `Rs` is semantically a list of signature nonces; legitimate aggregates in Serai's usage are bounded by the number of signers (a `u16` participant index space, i.e. ≤ 65535), so accepting up to `u32::MAX` entries is gratuitously permissive.

### Impact Explanation
Any party able to deliver serialized bytes to `SchnorrAggregate::read` (e.g., an aggregate signature supplied to a verifier/aggregation endpoint) can force the host to:

- Allocate an unbounded `Vec<C::G>` proportional to the attacker's payload (each entry a heap point, 32–100+ bytes of heap plus `Vec` growth).
- Burn CPU in variable-time point decompression for every element — thousands of cycles per ~33 input bytes.

A sustained stream of a few hundred MB of crafted "Rs" translates into minutes of CPU and GB-scale memory in a single `read` call, freezing or OOM-killing the process — paralleling the BBB finding where one oversized array froze the whole server. Unlike the `ThresholdKeys::read` path (whose count is a `u16` capped at 65,535 — `crypto/dkg/src/lib.rs:608-622`), this bound is `u32::MAX`, making it the strongest reachable resource-exhaustion analog in the in-scope code.

### Likelihood Explanation
`SchnorrAggregate::read` is a public API in the in-scope `crypto/schnorr` crate, in the same untrusted-bytes category as `DLEqProof::read`/`SchnorrSignature::read`. The only precondition is that an integrator deserializes aggregate signatures from an untrusted channel before verifying them — the normal usage pattern for a compact aggregate signature. No privileges, keys, or collusion are required; the attacker just needs to get bytes parsed.

### Recommendation
- Bound `len` before the loop: reject counts exceeding a protocol-meaningful maximum (e.g., `u16::MAX` signers) or the number of entries the remaining input could possibly contain (`remaining_bytes / C::G::Repr::len()`).
- Prefer `Vec::with_capacity` only after validation, and/or stream-check element count against the reader's known length when reading from `&[u8]`.

### Proof of Concept
```rust
use schnorr::SchnorrAggregate;
use ciphersuite::Secp256k1; // any Ciphersuite

// Attacker-crafted buffer: len = u32::MAX, followed by as many
// valid compressed points as bandwidth allows.
let mut buf = Vec::new();
buf.extend_from_slice(&u32::MAX.to_le_bytes());
// Append millions of valid 33-byte secp256k1 points (~33 bytes each).
// Server performs one point decode + one Vec push per 33 bytes
// received, with no upper bound on count or memory.
let mut slice = buf.as_slice();
let _ = SchnorrAggregate::<Secp256k1>::read(&mut slice);
// Even without filling the buffer, len is never validated against
// input size; with filled input, heap grows unboundedly to ~4B entries.
```

Note: amplification is linear in bytes actually supplied (no pre-allocation occurs), so impact requires a large attacker payload; severity is Medium-High depending on whether the surrounding transport already bounds message size. If the calling protocol enforces a small message cap upstream, this degrades to negligible; the library itself provides no defense.
