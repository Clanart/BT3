### Title
`Scanner::scan_transaction` accepts zero-value/dust outputs, enabling unbounded registration of unspendable outputs that force threshold-signing work - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to `sendMessage()` accepting zero-length data at zero fee, `Scanner::scan_transaction` accepts any transaction output whose `script_pubkey` matches a registered P2TR script with **no lower bound on `output.value`**. Any unprivileged party can mine or broadcast transactions creating arbitrarily many zero-value or sub-dust outputs to Serai's group key. Each is returned as a `ReceivedOutput`, fed into the processor's output-tracking and aggregation pipeline, and must eventually be spent by a threshold (FROST) signature whose fee cost exceeds the output's value — a costless-to-cheap way to saddle the network with unprofitable, effectively unspendable outputs.

### Finding Description
`Scanner` indexes registered offsets by `script_pubkey` and `scan_transaction` pushes a `ReceivedOutput` for every matching output, checking only the `vout` index bound. There is no `output.value` check anywhere in the in-scope crate:

```rust
// networks/bitcoin/src/wallet/mod.rs
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
``` [1](#0-0) 

Bitcoin consensus permits outputs with `value = 0` (they are merely relay-nonstandard, so an attacker with any miner access — or dust outputs, which are standard — can place them on-chain). Each `ReceivedOutput` is treated as funds received and becomes a candidate input for `SignableTransaction`, where Serai must run a full FROST signing session and pay the input's weight in fees. The processor-side code confirms this hazard was recognized but pushed the check out of the library: the scanner only filters `output.balance().amount.0 >= N::DUST` after `get_outputs` has already done per-transaction origin lookups, and `COST_TO_AGGREGATE` (800 sat) documents that aggregating an output costs real money. [2](#0-1) [3](#0-2) 

Note the dust filter lives in the processor and is applied per-key after scanning, while the in-scope `Scanner` itself — the component that decides "funds received" — reports everything, including 0-value outputs. `scan_block` also scans the coinbase with only a doc-comment caveat, again deferring safety to callers. [4](#0-3) 

### Impact Explanation
An attacker can create an unbounded number of dust/zero-value outputs to Serai's group key. Every such output is reported as received funds, enters DB tracking, and becomes an aggregation/spend candidate. Spending one requires a threshold signature and an input weight costing ~`COST_TO_AGGREGATE` fees, so outputs below that cost are funds reported received that are not economically spendable — the network either burns fees exceeding their value or accumulates unspendable UTXOs indefinitely. This maps directly onto the "fee-free spam of off-chain infrastructure" class: a zero-value output is the analog of a zero-length message — zero intrinsic cost borne by the sender beyond the carrier transaction, while the receiving infrastructure does real work per item.

### Likelihood Explanation
Reachable by any unprivileged party sending a Bitcoin transaction — the reachability bar for this analog. Dust outputs are relay-standard, so no miner cooperation is needed for sub-10,000-sat spam; zero-value outputs need only a single complicit/self-mined block. Cost to the attacker is bounded by the carrier transaction's fee, amortized over up to thousands of matching outputs per transaction, since `scan_transaction` iterates all outputs with no cap other than the `u32` vout bound.

### Recommendation
Enforce a minimum-value check inside `Scanner::scan_transaction` itself (e.g., skip outputs whose `value.to_sat()` is below a `dust_threshold` configured at construction, defaulting to the aggregation cost), rather than relying on every downstream consumer to filter. Document that `ReceivedOutput` is only emitted for economically spendable outputs, and keep the coinbase-maturity caveat consistent with it.

### Proof of Concept
On regtest (as in `networks/bitcoin/tests/wallet.rs::test_scanner`), craft a transaction with e.g. 100 outputs, each `TxOut { value: Amount::from_sat(0) /* or 1 sat */, script_pubkey: p2tr_script_buf(group_key) }`. `scanner.scan_transaction(&tx)` returns 100 `ReceivedOutput`s despite none being economically spendable, demonstrating the missing lower-bound check at `networks/bitcoin/src/wallet/mod.rs:199-214`. The analogous fix mirrors the audit recommendation: `if output.value.to_sat() < self.dust_threshold { continue; }` before pushing the output.

*Caveat: the processor's `N::DUST` filter partially mitigates this downstream, so residual impact in the full stack is bounded; the library-level gap and the per-output/per-tx scanning work remain real.*

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```

  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
