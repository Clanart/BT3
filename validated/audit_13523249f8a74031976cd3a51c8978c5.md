### Title
Zero-slippage WOM→mWOM buyback swap in `SmartWomConvert.convert()`/`_convertFor()` enables sandwich-attack theft of user deposits - ([File: wombat/SmartWomConvert.sol])

### Summary
`SmartWomConvert._convertFor()` executes the Wombat router swap of the buyback portion of WOM for mWOM with a hardcoded `amountOutMin` of `0`, and only checks the aggregate `_minRec` *after* the swap has already executed. When this path is reached with `_minRec == 0` — which happens for an ordinary, unprivileged user via `ArbWomUp3._deposit()` (mode 2) calling `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` — there is no slippage protection at all on the actual swap, allowing a classic sandwich attack to steal the swapped WOM value from the user/protocol. This directly mirrors the HAL-01 report's bug class (unsafe/absent `amountOutMinimum` on an on-chain swap reachable from a normal transaction).

### Finding Description
`SmartWomConvert.sol` internal function `_convertFor()` performs the actual DEX-level swap with a literal `0` passed as the router's minimum-output parameter: [1](#0-0) 
The caller-supplied `_minRec` is only enforced by a check *after* the swap has already been executed on-chain: [2](#0-1) 

This means the swap itself has zero on-chain slippage protection — the router will accept any execution price, including one manipulated by a sandwich bot, as long as the post-hoc aggregate check (`convertAmount + amountRec >= _minRec`) passes. If `_minRec` is `0`, the post-check is a no-op and the entire buyback amount can be sandwiched down to near-zero output with no revert.

The externally callable `convert()` function forwards the caller's `_minRec` unchanged into `_convertFor()`: [3](#0-2) 

An ordinary, unprivileged wallet reaches this exact zero-protection path through `ArbWomUp3.sol`'s public `incentiveDeposit()` → internal `_deposit()` (mode 2), which explicitly hardcodes `_minRec = 0` when converting half of the user's deposited WOM: [4](#0-3) 
`incentiveDeposit()` is external, unprivileged, and only requires `_amount != 0` and the contract not paused: [5](#0-4) 

By contrast, `WombatStaking._sendRewards()`'s call to `smartConvert()` is safer because `smartConvert()` forces `_minRec = _amountIn` before calling `_convertFor()`: [6](#0-5) 
but that internal safety net does not exist for the `convert()`/`convertFor()` entry points used by `ArbWomUp3`.

### Impact Explanation
Any user calling `ArbWomUp3.incentiveDeposit()` with `_mode == 2` has half of their deposited WOM routed through a swap with no slippage floor. A searcher can sandwich this transaction (front-run to push the WOM/mWOM pool price unfavorably, let the victim's swap execute at the manipulated price, then back-run to restore price and capture the difference), extracting value directly from the user's deposited principal. Because the mWom output from this swap is then locked into `mWomSV` on the user's behalf, the loss is a permanent, direct loss of the depositing user's funds (not just fees), matching the "direct theft of user funds" impact bar.

### Likelihood Explanation
The `_deposit()` mode-2 path is reachable by any unprivileged wallet with a single external call (`incentiveDeposit`) and no special preconditions beyond having WOM and the contract being unpaused. Wombat's WOM/mWOM pool typically has finite depth, and the WOM airdrop/incentive program is likely to attract meaningfully-sized deposits, making the attack profitable to a sandwiching bot whenever deposit size exceeds pool depth economics — a realistic and repeatable condition, not a contrived edge case.

### Recommendation
- Remove the hardcoded `0` in the router call inside `_convertFor()` and pass a real minimum output derived from `_minRec` (or an on-chain quote with configurable slippage tolerance) directly into `IWombatRouter.swapExactTokensForTokens()`, so unfavorable execution reverts atomically instead of after-the-fact.
- In `ArbWomUp3._deposit()`, stop hardcoding `_minRec = 0`; require callers of `incentiveDeposit()` to supply a caller-computed minimum acceptable output (computed off-chain immediately before submission), or have the contract fetch `IWombatRouter.getAmountOut()` at call time and apply a bounded slippage tolerance.
- Apply the same fix pattern used in `smartConvert()` (forcing `_minRec` to a value tied to `_amountIn`) uniformly across all callers of `_convertFor()`.

### Proof of Concept
1. Attacker monitors the mempool for calls to `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, 2)`.
2. Upon seeing a pending victim transaction, attacker front-runs by swapping a large amount of WOM into the WOM/mWOM Wombat pool, sharply increasing the WOM price relative to mWOM.
3. Victim's transaction executes: `_deposit()` mode 2 calls `smartWomConvert.convert(toSwap, _convertRatio, 0, 0)` → `_convertFor()` executes `IWombatRouter.swapExactTokensForTokens(..., 0, ...)`; because the router-level minimum is `0` and `_minRec` is `0`, the swap succeeds even though the victim receives far less mWom than fair value.
4. Attacker back-runs, swapping mWom back to WOM at the now-favorable price, capturing the value siphoned from the victim's deposit.
5. Victim's `mWomSV` lock reflects the reduced mWom amount — a permanent, unrecoverable loss of deposited principal.
