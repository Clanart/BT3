## Title
`reassembleResolvedFile` silently deletes conflict-marker blocks when Copilot's hunk count doesn't match the file's actual conflicts, corrupting what gets committed - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
This is the same bug-class as the Otc report: a value that falls below (or here, doesn't match) an implicit "minimum/expected" quantity is silently treated as if it were absent, so real content is dropped rather than the discrepancy being rejected or flagged. In the Otc contract, `gnsAmount < MIN_GNS_WEI_IN` let a trade through but the reward accumulator silently truncated to zero. In Desktop's Copilot conflict-resolution feature, `reassembleResolvedFile` walks the on-disk file (still containing `<<<<<<<`/`=======`/`>>>>>>>` markers) and splices in the model's per-hunk resolution "matched by order, not by line number" [1](#0-0) . If the number of hunk resolutions returned by the LLM is smaller than the number of well-formed conflict blocks actually present in the file, the code only splices content `if (hunkIndex < hunkResolutions.length)` [2](#0-1) ; for every conflict block beyond that count, nothing is pushed at all — both `ours` and `theirs` content, plus the markers, vanish with no substitute text, no error, and no warning.

### Finding Description
`reassembleResolvedFile` is the last stage before Copilot's suggested content is written to disk and staged for commit [3](#0-2) . The reassembly logic explicitly treats "malformed" markers (missing separator or missing closing marker) as safe pass-through content to "avoid data loss from malformed or stray markers" [4](#0-3) , but it applies no equivalent safety net for the case where the marker block *is* well-formed yet the model's `hunks` array is shorter than the number of blocks found:

```
if (hunkIndex < hunkResolutions.length) {
  const resolved = hunkResolutions[hunkIndex].resolvedContent
  if (resolved.length > 0) {
    resultLines.push(...resolved.split(/\r?\n/))
  }
}
hunkIndex++
``` [5](#0-4) 

Nothing in `parseCopilotConflictResolution` cross-checks `hunks.length` in the model's JSON response against the actual number of conflict blocks counted from `IFileConflictContext.rawContent`/`hunks` gathered by `copilot-conflict-context.ts` before reassembly is invoked in `reassembleResolutions` [6](#0-5) . The system prompt *asks* the model to return "one entry per conflict in the file" [7](#0-6) , but this is a prompt instruction, not an enforced invariant — an LLM response is inherently attacker-adjacent/unreliable input (truncated output, a dropped hunk due to context-window limits, or a hostile PR/commit whose description is crafted to bias the model into omitting a hunk). Any mismatch causes silent deletion of an entire merged section instead of a hard failure.

This mirrors the root cause of the Otc finding precisely: an unvalidated quantity (`gnsAmount` / hunk count) that falls short of what's needed is allowed through the "happy path," causing the operation to complete while silently under-recording/deleting the payload, rather than being rejected outright with a `BelowMin()`-style guard.

### Impact Explanation
The write path applies `resolution.resolvedContent` directly via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and then `git add`s the file [8](#0-7) . If a hunk resolution is missing, the resulting file is written and staged for commit/rebase/cherry-pick with an entire code region silently deleted — no conflict markers, no error, no diff-review flag beyond the standard diff view. Because the "malformed markers" guard could give a false sense of safety ("no data loss from malformed markers"), reviewers reasonably assume the reassembly is lossless when it is not. This can result in corrupted commits/pushes (removed logic, removed security checks, removed lines from lockfiles) that ship to the remote, which fits the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Medium. Triggering requires the number of hunk resolutions returned by Copilot's SDK response to differ from the number of well-formed conflict blocks in the file — plausible via model truncation, an attacker-influenced PR/commit description used as "context" that biases the model to omit a hunk, or large files where hunks are chunked (`SinglePromptFileLimit`/`MaxConcurrentChunks` batching at [9](#0-8)  introduces more surface for hunk-count drift across chunk boundaries). This is not a purely theoretical LLM hallucination scenario; the codebase's own comment/history around this feature (`changelog.json` mentions "Copilot conflict resolution data loss where file content outside conflicted regions was overwritten") shows the reassembly logic has already had at least one prior data-loss defect, indicating the splice-by-order design is fragile [10](#0-9) . No local/physical access or credentials are needed — the trigger is entirely within the normal "Resolve with Copilot" conflict-resolution flow that an unprivileged user invokes on their own repository state.

### Recommendation
Before calling `reassembleResolvedFile`, validate that `raw.hunks.length` exactly equals the number of well-formed conflict blocks counted from `rawContent` for that path, and throw a `CopilotValidationError` (triggering the existing retry path) on mismatch instead of silently proceeding. Additionally, change the reassembly loop so any conflict block for which no resolution exists is treated the same as a malformed marker (pass through the original ours/theirs content unresolved) rather than being deleted outright, ensuring the fail-safe behavior is symmetric for "too few hunks" and "malformed markers."

### Proof of Concept
1. Construct a file with two well-formed conflict blocks.
2. Have `reassembleResolutions` process a model response containing only one entry in `hunks` for that file (simulating truncated/short LLM output — no code path currently rejects this).
3. Call `reassembleResolvedFile(rawContent, [{resolvedContent: 'resolved-1'}])` on the file — the existing test suite already demonstrates the splice-by-index mechanics for the matching case [11](#0-10) ; running it with one fewer resolution than blocks shows the second conflict block's content (both `our-2` and `their-2`) is entirely omitted from the output, with no error and no marker.
4. `_applyCopilotConflictResolutions` writes this truncated content to disk and stages it via `git add`, so the corrupted file becomes part of the next commit/rebase/cherry-pick [8](#0-7) .

```typescript
export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
```
