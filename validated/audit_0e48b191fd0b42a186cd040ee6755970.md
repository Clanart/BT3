### Title
Unsanitized pull-request fork `clone_url` from GitHub API reaches `git remote add`/`fetch` without transport-protocol restriction, enabling `ext::` helper command execution - (File: app/src/lib/git/remote.ts, app/src/lib/stores/app-store.ts)

### Summary
The reported bug is about a broken invariant: an attacker-influenced identifier/value (a "distribution ID") is used to drive a state-changing operation without validating that it is safe to reuse, and the surrounding code performs no additional integrity check before acting on it. The closest reachable Desktop analog is the pull-request checkout flow, where a value that is fully controlled by an external, un-trusted GitHub API response (`pullRequest.head.repo.clone_url`) is fed straight into `git remote add` and subsequently `git fetch`, with no allow-listing of the transport scheme (`ext::`, `fd::`, `file://`, etc.) that Git supports.

### Finding Description
When the user opens a pull request from a URL/deep link or from the PR list, `openPullRequestFromUrl` in `dispatcher.ts` fetches PR metadata from the GitHub API and forwards the head repository's `clone_url` unmodified into `_checkoutPullRequest`: [1](#0-0) 

That flows into `_findPullRequestBranch`, where the URL is passed directly to `addRemote`: [2](#0-1) 

`addRemote` shells out to `git remote add <name> <url>` with the API-provided URL as a raw, unsanitized argument and no separator/allow-list is applied: [3](#0-2) 

The remote is then fetched via `_fetchRemote`, which will cause Git itself to interpret the `url` value and choose a transport based on its scheme. I found no code anywhere in `app/src/lib/git/environment.ts` or the remote/fetch code paths that sets `GIT_ALLOW_PROTOCOL`, restricts the url scheme, or rejects Git's `ext::`/`fd::` "remote helper" transports before invoking `git remote add`/`git fetch` on a value that originates from a network response rather than something the user typed: [4](#0-3) 

Git natively supports remote helpers such as `ext::<command>` that execute an arbitrary shell command as the "transport" for a URL. If the `clone_url` field of a PR's head repository (as returned by the GitHub API, or by a malicious/compromised GitHub Enterprise server, which the report explicitly lists as an in-scope attacker-controlled surface) is `ext::sh -c "curl$IFS...|sh"` or similar, `git remote add` will store it, and `git fetch <remote-name>` will execute the embedded command via the `ext` transport with no user confirmation. Unlike `parseAppURL`'s handling of `branch`/`filepath` (which is explicitly validated with `testForInvalidChars` and `resolveWithin`), this is a case where the value corrupted is the git remote URL stored in `.git/config`, which is used unchecked for a live network operation.

### Impact Explanation
If exploitable, this results in arbitrary command execution on the user's machine, triggered purely by the user clicking "View on GitHub Desktop" / opening a PR from a repository whose GitHub (Enterprise) API response is attacker-controlled. This matches the in-scope impact classes: code execution via a "GitHub API object" the attacker controls, without any admin rights, local access, or pre-existing malware.

### Likelihood Explanation
This requires the attacker to control (or spoof/compromise) the GitHub API response describing the PR's head repository `clone_url` — feasible against a malicious/compromised GitHub Enterprise Server endpoint or a man-in-the-middle on that connection, both of which are explicitly in-scope per the "GitHub API object" and "git remote/proxy response" categories in the report's Valid Impact section. I was not able to fully confirm from the indexed code whether dugite/Git on the host is configured system-wide with `GIT_ALLOW_PROTOCOL` restrictions (e.g. via a bundled `gitconfig` or dugite's own defaults) that would neutralize `ext::`, since that configuration may live in the bundled Git distribution rather than in this repository's TypeScript sources — this is a gap in what I could verify from the index alone.

### Recommendation
- Validate `clone_url` values retrieved from the API before passing them to `addRemote`/`git fetch`: enforce an allow-list of schemes (`https:`, `http:`, `git:`, `ssh:`) and reject `ext::`, `fd::`, `file://`, and other local/helper transports.
- Alternatively/additionally, set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` in the environment used for these specific operations (`envForRemoteOperation` in `app/src/lib/git/environment.ts`) rather than relying on Git's own defaults.
- Apply the same validation consistently anywhere else an API-derived clone URL is used to add a remote (e.g., `addUpstreamRemoteIfNeeded`, `ensureUpstreamRemoteURL` in `git-store.ts`).

### Proof of Concept
Conceptual (I could not execute this, only trace the code path):
1. Point Desktop at a malicious/compromised GitHub Enterprise endpoint, or MITM the API response for a pull request.
2. Craft the PR API response so `head.repo.clone_url` = `ext::sh -c "touch /tmp/pwned"`.
3. User opens that PR from Desktop (e.g., via "Open in Desktop" deep link `x-github-client://openRepo/...?pr=<n>`, handled in `parse-app-url.ts`/`dispatcher.ts`).
4. `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` → `addRemote(repository, forkRemoteName, headCloneUrl)` stores the malicious URL, then `_fetchRemote` invokes Git against that remote, triggering the `ext::` helper and executing the embedded command. [5](#0-4)
