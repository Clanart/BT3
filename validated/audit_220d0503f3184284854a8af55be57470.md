## Finding: Unbounded login capture in `StealthEmailRegexp` flows unsanitized into authenticated `api.fetchUser()` call

### Summary

`parseStealthEmail`'s regex allows an attacker-crafted commit author email to inject an arbitrary string (including `/`, `.`, `[`, `]`) as the "login," and this value is passed unvalidated into `api.fetchUser(login)`, which issues an authenticated request (with `account.token`) using that string as part of the request path. I was able to confirm the vulnerable regex and its usage in `avatar.tsx`, but ran out of tool budget before verifying the exact URL-building logic in `app/src/lib/http.ts`/`api.ts`'s `request()` function, which determines the full blast radius (same-host path manipulation vs. cross-host SSRF/token leak). That verification gap is noted explicitly below.

### Finding Description

`StealthEmailRegexp` is defined as: [1](#0-0) 

`parseStealthEmail` requires the domain portion (group 3) to exactly equal the expected stealth host (`users.noreply.github.com` or the GHES equivalent), but places no restriction whatsoever on the characters allowed in the login capture group (group 2): [2](#0-1) 

Because group 2 uses a lazy `(.+?)`, the regex engine will expand it to include any characters — including `/`, `..`, `[`, `]`, even embedded `@` characters — up until the point where the remainder of the string exactly matches `@users.noreply.<host>$`. This means an attacker-controlled commit author email such as `../../evil[bot]@users.noreply.github.com` (embedded in a cloned repository's git history) parses successfully, yielding `login = "../../evil[bot]"`.

This untrusted `login` is then used in `getBotLogin`, which only checks that it ends with `[bot]` before treating it as a legitimate bot login: [3](#0-2) 

`botAvatarCache`'s resolver then calls `api.fetchUser(login)` using the current account's token: [4](#0-3) 

This flow is triggered automatically whenever an `Avatar` component mounts/updates for a commit author matching a stealth-email pattern, via `resolveBotAvatar` in `componentDidMount`/`componentDidUpdate`: [5](#0-4) 

No sanitization of `login` (e.g., restricting to valid GitHub username characters `[A-Za-z0-9-]`) occurs anywhere in this chain before it reaches `api.fetchUser`.

### Impact Explanation

An authenticated API request (bearing `account.token`) is constructed from attacker-controlled text with no character restrictions. At minimum this allows path-segment injection (e.g., `..` traversal, `/` injection) into the request path used by `api.fetchUser`, potentially causing the client to hit unintended API paths on the configured endpoint host while attaching the user's OAuth token. Whether this can be escalated to a cross-host request (i.e., token exfiltration to an attacker-controlled server) depends on how the low-level `request()`/URL-joining logic in `app/src/lib/http.ts` resolves the path (e.g., whether a `//host` or absolute-URL-like login value can override the resolved host in a `new URL(path, base)` call). **I was not able to inspect that file within the available tool budget**, so I cannot confirm or rule out full SSRF/cross-host token leakage — only that unsanitized, attacker-controlled data reaches the request-construction sink is confirmed.

### Likelihood Explanation

Reachability is straightforward and requires no unusual user action: merely cloning/fetching a repository containing a commit with a crafted author email is enough to trigger `Avatar` rendering (e.g., in commit lists, history view) and thus the vulnerable `getBotLogin` → `api.fetchUser` chain, satisfying the "attacker controls a cloned/fetched repository" scope condition.

### Recommendation

Restrict the login capture group in `StealthEmailRegexp` to valid GitHub username characters (alphanumeric and hyphens, plus the literal `[bot]` suffix for bot accounts), e.g. `^(?:(\d+)\+)?([a-z0-9](?:-?[a-z0-9])*(?:\[bot\])?)@(users\.noreply\..+)$`. Additionally, `api.fetchUser` (and any other API call site consuming `login` derived from `parseStealthEmail`) should validate/encode the login (e.g., `encodeURIComponent`) and reject values containing path-control characters (`/`, `..`, `@`, etc.) before constructing request URLs.

### Proof of Concept

1. Create a commit in a repository with author email `../../evil[bot]@users.noreply.github.com`.
2. Have the victim clone/fetch this repository in GitHub Desktop and view the commit (triggering `Avatar` render with this author).
3. `getAvatarUserFromAuthor` constructs an `IAvatarUser` with `email = "../../evil[bot]@users.noreply.github.com"`.
4. `getBotLogin` calls `parseStealthEmail(email, endpoint)`, which returns `{ login: "../../evil[bot]" }` since the domain suffix matches exactly and the lazy capture absorbs everything before the literal `@users.noreply.github.com`.
5. Since `"../../evil[bot]".endsWith('[bot]')` is true, `getBotLogin` returns this attacker string as a legitimate login.
6. `botAvatarCache`'s resolver calls `api.fetchUser("../../evil[bot]")` with the signed-in account's token attached, sending the attacker-controlled string into the request path construction — confirmed at the code level; the ultimate resolved URL/host depends on unverified logic in `http.ts`. const StealthEmailRegexp = /^(?:(\d+)\+)?(.+?)@(users\.noreply\..+)$/i

export const parseStealthEmail = (email: string, endpoint: string) => {
  const stealthEmailHost = getStealthEmailHostForEndpoint(endpoint)
  const match = StealthEmailRegexp.exec(email)

  if (!match || stealthEmailHost !== match[3]) {
    return null
  }

  const [, id, login] = match
  return { id: id ? parseInt(id, 10) : undefined, login }
}

const getBotLogin = (user: IAvatarUser) => {
  const { endpoint } = user
  if (user.avatarURL !== undefined || endpoint === null) {
    return undefined
  }

  const match = parseStealthEmail(user.email, endpoint)

  return match?.login?.endsWith('[bot]') ? match.login : undefined
}

const botAvatarCache = new ExpiringOperationCache<
  { user: IAvatarUser; accounts: ReadonlyArray<Account> },
  IAvatarUser
>(
  ({ user }) => `${user.endpoint}:${user.email}`,
  async ({ user, accounts }) => {
    const { endpoint } = user
    if (user.avatarURL !== undefined || endpoint === null) {
      throw new Error('Avatar URL already resolved or endpoint is missing')
    }

    const account = accounts.find(a => a.endpoint === user.endpoint)

    if (!account) {
      throw new Error('No account found for endpoint')
    }

    const login = getBotLogin(user)

    if (!login) {
      throw new Error('Email does not appear to be a bot email')
    }

    const api = new API(endpoint, account.token)
    const apiUser = await api.fetchUser(login)

    if (!apiUser?.avatar_url) {
      throw new Error('No avatar url returned from API')
    }

    return { ...user, avatarURL: apiUser.avatar_url }

    const { accounts } = this.props
    const { user } = this.state

    if (user?.endpoint && !user.avatarURL && getBotLogin(user)) {
      botAvatarCache
        .get({ user, accounts })
        .then(resolved => {
          if (
            !this.cancelAvatarRequests &&
            user.endpoint === resolved.endpoint &&
            user.email === resolved.email &&
            user.name === resolved.name &&
            user.avatarURL !== resolved.avatarURL

              this.resetAvatarCandidates()
            )
