### Title
OP_RETURN data output omitted from weight/fee calculation causes fee underestimation and potentially non-standard transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output carrying user-supplied `data` to `tx_outs`, but `calculate_weight_vbytes` reconstructs the transaction from `payments` (and optional `change`) only — it never models the `OP_RETURN` output. Every subsequent size-derived quantity (vbytes, `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check) is therefore computed on a smaller transaction than the one actually produced and signed.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is pushed into `tx_outs` at `networks/bitcoin/src/wallet/send.rs:194-202`:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```

However, the fee calculation at lines 204–206 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a fresh `Transaction` whose outputs are only `payments` plus an optional change output (lines 85–99). The data output is never included. The same omission applies to the change branch (lines 225–227) and to the final `weight > MAX_STANDARD_TX_WEIGHT` standardness check at line 241, since `weight`/`weight_with_change` both derive from the same payment-only reconstruction.

This is the Serai-shaped analog of the reported bug class: an amount/size is used without accounting for a component that changes the real value — the caller pays a fee computed for a transaction that is not the transaction being signed.

### Impact Explanation
An `OP_RETURN` output with `data` adds ~11–91 bytes (output overhead plus pushdata of up to 80 bytes, per the `data.len() > 80` check at line 171) that are charged no fee. Consequences:

- The realized fee rate (`(sum(inputs) - sum(outputs)) / actual_vsize`) is lower than the caller-requested `fee_per_vbyte`.
- The `TooLowFee` guard at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` where `vbytes` is underestimated, so the check can pass while the real transaction is below the minimum relay fee and will not propagate.
- The `MAX_STANDARD_TX_WEIGHT` check at line 241 can pass while the actual transaction exceeds the standard weight limit, producing a signed transaction that can never be relayed or mined — funds are committed to inputs of a permanently unbroadcastable transaction until a replacement is constructed.

### Likelihood Explanation
Reachable by any caller of `SignableTransaction::new` who supplies `Some(data)` (an untrusted byte vector up to 80 bytes) together with a `fee_per_vbyte` near the minimum, or with input/output counts near `MAX_STANDARD_TX_WEIGHT`. No privileged position is required; the inputs (payments, change, data, fee rate) are all caller-controlled public values. The error is deterministic whenever `data` is present; it is simply bounded in magnitude by the 80-byte cap.

### Recommendation
Include the data output in the transaction reconstructed inside `calculate_weight_vbytes`. Either pass the `OP_RETURN` `ScriptBuf` (or its serialized length) into `calculate_weight_vbytes` and append a `TxOut { value: Amount::ZERO, script_pubkey }` to `tx.output`, or restructure the function to compute weight/vbytes from the fully assembled `tx_outs` plus the candidate change output. This ensures `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction actually signed in `TransactionSignMachine::sign`.

### Proof of Concept
```rust
// Conceptual reproduction against SignableTransaction::new
// in networks/bitcoin/src/wallet/send.rs
//
// Construct inputs, one payment, no change, and 80 bytes of OP_RETURN data:
let data = Some(vec![0u8; 80]); // passes the <= 80 check
let tx = SignableTransaction::new(inputs, &payments, None, data, fee_per_vbyte).unwrap();

// needed_fee was computed as fee_per_vbyte * vbytes_of(payments-only tx)
let estimated = tx.needed_fee();

// The real transaction carries an extra ~91-vbyte OP_RETURN output:
let actual_vsize = tx.transaction().vsize() as u64;

// The effective fee rate is strictly below the requested one:
// fee() / actual_vsize < fee_per_vbyte
// and if fee_per_vbyte == 1 sat/vb, fee() can be < DEFAULT_MIN_RELAY_TX_FEE
// * actual_vsize / 1000 even though the TooLowFee check passed, leaving the
// signed transaction unrelayable / below the standard weight accounting.
```

The divergence is bounded by the size of the `OP_RETURN` output (~91 vbytes max), so severity is limited to Medium: it produces fee-miscalculated or non-standard transactions rather than direct fund theft.
