### Title
Ed448 point decoding's torsion-free check is vacuous, accepting small-order/torsion points as `PrimeGroup` members - ([File: crypto/ed448/src/point.rs](crypto/ed448/src/point.rs))

### Summary
Analogous to the reported bug class — a library assuming externally supplied objects comply with the strict invariants the protocol requires (there: ERC20-compliant tokens; here: prime-order group elements) — `Point::is_torsion_free` in `crypto/ed448` is mathematically a no-op. Every curve point that decompresses is accepted as torsion-free, so untrusted bytes passed to `read_G`, `DLEqProof::read`, `SchnorrSignature::read`, `ThresholdKeys::read`, etc. can decode order-2 and order-4 torsion components into a type declared to be a `PrimeGroup`.

### Finding Description
`Point::is_torsion_free` is implemented as:

```rust
fn is_torsion_free(&self) -> Choice {
    ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
}
```

`Scalar::ZERO - Scalar::ONE` is `-1 mod l` (where `l` is the Ed448 prime subgroup order / scalar modulus). Multiplying a point by `-1` and adding the original point yields the identity for *every* point, unconditionally. The expression is `(-P) + P == identity`, which is always true. The check therefore never rejects anything.

This matters because Ed448 has cofactor 4: the curve contains a prime-order subgroup plus a small torsion subgroup of order 4. `GroupEncoding::from_bytes` (crypto/ed448/src/point.rs:303-319) gates acceptance on `not_negative_zero & point.is_torsion_free()`, so the torsion gate is the only thing preventing small-order points from becoming `Point` values. With it vacuous, any decompressible encoding — including points with order 1, 2, or 4 — is returned as a valid `CtOption`.

Upstream, `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101) only checks decode success and canonical re-encoding; it does not reject identity or torsion. `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) rejects the identity but not non-identity torsion points (order 2/4). All deserialization entry points listed as attacker-reachable (`read_G`, `DLEqProof::read`, `SchnorrSignature::read`, `Commitments::read`, `read_share`, `ThresholdKeys::read`, `ReceivedOutput::read`) therefore admit torsioned `Ed448`/`Ed25519`-style points when the ciphersuite is `Ed448`.

The type-level contract is broken: `Point` claims `PrimeGroup` membership (crypto/ed448/src/point.rs:16), yet instances can carry order-4 torsion components that all downstream verification math assumes are absent.

### Impact Explanation
Verification equations across the codebase compute with scalars reduced mod `l`, so scalar multiplication cannot cancel torsion components: for a torsion point `T` of order 4 and challenge `c`, `[c]T = [c mod 4]T`, not `0`. An attacker feeding untrusted bytes can substitute `P' = P + T` wherever a canonical prime-order point is expected, shifting a verification equation's torsion component by a controllable amount.

Concretely for `DLEqProof`/`SchnorrSignature` verification on `Ed448`, the check is a linear relation `Σ w_i P_i = 0` evaluated via `multiexp_vartime` (crypto/schnorr/src/lib.rs:88-100, crypto/dleq/src/lib.rs). An attacker who adds an order-4 component `T` to a submitted point must only satisfy the equation modulo the torsion subgroup, i.e. `T + [c mod 4]T' = 0`. Since `c mod 4` has only 4 possible values and `c` is derived from a hash over attacker-chosen bytes, the attacker can grind free nonce/randomness bytes until `c mod 4` takes the needed value (~4 expected attempts). This yields proofs/signatures that verify for points whose prime-order discrete log relationship does not hold — a forged proof/signature accepted by `verify`, and acceptance of `ThresholdKeys`/verification-share encodings whose group key is offset by torsion, making funds reported under a corrupted key effectively unspendable or attributing shares to the wrong verification share.

### Likelihood Explanation
Fully attacker-reachable: any untrusted serialized point fed to a `read_*`/`verify` API for the `Ed448` ciphersuite can carry a torsion component. Exploitation requires only fixing a 2-bit condition on a hash output, which is trivially grindable by varying attacker-controlled message/nonce bytes. Severity is bounded by the need for a ciphersuite deployment that uses `Ed448` (the crate and its FROST curve wrapper exist in-tree at crypto/frost/src/curve/ed448.rs) and a protocol path where the torsioned relation is security-relevant.

### Recommendation
Implement a real subgroup check. Options:
- Multiply by the true subgroup order using a wide-scalar/double-and-add path (the scalar field `mod l` cannot represent `l`, so `is_torsion_free` must not use `Scalar` multiplication), e.g. compute `[l]P` with a dedicated addition chain or the cofactor-aware technique of checking `[4]P`'s subgroup membership via `[l]([4]P)` equivalently testing whether `P` lies in the image of multiplication-by-4 on decoded points.
- Alternatively reject any point for which `[4]P` has order < `l` by checking `[l]P == identity` via a `crypto_bigint`-based scalar mul over `U448` with the non-reduced modulus `l`.
- Additionally reject the identity in `Ciphersuite::read_G` or at each consumer, matching `Curve::read_G`'s existing identity rejection.

### Proof of Concept
In `crypto/ed448/src/point.rs`, for any `Point` `P` (including a pure order-4 torsion point or `Q + T`):

```
(*P * (Scalar::ZERO - Scalar::ONE)) + P == (-P) + P == identity
```

so `Point::from_bytes` returns `CtOption::new(point, 1)` — accepting any decompressible encoding. A test: decode the Ed448 low-order encodings (e.g., the order-2 point `y = -1, x = 0`, and the two order-4 points with `x^2 = -1`) via `Ed448::read_G`; all are accepted despite none being in the prime-order subgroup. Feeding such a point as `R` in `SchnorrSignature::read`/`verify` or inside `DLEqProof::read`-consumed buffers lets the torsion component survive verification math, enabling the `c mod 4` grinding forgery described above.
