### Title
Legacy EVM precompiles dereference a possibly-nil `*DBImpl` in their error-defer path, causing a node panic on `SetPrecompileError` - ([File: precompiles/pointer/legacy/v552/pointer.go])

### Summary
Multiple legacy-versioned EVM precompile implementations register a `defer` that unconditionally dereferences the result of `state.GetDBImpl(evm.StateDB)` to call `.SetPrecompileError(err)`, without checking for `nil` first — the same bug class as CVE-2024-56634 (an unchecked possibly-nil return value dereferenced in a reachable code path). The current/non-legacy implementation of this same defer logic was hardened to check for `nil` before dereferencing, confirming the pattern is a known-fixed defect that still exists in the legacy, per-height precompile snapshots kept in the repository.

### Finding Description
`state.GetDBImpl` performs a type assertion on `evm.StateDB` and returns `nil` when the StateDB is not the expected `*DBImpl` concrete type. The `Prepare` helper used by these precompiles already checks for this: [1](#0-0) 

But the top-level `RunAndCalculateGas`/`Run` defer in the legacy pointer precompile does **not** perform the same check — it calls `state.GetDBImpl(evm.StateDB)` a second time and immediately dereferences it: [2](#0-1) 

Because `p.Prepare(evm, input)` itself returns an error precisely in the case where `state.GetDBImpl(evm.StateDB)` is `nil` (`"cannot get context from EVM"`), the `err != nil` branch of the defer is guaranteed to run for exactly the case where `GetDBImpl` will return `nil` again — producing an unconditional nil-pointer dereference and a panic. The same defer pattern (`state.GetDBImpl(evm.StateDB).SetPrecompileError(err)`) is repeated, unguarded, across a wide set of legacy precompile packages and legacy versions of the shared `common` helper: `precompiles/addr/legacy/v555/addr.go`, `precompiles/bank/legacy/v552`, `precompiles/bank/legacy/v555`, `precompiles/distribution/legacy/v552`, `precompiles/distribution/legacy/v555`, `precompiles/gov/legacy/v555`, `precompiles/json/legacy/v552`, `precompiles/json/legacy/v555`, `precompiles/oracle/legacy/v555`, `precompiles/pointer/legacy/v552`, `precompiles/pointer/legacy/v555`, `precompiles/pointerview/legacy/v555`, `precompiles/staking/legacy/v555`, `precompiles/wasmd/legacy/v552`, `precompiles/wasmd/legacy/v555`, and `precompiles/common/legacy/{v562,v575,v580,v600,v605,v606,v610}/precompiles.go`.

By contrast, the current (non-legacy) implementation fixed this exact issue by adding a `nil` guard: [3](#0-2) 
and the later legacy revisions (`v66`, `v67`, `v614`, `v620`, `v630`, `v640`, `v65`) also carry the fixed `HandlePrecompileError` with the guard, confirming this was a real, previously-latent defect in the earlier snapshots that remains present in those older, still-shipped packages.

### Impact Explanation
If `evm.StateDB` is ever not the expected `*DBImpl` concrete type when one of these legacy-versioned precompiles is invoked (e.g., during any EVM execution path that wraps or substitutes the StateDB — such as tracing/simulation call paths that reuse the historical, per-height precompile set for old blocks), the `defer` in `RunAndCalculateGas`/`Run` will panic with a nil-pointer dereference. Because this occurs inside EVM/precompile execution that participates in consensus state transition (or, for read/trace-only paths, inside the node process serving public RPC), the practical outcomes are either a crash of the executing node process (validator halt / crash of default-configuration RPC nodes) or a panic during transaction processing that must be recovered by the same guard already added upstream to prevent a chain-wide failure.

### Likelihood Explanation
These precompile "legacy" packages exist specifically because sei-chain locks previously-deployed precompile behavior to be replayed unchanged at historical block heights (an EVM/height-based precompile registry pattern used throughout this codebase, evidenced by the parallel `legacy/vNNN` directory structure for `pointer`, `bank`, `addr`, `distribution`, `gov`, `json`, `oracle`, `staking`, `wasmd`, and `common`). Any caller that triggers one of these precompiles at a historical height — including a public RPC client issuing a call/trace against an old block, or normal block replay — can exercise the vulnerable defer. I was not able to fully confirm from index-limited search whether all call sites that could pass a non-`*DBImpl` `StateDB` are reachable via public unauthenticated RPC in the current build; this should be verified directly in a running node.

### Recommendation
Apply the same `nil`-check fix that was already made in the current `precompiles/common/precompiles.go` (`HandlePrecompileError`) to every legacy precompile package listed above: guard the `state.GetDBImpl(evm.StateDB)` call in the `defer` with a `nil` check before calling `.SetPrecompileError(err)`, e.g.:
```go
defer func() {
    if err != nil {
        if sdb := state.GetDBImpl(evm.StateDB); sdb != nil {
            sdb.SetPrecompileError(err)
        }
    }
}()
```
Since these are historical/frozen packages, consider consolidating them to call a single shared, already-patched `HandlePrecompileError` helper rather than duplicating the unguarded pattern in each legacy version.

### Proof of Concept
1. Construct/obtain an EVM execution context whose `vm.EVM.StateDB` is not backed by `*state.DBImpl` (any StateDB implementation used by a non-standard call/trace/simulation path).
2. Route a call to the historical pointer precompile at address `0x000000000000000000000000000000000000100b` for a block height mapped to the `v552`/`v555` precompile set (or any other affected legacy precompile/address).
3. `p.Prepare(evm, input)` calls `state.GetDBImpl(evm.StateDB)`, gets `nil`, and returns the error `"cannot get context from EVM"`. [1](#0-0) 
4. `RunAndCalculateGas` returns with `err != nil`; its deferred function executes `state.GetDBImpl(evm.StateDB).SetPrecompileError(err)`, calling `GetDBImpl` again (still `nil`) and immediately dereferencing it. [4](#0-3) 
5. The node panics with a nil-pointer dereference inside precompile execution.
