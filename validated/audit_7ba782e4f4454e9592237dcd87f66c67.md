### Title
Bitcoin deposits below the `DUST` threshold are received at the multisig address but silently dropped by the Scanner, permanently locking user funds - ([File: processor/src/multisigs/scanner.rs])

### Summary
The external report describes a deposit path that accepts an asset while the corresponding redemption path is disabled, leaving user funds locked. The direct Serai analog lives in the Bitcoin processor's scanner: any output sent to the multisig's P2TR script whose value is below `Bitcoin::DUST` (10,000 sats) is detected by `Scanner::scan_transaction` but then discarded in `processor/src/multisigs/scanner.rs`, never emitted as a `ScannerEvent::Block`, never written via `ScannerDb::save_outputs`, and therefore never spendable by the threshold multisig. An unprivileged party only needs to broadcast a Bitcoin transaction paying <10,000 sats to the Serai deposit address to permanently burn funds against the multisig.

### Finding Description
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` reports every output whose `script_pubkey` matches a registered script, regardless of value (lines 199-214). The processor-side filter is applied later in `processor/src/multisigs/scanner.rs`:

```rust
for output in network.get_outputs(&block, key).await {
  assert_eq!(output.key(), key);
  if output.balance().amount.0 >= N::DUST {
    outputs.push(output);
  }
}
```

For Bitcoin, `N::DUST` is 10,000 sats (`processor/src/networks/bitcoin.rs` line 638). An output below this value is silently dropped. Because outputs are only persisted and routed into plans via the emitted `ScannerEvent::Block { outputs }`, a dropped output is never scheduled into a `SignableTransaction` input set. There is no sweep/refund path and no way for the depositor to reclaim the funds — the multisig only ever signs spends of outputs that were reported, so the sats remain locked at the threshold key's script forever. This mirrors the report exactly: a deposit is accepted on-chain (the script accepts any amount; there is no protocol-level minimum on a P2TR output), while the "redemption" path (inclusion in a future spend) is unconditionally disabled for that output.

### Impact Explanation
Any user depositing less than 10,000 sats to a Serai Bitcoin address loses the funds permanently. Unlike the `DUST` constant's own justification (that below-dust outputs are uneconomical to spend at ~5 sat/vbyte), the issue is that the deposit is still *accepted and credited nowhere*: the depositor's external balance is never minted, and the UTXO sits at a spendable key-path script that the multisig will never sign for because the scheduler never sees it. If the sender's wallet does not warn them, small deposits are irrecoverably burned rather than merely expensive to move.

### Likelihood Explanation
Likelihood is moderate. 10,000 sats is a non-trivial threshold (~well above typical wallet dust limits of ~294-546 sats for Taproot). Standard wallets and CEXs will happily construct a P2TR output of a few thousand sats without any warning, and nothing in the deposit flow enforces or communicates the 10,000 sat floor. The attack/mistake requires only a single normal Bitcoin transaction from an unprivileged sender.

### Recommendation
Either reject/handle sub-dust deposits explicitly — e.g., emit them in the `ScannerEvent` with a flag so the coordinator can refund or aggregate them once fee conditions improve — or enforce the 10,000 sat minimum at the deposit-address level by documenting/communicating it to integrators and refunding below-threshold outputs in a dedicated plan. At minimum, the `N::DUST` drop in `processor/src/multisigs/scanner.rs` should not silently discard the output without any recovery path.

### Proof of Concept
1. Serai activates a Bitcoin multisig with group key `K`; `get_outputs` (`processor/src/networks/bitcoin.rs` lines 686-740) builds a `Scanner` registering the External/Change/Branch/Forwarded scripts.
2. An external user sends a transaction with a 5,000-sat output to `p2tr_script_buf(K)` (the External script, offset `Scalar::ZERO`, `networks/bitcoin/src/wallet/mod.rs` line 164). The transaction confirms.
3. The scanner iterates blocks and calls `network.get_outputs(&block, key)`; `scan_transaction` matches the output's `script_pubkey` and returns a `ReceivedOutput` with `value() == 5_000`.
4. Back in `processor/src/multisigs/scanner.rs`, `output.balance().amount.0 (5_000) >= N::DUST (10_000)` is false; the output is dropped and never added to `outputs`, never passed to `ScannerDb::save_outputs`, never emitted.
5. The depositor is never credited on Serai, and since `make_signable_transaction` only ever consumes reported `Output`s, the 5,000 sats can never be spent by the multisig — permanently locked, exactly analogous to deposit-accepted/redeem-disabled. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
