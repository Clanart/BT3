### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` parsing untrusted M-of-N custody memos can exhaust the Python call stack - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a custody puzzle tree (used by the CHIP-0043 custody architecture and consumed by `chia/pools/plotnft_drivers.py`) from an attacker-influenced `Program` (memo). When the memo encodes an `MofN` node, the method recurses into itself once per member with no depth limit, mirroring the CVE-2020-16094 pattern of unbounded recursive descent into a nested, attacker-supplied tree causing stack consumption.

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses a CLVM `Program` memo that describes a custody arrangement (single member vs. `MofN` composition): [1](#0-0) 

When `further_branching` is true (i.e., the memo declares an `MofN` node), the code builds `MofNHint.from_program(puzzle_hint_prog)` and then recurses:
```
puzzle = MofN(m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos])
```
There is no recursion-depth guard, no limit on `MofNHint.member_memos` length, and no limit on nesting depth of `MofN` members inside members. This is a standard Python recursive function (unlike `chia/types/blockchain_format/tree_hash.py`'s `sha256_treehash`, which is explicitly implemented iteratively "so we don't have to worry about blowing out the python stack" — a design contract this new code does not follow): [2](#0-1) 

A memo can be nested arbitrarily deep because a `PuzzleWithRestrictions.memo()` (the inverse serialization function) itself recurses per `MofN` member with no depth cap: [3](#0-2) 

so nothing in the wire format itself prevents deep nesting; it's purely a CLVM list structure that any counterparty producing a custody memo can construct to be as deep as desired. The `MofN.__post_init__` sanity checks (`m <= n`, `m >= 1`, no duplicate merkle nodes) do not bound recursion depth: [4](#0-3) 

Because `from_memo` is documented as the mechanism "to sync an unknown inner puzzle from on chain" (per test docstring), the memo is meant to be consumed from data observed on-chain / from a counterparty, not something the local wallet fully controls: [5](#0-4) 

The custody architecture is consumed in production by `chia/pools/plotnft_drivers.py` (plotnft/pool transitions, an in-scope surface per the rules), which imports and constructs `PuzzleWithRestrictions` from puzzle data. If pool/plotnft drivers or wallet sync code that recognizes this puzzle type call `from_memo` on a memo derived from a puzzle reveal supplied by a remote peer/pool/counterparty, sufficiently deep nesting will exhaust the Python recursion limit before any CLVM cost accounting is applied — the recursion happens in pure Python before/independently of any mempool cost checks.

### Impact Explanation
A crafted, deeply-nested custody memo can cause a `RecursionError` (or, depending on the interpreter/thread stack configuration, a native stack overflow/segfault) in any wallet or pool-client process that calls `PuzzleWithRestrictions.from_memo()` on untrusted data. Since this path is used to reconstruct custody state "from on chain" for wallets participating in composable/multisig-style custody or plotnft/pool flows, an attacker who can get a peer to parse such a memo (e.g., via a puzzle reveal encountered during sync, or a pool/plotnft-related custody puzzle) can crash or hang that process — a transaction/spend-processing-halt class issue, consistent with the accepted impact categories (spend-triggered processing halt).

### Likelihood Explanation
Likelihood is constrained by how directly reachable `from_memo` is from unauthenticated input in the current codebase: it is currently invoked in production only indirectly through the custody/plotnft driver code path (`chia/pools/plotnft_drivers.py`), and I could not fully confirm within the available index whether that code path feeds an unauthenticated remote-supplied memo directly into `from_memo` versus only locally-constructed data. This uncertainty should be resolved by reviewing `chia/pools/plotnft_drivers.py` directly, since the indexed search only confirmed the import/usage count, not the full call chain semantics, and the size of that file exceeds what was inspected here.

### Recommendation
Convert `PuzzleWithRestrictions.from_memo()` (and its recursive counterpart `memo()`) to an iterative implementation using an explicit work stack, following the pattern already used in `chia/types/blockchain_format/tree_hash.py`'s `sha256_treehash`. Alternatively/additionally, enforce an explicit maximum nesting depth (and maximum `MofN` member count) before recursing, and raise a well-defined error (not a raw `RecursionError`) when the limit is exceeded, so any caller processing untrusted memos fails safely rather than exhausting the stack.

### Proof of Concept
1. Construct a `PuzzleWithRestrictions` whose `puzzle` field is an `MofN` with `m=1` and a single member that is itself another `MofN` with the same shape, and repeat this nesting programmatically N times (e.g., N = 50,000+), each layer built via `MofN(m=1, members=[PuzzleWithRestrictions(nonce=i, restrictions=[], puzzle=<next layer>)])`.
2. Call `outer.memo()` to obtain the serialized CLVM memo `Program` (or hand-construct the equivalent nested CLVM structure directly, since an attacker does not need the local `memo()` API to produce this wire format — only a compatible nested list of `(m, member_memos)` MofN hints).
3. Call `PuzzleWithRestrictions.from_memo(memo)` on the resulting deeply-nested `Program`.
4. Observe a Python `RecursionError` (or process crash) inside the recursive branch at `chia/wallet/puzzles/custody/custody_architecture.py:284-286`, before any CLVM cost or `MofN.__post_init__` validation limits the structure size.

    @classmethod
    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
            puzzle=puzzle,
            additional_memos=additional_memos,
        )
