### Title
Fee-on-Transfer ERC20 Tokens Break Bridge Accounting in `BridgeTransferERC20` - (File: contracts/service_chain/bridge/BridgeTransferERC20.sol)

### Summary
`requestERC20Transfer` and `_requestERC20Transfer` in `BridgeTransferERC20.sol` assume the ERC20 `_value` and `_feeLimit` parameters supplied by the caller equal the actual token amount received by the bridge contract. If a registered token deducts a transfer fee (fee-on-transfer / deflationary ERC20), the bridge's real balance increase from `safeTransferFrom` will be less than `_value.add(_feeLimit)`, while the contract's fee/refund/burn logic and the `RequestValueTransfer`/`HandleValueTransfer` events (and subsequent mint on the counterpart chain) still operate on the nominal, unadjusted `_value`.

### Finding Description
`requestERC20Transfer` (lines 124-135) does:
```solidity
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

`_requestERC20Transfer` then pays the fee/refund and, in mint/burn mode, burns exactly `_value` from the bridge's own holdings:
```solidity
uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);
if (modeMintBurn) {
    ERC20Burnable(_tokenAddress).burn(_value);
}
``` [2](#0-1) 

None of this logic checks the bridge's actual balance delta before vs. after the `safeTransferFrom` call — it is implicitly assumed that the bridge received exactly `_value + _feeLimit`. On the counterpart chain, `handleERC20Transfer` mints/transfers the nominal `_value` to the recipient unconditionally:
```solidity
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
``` [3](#0-2) 

If the token deducts a transfer fee, the bridge's actual token inflow is smaller than `_value + _feeLimit`. This breaks the 1:1 backing assumption between locked/burned tokens on the source chain and minted/released tokens on the destination chain: the destination side still credits the full nominal `_value`, while the source side may have burned/held less than that (or the `burn(_value)` call may revert due to insufficient actual balance, which is a functional break rather than a silent inflation in lock/unlock mode, but a genuine backing mismatch in mint/burn mode when the shortfall happens to not trigger a revert, e.g., partial fills across multiple deposits netting out). This mirrors exactly the reported bug class — `PositionsManager` crediting the nominal transferred amount instead of the actually-received balance delta.

### Impact Explanation
In `modeMintBurn` operation, an under-collateralized burn relative to the nominal value that is subsequently minted 1:1 on the counterpart chain constitutes unbacked supply inflation of the bridged token — a direct value-movement / double-counting bug reachable by any unprivileged holder of a registered ERC20 calling the public `requestERC20Transfer` function. Even outside of an exploit that fully avoids the `burn()` revert, this at minimum causes systemic accounting divergence between the two bridged chains for any token that later becomes (or is deployed as) a fee-on-transfer token, which the codebase does nothing to detect or reject.

### Likelihood Explanation
Likelihood is Medium: the vulnerability is only actually reachable once a fee-on-transfer ERC20 is registered on the bridge (`registerToken`, an operator-controlled action), but once registered, the fee-based accounting mismatch is triggered by any ordinary unprivileged user simply calling the public `requestERC20Transfer` — no additional privilege, timing, or malicious-node behavior is required. This matches the original report's acknowledgment that the risk is real but considered low-probability because the specific tokens deployed are expected not to charge transfer fees — the code itself has no enforcement or detection of this assumption.

### Recommendation
In `requestERC20Transfer`/`onERC20Received`, measure the bridge's actual token balance before and after `safeTransferFrom` and use the observed delta (rather than the caller-supplied `_value + _feeLimit`) for all subsequent fee, refund, burn, and event-emission logic, consistent with the general fix recommended for `PositionsManager`.

### Proof of Concept
1. Operator registers a fee-on-transfer ERC20 token `T` (deducts e.g. 5% on every `transfer`/`transferFrom`) via `BridgeTokens.registerToken`, and the bridge runs in `modeMintBurn = true`.
2. User calls `requestERC20Transfer(T, to, value=100, feeLimit=0, extraData)`.
3. `safeTransferFrom(msg.sender, bridge, 100)` actually delivers only 95 tokens to the bridge due to the token's fee.
4. `_requestERC20Transfer` proceeds to call `ERC20Burnable(T).burn(100)` — either it reverts (DoS on legitimate transfers for fee tokens) or, if the bridge holds surplus `T` from other pending operations, it succeeds by burning tokens that were not contributed by this user, silently consuming other users'/the bridge's balance.
5. Regardless of outcome, the emitted `RequestValueTransfer` event records `_value = 100`, and once relayed, `handleERC20Transfer` on the counterpart chain mints exactly 100 tokens to `_to` — 5% more than the token amount actually removed from circulation on the source chain, producing unbacked cross-chain token supply.
