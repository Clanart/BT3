The upb JSON encoder is confirmed to lack HTML-unsafe character escaping that the Java/C#/C++ JSON writers deliberately added. Let me verify this gap is consistent and not compensated elsewhere in the Python/Ruby/PHP binding layers.## Analysis

The osctrl advisory describes a **stored XSS**: an attacker-controlled string (a query) is persisted and later re-emitted into an HTML page without HTML/JS-context-aware encoding, so `<`/`>`/`&`-style metacharacters break out of the intended context and execute as script in a victim's browser.

The structurally closest Protobuf analog is **ProtoJSON string serialization**, since that is the one place Protobuf emits attacker-controlled string field content that consuming applications commonly embed directly into HTML documents (e.g. `<script>var data = {{json}};</script>` state-hydration patterns). Protobuf's own Java, C#, and newer C++ JSON writers treat this as a real security boundary and explicitly escape `<`, `>`, `&`, `=`, `'` as defense-in-depth against exactly this XSS pattern:

- `src/google/protobuf/json/internal/writer.cc:239-240` (`MustEscape`) explicitly escapes `<`/`>` "to prevent security bugs in JavaScript."
- `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java:1583-1591` escapes `<>&='` "to prevent XSS risks", with a dedicated regression test `testHtmlEscape` in `java/util/src/test/java/com/google/protobuf/util/JsonFormatTest.java:2016-2035`.
- `csharp/src/Google.Protobuf/JsonFormatter.cs:61-83` bakes the same `<`/`>` escaping into `CommonRepresentations`.

However, the **upb-based JSON encoder** — shared verbatim by the Python, Ruby, and PHP native bindings — only implements the bare JSON-spec-required escapes and does **not** escape `<`/`>`/`&`:

- `upb/json/encode.c:268-301` (`jsonenc_put_escaped_char`)
- identical code copied into `php/ext/google/protobuf/php-upb.c:6807-6839`
- identical code copied into `ruby/ext/google/protobuf_c/ruby-upb.c:5560-5593`

This is directly confirmed by Python's own test suite: `python/google/protobuf/internal/json_format_test.py:296-304` sets `string_value = '&\n<"\r>\b\t\f\\\001/'` and asserts the output is `"&\\n<\\"\\r>\\b\\t\\f\\\\\\u0001/\\u2028\\u2029"` — note `<` and `>` pass through **literally unescaped**, whereas the equivalent Java test (`testHtmlEscape`) asserts they become `\u003c`/`\u003e`. Python's pure-Python path (`python/google/protobuf/json_format.py:224-228`, `ToJsonString` → `json.dumps`) inherits the same gap since `json.dumps` doesn't HTML-escape by default either.

### Title
Missing HTML/JS-context escaping (`<`, `>`, `&`) in ProtoJSON string encoding for Python/Ruby/PHP (upb) — inconsistent with Java/C#/C++ - (File: `upb/json/encode.c`)

### Summary
The upb JSON encoder, shared by Python's C-accelerated extension, Ruby, and PHP bindings, serializes proto string field values to JSON using only the bare JSON-spec escapes (quote, backslash, control chars). Unlike Java's `JsonFormat`, C#'s `JsonFormatter`, and C++'s newer `json/internal` writer — which deliberately additionally escape `<`, `>`, `&`, `=`, `'` specifically to prevent XSS when JSON is embedded in an HTML/`<script>` context — the upb encoder emits these characters raw.

### Finding Description
`jsonenc_put_escaped_char` in `upb/json/encode.c:268-301` (duplicated in `php-upb.c` and `ruby-upb.c`) only special-cases `\n \r \t \" \f \b \\` and ASCII control bytes `< 0x20`. `<`, `>`, and `&` fall through to the `default` branch and are written verbatim via `jsonenc_putbytes`. The sibling Java/C#/C++ implementations treat `<`/`>`/`&` as security-relevant characters (comments explicitly say "to prevent security bugs in JavaScript" / "to prevent XSS risks") and convert them to `\uXXXX` escapes. This is a genuine cross-implementation inconsistency in behavior for the *same* ProtoJSON specification, not an intentional interpretation difference — the Java/C# implementations exist precisely because this exact bug class was previously identified as a risk (see the `b/73832901` regression test reference in `JsonFormatTest.java`).

### Impact Explanation
An attacker who controls a proto string field value (via a bounded binary Protobuf parse or a JSON parse-then-reserialize round trip through a public API) can inject `</script><script>...</script>` or similar payloads. If a Python/Ruby/PHP consuming application follows the common state-hydration pattern of embedding `json_format.MessageToJson(msg)` (or the upb-backed equivalents) directly inside an HTML `<script>` block — exactly the "stored value later rendered unescaped on a page viewed by other users" pattern described in the osctrl advisory — the unescaped `<`/`>` allow the attacker's payload to break out of the script context and execute in the browser of any user who views that page. This mirrors the osctrl CWE-79 impact: stored XSS reachable by any user permitted to set the string field, potentially escalating to session/CSRF-token theft of higher-privileged viewers.

### Likelihood Explanation
Likelihood is Medium: it requires (1) an attacker able to set a proto string field that reaches serialization via the Python/Ruby/PHP ProtoJSON path, and (2) a consuming application that embeds that JSON output into an HTML/script context without its own escaping — a documented but common anti-pattern for client-side state hydration. It does not require any privileged access, malicious peer, or resource exhaustion; it only requires an ordinary bounded string input through a supported public serialization API.

### Recommendation
Align the upb JSON encoder (used transitively by Python's C extension, Ruby, and PHP) with the Java/C#/C++ behavior by escaping `<`, `>`, `&` (and ideally `=`, `'` for parity) as `\uXXXX` sequences in `jsonenc_put_escaped_char` (`upb/json/encode.c`, and its duplicated copies in `php-upb.c` / `ruby-upb.c`), and audit the pure-Python `json_format.py` path (`ToJsonString`) to apply the same post-processing before returning JSON strings, so all officially supported language bindings provide consistent XSS-hardening for ProtoJSON output.

### Proof of Concept
Using the pure-Python binding (or the C-extension, same behavior per `upb/json/encode.c`):
```python
from google.protobuf import json_format
msg = json_format_proto3_pb2.TestMessage()
msg.string_value = '</script><script>alert(document.cookie)</script>'
print(json_format.MessageToJson(msg))
# {
#   "stringValue": "</script><script>alert(document.cookie)</script>"
# }
```
Compare with the Java implementation on an equivalent message (`JsonFormatTest.testHtmlEscape`, `java/util/src/test/java/com/google/protobuf/util/JsonFormatTest.java:2016-2021`), which converts `</script>` to `\u003c/script\u003e`. If the consuming web application embeds the Python-produced JSON string inside `<script>var msg = {json};</script>`, the payload breaks out of the script tag and executes.
