### Title
Unverified proof-of-possession allows blame-triggered leak of honest participants' secret shares — ([File: crypto/dkg/pedpop/src/lib.rs](https://github.com/serai-dex/serai/blob/main/crypto/dkg/pedpop/src/lib.rs))

### Summary
Analog of CVE-2024-0804 (insufficient policy enforcement leaking cross-origin data): `KeyMachine::calculate_share` emits an `EncryptionKeyProof` — which reveals the ECDH shared key for a message — on the scalar-deserialization error path *before* the message's Schnorr proof-of-possession (PoP) has been verified. The PoP exists specifically to prevent exactly this leak (per the in-code comment), but it is only queued into a `BatchVerifier` that is never checked before the early `?` return. A malicious DKG participant can therefore cause an honest victim to produce and publish a blame proof that decrypts a *different* honest party's share message, leaking secret DKG shares.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Encryption::decrypt` (lines 469-501) does three things in order:

1. Queues `msg.pop.batch_verify(...)` into the caller-supplied `BatchVerifier` under `BatchId::Decryption(from)` — this is only *queued*, not verified.
2. Computes `key = ecdh(&self.enc_key, msg.key)`, applies the ChaCha20 keystream to the ciphertext.
3. Unconditionally constructs and returns `EncryptionKeyProof { key, dleq }`, a DLEq proof binding `key` to `self.enc_key * msg.key`, which lets any third party decrypt the message.

The header comment at `encryption.rs:83-90` explains the PoP exists because, without it, Eve can replay Alice's encryption key `X`; when Bob reveals `bX` as a blame proof, Alice's message to Bob is exposed.

In `KeyMachine::calculate_share` (`pedpop/src/lib.rs:476-499`):

```rust
let (mut share_bytes, blame) =
  self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
```

If the decrypted bytes are not a canonical scalar, the function returns `InvalidShare { blame: Some(...) }` immediately — before `batch.verify_with_vartime_blame()` at line 493 ever checks the queued PoP. The correct path (line 494-498) maps a `Decryption` batch failure to `blame: None` precisely because the ECDH key must not be revealed when the PoP is bad; the early `?` bypasses that safeguard.

### Impact Explanation
Eve participates in a PedPoP DKG and observes Alice's `EncryptedMessage` to Bob over the authenticated channel, reusing Alice's ephemeral key `X` (Eve does not know `x`). Eve sends Bob a crafted `EncryptedMessage` with `key = X`, an invalid PoP, and a ciphertext that will decrypt to non-canonical bytes under `bX` (Eve cannot compute `bX`, but can simply send garbage — the keystream output under a random `proof.key`-equivalent is overwhelmingly non-canonical; more practically, Eve *can* pick her own `e`, compute `eB`, encrypt an invalid scalar, then swap the header `key` field to `X` — the cipher is keyed by `b*msg.key = bX`, so the payload just needs to fail `from_repr`, and since Eve doesn't know `bX` the simplest route is a random payload which fails with probability ~1 - 2^-… actually suffices since only non-canonicity is required and Eve can retry or just send any bytes — the PoP check is the only barrier and it's skipped).

Bob's `calculate_share` hits the `from_repr` failure and returns `InvalidShare { participant: Eve, blame: Some(EncryptionKeyProof { key: bX, dleq }) }`. The blame proof's entire purpose is third-party adjudication via `Decryption::decrypt_with_proof` / `AdditionalBlameMachine`, so it is published or submitted to an arbiter. That arbiter (or anyone observing it) now holds `bX`, which is the *same* ECDH key protecting Alice's genuine share message to Bob — `cipher` derives the ChaCha20 key purely from `context || ecdh`, with no sender binding (`encryption.rs:101-133`). Anyone can now decrypt Alice's secret share `f_A(bob)`.

Repeating against `t` distinct recipients (or via multiple blame rounds) recovers `t` evaluations of Alice's degree-`t-1` polynomial, fully reconstructing Alice's constant coefficient — i.e., Alice's secret contribution to the threshold key. This is key-share recovery by an unprivileged protocol participant, violating the DKG's confidentiality guarantee.

### Likelihood Explanation
- Reachable with public inputs only: Eve needs a valid DKG slot ( Participant index) and an authenticated channel to Bob — the standard threat model. She crafts `EncryptedMessage` bytes fed to `calculate_share`, an in-scope untrusted-input path.
- Deterministic trigger: the early `?` fires whenever the decrypted payload fails `from_repr`; Eve's garbage ciphertext fails with overwhelming probability.
- Requires the deployment to actually surface/publish the returned `blame` — which is the documented purpose of `EncryptionKeyProof` and `BlameMachine`/`AdditionalBlameMachine` (third-party fault adjudication). Under that intended usage the leak is automatic.
- Mitigating factor: the leak is per-recipient and requires the blame to be published; a caller that discards the error avoids it. Still, the library explicitly returns the proof expecting it to be used, so the vulnerable path is the designed workflow.

### Recommendation
In `KeyMachine::calculate_share`, never emit an `EncryptionKeyProof` for a message whose PoP has not yet been verified. Concretely:

- Restructure so the batched PoP verification is checked (or the per-message `msg.pop.verify(...)` is performed inline) before any code path can return `blame: Some(blame)`, or
- Split decryption into two phases: first verify all PoPs via the batch verifier, and only then decrypt and construct `EncryptionKeyProof`s; on the `from_repr` failure, return `blame: None` unless the PoP is known-good, or
- At minimum, on the `from_repr` error path, return `blame: None` (matching the `BatchId::Decryption` failure handling at line 495) since a message with an unverified PoP cannot have its key safely revealed.

### Proof of Concept
```rust
// Participants: Alice=1, Bob=2, Eve=3, t=2, n=3, context C.
// Round 1 proceeds honestly; all parties exchange EncryptionKeyMessage<Commitments>.

// Round 2: Alice sends Bob EncryptedMessage { key: X, pop: sig_A, msg: ct_A }
//          where ct_A = share f_A(2) XOR keystream(KDF(b*X)).

// Eve observes Alice's message and constructs for Bob:
let mut forged = EncryptedMessage::<C, SecretShare<C::F>> {
    key: alice_msg.key,                  // reuse X; Eve does NOT know x
    pop: SchnorrSignature { R: <any point>, s: <any scalar> }, // invalid PoP
    msg: SecretShare(random_bytes),       // decrypts under b*X to garbage
};

// Bob calls:
//   key_machine.calculate_share(rng, {Alice: msg_A_ok, Eve: forged, ...})
// Inside Encryption::decrypt for Eve's message:
//   - pop.batch_verify(...) is only QUEUED (encryption.rs:479-485)
//   - key = ecdh(b, X) = bX computed (line 487)
//   - blame = EncryptionKeyProof { key: bX, dleq } returned (lines 490-499)
// Back in calculate_share (lib.rs:480-482):
//   C::F::from_repr(garbage) -> None
//   => return Err(InvalidShare { participant: Eve, blame: Some(proof_for_bX) })
//   — batch.verify_with_vartime_blame() at line 493 is NEVER reached,
//     so the invalid PoP is never detected before the ECDH key is released.

// Bob (or an arbiter via AdditionalBlameMachine) publishes the blame proof.
// Any observer computes keystream = cipher(context, proof.key = bX)
// and decrypts Alice's original ct_A, recovering Alice's share f_A(bob).
// Repeat for t recipients to interpolate Alice's polynomial and recover
// her secret key contribution.
```

The root cause is an ordering violation: a cryptographic policy check (the PoP, added specifically to prevent key-reuse blame leaks per the comment at `encryption.rs:83-90`) is enforced by a batch verifier whose result is consulted only on a path the deserialization error return bypasses.
