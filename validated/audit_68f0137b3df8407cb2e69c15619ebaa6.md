### Title
Unchecked wrapping arithmetic on payment amounts defeats the solvency check in `SignableTransaction::new`, producing a threshold-signed consensus-invalid transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Alchemix `convert(int -> uint)` underflow that defeated the `min()` cap in `Vault._calculate_max_mintable_amount`, `SignableTransaction::new` performs unchecked `u64` addition and wrapping `sum::<u64>()` over caller-supplied payment amounts. When the sum of payments overflows `u64`, the `NotEnoughFunds` solvency cap is bypassed and the resulting `SignableTransaction` carries outputs whose total value exceeds its inputs. `TransactionSignMachine::sign` then drives FROST to produce valid Schnorr signatures over a transaction Bitcoin consensus will reject.

### Finding Description
In `SignableTransaction::new`, the aggregate of payments is computed with a wrapping iterator sum, and the solvency check uses a plain `+`:

```rust
// send.rs:175
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
// send.rs:187
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
// send.rs:206,215
let mut needed_fee = fee_per_vbyte * vbytes;
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { ... })?;
}
```

`payments: &[(ScriptBuf, u64)]` is untrusted input — each `u64` is only checked against `DUST` (send.rs:165-169), never against `MAX_MONEY` or against a checked cumulative total. Two payments of `u64::MAX` make `payment_sat` wrap to a small value, so `input_sat < payment_sat + needed_fee` is false and the solvency check passes. The change path (send.rs:228) uses `checked_sub` on the already-wrapped `payment_sat + fee_with_change`, so a near-`input_sat` change output is pushed while every payment `TxOut` retains its full declared `u64` value (send.rs:190). The result is a `Transaction` where `sum(outputs) >> sum(inputs)` — invalid under Bitcoin consensus (and also above `MAX_MONEY` per-output).

`fee()` (send.rs:138-141) then computes `sum(inputs) - sum(outputs)` with an unchecked `-`, which underflows/panics whenever this occurs — the exact structural analog of the report's `convert(int256 -> uint256)` on a value that can be `<= 0`.

`TransactionSignMachine::sign` (send.rs:355-398) commits all prevouts (`Prevouts::All`) and produces a valid BIP-340 signature share per input for this malformed transaction; `complete` (send.rs:413-428) assembles witness signatures for a TX the network can never accept.

### Impact Explanation
A party able to specify payments (e.g., a withdrawal request routed into a Plan, or any caller of `SignableTransaction::new`) can cause the threshold group to produce a fully-signed transaction that is permanently unbroadcastable — it can never be mined, so the payment is never executed while the signing session, preprocesses, and scheduler accounting for the plan are consumed. Any subsequent call to `fee()` underflows (`u64` wrap in release, panic in debug), corrupting fee accounting or crashing the caller. This mirrors the report's shape: a solvency/cap check is silently neutralized by arithmetic wraparound, and downstream logic proceeds on an absurd value.

### Likelihood Explanation
Requires an integrator/scheduler path to place two or more payment amounts whose `u64` sum overflows (or `payment_sat + needed_fee`/`fee_per_vbyte * vbytes` overflowing). Payment amounts come from off-chain requests, not chain-validated data, so no chain state preconditions are needed — only sufficiently large requested amounts. In release builds all these operations wrap silently; in debug builds they panic.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`: accumulate `payment_sat` with `checked_add`/`try_fold`, compute `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`, reject any payment exceeding `Amount::MAX_MONEY`, and make `fee()` use `checked_sub` (returning `Option`/`Result`). The invariant `sum(outputs) <= sum(inputs)` should be enforced exactly once on non-wrapped totals.

### Proof of Concept
```rust
// Two payments whose sum wraps u64
let payments = vec![
  (payment_script_a, u64::MAX),       // >= DUST, passes per-payment check
  (payment_script_b, u64::MAX - 100), // >= DUST
];
// payment_sat wraps to ~u64::MAX - 101 + u64::MAX -> small value
// input_sat < payment_sat + needed_fee evaluates against the wrapped sum -> passes
let signable = SignableTransaction::new(
  vec![one_small_input],              // e.g. 100_000 sats
  &payments,
  Some(change_script),
  None,
  fee_per_vbyte,
).unwrap();
// signable.tx.output sum exceeds sum(inputs) -> consensus-invalid,
// yet TransactionSignMachine::sign produces valid signatures for it.
// signable.fee() underflows (panics in debug, wraps in release).
```
