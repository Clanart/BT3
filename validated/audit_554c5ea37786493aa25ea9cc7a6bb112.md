## Confirmed root cause

`NewAccountKey(t)` returns a fresh `*AccountKeyRoleBased` whenever `keyType == AccountKeyTypeRoleBased`, with no depth/nesting tracking: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` decodes the `keyType` tag, constructs the corresponding `AccountKey` via `NewAccountKey`, and then decodes into it — recursively, if the constructed key is itself an `*AccountKeyRoleBased`: [2](#0-1) 

`AccountKeyRoleBased.DecodeRLP` reads a list of RLP-encoded byte blobs and, for **each element**, calls `rlp.DecodeBytes(b, &serializer)` — invoking `AccountKeySerializer.DecodeRLP` again — with **no depth limit or composite-type check at decode time**: [3](#0-2) 

The only defense against nested `RoleBased` keys — `ErrNestedCompositeType` — is enforced in `CheckInstallable`/`CheckUpdatable`, which run **after** decoding is already complete: [4](#0-3) [5](#0-4) 
This is confirmed by the existing regression test, which shows the nested-composite rejection happening at `txpool.AddRemote` / block validation time (`kerrors.ErrNestedCompositeType`), i.e. only after the RLP structure has already been fully decoded/allocated: [6](#0-5) 

### Reachability
`AccountKeySerializer`/`AccountKeyRoleBased.DecodeRLP` is invoked while decoding a `TxTypeAccountUpdate` transaction's `TxValueKeyAccountKey` field. Any unauthenticated sender can submit such a transaction (or an equivalent RLP payload) directly to a public node's `AddRemote`/RPC entrypoint. The decode step happens **before** any signature or gas validation short-circuits attacker-controlled recursion, so a crafted, deeply nested `AccountKeyRoleBased → AccountKeySerializer → AccountKeyRoleBased → …` byte-string chain drives unbounded recursive `DecodeRLP` calls purely from the encoded byte length, with only a few bytes of RLP overhead required per nesting level. This mirrors the Ion-C bug class precisely: an external, untrusted structured-data decoder recurses in lock-step with attacker-controlled input nesting depth, with no explicit recursion-depth guard, risking native/Go stack exhaustion and process crash — a denial of service reachable by a single unprivileged transaction sender.

### Limitation of my analysis
I could not fully verify the exact maximum transaction payload size enforced by `blockchain/tx_pool.go` (`txMaxSize` and related size-limit constants), which determines how many nesting levels are actually achievable within one transaction and thus how severe the stack growth would be in practice. This is a quantitative detail that a background agent with full repo/test access should confirm via `blockchain/tx_pool.go` before finalizing severity, since Go's default goroutine max stack size (1 GiB) is large and the actual exploitability depends on frame size × achievable nesting depth given the configured max tx size.

### Title
Uncontrolled recursion in `AccountKeyRoleBased`/`AccountKeySerializer` RLP decoding allows stack-exhaustion DoS via nested account keys - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes nested `AccountKeySerializer` entries with no depth limit. Because the only guard against nested `RoleBased` keys (`ErrNestedCompositeType`) is checked post-decode in `CheckInstallable`/`CheckUpdatable`, an attacker can submit a `TxTypeAccountUpdate` transaction (or raw RLP passed to `KaiaAPI.DecodeAccountKey`) whose `AccountKey` field contains many levels of nested `AccountKeyRoleBased` values, driving unbounded recursive Go function calls purely from the byte layout of the payload.

### Finding Description
`NewAccountKey` returns an `*AccountKeyRoleBased` for `AccountKeyTypeRoleBased` without tracking nesting depth [1](#0-0) . `AccountKeySerializer.DecodeRLP` reads the key type then recursively decodes into the corresponding concrete key type [2](#0-1) . `AccountKeyRoleBased.DecodeRLP` iterates a list of byte-string elements and calls `rlp.DecodeBytes` on each, re-entering `AccountKeySerializer.DecodeRLP` [3](#0-2) . If the inner serializer's key type is again `RoleBased`, this chain repeats with no bound. The composite-type rejection exists only in `CheckInstallable`/`CheckUpdatable`, executed after decode completes [4](#0-3) .

### Impact Explanation
A crafted RLP payload with deeply nested `AccountKeyRoleBased` entries forces the decoder to recurse to a depth proportional to the attacker-chosen nesting count, achievable with only a few bytes of RLP overhead per level. This can exhaust the goroutine stack and crash the node process (fatal, unrecoverable in Go) processing the transaction — whether via `TxPool.AddRemote`, block/transaction validation, or the `kaia_decodeAccountKey` RPC method [7](#0-6) . This is a remote, unauthenticated denial-of-service vector against any public node accepting transactions or RPC calls.

### Likelihood Explanation
High: no signature, gas, or size check occurs before the recursive decode is invoked; constructing the nested payload requires no special privileges — just standard RLP encoding knowledge. The transaction sender only needs to submit `TxTypeAccountUpdate` (or call `kaia_decodeAccountKey`) with the crafted key bytes.

### Recommendation
Add an explicit recursion-depth counter/limit to `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., reject decoding if depth exceeds 1, consistent with the "RoleBased cannot contain RoleBased" invariant already enforced post-decode), so the composite-type restriction is enforced **during** decoding rather than only afterward.

### Proof of Concept
Conceptually: encode an `AccountKeySerializer` whose `keyType = AccountKeyTypeRoleBased` and whose key payload is `[[serializer_bytes]]`, where `serializer_bytes` is itself an `AccountKeySerializer` with `keyType = AccountKeyTypeRoleBased` wrapping another single-element list, repeated N times (N large, e.g. tens of thousands, bounded only by the node's max accepted transaction/RPC payload size). Submitting this via a `TxTypeAccountUpdate` transaction's `AccountKey` field (or directly via `kaia_decodeAccountKey`) triggers N recursive calls through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` before any nested-composite check runs, potentially exhausting the stack and crashing the node. I was unable to empirically execute this against the live codebase in this session, so actual crash depth/feasibility relative to the enforced max transaction size should be validated by a background agent with execution access.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (a *AccountKeyRoleBased) CheckUpdatable(newKey AccountKey, currentBlockNumber uint64) error {
	if newKey, ok := newKey.(*AccountKeyRoleBased); ok {
		lenOldKey := len(*a)
		lenNewKey := len(*newKey)
		// If no key is to be replaced, it is regarded as a fail.
		if lenNewKey == 0 {
			return kerrors.ErrZeroLength
		}
		// Do not allow undefined roles.
		if lenNewKey > (int)(RoleLast) {
			return kerrors.ErrLengthTooLong
		}
		for i := range lenNewKey {
			switch {
			// A composite key is not allowed.
			case (*newKey)[i].IsCompositeType():
				return kerrors.ErrNestedCompositeType
			// If newKey is longer than oldKey, init the new attributes.
			case i >= lenOldKey:
				if err := (*newKey)[i].CheckInstallable(currentBlockNumber); err != nil {
					return err
				}
			// Do nothing for AccountKeyTypeNil
			case (*newKey)[i].Type() == AccountKeyTypeNil:

			// Check whether the newKey is replacable or not
			default:
				if err := CheckReplacable((*a)[i], (*newKey)[i], currentBlockNumber); err != nil {
					return err
				}
			}
		}
		return nil
	}
	// Update is not possible if the type is different.
	return kerrors.ErrDifferentAccountKeyType
}
