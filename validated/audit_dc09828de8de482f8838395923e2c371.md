## Title
Silent, unconfirmed rewrite of a repository's push/fetch remote URL driven by attacker-controlled GitHub API data - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically re-fetches a repository's metadata from the GitHub/GHES API and, based solely on the returned `clone_url` field, automatically calls `git remote set-url` on the user's local repository — with no user prompt, confirmation dialog, or diff shown. This mirrors the report's underlying broken invariant ("a security-relevant configuration/value is written from an external source without any way to safely gate, review, or reject updates to it") but manifests in Desktop as an unconfirmed, fully automatic mutation of the value that determines where the user's future `git push`/`git fetch` traffic goes.

### Finding Description
`updateRemoteUrl` compares the currently configured git remote against the `clone_url` reported by the API and, if a set of heuristic conditions hold, silently rewrites the remote: [1](#0-0) 

The guard conditions are:
- `protocolsMatch` — only compares URL *scheme*, not host.
- `remoteUrlUnchanged` — true if the *previously stored* `gitHubRepository.cloneURL` still matches the current git remote, i.e. "the user hasn't manually diverged from what we last got from the API."
- `!urlsMatch` — the new API URL differs from the current remote.

Both `remoteUrl` (current git remote) and `gitHubRepository.cloneURL` (the value being compared against) were themselves populated by a previous call to the very same API endpoint, via `_upsertGitHubRepository`: [2](#0-1) 

This function is invoked from `repositoryWithRefreshedGitHubRepository`, which fetches the repo from the API using an account matched purely by comparing the remote's hostname against the account's endpoint hostname (`matchGitHubRepository`), and then unconditionally trusts and applies the response: [3](#0-2) [4](#0-3) 

Because the "old" value used for the `remoteUrlUnchanged` check and the "new" value being applied both originate from the same API/server, an attacker who controls that API endpoint (e.g. a malicious/compromised GitHub Enterprise Server instance the user has added as an account, or a network-position attacker able to answer that endpoint's HTTPS requests with a certificate the user's OS trusts) fully controls both sides of the comparison. On the first refresh they can return a `clone_url` that matches the user's existing remote (establishing `remoteUrlUnchanged = true` for all subsequent refreshes as long as the remote isn't touched), and on a later refresh simply return a different `clone_url` on the same protocol pointing to attacker infrastructure. `updateRemoteUrl` will then call: [5](#0-4) 

which executes `git remote set-url <name> <attacker-url>` against the user's real repository, with **no dialog, no diff of old vs new URL, and no explicit user action** — unlike the analogous "Untrusted Certificate" flow which *does* require the user to click through a warning: [6](#0-5) 

No equivalent confirmation exists for a remote-URL change driven by API data alone. The UI-driven manual remote-URL edit path only warns via a generic error toast on failure, not a trust decision on success: [7](#0-6) 

### Impact Explanation
Once the remote is silently rewritten, the corrupted value is the git remote URL used for all subsequent `push`/`fetch`/`pull` operations. The next time the user pushes from Desktop, their commits (potentially including proprietary source, secrets embedded in code, etc.) are sent to the attacker-controlled remote instead of the legitimate one. The next fetch/pull can also merge attacker-supplied history into the user's local repository. This is exactly the class of impact called out as valid: "silent corruption of what the user commits or pushes," driven entirely by an attacker-controlled GitHub API object (`IAPIRepository.clone_url`), with no local access, no admin rights, and no social engineering step beyond having previously added an account for the (now attacker-influenced) API endpoint.

### Likelihood Explanation
This affects any Desktop user connected to a GitHub Enterprise Server account (self-hosted, more likely to be attacker-influenced/compromised/MITM'd than github.com) whose repository is periodically refreshed (e.g. `repositoryWithRefreshedGitHubRepository`, triggered on account refresh / selection). The heuristic guard was designed to protect *user-intentional* manual remote edits, not to authenticate the API response itself, so it provides no protection against a malicious/compromised API endpoint returning attacker-controlled `clone_url` values. Exploitation requires no unusual user interaction beyond normal use of an already-added GHES account.

### Recommendation
- Require explicit user confirmation (a dialog showing the old and new remote URLs, similar to the untrusted-certificate flow) before automatically rewriting a remote URL sourced from API data.
- Validate that the new `clone_url`'s hostname matches the account's configured endpoint hostname before ever applying it via `setRemoteURL`.
- Do not use "did the remote still match a previous API response" as a security gate, since both values are attacker-controllable when the API endpoint itself is untrusted/compromised.

### Proof of Concept
1. User adds a GitHub Enterprise Server account in Desktop pointing at `ghes.corp.example` and clones a repository whose remote is `https://ghes.corp.example/team/project.git`.
2. The GHES instance (compromised, or an attacker positioned to answer its API responses) returns, via `GET /repos/team/project`, `clone_url: "https://ghes.corp.example/team/project.git"` — matching the existing remote, so `remoteUrlUnchanged` becomes `true` on the next refresh cycle. [8](#0-7) 
3. On a subsequent refresh (e.g. `refreshSelectedRepositoryAfterAccountChange` → `repositoryWithRefreshedGitHubRepository`), the same API endpoint instead returns `clone_url: "https://ghes.corp.example/attacker/project.git"` (same host/protocol, different repo/path an attacker controls, or DNS-consistent attacker infra). [9](#0-8) 
4. `updateRemoteUrl` sees `protocolsMatch = true`, `remoteUrlUnchanged = true`, `urlsMatch = false`, and calls `gitStore.setRemoteURL(...)`, silently running `git remote set-url origin https://ghes.corp.example/attacker/project.git` with no dialog shown to the user. [10](#0-9) 
5. The user, unaware of the change, clicks "Push" in Desktop; their commits are sent to the attacker's repository.

Note: I could not fully trace every automatic trigger path (all 7 call sites of `repositoryWithRefreshedGitHubRepository` in `app-store.ts`) within the available indexed content, so the exact frequency/UI triggers of this refresh in the running app could not be fully confirmed from the index alone — a Devin session with full repo access would be needed to enumerate all call sites and confirm background-refresh timing.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
