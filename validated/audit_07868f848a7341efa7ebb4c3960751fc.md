## Title
Unprivileged prompt-injection can exhaust the hourly commit-review rate-limit budget, causing subsequent malicious commits/pushes to bypass automated security review - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
The `security-guidance` plugin's `PostToolUse` hooks (`handle_commit_review_posttooluse` and `handle_push_sweep_posttooluse`) run an LLM-based security review on every `git commit`/`git push` a session performs, but gate the actual review behind a shared rolling-hour counter, `atomic_check_rate_limit(session_id, "CommitReview"/"PushSweep", MAX_COMMIT_REVIEWS_PER_HOUR, COMMIT_REVIEW_RATE_WINDOW_S)` [1](#0-0) . The cap defaults to 20 reviews/hour and is shared across both commit-review and push-sweep paths [2](#0-1) . Once the budget is exhausted, the hook exits silently with `skip_reason=23` and performs no review of the diff at all [3](#0-2) [4](#0-3) .

### Finding Description
This is a structural analog of the SEDA "cheap fake requests clog the processing queue" bug class: an unprivileged/low-cost actor can flood a bounded processing budget with worthless entries so that a legitimate/malicious item slips through unprocessed once the cap is hit. Here, the "queue" is the per-session rolling-hour review budget, and the "cheap request" is any trivial `git commit`/`git push` invocation — something an attacker's untrusted content (e.g., a malicious `CLAUDE.md`, README, or repo instructions ingested via prompt injection) can induce the agent to perform repeatedly at near-zero cost. Each trivial commit consumes one slot of `MAX_COMMIT_REVIEWS_PER_HOUR` [5](#0-4) , and the counter/`with_locked_state` mechanism has no concept of caller trust, commit size, or "cheapness" — it treats one no-op commit exactly like one with a genuinely risky diff. Once the hourly cap is reached, all further commits/pushes in that window skip review entirely and silently (`skip_reason=23`, `sys.exit(0)`), with no fallback safety net noted in this window besides the `Stop` hook backstop that exists for oversized ranges, not for rate-limited ones [4](#0-3) .

Because the review is the only automated gate that inspects diffs for injected vulnerabilities before they are committed/pushed, exhausting the budget with junk commits is functionally a hook-bypass: it defeats the intended "PreToolUse/PostToolUse review" trust boundary described in the plugin's own security posture (`security-guidance`), letting a subsequent attacker-crafted diff pass uninspected.

### Impact Explanation
If an attacker can get the agent to issue many trivial commits/pushes (via prompt injection embedded in repository content the agent reads, e.g. instructions in a README, issue, or CLAUDE.md), they can burn through the shared 20/hour budget before their actual malicious payload commit lands, causing that payload to be pushed/committed without any automated security review. This is a direct compromise of the security-review trust boundary for the local project/session — the same class of impact called out as acceptable ("hook bypass") in the validation rules, since it results in unreviewed code reaching the repository silently.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control content the agent ingests and get the agent to perform repeated low-value git operations (a realistic prompt-injection scenario, e.g. "helpfully" auto-committing many small fixups), and requires it to happen within the same hour window as the actual malicious commit. The rate limit is per-session and rolling-hour, which bounds the blast radius, but the bypass condition (`skip_reason=23`) is silently logged only via `debug_log`/telemetry, not surfaced to the user, so there is no user-facing warning that review has stopped happening.

### Recommendation
- Do not silently skip review on rate-limit exhaustion; instead, surface a clear warning/notification to the user (and/or block further auto-commits) when the budget is exhausted, rather than exiting quietly.
- Consider prioritizing/queuing skipped reviews for later processing (catch-up review) instead of dropping them outright, analogous to fixing the SEDA queue by adding cost/whitelisting — here, add a minimum "cost" per review slot proportional to actual diff risk, or reserve slots so a burst of low-value commits cannot fully exhaust the hourly window.
- Track and cap trivial/no-op commits separately from substantive ones so spam commits cannot consume the same limited budget as genuinely risky diffs.

### Proof of Concept
Not independently executed against a live session (index-only analysis); the mechanism is demonstrated in code: repeatedly triggering `git commit`/`git push` within one hour up to `MAX_COMMIT_REVIEWS_PER_HOUR` (default 20) causes `atomic_check_rate_limit` to return `allowed=False` for the 21st+ operation, which then hits `skip_reason=23` and exits without calling `analyze_code_security` [6](#0-5) , i.e., the diff of that commit is never scanned.
