### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` causes stack-exhaustion DoS before composite-type validation - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
The reported Alpine advisory describes a stack-exhaustion crash in dovecot caused by processing attacker-supplied, recursively-structured compressed data before any bound on recursion depth is enforced. Kaia has an analogous bug class in its `AccountKey` RLP decoding path: `AccountKeyRoleBased.DecodeRLP` decodes a list of opaque byte strings and, for each one, recursively invokes `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → (potentially) `AccountKeyRoleBased.DecodeRLP` again. Because this happens purely through native Go function-call recursion driven by attacker-controlled, nested byte content, an attacker can submit a single `TxTypeAccountUpdate` transaction whose `Key` field encodes deeply nested `AccountKeyRoleBased` values. The composite-type rejection (`IsCompositeType`/`CheckInstallable`/`ErrNestedCompositeType`) is only checked *after* decoding succeeds, so the stack growth happens unconditionally during decode, before any validation can reject the nesting.

### Finding Description
`TxInternalDataAccountUpdate.fromSerializable` decodes the transaction's `Key` bytes via: [1](#0-0) 

This calls `AccountKeySerializer.DecodeRLP`, which reads a `keyType` and then decodes the concrete key type via `s.Decode(serializer.key)`: [2](#0-1) 

When `keyType == AccountKeyTypeRoleBased`, this dispatches to `AccountKeyRoleBased.DecodeRLP`, which decodes a `[][]byte` and, for *each* element, calls `rlp.DecodeBytes` to decode another `AccountKeySerializer` — recursing back into the same code path: [3](#0-2) 

Nothing in this decode path enforces a maximum nesting depth. The only defense against nested `RoleBased` keys is `IsCompositeType()`/`CheckInstallable()`/`CheckUpdatable()`, which reject nested composite types — but these checks run strictly *after* the RLP decode has already completed successfully: [4](#0-3) 

Because each level of nesting requires only decoding a byte-string wrapper plus a type tag, an attacker can encode thousands of nesting levels compactly (each level adds only a handful of bytes to the RLP payload), driving the Go call stack (`DecodeRLP` → `rlp.DecodeBytes` → `Stream.Decode` → `DecodeRLP` → …) to exhaustion. Go goroutine stacks grow dynamically but a runtime stack-overflow still triggers a fatal, unrecoverable process crash (`runtime: goroutine stack exceeds ... — fatal error: stack overflow`), which cannot be caught by `recover()`.

### Impact Explanation
A single `TxTypeAccountUpdate` transaction, reachable by any unprivileged transaction sender (or gasless/fee-delegated sender, since `AccountUpdate` transactions can also carry a fee payer), is decoded by every node that receives it — in the tx pool (`AddRemote`) and again during block execution. A crafted transaction with deeply nested `AccountKeyRoleBased` payload can crash any node's process the moment it attempts to decode the transaction (in tx-pool ingestion, RPC decoding of raw transactions, or block validation), producing a denial-of-service across the network as nodes that receive/relay the transaction or process a block containing it crash. This matches the "acceptance of an invalid transaction or block" / DoS impact class permitted by the analog rules.

### Likelihood Explanation
Likelihood is high: constructing the malicious payload requires no special privileges, no valid account keys, and no consensus access — only crafting RLP bytes for a `TxTypeAccountUpdate`'s `Key` field with deep `AccountKeyRoleBased` nesting and submitting it via public RPC (`eth_sendRawTransaction`) or gossip. The `MaxNumKeysForMultiSig` limit (10) only bounds the *width* of a `WeightedMultiSig` key, not the *depth* of `RoleBased` nesting, and depth-limiting checks (`CheckInstallable`) run only after decode succeeds.

### Recommendation
Enforce a maximum recursion/nesting depth in `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., pass a depth counter through decoding and reject once a small threshold, such as 1 level, is exceeded — consistent with the existing invariant that `RoleBased` keys must not contain composite sub-keys). Alternatively, perform an early, cheap depth/size check on the raw RLP bytes before invoking the recursive decoder, so that oversized/nested payloads are rejected without engaging the recursive `DecodeRLP` call chain.

### Proof of Concept
1. Programmatically build a byte string `keyN = RLP([]byte{AccountKeyTypeRoleBased}, RLP([][]byte{keyN-1}))`, seeded with a trivial base key (e.g., `AccountKeyTypeNil`), and repeat for N ≈ tens of thousands of nesting levels (each level costs only a few bytes, so the total payload can stay within reasonable transaction size limits while still driving Go's stack to its limit).
2. Wrap the outermost encoded key as the `Key` field of a `TxTypeAccountUpdate` transaction (`txInternalDataAccountUpdateSerializable.Key = keyN`), sign it with an arbitrary key so it passes the signature-format checks prior to key decoding, and RLP-encode the full transaction.
3. Submit the raw transaction via `eth_sendRawTransaction` to a Kaia node's public RPC, or directly call `txpool.AddRemote(tx)` / `rlp.DecodeBytes` on the raw bytes.
4. Observe that `TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recurses N times, exhausting the goroutine stack and crashing the node with a fatal `runtime: stack overflow` error, terminating the process (verified only via code-path tracing per index limitations; exact N required to overflow depends on Go runtime stack growth limits and was not empirically measured in this environment).

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
