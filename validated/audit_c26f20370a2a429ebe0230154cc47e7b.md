### Title
Declared-`n` heap preallocation in `ThresholdKeys::read` enables memory-amplification DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` trusts an attacker-controlled `n` field (the participant count, a `u16` read directly from the stream) and immediately performs `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector — and then iterates `1 ..= n` inserting into a `HashMap` — before validating `n` against `t`/`i` or the actual stream length. This is the same bug class as CVE-2026-75935: a declared-length field drives heap preallocation disproportionate to the bytes supplied.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` deserializes `t`, `n`, `i` from the input at lines 591–602. `ThresholdParams::new` is only invoked *after* parsing (line 626), so at line 608 `n` is a raw, unbounded `u16` from the wire:

```rust
// crypto/dkg/src/lib.rs:606-613
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
```

`Vec::with_capacity(usize::from(n))` allocates `n * size_of::<C::F>()` bytes eagerly, before a single scalar is read. With `n = 0xFFFF`, that is 65535 × 32 B ≈ 2 MiB allocated in response to a ~10-byte prefix. `read_F` will fail fast on a short stream, but the capacity allocation has already occurred; an unprivileged party can repeat this per connection/request to amplify heap pressure (allocation is on the read path, not gated by validation). Additionally, the `verification_shares` loop at lines 621–623 iterates `1 ..= n` attempting `n` point reads/insertions regardless of the real `ThresholdParams` validity, so declared `n` also drives work proportional to `n` even when `i > n` (which would later be rejected at line 626). The `ThresholdParams::new(t, n, i)` check that would reject `i > n` or `t > n` happens only after all `n` reads were attempted, so malformed ordering yields parsing effort on data that is guaranteed-invalid.

### Impact Explanation
`ThresholdKeys::read` is listed among the untrusted-bytes entry points. A remote party feeding crafted bytes to this deserialization path can force ~2 MiB of allocation and up to 65535 point-deserialization/HashMap-insert operations per message, with a payload as small as a few bytes (capacity is reserved before `read_F` fails). Repeated across connections/messages this is a memory-amplification denial of service against any service that parses `ThresholdKeys` from peer-supplied data (e.g., multisig re-serialization/recovery flows). Impact is availability-only — no secret leakage or signature forgery — consistent with Medium severity.

### Likelihood Explanation
Reachable wherever `ThresholdKeys::read` consumes non-local bytes; the attacker controls only the first ~11 bytes (`id_len` must match, then `t`, `n=0xFFFF`, `i`, interpolation tag `0`). No valid key material is needed to trigger the allocation. The amplification factor is bounded by `u16` (max 65535 elements), which caps severity at Medium rather than High, and the vector is only exploitable if an integrator actually deserializes attacker-controlled `ThresholdKeys` — the raw `io::Read` signature makes no authenticity guarantee.

### Recommendation
Validate `n` before any allocation: construct `ThresholdParams::new(t, n, i)` immediately after reading the header and reject `t > n`, `i > n`, `i == 0` up front. Cap `n` at a protocol maximum (e.g., the real participant bound) before `Vec::with_capacity`. Prefer `Vec::new()` + `push` over `with_capacity(n)` so allocation grows only as real elements are successfully read, and bound `n` against the remaining stream length (`F::Repr` size × n) before iterating.

### Proof of Concept
Input bytes to `ThresholdKeys::<Ed25519>::read`: `u32` len of `C::ID` (LE), `C::ID`, `t=0x0001`, `n=0xFFFF`, `i=0x0001`, interpolation tag `0x00`, then EOF. Line 608 executes `Vec::with_capacity(65535)` allocating ~2 MiB; `C::read_F` then fails on the empty stream but the allocation already occurred. Repeating this in a loop against an endpoint that calls `read` on peer data amplifies attacker bytes into megabytes of heap churn per attempt, exhausting memory far faster than bandwidth consumed.
