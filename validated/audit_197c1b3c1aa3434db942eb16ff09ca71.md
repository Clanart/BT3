### Title
AI conflict-resolution reassembly can silently splice wrong content into a committed file due to naive first-match marker scanning - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
The Copilot-assisted merge conflict resolution feature reassembles the final file content by re-scanning the on-disk conflicted file for `<<<<<<<`/`=======`/`>>>>>>>` markers and splicing in per-hunk AI-provided resolutions by **position** (`hunkIndex`), not by content matching. `reassembleResolvedFile` uses a greedy "first match wins" algorithm to locate the separator and closing marker for each conflict block, which can be desynchronized by conflict-marker-like text that legitimately exists inside one side of a real conflict (e.g. a file whose own content documents or exemplifies Git conflict markers). This causes hunks to be misaligned, resulting in the wrong resolved content — or leftover fake markers plus unrelated code — being written into the file that the user ultimately commits/pushes.

### Finding Description
`reassembleResolvedFile` walks the raw conflicted file line-by-line: [1](#0-0) 

For each line matching the "ours" marker regex (`^<{7}(?:\s|$)`), it look-aheads for the **first** line matching the separator regex (`^={7}$`) and then the **first** line after that matching the "theirs" marker regex (`^>{7}(?:\s|$)`), treating everything between as one conflict block to be replaced by `hunkResolutions[hunkIndex]`: [2](#0-1) 

This algorithm assumes the conflict-marker lines it finds always belong to the *same* real conflict block delimited by Git. That assumption breaks when the raw file (attacker-influenced repository content, i.e. a branch merged/fetched by the victim) contains additional lines that coincidentally match the marker regexes but are not real Git conflict boundaries — for example:
- A file whose legitimate content documents/quotes Git conflict markers (e.g. a README about how to resolve merge conflicts, or test fixtures), placed anywhere in the file.
- A genuine conflict where one side's own changed text happens to contain lines starting with 7+ `<`, `=`, or `>` characters (nested-looking markers), which is trivially craftable by an attacker who controls a branch that will be merged.

In either case, the naive scanner's first-match-wins search for separator/closing lines can bind to the wrong line, so the computed `closingIndex` does not correspond to the real end of the actual conflict block. This shifts what text is treated as "regular content" versus "inside a conflict block," and also increments `hunkIndex` at the wrong points. Because the correspondence between `hunkResolutions` (from the LLM, in order) and detected blocks is purely positional, any misalignment causes resolution content meant for one hunk to be spliced into a different location, or leftover raw marker/data lines to remain in the final file.

The separate hunk-count validation in `validateResolutionPaths` only checks that the count of `hunks` **the model returned** matches the count of hunks **the context builder computed elsewhere** (`IFileConflictContext.hunks.length`): [3](#0-2) 
This does not protect against `reassembleResolvedFile`'s own independent, naive re-scan of the raw file finding a different set of "blocks" than the context builder found — the two parsers are not the same code path, so a mismatch between them is not caught by this check.

### Impact Explanation
This corrupts what the user commits or pushes without any warning: the AI-resolution flow is explicitly designed to write the reassembled content as the final, already-resolved file, staged and committed by the user (per the code's own framing as "the write path"). A user who resolves a conflict on a malicious/compromised branch could end up committing/pushing a file where unrelated hunks' resolved content ends up in the wrong place, or where fragments of raw conflict-marker text survive into the shipped file — silent corruption of source that could reintroduce vulnerable code, break builds, or smuggle attacker content into what looks like an AI-approved clean merge.

### Likelihood Explanation
Exploitation requires only that the victim (a) clones/fetches a repository containing an attacker-authored branch with conflict-marker-like text inside a file that will conflict, and (b) uses the built-in Copilot AI conflict-resolution feature to resolve it — no admin rights, no local access, and no unnatural steps beyond normal repository collaboration and using an in-product feature as intended. The trigger condition (marker-like lines coincidentally or deliberately present in file content) is easy for an attacker to construct deterministically.

### Recommendation
Do not rely on positional re-scanning of raw marker text disjoint from the parser that originally identified the real conflict hunks. Instead, reuse the exact boundaries (line offsets) computed when the conflict hunks were parsed for context in `copilot-conflict-context.ts` to drive `reassembleResolvedFile`, rather than independently re-deriving them via regex. If independent re-scanning must be kept, make it verify the resulting hunk count strictly matches the expected count *before* accepting any spliced content, and fail closed (skip the file, surface it as `ICopilotSkippedFile`) rather than writing a best-effort reassembly when ambiguity is detected (e.g., when scanning encounters more/less separator or closing markers than expected, or nested-marker patterns).

### Proof of Concept
Given a conflicted file with genuine outer Git markers where the "theirs" side content itself contains a marker-like line block (fully constructible by an attacker committing such content on their branch):
```
<<<<<<< HEAD
real ours content
=======
theirs content that includes, as ordinary data/documentation:
<<<<<<< example
inner fake
=======
inner fake 2
>>>>>>> example
more theirs content after the fake block
>>>>>>> feature-branch
```
When `reassembleResolvedFile` scans from the outer `<<<<<<< HEAD`, its look-ahead loop (`app/src/lib/copilot-conflict-resolution.ts:565-572`) finds the **inner** `=======` as `hasSeparator` and the **inner** `>>>>>>> example` as `closingIndex`, terminating the "conflict block" early. The real closing `>>>>>>> feature-branch` and the trailing "more theirs content..." line are then treated as ordinary file content and copied through verbatim into the final resolved file — leaving stray marker text and unrelated content in what is presented to the user as a clean, fully-resolved file ready to commit.
