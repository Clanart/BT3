### Title
Attacker-controlled length field causes pre-allocation amplification in `ThresholdKeys::read` — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` in the `dkg` crate reads the participant count `n` directly from the attacker-supplied byte stream and immediately performs `Vec::with_capacity(usize::from(n))` when the interpolation discriminant is `0` (`Constant`), before verifying that the corresponding field elements are actually present in the input. A ~20-byte input can therefore claim a buffer sized for `u16::MAX` field elements — the same improper-handling-of-length/data-amplification class as CVE-2024-1947.

### Finding Description
In `ThresholdKeys::read`, after reading the ciphersuite ID and the `(t, n, i)` triple, the code branches on a single interpolation byte. For `Interpolation::Constant` it executes:

```rust
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
``` [1](#0-0) 

`n` is a `u16` read verbatim from the reader at lines 591-602 with no upper bound imposed before allocation (`ThresholdParams::new` validation at lines 625-631 runs only after all `n` reads have been attempted). `Vec::with_capacity(65535)` commits ~2 MiB of heap memory (for 32-byte field elements) based on a claimed length; the reader does not need to supply those bytes — `read_F` fails on the first missing element, but the allocation already happened and is only freed on drop. For comparison, Serai itself acknowledges this exact pattern as "a valid DoS" in `Call::read` and chunked the read there to cap amplification at 1 KB [2](#0-1) , and the tributary `DkgCommitments` reader validates `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT` before allocating [3](#0-2)  — the same defense is missing here.

`ThresholdKeys::read` is a public deserialization API over untrusted bytes (it is explicitly one of the untrusted-input `read` entry points), so an unprivileged party who can feed serialized keys to a node triggers the amplification.

### Impact Explanation
Each invocation of `ThresholdKeys::read` on ~20 attacker bytes forces an allocation of up to ~2 MiB (bounded by `u16::MAX` × `F::Repr` size). Repeated calls — e.g., in a service deserializing key material or retrying parse — amplify a negligible amount of network input into gigabytes of churned heap, degrading or crashing the process. The allocation is transient (freed when `read` errors), so this is a CPU/allocator-pressure and transient-memory DoS, not a persistent leak; impact is availability only.

### Likelihood Explanation
Reachable wherever serialized `ThresholdKeys` are read from storage or messages an external party can influence. Per-call amplification is capped by the `u16` width of `n`, so a sustained stream is required for meaningful memory pressure — consistent with Medium.

### Recommendation
Validate `n` against `t`/`i` sanity and a maximum (or against remaining input length when a sized buffer is available) before `Vec::with_capacity`, or drop `with_capacity` entirely and push into `Vec::new()`, letting the vector grow only as bytes are actually read — mirroring the chunked-read fix in `networks/ethereum/src/machine.rs`.

### Proof of Concept
```rust
// crypto/dkg ThresholdKeys::<C>::read trigger.
// Input layout: id_len(4) | C::ID | t(2) | n(2) | i(2) | interpolation(1)
let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&1u16.to_le_bytes());      // t
buf.extend(&u16::MAX.to_le_bytes());  // n = 65535
buf.extend(&1u16.to_le_bytes());      // i
buf.push(0);                          // Interpolation::Constant
// ~20 bytes in -> Vec::with_capacity(65535) reserves ~2 MiB before
// the first read_F fails on the empty remainder.
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice()); // Err, but allocation occurred
```
