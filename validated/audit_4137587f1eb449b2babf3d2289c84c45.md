### Title
ReceivedOutput::read accepts an arbitrary spend-offset without proving it corresponds to the output's script_pubkey - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` pairs a scalar `offset` with a `TxOut`/`OutPoint`. The offset is the sole authorization data for spending: it is later applied to the threshold keys (`ThresholdKeys::offset`) so the group signs under the tweaked key `key + offset·G`. Legitimate construction goes through `Scanner::register_offset`, which iterates until the tweaked point is even and derives a `p2tr` script that is then stored in `scripts` and matched during `scan_transaction` — i.e., the offset is proven to correspond to a specific script_pubkey.

`ReceivedOutput::read` (wallet/mod.rs:122-134) reconstructs this struct from raw bytes by simply reading a scalar via `Secp256k1::read_F` and consensus-decoding the `TxOut`/`OutPoint`. It performs no check that `key + offset·G` produces `output.script_pubkey`, no check that the offset was one registered through the even-Y iteration, and no check that the script is a bare key-path `p2tr` output with no script path. This is the Serai analog of the Mattermost bug: a deserialization endpoint lets untrusted bytes set a security-critical field (`offset`, analogous to `scheme_admin`) without any consistency/authorization check tying it to the resource it claims (`output`).

### Finding Description
- `Scanner::scan_transaction` only emits a `ReceivedOutput` when `self.scripts` contains `output.script_pubkey`, guaranteeing `output.script_pubkey == p2tr(key + offset·G)` for a registered `offset` (wallet/mod.rs:199-214).
- `ReceivedOutput::read` skips all of that. It trusts the embedded `offset` for an arbitrary `output` (wallet/mod.rs:123-133).
- `register_offset` documents that arbitrary offsets "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script (not by the signature of the key)" (wallet/mod.rs:177-179). The read path imports exactly such arbitrary offsets with no guard.

An attacker who can supply bytes to `ReceivedOutput::read` (e.g., a state-sync blob, a coordinator distributing detected deposits) can:
1. Claim an output paying to a script only *they* can satisfy (script path), reported to the wallet as a normal key-path spendable output — funds reported received that are not spendable by the group key.
2. Pair a legitimately-received output with a different offset, so the signer set produces a signature under `key + wrong_offset·G` that does not correspond to the output's actual tweaked key — the output is rendered unspendable by the wallet despite appearing valid.

### Impact Explanation
High/Medium integrity impact: the wallet's view of spendable funds is corrupted via untrusted bytes. An attacker can cause funds to be reported as received that the threshold key cannot actually spend (offset/script mismatch), or can cause the group to sign under an attacker-chosen tweak. Since `ReceivedOutput` is the input to the spend pipeline (`send.rs` consumes `offset()` to re-key per input), a malicious offset silently redirects the effective signing key.

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput` records cross a trust boundary — the type exposes `serialize`/`write`/`read` precisely so outputs can be transported or persisted. Any deployment that accepts scan results from an untrusted peer or restores state from shared storage is exposed. No threshold collusion, no leaked key, and no malicious validator is required — only attacker-chosen bytes fed to `read`.

### Recommendation
Either bind the offset to the output cryptographically or re-derive it: store the `Scanner`'s base key with the output and, on read, verify `p2tr_script_buf(key + offset·G) == Some(output.script_pubkey)`, rejecting otherwise. At minimum, re-scan the containing transaction's `TxOut` against the `Scanner`'s `scripts` map instead of trusting the serialized offset.

### Proof of Concept
```rust
// Attacker-controlled bytes: an offset they picked, plus any TxOut paying to
// a script only they can satisfy (e.g., p2tr with an attacker script path).
let mut buf = Vec::new();
buf.extend(attacker_offset.to_bytes());          // arbitrary Scalar
buf.extend(serialize(&attacker_txout));          // TxOut to attacker's script
buf.extend(serialize(&outpoint));
let claimed = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// `claimed` is accepted; scanner invariants (offset -> this script_pubkey) never checked.
// Wallet reports it received; the group either cannot spend it, or signs under
// key + attacker_offset*G while the output is actually spendable by the
// attacker's script path.
```

Verification step: construct `ReceivedOutput` via `read` where `p2tr_script_buf(scanner_key + GENERATOR*offset) != output.script_pubkey`; observe `read` returns `Ok` while `Scanner::scan_transaction` on the same output returns empty. This demonstrates the missing check.

Note: I was unable to inspect `networks/bitcoin/src/wallet/send.rs` to confirm exactly how `ReceivedOutput::offset()` is consumed at spend time; the re-keying path is implied by the type's documentation and `ThresholdKeys::offset`/`tweak_keys`, but the precise spend call site is unverified.
