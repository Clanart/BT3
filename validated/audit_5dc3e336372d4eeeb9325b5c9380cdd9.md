### Title
Argument injection via unsanitized `branch` parameter in "Open in Desktop" deep links reaching `git clone -b` - ([File: app/src/lib/parse-app-url.ts])

### Summary
GitHub Desktop registers custom URL protocols (`x-github-client://`, `github-mac://`, `github-windows://`) and parses attacker-influenced deep links via `parseAppURL()`. For the `openRepo` action, the `branch` query parameter is validated only with `testForInvalidChars()`, whose regex does not reject a leading `-`. That same `branch` value is the intended payload for `CloneOptions.branch`, which `clone()` passes to git as `-b <branch>` *before* the `--` argument terminator. A branch value starting with `-` is therefore not treated by git as a ref name but as a command-line option, enabling argument/option injection into `git clone`.

### Finding Description
`parseAppURL` extracts and "validates" the `branch` parameter from an attacker-controlled URL: [1](#0-0) 

The only gate applied is `testForInvalidChars(branch)`: [2](#0-1) 

The `invalidCharacterRegex` blocks control characters, space, and the set `~^:?*[\|"<>`, `@{`, doubled/leading/trailing dots, `.lock`, and trailing slash — but it never excludes a leading `-`. A string such as `--upload-pack=/bin/touch /tmp/pwned;` or `--upload-pack=…` passes this check untouched, because `sanitizedRefName`'s dash-stripping (`.replace(/^[-\+]*/g, '')`) is a *different* function only used for sanitizing UI-typed names, not for the deep-link `testForInvalidChars` validation path.

Downstream, `clone()` builds the git command line by pushing the (attacker-controlled) branch value with `-b` *before* the `--` separator that would otherwise stop option parsing for `url`/`path`: [3](#0-2) 

Because `-b <value>` is positioned ahead of `--`, if `<value>` itself begins with `-`, git's argument parser will interpret it as a flag rather than a literal branch name — the classic "argument injection" pattern. Git supports `--upload-pack=<program>` on transports such as `ssh://`/`file://`/local paths, which lets the invoker specify an arbitrary executable to run in place of `git-upload-pack` on the remote side of the transport. If reachable, this converts an "Open in Desktop"-style clone action into command execution under the user's account.

This is the structural analog to the PoolTogether bug: a value is validated by a check (`testForInvalidChars`) that the code *assumes* fully sanitizes it for its downstream use (`-b` argument to git), but the check's definition of "invalid" doesn't cover the specific case that breaks the invariant "branch value is always used as a ref, never as an option" — just as the Pod contract assumed "individual balance update always implies a corresponding supply update," when in fact one path (withdraw-before-draw) broke that invariant.

### Impact Explanation
If exploitable, a link the user is enticed to click (no local access, no prior malware, no leaked credentials — matching the allowed "link or deep link the user clicks" threat) could result in argument injection into a `git clone` invocation performed automatically by Desktop, potentially leading to code execution outside of normal repository operations. This maps to the allowed impact categories: "code execution... outside the repo" via a crafted link.

### Likelihood Explanation
Requires the user to click a specially crafted `x-github-client://openRepo/...?branch=...` (or `github-mac://`/`github-windows://`) link and for Desktop to not already have the repository cloned (so the "clone" path with `-b` is exercised) — this is the same "Open in Desktop" flow GitHub.com itself generates, so links of this form are not unnatural for users to click. The concrete git-side severity (whether `--upload-pack` or another injectable flag is actually reachable/exploitable for RCE in this exact call, e.g., transport restrictions, `protocol.allow` defaults) was not able to be fully verified from the indexed code in the time available — I was not able to trace, with certainty, the exact function in `app-store.ts`/`dispatcher.ts` that copies `IOpenRepositoryFromURLAction.branch` into `CloneOptions.branch` before this iteration budget ran out, though the field names, types (`branch: string | null`), and existing "Open in Desktop" feature description strongly indicate this is the intended path.

### Recommendation
- In `testForInvalidChars` (or a dedicated validator applied before accepting `branch` from URL actions), reject/strip any value that starts with `-` in addition to the existing character blacklist, mirroring what `sanitizedRefName` already does for typed input.
- In `clone()`, always pass `-b`/branch values after a `--` terminator, or use `git clone --branch=<value>` with an explicit check that `<value>` does not begin with `-`, so a malformed/malicious branch string can never be interpreted as an option regardless of upstream validation gaps.
- Apply the same leading-dash defense-in-depth check anywhere else an externally-supplied ref/branch name is passed to git before a `--`.

### Proof of Concept
1. Attacker hosts or sends a link:
   `x-github-client://openRepo/https://github.com/attacker/repo?branch=--upload-pack=%2Fbin%2Ftouch%20%2Ftmp%2Fpwned%3B`
2. Victim clicks the link; the OS invokes GitHub Desktop with this URL.
3. `parseAppURL` parses `actionName === 'openrepo'`, extracts `branch = "--upload-pack=/bin/touch /tmp/pwned;"`, and `testForInvalidChars(branch)` returns `false` (no blocked characters present), so the action `{ name: 'open-repository-from-url', url, branch, pr, filepath }` is accepted. [4](#0-3) 
4. If the repository is not already cloned, Desktop's clone flow calls `clone(url, path, { branch, ... })`, which appends `['-b', branch]` to the git argument list ahead of the `--` separator. [3](#0-2) 
5. Git receives `... clone -b --upload-pack=/bin/touch\ /tmp/pwned; -- https://github.com/attacker/repo <path>`, and — depending on transport support for `--upload-pack` — may execute the injected program.

```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```
