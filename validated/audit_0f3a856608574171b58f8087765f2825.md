### Title
Missing HTML/script-context defensive escaping of `<`/`>` in the upb JSON encoder (used by PHP, Ruby, Lua bindings) - (File: `upb/json/encode.c`)

### Summary
The GLPI CVE-2018-7563 is a reflected-XSS bug class: an attacker-controlled value (`preference.php` query string) is echoed into an HTML/script response context without HTML-safe escaping, so a downstream browser interprets attacker bytes as markup/script. The consuming-application analog in Protobuf is ProtoJSON serialization: many applications feed protobuf messages (which may contain attacker-supplied string fields obtained from a bounded, trusted-schema parse) straight into `MessageToJson`/`PrintToString`/`upb_JsonEncode` and then embed that JSON literal inside an HTML `<script>` block (a common "bootstrap client state" pattern). Google's C++ core JSON writer and the Java `JsonFormat` printer both implement defense-in-depth escaping of `<`, `>` (Java also escapes `&`, `=`, `'`) specifically to make this embedding pattern XSS-safe, even though these characters are not required to be escaped by the JSON spec. The upb-based JSON encoder — shared by the PHP, Ruby and Lua native bindings — never received this hardening.

### Finding Description
- C++ core JSON writer explicitly escapes `<` and `>` (and a table of other Unicode "security" characters) with the comment "not required by the JSON spec, but help to prevent security bugs in JavaScript": [1](#0-0) , applied via the unsafe-character set check `absl::CharSet("\"\\<>")` in `WriteEscapedUtf8`: [2](#0-1) .
- Java's `JsonFormat.Printer` independently implements the same defense-in-depth: it explicitly escapes `<`, `>`, `&`, `=`, `'` "to prevent XSS risks" (mirroring Gson's default HTML-escaping behavior), plus `\u2028`/`\u2029`: [3](#0-2) , and this is regression-tested against `</script>` payloads: [4](#0-3)  and [5](#0-4) .
- The C++ conformance/behavior test confirms `</script>` in a string field is expected to serialize as `\u003c/script\u003e`: [6](#0-5) .
- In contrast, the shared upb JSON encoder `jsonenc_put_escaped_char`/`jsonenc_stringbody` — the encoder embedded verbatim in `upb/json/encode.c`, `php/ext/google/protobuf/php-upb.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, and `lua/msg.c` — only escapes the mandatory JSON control characters (`\n`, `\r`, `\t`, `"`, `\f`, `\b`, `\\`, and `< 0x20` control codes). `<` and `>` fall through to the `default` branch and are emitted as raw bytes: [7](#0-6) . The identical code is compiled into the PHP extension: [8](#0-7) .
- The PHP pure-PHP fallback path (`GPBJsonWire::escapedJson`) shows the same gap — only RFC 4627-mandatory characters and control chars are escaped, `<`/`>` are untouched: [9](#0-8) .

The failed invariant: Protobuf's own JSON writer already establishes (and tests) an internal security invariant — "ProtoJSON string values must not contain literal `<`/`>` sequences that could close an enclosing `<script>` tag" — as a deliberate defense-in-depth for the well-known JSON-embedded-in-HTML XSS pattern. That invariant is enforced in the C++ core and Java runtimes but silently absent in the upb-backed encoder used by PHP, Ruby, and Lua.

### Impact Explanation
If an application (per the report's exposure assumption: any consuming application) parses attacker-controlled but schema-valid, bounded binary/ProtoJSON input containing a string field such as `</script><script>alert(1)</script>`, then re-serializes that message to ProtoJSON using the PHP or Ruby bindings and embeds the result inside a server-rendered `<script>` block (a documented technique for hydrating client-side state from protobuf-derived JSON), the `</script>` sequence is emitted verbatim and will prematurely close the script tag, allowing injected markup/script to execute in the victim's browser — the same class of impact as CVE-2018-7563 (confidentiality/integrity impact via script execution in another user's session), Medium severity (CVSS-like AV:N/AC:L/UI:R, C:L/I:L).

### Likelihood Explanation
Likely exploitable specifically for PHP, Ruby, and Lua consumers of ProtoJSON output who follow the same JSON-in-`<script>`-tag embedding pattern that Google's own Java/C++ maintainers hardened against. Likelihood is bounded by the fact that this requires (a) an application embedding raw ProtoJSON output inside HTML/script without its own separate escaping, and (b) the PHP/Ruby/Lua binding rather than the C++/Java one. This is a genuine interoperability/hardening gap, not a novel Protobuf memory-safety bug — but it is a concrete, provable inconsistency between backends' security postures for the identical documented `</script>` test case that C++ and Java already codify as security-relevant.

### Recommendation
Port the `<`/`>` (and ideally `\u2028`/`\u2029`) defensive escaping from `src/google/protobuf/json/internal/writer.cc`'s `MustEscape` into `upb/json/encode.c`'s `jsonenc_put_escaped_char`/`jsonenc_stringbody`, so the fix automatically propagates to PHP, Ruby, and Lua bindings that embed this shared upb source. Apply the equivalent fix to the PHP pure-PHP fallback in `GPBJsonWire::escapedJson`. Add a `</script>` regression test to `upb/json/encode_test.cc` mirroring the existing C++ (`json_test.cc:1583`) and Java (`JsonFormatTest.java:2016`) tests.

### Proof of Concept
Using the PHP extension (upb-backed):
```php
$m = new \Foo\TestMessage();
$m->setOptionalString("</script><script>alert(document.cookie)</script>");
echo $m->serializeToJsonString();
// Actual (vulnerable): {"optionalString":"</script><script>alert(document.cookie)</script>"}
// Expected (matching C++/Java hardening): {"optionalString":"\u003c/script\u003e\u003cscript\u003ealert(document.cookie)\u003c/script\u003e"}
```
Compare directly against the C++ core behavior for the identical input, which is asserted by the existing test `JsonTest.HtmlEscape`: [6](#0-5) . Running the equivalent string through PHP/Ruby's `serializeToJsonString`/`to_json` (both compiled from `upb/json/encode.c`) will not perform this transformation, confirming the divergence.

**Uncertainty:** I could not execute PHP/Ruby extension code in this environment (index/read-only access) to literally run the PoC; the divergence is established by static comparison of the escaping tables across `src/google/protobuf/json/internal/writer.cc`, `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`, and `upb/json/encode.c`/`php-upb.c`/`ruby-upb.c`. A Devin session with build/test access would be needed to compile and run the PoC end-to-end for final confirmation.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

    // Used for escaping control chars in strings.
    private static $k_control_char_limit = 0x20;

    private static function jsonNiceEscape($c)
    {
      switch ($c) {
          case '"':  return "\\\"";
          case '\\': return "\\\\";
          case '/': return "\\/";
          case '\b': return "\\b";
          case '\f': return "\\f";
          case '\n': return "\\n";
          case '\r': return "\\r";
          case '\t': return "\\t";
          default:   return NULL;
      }
    }

    private static function isJsonEscaped($c)
    {
        // See RFC 4627.
        return $c < chr($k_control_char_limit) || $c === "\"" || $c === "\\";
    }

    public static function escapedJson($value)
    {
        $escaped_value = "";
        $unescaped_run = "";
        for ($i = 0; $i < strlen($value); $i++) {
            $c = $value[$i];
            // Handle escaping.
            if (static::isJsonEscaped($c)) {
                // Use a "nice" escape, like \n, if one exists for this
                // character.
                $escape = static::jsonNiceEscape($c);
                if (is_null($escape)) {
                    $escape = "\\u00" . bin2hex($c);
                }
                if ($unescaped_run !== "") {
                    $escaped_value .= $unescaped_run;
                    $unescaped_run = "";
                }
                $escaped_value .= $escape;
            } else {
              if ($unescaped_run === "") {
                $unescaped_run .= $c;
              }
            }
        }
        $escaped_value .= $unescaped_run;
        return $escaped_value;
    }
