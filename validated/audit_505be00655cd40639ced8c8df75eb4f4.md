## Analysis

The ASTRO-13 report's core broken invariant is: **a state variable that gates future money-movement decisions is mutated (or left un-mutated) inconsistently around an external call that can fail, so parallel code paths later act on stale/incorrect state and money moves incorrectly.**

Searching Hyperbridge for the analogous pattern — state that should be cleared once a cross-chain request is "settled" but is only cleared on some code paths — turns up the exact bug class in `EvmHost.sol`'s request/response/timeout trio.

`_requestCommitments[commitment]` (a `FeeMetadata{sender, fee}`) is the single source of truth for "this outgoing request is still open and its fee is claimable." Every consuming path is supposed to clear it once the request is finalized:

- `dispatchTimeOut(GetRequestTimeout...)` — explicitly `delete _requestCommitments[commitment];` before the external call, and restores it on failure ("so that it can be retried"): [1](#0-0) 

- `dispatchTimeOut(PostRequestTimeout...)` — same pattern: [2](#0-1) 

- `dispatchIncoming(GetResponse ...)` — reads and pays out the fee, but **never deletes `_requestCommitments[commitment]`**: [3](#0-2) 

This is precisely the ASTRO-13 defect shape: the debt/commitment bookkeeping is mutated correctly on some exit paths (the timeout paths delete-and-restore around the try/catch-equivalent external call) but is left stale on another exit path (`GetResponse` delivery), corrupting downstream logic that trusts `_requestCommitments`.

The downstream logic that trusts this mapping is `fundRequest`, which only checks that a commitment record still exists (`metadata.sender != address(0)`) — it has no awareness of whether the request has already been serviced: [4](#0-3) 

Because `dispatchIncoming(GetResponse)` never deletes the record, `fundRequest` remains permanently callable on a commitment whose GET request has already been answered and paid out. Any unprivileged caller who tops up such a commitment transfers real `feeToken` (or native token swapped into it) into the Host contract for a request that will never be dispatched again — `dispatchIncoming(GetResponse)` only fires once per relayed response, and for the common case of `timeout: 0` (as used by, e.g., `pallet-bandwidth`'s `purchase()` messages and other zero-timeout dispatches — see `evm/src/apps/BandwidthManager.sol` `dispatch` call with `timeout: 0`), `dispatchTimeOut` can *never* be invoked to refund it either, since the request has no timeout timestamp.

### Title
Stale `_requestCommitments` entry after `GetResponse` delivery permanently locks user funds sent via `fundRequest` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`dispatchIncoming(GetResponse, address)` pays out the relayer fee from `_requestCommitments[commitment]` on successful delivery but, unlike both `dispatchTimeOut` overloads, never deletes the entry. The permissionless `fundRequest` function only checks that a commitment record exists, not that it is still pending, so anyone can send additional fee-token funds against an already-finalized (and, for zero-timeout requests, never-timeout-able) commitment. Those funds become permanently unrecoverable.

### Finding Description
`_requestCommitments` is the canonical "is this outgoing request still open" record. `dispatchTimeOut` (both GET and POST variants) treats it as consumed exactly once: it deletes the entry before attempting delivery of the timeout callback, and restores it only if that callback reverts, so the record correctly reflects "still pending" vs. "settled": [1](#0-0) 

`dispatchIncoming(GetResponse, address)` is the sibling "successful delivery" path for the exact same class of request (a `GetRequest` that was dispatched via `dispatch(DispatchGet)` and recorded in `_requestCommitments`), yet it reads `_requestCommitments[commitment].fee`, pays it to the relayer, and leaves the mapping entry intact: [5](#0-4) 

`fundRequest` is a public, unauthenticated entrypoint that trusts this mapping as the sole gate for whether a commitment is "live": [6](#0-5) 

Because the `GetResponse` delivery path never clears the record, `metadata.sender` remains non-zero forever after a successful response, so `fundRequest` continues to accept and lock funds for a request that has already reached its terminal state and will never be dispatched or timed out again (especially for `timeoutTimestamp == 0` requests, which by design never expire and thus never hit `dispatchTimeOut`).

### Impact Explanation
This is an unprivileged, direct loss-of-funds bug: any caller's `feeToken` (or native ETH swapped through the Uniswap router in `fundRequest`) sent against a commitment whose `GetResponse` already landed is irrecoverably locked in the `EvmHost` contract — no code path pays it back out or delivers anything further for that commitment. This matches the bounty's "stealing or loss of funds" / "false state acceptance" (the contract accepts funding for a request state it silently treats as still-open when it is not) impact category.

### Likelihood Explanation
`fundRequest` is a fully public function with no privileged role check, callable by anyone with knowledge of a `commitment` — which is visible on-chain via the `PostRequestEvent`/`GetRequestEvent` and `GetRequestHandled` logs. No malicious relayer, prover, or admin is required; a normal user error (funding a request they believe is still pending, e.g., to guarantee timeout refund) or an attacker deliberately luring another user/integrator to top up a dead commitment is sufficient to trigger fund loss.

### Recommendation
Delete `_requestCommitments[commitment]` inside `dispatchIncoming(GetResponse, address)` immediately after the fee payout, mirroring the pattern already used in both `dispatchTimeOut` overloads. Additionally, harden `fundRequest` to check `_responseReceipts`/delivery state (or an explicit "finalized" flag) before accepting new funding for a commitment, so it cannot accept payment for a request that has already reached a terminal state.

### Proof of Concept
1. App A dispatches a `GetRequest` via `dispatch(DispatchGet)` with `timeout = 0` and `fee = F`; `_requestCommitments[commitment] = {sender: A, fee: F}` is stored.
2. A relayer submits a valid `GetResponse` proof; `HandlerV2` calls `dispatchIncoming(GetResponse, relayer)`. `onGetResponse` succeeds, `fee = F` is transferred to `relayer`, but `_requestCommitments[commitment]` is left untouched (still `{sender: A, fee: F}`). [7](#0-6) 
3. Because `timeoutTimestamp == 0`, this commitment can never legitimately reach `dispatchTimeOut`.
4. Any user B calls `fundRequest(commitment, amount)`. The check `metadata.sender == address(0)` passes (sender is still `A`), `amount` of `feeToken` is pulled from B and added to the still-live-looking `_requestCommitments[commitment].fee`. [6](#0-5) 
5. `amount` is now permanently stuck in the `EvmHost` contract: no further `dispatchIncoming(GetResponse)` call can occur for this already-delivered response, and no `dispatchTimeOut` call can ever occur for a zero-timeout request. Funds are lost.

     * @dev Dispatch an incoming GET response to source module
     * @param response - get response

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
