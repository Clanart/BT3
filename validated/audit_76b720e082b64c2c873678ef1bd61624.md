### Title
Hidden bidirectional-Unicode ("Trojan Source") warning is silently dropped for large diffs, letting attacker-crafted files be committed/pushed unreviewed - (File: `app/src/lib/git/diff.ts`)

### Summary
GitHub Desktop detects invisible bidirectional Unicode control characters (the "Trojan Source" class of attack) via `HiddenBidiCharsRegex` in the diff parser and surfaces a warning banner (`DiffContentsWarning`) whenever a diff is rendered. [1](#0-0) [2](#0-1)  However, this protection depends entirely on the diff actually being classified as renderable. When the raw diff buffer from `git` exceeds a hardcoded size threshold, the diff is instead classified as `Unrenderable` and no `hasHiddenBidiChars` information is even computed or surfaced to the user, meaning the bidi-warning UI is structurally unreachable for that file.

### Finding Description
`buildDiff` in `app/src/lib/git/diff.ts` first checks `isValidBuffer(buffer)`, which compares the buffer length against a fixed constant `MaxDiffBufferSize = 70e6` (70MB), independent of file type, content, or number of hidden characters involved: [3](#0-2) 

If the buffer exceeds that fixed threshold, the function short-circuits and returns `{ kind: DiffType.Unrenderable }` before the diff is ever parsed and before `HiddenBidiCharsRegex` is ever evaluated: [4](#0-3) 

Contrast this with the "large but still renderable" path (`isBufferTooLarge` / `isDiffTooLarge`, driven by `MaxReasonableDiffSize` and the also-fixed `MaxCharactersPerLine = 5000`), which does compute `hasHiddenBidiChars` and preserves it on the `ILargeTextDiff` object so the warning can eventually be shown if the user clicks "Show Diff": [5](#0-4) 

For the `Unrenderable` case, the UI component only shows a generic "The diff is too large to be displayed" message with no bidi warning and no way to inspect content at all: [6](#0-5) 

This is the same bug *class* as the report: a single fixed raw constant (`1e10` in the C4 finding; `70e6` bytes here) is applied uniformly without regard to the actual semantic content it gates, producing a silent, unreviewed pass-through for a subset of inputs. Here, the "reward token decimals" analog is "diff byte size vs. number of malicious hidden characters" — a 70MB+ file can carry the exact same handful of `\u202A-\u202E`/`\u2066-\u2069` bidi override characters as a tiny file, but only the tiny file gets flagged.

### Impact Explanation
An attacker who controls content the victim fetches or checks out (a cloned/fetched repository, a large file added via a branch/PR the user pulls, or a git remote response) can hide Trojan-Source-style bidi characters inside a file whose diff happens to exceed the 70MB raw buffer threshold. Desktop will never compute or display the hidden-bidi warning for that file, and the working-directory changes list still allows the user to stage and commit/push the file normally (whole-file staging does not go through the same `Unrenderable` guard used for partial-patch application in `applyPatchToIndex`, which only blocks *partial* commits, not full "Commit all"). The user is left believing the file was reviewed ("no diff shown" reads as benign/large, not "malicious content hidden"), when in fact the strongest protection Desktop has against this attack class was silently skipped.

### Likelihood Explanation
Requires only that the victim pull/fetch a repository containing one large text file (or that the file grows past ~70MB in the working tree) — no local access, no admin rights, no social engineering beyond a normal clone/fetch/pull, which is squarely inside Desktop's threat model of "attacker controls a cloned/fetched repository." Large generated/vendored files (data dumps, generated code, minified bundles) commonly exceed tens of MB, making the 70MB threshold plausible to hit unintentionally, and trivial for an attacker to engineer intentionally by padding a file.

### Recommendation
Compute `hasHiddenBidiChars` (a cheap regex scan) independently of the `MaxDiffBufferSize`/renderability decision, and surface a warning even for `Unrenderable` diffs — e.g., scan the raw stdout buffer for the bidi character ranges before/regardless of the size gate, and show the same `DiffContentsWarning` banner in `renderUnrenderableDiff()`. Alternatively, scale detection to the file rather than the diff, e.g. via `git grep`/`--all-match` for the specific bidi codepoint ranges, which is independent of diff size.

### Proof of Concept
1. Attacker creates a repository with a text file `payload.txt` that (a) exceeds ~70MB after diffing (e.g., padded content) and (b) contains a small block of hidden bidi override characters (`\u202E`, `\u2066`, etc.) disguising, for example, a backdoored conditional as something else when rendered in a normal editor/terminal.
2. Victim clones/fetches/pulls this branch into GitHub Desktop.
3. Desktop computes the diff via `getWorkingDirectoryDiff`/`buildDiff`; because `buffer.length > MaxDiffBufferSize` (70e6 bytes), `isValidBuffer` returns `false` and `buildDiff` returns `{ kind: DiffType.Unrenderable }` without ever calling `diffFromRawDiffOutput`/`DiffParser.parse`, so `HiddenBidiCharsRegex.test(text)` is never executed. [4](#0-3) 
4. The Changes view renders `renderUnrenderableDiff()`, showing only "The diff is too large to be displayed" — no bidi warning is possible since the diff object carries no such field. [6](#0-5) 
5. Victim stages and commits/pushes the file via the normal "Commit to <branch>" flow (full-file staging, not the partial-patch path in `applyPatchToIndex` that explicitly blocks `Unrenderable` diffs). [7](#0-6) 
6. The hidden bidi payload is committed/pushed with no warning ever shown to the user, despite Desktop having a dedicated mechanism (`HiddenBidiCharsRegex`/`DiffContentsWarning`) specifically designed to catch this.

```typescript
/**
 * V8 has a limit on the size of string it can create (~256MB), and unless we want to
 * trigger an unhandled exception we need to do the encoding conversion by hand.
 *
 * This is a hard limit on how big a buffer can be and still be converted into
 * a string.
 */
const MaxDiffBufferSize = 70e6 // 70MB in decimal

/**
 * Where `MaxDiffBufferSize` is a hard limit, this is a suggested limit. Diffs
 * bigger than this _could_ be displayed but it might cause some slowness.
 */
const MaxReasonableDiffSize = MaxDiffBufferSize / 16 // ~4.375MB in decimal

/**
 * The longest line length we should try to display. If a diff has a line longer
 * than this, we probably shouldn't attempt it
 */
const MaxCharactersPerLine = 5000

/**
 * Utility function to check whether parsing this buffer is going to cause
 * issues at runtime.
 *
 * @param buffer A buffer of binary text from a spawned process
 */
function isValidBuffer(buffer: Buffer) {
  return buffer.length <= MaxDiffBufferSize
}

/** Is the buffer too large for us to reasonably represent? */
function isBufferTooLarge(buffer: Buffer) {
  return buffer.length >= MaxReasonableDiffSize
}
```
