### Title
Single reverting/insufficient reward token permanently blocks claim of all other accrued rewards - (File: rewards/BaseRewardPool.sol)

### Summary
The CometBFT report concerns a system that halts irrecoverably when a single dependent call errors instead of isolating the failure. The closest reachable analog in this codebase's unprivileged reward-claim path is `BaseRewardPool.getReward`, which iterates over all registered reward tokens in one loop and performs an unguarded `safeTransfer` for each. A failure on any single token transfer (e.g. insufficient contract balance for that token due to accounting drift, or a token that reverts transfers) reverts the entire transaction, blocking the user from claiming any of their other, otherwise-healthy accrued rewards.

### Finding Description
`getReward` loops through `rewardTokens` and unconditionally calls `IERC20(rewardToken).safeTransfer(_receiver, reward)` for every token with a nonzero pending balance: [1](#0-0) 

There is no isolation (no try/catch, no per-token skip-on-failure) around each transfer. The same unguarded, all-or-nothing pattern for reward disbursement recurs across the reward system (e.g. `_getReward` in `rewards/BribeRewardPool.sol`, `_getDelegateReward` in `rewards/DelegateVoteRewardPool.sol`, `_sendReward` in `rewards/mWOMSVBaseRewarder.sol` and `rewards/vlMGPBaseRewarder.sol`): [2](#0-1) [3](#0-2) 

If bookkeeping (`userRewards`) for any one reward token ever exceeds the pool's actual token balance for that token — which can happen from rounding/precision drift in `rewardPerToken`/`_earned` accumulation over many small `queueNewRewards` calls, or simply because the pool is transiently under-funded relative to accrued claims before the next `donate`/`queueNewRewards` call tops it up — the `safeTransfer` for that one token reverts. Because all reward tokens are drained in a single loop within a single external call guarded by `updateReward`, that one bad token halts the whole function: no reward token in that call can be paid out, even the ones that are perfectly solvent. This mirrors the reported bug class where a single unrecoverable error from one dependency call is allowed to halt/abort the entire multi-item operation instead of being isolated.

### Impact Explanation
Because `getReward`/`_sendReward` in these reward pools are the only user-facing paths to claim accrued MGP/WOM/bribe rewards, an unprivileged condition (transient balance shortfall on one of several reward tokens tracked in the same pool) can make claims for that account permanently or indefinitely revert until the shortfall is manually resolved by someone funding the pool. Since these pools track multiple reward tokens per staking position (as seen from the loops over `rewardTokens`/`rewardTokensList`), a shortfall on any single token in the array is sufficient to freeze claims of all other, fully-funded reward tokens for that user, which can persist well beyond 24 hours if the deficient token is never replenished.

### Likelihood Explanation
Reachable purely through normal, unprivileged protocol usage: any user calling harvest/claim via `MasterMagpie`, which calls into `getReward` on the relevant `BaseRewardPool`/rewarder, is exposed once the underlying per-token accounting and actual balance diverge for any one of potentially several tracked reward tokens. No admin or governance action is required to trigger the condition once it exists; only the initial creation of the deficit (which can arise from ordinary reward-token addition/removal churn or precision loss during `queueNewRewardsWithoutTransfer` divisions) is needed.

### Recommendation
Wrap each per-token transfer in `getReward`/`_sendReward` (and the analogous loops in `BribeRewardPool`, `DelegateVoteRewardPool`, `mWOMSVBaseRewarder`, `vlMGPBaseRewarder`) so that a failure on one token does not revert the whole call — e.g. cap the transferred amount to `min(reward, IERC20(rewardToken).balanceOf(address(this)))`, or use a try/catch (or low-level call) around each `safeTransfer` and carry any un-paid remainder forward in `userRewards` rather than reverting the entire batch.

### Proof of Concept
Not independently reproducible with the tools available in this session (read-only code index without ability to run a local test harness). The claim is based on static analysis of `rewards/BaseRewardPool.sol` lines 219-240 and the equivalent multi-token payout loops in the other cited reward contracts, all of which lack per-token failure isolation.     /// @notice Calculates and sends reward to user. Only callable by masterMagpie
    /// @param _account Address account
    function getReward(address _account, address _receiver)
        override
        public
        onlyMasterMagpie
        updateReward(_account)
        returns (bool)
    {
        uint256 length = rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
            if (reward > 0) {
                userRewards[rewardToken][_account] = 0;
                IERC20(rewardToken).safeTransfer(_receiver, reward);
                emit RewardPaid(_account, _receiver, reward, rewardToken);
            }
        }

        return true;
    }
