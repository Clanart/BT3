### Title
Deserializing large Lagrange-interpolated threshold keys causes quadratic group-key validation - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t` and `n` values as large as `u16::MAX`, then calls `ThresholdKeys::new`, which computes the group key by evaluating one Lagrange interpolation factor per participant. Each Lagrange factor calculation iterates over the complete `1..=t` participant list, producing `O(t²)` scalar arithmetic. A serialized key with `t = n = 65535` therefore triggers approximately 4.29 billion inner-loop iterations during deserialization.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, and `i` before selecting the interpolation mode and reading the secret share and `n` verification shares [1](#0-0) . `ThresholdKeys::new` then derives the group key by calling `interpolation_factor` once for every participant in `1..=t` [2](#0-1) . For `Interpolation::Lagrange`, each call loops over all included participants and performs two scalar multiplications per other participant [3](#0-2) .

Thus, a syntactically well-formed serialized key can declare a 65535-of-65535 Lagrange threshold and force roughly `65535 * 65534 = 4,294,836,225` scalar multiplications/subtractions before validation completes.

### Impact Explanation
An unprivileged party that can cause an application to deserialize untrusted `ThresholdKeys` data can consume excessive CPU in a single `ThresholdKeys::read` call. Applications exposing key import, backup restoration, configuration loading, or peer-supplied threshold-key material may experience a denial of service.

### Likelihood Explanation
The malicious input is only a few megabytes: the Lagrange variant requires one scalar and `n` encoded verification shares after the small header. All verification shares can reuse the canonical generator encoding, so constructing the input does not require solving a hard cryptographic problem. The cost multiplier comes from the quadratic interpolation logic rather than from input size.

### Recommendation
Validate `t` and `n` against an application-level maximum before constructing `ThresholdKeys`, and compute the group key using an aggregate/interpolation algorithm that is at most `O(t)` after preprocessing. Alternatively, precompute the products over all participant IDs and derive each factor by multiplying by the inverse of the omitted term, or reject serialized Lagrange parameters beyond a conservative protocol limit.

### Proof of Concept
Conceptually, serialize the following `ThresholdKeys<C>` payload:

1. The expected curve ID length and curve ID.
2. `t = 65535`, `n = 65535`, `i = 1`.
3. Interpolation tag `1` (`Interpolation::Lagrange`).
4. Any canonical scalar as `secret_share`.
5. `65535` copies of the canonical generator encoding as verification shares.

Calling `ThresholdKeys::<C>::read` reaches `ThresholdKeys::new`, which invokes Lagrange `interpolation_factor` for participants `1..=65535`; every invocation scans the other `65534` participant IDs, causing billions of scalar operations.
