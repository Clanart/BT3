### Title
False-positive "[gone]" match on commit-message text causes destructive force-deletion of unrelated branches/worktrees - ([File: plugins/commit-commands/commands/clean_gone.md])

### Summary
The cleanup script greps the output of `git branch -v` for the literal substring `[gone]`, but `git branch -v` (without the second `-v`) never emits upstream tracking/gone status — only the branch name, abbreviated commit hash, and the first line of the commit subject. Because git branch names cannot contain `[`, the only place a `[gone]` substring can legitimately come from in that output is an attacker-controlled commit subject line, so any commit whose first line contains the literal text `[gone]` will cause its branch (and any worktree checked out on it) to be force-deleted.

### Finding Description
Step 1 of the command runs `git branch -v` [1](#0-0)  which per git's own documentation only shows `<branch> <hash> <subject>` — tracking/"gone" info is only shown with `-vv`. Step 3 then filters that same output with `grep '\[gone\]'` [2](#0-1)  assuming it will only match branches whose upstream was deleted. Since `-v` never prints that marker, and git branch names disallow the `[` character, the only source of a `[gone]` match in this pipeline is a commit subject line that happens to contain the literal string `[gone]` (e.g. `"docs: mark old flag as [gone] and remove"`).

Once matched, the branch name is extracted with `sed`/`awk` and fed into:
```
worktree=$(git worktree list | grep "\\[$branch\\]" | awk '{print $1}')
...
git worktree remove --force "$worktree"
...
git branch -D "$branch"
``` [3](#0-2) 
Both `git worktree remove --force` and `git branch -D` are destructive, non-recoverable operations: `--force` discards uncommitted/unstaged changes in the worktree, and `-D` force-deletes the branch even if it has unmerged commits. There is no check anywhere in the script that the branch actually has a deleted/gone upstream — the entire "is this branch gone" determination rests on the unreliable text match against `git branch -v` output.

An attacker who can get a commit merged, reviewed, or checked out locally (e.g., via a pull request that a maintainer fetches into a local branch/worktree to review) controls the commit subject line and can plant the string `[gone]` in it. When the victim later runs the `/clean_gone` command (a documented, expected maintenance workflow per the plugin's README, which explicitly claims "Safe to run - only removes branches already deleted remotely") [4](#0-3) , Claude Code executes this script and force-deletes the attacker-targeted branch and its worktree, even though the branch's remote upstream is still live and the branch may contain unmerged or uncommitted work.

### Impact Explanation
This is an unauthorized/destructive git automation action triggered by ordinary repository content (a commit message) that the victim did not intend to act on. It can cause irreversible loss of uncommitted worktree changes and unmerged branch commits, violating the command's documented safety guarantee ("only removes branches already deleted remotely"). This matches a data-loss / unauthorized file-and-git-state-mutation impact class, reachable purely through attacker-controlled commit text merged or checked out through normal review workflows — no elevated privilege, leaked keys, or social engineering beyond a normal contribution/PR is required.

### Likelihood Explanation
Preconditions: (1) victim uses the `/clean_gone` plugin command as documented for routine maintenance, and (2) at the time of running it, at least one local branch's HEAD commit subject contains the literal substring `[gone]` — this can be planted by any contributor whose commit gets checked out locally (common for PR review via local branches/worktrees). No race condition or timing is needed; the match is purely textual and deterministic, making this fully repeatable whenever such a commit message exists among local branch tips.

### Recommendation
Do not rely on substring-matching arbitrary commit-subject text. Use `git branch -vv` and parse the actual tracking-status field (or better, `git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads` and check for the exact `[gone]` token in the upstream-track field, not free text), and only ever consider a branch a candidate if `git rev-parse --verify <branch>@{upstream}` fails specifically due to the upstream ref being deleted. Additionally, avoid `--force` on `git worktree remove` and `-D` on `git branch` without first checking for uncommitted changes/unmerged commits and prompting for explicit confirmation.

### Proof of Concept
Integration test (bash):
1. Create a temp git repo `origin` with a branch `feature`; clone it to `work`.
2. In `work`, create commit on `feature` with subject: `"cleanup: rename [gone] flag"` (contains literal `[gone]` but branch is *not* deleted from remote).
3. Add a worktree for `feature`: `git worktree add ../wt feature`, and create an uncommitted file in `../wt`.
4. Extract and run the exact step-3 script from `clean_gone.md` against `work`.
5. Assert:
   - `git branch -D feature` was executed (branch removed) despite `feature`'s remote upstream (`origin/feature`) still existing (`git ls-remote origin feature` still returns the ref).
   - The worktree `../wt` was force-removed, discarding the uncommitted file, even though no upstream was actually deleted.
   - Test fails prior to fix (branch/worktree improperly removed) and passes after switching to `git branch -vv`/`for-each-ref` based gone-detection, where the same commit-message text no longer triggers deletion.

   ```bash
   # Process all [gone] branches, removing '+' prefix if present
   git branch -v | grep '\[gone\]' | sed 's/^[+* ]//' | awk '{print $1}' | while read branch; do
     echo "Processing branch: $branch"
     # Find and remove worktree if it exists
     worktree=$(git worktree list | grep "\\[$branch\\]" | awk '{print $1}')
     if [ ! -z "$worktree" ] && [ "$worktree" != "$(git rev-parse --show-toplevel)" ]; then
       echo "  Removing worktree: $worktree"
       git worktree remove --force "$worktree"
     fi
     # Delete the branch
     echo "  Deleting branch: $branch"
     git branch -D "$branch"
   done
