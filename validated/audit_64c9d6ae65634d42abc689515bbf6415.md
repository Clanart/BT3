### Title
BalanceHandler shared-state reuse across recursive/nested precompile calls corrupts EVM StateDB vs. x/bank ledger — analogous checkpoint/reset desync — ([File: precompiles/common/balance_handler.go])

### Summary
The Alchemix `Voter`/`Bribe` bug arises because a shared, mutable accounting cursor (`totalVoting`) is reset by one code path (`resetVoting()`) without being synchronized with another path that reads/writes per-user checkpoints (`getRewardForOwner` → `_writeCheckpoint`). The two subsystems silently diverge, and an attacker can exploit ordering of calls across epochs to steal or lock value.

The Cosmos EVM repository contains a structurally identical class of bug in the precompile "native balance sync" bridge between the Cosmos `x/bank` event log and the EVM `statedb.StateDB` balances: `precompiles/common/balance_handler.go`. `BalanceHandler.prevEventsLen` is exactly this kind of mutable cursor — it is set by `BeforeBalanceChange` (a "reset") and consumed by `AfterBalanceChange` (a "checkpoint replay" that mutates `stateDB.AddBalance`/`SubBalance` based on the bank events emitted since the cursor). If the same `BalanceHandler` instance is reused/shared across nested or recursive precompile invocations within one EVM call tree, an inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, so the outer call's `AfterBalanceChange` replays the wrong slice of `x/bank` events into the EVM `StateDB` — mirroring exactly the "totalVoting reset without checkpoint sync" bug pattern, except the value being desynchronized is the native/EVM dual-balance representation instead of vote weights.

### Finding Description
- `BalanceHandler` is a small state machine with a single mutable field: `prevEventsLen`. [1](#0-0) 
- `AfterBalanceChange` slices `ctx.EventManager().Events()` starting at `bh.prevEventsLen` and, for every `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` event since that point, mutates the EVM `StateDB` balance via `AddBalance`/`SubBalance`. [2](#0-1) 
- The safe pattern used by the primary `RunNativeAction`/`runNativeAction` flow allocates a **fresh** `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()`, scoping the cursor to a single invocation. [3](#0-2) 
- However, the repository's own test/reference implementation, the debug precompile (`testutil/testdata/debug/debug.go`), demonstrates the unsafe pattern: it calls `p.GetBalanceHandler()` — a single handler instance retained on the `Precompile` struct — rather than instantiating a new one per call. `BeforeBalanceChange`/`AfterBalanceChange` are invoked directly against this shared instance. [4](#0-3) 
- The repository ships a dedicated regression test suite explicitly documenting this as a known bug class: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* The test drives a contract that recursively calls back into the precompile (`callback(0)`) and asserts a specific count of `debug_precompile` events, confirming the recursive-call/shared-instance scenario is reachable from ordinary contract bytecode. [5](#0-4) [6](#0-5) 

The root-cause invariant break: **`prevEventsLen` must bound exactly the set of `x/bank` events attributable to one particular precompile call's native action.** If a nested/recursive precompile call (contract → precompile A → EVM call → precompile B, or self-recursion through a caller contract) shares the handler instance, the inner call resets `prevEventsLen` to a later index. When the outer call later invokes `AfterBalanceChange`, it now replays only the events *after* the inner call — silently dropping the outer call's own bank-event-driven `StateDB.AddBalance`/`SubBalance` mutations (or, depending on ordering, double-applying the inner call's delta to the outer scope). This produces a StateDB balance that no longer matches the ground-truth `x/bank` coin balance for the affected address(es) — an accounting-corruption of spendable value across the native/EVM dual-balance representation, which is explicitly the "Asset-representation path" invariant called out in the audit pivots (x/vm statedb must preserve 1:1 accounting with bank balances).

### Impact Explanation
If StateDB and x/bank fall out of sync for an account balance:
- The EVM's view of an account's spendable ETH-denominated balance can diverge from the actual bank balance backing it, enabling either (a) balances to be inflated in StateDB relative to bank (theft/duplication — the account can spend EVM value that isn't actually backed by real coins once committed), or (b) balances to be under-credited (funds effectively frozen/lost from the EVM-visible side while genuinely held in `x/bank`).
- Because `StateDB` changes are what get persisted into consensus state on commit, this is a direct, unprivileged-triggerable corruption of "spendable user value across native balances, EVM balances" — matching the required Critical impact category.

### Likelihood Explanation
This is only exploitable if a reachable *production* precompile follows the unsafe "shared/instance-level `BalanceHandler`" pattern (as the debug precompile does) and can be recursively invoked within a single EVM transaction (e.g., precompile-to-precompile call, or a contract re-entering the same precompile through a callback). I was **not able to fully verify** whether any of the currently registered, non-test precompiles (staking, distribution, bank, erc20, ics20, gov, slashing) actually retain a `BalanceHandler` on the struct instance rather than using the safe per-call `BalanceHandlerFactory.NewBalanceHandler()` path in `precompiles/common/precompile.go`. The main `RunNativeAction` code path appears to correctly scope the handler per call, which would mitigate the issue for precompiles that go through it. The debug precompile and its dedicated regression test strongly suggest this exact bug was identified as reachable through recursive precompile calls at some point in this codebase's history, but confirming whether it remains exploitable in a currently-shipped production precompile (vs. already mitigated by the factory pattern, with the debug precompile/test kept only as a regression guard) requires deeper code review than the indexed context allows.

### Recommendation
- Audit every concrete `Run`/`Execute` implementation for all registered precompiles (static and dynamic, including any custom/`werc20`/ICS20 precompiles) to confirm each call path allocates a **new** `BalanceHandler` via `BalanceHandlerFactory.NewBalanceHandler()` scoped strictly to that invocation, never reusing a struct-level shared instance (the pattern in `testutil/testdata/debug/debug.go` should not be replicated in production precompiles).
- Add an explicit guard/assertion that `prevEventsLen` monotonically corresponds to the correct call frame — e.g., track the cursor on a stack keyed by `stateDB.precompileCallsCounter`/journal snapshot ID rather than a single scalar, so nested calls cannot clobber an outer frame's baseline.
- Extend `evmd/tests/integration/balance_handler/balance_handler_test.go`-style tests to run against every production precompile capable of triggering nested EVM/precompile calls, not just the debug precompile, to close the coverage gap.

type BalanceHandler struct {
	bankKeeper    BankKeeper
	prevEventsLen int

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.Wrap(errors2.ErrUnauthorized, "could not create statedb in debug precompile")
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	err = stateDB.AddPrecompileFn(p.Address(), snapshot, events)
	if err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	// Start the balance change handler before executing the precompile.
	p.GetBalanceHandler().BeforeBalanceChange(ctx)

	initialGas := ctx.GasMeter().GasConsumed()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)
	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	// This handles any out of gas errors that may occur during the execution of a precompile tx or query.
	// It avoids panics and returns the out of gas error so the EVM can continue gracefully.
	defer cmn.HandleGasError(ctx, contract, initialGas, &err)()

	res, err := p.Execute(ctx, stateDB, contract, readonly)
	if err != nil {
		return nil, err
	}

	if err != nil {
		return nil, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	// Process the native balance changes after the method execution.
	if err := p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB); err != nil {
		return nil, err
	}

	return res, nil
}

func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {

		ConstructorArgs: []interface{}{},
