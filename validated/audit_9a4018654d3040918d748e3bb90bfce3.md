Confirmed: the canonical `pallet-messaging-incentives::FeeHandler::on_executed` path recovers the `relayer` account by cryptographically verifying the sr25519 signature on the message's `signer` field (`relayer_for`, `modules/pallets/messaging-incentives/src/lib.rs:140-153`), so reputation can only be minted to whoever actually signed the delivered message. `pallet-state-coprocessor::handle_get_requests`, however, mints the same `ReputationAsset` using a completely different, unauthenticated path.

### Title
Unauthenticated relayer-address field lets anyone redirect `pallet-state-coprocessor` reputation-token rewards to any account - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`handle_get_requests` mints `ReputationAsset` tokens to `address`, a raw byte field taken verbatim from the caller-supplied `GetRequestsWithProof` payload, with no signature or on-chain evidence binding that address to the entity that produced the proof. The entry point (`handle_unsigned`) is a permissionless unsigned extrinsic (`ensure_none`), and the mint amount scales with `total_bytes` of the batch's GetResponses — a quantity the caller substantially controls by choosing which storage keys to query. This mirrors the StakeUp `depositTby` bug class: a reward is paid out proportional to an easily-inflated, caller-chosen metric, without verifying that the claimed beneficiary actually performed (or is entitled to) the work being rewarded.

### Finding Description
`GetRequestsWithProof::address` (`modules/pallets/state-coprocessor/src/impls.rs:54`, "Address that should be credited with fees") flows straight into the mint call: [1](#0-0) 

There is no signature check anywhere in this path tying `address` to the submitter. Compare this with the sibling pallet `pallet-messaging-incentives`, whose canonical `FeeHandler::on_executed` mint path explicitly recovers the relayer from a verified sr25519 signature before minting: [2](#0-1) 

and the outbound-request delivery reward on `pallet-relayer` requires a signature whose recovered signer must match the address proven in the destination's receipt slot before any payout: [3](#0-2) 

`pallet-state-coprocessor` has no equivalent check. The extrinsic that reaches this code is unsigned and open to anyone: [4](#0-3) 

`validate_unsigned` only re-runs `handle_get_requests` (to check the proof is valid) and de-duplicates by request commitment hash — it never inspects or constrains `address`: [5](#0-4) 

The only "cost" gating this path is the destination app's prepaid `BandwidthGate::try_consume` allowance (charged against `(response.get.source, response.get.from)` — i.e. the querying app, not the address receiving reputation) and the state-proof verification itself: [6](#0-5) 

Because the mint amount is `rate * total_bytes` and `total_bytes` is the abi-encoded size of the *values* returned for caller-chosen storage `keys`, a caller can pick keys known to resolve to large on-chain values (or simply request many/large keys against an app whose bandwidth allowance they control or that is on the `Allowlist` bypass) to inflate `total_bytes` far beyond any real "delivery effort," and then name an arbitrary `address` — including an address with no relationship to the request, proof construction, or relaying infrastructure — to receive the resulting reputation mint. Anyone capable of constructing a valid Get response state proof (which requires no privileged relayer role or admin/governance access — proofs are derived from public chain state) can claim this reward for themselves or any account they choose.

### Impact Explanation
`ReputationAsset` is a real fungible asset minted via `frame_support::traits::fungible::Mutate` (`modules/pallets/messaging-incentives/src/lib.rs:80`), i.e., genuine on-chain value creation, not merely an informational counter. Unauthorized minting of this asset to an attacker-controlled address, driven by a caller-chosen, inflatable byte metric rather than verified delivery work, is an unauthorized-execution / false-attribution issue: it lets an unprivileged party redirect protocol-funded relayer incentives to themselves at a rate decoupled from actual relaying effort, directly paralleling the "SUP rewards gamed by depositing near-expiry TBYs" bug class (reward proportional to a gameable metric rather than true economic/operational contribution).

### Likelihood Explanation
High. The entry point is a permissionless unsigned extrinsic reachable by any network participant; no relayer role, governance action, or compromised key is required. The only prerequisite is producing a valid ISMP Get-request/response state proof, which is a normal, public operation (any party running a light client / state proof tooling can do this, and can even be the same actor that dispatched the underlying `GetRequest` from a self-controlled app). Dedup (`response_receipt`) prevents replaying the exact same request twice, but does not prevent an attacker from repeatedly dispatching fresh, self-chosen `GetRequest`s designed to maximize `total_bytes` per proof batch while naming themselves as `address` each time.

### Recommendation
Bind the reputation-reward recipient to verifiable on-chain evidence of who performed the delivery, consistent with the pattern already used elsewhere in the codebase:
- Require `handle_unsigned`/`GetRequestsWithProof` to carry a signature (as `pallet-messaging-incentives::relayer_for` does) over the request/response commitments, and recover the reward recipient from that signature rather than trusting the raw `address` field, or
- Remove the caller-supplied `address` entirely and instead attribute the reward to the account that authored the extrinsic (requiring a signed, fee-paying origin) or to an address cryptographically tied to the proof submission.
Additionally, consider capping/normalizing the byte metric used for minting (e.g., per-request caps, or excluding attacker-influenced value sizes) so the reward cannot be trivially inflated by querying large storage values.

### Proof of Concept
1. Attacker deploys (or uses an already-registered) source-chain app and dispatches one or more `GetRequest`s whose `keys` are chosen to resolve to large stored values on the destination chain (e.g., large blobs), and ensures the app has sufficient/no-cost bandwidth allowance (own subscription, or an allowlisted app).
2. Attacker (or anyone) constructs the corresponding source-membership proof and destination state proof for these requests, and submits `state_coprocessor::handle_unsigned(GetRequestsWithProof { requests, source, response, address: <attacker_account_bytes> })` as an unsigned extrinsic — no signing key or fee payment required (`ensure_none` origin).
3. `handle_get_requests` verifies the proofs (they are valid, since the attacker legitimately dispatched/queried real state), computes `total_bytes` from the large response values, and mints `MintPerByte * total_bytes` of `ReputationAsset` directly to `attacker_account_bytes` (`modules/pallets/state-coprocessor/src/impls.rs:164-186`) — with no check that this account is the entity that produced the proof, ran relayer infrastructure, or is registered as a relayer in any way.
4. Repeat with fresh `GetRequest`s (dedup only blocks exact re-processing of the same request) to continuously mint reputation to the attacker's address, decoupled from genuine relaying work.

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
