## Title
Symlinked `.gitignore` write follows symlink to external target with no `O_NOFOLLOW`/lstat guard - (File: `app/src/lib/git/gitignore.ts`)

## Summary
`saveGitIgnore` computes `ignorePath` as `Path.join(repository.path, '.gitignore')` and passes it directly to `fs/promises` `writeFile(ignorePath, fileContents)` with no `lstat`/symlink check and no `O_NOFOLLOW`/`wx` flag. [1](#0-0) 

## Finding Description
Node's `fs.promises.writeFile` opens the final path component with the default `'w'` flag, which follows symlinks rather than rejecting or replacing them. If a cloned/fetched repository ships `.gitignore` as a symlink pointing to a path outside the repository, `writeFile(ignorePath, fileContents)` transparently opens and truncates the symlink *target*, not the symlink itself. The companion read path, `readGitIgnoreAtRoot`, uses `FS.readFile` which likewise follows the symlink, so `appendIgnoreRule` reads the external target's current contents, appends the escaped pattern, and `saveGitIgnore` writes the combined content back through the same symlink to the same external target every time. [2](#0-1) [3](#0-2) 

Notably, elsewhere in the codebase a dedicated `resolveWithin` helper is used specifically to guard against "path traversal and symlink escapes" before reading conflict files, showing the project is aware of and mitigates this class of issue in some code paths — but that protection is absent here. [4](#0-3) 

Because there is no `O_NOFOLLOW`/`lstat` check, this behavior is stable and repeatable: every invocation of the "Ignore file" action (via `appendIgnoreFile` → `appendIgnoreRule` → `saveGitIgnore`, wired to `Dispatcher.appendIgnoreFile` and `AppStore._appendIgnoreFile`) re-opens the same symlink and redirects the write to the same external target, confirming the described "repeat the action twice" behavior. [5](#0-4) 

## Impact Explanation
An attacker-controlled repository can ship a `.gitignore` file that is a filesystem symlink (git supports committing symlinks as blobs; on macOS/Linux a normal `git clone`/checkout materializes it as a real symlink) pointing at a sensitive file outside the repository (e.g., a dotfile, shell profile, or any file writable by the user). When the victim uses the ordinary "Ignore file" context-menu action in GitHub Desktop on any changed/untracked file, GitHub Desktop reads the current contents of the external target (following the symlink) and rewrites it with the original contents plus the newly appended, git-escaped ignore pattern — a file write outside the repository whose content is partially attacker-influenced (pre-seeded target content) and partially user-influenced (the ignored file name). This matches the program's "file write... outside the repo" valid-impact category.

## Likelihood Explanation
Exploitation only requires the victim to clone/open an attacker-supplied repository and perform the common "Ignore file" action on any file in the Changes list — no unnatural steps, no admin rights, no local access. This is a normal, expected GitHub Desktop workflow, making the likelihood high wherever symlinked working-tree files are honored (i.e., macOS/Linux, and Windows with symlink support enabled).

## Recommendation
Before writing to `ignorePath`, verify with `fs.lstat`/`fs.promises.lstat` that the path is not a symlink (or resolve it with the repository-scoped `resolveWithin` helper already used in `copilot-conflict-context.ts`) and reject/refuse to write if it resolves outside `repository.path`. Alternatively, open the file with flags that avoid following an existing symlink (e.g., unlink-then-create, or use `O_NOFOLLOW` where supported) so writes cannot be redirected to an external target.

## Proof of Concept
1. Create a malicious repository whose `.gitignore` is a symlink to an external file, e.g. `ln -s ~/.bash_profile .gitignore` inside the repo, then commit/push it (git tracks and stores symlinks as blobs).
2. Victim clones this repository with GitHub Desktop on macOS/Linux; the working tree materializes `.gitignore` as a real symlink to `~/.bash_profile`.
3. Victim right-clicks any untracked/changed file in the Changes list and selects "Ignore file". This calls `appendIgnoreFile` → `appendIgnoreRule` → `saveGitIgnore`. [6](#0-5) 

4. Observe that `~/.bash_profile` (not a file inside the repo) now contains its original content plus the new ignore pattern.
5. Repeat step 3 with a different file; observe the write again lands on `~/.bash_profile`, confirming the symlink is followed on every invocation rather than being replaced or rejected.

export async function readGitIgnoreAtRoot(
  repository: Repository
): Promise<string | null> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  return new Promise<string | null>((resolve, reject) => {
    FS.readFile(ignorePath, 'utf8', (err, data) => {
      if (err) {
        if (err.code === 'ENOENT') {
          resolve(null)
        } else {
          reject(err)
        }
      } else {
        resolve(data)
      }
    })
  })
}

export async function saveGitIgnore(
  repository: Repository,
  text: string
): Promise<void> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  if (text === '') {
    return new Promise<void>((resolve, reject) => {
      FS.unlink(ignorePath, err => {
        if (err) {
          reject(err)
        } else {
          resolve()
        }
      })
    })

  await writeFile(ignorePath, fileContents)

/** Add the given pattern or patterns to the root gitignore file */
export async function appendIgnoreRule(
  repository: Repository,
  patterns: string | string[]
): Promise<void> {
  const text = (await readGitIgnoreAtRoot(repository)) || ''

  const currentContents = await formatGitIgnoreContents(text, repository)

  const newPatternText =
    patterns instanceof Array ? patterns.join('\n') : patterns
  const newText = await formatGitIgnoreContents(
    `${currentContents}${newPatternText}`,
    repository
  )

  await saveGitIgnore(repository, newText)
}
