### Title
ProtoJSON parser silently accepts duplicate fields expressed via alternate name spellings (camelCase vs snake_case), allowing value confusion - (File: python/google/protobuf/json_format.py)

### Summary
Protobuf's ProtoJSON parser is documented to reject a JSON object that sets the same field twice. In the pure-Python implementation, this duplicate-key check is keyed on the literal JSON text string, not on the resolved `FieldDescriptor`. Because a field can be legally addressed by either its `json_name` (camelCase) or its declared `name` (snake_case), an attacker who controls a JSON payload can supply the same logical field twice under two different spellings; the second occurrence is accepted and silently overwrites the first, and no "multiple fields" error is raised.

### Finding Description
`_ConvertFieldValuePair` builds `fields_by_json_name` from `message_descriptor.fields` [1](#0-0) , then for each incoming JSON key resolves a field first by `json_name`, falling back to the declared proto `name` [2](#0-1) . The only duplicate-detection guard tracks the literal key string in a `names` list and raises only if the identical string repeats [3](#0-2) , rather than tracking the resolved `FieldDescriptor`. Consequently `{"int32Value": 1, "int32_value": 2}` is accepted, and the field ends up holding `2` — the value from whichever key was processed last — with no diagnostic. Python's own test suite documents this as intentional-but-acknowledged incorrect behavior: [4](#0-3) . This is the exact bug class described in CVE‑2017‑17843: a parser that extracts/matches an attacker-controlled textual identifier using a check that considers two different spellings/representations as distinct when the downstream consumer actually treats them as referring to the same logical entity, allowing an attacker to smuggle a second, conflicting value past validation logic that only looked at the first-seen key.

### Impact Explanation
Any application that (a) inspects a ProtoJSON payload's keys or does field-name-based validation/allow-listing before or independent of full ProtoJSON parsing, or (b) relies on "duplicate field ⇒ parse error" as a safety net (e.g., anti-JSON-parameter-pollution logic) can be bypassed: the attacker supplies the "safe" value under one spelling for any external inspection and the actual malicious value under the other spelling, which wins during protobuf's own parse. This is a data-integrity/parser-differential issue (not memory corruption), matching the Medium severity of the analog CVE, whose impact was also "wrong value used due to ambiguous identifier extraction," not RCE or crash.

### Likelihood Explanation
Trivial to trigger with an ordinary bounded ProtoJSON payload through the public `json_format.Parse`/`MessageToJson` round-trip API; requires no special schema, no arena/registry corruption, and no privileged access — only two JSON keys that map to the same field via its documented dual naming (`json_name` vs `name`). Likelihood is high since it is a normal-looking payload, but the impact is confined to the specific pattern of an application trusting duplicate-key rejection or per-key inspection prior to full protobuf parsing.

### Recommendation
Change the duplicate-detection in `_ConvertFieldValuePair` to track the resolved `FieldDescriptor` object (or its number) rather than the raw JSON key string, so that any second occurrence of the same field — regardless of which of its valid spellings is used — raises the existing "should not have multiple … fields" `ParseError`. Apply the same fix to the analogous map/extension alternate-name paths noted in `testDuplicateFieldAlternateNamesMap` [5](#0-4) .

### Proof of Concept
Using the pure-Python `json_format` module (matching the existing acknowledged test):
```python
from google.protobuf import json_format
from google.protobuf.internal import test_util  # or any generated message with int32_value field
msg = json_format_proto3_pb2.TestMessage()
json_format.Parse('{"int32Value": 1, "int32_value": 2}', msg)
assert msg.int32_value == 2  # silently overwritten, no ParseError raised
```
This is exercised verbatim by the existing repository test `testDuplicateFieldAlternateNames` [6](#0-5) , which documents the expected (but flagged-as-buggy) result `parsed_message.int32_value == 2`.
