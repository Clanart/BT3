### Title
`deny_list` method blocking is enforced only on the EVM HTTP RPC server and silently bypassed via the EVM WebSocket RPC server - (File: evmrpc/rpcstack.go)

### Summary
The `[evm].deny_list` config option is meant to let operators fail-fast on specific JSON-RPC methods (per `evmrpc/AGENTS.md`: "Deny list defines list of methods that EVM RPC should fail fast, e.g `["debug_traceBlockByNumber"]`"). This is implemented by calling `srv.RegisterDenyList(method)` only inside `HTTPServer.EnableRPC` [1](#0-0) . `HTTPServer.EnableWS`, which stands up the separate WebSocket JSON-RPC server on the EVM WS port, never receives or registers any deny list at all [2](#0-1) , and `WsConfig` has no `DenyList` field to carry it [3](#0-2) . `NewEVMWebSocketServer` builds its own `wsConfig` from `evmrpcconfig.Config` without ever referencing `config.DenyList` [4](#0-3) , unlike `NewEVMHTTPServer`, which explicitly wires `httpConfig.DenyList = config.DenyList` [5](#0-4) .

### Finding Description
This is structurally the same bug class as GHSA-w42g-7vfc-xf37: a request-admission restriction (there, GraphQL validation rules/introspection disabling; here, the EVM RPC `deny_list`) is correctly enforced on the primary/HTTP transport but is never propagated to the secondary WebSocket transport that the same server exposes, because the WS code path builds an independent `rpc.Server` and independent config struct.

Concretely:
- `HTTPServer.EnableRPC` creates its own `rpc.Server`, registers the configured APIs, and then loops over `config.DenyList` calling `srv.RegisterDenyList(method)` [6](#0-5) .
- `HTTPServer.EnableWS` creates a second, independent `rpc.Server`, registers largely the same APIs (`RegisterApis(apis, config.Modules, srv)`), but has no equivalent deny-list registration step anywhere in the function [7](#0-6) .
- The `WsConfig` struct that parameterizes `EnableWS` simply does not carry a `DenyList` field to begin with [3](#0-2) , so there is no way for the caller to even supply one.
- `server.go`, the only caller of both `EnableRPC`/`EnableWS` in production, only sets `DenyList` on `httpConfig`, not on `wsConfig` [5](#0-4) [4](#0-3) .

Because both `NewEVMHTTPServer` and `NewEVMWebSocketServer` register the `eth` namespace (`BlockAPI`, `TransactionAPI`, `StateAPI`, `InfoAPI`, `SendAPI`, `SimulationAPI`) and `net`/`web3` on WS as well as HTTP [8](#0-7) , any `eth_*`/`net_*`/`web3_*` method name an operator adds to `deny_list` to fail-fast on the HTTP endpoint remains fully callable through the WebSocket endpoint (default `ws://0.0.0.0:8546`), since the WS `rpc.Server` was never told about the deny list. (`debug_*` and `sei_*` methods are not registered on WS at all regardless of this bug, so the specific `debug_traceBlockByNumber` example in `AGENTS.md` is not itself reachable via WS — but any deny-listed `eth_*`/`net_*`/`web3_*` method is.)

### Impact Explanation
`deny_list` is the operator's mechanism to fail-fast/disable specific JSON-RPC methods that are deemed unsafe, unstable, or too resource-intensive for that node's default configuration. An operator who disables a heavy or unsafe `eth_*` method (e.g., an expensive simulation/estimateGas variant, or any future method added to `deny_list`) on the assumption that the whole RPC surface is protected can be trivially bypassed by any public client simply connecting to the WS port and invoking the same method name — since `WsConfig`/`EnableWS` provide no enforcement path at all. Depending on which method an operator has deny-listed for protection (this is a generic mechanism, not scoped to specific method names), this can translate into resource exhaustion / crash of a default-configuration public RPC node, since the operator's chosen safety valve for that node is entirely absent on the WS listener.

### Likelihood Explanation
Any unprivileged public RPC/WebSocket client can trigger this: it requires nothing more than connecting to the exposed EVM WebSocket JSON-RPC endpoint (which is enabled by default alongside HTTP) and calling the exact method name the operator intended to block. No special privileges, no malicious peer/validator behavior, and no dependency-only code path — purely a public-RPC transport-selection bypass of an operator security control.

### Recommendation
Thread `DenyList` (and ideally `SeiLegacyAllowlist`, to the extent WS ever exposes gated namespaces) into `WsConfig`, and call `srv.RegisterDenyList(method)` for each entry inside `HTTPServer.EnableWS`, mirroring `EnableRPC`. Wire `wsConfig.DenyList = config.DenyList` in `NewEVMWebSocketServer` (`evmrpc/server.go`) so both transports share the same admission behavior for the methods they both register.

### Proof of Concept
1. Configure `app.toml` `[evm]` with `deny_list = ["eth_call"]` (or any `eth_*`/`net_*`/`web3_*` method registered on both transports) and start a node with both EVM HTTP and WS enabled.
2. Confirm the HTTP JSON-RPC endpoint fails fast on `eth_call` (per `srv.RegisterDenyList` behavior registered in `EnableRPC`).
3. Connect to the EVM WebSocket endpoint (default `ws://<host>:8546`) and send the same JSON-RPC request, e.g. `{"jsonrpc":"2.0","id":1,"method":"eth_call","params":[...]}`.
4. Observe the WS server executes the call successfully, because `EnableWS`/`WsConfig` never registered any deny list, demonstrating the bypass of the operator-configured restriction via transport selection.

func (h *HTTPServer) EnableWS(apis []rpc.API, config WsConfig) error {
	h.mu.Lock()
	defer h.mu.Unlock()

	if h.wsAllowed() {
		return fmt.Errorf("JSON-RPC over WebSocket is already enabled")
	}
	// Create RPC server and handler.
	srv := rpc.NewServer()
	srv.SetBatchLimits(config.batchItemLimit, config.batchResponseSizeLimit)
	readLimit := effectiveMaxRequestBodyBytes(config.readLimit)
	srv.SetReadLimits(readLimit)
	// maxConcurrentRequestBytes is passed through raw; rpc.Server.recomputeWSConcurrentBudget
	// raises it to readLimit when smaller, matching
	// newRequestSizeLimiter's max(budget, maxBody) rule on the HTTP protocol.
	srv.SetWSConcurrentRequestBytes(config.maxConcurrentRequestBytes)
	srv.SetWSAdmissionTimeout(config.wsAdmissionTimeout)
	srv.SetWSAdmissionEventHook(func(reason string) {
		// Hook carries no request context, and the fork's own connCtx is context.Background() too.
		recordWSAdmissionRejected(context.Background(), reason)
	})
	logger.Info("Registering apis for evm websocket")
	if err := RegisterApis(apis, config.Modules, srv); err != nil {
		return err
	}
	h.WsConfig = config
	h.wsHandler.Store(&rpcHandler{
		Handler: NewWSHandlerStack(srv.WebsocketHandler(config.Origins), config.JwtSecret),
		server:  srv,
	})
	return nil
}
