## Title
Users may receive less than their computed WOM-conversion incentive with no minimum-received protection - (File: `wombat/ArbWomUp.sol`)

### Summary
`ArbWomUp.incentiveDeposit()` pays out a USDT incentive computed from a tiered reward schedule, but silently caps the payout to whatever USDT balance the contract currently holds, exactly like the `min(reserve(), amount)` pattern flagged in the referenced Vader finding. Callers cannot specify a minimum acceptable payout, so an ordinary user competing with other depositors for the same limited USDT pool can receive less than the reward their deposit should have earned, with no revert and no guaranteed path to recover the shortfall.

### Finding Description
`getRewardAmount()` computes the tier-based reward owed to a depositor and then clamps it to the contract's live USDT balance: [1](#0-0) 

`incentiveDeposit()` uses this clamped value directly as the amount transferred to the user, and — critically — increments `claimedReward[msg.sender]` only by the *actual* (possibly reduced) amount sent, not by the full amount that was owed for the WOM just deposited: [2](#0-1) 

Because `claimedReward` is only incremented by what was actually transferred, any shortfall (`usdtReward - usdtleft`) is not tracked as an explicit "pending" balance the user can later claim on demand — it can only ever be recovered if that same user calls `incentiveDeposit()` again with a nonzero WOM amount in the future (the `_checkAmount` modifier reverts on a zero deposit, so there is no separate "claim outstanding incentive" entry point). If the USDT incentive pool is simply undersized relative to total tiered demand (a normal, non-malicious operational condition — no privileged action is required), later depositors racing for the same finite USDT balance receive less reward than their WOM deposit should entitle them to, and have no way to enforce a minimum acceptable payout or to guarantee recovery of the difference.

This mirrors the reported root cause precisely: `usdtReward > usdtleft ? usdtleft : usdtReward` is the same construction as `VaderReserve`'s `_min(reserve(), amount)`, and just like the router in the original report, `incentiveDeposit()` exposes no `minRec`/`minAmountOut` parameter to let the caller protect themselves.

### Impact Explanation
Ordinary users depositing WOM through `incentiveDeposit()` can receive a USDT incentive smaller than what the tier schedule promises for their deposit, with the deficit not guaranteed to ever be paid (it depends on the same user making a further deposit while the contract happens to be refunded with more USDT). This is a loss/freezing of the incentive yield the user was entitled to at the time of an ordinary, unprivileged transaction — no admin action or governance change is needed to trigger it, only a normal case of two depositors converting WOM in the same or nearby blocks against a limited USDT balance.

### Likelihood Explanation
This requires no privileged role, oracle manipulation, or admin misbehavior — it only requires that the fixed USDT incentive balance be insufficient to cover the tiered reward for all deposits made against it, which is a realistic and likely operational state as the incentive program is used over time (the balance is monotonically decreasing and only reduced, never automatically replenished by the contract logic itself).

### Recommendation
Add a `minAmountOut`/`minUsdtReward` parameter to `incentiveDeposit()` and revert if `rewardToSend` would be less than the caller's specified minimum, mirroring the recommendation in the referenced report. Alternatively, track the full entitled-but-unpaid reward separately from `claimedReward` (as an explicit "pending" balance) and expose a dedicated function allowing users to claim outstanding incentive independent of making a new deposit, so the shortfall is not silently deferred indefinitely.

### Proof of Concept
1. Contract holds 100 USDT and reward tiers are configured such that depositing 1000 WOM earns 150 USDT.
2. User A calls `incentiveDeposit(1000e18)`. `getRewardAmount` computes `usdtReward = 150e18`, but `usdtleft = 100e18`, so `rewardToSend = 100e18`.
3. `claimedReward[A] += 100e18` (not `150e18`), and A receives only `100e18` USDT despite depositing WOM that should earn `150e18`.
4. The contract's USDT balance is now `0`; A has no way to recover the missing `50e18` unless they deposit additional WOM later at a time the contract happens to hold more USDT — there is no direct claim function and no minimum-received check to have reverted the underpaying transaction in step 2. [3](#0-2)

    function incentiveDeposit(
        uint256 _amount
    ) external _checkAmount(_amount) whenNotPaused nonReentrant {
        uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender);
        _deposit(_amount);

    function getRewardAmount(uint256 _amount, address _account) external view returns (uint256) {
        if (_amount == 0 || rewardMultiplier.length == 0) return 0;
        uint256 accumulated = _amount + userWOMDeposited[_account];

        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accumulated > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }
        rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];

        uint256 usdtReward = (rewardAmount / DENOMINATOR) - claimedReward[_account];
        uint256 usdtleft = IERC20(usdt).balanceOf(address(this));

        return usdtReward > usdtleft ? usdtleft : usdtReward;
    }
