### Title
Panic on unvalidated participant indexes in PedPoP blame handling - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to CVE-2021-25214 (a malformed input that is accepted and later triggers a fatal assertion/termination when processed), `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept attacker-influenced `sender`/`recipient` participant indexes and feed them into `blame_internal`, which indexes `self.commitments[&sender]` unconditionally. An accusation naming a participant index not present in the commitments map (e.g. `> n`, or any index omitted from a partially populated map) causes a `HashMap` index panic, aborting the caller's process instead of returning an error. When a `proof` is supplied, `Decryption::decrypt_with_proof` additionally indexes `self.enc_keys[&decryptor]` with the same unvalidated accuser-controlled index.

### Finding Description
`blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609) is reachable through two public APIs:

- `BlameMachine::blame(sender, recipient, msg, proof)` (line 623)
- `AdditionalBlameMachine::blame(sender, recipient, msg, proof)` (line 674), constructible by any observer via `AdditionalBlameMachine::new` (line 649) from public commitment messages.

Inside `blame_internal`:

```rust
// crypto/dkg/pedpop/src/lib.rs:599
&self.commitments[&sender],
```

`sender` and `recipient` are never validated against `1 ..= n` nor against membership in `self.commitments` / `self.encryption.enc_keys`. `Participant::new` only rejects zero (crypto/dkg/src/lib.rs:29-35), so any `u16` up to `u16::MAX` is a well-formed `Participant`. A blame accusation delivered over the authenticated channel that names a nonexistent sender (e.g. index `n + 1`, or a participant whose commitments were never registered) drives `HashMap`'s `Index` impl to panic. Similarly, in `decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:388):

```rust
&[self.enc_keys[&decryptor], *proof.key],
```

an accusation carrying a valid `EncryptionKeyProof` but naming a `recipient`/`decryptor` outside the registered set panics on the `enc_keys` lookup.

Note the protocol already treats malformed-blame inputs as error paths elsewhere (`DecryptionError::InvalidSignature`, `DecryptionError::InvalidProof` at encryption.rs:332-338), so the panic is an inconsistency: some bad inputs return `Err`, others terminate the process.

### Impact Explanation
An unprivileged participant in the DKG (or any party able to submit a blame accusation naming sender/recipient indexes) can deterministically crash every node that evaluates the accusation. In a threshold-key ceremony this halts blame adjudication and key generation across all honest parties that process the message — a remote, input-triggered denial of service, matching the availability impact (CVSS A:H) of the BIND assertion-failure class. No secret material is leaked, but liveness of the signing group is broken by a single malformed accusation.

### Likelihood Explanation
Reachability requires only that a party broadcast (or relay) a blame accusation containing an out-of-range or unregistered `sender`/`recipient` index. Both `blame` entry points are public APIs taking `Participant` values deserialized from network messages; neither validates range. `AdditionalBlameMachine::new` is explicitly designed for use "regardless of if the caller was a member in the DKG protocol" (lib.rs:640-648), widening the set of callers that will evaluate attacker-chosen indexes. Likelihood is bounded by the fact that processing a blame message implies the ceremony is already aborting, limiting impact to DoS rather than consensus corruption — hence Medium rather than High.

### Recommendation
Validate `sender` and `recipient` before indexing:

- In `blame_internal`, return early (blaming the accuser or returning an explicit error) when `sender`/`recipient` are not present in `self.commitments`, e.g. `self.commitments.get(&sender)` with a defined fallback.
- In `Decryption::decrypt_with_proof`, replace `self.enc_keys[&decryptor]` with a checked lookup returning `DecryptionError::InvalidProof` on absence.
- Consider changing `blame` to return `Result<Participant, PedPoPError<C>>` so malformed accusations are surfaced as errors, consistent with the rest of the module's error handling.

### Proof of Concept
Conceptual (requires a DKG in progress or a completed `BlameMachine`):

```rust
// n = 3 participants; attacker submits a blame accusation naming participant 4
let sender = Participant::new(4).unwrap();   // never registered
let recipient = Participant::new(1).unwrap();
// `msg` is any EncryptedMessage<C, SecretShare<C::F>> whose PoP verifies,
// or fails verification - either path reaches the indexing when `proof` is used.
let (_, _faulty) = blame_machine.blame(sender, recipient, msg, Some(proof));
// panics at crypto/dkg/pedpop/src/lib.rs:599 -> self.commitments[&sender]
```

Alternatively, with `sender` valid and `recipient = Participant::new(4)` plus a well-formed `EncryptionKeyProof`, the panic occurs at crypto/dkg/pedpop/src/encryption.rs:388 on `self.enc_keys[&decryptor]`.
