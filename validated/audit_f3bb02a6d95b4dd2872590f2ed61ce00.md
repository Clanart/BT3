### Title
Unauthenticated oversized `ThresholdKeys` deserialization causes expensive participant-scale work - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` trusts the serialized `n` field before validating the threshold parameters or bounding the participant count. A public byte stream can declare `t = n = 65,535`, causing the parser to read and decode 65,535 scalar coefficients and 65,535 group elements, then perform approximately 65,535 scalar-point multiplications while constructing the group key. [1](#0-0) [2](#0-1) 

### Finding Description
The deserializer reads `t`, `n`, and participant `i` from attacker-controlled bytes, but defers `ThresholdParams::new` until after all variable-sized material has been consumed. [3](#0-2)  With interpolation byte `0`, it allocates and fills a vector of `n` scalars; it then reads `n` verification shares into a map. [4](#0-3)  `ThresholdKeys::new` accepts constant interpolation only when `t == n`, so setting both to `u16::MAX` reaches the group-key calculation over participants `1..=65,535`. [5](#0-4) 

### Impact Explanation
An unprivileged party that can supply bytes to `ThresholdKeys::read` can make a verifier or key-loading endpoint perform participant-scale field decoding, point decoding, hashing, allocation, and scalar multiplication from a single roughly 4 MiB input for 32-byte encodings. Repeated requests can monopolize CPU and memory bandwidth, producing a partial denial of service comparable to the reported vulnerability class. [4](#0-3) [6](#0-5) 

### Likelihood Explanation
The input needs no secret, signature, valid proof, existing key share, or malicious validator privileges; it only needs to be syntactically valid serialized `ThresholdKeys`. All coefficients can be the canonical encoding of one, all verification shares can be the canonical generator encoding, and `i = 1` satisfies participant validation. [7](#0-6) [1](#0-0) 

### Recommendation
Validate `t`, `n`, and `i` immediately after reading them, enforce a protocol-level maximum participant count before allocating or parsing variable-sized sections, and preferably deserialize against caller-supplied expected `ThresholdParams` rather than an embedded `n`. Reject constant-interpolation encodings whose coefficient count is not an explicitly bounded expected threshold. [8](#0-7) 

### Proof of Concept
For any in-scope `Ciphersuite` with canonical 32-byte scalar and compressed-point encodings, construct this byte stream:

```rust
let n: u16 = u16::MAX;
let mut bytes = Vec::new();

bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(n.to_le_bytes()); // t = 65,535
bytes.extend(n.to_le_bytes()); // n = 65,535
bytes.extend(1u16.to_le_bytes()); // i = Participant(1)
bytes.push(0); // Interpolation::Constant

for _ in 0..n {
  bytes.extend(C::F::ONE.to_repr().as_ref());
}
bytes.extend(C::F::ONE.to_repr().as_ref()); // secret_share

let generator = C::generator().to_bytes();
for _ in 0..n {
  bytes.extend(generator.as_ref());
}

let keys = ThresholdKeys::<C>::read(&mut bytes.as_slice()).unwrap();
```

This input satisfies `t == n` for constant interpolation and forces group-key construction to multiply and sum all 65,535 supplied verification shares. [5](#0-4)
