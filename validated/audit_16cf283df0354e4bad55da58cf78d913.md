### Title
`SchnorrAggregate::verify` accepts an empty signature aggregate as valid, letting a proof attest to deposits/claims backed by nothing - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external report describes a vault "depositing into itself" — minting units backed by value it already controls, inflating supply without new backing. The closest analog in Serai is in `SchnorrAggregate::verify` (`crypto/schnorr/src/aggregate.rs:127-146`): the verifier never requires `keys_and_challenges` (and hence `self.Rs`) to be non-empty. An aggregate with zero `Rs` and `s = 0` reduces to `multiexp_vartime(&[(-0, G)]) = identity`, so `verify` returns `true` for a statement bound to no keys, no challenges, and no nonces — a cryptographic claim of backing by nothing.

### Finding Description
`SchnorrAggregate::read` accepts a length-prefixed `Rs` vector of any size, including zero (`aggregate.rs:77-88`), and `s` is an arbitrary scalar from `read_F`. In `verify`:

```rust
// crypto/schnorr/src/aggregate.rs:127-146
pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
  if self.Rs.len() != keys_and_challenges.len() {
    return false;
  }
  // ... weights derived only from challenges ...
  pairs.push((-self.s, C::generator()));
  multiexp_vartime(&pairs).is_identity().into()
}
```

With `keys_and_challenges = []` and `Rs = []`, `pairs` is just `[(-s, generator)]`. Any attacker supplies `s = 0` (33 bytes: `len=0` + 32 zero bytes via `SchnorrAggregate::read`) and the multiexp is the identity → `verify` returns `true`. Unlike `SchnorrAggregator::complete`, which refuses empty input (`aggregate.rs:175-178`), `verify` has no such guard. This is the aggregate-signature analogue of "units minted with no deposit": the equation is satisfiable entirely from the verifier's own side, producing acceptance backed by no signature material. Any downstream caller that treats `aggregate.verify(dst, list)` as "`list` parties each produced a valid Schnorr signature" will honor a forgery whenever the attested list is attacker-influenceable to be empty or whenever the bytes `len=0 || 0x00*32` reach `read`.

### Impact Explanation
A forged "aggregate signature" that validates against zero public keys. If any Serai component (or integrator) verifies an aggregate over a validator/signer list that can resolve to empty — e.g., a set whose members were all removed, or a list derived from attacker-controlled bytes — the attacker gains acceptance of an authorization claim backed by no key material, paralleling the report's "units backed by tokens already controlled". Impact is bounded by where the `aggregate` feature is consumed; within this repo no in-scope caller was found invoking `SchnorrAggregate::verify` on attacker-controlled lists, which caps reachability.

### Likelihood Explanation
Triggering requires only untrusted bytes into `SchnorrAggregate::read` plus a `verify` call with a matching-length (empty) `keys_and_challenges` — fully within the "untrusted bytes fed to a read/verify API" reachability model. However, exploitation requires a real call site that derives `keys_and_challenges` in a way an attacker can empty, or that credits the verification result without checking the list was non-empty. No such call site is present in the indexed code, so likelihood is conditional on integrator usage — consistent with Medium rather than High.

### Recommendation
Reject vacuous verification: return `false` early in `SchnorrAggregate::verify` when `self.Rs.is_empty()` (equivalently, when `keys_and_challenges` is empty), mirroring `SchnorrAggregator::complete`'s `None` on empty input. Optionally also reject `s == 0` / identity `R` points, though the non-empty check is the minimal fix that restores the invariant "a passing verification attests at least one signature".

### Proof of Concept
```rust
// Attacker supplies these bytes to SchnorrAggregate::read:
//   [0x00,0x00,0x00,0x00]  (Rs len = 0)
//   [0x00; 32]             (s = 0)
let agg = SchnorrAggregate::<C>::read::<&[u8]>(
  &mut [0u8; 36].as_slice() // len=0, s=0 for a 32-byte scalar field
).unwrap();

// Any dst; keys_and_challenges must simply be empty
assert!(agg.verify(b"any-dst", &[])); // returns true with zero signatures
```
Root cause: `verify` performs only the `Rs.len() == keys_and_challenges.len()` length check (`aggregate.rs:128`) and then verifies `Σ z_i·R_i + z_i·c_i·P_i - s·G == 0`, which degenerates to `0·G == identity` for the empty case — acceptance with no cryptographic backing, the precise structural analog of value issued with no deposit.
