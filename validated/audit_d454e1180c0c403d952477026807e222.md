Based on the code evidence gathered, I found a solid on-chain analog to the M-13 pattern (loop over multiple items where a single "missing" item makes the whole batch revert, denying settlement to items that were fine).

### Title
`_withdraw()` reverts and locks all escrowed tokens in a withdrawal batch when any single token entry has already been fully released — (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` iterates over `body.tokens[]` (an order's full input-token list) and, for every entry whose escrow has already reached zero, unconditionally reverts with `UnknownOrder()` rather than skipping that entry: [1](#0-0) . This is the same defect class as the M-13 report: a loop over N independent balance components where one component being "empty" (zero reward token / zero remaining escrow) aborts settlement for every other component in the same call, even though those other components still hold real, releasable funds.

### Finding Description
`_withdraw` is the internal settlement primitive used by both cross-chain `RedeemEscrow`/`RefundEscrow` message handling (`onAccept`) and the same-chain cancel/fill paths in `IntentGatewayV2`. It takes a `WithdrawalRequest.tokens` array (normally `order.inputs`, the full set of input tokens escrowed at order placement) and, for each token:

```solidity
for (uint256 i; i < len; i++) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (amount == 0) continue;

    uint256 escrowed = _orders[body.commitment][token];
    if (escrowed == 0) revert UnknownOrder();   // <-- aborts the ENTIRE batch

    _orders[body.commitment][token] = escrowed - amount;
    ...
}
``` [1](#0-0) 

For same-chain orders, `_orders[commitment][token]` is decremented incrementally by partial fills, proportionally per output pair: "solvers can fill any portion of the output... the proportional share of escrowed inputs is released immediately" [2](#0-1) . Because partial fills can be driven independently per output-token pair ("Surplus only applies on the first fill of each output token pair" [3](#0-2) ), it is possible for one of an order's several input tokens to reach `_orders[commitment][token] == 0` (fully drained by earlier partial fills) while a sibling input token in the same order still holds a positive escrowed balance.

Any subsequent call that finalizes the order — a full fill, a same-chain cancel, or a `RefundEscrow`/`RedeemEscrow` cross-chain message — reconstructs `body.tokens` from the order's original `inputs` list (see `cancelOrder`/`withdraw(body, true)` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, lines 519–530, which builds `body.tokens = order.inputs` unconditionally) [4](#0-3) . Because that finalize call still requests the original non-zero `amount` for the already-drained token, `_withdraw` hits `escrowed == 0` for that one token and reverts `UnknownOrder()` for the whole call — including the transfer of every other input token that still has a real, non-zero escrowed balance.

### Impact Explanation
The result is a locked-funds condition: once any single input token of a multi-input order is fully drained by partial fills, the order can no longer be finalized (fully filled, cancelled, or refunded) through the normal `_withdraw` path, because the batch call for the *entire* set of original input amounts will always revert on the already-zeroed token. The remaining escrowed balance of the other, still-funded input tokens becomes permanently stuck in the gateway contract with no code path that releases it — this is a genuine "loss/lock of funds" impact matching the bounty's accepted class (funds move exactly once and only to the rightful beneficiary — here they never move at all for the surviving tokens).

### Likelihood Explanation
This is reachable without any privileged actor, malicious relayer, or malicious node: any order with two or more input tokens that undergoes independent per-output-pair partial fills (an explicitly documented, user-facing feature) can end up in this state purely through normal solver/user interaction with `fillOrder`. No proof forgery or relayer collusion is required — the bug triggers purely from the order-management arithmetic in `_withdraw`/`_orders`.

### Recommendation
In `_withdraw`, skip token entries whose remaining escrow has already reached zero (analogous to the suggested M-13 fix of `continue`-ing past a zero reward token) instead of reverting the entire batch:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) continue;   // already released by a prior partial fill
uint256 toRelease = amount > escrowed ? escrowed : amount;
_orders[body.commitment][token] = escrowed - toRelease;
```
This preserves release of the remaining, correctly-escrowed tokens instead of allowing one drained token to block settlement of the whole order.

### Proof of Concept
1. User places a cross-chain (or same-chain) order with two input tokens: `TokenA` (100 units) and `TokenB` (100 units), escrowed via `placeOrder`.
2. A solver performs a partial fill against the output pair that is proportionally tied to `TokenA`, fully draining `TokenA`'s escrow (`_orders[commitment][TokenA] == 0`) while `TokenB` still has 100 units escrowed (`_orders[commitment][TokenB] == 100`).
3. The order owner later calls `cancelOrder` (same-chain) or the cross-chain settlement message triggers `onAccept` → `withdraw(body, true)`, where `body.tokens = order.inputs = [TokenA:100, TokenB:100]` [5](#0-4) .
4. `_withdraw` iterates: for `TokenA`, `escrowed == 0` → `revert UnknownOrder()` [6](#0-5) , aborting before `TokenB`'s transfer is ever reached.
5. The order can never be cancelled, filled, or refunded through this contract again — `TokenB`'s 100 units remain permanently locked in the gateway.
