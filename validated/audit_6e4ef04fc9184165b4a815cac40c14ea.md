Audit Report

## Title
Exact-stake-equal-to-threshold vote never marked as "reached threshold" in `VoteStakeTracker::add_vote_pubkey` - ([File: core/src/consensus/vote_stake_tracker.rs])

## Summary
`add_vote_pubkey` computes `threshold_stake = (total_stake as f64 * threshold) as u64` and reports a threshold as newly reached only when `old_stake <= threshold_stake && threshold_stake < new_stake`. When a vote brings `new_stake` to a value exactly equal to `threshold_stake`, the strict `<` comparison evaluates false, so the threshold is never reported as reached for that vote, even though the cumulative stake numerically satisfies "≥ threshold."

## Finding Description
The threshold-crossing check in `add_vote_pubkey` [1](#0-0)  uses `threshold_stake < new_stake` rather than `threshold_stake <= new_stake`. If the sum of stakes voting for a given `(slot, hash)` lands exactly on `threshold_stake`, that specific vote does not set the corresponding entry in `reached_threshold_results` to `true`. Only a strictly later vote that pushes `new_stake` above `threshold_stake` would trigger it; if no further vote for that exact hash arrives (e.g., remaining stake votes for a competing hash on the same slot), the threshold crossing is permanently missed for that hash. This function backs `ClusterInfoVoteListener::add_optimistic_vote` and `track_optimistic_confirmation_vote`, which check `DUPLICATE_THRESHOLD` and `VOTE_THRESHOLD_SIZE` and drive `duplicate_confirmed_slot_sender` and `BankNotification::OptimisticallyConfirmed` [2](#0-1) . There is no existing guard that treats an exact-equal boundary as reached; the existing unit test `test_add_vote_pubkey` [3](#0-2)  only exercises the strictly-greater-than crossing case (`i == 6`, `new_stake=7 > threshold_stake=6`), leaving the exact-equal case untested and unhandled.

## Impact Explanation
A missed threshold-reached signal for the boundary-equal case can delay or suppress duplicate-confirmation (`duplicate_confirmed_slot_sender`) and optimistic-confirmation (`BankNotification::OptimisticallyConfirmed`) notifications for a specific `(slot, hash)` pair, even though the required stake percentage has numerically been met. This is a real correctness defect in the vote-tracking boundary logic, affecting consensus-adjacent signaling paths in `core/src/cluster_info_vote_listener.rs`.

## Likelihood Explanation
Triggering the bug requires the cumulative voting stake for one specific `(slot, hash)` to land exactly on the integer-truncated `threshold_stake` value, and no subsequent vote pushing it strictly above ever arrives for that hash. This is possible under naturally occurring, non-adversarial stake distributions and requires no malicious or privileged actor, but it is a narrow coincidence-dependent condition rather than a guaranteed or easily attacker-controlled trigger, and its practical downstream consensus consequence (whether the fork/hash confirmation signal can be independently re-derived via a later vote or an alternate path) was not fully traced in the available code.

## Recommendation
Change the comparison to treat a stake landing exactly on `threshold_stake` as reaching the threshold, e.g. use `old_stake <= threshold_stake && threshold_stake <= new_stake` while ensuring the crossing is only reported once (guard on `old_stake < threshold_stake + 1` or equivalent), so a vote that brings `new_stake == threshold_stake` is correctly reported as newly reached.

## Proof of Concept
1. Set `total_stake = 100`, threshold `= 0.10`, giving `threshold_stake = 10`.
2. A single voter with `stake = 10` casts the first vote for `(slot, hash)`: `old_stake = 0`, `new_stake = 10`.
3. Evaluate `old_stake <= threshold_stake && threshold_stake < new_stake` → `0 <= 10 && 10 < 10` → `false`; the threshold is not reported reached despite `new_stake == threshold_stake`.
4. If no further vote for that exact hash arrives, the corresponding duplicate/optimistic-confirmation notification for this hash is never emitted, verifiable by extending `test_add_vote_pubkey` [3](#0-2)  with a case where `new_stake` is engineered to equal `threshold_stake` exactly.
