### Title
Auction `bidPool.running` flag conflates bid admission with bid execution, causing already-accepted winning bids to be silently dropped - ([File: kaiax/auction/impl/builder.go], [File: kaiax/auction/impl/execution.go])

### Summary
The `bidPool.running` flag in the Kaia auction (KIP-249) module is used both to gate admission of *new* bids in `AddBid` and to gate *extraction/execution* of bids that have already been validated and accepted into the bid pool via `ExtractTxBundles`. This mirrors the reported MarginDex pattern where `is_accepting_new_orders`, meant only to control new-order admission, is incorrectly reused to block execution of already-accepted orders.

### Finding Description
`BidPool.AddBid` correctly rejects new bid submissions while the pool is not running: [1](#0-0) 

However, the same `running` flag is reused inside `ExtractTxBundles`, the function responsible for pulling an already-admitted, already-validated winning bid into the block being built and generating the settlement bundle (`[BidTx]`) that must execute immediately after its target transaction: [2](#0-1) 

`FilterTxs` similarly short-circuits on the same flag: [3](#0-2) 

The `running` flag itself is toggled off transiently in `PostInsertBlock`, independent of whether bids are already accepted and waiting to execute at the very next block: it is cleared whenever the downloader is synchronizing, the Randao fork condition check fails, or `updateAuctionInfo` cannot resolve the auctioneer/entry-point/gas-buffer from the `SystemRegistry` for that block (e.g., a transient state read failure): [4](#0-3) 

Because a bid's validity window is only `[currentBlockNumber+1, currentBlockNumber+allowFutureBlock]` (`allowFutureBlock = 2`) as documented, and because `ExtractTxBundles` is invoked per candidate block during block building, a single block in which `running` is momentarily `0` means the winning, already-validated bid for that block is skipped entirely (no bundle is generated, so it is never mined). Since block building is a one-shot process (a missed block cannot be retroactively re-mined for that height), the bid is effectively lost/forfeited even though it was already accepted, signed by the `Auctioneer`, and stored in the bid pool. The stale bid is then purged in the subsequent `removeOldBids` cleanup once the target block height has passed, with no fallback resubmission.

### Impact Explanation
This breaks the intended guarantee of the auction system: a winning bid, once admitted to the pool with a valid `Auctioneer` signature and a bid amount, is supposed to be executed atomically after its target transaction at the specified block. A transient toggle of the admission-only `running` flag (triggered by node sync state or a one-block registry read hiccup, both outside the searcher's/auctioneer's control) can cause legitimate, already-paid-for settlement to be skipped for that block height, denying the auction outcome (reward redirection / lost settlement) without any compensating mechanism, and diverging the auction's execution guarantee between a proposer that happens to have `running=0` for that single block versus one that doesn't — a form of state/behavior divergence across otherwise-honest block producers for the same target block.

### Likelihood Explanation
Medium likelihood: this does not require a malicious actor — it can occur naturally whenever `PostInsertBlock` observes `Downloader.Synchronising()==true` for one block or a transient failure in reading `SystemRegistry`/`AuctionEntryPoint` state at a given block height, both of which are outside adversarial control but plausible in normal operation (e.g., brief resync, minor RPC/backend hiccups). Because `ExtractTxBundles` and `FilterTxs` both gate on the same flag meant only for admission, any such single-block blip silently drops execution of an already-accepted bid rather than merely blocking new admissions, exactly matching the reported bug class.

### Recommendation
Decouple the "accepting new bids" concept from the "eligible for execution/extraction" concept, analogous to the recommended fix in the source report (adding a distinct pause check rather than reusing the same guard for two different operations):
- Keep the `running` check in `AddBid` (admission gating) only.
- In `ExtractTxBundles`/`FilterTxs`, do not gate on `running`; instead rely on the bid's own validity window (`bid.BlockNumber` vs. current mining block) so that already-accepted bids are still honored for execution even if `running` is momentarily toggled off for unrelated reasons (sync state, registry read hiccups). If a genuine execution-blocking pause is required, introduce a separate explicit flag for that purpose distinct from the new-bid-admission flag.

### Proof of Concept
1. Auctioneer submits a valid, signed winning bid via `auction_submitBid` targeting `blockNumber = N`, which is admitted while `bidPool.running == 1` (passes `AddBid` in `bid_pool.go`). [5](#0-4) 
2. Before block `N` is mined by this node, `PostInsertBlock` runs for block `N-1` and one of `Downloader.Synchronising()`, the Randao-fork check, or `updateAuctionInfo` returns a state that clears `running` to `0`: [4](#0-3) 
3. When building block `N`, `ExtractTxBundles` observes `running == 0` and returns an empty bundle list, so the bid's settlement transaction is never generated/included, even though `bid.BlockNumber == N` is exactly within its valid window and the bid was already accepted: [2](#0-1) 
4. After block `N` is mined without the bid's settlement, the bid's target block has passed and it becomes stale, to be purged by `removeOldBids` — the already-accepted, paid bid never executes despite having been validly admitted.

```go
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
```

```go
	if a.Downloader.Synchronising() || !a.ChainConfig.IsRandaoForkEnabled(block.Number()) {
		atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)
		return nil
	}

		logger.Debug("stop auction since auctioneer or auction entry point is not set")

	}
```
