### Title
Missing zero-value validation for `kip71.gastarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: `params/kip71_config.go`)

### Summary
The governance parameter `Kip71GasTarget` (`kip71.gastarget`) is registered with a `noopFormatChecker`, meaning any `uint64` value including `0` is accepted as valid. This value is later used directly as a divisor in `KIP71Config.NextMagmaBlockBaseFee`. If the parameter is set to `0` via governance and a block is produced with nonzero gas usage, every node computing/verifying the next block's `baseFee` performs a `big.Int` division by zero, which panics in Go.

### Finding Description
`Kip71GasTarget` is defined with no format validation: [1](#0-0) 

This is inconsistent with the sibling parameter `Kip71BaseFeeDenominator`, which explicitly rejects zero: [2](#0-1) 

The accepted `GasTarget` value flows unvalidated into `ParamSet` and then into `KIP71Config`: [3](#0-2) 

In `NextMagmaBlockBaseFee`, `gasTarget := kc.GasTarget` is used as a divisor with no zero-check (unlike `BaseFeeDenominator`, which has an explicit `if kc.BaseFeeDenominator == 0 { ... }` fallback just above it): [4](#0-3) 

Specifically, if `parentGasUsed != gasTarget` (true whenever `gasTarget == 0` and any gas was used), the code computes:
```
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))  // division by zero when gasTarget == 0
```
Go's `big.Int.Div` panics on division by zero (there is no UB as in C, but the effect is the same class of bug as the iccDEV division-by-zero: an unchecked divisor reaching a `Div` operation). This function is invoked from `VerifyMagmaHeader`, which is called during header verification for every block after the Magma hardfork — a mandatory, unconditional consensus path executed by every node (miners and full nodes alike) on every new block.

### Impact Explanation
Because `NextMagmaBlockBaseFee`/`VerifyMagmaHeader` executes on the block-processing path of every node, a panic here is not a localized failure — it crashes/halts every node that processes the next block once `gastarget` is set to `0` (assuming nonzero gas usage in the parent block, which is the common case). This satisfies the "acceptance of an invalid transaction/block" and "state divergence between honest nodes" criteria indirectly by way of a chain-wide processing halt/crash triggered through a single governance parameter change — a network-wide denial of service reachable through the standard governance parameter-setting mechanism (not a P2P/validator-only mechanism, but the same governance-parameter path already listed as in-scope). This is a Medium-severity, consensus/liveness-impacting bug, analogous in root cause (unchecked divisor value flowing to a division operation, as in the iccDEV TIFF advisory) even though the underlying language-level failure mode differs (Go runtime panic vs. C UB).

### Likelihood Explanation
Triggering this requires that governance actually sets `kip71.gastarget` to `0`. This is a legitimate, in-scope governance action (the report's rules explicitly list "governance parameters" as an allowed reachable-path category), and the code provides no defense against it — contrasted with the neighboring `BaseFeeDenominator`, which is explicitly hardened against the same zero-value case. This strongly suggests the missing check is an oversight rather than an intentional design choice, and any governance body (or malicious/compromised governing node under `governancemode=single`) can trigger it with a single parameter vote.

### Recommendation
Add a zero-value rejection to `Kip71GasTarget`'s `FormatChecker` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check) in `kaiax/gov/param.go`, and/or add a defensive fallback in `NextMagmaBlockBaseFee` in `params/kip71_config.go` (similar to the existing `BaseFeeDenominator == 0` fallback) to avoid dividing by a zero `gasTarget`.

### Proof of Concept
1. Via governance (e.g. `governancemode=single` with a governing node, or a passed governance vote), set `kip71.gastarget = 0`.
2. Once the vote is applied (per `GetParamSet` for the next block), produce/receive a block after the Magma hardfork whose parent block has nonzero `GasUsed` (the normal case).
3. Every node calls `KIP71Config.VerifyMagmaHeader` → `NextMagmaBlockBaseFee` while validating/building the following header: [5](#0-4) 
4. Inside `NextMagmaBlockBaseFee`, since `parentGasUsed (>0) != gasTarget (0)`, the "gas used above target" branch executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, causing a runtime panic on every node processing this header, halting the chain.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
