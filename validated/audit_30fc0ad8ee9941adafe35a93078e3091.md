### Title
Stale index-based partial-commit selection can silently commit unintended lines when the working file changes between diff load and commit - (File: `app/src/lib/stores/app-store.ts`, `app/src/models/diff/diff-selection.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
`DiffSelection` records which lines a user wants to stage/commit purely as a set of **positional integer indices** into the flattened diff-hunk lines (`hunk.unifiedDiffStart + lineIndex`), not by line content. When the diff is reloaded because the on-disk file changed (external edit, formatter, git hook, `checkout`/`pull` racing with the UI, or content supplied by a hostile clone/fetch/remote), the app only *prunes* indices that are no longer selectable — it does not re-anchor them to the same textual content. `formatPatch()`/`applyPatchToIndex()` then blindly reuses these indices against the freshly-fetched diff to build the `git apply --cached` patch that becomes the actual commit. This mirrors the `only-boost` `rebalance()` flaw: a value (the "optimal" line selection) computed against one state is applied unchanged against a materially different state, producing silent corruption instead of the intended, user-reviewed result.

### Finding Description
`DiffSelection.isSelected(lineIndex)` and `withSelectableLines()` operate purely on numeric offsets: [1](#0-0) [2](#0-1) 

When the working-directory diff for the currently selected file is reloaded, `updateChangesWorkingDirectoryDiff()` explicitly acknowledges that the diff "might have changed dramatically" but only removes indices that no longer map to an includable line — it does **not** validate that a surviving index still points at the same textual change: [3](#0-2) 

At commit time, `stageFiles()` → `applyPatchToIndex()` re-fetches the diff from disk fresh (`getWorkingDirectoryDiff`) and builds the patch from the file's *current* selection object against that *new* diff via `formatPatch()`, using the same `absoluteIndex = hunk.unifiedDiffStart + lineIndex` scheme: [4](#0-3) [5](#0-4) 

Because hunk boundaries and `unifiedDiffStart` offsets are recomputed from scratch on every diff parse, a file mutation that shifts, splits, or reorders hunks (adding/removing a line above a hunk, a line-ending change, whitespace-driven hunk merges, etc.) can leave old indices numerically valid but semantically pointing at entirely different lines in the new diff. The reconciliation logic in `app-store.ts` only guards against indices becoming *out of range or non-includable*; it has no notion of "this content moved." The same unguarded index-reuse also occurs in `discardChangesFromSelection`/`formatPatchToDiscardChanges`, which uses `selection.isSelected(absoluteIndex)` against a diff object passed in from a possibly different point in time than the one the selection was built against: [6](#0-5) [7](#0-6) 

The root cause is structurally identical to the `only-boost` bug: a decision (line selection / optimal deposit) is computed under an assumption of a stable base state, then a large state change occurs (file rewritten / all funds withdrawn), and the stale decision is applied to the new, materially different state without recomputation or content-based validation.

### Impact Explanation
If exploited, a user could stage/commit (or discard) different lines than the ones they visually selected and reviewed in the diff viewer — i.e., **silent corruption of what the user commits or pushes**, one of the explicitly valid impact classes. This is worse than a normal race because Desktop's own partial-commit UI is the mechanism that is supposed to give users fine-grained, auditable control; a mismatch here defeats that guarantee without any error or warning, and the corrupted commit is what gets pushed to the remote and reviewed by others.

### Likelihood Explanation
The attacker primitive required is exactly one of the accepted classes: control over the content of a cloned/fetched repository (e.g., a repo shipping a `post-checkout`/`post-merge` hook, `.gitattributes`-driven filters, or CI/build tooling the project instructs contributors to run) that rewrites tracked files shortly after the user opens the diff and starts selecting lines, but before they click "Commit." Desktop already live-refreshes diffs on filesystem change events during normal partial-selection workflows, so the reconciliation path in `updateChangesWorkingDirectoryDiff` is reached routinely, not only in edge cases — the guard exists specifically because this scenario is expected to happen, but the guard does not fully solve the described corruption because it is index-based, not content-based.

### Recommendation
Anchor the diff selection to line content/hash (or old/new file-line numbers from the hunk header) instead of flattened positional indices, or, when a diff reload detects that hunks have shifted/changed shape, re-map or invalidate the entire selection for the affected hunk(s) rather than pruning individual indices. At minimum, before generating the commit patch, re-diff the file and compare it against the diff the user last visually reviewed; if it differs materially, force the user to re-review/re-select rather than silently reusing the old `DiffSelection`.

### Proof of Concept
1. Modify a tracked file so it has several separate hunks; open it in Desktop's Changes view and select only specific added lines in the middle hunk for a partial commit (leave rest unselected).
2. Before clicking "Commit", have an external process (e.g., a `post-checkout`/format-on-save tool, or simply another terminal) insert/remove a line above that hunk in the same file, which shifts `unifiedDiffStart` for subsequent hunks without changing the total count of includable lines in a way the pruning logic would flag.
3. Desktop's live-refresh calls `updateChangesWorkingDirectoryDiff`, which keeps the previously diverging indices (since they still map to includable lines in the new diff) — `app/src/lib/stores/app-store.ts:3478-3497`.
4. Click "Commit". `applyPatchToIndex` re-diffs and `formatPatch` applies the stale indices to the new hunk layout — `app/src/lib/git/apply.ts:60-81`, `app/src/lib/patch-formatter.ts:143-171` — producing a patch that stages/commits lines the user never selected (or omits lines they did select), with no warning shown.

Note: I was not able to execute this scenario end-to-end (no filesystem/terminal access in this environment) to confirm the exact hunk-shift conditions that defeat the pruning check; this should be validated with a live Desktop instance and a crafted repo/hook before treating it as confirmed.

      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {

        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`

    }

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection

  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.

  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
