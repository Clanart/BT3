## Title
Webhook HMAC verification validates payload integrity but does not bind the `X-Shopify-Shop-Domain` header, allowing forged shop attribution on replayed/self-generated webhooks - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
This is the same bug class as the reported `V3Vault.sol` finding: a cryptographic signature is verified for authenticity, but a security-critical field used downstream for authorization/attribution is never checked against the signed content. In `V3Vault.sol`, `permit2.permitTransferFrom()` verified the Permit2 signature but never checked `permit.permitted.token == asset`, letting an attacker supply an arbitrary token while the vault treated it as USDC. In `shopify_app`, `ShopifyApp::WebhookVerification#hmac_valid?` verifies the HMAC over `request.raw_post` only, and `shop_domain` is read straight from the unsigned `X-Shopify-Shop-Domain` header, with no binding between the two.

### Finding Description
`ShopifyApp::PayloadVerification#hmac_valid?` computes/compares HMAC-SHA256 solely over `request.raw_post`: [1](#0-0) 

`ShopifyApp::WebhookVerification` uses this same check as its only `before_action`, and separately exposes `shop_domain`, which is read directly from the `X-Shopify-Shop-Domain` request header — a value that is never included in the HMAC computation: [2](#0-1) 

The gem's own documentation instructs developers to build custom webhook controllers exactly this way — trusting `shop_domain` (header-derived) alongside the HMAC-"verified" body to dispatch background jobs that act on shop data: [3](#0-2) 

The generated declarative-webhook controller template exhibits the identical pattern, passing the header-derived `webhook_request.shop` into `perform_later` alongside the HMAC-checked body: [4](#0-3) 

Because the HMAC only proves "this body byte-stream was signed with the app's shared secret" and says nothing about which shop the header claims to be, an attacker who can obtain any one valid `(raw_post, hmac)` pair — trivially available since the attacker can install the (typically free-to-install) app on their own shop and trigger a webhook containing attacker-influenced content (e.g. an order note, product title, cart line item, or any other value included in the payload) — can replay that exact body/HMAC pair to the webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `verify_request` still passes because the body is untouched, so `head(:unauthorized)` is never triggered: [5](#0-4) 

The endpoint is unauthenticated by design (`skip_before_action :verify_authenticity_token`), so this is reachable by any anonymous/unrelated-merchant HTTP request that also knows one legitimately-signed body: [6](#0-5) 

This directly mirrors the report's root cause: `TokenPermissions.token` was signed and cryptographically valid, but never checked against the expected value (`asset`/USDC) before being trusted for a security decision. Here, the HMAC is valid for the body, but `shop_domain` — the value actually used to decide *whose* data the job acts on — is never checked against anything the signature covers.

### Impact Explanation
An attacker can cause the app's background jobs to execute with an attacker-chosen `shop_domain` (any victim's `myshopify.com` domain) paired with attacker-controlled webhook body content. Depending on which job/topic is abused, this enables cross-shop data corruption/injection (e.g., writing fabricated order/product/cart data attributed to a victim shop) or, for the mandatory privacy topics (`customers/data_request`, `customers/redact`, `shop/redact`), triggering data-redaction workflows against a shop the attacker does not operate — a concrete cross-shop impact analogous to "stealing" the victim's data context in the original report.

### Likelihood Explanation
Reachable by any unprivileged actor with their own (even free/trial) app installation to obtain one valid signed body, then a single unauthenticated POST with a modified header to the public webhook endpoint. No secret leakage or host-operator access is required — only knowledge of a single legitimately-delivered webhook body/HMAC pair, which any merchant using the app naturally receives.

### Recommendation
Bind the shop identity to the signed payload before trusting it:
- Verify that `shop_domain` from the header matches the shop encoded in the parsed webhook body (where the topic/body includes shop-identifying data), or
- Prefer using `ShopifyAPI::Webhooks::Registry.process`/`ShopifyAPI::Webhooks::Request` end-to-end (which is designed to validate topic/shop together) instead of manually trusting the header value in custom controllers, and update the documented custom-controller pattern and the `add_declarative_webhook` generator template to not treat the header-derived `shop`/`shop_domain` as authoritative without cross-checking it against the verified request context.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook whose body content is attacker-influenced (e.g. update a product title to an attacker-chosen payload, triggering `products/update`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends.
3. Replay the exact same POST body and HMAC header to the app's webhook endpoint (e.g. `/webhooks/products_update`), but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which passes because the body/HMAC pair is genuinely valid.
5. The controller/job (per the documented pattern in `docs/shopify_app/webhooks.md` and the generator template) calls `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)` using the forged `victim.myshopify.com` value, causing the job to process attacker-controlled webhook content under the victim shop's identity.

      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|

# frozen_string_literal: true

module ShopifyApp
  module WebhookVerification
    extend ActiveSupport::Concern
    include ShopifyApp::PayloadVerification

    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_request
    end

    private

    def verify_request
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end

    def shop_domain
      request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]
    end
  end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
