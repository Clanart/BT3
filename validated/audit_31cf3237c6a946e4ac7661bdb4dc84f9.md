### Title
`ThresholdKeys::new`/`read` accept arbitrary verification shares, deriving an attacker-controlled or unspendable `group_key` - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the Derive report (arbitrary manager address accepted at account setup → deposited funds stuck or unspendable), `ThresholdKeys::new` accepts a caller/deserializer-supplied `verification_shares` map and computes `group_key()` purely as a linear combination of those unchecked points. It never verifies that the local `secret_share` corresponds to `verification_shares[i]`, nor that the shares lie on a common polynomial. An unprivileged party who can feed crafted bytes to `ThresholdKeys::read` (explicitly a public-input surface) obtains a `ThresholdKeys` whose `group_key()` is either attacker-known or unspendable.

### Finding Description
`ThresholdKeys::new` performs only two validations on `verification_shares`: count equals `n` and all participant indexes `<= n` [1](#0-0) . It then derives the group key as `Σ_{i=1..=t} V_i * interpolation_factor(i)` directly from the supplied points [2](#0-1) . There is no check that `C::generator() * secret_share == verification_shares[i]`, and no pairwise consistency check across the shares.

`ThresholdKeys::read` reconstructs `t, n, i`, the interpolation, the secret share, and `n` arbitrary curve points via `C::read_G`, then calls `ThresholdKeys::new` [3](#0-2) . Any downstream consumer that uses `keys.group_key()` as a deposit address (e.g., `Scanner::new(keys.group_key())`, `Bitcoin::tweak_keys`/`scanner(key)` which registers deposit offsets under `group_key()`) will report funds as received against this key [4](#0-3) .

Two failure modes result:

1. **Attacker-controlled deposit key.** Set every `V_i = G * a_i` with attacker-known `a_i`. The group secret is `Σ L_i a_i`, known to the attacker, while the victim's `secret_share` is unrelated. Funds sent to `group_key()` are spendable by the attacker alone.
2. **Locked funds.** With honest-looking but inconsistent shares, FROST `complete()` fails aggregate `verify`, falls into per-share `verify_share` blame, and the honest holder's share may verify while the group signature can never be produced — matching the Derive report's "assets stuck because risk checks revert / unspendable" outcome. Serai itself notes this reachable state: "The only known way to cause this... is to deserialize a semantically invalid FrostKeys" [5](#0-4) .

### Impact Explanation
High. Any flow that deserializes `ThresholdKeys` from storage/peer input and derives a receive address from `group_key()` either (a) loses all deposited funds to the supplier of the blob (they hold the group secret), or (b) permanently locks the funds since no threshold coalition can produce a signature matching `group_key()` — the interpolated secret shares don't reconstruct it. This mirrors the external report's "assets stuck, unliquidatable" class with the added theft variant.

### Likelihood Explanation
Medium. Exploitation requires an integrator to deserialize attacker-influenced `ThresholdKeys` bytes (backup/restore, peer-synced key blobs, DB corruption boundary) and then treat `group_key()` as authoritative. The reachability surface (`ThresholdKeys::read` on untrusted bytes) is explicitly in scope; no malformed curve encoding is needed — the points are canonical and `read`/`new` succeed.

### Recommendation
In `ThresholdKeys::new`, verify self-consistency: check `C::generator() * secret_share == verification_shares[&params.i()]` and, ideally, that the shares form a coherent set (e.g., verify the `t`-of-`n` Lagrange reconstruction against a committed polynomial/commitment, or at minimum that a signature share produced under `view` verifies against `verification_share(i)`). Since full polynomial consistency isn't checkable from shares alone, also document/encode a `group_key` commitment in `write`/`read` so the deserialized key must match the key all signers agreed on at DKG time.

### Proof of Concept
```rust
// Attacker crafts a ThresholdKeys blob for C (e.g., Secp256k1):
// t = 2, n = 3, i = 1, Interpolation::Lagrange, secret_share = random s
// verification_shares = {1: G*a1, 2: G*a2, 3: G*a3} with known a1,a2,a3
let keys = ThresholdKeys::<Secp256k1>::read(&mut blob.as_slice()).unwrap();
// keys.group_key() == L1*G*a1 + L2*G*a2 == G*(L1*a1 + L2*a2): attacker knows the scalar
// Victim registers deposit offsets under keys.group_key() via scanner(key);
// scanned ReceivedOutputs are unspendable by the victim and spendable by the attacker.
// Honest signing either fails aggregate verify or blames a valid share, locking funds.
```

```rust
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
```
