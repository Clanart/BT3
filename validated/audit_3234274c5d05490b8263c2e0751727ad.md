## Title
`DeployWithMaxDataLen` programdata PDA is a public, unsigned address that can be pre-funded to DoS program deployment - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `bpf_loader_upgradeable` `DeployWithMaxDataLen` instruction handler derives the `ProgramData` account address deterministically from the new program's pubkey and then calls `system_instruction::create_account` (via CPI) to create it. Because the derived address and the seeds used to compute it are fully public (`Pubkey::find_program_address(&[new_program_id.as_ref()], program_id)`), and because Solana's `SystemProgram::CreateAccount` refuses to create an account that already holds any lamports, any unprivileged actor can pre-fund that address with a trivial system transfer before the deployer's transaction lands, permanently blocking that specific program from ever being deployed. This mirrors the `pump-science` `lock_escrow` DoS: a deterministic, unsigned PDA whose creation is gated only by "must have zero lamports," letting a griefer squat the address ahead of the legitimate creator. [1](#0-0) 

### Finding Description
In `deploy_with_max_data_len` (bpf_loader_upgradeable), the ProgramData address is derived purely from the program id being deployed:
```
let (derived_address, bump_seed) =
    Pubkey::find_program_address(&[new_program_id.as_ref()], program_id);
if derived_address != programdata_key {
    ic_logger_msg!(log_collector, "ProgramData address is not derived");
    return Err(InstructionError::InvalidArgument);
}
...
let mut instruction = system_instruction::create_account(
    &payer_key,
    &programdata_key,
    1.max(rent.minimum_balance(programdata_len)),
    programdata_len as u64,
    program_id,
);
invoke_context
    .native_invoke_signed(instruction, &[&[new_program_id.as_ref(), &[bump_seed]]])?;
``` [2](#0-1) 

This CPI is handled by the System Program's `create_account`, which unconditionally rejects the creation if the destination already holds any lamports at all:
```
fn create_account(...) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    transfer(from_account_index, to_account_index, lamports, invoke_context, instruction_context)
}
``` [3](#0-2) 

Because `new_program_id` (the keypair that will own the program) is chosen by, and known to, the deployer before the deploy transaction is sent (it's typically funded and used as a signer earlier in the same flow, and its pubkey is public once any preparatory transaction—e.g. buffer creation, funding, or even simple wallet activity—references it), an attacker who learns the target `new_program_id` can pre-compute `programdata_key` off-chain with the same `find_program_address` call and send an ordinary `SystemProgram::Transfer` of 1 lamport to it before the deploy transaction executes. Once that lamport lands, `to.get_lamports() > 0` is true forever (the deployer has no way to CPI-close or drain an account it doesn't yet own/control the seeds signer for in a permissionless way through this path), so every subsequent `DeployWithMaxDataLen` for that `new_program_id` fails with `SystemError::AccountAlreadyInUse`, permanently bricking deployment for that specific program id. This is directly analogous to the `pump-science` `lock_escrow` account being derived from public seeds (`pool`, `owner`) and created without any signature from `owner`, allowing preemptive creation and DoS of `lock_pool`.

Unlike the newer `CreateAccountAllowPrefund` instruction added to the System Program specifically to tolerate pre-funded destinations, `deploy_with_max_data_len` still uses the strict `system_instruction::create_account`, which has no tolerance for pre-existing lamports:
```
/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
fn create_account_allow_prefund(...)
``` [4](#0-3) 

The existence of this dedicated feature-gated instruction is itself an implicit acknowledgment that ordinary `create_account` is griefable by prefunding — but `deploy_with_max_data_len` was not migrated to use it.

### Impact Explanation
Any unprivileged network participant who can learn/predict a soon-to-be-deployed program's pubkey (which is common — deployer wallets often fund/reference the program keypair before the final deploy transaction, and the deploy transaction itself can be observed in the mempool/gossip before it lands due to normal network propagation and any retries) can permanently deny deployment of that specific program by sending a 1-lamport transfer to its PDA-derived programdata address. This is a non-RPC, unprivileged, remote griefing/DoS vector against the on-chain program-deployment path of a live Agave validator/cluster — the deployer must abandon the chosen program id and generate a new one, and any observed retried deploy attempt (with the same program id) can be front-run again.

### Likelihood Explanation
Likelihood is high for any given deploy the attacker actually targets: the derivation is a single, well-known PDA formula (`find_program_address(&[new_program_id.as_ref()], bpf_loader_upgradeable::id())`), requires no privileged access, and the griefing transaction is a trivial, cheap `SystemProgram::Transfer` that any wallet can send. The main precondition is that the attacker learns the target `new_program_id` before the deploy transaction is confirmed, which is realistic given transaction propagation delays, public buffer-account funding transactions that reference the same program keypair, and common tooling patterns (deploy scripts often fund the program-data-owning keypair from a known/traceable source before deploying).

### Recommendation
Migrate `deploy_with_max_data_len` (and any other bpf_loader_upgradeable code path that creates a PDA-derived account via a plain `system_instruction::create_account` CPI) to use the prefund-tolerant creation path (`CreateAccountAllowPrefund`/`create_account_allow_prefund`) already introduced in `system_processor.rs`, so that a pre-funded programdata address no longer blocks legitimate deployment. Alternatively, before invoking `create_account`, check whether the derived address already has a nonzero balance and, if so, drain/rent-reclaim it via a permissionless mechanism, or use `allocate`+`assign` semantics that tolerate existing lamports instead of requiring a fresh, zero-lamport account.

### Proof of Concept
1. Attacker observes (or predicts) the `new_program_id` a deployer intends to use for `DeployWithMaxDataLen` (e.g., by watching for the associated buffer-creation/funding transaction referencing that pubkey, which typically precedes the deploy instruction).
2. Attacker computes `programdata_key = Pubkey::find_program_address(&[new_program_id.as_ref()], &bpf_loader_upgradeable::id()).0` — no signature or special permission required, matching `programs/bpf_loader/src/lib.rs:280-281`.
3. Attacker submits an ordinary `SystemProgram::Transfer` of 1 lamport to `programdata_key`, creating a system-owned account with `lamports = 1` at that address.
4. The legitimate deployer's `DeployWithMaxDataLen` transaction executes; inside it, the CPI to `system_instruction::create_account` for `programdata_key` hits the `to.get_lamports() > 0` guard in `system_processor.rs:164-171` and returns `SystemError::AccountAlreadyInUse`, aborting the deployment.
5. Because the PDA address is fixed for that `new_program_id`, every retry of deployment for the same program id fails identically, forcing the deployer to abandon that program id.

**Uncertainty note:** I could not fully inspect the earlier portion of `deploy_with_max_data_len` (the buffer/authority validation preceding line 232) or confirm whether any other Agave-side guard elsewhere in the deployment flow (e.g., in `bank.rs` program-cache loading) neutralizes a pre-funded-but-uninitialized `programdata_key` before this CPI runs, since the tool budget was exhausted before that section could be read in full. If such a guard exists, it would need to be checked against this PoC before treating the finding as fully confirmed.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
