## #Valid Finding

### Title
Non-canonical `action` values silently downgrade blocking rules to warnings while still injecting rule message - ([File: plugins/hookify/core/config_loader.py])

### Summary
`Rule.from_dict()` stores the frontmatter `action` value verbatim with no normalization or validation, and `RuleEngine.evaluate_rules()` only treats a rule as blocking when `rule.action` is the exact, lowercase string `'block'`. Any deviation — different casing, extra whitespace, a misspelling, or an empty string — causes the rule to fall into the warning path, so the guarded operation proceeds while the rule's message is still displayed as if enforcement occurred.

### Finding Description
`Rule.from_dict()` reads the action field with `action=frontmatter.get('action', 'warn')` [1](#0-0)  and performs no `.strip().lower()` normalization or validation against the allowed set `{'warn', 'block'}`.

`RuleEngine.evaluate_rules()` then classifies matched rules using a strict equality check:
```python
if rule.action == 'block':
    blocking_rules.append(rule)
else:
    warning_rules.append(rule)
``` [2](#0-1) 

Because this is a case-sensitive exact match with no trimming, values such as `Block`, `BLOCK`, `' block'` (leading space), `blocked`, or `''` (from a mistakenly emptied field) all fall through to the `else` branch and are added to `warning_rules` instead of `blocking_rules`. In the final response construction, warning rules still produce a `systemMessage` containing the rule's message text but never set `permissionDecision: "deny"` or `decision: "block"` [3](#0-2) , so `pretooluse.py`, `posttooluse.py`, and `stop.py` all report the operation as allowed [4](#0-3)  — meanwhile the exact same "camouflage" message that a real block would have shown is still surfaced to the user/agent, creating false confidence that the guard fired.

This is reachable through ordinary frontmatter/hook parsing: a `.claude/hookify.*.local.md` rule file — whether hand-authored, LLM-generated via `/hookify` (which explicitly instructs `action: {warn|block}` in Step 3 [5](#0-4) ), or introduced through repository content such as a PR — can specify a non-canonical `action` value that a reviewer or user would reasonably assume enforces blocking (e.g. `action: Block`), but which the engine silently treats as `warn`.

### Impact Explanation
This breaks the "deny means deny" invariant for hookify's PreToolUse/PostToolUse/Stop enforcement. An operator who believes a rule blocks a dangerous action (e.g., editing a `.env`/secrets file, or running `rm -rf`) will see the rule's warning text appear and reasonably conclude the guard executed, when in fact `permissionDecision` was never set to `deny` and the underlying tool call (file write/edit, bash command) proceeds unblocked. This is an approval-gate/guard bypass reachable purely through hook/frontmatter content, matching the "bypass of an intended guard, allowing the underlying tool operation to proceed while attacker/user content is injected as camouflage" impact category.

### Likelihood Explanation
Trivial to trigger and highly plausible in practice: any typo, casing inconsistency, or subtly malformed rule file (whether accidental or intentionally crafted in a PR/plugin content that a maintainer merges without close scrutiny) will hit this path. No privilege escalation is needed beyond the ability to introduce or edit a `.claude/hookify.*.local.md` file, which is exactly the mechanism the plugin's own commands (`/hookify`, `configure.md`) are designed to create/edit.

### Recommendation
Normalize and validate the `action` field in `Rule.from_dict()`:
```python
action_raw = str(frontmatter.get('action', 'warn')).strip().lower()
action = action_raw if action_raw in ('warn', 'block') else 'warn'
```
Additionally, log/emit a warning (e.g., to stderr, and ideally surfaced to the user) when an unrecognized `action` value is encountered, rather than silently coercing it to `warn`, so authors are alerted that their intended blocking rule is not enforceable as written.

### Proof of Concept
Unit test against `RuleEngine.evaluate_rules()`:
```python
import pytest
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

@pytest.mark.parametrize("action_value", ["Block", "BLOCK", " block", "blocked", ""])
def test_non_canonical_action_does_not_block(action_value):
    rule = Rule(
        name="secret-file-guard",
        enabled=True,
        event="file",
        conditions=[Condition(field="file_path", operator="regex_match", pattern=r"\.env$")],
        action=action_value,
        message="Blocked: attacker camouflage message",
    )
    engine = RuleEngine()
    result = engine.evaluate_rules([rule], {
        "hook_event_name": "PreToolUse",
        "tool_name": "Write",
        "tool_input": {"file_path": ".env", "content": "SECRET=1"},
    })
    # Assert the operation is NOT denied despite an intended "block" action
    hook_output = result.get("hookSpecificOutput", {})
    assert hook_output.get("permissionDecision") != "deny"
    # But the message still appears, camouflaging the bypass
    assert "systemMessage" in result

def test_only_exact_lowercase_block_denies():
    rule = Rule(
        name="secret-file-guard", enabled=True, event="file",
        conditions=[Condition(field="file_path", operator="regex_match", pattern=r"\.env$")],
        action="block", message="Blocked",
    )
    engine = RuleEngine()
    result = engine.evaluate_rules([rule], {
        "hook_event_name": "PreToolUse", "tool_name": "Write",
        "tool_input": {"file_path": ".env", "content": "SECRET=1"},
    })
    assert result["hookSpecificOutput"]["permissionDecision"] == "deny"
```
Expected: the first parametrized test fails against current code (no `deny` produced for non-canonical values), demonstrating the silent downgrade; the second confirms only the exact string `'block'` triggers deny.
