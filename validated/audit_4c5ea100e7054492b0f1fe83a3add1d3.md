### Title
Unbounded `changeDepositVault` in `AuctionEntryPoint` (KIP-249) Can Strand Searcher Deposits - (File: contracts/bindings/auction/Kip249.go / contracts/bindings/auctionv3/Kip249V3.go)

### Summary
The `IAuctionEntryPoint` system contract (KIP-249, used by Kaia's `kaiax/auction` module) exposes a `changeDepositVault(address _depositVault)` admin function that repoints the `depositVault` state variable to a new address, alongside per-searcher deposit accounting exposed by `getNoncesAndDeposits`. This mirrors the exact bug class from the referenced Redacted Cartel `RewardDistributor.setBribeVault()` finding: an admin-controlled address that both (a) tracks/holds user-owned value and (b) can be swapped without any check that the outstanding balance is zero, stranding funds credited against the old vault address.

### Finding Description
`IAuctionEntryPoint` (the KIP-249 auction entry point interface bound in `contracts/bindings/auction/Kip249.go` and `contracts/bindings/auctionv3/Kip249V3.go`) defines:
- `depositVault()` — a view getter for the vault address that presumably custodies/tracks searcher bid deposits [1](#0-0) 
- `changeDepositVault(address _depositVault)` — a state-changing function, emitting `ChangeDepositVault(oldDepositVault, newDepositVault)`, that reassigns the vault address [2](#0-1) [3](#0-2) 
- `getNoncesAndDeposits(address[] searchers)` — returns per-searcher `deposits_`, i.e., an accounting ledger of value searchers have deposited into the auction system to back their bids [4](#0-3) 

This is structurally identical to the `RewardDistributor.bribeVault` pattern: a vault address is both the custodian of pooled value and a mutable configuration parameter, with per-user/per-searcher balances tracked separately from the vault's own identity. If `changeDepositVault` can be invoked (by governance/admin/auctioneer) while searchers still have nonzero deposits recorded against the *old* vault, those balances become unreachable or point to a vault contract that no longer recognizes/holds the corresponding funds — precisely the "changing a vault address locks currently held funds" bug class from the external report.

The `kaiax/auction` off-chain module explicitly treats `AuctionEntryPoint`-related address changes as a "config change" event that just clears the local bid pool state, with no on-chain guarantee that deposits were drained first: *"This module reads `SystemRegistry` and `AuctionEntryPoint` to detect any changes of `AuctionEntryPoint` address, `bidTxGasBuffer` and `Auctioneer` address. If the one of them is changed, the module will clear the existing bids in the bid pool."* [5](#0-4)  This confirms that vault/entry-point address changes are a first-class, live-network occurrence the client is designed to react to — reinforcing that this is a reachable, in-scope operational event, not merely a theoretical setter.

Because the actual on-chain implementation contract for `AuctionEntryPoint`/its `depositVault` withdrawal logic is not included as full Solidity source in this repository (only the `IAuctionEntryPoint` ABI/interface bindings and a stripped-down `AuctionEntryPointMock.sol` test double that doesn't implement deposit/withdraw at all [6](#0-5) ), I cannot verify from this codebase whether the real deployed implementation already enforces `balanceOf(vault) == 0` (or an equivalent invariant) before allowing `changeDepositVault` to succeed. This is a genuine limitation of the available index/context, not evidence either way.

### Impact Explanation
If `changeDepositVault` is unguarded, an auctioneer/admin action (or a compromised/erroneous governance call) that updates the vault mid-operation — while searchers hold nonzero deposits — could permanently orphan searcher funds recorded via `getNoncesAndDeposits`, denying auction bidders access to their own escrowed KAIA. This is a fund-lock/loss condition reachable by any of: (1) the privileged party invoking `changeDepositVault`, triggered against (2) an unprivileged auction bidder/searcher's already-deposited funds — matching the "gasless and auction modules" / "auction bidder" reachability scope explicitly permitted by the rules.

### Likelihood Explanation
Medium: triggering requires the vault-changing privileged call to occur while deposits are outstanding. This is plausible during legitimate vault migrations/upgrades of the auction system (a realistic operational scenario, as evidenced by the client explicitly watching for and reacting to `AuctionEntryPoint`/vault address changes), rather than requiring an attacker to compromise the privileged account.

### Recommendation
Enforce an invariant in the `changeDepositVault` (and analogous `changeAuctioneer`) implementation that all outstanding searcher deposits are zero (or migrated) before the vault address is rotated — e.g., require `totalDeposits == 0` / iterate and refund searchers, or make the deposit-holding component immutable and separate from any admin-mutable routing address, following the same remediation applied to the original `RewardDistributor` finding (`kphed`'s fix: make the vault immutable and remove the setter).

### Proof of Concept
Conceptual sequence (concrete PoC not verifiable without the full on-chain `AuctionEntryPoint` implementation source, which is not present in this repository — only interface bindings/ABI and a non-functional mock were found):
1. Searcher calls the auction deposit flow, crediting `deposits[searcher]` against the current `depositVault`.
2. Privileged caller invokes `changeDepositVault(newVault)` via the bound method `ChangeDepositVault` [2](#0-1)  while `deposits[searcher] > 0`.
3. `ChangeDepositVault` event fires [3](#0-2) , and subsequent withdrawal attempts against the stale vault reference fail or transfer to/interact with the wrong custodial contract, per `getNoncesAndDeposits` still reporting the stranded balance [4](#0-3) .

Given the missing implementation source, this should be treated as a **hypothesis requiring verification against the actual deployed `AuctionEntryPoint` contract bytecode/source** (not indexed in this repository) before being escalated with full confidence.

// Solidity: function getNoncesAndDeposits(address[] searchers) view returns(uint256[] nonces_, uint256[] deposits_)
func (_IAuctionEntryPoint *IAuctionEntryPointCaller) GetNoncesAndDeposits(opts *bind.CallOpts, searchers []common.Address) (struct {
	Nonces   []*big.Int
	Deposits []*big.Int
}, error) {
	var out []interface{}
	err := _IAuctionEntryPoint.contract.Call(opts, &out, "getNoncesAndDeposits", searchers)

	outstruct := new(struct {
		Nonces   []*big.Int
		Deposits []*big.Int
	})
	if err != nil {
		return *outstruct, err
	}

	outstruct.Nonces = *abi.ConvertType(out[0], new([]*big.Int)).(*[]*big.Int)
	outstruct.Deposits = *abi.ConvertType(out[1], new([]*big.Int)).(*[]*big.Int)

	return *outstruct, err

}
