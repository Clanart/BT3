### Title
Persistent, Unrevoked ERC20 Allowance Granted to Arbitrary IBC-Callback Contract Enables Fund Drain from the Isolated Receiver Address - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`IBCReceivePacketCallback` approves the destination-callback `contractAddress` for the *full* transferred token amount on behalf of the isolated receiver address, then invokes the contract's calldata, and finally only checks that the isolated address's balance is zero. It never revokes the allowance afterward. Because the isolated address is deterministically derived from `(destChannel, sender)` and is reused across multiple IBC transfers/callbacks with the same sender/channel/contract, a leftover or under-consumed allowance can be exploited by the same (now-untrusted or later-compromised/malicious) contract to pull tokens from future deposits into that same isolated address without needing a fresh approval.

### Finding Description [1](#0-0) 
The isolated address is generated deterministically from `destChannel` and `sender`, meaning the *same* isolated address (and therefore the same ERC20 "owner" for allowance purposes) is reused for every IBC receive-callback packet coming from that sender/channel pair. [2](#0-1) 
The keeper calls `approve(contractAddr, amountInt)` on behalf of `receiverHex` (the isolated address) for the full packet amount, checking only that `approve` returned `true`. [3](#0-2) 
It then calls the contract's arbitrary calldata and, afterward, only validates that `receiverHex`'s ERC20 balance is `0`. There is no explicit revocation of the allowance (`approve(contractAddr, 0)`) after the callback completes, and there is no check that the *allowance itself* was consumed down to zero — only that the balance is zero. If the contract's calldata does not fully consume the allowance (e.g., it transfers less than `amountInt`, or does not call `transferFrom` for the full spend limit, or reverts partway through logic that leaves balance at zero through some other path), a non-zero allowance for `contractAddr` can persist against `receiverHex`.

Since `receiverHex` (the isolated address) is reused for subsequent transfers from the same sender on the same channel, and the erc20 precompile's `Approve`/allowance mechanics allow the allowance to persist in module state (`p.erc20Keeper.SetAllowance` in `precompiles/erc20/approve.go:73-83` and `precompiles/erc20/tx.go:89-110`) until explicitly zeroed or fully drained via `transferFrom`, a subsequent IBC receive to the same isolated address that increases its ERC20 balance (from a new legitimate transfer) becomes immediately spendable by the previously-approved `contractAddr` — even without a new callback packet needing to run — because the old allowance was never revoked to zero.

This mirrors the reported analog exactly: an approval is granted for a one-shot operation, the operation completes, and the excess/leftover approval is not revoked, leaving it exploitable to extract funds that arrive later or exceed the checked-out amount.

### Impact Explanation
If a destination-callback contract is malicious, buggy, or later compromised (upgradeable proxy, owner key compromise, etc.), it can retain spend rights over the isolated address indefinitely and drain any future token balance credited to that same isolated address via subsequent IBC transfers from the same sender/channel — without the user's consent for that specific transfer. This is an unauthorized extraction of user (IBC-escrowed/native-representation) funds, matching the "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds ... or token-pair-backed balances" impact class.

### Likelihood Explanation
Likelihood depends on: (1) a contract used as an IBC destination callback not fully consuming its approved allowance (plausible for buggy/partial-transfer contracts, or contracts that intentionally only pull part of the amount), and (2) the same isolated address receiving additional transfers later (deterministic and attacker-influenceable since `isolatedAddr` is derived from `sender`, which the attacker/relayer-adjacent party controls as the IBC sender on the counterparty chain). An attacker who controls both the sending account on the source chain and the destination-callback contract can deliberately engineer this: approve a large amount, only partially consume it in the callback (leaving balance at zero via a different mechanism, e.g. forwarding tokens elsewhere without using the full allowance), then send a second, larger, callback-free (or callback-lite) transfer to the same isolated address and drain it using the still-valid leftover allowance from the first packet — entirely through ordinary, unprivileged user-triggered IBC transfer flows.

### Recommendation
After the contract call in `IBCReceivePacketCallback`, explicitly revoke any remaining allowance granted to `contractAddr` (e.g., call `approve(contractAddr, 0)` or use `erc20Keeper.DeleteAllowance`) regardless of the balance check outcome, so no residual spend right survives the callback. Alternatively/additionally, verify that the on-chain allowance for `(receiverHex, contractAddr)` is exactly zero (not just the balance) before returning success, and fail/roll back the packet if a residual allowance remains.

### Proof of Concept
1. Attacker controls `senderX` on chain A and deploys `EvilCallback` contract on chain B (destination-callback target).
2. Attacker sends IBC transfer #1 from `senderX` with destination callback pointing to `EvilCallback`, amount `A1`. `IBCReceivePacketCallback` runs: approves `EvilCallback` for `A1` on `isolatedAddr = f(destChannel, senderX)`, then calls `EvilCallback`'s calldata. `EvilCallback` is crafted to `transferFrom` only a small sub-amount to itself and forward/burn the rest through a path that still zeroes `isolatedAddr`'s balance (e.g., calling `transfer` for the remainder to another attacker-controlled address instead of using the approval), passing the final balance check with allowance for `A1 - subamount` still outstanding.
3. Attacker sends IBC transfer #2 from `senderX` (no callback needed this time) crediting the same `isolatedAddr` with a larger amount `A2`.
4. `EvilCallback`, still holding the un-revoked allowance from packet #1, calls `transferFrom(isolatedAddr, EvilCallback, min(allowance, A2))` directly (outside of any callback context, as an ordinary EVM transaction), draining part or all of the newly received `A2` tokens without further authorization from the isolated address or the packet processing.

Note: Exact feasibility of step 2 (leaving balance zero while allowance nonzero) depends on precise contract logic reachable within `cbData.Calldata`; this could not be fully verified end-to-end without a live testnet trace due to index depth limits, but the missing revocation of allowance after the callback is a directly observed and unguarded code path.
