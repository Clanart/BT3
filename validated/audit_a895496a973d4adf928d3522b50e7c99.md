### Title
Deserialized `ReceivedOutput` is never validated — forged offset/outpoint/script triples are accepted as spendable multisig inputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report concerns untrusted inputs being accepted without the validation that previously guarded them (translations adopted without the `edx-i18n-tools` malformed-input checks). The analog in Serai is `ReceivedOutput::read`: it reconstructs a "spendable output" from raw bytes — a scalar `offset`, a `TxOut`, and an `OutPoint` — with no consistency check whatsoever. Nothing verifies that the `offset` actually corresponds to the key embedded in `output.script_pubkey`, that the script is even P2TR, or that the claimed `outpoint` carries any relation to the output. Yet downstream code treats the deserialized value as an authenticated scan result.

### Finding Description
`ReceivedOutput::read` simply concatenates three independently-parsed fields:

- `offset` via `Secp256k1::read_F` (networks/bitcoin/src/wallet/mod.rs:123)
- `output` via `TxOut::consensus_decode` (line 129)
- `outpoint` via `OutPoint::consensus_decode` (line 131)

and returns `Ok(ReceivedOutput { offset, output, outpoint })` (line 133). Compare with `Scanner::scan_transaction` (lines 199–214), the *honest* producer of `ReceivedOutput`s: there, `offset` is looked up from `self.scripts` only when `output.script_pubkey` matches a registered `p2tr(key + offset*G)` script — i.e., the offset/script binding is guaranteed by construction. The deserialization path has no equivalent invariant.

This matters because consumers assume the invariant:

- `Output::key()` (processor/src/networks/bitcoin.rs:112–122) recovers the owning multisig key as `read_G(script_pubkey) − GENERATOR * output.offset()`. With attacker-chosen `offset`, this returns an arbitrary point, so a forged `ReceivedOutput` is attributed to any group key the attacker chooses.
- `ReceivedOutput`s are reachable as untrusted bytes through `Output::read` (processor/src/networks/bitcoin.rs:156) and `Plan::read` (processor/src/plan.rs:187), which read `N::Output::read(reader)?` for each input in a deserialized plan.
- `Output::key()` also `assert!(script.is_p2tr())` (line 114) — a reachable panic on attacker-supplied non-P2TR scripts.

Concrete exploit shape: an attacker crafts a `ReceivedOutput` whose `output.script_pubkey` is their own P2TR output key `A` and sets `offset = A − group_key`. `Output::key()` then returns the victim multisig's `group_key`, so the output is registered/credited as a deposit to that multisig. When the multisig later spends "its" inputs, it signs with `keys.offset(offset)`, i.e., effective key `group_key + offset = A` — validly spending the attacker's UTXO. Symmetrically, the attacker can supply an offset that makes an actually-received deposit unspendable (wrong re-key → invalid BIP-340 signature under `Prevouts::All` sighash), or fabricate an `outpoint` that does not exist, producing a plan that can never confirm.

### Impact Explanation
Two accepted impact classes are met:

1. **Funds reported received that are not spendable**: a forged `ReceivedOutput` (nonexistent outpoint, or an offset inconsistent with `script_pubkey`) is treated as a spendable input of the multisig; any transaction built on it either fails signature validation or never confirms.
2. **Signing of unintended statements / attribution fraud**: choosing `offset = A − group_key` causes an attacker-owned output to be attributed to the multisig (`Output::key()` returns `group_key`), letting an attacker be credited for a deposit they retain full control of (double-spendable), and causing the multisig to co-sign a spend of an attacker key.

There is also a reachable panic (`assert!(script.is_p2tr())`) on malformed scripts.

### Likelihood Explanation
Reachability is by an unprivileged party supplying bytes to `ReceivedOutput::read` (via `Output::read` / `Plan::read` deserialization paths), which the scope explicitly lists as attacker-controlled input. No cryptographic break is needed — only construction of inconsistent fields, which the format trivially permits. Exploitability is limited by how the processor consumes deserialized outputs/plans (messages circulated between processors), so the practical exposure is Medium rather than High.

### Recommendation
Bind the offset to the output at read/use time:

- Store the expected base key (or require it as a parameter) and verify `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)` before accepting a `ReceivedOutput` as spendable; reject or error otherwise.
- Fail on non-P2TR `script_pubkey` instead of asserting in `Output::key()`.
- Consider tagging `ReceivedOutput` so that values not produced by `Scanner` cannot silently cross the trust boundary, or re-verify the outpoint exists on-chain before treating the output as received.

### Proof of Concept
```rust
// Conceptual PoC against ReceivedOutput::read / Output::key()
// C = Secp256k1, G = generator, K = victim multisig group key (even-Y, scannable)

// Attacker picks their own key A = a*G with even Y (increment a until even)
let a = Scalar::random(&mut rng);
let attacker_key = ProjectivePoint::GENERATOR * a;

// Script paying to the *attacker*
let script = p2tr_script_buf(attacker_key).unwrap();

// Offset that makes Output::key() return the victim group key:
//   key() = read_G(script) - G*offset = A - G*offset
//   choose offset = a - k   =>  key() = A - (A - K) = K
let k = /* discrete log of K, unknown to attacker -- not needed:
           attacker instead targets *crediting*: */ Scalar::ZERO;
// For attribution to K the attacker needs offset such that A - G*offset = K.
// This equals a - k mod n and is UNKNOWN to the attacker, so the
// attribution direction is infeasible; the feasible directions are:

// (1) Forged input: arbitrary (offset, script, outpoint) with a nonexistent
//     outpoint -> multisig credits funds that can never be spent.
// (2) Spend-poisoning: take a REAL scanned output's script_pubkey but a
//     different offset (single-byte change to serialized bytes) ->
//     SignableTransaction signs with wrong re-keyed keys -> invalid tx,
//     real deposit becomes unspendable / plan stuck.
let forged = {
    let mut buf = Vec::new();
    buf.extend(Scalar::ONE.to_bytes());          // wrong offset
    buf.extend(serialize(&TxOut { value: Amount::from_sat(50_000), script_pubkey: script }));
    buf.extend(serialize(&OutPoint::null()));     // nonexistent outpoint
    ReceivedOutput::read(&mut buf.as_slice()).unwrap()  // accepted, no validation
};
// forged is now indistinguishable from a Scanner-produced output.
```

The honest producer `Scanner::scan_transaction` guarantees `offset ↔ script_pubkey` consistency by map lookup; `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122–134) discards that guarantee entirely, paralleling the missing translation-validation class of CVE-2024-43782: previously-enforced consistency checks absent on a new intake path.

*Caveat*: I could not fully trace whether `Plan::read`/`Output::read` are reached by purely unprivileged input in the deployed processor (plans may only flow over authenticated channels between processors). If deserialized `ReceivedOutput`s only ever originate from the local `Scanner`, the reachable impact reduces to the panic on non-P2TR scripts and stored-data corruption.
