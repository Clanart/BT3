## Title
Silent git remote URL rewrite trusts unvalidated GitHub API `clone_url` field, allowing repository‑renamed/compromised‑endpoint responses to redirect commits/pushes to an attacker host - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a user's local git `origin` remote URL whenever the GitHub API's `clone_url` for the matched repository differs from what Desktop last cached, with no user confirmation and only a same-protocol check. [1](#0-0)  This mirrors the Aave finding's core flaw: a value obtained once from a trusted-but-mutable upstream source (there: `PoolAddressesProvider`'s cached oracle address; here: the cached `GitHubRepository.cloneURL` / live API `clone_url`) is treated as authoritative for subsequent security-relevant decisions without adequately re-validating the change is legitimate.

### Finding Description
When Desktop refreshes a repository's GitHub metadata (`repositoryWithRefreshedGitHubRepository`), it calls `api.fetchRepository(owner, name)` and then unconditionally calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [2](#0-1) 

Inside `updateRemoteUrl`, the only guards before silently running `git remote set-url` are:
- `protocolsMatch` – confirms the URL scheme (http/https) hasn't changed, but does **not** validate hostname, owner, or repo name.
- `remoteUrlUnchanged` – confirms the *current* local remote still equals the *previously cached* `gitHubRepository.cloneURL` (i.e. the user hasn't manually edited the remote).
- `!urlsMatch` – confirms the new API `clone_url` differs from the current remote.

If all three hold, Desktop calls `gitStore.setRemoteURL(...)` and rewrites `origin` to whatever `clone_url` the API returned — with no host/owner allow-listing and no user prompt. [3](#0-2) 

This was designed for the legitimate case of a renamed repository, but the trust boundary is broken: the `clone_url` field comes from an **attacker-controllable GitHub API object** (per the task's Valid Impact list) — e.g. a repository owner/collaborator who renames/transfers a repo, a compromised or malicious GitHub Enterprise Server the user is signed into, or a tampered API response reaching Desktop through any means that can influence what `api.fetchRepository` returns for the matched repo. Desktop's matching logic (`matchGitHubRepository`) only checks that the *account's endpoint hostname* matches the remote's hostname; it does not independently verify that the new `clone_url`'s host/owner is expected before trusting it as the new remote. [4](#0-3) 

Existing guards do not stop this path because:
- `protocolsMatch` only checks `https://` vs `https://`, not the host.
- `remoteUrlUnchanged` is satisfied by definition on first refresh after add/clone (cache == current remote), so a hostile `clone_url` returned on the very next API refresh passes.
- There is no user-facing confirmation dialog analogous to `UntrustedCertificate` or `AddSSHHost` for this specific action, unlike other trust-decision surfaces in the app. [5](#0-4) 

### Impact Explanation
Once the local `origin` remote is silently repointed to an attacker-controlled URL, subsequent `git fetch`/`git pull`/`git push` operations transparently target the new host. This directly matches the "silent corruption of what the user commits or pushes" impact category: a user believing they are pushing to their known repository could instead push commits (and potentially credentials via the credential helper, if the new host is later recognized as a known GitHub endpoint) to an attacker-controlled remote, or unknowingly pull/fetch attacker-supplied history into their working copy.

### Likelihood Explanation
This path triggers automatically during routine background refreshes (`repositoryWithRefreshedGitHubRepository`, invoked e.g. after account changes) without any explicit user action beyond having previously added/signed into the repository/account — no additional local access, admin rights, or social engineering step is required beyond the attacker being able to influence the API's `clone_url` response for the specific matched repo (e.g., via a renamed/transferred repository they control, or a hostile GHE server). This satisfies the "attacker controls ... a GitHub API object" criterion explicitly listed as valid.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that the new `clone_url`'s hostname matches the account's expected endpoint host (not just protocol), and/or surface an explicit confirmation dialog to the user (similar to `UntrustedCertificate`/`AddSSHHost`) whenever the remote host or owner is about to change, rather than silently rewriting it whenever only the protocol matches.

### Proof of Concept
1. User has a repository cloned with `origin` pointing to `https://github.com/acme/widget.git`, and it is associated with a GitHub.com account.
2. The attacker (an owner/admin of `acme/widget`, or a compromised/hostile server backing a GHE endpoint the user is signed into) causes the GitHub API's repository object for the matched `owner/name` to report a different `clone_url`, e.g. `https://github-mirror.evil.example/acme/widget.git` (same `https` protocol).
3. On the next background refresh, `repositoryWithRefreshedGitHubRepository` fetches this repo object and calls `updateRemoteUrl`; `protocolsMatch` is true, `remoteUrlUnchanged` is true (nothing else has changed it), and `urlsMatch` is false. [6](#0-5) 
4. Desktop calls `gitStore.setRemoteURL('origin', 'https://github-mirror.evil.example/acme/widget.git')` with no prompt. [7](#0-6) 
5. Subsequent pushes from Desktop go to `github-mirror.evil.example` instead of the user's real repository.

Note: I was unable to fully trace every call site of `repositoryWithRefreshedGitHubRepository`/`matchGitHubRepository` within `app-store.ts` (12 matches found but not all individually reviewed) or confirm exact triggering cadence/background scheduling due to iteration limits; a Devin session with full file access would be needed to enumerate every code path that reaches this function and confirm real-world triggering frequency.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
