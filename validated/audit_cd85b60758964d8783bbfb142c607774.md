### Title
Trampoline credential-helper token leaks into unproxied git-hook processes spawned during `clone --recursive`, allowing an attacker-controlled repository to exfiltrate GitHub credentials - ([File: app/src/lib/trampoline/trampoline-server.ts])

### Summary
The external report's core primitive is: a shared, globally-scoped callback/registration mechanism (ERC1820) lets an attacker register itself so that a hook meant to run in the context of *another user's* operation actually invokes attacker code, because the mechanism does not verify that the caller "owns" the current operation. GitHub Desktop has a structurally identical defect in its trampoline credential system: the trampoline token is validated only against a **global** set of currently-active tokens with no binding to the connection, process, or operation that is allowed to use it [1](#0-0) [2](#0-1) , and that token (together with the server's TCP port) is broadcast as plain environment variables to every process `git` spawns during a `clone`, because `clone` does not route hook execution through Desktop's hook-proxy sandbox.

### Finding Description
`withTrampolineEnv` unconditionally injects `DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT` into the environment of every `git` invocation, including `git clone` [3](#0-2) . `git`'s own environment is inherited by any hook/filter/sub-process it spawns unless Desktop explicitly intercepts hooks via `opts.interceptHooks` and reroutes them through the sandboxed `hooks-proxy`/`process-proxy` mechanism [4](#0-3) .

`clone.ts`, however, never sets `interceptHooks` - its options object is only `{ env }` [5](#0-4) . That means any hook that Git executes as part of a `clone --recursive` (e.g. a submodule hook triggered through Git's hook-execution surface during recursive clone/checkout) runs **outside** the hooks-proxy sandbox and inherits the raw process environment - including the live `DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT`.

Once a hook process obtained through a cloned/attacker-controlled repository has that token, nothing stops it from opening a raw TCP connection to `127.0.0.1:<DESKTOP_PORT>` and speaking the trampoline protocol directly, because `TrampolineServer.processCommand` only checks `isValidTrampolineToken(command.trampolineToken)` - a lookup in a process-wide `Set<string>` with no notion of which git invocation, working directory, or socket the token belongs to [6](#0-5) . A forged `CREDENTIALHELPER get` command using the leaked token is routed straight to `createCredentialHelperTrampolineHandler` → `getCredential`, which will return the user's stored GitHub credential for the current endpoint, or otherwise trigger `ui.promptForGitHubSignIn` [7](#0-6) [8](#0-7) .

This is the same broken invariant as the ERC777 report: a value meant to scope a callback to a single legitimate operation (the ERC1820 interface implementer / here the trampoline token) is globally shared and can be hijacked by an unrelated, attacker-controlled execution context that runs concurrently with (or as a child of) the legitimate operation.

### Impact Explanation
If exploitable, this results in silent exfiltration of the signed-in user's GitHub credential/token merely by cloning an attacker's repository - matching the "credential/token exfiltration" and "unauthorized OAuth/account binding" categories of valid impact. No local access, malware, or unnatural user steps beyond "clone this repository" are required.

### Likelihood Explanation
Medium-to-low confidence overall: the mechanism for a hook to execute automatically and unproxied during `git clone --recursive` (e.g. via a maliciously crafted submodule) depends on the underlying Git/dugite version bundled with Desktop, and I could not verify from the indexed code which exact Git version ships or whether it is still vulnerable to hook-execution-during-recursive-clone bugs. What **is** independently verifiable from local code is the structural weakness: `clone.ts` never proxies hooks (unlike `pull.ts`/`push.ts`/`commit.ts` which set `interceptHooks`) [9](#0-8) [10](#0-9) , and the trampoline token validation is unscoped. That combination is a real gap even if the specific hook-triggering technique needs confirmation against the bundled Git version.

### Recommendation
- Route `clone` (and `submodule update --init --recursive`) through the same hook-interception/sandbox path used by `pull`/`push`/`commit`, or explicitly disable hook execution during clone (`--no-recurse-submodules` hooks / `-c core.hooksPath=/dev/null`-style neutralization) until the repository has been fully fetched and vetted.
- Scope trampoline tokens to the specific git invocation/socket (e.g. bind token validity to the spawned child process's PID or a per-command nonce checked against the connecting request's originating command name) rather than a flat global `Set`.
- Strip `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` from the environment passed to any hook or filter subprocess that isn't explicitly proxied.

### Proof of Concept
1. Attacker crafts a repository with a submodule configuration designed to have Git execute a hook script automatically during `git clone --recursive` (the class of submodule/hook-execution issues affecting recursive clones).
2. The hook script reads `process.env.DESKTOP_TRAMPOLINE_TOKEN` and `process.env.DESKTOP_PORT`, both of which are present because `clone.ts` never sets `interceptHooks` [5](#0-4) .
3. The script opens a TCP socket to `127.0.0.1:<DESKTOP_PORT>` and sends a well-formed `CREDENTIALHELPER get` trampoline command carrying the stolen token.
4. `TrampolineServer.processCommand` accepts it because `isValidTrampolineToken` only checks set membership [2](#0-1) , and `getCredential` returns the signed-in GitHub user's stored credential to the attacker's script [7](#0-6) .

Note: step 1 (automatic, unprompted hook execution during recursive clone) is the part I could not fully confirm against the specific Git/dugite version bundled in this repo; I recommend verifying the bundled Git version's susceptibility to hook-execution-during-clone issues via a Devin session with full repository/dependency access, since the index does not expose the vendored Git binary version.

    // Messages coming from the trampoline client will be separated by \0
    socket.pipe(split2(/\0/)).on('data', data => {
      this.onDataReceived(socket, parser, data)
    })

  }

  private onDataReceived(
    socket: Socket,
    parser: TrampolineCommandParser,
    data: Buffer
  ) {
    const value = data.toString('utf8')

    try {
      parser.processValue(value)
    } catch (error) {
      log.error('Error processing trampoline data', error)
      socket.end()
      return
    }

    if (!parser.hasFinished()) {
      return
    }

    const command = parser.toCommand()
    if (command === null) {
      socket.end()
      return
    }

    this.processCommand(socket, command)
  }

export async function withTrampolineEnv<T>(
  fn: (env: object) => Promise<T>,
  path: string,
  isBackgroundTask = false,
  customEnv?: Record<string, string | undefined>
): Promise<T> {
  const sshEnv = await getSSHEnvironment()

  return withTrampolineToken(async token => {
    isBackgroundTaskEnvironment.set(token, isBackgroundTask)
    trampolineEnvironmentPath.set(token, path)

    const existingGitEnvConfig =
      customEnv?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    // The code below assumes a few things in order to manage SSH key passphrases
    // correctly:
    // 1. `withTrampolineEnv` is only used in the functions `git` (core.ts)
    // 2. Those two functions always thrown an error when something went wrong,
    //    and just return a result when everything went fine.
    //
    // With those two premises in mind, we can safely assume that right after
    // `fn` has been invoked, we can store the SSH key passphrase for this git
    // operation if there was one pending to be stored.
    try {
      return await fn({
        DESKTOP_PORT: await trampolineServer.getPort(),
        DESKTOP_TRAMPOLINE_TOKEN: token,
        GIT_ASKPASS: '',
        // This warrants some explanation. We're configuring the
        // credential helper using environment variables rather than
        // arguments (i.e. -c credential.helper=) because we want commands
        // invoked by filters (i.e. Git LFS) to be able to pick up our
        // configuration. Arguments passed to git commands are not passed
        // down to filters.
        //
        // We're using the undocumented GIT_CONFIG_PARAMETERS environment
        // variable over the documented GIT_CONFIG_{COUNT,KEY,VALUE} due
        // to an apparent bug either in a Windows Python runtime
        // dependency or in a Python project commonly used to manage hooks
        // which isn't able to handle the blank environment variables we
        // need when using GIT_CONFIG_*.
        //
        // See https://github.com/desktop/desktop/issues/18945
        // See https://github.com/git/git/blob/ed155187b429a/config.c#L664
        GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'credential.helper=' 'credential.helper=desktop'`,

        GIT_USER_AGENT: await GitUserAgent(),
        ...sshEnv,
      })

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

export const createCredentialHelperTrampolineHandler: (
  store: AccountsStore
) => TrampolineCommandHandler = (store: Store) => async command => {
  const firstParameter = command.parameters.at(0)
  if (!firstParameter) {
    return undefined
  }

  const { trampolineToken: token } = command
  const input = parseCredential(command.stdin)

  if (__DEV__) {
    debug(
      `${firstParameter}\n${command.stdin
        .replaceAll(/^password=.*$/gm, 'password=***')
        .replaceAll(/^(.*)$/gm, '  $1')
        .trimEnd()}`
    )
  }

  try {
    if (firstParameter === 'get') {
      const cred = await getCredential(input, store, token)
      if (!cred) {
        const endpoint = `${getCredentialUrl(input)}`
        info(`could not find credential for ${endpoint}`)
        setHasRejectedCredentialsForEndpoint(token, endpoint)
      }
      return cred ? formatCredential(cred) : undefined
    } else if (firstParameter === 'store') {
      await storeCredential(input, store, token)
    } else if (firstParameter === 'erase') {
      await eraseCredential(input, store, token)
    }
    return undefined
