### Title
Daemon Debug-Level Logging Bypasses Sensitive-Data Redaction, Exposing Keyring Secrets in Log Files - (File: chia/daemon/server.py)

### Summary
`chia/daemon/server.py` implements a `redact_sensitive_data()` helper that is applied to inbound websocket message logging (`"Received message: ..."`), but several other `self.log.debug(...)` / `self.log.info(...)` calls in the same `WebSocketServer` class log raw dictionaries that were never passed through this redaction function. This is the same bug class as CVE-2024-47083 (Power Platform Terraform Provider): a secret-masking mechanism exists, but coverage is incomplete, so sensitive values can still be persisted to disk/log files at `DEBUG` level.

### Finding Description
`redact_sensitive_data()` is defined in [1](#0-0)  and is used to sanitize the logging of received websocket messages before they are recorded, per the test in [2](#0-1) , which validates that fields like `password`, `private_key`, `secret_value`, `mnemonic`, `passphrase`, `api_key`, and `seed_mnemonic` get redacted in the "Received message" log line.

However, `keyring_status()` builds a response dictionary that includes the user-configured `passphrase_hint` in cleartext and then logs that entire dictionary directly, bypassing `redact_sensitive_data()` entirely: [3](#0-2) 

This is not an isolated occurrence — the project's own CHANGELOG explicitly documents this exact bug class as a known, unresolved issue: DEBUG-level daemon logging can expose the local keyring passphrase to the log file. [4](#0-3) 

Other daemon operations that handle the same class of secret material (`unlock_keyring`, `validate_keyring_passphrase`, `set_keyring_passphrase`) construct local variables named `key`, `current_passphrase`, and `new_passphrase` containing cleartext secrets, per [5](#0-4) . While these specific handlers only log exception text (not the variables themselves) today, the broader pattern in this file is that redaction is applied ad hoc per call site rather than centrally enforced on all outbound/inbound log statements — exactly the "error in the logging code causing secrets to not be properly masked" scenario described in the CVE.

### Impact Explanation
Any local process capable of connecting to the daemon RPC/websocket (a local RPC caller, as scoped) can trigger `keyring_status` (used by the GUI on every daemon connection) and cause the daemon to write the operator's keyring passphrase hint into the log file whenever the daemon is run with `--log-level DEBUG`. If a log file is persisted, shipped to a monitoring system, or accidentally shared for debugging, this can leak information intended to be confidential. Because the redaction function exists but is not uniformly applied, any future daemon RPC handler that logs a raw request/response dict (following the same pattern as `keyring_status`) risks leaking full passphrases, private keys, or mnemonics — not just hints — since the coverage of `redact_sensitive_data()` depends entirely on individual developers remembering to call it at each log site.

### Likelihood Explanation
High likelihood of at least partial exposure: `keyring_status()` is called automatically by the daemon/GUI handshake flow, so the leaking debug log line at [6](#0-5)  fires routinely whenever DEBUG logging is enabled — no attacker action beyond normal daemon usage is required. The project's own changelog confirms this has already manifested as a known issue for the master passphrase itself, indicating the gap is real and has been observed in production use, not merely theoretical.

### Recommendation
- Apply `redact_sensitive_data()` (or an equivalent centralized sanitizer) to every `self.log.debug`/`self.log.info` call in `chia/daemon/server.py` that logs a request or response dictionary, including the `keyring_status()` response at line 516.
- Consider wrapping the logging call sites so that `redact_sensitive_data()` is invoked automatically at the point where any dict-typed payload is passed to the logger (e.g., a custom log filter or a `log_redacted()` wrapper), rather than relying on redaction being manually inserted per call site.
- Remove `passphrase_hint` from the debug-logged dict, or redact it explicitly, and audit `unlock_keyring`, `validate_keyring_passphrase`, and `set_keyring_passphrase` to ensure no code path ever formats the raw `key`/`current_passphrase`/`new_passphrase` values into a log message.
- Update the CHANGELOG "Known Issues" note once fixed, and add a regression test analogous to `test_message_logging_redaction` that specifically covers `keyring_status()`'s debug log line.

### Proof of Concept
1. Start the chia daemon with `--log-level DEBUG` (or equivalent config setting `chia.daemon: DEBUG` in `log_level`).
2. Set a keyring passphrase hint via the `set_keyring_passphrase` RPC command with `passphrase_hint` set to a sensitive value (e.g., part of the actual passphrase, as many users do).
3. From any local client connected via the daemon websocket (no special daemon RPC privilege beyond a valid client cert), trigger the `keyring_status` command (this also happens automatically when the GUI connects).
4. Inspect the daemon log file: the line `Keyring status: {...'passphrase_hint': '<value>'...}` produced by [6](#0-5)  contains the hint in cleartext, unlike the "Received message" log line which is properly redacted by `redact_sensitive_data()`.

```python
def redact_sensitive_data(obj: Any, redaction_triggers: Collection[str] = ("pass", "key", "secret", "mnemonic")) -> Any:
    """Recursively redact sensitive data from nested dictionaries."""
    if isinstance(obj, dict):
        return {
            key: "***<redacted>***"
            if any(trigger.casefold() in key.casefold() for trigger in redaction_triggers)
            else redact_sensitive_data(value, redaction_triggers)
            for key, value in obj.items()
        }
    else:
        return obj
```

```python
    async def unlock_keyring(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        key: str | None = request.get("key", None)
        if type(key) is not str:
            return {"success": False, "error": "missing key"}

        try:
            if Keychain.master_passphrase_is_valid(key, force_reload=True):
                Keychain.set_cached_master_passphrase(key)
                success = True
                # Inform the GUI of keyring status changes
                self.keyring_status_changed(await self.keyring_status(), "wallet_ui")
            else:
                error = "bad passphrase"
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Keyring passphrase validation failed: {e} {tb}")
            error = "validation exception"

        if success and self.run_check_keys_on_unlock:
            try:
                self.log.info("Running check_keys now that the keyring is unlocked")
                check_keys(self.root_path)
                self.run_check_keys_on_unlock = False
            except Exception as e:
                tb = traceback.format_exc()
                self.log.error(f"check_keys failed after unlocking keyring: {e} {tb}")

        response: dict[str, Any] = {"success": success, "error": error}
        return response

    async def set_keyring_passphrase(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        current_passphrase: str | None = None
        new_passphrase: str | None = None
        passphrase_hint: str | None = request.get("passphrase_hint", None)
        save_passphrase: bool = request.get("save_passphrase", False)

        if using_default_passphrase():
            current_passphrase = default_passphrase()

        if Keychain.has_master_passphrase() and not current_passphrase:
            current_passphrase = request.get("current_passphrase", None)
            if type(current_passphrase) is not str:
                return {"success": False, "error": "missing current_passphrase"}

        new_passphrase = request.get("new_passphrase", None)
        if type(new_passphrase) is not str:
            return {"success": False, "error": "missing new_passphrase"}

        if not Keychain.passphrase_meets_requirements(new_passphrase):
            return {"success": False, "error": "passphrase doesn't satisfy requirements"}

        try:
            assert new_passphrase is not None  # mypy, I love you
            Keychain.set_master_passphrase(
                current_passphrase,
                new_passphrase,
                passphrase_hint=passphrase_hint,
                save_passphrase=save_passphrase,
            )
        except KeychainCurrentPassphraseIsInvalid:
            error = "current passphrase is invalid"
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Failed to set keyring passphrase: {e} {tb}")
        else:
            success = True
            # Inform the GUI of keyring status changes
            self.keyring_status_changed(await self.keyring_status(), "wallet_ui")

        response: dict[str, Any] = {"success": success, "error": error}
```
