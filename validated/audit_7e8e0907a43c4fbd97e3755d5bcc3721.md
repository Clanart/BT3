Based on the investigation, the closest structural analog to the `OperatorsRegistry.removeValidators` ordering bug is GitHub Desktop's **discard-selection** flow, which applies a line-number-based patch computed from a `diff` snapshot without ever re-validating that the working-directory file still matches that snapshot before writing to it.

### Title
Stale-diff patch application in `discardChangesFromSelection` can silently corrupt working-directory content - (File: app/src/lib/git/apply.ts)

### Summary
`discardChangesFromSelection` builds a `git apply` patch from a `diff: ITextDiff` object that is captured once (when the diff panel renders) and passed all the way down to the actual git write call with no re-check that the file on disk still matches that diff. Because the patch is applied with `--unidiff-zero` (no context-line verification, pure line-number based), if the underlying file changes between "diff computed" and "discard executed" — the exact same "T1 read, T2 uses stale state to write" ordering problem described in the report — the patch is applied against the wrong lines of the *current* file, silently producing corrupted content instead of failing loudly.

### Finding Description
The write path is:
- UI captures a `diff`/`selection` snapshot and stores it in component state / passes it as a prop (e.g. `app/src/ui/discard-changes/discard-selection-dialog.tsx:113-121`, `app/src/ui/diff/side-by-side-diff.tsx:1590-1607` which explicitly notes it uses "the original diff (from props) instead of the (potentially) expanded one").
- That stale `diff` is forwarded unchanged through `Dispatcher.discardChangesFromSelection` → `AppStore._discardChangesFromSelection` (`app/src/lib/stores/app-store.ts:5723-5733`) → `GitStore.discardChangesFromSelection` → `formatPatchToDiscardChanges` (`app/src/lib/patch-formatter.ts:251-335`) → `git apply --unidiff-zero` (`app/src/lib/git/apply.ts:102-119`).
- `formatPatchToDiscardChanges` builds the patch purely from hunk line offsets recorded in the *old* diff (`hunk.unifiedDiffStart + lineIndex`), with no re-comparison against the file's current content.
- `--unidiff-zero` explicitly disables context-line matching, so `git apply` cannot detect that the target lines have shifted; it will apply the patch at the recorded line numbers regardless of whether that content still matches what the diff was built from.

Notably, the codebase *already has* a pattern for guarding against exactly this kind of staleness on the read side: `updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts:3450-3464`) explicitly re-checks `arrayEquals(changesState.selection.selectedFileIDs, selectedFileIDsBeforeLoad)` before accepting a freshly-loaded diff, specifically because "a different file (or files) could have been selected while we were loading the diff." That same discipline is absent from the *write* path — there is no equivalent check comparing the file's current diff/hash to the diff being discarded before invoking `git apply`. ### Impact Explanation
If the tracked file's content changes between the moment Desktop renders the diff and the moment the user confirms "Discard changes"/"Discard selected lines" (e.g. because a repository-provided git hook such as `post-checkout`/`post-merge` — which Desktop invokes automatically as part of normal checkout/merge/pull operations on an attacker-authored repository — rewrites the file, or because a background refresh/second operation updates the file), the zero-context patch is applied against line offsets that no longer correspond to the intended content. `git apply --unidiff-zero` has no context to detect the mismatch, so it silently rewrites the wrong lines of the file rather than failing. The corrupted file is then whatever the user goes on to `git add`/commit/push, i.e. this is a "silent corruption of what the user commits or pushes" class issue, directly analogous to the operator's "unnoticed" reordering outcome described in the report.

### Likelihood Explanation
The precondition — the file changing underneath an already-computed diff before the discard action is confirmed — is entirely plausible in normal Desktop usage without any unnatural steps: any concurrent Desktop-triggered git operation (hooks, fetch-triggered refresh, another discard/commit) that touches the same file between diff render and discard-click reorders the effective read/write, and none of the intermediate layers (`app-store.ts`, `git-store.ts`, `apply.ts`) re-validate staleness before the destructive `git apply` call — unlike the sibling read-path code that does perform this check.

### Recommendation
Before invoking `git apply` in `discardChangesFromSelection`, re-fetch the current diff for `filePath` (or at minimum compare a content hash/mtime) and abort/re-prompt if it differs from the `diff` passed in, mirroring the staleness guard already implemented in `updateChangesWorkingDirectoryDiff`. Consider also avoiding `--unidiff-zero` in favor of a patch mode that retains context lines so `git apply` can naturally reject mismatched hunks instead of silently rewriting the wrong content.

### Proof of Concept
1. Open a repository in Desktop with a tracked file `notes.txt` containing multiple lines, with local uncommitted modifications.
2. In the Changes diff view, select a hunk/lines to discard — Desktop computes `diff` (`ITextDiff`) and stores it in the dialog's props/state.
3. Before confirming "Discard changes", trigger a repository-invoked hook or a second git operation (e.g. another discard/checkout affecting `notes.txt`) that changes the number/content of lines in `notes.txt` on disk, without Desktop re-rendering/refreshing the discard dialog's `diff` prop.
4. Confirm the discard. `formatPatchToDiscardChanges` builds a patch from the stale hunk line offsets and `git apply --unidiff-zero` applies it to the now-different file content at those same line numbers, silently corrupting unrelated lines instead of failing.
5. The corrupted `notes.txt` is then committed/pushed by the user without any warning from Desktop.
