### Title
Silent exception swallowing in `Offer.__post_init__()` causes unhandled `KeyError` crash when processing malicious/malformed offers - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.__post_init__()` computes and caches per-coin-spend additions via `compute_spend_hints_and_additions()`, but wraps the call in a bare `except Exception: continue` that silently drops any coin spend whose condition parsing fails, without recording a placeholder or otherwise flagging the failure. Downstream consumers (`_get_offered_coins()`, `additions()`, `get_offered_amounts()`, `arbitrage()`, `is_valid()`) assume every coin spend in `self._bundle.coin_spends` has a corresponding entry in `self._additions`, and directly index into it. A coin spend engineered to raise a generic (non-`ValidationError`, non-recognized-`ValueError`) exception inside `compute_spend_hints_and_additions()` is silently absorbed at construction time, but later causes an unhandled `KeyError` the first time offer summary/validity logic is invoked on the same offer.

### Finding Description
`compute_spend_hints_and_additions()` uses a bare `assert rf is not None` on the puzzle-hash argument of a `CREATE_COIN` condition [1](#0-0) . If the argument is not an atom (e.g. a crafted cons-pair instead of a bytes32 puzzle hash), this raises `AssertionError`.

In `Offer.__post_init__()`, this call is guarded only against `ValidationError` (re-raised) and a specific `ValueError` message (`"cost exceeded or below zero"`); every other exception, including `AssertionError`, falls into a bare `except Exception: continue` that skips populating `adds[cs.coin]` for that spend entirely [2](#0-1) .

Because the loop key is `cs.coin` and the exact same list `self._bundle.coin_spends` is iterated again later in `_get_offered_coins()`, which unconditionally indexes `self._additions[parent_spend.coin]` [3](#0-2) , any coin spend whose additions computation silently failed during construction produces a missing dictionary key. The `Offer` object is constructed successfully (no exception surfaces at parse time), but the very first later call that reaches `_get_offered_coins()` — e.g. `get_offered_coins()`, `get_offered_amounts()`, `arbitrage()`, or `is_valid()` — raises an unhandled `KeyError` [4](#0-3) .

These methods are reached from normal, unprivileged offer-processing paths: `TradeManager.respond_to_offer()`/`check_offer_validity()`/`calculate_tx_records_for_offer()` (invoked from the `take_offer`/`check_offer_validity` RPCs) [5](#0-4) , and DataLayer's offer summary/verification path (`DataLayerWallet.get_offer_summary`, `verify_offer`) [6](#0-5) [7](#0-6) . Any of these can be triggered simply by receiving an untrusted, attacker-crafted offer file (bech32-encoded `Offer`) and calling `check_offer_validity`, `get_offer`, or `take_offer` on it — no special privilege beyond being an offer counterparty is required.

### Impact Explanation
This is the same bug class as the reported issue: a function (`getProxyAdmin`) fails to properly propagate/handle an error from an underlying call, letting execution continue in an inconsistent state instead of failing cleanly or succeeding correctly. Here, `Offer.__post_init__()` improperly swallows a broad class of exceptions from `compute_spend_hints_and_additions()`, leaving `self._additions` in an inconsistent state relative to `self._bundle.coin_spends`. The concrete, reachable impact is an unhandled `KeyError` raised deep inside wallet/offer-processing logic when a client (wallet RPC caller or DataLayer node) merely inspects or attempts to validate a maliciously crafted offer — a spend-triggered transaction-processing halt reachable by any offer counterparty, without needing to actually push the transaction to the mempool.

### Likelihood Explanation
Likelihood is high for the crash path: any user of `take_offer`, `check_offer_validity`, or DataLayer's `verify_offer`/`take_offer` RPCs who receives an attacker-supplied offer bech32 string containing a coin spend with a malformed `CREATE_COIN` puzzle-hash argument (a cons-pair instead of an atom) will trigger this. Constructing such an offer only requires crafting an arbitrary CLVM puzzle/solution pair as one of the offer's coin spends — no signature over real funds or special access is needed, since the crash occurs purely from condition-list parsing before any full-node interaction.

### Recommendation
- In `Offer.__post_init__()`, do not silently `continue` on arbitrary exceptions from `compute_spend_hints_and_additions()`; either re-raise as a `ValidationError`/`ValueError` (rejecting the malformed offer at construction time, consistent with how `ValidationError` and the cost-exceeded `ValueError` are already handled), or explicitly track which coins failed and have every downstream consumer (`_get_offered_coins()`, `additions()`, etc.) use `.get()`/default handling instead of direct indexing.
- Replace the internal `assert rf is not None` in `compute_hints.py` with an explicit, typed validation error so failure modes are deterministic and cannot be conflated with a generic `Exception` catch-all.
- Add regression tests constructing an `Offer` whose coin spend puzzle output includes a malformed `CREATE_COIN` condition, asserting that offer construction/validation raises a clean, typed error rather than crashing downstream with `KeyError`.

### Proof of Concept
1. Build a `CoinSpend` whose puzzle reveal, when run, returns a condition list containing `(CREATE_COIN <cons-pair> <amount>)` where the second argument (`rf`) is a cons cell (e.g., `(1 . 2)`) instead of a 32-byte atom.
2. Wrap this spend, plus a legitimate settlement-payment spend, into a `WalletSpendBundle`, and construct an `Offer(requested_payments, bundle, driver_dict)`.
   - During `__post_init__`, `compute_spend_hints_and_additions()` raises `AssertionError` on `assert rf is not None`.
   - The `except Exception: continue` swallows it; `Offer` construction succeeds silently, but `self._additions` is missing the entry for that spend's coin.
3. Call `offer.get_offered_coins()` (or `offer.is_valid()`, `offer.arbitrage()`, or route the offer through `TradeManager.check_offer_validity()` / DataLayer's `verify_offer`).
   - `_get_offered_coins()` executes `additions: list[Coin] = self._additions[parent_spend.coin]` for the malformed spend's coin, which is not present in the dict, raising an unhandled `KeyError` that propagates out of the RPC handler.
