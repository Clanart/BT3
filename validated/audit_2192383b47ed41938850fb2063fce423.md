### Title
Copilot conflict resolution always writes resolved files as UTF-8, silently corrupting non-UTF-8-encoded files that get committed - ([File: app/src/lib/stores/app-store.ts])

### Summary
Desktop's "Resolve with Copilot" merge-conflict feature reads a conflicted file's on-disk content, sends it to the Copilot model, splices the model's per-hunk output back into the original text, and then writes the reassembled result back to disk with a hard-coded `'utf8'` encoding — regardless of what encoding the file actually uses. Just as the Illuminate report describes external inputs (Swivel/Pendle/Notional PTs) being treated as fungible 1:1 with the underlying asset despite having different "decimal" representations, Desktop treats every conflicted file's bytes as if they were already UTF-8 text and re-encodes them as UTF-8 on write, without ever checking or preserving the file's real encoding.

### Finding Description
The write-back path is `_applyCopilotConflictResolutions`, which iterates over the model's resolutions and writes each one directly to disk: [1](#0-0) 

Notice line 7258: `await writeFile(absolutePath, resolution.resolvedContent, 'utf8')`. The `resolvedContent` string is produced upstream by `reassembleResolvedFile`, which builds the final output by splitting the *original on-disk file content* into lines and splicing in the LLM's hunk resolutions: [2](#0-1) 

The `rawContent` that seeds this reassembly is captured earlier when gathering conflict context (`copilot-conflict-context.ts`) and is passed through the whole system as a JS `string`. Once file bytes have been decoded into a JS string anywhere in this pipeline (context gathering → prompt building → model round-trip → reassembly), Node has already interpreted them under some encoding assumption; writing back with an explicit, unconditional `'utf8'` encoding discards whatever the original encoding was. For any file that is not actually UTF-8 (UTF-16 with BOM, Latin-1/Windows-1252, Shift-JIS, etc. — all valid, common encodings for legacy or localized source/config files that end up in Git conflicts), the round trip corrupts non-ASCII bytes: characters silently become mangled or replaced (e.g., U+FFFD replacement characters), because the original byte sequence is never faithfully preserved through the decode → LLM  → re-encode pipeline.

This mirrors the Illuminate bug's root cause: the code assumes an external representation (a foreign PT's decimals / a file's non-UTF-8 bytes) is directly interchangeable with the canonical representation (Illuminate's underlying decimals / UTF-8 text) with no conversion or validation step, and blindly performs a 1:1 substitution.

### Impact Explanation
This falls squarely under "silent corruption of what the user commits or pushes." The user clicks "Continue Merge" trusting that Copilot only touched the conflicted hunks; instead, the entire file's non-ASCII content can be silently mangled at write time and then `git add`-ed and eventually committed: [3](#0-2) 

Because the corruption happens transparently as part of the normal "accept Copilot's resolution" flow, the user has no indication anything went wrong — the diff/summary UI shows the model's resolved hunks, not a warning about encoding loss for the untouched parts of the file. Repositories with non-UTF-8-encoded source files (common on Windows, in localized codebases, or with legacy resource files) can end up with corrupted commits pushed to shared history.

### Likelihood Explanation
This is triggered by ordinary, unprivileged use of a supported feature (Copilot conflict resolution) on any file whose content is not strictly UTF-8, with no attacker interaction needed beyond having such a file conflict during a merge/rebase/cherry-pick — a routine occurrence in real repositories. No special permissions, local file-system tricks, or malicious remotes are required; it's an inherent property of the write path always using `'utf8'` regardless of the file's real encoding.

### Recommendation
Detect and preserve the original file's encoding (or at minimum its raw byte buffer) through the entire conflict-resolution pipeline instead of hard-coding UTF-8:
- Read the conflicted file's raw bytes and encoding metadata once (similar to how `getBlobContents`/`coerceToBuffer` already support buffer-based reads elsewhere in the codebase, e.g. `app/src/lib/git/show.ts`).
- When splicing hunk resolutions back into the original content, operate on the detected encoding, and write the file back with the same encoding using `writeFile(absolutePath, resolvedBuffer)` rather than an explicit `'utf8'` string encoding.
- If encoding cannot be reliably detected, at least warn the user and refuse to silently reinterpret bytes as UTF-8, rather than performing a lossy 1:1 write.

### Proof of Concept
1. In a repository, create a file `legacy.txt` encoded in Windows-1252 (or UTF-16) containing extended characters (e.g., `é`, `ñ`, `“curly quotes”`) that are not valid/identical in UTF-8 byte sequences.
2. Create a merge conflict touching a small region of `legacy.txt` on two branches, leaving the rest of the file (with the non-UTF-8 bytes) untouched.
3. Trigger "Resolve with Copilot" from the manual conflicts dialog (`app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`, `onContinue` → `dispatcher.applyCopilotConflictResolutions`).
4. Observe that `_applyCopilotConflictResolutions` calls `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` [4](#0-3) .
5. Inspect `legacy.txt` on disk after the write: the previously Windows-1252/UTF-16-encoded bytes for extended characters are corrupted/replaced, and this corrupted content is then `git add`-ed and committed as part of "Continue Merge."

I was unable to fully verify the exact encoding-detection logic (if any) used when `copilot-conflict-context.ts` first reads `rawContent` from disk, since the index did not return the specific `readFile` call site content; a Devin session with full repository access would be needed to confirm whether any encoding sniffing occurs earlier in the pipeline before the string is passed through to the `reassembleResolvedFile` → `writeFile(..., 'utf8')` path described above.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
