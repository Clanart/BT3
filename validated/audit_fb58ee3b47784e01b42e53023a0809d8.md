### Title
Symlink path-traversal in `discardChanges` allows a malicious repository to delete/move arbitrary files outside the working directory - ([File: app/src/lib/stores/git-store.ts])

### Summary
`GitStore.discardChanges()` resolves each file path reported by `git status` using a raw `Path.resolve`/`Path.join` against the repository root, with no check that the resulting real path stays inside the repository. The codebase already has a hardened helper, `resolveWithin` (`app/src/lib/path.ts`), that explicitly guards against exactly this kind of symlink escape and is used elsewhere (`app/src/lib/copilot-conflict-context.ts`), but it is not applied in `discardChanges`. A malicious/attacker-controlled repository can commit a symlink that points outside the working directory; once checked out, files "inside" that symlinked directory resolve to paths on the user's disk outside the repo. When the user (or Desktop itself, e.g. via "Discard All Changes"/stash flows) discards changes touching those paths, Desktop will move or permanently delete files outside the repository boundary.

### Finding Description
`discardChanges` iterates over `WorkingDirectoryFileChange` entries produced by `getStatus()` (`app/src/lib/git/status.ts`) and, for each file, computes the on-disk path with: [1](#0-0) 

```ts

  if (moveToTrash) {
    try {

        Path.resolve(this.repository.path, file.path)

    } catch (e) {

      if (file.status.kind === AppFileStatusKind.Untracked) {

      }
    }
  } else if (moveToTrash === false) {
    if (file.status.kind === AppFileStatusKind.Untracked) {
      await rm(Path.join(this.repository.path, file.path))
    }
  }

```

`file.path` comes directly from `git status --porcelain=2` parsing (`buildStatusMap` in `app/src/lib/git/status.ts`). Git happily reports untracked/modified files that live underneath a symlinked directory that is itself part of the working tree (a symlink can be committed to a repository and checked out by `git clone`/`git checkout`). `Path.resolve`/`Path.join` do not dereference symlinks, but the actual filesystem operations (`shell.moveItemToTrash`, `rm`) do follow them at the OS level, so the effective target of the delete/move can be anywhere on disk that the symlink points to, entirely outside `repository.path`.

The project has already recognized and centrally fixed this exact class of bug once — `resolveWithin()` in `app/src/lib/path.ts` performs `realpath` on both the root and the candidate path and rejects any result that escapes the root: [2](#0-1) 

and it is used to guard file reads in the Copilot conflict-resolution code path: [3](#0-2) 

But `discardChanges` in `git-store.ts` — a much older and more security-sensitive code path that performs destructive filesystem writes/deletes rather than reads — was never updated to use `resolveWithin`. This is analogous to the report's underlying theme: a security-relevant invariant (paths must stay inside the repo) is enforced ad hoc in some places and implicitly assumed/unchecked in others, and the implicit trust in `file.path` throughout `discardChanges` (and its callers `AppStore._discardChanges`/`_discardChangesFromSelection`) makes the invariant easy to violate without anyone noticing, exactly as flagged in the original report about implicit, unchecked state/derived values propagating unchecked through many call sites.

### Impact Explanation
An attacker who controls a cloned/fetched repository (e.g. a public repo the victim clones, or a fork/PR checked out in Desktop) can commit a symlink such as `evil -> /home/victim` (or, on Windows, a junction/symlink to a sensitive directory) plus an "untracked" or "modified" file path underneath that symlink name. When the victim opens Desktop's Changes view and clicks "Discard changes" (or "Discard All Changes"), Desktop will call `shell.moveItemToTrash` (or `rm`) on a path that traverses through the symlink, deleting or moving files that live entirely outside the cloned repository — e.g. arbitrary files in the user's home directory, SSH keys, other project files, etc. This is a file write/delete outside the repository triggered purely by content of an attacker-controlled repository, matching the "attacker controls a cloned/fetched repository ... resulting in file write/read outside the repo" impact category.

### Likelihood Explanation
Requires no special user action beyond normal Desktop usage: clone/open an attacker's repository and use the standard "Discard Changes" feature (a very common, everyday action, and one that Desktop's own UI actively prompts for on many operations, e.g. stash/pop-related flows or the "Discard All Changes" banner). No admin rights, no pre-existing malware, and no unusual steps are required — the victim simply needs to discard changes in a repository that contains a malicious symlink. The existing `resolveWithin` guard proves the team is aware of this class of bug and considers it worth defending against elsewhere, but the guard is not applied in `discardChanges`, so nothing in the current code stops this path.

### Recommendation
Apply the existing `resolveWithin` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate) helper from `app/src/lib/path.ts` to every path derived from git status output before performing filesystem mutations in `discardChanges` (and `discardChangesFromSelection`), rejecting/skipping any file whose resolved real path escapes `repository.path`. Consider also detecting symlinked directories introduced within the working tree during status parsing and refusing to treat paths beneath them as safe for destructive operations, consistent with the guard already used in the Copilot conflict-resolution code path.

### Proof of Concept
1. Attacker creates a repository containing:
   - a symlink `link` → `/home/victim` (committed as a symlink blob), and
   - after checkout, creates/leaves an untracked file appearing as `link/some-file` in `git status` (or simply relies on existing content under the symlinked target being reported by `git status --untracked-files=all`).
2. Victim clones this repository with GitHub Desktop and opens it.
3. Desktop's Changes view shows `link/some-file` as an untracked/modified change.
4. Victim clicks "Discard changes" for that file (or "Discard All Changes").
5. `GitStore.discardChanges()` computes `Path.resolve(repository.path, 'link/some-file')`, which the OS resolves through the symlink to `/home/victim/some-file`, and calls `shell.moveItemToTrash`/`rm` on it — deleting or trashing a file entirely outside the cloned repository.

Note: I was not able to execute this PoC in a live Desktop instance (no filesystem/terminal access in this environment); the analysis is based on static review of `discardChanges` in `app/src/lib/stores/git-store.ts`, the status-parsing code in `app/src/lib/git/status.ts`, and the sibling safe-path helper in `app/src/lib/path.ts`. A full confirmation would require running Desktop against a crafted repository with a symlink, ideally in a Devin session with filesystem/terminal access.
