### Title
`Bitcoin::get_outputs` applies the last-scanned transaction's origin and InInstruction data to every output accumulated from earlier transactions in the same block - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` iterates over `block.txdata[1 ..]`, pushing every scanned `Output` into a single `outputs` vector declared *outside* the per-transaction loop. After scanning each transaction, it then writes that transaction's `presumed_origin` (derived from `tx.input[0]`) and `data` (from `extract_serai_data(tx)`) onto **all** accumulated outputs — including outputs belonging to earlier, unrelated transactions. This is the same class of bug as the report: a per-position check/assignment is applied uniformly across a sequence, so the context of a later item incorrectly overwrites the attributes of earlier items.

### Finding Description
In `processor/src/networks/bitcoin.rs` lines 686-739:

```rust
let mut outputs = vec![];
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) {
    ...
    outputs.push(output);
  }
  if outputs.is_empty() { continue; }
  let presumed_origin = { ... tx.input[0] ... };
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs {            // <-- iterates ALL txs' outputs, not just `tx`'s
    if output.kind == OutputType::External {
      output.data.clone_from(&data);      // overwritten every iteration
    }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
```

Two compounding defects follow:

1. `outputs` is never scoped/cleared per transaction. The post-processing loop `for output in &mut outputs` touches outputs from *every* transaction scanned so far, so each subsequent transaction overwrites the `data` and `presumed_origin` of outputs produced by earlier transactions. The final state of every output in the block reflects only the **last** transaction that triggered the block (any transaction after at least one output exists — the `if outputs.is_empty()` guard only skips while the accumulator is empty).
2. The `continue` guard checks the accumulator, not the current transaction's results. A transaction that produced zero Serai outputs still triggers the origin/data overwrite for all previously collected outputs.

`output.data` is the `InInstruction` payload extracted from `OP_RETURN` (`extract_serai_data`), which is what tells Serai which account/action a deposit maps to. `presumed_origin` feeds `Output::presumed_origin()` used for attribution/refunds (`Output` write/read at lines 124-165 confirms these fields are persisted and consumed downstream).

### Impact Explanation
Any user depositing to a Serai Bitcoin address in a block containing more than one transaction-after-the-coinbase can have their deposit's `InInstruction` data replaced by bytes from an unrelated transaction. An unprivileged attacker only needs to get *any* transaction mined in the same block (nothing about ordering is required — any position after the victim's works, and even before works if other outputs exist): the victim's `External` output will carry the attacker's `OP_RETURN` data instead of their own. This can redirect a deposit to an attacker-chosen Serai address/instruction, or clobber it with empty/malformed data making the funds unspendable or mis-credited — i.e., funds reported received under an instruction the depositor never authored. `presumed_origin` is likewise corrupted for every output, breaking refund/attribution.

### Likelihood Explanation
Triggering requires only that a block contains more than one transaction where at least one produces Serai outputs — the normal case once the protocol processes deposits alongside arbitrary Bitcoin traffic. No control over miners, ordering, or validators is needed; the attacker broadcasts an ordinary public transaction (public input, fully in scope per `networks/bitcoin/src` reachability rules).

### Recommendation
Scope the post-processing to the current transaction's outputs: collect `scanner.scan_transaction(tx)` results into a per-transaction vector, apply `presumed_origin`/`data` to that vector only, then `extend` the block-level `outputs`. Equivalently, move `let mut outputs = vec![];` inside the `for tx` loop (and track whether *this* tx produced outputs for the `continue` guard), appending finished outputs to the result list.

### Proof of Concept
Consider a block with `txdata[1] = victim_tx` (pays 0.1 BTC to Serai's `External` address with `OP_RETURN` InInstruction crediting `serai_victim`) and `txdata[2] = attacker_tx` (any transaction the attacker broadcasts; optionally with its own `OP_RETURN` data `D_a` crediting `serai_attacker`).

- Iteration 1: `scan_transaction(victim_tx)` pushes `Output { data: vec![], presumed_origin: None, .. }` into `outputs`. Post-loop writes `data = D_v`, `presumed_origin = victim_addr` onto `outputs[0]`.
- Iteration 2: `attacker_tx` may produce zero scanned outputs — `outputs.is_empty()` is false (it holds the victim's output), so the guard does not `continue`. The post-loop again iterates `&mut outputs`, overwriting `outputs[0].data` with `D_a` and `presumed_origin` with `attacker_tx.input[0]`'s origin.

Result: the processor observes a 0.1 BTC output whose `data()` is the attacker's instruction — the victim's deposit is credited to `serai_attacker` (or dropped if `D_a` is empty/invalid), while `assert_eq!(output.tx_id(), tx.id())` still passes because `tx_id` is derived from the stored outpoint, not the corrupted fields. The fix is a one-line scoping change; the corruption applies to every earlier output per triggering transaction. [1](#0-0)
