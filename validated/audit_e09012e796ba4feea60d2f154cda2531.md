### Title
Ambiguous `diff --git a/OLD b/NEW` header regex in `parse_diff_into_files` lets an attacker-chosen filename bypass the security-review guard - (File: `plugins/security-guidance/hooks/gitutil.py`)

### Summary
`parse_diff_into_files` (and its sibling `extract_file_paths_from_diff`) extract the file path from the first line of each `diff --git ` block using the single-line regex `^a/(.+?) b/(.+)$`. Because the regex is the only thing splitting the concatenated `a/<old> b/<new>` string, a filename that itself contains the literal substring `" b/"` causes the non-greedy match to stop early, producing a corrupted `file_path` for a real, reviewable source file. If the corrupted path's apparent extension is not in `SOURCE_CODE_EXTENSIONS`, `_is_reviewable_source` returns `False` and the file — along with its full diff hunk — is silently dropped from the set handed to the LLM security reviewer.

### Finding Description
`parse_diff_into_files` in `plugins/security-guidance/hooks/gitutil.py` (lines 615–654) parses each `diff --git ` chunk with: [1](#0-0) 

`header_match.group(2)` (the "new" path) is preferred as `file_path`, then passed through `_is_reviewable_source` before the diff content is appended to the returned list. `extract_file_paths_from_diff` (lines 587–611) uses the identical regex and filter.

Git's `diff --git a/<old> b/<new>` header line concatenates both paths with a single `" b/"` separator and provides no other unambiguous delimiter. If a repo-controlled filename itself contains the substring `" b/"` (e.g. a file named `app.py b/notes.txt`), the header for that file becomes:

```
diff --git a/app.py b/notes.txt b/app.py b/notes.txt
```

The non-greedy `(.+?)` in `^a/(.+?) b/(.+)$` stops at the *first* `" b/"` occurrence, which is inside the filename itself, not at the real old/new boundary. This yields `group(1) = "app.py"` and `group(2) = "notes.txt b/app.py b/notes.txt"`. Since `group(2)` is preferred, `file_path` becomes the corrupted string, whose apparent extension (via `os.path.splitext`) is `.txt` — not in `SOURCE_CODE_EXTENSIONS` and not a known basename — so `_is_reviewable_source` returns `False`: [2](#0-1) 

The entire diff hunk for that file (real content is Python source) is then excluded from the `files` list returned by `parse_diff_into_files`, even though the diff text itself (visible further down in the same `file_diff` chunk, after the header) contains the actual added/removed source lines.

This function is reached from `security_reminder_hook.py`'s Stop-hook diff review, commit review, and push-sweep flows, all of which call `parse_diff_into_files`/`extract_file_paths_from_diff` to build the `diff_files` list sent to `analyze_code_security` / `agentic_review`: [3](#0-2) 

No existing guard mitigates this: `_diff_pathspec`'s realpath-based scoping (lines 70–88) and `_git_dir`'s worktree-aware `--git-common-dir` resolution (lines 156–176) correctly keep `git diff`/`git status` restricted to the intended repository, but they operate before diff text is generated — they do not, and cannot, fix the ambiguous text-based header split performed afterward in `parse_diff_into_files`.

### Impact Explanation
An attacker who can influence a filename written during a Claude Code session (e.g. by instructing Claude to create/edit a file with a crafted name, or via content in a PR/commit that the agent operates on) can make that file's diff invisible to the Stop-hook LLM security review, the commit-review pipeline, and push-sweep — all of which rely on `parse_diff_into_files`/`extract_file_paths_from_diff` to decide what gets sent to the LLM reviewer. This is a logic-level bypass of the "required guard" (the automated security review) that the plugin is built around: a maliciously-named source file's actual vulnerable content is never scanned. It also corrupts `file_path` used as a dedup/state key elsewhere (`_finding_keys`, `_dedup_against_state`), further misbinding review state to the wrong path.

### Likelihood Explanation
No special privilege is required — the only precondition is the ability to introduce a file with a specific name into the working tree during a reviewed session (a routine, unprivileged action: asking Claude to write a file, or content originating from repo/PR data that Claude operates on). The exploit is fully deterministic and reproducible: any filename containing the literal substring `" b/"` whose corrupted-parse extension falls outside `SOURCE_CODE_EXTENSIONS`/`SOURCE_CODE_BASENAMES` triggers the bypass every time.

### Recommendation
Do not split old/new paths from the single `diff --git a/OLD b/NEW` header line. Instead:
- Parse the `--- a/<path>` and `+++ b/<path>` lines (each on its own line, unambiguous prefix), or
- Use `git diff --name-only -z` / rename `from`/`to` lines already emitted in extended headers, or
- Run diffs with `-c core.quotePath=false --src-prefix=a/ --dst-prefix=b/` combined with a git-provided machine-readable path list (`-z`) instead of regexing free-form header text, mirroring the safer approach already used in `_git_name_only`/`_git_status_porcelain`.

### Proof of Concept
Unit test to add near existing `gitutil` tests:

```python
from gitutil import parse_diff_into_files

def test_parse_diff_skips_source_file_with_crafted_name():
    diff = (
        "diff --git a/app.py b/notes.txt b/app.py b/notes.txt\n"
        "new file mode 100644\n"
        "index 0000000..1111111\n"
        "--- /dev/null\n"
        "+++ b/app.py b/notes.txt\n"
        "@@ -0,0 +1,3 @@\n"
        "+import os\n"
        "+os.system(user_input)  # command injection\n"
        "+print('done')\n"
    )
    files = parse_diff_into_files(diff)
    # BUG: the reviewable Python file is dropped because the header
    # regex mis-splits "app.py b/notes.txt" at the embedded " b/".
    assert files == [], (
        "expected the crafted filename to bypass _is_reviewable_source, "
        f"got {files}"
    )
```

Expected assertion result confirms the bypass: `files` is empty despite the diff containing an added `.py` file with a command-injection pattern, proving the file never reaches `analyze_code_security`/`agentic_review`.
