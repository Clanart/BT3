### Title
Escrow release/refund reverts entirely when any single output token blocks the beneficiary, permanently locking all escrowed assets - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` releases every escrowed token for an order commitment to a single beneficiary in one all-or-nothing loop. If any one of the order's input tokens is (or becomes) a token that reverts transfers to that specific beneficiary, the whole withdrawal reverts — including release of the other, non-malicious escrowed tokens and the accumulated protocol/relayer fee — with no partial-withdrawal or retry-per-token fallback. This mirrors the C4 finding: a party who controls which tokens go into the batch (the order creator picking `order.inputs`) can grief a specific counterparty (the filler/beneficiary) once their address is known, permanently freezing their legitimate escrowed funds.

### Finding Description
`_withdraw` iterates over `body.tokens` (which for `RedeemEscrow` == `order.inputs`, chosen entirely by the order creator at order-creation time) and does an unconditional `IERC20(token).safeTransfer(beneficiary, amount)` for each entry inside a single loop, in a single transaction: [1](#0-0) 

Order creation lets the order creator choose an arbitrary set of `order.inputs` tokens/amounts to escrow (there is no allowlist enforced at this layer), and the beneficiary of the eventual `RedeemEscrow` withdrawal is the filler's address (`msg.sender` at fill time), which becomes fully known to anyone observing the fill transaction on-chain, exactly as in the referenced report where the receipt owner is discoverable before withdrawal: [2](#0-1) 

Because `_withdraw` uses `SafeERC20.safeTransfer`, which reverts the entire call if the token's `transfer` reverts (e.g. a blocklist/pausable/fee-token variant configured to block a specific address), a single malicious or mutable token among `order.inputs` is enough to make the whole `withdraw` (and hence release of every other legitimate token plus the accrued transaction fee) permanently unexecutable for that beneficiary — since the beneficiary and token set for a given commitment are fixed inputs baked into the order/commitment and cannot be changed post-hoc.

This is the same broken invariant as the C4 report: a single-recipient batch operation is structured so that any one hostile/blocking asset in the batch can indefinitely block redemption of everything else owed to that recipient, with no mechanism to skip the bad leg or retry per-asset.

### Impact Explanation
This causes permanent loss of access to legitimate escrowed funds and accrued relayer/protocol fees for the targeted beneficiary (filler or refund recipient), for that specific order commitment — an unauthorized loss/lock of funds that matches the bounty's "stealing or loss of funds" / "logic attacks" category. Because `_orders[commitment][token]` bookkeeping and `_filled[commitment]` finalization state changes happen inside the same reverting transaction, there is no way to salvage the non-poisoned tokens or the transaction fee for that commitment — they remain stuck in the contract indefinitely.

### Likelihood Explanation
The attack requires no privileged role, relayer, prover, or governance action — an ordinary order creator can pick any ERC20 address (including a token they control or a mutable/blocklist-capable token) as one of `order.inputs`. The beneficiary/filler address is publicly visible once the order is filled (before the `RedeemEscrow` request settles), giving the attacker a window to target that specific address. This is directly analogous to, and as practically exploitable as, the original C4 finding, which was confirmed by the sponsor.

### Recommendation
Avoid all-or-nothing multi-asset release: transfer each token independently with per-token try/catch (or low-level `call` with success tracked per index) instead of a single reverting loop, marking each token as released once its transfer succeeds and allowing the order to remain partially redeemable; expose a per-token retry/claim entrypoint so a griefed token doesn't block release of the rest. Alternatively, provide an emergency/administrative sweep path that lets the beneficiary claim non-poisoned assets and fees even if one token transfer permanently fails.

### Proof of Concept
1. Order creator constructs a cross-chain order with `order.inputs = [LEGIT_TOKEN (large value), EVIL_TOKEN (small amount)]`, where `EVIL_TOKEN` is an ERC20 whose owner can later block `transfer` to specific addresses (or is deliberately deployed to always revert for a hardcoded address once "configured").
2. A filler calls `_fillCrossChain`, becoming `msg.sender`/beneficiary and revealing their address publicly in the fill transaction and `OrderFilled` event: [2](#0-1) 
3. The order creator (who deployed/controls `EVIL_TOKEN`) sees the filler's address and configures `EVIL_TOKEN` to revert transfers to that address.
4. When the `RedeemEscrow` post request is processed and `_withdraw` is invoked with `body.tokens = order.inputs` and `beneficiary = filler`, the loop's `safeTransfer` call for `EVIL_TOKEN` reverts, reverting the entire `_withdraw` call: [3](#0-2) 
5. The filler can never retrieve `LEGIT_TOKEN` or the accumulated transaction fee for this commitment, since every retry hits the same revert on `EVIL_TOKEN`.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
