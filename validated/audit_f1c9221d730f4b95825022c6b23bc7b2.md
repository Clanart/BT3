### Title
Unauthenticated `ReceivedOutput` permits signing a spend of an unrelated group-controlled UTXO - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/Annirich/serai--005/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary
`ReceivedOutput::read` accepts an offset, `TxOut`, and outpoint without authenticating that the submitter is entitled to spend that output. [1](#0-0)  `SignableTransaction::new` then converts those caller-controlled fields into transaction inputs, while `multisig` only verifies that the supplied output script corresponds to the threshold key and offset. [2](#0-1) [3](#0-2)  An attacker who can submit transaction data for signing can therefore select any confirmed UTXO controlled by the group key and specify a payment to themselves, analogous to withdrawing marketplace assets belonging to another user.

### Finding Description
The serialized `ReceivedOutput` format has no MAC, account binding, spend authorization, or proof that the requester owns the represented output; it is only `offset || TxOut || OutPoint`. [4](#0-3)  During transaction construction, the attacker-controlled outpoint becomes a `TxIn`, and the attacker-controlled payments become transaction outputs. [5](#0-4)  The only ownership check performed before creating the FROST signing machines is that `p2tr_script_buf(keys.offset(offset).group_key())` equals the supplied `script_pubkey`; this proves the threshold group can spend the output, not that the requester may spend it. [6](#0-5)  The signing path then commits to all supplied prevouts and produces the Taproot witness needed to spend the selected UTXO. [7](#0-6) [8](#0-7) 

### Impact Explanation
A successful request produces a valid threshold-signed Bitcoin transaction sending the selected group-controlled UTXO to attacker-chosen destinations. [9](#0-8) [8](#0-7)  For a base-address output, the attacker can use offset zero; the public blockchain supplies the outpoint and exact `TxOut`, so no private key material or malformed signature is needed. [10](#0-9) [11](#0-10)  This is a direct loss of funds when caller-supplied transaction data can reach the signing machines.

### Likelihood Explanation
The attack requires a reachable path that accepts serialized `ReceivedOutput` data or caller-constructed `SignableTransaction` inputs and causes validators to sign them, which is the intended public-input boundary for this API. [1](#0-0) [12](#0-11)  It does not require controlling a validator, learning a key share, creating an invalid prevout, or bypassing consensus because the selected UTXO genuinely belongs to the threshold key. [3](#0-2)  The practical severity is Medium where signing requests are otherwise policy-gated, and High if unauthenticated users can directly submit spend transactions.

### Recommendation
Do not treat a scan result or deserialized `ReceivedOutput` as authorization to spend it. Signing requests should reference an internally stored, scanner-generated output identifier and an authenticated withdrawal record or plan, rather than accepting attacker-controlled `offset`, `TxOut`, and `OutPoint` fields. [1](#0-0) [12](#0-11)  Before signing, validators should resolve the outpoint against trusted chain state, compare the full `TxOut`, and verify a separately authenticated requester entitlement or payment intent; script-key equivalence alone is insufficient. [3](#0-2)

```rust
// `victim_outpoint` and `victim_txout` are public blockchain data for a UTXO
// paying the threshold group's base Taproot script.
let mut encoded = Scalar::ZERO.to_bytes().to_vec();
encoded.extend(bitcoin::consensus::serialize(&victim_txout));
encoded.extend(bitcoin::consensus::serialize(&victim_outpoint));

let input = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();

let spend = SignableTransaction::new(
  vec![input],
  &[(attacker_script_pubkey, victim_txout.value.to_sat() - fee)],
  None,
  None,
  fee_rate,
).unwrap();

// On each validator:
let machine = spend.clone().multisig(&validator_threshold_keys).unwrap();
```

The script check in `multisig` succeeds because the supplied offset and `TxOut` describe the real group-controlled prevout, while the attacker-controlled payment destination is already embedded in the transaction.
