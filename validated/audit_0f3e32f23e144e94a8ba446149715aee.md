### Title
`updateEndRemainingAllocation()` is publicly callable and re-snapshots after the first claim, letting an attacker inflate their bonus share and drain funds owed to other claimants - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is a `public` function with no one-shot guard of its own; it simply overwrites `totalEndRemainingAllocation` with the current `totalRemainingAllocation` every time it is called after `periodsEndTime[4]`. `claim()` only invokes it conditionally (`if (totalEndRemainingAllocation == 0)`), so the *internal* auto-snapshot is effectively one-shot, but the *public* entrypoint is not. Any unprivileged actor can call `updateEndRemainingAllocation()` directly after other users have already claimed (which shrinks `totalRemainingAllocation`), re-snapshotting a smaller `totalEndRemainingAllocation` and inflating their own bonus share in `getBonusAmount()`, at the expense of users who have not yet claimed.

### Finding Description
`getBonusAmount()` computes each user's bonus as: [1](#0-0) 
`totalEndRemainingAllocation` is meant to be a fixed snapshot of `totalRemainingAllocation` taken exactly once, at the moment `block.timestamp` first reaches `periodsEndTime[4]`, so that the bonus pool (`totalBonus`) is fairly split among all users who had not yet claimed at that moment.

However, `updateEndRemainingAllocation()` itself has no protection against being called more than once: [2](#0-1) 
It is `public`, so anyone can call it directly, at any time after `periodsEndTime[4]`, and it will unconditionally overwrite `totalEndRemainingAllocation = totalRemainingAllocation` with whatever the *current* value is - not just the first-observed value.

`claim()` only relies on the `totalEndRemainingAllocation == 0` guard to decide whether to auto-snapshot: [3](#0-2) 
This guard protects the *internal* call inside `claim()` from re-triggering once a nonzero value exists, but it does not stop anyone from calling the public `updateEndRemainingAllocation()` directly, which has no such guard and will happily overwrite an already-nonzero `totalEndRemainingAllocation`.

Exploit flow, starting right after `block.timestamp` passes `periodsEndTime[4]` with no claims yet (`totalEndRemainingAllocation == 0`):
1. A legitimate user (or the attacker's own decoy tx) calls `claim()`. Since `totalEndRemainingAllocation == 0`, it snapshots `totalEndRemainingAllocation = totalRemainingAllocation` (full remaining pool, e.g. including allocations of users A, B, C). The caller's allocation is then zeroed and subtracted from `totalRemainingAllocation` at line 164.
2. Attacker calls `updateEndRemainingAllocation()` directly (public, no access control, no `nonReentrant`). Since `block.timestamp >= periodsEndTime[4]` still holds, it recomputes `totalEndRemainingAllocation = totalRemainingAllocation`, now a smaller number because step 1 already reduced it.
3. Attacker calls `claim()`. `getBonusAmount()` now divides by the smaller `totalEndRemainingAllocation`, inflating the attacker's bonus proportionally.
4. Because `totalBonus` was fixed by the earlier forfeitures and is not adjusted for this re-snapshot, the sum of bonuses distributable across all remaining unclaimed users can exceed the actual `totalBonus` pool that was intended to be shared, and can exceed the token balance held in the contract that is earmarked for other users' un-claimed principal allocations. Later, honest users who still hold unclaimed `allocations[user]` can have their `claim()` revert with `InsufficientBalance()` (line 160) because the attacker already extracted more tokens than the contract's remaining balance can safely cover, or they receive less than their entitled principal+bonus.

This violates the invariant that the automatic path (`claim()`'s internal guarded call) and the manual/public path (`updateEndRemainingAllocation()` called directly) must enforce the same one-shot constraint on `totalEndRemainingAllocation`.

### Impact Explanation
Direct theft of user funds: the attacker manipulates the shared bonus-pool denominator to extract a disproportionately large share of `aidropToken` relative to their true entitlement, at the direct expense of other allocation holders who have not yet claimed and whose subsequent `claim()` can revert (`InsufficientBalance`) or return less than owed. This matches "Critical - Direct theft of user funds" since real ERC20 value is redirected from legitimate claimants to the attacker.

### Likelihood Explanation
- No privileged role required: `updateEndRemainingAllocation()` is `public` with zero access control.
- Only precondition is `block.timestamp >= periodsEndTime[4]` (a natural point in the airdrop lifecycle) and at least one prior claim having already reduced `totalRemainingAllocation` from its value at the moment of the first snapshot.
- No capital required beyond gas and being an allocation holder large enough to matter.
- Fully repeatable: the attacker (or a colluding party) can call `updateEndRemainingAllocation()` again after every subsequent claim to keep shrinking the denominator before submitting their own `claim()`.

### Recommendation
Make `updateEndRemainingAllocation()` itself enforce the one-shot invariant instead of relying on the caller (`claim()`) to gate it, e.g.:
```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4] && totalEndRemainingAllocation == 0) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
```
This makes the public and internal paths consistent, guaranteeing the snapshot can only ever be taken once, regardless of who calls it or how many claims have already occurred.

### Proof of Concept
Foundry/Hardhat test plan:
1. Deploy `Airdrop` with `startTime`; register allocations for users A, B, C (e.g., 1000, 1000, 1000 MGP) and fund the contract with enough `aidropToken` to cover principal + expected bonus.
2. Warp `block.timestamp` to just past `periodsEndTime[4]`.
3. Have some prior claim activity accrue `totalBonus` (e.g., have A claim in an earlier period before period 4 so a `forfeited` amount is added to `totalBonus`), or just accept `totalBonus` from natural early-period forfeitures.
4. At `t > periodsEndTime[4]`, call `claim()` from user B. Assert `totalEndRemainingAllocation == totalRemainingAllocation_before_B` (the full remaining pool including B and C).
5. Directly call `updateEndRemainingAllocation()` from an attacker EOA (C). Assert `totalEndRemainingAllocation` is now reduced (excludes B's allocation, since B already claimed and zeroed out).
6. Call `claim()` from C and record `claimableAmount` (principal + bonus).
7. Compare C's received bonus against the bonus C would have received had `totalEndRemainingAllocation` never been re-snapshotted (i.e., using the value captured in step 4). Assert C's actual bonus is strictly larger, demonstrating denominator manipulation.
8. Show that the sum of bonuses actually paid out (or the contract's remaining balance) is insufficient to pay a hypothetical additional legitimate claimant D with an allocation equal to C's, i.e. `aidropToken.balanceOf(address(airdrop)) < getClaimableAmount(D)`, and that `claim()` for D reverts with `InsufficientBalance()`.         allocations[msg.sender] = 0;

            totalBonus += forfeited;
        }
