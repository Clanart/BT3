Based on my investigation, the strongest analog to the RLP-encoding bug class is in GitHub Desktop's custom unified-diff (patch) re-serialization logic, used when applying partial line selections to the index or discarding changes — a hand-rolled encoder that must exactly match the standard `git apply` expects, operating on attacker-influenced diff content from a cloned/fetched repository.

### Title
Custom unified-diff re-encoding in `formatPatch`/`formatPatchToDiscardChanges` does not preserve standard hunk-count invariants, risking silent corruption of partial commits/discards - (File: `app/src/lib/patch-formatter.ts`)

### Summary
Just like the Scroll `store_uint` helper hand-encodes RLP integers and diverges from the standard for the zero case, GitHub Desktop hand-encodes GNU unified diff hunks in `formatPatch` and `formatPatchToDiscardChanges` instead of relying on `git`'s own patch generation. These functions recompute `oldCount`/`newCount` from the user's line *selection* but reuse the *original* hunk's `oldStartLine`/`newStartLine` [1](#0-0)  from the full (unfiltered) hunk parsed out of real `git diff` output by `DiffParser.parseHunk` [2](#0-1) . The header line/count fields written by `formatHunkHeader` are therefore a custom encoding of the hunk's position/size that is expected to satisfy the same invariants `git apply` enforces internally, without validation that they actually do. [3](#0-2) 

### Finding Description
`formatPatch` walks each parsed `DiffHunk`'s `lines`, decides per-line whether to keep it as-is, drop it, or convert a deletion to a context line, based on `file.selection.isSelected(...)`, and tallies `oldCount`/`newCount` accordingly. [4](#0-3)  It then writes the hunk header using the *original* `hunk.header.oldStartLine`/`newStartLine` combined with the *recomputed* counts: [1](#0-0) . `formatPatchToDiscardChanges` does the mirror-image transformation. [5](#0-4) 

This is a bespoke, from-scratch encoder for a format (GNU unified diff / git patch) with strict, well-known edge-case rules — the same class of defect as the RLP report: a manual serializer that is *supposed* to be standard-compliant but only handles the "normal" case correctly, while a special case (a hunk whose original/new side count collapses to `0`, or whose start line context shifts due to selection) is not renormalized to match what `git apply`/`git`'s own hunk emitter would produce. The generated patch is then fed directly to `git apply --cached` (for partial staging) or `git apply` (for partial discard) in `app/src/lib/git/apply.ts` [6](#0-5)  and [7](#0-6) , exactly the way the malformed L1 transaction hash was fed into a verification step expecting standard encoding.

The line data itself (`line.text`) originates from real diff output of files in the repository, so its content is influenced by whatever a cloned/fetched remote repository contains — an attacker who controls repository content controls the exact bytes that flow, unsanitized beyond prefix stripping, into the custom-built patch that Desktop applies to the user's index/working tree.

### Impact Explanation
If the hand-rolled header/count encoding for an edge-case selection (e.g., a hunk that becomes all-context on one side, or a deletion-only/addition-only hunk sliced out of a larger hunk) does not exactly match what `git apply` expects for that combination of start line and count, `git apply` can either reject the patch (a benign failure) or, in less strict modes such as the `--unidiff-zero` flag Desktop always passes here [8](#0-7) , apply the hunk against a mismatched context and silently produce a different result than the user selected in the UI. Because this code path runs on every partial-stage ("select lines to commit") and partial-discard ("discard selected changes") operation, a mismatch here means the content the user believes they are committing or discarding is not the content that is actually written to the index or working tree — i.e. silent corruption of what the user commits, matching the "Valid Impact" category in the report.

### Likelihood Explanation
This is speculative without a concrete failing selection reproduced end-to-end: I was not able to construct or verify a specific selection state that produces a header the actual `git apply` binary rejects/misapplies (my tool access is read-only and I could not execute `git apply` against a crafted patch). The existing unit tests in `patch-formatter-test.ts` cover several edge cases (all-context hunks skipped, new-file hunk rewritten to `@@ -0,0 +1 @@`, no-newline markers) and pass, suggesting common cases are handled, but they do not exhaustively cover every combination of original start-line vs. reduced count for modified-file hunks with mixed add/delete selections. [9](#0-8) 

### Recommendation
Treat `formatPatch`/`formatPatchToDiscardChanges` as a standard-format encoder and add explicit round-trip verification: after building each hand-written patch, re-parse it with `DiffParser` (or dry-run `git apply --check`) and assert the header counts match the number of physical `+`/`-`/context lines actually written before invoking `git apply` against the real index/working tree. Add targeted unit tests for hunks whose original start line is offset from the recomputed post-selection start line (e.g., first N lines of a hunk deselected, or trailing lines deselected) to ensure the emitted header always matches git's own conventions for zero-length ranges and shifted context.

### Proof of Concept
Not executed — this would require running `git apply` (or dugite) locally against a crafted `WorkingDirectoryFileChange`/`DiffSelection` where only a subset of a multi-line hunk near a boundary is selected, then diffing the resulting index/working tree content against what the UI displayed as "selected," which was outside the scope of the available read-only tools.

function formatHunkHeader(
  oldStartLine: number,
  oldLineCount: number,
  newStartLine: number,
  newLineCount: number,
  sectionHeading?: string | null
) {
  // > @@ -l,s +l,s @@ optional section heading
  // >
  // > The hunk range information contains two hunk ranges. The range for the hunk of the original
  // > file is preceded by a minus symbol, and the range for the new file is preceded by a plus
  // > symbol. Each hunk range is of the format l,s where l is the starting line number and s is
  // > the number of lines the change hunk applies to for each respective file.
  // >
  // > In many versions of GNU diff, each range can omit the comma and trailing value s,
  // > in which case s defaults to 1
  const lineInfoBefore =
    oldLineCount === 1 ? `${oldStartLine}` : `${oldStartLine},${oldLineCount}`

  const lineInfoAfter =
    newLineCount === 1 ? `${newStartLine}` : `${newStartLine},${newLineCount}`

  sectionHeading = sectionHeading ? ` ${sectionHeading}` : ''

  return `@@ -${lineInfoBefore} +${lineInfoAfter} @@${sectionHeading}\n`
}

export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.newStartLine,
      newCount,
      hunk.header.oldStartLine,
      oldCount
    )
    patch += hunkBuf
  })

  if (patch.length === 0) {
    // The selection resulted in an empty patch.
    return null
  }

  return formatPatchHeader(filePath, filePath) + patch
}

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
