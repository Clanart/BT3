### Title
Silent, unconfirmed remote-URL rewrite from GitHub API `clone_url` can redirect future pushes to an attacker-controlled repository - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a repository's local `origin` remote URL whenever the GitHub API's `clone_url` for the associated `GitHubRepository` no longer matches the local remote (e.g., after what Desktop interprets as a repo rename/transfer), with no user prompt or confirmation. Because the trigger value (`apiRepo.clone_url`) originates from a GitHub API response object, it is exactly the kind of "attacker-controlled GitHub API object" the task calls out. If an attacker can influence that field (compromised/rogue GitHub Enterprise API endpoint, a malicious proxy the user has configured, or a repo-transfer/rename race), Desktop will silently call `gitStore.setRemoteURL` and re-point the user's `origin` at a different host/owner/repo without any user awareness, corrupting where subsequent commits are pushed. [1](#0-0) 

### Finding Description
`updateRemoteUrl` computes three booleans and, if all align, silently updates the git remote:
- `urlsMatch`: whether the *new* `apiRepo.clone_url` matches the current local remote.
- `protocolsMatch`: whether the URL scheme (https/ssh) of the local remote and the new URL are the same.
- `remoteUrlUnchanged`: whether the *previously cached* `gitHubRepository.cloneURL` still matches the current local remote (i.e., the user hasn't manually changed the remote away from what Desktop last knew). [2](#0-1) 

When `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, Desktop calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` — no confirmation dialog, no diff shown to the user, and no restriction that the new URL's hostname stays the same as before. The matching helper `urlMatchesRemote`/`parseRemote` only compares protocol/hostname/owner/name structurally; it does not pin the new URL to the *same* hostname as the old one when the values disagree (a hostname change is precisely one of the conditions that produces `!urlsMatch = true`, which is required to enter the branch). [3](#0-2) 

This function is fed directly from the GitHub API response object (`IAPIRepository`), which is fetched over the network from whatever endpoint the user's account is configured against (dotcom or a GitHub Enterprise host, or through a corporate proxy) — i.e., it is a "GitHub API object" that is not locally validated against the previous trusted value beyond loose string/owner/name matching. The unit tests confirm the mechanism is designed to silently follow a changed `clone_url` as long as the user hasn't manually diverged their remote: [4](#0-3) 

Existing guards are insufficient to stop a malicious redirect:
- `remoteUrlUnchanged` only prevents the rewrite if the user has *already* manually pointed `origin` somewhere unrelated to what Desktop cached — it does nothing to validate that the *new* URL is safe/expected.
- `protocolsMatch` only checks the scheme (`https:` vs `ssh:`), not the host, owner, or repo name — an attacker-supplied `clone_url` of a completely different host but same protocol passes this check.
- There is no user confirmation step or diff/banner shown before the remote is silently rewritten via `git remote set-url`.

### Impact Explanation
`origin`'s URL is the destination for all future `git push`/`git fetch` operations performed via the UI. Silently rewriting it to an attacker-controlled host means:
- Future pushes (including credentials sent by Desktop's credential-helper trampoline, which resolves credentials per-endpoint) could be sent to a different host, and/or code the user believes they are pushing to their own repo could instead go to an attacker's repository, corrupting the semantics of what the user believes they are pushing/sharing.
- Because trampoline credential lookups are keyed off the remote's endpoint/host, a redirected remote pointing at an attacker's HTTPS endpoint could also cause the credential helper to attempt authentication against attacker infrastructure. [5](#0-4) 

This matches the requested "silent corruption of what the user commits or pushes" impact class, and the trigger primitive matches "attacker controls ... a GitHub API object ... or a git remote/proxy response."

### Likelihood Explanation
This is reachable without any local/physical access or leaked credentials, provided the attacker can influence one API response field (`clone_url`) reaching the Desktop client — realistic for: a compromised/malicious GitHub Enterprise Server instance the user is signed into, a corporate/transparent proxy or DNS/TLS-terminating MITM in an environment where the client's TLS trust store is attacker-influenced, or a narrower race during legitimate repository transfer/rename where an attacker claims resulting naming collisions. The exact reachability against dotcom over standard TLS is more constrained (requires a compromised GitHub API response), which is why this is presented as a real-code analog to the audit finding rather than a fully proven zero-click dotcom exploit — the code path itself, however, unambiguously performs the silent, unconfirmed remote rewrite once its three loose conditions are satisfied.

### Recommendation
- Before silently updating `origin`, require the new URL to at least retain the same hostname as the previous URL, or otherwise restrict automatic follow-redirect behavior to same-origin renames/transfers only.
- Surface a non-silent confirmation/banner to the user before changing a remote URL that will affect where future pushes go, rather than performing `setRemoteURL` invisibly.
- Consider not auto-following `clone_url` changes for cross-owner "transfers" at all, since a transfer to an unexpected owner is exactly the scenario a user would want to be alerted about.

### Proof of Concept
1. User has GitHub Desktop configured with an account pointed at a compromised/malicious GitHub Enterprise (or proxied) API endpoint, with `origin` remote at `https://ghe.example.com/acme/project.git`, matching the cached `gitHubRepository.cloneURL`.
2. The malicious API endpoint returns a repository payload for the same `dbID`/full name with `clone_url` changed to `https://attacker.example.com/acme/project.git` (still `https:`, so `protocolsMatch` is true; owner/name differ so `urlsMatch` is false; user never touched the remote so `remoteUrlUnchanged` is true).
3. On the next repository refresh, `updateRemoteUrl` (invoked from `app-store.ts`) executes `gitStore.setRemoteURL('origin', 'https://attacker.example.com/acme/project.git')` with no prompt, confirmed by the equivalent unit test behavior. [4](#0-3) 
4. The user's next `git push` from the Desktop UI silently pushes to `attacker.example.com` instead of the trusted host, and any credential-helper prompt/lookup is now scoped to the attacker endpoint. [6](#0-5)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
