### Title
Security-review rate limiter can be exhausted with trivial commits to smuggle a malicious commit/push past the security-guidance hook - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
The `security-guidance` plugin's `CommitReview` and `PushSweep` `PostToolUse` hooks gate their LLM-based vulnerability analysis behind a rolling-hour rate limiter (`atomic_check_rate_limit(session_id, "CommitReview", MAX_COMMIT_REVIEWS_PER_HOUR, COMMIT_REVIEW_RATE_WINDOW_S)`). Once the quota for the session is exhausted, every subsequent commit/push in that window is silently skipped (`skip_reason: 23`) without ever calling `analyze_code_security`, i.e. without any security review or blocking `sys.exit(2)`. This mirrors the "dust position" pattern in the reported bug: an unprivileged actor can cheaply trigger/consume the enforcement mechanism with many trivial actions, then slip the real malicious action through once the mechanism is disabled for the remainder of the window.

### Finding Description
`handle_commit_review_posttooluse` and `handle_push_sweep_posttooluse` both call the same style of rate check before invoking the LLM review: [1](#0-0) [2](#0-1) 

When `_allowed` is `False`, the handler exits with `sys.exit(0)` at `skip_reason: 23` and never calls `analyze_code_security`/`_agentic_review_with_race`, meaning no vulnerability scan, no blocking guidance, and no `sys.exit(2)` are produced for that commit or push.

Because the counter is a shared per-session, per-hour bucket (keyed only by session id and the `"CommitReview"`/`"PushSweep"` label, tracked via `with_locked_state`), any sequence of commits within the window consumes the same quota regardless of their content or size — a trivial no-op commit (e.g., whitespace or comment-only changes) counts exactly the same as a commit that introduces a real vulnerability: [3](#0-2) 

An unprivileged user (or an agent driven by an untrusted prompt/repo instructions) that controls the commit cadence within a session can issue a burst of "dust" commits (or prompt Claude to do so) purely to burn through `MAX_COMMIT_REVIEWS_PER_HOUR` slots, then commit the actual malicious change once the limiter starts returning `False`. That final, real commit — the one that matters — is the one that is `skip_reason: 23`'d and never reviewed, exactly as the liquidation-dust attacker exhausts the liquidator's willingness/ability to process the real position by first creating a cheap trigger.

### Impact Explanation
This allows a vulnerability-introducing commit or push to bypass the security-guidance plugin's only enforcement point — the LLM-based `analyze_code_security` review and its `exit(2)` continuation-forcing guidance — inside the same session, effectively neutralizing the plugin's security review guarantee for the remainder of the rate-limit window. Since this plugin is explicitly designed to catch and block vulnerable code before it's committed/pushed, silently disabling it via cheap trigger commits undermines the intended trust boundary between untrusted code changes and the review gate.

### Likelihood Explanation
Any user or agent workflow that can issue multiple git commits/pushes within a session (a normal, unprivileged capability) can trigger this — no special permissions, exploits, or hook bypass are required, just volume of trivial commits within `COMMIT_REVIEW_RATE_WINDOW_S`. The exact value of `MAX_COMMIT_REVIEWS_PER_HOUR`/`COMMIT_REVIEW_RATE_WINDOW_S` was not directly located in the excerpts retrieved, so the precise number of "dust" commits needed to exhaust the quota is unconfirmed, but the mechanism itself (shared session-scoped counter gating the only review call) is clearly present and reachable.

### Recommendation
Do not let the review-skip decision be purely quota-based with no fallback. Options: (1) when the rate limit is hit, still run a fast, cheap heuristic/pattern-based check (already present elsewhere in the plugin) instead of skipping outright; (2) prioritize/queue reviews so the most recent or largest diff is still reviewed even if older small commits consumed the quota; (3) make the rate limiter cost-proportional to diff size/risk rather than a flat per-commit charge, so trivial dust commits don't consume the same budget as substantive ones; (4) surface a clear warning to the user when reviews are being skipped due to rate limiting so it isn't silent.

### Proof of Concept
1. In a single Claude Code session with the `security-guidance` plugin active, script or prompt Claude to make N trivial commits (e.g., whitespace-only or comment-only edits) in rapid succession until `atomic_check_rate_limit(session_id, "CommitReview", ...)` starts returning `False` (confirmed by `skip_reason: 23` in emitted metrics/debug logs at [4](#0-3) ).
2. Once the quota is exhausted, commit the actual malicious/vulnerable code change (e.g., a hardcoded credential, SQL injection, command injection).
3. Observe that `handle_commit_review_posttooluse` exits at the rate-limit check before ever calling `analyze_code_security`, so no security guidance is emitted and the commit is not blocked with `sys.exit(2)`.
4. If the branch is then pushed, `handle_push_sweep_posttooluse` is subject to the same shared-style rate limiter (`"PushSweep"` key, same `MAX_COMMIT_REVIEWS_PER_HOUR`/`COMMIT_REVIEW_RATE_WINDOW_S` constants), so the malicious commit can also evade the push-time sweep if that quota is separately exhausted with dust pushes.
