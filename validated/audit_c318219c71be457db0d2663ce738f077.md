Based on the investigation, the strongest local analog is a fee-clearing asymmetry in `EvmHost.dispatchIncoming` for GET responses — the same class of bug as the Perennial issue (a value that should be consumed/zeroed after being paid out is left intact, enabling reuse).

### Title
Relayer fee for GET requests is not cleared after payout in `dispatchIncoming`, enabling duplicate fee payment on resubmission - (evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming` pays the relayer the fee stored in `_requestCommitments[commitment]` for a GET request/response pair, but unlike every other terminal fee-payout path in the same contract (`dispatchTimeOut` for both GET and POST), it never deletes or zeroes `_requestCommitments[commitment]` after paying.

### Finding Description
In `EvmHost.sol`, the GET-timeout and POST-timeout paths both explicitly clear `_requestCommitments[commitment]` before/around the fee refund to guarantee the commitment (and its `fee`) can't be reused: [1](#0-0) [2](#0-1) 

By contrast, `dispatchIncoming` (the successful-delivery path for a GET response) sets `_responseReceipts[commitment]` for replay protection of the *response*, but pays the relayer fee out of `_requestCommitments[commitment].fee` without ever deleting that entry: [3](#0-2) 

The commitment key here, `response.request.hash()`, is derived from the *original request*, not from the response content. The replay guard `_responseReceipts[commitment]` is written unconditionally at the top of the function on every call — it is not checked/read as a "have I already processed this?" guard before proceeding; it is simply overwritten. This means the anti-replay property for `dispatchIncoming` relies entirely on whatever check exists upstream in the handler layer, not on the host itself. Since `_requestCommitments[commitment]` is never zeroed, if the handler/proof layer ever allows `dispatchIncoming` to be invoked more than once for the same request commitment (e.g., a second valid GET-response message for the same still-unexpired request, submitted with a different relayer address, before/without any host-side idempotency on `_requestCommitments`), the `fee` value read at line 842 is non-zero every time and gets paid to the caller-supplied `relayer` address again.

This mirrors the Perennial root cause precisely: a value used to gate/pay out (there: `oracleFee`; here: `_requestCommitments[commitment].fee`) is not consumed/reset after being paid, so the same underlying state can be walked through the payout path repeatedly by anyone able to reach the entrypoint.

### Impact Explanation
If the duplicate-delivery guard for GET responses is not fully enforced upstream (only the POST duplicate check is documented — `host.requestReceipts(commitment) != address(0)` — with no equivalent code shown for GET responses), each additional call drains `feeToken()` balance held by the host to an attacker-chosen `relayer` address for free, directly matching "stealing or loss of funds" and "double-claim/double-settlement" from the impact gate. Even in the best case where the handler does dedupe, the missing zeroing is a structural inconsistency with the pattern used everywhere else fees are paid in this file, and is the exact broken invariant class the seed report exploited (a not-quite-consumed fee record).

### Likelihood Explanation
Medium: this requires that the GET-response delivery path can be invoked more than once for the same request commitment through the public handler/proof-verification flow (restricted to `_hostParams.handler`, but the handler is the standard entrypoint reachable by any relayer with a valid state proof for a *new* response object hashing back to the same `request`). The exact upstream duplicate-check code for GET responses (as opposed to POST requests, whose check is explicitly documented) was not found in the available index, so it is uncertain whether a second, distinct valid `GetResponse` for the same request can be proven and delivered twice before this window is closed elsewhere.

### Recommendation
Delete (or zero) `_requestCommitments[commitment]` in `dispatchIncoming` immediately after transferring the fee (mirroring the pattern in both `dispatchTimeOut` overloads), and/or add an explicit host-side check that `_requestCommitments[commitment].fee == 0` / the commitment hasn't already been paid before executing the transfer, so the fee can only ever be paid once regardless of how many times a valid response for that request is delivered upstream.

### Proof of Concept
Not independently reproduced against a running node — this finding is based on static code comparison within `EvmHost.sol`: `dispatchIncoming` (lines 824-847) omits the `delete _requestCommitments[commitment]` step that both `dispatchTimeOut` overloads (lines 856-877, 885-900) perform. Confirming exploitability requires verifying, in `HandlerV2.sol`, whether GET-response messages have the same duplicate-commitment rejection that was shown for POST requests (`if (host.requestReceipts(commitment) != address(0)) revert DuplicateMessage();`) — that check was documented in the docs only for POST requests, and its GET-response equivalent was not located in the available index. This gap should be verified directly against `evm/src/core/HandlerV2.sol` before treating this as fully confirmed.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
