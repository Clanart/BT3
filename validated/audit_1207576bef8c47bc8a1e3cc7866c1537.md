### Title
Outbound Bitcoin transactions do not validate payment script standardness, producing unbroadcastable signed transactions that permanently block the outbound queue - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` validates dust, fee rate, funds, and total weight, but never validates that a payment's `script_pubkey` is standard or even well-formed. A burn to a non-standard destination script produces a transaction the threshold network will fully sign but which Bitcoin Core rejects at relay as "non-standard". Because the outbound flow has already committed inputs and signatures, the stuck output blocks subsequent outbounds — the same bug class as M-25 (insufficient validation of outbound parameters creating an unprocessable outbound that wedges the nonce/queue).

### Finding Description
The outbound-construction entry point checks payment *amounts* but not payment *scripts*:

```rust
// networks/bitcoin/src/wallet/send.rs:165-169
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

The only subsequent checks are OP_RETURN data length (`:171`), minimum fee (`:211`), sufficient funds (`:215`), and `MAX_STANDARD_TX_WEIGHT` (`:241`). The `ScriptBuf` in each `(ScriptBuf, u64)` payment tuple is copied verbatim into the output (`:188-191`) with no call to any standardness/well-formedness check.

Bitcoin Core's `IsStandard` policy only accepts scripts that solve into a known type (P2PK, P2PKH, bare multisig with ≤3 keys, OP_RETURN, segwit programs). An attacker-controlled burn destination address is just a `ScriptBuf` (the processor's `Address` type wraps raw `ScriptBuf`s — e.g. `Address::new(spent_output.script_pubkey)` in `processor/src/networks/bitcoin.rs:728`). A destination such as an arbitrary unparsable script, a bare multisig with >3 keys, or a script whose serialized size makes 546 sats below its true dust limit yields a transaction that:

1. passes every check in `SignableTransaction::new`,
2. is consumed by `multisig()`/`TransactionMachine` and fully signed by FROST (`send.rs:273-285`, `:373-398`),
3. is rejected by `sendrawtransaction`/mempool policy as `nonstandard` (or `dust`), so it can never confirm.

The analogous failure in M-25 was a CCTX that signed/queued but errored at the external chain, blocking all subsequent outbounds under strict nonce ordering; here the signed-but-unrelayable TX blocks the Bitcoin outbound pipeline for the affected multisig, since the attempted inputs and the pending output must be resolved/retry-handled before new sends can proceed.

### Impact Explanation
An unprivileged user performing a `burn` with a maliciously crafted Bitcoin destination `ScriptBuf` causes the network to finalize a threshold signature over a transaction that can never be relayed. The resulting outbound is permanently unprocessable, wedging the Bitcoin send queue for that multisig (inputs are earmarked, the plan/eventuality never completes). This matches the report's impact: invalid outbound parameters admitted because validation was missing, with downstream blocking rather than a clean rejection. Funds are not directly stolen, but protocol liveness for Bitcoin outbounds is degraded by a single cheap burn — a Medium.

### Likelihood Explanation
Any user can burn with arbitrary external address bytes; no validator collusion or privileged access is required. The cost is only the burned amount (≥ dust). The failure is deterministic: a nonstandard or dust-violating output is rejected by every default-policy node, regardless of which peers the processor broadcasts to.

### Recommendation
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256), validate each payment script for standardness before building `tx_outs` — e.g. require it to parse into a known `Address`/`script type` (P2PKH/P2SH/P2WPKH/P2WSH/P2TR) or be the single OP_RETURN output, reject bare scripts and scripts exceeding standard size limits, and enforce per-output-type dust thresholds instead of the flat `DUST = 546`. Mirror the M-25 mitigation: ensure only relayable, processable transactions enter the signing queue.

### Proof of Concept
```rust
// A burn destination that is not a standard script: e.g. a bare 5-of-5 multisig
// (>3 keys => "nonstandard" per Bitcoin Core solver) or any unparsable script.
let evil_script = ScriptBuf::from_bytes(vec![0x51, 0x51, 0xae]); // OP_1 OP_1 OP_CHECKMULTISIG
// or simply:
let evil_script = ScriptBuf::from_bytes(vec![0xff; 200]); // unparsable, nonstandard

// This succeeds: no script validation exists.
let tx = SignableTransaction::new(
    vec![received_output],        // a normal scanned input
    &[(evil_script, 10_000)],     // amount >= DUST passes
    Some(change_script),
    None,
    fee_per_vbyte,
).unwrap();

// The FROST network signs it fine — sighash and Schnorr are well-formed.
let tx = sign(&keys, &tx);

// send_raw_transaction / mempool rejects it: "nonstandard".
// The outbound is signed, inputs committed, yet can never confirm —
// identical blocking effect to the invalid CCTX in M-25.
```
