### Title
Trampoline server accepts credential/askpass requests from any local socket connection with only a bare token-existence check, allowing a git subprocess spawned during a hostile clone/fetch (filter/diff/merge driver, GCM, or LFS custom transfer) to exfiltrate stored GitHub OAuth tokens for arbitrary endpoints - (File: app/src/lib/trampoline/trampoline-server.ts)

### Summary
`TrampolineServer.processCommand` only verifies that the `trampolineToken` sent by a TCP client is a currently outstanding token from a global `Set` [1](#0-0) , and `isValidTrampolineToken` does nothing beyond `trampolineTokens.has(token)` [2](#0-1) . Nothing ties an incoming connection to the specific git subprocess Desktop actually spawned for that operation, and nothing validates that the `host`/`url` fields inside a "get" credential request match the remote that the current git operation is actually talking to. This mirrors the flash-loan bug's broken invariant: the callback checks "is this a legitimate caller class" (module / valid token) but never checks "did *I* initiate this specific request with these specific parameters."

### Finding Description
Desktop starts a TCP server bound to `127.0.0.1` on an OS-assigned ephemeral port [3](#0-2) . For every git invocation that may need auth, it mints a short-lived UUID token and passes both the port and token to the git process via `DESKTOP_PORT` / `DESKTOP_TRAMPOLINE_TOKEN` environment variables [4](#0-3) . Git (and any subprocess git spawns — credential helpers, diff/merge/textconv filters, GCM, LFS custom transfer agents) inherits these environment variables. The native `desktop-trampoline` executable forwards whatever arguments/stdin it receives straight to that TCP socket along with the token [5](#0-4) .

`onNewConnection`/`processCommand` on the server side treat any TCP client presenting a currently-valid token as trusted, and dispatch to the registered `AskPass` or `CredentialHelper` handler with attacker-suppliable parameters [6](#0-5) . The credential-helper handler's "get" path derives an arbitrary `endpoint` URL from the request payload and looks up a stored GitHub account for that endpoint, returning the account's login/token if found [7](#0-6) [8](#0-7) . Crucially, the `host`/`url` in the credential request is not checked against the remote that the actual git operation (identified by that token) is really talking to — any process that can reach the socket and reuse the valid token can request credentials for `https://github.com` or any configured GHE endpoint, not just the endpoint of the repo being cloned/fetched.

This is the same class of defect as the `LeverageStrategy.receiveFlashLoan` bug: the module verifies the *caller* class (flash-loan module / TCP client with a live token) but not that *this contract itself* (Desktop) initiated this exact call with these exact parameters. Here, the corrupted value is the `endpoint`/`host` field trusted inside `getGitHubCredential`/`getCredential`, which is fully attacker-controlled once a connection with a valid token is possible [9](#0-8) .

### Impact Explanation
If a malicious repository can get any code to execute as a child of the git process during a clone/fetch/checkout that Desktop initiated (e.g. via a locally-configured filter/diff/merge driver, LFS custom transfer, or GCM invoked while `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` are live in the environment), that code can connect directly to `127.0.0.1:<DESKTOP_PORT>` and issue a forged `CredentialHelper` "get" command for an unrelated endpoint (e.g. `github.com`), causing Desktop to hand back the user's stored GitHub OAuth token in the credential-helper response, formatted by `formatCredential` [10](#0-9) . That is credential exfiltration of the user's GitHub account token, not merely the credential relevant to the operation in progress.

### Likelihood Explanation
This requires the attacker to get some process execution as a byproduct of Desktop's own git invocation while a token is live — this is a narrower bar than plain local malware, but it is not a fully "remote, zero-interaction" primitive either, since it depends on an existing filter/helper/LFS transfer being configured or invoked as part of processing repository content. I could not confirm from the indexed code whether Desktop restricts which drivers/helpers can run during its automated background fetches, or whether any origin/PID check exists beyond the token-existence check shown above — this is a gap in what I could verify from the available files.

### Recommendation
Bind server-side trust to the specific operation, not just "any live token": (1) scope each token to the exact expected remote endpoint(s) for that git invocation (recorded in `trampolineEnvironmentPath`-style maps) and reject/flag credential requests whose `host`/`url` doesn't match the expected remote for that token; (2) consider one-time-use tokens per socket connection instead of a shared existence check in a global `Set`; (3) verify the peer PID of the connecting socket corresponds to the process tree spawned for that trampoline token where the OS allows it.

### Proof of Concept
Not able to fully construct end-to-end from static analysis alone — reproducing this requires an environment where a locally configured git filter/diff/merge driver, GCM, or LFS transfer agent is triggered during a Desktop-initiated clone/fetch of a hostile repository, then having that spawned process read `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from its environment and open a raw TCP connection sending a `CredentialHelper` "get" command with `host=github.com` before the operation completes and the token is revoked (`revokeTrampolineToken` in `withTrampolineToken`) [11](#0-10) . I was not able to verify within the indexed codebase alone which specific git-invoked subprocess a hostile repository can control to make this remotely triggerable versus requiring a pre-existing local configuration; this uncertainty should be resolved with a live Desktop build/test environment.

  private onNewConnection(socket: Socket) {
    const parser = new TrampolineCommandParser()

    // Messages coming from the trampoline client will be separated by \0
    socket.pipe(split2(/\0/)).on('data', data => {
      this.onDataReceived(socket, parser, data)
    })

    socket.on('error', this.onClientError)
  }

  private onDataReceived(
    socket: Socket,
    parser: TrampolineCommandParser,
    data: Buffer
  ) {
    const value = data.toString('utf8')

    try {
      parser.processValue(value)
    } catch (error) {
      log.error('Error processing trampoline data', error)
      socket.end()
      return
    }

    if (!parser.hasFinished()) {
      return
    }

    const command = parser.toCommand()
    if (command === null) {
      socket.end()
      return
    }

    this.processCommand(socket, command)
  }
