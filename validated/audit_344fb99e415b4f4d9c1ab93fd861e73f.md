### Title
`WSEI.withdraw()` uses a hard-coded-gas `payable.transfer()`, causing frozen funds for smart-contract holders of Wrapped SEI - ([File: contracts/src/WSEI.sol])

### Summary
`WSEI.sol`, the canonical Wrapped SEI (WSEI) token contract used on Sei's EVM (deployable via the `x/evm` CLI's `CmdDeployWSEI`, with its bytecode embedded at `x/evm/artifacts/wsei/artifacts.go`), implements `withdraw()` using Solidity's `payable(msg.sender).transfer(wad)`. This is the exact bug class described in the referenced OpenLevV1/LPool report: a native-value transfer with Solidity's hard-coded 2300 gas stipend that will revert whenever the recipient is a smart contract with a non-trivial (or missing) fallback/receive function.

### Finding Description
`WSEI.withdraw()`: [1](#0-0) 

```solidity
function withdraw(uint wad) public {
    require(balanceOf[msg.sender] >= wad);
    balanceOf[msg.sender] -= wad;
    payable(msg.sender).transfer(wad);
    emit Withdrawal(msg.sender, wad);
}
```

`balanceOf[msg.sender]` is decremented *before* the `transfer` call, so the WSEI accounting (total supply / balance bookkeeping) is updated unconditionally, but the actual native-SEI transfer to `msg.sender` uses `.transfer()`, which forwards only 2300 gas to the recipient. Any contract that calls `withdraw()` — e.g., a router, vault, DeFi protocol, or any smart-contract wallet — and either:
- has no payable `receive()`/`fallback()`, or
- has a `receive()`/`fallback()` that consumes more than 2300 gas (e.g., emits an event, writes storage, calls another contract)

will have the native-SEI transfer revert. Because `transfer()` reverts on failure, the entire `withdraw()` transaction reverts too, which actually protects against **corrupted accounting** (the `balanceOf` decrement gets rolled back along with the failed transfer since it's all one transaction). However, this does **permanently and unconditionally deny withdrawal** of the underlying native SEI for any smart-contract holder of WSEI whose fallback function costs more than 2300 gas — there is no alternative withdrawal path (no `call{value}` based method, no allowance for the contract to specify its own gas). This matches the report's root cause: hard-coded stipend transfer for a wrapped-native-token unwrap operation, `WSEI.sol` line 30 being the direct analog of `OpenLevV1Lib.doTransferOut`/`LPool.doTransferOut`.

WSEI is provided as first-class infrastructure in the repository: it's shipped as pre-compiled bytecode via `x/evm/artifacts/wsei/artifacts.go` and deployable through the EVM module's CLI command `CmdDeployWSEI` [2](#0-1) , i.e., it is meant to serve as the canonical Wrapped SEI token that DEXs and other DeFi contracts (e.g., the UniswapV2 fork under `integration_test/load_generator/contracts/uniswapv2/`) integrate against as their WETH-equivalent.

### Impact Explanation
Any contract-based user (router, multisig, vault, DEX pair holding WSEI as intermediate liquidity, aggregator, etc.) that unwraps WSEI back to native SEI via `withdraw()` can have its funds permanently locked inside the WSEI contract if its own receive/fallback logic exceeds the 2300 gas stipend. Because there is no `call.value()`-based alternative and no way to specify additional gas, the funds are frozen with no recovery path short of a contract upgrade to WSEI itself (which is not typically possible for an already-deployed canonical wrapped-token contract). This is a fund-freezing vulnerability of medium/high severity for any protocol built to interoperate with WSEI as its native-wrapped-token standard.

### Likelihood Explanation
Likelihood is high in practice: any non-trivial smart contract (e.g., one that logs events, updates internal accounting, or forwards funds onward in its `receive()`) will exceed 2300 gas. This is a well-known, common failure mode for Solidity's `transfer()`/`send()` when the sender is a contract, and WETH-style wrapped-native contracts are heavily integrated with by other DeFi contracts (routers, vaults) rather than only EOAs.

### Recommendation
Replace the `payable.transfer()` call in `WSEI.withdraw()` with a low-level `call{value: wad}("")` and check the boolean success return (following the checks-effects-interactions pattern, which is already respected since balance is decremented first), e.g.:
```solidity
(bool success, ) = msg.sender.call{value: wad}("");
require(success, "WSEI: ETH transfer failed");
```
This mirrors the fix already used correctly elsewhere in the same monorepo, e.g. `TransferHelper.safeTransferETH` in `integration_test/load_generator/contracts/uniswapv2/libraries/TransferHelper.sol`: [3](#0-2) 

### Proof of Concept
1. Deploy a contract `Locker` with no `receive()`/`fallback()`, or with a `receive()` that does `sstore` writes or an external call (i.e., consumes > 2300 gas).
2. `Locker` calls `WSEI.deposit{value: X}()` to acquire `X` WSEI.
3. `Locker` calls `WSEI.withdraw(X)`.
4. The internal `payable(address(Locker)).transfer(X)` call reverts because the gas stipend (2300) is insufficient for `Locker`'s fallback logic (or absent, but even absent receive() with no payable would revert on plain EOA-style transfer too if no receive at all).
5. The entire `withdraw()` transaction reverts; `Locker`'s WSEI balance remains locked in the WSEI contract with no way to redeem it for native SEI, since no alternative unwrap function exists. [4](#0-3)

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract WSEI {
    string public name     = "Wrapped Sei";
    string public symbol   = "WSEI";
    uint8  public decimals = 18;

    event  Approval(address indexed src, address indexed guy, uint wad);
    event  Transfer(address indexed src, address indexed dst, uint wad);
    event  Deposit(address indexed dst, uint wad);
    event  Withdrawal(address indexed src, uint wad);

    mapping (address => uint)                       public  balanceOf;
    mapping (address => mapping (address => uint))  public  allowance;

    fallback() external payable {
        deposit();
    }
    receive() external payable {
        deposit();
    }
    function deposit() public payable {
        balanceOf[msg.sender] += msg.value;
        emit Deposit(msg.sender, msg.value);
    }
    function withdraw(uint wad) public {
        require(balanceOf[msg.sender] >= wad);
        balanceOf[msg.sender] -= wad;
        payable(msg.sender).transfer(wad);
        emit Withdrawal(msg.sender, wad);
    }

    function totalSupply() public view returns (uint) {
        return address(this).balance;
    }

    function approve(address guy, uint wad) public returns (bool) {
        allowance[msg.sender][guy] = wad;
        emit Approval(msg.sender, guy, wad);
        return true;
    }

    function transfer(address dst, uint wad) public returns (bool) {
        return transferFrom(msg.sender, dst, wad);
    }

    function transferFrom(address src, address dst, uint wad)
        public
        returns (bool)
    {
        require(balanceOf[src] >= wad);

        if (src != msg.sender && allowance[src][msg.sender] != type(uint).max) {
            require(allowance[src][msg.sender] >= wad);
            allowance[src][msg.sender] -= wad;
        }

        balanceOf[src] -= wad;
        balanceOf[dst] += wad;

        emit Transfer(src, dst, wad);

        return true;
    }
}
