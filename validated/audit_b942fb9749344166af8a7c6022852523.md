Found the analog: a stale-content splice (TOCTOU) between context-gathering and write-back in the Copilot conflict-resolution flow, which corrupts what the user actually commits.

### Title
Stale `rawContent` capture lets a resolved commit silently discard concurrent conflict-marker edits during Copilot conflict resolution - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolutions()` splices the model's per-hunk resolutions back into the file content that was captured *once*, at the start of the flow, in `buildConflictContext()` (`ctx.rawContent`), rather than the file's on-disk content at the moment the resolution is applied. Because Copilot resolution is long-running (network round trip, up to a 600s timeout, retries) and the user is explicitly allowed to keep interacting with the repository while it runs, the on-disk conflicted file can change during that window. The final write silently reverts/discards whatever changed on disk in the interim, without any re-check that the captured snapshot is still current.

### Finding Description
The flow is:
1. `buildConflictContext()` reads each conflicted file from disk and stores the full original content (including markers) in `IFileConflictContext.rawContent`. [1](#0-0) 
2. This context is handed to Copilot; the request/response round trip can take up to 10 minutes (`timeoutMs: modelConfig.timeoutMs ?? 600_000`) and includes a retry path. [2](#0-1) 
3. While this is in flight, the app deliberately lets the user navigate away and keep working: `_startCopilotConflictResolution` explicitly supports the user leaving the loading step, cancelling, restarting, or dismissing the dialog, and the resolution "continues in the background." [3](#0-2) 
4. When the model responds, `reassembleResolutions()` reconstructs the "resolved" file by splicing hunk resolutions into `ctx.rawContent` — the snapshot from step 1 — not by re-reading the file from disk. [4](#0-3) 
5. `reassembleResolvedFile()` walks that stale snapshot line-by-line, copying all non-conflict-marker lines through verbatim and replacing marker blocks with the model's hunk content — i.e., every non-conflict line of the *original* capture is what ends up on disk. [5](#0-4) 

There is no invariant check anywhere in this path verifying that the file on disk still matches `rawContent` before the reassembled content is written and eventually committed as the merge/rebase/cherry-pick resolution. This is structurally the same broken invariant as the DYAD report: a check/snapshot is taken ("no assets" / "file content X"), a long asynchronous window follows during which a third party can change the underlying state (deposit assets / edit the file), and the final privileged action (`remove()` / write resolved file) proceeds against the stale state instead of re-validating it — silently corrupting the outcome the user expects.

Concretely, an attacker who controls the *other* side of the merge/rebase (e.g., a malicious PR branch or fetched remote ref the victim is resolving conflicts against) doesn't even need a race with the user — the exploitable gap is any edit the user or another tool makes to the conflicted file between the time Copilot starts resolving and the time the result is written. Because the write path is `ctx.rawContent`-based, not disk-based, any manual edits, a `git status`/checkout, or another automated tool touching that file during the multi-minute window are silently discarded when the Copilot resolution is later applied — corrupting what the user ultimately commits/pushes, with no warning that the write is based on stale content.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user could manually fix a conflict (or partially resolve it) while Copilot is still "thinking" in the background, then accept the Copilot result later (from the `ConfirmAbort`/return-to-result-dialog path, which is explicitly supported), unaware that their manual edit was overwritten because the write was spliced against the pre-edit snapshot. In a merge/rebase/cherry-pick context, this can reintroduce reverted security-relevant changes, drop a fix, or resurrect code the user intentionally removed — and the user has no signal that this happened, since the UI only shows the model's own reasoning/summary, not a diff against current disk state.

### Likelihood Explanation
Moderate. It requires the resolution to be in flight long enough for the file to change (this is common: response times of tens of seconds up to the 600s timeout, plus a possible retry) and for the user (or another background process) to touch the same conflicted file during that window — a scenario the app itself explicitly enables by letting the user dismiss/re-open the dialog and continue working while resolution runs in the background. No local/admin access or malware is required; this is a normal usage pattern the feature was designed to support.

### Recommendation
Before applying (`reassembleResolutions`/writing) the Copilot resolution, re-read the current on-disk content for each file and compare it against the captured `rawContent` (e.g., hash comparison). If the file changed since the context was gathered, refuse to auto-apply that file's resolution and surface it as "content changed since resolution started — please re-resolve or apply manually," mirroring the existing `skippedReason` mechanism already present in `IFileConflictContext`.

### Proof of Concept
1. Trigger a merge/rebase with a conflicting file (e.g., `THING.md`).
2. Click "Resolve with Copilot" (`onResolveWithCopilot` → `_attemptCopilotConflictResolution` → `_startCopilotConflictResolution`). This reads and snapshots `THING.md` into `rawContent` via `buildConflictContext`.
3. While the request is in flight (up to 600s, `IRunConflictResolutionTurnOptions.timeoutMs`), dismiss the dialog (supported — resolution "continues in the background") and manually edit `THING.md` on disk to resolve the conflict differently, or run an unrelated `git` command that alters the file.
4. Reopen the dialog when Copilot's result is ready and click "Continue Merge" to apply the stored `result.resolutions`.
5. Observe that the written file matches `reassembleResolvedFile(ctx.rawContent, hunks)` — i.e., the manual edit from step 3 is silently discarded because the splice used the snapshot from step 2, not the current disk content. [6](#0-5)

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
