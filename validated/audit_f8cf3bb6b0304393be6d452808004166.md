### Title
SchnorrAggregate::verify accepts an empty aggregate (Rs = [], s = 0) as a valid signature - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The referenced bug is a missing zero-case guard: `updateGlobalExchangeRate` behaves incorrectly when `totalGlobalShares` is zero, because the code never considered the denominator/accumulator being empty after previously being non-empty. The analog in Serai is `SchnorrAggregate::verify`, which validates an aggregate signature by checking `sum(z_i * R_i) + sum(z_i * c_i * P_i) - s * G == 0`. When the aggregate contains **zero** signatures (`Rs` is empty) and the caller's `keys_and_challenges` list is empty, the check degenerates to `-s * G == identity`, which is satisfied by `s = 0`. An attacker can therefore serialize `len = 0` followed by a zero scalar, feed it to `SchnorrAggregate::read`, and have `verify` return `true` for a "signature" that nobody produced — the exact same class of "the empty/zero case was never handled" bug.

### Finding Description
`SchnorrAggregate::read` happily parses an empty `Rs` vector and an arbitrary `s` (aggregate.rs:77-88). `SchnorrAggregate::verify` only enforces `self.Rs.len() == keys_and_challenges.len()` (aggregate.rs:128-130) and then builds the multiexp pairs; for the empty case `pairs` reduces to the single term `(-self.s, C::generator())` (aggregate.rs:138-145), so the verification equation becomes `s == 0`. Nothing rejects an empty aggregate — unlike `SchnorrAggregator::complete`, which explicitly returns `None` when `self.sigs.is_empty()` (aggregate.rs:175-178). The honest aggregation path refuses to *produce* an empty aggregate, but the deserialization/verification path accepts and validates one. This asymmetry is the analog of the Covalent bug: the code handles the non-empty case correctly but the "total is zero" state is reachable (via attacker-supplied bytes to `read`) and resolves to "valid" instead of being rejected.

### Impact Explanation
Any consumer that aggregates Schnorr signatures over a caller-supplied or message-derived set of `(key, challenge)` pairs can be handed a forged aggregate signature: bytes `00 00 00 00 || 00…00` deserialize to `Rs = [], s = 0`, and if the verifier's key list is empty (e.g., zero signers registered for an epoch/set — directly mirroring "totalGlobalShares became 0 after unstake/disable"), `verify` returns `true`. The result is acceptance of a signature no party ever produced — a vacuous forgery over an empty signer set, the same failure mode as funds being mis-accounted when the share denominator is zero. The criteria "a forged proof or signature" / "incorrect verifier formula" are met.

### Likelihood Explanation
Reachability is high: `SchnorrAggregate::read` is one of the enumerated untrusted-byte entry points, and the malicious input is 36 fixed bytes with no computational work required. The precondition is that the verifier's `keys_and_challenges` is empty — which is precisely the "the set shrank to zero" scenario the source finding warns about (validator disabled/unstaked → empty set). This is a Medium-severity logic flaw rather than High because it requires the caller to be verifying over an empty set; it does not let an attacker forge an aggregate over a non-empty key list, since the length check binds `Rs` to the expected keys.

### Recommendation
Reject empty aggregates in `verify` (return `false` when `self.Rs.is_empty()` or `keys_and_challenges.is_empty()`), matching the explicit empty-set rejection already present in `SchnorrAggregator::complete`. Optionally also reject `Rs` length 0 in `SchnorrAggregate::read` so the invalid state is unrepresentable.

### Proof of Concept
```rust
// crypto/schnorr: verifier side
let mut bytes: &[u8] = &{
    let mut v = vec![0u8; 4];      // Rs length = 0
    v.extend([0u8; 32]);           // s = 0
    v
};
let agg = SchnorrAggregate::<Secp256k1>::read(&mut bytes).unwrap();
// An unprivileged caller needs no keys; any dst works.
assert!(agg.verify(b"some_dst", &[])); // passes: multiexp = (-0)*G = identity
```
The attacker controls both inputs (`read` bytes and an empty challenge list, e.g., a validator set that became empty), so `verify` returns `true` for a signature that was never produced — the degenerate zero-total case, directly analogous to rewards/accounting misbehaving when `totalGlobalShares == 0` in the source finding.

One caveat to flag honestly: impact depends on an integrator calling `verify` with an empty `keys_and_challenges` list and treating `true` as authorization. Within the in-scope crates the formula flaw itself is concrete and reachable; whether a specific consumer hits it is outside the scoped code.
