### Title
Missing zero-check on governance parameter `kip71.gastarget` causes division-by-zero panic in `NextMagmaBlockBaseFee` - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee()` divides by the `GasTarget` governance parameter with no zero-guard, unlike the sibling `BaseFeeDenominator` parameter which explicitly rejects zero. If governance sets `kip71.gastarget` to `0`, every subsequent block computation (`work/worker.go` block assembly, `blockchain/tx_pool.go`, `blockchain/chain_makers.go`, `blockchain/block_validator.go`'s `VerifyMagmaHeader`, and the gas price oracle in `node/cn/gasprice/`) will panic with a division-by-zero, since `gasTarget=0` makes `parentGasUsed > gasTarget` true for virtually every block, entering the branch that computes `x.Div(x, new(big.Int).SetUint64(gasTarget))`.

### Finding Description
`Kip71GasTarget` is registered in the governance parameter table with `FormatChecker: noopFormatChecker`, i.e. no validation at all: [1](#0-0) 

Compare this to `Kip71BaseFeeDenominator`, which explicitly guards against zero: [2](#0-1) 

In `NextMagmaBlockBaseFee`, `baseFeeDenominator` has a defensive zero-check that falls back to `64`: [3](#0-2) 

But `gasTarget` has no such fallback and is used directly as a divisor in both the "above target" and "below target" branches: [4](#0-3) 

Specifically:
- If `parentGasUsed > gasTarget` (line 92-109), the code computes `y := x.Div(x, gasTarget)` (line 102) — this is unconditional except for the short-circuit case where `parentBaseFee` already equals `upperBoundBaseFee`.
- If `parentGasUsed < gasTarget` (line 110-128), the code computes `y := x.Div(x, gasTarget)` (line 120) similarly, unless `parentBaseFee` already equals `lowerBoundBaseFee`.

When `gasTarget == 0`, `parentGasUsed == gasTarget` is only true when `parentGasUsed == 0` (an essentially empty block); for any block with `gasUsed > 0`, execution enters the `>` branch and divides by `SetUint64(0)`. Go's `big.Int.Div` panics on division by zero (unrecoverable runtime panic, not a returned error), unlike the Solidity report where the division-by-zero is a catchable revert. This function is called from consensus-critical and block-production paths, including `blockchain/chain_makers.go` and `work/worker.go` (block assembly) and `blockchain/tx_pool.go` (tx admission/pricing) — the analog of `InterestModel.calculateInterest()` being invoked repeatedly by `Lender.accrueInterest()`.

### Impact Explanation
Once `gasTarget` is set to `0` via a successful governance vote and the parameter takes effect at the next epoch/param-set boundary, all conforming nodes that produce, validate, or price transactions against a non-empty block will panic in `NextMagmaBlockBaseFee`. This is worse than the original Solidity bug (which merely skipped interest accrual and was caught by `try/catch`): here the divide-by-zero is an unrecoverable Go panic, capable of crashing full nodes, halting block production entirely (denial of service to the whole chain), and causing divergence/crash across the network simultaneously since every honest node performing header verification (`blockchain/block_validator.go`'s `VerifyMagmaHeader`) or block assembly hits the same code path. This satisfies the "state divergence between honest nodes" / "acceptance of an invalid transaction or block" criteria via network-wide chain halt.

### Likelihood Explanation
Requires a governance parameter change (`kip71.gastarget = 0`) to be voted in and take effect — this is gated by the governance/voting mechanism, not a single arbitrary unprivileged transaction. However, the prompt's rules explicitly list "governance parameters" as an in-scope reachable analog path, and nothing in the codebase (`kaiax/gov/param.go`, `kaiax/gov/headergov`) prevents a validly-formatted vote proposing `gastarget=0` from being accepted, since `FormatChecker` is a no-op for this specific parameter. The likelihood of the vote being cast intentionally or accidentally is nontrivial given the total absence of a guard that exists for the nearly-identical `BaseFeeDenominator` parameter — this strongly suggests an oversight rather than an intentional design choice.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` rejecting `v == 0`, consistent with `Kip71BaseFeeDenominator`. Additionally, add a defensive zero-check inside `NextMagmaBlockBaseFee` (mirroring the existing `baseFeeDenominator` fallback) so that a `GasTarget` of zero read from a legacy/misconfigured `ChainConfig` cannot crash node processes.

### Proof of Concept
Not executed (no test harness run); reasoning is based on static code tracing:
1. Submit/pass a governance vote setting `kip71.gastarget` to `0` (accepted because `Kip71GasTarget.FormatChecker == noopFormatChecker`).
2. At the next block after the param takes effect, any block with `GasUsed > 0` triggers `parentGasUsed > gasTarget` in `NextMagmaBlockBaseFee`.
3. `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` at [5](#0-4)  panics with division by zero, crashing the calling node process during block assembly/validation.
