### Title
`ReceivedOutput::read` accepts attacker-supplied `offset`/`output`/`outpoint` with no binding check, allowing unspendable outputs to be reported as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) deserializes all three security-relevant fields — `offset`, `output` (a `TxOut` including `script_pubkey` and value), and `outpoint` — directly from attacker-controlled bytes, and never verifies that `output.script_pubkey` equals `p2tr(key + offset * G)`. This is the same bug class as the FOSSBilling advisory: an endpoint reachable by a low-privileged party performs a privileged action (crediting funds to the wallet) without performing the authorization-equivalent check that the legitimate producer (`Scanner::scan_transaction`) always enforces.

### Finding Description
In the honest path, `Scanner::scan_transaction` (mod.rs:199-214) only constructs a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` succeeds, i.e., the output's script is cryptographically bound to a registered scalar offset against the threshold group's key. That binding is what makes the returned output *spendable*: `send.rs` spending logic applies `offset` to the `ThresholdKeys` so the group can produce a BIP-340 signature for the tweaked key.

`ReceivedOutput::read` bypasses that check entirely. Any party who can feed bytes into `read` (deserialization of a remote/untrusted payload, a corrupted scan cache, or any serialized-output channel an integrator treats as untrusted) can produce a `ReceivedOutput` claiming:

- arbitrary `value` (inflating reported wallet balance / incoming funds),
- an `outpoint` referencing a real or fake UTXO,
- an `offset` that does not correspond to `output.script_pubkey` under the group's key.

The struct exposes `offset()`, `output()`, `outpoint()`, and `value()` (mod.rs:99-118) with no way for downstream code to distinguish a scan-produced output from a deserialized forgery.

### Impact Explanation
Funds can be reported as received that are not spendable by the threshold group. If deserialized outputs are queued for spending, the signer set will attempt to sign for a key (`group_key + offset*G` plus tap-tweak) that does not control the referenced UTXO, burning signing rounds and producing batches that fail on-chain — or worse, crediting deposits that can never be moved. An attacker can also graft a real high-value `outpoint`/`TxOut` belonging to someone else with a chosen offset, causing accounting corruption where Serai records received liquidity that does not exist under its keys.

### Likelihood Explanation
Reachability requires an integrator deserializing `ReceivedOutput`s from a source an external party can influence (processor DB sync, network gossip, or persisted scanner state). `read` is `pub`, `cfg(feature = "std")` gated, and takes a plain `Read`. The check it omits is cheap and already implemented two functions away in `scan_transaction` via the `scripts` map. Impact is bounded to mis-accounting/unspendable-funds reporting rather than direct theft (a forged `offset` cannot make an attacker-chosen script spendable by the group, since `p2tr` construction uses an unspendable script path), placing this at Medium severity.

### Recommendation
Either (a) remove the public `read`/`write` round-trip trust assumption by re-validating on deserialization — store the group's `Scanner` alongside and re-run `scripts.get(&output.script_pubkey)`-equivalent validation, or at minimum check `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey`; or (b) document and type-separate the deserialized form (e.g., `UnverifiedReceivedOutput`) so a `ReceivedOutput` can only be produced by `scan_transaction`/`scan_block` or by an explicit verification step that binds `offset` to `script_pubkey`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs reachable via ReceivedOutput::read
// Attacker crafts bytes: [offset][TxOut][OutPoint] where TxOut.script_pubkey
// is NOT p2tr(group_key + offset*G).
let forged: ReceivedOutput = ReceivedOutput::read(&mut &attacker_bytes[..]).unwrap();
// forged.value() reports an arbitrary amount; forged.offset() is arbitrary.
// Any code treating `forged` like a scanner-produced output will attempt to
// spend a UTXO the threshold key does not control.
```
The honest path that `read` fails to replicate is the `self.scripts.get(&output.script_pubkey)` lookup in `Scanner::scan_transaction` (mod.rs:205-211), which guarantees `offset` ↔ `script_pubkey` correspondence.

Note: confirmation is by source analysis only; whether Serai's processor actually round-trips `ReceivedOutput` over an attacker-influenced channel was not fully verified — if serialized outputs only ever come from the node's own `scan_transaction`, practical reachability drops and this becomes a hardened-API concern rather than an exploitable path.
