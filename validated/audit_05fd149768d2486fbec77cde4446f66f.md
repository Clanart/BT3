### Title
Fee/weight estimate in `SignableTransaction::new` ignores the OP_RETURN `data` output, producing under-priced transactions that can be unrelayable/stuck - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` commits to an immutable fee (`needed_fee`) computed from `calculate_weight_vbytes`, but the dummy transaction used for the weight/vbyte estimate is built only from `payments` and `change` — the OP_RETURN output carrying caller-supplied `data` is never included. The signed transaction can therefore be up to ~92 vbytes larger than estimated, silently dropping its effective fee rate below the caller's requested `fee_per_vbyte` and potentially below the network minimum relay fee. Analogous to the immutable `gasLimit` bug in `WormholeTransceiver`, the resource budget is fixed at construction and committed to by the threshold signature (sighash `Prevouts::All` + `TapSighashType::Default`), so it cannot be bumped after signing, and the `TooLowFee`/`MAX_STANDARD_TX_WEIGHT` checks are evaluated against the underestimated weight.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed to `tx_outs` before the weight estimate: [1](#0-0) 

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds a mock `Transaction` whose `output` field is populated **only** from `payments` (plus optional `change`), so the OP_RETURN output contributes zero to `weight`/`vbytes`: [2](#0-1) 

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) underpays by `fee_per_vbyte * data_output_vbytes`. With an 80-byte payload, the OP_RETURN output is ~91–94 bytes of base (non-witness) data, i.e. ~92 vbytes unaccounted.
2. The minimum-relay-fee check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (line 211) uses the same underestimated `vbytes` on both sides, so a transaction can pass the check while its *actual* feerate is below `DEFAULT_MIN_RELAY_TX_FEE` — making it non-relayable by default-policy nodes.
3. The `MAX_STANDARD_TX_WEIGHT` check (line 241) uses `weight` that excludes the data output, so a transaction slightly under the limit can actually exceed it and be rejected as non-standard.
4. Once signed, the fee is immutable: `complete` produces witnesses committing via `taproot_key_spend_signature_hash(i, &Prevouts::All(...), TapSighashType::Default)` (lines 375–386), so the transaction's fee is `sum(inputs) - sum(outputs)` fixed at construction (line 139), and `Sequence::MAX` means no BIP-125 replaceability signaling.

### Impact Explanation
A transaction built with `data` and a `fee_per_vbyte` at or near the caller's intended rate will be broadcast with a materially lower effective feerate. If `fee_per_vbyte` equals the minimum relay rate (1 sat/vB), the actual feerate falls below the minimum and the transaction will not propagate; pending payments are stuck and the inputs are locked until a replacement is constructed and re-signed through the FROST ceremony. Like the WormholeTransceiver finding, re-estimating the budget has no effect on the already-signed transaction — the signature commits to the under-priced output set, so "redelivery with a higher gas limit" requires a full re-sign of a new transaction spending the same inputs (the stale signed tx remains broadcastable-but-stuck). Inputs are not permanently burned, but funds are unspendable until the threshold group coordinates a corrected transaction.

### Likelihood Explanation
Reachable by an unprivileged party: `data` and `fee_per_vbyte` are public inputs to `SignableTransaction::new`, and `data` is only bounded by the 80-byte `TooMuchData` check — any caller supplying data triggers the underestimate. The severity of the shortfall scales with payload size (~92 vbytes max, ~10–15% underestimate for typical small transactions), so the strongest impact (sub-relay-fee, stuck transaction) requires `fee_per_vbyte` to be near the minimum; at higher fee rates the tx is merely cheaper than intended. No malicious validator or leaked key is needed — this is purely untrusted bytes into a public constructor.

### Recommendation
Include the OP_RETURN output in the weight estimate: build the mock transaction in `calculate_weight_vbytes` from the final `tx_outs` (or pass `data`/`payments` consistently), rather than from `payments` alone. Compute `weight`/`vbytes` once after all outputs (payments, OP_RETURN, change) are known — e.g. compute both variants (with/without change) including the data output — and evaluate `needed_fee`, `TooLowFee`, and `MAX_STANDARD_TX_WEIGHT` against the actual final weight.

### Proof of Concept
```rust
// In networks/bitcoin (e.g. tests/wallet.rs), with one confirmed ReceivedOutput
// `output` worth >= 546 + 200 sats, key `key`, script `p2tr_script_buf(key)`:

let data = vec![0u8; 80]; // passes the TooMuchData check (<= 80)
let payments = [(p2tr_script_buf(key).unwrap(), 546)];

// Request the minimum relay fee rate: 1 sat/vB
let signable = SignableTransaction::new(
  vec![output],
  &payments,
  None,
  Some(data),
  1, // fee_per_vbyte at DEFAULT_MIN_RELAY_TX_FEE equivalent
).unwrap(); // TooLowFee check passes using underestimated vbytes

let tx = signable.transaction();
let actual_vsize = /* get_virtual_tx_size(tx.weight()) */;
let actual_fee = signable.fee(); // == needed_fee, fixed forever post-signing

// effective feerate = actual_fee / actual_vsize < 1 sat/vB
// => below DEFAULT_MIN_RELAY_TX_FEE => non-relayable, stuck
assert!(actual_fee < actual_vsize); // holds: ~92 vbytes never charged
```
`calculate_weight_vbytes(1, &payments, None)` produces a mock tx with a single ~43-byte payment output; the real tx additionally carries the ~92-byte OP_RETURN output, so `vsize(real) - vsize(estimated) ≈ 92` while `fee` is unchanged — an under-estimate proven entirely from `send.rs` lines 193–211.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
