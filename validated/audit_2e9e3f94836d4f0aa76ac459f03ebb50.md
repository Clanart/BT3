### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub Enterprise trust classification and redirects native sign-in flow to attacker's server - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The Uniswap report's broken invariant is: an attacker-controlled, easily-forged signal (spot price from a quoter) is trusted directly for a security-critical decision (collateral valuation) with no independent verification. The Desktop analog is structurally identical: an attacker-controlled signal — the `WWW-Authenticate` HTTP header returned by an arbitrary git remote server during authentication — is trusted by `getEndpointKind()` to classify that remote as a genuine "GitHub Enterprise" host, purely because the header string contains `realm="GitHub"`. That classification then drives `promptForGitHubSignIn()`, which opens Desktop's native, "trusted-looking" Sign-in-to-GitHub-Enterprise flow pointed at the attacker's origin.

### Finding Description
When Git needs credentials for a remote, it forwards `WWW-Authenticate` response headers from the server to Desktop's credential-helper trampoline as `wwwauth[...]` fields [1](#0-0) . `getEndpointKind()` treats these headers as authoritative: if any contains `realm="GitHub"` it returns `'enterprise'` for that endpoint, without any cryptographic or out-of-band verification that the server is an actual GitHub Enterprise instance: [2](#0-1) 

This value flows into `getCredential()`. Because the endpoint kind is not `'generic'` and the user has no stored account for that (attacker) endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)` [3](#0-2) , where `endpoint` is the URL of whatever host Git was talking to (i.e., fully attacker-controlled if the user added a malicious remote/fork or was redirected there).

`promptForGitHubSignIn()` then unconditionally trusts that endpoint's `hostname`/`origin` to route the user into the native "Sign in to GitHub Enterprise" dialog, pre-populating the sign-in endpoint with the attacker's origin: [4](#0-3) 

The corrupted value here is the derived `endpointKind` (and consequently the sign-in `endpoint`/`origin`) — it is computed from attacker-controlled network response data (`WWW-Authenticate`) but used as if it were a verified property of a legitimate GitHub Enterprise server. Existing guards don't stop this: `getEndpointKind()`'s earlier checks (`isDotCom`, `isGHE`, existing account lookup) only special-case *already known* hosts; the `wwwauth` heuristic is a fallback specifically meant to *identify new/unknown* GitHub hosts, and it has no allow-list or verification step — any HTTP(S) server can emit `WWW-Authenticate: Basic realm="GitHub"` and be classified as `'enterprise'`.

### Impact Explanation
Because Desktop's own native sign-in dialog is opened and pre-targeted at the attacker's server, the interaction looks like a first-party Desktop workflow rather than an external phishing page, which defeats the user's normal "check the URL" instinct. Depending on how Desktop's Enterprise sign-in dialog subsequently authenticates against that pre-populated endpoint (OAuth device flow vs. legacy basic-auth fallback for older/unsupported GHE instances — noted as historically supported in Desktop for username/password sign-in against enterprise servers, though this was not independently re-verified within the tool budget of this session), this can range from confusing UX to leaking the user's real GitHub Enterprise username/password or a generated token directly to the attacker-controlled host, since the destination of the authentication request is the attacker's server, not the user's real enterprise instance. This satisfies the "credential/token exfiltration" and "unauthorized OAuth/account binding" impact categories, driven purely by data returned from an untrusted git remote/proxy response — no local access, admin rights, or prior malware required.

### Likelihood Explanation
Triggering this requires only that the user's Desktop client perform a Git network operation (fetch/pull/push/clone) against a remote controlled by, or interposed by (e.g., MITM proxy, malicious fork, compromised self-hosted server), an attacker, and that the remote respond with a crafted `WWW-Authenticate` header — something any HTTP server operator fully controls. Since Desktop routinely fetches/authenticates against remotes configured in cloned repositories (including remotes an attacker could add via a malicious fork's `.git/config` or a crafted remote URL the user is asked to add), and the header spoofing requires no interaction with git internals, the precondition is realistic and unprivileged.

### Recommendation
Do not classify a remote as `'enterprise'` (GitHub Enterprise) based solely on a self-reported `WWW-Authenticate` realm string. Require corroborating, attacker-uncontrollable evidence before offering the "Sign in to GitHub Enterprise" flow for an unknown host — e.g., verify via a request to that host's `/api/v3/meta` (or equivalent GHE-specific API) with expected response shape/certificate pinning, or simply fall back to the generic username/password credential prompt (clearly labeled as an unverified/generic Git host) instead of the trusted-branded Enterprise sign-in UI whenever the endpoint isn't already a known/previously-authenticated account.

### Proof of Concept
1. Attacker stands up an HTTPS git server (or a MITM/malicious fork remote) at `https://evil.example.com/repo.git`.
2. Victim adds/clones this as a remote in GitHub Desktop and performs a fetch/pull requiring auth.
3. Attacker's server responds to Git's credential probe with `WWW-Authenticate: Basic realm="GitHub"`.
4. `getEndpointKind()` returns `'enterprise'` for `https://evil.example.com` [5](#0-4) .
5. Since no account matches this endpoint, `promptForGitHubSignIn('https://evil.example.com')` is invoked, opening Desktop's native "Sign in to GitHub Enterprise" dialog with the sign-in endpoint pre-set to `evil.example.com` [6](#0-5) .
6. The victim, believing this is Desktop's legitimate first-party sign-in surface, completes authentication against the attacker's server.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
