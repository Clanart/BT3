### Title
Unauthenticated `SetOperatorKeys` RPC lets any caller front-run an operator's BitVM commitment, permanently blocking that operator's reimbursement - (File: core/src/rpc/verifier.rs)

### Summary
The `ClementineVerifier.SetOperatorKeys` RPC has no caller authentication and writes operator-identifying protocol state (BitVM Winternitz public keys and challenge-ACK hashes) keyed only by a public `operator_xonly_pk` and a deposit outpoint. Because the underlying database insert is "insert-if-not-exists", the *first* caller to submit keys for an `(operator_xonly_pk, deposit_outpoint)` pair wins, and the legitimate operator's later, correct submission is silently discarded. Any unprivileged gRPC caller reaching a verifier can therefore front-run the real key-distribution step of the deposit flow, permanently corrupting that operator's committed BitVM/Winternitz roots for that deposit.

### Finding Description
`SetOperatorKeys(OperatorKeysWithDeposit) returns (Empty)` is defined with no access-control annotation or caller check: [1](#0-0) 

The trait method and server implementation accept the request from any client that can reach the verifier's gRPC endpoint, performing no signature or identity check binding the request to the `operator_xonly_pk` it claims to act for: [2](#0-1) [3](#0-2) 

The handler `Verifier::set_operator_keys` only validates the deposit (`is_deposit_valid`) and the *shape* of the payload (correct number of Winternitz keys / ACK hashes) - it never verifies that the caller possesses the operator's private key or is otherwise authorized to submit keys on that operator's behalf: [4](#0-3) 

It then persists the attacker-controlled Winternitz keys and derives/stores the BitVM assert/disprove taproot root hashes from them: [5](#0-4) 

The persistence layer uses `ON CONFLICT DO NOTHING`, so whichever caller writes first for a given `(xonly_pk, deposit_id)` becomes permanent; a subsequent legitimate write from the real operator is silently dropped: [6](#0-5) 

The binding that should hold is: *BitVM Winternitz keys stored for operator X on deposit D == keys operator X itself generated for D*. Before the attack, this equality holds for every operator that has been given a chance to register first. After an unauthenticated caller calls `SetOperatorKeys` with operator X's public `operator_xonly_pk` (discoverable via `GetXOnlyPublicKey`) and attacker-chosen key material for a not-yet-registered deposit, the equality breaks: the DB permanently holds attacker-chosen keys attributed to operator X, and operator X's real registration attempt is a no-op due to `ON CONFLICT DO NOTHING`.

### Impact Explanation
Once verifiers hold the wrong BitVM Winternitz commitments/root hashes for operator X on deposit D, any assert/disprove transaction operator X produces for that deposit using its real (correct) Winternitz preimages will not match what verifiers committed to. This makes it impossible for the honest operator to be reimbursed for that deposit going forward (its kickoff/assert flow for that specific deposit is corrupted at the verifier layer), matching the Critical category "an honest operator permanently unable to be reimbursed." This is a direct RPC-level analog to the reported `proposeSetConsensusTargetRate` issue: an externally-callable, state-mutating method with no access control, where an unprivileged caller can bind arbitrary parameters to a victim identity/protocol object.

### Likelihood Explanation
Exploitation requires only network access to a verifier's gRPC endpoint and knowledge of the target operator's `operator_xonly_pk` (obtainable via the unauthenticated `GetXOnlyPublicKey`/public operator registry) and the deposit outpoint being set up (which is not secret - it's the on-chain deposit transaction that verifiers must validate as legitimate via `is_deposit_valid`). The race is against the normal, once-per-deposit key-distribution step done by the aggregator, so an attacker simply needs to submit before the aggregator forwards the operator's real keys.

### Recommendation
Require the `SetOperatorKeys` call to be authenticated as originating from the aggregator (or from the operator itself via a signature over the submitted keys/deposit outpoint), and reject/overwrite-protect only after verifying that authorization, rather than relying purely on "insert if not exists" semantics with an open RPC surface.

### Proof of Concept
1. Discover an operator's `operator_xonly_pk` via the unauthenticated `GetXOnlyPublicKey` RPC, and observe a fresh deposit outpoint on Bitcoin destined for that operator's setup (deposit outpoints are public on-chain data).
2. Before the aggregator's `new_deposit`/key-distribution flow reaches the verifiers, an attacker directly calls each verifier's `SetOperatorKeys` RPC with the victim operator's `operator_xonly_pk`, the real `deposit_outpoint`, and attacker-generated Winternitz public keys / challenge-ACK hashes (structurally valid: correct counts as checked in `core/src/verifier.rs:1746` and `core/src/verifier.rs:1770`).
3. Verifier's DB insert succeeds (`insert_operator_bitvm_keys_if_not_exist`, `insert_operator_challenge_ack_hashes_if_not_exist`) because no prior row exists.
4. When the legitimate operator later performs the real key distribution for that deposit through the aggregator, the verifier's `SetOperatorKeys` again calls the same "insert if not exists" functions, which are now no-ops (`ON CONFLICT DO NOTHING`), so the operator's genuine keys are never stored.
5. The operator subsequently cannot produce valid BitVM asserts for that deposit matching the corrupted verifier-side commitments, permanently losing the ability to be reimbursed for it.

    pub async fn set_operator_keys(
        &self,
        mut deposit_data: DepositData,
        keys: OperatorKeys,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<(), BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        self.citrea_client
            .check_nofn_correctness(deposit_data.get_nofn_xonly_pk()?)
            .await?;

        self.is_deposit_valid(&mut deposit_data).await?;

        self.db
            .insert_deposit_data_if_not_exists(
                Some(&mut dbtx),
                &mut deposit_data,
                self.config.protocol_paramset(),
            )
            .await?;

        let hashes: Vec<[u8; 20]> = keys
            .challenge_ack_digests
            .into_iter()
            .map(|x| {
                x.hash.try_into().map_err(|e: Vec<u8>| {
                    eyre::eyre!("Invalid hash length, expected 20 bytes, got {}", e.len())
                })
            })
            .collect::<Result<Vec<[u8; 20]>, eyre::Report>>()?;

        if hashes.len() != self.config.get_num_challenge_ack_hashes(&deposit_data) {
            return Err(eyre::eyre!(
                "Invalid number of challenge ack hashes received from operator {:?}: got: {} expected: {}",
                operator_xonly_pk,
                hashes.len(),
                self.config.get_num_challenge_ack_hashes(&deposit_data)
            ).into());
        }

    /// Sets Winternitz public keys for bitvm related inputs of an operator.
    pub async fn insert_operator_bitvm_keys_if_not_exist(
        &self,
        mut tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
        deposit_outpoint: OutPoint,
        winternitz_public_key: Vec<WinternitzPublicKey>,
    ) -> Result<(), BridgeError> {
        let wpk = borsh::to_vec(&winternitz_public_key).wrap_err(BridgeError::BorshError)?;
        let deposit_id = self
            .get_deposit_id(tx.as_deref_mut(), deposit_outpoint)
            .await?;
        let query = sqlx::query(
                "INSERT INTO operator_bitvm_winternitz_public_keys (xonly_pk, deposit_id, bitvm_winternitz_public_keys) VALUES ($1, $2, $3)
                ON CONFLICT DO NOTHING;",
            )
            .bind(XOnlyPublicKeyDB(operator_xonly_pk))
            .bind(i32::try_from(deposit_id).wrap_err("Failed to convert deposit id to i32")?)
            .bind(wpk);

        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
