### Title
Copilot conflict-marker miscounting causes silent misapplication/loss of AI merge resolutions and lets raw conflict markers be committed - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot merge-conflict resolution feature extracts conflict hunks with one parser (`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts`) to build the model prompt, then splices the model's per-hunk answers back into the file with a **second, independently-written** parser (`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts`). The two parsers use subtly different marker-matching logic. When a conflicted file's `ours` region happens to contain a line that matches the `>>>>>>>` regex (attacker-controlled content merged into the repo, e.g. a text/markdown/code file that legitimately contains a line of 7+ `>` characters), the two parsers disagree about where the conflict block ends. The counting parser (used for the prompt) treats it as one well-formed hunk; the splicing parser treats the same block as malformed and refuses to touch it — while, for any hunks that follow, `hunkIndex` desynchronizes, so a later hunk’s resolution gets spliced into the wrong location, or a hunk with valid AI content never gets consumed at all. This is the same class of bug as the GoGoPool report: an unchecked assumption (“the two counts agree”) that is silently violated by attacker-influenced input, corrupting output instead of failing loudly.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-278`) walks the file line by line. When collecting the "ours" side of a hunk it only stops at a `|||||||` or `=======` line: [1](#0-0) 
Any line that happens to match the theirs-marker pattern (`^>{7}(?:\s|$)`) is *not* treated specially here — it's collected as ordinary "ours" text, so the hunk is reported as well-formed and complete, with that line embedded in `oursContent`.

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) re-scans the same raw file independently, using its own copies of the marker regexes: [2](#0-1) 
Its lookahead loop breaks out the instant it sees *any* line matching the theirs-marker regex, whether or not a `=======` separator has been seen first: [3](#0-2) 
If the embedded look-alike `>>>>>>>` line inside the real "ours" content is hit before the real `=======` separator, `hasSeparator` is still `false` when the loop breaks, so the block is classified malformed: [4](#0-3) 
The `<<<<<<<` marker line is pushed through as plain text, `i` only advances by one, and — critically — `hunkIndex` is **not** incremented. Parsing then resumes mid-conflict-block treating the real `=======`, the real `theirs` text, and the real closing `>>>>>>>` as ordinary file lines, all copied through verbatim into the "resolved" output.

Because `extractConflictHunks` counted this as hunk N (and the model dutifully returned a resolution for hunk N), but `reassembleResolvedFile` never consumes it, two things happen:
- The resolution intended for this hunk is dropped.
- `hunkIndex` fails to advance, so the resolution for this hunk gets applied to whatever *next* real conflict block is encountered instead — silently splicing the wrong merged content into a different location in the file.

### Impact Explanation
`_applyCopilotConflictResolutions` (`app/src/ui/…` via `app-store.ts:7169-7269`) writes `resolution.resolvedContent` straight to disk and stages it with `git add` once the user clicks "Continue Merge": [5](#0-4) 
There is no post-write verification that the reassembled content is free of `<<<<<<<`/`=======`/`>>>>>>>` markers or that hunk counts matched. Consequently:
- A file can be committed (and pushed) still containing raw, unresolved conflict markers mixed with real code, which is invalid/broken source that silently lands on the target branch.
- A resolution meant for one conflict region can be spliced into an unrelated conflict region in the same file, silently corrupting the file's semantics without any error or warning to the user, who believes the merge was cleanly resolved by Copilot.

This satisfies the "silent corruption of what the user commits or pushes" impact class: the attacker only needs to control content that ends up on one side of a merge (a PR/branch the victim merges, rebases, or cherry-picks against), not local access, credentials, or admin rights.

### Likelihood Explanation
Any text, markdown, config, or code file can legitimately contain a line consisting of 7+ `>` (or `<`) characters followed by whitespace or end-of-line — e.g., blockquote markers in markdown, ASCII banners, changelog formatting, or minified/generated content. An attacker who authors a branch/PR that the victim later merges with Copilot's "Resolve with Copilot" feature can deliberately place such a line inside a hunk that will conflict, making the exploit reliable and repeatable rather than probabilistic. The feature is specifically designed to run over externally-authored branches (that's the entire point of merge conflict resolution), so the attacker-influence path is direct.

### Recommendation
Do not maintain two independently-implemented marker scanners. `reassembleResolvedFile` should reuse the exact same hunk boundaries already computed by `extractConflictHunks` (e.g., by returning marker line indices alongside `IConflictHunk`) instead of re-deriving them from raw text with different rules. As defense in depth, after reassembly, assert that: (1) `hunkIndex === hunkResolutions.length` (all resolutions were consumed), and (2) the final `resolvedContent` contains no lines matching the conflict-marker regexes. If either check fails, treat the file as unresolved/skip it and surface the failure to the user instead of writing the corrupted content to disk.

### Proof of Concept
1. Attacker pushes/opens a branch where a file (e.g. `NOTES.md`) contains, as legitimate content on the attacker's side of a future merge, a line that is exactly `>>>>>>> release-notes` (7 `>` + space + text) inside a region that will conflict with the victim's local changes.
2. Victim merges/rebases against this branch in Desktop; git produces on-disk conflict markers around the change, e.g.:
   ```
   <<<<<<< HEAD
   victim's actual change
   >>>>>>> release-notes
   =======
   attacker's actual change
   >>>>>>> feature
   ```
   (the middle `>>>>>>> release-notes` line is genuine content from the attacker's side, not a real closing marker).
3. `extractConflictHunks` reports one well-formed hunk (`oursContent` includes the embedded `>>>>>>> release-notes` line, `theirsContent = "attacker's actual change"`); the model is asked to resolve it and returns a merged replacement.
4. `reassembleResolvedFile` re-scans the raw content, hits the embedded `>>>>>>> release-notes` line first, treats the whole `<<<<<<<` block as malformed, and copies the real `=======`/theirs/`>>>>>>>` lines through unchanged. If any further real conflict hunk exists later in the same file, its `hunkIndex` is now off by one and the model's resolution for the *first* hunk gets spliced into the *second* hunk's location instead.
5. The user clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes and `git add`s the file as-is — the committed file contains leftover raw conflict markers and/or a resolution applied to the wrong location, with no warning shown. [6](#0-5) [7](#0-6)
