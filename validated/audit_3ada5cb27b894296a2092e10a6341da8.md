### Title
PedPoP encryption key registration accepts the identity point, causing secret shares to be encrypted under a publicly-known ChaCha20 key - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

The external report concerns an unauthenticated endpoint feeding attacker-controlled input into a privileged evaluator. The Serai analog: `EncryptionKeyMessage::read` in `crypto/dkg/pedpop/src/encryption.rs:57-59` reads each participant's ECDH encryption key with `C::read_G` (`Ciphersuite::read_G`), which enforces canonicality but does **not** reject the identity point (`crypto/ciphersuite/src/lib.rs:91-101`). Only `frost::Curve::read_G` rejects identity (`crypto/frost/src/curve/mod.rs:125-131`), and PedPoP deliberately uses the ciphersuite-level reader. A malicious DKG participant can therefore register `enc_key = identity`; every honest party then ECDH-encrypts that participant's secret shares to `identity * key = identity`, deriving a ChaCha20 key from a publicly-known constant. The shares are recoverable by anyone observing the ciphertexts.

### Finding Description

The PedPoP DKG encrypts per-participant secret shares with a per-message key combined via ECDH against the recipient's registered encryption key:

- `EncryptionKeyMessage::read` parses `enc_key` via `C::read_G` — canonicality check only, no identity rejection:
  `crypto/dkg/pedpop/src/encryption.rs:57-59`.
- `Decryption::register` / `Encryption::register` store `msg.enc_key` verbatim, only asserting no re-registration (`encryption.rs:351-362`).
- `encrypt` computes `ecdh(key, to) = to * key` (`encryption.rs:95-97, 153-154`). If `to` is the identity, the shared point is the identity.
- `cipher` derives the ChaCha20 key from a transcript containing only `context` and `shared_key` (`encryption.rs:101-133`). With `shared_key = identity.to_bytes()`, the key is fully determined by the public `context` — computable by anyone.

For Ristretto and Ed25519 (dalek-ff-group), the identity has a canonical encoding (`[0; 32]` Ristretto; `01 00…00` Ed25519) that passes `from_bytes` and the `to_bytes` round-trip; the torsion check accepts it since identity is in the prime subgroup (`crypto/dalek-ff-group/src/lib.rs:429-446`). Nothing downstream rejects it — the PoP/registration flow carries no proof of knowledge over `enc_key` at all (unlike `Commitments`, which carries a Schnorr PoK over `commitments[0]`).

Contrast with FROST's `Curve::read_G`, which explicitly rejects identity (`crypto/frost/src/curve/mod.rs:123-131`) — the protection exists in the codebase but is not applied on this path.

### Impact Explanation

Every honest participant `i` calls `self.encryption.encrypt(rng, l, share)` for each other participant `l` (`crypto/dkg/pedpop/src/lib.rs:359-369`). Shares destined for the malicious participant `M` (who registered `enc_key = identity`) are XORed with a keystream derived from the constant identity shared key. Any party who observes the `EncryptedMessage<C, SecretShare>` ciphertexts to `M` (including every other participant who receives the same broadcast transcript, or any network observer) can recompute the cipher and recover `M`'s received shares — shares belonging to honest signers. Combined with the observer's own share, an attacker can accumulate more shares than their legitimate allotment, defeating the `t`-of-`n` threshold: e.g., in a 2-of-3, a malicious participant who also eavesdrops obtains their own share plus `n-1` leaked shares, recovering the full group secret key. This is key-share/group-key recovery reachable purely from bytes an unprivileged DKG participant supplies to `EncryptionKeyMessage::read`.

### Likelihood Explanation

Exploitation requires only that the attacker be a participant in the DKG and submit a malformed `EncryptionKeyMessage` — a single 32-byte identity encoding in place of `enc_key`. No authentication, collusion, or computational work is needed; the field inputs (context, identity encoding) are public constants. The only mitigation is out-of-band: callers discarding inconsistent transcript views, which does not prevent the cryptographic leakage itself.

### Recommendation

Reject the identity point for `enc_key` in `EncryptionKeyMessage::read` (use `frost::Curve::read_G`-style validation, or check `enc_key.is_identity()` after `C::read_G`). More robustly, require a Schnorr proof of knowledge over `enc_key` at registration time — as `Commitments` already does for `commitments[0]` — so keys with unknown discrete logs (including identity) cannot be registered. Apply the same check to `EncryptedMessage::read`'s `key` field (`encryption.rs:171-176`), which is also read via `C::read_G` and used in `ecdh`.

### Proof of Concept

Conceptual reproduction for `C = Ristretto`:

1. Attacker `M` (Participant 2) runs `KeyGenMachine::generate_coefficients` normally, but before broadcasting replaces the `enc_key` field of its `EncryptionKeyMessage<Commitments>` with the identity encoding. Equivalently, it serializes the message and overwrites the trailing 32 bytes with `00…00` (Ristretto identity). The message passes `EncryptionKeyMessage::read` and `register` on all honest nodes.
2. Each honest participant `i` executes `generate_secret_shares`, computing `ecdh(key_ij, identity) = identity` and `ChaCha20(key = H(context || identity_bytes), iv = "DKG IV v0.2\0")` applied to `SecretShare` ciphertexts addressed to `M`.
3. The attacker (or any observer) reads the ciphertext bytes of each `EncryptedMessage` sent to `M`, re-derives `cipher(context, identity)` — all inputs are public — and XORs the keystream to recover every honest share sent to `M`.
4. Attacker combines the `n-1` recovered shares with its own to interpolate the group secret with fewer than `t` cooperating parties, breaking the threshold assumption (full key recovery when `n-1 ≥ t`).
