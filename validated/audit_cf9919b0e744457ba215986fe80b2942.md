### Title
Withdrawal `idx` deduplication is missing on `withdrawal_utxo_txid`/`vout`, allowing one fronted payout to satisfy multiple withdrawal indices and double-reimburse an operator - (`core/src/database/verifier.rs`)

### Summary
The `withdrawals` table has no uniqueness constraint tying `withdrawal_utxo_txid`/`withdrawal_utxo_vout` to a single `idx`, and `get_payout_txs_for_withdrawal_utxos` joins the spent-UTXO table purely on `(txid, vout)`, not on `idx`. If two `withdrawals` rows (two different Citrea withdrawal indices) ever end up holding the same physical withdrawal UTXO, a single Bitcoin payout transaction that spends that UTXO gets attributed to **both** `idx` rows, letting an operator who fronted exactly one payout be reimbursed for two (or more) deposits.

### Finding Description
The broken binding is: `withdrawals.idx` credited with a payout == the specific fronted withdrawal that `idx` represents, counted exactly once. The code never enforces `withdrawal_utxo_txid/vout` uniqueness across `idx` values:

- `core/src/database/schema.sql:269-281` defines `withdrawals(idx primary key, ..., withdrawal_utxo_txid, withdrawal_utxo_vout, ...)` with **no unique constraint** on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`.
- `update_withdrawal_utxo_from_citrea_withdrawal` (`core/src/database/verifier.rs:108-135`) blindly writes whatever `(txid, vout)` Citrea reports for a given `citrea_idx`, with no check against other rows.
- `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) joins `withdrawals w` to `bitcoin_syncer_spent_utxos bsu` on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout` — if two rows `w` share the same UTXO, **both** rows match the single spending transaction recorded in `bsu`.
- `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`) then writes the same `payout_txid`/`payout_payer_operator_xonly_pk` onto both `idx` rows.
- `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`) and `mark_payout_handled` (`core/src/database/verifier.rs:348-362`) key exclusively on `idx`, so `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) will independently discover and process **each** `idx` as an unhandled payout, calling `handle_finalized_payout` (`core/src/operator.rs:839-...`) once per `idx`.

Root cause: the withdrawal UTXO -> `idx` mapping is assumed 1:1, driven by Citrea's `withdrawalUTXOs(index)` mapping (`core/src/citrea.rs:458-496`), but this repository never validates that assumption when ingesting withdrawal data, and `Operator::withdraw` (`core/src/operator.rs:560-637`) does not check whether the `in_outpoint` has already been registered for another `withdrawal_index`, nor whether it's already spent (unlike `sign_optimistic_payout`, which does call `is_utxo_spent`, `core/src/verifier.rs:1581-1586`).

Exploit flow: the attacker (who controls Citrea `withdraw()`/`safeWithdraw()` calls and chooses the withdrawal UTXO bytes) registers the SAME physical outpoint for two different withdrawal indices on Citrea (funding each registration per Citrea's own accounting, which is out of scope to further re-verify here but is a precondition, not a fix present in this repo). Once both `withdrawals` rows in this repo have identical `withdrawal_utxo_txid/vout` with distinct `idx`, only one Bitcoin transaction can ever spend that outpoint (paid for by one operator). `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) sees this single spend match via the join and records it against both `idx` rows with the same operator `xonly_pk`. That operator's `PayoutCheckerTask` then calls `handle_finalized_payout` twice — once per `idx`/deposit — since each `idx` maps to its own `move_to_vault_txid`/`deposit_id`, and `handle_finalized_payout` grants a fresh kickoff/reimbursement per `deposit_id` (`core/src/operator.rs:839-885`, `validate_payer_is_operator` at `core/src/operator.rs:1686-1740`) with no cross-check that the same physical payout has already discharged another deposit's obligation.

### Impact Explanation
The operator is reimbursed for two deposits' worth of collateral while having fronted only one payout transaction; BTC leaves the second deposit's move-to-vault UTXO without ever having a matching fronted withdrawal for it. This matches the Critical category: "an operator reimbursed for a payout it never funded." The blast radius scales with however many withdrawal indices the attacker can register against the same UTXO, and is repeatable across deposits/operators as long as duplicate `(withdrawal_utxo_txid, vout)` registrations across `idx` can occur.

### Likelihood Explanation
This finding's exploitability inside this repository depends entirely on whether an unprivileged withdrawer can actually get Citrea's bridge contract to register the same `(txid, vout)` pair under two different withdrawal indices — that registration path lives in the Citrea smart contract, which is explicitly out of scope for this audit ("third-party crate, Citrea contract... defects with no path through this repository" are rejected). Within this repository, no additional defense exists to catch or reject such duplicate registrations before they propagate into double payout attribution, so if the precondition holds, the exploit is deterministic and repeatable at low additional cost (one payout's worth of BTC fees) for each extra `idx` compromised.

### Recommendation
Add a unique constraint on `withdrawals(withdrawal_utxo_txid, withdrawal_utxo_vout)` (nullable-safe), and have `update_withdrawal_utxo_from_citrea_withdrawal` reject/alert when a UTXO is already used by a different `idx`. Additionally, change `get_payout_txs_for_withdrawal_utxos`/`update_finalized_payouts` to attribute a spent UTXO to at most one `idx` (e.g., by tracking which `idx` first observed that UTXO, or storing a spent-UTXO -> single idx uniqueness invariant enforced at the DB level) so a single Bitcoin spend can never satisfy more than one withdrawal index.

async fn duplicate_withdrawal_utxo_double_credits_payout() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    let mut dbtx = db.begin_transaction().await.unwrap();

    let txid = Txid::from_byte_array([0x45; 32]);
    let utxo = OutPoint { txid: Txid::from_byte_array([0x99; 32]), vout: 0 };
    let operator_pk = generate_random_xonly_pk();
    let block_hash = BlockHash::all_zeros();

    // Two distinct deposits/idx values, each with its own move_to_vault_txid
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), 5, &Txid::from_byte_array([1;32])).await.unwrap();
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), 6, &Txid::from_byte_array([2;32])).await.unwrap();

    // Both idx=5 and idx=6 registered with the SAME withdrawal UTXO (simulating Citrea contract state)
    let block_id = db.insert_block_info(Some(&mut dbtx), &block_hash, &block_hash, 0).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), 5, utxo, block_id).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), 6, utxo, block_id).await.unwrap();

    // A single Bitcoin transaction spends that UTXO once
    db.insert_txid_to_block(&mut dbtx, block_id, &txid).await.unwrap();
    db.insert_spent_utxo(&mut dbtx, block_id, &txid, &utxo.txid, utxo.vout.into()).await.unwrap();

    // Verifier attributes the single spend to BOTH idx rows
    db.update_payout_txs_and_payer_operator_xonly_pk(
        Some(&mut dbtx),
        vec![(5, txid, Some(operator_pk), block_hash), (6, txid, Some(operator_pk), block_hash)],
    ).await.unwrap();

    // Assertion: both idx=5 and idx=6 are independently "unhandled payouts" for the same operator,
    // meaning PayoutCheckerTask will call handle_finalized_payout twice for one fronted tx.
    let first = db.get_first_unhandled_payout_by_operator_xonly_pk(Some(&mut dbtx), operator_pk).await.unwrap().unwrap();
    assert_eq!(first.0, 5);
    db.mark_payout_handled(Some(&mut dbtx), 5, Txid::from_byte_array([9;32])).await.unwrap();

    let second = db.get_first_unhandled_payout_by_operator_xonly_pk(Some(&mut dbtx), operator_pk).await.unwrap().unwrap();
    assert_eq!(second.0, 6); // BUG: same physical payout tx credits a second, unrelated deposit idx
}

        let unhandled_payout = self

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;

            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;

        dbtx.commit().await?;

        Ok(true)
    }

            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())
    }
