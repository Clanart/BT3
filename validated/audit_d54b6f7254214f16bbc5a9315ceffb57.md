### Title
BSC consensus verifier accepts sub-2/3 validator quorums due to floor-division threshold, breaking BFT safety and permitting false state commitment acceptance - ([File: modules/consensus/bsc/verifier/src/lib.rs])

### Summary
`verify_bsc_header` in `modules/consensus/bsc/verifier/src/lib.rs` accepts a BSC (Parlia) consensus update whenever `participant_count >= floor(2 * N / 3)`, i.e. it only rejects when `participant_count < (2*N)/3` [1](#0-0) . This is the same class of rounding-down bug as the external report's `no_guards/2` short-circuit threshold: whenever `2*N` is not a multiple of `3`, integer division truncates the true supermajority requirement downward, so the check accepts a set of signers that is strictly *less* than two-thirds of the validator set.

### Finding Description
Every other quorum/supermajority check in this same codebase consistently rounds the BFT threshold **up** by adding `+1` after the floor division, to guarantee that any two accepted quorums must overlap in at least one honest validator:
- `modules/consensus/beefy/verifier/src/lib.rs` (`check_participation_threshold`): `len >= ((2 * total) / 3) + 1` [2](#0-1) 
- `modules/consensus/pharos/verifier/src/lib.rs` (`verify_stake_threshold`): `required = (total_stake * 2 / 3) + 1` [3](#0-2) 
- `modules/consensus/sync-committee/verifier/src/lib.rs`: `sync_aggregate_participants < ((2 * committee_size as u64) / 3) + 1` [4](#0-3) 
- `tesseract/messaging/evm/src/byzantine.rs` and `tesseract/messaging/fisherman/src/quorum.rs`: `total * 2 / 3 + 1` [5](#0-4) 

The BSC verifier is the outlier: it omits the `+1`, so it accepts `participant_count == floor(2N/3)` as sufficient. For any `N` where `2N` is not divisible by 3 (e.g. `N = 22, 25, 28...`), `floor(2N/3)` is strictly less than the true `2N/3` supermajority. Concretely for `N = 22`: true threshold is `14.67`, but the code accepts `participant_count = 14`. Two independently signed, non-overlapping subsets of size 14 each (28 total signatures) can exist among 22 validators only with overlap, but the key BFT safety property — that any two quorums meeting the threshold *must* share at least one honest signer — requires threshold `> 2N/3`, not `>= floor(2N/3)`. With the off-by-one-shy threshold, an attacker controlling roughly one-third of validators (still under the honest-majority assumption elsewhere in the protocol) has a materially larger window to assemble a fraudulently-attested vote set — the exact same "rounds down, so short-circuits/finalizes prematurely with insufficient votes" defect as the M-09 report, just applied to Parlia BLS quorum instead of guard down-votes.

This verifier result flows directly into `BscClient::verify_consensus` (`modules/ismp/clients/bsc/src/lib.rs`), which takes the returned `finalized_header.state_root` and persists it as the trusted `StateCommitment` for the BSC/BSC-Testnet state machine [6](#0-5) . That state commitment is what `handlePostRequests`/`handleGetResponses` and other proof-consuming handlers on Hyperbridge trust to validate cross-chain request/response Merkle proofs, i.e., it is the root of trust for money-moving message dispatch on the BSC side of the bridge.

### Impact Explanation
Accepting a sub-supermajority-signed header as finalized allows a false BSC state commitment to become the trusted root for state/request proofs. Because Hyperbridge's request/response handlers (`handlePostRequests`, `handleGetResponses` in `evm/src/core/HandlerV2.sol`) verify Merkle proofs against exactly this stored `stateMachineCommitment`, a forged/insufficiently-attested state root can be used to fabricate proofs of requests/responses that never happened on BSC, enabling unauthorized dispatch, and potentially fund loss on the bridge — squarely inside the bounty's "false proof/state acceptance" and "unauthorized transaction or execution" categories.

### Likelihood Explanation
This requires no malicious relayer, prover, or admin — an attacker only needs to gather a subset of validator signatures reaching `floor(2N/3)` (instead of the true `floor(2N/3)+1`) for a given `N`, then submit the resulting `BscClientUpdate` through the ordinary, unprivileged consensus-update path (`verify_consensus`). The window is small (typically exactly one fewer signer needed than the theoretically-required minimum) but is a strict logic bug independent of any external actor's honesty — it is a deterministic miscalculation baked into the verifier, matching the report's "rounds down so it can be short-circuited" pattern.

### Recommendation
Change the rejection condition in `verify_bsc_header` from `participant_count < ((2 * current_validators.len()) / 3)` to `participant_count < ((2 * current_validators.len()) / 3) + 1`, matching the `+1` convention used consistently by every other supermajority check in this codebase (`beefy`, `pharos`, `sync-committee`, `byzantine.rs`, `fisherman/quorum.rs`).

### Proof of Concept
1. Configure a BSC consensus state with `N = 22` current validators.
2. Craft a `BscClientUpdate` whose `vote_address_set` bitvector has exactly `14` bits set (any 14 of the 22 validators), with a valid BLS aggregate signature from those 14 signers over `vote_data`.
3. Submit via `BscClient::verify_consensus` (or directly call `verify_bsc_header`). `participant_count = 14`, and `(2 * 22) / 3 = 14` (integer division), so `14 < 14` is `false` — verification proceeds and the header is accepted as finalized, even though 14/22 ≈ 63.6%, strictly less than the required 2/3 (66.7%) supermajority.
4. Compare against `modules/consensus/beefy/verifier/src/lib.rs::check_participation_threshold`, which for the same `N=22` requires `>= 15` (`(2*22)/3 + 1 = 15`) — the BSC path lets a strictly weaker attestation through the identical safety-critical check. [1](#0-0) [2](#0-1)
