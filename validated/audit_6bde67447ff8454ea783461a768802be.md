### Title
`host_deposit_constant` Passes `deposit_value_bytes` Instead of `move_txid`, Causing Permanent Bridge Proof Generation Failure and Operator Collateral Slashing - (File: bridge-circuit-host/src/structs.rs)

### Summary

The `host_deposit_constant` function in `bridge-circuit-host/src/structs.rs` passes `deposit_value_bytes` (the deposit amount in wei from the Citrea storage proof) as the 4th argument to `deposit_constant`, where `move_txid` (the Bitcoin move-to-vault transaction ID) is required. The ZK circuit in `circuits-lib/src/bridge_circuit/mod.rs` correctly uses `move_txid`. This mismatch causes the journal hash check inside `prove_bridge_circuit` to always fail, permanently preventing the operator from generating a valid bridge proof. Without a valid proof, the operator cannot respond to challenges, and their collateral is unconditionally burned.

### Finding Description

The `deposit_constant` function signature is:

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],       // ← 4th parameter: move-to-vault txid
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant
``` [1](#0-0) 

Three call sites pass `move_txid` correctly:

**ZK circuit** (`circuits-lib/src/bridge_circuit/mod.rs:221-229`):
```rust
let deposit_constant = deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    *move_txid,   // ← correct: move txid from verify_storage_proofs
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
);
``` [2](#0-1) 

**On-chain script builder** (`core/src/builder/transaction/creator.rs:749-757`): [3](#0-2) 

**Verifier additional disprove** (`core/src/verifier.rs:2478-2486`): [4](#0-3) 

However, `host_deposit_constant` in `bridge-circuit-host/src/structs.rs` passes the **wrong value**:

```rust
let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    deposit_value_bytes,  // ← BUG: deposit amount in wei, not move_txid
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
``` [5](#0-4) 

`host_deposit_constant` is called by `SuccinctBridgeCircuitPublicInputs::new()`: [6](#0-5) 

Which is used in `prove_bridge_circuit` to compute the expected journal hash, then compared against the actual ZK circuit output:

```rust
if *journal_hash.as_bytes() != succinct_receipt_journal {
    return Err(eyre!("Journal hash mismatch"));
}
``` [7](#0-6) 

Since `deposit_value_bytes` (a 32-byte big-endian encoding of the deposit amount in wei) is never equal to `move_txid` (a Bitcoin transaction ID), this check **always fails** in production.

### Impact Explanation

The operator calls `prove_bridge_circuit` to generate the bridge proof needed to respond to a BitVM challenge. Because the journal hash check always fails, the operator can never produce a valid proof. Without a valid proof, the operator cannot send correct assert transactions. After the assert timeout expires, verifiers send the assert timeout transaction, burning the operator's `BurnConnector` collateral (the `CollateralInRound` UTXO in the round transaction). This is an unconditional, permanent slashing of operator collateral for every challenged kickoff, regardless of whether the operator behaved honestly.

The `disprove_if_ready` condition in the kickoff state machine requires all operator asserts to be received before a disprove can be sent: [8](#0-7) 

Without valid asserts, the assert timeout path fires instead, burning collateral.

### Likelihood Explanation

Any party can challenge any kickoff by spending the challenge UTXO. Since the bug is in the proof generation library (`bridge-circuit-host`), every operator running the standard codebase is affected. The bug is deterministic — it fires on every challenged kickoff without exception.

### Recommendation

In `host_deposit_constant` (`bridge-circuit-host/src/structs.rs`), replace `deposit_value_bytes` with the move transaction ID derived from the storage proof (consistent with how the ZK circuit computes it via `verify_storage_proofs`). The 4th argument must be the Bitcoin move-to-vault transaction ID, not the deposit value.

### Proof of Concept

1. Operator fronts a withdrawal and sends a kickoff transaction.
2. A verifier challenges the kickoff by spending the challenge UTXO.
3. The operator's automation calls `prove_bridge_circuit` to generate a bridge proof.
4. Inside `prove_bridge_circuit`, the ZK circuit executes and produces a journal hash using `move_txid` in `deposit_constant`.
5. The host computes `journal_hash` via `SuccinctBridgeCircuitPublicInputs::new()` → `host_deposit_constant`, which substitutes `deposit_value_bytes` for `move_txid`.
6. The check `if *journal_hash.as_bytes() != succinct_receipt_journal` fails unconditionally.
7. `prove_bridge_circuit` returns `Err("Journal hash mismatch")`.
8. The operator cannot submit a valid proof or correct assert transactions.
9. After the assert timeout, verifiers send the assert timeout transaction, permanently burning the operator's collateral.
