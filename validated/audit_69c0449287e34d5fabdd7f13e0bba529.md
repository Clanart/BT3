Missing zero-check on governance-settable `Kip71.GasTarget` causes division-by-zero panic in base fee calculation - ([File: params/kip71_config.go])

### Summary
`params.KIP71Config.NextMagmaBlockBaseFee` uses `GasTarget` as a divisor when computing the next block's base fee, but the `kaiax/gov` parameter registry does not validate that `Kip71GasTarget` is non-zero, unlike its sibling parameter `Kip71BaseFeeDenominator`, which explicitly guards against zero. A governance vote (or contract-governance update per KIP-81) that sets `GasTarget` to `0` will cause every node to hit a `big.Int` division-by-zero panic while validating/producing the very next Magma-fork block, crashing all nodes attempting to process that block.

### Finding Description
`NextMagmaBlockBaseFee` computes the base fee delta by dividing by `gasTarget` in both the "gas used > target" and "gas used < target" branches: [1](#0-0) [2](#0-1) 

Note that `BaseFeeDenominator` is defensively guarded against zero (falling back to `64`) at line 71-76: [3](#0-2) 

But `gasTarget := kc.GasTarget` at line 77 has no equivalent guard: [4](#0-3) 

If `parentGasUsed != gasTarget` (true whenever `gasTarget == 0` and any gas was used, or even when `parentGasUsed == 0` and `gasTarget == 0` triggers the `==` branch harmlessly, but any nonzero gas usage with `gasTarget == 0` hits the `>` branch), the code executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, which panics in Go's `math/big` package (`big.Int.Div` panics on division by zero) at line 102 or 120: [5](#0-4) 

The root cause is in the governance parameter validation registry `kaiax/gov/param.go`. The `Kip71BaseFeeDenominator` parameter has a `FormatChecker` explicitly rejecting `0`: [6](#0-5) 

But `Kip71GasTarget` uses `noopFormatChecker`, which accepts any `uint64` value including `0`: [7](#0-6) [8](#0-7) 

This value flows unguarded from the parameter set into `KIP71Config.GasTarget` via `ParamSet.ToKip71Config`: [9](#0-8) 

`NextMagmaBlockBaseFee` is invoked from `VerifyMagmaHeader`, which is called during header validation in `blockchain/block_validator.go` for every node processing the block, as well as during block production (`work/worker.go`) and RPC gas price estimation paths (`node/cn/gasprice`).

### Impact Explanation
Because `NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is executed in the core consensus header-validation path on every full node (and in block production by the proposer), a governance vote setting `Kip71.GasTarget` to `0` will cause an unrecovered Go panic (`runtime error: integer divide by zero` from `math/big.Div`) as soon as a block with nonzero gas usage is produced/validated under the new parameter set. Since panics in Go crash the process unless explicitly recovered, this can crash all validating and full nodes simultaneously, causing a full network halt — a much more severe outcome than the referenced Sherlock report's "revert" (which merely blocks a single transaction/vault operation). This satisfies the "acceptance of an invalid transaction or block" / state-divergence class of impact (in this case, universal crash rather than divergence, since all honest nodes running unmodified code panic identically), and is explicitly within the allowed "governance parameters" category.

### Likelihood Explanation
Setting `GasTarget` to zero requires a governance decision (single-mode governing node vote or GC on-chain vote via `GovParam` contract per KIP-81). This is not a fully permissionless, single-transaction attack from an arbitrary EOA, but it is reachable through the normal, in-scope governance parameter update mechanism without any additional code-level restriction — no validation anywhere in the vote/parameter pipeline rejects `0` for `GasTarget`, unlike the analogous `BaseFeeDenominator` field which the developers clearly intended to protect. A malicious/compromised governing node, or an accidental misconfiguration (e.g., copy-paste error setting `GasTarget=0` instead of a large value), directly triggers the fault the next fork-active block with any gas usage.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0`, mirroring `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
},
```
Additionally, as defense-in-depth, add the same zero-guard fallback in `params.KIP71Config.NextMagmaBlockBaseFee` that already exists for `BaseFeeDenominator`:
```go
gasTarget := kc.GasTarget
if gasTarget == 0 {
    gasTarget = DefaultGasTarget // or MaxBlockGasUsedForBaseFee-based fallback
}
```

### Proof of Concept
1. Via governance vote (single governance mode or GC contract vote per KIP-81), set `kip71.gastarget` to `0`.
2. Once the vote takes effect and the parameter propagates into `ChainConfig.Governance.KIP71.GasTarget` (through `ParamSet.ToKip71Config`), any subsequent block after the Magma fork with `parentGasUsed > 0` will call:
   - `KIP71Config.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)` with `gasTarget = 0`
   - since `parentGasUsed (e.g. 21000) > gasTarget (0)`, execution reaches:
     ```go
     gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // = parentGasUsed
     x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
     y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0 → panic: division by zero
     ```
3. This panic occurs inside `VerifyMagmaHeader`, called from `blockchain/block_validator.go` during header verification on every node, as well as from `work/worker.go` during block assembly — crashing the node process network-wide.
