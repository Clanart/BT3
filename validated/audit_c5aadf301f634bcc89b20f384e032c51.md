### Title
Silent, unconfirmed rewrite of the local `origin` remote URL from an attacker-controlled GitHub API `clone_url` field - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop periodically refreshes a repository's associated GitHub metadata, it fetches the repository object from the GitHub/GHE API and, if the API's `clone_url` no longer matches the local `origin` remote, it **automatically rewrites the local remote URL** via `git remote set-url`, with no user prompt. This trusts the API response's `clone_url` field as ground truth for where the user's future `git push`/`git fetch` operations should go, mirroring the report's root cause: a privileged actor changes a reference (token / clone URL) that downstream logic silently follows, leaving the previous holder/consumer (the user's configured remote) permanently repointed with no opt-out or migration step.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` periodically re-resolves a repository's GitHub association and calls the API: [1](#0-0) 

It passes the fetched `apiRepo` into `updateRemoteUrl`, which compares the API's `clone_url` to the current `origin` remote and, if they differ (but protocols match and the remote hasn't been "manually" changed away from the previously-cached `cloneURL`), silently calls `gitStore.setRemoteURL(...)`: [2](#0-1) 

That in turn issues `git remote set-url` directly against the on-disk repository, with no confirmation dialog: [3](#0-2) [4](#0-3) 

The guard `urlMatchesRemote` only checks that hostname, owner, and name string-match between two URLs — it does not verify that the API server is the *same* trusted origin the user originally cloned from beyond a naive hostname string comparison: [5](#0-4) 

For GitHub Enterprise (self-hosted) accounts, the "API" is simply whatever server is configured at that `endpoint` — the app has no independent verification that the server's `fetchRepository` response is trustworthy beyond "it responded from that host." Because Desktop treats `clone_url` from that response as authoritative and silently updates the local git remote whenever it diverges from what Desktop last cached, a malicious or compromised GHES instance (or a MITM/DNS-hijacked endpoint the user is enrolled with) can return an arbitrary `clone_url` for the very same `owner/name` the local remote already targets, and Desktop will retarget the user's `origin` remote to that URL without any warning. This differs sharply from a very similar retargeting operation — updating the `upstream` remote for forks — which explicitly shows a confirmation dialog to the user before changing anything: [6](#0-5) 

No equivalent confirmation exists for `updateRemoteUrl`'s automatic rewrite of the primary `origin` remote.

### Impact Explanation
If the retargeted URL points to an attacker-controlled repository, the next `git push` (Desktop's normal "Push" action) silently sends the user's local commits — potentially including secrets, proprietary code, or credentials embedded in commit history — to the attacker's repository instead of the intended one. Conversely, the next `git fetch`/`pull` silently pulls attacker-controlled history/objects into the user's working repository, which is a supply-chain injection vector. This satisfies the "silent corruption of what the user commits or pushes" impact category, driven entirely by a GitHub API object (`IAPIRepository.clone_url`) that the attacker controls when they operate or compromise the queried endpoint.

### Likelihood Explanation
This code path runs automatically as part of Desktop's periodic background repository refresh — no user action beyond having the repository open is required, and there is no confirmation UI, unlike the analogous `UpstreamAlreadyExists` flow. The primary constraint is that the attacker must control (or MITM) the endpoint/API server the account is configured against — realistic for self-hosted GitHub Enterprise deployments, compromised/rogue GHES instances, or network-level interception of an enterprise endpoint, all of which fall within "attacker controls...a git remote/proxy response" or "a GitHub API object" per the valid-impact scope. It does not require local/physical access, admin rights, or pre-existing malware.

### Recommendation
Never silently auto-rewrite the primary `origin` remote based on API data. At minimum:
- Require explicit user confirmation before changing `origin`'s URL, consistent with the existing `UpstreamAlreadyExists` dialog pattern used for the `upstream` remote.
- Strengthen `urlMatchesRemote`/the update guard to pin against the account's original enrollment endpoint (not just a string-matched hostname), and refuse silent updates when the change would alter the underlying host identity or when TLS/host verification can't be established.
- Log/audit or diff-preview the proposed remote change so the user can see exactly what's changing before it's applied.

### Proof of Concept
1. User has a repository on a GitHub Enterprise Server (`https://ghes.example.com`) enrolled as an account in Desktop, with `origin` pointing at `https://ghes.example.com/org/repo.git`.
2. Attacker compromises (or operates) `ghes.example.com` and, when Desktop calls `fetchRepository(owner, name)` during its periodic refresh (`repositoryWithRefreshedGitHubRepository` → `api.fetchRepository`), returns an `IAPIRepository` payload for the same `owner/name` but with `clone_url: "https://ghes.example.com/org/repo-attacker-mirror.git"`.
3. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (matches previously cached `cloneURL`), and `urlsMatch === false`, so it calls `gitStore.setRemoteURL('origin', 'https://ghes.example.com/org/repo-attacker-mirror.git')` with no prompt — confirmed by the unit test demonstrating this exact update path: [7](#0-6) 
4. The user's next push in Desktop silently sends commits to `org/repo-attacker-mirror` instead of `org/repo`.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
