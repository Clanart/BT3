## Finding: GitHub Desktop disables Git's built-in clone-time repository protection [1](#0-0) 

### Title
Desktop force-disables Git's clone-time embedded-repository protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), enabling malicious repositories to write outside the intended clone directory - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` as part of the environment passed to every `git clone --recursive` invocation, for every URL the user (or a deep link / "Open in Desktop" action / fork add flow) asks Desktop to clone. [2](#0-1) 

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is Git's own environment switch for the embedded-repository / symlink hardening that was added to core Git in response to the class of vulnerabilities where a maliciously crafted repository (using nested/embedded `.git` directories, case-insensitive or Unicode-normalizing filesystem tricks, or submodules) can cause `git clone --recursive` to write files — including hook scripts — into a location controlled by the attacker rather than confined to the intended target directory. Git's protection is on by default precisely because attacker-controlled repository content is untrusted input during clone.

Desktop's `clone()` function builds the execution environment by merging `envForRemoteOperation(url)` with an explicit override that turns this protection off:
```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
``` [1](#0-0) 

This happens before any content of the remote repository has been inspected, and the clone is run with `--recursive`, which recursively fetches and initializes submodules defined by the (attacker-controlled) source repository: [3](#0-2) 

Note that Desktop does have a separate, narrower guard, `isClonePathSensitive()`, which only checks that the *destination directory chosen by the user* isn't `~`, `~/.ssh`, `~/.gnupg`, etc. [4](#0-3) 
That guard says nothing about what the *remote repository's contents* can do once Git's own embedded-repository protections have been switched off; the two checks are not equivalent. The `isClonePathSensitive` check validates the outer clone target, while `GIT_CLONE_PROTECTION_ACTIVE=false` removes Git's internal defense against a malicious repository writing paths outside that target directory (e.g., into `.git/hooks` of a nested/embedded repo boundary, or via case-insensitive/8.3-short-name/Unicode collisions on Windows/macOS). This is structurally the same class of bug as the reported EVM issue: a protective check that exists specifically to stop an attacker-controlled input from causing damage is bypassed/neutralized, and the remaining checks in the code (`isClonePathSensitive`) do not cover the gap.

### Impact Explanation
If a user clones, or Desktop programmatically clones (e.g. via `x-github-client://` deep links, "Open in Desktop", or adding/fetching a fork remote), a specially crafted attacker-controlled repository, the disabled protection removes Git's defense against writes escaping the intended repository directory during `--recursive` clone. Depending on the underlying filesystem and Git version behavior this protection guards against, this can result in arbitrary file writes outside the repo (e.g., hook scripts placed where they'll later be executed by Git), which is a listed valid impact ("attacker controls a cloned/fetched repository ... result is code execution, file write ... outside the repo").

### Likelihood Explanation
Cloning an attacker-supplied URL is a core, unprivileged Desktop workflow — via manual "Clone repository" with a URL, via deep links, or via the fork/PR remote-adding flow (`_findPullRequestBranch`, which calls `addRemote` with an attacker-controlled `headCloneUrl` from the GitHub API and subsequently fetches it) [5](#0-4) . Since `GIT_CLONE_PROTECTION_ACTIVE=false` is applied unconditionally to every `clone()` call regardless of whether the URL is trusted, no unusual user action beyond a normal clone/open-in-desktop click is required, satisfying the "unprompted unnatural user steps" exclusion (i.e. it is *not* excluded, since the trigger is an ordinary clone).

### Recommendation
Do not force-disable `GIT_CLONE_PROTECTION_ACTIVE`. If it was disabled to work around a compatibility issue, that decision should be scoped and justified (with tests demonstrating it's actually safe), or replaced with a narrower workaround; the default should be to leave Git's embedded-repository protection enabled during clones of untrusted, user/attacker-supplied URLs. At minimum, this override warrants a design review to confirm what compatibility problem it solves and whether an alternative fix exists that doesn't reintroduce the class of vulnerability the upstream Git protection was built for.

### Proof of Concept
1. Host a malicious Git repository that exploits Git's embedded-repository/case-insensitive-filesystem clone vulnerability class (the one `GIT_CLONE_PROTECTION_ACTIVE` was introduced to mitigate), such that a `git clone --recursive` with the protection disabled writes a file (e.g., a hook script) outside the target clone directory.
2. In GitHub Desktop, use "Clone repository" (or an `x-github-client://` deep link, or view/checkout a fork PR that adds the malicious URL as a remote) pointing at that malicious repository/URL.
3. Observe that `clone()` in `app/src/lib/git/clone.ts` invokes `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment [6](#0-5) , so Git's own embedded-repository defenses do not activate, and the file write occurs outside the intended repository path, only bounded by the unrelated `isClonePathSensitive` destination check which does not inspect the source repository's contents [4](#0-3) .

**Uncertainty note:** I could not verify from the indexed code why `GIT_CLONE_PROTECTION_ACTIVE` was set to `'false'` (no comment, changelog entry, or commit blame was retrievable in this environment) — it's possible this was done deliberately to fix a legitimate compatibility issue (e.g., with certain LFS/submodule workflows) rather than as an oversight. Confirming the original intent and the exact upstream Git behavior being disabled would require checking Desktop's commit history/PR discussion directly, which is outside what the local index exposes.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
