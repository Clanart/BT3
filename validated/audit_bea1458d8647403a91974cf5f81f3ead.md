## Analysis

The PoolTogether bug's core invariant break: **a single unprivileged, low-effort action lets an attacker manipulate a shared, queue-based accounting state that legitimate participants rely on, destroying value for others while the attacker bears little cost.** In Hyperbridge, the closest local analog is `pallet-bandwidth`'s FIFO subscription ledger combined with its cross-chain "sponsorship" model, which lets an unrelated, unprivileged party push entries into another app's bandwidth ledger and evict its paid-for allowance.

### Title
Unauthenticated cross-chain sponsorship lets any purchaser evict a victim app's prepaid bandwidth via FIFO cap eviction - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` keys prepaid byte allowances only by `(app_chain, app)`, not by payer, and explicitly allows any registered `BandwidthManager` purchase to credit *any* `(app_chain, app)` pair chosen by the buyer via the payload's `chain` field — this is the documented "Sponsorship" feature. Because the FIFO subscription list is capped at 1024 and `push_subscription` unconditionally evicts the oldest entry on every push regardless of who is pushing, an attacker with no relationship to a victim app can repeatedly purchase cheap subscriptions targeting the victim's `(app_chain, app)` key, evicting the victim's real, larger, legitimately-paid-for subscription before it can be consumed.

### Finding Description
The `Allowance` storage map is keyed purely by `(app_chain, app)`: [1](#0-0) 

The purchase flow is intentionally payer-agnostic — "a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`," and "the pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`": [2](#0-1) 

`push_subscription`, which is the single choke point used by both real purchases and admin `force_credit`, evicts the oldest entry the moment the list hits `MAX_SUBSCRIPTIONS` (1024), with no check on who is pushing or how much the evicted entry was worth relative to the new one: [3](#0-2) 

The docs acknowledge eviction is possible but assume it only happens under "pathological repeat-buy behavior" by the *same* app, i.e., "at the default of one purchase per cycle, 1024 buys is years of headroom": [4](#0-3) 

That assumption does not hold once the sponsorship model is factored in: because any purchaser can target any `(app_chain, app)`, the "1024 buys" no longer need to come from the victim app itself — a hostile third party can supply all 1024 pushes. There is no allowlist, minimum-purchase-size floor relative to existing entries, or per-payer restriction gating who may append to another app's queue.

### Impact Explanation
An attacker can grief any app's prepaid bandwidth balance by purchasing the cheapest configured tier 1024 times against the victim's `(app_chain, app)` key. Each push evicts the oldest entry in FIFO order; once the attacker's spam entries fill the list, the victim's own (possibly large, expensive) subscription is evicted with `SubscriptionEvicted`, and its `remaining_bytes` — bandwidth the victim already paid for — is permanently lost. This is a direct loss-of-funds/loss-of-paid-service impact: the victim paid real fee-token value for byte allowance that is destroyed by an unrelated third party at will, with no consent, and the destroyed bandwidth cannot be recovered short of admin `force_credit` intervention. This matches the bounty's "stealing or loss of funds" and "bridged asset/bandwidth balances must move exactly once and only to the rightful beneficiary" pivots.

### Likelihood Explanation
The attacker needs only: (1) a `BandwidthManager` already registered on some source chain (any chain governance has onboarded — not the victim's chain), and (2) enough fee-token to buy the cheapest tier 1024 times. No admin, relayer, or governance compromise is required — sponsorship purchases are a normal, permissionless, unprivileged user flow by design. The cost asymmetry can be severe: a victim who bought the most expensive tier once (e.g. the $1000/8MB plan) can have that single high-value subscription evicted by an attacker spending 1024 × cheapest-tier price, which — depending on configured tier economics — can be substantially cheaper than the value destroyed, and the attack scales to fully deny an app's bandwidth indefinitely by repeating each cycle. I was not able to fully verify from the indexed contents of `BandwidthManager.sol` whether `months = 0` purchases (which would make the attack near-zero-cost) are explicitly rejected on the EVM side; this should be confirmed directly against `evm/src/apps/BandwidthManager.sol`, which the index did not surface in full.

### Recommendation
Scope eviction protection by payer or by minimum committed value: either (a) key `Allowance` by `(app_chain, app, sponsor)` so unrelated sponsors cannot evict each other's entries, (b) require `set_allowlist`/opt-in sponsorship per `(app_chain, app)` so an app must explicitly authorize which source chains/payers may top up its bucket, or (c) change eviction policy to refuse a push that would evict an entry with more remaining value/duration than the incoming one, and instead reject or queue the purchase (refundable) once the cap is reached from non-authorized payers.

### Proof of Concept
1. Victim app `A` on `app_chain = Evm(8453)` buys `TierFour` (largest, most bytes) once — `Allowance[(Evm(8453), A)]` now holds one large subscription.
2. Attacker deploys/uses any registered `BandwidthManager` on a different, already-onboarded source chain and calls `purchase()` 1024 times with the cheapest tier, each time setting the purchase payload's `chain = Evm(8453)` and `app = A` (per the Sponsorship model, this is a legitimate, permitted call — see `docs/content/developers/evm/bandwidth/overview.mdx:108-114`).
3. Each of the attacker's purchases reaches `on_accept` → `push_subscription` (`modules/pallets/bandwidth/src/lib.rs:400-437`), which appends to the same `(Evm(8453), A)` FIFO list.
4. Once list length hits `MAX_SUBSCRIPTIONS` (1024), each subsequent attacker purchase evicts the oldest entry — eventually evicting victim `A`'s original `TierFour` subscription and emitting `SubscriptionEvicted { lost_bytes: <A's paid bytes> }`.
5. Victim `A` has lost the bandwidth it paid for, destroyed by an account it never interacted with or authorized.

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
