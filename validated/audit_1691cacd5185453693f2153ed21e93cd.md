### Title
JSON parser duplicate-key detection can be bypassed via alternate field-name spellings, allowing a later key to silently overwrite/hide an earlier value - ([File: src/google/protobuf/json/internal/parser.cc], [File: python/google/protobuf/json_format.py])

### Summary
HedgeDoc's flaw is that a uniqueness/duplicate check (note alias vs. note ID) is bypassed because the database does *case-insensitive* comparison while the application's uniqueness check operates on a different representation, letting an attacker create a colliding alternate spelling that the check doesn't recognize as a duplicate, causing the original note to be effectively hidden/overwritten. The externally-invariant-transferring analog in this Protobuf checkout is Protobuf's JSON parser: it is documented and specified to treat multiple JSON spellings (the canonical `snake_case` proto field name, the default `lowerCamelCase` name, and a custom `json_name`) as referring to the *same* field, and it is specified to reject **duplicate keys** for a field within one JSON object. However, the duplicate-key detector only rejects keys that are *lexically identical strings* — it does not canonicalize alternate spellings before checking for duplicates. This means a JSON object containing two different spellings of the same field (e.g. `"int32Value"` and `"int32_value"`) is not detected as a duplicate, and the second occurrence silently overwrites the first, exactly mirroring the "different representation bypasses uniqueness check, second write wins, first is hidden" pattern in the HedgeDoc report.

### Finding Description
Protobuf's JSON wire parser (`ParseField` in `src/google/protobuf/json/internal/parser.cc`) resolves an incoming JSON key to a field via `Traits::FieldByName`, which accepts snake_case, lowerCamelCase, and custom `json_name` spellings for the same underlying field [1](#0-0) . Once resolved, it tracks whether the field has already been "seen" via `Traits::RecordAsSeen`, and if it has, raises `'%s' has already been set` [2](#0-1) . This detection is intended to enforce the JSON spec's requirement of no duplicate field assignments and is supposed to be spelling-agnostic since `RecordAsSeen` operates on the *resolved field*, not the raw key string. This should mean that even different spellings collapse into the same detected duplicate.

However, the equivalent higher-level Python/PHP-style JSON parsing (`python/google/protobuf/json_format.py`) implements its own duplicate-key check at the JSON-object level, which explicitly only rejects *exact-string* duplicate keys and is documented as *not* catching alternate spellings that map to the same field. This is confirmed by the project's own test suite: `testDuplicateFieldAlternateNames` explicitly states, "this behavior is non-spec and an oversight bug in the implementation... the duplicate field checker intends to reject inputs with duplicate key names, but it only catches keys that are exact matches and not alternate spellings that correspond to the same field" [3](#0-2) . In that test, `{"int32Value": 1,"int32_value":2}` parses successfully (no error) and the second value (`2`) silently overwrites the first, with no diagnostic indicating that data was hidden/lost [4](#0-3) . Compare this to the case where identical spellings are duplicated: `testDuplicateField` correctly raises `Failed to load JSON: duplicate key int32Value.` [5](#0-4) .

This is the direct structural analog of the HedgeDoc bug:
- **Failed invariant**: "one JSON key maps to one canonical field slot; a second occurrence of that slot must be rejected/last-wins consistently and detectably" — analogous to "one note ID/alias must be unique."
- **Attacker-controlled value**: the raw JSON key string spelling (snake_case vs. camelCase), analogous to HedgeDoc's attacker-controlled alias string that collides case-insensitively with an existing note ID.
- **Missing check**: the duplicate-key detector compares raw strings instead of canonicalized/resolved field identity, just as HedgeDoc's uniqueness check didn't account for the DB's case-insensitive collation.
- **Impact**: a value written under one spelling is silently, undetectably replaced/hidden by a value written under a different spelling of the same field — the original value is inaccessible from the perspective of that one JSON payload's processing.

Protobuf's binary wire format handles this correctly and deliberately (map entries and singular fields deterministically use "last one wins" as a documented merge semantic — see `DuplicateEntriesInWireFormatLastOneWins` [6](#0-5)  and `MapInt32Int32` C# test [7](#0-6) ), so those are *not* analogous — they are intended behavior with no "duplicate detection" requirement violated. The JSON-name-alias case is different because the code *explicitly promises* to detect and reject duplicates but silently fails to do so for a well-known class of alternate inputs (this is even called out by protobuf's own maintainers as a bug, but one they consider unfixable without breaking compatibility).

### Impact Explanation
Impact is data-integrity/confidentiality-adjacent within the scope of a single JSON payload: an attacker (or an application relying on protobuf's JSON parser to reject duplicate/conflicting fields as a safety net, e.g. for detecting malformed or adversarial input) cannot rely on the "duplicate key rejected" guarantee. A downstream application that assumes JSON-to-proto parsing will fail (or that assumes the first/only occurrence is authoritative) if two keys represent the same field can be tricked into accepting a payload where a security-relevant field (e.g. an authorization flag, an amount, a permission enum) is set once under `snake_case` for a validation/logging pass and once under `camelCase` to sneak past a different code path, with only the second value taking effect. This is a narrower, protocol-level integrity issue rather than a memory-safety or RCE issue, consistent with the original CVE's Medium severity (integrity impact "High", confidentiality "None", availability "Low").

### Likelihood Explanation
High likelihood of triggering in code review or fuzz testing (the behavior is deterministic and already caught by protobuf's own conformance/test suite, marked as a known "oversight" — see `FieldNameDuplicateDifferentCasing1`/`FieldNameDuplicateDifferentCasing2` conformance tests and their entries in the Python/upb failure lists, which explicitly document non-conforming duplicate detection across alternate spellings [8](#0-7) [9](#0-8) ). Any attacker who can submit arbitrary JSON to a public parse API (ProtoJSON `Parse`) can trivially construct this payload without any special privileges, matching the "ordinary client sending bounded ProtoJSON through a supported public parse API" threat model.

### Recommendation
Canonicalize the JSON key to its resolved field identity before performing duplicate detection, consistent with how the C++ `ParseField` path already tracks "seen" state on the resolved field object rather than the raw string [2](#0-1) , and apply the same field-identity-based duplicate check uniformly across all language bindings (Python, upb, etc.) instead of doing a raw-string-key duplicate check at the JSON-object level. Where an incompatible fix would break existing behavior, document this explicitly as a known limitation (as already begun in `edition-zero-json-handling.md` [10](#0-9) ), and warn consuming applications not to rely on JSON parsing to reject conflicting/duplicate field assignments across alternate spellings.

### Proof of Concept
Using the Python binding (`json_format.Parse`), reproduced by the existing (currently passing, i.e., non-failing) test `testDuplicateFieldAlternateNames`:
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2

msg = json_format_proto3_pb2.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', msg)
assert msg.int32_value == 2  # succeeds; no "duplicate key" error is raised,
                              # and the first value (1) is silently hidden/overwritten
```
This exact assertion is already codified in the repository's own test file [3](#0-2) , confirming the parser accepts this input without error while a strictly-identical duplicate key (`testDuplicateField`) correctly raises an error [5](#0-4) .
