## Title
Governance vote can set `reward.proposerupdateinterval` or `reward.stakingupdateinterval` to zero, causing division-by-zero panic in proposer/staking calculations - (File: kaiax/gov/param.go, kaiax/valset/impl/getter_proposers.go)

### Summary
The Kaia governance parameter framework validates most numeric parameters with a `FormatChecker`, but `RewardProposerUpdateInterval` and `RewardStakingUpdateInterval` — both of which are used as divisors in block-processing arithmetic — are registered with `noopFormatChecker`, which performs no validation at all. This mirrors the reported Tokemak bug class: a privileged-but-not-omnipotent actor (the governing/voting council, reachable through the standard on-chain governance vote mechanism) can set a duration-like parameter to zero, and downstream code that divides/rounds by that value will panic.

### Finding Description
In `kaiax/gov/param.go`, the parameter definitions for `RewardProposerUpdateInterval` and `RewardStakingUpdateInterval` explicitly use `noopFormatChecker`, unlike other numeric params such as `RewardMinimumStake` or `RewardStakingRewardThreshold` which enforce `v.Sign() >= 0` (still doesn't block zero, but shows the sibling parameters `RewardRatio`/`RewardKip82Ratio` do enforce structural sum checks; more importantly there is precedent elsewhere in the code that these two intervals must be nonzero): [1](#0-0) [2](#0-1) 

Confirmation that these intervals are treated as required-nonzero denominators exists in `params/config.go`'s genesis-defaulting logic, which explicitly guards against zero because "it is used as denominator": [3](#0-2) 

However, that genesis-time guard only applies when loading a genesis config (`SetDefaultsForGenesis`) — it is not re-applied when the parameter is changed later via an on-chain governance vote. Governance votes are validated through the `Params` map's `FormatChecker` in `kaiax/gov/param.go`, and since that checker is a no-op for these two parameters, a vote setting either interval to `0` will be accepted.

The value is then consumed directly as a divisor when computing the proposer update boundary for every block: [4](#0-3) 

`roundDown(c.num-1, uint64(c.pset.ProposerUpdateInterval))` rounds the block number down to the nearest multiple of the interval, which (based on the naming/semantics and the explicit "used as denominator" comment in `params/config.go`) performs a modulo/division operation. If the interval is zero, this will panic with a division-by-zero runtime error. The same interval is also used in `getRemoveVotesInInterval`/`scanBlocks` as a loop bound, but the primary risk is the `roundDown` call, which is invoked on every block's proposer-list computation.

Note: I could not view the body of `roundDown` (defined in `kaiax/staking/impl/getter.go` and `kaiax/valset/impl/getter_council.go`) within available tool calls, so the exact division/modulo operation inside `roundDown` is inferred from its name and usage context rather than directly confirmed from source.

### Impact Explanation
If `roundDown` performs an integer division/modulo by the interval (consistent with rounding-down semantics and the "used as denominator" comment guarding the genesis path), then a governance vote setting `reward.proposerupdateinterval` (or `reward.stakingupdateinterval`) to `0` would cause every node to panic while computing the proposer list or staking-interval boundary for the next block. Because this logic runs identically on every full node during block processing/consensus, this is not merely a single-node crash — it would cause a chain-wide halt (all honest nodes panicking at the same block height), which is a critical liveness/state-divergence risk far more severe than the original Tokemak Medium finding (a single skipped reward accrual due to `notifyRewardAmount` reverting).

### Likelihood Explanation
The likelihood depends on the specific governance process required to change this parameter (e.g., council supermajority, governing node authorization) — governance votes are gated by `VerifyVote`/`GoverningNode` checks in the `headergov` module, so this is not exploitable by an arbitrary unprivileged transaction sender, only by a party with governance voting rights. Given the "governance parameters" category is explicitly listed as in-scope for this analog scan, and given the complete absence of validation (unlike sibling parameters that do have `FormatChecker` bounds), this represents a real gap: nothing in the vote-acceptance path prevents an operator error or malicious-but-authorized voter from bricking the chain.

### Recommendation
Add a `FormatChecker` for `RewardProposerUpdateInterval` and `RewardStakingUpdateInterval` in `kaiax/gov/param.go` that rejects `0` (e.g., `func(cv any) bool { v, ok := cv.(uint64); return ok && v > 0 }`), consistent with the existing genesis-time invariant enforced in `params/config.go`. Additionally, add a defensive nonzero check in `roundDown` and in `getProposerList`/`getRemoveVotesInInterval` to prevent chain-wide panics even if an interval of zero were to slip through by other means (e.g., legacy on-chain governance encoding paths).

### Proof of Concept
1. A governance vote (via `headergov`) is cast and accepted for `reward.proposerupdateinterval = 0` (or `reward.stakingupdateinterval = 0`); acceptance succeeds because `RewardProposerUpdateInterval`'s `FormatChecker` is `noopFormatChecker` [1](#0-0) , unlike parameters that do enforce constraints (e.g. `RewardRatio` sum check) [5](#0-4) .
2. Once the new `ParamSet` becomes active at the target block, `getProposerList` is invoked for every subsequent block: `updateNum = roundDown(c.num-1, uint64(c.pset.ProposerUpdateInterval))` [4](#0-3) .
3. With `ProposerUpdateInterval == 0`, `roundDown` performs a division/modulo by zero (consistent with the "used as denominator" invariant documented in `params/config.go` [6](#0-5) ), panicking on every node processing that block, halting the chain.
