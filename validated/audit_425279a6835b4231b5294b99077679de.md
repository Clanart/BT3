### Title
Fee-ratio rounding truncates feePayer's share to zero on small transactions, shifting the entire fee burden to unintended party - (File: blockchain/types/tx_internal_data.go)

### Summary
The external report concerns integer division in Solidity token contracts (`DSTContract.sol`, `HackerGold.sol`) where small transaction values divided by a price constant truncate to zero, silently dropping value that should have been credited to the sender. The equivalent bug class in this codebase — integer division that truncates to zero for small inputs, resulting in an unintended reallocation of value — is present in `CalcFeeWithRatio`, which splits a fee-delegated transaction's fee between the sender and the fee payer according to a percentage ratio using unguarded integer division.

### Finding Description
`CalcFeeWithRatio` computes the fee payer's share as `fee * feeRatio / 100` using `big.Int` division, which truncates toward zero, and assigns the remainder entirely to the sender: [1](#0-0) 

For fee-delegated-with-ratio transaction types (e.g. `TxTypeFeeDelegatedValueTransferWithRatio` and its variants), the sender specifies `feeRatio` (percentage of the fee the fee payer bears) and the actual transaction fee is `gasPrice * gasUsed`. When the computed `fee` is small relative to 100 (e.g. very low gas price, or a transaction with minimal `gasUsed` for a token with negligible pricing), `fee * feeRatio / 100` truncates to 0 whenever `fee * feeRatio < 100`. In that case `feePayer` gets `0` and the entire fee is charged to `feeSender` instead of being split as the transaction's signed `feeRatio` field specifies. This is the same rounding-to-zero defect described in the external report: a value is silently zeroed out by integer division for sufficiently small inputs rather than being distributed proportionally or rounded up.

This same `CalcFeeWithRatio` function is used consistently in both fee accounting simulation and post-execution fee reconciliation, so the truncation defect propagates through the entire fee-delegation accounting path for -WithRatio transaction types: [2](#0-1) [3](#0-2) 

### Impact Explanation
Fee-delegation-with-ratio is a mechanism where a fee payer (e.g., a dApp or service) agrees ahead of time to shoulder a fixed percentage of a user's transaction fee, and the sender bears the rest. When the total fee is small enough that the payer's share rounds down to zero, the sender ends up paying 100% of the fee despite having a transaction that specifies a lower `feeRatio`, silently breaking the agreed cost-sharing contract between sender and fee payer for that transaction. Since fee payers (e.g., paymaster-like services) are unprivileged, externally-facing counterparties reachable via any submitted fee-delegated-with-ratio transaction, this constitutes unintended fee-obligation shifting reachable by any transaction sender who crafts a low-fee transaction, rather than a benign rounding artifact.

### Likelihood Explanation
Any account holding a signed fee-delegated-with-ratio transaction template (or any sender colluding with, or independent of, a fee payer under a ratio agreement) can trivially trigger this by submitting a transaction with a low `gasPrice` or minimal `gasUsed`, producing a `fee` value small enough that `fee * feeRatio < 100`. No special privileges, governance changes, or validator collusion are required — this is reachable purely from transaction construction and submission, matching the report's requirement of reachability by a single submitted transaction.

### Recommendation
Round the fee-payer's share using a round-half-up or ceiling division (mirroring the type of fix applied to `HackerGold.sol`), or explicitly enforce a minimum-fee threshold below which fee-ratio splitting is disallowed, ensuring `feePayer`'s share never silently truncates to zero when `feeRatio > 0`. Alternatively, compute both shares independently with rounding and adjust so the two shares always sum exactly to `fee`, with the rounding remainder allocated deterministically (e.g., always to whichever party's computed integer share is smaller) rather than unconditionally to the sender.

### Proof of Concept
1. Construct a `TxTypeFeeDelegatedValueTransferWithRatio` transaction with `gasPrice = 1` (in kei) and minimal `gasUsed` (e.g. the base 21000 intrinsic gas), and set `feeRatio = 1` (fee payer intended to pay 1%).
2. `fee = gasPrice * gasUsed = 21000`.
3. `feePayer = (21000 * 1) / 100 = 210` — with a low enough `gasPrice`/`gasUsed` combination (e.g. `gasPrice=1`, `gasUsed` such that `fee*feeRatio < 100`, e.g. `fee=50, feeRatio=1` → `feePayer = 50/100 = 0`), the fee payer's computed share becomes `0`: [4](#0-3) 
4. `feeSender = fee - feePayer = fee`, meaning the sender is charged the entire fee despite the transaction declaring `feeRatio = 1` (intended: fee payer covers a share of the cost). The fee payer contributes nothing for that transaction, silently breaking the declared cost-sharing ratio.

// CalcFeeWithRatio returns feePayer's fee and sender's fee based on feeRatio.
// For example, if fee = 100 and feeRatio = 30, feePayer = 30 and feeSender = 70.
func CalcFeeWithRatio(feeRatio FeeRatio, fee *big.Int) (*big.Int, *big.Int) {
	// feePayer = fee * ratio / 100
	feePayer := new(big.Int).Div(new(big.Int).Mul(fee, new(big.Int).SetUint64(uint64(feeRatio))), common.Big100)
	// feeSender = fee - feePayer
	feeSender := new(big.Int).Sub(fee, feePayer)

	return feePayer, feeSender
}
