### Title
Identity-point acceptance in `SchnorrSignature`/PedPoP encryption lets any unauthenticated observer forge a sender-bound `EncryptedMessage` and frame an honest DKG participant - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The external report's class is "an attacker who can get untrusted input processed by a victim causes unintended execution." The Serai analog is an unauthenticated party feeding a fully forged `EncryptedMessage` into `KeyMachine::calculate_share` / `BlameMachine::blame`: because `Ciphersuite::read_G` accepts the identity point and `SchnorrSignature::verify` has no identity rejection, the proof-of-possession `pop` is trivially forgeable for `key = identity` with `R = identity, s = 0`. The ECDH shared secret then degenerates to the identity point, yielding a publicly known ChaCha20 keystream, so the attacker controls the decrypted plaintext while the message is still attributed to an honest sender.

### Finding Description
`EncryptedMessage::read` reads `key` via `C::read_G` and the `pop` via `SchnorrSignature::read`, both of which resolve to `Ciphersuite::read_G`, which only enforces canonical encoding and does **not** reject the identity point [1](#0-0) [2](#0-1) . `Curve::read_G` in the FROST crate explicitly rejects identity, showing the authors knew this check was needed, but PedPoP uses `Ciphersuite`, not `Curve` [3](#0-2) .

Verification is `R + c·A − s·G == 0` via `batch_statements`/`multiexp_vartime`, with no check that `R` or the public key is non-identity [4](#0-3) . Setting `A = key = identity`, `R = identity`, `s = 0` satisfies the equation for any challenge, including the sender-bound `pop_challenge` which commits to `sender`, `key`, `nonce`, and `msg` — the forgery is still attributed to whatever `from` the attacker chooses [5](#0-4) [6](#0-5) .

Because `ecdh(enc_priv, identity) = identity`, `cipher()` derives a keystream from the publicly known identity encoding plus context — so the attacker fully controls the decrypted `SecretShare` bytes [7](#0-6) . The forged share then fails `share_verification_statements` (the attacker cannot match the honest sender's committed polynomial), causing `calculate_share` to return `PedPoPError::InvalidShare { participant: sender }` pointing at an innocent party [8](#0-7) . Worse, `blame_internal` will attribute fault to `sender` — the honest participant — since the forged message cannot produce a valid share for the sender's commitments [9](#0-8) . The same identity trick forges the round-1 `sig` PoK when `commitments[0] = identity` in `verify_r1` [10](#0-9) .

### Impact Explanation
Any party that observes the DKG transcript (not even a participant — the PoP challenge only binds `sender` bytes, not any authentication) can inject an `EncryptedMessage` that passes the PoP check, gets decrypted under a publicly derivable key, and deterministically causes an honest participant to be judged faulty by `BlameMachine::blame`. In a validator set where DKG blame drives removal/slashing decisions, this enables framing honest validators and forcing DKG aborts at will — an incorrect blame verdict produced purely from attacker-supplied bytes.

### Likelihood Explanation
Reachable by any unprivileged party able to deliver bytes to `EncryptedMessage::read` / `calculate_share` (the exact untrusted-input path the rules require). Forgery requires no secret knowledge and no interaction — it is a constant-cost, deterministic construction (`key` = identity encoding, `pop` = identity `R` plus `s` = 0), exploitable in every PedPoP DKG session.

### Recommendation
Reject the identity point in the read paths used by PedPoP: `EncryptedMessage::read` (`key`, `pop.R`), `EncryptionKeyMessage::read` (`enc_key`), `Commitments::read`, `EncryptionKeyProof::read`, and `SchnorrSignature::read` generally — e.g., by adding a `read_G` wrapper that checks `is_identity()` as `Curve::read_G` already does in `crypto/frost/src/curve/mod.rs:125`. Defense-in-depth: additionally reject identity public keys/`R` inside `SchnorrSignature::verify`/`batch_statements`, and reject ECDH results that are the identity before deriving the cipher.

### Proof of Concept
1. Observe a PedPoP round-2 session; choose any honest `sender` and target `recipient`.
2. Build `EncryptedMessage { key: identity, pop: SchnorrSignature { R: identity, s: 0 }, msg: arbitrary 32 bytes }` and serialize via `write`.
3. Deliver it to `recipient`'s `KeyMachine::calculate_share` keyed under `sender`. `msg.pop.batch_verify` passes because `identity + c·identity − 0·G = identity` for the `pop_challenge(context, identity, identity, sender, msg)`.
4. Decryption uses `ecdh(recipient_enc_priv, identity) = identity` → known keystream → `msg` decrypts to attacker-chosen `SecretShare` bytes; if non-canonical, `InvalidShare { participant: sender, blame: Some(..) }`; if canonical, the share-verification multiexp fails → same blame.
5. In `blame`, `decrypt_with_proof` verifies the forged PoP and the recipient-provided DLEq (whose `key` is `enc_priv·identity = identity`, trivially provable), the decrypted share fails `share_verification_statements`, and `blame_internal` returns `sender` — the honest participant is declared faulty.

Uncertainty note: whether downstream Serai consensus treats a blame verdict as slashable determines realized severity; the framing primitive itself is unconditional within `crypto/dkg/pedpop`.

// Each ecdh must be distinct. Reuse of an ecdh for multiple ciphers will cause the messages to be
// leaked.
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
