Based on my research, the closest verifiable Desktop analog to the "accounted value never removed, enabling double-spend" pattern is a **security control that is explicitly overridden** rather than a missing decrement — Desktop re-enables Git's `protocol.file.allow` restriction (which was hardened upstream specifically to stop a malicious repository from using submodules to read/exfiltrate arbitrary local files) whenever an `allowFileProtocol` flag is threaded through checkout/submodule code.

### Title
Desktop re-enables Git's disabled `protocol.file.allow` guard during submodule updates, allowing a malicious repository's `.gitmodules` to reference arbitrary local `file://` paths - (File: app/src/lib/git/submodule.ts)

### Summary
Upstream Git disabled automatic following of `file://` submodule URLs by default (`protocol.file.allow=user`) specifically because a malicious repository can craft a `.gitmodules` entry pointing at an arbitrary local path, and if any git operation blindly runs `submodule update --init --recursive`, that local path/repository gets pulled into the attacker's repository tree. Desktop's `updateSubmodulesAfterOperation` explicitly overrides this protection with `-c protocol.file.allow=always` whenever the caller passes `allowFileProtocol: true` to `checkoutBranch`/`checkoutCommit`.

which conditionally prepends `-c protocol.file.allow=always` before `submodule update --init --recursive`. This flag is threaded through both branch and commit checkout paths as a plain boolean parameter defaulting to `false`: [2](#0-1) [3](#0-2) 

The broken invariant is analogous to the report's core issue: a defensive value/guard (`protocol.file.allow=user`, the safe default that prevents automatic following of `file://` submodule URLs) is silently neutralized (`=always`) for an operation whose input — the `.gitmodules` file and submodule URLs — is fully attacker-controlled content coming from a cloned/fetched repository, exactly like the pool's `collected_token*_protocol_fee` counters were tracked but never actually removed from `reserve0`/`reserve1`, letting attacker-influenced state bypass the accounting guard.

### Impact Explanation
If `allowFileProtocol` is passed as `true` on a checkout triggered by content the app doesn't fully control (e.g., checking out a branch/commit whose tree, or whose submodule's `.gitmodules`, was fetched from an untrusted/malicious remote), `git submodule update --init --recursive` would honor `file://` (or bare local path) submodule URLs pointing anywhere on the local filesystem the OS user can read, including outside the current repository. This can cause a local, unrelated Git repository (or any directory git can treat as one) to be materialized inside the malicious repo's working tree, where the user could then unknowingly `git add`/commit/push it — satisfying the "silent corruption of what the user commits/pushes" and potential credential/data exfiltration criteria, since arbitrary local repo contents (which may include secrets, `.env` files tracked in another local repo, etc.) could be smuggled into a push to an attacker-controlled remote.

### Likelihood Explanation
I was not able to fully confirm, within the available search budget, the exact production call sites in `app-store.ts`/`dispatcher.ts` that decide when `allowFileProtocol: true` is actually passed to `checkoutBranch`/`checkoutCommit` versus left at the safe default `false`. The test fixtures I found (`setupRepositoryWithUninitializedSubmodule`, `pull-test.ts`) only demonstrate the mechanism in a controlled/local-fixture context, not a proven unprivileged attacker path through the production UI. This is a meaningful gap: the strength of the report hinges entirely on whether real user-facing flows pass `true` unconditionally (high likelihood) or only after some form of user trust/consent (e.g., similar to the "unsafe repository" trust prompts I saw in `add-existing-repository.tsx` and `missing-repository.tsx`) (low likelihood). I could not verify which is the case.

### Recommendation
- Audit every caller of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is only ever `true` when the repository/submodule origin has been explicitly trusted by the user for local/file-protocol submodules, never as a blanket default for arbitrary fetched/cloned content.
- Prefer Git's safer default (`protocol.file.allow=user` or unset) and only opt into `=always` per-submodule after validating the submodule URL is expected/allow-listed, rather than as a boolean threaded transparently through the whole checkout pipeline.
- Add an explicit test asserting that checking out a branch from an untrusted/attacker-crafted `.gitmodules` with a `file://` URL pointing outside the repository does **not** get initialized without additional confirmation.

### Proof of Concept
This needs to be validated in a real Desktop session (not confirmable from static code alone) by: cloning/adding a malicious repository containing a `.gitmodules` entry such as `url = file:///Users/victim/some-other-local-repo`, then performing a checkout/branch-switch operation in the app while observing whether `git submodule update --init --recursive` is invoked with `-c protocol.file.allow=always` and successfully materializes the victim's unrelated local repository inside the malicious repo's working tree. export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
