### Title
Serialized `ReceivedOutput` fields can be rebound to report an unspendable UTXO - (networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts the spend offset, full `TxOut`, and `OutPoint` as independently attacker-controlled fields, without proving that the supplied outpoint actually contains the supplied output. [1](#0-0)  A valid `Scanner` establishes this relationship from confirmed transaction data, but deserialization allows an attacker to forge that provenance. [2](#0-1) 

### Finding Description
`ReceivedOutput` has three security-relevant fields: `offset`, `output`, and `outpoint`. [3](#0-2)  Its deserializer reads all three directly from the input stream and returns the object without checking that `outpoint` resolves to `output` or that the output is confirmed on Bitcoin. [1](#0-0) 

`SignableTransaction::new` then trusts the supplied `output.value` as the input amount and the supplied `outpoint` as the transaction input. [4](#0-3)  The signing setup only verifies that `offset` produces the claimed `script_pubkey`; it cannot detect that the referenced UTXO is nonexistent or contains a different amount or script. [5](#0-4)  The transaction machine commits those attacker-selected prevouts and outpoints into the Taproot sighash. [6](#0-5) 

This is the Serai analogue of autobinding: attacker-controlled serialized parameters populate separate object fields whose required relationship was originally established by a trusted scanner, but is not re-established during deserialization. [7](#0-6) 

### Impact Explanation
An attacker can provide bytes that cause an application to treat a nonexistent or mismatched UTXO as received funds controlled by the wallet. [7](#0-6)  If the application accepts such objects as payment evidence, it can report funds that are not spendable as claimed. [8](#0-7) 

The resulting transaction can be constructed and submitted to the threshold-signing flow, but its signatures commit to false prevout data or the input references an outpoint that does not contain the claimed output, so the spend will not validate. [6](#0-5)  This enables false deposit crediting and wasted signing activity rather than recovery of the threshold private key. [9](#0-8) 

### Likelihood Explanation
The issue is reachable whenever `ReceivedOutput::read` is used on synchronization data, peer-provided data, backups, or other bytes not already known to have come from a trusted local `Scanner`. [1](#0-0)  The attacker only needs a wallet Taproot script to populate `output.script_pubkey`; the corresponding offset, claimed value, and arbitrary outpoint can then be chosen independently. [10](#0-9)  For `Scalar::ZERO`, the wallet’s normal script is sufficient, and `SignableTransaction::multisig` will accept the script relationship even though the outpoint provenance is false. [5](#0-4) 

### Recommendation
Do not treat `ReceivedOutput::read` as producing an authenticated receive report for untrusted input. [1](#0-0)  Deserialize only trusted scanner records, or make the serialized form carry enough authenticated context to bind `offset`, `TxOut`, and `OutPoint` together. [11](#0-10)  Before accepting or spending a deserialized output, verify the outpoint on confirmed chain data and compare the returned `TxOut` byte-for-byte against the serialized object. [4](#0-3) 

### Proof of Concept
```rust
use bitcoin::{
  consensus::encode::serialize,
  Amount, OutPoint, TxOut, Txid,
  hashes::Hash,
};
use k256::Scalar;
use serai_bitcoin::wallet::ReceivedOutput;

// wallet_script is the wallet's normal P2TR script, learned from a public address.
// Scalar::ZERO selects that normal key when the output was generated without a
// registered offset.
let forged = [
  Scalar::ZERO.to_bytes().to_vec(),
  serialize(&TxOut {
    // Report an amount which is not actually locked to the referenced outpoint.
    value: Amount::from_sat(1_000_000),
    script_pubkey: wallet_script,
  }),
  serialize(&OutPoint {
    // Any nonexistent or unrelated outpoint can be assigned independently.
    txid: Txid::all_zeros(),
    vout: 0,
  }),
]
.concat();

let output = ReceivedOutput::read(&mut forged.as_slice()).unwrap();

// The object now claims that wallet-controlled funds exist at the arbitrary
// outpoint. No check established that the outpoint contains this TxOut.
assert_eq!(output.value(), 1_000_000);
```

Passing this object into `SignableTransaction::new` causes its claimed value to be counted and its arbitrary outpoint to be used as an input. [4](#0-3)  `SignableTransaction::multisig` accepts the zero-offset script relationship and creates a signing machine for the forged input. [5](#0-4)
