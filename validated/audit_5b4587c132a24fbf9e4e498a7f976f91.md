### Title
Discard Changes resolves attacker-controlled `file.path`/`oldPath` outside `resolveWithin`, allowing symlink escape to trash/delete files outside the repository - ([File: app/src/lib/stores/git-store.ts])

### Summary
`GitStore.discardChanges` moves or deletes files reported by `git status` using `Path.resolve(this.repository.path, file.path)` / `Path.join(this.repository.path, file.path)` directly, without ever passing them through the codebase's own path-traversal guard, `resolveWithin`. Other parts of the same codebase (`openRepositoryFromUrl`, `buildConflictContext` in `copilot-conflict-context.ts`) explicitly use `resolveWithin`/`isAbsolute` checks specifically to stop exactly this class of bug (an unchecked destination/target derived from untrusted input), showing the maintainers are aware of the risk class but did not apply the same guard to the Discard Changes path.

### Finding Description
`discardChanges` in [1](#0-0)  iterates over `WorkingDirectoryFileChange` entries (`file.path`, `file.status.oldPath`) that originate from parsing `git status` output, and for each file not marked `Deleted`: [2](#0-1) 

- `this.shell.moveItemToTrash(Path.resolve(this.repository.path, file.path))`
- `rm(Path.join(this.repository.path, file.path))`

Neither call is preceded by any traversal/symlink validation. `Path.resolve`/`Path.join` will happily follow the joined path wherever it lands, including through a symlink. Git treats a tracked symlink as a single blob, but when scanning the working directory for **untracked** files, `git status` walks into symlinked directories present in the working tree and reports files under them using the tracked symlink name as a path prefix (e.g. `shared/id_rsa`). A malicious repository can therefore commit a symlink (e.g. `shared -> ../../.ssh` or an absolute path) that, once cloned, causes any pre-existing files at that target location to appear in Desktop's Changes list as new/untracked files under `shared/...`.

The codebase demonstrates it already understands this exact hazard and has a dedicated helper for it: [3](#0-2) 
and it is exercised specifically against symlink escape in tests: [4](#0-3) 

It is also used correctly elsewhere for very similar "open/act on a path derived from action metadata" flows: [5](#0-4) [6](#0-5) 

`discardChanges`, however, bypasses this guard entirely, so a `file.path` that resolves (via a symlink component) outside `repository.path` is not rejected before a destructive file operation is performed on it.

### Impact Explanation
If a user clones/opens a malicious repository containing a symlink into a sensitive location, and then uses the ordinary "Discard Changes" action on the resulting untracked entry (a very natural action to "clean up" what looks like repo noise), Desktop will call `shell.moveItemToTrash` or `rm` on a path resolved through the symlink — i.e., on a file physically outside the cloned repository (e.g. the user's `~/.ssh` directory or another sensitive folder), without ever validating that the resolved path is inside the repo. This is a file write/delete outside the intended repository boundary, directly caused by content controlled by the party who authored/pushed the cloned repository, matching the "attacker controls a cloned/fetched repository ... result is file write or read outside the repo" impact class.

### Likelihood Explanation
Requires: (1) the user clones or opens a repository containing an attacker-supplied symlink, and (2) the user acts on the resulting entry in the Changes list via "Discard Changes" (a routine, one-click action for anything that looks like clutter, no unusual steps). No admin rights, no pre-existing malware, and no social engineering beyond the ordinary "clone this repo" step are required. The main untested variable is exactly how `git status` on the target platform enumerates untracked contents beneath a working-tree symlink (behavior can vary with `core.symlinks` and OS); this should be validated empirically in a live environment, which was not possible from static code review alone.

### Recommendation
Route `file.path` and `file.status.oldPath` in `GitStore.discardChanges` (and any other file-system destructive operation keyed off status-derived paths) through `resolveWithin(this.repository.path, file.path)` before calling `shell.moveItemToTrash` or `rm`, refusing to act (and surfacing an error) when the resolved path is `null` (outside the repository root), consistent with the pattern already used in `dispatcher.ts` and `copilot-conflict-context.ts`.

### Proof of Concept
1. Attacker creates a repo containing a symlink `shared` pointing to a relative path that, once cloned into a directory under the victim's home folder, resolves outside the clone root (e.g. `../../.ssh` relative to a plausible clone location, or simply a symlink to an absolute sensitive path if the OS/git config permits it).
2. Victim clones the repository with GitHub Desktop.
3. Because `~/.ssh` (or another target) already contains files, `git status` reports them as untracked entries prefixed by `shared/`, and they appear in Desktop's Changes list.
4. Victim selects "Discard Changes" on these entries (a normal cleanup action).
5. `GitStore.discardChanges` executes `shell.moveItemToTrash(Path.resolve(repoPath, "shared/id_rsa"))`, which — because `Path.resolve` follows the `shared` symlink semantics of the OS path — actually targets `~/.ssh/id_rsa`, trashing/removing a file outside the cloned repository without any confirmation that this was the user's intent or that the path was inside the repo.

(Exact reproduction depends on OS-level `git status` symlink-walk behavior and was not verified against a live checkout in this review; recommend confirming with a sandboxed clone before treating as fully proven.)

  public async discardChanges(
    files: ReadonlyArray<WorkingDirectoryFileChange>,
    moveToTrash: boolean = true,
    askForConfirmationOnDiscardChangesPermanently: boolean = false
  ): Promise<void> {
    const pathsToCheckout = new Array<string>()
    const pathsToReset = new Array<string>()

    const submodules = await listSubmodules(this.repository)

    for (const file of files) {
      const foundSubmodule = submodules.some(s => s.path === file.path)

      if (file.status.kind !== AppFileStatusKind.Deleted && !foundSubmodule) {
        if (moveToTrash) {
          try {
            await this.shell.moveItemToTrash(
              Path.resolve(this.repository.path, file.path)
            )
          } catch (e) {
            if (askForConfirmationOnDiscardChangesPermanently) {
              throw new DiscardChangesError(e, this.repository, files)
            }

            // The user has received the confirmation dialog in past and has
            // chosen to always discard the changes permanently if trash failes.
            // We need to remove the file manually.
            if (file.status.kind === AppFileStatusKind.Untracked) {
              await rm(Path.join(this.repository.path, file.path))
            }
          }
        } else if (moveToTrash === false) {
          // The user has received the confirmation dialog and has chosen to
          // discard the changes permanently. We need to remove the file
          // manually.
          if (file.status.kind === AppFileStatusKind.Untracked) {
            await rm(Path.join(this.repository.path, file.path))
          }
        }
      }

      if (
        file.status.kind === AppFileStatusKind.Copied ||
        file.status.kind === AppFileStatusKind.Renamed
      ) {
        // file.path is the "destination" or "new" file in a copy or rename.
        // we've already deleted it so all we need to do is make sure the
        // index forgets about it.
        pathsToReset.push(file.path)

        // checkout the old path too
        pathsToCheckout.push(file.status.oldPath)
        pathsToReset.push(file.status.oldPath)
      } else {
        pathsToCheckout.push(file.path)
        pathsToReset.push(file.path)
      }
    }

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
