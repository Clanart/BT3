### Title
ReceivedOutput deserialization accepts unattested offset/output/outpoint tuples, allowing fabricated inputs to be treated as spendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts three completely unbound fields — a scalar `offset`, a `TxOut`, and an `OutPoint` — with no verification that the claimed outpoint exists on-chain, that the declared `TxOut` matches the actual output at that outpoint, or that `offset` actually derives the script pubkey in `TxOut` from the scanner's key. This is the Serai analog of the Cooler `claimDefaulted` bug: just as `claimDefaulted` accepted any loan produced by a trusted factory without checking the clearinghouse originated it, `ReceivedOutput`/`SignableTransaction` accept any tuple whose fields are individually well-formed ("a valid cooler") without checking the wallet actually owns the referenced outpoint ("a loan originated by the clearinghouse"). The corrupted accounting then propagates: fabricated inputs inflate the perceived balance and are committed into a Taproot sighash, producing transactions that are permanently unbroadcastable.

### Finding Description
The external report's bug class is: *a consumer validates that an input object belongs to a trusted container/type, but never validates that this contract actually originated/owns it, so foreign objects corrupt internal accounting.*

In Serai:

- `ReceivedOutput` is the unit of "spendable funds". `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) deserializes `offset`, `output`, and `outpoint` from untrusted bytes with zero cross-field or on-chain validation.
- `Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) is the only constructor that binds `outpoint`/`output` to a real transaction, and it only matches `script_pubkey` — meaning *any* party who sends funds to a registered script (including the deterministic `Branch`/`Change`/`Forwarded` offset addresses derived via `hash_to_F(KEY_DST, ...)` in processor/src/networks/bitcoin.rs:333-344) is reported as a wallet-owned output of an internal `OutputType`.
- `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256) consumes `Vec<ReceivedOutput>` directly: `input_sat` is summed from the *declared* `TxOut.value` (line 175), and `prevouts` are built from the *declared* `TxOut`s (line 253) — no outpoint-existence or value check.
- `TransactionSignMachine::sign` (send.rs:373-390) signs with `Prevouts::All(&self.tx.prevouts)`, committing every input's signature to the *declared* prevout values. BIP-341 requires each prevout amount to match the real UTXO, so any fabricated/mismatched `TxOut` makes the entire transaction consensus-invalid.
- `SignableTransaction::multisig` (send.rs:273-285) only checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey`. An attacker who copies a *real* script pubkey (publicly visible on-chain for every registered offset) trivially satisfies this while supplying a bogus outpoint or inflated value.

### Impact Explanation
- **Funds reported received that are not spendable**: a deserialized `ReceivedOutput` with a fabricated outpoint/value is indistinguishable from a real one. The wallet treats it as spendable input value (`input_sat` at send.rs:175), plans payments against it, and produces a threshold signature over `Prevouts::All` — but the resulting transaction can never confirm because the prevout data committed in the sighash doesn't match the chain.
- **Signing-session poisoning / withdrawal DoS**: one forged `ReceivedOutput` in the input set invalidates every input's signature. Because inputs can be aggregated across many outputs, a single bogus entry makes the whole batch transaction unbroadcastable. Retries rebuilt from the same tainted output set fail identically, permanently stalling the spend path.
- **Balance/fee misaccounting**: `fee()` (send.rs:138-141) and `needed_fee` are computed from declared values; inflated values cause `NotEnoughFunds` checks to pass when they shouldn't, or change outputs to be computed against nonexistent value.

### Likelihood Explanation
Reachable by an unprivileged party wherever serialized `ReceivedOutput`/`Output` bytes (or `Output::read`, which embeds `ReceivedOutput::read` at processor/src/networks/bitcoin.rs:156) are accepted across a trust boundary — e.g., coordinator-supplied input lists or stored outputs replayed after a scan. The script-pubkey consistency check in `multisig` is bypassed by copying any observed wallet script pubkey, so no private material is needed. This is a Medium/High availability and accounting-integrity issue rather than direct theft: the multisig's keys are not compromised, but the spend path can be durably poisoned and phantom balances introduced.

### Recommendation
- Bind `ReceivedOutput` at construction: `ReceivedOutput::read` should be considered raw bytes only; before an output enters `SignableTransaction::new`, verify (a) the outpoint exists on-chain, (b) its actual `TxOut` equals the declared `TxOut` (value *and* script_pubkey), and (c) `script_pubkey == p2tr_script_buf(group_key + G*offset)`. Move the check currently in `multisig` into construction so failures are detected before signing, and add an outpoint/RPC verification step.
- Treat scanner-produced and deserialized `ReceivedOutput`s as distinct types so unverified deserialized values cannot enter `SignableTransaction::new`.
