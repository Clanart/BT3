### Title
Attacker-Controlled Git Server Can Spoof `WWW-Authenticate: realm="GitHub"` to Trigger an Enterprise Sign-In/OAuth Flow Bound to a Malicious Endpoint - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
`getEndpointKind()` classifies a credential request as GitHub `'enterprise'` based on a `WWW-Authenticate` header value (`realm="GitHub"`) returned by whatever git server handled the request, with no verification that the server is actually a GitHub Enterprise instance. [1](#0-0) 
That classification is then used by `getCredential()` to automatically invoke `ui.promptForGitHubSignIn(endpoint)`, which drives the app's real Enterprise/OAuth sign-in UI against the attacker-chosen `endpoint` extracted directly from the credential-request URL, with no allow-list or user confirmation of the destination before the sign-in flow starts. [2](#0-1) [3](#0-2) 

### Finding Description
The broken invariant is: "GitHub sign-in/OAuth is only offered for endpoints that are actually GitHub/GHE hosts." This is enforced by a heuristic — a header value sent by the remote server itself — instead of a hard-trust boundary.

Flow:
1. Desktop performs a git operation (`clone`/`fetch`/`push`/`pull`, including submodule updates) against a remote URL supplied by the user or embedded in a repository (e.g. a `.gitmodules` entry, an org's fork remote, or any URL the app is told to open/clone).
2. When that remote requires authentication, git invokes Desktop's credential-helper trampoline; the request includes any `WWW-Authenticate` headers the server returned, forwarded verbatim as `wwwauth[]` entries. [1](#0-0) 
3. `getEndpointKind()` checks these attacker-supplied headers: if any contains `realm="GitHub"`, the endpoint is classified `'enterprise'` — a fully attacker-controlled, unauthenticated signal.
4. In `getCredential()`, if the endpoint is not `'generic'` and no existing account matches, Desktop calls `ui.promptForGitHubSignIn(endpoint)` using the attacker's own host as `endpoint`. [4](#0-3) 
5. `promptForGitHubSignIn()` takes that raw `origin` and calls `dispatcher.beginEnterpriseSignIn(cb)` + `dispatcher.setSignInEndpoint(origin)`, then shows the real `SignIn` popup (`isCredentialHelperSignIn: true`) pointed at the attacker's origin. [3](#0-2) 

This mirrors the report's broken-invariant shape: a reward/trust decision (here, "this is a legitimate GitHub endpoint worth an OAuth/sign-in flow") is made from a transient, attacker-controllable signal (the “in-range at removal time” state in the original report; here, a self-reported HTTP header) rather than from a persistent, verified property. Just as account B could pose as an eligible in-range LP without earning the fees, an attacker-controlled git host can pose as “GitHub Enterprise” without being one, and get the app's trusted sign-in machinery pointed at it.

Existing guards that fail to stop this:
- `isGist`/`isDotCom`/`isGHE` checks run first but only match well-known GitHub domains, so any other host falls through to the header-based heuristic.
- `findGitHubTrampolineAccount` is only consulted for *existing* accounts; it does not gate whether a *new* sign-in should be offered.
- There is no check that the header actually reflects a GHE-branded `WWW-Authenticate` response from a domain the user previously trusted, and no user-facing warning that the sign-in destination is attacker-influenced rather than user-chosen (contrast with normal Enterprise sign-in, where the user manually types the hostname).

### Impact Explanation
This enables unauthorized/unexpected OAuth or account-binding flows against a host the user did not intentionally choose to authenticate to, satisfying the "unauthorized OAuth or account binding" impact category. Concretely:
- A malicious git remote (or a MITM/compromised proxy sitting between Desktop and a real remote) can, purely by returning a crafted `WWW-Authenticate` header on a 401, cause Desktop to launch its native "Sign in to GitHub Enterprise" popup scoped to the attacker's `origin`.
- If the user (believing this is a legitimate app-initiated Enterprise sign-in, since it uses the real `SignIn` popup) completes the flow — via OAuth callback or manual PAT entry — the resulting token exchange/account binding happens against the attacker-controlled host, and any token or callback data is exposed to the attacker's server rather than a real GitHub endpoint.
- Since `updateSubmodulesAfterOperation`/`envForRemoteOperation` machinery routes submodule fetches through the same trampoline credential helper, this attack surface is reachable via a cloned/fetched repository containing a submodule pointing at attacker infrastructure, matching the "attacker controls a cloned/fetched repository" and "git remote/proxy response" valid-impact criteria. [5](#0-4) 

### Likelihood Explanation
Moderate. It requires the user to actually complete a sign-in prompt pointed at an unfamiliar host, so some social element remains (the user must notice/accept the popup), but no special local access, malware, or leaked credentials are required — only a git remote or a MITM/proxy under attacker control returning a specific HTTP header on the auth challenge, which is trivial for the operator of any git server the app is pointed at (including via a submodule embedded in an otherwise innocuous cloned repository).

### Recommendation
Do not use unauthenticated header content (`WWW-Authenticate` realm strings) as sufficient basis to launch the Enterprise/OAuth sign-in UI. At minimum:
- Require an explicit, out-of-band trust decision (e.g., the user must have manually added this GHE endpoint before, or must be shown/confirm the exact hostname with a clear "unverified" warning) before invoking `beginEnterpriseSignIn`/`setSignInEndpoint` based on header heuristics.
- Consider dropping the `wwwauth[]`-based enterprise inference entirely, or gating it behind an active network probe (`isGitHubHost`) rather than trusting the string returned by the remote, since `isGitHubHost` is already used as the fallback and is a stronger signal. [6](#0-5) 
- Surface the discovered `endpoint` prominently and unmistakably in the `SignIn` popup so the credential-helper–initiated flow is visually distinct from a user-initiated "Add Enterprise account" flow.

### Proof of Concept
1. Attacker stands up a git-over-HTTPS server at `https://attacker.example` that responds to unauthenticated requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote (or clones a repository containing a `.gitmodules` submodule pointing at it) and triggers any git network operation (`fetch`, `clone`, `push`, or submodule update) in Desktop.
3. Git invokes Desktop's credential helper; the `wwwauth[]` header is forwarded to `getEndpointKind`, which returns `'enterprise'` due to the `realm="GitHub"` match. [7](#0-6) 
4. Since no existing account matches `https://attacker.example`, `getCredential` calls `ui.promptForGitHubSignIn('https://attacker.example')`. [4](#0-3) 
5. Desktop opens its real `SignIn` popup, calling `beginEnterpriseSignIn` and `setSignInEndpoint('https://attacker.example')`, initiating an OAuth/PAT flow against the attacker's host. [8](#0-7) 

Note: I could not fully trace the downstream `beginEnterpriseSignIn`/OAuth exchange implementation (e.g., exact token-exchange endpoint construction) within the indexed portion of the codebase, so I cannot confirm with certainty whether additional server-side validation in the OAuth exchange step would block credential exfiltration in all cases (e.g., PAT-based manual sign-in vs. browser OAuth). This should be verified with a full checkout of the repository before treating impact severity as final.

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.

    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
