### Title
Webhook Shop Domain Spoofing via Unauthenticated Header - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` authenticates an incoming webhook by HMAC-validating only the raw request body, while the shop that the webhook is attributed to is read from the unauthenticated `X-Shopify-Shop-Domain` HTTP header. Because the webhook HMAC secret is the app's single `api_secret_key`/`old_secret`, shared across every shop that has installed the app (not a per-shop secret), any merchant who has installed the app can capture a legitimately HMAC-signed webhook delivered to their own store, swap the `X-Shopify-Shop-Domain` header to a victim shop's domain, and replay it. The body HMAC remains valid (it never covered the header), so `verify_request` passes, and the app processes attacker-controlled webhook data attributed to a shop the attacker doesn't own — the same bug class as the reported issue, where a value (`encryptedOutputs`/here, the shop-domain attribution) is not bound by the integrity check that gates acceptance of the message.

### Finding Description
`WebhookVerification#verify_request` only computes and checks the HMAC over `request.raw_post`: [1](#0-0) 

The module's own `shop_domain` helper — explicitly documented and used by generated/custom webhook controllers to route/attribute the webhook — reads directly from the request header, which is completely outside the HMAC's coverage: [2](#0-1) 

Both the docs and the generator template instruct app developers to build shop-scoped jobs directly from this unauthenticated value: [3](#0-2) [4](#0-3) 

`PayloadVerification#hmac_valid?` confirms the digest is computed only over `data` (the body) using the app's global secret(s), with no shop-specific binding: [5](#0-4) 

Since the HMAC secret is the single app-level secret shared by all merchants who install the app (this is standard Shopify app architecture — not a leaked/compromised secret scenario), any installed merchant can legitimately obtain a validly-signed webhook for their own shop and then modify the `X-Shopify-Shop-Domain` header before replaying it to the app's webhook endpoint. The signature check still passes because it never covered that header, exactly mirroring the reported class of bug: a value trusted downstream for attribution/decryption/dispatch is excluded from the authenticity check that is supposed to make the message untamperable.

### Impact Explanation
Any custom webhook controller (or generator-produced controller) that follows the documented pattern of using `shop_domain` (or the header directly) to key persistence, deletion, redaction, or entitlement logic can be tricked into performing shop-scoped actions attributed to a victim shop while the actual payload/content originates from the attacker's own shop. This is a cross-shop data-integrity/data-confusion vulnerability: a malicious but legitimately-installed merchant can inject or misattribute events for another merchant's shop, potentially corrupting per-shop state, triggering deletion/redaction workflows against the wrong tenant, or causing desynchronization between the app's data and the true store the event pertains to.

### Likelihood Explanation
Any actor able to install the app on at least one shop (a normal, unprivileged action) can trivially capture their own valid webhook and modify the shop-domain header before replaying it, since no signing material beyond the shared app secret is required and that secret is common to the entire app's install base. The bug requires no leaked secret and no elevated privilege — only participation as an ordinary merchant, which satisfies an "unrelated-merchant" threat model.

### Recommendation
Bind the shop identity into the integrity check, e.g., include the shop domain in the HMAC input (mirroring the "include `encryptedOutputs` in `callDataHash`" recommendation from the report) or cross-validate `X-Shopify-Shop-Domain` against a shop identifier embedded in the verified payload body before trusting it for any downstream routing, storage, or destructive operation. At minimum, documentation and generated templates should warn against using the raw header value for shop attribution without further validation against session/install records.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` (a normal install, no special privilege).
2. Shopify sends attacker a legitimate webhook, HMAC-signed with the app's shared secret, headers include `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the identical body/HMAC to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `WebhookVerification#verify_request` recomputes the HMAC over the (untouched) body and it still matches, so the request passes verification.
5. The controller/job built per the documented pattern (`SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`) executes using `shop_domain == "victim.myshopify.com"`, even though the payload content originated from the attacker's shop — demonstrating cross-shop attribution without needing the victim's credentials or any leaked secret.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
