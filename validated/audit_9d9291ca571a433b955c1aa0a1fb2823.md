## Analysis

The Caviar bug's core invariant is: **a single beneficiary that cannot accept a forced native-token push causes an unrelated, otherwise-successful operation to revert.** In Hyperbridge, the exact same "recipient rejects ETH → revert" pattern exists in the escrow-release paths, but it becomes exploitable at scale because the ISMP message handler processes **multiple unrelated requests in one atomic batch, with no per-request isolation**.

### Title
Atomic multi-request batching in `handlePostRequests` lets a single unpayable-ETH beneficiary block delivery of unrelated requests - (`evm/src/core/HandlerV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` pushes native ETH to an attacker-supplied `beneficiary` and unconditionally reverts the whole call if the low-level `call` fails: [1](#0-0) . This `_withdraw` runs inside `onAccept`, which is invoked by `IHost.dispatchIncoming` from `HandlerV2.handlePostRequests`, which loops over **every leaf in the submitted batch** and dispatches them sequentially with no isolation between requests: [2](#0-1) . Because there is no try/catch around `host.dispatchIncoming`, a revert triggered by processing one poisoned request rolls back the entire `handlePostRequests` transaction — including the Merkle proof verification and dispatch of every other, unrelated request bundled in the same call.

### Finding Description
An unprivileged attacker can place a cross-chain intent order whose `order.user` (the escrow beneficiary on refund/cancel/redeem) is a contract with no payable `receive()`/`fallback()`, using a native-token (`address(0)`) input asset. When that order is later refunded or redeemed — e.g., via `RedeemEscrow`/`RefundEscrow` on cancellation or timeout — the destination dispatches a `WithdrawalRequest` `PostRequest` back to the source chain whose `beneficiary` field is the attacker's non-payable contract: [3](#0-2) .

When this request is delivered, `HandlerV2.handlePostRequests` verifies a single Merkle-Mountain-Range proof covering the *entire* batch of leaves supplied by the relayer, then dispatches each leaf one by one via `host.dispatchIncoming`: [4](#0-3) . The identical atomic-batch pattern also exists in `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`, and is explicitly documented for `IHandlerV2.batchCall`: "If any call fails, the entire batch reverts": [5](#0-4) .

Because `_withdraw`'s native transfer reverts deterministically for the poisoned request (the contract has no payable fallback — this is not a gas-griefing or reentrancy condition, it is a hard revert), any batch that includes this request together with other, unrelated pending requests fails as a whole. Relayers batch requests for gas efficiency by construction (this is the normal/expected/honest behavior documented for the fee/proof pipeline), so no malicious relayer, prover, or governance actor is required — an ordinary relayer doing its normal job of bundling pending leaves into one MMR-proof submission is sufficient to reproduce the block.

### Impact Explanation
This is a logic attack against request delivery, not a generic gas DoS: the attacker deterministically and repeatedly poisons any batch containing their crafted request, since the same leaf will keep reappearing in subsequent MMR proofs until it is delivered or times out. Every other request whose commitment happens to land in the same relayer-submitted batch is blocked from being delivered while the challenge period/timeout clock keeps running. Requests that consequently expire enter the timeout path, forcing legitimate, uninvolved users into refund flows they did not choose — losing the intended cross-chain settlement, any surplus/dust split that only applies on a genuine fill, and the gas/time already spent, which is a concrete funds-availability/loss-of-intended-outcome impact for third parties, triggered purely by an unprivileged attacker's own order configuration.

### Likelihood Explanation
Likelihood is high for the attacker's own poisoned request (trivial to construct: deploy a contract with no payable fallback, use it as `order.user`, use native ETH as an input asset, then trigger cancellation/timeout to generate the malicious `WithdrawalRequest`). The blast radius on other users depends on relayer batching granularity, but batching multiple pending leaves per MMR proof is the documented, expected relayer behavior rather than an edge case, since `handlePostRequests` is explicitly designed to process `request.requests` as an array in one call.

### Recommendation
Wrap each per-leaf dispatch in `handlePostRequests` (and the analogous loops in `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) in a call that isolates failures per request (e.g., an internal `try/catch` around `dispatchIncoming`, marking the failed leaf's receipt so it can be retried/timed-out individually instead of reverting the whole batch). Additionally, apply the same "native-push-with-WETH-fallback" pattern already used in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` ( [6](#0-5) ) to `IntentsBase._withdraw` and `IntentGatewayV2.withdraw`, so a beneficiary that cannot accept native ETH degrades to a wrapped-token transfer instead of hard-reverting the entire request.

### Proof of Concept
1. Deploy `RejectETH` — a contract with no `receive()`/payable `fallback()`.
2. Place a same-chain or cross-chain intent order (`IntentGatewayV2`/`IntentsBase`) with `order.user = address(RejectETH)` and a native-ETH input asset, escrowing funds normally.
3. After the order's deadline (or on a legitimate cancel), trigger the refund path so a `WithdrawalRequest{beneficiary: RejectETH, tokens: [native]}` `PostRequest` is dispatched back to the source chain, per `IntentsBase._withdraw`/`IntentGatewayV2.withdraw` ( [1](#0-0) , [7](#0-6) ).
4. When a relayer submits this request together with any other pending request in the same `PostRequestMessage.requests` array to `HandlerV2.handlePostRequests`, `host.dispatchIncoming` for the poisoned leaf reverts inside `_withdraw`'s `if (!sent) revert InsufficientNativeToken();`, which bubbles up and reverts the *entire* `handlePostRequests` call ( [2](#0-1) ), rolling back delivery of every other leaf in that submission regardless of their own validity.
5. Repeat submission attempts with the same batch composition fail identically until the poisoned leaf is excluded, during which unrelated requests' timeout clocks continue to run.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
