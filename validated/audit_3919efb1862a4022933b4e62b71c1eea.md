### Title
Deposits to publicly-derivable internal offset addresses (Branch/Change/Forwarded) are scanned and reported as received but are never credited nor recoverable — ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
The analog of M-02 (ETH escrowed to a recipient that can never withdraw) is Serai's Bitcoin scanner unconditionally reporting any output paying to a registered offset script as a received output, while only `External`-kind outputs are given depositor data and downstream crediting. Since the `Branch`, `Change`, and `Forwarded` offsets are deterministically derived via `Secp256k1::hash_to_F(KEY_DST, ...)`, anyone can compute these internal addresses and send BTC to them. The scanner will report the output as received (kind `Forwarded`/`Change`/`Branch`), but `get_outputs` only attaches the `InInstruction` data to `External` outputs, so the depositor's funds sit in the multisig with no attribution and no recovery path — locked, exactly as in M-02.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`, `Scanner::register_offset` registers deterministic offsets and `scan_transaction` matches purely on `output.script_pubkey` — it cannot distinguish who created the output or why [1](#0-0) .

In `processor/src/networks/bitcoin.rs`, the `scanner()` function registers `Branch`, `Change`, and `Forwarded` offsets from fixed `hash_to_F(KEY_DST, b"branch" | b"change" | b"forward")` values [2](#0-1) . These are public constants — `forward_address` exposes exactly this derivation [3](#0-2)  — so any unprivileged party can compute a valid, scanner-watched script_pubkey.

`get_outputs` then scans every non-coinbase transaction, classifies each matched output by offset, and attaches the extracted `InInstruction` data **only** to `OutputType::External` outputs [4](#0-3) [5](#0-4) . A user depositing to the `Forwarded`/`Branch`/`Change` script produces a `Forwarded`/`Change`/`Branch` output with empty `data`, which downstream code treats as an internal transfer artifact rather than a deposit.

### Impact Explanation
Like `pendingWithdrawals` in M-02, the BTC is correctly held by the threshold multisig (it is spendable in principle via `key + offset`), but it is never credited to the sender, carries no refund instruction, and no withdrawal/recovery path exists for it. Worse, a `Forwarded`-kind output can be misinterpreted as the completion of an actual forward eventuality, desynchronizing processor state. Funds are effectively locked in escrow — recoverable only via manual coordinator intervention, identical to Foundation's "migrate to FETH" fix.

### Likelihood Explanation
Any external user can compute the internal addresses with only the group key (public) and the fixed DST string — `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")` needs no privileged access. A mistaken or malicious deposit, or deliberate griefing by sending dust-above-`N::DUST` to `Branch`/`Forwarded` addresses, triggers misclassified outputs. Medium severity: funds are recoverable by the validator set in principle (key-path spend with the known offset), so the worst case is temporarily unavailable funds plus accounting corruption — the same reasoning that downgraded M-02 to Medium.

### Recommendation
Restrict which scripts external deposits may be credited against, or explicitly handle non-`External` outputs that carry depositor `data`/`presumed_origin`: treat an output at a `Forwarded`/`Change`/`Branch` script originating from an unrecognized external input as an `External` deposit (with refund capability), or add an explicit recovery path so escrowed funds at internal offsets can be returned. At minimum, do not silently classify external sends to internal scripts as internal transfer artifacts.

### Proof of Concept
1. Obtain the multisig group key `key` (public).
2. Compute `forward_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")` and the address `p2tr_script_buf(key + G*forward_offset)` — the same computation as `forward_address` [3](#0-2) .
3. Send BTC to that address in a normal transaction.
4. `Scanner::scan_transaction` matches the `script_pubkey` and emits a `ReceivedOutput` with the `Forwarded` offset [1](#0-0) ; `get_outputs` reports it as `OutputType::Forwarded` with empty `data` [5](#0-4) .
5. The deposit is never credited to any account and has no defined reclaim path — escrowed funds exactly analogous to M-02's trapped `pendingWithdrawals`.
