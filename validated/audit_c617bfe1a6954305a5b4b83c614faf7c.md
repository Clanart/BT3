## Finding

GitHub Desktop's clone implementation explicitly disables Git's built-in clone-time protection against the CVE-2024-32002 class of RCE, while cloning attacker-controlled repositories with `--recursive` (submodules) by default.

### Title
Clone explicitly disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard, re-opening malicious-repo RCE via case-folding/`.git`-collision during recursive clone - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` builds the environment for every `git clone` invocation and hard-codes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` [1](#0-0) , unconditionally, for every clone the app performs, including `--recursive` clones of arbitrary, attacker-supplied URLs [2](#0-1) . `GIT_CLONE_PROTECTION_ACTIVE` is the exact environment variable upstream Git added to let a caller opt back into (or out of) the hardened clone checks introduced to fix CVE-2024-32002 (a case-insensitive/Unicode-normalizing filesystem collision between a tracked file/submodule path and `.git/hooks`, allowing a hook to be written and executed during clone). By setting this flag to `'false'`, Desktop is deliberately turning that protection off for every clone, rather than relying on Git's default (protection enabled).

### Finding Description
The only local mitigation present is `isClonePathSensitive()`, which only checks whether the *destination directory itself* resolves to a sensitive system path (home dir, `.ssh`, `.gnupg`, `.config`, `%APPDATA%`) [3](#0-2) . That check is orthogonal to the vulnerability class the `GIT_CLONE_PROTECTION_ACTIVE` guard is designed to stop: it does nothing about a malicious *repository being cloned* containing a submodule or tree entry whose name collides with `.git` on a case-insensitive or Unicode-normalizing filesystem (e.g. default macOS/Windows). The `clone` function always adds `--recursive` [4](#0-3)  so any submodules referenced by an attacker-controlled repo are fetched and checked out automatically as part of the normal "Clone repository" flow (`cloningRepositoriesStore.clone` → `cloneRepo` → `clone()`) [5](#0-4) , with no user prompt or review of submodule content before the recursive checkout runs.

### Impact Explanation
This fits the "attacker controls a cloned/fetched repository" primitive precisely: a user only needs to clone (or "Open in Desktop" / "Clone Again") a malicious public/shared repository URL. If Git's clone-protection guard is what stands between a crafted repo and writing into `.git/hooks` (via a case/normalization collision path introduced by CVE-2024-32002), explicitly forcing `GIT_CLONE_PROTECTION_ACTIVE=false` removes that backstop for all Desktop clones, independent of the Git version bundled, and could let a maliciously crafted repository achieve arbitrary code execution on checkout/hook invocation during a normal, expected clone action.

### Likelihood Explanation
Likelihood is high for exposure: every clone Desktop performs goes through this single `clone()` function and every one of them disables the protection, unconditionally, with `--recursive` enabled by default [6](#0-5) . The action is a completely ordinary, expected user action (cloning a repo from a link, "Open in Desktop", or "Clone Again" from a missing repository) [7](#0-6) [8](#0-7) , requiring no unnatural steps, admin rights, or pre-existing compromise.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` so the bundled Git's default (protection enabled) applies, or set it to `'true'` explicitly; if there is a specific compatibility reason it was disabled, gate it behind an explicit, narrowly-scoped exception rather than a blanket override for every clone.

### Proof of Concept
1. Craft a malicious Git repository containing a submodule/path entry designed to collide with `.git`/`.git/hooks` under case-insensitive/Unicode-normalizing filesystem semantics (the CVE-2024-32002 pattern).
2. Share the repository URL and have a victim clone it via GitHub Desktop's clone dialog or an `x-github-client://openRepo` deep link that resolves to `_clone`/`clone()` [9](#0-8) .
3. Because `clone()` always passes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and `--recursive` [10](#0-9) , Git's hardened collision check is bypassed during the recursive checkout, allowing the crafted submodule entry to land in/execute from `.git/hooks` on checkout.

Note: I could not execute Git locally to empirically reproduce the CVE-2024-32002 collision inside this sandbox (index-only access), so step 3's exploitability depends on the bundled `dugite`/Git version's behavior when the flag is disabled — this should be validated against the actual bundled Git version in a full Devin session with terminal access.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

  public async clone(
    url: string,
    path: string,
    options: CloneOptions
  ): Promise<boolean> {
    const repository = new CloningRepository(path, url)
    this._repositories.push(repository)

    const title = `Cloning into ${path}`

    this.stateByID.set(repository.id, { kind: 'clone', title, value: 0 })
    this.emitUpdate()

    let success = true
    try {
      await cloneRepo(url, path, options, progress => {
        this.stateByID.set(repository.id, progress)
        this.emitUpdate()
      })
    } catch (e) {
      success = false

      const retryAction: RetryAction = {
        type: RetryActionType.Clone,
        name: repository.name,
        url,
        path,
        options,
      }
      e = new ErrorWithMetadata(e, { retryAction, repository })

      this.emitError(e)
    }

    this.remove(repository)

    return success
  }
