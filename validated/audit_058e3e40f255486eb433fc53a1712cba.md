Confirmed: `ParseTransferArgs`/`ParseTransferFromArgs` in the ERC20 precompile perform no zero-address validation, and the `transfer` handler passes `to` straight into a `banktypes.MsgSend` without checking against `address(0)`.

### Title
ERC20/WERC20 precompile permits transfers to the zero address, permanently freezing user funds - (File: `precompiles/erc20/tx.go`, `precompiles/erc20/types.go`)

### Summary
The Nouns Builder finding is about `_delegate` never guarding against `address(0)` as a destination, causing voting power to be silently and permanently lost when a user "delegates" to the zero address. The Cosmos EVM analog is the `erc20` (and by extension `werc20`) precompile's `transfer`/`transferFrom` implementation, which similarly never validates that the destination `to` address is non-zero before executing a native bank `MsgSend`. Unlike a standard OpenZeppelin ERC20 (`require(to != address(0), "ERC20: transfer to the zero address")`, as seen for reference in `precompiles/erc20/testdata/ERC20NoMetadata.sol:213` and `tests/evm-tools-compatibility/hardhat/Flattened.sol:583-585`), the precompile path has no such check.

### Finding Description
- `Transfer` and `TransferFrom` call `ParseTransferArgs`/`ParseTransferFromArgs` (`precompiles/erc20/types.go:26-71`), which only type-assert the `to`/`from` arguments — they never reject `common.Address{}` (the EVM zero address). [1](#0-0) 
- The shared `transfer` helper then builds a Cosmos bank `MsgSend` directly from these unchecked addresses and dispatches it via the bank message server, with no zero-address guard: [2](#0-1) 
- The Cosmos SDK bank module only rejects `BlockedAddr` recipients (module accounts, e.g. `x/precisebank`'s reserve as shown in `tests/integration/x/precisebank/test_mint_integration.go:23-44`), not the all-zero `AccAddress`. Sending to `0x000...000` succeeds as an ordinary account credit.
- Because no private key (in practice) corresponds to the all-zero address, and the precompile/bank layer performs no burn accounting for it (unlike `_mint`/`_burn` in the reference OpenZeppelin contract, which explicitly routes `address(0)` through total-supply adjustment, see `precompiles/erc20/testdata/ERC20NoMetadata.sol:243-285`), the transferred coins are not burned nor returned — they are irrecoverably locked in an unspendable account.
- This affects every token-pair-backed ERC20 precompile instance (native coins, registered IBC vouchers, converted native ERC20s), since all of them share this `transfer` code path.

### Impact Explanation
Any unprivileged user who calls `transfer(address(0), amount)` or is tricked/misconfigured (e.g., a dApp integration bug, a poorly sanitized "burn" call, or a delegate/proxy contract computing a bad recipient) irreversibly locks their own or a third party's escrowed value with no recovery path — this matches the "Critical permanent freezing/locking/theft of user funds" impact category. Because the ERC20 precompile is the standard interface bridging native Cosmos coins (and IBC voucher balances) into the EVM, this is a chain-wide token/accounting integrity issue, not merely a UX inconvenience, and it applies uniformly across every registered token pair.

### Likelihood Explanation
The trigger is a single unprivileged EVM call (`IERC20(precompileAddr).transfer(address(0), amount)`), requiring no special permissions, validator collusion, or multi-step setup. It is exactly analogous to the original Nouns Builder scenario in that it stems from an omitted `!= address(0)` check on a value-moving code path that is otherwise expected to include it (as evidenced by the very OpenZeppelin ERC20 template shipped elsewhere in this same repo, which does include the check).

### Recommendation
Add an explicit zero-address check in `precompiles/erc20/types.go`'s `ParseTransferArgs`/`ParseTransferFromArgs` (and equivalently in the `werc20` transfer path, since it reuses the same ERC20 handler) to reject `to == common.Address{}`, mirroring the standard ERC20 `_transfer` zero-address guard already present in the repo's own reference `ERC20NoMetadata.sol`/`Flattened.sol` contracts. Alternatively/additionally, add `common.Address{}`'s corresponding `sdk.AccAddress` to the bank module's blocked-address set used by `BlockedAddr`.

### Proof of Concept
1. Deploy/enable an ERC20 token-pair precompile for any native/IBC denom (as in `precompiles/erc20/erc20.go:79-98`).
2. From an EOA holding a balance of that token, call `precompile.transfer(address(0), amount)` directly through the precompile ABI (`TransferMethod`, `precompiles/erc20/tx.go:17-44`).
3. Observe: `msgSrv.Send(ctx, msg)` succeeds (`precompiles/erc20/tx.go:112-116`) because the Cosmos bank keeper does not treat the zero `AccAddress` (20 zero bytes) as a `BlockedAddr`; funds are debited from the sender and credited to an address no one can access.
4. Query `balanceOf(address(0))` via the precompile — it will report the locked balance, but there is no `withdraw`/`burn` path to recover or reclaim it, confirming permanent, irreversible fund loss.

func ParseTransferArgs(args []interface{}) (
	to common.Address, amount *big.Int, err error,
) {
	if len(args) != 2 {
		return common.Address{}, nil, fmt.Errorf("invalid number of arguments; expected 2; got: %d", len(args))
	}

	to, ok := args[0].(common.Address)
	if !ok {
		return common.Address{}, nil, fmt.Errorf("invalid to address: %v", args[0])
	}

	amount, ok = args[1].(*big.Int)
	if !ok {
		return common.Address{}, nil, fmt.Errorf("invalid amount: %v", args[1])
	}

	return to, amount, nil
}

func (p *Precompile) transfer(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
	method *abi.Method,
	from, to common.Address,
	amount *big.Int,
) (data []byte, err error) {
	coins := sdk.Coins{{Denom: p.tokenPair.Denom, Amount: math.NewIntFromBigInt(amount)}}

	msg := banktypes.NewMsgSend(from.Bytes(), to.Bytes(), coins)

	if err = msg.Amount.Validate(); err != nil {
		return nil, err
	}

	isTransferFrom := method.Name == TransferFromMethod
	spenderAddr := contract.Caller()
	newAllowance := big.NewInt(0)

	if isTransferFrom {
		prevAllowance, err := p.erc20Keeper.GetAllowance(ctx, p.Address(), from, spenderAddr)
		if err != nil {
			return nil, ConvertErrToERC20Error(err)
		}

		newAllowance = new(big.Int).Sub(prevAllowance, amount)
		if newAllowance.Sign() < 0 {
			return nil, ErrInsufficientAllowance
		}

		if newAllowance.Sign() == 0 {
			// If the new allowance is 0, we need to delete it from the store.
			err = p.erc20Keeper.DeleteAllowance(ctx, p.Address(), from, spenderAddr)
		} else {
			// If the new allowance is not 0, we need to set it in the store.
			err = p.erc20Keeper.SetAllowance(ctx, p.Address(), from, spenderAddr, newAllowance)
		}
		if err != nil {
			return nil, ConvertErrToERC20Error(err)
		}
	}

	msgSrv := NewMsgServerImpl(p.BankKeeper)
	if err = msgSrv.Send(ctx, msg); err != nil {
		// This should return an error to avoid the contract from being executed and an event being emitted
		return nil, ConvertErrToERC20Error(err)
	}
