### Title
Attacker-controlled `t`/`n` in serialized `ThresholdKeys` forces quadratic Lagrange interpolation causing CPU-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::read` deserializes `t`, `n`, and `i` directly from attacker-controlled bytes, then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for each of participants `1..=t`. Each `interpolation_factor` call under `Interpolation::Lagrange` iterates over all `t` participants and performs one field inversion, giving total complexity O(t²) modular multiplications plus O(t) field inversions and O(t) scalar-point multiplications — all triggered by a few bytes of input with `t = n = 65535` (u16 max).

### Finding Description

In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, `i` as raw `u16`s from the stream and passes them to `ThresholdParams::new`/`ThresholdKeys::new` without any bound beyond `t <= n <= 65535` (lines 591–631). `ThresholdKeys::new` then computes:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

(lines 376–378). `Interpolation::Lagrange::interpolation_factor` loops over all `t` entries in `included` multiplying numerator/denominator, and ends with `num * denom.invert().unwrap()` — a full field inversion per participant (lines 226–248). So one call to `ThresholdKeys::new` costs `t` inversions plus `t²` field multiplications and `t` group scalar multiplications. With `t = n = 65535`, a single untrusted serialized blob of ~4 MB forces ~4·10⁹ field multiplications plus 65k inversions and 65k point multiplications — analogous to CVE-2023-50868, where a small attacker input forces a disproportionate number of expensive hash computations (CPU-amplification DoS).

The same amplification exists on the signing path: `ThresholdKeys::view` calls `interpolation_factor` once per included participant (lines 500–507), and `ThresholdView::interpolation_factor` exposes it again at line 657, each with a field inversion and O(|included|) work.

### Impact Explanation

An unprivileged party who can feed crafted bytes to `ThresholdKeys::read` (e.g., keys/gossip/state received over the network during reshare or session setup) can stall the victim's CPU with ~billions of modular multiplications per deserialization. The `invert().unwrap()` cannot panic (denominator is non-zero since `i` is skipped), so the result is pure CPU exhaustion, exactly the NSEC3-style "many expensive operations from small input" class. This is a genuine availability impact on a reachable public-input path.

### Likelihood Explanation

Likelihood depends on the deployment deserializing untrusted `ThresholdKeys`; the deserialization path itself performs the expensive work eagerly inside `ThresholdKeys::new` before the caller can apply any policy. No validation short-circuits the O(t²) interpolation — it runs unconditionally for every `read`.

### Recommendation

Cap `t`/`n` to a sane protocol bound (e.g., a few hundred) in `ThresholdParams::new` or early in `ThresholdKeys::read` before interpolation, and/or precompute and cache Lagrange coefficients so `interpolation_factor` is O(t) total (product-prefix technique) instead of O(t²) with per-participant inversions.

### Proof of Concept

Serialize a `ThresholdKeys` blob with `t = n = 0xFFFF`, `i = 1`, `Interpolation::Lagrange` (byte `1`), any canonical secret share, and 65535 canonical generator encodings. Feeding it to `ThresholdKeys::read` reaches `ThresholdKeys::new` at `crypto/dkg/src/lib.rs:376-378`, which performs 65535 calls to `interpolation_factor`, each iterating 65535 field elements and performing one `invert()` at `crypto/dkg/src/lib.rs:246` — ~4.3·10⁹ field multiplications plus 65535 inversions and 65535 point multiplications, exhausting CPU from a ~4 MB input.   fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
