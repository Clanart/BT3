## Missing `output.assets.length != 0` validation in `placeOrder` allows a full escrow release for zero consideration - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` validates `order.inputs.length == 0` but never validates that `order.output.assets.length` is non-zero [1](#0-0) . Both fill paths (`_fillSameChain` and `_fillCrossChain`) derive their loop bound and their "fully filled" success condition directly from `order.output.assets.length`, and both default to treating an order as fully satisfied when that length is `0` — releasing the *entire* escrowed input to the filler while requiring the filler to deliver nothing. This is the structural equivalent of the reported `lower == upper` Uniswap tick bug: an unchecked "degenerate range" (here, an empty output requirement) causes the code to fall through branches that were written assuming a non-trivial range/requirement, yielding a token amount of zero on the side that is supposed to gate the payout.

### Finding Description
In `_fillSameChain`, `outputsLen = order.output.assets.length` bounds the `for` loop that both delivers output tokens to the beneficiary and marks `isFullyFilled` (initialized `true` and only ever set `false` inside the loop) [2](#0-1) . If `outputsLen == 0`, the loop body never executes, `isFullyFilled` remains `true`, and the function proceeds straight to:
```
_withdraw(body, false, isFullyFilled);
```
releasing 100% of the escrowed `order.inputs` to `msg.sender` with `_execute(order, outputsLen)` also running unconditionally on the "full fill" path [3](#0-2) .

The cross-chain path has the identical structure: `outputsLen = order.output.assets.length` bounds the loop that requires `solverAmount >= totalRequired` per asset [4](#0-3) . With zero outputs, the loop never runs, no `InvalidInput` check is ever hit, and the function immediately dispatches a `RedeemEscrow` message back to the source chain that unconditionally releases the full escrowed input set to the filler [5](#0-4) .

`fillOrder`'s shared pre-checks only assert `options.outputs.length == outputsLen` and `order.inputs.length == outputsLen` [6](#0-5)  — both of which are trivially satisfiable when all three arrays are empty, since `order.inputs.length == 0` is rejected only in `placeOrder`, not here, and `order.output.assets.length` is never bounded away from zero anywhere in the codebase.

This is the direct analog of the H-03 root cause: a boundary condition (`lower == upper` there, `outputs.length == 0` here) that other code paths implicitly assume cannot occur, causing the "amount required from the counter-party" computation to silently collapse to zero while the escrow-release/liquidity-credit logic still executes as if a legitimate fill had occurred.

### Impact Explanation
Any order committed on-chain via `placeOrder` with an empty `output.assets` array can be "filled" by calling `fillOrder` with matching empty `FillOptions.outputs`, immediately draining 100% of the escrowed input tokens to the caller without delivering any value to the order's beneficiary. Because `fillOrder` is a permissionless, unauthenticated entry point (guarded only by `solverSelection`, which is optional per-deployment config) [7](#0-6) , whoever observes such an order first captures the full escrow — this is unauthorized transaction/execution and direct loss of escrowed funds, not merely a self-inflicted user error, since `solverSelection` off (the default absent explicit config) permits any address to race for the fill.

### Likelihood Explanation
Exploitability depends entirely on whether an order with `output.assets.length == 0` can be produced — the contract itself places no floor on this value, so the guarantee that "every order specifies a non-trivial output" rests entirely on client/SDK behavior rather than on-chain enforcement. Given that Hyperbridge documents `output.assets` as attacker/user-suppliable struct fields with no on-chain minimum-length invariant, any integration bug, malformed SDK call, or direct contract interaction bypassing the reference frontend can produce this state, at which point exploitation requires no privileged role, relayer collusion, or governance action — only a standard `fillOrder` call.

### Recommendation
Add an explicit check in `placeOrder` (mirroring the `order.inputs.length == 0` guard) rejecting orders where `order.output.assets.length == 0`, and additionally defense-in-depth check in `_fillSameChain` / `_fillCrossChain` / `fillOrder` that `outputsLen != 0` before proceeding, so a degenerate order can never reach the unconditional "fully filled" branch.

### Proof of Concept
```solidity
// Attacker (or any careless integrator) places an order with an empty output array.
Order memory order = Order({
    user: bytes32(0),
    source: "",
    destination: host.host(),
    deadline: block.number + 100,
    nonce: 0,
    fees: 0,
    session: address(0),
    predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
    inputs: inputs,                       // e.g. 1000 USDC escrowed
    output: PaymentInfo({
        beneficiary: bytes32(uint256(uint160(user))),
        assets: new TokenInfo[](0),        // <-- zero-length, never rejected
        call: ""
    })
});

vm.startPrank(user);
usdc.approve(address(intentGateway), inputAmount);
intentGateway.placeOrder(order, bytes32(0));   // escrows 1000 USDC
vm.stopPrank();

// Any third party can now "fill" with zero outputs and drain the full escrow.
order.user = bytes32(uint256(uint160(user)));
order.source = host.host();
order.nonce = 0;

vm.startPrank(attacker);
intentGateway.fillOrder(
    order,
    FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: new TokenInfo[](0)})
);
vm.stopPrank();

// attacker now holds the full 1000 USDC escrow; user received nothing.
```
