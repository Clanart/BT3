## Finding: Native-token overpayment permanently locked in `EvmHost` due to missing swap-refund handling

### Title
Excess ETH sent to `EvmHost.dispatch`/`fundRequest` is swapped via Uniswap but never refunded to the caller, permanently locking user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report's root defect is a swap-execution path that fails to protect the depositor's value when paying with native tokens for a fee-bearing operation. The local Hyperbridge analog is not a stale-price sandwich but a structurally identical failure mode in the same category of code: `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all perform an ETH→feeToken swap via Uniswap V2 with `deadline = block.timestamp` and no accounting for unspent input, unlike the sibling contract `IntentGatewayV2.sol` which explicitly tracks and refunds the swap's leftover `msg.value`.

### Finding Description
In `EvmHost.sol`, three public payable entrypoints convert native ETH to `feeToken` by calling Uniswap V2's exact-output swap, using the entire `msg.value` as the upper bound on input: [1](#0-0) [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` is an exact-output call: it spends only as much ETH as needed to acquire the requested `post.fee`/`get.fee`/`amount` of `feeToken`, and the Uniswap V2 router refunds any unspent ETH to the caller of the swap — which in this code path is `EvmHost` itself (`address(this)` is the swap `msg.sender`, since `EvmHost` is the contract forwarding `{value: msg.value}`). Nowhere in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest` is that refunded ETH forwarded back to the original depositor (`_msgSender()`), nor is `amounts[0]` (actual ETH spent) captured to compute a difference to return.

This is a clear structural gap when compared with the correct pattern used elsewhere in the same repository, `IntentGatewayV2.placeOrder`, which performs the identical kind of swap but explicitly tracks the spent amount and refunds the remainder to the user: [4](#0-3) 

Because any real-world caller of `EvmHost.dispatch`/`fundRequest` cannot know the exact ETH cost of the swap in advance (it depends on the live AMM reserves, i.e., pool price, at execution time — the very quantity the original Compound/Uniswap report flags as attacker-influenceable), essentially every native-token payment to these entrypoints will send strictly more ETH than the swap consumes. That leftover, which the router faithfully returns to `EvmHost`, has no code path back to the user and becomes permanently trapped in the `EvmHost` contract balance.

### Impact Explanation
This is a direct, unprivileged loss of funds on a live, public entrypoint: any user calling `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest` with native ETH loses the unspent portion of `msg.value` with no way to reclaim it, since `EvmHost` has no user-facing sweep/withdraw path for this stranded ETH visible in the dispatch/fundRequest logic. This satisfies the bounty's "stealing or loss of funds" impact category without requiring a malicious peer, relayer, prover, or governance actor — the loss is triggered by ordinary use of the protocol's own dispatch mechanism.

### Likelihood Explanation
High. This isn't a rare MEV/sandwich edge case; it happens on essentially every call where `msg.value` isn't the exact wei amount the AMM consumes at execution time, which is the normal case since callers must estimate the ETH needed for a fee-token-denominated fee ahead of time (quoted off-chain, subject to normal price drift between quoting and execution). The `deadline = block.timestamp` pattern (mirroring the reported bug) additionally means there's no expiration guard forcing fresh price checks, so stale, unfavorable estimates go through silently rather than reverting, compounding the leftover-ETH lock.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.sol`: capture `amounts[0]` returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`. Additionally, replace `block.timestamp` with a caller-supplied or bounded deadline parameter so transactions can't be held indefinitely and executed against stale price expectations.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` requires, say, only 0.8 ETH worth of `feeToken` at current pool price.
2. `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` executes; the router consumes ~0.8 ETH and refunds ~0.2 ETH to `address(this)` (i.e., `EvmHost`).
3. `dispatch` proceeds to commit the request and emit the event without ever transferring the ~0.2 ETH refund back to the user.
4. The ~0.2 ETH remains in `EvmHost`'s balance indefinitely — no function in the dispatch/fundRequest paths (or shown withdrawal path) returns it to the depositor, constituting a direct loss of user funds. [1](#0-0)
