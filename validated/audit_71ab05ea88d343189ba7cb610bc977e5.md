### Title
Attacker-controlled `n` triggers oversized pre-allocation during `ThresholdKeys` deserialization - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` trusts the serialized `n` field (a `u16`) and uses it to size a `Vec::with_capacity` for `Interpolation::Constant` coefficients before validating that the stream actually contains that many elements. An unprivileged party supplying crafted bytes to `ThresholdKeys::read` can force allocations of up to ~2–4 MB of field elements from a ~15-byte input, a large memory/CPU amplification usable as a denial-of-service primitive against any service that deserializes `ThresholdKeys` from untrusted input.

### Finding Description
The external report's class is: untrusted input causes a loop/allocation sized by attacker data, producing resource exhaustion for honest users. The Serai analog lives in the `ThresholdKeys` deserializer in `crypto/dkg/src/lib.rs`:

```rust
// crypto/dkg/src/lib.rs:597-613
(
  read_u16()?,          // t
  read_u16()?,          // n  <- attacker controlled, up to 65535
  Participant::new(read_u16()?)...
)
...
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));   // allocates n * sizeof(F)
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);                      // fails on EOF *after* alloc
    }
    res
  }),
  1 => Interpolation::Lagrange,
  ...
};
```

After `n`, `read` also iterates `for l in 1 ..= n` calling `read_G` to build `verification_shares` [1](#0-0)  and then calls `ThresholdKeys::new`, which interpolates `group_key` from `n` verification shares [2](#0-1)  — a multiexponentiation over up to 65,535 points driven by a 2-byte field. The `Vec::with_capacity(n)` allocation happens before a single scalar is consumed, so a truncated input still pays the full allocation. The analogous pattern also appears in `SchnorrAggregate::read`, which iterates `0 .. u32::from_le_bytes(len)` reading points [3](#0-2) , though that loop is bounded by the stream's actual contents; the `ThresholdKeys` capacity reservation is not.

### Impact Explanation
Any deployment that feeds network/peer-supplied bytes into `ThresholdKeys::read` (an API explicitly exposed for deserialization of shares) lets a remote party repeatedly force multi-megabyte allocations and, when enough trailing bytes are provided, an `n`-point multiexp in `ThresholdKeys::new` — all from a few bytes of input. Sustained requests cause memory pressure and allocator churn, degrading or stalling the host process, the same "expensive work gated on unvalidated input" denial-of-service shape as the reference finding (a gas-heavy token bricking a claim loop).

### Likelihood Explanation
Exploitation only requires reaching `ThresholdKeys::read` with attacker bytes — a listed reachable input surface. No secret knowledge, collusion, or privileged position is needed. The amplification factor (~13 bytes → ~2–4 MB allocation plus up to 65k point reads) is significant, though each allocation is transient (released when `read` errors), so impact is sustained-load DoS rather than permanent lockup — consistent with Medium/High DoS severity rather than a critical one.

### Recommendation
Validate `n` against `ThresholdParams` constraints (`t <= n`, and `n` bounded by the expected multisig size) before allocating, or drop the `with_capacity` hint and let the `Vec` grow only as real data is consumed. Similarly, cap `SchnorrAggregate`'s declared `len` against the remaining input length before looping.

### Proof of Concept
```rust
// Construct a ThresholdKeys serialization prefix with interpolation = Constant (0)
// and n = 0xFFFF, then truncate. ThresholdKeys::read allocates
// Vec::with_capacity(65535) (~2-4 MB of C::F) before read_F hits EOF.
let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&1u16.to_le_bytes());      // t
buf.extend(&u16::MAX.to_le_bytes());  // n = 65535
buf.extend(&1u16.to_le_bytes());      // i
buf.push(0u8);                        // Interpolation::Constant
// no further bytes: allocation of 65535 scalars occurs, then EOF error
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
```
Repeating this request forces continuous multi-megabyte allocations per invocation; providing the full `n` scalars/points additionally forces a 65,535-term `group_key` interpolation inside `ThresholdKeys::new` [4](#0-3) .

Caveat: I verified this path statically; whether a production caller actually routes unauthenticated bytes into `ThresholdKeys::read` depends on integration code outside the indexed scope.
