### Title
Stale line-selection bitmap is silently re-applied to a freshly re-fetched diff when staging partial commits, allowing attacker-controlled repository content to corrupt what the user commits - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The report's broken invariant is: *a value computed from an "old" state (lock duration / accrual rate) is retroactively applied to state that has since changed, without re-validating or flushing first.* The GitHub Desktop analog is in the partial-commit staging path: the line-selection bitmap the user builds while reviewing one diff is later re-applied, by absolute line index, to a **second, independently-fetched diff** of the same file at commit time — with no check that the two diffs still line up.

### Finding Description
When the user reviews a file's diff in the Changes view, the app fetches a diff and lets the user toggle individual lines/hunks for inclusion. That selection is stored as a `DiffSelection` bitmap keyed by `absoluteIndex` (the line's position within that diff's hunks), computed in `updateChangesWorkingDirectoryDiff`: [1](#0-0) 

When the user actually commits, `createCommit` calls `stageFiles`, which for any file with a `Partial` selection calls `applyPatchToIndex`: [2](#0-1) 

`applyPatchToIndex` does **not** reuse the diff the user reviewed — it fetches a brand-new diff of the working file immediately before building the patch: [3](#0-2) 

That freshly-fetched diff is then handed to `formatPatch`, which reapplies the *old* `file.selection` object by raw absolute line index against the *new* diff's hunks, with no verification that the hunk structure/line meanings are still the same: [4](#0-3) 

The only place that re-validates a stale selection against a changed diff is `updateChangesWorkingDirectoryDiff`, which recomputes `selectableLines` and drops selections that no longer exist — but this only runs opportunistically when a file-watcher status refresh happens to fire and complete before the user clicks "Commit": [5](#0-4) 

There is no synchronous re-diff/re-validation step between "user finishes selecting lines" and "`createCommit` stages the patch." If the tracked file's content changes between those two points — e.g. because the repository contains a `.gitattributes` clean/smudge filter, a `post-checkout`/background process, or any other repo-controlled mechanism that rewrites working-tree content — `applyPatchToIndex` will silently build a patch whose selected "lines" (by index) may now correspond to *different, attacker-supplied content* than what the user actually reviewed and approved in the UI.

### Impact Explanation
This is a "silent corruption of what the user commits" bug class, directly enumerated as valid impact. A hostile repository can cause the app to stage/commit lines the user never saw (attacker-injected code, secrets, or malicious content) or to drop lines the user intended to include, because the bitmap-by-index selection is blindly reapplied to a diff recomputed at a different point in time than the one the user reviewed. The user believes they reviewed and approved exactly what gets committed and pushed, but the actual staged patch can diverge from the reviewed diff.

### Likelihood Explanation
Requires the attacker (via a cloned/fetched malicious repository) to have some mechanism that mutates a tracked file's working-tree bytes between diff-review time and commit time (e.g., `.gitattributes` filters, hooks, or a repo-embedded background tool the project instructs the victim to run) — no local/admin access or leaked credentials are needed, only a repository the user opens and reviews/commits within Desktop, which matches the allowed attacker model ("attacker controls a cloned/fetched repository"). The race window is real because Desktop's staleness-recovery (`updateChangesWorkingDirectoryDiff`) is not gated by anything before the commit call executes.

### Recommendation
Before staging a partially-selected file for commit, `applyPatchToIndex`/`stageFiles` (or the caller in `createCommit`) should re-fetch the diff and re-validate the file's `DiffSelection` against it (comparable to the reconciliation logic already used in `updateChangesWorkingDirectoryDiff`), rejecting or re-prompting the user if the diff has materially changed since it was last reviewed, rather than blindly reapplying the old selection bitmap to a newly computed diff.

### Proof of Concept
1. Clone a malicious repository containing a `.gitattributes` `clean`/`smudge` filter (or similarly repo-triggerable mechanism) that rewrites a tracked file's working-tree content shortly after checkout/on a timer.
2. In GitHub Desktop, open the file's diff and select a subset of lines for a partial commit.
3. Before the file-watcher-driven `updateChangesWorkingDirectoryDiff` refresh completes/reflects the change, click "Commit" — triggering `createCommit` → `stageFiles` → `applyPatchToIndex`.
4. `applyPatchToIndex` re-fetches the diff (now reflecting the filter-mutated content) and `formatPatch` reapplies the user's old line-index selection to it, producing a patch whose actual staged content differs from what the user reviewed and approved, silently committing/pushing unintended content.
