### Title
Data Layer SSRF via unrestricted mirror URL fetch in `http_download()` - (File: `chia/data_layer/download_data.py`)

### Summary
Any user who owns or subscribes to a DataLayer store can publish an arbitrary mirror URL on-chain via the `add_mirror` DataLayer RPC/CLI command. That URL is later fetched directly by any peer's `DataLayer` service via `session.get()` in `http_download()` with no scheme allow-listing, no host/IP blacklisting, and no redirect restriction — the same root cause reported for Uppy (`downloadURL()` calling the raw URL with no sanitization).

### Finding Description
- Mirror URLs are recorded on-chain as `ServerInfo` entries and consumed by `DataLayer.fetch_and_validate()`, which iterates `servers_info` and calls `insert_from_delta_file()` with `server_info=server_info`. [1](#0-0) 
- `insert_from_delta_file()` calls `download_file()`, which — when no plugin `downloader` is configured — calls `http_download()` directly with `server_info.url`. [2](#0-1) 
- `http_download()` builds the request target by simple string concatenation of the attacker-controlled `server_info.url` and performs an `aiohttp` `session.get()` request with no scheme validation (e.g. no enforcement of `http`/`https` only), no check against private/link-local/metadata IP ranges, and no disabling of redirects — mirroring the exact SSRF pattern from the Uppy report (`downloadURL` calling the URL directly without sanitization or a whitelist/blacklist). [3](#0-2) 
- The module-level documentation for DataLayer explicitly notes that mirror URLs are an external trust input and that this area is a known fragility hotspot, but the enforcement described there (path/name validation) does not cover URL host/scheme validation for outbound fetches. [4](#0-3) 
- Any wallet user with DataLayer support enabled can trigger this by publishing a mirror coin with a crafted URL (e.g. `http://169.254.169.254/...` or `http://localhost:<internal-port>/...`) for a store they own, or by tricking another node into subscribing to a store whose mirror list they control (`add_mirror` CLI command shown reaching `add_mirror_cmd`). [5](#0-4) 

Once any other DataLayer node subscribes to that store and runs its periodic sync loop (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`), it will unconditionally issue outbound HTTP requests to the attacker-chosen URL, exactly analogous to the Uppy `/get` endpoint blindly fetching `req.body.url`.

### Impact Explanation
This is a genuine SSRF primitive reachable by an ordinary Data Layer/wallet user: publish a mirror URL pointing at internal-only services (cloud metadata endpoints, internal admin APIs, other local RPC ports on the same host/network) and wait for any subscribing node to fetch it. Impact matches the referenced report's class: internal network reconnaissance, interaction with internal services reachable only from the node's host/network, and potential disclosure of instance metadata or credentials if the node runs in a cloud environment. It does not by itself grant coin/supply/consensus impact, but it is a legitimate Medium/High-severity SSRF analog reachable purely through an unprivileged Data Layer client action (publishing a mirror), consistent with the scan's allowed categories ("Data Layer client... Data Layer roots and proofs").

### Likelihood Explanation
Likelihood is high for any node that subscribes to third-party DataLayer stores (a normal, intended DataLayer workflow) since `fetch_and_validate()` runs automatically in the periodic background sync loop without any operator interaction, and the mirror URL is fully attacker-controlled data published on-chain.

### Recommendation
- Enforce a strict allow-list of URL schemes (`http`/`https` only) before use in `http_download()`.
- Resolve and validate the target host against a deny-list of private/loopback/link-local/metadata IP ranges (e.g. `127.0.0.0/8`, `169.254.0.0/16`, `10.0.0.0/8`, etc.) prior to connecting, and re-validate after DNS resolution to prevent DNS rebinding.
- Disable or tightly restrict following redirects when downloading mirror data, or re-validate the redirect target against the same allow/deny lists.
- Apply the same validation to the `PluginRemote`/S3 plugin download paths and to `get_downloader()`'s POST calls, which also use raw mirror-provided URLs.

### Proof of Concept
1. As any wallet/DataLayer user, create or own a DataLayer store and run `chia data add_mirror --id <store_id> --url http://169.254.169.254/latest/meta-data/` (per `chia/cmds/data.py`'s `add_mirror` command) to publish the malicious mirror URL on-chain.
2. Wait for (or induce) another DataLayer node to subscribe to the same store id.
3. On its next `periodically_manage_data()` cycle, that node's `fetch_and_validate()` will pick the malicious `ServerInfo.url` and call `http_download()`, causing the victim node to issue an outbound HTTP GET to the internal/metadata address supplied by the attacker, exactly as described in the original Uppy SSRF report.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```

```markdown
- `fetch_and_validate()` uses wallet singleton history as the target generation/root sequence, randomizes eligible server URLs, tries plugin-specific or plain HTTP delta downloads, and marks mirror/server failures with backoff in the subscriptions table.
- Unsubscribe is queued and processed only after fetch jobs complete while holding `subscription_lock`, avoiding races between deletion of local subscription/data and active download/update work.
- Owned stores are treated as local publication sources even when they have no external mirror URLs. Subscribed stores are treated as replication targets whose chain roots are verified through wallet state.

## Proofs, Offers, And Singleton Coupling

- Inclusion proofs are rooted in DataLayer Merkle roots, but proof verification also binds those roots to the DataLayer singleton puzzle hash. `dl_verify_proof_internal()` reconstructs the host full puzzle from `inner_puzzle_hash`, proof root, and store id, then verifies `ProofOfInclusion.valid()`.
- `verify_proof()` checks wallet coin state for the proof coin id and reports `current_root` by testing whether that singleton coin is unspent. Historical proofs can verify successfully while not being current.
- Offer construction mutates/uses local stores to produce the maker/taker inclusion sets and solver dependencies. `process_offered_stores()` may stage local inserts before generating proofs, so offer creation is a local data mutation path, not a pure read.
- `make_offer()` verifies the constructed `TradingOffer` summary against local `StoreProofs` before returning. `take_offer()` verifies maker proofs, builds `proofs_of_inclusion` solver data, and then calls wallet RPC outside the data-store transaction because wallet failures may happen after chain submission.
- Non-secure offer cancellation asks wallet RPC for the offer, derives affected store ids from the DataLayer offer summary, then clears pending roots for those stores after cancellation.

## RPC And Compatibility Notes

- RPC request fields mix legacy names (`id`, `root_hash`, `changelist`) with streamable request/response classes for newer offer/proof paths. Preserve wire shapes unless deliberately changing public RPC behavior.
- `root_hash` omission means "latest local committed root" via `Unspecified`; explicit empty-root sentinels can mean the empty tree. `None`, omitted, and `bytes32.zeros` are not interchangeable across RPC, service, and wallet layers.
- Pagination is byte-size based over key/value blob lengths, not item-count based. Oversized single items raise rather than splitting.
- `DataLayerRpcClient` is a thin convenience wrapper and does not cover every server-side nuance; do not infer server behavior solely from client helper argument types.
- Static file serving validates filenames but uses direct synchronous file reads in the request handler. It assumes files are already written under `server_files_location` by the service or plugin.

## Fragility Hotspots

- High-risk edits move work across DB writer transactions, `_update_confirmation_status()`, pending-root status changes, or wallet RPC calls. These boundaries encode publication and rollback assumptions.
- File-system writes for Merkle blobs, key/value blobs, and `.dat` files have TODOs around locking. Concurrent service/plugin/server access should be treated as a real consistency concern.
- Empty-root normalization is subtle and historically uneven. Audit any change touching `bytes32.zeros`, `None`, `Root.node_hash`, or proof roots with both empty and non-empty stores.
- Plugin and mirror URLs are external trust inputs. Downloaded data must continue to be verified against wallet-advertised roots, and file path/name validation must stay strict.
```
