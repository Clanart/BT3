## Analysis

The Aura Finance bug's core invariant: **a global rate/allocation parameter used to size a pending payout must be pinned before it changes, or a stale/mid-flight computation gets priced against the wrong rate.** `add()`/`set()` mutate `totalAllocPoint` (a rate denominator) without first calling `massUpdatePools()` to settle rewards accrued under the old rate — a legitimate admin action creates an inconsistent payout for anyone whose reward computation straddles the change.

The closest local analog is `pallet-bandwidth`'s tier-based bandwidth crediting. A buyer pays for bandwidth on an EVM chain at a price keyed to a `TierIndex` (`tierPrice[tier]` on `BandwidthManager.sol`), but the actual **byte/duration allocation** for that tier is a *separate* value stored on Hyperbridge (`Tiers::<T>`) and is only read at delivery time — not pinned at purchase time. [1](#0-0) 

`set_tier` (a normal, non-malicious governance action) can change `TierConfig{bytes, duration_secs}` for any `TierIndex` at any time — there is no notion of versioning or "settling" purchases already in flight under the old config. [2](#0-1) 

`on_accept` (the handler invoked when a relayer — which can be the buyer themself, since ISMP relaying is permissionless — delivers the purchase message) reads `Tiers::<T>::get(tier)` **at delivery time**, not at purchase time, and computes `bytes = cfg.bytes * months` / `duration = cfg.duration_secs * months` from whatever config is live at that moment.

### Title
Bandwidth purchase credits use the tier config live at delivery time instead of the config the buyer paid against - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth::on_accept` decodes a purchase message that carries only `{app, tier, months, chain}` — no reference to the tier's byte/duration terms at purchase time — and resolves the actual `bytes`/`duration_secs` from the pallet's *current* `Tiers` storage. Because delivery of a Hyperbridge-originated request is permissionless (any relayer, including the buyer's own tooling, decides when to submit the proof), a buyer can defer delivery of an already-paid-for purchase until after a `set_tier` update lands, receiving a different (potentially much larger) byte/duration allocation than what was priced and paid for on the source chain.

### Finding Description
The purchase flow splits pricing and allocation across two independently-updatable state variables:
- **Price** lives on the EVM `BandwidthManager` contract (`tierPrice[tier]`), fixed at the moment `purchase()` executes and the fee token is pulled.
- **Allocation** (`TierConfig{bytes, duration_secs}`) lives on Hyperbridge in `Tiers::<T>`, set independently via `set_tier` [3](#0-2) , and is completely decoupled from the price side (the docs confirm this: "This step is per-tier, not per-chain — the byte/duration side is global on Hyperbridge").

The purchase message dispatched from EVM only encodes `{app, tier, months, chain}` — the tier byte/duration terms are never captured in the message itself. When the message is later delivered to Hyperbridge, `on_accept` resolves `cfg = Tiers::<T>::get(tier)` fresh, at delivery time, and mints a subscription sized to *that* config [4](#0-3) :
```rust
let cfg = Tiers::<T>::get(tier).ok_or_else(...)?;
let bytes = cfg.bytes.saturating_mul(msg.months as u128);
let duration = cfg.duration_secs.saturating_mul(msg.months as u64);
```

Delivery is not bound to any admin action, block height, or version of `Tiers` — it is purely a function of when a relayer (including the buyer) submits the proof of the source-chain `BandwidthPurchased` event. There is no mechanism analogous to `massUpdatePools()` that settles/finalizes in-flight purchases against the pre-change tier terms before `set_tier` takes effect, and no snapshot of the tier config is taken at dispatch time to travel with the message.

This is structurally identical to the reported bug class: a global rate/allocation variable (`Tiers`) is mutated without first draining/settling computations that are "pending" against the old value (in-flight purchase messages), so the eventual computation silently uses whichever value happens to be live when it executes.

### Impact Explanation
If governance increases a tier's `bytes`/`duration_secs` (e.g., scaling up a package, a routine and legitimate operation), any buyer who purchased under the old, smaller config but has not yet had their purchase delivered can delay delivery until after the update and receive the larger allocation for the price they already paid at the old rate. This is an unauthorized "wrong amount" credit on Hyperbridge's bandwidth ledger — bandwidth is a rate-limiting/billing primitive gating ISMP message dispatch, so over-crediting effectively grants free message-dispatch capacity beyond what was purchased, at the expense of the protocol's bandwidth-sale economics. The reverse (governance decreasing a tier) silently under-delivers to buyers who cannot control relayer timing, causing loss of paid-for value.

### Likelihood Explanation
Delivery timing is entirely attacker (buyer)-controlled: ISMP request delivery to Hyperbridge is permissionless, and a buyer can submit their own purchase proof (or instruct a cooperating relayer) whenever they choose, holding a paid purchase message unsubmitted indefinitely. `set_tier` changes are visible on-chain before finalization (mempool/pending extrinsic), giving an attentive buyer a window to time delivery around a known upcoming increase. No special privileges, malicious relayer, or compromised keys are required — only an unprivileged buyer exploiting the gap between price-fixing (EVM, at purchase) and allocation-fixing (Hyperbridge, at delivery).

### Recommendation
Snapshot the tier's `TierConfig` (bytes, duration_secs) into the purchase message payload at dispatch time on the EVM side (or have the Hyperbridge dispatcher pin the config version consumed at accumulation), and validate at `on_accept` that the snapshot matches (or falls within a governance-tolerated range of) the config in effect at the time the buyer's price was captured, rejecting or reconciling mismatches rather than silently applying whatever `Tiers::<T>::get(tier)` returns at delivery time.

### Proof of Concept
1. Governance configures `TierIndex::TierOne` with `TierConfig{bytes: 1_000_000, duration_secs: 30d}` and pushes price `50e18` via `dispatch_set_tiers`.
2. Buyer calls `BandwidthManager.purchase()` on EVM for `TierOne × 1 month`, paying `50e18`, which dispatches a `BandwidthPurchaseMsg{app, tier: TierOne, months: 1, chain}` ISMP POST with `fee: 0`, `timeout: 0`.
3. Buyer holds the resulting commitment undelivered (does not submit the proof to Hyperbridge).
4. Governance later (legitimately) bumps `TierOne` via `set_tier` to `TierConfig{bytes: 10_000_000, duration_secs: 30d}` (a 10x package increase, e.g. a promotional resize) — see `modules/pallets/bandwidth/src/lib.rs:274-291`.
5. Buyer now submits the previously-withheld proof of their step-2 purchase to Hyperbridge. `on_accept` reads the *current* `Tiers::<T>::get(TierOne)` (the 10M-byte config) and credits `10_000_000` bytes — `modules/pallets/bandwidth/src/lib.rs:467-477` — for the price originally paid against the 1M-byte config.
6. `BandwidthCredited` is emitted with the inflated `bytes`, and `Pallet::remaining` reflects the over-credit, confirmed against the original `50e18` payment recorded on the EVM side.

		) -> DispatchResult {
			<T as pallet_ismp::Config>::AdminOrigin::ensure_origin(origin)?;
			match config {
				None => Tiers::<T>::remove(tier),
				Some(cfg) => {
					ensure!(cfg.bytes > 0 && cfg.duration_secs > 0, Error::<T>::InvalidTierConfig);

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
