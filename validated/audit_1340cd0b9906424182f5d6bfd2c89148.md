### Title
`RecoverPolynomialCoefficients` truncates recovered coefficients without verifying high-order terms are zero, breaking the `recovered[cellIDs[i]] == cells[i]` invariant - (File: `internal/erasure_code/erasure_code.go`)

### Summary
`DataRecovery.RecoverPolynomialCoefficients`, reachable from the unprivileged `Context.RecoverCellsAndComputeKZGProofs` / `Context.RecoverCells` entrypoints via `recoverPolynomialCoeffs`, computes the exact erasure-decoding quotient polynomial and then blindly slices it to the first `numScalarsInDataWord` (4096) coefficients without checking that the discarded upper half is all-zero. When an attacker supplies more "known" cells than the strict minimum required for reconstruction (i.e., fewer missing blocks than the maximum the algorithm is designed for) and those cells are not genuine evaluations of a degree<4096 polynomial, the true quotient polynomial has non-zero coefficients above index 4096 that get silently dropped, causing the recomputed cells/proofs to correspond to a different polynomial than the one the caller supplied.

### Finding Description
The broken equality is: for every supplied `cellIDs[i]`, the recomputed cell `recoveredCells[cellIDs[i]]` (from `ctx.computeCellsFromPolyCoeff(polyCoeff, ...)` in `api_eip7594.go`) must equal the attacker-supplied `cells[i]`.

Code path: `Context.RecoverCellsAndComputeKZGProofs` → `ctx.recoverPolynomialCoeffs(cellIDs, cells)` [1](#0-0)  → `ctx.dataRecovery.RecoverPolynomialCoefficients(extendedBlob, missingCellIds)` [2](#0-1) .

Inside `RecoverPolynomialCoefficients`, the algorithm builds the vanishing polynomial `Z(x)` over the *missing* block-erasure indices, computes `D(x)*Z(x)` in evaluation form via the full extended domain (size `numScalarsInCodeword` = 8192), inverse-FFTs it to coefficient form, then divides by `Z(x)` via a coset FFT to obtain the exact quotient polynomial, and finally truncates: [3](#0-2) 

The only length precondition enforced before this call is a *lower* bound, `len(cellIDs) >= ctx.dataRecovery.NumBlocksNeededToReconstruct()` [4](#0-3) , which caps the number of *missing* blocks at at most half of `CellsPerExtBlob`. It does not cap the maximum number of supplied cells — an attacker may supply more cells than the minimum (up to all `CellsPerExtBlob`), shrinking `deg(Z)` below `numScalarsInDataWord`. The true quotient polynomial `P(x) = (D*Z)(x)/Z(x)` then has degree bound `deg(Q) - deg(Z)` where `deg(Q)` can be as large as `numScalarsInCodeword - 1` (8191); since `deg(Z)` is now small, `deg(P)` can exceed `numScalarsInDataWord - 1` (4095). Because the attacker's "cells" are arbitrary bytes and need not be evaluations of a genuine degree<4096 polynomial, this high-order content is real, not an artifact — yet line 146 discards it without ever asserting `cosetQuotientEval[numScalarsInDataWord:]` is all-zero.

The consequence is that the returned `polyCoeff` (degree < 4096, thus a legitimate, verifiable polynomial with a self-consistent commitment/opening) does not match the polynomial implied by the attacker's original `cells` input. Re-evaluating it via `computeCellsFromPolyCoeff`/`computeKZGProofsFromPolyCoeff` produces cells/proofs for a *different* polynomial than the one whose evaluations were supplied, so `recoveredCells[cellIDs[i]] != cells[i]` for the originally-provided indices — violating the required round-trip invariant. No existing guard (`ErrNumCellIDsNotEqualNumCells`, `isAscending`, `ErrFoundInvalidCellID`, `ErrNotEnoughCellsForReconstruction`) checks for this condition, since they only bound cell count and ordering, not the polynomial-degree consistency of the actual field-element content.

### Impact Explanation
The pairing/verification machinery is not fooled about a false opening in isolation (the emitted proofs are consistent with the truncated, degree<4096 polynomial actually computed), but the library silently substitutes a different polynomial/commitment than what the supplied cell data represents. This is a High-severity client-split scenario: for the same caller-supplied `(cellIDs, cells)` input, go-eth-kzg can emit `recoveredCells`/proofs that fail to reproduce the very cells given as input at the supplied indices, which is exactly the invariant the consensus protocol relies on when cells are recovered from a subset and then compared/gossiped against originally seen cells. This produces "recovered cell/proof output diverges from the supplied ground-truth data for the same input," matching the "High" impact category described (mismatched recovered data / potential disagreement vs. spec expectations for the same input).

### Likelihood Explanation
- Precondition: attacker must supply a `cells`/`cellIDs` batch where the number of "known" cells exceeds the strict minimum (`NumBlocksNeededToReconstruct`) needed for reconstruction, and the field-element content of those cells is not derived from a genuine degree<4096 polynomial (e.g., synthesized/garbage cell bytes, which are trivially producible since cell bytes only need to pass `deserializeCell`'s canonical field-element checks).
- No special privileges are needed: `RecoverCellsAndComputeKZGProofs` is a public method any caller can invoke with arbitrary well-formed cell bytes.
- Fully repeatable and deterministic for any qualifying input; cost is a single call.

### Recommendation
After computing `cosetQuotientEval` in `RecoverPolynomialCoefficients`, verify that all coefficients from index `numScalarsInDataWord` to `numScalarsInCodeword-1` are zero before truncating (mirroring the "the recovered polynomial has degree < ScalarsPerBlob, else an error" invariant), and return an error such as `ErrPolynomialNotLowDegree` if that check fails, matching the equivalent check that the consensus-spec/c-kzg reference implementation performs.

### Proof of Concept
```go
package erasure_code_test

import (
    "testing"

    "github.com/consensys/gnark-crypto/ecc/bls12-381/fr"
    "github.com/crate-crypto/go-eth-kzg/internal/erasure_code"
    "github.com/stretchr/testify/require"
)

func TestRecoverPolynomialCoefficients_NoDegreeCheck(t *testing.T) {
    // Parameters matching the 4096/8192 blob/extended-blob setup used by Context.
    dr := erasure_code.NewDataRecovery(/* blockErasureSize */ 64, /* numScalarsInDataWord */ 4096, /* expansionFactor */ 2)

    // Supply ALL 128 cells (no missing blocks) -> missingIndices is empty, deg(Z)=0.
    data := make([]fr.Element, 8192)
    for i := range data {
        data[i].SetUint64(uint64(i + 1)) // arbitrary, NOT evaluations of a degree<4096 polynomial
    }

    polyCoeff, err := dr.RecoverPolynomialCoefficients(data, nil /* no missing indices */)
    require.NoError(t, err) // BUG: should fail because true quotient has nonzero terms >= index 4096

    // Re-encode polyCoeff and confirm it does NOT reproduce the original `data` at known evaluation points,
    // i.e. recovered[cellIDs[i]] != cells[i] for the originally supplied cell data.
    reencoded := dr.Encode(append([]fr.Element{}, polyCoeff...))
    mismatch := false
    for i := range data {
        if !reencoded[i%len(reencoded)].Equal(&data[i]) {
            mismatch = true
            break
        }
    }
    require.True(t, mismatch, "expected divergence between recovered polynomial's evaluations and supplied cell data")
}
```
This demonstrates that `RecoverPolynomialCoefficients` accepts the input and silently truncates without asserting the high-order coefficients (indices 4096..8191) are zero, so the round-trip invariant `recovered[cellIDs[i]] == cells[i]` fails for attacker-chosen non-codeword data.
