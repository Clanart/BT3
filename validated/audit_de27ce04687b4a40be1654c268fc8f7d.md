### Title
IntentGatewayV2 (Tron) `instance()` fallback to `address(this)` lets unauthorized RedeemEscrow/RefundEscrow messages drain escrowed order funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2` resolves the trusted cross-chain gateway peer with a function that silently substitutes `address(this)` when no instance has been registered for a source chain, instead of reverting. This is the exact bug class from the external report: a lookup for a "should-be-set" address returns a safe-looking default (there `address(0x0)`, here `address(this)`) rather than failing, and that default is then trusted in a security check that gates fund movement. This is the same bug the canonical EVM implementation (`IntentsBase._instance`) already fixed by reverting — the Tron copy was never updated.

### Finding Description
`instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` returns the gateway's own address whenever no peer has been registered for a state machine: [1](#0-0) 

This value feeds directly into the authentication gate for incoming cross-chain messages: [2](#0-1) 

`authenticate()` is the only check performed before `onAccept` executes `RedeemEscrow`/`RefundEscrow`, both of which call `withdraw()` and transfer escrowed tokens to an attacker-controlled `beneficiary`: [3](#0-2) [4](#0-3) 

Contrast with the canonical (fixed) EVM implementation, which reverts with `UnknownInstance` instead of returning a default address: [5](#0-4) 

Because `_instances[keccak256(stateMachineId)]` defaults to `address(0)` for any state machine the Tron gateway has not been told about (via the governance-only `NewDeployment` message), `instance()` for those chains returns the gateway's own address (`address(this)`) instead of reverting. `authenticate()` then accepts any incoming message whose `from` field (the calling contract's address on the source chain, set by the real Hyperbridge host) equals that fixed value. `IntentsBase.sol` explicitly documents that this contract family relies on **identical CREATE2 deployment addresses across chains** to keep behavior/bytecode consistent: [6](#0-5) 

That design intent means the Tron gateway's own address is a fixed, publicly known constant that is also the address the deployment pattern targets on every other chain. An attacker who deploys any contract (with the real, public `IntentGatewayV2` bytecode or CREATE2 salt used by the deployer) to that exact address on a state machine Hyperbridge supports but for which the Tron team has **not yet dispatched `NewDeployment`** for that chain, can then call the real, production Hyperbridge host's `dispatch()` from that contract. The resulting `PostRequest.from` will legitimately equal the Tron gateway's address, `request.source` will be the unregistered chain, and `instance(source)` on Tron resolves (by the buggy fallback) to that same address — passing `authenticate()` with no relayer, prover, or admin compromise required.

### Impact Explanation
Once `authenticate()` is bypassed, the attacker crafts an arbitrary `WithdrawalRequest` body naming any existing order `commitment` with nonzero escrow in `_orders` and sets `beneficiary` to their own address. `onAccept` → `withdraw()` releases the full escrowed token/native balances (and any accrued relayer/tx fees) for that commitment to the attacker, with no check that this redemption corresponds to a genuine fill or refund event on the real destination/source chain. This is direct theft of user-escrowed intent funds — the exact "stealing/loss of funds" and "false proof/state acceptance via wrong module binding" impact categories called out in the bounty scope, achieved purely through a public entrypoint on a chain that has not yet been registered as a peer, with no reliance on a malicious relayer, prover, or admin key.

### Likelihood Explanation
The trigger condition — a Hyperbridge-supported state machine for which the Tron `IntentGatewayV2` has not yet received a `NewDeployment` registration — is a normal, expected operational state during any rollout phase (new chains are added incrementally via governance messages), not a rare misconfiguration. Deploying a contract at a specific CREATE2 address on an arbitrary EVM-compatible chain using public deployer/salt/bytecode is a standard, unprivileged operation. The only requirement is genuine (not forged) message delivery via the real Hyperbridge consensus/proof pipeline from that source chain, which any user can trigger by calling the source chain's public `IDispatcher.dispatch`. No relayer collusion, prover compromise, or governance action is needed.

### Recommendation
Make `instance()` revert (as `IntentsBase._instance` already does) when no peer is registered for the given state machine, instead of returning `address(this)`:
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```
Apply the same fix to every call site depending on the current fallback semantics (`cancelOrder`'s cross-chain branches), and audit for any other duplicated/forked contract copies (Tron, or other chain-specific ports) that may have drifted from the canonical, already-patched EVM implementation.

### Proof of Concept
1. Identify a Hyperbridge-supported state machine `C` for which the Tron `IntentGatewayV2._instances[keccak256(C)]` is still `address(0)` (not yet configured via `NewDeployment`).
2. Using the public deployer/salt/init-code used to deploy `IntentGatewayV2` on Tron (or any contract landing at that same CREATE2 address), deploy a minimal contract at the identical address on chain `C`.
3. From that contract, call the real Hyperbridge host's `dispatch(DispatchPost)` on chain `C` with:
   - `dest` = Tron's state machine id,
   - `to` = Tron `IntentGatewayV2` address,
   - `body` = `bytes1(RequestKind.RedeemEscrow) || abi.encode(WithdrawalRequest{commitment: <existing order commitment>, tokens: <its escrowed tokens>, beneficiary: <attacker address>})`.
4. The message is honestly relayed/proven by Hyperbridge (no forged proof needed) and delivered to Tron's `onAccept`.
5. `authenticate()` computes `instance(C)` → `_instances[keccak256(C)] == address(0)` → returns `address(this)` (Tron gateway address) which equals `module` (the attacker's contract address on `C`, by CREATE2 construction) → check passes.
6. `withdraw()` releases the escrowed tokens for the targeted commitment to the attacker's `beneficiary`.
