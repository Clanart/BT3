### Title
Spoofed `WWW-Authenticate` realm header from an untrusted git remote causes Desktop to launch a trusted "Sign in to GitHub Enterprise" flow against an attacker-controlled host - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
Desktop's git credential trampoline classifies a remote host as `enterprise` (i.e. a first‑party GitHub Enterprise Server) based on a `WWW-Authenticate` header value that is fully controlled by whatever server the credential request targets. This classification, driven entirely by attacker-suppliable data, is used to decide whether to invoke the GitHub Enterprise sign-in UI flow (`promptForGitHubSignIn` → `dispatcher.beginEnterpriseSignIn` → `setSignInEndpoint`) against the untrusted host, presenting the user with the app's native "Sign in to GitHub" chrome for a server that has no actual affiliation with GitHub.

### Finding Description
When Git needs credentials for any remote (origin, an LFS endpoint, or a submodule URL — none of which need be hosted on GitHub), it invokes Desktop's credential helper trampoline with the target URL and any `wwwauth[...]` headers the server returned. `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` uses these headers as a trust oracle: [1](#0-0) 

If the untrusted server includes `realm="GitHub"`, the code returns `'enterprise'` regardless of hostname, TLS chain, or any other property of the connection — exactly like the reported oracle bug where a foreign asset's value is accepted as equal to a reference asset's value with no real linkage between the two. There is no verification step tying the header's claim to any actual identity (no meta endpoint probe, no certificate check, nothing) once the header matches; the more careful `isGitHubHost` network probe is only used later, as a fallback when this header shortcut doesn't apply.

That endpoint kind then flows into `getCredential`: [2](#0-1) 

Since no account exists for a brand-new attacker-controlled host, `apiEndpoint` won't match any stored account, so `ui.promptForGitHubSignIn(endpoint)` fires (as long as this is not a background task). That helper drives the dispatcher's real enterprise sign-in flow directly against the attacker's `origin`: [3](#0-2) 

The user is shown Desktop's built-in `PopupType.SignIn` dialog, which normally only appears for genuine GitHub.com/GHES hosts, but here is triggered purely because the remote server echoed `WWW-Authenticate: ...realm="GitHub"`. Any server an attacker can get Desktop to contact via git operations (a malicious `origin`, a submodule URL, an LFS pointer target, or a proxied response) can trigger this.

### Impact Explanation
This misclassification corrupts the trust decision "is this host GitHub" — the same class of corrupted value as the report's mispriced WBTC — and channels it into user-facing authentication UI. It doesn't silently exfiltrate an existing stored token (the existing-account matching still requires a hostname match via `isDotCom`/`isGHE`/`findGitHubTrampolineAccount`, which the attacker cannot spoof for `github.com` itself), but it does allow an attacker-controlled server to impersonate a legitimate GitHub Enterprise sign-in prompt inside Desktop's own trusted chrome, at a time and host of the attacker's choosing, increasing the chance a user completes an authentication/PAT flow that hands credentials to the attacker's endpoint. This matches the valid-impact category "unauthorized OAuth or account binding" / "credential exfiltration" resulting from "a git remote/proxy response."

### Likelihood Explanation
Any repository the victim clones or adds a remote/submodule for can point to an attacker-controlled HTTPS server; simply returning `401` with `WWW-Authenticate: Basic realm="GitHub"` on the git-http-backend info/refs request is sufficient to reach this code path the next time Git needs credentials for that URL (fetch, push, submodule update, or LFS). No special privileges, MITM, or DNS control of `github.com` are required — only that the victim interacts with a repository/remote the attacker set up, which is squarely in-scope ("attacker controls...a git remote/proxy response").

### Recommendation
Do not trust the `WWW-Authenticate` realm string as sufficient proof of GitHub identity. Either drop the header-based shortcut entirely and always fall back to the network-verified `isGitHubHost` check (which validates the `x-github-request-id` response header over a real connection), or additionally require corroborating evidence (e.g., a successful `isGitHubHost` probe) before classifying a previously-unseen host as `'enterprise'` and before invoking `promptForGitHubSignIn`, so an attacker-controlled server cannot unilaterally trigger the trusted enterprise sign-in flow just by echoing a header value.

### Proof of Concept
1. Stand up an HTTPS server at `https://evil.example.com/repo.git` that behaves as a normal git-http-backend but adds `WWW-Authenticate: Basic realm="GitHub"` to any `401` response for `/info/refs` or `/git-upload-pack`.
2. Victim adds this URL as a remote (or it's referenced by a submodule, or set as an LFS endpoint) and performs an interactive fetch/push/pull in Desktop.
3. Git invokes the credential helper trampoline with the `wwwauth[...]=Basic realm="GitHub"` field; `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:153-166`) returns `'enterprise'` without any network verification of the host.
4. `getCredential` finds no matching stored account for `evil.example.com` and calls `ui.promptForGitHubSignIn('https://evil.example.com/...')` (`app/src/lib/trampoline/trampoline-credential-helper.ts:118`).
5. `promptForGitHubSignIn` (`app/src/lib/trampoline/trampoline-ui-helper.ts:80-99`) invokes `dispatcher.beginEnterpriseSignIn` and `setSignInEndpoint(origin)` with the attacker's origin, then shows Desktop's native `PopupType.SignIn` dialog — presenting the attacker's host as if it were a legitimate GitHub Enterprise instance to be signed into.

Note: I was not able to trace the full downstream OAuth/token-exchange path (`sign-in-store.ts`'s `resolveOAuthRequest`/`requestOAuthToken`) against this attacker-controlled `endpoint` in this session to confirm whether a full OAuth code exchange would also be redirected to the attacker's server versus failing safely; this would need to be verified in a live/dynamic environment (e.g., a Devin session) to fully substantiate the credential-exfiltration severity versus a UI-spoofing-only outcome.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
