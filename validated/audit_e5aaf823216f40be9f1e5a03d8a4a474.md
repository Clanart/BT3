### Title
Data Layer Mirror-URL Server-Side Request Forgery via On-Chain Mirror Coin Data - (File: chia/data_layer/download_data.py)

### Summary
The DataLayer sync/subscription pipeline downloads delta/full-tree files from server URLs that ultimately originate from an on-chain mirror coin published by any wallet, without validating the host/IP of the URL or restricting the destination to public/non-loopback/non-link-local addresses.

### Finding Description
`DataLayer.add_mirror()` lets any wallet owner publish a `DLNewMirror` coin containing an arbitrary list of URL strings, with the only check being that the list is not empty [1](#0-0) . Any node that subscribes to that store calls `update_subscriptions_from_wallet()`, which reads the mirror URLs straight from the wallet's on-chain-derived `dl_get_mirrors()` result and merges them, unvalidated, into the local subscription server list [2](#0-1) .

During the periodic sync loop, `fetch_and_validate()` picks one of these attacker-supplied server URLs and passes it into `insert_from_delta_file()` / `download_file()`, which in turn calls `http_download()` [3](#0-2) . `http_download()` issues an `aiohttp` GET request directly to `server_info.url + "/" + filename` with no scheme/host allow-list, no rejection of loopback/private/link-local addresses or hostnames resolving to them, and no bound on the number of redirects followed (default `allow_redirects=True`) [4](#0-3) . A search of the module confirms there is no `ipaddress`-based or similar host-safety check anywhere in `chia/data_layer/` (verified via search for `is_safe`, `private`, `loopback`, `link.local`, `ipaddress` and `allow_redirects`/`max_redirects`).

This mirrors the reported bug class exactly: a caller-supplied target ("mirror URL") is forwarded by the service to an internal `aiohttp` request with no destination-address validation and no re-validation on redirect — the same root cause as `mountMcpProxy` accepting unchecked `X-Target-URL` values.

### Impact Explanation
Any wallet user can create a DataLayer store, add a mirror with a URL pointing at loopback or private/link-local addresses (e.g., the victim's own RPC ports, other services bound to `127.0.0.1`, or cloud metadata endpoints such as `169.254.169.254`), and get that URL published on-chain. Any other node that later subscribes to (or is auto-tracking as an owner/subscriber of) that store will have its DataLayer service issue outbound HTTP requests to the attacker-chosen internal target and process the response as delta-file bytes, which is a network-reachable SSRF primitive against infrastructure that is otherwise only reachable from the victim's own host. Because subscribing to public/shared DataLayer stores is normal usage (explorers, aggregators, and general DL clients), the attack surface is broad and unauthenticated from the attacker's perspective.

### Likelihood Explanation
Likelihood is high: creating a store and a mirror coin is a cheap, standard, permissionless DataLayer wallet operation, and the vulnerable code path (`update_subscriptions_from_wallet` → `fetch_and_validate` → `http_download`) runs automatically on the periodic `manage_data_interval` loop for any subscribed store without further user interaction [5](#0-4) .

### Recommendation
Validate mirror/server URLs before use in `add_mirror()` and/or before merging chain-provided mirror URLs into the local subscription list in `update_subscriptions_from_wallet()`: reject non-HTTP(S) schemes and resolve the hostname to confirm it is not a loopback, private, link-local, or otherwise reserved address (analogous to `isSafeProxyTarget` in the referenced fix). Apply the same check in `http_download()` immediately before issuing the request, disable `allow_redirects` or re-validate the resolved address after each redirect hop, and set an explicit `max_redirects` bound.

### Proof of Concept
1. Attacker creates a DataLayer store and calls `add_mirror` with `urls=["http://127.0.0.1:<victim_rpc_port>"]` (or an internal-only address), which is accepted because only emptiness is checked (`chia/data_layer/data_layer.py:965-971`).
2. The mirror coin/URL is committed on-chain via `dl_new_mirror`.
3. A victim node subscribes to (or already owns/tracks) the store; on its next `manage_data_interval` cycle, `update_subscriptions_from_wallet()` pulls the malicious URL from `dl_get_mirrors()` and stores it as a subscription server (`chia/data_layer/data_layer.py:979-985`).
4. `fetch_and_validate()` selects that server and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, causing the victim's node to issue a real outbound HTTP GET to the attacker-chosen internal target (`chia/data_layer/download_data.py:298-323`), demonstrating SSRF from the victim's DataLayer service.

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
