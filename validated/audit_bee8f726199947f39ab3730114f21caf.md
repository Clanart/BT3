### Title
Post-mint conversion failure in ERC20 IBC middleware returns error acknowledgement after coins are already minted, causing duplicate value across chains - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
The Uniswap report describes a class of bug where an operation that assumes "this resource does not yet exist" can be front-run/blocked by an attacker, causing an irrecoverable revert. In this Cosmos EVM fork, the `x/erc20` IBC middleware's `OnRecvPacket` performs a similar "create if not exists" operation (`RegisterERC20Extension` → `CreateNewTokenPair`) *after* the underlying ICS-20 transfer has already minted vouchers to the receiver. If that post-mint step fails and an error acknowledgement is returned, the failure is not atomic with the mint that already occurred, unlike standard ICS-20 semantics where a failure ack implies no state change occurred on the receiving chain.

### Finding Description
`IBCMiddleware.OnRecvPacket` first calls the underlying ICS-20 transfer application's `OnRecvPacket`, which mints/unescrows the transferred coin into the receiver's account and returns a **success** acknowledgement only if that step succeeded: [1](#0-0) 

Only if the underlying transfer succeeded does execution proceed to `k.OnRecvPacket`, which performs additional ERC20 conversion logic in the **same, uncommitted-but-already-mutated** `ctx`: [2](#0-1) 

For a newly-seen `ibc/` denom, the middleware calls `RegisterERC20Extension`, which derives a deterministic ERC-20 address from the denom and creates a token pair, explicitly failing with `ErrTokenPairAlreadyExists` if an account with code already occupies that deterministically-derived address: [3](#0-2) [4](#0-3) 

If this registration fails (e.g., an unprivileged attacker pre-deploys a contract at the address that will later be deterministically derived for a given IBC denom, mirroring the Uniswap "pair already exists" front-run), `OnRecvPacket` returns `channeltypes.NewErrorAcknowledgement(err)`: [5](#0-4) 

The same non-atomicity applies to the `found && pair.IsNativeERC20()` branch, where `MintingEnabled` or `ConvertCoinNativeERC20` can fail for reasons outside the receiver's control (e.g., the escrowed ERC20 balance/allowance being insufficient, or the ERC20 contract reverting), again returning an error ack **after** the underlying bank mint has already been committed to state: [6](#0-5) 

Under standard ICS-20/IBC semantics, an error acknowledgement instructs the **source** chain to refund (unescrow) the sender's original funds, on the assumption that the destination chain made no corresponding state change. Here, that assumption is violated: the destination chain's bank module has already credited the receiver with the voucher coins via `im.Module.OnRecvPacket`, and this mutation is not rolled back merely by returning a different acknowledgement value later in the same transaction — no `CacheContext`/branch-and-discard mechanism is used across the `im.Module.OnRecvPacket` → `k.OnRecvPacket` boundary.

### Impact Explanation
If the source chain unescrows/refunds the sender upon receiving the error ack, while the destination chain's receiver retains the already-minted voucher balance, the same underlying value now exists on both chains simultaneously. This is a duplication of spendable user value across an IBC escrow/voucher pair, matching the "Critical unauthorized minting/duplication ... across ... IBC escrows" impact category. It can be triggered by unprivileged relayer/user activity that causes the post-mint conversion step to fail (e.g., front-running a deterministic ERC-20 address, or otherwise causing `ConvertCoinNativeERC20`/`MintingEnabled` to fail), without needing any privileged access.

### Likelihood Explanation
Likelihood depends on how easy it is to force the post-mint conversion step to fail in practice:
- For the `RegisterERC20Extension` path, this requires an attacker to predict the deterministic ERC-20 address for a not-yet-used IBC denom and deploy code there first — this mirrors exactly the Uniswap front-run scenario from the seed report, and is plausible on the *first* transfer of any new IBC denom (analogous to "new chain deployment" in the original report).
- For the native-ERC20 branch (`ConvertCoinNativeERC20`/`MintingEnabled`), failures could occur from more mundane conditions (e.g., paused/disabled ERC20 contract, insufficient module-owned ERC20 balance), which may be easier to trigger or occur incidentally rather than via deliberate attack.

I was not able to fully verify (due to tool access ending) the exact address-derivation formula in `NewTokenPairSTRv2` or confirm ibc-go v10's exact acknowledgement-driven refund behavior in this fork's vendored/patched IBC core, so the precise ease of exploitation and the exact refund mechanics on the source chain could not be independently confirmed from the indexed code alone.

### Recommendation
Make the mint (performed by the underlying transfer application) and the ERC20 conversion step atomic with respect to the acknowledgement: wrap the call to the underlying `im.Module.OnRecvPacket` together with the `k.OnRecvPacket` conversion logic in a `ctx.CacheContext()`, and only write the cached changes to the parent context if the *combined* result (transfer + conversion) succeeds; otherwise return the error acknowledgement without having mutated the receiver's balance, so that the source chain's refund and the destination chain's state remain consistent. Additionally, apply the same existence-check-before-create pattern recommended in the original report — check whether the deterministically-derived ERC-20 address already has code before treating registration failure as fatal, and consider handling collisions gracefully rather than aborting after value has already moved.

### Proof of Concept
Conceptual sequence (not independently executed against a live testnet due to ask-only/read-only access):
1. Attacker observes (or knows in advance) the deterministic ERC-20 address that `NewTokenPairSTRv2` will derive for a specific new `ibc/<hash>` denom that is about to be used for the first time on the destination Cosmos EVM chain.
2. Attacker deploys arbitrary contract bytecode to that exact address via a normal EVM transaction, ahead of the first IBC transfer of that denom.
3. A legitimate user sends an ICS-20 transfer of that denom from the source chain to the destination chain.
4. `IBCMiddleware.OnRecvPacket` → `im.Module.OnRecvPacket` mints the voucher coin into the receiver's bank balance (state now mutated, success ack).
5. `k.OnRecvPacket` proceeds to `RegisterERC20Extension` → `CreateNewTokenPair`, which finds an existing code hash at the derived address and returns `ErrTokenPairAlreadyExists`.
6. `OnRecvPacket` returns `channeltypes.NewErrorAcknowledgement(err)` to the relayer/source chain, despite the receiver's bank balance already having been credited in step 4.
7. Source chain processes the error ack and unescrows/refunds the sender's original coins.
8. Result: sender has refunded coins on the source chain, and receiver retains freshly minted vouchers on the destination chain — the same value now exists twice across the two chains.

// RegisterERC20Extension creates and adds an ERC20 precompile interface for an IBC Coin.
//
// It derives the ERC-20 address from the token denomination and registers the
// EVM extension as an active dynamic precompile.
//
// CONTRACT: This must ONLY be called if there is no existing token pair for the given denom.
func (k Keeper) RegisterERC20Extension(ctx sdk.Context, denom string) (*types.TokenPair, error) {
	pair, err := k.CreateNewTokenPair(ctx, denom)
	if err != nil {
		return nil, err
	}

	// Add to existing EVM extensions
	if err := k.EnableDynamicPrecompile(ctx, pair.GetERC20Contract()); err != nil {
		return nil, err
	}

	return &pair, err
}

// CreateNewTokenPair creates a new token pair and stores it in the state.
func (k Keeper) CreateNewTokenPair(ctx sdk.Context, denom string) (types.TokenPair, error) {
	pair, err := types.NewTokenPairSTRv2(denom)
	if err != nil {
		return types.TokenPair{}, err
	}
	account := k.evmKeeper.GetAccount(ctx, pair.GetERC20Contract())
	if account != nil && account.HasCodeHash() {
		return types.TokenPair{}, errorsmod.Wrapf(types.ErrTokenPairAlreadyExists, "token already exists for token %s", pair.Erc20Address)
	}
	err = k.SetToken(ctx, pair)
	if err != nil {
		return types.TokenPair{}, err
	}
	return pair, nil
}
