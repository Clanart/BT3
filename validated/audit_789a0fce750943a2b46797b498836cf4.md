### Title
Cached FROST preprocess is reused whenever one already exists for the signing context, skipping fresh nonce generation and enabling secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
In `SigningProtocol::preprocess_internal`, the FROST preprocess seed is only freshly generated when `CachedPreprocesses::get(self.txn, &self.context)` returns `None`. If an entry already exists for the context, the existing encrypted seed is decrypted and passed to `AlgorithmSignMachine::from_cache`, which deterministically regenerates the identical nonces via `ChaCha20Rng::from_seed`. This mirrors the ArcadeDB bug class: the "already exists" branch bypasses the check (freshness/one-use enforcement) applied on the create path. Because the cache is keyed solely on `self.context` and is never deleted after `share_internal` runs, any second signing flow that resolves to the same context silently reuses the same nonce pair (d, e).

### Finding Description
`preprocess_internal` at `coordinator/src/tributary/signing_protocol.rs:123-145` writes `CachedPreprocesses::set` only inside the `is_none()` branch, then unconditionally loads the cached seed and calls `from_cache`. `from_cache` (`crypto/frost/src/sign.rs:268-274`) routes to `seeded_preprocess`, which expands the seed with `ChaCha20Rng::from_seed(*seed.0)` and derives the nonce scalars deterministically (`crypto/frost/src/sign.rs:121-144`, `crypto/frost/src/nonce.rs:107-124`). The FROST documentation in this same file states the contract being violated: "A preprocess MUST only be used once. Reuse will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:85-87`, `:211-213`). Nothing in `share_internal` clears or rotates the cache after use, so a repeated share request under the same `context` — e.g., a retried/duplicated signing attempt that re-enters `share_internal` with a different `msg` or a different set of peer preprocesses — produces a second signature share computed over the same (d, e) nonce pair.

### Impact Explanation
With two shares `s1 = d + ρ1·e + λ·c1·share` and `s2 = d + ρ2·e + λ·c2·share` produced under identical nonces but different binding factors ρ (ρ is derived from `rho_transcript` covering `group_key`, `hash_msg(msg)`, and the commitments challenge — `crypto/frost/src/sign.rs:361-371`), the secret share becomes recoverable by the algebraic relations the library itself warns about, and at minimum the nonce scalars are exposed once shares are broadcast. This constitutes key share recovery, one of the accepted impact classes.

### Likelihood Explanation
Exploitation requires two `share_internal` executions that resolve to the same encoded `context` but different signing content — a duplicate/retry attempt or a context that does not commit to the message and attempt number. Triggering input is partially attacker-influenced since peer preprocess bytes (untrusted, fed to `read_preprocess`) alter ρ while the nonce stays fixed. Whether a legitimate protocol flow can reproduce a context collision depends on how `C` is constructed by callers, which is not fully visible in this excerpt; the missing cache invalidation is, however, unconditional in the code.

### Recommendation
Delete or overwrite `CachedPreprocesses` once `sign` has consumed it (single-use semantics), or include the message/attempt in the cache key so distinct signing sessions can never share a seed. Alternatively, hash the intended `msg` and participant set into the stored value and panic on mismatch.

### Proof of Concept
Conceptual: invoke `share_internal` twice with the same `self.context` but different `msg`/preprocess maps. Both calls decrypt the identical cached seed, `seeded_preprocess` regenerates the same `nonces` via `ChaCha20Rng::from_seed` (`crypto/frost/src/sign.rs:127-133`), and two shares over the same (d, e) pair but different ρ are emitted — the exact precondition the FROST docs say leaks the private key share.
