### Title
Silent Trust of GitHub API `clone_url` Redirects Local `origin` Remote to Attacker-Controlled Host - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` automatically rewrites a repository's `origin` remote URL using the `clone_url` field returned by the GitHub API, verifying only that the transport protocol (`http:`/`https:`) is unchanged — it never verifies that the **hostname** of the new URL matches the hostname the repository was originally associated with. [1](#0-0) 

### Finding Description
The invariant that should hold is: "Desktop will only auto-update a remote to point at a location the user actually trusts (the same GitHub/GHE host the repository was cloned from)." Instead, `updateRemoteUrl` computes `urlsMatch`/`protocolsMatch`/`remoteUrlUnchanged` purely via `urlMatchesRemote`, which itself only compares `hostname`, `owner`, and `name` between the *old* and *new* URL to decide whether to skip the update — it is never used to pin the new URL's host to a known-good value. [2](#0-1) 

`protocolsMatch` only checks `URL.parse(...).protocol` equality (e.g. `https:` === `https:`), which is satisfied by `https://github.com/...` and `https://evil.com/...` alike: [3](#0-2) 

If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, the code calls `gitStore.setRemoteURL(...)`, which shells out to `git remote set-url` with the attacker-influenced value, with no dialog or user confirmation: [4](#0-3) [5](#0-4) 

This is structurally the same class of bug as the Chainlink report: an externally supplied data object (`IAPIRepository.clone_url`, analogous to the oracle's price feed) is consumed and applied to a security-relevant state (the git remote / oracle price) with insufficient validation of its trustworthiness (host/round-completeness), and the result silently corrupts downstream behavior (future `push`/`fetch`/`pull` target the wrong endpoint, analogous to bad price data propagating through the protocol).

Contrast this with the semantically similar "upstream remote points elsewhere" flow, which *does* prompt the user before rewriting a remote: [6](#0-5) 

`updateRemoteUrl`, by contrast, performs the rewrite unconditionally and silently, as documented by the changelog feature description ("Update the remote url when a repository's name changes on GitHub").

### Impact Explanation
If the GitHub API response for a repository (a GitHub API object) is attacker-influenced — e.g., a compromised or malicious GitHub Enterprise Server instance, a rogue/legacy enterprise proxy terminating TLS for the configured API endpoint, or any scenario where the `repos/:owner/:repo` JSON payload's `clone_url`/`ssh_url` field is not what the legitimate host would return — Desktop will silently rewrite the user's `origin` remote to point at an attacker-controlled git server, as long as the URL scheme is unchanged. Subsequent `git fetch`/`pull`/`push` operations initiated by the user (unaware the remote changed) would interact with the attacker's server instead of the real one, enabling credential harvesting (via HTTP Basic/token in transport, or SSH probing) and, on push, silent redirection of the user's commits to attacker infrastructure instead of (or in addition to) the intended remote.

### Likelihood Explanation
The update path runs automatically as part of Desktop's normal repository refresh/background sync with the GitHub API and requires no unusual user action — it fires whenever `updateRemoteUrl` is invoked with a differing `clone_url` while the previous state matched the stored `GitHubRepository.cloneURL`. The precondition is a compromised/malicious API endpoint returning an unexpected `clone_url`, which is more plausible for GitHub Enterprise deployments (self-hosted, admin-controlled or MITM-able infrastructure) than for github.com, but fits squarely within the accepted "attacker controls a GitHub API object" primitive.

### Recommendation
In `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts`), require that the new `clone_url`'s hostname matches the hostname of the account/endpoint that produced it (or matches the previously trusted remote's hostname) before calling `gitStore.setRemoteURL`. At minimum, compare `parsedRemoteUrl.hostname` against `parsedUpdatedRemoteUrl.hostname` in addition to protocol, and consider surfacing a confirmation dialog (similar to `UpstreamAlreadyExists`) whenever the hostname changes, rather than silently rewriting the remote.

### Proof of Concept
1. User has a repository cloned from `https://ghe.corp.example.com/owner/repo.git`, with the account configured against that GHE endpoint.
2. The GHE server (compromised, or proxied by a malicious intermediary trusted at the network layer) is made to return, for `GET repos/owner/repo`, a JSON body with `"clone_url": "https://ghe.corp.example.com.evil.com/owner/repo.git"` (same scheme, different host) while leaving `owner`/`name` fields intact.
3. On the next repository refresh, `updateRemoteUrl` computes `protocolsMatch = true` (both `https:`), `remoteUrlUnchanged = true` (git remote still matches the last known-good `cloneURL`), and `urlsMatch = false` (hostnames differ) — no host equality check exists to block this.
4. `gitStore.setRemoteURL('origin', 'https://ghe.corp.example.com.evil.com/owner/repo.git')` executes `git remote set-url origin ...`, silently repointing `origin` without any user prompt.
5. The next `git push`/`fetch` transparently targets the attacker's host. [7](#0-6)

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
