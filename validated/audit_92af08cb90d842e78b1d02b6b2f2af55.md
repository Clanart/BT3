### Title
Gasless swap admission check is front-runnable via AMM reserve manipulation, enabling DOS of legitimate GaslessSwapTx - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The `kaiax/gasless` module admits `GaslessSwapTx` into the transaction pool only if the declared `amountIn` covers a `requiredAmountIn` computed live from the current AMM reserves via `GetAmountIn`. Because this quantity is derived from mutable, attacker-influenceable on-chain state (pool reserves) at the moment of admission/re-validation, an attacker can shift the reserves with an ordinary swap so that a pending, otherwise-valid `GaslessSwapTx` fails this check and is rejected/evicted — the same class of bug as TRST-M-2, where a strict ratio/ amount check against a live, donatable/movable balance is abused to DOS an honest pending transaction.

### Finding Description
`checkBalanceForSwap` in `kaiax/gasless/impl/tx_pool.go` is registered as the pool's `GetCheckBalance` callback and is invoked whenever a `GaslessSwapTx` is added to (or re-validated in) the transaction pool: [1](#0-0) 

Inside it, when `ShouldCheckSwapAmount()` is enabled (the default, `BalanceCheckLevelAll`), the module queries the live DEX/swap-router state to compute the amount of token required for the user's declared `minAmountOut`, and rejects the transaction if the user-specified `amountIn` is insufficient: [2](#0-1) 

`requiredAmountIn` comes from `routerContract.GetAmountIn(nil, token, minAmountOut)`, which reads the current state of the swap pool (reserves) at call time — this is directly analogous to the Vault contract's `ratiosMatch(balances, amts)` check, which compares a user-submitted amount against the vault's current, externally-movable balances. Just as an attacker could donate tokens to the Vault to desynchronize `targetRatios` vs. `sourceRatios` and revert a pending deposit, here an attacker can execute an ordinary swap against the same pool (front-running the victim's pending `GaslessSwapTx`) to move the reserves enough that `requiredAmountIn` increases past the victim's already-signed, fixed `amountIn`. Because `amountIn`, `minAmountOut`, and `amountRepay` are all baked into the signed transaction and cannot be adjusted after signing, the check will fail on the next admission/re-check, causing the pending gasless transaction to be rejected or dropped from the pool.

Unlike SP1–SP4 checks validated in `VerifyExecutable`/`IsExecutable` (nonce sequencing, sender/token match, repay amount) which are static and do not depend on live reserves, this specific `ShouldCheckSwapAmount` check is the only one tied to mutable external state, making it the narrow analog of the Vault's balance-ratio check. [3](#0-2) 

### Impact Explanation
A successful attack denies service to gasless-swap users: their otherwise valid, fee-delegated (proposer-lent) swap transaction is rejected from or evicted out of the mempool, causing the user's gas-lending flow (`GetLendTxGenerator` bundle) to never execute. This is a low-cost, repeatable griefing vector against any specific gasless user or against the gasless subsystem broadly (any pool used for gasless swaps can be nudged this way with a same-block trade), degrading availability of the KIP-247 gasless transaction feature for legitimate endpoint-node/public-RPC callers.

### Likelihood Explanation
Likelihood is high for an attacker with visibility into the mempool: pending `GaslessSwapTx` (amountIn, minAmountOut, token, deadline) are visible before inclusion, and the attacker only needs to submit an ordinary swap on the target pool that moves the reserve ratio enough to push `GetAmountIn` above the victim's fixed `amountIn`. This requires no special privileges — any unprivileged transaction sender can submit the front-running swap. The cost is bounded by DEX trading fees/slippage, similar to the "negligible donation" cost noted in the original Vault report.

### Recommendation
Avoid rejecting/evicting an already-admitted `GaslessSwapTx` purely because instantaneous pool state has since drifted from the value implied by the user's signed parameters. Options include: (1) tolerating a bounded slippage margin instead of an exact `amountIn >= requiredAmountIn(now)` comparison; (2) deferring/soft-failing the swap-amount check by re-attempting execution at block-building time rather than dropping from the pool outright, since ultimate correctness is enforced on-chain by the swap router's own slippage checks; (3) rate-limiting or making this specific check advisory (logged) rather than pool-admission-fatal, since the router itself already reverts unprofitable swaps at execution.

### Proof of Concept
1. Victim signs and submits a `GaslessSwapTx` calling `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` with `amountIn` computed to just satisfy the current `GetAmountIn(token, minAmountOut)`.
2. Attacker observes this pending tx in the mempool (endpoint node) and submits an ordinary swap transaction on the same underlying DEX pool that shifts reserves against `token`, increasing `GetAmountIn(token, minAmountOut)`.
3. When the pool next validates/re-validates the victim's tx via `checkBalanceForSwap` (`kaiax/gasless/impl/tx_pool.go:128-142`), `swapArgs.AmountIn.Cmp(requiredAmountIn) < 0` now holds, and the transaction is rejected with `"insufficient amountIn"`.
4. The victim's gasless swap is denied inclusion (or evicted if already pending), even though it was fully valid when signed, at negligible cost to the attacker. [2](#0-1)

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}

// VerifyExecutable checks if the given transactions form a valid gasless transaction
// It returns an error explaining why the transaction is not executable if it's not,
// and a boolean indicating whether the transaction is executable
func (g *GaslessModule) VerifyExecutable(approveTxOrNil, swapTx *types.Transaction) error {
	// Sx.
	swapArgs, ok := decodeSwapTx(swapTx, g.signer)
	if !ok {
		return ErrDecodeSwapTx
	}
	if !g.isSwapTx(swapArgs) {
		return ErrSwapTxInvalid
	}

	// Conditions involving ApproveTx
	if approveTxOrNil != nil {
		// Ax.
		approveArgs, ok := decodeApproveTx(approveTxOrNil, g.signer)
		if !ok {
			return ErrDecodeApproveTx
		}
		if !g.isApproveTx(approveArgs) {
			return ErrApproveTxInvalid
		}
		// AP1.
		if approveArgs.Sender != swapArgs.Sender {
			return ErrDifferentSenders
		}
		// SP1.
		if approveArgs.Token != swapArgs.Token {
			return fmt.Errorf("%w: approve token %s, swap token %s", ErrDifferentTokens, approveArgs.Token.Hex(), swapArgs.Token.Hex())
		}
		// SP2.
		if approveArgs.Amount.Cmp(swapArgs.AmountIn) < 0 {
			return fmt.Errorf("%w: approve amount %s, required amount %s", ErrInsufficientApproveAmount, approveArgs.Amount.String(), swapArgs.AmountIn.String())
		}
		// SP3.
		if approveTxOrNil.Nonce()+1 != swapTx.Nonce() {
			return fmt.Errorf("%w: approve nonce %d, swap nonce %d (expected %d)", ErrNonSequentialNonce, approveTxOrNil.Nonce(), swapTx.Nonce(), approveTxOrNil.Nonce()+1)
		}
		if nonce := g.getCurrentStateNonce(approveArgs.Sender); nonce != approveTxOrNil.Nonce() {
			return fmt.Errorf("%w: approve nonce %d, current nonce %d", ErrApproveNonceNotCurrent, approveTxOrNil.Nonce(), nonce)
		}
	} else {
		// SP3.
		if nonce := g.getCurrentStateNonce(swapArgs.Sender); nonce != swapTx.Nonce() {
			return fmt.Errorf("%w: swap nonce %d, current nonce %d", ErrSwapNonceNotCurrent, swapTx.Nonce(), nonce)
		}
	}

	// SP4.
	if swapArgs.AmountRepay.Cmp(repayAmount(approveTxOrNil, swapTx)) != 0 {
		return fmt.Errorf("%w: got %s, expected %s", ErrIncorrectRepayAmount, swapArgs.AmountRepay.String(), repayAmount(approveTxOrNil, swapTx).String())
	}

	return nil
}
