### Title
Inconsistent cross-validation of `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` votes allows an invalid bound ordering to be ratified within a single epoch - (File: kaiax/gov/headergov/impl/header.go)

### Summary
This is the closest analog to the `setPlotsAvailablePerSize` bug class: a governance-settable parameter pair is validated only against the *currently active* value of its counterpart, not against other pending votes in the same batch/epoch, allowing a state that later breaks an invariant relied upon by downstream arithmetic.

### Finding Description
`checkConsistency` in `headerGovModule` validates `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` votes independently, each comparing the proposed new value against the *current* `GetParamSet(blockNum)` value of the other bound, not against any other vote submitted within the same epoch: [1](#0-0) 

Because ratification aggregates "the last vote in the epoch" per parameter name independently (per `kaiax/gov/headergov/README.md`), it is possible within a single epoch for one vote to raise `LowerBoundBaseFee` (validated against the old, lower `UpperBoundBaseFee`) and another vote to lower `UpperBoundBaseFee` (validated against the old, lower `LowerBoundBaseFee`) such that each individually passes `checkConsistency`, but the resulting ratified pair has `LowerBoundBaseFee > UpperBoundBaseFee`.

That inconsistent pair then feeds into `NextMagmaBlockBaseFee`, which assumes `lowerBoundBaseFee <= upperBoundBaseFee` when clamping `parentBaseFee`: [2](#0-1) 

### Impact Explanation
If `lowerBoundBaseFee > upperBoundBaseFee`, the clamping logic (`if parentBaseFee >= upperBound ... else if parentBaseFee <= lowerBound ...`) produces an ill-defined base fee trajectory (e.g., a fee could get clamped to the "upper" bound that is actually smaller than the "lower" bound, or vice versa), corrupting the deterministic base-fee calculation used for every subsequent block's fee market and burn accounting. Because this computation is deterministic and all honest nodes compute the same (broken) values from the same governance state, it does not directly cause a consensus split, but it can produce economically nonsensical/frozen base fees that misprice EVM computation for an entire epoch, effectively breaking the KIP-71 fee mechanism until the next epoch's governance vote corrects it.

### Likelihood Explanation
This requires the governing node (in `single` mode) or GC members (in `none` mode) to submit two governance votes in the same epoch — a privileged but ordinary governance action, not requiring any special exploit. The check exists precisely to prevent inverted bounds but only guards against a single vote per epoch, not concurrent votes on both parameters, so it is a real gap in the validation rather than a hypothetical one. However, it does require submitting a specific pair of votes within one epoch window, which lowers the likelihood versus an always-reachable path.

### Recommendation
When ratifying an epoch's votes in `getExpectedGovernance` / `checkConsistency`, validate `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` against each other's *pending* (to-be-ratified) values for the same epoch, not just the currently active `GetParamSet` value, and reject ratification (or fall back to defaults) if the final pair would violate `lowerBound <= upperBound`.

### Proof of Concept
1. Governing node casts vote A: `Kip71LowerBoundBaseFee = X` where `X <= current UpperBoundBaseFee` (passes `checkConsistency`).
2. In the same epoch, governing node casts vote B: `Kip71UpperBoundBaseFee = Y` where `Y >= current LowerBoundBaseFee` but `Y < X` (also passes `checkConsistency`, since it's checked against the pre-vote `LowerBoundBaseFee`, not the newly-voted `X`).
3. Both votes are ratified at the epoch boundary via `getExpectedGovernance`, producing a `ParamSet` where `LowerBoundBaseFee (X) > UpperBoundBaseFee (Y)`.
4. `NextMagmaBlockBaseFee` for the next epoch now clamps `parentBaseFee` using an inverted bound pair, producing incorrect/frozen base fees for all blocks in that epoch.
