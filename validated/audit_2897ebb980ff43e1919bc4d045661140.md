### Title
No reentrancy guard on `BridgeTransferERC20.requestERC20Transfer`/`handleERC20Transfer`, which perform external token calls with callback potential - (File: contracts/service_chain/bridge/BridgeTransferERC20.sol)

### Summary
`BridgeTransferERC20.sol` exposes `requestERC20Transfer` and `handleERC20Transfer` as unprivileged/operator-reachable entry points that make external calls into the token contract (`safeTransferFrom`, `safeTransfer`, `mint`, `burn`) before or alongside bridge-state bookkeeping (nonce increments, vote counting, handled-request tracking), yet neither function nor `BridgeTransferERC20` itself is protected by `ReentrancyGuard`/`nonReentrant`. This mirrors the reported bug class (`safeTransferFrom()` calling into a token/callback target without a reentrancy guard) almost exactly, and is inconsistent with the sibling contract `BridgeTransferKLAY.sol`, which explicitly wraps its analogous functions in `nonReentrant`.

### Finding Description
`BridgeTransferERC20.requestERC20Transfer` is `public` and callable by any transaction sender: [1](#0-0) 

It calls `IERC20(_tokenAddress).safeTransferFrom(...)` — an external call into an admin-registered token contract — and then calls `_requestERC20Transfer`, which itself calls `_payERC20FeeAndRefundChange`, performing further external `safeTransfer` calls to `feeReceiver` and back to `msg.sender`/`from` before the `RequestValueTransfer` event is emitted and `requestNonce` is incremented: [2](#0-1) [3](#0-2) 

`handleERC20Transfer`, callable by operators, similarly performs `ERC20Mintable(_tokenAddress).mint(_to, _value)` or `IERC20(_tokenAddress).safeTransfer(_to, _value)` — calls that can trigger a receiver-side callback (e.g., an ERC777-style `tokensReceived` hook or a malicious `_to` contract) — interleaved with nonce/vote bookkeeping (`_voteValueTransfer`, `_updateHandleNonce`, `_setHandledRequestTxHash`): [4](#0-3) 

Critically, `BridgeFee._payERC20FeeAndRefundChange` has no reentrancy protection of its own, unlike its KLAY counterpart, which explicitly documents the requirement that its caller must be `nonReentrant`: [5](#0-4) 

By contrast, `BridgeTransferKLAY` — the sibling contract for native KLAY transfers — explicitly imports `ReentrancyGuard` and applies `nonReentrant` to its request/handle functions that perform the equivalent external `.call.value()` transfers: [6](#0-5) [7](#0-6) 

`BridgeTransferERC20` inherits only `BridgeTokens`, `IERC20BridgeReceiver`, and `BridgeTransfer` (which inherits `BridgeHandledRequests`, `BridgeFee`, `BridgeOperator`) — none of which provide a `nonReentrant` guard: [8](#0-7) [9](#0-8) 

This is functionally the same defect class as the Sherlock report: a function that calls `safeTransferFrom`/`safeTransfer` (capable of invoking a callback on tokens with transfer hooks, e.g., ERC777-style tokens, or any registered token contract with delegatecall/proxy upgradeability) is not guarded against reentrancy, while state variables (`requestNonce`, `lowerHandleNonce`/`upperHandleNonce`, `closedValueTransferVotes`) are updated around those external calls.

### Impact Explanation
If a registered ERC20 token used with the bridge implements pre/post-transfer hooks (or is later upgraded/replaced to add such a hook — bridges commonly whitelist many arbitrary tokens), reentering `requestERC20Transfer`/`onERC20Received` or `handleERC20Transfer` during the external call could:
- Re-invoke `_requestERC20Transfer` recursively before `requestNonce++` is applied, corrupting the request-nonce sequencing that the counterpart-chain relayer relies on to order value transfers, potentially causing double-processing or nonce desynchronization between the two chains.
- Re-invoke `handleERC20Transfer` during the mint/transfer callback before `_updateHandleNonce`/vote-closing state is finalized, potentially causing duplicate `mint`/`safeTransfer` payouts for the same `_requestedNonce` if the vote-closing check (`_voteValueTransfer`) can be reentered before its internal state is committed.

This maps to the "acceptance of an invalid transaction" / "unauthorized value movement" categories in scope, since it can lead to duplicate token minting or duplicate transfers of bridged value.

### Likelihood Explanation
Medium. Exploitation requires a token registered via `registerToken` (owner-controlled) to have transfer/mint callback semantics, or a bridge operator/owner to register such a token (which does happen in production ERC20 bridges supporting diverse token standards). The `to`/`from` addresses in `handleERC20Transfer`/`requestERC20Transfer` are attacker-controlled (any unprivileged caller can pick `_to`), so a contract implementing a receive hook is directly reachable by an unprivileged transaction sender if the token itself supports hooks (e.g., ERC777) or is upgradeable.

### Recommendation
Add `ReentrancyGuard`/`nonReentrant` to `BridgeTransferERC20.requestERC20Transfer`, `onERC20Received`, `_requestERC20Transfer`, and `handleERC20Transfer`, mirroring the protection already applied in `BridgeTransferKLAY`. Alternatively, enforce checks-effects-interactions ordering by updating `requestNonce`/handle-nonce state and emitting events before making any external token calls.

### Proof of Concept
Conceptual PoC (cannot be executed in this read-only session):
1. Owner registers a malicious/hook-bearing ERC20-like token `T` via `registerToken(T, cToken)`.
2. Attacker deploys contract `A` implementing token `T`'s receive/send hook, which calls back into `Bridge.requestERC20Transfer(T, A, value, feeLimit, data)` (or `handleERC20Transfer`, if `A` is set as `_to` and an operator processes a transfer) during the `safeTransferFrom`/`safeTransfer`/`mint` callback triggered in `_requestERC20Transfer`/`handleERC20Transfer`.
3. Because neither function has `nonReentrant`, the reentrant call executes before `requestNonce++`/`_updateHandleNonce` finalize state from the outer call, allowing nonce desynchronization or duplicate value-transfer event emission/processing. [10](#0-9)

    // Caller of this function must be nonReentrant.
    // - BridgeTransferKLAY._requestKLAYTransfer() is nonReentrant
    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
