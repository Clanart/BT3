### Title
Unsynchronized lazy field-decoder cache allows cross-message corruption during concurrent `MergeFromString`/`ParseFromString` calls in pure-Python protobuf implementation - ([File: python/google/protobuf/internal/python_message.py])

### Summary
The webargs advisory (GHSA-8554-jxcw-454q) describes a thread-safety failure: a lazily-populated, per-process JSON parse cache was mutated without synchronization while being read/written by concurrent request-handling threads, so one request's cached (possibly still-being-constructed) value could leak into or corrupt another concurrent request's parse. The invariant that failed was "the cache must only ever be observed in a fully-constructed, request-independent state." The strongest structural analog in this Protobuf checkout is the pure-Python message parser's lazy decoder cache: `FieldDescriptor._decoders`, populated on first use by `_MaybeAddDecoder(cls, field_des)` and consumed unsynchronized from `InternalParse` (`python_message.py`) on every `MergeFromString`/`ParseFromString` call across all instances of a message class. This mirrors the same bug class — a shared, class/descriptor-scoped mutable cache mutated during message parsing, read by concurrent parser invocations without a lock.

### Finding Description
`_AddMergeFromStringMethod` builds `InternalParse`, which on every parsed field does: [1](#0-0) 
```
        _MaybeAddDecoder(cls, field_des)
        field_decoder = field_des._decoders[is_packed]
        pos = field_decoder(
            buffer, new_pos, end, self, field_dict, current_depth
        )
```
`field_des` (a `FieldDescriptor`) is shared across *every* message instance of that type, i.e. it is process-wide, class-level state — analogous to webargs' shared parse cache being reused across concurrent requests. `_MaybeAddDecoder` lazily creates and attaches the `_decoders` dict/tuple to the field descriptor the first time any message of that type is parsed, with no lock protecting the check-then-act sequence (`hasattr`/attribute-set race). This is exactly the pattern the project's own regression test targets: [2](#0-1) 
The test explicitly deletes `field_des._decoders` before each iteration and races two threads calling `ParseFromString` concurrently on independent messages sharing the same field descriptor, checking equality of the parsed result — i.e., verifying that the lazily-built, unsynchronized decoder cache does not yield a corrupted/incomplete decoder for one of the two concurrent parses. The comment in the test itself states: "delete the `_decoders` because only the first time parse the field may cause data race," confirming the maintainers know the *first* population of this shared cache is racy.

Additionally, `InternalParse`'s hot-path lookup `field_des._decoders[is_packed]` assumes the attribute exists and is fully populated by the time it's read; if `_MaybeAddDecoder` (called from a concurrent thread on another message of the same type) is caught mid-construction, a reader could observe a partially built structure or a `KeyError`/`AttributeError`, or in the worst case retrieve a decoder function object that hasn't been fully bound/initialized, silently corrupting the field decode for one of the two concurrent, unrelated messages — the direct analog of webargs parsing "incorrect JSON payloads... for concurrent requests."

### Impact Explanation
In the pure-Python protobuf backend (`api_implementation` = python), an application that parses attacker-supplied bounded Protobuf bytes from multiple threads concurrently for the *same message type* (a very common server pattern — e.g., a thread pool parsing independent RPC bodies of the same proto type) can, on the first concurrent parse of a given field, hit the unsynchronized lazy-build path in `_MaybeAddDecoder`/`field_des._decoders`. Because the cache is keyed per-`FieldDescriptor` and shared globally, a race there does not merely affect a single request: it can corrupt the decode of a concurrently-running, unrelated message instance, i.e., cross-request data corruption/integrity failure without attacker authentication — matching the CWE-362/high-severity classification of the original report (data corruption/integrity impact under ordinary concurrent use, not a crash-only or exhaustion issue).

### Likelihood Explanation
This only manifests on the pure-Python (`api_implementation=python`) backend — the C++/upb backends handle decoding in native code with different (and generally properly synchronized) mechanisms, so this is not a cross-backend issue. It also only triggers on the very first parse of a given field per process (after which `_decoders` is cached and stable), narrowing the exploitable window; the project's own test needed to `delattr` the cache before each iteration and use 1000 repetitions to reliably surface the race, indicating the window is narrow but real and already known/tracked internally. Likelihood is Medium: it requires the pure-Python backend, concurrent first-time parsing of the same message type, and does not require any privileged access — an attacker only needs to be one of several concurrent legitimate/otherwise-untrusted clients causing simultaneous first-parses.

### Recommendation
Guard `_MaybeAddDecoder`'s check-then-populate sequence on `field_des._decoders` with a lock (or use `threading.Lock`/double-checked locking with an atomic "already built" flag) so that concurrent first-parses of the same field descriptor cannot observe or install a partially-constructed decoder table. Alternatively, precompute and freeze `_decoders` eagerly at class-creation time (when the message class is built) rather than lazily on first parse, removing the racy lazy-initialization path entirely from `InternalParse`'s hot loop.

### Proof of Concept
The existing regression test already reproduces the described race condition end-to-end: [2](#0-1) 
It resets the shared `_decoders` cache on the field descriptor and runs two threads calling `ParseFromString` on two independently-constructed messages of the same type concurrently, then asserts both parses produced results equal to the expected message; the comment notes the race is specifically triggered "only the first time [the] field" is decoded, confirming the lazy, unsynchronized cache population in `_MaybeAddDecoder`/`field_des._decoders` (`python_message.py:1404-1409`) is the concrete unguarded shared-cache write path analogous to the webargs advisory.

Note: I could not locate the exact source of `_MaybeAddDecoder`'s implementation body within the indexed context (only its call sites were found), so the precise mechanics of the lazy-build (e.g., whether it uses `hasattr` check-then-set or `setattr` unconditionally) could not be fully verified from the available index; a full-repository read (e.g., via a Devin session) would be needed to inspect that function definition directly and confirm the exact race window before treating this as fully proven.

  def testFieldDecodersDataRace(self):
    msg = unittest_pb2.TestAllTypes(optional_int32=1)
    serialized_data = msg.SerializeToString()
    lock = threading.Lock()

    def ParseMessage():
      parsed_msg = unittest_pb2.TestAllTypes()
      time.sleep(0.005)
      parsed_msg.ParseFromString(serialized_data)
      with lock:
        if msg == parsed_msg:
          self.success += 1

    field_des = unittest_pb2.TestAllTypes.DESCRIPTOR.fields_by_name[
        'optional_int32'
    ]
    count = 1000
    for x in range(0, count):
      # delete the _decoders because only the first time parse the field
      # may cause data race.
      if hasattr(field_des, '_decoders'):
        delattr(field_des, '_decoders')
      thread1 = threading.Thread(target=ParseMessage)
      thread2 = threading.Thread(target=ParseMessage)
      thread1.start()
      thread2.start()
      thread1.join()
      thread2.join()

    self.assertEqual(count * 2, self.success)
