## Finding

The bug-class here — a callback that trusts caller-supplied identity data without cryptographically binding it to the signed/verified payload — has a direct analog in this repo's custom webhook path.

`ShopifyApp::WebhookVerification#verify_request` only HMAC-validates `request.raw_post` (the body), while `shop_domain` is read straight from the `X-Shopify-Shop-Domain` request header, which is never included in the HMAC computation: [1](#0-0) 

The HMAC secret used is the app's single global secret, not per-shop, so any actor who installs the app on their own (unrelated) store can generate a genuinely-signed `(body, HMAC)` pair from their own shop's real webhook traffic: [2](#0-1) 

Since the header is unauthenticated, that attacker can replay the same signed body directly at the app's public custom webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header claiming to be a victim shop. `verify_request` still passes because it never checks the domain. The docs explicitly document this pattern for custom controllers, forwarding the unauthenticated `shop_domain` straight into job processing: [3](#0-2) 

Downstream job templates then act on that spoofed shop domain, e.g. the generated `AppUninstalledJob` looks up and destroys the shop record purely by `shop_domain`: [4](#0-3) 

### Title
Webhook HMAC verification does not bind `X-Shopify-Shop-Domain` header, allowing cross-shop forged webhook replay - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates only the HMAC over the request body using the app's single shared secret; it never verifies that the `X-Shopify-Shop-Domain` header corresponds to the shop that actually produced the signed payload. Any merchant who installs the app on their own store can obtain a validly-signed `(body, HMAC)` pair from their own shop's webhook traffic, then replay it at the app's custom webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. The verification passes, and the (attacker-controlled) body is processed in the context of the victim shop.

### Finding Description
`hmac_valid?` computes/compares HMAC-SHA256 over `request.raw_post` only, using `ShopifyApp.configuration.secret`/`old_secret` — the app-wide client secret, identical for every installed shop: [5](#0-4) 

`verify_request` in `WebhookVerification` calls this check and, if it passes, allows the request through; `shop_domain` is derived independently from a header that plays no role in the HMAC: [1](#0-0) 

Because the secret is shared across all shops, the HMAC only proves "this body was sent by Shopify for some installed shop" — it does not prove which shop. An attacker who installs the app on their own store (an unprivileged, unrelated-merchant action) can trigger a real webhook event (e.g., rename a product, update an order) to obtain a body+HMAC pair that legitimately passes verification, then POST that same body/HMAC to the app's public webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` header. This is structurally identical to the reported analog: a privileged state-mutating handler (`onOwnershipTransferred`) trusted the caller's claimed identity/context without checking it against the actual authorized owner; here the handler trusts the caller-supplied shop-domain header without checking it against the actual signer of the payload.

The docs' own recommended custom-controller pattern forwards this unauthenticated `shop_domain` directly into background job processing: [6](#0-5) 

And the generator-provided `AppUninstalledJob` template acts on it destructively, purely keyed by `shop_domain`: [4](#0-3) 

Similarly, `WebhooksManagerJob` re-creates a live Shopify session/token context from `shop_domain` alone: [7](#0-6) 

### Impact Explanation
An attacker with no relationship to the victim shop (only requiring their own free/trial install of the app) can force the app to process attacker-controlled webhook data under the identity of a victim shop. Depending on which webhook jobs are configured, this enables:
- Destroying the victim's persisted `Shop`/session record via `AppUninstalledJob`, forcing de-authorization/denial of service.
- Injecting attacker-chosen data (order/customer/product payloads) into the victim shop's data pipeline, since job classes trust `shop_domain` to scope the operation.
- Triggering privacy webhooks (`customers/redact`, `shop/redact`) against a shop that never requested them.

This is a cross-shop access/data-integrity break stemming from an accepted forged (mis-bound) signed request.

### Likelihood Explanation
Medium-to-High: exploitation only requires the ability to install the app on any shop (an unrelated/unprivileged merchant action) and knowledge of the app's public webhook URL, both trivially available for any Shopify app. No secret leakage or privileged access is required — only the documented custom-controller integration pattern using `ShopifyApp::WebhookVerification`.

### Recommendation
1. Do not treat `X-Shopify-Shop-Domain` as trusted unless it is cryptographically bound to the payload. Prefer deriving the shop from data validated by the signature (e.g., match against a shop resolved via the already-stored, previously-verified session/token for that domain, and reject if the shop referenced by the payload's own resource data disagrees).
2. Where feasible, use per-shop webhook secrets/HMAC keys or verify webhook `id`/topic against a known active subscription for the claimed shop before dispatching jobs.
3. In generated job templates (e.g. `AppUninstalledJob`), require that the acting shop domain has an existing, matching authenticated session before performing destructive actions, rather than trusting the header value alone.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining valid OAuth/session.
2. Attacker performs an action that triggers a subscribed webhook (e.g., uninstalls the app to trigger `app/uninstalled`), and captures the raw POST body and the resulting `X-Shopify-Hmac-Sha256` header sent by Shopify to the app's webhook endpoint (e.g., via a local intercepting proxy on infrastructure they control, or by using a webhook forwarding tool they operate).
3. Attacker replays that exact `(body, X-Shopify-Hmac-Sha256)` pair to the same public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which succeeds (same body, same app-wide secret) — request is accepted.
5. `shop_domain` resolves to `victim-shop.myshopify.com` from the header; `AppUninstalledJob.perform(shop_domain: "victim-shop.myshopify.com", ...)` looks up and destroys the victim's `Shop` record, even though the victim never uninstalled the app.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
