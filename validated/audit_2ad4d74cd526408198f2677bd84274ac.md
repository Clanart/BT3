## Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo` parsing custody vault memos can cause a Python stack overflow / crash - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

## Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a wallet-vault custody structure from an on-chain/offer-carried memo `Program`. When the memo indicates "further branching" (an `MofN` composite), it recursively calls itself once per member, with no limit on nesting depth [1](#0-0) . This is structurally the same bug class as CVE-2026-46557 (ImageMagick `fx`): a recursive parser that walks attacker-controlled input with no depth check, leading to a stack overflow / crash.

## Finding Description
`PuzzleWithRestrictions.memo()` serializes a wallet-vault custody tree (used for `MofN` multisig/threshold custody puzzles) into a CLVM `Program`, intended to be attached as a coin memo/hint so other wallets/participants can reconstruct the custody structure later [2](#0-1) .

The corresponding parser, `from_memo()`, checks a "further branching" flag; if set, it parses an `MofNHint` and recursively calls `PuzzleWithRestrictions.from_memo` once per member of the `member_memos` list: [3](#0-2) 

There is no explicit recursion-depth limit anywhere in this parsing path. `MofNHint.from_program` simply reads an `m` value and a list of member memos, without validating their size or nesting depth [4](#0-3) . Because `MofN.__post_init__` and depth constraints are only enforced when *constructing* a `PuzzleWithRestrictions`/`MofN` from application logic — not when parsing an arbitrary memo `Program` — a maliciously crafted memo can nest `MofN` structures (each nesting level being a valid `(m . [nested_memo, ...])` shape) arbitrarily deep, since each nesting level only needs one `Program` cons cell.

This contrasts with the codebase's own established pattern for untrusted/deeply-nested `Program` trees, where tree-hashing is deliberately implemented iteratively "so we don't have to worry about blowing out the python stack" [5](#0-4) . `from_memo` does not follow that pattern and recurses directly in Python.

Every layer of recursion also does non-trivial Python-level work (`RestrictionHint.from_program`, `MemberHint.from_program`, dataclass construction, dictionary building) rather than a cheap tail-call, so even before hitting CPython's `RecursionError` limit, a sufficiently deep-but-still-under-limit memo can consume significant native C stack, and a memo built to exceed CPython's recursion limit will raise `RecursionError`/`SystemError`, crashing whatever wallet process attempts to sync/import it (Python doesn't reliably distinguish "safe recursion limit hit" from real stack exhaustion in all interpreter/thread-stack-size configurations).

## Impact Explanation
A wallet participant importing/syncing a custody-vault memo (or a peer/participant supplying a `PuzzleWithRestrictions` memo as part of vault setup/coordination) that contains a deeply nested `MofN` structure can crash or hang the parsing wallet process, halting transaction/wallet-state processing for that wallet — matching the "spend-triggered transaction-processing halt" impact class called out for this scan. This is a Medium-severity availability issue, not a fund-theft or consensus-divergence issue; the parser only reconstructs local wallet state, it does not itself grant unauthorized spend authority. No supply inflation, unauthorized coin movement, or coin-set divergence is introduced.

## Likelihood Explanation
`from_memo()` is documented in this repo's own test-guidance docs as "the on-chain/exported synchronization contract" meant to let "later wallet code fill known puzzle implementations by puzzle hash," i.e. it is meant to process untrusted/foreign-provided data during custody-vault synchronization [6](#0-5) . Constructing a deeply nested memo is trivial (a chain of nested lists), requiring no special privileges, keys, or costly on-chain computation — an attacker only needs to hand a crafted memo `Program` to a wallet that calls `from_memo`.

## Recommendation
- Add an explicit maximum recursion/nesting depth (and/or maximum total node count) check in `PuzzleWithRestrictions.from_memo`, rejecting memos that exceed the depth used by any legitimate custody configuration.
- Alternatively, rewrite `from_memo` as an iterative parser using an explicit work-stack (following the pattern already used in `chia/types/blockchain_format/tree_hash.py`) so deeply nested memos cannot exhaust the Python/C call stack regardless of depth.
- Validate `member_memos` length and overall memo size before recursing, consistent with `MofN.__post_init__`'s existing sanity checks (`m <= n`, no duplicate nodes) [7](#0-6) .

## Proof of Concept
Construct a memo `Program` recursively N times deep, where each level is:
```
("CHIP-0043", [nonce, [], 1, (1, [inner_memo])])
```
i.e. each level sets `further_branching = 1` (truthy) and supplies a single-member `MofNHint` whose only member memo is the next nested level. Repeating this construction ~a few thousand times (well within CLVM program size limits) and calling:
```python
PuzzleWithRestrictions.from_memo(deeply_nested_memo)
```
will drive Python recursion to `RecursionError` (or, depending on stack-size configuration/thread, a genuine native stack overflow), matching the pattern already exercised for `chia_rs.datalayer` in this repo's own recursion-depth tests (e.g. `test_insert_into_data_store_from_file_line_graph_depth`, which explicitly documents that unbounded recursion depth is a recognized hazard class in this codebase) [8](#0-7) .

@dataclass(kw_only=True, frozen=True)
class MofNHint:
    m: int

    def to_program(self) -> Program:
        return Program.to([self.m, self.member_memos])

    @classmethod
    def from_program(cls, prog: Program) -> MofNHint:
        m, member_memos = prog.as_iter()
        return MofNHint(
            m=m.as_int(),
            member_memos=list(member_memos.as_iter()),

@pytest.mark.anyio
@pytest.mark.parametrize("depth", [1000, 100_000])
async def test_insert_into_data_store_from_file_line_graph_depth(
    data_store: DataStore,
    store_id: bytes32,
    tmp_path: Path,
    depth: int,
) -> None:
    # Binary "line graph":
    #   1 -> leaf_1, 2
    #   2 -> leaf_2, 3
    #   ...
    #   depth -> leaf_depth, leaf_end
    #
    # This stresses depth/stack handling while staying strictly binary.
    #
    # Node IDs:
    # - internal nodes: 1..depth
    # - per-level leaf nodes: (depth+1)..(2*depth)
    # - final leaf: (2*depth+1)
    internal_first = 1
    internal_last = depth
    leaf_base = internal_last + 1
    leaf_end = (2 * depth) + 1

    edges: list[tuple[int, int]] = []
    for i in range(internal_first, internal_last):
        # Order matters: first edge is left child, second edge is right child.
        edges.append((i, leaf_base + (i - internal_first)))  # unique leaf for this internal node
        edges.append((i, i + 1))  # next internal node

    # last internal points to its leaf and a final leaf
    edges.append((internal_last, leaf_base + (internal_last - internal_first)))
    edges.append((internal_last, leaf_end))

    filename = tmp_path / f"line_graph_depth_{depth}.dat"
    root_hash = create_graph_util(filename, edges)

    with pytest.raises(chia_rs.datalayer.RecursionDepthExceededError):
        await data_store.insert_into_data_store_from_file(store_id, root_hash, filename)
