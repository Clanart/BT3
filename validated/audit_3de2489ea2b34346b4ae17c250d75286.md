Based on the investigation, I found a genuine structural analog to the Arrakis `setModule` bug class in Hyperbridge's shared `CallDispatcher` contract, which is used exactly the way the vulnerable module was: as an intermediate holder of funds that then executes attacker/caller-suppliable arbitrary payloads.

### Title
Unrestricted `CallDispatcher.dispatch()` allows anyone to drain assets left transiently on the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, permissionless utility contract used by multiple Hyperbridge apps (`IntentGatewayV2` predispatch/postdispatch, `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata delivery) to hold assets briefly and then run caller-specified `Call[]` batches against them [1](#0-0) . Its `dispatch()` function has **no access control whatsoever** — no `onlyGateway`, no `msg.sender` allowlist, nothing beyond checking that the target has code [2](#0-1) . This mirrors the root cause of H-4: a step that moves funds into an intermediary is followed by a step that runs arbitrary, unauthenticated payloads against that same intermediary, with nothing tying "which payload may run" to "who owns the balance sitting there."

### Finding Description
Every flow that uses `CallDispatcher` follows the same two-phase pattern documented for both `IntentGatewayV2` and the HyperFungibleToken family: assets are moved to the dispatcher first, then `dispatch()` is called (potentially more than once) to run calls and sweep the residual balance back [3](#0-2) . The dispatcher's own contract enforces nothing about *who* may trigger the execution step or *which* calls are legitimate for the balance it currently holds — `dispatch(bytes memory encoded)` simply decodes whatever `Call[]` it is given and executes it against arbitrary targets with arbitrary value [2](#0-1) .

Because the contract has a public `receive()` and its address is documented/fixed for cross-app use ("mint to the `CallDispatcher` so the swap can spend the tokens" / "unlock to the `CallDispatcher` so it receives the unwrapped ETH") [4](#0-3) [5](#0-4) , any window in which the dispatcher holds a balance before the legitimate app calls `dispatch()` to sweep it is a window in which **any external account** can call `CallDispatcher.dispatch()` directly with its own `Call[]` and redirect that balance to itself. The `IntentGatewayV2`/`IntentsBase` call sites are guarded by being invoked entirely within one atomic external call from the gateway (transfer → dispatch(predispatch.call) → dispatch(sweep) all in one transaction, `placeOrder` is `nonReentrant`) [6](#0-5) , so a plain, non-reentrant ERC-20 flow through the gateway is not exploitable. But this atomicity is a property of the *caller's* code, not of `CallDispatcher` itself — the dispatcher provides zero protection on its own, exactly as `ValantisHOTModule`/`ArrakisMetaVault` provided no protection once funds were moved into the new module and arbitrary `payloads_` were allowed to run against it.

The unresolved risk (not confirmed against `HyperFungibleTokenImpl`/`onAccept` in this pass) is any flow where the "mint/unlock tokens to `to = CALL_DISPATCHER`" step and the "execute `data` via dispatch" step are **not** forced into the same atomic call — the documentation's phrasing ("Tokens are unlocked ... to `to` first, then the `CallDispatcher` executes each call in sequence") describes them as sequential steps, and if any code path allows the second step to be triggered by anyone as a follow-up call, or if a reentrant/callback-bearing ERC-20 is used as a predispatch/input asset, an attacker can call `dispatch()` in that gap and steal the balance meant for the legitimate recipient — precisely the "move funds, then attacker supplies payloads" primitive from H-4.

### Impact Explanation
If exploitable, this allows outright theft of any tokens or ETH transiently held by `CallDispatcher` — funds belonging to intent-gateway solvers/users or HyperFungibleToken bridge recipients — redirected to an arbitrary attacker address. This satisfies the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" impact categories.

### Likelihood Explanation
Confirmed fact: `CallDispatcher.dispatch()` is public with zero access control [2](#0-1) . What remains unverified in this session is whether any production entrypoint leaves a non-atomic, externally-observable window where the dispatcher holds value before its own sweep/dispatch executes (e.g., a token with transfer callbacks used as a predispatch/input asset, or an HFT flow where mint and dispatch are separate top-level transactions rather than one atomic call). I was not able to load `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`'s `onAccept`/receive logic before this session ended, so I cannot confirm or rule out that specific path — this should be verified directly against that file and against any ERC-20 predispatch/input asset that could carry transfer hooks.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by a registered set of trusted app contracts (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, etc.), or make the dispatcher single-use/ephemeral per operation (e.g., deploy a minimal proxy instance per call, or gate `dispatch()` behind a caller check plus a "pending operation" commitment set atomically when assets are deposited). At minimum, verify and close any window in the HyperFungibleToken flows where minting/unlocking to the dispatcher and the corresponding `dispatch()` call are not enforced to happen inside a single atomic transaction initiated solely by the protocol's own bridge-message handler.

### Proof of Concept
Not constructible with full confidence from the code reviewed in this session — the `IntentGatewayV2`/`IntentsBase` call sites are atomic and non-reentrant as written, so the concrete PoC target is the HyperFungibleToken mint/unlock-then-dispatch path, which needs direct inspection of `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` and `HyperFungibleTokenImpl.sol` to confirm whether the two steps are separable by an external caller. Recommend a Devin session load those files and trace: (1) does `onAccept`/message-receive mint/unlock tokens to `to` and call `CallDispatcher.dispatch(data)` in the same call frame with no external call in between, and (2) can any ERC-20 used in `IntentGatewayV2.placeOrder`'s predispatch/input path trigger a transfer-hook callback that calls `CallDispatcher.dispatch()` before the gateway's own sweep executes.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
