## Title
Ineffective deadline protection in `WombatStaking.withdraw` due to hardcoded `block.timestamp` — ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.withdraw` performs an unprivileged-wallet-triggered withdrawal from the underlying Wombat pool but passes `block.timestamp` as the `deadline` argument to `IWombatPool.withdraw`, exactly mirroring the reported bug class in `CurveLiquidityWarehouse._withdrawFromTarget`: the deadline is computed at execution time rather than supplied by the user ahead of time, so it provides no real protection against a delayed/displaced transaction.

### Finding Description
`WombatStaking.withdraw` is called by `WombatPoolHelper.withdraw`/`WombatPoolHelperV2.withdraw`, both of which are external functions any ordinary wallet can call directly to unstake and withdraw its LP position: [1](#0-0) 

Internally, `WombatStaking.withdraw` forwards the call to the Wombat pool with `block.timestamp` as the deadline: [2](#0-1) 

Because `deadline` is set to `block.timestamp` inside the transaction itself (evaluated only once the transaction is actually mined), the deadline check on the underlying pool (`require(deadline >= block.timestamp)`) is trivially satisfied no matter how long the transaction has been sitting in the mempool. This defeats the entire purpose of a deadline: a transaction can be held back by a validator/searcher and included in a later block where the pool price has moved unfavorably for the withdrawing user, and it will still execute, since the "deadline" is always "now" by construction.

The same anti-pattern also appears in `SmartWomConvert._convertFor` (reachable by any wallet via `SmartWomConvert.convert`/`convertFor`, and via `ManualCompound.compound`), where the router swap is called with `block.timestamp` as deadline and, notably, `0` as `minAmountOut` for the underlying swap call itself: [3](#0-2) 

### Impact Explanation
A withdrawing/converting user has no protection against their transaction being displaced to a later block. Combined with `_minAmount`/`_minRec` values that are computed off-chain at submission time (and may become loose relative to a moved market by the time the tx actually executes), a delayed or sandwiched execution can still pass the on-chain checks while delivering a materially worse price than the user intended — a direct value loss to the depositor's/withdrawer's own funds, consistent with the "worse price from displaced transaction" impact described in the report.

### Likelihood Explanation
Both `WombatStaking.withdraw` (via `WombatPoolHelper`/`WombatPoolHelperV2`) and `SmartWomConvert.convert`/`convertFor` (directly, or via `ManualCompound.compound`) are unauthenticated entry points reachable by any wallet in normal operation, so every withdrawal/convert transaction is exposed to this weakness whenever it is delayed (mempool congestion, MEV reordering, or a searcher deliberately holding the transaction).

### Recommendation
Add a real `deadline` parameter to `WombatPoolHelper(V2).withdraw`, `WombatStaking.withdraw`, `SmartWomConvert.convert`/`convertFor`, and any other function forwarding calls to the Wombat pool/router, and forward the caller-supplied deadline instead of `block.timestamp`. Additionally, in `SmartWomConvert._convertFor`, pass a derived minimum output (based on `_minRec`) to the router's `swapExactTokensForTokens` call instead of `0`.

### Proof of Concept
1. A user calls `WombatPoolHelper.withdraw(_liquidity, _minAmount)` with `_minAmount` computed from the current pool price, intending the transaction to be stale/invalid if not executed promptly.
2. The transaction is picked up but held/reordered by a block producer or MEV searcher for several blocks while the pool price moves against the user (still above `_minAmount`).
3. When finally mined, `WombatStaking.withdraw` computes `deadline = block.timestamp` at that later block, so `IWombatPool.withdraw`'s deadline check always passes trivially.
4. The withdrawal executes at the later, worse price, and the user has no way to have their transaction reverted for staleness as intended.
