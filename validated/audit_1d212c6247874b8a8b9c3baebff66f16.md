## Analog Identified

The reported pattern — an "expected amount" is silently trusted without checking that it equals what was actually consumed/counted, leading to unrecoverable corruption — maps to the GitHub Copilot AI merge-conflict resolution feature added to GitHub Desktop.

### Title
Silent hunk-to-conflict-block misalignment in Copilot conflict-resolution reassembly can corrupt committed file content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` splices Copilot's per-hunk resolutions into the on-disk conflicted file purely by **positional order**, with no verification that the number of well-formed conflict-marker blocks it encounters while walking the file equals `hunkResolutions.length`. [1](#0-0)  Just like the reported `buyNFT`/`buyMultipleNFT` bug — where an expected paid amount is assumed to equal `msg.value` without a `require` check — this function assumes the expected hunk count equals the actual number of conflict blocks it finds, and never asserts that invariant.

### Finding Description
`validateResolutionPaths` only checks that the model's declared `hunks.length` matches `expectedHunkCounts`, a value computed once from `extractConflictHunks(content)` at context-build time. [2](#0-1)  That check never touches `reassembleResolvedFile`, which independently re-walks `rawContent` at reassembly time looking for `<<<<<<<` / `=======` / `>>>>>>>` blocks using its own regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`). [3](#0-2) 

Critically, when it finds a marker block it just does:
```
if (hunkIndex < hunkResolutions.length) {
  const resolved = hunkResolutions[hunkIndex].resolvedContent
  ...
}
hunkIndex++
``` [4](#0-3) 

There is no assertion at the end of the loop that `hunkIndex === hunkResolutions.length`. If the file (which comes from an attacker-controlled merge/rebase/cherry-pick source, per the function's own doc: "the original file content on disk, which still has conflict markers") contains any conflict-marker-shaped text that is counted differently between the context-extraction pass and the reassembly pass — e.g. an extra or missing well-formed `<<<<<<<...=======...>>>>>>>` block earlier in the file — every subsequent resolution is spliced into the **wrong** conflict block. Excess resolutions are silently dropped; a shortfall silently leaves raw conflict markers in trailing blocks unresolved-but-undetected as such by the write path.

This reassembled content is then written straight to disk and staged without re-validation:
```
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
...
await git(['add', '--', ...pathsToStage], repository.path, 'copilotConflictResolution')
``` [5](#0-4)  The only pre-write guard checks whether the file is *already fully resolved* on disk (to avoid clobbering a user's own manual fix); it does not check whether the block count still matches what was resolved. [6](#0-5) 

### Impact Explanation
This results in **silent corruption of what the user commits/pushes** — code from one conflict resolution can be spliced into an unrelated location in the file, or leftover unresolved conflict markers can be written and committed as valid-looking source without any error surfaced to the user (`onContinue` in the dialog proceeds straight to commit/continue-merge after `applyCopilotConflictResolutions` succeeds). [7](#0-6)  Since the user explicitly reviews Copilot's summarized resolution rather than a byte-for-byte diff before clicking "Continue Merge," this is highly likely to go unnoticed and get committed/pushed.

### Likelihood Explanation
The trigger surface is a merge/rebase/cherry-pick against attacker-influenced content (a malicious branch or PR the user merges), which is squarely within scope ("attacker controls a cloned/fetched repository"). I was not able to fully inspect `extractConflictHunks` in `copilot-conflict-context.ts` (the counting logic used to populate `expectedHunkCounts`) within the tool budget available, so I cannot conclusively prove today that its counting diverges from `reassembleResolvedFile`'s block-walk in a specific crafted input — this is the one open item that would need direct code comparison to nail down a concrete PoC file. What is confirmed directly from the code is the structural weakness: **no invariant check (`hunkIndex === hunkResolutions.length`) exists at the end of reassembly**, which is the same class of missing "actual == expected" guard as the original report.

### Recommendation
In `reassembleResolvedFile` (or its caller `reassembleResolutions`), after the walk completes, assert `hunkIndex === hunkResolutions.length` and throw a `CopilotValidationError` (mirroring `validateResolutionPaths`'s existing pattern) if they differ, rather than silently truncating/misaligning. Additionally, re-derive `expectedHunkCounts` using the exact same block-detection logic (ideally the same function) that `reassembleResolvedFile` uses, so the two passes cannot disagree by construction.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
