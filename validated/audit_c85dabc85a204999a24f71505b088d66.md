Based on my analysis, I found a concrete analog in GitHub Desktop's diff-expansion / line-selection logic. Like the original `getActiveTickIndex` bug — where an index computed for one state was silently reused for a different state, misallocating funds to the wrong "tick" — Desktop's `expandTextDiffHunk` reuses a stale line index (`unifiedDiffStart`) after inserting new lines, which desynchronizes the persistent `DiffSelection` index map from the actual diff-line positions.

### Title
Stale `unifiedDiffStart` after upward hunk expansion desynchronizes line-selection indices, silently altering staged/committed content - (File: app/src/ui/diff/text-diff-expansion.ts)

### Summary
`expandTextDiffHunk` prepends new context lines to a hunk when expanding "up" but keeps the hunk's `unifiedDiffStart` unchanged, even though the position of the pre-existing (selectable) lines within the hunk has shifted. Downstream code (`patch-formatter.ts`, `diff-explorer.ts`) computes `absoluteIndex = hunk.unifiedDiffStart + lineIndex` to look up per-line inclusion state in the persistent `DiffSelection` object, which stores selection state keyed by these absolute indices. After an up-expansion the same absolute index now points at a different line than the one the user actually selected/deselected.

### Finding Description
`expandTextDiffHunk` builds the new hunk lines as: [1](#0-0) 
When `isExpandingUp` is true, `numberOfLinesToAdd` new context lines are prepended before the original hunk lines, but the updated hunk is constructed re-using the original `hunk.unifiedDiffStart`: [2](#0-1) 
Because the array of lines grew at the front while `unifiedDiffStart` stayed fixed, every pre-existing line inside that hunk (the actual Add/Delete/Context lines a user may have selected) now resolves to an `absoluteIndex` that is `numberOfLinesToAdd` higher than before. This absolute index is exactly the key used elsewhere to persist and query selection state: [3](#0-2) [4](#0-3) 
The `DiffSelection` model that stores per-line selection is a flat `Set<number>` of "diverging" indices with no knowledge of hunk boundaries or expansion events: [5](#0-4) 
Nothing in `expandTextDiffHunk` or its caller `expandWholeTextDiff` remaps or invalidates these stored indices to account for the shift; only `hunk.unifiedDiffEnd` and the following hunks' `unifiedDiffStart`/`unifiedDiffEnd` are adjusted by `numberOfNewDiffLines`, not the expanded hunk's own start offset relative to its (now shifted) content.

### Impact Explanation
This is the same class of defect as the reported `getActiveTickIndex` bug: a lookup key/index that should track the entity's *new* position is instead left pointing at the position from before a structural change, so state (selection/inclusion) gets silently applied to the wrong entity (line). In Desktop's case that means: after a user expands a hunk upward (a routine action to see more surrounding context before staging a partial commit) and then partially (de)selects lines, the line ultimately staged/committed via `git apply --cached` (`applyPatchToIndex`) or discarded via `git apply` (`discardChangesFromSelection`) can be a different line than the one the user intended — silently corrupting what gets committed or discarded, with no error surfaced to the user. This matches the "silent corruption of what the user commits or pushes" impact category. A malicious repository author could increase the likelihood of triggering this by shaping file diffs (e.g., large files with sparse, widely separated changes) that naturally encourage users to expand hunks before doing partial-line commits/discards.

### Likelihood Explanation
Medium. Hunk expansion combined with partial line selection is a normal, commonly-used Desktop workflow (reviewing more context before staging specific lines). No exotic input is required beyond a repository whose file diffs are structured to make expansion likely; the bug then triggers deterministically from the described sequence (expand-up → select/deselect lines → commit or discard). I was not able to fully trace, within the available budget, whether a later call to `withSelectableLines` (seen used elsewhere with `DiffSelection`) recomputes and re-intersects selectable line sets on every diff update in a way that fully mitigates or instead exacerbates the desync (e.g., by silently dropping previously-selected lines rather than misapplying them to a different line) — this should be verified with a live session before treating severity as confirmed at "silently commits wrong content" versus "silently drops selection."

### Recommendation
When constructing the updated (expanded) hunk in `expandTextDiffHunk`, shift `unifiedDiffStart` (and consequently every downstream absolute-index computation for that hunk) to account for `numberOfLinesToAdd` when `isExpandingUp` is true, and/or re-key the `DiffSelection` state by content identity (e.g., original line number) rather than a diff-order absolute index that is invalidated by structural edits to the hunk list. Add a regression test that selects specific lines, expands the containing hunk upward, and asserts that the resulting patch still reflects the original line-level selection.

### Proof of Concept
1. Open a file with a modification whose surrounding hunk allows upward expansion (`DiffHunkExpansionType.Up`).
2. In the Changes view, select an individual line (or a subset) for partial commit, e.g. via `DiffSelection.withLineSelection(N, true)`.
3. Trigger "Expand hunk up" (calls `expandTextDiffHunk(diff, hunk, 'up', ...)`), which prepends `numberOfLinesToAdd` context lines while keeping `hunk.unifiedDiffStart` fixed: [6](#0-5) 
4. Commit the partial selection; `formatPatch` computes `absoluteIndex = hunk.unifiedDiffStart + lineIndex` and queries `file.selection.isSelected(absoluteIndex)` against the *old* stored index — now pointing at a different (shifted) line than the one originally selected in step 2, so the wrong line ends up in the generated patch applied via `git apply --cached`.

export function diffHunkForIndex(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): DiffHunk | null {
  const hunk = hunks.find(h => {
    return index >= h.unifiedDiffStart && index <= h.unifiedDiffEnd
  })
  return hunk || null
}

/**
 * Locate the diff line and hunk for the given (absolute) line number in the diff.
 */
function diffLineInfoForIndex(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): IDiffLineInfo | null {
  const hunk = diffHunkForIndex(hunks, index)
  if (!hunk) {
    return null
  }

  const line = hunk.lines[index - hunk.unifiedDiffStart]
  if (!line) {
    return null
  }

  return { hunk, line }
}
