## Title
Integer overflow in TcParser fast-table skip-entry count (uint16_t wraparound) corrupts field dispatch during binary parsing - (File: `src/google/protobuf/generated_message_tctable_lite_test.cc`)

## Summary
The SpiceDB advisory's failed invariant is a 16-bit unsigned counter that silently wraps around when the attacker-controlled cardinality of an input structure (relationship count) exceeds `65535`, causing the dispatch/chunking logic to compute wrong offsets and either skip elements or crash. The Protobuf C++ full runtime has a directly analogous invariant in its generated "tail-call" parse tables (`TcParseTableBase`): the number of 16-bit skip-map entries used to dispatch field numbers to parse handlers is tracked in a `uint16_t`, and when a message descriptor produces more than `65535` such entries, the count wraps, producing a corrupted skip/field-entry table that is then used during **untrusted binary parsing** to locate handlers for field numbers.

## Finding Description
The tail-call parser builds a `TcParseTableBase` with a "skip map" that maps field numbers to entries used for fast dispatch during `ParseFrom*`. The field/skip entry counts feeding this table are declared as `uint16_t` (e.g., `field_entry_offset`, `static_cast<uint16_t>(fields.size())`, `static_cast<uint16_t>(table_info.aux_entries.size())`) in `Reflection::CreateTcParseTable` [1](#0-0) . A regression test, `OobGenReproduction`, demonstrates that when a message schema is engineered (via widely spaced field numbers) so that the total number of generated skip-table entries reaches and overflows `65536`, the stored count wraps to a small value (`3` in the repro) [2](#0-1) . The test explicitly documents the mechanism: "We want to overflow the uint16_t entry count (65535)... entries[kWrappedCount] (entries[3]) is a filler entry ... Reinterpreted fstart = skipmap | (field_entry_offset << 16) ... We need target field number > fstart to trigger OOB" [3](#0-2) . The test then builds a `DynamicMessage`/`TcParseTable` from that schema and parses a crafted payload containing a field number chosen specifically to hit the wrapped, reinterpreted table slot, exercising the out-of-bounds/corrupted dispatch path during `ParseFromString` [4](#0-3) .

This mirrors the SpiceDB bug class precisely: a 16-bit counter used to determine chunk/dispatch boundaries for an attacker-influenced cardinality (number of skip entries, driven by field-number spacing/count in the schema) overflows without a bounds check, and the wrapped value is subsequently used as an index/offset during the actual dispatch of incoming data (field parsing), rather than during data content processing.

Where the analogy diverges: in Protobuf, the *schema* (message descriptor with its field numbers/spacing) is a trusted input per this analysis's threat model — an attacker sending bounded binary payloads to a fixed, compiled-in schema cannot control the field-number layout that determines skip-table sizing. The overflow is only reachable if the schema itself is attacker-influenced (e.g., building a `DynamicMessage`/pool from an externally supplied `FileDescriptorProto`, as the test does via `pool.BuildFile(file_proto)` with `EnforceProtoLimits(false)`), which is outside the "ordinary client sending bounded protobuf bytes against a trusted, compiled schema" exposure assumption stated in the rules.

## Impact Explanation
If reachable with a fixed/trusted schema, a wrapped skip-table count would cause `TcParser` fast-path dispatch to read attacker-supplied field-number tags against a corrupted/undersized table, potentially reading out-of-bounds memory or misrouting field parsing (analogous to SpiceDB's "checks that should deny are allowed" / crash outcome). However, because the overflow is driven by the number of skip entries generated from the **descriptor's field layout** (not by data received at parse time for a fixed schema), a normal client cannot trigger it against a compiled-in, trusted `.proto` schema. It is only demonstrated using `DescriptorPool::EnforceProtoLimits(false)` plus an attacker-supplied `FileDescriptorProto` with deliberately wide field-number spacing — i.e., a hostile-schema scenario explicitly excluded by the rules.

## Likelihood Explanation
Low under the stated threat model. Reaching the wrap requires control over the message descriptor (field numbers/spacing) sufficient to produce ≥65536 skip entries, which is not possible for an "ordinary client sending bounded binary protobuf against a supported public parse API" with a trusted, pre-compiled schema. It is only demonstrated via `DynamicMessageFactory` + `DescriptorPool::EnforceProtoLimits(false)` with an attacker-controlled `FileDescriptorProto`, which is a hostile-schema/internal-API scenario excluded per the rules.

## Recommendation
Given the trust boundary, no action is required for normal parse-API consumers using compiled-in schemas. For any code path that builds `TcParseTableBase`/dynamic messages from untrusted `FileDescriptorProto` input, ensure `DescriptorPool::EnforceProtoLimits` remains enabled (default) and add explicit bounds checks/`ABSL_CHECK` in `generated_message_tctable_gen.cc`/`Reflection::CreateTcParseTable` on the skip-entry and field-entry counts before narrowing them to `uint16_t`, rather than relying on silent truncation.

## Proof of Concept
The existing regression test is the concrete reproduction: it builds a `DescriptorPool` with `EnforceProtoLimits(false)`, constructs a `FileDescriptorProto` with `kNumFields` fields spaced to make the cumulative skip-table entry count overflow `uint16_t` (wrapping to `3`), builds a `DynamicMessage` from it, and calls `msg->ParseFromString(payload)` with a crafted tag (`kTargetFieldNumber = 131072`) chosen to land on the corrupted, reinterpreted table slot [5](#0-4) . This test exists specifically to catch/guard this OOB scenario ("OobGenReproduction"), confirming the underlying `uint16_t` overflow is a recognized, real code-path issue in the parse-table generator, gated behind non-default, untrusted-schema conditions.

TEST(TcParserTest, OobGenReproduction) {
  constexpr int kStartFieldNumber = 33;
  constexpr int kFieldSpacing = TailCallTableInfo::kMaxSkipEntrySpacing;

  constexpr int kTargetSkipEntryNum = 0xFFFF;
  constexpr int kTargetDistance = kTargetSkipEntryNum * /* bits-per-entry */ 16;
  constexpr int kLastStepSpacing = kTargetDistance % kFieldSpacing;

  // Each field spaced kFieldSpacing apart adds (kFieldSpacing / 16) entries
  // to the skip table block.
  constexpr int kEntriesPerField = kFieldSpacing / 16;

  // We want to overflow the uint16_t entry count (65535).
  // The first field adds 1 entry, and each subsequent field adds
  // kEntriesPerField. We want total_entries >= 65536 to overflow. 1 +
  // kEntriesPerField * (kNumFields - 1) >= 65536 kNumFields - 1 >= (65536 - 1)
  // / kEntriesPerField (round up)
  constexpr int kTargetEntries = 65536;
  constexpr int kNumFields =
      (kTargetEntries - 1 + kEntriesPerField - 1) / kEntriesPerField + 1;

  // The count wraps to:
  constexpr int kTotalEntries = 1 + kEntriesPerField * (kNumFields - 1);
  constexpr int kWrappedCount = kTotalEntries % 65536;
  static_assert(kWrappedCount == 3,
                "Wrapped count must be 3 to trigger the bug");

  // entries[kWrappedCount] (entries[3]) is a filler entry for the first field.
  // Filler entries have skipmap = 0xFFFF and field_entry_offset = 1.
  // Reinterpreted fstart = skipmap | (field_entry_offset << 16) =
  // 0xFFFF | (1 << 16) = 131071. We need target field number > fstart to
  // trigger OOB.
  constexpr int kReinterpretedFstart = 0xFFFF | (1 << 16);
  constexpr int kTargetFieldNumber = kReinterpretedFstart + 1;  // 131072

  FileDescriptorProto file_proto;
  file_proto.set_name("poc.proto");
  file_proto.set_syntax("editions");
  file_proto.set_edition(Edition::EDITION_2023);

  DescriptorProto* message_proto = file_proto.add_message_type();
  message_proto->set_name("M");

  int fnum = kStartFieldNumber;
  for (int i = 0; i < kNumFields; ++i) {
    FieldDescriptorProto* field = message_proto->add_field();
    field->set_name(absl::StrCat("f_", i));
    field->set_number(fnum);
    field->set_label(FieldDescriptorProto::LABEL_OPTIONAL);
    field->set_type(FieldDescriptorProto::TYPE_INT32);

    // We need to adjust one of them to ensure exact 0xFFFF overflow.
    fnum += i == kNumFields - 2 ? kLastStepSpacing : kFieldSpacing;
  }

  DescriptorPool pool;
  pool.EnforceProtoLimits(false);
  const FileDescriptor* file_desc = pool.BuildFile(file_proto);
  ASSERT_NE(file_desc, nullptr);

  const Descriptor* desc = file_desc->FindMessageTypeByName("M");
  ASSERT_NE(desc, nullptr);

  DynamicMessageFactory factory(&pool);
  std::unique_ptr<Message> msg(factory.GetPrototype(desc)->New());

  std::string payload;
  {
    io::StringOutputStream output(&payload);
    io::CodedOutputStream coded_output(&output);
    coded_output.WriteVarint32(WireFormatLite::MakeTag(
        kTargetFieldNumber, WireFormatLite::WIRETYPE_VARINT));
    coded_output.WriteVarint32(1);  // value
  }

  (void)msg->ParseFromString(payload);
