### Title
`PreviousStateMachineHeight` is silently overwritten by successive honest updates, so a fisherman veto of a stale-but-still-fraudulent height rolls `LatestStateMachineHeight` back to the wrong safety point instead of blocking it - ([File: modules/pallets/ismp/src/host.rs])

### Summary
`store_latest_commitment_height` caches only a single "previous height" watermark per state machine, and every call to it unconditionally overwrites that watermark with whatever was `LatestStateMachineHeight` a moment ago — exactly the same "cache clobbered on repeated calls" defect described in the external `CashAsset.socializeLoss()` report. In Hyperbridge this watermark is not just an economic parameter; `delete_state_commitment` (triggered by a fisherman's `veto_state_commitment`) uses it to decide what height to roll `LatestStateMachineHeight` back to when the currently-latest height is vetoed.

### Finding Description
`store_latest_commitment_height` in `modules/pallets/ismp/src/host.rs` implements the "advance and remember what came before" pattern: [1](#0-0) 

Every accepted consensus update overwrites `PreviousStateMachineHeight` with the height that was current *just before this call*, regardless of whether that prior height itself is still trusted or has already been superseded by a second update in the same block/session. There is no check that the previous height has cleared its challenge period, or that no fraud has been reported against it, before it becomes the new "safe" rollback target.

This single watermark is then consumed by `delete_state_commitment`, the function a fisherman's veto calls: [2](#0-1) 

Consider a state machine that receives two consecutive honest-looking updates in quick succession, `H1` then `H2` (both greater than the prior latest height, e.g. a relayer batching two state proofs before the fishermen's polling loop reacts):

- After `H1` commits: `PreviousStateMachineHeight = H0` (old latest), `LatestStateMachineHeight = H1`.
- After `H2` commits: `PreviousStateMachineHeight = H1`, `LatestStateMachineHeight = H2`. `H1`'s own "previous" value (`H0`) is gone — clobbered exactly like `previousSmFeePercentage` in the reference bug.

If a fisherman later determines `H1` was fraudulent and calls `veto_state_commitment(H1)`, `delete_state_commitment` only rolls `LatestStateMachineHeight` back to `PreviousStateMachineHeight` **when `height == LatestStateMachineHeight` at veto time**:

```
if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
    if latest == height.height {
        let prev_height = PreviousStateMachineHeight::<T>::get(height.id)...
        LatestStateMachineHeight::<T>::insert(height.id, prev_height);
    }
}
```

Since `latest` is now `H2`, not `H1`, this branch does **not** fire — the safety-check comment even calls this out ("technically any state commitment can be vetoed, safety check that it's the latest before resetting it"). The commitment for `H1` is deleted from the trusted-commitment map, but `LatestStateMachineHeight` stays pinned at `H2`. Because the watermark only ever tracks one predecessor, there is no mechanism that also unwinds `H2` (which was accepted while `H1` was the trusted "latest", and whose own consensus verification chained off it) — `H2` continues to be treated as canonical, and state/receipt proofs built against `H2` remain acceptable for request/response delivery on Hyperbridge.

This is compounded by the test suite's own admission that the watermark degrades under exactly this kind of resubmission/rollback sequencing — `reward_covers_only_unpaid_heights_after_rollback` demonstrates the pointer being carried forward "stale" across a veto-then-resubmit cycle: [3](#0-2) 

### Impact Explanation
`LatestStateMachineHeight`/`state_machine_commitment` values are the trust anchor Hyperbridge uses to accept incoming state proofs for cross-chain requests/responses. If a fraudulent height can be vetoed without invalidating the newer height that was built (and accepted) on top of it, false remote state remains trusted after the fisherman mechanism believes it has removed it — a direct violation of the "false proof/state acceptance" bounty criterion. Any request or response whose proof is verified against the still-latest (but downstream-of-fraud) commitment would be wrongly accepted, which can be leveraged for unauthorized execution or fund loss on modules (bandwidth, intents, relayer withdrawals, token gateways) that trust Hyperbridge's state-machine commitments.

### Likelihood Explanation
Triggering this requires only ordinary, permissionless conditions already present in the protocol design: two state updates landing for the same state machine before the fisherman veto for the first one lands (a realistic race given the fisherman's polling cadence and normal relayer batching of multiple heights), followed by a single honest fisherman veto call, which is itself a normal, expected operation with no special privilege beyond being an active collator. No malicious relayer, prover, or governance actor is required — the flaw is in the bookkeeping logic itself, not in trusting a compromised party.

### Recommendation
Do not collapse rollback state into a single scalar watermark. Either:
- Maintain a bounded history/queue of prior heights (mirroring the existing `StateCommitmentQueue`) so `delete_state_commitment` can walk back to the last height that is *not itself downstream of the vetoed height*, or
- When vetoing a height that is not the current latest, cascade the veto to invalidate every height greater than the vetoed one for that state machine (since they were accepted on top of state that is now known to be fraudulent), rather than silently leaving `LatestStateMachineHeight` untouched.

### Proof of Concept
1. Configure a state machine and drive two accepted consensus updates for heights `H1 < H2` in succession (as in `store(10); store(11);` pattern used in `vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early`).
2. Call `pallet_fishermen::veto_state_commitment(H1)`.
3. Observe: `pallet_ismp::LatestStateMachineHeight::<T>::get(id)` still returns `H2`, and `state_machine_commitment(H2)` still resolves successfully, even though `H2` was built while `H1` (now proven fraudulent) was the trusted state.
4. Submit any request/response proof against `H2` — it verifies successfully despite the underlying fraud not being fully unwound. [4](#0-3) [5](#0-4)

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}

	fn freeze_consensus_client(&self, client: ConsensusStateId) -> Result<(), Error> {
		FrozenConsensusClients::<T>::insert(client, true);
		Ok(())
	}

	fn store_latest_commitment_height(&self, height: StateMachineHeight) -> Result<(), Error> {
		let previous_height = LatestStateMachineHeight::<T>::get(height.id).unwrap_or_default();
		PreviousStateMachineHeight::<T>::insert(height.id, previous_height);
		LatestStateMachineHeight::<T>::insert(height.id, height.height);
		Ok(())
	}

		pub fn veto_state_commitment(
			origin: OriginFor<T>,
			height: StateMachineHeight,
		) -> DispatchResult {
			let account = ensure_signed(origin)?;
			ensure!(T::IsCollator::contains(&account), Error::<T>::UnauthorizedAction);

			let ismp_host = <T as Config>::IsmpHost::default();
			let commitment =
				ismp_host.state_machine_commitment(height).map_err(|_| Error::<T>::VetoFailed)?;
			ismp_host.delete_state_commitment(height).map_err(|_| Error::<T>::VetoFailed)?;

			Self::deposit_event(Event::StateCommitmentVetoed {
				height,
				commitment,
				fisherman: account.clone(),
			});
			pallet_ismp::Pallet::<T>::deposit_event(
				ismp::events::Event::StateCommitmentVetoed(StateCommitmentVetoed {
					height,
					fisherman: account.as_ref().to_vec(),
				})
				.into(),
			);

			Ok(())
		}
