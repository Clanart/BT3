### Title
SignableTransaction trusts the recorded `ReceivedOutput` value instead of the actual outpoint value, so stale/forged bookkeeping yields an unspendable signed transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The FraxSwap report describes a class of bug where internal bookkeeping of a balance is trusted even though the real balance has changed externally, causing transfers/withdrawals to fail. `SignableTransaction` exhibits the same class: it treats the `TxOut` embedded in each `ReceivedOutput` (deserializable from arbitrary bytes via `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122`) as ground truth for both the fee/change math and the sighash `Prevouts::All` commitment, without ever checking the value against the actual on-chain output.

### Finding Description
In `SignableTransaction::new` (send.rs:150), `input_sat` is summed from `input.output.value` (send.rs:175), and this same recorded `TxOut` is stored in `self.prevouts` (send.rs:253). During signing, `TransactionSignMachine::sign` commits to these prevouts via `Prevouts::All(&self.tx.prevouts)` (send.rs:375), which binds every input's *claimed* amount into the BIP-341 sighash. The only integrity check, `SignableTransaction::multisig` (send.rs:277), verifies the prevout's `script_pubkey` matches `key + offset*G` — it never verifies the `value` or that the `outpoint` still holds that amount on-chain.

Analogous to a rebasing token draining the pair's real balance while internal accounting stays fixed, the recorded `TxOut.value` can diverge from the chain: a `ReceivedOutput` read from untrusted bytes (`ReceivedOutput::read`, listed in-scope) can carry a valid outpoint and valid script_pubkey but an inflated value. The inflated `input_sat` then (a) bypasses the `NotEnoughFunds` check at send.rs:215, and (b) inflates the change output at send.rs:228-230, so the final transaction's outputs exceed the real input value. The resulting fully-signed transaction commits to a false `Prevouts::All` amount and is consensus-invalid — every honest signer produced a signature share for a transaction that can never confirm, exactly mirroring the report's "transfer reverts / funds locked until tokens are sent in" outcome.

### Impact Explanation
The multisig signs and "completes" a transaction that Bitcoin consensus rejects (sighash prevout amounts must equal actual UTXO amounts under `Prevouts::All`). Funds are reported as spendable inputs but are not actually spendable through this flow; the UTXOs remain on-chain, but the signing round is burned and all subsequent withdrawal attempts built on the same stale/forged bookkeeping fail identically — matching the report's exhaustion/revert scenario. No funds are stolen; severity is Medium (liveness/funds-availability loss reachable via untrusted deserialization input).

### Likelihood Explanation
Reachability requires an untrusted party to supply `ReceivedOutput` bytes into the wallet-signing path (explicitly in scope per the rules covering `ReceivedOutput::read`) or for bookkeeping to go stale relative to the chain. The honest `Scanner` path (`scan_transaction`, mod.rs:199) always copies the real on-chain `TxOut`, so exploitation depends on the deserialization/API entry point; hence Medium rather than High likelihood.

### Recommendation
When constructing `SignableTransaction`, validate each `ReceivedOutput`'s recorded `value`/`script_pubkey` against the referenced outpoint (e.g., by fetching the prevout via RPC, or by committing to a verified prevout set) rather than trusting embedded bookkeeping. Alternatively, document that `ReceivedOutput`s must only originate from the trusted `Scanner` and must not be accepted from deserialized/untrusted sources.
