### Title
Panic on duplicate encryption-key registration message causes node DoS in PedPoP DKG - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::register` enforces "at most one encryption-key message per participant" with an `assert!` instead of a recoverable error. An unprivileged DKG participant who broadcasts a second `EncryptionKeyMessage` (readable via `EncryptionKeyMessage::read` from untrusted bytes) causes every honest peer that processes it to panic, aborting the key-generation session — the Rust analog of CVE-2025-61105's NULL-deref DoS triggered by a crafted wire message.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Decryption::register` (lines 352–362) executes:

```rust
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
```

`enc_keys` is a `HashMap<Participant, C::G>` populated only by calls to `register`, which is reached through `Encryption::register` (line 452) after the caller deserializes a peer-supplied `EncryptionKeyMessage` via `EncryptionKeyMessage::read` (line 57). The read path performs no deduplication or validity checks on the sender's identity — the sender identity is supplied by the calling protocol layer, which forwards one registration per received broadcast message.

The analogous guard for duplicate `Commitments` is documented as the caller's responsibility in `crypto/dkg/pedpop/src/lib.rs:98-101`, but the duplicate-`EncryptionKeyMessage` case is handled by a hard `assert!` inside the library itself. Because PedPoP participants already broadcast at least two message types (the `EncryptionKeyMessage` and later `Commitments`/share messages), a malicious (or merely buggy/reconnecting) participant can cause a second registration for the same `Participant` index — e.g., by sending their key-registration message twice, or by an honest coordinator that retries/replays a registration into a fresh `Decryption` that already holds it — and the second call panics.

The same pattern exists at `decrypt_with_proof` (line 388), which indexes `self.enc_keys[&decryptor]` directly: if the decryptor's registration was never recorded (e.g., dropped after a partial session), the blame/decryption path panics on a missing key instead of returning an error.

### Impact Explanation
A panic in `Decryption::register` unwinds through (or aborts) the host process running the DKG. In a validator/processor deployment this kills the key-generation attempt for the whole set, and a persistent malicious participant can repeat it every session, indefinitely preventing new key generation — a remote, unauthenticated-party-triggered denial of service. This matches the CVE bug class (reachable crash on crafted peer input); Rust panics are the direct analog of the NULL dereference. Severity: High DoS; no secret leakage.

### Likelihood Explanation
Triggering requires only that a DKG participant's key-registration message be processed twice for the same `Participant` index. The library's own documentation acknowledges faulty/malicious participants are expected and handled as data (`Err`/blame) elsewhere; nothing in the read path or the message format makes a duplicate registration impossible — it is only "impossible" under the assumption the caller perfectly deduplicates, an assumption the code punts on (`as this library does not handle networking, it is unable to detect...`). Since the crash is inside library code rather than the caller's dedup logic, any caller that forwards messages faithfully is exposed.

### Recommendation
Return a typed error (e.g., `io::Error::other` or a dedicated `DkgError`/`DecryptionError` variant) from `register` instead of `assert!`, and treat a second registration either as idempotent-equal-check (same `enc_key` → Ok) or as explicit faulty-participant evidence surfaced to the caller. Similarly, replace `self.enc_keys[&decryptor]` in `decrypt_with_proof` with `get(...).ok_or(DecryptionError::...)`.

### Proof of Concept
```rust
// Attacker, participant j, sends EncryptionKeyMessage twice.
// Honest party i processes each message:
let mut decryption = Decryption::<C>::new(context);
let msg: EncryptionKeyMessage<C, M> =
  EncryptionKeyMessage::read(&mut wire_bytes, params)?; // untrusted bytes
decryption.register(attacker_id, msg.clone());           // first: Ok
// attacker rebroadcasts the same (or a second) message
let msg2 = EncryptionKeyMessage::read(&mut wire_bytes2, params)?;
decryption.register(attacker_id, msg2);                  // panic! at encryption.rs:356
```
