### Title
Gasless swap admission check validates `AmountIn` against a stale KIP-247 exchange rate while the actual repay/lend accounting is fixed at submission time, allowing `RepayAmount` collection to diverge from the real swap output - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The external report's bug class is: a value/limit check is performed on a *base* amount that omits a fee/delta that gets added afterward, so the final on-chain value can exceed what the check actually validated. The closest reachable analog in this Kaia codebase is in the gasless swap-for-gas admission path, where `checkBalanceForSwap` validates `AmountIn` against a `GetAmountIn(token, minAmountOut)` quote taken from **current** state at tx-pool admission time, but the `AmountRepay` that the lending mechanism collects is a value the user freely picks at submission time (only checked against `MinAmountOut`, not against the router's live pricing at execution time).

### Finding Description
In the gasless flow, a validator "lends" KAIA gas money to a sender via a synthetic `LendTx` and expects to be repaid via the swap transaction's proceeds: [1](#0-0) 

`lendAmount` = `ApproveTx.Fee() + SwapTx.Fee()`. `repayAmount` = `LendTx.Fee() + lendAmount`. The only correctness check tying the user-declared `AmountRepay` to reality is: [2](#0-1) 

which ensures `SwapTx.AmountRepay == repayAmount(...)` — a purely arithmetic identity based on gas prices, not on whether the swap will actually produce enough output. The only check that ties `AmountIn`/`MinAmountOut` to the AMM's real exchange rate is optional and performed once, at tx-pool admission time, using the *current* router state: [3](#0-2) 

This `ShouldCheckSwapAmount()` gate is configurable (`g.GaslessConfig.ShouldCheckSwapAmount()`), and even when enabled, it merely verifies `AmountIn >= requiredAmountIn` for the `MinAmountOut` declared by the transaction — it does not re-verify at execution/block-assembly time. Because the tx can sit in the pool, be requeued, or be included several blocks later (subject only to `QueueTimeout`/`PendingTimeout`), the AMM price can move between the admission-time check and actual inclusion. If `MinAmountOut` (and therefore the checked `AmountIn`) is set to just barely satisfy `MinAmountOut >= AmountRepay`, and the pool/quote moves unfavorably before inclusion, the swap can settle for less than `AmountRepay`, or on-chain `swapForGas` slippage protection may cause a revert; but the fee-lending outlay (`LendTx`) is already broadcast/bundled with the swap unconditionally by `ExtractTxBundles`: [4](#0-3) 

This mirrors the report's pattern precisely: the admission-time check (analogous to `totalSupply.add(_amount) <= maxCap`) is computed from a *base*/quoted amount, while the actually-collected/repaid amount is a separately user-supplied value (`AmountRepay`) that is only checked for self-consistency with fee math, not against the live, at-inclusion market state that determines whether the "repay" can really be extracted without loss to the lender (the block proposer/validator advancing the `LendTx`).

### Impact Explanation
If the pool price moves between the tx-pool admission-time `GetAmountIn` check and actual block inclusion (a normal AMM condition, exploitable by anyone submitting the gasless bundle and then trading against the pool, or simply due to time-of-check/time-of-use skew), the swap can execute with less favorable terms than assumed when the `LendTx` amount was computed and broadcast. Because the lending amount (`lendAmount`) is fixed off-chain at bundle construction, not derived from the swap's actual settlement, a validator/proposer that advances gas on behalf of the sender can end up under-repaid relative to what was lent, since the swap's success is protected only by `minAmountOut` at the AMM level, not by a live-repricing of the whole gasless bundle's economics at inclusion time. This is a fee/repay-abuse-class issue as scoped by the task's "gasless and auction modules" category, causing potential value leakage between the assumed and actual repay to the fee-lending party.

### Likelihood Explanation
Medium: the `ShouldCheckSwapAmount` check is admission-time only and not re-verified per block; the time window between mempool admission and inclusion (bounded by `QueueTimeout`/`PendingTimeout`, i.e., up to 10 seconds, but potentially longer if repeatedly requeued via `PreReset`/`PostReset`) is enough for AMM prices to move on any actively traded pool, especially since KIP-247's `GetAmountIn` is a spot-price quote with no time-weighted averaging protection referenced in this code path. Any unprivileged sender can construct an approve+swap bundle at the edge of the check's tolerance, requiring no special privileges beyond normal transaction submission.

### Recommendation
Re-validate `AmountIn`/`MinAmountOut` against the router's exchange rate at block-assembly/inclusion time (not just at tx-pool admission), or bind the `LendAmount`/`RepayAmount` accounting to the swap's actual settlement result rather than to values fixed at bundle-construction time. Consider tightening `ShouldCheckSwapAmount` to be mandatory (not configurable) and adding a maximum staleness/slippage margin so the quoted `requiredAmountIn` cannot drift arbitrarily from the price realized at inclusion.

### Proof of Concept
1. Attacker holds an ERC-20 token in the gasless whitelist and constructs an `approve` + `swapForGas` bundle where `MinAmountOut` is set exactly to `AmountRepay` (the minimum allowed by the `minAmountOut.Cmp(amountRepay) < 0` check in `checkBalanceForSwap`, `kaiax/gasless/impl/tx_pool.go:118`).
2. The bundle passes `checkBalanceForSwap`'s `GetAmountIn` check using the current pool state; `AmountIn` is the minimal amount satisfying the quote at that instant.
3. The transaction sits in the pool (or is intentionally resubmitted/paced) while the attacker (or an unrelated third party) trades against the same AMM pool, shifting the exchange rate unfavorably for the pending swap.
4. When later included, the swap either reverts (if the AMM's own `minAmountOut` protection triggers, wasting the proposer's already-lent gas since `LendTx` was bundled unconditionally per `ExtractTxBundles`) or settles with output just at `AmountRepay`, leaving no safety margin against price movement that occurred between quoting and inclusion — unlike a correct design that would re-derive/re-check the required amounts against state at inclusion time.

Note: I was not able to fully trace the KIP-247 `GaslessSwapRouterCaller.GetAmountIn`/`swapForGas` on-chain contract logic (not indexed in this codebase snapshot) to confirm whether the AMM contract itself enforces additional protections beyond `minAmountOut`; a Devin session with full repository/contract access would be needed to conclusively verify whether on-chain slippage protection independently closes this gap.

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}

func (g *GaslessModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	// there are only at most two gasless transactions in pending for a sender
	bundles := []*builder.Bundle{}
	approveTxs := map[common.Address]*types.Transaction{}
	targetTxHash := common.Hash{}
	for _, tx := range txs {
		addr, err := types.Sender(g.signer, tx)
		if err != nil {
			continue
		}
		if g.IsApproveTx(tx) {
			approveTxs[addr] = tx
		} else if g.IsSwapTx(tx) && g.IsExecutable(approveTxs[addr], tx) {
			bundleTxs := builder.NewTxOrGenList(g.GetLendTxGenerator(approveTxs[addr], tx))
			if approveTxs[addr] != nil {
				bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(approveTxs[addr]))
			}
			bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(tx))

			b := builder.NewBundle(
				bundleTxs,
				targetTxHash,
				false,
			)

			targetTxHash = tx.Hash()

			isConflict := false
			for _, prev := range append(prevBundles, bundles...) {
				if prev.IsConflict(b) {
					isConflict = true
					break
				}
			}
			if isConflict {
				// Gasless transactions will just fail even if they aren't bundled.
				continue
			}
			bundles = append(bundles, b)
		} else {
			targetTxHash = tx.Hash()
		}
	}
	return bundles
}
