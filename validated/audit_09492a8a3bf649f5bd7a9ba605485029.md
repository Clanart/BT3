### Title
Unauthenticated blame evaluation lets anyone convict an honest DKG participant - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` attribute fault to the `recipient` whenever the supplied `EncryptionKeyProof` is missing or fails verification. There is no check that the party invoking blame is actually the message's recipient, and `AdditionalBlameMachine` is explicitly constructed so non-participants can evaluate blame. Any observer can therefore submit an accusation `(sender, recipient)` over a perfectly valid encrypted share with `proof = None` (or garbage) and obtain a verdict marking an honest `recipient` as faulty — a forged blame verdict with no cryptographic evidence behind it.

### Finding Description
`AdditionalBlameMachine::new` takes only the public commitment messages and states it is "capable of evaluating Blame regardless of if the caller was a member in the DKG protocol" (`crypto/dkg/pedpop/src/lib.rs:639-662`). `blame_internal` then resolves fault purely from the message and the optional proof (`crypto/dkg/pedpop/src/lib.rs:575-609`):

```rust
let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
  Ok(share_bytes) => share_bytes,
  Err(DecryptionError::InvalidSignature) => return sender,
  Err(DecryptionError::InvalidProof) => return recipient,   // <- reached for proof: None
};
```

`Decryption::decrypt_with_proof` returns `InvalidProof` whenever `proof` is `None` (`crypto/dkg/pedpop/src/encryption.rs:381-396`). Nothing binds the accuser's identity to `recipient`, and nothing requires the accuser to demonstrate knowledge of the correct ECDH key before `recipient` is declared the liar. The verdict semantics encode "the accuser is the recipient, and they failed to produce the decryption key, so they lied" — but the accuser's identity is never verified, so the library will emit that verdict for an accusation fabricated by a third party naming an arbitrary honest `recipient`.

The downstream consumer treats the returned `Participant` as the faulty party: `CoordinatorMessage::VerifyBlame` runs `AdditionalBlameMachine::new(...).blame(accuser, accused, share, blame)` and emits `ProcessorMessage::Blame { participant: accuser }` or `{ participant: accused }` accordingly (`processor/src/key_gen.rs:504-563`), and `Transaction::InvalidDkgShare` handling leads to `fatal_slash` on the blamed key (`coordinator/src/tributary/handle.rs:461-505`). Notably, the processor passes `(accuser, accused)` as `(sender, recipient)`, inverting the documented library semantics ("a copy of the encrypted secret share from the accused sender to the accusing recipient"), so the share actually evaluated is the accuser's own outbound share — a valid share which still resolves blame against `accused` via the `InvalidProof`/`valid share → recipient` branches.

### Impact Explanation
Any party able to feed an `EncryptedMessage` and `Option<EncryptionKeyProof>` into `blame`/`AdditionalBlameMachine::blame` can obtain a verdict declaring an honest participant faulty, without any valid decryption proof. In Serai's usage this maps to a fatal slash of an honest validator's key and abort of the DKG, i.e., an unauthorized party successfully "claiming" a conviction (and the associated slashing of stake) that only the true recipient — the sole holder of the ECDH private key — should be able to substantiate. This is the same class as the report: a claim path gated only on participation/authenticity of the message, with no authorization check on who may invoke it.

### Likelihood Explanation
Reachable by anyone holding the DKG transcript: commitment messages and the published `EncryptedMessage`s are sufficient to instantiate `AdditionalBlameMachine::new` and call `blame`, and an in-set signer can route the same primitive through `VerifyBlame`/`InvalidDkgShare` since `accuser` only needs to lie within the signer's own `Participant` range (`coordinator/src/tributary/handle.rs:467-484`). No secret knowledge is required: choosing `proof = None` always drives `decrypt_with_proof` to `InvalidProof` → `recipient` blamed. Likelihood is bounded by requiring a live DKG session, and slash resolution may be subject to set consensus, but the cryptographic precondition is trivially satisfiable.

### Recommendation
Bind the accuser to the verdict. `blame` should (a) require a valid `EncryptionKeyProof` before ever returning `recipient` as faulty — with `proof: None`, only `sender` (invalid PoP/encoding) should be blamable; and (b) have callers authenticate that the accusing party is the `recipient`, e.g., by requiring the DLEq proof to be generated against `recipient`'s registered `enc_keys` entry (already done) plus a signature/PoP from `recipient`'s encryption key attesting to the accusation. The processor should also pass `(accused, accuser)` to `blame` to match the documented sender/recipient semantics.

### Proof of Concept
1. Complete (or observe) any PedPoP DKG round: collect each participant's `EncryptionKeyMessage<Commitments>` and a valid `EncryptedMessage<SecretShare>` from honest `sender` S to honest `recipient` R.
2. Construct `AdditionalBlameMachine::new(context, n, commitment_msgs)`.
3. Call `.blame(S, R, msg_S_to_R.clone(), None)`. `decrypt_with_proof` verifies S's PoP (valid), sees `proof.is_none()`, returns `InvalidProof`, and `blame` returns `R` — honest R is adjudicated the faulty party, with zero evidence.
4. Equivalently, pass a randomly generated `EncryptionKeyProof`: the DLEq verification fails → `InvalidProof` → `R` blamed again.

In the deployed flow, a signer submits `Transaction::InvalidDkgShare { accuser: own_index, faulty: victim, blame: None }`; `DkgShare::get`/`EncryptedMessage::read` succeed (the stored accuser→victim share is well-formed), `VerifyBlame` runs `blame(accuser, victim, share, None)`, `blame_internal` returns `victim` via `InvalidProof`, and the processor emits `ProcessorMessage::Blame { participant: victim }`, fatally slashing an honest participant for an accusation anyone could fabricate.
