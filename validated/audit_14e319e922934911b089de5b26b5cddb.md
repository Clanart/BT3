### Title
`ThresholdKeys::read` deserializes `secret_share` and `verification_shares` without ever checking their consistency, letting attacker-supplied bytes install a key whose group secret the attacker knows - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The external report is insecure deserialization (CWE-502): attacker-controlled bytes are deserialized and trusted without validating that the resulting object is semantically sound. The direct analog in Serai is `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), which reconstructs a fully operational `ThresholdKeys` from raw bytes — `t`, `n`, `i`, an `Interpolation`, a `secret_share` scalar, and `n` verification-share points — and passes them to `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`). `new` only checks the *count* and *index range* of the verification shares (`:355-365`) and the applicability of the interpolation mode (`:367-374`). It never verifies that `verification_shares[i] == secret_share * G` for the local participant, nor that the shares form a consistent Shamir commitment set. The group key is then computed purely from the attacker-supplied `verification_shares` (`:376-378`). This is a CWE-502 analog: deserialization produces a semantically invalid object that is trusted as authoritative key material.

### Impact Explanation
Whoever controls the serialized bytes controls the resulting `ThresholdKeys` in arbitrary ways:

- **Attacker-known group secret**: an attacker supplies a `secret_share` and `verification_shares` for a polynomial they chose. The derived `group_key` (`crypto/dkg/src/lib.rs:377-378`, `:445-447`) is then a key whose discrete logarithm the attacker knows. Any FROST/MuSig/Taproot outputs addressed to this group key are spendable by the attacker alone — funds reported received under this key are not safely spendable by the threshold.
- **Forged signature outcome / share confusion**: the attacker can set the victim's `secret_share` to a value inconsistent with `verification_shares[i]`. In `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:447-495`), the victim's valid-looking share then fails aggregate verification, and the code itself acknowledges the only way to reach the "everyone had a valid share yet the signature was still invalid" error is "to deserialize a semantically invalid FrostKeys" (`crypto/frost/src/sign.rs:491-494`) — i.e., this inconsistency is a known possible state the library produces without warning at deserialization time.
- **Constant-interpolation malleability**: with `Interpolation::Constant`, the `n` deserialized scalars (`:607-613`) directly become per-participant additive coefficients; a malicious blob can craft coefficients that give the attacker a known effective share while still satisfying `t == n`.

Severity: High — key-share/group-key substitution through untrusted deserialized state, with loss-of-funds impact when the blob seeds a Bitcoin/Monero-style vault key.

### Likelihood Explanation
`ThresholdKeys::read` is the canonical restoration path for threshold key material (e.g., a node loading keys supplied by an operator, backup, recovery coordinator, or any external store). The prompt's reachability rule explicitly admits untrusted bytes fed to `ThresholdKeys::read`. No signature, MAC, or self-consistency check binds the serialized blob to the party that produced it: `read` accepts any byte stream of the right shape, and `write`/`serialize` produce no authentication tag (`crypto/dkg/src/lib.rs:538-562`). Any deployment where the key blob can be influenced by an unprivileged party — an untrusted backup provider, a recovery service, a config store — reaches this path directly. Likelihood is medium-high wherever keys are restored from externally supplied bytes rather than kept exclusively in a trusted enclave; it collapses to low only if the deployment guarantees the blob's authenticity out-of-band (which the format itself does not provide or document).

### Recommendation
- In `ThresholdKeys::new` (or at least in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[i]` for the local participant and, for `Interpolation::Lagrange`, that the shares interpolate consistently — e.g., reject if `group_key` computed from participants `1..=t` is identity, and document/require that verification shares come from an authenticated DKG transcript.
- Serialize a binding commitment (e.g., a hash of `group_key` and the DKG `context`) inside the blob and check it on read, so a blob forged independently of the original DKG is rejected.
- Document `ThresholdKeys::read` as requiring an authenticated/integrity-protected source, matching the warnings already present for `CachedPreprocess` (`crypto/frost/src/sign.rs:84-92`).
