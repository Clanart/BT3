## Finding: GitHub Desktop explicitly disables Git's built-in clone-time exploit protections [1](#0-0) 

### Title
GitHub Desktop force-disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard during recursive clones, re-enabling hook/config injection from malicious repositories - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment for every `git clone --recursive` invocation: [2](#0-1) 
This variable controls Git's internal defense-in-depth checks (added after the 2024 clone-time RCE disclosures, e.g. CVE-2024-32002/32004/32020/32021) that detect maliciously crafted repository layouts — such as symlinked, case-confusable, or nested `.git`/`.git/hooks`/`.gitmodules` paths inside submodules — which, when cloned recursively, can cause an attacker's payload to land inside the *real* `.git/hooks` directory of the resulting checkout and execute automatically on subsequent checkout/fetch operations. By setting this flag to `false`, Desktop opts every clone back into the vulnerable code path that upstream Git intentionally guards against.

### Finding Description
The broken invariant is: *"a freshly cloned repository's Git-internal metadata (hooks, config, submodule targets) cannot be attacker-controlled without the user's `--recursive` submodule content first passing Git's clone-protection checks."* Desktop breaks this invariant by disabling those checks globally via `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before invoking `clone`, which always runs with `--recursive`: [3](#0-2) 
The attacker primitive is identical in shape to the ERC‑1155 report's core class — a trusted operation (here, "clone a remote repository") is made to process attacker-supplied structured data (a maliciously nested submodule/`.git` layout) with a safety check purposefully switched off, allowing the attacker's payload to reach an execution surface (`git hooks`) that the operator (Desktop/the user) did not expect to be reachable at this stage.

None of Desktop's existing user-facing guards catch this:
- The "unsafe repository" ownership-based warning only fires for **already-existing local directories** being added via `AddExistingRepository`/`MissingRepository`, not for the destination of a brand-new `clone()` call: [4](#0-3) 
- `isClonePathSensitive()` only protects against the *destination path* being a sensitive system directory; it does nothing to validate the *content* fetched from the untrusted remote: [5](#0-4) 
- `withHooksEnv`/`getRepoHooks`/hooks-proxy only intercept hooks during operations explicitly listed by `interceptHooks` (commit, pull, push) — `clone()` passes no `interceptHooks` at all, so any hook that lands on disk via the disabled protection is never routed through the sandboxed hook proxy in the first place: [6](#0-5) 

### Impact Explanation
An attacker who controls a repository URL a victim clones through GitHub Desktop (e.g., a public repo the victim is directed to clone, or a submodule reachable from a repo the victim clones with the default `--recursive` behavior) can craft a submodule/`.git` structure that Git's clone protections would normally reject or neutralize. With those protections disabled, the crafted content can be written into the resulting repository's real hooks directory and get executed with the victim's OS privileges the next time Git or Desktop touches that repository (checkout, fetch, commit, etc.) — i.e., remote-triggered code execution originating purely from cloning a URL, satisfying the "attacker controls a cloned/fetched repository ... results in code execution" criterion.

### Likelihood Explanation
Cloning arbitrary repository URLs (including ones with submodules) is a core, everyday Desktop workflow, and `clone()` always requests `--recursive` with no opt-out, meaning every clone operation is affected. No unusual local access, prior malware, or leaked credentials are required — only that the victim clones a URL the attacker controls or that is nested as a submodule of a repo they clone.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (`app/src/lib/git/clone.ts`) so Git's built-in clone-time protections remain active. If a specific compatibility issue motivated disabling it, that issue should be root-caused and fixed without turning off the security check globally; at minimum the override should never apply to recursive clones of untrusted/remote URLs.

### Proof of Concept
1. Attacker publishes a Git repository (or a submodule referenced by a repository the victim will clone) that is crafted to exploit the class of clone-time issues Git's `GIT_CLONE_PROTECTION_ACTIVE` guard was built for (e.g., a submodule path/`.gitmodules` entry engineered to place a hook at the real `.git/hooks` path of the outer checkout on a case-insensitive filesystem).
2. Victim clones this repository (or a repository containing it as a submodule) via Desktop's "Clone repository" flow, which calls `clone()`: [7](#0-6) 
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` and `--recursive` is always used, Git does not apply the safety checks that would otherwise reject/neutralize the crafted layout.
4. The attacker-controlled hook is written to the real `.git/hooks` directory of the victim's newly cloned repository and executes with the victim's privileges on a subsequent Git operation (checkout/fetch/commit), all performed by Desktop.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
