### Title
Denial of Service via Unbounded Signature Array in Kaia Transactions Before Account-Key Limit Check - (File: blockchain/types/transaction.go)

### Summary
A remote, unauthenticated transaction sender can submit a syntactically-valid Kaia transaction (or use `eth_sendRawTransaction`) containing an oversized array of bogus `(V,R,S)` signature tuples. The node performs a full ECDSA public-key recovery for **every** signature in `tx.ValidateSender()` before the `MaxNumKeysForMultiSig` cap is enforced, allowing an attacker to force expensive cryptographic work on the node for a transaction that is guaranteed to be rejected and costs the attacker no gas.

### Finding Description
`TxPool.validateTx()` calls `tx.ValidateSender(pool.signer, pool.currentState, pool.currentBlockNumber)` [1](#0-0) . For non-legacy Kaia transactions, this invokes `SenderPubkey(signer, tx)`, which ultimately calls `TxSignatures.RecoverPubkey`, iterating over the *entire* signature slice and doing an elliptic-curve public-key recovery for each entry with no bound check: [2](#0-1) 

Only *after* all of these expensive recoveries complete does `tx.ValidateSender` call `accKey.SigValidationGas(currentBlockNumber, ..., len(pubkey))`: [3](#0-2) 

The `MaxNumKeysForMultiSig` (10) limit is enforced only inside `SigValidationGas`/`CheckInstallable`, i.e., after the fact: [4](#0-3) 

The only place `MaxNumKeysForMultiSig` gates the *number of signatures before* recovery is `NewTxSignaturesWithValues`, a local signing helper used only when the node itself constructs and signs a transaction — it is not part of the RLP-decoding or tx-pool admission path for externally-submitted, already-signed transactions: [5](#0-4) 

The tx-pool's only guard that limits signature count indirectly is the aggregate transaction-size check (`MaxTxDataSize`, 32 KiB), which runs *before* `ValidateSender` [6](#0-5) . Because each `(V,R,S)` signature RLP-encodes to roughly 70–100 bytes, an attacker can still pack several hundred garbage signatures into a single 32 KiB transaction, all of which get individually recovered via secp256k1 ECDSA-recover (a costly EC point operation) before the tx is finally rejected with `ErrMaxKeysExceedInValidation`.

### Impact Explanation
This matches the reported bug class (crafted payload causing resource-exhaustion DoS reachable by a low-privilege/unauthenticated actor): any public-RPC caller submitting `eth_sendRawTransaction` (or any tx broadcast reaching `TxPool.AddRemote`/`AddRemotes`) can force the node to spend CPU on hundreds of EC-recovery operations per crafted transaction, at essentially zero cost to the attacker because the transaction is always rejected before inclusion (no gas is ever charged). Repeated submission of such transactions (from many source addresses/nonces to bypass per-account or per-hash de-duplication) can degrade tx-pool throughput and overall node responsiveness for legitimate `AddRemote`/`AddRemotes` calls, which run under `pool.txMu` and block subsequent processing.

### Likelihood Explanation
High: this requires only crafting and RLP-encoding a transaction with an inflated signature array and posting it via a standard `eth_sendRawTransaction`/p2p tx broadcast — no special privileges, valid account key, or funded balance are needed to trigger the expensive recovery path, since the wasted computation happens before nonce/balance/account-key validity is even confirmed to be legitimate.

### Recommendation
Add an early, cheap bound check on `len(tx.RawSignatureValues())` (and any fee-payer signature array) against `accountkey.MaxNumKeysForMultiSig` immediately upon tx pool admission / RLP decode, before any `RecoverPubkey`/ECDSA-recovery work is performed in `ValidateSender`/`ValidateFeePayer`, mirroring the guard already present in `NewTxSignaturesWithValues`.

### Proof of Concept
1. Construct a Kaia transaction (e.g., `TxTypeValueTransfer` or `TxTypeFeeDelegatedValueTransfer`) targeting an arbitrary funded or unfunded `from` address.
2. Populate its `TxSignatures` field with several hundred garbage `(V,R,S)` tuples (values need not correspond to a real signature — ECDSA recovery succeeds and returns *some* public key even for non-matching signatures) such that total RLP size stays under `MaxTxDataSize` (32 KiB).
3. Submit the crafted, RLP-encoded transaction via `eth_sendRawTransaction` (public RPC) or broadcast it as a remote tx.
4. Observe that `TxPool.validateTx` → `tx.ValidateSender` performs one EC-recovery per signature entry before ultimately returning `kerrors.ErrMaxKeysExceedInValidation`; repeat with many such crafted transactions from different throwaway keys to amplify CPU load on the node without paying any transaction fee.

Note: I was unable to fully verify (within the available tool budget) whether any RLP-decoding-layer length cap exists elsewhere for `TxSignatures` prior to reaching `ValidateSender`; the code paths inspected (`blockchain/types/tx_signatures.go`, `blockchain/types/transaction.go`, `blockchain/tx_pool.go`) show no such cap before the expensive recovery loop.

func NewTxSignaturesWithValues(signer Signer, tx *Transaction, txhash common.Hash, prv []*ecdsa.PrivateKey) (TxSignatures, error) {
	if len(prv) == 0 {
		return nil, kerrors.ErrEmptySlice
	}
	if uint64(len(prv)) > accountkey.MaxNumKeysForMultiSig {
		return nil, kerrors.ErrMaxKeysExceed
	}
	txsigs := make(TxSignatures, len(prv))

	for i, p := range prv {
		t, err := NewTxSignatureWithValues(signer, tx, txhash, p)
		if err != nil {
			return nil, err
		}
		txsigs[i] = t
	}

	return txsigs, nil
}

func (t TxSignatures) RecoverPubkey(txhash common.Hash, homestead bool, vfunc func(*big.Int) *big.Int) ([]*ecdsa.PublicKey, error) {
	var err error

	pubkeys := make([]*ecdsa.PublicKey, len(t))
	for i, s := range t {
		pubkeys[i], err = s.RecoverPubkey(txhash, homestead, vfunc)
		if err != nil {
			return nil, err
		}
	}

	return pubkeys, nil
}

func (a *AccountKeyWeightedMultiSig) SigValidationGas(currentBlockNumber uint64, r RoleType, numSigs int) (uint64, error) {
	numKeys := uint64(len(a.Keys))
	if numKeys > MaxNumKeysForMultiSig {
		logger.Warn("validation failed due to the number of keys in the account is larger than the limit.",
			"account", a.String())
		return 0, kerrors.ErrMaxKeysExceedInValidation
	}
	if numKeys == 0 {
		logger.Error("should not happen! numKeys is equal to zero!")
		return 0, kerrors.ErrZeroLength
	}

	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul
	if isIstanbul {
		return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
	}
	return (numKeys - 1) * params.TxValidationGasPerKey, nil
}
