### Title
Pool can permissionlessly sweep already-farmed rewards to itself after a Plot NFT has already left/is leaving the pool - (File: `chia/pools/plotnft_drivers.py`)

### Summary
`PlotNFT.forward_pool_reward()` builds a spend of an already-farmed pool reward coin that pays the reward to the pool's `pool_puzzle_hash`. The authorization branch for this action (`pool_proven_spend()`) is a `FixedPuzzleMember` keyed only to the fixed tree hash of `claim_pool_reward_dpuz()` — it requires no signature at all (the accompanying test builds the spend bundle with `G2Element()`, i.e. no signature) [1](#0-0) . Because this authorization branch stays valid on the singleton for as long as `pool_config` is still present (i.e., through the entire `LEAVING_POOL`/waiting-room period, not just while actively `FARMING_TO_POOL`), the pool (or anyone constructing this exact spend) can redirect a reward coin to the pool even after the owner has already initiated `leave_pool()`, before the owner can claim it for themselves.

### Finding Description
`forward_pool_reward()` is only guarded by `if not self.pooling: raise ValueError(...)`, i.e. it is available whenever `pool_config is not None`, which covers both the `FARMING_TO_POOL` state and the `LEAVING_POOL`/waiting-room state (`exiting=True` while `pool_config` is still set) [2](#0-1) . Meanwhile `claim_pool_rewards()`, the function that lets the *owner* keep already-farmed rewards, explicitly refuses to run while `self.pooling` is true: `"Cannot claim rewards while pooling. If you're a pool, try forward_pool_rewards"` [3](#0-2) .

This creates a window, confirmed by the project's own test suite, where:
1. The owner calls `leave_pool()` (starts exiting the pool; `pool_config` is still set, `exiting=True`).
2. The owner cannot yet call `claim_rewards()` for a reward that was farmed to the singleton, because `pooling` is still true — this is proven directly by the test raising `"Cannot claim rewards while pooling..."` right after `leave_pool()` [4](#0-3) .
3. Anyone (no signature required) can call `forward_pool_reward()` on that same reward coin, sweeping it to the pool's puzzle hash, permanently removing it from the owner's balance. The test explicitly documents this outcome under the comment `# LOSE REWARDS (while leaving)`, and shows the plotnft wallet's confirmed/unconfirmed/spendable balances all decreasing by `POOL_REWARD_AMOUNT` as a result of a spend bundle signed with an empty `G2Element()` [5](#0-4) .

The root cause is the asymmetric authorization model: `pool_proven_spend()` requires only a `FixedPuzzleMember` structural match (no key/signature check) to redirect a reward coin to the pool [6](#0-5) , whereas the owner's own path (`claim_pool_rewards()`) is blocked during the same period by the `pooling` gate [7](#0-6) . There is no mechanism that revokes or narrows the pool's sweep authority once the owner has signaled intent to leave; the sweep authority is tied only to `pool_config is not None`, which persists through the full waiting-room/lock-height period.

### Impact Explanation
Reward coins that a Plot NFT owner has already earned on-chain (their block reward) can be redirected to the pool's puzzle hash without owner consent during the period between initiating a pool exit and the exit being finalized. Unlike a normal, expected "while farming to the pool, the pool gets the reward" behavior, this specific window is one where the owner has already declared intent to leave and cannot yet reclaim the coin themselves — yet the pool-side sweep path remains fully open and permissionless. This is a genuine, on-chain, unauthorized-redirection-of-value bug: value that should belong to the owner (post-declaration-of-exit) is diverted to a third party (the pool) with no recovery path for the owner, matching the "reward redirection" impact category. Severity is bounded by the value of individual un-swept reward coins during the exit window, but it is a concrete coin-value loss triggered by a permissionless spend, not merely a UX/gas issue.

### Likelihood Explanation
Likelihood is fairly high in practice: any pool operator (who already knows `pool_puzzle_hash`/`pool_memoization` and constructs `forward_pool_reward_dpuz`) can race to sweep pending reward coins the moment they see a `leave_pool`/exit spend appear in the mempool or a block, before the owner's own claim path becomes available (only after `pool_config` is cleared at the end of the waiting-room lock height). No special permission or signature is needed — the spend bundle in the reproducing test uses an empty signature (`G2Element()`), confirming zero authorization cost for whoever performs the sweep.

### Recommendation
Gate `forward_pool_reward()` (or its underlying `pool_proven_spend`/`FixedPuzzleMember` authorization) so it cannot be exercised once the owner has entered the `exiting`/waiting-room state, or alternatively allow the owner's `claim_pool_rewards()` to compete for/claim reward coins farmed after the exit was signaled, so that the owner's declared intent to leave the pool takes priority over the pool's sweep rights for rewards farmed during the transition window. At minimum, document and clearly surface this race to plotnft owners so they can claim/forward rewards proactively before initiating `leave_pool()`, but a structural fix (disallowing pool-side sweeps once `exiting=True`) removes the unauthorized-redirection risk entirely.

### Proof of Concept
This is directly reproduced by the existing project test:
1. Plot NFT owner joins a pool (`pool_config` set) and a pool reward coin is farmed to the singleton (`mint_reward`/`get_pool_rewards`).
2. Owner calls `leave_pool()` — this pushes the exit-to-waiting-room transition, `pool_config` remains present but `exiting=True`.
3. Owner attempts `claim_rewards()`; this fails with `"Cannot claim rewards while pooling..."` because `pooling` (i.e. `pool_config is not None`) is still true [4](#0-3) .
4. Anyone builds `plotnft.forward_pool_reward(pool_reward)` and pushes it with an unsigned (`G2Element()`) spend bundle; it is accepted, and the reward is swept to the pool, permanently reducing the plotnft's confirmed balance by `POOL_REWARD_AMOUNT` [5](#0-4) .

    def forward_pool_reward(self, reward: PoolReward) -> list[CoinSpend]:
        if not self.pooling:
            raise ValueError("Cannot forward pool reward while self pooling. Try `claim_pool_rewards`")
        return [
            self.singleton_action_spend(inner_solution=self.forward_pool_reward_inner_solution(reward)),
            make_spend(
                coin=reward.coin,
                puzzle_reveal=reward.puzzle(),
                solution=reward.solve(
                    self.inner_puzzle_hash(),
                    delegated_puzzle_and_solution=DelegatedPuzzleAndSolution(
                        puzzle=self.forward_pool_reward_dpuz(),
                        solution=Program.to([reward.coin.amount]),
                    ),
                ),
            ),
        ]
