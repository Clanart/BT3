### Title
Automatic, unconfirmed rewrite of a repository's git remote URL from GitHub API data allows silent redirection of user pushes/fetches - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
Derby's bug is "an untrusted/attacker-influenced parameter (`_slippage`) is passed straight into a state-changing operation (`xTransfer`) with no bounds checking, so a party who doesn't control the call can still control its effect." The GitHub Desktop analog is `updateRemoteUrl()`, which takes `clone_url` returned by the GitHub API for the matched repository and, based only on a weak heuristic, calls `git remote set-url` on the user's local repository **without any user confirmation or review** — unlike the equivalent user-facing flow in Repository Settings.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  reads `apiRepo.clone_url` from a live GitHub API response and, if the URL's protocol matches the current remote's protocol and the current remote still matches the *previously cached* `gitHubRepository.cloneURL`, silently rewrites the local remote:

```
if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
  await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
}
```

`setRemoteURL` directly executes `git remote set-url <name> <url>` with no path/host allow-list [2](#0-1) .

This function is invoked from `repositoryWithRefreshedGitHubRepository`, which fetches repository info via `api.fetchRepository(owner, name)` for whichever account/endpoint was matched by hostname from the existing remote, and then calls `updateRemoteUrl` unconditionally on the result [3](#0-2) . That refresh path is exercised on ordinary repository selection (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`) [4](#0-3)  and before every fetch through `withRefreshedGitHubRepository` [5](#0-4)  which backs `_fetch`/`_fetchRemote` [6](#0-5) .

The matching heuristic (`urlMatchesRemote`) only compares hostname/owner/repo-name strings parsed out of the URLs [7](#0-6) ; it does not verify that the "new" clone URL is still owned by the same principal, nor prompt the user, nor require the change to originate from an explicit settings-save action the way the manual flow in `RepositorySettings.onSubmit` does [8](#0-7) .

The exact corrupted value is the local git remote URL (`.git/config`'s `remote.<name>.url`), which subsequent `git push`/`git fetch` operations use as their destination/source. Because the value driving the change comes from a server-returned API object (`IAPIRepository.clone_url`) for whatever endpoint/account matched the remote's hostname, anyone able to influence that field for the matched owner/name — e.g. a compromised or malicious self-hosted GitHub Enterprise Server the app is configured against, or a repository transfer/rename to an attacker-controlled destination while keeping the same protocol — can cause Desktop to retarget the user's remote with zero user interaction or visible confirmation.

### Impact Explanation
If exploited, a user's next `git push` after this silent rewrite goes to the attacker-controlled remote instead of the repository they believe they're working with — i.e. silent corruption of what the user pushes, and potential leakage of proprietary source code/history to the attacker's host. Because outgoing git operations (and any credential helper/proxy resolution used for them) are keyed off the remote URL via `envForRemoteOperation(url)` [9](#0-8) , redirecting the remote can also cause credentials to be presented to the new (attacker) host during subsequent operations.

### Likelihood Explanation
The change requires no local access, no admin rights, and no user misstep: it fires automatically as part of routine repository-selection/fetch bookkeeping (`repositoryWithRefreshedGitHubRepository`), gated only by a string-based heuristic (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`) evaluated against server-supplied `clone_url` data, with no confirmation dialog shown to the user, unlike the deliberate, user-initiated remote change in Repository Settings.

### Recommendation
Do not silently mutate `remote.<name>.url` from background API refreshes. At minimum:
- Require explicit user confirmation (a dialog explaining the old vs. new remote URL) before calling `setRemoteURL` from `updateRemoteUrl`.
- Restrict automatic rewrites to cases with strong evidence of a legitimate rename/transfer (e.g., matching repository ID, not just owner/name strings) rather than relying solely on hostname/owner/name string comparison.
- Treat `clone_url` from non-dotcom (GitHub Enterprise) endpoints as less trusted for this purpose, or disable silent remote rewriting entirely for those endpoints.

### Proof of Concept
1. User has Desktop configured against a GitHub Enterprise Server endpoint (or the target repository is later transferred/renamed while remaining under the same protocol).
2. The user has a repository cloned with `origin` pointing at `https://ghe.example.com/org/repo.git`, and Desktop's cached `GitHubRepository.cloneURL` matches this.
3. The server (compromised admin, malicious GHES instance, or legitimate rename to a different owner) starts returning `clone_url: "https://ghe.example.com/attacker/repo.git"` for the same `owner/name` lookup used to match the account (hostname-based matching in `matchGitHubRepository`).
4. On the next repository selection or background fetch, `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` sees protocol match and `remoteUrlUnchanged` (user hasn't manually edited the remote) and silently runs `git remote set-url origin https://ghe.example.com/attacker/repo.git`.
5. The user, unaware, performs a normal `git push` from Desktop; the commits land in `attacker/repo` instead of `org/repo`. [1](#0-0) [3](#0-2)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
