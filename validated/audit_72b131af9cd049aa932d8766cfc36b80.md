### Title
Missing/insufficient slippage protection on the WOM→mWOM buyback swap triggered from `WombatStaking.harvest()` enables MEV to steal a portion of user reward yield - (File: `wombat/SmartWomConvert.sol`, `wombat/WombatStaking.sol`)

### Summary
`WombatStaking.harvest()` is a permissionless function that any wallet can call. It routes a portion of harvested WOM rewards ("fee") into `SmartWomConvert.smartConvert()`, which internally performs an on-chain AMM swap with the `amountOutMin` parameter hardcoded to `0`. The resulting converted tokens are queued as claimable yield in a `BaseRewardPool`, so any value siphoned off by a sandwich attacker directly reduces the yield ultimately claimable by stakers.

### Finding Description
`WombatStaking.harvest(address _lpToken)` has no access control beyond `whenNotPaused`/`_onlyActivePool`, so it is callable by any unprivileged wallet: [1](#0-0) 

It calls `_toMasterWomAndSendReward`, which in turn calls `_sendRewards` for the harvested WOM. When a fee is configured as `isMWOM`, and a `smartWomConverter` is set, the fee portion is routed through `smartConvert`: [2](#0-1) 

The converted amount is then queued directly as new rewards to a `BaseRewardPool` (when `!feeInfo.isAddress`), meaning it becomes claimable yield for that pool's stakers: [3](#0-2) 

Inside `SmartWomConvert.smartConvert`, the `_minRec` bound passed down is simply the raw input amount (`_amountIn`), not a value based on the fair expected market output: [4](#0-3) 

The actual AMM leg of the conversion, `_convertFor`, calls the Wombat router's `swapExactTokensForTokens` with the `amountOutMin` parameter hardcoded to `0`, i.e. no real per-swap slippage protection: [5](#0-4) 

The only post-swap guard is a loose floor check: [6](#0-5) 

This floor (`convertAmount + amountRec >= _amountIn`) only guarantees the converted mWOM is not less than the raw WOM amount put in — it does not enforce that the swap executes near the real market rate. Because `smartConvert` is only invoked when `currentRatio() < buybackThreshold` (i.e., mWOM trades at a discount to WOM), the "fair" output should normally be meaningfully above the 1:1 floor. An MEV bot can sandwich the harvest transaction (front-run to push the pool price against the swap, back-run to capture the difference) and extract nearly all of the premium between the floor and the fair market price, since `amountOutMin = 0` gives the sandwicher free rein down to that floor.

This exactly matches the reported bug class (harvest-time swap with `amountOutMin = 0`, no MEV/slippage protection), reachable here through the permissionless `WombatStaking.harvest()` entry point rather than a strategy vault, and it affects protocol reward-fee routing that is queued directly into a `BaseRewardPool` as user-claimable yield.

### Impact Explanation
Any wallet can trigger `harvest()` at any time (including immediately after large trades on the WOM/mWOM pool, or via flash-loan-assisted price manipulation), causing the fee-conversion swap to execute with zero real slippage protection. An MEV searcher sandwiching this call can capture essentially the entire premium between the market rate and the 1:1 floor, permanently diverting value that would otherwise have been queued as claimable yield for reward-pool stakers. This is a recurring, harvest-by-harvest leak of unclaimed protocol/user yield.

### Likelihood Explanation
`harvest()` is unauthenticated and can be called by anyone, including MEV bots themselves, at a time of their choosing (e.g., right after manipulating the WOM/mWOM pool price), making this trivially and repeatedly exploitable with no privileged access required.

### Recommendation
Do not hardcode `amountOutMin = 0` in `SmartWomConvert._convertFor`'s router call. Instead, derive a realistic minimum output on-chain immediately before the swap (e.g., via `IWombatRouter.getAmountOut` with a configurable slippage tolerance) and pass that as `amountOutMin`, in addition to (not instead of) the existing `_minRec` floor check.

### Proof of Concept
1. Attacker (or any bot) monitors mempool for calls to `WombatStaking.harvest(_lpToken)` where the harvested WOM includes an `isMWOM` fee and `smartWomConverter` is set.
2. Before the harvest tx, attacker manipulates the WOM/mWOM Wombat pool price (or simply waits for natural volatility) so that the true `getAmountOut` for `buybackAmount` is well above the input amount but the pool is thin/movable.
3. Attacker front-runs the harvest transaction to worsen the swap price, letting `SmartWomConvert._convertFor`'s `swapExactTokensForTokens(..., 0, ...)` execute at a much worse rate (bounded only by `amountRec + convertAmount >= _amountIn`).
4. Attacker back-runs to restore the pool price and capture the difference as profit, extracted from what would otherwise be queued as reward-pool yield via `IBaseRewardPool(feeInfo.to).queueNewRewards(...)`.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
