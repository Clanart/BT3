Confirmed: `ParseTransferArgs`/`ParseTransferFromArgs` perform no zero-address check on `to`, and `Precompile.transfer` in `precompiles/erc20/tx.go` sends straight to a plain `banktypes.NewMsgSend` — there is no rejection of `to == common.Address{}` anywhere in the call path.

### Title
ERC20 precompile `transfer`/`transferFrom` permanently locks user funds when sent to the zero address due to missing `to != address(0)` check - (File: `precompiles/erc20/tx.go`, `precompiles/erc20/types.go`)

### Summary
The Cosmos EVM `erc20` precompile (`precompiles/erc20/tx.go`) implements ERC-20 `transfer`/`transferFrom` on top of the bank module via a plain `MsgSend`, but never validates that the destination address is non-zero, unlike standard OpenZeppelin ERC-20 implementations (`_transfer` explicitly reverts with `to != address(0)` — see `contracts/solidity/precompiles/erc20/testdata/ERC20NoMetadata.sol:213` and the flattened OZ contract at `tests/evm-tools-compatibility/hardhat/Flattened.sol:583-585`). This is the same bug class as the reported `VaultFactory.claimFees`/`LoanCore.withdraw` missing zero-address check, applied to the native erc20 precompile's transfer path.

### Finding Description
`Precompile.Transfer` and `Precompile.TransferFrom` call `ParseTransferArgs`/`ParseTransferFromArgs` (`precompiles/erc20/types.go:26-71`), which only type-assert the ABI-decoded `to`/`from` addresses — no check rejects `common.Address{}` (EVM's canonical "burn"/zero address). The resulting `to` is passed unmodified into `p.transfer` (`precompiles/erc20/tx.go:69-131`), which builds `banktypes.NewMsgSend(from.Bytes(), to.Bytes(), coins)` and executes it through the bank keeper's `Send` handler. The Cosmos SDK bank module has no notion of "the zero address is invalid" — an all-zero 20-byte `sdk.AccAddress` is a syntactically valid account and `SendCoins` will happily credit it. This breaks the expected ERC-20 invariant that transfers to `address(0)` must revert (as codified in the module's own bundled reference ERC-20 implementations at `contracts/solidity/precompiles/erc20/testdata/ERC20NoMetadata.sol:212-213` and `tests/evm-tools-compatibility/hardhat/Flattened.sol:583-585`). No wallet/private key exists for the address consisting of all-zero bytes, so any tokens sent there via the precompile become permanently inaccessible — a real, on-chain balance is created for an address nobody can ever sign for.

### Impact Explanation
Any unprivileged user can call `transfer(address(0), amount)` or `transferFrom(owner, address(0), amount)` on any registered ERC20 token pair's precompile. Because the bank module accepts the zero-length-key-equivalent (all-zero-byte) address as valid, the coins are moved out of the sender's spendable balance into an account that is permanently unreachable — no keypair maps to the zero address. This is a permanent, irreversible freezing/loss of user funds (native coin balances underlying the token pair), matching the "Critical permanent freezing... of user funds... or token-pair-backed balances" impact category. It is user-triggerable via ordinary EVM transaction flow with no privileged access required, though it typically only harms the caller themselves (self-inflicted loss) unless invoked accidentally by tooling/scripts (mirroring the report's exploit scenario of an uninitialized `to` parameter defaulting to zero in an automated withdrawal script).

### Likelihood Explanation
Likelihood of accidental triggering is realistic: any dApp, bridge, bot, or script integrating with the erc20 precompile that fails to validate a `to` address (e.g., an uninitialized `address` variable in Solidity defaults to `address(0)`) will silently burn funds instead of reverting, exactly as described in the source report's exploit scenario. Because ordinary OpenZeppelin ERC-20 tokens revert in this situation, developers/integrators reasonably assume this same protection exists on the precompile, increasing the chance of accidental fund loss when composing contracts with the precompile.

### Recommendation
Add an explicit check in `precompiles/erc20/tx.go`'s `transfer` (or in `ParseTransferArgs`/`ParseTransferFromArgs`) to reject `to == common.Address{}`, returning an ERC20-compatible revert (mirroring the OZ `ERC20InvalidReceiver`/`"ERC20: transfer to the zero address"` behavior). Apply the same defensive check pattern anywhere else precompiles convert an EVM `address` argument directly into an `sdk.AccAddress` used for a bank transfer (e.g., `werc20` deposit/withdraw target resolution, if applicable) to keep behavior consistent with standard ERC-20 semantics that external integrators expect.

### Proof of Concept
1. Deploy/identify a registered ERC20 token pair precompile (e.g., at `0x...` per `x/erc20` token pair registration).
2. From an EOA holding a balance of the token, call `transfer(address(0), <amount>)` via the precompile ABI (`TransferMethod` in `precompiles/erc20/tx.go:30-44`).
3. Observe: `ParseTransferArgs` accepts `to = common.Address{}` without error; `p.transfer` executes `banktypes.NewMsgSend(from.Bytes(), (common.Address{}).Bytes(), coins)` successfully via `msgSrv.Send` (`precompiles/erc20/tx.go:112-116`); a `Transfer` event is emitted with `to = 0x000...000`.
4. Query the bank balance of the all-zero `sdk.AccAddress`: it now holds the transferred coins, permanently inaccessible since no private key corresponds to that address.

func ParseTransferArgs(args []interface{}) (
	to common.Address, amount *big.Int, err error,
) {
	if len(args) != 2 {
		return common.Address{}, nil, fmt.Errorf("invalid number of arguments; expected 2; got: %d", len(args))
	}

	to, ok := args[0].(common.Address)
	if !ok {
		return common.Address{}, nil, fmt.Errorf("invalid to address: %v", args[0])
	}

	amount, ok = args[1].(*big.Int)
	if !ok {
		return common.Address{}, nil, fmt.Errorf("invalid amount: %v", args[1])
	}

	return to, amount, nil
}

func (p *Precompile) transfer(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
	method *abi.Method,
	from, to common.Address,
	amount *big.Int,
) (data []byte, err error) {
	coins := sdk.Coins{{Denom: p.tokenPair.Denom, Amount: math.NewIntFromBigInt(amount)}}

	msg := banktypes.NewMsgSend(from.Bytes(), to.Bytes(), coins)

	if err = msg.Amount.Validate(); err != nil {
		return nil, err
	}

	isTransferFrom := method.Name == TransferFromMethod
	spenderAddr := contract.Caller()
	newAllowance := big.NewInt(0)

	if isTransferFrom {
		prevAllowance, err := p.erc20Keeper.GetAllowance(ctx, p.Address(), from, spenderAddr)
		if err != nil {
			return nil, ConvertErrToERC20Error(err)
		}

		newAllowance = new(big.Int).Sub(prevAllowance, amount)
		if newAllowance.Sign() < 0 {
			return nil, ErrInsufficientAllowance
		}

		if newAllowance.Sign() == 0 {
			// If the new allowance is 0, we need to delete it from the store.
			err = p.erc20Keeper.DeleteAllowance(ctx, p.Address(), from, spenderAddr)
		} else {
			// If the new allowance is not 0, we need to set it in the store.
			err = p.erc20Keeper.SetAllowance(ctx, p.Address(), from, spenderAddr, newAllowance)
		}
		if err != nil {
			return nil, ConvertErrToERC20Error(err)
		}
	}

	msgSrv := NewMsgServerImpl(p.BankKeeper)
	if err = msgSrv.Send(ctx, msg); err != nil {
		// This should return an error to avoid the contract from being executed and an event being emitted
		return nil, ConvertErrToERC20Error(err)
	}
