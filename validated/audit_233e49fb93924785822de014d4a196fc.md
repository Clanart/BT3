## SSRF via Unauthenticated DataLayer Mirror Coins Fetched by Any Subscribing Node's DataLayer Client

The Craft CMS report is about SSRF caused by insufficient IP-notation validation before Guzzle fetches an attacker-supplied URL server-side. Chia's DataLayer subsystem has an analogous (and more direct) SSRF: mirror URLs are attached to a publicly-spendable coin puzzle for *any* launcher id, with **zero URL/host validation at all**, and any node that syncs/subscribes to that store will automatically perform an outbound HTTP fetch to the attacker's URL.

### Title
Unauthenticated DataLayer Mirror Coins Enable SSRF Against Any Subscribing DataLayer Client - (File: `chia/data_layer/download_data.py`)

### Summary
The DataLayer mirror-coin puzzle (`create_mirror_puzzle()`) is a generic `P2_PARENT` puzzle with no ownership check tying the coin to the `launcher_id` it names in its memos. Any wallet holding mojos can create a mirror coin for **any** DataLayer store id (not just one it owns) and embed arbitrary URLs in the coin memos. Every node whose `DataLayerWallet` tracks that `launcher_id` will ingest the mirror via `coin_added()` and later feed its URL into the DataLayer service's HTTP downloader (`http_download()`), which issues an outbound `aiohttp` GET with no hostname/IP validation whatsoever.

### Finding Description
`create_mirror_puzzle()` returns `P2_PARENT.curry(Program.to(1))` [1](#0-0) , a puzzle that can be spent to create a coin with arbitrary memos encoding a `launcher_id` and URL list via `create_new_mirror()` [2](#0-1) . Nothing in `create_new_mirror()` or the mirror puzzle restricts the `launcher_id` argument to a store the spender actually owns — the attacker only needs any spendable XCH.

When such a mirror coin is confirmed, every node's `DataLayerWallet.coin_added()` checks only `is_launcher_tracked(launcher_id)` before recording the mirror, with no check on who created the coin: `if await self.wallet_state_manager.dl_store.is_launcher_tracked(launcher_id): ... await self.wallet_state_manager.dl_store.add_mirror(Mirror(coin.name(), launcher_id, ..., Mirror.decode_urls(urls), ours, height))` [3](#0-2) .

The `DataLayer` service periodically calls `update_subscriptions_from_wallet()`, which pulls every mirror URL for a tracked store id and pushes it into the local subscription server list unconditionally: `mirrors: list[Mirror] = (await self.wallet_rpc.dl_get_mirrors(...)).mirrors; urls += mirror.urls; await self.data_store.update_subscriptions_from_wallet(store_id, urls)` [4](#0-3) .

During the sync loop, `fetch_and_validate()` iterates these server URLs and calls `insert_from_delta_file()` [5](#0-4) , which calls `download_file()` → `http_download()`. `http_download()` performs the request with **no validation of the target host/IP at all** — not even a naive denylist like the one bypassed in the Craft CMS advisory:
```python
async with session.get(
    server_info.url + "/" + filename,
    headers=headers,
    timeout=timeout,
    proxy=proxy_url,
) as resp:
``` [6](#0-5) 

### Impact Explanation
Any unprivileged actor who can create a spend bundle (a mirror-coin creation transaction costing only mempool fees plus a token mirror amount, potentially `0`) can force every node that tracks/subscribes to a given DataLayer store — including stores that actor does not own — to make outbound HTTP requests to attacker-chosen URLs (e.g. cloud metadata endpoints, internal admin services, or arbitrary internal hosts) during the routine `periodically_manage_data()` sync loop. This is a spend-triggered SSRF against any Data Layer client node, and the response content is subsequently fed into `insert_into_data_store_from_file()` — while malformed data is expected to be rejected by root-hash validation, the outbound request itself (a full SSRF primitive: arbitrary host/port reachability, banner/response leakage via error logs, and internal network probing) already succeeds unconditionally before any data validation occurs.

### Likelihood Explanation
Likelihood is high for any node that has ever subscribed to (or auto-subscribes to, per DL config) a DataLayer store: the mirror coin's `launcher_id` is attacker-chosen and requires no relationship to the coin's owner, the mirror puzzle spend is a standard, mempool-admissible transaction, and the fetch path (`http_download`) contains no host allowlist/denylist, unlike the (bypassable) Craft CMS blocklist. No wallet or RPC authorization step is required by the victim — sync happens automatically in the background loop.

### Recommendation
- Validate/authorize that the mirror-coin creator is entitled to add mirrors for the referenced `launcher_id` before `coin_added()` records the mirror as trusted (e.g., require the mirror to be created within the same singleton lineage/wallet, or otherwise cryptographically tie the mirror to store ownership).
- In `http_download()`/`download_file()`, resolve and validate the target host against a private/link-local/metadata-address denylist (using `ipaddress` parsing of the resolved IP, not just the literal hostname string) before issuing the request, mirroring the class of fix applied upstream in Craft CMS but avoiding the same alternate-notation bypass by validating the *resolved* IP, not the raw string.
- Consider requiring explicit user confirmation/opt-in before automatically fetching from mirror URLs discovered on-chain for stores the local node does not own.

### Proof of Concept
1. Attacker crafts and broadcasts a standard coin spend using `create_mirror_puzzle()` as demonstrated by `create_new_mirror()` / `DLNewMirror` RPC, but sets `launcher_id` to a *victim's* DataLayer store id (which the attacker does not own) and `urls=["http://169.254.169.254/latest/meta-data/"]`, with `amount=0`.
2. The transaction confirms; any node that tracks that `launcher_id` (e.g., subscribers or the store owner itself) records the mirror in `coin_added()` regardless of the coin's actual creator [7](#0-6) .
3. On the victim node's next `periodically_manage_data()` cycle, `update_subscriptions_from_wallet()` adds the malicious URL to the store's subscription list [4](#0-3) .
4. `fetch_and_validate()` → `insert_from_delta_file()` → `download_file()` → `http_download()` issues an outbound GET to `http://169.254.169.254/latest/meta-data/...` from the victim node with no host validation [8](#0-7) .

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
