### Title
Reusable deterministic FROST preprocess enables secret-key recovery across modified signing attempts - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::share` can be executed multiple times for the same context while accepting independently supplied preprocess sets. Each invocation reconstructs the same secret nonce from the cached seed, but attacker-controlled nonce commitments can change the aggregate nonce and Schnorr challenge. Two shares produced under the same nonce therefore reveal the validator’s private key share.

### Finding Description
`preprocess_internal` stores only a 32-byte seed under `CachedPreprocesses`, keyed solely by `self.context`, and later decrypts and reloads that same seed through `AlgorithmSignMachine::from_cache`. [1](#0-0)  `seeded_preprocess` turns that seed into a deterministic `ChaCha20Rng`, regenerating the same secret nonce pair and public commitments every time it is invoked. [2](#0-1) 

`share_internal` calls `preprocess_internal` again, reads every supplied preprocess from attacker-controlled bytes, and passes the resulting commitments to `sign`. [3](#0-2)  A later call may preserve the same participant IDs while changing a commitment point, because `read_preprocess` only parses canonical non-identity points; there is no proof binding the two commitment points to a common nonce. [4](#0-3) [5](#0-4) 

The participant map is checked for threshold membership, bounds, and duplicates, but not for equality with commitments used by any earlier share operation. [6](#0-5)  The changed commitments alter the binding-factor transcript and aggregate nonce `Rs`. [7](#0-6)  Schnorr signing then returns `s = nonce + challenge * secret_share`, where the challenge binds the new aggregate nonce. [8](#0-7) 

`DkgConfirmer::share` exposes this behavior directly, while `complete` separately accepts another preprocess map and reconstructs the same deterministic signing machine. [9](#0-8) [10](#0-9) 

### Impact Explanation
For two invocations using the same participant IDs but modified commitment bytes, the victim emits:

```text
s1 = r + c1 * a
s2 = r + c2 * a
```

The same `r` is reused because the seed cache is keyed only by context, while `a` remains the same interpolated MuSig key share. [11](#0-10) [12](#0-11)  The attacker recovers the key share as `(s1 - s2) / (c1 - c2)`. For the MuSig keys used here, dividing by the participant’s public constant-interpolation coefficient recovers the validator’s actual private key. [13](#0-12) 

This is secret-key recovery rather than a benign determinism issue: the cached preprocess mechanism intentionally regenerates identical nonce material, while independent inputs can change the challenge. [14](#0-13) [15](#0-14) 

### Likelihood Explanation
A party able to supply or influence preprocess bytes can submit a syntactically valid but semantically different preprocess for an existing participant; canonical parsing does not prove possession of the underlying nonce. [16](#0-15)  A retry, repeated `share` call, or `complete` invocation using a differing preprocess map is sufficient because the code never marks the cached seed consumed or authenticates that the second set equals the first. [17](#0-16) 

### Recommendation
Bind each cached preprocess to a single immutable signing session. Store the selected participant IDs and the digest of their complete serialized preprocesses alongside the seed, and reject any later `share`/`complete` call whose map differs. Alternatively, retain the `AlgorithmSignMachine` itself between rounds and never reconstruct it from the same seed for new public inputs. At minimum, delete or tombstone `CachedPreprocesses[context]` after the first successful share-generation attempt so retries cannot reuse the nonce. [1](#0-0) 

### Proof of Concept
Conceptual execution against `DkgConfirmer`:

```rust
// Same participant IDs in both maps.
let mut preprocesses_1: HashMap<Participant, Vec<u8>> = fetch_preprocesses();
let mut preprocesses_2 = preprocesses_1.clone();

// Replace participant j's binding nonce commitment E_j with another
// canonical, non-identity Ristretto encoding. The 64-byte Schnorrkel
// preprocess consists of commitment_D || commitment_E.
preprocesses_2
    .get_mut(&participant_j)
    .unwrap()[32..64]
    .copy_from_slice(other_valid_point_bytes);

// First share uses nonce r and challenge c1.
let s1 = confirmer.share(preprocesses_1, &key_pair).unwrap();

// The same context reloads the same nonce seed, but the changed
// commitment produces aggregate nonce R2 and challenge c2.
let s2 = confirmer.share(preprocesses_2, &key_pair).unwrap();

// Decode both returned [u8; 32] values as Ristretto scalars.
let a = (s1 - s2) * (c1 - c2).invert().unwrap();

// For MuSig's Constant interpolation, a == binding_factor_i * private_key.
let private_key = a * binding_factor_i.invert().unwrap();
```

The modified preprocess is accepted because deserialization validates encodings rather than nonce consistency. [4](#0-3)  Both calls reuse the seed at `CachedPreprocesses`, while the differing commitments alter the transcript used for the aggregate nonce and challenge. [11](#0-10) [7](#0-6)
