### Title
Unbound secret share in `ThresholdKeys::read`/`ThresholdKeys::new` lets crafted key material produce a group key with attacker-known discrete log - (File: crypto/dkg/src/lib.rs)

### Summary

The external report (CVE-2026-7871) describes a party with access to a privileged store (Redis) gaining full control over application secrets and integrity. The Serai analog lives in the deserialization path for threshold key material: `ThresholdKeys::read` consumes attacker-controlled `t`, `n`, `i`, `interpolation`, `secret_share`, and `n` verification shares, then hands them to `ThresholdKeys::new`, which never binds the secret share to `verification_shares[i]` — and more importantly computes `group_key` purely from the attacker-supplied verification shares. An attacker who can feed crafted bytes to `ThresholdKeys::read` produces a valid `ThresholdKeys` whose group key has a discrete log they fully know, giving them unilateral signing capability under that key — the exact analog of "compromising all secrets and system integrity."

### Finding Description

`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses every field from the reader: the params `(t, n, i)` (lines 591-602), the interpolation method including a fully attacker-controlled `Vec<C::F>` for `Interpolation::Constant` (lines 604-616), the `secret_share` (line 618), and a map of `verification_shares` over `1..=n` (lines 620-623). It then calls `ThresholdKeys::new`.

`ThresholdKeys::new` (lines 349-391) validates only:

- `verification_shares.len() == n` (line 355),
- all share indices `<= n` (lines 361-365),
- `t == n` when `Interpolation::Constant` is used (lines 367-374).

It then derives the group key as the interpolation of `verification_shares[1..=t]` (lines 376-378) and stores everything. Nowhere does it check that `secret_share * C::generator() == verification_shares[i]` — the private share is cryptographically unbound from the public verification shares, and all verification shares are trusted as-is.

For `Interpolation::Lagrange`, the attacker picks arbitrary `Y_j = y_j * G` for `j = 2..=n` with known `y_j`, sets `i = 1`, `secret_share = a`, `verification_shares[1] = a * G` (so any local share-consistency checks downstream pass), and the resulting `group_key = sum_{j=1..=t} lambda_j * Y_j` is a point whose discrete log `sum lambda_j * y_j` is known to the attacker. Every FROST signing session run with this `ThresholdKeys` produces signatures under a key the attacker can also sign for alone — and can have signed for from the start.

### Impact Explanation

If deserialized `ThresholdKeys` bytes are reachable by an unprivileged party (provisioned key files, backup/restore paths, coordination messages carrying key material — `ThresholdKeys::read` is an explicit public-input sink), the attacker substitutes key material yielding a group key with known discrete log. Consequences matching the accepted-impact criteria:

- Forged signatures: the attacker signs arbitrary messages for the derived group key without any threshold participation.
- Signature theft/normalization: all FROST shares issued under these keys certify a key the attacker controls outright.

This mirrors the CVE's class: compromise of a trusted store of sensitive material escalates to total control of the security-relevant output.

### Likelihood Explanation

Reachability is conditional on the integrator feeding attacker-influenced bytes to `ThresholdKeys::read` — the same precondition shape as the CVE (access to a storage channel the application trusts). Given that precondition, exploitation is trivial: the attacker needs no interaction, no colluding participants, and no computational work — just algebra over chosen scalars. Severity High: full key/signing compromise, but gated on the key-material delivery path being attacker-reachable rather than a pure network input.

### Recommendation

In `ThresholdKeys::new`, after computing `group_key`, verify `C::generator() * secret_share == verification_shares[&params.i()]` (rejecting on mismatch). Ideally, also require the caller to supply an expected `group_key` or a hash commitment over the verification shares established during the DKG, so deserialized material is bound to a previously agreed transcript rather than self-authenticating.

### Proof of Concept

```rust
// Attacker crafts bytes for ThresholdKeys::<Ed25519>::read
let n: u16 = 3; let t: u16 = 2;
let a = Scalar::random(OsRng);      // attacker's own share for slot i=1
let y2 = Scalar::random(OsRng);     // known DL for participant 2's verification share
let y3 = Scalar::random(OsRng);

let mut buf = vec![];
buf.extend((Ed25519::ID.len() as u32).to_le_bytes()); buf.extend(Ed25519::ID);
buf.extend(t.to_le_bytes()); buf.extend(n.to_le_bytes()); buf.extend(1u16.to_le_bytes()); // i = 1
buf.push(1u8);                                                // Interpolation::Lagrange
buf.extend(a.to_repr());                                      // secret_share
for y in [a, y2, y3] { buf.extend((EdwardsPoint::generator() * y).to_bytes()); }

let keys = ThresholdKeys::<Ed25519>::read(&mut buf.as_slice()).unwrap();

// group_key = lambda_1*a*G + lambda_2*y2*G (Lagrange, set {1,2})
// Attacker computes lambda_1, lambda_2 for included = {1,2} and knows
// dlog(group_key) = lambda_1 * a + lambda_2 * y2
// => attacker signs alone as the group; local share check
//    (a*G == verification_shares[1]) still passes for i = 1.
```

Root cause: crypto/dkg/src/lib.rs:376-378 derives `group_key` from fully deserialized `verification_shares`, and crypto/dkg/src/lib.rs:349-391 performs no check that `secret_share` corresponds to `verification_shares[i]` or that the shares come from a trusted DKG transcript.
