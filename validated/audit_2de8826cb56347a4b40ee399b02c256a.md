### Title
`HostManager.onAccept` authorizes privileged withdraw/host-param actions by checking only `request.source`, never `request.from` - (File: `evm/src/core/HostManager.sol`)

### Summary
`HostManager.onAccept` executes two highly privileged actions — withdrawing accumulated bridge revenue and overwriting the `EvmHost` security parameters (fee token, admin, per-byte fees, etc.) — after checking only that the incoming ISMP request's `source` chain equals the Hyperbridge parachain. It never checks the request's `from` field (the specific module/pallet on Hyperbridge that dispatched the message), unlike every other `onAccept` implementation in this codebase, which binds *both* chain and module identity before trusting a message.

### Finding Description
`HostManager.onAccept` is invoked only by the local `EvmHost` (`restrict(_params.host)`), so the surrounding ISMP consensus/state proof machinery is sound — the request really was dispatched from the Hyperbridge parachain. The bug is entirely in the authorization logic performed *after* that point: [1](#0-0) 

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
    PostRequest calldata request = incoming.request;
    // Only the Hyperbridge parachain can send requests to this module.
    if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

    OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
    if (action == OnAcceptActions.Withdraw) {
        WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
        IHostManager(_params.host).withdraw(withdrawParams);
    } else if (action == OnAcceptActions.SetHostParam) {
        HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
        IHostManager(_params.host).updateHostParams(hostParams);
    }
}
```

The only check is `request.source == hyperbridge()`. `request.from` (the specific pallet/account on the Hyperbridge chain that originated the dispatch) is completely unused. Compare this with every other `onAccept` in the codebase, all of which explicitly bind `from` as well as `source`: [2](#0-1) [3](#0-2) 

These modules require `request.from` to equal a registered per-chain module/instance address; a message whose `source` is right but `from` is wrong is rejected with `Unauthorized`/`UnauthorizedSource`. `HostManager` skips this step entirely.

This is the direct structural analog to the PhiFactory `merkleClaim` bug: the report showed that checking only `minter_` (one identity field) while leaving `ref_`/`artId_`/`imageURI` (other decodable fields) unverified let an attacker substitute unapproved values that drove fund flow and state. Here, `HostManager` checks only the chain-level identity field (`source`) and leaves the module-level identity field (`from`) completely unverified before trusting the payload to mean "governance says: withdraw funds / rewrite host security parameters."

### Impact Explanation
Since `request.from` is never checked, **any** ISMP-capable dispatcher on the Hyperbridge parachain that is able to address a POST request `to` this `HostManager` contract — regardless of which pallet or account actually built the message — is treated as fully authorized governance. The two reachable actions are severe:

- `OnAcceptActions.Withdraw` → calls `IHostManager(_params.host).withdraw(withdrawParams)`, moving accumulated bridge/protocol revenue out of the host.
- `OnAcceptActions.SetHostParam` → calls `IHostManager(_params.host).updateHostParams(hostParams)`, which can rewrite `EvmHost`'s security-critical parameters (fee token, per-byte fee, challenge period, admin, handler, etc.) — a full governance takeover primitive for that EVM host.

Since the module-binding check that every sibling `onAccept` (`ExtrinsicIntents`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) performs is absent here, `HostManager` cannot distinguish a legitimate governance module's message from a message dispatched by any other pallet/extrinsic path on Hyperbridge whose body happens to be shaped like `OnAcceptActions.Withdraw`/`SetHostParam`. This satisfies the bounty's "cross-chain admin or host-management effects reachable through … wrong module bindings" category directly: theft of bridge revenue and/or hostile reconfiguration of `EvmHost` parameters.

### Likelihood Explanation
Exploitability hinges on whether any dispatch surface on the Hyperbridge parachain lets a caller (ideally unprivileged) choose an arbitrary `to` (the destination `HostManager` address) and `body` for an ISMP POST request while the `from` field is set to something other than the intended governance module id. The repository's own incentivization documentation confirms multiple pallets besides governance dispatch ISMP POST requests through the generic `IsmpDispatcher::dispatch_request` path (host executive, intents-coprocessor, token-governor, the relayer pallet's own withdrawal path): [4](#0-3) 

The `HostManager.onAccept` code makes clear that the developers *intended* "only the Hyperbridge parachain can send requests to this module" as the sole authorization check, without also pinning `from` to a trusted governance module id — this is a straightforward oversight rather than a defense-in-depth omission, since the destination-side identity binding is exactly the pattern used everywhere else in the same codebase. This makes the missing check locally provable and directly comparable to the confirmed PhiFactory finding; I could not fully trace every possible caller of `dispatch_request` on the parachain side within this session to confirm a concrete unprivileged reachability path, so the precise blast radius (whether reachable by any unprivileged extrinsic today, or only by another privileged-but-non-governance pallet) is not fully verified here and should be confirmed in a live session.

### Recommendation
Add an explicit `from`-binding check in `HostManager.onAccept`, mirroring the pattern used in `ExtrinsicIntents._authenticate` and `HyperFungibleToken.onAccept`:
```solidity
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
if (keccak256(request.from) != keccak256(TRUSTED_GOVERNANCE_MODULE_ID)) revert UnauthorizedAction();
```
where `TRUSTED_GOVERNANCE_MODULE_ID` is the fixed pallet/module id on Hyperbridge that is exclusively permitted to originate `Withdraw`/`SetHostParam` messages (configurable via the same admin-only setter pattern already used for `_params.host`).

### Proof of Concept
Conceptual PoC (cannot be executed without full access to the Hyperbridge parachain's dispatch surfaces, flagged as unverified):
1. Identify any Hyperbridge-parachain pallet/extrinsic that calls `IsmpDispatcher::dispatch_request` with attacker-influenced `to` and `body` fields (e.g. a generic cross-chain messaging entrypoint, or any future/auxiliary pallet not intended to be the governance module).
2. Craft `to = <HostManager address on target EVM chain>`, `body = 0x00 || abi.encode(WithdrawParams{...})` (or `0x01 || abi.encode(HostParams{ admin: attacker, ... })`).
3. Wait for normal ISMP relaying/finalization (no forged proof needed — the message is legitimately dispatched from Hyperbridge, just from the wrong pallet).
4. On delivery, `EvmHost.dispatchIncoming` calls `HostManager.onAccept`, which passes the `request.source.equals(hyperbridge())` check (true) and, absent any `from` check, executes the attacker-crafted `Withdraw` or `SetHostParam` call — draining bridge revenue or overwriting host admin/fee parameters.
