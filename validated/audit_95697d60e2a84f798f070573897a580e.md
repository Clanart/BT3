### Title
Missing participant in promotion proof map causes panic / DoS (`proofs.get(&i).unwrap()`) - ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary
`GeneratorPromotion::complete` validates the *count* and *upper bound* of the peer-supplied `proofs` map, but never validates that the map's key set is exactly `1..=n` minus `params.i()`. A proof map containing `params.i()` itself (or any duplicate-free set that omits another participant `j`) passes all checks and then panics on `proofs.get(&i).unwrap()`, a reachable denial of service via untrusted DKG-protocol input — the same bug class as the FFmpeg off-by-one (insufficient index validation leading to a crash on crafted input).

### Finding Description
In `GeneratorPromotion::complete`, the caller supplies `proofs: &HashMap<Participant, GeneratorProof<C1>>` collected from the other participants:

```rust
// crypto/dkg/promote/src/lib.rs:125-156
if proofs.len() != (usize::from(params.n()) - 1) { ... }
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... }
}
...
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();   // line 146 — panics if `i` absent
```

The validation checks:
1. `proofs.len() == n - 1`
2. every key `<= n` (and keys are `Participant`, so `>= 1` by construction)

It does **not** check that `params.i()` is absent from `proofs`, nor that every `i != params.i()` in `1..=n` is present. A map containing `params.i()` as a key while omitting some other participant `j` satisfies both checks (still `n - 1` entries, all `<= n`), then reaches `proofs.get(&j).unwrap()` and panics on a `None`.

The `proofs` map is built from `GeneratorProof` messages broadcast by other participants in the key-promotion protocol — untrusted, attacker-controlled public input (`GeneratorProof` is even re-deserialized through `GeneratorProof::read` in the test at `crypto/dkg/promote/src/tests.rs:90`). The panic aborts the caller's promotion task rather than returning a `PromotionError`, which the error enum (`IncorrectAmountOfParticipants`, `InvalidParticipant`, `InvalidProof`) clearly intends for this exact failure category.

### Impact Explanation
Denial of service: a single protocol participant can crash the promotion routine of every honest party that runs `complete` with the malformed map. Since `GeneratorPromotion` is used to migrate threshold keys to a new generator, a panic mid-protocol halts the generator-promotion ceremony for the affected validator; if the panic occurs inside a larger task or loop over promotions, it can abort broader processing. This maps to the external report's Medium-severity DoS-via-crafted-input classification.

### Likelihood Explanation
- Reachability: high — the malformed `HashMap` is trivially constructible by any participant broadcasting proofs (just insert an entry keyed by the victim's `Participant` index and omit someone else's).
- Preconditions: the attacker must be a member of the participant set during a generator-promotion run; promotion is an occasional maintenance operation rather than a per-transaction path, which caps the practical blast radius.
- Detection/mitigation: the panic is deterministic and attributable (the faulty proof map is identifiable), but the code offers no graceful recovery path.

Net: Medium, matching the source CVE's DoS severity.

### Recommendation
Replace the `unwrap()` at `crypto/dkg/promote/src/lib.rs:146` with a checked lookup and tighten the set validation:

```rust
// after the existing bounds check
if proofs.contains_key(&params.i()) {
  Err(PromotionError::InvalidParticipant { n: params.n(), participant: params.i() })?;
}
...
let proof = proofs
  .get(&i)
  .ok_or(PromotionError::IncorrectAmountOfParticipants {
    t: params.n(),
    n: params.n(),
    amount: proofs.len() + 1,
  })?;
```

Equivalently, verify `proofs.keys().copied().collect::<HashSet<_>>() == (1..=params.n()).map(Participant::new).collect::<HashSet<_>>() - {params.i()}` before consuming the map.

### Proof of Concept
```rust
// Setup: 3-of-3 ThresholdKeys over Ristretto promoted to AltGenerator<Ristretto>,
// as in crypto/dkg/promote/src/tests.rs.
// Victim is participant 1. Instead of proofs from {2, 3}, the attacker submits
// proofs keyed by {1, 2} — victim's own index plus participant 2, omitting 3.

let mut bad_proofs = HashMap::new();
bad_proofs.insert(Participant::new(1).unwrap(), proof_from_anyone.clone());
bad_proofs.insert(Participant::new(2).unwrap(), proof_from_2);

// passes: proofs.len() == n - 1 == 2
// passes: all keys <= n
// panics at crypto/dkg/promote/src/lib.rs:146 when i == 3:
//   proofs.get(&Participant(3)).unwrap() -> None -> panic
promotion_for_participant_1.complete(&bad_proofs);
```

Expected result with the fix: `Err(PromotionError::...)`. Current result: `thread panicked at 'called Option::unwrap() on a None value'`.

Caveat: the exact call site that feeds attacker-controlled `proofs` into `complete` lives in processor/coordinator glue code not in scope here; the library-level panic itself is confirmed by the unconditional `unwrap()` in the in-scope file.
