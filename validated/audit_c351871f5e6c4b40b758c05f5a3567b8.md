### Title
Immutable NFT royalty address can permanently trap CR-CAT royalty payments if the recipient's VC/provider authorization is lost - (File: `chia/wallet/nft_wallet/nft_puzzle_utils.py`, `chia/wallet/vc_wallet/cr_cat_wallet.py`)

### Summary
NFT royalty payouts are always sent to a `royalty_puzzle_hash` that is permanently curried into the NFT's transfer program at mint time, with no protocol mechanism to change it. If an NFT is traded in an offer for a Credential-Restricted CAT (CR-CAT), the royalty payment coin created at the royalty address is itself a CR-CAT coin, which can only be spent by presenting a valid VC issued by one of the `authorized_providers`. If that royalty recipient's ability to obtain such a VC is lost (VC revoked or no VC ever held for that provider), the royalty payment becomes permanently unspendable — this mirrors the reported MAINTAINER-address blacklist issue: a fixed recipient address for protocol fee/royalty payments that becomes permanently unable to satisfy the token's own transfer-authorization requirement, with no owner-facing recovery path.

### Finding Description
The royalty address for an NFT is fixed once at mint time inside the NFT's ownership/transfer-program layer and cannot be updated afterward: [1](#0-0) [2](#0-1) 

There is no wallet or RPC function anywhere in the NFT wallet code that allows changing `royalty_puzzle_hash` after mint (searched `royalty_puzzle_hash`/`royalty_address` usages across `chia/wallet/nft_wallet/*.py`; only mint-time construction and read paths exist).

When an offer settles and the requested/offered fungible asset is a CR-CAT, the royalty payment condition creates a coin at `royalty_ph`/`address` using the same CAT asset driver (including the CR layer), so the royalty payout inherits the CR-CAT's credential-gated spend requirements: [3](#0-2) 

Spending any CR-CAT coin — including this royalty payment — requires locating a `VerifiedCredential` whose `authorized_providers`/proofs satisfy the CAT's `proofs_checker`: [4](#0-3) [5](#0-4) 

If no such VC exists (revoked via `activate_backdoor`, expired, or never issued for that provider to the royalty puzzle-hash's key), spending is impossible: [6](#0-5) [7](#0-6) 

Since the royalty address is immutably curried into the NFT's transfer program and there is no update mechanism (unlike, e.g., `PoolWallet.update_pool_config()`/`change_payout_instructions` which lets a pool owner change payout puzzle hash), the royalty recipient has no way to redirect future or already-received royalty payments to an address they can actually spend from.

### Impact Explanation
Any CR-CAT-denominated royalty payment sent to an NFT's immutable royalty address becomes permanently unspendable once the recipient loses (or never had) an authorizing VC for that CR-CAT's provider set. This is a real, on-chain fund lock of a legitimate settlement output — directly analogous to the reported bug class (a hardcoded fee/recipient address that a token issuer can render permanently unauthorized). Because NFT trading via offers is a core, unprivileged wallet flow and royalty percentage/address are mint-time parameters chosen by ordinary users (not protocol operators), this is reachable by any NFT creator/seller who happens to trade for a CR-CAT.

### Likelihood Explanation
Requires: (1) an NFT minted with royalties, (2) an offer settled using a CR-CAT as the fungible payment asset, and (3) the royalty puzzle hash's owner subsequently lacking a valid VC for the CR-CAT's authorized providers (revocation, VC never obtained, or provider set narrowed). CR-CAT/VC usage is a supported, first-class Chia primitive intended for regulated assets, and provider-controlled VC issuance/revocation is an expected, non-malicious-node operation reachable purely through legitimate offer settlement — making this a plausible, not purely theoretical, scenario for royalty-bearing NFTs traded against CR-CATs.

### Recommendation
- Warn (and ideally block by default) NFT creators/wallets from accepting or constructing offers where royalty payment currency is a CR-CAT unless the royalty address is known to be able to obtain a qualifying VC.
- Consider allowing royalty payouts denominated in CR-CATs to route through a "pending approval" state (as already used elsewhere in the CR-CAT flow, see `construct_pending_approval_state` in `cr_cat_wallet.py`) so a future VC holder can claim them, rather than sending directly to the raw royalty puzzle hash.
- Document clearly that royalty addresses are immutable and should not be used as-is for assets that impose transfer-time credential checks.

### Proof of Concept
1. Mint an NFT with `royalty_percentage > 0` and `royalty_puzzle_hash = X`, where `X` corresponds to a key the seller controls (`nft_wallet.py::generate_new_nft`, `create_ownership_layer_puzzle`).
2. Create/accept an offer where the fungible payment asset is a CR-CAT (`AssetType.CR`), following the flow in `NFTWallet.make_nft1_offer` / `trade_manager.check_for_requested_payment_modifications`, which requires a VC to exist at settlement time (`get_or_create_vc_wallet().get_vc_with_provider_in_and_proofs`).
3. Settle the trade; the royalty payment coin is created at puzzle hash `X` as a CR-CAT (see `nft_wallet.py` lines 1082-1130), inheriting the `authorized_providers`/`proofs_checker` of that CAT.
4. Have the VC provider revoke the VC associated with key `X` via `VerifiedCredential.activate_backdoor()`, or simply never have obtained a VC for that provider under key `X`.
5. Any subsequent attempt to spend the royalty coin at `X` fails in `CRCATWallet._generate_unsigned_spendbundle`/`claim_pending_approval_balance` because no VC can be found (`RuntimeError("CR-CATs cannot be spent without an appropriate VC")`), and since the royalty address is immutably baked into the NFT and cannot be redirected, the funds are permanently stuck.

    async def get_vc_with_provider_in_and_proofs(
        self, authorized_providers: list[bytes32], proofs: list[str]
    ) -> VerifiedCredential:
        vc_records: list[VCRecord] = await self.store.get_vc_records_by_providers(authorized_providers)
        if len(vc_records) == 0:  # pragma: no cover
            raise ValueError(f"VCWallet has no VCs with providers in the following list: {authorized_providers}")
        else:
            for rec in vc_records:
                if rec.vc.proof_hash is None:
                    continue  # pragma: no cover
                vc_proofs: VCProofs | None = await self.store.get_proofs_for_root(rec.vc.proof_hash)
                if vc_proofs is None:
                    continue  # pragma: no cover
                if all(proof in vc_proofs.key_value_pairs for proof in proofs):
                    return rec.vc
        raise ValueError(f"No authorized VC has the correct proofs: {proofs}")  # pragma: no cover

        self, provider_innerpuzhash: bytes32, announcement_nonce: bytes32 | None = None
    ) -> tuple[CreatePuzzleAnnouncement, CoinSpend]:
        """
        Activates the backdoor in the VC to revoke the credentials and remove the provider's DID.

        Returns the announcement we expect from the provider's DID authorizing this, and the spend of the VC.
        Sync attempts by this class on spends generated by this method are expected to fail. This could be improved in
        the future with a separate type/state of VC that is revoked, but perfectly useful as a singleton.
        """
        vc_solution: Program = solution_for_singleton(
            self.singleton_lineage_proof,
            uint64(self.coin.amount),
            Program.to(
                [  # solve EML
                    solve_revocation_layer(
                        self.hidden_puzzle(),
                        solve_std_vc_backdoor(
                            self.launcher_id,
                            Program.to((self.proof_provider, self.proof_hash)).get_tree_hash(),
                            self.construct_transfer_program().get_tree_hash(),
                            self.inner_puzzle_hash,
                            uint64(self.coin.amount),
                            self.eml_lineage_proof,
                            provider_innerpuzhash,
                            self.coin.name(),
                            announcement_nonce,
                        ),
                        hidden=True,
                    ),
                ]

        return (
            expected_announcement,
            make_spend(self.coin, self.construct_puzzle(), vc_solution),
