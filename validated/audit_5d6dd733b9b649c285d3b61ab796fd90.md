### Title
Finishing a conflicted merge silently skips commit hooks that were enforced for the initial merge attempt, letting rejected content be committed and reported as success - (File: `app/src/lib/git/commit.ts`)

### Summary
`app-store.ts` calls `createMergeCommit()` in `app/src/lib/git/commit.ts` to finalize a merge once the user has resolved conflicts. Unlike the normal commit path (`createCommit`) and the initial merge attempt (`merge()` in `app/src/lib/git/merge.ts`), `createMergeCommit` never sets `interceptHooks`, so no hook enforcement (pre-commit/commit-msg/pre-merge-commit) is applied when the merge is actually finalized.

### Finding Description
Two related, but inconsistent, code paths exist for creating a merge commit:

- `merge()` in `app/src/lib/git/merge.ts` runs `git merge` with `interceptHooks: ['pre-merge-commit', 'post-merge', 'commit-msg']` [1](#0-0) , so if the merge completes cleanly, hooks like `commit-msg` (which can reject secrets, enforce DCO trailers, enforce message formats, etc.) run and can block the commit.
- However, if the merge hits conflicts, `MergeResult.Failed`/conflict state is returned, and the app defers finishing the commit until the user resolves conflicts. At that point, `_finishConflictedMerge`-style flows in `app-store.ts` call `createMergeCommit()` [2](#0-1)  to actually create the commit.
- `createMergeCommit` builds its `git commit --no-edit --cleanup=strip` invocation with **no `interceptHooks` option at all** [3](#0-2) , in contrast to `createCommit`, which always sets `interceptHooks: ['pre-commit', 'prepare-commit-msg', 'commit-msg', 'post-commit', ...]` [4](#0-3) .

This mirrors the structure of the LES bug: one code path (`merge()`, analogous to `EthAPIBackend.SendTx`) performs the "important" step (hook interception/enforcement), while a second, related code path that handles the same logical operation but under a different trigger (`createMergeCommit`, analogous to `LesApiBackend.SendTx`) silently omits that step. The result: whatever validation a repository's hooks are meant to enforce (secret scanning, commit message policy, signed-commit checks implemented via hooks, etc.) is bypassed specifically for the "resolve conflicts and finish merge" flow, while the app still reports the merge as completed successfully.

Because GitHub Desktop's `interceptHooks` mechanism is what wires local Git hooks into the app's hook-progress/hook-failure UI (`with-hooks-env.ts`) [5](#0-4) , omitting it doesn't just skip UI feedback — it skips hook execution altogether for that commit, since `withHooksEnv` only sets up the hooks proxy `if (opts?.interceptHooks ...)`.

### Impact Explanation
For repositories that rely on local Git hooks (via `core.hooksPath` interception) to gate what gets committed — e.g., a `commit-msg` hook that rejects credentials/secrets accidentally staged during conflict resolution, or enforces required trailers/signing policy — finishing a conflicted merge in Desktop silently bypasses that gate. The user sees a normal "merge completed" UX with no indication that hook checks were skipped, unlike a clean merge (no conflicts) where the same hooks would have been enforced. This is a silent-corruption-of-what-the-user-commits scenario: the invariant "hooks configured for this repo run on every commit unless the user explicitly bypasses them via 'Bypass Commit Hooks'" is broken specifically for merge-conflict resolution commits, without any explicit user action or `--no-verify` flag being requested.

### Likelihood Explanation
This path is hit any time a user merges a branch, encounters conflicts, resolves them, and clicks to complete the merge — a very common workflow. No attacker interaction with GitHub Desktop internals is required; a malicious/compromised remote branch that intentionally introduces conflicting content designed to slip past hook-based checks (e.g., secret scanners or message-policy hooks) only needs to be merged and have conflicts, which is a normal, unprivileged repository-content-controlled trigger consistent with the "attacker controls a cloned/fetched repository" impact criterion.

### Recommendation
Pass the same `interceptHooks` set used by `createCommit`/`merge` (i.e., `pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`, plus `pre-merge-commit`/`post-merge` where relevant) into `createMergeCommit`'s git invocation, respecting the existing `skipCommitHooks` app setting so behavior is consistent between a clean merge and a merge that required manual conflict resolution.

### Proof of Concept
1. In a test repository, install a `commit-msg` hook (or `pre-commit` hook) that rejects commits under some condition (e.g., blocks a string like `SECRET_TOKEN`).
2. Create a branch that merges cleanly with no conflicts and contains `SECRET_TOKEN` — confirm the hook fires via `merge()`'s `interceptHooks` and the commit is blocked/flagged in the UI.
3. Create a second scenario where the same content instead causes a merge conflict (e.g., colliding line edits) so the user must manually resolve conflicts and finish the merge via Desktop's conflict-resolution flow (`createMergeCommit`).
4. Observe that the resulting merge commit is created successfully with the `SECRET_TOKEN` content, and the hook does not run/block, because `createMergeCommit` (`app/src/lib/git/commit.ts:82-136`) never sets `interceptHooks`, unlike `createCommit` and `merge()`.

Note: I was not able to fully trace every call site of `createMergeCommit` in `app-store.ts` (e.g., confirm whether `skipCommitHooks` is intentionally never threaded through for this specific function, or whether there is a compensating check elsewhere) within the tool budget available — a Devin session with full repo access would be needed to confirm no other guard exists before this is finalized as a confirmed vulnerability rather than a strong candidate analog.

export async function createMergeCommit(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map()
): Promise<string> {
  // apply manual conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file !== undefined) {
      await stageManualConflictResolution(repository, file, resolution)
    } else {
      log.error(
        `couldn't find file ${path} even though there's a manual resolution for it`
      )
    }
  }

  const otherFiles = files.filter(f => !manualResolutions.has(f.path))

  await stageFiles(repository, otherFiles)
  const result = await git(
    [
      'commit',
      // no-edit here ensures the app does not accidentally invoke the user's editor
      '--no-edit',
      // By default Git merge commits do not contain any commentary (which
      // are lines prefixed with `#`). This works because the Git CLI will
      // prompt the user to edit the file in `.git/COMMIT_MSG` before
      // committing, and then it will run `--cleanup=strip`.
      //
      // This clashes with our use of `--no-edit` above as Git will now change
      // it's behavior to invoke `--cleanup=whitespace` as it did not ask
      // the user to edit the COMMIT_MSG as part of creating a commit.
      //
      // From the docs on git-commit (https://git-scm.com/docs/git-commit) I'll
      // quote the relevant section:
      // --cleanup=<mode>
      //     strip
      //        Strip leading and trailing empty lines, trailing whitespace,
      //        commentary and collapse consecutive empty lines.
      //     whitespace
      //        Same as `strip` except #commentary is not removed.
      //     default
      //        Same as `strip` if the message is to be edited. Otherwise `whitespace`.
      //
      // We should emulate the behavior in this situation because we don't
      // let the user view or change the commit message before making the
      // commit.
      '--cleanup=strip',
    ],
    repository.path,
    'createMergeCommit'
  )
  return parseCommitSHA(result)
}

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
