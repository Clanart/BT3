### Title
Payout attribution is bound only to an unsigned OP_RETURN, letting anyone credit/reimburse an unrelated operator for a payout they never funded - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` embeds the "fronting operator" identity in a plain, unsigned `OP_RETURN` output that is never covered by any operator signature, and the withdrawal input is signed by the user with `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`, which commits only to input0/output0. Anyone able to produce that withdrawal signature (including the withdrawing user/attacker themselves) can build and broadcast the payout transaction, fund output0 entirely from their own coins, and put a real, uninvolved operator P's x-only pubkey in the `OP_RETURN`. The chain of trust that credits/reimburses "the operator" is derived solely from this `OP_RETURN` field, so P's automation will pick up the withdrawal as its own and get reimbursed `bridge_amount` from the move-to-vault UTXO.

### Finding Description
The broken binding is:

`payout_payer_operator_xonly_pk` (stored in DB, parsed from the confirmed payout tx's `OP_RETURN`) == the party whose own coins funded `output0` of that confirmed payout tx.

Trace:
- `create_payout_txhandler` builds the payout tx with input0 = withdrawal UTXO (spent via the user's own key-path signature, `NormalSignatureKind::NotStored`, `SpendPath::KeySpend`), output0 = user payout, and an `op_return_txout` containing whatever `operator_xonly_pk` is passed in — completely unauthenticated and not part of any operator credential check. [1](#0-0) 
- `Operator::withdraw` verifies the user's signature only against input0/output0 with `sighash_type` expected to be `SinglePlusAnyoneCanPay`, then funds the transaction via `fund_raw_transaction` with `add_inputs: true` — i.e., extra inputs (and by extension, whose money actually pays for output0) are not covered by the user's signature at all. [2](#0-1) 
- Verifiers determine the "payer operator" purely by parsing the `OP_RETURN` of whichever payout tx actually confirms on-chain, with no check that the named operator authored, signed, or funded any part of the transaction: [3](#0-2) 
- This value is persisted as `payout_payer_operator_xonly_pk` and is the sole key used by `get_first_unhandled_payout_by_operator_xonly_pk`, which `PayoutCheckerTask::run_once` polls using the operator's *own* key: [4](#0-3) [5](#0-4) 
- The only sanity check against a mismatched operator, `is_kickoff_malicious`, compares the DB-recorded `operator_xonly_pk` (again, derived only from `OP_RETURN`) against the kickoff's claimed `kickoff_data.operator_xonly_pk` — since both are attacker-controlled/self-declared and equal (P's key), this check passes and the kickoff is *not* flagged malicious: [6](#0-5) 

Exploit flow: The attacker is the withdrawing user (deposits, calls Citrea `withdraw`, and thus legitimately controls `withdrawal_utxo`, its private key, and a valid `SIGHASH_SINGLE|ANYONECANPAY` signature over their own output0). Instead of relying on any operator, the attacker themselves constructs the exact payout transaction shape used by `create_payout_txhandler` — same input0 (their own withdrawal UTXO, self-signed), same output0 (their own payout amount/script) — but adds their own funding input(s) to cover output0's value and sets the `OP_RETURN` to operator P's real, public x-only pubkey. They broadcast it directly to Bitcoin and let it confirm. No operator signature, operator collaboration, or operator broadcast is required anywhere in this path.

Once finalized, `update_finalized_payouts` records payer = P. P's own `PayoutCheckerTask` (running with automation, as it does for every operator) finds this "unhandled payout for P," calls `handle_finalized_payout`, builds and sends a `Kickoff`, and eventually the `Reimburse` transaction pays P `bridge_amount` from the deposit's move-to-vault UTXO — even though P never saw, signed, or funded any part of this payout.

### Impact Explanation
This is a Critical finding: a real, honest, uninvolved operator P is credited and reimbursed `bridge_amount` for a withdrawal it never fronted, and the move-to-vault UTXO is drained to P based purely on the attacker's own self-funded transaction. It is repeatable for every deposit/withdrawal cycle and for any operator whose x-only pubkey is public (all operator pubkeys are public by protocol design). This directly matches the listed Critical category "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" (from the true fronting operator's perspective, since no operator actually fronted this withdrawal).

### Likelihood Explanation
Preconditions are attacker-only and cheap to satisfy: the attacker needs to be a normal bridge user (deposit + call Citrea `withdraw`), needs to know a real operator's x-only pubkey (public), and needs to fund `output0` from their own wallet (cost ≈ withdrawal amount, which they receive back themselves as the withdrawing user — so their net BTC cost for causing this misattribution is close to zero beyond fees). No majority hashrate, no key compromise, and no operator/verifier privilege is required. Automation being enabled on P (the default expected operational mode for a live operator) is the only external precondition, and is explicitly assumed in scope.

### Recommendation
Bind the fronting-operator identity cryptographically rather than trusting an unsigned `OP_RETURN`: require the payout transaction's `OP_RETURN` (or an equivalent operator-identity commitment) to be covered by an operator signature (e.g., have the operator co-sign or use `SIGHASH_ALL`/`SIGHASH_SINGLE` without `ANYONECANPAY` on a dedicated operator-controlled input, or require an operator-signed commitment tying `input_utxo`+`output_txout`+`operator_xonly_pk` together) so the credited operator must be the party who actually authorizes and funds the payout. Additionally, before honoring `payout_payer_operator_xonly_pk` in `PayoutCheckerTask`/`is_kickoff_malicious`, verify that the named operator's own outputs/inputs (not just an arbitrary OP_RETURN byte string) actually funded the differential value beyond the withdrawal UTXO.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
