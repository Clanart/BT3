### Title
Missing-participant panic in `GeneratorPromotion::complete` via attacker-shaped proof map - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the *length* and *upper bound* of the `proofs` map, then unconditionally unwraps `proofs.get(&i)` for every `i` in `1 ..= n`. A malformed map that substitutes an entry keyed at the local participant `params.i()` (or any duplicated/wrong participant) for a genuinely missing participant passes both checks and triggers a panic — an improper-input-validation denial of service directly analogous to the nghttp2 ALTSVC segfault (CVE-2018-1000168).

### Finding Description
The function performs two checks on the untrusted `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

- `proofs.len() == n - 1` [1](#0-0) 
- every key `i` satisfies `u16::from(i) <= params.n()` [2](#0-1) 

Neither check ensures the map actually contains a proof for every participant `1 ..= n` other than `params.i()`. The subsequent loop then does:

```rust
let proof = proofs.get(&i).unwrap();
``` [3](#0-2) 

Because `Participant` is only validated as `non-zero` and `<= n`, a map containing a proof keyed under `params.i()` (the local party, which is skipped by `if i == params.i() { continue; }`) counts toward `n - 1` while leaving some real participant `j` absent. When the loop reaches `j`, `proofs.get(&j)` returns `None` and `.unwrap()` panics, aborting the caller's promotion flow. The `ThresholdKeys::new(...).unwrap()` at line 165 is similarly reachable with attacker-influenced `verification_shares` (each `proof.share` is an unchecked `C::G` read via `read_G`), though the DLEq verification normally constrains it.

### Impact Explanation
Any participant (or anyone able to feed a `Participant`-keyed `GeneratorProof` map, deserialized via `GeneratorProof::read` from untrusted bytes) in a generator-promotion ceremony can deterministically crash the node executing `complete`. In Serai's usage, promotion runs when rotating validators between generators (e.g., Bitcoin → external-generator contexts); a panic here kills the processor/coordinator task mid-protocol, denying service for the key-rotation and any dependent signing. This is a remote, input-triggered denial of service — the same consequence class as the reference advisory.

### Likelihood Explanation
Triggering requires only that a counterparty's proof be delivered under an incorrect/absent `Participant` key such that the map length is still `n - 1`. The protocol explicitly accepts `n - 1` *other* proofs, so a malicious or buggy peer that causes their proof to be registered under the victim's own index (or simply a colluding-by-omission index collision in the integrator's map construction) satisfies the length check while leaving a hole the `unwrap` hits. No cryptographic break is needed — just one malformed keying in a public protocol message. Since the panic occurs before any share math, it works regardless of the DLEq proofs' validity.

### Recommendation
Replace the implicit coverage assumption with an explicit completeness check before the loop — e.g., reuse a `validate_map`-style helper (as in `crypto/dkg/pedpop/src/lib.rs` lines 57–83) that verifies `proofs` contains exactly `{1 ..= n} \ {params.i()}`, rejecting self-keyed and missing entries with `PromotionError::MissingParticipant`/`InvalidParticipant` instead of panicking. At minimum, replace `proofs.get(&i).unwrap()` with `.ok_or(PromotionError::InvalidParticipant { n: params.n(), participant: i })?`.

### Proof of Concept
```rust
// n = 3, local i = 1 (params.i() == Participant(1))
// proofs map supplied by peers keyed at participants {1, 2} — len == n-1 == 2
let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof_a); // keyed at self!
proofs.insert(Participant::new(2).unwrap(), honest_proof_b);   // participant 3 missing

// checks pass: len == 2, all keys <= 3
promotion.complete(&proofs);
// loop: i=1 skipped (self), i=2 verified, i=3 -> proofs.get(&3) == None -> panic! at lib.rs:146
```
