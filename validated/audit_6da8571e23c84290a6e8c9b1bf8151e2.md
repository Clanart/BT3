### Title
Unbounded attacker-controlled element count in `SchnorrAggregate::read` enables memory-exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
CVE-2012-6122 describes a crash caused when an attacker supplies a large integer that is consumed unchecked by a resource-management routine. The Serai analog is `SchnorrAggregate::read`: a 4-byte little-endian `u32` field read from an untrusted stream directly bounds a deserialization loop with no sanity cap, allowing memory usage proportional to — and far exceeding — any sane proof size, up to ~2^32 decoded group elements.

### Finding Description
`SchnorrAggregate::read` reads a `u32` `len` and then loops `0 .. u32::from_le_bytes(len)` pushing `C::read_G(reader)?` into a `Vec<C::G>` [1](#0-0) . There is no upper bound on `len` other than `u32::MAX`, and no cross-check against the number of signatures actually being aggregated (unlike `verify`, which only checks `Rs.len() == keys_and_challenges.len()` [2](#0-1) ).

The count is entirely attacker-controlled. When the reader is a stream (network socket, `io::Read` wrapper) rather than a fixed slice, the attacker can dribble a continuous supply of valid point encodings, forcing the `Vec` to grow toward 4 billion entries. Each entry is a full decompressed/validated group element (32–57+ bytes plus heap overhead), so a single `read` call can consume tens of gigabytes, terminating the process via OOM — a crash reachable purely from the claimed length field, mirroring the original bug class (large integer → unchecked resource consumption → crash).

Note the contrast with defensive patterns elsewhere in the same codebase: `Transaction::read` for DKG commitments checks `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` before allocating [3](#0-2) , and the Ethereum `Call::read` explicitly chunks reads to avoid exactly this DoS [4](#0-3) . `SchnorrAggregate::read` has no equivalent guard.

### Impact Explanation
An unprivileged party who can get a processor/verifier to deserialize a `SchnorrAggregate` (aggregate signature verification is a public-input path) supplies `0xFFFFFFFF` as the length and streams valid group element encodings. The host allocates and retains an unbounded `Vec<C::G>`, exhausting memory and crashing the node — denial of service of a validator/processor, matching the CVE's DoS impact.

### Likelihood Explanation
Requires only that some caller feeds untrusted bytes to `SchnorrAggregate::read` from a non-bounded `Read` source. If all callers use fixed slices, the loop terminates at the first failed `read_G` at EOF and only allocates proportional to real input — reducing this to a proportional-cost issue. The residual risk (streaming readers, or per-call overhead multiplied by repeated requests) keeps this at Medium severity rather than higher.

### Recommendation
Bound `len` in `SchnorrAggregate::read` before the loop — e.g., reject counts above a sane protocol maximum (participant count / `MAX_KEY_SHARES_PER_SET`-style bound), or require `len` to equal the expected `keys_and_challenges.len()` when that is known at read time. Alternatively, read incrementally and cap total bytes consumed, as `Call::read` does [5](#0-4) .

### Proof of Concept
```rust
// Attacker-controlled bytes fed to SchnorrAggregate::<C>::read
let mut msg = vec![];
msg.extend(0xFFFF_FFFFu32.to_le_bytes()); // claim ~4 billion Rs
// Append a continuous stream of valid C::G encodings;
// each read_G succeeds, pushing another element into Rs.
// Vec<C::G> grows unboundedly until the process is OOM-killed.
let _ = SchnorrAggregate::<C>::read(&mut stream); // reader yields attacker bytes
```

Caveat: if every reachable call site in Serai reads from bounded in-memory buffers, the impact degrades to proportional-cost memory use only; full exploitability confirmation requires auditing the callers of `SchnorrAggregate::read`, which live in `processor/` (outside the in-scope crates enumerated for this review).
