## Title
Persisted ERC20 allowance survives failed IBC receive-callback, enabling theft of tokens locked in an unrecoverable isolated address - (File: x/ibc/callbacks/keeper/keeper.go)

## Summary
`IBCReceivePacketCallback` grants an ERC20 `approve` to an attacker-controlled `contractAddress` and then invokes that contract, assuming the invoked function will actually pull the funds via `transferFrom`. The state produced by these two EVM calls (the approval and any side effects the target contract performs) is written back to the real context via `writeFn()` *before* the function verifies that the transfer actually happened. If the post-hoc balance check subsequently fails, the callback returns an error, but the already-committed `approve` is never revoked.

## Finding Description
The comment in the report describes a class of bug where a caller assumes an "action" was executed because the outer call succeeded, while the callee can silently do nothing (or something else), and other state changes made in anticipation of that action are not rolled back. `IBCReceivePacketCallback` reproduces exactly this pattern: [1](#0-0) 

1. `k.erc20Keeper` mints/holds the received IBC tokens on an "isolated address" (`receiverHex`) that is deterministically derived from channel + sender and has no associated private key [2](#0-1) .
2. The keeper calls `approve(contractAddr, amountInt)` **as the isolated address**, granting the attacker-supplied `contractAddress` (taken from the packet memo `dest_callback.address`, fully controlled by the packet sender) permission to move the entire received amount out of the isolated address [3](#0-2) .
3. It then calls the contract with the memo-supplied calldata, expecting the contract to consume that allowance via `transferFrom(receiverHex, contractAddr, amount)` [4](#0-3) .
4. `writeFn()` unconditionally commits both the `approve` and whatever the arbitrary contract call did [5](#0-4) .
5. **Only after commit** does the code check whether the isolated address still holds a non‑zero balance, and if so returns an error [6](#0-5) .

Because commit happens before the invariant check, the check can only *report* that the intended action ("pull all funds") did not happen — it cannot undo the `approve` that was already written to state. An attacker who controls the `contractAddress` field of the memo can trivially author a contract whose invoked function is a no-op (or does something unrelated), deliberately causing the invariant check to fail and the callback to be reported as failed — while the ERC20 allowance for `amountInt` from `receiverHex` to `contractAddr` remains valid in state forever. Since `receiverHex` (the isolated address) has no private key, the tokens can never be moved by their "owner"; the only party who can ever move them is whoever holds `contractAddr`, i.e., the attacker who supplied that address. The attacker can then, in a completely separate later transaction, call `transferFrom(receiverHex, contractAddr, amountInt)` on the ERC20 token/precompile to drain the tokens that are supposedly "stuck" (and which the code comment claims are only meant to become "unrecoverable", not stealable).

## Impact Explanation
This allows unauthorized extraction of user funds that were legitimately transferred via IBC and converted to their ERC20 representation. The victim (the original IBC sender) permanently loses access to the tokens (isolated address has no key), and the attacker (who supplied `contractAddress` in the packet memo) can unilaterally redeem them at will using the surviving allowance — a clear theft of user value mediated entirely through ordinary transaction/callback flow with no privileged access required. This fits the "Critical … theft, or unauthorized extraction of user funds … token-pair-backed balances" impact category.

## Likelihood Explanation
The trigger requires only that an unprivileged user (attacker) initiate/craft an ICS-20 transfer with a `dest_callback` memo pointing at a contract they control that they deliberately author to not call `transferFrom` (or to only partially do so). This is fully within reach of any user who can send an IBC transfer with a custom memo to the target chain — no relayer collusion, validator privilege, or governance action is required. The scenario is a natural variant of already-tested "callback fails" cases in the repo's test suite (see `TestOnRecvPacketWithCallback`), which validate ack/error handling paths but do not appear to assert that the granted allowance is revoked on callback failure.

## Recommendation
- Revoke (or reset to zero) the `approve` granted to `contractAddr` if the post-execution balance check indicates the funds were not fully pulled, before returning the error.
- Alternatively, perform the balance-invariant check inside the same cached context prior to calling `writeFn()`, so that on failure nothing (including the approval) is committed to the real store.
- Consider not granting a standing `approve` at all; instead, use a call pattern that atomically transfers funds to the target contract (or reverts) rather than relying on a callee-initiated `transferFrom` combined with an after-the-fact invariant check.

## Proof of Concept
1. Attacker sends an ICS-20 transfer to the EVM chain with `dest_callback.address` set to `AttackerContract`, where `AttackerContract`'s invoked function is a no-op (does nothing, or only performs unrelated logic) and does not call `transferFrom`.
2. `IBCReceivePacketCallback` executes:
   - `approve(AttackerContract, amount)` from the isolated address `receiverHex` — committed via `writeFn()`.
   - Calls `AttackerContract` with the memo calldata — no tokens moved — committed via `writeFn()`.
   - Balance check finds `receiverHex` still holds `amount` tokens → returns an error; the callback is reported/logged as failed (per IBC-Go callbacks semantics this does not revert the whole packet-receive transaction, since callback failures are isolated from the base transfer application logic).
3. Because `writeFn()` already ran, the `approve(AttackerContract, amount)` persists in state.
4. In a later, independent transaction, `AttackerContract`'s controller calls `token.transferFrom(receiverHex, AttackerContract, amount)` using the still-valid allowance, draining the tokens that legitimately belonged to the original IBC sender (who has no way to ever recover them from `receiverHex`, since it has no private key).

Note: I was not able to fully trace how `ProcessCallback` in the vendored `ibc-go` `callbacks` module treats an error returned from `IBCReceivePacketCallback` (whether it always allows the base transfer/ack to succeed independent of callback failure) since that logic lives in an external dependency not indexed in this repository; this assumption should be verified against the specific `ibc-go` version pinned in `go.mod` before treating this report as fully confirmed, but the core state-commit-before-validation ordering bug in `IBCReceivePacketCallback` itself is directly verifiable from the code shown above.
