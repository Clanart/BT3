### Title
Deep-link/CLI clone URL is passed to `git clone` without protocol allow-listing, enabling `ext::`/`fd::` transport code execution - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/git/clone.ts`)

### Summary
The reported Flayer bug is a "trusted invariant that isn't actually enforced" class of bug: a value that should be constrained/validated (the tax-relevant listing parameters) is allowed to flow through an unchecked path (reserve→liquidate→relist) and produces an unintended, attacker-favorable state. The Desktop analog with the same shape is: a value that should be constrained/validated (the git remote/clone **URL** coming from an untrusted, attacker-controlled deep link or CLI argument) is passed straight into a `git clone` invocation without any protocol allow-listing, letting the attacker choose a Git "transport helper" URL scheme (`ext::`, `fd::`) that Git treats as a local command to execute.

### Finding Description
`parseAppURL` extracts the `url` used for `openRepo` deep links directly from the URL path with no validation of scheme/host — it only regex-validates the `branch` and `pr` query parameters: [1](#0-0) 

This unvalidated `url` is handed to `Dispatcher.openRepositoryFromUrl`, which for the common case (no `pr`/`branch`) calls `openOrCloneRepository(url)`: [2](#0-1) 

The same unvalidated `url` also reaches the app through `--cli-clone` CLI argument handling with no scheme check either: [3](#0-2) 

Eventually the URL is passed as a positional argument to `git clone`: [4](#0-3) 

`clone()` only guards the destination `path` via `isClonePathSensitive`, and only sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and proxy/auth env vars via `envForRemoteOperation`: [5](#0-4) [6](#0-5) 

Nowhere in `envForRemoteOperation`/`envForProxy`, or in `clone.ts`, is `GIT_ALLOW_PROTOCOL` set or is the URL scheme checked against an allow-list (only `https?://` is special-cased for proxy resolution, everything else — including `ext::`, `fd::`, `file://` — passes through untouched): [7](#0-6) 

Git's `ext::` and `fd::` transport helpers execute an arbitrary shell command supplied as part of the "URL" (e.g. `ext::sh -c "id > /tmp/pwn"`). This is a long-known Git remote-helper foot-gun (the class of issue behind CVE-2017-1000117 and related advisories) that upstream Git mitigates for *automatically triggered* clones (e.g., submodule recursion) via `protocol.<name>.allow` defaulting to `user` for `ext`, but a *directly invoked* top-level `git clone <url>` is treated as user-initiated and is not blocked unless the caller explicitly restricts protocols with `GIT_ALLOW_PROTOCOL`/`protocol.allow` env or config. Desktop does none of that here — the `--openrepo`/`x-github-client://` handler and the `--cli-clone` handler both feed an attacker-controlled string straight to the top-level `git clone` invocation.

### Impact Explanation
An attacker who gets a victim to click a `x-github-client://openrepo/<payload>` deep link (e.g. embedded in a webpage, README, or chat message) — or who convinces the victim to run a crafted `--cli-clone` argument, or supplies it via a crafted `github-windows://`/`github-mac://` handoff — can achieve arbitrary command execution on the victim's machine outside of any repository sandbox, with the privileges of the Desktop process. This satisfies the "attacker controls a link/deep link the user clicks... and the result is code execution" criterion directly.

### Likelihood Explanation
The `openrepo` URL action is a first-class, always-registered OS-level protocol handler (`app.setAsDefaultProtocolClient`) reachable from any web page, chat client, or email the moment Desktop is installed and running, requiring only a single click and no other user interaction or pre-existing malware/credentials. The existing validation logic in `parseAppURL` (`testForInvalidChars` on `branch`, digit regex on `pr`) demonstrates the developers know this URL is untrusted input, yet the `url` field itself — which is the one that ultimately reaches `git clone`/`git remote add`/`git fetch` — has no equivalent scheme/host restriction, and no `GIT_ALLOW_PROTOCOL` hardening is applied anywhere in the environment-construction path.

### Recommendation
- Before invoking any git command with a user/URL-supplied remote, reject any URL whose scheme isn't in an explicit allow-list (`https`, `ssh`/`git@` forms already recognized by `remote-parsing.ts`), independent of what Git itself would accept.
- Set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or use `-c protocol.ext.allow=never -c protocol.fd.allow=never -c protocol.file.allow=user`) in `envForRemoteOperation`/`clone()` for every remote-facing git invocation (`clone`, `fetch`, `push`, `pull`, `remote add`, `ls-remote`, ...), not just clone destination path checks.
- Apply the same scheme validation to the `--cli-clone` command-line handler in `app/src/main-process/main.ts`, since it shares the identical unchecked path to `git clone`.

### Proof of Concept
1. Attacker hosts/sends a link:
   `x-github-client://openRepo/ext::sh%20-c%20touch%20/tmp/pwned`
2. Victim (with GitHub Desktop installed and the protocol registered, see `setAsDefaultProtocolClient` in `app/src/main-process/main.ts`) clicks the link.
3. `handleAppURL` → `parseAppURL` parses this as `{ name: 'open-repository-from-url', url: 'ext::sh -c touch /tmp/pwned', branch: null, pr: null, filepath: null }` — no scheme check rejects it (`app/src/lib/parse-app-url.ts:98-124`).
4. `Dispatcher.openRepositoryFromUrl` → `openOrCloneRepository(url)` → eventually `clone(url, path, options)` in `app/src/lib/git/clone.ts` runs `git ... clone --recursive -- "ext::sh -c touch /tmp/pwned" <path>`.
5. Git's `ext::` helper executes `sh -c touch /tmp/pwned` on the victim's machine, demonstrating arbitrary command execution triggered purely by clicking a link.

Note: I was unable to view the full body of `openOrCloneRepository` in `dispatcher.ts` (only its call sites) due to iteration limits, so I cannot 100% confirm there isn't an intermediate scheme check inside that specific method; based on all other validation code found (`parseAppURL`, `remote-parsing.ts`, `repository-matching.ts`, `environment.ts`), no scheme/protocol allow-listing exists anywhere in the reachable path. A Devin session with full file access should verify `openOrCloneRepository`'s implementation directly to close out this gap.
