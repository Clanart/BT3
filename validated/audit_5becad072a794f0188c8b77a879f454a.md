### Title
Auctioneer Signature Does Not Bind Bid Content, Enabling Bid-Field Substitution After Approval - ([File: kaiax/auction/bid.go])

### Summary
In the Kaia auction (KIP-249) bid-pool module, a winning bid is only admitted once two signatures pass: `SearcherSig` (an EIP-712 signature over the `BidData` struct) and `AuctioneerSig` (meant to certify that the `Auctioneer` approved that specific bid). However, `AuctioneerSig` is computed and verified over the *raw bytes of `SearcherSig`* rather than over the `BidData` payload itself [1](#0-0) . This mirrors the authentik SAML bug class: a "wrapper" signature (`AuctioneerSig`, analogous to the SAML Response signature) is checked, but it does not bind the actual content (`BidData`, analogous to the SAML assertion) that the system later trusts and executes — it only certifies that *some* searcher signature blob was seen, not which fields accompany it.

### Finding Description
`ValidateAuctioneerSig` recovers the signer from `GetEthSignedMessageHash()`, which hashes only `b.SearcherSig`: [2](#0-1) 

```go
func (b *Bid) GetEthSignedMessageHash() []byte {
    data := b.SearcherSig
    return crypto.Keccak256(fmt.Appendf(nil, "\x19Ethereum Signed Message:\n%d%s", len(data), data))
}
``` [1](#0-0) 

The pool's admission logic runs both checks independently and treats the pair as sufficient proof of a fully-authorized bid: [3](#0-2) 

Because `AuctioneerSig` never touches `BidData` fields, the auctioneer's approval is only cryptographically bound to the opaque `SearcherSig` blob. The only thing preventing tampering with `BidData` is that `SearcherSig` itself is an EIP-712 signature over `BidData` via `GetHashTypedData` (checked in `ValidateSearcherSig`) [4](#0-3) . This is safe *only if every field of `BidData` that is later consumed by the block-builder/bid-tx-generator is included in that EIP-712 struct hash*.

The `BidData` struct contains a field, `MaxGasPrice`, marked `omitempty` in its JSON tag — unlike every other field in the struct (`TargetTxHash`, `BlockNumber`, `Sender`, `To`, `Nonce`, `Bid`, `CallGasLimit`, `Data`, `SearcherSig`, `AuctioneerSig`, none of which use `omitempty`): [5](#0-4) 

This tag pattern is a strong indicator that `MaxGasPrice` was added to the struct after the original EIP-712 type layout was finalized. If the EIP-712 struct-hash logic (`eip712.go`, `GetHashTypedData`) was not updated in lockstep to include `MaxGasPrice` in the signed digest, then `MaxGasPrice` sits outside the scope of `SearcherSig`'s cryptographic binding — exactly the "assertion wrapping" pattern: a field that rides alongside a signed/verified structure but is not itself covered by any signature that is actually checked before the structure is trusted and acted upon (in this case, used by `BidTxGenerator`/gas-price capping logic referenced in `kaiax/auction/impl/api.go` and `blockchain/system/auction.go`).

Note: I was not able to fully inspect `kaiax/auction/eip712.go`'s exact struct-hash field list before running out of investigation budget, so whether `MaxGasPrice` (or any other field) is concretely excluded from the EIP-712 digest is not 100% confirmed from the code I retrieved — this should be verified directly against `GetHashTypedData`'s field list. What is confirmed is the structural weakness: `AuctioneerSig` provides zero content-binding of its own, so the security of the whole two-signature scheme rests entirely on `SearcherSig`'s struct hash being complete, with no defense-in-depth if it is not.

### Impact Explanation
If any `BidData` field consumed during bid execution (e.g., `MaxGasPrice`, which gates the gas price used to build/execute the winning bid transaction per `blockchain/system/auction.go`) is not included in the EIP-712 digest signed by `SearcherSig`, a bid relayer/searcher/attacker-in-the-middle of the P2P bid gossip (`HandleBid` in `kaiax/auction/impl/bid_pool.go`, lines 421-437) could mutate that field after obtaining a valid `(SearcherSig, AuctioneerSig)` pair while both signature checks still pass. This could be used to bypass the searcher's intended gas-price cap, causing unintended fee extraction/fee abuse during auction settlement, or to manipulate other unbound fields to redirect execution parameters — a concrete fee/auction-settlement abuse scenario reachable purely by an unprivileged auction bidder/searcher, matching the required impact class (fee abuse / auction settlement theft).

### Likelihood Explanation
Likelihood depends entirely on whether `GetHashTypedData` in `eip712.go` omits any live `BidData` field (most plausibly `MaxGasPrice`, given its distinct `omitempty` tag suggesting later addition). If confirmed, exploitation requires no special privilege beyond being able to observe or relay a legitimately-approved bid (any auction participant/searcher, or any P2P peer relaying `HandleBid` messages), making likelihood Medium-to-High if the gap exists, though this final confirmation could not be completed due to tool-call exhaustion.

### Recommendation
- Audit `kaiax/auction/eip712.go`'s `GetHashTypedData` to confirm every field of `BidData` (especially `MaxGasPrice`) is included in the EIP-712 struct hash that `SearcherSig` commits to.
- Change `AuctioneerSig` to sign over the full canonical `BidData` (or its RLP/EIP-712 hash) rather than the raw `SearcherSig` bytes, so the auctioneer's approval is directly and independently bound to bid content — removing single-point-of-failure reliance on `SearcherSig`'s completeness.
- Add a regression test that mutates each `BidData` field individually after both signatures are generated and asserts that `ValidateSearcherSig` and/or `ValidateAuctioneerSig` fail for every field.

### Proof of Concept
Conceptual (pending confirmation of the exact unbound field via `eip712.go`):
1. A searcher builds a legitimate `Bid` with `MaxGasPrice = X`, computes `SearcherSig` over the EIP-712 digest of `BidData`, and submits it to the `Auctioneer`.
2. The `Auctioneer` approves it, computing `AuctioneerSig` over `keccak256("\x19Ethereum Signed Message:\n" + len(SearcherSig) + SearcherSig)` — i.e., only over the `SearcherSig` bytes [1](#0-0) .
3. Before/while relaying the bid over the auction P2P channel (`HandleBid`), an intermediary changes `bid.MaxGasPrice` to a different value, leaving `SearcherSig` and `AuctioneerSig` byte-for-byte unchanged.
4. `validateBidSigs` calls `ValidateSearcherSig` and `ValidateAuctioneerSig` [3](#0-2) ; if `MaxGasPrice` is not part of the EIP-712 digest, `ValidateSearcherSig` still succeeds (digest unchanged), and `ValidateAuctioneerSig` trivially succeeds (it never looked at `MaxGasPrice`). The tampered bid is admitted to the pool and used for block building with the attacker-controlled `MaxGasPrice`.

func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

	}

		return fmt.Errorf("invalid auctioneer sig: expected %v, calculated %v", auctioneer.String(), recoveredAuctioneer.String())

```go
func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
