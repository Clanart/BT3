### Title
Bitcoin transaction signatures are replayable across compatible chain forks - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`TransactionSignMachine::sign` signs only the Taproot key-spend sighash for each input, using `Prevouts::All`; it does not bind the signature to a chain identifier, genesis hash, or other fork-specific value. The challenge used by the Bitcoin Schnorr algorithm commits only to the nonce, public key, and supplied sighash message. Consequently, a completed transaction can be replayed on a compatible fork where the same UTXOs exist.

### Finding Description
`TransactionSignMachine::sign` requires the externally supplied message to be empty and internally derives every signing message from the transaction and all previous outputs. [1](#0-0) [2](#0-1)  Each input is signed with `taproot_key_spend_signature_hash`, but neither the transaction structure nor the resulting Taproot sighash includes a Serai-level chain or network identifier. [3](#0-2) 

The Bitcoin Schnorr challenge is computed as `BIP0340/challenge` over the x-coordinates of `R` and `A` plus the supplied message. No additional chain/domain field is incorporated before reduction to the challenge scalar. [4](#0-3)  After completion, the signature is copied directly into the transaction witness, leaving the completed transaction valid on any compatible chain sharing the same consensus rules and UTXO state. [5](#0-4) 

### Impact Explanation
If the chain forks while preserving Serai-controlled UTXOs and the same Taproot signing rules, a signed spend intended for one fork remains valid on the other fork. An observer can copy the completed transaction and broadcast it on the second chain, causing the same inputs to be spent and the same outputs to be created there without any additional authorization from the threshold group.

For example, if the transaction pays Alice on the new fork and includes Bob's change output, Alice can replay it on the old fork and receive the corresponding old-fork coins while Bob receives only the duplicated change output. The impact is loss of fork-side funds controlled by the transaction outputs, not compromise of the threshold secret shares.

### Likelihood Explanation
Exploitation requires a compatible fork sharing the UTXO set, output scripts, Taproot signature rules, and sighash algorithm. It also requires the attacker to obtain the completed transaction, which becomes public once broadcast or can otherwise be supplied by a signing participant. When those prerequisites hold, replay requires no private-key material or interaction with the signers because the already-produced witness satisfies the copied transaction.

### Recommendation
Document that `SignableTransaction` produces network-portable Bitcoin spends and must only be used for chains whose consensus already provides replay protection. Where cross-fork replay must be prevented, require the target chain to provide a distinct signature hash domain or other consensus-level replay mechanism, and ensure the fork uses different threshold keys or output offsets. Do not attempt to append an ad-hoc chain identifier to the existing BIP-340 message unless the target consensus validates that modified message format.

### Proof of Concept
1. Create two compatible chains from a common snapshot in which the same Serai-controlled Taproot UTXO exists.
2. On chain A, build a spend paying Alice with `SignableTransaction::new`, then run `multisig`, `preprocess`, `sign`, and `complete`. `sign` ignores external context and signs the ordinary Taproot sighash for each input. [1](#0-0) [3](#0-2) 
3. Broadcast or disclose the completed transaction.
4. Alice submits the byte-identical transaction on chain B. Because the challenge commits only to `R`, the public key, and the unchanged sighash, the copied witness remains valid while chain B contains the same spendable input. [4](#0-3) [5](#0-4)
