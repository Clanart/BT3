### Title
Attacker-controlled length field in `SchnorrAggregate::read` drives an unbounded loop of group-element decompressions, enabling CPU/memory exhaustion — ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
The reported bug class is "an unbounded loop over an attacker-controlled list whose per-iteration cost exhausts resources and aborts the operation." In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregate::read` reads a raw `u32` element count from untrusted bytes and then executes `for _ in 0 .. u32::from_le_bytes(len) { Rs.push(C::read_G(reader)?) }` with no upper bound on the declared count. This is a generic `read` entry point in the in-scope `schnorr` crate, reachable whenever aggregate signatures (e.g., `SignedBatch`-style aggregates used to cosign tributary blocks / network batches) are deserialized from wire bytes.

### Finding Description
In `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`):

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }

    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

Two resource issues exist:

1. **Unbounded iteration count**: `len` is a fully attacker-controlled `u32` (up to ~4.3 billion). There is no sanity cap relating `len` to the number of signers, the set size, or the remaining input length before the loop begins. Each iteration performs `C::read_G`, which for in-scope ciphersuites (Ristretto via `dalek-ff-group`, secp256k1, ed448, schnorrkel curve) is a full point decompression — canonical-encoding check plus a field square root / inversion — orders of magnitude more expensive than the ~32 bytes of input consumed per element. An attacker controls the total expensive work performed purely by setting the prefix and supplying compressed points, obtaining significant CPU amplification per byte sent.

2. **Unbounded memory growth**: `Rs` starts as `vec![]` and grows one `C::G` per iteration. Unlike `Commitments::read` in `crypto/dkg/pedpop/src/lib.rs:111` — which is bounded by `params.t()` — or `ThresholdKeys::read` in `crypto/dkg/src/lib.rs:608-623` — which is bounded by a `u16` `n` — here the bound is `u32::MAX` with no protocol-level cap. For internal point representations larger than their encoding (e.g., curve25519 `EdwardsPoint` is 4× its 32-byte repr), an attacker-supplied buffer of size `m` inflates into several times `m` bytes of resident group elements.

The same shape exists in `SchnorrAggregate::verify` (`aggregate.rs:127-146`), where `keys_and_challenges.len()` is compared against `self.Rs.len()` and then a per-element `weight()` derivation plus a `multiexp_vartime` over `2n+1` pairs is run — the verify path amplifies the attacker's declared `n` into `O(n)` hash-transcript squeezes and `O(n log n)` multiexponentiation work, all driven by the deserialized `Rs` count.

### Impact Explanation
An unprivileged party that can cause a validator/processor/coordinator to deserialize attacker bytes through `SchnorrAggregate::read` (or any verifier that forwards deserialized `Rs`/`keys_and_challenges` into `verify`) can force the node to spend unbounded CPU on point decompressions and unbounded memory on the `Rs` vector, stalling block/cosignature processing or crashing via OOM — the direct analog of "the unbounded loop consumes all gas and reverts the transaction." Because aggregate signatures gate progress (a batch that fails to verify or a node that stalls aborts the round), repeated malicious inputs create a persistent liveness failure for the affected validator set. No secret material is needed by the attacker; only control over the length prefix and following bytes.

### Likelihood Explanation
The length field is a plain `u32` under the sender's control, deserialization happens before any signature validity is established, and `read` is invoked by callers on wire bytes. The exploit requires only sending bytes with a large count followed by valid compressed encodings (or even arbitrary bytes up to the first invalid element, still consuming a decompression per element). No valid signature, key share, or privileged position is required.

### Recommendation
- Bound `len` in `SchnorrAggregate::read` against a protocol maximum (the maximum possible number of aggregated signers/statements), rejecting inputs that exceed it before looping.
- Pre-check that the remaining input is at least `len * size_of::<C::G::Repr>()` so a short buffer fails fast instead of burning a decompression per element.
- Use `Vec::with_capacity(len)` only after the bound check, or stream-verify without materializing all `Rs` first.
- In `verify`, early-reject `keys_and_challenges`/`Rs` counts above the validator-set size before entering `weight()`/`multiexp_vartime` loops.

### Proof of Concept
Conceptually, against a Ristretto-based aggregate reader:

```rust
use std::io::Cursor;
use schnorr::SchnorrAggregate;
use ciphersuite::Ristretto;

// Attacker claims ~4.3 billion nonces
let mut buf = u32::MAX.to_le_bytes().to_vec();
// Append as many valid compressed Ristretto encodings as bandwidth allows.
// Each 32 bytes forces a full decompress + grows Rs by one EdwardsPoint (~128 B).
let identity = <Ristretto as ciphersuite::Ciphersuite>::generator();
for _ in 0 .. 1_000_000 { // 32 MB input -> ~128 MB of points + 1M decompressions
    buf.extend(identity.to_bytes());
}
let _ = SchnorrAggregate::<Ristretto>::read(&mut Cursor::new(buf));
```

Even without valid points, each iteration still attempts `read_G` until the first invalid encoding, so cost scales linearly with attacker-supplied bytes at heavy per-element cost; with valid encodings, memory grows without any protocol cap. A subsequent `verify` call with a matching `keys_and_challenges` list compounds this into `O(n)` transcript squeezes and a `2n+1`-term `multiexp_vartime`.
