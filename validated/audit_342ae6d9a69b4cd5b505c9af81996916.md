### Title
Fee/weight estimation omits the OP_RETURN output, so the signed transaction pays less than the requested fee rate and can exceed the standard weight limit - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` estimates the transaction weight/vbytes (and hence `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check) by building a template transaction from `payments` only, after the OP_RETURN data output has already been pushed into `tx_outs`. The discrepancy between the computed and actual fee grows with the attacker-controlled `data` length, mirroring the audit class where an iterated/approximated model drifts unpredictably from the true value. An unprivileged party who can get a payment signed with `data` causes the multisig to sign a transaction that underpays the requested feerate — possibly below the relay minimum — or exceeds the standard weight, leaving funds stuck in an unbroadcastable transaction.

### Finding Description
- The OP_RETURN output is appended to `tx_outs` before any weight calculation:
  `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })` [1](#0-0) 
- `calculate_weight_vbytes` is then called with `payments` (which excludes `data`), so both `weight`/`vbytes` and the change-inclusive `weight_with_change`/`vbytes_with_change` never account for the OP_RETURN output:
  `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);`
  and `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` [2](#0-1) 
- `needed_fee = fee_per_vbyte * vbytes` and the minimum-relay check both use this underestimated vbytes, so the paid fee can fall below `DEFAULT_MIN_RELAY_TX_FEE` for the actual transaction size [3](#0-2) 
- The change amount is computed as `input_sat - payment_sat - fee_with_change`, so the leftover (which should have been fee for the OP_RETURN bytes) is swept into change — the transaction genuinely pays the underestimated fee [4](#0-3) 
- The weight cap check `weight > MAX_STANDARD_TX_WEIGHT` also uses the underestimated weight, so a transaction near the limit with up to 80 bytes of `data` (~370 extra weight units: 8-byte amount + script + output overhead, serialized non-witness) can exceed the standard limit and be rejected by relay policy [5](#0-4) 

### Impact Explanation
The signed transaction pays `fee_per_vbyte * vbytes_underestimated` while its real vsize is larger by the OP_RETURN output (~34 vbytes for 80 bytes of data). At low specified feerates the effective feerate can drop below Bitcoin's minimum relay fee, making the transaction unpropagatable; near `MAX_STANDARD_TX_WEIGHT` the transaction can be outright nonstandard. Funds committed as inputs are locked in a transaction the network will not accept, requiring a costly recovery (new signatures on a corrected transaction). Additionally `needed_fee()`/`fee()` report an incorrect accounting to callers such as the processor's `needed_fee`/`amortize` logic, so fee amortization charged to payments is understated.

### Likelihood Explanation
Any caller supplying `data` (up to 80 bytes, permitted by the `TooMuchData` check) triggers the underestimate. The stuck-transaction case additionally requires the feerate to be near the minimum or the weight near the cap, but the systematic underpayment of the requested feerate occurs on every transaction carrying data.

### Recommendation
Include the OP_RETURN output in the template transaction used by `calculate_weight_vbytes` — e.g., pass `tx_outs` (or `payments` plus the data output) so `weight`, `vbytes`, `needed_fee`, the minimum-fee check, and the `MAX_STANDARD_TX_WEIGHT` check are computed over the exact final output set. Alternatively, build the full transaction once and compute weight directly from it rather than from an approximation.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// With inputs = [one ReceivedOutput], payments = [one payment], change = Some(...),
// and data = Some(vec![0u8; 80]):

let tx = SignableTransaction::new(inputs, &payments, change, data, fee_per_vbyte)?;

// tx_outs contains: payment output, OP_RETURN output, change output
// but weight/vbytes were computed only for payment + change outputs.
let actual_vsize = tx.transaction().vsize() as u64;
let paid_fee = tx.fee();               // == fee_per_vbyte * underestimated_vbytes
let intended = fee_per_vbyte * actual_vsize;
assert!(paid_fee < intended);          // underpay grows with data.len()

// If fee_per_vbyte * underestimated_vbytes == min relay fee for the
// underestimated size, the real feerate is < DEFAULT_MIN_RELAY_TX_FEE
// and the fully-signed TX is rejected by relay policy.
```
