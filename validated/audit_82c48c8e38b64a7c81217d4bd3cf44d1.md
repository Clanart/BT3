This CVE describes a Java-specific vulnerability class — JNDI `ObjectFactory` reference deserialization enabling "gadget chain" exploitation via `com.mchange.v2.naming.JavaBeanObjectFactory` and `ReferenceIndirector`. This bug class fundamentally relies on Java's JNDI lookup mechanism and Java's native object serialization (`ObjectInputStream`), neither of which exist in Go.

I checked the relevant deserialization/reflection-based decoding paths in sei-chain for an analogous pattern (arbitrary type materialization from untrusted input):

- `sei-cosmos/codec/types/interface_registry.go`'s `UnpackAny` only constructs types that are explicitly present in a pre-registered `interfaceImpls` map keyed by `TypeUrl`, and requires the type to implement `proto.Message` — there is no arbitrary class instantiation path. [1](#0-0) 
- The legacy Amino-style JSON decoder in `sei-tendermint/libs/json/decoder.go` explicitly refuses to decode into `reflect.Interface` kinds, closing off the "materialize arbitrary type from data" pattern that JNDI/Java deserialization gadgets rely on. [2](#0-1) 
- CosmWasm's custom message decoding (`fromReflectRawMsg` in `sei-wasmd/x/wasm/keeper/reflect_test.go`) unpacks `Any` messages the same restricted way, through `cdc.UnpackAny`, bound to the registry. [3](#0-2) 

None of these expose a mechanism where an unprivileged transaction sender, contract deployer, or RPC client could cause the node to instantiate an attacker-chosen class/type and invoke arbitrary property setters or trigger a "gadget chain," which is the actual root cause described in the advisory. This is a dependency-only bug specific to a Java library (`mchange-commons-java`/JNDI) with no reachable analog in sei-chain's Go codebase, so per the rules (dependency-only bugs are out of scope, and no equivalent code path exists), there is no valid analog to report.
