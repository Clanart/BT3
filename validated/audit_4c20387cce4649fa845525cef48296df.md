### Title
Oracle staleness gating in `price-resolve` can indefinitely block withdrawals, repayments, and borrows, freezing user funds - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`price-resolve` in `mainnet/contracts/market/v0-4-market.clar` reverts with `ERR-ORACLE-INVARIANT` whenever a feed's Pyth/DIA timestamp is older than the asset's `max-staleness` window, or reverts with `ERR-PRICE-CONFIDENCE-LOW` whenever the Pyth confidence interval exceeds `max-confidence-ratio`. Every user action that needs to value the user's position — `collateral-remove` with an open debt, `borrow`, and by extension `repay`/liquidation flows — calls into this same gated price path for every asset in the user's collateral/debt mask. This is the same bug class as the reported `finalizeGame()` issue: a hard time/confidence threshold that, once missed (chain congestion, delayed Pyth/DIA publishes, feed provider downtime), makes the contract permanently unable to settle a user's already-earned position until a fresh, in-threshold report arrives, with no alternate path to unlock the user's own funds in the meantime.

### Finding Description
`oracle-timestamp-fresh` enforces `delta <= max-staleness` where `delta` is the difference between `stacks-block-time` and the feed's `publish-time`: [1](#0-0) 

`price-resolve` asserts both this freshness check and `oracle-price-legal`, aborting the whole call with `ERR-ORACLE-INVARIANT` if either fails: [2](#0-1) 

`resolve-pyth` additionally gates on confidence via `check-confidence`, which reverts with `ERR-PRICE-CONFIDENCE-LOW` if the reported confidence interval is too wide relative to price: [3](#0-2) 

This gated `price-resolve` is not confined to a single, isolated action — it is invoked from the core user-facing flows. `collateral-remove` (when the account has any debt) computes `notional-valued-assets` over the account's full asset mask and, for disabled collateral, calls `price-resolve` directly with `ERR-DISABLED-COLLATERAL-PRICE-FAILED` on failure: [4](#0-3) 

`borrow` similarly resolves prices for the account's whole mask before allowing the borrow to proceed: [5](#0-4) 

Because `get-asset-value`/`get-notional-evaluation` calls `price-resolve` per asset in the account's mask (via `try!`), a single stale or low-confidence feed for *any* asset the account holds as collateral or debt — not necessarily the asset the user is trying to act on — is enough to abort the entire transaction: [6](#0-5) 

There is no fallback that lets a user withdraw already-healthy collateral, repay debt (an action that only reduces risk), or otherwise recover funds while the feed is stale/low-confidence — the transaction simply reverts until a compliant new report is published on-chain.

### Impact Explanation
This is a staleness/confidence-gating bug class: an external dependency (oracle publish cadence) directly controls the availability of the user's own already-deposited or repayable funds. During any period where Pyth/DIA publishing lags, is delayed, or produces high-confidence-interval reports beyond `max-confidence-ratio`, users holding or owing an affected asset cannot withdraw enabled collateral, cannot repay debt to de-risk their own position, and cannot borrow — even though their position may be perfectly healthy and the action would not require an updated price to be safe (e.g., pure debt repayment). This matches the "High — temporary freezing of funds" impact class: funds are not stolen, but legitimate, non-risk-increasing user actions on the user's own funds are blocked for the duration of the oracle disruption, with no override.

### Likelihood Explanation
Likelihood is tied to oracle infrastructure reliability rather than an on-chain exploit: Stacks chain congestion, Pyth/DIA publisher downtime, or any delay that pushes `publish-time` beyond the configured `max-staleness` (or produces an abnormally wide confidence interval) will trigger this for every affected asset simultaneously across the whole market, not just a single position. This requires no attacker action and can occur purely from external infrastructure conditions, similar to the reported chain-downtime scenario in the original `finalizeGame()` bug.

### Recommendation
Decouple the ability to close/exit a position from the requirement of a perfectly fresh oracle report:
- Allow risk-reducing actions (repay, and withdrawals that keep the position healthier) to proceed using the most recent stored price even if it exceeds `max-staleness`, clearly flagging such operations as using a stale/lower-confidence price rather than reverting outright.
- Consider a degraded/fallback mode (e.g., using the last valid on-chain reference price with a wider safety margin) instead of a hard revert, so temporary oracle unavailability cannot indefinitely lock user funds.
- Ensure repay-type flows do not require resolving prices for unrelated collateral assets in the mask when the action itself cannot worsen the account's health.

### Proof of Concept
1. User has a healthy position with collateral in asset A (fresh) and asset B (stale beyond `max-staleness` due to Pyth publisher delay).
2. User calls `repay` or `collateral-remove` intending only to reduce or remove asset-A-related risk.
3. Because the account's mask includes asset B, `get-notional-evaluation`/`get-asset-value` invokes `price-resolve` for asset B, which reverts with `ERR-ORACLE-INVARIANT` per [7](#0-6) .
4. The entire transaction reverts; the user cannot repay or withdraw until Pyth/DIA republishes a fresh-enough, sufficiently confident price for asset B — funds remain temporarily frozen with no on-chain workaround.
