### Title
Silent Git Remote Overwrite via Owner/Name-Keyed GitHub Repository Upsert - (File: `app/src/lib/stores/repositories-store.ts`)

### Summary
`RepositoriesStore._upsertGitHubRepository()` resolves whether an incoming `IAPIRepository`/`IAPIFullRepository` object corresponds to an *already-tracked* local `GitHubRepository` record purely by looking up the composite index `[ownerID+name]`, never by the GitHub API's stable numeric repository `id`. If a repository object arrives (from a background refresh, PR fetch, or fork conversion) whose owner login and name collide with an existing tracked repository but which actually represents a *different* underlying GitHub repository, the existing DB record's `cloneURL`/`htmlURL` fields are silently overwritten. This is the same broken-invariant class as the reported Solidity bug: a duplicate/identity check that inspects a mutable, attacker-influenceable proxy value (owner login + name) instead of a durable unique identifier, permitting overwrite of a security-relevant stored reference.

### Finding Description
`_upsertGitHubRepository` performs the lookup and overwrite here: [1](#0-0) 
and then persists the new URLs onto the *existing* row (same `id`) without ever comparing a stable GitHub repository identifier: [2](#0-1) 

The composite key used for identity is `[ownerID+name]` — i.e., "does the owner and repo name match" — which is exactly analogous to the vault's `require()` check that only inspected a mutable flag (`creditManagersCanRepay`) instead of true membership in the `creditManagers` list. Here, owner login/repo name is not a durable identity: GitHub repositories can be deleted and re-created under the identical `owner/name` pair (or an org can be renamed/reused), producing a completely different underlying repository with a different clone URL, while presenting the same `owner.login` + `name` to the API.

Once the stale local `GitHubRepository.cloneURL` has been overwritten with attacker-controlled data, `updateRemoteUrl()` can then silently repoint the user's actual git remote to match it, with no user confirmation: [3](#0-2) 

This function trusts `gitHubRepository.cloneURL` (the very same field that was just silently overwritten) as the baseline for deciding whether the user's remote is "unchanged" and safe to auto-update to the new API-provided clone URL.

### Impact Explanation
If exploited, this leads to silent corruption of what the user pushes/fetches: Desktop's own git remote URL for `origin` can be rewritten to a URL that is not the one the user originally configured, without any dialog or confirmation. Because the trigger is a normal API response (repository info refresh, pull-request data, or fork lookups) rather than any local/admin action, this falls squarely into the requested impact class ("silent corruption of what the user commits or pushes," driven by "a GitHub API object"). Depending on where the mismatched repository is subsequently used (push destination, clone re-validation), this could result in the user unknowingly pushing commits to, or fetching malicious refs from, an attacker-controlled repository.

### Likelihood Explanation
Likelihood is **uncertain/moderate** rather than confirmed high, for two reasons I could not fully verify within the indexed code:
1. I could not fully trace every call site that supplies attacker-influenceable `IAPIRepository`/`IAPIFullRepository` objects into `upsertGitHubRepository`/`upsertGitHubRepositoryLight` (e.g., `pull-request-store.ts` upserts using PR head/base repo data returned by the API, which is a plausible attacker-adjacent input path since PR head repos are often forks controlled by third parties) — see the caller here: [4](#0-3) 
2. I could not confirm the exact implementation of `putOwner()` (not retrieved in this session) to verify it doesn't itself pin the owner to a durable numeric owner ID that would prevent the name-collision scenario.

Both gaps stem from index size limits on the codebase; a full-repository clone/session would be needed to confirm every call path and the `putOwner` implementation.

### Recommendation
Change the identity check in `_upsertGitHubRepository` (and `upsertGitHubRepositoryFromMatch`) to key off the GitHub API's immutable repository `id` rather than the `[ownerID+name]` composite, falling back to name-based matching only for brand-new repositories never seen before. Additionally, `updateRemoteUrl()` should not automatically rewrite a user's configured git remote based on API-supplied `clone_url` without confirming the underlying repository `id` is unchanged, and ideally should prompt the user before altering remote configuration.

### Proof of Concept
1. User clones `https://github.com/org-x/widget` and Desktop tracks it, storing a `GitHubRepository` DB row keyed by `[ownerID(org-x), name(widget)]` with `cloneURL = https://github.com/org-x/widget.git`.
2. `org-x/widget` is deleted and immediately re-created (or transferred) such that a different underlying repository now exists at the same `owner.login/name` but with a different `clone_url` (e.g., pointing to an attacker-controlled mirror/proxy, or simply a different, unrelated codebase).
3. Any Desktop background flow that calls `upsertGitHubRepository`/`upsertGitHubRepositoryLight` with the new API repository object (e.g., PR fetch flow in `pull-request-store.ts`, periodic repository info refresh) matches the existing DB row via `[ownerID+name]` and overwrites `cloneURL`/`htmlURL` in place — see `app/src/lib/stores/repositories-store.ts:613-666`.
4. On the next fetch/refresh cycle, `updateRemoteUrl()` sees `remoteUrlUnchanged === true` (compared against the just-overwritten `cloneURL`) and `urlsMatch === false` (new clone URL differs from the actual git remote), and silently calls `gitStore.setRemoteURL(...)` to repoint the user's real `origin` remote — `app/src/lib/stores/updates/update-remote-url.ts:36-44`.
5. Subsequent user-initiated `git push`/`git fetch` operations from Desktop now target the unintended repository, with no warning shown to the user.
