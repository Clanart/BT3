### Title
Unauthenticated aggregator gRPC calls can trigger `get_entity_statuses(restart_tasks=true)`, restarting verifier/operator background tasks with no client certificate - ([File: core/src/servers.rs])

### Summary
When `config.client_verification == false`, `create_grpc_server` builds `ServerTlsConfig::new().identity(server_identity)` with no `.client_ca_root(...)` and wraps the service with the `Noop` interceptor instead of `OnlyAggregatorAndSelf`. This means the aggregator's public TLS listener performs no client-certificate request or authorization check at all, so any internet host can call `AggregatorServer::get_entity_statuses` with `restart_tasks=true`, causing the aggregator to invoke `restart_background_tasks` on every reachable operator and verifier.

### Finding Description
The broken binding: `caller of get_entity_statuses(restart_tasks=true)` should equal `an authorized/authenticated party the aggregator's operator and TLS layer trusts`, but with `client_verification == false` this equality fails — no client certificate is required at the transport layer at all.

Code path:
- [1](#0-0)  — the TLS config branch only calls `.identity(server_identity)` when `client_verification` is false, omitting `.client_ca_root(...)` entirely, so rustls/tonic never requests or verifies a client certificate during the handshake.
- [2](#0-1)  — the interceptor selection mirrors this: when `client_verification` is false the `Noop` interceptor is installed instead of `OnlyAggregatorAndSelf`, so there is no post-handshake authorization check either.
- [3](#0-2)  — `Aggregator::get_entity_statuses` accepts a `restart_tasks: bool` argument directly from the RPC caller with no internal permission check.
- [4](#0-3)  — when `restart_tasks` is true, the aggregator calls `restart_background_tasks` on every operator and verifier client it holds, which is a real state-changing RPC dispatched to all connected verifiers/operators.

Exploit flow: an attacker with no key material, no TLS certificate, and no bridge role opens a TLS connection to the aggregator's public gRPC port (which, per the claim, defaults to `client_verification == false`), completes the handshake with no client cert exchange (permitted because `client_ca_root` was never configured), and calls `GetEntityStatuses{restart_tasks: true}`. The `Noop` interceptor passes the request through unchecked, and `get_entity_statuses` unconditionally issues `restart_background_tasks` RPCs to every operator/verifier client in `operator_clients`/`verifier_clients`.

Why existing guards don't help: `OnlyAggregatorAndSelf` (which validates the caller's certificate against `aggregator_cert`/`our_cert`) is only installed when `client_verification == true`; it is bypassed by design in the `false` branch, and there is no secondary authorization check inside `get_entity_statuses` itself.

### Impact Explanation
The directly reachable state change is limited to invoking `restart_background_tasks` on operator and verifier servers via the aggregator's own (separately mutually-authenticated) channel to those entities — the attacker does not directly reach verifier/operator RPC surfaces, only forces the aggregator to relaunch its own background task supervisors. This repo's own background-task restart mechanism is a supervised task respawn, and no code path was found in the excerpts reviewed that ties a restart of these tasks to fund movement, reimbursement crediting, or collateral loss (no move-to-vault UTXO spend, no reimbursement transaction, no collateral burn is triggered by this call). Per the audit's severity rubric, "an unauthenticated state-changing… call" is listed as a High category on its own, and this call does qualify structurally as unauthenticated and state-changing, but the practical blast radius demonstrated here is an availability/operational disruption (background task restarts across every reachable verifier and operator) rather than a fund-moving or reimbursement-affecting mutation, and the audit rules explicitly exclude denial-of-service/retry/resource-exhaustion-style findings from scope.

### Likelihood Explanation
Preconditions are narrow but plausible: `config.client_verification == false` on the aggregator's TCP listener (claimed to be the aggregator default), and network reachability to the aggregator's gRPC port. No BTC, fees, or any bridge role is required — a bare TLS client is sufficient, and the call is trivially repeatable against every deployment running with this configuration.

### Recommendation
Always configure `.client_ca_root(...)` on the aggregator's `ServerTlsConfig` (mutual TLS should not be optional for a component with authority to trigger background-task restarts across the fleet), or, at minimum, gate `restart_tasks=true` behind the same `OnlyAggregatorAndSelf`-style certificate check regardless of the global `client_verification` flag, rather than relying on a `Noop` interceptor when verification is disabled.
