### Title
OP_RETURN `data` output excluded from fee/weight estimation, producing transactions that under-pay the intended fee rate and can fall below the minimum relay fee - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
This is an analog of the GMX "gas measured before the external call" finding: a resource cost is measured on an incomplete object, so the accounting derived from it (`needed_fee`, minimum-relay-fee check, `NotEnoughFunds` check, and the change calculation) is wrong. In `SignableTransaction::new`, the OP_RETURN output carrying caller-supplied `data` is pushed into `tx_outs` (send.rs:194-202) *before* `calculate_weight_vbytes` is invoked, yet `calculate_weight_vbytes` is only given `tx_ins.len()` and `payments` (send.rs:204) — the data output is never included in the estimated transaction. Every fee-related decision that follows is computed against a transaction that is smaller than the one actually built.

### Finding Description
`SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150) builds the real `tx_outs` list, appending a zero-valued OP_RETURN output when `data` is `Some`:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` (send.rs:62-127) reconstructs a template `Transaction` from `inputs`, `payments`, and an optional `change` script — it has no awareness of `data`/`tx_outs`. Consequently:

1. `vbytes`/`needed_fee` understate the real serialized size by `OP_RETURN_output_size` (up to ~90+ bytes for the 80-byte data limit checked at send.rs:171).
2. The `TooLowFee` check at send.rs:211 validates `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the understated `vbytes`, so a transaction can pass this check while its *actual* fee rate is below the minimum relay fee.
3. When `change` is provided, `fee_with_change` (send.rs:225-227) is computed the same way, and the change output value is `input_sat - payment_sat - fee_with_change`. Since the OP_RETURN is valueless, the change amount itself is "correct" arithmetically, but the *realized* fee rate is `(actual_fee) / (actual_vbytes)`, strictly less than `fee_per_vbyte` requested.
4. `needed_fee()` (send.rs:133) reports the underestimated value to callers, while `fee()` (send.rs:138) reports the true fee — the two disagree whenever `data` is set.

Mirroring the original report: the "starting gas" (`vbytes`) is measured before the full payload (the data output) is accounted for, so the derived refund/fee accounting is systematically wrong.

### Impact Explanation
- Any `SignableTransaction` built with `data` pays a lower effective sat/vbyte than the caller specified. If `fee_per_vbyte` is at or near the minimum relay rate, the resulting transaction is below `DEFAULT_MIN_RELAY_TX_FEE` for its real size and will be rejected by Bitcoin Core relay — funds committed as inputs are unspendable via this transaction and the send silently produces an unbroadcastable artifact (the constructor returns `Ok`).
- Callers relying on `needed_fee()` under-budget the fee; callers relying on `fee()` after the fact observe a fee that never matched the requested rate. On Serai's usage pattern (`processor/src/networks/bitcoin.rs:446` currently passes `data: None`), the bug is latent, but `data` is a public parameter of an in-scope wallet API and the failure is deterministic for any `Some(data)` input.

### Likelihood Explanation
The defect is unconditional: any call to `SignableTransaction::new` with `data: Some(_)` triggers it — no attacker timing or privileged position needed. Realization of harm additionally requires `fee_per_vbyte` near the relay minimum (for unrelayable TXs) or a consumer that trusts `needed_fee()`/`fee()` consistency. Because `data` is untrusted/caller-supplied bytes to a public constructor and the miscalculation always occurs, likelihood of the miscalculation itself is certain; likelihood of a stuck transaction is moderate.

### Recommendation
Include the OP_RETURN output in weight/vbyte estimation. Either pass the actual `tx_outs` (or at minimum `payments` plus a synthetic `TxOut` for the OP_RETURN script) into `calculate_weight_vbytes`, or compute the weight directly from the fully-constructed `tx_outs`/`tx_ins` instead of a parallel template. Also recompute the minimum-fee check against the vbytes of the transaction that will actually be signed.

### Proof of Concept
Construction-level PoC (no node required):

```rust
// networks/bitcoin context
let data = vec![0xAA; 80]; // max allowed, passes the <= 80 check at send.rs:171
let st = SignableTransaction::new(
    vec![received_output],           // any valid ReceivedOutput
    &[(payment_script, 10_000)],
    Some(change_script),
    Some(data),
    1,                               // fee_per_vbyte = 1 sat/vB (near min relay)
).unwrap();

// needed_fee was computed WITHOUT the OP_RETURN output
let estimated = st.needed_fee();

// The real tx is larger by the serialized OP_RETURN output size,
// so the *realized* fee rate is fee / actual_vbytes < 1 sat/vB,
// while the TooLowFee check at send.rs:211 passed using the smaller vbytes.
```

Direct code trace: `data` is appended to `tx_outs` at send.rs:194-202; `calculate_weight_vbytes` at send.rs:204 is passed only `tx_ins.len()`, `payments`, `None` — it never sees `tx_outs` — and its internal template transaction (send.rs:68-99) contains only payments + optional change. The signed transaction serialized/relayed contains the extra OP_RETURN output, so `weight`/`vbytes`/`needed_fee`/`fee_with_change` are all understated, exactly as `startingGas` was overstated in the GMX original.
