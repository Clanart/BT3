### Title
Consensus batch reward misattribution — all `StateMachineUpdated` rewards in a `handle_messages` batch are paid to the signer of `messages[0]` instead of the relayer who actually delivered each proof - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`Pallet::on_executed`, the `FeeHandler` hook invoked by `pallet-ismp` after processing a batch of ISMP messages, derives a single `relayer_account` from the *first* message in the batch (`messages.get(0)`) and then pays **every** `StateMachineUpdated` reward found anywhere in the batch's `events` to that one account, regardless of which consensus message actually produced each event.

### Finding Description
`on_executed` receives `Vec<MessageWithWeight>` and `Vec<IsmpEvent>` for an entire submitted batch (a single `handle_messages` extrinsic can carry multiple independent `Message::Consensus` entries targeting unrelated state machines, interleaved with request/response/timeout messages): [1](#0-0) 

The relayer identity is extracted **only** from `messages[0]`:
```rust
let maybe_relayer_account = messages.get(0).and_then(|first_message| {
    if let Message::Consensus(consensus_msg) = &first_message.message {
        ...verify signature, recover pubkey...
    } else { None }
});
```

If that succeeds, the code then collapses **all** `StateMachineUpdated` events in the batch (which may originate from several distinct `Message::Consensus` entries, each carrying its own independently-verified `signer` field) into a per-state-machine highest-height map, and pays every one of those rewards to the single `relayer_account` derived from `messages[0]`: [2](#0-1) 

The comment at lines 125-132 documents that the *intra-state-machine* double-count for a single relayer's own repeated updates was fixed, but it does not address the *cross-message* attribution problem: nothing ties a given `state_machine_id`'s reward back to the specific `Message::Consensus` (and therefore the specific verified signer) that produced its `StateMachineUpdated` event.

Consensus proofs and their embedded `signer` attestation (`Signature` over `keccak256(consensus_proof)`) are public data once produced — they are not secrets and can be relayed by anyone (`handleConsensus`/`handle_messages` is explicitly a permissionless relayer function). An unprivileged party can therefore assemble a `handle_messages` batch where:
- `messages[0]` is their own genuine, self-signed consensus update for state machine A (so `maybe_relayer_account` resolves to the attacker), and
- subsequent messages are additional, otherwise-valid consensus proofs for unrelated state machines B, C, … (data that is publicly obtainable/relayable, not requiring any secret belonging to another relayer).

Both proofs verify successfully and each produces its own `StateMachineUpdated` event, but because reward attribution keys off `messages[0]`'s signer alone, the pallet credits the attacker with the treasury payout and `ReputationAsset` mint for state machines B and C as well as A — funds and reputation that the protocol intends to go to the relayer who actually produced/holds the incentive for each corresponding update.

Existing guards do not stop this: the signature check in `on_executed` only validates that `messages[0]`'s `signer` is a genuine sr25519 signature over that message's own proof hash — it never re-derives or checks a signer per state machine, and `calculate_reward`/`process_message` operate purely on `(state_machine_id, block_cost, LastRewardedHeight)` with no relayer-identity binding beyond the single account passed in.

### Impact Explanation
This directly breaks the "relayer rewards ... must move exactly once and only to the rightful beneficiary and amount" invariant. An unprivileged actor who is capable of submitting a `handle_messages` batch (which is by design permissionless) can redirect treasury-funded consensus-delivery rewards and reputation-asset mints for state machines they did not deliver the "real" incentivized update for, simply by bundling additional legitimate consensus proofs behind their own in a single extrinsic. This is a loss/misdirection of protocol treasury funds to an incorrect beneficiary — not a generic gas DoS, not dependent on a malicious relayer/prover assumption being broken, and not front-run-only (the attacker constructs and submits their own single transaction; they do not need to race anyone else's pending transaction).

### Likelihood Explanation
Likelihood is moderate-to-high: `handle_messages` (or equivalent batched submission) is a normal, permissionless relayer operation, and Hyperbridge's own relayer tooling already batches multiple message kinds together (see `tesseract/messaging/evm/src/tx.rs` `submit_batch_messages`/`batchCall` patterns, showing batching multiple messages in one transaction is an expected, supported workflow). Any relayer running standard tooling — or a party who simply observes publicly broadcast/relayable consensus proofs for other state machines — can construct a batch that exploits this attribution flaw without needing privileged access, a compromised key, or front-running another party's transaction.

### Recommendation
Attribute each `StateMachineUpdated` reward to the signer of the specific `Message::Consensus` entry that produced it, not to `messages[0]`. Concretely: iterate `messages`, and for each `Message::Consensus`, verify its own signer and record `(state_machine_id → relayer_account)` pairs from the intermediate states/heights it actually reports, then apply `highest_per_state_machine` collapsing per `(state_machine_id, relayer_account)` rather than globally per batch. Reject or ignore `StateMachineUpdated` events that cannot be matched to a verified consensus message signer within the same batch.

### Proof of Concept
1. Attacker (A) holds a valid, freshly-produced consensus proof for state machine `SM_A` and self-signs it (`signer_A`), producing `Message::Consensus(msg_A)`.
2. Attacker independently obtains a second valid, not-yet-submitted consensus proof for an unrelated state machine `SM_B`, already signed by relayer B (`signer_B`) — this data is public (e.g., picked up from a shared relay/mempool source, not a secret).
3. Attacker submits a single `handle_messages(vec![msg_A, msg_B])` extrinsic (or the batched EVM equivalent), with `msg_A` placed at index 0.
4. `pallet-ismp` processes both messages, verifying each proof independently and emitting two `StateMachineUpdated` events — one for `SM_A`, one for `SM_B`.
5. `on_executed` is invoked with `messages = [msg_A, msg_B]` and both events. `messages.get(0)` resolves to `msg_A`, and `relayer_account` becomes A's account.
6. The loop over `highest_per_state_machine` pays **both** the `SM_A` and `SM_B` rewards (treasury transfer + `ReputationAsset::mint_into`) to A's account, even though B produced/holds the legitimate claim to the `SM_B` proof and its associated incentive.
7. Result: attacker A receives reward funds and reputation for a state machine update they did not originate, at the expense of the rightful relayer.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});
