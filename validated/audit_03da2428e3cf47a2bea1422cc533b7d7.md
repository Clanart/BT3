## Verdict: Valid vulnerability confirmed

The reported issue is real. `withTrampolineEnv` unconditionally injects `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` into the environment of every Git process it spawns (including `git revert`), and the code comment explicitly documents that this is done via environment variables (rather than `-c` args) *specifically so that filter processes such as Git LFS clean/smudge can pick them up* [1](#0-0) . That means any `clean`/`smudge`/`filter.lfs.process` command declared in the attacker-controlled repository's `.gitattributes`/`.git/config` inherits these two secrets.

The trampoline server only validates that the token is *currently active* — it does not verify that the request originates from the legitimate `desktop-trampoline` credential-helper binary, nor that the requested host matches the host of the actual git operation in progress: [2](#0-1) 

Once connected with a valid token and `DESKTOP_TRAMPOLINE_IDENTIFIER=CREDENTIALHELPER`, the handler's `get` path calls `getGitHubCredential` *unconditionally, before any other endpoint checks*, resolving whatever `protocol`/`host` the attacker supplied in the crafted stdin payload to a signed-in account and returning its real login/token: [3](#0-2) [4](#0-3) 

`getCredentialUrl`/`findGitHubTrampolineAccount` match purely on URL origin against the user's stored accounts, with no binding to the remote of the repository/operation that actually spawned the filter: [5](#0-4) [6](#0-5) 

The trampoline server listens on `127.0.0.1` on an ephemeral port obtainable only via `DESKTOP_PORT`, so it's local-only, but any process with that port+token (i.e., the malicious filter) can reach it: [7](#0-6) 

This is reachable from `git revert` because `revertCommit` calls `git(...)`, which internally uses `withTrampolineEnv` (via `spawnGit`) for every invocation, regardless of whether the revert actually needs network/credential access: [8](#0-7) [9](#0-8) 

### Title
Repository-defined Git filter processes can hijack the local trampoline credential-helper channel to exfiltrate stored GitHub credentials - (File: `app/src/lib/trampoline/trampoline-environment.ts`)

### Summary
`withTrampolineEnv` places `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` into the environment of every Git operation, intentionally so that filter/LFS subprocesses can use the `credential.helper=desktop` config. However, nothing prevents a malicious `clean`/`smudge`/`filter.<name>.process` command declared inside the cloned repository from reading these two values directly and speaking the trampoline wire protocol itself (bypassing the actual `desktop-trampoline` binary and Git's real credential-helper invocation semantics), requesting credentials for an arbitrary host of the attacker's choosing (e.g. `github.com`) instead of the host Git is actually authenticating against.

### Finding Description
The trampoline token check in `TrampolineServer.processCommand` (`app/src/lib/trampoline/trampoline-server.ts`) only validates that the token is currently outstanding (`isValidTrampolineToken`), not that the caller is the legitimate credential-helper binary or that the requested `protocol`/`host` corresponds to the actual remote of the operation that created the token. The credential-helper `get` handler (`app/src/lib/trampoline/trampoline-credential-helper.ts`) resolves credentials purely from the attacker-supplied `host`/`protocol` fields in the request body, first attempting `getGitHubCredential`, which matches any signed-in GitHub/GHE account by URL origin with no further gating.

### Impact Explanation
A filter process defined entirely within the untrusted repository (no network operation, remote-URL relevance, or user authentication prompt required) can silently obtain the user's real GitHub/GHE session credential (PAT/OAuth token) for any account signed into GitHub Desktop, by directly connecting to `127.0.0.1:$DESKTOP_PORT` and issuing a forged credential-helper `get` request with a host of its choosing. This is a credential-exfiltration primitive triggered purely by cloning/checking out attacker content — it satisfies the program's "credential/token exfiltration" impact criterion.

### Likelihood Explanation
Any local git operation that goes through `git()`/`withTrampolineEnv` — `revert`, `checkout`, `merge`, `pull`, etc. — sets up this environment, so a repository merely needs to declare a `clean`/`smudge` filter (or `filter.lfs.process`) in its tracked `.gitattributes`/`.git/config` and have the user perform a normal repository action (open/checkout/revert/pull) that triggers the filter on any file. No special user interaction beyond routine repository use is required, making this readily reachable for anyone who can get a victim to clone and interact with a crafted repository.

### Recommendation
Bind trampoline credential-helper requests to the specific operation/remote context they were issued for (e.g., validate the requested host against the remote URL(s) associated with the token's git operation), and/or restrict which command identifiers a token may be used for based on how it was minted, rather than allowing any process holding a valid token to freely issue arbitrary `CREDENTIALHELPER` `get` requests for any host.

### Proof of Concept
1. Create a repository containing a `.gitattributes` entry such as `* filter=exfil` and a corresponding `filter.exfil.clean` command in `.git/config` (or an equivalent LFS `filter.lfs.process` hook) pointing to an attacker script.
2. The script reads `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` from its environment.
3. It opens a raw TCP socket to `127.0.0.1:$DESKTOP_PORT` and manually writes the trampoline wire protocol: parameter count `1`, parameter `get`, environment-variable count `2`, `DESKTOP_TRAMPOLINE_IDENTIFIER=CREDENTIALHELPER`, `DESKTOP_TRAMPOLINE_TOKEN=<leaked token>`, and stdin body `protocol=https\nhost=github.com\n\n`.
4. Have the victim run `git revert <commit>` (or any operation that triggers the filter) in GitHub Desktop while signed into a GitHub account.
5. Observe the socket response contains `username=<login>` and `password=<real token>` for the victim's GitHub account.

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}
