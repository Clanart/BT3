### Title
Vetoing the latest state commitment resets the height tracker to a fixed sentinel, breaking monotonicity and letting stale state commitments be re-accepted - ([File: evm/src/core/EvmHost.sol])

### Summary
This is a local analog of the `AssetProxyOwner` bug class: an incidental state-mutating event (there: changing confirmation count; here: a fisherman veto of the current tip) resets a value that downstream logic treats as monotonic/authoritative, breaking the invariant that gated correctness. In `EvmHost.sol`, deleting the currently-latest state machine commitment resets `_latestStateMachineHeight` to the fixed value `1` instead of the true previous-highest verified height, which lets subsequently-submitted consensus proofs re-store *any* height greater than `1` as the new "latest" — including stale, already-superseded heights.

### Finding Description
`deleteStateMachineCommitmentInternal` is called (handler-restricted) whenever a fisherman successfully vetoes a state commitment: [1](#0-0) 

When the vetoed height happens to be the current tip, the code does not recompute the true previous-highest verified height; it simply sets `_latestStateMachineHeight[height.stateMachineId] = 1` — an artificial sentinel, not a re-derived monotonic value.

Meanwhile, `storeStateMachineCommitment` blindly overwrites the tracked tip whenever it is invoked, with an explicit comment that it "Assumes the state commitment is of the latest height": [2](#0-1) 

The only gate protecting that assumption lives in the caller, `HandlerV2.handleConsensus`: [3](#0-2) 

```
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    ... host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
```

This is an exact structural match to the original bug's `isConfirmed()` / time-lock reset: a single event (veto of the tip) resets a tracked counter to a value lower than reality, and every subsequent state-mutating action re-evaluates against the *reset* value instead of the true prior state, exactly like reconfirmation resetting the multisig's time lock. Once `_latestStateMachineHeight` is `1`, any intermediate height `> 1` — even one that is *lower* than other already-stored, still-canonical commitments left untouched by the veto — passes the `intermediate.height > latestHeight` check and is written as the new "latest," silently regressing the tracked tip and re-arming `_stateCommitmentsUpdateTime` (the challenge-period clock) for that lower height.

### Impact Explanation
`_latestStateMachineHeight` and `_stateCommitmentsUpdateTime` are the two values every downstream ISMP handler trusts for challenge-period gating and "is this the current canonical state" checks (`handlePostRequests`, `handleGetResponses`, timeout handling, `stateMachineCommitmentUpdateTime`). Breaking the monotonic invariant means:
- A previously superseded/older intermediate state (already available and possibly already used to satisfy or fail proofs) can be re-stored as "latest," re-arming its challenge-period timer and changing which state root proofs are verified against.
- The protocol's implicit assumption "the state machine can only advance forward" is violated by a single veto of the tip, undermining the security model that request/response/timeout processing relies on for false-state-acceptance protection.

This does not require a malicious peer, prover, or admin key — a fisherman successfully vetoing the *current tip* (a legitimate, permissionless, proof-gated protocol role) is enough to trigger the reset; from there, any relayer submitting an otherwise-valid consensus proof for an old height can exploit the broken monotonicity check.

### Likelihood Explanation
Requires two ordinary, unprivileged sequential events already supported by the protocol: (1) a fisherman vetoes the current tip via a valid fraud/veto proof (an intended, permissionless mechanism, not an admin or malicious-peer assumption), and (2) any relayer subsequently submits a consensus proof carrying an intermediate state at a height greater than `1`. Neither step needs a compromised key, governance action, or malicious peer — only normal use of the existing veto and consensus-update entrypoints — making this readily reachable in practice whenever a tip veto occurs.

### Recommendation
On veto of the current tip, recompute `_latestStateMachineHeight` from the actual highest remaining stored/verified commitment (or track a proper ordered set of heights) instead of hardcoding the sentinel `1`. Additionally, `storeStateMachineCommitment` should not unconditionally trust the caller's "greater than latest" check computed against a possibly-corrupted value; it should independently enforce (or the host should expose) a monotonic invariant that can't be rolled back to an artificial floor.

### Proof of Concept
1. Consensus proofs advance state machine `A` to height `100`; `_latestStateMachineHeight[A] = 100`, commitment `C100` stored (`storeStateMachineCommitment`, `EvmHost.sol:687-699`).
2. A fisherman submits a valid veto/fraud proof against height `100` through the handler, invoking `deleteStateMachineCommitment(height=100, fisherman)` → `deleteStateMachineCommitmentInternal` deletes `C100` and executes `_latestStateMachineHeight[A] = 1` (`EvmHost.sol:714-732`), because `100 == _latestStateMachineHeight[A]`.
3. Earlier commitments (e.g., height `50`, still stored/canonical and possibly already relied upon by delivered requests) are untouched by the veto.
4. Any relayer submits a new (otherwise legitimate) consensus proof to `handleConsensus` carrying an intermediate state at height `60` for state machine `A`.
5. `HandlerV2.handleConsensus`'s guard `latestHeight != 0 && intermediate.height > latestHeight` now evaluates `1 != 0 && 60 > 1` → true, so `host.storeStateMachineCommitment({A, 60}, commitment)` is called, silently regressing `_latestStateMachineHeight[A]` from its true prior value down to `60` and resetting `_stateCommitmentsUpdateTime[A][60]` to `block.timestamp`, restarting that height's challenge-period clock and corrupting the monotonic-height invariant every downstream ISMP handler depends on.

    /**
     * @dev Store the state commitment at given state height alongside relevant metadata.
     * Assumes the state commitment is of the latest height.
     */
    function storeStateMachineCommitment(StateMachineHeight memory height, StateCommitment memory commitment)
        external
        restrict(_hostParams.handler)
    {
        _stateCommitments[height.stateMachineId][height.height] = commitment;
        _stateCommitmentsUpdateTime[height.stateMachineId][height.height] = block.timestamp;
        _latestStateMachineHeight[height.stateMachineId] = height.height;

        emit StateMachineUpdated({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId), 
            height: height.height
        });
    }

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
