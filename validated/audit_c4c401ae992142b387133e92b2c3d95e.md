### Title
Unbounded participant count in `ThresholdKeys::read` enables CPU/memory exhaustion via attacker-controlled `t`/`n` with quadratic Lagrange interpolation - (File: crypto/dkg/src/lib.rs)

### Summary
The GraphQL report's core bug class — attacker-controlled repetition factors (aliases, duplicate fields, fragment depth) that amplify a small request into disproportionate server work — has a direct analog in `ThresholdKeys::read`. Both `t` and `n` are deserialized as raw `u16`s with no early cap, then used to drive a `Vec::with_capacity(n)` allocation, `n` point decodings, and `ThresholdKeys::new`, which computes the group key by summing `t` Lagrange interpolation factors — each factor itself an O(t) field-multiplication loop — for a total of O(t²) field operations plus O(n) point decompressions, all before any semantic validation rejects the input. A few bytes from an unprivileged party can therefore force billions of field operations and ~4 MiB of allocation/decompression work per call.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` as u16s, then immediately trusts `n` for allocation and parsing:

```rust
// crypto/dkg/src/lib.rs
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
...
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
``` [1](#0-0) 

It then calls `ThresholdKeys::new`, which validates `verification_shares.len() == n` but performs the expensive work unconditionally: for each of the `t` participants `1..=t`, it calls `interpolation_factor`, whose `Interpolation::Constant` arm is a single indexing op but whose `Interpolation::Lagrange` arm iterates the entire `included` list (length `t`) doing two field multiplications per element, plus an inversion:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [2](#0-1) [3](#0-2) 

With `t = n = 65535` (all valid u16 inputs that pass `ThresholdParams::new`'s only checks — nonzero and `t <= n`), a single `ThresholdKeys::read` on Lagrange-interpolated bytes performs ~4.3 billion field multiplications for the group key alone, on top of 65535 `read_G` point decompressions and a 65535-entry `HashMap`. Notably, the expensive group-key computation runs regardless of whether the caller ever uses the key, and it happens after deserialization succeeds — the only gate is `ThresholdParams::new`, which accepts any `t <= n <= 65535`. This mirrors the report's "field duplication" pattern exactly: an unbounded repetition count embedded in untrusted input multiplies the verifier's work quadratically/cubically with no complexity limit.

This is reachable wherever untrusted bytes are passed to `ThresholdKeys::read` (explicitly in scope per the reachable-API rules), e.g., key material or key-set data supplied by an external party.

### Impact Explanation
Availability impact only — the analog holds as a DoS vector, consistent with the source report. A ~2 MiB input (`65535` compressed points plus scalars and a constant-coefficient vector, or less if the reader is fed a truncated stream that still passes the `with_capacity` allocation) forces the deserializer into ~4×10⁹ scalar multiplications plus 65k point decompressions and a 65k-entry map construction. Repeated submissions of such payloads exhaust CPU on the parsing/validation path. No key material, signature forgery, or funds are at stake; impact is bounded to resource exhaustion, matching the report's DoS-only framing.

### Likelihood Explanation
Exploitation requires a path where an unprivileged party's bytes reach `ThresholdKeys::read` — e.g., loading key material received or reconstructed from external input. Where that path exists (the rules treat `ThresholdKeys::read` as reachable), the attack needs no privileges, no valid key, and no cooperation: any byte string declaring `t = n = 65535` triggers the work before `ThresholdKeys::new`'s share-count check can reject it, since the interpolation and group-key summation in `ThresholdKeys::new` execute unconditionally once `n` points parse. The `Vec::with_capacity(n)`/`HashMap` reservations also occur before a single byte of payload is validated, so even a short input claiming a large `n` forces allocation.

### Recommendation
Apply the report's own remediation pattern — bound the repetition factor before allocating or iterating:

- Reject `n` above a protocol-meaningful maximum (the codebase elsewhere uses `MAX_KEY_SHARES_PER_SET`, e.g., in `coordinator/src/tributary/transaction.rs`) at the top of `ThresholdKeys::read`, before `Vec::with_capacity(n)` and before the `1..=n` `read_G` loop.
- Similarly cap `t` before `ThresholdKeys::new` computes `group_key`, or make `ThresholdKeys::new`/`view` enforce a documented maximum so the O(t²) Lagrange work cannot be triggered by untrusted parameters.
- Avoid `Vec::with_capacity(n)`/`HashMap` preallocation sized by untrusted input; grow incrementally or size the capacity after a sanity check.

### Proof of Concept
Serialize a `ThresholdKeys` byte stream for any in-scope `Ciphersuite` with: `id_len`/ID valid, `t = 0xFFFF`, `n = 0xFFFF`, `i = 1`, interpolation byte `1` (Lagrange), followed by a valid `secret_share` scalar and 65535 valid point encodings (e.g., the generator repeated). Feed it to `ThresholdKeys::<C>::read`. Deserialization succeeds and `ThresholdKeys::new` then evaluates `interpolation_factor` for each of 65535 participants, each iterating 65535 terms — ~4×10⁹ field multiplications — before returning. The truncated variant (valid header claiming `n = 0xFFFF` with no body) still forces `Vec::with_capacity(65535)` and fails only after allocation.
