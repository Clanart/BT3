## Analysis

The Ammplify bug's core invariant is: **credit/accounting for an amount is computed from a pre-callback value, then an untrusted external call runs, and the amount actually moved is never reconciled against what was accounted for.** The strongest local analog is not in the current (already-hardened) `evm/src/apps/IntentGatewayV2.sol`, but in the parallel Tron deployment of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, whose `placeOrder` predispatch-escrow flow diverges from the fixed EVM version in exactly the way that reintroduces the broken invariant.

### Title
Escrow credited from pre-dispatch declared amount instead of actual dispatcher-delivered balance in `placeOrder` predispatch flow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, when an order carries `predispatch` calldata, the escrow ledger `_orders[commitment][token]` is credited with the user-declared `reducedInputs[i].amount` immediately after the attacker-controlled `predispatch.call` executes, based only on the dispatcher's balance check (`balance < requiredAmount` revert), rather than on the tokens actually swept back into the gateway. The final settlement transfer (`ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`) happens afterward and its result is never measured or reconciled against the escrow amount already recorded.

### Finding Description
`placeOrder` in the Tron contract computes the order `commitment` and the escrow amounts from `reducedInputs`/`order.inputs[i].amount` — values fixed before any token movement through the dispatcher occurs: [1](#0-0) 

It then transfers the predispatch assets to the shared `CallDispatcher` and executes fully attacker-supplied calldata (`order.predispatch.call`): [2](#0-1) 

Immediately after that untrusted callback returns, the code re-reads the dispatcher's balance, only asserts `balance >= requiredAmount`, computes `dust = balance - requiredAmount`, and then **credits escrow using the static `reducedInputs[i].amount`, not `balance` and not any post-sweep delta**: [3](#0-2) 

The actual transfer of tokens from the dispatcher back to the gateway is deferred to a second, separate `ICallDispatcher(dispatcher).dispatch(...)` call that runs after escrow has already been credited, and its outcome is never checked against a `balanceOf(address(this))` before/after delta: [4](#0-3) 

Compare this to the hardened EVM mainnet contract, which snapshots `balancesBefore[i]` for the *gateway itself*, executes the sweep, and only then computes `received = balanceOf(address(this)) - balancesBefore[i]`, using that measured value — not the pre-declared amount — for both dust accounting and escrow crediting: [5](#0-4) 

The Tron version's checks are all performed against the *dispatcher's* balance, which is exactly the state an attacker's `predispatch.call` (executed by the dispatcher, in the dispatcher's own context, per `CallDispatcher.dispatch`) can freely manipulate — moving tokens in and out of the dispatcher, front-loading it with exactly `requiredAmount` while diverting genuine surplus elsewhere, or leaving it short in ways the second dispatch call (itself another opaque external call with an unchecked outcome) never gets validated against. `_orders[commitment][token]` — the value redeemed by solvers on fill (`_withdraw` in `IntentsBase.sol`) — is thus set from a value that was never verified to correspond to tokens the gateway actually now holds: [6](#0-5) 

This is the same broken invariant as the Ammplify H-2 report: state that gates fund custody (there, Uniswap liquidity minted; here, escrowed input amount) is derived from a value computed *before* an untrusted external call, while the call itself is trusted to deliver a matching amount, with no reconciling balance check after the fact.

### Impact Explanation
If exploitable, an attacker placing an order with malicious `predispatch.call` and a manipulated dispatcher interaction could get `_orders[commitment][token]` credited for more than what the gateway actually received (or, depending on `CallDispatcher.dispatch`'s all-or-nothing revert semantics, could at minimum decouple recorded escrow from real custody). Any downstream solver fill or refund path (`_withdraw`) pays out of `_orders[...]`, which is Taker/solver-facing collateral — a mismatch here causes the gateway to pay out tokens it does not actually hold, draining balances belonging to other orders/users, matching the "stealing or loss of funds" and "false state acceptance" impact classes.

### Likelihood Explanation
The predispatch code path is reachable by any unprivileged user calling `placeOrder` with `predispatch.call` populated — no relayer, prover, or admin involvement is required, and the `CallDispatcher` is explicitly designed to execute arbitrary user-supplied calldata (`ICallDispatcher.dispatch`) as a "swap-then-escrow" primitive. The divergence from the corrected EVM mainnet implementation (which the `IntrinsicIntentsReentrancyTest.sol` suite shows was already hardened for a related reentrancy class) strongly suggests the Tron contract is a stale/unpatched fork that did not receive the same balance-delta fix.

### Recommendation
Mirror the EVM mainnet fix in `evm/src/apps/IntentGatewayV2.sol`: measure the gateway's own `balanceOf`/native balance immediately before and after the final sweep `dispatch` call, and credit `_orders[commitment][token]` (and compute `commitment`/protocol fees) strictly from that measured delta — never from the pre-dispatch declared `order.inputs[i].amount`. Ensure the same fix is applied consistently across all deployed variants of `IntentGatewayV2` (EVM mainnet, Tron, and any other chain-specific forks).

### Proof of Concept
1. Attacker calls `placeOrder` with `order.predispatch.assets` = 100 TOKEN and `order.predispatch.call` containing calldata that, when executed by the `CallDispatcher`, moves TOKEN out of the dispatcher to an attacker-controlled address and back in a way that leaves the dispatcher's `balanceOf` reading exactly `requiredAmount` at the check point (satisfying `balance < requiredAmount` revert guard) while actually holding less real value than expected, or arranges timing so the second sweep `dispatch` under-delivers to the gateway.
2. The check at [7](#0-6)  passes on the manipulated dispatcher balance.
3. `_orders[commitment][token] += reducedInputs[i].amount` credits the full declared amount regardless of what is later actually swept to the gateway.
4. A solver later fills the order and `_withdraw` releases `_orders[commitment][token]` from the shared escrow pool, potentially exceeding the gateway's real balance for that token and consuming funds escrowed for other orders.

Note: I was not able to execute this against a live fork to conclusively prove the dispatcher-balance manipulation step (exact feasibility depends on `CallDispatcher`'s all-or-nothing call semantics and what predispatch calls are permitted); the structural flaw — crediting escrow from a pre-callback declared amount instead of a post-callback measured delta — is directly confirmed by the code and is the same class of accounting bug as the Ammplify report.
