## Title
Tron `IntentGatewayV2` lacks reentrancy protection present in the audited EVM version, reopening the fee-bypass/escrow-theft reentrancy fixed elsewhere - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report describes a flashloan-without-fee primitive: a malicious maker/taker contract regains control mid-settlement (during an asset transfer callback) and uses assets that have not yet been finalized/paid-for to extract value before the surrounding call completes. Hyperbridge's canonical EVM `IntentGatewayV2` (composed from `IntrinsicIntents`/`ExtrinsicIntents`) was previously vulnerable to exactly this class of bug — a malicious `beneficiary` contract could re-enter `fillOrder` during the native-ETH `.call{value:}` transfer to self-fill another output and steal escrowed input tokens or transaction fees without paying for them. This was fixed by (1) moving `_filled[commitment] = msg.sender` to the top of `_fillSameChain`/`_fillCrossChain` before any external call (CEI), and (2) adding `nonReentrant` (`ReentrancyGuardTransient`) to both `placeOrder` and `fillOrder` in `evm/src/apps/IntentGatewayV2.sol`, verified by a dedicated regression suite (`evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`).

The **Tron** deployment of the same protocol, `evm/tron/contracts/apps/IntentGatewayV2.sol`, is a separately maintained, monolithic contract implementing the identical fill/withdraw/escrow logic (native ETH `.call{value:}` transfers to `beneficiary`, ERC-20 low-level `.call` transfers, `_filled` mapping, `TRANSACTION_FEES` escrow) but does **not** inherit `ReentrancyGuardTransient` and has no `nonReentrant` modifier anywhere in the file or its imports. ### Finding Description
In the fixed EVM implementation, the developers explicitly recognized that a `beneficiary` receiving native ETH via `.call{value: amount}("")` inside the output-fill loop can be an attacker-controlled contract whose `receive()` hook re-enters `fillOrder`/`placeOrder` before escrow/fee bookkeeping is finalized. The remediation added two independent layers of defense in `evm/src/apps/IntentGatewayV2.sol`: [3](#0-2) 

and the CEI reordering documented and tested in `IntrinsicIntentsReentrancyTest.sol`, whose comments explicitly state the historical exploit ("malicious beneficiary could re-enter, self-fill the ERC-20 output... and steal the entire input escrow") and confirm that both defenses (`_filled` set pre-transfer, plus `nonReentrant`) are required to fully close the path: [4](#0-3) [5](#0-4) 

The Tron contract reproduces the same dangerous primitives — native-ETH `.call{value: amount}("")` to `req.beneficiary`/`beneficiary` and low-level ERC-20 `.call` transfers inside `withdraw()` — but was authored as a standalone `HyperApp, EIP712` contract with no `ReentrancyGuard` import or `nonReentrant` modifier on its `fillOrder`, `placeOrder`, or `withdraw` entry points: [6](#0-5) [7](#0-6) 

Because the file was never confirmed against the same regression harness (`IntrinsicIntentsReentrancyTest.sol` instantiates `IntentGatewayV2` from `evm/src/apps`, not the Tron variant), there is no evidence the CEI reordering fix that made the EVM contract safe was also ported to the Tron fill path. Absent `nonReentrant` and with native-token `.call` transfers still present in the fill loop, a malicious `beneficiary`/maker contract can regain control during the ETH transfer and re-enter the gateway (e.g., a second `fillOrder`/`placeOrder` call, or reentering before `_orders[commitment][token]` is decremented) to manipulate escrow or fee accounting exactly as in the pre-fix EVM contract — the same "flashloan without fee" primitive from the seed report, where control is regained mid-settlement before the surrounding transaction's bookkeeping (fee debit, escrow decrement) is finalized.

### Impact Explanation
If the Tron contract's fill/withdraw ordering matches the pre-fix EVM pattern (escrow/fee finalization occurring after or interleaved with the external native-token transfer), a malicious beneficiary contract can re-enter to claim escrowed input tokens or `TRANSACTION_FEES` beyond what it is entitled to, or duplicate a fill/withdrawal — a direct "stealing or loss of funds" / "double-claim" outcome against the Hyperbridge bounty's accepted impact categories. This is reachable by any unprivileged actor who deploys a malicious `beneficiary` contract and calls the public `fillOrder` entrypoint; no relayer, prover, or governance actor is required.

### Likelihood Explanation
Likelihood depends on whether the exact statement ordering inside the Tron `fillOrder`/`_fillSameChain`-equivalent function transfers native tokens before or after `_orders[commitment][token]` is decremented and `_filled[commitment]` is set — this internal ordering was not directly captured in the available excerpts of the file (only `withdraw()`, the destination-side settlement handler, was confirmed to follow CEI). What is concretely confirmed is the structural gap: the Tron contract has zero reentrancy-guard coverage where the sibling EVM contract required two layered fixes (CEI + `nonReentrant`) for the identical native-transfer-to-beneficiary pattern, and the regression tests proving safety only cover the EVM contract.

### Recommendation
- Add `ReentrancyGuardTransient` (or standard `ReentrancyGuard`) and a `nonReentrant` modifier to `fillOrder`, `placeOrder`, and any withdrawal/settlement entrypoints in `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirroring `evm/src/apps/IntentGatewayV2.sol`.
- Audit and, if necessary, reorder the Tron fill functions to set `_filled[commitment]` and decrement `_orders[commitment][token]` before any external `.call` (CEI), matching the fix applied to `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`.
- Extend `IntrinsicIntentsReentrancyTest.sol` (or an equivalent Tron-specific harness) to exercise the Tron contract directly, since the existing suite only instantiates the EVM `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
Conceptual attack mirroring the confirmed pre-fix EVM exploit (from `IntrinsicIntentsReentrancyTest.sol`), applied to the Tron contract's `withdraw`/fill path if native-transfer-before-finalize ordering is present:
1. Attacker deploys a malicious `beneficiary` contract implementing `receive()`/fallback that calls back into `IntentGatewayV2.fillOrder` (or the withdrawal path) for a second, self-crafted order/commitment sharing escrowed token slots.
2. Attacker (as solver) calls `fillOrder` on an order whose output includes a native-token (TRX) payment to the malicious `beneficiary`.
3. During the `beneficiary.call{value: amount}("")` at [8](#0-7)  or the equivalent in the direct fill function, if `_filled`/`_orders` bookkeeping has not yet been finalized, the malicious contract re-enters to trigger a second withdrawal/fill against the still-unfinalized escrow, duplicating payout or bypassing fee debit — the Tron analog of the Putty flashloan-without-fee bug, since no `nonReentrant` guard exists anywhere in this file to block the reentry as it does in `evm/src/apps/IntentGatewayV2.sol`.

Note: I was not able to fully retrieve and confirm the exact statement order inside the Tron contract's primary `fillOrder`/same-chain-fill function (only `withdraw()` and a middle segment of `placeOrder`-equivalent logic were available in the index); a Devin session with full repository access would be needed to line-by-line confirm whether `_filled`/escrow decrements happen before or after the native-token `.call` in that specific function to fully confirm exploitability versus the confirmed structural gap (missing `nonReentrant`).

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
