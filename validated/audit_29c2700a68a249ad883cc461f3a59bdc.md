### Title
SignableTransaction::new accepts duplicated inputs, double-counting `input_sat` and producing an unspendable transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` never checks that the `ReceivedOutput`s passed in `inputs` are distinct. The same outpoint can be supplied multiple times (each copy can even carry a different `offset`/`output` payload via `ReceivedOutput::read`), causing `input_sat` — the sum of claimed input value — to be inflated. The resulting transaction passes the `NotEnoughFunds` check, is signed, yet can never confirm because it spends the same UTXO twice (or spends an outpoint whose real output doesn't match `prevouts`).

### Finding Description
The JUSD bug was an `_addReserve` that (a) used `reservesNum <= maxReservesNum` instead of `<`, permitting `max + 1` entries, and (b) never checked that a reserve was already present, so re-adding it corrupted `reservesNum`. The analog here is the "re-addition corrupts the accounting" half: `inputs` is a `Vec<ReceivedOutput>` consumed verbatim.

In `networks/bitcoin/src/wallet/send.rs`:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
let offsets = inputs.iter().map(|input| input.offset).collect();
let tx_ins = inputs.iter().map(|input| TxIn {
    previous_output: input.outpoint,
    ...
}).collect::<Vec<_>>();
``` [1](#0-0) 

There is no deduplication or uniqueness check on `input.outpoint` anywhere between here and `Ok(SignableTransaction { .. })`. The sufficiency gate is:

```rust
if input_sat < (payment_sat + needed_fee) {
    Err(TransactionError::NotEnoughFunds { ... })?;
}
``` [2](#0-1) 

`input_sat` is the sum over *declared* outputs, so a duplicated (or entirely fabricated, see below) `ReceivedOutput` inflates it arbitrarily.

Two consequences:

1. **Duplicate outpoint.** The same `OutPoint` appearing twice yields two `TxIn`s spending one UTXO. `input_sat` counts the value twice, so the caller can be shown a `SignableTransaction` claiming to fund `payment_sat` that the real inputs cannot cover. The transaction is consensus-invalid; any Bitcoin node rejects it. Funds reported as spendable/received are not spendable.

2. **Forged `ReceivedOutput`.** `ReceivedOutput::read` accepts arbitrary bytes for `offset`, `output` (a full `TxOut`), and `outpoint`, with no check that `offset` actually corresponds to `output.script_pubkey` or that the outpoint exists:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    output = TxOut::consensus_decode(&mut buf_r)...;
    outpoint = OutPoint::consensus_decode(&mut buf_r)...;
    Ok(ReceivedOutput { offset, output, outpoint })
}
``` [3](#0-2) 

The only consistency check happens later in `multisig()`, where `p2tr_script_buf(offset.group_key()) != prevouts[i].script_pubkey` is verified [4](#0-3)  — but that binds `offset` to the *claimed* `TxOut`, not the claimed `TxOut` to the real on-chain output referenced by `outpoint`. A `ReceivedOutput` naming a victim's outpoint with an attacker-chosen `TxOut` passes `SignableTransaction::new`, and the forged `TxOut` is committed into `Prevouts::All` for the sighash [5](#0-4) . The network then produces a valid FROST signature over a transaction whose prevout values don't match reality — again consensus-invalid under `TapSighashType::Default` semantics (BIP-341 commits to the prevout amounts, so the signature itself verifies against the wrong amounts and Bitcoin Core rejects the spend).

### Impact Explanation
- Fee/change math and the `NotEnoughFunds` gate operate on attacker-inflated `input_sat`, so the protocol can sign transactions claiming funds that do not exist or double-counting the same UTXO.
- A signature is produced and broadcast for a transaction that can never confirm, burning the signing session and producing misleading "payment sent" state (`txid()` is computed and returned before any validity reality-check).
- Where a duplicated input's `offset` is real (e.g., two outputs to the same script — `Scanner::scan_transaction` legitimately emits multiple `ReceivedOutput`s sharing one `offset`, and nothing prevents a caller from also duplicating the `outpoint` when constructing inputs manually or via deserialized data), the double-spend is silent at signing time.

This matches the report's "management/accounting risk" — the tracked total (`input_sat`, analogous to `reservesNum`) is corrupted by re-adding an already-present item.

### Likelihood Explanation
Reachability requires untrusted bytes flowing into `SignableTransaction::new`'s `inputs`. `ReceivedOutput::read` is an explicitly in-scope untrusted-bytes sink, so any deployment where inputs are constructed from deserialized/network-provided data (rather than solely from a locally-trusted `Scanner`) is exposed. Even without hostile deserialization, `SignableTransaction::new` is a public API that silently accepts duplicate outpoints, so any caller merging input lists (e.g., combining outputs from multiple scans or sources) can corrupt the accounting without any error being raised. Severity is Medium: no key recovery or forged signature over a *valid* unintended message occurs, but funds/inputs are misreported and an unusable signature is produced, matching the class's "management risk" impact.

### Recommendation
1. In `SignableTransaction::new`, reject duplicate outpoints (e.g., collect `input.outpoint` into a `HashSet` and error on collision), mirroring the fix "check that the reserve was not added before".
2. Document or enforce that `inputs` must originate from `Scanner` results verified against chain state, or have `ReceivedOutput` carry proof the `outpoint`'s actual `TxOut` equals `output` (i.e., verify against `Prevouts`/chain data before summing `input_sat`).

### Proof of Concept
```rust
// Two ReceivedOutputs referencing the same outpoint, both with a
// scanner-derived offset/script the key controls.
let dup = real_received_output.clone();
let inputs = vec![real_received_output, dup];

// input_sat is 2 * value, but only `value` is actually spendable.
// A payment of, e.g., 1.5 * value passes NotEnoughFunds.
let tx = SignableTransaction::new(
    inputs,
    &[(payment_script, payment_value /* > real UTXO value, <= 2x */)],
    None, None, fee_per_vbyte,
).unwrap();

// multisig() succeeds: each input's offset/script check passes
// because both copies carry the same valid offset.
let machine = tx.multisig(&keys).unwrap();
// The signed transaction double-spends the outpoint -> rejected by the network.
```

  pub fn multisig(self, keys: &ThresholdKeys<Secp256k1>) -> Option<TransactionMachine> {
    let mut sigs = vec![];
    for i in 0 .. self.tx.input.len() {
      let offset = keys.clone().offset(self.offsets[i]);
      if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
        None?;
      }

    }
