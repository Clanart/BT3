### Title
Stale trust: removed state machines remain permanently accepted by `handleConsensus` - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParamsInternal` is the single governance-controlled configuration function that replaces `HostParams.stateMachines` (the whitelist of remote chains whose state commitments are trusted). Like the crowdsale's fragmented `setAgent` calls, this function conflates "add" and "replace" semantics: it only ever *adds* new state machine IDs to `_latestStateMachineHeight`, and never deletes IDs that are dropped from the new list. Once a chain has been whitelisted, its trust flag can never be revoked through this configuration path, so `handleConsensus` keeps accepting and storing new state commitments for a chain governance believed it had de-authorized.

### Finding Description
`updateHostParamsInternal` only performs additive initialization for whitelisted chains: [1](#0-0) 

There is no corresponding cleanup step that deletes `_latestStateMachineHeight[id]` for any `id` that was present in the *old* `_hostParams.stateMachines` but is absent from the *new* `params.stateMachines`. The docstring for the getter confirms the semantic contract that a zero value means "unsupported": [2](#0-1) 

`HandlerV2.handleConsensus` (called permissionlessly by any relayer) uses exactly this flag as its sole gate for accepting a new intermediate state commitment for a state machine: [3](#0-2) 

Because `_latestStateMachineHeight[id]` is never reset to `0` when `id` is dropped from `HostParams.stateMachines`, governance's intent to revoke trust in a chain (e.g., because its validator set was compromised, it forked, or its consensus proof became untrustworthy) has no actual effect on the host's willingness to accept new state commitments for that chain. `handleConsensus` will keep accepting `intermediate.height > latestHeight` updates for the "removed" chain, and those state roots then feed directly into `handlePostRequests`/`handleGetResponses`, which trust `host.stateMachineCommitment(...)` without any additional check that the state machine ID is still in the currently configured whitelist: [4](#0-3) 

### Impact Explanation
This breaks the core invariant "state commitments must never let false remote state become trusted." If a chain is removed from `HostParams.stateMachines` specifically because its consensus can no longer be trusted, an attacker (any permissionless relayer) can continue to submit consensus/state proofs for that chain and have them stored and acted upon by `EvmHost`/`HandlerV2`, letting forged or compromised remote state produce dispatched post requests/get responses on the host — i.e., false state acceptance leading to unauthorized execution or fund loss via requests that should no longer be honored.

### Likelihood Explanation
The path requires no malicious admin, relayer collusion, or leaked keys — it only requires that governance legitimately performs its documented job (updating `HostParams.stateMachines` to remove a chain), which is a normal, expected operational action, combined with an ordinary permissionless relayer call to `handleConsensus`/`handlePostRequests`. The bug is a pure logic gap in `updateHostParamsInternal`, always reachable once any chain has ever been de-listed.

### Recommendation
In `updateHostParamsInternal`, diff the old `_hostParams.stateMachines` against the new `params.stateMachines` and explicitly `delete _latestStateMachineHeight[id]` (and any associated state commitments/update-time entries) for every ID that is no longer present, in addition to the current add-only loop.

### Proof of Concept
1. Governance calls `updateHostParams` with `stateMachines = [X]`; `_latestStateMachineHeight[X]` becomes `1`.
2. A relayer submits a consensus proof; `handleConsensus` stores `intermediate.height = 100` for `X` since `latestHeight(1) != 0`.
3. Chain `X`'s validator set is later compromised; governance calls `updateHostParams` again with `stateMachines = [Y]` (X removed) intending to revoke trust in X.
4. `updateHostParamsInternal`'s loop only sets `_latestStateMachineHeight[Y] = 1` if it was `0`; it never touches `_latestStateMachineHeight[X]`, which remains `100`.
5. An attacker (any relayer) submits a new — potentially forged/compromised — consensus proof for `X`. `handleConsensus` still executes `host.storeStateMachineCommitment` because `latestHeight(100) != 0`, and the new state root is then used by `handlePostRequests`/`handleGetResponses` to dispatch requests as if `X` were still a trusted, currently-whitelisted chain.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
