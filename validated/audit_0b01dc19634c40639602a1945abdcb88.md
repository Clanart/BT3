I found a concrete local analog to the Reserve `Distributor.setDistribution` bug: a governance-mutable parameter (`feeToken`) is read at two different points in time for the same escrowed value in `IntentGatewayV2`/`IntentsBase`, with no snapshot binding the escrowed fee to the token it was actually collected in.

### Title
Stale `feeToken()` read at withdrawal pays out order fees in the wrong ERC-20 if the host's fee token is changed between `placeOrder` and settlement - (File: evm/src/apps/IntentGatewayV2.sol, evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder` escrows the user's relayer fee by reading `IDispatcher(hostAddr).feeToken()` at order-creation time and storing the raw amount under the sentinel key `_orders[commitment][TRANSACTION_FEES]` [1](#0-0) . When the order is later settled, `IntentsBase._withdraw` releases that stored amount by calling `IDispatcher(host()).feeToken()` again — a fresh, *current* read, not the value cached at order placement [2](#0-1) . The same pattern exists in the Tron `IntentGatewayV2.withdraw` [3](#0-2) . This mirrors the Reserve `Distributor` bug exactly: a parameter (`feeToken`, analogous to the revenue-distribution split) that governs how an already-escrowed value should be distributed is allowed to change *between* the time value is accrued and the time it is paid out, and the payout path never re-derives or snapshots the value against the parameter that was actually in effect at accrual time.

### Finding Description
- At `placeOrder`, the user's `order.fees` (native or ERC-20) is pulled into escrow denominated in whatever `feeToken()` currently returns, and the raw numeric amount is written to `_orders[commitment][TRANSACTION_FEES]` [1](#0-0) .
- `EvmHost.updateHostParamsInternal` (called via cross-chain `hostManager` governance) permits changing `feeToken` as long as the *current* balance of the old fee token held by the host is zero [4](#0-3) . This guard only protects the Host contract's own balance — it has no visibility into, and does not protect, ERC-20 balances escrowed inside downstream `IApp`s like `IntentGatewayV2`.
- At settlement (`_withdraw` with `finalize == true`), the contract reads the *current* `feeToken()` from the host and transfers `fees` (the amount originally denominated in the *old* fee token) out in whatever token `feeToken()` now points to:
  ```solidity
  uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
  if (fees > 0) {
      delete _orders[body.commitment][TRANSACTION_FEES];
      IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
  }
  ``` [2](#0-1) 
- There is no snapshot of the fee token address in the order or in `_orders` storage — only the numeric `fees` amount is stored under the `TRANSACTION_FEES` sentinel key, keyed purely by `commitment`, with no token dimension [5](#0-4) .
- If governance rotates `feeToken` from token A to token B after orders were placed (funding escrow in token A) but before those orders are filled/refunded, `_withdraw` will attempt `IERC20(tokenB).safeTransfer(beneficiary, fees)`. Two outcomes:
  1. The gateway holds no balance of token B for those fees → the transfer reverts, permanently bricking settlement of that order (the whole `_withdraw` call, which also releases the principal `_orders[commitment][token]` escrow, reverts atomically) — funds lock.
  2. If the gateway happens to hold token B (e.g., from other users' newer orders funded in token B), the transfer succeeds but pays the beneficiary an amount of the *wrong token*, and drains fee-token liquidity that belongs to other orders/users — cross-order fund misappropriation, exactly the "stuck/misdirected revenue" class from the Reserve report.

### Impact Explanation
This is a fund-loss / fund-lock / wrong-beneficiary-amount class bug on a live production path (`fillOrder`/`cancelOrder` → `_withdraw`), reachable by any user who places or fills orders with no privileged actor required to trigger the loss — governance only needs to perform the already-supported, ungated `updateHostParams` fee-token rotation once while intents are in flight. It satisfies the bounty gate: "unauthorized transaction or execution... logic attacks... false proof/state acceptance" is not required here; this is a direct "bridged assets... must move exactly once and only to the rightful beneficiary and amount" violation, since a beneficiary either receives the wrong ERC-20 or nothing at all while the fee remains permanently locked in the gateway contract with no recovery path (the escrow slot is deleted only after a successful transfer; if the transfer reverts, the whole settlement reverts, and the escrow can never be released again since `_filled` would be marked, or the transaction would never complete).

### Likelihood Explanation
The `updateHostParams` fee-token-change path is an already-implemented, intended governance capability (guarded only against the Host's *own* zero balance) [4](#0-3) , and `IntentGatewayV2` orders can remain open for extended periods (`order.deadline` denominated in blocks, potentially days) [6](#0-5) , so the window for a fee-token rotation to land while orders are pending is realistic in any deployment lifecycle (e.g., migrating from one stablecoin to another). No malicious relayer, prover, or leaked key is required — only a normal, sanctioned governance parameter update plus normal user order flow.

### Recommendation
Snapshot the fee token address alongside the fee amount at `placeOrder` time (e.g., store `(feeToken, amount)` instead of a raw `uint256` under `TRANSACTION_FEES`, or key `_orders[commitment][feeTokenAtPlacement]` directly), and use that snapshotted token address — not a live `feeToken()` call — when releasing fees in `_withdraw`. Additionally, `EvmHost.updateHostParamsInternal`'s `CannotChangeFeeToken` guard should be reconsidered/extended, or downstream `IApp`s should be required to drain/migrate their own fee-token-denominated escrow before a fee-token rotation is permitted.

### Proof of Concept
1. Governance sets `feeToken = TokenA` on `EvmHost`.
2. User calls `IntentGatewayV2.placeOrder` with `order.fees = 100`, which pulls `100 TokenA` into the gateway and records `_orders[commitment][TRANSACTION_FEES] = 100` [1](#0-0) .
3. Before the order is filled, `EvmHost` balance of TokenA is zero (nothing else routes TokenA through the host directly), so governance successfully calls `updateHostParams` to set `feeToken = TokenB` — the `CannotChangeFeeToken` check only inspects the Host's own balance, not the gateway's escrow [4](#0-3) .
4. A solver later fills the order; `_withdraw` is invoked with `finalize = true`. It reads `fees = 100` from storage, then calls `IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, 100)`, which now resolves to `TokenB` [2](#0-1) .
5. If the gateway holds no TokenB, this reverts and the entire settlement (including principal release) is blocked, locking the user's escrowed input tokens along with the fee. If the gateway does hold TokenB (from other orders), the solver/beneficiary is paid 100 units of TokenB drawn from other orders' escrow instead of the 100 TokenA that was actually collected for this order — a direct misappropriation of funds belonging to other users.
