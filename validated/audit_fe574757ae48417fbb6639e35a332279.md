### Title
Usage of `.transfer()` in `WSEI.withdraw()` can permanently lock user funds when withdrawing to a contract that needs >2300 gas - (File: contracts/src/WSEI.sol)

### Summary
`WSEI.sol`, the native Wrapped-SEI ERC20 contract shipped with sei-chain (compiled artifacts embedded in `x/evm/artifacts/wsei/artifacts.go` and referenced by `x/evm/client/cli/tx.go`), uses Solidity's `.transfer()` to send native value back to the caller in `withdraw()`. `.transfer()` forwards a hard-coded 2300 gas stipend to the recipient, which will revert if the recipient is a contract with a fallback/receive function that requires more than 2300 gas, has no payable fallback, or is invoked via a proxy/multisig that pushes gas usage above the stipend.

### Finding Description
`withdraw()` deducts the caller's WSEI balance and then unconditionally uses `payable(msg.sender).transfer(wad)`: [1](#0-0) 

Because `.transfer()` hard-limits the gas stipend to 2300 units, any `msg.sender` that is a smart contract (e.g., a DEX router, a multisig wallet, an account-abstraction wallet, or any contract with logic in its `receive`/`fallback` function) will have the withdrawal revert if its fallback function consumes more than 2300 gas, or if it lacks a payable fallback entirely. Because the balance is already decremented before the transfer, on EVM semantics the whole transaction reverts atomically on failure — so no direct fund loss occurs in a single call — but any protocol or user that composes calls into `withdraw()` (e.g., DEX routers or vault contracts that unwrap WSEI as part of a larger transaction) will have their entire composite transaction revert, and worse, if a contract's balance of native SEI is *only* reachable by calling `withdraw()` (i.e., it never implemented a way to receive value except via WSEI unwrap) it can become permanently unable to redeem its WSEI balance for the underlying native asset once deployed, freezing the wrapped funds indefinitely (since the WSEI contract has no fallback `withdraw`-via-call path).

### Impact Explanation
This qualifies as a Medium-severity issue: it can cause a contract's WSEI balance to become permanently unredeemable (frozen funds) if that contract cannot receive value with only 2300 gas and there's no alternative unwrap mechanism, and it silently breaks composability for any router/vault/multisig contract that integrates WSEI (a core wrapped-asset contract deployed as part of sei-chain's EVM tooling) without foreseeing the gas-stipend restriction. This matches the accepted "permanent freezing of funds" impact category, scoped to a public, unprivileged EVM caller (any contract holding WSEI can trigger this by calling `withdraw()`).

### Likelihood Explanation
Likelihood is moderate: this triggers deterministically whenever a smart-contract holder of WSEI (not a plain EOA) calls `withdraw()` and its receive/fallback logic exceeds 2300 gas — a common scenario for contracts that emit events, update storage, or forward calls in their fallback (e.g., proxies, multisigs, ERC-4337 wallets, DeFi vaults). No special privilege or timing is required; it is reachable by any contract user of the wrapped-SEI token.

### Recommendation
Replace `payable(msg.sender).transfer(wad)` in `contracts/src/WSEI.sol` with a low-level `call` and explicit success check, forwarding all available gas, following the standard "checks-effects-interactions" pattern already used (balance is decremented before the external call):
```solidity
(bool success, ) = msg.sender.call{value: wad}("");
require(success, "WSEI: ETH transfer failed");
```

### Proof of Concept
1. Deploy a contract `Recipient` whose `receive()` function performs an SSTORE or emits an event (>2300 gas cost), with no other way to withdraw native SEI.
2. `Recipient` deposits native SEI into `WSEI` via `deposit()`, receiving WSEI balance.
3. `Recipient` calls `WSEI.withdraw(wad)`.
4. The internal `payable(msg.sender).transfer(wad)` call reverts due to insufficient forwarded gas (2300) for `Recipient`'s `receive()` logic, per [2](#0-1) , causing the entire `withdraw()` transaction to revert and leaving `Recipient`'s wrapped balance permanently stuck if no alternate unwrap path exists.
