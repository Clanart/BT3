### Title
Scanner reports immature coinbase outputs as spendable `ReceivedOutput`s, making unspendable funds indistinguishable from spendable ones - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The WithdrawProxy bug allowed redemptions whenever `totalAssets() > 0`, inferring readiness from a balance rather than an explicit "reserve received" gate — so premature redemptions paid out against an incomplete deposit. The same bug class exists in `bitcoin-serai`'s `Scanner`: `scan_block` iterates `block.txdata` including `txdata[0]` (the coinbase transaction) and emits `ReceivedOutput`s for coinbase outputs, even though coinbase outputs are consensus-unspendable for 100 blocks. Worse, `ReceivedOutput` carries no flag or metadata indicating coinbase provenance, so downstream consumers (the multisig scheduler, which builds `Plan`s from `ReceivedOutput`s) cannot distinguish an immature output from a spendable one without re-scanning the block.

### Finding Description
`scan_transaction` matches outputs purely by `script_pubkey` membership in `self.scripts` and wraps each match into a `ReceivedOutput { offset, output, outpoint }` [1](#0-0) . `scan_block` calls it over `&block.txdata`, which includes the coinbase transaction at index 0 [2](#0-1) . The `ReceivedOutput` struct stores only `offset`, `output`, and `outpoint` — no `is_coinbase`/maturity field [3](#0-2) . The doc comment on `scan_block` acknowledges coinbase outputs are "bound by maturity" and suggests a "post-processing pass" or calling `scan_transaction` on `block.txdata[1 ..]` [4](#0-3) , but the API itself neither performs nor enables the check: the coinbase-ness of an output is erased the moment it is wrapped, so a post-processing pass over `Vec<ReceivedOutput>` cannot identify which entries came from the coinbase without re-fetching the block and recomputing txids.

### Impact Explanation
Any unprivileged miner can send a coinbase output paying a scanned multisig script (directly, or via a registered offset). The scanner then reports funds as received that are not spendable for 100 blocks. A scheduler that consumes these `ReceivedOutput`s (the processor's UTXO scheduler builds `Plan`s directly from scanned outputs) will construct a transaction spending an immature coinbase, which is consensus-invalid: the funding transaction can never be included, stalling payments/Burns and misreporting available balance. This matches the accepted impact class "funds reported received that are not spendable." Unlike the WithdrawProxy case where the user could simply wait, here the invalid output poisons the UTXO set until it is manually excluded — and the API provides no field to do so.

### Likelihood Explanation
Reachable by any miner: they control coinbase outputs and can set arbitrary `script_pubkey`s, including the multisig's P2TR script or any registered-offset script. No collusion, threshold compromise, or malicious peer is required — just a Bitcoin transaction (the coinbase) the attacker causes to exist. Likelihood of a miner doing this to a specific script is low (it costs them nothing to try but requires finding the multisig script), and the failure mode is a stall/invalid plan rather than direct theft, so this is Medium rather than High.

### Recommendation
Apply the report's "Option 2" fix: explicitly mark outputs as spendable rather than inferring it from presence. Concretely:
- In `scan_block`, skip `block.txdata[0]` entirely (coinbase can never be immediately spendable), or
- Add a `coinbase: bool`/maturity field to `ReceivedOutput` and set it when scanning `txdata[0]`, so downstream scheduling can filter or defer, and
- Reject/handle coinbase-derived `ReceivedOutput`s in `ReceivedOutput::read` consumers that assume immediate spendability.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
