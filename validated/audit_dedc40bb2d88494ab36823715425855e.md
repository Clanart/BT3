## Title
Trampoline server authenticates commands solely by knowledge of a shared secret, allowing any process that can read a git subprocess's environment (including repository-controlled git hooks) to impersonate the askpass/credential-helper client and exfiltrate stored GitHub credentials - (File: `app/src/lib/trampoline/trampoline-server.ts`)

### Summary
`TrampolineServer.processCommand()` validates a trampoline command purely by checking that `command.trampolineToken` is present in the module-level `trampolineTokens` Set via `isValidTrampolineToken()`. It never verifies which process, socket peer, or binary sent the request. [1](#0-0) [2](#0-1) 

### Finding Description
The token and port are injected as environment variables (`DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`) into the environment of the `git` process spawned by Desktop for the duration of that operation, and revoked only in the `finally` block after the whole git invocation completes: [3](#0-2) [4](#0-3) [5](#0-4) 

Any child process spawned by that `git` invocation — including repository-controlled hooks such as `post-checkout`, `post-merge`, `post-commit`, `pre-push`, or Git LFS filters — inherits the parent process's environment by default, and therefore inherits `DESKTOP_PORT` and the still-valid `DESKTOP_TRAMPOLINE_TOKEN`. The trampoline design intentionally relies on env-var inheritance so that legitimate askpass/credential-helper subprocesses and LFS filters can reach the server (this is explicitly called out as a design goal in the comment about `GIT_CONFIG_PARAMETERS` needing to propagate to filters): [6](#0-5) 

Because `processCommand()` performs no additional binding to the expected client (no per-command nonce tied to a specific spawned child, no PID/parent-PID check, no check that the identifier came from the actual `desktop-askpass-trampoline`/credential-helper binary that Desktop itself launched), any process that can read this inherited environment can open its own TCP connection to `127.0.0.1:<DESKTOP_PORT>` and send a raw `CREDENTIALHELPER` frame with `firstParameter = 'get'` and `url=https://github.com`. The handler resolves this straight to `getCredential()` → `getGitHubCredential()`, which looks up the stored account matching that URL's origin and returns the account's real GitHub username/token via `formatCredential()`: [7](#0-6) [8](#0-7) 

### Impact Explanation
A malicious `post-checkout`/`post-merge` hook shipped in a cloned/fetched repository can, during a legitimate Desktop-initiated git operation, read `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from its own environment and forge a `CREDENTIALHELPER get url=https://github.com` request to the trampoline server, exfiltrating the user's real GitHub OAuth token for `github.com` (or any other configured GitHub/GHE endpoint) rather than credentials scoped to the attacker's own repo/host. This is a token exfiltration vulnerability entirely driven by attacker-controlled repository content (a hook), matching the "credential/token exfiltration" impact category in scope.

### Likelihood Explanation
Whether this is exploitable in practice depends on whether Desktop actually executes untrusted repository-provided hooks during its git operations by default. I was not able to fully confirm within the available context whether Desktop disables hooks (e.g., via `core.hooksPath`, `--no-verify`, or hook-stripping options) for clone/fetch/checkout/merge operations — the `git()`/`withHooksEnv()` wrapper in `app/src/lib/git/core.ts` was only partially inspected before running out of iterations, and I could not verify its full contents or whether it neutralizes hooks. Standard git behavior does execute repository hooks like `post-checkout` and `post-merge` unless explicitly disabled, and nothing in `trampoline-server.ts`, `trampoline-environment.ts`, or `trampoline-tokens.ts` provides any mitigation against a hook (or any other process with access to the git child's environment) issuing forged trampoline commands. Absent confirmation that Desktop suppresses hook execution or otherwise isolates the environment for hook subprocesses, the authentication model here relies entirely on secrecy of an environment variable that is, by the trampoline's own design, propagated to child processes — including ones the repository itself controls.

### Recommendation
- Bind trampoline tokens to the specific client/process that Desktop itself spawns rather than to a bearer secret alone (e.g., verify the connecting socket originates from a process that is a descendant of the exact `desktop-askpass-trampoline`/credential-helper binary invocation, or use a one-time-use token per invocation rather than one shared across the whole git operation and its hooks).
- Confirm and, if not already done, explicitly disable hook execution or scrub `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from the environment before invoking any repository-controlled hook process (Git provides mechanisms to exclude specific env vars from hook execution, or hooks can be disabled entirely via `core.hooksPath=/dev/null` for untrusted operations such as initial clone).
- Consider scoping `CREDENTIALHELPER get` responses to the `url`/host that Desktop itself expects for that specific operation, rather than trusting the `url` field embedded in the untrusted request body.

### Proof of Concept
1. Create a repository containing a `post-checkout` hook (or `.gitattributes`-driven LFS filter) that reads `process.env.DESKTOP_PORT` and `process.env.DESKTOP_TRAMPOLINE_TOKEN`.
2. The hook opens a raw TCP connection to `127.0.0.1:<DESKTOP_PORT>` and sends a trampoline frame equivalent to what `desktop-trampoline` sends for `CREDENTIALHELPER get`, including `DESKTOP_TRAMPOLINE_TOKEN=<token>`, `DESKTOP_TRAMPOLINE_IDENTIFIER=CREDENTIALHELPER`, parameter `get`, and stdin body `url=https://github.com\n\n`.
3. Have the victim clone/fetch/pull this repository in GitHub Desktop while signed into a real GitHub account.
4. During the git operation, the hook fires, the forged socket connects while the token is still valid, and the trampoline server's `formatCredential()` response returns the victim's real GitHub username/OAuth token back to the hook process, which can write it to disk or exfiltrate it over the network.

**Note on confidence**: I could not fully verify within the available tool budget whether Desktop's `withHooksEnv()`/`git()` wrapper already disables or sandboxes hook execution for untrusted operations (e.g., first clone), which would materially affect the likelihood of this being reachable. This should be verified against the full contents of `app/src/lib/git/core.ts` (`withHooksEnv`) before treating this as conclusively exploitable end-to-end.
