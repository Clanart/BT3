## Title
`IntentGatewayV2` escrow withdrawal loops over attacker-chosen input tokens without duplicate/malicious-token isolation, letting a blocked/blacklisting token permanently stick legitimate escrow and block both fill-settlement and cancel/refund - (`evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder()` lets any unprivileged user pick arbitrary ERC-20 `token` addresses for `order.inputs`, with no allowlist. `_withdraw()` (called by both the fill-settlement path and the cancel/refund path) iterates all escrowed input tokens and transfers each with `IERC20.safeTransfer` in a single atomic call. If one of the attacker-chosen input tokens is a malicious/blacklisting ERC-20 that reverts a transfer to the beneficiary (solver on fill, or user on refund), the entire settlement transaction reverts — permanently stranding every other legitimate escrowed asset in the same order and blocking both the "pay the solver" and "refund the user" recovery paths, exactly mirroring the Mantra `x/tokenfactory` DoS pattern (aggregated payout, single failure point, attacker-supplied token, no fallback for the admin/owner recovery path).

### Finding Description
`placeOrder()` in `evm/src/apps/IntentGatewayV2.sol` performs no allowlist check on `order.inputs[i].token`: [1](#0-0) [2](#0-1) 

Any address can be used as an input token, and multiple distinct tokens are supported per order (only exact duplicates are rejected): [3](#0-2) 

Settlement (whether from a solver's fill via `RedeemEscrow`, or a user/anyone's cancel via `RefundEscrow`/`onGetResponse`) funnels into the same `_withdraw()` helper in `IntentsBase.sol`, which loops through `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each token sequentially, inside one atomic external call: [4](#0-3) 

This is invoked from `onAccept` for both the fill-redemption and refund/cancel flows: [5](#0-4) 

and from the source-chain cancel path via `onGetResponse` in the Tron variant (structurally identical logic exists in the EVM `IntentsBase`/`IntentGatewayV2` combo): [6](#0-5) 

Attack path:
1. Attacker calls `placeOrder()` escrowing two input tokens: one legitimate token (e.g., USDC) and one attacker-deployed ERC-20 with a `transfer`/`safeTransfer` hook that can be made to revert for a chosen address (e.g., a pausable or blacklistable token, or one that reverts once a target condition is met — fully attacker-controlled since the attacker deployed and owns it).
2. A solver fills the order, or the attacker later triggers cancellation. Either path invokes `_withdraw()`/`withdraw()`.
3. Before (or during) settlement, the attacker flips the malicious token's blacklist/pause state to make transfers to the solver or to itself/refund path fail.
4. `_withdraw()`'s loop hits the malicious token's `safeTransfer` and reverts, which reverts the *entire* `onAccept`/`onGetResponse` call — meaning the legitimate USDC leg (already unlocked in the same loop iteration set) never gets paid out, and the order can never be finalized because every future settlement attempt (fill-redeem or cancel-refund) re-enters the same all-or-nothing loop and fails again.
5. Because both the solver-fill settlement path (`RedeemEscrow`) and the recovery/cancel path (`RefundEscrow`, `onGetResponse`) share the identical `_withdraw()` code with no per-token isolation or `try/catch`, there is no owner or protocol-level path to disentangle the stuck legitimate asset — just as in Mantra, where `close_farms`'s automatic refund made the malicious farm unclosable.

### Impact Explanation
This falls squarely under "stealing or loss of funds" and "logic attacks" impacts. A solver who fills a cross-chain or same-chain order can be permanently denied their earned escrow release, and the order's legitimate input token becomes permanently locked in the gateway (no code path releases individual legs of a `WithdrawalRequest`; `_withdraw` reverts wholesale on any single token failure). This also blocks the cancel/refund recovery mechanism the protocol relies on to un-stick bad orders (the same `_withdraw` is used for `RefundEscrow`), so there is no admin or governance lever available on the EVM side to recover the legitimate funds either — the analog to Mantra's finding that `close_farms` itself became unusable.

### Likelihood Explanation
The attack requires only an unprivileged user role that is explicitly permitted by the protocol design: placing an order with arbitrary, attacker-chosen ERC-20 addresses (`placeOrder` performs no token allowlist). Deploying a token whose `transfer` can be selectively blocked (pausable/blacklistable/self-destructing on a condition) is a standard primitive available to any EOA and needs no relayer, prover, governance, or leaked-key assumption. The only requirement is a solver being willing to fill the order (a routine operation) or the attacker/anyone triggering the cancel path after expiry, both of which are normal user-level operations already documented in the protocol's flow.

### Recommendation
- Restrict `order.inputs`/`order.output.assets` tokens at `placeOrder()`/`fillOrder()` time to a protocol-governed allowlist of vetted ERC-20s (mirrors the Mantra fix's need to control which assets can enter aggregated payout paths).
- Make `_withdraw()`/`withdraw()` resilient to a single leg's transfer failure: either (a) process each token transfer independently (e.g., via a low-level call wrapped so a revert on one token doesn't abort the others, crediting a per-user/per-token pull-based balance on failure), or (b) escrow-release per token rather than atomically for the whole order, so a malicious token cannot hold hostage the other legitimate legs or block the cancel/refund path.
- Ensure the cancel/refund settlement path (`onGetResponse`/`RefundEscrow`) has a fallback that can still finalize and release the well-behaved tokens even if one input token's transfer reverts.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer()` reverts once `attacker` calls `EvilToken.arm()`.
2. Attacker calls `placeOrder()` on `IntentGatewayV2` with `order.inputs = [ {token: USDC, amount: X}, {token: EvilToken, amount: Y} ]` and a normal output requirement (e.g., DAI on same or different chain). No allowlist check rejects `EvilToken` (see `placeOrder` at `evm/src/apps/IntentGatewayV2.sol:162-343`, no token validation beyond duplicate-check).
3. A solver calls `fillOrder()`, providing the DAI output and triggering the settlement dispatch (`RedeemEscrow` cross-chain, or direct `_withdraw` same-chain).
4. Before the settlement executes (or before a same-chain fill completes), attacker calls `EvilToken.arm()`, and additionally (for the destination-chain solver) ensures the solver address is blacklisted/blocked.
5. `_withdraw()` in `IntentsBase.sol:390-410` iterates `[USDC, EvilToken]`; the `EvilToken.safeTransfer` call reverts, reverting the whole `_withdraw` call and hence the entire `onAccept`/fill transaction. The solver never receives USDC despite having delivered the DAI output (already sent to the beneficiary in `fillOrder` before the escrow-release dispatch, per `ExtrinsicIntents.sol` output-transfer-then-dispatch ordering), and the escrow entry for USDC remains locked in the gateway with no way to release it, since every retry hits the same malicious token in the loop.
6. Cancel path is equally blocked: calling `cancelOrder()` after expiry routes to the same `_withdraw`/`withdraw` function with the identical token list, so the user cannot recover the legitimate USDC escrow either.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
