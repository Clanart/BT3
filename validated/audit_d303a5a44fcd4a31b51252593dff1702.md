### Title
Unauthenticated `ReceivedOutput` deserialization bypasses scanner ownership checks - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` represents a spendable Bitcoin output and the scalar offset needed to spend it. [1](#0-0)  Its deserializer accepts an attacker-controlled offset, `TxOut`, and outpoint without checking that the output script belongs to the wallet or that the outpoint exists. [2](#0-1) 

### Finding Description
The trusted construction path is `Scanner::scan_transaction`, which only creates a `ReceivedOutput` after finding `output.script_pubkey` in the scanner’s registered script-to-offset map. [3](#0-2)  `ReceivedOutput::read` bypasses that authorization invariant entirely: it independently accepts `offset`, `output`, and `outpoint` from serialized bytes and returns the security-bearing object. [2](#0-1) 

An attacker can therefore encode an arbitrary P2TR output paying to their own key, pair it with any scalar offset and arbitrary or unrelated outpoint, and have it accepted as a received output. The parsed object will report the attacker-chosen amount through `ReceivedOutput::value`. [4](#0-3) 

### Impact Explanation
A wallet or processor that accepts serialized `ReceivedOutput` values from an untrusted source can report funds as received even though Serai cannot spend them. Spending will use the supplied scalar offset as the output-key offset, but the attacker-selected script need not correspond to `key + offset * G`; the resulting spend will not satisfy the actual output script. [1](#0-0) 

This is analogous to incorrect access control because deserialization acts as an alternate construction path that omits the ownership check enforced by `Scanner`. [3](#0-2) 

### Likelihood Explanation
Exploitation requires only control of bytes passed to `ReceivedOutput::read`, such as an untrusted import, cache, replication message, or stored output record. No private key, validator privilege, threshold collusion, or protocol interaction is required. [2](#0-1) 

### Recommendation
Do not use `ReceivedOutput::read` as an unauthenticated constructor for spendable outputs. Either authenticate serialized outputs as trusted local state, or reconstruct them through `Scanner` so `script_pubkey` is checked against the registered key-plus-offset mapping. [5](#0-4)  Before marking an output received, also verify that the declared outpoint exists on-chain and that its consensus-decoded `TxOut` exactly matches the scanned output. [3](#0-2) 

### Proof of Concept
The following byte-level construction demonstrates the missing validation:

```rust
use bitcoin::{
  consensus::Encodable,
  OutPoint, TxOut, Amount,
};
use k256::Scalar;
use bitcoin_serai::wallet::ReceivedOutput;

// Any valid P2TR script controlled by the attacker, rather than the scanner's key.
let attacker_owned_txout = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: attacker_owned_p2tr_script,
};

let mut encoded = Vec::new();
encoded.extend_from_slice(Scalar::ZERO.to_bytes().as_ref());
attacker_owned_txout.consensus_encode(&mut encoded).unwrap();
OutPoint::null().consensus_encode(&mut encoded).unwrap();

let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
assert_eq!(forged.value(), 100_000);
assert_eq!(forged.offset(), Scalar::ZERO);
assert_eq!(forged.outpoint(), &OutPoint::null());
```

`read` accepts the object even though `Scanner::scan_transaction` would never emit it for a wallet whose script map does not contain `attacker_owned_p2tr_script`. [2](#0-1)
