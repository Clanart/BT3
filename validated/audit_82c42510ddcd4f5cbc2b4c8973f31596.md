### Title
Unchecked `payment_sat + needed_fee` (and `payment_sat + fee_with_change`) overflow in `SignableTransaction::new` bypasses the insufficient-funds check and produces an invalid/over-fee transaction or a panic - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to CVE-2020-0198 (integer overflow → abort on attacker-influenced data), `SignableTransaction::new` in `bitcoin-serai` performs unchecked `u64` addition and multiplication on amounts derived from requested payments when constructing the multisig's Bitcoin spend. The overflow either aborts (debug/overflow-checks builds) or wraps (release), defeating the `NotEnoughFunds` guard and producing a transaction whose outputs exceed its inputs — which the FROST machines then sign, yielding an unbroadcastable transaction and/or a subsequent underflow panic in `fee()`.

### Finding Description
In `SignableTransaction::new`:

```rust
// networks/bitcoin/src/wallet/send.rs:187-215
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
...
let mut needed_fee = fee_per_vbyte * vbytes;              // L206: unchecked mul
...
if input_sat < (payment_sat + needed_fee) {               // L215: unchecked add
  Err(TransactionError::NotEnoughFunds { ... })?;
}
```

and again at L228:

```rust
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
```

`payment_sat` is the sum of caller-supplied payment amounts (`payments: &[(ScriptBuf, u64)]`), and `fee_per_vbyte` is a caller-supplied rate. `payment_sat + needed_fee` and `fee_per_vbyte * vbytes` can each overflow `u64`. With `overflow-checks` on, this is a direct abort (the exif UBSAN-abort analog). In release it wraps: `payment_sat + needed_fee` wraps to a small value, so the `input_sat < ...` test passes even though `payment_sat > input_sat`. The `checked_sub` at L228 contains the *same* wrapping sub-expression, so it too returns `Some(value)` for a wrapped difference, letting a change output be appended. The result is a `SignableTransaction` whose output total exceeds its input total.

This is reachable via the payment/amount fields of a withdrawal the user causes the multisig to sign — `payments` flow from externally requested outputs into `SignableTransaction::new`, and `input_sat` is bounded by the real scanned UTXOs (≤ 21M BTC in sats), so an oversized payment amount is the only ingredient needed.

### Impact Explanation
- **Abort/DoS**: in any build with overflow checks, `payment_sat + needed_fee` panics, crashing the signing path for that attempt.
- **Incorrectly signed transaction**: in release, the wrapped comparison admits a transaction with `sum(outputs) > sum(inputs)`. `TransactionSignMachine::sign` (send.rs:355-397) will then produce valid FROST signature shares for it via `taproot_key_spend_signature_hash`, wasting the nonce round on a transaction Bitcoin consensus will reject — a denial of service on the spend pipeline.
- **Secondary underflow**: `SignableTransaction::fee()` (send.rs:138-141) computes `sum(prevouts) - sum(outputs)` with plain subtraction; for the overflowed transaction this underflows, panicking under overflow checks or reporting a garbage (near-`u64::MAX`) fee in release.

### Likelihood Explanation
Triggering requires a payment amount large enough that `payment_sat + needed_fee` exceeds `u64::MAX` (~1.8e19 sats), i.e. a payment list whose sum approaches `2^64`. Whether callers can submit such amounts depends on upstream validation of payment values before they reach `SignableTransaction::new`; the function itself performs no cap. If any path feeds unvalidated withdrawal amounts (or `fee_per_vbyte`) into this constructor, the overflow is trivially induced by an unprivileged party requesting the signature.

### Recommendation
Use checked arithmetic for all amount math in `SignableTransaction::new`: `payment_sat.checked_add(needed_fee)`, `fee_per_vbyte.checked_mul(vbytes)`, and `payment_sat.checked_add(fee_with_change)`, mapping overflow to `TransactionError::NotEnoughFunds`/`TooMuchData`. Also make `fee()` use `checked_sub` or `saturating_sub` so a malformed transaction cannot panic.

### Proof of Concept
```rust
// Conceptual: payments whose sum wraps u64
let huge_payment = (script_pubkey, u64::MAX); // payment.1
// input_sat is bounded by real UTXOs, e.g. 1_000_000 sats
// payment_sat + needed_fee wraps to (u64::MAX + fee) - u64::MAX ≈ fee - 1 < input_sat
// => NotEnoughFunds check bypassed; fee() then underflows:
//    sum(prevouts) - sum(outputs) = 1_000_000 - u64::MAX  => panic / wrap
SignableTransaction::new(inputs, &[(script_pubkey, u64::MAX)], None, None, 1);
```
