### Title
Governance vote can set `kip71.gastarget` to zero, causing a division-by-zero panic in `KIP71Config.NextMagmaBlockBaseFee` used by every node during block validation and assembly - ([File: params/kip71_config.go])

### Summary
This is the same bug class as Sherlock M-13 (`BondBaseSDA.setDefaults` accepting unvalidated parameters that break protocol logic): Kaia's governance parameter framework accepts a new value for `kip71.gastarget` without any format/consistency check, and a zero value causes a `big.Int` division-by-zero panic in the KIP-71 base-fee formula that runs on every block.

### Finding Description
The `Kip71GasTarget` governance parameter is registered with `FormatChecker: noopFormatChecker`, which always returns `true`, i.e. no validation is applied to the submitted value: [1](#0-0) 

The header-vote consistency checker (`checkConsistency`) also performs no cross-check for `gov.Kip71GasTarget` — it falls into the default "no more checks here" bucket: [2](#0-1) 

Unlike `BaseFeeDenominator`, which explicitly guards against zero (`v != 0` in its `FormatChecker`) and also has a runtime zero-check fallback in `NextMagmaBlockBaseFee`, `GasTarget` has neither: [3](#0-2) [4](#0-3) 

If `kc.GasTarget == 0` and `parentGasUsed > 0` (the overwhelmingly common case), the code takes the "usage above target" branch and performs `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`, which panics in Go's `math/big` package: [5](#0-4) 

The same divide-by-zero also occurs in the "usage below target" branch: [6](#0-5) 

### Impact Explanation
`NextMagmaBlockBaseFee` (and its wrapper `VerifyMagmaHeader`) is invoked by all nodes during block validation and by proposers during block assembly. Once a `kip71.gastarget = 0` vote is committed to a block header (governance votes are cast by the governing node in `single` mode, or via the governance mechanism in general — an explicitly in-scope path per this scan's rules), every subsequent node that processes a block with nonzero gas usage will panic while computing/verifying the base fee. This is a chain-halting bug: it prevents the network from producing or validating further blocks, i.e. a network-wide denial of service triggered by a single governance parameter update, matching the "state divergence between honest nodes / acceptance of invalid state" severity bar.

### Likelihood Explanation
The parameter is a plain governance vote value (`uint64`) with no bounds checking anywhere in the vote-submission, vote-verification, or parameter-canonicalization pipeline. Any actor with governance voting rights (the governing node in `single` mode) can submit this value in a single transaction/header vote; no other preconditions are required.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects zero (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check), and additionally add a defensive zero-check fallback in `NextMagmaBlockBaseFee` (as already done for `BaseFeeDenominator`) so that a zero `GasTarget` cannot reach the division operations.

### Proof of Concept
1. As the governing node (in `single` governance mode), submit a header vote setting `gov.Kip71GasTarget = 0` (format-accepted since `FormatChecker` is `noopFormatChecker` and `checkConsistency` performs no check for this parameter).
2. Once the vote is finalized and applied to the effective `ParamSet`/`ChainConfig.Governance.KIP71.GasTarget`, the next block with `gasUsed > 0` triggers `NextMagmaBlockBaseFee`.
3. Inside `NextMagmaBlockBaseFee`, since `parentGasUsed > gasTarget (0)`, the code executes `x.Div(x, new(big.Int).SetUint64(0))`, causing a runtime panic in every node that validates or assembles that block, halting the chain.
