## Analysis

The external report's core broken invariant: an **admin "update" function silently changes a critical token/contract binding without preserving the operational guarantees that existing custodied state depends on**, resulting in stuck or misrouted funds.

The strongest local analog in Hyperbridge is in `WrappedHyperFungibleToken.configure()`, which re-binds `_underlying` (and `_dispatcher`) with no protection for tokens that are already escrowed under the *old* binding — unlike `EvmHost.updateHostParamsInternal`, which explicitly guards against this exact class of bug for `feeToken`.

### Title
Reconfiguring `_underlying` in `WrappedHyperFungibleToken` while transfers are in flight mispays or strands escrowed funds - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.configure()` allows the `_underlying` token address to be changed at any time (only `_host` is set-once), with no check that the contract holds no outstanding balance of the token currently locked against in-flight ISMP requests. `onAccept` and `onPostRequestTimeout` always read the *current* `_underlying` state variable rather than any value bound to the specific request being settled, so if the owner reconfigures the token while `send()`-originated commitments are still pending, incoming settlement/timeout payouts execute against the wrong ERC-20, either draining unrelated token balance or reverting/permanently stranding the funds actually locked from the original escrow.

### Finding Description
- `send()` locks the underlying token current at call time: `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);` [1](#0-0) 
- `configure()` can change `_underlying` (and `_dispatcher`) at any time after deployment — only `_host` is set-once and immutable thereafter: [2](#0-1) 
- `onAccept` (settling an incoming transfer) and `onPostRequestTimeout` (refunding a timed-out send) both pay out using the *current* `_underlying` value, not the token that was actually escrowed for that specific commitment: [3](#0-2) [4](#0-3) 

Because there is no per-commitment binding of the escrowed token, once `_underlying` is switched:
- A completed remote transfer that arrives via `onAccept` will pay the beneficiary in the *new* underlying token, using whatever balance of that new token the contract happens to hold — this can pay the wrong asset/amount relationship to the beneficiary (drains unrelated funds, e.g. dust reserves or accidentally-sent tokens) or simply revert if the contract holds none, permanently blocking settlement of that commitment.
- A `send()` that is later timed out will attempt to refund the sender in the *new* underlying token via `onPostRequestTimeout`, even though the sender's original tokens were the *old* underlying — the sender either gets refunded the wrong asset or the refund reverts, permanently locking their original escrowed tokens in the contract with no recovery path (no rescue/sweep function exists in this contract).

This is exactly the same defect class as the report's `updateGToken`: a critical address is updated by an "update"-style entrypoint, but the invariant that existing escrowed value remains redeemable/transferable is not preserved, and the contract provides no protective check. Notably, the codebase's own `EvmHost.updateHostParamsInternal` demonstrates the fix pattern already exists for the analogous `feeToken` field:
```
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
``` [5](#0-4) 

`WrappedHyperFungibleToken.configure()` has no equivalent guard for `_underlying`.

### Impact Explanation
This directly maps to the Hyperbridge bounty's "Bridged assets ... must move exactly once and only to the rightful beneficiary and amount" pivot. The result is either:
- wrong-token/wrong-amount payout to a beneficiary or sender (transaction manipulation / fund loss for the protocol or other users whose tokens are drained), or
- permanent locking of legitimately escrowed user funds with no recovery mechanism in the contract.

Both are within the "stealing or loss of funds" / "unauthorized transaction or execution" impact categories, not merely an operational inconvenience.

### Likelihood Explanation
Medium: it requires an owner-initiated `configure()` call while requests are in flight (a normal operational action such as migrating to a new canonical token or dispatcher, not a compromise), combined with the natural latency of cross-chain settlement (which routinely spans the challenge period). No malicious relayer, prover, or governance compromise is needed — only a legitimate, foreseeable admin re-configuration performed without draining/pausing in-flight state first, matching the same likelihood profile ("Medium") as the original `updateGToken` report.

### Recommendation
Add the same protective pattern already used in `EvmHost.updateHostParamsInternal` for `feeToken`: before allowing `_underlying` (or `_dispatcher`) to change in `configure()`, require `IERC20(_underlying).balanceOf(address(this)) == 0`, or alternatively bind the escrowed token address into the dispatched `Message`/commitment so `onAccept`/`onPostRequestTimeout` always settle against the token that was actually locked, independent of the current `_underlying` value. Consider also pausing sends before migration and providing an explicit drain/rescue path for stranded balances.

### Proof of Concept
1. Owner deploys and configures `WrappedHyperFungibleToken` with `underlying = TokenA`.
2. User calls `send()`, locking `1000 TokenA` in the contract; a POST request commitment is dispatched cross-chain.
3. Before the request is delivered or times out, owner calls `configure()` again with `underlying = TokenB` (e.g., migrating to a new canonical token) — permitted with no restriction: [2](#0-1) 
4. If the request later times out, `onPostRequestTimeout` executes `IERC20(_underlying).safeTransfer(refundee, message.amount)` against `TokenB`, not the `TokenA` the user actually locked — either reverting (locking the user's `TokenA` permanently, since no rescue function exists) or paying out `TokenB` if the contract happens to hold some (fund loss/misallocation for whoever's `TokenB` balance gets drained).
5. Symmetric failure occurs on the `onAccept` settlement path for legitimate incoming transfers dispatched under the old `TokenA` binding.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
