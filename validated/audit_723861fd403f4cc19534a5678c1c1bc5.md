### Title
`placeOrder` escrow accounting in the Tron `IntentGatewayV2` ignores fee-on-transfer token loss, over-crediting escrow beyond actual custody - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the escrowed/committed input amounts from the user-declared `order.inputs[i].amount` **before** the token transfer takes place, and then performs the actual transfer with a bare `safeTransferFrom` with no balance-based verification of what the contract actually received. For any ERC20 with a transfer fee/tax (the exact class of token flagged in the referenced M04 report), the escrow ledger `_orders[commitment][token]` is credited with more tokens than the gateway actually custodies.

### Finding Description
In `placeOrder`, the reduced (post protocol-fee) input amounts and the order `commitment` are derived directly from the caller-supplied amount: [1](#0-0) 

This `reducedInputs` array (and the `commitment` hash) is fixed before any tokens move. The actual token movement in the non-predispatch path then just calls `safeTransferFrom` and unconditionally credits the escrow with the pre-computed `reducedInputs[i].amount`, without ever checking how many tokens the gateway actually received: [2](#0-1) 

The predispatch path has the same flaw: the sweep step does compute `dust = balance - requiredAmount` for emitting an event, but escrow crediting still uses the pre-computed `reducedInputs[i].amount`, not the amount actually swept into the gateway: [3](#0-2) 

This is a direct regression/analog of the exact bug class described in the external report: `safeTransferFrom` gives no guarantee that the recipient balance increased by the transferred amount, and any accounting that assumes it did will be wrong for deflationary/fee-charging tokens.

Contrast this with the sibling implementation `evm/src/apps/IntentGatewayV2.sol`, which was hardened against exactly this issue: it snapshots `balanceOf(address(this))` before `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual delta before computing protocol fees/commitment/escrow: [4](#0-3) 
Foundry tests explicitly validate this behavior on the main EVM contract: [5](#0-4) 

The Tron contract lacks this fix entirely, so its escrow ledger and `commitment` hash can diverge from the gateway's real custodied balance.

### Impact Explanation
`_orders[commitment][token]` is a shared bookkeeping map over a token type that is *not* physically segregated per-order — the actual custody is just the gateway's aggregate ERC20 balance. If an order is placed with a fee-on-transfer input token, the escrow ledger records more tokens than were actually deposited. When that order is later filled (escrow released to solver) or cancelled/refunded (`withdraw`, reachable via `cancelOrder` same-chain path or via `RedeemEscrow`/`RefundEscrow` in `onAccept`), the contract will attempt to pay out the inflated, declared amount recorded in escrow rather than what it actually holds for that token. Because the underlying balance is shared across all orders for that token, this shortfall is paid for out of other users' legitimately escrowed funds, i.e., loss of funds / broken settlement invariant — the escrow state is falsely accepted as fully collateralized when it is not. This matches the "stealing or loss of funds" / "false state acceptance" impact classes in the bounty scope, mirroring the original SwapUtils issue where miscounted transferred amounts corrupted downstream financial calculations.

### Likelihood Explanation
This is triggerable by any unprivileged user who calls `placeOrder` with an input token that charges a transfer fee (a known, real-world token category — USDT-style fee toggles, and many "tax token" ERC20s deployed on Tron/EVM chains). No relayer, prover, or admin cooperation is required; the corruption happens purely from normal ERC20 transfer semantics interacting with the unguarded arithmetic in `placeOrder`.

### Recommendation
Apply the same balance-delta pattern used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: snapshot `balanceOf(address(this))` (or the dispatcher's balance for the predispatch sweep) before and after each `safeTransferFrom`/sweep, mutate `order.inputs[i].amount` to the actual received delta, and only then compute `protocolFeeBps`, `reducedInputs`, the `commitment` hash, and the `_orders[commitment][token]` escrow credit.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) on the Tron-deployed `IntentGatewayV2`.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`.
3. `reducedInputs[0].amount` is computed as `1000e18 - protocolFee` (based on the full 1000e18, not on what's received).
4. `safeTransferFrom` executes; gateway actually receives only `990e18` (1% fee burned/taken).
5. `_orders[commitment][FOT] += reducedInputs[0].amount` credits ~`1000e18 - protocolFee`, i.e. more than the `990e18` actually held.
6. On fill/cancel, `withdraw` will attempt to pay out the escrowed (inflated) amount from the gateway's shared FOT balance, depleting funds belonging to other unrelated orders using the same token, eventually causing their legitimate withdrawals to revert or receive less than entitled.

This exact scenario is already unit-tested and confirmed fixed on the main EVM contract (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`) but the equivalent protection is absent from `evm/tron/contracts/apps/IntentGatewayV2.sol`. [6](#0-5)

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }

    function testPlaceOrder_FeeOnTransferToken_WithProtocolFee() public {
        IntentGatewayV2 gatewayWithFees = _deployGatewayProxy();

        uint256 expectedEscrow = receivedAfterTransferFee - protocolFee;

        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);

            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(gatewayWithFees), inputAmount);
        gatewayWithFees.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.source = host.host();

        order.inputs[0].amount = expectedEscrow; // commitment is hashed with reduced amount
        bytes32 commitment = keccak256(abi.encode(order));

        assertEq(
            gatewayWithFees._orders(commitment, address(fot)),
            expectedEscrow,
            "Escrow should equal received minus protocol fee"
        );
    }
