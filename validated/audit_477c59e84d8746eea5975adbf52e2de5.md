### Title
Governance can set `kip71.gastarget` to 0, causing a division-by-zero panic in base fee computation with no recovery - (File: params/kip71_config.go)

### Summary
The KIP-71 dynamic base-fee mechanism computes the next block's base fee using `GasTarget` as a divisor, but the `Kip71GasTarget` governance parameter has no validation preventing it from being set to zero, unlike its sibling parameter `Kip71BaseFeeDenominator` which explicitly rejects zero. Once a value of `0` for `GasTarget` is accepted by governance and activated, every node computing the next base fee (during block production, block validation, and gas price estimation) will hit an integer division by zero and panic, halting the chain with no way to recover, analogous to the reported "no way to remove GasThrottle" issue where a compromised value with no override caused unrecoverable denial of service.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` in both the "gas used above target" and "gas used below target" branches: [1](#0-0) [2](#0-1) 

`gasTarget` is taken directly from `KIP71Config.GasTarget` with no zero-guard (unlike `baseFeeDenominator`, which falls back to a hardcoded default of 64 when zero): [3](#0-2) 

The governance parameter registry defines `Kip71GasTarget` with `FormatChecker: noopFormatChecker`, meaning any `uint64` value including `0` passes validation and canonicalization: [4](#0-3) 

By contrast, `Kip71BaseFeeDenominator` explicitly enforces `v != 0` in its `FormatChecker`: [5](#0-4) 

This asymmetry shows the zero-check was consciously applied to `BaseFeeDenominator` but omitted for `GasTarget`, despite `GasTarget` being used identically as a divisor in `NextMagmaBlockBaseFee`.

`NextMagmaBlockBaseFee` is invoked on the hot path of block production and validation - in `blockchain/block_validator.go`, `work/worker.go`, `blockchain/chain_makers.go`, and `blockchain/tx_pool.go` - meaning a `GasTarget = 0` value would trigger the panic on essentially every node computing or validating the next block's header, not just a single actor.

### Impact Explanation
If a governance vote sets `kip71.gastarget` to `0` and it is finalized/activated (unless voting-value validation elsewhere blocks it, which the codebase's own `FormatChecker` mechanism explicitly does not for this parameter), then as soon as the parent block's `GasUsed` is not exactly `0` (i.e., in the overwhelming majority of real blocks), `parentGasUsed > gasTarget` is true, and the subsequent `x.Div(x, new(big.Int).SetUint64(gasTarget))` performs a division by zero. Go's `math/big` `Int.Div` panics on division by zero. This function runs in the header-preparation/validation path used by every honest node building or verifying the next block, so the panic would crash consensus block-processing goroutines network-wide, producing a chain halt with no way to recover on-chain (a subsequent corrective governance vote cannot even be processed because block production/validation itself panics first). This is a critical, unrecoverable denial-of-service on the whole network, directly analogous to the reported GasThrottle issue (a single unguarded parameter with no override causing all transaction/block processing to permanently fail), but with node-crashing severity rather than mere tx-revert severity.

### Likelihood Explanation
Reaching this requires a governance-parameter vote to set `kip71.gastarget = 0`, which is the standard, expected mechanism for adjusting KIP-71 parameters (the same mechanism used to set `LowerBoundBaseFee`, `UpperBoundBaseFee`, etc., which do have some bound handling built into `NextMagmaBlockBaseFee` itself). Since `Kip71GasTarget`'s `FormatChecker` is a `noopFormatChecker`, nothing in the parameter layer rejects the zero value before it is written to `ParamSet`/`ChainConfig`, so the sole gate is voting governance/social process, not code-level input validation. This is a straightforward oversight (missing zero-check that its sibling parameter has) rather than requiring deep cryptographic or timing conditions, making it moderately likely for a malicious or careless governance proposal to trigger it.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`, if it can also reach a zero-divide path) that rejects `0`, mirroring the existing `Kip71BaseFeeDenominator` check:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, as defense-in-depth (consistent with the `GasThrottle` mitigation recommendation to "allow governance to turn it off" or otherwise fail safe), `NextMagmaBlockBaseFee` in `params/kip71_config.go` should guard against `gasTarget == 0` the same way it already guards `baseFeeDenominator == 0` (fallback to a safe default) rather than relying solely on upstream input validation.

### Proof of Concept
1. Governance vote sets `kip71.gastarget` to `0` via the standard governance vote flow (`kaiax/gov/param.go`, `Kip71GasTarget` entry), which is accepted because `FormatChecker` is `noopFormatChecker`. [4](#0-3) 
2. Vote is finalized and the parameter becomes active in a subsequent `ParamSet`/`ChainConfig.Governance.KIP71.GasTarget`.
3. On the next block after activation, any node calling `KIP71Config.NextMagmaBlockBaseFee` (block proposer in `work/worker.go`, validators in `blockchain/block_validator.go`, or gas price oracle in `node/cn/gasprice/gasprice.go`) computes `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)`; since the parent block almost certainly used gas (`parentGasUsed != 0 == gasTarget`), the code takes the `parentGasUsed > gasTarget` branch: [6](#0-5) 
4. `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` executes with `gasTarget == 0`, causing a `runtime` panic (division by zero) in every node performing this computation, halting block production/validation network-wide with no in-protocol recovery path.
