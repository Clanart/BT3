### Title
Missing `chain_id` in Static EIP-712 Domain Separator Enables Cross-Deployment Signature Replay on Optimistic Payout and Withdrawal Authorization — (`File: core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

`CLEMENTINE_EIP712_DOMAIN` is declared as a compile-time `static` constant with only `name` and `version` fields. The `chain_id` (and `verifying_contract`) fields mandated by EIP-712 for replay protection are absent. Because the domain separator does not bind to any specific Citrea network, a valid aggregator signature produced for one deployment (e.g., testnet, chain_id=5655) is cryptographically indistinguishable from a valid signature for any other deployment (e.g., mainnet, chain_id=5115) that uses the same aggregator key. This is the direct Clementine analog of the uninitialized EIP-712 domain bug: the domain is present but critically incomplete, leaving the signing context unbound to the network.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

No `chain_id` or `verifying_contract` field is present. The `citrea_chain_id` is available in `BridgeConfig` at runtime but is never incorporated into the domain. [2](#0-1) 

This domain is consumed in `recover_address_from_ecdsa_signature`, which is the sole function used to authenticate the aggregator's identity for both optimistic payout and operator withdrawal:

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)...;
``` [3](#0-2) 

The recovered address is then compared against `aggregator_verification_address` in two places:

**Verifier — optimistic payout path** (`sign_optimistic_payout`): [4](#0-3) 

**Operator — withdrawal path** (`withdraw` RPC handler): [5](#0-4) 

Because the domain separator is network-agnostic, the EIP-712 hash of a given `(withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount)` tuple is identical across all Citrea deployments. A signature produced by the aggregator key on deployment A is valid on deployment B.

---

### Impact Explanation

The `aggregator_verification_address` check is the gating authorization control that prevents unauthorized parties from triggering optimistic payouts and operator withdrawals. When this check is enabled (i.e., `aggregator_verification_address` is `Some`), the missing `chain_id` in the domain separator means:

1. A signature produced by the aggregator for a withdrawal on Citrea testnet (chain_id=5655) passes the address-recovery check on Citrea mainnet (chain_id=5115) unchanged, because the EIP-712 hash is identical on both networks.
2. If the same Bitcoin UTXO (`input_outpoint`) is recorded as a valid withdrawal UTXO in both deployments' databases (possible when both deployments track the same Bitcoin chain), the replayed signature passes all downstream guards in `sign_optimistic_payout` and `withdraw`, causing verifiers to co-sign an optimistic payout transaction or the operator to execute a payout transaction that was never authorized for that deployment.
3. The result is an unauthorized spend of bridge-controlled funds (the move-to-vault UTXO) or an unauthorized reimbursement of operator collateral. [6](#0-5) 

---

### Likelihood Explanation

The attack requires two conditions to hold simultaneously:

1. **Same aggregator key across deployments** — the `aggregator_verification_address` is a single Ethereum address configured identically on all deployments. If the same key pair is used (common operational practice), signatures are cross-replayable.
2. **Matching withdrawal parameters on both deployments** — the `input_outpoint` (Bitcoin UTXO) and `deposit_id` must resolve to valid entries in the target deployment's database. This is plausible when both a testnet and mainnet Citrea deployment track the same Bitcoin mainnet chain, causing the same UTXOs to appear in both databases.

The `aggregator_verification_address` field defaults to `Some(...)` in `BridgeConfig::default()`: [7](#0-6) 

This means the check is active in the default configuration, making the domain weakness reachable in production.

---

### Recommendation

Replace the compile-time static domain with a runtime-constructed domain that incorporates `citrea_chain_id` from `BridgeConfig`:

```rust
pub fn clementine_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass `config.citrea_chain_id as u64` wherever `CLEMENTINE_EIP712_DOMAIN` is currently used in `recover_address_from_ecdsa_signature`, `sign_optimistic_payout`, `withdraw`, and `sign_withdrawal_verification_signature`. [8](#0-7) [9](#0-8) 

---

### Proof of Concept

1. Deploy Clementine on Citrea testnet (chain_id=5655) and Citrea mainnet (chain_id=5115), both tracking Bitcoin mainnet, using the same aggregator key pair.
2. On testnet, the aggregator signs an `OptimisticPayoutMessage` for `(withdrawal_id=42, input_outpoint=X:0, output_script_pubkey=P, output_amount=A)` and produces signature `σ`.
3. Confirm that `eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)` produces the same 32-byte hash on both deployments for the same message fields — this is guaranteed because `CLEMENTINE_EIP712_DOMAIN` contains no chain-specific data.
4. Submit `σ` to the mainnet verifier's `optimistic_payout_sign` RPC with the same parameters. The verifier calls `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>` with the same static domain, recovers the same aggregator address, and passes the `address_from_sig != address_in_config` check.
5. If `input_outpoint=X:0` is also a recorded withdrawal UTXO in the mainnet database (step 4 of `sign_optimistic_payout`), the verifier proceeds to co-sign the optimistic payout transaction, spending the mainnet bridge UTXO without a legitimate mainnet aggregator authorization. pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}

        &self,
        nonce_session_id: u128,
        agg_nonce: AggregatedNonce,
        deposit_id: u32,
        input_signature: taproot::Signature,
        input_outpoint: OutPoint,
        output_script_pubkey: ScriptBuf,
        output_amount: Amount,
        verification_signature: Option<PrimitiveSignature>,
    ) -> Result<PartialSignature, BridgeError> {
        // if the withdrawal utxo is spent, no reason to sign optimistic payout
        if self.rpc.is_utxo_spent(&input_outpoint).await? {
            return Err(
                eyre::eyre!("Withdrawal utxo {:?} is already spent", input_outpoint).into(),
            );
        }

        // check for some standard script pubkeys
        if !(output_script_pubkey.is_p2tr()
            || output_script_pubkey.is_p2pkh()
            || output_script_pubkey.is_p2sh()
            || output_script_pubkey.is_p2wpkh()
            || output_script_pubkey.is_p2wsh())
        {
            return Err(eyre::eyre!(format!(
                "Output script pubkey is not a valid script pubkey: {}, must be p2tr, p2pkh, p2sh, p2wpkh, or p2wsh",
                output_script_pubkey
            )).into());
        }

        // if verification address is set in config, check if verification signature is valid
        if let Some(address_in_config) = self.config.aggregator_verification_address {
            // check if verification signature is provided by aggregator
            if let Some(verification_signature) = verification_signature {
                let address_from_sig =
                    recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>(
                        deposit_id,
                        input_signature,
                        input_outpoint,
                        output_script_pubkey.clone(),
                        output_amount,
                        verification_signature,
                    )?;

                // check if verification signature is signed by the address in config
                if address_from_sig != address_in_config {
                    return Err(BridgeError::InvalidECDSAVerificationSignature);
                }
            } else {
                // if verification signature is not provided, but verification address is set in config, return error
                return Err(BridgeError::ECDSAVerificationSignatureMissing);
            }
        }
