Based on the trampoline credential-helper code paths, the closest analog to the "overwrite without uniqueness check" bug class in Desktop is the generic-credential storage path used by the git credential helper trampoline.

### Title
Generic Git Credential Overwrite Without Existing-Entry Check in `setGenericCredential` - (File: app/src/lib/generic-git-auth.ts)

### Summary
`ResourceLock`'s bug is that a session's storage key (`sessionKey`+`msg.sender`) is written unconditionally, silently overwriting a live session and orphaning related state. The Desktop analog is `setGenericCredential`/`setGenericUsername`/`setGenericPassword`, which persist a login/token for a host **key derived from the credential URL git hands to the trampoline**, with no check for whether a credential is already stored for that key before overwriting it.

### Finding Description
`createCredentialHelperTrampolineHandler`'s `store` command calls `storeCredential`, which for any endpoint classified as `generic` (i.e., not a recognized GitHub.com/GHE host — determined by `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts:137-179`) calls: [1](#0-0) 

This flows into `setGenericCredential`, which unconditionally calls `localStorage.setItem` for the username and `TokenStore.setItem` (keytar) for the password, keyed purely by `endpoint`: [2](#0-1) 

There is no check analogous to the recommended `if (sessionData[...].live) revert()` — no comparison against an existing username/password for that endpoint, and no confirmation that the endpoint corresponds to the same logical remote/session the user originally authenticated. The `endpoint` key itself is derived from `getCredentialUrl(cred)` (`app/src/lib/trampoline/trampoline-environment.ts:46-59`), which is built straight from the `url`/`protocol`/`host`/`path` fields Git passes to the credential helper for the current operation — values that originate from the remote/proxy response Git is talking to (e.g., following a redirect or a `WWW-Authenticate` challenge on a non-GitHub host).

### Impact Explanation
Because the write path never checks for or protects an existing entry, a second `store` invocation for the same host (triggered by any subsequent fetch/push/clone against an attacker-controlled or attacker-redirected generic git endpoint) silently clobbers the previously stored username/password for that host. This mirrors the `ResourceLock` bug's "silent overwrite of live session data" invariant break: the legitimate credential is discarded without warning, and any code path that later reads it via `getGenericPassword`/`findGenericTrampolineAccount` (`app/src/lib/trampoline/find-account.ts:31-59`) will authenticate future git operations against that host using the attacker-influenced credential instead of the user's real one — leading to credential exfiltration on the next legitimate push/fetch, or the user's real credential being silently lost.

### Likelihood Explanation
This path only triggers for hosts classified as `generic` (non-GitHub), which requires the attacker to control (or man-in-the-middle) a plain/self-hosted git remote the user already interacts with, and to be able to cause Git to issue a `store` command for that endpoint (normal Git credential-helper behavior after a successful HTTP auth). I was not able to fully verify from the indexed code whether Git's own redirect/host-scoping protections (which normally prevent credentials for host A from being requested/stored under host B) are bypassed here, since that enforcement partly lives in Git itself rather than in this trampoline code — this is the main uncertainty in the analysis.

### Recommendation
Before overwriting, compare the incoming username/password against any existing entry for the endpoint and require explicit user confirmation (similar to the `ExistingAccountWarning` flow already used in `SignInStore`) or reject silent overwrite when an existing credential's username differs, mirroring the `ResourceLock` fix's "check if already live/in-use" pattern.

### Proof of Concept
Not independently verifiable purely from the indexed code — reproducing this would require driving Git's actual credential-helper protocol against a proxy/MITM'd generic git host and observing the keytar/localStorage overwrite, which requires runtime/filesystem access unavailable in this read-only analysis. This should be validated with a live Desktop session rather than asserted as confirmed.

```typescript
/** Implementation of the 'store' git credential helper command */
async function storeCredential(cred: Credential, store: Store, token: string) {
  if ((await getEndpointKind(cred, store)) !== 'generic') {
    return
  }

  return useExternalCredentialHelper()
    ? storeExternalCredential(cred, token)
    : setGenericCredential(
        urlWithoutCredentials(getCredentialUrl(cred)),
        forceUnwrap(`credential missing username`, cred.get('username')),
        forceUnwrap(`credential missing password`, cred.get('password'))
      )
```

```typescript
/** Set the username for the host. */
export function setGenericUsername(endpoint: string, username: string) {
  const key = getKeyForUsername(endpoint)
  return localStorage.setItem(key, username)
}

/** Set the password for the username and host. */
export function setGenericPassword(
  endpoint: string,
  username: string,
  password: string
): Promise<void> {
  const key = getKeyForEndpoint(endpoint)
  return TokenStore.setItem(key, username, password)
}

export function setGenericCredential(
  endpoint: string,
  username: string,
  password: string
) {
  setGenericUsername(endpoint, username)
  return setGenericPassword(endpoint, username, password)
}
```
