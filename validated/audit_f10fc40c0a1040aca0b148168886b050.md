### Title
ProtoJSON alternate-key (camelCase/snake_case/JSON-name) duplicate-field aliasing bypasses duplicate-key rejection, producing implementation-divergent "last one wins" field resolution - ([File: src/google/protobuf/json/internal/parser.cc])

### Summary
The C++ ProtoJSON parser's duplicate-key detector (`RecordAsSeen` in `src/google/protobuf/json/internal/parser_traits.h`) tracks "have I seen this field before" by the resolved `FieldDescriptor` (field number / oneof index), but the *lexer/lookup layer* resolves a JSON member name to a field by trying multiple accepted spellings (original proto name, lowerCamelCase JSON name, and case-insensitive variants) before that check ever runs. When two JSON object members use *different* textual spellings that both resolve to the same underlying field (e.g. `"optional_nested_message"` and `"optionalNestedMessage"`), the legacy/default parsing mode treats this as two "occurrences" and applies "last one wins" merge semantics rather than rejecting the input as a duplicate key, even though canonical JSON requires unique member names and the two spellings are semantically the same key.

### Finding Description
The Undertow flaw is a class of bug where an ambiguous/duplicate-representation of the *same logical delimiter* (header terminator) is accepted by one implementation but not another, so two systems parsing the identical byte stream disagree on where a message starts/ends — enabling smuggling. The transferable invariant is: **a single canonical value must not have two different accepted textual encodings that resolve inconsistently across implementations/parsers.**

In protobuf's ProtoJSON, the analogous invariant is that a JSON object must have unique member names, and each field has exactly one canonical externally-visible spelling. However:

- `SeenState RecordAsSeen(Field f, Msg& msg)` in [1](#0-0)  and the proto3 variant [2](#0-1)  only reject a *second occurrence of the same resolved field* when `allow_legacy_nonconformant_behavior` is disabled: [3](#0-2) 
- The comment explicitly documents the gap: "Legacy nonconformant behavior only enforces duplicate key checking for fields within the same oneof, otherwise enforce duplicate keys for all fields" — meaning that outside oneofs, in the (default/legacy) mode, a name that maps to the same field via an *alternate spelling* is accepted and simply overwrites/merges over the previous value rather than being flagged as a duplicate key.
- This is confirmed as a known, acknowledged defect in other official bindings: the Python conformance test explicitly documents it as "non-spec and an oversight bug in the implementation" that "only catches keys that are exact matches and not alternate spellings that correspond to the same field" [4](#0-3) .
- Java's `JsonFormat` test suite shows the *opposite*, stricter behavior is actually expected/desired (rejecting `optionalNestedMessage` + `optional_nested_message` as duplicates) [5](#0-4) , and its own comment notes the underlying GSON tokenizer will otherwise silently keep the *last* value for exact-name duplicates [6](#0-5) .
- The conformance suite itself documents this exact case, `FieldNameDuplicateDifferentCasing1/2`, and marks it merely "RECOMMENDED" with the outcome allowed to be either "last-wins or parse failure" [7](#0-6) , and multiple language bindings (jruby, ruby) are listed as *failing* this recommended check, i.e., silently accepting the alias-duplicate rather than failing [8](#0-7) [9](#0-8) .

So the "missing check" is: the duplicate-detector operates post-resolution on field identity, but different implementations disagree on whether alternate-spelling duplicates should be treated as duplicate keys at all (RECOMMENDED, not REQUIRED, and inconsistently enforced across Python/Java/Ruby/JRuby/C++). This is exactly the shape of the Undertow bug: an ambiguous encoding of a single logical entity (one JSON "key") is accepted differently by different parser implementations of the same specification.

### Impact Explanation
If a system uses two different official Protobuf JSON parsers at different trust boundaries on the same wire payload (e.g., an API gateway written in one language validating/authorizing based on a field value, and a backend written in another language, or even the same language using two code paths — reflection-based `Message.Builder` and the newer `json_internal` implementation), an attacker can craft a JSON body containing both spellings of a security-relevant field (e.g., `"user_id"` and `"userId"` with different values). One implementation may keep the first occurrence's value (rejecting as duplicate, or accepting only the first per its resolution order) while another keeps the last occurrence's value, exactly mirroring the "front-end vs back-end disagree on what the message says" class of vulnerability from the Undertow advisory. This can enable authorization/routing bypass analogous to request smuggling: gateway sees value A, backend acts on value B (or vice versa).

This is a CWE-444-class ("Inconsistent Interpretation of HTTP Requests") analog applied to structured serialization rather than transport framing. Severity is bounded by the fact that exploitation requires the consuming application to run two divergent parser implementations/paths on the same payload and to make a security decision based on the divergent field — this is a realistic but not universally-applicable precondition, so I'd assess it as **Medium**, not High, unlike the original CVSS 3.1 AV:N/AC:H/S:C High rating for Undertow, because Protobuf itself has no network boundary and the "changed scope" only materializes if the deployment pattern includes multiple disagreeing parsers.

### Likelihood Explanation
Likelihood is limited by the documented "RECOMMENDED" (not "REQUIRED") status of the relevant conformance tests and the fact that the divergence is a *known, long-standing, acknowledged oversight* rather than a newly introduced regression — several bindings (Ruby, JRuby) are already flagged as intentionally non-conformant here without a tracked fix commitment. An attacker needs no special access: this is reachable through the standard public `JsonFormat.Parser` / `json_format.Parse` / `google::protobuf::json::MessageToJsonString`-style ProtoJSON parse APIs with a bounded, valid payload, satisfying the "ordinary client sending bounded ProtoJSON" threat model.

### Recommendation
- Make duplicate detection spelling-agnostic and consistent across the field-name resolution step: reject (or deterministically resolve) any JSON payload where two different JSON member names resolve to the same `FieldDescriptor`, not only exact string duplicates, in *all* language bindings and enforce this at `REQUIRED` conformance level rather than `RECOMMENDED`.
- Align `allow_legacy_nonconformant_behavior` default behavior across C++, Java, Python, Ruby, and JRuby so the same input always produces the same accept/reject/last-wins outcome, removing the possibility of divergent interpretation across implementations of the same specification.
- Track and close the acknowledged gaps documented in `conformance/failure_list_jruby_ffi.txt` and `conformance/failure_list_ruby.txt` for `FieldNameDuplicateDifferentCasing1/2`.

### Proof of Concept
Given a proto message with field `optional_nested_message` (JSON name `optionalNestedMessage`), the following payload is accepted by legacy-mode C++/Python/Ruby/JRuby parsers with "last one wins," while other conformant configurations reject it:
```json
{
  "optionalNestedMessage": {"a": 1},
  "optional_nested_message": {}
}
```
This is directly exercised by the conformance test case `FieldNameDuplicateDifferentCasing1` [10](#0-9) , whose expected behavior is explicitly ambiguous ("either last-wins or parse failure"), and which is recorded as failing (silently accepted, non-conformant) in the Ruby/JRuby failure lists [9](#0-8) . I was not able to execute this conformance test in this environment to observe live divergence between two specific implementations side-by-side; the evidence above is drawn from the conformance suite's documented expectations, the explicit "oversight bug" comment in the Python test file, and the differing enforcement code paths in `parser_traits.h`/`JsonFormat.java`, not from a runtime reproduction.

```text
  static SeenState RecordAsSeen(Field f, Msg& msg) {
    if (f->real_containing_oneof() != nullptr) {
      int oneof_index = f->real_containing_oneof()->index();
      bool oneof_inserted =
          msg.parsed_oneofs_indices_.insert(oneof_index).second;
      if (!oneof_inserted) {
        // Oneof takes precedent over Field in the case of "this is in a oneof
        // and the field is set"
        return SeenState::kOneofAlreadySeen;
      }
    }

    bool field_inserted = msg.parsed_fields_.insert(f->number()).second;
    if (!field_inserted) {
      return SeenState::kFieldAlreadySeen;
    }

    return SeenState::kFirstSeen;
  }
```
