### Title
Unauthenticated pre-validation SSRF via attacker-controlled DataLayer mirror URLs - (File: `chia/data_layer/data_layer.py`, `chia/data_layer/download_data.py`, `chia/data_layer/data_layer_wallet.py`)

### Summary
`DLNewMirror`/`create_new_mirror` lets any wallet publish an on-chain "mirror" URL list for an arbitrary `launcher_id` (store id) that it does not own. Any DataLayer node that subscribes to, owns, or auto-tracks that store id will later fetch those URLs via a real outbound HTTP GET, before the fetched content is validated against the wallet-advertised Merkle root.

### Finding Description
`DataLayerWallet.create_new_mirror()` [1](#0-0)  spends a standard coin encoding `memos=[[launcher_id, *urls]]` with no check that the caller owns or controls `launcher_id`. The wallet RPC entry point `dl_new_mirror` [2](#0-1)  and the CLI/service wrapper `DataLayer.add_mirror()` [3](#0-2)  forward this without ownership validation either.

Once confirmed on chain, any peer's `periodically_manage_data()` loop pulls mirrors for tracked/owned/subscribed stores and feeds their URLs directly into the local subscription server list via `update_subscriptions_from_wallet()` [4](#0-3) , only stripping trailing slashes — no scheme/host allow-listing or SSRF protection.

`fetch_and_validate()` then selects one of these attacker-controlled server URLs [5](#0-4)  and calls `insert_from_delta_file()` → `download_file()` [6](#0-5) , which for the no-plugin path calls `http_download()` [7](#0-6) . This issues a genuine `aiohttp.ClientSession().get(server_info.url + "/" + filename, ...)` request to the attacker-chosen host/port — this is the outbound network call that happens *before* the downloaded bytes are ever checked against the wallet-advertised root (`insert_into_data_store_from_file()` validation happens only after the HTTP fetch completes).

This mirrors the CloudStack bug class exactly: a network-facing action (HTTP request to a caller-supplied URL) is performed by server-side code before the URL/content is validated for legitimacy, enabling SSRF against the requesting node's internal network (e.g., localhost services, cloud metadata endpoints, internal admin ports) merely by having the node track/subscribe to a store an attacker has "mirrored."

### Impact Explanation
An unprivileged attacker who can submit a spend bundle (any wallet holder with a small fee) can force any DataLayer-participating node that later tracks/subscribes to the targeted store to make outbound HTTP requests to attacker-chosen internal or external endpoints. This enables SSRF: probing/reaching internal services, cloud metadata endpoints, or other victim-adjacent infrastructure that is otherwise unreachable from the public internet, without needing to compromise the victim's DataLayer server file protocol itself. Because ownership of the target `launcher_id` is not required, the attacker can target well-known/public DataLayer stores that many honest nodes subscribe to, maximizing blast radius.

### Likelihood Explanation
Likely reachable in normal operation: DataLayer is designed around third parties subscribing to/replicating others' stores (offers, public datasets), and nodes periodically re-poll on-chain mirrors for all tracked stores (`periodically_manage_data`). No special privilege beyond submitting a standard, low-fee coin spend is required to register the malicious mirror.

### Recommendation
Require that `create_new_mirror`/`dl_new_mirror` be restricted to store ids actually owned by the calling wallet (or explicitly document/opt-in for non-owned mirrors), and enforce URL/host validation (scheme allow-list, reject loopback/link-local/private ranges, or require operator opt-in) in `update_subscriptions_from_wallet()`/`http_download()` before any outbound request is issued to a chain-sourced mirror URL.

### Proof of Concept
1. Attacker wallet A (no special role) calls `dl_new_mirror` (`DLNewMirror(launcher_id=<victim's public store id>, amount=1, urls=["http://169.254.169.254/latest/meta-data/"], fee=...)`) and pushes the resulting spend bundle to the mempool; it confirms as a standard coin spend.
2. Any honest node B that already tracks/subscribes to that `launcher_id` (common for widely-used/public DataLayer stores) runs its normal `periodically_manage_data()` cycle, calls `update_subscriptions_from_wallet()` and picks up the new mirror URL with no validation.
3. On the next `fetch_and_validate()` cycle, node B's DataLayer service issues an outbound `aiohttp` GET to `http://169.254.169.254/latest/meta-data/<filename>` (or any other attacker-chosen internal address) via `http_download()`, before any content validation occurs.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
