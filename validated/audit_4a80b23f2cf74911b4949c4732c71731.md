### Title
Stale partial-diff line selection is preserved across background status refreshes, causing silent inclusion of unreviewed lines in a commit - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`updateChangedFiles` in `app/src/lib/stores/updates/changes-state.ts` matches working-directory files between the old and new git status purely by `WorkingDirectoryFileChange.id`, which is derived only from the file's path and its `AppFileStatusKind` (and `oldPath` for renames), not from its content. When a background status refresh happens with `clearPartialState: false` (the default path used by `_refreshRepository`/`_changeRepositorySection`), any partial line selection a user made in an older diff is carried over onto the "same" file (matched by that coarse ID) even though the underlying content/diff has changed. `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts` then only recomputes the *set of selectable line indices* from the new diff and keeps previously selected indices that still fall in that set — it explicitly does not verify that the selected lines still correspond to the same actual content, as the code comment acknowledges.

### Finding Description
`WorkingDirectoryFileChange`'s `id` is built purely from `status.kind` and `path` (plus `oldPath` for renames): [1](#0-0) 

`updateChangedFiles` uses this `id` to look up the "existing" file and reapply its old `selection` object to the newly-fetched file object, regardless of whether the diff content changed: [2](#0-1) 

This is invoked from `_loadStatus` with a `clearPartialState` flag that defaults to `false` for most non-commit refresh paths (background refresh, tab switching, watcher-triggered refresh): [3](#0-2) [4](#0-3) [5](#0-4) 

`clearPartialState: true` is only passed after an actual commit completes or when whitespace-diff settings change: [6](#0-5) [7](#0-6) 

After the coarse-grained selection is carried over, `updateChangesWorkingDirectoryDiff` recomputes only the *selectable line index set* from the new diff and reapplies it to the stale selection, explicitly by design not validating that a previously selected line index still maps to the same actual text: [8](#0-7) 

The broken invariant is analogous to the LT contract bug: a derived/cached value (`self.totalSupply` there, the per-line partial "included in commit" selection here) is not recalculated/invalidated before being used to produce the final artifact (minted tokens there, the staged/committed diff here). The guard that exists (`clearPartialState`) only fires on an explicit commit or setting change — it does not fire on ordinary background refreshes, tab switches, or repository re-scans triggered by external changes to the working tree (e.g., a git hook such as `post-checkout`/`post-merge`/`post-fetch`, or a smudge/clean filter contained in a cloned/fetched repository that rewrites tracked files after checkout). Since these hooks/filters execute with the attacker's chosen content but the same file path and same coarse status kind (e.g. still `Modified`), the file `id` is unchanged, so the old partial selection is preserved onto entirely different content.

### Impact Explanation
If the underlying file content changes between when the user makes a partial line selection and when they actually click "Commit" (e.g., due to a hook/filter execution from a repository the attacker controls, running silently on checkout/fetch/merge), the stale selection may still validate against the new diff's selectable-line index set (which is only checked for existence, not equivalence of content). This can cause Desktop to stage and commit lines the user never reviewed or intended to include — silently corrupting what the user commits/pushes, matching the "silent corruption of what the user commits or pushes" impact category. This does not require local/physical access or malware already on the host; it only requires the user to interact with a repository whose hooks/filters are attacker-controlled (a normal, expected Desktop workflow: clone/fetch and checkout).

### Likelihood Explanation
Medium. It requires: (1) the user to have an open partial selection on a file in the Changes view, (2) a background status refresh to occur (which happens routinely — tab switches, file-watcher-driven refreshes, periodic indicator refresh), and (3) the tracked file's content to change on disk in between via an attacker-controlled git hook or filter without the user re-reviewing the diff before committing. This is a plausible but not trivial sequence — it depends on timing relative to the user's commit action, which is why likelihood is medium rather than high.

### Recommendation
Include a content-derived component (e.g., a hash of the diff or file OID) in the matching key used by `updateChangedFiles`, or explicitly invalidate/clear any partial selection whenever the file's diff has structurally or textually changed since the selection was made — not just when line-count-based `selectableLines` shrinks. At minimum, `updateChangesWorkingDirectoryDiff` should compare something akin to the underlying blob OID/hash to confirm the diff content is unchanged before trusting previously-selected line indices, rather than only checking that the indices still fall within the new selectable-line set.

### Proof of Concept
1. Clone or fetch a malicious repository containing a `post-checkout` (or `post-merge`) hook that rewrites a tracked file's contents (same path, still shows as `Modified`) shortly after checkout completes.
2. In GitHub Desktop, open the file's diff in the Changes view and select only specific lines (partial selection) for staging.
3. Trigger a background status refresh without committing (e.g., switch to History tab and back, or wait for the periodic repository-indicator/file-watcher refresh) — this calls `_loadStatus`/`refreshChangesSection` with `clearPartialState: false`.
4. During this window, have the hook rewrite the file's content with different lines at similar/overlapping line offsets.
5. Because the file `id` (path + status kind) hasn't changed, `updateChangedFiles` reapplies the old partial `selection` object onto the new file entry; `updateChangesWorkingDirectoryDiff` only prunes indices that no longer exist in `selectableLines`, not indices whose underlying content changed.
6. Commit — the resulting commit silently includes attacker-influenced content that the user never actually reviewed/selected in the diff view they last saw.
