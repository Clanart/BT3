### Title
Panic in `GeneratorPromotion::complete` on incomplete peer proof set crashes the node - (File: crypto/dkg/promote/src/lib.rs)

### Summary

The external advisory (CWA-2024-008 / GHSA-vmqh-5232-v43r) describes a remotely triggerable panic in wasmvm that degrades block production. The analogous bug class in Serai is a panic reachable from untrusted network input: `GeneratorPromotion::complete` validates the count and bounds of the peer-supplied `proofs` map but never checks that it contains exactly the expected participant set, then unconditionally `unwrap()`s each lookup. A proof set that includes the local participant's own index (or duplicates exclusion of any single participant) satisfies both checks yet causes an out-of-bounds `HashMap` lookup panic.

### Finding Description

In `crypto/dkg/promote/src/lib.rs`, `complete` performs two validations on the caller-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

1. `proofs.len() == params.n() - 1` [1](#0-0) 
2. every key satisfies `u16::from(i) <= params.n()` [2](#0-1) 

It then iterates `1 ..= n`, skipping only `params.i()`, and does `proofs.get(&i).unwrap()` [3](#0-2) .

Neither check enforces that `params.i()` is absent from `proofs`. A malicious or misbehaving participant can supply a proof map of size `n - 1` containing `params.i()` and omitting some honest participant `j`. Both validations pass, but `proofs.get(&j)` returns `None` and the `unwrap()` panics.

This is reachable by an unprivileged party: `GeneratorProof`s are the per-participant broadcast messages of the promotion protocol, read from untrusted bytes via `GeneratorProof::read` (which calls `C::read_G` and `DLEqProof::read`) [4](#0-3)  and assembled by the integration layer into the `proofs` map fed to `complete`.

### Impact Explanation

The panic aborts the promotion protocol and, since Serai's DKG/signing code is executed inside consensus-critical machinery (FROST-based TSS for Serai's validator set), a panic propagating to the node runtime can crash or stall the coordinator — the same "panic reachable by untrusted input degrades block production" impact as CWA-2024-008. Any single participant can trigger it deterministically with a malformed proof set; no valid proof forgery or private key material is needed. The crate itself documents that this surface is expected to be panic-free for invalid protocol inputs: `AdditionalBlameMachine::new` in the sibling pedpop crate explicitly warns that invalid inputs "may cause everything from inaccurate blame to panics", indicating panics are treated as a defect class. [5](#0-4) 

### Likelihood Explanation

Triggering requires only that a participant send a syntactically valid `GeneratorProof` map whose key set is wrong — e.g., echoing the victim's own index back instead of a missing peer. The `GeneratorProof` bytes need not even verify, since the panic occurs at the `unwrap()` before `proof.proof.verify` is reached for the missing index [6](#0-5) . Detection is trivial for the attacker (send once, victim crashes/aborts). Severity: Medium — availability-only impact, but deterministically reachable by a single unprivileged counterparty.

### Recommendation

Replace the `proofs.get(&i).unwrap()` with a checked lookup returning `PromotionError::MissingParticipant`/`InvalidParticipant`, and explicitly reject `proofs` maps that contain `params.i()`:

```rust
// crypto/dkg/promote/src/lib.rs, in complete()
if proofs.contains_key(&params.i()) {
  Err(PromotionError::InvalidParticipant { n: params.n(), participant: params.i() })?;
}
let proof = proofs
  .get(&i)
  .ok_or(PromotionError::InvalidParticipant { n: params.n(), participant: i })?;
```

Alternatively, keep a single `Participant` keyed existence check per iteration so a missing entry produces a `PromotionError` rather than a panic.

### Proof of Concept

```rust
// n = 3, local participant i = 2.
// Attacker (participant 1) is responsible for relaying/collecting proofs.
let mut proofs: HashMap<Participant, GeneratorProof<C>> = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof);
// Includes the victim's own index, omits participant 3.
proofs.insert(Participant::new(2).unwrap(), attacker_proof_for_2);
// proofs.len() == 2 == n - 1: passes the count check.
// All keys <= 3: passes the bounds check.

promotion.complete(&proofs);
// Iteration i = 3: proofs.get(&Participant(3)) -> None -> panic on unwrap()
// at crypto/dkg/promote/src/lib.rs:146
```

The panic occurs before `DLEqProof::verify` is invoked for participant 3, so the injected proofs need not be valid — any well-formed `GeneratorProof` bytes (readable via `GeneratorProof::read`) suffice.
