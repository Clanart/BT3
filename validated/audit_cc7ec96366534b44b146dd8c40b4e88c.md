### Title
Escrow accounting can exceed actual custody balance in `IntentGatewayV2`, causing unrecoverable `withdraw()` reverts for legitimate solvers/users (bad-debt analog) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` maintains a single pooled ERC-20 balance per token address that backs the `_orders[commitment][token]` escrow accounting of *every* order using that token. On the direct (non-predispatch) escrow path, the contract credits `_orders[commitment][token]` with the full requested input amount without verifying that the actual token balance received matches (unlike the predispatch path, which correctly measures the balance delta). For any fee-on-transfer, rebasing, or otherwise non-1:1 ERC-20 token, this creates a persistent shortfall between the sum of all `_orders[...][token]` entries and the contract's real token balance for that address.

### Finding Description
`withdraw()` (both the `evm/tron/contracts/apps/IntentGatewayV2.sol` internal variant and the equivalent `_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol`) performs a hard, unconditional token transfer to the beneficiary and reverts entirely if that transfer fails: [3](#0-2) 

Because the token balance backing escrow is a **shared pool** across all commitments using that token (exactly the "LendingPool" pattern in the external report — one shared reserve serving many independent positions), an accounting drift caused by one order (fee-on-transfer input, or any deposit path that credits more escrow than was actually received) reduces the pool below what is owed to *other, unrelated* orders. When a later, entirely legitimate order attempts `withdraw()` (via `RedeemEscrow` after a cross-chain fill, or `RefundEscrow`/`onGetResponse` after cancellation), the ERC-20 `transfer` call can fail for lack of funds, and the whole function reverts — there is no fallback such as partial settlement or an alternate claim mechanism.

This mirrors the report's core broken invariant precisely: a shared custody pool serving multiple independent positions/orders can be driven into deficit by one flow, after which unrelated withdrawals revert with no graceful degradation path, and the only "fix" offered by the report (accept an alternate token/receipt instead of the underlying) is likewise absent here.

### Impact Explanation
Once the per-token pool is deficient, a solver who already delivered output tokens to the beneficiary on the destination chain (cross-chain fill) can be permanently unable to collect the escrowed input on the source chain when the `RedeemEscrow` message arrives — `onAccept` → `withdraw()` reverts. Since ISMP `onAccept` failure of an already-delivered incoming POST is not something the solver can retry with different parameters (the commitment, tokens, and beneficiary are fixed by the request body), the solver's due escrow can become permanently unrecoverable while the escrow accounting (`_orders[commitment][token]`) still shows the amount as owed. This is a fund-loss/fund-lock impact matching the bounty's "stealing or loss of funds" category, reachable purely through normal, unprivileged order placement and fill flow — no malicious relayer, prover, or admin action is required.

### Likelihood Explanation
Likelihood depends on whether fee-on-transfer/deflationary/rebasing ERC-20 tokens (or any other divergence between requested and received amount) are ever accepted as order inputs on the non-predispatch path. The predispatch path in the same contract explicitly defends against this class of token by measuring balance deltas, which is strong evidence that the protocol anticipates such tokens being used, yet the more common direct-escrow path lacks the same guard. Any order placed with such a token via the non-predispatch path introduces drift; repeated use compounds the shared-pool shortfall until an otherwise-legitimate `withdraw()` fails.

### Recommendation
Apply the same balance-delta measurement used in the predispatch branch to the direct escrow path: record `balanceBefore`, perform `safeTransferFrom`, then credit `_orders[commitment][token]` with `balanceAfter - balanceBefore` rather than the nominal requested amount. Additionally, consider making `withdraw()` resilient to a pool shortfall — e.g., transferring the minimum of the owed amount and available balance, and tracking any residual as a claimable deficit — so a shortfall in one order's accounting cannot block or permanently strand a different, correctly-accounted order's or fee.

### Proof of Concept
1. Deploy `IntentGatewayV2` with a fee-on-transfer ERC-20 `T` (e.g., 2% transfer fee) as a supported input asset, using the direct (non-predispatch) `placeOrder` path.
2. User A places order O1 with `inputs[0] = {token: T, amount: 1000}`. `safeTransferFrom` moves only 980 `T` into the gateway (2% fee burned), but `_orders[commitment_O1][T] += 1000` is recorded (line 457 in `evm/tron/contracts/apps/IntentGatewayV2.sol`). The gateway's actual `T` balance is now 980, but total accounted escrow is 1000 — a 20-token deficit.
3. User B places a normal order O2 with `inputs[0] = {token: T, amount: 500}` via a token that happens to not lose value in transfer (or another instance where actual receipt matches). Contract `T` balance is now 1480 (980+500), accounted escrow across both orders is 1500.
4. O2 gets filled cross-chain; the `RedeemEscrow` message triggers `withdraw()` for O2's 500 `T`. If O1's shortfall has already been drawn down by O1's own withdrawal (leaving the pool short), or once enough such orders accumulate, a later legitimate `withdraw()` call attempts to transfer more `T` than the contract actually holds, and the `token.call(... IERC20.transfer ...)` returns `success = false`, causing `revert TransferFailed()` (line 698) — the entire withdrawal reverts and the beneficiary's already-earned escrow becomes stuck, even though `_orders[commitment][token]` still shows the balance as owed and the beneficiary already fulfilled their side of the trade on the destination chain.
