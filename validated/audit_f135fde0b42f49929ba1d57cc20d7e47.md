## Title
Deep link `openRepo`/branch flow silently checks out an attacker-chosen branch on an already-open local repository without user confirmation - (File: `app/src/ui/dispatcher/dispatcher.ts`)

## Summary
The `x-github-client://openRepo/<url>?branch=<name>` deep link handler in `Dispatcher.openBranchNameFromUrl` resolves the target repository via `openOrCloneRepository(url)` and, once resolved, immediately fetches and performs `checkoutLocalBranch(repository, branchName)` with no intervening confirmation dialog that distinguishes this deep-link-triggered checkout from a manually initiated one.

## Finding Description
`openBranchNameFromUrl` is invoked from the deep link parsing pipeline (`x-github-client://openRepo/...`) with an attacker-controlled `url` and `branchName`. [1](#0-0) 

Inside this function:
1. `openOrCloneRepository(url)` is called to resolve a `Repository`. This resolution is driven by matching the remote URL of already-tracked repositories (via helpers such as `urlMatchesRemote`/`urlsMatch` in `app/src/lib/repository-matching.ts`), meaning any locally cloned repository whose remote matches the attacker-supplied URL string can be selected — the attacker does not need the user to have cloned *their* exact malicious repo, just one whose remote happens to structurally match (hostname/owner/name). [2](#0-1) 
2. The code refreshes and fetches the repository, then unconditionally calls `this.checkoutLocalBranch(repository, branchName)`. [3](#0-2) 

There is no visible consent/confirmation UI step gating this checkout inside `openBranchNameFromUrl` itself — unlike the sibling `filepath`-handling branch above it, which at least validates the path is not absolute and stays within the repo root before calling `shell.showItemInFolder`. [4](#0-3) 

## Impact Explanation
If confirmed end-to-end, this would let a webpage the user merely visits (via a clicked or auto-triggered custom-protocol link) force GitHub Desktop to switch the working tree of an already-open, unrelated repository to an attacker-named branch, without any dialog distinguishing this from a deliberate user checkout. Combined with dirty-working-directory handling elsewhere in the checkout flow, this could silently change what the user believes they are committing/pushing.

## Likelihood Explanation
I was not able to fully verify this within the available tool budget. Specifically, I could not inspect:
- The implementation of `checkoutLocalBranch` itself (only its call site was found) — it's possible this internal method surfaces a confirmation dialog (e.g., for uncommitted changes, stashing, or an explicit "Switch branch?" prompt) before performing the actual `git checkout`.
- The implementation of `openOrCloneRepository` — it's possible it already shows a "Clone in Desktop" / "open repository" confirmation dialog to the user before returning a `Repository`, which would count as the "fresh explicit consent step" required.
- The deep-link entry point (`app/src/main-process` / `parse-app-url`) that dispatches to `openBranchNameFromUrl`, to confirm whether any upstream URL scheme/host validation occurs before reaching this function.

Because these gating checks (if they exist) live outside the code I was able to retrieve, I cannot definitively state whether "existing checks already stop it" per the review path's step 4. The code shown is consistent with the reported behavior (no confirmation *within* `openBranchNameFromUrl`), but I cannot rule out a confirmation dialog rendered earlier in `openOrCloneRepository` or later inside `checkoutLocalBranch`.

## Recommendation
Given the uncertainty, I recommend a background agent:
1. Read the full implementations of `Dispatcher.checkoutLocalBranch` and `Dispatcher.openOrCloneRepository` in `app/src/ui/dispatcher/dispatcher.ts`, and the deep-link entry point in `app/src/main-process` / `app/src/lib/parse-app-url.ts`.
2. Confirm whether any of these paths present a user-facing confirmation dialog before checkout, and whether the deep link's repository resolution can match a repo with only a coincidentally-matching remote (not the actual attacker-owned repo).
3. If no confirmation exists, add an explicit consent dialog before `checkoutLocalBranch` is invoked from `openBranchNameFromUrl`, showing the target repository path and branch name, and requiring the user to confirm — especially when there are uncommitted/unpushed local changes.

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
