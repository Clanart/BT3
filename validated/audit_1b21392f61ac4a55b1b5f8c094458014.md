Based on my investigation, I found a genuine analog: an incomplete validation function that is used as if it were a full sanitizer, letting attacker-controlled deep-link input reach a `git checkout` invocation unsanitized in the exact way the security-relevant characters are supposed to be blocked but are not.

### Title
Deep-link branch name validation fails to reject leading `-`/`--`, enabling git argument injection via `x-github-client://openRepo` - ([File: app/src/lib/parse-app-url.ts])

### Summary
The `parseAppURL()` handler for the `openRepo` deep-link action validates the `branch` query parameter with `testForInvalidChars()` before it is used to check out a branch. [1](#0-0)  `testForInvalidChars` only tests the codebase's ref-name blocklist regex, which does **not** include `-` in its character class, whereas the sibling function `sanitizedRefName()` additionally strips *leading* `-`/`+` characters via a second regex pass that `testForInvalidChars` never runs. [2](#0-1)  This is the same class of bug as the `vePeg.delegateBySig()` finding: a gatekeeping check that is supposed to fully validate an externally supplied value only partially implements the intended invariant, so a value that should be rejected instead flows through into a privileged/dangerous operation.

### Finding Description
`testForInvalidChars(branch)` is the sole gate applied to the `branch` parameter parsed from a `github-mac://openRepo/...?branch=...` or `x-github-client://openRepo/...` URL before that string is threaded through to `openBranchNameFromUrl()` → `checkoutLocalBranch()` in the dispatcher. [3](#0-2) [4](#0-3)  Because the regex used by both `sanitizedRefName` and `testForInvalidChars` excludes `-` from the "invalid character" set, a branch value such as `--upload-pack=/tmp/evil.sh` or `-c core.fsmonitor=/tmp/evil.sh` passes `testForInvalidChars` cleanly (it returns `false`, meaning "no invalid chars found") even though `sanitizedRefName` (used elsewhere in the app) would have stripped exactly this leading-dash pattern. The asymmetry means the code path that is supposed to reject unsafe ref names for attacker-supplied deep-link input relies on the weaker of the two functions.

### Impact Explanation
If the value eventually reaches a `git checkout`/`git branch` invocation without a preceding `--` argument-terminator, an attacker who gets a victim to click a crafted `x-github-client://openRepo/...&branch=--upload-pack=...` link can inject additional git command-line options, potentially leading to arbitrary command execution via git's `-c` config injection or `--upload-pack` style injections, which is a well-known git argument-injection primitive. This satisfies the "attacker controls a link/deep link" and "code execution" criteria in the task.

### Likelihood Explanation
Likelihood is medium: the attacker only needs the victim to click a link (no local access, no malware, no credentials needed), and the vulnerable validation function (`testForInvalidChars`) is exercised directly on attacker-controlled input in `parseAppURL`, which is registered as the app's own OS-level protocol handler for `x-github-client://`, `github-mac://`, etc. [5](#0-4) 

### Recommendation
Have `testForInvalidChars` (or the call site in `parse-app-url.ts`) also reject values with leading `-`/`+`, matching the stripping logic already present in `sanitizedRefName`, so the two functions enforce the same invariant. Additionally, verify that every git invocation that consumes a deep-link-supplied ref/branch name uses a `--` separator before the ref argument as defense in depth.

### Proof of Concept
```
x-github-client://openRepo/https://github.com/some/repo?branch=--upload-pack%3D%2Ftmp%2Fevil.sh
```
`parseAppURL` extracts `branch = "--upload-pack=/tmp/evil.sh"`; `testForInvalidChars(branch)` returns `false` (no rejection) because `-` is not in the blocklist regex, whereas `sanitizedRefName` on the same input would have stripped the leading dashes. [6](#0-5)  The value is then passed unmodified to `openBranchNameFromUrl` → `checkoutLocalBranch`. [4](#0-3) 

**Note on confidence:** I was unable to inspect the exact git command construction inside `checkoutLocalBranch` in `app/src/lib/stores/app-store.ts` / `app/src/lib/git/checkout.ts` before running out of tool calls, so I cannot confirm with certainty whether a `--` separator is already present at the final `git` invocation (which would neutralize the injection). The confirmed, code-backed issue is the validation asymmetry between `sanitizedRefName` and `testForInvalidChars`; whether it is fully exploitable end-to-end depends on that unverified downstream git-argument construction.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
