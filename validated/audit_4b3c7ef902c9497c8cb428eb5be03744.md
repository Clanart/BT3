Based on the investigation, I found a solid analog: a documented safety invariant that's enforced only on one platform.

### Title
`UNSAFE_openDirectory` invariant against opening repository-derived paths is not enforced on Windows/Linux, enabling submodule-path code execution - (File: app/src/ui/main-process-proxy.ts)

### Summary
`app/src/main-process/shell.ts` documents an explicit invariant on `UNSAFE_openDirectory`: "This method should never be used to open user-provided or derived paths. Its sole use is to open directories that we know to be safe, no verification is performed to ensure that the provided path isn't actually an executable." [1](#0-0)  That invariant is documentation-only — like the `batchSettlement` NatSpec comment in the seed report — and `showFolderContents` in `app/src/ui/main-process-proxy.ts` violates it for non-macOS platforms by calling `UNSAFE_openDirectory(path)` directly on any repository-derived directory path without any bundle/executable check. [2](#0-1) 

### Finding Description
`showFolderContents(path)` is a shared helper reachable from renderer UI flows that let a user "open" a directory associated with repository content (e.g. a submodule's on-disk folder, whose path/location is derived from `.gitmodules` entries that ship inside a cloned/fetched, attacker-controlled repository). On macOS, before calling the unsafe API, the code performs an `isApplicationBundle` check and redirects to `_showItemInFolder` if the path looks like an app bundle: [3](#0-2) . But for Windows and Linux, the code takes a different branch that skips this check entirely:

```
if (!__DARWIN__) {
    UNSAFE_openDirectory(path)
    return
}
``` [2](#0-1) 

This directly contradicts the CAUTION comment on `UNSAFE_openDirectory` itself, which states it must only be used on paths "we know to be safe" and that "no verification is performed to ensure that the provided path isn't actually an executable." [1](#0-0)  The only Windows-specific mitigation inside `UNSAFE_openDirectory` is appending a trailing separator to avoid the `foo` vs `foo.exe` collision [4](#0-3) , which does not address the broader class of unsafe paths (e.g., paths ending in `.exe`, `.bat`, `.lnk`, `.scf`, or a `.appref-ms` masquerading with a trailing separator quirk, or a directory containing a `desktop.ini`/`.lnk`-based shell command trick). The IPC channel itself accepts an arbitrary string with zero validation on the main-process side: `ipcMain.on('unsafe-open-directory', async (_, path) => UNSAFE_openDirectory(path))` [5](#0-4) .

### Impact Explanation
Because the invariant "only call this with known-safe paths" is not enforced by any storage flag, allow-list, or type distinction — exactly the same class of defect as the seed report — a maliciously crafted repository (via a submodule path or other repository-controlled folder reference) that reaches `showFolderContents` on Windows/Linux bypasses the one safety check that exists (the bundle check), which was only wired up for `__DARWIN__`. This can result in file-shell interactions with attacker-influenced folder names/content outside expected bounds, matching the "attacker controls a cloned/fetched repository" and "file write/read or code execution" impact categories.

### Likelihood Explanation
Low-to-medium: it requires a renderer code path that feeds a repository/submodule-derived path into `showFolderContents` without the caller itself validating it's a benign directory, and it requires Windows or Linux (macOS is guarded). I was not able to fully enumerate every renderer caller of `showFolderContents` within the tool-call budget available, so it's not confirmed with certainty that a fully attacker-controlled path reaches this function today — this needs further tracing of all call sites of `showFolderContents`/`UNSAFE_openDirectory` exposed through submodule/context-menu UI actions.

### Recommendation
Apply the same executable/bundle-style validation on Windows/Linux that already exists for macOS (e.g., reject or redirect to `_showItemInFolder` for reparse points, `.exe`/`.bat`/`.cmd`/`.lnk`/`.scf` suffixes, or paths containing shell-executable content), or better, replace the comment-based invariant with an explicit allow-list/flag parameter threaded from trusted call sites only, so `UNSAFE_openDirectory` cannot be reached with a repository-derived path on any platform.

### Proof of Concept
Not independently verified end-to-end due to incomplete enumeration of all renderer callers of `showFolderContents` within the available tool budget; a full PoC would require confirming a UI action (e.g., "Show submodule folder" from a submodule diff view) that passes a `.gitmodules`-controlled path straight into `showFolderContents` on Windows/Linux without prior sanitization, then crafting a submodule path pointing at a directory/file the platform shell would treat unsafely.
