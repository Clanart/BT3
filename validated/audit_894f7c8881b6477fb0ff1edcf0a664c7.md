### Title
IPC trust check validates the WebContents container, not the actual frame origin — analogous to checking `msg.sender` instead of `from` - ([File: app/src/main-process/ipc-main.ts])

### Summary
The External report's core lesson is: authorization/whitelist checks that validate the wrong identity (`msg.sender`, the immediate caller) instead of the real party of interest (`from`, the true origin of the action) can be silently bypassed when an intermediary/container is treated as fully trusted. GitHub Desktop's IPC trust gate has the same structural flaw: it authorizes IPC messages based on the identity of the top-level `WebContents` container rather than the actual frame/origin that dispatched the message.

### Finding Description
Every privileged IPC call from the renderer to the main process passes through `safeListener`, which authorizes the call solely via `isTrustedIPCSender(event.sender)`: [1](#0-0) 

`isTrustedIPCSender` only checks whether `event.sender.id` (the `WebContents` id of the whole window) is in `trustedSenders`: [2](#0-1) 

`addTrustedIPCSender` is called once per `BrowserWindow`, at window creation, in `app-window.ts` and `crash-window.ts`: [3](#0-2) 

The main window is created with `nodeIntegration: true` and `contextIsolation: false`: [4](#0-3) 

`event.sender` identifies the entire `WebContents` (the window/container), not the specific frame (`event.senderFrame`) that actually invoked `ipcRenderer.send`/`invoke`. This is the same broken invariant as the report: the check is performed on the "operator"/container (`msg.sender`) rather than on the true originating party (`from`/`senderFrame`). Any content capable of running script inside that same `WebContents` — for example an `<iframe>` used to render remote or repository-derived content such as `sandboxed-markdown.tsx` (which the app uses to render README/commit/PR body markdown, i.e. attacker-influenced GitHub API objects) — would satisfy `isTrustedIPCSender` because it shares the same `WebContents` id as the trusted top frame, even though its content originates from an untrusted source (a cloned/fetched repo or GitHub API response).

I was not able to fully verify, within the remaining tool budget, whether the markdown iframe in `sandboxed-markdown.tsx` is configured with the `sandbox` attribute and script execution disabled, which would be the actual mitigating control preventing this from being exploitable. That file's rendering/sandbox configuration should be reviewed directly, since the index only surfaced a single match for the `iframe` keyword.

### Impact Explanation
If the markdown/rendering iframe (or any future iframe/embedded content loaded inside the main `BrowserWindow`) can execute script — whether through a sandbox-escape, a CSP misconfiguration, or a future feature that loads less-trusted HTML into the same window — that content would be treated as a fully trusted IPC sender for every privileged channel registered via `ipcMain.on`/`handle`, including `open-external`, `move-to-trash`, `get-app-path`, `save-dialog`, and other filesystem/process-affecting operations. This mirrors the report's impact: an untrusted party operating "through" a trusted container bypasses the intended trust boundary entirely.

### Likelihood Explanation
Likelihood depends entirely on whether any content rendered inside the main window's frames can execute arbitrary script — which I could not fully confirm from the available index (the sandboxed markdown component name strongly suggests script execution is deliberately disabled for that specific case). Absent a concrete script-execution primitive inside a non-top-level frame of the main `BrowserWindow`, this is a defense-in-depth gap rather than a directly exploitable path today. I flag it as the closest structural analog to the reported bug class rather than a confirmed high-likelihood exploit.

### Recommendation
Validate `event.senderFrame` (its URL/origin) in `isTrustedIPCSender`/`safeListener`, not just `event.sender` (the container `WebContents`), so that IPC trust is anchored to the actual origin of the calling frame rather than the window that happens to host it — directly mirroring the report's recommendation to check `from` instead of `msg.sender`.

### Proof of Concept
Not independently reproducible from the indexed code alone: exploitation would require confirming that some frame other than the top-level trusted renderer frame inside the main `BrowserWindow` (e.g., the markdown-rendering iframe) can execute arbitrary JavaScript. I could not verify the sandbox configuration of `app/src/ui/lib/sandboxed-markdown.tsx` within the available tool budget. A Devin session with full file access should inspect that component's `iframe` `sandbox`/CSP settings to determine whether this is exploitable in practice or already mitigated.

```typescript
function safeListener<E extends IpcMainEvent | IpcMainInvokeEvent, R>(
  listener: (event: E, ...a: any) => R
```

```typescript
import { WebContents } from 'electron'

// WebContents id of trusted senders of IPC messages. This is used to verify
// that only IPC messages sent from trusted senders are handled, as recommended
// by the Electron security documentation:
// https://github.com/electron/electron/blob/main/docs/tutorial/security.md#17-validate-the-sender-of-all-ipc-messages
const trustedSenders = new Set<number>()

/** Adds a WebContents instance to the set of trusted IPC senders. */
export const addTrustedIPCSender = (wc: WebContents) => {
  trustedSenders.add(wc.id)
  wc.on('destroyed', () => trustedSenders.delete(wc.id))
}

/** Returns true if the given WebContents is a trusted sender of IPC messages. */
export const isTrustedIPCSender = (wc: WebContents) => trustedSenders.has(wc.id)


```
