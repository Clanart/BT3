### Title
ThresholdKeys deserialization accepts attacker-consistent state without verifying `secret_share` binds to the serialized verification shares or that shares lie on a common polynomial - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reconstructs full threshold key state — `t`, `n`, `i`, the interpolation coefficients, the secret share, and all `n` verification shares — purely from untrusted bytes, then calls `ThresholdKeys::new` which derives `group_key` as `Σ verification_shares[i] * interpolation_factor(i)` over participants `1..=t` (crypto/dkg/src/lib.rs:376-378). No check verifies that the deserialized `secret_share` actually corresponds to `verification_shares[i]` (i.e. `C::generator() * secret_share == verification_shares[&params.i()]`), nor that the `n` verification shares are consistent with one another / with `group_key`. This is the deserialization-of-untrusted-data class mapped onto Serai: the blob is trusted as self-consistent, but nothing enforces it.

### Finding Description
- `read` parses `t`, `n`, `i` (lines 591-602), an interpolation tag plus `n` scalars for `Constant` (lines 604-616), a `secret_share` scalar (line 618), and `n` group elements via `Ciphersuite::read_G` (lines 620-623), which enforces canonical encodings but nothing else — `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101) even accepts the identity point, unlike `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) which rejects it.
- `ThresholdKeys::new` (lines 349-391) only checks the count of verification shares and that indexes are `<= n`, then computes `group_key` from shares `1..=t`. `secret_share` is stored verbatim and never compared against its claimed verification share, and shares `t+1..=n` are never checked to lie on the polynomial implied by the first `t` shares.
- By contrast, every honest constructor binds the share: `dealer::key_gen` inserts `C::generator() * secret_share` per participant (crypto/dkg/dealer/src/lib.rs:53), PedPoP verifies shares against commitments via `share_verification_statements`/`BatchVerifier` (crypto/dkg/pedpop/src/lib.rs:430-499), and MuSig recomputes `verification_shares` from the public keys (crypto/dkg/musig/src/lib.rs:142-150). The deserialize path bypasses all of these bindings.
- `view()` (lines 463-533) interpolates the deserialized `secret_share` and adds `offset` to `included[0]`'s secret share and verification share — all arithmetic proceeds on the forged state without further validation.

### Impact Explanation
An attacker who can cause a node to deserialize a crafted `ThresholdKeys` blob (e.g., corrupted/unsigned stored key material or any channel that feeds `ThresholdKeys::read`) obtains a key object where:
- The `secret_share` doesn't match `verification_shares[i]`: FROST signing then emits a share that fails `ThresholdView::verification_share` checking, causing the honest node to be blamed/faulted (liveness / unfair-blame), or produces an aggregate that doesn't verify.
- More severely, all `n` verification shares can be chosen on a polynomial of the attacker's choice, making `group_key` a key whose discrete log is known only to the attacker, while the local `secret_share` is junk. If this `group_key` is then registered with the scanner/wallet (`Scanner::new`/`register_offset`, networks/bitcoin/src/wallet/mod.rs:158-196), deposits to its P2TR outputs are either unspendable by the group (inconsistent state) or spendable by the attacker (attacker-consistent state) — funds reported received that are not controlled by the validator set. Additionally, identity verification shares are accepted, letting a blob encode `group_key` as a partial or complete identity/trivial combination.

### Likelihood Explanation
`ThresholdKeys` are persisted via `serialize`/`read` (used by `GeneratedKeysDb::read_keys`/`save_keys` in processor) and the format is explicitly documented as public API for reloading keys. Any path that loads keys from storage an attacker can influence, or any integrator that accepts serialized keys from peers rather than re-deriving them through the DKG, is exposed. The required bytes are just `4 + ID + 6 + 1 (+ n·scalar) + scalar + n·point` — trivially constructible offline. Exploitation requires write access to a key-loading channel, hence Medium rather than Critical.

### Recommendation
In `ThresholdKeys::read` (or `ThresholdKeys::new`), after constructing the params:
1. Assert `C::generator() * secret_share == verification_shares[&params.i()]` — reject blobs whose secret share doesn't match its own verification share.
2. For `Interpolation::Lagrange`, verify the shares are mutually consistent (e.g., that `group_key` recomputed from different `t`-subsets of verification shares agrees, or commit to the polynomial). At minimum, reject identity verification shares (`res.is_identity()` check as `Curve::read_G` does).
3. Consider authenticating stored key material (MAC/signature over the serialization) so deserialization is never fed unauthenticated bytes.

### Proof of Concept
```rust
// crypto/dkg: forge a ThresholdKeys blob for Secp256k1/Ristretto `C`
// where group_key is attacker-controlled and secret_share is inconsistent.
let attacker_scalar = C::F::random(&mut OsRng);          // attacker knows dlog
let attacker_point  = C::generator() * attacker_scalar;

let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(1u16.to_le_bytes());                          // t = 1
blob.extend(1u16.to_le_bytes());                          // n = 1
blob.extend(1u16.to_le_bytes());                          // i = 1
blob.push(1);                                             // Interpolation::Lagrange
blob.extend(C::F::random(&mut OsRng).to_repr().as_ref()); // arbitrary secret_share
blob.extend(attacker_point.to_bytes().as_ref());          // verification_share[1]

// Succeeds: read() -> ThresholdKeys::new() sets group_key = attacker_point
// despite secret_share * G != attacker_point.
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
assert_eq!(keys.group_key(), attacker_point);             // attacker knows the key
assert_ne!(C::generator() * *keys.original_secret_share(),
           keys.original_verification_share(Participant::new(1).unwrap()));
```
With `t = n = 1` this is immediate; for `t > 1` the attacker picks the first `t` verification shares on a polynomial they interpolate, and arbitrary (or identity) shares for `t+1..=n`, since no cross-share consistency is enforced. Signing with these keys yields shares inconsistent with `verification_shares`, causing blame/abort, while `group_key` — usable as a deposit address — is fully attacker-determined.
