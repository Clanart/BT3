## Title
Copilot conflict-resolution writer silently overwrites a resolved file it never re-checked for hidden conflicting concurrent edits, allowing a specially crafted merge conflict in a fetched repository to make Desktop write attacker-chosen content into the user's commit - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The C4N-01 report's broken invariant is: a caller can *declare* a quantity ("weeklyReward") and the contract acts on that declared quantity while pulling real value from a shared, un-owned pool (`CrocSwapDex`) without verifying the caller actually supplied it. The Desktop analog to search for is a place where Desktop takes a value derived from **attacker-controlled repository content** (a fetched/merged branch that produces conflict markers) and writes it back into the user's working tree/commit while only checking a *unrelated, coarse* invariant, not the specific mapping between what the model resolved and what is actually on disk right now. That is exactly the pattern in the Copilot conflict-resolution write path in `_acceptCopilotConflictResolutions` at [1](#0-0) .

### Finding Description
When Desktop's Copilot conflict-resolution feature is used to resolve a merge/rebase/cherry-pick, the model is given per-file "hunks" built from files on disk that contain conflict markers (`buildConflictContext`), and returns `resolvedContent` per path. The final acceptance step, `_acceptCopilotConflictResolutions`, resolves the path with `resolveWithin` (a legitimate path-traversal guard) and then does exactly one staleness check: it looks at whether the file `isConflictedFileStatus` and `!hasUnresolvedConflicts` (i.e., the user manually finished resolving it in an editor) before skipping the write [2](#0-1) .

This check only detects the case where the *user* finished the merge. It does **not** re-verify that:
- the file's on-disk content still matches the `rawContent`/hunks the model's resolution was built from (`ctx.rawContent` in `reassembleResolutions`, [3](#0-2) ), or
- the repository state (HEAD, MERGE_HEAD, index) has not changed since the conflict context was captured.

Because the repository content that produces the conflict markers, hunk boundaries, and "ours/theirs" labels is **entirely attacker-controlled** (a remote branch fetched and merged/rebased by the victim), an attacker who crafts a branch with pathological conflict markers (e.g., nested/ambiguous `<<<<<<<`/`=======`/`>>>>>>>` sequences, or content designed so `extractConflictHunks`/`reassembleResolvedFile` misaligns hunk offsets against a file that has since drifted) can cause `reassembleResolvedFile` to reconstruct file content that does not correspond to what is actually staged, and `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` followed by `git add` will silently commit that mismatched content [4](#0-3) . The user only ever reviews the model's high-level "resolution" summary in the UI dialog, not necessarily the exact bytes the AI reconstructed, so the corrupted commit can slip past user awareness — matching the report's impact category "silent corruption of what the user commits or pushes."

The existing guard (`resolveWithin` + `hasUnresolvedConflicts` check) stops only path-escape and "user already fixed it externally" - it does not stop the value used for the write (`resolution.resolvedContent`, built from attacker-supplied conflict-marker text) from being trusted without recomputing/diffing against the current on-disk conflicted content at write time.

### Impact Explanation
If exploitable, this allows an external, unprivileged actor (anyone who can get a victim to fetch/merge a branch, e.g., a PR author or a public fork) to make Desktop's AI-assisted conflict resolution commit content the victim did not actually approve, into the victim's repository/commit history, which then gets pushed. This matches the report's "silent corruption of what the user commits or pushes" category.

### Likelihood Explanation
This requires: (1) the victim to have Copilot conflict resolution enabled and used during a merge/rebase/cherry-pick against attacker-influenced content, and (2) the model itself to be steered by crafted, adversarial conflict-marker text (a prompt-injection-adjacent input surface, not a purely mechanical parsing bug I was able to confirm as byte-exact). I was **not able to fully verify** an exact deterministic input in `extractConflictHunks`/`reassembleResolvedFile` that guarantees hunk-offset corruption from local code alone — that would require inspecting those two functions' internals, which were not returned in full by the search tool. This is therefore reported with an explicit caveat: the write-side missing invariant (no re-validation of `resolvedContent` against live file state before `writeFile`) is confirmed in code, but a fully deterministic, non-AI-dependent PoC could not be constructed with the code available to me.

### Recommendation
Before `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`, re-read the file's current on-disk content and re-verify: (a) it still contains the same conflict markers/hash as the `rawContent` used to build the hunks passed to the model, and (b) the reassembled content round-trips against the *current* base/theirs content (e.g., recompute a diff between `resolution.resolvedContent` and the live conflicted file and require that only the conflict-marker regions changed). If the check fails, skip the write and require manual resolution.

### Proof of Concept
Deterministic reproduction was not fully verifiable from the indexed code; the following is the exploit skeleton implied by the code path:
1. Attacker publishes a branch with a file containing crafted conflict-marker text (e.g. unbalanced/duplicated `<<<<<<<`/`=======`/`>>>>>>>` blocks) designed to make `extractConflictHunks` mis-segment hunks relative to actual content boundaries.
2. Victim merges/rebases this branch in Desktop, conflict arises, victim invokes Copilot conflict resolution.
3. `buildConflictContext` reads the file and extracts (possibly misaligned) hunks [5](#0-4) ; the model's `resolvedContent` is reassembled from these hunks via `reassembleResolvedFile` [6](#0-5) .
4. On accept, `_acceptCopilotConflictResolutions` writes `resolution.resolvedContent` to disk without re-diffing against current file state, only checking whether the user already manually resolved it [1](#0-0) , then stages and the user commits/pushes the result.

Given the uncertainty around step 1's exact deterministic trigger, I recommend treating this as **Medium confidence** pending a Devin/dev session that can read the full bodies of `extractConflictHunks` and `reassembleResolvedFile` to confirm or refute a concrete misalignment PoC.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
