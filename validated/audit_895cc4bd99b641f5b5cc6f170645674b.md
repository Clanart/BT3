## Analysis

The claimed binding is: **for all withdrawal indices `i ≠ j`, `(withdrawal_utxo_txid_i, withdrawal_utxo_vout_i) ≠ (withdrawal_utxo_txid_j, withdrawal_utxo_vout_j)`** — i.e., one physical Bitcoin UTXO backs exactly one `idx`'s payout.

Tracing the code confirms this binding is **not enforced anywhere in this repo**:

- The `withdrawals` table only has `idx int primary key`; `withdrawal_utxo_txid`/`withdrawal_utxo_vout` carry no uniqueness constraint. [1](#0-0) 
- `Database::update_withdrawal_utxo_from_citrea_withdrawal` blindly writes whatever `(txid, vout)` Citrea reports for `idx`, with no check against existing rows. [2](#0-1) 
- `collect_withdrawal_utxos` pulls the raw, caller-supplied `(txId, outputId)` bytes straight from the Citrea Bridge contract's `withdrawalUTXOs` mapping — Citrea has no L1 visibility and cannot itself detect that a UTXO was already used by an earlier withdrawal id. [3](#0-2) 
- `Database::get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` purely by `(txid, vout)` equality; if two rows share that pair, **both** get matched to the same on-chain spend. [4](#0-3) 
- `update_finalized_payouts` then writes the same `payout_txid`/`operator_xonly_pk`/`block_hash` into every matched `idx` row via `update_payout_txs_and_payer_operator_xonly_pk`. [5](#0-4) 

Critically, the zk bridge circuit doesn't independently guard against this either: it only checks that the *presented* payout transaction's input at `payout_input_index` matches the withdrawal outpoint recorded in the storage proof for that specific `deposit_idx`, and that the deposit's own `move_txid` is embedded in `deposit_constant`. It never checks that this same physical payout transaction hasn't already been used to justify reimbursement of a *different* deposit. [6](#0-5) [7](#0-6) 

**Exploit flow:** An attacker deposits and requests a withdrawal for their own `idx2`, but instead of pointing to a fresh output they control, they call Citrea's `withdraw(txid, vout)` with the exact `(txid, vout)` of a UTXO that already backs an older withdrawal `idx1` (whose real payout will or has already occur(ed)). Once Clementine syncs `idx2`'s registration and the block containing `idx1`'s real payout tx is (re)processed, the join in `get_payout_txs_for_withdrawal_utxos` attributes `idx1`'s genuine payout transaction to `idx2` as well. An operator eligible for `idx2`'s deposit can then run the normal `send_asserts`/kickoff reimbursement flow (`get_payout_info_from_move_txid` → SPV + storage proof of `idx1`'s real, already-confirmed payout tx) and get reimbursed for `idx2` without ever funding a distinct payout — the actual withdrawer for `idx2` never receives BTC even though their L2 funds were consumed. [8](#0-7) 

The existing guards (`Verifier::sign_optimistic_payout`'s spent-UTXO check, `Operator::withdraw`'s `get_txout_from_outpoint`) only prevent an operator from *cooperatively signing a new* payout for an already-spent outpoint — they don't stop the DB from misattributing an *already-existing* spend to a second `idx`, nor does the circuit reject re-use of one payout tx across two deposits' proofs.

### Title
Missing uniqueness on `withdrawal_utxo_txid`/`vout` across withdrawal indices lets one payout satisfy two withdrawals - (File: core/src/database/verifier.rs)

### Summary
The `withdrawals` table's primary key is `idx` alone, with no uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, and `Database::get_payout_txs_for_withdrawal_utxos` matches spent UTXOs to withdrawal rows purely by that pair. An attacker who registers the same already-used Bitcoin outpoint under a second withdrawal `idx` on Citrea causes Clementine to attribute one real payout transaction to two distinct withdrawals, and the bridge circuit performs no cross-deposit check to prevent an operator from using that misattribution to claim reimbursement it never funded.

### Finding Description
The broken binding is: `(withdrawal_utxo_txid_i, withdrawal_utxo_vout_i) ≠ (withdrawal_utxo_txid_j, withdrawal_utxo_vout_j)` for `i ≠ j`. Nothing enforces this: schema (`core/src/database/schema.sql:269-281`), the writer `Database::update_withdrawal_utxo_from_citrea_withdrawal` (`core/src/database/verifier.rs:108-135`), and the reader `Database::get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) all treat `idx` as the only key, joining spends to withdrawal rows solely by `(txid, vout)` equality. When a second `idx` is registered on Citrea pointing at an outpoint that already backs another withdrawal's real (or eventual) payout, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) writes the same `payout_txid`/`operator_xonly_pk`/`block_hash` into both rows. The bridge circuit's checks (`circuits-lib/src/bridge_circuit/mod.rs:182-229`, `storage_proof.rs:44-133`) only verify that the presented payout tx's input matches the withdrawal outpoint stored at the *specific* `deposit_idx`'s storage slot — since the attacker made that slot's value equal to the recycled, already-spent outpoint, the assertions pass. No component checks that a single physical payout transaction hasn't already been used as reimbursement evidence for a different deposit.

### Impact Explanation
An operator eligible for the second deposit's presigned graph can run the kickoff/reimbursement flow using the older, already-broadcast, unrelated payout transaction as "proof" of having funded the second withdrawal, without spending a single additional satoshi for that user. This is a move-to-vault UTXO being released via reimbursement with no matching fronted withdrawal for that specific deposit — the withdrawer whose L2 funds were burned for the duplicated `idx` receives nothing. This matches "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" (Critical). It is repeatable across any deposit/operator pair where an attacker can get a second withdrawal id registered pointing at a UTXO already spent (or about to be spent) for another withdrawal.

### Likelihood Explanation
The attacker only needs standard, unprivileged capabilities: make a deposit, then call Citrea's `withdraw()` supplying arbitrary `(txid, vout)` bytes copied from an existing/older withdrawal's outpoint — Citrea's contract has no L1 visibility to reject this. The window to win the "race" is on the order of a Bitcoin block interval (until Clementine's syncer finalizes the block containing the reused UTXO's spend), which is comfortably achievable. Extracting value additionally requires a rational operator (who need not collude in advance) to notice and use the misattributed record during their normal reimbursement claim — this is a natural incentive, not an unusual action.

### Recommendation
Add a uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table (or reject/flag registrations that reuse an outpoint already assigned to another `idx`) in `update_withdrawal_utxo_from_citrea_withdrawal`. Additionally, have the bridge circuit/verifier bind the `deposit_constant`/journal to the specific `payout_spv.transaction` per deposit, and reject reimbursement claims where the same payout transaction has already been credited to a different `idx`/deposit (e.g., persist and check a global "payout_txid already used for reimbursement" set keyed independent of `idx`).

    storage_proof: &StorageProof,
    state_root: [u8; 32],
) -> (WithdrawalOutpointTxid, u32, MoveTxid) {

        serde_json::from_str(&storage_proof.storage_proof_utxo)
            .expect("Failed to deserialize UTXO storage proof");

    let vout_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_vout)
            .expect("Failed to deserialize vout storage proof");

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_deposit_txid)
            .expect("Failed to deserialize deposit storage proof");

    let storage_address: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(UTXOS_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let storage_key_utxo: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2);

    let storage_key_vout: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2 + 1);

    let storage_address_deposit: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(DEPOSIT_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let deposit_storage_key: alloy_primitives::Uint<256, 4> =
        storage_address_deposit + U256::from(storage_proof.index);

    let deposit_storage_key_bytes = deposit_storage_key.to_be_bytes::<32>();

    if deposit_storage_key_bytes != deposit_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid deposit storage key. left: {:?} right: {:?}",
            deposit_storage_key_bytes,
            deposit_storage_proof.key.as_b256().0
        );
    }

    if storage_key_utxo.to_be_bytes() != utxo_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal UTXO storage key. left: {:?} right: {:?}",
            storage_key_utxo.to_be_bytes::<32>(),
            utxo_storage_proof.key.as_b256().0
        );
    }

    if storage_key_vout.to_be_bytes() != vout_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal vout storage key. left: {:?} right: {:?}",
            storage_key_vout.to_be_bytes::<32>(),
            vout_storage_proof.key.as_b256().0
        );
    }

    storage_verify(&utxo_storage_proof, state_root);

    storage_verify(&deposit_storage_proof, state_root);

    storage_verify(&vout_storage_proof, state_root);

    let buf: [u8; 32] = vout_storage_proof.value.to_be_bytes();

    // ENDIANNESS SHOULD BE CHECKED THIS FIELD IS 4 BYTES in the contract
    let vout = u32::from_le_bytes(
        buf[28..32]
            .try_into()
            .expect("Vout value conversion failed"),
    );

    let wd_outpoint = WithdrawalOutpointTxid(utxo_storage_proof.value.to_be_bytes());

    let move_txid = MoveTxid(deposit_storage_proof.value.to_be_bytes());

    (wd_outpoint, vout, move_txid)
}
