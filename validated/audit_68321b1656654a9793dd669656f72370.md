### Title
Direct stakingToken donation to MasterMagpie inflates `totalStaked()` and permanently dilutes/freezes queued rewards - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPoolV2.totalStaked()` computes the reward-per-token denominator from the raw ERC20 balance of the `operator` (MasterMagpie) rather than from the sum of tracked user stakes. An attacker can transfer `stakingToken` directly to MasterMagpie (bypassing `deposit`/`depositFor`), which increases this balance without crediting any user's `userInfo[stakingToken][user].amount`, causing `_provisionReward` to under-distribute newly queued rewards, permanently trapping the shortfall in the pool.

### Finding Description
`totalStaked()` reads the actual on-chain balance of `stakingToken` held by `operator` (MasterMagpie): [1](#0-0) 

Meanwhile, per-user shares are read from MasterMagpie's internal accounting, not from the token balance: [2](#0-1) [3](#0-2) 

Legitimate deposits increase both the real token balance and `userInfo[...].amount` together via `safeTransferFrom` in `_deposit`: [4](#0-3) 

However, `stakingToken` (e.g., a Wombat receipt token or any standard ERC20 pool token) is a normal transferable token. An attacker can call `IERC20(stakingToken).transfer(masterMagpieAddress, amount)` directly — this is a plain ERC20 transfer that bypasses `_deposit` entirely, so it increases `IERC20(stakingToken).balanceOf(operator)` (and thus `totalStaked()`) without touching `userInfo` for any account.

When a manager subsequently calls `queueNewRewards` → `_provisionReward`, the reward-per-token increment is computed as: [5](#0-4) 

Because `totalStaked()` is now inflated relative to `sum(balanceOf(user))` across all stakers, `rewardPerTokenStored` is incremented by a smaller amount than it would be if computed against the true staked sum. Each user's claimable amount is `_earned = userShare * (rewardPerToken - paid) / 1e18 + accrued`: [6](#0-5) 

Summed over all users, total claimable = `sum(balanceOf(user)) * delta_rewardPerToken / 1e18`, which is strictly less than the `_amountReward` that was pulled into the contract via `safeTransferFrom` in `_provisionReward`. The difference remains as an ERC20 balance sitting in `BaseRewardPoolV2`, but there is no code path that ever increments `rewardPerTokenStored` to account for it (the only "catch-up" mechanism, `queuedRewards`, only triggers when `totalStaked() == 0`, not for partial dilution). The residual is therefore permanently unclaimable and stuck.

No existing modifier (`onlyManager`, `updateReward`, `nonReentrant`) prevents this because the root cause is the mismatch between the trusted denominator source (raw token balance) and the trusted numerator source (internal accounting mapping) — the attacker's transfer is a completely permissionless, unguarded ERC20 transfer to an arbitrary address that happens to be the accounting anchor for every `BaseRewardPoolV2` instance.

### Impact Explanation
This causes a permanent freezing of a portion of every future reward distribution queued after the donation, for as long as the inflated balance remains and until further legitimate deposits eventually rebalance the ratio (rare, since the diluted portion is never made up for previous distributions). This matches the Immunefi impact class "theft or permanent freezing of unclaimed yield" / "freezing of funds ≥24 hours," since queued reward tokens are locked in the contract indefinitely with no code path to release them to any user.

### Likelihood Explanation
The attack requires only that the attacker holds (or acquires cheaply) some amount of `stakingToken` and performs a plain `transfer()` to the MasterMagpie address — no special privileges, no flash loan needed (though one could be used to amplify the effect cheaply), and it is fully repeatable before every `queueNewRewards` call. The attacker gains nothing directly (pure griefing) but the cost is only the (recoverable, since attacker still owns... actually the tokens are not recoverable, they are lost/donated) value of tokens donated, so likelihood depends on economic incentive for a griefer, but the mechanism itself is trivially exploitable by any unprivileged actor.

### Recommendation
Do not use `IERC20(stakingToken).balanceOf(operator)` as the reward denominator. Instead, track and use the sum of all `userInfo[stakingToken][user].amount` (i.e., an explicit `totalStaked` counter incremented/decremented within `_deposit`/`_withdraw` in `MasterMagpie`) so that direct token donations cannot influence reward accounting.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPoolV2` for a mock `stakingToken` and `rewardToken`, register pool with `rewardManager`.
2. User A deposits `100e18 stakingToken` via `MasterMagpie.deposit`.
3. Attacker (holding stakingToken from an open market/mint) calls `stakingToken.transfer(address(masterMagpie), 900e18)` directly — no `deposit` call.
4. Assert `BaseRewardPoolV2.totalStaked() == 1000e18` while `BaseRewardPoolV2.balanceOf(userA) == 100e18` (i.e., sum of all users' `balanceOf` = 100e18 ≪ totalStaked).
5. `rewardManager` calls `queueNewRewards(1000e18, rewardToken)`.
6. Compute `userA.earned(rewardToken)`. Expected: `100e18 * (1000e18 * 1e18/1000e18) / 1e18 = 100e18`, i.e., only 10% of the 1000e18 queued reward is claimable — the remaining 900e18 rewardToken balance sits in `BaseRewardPoolV2` forever with no code path to release it.
7. Assert `sum(all users' earned()) < 1000e18` (strictly, `== 100e18`) and that no subsequent legitimate call can recover the 900e18 residual, confirming permanent freezing.
