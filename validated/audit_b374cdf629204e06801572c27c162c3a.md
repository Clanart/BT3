## Finding: Griefing solver can permanently lock cross-chain intent escrow via reverting native-token beneficiary

### Title
Reverting native-ETH transfer to solver-controlled beneficiary permanently locks escrowed order funds in `IntentsBase#_withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase#_withdraw` [1](#0-0)  releases every token in a `WithdrawalRequest` in a single loop, using a hard-reverting low-level `.call` for native ETH (`if (!sent) revert InsufficientNativeToken();`). The `beneficiary` for a `RedeemEscrow` withdrawal is set to `msg.sender` at fill time in `ExtrinsicIntents#_fillCrossChain` [2](#0-1) , i.e. it is chosen by whoever calls the fill function — an unprivileged, attacker-controlled address. If that address is a contract with no payable fallback, the one-time `RedeemEscrow` cross-chain message that later credits the source-chain escrow can never succeed: the same immutable beneficiary is baked into the message body, so every delivery/retry attempt reverts identically, exactly like the `_mint`/`_safeMint` mismatch in the source report where a non-ERC721Receiver contract can receive but never claim a soul-bound NFT.

### Finding Description
- On the destination chain, `_fillCrossChain` records `_filled[commitment] = msg.sender` and uses `order.output.beneficiary` for direct output transfers, then dispatches a `RedeemEscrow` `WithdrawalRequest` back to source with the solver as beneficiary [2](#0-1) .
- On the source chain, `_withdraw` decodes `body.beneficiary` and, for any escrowed native-token input, performs `beneficiary.call{value: amount}("")`; on failure it unconditionally reverts the whole function with `InsufficientNativeToken` [3](#0-2) .
- Because the loop processes *all* tokens for the commitment atomically, a revert on the native-token leg also blocks release of any ERC20 legs in the same order, and `_filled[commitment]` is never finalized, so the escrow stays locked with no alternate beneficiary or pull-based rescue path.
- This is the same class of bug already recognized and explicitly mitigated elsewhere in this repository for the analogous "unpayable reward" hazard: `pallet_beefy_consensus_proofs` deliberately treats a failing reward transfer as non-fatal so it can never permanently block consensus settlement [4](#0-3) . `IntentsBase#_withdraw` has no equivalent safeguard — a failing beneficiary transfer is fatal and, because the beneficiary is fixed by the original cross-chain request body, is fatal forever.

### Impact Explanation
Any user can act as a solver, fill a cross-chain order using a `msg.sender` contract deliberately built to reject native ETH, and cause the corresponding source-chain escrow (which may also hold unrelated ERC20 amounts for the same commitment) to become permanently unredeemable. This is a direct loss-of-funds/logic-attack outcome reachable from a fully public, unprivileged entrypoint (`fillOrder`/`_fillCrossChain`), with no reliance on a malicious relayer, prover, or admin — only a self-controlled solver contract.

### Likelihood Explanation
Deploying a contract without a payable `receive()`/`fallback()` (or one that explicitly reverts) is trivial and free for any address that calls the public fill entrypoint. The only requirement is that the order includes a native-token (`token == address(0)`) input, which is a normal, common configuration.

### Recommendation
Mirror the pattern already used for the WETH-timeout refund path in `WrappedHyperFungibleTokenUpgradeable#onPostRequestTimeout` [5](#0-4) , which already falls back to a wrapped ERC20 transfer instead of hard-reverting on a failed native push: in `IntentsBase#_withdraw`, do not let a failed native-ETH `.call` revert the whole settlement. Either (a) wrap/queue the unclaimed native amount as WETH/pull-payment credited to `beneficiary` instead of reverting, or (b) process each token leg independently so one failing beneficiary cannot block settlement of the rest, consistent with the "unpayable reward must not block settlement" design already adopted in `pallet_beefy_consensus_proofs`.

### Proof of Concept
1. Attacker deploys `EvilSolver`, a contract with no payable fallback (any call sending value reverts).
2. Attacker calls the order's cross-chain fill entrypoint from `EvilSolver` so that `_filled[commitment] = address(EvilSolver)` and `order.output.beneficiary` transfers succeed on destination (attacker funds the output tokens themselves) — see `_fillCrossChain` [2](#0-1) .
3. The `RedeemEscrow` `WithdrawalRequest` is dispatched to source chain with `beneficiary = address(EvilSolver)`.
4. When the request is delivered/proven on the source chain, `_withdraw` attempts `beneficiary.call{value: amount}("")` for the escrowed native input; `EvilSolver` rejects it, causing `revert InsufficientNativeToken()` [6](#0-5) .
5. Because the request body (and thus the beneficiary) is immutable, every retry of the same commitment fails identically, permanently locking the escrowed input tokens (native and any co-escrowed ERC20 for that commitment) with no recovery path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
