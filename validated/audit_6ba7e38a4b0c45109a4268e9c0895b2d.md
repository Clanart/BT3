I found a confirmed divide-by-zero (integer FPE-equivalent panic) analog in the KIP-71 base fee calculation, reachable via governance-set `GasTarget`.

### Title
Unchecked `GasTarget` governance parameter causes divide-by-zero panic in `NextMagmaBlockBaseFee`, crashing all nodes - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `kc.GasTarget` without validating it is non-zero, unlike the adjacent `BaseFeeDenominator` parameter which is explicitly guarded against zero.

### Finding Description
In `params/kip71_config.go`, `NextMagmaBlockBaseFee` explicitly checks `BaseFeeDenominator == 0` and substitutes a safe default to "avoid panic" [1](#0-0) , but the same protection is missing for `gasTarget`. When `parentGasUsed != gasTarget`, the code computes `x.Div(x, new(big.Int).SetUint64(gasTarget))` in both the "above target" and "below target" branches [2](#0-1) [3](#0-2) . In Go's `math/big`, `Int.Div` panics with "division by zero" when the divisor is zero, analogous to the CWE-369 floating/integer point exception described in the PaddlePaddle advisory.

The `GasTarget` governance parameter (`Kip71GasTarget`) uses `noopFormatChecker`, meaning it accepts any `uint64` value including `0`, in contrast to `Kip71BaseFeeDenominator` which explicitly rejects `0` via its `FormatChecker` [4](#0-3) . This asymmetry indicates the zero-check was deliberately added for `BaseFeeDenominator` but overlooked for `GasTarget`.

`NextMagmaBlockBaseFee` / `VerifyMagmaHeader` are invoked on the consensus-critical path for every block (header preparation in `blockchain/chain_makers.go`, header verification in `blockchain/block_validator.go`, block assembly in `work/worker.go`), meaning a zero `GasTarget` would panic every node processing a block once Magma is active.

### Impact Explanation
If a governance vote (an unprivileged governance parameter change reachable through the on-chain governance/voting mechanism) sets `governance.kip71.gastarget` to `0`, then as soon as any block has `parentGasUsed != 0` (virtually guaranteed under normal traffic), every node's base fee calculation panics, crashing block production and header validation network-wide — a full chain halt/denial of service, which maps to "state divergence between honest nodes / acceptance of an invalid block" is actually a total processing crash rather than a subtle divergence, but qualifies as a severe DoS analogous to the referenced CVE's "runtime crash and denial of service."

### Likelihood Explanation
Requires a governance parameter update to set `GasTarget = 0`, which passes the `FormatChecker` since it's a no-op check accepting any `uint64` [5](#0-4) . Whether this can be triggered purely by an unprivileged transaction sender or requires validator/governing-node privilege depends on the governance mode (single vs. contract-based); if `GovernanceMode` is contract-based and the governance contract does not itself reject `gasTarget=0`, this becomes reachable by any account with voting rights, not necessarily a validator. This aspect could not be fully confirmed from the available context, as the governance-vote submission and validation path (whether arbitrary uint64 values for `gastarget` pass through to `HeaderGov`/contract-based `ParamSet` unvalidated) was not traced in full within the available indexing.

### Recommendation
Add an explicit zero-check for `gasTarget` in `NextMagmaBlockBaseFee`, mirroring the existing `BaseFeeDenominator` fallback, e.g., default to a safe non-zero value or reject invalid headers/params instead of dividing by a potentially-zero value. Additionally, add a `FormatChecker` for `Kip71GasTarget` (and any other parameter used as a divisor) that rejects `0`, consistent with `Kip71BaseFeeDenominator`.

### Proof of Concept
1. Submit/pass a governance parameter update setting `governance.kip71.gastarget = 0` (format-checker for this key currently accepts any uint64, per `kaiax/gov/param.go`).
2. Once this parameter set becomes active post-Magma-fork, produce or receive a block whose parent had non-zero `GasUsed` (any normal block).
3. `NextMagmaBlockBaseFee` computes `parentGasUsed > gasTarget` (true, since gasTarget=0 and gasUsed>0), and executes `x.Div(x, new(big.Int).SetUint64(0))`, which panics inside `math/big`.
4. The panic occurs in header preparation (`chain_makers.go`), header verification (`block_validator.go`), and block assembly (`worker.go`) — crashing every node's block processing goroutine, i.e., halting the chain. [2](#0-1) [3](#0-2) [4](#0-3)
