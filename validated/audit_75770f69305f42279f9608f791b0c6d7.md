### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers O(n²) field operations + O(n) inversions/point-multiplications during Lagrange `group_key` derivation, enabling asymmetric CPU DoS — ([File: crypto/dkg/src/lib.rs])

### Summary
GHSA-vx74-f528-fxqg (HTTP/2 Rapid Reset) is a CWE-400 bug where a cheap client action (HEADERS + RST_STREAM) forces the server to burn unbounded work per request. The Serai analog lives in `ThresholdKeys::read` / `ThresholdKeys::new`: the deserialization trusts an attacker-supplied `n` (u16, up to 65535), then computes the group key by evaluating a Lagrange `interpolation_factor` — itself an O(n) loop with a field inversion — for each of `t` participants, yielding O(t·n) ≈ 4.3 billion field multiplications plus 65535 point multiplications for ~2 MB of input bytes.

### Finding Description
`ThresholdKeys::<C>::read` reads `t`, `n`, `i` directly from the input byte stream and then calls `ThresholdKeys::new(ThresholdParams::new(t, n, i)?, …)` [1](#0-0) . `ThresholdParams::new` only enforces `t <= n` and `i <= n` — there is no bound on `n` beyond u16::MAX [2](#0-1) .

Inside `ThresholdKeys::new`, the group key is computed as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [3](#0-2) 

With `Interpolation::Lagrange` (a single `1` byte in the stream selects it, avoiding the `n` scalar reads of `Constant`), each `interpolation_factor` call iterates over the entire `included` set — all `t` participants — performing field multiplications and, crucially, a field **inversion** (`denom.invert().unwrap()`) per call [4](#0-3) . The result is:

- `t` × O(t) field multiplications → O(t²) = ~4.3 × 10⁹ for `t = n = 65535`,
- `t` field inversions (each ~100–300 field mults),
- `t` variable-time scalar·point multiplications over the caller's curve.

The attacker's cost is only `n` serialized group elements (~33 B each for compressed points ≈ 2.2 MB total) plus a handful of header bytes — i.e., thousands of field operations per input byte, the same small-request/large-work asymmetry as Rapid Reset. `read` is explicitly in the set of entry points reachable with untrusted bytes (`ThresholdKeys::read`), and `read_G` deserialization of the verification shares must succeed, so the payload is just `n` valid encoded points (the identity point suffices if `read_G` accepts it, or any fixed valid point repeated).

### Impact Explanation
Any party able to submit a serialized `ThresholdKeys` blob to a verify / sign / key-setup path can stall the victim in a single `ThresholdKeys::new` call performing billions of scalar-field operations and tens of thousands of elliptic-curve multiplications. This is a CPU-exhaustion DoS of the signing/key-management component — it blocks the victim's participation in DKG/FROST rounds and can prevent timely signing. Rapid-Reset-style repetition amplifies the effect: each ~2 MB message re-triggers the full O(n²) computation since work is performed during construction, before any check could reject the keys.

### Likelihood Explanation
Reachable wherever `ThresholdKeys::read` consumes peer/validator-supplied bytes (key-share exchange, key recovery / promotion flows, or any transport carrying serialized `ThresholdKeys`). Requires no privileges, collusion, or valid shares — only well-formed curve encodings. Likelihood is bounded only by whether the deployment actually exposes this deserialization to untrusted input; within the permitted scope rules it is a listed reachable API.

### Recommendation
- Bound `n` in `ThresholdKeys::read` (and `ThresholdParams::new` consumers generally) to a protocol maximum such as `MAX_KEY_SHARES_PER_SET` before allocating or interpolating.
- Compute `group_key` more cheaply: for Lagrange, evaluate the interpolation once per distinct factor or batch-invert denominators (Montgomery trick) to remove the O(t) inversions; better, cache/derive the group key from commitments rather than re-interpolating all `t` factors on deserialization.
- Reject `Interpolation` modes/params inconsistent with the caller's expected parameters before doing any group arithmetic.

### Proof of Concept
1. Build a buffer: `u32` id_len + `C::ID` + `t = 0xFFFF` + `n = 0xFFFF` + `i = 1` + interpolation byte `0x01` (Lagrange) + one scalar for `secret_share` + 65535 copies of a valid `C::G` encoding (e.g., the generator).
2. Feed it to `ThresholdKeys::<C>::read`.
3. `ThresholdKeys::new` passes `t ≤ n`, then evaluates `group_key` = Σ over 65535 participants, each Lagrange factor looping over all 65535 indexes and performing one field inversion — ~4.3 × 10⁹ field mults, 65535 inversions, 65535 point mults — for a ~2.2 MB input.
