### Title
Wallet RPC `get_private_key` Discloses Any Keychain Identity's Seed Regardless of Logged-In Fingerprint - (File: `chia/wallet/wallet_rpc_api.py`)

### Summary
The wallet RPC endpoint `get_private_key` accepts an arbitrary `fingerprint` in the request and returns the full private key/mnemonic seed for that fingerprint without checking whether it matches the wallet service's currently logged-in/active fingerprint. Any local RPC caller authorized to talk to the wallet service (e.g. via a shared or lower-trust client cert, or any caller that can reach the wallet RPC port) can enumerate fingerprints via `get_public_keys` and then retrieve the private key/seed material for *every* key stored in the shared keychain, not just the one they are supposed to be scoped to.

### Finding Description
`WalletRpcApi.get_private_key()` resolves the requested fingerprint by scanning **all** private keys returned by `self.service.keychain_proxy.get_all_private_keys()`: [2](#0-1) 

There is no comparison of `request.fingerprint` against `self.service.logged_in_fingerprint`, and no check that the caller is authorized specifically for that identity. `get_public_keys` (also unauthenticated at the fingerprint level) exposes the full list of fingerprints present in the keychain, so a caller can trivially discover valid fingerprints to query.

This is registered as a plain RPC route without any additional wrapper or authorization gate — contrast with `tx_endpoint`, which wraps transaction-related endpoints with sync/action-scope logic but still performs no identity-scoping either: [3](#0-2) 

The underlying `Keychain.get_key`/`get_all_private_keys` methods themselves are identity-agnostic — they return whatever matches the fingerprint from the full on-disk keyring, with no user/service partition check applied at this call site: [4](#0-3) 

This mirrors the Airflow CVE-2024-27906 bug class: an endpoint returns sensitive resource data (DAG code / here, private key seed) for an object identified by a caller-supplied ID, without verifying the caller has permission to view *that particular* object — only checking that the caller is generically authenticated to the service.

### Impact Explanation
Exposure of a private key/mnemonic seed is a full compromise of that identity — the requester can derive the same wallet's spend keys, farmer key, and pool key (as constructed in `GetPrivateKeyResponse`), and can move all funds controlled by that fingerprint. On a machine or daemon that manages multiple keychain identities (a common multi-wallet/multi-user setup, or shared Chia daemon with several fingerprints added via `add_key`), any caller that has generic wallet-RPC reachability but is only supposed to be scoped to one logged-in wallet identity can silently exfiltrate the keys of every other identity in the keychain. This is a concrete unauthorized-disclosure-leading-to-fund-theft impact, not a low-severity issue.

### Likelihood Explanation
This requires only that the caller can reach the wallet RPC (the "local RPC caller" trust boundary explicitly in scope) and knows or discovers a fingerprint via `get_public_keys`. No malicious peer, node, or special privilege is needed — a normal local wallet RPC client is sufficient. Any environment running multiple wallet fingerprints under one daemon (e.g. hosted wallet services, shared machines, CI wallets) is directly exposed.

### Recommendation
Scope `get_private_key` (and any other keychain-reading RPC/daemon path) to the currently logged-in fingerprint by default, and require explicit administrative privilege or a match against `self.service.logged_in_fingerprint` before returning key material for a different fingerprint. At minimum, reject requests where `request.fingerprint != self.service.logged_in_fingerprint` unless an additional authorization mechanism is introduced.

### Proof of Concept
1. Start a wallet daemon and add two independent keys via `add_key` (fingerprints `A` and `B`), with the wallet currently logged in as fingerprint `A` (`log_in`).
2. As a normal wallet RPC client authenticated only to interact with fingerprint `A`'s wallet, call `get_public_keys` to enumerate fingerprints, discovering fingerprint `B`.
3. Call `get_private_key` with `fingerprint=B`.
4. Observe that `WalletRpcApi.get_private_key()` returns `GetPrivateKeyResponse` containing the full `sk`/`seed` (mnemonic) for fingerprint `B`, even though the caller was never authenticated as or authorized for identity `B`. [5](#0-4)
