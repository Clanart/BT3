## Title
Payout `OP_RETURN` operator attribution is not covered by the SIGHASH_SINGLE|ANYONECANPAY payout signature, letting anyone front-run a withdrawal to strip its operator credit and permanently freeze reimbursement - (`core/src/builder/transaction/operator_reimburse.rs`, `core/src/operator.rs`, `core/src/verifier.rs`)

### Summary
`create_payout_txhandler` builds the payout transaction with a single user-signed input and three outputs: the user's payout, an anchor, and an `OP_RETURN` embedding the fronting operator's x-only pubkey. [1](#0-0)  The witness on the sole input is the user's own `SinglePlusAnyoneCanPay` signature, whose sighash type is strictly enforced at parse time. [2](#0-1)  Because `SIGHASH_SINGLE|ANYONECANPAY` only commits the withdrawing user's input and the output at the same index (index 0), it never commits to output index 2 (the `OP_RETURN` operator attribution) or to any extra funding inputs added later. Any party who obtains the (deliberately shareable) presigned withdrawal signature and outpoint can therefore build an alternative, fully valid payout transaction that pays the same user output but carries an arbitrary or missing `OP_RETURN`.

### Finding Description
The equality that must hold is: `operator credited for a payout == party that actually fronted/authorized that payout`. The protocol derives "who fronted a payout" purely from parsing the `OP_RETURN` output of the confirmed payout transaction:

```
core/src/verifier.rs:2283 update_finalized_payouts()
  ... op_return_output = get_first_op_return_output(&circuit_payout_tx);
  operator_xonly_pk = op_return_output.and_then(parse_op_return_data).and_then(XOnlyPublicKey::from_slice)
  // if OP_RETURN missing/invalid -> operator_xonly_pk = None, stored as NULL in DB
``` [3](#0-2) 

This field is subsequently the sole basis for:
- `payout_checker` picking up "my" unhandled payout by matching `payout_payer_operator_xonly_pk` [4](#0-3) 
- `validate_payer_is_operator`, which errors out (no reimbursement path) if the payer pubkey is `None` or does not match the operator's own key [5](#0-4) 
- `is_kickoff_malicious`, which treats a missing/mismatched operator pubkey in the payout `OP_RETURN` as proof the kickoff is malicious [6](#0-5) 

None of this data is authenticated by the withdrawing user's signature. The user's signature (enforced to be `SinglePlusAnyoneCanPay`, see `parse_withdrawal_sig_params`) only binds output index 0 (the user's own payout) and input index 0's own outpoint/value/script — it explicitly does **not** bind outputs 1/2 or any additional inputs, by design of that sighash flag combination. The actual operator-side code that builds the transaction (`operator.rs::withdraw`) funds the remainder via `fund_raw_transaction`/RBF using the calling operator's own bitcoind wallet, and only *that* operator's own pubkey is put in `OP_RETURN` — but nothing on the Bitcoin-consensus level, nor any check in `create_payout_txhandler`, ties this attribution back to whoever actually supplied the additional funding inputs. [7](#0-6) 

Consequently, once the presigned withdrawal signature and outpoint are public (they are intentionally fanned out by the Aggregator to every registered operator via `withdraw`/`InternalWithdraw`, and become visible on the Bitcoin mempool the instant any operator broadcasts a funding attempt), **any unprivileged party** can:
1. Reuse the same single input + witness (still validates against the user's signature, since ANYONECANPAY/SINGLE do not constrain what else is in the transaction).
2. Reproduce the exact committed output 0 (same script_pubkey/amount) to keep the signature valid.
3. Fund the transaction with their own inputs (or, via RBF, replace a pending legitimate operator's funding inputs with their own, using a higher fee) instead of any operator's wallet.
4. Set the `OP_RETURN` output to an invalid/garbage value, or omit it entirely.
5. Broadcast/confirm this transaction.

The withdrawal completes correctly on-chain (the user is still paid exactly what they signed for), but the recorded `payout_payer_operator_xonly_pk` becomes `NULL`. From this point on, per `validate_payer_is_operator`, **no operator can ever obtain reimbursement** for the corresponding deposit's move-to-vault UTXO through the normal path, and per `is_kickoff_malicious`, any operator who nonetheless attempts to kick off a reimbursement for this deposit will be flagged as sending a malicious kickoff (their committed blockhash cannot be validated against a payer that does not exist), exposing them to challenge/disprove.

### Impact Explanation
This breaks the "operator credited versus the party that paid" binding described in scope, mapping to two of the listed Critical impacts:
- **A vault UTXO permanently frozen**: the move-to-vault deposit's `DepositInMove` output can never legitimately be spent by the `reimburse_tx` path once `payout_payer_operator_xonly_pk` is NULL/mismatched for that deposit, since `validate_payer_is_operator` unconditionally errors when the payer is unknown. [8](#0-7) 
- **An honest operator permanently unable to be reimbursed / an honest operator's collateral burned**: if an operator (who may be unaware their withdrawal was intercepted) still attempts to send a kickoff for that deposit, verifiers treat it as malicious per `is_kickoff_malicious`, triggering the challenge/disprove flow against that operator's collateral. [9](#0-8) 

No verifier, operator, watchtower, or key-holder role is required to carry out the corruption itself — only knowledge of the public presigned withdrawal signature/outpoint (by design shared to all operators and visible in the public Bitcoin mempool) and enough BTC to fund the fixed output amount.

### Likelihood Explanation
Likelihood is moderate: the attacker must be able to see the presigned signature before (or race against) a legitimate operator's broadcast, and must front the exact withdrawal amount themselves with no compensation — this is a costly, largely griefing-style attack rather than a profit-seeking one. However, it requires no privileged role, no key compromise, and no deviation from documented configuration; it purely exploits the fact that `SIGHASH_SINGLE|ANYONECANPAY` does not cover the `OP_RETURN` attribution output that the entire off-chain reimbursement bookkeeping depends on.

### Recommendation
Do not rely on an unauthenticated `OP_RETURN` output for operator attribution. Instead, commit the fronting operator's identity inside the portion of the transaction that is covered by an authenticated signature (e.g., have the operator co-sign the full transaction, or use `SIGHASH_ALL`/`SIGHASH_SINGLE` without `ANYONECANPAY` for a dedicated operator-controlled input, or otherwise bind the attribution to something enforced by Bitcoin script/consensus rather than free-form transaction data that any funder can set arbitrarily).

### Proof of Concept
1. The Aggregator's `withdraw` RPC fans out `WithdrawParamsWithSig` (containing the enforced `SinglePlusAnyoneCanPay` `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`) to all registered operators. [10](#0-9) 
2. An outside observer captures this data (from the fan-out, or from the Bitcoin mempool once any operator begins funding it via `fund_raw_transaction`+RBF in `operator.rs::withdraw`). [11](#0-10) 
3. The observer constructs their own transaction reusing input 0 and the user's witness, keeping output 0 identical (satisfies the `SinglePlusAnyoneCanPay` commitment), funds it themselves, and sets an invalid/garbage/missing `OP_RETURN` (output 2) instead of a real operator pubkey (this is not covered by the payout signature, per the sighash construction verified against in `core/src/verifier/bridge_circuit` logic and consistent with `create_payout_txhandler`). [1](#0-0) 
4. Broadcasts and gets this transaction confirmed (either first, or via RBF replacing a legitimate operator's in-flight funding tx).
5. `update_finalized_payouts` records `payout_payer_operator_xonly_pk = NULL` for this withdrawal. [12](#0-11) 
6. Any operator attempting `get_reimbursement_txs`/`handle_finalized_payout` for this deposit now fails at `validate_payer_is_operator`, and any operator that nonetheless sends a kickoff is flagged malicious by `is_kickoff_malicious`. [13](#0-12) [6](#0-5) 

Note: I was unable to fully trace within the available search budget the exact downstream consequence of a verifier flagging a kickoff "malicious" (i.e., the precise disprove/collateral-burn mechanics) — this would need to be confirmed against the disprove/challenge transaction-building code (`core/src/builder/transaction/` challenge/disprove paths) in a follow-up session to fully validate the "collateral burned" sub-claim; the "permanently frozen vault UTXO / unreimbursable operator" portion of the impact is directly supported by the cited code.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

#[allow(clippy::result_large_err)]
pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    let input_outpoint: OutPoint = params
        .input_outpoint
        .ok_or_else(error::input_ended_prematurely)?
        .try_into()?;

    let users_intent_script_pubkey = ScriptBuf::from_bytes(params.output_script_pubkey);

    Ok((
        params.withdrawal_id,
        input_signature,
        input_outpoint,
        users_intent_script_pubkey,
        Amount::from_sat(params.output_amount),
    ))
}
