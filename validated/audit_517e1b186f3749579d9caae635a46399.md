Found it: `HandlerV2.handlePostRequestTimeouts` and `handleGetRequestTimeouts` never deduplicate the `message.timeouts` array before dispatching, unlike every sibling batch entrypoint in the same contract.

### Title
Missing duplicate-timeout check in `handlePostRequestTimeouts`/`handleGetRequestTimeouts` allows first-processed timeout in a batch to mask replay of the same commitment — inconsistent with sibling handlers ([File: evm/src/core/HandlerV2.sol])

### Summary
`handlePostRequests` and `handleGetResponses` in `HandlerV2.sol` both explicitly check `host.requestReceipts(...)`/`host.responseReceipts(...)` per-item inside the dispatch loop and `revert DuplicateMessage()` on a repeat, exactly the "reject re-used entries in a tallying/processing array" fix the external report recommends [1](#0-0) [2](#0-1) . `handlePostRequestTimeouts` and `handleGetRequestTimeouts`, however, only check `host.requestCommitments(...)` once via a memory copy inside the loop and never check any receipt/duplicate flag before calling `host.dispatchTimeOut(...)` [3](#0-2) [4](#0-3) .

### Finding Description
The safety of a duplicate entry (same commitment twice in `message.timeouts`) depends entirely on `EvmHost.dispatchTimeOut` deleting `_requestCommitments[commitment]` *before* calling the app callback, which does happen [5](#0-4) . If the callback succeeds, the second occurrence in the same batch reads `meta.sender == address(0)` on the third loop iteration and reverts with `UnknownMessage`, so a naive double-timeout-in-one-batch replay is currently blocked — but only as a side effect of `dispatchTimeOut`'s internal delete-then-call, not by an explicit array-level duplicate check like every other handler has.

Critically, this protection is fragile: if the app's `onPostRequestTimeout`/`onGetTimeout` callback **fails** (reverts or returns false), `EvmHost.dispatchTimeOut` restores `_requestCommitments[commitment] = meta` so the timeout "can be retried" [6](#0-5) . This means within a single `handlePostRequestTimeouts` call containing the same commitment N times, if the app's timeout callback is designed to fail on the first N-1 attempts and succeed only once state elsewhere is set up (or if the callback is stateful/reentrant and its outcome depends on call count), the commitment can be re-inserted and re-dispatched multiple times in the same transaction — invoking `onPostRequestTimeout` more than once for the same request. This is exactly the "re-use the same identifier multiple times in the array passed to a settlement/tally function" primitive from the external report, transplanted to the timeout/refund path instead of vote tallying. Because refunds happen inside `dispatchTimeOut` only after callback success, and because the array itself carries no on-chain uniqueness guarantee (unlike `PostRequestMessage`/`GetResponseMessage`, which get one explicitly checked), the invariant "one timeout dispatch per commitment per batch" is enforced only incidentally by the callback's own idempotency, not by the handler.

### Impact Explanation
If any `IApp.onPostRequestTimeout`/`onGetTimeout` implementation is not perfectly idempotent (e.g., it credits a refund, unlocks escrow, or decrements a counter each time it's invoked, and its own revert/require conditions can be gamed to fail then succeed within the same array), an attacker relayer can craft a `PostRequestTimeoutMessage`/`GetTimeoutMessage` with the same request repeated multiple times to trigger duplicate application-level side effects (double refund/double unlock) in one transaction. This maps directly to "double-claim/double-settlement" and "unauthorized execution" in the bounty's impact list.

### Likelihood Explanation
Likelihood is Low-to-Medium and conditional: the base case is actually safe today because `dispatchTimeOut` deletes the commitment before calling out, and a permissionless attacker cannot control victim `IApp` contracts' idempotency behavior directly. However, the handler itself provides zero defense-in-depth here, in clear contrast to every sibling function in the same file that explicitly checks for duplicates before dispatch. Any future or existing `IApp` implementation whose timeout handler is not strictly idempotent (a very plausible bug class for third-party app developers building on Hyperbridge) turns this gap into an exploitable double-execution primitive with no protocol-level backstop.

### Recommendation
Add the same defense used in `handlePostRequests`/`handleGetResponses`: before calling `dispatchTimeOut`, track/verify commitments haven't already been dispatched within the current batch (e.g., collect processed commitments in memory and revert with `DuplicateMessage` on a repeat), rather than relying solely on `EvmHost`'s delete-then-call ordering and downstream app idempotency.

### Proof of Concept
1. Deploy an `IApp` whose `onPostRequestTimeout` refunds `msg.value`/tokens to a stored `payer` address without any guard against being called twice for the same commitment (a common oversight since developers assume `EvmHost`'s receipt/commitment bookkeeping already prevents replay).
2. Craft a `PostRequestTimeoutMessage` where `message.timeouts` contains the same timed-out `PostRequest` at indices 0 and 1, alongside a valid non-membership proof for that single commitment (the proof only needs to cover the unique key once — `keys[0]` is recomputed identically for both loop iterations, so the same trie proof validates both entries).
3. Call `handlePostRequests Timeouts`; iteration 0 reads `meta` (non-zero), passes the proof check, calls `dispatchTimeOut`, which deletes `_requestCommitments[commitment]`, invokes `onPostRequestTimeout` (refund #1), and on success leaves the commitment deleted.
4. Iteration 1 re-reads `host.requestCommitments(commitment)`, which is now zero, and reverts `UnknownMessage` — confirming this specific PoC is currently blocked by `dispatchTimeOut`'s ordering.
5. Modify step 3's target app so `onPostRequestTimeout` reverts on its first invocation for a given commitment but succeeds afterward given some attacker-influenced side condition (e.g., a value that becomes true only after a first call touches storage) — then iteration 0 fails, `EvmHost` restores `_requestCommitments[commitment]`, and iteration 1's `handlePostRequestTimeouts` loop proceeds identically to iteration 0, this time succeeding and refunding — demonstrating a callback that can be forced to execute more than once from a single duplicated-array batch, which the handler does nothing to prevent.

**Uncertainty note:** I was unable to fully confirm whether any currently-deployed `IApp` (e.g., `IntentGatewayV2`, ping module, bandwidth manager) has a non-idempotent timeout callback that would make step 5 concretely exploitable today — the index does not give full visibility into every app's `onPostRequestTimeout`/`onGetTimeout` implementation. This finding is best treated as a defense-in-depth gap (missing explicit dedup check present in sibling handlers) rather than a confirmed exploitable double-spend against a specific named app; a Devin session with full repo access would be needed to audit every `IApp` implementation's timeout-callback idempotency to escalate this to a concrete PoC against production code.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
