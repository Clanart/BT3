### Title
Schnorr verification accepts the identity public key and identity nonce - ([File: crypto/schnorr/src/lib.rs](crypto/schnorr/src/lib.rs))

### Summary
`SchnorrSignature::verify` treats the identity group element as an ordinary public key and nonce. For `public_key = 0`, the signature `(R = 0, s = 0)` satisfies its verification equation `R + cA - sG = 0` for every challenge and message. This mirrors the external bug class: authentication succeeds because a required validity condition—the signer key being a non-identity group member—is assumed to have been enforced elsewhere.

### Finding Description
`SchnorrSignature::verify` directly runs `multiexp_vartime` over `batch_statements` without rejecting an identity `public_key` or identity `R`. `batch_statements` encodes only `R + cA - sG == 0`, so identity inputs make all terms vanish. [1](#0-0) 

The deserializer also delegates nonce decoding to `C::read_G` and does not add an identity check. [2](#0-1)  By contrast, the FROST curve wrapper explicitly recognizes identity points as invalid when reading protocol points. [3](#0-2) 

### Impact Explanation
Any caller that verifies an attacker-supplied `(public_key, signature)` pair without independently rejecting the identity public key will accept a forged signature for every message and challenge. This is an authentication bypass at the primitive boundary rather than merely malformed-input handling: the attacker needs no private key because the encoded key itself degenerates the relation.

### Likelihood Explanation
The attack requires the surrounding protocol to let an untrusted party choose or register the identity public key, or to deserialize such a key without rejecting it. `SchnorrSignature::read` does not protect against `R = identity`, and `verify` does not protect the supplied public key, so any integration that relies on this API as its authentication check is reachable with public bytes.

### Recommendation
Reject identity public keys and identity nonce commitments in `SchnorrSignature::verify` and `batch_verify`, or change `SchnorrSignature::read` and all public-key ingestion paths to enforce non-identity consistently. The check should live in the signature API rather than relying on every caller to validate the key separately.

### Proof of Concept
For any ciphersuite `C`, public challenge `c`, and message context used to derive `c`:

```rust
let public_key = C::G::identity();
let forged = SchnorrSignature::<C> {
    R: C::G::identity(),
    s: C::F::ZERO,
};
assert!(forged.verify(public_key, c));
```

The verification statement is:

```text
R + cA - sG
= 0 + c·0 - 0·G
= 0
```

Therefore `multiexp_vartime(...).is_identity()` is true regardless of `c`, so the forged signature is accepted.

```rust
  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,
  /// and any message. Failure to do so will let a malicious adversary to forge signatures for
  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
  }
```
