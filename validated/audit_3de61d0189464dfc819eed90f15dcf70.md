### Title
Broken linear-vesting formula in `_getClaimable` lets `claim(isLock=true)` instantly lock the *entire* unvested airdrop allocation into vlMGP, granting premature voting power - ([File: rewards/ArbitrumMWomAirdrop.sol])

### Summary
`_getClaimable` ignores `startVestingTime`, `vestingPeriodCount`, and `intervals` entirely and simply returns `totalAmount - claimed`, so the full merkle-allocated amount is claimable the instant `block.timestamp >= startVestingTime`. Because `claim(isLock=true)` forwards this fully-drained `claimable` straight into `locker.lockFor(claimable, msg.sender)`, an attacker with a valid merkle leaf can acquire the entire intended-to-vest allocation as locked vlMGP-equivalent voting weight in a single transaction, rather than accruing it gradually.

### Finding Description
The vesting computation is:
```solidity
function _getClaimable(address account, uint256 totalAmount) internal view returns (uint256) {
    uint256 claimed = getClaimed(account);
    if (claimed >= totalAmount) {
        return 0;
    }
    uint256 vested = totalAmount;          // <-- no time-based scaling
    if (vested > totalAmount) {
        return totalAmount - claimed;
    }
    return vested - claimed;
}
``` [1](#0-0) 

`vested` is hard-set to `totalAmount` with no reference to `startVestingTime`, `vestingPeriodCount`, or `intervals`, even though these state variables exist and are set in the constructor [2](#0-1) [3](#0-2) , implying a linear-vesting schedule was intended but never wired into the formula. As a result, `claim()` allows the full allocation to be pulled as soon as `block.timestamp >= startVestingTime`:
```solidity
require(block.timestamp >= startVestingTime, "ArbitrumMWomAirdrop: Drop dose not start.");
...
uint256 claimable = _getClaimable(msg.sender, totalAmount);
...
} else if (isLock) {
    reward.safeApprove(address(locker), claimable);
    locker.lockFor(claimable, address(msg.sender));
}
``` [4](#0-3) 

Since `locker` is a vlMGP-like contract that grants voting weight proportional to locked amount (per the interface `ILocker.lockFor(uint256 _amount, address _for)` [5](#0-4) ), any attacker holding a valid merkle leaf can, in one call, convert their entire future-vesting allocation into present-day locked voting weight. No modifier (`whenNotPaused`, `nonReentrant`, merkle verification) prevents this because the check only gates *whether* a claim is allowed, not *how much* should be vested at that point in time. This vote weight is then usable immediately in `WombatBribeManager` votes, whereas under a correct linear-vesting design the attacker should only control a fraction of that weight until the vesting period completes.

### Impact Explanation
This enables governance voting result manipulation: an attacker (or several colluding attackers with sizeable merkle allocations) can acquire outsized vlMGP voting weight far earlier than intended and use it to outvote legitimate stakers whose lock positions were built up gradually/legitimately, in bribe or gauge votes managed by `WombatBribeManager`. This matches the "governance voting result manipulation" impact class explicitly listed in scope.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: possession of any valid merkle leaf (i.e., being an eligible airdrop recipient, which requires no privileged role) and a lock-capable `locker` contract. No flash loans, reentrancy, or special capital are required beyond having an allocation. The exploit is a single, straightforward transaction (`claim(totalAmount, proof, false, true)`) executable by any unprivileged EOA immediately at `startVestingTime`, making it highly likely to occur if any economically meaningful allocation exists.

### Recommendation
Implement the intended linear-vesting formula using `startVestingTime`, `vestingPeriodCount`, and `intervals`, e.g.:
```solidity
uint256 elapsed = block.timestamp - startVestingTime;
uint256 vestedIntervals = elapsed / intervals;
if (vestedIntervals > vestingPeriodCount) vestedIntervals = vestingPeriodCount;
uint256 vested = totalAmount * vestedIntervals / vestingPeriodCount;
```
and only forward the correctly-vested `claimable` amount to `locker.lockFor`, `helper.depositFor`, or direct transfer.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbitrumMWomAirdrop` with `startVestingTime = T`, `vestingPeriodCount = 12`, `intervals = 30 days`, and a merkle root containing attacker leaf `(attacker, totalAmount)`.
2. Deploy a mock `ILocker` that records `lockFor(amount, for)` calls and exposes a `votingWeight(address)` view proportional to locked amount (mirroring vlMGP semantics).
3. Warp to `T` (exactly at vesting start, 0 elapsed time).
4. Call `claim(totalAmount, proof, false, true)` from attacker.
5. Assert `mockLocker.votingWeight(attacker) == totalAmount`-equivalent weight, i.e., 100% of the allocation is locked at t=0.
6. Compute expected correctly-vested amount under linear vesting at t=0 (`0`, since no interval has elapsed) and assert the discrepancy (`fullAmount - 0`).
7. Optionally wire a mock `WombatBribeManager.vote()` call using the inflated weight and show the attacker's vote share exceeds what it should be, changing a simulated bribe outcome versus the corrected-formula scenario.
