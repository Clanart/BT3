### Title
OP_RETURN data output omitted from fee/weight calculation produces under-fee transactions that fail relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output carrying the caller-supplied `data` to `tx_outs`, but computes `weight`/`vbytes` (and hence `needed_fee`, the min-relay check, the change amount, and the `MAX_STANDARD_TX_WEIGHT` check) via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which only accounts for `payments` and the change script. The data output's weight is never counted, so the transaction pays the estimated fee for a smaller transaction than the one actually produced — the exact "requested amount assumed, actual amount differs" shape of the reference bug.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` builds `tx_outs` from `payments`, then pushes a zero-value `OP_RETURN` output when `data` is supplied (`send.rs:194-202`). The size estimation that determines `needed_fee` happens at `send.rs:204` and `send.rs:225-227` through `calculate_weight_vbytes`, which constructs a dummy `Transaction` whose `output` vector is built *only* from `payments` plus the optional change output (`send.rs:85-99`). The data output never enters the estimate.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` is under-estimated by the vsize of the OP_RETURN output (up to ~80 bytes of data plus script overhead, ≈25+ vbytes).
- The minimum-relay-fee check at `send.rs:211` compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the *understated* `vbytes`.
- When a change output is added (`send.rs:228-233`), `change = input_sat - payment_sat - fee_with_change`, and the actual fee equals `fee_with_change` — the under-estimate directly becomes the real fee, with no slack absorbed elsewhere.
- The `MAX_STANDARD_TX_WEIGHT` bound at `send.rs:241` is checked against the understated `weight`, so an oversized transaction can also be constructed.

`data` is attacker-reachable bytes: it is the channel through which external transactions embed `InInstruction`s/`RefundableInInstruction`s, and is validated only by the 80-byte length cap at `send.rs:171`.

### Impact Explanation
When `fee_per_vbyte` is set at or near the minimum relay rate (the normal operating point), the serialized transaction's effective fee rate `needed_fee / actual_vbytes` drops below `DEFAULT_MIN_RELAY_TX_FEE`. The signed transaction is then rejected as non-standard by the Bitcoin network, so the spend never propagates or confirms — a denial of service of the wallet spend path whenever a data output is attached, exactly analogous to the reference finding where ignoring the real (post-fee) amount makes the subsequent operation always fail. If change is present, the under-estimate also inflates the change amount, so `fee()` — documented as "the fee this transaction will use" (`send.rs:137-141`) — ends up below the `needed_fee` callers rely on.

### Likelihood Explanation
Any caller constructing a `SignableTransaction` with `data: Some(..)` and a low fee rate triggers it; the fee shortfall is proportional to the data length and requires no collusion or privileged access — the data bytes are externally supplied. It does not require an edge-case input, just the data path plus a minimum-fee target.

### Recommendation
Include the OP_RETURN output in the size estimate: build the dummy transaction in `calculate_weight_vbytes` (or a variant of it) with the data output appended, and use that weight/vbytes for `needed_fee`, the min-relay check, the change calculation, and the `MAX_STANDARD_TX_WEIGHT` check. Equivalently, pass `tx_outs` (already containing the data output) into the estimator so estimate and reality cannot diverge, mirroring the reference fix of using the actual returned value rather than the assumed amount.

### Proof of Concept
```rust
// Fee at exactly the minimum relay rate (~1 sat/vbyte equivalent)
let data = vec![0u8; 80]; // max allowed
let tx = SignableTransaction::new(
  vec![input],                 // ReceivedOutput with sufficient funds
  &[(payment_script, 1000)],   // one payment
  None,                        // no change: excess still becomes fee
  Some(data),
  fee_per_vbyte,               // chosen so needed_fee == min_relay * vbytes_est / 1000
).unwrap();

// needed_fee passes the TooLowFee check because `vbytes` excluded the OP_RETURN
let actual_vbytes = tx.transaction().vsize() as u64; // ~25 vbytes larger than estimate
let actual_fee_rate = tx.fee() / actual_vbytes;      // < 1 sat/vb => non-standard, rejected
```
