### Title
Unhandled `AssertionError`/`EvalError` in `compute_spend_hints_and_additions()` when a `CREATE_COIN` condition lacks a puzzle-hash IE crashes wallet sync processing - (File: chia/wallet/util/compute_hints.py)

### Summary
`compute_spend_hints_and_additions()` parses `CREATE_COIN` conditions coming out of an untrusted, attacker-controlled puzzle reveal/solution without first verifying that the expected argument ("IE") is present, mirroring the Ella Core NAS bug class where an Authentication Response/Failure message was processed without checking for the presence of expected information elements before dereferencing them.

### Finding Description
`compute_spend_hints_and_additions()` iterates over the conditions produced by running a `CoinSpend`'s puzzle reveal against its solution, and for every `CREATE_COIN` condition (opcode 51) it unconditionally extracts the puzzle-hash argument and asserts it is present: [1](#0-0) 

```
if op != ConditionOpcode.CREATE_COIN.value:
    continue
cost += ConditionCost.CREATE_COIN.value

rf = condition.at("rf").atom
assert rf is not None

coin: Coin = Coin(cs.coin.name(), bytes32(rf), uint64(condition.at("rrf").as_int()))
```

The `condition.at("rf")` call walks the CLVM tree with the path selector `"rf"` (rest, then first). If the `CREATE_COIN` condition output by a malicious puzzle is malformed — e.g. `(51)` with no further arguments, or `(51 . 0)` where the "rest" is an atom instead of a pair — `Program.at()` raises `EvalError`/`ValueError` for non-pair paths, and even when a value is returned, `rf.atom` can be `None` (a cons cell where an atom was expected), which trips the bare `assert rf is not None` on line 53. Neither of these failure modes is a `ValidationError`/`ConsensusError` that callers are expected to catch; they are raw Python exceptions/`AssertionError`s. `Program.at()` is documented elsewhere in the codebase to raise `ValueError`/`EvalError` for missing or wrong-typed IEs when the requested tree path does not exist: [2](#0-1) 

The same unguarded pattern is repeated for `condition.at("rrf")`, `condition.at("rrr")`, `condition.at("rrrf")`, and `condition.at("rrrff")` in the hint-extraction logic — none of these paths are validated for presence before being dereferenced: [3](#0-2) 

This function is invoked from multiple wallet subsystems that process spends originating from data the attacker fully controls (an on-chain coin's puzzle reveal/solution, or an offer's coin spends), including `chia/wallet/wallet_state_manager.py`, `chia/wallet/cat_wallet/cat_wallet.py`, `chia/wallet/did_wallet/did_wallet.py`, `chia/wallet/trade_manager.py`, `chia/wallet/trading/offer.py`, and `chia/wallet/vc_wallet/cr_cat_wallet.py`. In particular, `Offer.conditions()` runs arbitrary attacker-supplied coin spends from an offer file through the same class of unguarded CLVM-path parsing (`parse_conditions_non_consensus`), though that call site is wrapped in a broad `try/except Exception: continue`: [4](#0-3) 

By contrast, `compute_spend_hints_and_additions()` itself has no such guard around the `CREATE_COIN` argument extraction, so any caller that does not wrap the call in a broad exception handler will propagate the `AssertionError`/`EvalError` up the stack.

### Impact Explanation
An attacker who controls a puzzle (e.g., a CAT/DID/VC inner puzzle, or any puzzle whose coin a victim wallet will process during sync, trade acceptance, or offer inspection) can craft a spend whose `CREATE_COIN` condition output is missing the puzzle-hash argument. When a victim's wallet processes that coin spend — during normal chain sync of a block containing the spend, or while parsing a maliciously crafted offer/trade — `compute_spend_hints_and_additions()` will raise an unhandled `AssertionError` or `EvalError`. If the call site lacks a catch-all exception handler, this halts wallet transaction/coin processing for that wallet instance, causing a spend-triggered denial of service against wallet software for any user whose wallet observes the malicious coin (analogous to the Ella Core NAS-parsing panic: an unauthenticated/unprivileged input path that omits an expected field crashes ongoing processing). This is a process-halting bug rather than a fund-theft or consensus-divergence bug.

### Likelihood Explanation
Likelihood is moderate to high for triggering the crash condition itself, since any spend bundle submitter or offer creator can trivially construct a puzzle that emits a `CREATE_COIN` condition with a missing or malformed puzzle-hash argument. However, the codebase indexed here does not let me confirm with certainty whether every call site of `compute_spend_hints_and_additions()` (in `wallet_state_manager.py`, `cat_wallet.py`, `did_wallet.py`, `trade_manager.py`, `cr_cat_wallet.py`) wraps the call in a broad exception handler the way `Offer.conditions()` does for `parse_conditions_non_consensus`. I was not able to retrieve the exact surrounding try/except context for those call sites before running out of tool iterations, so whether this specific path is fully exploitable end-to-end (uncaught all the way to a wallet-sync-halting crash) versus already mitigated by an enclosing `try/except` at each caller is **unverified**. This is the key uncertainty in this finding.

### Recommendation
Add explicit presence/type validation for all condition-argument tree paths accessed in `compute_spend_hints_and_additions()` (mirroring the fix pattern in the Ella Core advisory of adding IE presence verification before dereferencing NAS message fields):
- Replace the bare `assert rf is not None` with an explicit check that raises a caught, expected exception type (e.g., skip the malformed condition or raise `ValidationError`) rather than an `AssertionError`.
- Guard `condition.at("rrf")`, `condition.at("rrr")`, `condition.at("rrrf")`, and `condition.at("rrrff")` calls with try/except (or `Program.at()`-safe alternatives) so malformed/missing arguments cause the condition to be skipped rather than raising an uncaught exception.
- Audit every caller of `compute_spend_hints_and_additions()` (`wallet_state_manager.py`, `cat_wallet.py`, `did_wallet.py`, `trade_manager.py`, `offer.py`, `cr_cat_wallet.py`) to confirm they wrap the call in a handler that converts CLVM-path failures into a rejected/ignored spend instead of propagating an unhandled exception that could interrupt wallet sync.

### Proof of Concept
1. Construct a coin whose puzzle, when run with any solution, outputs a condition list containing a truncated `CREATE_COIN` condition, e.g. CLVM output `(51)` (opcode only, no puzzle hash) or `(51 . 0)` (malformed rest).
2. Include this coin's spend in a block that a victim's wallet will sync, or embed the spend in an offer file presented to the victim.
3. When the victim wallet calls `compute_spend_hints_and_additions()` on this `CoinSpend` (via `wallet_state_manager.py`/`cat_wallet.py`/etc.), `condition.at("rf").atom` returns `None` or `condition.at("rrf")` raises `EvalError`, triggering the bare `assert rf is not None` failure or an unhandled `EvalError`/`ValueError` at `chia/wallet/util/compute_hints.py:52-55`, potentially halting the wallet's coin/transaction processing loop if the calling context lacks a matching exception handler.
