## Analysis

The external report's core broken invariant: a migration/redeployment path replaces the contract identity that custodies escrowed funds, but cross-chain messages that release that escrow are addressed/authenticated against the *new* identity — leaving the original custody stranded with no reclaim path, and forcing capital to be duplicated or lost.

The closest verifiable local analog is `IntentGatewayV2`'s `_instances` registry (`evm/src/apps/intentsv2/IntentsBase.sol`), which backs both the *routing* of escrow-release messages (`_fillCrossChain`, `_cancelFromSource`, `_cancelFromDest` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`) and the *authentication* of inbound `RedeemEscrow`/`RefundEscrow` messages (`_authenticate`).

### Title
Governance `NewDeployment` remapping strands in-flight cross-chain escrow in `IntentGatewayV2` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`_instances[keccak256(chain)]` is looked up *at message-processing time*, not at order-placement time. `_addDeployment` (triggered by a `NewDeployment` governance request) overwrites the mapping in place with no versioning and no migration of orders that were placed while the old address was registered.

### Finding Description
`_instance(stateMachineId)` (`IntentsBase.sol:358-362`) resolves the peer gateway address purely from current storage: `_instances[keccak256(stateMachineId)]`. This value is used both to route outbound escrow-release/refund dispatches and to authenticate inbound ones via `_authenticate` (`ExtrinsicIntents.sol:63-67`), which requires `request.from == _instance(request.source)`.

Order escrow itself lives in per-contract storage (`_orders[commitment][token]`, `IntentsBase.sol:140`) on whichever gateway instance was live when `placeOrder` executed. If governance later dispatches `NewDeployment` (`RequestKind.NewDeployment`, handled by `_addDeployment`, `IntentsBase.sol:521-524`) to point `_instances[chain]` at a freshly redeployed gateway contract for that chain (e.g. after a non-upgradeable redeploy, chain migration, or address rotation), every order still in flight under the old instance is affected:

- On the destination side, `_fillCrossChain` (`ExtrinsicIntents.sol:89-171`) builds the `RedeemEscrow` dispatch with `to: abi.encodePacked(_instance(order.source))` — the *current* registered source address, not the one that held the order's original escrow. If the source instance was rotated, the message is sent to a contract that has no matching `_orders[commitment]` entry, so `_withdraw` (`IntentsBase.sol:390-425`) reverts with `UnknownOrder` — the solver's fill succeeds (output already delivered) but the input-side escrow release fails.
- Symmetrically, `_cancelFromSource`/`_cancelFromDest` compute proof keys and dispatch targets from `_instance(order.destination)`/`_instance(order.source)` at cancel time, not placement time, so a rotation on either side breaks the GET-proof key derivation or misdirects the `RefundEscrow` message.
- The old gateway contract has no privileged or user-callable path to reclaim `_orders[commitment][token]` once its address is no longer the one referenced by peers — there is no analog to `sweepDust`/`withdraw` for user-owned escrow, only for protocol dust.

This exactly mirrors the M-22 pattern: escrow custody is bound to a contract identity, governance-driven redeployment silently changes what identity is authoritative going forward, and funds already escrowed under the old identity become unrecoverable through the normal cross-chain flow — with the destination-side output having already been paid out to the beneficiary, compounding the loss (solver/user pays twice, or user's principal is stuck).

### Impact Explanation
This is a fund-loss/fund-lock bug on a live escrow custody path: `_orders[commitment][token]` balances become permanently stranded in a superseded `IntentGatewayV2` instance after a `NewDeployment` remap, with the standard `RedeemEscrow`/`RefundEscrow` release paths broken by address mismatch, and no dedicated recovery mechanism for user escrow (only `SweepDust` exists, and that is scoped to protocol-owned surplus, not user orders).

### Likelihood Explanation
Requires a legitimate governance `NewDeployment` action (contract redeployment/rotation) to land while orders are in flight — a plausible operational event (e.g. migrating off a compromised or bugged gateway version) rather than an attacker-controlled trigger, so it is a genuine design gap rather than a privileged-actor abuse scenario. It does not require a malicious peer, relayer, or key compromise — only ordinary lifecycle timing between an in-flight order and a routine instance-address update.

### Recommendation
Bind escrow lookups and message authentication to the instance address that was authoritative when the order was placed (e.g. snapshot the peer address into the order/commitment at `placeOrder` time, or version the `_instances` map so old entries remain valid for messages referencing pre-existing commitments) rather than always resolving through the live `_instances` mapping. Additionally, provide a governance-gated recovery path that lets a superseded gateway instance forward/migrate its outstanding `_orders` escrow to the new instance, or allow direct withdrawal against a proof that the order was legitimately created there.

### Proof of Concept
1. `placeOrder` on chain A escrows tokens in `IntentGatewayV2` instance `A_old`, with `order.destination = chain B`, and `B`'s registered `_instances[keccak256("A")] == A_old`.
2. Governance dispatches `NewDeployment` to chain B's gateway, updating `_instances[keccak256("A")] = A_new` (e.g., migrating chain A's gateway to a new address after a redeploy).
3. A solver fills the order on chain B via `fillOrder` → `_fillCrossChain`; it pays the beneficiary the output tokens, then dispatches `RedeemEscrow` with `to = _instance(order.source) = A_new`.
4. On chain A, `A_new.onAccept` receives the `RedeemEscrow` message and calls `_withdraw`, but `A_new._orders[commitment][token]` is `0` (the escrow was recorded in `A_old`), so it reverts with `UnknownOrder`.
5. The solver has already paid out the destination-side output but cannot collect the source-side escrow; the original input tokens remain locked in `A_old` indefinitely, with no function exposed to migrate or reclaim per-order escrow from a superseded instance.     function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
