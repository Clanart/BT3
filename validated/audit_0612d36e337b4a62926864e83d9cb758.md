### Title
Fee estimation omits OP_RETURN data output, underpaying the intended feerate and risking non-relayable transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying caller-supplied `data` to `tx_outs` before computing the transaction's weight/vbytes, but calls `calculate_weight_vbytes` with `payments` — a list that excludes the OP_RETURN output. The resulting `needed_fee` is therefore computed on a transaction that is smaller than the one actually built, so the real transaction pays a lower sat/vbyte rate than requested, and can fall below the mempool's minimum relay feerate.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202`, when `data` is `Some`, an extra `TxOut` with an OP_RETURN script is pushed onto `tx_outs`. The weight/vbyte estimate at line 204 (`Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`) is then derived from `payments` only, never accounting for the OP_RETURN output that was just appended. `calculate_weight_vbytes` (lines 62-127) builds the dummy transaction's `output` list solely from `payments` plus an optional change output, so the OP_RETURN's ~10-90+ serialized bytes are missing from the weight used at line 206 (`needed_fee = fee_per_vbyte * vbytes`). The final transaction (lines 245-255) nevertheless includes the OP_RETURN output, so `fee() = inputs - outputs = needed_fee` is spread over a larger vsize than estimated. The change-output path at lines 224-235 recomputes weight correctly for change but still uses `payments` and inherits the same omission. The minimum-fee guard at lines 211-213 only rejects `needed_fee` relative to the underestimated `vbytes`, so a `fee_per_vbyte` at or near the minimum still passes while the real feerate falls under `DEFAULT_MIN_RELAY_TX_FEE`.

### Impact Explanation
The produced transaction's effective feerate is `needed_fee / actual_vsize < fee_per_vbyte`. With maximal data (up to 80 bytes permitted by the check at line 171), the discrepancy is roughly 90+ weight units of uncounted output. When `fee_per_vbyte` is close to the minimum relay rate, the transaction falls below relay policy and will not propagate — a denial of service for the withdrawal/operation — while the signed transaction still commits its inputs and pays `needed_fee` to miners if it ever does confirm late. Even when it does relay, it confirms slower than the rate the operator paid for, degrading the fee guarantee the `fee_per_vbyte` parameter is supposed to provide.

### Likelihood Explanation
The trigger is entirely in-band: any payment/`data` path that attaches an OP_RETURN (which `SignableTransaction::new` explicitly supports) hits the miscalculation every time — it is deterministic, not probabilistic. Whether it crosses the relay threshold depends on the chosen `fee_per_vbyte` and data size, so at worst it is a guaranteed systematic underpayment and at a minimum it silently mischarges the feerate; the under-estimation exists for every `data`-bearing transaction.

### Recommendation
Compute weight/vbytes from the actual output list (including the OP_RETURN output) rather than from `payments`. Either build the dummy transaction's outputs from `tx_outs`, or pass the OP_RETURN `TxOut` into `calculate_weight_vbytes` so its script size is counted. Also consider validating the final `tx`'s real vsize against the minimum relay feerate, not the estimate.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, &payments, None, Some(vec![0; 80]), fee_per_vbyte)` where `fee_per_vbyte` equals the minimum relay rate (e.g., 1 sat/vbyte, i.e., `DEFAULT_MIN_RELAY_TX_FEE / 1000` rounded up).
2. Line 171's `data.len() <= 80` check passes and an OP_RETURN output is appended at lines 194-202.
3. `calculate_weight_vbytes` at line 204 builds the sizing transaction from `payments` only; the ~89-byte OP_RETURN output contributes nothing to `vbytes`.
4. The check at line 211 passes because `needed_fee = 1 * vbytes` meets the minimum for the underestimated size.
5. The returned transaction includes the OP_RETURN output; its actual vsize is ~22+ vbytes larger than `vbytes`, so `fee() / actual_vsize < 1 sat/vbyte` — below the minimum relay feerate — producing a transaction that nodes will not relay (DoS) while still spending the inputs and committing `needed_fee` as miner fee if it is ever mined.
