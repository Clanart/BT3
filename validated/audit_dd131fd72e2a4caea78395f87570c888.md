### Title
`TxSender` background task never started for `OperatorServer` — operator-queued Bitcoin transactions permanently stuck in DB - (File: `core/src/operator.rs`)

### Summary

`OperatorServer::start_background_tasks` omits the `TxSender` background task that is required to drain the operator's transaction queue and broadcast signed Bitcoin transactions. The analogous `VerifierServer::start_background_tasks` correctly starts this task. As a result, every transaction the operator queues — round txs, kickoff txs, reimbursement txs, challenge-ack/nack txs — accumulates in the database and is never broadcast to Bitcoin.

### Finding Description

`Operator::new` creates a `TxSenderClient` backed by the operator's own DB pool:

```rust
// core/src/operator.rs:241-242
let tx_sender =
    TxSenderClient::new(clementine_tx_sender::TxSenderDb::from_pool(db.get_pool()));
``` [1](#0-0) 

`TxSenderClient` is a write-only queue handle — it only inserts rows into the DB. The actual `TxSender` task is what reads those rows and broadcasts transactions to Bitcoin via RPC. The verifier correctly creates and starts this task:

```rust
// core/src/verifier.rs:271-276
let tx_sender_cfg = self.verifier.config.tx_sender_config();
let tx_sender = TxSender::new(tx_sender_cfg).await?;
self.background_tasks
    .ensure_task_looping(tx_sender.into_task())
    .await;
``` [2](#0-1) 

The operator's `start_background_tasks` contains no equivalent block — it starts the `StateManager`, `PayoutCheckerTask`, and `EntityMetricPublisher`, but never starts a `TxSender` task: [3](#0-2) 

The operator queues multiple critical transaction types through `self.tx_sender`:

- **Round tx** (`start_first_round`, line 992): the collateral-spending round transaction that opens a new kickoff window
- **Kickoff-related txs** (`queue_relevant_txs_for_new_kickoff`, line 2489): `OperatorChallengeAck`, `WatchtowerChallengeTimeout`, `ChallengeTimeout`, `DisproveTimeout`, `Reimburse` [4](#0-3) [5](#0-4) 

None of these are ever broadcast because no task is polling the queue.

### Impact Explanation

Without the `TxSender` task running for the operator:

1. **Round transactions are never sent.** The operator cannot advance its round state machine, so no kickoffs can ever be initiated. This is a complete bridge liveness failure for that operator.
2. **Reimbursement transactions are never sent.** After a valid payout, the operator cannot reclaim its collateral UTXO. The collateral remains locked indefinitely.
3. **Challenge-ack/nack and timeout transactions are never sent.** If a verifier challenges a kickoff, the operator cannot respond within the timelock window, resulting in the operator's collateral being slashed.

This is a permanent loss/lock of operator collateral and a bridge liveness break — both within the allowed impact gate.

### Likelihood Explanation

This bug is triggered whenever an operator node is deployed with the `automation` feature enabled as a standalone process (i.e., with its own `db_name`, separate from any verifier). The production entry point `create_operator_grpc_server` calls `operator.start_background_tasks()` directly: [6](#0-5) 

In tests, operators and verifiers share the same DB (via `verifier_config.clone()` in `TestOperator::new`), so the verifier's `TxSender` incidentally drains the operator's queue — masking the bug in the test suite. [7](#0-6) 

### Recommendation

Add the `TxSender` task to `OperatorServer::start_background_tasks` inside the `#[cfg(feature = "automation")]` block, mirroring the verifier:

```rust
#[cfg(feature = "automation")]
{
    let tx_sender_cfg = self.operator.config.tx_sender_config();
    let tx_sender = TxSender::new(tx_sender_cfg).await?;
    self.background_tasks
        .ensure_task_looping(tx_sender.into_task())
        .await;

    // ... existing state_manager setup ...
}
```

Also add the `BitcoinSyncer` task, which is similarly absent from the operator but present in the verifier.

### Proof of Concept

1. Deploy an operator node standalone (separate DB from any verifier) with `automation` feature enabled.
2. Call `setup` via the aggregator to register the operator.
3. Observe that `start_background_tasks` completes without starting any `TxSender` task — `TaskVariant::TxSender` is absent from the operator's `BackgroundTaskManager` registry.
4. The operator's state machine calls `start_first_round` → `self.tx_sender.insert_try_to_send(...)` → row inserted into `tx_sender_try_to_send` table.
5. No round transaction is ever broadcast to Bitcoin. The operator's round state machine stalls. No kickoffs are ever initiated. Collateral UTXO remains unspent and inaccessible. [3](#0-2) [8](#0-7) [9](#0-8)

    pub async fn start_background_tasks(&self) -> Result<(), BridgeError> {
        // initialize and run state manager
        #[cfg(feature = "automation")]
        {
            let state_manager = StateManager::new(
                self.operator.db.clone(),
                self.operator.clone(),
                self.operator.rpc.clone(),
                self.operator.config.clone(),
            )
            .await?;

            let should_run_state_mgr = {
                #[cfg(test)]
                {
                    self.operator.config.test_params.should_run_state_manager
                }
                #[cfg(not(test))]
                {
                    true
                }
            };

            if should_run_state_mgr {
                self.background_tasks
                    .ensure_task_looping(state_manager.block_fetcher_task().await?)
                    .await;
                self.background_tasks
                    .ensure_task_looping(state_manager.into_task())
                    .await;
            }
        }

        // run payout checker task
        self.background_tasks
            .ensure_task_looping(
                PayoutCheckerTask::new(self.operator.db.clone(), self.operator.clone())
                    .with_delay(PAYOUT_CHECKER_POLL_DELAY),
            )
            .await;

            .ensure_task_looping(
                EntityMetricPublisher::<Operator<C>, C>::new(
                    self.operator.db.clone(),
                    self.operator.rpc.clone(),
                    self.operator.config.clone(),
                    self.operator.citrea_client.clone(),
                )
                .with_delay(ENTITY_METRIC_PUBLISHER_INTERVAL),
            )
            .await;

        tracing::info!("Payout checker task started");

        // track the operator's round state
        #[cfg(feature = "automation")]
        {
            // Will not start a new state machine if one for the operator already exists.
            self.operator.track_rounds().await?;
            tracing::info!("Operator round state tracked");
        }

        Ok(())
    }
