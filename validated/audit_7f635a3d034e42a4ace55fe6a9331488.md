### Title
Unbounded memory allocation in `eth_getProof` via arbitrarily large `storageKeys` array - (File: api/api_eth.go)

### Summary
The `eth_getProof` / `kaia_getProof` public JSON-RPC method accepts a caller-supplied `storageKeys []string` parameter and immediately allocates several slices sized to `len(storageKeys)` before any bound, deduplication, or plausibility check is applied to that length, mirroring the class of bug in CVE-2021-22207 where the MS-WSP dissector allocated memory proportional to an attacker-controlled length field before validating it.

### Finding Description
`doGetProof` is the shared implementation backing both `EthAPI.GetProof` and `KaiaBlockChainAPI.GetProof`, exposed on the public RPC surface with no special privilege required: [1](#0-0) 

```go
func doGetProof(ctx context.Context, b Backend, address common.Address, storageKeys []string, blockNrOrHash rpc.BlockNumberOrHash) (*EthAccountResult, error) {
	var (
		keys         = make([]common.Hash, len(storageKeys))
		keyLengths   = make([]int, len(storageKeys))
		storageProof = make([]EthStorageResult, len(storageKeys))
	)
	...
```

Three slices (`keys`, `keyLengths`, `storageProof`) are allocated with a capacity directly derived from the untrusted `len(storageKeys)` parameter, before any of the elements are validated by `decodeHash`, and before the function even checks that the target account/state exists. Unlike the RLP decoding path in the same repository, which enforces `ErrValueTooLarge`/`ErrElemTooLarge` checks against the remaining input length before allocating (`rlp/decode.go` `Stream.Kind`), this JSON-RPC argument path has no analogous length cap specific to the number of storage keys a single call may request. The exposed methods: [3](#0-2) [4](#0-3) 

Both are plain public RPC endpoints reachable by any unauthenticated RPC caller.

### Impact Explanation
A caller can submit a single `eth_getProof`/`kaia_getProof` request with a very large `storageKeys` JSON array. Each element only needs to be a short hex string, so the memory blow-up ratio between request size and allocated Go objects is large: each string element causes allocation of a `common.Hash` (32 bytes), an `int`, and an `EthStorageResult` struct (containing a `*hexutil.Big`, a string, and a `[]string` slice) — well beyond the size of the input string itself. This can be used to exhaust node memory or cause excessive GC pressure/latency on the node's public RPC endpoint, a resource-exhaustion / availability impact consistent in class with the referenced Wireshark dissector bug (CVE-2021-22207), where oversized allocations from an untrusted length field caused denial of service.

### Likelihood Explanation
The endpoint is part of the standard, publicly documented Ethereum-compatibility JSON-RPC namespace (`eth_getProof`) and requires no special permissions, staking, or fee payment (RPC calls are not gas-metered the way transactions are). The only practical limiter is the RPC server's total HTTP request content-length cap (`networks/rpc/http.go`), which bounds the raw JSON payload size but does not specifically cap the number of `storageKeys` entries or the resulting in-memory allocation multiplier. Within that content-length budget, an attacker can still pack a very large number of short hex strings, achieving a substantial allocation amplification per request, and can repeat/parallelize such requests.

### Recommendation
- Add an explicit upper bound on `len(storageKeys)` in `doGetProof` (e.g., reject if it exceeds a small constant such as a few hundred/thousand keys), returning an RPC error before any allocation.
- Alternatively/additionally, allocate `storageProof`/`keys`/`keyLengths` lazily via `append` as each key is successfully decoded, rather than pre-allocating full-size slices from the untrusted length.
- Consider validating/deduplicating `storageKeys` before allocation to avoid amplification from repeated identical keys.

### Proof of Concept
Send a single JSON-RPC request to a public node:
```json
{
  "jsonrpc": "2.0",
  "method": "eth_getProof",
  "params": [
    "0x0000000000000000000000000000000000000000",
    ["0x00", "0x00", "0x00", ... /* repeated up to the HTTP body size limit, e.g. hundreds of thousands of short entries */],
    "latest"
  ],
  "id": 1
}
```
Each `"0x00"` entry is only 4 bytes in the request body but triggers allocation of a `common.Hash` (32 bytes), an `int`, and an `EthStorageResult` struct with nested fields in `keys`, `keyLengths`, and `storageProof`, executed in `doGetProof` (api/api_eth.go:296-301) before any of the individual hash strings are decoded or validated against actual state.

func doGetProof(ctx context.Context, b Backend, address common.Address, storageKeys []string, blockNrOrHash rpc.BlockNumberOrHash) (*EthAccountResult, error) {
	var (
		keys         = make([]common.Hash, len(storageKeys))
		keyLengths   = make([]int, len(storageKeys))
		storageProof = make([]EthStorageResult, len(storageKeys))
	)
	// Deserialize all keys. This prevents state access on invalid input.
	for i, hexKey := range storageKeys {
		var err error
		keys[i], keyLengths[i], err = decodeHash(hexKey)
		if err != nil {
			return nil, err
		}
	}
