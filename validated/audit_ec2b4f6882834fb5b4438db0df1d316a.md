### Title
Unvalidated `Participant` indexes in the PedPoP blame path panic via unchecked `HashMap` indexing - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The DKG blame-resolution API (`BlameMachine::blame` / `AdditionalBlameMachine::blame` in `crypto/dkg/pedpop/src/lib.rs`) accepts arbitrary `sender` and `recipient` `Participant` values from an accuser and indexes `HashMap`s with them. `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` and `blame_internal` evaluates `self.commitments[&sender]` without checking membership. Since `Participant` is any non-zero `u16` and the maps only contain `1..=n`, an accuser who names an out-of-range index causes an unconditional panic — a denial of service analogous to the falsifiable `CHECK`s in `function.cc`.

### Finding Description
`Participant::new` only rejects `0` (`crypto/dkg/src/lib.rs:29-35`), so `Participant` values up to `u16::MAX` are well-formed on the wire. `Decryption` populates `enc_keys` strictly for registered participants (`crypto/dkg/pedpop/src/encryption.rs:348-362`), and `BlameMachine`/`AdditionalBlameMachine` populate `commitments` strictly for `1..=n` (`crypto/dkg/pedpop/src/lib.rs:656-661`, `:331-336`).

`blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-609`) forwards the accuser-supplied `recipient` into `decrypt_with_proof`, which after a successful PoP check and `proof.is_some()` executes:

```rust
&[self.enc_keys[&decryptor], *proof.key]   // encryption.rs:388
```

`HashMap`'s `Index` impl panics on a missing key. If the PoP/proof path is passed with a registered `decryptor` but an out-of-range `sender`, the same panic occurs at `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`). Neither `blame` entry point validates that `sender`/`recipient` are in `1..=n`. `AdditionalBlameMachine` explicitly exists so any caller — including non-participants — can evaluate submitted accusations (`crypto/dkg/pedpop/src/lib.rs:638-662`), making this reachable from an unauthenticated accusation carrying a copy of a real encrypted share (whose `pop` is valid over the public `msg.key`/`from`/`msg` bytes at `encryption.rs:374-379`).

### Impact Explanation
A single malformed accusation aborts the process evaluating blame. In deployment this runs on validator/coordinator nodes resolving DKG faults, so any party able to submit an accusation (a normal DKG participant, or any observer via `AdditionalBlameMachine`) can crash every node that evaluates it, stalling key generation and any signing dependent on the resulting `ThresholdKeys`. This matches the reported bug class: an assertion-like failure (here, unchecked `HashMap::index` / `assert!`s) falsified by attacker-supplied input, causing an interpreter/process crash (CWE-617, availability impact only).

### Likelihood Explanation
Requires only that a party submit a blame accusation naming `sender` or `recipient` outside `1..=n` (e.g., `Participant::new(n + 1)`), plus a message with a valid PoP — trivially satisfied by forwarding the genuine `EncryptedMessage` the accused sender broadcast. The `enc_keys[&decryptor]` panic fires as soon as `proof: Some(_)` is supplied, before any share-validity check. No cryptographic break or collusion is needed; the sole prerequisite is that the deployment exposes blame evaluation, which the API is designed for.

### Recommendation
In `blame_internal` (or the `blame` wrappers), reject `sender`/`recipient` not present in `self.commitments`/`self.encryption.enc_keys` before indexing, returning a defined `PedPoPError`/`Participant` verdict. Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `get`/`ok_or`-style lookups, and bound-check both indexes against `params.n()`.

### Proof of Concept
```rust
// n = 3 DKG among participants 1,2,3. After all commitment msgs are collected:
let machine = AdditionalBlameMachine::<Ed25519>::new(context, 3, commitment_msgs).unwrap();

// Attacker (participant 2) takes the *real* EncryptedMessage participant 1 sent,
// which has a valid `pop`, and any EncryptionKeyProof, then accuses with an
// out-of-range recipient:
let bogus_recipient = Participant::new(4).unwrap(); // valid Participant, not in 1..=n
machine.blame(
  Participant::new(1).unwrap(),   // sender
  bogus_recipient,                // recipient
  msg_from_1_to_2,                // pop verifies: bound to from=1, msg bytes
  Some(EncryptionKeyProof::read(&mut &proof_bytes[..]).unwrap()),
);
// decrypt_with_proof: msg.pop.verify(...) passes, proof.is_some() ->
// `self.enc_keys[&Participant(4)]` at encryption.rs:388 panics:
// "index not found" -> process abort.
```
Variant: keep `recipient` valid and pass `sender = Participant(4)` with a `proof` that survives to `blame_internal`'s share check — `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599` panics identically.
