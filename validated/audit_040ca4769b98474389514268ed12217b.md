## Title
`_checkoutBranch` performs a branch checkout with no guard against an in-progress rebase/merge/cherry-pick conflict state - ([File: app/src/lib/stores/app-store.ts])

## Summary
`AppStore._checkoutBranch` (`app/src/lib/stores/app-store.ts:4578-4643`) never inspects `changesState.conflictState` before calling `checkoutImplementation`/`git checkout`. The only place this state is defensively used is UI-level: `BranchDropdown` disables its own dropdown when `conflictState` is a rebase conflict (`app/src/ui/toolbar/branch-dropdown.tsx:188-195`), but that is a rendering concern for one specific entry point, not an invariant enforced in the store method that actually performs the checkout.

## Finding Description
This is the same bug class as the "liquidation works while paused" report: a security-relevant state flag (`isPaused` in the contract; `conflictState`/in-progress rebase, merge, or cherry-pick in Desktop) exists and is read in one place to gate the UI, but the underlying state-mutating operation does not itself check that flag.

Evidence:
- `_checkoutBranch` reads only `changesState.currentBranchProtected`, `changesState.stashEntry`, and `branchesState.tip` [1](#0-0) . It never reads `changesState.conflictState`.
- The guard against checking out during an in-progress operation lives only in `BranchDropdown.render`, which sets `disabled = true`/`canOpen = false` when `isRebaseConflictState(conflictState)` is true [2](#0-1) . It only covers the rebase case, not merge or cherry-pick conflicts, and only covers this one toolbar widget.
- `_checkoutBranch` is invoked from multiple other UI surfaces (`branches-container.tsx`, `stash-and-switch-branch-dialog.tsx`, `overwrite-stashed-changes-dialog.tsx`) which do not check `conflictState` before calling it.
- Once a rebase/merge/cherry-pick is in a conflicted state, Desktop tracks it via `.git/REBASE_HEAD`, `MERGE_HEAD`, or `CHERRY_PICK_HEAD` and surfaces it through `getConflictState`/`ConflictState` in `app/src/lib/stores/updates/changes-state.ts:118-176`. Running `git checkout <otherBranch>` while one of these sequencer states is present can silently discard the in-progress operation's conflict-resolution work (uncommitted resolutions in the working directory) or leave the repository in a state where the rebase/merge markers become stale relative to the new HEAD, without any explicit confirmation to the user analogous to the "Abort" flow that `ConfirmAbort`/`_abortRebase` normally requires.

## Impact Explanation
An attacker who controls a fetched/cloned repository can craft history that reliably produces conflicts on rebase/merge/cherry-pick (a routine, natural git scenario, not something requiring social engineering). If the user then switches branches through any of the checkout entry points that call `_checkoutBranch` (rather than using the "Abort" button in the dedicated conflicts UI, which does check state and calls `abortRebase`/`abortMerge`), Desktop performs the checkout without warning that an operation is in progress. This can silently corrupt what the user later commits/pushes: partially-resolved conflict markers or staged manual resolutions can be left orphaned, and the working directory ends up reflecting a mix of the old (conflicted) target branch state and the newly checked-out branch, contrary to the user's mental model of "the rebase is still going." That matches the class of issue described as valid: silent corruption of what the user commits or pushes, reached without local/physical access or prior malware — only a crafted repository and a normal user action (switch branch).

## Likelihood Explanation
Medium. The precondition (crafted conflicting commits reachable via a normal `git fetch`/`clone`, combined with the user manually resolving a merge/rebase and then switching branches from a secondary entry point instead of the guarded toolbar dropdown or explicit "Abort") is plausible but requires a somewhat specific sequence of user actions. The severity is bounded by the fact that git itself, not Desktop, ultimately performs the checkout, so most straightforward cases (e.g., unresolved index conflicts) would be rejected by git — but Desktop's own gating is inconsistent across UI surfaces, and cases where the working tree is "clean enough" for git to allow the checkout (e.g. once file conflicts are staged/resolved but the rebase/merge hasn't been continued) are exactly where Desktop's higher-level `conflictState` tracking should have intervened and currently does not, except in one widget.

## Recommendation
Add an explicit guard at the top of `_checkoutBranch` (and/or in `checkoutImplementation`) that checks `repositoryState.changesState.conflictState !== null` and, if so, blocks the checkout and surfaces a confirmation/abort dialog (reusing the existing `ConfirmAbort`/`_abortRebase`/`abortMerge`/`abortCherryPick` flows) instead of silently proceeding — consistent for merge, rebase, and cherry-pick conflict kinds, and consistent across every call site (branches container, stash dialogs, PR checkout, recent branches), not just the toolbar `BranchDropdown`.

## Proof of Concept
1. Create a repository with two branches whose histories conflict on rebase (or merge).
2. In Desktop, start a rebase (`Branch > Rebase Current Branch...`) that results in conflicts; Desktop shows the `ConflictsDialog` and tracks `conflictState` via `getConflictState` (`app/src/lib/stores/updates/changes-state.ts:121-176`).
3. Instead of clicking "Abort rebase" or continuing, open the branches list from a non-toolbar entry point (e.g. `branches-container.tsx`'s branch list, which calls into `_checkoutBranch` without checking `conflictState`) and select a different branch.
4. Observe that `_checkoutBranch` proceeds directly to `checkoutImplementation` (`app/src/lib/stores/app-store.ts:4578-4643`) with no check on `changesState.conflictState`, performing `git checkout` while `.git/REBASE_HEAD` still exists — leaving the rebase sequencer state orphaned/stale relative to the new HEAD, unlike the guarded path via `BranchDropdown`, which would have disabled this action for the rebase case (but not for merge/cherry-pick).

Note: I was not able to fully trace every downstream consequence git itself imposes in each precise conflict sub-state (e.g., whether git's own safety checks would abort the `checkout` in every scenario); a Devin session with full repo/checkout access would be needed to reproduce end-to-end and confirm the exact on-disk corruption in each of the merge/rebase/cherry-pick sub-cases.
