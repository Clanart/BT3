Based on the investigation, the strongest confirmed analog is in GitHub Desktop's git credential-helper trampoline, where **the classification of a remote endpoint as a "GitHub" host is derived from an attacker-controlled `WWW-Authenticate` response header rather than from a validated hostname**.

### Title
Git credential-helper endpoint classification trusts attacker-controlled `WWW-Authenticate` header, causing GitHub sign-in flow to be triggered against an untrusted remote - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
Similar to the FluxToken report's core flaw — a security-relevant classification/state transition (`accrueFlux`) that trusts caller-supplied invocation frequency instead of a validated epoch boundary — GitHub Desktop's `getEndpointKind()` classifies a git remote as a GitHub/Enterprise endpoint by trusting attacker-suppliable data (`wwwauth[]` header content forwarded by Git) instead of validating the actual hostname against a known GitHub allowlist.

### Finding Description
When Git needs credentials for an HTTPS remote, it invokes Desktop's credential helper trampoline (`createCredentialHelperTrampolineHandler`) with a `get` command. The stdin payload includes any `WWW-Authenticate` headers the *remote server* returned, exposed as `wwwauth[...]` keys [1](#0-0) . `getEndpointKind()` uses the literal content of that attacker-controlled header to decide the endpoint's trust classification:

```
for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
``` [2](#0-1) 

This check runs *before* the protocol/host-based fallback (`credentialUrl.protocol !== 'https:'` and `isGitHubHost(endpoint)`) [3](#0-2) , meaning any HTTP(S) server — including a malicious `origin` remote added to a cloned/fetched repository, or a MITM proxy sitting on the git transport — can force the endpoint to be classified as `'enterprise'` simply by returning `WWW-Authenticate: Basic realm="GitHub"` on an unauthenticated request.

Once classified as non-generic, `getCredential()` skips the generic credential-manager/prompt path entirely and, if no existing account matches that endpoint, calls `ui.promptForGitHubSignIn(endpoint)` [4](#0-3)  — routing the user into Desktop's GitHub-specific OAuth sign-in flow, using the attacker's own endpoint as the OAuth base URL. That flow builds the authorize URL and later exchanges the code via `requestOAuthToken`, which POSTs Desktop's shared `ClientID`/`ClientSecret` to whatever host was supplied as `endpoint` [5](#0-4) .

The broken invariant: **endpoint trust classification (`endpointKind`) should be derived from a validated, attacker-uncontrollable source (hostname against a known allowlist / config), but instead is derived from content the remote server itself supplies.** The existing "GitHub.com/GHE creds are only stored internally" guard at line 128 does not stop this because it only prevents *storing* the credential — it does not stop the classification from misrouting the *sign-in* trigger to an attacker endpoint in the first place.

### Impact Explanation
An attacker who controls a git remote (e.g., set as `origin` in a repository the victim clones/adds, or a transparent proxy intercepting a fetch/push) can force Desktop to present its native "Sign in to GitHub" flow pointed at the attacker's server during an ordinary `fetch`/`push`/`pull`, rather than the expected generic-credential prompt. This creates a route to leak Desktop's shared OAuth `ClientSecret` to the attacker's endpoint via `requestOAuthToken`, and — because the flow is indistinguishable from a legitimate GitHub Enterprise sign-in inside the trusted Desktop UI — creates a strong phishing primitive for the user's real GitHub credentials/PAT, entirely triggered by attacker-controlled server responses rather than any out-of-band social engineering.

### Likelihood Explanation
Triggering the vulnerable code path requires no special user action beyond a normal git operation (fetch/push/pull) against a remote the attacker controls or proxies — something explicitly in-scope per the task's threat model ("attacker controls...a git remote/proxy response"). The header-based classification bypasses hostname verification entirely, so likelihood is high for any repository where the user's remote can be attacker-influenced.

### Recommendation
`getEndpointKind()` should never elevate trust based on response header content alone; classification as `'enterprise'`/GitHub should require the hostname to match a configured/known GitHub Enterprise endpoint (as already done via `isGitHubHost`), with the `wwwauth[]` heuristic used only as a secondary hint gated behind that hostname check, not as a standalone deciding branch.

### Proof of Concept
1. Attacker stands up an HTTPS git server (or MITM proxy) and configures it as the sole remote of a repository (e.g. via a malicious clone URL, or by rewriting `origin` in a repo the victim opens).
2. Server responds to an authenticated git operation with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. Victim performs `git fetch`/`push` via Desktop; Desktop's trampoline credential helper receives `wwwauth[...]=Basic realm="GitHub"` in the `get` command stdin.
4. `getEndpointKind` returns `'enterprise'` for the attacker's host [2](#0-1) , and since no stored account matches that host, Desktop invokes `ui.promptForGitHubSignIn(endpoint)` with the attacker's URL as the endpoint [6](#0-5) .
5. The resulting OAuth exchange (`requestOAuthToken`) sends Desktop's `ClientID`/`ClientSecret` to the attacker's endpoint [5](#0-4) .

**Note on verification limits**: I was unable to inspect `app/src/lib/trampoline/trampoline-ui-helper.ts` (`promptForGitHubSignIn`) and the exact `isGitHubHost`/account-matching implementation before running out of tool calls, so the precise UI copy/flow shown to the victim and whether any additional hostname confirmation exists there is not fully verified — only the `getEndpointKind` classification logic and the OAuth token exchange sink were directly confirmed in code.
