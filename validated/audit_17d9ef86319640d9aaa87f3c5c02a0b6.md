### Title
Malicious remote can spoof `WWW-Authenticate: realm="GitHub"` to force a GitHub Enterprise sign-in prompt for an attacker-controlled host - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
`getEndpointKind()` in the credential-helper trampoline classifies a Git remote endpoint as `'enterprise'` (i.e., a trusted GitHub Enterprise host) purely based on an unauthenticated, attacker-supplied `WWW-Authenticate` header value forwarded by Git, without ever validating that the host is actually a GitHub instance via `isGitHubHost()`. This lets any Git server the user is talking to (a compromised/malicious remote, or a MITM proxy on an `http(s)` transport) force GitHub Desktop into its GitHub-sign-in code path for a host of the attacker's choosing.

### Finding Description
When Git needs credentials for a remote, it can capture `WWW-Authenticate` response headers from the server and forward them to the configured credential helper as `wwwauth[N]=...` key/value pairs. `getEndpointKind()` uses these values as a trust oracle:

```ts
// app/src/lib/trampoline/trampoline-credential-helper.ts:153-165
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
``` [1](#0-0) 

The comment explicitly frames this as a shortcut "without having to resort to making a request ourselves" - i.e., it deliberately bypasses the actual verification step, `isGitHubHost(endpoint)`, that exists later in the same function as the real check:

```ts
// app/src/lib/trampoline/trampoline-credential-helper.ts:172-178
if (credentialUrl.protocol !== 'https:') {
  return 'generic'
}
return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
``` [2](#0-1) 

The `realm="GitHub"` string is entirely attacker-controlled: any HTTPS Git server (arbitrary hostname added by the user as a remote, or a proxy/MITM sitting in front of one) can simply answer authentication challenges with a header containing that literal string. Because the check happens before the real `isGitHubHost` verification and short-circuits with an early `return`, the value computed by the trustworthy check is never reached or used to correct a wrong classification made from untrusted input.

Once `endpointKind` is `'enterprise'`, `getCredential()` takes the "trusted GitHub host" branch:

```ts
// app/src/lib/trampoline/trampoline-credential-helper.ts:109-125
if (
  endpointKind !== 'generic' &&
  !accounts.some(a => a.endpoint === apiEndpoint)
) {
  if (getIsBackgroundTaskEnvironment(token)) {
    debug('background task environment, skipping prompt')
    return undefined
  }
  const account = await ui.promptForGitHubSignIn(endpoint)
  ...
}
``` [3](#0-2) 

For any endpoint that has no existing matching account, this triggers `ui.promptForGitHubSignIn(endpoint)` with `endpoint` derived directly from the attacker's server URL — a GitHub-branded sign-in flow is invoked for a host the user never indicated was a GitHub Enterprise server. This is a break in the "not-generic implies verified GitHub host" invariant the rest of `getCredential`/`storeCredential`/`eraseCredential` rely on (e.g., `storeCredential` and `eraseCredential` refuse to touch generic-credential storage for anything classified `!== 'generic'`, trusting the same unverified classification).

### Impact Explanation
This falls under "unauthorized OAuth or account binding": a user adding/cloning from a non-GitHub Git remote (which they may believe is just a generic Git host, e.g. a self-hosted Gitea/GitLab-alike or intranet server) can have GitHub Desktop pop a GitHub/GHE sign-in prompt scoped to that attacker-controlled host purely because the server lied in its `WWW-Authenticate` header. Depending on how `promptForGitHubSignIn`/the underlying OAuth device flow resolves the authorization host from the supplied `endpoint`, this can be leveraged to phish the user into initiating an OAuth/PAT sign-in against an attacker-chosen server while Desktop's UI implies GitHub-branded trust, or to have Desktop persist an "enterprise" account entry keyed to that endpoint. It also silently disables the intended generic-credential-store path (`storeCredential`/`eraseCredential` skip generic storage for non-generic classification), meaning any credentials the user does end up entering never get safely stored/managed as generic credentials.

### Likelihood Explanation
High for the classification bypass itself: any server the client talks to over HTTPS controls its own HTTP response headers, and Git faithfully forwards `WWW-Authenticate` values to the credential helper — no special network position or privileges are required beyond the user configuring/cloning from an attacker's URL (which is squarely in scope: "a git remote/proxy response" attacker model). The remaining question of exact end-user impact (what URL the resulting sign-in flow authorizes against) depends on `trampolineUIHelper.promptForGitHubSignIn`'s implementation, which was not fully inspected in this review — that part is not fully verified.

### Recommendation
Do not trust the `wwwauth[...]` header value as authoritative proof of a GitHub/GHE host. Either remove the header-based shortcut entirely and always fall back to the authenticated `isGitHubHost(endpoint)` check, or use the header only as a hint to *skip* the network round trip when the result would be `'generic'`/negative, while always requiring `isGitHubHost()` verification before ever classifying an endpoint as `'enterprise'` and invoking `ui.promptForGitHubSignIn`.

### Proof of Concept
1. Attacker stands up an HTTPS Git server at `https://evil.example.com/some/repo.git` (a plain generic server, not a real GitHub Enterprise instance).
2. Victim adds this as a remote/clones it in GitHub Desktop; Desktop invokes `git` which contacts the server for HTTP Basic auth.
3. The attacker's server responds to the auth challenge with `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this to the `desktop` credential helper as `wwwauth[0]=Basic realm="GitHub"`.
5. `getEndpointKind()` matches `v.includes('realm="GitHub"')` and returns `'enterprise'` without ever calling `isGitHubHost()`.
6. Since no account matches `apiEndpoint` for `evil.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`, presenting a GitHub-style sign-in flow scoped to the attacker's host instead of treating the remote as a generic Git server requiring a normal username/password prompt.
