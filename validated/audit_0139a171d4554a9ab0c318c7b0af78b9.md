### Title
Unverified `ReceivedOutput` offset lets an attacker claim unspendable outputs as received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The ReferralFeeReceiver bug class is "a user-supplied object is trusted without verifying it was produced by the system's trusted construction path, so its reported properties are attacker-chosen and decoupled from the recorded state." In `ReferralFeeReceiver`, `mooniswap.getTokens()` returned whatever token the attacker wanted at claim time versus freeze time.

In bitcoin-serai, `ReceivedOutput` is the analogous object: it pairs a Taproot `script_pubkey` (`output`) with a scalar `offset` that claims `key + G*offset` derives that script. `Scanner` only ever produces `ReceivedOutput`s where this invariant holds — `register_offset` computes `p2tr_script_buf(self.key + G*offset)` and `scan_transaction` matches `output.script_pubkey` against that map [1](#0-0) . However, `ReceivedOutput::read` deserializes `offset`, `output`, and `outpoint` from untrusted bytes with no check whatsoever that `p2tr_script_buf(key + G*offset) == output.script_pubkey` [2](#0-1) . Like the unverified `mooniswap` address, the provenance of this object is never enforced.

### Finding Description
`ReceivedOutput` has three independent fields: `offset: Scalar`, `output: TxOut`, `outpoint: OutPoint`. The only place the semantic binding between them is established is inside `Scanner::register_offset`/`scan_transaction`, which produces them correctly for a known `key`. `ReceivedOutput::read` (the deserialization path for untrusted bytes, per `read_F`/`TxOut::consensus_decode`/`OutPoint::consensus_decode`) performs no such binding:

- `offset` is any valid `Secp256k1` scalar (`Secp256k1::read_F`).
- `output` is any valid `TxOut` — including a `script_pubkey` paying to a completely unrelated key, an arbitrary script path, or a provably unspendable script.
- `outpoint` is any `OutPoint` — including one that doesn't exist or belongs to an unrelated output.

The consumer (`send.rs`, gated on `#[cfg(feature = "std")]` in the same module) uses `offset` to re-key the threshold keys per input when signing the spend. If the attacker-controlled `offset` does not match `output.script_pubkey`, the wallet reports the output as received and attempts to spend it, but the resulting signature cannot satisfy the script — the "funds" are not spendable by the group. This is the direct analog of `claimFrozenEpoch` paying out `DAI` based on balances recorded for `ATTK`: the checkout path acts on a different claimed identity than the recording path established.

### Impact Explanation
An unprivileged party who can feed bytes into `ReceivedOutput::read` can cause the wallet to treat arbitrary outputs — or nonexistent/misattributed outpoints — as spendable funds belonging to the threshold group. The result is funds reported as received that are not actually spendable, and a signing operation invoked over inputs whose true controlling key does not match the applied offset, producing an invalid transaction and blocking legitimate spends built on those phantom inputs (per-input re-keying fails for every mismatched input in a batch).

### Likelihood Explanation
Reachability is by design: `ReceivedOutput::read` exists precisely to ingest externally supplied output records. No authentication, provenance tag, or binding to the `Scanner`'s key is embedded in the serialization (`write`/`serialize` emit only the three raw fields) [3](#0-2) . Any transport, coordinator, or peer that supplies these records can substitute them. Severity is bounded by the fact that the damage is misattribution/unspendability rather than direct theft — analogous in spirit, though weaker than the full drain in the original report — so this rates Medium.

### Recommendation
Bind the offset to the output at construction and deserialization:

- In `ReceivedOutput::read` (or a `verify(&key)` method called on it), recompute `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset)` and reject the record unless it equals `output.script_pubkey` — the same "verify the supplied object was produced by the trusted factory" fix recommended for `mooniswap`.
- Consider carrying the registered `Scanner`'s expected script set (or a checksum keyed by it) in the serialized record so mismatched-offset records are rejected before reaching the signing path in `send.rs`.

### Proof of Concept
1. Attacker constructs bytes: `offset = O` (arbitrary scalar), `output = TxOut { value: V, script_pubkey: <attacker's own P2TR or arbitrary script> }`, `outpoint = <any outpoint>`, serialized via the `ReceivedOutput` wire format.
2. Wallet calls `ReceivedOutput::read` — succeeds, since no binding is checked.
3. Wallet reports a received output of value `V` (via `output()`/`value()`/`outpoint()` accessors) even though `O` does not derive `script_pubkey` under the group's key.
4. When the spend is built, the per-input key tweak uses `O`; the signature produced cannot satisfy `output.script_pubkey`, so the reported funds are unspendable and the transaction is invalid.

Note on uncertainty: I verified `ReceivedOutput::read`, `Scanner::register_offset`, `Scanner::scan_transaction`, and the serialization format directly; I did not fully read `networks/bitcoin/src/wallet/send.rs` (only confirmed it references `register_offset`-style offset usage via grep), so the exact signing-path consumption of `offset` is inferred from the documented design rather than fully traced.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }
