### Title
Native-token overpayment for cross-chain dispatch fees becomes permanently stranded in `EvmHost` - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept `msg.value` and swap it for an *exact* amount of `feeToken` (`post.fee`/`get.fee`) via a configurable `uniswapV2` wrapper. Any leftover native token from that swap is refunded, but the refund target is `msg.sender` **as seen by the wrapper**, which is `EvmHost` itself (since `EvmHost` is the caller of the wrapper), not the original user who sent the overpaying transaction. In the Gnosis wrapper the entire `msg.value` (not just `post.fee`) is converted and credited to `EvmHost`'s own address. In either case, any native-token amount beyond the exact fee required is absorbed into `EvmHost`'s balance and is never returned to the payer nor accounted for against any request commitment — mirroring the reported Trading.sol pattern where `msg.value` is only used in one code path and otherwise sits stuck in the contract.

### Finding Description
`EvmHost.dispatch(DispatchPost)` [1](#0-0)  does:
```solidity
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
} else if (post.fee > 0) {
    IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
}
```
Only `post.fee` is ever recorded against the request in `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})` [2](#0-1) . The same pattern repeats for `dispatch(DispatchGet)` [3](#0-2) .

The actual behavior of the swap depends on the configured `uniswapV2` wrapper:

- `GnosisUniswapV2Wrapper.swapETHForExactTokens` converts **the full `msg.value`** (not just `amountOut`) to `WETH`/`WXDAI` and sends it all to `msg.sender` (i.e. `EvmHost`): [4](#0-3) . Any excess beyond `post.fee` becomes an unaccounted `feeToken` balance sitting in `EvmHost` forever — no commitment references it and there's no per-payer bookkeeping for it.
- `UniV3UniswapV2Wrapper.swapETHForExactTokens` does refund the unspent portion, but the refund is sent back to `msg.sender`, which from the wrapper's perspective is `EvmHost` itself (the entity that invoked the wrapper with `{value: msg.value}`), not the original transaction sender who overpaid: [5](#0-4) . This relocates the surplus from native ETH sent by the user into native ETH permanently held by `EvmHost`.

In neither branch does `EvmHost` return the unspent difference to `_msgSender()` (the actual dispatch caller), and the documentation itself instructs callers to just forward `msg.value` without guaranteeing exact-fee sizing: [6](#0-5) . Because the exact quoted fee (via Uniswap pricing) can shift between the client-side quote and on-chain execution, or because integrators (as shown across `HyperFungibleToken.sol`, `WrappedHyperFungibleToken.sol`, `IntentGatewayV2.sol`, `HyperbridgeLzEndpoint.sol`) commonly forward the caller's *entire* `msg.value` into `dispatch{value: msg.value}(...)` without first subtracting the exact required fee, any positive slippage or overestimation results in funds being irrecoverably absorbed by `EvmHost`.

### Impact Explanation
This is a direct loss-of-funds bug: end users (or intermediate app contracts forwarding user funds) who supply more native token than the exact dispatch fee lose the difference with no recovery path, since:
1. The excess is not tracked in any `FeeMetadata`/commitment structure, so it cannot be claimed via the existing timeout-refund path (`dispatchTimeOut`, which only refunds `meta.fee`) [7](#0-6) .
2. There is no user-facing withdrawal function for this stranded balance in `EvmHost.sol`'s dispatch/fee logic path, meaning overpaid ETH/feeToken accumulates in the contract permanently, unattributable to the original payer.

This satisfies the "loss of funds" bucket of the bounty scope and requires no malicious relayer, prover, or admin — only a normal user or normal integrator contract forwarding `msg.value` in the documented way.

### Likelihood Explanation
High: the documented usage pattern explicitly tells integrators to call `dispatch{value: msg.value}(post)` [6](#0-5) , and this exact pattern is replicated across production app contracts (`HyperFungibleToken.send`, `WrappedHyperFungibleToken.send`, `IntentGatewayV2` fill/cancel flows, `HyperbridgeLzEndpoint.send`) that forward `msg.value` without first computing/deducting the precise on-chain swap cost. Any mismatch between the quoted fee and swap execution price (which is expected with an AMM-based swap under normal price movement) triggers fund loss on every affected dispatch call, not just an edge case.

### Recommendation
- In `EvmHost.dispatch(DispatchPost)`/`dispatch(DispatchGet)`, after the swap, compute the actual native amount spent and refund any unspent `msg.value` directly to `_msgSender()` (the original caller), not rely on the wrapper's internal refund-to-caller semantics.
- Fix `GnosisUniswapV2Wrapper.swapETHForExactTokens` to only convert/forward `amountOut`, refunding the remainder of `msg.value` to the true originating caller.
- Add an explicit accounting mechanism (or a `withdrawExcessFee`/sweep function) so any historically stranded native/feeToken balance in `EvmHost` can be recovered by its rightful payer, and add off-chain/on-chain checks so integrators don't need to overpay before the exact swap price is known.

### Proof of Concept
1. A user calls an app's `send(...)`/`fillOrder(...)` function which forwards `msg.value` into `IDispatcher(host).dispatch{value: msg.value}(request)`, e.g. `WrappedHyperFungibleToken.send` [8](#0-7) .
2. `EvmHost.dispatch(DispatchPost)` receives `msg.value > post.fee`'s worth of native token (e.g., due to client-side quote slippage) and calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`.
3. On Gnosis, the wrapper wraps and forwards the entire `msg.value` (not `post.fee`) to `EvmHost`, permanently crediting the surplus `feeToken` to `EvmHost`'s own balance with no commitment tracking it.
4. On a UniV3/V4-wrapper chain, unspent ETH is refunded to `msg.sender`=`EvmHost`, meaning `EvmHost`'s own ETH balance permanently grows by the overpaid amount with no function to return it to the original payer.
5. Repeating this across many dispatch calls accumulates unrecoverable user funds inside `EvmHost`, confirmed by the absence of any commitment-level accounting for amounts beyond `post.fee`/`get.fee` in `_requestCommitments`.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory)
    {
        address weth = _params.WETH;
        if (path[0] != weth) revert InvalidWethAddress();

        (bool sent,) = weth.call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IV3SwapRouter.ExactOutputSingleParams memory params = IV3SwapRouter.ExactOutputSingleParams({
            tokenIn: weth,
            tokenOut: path[1],
            fee: _params.maxFee,
            recipient: recipient,
            amountOut: amountOut,
            amountInMaximum: msg.value,
            sqrtPriceLimitX96: 0
        });

        bytes memory swapCall = abi.encodeWithSelector(IV3SwapRouter.exactOutputSingle.selector, params);

        bytes[] memory data = new bytes[](1);
        data[0] = swapCall;

        bytes[] memory results = IMulticallExtended(_params.swapRouter).multicall(deadline, data);
        uint256 spent = abi.decode(results[0], (uint256));

        if (spent < msg.value) {
            uint256 refund = msg.value - spent;
            IWETH(weth).withdraw(refund);

            (bool success,) = msg.sender.call{value: refund}("");
            if (!success) revert RefundFailed();
        }

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
