### Title
CW721-to-ERC721 pointer only exposes an unsafe `transferFrom`, and inherited `safeTransferFrom` is unusable — leading to permanent NFT freezing - ([File: contracts/src/CW721ERC721Pointer.sol])

### Summary
`CW721ERC721Pointer` is an EVM ERC721 façade over a CosmWasm CW721 collection, reachable by any EVM account/contract that calls its public transfer functions. It overrides `transferFrom` to forward `transfer_nft` to the CW721 contract with no check that the recipient can actually receive/handle the token, while `safeTransferFrom` (inherited from OpenZeppelin's `ERC721`) is silently broken because the pointer never maintains the OZ internal storage (`_owners`/`_tokenApprovals`) that OZ's `safeTransferFrom`/`_isApprovedOrOwner`/`_transfer` rely on.

### Finding Description
`CW721ERC721Pointer` overrides only the state-changing entry points `transferFrom`, `approve`, and `setApprovalForAll`, and the view functions `balanceOf`, `ownerOf`, `getApproved`, `isApprovedForAll`, all of which proxy to the CW721 contract via the wasmd precompile: [1](#0-0) 

It does not override `safeTransferFrom`, `_ownerOf`, `_isApprovedOrOwner`, `_update`/`_transfer`, `_mint`, `_approve`, or `_setApprovalForAll`. Because the contract never calls `_mint`, `_approve`, or `_setApprovalForAll` internally (all real state lives in the CW721 wasm contract, not in the OZ base contract's storage), OpenZeppelin's default `safeTransferFrom` — which internally checks ownership/approval against the OZ base contract's own `_owners`/`_tokenApprovals` mappings before performing an internal `_transfer` — always operates on empty internal state. This causes `safeTransferFrom` calls on the pointer to fail authorization checks unconditionally, since the internal (unused) owner for any `tokenId` is always `address(0)`.

As a direct consequence, the only usable transfer path on this pointer is the raw, unsafe `transferFrom` at [2](#0-1) , which sends the underlying CW721 token to the Sei address associated with `to` without verifying `to` (when it is a contract) can do anything meaningful with an ERC721/CW721 asset, and with no `onERC721Received`-style callback or receiver check, mirroring exactly the bug class in the referenced report (raw `transferFrom` instead of `safeTransferFrom` for ERC721).

### Impact Explanation
Any account calling `transferFrom` on `CW721ERC721Pointer` (directly, or via a contract's `transferFrom` call as part of a marketplace/vault/router flow) can move the wrapped CW721 NFT to a contract address that has no way to move it onward (e.g., a contract with no code path to invoke CosmWasm execute on its own behalf, or no EVM<->Sei address association usable for signing). Because the safe variant is non-functional, callers have no alternative to explicitly guard against sending to such addresses. This results in a real fund-loss/permanent-freezing condition — the NFT becomes stuck, unable to be retrieved by the depositor or by the destination address — matching the "Accept" criteria of permanent freezing.

### Likelihood Explanation
Likelihood is significant because `transferFrom` is the primary, and effectively only, working transfer entry point exposed by the pointer; any integrator or user relying on the ERC721 `safeTransferFrom` semantics (a very common assumption for ERC721-compliant contracts) will either get an unexpected revert (DoS on transfers to any address) or, if they/other contracts fall back to `transferFrom`, silently expose users to permanent asset loss when transferring to non-cooperative contract addresses. This requires no special privilege — any transaction sender or contract holding/approved for the pointer NFT can trigger it.

### Recommendation
- Override `safeTransferFrom` (both variants) in `CW721ERC721Pointer` to perform the same CW721 `transfer_nft` execution as `transferFrom`, followed by an explicit `to.code.length == 0 || IERC721Receiver(to).onERC721Received(...) == selector` check, mirroring the pattern already used correctly elsewhere in the repo's `ERC721.sol` reference implementation at [3](#0-2) .
- Alternatively/additionally, add the same receiver-capability check directly inside `transferFrom` so the unsafe path cannot be used to send to non-ERC721Receiver contracts at all.

### Proof of Concept
1. Deploy/register a `CW721ERC721Pointer` for an existing CW721 collection (as done via `AddCW721`/`registerPointerForERC721`), see [4](#0-3) .
2. As the NFT owner, call `pointer.safeTransferFrom(owner, recipient, tokenId)` — this reverts because the internal `_isApprovedOrOwner` check operates on the unused OZ storage (owner is `address(0)` internally), even though `ownerOf`/`transferFrom` correctly show the caller as the true owner via the CW721 query, as demonstrated by the plain `transferFrom` test flow at [5](#0-4) .
3. As a result, the only usable transfer path is `pointer.transferFrom(owner, contractRecipient, tokenId)`, which moves the token to `contractRecipient`'s associated Sei address without any receiver check. If `contractRecipient` cannot independently execute a CW721 `transfer_nft`/`send`/EVM `transferFrom` call (e.g., no logic to interact with the pointer or CW721 contract), the NFT is permanently stuck in that address with no recovery path.

    function transferFrom(address from, address to, uint256 tokenId) public override {
        if (to == address(0)) {
            revert ERC721InvalidReceiver(address(0));
        }
        require(from == ownerOf(tokenId), "`from` must be the owner");
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
        _execute(bytes(req));
    }
