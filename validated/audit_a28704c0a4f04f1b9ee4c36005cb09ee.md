### Title
Sybil self-referral via `ReferralStorage.registerCode`/`useCode` allows an attacker to farm referral bonuses and drain the shared MGP reward reserve - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage.useCode` only blocks a user from using their own code directly (`codeOwners[_code] == msg.sender` check), but does nothing to prevent one attacker from controlling two addresses (A registers a code, B uses it). When B performs ordinary staking/claiming through `MasterMagpie`, `trigger()` credits both `refererInfo.rewardAmount` (A) and `refereeInfo.rewardAmount` (B) — both fully controlled by the same attacker — funded from `ReferralStorage`'s single shared MGP balance meant for genuine referrer/referee pairs.

### Finding Description
`useCode` at [1](#0-0)  only reverts with `Circled()` if `codeOwners[_code] == msg.sender`, i.e. it prevents a single address from referring itself, but it has no way (nor could it, on-chain) to detect that address B and the code owner A are controlled by the same person. `registerCode` at [2](#0-1)  lets any address freely register an arbitrary unused code.

Once B is linked to A via `myReferer[B] = A`, any real staking/claim activity by B in `MasterMagpie` — even using capital B fully controls and later gets back — will route through `_multiClaim`, which computes `totalReward` from B's own accrued MGP emissions and then calls `IReferralStorage(referral).trigger(_user, totalReward)` at [3](#0-2) .

Inside `trigger`, both a "referer" bonus for A and a "referee" bonus for B are computed as a percentage of `_amount` and added to `userInfos[A].rewardAmount` and `userInfos[B].rewardAmount` respectively: [4](#0-3) . These reward balances are later paid out via `claimReward`, which transfers directly from the contract's own MGP token balance: [5](#0-4) .

There is no per-referral-pair earmarked reserve — `claimReward` draws from `ReferralStorage`'s single pooled `MGP` balance (`MGP.safeTransfer(msg.sender, userInfo.rewardAmount)`), which must be funded by the protocol/owner in advance for all legitimate referrer payouts. Because nothing stops A and B from being the same attacker, the attacker can manufacture an unlimited number of "self-referral" pairs, each time B stakes/claims through `MasterMagpie` with capital it fully controls, and receive an unearned bonus (`refererAmount` + `refereeAmount`) on top of the reward it would have received anyway — funded from the same finite pool intended to pay real, distinct referrers. This depletes the shared reserve, at the expense of legitimate referrers who registered codes for actual third parties.

### Impact Explanation
This is a theft-of-unclaimed-yield / protocol-insolvency issue against the referral reward reserve: the attacker extracts MGP tokens from `ReferralStorage`'s shared balance without any real distinct-party referral relationship, reducing (or exhausting) the funds available to legitimate referrers who registered codes used by genuine, unrelated referees. Since `claimReward` will revert with `InsufficientRewardBalance` once the pooled MGP is depleted, this can also result in legitimate referrers being permanently unable to claim earned rewards.

### Likelihood Explanation
The attack requires only unprivileged capabilities: deploying two addresses, calling `registerCode`/`useCode` (both external, no access control beyond the trivial self-code check), and performing ordinary staking/claim flows in `MasterMagpie` with the attacker's own capital. It is fully repeatable — the attacker can create arbitrarily many A/B pairs (or reuse the same pair repeatedly across staking cycles) to keep extracting bonus MGP as long as the pool has funds, at essentially zero net capital cost beyond gas, since staked principal is returned to the attacker.

### Recommendation
Referral bonus rewards should not be funded from an unbounded shared pool that is also relied upon by unrelated legitimate referrers without any Sybil-resistance or economic disincentive. Consider: (1) requiring a minimum time-locked, non-recoverable stake or KYC/whitelisting for code registration, (2) capping/rate-limiting bonus accrual per referrer-referee pair relative to independently verifiable distinct activity, or (3) funding referral rewards from a per-referrer allocation set by governance rather than a single shared MGP balance, so that Sybil self-referral cannot dilute rewards owed to unrelated referrers.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `vlMGP`, `ReferralStorage`, MGP token; fund `ReferralStorage` with MGP as the protocol would for legitimate referral payouts.
2. From address A (attacker EOA #1): call `ReferralStorage.registerCode(codeA)`.
3. From address B (attacker EOA #2): call `ReferralStorage.useCode(codeA)`; assert `myReferer[B] == A`.
4. From B: stake MGP/LP into `MasterMagpie` using attacker-owned capital, advance time to accrue emissions, then call the claim function that triggers `_multiClaim`.
5. Assert `ReferralStorage.userInfos[A].rewardAmount` and `userInfos[B].rewardAmount` both increased by `refererAmount`/`refereeAmount` proportional to `totalReward`, despite A and B being the same attacker.
6. From A: call `claimReward()` and assert MGP is transferred out of `ReferralStorage`'s balance to A, reducing the shared reserve available for other, unrelated referrers.
7. Repeat steps 3–6 to show the reserve can be drained by repeated self-referral cycles, and demonstrate a legitimate third-party referrer's later `claimReward()` reverting with `InsufficientRewardBalance` due to depletion.

        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
