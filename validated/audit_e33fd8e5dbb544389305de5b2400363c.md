### Title
Unbounded attacker-controlled participant count in `ThresholdKeys::read` enables quadratic-cost deserialization DoS — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts a `u16` `n` (and `t`) from the input byte stream, allocates proportional vectors/maps, reads `n` field elements and `n` group elements, and then runs `ThresholdKeys::new`, which performs participant-indexed interpolation whose cost grows quadratically in `n`. A single untrusted blob of a few MB can drive billions of field operations, matching the unbounded-count denial-of-service class of CVE-2024-28949.

### Finding Description
The Mattermost bug allowed an attacker to submit an unlimited number of records. In Serai, the analogous surface is `ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs:574-632`:

```rust
let (t, n, i) = (read_u16()?, read_u16()?, Participant::new(read_u16()?)...);
// interpolation == 0 => reads `n` F elements (Vec::with_capacity(n))
// then reads `n` verification shares into a HashMap (lines 620-623)
ThresholdKeys::new(ThresholdParams::new(t, n, i)?, interpolation, secret_share, verification_shares)
```

There is no cap on `n`/`t` beyond `u16::MAX` (65535) and `ThresholdParams`' consistency checks (`t <= n`, `i <= n`). The parser will:

1. Allocate `Vec::with_capacity(n)` and a `HashMap` with `n` entries.
2. Call `C::read_F` `n` times and `C::read_G` `n` times — each `read_G` performs point decompression/validation.
3. Call `ThresholdKeys::new`, which derives the group key by interpolating the verification shares for participants `1..=t`. Each interpolation factor evaluation is `O(n)` in the participant set for `Constant`/`Lagrange` interpolation, so deriving the shares/key across `t` participants costs `O(n * t)` field operations — up to ~4.3 billion field multiplications for `t = n = 65535`, triggered by a ~4–5 MB input.

Other in-scope readers impose such limits (`Commitments::read` in `crypto/dkg/pedpop/src/lib.rs:110-128` is bounded by `params.t()`; `Transaction::read` for `DkgCommitments` checks `TRANSACTION_SIZE_LIMIT` in `coordinator/src/tributary/transaction.rs:286`), but `ThresholdKeys::read` has none.

### Impact Explanation
Any component that feeds attacker-influenced bytes to `ThresholdKeys::read` — an explicitly in-scope input surface — lets an unprivileged party pin a CPU core for an extended period and force large transient allocations from a small input. Repeated submissions starve signing/key-recovery flows in validators/processors using this path. This is a resource-exhaustion DoS identical in class to the advisory (CWE-400/CWE-770), with roughly 1000x work amplification (billions of field ops for ~4 MB input).

### Likelihood Explanation
Exploitation requires a path where remote bytes reach `ThresholdKeys::read` (e.g., key material provisioning, recovery, or serialized keys relayed between participants during set recovery/reshare). `Participant::new` rejects index 0 but does not bound `n`. The attack is deterministic, cheap to construct, and requires no key knowledge or collusion — only the ability to deliver a serialized `ThresholdKeys` blob. Likelihood depends on deployment wiring of that input surface; where reachable, exploitation is trivial.

### Recommendation
- Bound `n` (and `t`) in `ThresholdKeys::read` to a protocol-meaningful maximum (e.g., the validator-set size limit) before allocating, mirroring the `TRANSACTION_SIZE_LIMIT` check used for `DkgCommitments`.
- Validate `t <= n <= MAX_PARTICIPANTS` inside `ThresholdParams::new` or at the deserialization boundary.
- Where a size hint is available (expected set size), pass an expected-`n` parameter into `read` and reject mismatches up front.

### Proof of Concept
```rust
// crypto/dkg — conceptual PoC against e.g. Secp256k1
use frost::curve::{Ciphersuite, Secp256k1};
use frost::dkg::ThresholdKeys;

fn main() {
    let mut buf = vec![];
    // C::ID header
    buf.extend(u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes());
    buf.extend(Secp256k1::ID);
    // t = 65535, n = 65535, i = 1
    buf.extend(0xffffu16.to_le_bytes());
    buf.extend(0xffffu16.to_le_bytes());
    buf.extend(1u16.to_le_bytes());
    // interpolation = Constant with n coefficients
    buf.push(0u8);
    let zero = <Secp256k1 as Ciphersuite>::F::ZERO.to_repr();
    for _ in 0 .. 0xffffu16 { buf.extend(zero.as_ref()); }
    // secret share
    buf.extend(zero.as_ref());
    // n verification shares (generator bytes repeated)
    let g = <Secp256k1 as Ciphersuite>::generator().to_bytes();
    for _ in 0 .. 0xffffu16 { buf.extend(g.as_ref()); }

    // ~4.3 MB input => allocation of 65535-entry Vec + HashMap, 65535 point
    // decompressions, then O(n * t) interpolation work inside ThresholdKeys::new
    let _ = ThresholdKeys::<Secp256k1>::read(&mut buf.as_slice());
}
```
