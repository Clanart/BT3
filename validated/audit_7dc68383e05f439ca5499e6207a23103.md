## Title
Automatic SSH host-key trust for GitHub.com relies on a hardcoded, superseded (compromised) RSA fingerprint - (File: `app/src/lib/trampoline/trampoline-askpass-handler.ts`)

### Summary
GitHub Desktop auto-answers SSH's "authenticity of host … can't be established" prompt with `yes` — silently adding the host key to `known_hosts` without any user confirmation — whenever the presented key type is `RSA` and its fingerprint exactly equals a single hardcoded string, `SHA256:nThbg6kXUpJWGl7E1IGOCspRomTxdCARLviKw6E5SY8`. This is exactly the "fixed value used unconditionally instead of validating dynamically" pattern from the report: instead of consulting an up-to-date/authoritative source (or at minimum prompting the user), Desktop trusts one baked-in constant forever.

### Finding Description
`handleSSHHostAuthenticity` in `app/src/lib/trampoline/trampoline-askpass-handler.ts` parses the SSH askpass prompt and, for `github.com`, compares the offered RSA key fingerprint against a single hardcoded constant: [1](#0-0) 

If it matches, the function returns `'yes'` and the trampoline answers the SSH client's host-authenticity prompt automatically — see the dispatch in `createAskpassTrampolineHandler`: [2](#0-1) 

Otherwise the user is prompted via `promptAddingSSHHost` / the `AddSSHHost` dialog, which shows the fingerprint and asks the user to confirm: [3](#0-2) 

The broken invariant: the hardcoded fingerprint `SHA256:nThbg6kXUpJWGl7E1IGOCspRomTxdCARLviKw6E5SY8` is GitHub's **old** RSA host key, which GitHub publicly rotated away from in March 2023 after that private key was briefly exposed in a public repository. GitHub's current RSA host key fingerprint is different (`SHA256:uNiVztksCsDhcc0u9e8BujQXVUpKZIDTMczCvj3tD1o`). Just like the Uniswap report's hardcoded fee tier that stopped matching the actual optimal/valid pool, this hardcoded fingerprint no longer matches GitHub's actual current key — but rather than simply causing an inefficiency, it stays wired to accept the specific fingerprint of a key that was exposed to the public. Anyone who retained a copy of that formerly-public private key can present it as `github.com`'s host key during an SSH MITM (e.g. via DNS spoofing, ARP poisoning, malicious proxy/VPN, or captive-portal interception), and Desktop's askpass handler will silently answer `yes`, add the attacker's key to `known_hosts`, and proceed with the SSH session — with zero user-visible warning, since the code path that would show the `AddSSHHost` confirmation dialog is bypassed entirely.

### Impact Explanation
An attacker positioned as a network MITM for a victim's SSH traffic to `github.com` (or who controls a proxy the victim configured) can supply the old, once-publicly-exposed RSA key. Desktop auto-trusts it, so subsequent `git fetch`/`clone`/`push` traffic over SSH for that connection is silently subject to interception/tampering — allowing an attacker to serve malicious repository content on fetch/clone (supply-chain injection into what the user later builds/reviews) or manipulate what gets pushed, without any host-key warning dialog the user could catch. This satisfies the valid-impact criteria: attacker controls a git remote/proxy response, resulting in silent corruption of what the user clones/pushes, without requiring local access, admin rights, or prior malware.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to be capable of intercepting/spoofing the victim's SSH traffic to `github.com` (network MITM, malicious Wi-Fi/proxy, DNS/ARP spoofing) and to possess the old exposed RSA private key, which was public for a period before GitHub's 2023 rotation and thus may still circulate. The check only inspects `keyType === 'RSA'` and a single fixed fingerprint string, so no additional identity binding (e.g. current key material, IP, or timestamp) constrains it — there is no mechanism to ever retire this hardcoded trust once GitHub rotates keys again.

### Recommendation
Do not hardcode a single accepted fingerprint. Instead, dynamically fetch/verify GitHub's currently published host key fingerprints (e.g., via GitHub's `/meta` API `ssh_keys` field over HTTPS, or a periodically-updated, signed list bundled with app updates) rather than trusting one baked-in value indefinitely. At minimum, retire superseded fingerprints from the trusted set as soon as they're rotated by GitHub, mirroring the report's fix of using "the fee/value from a previously accepted, validated source" instead of a stale hardcoded constant.

### Proof of Concept
1. Attacker positions themselves as a network MITM for a victim configured to use SSH remotes (e.g. `git@github.com:owner/repo.git`), for example via a rogue Wi-Fi AP, ARP spoofing, or a malicious SSH-capable proxy.
2. Attacker's SSH server presents the old GitHub RSA host key (public before GitHub's March 2023 rotation), which still produces fingerprint `SHA256:nThbg6kXUpJWGl7E1IGOCspRomTxdCARLviKw6E5SY8`.
3. Victim performs a `git fetch`/`clone`/`push` in GitHub Desktop against `github.com` over SSH; the underlying `ssh` invokes Desktop's askpass trampoline with the "authenticity of host 'github.com …' can't be established … RSA key fingerprint is SHA256:nThbg6kXUpJWGl7E1IGOCspRomTxdCARLviKw6E5SY8" prompt.
4. `handleSSHHostAuthenticity` matches the hardcoded string and returns `'yes'` automatically — no `AddSSHHost` dialog is ever shown to the victim, and the attacker's key is accepted/added to `known_hosts`.
5. All subsequent SSH traffic for that session is now MITM'd by the attacker, who can serve altered repository objects on clone/fetch or capture/alter push traffic.
