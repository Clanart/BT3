### Title
Reward-backlog can be captured by a single-wei staker after totalSupply is driven to zero - ([File: rewards/DelegateVoteRewardPool.sol])

### Summary
`DelegateVoteRewardPool.totalSupply` tracks vlMGP delegated to the `delegatedPool` slot in `WombatBribeManager`, and is mutated only through the permissionless `vote()`/`unvote()` entry points (`stakeFor`/`withdrawFor`). If the sole (or last) voter for `delegatedPool` unvotes fully, `totalSupply` hits zero while `harvestAll()` remains callable by anyone, causing accrued bribe rewards to pile into `rewardInfo.queuedRewards` instead of being distributed. When the attacker subsequently restakes a trivial amount (1 wei of vote), the next reward-queueing call folds the *entire* backlog into `rewardPerTokenStored` divided by that trivial `totalSupply`, letting the attacker claim essentially all previously-queued yield.

### Finding Description
`_queueNewRewardsWithoutTransfer` in `DelegateVoteRewardPool.sol` implements the classic zero-totalSupply reward bucket pattern: [1](#0-0) 

When `totalSupply == 0`, new rewards accumulate in `rewardInfo.queuedRewards` with no cap and no vesting; when `totalSupply` becomes non-zero again, the *whole* backlog is dumped at once into `rewardPerTokenStored`, scaled only by the `totalSupply` at that instant.

`totalSupply`/`_balances` are driven purely by `WombatBribeManager.vote()`/`unvote()`, which are public, unprivileged functions gated only by the caller's own vlMGP voting power: [2](#0-1) 

Because `msg.sender != delegatedPool` gating only affects `userTotalVotedInVlmgp`/`totalVlMgpInVote` bookkeeping (not the rewarder's `stakeFor`/`withdrawFor` calls), any vlMGP holder who is (or becomes, e.g. by being the only remaining participant) the sole voter routed to `delegatedPool` can call `unvote(delegatedPool)` and drive `DelegateVoteRewardPool.totalSupply` to exactly zero.

`harvestAll()` is external and has no access control or `totalSupply` guard: [3](#0-2) 

Bribes claimed from `claimAllBribes` reflect on-chain votes previously cast to underlying LPs (independent of the current `totalSupply` of the delegate pool), so bribes continue to be harvestable and get force-queued while `totalSupply == 0`. Once the attacker re-votes even 1 wei to `delegatedPool` (calling `stakeFor(attacker, 1)` via `vote()`), the next `_queueNewRewardsWithoutTransfer` invocation folds the entire `queuedRewards` backlog into `rewardPerTokenStored` scaled by `totalSupply = 1`, and the attacker calls `getReward`/`claimAllBribes` to withdraw essentially the full backlog that was economically earned by prior, larger delegators.

No modifier, snapshot, or vesting mechanism prevents this; `updateRewards` only synchronizes `userRewardPerTokenPaid` at stake/withdraw time and does not protect against the backlog-dump-on-refill pattern.

### Impact Explanation
This is a theft of unclaimed yield: bribe rewards that economically belong to (or would have been distributed pro-rata among) all prior delegators to `delegatedPool` are misappropriated by a single attacker who re-stakes a negligible amount at the right moment. This matches the Immunefi "theft of unclaimed yield" impact class for reward-pool contracts.

### Likelihood Explanation
Feasibility depends on the attacker being able to bring `DelegateVoteRewardPool.totalSupply` to exactly zero, which requires being the sole (or last) active voter routed to `delegatedPool`, or coordinating/waiting for all other delegators to withdraw. The prompt's stated precondition ("attacker controls enough vlMGP to be the sole voter routed through delegatedPool") is required — this is not automatically guaranteed in production where multiple independent delegators may hold non-trivial balances simultaneously. Given that precondition holds, the rest of the exploit chain (`unvote` → wait/harvest → `vote` 1 wei → `getReward`) uses only public, unprivileged calls and is fully repeatable each time `totalSupply` returns to zero.

### Recommendation
Do not allow the entire `queuedRewards` backlog to be attributed based on an arbitrarily small post-zero `totalSupply`. Options: require a minimum `totalSupply` threshold before releasing queued rewards, vest/distribute queued rewards linearly over time rather than as an instant lump sum, or snapshot/checkpoint `queuedRewards` distribution against the balances that were staked when the rewards were originally earned (e.g., via a per-epoch accounting model rather than a single global `rewardPerTokenStored`).

### Proof of Concept
Foundry test plan:
1. Deploy `DelegateVoteRewardPool` wired to a mock `WombatBribeManager`/mock bribe source; register it as `delegatedPool`.
2. Have delegator A `vote()` a large vlMGP amount to `delegatedPool` (sets `totalSupply = N`).
3. Simulate bribe accrual, call `harvestAll()` once to establish baseline (rewards should distribute pro-rata to A here — sanity check).
4. Have A fully `unvote(delegatedPool)`, asserting `DelegateVoteRewardPool.totalSupply() == 0`.
5. Simulate further bribe accrual and call `harvestAll()` one or more times; assert `rewards[token].queuedRewards` grows and `rewardPerTokenStored` does not change (since `totalSupply == 0`).
6. Attacker calls `vote()` with `delta = 1` wei routed to `delegatedPool` (`stakeFor(attacker, 1)`), setting `totalSupply = 1`.
7. Call `harvestAll()` again (or trigger any path invoking `_queueNewRewardsWithoutTransfer`); assert `rewardInfo.queuedRewards` resets to 0 and `rewardPerTokenStored` jumps by `backlogAmount * 10**decimals / 1`.
8. Attacker calls `getReward(attacker)`/`claimAllBribes(attacker)`; assert attacker receives (approximately) the full backlog amount despite holding only 1 wei of stake, while previous stakers who actually earned the underlying bribes receive nothing further.

    function vote(address[] calldata _lps, int256[] calldata _deltas) override public {
        if (_lps.length != _deltas.length)
            revert LengthMismatch();

        uint256 length = _lps.length;
        int256 totalUserVote;

        for (uint256 i; i < length; i++) {
            Pool storage pool = poolInfos[_lps[i]];
            if (!pool.isActive)
                revert PoolNotActive();
            int256 delta = _deltas[i];
            totalUserVote += delta;
            if (delta != 0) {
                if (delta > 0) {
                    pool.totalVoteInVlmgp += uint256(delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] += uint256(delta);
                    IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta));
                } else {
                    pool.totalVoteInVlmgp -= uint256(-delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] -= uint256(-delta);
                    IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(-delta), false);
                }
            }
        }

        if (msg.sender != delegatedPool) {
            if (totalUserVote > 0) {
                userTotalVotedInVlmgp[msg.sender] += uint256(totalUserVote);
                totalVlMgpInVote += uint256(totalUserVote);
            } else {
                userTotalVotedInVlmgp[msg.sender] -= uint256(-totalUserVote);
                totalVlMgpInVote -= uint256(-totalUserVote);
            }
        }

        if (userTotalVotedInVlmgp[msg.sender] > getUserVotable(msg.sender))
            revert NotEnoughVote();
    }

    /// @notice Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing
    function unvote(address _lp) public {
        Pool storage pool = poolInfos[_lp];
        uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
        if(!pool.isActive)
            revert PoolNotActive();
        
        pool.totalVoteInVlmgp -= uint256(currentVote);
        userTotalVotedInVlmgp[msg.sender] -= uint256(currentVote);
        userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] = 0;
        if (msg.sender != delegatedPool) {
            totalVlMgpInVote -= currentVote;
        }
        
        IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(currentVote), true);
    }
