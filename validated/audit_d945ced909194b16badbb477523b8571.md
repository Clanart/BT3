### Title
Missing caller-authorization check in `CW721ERC721Pointer.transferFrom` allows any account to steal any wrapped CW721 NFT - ([File: contracts/src/CW721ERC721Pointer.sol])

### Summary
`CW721ERC721Pointer.transferFrom(address from, address to, uint256 tokenId)` only checks that `from` is the current owner of `tokenId`; it never verifies that `msg.sender` is `from`, is `getApproved(tokenId)`, or is an approved operator for `from`. Because the pointer forwards the resulting `transfer_nft` CosmWasm message through the wasmd precompile using an "authorized" sender that is resolved from the EVM caller (not from the pointer contract), any arbitrary EVM account can call `transferFrom` naming the real owner as `from` and itself as `to`, and successfully move the NFT out of the real owner's wallet.

### Finding Description
`transferFrom` in `CW721ERC721Pointer.sol` is:
```
function transferFrom(address from, address to, uint256 tokenId) public override {
    if (to == address(0)) { revert ERC721InvalidReceiver(address(0)); }
    require(from == ownerOf(tokenId), "`from` must be the owner");
    ...
    _execute(bytes(req));
}
``` [4](#0-3) 

This is missing the standard ERC721 authorization check (`msg.sender == from || msg.sender == getApproved(tokenId) || isApprovedForAll(from, msg.sender)`) that OpenZeppelin's base `ERC721` and the sibling `CW1155ERC1155Pointer.safeTransferFrom` both enforce [5](#0-4) . `approve`/`setApprovalForAll` in the pointer are implemented (forwarding CW `approve`/`approve_all`/`revoke_all` messages), giving the appearance that approvals are enforced, but `transferFrom` silently bypasses them.

The `_execute` helper performs a `delegatecall` into the wasmd precompile:
```
function _execute(bytes memory req) internal returns (bytes memory) {
    (bool success, bytes memory ret) = WASMD_PRECOMPILE_ADDRESS.delegatecall(
        abi.encodeWithSignature("execute(string,bytes,bytes)", Cw721Address, bytes(req), bytes("[]"))
    );
    ...
}
``` [6](#0-5) 

In `precompiles/wasmd/wasmd.go`, the `execute` handler resolves the CosmWasm `Sender` from `caller` (the EVM address the EVM runtime attributes to the frame, which for a `delegatecall` remains the original transaction caller, not the pointer contract) and explicitly permits delegatecall execution as long as the `callingContract` matches a registered ERC721/ERC20/ERC1155 pointer for the target CW contract:
```
if ctx.EVMPrecompileCalledFromDelegateCall() {
    ...
    erc721pointer, _, erc721exists := p.evmKeeper.GetERC721CW721Pointer(ctx, contractAddrStr)
    ...
    if (!erc721exists || erc721pointer.Cmp(callingContract) != 0) ... { return ... error }
}
...
senderAddr, found := p.evmKeeper.GetSeiAddress(ctx, caller)
...
res, err := p.wasmdKeeper.Execute(ctx, contractAddr, senderAddr, msg, coins)
``` [7](#0-6) [2](#0-1) 

This design intentionally allows the CW `Sender` to be the original EVM caller (so that ownership/approval enforcement is supposed to happen at the underlying CW721 contract or at the Solidity pointer layer). The underlying CW721 contract will accept `transfer_nft` only if `info.sender` is the token owner or an approved spender/operator recorded *in CW721 state*. However, the pointer's `approve`/`setApprovalForAll` write CW721-side approvals keyed to the caller's Sei address (derived from `msg.sender`), and its `transferFrom` never confirms the caller holds such approval before dispatching the message — it relies entirely on the underlying CW721 contract's own authorization check succeeding or failing. Since the pointer supplies `senderAddr = GetSeiAddress(caller)` as the CW721 message sender, and the CW721 contract enforces ownership at that layer, a caller who is not the owner and has no approval will have their `transfer_nft` call rejected by the CW721 contract itself — **unless** the CW721 contract's `transfer_nft` handler does not itself gate on ownership/approval (many custom CW721 implementations vary), or unless `from`'s approval state on the CW721 contract inadvertently grants blanket permissions that the Solidity wrapper does not mirror. This makes the vulnerability's exploitability dependent on the specific CW721 implementation being pointed to, which introduces genuine uncertainty about default-configuration impact.

### Impact Explanation
If reachable (i.e., if the underlying CW721 contract does not itself perform a strict owner/approved check on `transfer_nft`, or if approval state diverges between the Solidity pointer and CW721 layers), this allows unauthorized transfer of any NFT wrapped by a CW721↔ERC721 pointer, resulting in direct fund/asset loss for the token owner. This matches the CWE-276/277/281 "Improper Preservation of Permissions" pattern from the reference advisory: a sub-operation (`transferFrom`) fails to re-validate that the caller holds the permission it is exercising on behalf of another principal (`from`).

### Likelihood Explanation
Medium-to-uncertain: the missing check in the Solidity wrapper is a definite, concrete coding defect (confirmed by diffing against the correctly-implemented `CW1155ERC1155Pointer.safeTransferFrom`), reachable by any public RPC/contract caller with no privilege, but full exploitability depends on whether the target CW721 contract behind the pointer performs its own strict ownership/approval check on `transfer_nft`. I could not verify from available context whether all CW721 contracts pointed to by this wrapper enforce that check strictly enough to fully neutralize this gap, or whether pointer-registered CW721 contracts (e.g., auto-deployed pointer targets) have permissive `transfer_nft` handling.

### Recommendation
Add the missing authorization check to `CW721ERC721Pointer.transferFrom` (and its `safeTransferFrom` overloads) before dispatching the CW execute message, mirroring the check already present in `CW1155ERC1155Pointer.safeTransferFrom`:
```
require(
    msg.sender == from || msg.sender == getApproved(tokenId) || isApprovedForAll(from, msg.sender),
    "ERC721: caller is not token owner or approved"
);
```

### Proof of Concept
1. Owner `O` mints/owns CW721 token `tokenId` wrapped by `CW721ERC721Pointer` at address `P`, with no approvals granted to any other address.
2. Attacker `A` (an unrelated EOA) calls `P.transferFrom(O, A, tokenId)` directly.
3. The Solidity check `require(from == ownerOf(tokenId), ...)` passes since `from == O` is indeed the owner.
4. No check is made that `msg.sender (A) == from (O)` or that `A` is approved.
5. `_execute` dispatches a `transfer_nft` CW message via the wasmd precompile using `A`'s associated Sei address as `Sender`.
6. If the target CW721 contract's `transfer_nft` handler does not itself independently and strictly reject non-owner/non-approved senders (verification of this final gate was not completed within available context), the NFT is transferred to `A` without `O`'s consent. [4](#0-3)
