## Title
Git filter/credential-helper processes inherit the trampoline session token, allowing an attacker-controlled repository to exfiltrate a signed-in account's OAuth token via the credential-helper protocol - ([File: app/src/lib/trampoline/trampoline-environment.ts])

## Summary
The report's underlying bug class is a **broken trust boundary/replay**: a privileged credential/authorization channel that was meant to be scoped to a single, specific operation can instead be invoked again — from attacker-influenced code that runs *during* that same operation — to obtain the same privileged result for a different purpose. In GitHub Desktop, the analog is the Git "trampoline" mechanism: every remote git invocation is wrapped in `withTrampolineEnv`, which hands out a single `DESKTOP_PORT` / `DESKTOP_TRAMPOLINE_TOKEN` pair to the *entire* git process tree for that operation, including filter/helper subprocesses that Git spawns on behalf of content found in the repository being cloned/fetched (e.g. LFS smudge/clean filters, credential-helper invocations for submodule URLs, etc.). The credential-helper trampoline handler (`createCredentialHelperTrampolineHandler` / `getGitHubCredential`) does not verify that the "get" request originates from, or is scoped to, the same remote/host the top-level operation was authorized for — it simply matches on request `host`/`url` origin against the user's stored accounts and hands back the real OAuth token.

## Finding Description
`withTrampolineEnv` mints one `token` per git invocation and exposes it (plus `DESKTOP_PORT`) to the whole process tree spawned by that `git` call: [1](#0-0) 

The comment in that same function explicitly acknowledges that this environment, including the credential helper configuration, is deliberately made visible to **filter processes** (e.g. Git LFS smudge/clean) invoked as part of the git operation, not just the top-level git process: [2](#0-1) 

When a "get" request reaches the trampoline server, `getGitHubCredential` looks up a stored account purely by comparing the request's URL origin to an account's endpoint, and unconditionally returns the account's real login and token if it matches: [3](#0-2) [4](#0-3) 

Critically, this lookup has no concept of "which repository/operation is this credential request for" — it is not scoped to the URL/path that the outer `git` (or `clone`) call was invoked with. `clone()` runs `git clone --recursive`, meaning the *entire* recursive submodule fetch for an untrusted, attacker-authored repository happens under one single trampoline token/session: [5](#0-4) 

Because `credential.helper=desktop` is configured via `GIT_CONFIG_PARAMETERS` (rather than a git argument) specifically so that it propagates to child/filter processes, any process spawned during that clone/fetch that can reach `127.0.0.1:$DESKTOP_PORT` with the (leaked/inherited) `DESKTOP_TRAMPOLINE_TOKEN` can issue an arbitrary `git-credential` `get` request and receive back the signed-in user's real GitHub token for whatever host it names — independent of what host the outer operation was actually cloning from. Hook execution is explicitly hardened against this (`hooks-proxy.ts` only forwards `GIT_*`/`GITHEAD_*` env vars to hook subprocesses, deliberately excluding `GIT_ASKPASS`/`GIT_SSH_COMMAND`, and never forwards `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN`): [6](#0-5) 

but **no equivalent scoping/allow-list exists for filter processes** (LFS smudge/clean, custom transfer agents) invoked outside the hooks proxy — they are spawned by dugite/git directly with the full trampoline env attached, exactly as the code comment describes.

## Impact Explanation
This corresponds to "credential/token exfiltration" and "unauthorized OAuth/account binding" impact categories: an attacker who controls a cloned/fetched repository's content (e.g. `.gitattributes` + a filter definition that's already configured on the victim's machine, such as a pre-existing `git-lfs` install, or a `.gitmodules` file triggering nested URLs/credential lookups within the same clone session) can cause a subprocess in that session to query the trampoline credential-helper for `github.com`/GHE credentials and receive the victim's real OAuth token, with no re-prompt and no scoping check tying the request back to the URL the user actually intended to authenticate against. The token can then be relayed off-box by the attacker-controlled process.

## Likelihood Explanation
Likelihood is moderate: exploitation requires a subprocess capable of speaking the trivial line-based trampoline/credential-helper protocol to run during a clone/fetch of an attacker-supplied repository, and requires either (a) a filter mechanism (e.g. LFS) already configured on the host that the attacker's repo content can trigger, or (b) some other Desktop-spawned helper that inherits `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` without env-scrubbing equivalent to `hooks-proxy.ts`'s `safeEnv` allow-list. I was not able to fully confirm within this repository whether a specific bundled component other than hooks executes with the unscrubbed environment during a hostile clone (e.g., whether LFS custom-transfer/extension commands defined in a repository's own `.lfsconfig` are actually invoked by the bundled git-lfs without a trust prompt) — that would need to be verified against the specific dugite/git-lfs build and any allow-list logic beyond what's visible in this codebase's hook-proxy sanitation.

## Recommendation
- Scope every credential-helper "get" response to the URL/host that the *outer* operation (the specific `git` invocation from `core.ts`, keyed by `trampolineEnvironmentPath`) was actually invoked against, rejecting or re-prompting for credential requests for hosts unrelated to that operation's target remote.
- Apply the same environment allow-list used in `hooks-proxy.ts` (`safePrefixes`/`excludedEnvVars`) to *all* subprocess environments spawned as part of a git operation — not just the interactive hooks proxy — so that `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` are not exposed to filter/extension processes unless those processes are part of a vetted allow-list (e.g. the specific `git-lfs` binary path, not arbitrary repo-defined commands).
- Bind trampoline tokens to a single, specific remote URL/origin at mint time (in `withTrampolineEnv`) rather than to an entire (possibly recursive/multi-host) operation, so a token minted for cloning host A can never be redeemed for credentials to host B.

## Proof of Concept
Not independently reproduced in this session — the theoretical PoC would be: attacker publishes a repository with a `.gitattributes`/`.gitmodules` configuration that triggers execution of a filter or nested URL resolution during `git clone --recursive` (`app/src/lib/git/clone.ts`); that subprocess inherits `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from the git process environment, opens a TCP connection to `127.0.0.1:$DESKTOP_PORT`, and sends a `git-credential`-style `get` request for `https://github.com` (or the victim's GHE endpoint); `createCredentialHelperTrampolineHandler`/`getGitHubCredential` returns the victim's real login/token without verifying the request pertains to the clone's actual target host, at which point the attacker's subprocess can forward that token elsewhere. Full confirmation requires validating exactly which subprocess types (LFS filters, custom transfer agents, etc.) are spawned with the unsanitized environment versus the hooks-proxy path in a live build.

export async function withTrampolineEnv<T>(
  fn: (env: object) => Promise<T>,
  path: string,
  isBackgroundTask = false,
  customEnv?: Record<string, string | undefined>
): Promise<T> {
  const sshEnv = await getSSHEnvironment()

  return withTrampolineToken(async token => {
    isBackgroundTaskEnvironment.set(token, isBackgroundTask)
    trampolineEnvironmentPath.set(token, path)

    const existingGitEnvConfig =
      customEnv?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    // The code below assumes a few things in order to manage SSH key passphrases
    // correctly:
    // 1. `withTrampolineEnv` is only used in the functions `git` (core.ts)
    // 2. Those two functions always thrown an error when something went wrong,
    //    and just return a result when everything went fine.
    //
    // With those two premises in mind, we can safely assume that right after
    // `fn` has been invoked, we can store the SSH key passphrase for this git
    // operation if there was one pending to be stored.
    try {
      return await fn({
        DESKTOP_PORT: await trampolineServer.getPort(),
        DESKTOP_TRAMPOLINE_TOKEN: token,
        GIT_ASKPASS: '',
        // This warrants some explanation. We're configuring the
        // credential helper using environment variables rather than
        // arguments (i.e. -c credential.helper=) because we want commands
        // invoked by filters (i.e. Git LFS) to be able to pick up our
        // configuration. Arguments passed to git commands are not passed
        // down to filters.
        //
        // We're using the undocumented GIT_CONFIG_PARAMETERS environment
        // variable over the documented GIT_CONFIG_{COUNT,KEY,VALUE} due
        // to an apparent bug either in a Windows Python runtime
        // dependency or in a Python project commonly used to manage hooks
        // which isn't able to handle the blank environment variables we
        // need when using GIT_CONFIG_*.
        //
        // See https://github.com/desktop/desktop/issues/18945
        // See https://github.com/git/git/blob/ed155187b429a/config.c#L664
        GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'credential.helper=' 'credential.helper=desktop'`,

        GIT_USER_AGENT: await GitUserAgent(),
        ...sshEnv,
      })

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
