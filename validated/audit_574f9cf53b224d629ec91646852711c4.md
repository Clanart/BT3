### Title
Integer overflow in payment/fee arithmetic allows signing a transaction paying unintended fee or DoS - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` performs unchecked `u64` multiplication and addition on attacker-influenced values (`payments` amounts and `fee_per_vbyte`). Unlike the change path, which uses `checked_sub`, the "not enough funds" guard at `input_sat < (payment_sat + needed_fee)` relies on `payment_sat`, `payment_sat + needed_fee`, and `fee_per_vbyte * vbytes` — all of which can overflow `u64` and either panic (DoS, the direct analog of CVE-2022-31005) or wrap, bypassing the funds check and producing a signed transaction whose implied fee burns funds.

### Finding Description
- `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>()` sums untrusted payment amounts with no bound check (each payment only must be `>= DUST = 546`). Two payments of `u64::MAX` sum to `u64::MAX - 1`... actually overflow, panicking under `overflow-checks` or wrapping to `~2 * u64::MAX mod 2^64` otherwise.
- `let mut needed_fee = fee_per_vbyte * vbytes;` overflows for large `fee_per_vbyte`.
- `if input_sat < (payment_sat + needed_fee)` can itself overflow the addition, so the guard can wrap and pass even though `payment_sat` alone far exceeds `input_sat`.
- If wrapping arithmetic passes, the change computation `input_sat.checked_sub(payment_sat + fee_with_change)` may also pass on a wrapped value, `Amount::from_sat(value)` accepts any `u64` without a 21M-coin bound, and the resulting `tx` is signed by `TransactionSignMachine::sign` / `TransactionSignatureMachine::complete`, producing a network-invalid transaction whose inputs are consumed (spent) as a gigantic fee — funds burned.
- The analogous upstream bug (Vapor FileMiddleware) is a DoS via unchecked integer arithmetic on untrusted input; here the same class appears on untrusted monetary values, with panic-DoS guaranteed and value mis-accounting in wrap builds.

### Impact Explanation
Minimum: unprivileged crash of the signing process (denial of service) by supplying payment amounts that overflow `sum::<u64>()` or `fee_per_vbyte * vbytes`. Worst case (wrapping arithmetic): the `NotEnoughFunds` check is bypassed and `TransactionMachine` produces and signs a transaction paying `input_sat - outputs` as fee, rendering received funds unspendable — a loss-of-funds outcome matching the "funds reported received that are not spendable" / unintended-signing acceptance criteria.

### Likelihood Explanation
`payments` amounts and `fee_per_vbyte` originate from withdrawal/plan construction driven by external coin data; no upper bound (e.g., Bitcoin's `MAX_MONEY`) is enforced anywhere in `SignableTransaction::new`. Reachability requires only influencing requested payment amounts, which is a normal part of the wallet's public interface.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`: `checked_sum`/`checked_add` for `input_sat`, `payment_sat`, `payment_sat + needed_fee`, and `checked_mul` for `fee_per_vbyte * vbytes`, returning a `TransactionError` on overflow. Additionally bound each payment and the total to `bitcoin::Amount::MAX_MONEY` (`21_000_000 * 100_000_000` sats) before constructing `TxOut`s.

### Proof of Concept
```rust
// In networks/bitcoin/src/wallet/send.rs logic:
// payments = [(script, u64::MAX), (script, u64::MAX)]
// payment_sat = sum::<u64>() -> overflow panic (overflow-checks on)

// needed_fee = fee_per_vbyte * vbytes also unchecked.
// payment_sat + needed_fee wraps low, so:

// -> panic on overflow-checks builds; silent fee-burning tx otherwise.
```
