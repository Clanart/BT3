### Title
External senders can reach internal-only output paths: deterministic offset addresses (Branch/Change/Forwarded) are scanned and classified as internal `OutputType`s purely by `script_pubkey` match — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs), [File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
CVE-2020-26978 ("slipstream") let a malicious public webpage cause the browser to reach endpoints on the internal network/localhost that should have been unreachable from the outside. The Serai analog: any external, unprivileged Bitcoin sender can send to the *internal-only* addresses — branch, change, and forwarded-output addresses — because they are deterministically derived from the group key via public `hash_to_F("Serai Bitcoin Output Offset", ...)` scalars, and `Scanner::scan_transaction`/`get_outputs` classifies matching outputs purely by `script_pubkey` with no check that the sender is the multisig itself. The processor then treats attacker-created outputs as internal deposits, silently dropping the attached `InInstruction` data for non-`External` kinds.

### Finding Description
`processor/src/networks/bitcoin.rs` `scanner()` registers four deterministic offsets — `External` (scalar zero), `Branch`, `Change`, and `Forwarded` — all derived as `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"...")` (lines 308–346). These scalars are public constants; anyone can compute `key + G * offset` and the corresponding P2TR `script_pubkey`. `Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) returns a `ReceivedOutput` for any tx output whose `script_pubkey` is in the map, with no provenance check. `Bitcoin::get_outputs` (processor/src/networks/bitcoin.rs:686-740) then looks up `kinds[offset_repr]` to assign the `OutputType` and only attaches the extracted `InInstruction` data when `kind == OutputType::External` (lines 731-735). The comments on `OutputType` in `processor/src/networks/mod.rs:48-82` explicitly state `External` is "needs to be processed/sent up to Substrate" while `Branch`/`Change`/`Forwarded` are internal-only roles (scheduled branches are assumed to be multisig-created; `Forwarded` is "from the prior multisig"), yet the scan path cannot distinguish an internal TX from an attacker's TX — `mod.rs:68-69` even concedes "or Eve, a malicious actor, has sent us a forged TX".

### Impact Explanation
Two concrete effects:

1. **Uncredited deposits / funds received that the protocol treats as internal.** An output sent by an external party to the `Change` or `Forwarded` address is classified as internal; `get_outputs` discards the tx's `InInstruction` data (`if output.kind == OutputType::External` guard, bitcoin.rs:732-734), so the deposit is never reported up to Substrate for crediting. The coins sit under the multisig but are invisible to the deposit flow — funds are reported received as internal outputs yet never processed for the depositor.
2. **Injection of internal scheduler state.** An attacker output on the `Branch` address is consumed by the branch-queue logic ("push that plan to a queue of plans to perform when instances of that output occur", mod.rs:71-74). Since the queue cannot bind an output instance to the plan that produced it, an attacker-created branch output (arbitrary amount ≥ `DUST` = 10_000 sats) can trigger scheduled plans or produce `PostFeeBranch` mismatches (`expected` vs `actual` mismatch in `drop_branches`/`prepare_send`, mod.rs:221-232, 504-517), corrupting the deterministic schedule assumptions and causing plan drops / misaccounted operating costs.

### Likelihood Explanation
Medium. The branch/change/forwarded addresses are computable by anyone from the public group key and the fixed `hash_to_F` DST — no key material or validator position is needed, just a standard Bitcoin transaction. The attacker's own funds are spent in the attempt, so it is primarily a griefing/accounting-corruption vector rather than direct theft, and outputs under `DUST` are filtered (processor/src/multisigs/scanner.rs:564).

### Recommendation
Bind internal outputs to internal provenance rather than `script_pubkey` alone. Options: (a) for `Branch`/`Change`/`Forwarded`-classified outputs, only accept them when the spending transaction or its inputs are verifiably multisig-produced (e.g., check `tx.input[*].previous_output` belongs to a known multisig output, or require the txid match a registered eventuality); (b) for `Forwarded`, only accept forwards during the retirement window from the specific prior group key; (c) at minimum, treat externally-received outputs on internal offsets as `External`-kind deposits so attached `InInstruction` data is processed rather than silently dropped.

### Proof of Concept
1. Compute `branch_scalar = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch")` and `change_scalar`/`forward_scalar` similarly; derive `p2tr_script_buf(group_key + G*scalar)` — exactly what `scanner()` does.
2. Broadcast a normal Bitcoin TX paying ≥ 10_000 sats to the `Forwarded` script with an OP_RETURN `InInstruction` transfer payload.
3. `Bitcoin::get_outputs` scans it: `scan_transaction` matches the script, `kinds[offset_repr]` yields `OutputType::Forwarded`, the `InInstruction` is skipped (bitcoin.rs:732), and the output is emitted to the coordinator as an internal forwarded output — no deposit credited, and it enters scheduler paths reserved for prior-multisig forwards.
4. Alternatively, pay the `Branch` script with an amount not matching any in-flight plan: the branch-output queue pops a queued plan against an attacker-supplied amount, producing a `PostFeeBranch { expected, actual }` divergence and plan-drop/operating-cost miscalculation in `prepare_send`.
