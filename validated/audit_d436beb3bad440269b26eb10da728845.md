I found a direct analog to the reported bug class: a boundary-inequality mismatch between documented requirement and implemented comparison in the bridge circuit's work-comparison assertion.### Title
Bridge circuit accepts ties between operator and watchtower total work, violating the documented "strictly greater" canonical-chain requirement - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
The `bridge_circuit` function's work-comparison guard uses a strict `<` check that only panics when the operator's `total_work` is *less than* the watchtower's `max_total_work`, silently accepting the case where the two are exactly equal. The function's own documentation states the requirement should be that the operator's work is *greater than* the watchtower's maximum work, not greater-or-equal. This is the same class of bug as the referenced Y2K Finance report: a strict vs. non-strict boundary mismatch between the documented invariant and the implemented comparison, which allows a state transition (here, canonical-chain acceptance in a zk-verified circuit) to occur under conditions the specification says should be rejected.

### Finding Description
`bridge_circuit` in [1](#0-0)  computes `max_total_work` from watchtower challenge proofs via `total_work_and_watchtower_flags`, and compares it against the operator's own `total_work` taken from their verified header-chain proof (HCP):

```
// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [2](#0-1) 

The function doc comment explicitly states the intended invariant as a strict inequality: "Asserts that the operator's claimed work is greater than the maximum work submitted by any valid watchtower" and "If `max_total_work` given by watchtowers is greater than `hcp.chain_state.total_work`" it should panic [3](#0-2) [4](#0-3) . This is corroborated by the design docs: "The Operator must provide a HCP with more work compared to the WOP with maximum Work" [5](#0-4) .

The implemented condition `total_work < max_total_work` is logically equivalent to `max_total_work > total_work`, so it only panics when the watchtower's work strictly exceeds the operator's. When `total_work == max_total_work` (a tie), the panic does not fire, and the circuit proceeds to treat the operator's claimed chain as canonical — exactly the boundary condition ("equal to" rather than "strictly greater/less than") that the documentation says must be rejected. This mirrors the Y2K Finance `isDisaster` bug, where `<` was used instead of `<=` at a price/strike boundary, allowing an event to occur exactly at the boundary that the spec said should not trigger it.

### Impact Explanation
This assertion is the core soundness check that determines whether the operator's claimed Bitcoin chain state (embedded in their HCP) is heavier than — and therefore takes precedence over — the chain implied by the highest-work challenging watchtower. Because Bitcoin's canonical chain is determined by total accumulated proof-of-work, a tie does not establish which chain is actually canonical; the specification's choice of strict inequality reflects that a tie should not be resolved in the operator's favor. Accepting equality lets the circuit's guest-side (in-circuit) logic emit a valid Groth16 proof / journal for a payout claim under a condition the documented invariant forbids. Since this proof underlies the on-chain BitVM2 disprove path (`BridgeDisproveScript` verifies this same Groth16 proof on-chain) [6](#0-5) , this is a soundness defect in the circuit itself: it allows a claim that the specification would classify as invalid to nonetheless be provable, matching the "Critical — a false circuit claim proved or a true one made unprovable" impact category.

### Likelihood Explanation
Reaching the tie exactly requires the operator's own header-chain total work to numerically equal the challenging watchtower's proven work value — a narrow condition compared to arbitrary chain manipulation, and the assignment of exact work values is otherwise constrained by real proof-of-work accumulation. I could not fully verify from the available code how granular/controllable the 16-byte `total_work` value is at the boundary the operator selects (e.g., whether an operator can choose a header-chain endpoint that lands on an exact tie without needing majority hashrate), so likelihood of practical exploitation is uncertain and may be low in practice; nonetheless, the logic is objectively incorrect relative to its own specification and constitutes a genuine boundary bug in the trust-minimization guarantee, independent of how hard it is to trigger.

### Recommendation
Change the comparison in `circuits-lib/src/bridge_circuit/mod.rs` (around line 156) from `total_work < max_total_work` to `total_work <= max_total_work`, so that a tie between the operator's total work and the watchtower's max total work causes the circuit to panic, consistent with the documented "strictly greater than" requirement.

### Proof of Concept
1. An operator constructs (or, over time, naturally produces) an HCP whose `chain_state.total_work` exactly equals the `max_total_work` value provable by the highest-work challenging watchtower's work-only Groth16 proof.
2. `total_work_and_watchtower_flags` returns this `max_total_work`, and the equality check at [7](#0-6)  evaluates `total_work < max_total_work` as `false` (since they are equal), so no panic occurs.
3. The circuit proceeds to SPV/light-client/storage verification and produces a valid journal/proof, despite the specification requiring the operator's work to be strictly greater than the watchtower's for the claim to be considered canonical/valid.
