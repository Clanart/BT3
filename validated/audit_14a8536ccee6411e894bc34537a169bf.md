### Title
Unhandled `first()`/`as_atom()` exception while parsing an untrusted `CREATE_COIN` condition crashes NFT wallet sync - ([File: chia/wallet/nft_wallet/nft_puzzle_utils.py])

### Summary
`get_metadata_and_phs()` in `chia/wallet/nft_wallet/nft_puzzle_utils.py` walks CLVM output conditions produced by running the *inner* p2 puzzle of an NFT coin's spend with attacker-controlled solution data, and blindly extracts a memo puzzle-hash via `condition.at("rrrff").as_atom()` whenever it sees a `CREATE_COIN` condition (opcode `51`) whose amount equals `1`, without first checking that a memo list argument is actually present. This mirrors the GStreamer `subrip_unescape_formatting` bug class: a parser walks attacker-supplied structured input and dereferences a field that can legitimately be absent/NULL, crashing the consumer.

### Finding Description
`get_metadata_and_phs` is called any time the wallet processes a spend of a coin it has uncurried as an NFT (`UncurriedNFT`), most notably from `NFTWallet.puzzle_solution_received()` [1](#0-0)  and from `WalletStateManager.manual_nft_search()` [2](#0-1) . These paths run whenever the wallet syncs a coin state / receives a puzzle-and-solution for an NFT coin — i.e., triggered purely by an inbound spend of a coin the victim wallet is watching (NFT transfer, offer settlement, DID transfer to the victim, etc.), with no wallet-side signature required from the attacker's inner solution content itself.

The parsing logic:
```
elif condition_code == 51:
    atom = condition.rest().rest().first().as_int()
    if atom == 1:
        ...
        memo = bytes32(condition.at("rrrff").as_atom())
``` [3](#0-2) 

A standard `CREATE_COIN` condition can legally have only 2 arguments (`puzzle_hash amount`), with no memo list at all — this is explicitly called out and defended against elsewhere in the codebase, e.g. in `compute_memos_for_spend`:
```
if condition[0] == ConditionOpcode.CREATE_COIN and len(condition) >= 4:
    ...
    if type(condition[3]) is not list:
        continue
``` [4](#0-3)  and in `run_block.py`'s `run_generator` [5](#0-4) . Both of those call sites explicitly check `len(condition) < 4` / `type(...) is not list` before touching the memo field.

`get_metadata_and_phs`, however, performs no such check. If the p2-puzzle output contains `(51 puzzle_hash 1)` (amount == 1, no third/memo argument), then `condition.at("rrrf")` resolves to `Program.NIL`, and `Program.at("rrrff")` calls `.first()` on that `NIL` atom. `Program`/`SExp.first()` raises `clvm.EvalError.EvalError` ("first of non-cons") when called on an atom, per the `EvalError` re-export in `chia/types/blockchain_format/program.py` [6](#0-5)  (used elsewhere in `uncurry()` to catch exactly this class of error). `get_metadata_and_phs` has no try/except around this call, so the `EvalError` (or, if there is a memo but it's not an atom, `as_atom()`'s `ValueError("expected atom")` per [7](#0-6) ) propagates uncaught up through `puzzle_solution_received` / `manual_nft_search`.

### Impact Explanation
Because `puzzle_solution_received` is invoked during normal coin-state processing for any coin the wallet has classified as an NFT (`determine_coin_type`, `chia/wallet/wallet_state_manager.py:965-976`), an attacker can construct and send/settle an NFT (via a direct transfer, or an offer/trade the victim accepts) whose inner p2-puzzle solution yields a `(51 ph 1)` condition without a memo argument. When the victim's wallet processes that spend during sync, the uncaught exception aborts the coin-processing task for that spend, which is a spend-triggered denial-of-service against the victim's wallet's transaction/coin-state processing pipeline — directly analogous to the GStreamer NULL-dereference crash while parsing an externally supplied structure. This does not directly enable theft or unauthorized coin movement, but it does allow an untrusted counterparty (NFT sender, offer counterparty) to reliably halt/crash coin-state processing for a targeted wallet using a single crafted spend.

### Likelihood Explanation
Likelihood is moderate-to-high for a wallet that accepts arbitrary inbound NFT transfers/offers: no special privileges are needed, only the ability to craft a coin spend (or an offer) whose p2-inner-puzzle output includes a bare `CREATE_COIN ph 1` (a legal, minimal CLVM condition) reaching a wallet that is tracking the corresponding NFT/DID coin. The path is exercised on every NFT coin-state update, so it is easily reachable without waiting for user confirmation of a specific transaction.

### Recommendation
In `get_metadata_and_phs` (and any similarly structured NFT-condition parsers), mirror the defensive pattern already used in `compute_memos_for_spend`/`run_generator`: verify the condition actually has a 4th (memo) argument and that it is a cons/list of atoms before calling `.at("rrrff").as_atom()`; treat a missing or malformed memo list as "no derivation puzzle hash found" rather than letting the exception propagate. Wrap the condition-walk in `get_metadata_and_phs` with handling for `Program.EvalError`/`ValueError` consistent with how `UncurriedNFT.uncurry` already guards against malformed CLVM structure [8](#0-7) .

### Proof of Concept
1. Mint/acquire an NFT (or DID-owned NFT) puzzle and construct (or have an attacker construct) a spend whose p2-inner puzzle, when run with the supplied inner solution, outputs conditions containing a bare `(CREATE_COIN puzzle_hash 1)` with no third memo argument (e.g., inner solution `[[51, some_ph, 1]]` with no `[some_ph]` memo list, structurally identical to the `skip_tp_spend`/`generic_spend` patterns already exercised in `chia/_tests/wallet/nft_wallet/test_nft_lifecycle.py:158-166` but omitting the memo list on the amount==1 output).
2. Push this spend / settle it as an offer to a victim wallet that is tracking the parent NFT/DID coin.
3. When the victim wallet syncs and calls `NFTWallet.puzzle_solution_received` → `get_metadata_and_phs(uncurried_nft, data.parent_coin_spend.solution)`, the call `condition.at("rrrff").as_atom()` raises an uncaught `EvalError`/`ValueError`, aborting the wallet's coin-processing for that spend.

Note: I was unable to fully trace whether an outer exception handler higher up in `wallet_state_manager`'s coin-state processing loop catches and logs this specific exception versus letting it terminate the sync task entirely — the exact blast radius (single-coin skip vs. full sync-loop crash) would need to be confirmed by tracing the caller chain around `determine_coin_type`/`_add_state_manager_coin` in a live Devin session, since the index does not show a full call-site of `puzzle_solution_received`'s exception handling.
