### Title
Forged `ReceivedOutput` encodings cause unspendable Bitcoin funds to be treated as spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts an attacker-supplied scalar offset, `TxOut`, and `OutPoint` without establishing that the referenced outpoint exists or that the claimed `TxOut` is the one actually present on Bitcoin. If the encoded `TxOut` uses a script matching a public key offset, `SignableTransaction::new` treats its declared value as spendable input, and `SignableTransaction::multisig` accepts the input because the supplied script matches the tweaked threshold key.

### Finding Description
`ReceivedOutput` is the wallet’s representation of a spendable output. It stores three independently controlled fields: `offset`, `output`, and `outpoint`. [1](#0-0) 

Its deserializer only parses these fields:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)
outpoint = OutPoint::consensus_decode(&mut buf_r)
```

It does not prove that `outpoint` resolves to `output`, nor does it verify that `output.script_pubkey` corresponds to a scanner-registered offset. [2](#0-1) 

Legitimate outputs are normally produced by `Scanner::scan_transaction`, which constructs `ReceivedOutput` only when a transaction output’s `script_pubkey` matches a registered script. [3](#0-2)  Deserializing untrusted bytes bypasses that provenance check while producing the same trusted `ReceivedOutput` type.

`SignableTransaction::new` then trusts both the encoded outpoint and encoded amount:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
let offsets = inputs.iter().map(|input| input.offset).collect();
previous_output: input.outpoint
``` [4](#0-3) 

The declared value is used to fund payments, change, and fees. [5](#0-4) 

The only wallet-level consistency check occurs later in `multisig`, which verifies that `prevouts[i].script_pubkey` equals the script for `keys.offset(offsets[i])`. It does not check whether the referenced outpoint exists or contains that output. [6](#0-5) 

### Impact Explanation
An unprivileged party who can submit bytes to `ReceivedOutput::read` can fabricate an apparently spendable input by choosing:

- a public threshold key offset;
- a `TxOut` whose script is the corresponding P2TR script;
- an arbitrary value;
- a nonexistent or unrelated `OutPoint`.

The wallet will then account for the fake value as input liquidity and construct a transaction spending the fake outpoint. If the script was correctly derived, threshold signing setup succeeds and produces a signature for the fabricated transaction. Bitcoin consensus will reject the transaction, while wallet state has reported funds as available that are not actually spendable.

This is analogous to the upstream bug’s poisoned anchor: data accepted into a privileged state object causes subsequent protocol operations to build around an invalid reference instead of rejecting the bad claim at the boundary.

### Likelihood Explanation
The attack requires an integrator or service to accept serialized `ReceivedOutput` values from an untrusted source. The type exposes a public `read` API and performs only syntactic deserialization, so malicious bytes can directly become a `ReceivedOutput`. [2](#0-1) 

The attacker does not need a private key. The threshold group key and any registered offsets/scripts are public wallet information, and the required script can be calculated with `p2tr_script_buf`. [7](#0-6) 

The forged input can waste threshold-signing attempts and cause funds-dependent operations to fail. Severity is bounded because the resulting Bitcoin transaction remains consensus-invalid, but the wallet incorrectly classifies nonexistent funds as spendable.

### Recommendation
Keep `ReceivedOutput` values trustworthy by making construction/registration prove the output-to-outpoint relationship. In particular:

1. Treat `ReceivedOutput::read` as untrusted input and return a separate unverified representation, or require callers to rescan the referenced transaction before constructing a `ReceivedOutput`.
2. Include or require the base key during deserialization and reject outputs whose `script_pubkey` does not equal `p2tr_script_buf(base_key + G * offset)`.
3. Before constructing `SignableTransaction`, validate each claimed outpoint against the canonical Bitcoin chain and require the actual on-chain `TxOut` to equal the supplied `TxOut`.
4. Consider storing the confirmed transaction ID/output index atomically with scanner results so externally supplied `ReceivedOutput` values cannot impersonate scanner results.

### Proof of Concept
Conceptually, for a known `ThresholdKeys<Secp256k1>`:

```rust
let offset = Scalar::ZERO;
let output = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: p2tr_script_buf(
    keys.clone().offset(offset).group_key()
  ).unwrap(),
};
let outpoint = OutPoint::new(Txid::all_zeros(), 0);

// Encode exactly as ReceivedOutput::write would.
let mut encoded = Vec::new();
encoded.extend(offset.to_bytes());
encoded.extend(serialize(&output));
encoded.extend(serialize(&outpoint));

let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
```

`ReceivedOutput::read` accepts the value because all three fields deserialize independently. [2](#0-1) 

Passing `forged` to `SignableTransaction::new` makes its claimed one-million-satoshi value contribute to `input_sat`, while its fake `OutPoint` becomes a transaction input. [4](#0-3)  `multisig` then accepts the input because the crafted `script_pubkey` matches `keys.offset(offset)`, despite the referenced outpoint being nonexistent or unrelated. [8](#0-7)
