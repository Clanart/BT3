Attacker-inflated median fee lets an unprivileged party drain multisig funds as miner fees - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::median_fee` computes the fee rate used for every Bitcoin `SignableTransaction` as the unbounded median of `tx_fee / vsize` over all non-coinbase transactions in a block, with no cap or sanity bound. That value is multiplied directly by the transaction's vsize in `SignableTransaction::new` (`needed_fee = fee_per_vbyte * vbytes`) and the difference between inputs and outputs is paid entirely to miners. An unprivileged attacker who fills the sampled block with high-fee transactions raises the median arbitrarily and causes the multisig to sign transactions burning up to nearly the entire input value as fee — an unnormalized product of an attacker-controlled factor, the same class as the reference report's `timeDiff * rewardsRate * liquidity * xp` reward formula.

Like the reference bug — where `rewards = timeDiff * rewardsRate * liquidity * xp` was missing the `1e18` scaling division so a large unnormalized `xp` let a tiny stake claim the whole supply — here the fee is an unnormalized product of an externally controlled rate. The protocol signs whatever `median * vbytes` computes, with no ceiling relative to the funds being moved or to a sane market rate.

### Impact Explanation
An attacker who controls the majority of transactions in the sampled block sets the median to any value up to what they are willing to pay. The multisig then signs a transaction whose `fee = sum(inputs) - sum(outputs)` equals that inflated rate times its vsize — potentially burning essentially the entire input value to miners while the intended payments still succeed. This is analogous to the reference report's ability to drain the entire kerosene supply: an unbounded attacker-influenced factor is multiplied into a funds-transferring quantity with no normalization or cap. Funds are irreversibly lost once the transaction confirms; fees paid to Bitcoin miners cannot be recovered.

### Likelihood Explanation
Reachability only requires the attacker to send ordinary, valid Bitcoin transactions — a public-input channel explicitly in scope. To move the median above `X` sat/vbyte the attacker needs more than half of the block's non-coinbase transactions to pay `>= X`; in low-activity blocks this is cheap, and the attacker can pick whichever `block_number` the processor samples by timing. The cost is bounded by the fees the attacker's own transactions pay, which is roughly proportional to the damage, but unlike a normal fee market the attacker also forces *every* Serai withdrawal signed against that block to overpay, and the attack can be repeated each block. No validator compromise, leaked key, or malicious-RPC assumption is needed — the median is computed purely over public on-chain data.

### Recommendation
Bound the sampled fee before multiplying it by the transaction size:
- Clamp `median_fee` to a hard maximum (e.g., a protocol-defined `MAX_SAT_PER_VBYTE`, or `k ×` the minimum relay fee) rather than accepting the raw median.
- Prefer a lower percentile or a configurable fee-rate oracle so a majority-of-block attacker cannot push the estimate.
- In `SignableTransaction::new`, additionally cap `needed_fee` at a fraction of `input_sat` (e.g., refuse to sign when `needed_fee` exceeds `input_sat / N`), so even a manipulated rate cannot burn the bulk of the funds.
- Use `checked_mul`/`checked_add` for `fee_per_vbyte * vbytes` and `payment_sat + needed_fee` so an extreme rate returns `TransactionError` instead of panicking or wrapping.

### Proof of Concept
1. Attacker observes (or waits for) a low-traffic Bitcoin block and broadcasts, e.g., 10 transactions each paying 1,000,000 sat/vbyte, so that over half of `block.txdata[1..]` has that fee rate.
2. The processor calls `median_fee(block)`; `fees.sort()` yields a median of 1,000,000 and returns `Fee(1_000_000)`.
3. `make_signable_transaction` builds a `SignableTransaction` spending a multisig input of `I` sats with payments `P`; `vbytes ≈ 200`, so `needed_fee = 1_000_000 * 200 = 200_000_000` sats (2 BTC).
4. If `I - P >= 200_000_000`, the `NotEnoughFunds` check passes, the transaction is constructed and routed to the FROST signing machine, and the multisig signs a transaction paying ~2 BTC to miners — permanently destroying multisig funds at the attacker's chosen rate.

  async fn median_fee(&self, block: &Block) -> Result<Fee, NetworkError> {
    let mut fees = vec![];
    if block.txdata.len() > 1 {
      for tx in &block.txdata[1 ..] {
        let mut in_value = 0;
        for input in &tx.input {
          let mut input_tx = input.previous_output.txid.to_raw_hash().to_byte_array();
          input_tx.reverse();
          in_value += self
            .rpc
            .get_transaction(&input_tx)
            .await
            .map_err(|_| NetworkError::ConnectionError)?
            .output[usize::try_from(input.previous_output.vout).unwrap()]
          .value
          .to_sat();
        }
        let out = tx.output.iter().map(|output| output.value.to_sat()).sum::<u64>();
        fees.push((in_value - out) / u64::try_from(tx.vsize()).unwrap());
      }
    }
    fees.sort();
    let fee = fees.get(fees.len() / 2).copied().unwrap_or(0);

    // The DUST constant documentation notes a relay rule practically enforcing a
    // 1000 sat/kilo-vbyte minimum fee.
    Ok(Fee(fee.max(1)))
  }
