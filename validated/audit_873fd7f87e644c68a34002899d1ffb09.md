Based on my analysis, I found a concrete, code-provable analog: the `RedeemEscrow` message dispatched in `_fillCrossChain` uses `timeout: 0` ("no timeout" per the protocol's own documentation), meaning once a solver fills a cross-chain order on the destination, there is no way to ever recover the source-chain escrow if the message is never delivered — the exact "31 ETH locked with no blame/recovery mechanism" pattern from the seed report.

### Title
Cross-Chain Order Fill Permanently Locks Source Escrow if RedeemEscrow Message Is Never Delivered - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_fillCrossChain` dispatches the `RedeemEscrow` message with `timeout: 0`, which per the protocol's own documentation means the message "will never expire." [1](#0-0)  Once the solver delivers output tokens on the destination and `_filled[commitment]` is set there, the order can never be cancelled from the destination chain (already finalized) and can never be cancelled from the source chain either, because `_cancelFromSource` proves via GET request that the destination `_filled` slot is non-empty and reverts with `Filled()`. [2](#0-1)  If the `RedeemEscrow` POST is never relayed to the source chain, the source-side escrow (`_orders[commitment][token]`) is permanently stuck: the solver who is entitled to it has no claim mechanism, and the user cannot reclaim funds they already effectively transferred value for. There is no analog of `fundRequest`-driven incentive combined with an unconditional non-expiring message — the "operator" (solver) has already done its part off-chain (destination delivery) but the protocol provides zero recovery path for the corresponding source-chain fund release if the single message carrying that state transition is dropped forever.

### Finding Description
The report's core broken invariant is: *an actor can move a system into a state that irreversibly locks a large amount of pooled/escrowed funds behind a single required action, without any timeout/blame path that lets a third party force resolution.*

In `StakeModuleLib.sol`, this happened because `stake()` was the only path to release the 31 ETH once a validator entered `PROPOSED`, and there was no timeout to reclaim/blame if the operator withheld the `stake()` call.

The Hyperbridge analog is in `IntentGatewayV2` cross-chain order fulfillment:

1. A solver calls `fillOrder()` on the destination chain, delivering output tokens to the beneficiary and dispatching `RedeemEscrow` back to source with `DispatchPost.timeout = 0`. [3](#0-2) 
2. Hyperbridge's own dispatch semantics define `timeout == 0` as "no timeout — messages will never expire," explicitly meaning no automatic timeout-refund path exists for such a request. [4](#0-3) [5](#0-4) 
3. On the source chain, `_cancelFromSource` is the only recovery path for the user, but it explicitly reverts if the destination `_filled` slot is non-empty. [2](#0-1)  Since the solver already filled on destination, this path is permanently blocked.
4. `_cancelFromDest` similarly only marks `_filled` and dispatches a refund — but since `_filled[commitment]` is already set to the solver (non-zero), `cancelOrder`'s top-level guard `if (_filled[commitment] != address(0)) revert Filled();` blocks any cancel attempt entirely. [6](#0-5) 
5. There is no `onPostRequestTimeout` handler in `ExtrinsicIntents.sol`/`IntentGatewayV2.sol` for the `RedeemEscrow`/`RefundEscrow` requests since they are dispatched with `timeout: 0` and thus never generate a timeout event at all — unlike the `HyperFungibleToken`/`WrappedHyperFungibleToken` apps, which correctly implement `onPostRequestTimeout` with nonzero timeouts to refund locked/burned assets. [7](#0-6) 

Existing guards (`Filled()` check, GET-response `Filled` proof check) are designed to prevent double-settlement, but they inadvertently also block any recovery once the destination-side state is set, and the `timeout: 0` dispatch removes the only other exit (timeout-driven fee/asset refund).

### Impact Explanation
If the `RedeemEscrow` message is dropped, censored, or simply never relayed (e.g., insufficient fee, indexer/relayer downtime, or host pausing on the source chain for an extended period), the escrowed input tokens for that order become permanently unrecoverable by anyone — not the user, not the solver, not the protocol. This is a direct loss/lock of user + solver funds with no recovery mechanism, matching the "stealing or loss of funds" / "fund loss/lock" category in the bounty's impact gate. The amount at risk scales with order size and is not bounded, and it does not require a malicious relayer — a relayer merely never delivering (which is explicitly foreseeable given `timeout: 0` and self-relay support) is sufficient.

### Likelihood Explanation
Any cross-chain order fill inherently creates this exposure window, and self-relay is a documented, encouraged pattern for `RedeemEscrow`-class dispatches; if the payer/solver does not self-relay and no third-party relayer picks up the message (e.g., zero/low fee, `fee: options.relayerFee` set to 0, or relayer outage), the funds are stuck indefinitely. This does not require any privileged, malicious, or adversarial actor — it is a direct consequence of pairing `timeout: 0` with a fill-then-message architecture that has no independent recovery path once destination state is finalized.

### Recommendation
Dispatch `RedeemEscrow` (and `RefundEscrow`) with a bounded, nonzero `timeout`, and implement `onPostRequestTimeout` in `ExtrinsicIntents.sol` to handle the case where the message never arrives — e.g., allow the solver (or, after a grace period, anyone) to resubmit a fresh `RedeemEscrow` dispatch backed by a fresh relayer fee, or add a governance/permissionless "force-settle" path gated by a valid destination-fill proof (reusing the existing GET-request proof infrastructure from `_cancelFromSource`) that lets the solver claim escrow directly from source without depending on the original POST message's delivery.

### Proof of Concept
1. User places a cross-chain order on chain A escrowing `inputAmount` of USDC via `IntentGatewayV2.placeOrder`.
2. Solver calls `fillOrder()` on chain B, delivering output tokens to the beneficiary; `_fillCrossChain` sets `_filled[commitment] = solver` on chain B and dispatches `RedeemEscrow` to chain A with `timeout: 0` and `fee: options.relayerFee`. [8](#0-7) 
3. Assume `options.relayerFee` is set to `0` (self-relay intended) but the solver never submits the self-relay transaction (e.g., crashes, goes offline, or deliberately withholds it after already being paid off-chain by the user through the destination output delivery).
4. On chain A, `_orders[commitment][usdc]` still holds the escrowed `inputAmount`; `_filled[commitment]` is still `address(0)`.
5. User attempts `cancelOrder` → `_cancelFromSource`: dispatches a GET request proving destination `_filled[commitment]`; the response returns non-empty (solver's address), so `onGetResponse` reverts with `Filled()`. [2](#0-1) 
6. Solver cannot claim escrow on chain A because `RedeemEscrow` was never delivered and there is no other entry point that transfers escrow to the solver.
7. Because `timeout: 0` means "never expire," no timeout message can ever be generated to unlock/refund the funds. The `inputAmount` in `_orders[commitment][usdc]` remains permanently locked in the `IntentGatewayV2` contract on chain A.

        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

            if (!sent) {

                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }
