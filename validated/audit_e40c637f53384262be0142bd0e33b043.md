## Title
Unbounded per-proposal deposit set enables a cheap out-of-gas/processing-delay DoS in `x/gov` `EndBlocker` deposit refund/burn path - (File: `sei-cosmos/x/gov/keeper/deposit.go`)

### Summary
The `x/gov` module lets any account submit a `MsgDeposit` on any active proposal with no cap on the number of unique depositor entries recorded per proposal. `AddDeposit` stores one `Deposit` record per unique depositor address, and this set is later iterated in full and unconditionally by `RefundDeposits`/`DeleteDeposits` inside `EndBlocker` when the proposal's voting/deposit period ends, exactly mirroring the OpenQ report's pattern of an attacker inflating an unbounded per-entity collection that is later iterated in a refund path with no early exit.

### Finding Description
`AddDeposit` requires only that the proposal be depositable and transfers `SendCoinsFromAccountToModule` for any non-zero coin amount; it does not limit the number of distinct depositor addresses recorded for a proposal: [1](#0-0) 

Each unique depositor address creates a new `Deposit` record keyed by `(proposalID, depositorAddr)`: [2](#0-1) 

When the proposal completes, `gov.EndBlocker` unconditionally calls `RefundDeposits` (or `DeleteDeposits` if the deposit is burned), which iterates every deposit record for that proposal via `IterateDeposits` with no batching, pagination, or per-block record budget — unlike the incremental tally logic that was explicitly bounded (`remainingRecords`) to avoid unbounded EndBlock work: [3](#0-2) [4](#0-3) [5](#0-4) 

`gov.EndBlocker` runs synchronously and deterministically on every validator node inside `EndBlock` for every block, via `legacyabci.EndBlock`: [6](#0-5) 

An attacker can generate an arbitrary number of throwaway accounts and submit minimal `MsgDeposit` transactions (e.g. 1 usei each) from each account to the same proposal. Because Sei's transaction fees are cheap (as noted in the original report for Polygon), this is inexpensive to scale to a very large number of unique depositor entries — analogous to the OpenQ attacker populating the `deposits` array cheaply with 1 WEI deposits of tokens they control. When the deposit/voting period ends, every validator's `EndBlocker` must iterate the entire inflated deposit set for `RefundDeposits`/`DeleteDeposits`, and the same unbounded iteration is also exercised by `ModuleAccountInvariant` and `GetAllDeposits`: [7](#0-6) 

### Impact Explanation
Because `EndBlocker` executes with an effectively unbounded work budget for this loop (no incremental cursor, unlike the tally queue processing which was explicitly redesigned to cap per-block work), a sufficiently large attacker-inflated deposit set forces every validator to spend unbounded, unmetered wall-clock time processing `RefundDeposits`/`DeleteDeposits` for a single proposal during block finalization. This directly risks block-processing delay beyond acceptable bounds across the entire validator set simultaneously (since `EndBlocker` runs identically and deterministically on every node), which is an accepted high-severity impact category (block delay). In the worst case for very large sets, this can also starve/legitimately DoS refunds to genuine depositors on the same proposal, since deposit refunds for that proposal cannot be short-circuited or retried in smaller batches.

### Likelihood Explanation
Likelihood is high: submitting `MsgDeposit` from many accounts is a standard, unprivileged, permissionless transaction type available to any public RPC client, requires no special permissions, and costs only minimal transaction fees plus a negligible deposit amount per account, similar to the original OpenQ attacker paying "1 WEI" per deposit to populate the vulnerable collection.

### Recommendation
Cap the number of distinct depositor entries allowed per proposal in `AddDeposit` (reject once a configurable `MaxDepositEntries` is reached, mirroring the recommended `depositLimit` check in the OpenQ report), and/or convert `RefundDeposits`/`DeleteDeposits` to incremental, per-block-bounded processing analogous to the incremental tally cursor already used for proposal tallying in `x/gov/abci.go`.

### Proof of Concept
1. Attacker submits an initial proposal or targets any open proposal in its deposit/voting period.
2. Attacker programmatically generates N throwaway accounts and submits `MsgDeposit` with a minimal amount (e.g., `1usei`) from each account to the same `proposalID`, each creating a new `Deposit` record via `AddDeposit`.
3. Once the proposal's voting/deposit period ends, `gov.EndBlocker` calls `RefundDeposits` (or `DeleteDeposits`), which iterates all N deposit records synchronously inside `EndBlock` on every validator.
4. As N grows large, this single-proposal cleanup work dominates `EndBlock` processing time chain-wide, risking block delay and blocking timely refunds for legitimate depositors on that proposal.

func (keeper Keeper) DeleteDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		err := keeper.bankKeeper.BurnCoins(ctx, types.ModuleName, deposit.Amount)

// AddDeposit adds or updates a deposit of a specific depositor on a specific proposal
// Activates voting period when appropriate
func (keeper Keeper) AddDeposit(ctx sdk.Context, proposalID uint64, depositorAddr sdk.AccAddress, depositAmount sdk.Coins) (bool, error) {
	// Checks to see if proposal exists
	proposal, ok := keeper.GetProposal(ctx, proposalID)
	if !ok {
		return false, sdkerrors.Wrapf(types.ErrUnknownProposal, "%d", proposalID)
	}

	// Check if proposal is still depositable
	if (proposal.Status != types.StatusDepositPeriod) && (proposal.Status != types.StatusVotingPeriod) {
		return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
	}
	if keeper.IncrementalTallyEnabled(ctx) && proposal.Status == types.StatusVotingPeriod {
		if proposal.VotingEndTime.Before(ctx.BlockTime()) || keeper.voteDelegationSnapshotFrozen(ctx, proposal) {
			return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
		}
	}

	// update the governance module's account coins pool
	err := keeper.bankKeeper.SendCoinsFromAccountToModule(ctx, depositorAddr, types.ModuleName, depositAmount)
	if err != nil {
		return false, err
	}

	// Update proposal
	proposal.TotalDeposit = proposal.TotalDeposit.Add(depositAmount...)
	keeper.SetProposal(ctx, proposal)

	// Check if deposit has provided sufficient total funds to transition the proposal into the voting period
	activatedVotingPeriod := false

	if proposal.Status == types.StatusDepositPeriod && proposal.TotalDeposit.IsAllGTE(keeper.GetDepositParams(ctx).GetMinimumDeposit(proposal.IsExpedited)) {
		keeper.ActivateVotingPeriod(ctx, proposal)

		activatedVotingPeriod = true
	}

	// Add or update deposit object
	deposit, found := keeper.GetDeposit(ctx, proposalID, depositorAddr)

	if found {
		deposit.Amount = deposit.Amount.Add(depositAmount...)
	} else {
		deposit = types.NewDeposit(proposalID, depositorAddr, depositAmount)
	}

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}

// ModuleAccountInvariant checks that the module account coins reflects the sum of
// deposit amounts held on store
func ModuleAccountInvariant(keeper Keeper, bk types.BankKeeper) sdk.Invariant {
	return func(ctx sdk.Context) (string, bool) {
		var expectedDeposits sdk.Coins

		keeper.IterateAllDeposits(ctx, func(deposit types.Deposit) bool {
			expectedDeposits = expectedDeposits.Add(deposit.Amount...)
			return false
		})

		macc := keeper.GetGovernanceAccount(ctx)
		balances := bk.GetAllBalances(ctx, macc.GetAddress())
		broken := !balances.IsEqual(expectedDeposits)

		return sdk.FormatInvariant(types.ModuleName, "deposits",
			fmt.Sprintf("\tgov ModuleAccount coins: %s\n\tsum of deposit amounts:  %s\n",
				balances, expectedDeposits)), broken
	}
