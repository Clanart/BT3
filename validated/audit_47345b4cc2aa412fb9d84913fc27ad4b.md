### Title
Reward-per-token precision loss causes permanent freezing of donated/queued reward tokens - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.sol` (and its sibling `BaseRewardPoolV2.sol`) compute the global reward index using a precision factor derived from the **staking token's** decimals (`10**stakingDecimals()`), not from the reward token's decimals or a fixed high-precision constant. When the staking token has 18 decimals and `totalStaked()` is large relative to a queued/donated reward amount of a lower-decimal token, the increment to `rewardPerTokenStored` truncates to zero, exactly as described in the external HAL-08 report for `HaloStakeVault.sol`'s `ACC_PRECISION` issue. This is reachable by an ordinary unprivileged wallet via the permissionless `donateRewards` function.

### Finding Description
`_provisionReward` updates the accumulator with:
```
rewardInfo.rewardPerTokenStored = rewardInfo.rewardPerTokenStored + (_amountReward * 10**stakingDecimals()) / this.totalStaked();
``` [1](#0-0) 

`stakingDecimals()` returns the decimals of `stakingToken` (typically 18 for HALO/receipt tokens), while `_amountReward` and `totalStaked()` are independent of that scale — `totalStaked()` is `IERC20(stakingToken).balanceOf(operator)` [2](#0-1) , and `_amountReward` is denominated in the reward token's own decimals (which can be lower, e.g. USDC-like tokens with 6 decimals). This mirrors the exact arithmetic pattern flagged in HAL-08: `amount * PRECISION / totalStaked`, where integer division truncates to 0 once `totalStaked` grows large enough relative to `amount * PRECISION`.

The tokens transferred in via `_provisionReward`'s `safeTransferFrom` (line 298-302) are pulled into the contract regardless of whether the division underflows to zero: `historicalRewards` is incremented, but `rewardPerTokenStored` is not, so no user's `earned()` value ever reflects those tokens. There is no `emergencyWithdraw`/rescue function in `BaseRewardPool.sol` to recover them, so the funds become permanently stuck in the contract.

Critically, `donateRewards` is a fully permissionless entry point — any ordinary wallet can call it for an already-registered reward token:
```
function donateRewards(uint256 _amountReward, address _rewardToken) external {
    if (!isRewardToken[_rewardToken]) revert MustBeRewardToken();
    _provisionReward(_amountReward, _rewardToken);
}
``` [3](#0-2) 

The same vulnerable pattern also exists in `BaseRewardPoolV2._provisionReward` [4](#0-3) , which is reachable through its own `queueNewRewards`/manager-triggered flow, but `donateRewards` in `BaseRewardPool.sol` is the clearest unprivileged path.

### Impact Explanation
Once `totalStaked()` (the staking token amount, 18 decimals) grows large enough relative to a `_amountReward * 10**stakingDecimals()` numerator, any subsequent low-value or low-decimal reward provisioning silently rounds `rewardPerTokenStored`'s increment to zero. The reward tokens are already pulled into the contract via `safeTransferFrom` and accounted in `historicalRewards`, but never become claimable by any staker and there is no recovery mechanism — a permanent freeze of those reward funds. Because `donateRewards` is unauthenticated, this state can be triggered by any ordinary wallet, and because it silently swallows any future queued reward whose value under the current `totalStaked()` rounds to zero, it can also perpetually suppress legitimate reward distributions for that token, causing permanent loss of unclaimed yield for all stakers of the pool.

### Likelihood Explanation
Likelihood is high in practice for pools using lower-decimal reward tokens (e.g., USDC/USDT-style 6-decimal tokens) paired with an 18-decimal staking token once `totalStaked()` reaches a large enough figure — a natural and expected end state for growing pools, not requiring any adversarial setup, and directly reachable by any address via `donateRewards`.

### Recommendation
Decouple the precision factor from `stakingDecimals()` and instead use a fixed high-precision constant (e.g., `1e18` or `1e36`) combined with the reward token's actual decimals when computing `rewardPerTokenStored`, mirroring the fix direction the HAL-08 remediation attempted. Additionally, revert (rather than silently truncate) when a reward provisioning would compute a zero increment, or accumulate the un-distributable remainder for correct later crediting instead of losing it permanently.

### Proof of Concept
1. Deploy `BaseRewardPool` with an 18-decimal `stakingToken` and register a 6-decimal `rewardToken` (e.g., mock USDC).
2. Grow `totalStaked()` (via normal deposits through `MasterMagpie`) to e.g. `10_000_001e18`.
3. Any wallet calls `donateRewards(10e6, rewardToken)` (10 USDC).
4. Inside `_provisionReward`: `rewardPerTokenStored += (10e6 * 1e18) / 10_000_001e18 = 0` (integer truncation), while `IERC20(rewardToken).safeTransferFrom` has already pulled in the 10 USDC.
5. `historicalRewards` increases by 10e6, but no user's `earned()` reflects any increase, and there is no function to withdraw the stranded 10 USDC — the funds are permanently frozen in the contract.

        IERC20(_rewardToken).safeTransferFrom(

            address(this),

        );

        rewardInfo.historicalRewards =

                rewardInfo.queuedRewards = 0;

                rewardInfo.rewardPerTokenStored +
