Based on my investigation, I found a concrete analog: an inconsistency in how GitHub Desktop validates file paths derived from repository content before invoking OS-level file operations. The codebase has a proper path-containment guard, `resolveWithin()` in `app/src/lib/path.ts`, which resolves symlinks via `realpath` and rejects any path that escapes the repository root [1](#0-0) . This guard is correctly used in `dispatcher.ts`'s `openRepositoryFromUrl` for deep-link file paths and in `copilot-conflict-context.ts` and `app-store.ts` for AI-conflict-resolution file writes [2](#0-1) [3](#0-2) .

However, the "Open with Default Program" action reachable from a commit's file context menu bypasses this guard entirely: [4](#0-3) 

The only checks gating this action are `fileExistsOnDisk` (existence) and `isSafeFileExtension(extension)` (an extension-name allow/deny list) — neither of which resolves symlinks or verifies containment within the repository, unlike `resolveWithin`.

### Title
Symlink-based file-read/execution escape via "Open with Default Program" bypassing the path-containment guard used elsewhere in Desktop - (File: `app/src/ui/history/selected-commits.tsx`)

### Summary
Git natively supports committing symlinks (mode `120000`). A malicious/compromised repository can commit a symlink whose name has an innocuous, "safe" extension (e.g. `notes.txt`) but which points outside the repository working directory (e.g. to `~/.ssh/id_rsa`, a shell profile, or an executable). When a victim who has cloned/fetched this repository browses its history and chooses "Open with Default Program" on that entry, GitHub Desktop resolves the path with a plain `Path.join(repository.path, file.path)` and hands it to the OS shell without ever calling `resolveWithin`, the very function the codebase already uses elsewhere specifically to reject symlink escapes.

### Finding Description
`onContextMenu` in `selected-commits.tsx` computes `fullPath = Path.join(repository.path, file.path)` and gates the "Open with Default Program" item purely on `isSafeFileExtension(extension) && fileExistsOnDisk` [5](#0-4) . Neither check inspects whether `file.path` is (or traverses through) a symlink that resolves outside the repository. This is the same class of bug as the external report: a security-relevant check (`resolveWithin`, analogous to Node's permission-policy check on `require`) exists and is used on some call paths, but an alternate, semantically-equivalent operation (`onOpenItem` / "Open with Default Program") reaches the same filesystem primitive through a different, unguarded route — exactly like `process.mainModule.__proto__.require()` reaching `require` without going through the checked `process.mainModule.require()`.

The dedicated `resolveWithin` guard specifically defends against this: its own test suite proves it detects and blocks a symlink used to escape a root directory [6](#0-5) , showing the developers are aware of and already mitigate this exact primitive in other code paths — just not in this one.

### Impact Explanation
If exploited, the victim's OS default-application handler opens (and for text files, displays) the content of a file outside the cloned repository, chosen entirely by the attacker who authored the malicious commit. This satisfies "file read outside the repo" / "credential exfiltration" (e.g., private key material, `.netrc`, `.git-credentials`, shell profiles) and, depending on the target and default-handler association, execution of external content. This does not require local/physical access, admin rights, prior malware, or leaked credentials — only that the victim clones/fetches a hostile repository and uses a normal Desktop feature.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to browse commit history and manually invoke "Open with Default Program" on a specific file — a two-click but ordinary Desktop workflow, not an "unnatural" step. Extension spoofing (naming the symlink `something.txt`) makes the file look benign and increases the chance a curious user opens it. The `isSafeFileExtension` allow-list does not protect against this because it only inspects the displayed filename's extension, not the actual resolved target.

### Recommendation
Route the resolved path through `resolveWithin(repository.path, file.path)` (as already done in `dispatcher.ts` and `copilot-conflict-context.ts`) before enabling/invoking `onOpenItem`, `revealInFileManager`, and any other direct `Path.join(repository.path, file.path)` usage that feeds into `shell.openExternal`/`shell.openPath`. Reject (or warn on) resolution failures the same way `openRepositoryFromUrl` does.

### Proof of Concept
1. Attacker creates a repository containing a symlink entry `notes.txt -> /home/victim/.ssh/id_rsa` (mode `120000`), commits and pushes it.
2. Victim clones or fetches the repository in GitHub Desktop and opens the History view.
3. Victim right-clicks `notes.txt` in a commit's changed-files list and selects "Open with Default Program".
4. `onOpenItem` builds `fullPath = Path.join(repository.path, 'notes.txt')` and passes it to `shell.openExternal`/`openPath` without any `resolveWithin` containment check; the OS follows the symlink and opens `~/.ssh/id_rsa` in the default text viewer, exposing its contents to the attacker-controlled UI/workflow (e.g., if screen-shared, or if the victim is guided to copy/paste it).

**Uncertainty note:** I could not fully view the body of `onOpenItem` itself (only its enable condition and call site were indexed), so I cannot cite the exact `shell.openExternal`/`openPath` invocation line inside that handler; a Devin session with full file access would be needed to confirm the exact downstream call and add a definitive fix in that function alongside the enable-check.
