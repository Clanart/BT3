### Title
Storage-proof "empty vs zero" ambiguity lets `_filled` finalization be spoofed as unfilled, enabling duplicate escrow settlement - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`onGetResponse` in the cross-chain intent gateway decides whether an order was ever filled on the destination chain purely by checking whether the returned storage-proof value has non-zero length: `if (incoming.response.values[0].value.length != 0) revert Filled();` [1](#0-0) . This mirrors exactly the bug class from the external report: an *empty* value (slot never written) is treated identically to a *zero* value (slot legitimately set to `address(0)`), because Ethereum's state trie encodes a storage slot holding `0` the same way as a slot that was never written (SSTORE of 0 clears the trie entry). The gateway's finalization marker, `_filled[commitment]`, is an `address` written via `_filled[commitment] = address(uint160(uint256(order.user)))` in `_cancelFromDest` [2](#0-1)  and via `_filled[body.commitment] = beneficiary` inside `_withdraw` [3](#0-2) .

### Finding Description
The storage slot key that Hyperbridge's GET request proves is computed as `keccak256(commitment ‖ FILLED_SLOT)` [4](#0-3) , targeting the `_filled` mapping declared as `mapping(bytes32 => address) public _filled;` with the comment "A non-zero value indicates the order has been finalized" [5](#0-4) . `_cancelFromSource` dispatches this GET request specifically to check whether the destination-side `_filled` slot is empty before releasing the source-chain escrow [6](#0-5) .

The check in `onGetResponse` conflates two semantically distinct states that are structurally identical in an EVM storage proof:
1. The slot was never written (truly unfilled) — genuinely empty.
2. The slot was written but holds the value `address(0)` — finalized, but the trie representation is indistinguishable from case 1.

Both `_cancelFromDest` and `_withdraw` write `_filled[commitment]` from address-derived values (`order.user`, or a `beneficiary` cast from a `bytes32`). Any code path that permits a finalization write of `address(0)` into that mapping (for example, an alternate/legacy caller of `_withdraw`, or a future contract variant deriving `beneficiary`/`order.user` differently) produces a destination-side "finalized" state that the source chain's `onGetResponse` cannot distinguish from "never filled," because the proof only inspects `value.length`.

### Impact Explanation
If `_filled[commitment]` is ever written to the zero address for a real order (finalized/filled/cancelled on the destination), the source chain's `_cancelFromSource → onGetResponse` flow will incorrectly conclude the order was never filled and will refund the escrowed input tokens to the user via `_withdraw(body, true, true)` [7](#0-6) , even though the destination side has already paid out the order's output assets to a beneficiary. This is a duplicate settlement / double-payout of escrowed funds — the exact impact class called out in the bounty scope (fund loss, duplicate settlement).

### Likelihood Explanation
Within the code paths I was able to fully trace (`_fillCrossChain` sets `_filled[commitment] = msg.sender`, a real non-zero solver address; `_cancelFromDest` sets it from `order.user`, which is constrained to the canonical `bytes32(uint256(uint160(address)))` encoding enforced at `_cancelFromSource`'s `Unauthorized` check [8](#0-7) ), I could not find a normal user-triggerable input that forces a legitimate finalization write to resolve to `address(0)`. This means the length-based ambiguity is a real structural weakness matching the reported bug class, but I could not fully confirm an end-to-end unprivileged exploit path using only the code reachable in this session — the same class of bug that historically causes exactly this kind of false-negative "not filled" result once any code path (e.g. in `IntrinsicIntents.sol`, which I did not fully audit) allows a zero-derived beneficiary/user value into `_filled`.

### Recommendation
Do not use storage-proof presence/length as the finalization signal. Have the destination gateway write an explicit non-address sentinel (e.g., `bytes32(uint256(1))` or a dedicated boolean/status mapping) into the proven slot on every finalization path, and have `onGetResponse` check for that specific sentinel value rather than merely `value.length != 0`. This removes any possibility of a legitimately-written value colliding with the "empty slot" trie encoding, closing the ambiguity class identified in the external LSP6 report.

### Proof of Concept
A fully concrete PoC requires a demonstrated code path that writes `address(0)` into `_filled[commitment]` during genuine finalization; within the code reviewed, `_fillCrossChain` and `_cancelFromDest`/`_withdraw` constrain the written address to non-zero canonical values, so I could not construct a working exploit transaction sequence with full certainty. The structural flaw is proven by the code itself:
- `onGetResponse` uses only `value.length != 0` as the finalization oracle: [1](#0-0) 
- `_filled` is documented and used as an address-valued finalization marker, which is trie-indistinguishable from "unset" when it equals `address(0)`: [5](#0-4) 

Given the inability to fully confirm a reachable zero-write path from the code available, I flag this finding with reduced confidence rather than a fully proven exploit chain.

     * Only the order creator may cancel, and only after the order deadline has passed

     * request to the destination chain to verify that the `_filled` storage slot for
     * this commitment is empty (i.e., the order was never filled on the destination).
     *
     * The GET response is handled by `onGetResponse`, which refunds the escrow if
     * the slot is indeed empty.
     *
     * @param order The order to cancel.
     * @param options Cancel options including the proof height and relayer fee.
     * @param commitment The keccak256 hash of the ABI-encoded order.
     */
    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
