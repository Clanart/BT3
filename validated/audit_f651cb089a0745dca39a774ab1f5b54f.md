### Title
Silent `TokenPair` deletion on ERC20 self-destruct permanently orphans escrowed collateral backing circulating native coins - (File: x/erc20/keeper/msg_server.go)

### Summary
This is the closest reachable analog to the `ShortToken.adjustPosition()` bug class ("burn/destroy an accounting entity without checking it still backs value"). In `x/erc20`, `ConvertERC20` and `ConvertCoin` both silently delete the `TokenPair` registry entry the moment the underlying "native ERC20" contract loses its code hash (self-destructed), without any check on whether the erc20 module account (`types.ModuleAddress`) still holds escrowed ERC20 collateral or whether there is still outstanding native-coin supply for that denom.

### Finding Description
`ConvertERC20` and `ConvertCoin` share the same pattern: [1](#0-0) [2](#0-1) 

Both check `acc == nil || !acc.HasCodeHash()` for the token-pair's ERC20 contract, and if true, call `k.DeleteTokenPair(ctx, pair)` and return `(nil, nil)` — a "successful" no-op transaction: [3](#0-2) 

`DeleteTokenPair` unconditionally wipes the `Erc20Map`, `DenomMap`, and all `Allowances` for that pair — exactly analogous to `ShortToken._burn(positionId)` firing on `shortAmount == 0` with no check of `collateralAmount != 0`. Here, the "position" is the `TokenPair`, and the "collateral" is:
1. Any ERC20 tokens escrowed in the `x/erc20` module account from prior `ConvertERC20` calls (`convertERC20IntoCoinsForNativeToken` escrows tokens via `transfer` to `types.ModuleAddress`) — see the escrow step at [4](#0-3) .
2. Any native Coins of that denom still circulating among users, minted 1:1 against that escrowed collateral (`ConvertCoinNativeERC20` burns/mints coins against the same collateral pool) — see [5](#0-4) .

Once the underlying contract's code hash is gone (self-destruct via `DeleteAccount`, which wipes balance, code, code hash, and *all* contract storage including the ERC20 `balances` mapping for every holder — see [6](#0-5) ), the `TokenPair` registry (the only bookkeeping link between the bank-side coin denom and the EVM-side collateral) is deleted the instant *any* user next calls `ConvertCoin`/`ConvertERC20`/`OnRecvPacket` against that denom. This deletion happens silently and irreversibly, with no reconciliation of the module's escrow balance or the coin's circulating supply, and no error is surfaced to the caller (`return nil, nil`).

The `RegisterERC20` entrypoint is permissionless when `params.PermissionlessRegistration` is true: [7](#0-6) 
so an unprivileged attacker can deploy and register an arbitrary "native ERC20" contract, let honest users convert into/out of it (building up genuine escrow and circulating coin supply), then self-destruct the contract. The next unrelated user interaction with that denom triggers the silent `DeleteTokenPair`, permanently destroying the only record needed to ever reconcile, freeze, or safely wind down the now-uncollateralized coin supply — the module-side escrow tokens are unrecoverable (their storage was wiped by the self-destruct) and the coin denom itself becomes an untracked, unbacked, freely-transferable liability with no registry path left to disable/handle it.

### Impact Explanation
This corrupts the 1:1 accounting invariant between native Coins and their ERC20/escrow backing that `x/erc20` is supposed to preserve. After the `TokenPair` is deleted, previously-minted Coins for that denom continue to be fully spendable/transferable via the bank module, but all bookkeeping tying them to real collateral is gone — an irreversible accounting corruption of spendable user value, matching the "unauthorized minting/burning/duplication/resurrection or irreversible accounting corruption" impact class. It also permanently stops governance/`ToggleConversion` or any other administrative response from being able to reference the pair again, since `GetTokenPairID` (via `DenomMap`/`ERC20Map`) returns nothing after deletion.

### Likelihood Explanation
Reachability hinges on whether `x/vm`'s full-wipe `DeleteAccount` path (which clears code, code hash, and *all* storage) is the code path actually invoked on ordinary post-creation self-destructs, versus a partial EIP-6780-style clear that leaves code/storage untouched for contracts not created in the same transaction (the statedb-level `SelfDestruct6780` gates full deletion on `stateObject.newContract`). I could not fully confirm from the indexed files which self-destruct path is wired into the committed/persisted flow for a contract self-destructed in a transaction *after* its creation transaction (the common case for a registered token pair). If the full-wipe path is reachable for normal (non-same-tx) self-destructs, likelihood is high given permissionless registration and self-destruct being a standard, unprivileged EVM operation available to any contract deployer. If only EIP-6780 semantics apply, the code path in `ConvertERC20`/`ConvertCoin` may rarely trigger, lowering likelihood.

### Recommendation
Before calling `k.DeleteTokenPair`, verify there is no remaining collateral/liability tied to the pair: check that the module account's ERC20 token balance for that contract is zero and that the circulating supply of `pair.Denom` (bank `GetSupply`) is zero. If either is non-zero, do not delete the pair; instead disable conversion (`Enabled = false`) while preserving the registry mapping, and expose a governance-gated recovery/write-off path, mirroring the recommended fix of not burning an entity while it still holds value.

### Proof of Concept
Conceptual reproduction (not run against the live repo due to read-only access):
1. With `params.PermissionlessRegistration = true`, an attacker deploys a normal-looking ERC20 contract and calls `MsgRegisterERC20` to create a `TokenPair` (`OWNER_EXTERNAL`/native ERC20 pair).
2. Honest users call `ConvertERC20` to escrow ERC20 tokens into `types.ModuleAddress` and receive minted native coins of `pair.Denom`.
3. The attacker (or the contract itself) self-destructs the ERC20 contract.
4. Any subsequent call to `ConvertCoin`/`ConvertERC20`/`OnRecvPacket` referencing `pair.Denom` or the contract address hits the `acc == nil || !acc.HasCodeHash()` branch and calls `k.DeleteTokenPair`, wiping `ERC20Map`/`DenomMap`/`Allowances` while native coins of `pair.Denom` remain in circulation and the module's escrowed balance record is gone, with the transaction reported as successful (`nil, nil`).

// DeleteTokenPair removes a token pair.
func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
}

func (k *Keeper) DeleteAccount(ctx sdk.Context, addr common.Address) error {
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	acct := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	if acct == nil {
		return nil
	}

	// NOTE: only Ethereum contracts can be self-destructed
	if !k.IsContract(ctx, addr) {
		return errors.New("only smart contracts can be self-destructed")
	}

	// set account to a base account to set the whole balance as spendable
	baseAccount := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	k.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(cosmosAddr, baseAccount.GetPubKey(), baseAccount.GetAccountNumber(), baseAccount.GetSequence()))

	// clear balance
	if err := k.SetBalance(ctx, addr, new(uint256.Int)); err != nil {
		return err
	}

	var keys []common.Hash

	// clear storage
	k.ForEachStorage(ctx, addr, func(key, _ common.Hash) bool {
		keys = append(keys, key)
		return true
	})

	for _, key := range keys {
		k.DeleteState(ctx, addr, key)
	}

	// clear code hash
	k.DeleteCodeHash(ctx, addr)

	// remove auth account
	k.accountKeeper.RemoveAccount(ctx, acct)

	k.Logger(ctx).Debug(
		"account suicided",
		"ethereum-address", addr.Hex(),
		"cosmos-address", cosmosAddr.String(),
	)

	return nil
}
