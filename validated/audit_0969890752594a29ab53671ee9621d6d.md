### Title
MGP emission accrual has no end condition or balance check, causing permanent freezing of unclaimed MGP rewards once the contract's MGP balance is exhausted - (File: `rewards/MasterMagpie.sol`)

### Summary
`MasterMagpie` accrues MGP rewards to every pool at a fixed `mgpPerSec` rate indefinitely, with no timestamp cutoff and no check that the contract's actual MGP token balance is sufficient to cover the amounts it has already promised to users. Because MGP is a fixed-supply ERC20 pre-minted once [1](#0-0) , `MasterMagpie` can only ever pay out MGP rewards up to whatever balance it happens to hold; once that balance is spent, every future claim that includes an MGP payout will revert.

### Finding Description
`updatePool` computes `accMGPPerShare` purely as a function of elapsed time and `mgpPerSec`, with no reference to the contract's remaining MGP balance and no expiry timestamp: [2](#0-1) 

This accrued, ever-growing entitlement is later paid out via `_sendMGP`, which does a plain `safeTransfer` from the contract's own balance with no pre-check that sufficient MGP is available: [3](#0-2) 

The same unchecked-transfer pattern is used for the vlMGP-locking and vlMGP-pool payout paths (`_sendVlMGPFor`, `_sendMGPForVlMGPPool`), all of which rely on `MasterMagpie` already holding enough MGP: [4](#0-3) .

These payout functions are reached through ordinary, unprivileged claim entry points such as `multiclaimSpec` / `multiclaimFor`, which any user can call at any time: [5](#0-4) . Inside `_multiClaim`, MGP amounts across all of a user's pools are aggregated and sent in a single call at the end of the loop [6](#0-5) ; if that final transfer reverts because the contract ran out of MGP, the entire claim transaction (including all other, unrelated reward tokens bundled in the same call) reverts as well — an all-or-nothing failure mode exactly analogous to the referenced Olympus report.

Unlike `BaseRewardPool`/`BaseRewardPoolV2`/`vlMGPBaseRewarder`'s `queueNewRewards`, which correctly pull the exact reward amount from the caller via `safeTransferFrom` at the time it is queued (i.e., already implementing the report's recommended fix) [7](#0-6) , the core MGP emission mechanism in `MasterMagpie` has no equivalent funding guarantee: `mgpPerSec` accrues perpetually against whatever fixed MGP balance the contract was seeded with, with no mechanism tying the emission rate/duration to the available balance.

### Impact Explanation
Because the total MGP supply is fixed and minted once to a single recipient at deployment, and `MasterMagpie`'s accrual has no end timestamp, the contract's committed (accrued but unclaimed) MGP obligations grow monotonically over time while its actual token balance only decreases as it pays out. Eventually the balance will be insufficient to cover all outstanding accrued rewards. At that point, any user claim path that would send MGP (`multiclaimSpec`, `multiclaimFor`, withdraw-with-harvest, vlMGP forfeiture harvesting, etc.) permanently reverts for every user, since MGP payment is bundled into the same atomic transaction as all other reward types. This results in a permanent freeze of user-owned unclaimed yield with no user-triggerable recovery path.

### Likelihood Explanation
This does not require any admin/governance misbehavior — it is a deterministic consequence of the accrual design given a fixed-supply reward token and unbounded, uncapped time-based accrual. It will occur whenever the MGP allocated to `MasterMagpie` for emissions is exhausted relative to the rate and duration it has been emitting, i.e., it is a "when," not "if," scenario as described in the reference report's title.

### Recommendation
Track a cap or remaining-balance check in `updatePool`/`_calMGPReward` so that `accMGPPerShare` cannot accrue beyond what the contract can pay out, and/or require an explicit funding mechanism (e.g., pulling MGP proportional to accrual, similar to `queueNewRewards`' `safeTransferFrom` pattern) rather than relying on a static pre-funded balance with perpetual accrual and no expiry.

### Proof of Concept
1. `MasterMagpie` is funded with a finite amount of MGP tokens and `mgpPerSec` / pool `allocPoint`s are set.
2. Over time, `updatePool` (triggered by ordinary user deposit/withdraw/claim calls) keeps incrementing `accMGPPerShare` for every pool indefinitely, per [2](#0-1) .
3. Users progressively claim via `multiclaimSpec`/`multiclaimFor`, each time calling `_sendMGP`/`_sendVlMGPFor`/`_sendMGPForVlMGPPool`, which transfer directly from `MasterMagpie`'s MGP balance [4](#0-3) .
4. Once cumulative accrued-and-claimed MGP approaches the contract's original balance, a subsequent ordinary claim's MGP transfer underflows the balance and reverts inside `_multiClaim`'s aggregated send step [8](#0-7) , causing that entire multi-token claim transaction to fail for any user attempting to claim, permanently freezing their accrued MGP rewards.

```text
    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }    
```
