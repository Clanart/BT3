Based on the code I reviewed, the strongest analog to the `SRAV` bug — "one operand gets its safety mask applied, but a sibling operand of the same operation does not" — is in `parse-app-url.ts`, which handles GitHub Desktop's custom protocol handler (deep links like `x-github-client://openRepo/...`).

### Title
Deep-link `openRepo` action leaves the `filepath` query parameter completely unvalidated while sibling parameters are checked - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` validates the `pr` parameter against `/^\d+$/` and the `branch` parameter against both a PR-branch regex and `testForInvalidChars` (which rejects control characters, `..`, path separators, etc., per `app/src/lib/sanitize-ref-name.ts`), but the `filepath` parameter is read via `getQueryStringValue` and passed straight through into the returned `IOpenRepositoryFromURLAction` with no validation at all. [1](#0-0) 

### Finding Description
This mirrors the `SRAV` pattern exactly: the report's bug is that some shift amounts get masked (`& 0x1F`) while one code path uses the raw, unvalidated value. Here, `branch` is masked against `testForInvalidChars` (which blocks `..`, path separators effectively via the ref-name regex) and `pr` is masked against a digit-only regex, but `filepath` — which is attacker-controlled from a clicked deep link — has no equivalent guard: [1](#0-0) 

Compare with the explicit `testForInvalidChars` check applied only to `branch`: [2](#0-1) 

I traced that `filepath` is referenced downstream in `app/src/ui/dispatcher/dispatcher.ts` (6 occurrences) and `app/src/main-process/main.ts` (1 occurrence), which is consistent with it eventually being used to construct a path relative to the opened repository (e.g., to reveal/open a specific file after handling `openRepo`). I was not able to fully retrieve those call sites in this session to confirm the exact join/consumption logic, so **the exact sink and whether it uses `Path.join`/`resolveWithin` guarding is unverified** — this is a real limitation of this analysis.

### Impact Explanation
If the unverified sink joins `filepath` with the repository's working directory without going through the same `resolveWithin` traversal guard used elsewhere in this codebase (e.g., `app/src/lib/path.ts` `_resolveWithin`, used in `copilot-conflict-context.ts`), a crafted deep link such as:
```
x-github-client://openRepo/https://github.com/owner/repo?branch=main&filepath=..%2F..%2F..%2F.ssh%2Fid_rsa
```
could cause Desktop to open/reveal a file outside the cloned repository when the user clicks the link — matching the "attacker controls ... a link or deep link the user clicks" and "file ... read outside the repo" criteria in the Valid Impact definition.

### Likelihood Explanation
Moderate-to-uncertain. The asymmetric validation (branch/pr checked, filepath not) is confirmed directly in the source and is a clear implementation gap analogous to the missing `& 0x1F` mask in the report. However, actual exploitability depends entirely on how `filepath` is consumed downstream (dispatcher.ts / main.ts), which I could not fully verify in this session — if the consumer already uses `resolveWithin` or `Path.basename`-style sanitization (as the codebase does elsewhere, e.g. `sanitizeCloneName` in `app/src/lib/remote-parsing.ts` and `_resolveWithin` in `app/src/lib/path.ts`), the impact would be neutralized despite the missing check at parse time.

### Recommendation
Apply the same validation discipline used for `branch` to `filepath`: reject or sanitize it with `testForInvalidChars`/`sanitizedRefName`-style logic at parse time in `parseAppURL`, and additionally ensure any downstream consumer resolves `filepath` against the repository root using `resolveWithin` (`app/src/lib/path.ts`) before touching the filesystem, exactly as `copilot-conflict-context.ts` already does for other repo-relative paths. [3](#0-2)

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
