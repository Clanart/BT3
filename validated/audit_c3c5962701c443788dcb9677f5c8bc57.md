Confirmed: `Error::StaleMmrLeaf` exists in the shared error enum but is only ever constructed in `sp1.rs`; `verify_mmr_update_proof` in `lib.rs` never references it, and there's no corresponding freshness check or test in `test.rs` for the naive path.### Title
Naive BEEFY MMR path accepts stale MMR leaves, suppressing authority-set rotation - (File: `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
`verify_mmr_update_proof` (the `PROOF_TYPE_NAIVE` consensus path) never checks that `mmr.latest_mmr_leaf` is the leaf appended immediately before `commitment.block_number`. The sibling `verify_sp1_consensus` path explicitly guards against this with a `StaleMmrLeaf` check, but that guard was never ported to the naive path.

### Finding Description
`verify_mmr_update_proof` only rejects a proof if the overall height is stale: [1](#0-0) 

It then verifies the BEEFY commitment signatures/authority-set membership, and separately verifies that `mmr.latest_mmr_leaf` is included in the signed MMR root via `verify_mmr_leaf`, using a relayer-supplied `leaf_index`: [2](#0-1) [3](#0-2) 

Because an MMR is append-only, every historical leaf remains provable against any later root — there is nothing in `verify_mmr_leaf` or `verify_mmr_update_proof` that ties the chosen `leaf_index`/leaf's `parent_number_and_hash` to `commitment.block_number`. A relayer/unprivileged submitter can therefore supply a correctly-verifying MMR sub-proof for an *older* leaf while still satisfying the commitment/signature checks for the true, later `block_number`, then have the code advance `trusted_state.latest_beefy_height` while skipping the authority-set rotation logic that depends on `mmr.latest_mmr_leaf.beefy_next_authority_set`: [4](#0-3) 

By contrast, `verify_sp1_consensus` explicitly documents and enforces this exact invariant: [5](#0-4) 

and there is a dedicated regression test proving the SP1 path rejects a stale leaf: [6](#0-5) 

No equivalent test or check exists for `verify_mmr_update_proof`, and the shared `Error::StaleMmrLeaf` variant is documented as applying to "the proof" generically but is only ever constructed from `sp1.rs`: [7](#0-6) 

### Impact Explanation
This is reachable through the unprivileged, permissionless naive consensus proof submission path (`PROOF_TYPE_NAIVE` in `BeefyConsensusClient::verify_consensus`): [8](#0-7) 

An attacker who can produce a valid BEEFY commitment/signature set (which, per the scope, is not a "malicious relayer" assumption but simply using genuinely finalized, publicly available relay-chain commitments/leaves) can pick an MMR leaf older than the true latest leaf as of `block_number`, letting `trusted_state.latest_beefy_height` advance to that block while `next_authorities`/`current_authorities` do not get rotated. This strands the light client on a retired authority set, later allowing proofs signed by an authority set that should have been superseded to be accepted as valid consensus updates — a false-state-acceptance outcome directly in scope ("Consensus proofs... must never let false remote state become trusted").

### Likelihood Explanation
Medium-to-high: the attacker does not need any special access or compromised infrastructure — any party able to submit a naive consensus proof (an unprivileged message/proof path) can select which historical MMR leaf to attach, as long as it verifies against the currently signed root, which append-only MMR structure guarantees for any past leaf. The BEEFY commitment/signature verification and MMR-inclusion checks would all pass; only the missing freshness check stands between this and exploitation.

### Recommendation
Add the same freshness check used in `verify_sp1_consensus` to `verify_mmr_update_proof`/`verify_mmr_leaf`: require `mmr.latest_mmr_leaf.parent_number_and_hash.0.saturating_add(1) == commitment.block_number` (returning `Error::StaleMmrLeaf` otherwise), so the accepted leaf is provably the one truly latest as of the committed height, matching the invariant already enforced on the SP1 path.

### Proof of Concept
1. Trusted state at height `H-1` with `current_authorities = {id: N}`, `next_authorities = {id: N+1}`.
2. Relay chain finalizes block `H`, whose true latest MMR leaf carries `beefy_next_authority_set = {id: N+1}` (i.e., a rotation to `N+1` is due).
3. Attacker builds an `MmrProof` for `commitment.block_number = H` (a genuine, validly-signed commitment) but substitutes `latest_mmr_leaf` with an older leaf (e.g., parent block `H-500`) whose `beefy_next_authority_set.id <= N` (no rotation), together with a correct MMR inclusion sub-proof/`leaf_indices` for that older leaf against the same signed root (valid, since MMR is append-only).
4. Submit via `verify_mmr_update_proof`: all checks (stale height, supermajority, authorities merkle proof, MMR leaf inclusion) pass; `trusted_state.latest_beefy_height` is set to `H`, but `next_authorities`/`current_authorities` are left unrotated because `mmr.latest_mmr_leaf.beefy_next_authority_set.id (<=N)` is not greater than `trusted_state.next_authorities.id (N+1)`.
5. This mirrors exactly the scenario `rejects_sp1_proof_carrying_a_stale_mmr_leaf` guards against for the SP1 path — build the analogous test for `verify_mmr_update_proof` and observe it currently succeeds (`Ok`) rather than returning `Error::StaleMmrLeaf`, confirming the missing invariant.

```rust
fn verify_mmr_leaf<H: Keccak256 + Send + Sync>(
	mmr: &MmrProof,
	mmr_root: H256,
) -> Result<(), Error> {
	// `leaf_indices` is supplied by the relayer in the unsigned consensus message;
	// an empty vector previously panicked the runtime via the unchecked `[0]` index
	// after the BEEFY signature and authority membership checks had already succeeded.
	// This verifier checks a single MMR leaf, so reject any proof that does not carry
	// exactly one leaf index.
	if mmr.mmr_proof.leaf_indices.len() != 1 {
		Err(Error::InvalidMmrProof)?
	}
	let leaf_index = mmr.mmr_proof.leaf_indices[0];
	let leaf_hash = H::keccak256(&mmr.latest_mmr_leaf.encode());
	let mmr_size = leaf_index_to_mmr_size(leaf_index);

	let mmr_proof = MmrMerkleProof::<[u8; 32], KeccakMerge<H>>::new(
		mmr_size,
		mmr.mmr_proof.items.iter().map(|h| (*h).into()).collect(),
	);
	let leaf_pos = leaf_index_to_pos(leaf_index);
	let leaf = (leaf_pos, leaf_hash.into());
	let valid = mmr_proof
		.verify(mmr_root.into(), vec![leaf])
		.map_err(|e| Error::MmrVerificationFailed(e.to_string()))?;

	if !valid {
		Err(Error::InvalidMmrProof)?
	}

	Ok(())
}
```

```rust
fn rejects_sp1_proof_carrying_a_stale_mmr_leaf() {
	use beefy_verifier_primitives::Sp1BeefyProof;

	const SET_ID: ValidatorSetId = 42;
	const BLOCK_NUMBER: u32 = 1_000;
	// Mainnet SP1Beefy verification key, as in the fixture test above.

		latest_beefy_height: BLOCK_NUMBER - 1,
		beefy_activation_block: 0,
		mmr_root_hash: H256::zero(),
		current_authorities: authority_set(SET_ID, 100),
		next_authorities: authority_set(SET_ID + 1, 100),
	};

	let mut proof = Sp1BeefyProof {
		block_number: BLOCK_NUMBER,
		validator_set_id: SET_ID,
		mmr_leaf: MmrLeaf {
			version: MmrLeafVersion::new(0, 0),
			parent_number_and_hash: (BLOCK_NUMBER - 1, H256::zero()),
			beefy_next_authority_set: BeefyNextAuthoritySet {
				id: SET_ID + 1,
				len: 100,
				keyset_commitment: H256::zero(),
			},
			leaf_extra: H256::zero(),
		},
		headers: vec![],
		proof: vec![],
		nonce: H256::zero(),
	};

	// The leaf appended at `BLOCK_NUMBER` clears the freshness check and is only rejected
	// later, by the Groth16 verifier — so the check discriminates on leaf freshness alone.
```
