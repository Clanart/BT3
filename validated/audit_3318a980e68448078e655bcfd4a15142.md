### Title
Webhook shop-domain header is not cryptographically bound to the HMAC signature, enabling cross-shop identity spoofing - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates a webhook solely by comparing an HMAC of the raw body against the app's shared client secret, while the shop identity used downstream (`shop_domain`, reading `HTTP_X_SHOPIFY_SHOP_DOMAIN`) is never included in that HMAC computation. Because the client secret is shared across every shop that installs the app, a merchant who legitimately installs the app on their own store can capture a genuinely-signed webhook (raw body + valid HMAC) and replay it to the same endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop, producing a request that passes verification but is misattributed to the victim shop.

### Finding Description
The verification logic lives in `lib/shopify_app/controller_concerns/webhook_verification.rb`: [1](#0-0) 

`verify_request` only calls `hmac_valid?(request.raw_post)`, which is defined in `lib/shopify_app/controller_concerns/payload_verification.rb`: [2](#0-1) 

The HMAC is computed only from the raw request body and one of `ShopifyApp.configuration.secret` / `old_secret` — both app-level (not shop-level) secrets shared by every shop that installs the app. Nothing in this computation includes `HTTP_X_SHOPIFY_SHOP_DOMAIN`, `HTTP_X_SHOPIFY_TOPIC`, or any other header. Yet the `shop_domain` helper in the same concern trusts that header directly as shop identity: [3](#0-2) 

The gem's own documented custom-controller pattern uses this untrusted value to dispatch shop-scoped jobs: [4](#0-3) 

Exploit flow: a merchant installs the target app on their own shop (`attacker.myshopify.com`) and legitimately receives a real Shopify webhook — a valid `(raw_body, HMAC)` pair signed with the app's shared secret. They then POST that same body to `POST /webhooks/:type` (or a custom controller built per the documented pattern) but replace `X-Shopify-Shop-Domain` with a victim's domain (`victim.myshopify.com`). Because `hmac_valid?` never checks the shop-domain header, the forged request passes `verify_request`, and any downstream code that reads `shop_domain` (as the gem's own docs instruct) will act as though the payload originated from the victim shop.

### Impact Explanation
This enables cross-shop data spoofing: an attacker who legitimately controls one shop can make the host application believe a webhook (e.g. `orders/create`, `customers/data_request`, `shop/redact`) came from a different, unrelated shop, causing the app to create, mutate, or delete data keyed to the victim shop, or to enqueue privacy-mandated jobs against the wrong shop. This matches the Shopify HackerOne "cross-shop data spoofing via forged webhook headers" impact class described in the prompt.

### Likelihood Explanation
The only precondition is that the attacker installs the app on a shop they control (a normal, unprivileged action available to any Shopify merchant) and is able to capture one real webhook delivery, which is trivial (the app receives them constantly, and merchants can view their own store's webhook traffic via any request logger they control). No secret leak, no host misconfiguration, and no social engineering of the victim is required — this is fully repeatable and requires only the documented, encouraged usage pattern (`shop_domain` in `WebhookVerification`).

### Recommendation
Do not treat `HTTP_X_SHOPIFY_SHOP_DOMAIN` as a trusted identity. Bind shop identity to the verified request, e.g. by looking up the shop from an authenticated source (registered webhook subscription / session) rather than the raw header, or reject requests where the header's shop cannot be independently correlated with the API client that owns the given topic subscription. At minimum, document prominently that `shop_domain` is attacker-controllable and must be cross-checked against known installed shops before being used to scope any data operation.

### Proof of Concept
```ruby
# test/shopify_app/controller_concerns/webhook_verification_test.rb (illustrative addition)
test "hmac verification does not bind shop-domain header, allowing spoofing" do
  with_application_test_routes do
    params = { foo: "anything" }
    valid_hmac = "yCGX/RrK4fcuNtr3ztk5tQGsOBjcAzHpGLdMUrbV8yI=" # valid HMAC over the same body, from attacker's own shop delivery
    @request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"] = valid_hmac
    @request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"] = "victim-shop.myshopify.com" # attacker-forged, unrelated shop
    post :webhook_action, params: params
    assert_response :ok # passes verify_request despite shop_domain header being forged/unbound to HMAC
  end
end
```
This demonstrates that `verify_request` accepts the request purely based on body+shared-secret HMAC, regardless of what `HTTP_X_SHOPIFY_SHOP_DOMAIN` claims, confirming the header is not cryptographically bound to the signature.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
