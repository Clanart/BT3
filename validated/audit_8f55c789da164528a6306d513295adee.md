### Title
`SchnorrAggregate::verify` accepts a trivially forged signature when zero statements are verified - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to the unguarded zero-amount swap in `CurveSpell.closePositionFarm`, `SchnorrAggregate::verify` performs no check that at least one statement is being verified. When `keys_and_challenges` is empty and the attacker supplies an aggregate with `Rs = []` and `s = 0`, the multiexp reduces to a single term `(-0) * G = identity`, so verification unconditionally succeeds — a vacuous truth that lets anyone forge an aggregate Schnorr signature for an empty statement set.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregate::verify` first checks `self.Rs.len() != keys_and_challenges.len()` and returns `false` only on mismatch (line 128). An attacker-controlled `SchnorrAggregate` can be deserialized via `SchnorrAggregate::read` (lines 77–88) with a `u32` length of `0` followed by a zero scalar, giving `Rs = []` and `s = F::ZERO`. If the verifier calls `verify(dst, &[])` — e.g., a batch that ended up containing no signatures — the length check passes, the loop pushes no pairs, and the only multiexp term is `(-self.s, C::generator())` (line 144), i.e. `0 * G`. `multiexp_vartime(&pairs).is_identity()` (line 145) then evaluates to `true`. `SchnorrAggregator::complete` refuses to produce an empty aggregate (line 176: `if self.sigs.is_empty() { return None; }`), so honest aggregation can never create this object — the accept path exists only through attacker-supplied bytes via `read`, exactly the "zero input not guarded" shape of the reference bug.

### Impact Explanation
An unprivileged party can produce bytes (4 bytes of `0u32` length + a zero field element encoding) that verify as a valid `SchnorrAggregate` against an empty challenge list. In any integration where an empty statement list is a reachable state — for example, verification of a filtered/aggregated batch where all candidate signatures were excluded — the aggregate signature check is bypassed entirely. This constitutes a forged signature acceptance at the verifier boundary.

### Likelihood Explanation
Exploitation requires the calling context to invoke `verify` with an empty `keys_and_challenges` slice, which is a plausible edge case when aggregating over dynamically-sized sets (the same class of "zero quantity slips past a guard" as the reference report). No secret material, threshold cooperation, or malformed curve points are needed; the forgery is purely public input.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::verify`:

```diff
   pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
+    if keys_and_challenges.is_empty() {
+      return false;
+    }
     if self.Rs.len() != keys_and_challenges.len() {
       return false;
     }
```

A defensive `if self.Rs.is_empty() { return false; }` (or rejecting zero-length `Rs` in `SchnorrAggregate::read`) achieves the same.

### Proof of Concept

```rust
// crypto/schnorr — conceptual PoC for C = Secp256k1 (or any Ciphersuite)
// Attacker bytes: u32 length = 0, then a zero scalar.
let mut bytes = 0u32.to_le_bytes().to_vec();
bytes.extend(<Secp256k1 as Ciphersuite>::F::ZERO.to_repr());
let agg = SchnorrAggregate::<Secp256k1>::read(&mut &bytes[..]).unwrap();
// agg.Rs == [], agg.s == 0
assert!(agg.verify(b"some dst", &[])); // returns true — forged aggregate accepted
```

Verified facts from the code: `read` accepts a zero-length `Rs` (aggregate.rs:83–87), `verify` has no non-emptiness guard (aggregate.rs:127–130), and with `s = 0` the sole multiexp term `-s * G` is the identity (aggregate.rs:144–145). Not verified: whether any in-scope production caller reaches `verify` with an empty statement list — if none does, impact is limited to downstream integrators of the `schnorr` crate.
