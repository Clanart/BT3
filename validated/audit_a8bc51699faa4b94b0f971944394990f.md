### Title
BIP-340 signatures unconditionally invalid when group key has odd Y — x-only deposit addresses become unspendable - (File: networks/bitcoin/src/crypto.rs)

### Summary
The report's bug class is a caller using the wrong effective "signature" of an operation, causing the public entry point to fail unconditionally. In `networks/bitcoin/src/crypto.rs`, the FROST `Schnorr` algorithm produces BIP-340 signatures but only normalizes the nonce parity (`R`), never the group-key parity (`A`). BIP-340 verifiers always use the *even-Y lift* of the x-only public key. When the aggregated `group_key` has an odd Y coordinate (~50% of keys), the secret share corresponds to `A` while every verifier checks against `-A`, so every signature the multisig produces fails verification. Funds sent to the wallet's x-only address (`x_only(group_key)` in `wallet/mod.rs`) are reported as received yet can never be spent.

### Finding Description
`Hram::hram` hashes `x(R)`, `x(A)`, `m` and negates the challenge when `R` is odd, and `Schnorr::verify` negates `s` when `sig.R` is odd via `needs_negation(&sig.R)` (crypto.rs:59-73, 145-148). This correctly handles the BIP-340 requirement that `R` have even Y, but there is no corresponding negation for the group key. In `frost/src/algorithm.rs`, `sign_share` computes `s = r + c·a` using `params.secret_share()` — the share of the discrete log of `A` as-is (algorithm.rs:208-210). A BIP-340 verifier computes `s·G == R' + c·lift_x(A)` where `lift_x(A) = A` if `A` is even-Y and `-A` if odd. After the code's `s` negation for odd `R`, `s·G = -R + c·A`, which equals `-R + c·lift_x(A)` only when `A` is even. For odd `A` the equation becomes `-R + c·A` vs. required `-R - c·A` — a deterministic mismatch.

### Impact Explanation
Every spend path for a Bitcoin key whose `group_key` is odd-Y produces a signature that fails BIP-340 verification on-chain. Since `x_only` deliberately drops the key's sign when forming deposit addresses (crypto.rs:21-23), an attacker or ordinary depositor can send BTC to the published address and the network can detect/scan it as received, yet the multisig can never produce a valid spend signature. This is "funds reported received that are not spendable" — a permanent-loss/DoS condition for 50% of generated keys, matching the report's "deposits always revert" class mapped onto signature production.

### Likelihood Explanation
An unprivileged party needs no special access: they only need to cause a signature to be produced for an odd-Y group key (any normal signing request, e.g., spending a received output). The trigger is purely a property of the group key, which is beyond the caller's control and occurs with probability ~1/2 per key generation. No malicious validator, leaked key, or integrator misuse is required — the failure is in the library's own parity handling.

### Recommendation
Normalize the key parity alongside the nonce parity: when `group_key` is odd-Y, negate the effective secret contribution (equivalently, negate `s` once more when `needs_negation(&group_key)` is set, since `s·G` must bind to `lift_x(A)`). Concretely, in `Schnorr::verify` (crypto.rs:145-148) and consistently in `sign_share`/`verify_share` blame paths, apply `conditional_select(&s, &-s, needs_negation(&group_key))` — or offset the secret share at keygen so `group_key` is always even-Y. Note that `verify_share` blame statements in `frost/src/algorithm.rs:226` use `verification_share` directly, so the same parity correction must be applied there for consistent blame attribution.

### Proof of Concept
Conceptual: run FROST key generation over Secp256k1 until `needs_negation(group_key)` is true (expected within ~2 tries), then execute the normal sign flow (`AlgorithmMachine::preprocess` → `sign` → `complete`) on any `msg`. `complete` returns a 64-byte `Signature` from `Schnorr::verify` (crypto.rs:139-150). Feeding `(r_bytes, s_bytes)` plus `x(group_key)` into any standard BIP-340 verifier (e.g., `bitcoin::secp256k1` `verify_schnorr` or a Taproot script-path spend) rejects it, because the verifier lifts the x-only key to even Y while `s` was computed against the odd-Y `A`. Comparing against a locally-negated share (`s' = s` recomputed with `-a`) verifies, confirming the missing key-parity negation as the root cause — analogous to the report's extra `uint256` argument making the call unconditionally fail.
