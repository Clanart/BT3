Based on my research, the strongest analog to the Augur "overwrite instead of accumulate" bug class in this codebase is in GitHub Desktop's Copilot-based merge-conflict resolution feature, where per-hunk resolutions from an LLM are spliced into a conflicted file purely by **positional order**, with no verification that the count/identity of resolutions matches the actual conflicts present in the file.

### Title
Copilot conflict resolution splices resolved hunks by position only, allowing content from an attacker-controlled merge to be silently misapplied to the wrong conflict block - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
When a user resolves merge/rebase/cherry-pick conflicts with Copilot, Desktop sends the raw conflicting hunks (including content from a remote branch/PR the attacker controls) to an LLM and receives back a flat, ordered list of `resolvedContent` strings per file. `reassembleResolvedFile` walks the original conflicted file and replaces the *n*-th conflict-marker block with the *n*-th entry in `hunkResolutions`, matched strictly by array index rather than by any per-hunk identifier or line anchor. [1](#0-0) 

### Finding Description
The reassembly function's own documentation admits the matching is fragile: "matched by order, not by line number." [2](#0-1) 

The splice loop increments `hunkIndex` for every conflict block found in the file and pulls `hunkResolutions[hunkIndex]` positionally; if the model returns too few hunks for a file, later conflicts are silently dropped (conflict markers removed, no replacement text inserted) rather than causing an error: [3](#0-2) 

The only structural validation performed on the model's JSON output checks that `hunks` is a non-empty array and that no entry still contains raw conflict markers — it does not verify that the number of hunks returned for a file equals the number of actual conflict blocks in that file: [4](#0-3) 

`reassembleResolutions` then looks up the original file content purely by `path` and blindly calls `reassembleResolvedFile` with whatever hunk array the model produced: [5](#0-4) 

Since the system prompt instructs the model to resolve conflicts using "recent commit messages and/or PR title/description" as intent signals, and the conflicting file content itself (including comments) from the "theirs" side is untrusted, attacker-controlled text embedded in a branch/PR that a victim merges can act as a prompt-injection vector. If it induces the model to emit a hunk list with the wrong count or wrong ordering for a file with multiple conflicts, `reassembleResolvedFile`'s purely positional splicing will place content intended for one conflict region into a different (possibly security-relevant) region of the file — with no error, no diff-based sanity check, and no user-visible warning that resolution order was mismatched.

### Impact Explanation
This causes silent corruption of what the user ultimately commits and pushes: a resolved file can end up with logically incorrect content (e.g., security check code from one conflict spliced into an unrelated location, or a conflict silently resolved to empty/dropped content) while `resolvedContent` passes hunk-marker validation and is written straight to disk and staged: [6](#0-5) 

Because the write only skips a file if the user *externally* resolved conflict markers themselves, a file that is still marked as unresolved-conflict continues to be silently overwritten with a possibly mis-assembled result: [7](#0-6) 

### Likelihood Explanation
The precondition — a repo/PR the attacker controls being merged, and the user choosing Copilot's auto-resolution instead of manually reviewing every hunk — is a realistic normal Desktop workflow now that "Resolve merge conflicts with Copilot" is a shipped feature (added in 3.6.0). Exploitation depends on reliably steering the LLM's hunk count/order via prompt injection, which is probabilistic rather than deterministic, and I was not able to fully verify (within available tool budget) whether `validateResolutionPaths` performs any additional per-file hunk-count cross-check beyond path validation — this function exists in the file but its body was not inspected before the iteration budget was exhausted, so there is some residual uncertainty about whether a partial mitigation exists there.

### Recommendation
- Tag each hunk in the outbound prompt with a stable per-conflict identifier (e.g., index and a content hash of the original marker block) and require the model to echo it back, then match resolutions by identifier instead of raw array order.
- Reject (rather than silently truncate) any file resolution whose hunk count does not exactly equal the number of conflict blocks Desktop detected for that file before ever writing to disk.
- Surface an explicit diff/before-after review step for Copilot-resolved files prior to staging, rather than relying solely on "no conflict markers remain" as sufficient proof of correctness.

### Proof of Concept
Conceptual due to the probabilistic nature of LLM steering:
1. Attacker opens a PR/branch with a file containing two independent conflicting regions and, in code comments/PR description, includes instructions and content engineered to make the resolver model return only one `hunks` entry for that file (or reorder them) while claiming both conflicts are addressed.
2. Victim merges the attacker's branch locally in Desktop and clicks "Resolve merge conflicts with Copilot".
3. `parseCopilotConflictResolution` accepts the response since `hunks` is non-empty and contains no literal conflict-marker text.
4. `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) splices the single returned hunk into the *first* conflict block by position and drops the *second* block's replacement entirely (since `hunkIndex` runs out of `hunkResolutions`), silently discarding intended changes from the second conflict.
5. The victim clicks "Continue Merge"; `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7169-7259`) writes and stages the corrupted file, and it is committed and later pushed without further verification.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
