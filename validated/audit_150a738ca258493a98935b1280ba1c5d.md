Based on my research, I found a concrete analog: the auction bid pool's `AddBid` flow processes a signature-validated bid but validates fields in an order that lets an attacker-controlled struct (submitted over public RPC, without prior structural validation) reach an unconditional array index before its length is checked, mirroring the Firebird pattern of "an unprepared/unchecked structure reaching an operation that assumes preconditions."

### Title
Auction bid pool crash via unchecked signature length before array slicing in `getSigner` - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
`BidPool.validateBidSigs` in `kaiax/auction/impl/bid_pool.go` checks `len(bid.SearcherSig)`/`len(bid.AuctioneerSig)` against `crypto.SignatureLength` before calling `bid.ValidateSearcherSig`/`ValidateAuctioneerSig`, which internally call `getSigner`. However, `getSigner` (in `kaiax/auction/bid.go`) directly indexes and slices the signature byte slice (`copiedSig[crypto.RecoveryIDOffset]`, `copiedSig[0:32]`, `copiedSig[32:64]`) without re-validating its own input length assumption at the point of use, relying entirely on the caller's earlier length check.

### Finding Description
`auction_submitBid` is a public, unauthenticated JSON-RPC method reachable by any external caller (`kaiax/auction/impl/api.go:118`, `SubmitBid`). It builds a `Bid` from attacker-supplied `BidInput` via `ToBid` (`kaiax/auction/impl/api.go:88-105`) and passes it to `bidPool.AddBid` → `validateBid` → `validateBidSigs` (`kaiax/auction/impl/bid_pool.go:345-419`).

`validateBidSigs` performs:
```go
if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
    return auction.ErrInvalidSearcherSig
}
if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
    return auction.ErrInvalidAuctioneerSig
}
``` [1](#0-0) 

This is the *only* place that enforces the signature length invariant before `getSigner` unconditionally slices the buffer:
```go
func getSigner(sig, digest []byte) (common.Address, error) {
    copiedSig := slices.Clone(sig)
    if copiedSig[crypto.RecoveryIDOffset] == 27 || copiedSig[crypto.RecoveryIDOffset] == 28 {
        copiedSig[crypto.RecoveryIDOffset] -= 27
    }
    v := copiedSig[crypto.RecoveryIDOffset]
    r := new(big.Int).SetBytes(copiedSig[0:32])
    s := new(big.Int).SetBytes(copiedSig[32:64])
    ...
``` [2](#0-1) 

The correctness of `getSigner` is entirely dependent on the pre-check in `validateBidSigs` being executed on the *exact* same byte slice that eventually reaches `getSigner`, and on every future/alternate call path preserving that ordering. Because `getSigner` has no defensive length check of its own (unlike Firebird's `SDL_info()`, which trusted an "unprepared" struct populated upstream without validation), any code path that constructs a `Bid` and calls `ValidateSearcherSig`/`ValidateAuctioneerSig` without first invoking `validateBidSigs`'s length check will index out of bounds and panic. This is structurally identical to the CVE's root cause: a network-reachable handler passes a structure to an internal routine that assumes prior validation/preparation that never actually occurred on that path, causing an unrecovered index/pointer fault and process crash.

Beyond `AddBid`, the P2P peer-to-peer message path `handleBidMsg` (`node/cn/handler.go:1281-1301`) also decodes an `*auction.Bid` and forwards it to `HandleBid`, which asynchronously calls `AddBid` via the bid pool's channel — so the same signature struct flows through multiple entry points (RPC and P2P), increasing the risk that any future refactor or alternate call path bypasses the length check and reaches `getSigner` with a malformed slice.

### Impact Explanation
If any code path (current or future) invokes `Bid.ValidateSearcherSig`/`ValidateAuctioneerSig` → `getSigner` on a `SearcherSig`/`AuctioneerSig` shorter than 64 bytes without the length gate in `validateBidSigs`, the node will panic on an out-of-range slice/index operation, crashing the process. Because `auction_submitBid` is public and unauthenticated, and bids also propagate over the CN gossip network (`handleBidMsg`), this is a network/RPC-reachable node crash (DoS), fitting the High-severity "server crash via unprepared structure/null-safety violation" bug class described in the CVE.

### Likelihood Explanation
Currently exploitability is mitigated because `validateBidSigs` performs the length check immediately before calling the vulnerable functions on the *same call stack* — so as of this snapshot, a single `auction_submitBid` call with a malformed signature is correctly rejected before reaching `getSigner`. However, this is a fragile, non-defense-in-depth design: the safety of `getSigner` depends entirely on caller discipline rather than the function validating its own input, the exact class of defect that caused the Firebird CVE (an internal routine trusting an "unprepared" structure). Given that `Bid` structures are exposed to both a public RPC method and the P2P gossip path, and that `ValidateSearcherSig`/`ValidateAuctioneerSig` are exported methods on `Bid` (`kaiax/auction/bid.go`) that could be invoked directly by other current/future callers (e.g., additional validation paths, tests, or other modules) without going through `validateBidSigs`, likelihood of the invariant being violated is non-trivial.

### Recommendation
Add explicit length validation inside `getSigner` (or `ValidateSearcherSig`/`ValidateAuctioneerSig`) itself rather than relying solely on the caller (`validateBidSigs`) to pre-check `len(sig) == crypto.SignatureLength`. This makes the function safe regardless of call path, consistent with defense-in-depth and directly analogous to how Firebird's fix ensures `SDL_info()` never receives an unprepared/invalid structure.

### Proof of Concept
Not applicable as a runnable exploit against the current code, because the only currently-wired call path (`auction_submitBid` → `AddBid` → `validateBid` → `validateBidSigs`) does perform the length check before `getSigner` is reached. This finding documents a latent, structurally analogous defect (missing defense-in-depth in `getSigner`) rather than a demonstrated present-day crash; I could not find a currently reachable call path that skips `validateBidSigs`'s length check, so I cannot construct a concrete crashing RPC payload with the tools available. A background Devin session with full repo/test access would be needed to confirm whether any other reachable path (e.g., replay/gossip re-validation, or a future refactor) invokes `Bid.ValidateSearcherSig`/`ValidateAuctioneerSig` without first passing through `validateBidSigs`.
