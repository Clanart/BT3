### Title
Attacker can sandwich a `queueNewRewards` harvest event to steal a pro-rata share of WOM rewards with zero time-at-risk stake - ([File: rewards/BaseRewardPoolV2.sol], [File: wombat/WombatStaking.sol], [File: rewards/MasterMagpie.sol])

### Summary
`BaseRewardPoolV2._provisionReward` distributes newly harvested WOM rewards as an instantaneous, lump-sum increase to `rewardPerTokenStored` based on `totalStaked()` at the exact block the reward is queued, with no time-weighting, vesting, or minimum staking duration. Because `MasterMagpie.depositFor`/`withdrawFor` (and the pool helper's `depositLP`/`withdraw`) impose no cooldown or lock, an attacker can deposit a large stake immediately before a `harvest()`-triggered `queueNewRewards` call and withdraw immediately after, capturing a full pro-rata share of the newly distributed rewards for a holding period of essentially zero blocks.

### Finding Description
`WombatPoolHelperV2.harvest()` calls `IWombatStaking(wombatStaking).harvest(lpToken)` [1](#0-0) , which routes into `WombatStaking._toMasterWomAndSendReward`, ultimately calling `IBaseRewardPool(_rewarder).queueNewRewards(_amount, _rewardToken)` [2](#0-1) .

`BaseRewardPoolV2._provisionReward` updates the global index using the *current* `totalStaked()`: [3](#0-2) 
`totalStaked()` and `balanceOf()` simply read the live, real-time balances tracked in `MasterMagpie` — `IERC20(stakingToken).balanceOf(operator)` and `userInfo[stakingToken][account].amount` via `stakingInfo` [4](#0-3) . There is no snapshot, checkpoint, or per-block accrual — a stake credited one block (or even one transaction) before `queueNewRewards` is executed receives the full instantaneous benefit of the reward-per-token bump.

`MasterMagpie._deposit`/`_withdraw` (reached via `depositFor`/`withdrawFor`, which `WombatPoolHelperV2.depositLP`/`withdraw` call) have no cooldown, lock-up, or minimum holding period [5](#0-4) [6](#0-5) .

Exploit flow:
1. Attacker calls `WombatPoolHelperV2.depositLP(largeAmount)`. This is a self-contained call: `WombatStaking.depositLP` first triggers `_toMasterWomAndSendReward(..., true)` (harvest using the *old* `totalStaked()`, before attacker's stake exists) and only afterward mints/stakes the receipt token to `MasterMagpie` [7](#0-6) . So the attacker's own deposit-triggered harvest does not benefit them — but their large stake is now fully credited in `MasterMagpie`.
2. In the same block, a `harvest()` call occurs — either the attacker calls it directly, or the attacker front-runs a pending legitimate `harvest()` transaction from another user/keeper. This is a separate call from step 1, so `totalStaked()` now includes the attacker's freshly staked large amount, and `queueNewRewards` inflates `rewardPerTokenStored` shared uniformly across all current stakers, including the attacker.
3. Attacker immediately calls `WombatPoolHelperV2.withdraw(largeAmount, 0)`, which triggers `MasterMagpie._harvestAndUnstake` → `_harvestBaseRewarder` → `rewarder.updateFor(_account)`, which locks in `userRewards[token][attacker] = earned(...)` at the new, inflated `rewardPerToken` [8](#0-7) [9](#0-8) . The attacker can later call `getReward`/`multiclaim` to withdraw the captured WOM.

No modifier prevents this: `nonReentrant`/`whenNotPaused` on `depositFor`/`withdrawFor` guard against reentrancy/pausing only, not against same-block deposit-harvest-withdraw sequences; there is no minimum staking duration or reward vesting mechanism.

### Impact Explanation
This is a direct theft of unclaimed/accrued yield from long-term stakers: the attacker's flash-stake dilutes `rewardPerTokenStored` in their favor, transferring a share of freshly harvested WOM proportional to `largeAmount / totalStaked()` away from stakers who held their position for the entire accrual period, for a holding time of effectively zero blocks and minimal capital lock-up risk (only flash-loan/temporary capital, no slippage beyond LP deposit/withdraw fees if any). This matches the Immunefi impact class "theft of unclaimed yield" / "direct theft of user funds."

### Likelihood Explanation
- Requires only capital to acquire a large amount of the pool's LP token temporarily (flash-loanable or self-funded), no privileged role.
- Requires the ability to front-run/back-run in the same block, which the rules state is a valid attacker capability.
- Repeatable every time a `harvest()` (or `queueNewRewards`-triggering) event occurs and is either predictable (e.g., keeper-triggered on schedule) or directly attacker-triggerable, since `harvest()` on `WombatPoolHelperV2` is a public, unrestricted function `_onlyActivePool` (no manager/permission gate) [10](#0-9) .
- Profitability scales with pool size and reward amount relative to `totalStaked()`; larger reward events and higher attacker capital increase captured share.

### Recommendation
Introduce time-weighting or a minimum-holding checkpoint before rewards are attributable, e.g.:
- Snapshot `balanceOf`/eligibility using a block-delay (e.g., only count stake present before the block in which `queueNewRewards` was called), or
- Convert reward distribution to a continuous per-second streaming model (like `MasterMagpie`'s `accMGPPerShare` with `lastRewardTimestamp`) rather than instantaneous lump-sum injection, so rewards accrue proportional to time staked, or
- Add a minimum staking duration / withdrawal cooldown in `MasterMagpie._deposit`/`_withdraw` so a staker cannot deposit and withdraw within the same block/short window and still be eligible for interim reward distributions.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPoolV2`, `WombatStaking`, `WombatPoolHelperV2` with mocks for `MasterWombat`/`WombatPool` (already present under `mocks/wombat/`).
2. Seed a long-term staker `Alice` who deposits `100e18` LP via `depositLP` and holds for N blocks.
3. Have a pending WOM reward accrue in the underlying Wombat pool (mock `pendingTokens` to return a fixed WOM amount, e.g., `1000e18`).
4. In the same block: attacker `Bob` calls `depositLP(10000e18)` (100x Alice's stake), then calls `harvest()` (or simulate front-running a queued `harvest()` tx from `Alice`), then immediately calls `withdraw(10000e18, 0)`.
5. Assert: `BaseRewardPoolV2.earned(Bob, WOM)` after step 4 is > 0 and approximately `1000e18 * 10000/(10000+100)` (Bob's pro-rata share), despite Bob only holding stake for the single `harvest()` transaction.
6. Assert conservation violation: `earned(Alice, WOM) + earned(Bob, WOM) == totalHarvested`, but `earned(Bob, WOM)` is disproportionate to any meaningful time held, showing Bob captured yield that should have accrued only to time-weighted long-term stakers.

    function _deposit(address _stakingToken, address _account, uint256 _amount, bool _isVlmgp) internal {
        updatePool(_stakingToken);

        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][_account];

        if (user.amount > 0) {
            _harvestMGP(_stakingToken, _account);
        }
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount + _amount;
        if (!_isVlmgp) {
            user.available = user.available + _amount;
            IERC20(pool.stakingToken).safeTransferFrom(address(msg.sender), address(this), _amount);
        }
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;

        if (_amount > 0)
            if (!_isVlmgp)
                emit Deposit(_account, _stakingToken, _amount);
            else
                emit DepositNotAvailable(_account, _stakingToken, _amount);
    }

    /// @notice internal function to deal with withdraw staking token
    function _withdraw(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        _harvestAndUnstake(_stakingToken, _account, _amount, _isVlMgp);

        if (!_isVlMgp)
            IERC20(tokenToPoolInfo[_stakingToken].stakingToken).safeTransfer(address(msg.sender), _amount);
        emit Withdraw(_account, _stakingToken, _amount);
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
