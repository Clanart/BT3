## Analysis

The ENS bug's broken invariant: a security-relevant write path (`renew`) skips the wrapper layer (`NameWrapper`) that is supposed to validate/update protection state (`fuses`), so a value that should only be settable through a vetted layer gets set (or left stale) by going straight to the underlying primitive. The strongest Desktop analog is in the credential-helper trampoline, where the *classification* of a remote host as a trusted "GitHub"/"enterprise" endpoint — the gate that decides whether Desktop's stored OAuth credentials/sign-in flow are used — is derived from data the remote server itself supplies (`WWW-Authenticate` header), bypassing the actual verification path (`isGitHubHost`, matching against a known account endpoint). ### Title
Remote-controlled `WWW-Authenticate` header spoofs GitHub/Enterprise host classification in credential trampoline - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
`getEndpointKind` in the credential-helper trampoline classifies a remote endpoint as `'enterprise'` (a first-party GitHub host) purely because the HTTP response Git received during authentication contained a `WWW-Authenticate` header whose value includes `realm="GitHub"`. This value is attacker-controlled: any server behind a `git remote`/proxy the user fetches from can supply this header. `getCredential` then treats the endpoint as a GitHub host and either withholds generic-credential handling or triggers the GitHub sign-in prompt (`ui.promptForGitHubSignIn`) for that attacker-chosen host instead of applying the same rigor as the network-verified `isGitHubHost` check.

### Finding Description
`getEndpointKind` first checks known-good classifiers (`isGist`, `isDotCom`, `isGHE`) which are based on well-known, hardcoded domains. [2](#0-1) 

If none of those match, instead of relying solely on the legitimate verification path at the bottom of the function (`isGitHubHost(endpoint)`, an actual network probe), the function short-circuits based on the `wwwauth[...]` entries forwarded from Git's credential protocol:
```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
``` [3](#0-2) 

This header is emitted by whatever server the fetch/clone/push targets — it is not signed or otherwise validated, and comes straight from the network response. The comment even acknowledges it is a "happy-path... without having to resort to making a request ourselves," i.e. it deliberately substitutes an unauthenticated, attacker-suppliable signal for the real verification (`isGitHubHost`) that exists a few lines later in the same function.

Once `getEndpointKind` returns `'enterprise'`, `getCredential` treats the endpoint as first-party:
```
if (endpointKind !== 'generic' && !accounts.some(a => a.endpoint === apiEndpoint)) {
  ...
  const account = await ui.promptForGitHubSignIn(endpoint)
  ...
}
if (endpointKind !== 'generic') {
  return undefined   // generic credential helper never invoked
}
``` [4](#0-3) 

The consequence mirrors the ENS bug's shape precisely: a decision that should route through the vetted check (`isGitHubHost`, or matching against a known signed-in account's endpoint) is instead satisfied by a value the untrusted counterparty controls, and the "existing guard" (`isGitHubHost`) is bypassed entirely because the header-based branch returns before that code is ever reached.

### Impact Explanation
- The generic git credential helper / external credential manager flow (used for arbitrary hosts like self-hosted Git servers) is disabled for the spoofed host, since `endpointKind !== 'generic'` short-circuits `getGenericCredential`/`getExternalCredential`.
- Desktop will instead invoke `ui.promptForGitHubSignIn(endpoint)`, initiating the GitHub Enterprise sign-in/OAuth flow against a host the attacker fully controls, purely because the attacker's server sent a spoofed header during a fetch/clone/push the user initiated against a completely different (possibly malicious) remote. This satisfies "unauthorized OAuth or account binding" — the app performs an OAuth-style handshake toward attacker infrastructure it should not have classified as a GitHub endpoint.
- If the user, believing this is a normal Desktop-driven Enterprise-login prompt (which does occur legitimately for genuine GHE remotes), completes the flow, tokens/credentials are exchanged with the attacker's endpoint.

### Likelihood Explanation
The trigger requires only that the user add/fetch/clone from an attacker-controlled remote or through a proxy under attacker control — a normal, unprivileged action already covered by the valid-impact criteria ("attacker controls ... a git remote/proxy response"). No local access, malware, or leaked credentials are needed; the header is added by the server that responds to Git's HTTP request during authentication. This is a realistic MITM/malicious-remote scenario and does not require unnatural user steps beyond adding a remote and fetching, which Desktop already does automatically for background fetches.

### Recommendation
Do not trust the `wwwauth[...]` realm string as authoritative proof of GitHub/Enterprise identity. At minimum:
- Require the network-verified `isGitHubHost(endpoint)` check (or an existing matched account) before ever granting `'enterprise'`/`'github.com'` classification, rather than accepting an unauthenticated header as a substitute.
- If the header-based heuristic is kept for performance, treat it only as a hint to *prompt the user for confirmation* that the host is really GitHub Enterprise, not to silently short-circuit the classification and bypass the generic-credential path.

### Proof of Concept
1. Attacker stands up an HTTP server (or MITM proxy) that Desktop will fetch from — e.g., victim clones/adds a remote `https://evil.example.com/foo.git`.
2. When Git performs the initial unauthenticated request, the attacker's server responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. Git's credential helper protocol forwards this as a `wwwauth[]=...realm="GitHub"...` field to Desktop's credential trampoline (`createCredentialHelperTrampolineHandler` → `getCredential` → `getEndpointKind`).
4. `getEndpointKind` returns `'enterprise'` for `evil.example.com` without ever calling `isGitHubHost`.
5. `getCredential` disables the generic credential helper for this host and, if no matching account exists, calls `ui.promptForGitHubSignIn('https://evil.example.com')`, initiating GitHub-style sign-in/OAuth against the attacker's domain.

Note: I was not able to fully trace `ui.promptForGitHubSignIn`'s exact OAuth wiring or `isGitHubHost`'s implementation within the indexed context (its definition wasn't returned by search), so the precise downstream handling of the sign-in flow (e.g., whether device-flow tokens could be sent to the attacker host, or whether the dialog clearly warns the user) could not be fully confirmed from the available code. Starting a full Devin session against the repository would allow tracing `app/src/lib/api.ts`'s `isGitHubHost`/`getAPIEndpoint` and the `trampoline-ui-helper.ts` sign-in prompt to confirm exact exploitability and the best fix location.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
