### Title
Unauthenticated OP_RETURN operator-attribution in the `SinglePlusAnyoneCanPay`-signed payout tx lets anyone credit an arbitrary registered operator for a withdrawal it never funded - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The user's authorization for the payout transaction (`create_payout_txhandler`) is signed with `SIGHASH_SINGLE|ANYONECANPAY`, which commits only to input #0 (the withdrawal-registration UTXO) and output #0 (the user's payout). Neither the additional funding inputs nor the OP_RETURN output carrying `operator_xonly_pk` are covered by any signature, so anyone who possesses the user's signature (the withdrawing user themselves, trivially, since they generate it) can complete and broadcast a different transaction that pays the same committed output while stamping an arbitrary registered operator's x-only pubkey into the OP_RETURN. Both the off-chain DB check (`Verifier::is_kickoff_malicious`) and the ZK `bridge_circuit`'s `deposit_constant` binding trust this OP_RETURN value as ground truth for "who funded this payout," with no check that the named operator supplied the additional inputs.

### Finding Description
The broken binding, stated explicitly: the protocol implicitly assumes
`OPERATOR_WHO_FUNDED_PAYOUT_OUTPUT == operator_xonly_pk_in_OP_RETURN(payout_tx)`,
but nothing enforces this equality.

Trace:
1. `Operator::withdraw` (`core/src/operator.rs:560-637`) builds the payout tx via `create_payout_txhandler(input_utxo, output_txout, self.signer.xonly_public_key, in_signature, ...)` [1](#0-0) . `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) sets the P2TR key-spend witness for input 0 only, using `user_sig` [2](#0-1) . The OP_RETURN output carrying `operator_xonly_pk` is unsigned data, not committed by any signature.
2. `parser::operator::parse_withdrawal_sig_params` only enforces that the sighash type is `SinglePlusAnyoneCanPay` [3](#0-2) . Under BIP-341, `SinglePlusAnyoneCanPay` binds only input #0 and the corresponding output #0 - it does not commit to any other inputs (funding) or outputs (the OP_RETURN), as shown by the sighash construction in the circuit's own reimplementation (`taproot_encode_signing_data_to_with_annex_digest`, `circuits-lib/src/bridge_circuit/mod.rs:719-875`, note the `anyone_can_pay` branch skips all-prevouts/all-outputs commitments) [4](#0-3) .
3. Consequently, once the user submits (or an attacker intercepts/derives) that signature, anyone can assemble a competing transaction spending the same registered withdrawal input, paying the exact committed output, adding their own funding inputs, and writing ANY x-only pubkey (e.g. an uninvolved, real, registered operator's key) into the OP_RETURN. If this transaction confirms first, it becomes "the" canonical payout tx.
4. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) blindly parses this OP_RETURN and stores it as `payout_payer_operator_xonly_pk` for the deposit's `move_to_vault_txid` [5](#0-4) .
5. `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks `operator_xonly_pk != kickoff_data.operator_xonly_pk` where `operator_xonly_pk` is read back from the same forged DB row [6](#0-5) ; it never checks that the named operator supplied the funding inputs.
6. `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:137-244`) extracts `operator_xonlypk` from the same unauthenticated OP_RETURN of the SPV-proven payout tx and folds it into `deposit_constant` alongside the deposit's real `move_txid` (bound via `verify_storage_proofs`) [7](#0-6) . The circuit only proves that the SPV/storage-proof-identified withdrawal outpoint is spent by `input[payout_input_index]` of this transaction (`circuits-lib/src/bridge_circuit/mod.rs:186-204`) [8](#0-7)  - it never checks who funded the output or authorized the OP_RETURN.

Attacker's exact transaction: the withdrawing user (unprivileged, per the threat model) generates their own `SinglePlusAnyoneCanPay` signature over `(in_outpoint, output_script_pubkey, out_amount)`, then instead of relying on an operator's `Withdraw`/`InternalWithdraw` RPC, assembles and broadcasts a raw transaction reusing that signed input/output, adding their own funding inputs (paying themselves back, i.e. near-zero net cost beyond fees) and an OP_RETURN naming any registered operator's x-only pubkey. This transaction satisfies Citrea's withdrawal-fulfillment matching (same committed input/output) and the bridge circuit's SPV+storage-proof checks identically to a genuine operator-funded payout.

### Impact Explanation
If the named operator's automation (`PayoutCheckerTask`, `core/src/task/payout_checker.rs:31-111`) is running, it polls `get_first_unhandled_payout_by_operator_xonly_pk` for its own key [9](#0-8)  and will automatically drive the normal kickoff/reimbursement flow for a withdrawal that operator never funded. Since `is_kickoff_malicious` and `deposit_constant` both key off the same forged OP_RETURN, the kickoff succeeds and the operator's presigned reimbursement path pays out the full bridge amount from the N-of-N escrow. This is exactly the listed Critical impact "an operator reimbursed for a payout it never funded" and simultaneously "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" - the bridge's collective escrow loses `bridge_amount` per exploited deposit while the named operator supplied none of it. The attack is repeatable across every withdrawal and can target any registered operator, at attacker cost limited to Bitcoin fees (since the attacker funds their own payout output back to themselves).

### Likelihood Explanation
The attacker only needs standard, unprivileged capabilities explicitly granted by the threat model: deposit/withdraw on Citrea, and the ability to produce a `SinglePlusAnyoneCanPay` Schnorr signature and broadcast a raw Bitcoin transaction. No operator, verifier, or aggregator cooperation is required, and no key compromise, majority hashrate, or TLS interception is needed. The only race condition is confirming the attacker's variant before or as the canonical payout for that withdrawal - trivially achievable by using a competitive fee rate, since the legitimate operator flow has no urgency advantage.

### Recommendation
Bind the OP_RETURN operator attribution and the funding inputs to the same key cryptographically: e.g. require the operator to sign the entire payout transaction (including the OP_RETURN and all additional funding inputs) with their own key, or commit `operator_xonly_pk` inside the sighash-committed output (output #0) rather than as an unsigned side output, or require `is_kickoff_malicious`/`update_finalized_payouts` to additionally verify that the funding inputs of the recorded payout tx are actually owned by (or signed by) the operator named in the OP_RETURN before recording/trusting the attribution.

### Proof of Concept
`cargo test` plan (circuits-lib, no mainnet/live Citrea):
1. Build a genuine `deposit_storage_proof`/`move_txid` for deposit A exactly as `verify_storage_proofs` expects.
2. Construct a payout `Transaction` whose input #0 spends the registered withdrawal outpoint for deposit A with a `SinglePlusAnyoneCanPay` signature signed by the withdrawing user's key over `(input#0, output#0)` only, add an extra attacker-funded input, and add an OP_RETURN containing a completely unrelated registered operator O's x-only pubkey (not present in deposit A's operator set).
3. Feed this transaction as `payout_spv.transaction` into `BridgeCircuitInput`, along with valid SPV/light-client/storage proofs for deposit A.
4. Call `bridge_circuit::deposit_constant`/`bridge_circuit` and assert it still computes a valid `DepositConstant`/`journal_hash` (`assert!(deposit_constant(...).0 == expected)` and no panic on `verify_storage_proofs`/SPV checks), demonstrating `move_txid` (deposit A) and `operator_xonlypk` (O, uninvolved) are accepted together with no cross-check that O funded anything.
5. Separately, in `core/src/verifier.rs`, unit-test `is_kickoff_malicious` with a DB row where `payout_payer_operator_xonly_pk = O` (as `update_finalized_payouts` would store from step 2's OP_RETURN) and `kickoff_data.operator_xonly_pk = O`, asserting it returns `Ok(false)` (not malicious) even though O never supplied the funding input in the constructed transaction.

#[allow(clippy::result_large_err)]
pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }
