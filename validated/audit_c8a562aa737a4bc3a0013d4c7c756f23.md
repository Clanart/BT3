### Title
Uninitialized `enc_keys`/`commitments` map entries cause a reachable panic via attacker-controlled `recipient`/`sender` in blame evaluation - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2018-16058 was a crash caused by a data structure whose fields were left uninitialized and then dereferenced. The Serai analog is `Decryption::decrypt_with_proof`: its `enc_keys: HashMap<Participant, C::G>` is only populated for participants registered via `Decryption::register` (participants `1..=n`), yet it is indexed with `self.enc_keys[&decryptor]`, where `decryptor` is an untrusted `Participant` argument supplied to `BlameMachine::blame` / `AdditionalBlameMachine::blame`. Indexing a missing `HashMap` entry with `[]` panics in Rust. A blame claim naming a `recipient` that was never registered crashes the evaluating node before any proof verification occurs. The same class of bug exists in `blame_internal`, which later indexes `self.commitments[&sender]` with an unvalidated `sender`.

### Finding Description
`Decryption::new` creates an empty `enc_keys` map, and `register` only inserts an entry per participant that is actually processed (`assert!`ed not to be re-registered). In `AdditionalBlameMachine::new` (`crypto/dkg/pedpop/src/lib.rs`), only participants `1..=n` are registered:

```
for i in 1 ..= n {
  let i = Participant::new(i).unwrap();
  let Some(msg) = commitment_msgs.remove(&i) else { Err(...)? };
  commitments.insert(i, encryption.register(i, msg).commitments);
}
```

`blame` forwards the caller-supplied `sender` and `recipient` unchecked into `blame_internal`, which calls `decrypt_with_proof`. There, after the Schnorr PoP check passes (trivially satisfiable: the accuser crafts the `EncryptedMessage` and its PoP themselves — `pop_challenge` binds `from` as a label only, and the signing key is attacker-chosen), the code evaluates:

```
&[self.enc_keys[&decryptor], *proof.key]
```

as part of the DLEq verify call. If `decryptor` (e.g., `Participant(n+1)` or any index not registered) has no entry, `HashMap`'s `Index` impl panics. The panic occurs while *building the arguments*, i.e., before `dleq.verify` runs, so no valid `EncryptionKeyProof` is needed — `proof: Some(<arbitrary EncryptionKeyProof>)` suffices.

Likewise, if `sender` is unregistered but `recipient` is registered, `blame_internal` reaches `self.commitments[&sender]` and panics (in `AdditionalBlameMachine`, `commitments` only holds `1..=n`).

This mirrors the Wireshark defect precisely: a structure is only partially populated (keys `1..=n` initialized, the map's "field" for other indexes left unset) and then dereferenced by a parser/handler of untrusted protocol input, producing a crash.

### Impact Explanation
`AdditionalBlameMachine` exists explicitly so that blame can be evaluated by *any* party, including non-participants, over arbitrary accusations ("capable of evaluating Blame regardless of if the caller was a member of the DKG protocol"). An unprivileged party that can submit a blame claim — or a participant in a DKG where blame evaluation is performed by coordinators/validators — can crash every evaluating node by naming an out-of-range `recipient` (or `sender`). This is a remote denial of service of the DKG blame-arbitration path: a single malformed accusation aborts the process rather than returning a faulty-party verdict, preventing slashing/blame resolution and halting key generation handling entirely.

### Likelihood Explanation
Reachability requires only that `blame`/`blame_internal` be invoked on attacker-influenced arguments — the API is public and takes `sender`, `recipient`, `msg`, and `proof` verbatim. The `msg` must pass `msg.pop.verify`, which any attacker satisfies by encrypting with their own ephemeral key (the PoP binds `sender` as a transcript label, not a verified identity). The `decryptor` panic needs only `proof.is_some()`. No threshold collusion, leaked keys, or invalid-curve inputs are required — `Participant` accepts any nonzero `u16`, and nothing range-checks it against `n` before the `HashMap` index.

### Recommendation
Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with checked lookups:

```rust
let Some(enc_key) = self.enc_keys.get(&decryptor) else {
  return Err(DecryptionError::InvalidProof) // or treat recipient as faulty
};
```

and in `blame_internal`, `let Some(commitments) = self.commitments.get(&sender) else { return recipient };` (an accusation naming an unknown sender is itself malformed). Also consider bounding `sender`/`recipient` to `1..=n` at the `blame` entry points.

### Proof of Concept
```rust
// Setup: any party constructs an AdditionalBlameMachine for a DKG with n participants
let n: u16 = 4;
let machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// Attacker crafts an EncryptedMessage with a valid PoP (their own ephemeral key),
// claiming sender = Participant(1)
let msg: EncryptedMessage<Ristretto, SecretShare<...>> = /* encrypt(.., from = 1, ..) */;

// Attacker names an unregistered recipient, e.g., Participant(n+1) = 5
let bad_recipient = Participant::new(n + 1).unwrap();

// dummy proof: any parseable EncryptionKeyProof works; it is never verified
let proof = Some(dummy_encryption_key_proof);

// PANIC: `self.enc_keys[&decryptor]` in Decryption::decrypt_with_proof
// (crypto/dkg/pedpop/src/encryption.rs) indexes a missing HashMap key
machine.blame(Participant::new(1).unwrap(), bad_recipient, msg, proof);
```

The panic is reached at the `enc_keys` indexing inside `decrypt_with_proof`, which is evaluated before `proof.dleq.verify`, so the attacker never needs a valid DLEq proof — only a `Some(_)` value and a `msg` whose PoP verifies under their own key.
