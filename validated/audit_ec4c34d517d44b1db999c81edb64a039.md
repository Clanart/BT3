### Title
Duplicate `withdrawal_utxo` registration across deposit indices lets a payout be double-counted, allowing an operator to be reimbursed for a vault it never funded a payout for - ([File: core/src/database/verifier.rs])

### Summary
`Database::update_withdrawal_utxo_from_citrea_withdrawal` writes whatever `(txid, vout)` Citrea reports for a given withdrawal `idx` into the `withdrawals` table with no uniqueness check across other `idx` rows. `Database::get_payout_txs_for_withdrawal_utxos` then joins `withdrawals` to `bitcoin_syncer_spent_utxos` purely on `(txid, vout)`, so if two different deposit indices (`idx_a`, `idx_b`) are ever registered with the identical withdrawal outpoint bytes, a single confirmed spend of that outpoint is returned as two separate `(idx, payout_txid)` rows and gets written into both rows via `update_payout_txs_and_payer_operator_xonly_pk`.

### Finding Description
The intended binding is: `COUNT(payout tx that satisfies withdrawal idx_a) == 1 AND COUNT(payout tx that satisfies withdrawal idx_b) == 1`, where each count should come from a physically distinct Bitcoin spend. After the attack, both counts point to the same single payout transaction.

Path:
1. Attacker deposits twice (or arranges two distinct `move_to_vault_txid`s), giving two deposit/withdrawal indices `idx_a` and `idx_b`.
2. Attacker calls Citrea's `withdraw` twice, both times supplying identical outpoint bytes `X = (txid, vout)`. Nothing in this repo's Citrea sync path deduplicates outpoints across indices - `update_citrea_deposit_and_withdrawals` (`core/src/verifier.rs:2248-2262`) simply forwards whatever `collect_withdrawal_utxos` returns to `Database::update_withdrawal_utxo_from_citrea_withdrawal` for each `idx`, which issues a bare `UPDATE ... WHERE idx = $1` [1](#0-0)  with no check against other rows' `withdrawal_utxo_txid`/`withdrawal_utxo_vout`.
3. Some operator later legitimately funds and broadcasts one payout transaction spending `X` (for, say, `idx_a`). Once confirmed, `bitcoin_syncer_spent_utxos` records this single spend.
4. `update_finalized_payouts` calls `get_payout_txs_for_withdrawal_utxos(block_id)`, whose query joins on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout` [2](#0-1) . Because both `idx_a` and `idx_b` rows carry the identical outpoint, this query returns two rows - `(idx_a, payout_txid)` and `(idx_b, payout_txid)` - for the one real spend, exactly as demonstrated by the repo's own multi-row assertion pattern at the bottom of the existing test `update_get_payout_txs_from_citrea_withdrawal` [3](#0-2)  (that test uses distinct outpoints, but shows the API structurally returns N rows for N idx matches, which becomes a false duplication when outpoints collide).
5. `update_payout_txs_and_payer_operator_xonly_pk` then writes the same `payout_txid`, `payout_payer_operator_xonly_pk`, and `payout_tx_blockhash` into **both** `idx_a` and `idx_b` rows [4](#0-3) .
6. The safety check that is supposed to catch a fraudulent kickoff, `Verifier::is_kickoff_malicious`, only consults `get_payout_info_from_move_txid(move_txid)` for the deposit being kicked off, and only checks that the operator xonly-pk and the committed payout blockhash match [5](#0-4) . It does **not** verify that the payout transaction is uniquely tied to that specific deposit/withdrawal - so for `idx_b` it finds a "matching" payout record (planted by the DB conflation) and returns `false` (not malicious), suppressing any challenge.
7. Because the kickoff for `idx_b` is judged non-malicious, an operator (even without deliberate wrongdoing - `get_first_unhandled_payout_by_operator_xonly_pk` [6](#0-5)  will surface `idx_b` as an "unhandled payout it fronted" purely from the corrupted DB state) can submit a kickoff for `idx_b`'s vault and be reimbursed, despite never having created or broadcast a distinct payout transaction for `idx_b`'s withdrawer.

Existing guards fail to catch this specifically because: `is_kickoff_malicious` binds correctness to `move_to_vault_txid` (deposit-specific) but trusts the `payout_txid`/`payout_payer_operator_xonly_pk` columns unconditionally, and those columns were poisoned upstream by the outpoint-only join in `get_payout_txs_for_withdrawal_utxos`. The cryptographic bridge-circuit checks (`verify_storage_proofs`, `SPV::verify`) are only invoked if a challenge is actually raised; since the DB conflation prevents the challenge from being raised in the first place, the circuit-level checks never run for the fraudulent `idx_b` claim.

### Impact Explanation
This is Critical: an operator is reimbursed from a move-to-vault UTXO it never funded a payout for. The real withdrawer tied to `idx_b` never receives their payout output, yet the operator still drains `idx_b`'s vault via the (uncontested) round reimbursement path. The attack is repeatable across any number of deposit/withdrawal index pairs that are registered with colliding outpoint bytes, and does not require operator collusion - an honest operator's own automation can be misled into double-claiming.

### Likelihood Explanation
Preconditions are cheap and fully within the stated attacker capabilities: the attacker only needs to make two ordinary deposits and call Citrea's `withdraw` twice with attacker-chosen, identical outpoint bytes - no privileged role, no key compromise, no majority hashrate. The only genuinely external factor is whether the Citrea Bridge contract itself declines to store the same outpoint bytes at two different withdrawal indices; this repo's code performs no independent deduplication and unconditionally trusts and persists whatever Citrea reports. Given the stated attacker capability ("choose the bytes of a withdrawal UTXO"), the scenario is directly reachable through `core/src/verifier.rs`'s `update_citrea_deposit_and_withdrawals` → `Database::update_withdrawal_utxo_from_citrea_withdrawal` → `Database::get_payout_txs_for_withdrawal_utxos` pipeline with no in-repo constraint blocking it.

### Recommendation
Add a uniqueness/consistency check in `Database::update_withdrawal_utxo_from_citrea_withdrawal` (or a DB constraint) rejecting/flagging a `(withdrawal_utxo_txid, withdrawal_utxo_vout)` pair that is already assigned to a different `idx`. Additionally, change `get_payout_txs_for_withdrawal_utxos`'s join to also bind on `move_to_vault_txid`/deposit-specific data (or otherwise assert exclusivity - e.g. require `bitcoin_syncer_spent_utxos` matches be attributed to exactly one `idx`), and make `is_kickoff_malicious` verify that the payout transaction actually funds *this* deposit's specific withdrawal request (e.g., by checking the payout output against the withdrawal's registered `output_script_pubkey`/`output_amount`) rather than trusting the `withdrawals.payout_txid` column blindly.

// core/src/database/verifier.rs (test module)
#[tokio::test]
async fn duplicate_withdrawal_utxo_conflates_payout() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    let mut dbtx = db.begin_transaction().await.unwrap();

    let payout_txid = Txid::from_byte_array([0xAA; 32]);
    let idx_a = 1u32;
    let idx_b = 2u32;
    let move_txid_a = Txid::from_byte_array([0x01; 32]);
    let move_txid_b = Txid::from_byte_array([0x02; 32]);
    // SAME outpoint bytes registered for both indices
    let shared_utxo = bitcoin::OutPoint { txid: Txid::from_byte_array([0xFF; 32]), vout: 0 };

    let block_id = db.insert_block_info(Some(&mut dbtx), &BlockHash::all_zeros(), &BlockHash::all_zeros(), 0).await.unwrap();
    db.insert_txid_to_block(&mut dbtx, block_id, &payout_txid).await.unwrap();
    // only ONE real spend exists
    db.insert_spent_utxo(&mut dbtx, block_id, &payout_txid, &shared_utxo.txid, shared_utxo.vout.into()).await.unwrap();

    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_a, &move_txid_a).await.unwrap();
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_b, &move_txid_b).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_a, shared_utxo, block_id).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_b, shared_utxo, block_id).await.unwrap();

    // Binding under test: exactly 1 payout tx should exist for 1 real spend,
    // but conflation returns it twice, once per idx.
    let txs = db.get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id).await.unwrap();
    assert_eq!(txs.len(), 2); // BROKEN: should be 1 spend -> 1 attributable withdrawal
    assert!(txs.iter().any(|(i, t)| *i == idx_a && *t == payout_txid));
    assert!(txs.iter().any(|(i, t)| *i == idx_b && *t == payout_txid));

    // Confirm both deposits now show as "paid out" by the same tx/operator
    db.update_payout_txs_and_payer_operator_xonly_pk(Some(&mut dbtx), txs.iter().map(|(i,t)| (*i,*t, None, BlockHash::all_zeros())).collect()).await.unwrap();
    let info_a = db.get_payout_info_from_move_txid(Some(&mut dbtx), move_txid_a).await.unwrap().unwrap();
    let info_b = db.get_payout_info_from_move_txid(Some(&mut dbtx), move_txid_b).await.unwrap().unwrap();
    assert_eq!(info_a.2, payout_txid);
    assert_eq!(info_b.2, payout_txid); // BROKEN: idx_b falsely shows the same payout as satisfied
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
