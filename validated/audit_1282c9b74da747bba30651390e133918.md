### Title
Unbounded Memory Allocation via `getRPCRequests` in New Relic/Datadog RPC Tracing Wrappers Bypasses `MaxRequestContentLength` — ([File: networks/rpc/http_newrelic.go], [File: networks/rpc/http_datadog.go])

### Summary
When Kaia's JSON-RPC HTTP server is built/run with New Relic APM or Datadog APM tracing enabled (`NEWRELIC_APP_NAME`/`NEWRELIC_LICENSE` or `DD_TRACE_ENABLED` env vars), every inbound HTTP RPC request is first passed through `getRPCRequests(r)` in order to extract the method name for tracing/logging purposes. `getRPCRequests` calls `io.ReadAll(r.Body)` with no size limit whatsoever, before the request ever reaches `Server.ServeHTTP`'s `validateRequest` check that enforces `common.MaxRequestContentLength` (512 KB).

### Finding Description
`NewHTTPServer` builds the handler chain as: CORS → vhost → timeout → (optionally) New Relic wrapper → (optionally) Datadog wrapper, with the tracing wrappers applied outermost. [5](#0-4) 
Both `newNewRelicHTTPHandler` and `newDatadogHTTPHandler` unconditionally call `getRPCRequests(r)` as their very first action: [6](#0-5) 
`getRPCRequests` itself does an unlimited `io.ReadAll(r.Body)`: [1](#0-0) 
Only after this unbounded read completes does control pass into `handler.ServeHTTP(...)`, which is where `validateRequest` actually checks `r.ContentLength > common.MaxRequestContentLength` and rejects oversized requests with `413`: [7](#0-6) [8](#0-7) 
The `MaxRequestContentLength` guard (512 KB) that is supposed to bound RPC body size is therefore rendered ineffective whenever these optional tracing wrappers are active, because the entire attacker-controlled body is buffered into a Go byte slice via `io.ReadAll` regardless of its declared or actual size.

### Impact Explanation
A single unauthenticated HTTP POST to any public RPC endpoint of a node running with New Relic or Datadog tracing enabled can force the node to allocate memory proportional to the attacker-supplied body size, with no upper bound enforced at that stage. Repeated or large-enough requests can exhaust node memory, crashing the `kaiad`/RPC process (denial of service), consistent with CWE-770 (uncontrolled resource consumption) — directly analogous to the reported Salvo `form_data()`/`Extractible` issue where body reads occur before size validation. Because this is on the public JSON-RPC HTTP path, it is reachable by any public-RPC caller without prior authentication or special privileges, and can degrade or crash consensus/RPC-serving nodes that expose these integrations.

### Likelihood Explanation
Exploitation requires no authentication, no special transaction crafting, and no on-chain cost — just an HTTP POST with a large body to the node's RPC endpoint. The precondition is that the operator has enabled New Relic or Datadog tracing via environment variables, which is a supported, documented configuration path in `newNewRelicApp`/`newDatadogTracer` [9](#0-8) [10](#0-9) , not an attacker-controlled setting, so likelihood is tied to how commonly these APM integrations are used in production deployments of Kaia RPC nodes.

### Recommendation
Wrap `r.Body` in `io.LimitReader(r.Body, common.MaxRequestContentLength+1)` (mirroring the limiter already used in `newHTTPServerConn`, `networks/rpc/http.go:250`) before calling `io.ReadAll` inside `getRPCRequests`, and/or perform the `ContentLength`/content-type validation (`validateRequest`) prior to invoking the New Relic/Datadog wrappers so oversized requests are rejected with `413` before any tracing-related body buffering occurs.

### Proof of Concept
1. Run a Kaia node with `NEWRELIC_APP_NAME` and `NEWRELIC_LICENSE` (or `DD_TRACE_ENABLED=true`) set, exposing the JSON-RPC HTTP endpoint, in a memory-constrained environment.
2. Send an HTTP POST to the RPC endpoint with `Content-Type: application/json` and a body far exceeding `common.MaxRequestContentLength` (512 KB), e.g. several hundred MB of padding around a JSON-RPC payload, either with a spoofed/absent `Content-Length` or via chunked transfer encoding.
3. Observe that `newNewRelicHTTPHandler`/`newDatadogHTTPHandler` call `getRPCRequests(r)`, which reads the entire body into memory via `io.ReadAll` before `validateRequest`'s size check ever executes, causing large memory allocation; repeating/scaling the payload drives the process to OOM instead of returning `413 Request Entity Too Large`.

func getRPCRequests(r *http.Request) ([]*jsonrpcMessage, bool, error) {
	reqBody, err := io.ReadAll(r.Body)
	if err != nil {
		logger.Error("cannot read a request body", "err", err)
		return nil, false, err
	}

	r.Body = io.NopCloser(bytes.NewReader(reqBody))
	conn := &httpServerConn{Reader: io.NopCloser(bytes.NewReader(reqBody)), Writer: bytes.NewBufferString(""), r: r}

	codec := NewCodec(conn)

	defer codec.close()

	return codec.readBatch()
}

	}

func (s *Server) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	// Permit dumb empty requests for remote health-checks (AWS)

		return
	}

		http.Error(w, err.Error(), code)
		return
	}

func validateRequest(r *http.Request) (int, error) {
	if r.Method == http.MethodPut || r.Method == http.MethodDelete {
		return http.StatusMethodNotAllowed, errors.New("method not allowed")
	}
	if r.ContentLength > int64(common.MaxRequestContentLength) {
		err := fmt.Errorf("content length too large (%d>%d)", r.ContentLength, int64(common.MaxRequestContentLength))
		return http.StatusRequestEntityTooLarge, err
	}
	// Allow OPTIONS (regardless of content-type)
	if r.Method == http.MethodOptions {
		return 0, nil
	}
	// Check content-type
	if mt, _, err := mime.ParseMediaType(r.Header.Get("content-type")); err == nil {
		if slices.Contains(acceptedContentTypes, mt) {
			return 0, nil
		}
	}
	// Invalid content-type
	err := fmt.Errorf("invalid content type, only %s is supported", contentType)
	return http.StatusUnsupportedMediaType, err
}
