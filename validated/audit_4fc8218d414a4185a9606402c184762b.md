### Title
DataLayer mirror-URL SSRF via unauthenticated `create_new_mirror` coin — arbitrary outbound HTTP requests to attacker-chosen hosts during subscription sync - ([File: chia/data_layer/download_data.py])

### Summary
Any wallet user can publish an on-chain "mirror" coin for **any** DataLayer `launcher_id`, including stores they do not own, and populate it with arbitrary URLs. When another node subscribes to that store, `DataLayer.fetch_and_validate()` picks a server from these attacker-supplied mirror URLs and issues an outbound HTTP GET directly to it via `http_download()`, with no scheme/host allow-listing. This is the same bug class as CVE-2023-6853 (user-controlled "path"/URL parameter causing the server to make an SSRF request) — here the user-controlled value is the mirror URL embedded in a coin memo rather than an HTTP request parameter.

### Finding Description
`DataLayerWallet.create_new_mirror()` builds a standard coin spend that creates a coin with puzzle hash `create_mirror_puzzle().get_tree_hash()` and memos `[launcher_id, *urls]` [1](#0-0) . Crucially, this function performs no check that the caller owns or controls `launcher_id` — it is only a `standard_wallet.generate_signed_transaction` call, so any wallet holding a small amount of XCH can attach arbitrary attacker-chosen URL strings to *any* store id on chain, exposed also via the `dl_new_mirror` RPC/CLI path [2](#0-1) .

On the consumer side, `DataLayer.update_subscriptions_from_wallet()` pulls all mirror URLs for a store id from wallet RPC without any filtering [3](#0-2) . `fetch_and_validate()` then randomly selects one of these `servers_info` entries and passes its `url` down into `insert_from_delta_file()` → `download_file()` → `http_download()` [4](#0-3) .

`http_download()` issues the outbound request directly against the attacker-controlled base URL with no validation of scheme or host:
```
async with session.get(
    server_info.url + "/" + filename,
    headers=headers,
    timeout=timeout,
    proxy=proxy_url,
) as resp:
``` [5](#0-4) 

The only user-independent portion of the requested path is the deterministic `filename` suffix; the entire host/port/scheme/path prefix (`server_info.url`) is fully attacker-controlled, since it comes verbatim from the on-chain mirror coin memo. There is no allow-list, no restriction to `http`/`https`, and no blocking of private/loopback/link-local addresses (e.g. `127.0.0.1`, `169.254.169.254`, internal service ports) anywhere in this call chain.

This matches the project's own documentation of the trust boundary: "Plugin and mirror URLs are external trust inputs... Downloaded data must continue to be verified against wallet-advertised roots," which only addresses *data integrity* of what is downloaded, not the SSRF risk of the outbound connection itself [6](#0-5) .

### Impact Explanation
Any unprivileged wallet user (Data Layer client) can force other nodes that subscribe to a given store to make outbound HTTP requests to attacker-chosen hosts/ports, purely by spending mojos to create a mirror coin for that `launcher_id`. This enables internal network reconnaissance/port scanning from the victim's machine, requests to cloud metadata endpoints, or interaction with internal-only HTTP services reachable from the DataLayer host — all without needing the victim to trust or explicitly add the URL themselves, since it is auto-discovered via `update_subscriptions_from_wallet()`. Because downloaded content is still validated against the wallet-advertised root, this does not directly corrupt DataLayer data, but the SSRF side-channel (connection establishment, timing, error behavior) and potential exposure to internal services is a genuine confidentiality/integrity-adjacent risk on the host network, consistent with Medium severity per the CVSS vector in the report (AV:N/AC:L/PR:L/UI:N).

### Likelihood Explanation
Likelihood is moderate: the attacker needs only a funded wallet (no special privilege) to spend a small mirror-coin amount and set malicious URLs for any target `launcher_id`, and the victim need only be subscribed to that store — a normal DataLayer client action. The random server-selection logic in `fetch_and_validate()` means the malicious mirror will eventually be tried during the periodic sync loop.

### Recommendation
- Restrict `create_new_mirror`/`dl_new_mirror` mirror creation to only proceed for launcher ids the caller's wallet actually owns, or otherwise require an authorization signal tied to store ownership before the mirror is treated as legitimate.
- In `http_download()` (and `get_downloader()`), validate mirror URLs before connecting: enforce `http`/`https` scheme, resolve and reject private/loopback/link-local/metadata IP ranges, and consider an explicit user-approved mirror allow-list rather than fully automatic discovery from any on-chain mirror coin.
- Treat mirror URL fetch failures/successes as untrusted network I/O and sandbox/isolate outbound requests (e.g., via a dedicated egress proxy with SSRF protections) rather than direct `aiohttp.ClientSession` calls from the main DataLayer process.

### Proof of Concept
1. Attacker wallet calls `dl_new_mirror` (or CLI `chia data add_mirror`) targeting a victim's tracked `launcher_id` with `urls=["http://169.254.169.254/latest/meta-data/", ...]` and a small amount/fee [7](#0-6) .
2. Once confirmed on chain, the victim's DataLayer node calls `update_subscriptions_from_wallet()` for that store and adds the malicious URL to `servers_info` [3](#0-2) .
3. On the next `fetch_and_validate()` cycle, the victim's node randomly selects the malicious server and calls `http_download()`, issuing an outbound GET to the attacker-chosen internal/arbitrary host [5](#0-4) .

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
