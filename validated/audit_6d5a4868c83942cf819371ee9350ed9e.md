## Title
Reentrant double-drain of escrowed funds via check-before-effect ordering in `withdraw()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The core broken invariant in the seed report is: a guard reads a balance/state value, then an external-visible side effect happens, and only *afterward* is the accounting value decremented — so the guard is checked against stale state while state-changing/external actions are still in flight, letting the same "already-verified" resource be consumed more than once. In Timeswap, that stale-check let a burned token remain in an enumeration. In Hyperbridge's Tron `IntentGatewayV2.sol`, the exact same check-before-effect pattern appears in `withdraw()`, but here the intervening step is an **external native-token call to an attacker-controlled beneficiary**, turning the stale-check bug into a classic checks-effects-interactions violation and a reentrancy-based double-spend of escrowed funds.

### Finding Description
`withdraw()` is the internal settlement routine invoked from `onAccept()` (guarded only by `onlyHost`) for both `RedeemEscrow` and `RefundEscrow` request kinds: [1](#0-0) 

Inside `withdraw()`, for each token in the withdrawal request, the escrow-accounting decrement (`_orders[body.commitment][token] -= amount;`) happens **after** the external transfer, not before: [2](#0-1) 

Specifically the guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` only checks non-zero — it never checks `amount <= escrowed` — and the state mutation is deferred until after the raw `.call{value: amount}("")` (for native token) or the low-level `token.call(...transfer...)` (for ERC-20) has already executed and control has passed to `beneficiary`. Because `beneficiary` is attacker-chosen data embedded in the order (`body.beneficiary`, ultimately `order.user` on refund or the fill beneficiary on redeem), an attacker can set it to a malicious contract whose `receive()`/fallback reenters the gateway while `_orders[body.commitment][token]` still reflects the pre-withdrawal (undecremented) balance.

This mirrors the seed bug precisely: the check (`== 0` / `== 0` supply check) is evaluated against state that has not yet been updated to reflect the in-progress operation, so a second invocation observes the same "escrow present" state and is allowed through again before the first invocation's effects are committed.

Note that the sibling implementation in `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw()` gets the ordering right — it decrements `_orders[body.commitment][token]` **before** performing the external call: [3](#0-2) 
This confirms the Tron variant's ordering is a real, local regression of the checks-effects-interactions pattern relative to the intended design, not an inherent protocol requirement.

### Impact Explanation
This falls squarely under "stealing or loss of funds" and "logic attacks / replay double-settlement" in the bounty scope: a beneficiary-controlled contract can re-enter during the native-token `.call` in `withdraw()` and, before `_orders[body.commitment][token]` is decremented, trigger further consumption of the same escrow entry, draining more value than was actually escrowed for that commitment/token. Because `_filled[body.commitment]` is set once at the very top of `withdraw()` (line 684) rather than gating each token's payout, and there is no `nonReentrant` guard on `onAccept`/`withdraw`, the intra-function reentrancy window across the token loop is the exploitable primitive — an unprivileged order-placer (who fully controls the order's beneficiary field) can cause unauthorized extra fund movement out of the gateway's ERC-20/native custody.

### Likelihood Explanation
The trigger is fully within an unprivileged user's control: they only need to (1) place/cancel an order whose beneficiary is a contract they control, and (2) implement a `receive()`/fallback that reenters before returning. No malicious relayer, prover, or admin is required — the `onAccept` call itself is legitimately triggered by the host processing a normal `RedeemEscrow`/`RefundEscrow` message; the attacker's contribution is purely the reentrant beneficiary logic. This is a standard, well-understood reentrancy pattern, making exploitation straightforward once a message reaches `onAccept` for an order with a multi-token / native-token withdrawal.

### Recommendation
Apply checks-effects-interactions consistently in `withdraw()`: decrement `_orders[body.commitment][token]` (and validate `amount <= escrowed`, not just `!= 0`) *before* performing the native `.call` or ERC-20 `transfer` call, exactly as `IntentsBase.sol::_withdraw` already does. Additionally consider adding an explicit reentrancy guard on `onAccept`/`withdraw` as defense in depth.

### Proof of Concept
1. Attacker calls `placeOrder(order, graffiti)` on the source chain with `order.user`/beneficiary set to `AttackerContract`, escrowing e.g. 10 ETH + some ERC-20 as inputs.
2. Attacker (or anyone) triggers cancellation such that a `RefundEscrow` (or a solver fills the order producing `RedeemEscrow`) message is dispatched back to the source chain, eventually invoked via `onAccept()` → `withdraw(body, true)`.
3. In `withdraw()`'s loop, when processing the native-token entry, `(bool sent,) = beneficiary.call{value: amount}("")` transfers ETH to `AttackerContract` **before** `_orders[body.commitment][address(0)] -= amount` executes.
4. `AttackerContract.receive()` reenters (e.g., calls back into a path that reads `_orders[body.commitment][token]`, which still holds the pre-decrement value) to trigger another payout for the same commitment/token before the original call frame decrements the balance, extracting more funds than were actually escrowed.         address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();

                ++i;
            }
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
