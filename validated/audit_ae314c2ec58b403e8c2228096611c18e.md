### Title
Malicious Git server can spoof `WWW-Authenticate: realm="GitHub"` to hijack the credential-helper flow and redirect GitHub Enterprise OAuth sign-in to an attacker-controlled endpoint - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
Desktop's credential-helper trampoline classifies an unknown Git remote host as a "GitHub"-flavored endpoint (`'enterprise'`) purely by trusting a `WWW-Authenticate` header echoed back by the remote server, then automatically launches the GitHub Enterprise sign-in / OAuth flow pointed at that attacker-supplied `origin`. Because the attacker fully controls this response (it's returned by the very Git server/proxy the user is cloning/fetching/pushing from), they can trick Desktop into believing an arbitrary host is a GitHub Enterprise instance and drive the user into an OAuth/browser sign-in flow whose `endpoint` is the attacker's own server.

### Finding Description
When a `git` HTTP request needs credentials, `getEndpointKind` decides how to classify the remote: [1](#0-0) 

Critically, if the host isn't recognized as `github.com`/`ghe.com`/an existing account, the code falls back to inspecting `wwwauth[]` entries in the credential map — which originate directly from the `WWW-Authenticate` HTTP response header sent by the remote Git server:

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } ...
```

This header is fully attacker-controlled content coming from the remote the user is interacting with (a cloned/added remote, or a malicious proxy sitting between the user and a legitimate host). There is no cryptographic or DNS-based verification that the host is actually a GitHub Enterprise server — a plain string match on `realm="GitHub"` is sufficient.

Once classified as `'enterprise'`, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)`: [2](#0-1) 

`promptForGitHubSignIn` then drives the enterprise sign-in flow using the attacker's own `origin` as the sign-in endpoint: [3](#0-2) 

`setSignInEndpoint`/`setEndpoint` only performs syntactic URL validation (HTTPS + valid host) — it never verifies the host is a genuine GitHub Enterprise (or GHE.com) deployment: [4](#0-3) [5](#0-4) 

If the user chooses browser-based OAuth sign-in, Desktop opens `getOAuthAuthorizationURL(endpoint, csrfToken)` in the external browser and later exchanges the returned code via `requestOAuthToken(endpoint, action.code)` — both calls target the attacker-supplied `endpoint`: [6](#0-5) [7](#0-6) 

This mirrors the report's underlying broken invariant: a security-sensitive value (here, "which endpoint should receive our authentication material") is derived from and directed at data supplied by the untrusted counterparty, rather than an address the user explicitly trusts, and no downstream check reasserts the correct target before sensitive material (OAuth code exchange / a full sign-in flow presented as legitimate) is sent there.

### Impact Explanation
An attacker who controls a Git server/proxy that the victim clones, fetches, or pushes to (no local access or prior compromise needed) can:
- Force Desktop to present a "GitHub sign-in" UI/OAuth browser flow pointed at the attacker's own domain instead of a real GitHub Enterprise host, enabling credential/token phishing under a false sense of legitimacy created by Desktop itself.
- Cause OAuth authorization-code exchange requests (`requestOAuthToken`) to be sent to the attacker's server, potentially leaking the authorization code and any state Desktop includes in that request.
- This satisfies the "unauthorized OAuth or account binding" / "credential/token exfiltration" categories, since Desktop is convinced by remote-controlled data to bind a sign-in session to an attacker's endpoint.

### Likelihood Explanation
Medium: the attacker needs to control (or MITM/proxy) the Git remote endpoint the victim is interacting with, but this is squarely in-scope per the allowed impact criteria ("a git remote/proxy response"). No unusual user action is required beyond a normal `git fetch`/`clone`/`push` against a repository whose HTTPS remote is attacker-controlled or proxied, followed by responding to Desktop's authentication prompt as one normally would.

### Recommendation
- Do not use the `WWW-Authenticate` header content alone to classify a host as a trusted GitHub/Enterprise endpoint; require either a known/pinned account association or an authenticated discovery call (e.g., `isGitHubHost`) before treating an unknown host as `'enterprise'`.
- Before invoking `promptForGitHubSignIn`/`setSignInEndpoint` from a credential-helper-triggered flow, surface the target host clearly to the user and require explicit confirmation that this is the intended enterprise instance (i.e., don't silently drive the OAuth flow's `endpoint`/`origin` from the WWW-Authenticate value returned by the remote peer).
- Consider stripping or ignoring `wwwauth[]`-derived classification entirely for hosts not already associated with a stored account or a user-entered Enterprise URL.

### Proof of Concept
1. Attacker stands up an HTTPS Git server (or MITM proxy in front of a plausible-looking host) that, on an unauthenticated request, responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote (or clones it) in GitHub Desktop and performs a fetch/push.
3. Desktop's credential helper (`createCredentialHelperTrampolineHandler` → `getCredential` → `getEndpointKind`) reads the `wwwauth[]` value from git's credential protocol input, matches `realm="GitHub"`, and returns `'enterprise'`.
4. Since no account exists for that endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which calls `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` with `origin` equal to the attacker's server.
5. Desktop shows a "Sign in" dialog seemingly for a GitHub Enterprise instance whose endpoint is actually the attacker's server; if the user proceeds with browser-based OAuth, `shell.openExternal(getOAuthAuthorizationURL(endpoint, csrfToken))` opens a browser page hosted by the attacker, and any resulting code is later POSTed to the attacker via `requestOAuthToken(endpoint, action.code)`.

Note: I was unable to execute this end-to-end in a live environment (no browser/network access here); the analysis is based on static code tracing through `getEndpointKind`, `promptForGitHubSignIn`, `setSignInEndpoint`/`setEndpoint`, and `authenticateWithBrowser`/`resolveOAuthRequest`, all cited above.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
