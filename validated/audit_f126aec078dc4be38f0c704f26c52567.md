### Title
Permissionless `harvestAll()` enables reward-sniping / yield theft via flash-stake timing in `DelegateVoteRewardPool` - (File: rewards/DelegateVoteRewardPool.sol)

### Summary
`DelegateVoteRewardPool.harvestAll()` has no access-control modifier and can be called by any address at any time, triggering `claimAllBribes` → `_manageRewards` → `_queueNewRewardsWithoutTransfer` → `_provisionReward`. Because reward provisioning is instantaneous (no time-weighted streaming, no `periodFinish`/`rewardRate`), an attacker can stake into the delegate pool immediately before triggering harvest and withdraw immediately after, capturing a pro-rata share of rewards that accrued from bribes earned by long-term stakers, without bearing any real staking duration. [1](#0-0) 

### Finding Description
`harvestAll()` is `external` with no `onlyOperator`/`onlyOwner` restriction, unlike `stakeFor`/`withdrawFor` which are `onlyOperator`: [1](#0-0) 

It forwards to `IWombatBribeManager(operator).claimAllBribes(address(this))`, which — because the delegate pool itself is registered as a "voter" on the underlying LP pools via `_updateVote()` — harvests all bribe rewards owed to the delegate pool from every LP pool it has voted on, and returns them for queuing: [2](#0-1) [3](#0-2) 

`_manageRewards` then calls `_queueNewRewardsWithoutTransfer` → `_provisionReward` in `BaseRewardPoolV2`, which is not time-streamed: it immediately bumps `rewardPerTokenStored` by `_amountReward * 10**decimals / totalStaked()` based on the pool's *current* `totalSupply` at the moment of the call: [4](#0-3) 

The user-facing earning formula is `_userShare * (rewardPerToken - userRewardPerTokenPaid[account])`, and `userRewardPerTokenPaid` is only updated when `stakeFor`/`withdrawFor`/`getReward` runs the `updateRewards` modifier: [5](#0-4) [6](#0-5) 

Exploit flow:
1. Attacker votes into `delegatedPool` (i.e., calls the bribe manager's vote path that results in `DelegateVoteRewardPool.stakeFor(attacker, X)`), which snapshots `userRewardPerTokenPaid[attacker] = rewardPerTokenStored` at the pre-harvest value: [7](#0-6) 
2. Attacker (or anyone) immediately calls the unprotected `harvestAll()`, which pulls in bribes accrued from all LP pools over the time other delegate-pool stakers were staked, and instantly bumps `rewardPerTokenStored` using the current `totalSupply` (which now includes the attacker's freshly added stake).
3. Attacker withdraws/unvotes immediately, and `_getDelegateReward`/`earned()` credits them `X * (new rewardPerToken - old rewardPerToken)`, i.e., a full pro-rata share of the harvested rewards despite zero real holding duration. [8](#0-7) 

Existing checks do not stop this: there is no `nonReentrant` needed here (no reentrancy involved), no minimum staking duration/vesting, and no restriction on who can call `harvestAll()` to control the timing of reward realization. The root cause is architectural: reward accounting uses a single global `rewardPerTokenStored` snapshot model with instantaneous provisioning instead of a time-decayed/streamed distribution, combined with a permissionless trigger (`harvestAll()`) for when that provisioning happens.

### Impact Explanation
This is a theft of unclaimed yield: an attacker with no genuine economic exposure to the delegate pool over time can extract rewards that should accrue to long-term voters/stakers, diluting their expected share. This matches the "theft of unclaimed yield" impact class. The magnitude scales with the size of the bribe batch harvested and the attacker's ability to size their flash stake relative to `totalSupply` at harvest time.

### Likelihood Explanation
Feasibility depends on: (a) whether staking/voting into `delegatedPool` and unvoting can be done atomically or within a short window without lockup (not fully confirmed from the reviewed `vote`/unvote code path in `WombatBribeManager`), and (b) capital availability to size a large enough stake relative to `totalSupply` to meaningfully capture rewards. `harvestAll()` itself requires no privilege and no capital to call, and is repeatable at will since it has no rate limiting beyond what `claimAllBribes`/underlying bribe accounting naturally provides. This makes the timing-based exploit highly feasible from a purely permission standpoint; the exact capital/lockup constraints of the vote/unvote path in `WombatBribeManager` were not fully traced within available context and would need on-chain/test verification.

### Recommendation
- Convert `DelegateVoteRewardPool`'s (and `BaseRewardPoolV2`'s) reward distribution to a time-weighted streaming model (e.g., `rewardRate`/`periodFinish` accrued per second) instead of instantaneous `rewardPerTokenStored` bumps, so newly staked balances cannot capture rewards earned before their stake existed.
- Alternatively/additionally, restrict `harvestAll()` to a trusted caller (e.g., `onlyOperator` or a keeper role) and/or enforce a minimum bonding/cooldown period between `stakeFor` (vote) and `withdrawFor` (unvote) in the delegate pool to prevent flash-stake reward sniping.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `DelegateVoteRewardPool`, and underlying LP `BribeRewardPool`s with mock reward tokens; set up `delegatedPool` and register LP pools with voting weights.
2. Staker A votes into `delegatedPool` with amount `Y` and holds it while bribes accrue in the underlying LP `BribeRewardPool`s over simulated time (e.g., via `donateRewards`/`queueNewRewards` on the LP rewarders).
3. Immediately before triggering harvest, Attacker calls the bribe-manager vote path with amount `X` into `delegatedPool` (triggers `DelegateVoteRewardPool.stakeFor(attacker, X)`).
4. Anyone calls `DelegateVoteRewardPool.harvestAll()` directly (no privilege needed), which pulls bribes into the delegate pool and bumps `rewardPerTokenStored`.
5. Attacker immediately unvotes/withdraws (`withdrawFor` with `_claim = true`) and asserts `earned(attacker, rewardToken)` / actual payout is greater than zero and disproportionate — e.g., compare `attackerReward / X` (per-unit-stake, per-second held) versus `stakerAReward / Y` (per-unit-stake, per full period held) — expect attacker's per-unit-time yield to be orders of magnitude higher, demonstrating the reward-sniping dilution against Staker A.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;

                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
