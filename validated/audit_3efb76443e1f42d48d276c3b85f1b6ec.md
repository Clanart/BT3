## Finding

### Title
Silent, unconfirmed rewrite of a repository's git remote URL from an untrusted GitHub API field allows redirecting a user's fetch/push target - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
Desktop periodically refreshes the `GitHubRepository` metadata tied to a local repository by calling the GitHub REST API and, if certain conditions are met, silently rewrites the local `origin` remote's URL to whatever `clone_url` the API response contains. The only checks performed are protocol equality and "the current remote still matches what we last saw from the API" — the new hostname/owner/name from the API response is trusted implicitly. An attacker who controls the API response for a tracked repository (a malicious/compromised GitHub Enterprise Server, a MITM'd non-TLS-pinned proxy, or any server Desktop is configured to query) can set `clone_url` to an arbitrary host with the same URL scheme and Desktop will overwrite the user's real `origin` remote to point at it — without any prompt, diff, or confirmation.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  performs the update logic:

- `remoteUrl` = the current local remote URL.
- `updatedRemoteUrl` = `apiRepo.clone_url`, taken directly from the GitHub API response.
- `protocolsMatch` only compares the URL scheme string (`https:` vs `https:`), not the host.
- `remoteUrlUnchanged` only verifies that the *current* local remote still matches the *previously cached* `gitHubRepository.cloneURL` (i.e., the user hasn't manually edited the remote since the last known-good API value) — it says nothing about whether the *new* API value is trustworthy.
- If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, Desktop calls `gitStore.setRemoteURL(...)`, which runs `git remote set-url origin <new-url>` with no user interaction: [2](#0-1) .

Critically, none of these checks constrain the *new* URL's hostname to be the same as the previous hostname or the same as the account's configured endpoint. `urlMatchesRemote` (used inside `urlsMatch`/`remoteUrlUnchanged`) enforces hostname equality only between the *old* cached clone URL and the *current* remote — never between the *new* API value and anything trusted: [3](#0-2) .

This function is invoked from `repositoryWithRefreshedGitHubRepository`, which is triggered on ordinary flows such as adding a repository, selecting a repository, and other refresh paths, and it derives `apiRepo` straight from `api.fetchRepository(owner, name)`: [4](#0-3) .

The broken invariant is: **the local git remote configuration — the destination of every future `git push`/`fetch` — is treated as safely re-derivable from an untrusted, remote-controlled API field, with only a same-protocol check and no re-validation of host trust.** This mirrors the report's core flaw: a state (redemption/funding destination in the contract; push/fetch destination in Desktop) is silently migrated based on a value the app doesn't adequately validate, with no requirement that the change be reviewed/paused/confirmed first.

### Impact Explanation
If exploited, the user's `origin` remote silently becomes an attacker-controlled URL. Subsequent `git push` operations invoked through Desktop (`_push` → `performPush` → `pushRepo`) will send the user's commits to the attacker's server instead of the real GitHub repository, i.e. **silent corruption of what the user pushes**, and the user has no visual indicator this happened (the remote settings UI would show the new URL, but there's no confirmation dialog or diff shown at the time of the automatic change). Depending on the attacker's server response to Desktop's credential trampoline flow, this could also be leveraged to harvest credentials the user types in response to a spoofed authentication prompt for the new host, although GitHub/GHE stored tokens themselves are not automatically sent to hosts outside the recognized account endpoints.

### Likelihood Explanation
Requires the attacker to control or MITM the API responses Desktop makes for a specific tracked repository (e.g., a rogue/compromised GitHub Enterprise Server the victim already has configured, or a network position that can intercept `api.fetchRepository` calls when TLS validation is bypassed/misconfigured). This does not require local/physical access, prior malware, leaked credentials, or unnatural user steps — it happens automatically the next time Desktop refreshes GitHub repository metadata for that repo (e.g., on selecting the repository, adding it, or during background refresh), which is routine, unprompted app behavior.

### Recommendation
- Before silently rewriting a remote URL from API data, validate that the new URL's hostname belongs to the same trusted endpoint the account/API request was made against (i.e., reject any `clone_url` whose hostname differs from the known account endpoint's host), not just that the protocol string matches.
- Prefer prompting the user (similar to how repository renames are surfaced elsewhere in the app) before silently mutating `origin`, especially when the hostname portion of the URL changes.
- Treat `clone_url` (and similar fields) returned from the API as untrusted input requiring strict allow-listing against the expected endpoint, mirroring the report's recommendation to gate sensitive field changes behind stronger invariant checks rather than trusting a single external-controlled value.

### Proof of Concept
1. Point Desktop at a GitHub Enterprise Server account (or intercept the `api.fetchRepository` HTTPS response for a repo the victim has cloned, e.g. via a compromising server-side plugin or admin access to that GHES instance).
2. Ensure the victim's local `origin` still matches the previously known clone URL for that repo (default state for any repo the user hasn't manually reconfigured).
3. Have the malicious/compromised server return a repository JSON payload where `clone_url` is set to `https://evil-server.example/foo/bar.git` (same `https:` scheme as before, so `protocolsMatch` is true) instead of the real GHES clone URL.
4. Have the victim perform any action that triggers `repositoryWithRefreshedGitHubRepository` (e.g., select the repository, or reopen Desktop, or add the repository) — see call site: [5](#0-4) .
5. Observe that Desktop silently runs `git remote set-url origin https://evil-server.example/foo/bar.git` with no confirmation dialog, per the logic in [6](#0-5) .
6. The next push/fetch performed via Desktop's UI now targets the attacker's server.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
