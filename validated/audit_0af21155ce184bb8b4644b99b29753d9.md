### Title
Webhook shop-domain header is not covered by HMAC signature, enabling cross-shop webhook confusion - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` validates an inbound webhook solely by recomputing an HMAC over `request.raw_post` using the app's shared secret, then separately trusts the `X-Shopify-Shop-Domain` header — which is **not** part of the signed payload — to determine which shop the webhook belongs to.

### Finding Description
`verify_request` computes `hmac_valid?(data)` where `data = request.raw_post` [1](#0-0) , and `hmac_valid?` compares the `X-Shopify-Hmac-Sha256` header against `HMAC(secret, raw_post)` using the app-wide `ShopifyApp.configuration.secret`/`old_secret` [2](#0-1) . This secret is the app's single API secret, identical for every installed shop — it is not shop-specific. Separately, `shop_domain` in the same concern simply reads the `X-Shopify-Shop-Domain` header with no cryptographic binding to the signed body [3](#0-2) . The generated declarative webhook controller does the same: it forwards `webhook_request.shop` (derived from headers) to the background job that performs shop-scoped work, again without the shop identity itself being covered by the HMAC [4](#0-3) .

This mirrors the root cause in the reference report: an attacker-controlled value (there, the reward token/amount; here, the shop-domain header) that determines who benefits/whose data is acted upon is accepted without being validated against the cryptographically-verified portion of the request. Because the same app secret is used for HMAC generation across all shops that install the app, anyone who can obtain one genuine `(raw_body, hmac)` pair from a webhook that Shopify sent for *any* shop (including a shop they legitimately install the app on themselves) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header value naming a victim shop, and the HMAC check will still pass because that header is outside the signed data.

### Impact Explanation
If the app's webhook job logic keys any per-shop side effects (data storage, deletion, entitlement changes, uninstall handling, privacy webhooks, etc.) off of `shop_domain`/`webhook_request.shop` from the header, an attacker can cause shop-scoped jobs to run against an arbitrary victim shop identifier using a validly-signed payload they legitimately obtained for their own shop. This is a cross-shop data/action confusion analogous to the original report's cross-user reward misdirection: the "identity" field driving who is credited/affected is not covered by the trust mechanism (HMAC) that is supposed to guarantee authenticity.

### Likelihood Explanation
Medium: exploitation requires the attacker to (a) install the target app on their own shop (an unprivileged, self-service action for public apps) to obtain a legitimately-HMAC'd webhook body, and (b) replay it with a forged shop-domain header to the exposed webhook endpoint. No secret material needs to be known/leaked by the attacker — only capture/replay of a value they were legitimately sent.

### Recommendation
Bind the shop identity into the verified data rather than trusting an unauthenticated header: either derive `shop_domain` exclusively from a field contained in the signed webhook body (many Shopify webhook payloads include the shop's `myshopify_domain` or equivalent field), or additionally verify that the header-provided shop domain corresponds to a shop for which this exact HMAC/body combination could only have been generated (e.g., cross-check against session storage keyed by an already-authenticated identifier), and reject on mismatch before dispatching any job.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com`, triggering a real webhook delivery with a valid `X-Shopify-Hmac-Sha256` header computed over some `raw_post` body using the app's shared secret.
2. Attacker replays that exact `raw_post` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `hmac_valid?` succeeds (it only checks the body/HMAC pair, unchanged from the legitimate delivery) [1](#0-0) , and the downstream job is queued using the attacker-supplied `shop_domain` value rather than the shop that actually generated the payload.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
