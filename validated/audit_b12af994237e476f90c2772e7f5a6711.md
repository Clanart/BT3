## #Vulnerability found

### Title
Sequential integer division before multiplication causes systematic NFT royalty underpayment in offer settlement - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`compute_royalty_amount()` and the sibling `NFTWallet.royalty_calculation()` helper compute royalty payouts using two chained integer divisions instead of multiplying first and dividing once at the end. This is the exact "division before multiplication" precision-loss bug class described in the report, applied to the NFT royalty math used when constructing real on-chain offer settlements rather than to a management fee.

### Finding Description
`compute_royalty_amount` is defined as: [1](#0-0) 

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(...)
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    ...
```

The expression performs `abs(offered_amount) // royalty_split` **first** (an integer division that truncates), then multiplies by `percentage`, then divides by `MAX_ROYALTY_BASIS_POINTS` (10000) again. Each division step discards a remainder, and — because both divisions happen before the multiplication is done relative to the original numerator — the combined truncation loses more precision than a single final division would. Correct order (matching the report's recommended fix pattern) would be `abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`.

The same anti-pattern is repeated in the `royalty_calculation` static method used by the `nft_calculate_royalties` RPC: [2](#0-1) 

```python
"amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
```

`compute_royalty_amount` is not a cosmetic helper — it directly produces the `extra_royalty_amount` used to build the actual `CreateCoin` condition paid to the royalty address during NFT-offer settlement: [3](#0-2) 

```python
royalty_payments: dict[bytes32 | None, list[tuple[bytes32, CreateCoin]]] = {}
for asset, amount in fungible_asset_dict.items():  # offered fungible items
    if amount < 0 and request_side_royalty_split > 0:
        payment_list: list[tuple[bytes32, CreateCoin]] = []
        for launcher_id, address, percentage in required_royalty_info:
            extra_royalty_amount = compute_royalty_amount(amount, request_side_royalty_split, percentage)
            payment_list.append((launcher_id, CreateCoin(address, extra_royalty_amount, [address])))
        royalty_payments[asset] = payment_list
```

`royalty_split` (`request_side_royalty_split` / `offer_side_royalty_split`) is the count of royalty-enabled NFTs bundled together in a single offer (`amount > 0`/`amount < 0` accumulation), so any offer that bundles more than one NFT (`royalty_split > 1`) exercises the two-step truncation path.

Numeric example demonstrating the loss (percentage in basis points, `MAX_ROYALTY_BASIS_POINTS = 10000`):
- `offered_amount = 1_000_000`, `royalty_split = 3`, `percentage = 3333` (33.33%)
- Current (sequential-division) code: `1_000_000 // 3 = 333333`; `333333 * 3333 // 10000 = 111099`
- Correct (multiply-first) result: `1_000_000 * 3333 // (3 * 10000) = 111100`

The current implementation pays out 1 fewer mojo than the mathematically correct royalty, in this example and in general whenever `royalty_split > 1` and the division does not divide evenly.

### Impact Explanation
This causes the royalty address (the NFT creator/royalty beneficiary) to be systematically underpaid whenever multi-NFT bundle offers are settled, with the "missing" value effectively staying with the offer counterparty. This is a value-leak analogous to the reported bug: individually small (bounded by rounding, i.e., at most `royalty_split - 1` mojo-equivalent loss per settlement), but it recurs on every multi-NFT offer settlement across the network, systematically diverting value away from royalty recipients over time — the same "protocol undercharges legitimate parties" failure mode called out in the source report, here manifesting as under-delivery of royalty payments rather than under-collection of a management fee.

### Likelihood Explanation
Any wallet user or offer counterparty can trivially trigger this by constructing (as maker) or accepting (as taker) an NFT offer that bundles more than one royalty-enabled NFT (`royalty_split > 1`) via the standard `make_nft1_offer` / offer-taking flow — no special permissions or malicious peer/node behavior are required. The condition is hit on ordinary, commonly-used multi-NFT offer paths (see `chia/_tests/wallet/nft_wallet/test_nft_1_offers.py`'s `test_complex_nft_offer`, which already exercises multiple royalty-enabled NFTs in one offer).

### Recommendation
Refactor both `compute_royalty_amount` and `NFTWallet.royalty_calculation` to perform the multiplication first and a single final division, e.g.:

```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```

and similarly for `royalty_calculation`:

```python
"amount": abs(amount) * percentage // (len(royalty_assets_dict) * MAX_ROYALTY_BASIS_POINTS),
```

This preserves full precision and prevents the systematic royalty underpayment.

### Proof of Concept
1. Using `chia.wallet.nft_wallet.nft_wallet.compute_royalty_amount`, call:
   - `compute_royalty_amount(offered_amount=-1_000_000, royalty_split=3, percentage=3333)` → returns `uint64(111099)`.
2. Compute the mathematically correct value with multiply-first ordering: `1_000_000 * 3333 // (3 * 10000) = 111100`.
3. The discrepancy (`111100 - 111099 = 1` mojo per settlement in this example, larger for larger `royalty_split`/less-evenly-divisible amounts) demonstrates the systematic underpayment reproducible via `chia/_tests/wallet/nft_wallet/test_nft_royalty.py`-style unit tests, and is reachable in production through any `make_nft1_offer` call bundling multiple royalty NFTs (`request_side_royalty_split`/`offer_side_royalty_split > 1`) as shown at [4](#0-3)  and consumed at [5](#0-4) .

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
