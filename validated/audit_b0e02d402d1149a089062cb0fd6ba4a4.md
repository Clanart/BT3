### Title
`ThresholdKeys::read` deserializes an internally inconsistent, fully attacker-defined key object (no `secret_share·G == verification_shares[i]` binding, no DKG provenance) — (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2022-1802 is a prototype-pollution bug: an attacker corrupts the fields/methods of a trusted object, and privileged downstream code then acts on assumptions the object no longer satisfies. The Serai analog is `ThresholdKeys::read` / `ThresholdKeys::new` in `crypto/dkg`: deserialization accepts attacker-supplied `t`, `n`, `i`, interpolation coefficients, `secret_share`, and `verification_shares` and constructs a "trusted" `ThresholdKeys` whose fields are never checked for mutual consistency — in particular it never verifies that `secret_share * G == verification_shares[i]` nor that the key material corresponds to any completed DKG. The resulting object is then used by the privileged signing path (`view()`, `sign()`, `complete()`, `group_key()` as the deposit/validator identity).

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses all key fields directly from the byte stream and calls `ThresholdKeys::new` (lines 349-391). `new` validates only:

- `verification_shares.len() == n` and each key ≤ `n` (lines 355-365)
- `Constant` interpolation only when `t == n` (lines 367-374)

It then computes `group_key` as the interpolated sum of `verification_shares[1..=t]` (lines 376-378) and stores the attacker-supplied `secret_share` untouched. There is no check that:

- `C::generator() * secret_share == verification_shares[i]` — the holder's own share is consistent with its claimed public verification share;
- the `verification_shares` lie on a polynomial consistent with `secret_share`;
- the object corresponds to any real PedPoP/MuSig DKG output (the `context`, PoKs, and commitment messages that authenticate real key generation in `crypto/dkg/pedpop/src/lib.rs` are entirely absent from this serialization).

Additionally, `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101) enforces canonical encoding but permits the identity point, so an attacker can place arbitrary — including trivially-structured — points into `verification_shares` (e.g., `verification_shares[1] = λ₁⁻¹·Y_target`, remaining shares identity) to make `group_key()` equal any chosen point `Y_target`, including the key of an existing validator set or an attacker-controlled key.

### Impact Explanation
Like prototype pollution, the deserialized object violates invariants every downstream consumer assumes hold. `ThresholdKeys::view` (lines 463-533), `sign`, `verify_share`, and `complete` all trust `core.verification_shares`, `core.group_key`, and `core.secret_share` as a consistent DKG product. Consequences:

- Any party that loads attacker-supplied bytes (the scan scope explicitly covers untrusted bytes passed to `ThresholdKeys::read`) obtains a key object whose `group_key()` is fully attacker-determined. If that group key is reported as the multisig/validator address (as `processor/src/key_gen.rs` does via `GeneratedKeysDb`/generated-key reporting), funds sent to it are controlled by whoever chose the shares — i.e., deposits are reported received at an address not spendable by the presumed threshold quorum, only by the attacker.
- The secret share itself is silently replaced: an honest node's own `secret_share` field can be corrupted relative to its `verification_shares[i]`, causing it to emit signature shares that verify (or fail) arbitrarily, corrupting the quorum's signing output while blaming honest participants.

This is a key-share/group-key substitution through a corrupted trusted object — the precise analog of attacker-controlled object state reaching a privileged context.

### Likelihood Explanation
Reachability requires attacker-influenced bytes to reach `ThresholdKeys::read`. The scan rules stipulate this input surface is in scope, and `read` performs all the unchecked field assembly itself. The attack requires no collusion, no timing, and no malicious peer privileges — only the ability to feed crafted bytes to the deserializer (e.g., injected/rolled-back stored key material, cross-session key blobs, or any path where key bytes are not authenticated). Where `read` is only ever used on locally-generated, integrity-protected storage, likelihood drops, but the missing invariant check is a latent correctness/security gap regardless.

### Recommendation
In `ThresholdKeys::new` (or at the end of `read`), enforce:

```rust
if C::generator() * secret_share.deref() != verification_shares[&params.i()] {
  Err(DkgError::InvalidSecretShare)?;
}
```

and reject identity points in `verification_shares`. More fundamentally, serialization of `ThresholdKeys` should be authenticated (e.g., keyed MAC or binding to the DKG transcript/context) so a deserialized object cannot diverge from the DKG output it claims to represent — the pollution-defense equivalent of freezing the prototype.

### Proof of Concept
```rust
// C: some in-scope Ciphersuite, e.g. Ristretto / Secp256k1
let t = 2u16; let n = 2u16; let i = Participant::new(1).unwrap();

// Attacker chooses a target group key they control (or a victim's key)
let attacker_secret = C::random_nonzero_F(&mut rng);
let attacker_key = C::generator() * attacker_secret;

// Included set {1,2}: λ_1 = 2, λ_2 = -1 (Lagrange at 0).
// Set share_1 = λ1^-1 * attacker_key, share_2 = identity -> group_key == attacker_key
let lambda1 = C::F::from(2);
let share1 = attacker_key * lambda1.invert().unwrap();
let share2 = C::G::identity();

let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(t.to_le_bytes());
buf.extend(n.to_le_bytes());
buf.extend(i.to_bytes());
buf.push(1); // Lagrange
// secret_share: arbitrary scalar, NOT consistent with verification_shares[1]
buf.extend(C::random_nonzero_F(&mut rng).to_repr().as_ref());
buf.extend(share1.to_bytes().as_ref());
buf.extend(share2.to_bytes().as_ref());

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
// Succeeds despite the object being internally inconsistent:
// secret_share * G != verification_shares[i], and group_key is attacker-chosen
assert_eq!(keys.group_key(), attacker_key);
```

`ThresholdKeys::new` returns `Ok`, producing a corrupted key object whose `group_key` is entirely attacker-controlled — the polluted object then flows into `view()`/`sign()` as if it were a legitimate DKG output.
