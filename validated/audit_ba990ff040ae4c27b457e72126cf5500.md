### Title
Ambiguous parenthesis-splitting regex in `listSubmodules` lets a crafted `git describe` string corrupt `SubmoduleEntry.path` - (File: `app/src/lib/git/submodule.ts`)

### Summary
`listSubmodules` parses `git submodule status` output with the regex `/^.([^ ]+) (.+) \((.+?)\)$/gm` [1](#0-0) . This regex uses a greedy `(.+)` for the `path` capture group followed by a lazy `(.+?)` for the `describe` (i.e., `git describe`) capture group, both delimited only by the literal substring `" ("` and a trailing `")"` at end-of-line. Because `git describe` output for a submodule's checked-out commit is derived from the submodule's own tag/ref names — which git allows to contain parentheses — an attacker who controls the submodule's tags can produce a describe string that itself contains the exact delimiter sequence `") ("`. When that happens, the regex's greedy backtracking finds the *rightmost* `" ("` in the line (which now falls inside the attacker-crafted describe text rather than between the real path and real describe fields), causing part of the describe string to be absorbed into the `path` capture group and the true describe text to be truncated.

### Finding Description
The parsing loop is: [2](#0-1) 

For an input line of the form `<status><sha> <path> (<describe>)`, if `<describe>` itself contains a `") ("` sequence (e.g. describe = `evil) (fake`, producing the raw line `... foo (evil) (fake)`), the greedy `(.+)` for `path` backtracks from the end of the line and matches the *rightmost* `" ("` boundary it finds — which in this crafted case is the one embedded inside the malicious describe text, not the real boundary after the true path `foo`. The result: `path` is captured as `"foo (evil)"` instead of `"foo"`, and `describe` is captured as `"fake"` instead of the full malicious/true describe string.

Since submodule tag/ref names are allowed by git to contain parentheses (git's `check-ref-format` rules forbid space, `~`, `^`, `:`, `?`, `*`, `[`, `\`, control characters, and a few other patterns, but not `(`/`)`), an attacker who controls a submodule repository (e.g., via a malicious tag pushed to a submodule remote, or a crafted nested/vendored repo) can shape `git describe`'s output to contain this delimiter sequence and thereby corrupt the parsed `path` field of the resulting `SubmoduleEntry`.

### Impact Explanation
The corrupted `SubmoduleEntry.path` value is a string (not a validated filesystem path) that no longer matches the actual on-disk submodule path. Any consumer that uses this `path` to key operations — for example passing it into `resetSubmodulePaths` (`git submodule update --recursive --force -- <paths>`) [3](#0-2)  — would pass a bogus pathspec to git, meaning git would either fail to match anything (a no-op, i.e., a silent failure of the intended reset) or, in git's pathspec matching, could match an unintended path. Concretely, this can undermine the correctness of features that rely on `SubmoduleEntry.path` (e.g., commit-selection scoping or "discard changes to this submodule" style actions) so that they silently operate on the wrong path or silently fail to operate on the intended submodule. I was not able to fully trace every downstream consumer of `SubmoduleEntry.path` in the UI/`git-store.ts` in the time available, so I cannot confirm a concrete data-loss or unintended-publish scenario beyond the pathspec-mismatch effect described.

### Likelihood Explanation
Exploitation requires an attacker who controls a submodule's git history/tags (the submodule remote content) — this is within the stated scope ("attacker controls a cloned/fetched repository"). Crafting a tag name containing `") ("` is trivial since git ref names permit parentheses. However, actually triggering data loss (vs. a parsing curiosity) depends on how `path` is subsequently used and matched against git's pathspec semantics, which is not fully confirmed here.

### Recommendation
Replace the ambiguous regex-based split with a parsing approach that anchors on the known-fixed-width SHA (40 hex chars) and does not rely on searching for `" ("` inside free-form, attacker-influenced describe text — for example, capture the SHA with a strict `[0-9a-f]{40}` pattern, then take everything up to the *last* `" ("`/`")"` pair using an anchored, non-backtracking approach, or better, invoke `git submodule status` per-path / use `git submodule foreach` with `\t`- or NUL-delimited fields that cannot appear in a path, or use `git config -f .gitmodules` to enumerate declared submodule paths independently of the free-text describe suffix and only extract the SHA/status prefix from `git submodule status`.

### Proof of Concept
1. Create a submodule repository and add a tag whose name is `v1.0) (evil` is not directly usable as most git implementations may reject certain characters, but a validated non-space, non-`~^:?*[\` name such as `v1.0)-x-(evil` works within `check-ref-format` rules (parentheses are permitted).
2. Reference this submodule from a parent repo at path `sub`.
3. Run `git submodule status` from the parent repo; observe raw output like:
   ` <sha> sub (v1.0)-x-(evilg1234567)`
4. Apply the regex `/^.([^ ]+) (.+) \((.+?)\)$/gm` (as in `listSubmodules`) to this line and observe that `path` is captured as `sub (v1.0)-x-` (or similar corrupted value) rather than `sub`, while `describe` becomes truncated to `evilg1234567`.
5. This demonstrates the parsed `SubmoduleEntry.path` no longer equals the real on-disk submodule path `sub`, confirming the corruption described above. Note: I was unable to run this test against the live repository in this session; the PoC steps are derived from static analysis of the regex behavior and git's ref-naming rules, not an executed test run.

  }
