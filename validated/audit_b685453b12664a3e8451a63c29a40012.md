## Title
Honest operator can be permanently locked out of reimbursement when `current_round_index` outruns a deposit's pre-signed kickoff rounds - ([File: core/src/database/operator.rs])

### Summary
`get_unused_and_signed_kickoff_connector` selects the first round with an unused, pre-signed kickoff connector for a deposit whose `round_idx` is `>= current_round_index`: [1](#0-0) 

This exactly mirrors the structural pattern behind the reported fei-protocol bug: an entity (a gauge / here, a deposit's assigned kickoff round) has state that is only meaningful relative to a global monotonically-advancing counter (the gauge cycle / here, `current_round_index`), and once the global counter advances past the entity's own tracked range, the entity's required transition becomes permanently unsatisfiable rather than gracefully recoverable.

### Finding Description
Kickoff connectors are pre-signed by verifiers for a deposit at deposit-creation time, for a bounded set of rounds (round 0 through `num_round_txs`). `current_round_index` is a single global counter per operator, stored in `current_round_index` table, and only ever moves forward via `update_current_round_index` (called from `end_round`, `start_first_round`, `send_next_round_tx`): [2](#0-1) 

`handle_finalized_payout` looks up the next unused, signed kickoff connector for the specific deposit via `get_unused_and_signed_kickoff_connector`, and if none exists, returns a hard error: [3](#0-2) 

The subsequent sanity check assumes `current_round_index` can be at most one round behind the deposit's next assignable kickoff round, and calls `end_round` to advance if so: [4](#0-3) 

The equality being relied upon is: *for every payout the operator has fronted, there must exist a deposit-signed round with `round_idx >= current_round_index`*. This binding can break: if the operator continues to service other deposits/withdrawals (each of which independently advances `current_round_index` through `end_round`) while a particular payout's reimbursement has not yet been processed (e.g., it is queued/delayed, or `PayoutCheckerTask` has not caught up), `current_round_index` can advance past the highest round for which *that* deposit has a pre-signed, unused kickoff connector (bounded by `num_round_txs`, the number of rounds signed at deposit setup). Once that happens:
- `get_unused_and_signed_kickoff_connector` returns `None` (WHERE clause `ds.round_idx >= cr.round_idx` matches nothing).
- `handle_finalized_payout` returns `BridgeError::DatabaseError(RowNotFound)`.
- There is no code path that re-signs kickoff connectors for a deposit beyond its originally-provisioned rounds, and no path that lets `current_round_index` move backward.

This is the same failure mode as the referenced report: a value (`storedCycle` for the gauge / the deposit's assignable-round window here) becomes permanently stale relative to a monotonically advancing global counter, and a downstream invariant check (the `assert` in Fei / the `RowNotFound` + "should not be possible" sanity error here) turns that staleness into a hard, unrecoverable failure instead of a recoverable resync.

### Impact Explanation
This falls under the Critical impact category "an honest operator permanently unable to be reimbursed." An operator that has already fronted a withdrawal payout from its own funds can become permanently unable to claim reimbursement for that specific deposit if its round counter races ahead of that deposit's pre-signed kickoff-round window before the reimbursement flow executes. Because `current_round_index` never decreases and there is no mechanism to re-sign/extend kickoff connectors for an already-existing deposit for higher rounds, the lockout is permanent for that deposit, resulting in an operator-funded payout that can never be recovered from the bridge (a bridge fund loss to the operator, analogous to the "honest operator permanently unable to be reimbursed" critical impact category).

### Likelihood Explanation
Likelihood depends on operational timing rather than attacker action directly: it requires the operator's round index to advance by more than `num_round_txs` rounds relative to a specific deposit's window before that deposit's reimbursement is processed. This can be influenced by an unprivileged party who requests many other withdrawals be serviced by the same operator (each completed withdrawal cycle advances rounds), effectively forcing the operator through additional rounds while a target withdrawal's payout-to-kickoff request is delayed (e.g., queued behind other RPC calls, or during high load / restart recovery windows). Because the round-advance and reimbursement-processing paths are decoupled (operated by independent async tasks/RPCs) and the code assumes at most a 1-round drift (`current_round_index.next_round() != round_idx` triggers an "should not be possible" internal error branch), the precondition is plausible under normal operational load without requiring any privileged role, though exact reproduction requires further runtime/timing analysis that could not be completed within the scope of this static review.

### Recommendation
Do not let `current_round_index` for an operator advance past the highest round for which there exist deposits with unprocessed reimbursements and pre-signed kickoff connectors; alternatively, allow re-signing/extending a deposit's kickoff connector pre-signatures for rounds beyond its original window when it detects that the assignable range has been exhausted, and replace the hard `RowNotFound`/"should not be possible" error paths with an explicit recoverable resynchronization path (similar to the fix pattern in the referenced report: keep the per-entity state always included/synced with the global counter's progression instead of asserting a bounded drift).

### Proof of Concept
Not independently reproduced in a running environment within the scope of this review; the finding is derived from static analysis of the monotonic-counter/bounded-pre-signature interaction described above. Reproducing it end-to-end would require: (1) creating a deposit assigned kickoff signatures only through round N (`num_round_txs`), (2) driving the same operator through more than N `end_round` cycles via other deposits before calling `handle_finalized_payout`/`PayoutCheckerTask::run_once` for the original deposit, and (3) confirming that `get_unused_and_signed_kickoff_connector` returns `None`, producing `BridgeError::DatabaseError(RowNotFound)` in `handle_finalized_payout`. This is noted as unverified/uncertain and would need to be confirmed via a Devin session with test-harness/database access.

    pub async fn get_unused_and_signed_kickoff_connector(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(RoundIndex, u32)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, i32)>(
            "WITH current_round AS (
                    SELECT round_idx
                    FROM current_round_index
                    WHERE id = 1
                )
                SELECT
                    ds.round_idx as round_idx,
                    ds.kickoff_idx as kickoff_connector_idx
                FROM deposit_signatures ds
                CROSS JOIN current_round cr
                WHERE ds.deposit_id = $1  -- Parameter for deposit_id
                    AND ds.operator_xonly_pk = $2
                    AND ds.round_idx >= cr.round_idx
                    AND NOT EXISTS (
                        SELECT 1
                        FROM used_kickoff_connectors ukc
                        WHERE ukc.round_idx = ds.round_idx
                        AND ukc.kickoff_connector_idx = ds.kickoff_idx
                    )
                ORDER BY ds.round_idx ASC
                LIMIT 1;",
        )
        .bind(i32::try_from(deposit_id).wrap_err("Failed to convert deposit id to i32")?)
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let result = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        match result {
            Some((round_idx, kickoff_connector_idx)) => Ok(Some((
                RoundIndex::from_index(
                    usize::try_from(round_idx).wrap_err("Failed to convert round idx to u32")?,
                ),
                u32::try_from(kickoff_connector_idx)
                    .wrap_err("Failed to convert kickoff connector idx to u32")?,
            ))),
            None => Ok(None),
        }

    pub async fn get_current_round_index(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
    ) -> Result<RoundIndex, BridgeError> {
        let query =
            sqlx::query_as::<_, (i32,)>("SELECT round_idx FROM current_round_index WHERE id = 1");
        let result = execute_query_with_tx!(self.connection, tx, query, fetch_one)?;
        Ok(RoundIndex::from_index(
            usize::try_from(result.0).wrap_err(BridgeError::IntConversionError)?,
        ))
    }
