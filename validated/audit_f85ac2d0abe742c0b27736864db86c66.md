### Title
Attacker-controlled participant indexes in PedPoP blame handling cause a panic (DoS) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
CVE-2016-7054 is a remotely-triggerable crash: a malformed payload reaching a parser/verification path panics the process. The Serai analog is the PedPoP blame path. `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `Decryption::decrypt_with_proof` index `HashMap`s with `Participant` values supplied as part of a blame accusation. There is no bounds check that `sender`/`recipient` are members of `{1 ..= n}`; any out-of-set index panics via `HashMap`'s `Index` impl, crashing the party (or third-party arbitrator) evaluating the accusation.

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` take `sender: Participant` and `recipient: Participant` from the accusation and pass them to `blame_internal`. `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`, which performs `self.enc_keys[&decryptor]` — a panic on a missing key when `recipient` is not a registered participant. [1](#0-0)  Even when decryption fails earlier, `blame_internal` later does `self.commitments[&sender]`, again panicking if `sender` is outside the DKG set. [2](#0-1) 

`Participant::new` only rejects zero, so `Participant(n + 1)` through `Participant(65535)` are all constructible. [3](#0-2)  Neither `blame` nor `AdditionalBlameMachine::new`/`blame` validates that the accused/acusing indexes are within `1 ..= n`. [4](#0-3) [5](#0-4) 

The reachability is real: to satisfy the `msg.pop.verify` check inside `decrypt_with_proof` for `Commitments`-shaped traffic, an accuser needs a valid Schnorr PoP over `msg.key` — which any actual DKG participant (or anyone relaying an already-published `EncryptedMessage`, since `EncryptedMessage::read` accepts raw bytes) can supply. [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged party submits a blame accusation naming `sender` or `recipient` outside the participant set (e.g., `Participant(n + 1)`). Any honest node — or a non-participating arbitrator using `AdditionalBlameMachine::new` — that evaluates the accusation panics via `HashMap` indexing instead of returning `PedPoPError`. This is a single-message remote crash, the same bug class as CVE-2016-7054 (untrusted input reaches an unchecked path and crashes the process).

### Likelihood Explanation
Blame accusations are, by design, submitted by parties claiming fault — precisely the untrusted-input path. Triggering the panic requires only choosing an index `> n`, which `Participant` permits, plus a `msg`/`proof` shaped like real blame traffic. No threshold collusion, key material, or protocol position is required beyond the ability to file an accusation.

### Recommendation
In `blame_internal` and `Decryption::decrypt_with_proof`, replace `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with `get(...)` returning `PedPoPError`/`DecryptionError` (or identify the accuser as faulty) when the index is unknown, and validate `u16::from(sender) <= n`/`u16::from(recipient) <= n` at the top of `BlameMachine::blame` and `AdditionalBlameMachine::blame`.

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }
