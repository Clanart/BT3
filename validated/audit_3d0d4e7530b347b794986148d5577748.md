## #ValidAnalog

### Title
Hookify PreToolUse/PostToolUse rule evaluation fails open (bypassing blocking security rules) when a malformed tool_input crashes `RuleEngine._extract_field` - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
The external report describes `BufferRouter#resolveQueuedTrades`/`unlockOptions`, which are designed to be non-atomic (one bad item shouldn't abort the whole batch), but a single malformed signature causes `ECDSA.recover` to revert, aborting the entire transaction. The `hookify` plugin in this repo has the analogous design intent: `RuleEngine.evaluate_rules` is supposed to check *all* configured rules (including `action: block` rules meant to stop dangerous bash commands or sensitive file edits) and only "fail open" (allow the tool call) when there is genuinely no matching rule. However, a single malformed field inside `tool_input` can throw an uncaught exception deep inside rule evaluation, which is caught only by the hook's top-level `except Exception`, causing the entire batch of rules — including rules meant to `block` the operation — to be silently skipped, and the tool call to be allowed.

### Finding Description
`RuleEngine._extract_field` builds the field value used for condition matching. For `MultiEdit` it does: [1](#0-0) 
```
elif tool_name == 'MultiEdit':
    if field == 'file_path':
        return tool_input.get('file_path', '')
    elif field in ['new_text', 'content']:
        # Concatenate all edits
        edits = tool_input.get('edits', [])
        return ' '.join(e.get('new_string', '') for e in edits)
```
This assumes every element of `tool_input['edits']` is a dict. If any element is not a dict (e.g. a string, `None`, or a number), `e.get(...)` raises `AttributeError`, which propagates up through `_check_condition` → `_rule_matches` → `evaluate_rules`.

Neither `evaluate_rules` [2](#0-1)  nor `_rule_matches`/`_check_condition` wrap this per-rule evaluation in a try/except, so one malformed rule's field extraction crashes evaluation of **all** rules in the batch — exactly analogous to `_validateSigner`'s single bad signature reverting the whole `resolveQueuedTrades` loop.

The crash is caught only by the hook script's blanket exception handler, which is explicitly documented to fail open: [3](#0-2) 
```
except Exception as e:
    # On any error, allow the operation and log
    error_output = {
        "systemMessage": f"Hookify error: {str(e)}"
    }
    print(json.dumps(error_output), file=sys.stdout)

finally:
    # ALWAYS exit 0 - never block operations due to hook errors
    sys.exit(0)
```
Because the emitted JSON has no `hookSpecificOutput.permissionDecision: "deny"`, Claude Code treats this as an implicit allow, regardless of whether a `conditions`-based `action: block` rule (e.g. blocking edits to `.env`/secrets files, or blocking `rm -rf`) would otherwise have matched. `posttooluse.py` has the identical fail-open pattern. [4](#0-3) 

The remainder of the condition-checking code shows the codebase is aware exceptions here are dangerous (it guards `re.error` in `_regex_match`), but this guard only covers regex compilation, not the field-extraction step feeding it: [5](#0-4) 

### Impact Explanation
An attacker who can influence the shape of a tool call's parameters (e.g., via prompt injection content that steers the model into issuing a `MultiEdit` call whose `edits` array contains malformed entries, or a compromised/malicious MCP server response shaping tool arguments) can cause every configured hookify `block` rule for that tool invocation to be silently bypassed — including rules meant to prevent edits to secrets/`.env` files or other guardrails users configured. This is a concrete hook-bypass/security-control-defeat: a single crafted input defeats the entire rule-checking pass rather than just the malformed rule, letting an otherwise-blocked dangerous file edit or command proceed.

### Likelihood Explanation
Requires the attacker to control or influence the structure of a tool call's arguments so that a hookify rule referencing `new_text`/`content` for `MultiEdit` is active, which is a plugin most users must opt into and configure. It's a reachable but plugin-specific and narrower path than the Buffer Protocol case (any malformed signature), so likelihood is moderate rather than trivial — it depends on the model actually emitting a non-dict entry in `edits`, which is atypical for normal operation but plausible under prompt injection or a misbehaving/malicious MCP tool that shapes arguments before Claude Code executes them.

### Recommendation
Wrap per-rule/per-condition evaluation (`_check_condition`/`_extract_field`) in a narrow try/except that treats extraction failures as "condition not matched" for that specific rule (mirroring the existing `_regex_match` pattern), rather than letting the exception bubble up and be swallowed by the top-level hook handler that defaults to allow. Additionally, validate the type of list elements (e.g., `edits`) before calling `.get()`, and consider making `evaluate_rules` continue evaluating remaining rules with a per-rule try/except, similar to the `try ECDSA.recover ... catch return false` fix applied to `_validateSigner` in the referenced PR, so that a single malformed field cannot cause the entire rule-blocking pass to fail open.

### Proof of Concept
1. Configure a hookify blocking rule, e.g. `.claude/hookify.block-secrets.local.md`:
```
---
name: block-secret-edit
enabled: true
event: file
action: block
conditions:
  - field: new_text
    operator: contains
    pattern: API_KEY
---
Blocked: hardcoded secret detected.
```
2. Cause (via prompt injection or a manipulated tool call) a `MultiEdit` tool invocation whose `tool_input` is:
```json
{
  "tool_name": "MultiEdit",
  "tool_input": {
    "file_path": "config.env",
    "edits": ["not-a-dict-entry"]
  }
}
```
3. `pretooluse.py` invokes `load_rules` + `RuleEngine.evaluate_rules`, which calls `_extract_field('new_text', 'MultiEdit', tool_input, ...)`, which executes `e.get('new_string', '')` on the string `"not-a-dict-entry"`, raising `AttributeError: 'str' object has no attribute 'get'`.
4. The exception propagates to `pretooluse.py`'s outer `except Exception`, which prints a `systemMessage` only (no `permissionDecision: deny`) and `sys.exit(0)`.
5. Claude Code treats this as an allowed operation — the `block-secret-edit` rule that should have blocked the edit containing `API_KEY` never gets evaluated, and the edit proceeds despite the configured guardrail.

```python
    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)
```

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
```
