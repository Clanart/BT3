### Title
Regex Denial of Service (ReDoS) via the `=~` "Matches" query operator in `tx_search`/`block_search`/`Subscribe` - ([File: sei-tendermint/internal/pubsub/query/query.go])

### Summary
The CometBFT query language exposed by the public JSON-RPC endpoints `tx_search`, `block_search`, and `subscribe` supports a `=~` "matches" operator whose argument is compiled as a Go regular expression directly from the attacker-supplied query string and evaluated against attacker-influenceable event-attribute values, with no complexity bound or per-match timeout. This is the same bug class as CVE-2022-35142 (Raneto DoS via a crafted `Search` payload): unsanitized user input is fed straight into a pattern-matching engine that can be driven into catastrophic backtracking.

### Finding Description
The query grammar parser accepts a `TMatches` (`=~`) operator whose argument is an arbitrary string taken verbatim from the request: [1](#0-0) 

That raw string is compiled and executed as a Go regexp with no validation, size limit, or complexity check, both in the live pub/sub event matcher used by `subscribe`: [2](#0-1) 

and in the KV tx/block indexer scan used by `tx_search`/`block_search`: [3](#0-2) 

The only existing guard on this path is a maximum *query string length* check before parsing: [4](#0-3) 
and a scan-entry budget (`lease.Visit(1)`) that charges one unit per KV entry visited, regardless of how expensive matching each candidate value is: [5](#0-4) 

Neither of these bounds the CPU time of a single `regexp.MatchString` call. A short, length-limited pattern such as `(a+)+$` or `(a|a)*b` exhibits exponential-time behavior in Go's `regexp` engine relative to input length when matched against a non-matching long string. Because `eventValue` originates from indexed transaction/block event attributes (module event data, which can include attacker-influenced strings such as memo fields, wasm event attributes, or other message data), an attacker can:
1. Submit one or more ordinary transactions that cause an indexed event attribute to contain a long, crafted string (padding under existing tx/attribute size limits).
2. Issue a `tx_search`/`block_search`/`subscribe` RPC request with a query like `some.attr =~ '(a+)+$'` targeting that indexed tag.

Each matching candidate entry the scan visits then pays the exponential regex cost, while the scan-budget mechanism only counts "one visit" per entry — it does not account for the actual CPU consumed evaluating the regex, so the budget is exhausted in count but not in wall-clock cost, and a single high-cardinality tag with attacker-supplied long values can consume disproportionate CPU on the serving node before the context-cancellation check is reached.

### Impact Explanation
This is reachable by any unprivileged public JSON-RPC client (no auth required for `tx_search`/`block_search`/`subscribe` on a default-configuration full node or RPC node) and requires only ordinary, low-cost transactions plus a crafted query string — matching the CWE-1333/ReDoS class of the referenced Raneto advisory. A successful attack can pin a CPU core on the serving RPC node for an extended period per request, and repeated/concurrent requests can exhaust available RPC-serving goroutines/CPU, causing a crash or effective denial of service of the default-configuration RPC node's query surface, satisfying the "crash of default-configuration RPC nodes" impact bar.

### Likelihood Explanation
High likelihood: the operator is part of the default, undocumented-as-restricted query grammar, requires no special permissions, and the only mitigations present (max query length, per-entry KV scan budget, and a periodic `ctx.Done()` check between iterations) do not bound the cost of a single regex evaluation. An attacker only needs the ability to submit ordinary transactions (to seed a long attacker-controlled indexed attribute value) and to call the public RPC search/subscribe endpoints — both are unprivileged capabilities.

### Recommendation
- Reject or heavily restrict the `=~` operator on public RPC endpoints, or
- Compile candidate regexes with a hard input-length cap and use a linear-time regex engine mode, or
- Wrap each `regexp.MatchString` call with a strict, enforced CPU/time budget (not just a periodic context check) and charge the scan-budget lease proportionally to `len(eventValue)` (or a fixed high cost) for `TMatches` conditions rather than a flat 1 unit, so pathological patterns/values cannot bypass the existing `MaxSearchScanBudget` safety net.

### Proof of Concept
1. Submit a transaction (or several) whose module emits an indexed event attribute (e.g., a memo-derived or wasm event attribute) containing a long string of a benign repeated character, e.g. `"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaX"` (X breaks the match so the regexp engine must fully backtrack).
2. Call `tx_search` (or `block_search`/`subscribe`) with a query such as:
   `some.attr =~ '(a+)+$'`
3. The KV indexer's `TMatches` branch (`sei-tendermint/internal/state/indexer/block/kv/kv.go:729`) or the live pubsub matcher (`sei-tendermint/internal/pubsub/query/query.go:222`) compiles and evaluates this pattern against the long non-matching string, triggering exponential backtracking and pinning a CPU core for a duration disproportionate to the small request size, repeatable to exhaust RPC node CPU.

Note: exact catastrophic-backtracking behavior depends on the Go regexp engine version and pattern chosen; the root cause — unbounded, user-controlled regex compilation/evaluation with no complexity or time limit — is confirmed directly from the cited source, though I was not able to execute the PoC in this environment to measure exact wall-clock amplification.
