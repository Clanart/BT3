## Finding: Valid

### Title
Missing `--` argument separator in git push allows attacker-controlled branch/tag names to be parsed as git options - (File: app/src/lib/git/push.ts)

### Summary
`push()` builds the `git push` argument vector by directly concatenating `remote.name`, the `localBranch`/`remoteBranch` pair, and `tagsToPush` as bare positional arguments, with no `--` end-of-options marker separating them from git's own flags.

### Finding Description
The argument array is constructed as: [1](#0-0) 

`remote.name`, `localBranch`, `remoteBranch`, and every entry in `tagsToPush` are appended directly after `push` with no `--` separator before them. Branch and tag names are ref names that originate from repository content — a cloned or fetched repository controlled by an attacker can contain ref files (loose refs or `packed-refs`) whose names begin with `-` or `--` (e.g. `--upload-pack=...`, `-o`, `--force`). Git's ref-creation path (`check-ref-format`) normally rejects such names when a user creates them locally, but a maliciously crafted repository can ship refs directly on disk without going through that validation, and GitHub Desktop reads/lists these refs and later feeds the raw string into `push()` as `localBranch`/`remoteBranch`/`tagsToPush`. Because there is no `--` before the operand list, git's own argument parser will interpret such a string as an option rather than as the positional branch/tag operand, potentially changing the command's behavior (e.g. injecting flags that alter what is transferred, or targeting `--upload-pack`/`--receive-pack`-style option injection depending on the exact flag accepted by `git push`).

`progressCallback` itself is not the sink — it only receives already-computed progress metadata (`remote.name`, `localBranch`) for UI display and does not touch argv construction; the actual injection point is the `args` array built above, immediately before `git(args, repository.path, 'push', opts)` is invoked. [2](#0-1) 

### Impact Explanation
If an attacker can get a victim to clone/fetch a repository containing crafted ref names, or push tags with crafted names that reach `tagsToPush`, and the victim then performs a push operation in GitHub Desktop, git may parse the attacker-chosen string as a command-line option instead of a ref name. Depending on which option string is smuggled, this could alter push behavior unexpectedly (data corruption of what's pushed) or worse, depending on which git flags are reachable via this argument position.

### Likelihood Explanation
Exploitability depends on (a) GitHub Desktop actually surfacing such maliciously-named refs to the user as selectable branches/tags without prior validation, and (b) `git push` accepting an option in that specific argument slot that has a meaningful/dangerous effect. I was not able to fully verify within the available tool budget whether upstream code (e.g. in `git-store.ts`, `dispatcher.ts`) sanitizes/validates branch and tag names before calling `push()`, or whether the underlying git binary rejects such refs earlier in the pipeline (e.g., during `for-each-ref`/branch listing). This limits confidence in the finding to "plausible but unconfirmed."

### Recommendation
Insert a literal `--` separator into the `args` array immediately before the operand list (remote name, refspec, and tags) in `push()`, e.g. `args.push('--', remote.name, refspec, ...tagsToPush)` (after git's own flags like `--progress`, `--force-with-lease`, `--no-verify`, `--set-upstream`), consistent with the general mitigation pattern used elsewhere in the codebase for other git subcommands that take user-controlled ref/path operands. Additionally, ref/branch/tag names should be validated against `git check-ref-format` semantics before being trusted as operands anywhere in the app.

### Proof of Concept
Not independently verified due to tool-call budget exhaustion before confirming whether ref names beginning with `-`/`--` from a crafted repository actually reach `push()` unfiltered through `git-store.ts`/`dispatcher.ts`. A concrete PoC would require: (1) crafting a repository with a loose ref e.g. `.git/refs/heads/--upload-pack=touch /tmp/pwned;true`, (2) confirming GitHub Desktop lists/selects it as `localBranch` without rejecting the name, and (3) triggering push and observing git's argv parsing behavior via a mocked `git()`/`spawn` call to assert the value is passed as an option, not an operand.
