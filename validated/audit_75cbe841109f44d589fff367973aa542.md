### Title
Line-index-based diff selection can silently commit unintended lines when the working-directory diff shifts between selection and commit - (File: app/src/lib/stores/app-store.ts, app/src/models/diff/diff-selection.ts, app/src/lib/git/apply.ts)

### Summary
GitHub Desktop tracks a user's partial-commit line selection (`DiffSelection`) purely as a set of *absolute line indices* against a specific diff render. When a file's diff changes between the moment the selection was made and the moment the commit patch is built, Desktop only re-validates that the previously selected indices are still "selectable" — it does not verify they still refer to the same logical content. Because `applyPatchToIndex` re-fetches a brand-new diff at commit time and applies the stale index-based selection to it, the resulting patch (and thus the commit) can silently include or exclude different lines than what the user actually reviewed and checked in the UI.

### Finding Description
`DiffSelection` stores "diverging lines" as bare integer indices, with no binding to line content: [1](#0-0) 
`isSelected()` simply checks whether an absolute index is in the diverging-lines set, with no correlation to the actual text at that index: [2](#0-1) 

The store explicitly acknowledges that the diff backing a selection can change before the selection is consumed, and only patches up *selectability*, not *identity*, of previously selected lines: [3](#0-2) 

Critically, the final commit path does not use this "revalidated" diff. `applyPatchToIndex` independently re-fetches a **brand new** diff right before generating the patch: [4](#0-3) 

and `formatPatch` builds the actual patch by walking that freshly-fetched diff's hunks and asking `file.selection.isSelected(absoluteIndex)` for each line — using the (possibly stale) selection object carried over from `IChangesState`: [5](#0-4) 

The commit flow (`_commitIncludedChanges`) hands `state.changesState.workingDirectory.files` (i.e., whatever `WorkingDirectoryFileChange.selection` currently is) straight to `createCommit`, with no re-diff/re-validation step between "the user finished selecting lines" and "the patch is generated from a fresh diff": [6](#0-5) 

If the on-disk file content shifts (lines inserted/removed above the hunk the user was reviewing) between the last diff render Desktop showed the user and the diff fetched at `applyPatchToIndex` time, the hunk's `unifiedDiffStart` offsets and line ordering shift too. Because selection is keyed by raw index rather than by line content/hash, indices that map to "the line the user unchecked" in the old diff can now map to a completely different line in the new diff — and as long as that index is still "selectable" (any addition/deletion line qualifies), Desktop's only safeguard (`withSelectableLines`) will not catch the mismatch.

### Impact Explanation
This produces exactly the "broken invariant" pattern seen in the Nibiru report: a cached, index-based derived state (the user's line selection) is trusted and applied against a different, newer ground-truth state (the fresh diff) without validating that the two states still correspond. The result is silent corruption of what the user commits or pushes — content the user never reviewed/approved can be staged and committed, or content the user explicitly deselected can still be included, with no error and no visual indication in the UI (the commit succeeds normally). This is squarely in-scope per the report's "Valid Impact" criteria ("silent corruption of what the user commits or pushes"), and the attacker primitive is the same class as the original finding: authoritative state (git object/diff) diverges from a cached/derived value (line selection bitmap) that is not re-synced before being acted upon.

### Likelihood Explanation
Exploitation requires a window in which the working tree diff for a file changes after the user makes a partial line selection but before the commit patch is generated — e.g., a build tool, formatter, linter, git filter/smudge process, or any other process that rewrites tracked file content (potentially triggered by content/config supplied in an attacker-controlled cloned/fetched repository) racing with the user's review-then-commit workflow. Given Desktop's asynchronous diff loading (`updateChangesWorkingDirectoryDiff`) and the fact that the final patch always re-fetches the diff independently at commit time (`apply.ts:60`), this race window exists by design rather than as an edge case, making it a realistic (if narrow) window rather than a purely theoretical one. I was not able to fully verify within available context whether git hooks defined in the repository (`post-checkout`/`post-merge`/etc., see `app/src/lib/hooks/get-repo-hooks.ts`) are permitted to run and could be leveraged by a malicious repository to reliably trigger this race; this would need further investigation with direct code/file access to confirm hook execution policy and any additional guards not visible in the indexed context.

### Recommendation
Bind `DiffSelection` state to content rather than raw indices — e.g., key selections by a stable identifier per diff line (such as a hash of hunk header + line content, or line's before/after context) so that a definitively-changed diff invalidates the *specific* diverging lines it affects rather than only pruning indices that are no longer "selectable." Alternatively, before generating the commit patch, compare the diff used to build the current `file.selection` against the diff fetched in `applyPatchToIndex`/`getWorkingDirectoryDiff` (e.g., by hash) and abort/re-prompt the user if they differ, rather than silently applying an index-based selection to a diverged diff.

### Proof of Concept
Conceptual reproduction (exact timing requires a background agent with filesystem/terminal access to script the race, which was not available for this analysis):
1. Open a repository in Desktop containing a tracked file with multiple hunks of changes.
2. In the Changes view, partially select only some lines of a hunk (e.g., accept an innocuous change on line 20, reject a suspicious change on line 5), leveraging the `DiffSelection`/`formatPatch` line-index mechanism shown at [7](#0-6) .
3. Before clicking "Commit", trigger a change to the file that shifts line numbers above the reviewed hunk (e.g., an external process/editor auto-save/format-on-save inserts or removes lines earlier in the file), so the diff Desktop will fetch fresh at commit time (`app/src/lib/git/apply.ts:60`) has different `unifiedDiffStart` offsets than the diff the user reviewed.
4. Click "Commit". `createCommit` → `applyPatchToIndex` fetches the new diff and applies the old, unrevalidated `file.selection` indices to it via `formatPatch`.
5. Inspect the resulting commit: it can contain a line the user explicitly deselected (e.g., the "line 5" change), or omit a line the user selected, without any warning from Desktop.
