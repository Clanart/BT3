### Title
`ReceivedOutput::read` accepts an attacker-supplied offset without verifying it corresponds to the output's `script_pubkey`, desynchronizing the spend key from the output - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Gradle CVE-2023-44387 bug class is "resolve the reference, but apply the attributes of the reference (symlink) rather than the referent (linked file)". In `bitcoin-serai`, a `ReceivedOutput` is a pair (key-derivation `offset`, `TxOut`/`script_pubkey`) where the offset is only meaningful because `p2tr_script_buf(group_key + G*offset) == script_pubkey`. `ReceivedOutput::read` (an API explicitly exposed for untrusted bytes) reads both halves independently and never checks that relationship, so it applies the "permissions" of the serialized wrapper — whatever offset the bytes claim — instead of the offset that actually resolves to the output it carries. The same unchecked pair propagates into `SignableTransaction::multisig`, which signs under `keys.offset(offsets[i])` indexed by position.

### Finding Description
`Scanner::scan_transaction` produces consistent pairs by construction: it looks the script up in `self.scripts` and stores the matching offset alongside the cloned `TxOut` (`networks/bitcoin/src/wallet/mod.rs:199-214`). That invariant is not enforced anywhere else. `ReceivedOutput::read` (`mod.rs:122-133`) performs three independent decodes — `Secp256k1::read_F` for the offset, then `TxOut::consensus_decode` and `OutPoint::consensus_decode` — and returns the object with no consistency check. There is no key context at read time, so the library treats the serialized `offset` field as authoritative even though it is purely an attribute of whoever wrote the bytes, not of the output itself.

Downstream, `SignableTransaction::new` (`send.rs:175-176`) copies `input.offset` into `self.offsets` positionally, and `multisig` (`send.rs:273-285`) derives the per-input signing key as `keys.clone().offset(self.offsets[i])` and compares `p2tr_script_buf(offset.group_key())` against `self.prevouts[i].script_pubkey`. All binding between the spend key and the output therefore relies on a field that `read` never authenticated. A mismatched offset makes `multisig` return `None` — the output can never be assembled into a spendable transaction — while a same-script collision (surjective offsets, `register_offset` at `mod.rs:180-196` deliberately maps requested offset `k` to stored `k+j`) lets a byte-level crafted `ReceivedOutput` carry an offset belonging to a different registered purpose than the one that output was intended for.

### Impact Explanation
Two reachable consequences:

1. **Funds reported received that are not spendable.** An untrusted `ReceivedOutput` encoding whose `offset` does not satisfy `p2tr_script_buf(key + G*offset) == output.script_pubkey` deserializes successfully, is stored/tracked as a spendable output, and then deterministically fails in `SignableTransaction::multisig` (returns `None` at `send.rs:277-278`). The wallet has no recovery path — the UTXO is counted as received but cannot be signed for.

2. **Attribute confusion across registered offsets.** Because offsets are surjective and keyed only by script equality, feeding a valid-looking serialization that pairs a real output with the offset of a *different* registered script (e.g., a change/forward offset vs. an external deposit offset) passes the `multisig` script check only for the script the offset actually resolves to — meaning a crafted record can force the coordinator to attempt spending under the wrong key offset or misclassify the output's purpose. On the in-scope side this manifests as signatures produced for an input under an offset the integrator never intended to bind to that outpoint.

### Likelihood Explanation
Reachability requires untrusted bytes to reach `ReceivedOutput::read`, which is precisely the interface the rules enumerate as attacker-controlled. No cryptographic break is needed — the attacker only writes structurally valid serialized bytes (a canonical scalar, a valid `TxOut`, a valid `OutPoint`), all trivially constructible. The flaw is that `read` treats the `offset` field as self-authenticating metadata of the output, exactly as Gradle treated symlink permissions as the permissions of the resolved file. Severity is Medium: it causes misattribution and unspendable reported funds rather than direct key or signature forgery, since the `multisig` script-equality check prevents signing under a key that doesn't match the prevout script.

### Recommendation
- Make `ReceivedOutput::read` (or a new `read_for_key`/`verify` method) take the scanner's base key and reject any decoded pair where `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset) != output.script_pubkey`, restoring the invariant `scan_transaction` establishes.
- Alternatively store/derive the offset exclusively from the `Scanner`'s `scripts` map at use time rather than trusting the serialized field.
- In `SignableTransaction::multisig`, return an explicit error distinguishing "offset/script mismatch" from "wrong keys" so malformed inputs don't silently abort multisig creation.
