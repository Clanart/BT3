## Analysis

The Lido bug pattern is: a reward/fee calculation reads a *shared, batched* input and attributes the resulting value using stale/incorrect binding of "who did the work" to "who gets paid," causing an amount to be miscomputed relative to the actual unit of work performed. The closest verifiable Hyperbridge analog is in `pallet-consensus-incentives`, where the relayer-reward `FeeHandler::on_executed` hook derives *one* relayer identity from the batch and then pays that single identity for *every* state-machine advance found anywhere in the batch's events — regardless of which individual `ConsensusMessage` actually produced each advance.

### Title
Consensus-incentive rewards for an entire batch are misattributed to the signer of only the first message - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::on_executed` recovers a single relayer account from `messages[0]` only, then iterates over **all** `StateMachineUpdated` events produced by the whole batch (potentially covering several distinct state machines, each backed by a distinct `ConsensusMessage` with its own `signer`) and pays every one of those rewards to that single recovered account.

### Finding Description
`handle_unsigned` is a permissionless, unsigned extrinsic that accepts an arbitrary `Vec<Message>` [1](#0-0) . `Pallet::execute` runs every message through the handler, builds `messages_with_weights` and the aggregate `events` list for the *entire* batch, and hands both to the configured `FeeHandler::on_executed` in one call: [2](#0-1) .

`pallet-consensus-incentives` implements `FeeHandler::on_executed` by:
1. Looking only at `messages.get(0)` to recover a relayer's `sr25519` public key from that single message's embedded signature.
2. Collapsing **every** `StateMachineUpdated` event across the whole batch into a `BTreeMap<StateMachineId, u64>` of highest heights.
3. Paying the reward for **every** state machine in that map to the one relayer account recovered in step 1. [3](#0-2) 

The signer recovered in step 1 is cryptographically tied only to `messages[0]`'s own `consensus_proof`; it has no relationship to the other `ConsensusMessage`s in the batch or to whichever state machines they advance. Because `on_executed` receives the flattened `events` list rather than a per-message mapping, the pallet has no way to know — and does not attempt to check — which specific message produced which `StateMachineUpdated` event before paying out.

The docs describe proofs as public, freely obtainable data ("_These proofs can be generated by anyone, as they are freely provided by its connected chains_") [4](#0-3) , and `pallet_ismp::execute` is reachable by any unsigned caller. An attacker can therefore construct a single `handle_unsigned` batch of `Vec<Message>` where:
- element `0` is any `ConsensusMessage` the attacker can legitimately sign (even one advancing a state machine by a single block, or one with `block_cost == 0`, so it costs them nothing to be `messages[0]`), and
- elements `1..N` are additional, still-unprocessed `ConsensusMessage`s for *other* state machines with larger `latest_height` jumps and correspondingly larger `block_cost` rewards.

Once the batch executes, `StateMachinesCostPerBlock`-funded rewards for *all* of those other state machines get transferred from `TreasuryAccount` to the attacker's account (recovered from message 0), not to whichever key actually signed the higher-value `ConsensusMessage`s. The `LastRewardedHeight` watermark [5](#0-4)  only prevents double-payment for the *same* height range — it does nothing to bind reward payment to the correct signer.

### Impact Explanation
This is direct, unauthorized fund transfer out of `TreasuryAccount`: an attacker who controls only their own signing key can redirect treasury-funded relayer rewards for work embedded in other parties' `ConsensusMessage`s to their own account, simply by choosing batch ordering. `ReputationAsset` minted alongside the payment is likewise misattributed. This matches the bounty's "stealing or loss of funds" / "logic attacks" impact category and requires no malicious relayer, prover, admin, or leaked key — only the ability to submit an unsigned extrinsic with attacker-chosen message ordering, which is permissionless by design.

### Likelihood Explanation
Likelihood is moderate: the attacker needs at least one other still-unprocessed, valid `ConsensusMessage` (for some other state machine) available to include in their batch alongside their own trivial message. Since proofs are explicitly documented as public/freely generatable and `handle_unsigned` batches messages by caller-chosen order rather than any relayer-identity-preserving structure, this is achievable without compromising any other party's keys — it only requires observing/obtaining an unprocessed consensus proof and resubmitting it packaged behind the attacker's own first message.

### Recommendation
`on_executed` should bind each `StateMachineUpdated` reward to the signer of the specific `ConsensusMessage` that produced it, not to `messages[0]`'s signer applied over the whole event set. Concretely: iterate `messages`, recover a relayer identity per `Message::Consensus` entry, and only apply that identity's reward to the state machine height(s) that specific message's processing produced (e.g., by correlating message index/`state_machine_id` with the resulting event, not by flattening events across the whole batch first).

### Proof of Concept
1. Attacker holds their own signing key `K_attacker` and constructs `ConsensusMessage_0` — any proof they can legitimately sign, advancing state machine `A` by a minimal span (or costing `0` if `block_cost` is unset/small).
2. Attacker obtains `ConsensusMessage_1` for state machine `B`, a genuine, not-yet-processed proof (publicly available per protocol design) that was intended to be submitted/rewarded to relayer `K_honest`, advancing `B`'s height by a large span with a high configured `cost_per_block`.
3. Attacker submits `handle_unsigned(messages = [ConsensusMessage_0, ConsensusMessage_1])`.
4. `Pallet::execute` processes both messages, producing `StateMachineUpdated` events for both `A` and `B`, and calls `FeeHandler::on_executed(messages, events)` [2](#0-1) .
5. `on_executed` recovers `K_attacker` from `messages[0]` only, then pays the treasury-funded reward for **both** `A`'s and `B`'s height advances to `K_attacker` [6](#0-5) , even though `K_honest` — not `K_attacker` — is the one whose signature authenticates `ConsensusMessage_1`.
6. `K_honest` receives nothing for state machine `B`, despite having (or someone else having) produced the valid proof; `K_attacker` walks away with both rewards.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
