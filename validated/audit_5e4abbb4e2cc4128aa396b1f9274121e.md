Confirmed root cause chain: `CreateDenom(address)` deterministically derives the bank denom from the ERC20 contract's hex address (referenced by `types.CreateDenom` used throughout `x/erc20/keeper/msg_server.go` and `x/erc20/keeper/proposals.go`), and `registerERC20` only refuses registration when `IsERC20Registered` is currently true [1](#0-0) . Once a token pair is deleted, all three indices (`ERC20Map`, `DenomMap`, allowances) are wiped [2](#0-1) , clearing the way for the exact same address/denom to be re-registered later with a completely different contract.

### Title
Selfdestruct of a native ERC20 token-pair contract permanently orphans its bank-coin backing while leaving circulating supply spendable, and the freed address/denom can later be resurrected with unrelated collateral - (File: x/erc20/keeper/msg_server.go, x/erc20/keeper/token_pairs.go, x/vm/keeper/statedb.go)

### Summary
When a native ERC20 token pair's underlying contract self-destructs, `x/vm`'s `DeleteAccount` wipes the contract's balance, storage, and code to zero [3](#0-2) . The `x/erc20` module detects this lazily — only when a user calls `ConvertERC20`/`ConvertCoin` — and reacts by silently deleting the token pair mapping [4](#0-3) [5](#0-4) . This is the same class of bug as the reported `TimeLockUpgrade.sol`/`SetToken` issue: the module hard-binds economic claims (bank coins already minted 1:1 against escrowed ERC20 balance) to a specific contract address, and when that address is invalidated by an "upgrade" (here, a selfdestruct), the peg is severed with no reconciliation of already-issued claims, and — because the address/denom mapping is fully freed — the same denom string can later be **resurrected** and rebound to an entirely different, attacker-controlled contract.

### Finding Description
1. A native ERC20 pair is registered permissionlessly via `RegisterERC20`/`registerERC20`, deriving `pair.Denom` deterministically from the contract's address [6](#0-5) .
2. Users call `ConvertERC20`, escrowing ERC20 tokens into the module account and minting bank coins 1:1 via `bankKeeper.MintCoins` [7](#0-6) . These bank coins are ordinary, freely transferable Cosmos SDK coins with no linkage back to the token-pair state other than the shared denom string.
3. The contract deployer (an unprivileged, external actor, e.g. "Bob" in the original report) self-destructs the contract. `DeleteAccount` clears the contract's balance (including whatever the erc20 module had escrowed inside that contract's own storage/balance), code, and storage entirely [8](#0-7) .
4. The next time any user calls `ConvertERC20` or `ConvertCoin` for that pair, the keeper detects `acc == nil || !acc.HasCodeHash()` and calls `DeleteTokenPair`, which removes the `ERC20Map`, `DenomMap`, and allowance entries, then returns success (`nil, nil`) without adjusting bank supply [4](#0-3) [2](#0-1) .
5. Outstanding bank-coin balances of that denom held by users **are never burned or reconciled**, even though their backing (the escrowed ERC20 balance behind them) was irreversibly destroyed by the selfdestruct. The 1:1 invariant between escrowed ERC20 balance and circulating denom supply, which the code elsewhere explicitly checks and enforces during conversions (`types.ErrBalanceInvariance` checks in `convertERC20IntoCoinsForNativeToken`/`ConvertCoinNativeERC20`) [9](#0-8) [10](#0-9) , is silently abandoned once the pair is deleted, permanently orphaning any already-minted supply as fully transferable, uncollateralized value.
6. Because `IsERC20Registered`/`DenomMap` are cleared by `DeleteTokenPair`, the exact same contract address (and thus the exact same `CreateDenom`-derived denom string) becomes eligible for `RegisterERC20` again [11](#0-10) . Using `CREATE2`, an attacker can redeploy a different, malicious contract at the identical address and re-register it as the token pair for the same denom, resurrecting the mapping between old, still-circulating bank-coin supply and a completely unrelated/attacker-controlled ERC20 contract.

### Impact Explanation
This breaks the core `x/erc20` invariant that native-coin supply for a token pair must remain 1:1 backed by the corresponding escrowed ERC20 balance — an accounting-corruption/duplication scenario explicitly called out as Critical in scope ("unauthorized minting, burning, duplication, resurrection, or irreversible accounting corruption of spendable user value ... token-pair-backed balances"). Concretely:
- Any coin balance already converted before the selfdestruct becomes permanently uncollateralized yet fully spendable/transferable (including via IBC), i.e., value duplicated out of thin air relative to the destroyed backing.
- After resurrection with a new contract at the same address, the attacker controls whether/how much backing exists for the still-circulating old supply, letting them selectively honor or repudiate `ConvertCoin` redemptions — enabling theft/freezing of victim funds and creating a state where two independently-registered pairs' user-facing tokens are indistinguishable at the bank-coin layer.

### Likelihood Explanation
Reachable entirely by unprivileged users: registration is permissionless when `PermissionlessRegistration` is enabled [12](#0-11) ; deploying a self-destructing contract, converting funds, then triggering the selfdestruct, and later redeploying at the same address via `CREATE2` are all standard EVM operations requiring no special privilege, matching the ordinary "unprivileged trigger" bar for this scan.

### Recommendation
- Short term: When a token pair is deleted due to a selfdestructed/missing contract, do not merely delete the mapping — halt further `ConvertCoin` operations against that denom (mark disabled rather than fully removed) and/or burn/track the outstanding circulating supply so it cannot be silently re-bound to a different contract later. Never allow `RegisterERC20` to reuse a previously-deleted contract address/denom pairing.
- Long term: Track, per token pair, the invariant "circulating denom supply == escrowed ERC20 balance" as a persistent, verifiable module invariant, and design an explicit migration/deprecation flow (analogous to what the original report recommends) so that address-losing events like selfdestruct don't silently sever backing for already-issued claims.

### Proof of Concept
1. Deploy `MaliciousToken` (an ERC20 with a `selfdestruct`-capable admin function or a proxy that can be voided), register it via `MsgRegisterERC20` (permissionless).
2. Victim(s) call `MsgConvertERC20` to convert their MaliciousToken balance into bank coin `erc20/0x...` — module now escrows N tokens in `types.ModuleAddress`'s balance on the contract, and N coins are in circulation.
3. Attacker calls the contract's selfdestruct path; `DeleteAccount` zeroes the contract's balance/storage/code [8](#0-7) .
4. Attacker (or anyone) issues any `MsgConvertCoin`/`MsgConvertERC20` referencing the pair; keeper observes `acc == nil` and calls `DeleteTokenPair`, silently discarding the mapping while the N coins already held by the victim remain fully valid, transferable bank coins with zero remaining collateral [5](#0-4) .
5. Attacker redeploys a new contract via `CREATE2` at the identical address and calls `MsgRegisterERC20` again — succeeds because `IsERC20Registered` was cleared — binding the same `erc20/0x...` denom to unrelated attacker-controlled logic, from which point the attacker decides whether/whom to honor `ConvertCoin` redemption requests for the victim's outstanding coin balance.

// RegisterERC20 creates a Cosmos coin and registers the token pair between the

func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil

// DeleteAccount handles contract's suicide call:
// - clear balance
// - remove code
// - remove states
// - remove the code hash
// - remove auth account
func (k *Keeper) DeleteAccount(ctx sdk.Context, addr common.Address) error {
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	acct := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	if acct == nil {
		return nil
	}

	// NOTE: only Ethereum contracts can be self-destructed
	if !k.IsContract(ctx, addr) {
		return errors.New("only smart contracts can be self-destructed")
	}

	// set account to a base account to set the whole balance as spendable
	baseAccount := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	k.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(cosmosAddr, baseAccount.GetPubKey(), baseAccount.GetAccountNumber(), baseAccount.GetSequence()))

	// clear balance
	if err := k.SetBalance(ctx, addr, new(uint256.Int)); err != nil {
		return err
	}

	var keys []common.Hash

	// clear storage
	k.ForEachStorage(ctx, addr, func(key, _ common.Hash) bool {
		keys = append(keys, key)
		return true
	})

	for _, key := range keys {
		k.DeleteState(ctx, addr, key)
	}

	// clear code hash
	k.DeleteCodeHash(ctx, addr)

	// remove auth account
	k.accountKeeper.RemoveAccount(ctx, acct)

	k.Logger(ctx).Debug(
		"account suicided",
		"ethereum-address", addr.Hex(),
		"cosmos-address", cosmosAddr.String(),
	)

	return nil
}
