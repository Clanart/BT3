### Title
PedPoP blame proof leaks the ECDH key for a message whose proof-of-possession was never verified, enabling disclosure of another participant's encrypted share - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
The PedPoP encryption layer includes a Schnorr proof-of-possession (`pop`) on every `EncryptedMessage` specifically to stop the following attack: Eve copies Alice's per-message encryption key `X` into her own message to Bob; Bob's decryption fails, and Bob publishes a blame proof that reveals `bX` — the ECDH key shared with Alice's message — thereby decrypting Alice's secret share to Bob. The code comments and spec describe this exact side channel.

The defense is incomplete: in `KeyMachine::calculate_share`, the message's PoP is only *queued* into the `BatchVerifier` (via `Encryption::decrypt` → `pop.batch_verify`), while the `EncryptionKeyProof` — which contains the ECDH shared key plus a DLEq binding it to the victim's registered encryption key — is returned immediately. If the (garbage) decrypted bytes fail `C::F::from_repr`, `calculate_share` returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` *before* `batch.verify_with_vartime_blame()` ever runs, so the PoP is never checked. The victim then publishes this blame proof, disclosing the ECDH key for a `msg.key` the sender never proved possession of.

### Finding Description
- `Encryption::decrypt` computes `key = ecdh(enc_key, msg.key)` and returns `(msg.msg, EncryptionKeyProof { key, dleq })` unconditionally; the PoP is only batch-queued (`crypto/dkg/pedpop/src/encryption.rs:479-500`). [1](#0-0) 
- `calculate_share` uses the decrypted bytes immediately and early-returns `InvalidShare` with `blame: Some(blame)` on non-canonical scalar, before `batch.verify_with_vartime_blame()` at line 493 (`crypto/dkg/pedpop/src/lib.rs:476-499`). [2](#0-1) 
- The attack this defeats is explicitly documented in the code (`crypto/dkg/pedpop/src/encryption.rs:83-90`) and in `spec/cryptography/Distributed Key Generation.md:28-35`. [3](#0-2) [4](#0-3) 
- Although `BlameMachine::blame`/`decrypt_with_proof` does verify the PoP before accepting the proof (`encryption.rs:374-378`), the disclosure happens at publication time: the accuser has already broadcast `EncryptionKeyProof { key = victim_enc_key * msg.key }`. Anyone observing the blame can apply `cipher(context, proof.key)` to Alice's original ciphertext addressed to the victim and recover her secret share. [5](#0-4) 
- Reachability: a DKG participant sends the victim an `EncryptedMessage` whose `key` field is copied from another (honest) participant's per-message key and whose `msg` is attacker-chosen bytes. With overwhelming probability the ChaCha20-decrypted output is not a canonical `C::F`, triggering the early error return. No valid PoP over that key is required to reach it.

### Impact Explanation
Information disclosure of a secret DKG share: the published blame proof reveals the ECDH shared key for an honest participant's `msg.key`, letting any observer decrypt that participant's `EncryptedMessage` to the victim and recover the `SecretShare` — exactly the "massive side effect" the PoP was added to prevent. The malicious sender cannot produce a valid PoP for the copied key, so the intended protection fails only because the blame material is emitted on a code path that precedes PoP verification. Leaked shares reduce the effective confidentiality margin of the produced `ThresholdKeys`.

### Likelihood Explanation
Medium. Requires an active malicious DKG participant who crafts a ciphertext copying an observed honest `msg.key` — a routine capability in the threat model PedPoP is designed for (its entire `BlameMachine` exists for malicious participants). Success is near-deterministic since random plaintext almost never deserializes as a canonical scalar. Exploitation additionally requires the victim's blame proof to be published before being fully verified, which is the normal blame flow (the accuser publishes, the coordinator evaluates via `AdditionalBlameMachine`).

### Recommendation
Do not produce or release `EncryptionKeyProof` until the message's PoP has been verified. Concretely, in `KeyMachine::calculate_share`, defer attaching `blame: Some(...)` until after `batch.verify_with_vartime_blame()` confirms the `BatchId::Decryption(l)` statement; on a deserialization failure, record the candidate blame and only emit it once the batch verification succeeds for that message's PoP. Alternatively, verify `msg.pop` synchronously inside `Encryption::decrypt` before computing/returning the ECDH proof.

### Proof of Concept
1. Participants run PedPoP; honest Alice encrypts her share to victim Bob under per-message key `X` (public `X` visible in `EncryptedMessage.key`).
2. Malicious Eve constructs `EncryptedMessage { key: X, pop: <any signature>, msg: <arbitrary bytes> }` and sends it to Bob as her share.
3. Bob's `Encryption::decrypt` computes `key = ecdh(bob_enc_key, X)` = the shared key for Alice's message, queues the (invalid) PoP, and decrypts the garbage.
4. `C::F::from_repr` fails → `calculate_share` returns `InvalidShare { participant: Eve, blame: Some(EncryptionKeyProof { key, dleq }) }` without ever verifying Eve's PoP.
5. Bob publishes the blame. Any observer recomputes `cipher::<C>(context, &proof.key)` and decrypts Alice's original `EncryptedMessage` ciphertext, recovering Alice's secret share to Bob — disclosure of an honest party's share material.

**File:** spec/cryptography/Distributed Key Generation.md (L28-35)
```markdown
While key reuse by a participant is considered as them revealing the messages
themselves, and therefore out of scope, there is an attack where a malicious
adversary claims another participant's encryption key. They'll fail to encrypt
their message, and the recipient will issue a blame statement. This blame
statement, intended to reveal the malicious adversary, also reveals the message
by the participant whose keys were co-opted. To resolve this, a
proof-of-possession is also included with encrypted messages, ensuring only
those actually with per-message keys can claim to use them.
```
