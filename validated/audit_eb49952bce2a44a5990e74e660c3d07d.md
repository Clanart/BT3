## Title
Uncontrolled Resource Consumption via Unbounded `max_length` Override in `Offer.from_bech32` - (File: `chia/wallet/trading/offer.py`)

### Summary
`bech32_decode()` in `chia/util/bech32m.py` has a built-in DoS safeguard: a default `max_length: int = 90` parameter that rejects any bech32 string longer than a normal address/offer length before doing any expensive per-character processing. `Offer.from_bech32()` explicitly bypasses this safeguard by calling `bech32_decode(offer_bech32, max_length=len(offer_bech32))`, i.e. it sets the length cap to the length of the attacker-supplied string itself, making the check a no-op.

### Finding Description
`bech32_decode` is defined with a hard length cap intended to bound resource usage: [1](#0-0) 

But `Offer.from_bech32`, the entry point used to parse any offer string a user or offer counterparty supplies, disables that cap entirely: [2](#0-1) 

Once the (now-unbounded) length check passes, `bech32_decode` performs several full linear passes over the entire attacker-controlled string — `any(ord(x) ... for x in bech)`, `bech.lower()`/`bech.upper()` (each allocates a full copy of the string), `all(x in CHARSET for x in bech[pos+1:])` (a Python-level `in` scan against a 32-character string for every input character), and a list comprehension building a `data` list of the same size, followed by `bech32_polymod` iterating over that list again: [3](#0-2) [4](#0-3) 

After that, `convertbits` allocates yet another full-size output list, and the resulting bytes are fed into `try_offer_decompression` → `WalletSpendBundle.from_bytes` / CLVM deserialization — all of this happens *before* any CLVM cost metering (`MAX_BLOCK_COST_CLVM`, `max_tx_clvm_cost`) is ever applied, since those limits only apply once a real `SpendBundle` reaches `MempoolManager.pre_validate_spendbundle`.

This code path is reachable from multiple wallet-facing entry points that accept an untrusted `offer` string, all of which call `Offer.from_bech32` unconditionally before any size/sanity check:
- `WalletRpcApi.take_offer` via `TakeOffer.parsed_offer`: [5](#0-4) [6](#0-5) 
- `WalletRpcApi.check_offer_validity`: [7](#0-6) 
- `GetOfferSummary.parsed_offer`: [8](#0-7) 
- The CLI `take_offer` helper, which reads an arbitrary file or hex/bech32 blob and immediately calls `Offer.from_bech32`: [9](#0-8) 

### Impact Explanation
An offer counterparty (or anyone who can hand a wallet user/service an "offer" string, which is the entire purpose of the offer file format) can craft an oversized bech32 blob (megabytes to gigabytes) that will be decoded with no effective length limit. This forces the receiving wallet to perform multiple full-length string scans, allocate several full-size copies/lists, and attempt CLVM parsing — consuming disproportionate CPU and memory relative to the "advertised" content, before the recipient can even see the offer summary or decide to reject it. On a resource-constrained node (e.g., a service automatically evaluating incoming offers, or a GUI wallet), this can hang or crash the wallet process, denying transaction processing — the CWE-400/770 resource-exhaustion pattern described in the reference advisory.

### Likelihood Explanation
High from a reachability standpoint: any counterparty in a legitimate Chia offer exchange controls the exact string that is passed to `Offer.from_bech32`, and no size limit is enforced anywhere upstream (RPC layer, CLI, or `bech32_decode` itself once the cap is defeated). No signature, spend validity, or special privileges are required to trigger the expensive decode path — only that the wallet owner (or an automated offer-processing service) calls `take_offer`, `check_offer_validity`, or `get_offer_summary` on the malicious string.

### Recommendation
Restore a bounded `max_length` in `Offer.from_bech32` (e.g., a fixed generous cap such as a few hundred KB/MB, consistent with realistic offer sizes) instead of `max_length=len(offer_bech32)`, and reject oversized strings before any per-character processing begins.

### Proof of Concept
1. Construct a bech32m string (prefix `offer1...`) whose data payload is several hundred MB of arbitrary/garbage bytes (checksum failure is fine — the goal is to force full processing before rejection is possible, or a crafted checksum can make it pass longer).
2. Call `Offer.from_bech32(huge_offer_string)` directly, or submit it via the wallet RPC `take_offer` / `check_offer_validity` / `get_offer_summary` endpoints.
3. Observe that `bech32_decode` proceeds to scan/copy/allocate structures proportional to the full attacker-chosen size (no early rejection via `max_length`, since it is set to `len(offer_bech32)`), causing significant CPU time and memory allocation in the wallet process for a single "offer" input.

def bech32_polymod(values: list[int]) -> int:
    """Internal function that computes the Bech32 checksum."""
    generator = [0x3B6A57B2, 0x26508E6D, 0x1EA119FA, 0x3D4233DD, 0x2A1462B3]
    chk = 1
    for value in values:
        top = chk >> 25
        chk = (chk & 0x1FFFFFF) << 5 ^ value
        for i in range(5):
            chk ^= generator[i] if ((top >> i) & 1) else 0
    return chk
```

def bech32_decode(bech: str, max_length: int = 90) -> tuple[str | None, list[int] | None]:
    """Validate a Bech32 string, and determine HRP and data."""
    bech = bech.strip()
    if (any(ord(x) < 33 or ord(x) > 126 for x in bech)) or (bech.lower() != bech and bech.upper() != bech):
        return (None, None)
    bech = bech.lower()
    pos = bech.rfind("1")
    if pos < 1 or pos + 7 > len(bech) or len(bech) > max_length:
        return (None, None)
    if not all(x in CHARSET for x in bech[pos + 1 :]):
        return (None, None)
    hrp = bech[:pos]
    data = [CHARSET.find(x) for x in bech[pos + 1 :]]
    if not bech32_verify_checksum(hrp, data):
        return (None, None)
    return hrp, data[:-6]
```
