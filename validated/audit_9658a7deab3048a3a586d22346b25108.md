### Title
Quoted `event` frontmatter value with leading whitespace silently disables hookify rules for all event filters - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter` strips whitespace from a top-level YAML value *before* stripping surrounding quote characters, so a value like `event: " bash"` ends up stored as `' bash'` (with the internal leading space preserved) instead of `'bash'`. When `load_rules(event=...)` compares this malformed value against the requested event, the comparison `rule.event != 'all' and rule.event != event` is always `True`, so the rule is unconditionally skipped by the `continue` at that point—regardless of whether it is `enabled` and regardless of the requested event ("bash", "file", "stop", etc.)—effectively neutralizing the rule.

### Finding Description
In `extract_frontmatter` (plugins/hookify/core/config_loader.py, lines 136-152), a simple key:value line is parsed as:
```
key, value = line.split(':', 1)
key = key.strip()
value = value.strip()
...
value = value.strip('"').strip("'")
``` [1](#0-0) 

For the line `event: " bash"`, `value` after `.split(':', 1)` is `' " bash"'`. Calling `.strip()` first only removes the *outer* whitespace surrounding the quotes, yielding `'" bash"'`. The subsequent `.strip('"')` removes only the quote characters, exposing the internal leading space and producing the final stored value `' bash'`. This applies to the `event` key exactly the same as every other simple key, so it is not that `event` skips a `.strip()` call the way the question hypothesizes — rather, the *order* of `.strip()` then `.strip('"')` fails to normalize whitespace that is nested inside quotes for any key, including `event`.

That malformed value then flows through `Rule.from_dict` (line 78: `event=frontmatter.get('event', 'all')`) into the `Rule.event` field unmodified. [2](#0-1) 

In `load_rules`, the event filter is:
```
if event:
    if rule.event != 'all' and rule.event != event:
        continue
``` [3](#0-2) 

With `rule.event == ' bash'`, both `' bash' != 'all'` and `' bash' != 'bash'` are `True`, so the rule is always skipped via `continue` for every call to `load_rules(event=...)`, before the `rule.enabled` check is even reached (line 225). The rule file loads successfully (no parse error, `enabled: true` is respected by `load_rule_file`), giving the maintainer a false sense that the rule is active, while it is silently excluded from every event-filtered lookup used by the pretooluse/posttooluse/stop/userpromptsubmit hooks that call `load_rules(event=...)`.

### Impact Explanation
Any hookify rule (including a `action: block` rule meant to prevent dangerous Bash commands, file writes, etc.) can be silently disabled by a single-character whitespace change inside a quoted `event` value in its frontmatter. Because the rule is dropped before enforcement in every hook path (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`, all of which call `load_rules(event=...)`), this constitutes a trust-boundary/security-control bypass: an attacker who can edit or introduce a `.claude/hookify.*.local.md` rule file (e.g., via a malicious repo/plugin content or PR that a user merges) can neutralize a security block rule without triggering any parse warning, since the file is syntactically valid YAML-like frontmatter.

### Likelihood Explanation
Exploitation only requires the ability to edit or supply one hookify rule frontmatter file with `event: " bash"` (or any event with a leading/trailing space inside quotes) instead of `event: bash`. No special privileges are needed beyond the ability to modify/introduce a rule file, which is the same precondition needed to legitimately author hookify rules. The change is subtle (a single leading space inside quotes) and produces no error output, making it highly deniable and easy to slip into a review.

### Recommendation
In `extract_frontmatter`, strip quote characters before stripping whitespace (or strip whitespace again after removing quotes), e.g.:
```python
value = value.strip()
if (value.startswith('"') and value.endswith('"')) or (value.startswith("'") and value.endswith("'")):
    value = value[1:-1]
value = value.strip()
```
Additionally, defensively normalize `event` in `Rule.from_dict` with `.strip()` when read from frontmatter, and consider making `load_rules` log a warning when a rule's `event` doesn't match any known event value, to surface malformed rule files instead of silently dropping them.

### Proof of Concept
Unit test for `plugins/hookify/core/config_loader.py`:
```python
def test_quoted_event_with_leading_space_not_normalized():
    content = '''---
name: block-rm-rf
enabled: true
event: " bash"
action: block
pattern: "rm -rf"
---

Blocked!
'''
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)
    # Bug: rule.event retains internal whitespace instead of == 'bash'
    assert rule.event == 'bash'  # FAILS: actual value is ' bash'
```
Integration test against `load_rules`:
```python
def test_rule_silently_dropped_from_event_filter(tmp_path, monkeypatch):
    rule_dir = tmp_path / '.claude'
    rule_dir.mkdir()
    (rule_dir / 'hookify.block-rm.local.md').write_text('''---
name: block-rm-rf
enabled: true
event: " bash"
action: block
pattern: "rm -rf"
---

Blocked!
''')
    monkeypatch.chdir(tmp_path)
    rules = load_rules(event='bash')
    # Bug: rule is excluded even though it should apply to bash events
    assert len(rules) == 1  # FAILS: rules is empty
```
Both assertions fail on current code, confirming the rule is silently excluded from the `bash` event filter, disabling enforcement.
