### Title
Governance-settable `kip71.gastarget = 0` causes division-by-zero panic in Magma base-fee calculation, halting all consensus nodes - ([File: params/kip71_config.go])

### Summary
The `GasTarget` governance parameter (`kip71.gastarget`) has no lower-bound / non-zero validation anywhere in the governance vote pipeline, unlike its sibling parameters (`kip71.basefeedenominator` explicitly rejects 0, and `kip71.lowerboundbasefee`/`kip71.upperboundbasefee` are cross-checked against each other). A ratified vote setting `GasTarget = 0` causes `KIP71Config.NextMagmaBlockBaseFee` to perform an integer division by zero on `math/big.Int`, which panics in Go, crashing every node that computes the next block's base fee (proposers and validators alike). This is the same bug class as CVE-2024-1298 (UINT32 overflow leading to a division-by-zero causing loss of availability), reached here through a governance-controlled numeric parameter reaching zero rather than firmware S3 resume code.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the delta to the base fee using `gasTarget` as a divisor in two branches: [1](#0-0) [2](#0-1) 

Both branches divide by `gasTarget` (`x.Div(x, new(big.Int).SetUint64(gasTarget))`) with no zero-check, unlike `baseFeeDenominator`, which explicitly falls back to `64` if it is zero: [3](#0-2) 

`GasTarget` is a governance parameter registered with `noopFormatChecker`, meaning any `uint64` value including `0` passes format validation: [4](#0-3) 

The consistency check performed during header verification (`checkConsistency`) does not add any extra bound for `Kip71GasTarget` — it falls into the bucket of parameters that are accepted with "no more checks": [5](#0-4) 

By contrast, `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` do get bespoke consistency checks in the same switch statement: [6](#0-5) 

A vote is cast via the `governance_vote` RPC by a council member (in `none` mode) or the governing node (in `single` mode): [7](#0-6) 

Once ratified at an epoch boundary, `GasTarget=0` becomes part of the effective `ParamSet` and is fed into `KIP71Config.GasTarget` used by `NextMagmaBlockBaseFee`, which is on the block-production/verification hot path (called from `blockchain/block_validator.go`, `blockchain/chain_makers.go`, `blockchain/tx_pool.go`, `node/cn/gasprice/*`, and `work/worker.go`). With `GasTarget=0`, virtually every block's `parentGasUsed` will be `> gasTarget`, forcing the division-by-zero path, causing a Go runtime panic on every node (proposer and all validating nodes) simultaneously.

### Impact Explanation
A panic in `NextMagmaBlockBaseFee` is triggered synchronously in both block preparation (proposer) and block validation (all validators), because base-fee is a required consensus field validated on every header. This causes a chain-wide halt (loss of Availability) affecting the entire network deterministically and reproducibly, matching the CVSS vector of the referenced CVE (`AV:L/AC:L/PR:H/UI:N/S:C/C:N/I:N/A:H` — availability-only, local/privileged trigger with scope change). Here "privileged" maps to a governance council member or the single governing node, which is an in-scope actor archetype (governance parameters).

### Likelihood Explanation
Exploitation requires only a single successful vote-and-ratification cycle for `kip71.gastarget = 0` through the standard governance voting mechanism — no code exploit, memory corruption, or complex crafting is needed, just a plain governance parameter value that passes all existing validation. Given the complete absence of a zero-check (verified against the explicit zero-check present for the sibling `BaseFeeDenominator` parameter), this is a straightforward, deterministic trigger once the vote is ratified.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check), and/or add a defensive zero-check with a safe fallback inside `NextMagmaBlockBaseFee` before dividing by `gasTarget`, consistent with the existing fallback pattern used for `baseFeeDenominator`.

### Proof of Concept
1. As the governing node (single mode) or any council member (none mode), call `governance_vote` with `name="kip71.gastarget"`, `value=0`.
2. Because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` (always returns `true`) and `checkConsistency` performs no additional validation for this parameter, the vote is accepted and, once ratified at the next epoch boundary, becomes the effective `GasTarget`.
3. On the next block after ratification, any node (proposer preparing the header, or any validator verifying it) calls `KIP71Config.NextMagmaBlockBaseFee` with `gasTarget=0`. Since actual `parentGasUsed` will normally exceed `0`, execution takes the `parentGasUsed > gasTarget` branch and executes `y := x.Div(x, new(big.Int).SetUint64(gasTarget))`, i.e., division by the zero-valued `gasTarget`, causing a `runtime panic: division by zero` in every node performing this computation, halting the chain.

Note: I was unable to fully trace the exact call sites in `blockchain/block_validator.go`/`work/worker.go` within this session's tool-call budget (only grep hit counts were retrieved, not the surrounding code), so the precise panic-recovery behavior at each call site (e.g., whether any caller wraps this in a `recover()`) is not fully confirmed. Based on the file names and typical Kaia/klaytn architecture, these are core block-production and block-validation paths without panic recovery for this kind of arithmetic panic.
