### Title
Conflict-marker re-scan mismatch in Copilot merge-conflict reassembly can silently splice AI resolutions into the wrong location - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
The reported bug is a "wrong arithmetic operation causes a value to be silently miscalculated, and downstream consumers trust it without cross-checking." The closest verified Desktop analog is in `reassembleResolvedFile`, which reconstructs the final committed file content by re-scanning the *original* file for conflict-marker lines and splicing in the model's per-hunk resolutions **by positional order**, independent of the count/order that was used to prompt the model. If the conflicted file's non-conflicted regions contain lines that happen to match the marker regexes (attacker-controlled repository content), the second scan can find a different number/order of "conflict blocks" than what Copilot actually resolved, causing a resolution meant for one conflict to be spliced into a different location in the file — silently corrupting what gets written to disk and subsequently committed.

### Finding Description
`reassembleResolvedFile` at [1](#0-0)  walks the raw on-disk file line-by-line and treats any line matching `/^<{7}(?:\s|$)/` as the start of a conflict block, requiring a subsequent line matching `/^={7}$/` and `/^>{7}(?:\s|$)/` to close it: [2](#0-1) 

When a well-formed block is found, it is dropped and replaced with `hunkResolutions[hunkIndex].resolvedContent`, then `hunkIndex` is incremented — i.e., resolutions are matched **purely by the order in which marker patterns are encountered during this second, independent scan**, exactly as documented in the function's own comment: "matched by order, not by line number" [3](#0-2) .

The only safety net is `validateResolutionPaths`, which checks that the *count* of hunks returned by the model matches the *count* of hunks originally extracted from the file by a separate parser (`copilot-conflict-context.ts`) before the prompt was built [4](#0-3) . This guard only validates that the numbers match — it does nothing to guarantee that the *positions* found by the original hunk-extraction pass and the positions found by `reassembleResolvedFile`'s independent re-scan are the same. If the original file (which is attacker-influenced: any branch merged/rebased/cherry-picked by the user can introduce arbitrary content, including lines that are indistinguishable from git conflict markers, e.g. a documentation file discussing merge conflicts, ASCII-art separators of exactly 7 `=` characters, or a file left over from a previous botched/manual conflict resolution with stray marker-like text) causes the two independent scans to disagree on where conflict blocks begin/end while still agreeing on the total *count*, the model's hunk-N resolution can be spliced at a different byte range than the one it was actually written for.

The `resolvedContent` validation in `parseCopilotConflictResolution` only rejects resolutions that themselves still contain `<<<<<<<`/`=======` patterns [5](#0-4)  — it does not, and cannot, validate that the *original file's* marker positions are unambiguous.

### Impact Explanation
This falls squarely under "silent corruption of what the user commits" from the attacker-controlled-repository class. A malicious or booby-trapped repository (via a branch, PR, or file introduced through a merge that a user resolves with Copilot) can cause the reassembled file — the one written to disk and staged for commit — to differ from what the user believes was resolved (what they saw in the reasoning/summary shown by the UI, if any, or simply their expectation of "conflict N resolved as shown"). Because the splice happens silently at the string level with no diff-review step verifying the final byte-for-byte reassembly against the intended positions, a user could commit and push code where unrelated non-conflicted lines were dropped/overwritten, or a resolution meant for one hunk lands in another, without any error being surfaced.

### Likelihood Explanation
Requires a specific but plausible precondition: a file being conflict-resolved via Copilot must contain, in its non-conflicted regions, text lines that coincidentally match the strict `<{7}`/`={7}`/`>{7}` marker regexes. This is not exotic — projects that document Git workflows, contain sample conflict markers in tests/fixtures, or have prior manually-resolved conflicts with leftover marker fragments are realistic occurrences. No local access, admin rights, or social engineering beyond "the user merges/rebases a branch that includes such a file and uses the Copilot conflict-resolution feature" is required — this matches an attacker-controlled fetched/merged repository content scenario.

### Recommendation
Do not re-derive conflict-block boundaries with an independent regex scan at reassembly time. Instead, reuse the exact same hunk boundaries/positions (e.g., line offsets) that were captured when hunks were originally extracted for the prompt (`copilot-conflict-context.ts`), and pass those positions through to `reassembleResolvedFile` so splicing is anchored to verified byte/line ranges rather than being re-derived from regex matching. As a defense-in-depth measure, `validateResolutionPaths` should also validate positional correspondence (e.g., a hash/fingerprint of each original hunk's `oursContent`/`theirsContent`) rather than count alone.

### Proof of Concept
1. Create a repository containing a file `notes.md` with a section (outside of any real Git conflict) that looks like:
   ```
   Example of a conflict marker block:
   <<<<<<< HEAD
   =======
   >>>>>>> feature
   ```
   (a realistic scenario for tutorials/fixtures about Git).
2. Introduce a real merge conflict elsewhere in `notes.md` on a different branch and merge it in Desktop, triggering the Copilot conflict-resolution flow.
3. The original hunk-extraction pass (`copilot-conflict-context.ts`) parses the *real* conflict correctly and prompts the model with one hunk.
4. `reassembleResolvedFile`, re-scanning the raw file independently, encounters the fake, pre-existing marker-like block *first* (before or interleaved with the real conflict, depending on file order) and treats it as `hunkIndex === 0`, splicing the model's real resolution into the fake block location and leaving the actual conflict markers either untouched or misaligned with a shifted `hunkIndex`.
5. The resulting `resolvedContent` is written to disk and staged without any indication to the user that content was misplaced, and is then committed/pushed as-is.

(Note: full validation of this exact interleaving edge case would require exercising `copilot-conflict-context.ts`'s hunk-extraction logic side-by-side with `reassembleResolvedFile`, which the available indexed code did not let me fully trace within this session — the core structural flaw of "two independent, non-position-linked marker scans feeding a splice-by-order operation" is confirmed directly in the cited code.)

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
