### Title
Double-counted recursion depth for `MessageSet` extension parsing causes legitimate nested messages to be rejected - ([File: python/google/protobuf/internal/message_test.py], analog surface: `src/google/protobuf/extension_set_heavy.cc` / `wire_format.cc` C++ MessageSet parsing path)

### Summary
The GMX report describes a value (`swapImpactPoolAmount`) that is already included inside another aggregate (`poolAmount`) but gets added a second time when computing a validation threshold, making a stricter-than-intended check that rejects legitimate operations. The Protobuf C++ implementation has an analogous double-counting defect: when parsing a `MessageSet` extension item, the recursion depth is incremented twice for what should conceptually be a single level of nesting, so a message that is well within the configured recursion limit can be spuriously rejected as "too deeply nested."

### Finding Description
Protobuf's `CodedInputStream` enforces a recursion budget via `IncrementRecursionDepth()` / `DecrementRecursionDepth()` (and the combined `IncrementRecursionDepthAndPushLimit()`), decrementing `recursion_budget_` by one for each nested message/group entered [1](#0-0) . This is the safety invariant: one logical level of nesting should consume exactly one unit of recursion budget, matching the depth a legitimate/trusted schema actually has.

For the `MessageSet` wire format, however, the C++ implementation's own test suite documents that this invariant is violated: `message_set_extension` is double counted for depth in C++, so each layer of `TestMessageSet` extension nesting consumes two recursion-budget units instead of one, forcing the test to use half the depth (`depth = 33` for C++ vs `depth = 50` for other backends) to stay under the same nominal limit [2](#0-1) . This mirrors the GMX pattern precisely: a quantity (`recursion_budget_`) is decremented once by the generic "entering a message" accounting and then decremented again by the `MessageSet`-item-specific accounting, even though both charges represent the *same* logical nesting step — exactly like `swapImpactPoolAmount` being summed once as part of `poolAmount` and then summed again explicitly in `getExpectedMinTokenBalance`.

The consuming-application exposure here is: a public/trusted schema containing `message_set_wire_format = true` extensions, receiving a bounded, well-formed binary payload from an ordinary client through `ParseFrom*`/`MergeFrom*`. No malicious schema, no untrusted generated code — this is standard `MessageSet` usage (used for widely deployed legacy APIs).

### Impact Explanation
The consequence is availability/correctness impact, analogous to GMX's "legal swaps... considered illegal": a legitimately nested `MessageSet`-based message that is well inside the intended, documented recursion limit (default 100) can be rejected with `InvalidProtocolBufferException`/`recursionLimitExceeded` purely because the C++ backend's accounting overcharges the budget by 2x for `MessageSet` extension levels. This causes valid client traffic to be spuriously rejected in only the C++ backend (and any binding using it, e.g. Python's `cpp` implementation), while the same payload parses fine under the pure-Python or Java implementations — a parity/availability bug, not a memory-safety bug.

### Likelihood Explanation
Likelihood is Medium: it only manifests for messages using the `MessageSet` wire format with deep (>~33-50) extension nesting, which is a narrower usage pattern than plain nested messages, but `MessageSet` is still used in real production schemas (e.g., legacy Google APIs), and the double count is self-acknowledged in the codebase's own test comments as a known, unfixed discrepancy between backends rather than a hypothetical.

### Recommendation
In the C++ `MessageSet` parsing path (`extension_set_heavy.cc` / `wire_format.cc`, `ParseMessageSetItemTmpl` and related helpers), ensure only one `IncrementRecursionDepth`/`PushLimit` pair is charged per logical `MessageSet` item — i.e., the recursion-depth decrement that occurs when entering the `MessageSet` item container should not be duplicated by the decrement that occurs when parsing the embedded extension message itself. Align the C++ implementation's depth accounting with the Java/pure-Python implementations so that recursion limits are consistent across all official Protobuf backends for the same wire input.

### Proof of Concept
The existing test in the repository already demonstrates and documents the discrepancy without a fix: it builds a `TestMessageSet` extension chain and shows that the C++ backend must use `depth = 33` while other backends use `depth = 50` to stay under the same recursion limit, with an explicit `TODO` acknowledging the double count [2](#0-1) . Running `testRecisionMessageSet` with `api_implementation.Type() == 'cpp'` and a depth between 34 and 49 would successfully parse under Java/pure-Python but incorrectly raise a recursion-limit `DecodeError` under the C++ backend for the identical logical nesting depth — confirming that legitimate messages are rejected due to the double-counted budget. I was not able to pinpoint the exact duplicated `IncrementRecursionDepth` call sites in `extension_set_heavy.cc`/`wire_format.cc` within the available search iterations; a full reproduction/fix would require tracing `ParseMessageSetItemTmpl` and its caller in the C++ MessageSet parser to locate the second, redundant depth decrement.

inline void CodedInputStream::SetRecursionLimit(int limit) {
  recursion_budget_ += limit - recursion_limit_;
  recursion_limit_ = limit;
}

inline bool CodedInputStream::IncrementRecursionDepth() {
  --recursion_budget_;
  return recursion_budget_ >= 0;
}

inline void CodedInputStream::DecrementRecursionDepth() {
  if (recursion_budget_ < recursion_limit_) ++recursion_budget_;
}

inline void CodedInputStream::UnsafeDecrementRecursionDepth() {
  assert(recursion_budget_ < recursion_limit_);
  ++recursion_budget_;
}
