### Title
Sybil-splitting of vlMGP locks inflates attacker's aggregate `totalBoostFactor` share via `sqrt` concavity, diluting honest referrers' boosted rewardPercentage - (File: rewards/ReferralStorage.sol)

### Summary
`ReferralStorage.updateTotalFactor()` sets a referrer's `factor` to `DSMath.sqrt(vlMGPLockedAmount)` and adds it to the shared `totalBoostFactor` pool, while `_calBoosted()` computes each referrer's boosted share as `BoostPoint * factor / totalBoostFactor` [1](#0-0) [2](#0-1) . Because `sqrt` is concave, splitting a fixed capital `X` across `N` Sybil-registered accounts (each locking `X/N`) yields `N*sqrt(X/N) = sqrt(N*X) > sqrt(X)`, so the attacker's combined contribution to (and share of) `totalBoostFactor` grows with `sqrt(N)` relative to a single honest locker with the same total capital `X`.

### Finding Description
`registerCode()` is fully permissionless — any address can register a unique referral code with no capital or KYC requirement [3](#0-2) . `updateTotalFactor(_account)` is called by `vlMGP` (`_onlyVlMGP`) whenever a user with an active code changes their lock, e.g. via `startUnlock` in `VLMGP.sol` [4](#0-3) , and presumably on lock/relock as well. For any account with `myCode != 0`, it recomputes `factor = sqrt(getUserTotalLocked(_account))` and updates the shared `totalBoostFactor = totalBoostFactor - oldFactor + newFactor` [1](#0-0) .

`_calBoosted(_account) = BoostPoint * factor / totalBoostFactor` [2](#0-1)  is consumed in `trigger()` to compute `refererPercentage`/`refereePercentage`, which directly scale the MGP `rewardAmount` credited to the referrer and referee out of the referee's claimed amount `_amount` [5](#0-4) .

`DSMath.sqrt` is the standard Babylonian integer square root [6](#0-5) , which is strictly concave: for `N>1`, `N * sqrt(X/N) > sqrt(X)`. An attacker who registers `N` distinct EOAs, each calling `registerCode()` (permissionless) and locking `X/N` vlMGP each, causes each account's `factor` to be `sqrt(X/N)`, summing to `sqrt(N)*sqrt(X)` — strictly larger than the `sqrt(X)` a single honest locker of the same total capital `X` would contribute. Since `totalBoostFactor` is shared among ALL referral participants (not just the attacker), this inflates the attacker's aggregate numerator contribution relative to a fixed pool of other honest participants' unchanged factors, i.e. `share = attacker_factor_sum / (totalBoostFactor)` strictly increases with `N` for any positive amount of pre-existing background `totalBoostFactor` contributed by other referrers. This dilutes the `_calBoosted()` percentage available to honest, non-Sybil referrers holding equivalent locked capital, and correspondingly increases the fraction of `_amount` (referee reward) diverted to the Sybil attacker's `rewardAmount` balances via `trigger()`.

No existing check prevents this: `registerCode` has no per-address capital minimum or uniqueness-of-owner restriction, `updateTotalFactor` performs no anti-Sybil check (e.g., no linking of `msg.sender`/EOA clustering, no minimum-lock floor that would make `sqrt` behave linearly), and `_calBoosted` naively divides by the shared pool without normalizing for the number of participating addresses.

### Impact Explanation
This is a theft/dilution of unclaimed yield: honest referrers with vlMGP locked and referral codes see their `_calBoosted()` percentage — and therefore their share of `refererAmount`/`refereeAmount` distributed in `trigger()` — permanently reduced whenever a Sybil actor inflates `totalBoostFactor` through account splitting. Because `totalBoostFactor` is a running, mutually-shared denominator, this affects all current and future referral reward calculations for every registered code holder, not just the attacker's own referees. This matches the Immunefi impact class of "theft of unclaimed yield" from other users, scoped to the referral/boost reward mechanism in `rewards/ReferralStorage.sol`.

### Likelihood Explanation
- Fully permissionless: `registerCode()` has no gating, and vlMGP locking is a standard, unprivileged user action reachable by any EOA [3](#0-2) .
- No flash loan or reentrancy needed; only capital-splitting across N addresses and N separate `lock`/`registerCode` calls, which is cheap (gas cost of N transactions) relative to potential ongoing yield-share gains.
- The effect scales with `sqrt(N)`, so gains are strongest with modest `N` (diminishing returns per additional account), but any `N>1` produces a strict improvement over honesty, making this fully repeatable and always profitable in relative share terms as long as other referrers/lockers exist in the system contributing a nonzero background `totalBoostFactor`.
- The attack requires the attacker's Sybil accounts to actually attract/route referee trigger volume to realize monetary gain, but the boosted-percentage inflation itself is realized purely through capital-splitting + lock/registerCode calls, independent of referee volume.

### Recommendation
Redesign the boost-factor accounting to be Sybil-resistant:
- Cap or normalize `factor` per unique KYC-free identity is not feasible on-chain, so instead consider making the boost function convex-safe: use a floor/minimum lock threshold below which `factor = 0`, and/or use a linear (not square-root) or diminishing-marginal-return curve applied to a single canonical identity's total locked amount rather than per-registered-code account.
- Alternatively, tie `factor` computation to `msg.sender`'s totalLocked across the *entire* protocol identity (already done per account), but require a minimum-code-registration lock size, and rate-limit `updateTotalFactor` recomputation frequency, while also considering merging/whitelisting known-linked addresses is impractical — the more robust fix is to eliminate the concave aggregation exploit by making `totalBoostFactor` contributions additive/linear in locked amount instead of `sqrt`, since square-root aggregation is the direct mathematical root cause of the Sybil advantage.

### Proof of Concept
Foundry test plan:
1. Deploy `ReferralStorage`, `VLMGP` (or a mock exposing `getUserTotalLocked` and calling `updateTotalFactor`), and MGP token.
2. Seed a "background" honest referrer `H` with vlMGP lock `Y` and a registered code so `totalBoostFactor` starts non-zero (`sqrt(Y)`).
3. Case A (single locker): Attacker account `A1` calls `registerCode()`, then locks `X` vlMGP (triggering `updateTotalFactor(A1)`). Record `_calBoosted(A1)`.
4. Reset state (or use a duplicate deployment) — Case B (Sybil split): Deploy `N=10` fresh EOAs, each calls `registerCode()` then locks `X/10` vlMGP, each triggering `updateTotalFactor`. Compute `sum(_calBoosted(A_i) for i in 1..10)`.
5. Assert `sum(_calBoosted split)` > `_calBoosted(A1 single)` for identical total locked capital `X`, holding `H`'s background factor constant across both cases.
6. Extend to `trigger()`: simulate referees under each Sybil code claiming equal aggregate `_amount`, and assert the attacker's combined `refererAmount` collected across the 10 accounts exceeds what a single-account referrer with the same total `X` and same aggregate referee volume would have received — demonstrating measurable dilution of honest referrer `H`'s yield share and inflated extraction by the Sybil attacker.

    function updateTotalFactor(address _account) external override _onlyVlMGP {
        UserInfo storage userInfo = userInfos[_account];
        if (userInfo.myCode == bytes32(0)) return; // user did not activate referral feature
        
        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
        userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt);

        totalBoostFactor += userInfo.factor;
    }
