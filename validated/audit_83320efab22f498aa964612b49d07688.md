## Analog Found

### Title
DoS in `WombatStaking::_sendRewards` due to unrealistic `_minRec` check in `SmartWomConvert::smartConvert()` can block deposit/withdraw/harvest for an entire pool - (File: wombat/WombatStaking.sol, wombat/SmartWomConvert.sol)

### Summary
`WombatStaking::_sendRewards` forwards a protocol-computed WOM fee amount into `SmartWomConvert::smartConvert()`, which internally hardcodes `_minRec` to the *full* input amount even though part of that amount may be routed through an AMM swap that realistically returns less than 1:1 due to slippage/fees. When that happens, the whole reward-processing call reverts, and because this call is embedded (without try/catch) inside the code path shared by `deposit`, `depositLP`, `withdraw`, and `harvest`, an ordinary user's transaction fails for reasons entirely outside their control.

### Finding Description
`_sendRewards` computes a fee slice of harvested WOM (`feeAmount`, not user input) and, when the fee is configured to be converted to mWOM via `smartWomConverter`, calls: [1](#0-0) 

`smartConvert` always requires `convertAmount + amountRec >= _amountIn` because it passes `_amountIn` itself as `_minRec`: [2](#0-1) 

Inside `_convertFor`, whenever `buybackThreshold` triggers a partial swap of WOM→mWOM through the AMM router, the swap output (`amountRec`) is compared with 0 slippage protection at the swap call site, but the *aggregate* result is still checked against the full `_amount` sent in: [3](#0-2) 

Because an AMM swap realistically returns less value than was put in (fees/slippage), `convertAmount + amountRec < _minRec` will be true whenever the buyback branch executes, causing `MinRecNotMatch()` to revert.

This call sits inside `_toMasterWomAndSendReward`, which is invoked from every core user-facing entrypoint of `WombatStaking`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

Since there is no `try/catch` around `_sendRewards`, a revert inside `smartConvert` propagates and reverts `deposit`, `depositLP`, `withdraw`, and `harvest` entirely, for **all** users of that LP pool — not just the caller who triggered the fee.

### Impact Explanation
Whenever market conditions push `currentRatio()` below `buybackThreshold` (i.e., mWOM trades cheap relative to WOM, an ordinary/expected market state, not an admin/oracle manipulation), any call to `deposit`, `withdraw`, or `harvest` on the affected pool that generates a nonzero WOM fee will revert. Because `withdraw()` is on this same reverting path, users are unable to exit their staked LP position through the normal path for as long as this market condition persists. This can last well beyond 24 hours depending on AMM/market conditions, constituting a freeze of user funds until an admin manually intervenes (disabling the fee, changing `smartWomConverter`, or adjusting `ratio`/`buybackThreshold`).

### Likelihood Explanation
This does not require a malicious or privileged actor — it is triggered purely by an unprivileged user calling `deposit`/`withdraw`/`harvest` while the `smartWomConverter` fee is configured and the mWOM/WOM market ratio dips below `buybackThreshold`, a state driven by ordinary price/liquidity fluctuations in the WOM/mWOM pool. Any AMM swap with nonzero fee/slippage will trip the `_minRec` check, making this highly likely to occur in normal operating conditions once the fee/converter is active.

### Recommendation
Do not require the swap leg of `smartConvert` to return at least the full input value. Either drop the `_minRec == _amountIn` requirement in `smartConvert` (using a realistic, quote-based minimum with slippage tolerance) or wrap the `smartConvert` call in `_sendRewards` with a fallback (e.g., on failure, deposit the fee's WOM into `mWom` directly, as already done for the `smartWomConverter == address(0)` branch) so a swap/threshold revert cannot block deposits, withdrawals, or harvesting for the entire pool.

### Proof of Concept
1. Admin sets a fee entry with `isMWOM = true` and configures `smartWomConverter` (`WombatStaking::setFee`/`setBribe`-adjacent admin setup, not itself required to be malicious — this is standard intended configuration).
2. Market conditions cause `SmartWomConvert::currentRatio()` to fall below `buybackThreshold` (normal price fluctuation), so `smartConvert` computes a nonzero `amountToSwap` [8](#0-7) .
3. Any user calls `WombatPoolHelper::withdraw` → `WombatStaking::withdraw` → `_toMasterWomAndSendReward` → `_sendRewards` → `smartConvert(feeAmount, 0)`.
4. The AMM swap of `buybackAmount` returns less than `buybackAmount` due to slippage/fees, so `convertAmount + amountRec < _amountIn` and `_convertFor` reverts with `MinRecNotMatch()` [9](#0-8) .
5. The revert propagates up through `_sendRewards` and `_toMasterWomAndSendReward`, causing the user's `withdraw` (and equally `deposit`/`harvest`) call to fail, blocking all users of that pool from withdrawing until the market ratio recovers or an admin reconfigures the fee/converter.

    // should mainly used by wombat staking upon sending wom
    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
