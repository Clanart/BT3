### Title
Unquoted `$ARGUMENTS` expansion in `ralph-loop.md` enables shell command injection bypassing the `Bash(setup-ralph-loop.sh:*)` allowlist - (File: plugins/ralph-wiggum/commands/ralph-loop.md)

### Summary
The `ralph-loop.md` command template invokes the setup script as `"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" $ARGUMENTS` inside a `!` bash execution block with `$ARGUMENTS` left completely unquoted. Since `$ARGUMENTS` is textually substituted with attacker/user-controlled input before the resulting line is handed to a shell, any shell metacharacters (`$()`, backticks, `;`, `&&`, `|`) in the PROMPT or `--completion-promise` value are interpreted by the shell itself, not by `setup-ralph-loop.sh`'s argument parser — allowing execution of arbitrary commands that were never approved by the `allowed-tools` scoping.

### Finding Description
`plugins/ralph-wiggum/commands/ralph-loop.md` restricts execution via `allowed-tools: ["Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)"]` [1](#0-0) , intending to scope Bash execution to only that script. The command body then builds the actual shell invocation as:

```
"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" $ARGUMENTS
``` [2](#0-1) 

`$ARGUMENTS` here is Claude Code's slash-command argument-substitution token, documented as capturing "All arguments as single string" and expanded textually into the command/prompt before execution, as shown throughout `plugins/plugin-dev/skills/command-development/SKILL.md` (e.g. `Fix issue #$ARGUMENTS` → `Fix issue #123 ...`) [3](#0-2) . Because the substitution happens as plain text replacement and the resulting line is left completely unquoted, the substituted value is re-parsed by the shell that executes the `!` block. If the raw text contains shell metacharacters such as `$(...)`, they are evaluated as command substitution by the shell before `setup-ralph-loop.sh` ever runs. `setup-ralph-loop.sh` itself has no defense against this since its own `while/case` parser [4](#0-3)  never even sees the injected payload — the shell strips/executes it during word-splitting/expansion prior to `argv` being built for the script.

The `allowed-tools: Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)` restriction is a textual prefix match on the command string that Claude is about to run; it does not perform shell-syntax-aware analysis to detect that an embedded `$(...)` will cause the shell to execute an unrelated command as a side effect of expanding the argument list. As long as the literal command text still starts with the whitelisted script path, the permission check passes, even though the actual process the OS will spawn (due to shell expansion) executes attacker-supplied code outside that script.

Exploit flow: an attacker supplies a PROMPT (or `--completion-promise` value) containing `$(touch /tmp/pwned)` — this could reach `/ralph-loop` through any flow where PROMPT text originates from untrusted content (e.g., an autonomous/CI-driven agent that assembles a `/ralph-loop <task from issue text>` invocation from a GitHub issue, PR description, or other repo content). When Claude executes the `!` block, the shell expands `$(touch /tmp/pwned)` prior to invoking `setup-ralph-loop.sh`, running `touch /tmp/pwned` as an arbitrary command — a clear escape from the approved, whitelisted script-only Bash execution.

### Impact Explanation
This breaks the approval-scoped Bash execution invariant: a command explicitly restricted to only `setup-ralph-loop.sh` can be made to execute arbitrary attacker-chosen shell commands (file writes, destructive operations like `rm -rf`, data exfiltration via network utilities, etc.) with the same privileges as the Claude Code session. This matches the "unauthorized command execution / approval/allowlist bypass" impact category, since the whitelisted-tool guarantee is the security control being defeated.

### Likelihood Explanation
Exploitation requires only that the attacker control the text passed as PROMPT/`--completion-promise` to `/ralph-loop`, which is plausible in any workflow where such text originates from external/untrusted sources (issue bodies, PR descriptions, automation scripts that template slash-command invocations from repo content) rather than being typed directly and knowingly by a human operator. No privileged access, leaked credentials, or social engineering of a maintainer is required — only that untrusted text flows into the `$ARGUMENTS` slot. This is straightforward to reproduce and repeatable in any environment running this plugin.

### Recommendation
Quote `$ARGUMENTS` in the bash block (`"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" "$ARGUMENTS"` is still insufficient since it would collapse multi-arg parsing); instead pass individual arguments via positional `$1`/`$2`/etc. with each reference quoted, or have the command template pass the full raw string as a single quoted argument to the script and let the script perform its own robust word-splitting internally, rather than relying on shell word-splitting/expansion of unescaped input. Additionally, `setup-ralph-loop.sh` should not be trusted to receive shell-expanded input — the fix must happen at the template level (`ralph-loop.md`) by preventing shell metacharacter expansion of user-controlled text before it becomes part of the executed command line.

### Proof of Concept
Integration test plan:
1. Set up a Claude Code session with the `ralph-wiggum` plugin loaded, `allowed-tools` restricted exactly as in `ralph-loop.md`.
2. Invoke `/ralph-loop '$(touch /tmp/pwned)'` (or without quotes, since `$ARGUMENTS` is attacker-controlled text regardless of user-side quoting intent) and separately `/ralph-loop '; touch /tmp/pwned2'`.
3. Assert:
   - `/tmp/pwned` and `/tmp/pwned2` do NOT exist after execution (currently they WILL be created, demonstrating the vulnerability).
   - No process other than `setup-ralph-loop.sh` (and its expected children like `date`, `mkdir`, `cat`) was spawned — verifiable via `strace`/process-tree capture during the test.
   - `.claude/ralph-loop.local.md` prompt content reflects the literal attacker string rather than having had a subshell executed.
4. Expected (fixed) result: the payload is treated as literal PROMPT text stored in `.claude/ralph-loop.local.md`, and no `touch` side-effect file is created; expected (current/vulnerable) result: `/tmp/pwned` is created, proving shell metacharacter execution outside the whitelisted script.
