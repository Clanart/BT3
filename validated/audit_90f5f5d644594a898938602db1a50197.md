### Title
Unrefunded native token (`msg.value`) permanently locked in Tron `IntentGatewayV2.placeOrder` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder()` never refunds unspent `msg.value` to the caller, unlike the canonical EVM `IntentGatewayV2.sol` implementation, which explicitly returns any leftover native token at the end of `placeOrder`. This is the same fund-lock pattern described in the external report: a user attaches native currency that is not fully consumed by the contract logic, and it becomes permanently trapped with no automatic or user-triggered recovery path.

### Finding Description
In the reference/mainline contract, `placeOrder` tracks a running `msgValue` counter that is decremented as native tokens are consumed for inputs and solver fees, and any leftover is explicitly returned to `msg.sender` at the end of the function: [1](#0-0) 

The Tron variant of the same contract implements identical accounting logic — computing and decrementing `msgValue` while escrowing inputs and swapping for solver fees via `swapETHForExactTokens{value: msgValue}` — but the function ends immediately after emitting `OrderPlaced` with no refund step at all: [2](#0-1) 

Any of the following common conditions leave native token stranded in the contract with the Tron version:
- The user's order inputs are entirely ERC-20 tokens (no native input) and `order.fees == 0`, but the caller sends `msg.value > 0` (e.g. wallet/UI mismatch, or copying a native-order transaction template).
- `order.fees > 0` and the user overshoots the native amount needed for `swapETHForExactTokens`; the Uniswap V2 router refunds the unused ETH to `msg.sender` of the swap call, which is the `IntentGatewayV2` contract itself (not the original order placer), so the excess accumulates in the contract rather than reaching the user.
- Any generic overpayment on native-input orders (the exact scenario explicitly covered by a Foundry test on the mainline EVM contract) is not covered by an equivalent test or refund path on Tron. [3](#0-2) 

This directly parallels the external report's core broken invariant: funds attached via `msg.value` that are not consumed by the intended token/tranche logic are neither rejected up front nor refunded, resulting in silent fund loss for the caller.

### Impact Explanation
Any unprivileged user who places an order on the Tron `IntentGatewayV2` and sends native token that isn't fully required by the input/fee accounting permanently loses that value — it accumulates in the contract with no automatic refund and (unless a governance-only sweep exists) no user-facing recovery mechanism. This is a direct loss-of-funds bug reachable by any ordinary user through the public `placeOrder` entrypoint, matching the "stealing or loss of funds" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: SDK/wallet tooling that composes native-value batches (as documented for `placementCall`) can easily miscompute the exact `value` needed, and any deviation is silently swallowed by the Tron contract instead of being refunded as the mainline EVM contract does. No malicious actor, relayer, or governance participant is needed — a single honest user transaction with a slightly too-high `msg.value` triggers the loss.

### Recommendation
Port the same trailing refund logic from `evm/src/apps/IntentGatewayV2.sol` (lines 364-368) into the Tron `IntentGatewayV2.placeOrder()`: track the running `msgValue` remainder through both the input-escrow and fee-swap branches (capturing the actual `amounts[0]` consumed by `swapETHForExactTokens` rather than assuming the full value is spent), and return any leftover to `msg.sender` before the function returns. Add a Foundry/Tron test mirroring `testPlaceOrder_ExactNativeToken_NoRefundNeeded`/`overpayment` cases to lock in the invariant.

### Proof of Concept
1. On the Tron deployment, call `IntentGatewayV2.placeOrder(order, graffiti)` with `order.inputs` composed entirely of ERC-20 `TokenInfo` entries (`token != address(0)`) and `order.fees == 0`.
2. Attach `msg.value = 1 ether` (or any nonzero amount) to the call.
3. Observe: the ERC-20 inputs are pulled via `safeTransferFrom` as expected, `order.fees == 0` skips the fee branch entirely, and the function emits `OrderPlaced` and returns — the `1 ether` sent as `msg.value` remains permanently in the contract's balance, never returned to the caller and never credited to any escrow accounting (`_orders[commitment][...]` has no native-token entry for this order since `token == address(0)` never appears in `order.inputs`).
4. Compare against `evm/src/apps/IntentGatewayV2.sol`, where the identical scenario triggers the refund at lines 364-368, returning the full `msg.value` to `msg.sender`.
