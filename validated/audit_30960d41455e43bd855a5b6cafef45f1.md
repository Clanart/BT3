### Title
Cached FROST preprocess seed is set once per context and never refreshed, causing nonce reuse and secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to the L2ECO `inflationMultiplier` initialized to a fixed `1e18` and only updated by an external `rebase` call, `SigningProtocol::preprocess_internal` initializes a `CachedPreprocess` seed only when `CachedPreprocesses::get` returns `None` (`coordinator/src/tributary/signing_protocol.rs:123-135`), then reuses that stored seed on every subsequent call for the same context (`coordinator/src/tributary/signing_protocol.rs:137-145`). The seed deterministically drives `ChaCha20Rng` in `seeded_preprocess`, so the FROST nonces and addendum are identical every time (`crypto/frost/src/sign.rs:121-144`). The cache is a lagging variable: it is written once at first use and is never deleted or re-randomized after `from_cache` consumes it.

### Finding Description
`DkgConfirmer::share` and `DkgConfirmer::complete` both funnel into `share_internal`, which calls `preprocess_internal` again (`coordinator/src/tributary/signing_protocol.rs:288-327`). Because the context is just `(b"DkgConfirmer", attempt)` (`coordinator/src/tributary/signing_protocol.rs:274-277`), all calls within an attempt derive the same `CachedPreprocess` seed. `AlgorithmSignMachine::from_cache` regenerates the identical nonces from that seed (`crypto/frost/src/sign.rs:268-274`), yet the entry is left in the DB rather than cleared after use, contrary to the documented requirement that "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" (`crypto/frost/src/sign.rs:216-220`) and the spec's warning that "reusing preprocesses would enable a third-party to recover your private key share" (`spec/cryptography/FROST.md:51-55`). Each FROST share is `d_i + e_i·ρ_i + λ_i·s_i·c`; two shares issued under the same nonces but with a different signing set or message (different `ρ`/`c`) yield a linear system solvable for `s_i` (and `d_i`,`e_i`), recovering the MuSig private key share. The signature share computation is in `crypto/frost/src/sign.rs` following `sign` (`crypto/frost/src/sign.rs:283-318`).

### Impact Explanation
Reuse of the deterministic seed across two signing invocations for the same `(b"DkgConfirmer", attempt)` context — with any variation in the participating preprocess set or the signed `set_keys_message` — exposes the validator's Ristretto MuSig secret share via standard nonce-reuse linear algebra. That share participates in the validator-set MuSig key that authorizes `set_keys`, so recovery enables forging set-keys signatures. This is key-share recovery, an accepted critical-class impact.

### Likelihood Explanation
The reuse is guaranteed structurally: `share()` followed by `complete()` both reconstruct the machine from the same cached seed (`coordinator/src/tributary/signing_protocol.rs:301,321-326`), and nothing invalidates the DB entry. Whether the second invocation produces an exploitable share depends on the message/preprocess set differing; a participant submitting preprocesses (a reachable input: `read_preprocess` consumes untrusted bytes at `crypto/frost/src/sign.rs:276-281`) influences the binding factors ρ and challenge c, so differing preprocess sets across the two calls is sufficient for recovery of `d_i`/`e_i` and then `s_i`.

### Recommendation
Delete or rotate the `CachedPreprocesses` entry atomically when it is consumed in `preprocess_internal` (`coordinator/src/tributary/signing_protocol.rs:137-145`), so each `from_cache` call uses a fresh seed — the same "refresh on every read/use" fix the external report recommends for `inflationMultiplier`. Alternatively, key the cache by a value bound to the exact signing session (message hash + participant set) so any variation yields a distinct seed.

### Proof of Concept
1. In a DKG confirmation `attempt`, `DkgConfirmer::share(preprocesses_A, key_pair)` runs `preprocess_internal`; `CachedPreprocesses` is empty, so a seed `s` is stored and nonces `(d,e)` are derived (`coordinator/src/tributary/signing_protocol.rs:123-145`; `crypto/frost/src/sign.rs:127-132`). Share `σ_1 = d + e·ρ_A + λ·s_i·c_A` is emitted.
2. `DkgConfirmer::complete(preprocesses_B ≠ preprocesses_A, key_pair, shares)` re-enters `share_internal` → `preprocess_internal`; the cache hit returns the same seed `s`, regenerating the same `(d,e)` (`coordinator/src/tributary/signing_protocol.rs:321-323`).
3. With a different included set/message, the second share is `σ_2 = d + e·ρ_B + λ·s_i·c_B`. The observer solves the two linear equations for `d`, `e`, and the secret share `s_i`, recovering the validator's MuSig key share — precisely the documented consequence of `CachedPreprocess` reuse (`crypto/frost/src/sign.rs:85-92`, `216-220`).
