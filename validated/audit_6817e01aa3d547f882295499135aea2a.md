### Title
Recursive/nested precompile calls cause duplicate application of bank balance-change events to the EVM StateDB, allowing balance desync between `x/bank` and `x/vm` StateDB - (File: `precompiles/common/precompile.go`, `precompiles/common/balance_handler.go`)

### Summary
This is the direct Cosmos EVM analog of the `SnapshotERC20Guild` bug: a "child" execution context (a nested precompile call) commits state changes that the enclosing "parent" context is not aware were already reflected, so the parent re-applies logic based on stale bookkeeping. In `SnapshotERC20Guild`, the parent contract checked `votingPower` without knowledge of the child's snapshot. Here, an outer precompile invocation's `BalanceHandler` window (`prevEventsLen`) does not account for the fact that a nested/recursive precompile call already consumed and applied a sub-range of the same event log to the `StateDB`, so the outer handler re-processes (and re-applies) those same bank events a second time.

### Finding Description
Each stateful precompile call runs through `Precompile.runNativeAction` in `precompiles/common/precompile.go`: [1](#0-0) 

For every precompile invocation, a fresh `BalanceHandler` is created and `BeforeBalanceChange(ctx)` records `prevEventsLen = len(ctx.EventManager().Events())` at the current position in the (persistent, cache-context) event log: [2](#0-1) 

After `action(ctx)` runs, `AfterBalanceChange` replays `events[prevEventsLen:]` and applies `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events directly onto the `StateDB` via `AddBalance`/`SubBalance`: [3](#0-2) 

The problem is that `ctx.EventManager()` is shared/threaded through nested EVM calls that re-enter the precompile dispatch path (e.g., a contract calling precompile A, which internally triggers another EVM call into precompile B, or a debug/callback precompile recursing into itself). When a nested precompile call occurs *inside* `action(ctx)`:
1. The nested call creates its own `BalanceHandler`, records its own `prevEventsLen` (a later offset), executes, and applies `events[nestedPrevEventsLen:]` to `StateDB` — crediting/debiting balances for that nested bank operation.
2. Control returns to the outer call. The outer `action(ctx)` continues and eventually returns.
3. The outer's `AfterBalanceChange` then replays `events[outerPrevEventsLen:]`, which **still includes the events already consumed and applied by the nested call**, because the outer handler has no way to know that a portion of that range was already drained by an inner handler.
4. As a result, the same `CoinSpent`/`CoinReceived` events get applied to `StateDB.AddBalance`/`SubBalance` twice — once by the nested handler, once again by the outer handler.

This is functionally identical in shape to the reported analog: the outer "parent" logic (`BalanceHandler`/`runNativeAction`) performs a check/state-mutation based on a linear index (`prevEventsLen`) without being aware that the "child" (nested precompile call) already advanced/consumed part of that same shared state, leading to incorrect (here, duplicated) balance mutation instead of an incorrect revert.

This exact bug is explicitly called out by the repository's own test suite: [4](#0-3) 

with the accompanying comment "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."

### Impact Explanation
Duplicate application of `CoinReceived`/`CoinSpent` events onto `StateDB.AddBalance`/`SubBalance` desynchronizes the EVM-visible balance from the actual `x/bank` (and `x/precisebank`) ledger balance. Because native token balance as seen by the EVM (`StateDB.GetBalance`, used for `msg.value` checks, subsequent transfers, and gas accounting within the same or later EVM calls in the same transaction) can be inflated beyond what is actually backed in `x/bank`, an attacker who can trigger recursive/nested precompile calls (e.g., via a caller contract that invokes a precompile whose native action itself re-enters another precompile or itself) can cause the `StateDB` balance of an address to be credited more than once for a single real bank transfer. This is a duplication/unauthorized-inflation of spendable value on the EVM balance ledger relative to the backing `x/bank` supply — matching the "unauthorized minting/duplication of spendable user value across EVM balances" Critical impact category, and if committed, permanently corrupts the 1:1 accounting invariant between `x/bank` and EVM balances that `x/precisebank`/`x/vm` are designed to preserve.

### Likelihood Explanation
The mechanism requires only unprivileged access: any user can deploy a contract that calls a stateful precompile whose native handler itself triggers another (or the same) stateful precompile call, i.e., ordinary composable EVM call flows. The repository already contains a dedicated integration test (`TestRecursivePrecompileCallsWithDebugPrecompile`) built specifically to reproduce "recursive precompile calls" and observe the resulting event/balance behavior, indicating this is a known, reachable pattern in production precompiles (e.g., `distribution`'s deposit-with-internal-transfer flows, `bank`, `erc20`, `werc20`) rather than a purely theoretical or debug-only construct.

### Recommendation
Do not key `BalanceHandler` windows off a single mutable `prevEventsLen` shared through a linear, ever-growing `ctx.EventManager()` event log across nested precompile invocations. Instead:
- Track a stack (or reentrancy-aware boundary) of already-consumed event ranges so a nested handler's consumed events are excluded from the outer handler's replay window, or
- Have nested calls mark the events they've already applied (e.g., tag/consume them) so an enclosing handler's `AfterBalanceChange` only processes truly unprocessed events, or
- Refactor to apply balance-changing events immediately within the same event-processing pass regardless of nesting depth, using a single top-level handler for a full precompile call tree rather than one handler per call frame.

### Proof of Concept
The repository's own `evmd/tests/integration/balance_handler/balance_handler_test.go` is effectively the PoC: it deploys a caller contract that invokes a debug precompile recursively via `callback(0)`, funds the caller contract, and sends a transaction that triggers the recursive precompile calls. The test explicitly documents and asserts on the resulting event structure, which was specifically designed to surface the "balance desync between native bank keeper and EVM stateDB" caused by shared/overwritten `prevEventsLen` state during recursive `BalanceHandler` invocations: [5](#0-4) 

Note: I could not fully confirm from the available index whether the currently checked-in code represents the vulnerable state or an already-mitigated state (e.g., whether the test currently fails or is a regression guard for a fix applied elsewhere that I did not locate). The `BalanceHandlerFactory`/`NewBalanceHandler()` call in `runNativeAction` does create a new handler instance per call frame, but this does not resolve the shared-event-log double-counting issue described above since the underlying `ctx.EventManager()` events are cumulative across nested frames. This uncertainty should be verified by running the cited test and tracing whether `AfterBalanceChange` double-applies nested events in a live recursive-precompile scenario.

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
