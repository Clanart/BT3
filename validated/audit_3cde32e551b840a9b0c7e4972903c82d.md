### Title
Silent failure on `upb_Decode` status in PHP `Message::mergeFrom()` due to assert-only check - (File: `php/ext/google/protobuf/message.c`)

### Summary
`PHP_METHOD(Message, mergeFrom)` re-serializes the source message and re-parses those bytes into the destination message's underlying `upb_Message`, but only verifies the parse succeeded via `PBPHP_ASSERT(ok)` instead of surfacing a PHP-visible error, unlike the sibling `mergeFromString()` implementation in the same file which explicitly checks the `upb_DecodeStatus` and throws a `zend_exception` on failure.

### Finding Description
`Message::mergeFrom()` implements object-to-object merging by round-tripping through the wire format: [1](#0-0) 
It encodes `from->msg` with `upb_Encode`, checks that encode status, then calls `upb_Decode(pb, size, intern->msg, l, NULL, 0, arena)` and stores the boolean comparison result in `ok`, followed only by `PBPHP_ASSERT(ok)` — no `zend_throw_exception_ex` call, no early return, no propagation of failure to the PHP caller.

Contrast this with the adjacent, wire-level entry point `mergeFromString()`, which is the properly-guarded analog: [2](#0-1) 
Here the same `upb_Decode` return status is checked with a real conditional and a thrown `zend_throw_exception_ex(NULL, 0, "Error occurred during parsing")` on any non-OK status, including `kUpb_DecodeStatus_MaxDepthExceeded`.

The invariant that fails to transfer in `mergeFrom()` is: "a non-OK decode status must abort the operation and inform the caller." Because the check is only an assert-style macro (`PBPHP_ASSERT`), whose enforcement depends on build configuration, a decode failure inside `mergeFrom()` can be silently swallowed in a production build, exactly mirroring the Solidity `transfer()` pattern where a failed operation's return value is discarded and the caller proceeds as though it succeeded.

A concrete way an ordinary caller can drive `upb_Decode` to a non-OK status here is exceeding the decoder's recursion/depth limit: `upb_Decode` is invoked with `options = 0`, i.e. the library default max depth. If the source message `from` was built up via PHP API calls (e.g., repeatedly setting nested sub-message fields from attacker-influenced application logic) to a nesting depth beyond that default, `upb_Encode` will succeed (encoding doesn't depth-limit the same way), but the subsequent `upb_Decode` back into `intern->msg` can return `kUpb_DecodeStatus_MaxDepthExceeded`.

### Impact Explanation
If the assert is compiled out (common practice for release builds), `mergeFrom()` returns normally to PHP userland with no exception and no boolean/return-code indicating a problem, even though the destination message's `upb_Message` may have been left partially populated by the aborted decode (integrity/data-corruption concern), and the caller has no way to detect that the merge did not fully complete. This breaks the API's implicit contract (matching the sibling `mergeFromString` behavior) that a failed merge always raises a catchable exception, and can lead application code to operate on a silently incomplete/inconsistent message object — a direct analog to the `withdraw()` issue where failure to check a return value causes downstream logic to proceed on the false assumption of success.

### Likelihood Explanation
Likelihood is moderate to low: it requires the caller to actually invoke `mergeFrom()` (object-to-object, not the more common `mergeFromString()`/`parseFromString()` wire-parsing paths) with a source message deep enough to exceed the decoder's default max-depth limit, and it also depends on whether `PBPHP_ASSERT` is a no-op in the actual production build of the PHP extension. I was not able to fully confirm the exact macro definition/behavior of `PBPHP_ASSERT` under release-mode compilation within the available tooling, so this residual uncertainty should be resolved by inspecting `php/ext/google/protobuf/protobuf.h` directly in a full checkout.

### Recommendation
Change `PHP_METHOD(Message, mergeFrom)` to check the `upb_Decode` status explicitly and throw a `zend_exception` on any non-OK status, mirroring `mergeFromString()`'s handling, rather than relying on an assert-style check whose enforcement is build-configuration-dependent.

PHP_METHOD(Message, mergeFromString) {
  Message* intern = (Message*)Z_OBJ_P(getThis());
  char* data = NULL;
  zend_long data_len;
  zend_long recursion_limit = 0; /* 0 = use library default */
  const upb_MiniTable* l = upb_MessageDef_MiniTable(intern->desc->msgdef);
  upb_Arena* arena = Arena_Get(&intern->arena);

  if (zend_parse_parameters(ZEND_NUM_ARGS(), "s|l", &data, &data_len,
                            &recursion_limit) == FAILURE) {
    return;
  }

  int options = 0;
  if (recursion_limit != 0) {
    if (recursion_limit < 1 || recursion_limit > 0xffff) {
      zend_throw_exception_ex(NULL, 0,
                              "recursion_limit must be between 1 and 65535");
      return;
    }
    options = upb_DecodeOptions_MaxDepth((uint16_t)recursion_limit);
  }

  if (upb_Decode(data, data_len, intern->msg, l, NULL, options, arena) !=
      kUpb_DecodeStatus_Ok) {
    zend_throw_exception_ex(NULL, 0, "Error occurred during parsing");
    return;
  }
}
