### Title
`SignableTransaction::new` excludes the OP_RETURN `data` output from fee/weight estimation, so the signed transaction underpays its fee (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to DODO's `externalSwap` pulling the full `fromTokenAmount` while the swap target silently leaves an unreturned remainder, `SignableTransaction::new` adds an extra output (`data` as OP_RETURN) to the transaction *after* the weight/vbytes used for fee calculation were computed — an unaccounted remainder on the output side. The resulting transaction is larger than what was paid for, so its effective feerate is lower than the caller-specified `fee_per_vbyte`, and can fall below the minimum relay fee.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` at send.rs:194-202, but the weight and vbytes used to derive `needed_fee` are computed by `calculate_weight_vbytes(tx_ins.len(), payments, None)` at send.rs:204, whose dummy `Transaction` is built only from `payments` (and optionally `change`) — it never includes the `data` output. The same omission occurs in the change path at send.rs:225-226. [1](#0-0) 

`calculate_weight_vbytes` only serializes `payments` into the template transaction's `output` vector: [2](#0-1) 

Consequences:

1. `needed_fee` under-reports the true fee by `fee_per_vbyte * vsize(OP_RETURN_output)` — roughly `fee_per_vbyte * (9 + data.len())` vbytes, up to ~90 vbytes for the maximum 80-byte payload allowed at send.rs:171.
2. The `TooLowFee` check at send.rs:211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * underestimated_vbytes`. The signed transaction's real vsize is larger than estimated, so its real feerate can fall below the minimum relay feerate even though the check passed. Such a transaction will be rejected by `send_raw_transaction` / never relayed, while `needed_fee()` and the `Eventuality` (txid) report it as a valid plan.
3. When `change` is `Some`, the change amount `value = input_sat - payment_sat - fee_with_change` (send.rs:228) is computed against the under-estimated `fee_with_change`, so the change output is credited slightly more than it should be — i.e., the "remainder" is mis-accounted rather than correctly returned.

### Impact Explanation
This is a fee/change math defect in the transaction builder that produces the exact `Transaction` committed to by the FROST `TransactionSignMachine` (`taproot_key_spend_signature_hash` over `Prevouts::All`, send.rs:373-397). A plan whose transaction carries a `data` payload is signed with a fee below the intended rate; if the real feerate drops under the relay minimum, the signed transaction can never confirm, stalling the inputs' spend path until a replacement plan is signed. In the milder case the change output silently receives an incorrect (overstated) remainder — leftover funds are mis-attributed rather than correctly accounted, mirroring the DODO finding's unconsumed-remainder class.

### Likelihood Explanation
`data` is an optional, caller-supplied parameter of `SignableTransaction::new`. The bitcoin-serai processor currently always passes `None` (processor/src/networks/bitcoin.rs:450), so the bug is only reachable when `data` is supplied; the in-crate tests exercise `data` only for error paths (`TooMuchData`), never checking fee correctness with data present. Given a non-`None` `data`, the miscalculation is deterministic — every such transaction underpays.

### Recommendation
Include the `data`/OP_RETURN output (and any other output appended to `tx_outs`) in the template transaction inside `calculate_weight_vbytes`, or compute weight/vbytes from the final `tx_outs` vector rather than only from `payments`. Concretely, pass the OP_RETURN script (or an equivalently-sized placeholder) into `calculate_weight_vbytes` in both the no-change call at send.rs:204 and the change call at send.rs:225-226, and assert `tx.weight()` of the final transaction matches the estimated weight.

### Proof of Concept
Conceptual: call

```rust
SignableTransaction::new(inputs, &payments, None, Some(vec![0u8; 80]), fee_per_vbyte)
```

The returned `SignableTransaction` has `tx.output` containing the payments plus a ~91-byte OP_RETURN output, yet `needed_fee()` equals `fee_per_vbyte * vsize(payments-only tx)`. Comparing `tx.fee() / real_vsize` shows an effective feerate below `fee_per_vbyte`; with `fee_per_vbyte` at the minimum relay boundary, `send_raw_transaction` rejects the signed transaction despite the `TooLowFee` check having passed.
