### Title
Missing self-participant exclusion in `GeneratorPromotion::complete` causes an unconditional panic on attacker-shaped proof maps - (crypto/dkg/promote/src/lib.rs)

### Summary
The analog of the Merit Circle finding is a stale/incomplete validation pattern: `setCurvePoint` updated the curve array but forgot to update the derived `unit` variable, so a later index computation went out of bounds. In Serai, `GeneratorPromotion::complete` validates the *size* and *upper bound* of the `proofs` map, but forgets to validate that the map does not contain the caller's own participant index `params.i()`. A map that includes `i` necessarily displaces some other required participant `j`, and the subsequent `proofs.get(&j).unwrap()` panics — the same "an element was effectively removed/mislabeled and a derived lookup was not updated to account for it" shape. [1](#0-0) 

### Finding Description
`complete` performs two checks on the externally supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

1. `proofs.len() == n - 1` (line 125)
2. every key satisfies `key <= n` (lines 132–136)

It never checks `key != params.i()`. Since `Participant` is a nonzero `u16` and `HashMap` keys are unique, any map of `n - 1` keys drawn from `1..=n` that contains `i` must omit some other participant `j != i`. The loop at lines 140–146 iterates `1..=n`, skips only `i`, and then calls `proofs.get(&i).unwrap()` — which returns `None` for the omitted `j` and panics.

The parallel to the original bug is exact in structure: just as removing a curve point left `unit = maxLockDuration / (curve.len() - 1)` stale so `curve[maxLockDuration / unit]` indexed out of bounds, here admitting `i` into the proof set leaves the implicit invariant "every `1..=n` except `i` is present" broken, so the indexed lookup `proofs.get(&j)` dereferences a missing entry.

`GeneratorProof::read` accepts arbitrary untrusted bytes (a group element plus a `DLEqProof`), so a peer can supply a well-formed proof that gets keyed under `params.i()` by the caller's message-handling layer (or a caller that simply aggregates `(participant, proof)` pairs without deduplication/exclusion) — this is an untrusted-input path into a `complete` API. ### Impact Explanation
The `.unwrap()` on `proofs.get(&i)` (line 146) panics instead of returning a `PromotionError`. Because `GeneratorPromotion::complete` consumes `self`, the panic occurs mid-protocol after `promote` has already been executed and proofs exchanged; in an async/FFI embedding an unwind here aborts the promotion attempt entirely. This is a denial of service on the key-promotion path — the same impact class as the source finding (depositors permanently unable to use the maximal-bonus path after a curve-point removal). The panic is reachable solely through the contents of the `proofs` map, which is derived from peer-supplied bytes.

### Likelihood Explanation
Any single counterparty that causes their `GeneratorProof` to be inserted under the victim's own index `params.i()` (e.g., a mislabeled or replayed message, or an integrator that keys the map by an attacker-influenced field) triggers the panic deterministically: the length check passes (`n - 1` entries), the bound check passes (`i <= n`), and the unwrap panics on the first omitted participant. No cryptographic validity is needed beyond what `GeneratorProof::read` parses.

### Recommendation
Reject maps containing the caller's own index, mirroring how `ThresholdKeys::new` / `ThresholdView::view` validate participant sets:

```rust
for i in proofs.keys().copied() {
  if (u16::from(i) > params.n()) || (i == params.i()) {
    Err(PromotionError::InvalidParticipant { n: params.n(), participant: i })?;
  }
}
```

Alternatively (and more robustly), iterate `proofs` entries directly rather than re-deriving expected keys with `1..=n` and unwrapping, so map membership is validated in one pass.

### Proof of Concept
```rust
// crypto/dkg/promote/src/tests.rs — conceptual PoC
let mut keys = /* ThresholdKeys<Ristretto> for n = 5, i = 2, t = 5 */;
let (promotion, our_proof) =
    GeneratorPromotion::<Ristretto, AltGenerator<Ristretto>>::promote(&mut OsRng, keys.clone());

// Build a map with n - 1 = 4 entries that includes OUR OWN index (2)
// and therefore omits some other participant (e.g. 5).
let mut proofs = HashMap::new();
proofs.insert(keys.params().i(), our_proof);           // attacker-mislabeled entry keyed as `i`
for p in [1u16, 3, 4] {
    let p = Participant::new(p).unwrap();
    proofs.insert(p, our_proof);                       // contents don't matter; unwrap fires first
}
assert_eq!(proofs.len(), usize::from(keys.params().n()) - 1); // passes len check
// All keys <= n: passes bound check. Contains i, missing participant 5.
// complete() panics at `proofs.get(&i).unwrap()` when i = 5.
promotion.complete(&proofs);
```

`proofs.len() == n - 1` and every key `<= n`, so both validation gates pass; the loop reaches `Participant(5)`, `proofs.get(&Participant(5))` is `None`, and `.unwrap()` panics — a deterministic DoS triggered purely by the composition of the untrusted proof map.

  pub fn complete(
    self,
    proofs: &HashMap<Participant, GeneratorProof<C1>>,
  ) -> Result<ThresholdKeys<C2>, PromotionError> {
    let params = self.base.params();
    if proofs.len() != (usize::from(params.n()) - 1) {
      Err(PromotionError::IncorrectAmountOfParticipants {
        t: params.n(),
        n: params.n(),
        amount: proofs.len() + 1,
      })?;
    }
    for i in proofs.keys().copied() {
      if u16::from(i) > params.n() {
        Err(PromotionError::InvalidParticipant { n: params.n(), participant: i })?;
      }
    }

    let mut verification_shares = HashMap::new();
    verification_shares.insert(params.i(), self.proof.share);
    for i in 1 ..= params.n() {
      let i = Participant::new(i).unwrap();
      if i == params.i() {
        continue;
      }

      let proof = proofs.get(&i).unwrap();
      proof
        .proof
        .verify(
          &mut transcript(&self.base.original_group_key(), i),
          &[C1::generator(), C2::generator()],
          &[self.base.original_verification_share(i), proof.share],
        )
        .map_err(|_| PromotionError::InvalidProof(i))?;
      verification_shares.insert(i, proof.share);
    }
