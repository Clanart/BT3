### Title
Permanent DoS of bribe harvesting/voting for all pools via blacklisting a fixed protocol fee recipient in `WombatStaking.vote()` - (File: wombat/WombatStaking.sol)

### Summary
`WombatBribeManager.castVotes()`, a permissionless function callable by any ordinary wallet, drives `WombatStaking.vote()` which loops over every voted pool and every bribe reward token and unconditionally `safeTransfer`s a protocol fee slice to the fixed address `bribeFeeCollector` (and a caller-fee slice forwarded to `bribeManager`/`msg.sender`). If any bribe reward token behaves like USDC/USDT and blacklists the fixed `bribeFeeCollector` address, every future `safeTransfer(bribeFeeCollector, protocolFee)` for that token reverts, and because the transfer sits inside a loop shared by all pools within one atomic transaction, the entire `vote()`/`castVotes()` call reverts — blocking bribe harvesting and vote casting for every pool and every voter, not just one bad actor, until an admin intervenes.

### Finding Description
`castVotes()` is public/unprivileged and iterates over all registered pools to compute vote deltas, then calls `wombatStaking.vote(...)`: [1](#0-0) 

Inside `WombatStaking.vote()`, for every pool with pending bribe rewards and every reward token, a protocol fee is unconditionally transferred to the fixed `bribeFeeCollector` address, and a caller fee is transferred to `bribeManager`, before the remaining reward is queued into the pool's rewarder: [2](#0-1) 

This is analogous to the reported `AuctionUpgradeable` bug class: a blacklistable ERC20 (USDC/USDT-style bribe token) forces a `safeTransfer` to a fixed recipient that can become blacklisted by the token issuer, and because that transfer is embedded inside a loop that is shared across many pools/users in a single atomic call, one blacklisted recipient causes the *entire* batched operation to revert every time it is invoked — not just the transfer for the affected token/pool.

### Impact Explanation
Once `bribeFeeCollector` is blacklisted for a given bribe reward token, `WombatStaking.vote()` will always revert as long as that token has `rewardAmount > 0` for any pool, because the `protocolFee` transfer happens unconditionally before other pools/tokens are processed and the whole external call reverts atomically. Since `castVotes()` is the single function that both casts votes and harvests/forwards bribes for **all** pools in one transaction, this permanently freezes:
- Vote casting to Wombat's voter contract for all pools (not just the one with the blacklisted-token bribe).
- Harvesting and distribution of bribe rewards (unclaimed yield) to `BribeRewardPool`s for every voter across every pool, since `queueNewRewards` is never reached.

This matches the "permanent freezing of unclaimed yield" / 24h+ freeze impact bar, and unlike a self-inflicted issue, it is triggered by an external token-issuer action against a protocol-controlled fixed address, not the caller's own wallet, so it cannot be worked around by simply using a different caller.

### Likelihood Explanation
Likelihood depends on an external stablecoin issuer blacklisting the specific `bribeFeeCollector` address for a bribe token that is USDC/USDT-like. This is a low-probability but externally-triggerable event (same root cause class as the original report), and once triggered requires privileged admin intervention (e.g., updating `bribeFeeCollector` or removing/pausing the offending bribe token) to restore functionality — the underlying code path itself is fully reachable by any unprivileged caller and contains no per-token isolation or try/catch to prevent one bad token from freezing the whole batch.

### Recommendation
- Whitelist which tokens are permitted as bribe reward tokens, excluding known blacklistable stablecoins (USDC/USDT), mirroring the fix adopted by Irrigation Protocol (commit `cae1d1718ef504f4fc27ba1aa464600a71ae635a`) of enforcing a `sellToken`/reward-token whitelist.
- Alternatively, wrap the per-token/per-pool fee transfers in `try/catch` (or a pull-based fee-collection pattern) so a single failing transfer cannot revert the entire batched `vote()`/`castVotes()` call for unrelated pools and tokens.

### Proof of Concept
1. Bribe rewards accrue in a pool using a blacklistable token (e.g. a USDC-like bribe token) via `voter.vote()`.
2. The token issuer blacklists the fixed `bribeFeeCollector` address (an address entirely outside the control of ordinary users/voters).
3. Any user calls `WombatBribeManager.castVotes()` / `voteAndCast()`.
4. `WombatStaking.vote()` reaches `IERC20(rewardTokens[i][j]).safeTransfer(bribeFeeCollector, protocolFee)` for the blacklisted-recipient token and reverts.
5. Because this call is nested inside `castVotes()`, which processes voting and reward-forwarding for all pools in one transaction, the revert rolls back voting and bribe harvesting for every pool, not just the affected token/pool, freezing unclaimed bribe yield for all voters until governance intervenes.
