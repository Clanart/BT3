### Title
Unverified proof-of-possession allows blame proof to leak another participant's ECDH key and secret share - (File: crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to CVE-2026-2317 (an implementation flaw letting an attacker leak data they should not access), `Encryption::decrypt` returns an `EncryptionKeyProof` — the revealed ECDH shared key — before the message's Schnorr proof-of-possession has actually been verified. The PoP is only *queued* into a `BatchVerifier`, and `KeyMachine::calculate_share` can early-return the blame proof on the invalid-scalar path without ever running `batch.verify_with_vartime_blame`. This re-enables the exact attack the PoP was added to prevent: an attacker who copies the per-message key `X` from an honest sender's encrypted share can induce the victim to publish `b·X`, decrypting the honest sender's secret share.

### Finding Description
In `Encryption::decrypt`, the PoP is scheduled for later batch verification, then the ECDH key `enc_key * msg.key` is computed and wrapped into an `EncryptionKeyProof` that is returned immediately: [1](#0-0) 

In `KeyMachine::calculate_share`, if the decrypted bytes are not a canonical scalar, the function returns `PedPoPError::InvalidShare { blame: Some(blame) }` *before* `batch.verify_with_vartime_blame()` at line 493 is reached: [2](#0-1) 

The code comments explicitly describe this attack and state the PoP exists to prevent it — Eve copies the key `X` from Alice's message to Bob, sends her own message claiming `X`, Bob blames Eve and reveals `bX`, which also decrypts Alice's message: [3](#0-2) 

But the mitigation is only effective if the PoP is verified before the blame proof is disclosed. On the invalid-scalar early return, it is not: Eve's forged PoP (which she cannot compute, not knowing the discrete log of `X`) is never checked. `decrypt_with_proof` used by `BlameMachine` does verify the PoP first, so the blame will correctly finger Eve — but by then Bob has already broadcast `EncryptionKeyProof { key: bX }`, which is publicly decryptable via `Decryption::decrypt_with_proof` and also directly usable as the ChaCha20 shared secret. [4](#0-3) 

### Impact Explanation
The blame proof reveals `b·X`, the exact ChaCha20 input shared key for *Alice's* message to Bob (`cipher(context, ecdh)` with static IV derives the keystream solely from the ECDH point and context). Anyone observing the published blame — including Eve, who triggered it — can compute `cipher(context, bX)` and decrypt Alice's encrypted `SecretShare` to Bob. This leaks an honest participant's DKG secret share to an unrelated party, a confidentiality break of exactly the class "remote attacker leaks cross-origin data": secret bytes reachable purely from public inputs (an `EncryptedMessage` the attacker crafts and sends). If Eve is a threshold coalition member or colludes, recovered shares contribute toward reconstructing the threshold private key.

### Likelihood Explanation
An unprivileged DKG participant Eve performs: (1) observe Alice's `EncryptedMessage` to Bob on the broadcast channel, extract `msg.key = X`; (2) build `EncryptedMessage { key: X, pop: <arbitrary bytes that parse as a SchnorrSignature>, msg: <arbitrary ciphertext> }` — `EncryptedMessage::read` performs no verification, only parsing; (3) send it to Bob as Eve's share. Bob's `decrypt` queues the (invalid) PoP, computes `bX`, applies the keystream to Eve's ciphertext yielding pseudorandom bytes; for Ristretto/ed25519 the scalar modulus is ~2^252, so random 32-byte output is non-canonical with probability ≈ 1 − 2^252/2^256 ≈ 15/16. `calculate_share` then returns `blame: Some(proof)` exposing `bX` without checking the PoP. Deterministic and cheap to attempt; retries cost nothing.

### Recommendation
Do not release the `EncryptionKeyProof` until the PoP batch item for that message has been verified. Concretely: in `KeyMachine::calculate_share`, when `C::F::from_repr` fails, the PoP for that message must still be verified (e.g., complete `batch.verify_with_vartime_blame` first, or synchronously `msg.pop.verify(...)` inside `Encryption::decrypt`) before attaching `Some(blame)` to the error. Alternatively, make `decrypt` verify the PoP inline rather than queuing it, since the blame proof it returns is only meaningful once the PoP is known-valid — mirroring the ordering already enforced in `Decryption::decrypt_with_proof`.

### Proof of Concept
```rust
// crypto/dkg/pedpop/src/tests.rs style, C = Ristretto
// Alice = ONE, Bob = TWO, Eve = THREE in a 3-of-5 DKG.

// 1. Run round 1 honestly for all 5 participants.
let (machines, commitment_msgs, _, shares) = commit_enc_keys_and_shares::<_, Ristretto>(&mut OsRng);

// 2. Eve copies Alice's per-message encryption key for the message Alice -> Bob.
let alice_to_bob: &EncryptedMessage<Ristretto, SecretShare<_>> = &shares[&ONE][&TWO];
let stolen_key: <Ristretto as Ciphersuite>::G = alice_to_bob.key; // X

// 3. Eve forges a message claiming key X with a garbage PoP and garbage ciphertext.
//    (fields are crate-private; equivalent bytes parse fine via EncryptedMessage::read)
let mut forged = EncryptedMessage::<Ristretto, SecretShare<_>> {
  key: stolen_key,
  pop: SchnorrSignature::<Ristretto> { R: <Ristretto as Ciphersuite>::generator(), s: <Ristretto as Ciphersuite>::F::ONE },
  msg: Zeroizing::new(SecretShare([0x42u8; 32])),
};

// 4. Bob runs calculate_share with Eve's forged share substituted.
let mut bob_shares = generate_secret_shares(&shares, TWO);
bob_shares.insert(THREE, forged);
match machines[&TWO].calculate_share(&mut OsRng, bob_shares) {
  Err(PedPoPError::InvalidShare { participant: THREE, blame: Some(proof) }) => {
    // proof.key == b*X: the shared key for Alice's message to Bob.
    // Eve (or anyone seeing the blame) can now decrypt Alice's share:
    let mut alice_msg = alice_to_bob.clone();
    cipher::<Ristretto>(CONTEXT, &proof.key)
      .apply_keystream(alice_msg.msg.as_mut().as_mut());
    // alice_msg.msg now contains Alice's secret share for Bob — leaked.
  }
  _ => panic!("expected invalid-scalar blame path"),
}
// Note: forged.pop is never verified on this path — the early return at
// lib.rs:480-482 fires before batch.verify_with_vartime_blame() at lib.rs:493.
```
