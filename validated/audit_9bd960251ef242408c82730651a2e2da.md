## Finding: Bandwidth allowance is permanently consumed even when the metered request fails to reach its destination module

### Title
Bandwidth is drained by the gate even when message routing/delivery to the destination pallet fails, causing unrecoverable loss of prepaid bandwidth — ([File: parachain/runtimes/gargantua/src/ismp.rs], [File: parachain/runtimes/nexus/src/ismp.rs], [File: modules/pallets/bandwidth/src/lib.rs])

### Summary
The external report's core defect is "a guard can silently consume a resource (fee) on a path that then fails, and the resource is not returned." The same broken invariant reproduces in Hyperbridge's bandwidth-accounting subsystem: `ProxyModule::on_accept` deducts prepaid bandwidth bytes from an app's subscription *before* it knows whether the request can actually be routed/delivered to its destination module. If the destination lookup or the destination pallet's own `on_accept` subsequently fails, the bytes already drained by the bandwidth gate are never refunded — there is no compensating/rollback logic anywhere in `pallet-bandwidth`.

### Finding Description
`ProxyModule::on_accept` runs the bandwidth gate unconditionally (skipping only purchase messages) before it resolves and invokes the destination module: [1](#0-0) 

The same pattern exists on the nexus runtime, including a case where messages are additionally rejected for unrelated policy reasons (deprecated `TokenGateway`) or fail because the resolved `pallet_id` doesn't match any known module ("Destination module not found"): [2](#0-1) 

The gate itself (`BandwidthGate::try_consume`) performs an unconditional, non-reversible storage mutation the moment it is called — it drains bytes from the FIFO subscription list and deposits `BandwidthConsumed`: [3](#0-2) 

This mutation happens as ordinary Rust code inside `on_accept`, not inside a nested dispatchable call. Elsewhere in the codebase (timeout handling), the authors are explicit that individual-message failures inside a batch must **not** be allowed to propagate as an `Err` from the whole extrinsic, because that would roll back every other successfully-processed message in the same batch. Instead they manually restore state on a per-message basis: [4](#0-3) 

`ProxyModule::on_accept`, by contrast, has no such manual restoration for the bandwidth gate. If `try_consume` succeeds and a *later* step in the same function fails — an unrecognized `pallet_id` (`Err(anyhow!("Destination module not found"))`), a deprecated-gateway rejection, or an internal error inside the destination pallet's own `on_accept` (e.g. `pallet_hyper_fungible_token::on_accept` erroring on a malformed body) — the consumed bytes are not returned to the subscription. I reviewed `modules/pallets/bandwidth/src/lib.rs` in full and found no "refund," "uncommit," or "release" entry point for this case; the only bandwidth-restoring mechanism is `force_credit`, which is governance-only: [5](#0-4) 

### Impact Explanation
Bandwidth is a purchased, prepaid asset — the docs describe it explicitly as replacing a per-message fee with an upfront byte budget. Any code path that debits the budget for a request that never completes delivery is a direct, unrecoverable loss of funds for the paying app, with no attacker required: a normal, unprivileged app whose message happens to hit a benign failure mode (wrong `to`/module id, a destination-pallet-side validation error, a deprecated-gateway block on nexus) loses the bytes it paid for. Given `SubscriptionEvicted` already treats "lost bytes" as an auditable on-chain event for eviction, the pallet's own design philosophy treats byte loss as something that should be surfaced/compensated — yet no such handling exists for this failure path.

### Likelihood Explanation
This does not require a malicious peer, relayer, or admin — it triggers on ordinary conditions: a request whose destination `pallet_id`/module isn't recognized, a destination pallet's `on_accept` erroring on bad input, or (on nexus) an app inadvertently routed through a deprecated `TokenGateway` address. Any of these is plausible in normal operation (integration bugs, migrations, stale module registrations) and directly costs the calling app real, previously-paid bandwidth with no recourse other than governance intervention (`force_credit`).

### Recommendation
Only debit the bandwidth gate after the destination module has been resolved and its `on_accept` has returned `Ok`, or explicitly restore the consumed bytes (mirroring the pattern in `handlers/timeout.rs`) whenever the subsequent routing/dispatch to the destination pallet fails.

### Proof of Concept
1. An app on a registered source chain has a live bandwidth subscription (`Allowance::<T>`).
2. It dispatches a `PostRequest` whose `to` field encodes a `ModuleId` that does not match any pallet in `ProxyModule::on_accept`'s match arms (or hits the destination pallet's own internal validation failure).
3. `ProxyModule::on_accept` calls `BandwidthGate::try_consume` first — bytes are drained and `BandwidthConsumed` is emitted [6](#0-5) .
4. Execution reaches the `match pallet_id { ... _ => Err(anyhow!("Destination module not found")) }` arm and returns `Err` [7](#0-6) .
5. The app's `remaining_bytes` for that subscription stays permanently reduced; no code path restores it, and the app received zero delivered service for the bytes it paid for.

**Note on scope:** I was not able to directly inspect `modules/ismp/core/src/handlers/request.rs` (the code that ultimately invokes `router.module_for_id(...).on_accept(...)` for POST requests) within the available searches to confirm with 100% certainty that a per-message `Err` from `on_accept` does not trigger a full-extrinsic storage rollback. The finding above is inferred from (a) the explicit, hand-rolled per-message state-restoration pattern used in the sibling `timeout.rs` handler specifically to avoid batch-wide rollback, and (b) the absence of any refund/rollback code for bandwidth consumption anywhere in `pallet-bandwidth`. If request handling turns out to wrap each message in an automatic transactional rollback on `Err` (unlike the timeout path), this specific loss would not materialize and would need re-verification directly against `modules/ismp/core/src/handlers/request.rs`.

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}
