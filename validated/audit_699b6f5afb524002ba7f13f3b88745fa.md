Audit Report

## Title
`getRecentPrioritizationFees` accepts unbounded `pubkeys` array with no length limit, unlike sibling RPC methods - (File: `rpc/src/rpc.rs`)

## Summary
`JsonRpcRequestProcessor::get_recent_prioritization_fees` accepts an arbitrary-length `pubkeys: Vec<Pubkey>` and passes it directly into `PrioritizationFeeCache::get_prioritization_fees` with no length check, unlike sibling RPC handlers in the same file (`getMultipleAccounts`, `getSignatureStatuses`, `getInflationReward`, `getProgramAccounts` filters) which all enforce explicit `MAX_*` bounds before doing real work. [1](#0-0)  This allows an unprivileged remote client to submit a single request with an oversized `pubkeys` array, forcing `O(cached_slots * pubkeys.len())` synchronous hashmap-lookup work on the RPC dispatch path, degrading RPC availability for that node.

## Finding Description
The handler is defined as: [1](#0-0)  No `if pubkeys.len() > MAX_...` guard exists before this call, in contrast to the pattern used for `getInflationReward`'s bound check via `MAX_GET_INFLATION_REWARD_ADDRESSES` and `verify_filters`'s `MAX_GET_PROGRAM_ACCOUNT_FILTERS` check elsewhere in `rpc/src/rpc.rs`. The underlying cache method iterates every cached slot and, for each slot, iterates the full caller-supplied `account_keys` slice performing a hashmap lookup per key [2](#0-1) , meaning total work scales linearly with the number of pubkeys supplied, which is fully attacker-controlled with no upper bound. No `MAX_GET_RECENT_PRIORITIZATION_FEES_*`-style constant exists in `rpc-client-types/src/request.rs`, unlike the constants used by other bounded array-parameter endpoints, corroborating that this specific limit is missing. Unlike scan-heavy endpoints such as `get_filtered_program_accounts`, which offload to a blocking thread pool via `self.runtime.spawn_blocking`, this handler runs inline on the async RPC dispatch path with no offloading, meaning the unbounded work directly consumes the request-handling task's resources.

## Impact Explanation
This is an unprivileged, remotely triggerable RPC resource-exhaustion primitive falling within the allowed "single-client low-rate RPC crash/degradation" impact category: any external client can submit one `getRecentPrioritizationFees` request with an oversized `pubkeys` array and force disproportionate CPU work on the node's RPC-serving path, degrading RPC availability/latency for that node. It does not affect consensus, funds, or execution correctness — it is scoped to node-local RPC subsystem availability.

## Likelihood Explanation
The endpoint is part of the default full RPC API, requires no special privileges or prior state manipulation, and the missing check is a straightforward omission relative to the consistently-applied sibling limits (`MAX_MULTIPLE_ACCOUNTS`, `MAX_GET_SIGNATURE_STATUSES_QUERY_ITEMS`, `MAX_GET_INFLATION_REWARD_ADDRESSES`, `MAX_GET_PROGRAM_ACCOUNT_FILTERS`) enforced elsewhere in `rpc/src/rpc.rs`. A single crafted JSON-RPC POST with a large `pubkeys` array is sufficient; no gossip/peer trust or prior state manipulation is required, and the attack is trivially repeatable.

## Recommendation
Add an early length check on `pubkeys` in `get_recent_prioritization_fees` (or its RPC trait binding wrapper), mirroring the `MAX_GET_INFLATION_REWARD_ADDRESSES`/`MAX_MULTIPLE_ACCOUNTS` pattern: define a `MAX_GET_RECENT_PRIORITIZATION_FEES_ACCOUNTS` constant and reject requests exceeding it via `Error::invalid_params` before invoking `PrioritizationFeeCache::get_prioritization_fees`.

## Proof of Concept
1. Start a validator with the RPC service enabled (default full RPC API; `enable_rpc_transaction_history` not required).
2. Send a JSON-RPC request:
```json
{"jsonrpc":"2.0","id":1,"method":"getRecentPrioritizationFees","params":[[<N distinct base58 pubkeys, N = e.g. 1_000_000>]]}
```
3. Observe that `JsonRpcRequestProcessor::get_recent_prioritization_fees` (`rpc/src/rpc.rs:2440`) performs `O(cached_slots * N)` hashmap lookups synchronously on the request path with no rejection, unlike `getMultipleAccounts`/`getInflationReward`/`getProgramAccounts`, which reject oversized inputs immediately via their respective `MAX_*` checks.

```rust
    pub fn get_prioritization_fees(&self, account_keys: &[Pubkey]) -> Vec<(Slot, u64)> {
        self.cache
            .read()
            .unwrap()
            .iter()
            .map(|(slot, slot_prioritization_fee)| {
                let mut fee = slot_prioritization_fee
                    .get_min_compute_unit_price()
                    .unwrap_or_default();
                for account_key in account_keys {
                    if let Some(account_fee) =
                        slot_prioritization_fee.get_writable_account_fee(account_key)
                    {
                        fee = std::cmp::max(fee, account_fee);
                    }
                }
                (*slot, fee)
            })
            .collect()
    }
```
