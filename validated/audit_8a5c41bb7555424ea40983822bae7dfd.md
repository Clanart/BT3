### Title
Guard Bypass in `_fetchRefspec` Allows Concurrent Git Fetch During In-Progress Push/Pull, Enabling Ref/Working-Copy Corruption via a Malicious Fork PR - (File: app/src/lib/stores/app-store.ts)

### Summary
`AppStore._fetchRefspec` is explicitly documented and implemented to skip the `isPushPullFetchInProgress` concurrency guard that every other network operation (`_pull`, `performPull`, `_fetch`, `fetchForRepositoryIndicator`, etc.) honors via `withPushPullFetch`. This is the same class of bug as the reported Solidity issue: a "reentrancy guard" that is supposed to protect a critical section is bypassed for one code path, allowing an attacker-influenced operation to run concurrently with another privileged/critical git operation on the same repository.

### Finding Description
Every git network mutation the app performs on a repository is wrapped in `withPushPullFetch`, which checks/sets `state.isPushPullFetchInProgress` before allowing the operation to proceed: [1](#0-0) 

`_pull`/`performPull` and `_fetch` both go through this guard: [2](#0-1) 

However, `_fetchRefspec` is deliberately written to *not* use this guard. The comment directly above it acknowledges the tradeoff: [3](#0-2) 

`_fetchRefspec` is driven by data that originates from viewing a pull request from a fork — i.e., a `refspec`, remote URL, and ref name that are controlled by whoever owns the fork/PR head repository, as seen in the PR checkout/branch-resolution flow that adds a remote pointing at the attacker-controlled `headCloneUrl` and fetches `headRefName`: [4](#0-3) 

`GitStore.fetchRefspec` then iterates over *all* configured remotes and runs `git fetch <remote> <refspec>` for each one, still without acquiring the app-level in-progress guard: [5](#0-4) [6](#0-5) 

Because `isPushPullFetchInProgress` is the only mechanism preventing two network git operations from running at once on the same working copy, and `_fetchRefspec` never checks or sets it, a user who is actively pulling/pushing (or has a background fetch triggered by the repository indicator) can have a second, independent `git fetch` process spawned against the same `.git` directory at the same time the fork-PR-driven fetch runs. Concurrent git processes against the same repository race on shared state (packed-refs, loose ref files, `.git/index.lock`, gc/repack triggers), which is a known source of corrupted refs or failed/partial writes — the underlying git-level protection (the guard) that the rest of the codebase relies on is simply not applied here.

### Impact Explanation
The corrupted value is the repository's local git ref/object state (and, transitively, `state.isPushPullFetchInProgress`'s guarantee of exclusivity). Unlike the Solidity report where the attacker exploits an `onlyStrategyManager`-privileged code path via reentrancy, here the attacker (a fork owner whose PR the victim opens/views) supplies the remote URL and ref that trigger an un-guarded fetch. If this races with the user's own push/pull, the result can be a corrupted or unexpected local repository state — silently affecting what the user later commits or pushes — without any local access, malware, or leaked credentials required from the attacker.

### Likelihood Explanation
This requires the victim to have a push/pull/fetch already in flight (including the periodic background `RepositoryIndicatorUpdater`/`fetchForRepositoryIndicator` fetches, or a manual pull) at the same moment they open/view a PR from a fork, which triggers `_findPullRequestBranch`/`_fetchRefspec`. Given that GitHub Desktop performs background fetches automatically and users frequently browse PRs while other operations are running, the race window is plausible but not guaranteed on every occurrence — it is a timing-dependent race condition rather than a deterministic exploit.

### Recommendation
Route `_fetchRefspec` (and the remote-fetching calls in `_findPullRequestBranch`) through the same `withPushPullFetch` guard (or a per-repository serialization queue) used by `_pull`/`_fetch`, rather than deliberately opting out. If UX requires the PR-preview fetch to proceed even while another network operation is in progress, queue it to run after the in-progress operation completes instead of letting it run concurrently and unguarded.

### Proof of Concept
1. Open a repository in GitHub Desktop and start a manual `git pull` (or wait for a background repository-indicator fetch) so `isPushPullFetchInProgress` is (conceptually) active for a real push/pull.
2. As an attacker, have a PR open against that repository from a fork you control, and ensure the victim opens/previews that PR (e.g., via the "Open Pull Request" dialog or a `x-github-client://openPR` deep link handled by `openPullRequestFromUrl`), which drives `_checkoutPullRequest` → `_findPullRequestBranch` → `_fetchRemote`/`_fetchRefspec`.
3. Because `_fetchRefspec` never checks `state.isPushPullFetchInProgress`, this second `git fetch` executes concurrently with the in-flight pull/fetch against the same `.git` directory.
4. Concurrent git fetch/pull processes on the same repository can race on ref updates and lock files, producing an inconsistent local ref/object state that the user may then unknowingly commit on top of or push.

Note: I was not able to trace a live UI entry point that calls `dispatcher.fetchRefspec` directly (only the `AppStore._fetchRefspec`/`GitStore.fetchRefspec` definitions were found in the indexed code), so the exact current UI trigger for `_fetchRefspec` itself is unconfirmed from the available index; the `_findPullRequestBranch`/`_fetchRemote` path (which shares the same missing-guard characteristic) is confirmed and reachable from fork-PR checkout flows.

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }
