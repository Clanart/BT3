### Title
Operator payer attribution in the payout transaction is not signature-bound, letting an unprivileged party frame a different operator as having fronted a withdrawal it never funded - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `payout_tx` that records which operator "fronted" a Citrea withdrawal embeds the fronting operator's x-only pubkey in a plain, unsigned `OP_RETURN` output. The only cryptographic commitment present is the user's Taproot key-spend signature over the withdrawal input/output (`create_payout_txhandler`), and that signature is generated and consumed independently of the `OP_RETURN` output's content. Verifiers later parse this `OP_RETURN` to determine "the operator who paid" (`update_finalized_payouts`, `is_kickoff_malicious`), and operators use this attribution to claim reimbursement (`validate_payer_is_operator`, `get_reimbursement_txs`). If the `OP_RETURN` payload is not actually covered by the witness that authorizes spending the user's UTXO, anyone able to construct a valid spend of that UTXO (i.e., anyone holding the user's payout signature, which must be shared with operators to be fulfilled and can also be observed once broadcast/in mempool prior to confirmation) can swap out the `OP_RETURN` payload for an arbitrary operator xonly-pubkey before the tx confirms, misattributing which operator fronted the withdrawal.

### Finding Description
`create_payout_txhandler` in [1](#0-0)  builds the payout transaction with:
1. Input: the user's withdrawal UTXO, spent via `SpendPath::KeySpend` using the user's Taproot signature (`user_sig`).
2. Output 0: the user payout.
3. Output 1: anchor.
4. Output 2: an `OP_RETURN` carrying the fronting `operator_xonly_pk`, added via `op_return_txout` [2](#0-1) .

This attribution is trusted downstream: verifiers scan confirmed payout transactions and set `payout_payer_operator_xonly_pk` purely from parsing this `OP_RETURN` output [3](#0-2) . That value then drives (a) `is_kickoff_malicious`, which trusts the DB-recorded payer pubkey to decide whether a kickoff is legitimate [4](#0-3) , and (b) `validate_payer_is_operator`, which an operator calls to confirm it is entitled to reimbursement and to fetch the kickoff txid [5](#0-4) , subsequently used by `get_reimbursement_txs` to hand out reimbursement transactions [6](#0-5) .

The binding that must hold is: `operator credited as payer == operator whose funds actually left via the payout output`. Because the payer identity is embedded in an `OP_RETURN` output that is not part of the input/output set the withdrawal signature is scoped to authorize spending against, the identity of "who fronted" is attacker-controllable metadata rather than a cryptographically bound fact, unlike the input UTXO and payout output which are fixed by the withdrawal request registered on Citrea (`withdraw` checks `withdrawal_utxo != input_utxo.outpoint` in [7](#0-6) ).

I was not able to fully confirm within the available context whether the specific sighash flag used for `set_p2tr_key_spend_witness` in `TxHandler` (in `core/src/builder/transaction/txhandler.rs`) is a full-commitment `SIGHASH_ALL`-equivalent (in which case the signature would cover all outputs, including the `OP_RETURN`, and this analog would not hold) or a `SIGHASH_SINGLE|ANYONECANPAY`-style commitment that only covers the withdrawal output and not the `OP_RETURN`/anchor outputs. The doc comments in `WithdrawParams`/`clementine.proto` explicitly describe the input signature as a "`[bitcoin::sighash::TapSighashType::SinglePlusAnyoneCanPay]` signature" [8](#0-7) , which is consistent with a signature that does **not** cover the `OP_RETURN` output, but I could not directly inspect the exact sighash construction and flag used at signing time inside `core/src/actor.rs`/`txhandler.rs` in this session to prove it conclusively.

### Impact Explanation
If the withdrawal signature indeed does not commit to the `OP_RETURN` output (consistent with the documented `SinglePlusAnyoneCanPay` sighash type), an unprivileged party who obtains the user's withdrawal signature — which must be distributed to operators for fulfillment, and is also visible once any operator's payout tx enters the mempool before confirmation — can rebuild an equivalent payout transaction with the same input and payout output but a substituted `OP_RETURN` naming a different (potentially uninvolved or malicious) operator's xonly-pubkey as the fronting party. Once mined, this would let that named operator's kickoff/reimbursement flow proceed and be treated as legitimate by `validate_payer_is_operator`/`is_kickoff_malicious`, i.e., an operator would be reimbursed for a payout it never funded — this maps directly to the Critical impact category "an operator reimbursed for a payout it never funded."

### Likelihood Explanation
Likelihood depends entirely on the unresolved sighash-type question above. If the input signature is `SIGHASH_ALL`-equivalent (covering all outputs), this finding does not hold, because any modification to the `OP_RETURN` would invalidate the signature. This is a real possibility that must be checked in `core/src/builder/transaction/txhandler.rs::set_p2tr_key_spend_witness` and wherever the withdrawal signature is originally produced (client-side, outside this repo's control) before treating this as confirmed.

### Recommendation
Verify the exact sighash type computed for the payout transaction's key-spend witness. If it is `SinglePlusAnyoneCanPay` (or any type that excludes the `OP_RETURN`/anchor outputs), either (a) change the sighash type to commit to all outputs (e.g., `SIGHASH_ALL`) so the fronting operator's identity is cryptographically bound to the user's authorization, or (b) require the operator to separately produce and check a Schnorr signature over the `OP_RETURN` payload (operator's own key) before verifiers/operators trust the `payout_payer_operator_xonly_pk` derived from it, rather than trusting the raw on-chain `OP_RETURN` bytes as sufficient attribution.

### Proof of Concept
Not verifiable without confirming the sighash type; if `SinglePlusAnyoneCanPay` is confirmed to exclude the `OP_RETURN` output, PoC would be: intercept a broadcast (unconfirmed) payout tx or otherwise obtain the user's withdrawal signature, construct a new transaction spending the same input, with the same signed payout output, but replacing the `OP_RETURN` output with `attacker_chosen_operator_xonly_pk`, and get it mined ahead of the legitimate operator's transaction — causing `attacker_chosen_operator` to be recorded as the payer in `update_payout_txs_and_payer_operator_xonly_pk`.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
