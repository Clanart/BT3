### Title
ThresholdKeys::new/::read never binds `secret_share` to `verification_shares[i]`, letting attacker-supplied key material silently redefine the group key - (File: crypto/dkg/src/lib.rs)

### Summary
The injection bug class (an attacker-controlled parameter spliced into a security-sensitive query without sanitization) maps onto `ThresholdKeys::read`/`ThresholdKeys::new`: the `secret_share` scalar and the `verification_shares` map are accepted verbatim from untrusted bytes, and `group_key` is computed *solely* by Lagrange-interpolating the verification shares of participants `1..=t`. No check ever proves `C::generator() * secret_share == verification_shares[i]`, nor that the interpolated secret share belongs to the same polynomial the group key commits to. The injected "parameter" (the verification share vector) therefore fully determines which key the victim signs under, independent of the secret share they hold.

### Finding Description
`ThresholdKeys::new` validates only the cardinality of `verification_shares` and that participant indices are `<= n`, then derives `group_key` from `verification_shares[1..=t]` alone [1](#0-0) . It returns `Ok` without ever comparing `C::generator() * secret_share` against `verification_shares[&params.i()]` [2](#0-1) . The deserialization path `ThresholdKeys::read` reads `t`, `n`, `i`, the interpolation variant, the raw `secret_share` via `C::read_F`, and exactly `n` group elements via `C::read_G`, then passes them to `ThresholdKeys::new` [3](#0-2) . Two injection modes result:

1. **Inconsistent share/key**: set `verification_shares[i] != G * secret_share`. `group_key()` still yields a syntactically valid point derived from shares `1..=t`. In `ThresholdKeys::view` the victim's `secret_share` is interpolated with the same factors as the injected verification shares [4](#0-3) , so every share the victim signs is inconsistent — and, more importantly, the *reported* `group_key` corresponds to a secret the victim's share does not participate in as believed. Funds addressed to `group_key` are received but not spendable by the intended share holder.
2. **Fully consistent but attacker-chosen polynomial**: the attacker constructs `t` scalars `a_j`, writes `verification_shares = {g*a_j}` and `secret_share = a_i`. All internal checks pass, the victim signs validly, yet the attacker knows the full group secret — the "threshold" key is a solo attacker key. This mirrors the SQLi outcome: crafted input rewrites which "rows" (which secret/key) the operation actually applies to.

Reachability is via `ThresholdKeys::read` (listed untrusted-bytes entry point), e.g. imported/reshared key material or coordinator-distributed key blobs; the code's own comment in `complete` acknowledges "deserializing a semantically invalid FrostKeys" as a reachable state [5](#0-4) .

### Impact Explanation
Mode 2 yields signatures under a group key whose discrete log is fully known to the attacker — any UTXO/account controlled by the victim's "multisig" is unilaterally spendable by the attacker (equivalent to secret-key recovery/forgery). Mode 1 yields a group key the victim cannot validly sign for, so deposits are permanently locked — the "funds reported received that are not spendable" acceptance criterion. Both are concrete cryptographic impacts, not best-practice issues.

### Likelihood Explanation
Exploitation requires the attacker to feed bytes to `ThresholdKeys::read` (or otherwise control the `secret_share`/`verification_shares` inputs to `ThresholdKeys::new`). Honest PedPoP/`dealer` flows construct consistent inputs internally [6](#0-5) , so the attack needs a path where key material is imported, reshared, restored from attacker-influenced storage, or distributed by an untrusted coordinator — a real but narrower surface than the online signing messages, supporting Medium severity. The missing invariant check itself is unconditional and trivially exploitable once the input path exists.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs), after validating the share map, assert `C::generator() * *secret_share == verification_shares[&params.i()]` and return a `DkgError` on mismatch. For defense in depth, when `t < n` this only proves the holder's share is consistent; consumers importing `ThresholdKeys` should additionally verify `group_key()` against an externally authenticated expected key, since the polynomial's other shares are not provably consistent without a DKG transcript.

### Proof of Concept
Conceptual construction against `ThresholdKeys::<C>::read` (or `new`):

```rust
// Attacker picks any scalars they know, e.g. a_j = j for j = 1..=t (= n for simplicity).
let t = 2u16; let n = 2u16; let i = Participant::new(1).unwrap();
let a1 = C::F::from(0xdeadbeefu64);          // attacker-known secret share for i = 1
let a2 = C::F::from(0xfeedfaceu64);          // attacker-known share for j = 2

// Interpolation::Lagrange; group_key is interpolated from verification_shares[1..=2]
// = G * (a1*L1 + a2*L2) — a key whose discrete log the attacker fully knows.
let mut vs = HashMap::new();
vs.insert(Participant::new(1).unwrap(), C::generator() * a1);
vs.insert(Participant::new(2).unwrap(), C::generator() * a2);

// ThresholdKeys::new returns Ok — it never checks G*secret_share == vs[&i].
let keys = ThresholdKeys::new(
    ThresholdParams::new(t, n, i).unwrap(),
    Interpolation::Lagrange,
    Zeroizing::new(a1),
    vs,
).unwrap();

// Victim proceeds to FROST-sign under keys.group_key(); signatures are valid,
// yet the attacker (who knows a1, a2 and hence the interpolated group secret)
// can forge the same signatures and spend any funds at group_key() alone.
```

Variant B (mode 1): write `vs[&i] = C::generator() * (a1 + C::F::ONE)` while keeping `secret_share = a1`; `read` still succeeds, `group_key()` corresponds to no secret the victim holds, and every signature share the victim produces is invalid — deposits to `group_key()` are unspendable.

Caveat I could not fully verify within the iteration limit: whether an in-scope upstream consumer actually feeds attacker-controlled bytes into `ThresholdKeys::read` (e.g., a key-import or reshare flow outside `crypto/`); the analysis relies on the prompt's classification of `ThresholdKeys::read` as an in-scope untrusted-input sink.
