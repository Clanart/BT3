### Title
`forceUnLock()`, `unlock()` and `cancelUnlock()` never refresh referral boost factor - (File: VLMGP.sol)

### Summary
`VLMGP._lock()` and `startUnlock()` both call `IReferralStorage(referralStorage).updateTotalFactor(user)` whenever a user's locked balance changes, but `forceUnLock()`, `unlock()`, and `cancelUnlock()` do not, even though they all mutate `slot.amountInCoolDown`, `totalAmountInCoolDown`, and (via `_unlock()`) `totalAmount` and the user's MasterMagpie staked balance. This leaves `ReferralStorage.userInfos[user].factor` and the shared `totalBoostFactor` denominator stale relative to the user's real locked amount.

### Finding Description
`ReferralStorage.updateTotalFactor()` recomputes a user's boost `factor` as `sqrt(IVLMGP(vlMGP).getUserTotalLocked(_account))` and adjusts the global `totalBoostFactor` accordingly [1](#0-0) . This is invoked from `VLMGP._lock()` [2](#0-1)  and from `startUnlock()` [3](#0-2) .

However, `forceUnLock()` calls `_unlock(slot.amountInCoolDown)` (which reduces `totalAmount`/`totalAmountInCoolDown` and calls `IMasterMagpie(masterMagpie).withdrawVlMGPFor`, directly shrinking the user's real locked balance) and zeroes out the slot, but it never calls `updateTotalFactor` [4](#0-3) . The same omission exists in `unlock()` [5](#0-4)  and `cancelUnlock()` [6](#0-5) .

As a result, an attacker who calls `forceUnLock()` on a matured cooldown slot reduces their real locked/staked balance (`getUserTotalLocked` / `MasterMagpie.stakingInfo(vlMGP,user).staked`) without the referral factor being recalculated. Their stale `userInfo.factor` (computed from a larger prior balance) remains in `totalBoostFactor`, inflating their share of the boosted referral reward pool (`_calBoosted`) relative to their now-smaller real stake, and correspondingly diluting/skewing the boosted rewards owed to other referrers whose factors are correctly proportioned. This is a straightforward accounting-state desync, not merely an internal bookkeeping nit, since `_calBoosted` directly determines allocation of real reward tokens (`refererAmount`/`refereeAmount` in `ReferralStorage`) [7](#0-6) .

### Impact Explanation
The referral boost mechanism distributes a shared reward pool proportionally to `userInfo.factor / totalBoostFactor` [8](#0-7) . Since `forceUnLock`/`unlock`/`cancelUnlock` can reduce a user's real stake while leaving their `factor` artificially high, the attacker (if they have an active referral code) continues to receive an inflated boosted share of referral rewards disproportionate to their real locked MGP, at the expense of other referrers' rightful share — a theft of unclaimed yield from the shared boost pool. This matches the "High - Theft of unclaimed yield" impact category, though the magnitude is bounded by the referral reward pool size and the attacker's prior factor vs. others'.

### Likelihood Explanation
No privileged role is required: any user who has activated the referral feature (obtained a `myCode`) and has an unlock slot that has matured can call `forceUnLock()` (or `unlock()`/`cancelUnlock()`) directly. The only precondition is having previously locked MGP and started an unlock, then waiting for the slot to mature (or be in cooldown for `cancelUnlock`) — a normal, cheap, and repeatable user flow. The "exactly one second after maturity" detail affects only the penalty pricing curve in `expectedPenaltyAmount`, not the core factor-desync bug, which triggers on every call to these three functions.

### Recommendation
Add `if (referralStorage != address(0)) IReferralStorage(referralStorage).updateTotalFactor(msg.sender);` at the end of `forceUnLock()`, `unlock()`, and `cancelUnlock()` in `VLMGP.sol`, mirroring the calls already present in `_lock()` and `startUnlock()`, so that the referral factor and `totalBoostFactor` are refreshed on every code path that changes a user's locked balance.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, and `ReferralStorage`; wire `referralStorage` into `VLMGP` via `setReferralStorage`.
2. User A activates a referral code (`myCode != 0`), locks `X` MGP via `lock()` → assert `userInfos[A].factor == sqrt(X)` and `totalBoostFactor` includes it.
3. User A calls `startUnlock(X)` → factor recalculated (still X since slot pending) → capture `totalBoostFactor` snapshot.
4. Warp time to `slot.endTime + 1`.
5. User A calls `forceUnLock(0)`.
6. Assert: `getUserTotalLocked(A) == 0` and `MasterMagpie.stakingInfo(vlMGP, A).staked == 0`, but `userInfos[A].factor == sqrt(X)` (unchanged, stale) and `totalBoostFactor` still includes the stale `sqrt(X)` term — demonstrating the divergence.
7. Trigger a referral reward harvest event and show User A still receives a boosted share (`_calBoosted(A) > 0`) despite having zero real locked balance, confirming theft of yield from other referrers.
8. Repeat steps for `unlock()` and `cancelUnlock()` to show the same stale-factor divergence.

    function updateTotalFactor(address _account) external override _onlyVlMGP {
        UserInfo storage userInfo = userInfos[_account];
        if (userInfo.myCode == bytes32(0)) return; // user did not activate referral feature
        
        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
        userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt);

        totalBoostFactor += userInfo.factor;
    }
