### Title
SignableTransaction::new computes fee/weight without the OP_RETURN `data` output, producing transactions paying a lower effective fee rate than requested - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an OP_RETURN output carrying caller-supplied `data` onto `tx_outs`, but computes the transaction weight/vbytes — and therefore `needed_fee` — from `payments` only. The resulting transaction is larger than the weight used for fee calculation, so the committed fee buys a lower effective feerate than `fee_per_vbyte` and can fall below the minimum relay rate. Analogous to the reported bug class (delivering an asset in a form the recipient/context cannot handle), the release transaction is constructed such that the Bitcoin network may not accept it: the funds it was meant to deliver never arrive, even though the inputs are committed to this transaction's outpoints/signature.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

```rust
// tx_outs already contains the OP_RETURN data output pushed above
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds a template transaction whose `output` list is only `payments` (plus optional `change`). The `data` OP_RETURN output — up to ~91 bytes of serialized output (8-byte value, script, pushdata) — is never included in the weight or in the `MAX_STANDARD_TX_WEIGHT` check. The same omission exists in the change branch (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`), so both `needed_fee` and `fee_with_change` underestimate the real transaction size by up to ~90 vbytes.

A caller paying the default minimum relay feerate (where `needed_fee >= 1 sat/vbyte * vbytes`) ends up broadcasting a transaction whose actual feerate is below `DEFAULT_MIN_RELAY_TX_FEE`, making it a non-relayable transaction that no node will propagate or mine. The inputs were consumed by the signed transaction (and `Prevouts::All` binds the signatures to these exact prevouts/amounts), yet the payment outputs are never delivered — the economic equivalent of transferring the asset to a destination that cannot receive it.

### Impact Explanation
An attacker who controls the `data` field (e.g., a user supplying burn/withdrawal metadata up to the 80-byte cap) can force a maximal ~90 vbyte fee shortfall. For transactions built at or near the minimum relay feerate, the signed transaction is rejected by every standard node: the payment is never received on chain even though a valid signed transaction exists and the signers consider the spend committed. Recovery requires reconstructing and re-signing the entire transaction with a correct fee, and the discrepancy is silent — `needed_fee()`/`fee()` both report consistent-looking values because `fee()` is computed from the real (larger) outputs only implicitly via `prevouts - outputs`, masking that the weight accounting was wrong.

### Likelihood Explanation
The trigger requires only that `data` be present and the chosen `fee_per_vbyte` be near the minimum relay rate — a routine configuration. `data` is an untrusted, attacker-sized input bounded only by the 80-byte `TooMuchData` check. No collusion, privileged access, or timing is needed. The defect is deterministic: every transaction with an OP_RETURN output undercounts its size.

### Recommendation
Include the `data` output in the template transaction used by `calculate_weight_vbytes` (e.g., build the output list as `payments + data + change`), or add a conservative fixed bound for the OP_RETURN output's serialized size to the weight/vbytes computation. Ensure both the `needed_fee`/`fee_with_change` paths and the `MAX_STANDARD_TX_WEIGHT` check account for the data output.

### Proof of Concept
1. Construct inputs totaling `payment + minimum_fee + DUST + epsilon`.
2. Call `SignableTransaction::new(inputs, &payments, change, Some(vec![0u8; 80]), 1)`.
3. `calculate_weight_vbytes` returns vbytes excluding the ~91-byte OP_RETURN output; `needed_fee ≈ vbytes` (passes `TooLowFee`).
4. The assembled `self.tx` includes the OP_RETURN output, so `tx.vsize()` ≈ `vbytes + 22` while the fee paid ≈ `vbytes` sats, i.e., < 1 sat/vbyte.
5. Broadcasting the signed transaction is rejected by Bitcoin Core policy (`min relay fee not met`), so the intended recipient never receives the funds despite a fully valid signature over `Prevouts::All`.

Uncertainty note: I verified the omission statically against `calculate_weight_vbytes` and the `tx_outs` construction, but did not execute a regtest broadcast; the minimum-relay rejection threshold depends on node policy defaults.
