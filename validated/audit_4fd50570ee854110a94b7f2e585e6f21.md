### Title
Trampoline credential helper trusts attacker-supplied `host`/`url` fields, allowing hooks in a malicious clone to exfiltrate real GitHub tokens - (File: app/src/lib/trampoline/trampoline-environment.ts)

### Summary
The RocketPool bug stems from a function that trusts data/callbacks originating from an untrusted party (the withdrawal address) without validating that the *recipient* the funds are being sent to matches the *intended* invariant. The Desktop analog: the trampoline credential helper trusts the `host`/`url` fields supplied in the incoming git-credential-protocol request without validating that they match the remote the current git operation is actually targeting, and this credential helper is reachable from any git subprocess spawned during a clone/fetch/checkout — including attacker-controlled hooks and filters bundled in a malicious repository.

### Finding Description
When Desktop performs a git network operation it calls `withTrampolineEnv`, which sets `GIT_CONFIG_PARAMETERS` to force `credential.helper=desktop` and exports `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` into the git process environment: [1](#0-0) 

These environment variables are inherited by every child process git spawns for that operation, including repository-controlled hooks (`post-checkout`, `post-merge`, etc.) and filter/smudge commands configured via `.gitattributes`/`.lfsconfig`. Any such child process can simply run `git credential fill` (or speak the protocol directly to the trampoline TCP server) to request credentials.

On the Desktop side, `getCredentialUrl()` builds the target endpoint purely from attacker-controllable fields (`url`, or `protocol`+`host`+`path`) taken from the credential request body — there is no check that this host corresponds to the repository/remote that the current operation was actually launched for: [2](#0-1) 

`getCredential()` then uses that attacker-chosen endpoint to look up a matching GitHub account and, if found, merges the real account login/OAuth token into the returned credential: [3](#0-2) [4](#0-3) 

The trampoline server itself only checks that the token is *structurally valid* (`isValidTrampolineToken`), not that the request's target host is consistent with the operation the token was minted for: [5](#0-4) 

So a hook shipped inside a cloned/fetched repository that runs during that same git invocation (and therefore inherits the trampoline env vars) can request `protocol=https\nhost=github.com\n` regardless of what remote the user actually cloned, and receive the user's real `github.com` OAuth token back from Desktop's credential store.

### Impact Explanation
This breaks the invariant that credentials handed out via the trampoline should only ever be released for the endpoint actually being operated on. A malicious repository can smuggle a hook or LFS filter that queries the credential helper for `host=github.com` (or any GHE endpoint the victim has signed into) and exfiltrate the resulting OAuth token over the network from within the hook process — full account takeover potential, matching the "credential/token exfiltration" impact category.

### Likelihood Explanation
The attacker only needs the victim to clone/fetch/checkout a crafted repository through Desktop (an unprivileged, expected user action) — no local access, admin rights, or social engineering beyond opening a repository is required, since post-checkout-style hooks execute automatically as part of normal git operations invoked by Desktop.

### Recommendation
Bind the trampoline token to the specific remote/endpoint the git operation was started for (not just to a generic "valid token" check), and have `getCredential`/`getCredentialUrl` reject or ignore credential requests whose `host`/`url` does not match the endpoint associated with that specific trampoline token/operation, instead of trusting attacker-supplied protocol fields to select which stored account/token to hand back.

### Proof of Concept
1. Attacker creates a public repository containing a `post-checkout` hook (or a `.gitattributes` clean/smudge filter) that runs:
   `git credential fill <<< $'protocol=https\nhost=github.com\n'` and exfiltrates the resulting `username=`/`password=` (the real OAuth token) to an attacker server.
2. Victim, signed into GitHub Desktop with a `github.com` account, clones or fetches the attacker's repository.
3. Desktop's `withTrampolineEnv` sets `GIT_CONFIG_PARAMETERS=... credential.helper=desktop` and `DESKTOP_TRAMPOLINE_TOKEN` for the git process tree of the clone/fetch operation.
4. During checkout, git invokes the attacker's hook, which inherits these env vars and calls `git credential fill` with `host=github.com`.
5. Desktop's trampoline server accepts the request (token is structurally valid), `getCredentialUrl` parses `host=github.com` from the attacker-controlled request, `getGitHubCredential` matches the victim's real GitHub account, and the victim's OAuth token is written back to the hook's stdout — which the attacker's script then sends off-box.

**Uncertainty:** I could not fully verify within the indexed code whether Desktop disables hook execution (e.g., via `core.hooksPath`/`--no-verify`-equivalent) for clone/fetch/checkout operations it performs; no such hardening was found via search, but a background Devin session with full repo access would be needed to confirm hook execution behavior and any existing mitigations (e.g., token scoping per remote) before treating this as fully confirmed.

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}
