### Title
Reward forfeiture mechanism permanently disabled in `mWOMSVBaseRewarder` due to broken `_calExpireForfeit` calculation - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` is supposed to mirror the sibling contract `vlMGPBaseRewarder._calExpireForfeit`, which reduces a user's claimable reward based on how much of their stake is still "fully locked" versus in cooldown/early-unlock, and redirects the forfeited portion back into the reward pool for the benefit of remaining stakers. In `mWOMSVBaseRewarder` the percentage lookup was dropped, so the function is a permanent no-op: it always computes a forfeit of zero, meaning users who should be penalized for unlocking mWOMSV early instead receive 100% of accrued rewards, and the honest stakers who remain locked never receive the redistributed forfeited yield they are entitled to.

### Finding Description
In `vlMGPBaseRewarder.sol`, the forfeiture percentage is derived from the locker's live state: [1](#0-0) 
```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
```

The mWOMSV locker contract, `mWomSV.sol`, exposes the exact same kind of percentage function, computing the fraction of a user's mWOMSV that is still fully locked versus in cool-down (partial unlock) at any given moment: [2](#0-1) 

However, `mWOMSVBaseRewarder._calExpireForfeit` never calls this function on `mWOMSV`. Instead it sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount` is always computed as `_amount - _amount = 0`: [3](#0-2) 
```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
    return forfeitAmount;
}
```

This function is invoked from `_sendReward`, which is reached by an unprivileged wallet calling `getReward`: [4](#0-3) 

Because `forfeitAmount` is always zero, the `if(forfeitAmount > 0) _queueNewRewardsWithoutTransfer(...)` branch that redistributes forfeited yield to remaining stakers is dead code — it can never execute.

### Impact Explanation
The forfeiture design intends that any user who unlocks mWOMSV early only receives a partial share of accrued rewards, with the remainder redistributed as extra yield to users who keep their tokens locked. Because the percentage check is hard-coded to 100% rewardable, this redistribution never happens: locked stakers permanently lose the forfeited-yield share they are economically entitled to under the protocol's own reward design, while early unlockers claim rewards they should not be entitled to in full. This is a protocol-level economic/accounting break in the yield-forfeiture logic that any unprivileged mWOMSV staker can trigger simply by calling the normal, unprivileged `getReward`/harvest path, permanently misallocating (freezing from its intended recipients) a portion of unclaimed yield.

### Likelihood Explanation
The bug is deterministic and triggers on every single reward claim from any mWOMSV staking user — no special conditions, front-running, or timing are required. It is reached through ordinary, unprivileged user flows (`getReward`/harvest of mWOMSV staking rewards), not through any admin or governance action.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to compute `rewardableAmount` from the mWOMSV locker's actual live cooldown/lock ratio, mirroring `vlMGPBaseRewarder`:
```solidity
uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
```
so the forfeiture and redistribution logic actually engages for users unlocking early.

### Proof of Concept
1. User A stakes mWOMSV and begins the unlock/cooldown process (partial rewardable percentage < 100%, as reflected by `mWomSV.getRewardablePercentWAD`).
2. User A calls `getReward`, which triggers `_sendReward` → `_calExpireForfeit(userA, pendingReward)`.
3. Because `_calExpireForfeit` always sets `rewardableAmount = _amount`, `forfeitAmount` is always `0`, so User A receives the full pending reward with no penalty, regardless of their unlock status.
4. Because `forfeitAmount` is always `0`, `_queueNewRewardsWithoutTransfer` is never invoked, so honest locked stakers never receive the forfeited yield that the protocol design intends to redistribute to them — a permanent loss of that expected yield share. [5](#0-4)

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
