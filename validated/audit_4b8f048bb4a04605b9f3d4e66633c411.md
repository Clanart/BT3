## Title
Server-Side Request Forgery (SSRF) via DataLayer mirror URLs enables port scanning of internal/local network - (File: chia/data_layer/download_data.py)

### Summary
Any Chia wallet user who owns a DataLayer store can call the `add_mirror` RPC to register arbitrary attacker-controlled URLs (including `http://127.0.0.1:<port>/`, `http://169.254.169.254/...`, or internal RFC1918 addresses) as mirror server URLs for that store. These URLs are published on-chain via `dl_new_mirror` and later fetched by any other node's DataLayer service that subscribes to (or owns/mirrors) the same store. `DataLayer.fetch_and_validate()` reads mirror URLs from the wallet and passes them unchecked into `insert_from_delta_file()` → `download_file()` → `http_download()`, which issues an outbound `aiohttp` GET request to `server_info.url + "/" + filename` with no host/IP allowlist or blocklist. This is directly analogous to the Discourse webhook SSRF (BIT-discourse-2022-39241): a low-privileged actor (any DataLayer store owner, i.e., any wallet user) supplies a URL that a victim's node will fetch, enabling port enumeration of the victim's local host and internal network.

### Finding Description
- `add_mirror()` in `chia/data_layer/data_layer.py` lets a store owner register any URL as a mirror, with only a non-empty check (`if not urls: raise ...`), and pushes it on-chain via `wallet_rpc.dl_new_mirror`: [2](#0-1) 
- Any node subscribing to (or owning/mirroring) that store id will discover these mirrors through `update_subscriptions_from_wallet()`, which pulls `mirror.urls` straight from wallet RPC and stores them as subscription server URLs without any validation of scheme or destination host: [3](#0-2) 
- During periodic sync, `fetch_and_validate()` selects one of these `servers_info` entries and calls `insert_from_delta_file()`, which calls `download_file()`: [4](#0-3) 
- `download_file()` (no plugin downloader configured — the default path) calls `http_download()` directly with the attacker-supplied `server_info.url`: [5](#0-4) 
- `http_download()` performs an unrestricted `aiohttp.ClientSession().get(server_info.url + "/" + filename, ...)` request — there is no check against private/loopback/link-local IP ranges (no equivalent of Discourse's `blocked_ip_blocks`/`DISCOURSE_BLOCKED_IP_BLOCKS`): [1](#0-0) 

Because the request/response timing and HTTP status/exception behavior (`ClientConnectorError` vs successful response vs timeout, as handled in `fetch_and_validate()`'s exception handling) differ observably, the attacker can determine open vs closed/filtered ports on the victim's local host or internal network — exactly the port-enumeration primitive described in the referenced Discourse advisory.

### Impact Explanation
This lets an unprivileged wallet user (anyone who can create/own a DataLayer store and add mirrors) turn any other DataLayer-subscribing node into an SSRF proxy: it can be used to enumerate open ports on `127.0.0.1` (potentially reaching other local services such as the node's own RPC ports, other loopback services), on internal/private network hosts, or probe arbitrary Internet hosts while masking the true origin of the probe (using the victim node as a proxy). This is a High-severity Server-Side Request Forgery matching the reported bug class.

### Likelihood Explanation
Likelihood is high: any wallet user can create a DataLayer store and add mirrors with `add_mirror()`; no special permission beyond normal wallet/DataLayer usage is required. Any peer that subscribes to that store id (a normal, expected DataLayer usage pattern for data sharing) will automatically fetch from the malicious mirror URL during its periodic `periodically_manage_data()` / `update_subscription()` / `fetch_and_validate()` cycle.

### Recommendation
Validate and restrict mirror/server URLs before making outbound requests in `http_download()` (and the plugin `download_file()`/`get_downloader()` paths): resolve the hostname and reject requests targeting loopback, link-local, and private (RFC1918) address ranges unless explicitly allow-listed by the node operator (mirroring Discourse's `blocked_ip_blocks`/env-var override approach). Consider validating URLs at `add_mirror()` time as well, and/or enforcing an operator-configurable blocklist (e.g., `DATALAYER_BLOCKED_IP_BLOCKS`) applied consistently across `download_file()`, `http_download()`, and `get_downloader()`.

### Proof of Concept
1. Attacker creates a DataLayer store and calls `add_mirror(store_id, urls=["http://127.0.0.1:6379"], amount=..., fee=...)` (or targets an internal victim-network IP/port) — this publishes the mirror on-chain via `dl_new_mirror`.
2. Victim node subscribes to (or already owns/mirrors) the same `store_id` as part of normal DataLayer usage.
3. Victim's `periodically_manage_data()` loop eventually calls `update_subscription()` → `update_subscriptions_from_wallet()`, pulling the malicious mirror URL, then `fetch_and_validate()` → `insert_from_delta_file()` → `download_file()` → `http_download()`.
4. `http_download()` issues `GET http://127.0.0.1:6379/<filename>` from the victim node. By observing whether the request results in a connection error (`aiohttp.client_exceptions.ClientConnectorError`, logged in `fetch_and_validate()`), a timeout, or an HTTP response/`MaxDeltaFileSizeExceededError`, the attacker (who controls the store and can add many mirrors with different `host:port` combinations) can infer which internal ports are open on the victim's host, achieving port enumeration analogous to the reported Discourse webhook SSRF.
