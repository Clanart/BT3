### Title
`multisig` verifies only the prevout `script_pubkey`, so a forged `ReceivedOutput` amount makes the threshold sign a transaction committing to false input values - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The external report's bug class is *trusting a derived/claimed quantity instead of the authoritative value actually returned by the operation*. In bitcoin-serai, `SignableTransaction::multisig` treats the `prevouts` carried inside each `ReceivedOutput` as the source of truth for the input amounts. It only checks that the prevout's `script_pubkey` matches the (offset) group key — it never checks `prevouts[i].value`. Those attacker-controlled bytes (reachable via `ReceivedOutput::read`, which performs no validation beyond consensus-decoding the `TxOut`) are then committed to the signature via `Prevouts::All` in `TransactionSignMachine::sign`. The result is a fully-formed, threshold-signed transaction whose BIP-341 sighash commits to fabricated input amounts, which the Bitcoin network will reject — the signed spend is unspendable.

### Finding Description
`ReceivedOutput::read` deserializes `offset`, `output` (a `TxOut` including `value`), and `outpoint` from arbitrary bytes with no sanity checks (`networks/bitcoin/src/wallet/mod.rs:122-134`). `SignableTransaction::new` sums `input.output.value` into `input_sat` and derives the change/fee from it (`send.rs:175`, `send.rs:228`). `multisig` verifies only `p2tr_script_buf(offset.group_key()) == self.prevouts[i].script_pubkey` (`send.rs:276-279`) — the value field is never authenticated against the real UTXO. `sign` then computes `taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), TapSighashType::Default)` (`send.rs:375-390`), so the signature is bound to whatever `value` the supplied bytes claimed — the analog of `claimAmount` being computed from an assumed quantity rather than the actual claimed assets.

### Impact Explanation
- **Understated `value`**: `input_sat` is too small → change is reduced or dropped, and the difference is classified as fee; the signature commits to a prevout amount that does not match the chain → consensus-invalid transaction.
- **Overstated `value`**: an inflated change output is created and signed; the transaction spends more than the inputs contain → consensus-invalid transaction.

In both directions the multisig produces a signed transaction that cannot be broadcast and the signing session is burned. Since `NeededFee`/change math and the sighash both trust the unverified serialized amount (the "balance delta" analog), funds are effectively reported spendable in a form that is not spendable, and the threshold must detect and redo the ceremony.

### Likelihood Explanation
Any party able to feed bytes to `ReceivedOutput::read` (listed in-scope as an untrusted input path) can supply a `TxOut` whose `value` diverges from the real UTXO. No key compromise, malicious validator, or collusion is required — honest signers run `multisig`/`sign` on the forged `SignableTransaction` and emit valid signature shares for a message committing to false amounts. The check that would catch it (comparing `prevouts[i].value` to a trusted chain lookup, or re-deriving the amount) does not exist.

### Recommendation
In `SignableTransaction::multisig` (or `new`), authenticate the full prevout — not just `script_pubkey` — by verifying `output.value` against the confirmed transaction referenced by `outpoint`, or reject `ReceivedOutput`s that did not originate from `Scanner::scan_transaction`/`scan_block` (e.g., mark deserialized outputs as unverified). Failing that, `sign` should treat `Prevouts::All` contents as untrusted and refuse to sign when the committed amount cannot be independently confirmed.

### Proof of Concept
1. Observe a real deposit UTXO to the multisig's P2TR script: `value = 100_000` sats, `outpoint = (txid, 0)`, `offset = s`.
2. Craft bytes for `ReceivedOutput::read` with `offset = s`, `outpoint = (txid, 0)`, but `output.value = 10_000_000` (or `1_000`).
3. Call `SignableTransaction::new(vec![forged], &payments, Some(change), None, fee)` — `input_sat` uses the forged `10_000_000`, producing an inflated change output.
4. `multisig(keys)` succeeds because only `script_pubkey` is checked (`send.rs:277`); `sign`/`complete` produce a validly-signed transaction.
5. Broadcast fails consensus validation: the committed prevout amounts in `Prevouts::All` disagree with the real UTXO — the signed spend is unspendable and the signing round is wasted.
