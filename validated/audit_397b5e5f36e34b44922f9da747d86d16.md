## Title
`decode_receipt_relayer` accepts an unvalidated zero-address / empty signer as a "delivering relayer," unlike its sibling decoder which explicitly rejects it - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
The bug report's core pattern is: a privileged-role/identity field gets set to the zero address, and downstream code treats that zero value as a legitimate, meaningful identity rather than "unset/invalid." The Hyperbridge relayer pallet has the exact same shape in its receipt-decoding logic used to attribute fee/reward payouts to a delivering relayer.

### Finding Description
`Pallet::decode_epochs_slot_address` (outbound consensus path) explicitly treats a decoded zero address as "no value" and returns `None`, with an accompanying regression test and comment stating this is deliberate defence-in-depth "so a malicious actor can't claim a reward by writing zeros": [1](#0-0) [2](#0-1) 

`Pallet::decode_receipt_relayer`, the sibling decoder used for the **normal per-request relayer fee accumulation path (`accumulate_fees`) and the outbound-request delivery claim**, has no equivalent zero-value/zero-address guard — it just RLP/ABI-decodes whatever bytes are in the proof and returns them as the delivering relayer's identity, for all three destination kinds (Pharos, generic EVM, Substrate): [3](#0-2) 

This decoded value is used directly to attribute delivery/beneficiary identity in two places:
1. `process_outbound_request_delivery_claim`, where `delivered_by` from `decode_receipt_relayer` is compared against the signature recovery output before paying out the treasury reward: [4](#0-3) 
2. The core `accumulate_fees` flow (via `Self::verify_withdrawal_proof` → the equivalent decode step referenced by `accumulate.rs`), which credits `Fees::<T>` for the decoded relayer/beneficiary identity.

The proof-verification helper `verify_withdrawal_proof` returns `Ok(None)` for genuinely absent trie keys (mapped upstream to `OutboundDeliveryNotProven`/similar), so an *unset* slot is already filtered out before reaching the decoder. The residual risk is specifically bytes that decode successfully to the all-zero address/signer (e.g., a 21-byte RLP string `0x94` followed by 20 zero bytes, or an all-zero 32-byte Pharos slot) — the same byte pattern the sibling `decode_epochs_slot_address` function explicitly special-cases and rejects, but `decode_receipt_relayer` does not.

### Impact Explanation
If a state-proof value decodes to the zero address/zero-length signer through `decode_receipt_relayer` and is accepted as `delivered_by` / the accumulated address, the pallet would treat "the zero address delivered this request" as valid attribution. Combined with the well-known `ecrecover`/signature-recovery footgun where a malformed `(v, r, s)` triple can recover to `address(0)` without erroring, an attacker who can supply a forged/invalid signature that recovers to `address(0)` — and who can get a genuinely zero-valued slot into a proof value (e.g., a slot that was explicitly written with the zero address at some point, rather than simply never written) — could satisfy the `recovered == delivered_by` equality check in `process_outbound_request_delivery_claim` at line 173, or the analogous check in `accumulate_fees`, causing reward/fee funds to be paid or credited against a spoofed "zero-address relayer" identity instead of being rejected as a false/absent proof. This is structurally the same "zero value treated as a valid privileged identity" defect as the AlgebraFactory report, applied to Hyperbridge's relayer reward/fee custody rather than an admin role.

### Likelihood Explanation
This is a real code asymmetry with test-documented awareness of the exact same defect class in a sibling function, which increases confidence it is a genuine oversight rather than an intentionally-safe design. However, I could not fully verify the exploitability chain within the available context: I was unable to locate the `Signature::verify` implementation (in the `crypto_utils` crate) to confirm whether it can return `address(0)`/an empty signer without erroring on a malformed signature, and I could not confirm a concrete on-chain path by which a `RequestReceipts[commitment]` (or Substrate equivalent) slot would ever be populated with an explicit zero value that a state proof could then present (as opposed to simply being absent, which is already filtered separately). Both of these are necessary preconditions for actual fund impact, and neither is confirmed from the code available in this index.

### Recommendation
Add the same zero-value guard used in `decode_epochs_slot_address` to `decode_receipt_relayer` for all three branches (Pharos, generic EVM, Substrate), returning an error/`None` when the decoded relayer bytes are the zero address or an all-zero/empty signer, before that value is compared against a recovered signature or credited in `Fees::<T>`. Additionally, confirm that `Signature::verify` in `crypto_utils` cannot return the zero address / an empty signer for malformed input, and add an explicit rejection if it can.

### Proof of Concept
Not constructible with certainty from the available index: a full PoC requires (1) confirming `Signature::verify`'s behavior on malformed EVM signatures (potential `ecrecover`-style zero-address return), and (2) a concrete transaction sequence that causes a `RequestReceipts[commitment]` slot to hold an explicit zero address that survives into a storage proof. Neither could be verified with the tools available; flagging this as the primary residual uncertainty rather than asserting a working exploit.

```rust
impl<T: Config> Pallet<T> {
	/// Decode a proven `RequestReceipts[commitment]` value into the delivering
	/// relayer's bytes. EVM stores the address RLP encoded, substrate stores the
	/// signer bytes or a signature to recover the signer from. Used by both fee
	/// accumulation and the outbound request delivery claim.
	pub fn decode_receipt_relayer(state_id: StateMachine, raw: &[u8]) -> Result<Vec<u8>, Error<T>> {
		match state_id {
			s if crate::is_pharos(&s) =>
				if raw.len() == 32 {
					Ok(Address::from_slice(&raw[12..]).0.to_vec())
				} else {
					Err(Error::<T>::ProofValidationError)
				},
			s if s.is_evm() => {
				use alloy_rlp::Decodable;
				Ok(Address::decode(&mut &*raw)
					.map_err(|_| Error::<T>::ProofValidationError)?
					.0
					.to_vec())
			},
			s if s.is_substrate() => {
				use codec::Decode;
				let bytes =
					<Vec<u8>>::decode(&mut &*raw).map_err(|_| Error::<T>::ProofValidationError)?;
				Ok(if bytes.len() > 32 {
					Signature::decode(&mut &*bytes)
						.map_err(|_| Error::<T>::SignatureDecodingError)?
						.signer()
				} else {
					bytes
				})
			},
			_ => Err(Error::<T>::MismatchedStateMachine),
		}
	}
```
