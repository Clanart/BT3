## Title
Unchecked ERC-20 return value in escrow withdrawal and dust sweep leads to permanent loss of escrowed/solver funds — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed tokens and sweeps protocol dust using a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the *call itself* did not revert (`success`), never decoding/validating the ERC-20 boolean return value. This is the exact bug class from the seed report (unsafe `transfer`/`transferFrom` instead of `safeTransfer`/`safeTransferFrom`): for a "weird ERC20" that returns `false` on failure instead of reverting, `success` will still read `true`, so the contract treats the transfer as successful, finalizes escrow accounting, and emits a success event — while the beneficiary receives nothing.

### Finding Description
In `withdraw()`: [1](#0-0) 

- `_filled[body.commitment] = beneficiary;` is set unconditionally at the start of `withdraw()`.
- For each escrowed token, the contract issues a raw call: `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); if (!success) revert TransferFailed();`
- `success` only reflects whether the external call reverted — it does **not** decode the returned `bool` from `IERC20.transfer`. Per the `weird-erc20` catalogue (e.g. ZRX-style tokens), some ERC-20 implementations return `false` on failure without reverting.
- If `success == true` but the token actually returned `false` (transfer failed silently), execution proceeds to `_orders[body.commitment][token] -= amount;`, permanently zeroing/decrementing the escrow record and emitting `EscrowReleased`/`EscrowRefunded` — even though the beneficiary never received the tokens.
- The exact same unchecked pattern also releases transaction fees: `(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees)); if (!success) revert TransferFailed();` [2](#0-1) 

- And identically in the `SweepDust` handler inside `onAccept()`: [3](#0-2) 

By contrast, the canonical (non-Tron) EVM `IntentGatewayV2.sol`, `intentsv2/IntentsBase.sol`, and `intentsv2/ExtrinsicIntents.sol` consistently use OpenZeppelin's `safeTransfer`/`safeTransferFrom`, which decode and assert the boolean return value: [4](#0-3) 

The Tron port diverged from this safe pattern and reintroduced exactly the vulnerability class described in the seed report — checking only that a call "succeeded" rather than that the token transfer actually returned `true`.

### Impact Explanation
Once escrow accounting is finalized (`_orders[...] -= amount`, `_filled[commitment] = beneficiary`), there is no other code path to reclaim the funds — `onAccept`/`onGetResponse` for the same commitment will revert with `UnknownOrder()` on any retry since the escrow balance already reads zero. For any input/output token that is a non-reverting ERC-20 (a documented and common pattern), a user's escrowed funds, a solver's expected settlement, or accumulated protocol/transaction fees can be silently lost while the contract still emits success events — a direct loss-of-funds impact against the live bounty's "stealing or loss of funds" and "logic attacks" criteria, requiring no malicious relayer, prover, or admin action, only the natural behavior of a non-standard input token already supported by the generic `TokenInfo.token` field.

### Likelihood Explanation
Likelihood is high in effect any time the escrowed/fee token deviates from strict ERC-20 revert-on-failure semantics (a known, common real-world token class), and the contract places no restriction on which ERC-20 addresses may be used as `order.inputs`/`order.output.assets`/fee token. No privileged actor is required — this triggers automatically through the normal `onAccept`/`withdraw`/`SweepDust` flow whenever such a token is involved, exactly mirroring the original Cooler `clear()` finding.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` escrow release, fee release, and the `SweepDust` branch in `onAccept()`) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase.sol`, `ExtrinsicIntents.sol`, main `IntentGatewayV2.sol`). `safeTransfer` reverts unless the call succeeds *and* the token either returns no data or returns `true`, correctly handling non-standard ERC-20 tokens.

### Proof of Concept
1. Create an order whose input/output or fee token is a non-standard ERC-20 that returns `false` on a failed `transfer` (e.g., insufficient contract balance) instead of reverting — the classic `weird-erc20` "no revert on failure" pattern.
2. Arrange for the token contract itself to hold insufficient balance to complete the transfer to `beneficiary` at withdrawal time (e.g., through a race, external drain, or blocklist/logic quirk in the token implementation causing `transfer` to internally fail-soft).
3. Hyperbridge delivers the `RedeemEscrow`/`RefundEscrow` post request; `onAccept()` calls `withdraw(body, ...)`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(success=true, data=abi.encode(false))` because the callee did not revert.
5. `if (!success) revert TransferFailed();` does not trigger; `_orders[body.commitment][token] -= amount;` executes, zeroing escrow; `EscrowReleased`/`EscrowRefunded` is emitted.
6. `beneficiary` never received the tokens, and the commitment is now finalized (`_filled` set, escrow zero) with no remaining path to recover the funds — permanent loss.
