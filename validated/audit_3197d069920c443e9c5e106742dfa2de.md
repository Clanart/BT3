## Title
Arbitrary local file read via tracked symlink in working-directory file rendering - (File: `app/src/lib/git/diff.ts`)

### Summary
GitHub Desktop deliberately guards several file-path operations against symlink-based sandbox escapes with `resolveWithin()`, which resolves a repo-relative path and rejects it if the `realpath()` of the result escapes the repository root (`app/src/lib/path.ts:36-73`, confirmed by dedicated symlink tests in `app/test/unit/path-test.ts:65-101`). This guard is applied to deep-link file opening (`app/src/ui/dispatcher/dispatcher.ts:1957-1972`) and to the Copilot conflict-context file reader (`app/src/lib/copilot-conflict-context.ts:390-408`). However, the working-directory file-content readers used for the Changes/diff view do **not** use this guard — they build the path with a plain `Path.join(repository.path, file.path)` and call Node's `fs.readFile`, which follows symlinks.

### Finding Description
`getWorkingDirectoryImage()` reads the on-disk bytes of a changed working-directory file to render an image diff: [1](#0-0) 

Similarly, `getNewFileContent()` (used to feed syntax highlighting for the text diff view) reads the working-directory file the same unguarded way: [2](#0-1) 

Both take `file.path`, a repository-relative path taken directly from `git status`/`git diff` output (see `AppFileStatusKind`/`WorkingDirectoryFileChange` populated by `app/src/lib/git/status.ts` and `app/src/lib/status-parser.ts`), and neither passes it through `resolveWithin()` before reading. Git natively supports committing symlinks (mode `120000`), and the test-parser fixtures in this repo explicitly model type-change entries for such symlinks (`app/test/unit/status-parser-test.ts:109-118`). When such a blob is checked out (`core.symlinks` enabled, the default outside these test fixtures), git materializes a real OS symlink in the working directory pointing to any path the attacker chooses (e.g. `~/.ssh/id_rsa`, `~/.aws/credentials`, or an absolute Windows path). Desktop's status/diff pipeline reports this symlink like a normal changed file (`WorkingDirectoryFileChange`), and both readers above will resolve the symlink implicitly via `fs.readFile`/`readPartialFile`, reading the *target's* contents rather than the tracked blob, and then rendering it in the UI (as a decoded image or as syntax-highlighted diff content).

This is the exact bug class from the report: a "preopen"-style boundary (the repository working directory) is assumed to be the file sandbox, but a symlink placed inside it — fully attacker-controlled since it comes from a cloned/fetched repository — lets Desktop follow the link and read a file outside that boundary.

### Impact Explanation
Cloning or checking out an attacker-controlled repository/branch/PR that contains a symlinked tracked file causes GitHub Desktop to read and expose (in the renderer, via the diff/image preview UI) the contents of an arbitrary file on the victim's machine that the current OS user can read — including credentials, SSH keys, or config files outside the repository. This satisfies the "attacker controls a cloned/fetched repository... and the result is file read outside the repo" criterion from the task's Valid Impact list.

### Likelihood Explanation
No special privileges, local access, or social engineering beyond normal GitHub Desktop usage (clone/fetch a repo, then click the changed file to view its diff/preview) are required. The existing `resolveWithin()` helper shows the maintainers are aware of and actively mitigate this exact symlink class elsewhere in the codebase, but the mitigation was not consistently applied to the working-directory image/text content readers used by the Changes view, which is one of the most commonly exercised code paths in the app.

### Recommendation
Route `getWorkingDirectoryImage()` and the working-directory branch of `getNewFileContent()` through `resolveWithin(repository.path, file.path)` (as already done in `copilot-conflict-context.ts` and `dispatcher.ts`) before reading, and treat a `null` result (path escapes the root, e.g. via a symlink) as "cannot render"/skip rather than following it. Consider also detecting symlink working-tree entries (mode `120000`) up front in the status/diff pipeline and rendering them as a distinct "symlink" change rather than attempting to read file contents at all.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink, e.g.:
   ```
   ln -s ~/.ssh/id_rsa secret.png
   git add secret.png
   git commit -m "add image"
   git push
   ```
2. Victim clones/fetches and checks out this repository/branch in GitHub Desktop (`core.symlinks` enabled, the default), or the attacker introduces the same change via a PR/branch the victim checks out.
3. Victim opens the repository's Changes/History view and selects `secret.png`.
4. `getWorkingDirectoryImage()` (`app/src/lib/git/diff.ts:926-937`) does `readFile(Path.join(repository.path, 'secret.png'))`, which follows the OS symlink and returns the bytes of `~/.ssh/id_rsa`; these bytes are base64-encoded and rendered/embedded in the diff view, exposing the private key content in the app UI (and to anything with access to that view, e.g. screen readers, screenshots, or renderer devtools).

```typescript
export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}
```

```typescript
async function getNewFileContent(
  repository: Repository,
  file: ChangedFile
): Promise<Buffer | null> {
  if (file.status.kind === AppFileStatusKind.Deleted) {
    return null
  }

  if (file instanceof WorkingDirectoryFileChange) {
    return readPartialFile(
      Path.join(repository.path, file.path),
      0,
      MaxHighlightContentLength - 1
    )
  } else if (file instanceof CommittedFileChange) {
    return getPartialBlobContents(
      repository,
      file.commitish,
      file.path,
      MaxHighlightContentLength
    )
  }

  return assertNever(file, 'Unknown file change type')
}
```
