### Title
Self-Forfeit-Recapture of Queued MGP/Bonus Rewards via Sole-Staker Withdraw/Relock - (File: rewards/vlMGPBaseRewarder.sol)

### Summary
When a user is the sole vlMGP locker in the protocol, fully unlocking their MGP forces `_sendReward` to compute a 100% forfeiture of their pending, non-yet-claimed rewards (because `getRewardablePercentWAD` returns 0 once `userTotalVlmgp == 0`). That forfeited amount is routed to `rewards[_rewardToken].queuedRewards` because `totalStaked() == 0` at that instant [1](#0-0) . The same user can then relock MGP, becoming the sole staker again, and trigger any subsequent forfeit/queue event to fold the previously queued forfeiture into `rewardPerTokenStored`, allowing them to claim it back in full via `getReward`, completely negating the intended penalty.

### Finding Description
`vlMGPBaseRewarder.totalStaked()` returns `IERC20(vlMGP).totalSupply()`, the protocol-wide vlMGP supply [2](#0-1) . `_sendReward` computes a forfeit amount from `_calExpireForfeit`, which is based on `vlMGP.getRewardablePercentWAD(_account)` [3](#0-2) . `getRewardablePercentWAD` returns `0` whenever the user has no locked and no cooling-down MGP (`userTotalVlmgp == 0`) [4](#0-3) , meaning a user who has fully exited forfeits 100% of any unclaimed reward balance sitting in `userRewards[token][account]`.

That forfeited amount is pushed via `_queueNewRewardsWithoutTransfer`, which checks `totalStaked() == 0` and, if true, simply accumulates it into `rewardInfo.queuedRewards` without updating `rewardPerTokenStored` [1](#0-0) . If the forfeiting account was the sole vlMGP locker in the whole protocol, `totalStaked()` is indeed `0` right after their full withdrawal completes.

The attacker can then relock MGP (`VLMGP.lock`), again becoming the sole staker (or at least a large-share staker), and trigger any subsequent event that calls `_queueNewRewardsWithoutTransfer` or `queueNewRewards` with `totalStaked() > 0` — this folds the entire previously queued (forfeited) amount into `rewardPerTokenStored`, calculated as `queuedRewards * 1e18 / totalStaked()` [5](#0-4) . Since the attacker is once again the (near-)sole staker, they capture nearly 100% of this redistributed amount via a normal `getReward` call, recovering the exact amount that was supposed to be permanently forfeited as an early-exit penalty.

No modifier or check prevents this: `getReward`/`getRewards` are gated only by `onlyMasterMagpie`, reachable permissionlessly through the user's own `unlock()`/`lock()`/claim flow via `MasterMagpie`; there is no minimum-holding-period, no burn of queued forfeitures, and no restriction preventing the same address who generated the forfeiture from later reabsorbing it.

### Impact Explanation
This breaks the intended semantics of the early-exit/forfeiture mechanism: forfeited yield is meant to be lost or redistributed to *other* long-term stakers as a penalty/incentive design, not returned to the forfeiting party. A user exploiting sole-staker timing (e.g., during low-liquidity periods, a fresh reward-token deployment, or by simply waiting until they are momentarily the only locker) can fully recapture their own forfeited MGP/bonus token rewards, netting strictly more than their genuine `earned()` entitlement would allow at time of forfeiture. This is a theft/permanent-defeat of an economic penalty mechanism, matching an "unclaimed yield" theft impact class.

### Likelihood Explanation
The core precondition — being the sole vlMGP locker across the entire protocol at the moment of full unlock — is restrictive in a mature, highly-used deployment, but is realistic in early launch phases, low-TVL periods, niche reward tokens with few holders, or via patient waiting for other lockers to fully exit. No privileged role is required: the entire exploit is composed of ordinary `lock`, `startUnlock`, `unlock`, and claim calls available to any EOA, and is fully repeatable each time the attacker can regain sole/majority-staker status.

### Recommendation
Do not allow a user's own forfeiture to be reclaimed by the same address that generated it. Options: (1) permanently burn/send forfeited amounts to a separate penalty-distribution destination instead of `queuedRewards`, decoupling it from the staker-proportional reward accounting; (2) snapshot and exclude the forfeiting user from claiming shares of `queuedRewards` derived from their own past forfeiture (e.g., track forfeiture provenance and skip crediting the same address); (3) require `totalStaked()` checks to also verify that the staker set has changed / a minimum time-lock before queued forfeitures can be folded into `rewardPerTokenStored`.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, and `vlMGPBaseRewarder` with a mock MGP/bonus reward token; make `attacker` the only account that ever locks MGP.
2. `attacker` calls `VLMGP.lock(amount)`; verify `totalStaked() == amount` on the rewarder.
3. Have `rewardManager` queue a reward via `queueNewRewards` so `attacker` accrues `earned() > 0`.
4. `attacker` calls `VLMGP.startUnlock(amount)`, waits `coolDownInSecs`, then calls `VLMGP.unlock(slotIndex)` — this triggers `multiclaimFor` → `getReward` → `_sendReward`, and because `getRewardablePercentWAD == 0` after full unlock, 100% of `earned()` is forfeited into `rewards[token].queuedRewards` (assert `queuedRewards == priorEarned` and `totalStaked() == 0`).
5. `attacker` relocks the same MGP via `VLMGP.lock(amount)` — `totalStaked() > 0` again, `attacker` sole staker.
6. Trigger any additional forfeit/queue event (e.g., repeat startUnlock/unlock of a trivial amount, or have `rewardManager` call `queueNewRewards` with 0/small amount) so `_queueNewRewardsWithoutTransfer`/`queueNewRewards`'s `else` branch folds `queuedRewards` into `rewardPerTokenStored` while `attacker` holds ~100% of `totalStaked()`.
7. `attacker` calls `getReward` again and asserts they receive (close to) the full previously-forfeited amount back, i.e., total MGP/bonus received across the whole round-trip exceeds what a single continuous non-exploitative `earned()` accrual would have produced — proving the forfeiture penalty was fully bypassed.

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);

    function _sendReward(address _rewardToken, address _account, address _receiver) internal {
        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;
            
        if (toSend > 0) {
            IERC20(_rewardToken).safeTransfer(_receiver, toSend);
            emit RewardPaid(_account, _receiver, toSend, _rewardToken);
        }

        if(forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken);
    }
