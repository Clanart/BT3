## Finding: Confirmed Vulnerability

The reported issue is real and reproducible from the code paths shown. Tracing the exact flow:

1. `WombatBribeManager.vote(...)` calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta))` for any pool the voter increases their vote weight on [1](#0-0) .
2. `BribeRewardPool.stakeFor` runs the `updateRewards` modifier (which settles the caller's reward snapshot against the *current* `rewardPerTokenStored`, i.e., before any bribe for this call is queued) and then immediately increments `totalSupply` and `_balances[_for]` [2](#0-1) .
3. `WombatBribeManager.voteAndCast` calls `vote()` first, then `castVotes()` in the same transaction [3](#0-2) .
4. `castVotes()` harvests the pool's bribes via `wombatStaking.vote(...)`, which ultimately calls `IBaseRewardPool(_rewarders[i]).queueNewRewards(rewardAmount, ...)` on the same `BribeRewardPool` [4](#0-3) .
5. `queueNewRewards` → `_provisionReward` computes the reward-per-token increment using `totalStaked()` **at the moment of the flush**, which now already includes the balance the attacker staked in step 2, within the same transaction [5](#0-4) .

Because `userRewardPerTokenPaid` was set to the pre-harvest `rewardPerTokenStored` in step 2, the attacker's freshly-added balance is fully eligible to earn from the reward-per-token delta produced by the bribe harvested in step 4 — despite having contributed zero time to the pool before that bribe accrued. This dilutes the share that pre-existing, time-committed voters would otherwise have received, and lets an attacker with any amount of votable vlMGP capture a slice of a large pending unsettled bribe in a single atomic `voteAndCast` call, with no special role required.

### Title
Stake-before-harvest ordering in `WombatBribeManager.voteAndCast` lets a last-second voter dilute bribe rewards - (File: rewards/BribeRewardPool.sol / wombat/WombatBribeManager.sol)

### Summary
`voteAndCast` calls `vote()` (which increases a voter's stake in `BribeRewardPool` via `stakeFor`) before `castVotes()` harvests and queues the pool's pending bribe via `queueNewRewards`. Since `_provisionReward` distributes the queued bribe pro-rata over `totalStaked()` measured *after* the new stake is added, an attacker who adds vote weight to a pool with a large unsettled bribe balance immediately shares in that bribe despite contributing zero time.

### Finding Description
`BribeRewardPool.stakeFor` (called from `WombatBribeManager.vote`) settles a user's existing reward snapshot via the `updateRewards` modifier and increases `totalSupply`/`_balances` in the same call, before any new bribe is queued [2](#0-1) . Immediately afterward, `castVotes()` triggers `queueNewRewards` → `_provisionReward`, which increases `rewardPerTokenStored` using `totalStaked()` at that instant — a value that already includes the attacker's newly staked balance [6](#0-5) . Because the attacker's `userRewardPerTokenPaid` was fixed to the pre-harvest value, the entire post-harvest `rewardPerToken` delta is credited to them on their full new balance, not weighted by the time that balance was actually staked before the bribe was earned. Existing `nonReentrant`/`onlyOperator`/`updateRewards` checks do not prevent this because the ordering issue is a design/sequencing flaw, not an access-control or reentrancy bug — `vote` is intentionally callable by any vlMGP holder with votable balance.

### Impact Explanation
Any voter can capture a disproportionate share of an epoch's harvested bribe by increasing their vote weight on a pool right before calling `castVotes` (or atomically via `voteAndCast`), diluting the rewards that voters who committed capital for the full epoch should have received. This is a redistribution of bribe rewards from long-term voters to opportunistic last-moment stakers — a real, quantifiable loss of unclaimed yield for existing stakers.

### Likelihood Explanation
Requires only that the attacker hold some amount of votable (locked) vlMGP and target a pool with a large pending unsettled bribe — both conditions are realistic and attacker-controlled (the delta amount and target pool). The exploit executes atomically within a single `voteAndCast` transaction, requiring no flash loan, front-running, or privileged role, and is repeatable every epoch/harvest cycle.

### Recommendation
Decouple stake changes from reward flushing within the same transaction for the affected epoch: e.g., snapshot/flush the queued bribe (`queueNewRewards`) for a pool **before** processing any new `stakeFor`/`withdrawFor` calls that arrive in the same `vote`/`voteAndCast` transaction, or require that newly added vote deltas only become reward-eligible starting from the *next* `castVotes` cycle (checkpoint the stake increase separately from the currently-accruing reward window).

### Proof of Concept
Hardhat test plan:
1. Deploy `BribeRewardPool`/`WombatBribeManager` test harness with an existing staker A holding a vote balance in pool P, and let a bribe (e.g., 1000 tokens) accumulate as pending/unsettled in `WombatStaking` for P.
2. Have attacker B (holding some votable vlMGP, zero prior vote weight in P) call `voteAndCast([P], [delta], false)` in a single transaction.
3. Assert: immediately after the transaction, `BribeRewardPool.earned(B, rewardToken) > 0` even though B's stake existed for zero blocks before the bribe was queued.
4. Assert: `earned(A, rewardToken) / A_balance` (per-token reward rate for the pre-existing staker) is measurably lower than it would be had B not joined before the flush (i.e., compare against a control run without B's `vote` call).
5. Table-test boundary deltas (very small delta, delta equal to A's full balance, delta forcing `totalSupply` to double) and confirm in every row that B's captured share of the bribe is nonzero and unweighted by time, violating the time-weighted invariant.
