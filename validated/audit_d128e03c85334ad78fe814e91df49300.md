### Title
Early return on undecodable share emits a blame `EncryptionKeyProof` before the message's proof-of-possession is verified, leaking another participant's ECDH shared key - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` queues each `EncryptedMessage`'s Schnorr proof-of-possession into a `BatchVerifier`, but returns `PedPoPError::InvalidShare { blame: Some(..) }` via `?` as soon as the decrypted bytes fail `C::F::from_repr` — before `batch.verify_with_vartime_blame()` ever runs. The returned `EncryptionKeyProof` contains the recipient's ECDH shared key `enc_key * msg.key`. An attacker who replays an honest participant's observed per-message key under a forged PoP therefore extracts the shared key for the honest message and decrypts a secret share that was never addressed to them. This is exactly the attack the code comments claim the PoP prevents; the early `?` bypasses it.

### Finding Description
The bug class in the Deno advisory — a sensitive-data channel exempted from a security check — maps directly onto PedPoP's blame channel: publishing an `EncryptionKeyProof` reveals the ECDH shared key for a message, and the PoP on `EncryptedMessage` exists solely to prevent an attacker from triggering that reveal with a co-opted key (crypto/dkg/pedpop/src/encryption.rs:83-90). [1](#0-0) 

In `Encryption::decrypt`, the PoP is only *queued* into the batch verifier — it is not verified. The function then computes `key = ecdh(&self.enc_key, msg.key)`, decrypts, and unconditionally builds `EncryptionKeyProof { key, dleq }` proving that `key` is the correct ECDH for `msg.key` under the recipient's registered `enc_pub_key` (crypto/dkg/pedpop/src/encryption.rs:479-500). [2](#0-1) 

In `KeyMachine::calculate_share`, the deserialized share is checked inline:

```rust
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
```

This `?` early-returns with `blame: Some(blame)` — the `EncryptionKeyProof` containing the ECDH point — before `batch.verify_with_vartime_blame()` at line 493 is reached, so the queued PoP for that message is never checked (crypto/dkg/pedpop/src/lib.rs:476-499). [3](#0-2) 

Attack: Eve observes Alice's `EncryptedMessage` to Bob (per-message public key `kG`, ciphertext encrypted under shared key `b·kG` where `b` is Bob's `enc_key`). Eve sends Bob her own `EncryptedMessage` reusing `key = kG` with an arbitrary invalid `pop` and arbitrary `msg` bytes. `EncryptedMessage::read` accepts it, `decrypt` computes the same ECDH `b·kG` and returns a valid `EncryptionKeyProof` for it; the garbage plaintext fails `from_repr` with probability ≈ 1 − l/2^256; the early `?` emits the proof without the forged PoP ever being verified. Publishing the proof reveals `b·kG` to everyone, decrypting Alice's secret share to Bob.

The code itself acknowledges this threat and states the PoP is the mitigation ("Bob would then use this to create a blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob... a proof-of-possession is also included with encrypted messages"), but the mitigation only holds if the PoP is verified before the proof is emitted — which this code path violates. The parallel structure in the tests confirms intent: PoP failures are meant to surface as `blame: None` (crypto/dkg/pedpop/src/tests.rs:189-196), yet a non-canonical plaintext short-circuits to `blame: Some(..)` first. [4](#0-3) 

### Impact Explanation
The revealed `EncryptionKeyProof` publishes the ECDH shared key for *any* past or future message to that recipient using the same per-message `key`, and the embedded `DLEqProof` lets every observer confirm and use it via `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/lib.rs:582). Concretely, Eve obtains Alice's Pedersen secret share to Bob — a share of the DKG polynomial protected by the ECDH+ChaCha20 channel specifically because shares must remain confidential. Leaked shares reduce the confidentiality threshold of the produced `ThresholdKeys`; combined across victims (Eve can replay every observed per-message key, one `InvalidShare` report per message) honest shares can be exposed to parties below the intended access policy. The attack requires only public inputs: a crafted `EncryptedMessage` fed to `EncryptedMessage::read`/`calculate_share` by an unprivileged protocol participant.

### Likelihood Explanation
Deterministic from Eve's perspective: she needs no collusion, no timing, and no knowledge of any secret — only an observed honest `EncryptedMessage` (broadcast/coordinator-visible in the processor flow, processor/src/key_gen.rs:409) and the ability to submit her own shares as a DKG participant. The only probabilistic step is the decrypted garbage failing `from_repr`, which fails with overwhelming probability (~1 − 2^-128 for Ristretto). Every honest recipient running `calculate_share` over the malicious map produces the revealing proof; the processor serializes and publishes it as `ProcessorMessage::InvalidShare { blame }` (processor/src/key_gen.rs:420-425). [5](#0-4) 

### Recommendation
Verify the PoP before emitting any `EncryptionKeyProof`. Concretely, in `calculate_share`, do not attach `blame` on the `from_repr` early-return path unless the batch (or at least that message's queued `pop.batch_verify`) has been verified; simplest is to verify each message's PoP eagerly (or run `batch.verify` on the PoP statements) before decryption/`from_repr` can produce a proof-bearing error. Alternatively, gate the error on a per-message PoP check: `msg.pop.verify(...)` inside `decrypt` before constructing `EncryptionKeyProof`, returning `blame: None` on PoP failure — matching the `BatchId::Decryption` convention already used for PoP failures.

### Proof of Concept
1. Run a PedPoP DKG with `n ≥ 2`; let Alice (`sender = A`) send Bob (`recipient = B`, `enc_pub_key = bG`) `EncryptedMessage { key = kG, pop, msg = ct }` where `ct` encrypts `SecretShare` under key derived from `b·kG`.
2. Eve constructs `evil = EncryptedMessage::<C, SecretShare<C::F>> { key: kG, pop: SchnorrSignature { R: random_point, s: random_scalar }, msg: SecretShare([0xFF; 32]) }` — parseable by `EncryptedMessage::read`, invalid PoP, garbage ciphertext.
3. Bob calls `calculate_share(rng, shares)` with `shares[Eve] = evil`. `decrypt` queues the bogus PoP, computes `key = b·kG`, returns `EncryptionKeyProof { key: b·kG, dleq }`.
4. `from_repr(ChaCha20(b·kG) ⊕ 0xFF..)` yields `None` with overwhelming probability → `Err(InvalidShare { participant: Eve, blame: Some(proof) })?` returns before `batch.verify_with_vartime_blame()`, so Eve's forged PoP is never checked.
5. Bob publishes `proof`. Anyone verifies the DLEq against `bG`/`kG`, then decrypts Alice's `ct` via `cipher(context, b·kG)`, recovering Alice's secret share to Bob — the precise side effect the PoP was added to prevent (encryption.rs:84-88).
