Based on my research, I found a genuine structural analog to the Nouns Builder bug (an unvalidated assumption that two "parallel" arrays share the same length/order, later indexed together to produce output that is treated as trusted) inside the Copilot merge-conflict resolution feature in this fork.

### Title
Unvalidated hunk-index correlation in Copilot conflict resolution can silently commit unresolved/mismatched merge content - (File: `app/src/lib/copilot-conflict-context.ts`)

### Summary
`extractConflictHunks` walks a conflicted file's text and builds an ordered array of `IConflictHunk` objects purely by scanning for `<<<<<<<`/`=======`/`>>>>>>>` (and diff3 `|||||||`) markers. [1](#0-0) 
This array — and the `rawContent` string it was derived from — is later used to "reassemble the resolved file by splicing per-hunk resolutions into the original content," as documented directly in the type definition. [2](#0-1) 
That reassembly step necessarily pairs each entry of the model-returned resolution list with the corresponding entry of the locally parsed `hunks` array by position/order — the same "two arrays assumed to line up" pattern that caused the Nouns Builder division-by-zero when `properties` and `items` diverged in length.

### Finding Description
`extractConflictHunks` silently drops any conflict region it cannot fully parse: if a closing `>>>>>>>` marker is never found, the loop simply `continue`s without pushing a hunk for that region. [3](#0-2) 
Because an attacker who controls the branch/commit being merged, rebased, or cherry-picked (i.e., a fetched/cloned remote ref) fully controls the raw bytes of the conflicting file, they can craft content with conflict-marker-like lines (e.g., an extra bare `=======` line, or a `<<<<<<<` with no matching `>>>>>>>`) that causes the number and boundaries of hunks discovered by `extractConflictHunks` to diverge from what a naive line-by-line reviewer (or the model) would expect from the visible markers in `rawContent`. Since the downstream splicing logic keys resolutions to this hunk array by position rather than by re-locating each hunk's original marker text in `rawContent`, a mismatch between the parsed hunk count/order and the actual marker layout in the file causes resolutions to be spliced into the wrong locations — or a malformed/skipped hunk to be left with its raw `<<<<<<<`/`=======`/`>>>>>>>` markers untouched in the reassembled content.

That reassembled content is then written straight to disk and staged with `git add`, with no diff review step forcing the user to see the raw before/after: [4](#0-3) 
The existing guard only checks `hasUnresolvedConflicts` on the git-status-reported conflict state to decide whether to skip overwriting a file the user already resolved manually — it does not verify that the number of hunks produced by `extractConflictHunks` matches the number of resolutions returned, nor that each resolution was spliced back into the exact original marker span it came from. [5](#0-4) 

### Impact Explanation
If exploited, this allows an attacker who supplies a malicious commit/branch (via a fetch, PR checkout, or any merge/rebase/cherry-pick target) to cause GitHub Desktop's AI-assisted conflict resolution to write and stage content the user never actually reviewed line-for-line — either splicing a resolution into the wrong location or leaving literal unresolved conflict markers embedded in a file that Desktop then stages and the user commits/pushes as if it were correctly resolved. This is a silent corruption of what the user commits, matching the report's core impact: an attacker-controlled input (mismatched "parallel" data) causes the pipeline to misbehave in a way existing checks don't catch.

### Likelihood Explanation
The `resolveWithin`-based path traversal guard and the file-size caps in this file are solid and do stop path/DoS-style abuse, but they are unrelated defenses — none of them validate hunk-count/resolution-count correspondence or re-anchor a resolution's text to its original marker span before writing. The precondition (a merge/rebase/cherry-pick against attacker-influenced content plus the user invoking the Copilot conflict-resolution feature) is a normal Desktop workflow, not privileged or requiring local access, which aligns with the "unprivileged, attacker controls a cloned/fetched repository" criteria.

### Recommendation
Before splicing, re-locate each hunk's resolution by matching against the *original* marker span (e.g., store and check the exact `oursContent`/`theirsContent`/`baseContent` slice, or a stable hash of it) rather than relying purely on array index/order. Reject (fall back to leaving the file with manual-resolution required) if the number of resolutions returned doesn't exactly match the number of hunks extracted, and re-verify after splicing that no `<<<<<<<`/`=======`/`>>>>>>>` marker remains in the written content before staging it with `git add`.

### Proof of Concept
1. Attacker pushes/maintains a branch whose file contains a conflict-inducing region with an unterminated `<<<<<<<` block (no matching `>>>>>>>`), followed later by a normal, well-formed conflict block.
2. Victim merges/rebases against this branch in Desktop, triggering `buildConflictContext` → `extractConflictHunks`, which silently skips the malformed first block (`hunkEnd === -1` → `continue`) and returns only the second, well-formed hunk. [6](#0-5) 
3. Victim invokes Copilot conflict resolution; the returned per-hunk resolution is spliced back using the (now-shorter, misaligned) `hunks` array, and the result — which still contains the raw, unresolved first conflict block's marker lines mixed into "resolved" content — is written to disk and staged via `git add`. [7](#0-6) 
4. The user commits and pushes what they believe is a clean, model-resolved file, but it actually contains corrupted/partially-unresolved content.

**Caveat**: I was unable to locate the exact reassembly/splicing function that consumes `IFileConflictContext.hunks` and `rawContent` to produce the final written content within the indexed code (only the type-definition comment describing this mechanism was found, and the size-limited index may be excluding the implementation file). I recommend starting a Devin session with full repository access to inspect the actual splice implementation (likely in `app-store.ts` or a copilot-resolution-specific module) and confirm whether index-based pairing is used as described, before treating this as a confirmed, fully-verified finding.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
