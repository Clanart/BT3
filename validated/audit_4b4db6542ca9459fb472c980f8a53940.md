### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` allows stack-exhaustion DoS when parsing attacker-controlled coin memos - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a CHIP‑0043 custody puzzle description from an on-chain memo `Program`. For `MofN` puzzles it recurses into itself once per member, and each member's memo can itself encode another `MofN` with its own members, with no depth or size limit. This mirrors the CVE-2018-18701 bug class: an attacker-controlled, deeply nested serialized structure drives unbounded recursive parsing until the process stack is exhausted.

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses the CLVM memo, and when `further_branching` is true (i.e., the puzzle is a `MofN`), it calls `MofNHint.from_program()` to get `member_memos`, then recurses: [1](#0-0) 

Specifically: [2](#0-1) 

Each `member_memo` in `MofNHint.member_memos` is itself an arbitrary CLVM `Program` that can encode another `(spec_namespace [nonce restriction_hints 1 mofn_hint])` structure, so the attacker can nest `MofN` inside `MofN` indefinitely by crafting a single memo blob (e.g., embedded in a `CREATE_COIN` hint/memo field, or in a custody puzzle's `memo()` export used during wallet sync/import). There is no recursion-depth guard, unlike the deliberately-iterative `sha256_treehash()`/`chia/types/blockchain_format/tree_hash.py` (which explicitly documents avoiding Python recursion limits for this exact reason) and unlike the Data Layer's Rust merkle-tree loader, which enforces `chia_rs.datalayer.RecursionDepthExceededError` for deep trees (confirmed by `chia/_tests/core/data_layer/test_data_store.py` tests using `depth=100_000`). No equivalent guard exists for `PuzzleWithRestrictions.from_memo()`.

Because Python's default recursion limit (~1000) is comparatively small relative to the ability to encode thousands of nesting levels compactly in a CLVM list (as demonstrated by the analogous CLVM cons-list "recurse-1000000" test fixtures in `chia/_tests/core/mempool/test_mempool_manager.py`), a crafted memo can push the interpreter recursion depth well past the limit, raising `RecursionError`/crashing the parsing thread. `PuzzleWithRestrictions.from_memo()` is documented as "the on-chain/exported synchronization contract" used to reconstruct unknown members from data observed on-chain (e.g., plotnft/pool wallet custody sync in `chia/pools/plotnft_drivers.py`, and general wallet puzzle-driver recognition flows), meaning the memo content originates from spend data that any unprivileged party can construct and broadcast/gift to a wallet (e.g., via a coin's `CREATE_COIN` memo, or an offered puzzle reveal a wallet is asked to parse for CHIP‑0043 custody recognition).

### Impact Explanation
This is a spend/memo-triggered, unauthenticated recursive parse of attacker-supplied nested data with no depth cap, causing an uncaught `RecursionError` (or, in the worst case, a native stack overflow / interpreter crash depending on Python build and thread stack size) in the process handling wallet sync or custody puzzle recognition. This can halt wallet transaction-processing/sync for the affected wallet process — a denial-of-service reachable purely from data an unprivileged submitter or coin sender controls, matching the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Likelihood is limited by how directly reachable `from_memo()` is from fully untrusted network input in production code paths — the confirmed call sites found are in tests (`chia/_tests/clvm/test_custody_architecture.py`) and in `chia/pools/plotnft_drivers.py` (plotnft/pool wallet custody construction), which primarily processes the wallet's own puzzle data rather than arbitrary third-party memos. I was not able to fully confirm, within the available search budget, a call path where `from_memo()` is invoked automatically on unauthenticated third-party memo/hint data during ordinary wallet sync (e.g., from `compute_memos_for_spend`/hint processing) versus only being invoked deliberately by wallet code on its own custody puzzles. This uncertainty should be resolved before treating this as fully proven; if `from_memo()` is only ever called on puzzles the wallet itself constructed or explicitly imports, the practical attacker-reachability is much lower than assumed here.

### Recommendation
Add an explicit recursion-depth (and/or node-count) limit to `PuzzleWithRestrictions.from_memo()`/`MofNHint.from_program()` parsing, converting excess depth into a clean `ValueError` rather than an uncaught `RecursionError`, consistent with the iterative design already used in `sha256_treehash()` and the Rust Data Layer's `RecursionDepthExceededError` guard. Consider bounding member/restriction list sizes as well.

### Proof of Concept
Construct a memo `Program`:
```
memo = Program.to(("CHIP-0043", [0, [], 1, MofNHint(m=1, member_memos=[<same memo nested N times>]).to_program()]))
```
repeated to a nesting depth exceeding Python's recursion limit (~1000, easily encoded compactly as a CLVM cons chain), then call:
```python
PuzzleWithRestrictions.from_memo(memo)
```

    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:

            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")

        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)

        else:
