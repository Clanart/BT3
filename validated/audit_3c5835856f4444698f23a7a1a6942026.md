## Finding [1](#0-0) 

Setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` disables Git's own built-in defense against malicious repositories/submodules that try to write into `.git` internals during a `--recursive` clone.

### Title
Recursive clone explicitly disables Git's submodule/`.git`-write clone protection - (File: app/src/lib/git/clone.ts)

### Summary
Desktop's `clone()` function performs `git clone --recursive` while explicitly setting the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. This is the same guard Git upstream introduced (as part of the fix line for the class of vulnerabilities like CVE-2024-32002/case-insensitive-filesystem submodule attacks) to detect when a nested/submodule repository is crafted so that, on checkout, it writes files into the superproject's `.git` directory (e.g. planting a hook) instead of its own working tree. Desktop deliberately turns this protection off for every clone it performs.

### Finding Description
`clone()` builds the environment used for the `git clone --recursive` invocation: [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE=false` is passed unconditionally on every clone, and `--recursive` means submodules are fetched and checked out automatically without further user confirmation. The attacker-controlled input here is the repository content itself (a crafted top-level repo plus a crafted submodule, or a `.gitmodules`/`git config` entry pointing at an adversarial submodule) — exactly the kind of "attacker controls a cloned/fetched repository" scenario named in the task's valid-impact list.

Git's own protection (the flag Desktop is disabling) exists specifically to catch the case where a submodule's path/name, combined with case-insensitivity or path-separator tricks, resolves during checkout to a location inside the superproject's `.git` directory (e.g. `.git/hooks/post-checkout`) rather than inside the intended submodule working directory. Without that check active, a crafted repository can plant an executable file directly into the checked-out repository's hooks directory as part of the recursive clone/checkout.

Once such a hook file exists on disk, Desktop's own hook-execution pipeline will pick it up and run it on subsequent, completely ordinary user actions (commit, checkout, merge, push) performed from the Desktop UI: [2](#0-1) [3](#0-2) 

`getRepoHooks` enumerates files in `core.hooksPath` (or `.git/hooks`) and, if they are executable (or on Windows, simply present with a known hook name), `withHooksEnv` wires them into the hook-interception proxy so they run for the user's next Git operation. There is no verification anywhere in this pipeline that the hook file was placed there intentionally by the user rather than as a side effect of a recursive clone whose submodule-write protection was turned off.

This mirrors the broken invariant in the external report: a security check that exists specifically to prevent an attacker from forcing invalid/dangerous state (there: non-zero AMM reserves; here: attacker-controlled files landing in `.git/hooks`) is bypassed by the calling code (there: the router computing `addLiquidity` off unchecked reserves; here: Desktop explicitly disabling `GIT_CLONE_PROTECTION_ACTIVE`), and a later, seemingly unrelated operation (there: liquidity seeding; here: the hook-execution machinery) ends up acting on the corrupted state.

### Impact Explanation
If the clone-protection bypass allows a crafted repository/submodule pair to place an executable in `.git/hooks` (or wherever `core.hooksPath` points), Desktop's hook-interception system will execute attacker-supplied code in the context of the user's machine the next time the user performs a routine action in the app (commit, checkout, merge, etc.) on that repository — i.e., unprivileged remote-content-triggered code execution, which is explicitly in-scope per the "Valid Impact" criteria (attacker controls a cloned repository → code execution).

### Likelihood Explanation
The victim only needs to clone or open a malicious/compromised repository that contains a submodule crafted to exploit this class of write-outside-worktree behavior — no unusual user action beyond a normal clone is required, and `GIT_CLONE_PROTECTION_ACTIVE=false` is applied unconditionally to every clone Desktop performs, so the protection is never available even for repositories from untrusted sources.

### Recommendation
Do not disable `GIT_CLONE_PROTECTION_ACTIVE`; let Git's built-in protection remain active (or set it to `'true'`/leave unset) during `clone()`, especially since `--recursive` is used. If disabling it was done to work around a compatibility issue, it should be scoped/conditioned much more narrowly and paired with an independent post-clone integrity check (e.g., verifying no files were written outside the expected submodule working directories) before Desktop's hook-detection code (`getRepoHooks`) is allowed to treat newly-cloned repositories as trusted.

### Proof of Concept
1. Attacker publishes a repository containing a submodule entry whose path/name is designed to alias into the superproject's `.git/hooks` directory when checked out recursively (the class of issue Git's clone protection was built to catch).
2. Victim clones this repository in GitHub Desktop; `clone()` runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false`, so Git's own detection of the unsafe write does not abort the clone.
3. The malicious submodule checkout writes an executable file into `.git/hooks/<hookname>` of the newly cloned repository.
4. The victim performs a normal action in Desktop that triggers that hook (e.g. `post-checkout`, `pre-commit`) — `getRepoHooks`/`withHooksEnv` detect and execute the planted file via the hooks proxy, running attacker-controlled code on the victim's machine. [1](#0-0) [2](#0-1)

```typescript
export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
```

```typescript
export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
```
