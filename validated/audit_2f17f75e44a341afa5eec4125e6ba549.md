### Title
OP_RETURN data is omitted from fee/weight estimation, causing under-priced or oversized signed transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` appends an attacker-supplied `data` output before estimating transaction weight and fees, but `calculate_weight_vbytes` is called only with `payments`, not with the final `tx_outs` containing the OP_RETURN output. Consequently, `needed_fee`, the minimum-fee check, the funds check, the change calculation, and the maximum-standard-weight check all use a smaller transaction than the transaction ultimately signed. This is analogous to using a preview without validating that it reflects the operation actually executed.

### Finding Description

`SignableTransaction::new` accepts up to 80 bytes of caller-controlled `data` and inserts an OP_RETURN output into `tx_outs`. [1](#0-0)  The subsequent estimate calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, so the OP_RETURN output is absent from the transaction whose weight is used to compute `vbytes` and `needed_fee`. [2](#0-1)  The change-path estimate has the same issue because it likewise passes only `payments`, omitting the OP_RETURN output already added to `tx_outs`. [3](#0-2) 

The construction completes by storing the larger transaction containing the OP_RETURN output while retaining `needed_fee` and `weight` derived from the smaller transaction. [4](#0-3)  The resulting transaction is then committed to by the Taproot sighash and signed through `TransactionSignMachine::sign`. [5](#0-4) 

### Impact Explanation

A caller can cause validators to produce a valid signature for a Bitcoin transaction whose actual fee rate is lower than the requested `fee_per_vbyte`. [2](#0-1)  Because the minimum-relay-fee check uses the underestimated virtual size, it can pass even though the signed transaction does not meet the intended relay policy. [6](#0-5) 

The maximum-standard-weight check is also performed against the underestimated weight, so the signed transaction can exceed the checked bound after the OP_RETURN output is included. [7](#0-6)  When a change output is present, its amount is computed using the underestimated fee, reducing the retained change relative to the intended fee rate rather than preserving the specified policy. [3](#0-2) 

### Likelihood Explanation

The vulnerable inputs are public API arguments: `data` may be supplied directly to `SignableTransaction::new`, while `payments`, `change`, `inputs`, and `fee_per_vbyte` are also caller-controlled at this layer. [8](#0-7)  Any non-empty `data` triggers divergence between the estimated and signed transaction; larger payloads create a larger fee-rate and weight discrepancy. [1](#0-0) 

Exploitation does not require a malicious validator, private-key disclosure, invalid encodings, or control of consensus; it only requires reaching transaction construction with an OP_RETURN payload. [8](#0-7) 

### Recommendation

Estimate the fee using the exact output set that will be signed. Either move OP_RETURN insertion into the transaction model used by `calculate_weight_vbytes`, or change the estimator to accept the finalized `tx_outs` rather than `payments`. Recompute and validate `needed_fee`, minimum relay fee, available funds, change amount, and `MAX_STANDARD_TX_WEIGHT` after all outputs—including `data` and change—have been finalized. The signed transaction should also be checked to ensure `fee() >= fee_per_vbyte * actual_vsize` before producing signature shares.

### Proof of Concept

1. Construct any spendable `ReceivedOutput` and a valid non-dust payment.
2. Call `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0xaa; 80]), fee_per_vbyte)`.
3. The constructor first places an 80-byte OP_RETURN output in `tx_outs`. [9](#0-8) 
4. It then estimates `vbytes` from a transaction containing only `payments`, so the OP_RETURN script and its output encoding are omitted. [10](#0-9) [2](#0-1) 
5. On the change path, `fee_with_change` still omits the OP_RETURN output, and the change amount is derived from that underestimated fee. [3](#0-2) 
6. `new` returns a `SignableTransaction` whose `tx.output` includes the OP_RETURN output, while `needed_fee` remains based on the smaller transaction. [4](#0-3) 
7. Signing commits to the complete transaction—including the omitted OP_RETURN output—through `taproot_key_spend_signature_hash`, so the resulting signed transaction has a lower actual fee rate than requested and may violate the minimum relay fee or standard-weight bound. [5](#0-4)
