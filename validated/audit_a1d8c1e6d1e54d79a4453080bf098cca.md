### Title
DID recovery attestations use replayable `AGG_SIG_UNSAFE` signatures with no nonce or expiry - ([File: chia/wallet/did_wallet/did_wallet_puzzles.py])

### Summary
Chia's DID (`did_wallet`) recovery mechanism is a threshold multi-signer scheme conceptually equivalent to the report's "controllers with weights" model: a DID has a list of `backup_ids` (other DID coin IDs acting as controllers) and a `num_of_backup_ids_needed` threshold that must sign off to authorize recovery (i.e., replacing the DID's owning key/`p2_puzzle`). The attestation signature each backup controller produces is built by `create_recovery_message_puzzle()` and is never bound to a nonce or an expiry, mirroring exactly the "M-02" bug class from the external report.

### Finding Description
`create_recovery_message_puzzle()` builds the attestation puzzle a backup DID spends to endorse a recovery: [1](#0-0) 

The resulting condition set is:
- `CREATE_COIN_ANNOUNCEMENT recovering_coin_id`
- `AGG_SIG_UNSAFE pubkey newpuz`

The `AGG_SIG_UNSAFE` message signed by the backup controller is just `newpuz` (the proposed new p2 puzzle hash) — it is **not** combined with any nonce, nor with an expiry timestamp, nor even with the `recovering_coin_id` itself (that binding only exists in the separate coin announcement, which is a distinct, unsigned condition). `AGG_SIG_UNSAFE` by design has no per-coin/per-spend domain separation (unlike `AGG_SIG_ME`, whose message is salted with the spent coin's ID via `pkm_pairs`/`make_aggsig_final_message`): [2](#0-1) 

This means once a backup controller (analogous to the report's "controller C") signs an attestation for a given `newpuz`, that raw BLS signature is a standalone, self-contained authorization that:
1. Is not tied to the current on-chain state (current `backup_ids` list, current threshold `num_of_backup_ids_needed`, or current DID coin) beyond the announcement asserted by whichever recovery spend happens to be aggregated with it in the same bundle.
2. Never expires — the same signature is valid regardless of how much time has passed.
3. Can be withheld and later combined with a different bundle/at a different time, exactly like the report's scenario where a controller "refuses to sign" but their signature is later reused once conditions become favorable to them (e.g., after the DID's `backup_ids`/threshold configuration changes, since the puzzle itself is re-curried with the same static hash-based backup list check, and `find_lost_did`'s puzzle matching/override logic in `wallet_state_manager.py` shows the wallet already tolerates puzzle mismatches by trying overridden `recovery_list_hash`/`num_verification`).

### Impact Explanation
If a backup controller's stale attestation signature is reused later — e.g., pieced together with other backup signers' signatures the requester already collected — an attacker who is one of the `backup_ids` (or who obtains a leaked/old attestation) can drive the DID singleton's `p2_puzzle`/ownership to a `newpuz` of their choosing without renewed, contemporaneous consent from the rest of the quorum, similar to unauthorized coin/ownership takeover. This is a concrete unauthorized transfer of DID ownership (analogous to "unauthorized coin movement" / "forged asset identity" of the DID identity coin), matching the report's "personal benefit" impact class.

### Likelihood Explanation
Low, matching the original report's rating: it requires (a) a DID actually configured with `backup_ids`/threshold recovery (a legacy/deprecated feature per the wallet's own warning that "recovery list hash ... has been deprecated" for new DIDs, though still supported at the consensus/puzzle level for existing DIDs), (b) an attacker being one of the backup signers or obtaining a previously produced attestation, and (c) a favorable moment (e.g., after ownership/backup-list changes) to replay it. This narrows exploitation to specific legacy-configured DIDs and requires the attacker to already hold partial trust as a backup controller.

### Recommendation
- Bind the `AGG_SIG_UNSAFE` attestation message in `create_recovery_message_puzzle()` to the specific recovery attempt: include `recovering_coin_id` (and ideally a monotonically-increasing recovery nonce/DID coin generation) inside the signed message itself, not merely in a separate, unsigned `CREATE_COIN_ANNOUNCEMENT`.
- Add an expiry timestamp to the signed attestation data and require the DID inner puzzle's recovery spend to assert `ASSERT_BEFORE_SECONDS_ABSOLUTE`/`ASSERT_SECONDS_RELATIVE` (or similar) so stale attestations cannot be used indefinitely.
- Consider switching to `AGG_SIG_ME` (or a puzzle-level nonce curried into the message) for backup attestations so each signature is cryptographically scoped to a specific coin/spend, preventing cross-time or cross-context replay, consistent with the report's two recommendations (storage-tracked nonce + `expiredAt`).

### Proof of Concept
Conceptual sequence (mirrors the report's example):
1. DID `D` has `backup_ids = [A, B, C]`, `num_of_backup_ids_needed = 2`.
2. `D` requests recovery to `newpuz1`. `A` and `B` sign attestations via `create_recovery_message_puzzle(D, newpuz1, pubkey)`; `C` refuses but a copy of `A`'s and `B`'s signed attestations (bytes) is retained by whoever initiated the request.
3. Time passes; `D`'s backup list/threshold or the intended owner changes.
4. The retained attestations from `A` and `B` (which only commit to `newpuz1`, no expiry, no state-binding beyond the announcement) are replayed in a new spend bundle to force `D`'s p2_puzzle to `newpuz1`, even though the current context/holders no longer intend that transfer — because `AGG_SIG_UNSAFE` places no constraint preventing reuse of the exact same signature/message pair in any future spend bundle. def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle


def create_spend_for_message(
    parent_of_message: bytes32, recovering_coin: bytes32, newpuz: bytes32, pubkey: G1Element
) -> CoinSpend:
    """
    Create a CoinSpend for a atestment
    :param parent_of_message: Parent coin ID
    :param recovering_coin: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: CoinSpend
    """
    puzzle = create_recovery_message_puzzle(recovering_coin, newpuz, pubkey)
    coin = Coin(parent_of_message, puzzle.get_tree_hash(), uint64(0))
    solution = Program.to([])
    return make_spend(coin, puzzle, solution)
