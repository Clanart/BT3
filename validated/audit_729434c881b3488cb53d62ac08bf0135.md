### Title
`SignableTransaction` omits the OP_RETURN `data` output from all weight/fee calculations, producing transactions with an underpaid fee rate that can fall below the minimum relay feerate (or exceed the standard-weight limit) - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` accepts an optional `data` argument which is appended to the transaction as an `OP_RETURN` output. However, both invocations of `calculate_weight_vbytes` only account for `inputs`, `payments`, and `change` — the `data` output is never included in the serialized template transaction used to compute `weight` and `vbytes`. As a result, `needed_fee` (computed as `fee_per_vbyte * vbytes`) is systematically underestimated whenever `data` is present, and both the `TooLowFee` minimum-relay check and the `TooLargeTransaction` standard-weight check are evaluated against a weight that excludes the OP_RETURN output's ~90+ weight units. [1](#0-0) 

### Finding Description

The transaction weight is estimated by building a template `Transaction` containing only `inputs`, `payments`, and an optional `change` output:

```rust
// networks/bitcoin/src/wallet/send.rs
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
...
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```

But the OP_RETURN output is pushed into `tx_outs` (line 194–202) before, and independently of, these calculations — `calculate_weight_vbytes` has no `data` parameter at all (line 62–66). Concretely, when `data` is `Some`:

1. `needed_fee = fee_per_vbyte * vbytes` excludes the OP_RETURN output's virtual size (a push of up to 80 bytes plus output overhead ≈ 90–100 wu ≈ ~23–25 vb).
2. The minimum-fee guard `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` validates the underestimated size, so a transaction created at `fee_per_vbyte = 1` with `data` can have an *effective* feerate below 1 sat/vb and be rejected by every relaying node.
3. The change calculation `input_sat - (payment_sat + fee_with_change)` grants change based on the underestimated fee, so even the "correct" change doesn't compensate — the actual on-chain fee equals `needed_fee` regardless of the extra output's size.
4. The `weight > MAX_STANDARD_TX_WEIGHT` check uses the understated `weight`, so a transaction straddling the standardness limit can be produced and signed yet be inherently non-relayable.

An unprivileged party interacting with the protocol can supply or influence `data` (the OP_RETURN payload used for instructions/memo outputs in this protocol's usage), triggering construction of a transaction that signs successfully but cannot be broadcast or is stuck with a below-market/below-minimum feerate.

### Impact Explanation

FROST signing sessions produce signatures bound to the exact sighash of this malformed transaction (Prevouts::All + all outputs). Once signed and published, the transaction either fails relay (below `DEFAULT_MIN_RELAY_TX_FEE` effective rate or over `MAX_STANDARD_TX_WEIGHT`) or sits unconfirmed indefinitely. The inputs committed to it cannot be spent elsewhere without coordinating a new multisig session to sign a replacement, so funds are effectively locked pending manual recovery — a direct loss-of-availability of vault funds mirroring the referenced incident's "contract logic causes funds to become unspendable/lost" class. Since `data` of exactly ≤80 bytes is explicitly permitted, this is reachable through normal, intended API usage.

### Likelihood Explanation

Medium. Exploitation requires only that the `data` path be exercised (e.g., instruction payloads) combined with a `fee_per_vbyte` at or near the minimum, or inputs/payments sized near the standard-weight bound. No cryptographic assumptions are broken; it is a deterministic accounting error — every `data`-carrying transaction silently underpays its feerate by the OP_RETURN output's vsize.

### Recommendation

Pass `data` into `calculate_weight_vbytes` (or add the OP_RETURN `TxOut` to the template transaction in both the no-change and with-change calls) so that `vbytes`, `weight`, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all account for the data output. Alternatively, include the OP_RETURN output in the `payments`-style output list used for estimation.

### Proof of Concept

```rust
// networks/bitcoin/src/wallet/send.rs (conceptual test)
// Construct a 1-input transaction paying DUST+fee with data at the minimum
// relay rate: fee_per_vbyte chosen so needed_fee == DEFAULT_MIN_RELAY minimum.
let data = vec![0u8; 80]; // maximal allowed OP_RETURN payload
let tx = SignableTransaction::new(
    vec![input],            // one ReceivedOutput
    &[(addr(), 1000)],
    None,
    Some(data),
    1,                      // 1 sat/vb
).unwrap();

// tx.needed_fee() == vbytes(without OP_RETURN) * 1
// tx.transaction() includes the extra ~25 vb OP_RETURN output,
// so the effective feerate is < 1 sat/vb => DEFAULT_MIN_RELAY_TX_FEE
// violation. The signed transaction is rejected by Bitcoin Core's
// mempool ("min relay fee not met"), while the library reports it as
// a valid, correctly-fee'd SignableTransaction.
```

The analogous weight-limit case: craft `payments` such that the computed `weight` is exactly `MAX_STANDARD_TX_WEIGHT`; the check passes, but the real transaction (with the OP_RETURN output) exceeds the limit and is non-standard.
