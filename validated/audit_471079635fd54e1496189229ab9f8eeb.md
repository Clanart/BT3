### Title
Stale `lastRetainedCommitRef`/`HEAD` race in multi-commit operations (squash/reorder/rebase) can silently replay/drop unintended commits - (File: app/src/lib/git/reorder.ts, app/src/ui/dispatcher/dispatcher.ts)

### Summary
This is analogous to the `submitEpochReward()` bug: a boundary value (`startEpochId`/here, the "current tip"/`lastRetainedCommitRef`) is computed once and trusted for a multi-step async operation, but the underlying state (`HEAD`) can change between the moment the value is captured and the moment it's actually used to build the git range. Desktop never re-verifies that the captured tip is still the actual `HEAD` before running the interactive rebase.

### Finding Description
`dispatcher.reorderCommits()` (and analogous `squash`/`startRebase` flows) captures the branch tip early: [2](#0-1) 
It then does a chain of `await`s — `_checkForUncommittedChanges`, `_initializeMultiCommitOperation`, `_setMultiCommitOperationUndoState`, and conditionally `warnAboutRemoteCommits` (which itself performs `getBranches`/`getCommitsBetweenCommits` git calls) — before finally invoking `appStore._reorderCommits(repository, commitsToReorder, beforeCommit, lastRetainedCommitRef)`. [3](#0-2) 

Inside `reorder()`, the actual commit range to be rewritten is computed at execution time via `revRange(lastRetainedCommitRef, 'HEAD')`, resolving to whatever `HEAD` is *at that moment* — not the `tip.branch.tip.sha` captured when the flow started: [1](#0-0) 

Nowhere in this path is there a check that the current `HEAD` equals the `currentTip`/`lastRetainedCommitRef` captured at initialization (the guard that the reward-oracle report recommends: validate `startEpochId` against the expected value). Meanwhile, Desktop runs a `BackgroundFetcher` and `fastForwardBranches` logic that can move local branch refs (fast-forwarding tracking branches) concurrently while dialogs are open and the user is still on the multi-commit-operation flow: [4](#0-3) [5](#0-4) 

If the currently checked-out branch's ref is fast-forwarded (or otherwise updated) by this background activity between the time the reorder/squash dialog captured `lastRetainedCommitRef`/`commits` and the time `reorder()`/`rebaseInteractive` actually runs, the git range `lastRetainedCommitRef..HEAD` used to build the rebase todo list will silently include extra commits that were not part of the user-reviewed/selected set (`commitsToReorder`/`toSquash`), because the code trusts live `HEAD` instead of re-validating it equals the previously captured tip.

### Impact Explanation
Extra, unreviewed commits could be silently folded into a reorder/squash/rebase todo list and rewritten (picked, reworded, or replayed in unexpected order) without the user's knowledge, corrupting the commit history the user believes they are creating — directly matching the "extra rewards being reported" class of bug (wrong quantity of items processed due to a stale boundary value). This can result in unintended commits being force-pushed to a remote via the resulting rebase, corrupting what the user pushes.

### Likelihood Explanation
Requires a narrow timing window where `HEAD` changes (e.g., via background fetch/fast-forward, another rebase continuation, or a hook) between dialog-open time and rebase execution — this is a race condition dependent on background sync timing rather than a guaranteed trigger, so likelihood is moderate/low but the report explicitly seeds this exact "race condition on a computed boundary value" bug class.

### Recommendation
Before invoking `reorder()`/`rebaseInteractive()`/`rebase()`, re-resolve the current `HEAD`/tip and compare it against the `currentTip` captured at `_initializeMultiCommitOperation` time; abort (or refresh and re-prompt) the operation if they differ, mirroring the reward-oracle fix of passing an explicit `startEpochId` and rejecting mismatches rather than recomputing it implicitly at execution time.

### Proof of Concept
1. Select several commits and start "Reorder" or "Squash" in Desktop; this captures `lastRetainedCommitRef` = SHA_A and shows the multi-commit-operation dialog.
2. While the dialog is open (before confirming), have background fetch/fast-forward update the checked-out branch's `HEAD` to SHA_B (e.g., a fast-forwarded tracking branch, or another process moving the ref).
3. Confirm the operation. `reorder()` computes `revRange(lastRetainedCommitRef, 'HEAD')` against the now-current `HEAD` (SHA_B) rather than the originally captured tip (SHA_A), silently pulling in commits between SHA_A and SHA_B that were never part of the reviewed/selected commit set into the rebase todo list. [6](#0-5)
