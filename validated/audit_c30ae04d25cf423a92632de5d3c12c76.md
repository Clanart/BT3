### Title
Truncated serialized threshold keys trigger attacker-controlled memory allocation - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts a two-byte participant count and immediately allocates a `Vec` with capacity for that many field elements when the interpolation tag specifies `Interpolation::Constant`. [1](#0-0)  The resulting `ThresholdParams` is not validated until after all coefficients, the secret share, and all verification shares have been read. [2](#0-1) 

### Finding Description
After checking the curve identifier, the parser reads `t`, `n`, and `i` directly from the input. [3](#0-2)  For interpolation tag `0`, it calls `Vec::with_capacity(usize::from(n))` before confirming that `n` describes valid threshold parameters or that the input actually contains the promised coefficients. [4](#0-3) 

An attacker can therefore provide the valid curve header, `t = 1`, `n = 65535`, `i = 1`, interpolation tag `0`, and then truncate the stream. The implementation allocates space for 65,535 field elements before the first `C::read_F` returns an EOF or decoding error. [4](#0-3) 

### Impact Explanation
Each malicious tiny input can force a multi-megabyte allocation proportional to `n * size_of::<C::F>()` and then fail. Repeated or concurrent calls to `ThresholdKeys::read` on attacker-controlled input can create allocator pressure, transient memory exhaustion, or process termination on allocation failure. [5](#0-4) 

### Likelihood Explanation
This requires an execution path that passes unauthenticated serialized `ThresholdKeys` to `ThresholdKeys::read`. The attacker does not need a valid secret share, valid coefficients, or a complete payload; the allocation occurs before semantic parameter validation and before the declared coefficient data is consumed. [6](#0-5) 

### Recommendation
Construct and validate `ThresholdParams` immediately after reading `t`, `n`, and `i`, before allocating based on `n`. [7](#0-6)  Avoid `Vec::with_capacity(n)` on unauthenticated input, or bound `n` to the expected maximum participant count before allocation. Reading coefficients incrementally with `Vec::new` and `push` would prevent a short header from forcing an upfront allocation. [4](#0-3) 

### Proof of Concept
For a concrete `C: Ciphersuite`, an input with the following layout triggers the allocation and then reaches EOF:

```text
u32le(C::ID.len()) || C::ID ||
u16le(1)           ||       // t
u16le(65535)       ||       // n
u16le(1)           ||       // i
0x00               || EOF   // Interpolation::Constant
```

The relevant parser path is:

```rust
// crypto/dkg/src/lib.rs:604-613
let mut interpolation = [0];
reader.read_exact(&mut interpolation)?;
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
```

With `n = 65535`, `Vec::with_capacity` reserves space for 65,535 field elements before `C::read_F` observes the truncated input. [4](#0-3)
