Let me verify who can supply `data` and how the fee/change values are used downstream.### Title
Fee/change accounting omits the OP_RETURN data output's size, causing the signed transaction to pay a lower fee rate than required - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report's bug class is a leftover/entitlement calculation that fails to subtract a component which was already credited, producing systematically wrong distribution of value. The same class exists in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`: when a `data` payload is supplied, an OP_RETURN `TxOut` is pushed into `tx_outs` (lines 194-202), but both calls to `calculate_weight_vbytes` (lines 204 and 225-226) measure the transaction using only `payments` plus an optional change output. The OP_RETURN output — up to 80 bytes of pushdata plus output overhead — is part of the signed transaction yet is never accounted for in the weight/vbyte/fee computation.

### Finding Description
`SignableTransaction::new` builds `tx_outs` by appending the OP_RETURN output before any fee measurement:

- Line 195-202: `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: new_op_return(data) })`
- Line 204: `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — `payments` does not include the data output.
- Line 225-226: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` — again excludes the data output.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed on an under-measured vsize. The final transaction is `fee_per_vbyte * (size_with_op_return - size_without)` satoshis short of the requested rate; the effective fee rate of the signed transaction is strictly less than `fee_per_vbyte`.
2. The minimum-relay-fee check at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) uses the same underestimated `vbytes`, so it can pass while the *actual* fee density of the final, larger transaction falls below the relay minimum. The signed transaction may then be rejected from mempool propagation entirely, leaving vault inputs locked in an unconfirmable/unspendable state until re-planned.
3. The change leftover mirrors the report exactly: line 228 computes `input_sat.checked_sub(payment_sat + fee_with_change)` where `fee_with_change` is under-measured, so the change output is over-credited relative to the intended fee — the "leftover" formula omits a component (the data output's marginal fee) just as the Arrakis `leftOver0/leftOver1` omitted `total.fee0/fee1`.

All bytes in `data` and the `payments`/`change` values are caller-supplied inputs to `SignableTransaction::new`, so the under-accounting is reachable purely from public transaction-construction inputs; the resulting transaction is what `TransactionSignMachine::sign` (lines 373-397) commits to via `Prevouts::All` sighashes.

### Impact Explanation
Any plan whose transaction carries an OP_RETURN `data` output produces a signed transaction whose true fee density is below both the requested `fee_per_vbyte` and potentially the network's minimum relay fee. The vault signs and broadcasts a transaction that cannot propagate or confirm in a timely manner; the spent inputs are encumbered by the signatures (SIGHASH_ALL/Default binding all inputs via `Prevouts::All`), so the funds are effectively reported spent/committed while the transaction is unrelayable. When a change output exists, change is additionally over-valued by the omitted fee amount, directly reducing the fee below intent — the same "credited component left out of the leftover subtraction" structure as the reference finding.

### Likelihood Explanation
Triggering requires only that `SignableTransaction::new` be invoked with `data: Some(_)`, which is a supported public code path guarded by the `TooMuchData` (≤80 byte) check rather than disabled. The defect is deterministic — it misprices every data-carrying transaction — and its severity grows with payload size (maximum ~80-byte underestimation). Whether it reaches production depends on the processor passing `data` through `make_signable_transaction` in `processor/src/networks/bitcoin.rs`; I could not fully confirm that call site passes non-`None` data, but the API path exists and is reachable from public inputs per the rules.

### Recommendation
Include the OP_RETURN output in the measured output set. Either:
- Pass a representation of the data output into `calculate_weight_vbytes` (e.g., extend `payments` with `(op_return_script, 0)` or accept the full `tx_outs`/`Vec<TxOut>`), for both the no-change and with-change weight computations; or
- Build the fee-estimation transaction from the final `tx_outs` vector so measurement can never diverge from the signed transaction.

Also re-verify the `TooLowFee` check against the corrected vbytes.
