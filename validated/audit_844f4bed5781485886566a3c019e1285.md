### Title
Inline trailing `#` comment on `action:`/`enabled:` frontmatter line causes hand-rolled parser to silently downgrade `block` rules to warnings while displayed rule status differs - (File: plugins/hookify/core/config_loader.py -> extract_frontmatter)

### Summary
`extract_frontmatter` splits a top-level `key: value` line only on the first `:` and never removes an inline `# ...` trailing comment, so `action: block  # keep strict` is stored as the literal string `"block  # keep strict"`. Since `RuleEngine.evaluate_rules` compares `rule.action == 'block'` exactly (plugins/hookify/core/rule_engine.py:55), this rule is silently demoted to a non-blocking warning rule even though a human/LLM reading the same file (as instructed by `/hookify:list`, plugins/hookify/commands/list.md steps 2-3) would report `action: block`.

### Finding Description
- `extract_frontmatter` (plugins/hookify/core/config_loader.py:125-152) parses top-level key/value lines with `key, value = line.split(':', 1)` and only strips surrounding whitespace/quotes — no logic removes a trailing `#comment`. Full-line comment stripping only applies via `stripped.startswith('#')` at line 118, which does not catch inline comments appended after real content.
- `Rule.from_dict` (line 81) stores this corrupted value directly: `action=frontmatter.get('action', 'warn')`.
- `RuleEngine.evaluate_rules` (plugins/hookify/core/rule_engine.py:55) does a strict equality check `if rule.action == 'block':`; the corrupted value `"block  # keep strict"` fails this check, so the rule falls into `warning_rules` instead of `blocking_rules`, meaning the operation is never blocked—only a warning message is surfaced.
- Meanwhile, `/hookify:list` (plugins/hookify/commands/list.md) is an LLM-driven command whose steps 2-3 say to "Read the file" and "Extract frontmatter fields," relying on the model's own (correct) YAML-like comprehension rather than `extract_frontmatter`. A capable LLM will correctly interpret `action: block  # keep strict` as `action: block` and display "✅ Blocking" or similar to the user, creating a discrepancy between what the user believes is enforced and what actually happens at hook-evaluation time.
- Attack path: an unprivileged actor who can place or influence content of a `.claude/hookify.*.local.md` file (e.g., via a shared repo, a suggested rule from a PR/commit, or output from `/hookify` rule-authoring flow that a user copies from untrusted content) can add an innocuous-looking trailing comment to the `action:` line. This causes intended blocking security rules (e.g., blocking `rm -rf`, blocking secret exfiltration commands, etc.) to be silently downgraded to non-blocking warnings, while `/hookify:list` continues to report the rule as an active blocking rule, giving the user false assurance.
- Existing checks do not catch this: there is no validation that `frontmatter['action']` is exactly `'block'` or `'warn'` (any other string falls to the warn path by default), no schema check, and no test comparing parser output against a real YAML parser.

### Impact Explanation
This causes a security control failure (loss of intended block enforcement) that is not visible to the user, since the LLM-driven `/hookify:list` report will misrepresent the rule's actual enforcement action as "block" while `RuleEngine` treats it as "warn." This matches a "trust boundary bypass / hook enforcement bypass" style impact: a rule meant to hard-block dangerous file/bash operations quietly becomes advisory-only, defeating the plugin's core safety mechanism without any visible error, log, or user awareness discrepancy resolution.

### Likelihood Explanation
Feasibility is high and requires only an unprivileged party able to influence the text of a `.claude/hookify.*.local.md` file (a plain markdown file with YAML-like frontmatter that is commonly shared, copy-pasted from docs/examples, or auto-generated by `/hookify` from conversation text incorporating a code comment style suggestion). No special privilege, key, or approval is needed — merely including a trailing comment such as `action: block  # keep strict` in the frontmatter, a stylistically ordinary and unsuspicious thing to write. The bug is 100% deterministic and repeatable given the parser code shown.

### Recommendation
In `extract_frontmatter`, before assigning `value`, strip inline trailing comments (e.g., using a YAML-aware split that respects quoting, such as regex `re.split(r'(?<!\\)\s+#', value, maxsplit=1)` or simply using `yaml.safe_load` for parsing the frontmatter block instead of a hand-rolled parser). Additionally, validate `frontmatter.get('action')` against an explicit allow-list (`{'block', 'warn'}`) and fail loudly (reject/log error) rather than silently defaulting unknown values to `'warn'`.

```python
import yaml
from plugins.hookify.core.config_loader import extract_frontmatter, Rule
from plugins.hookify.core.rule_engine import RuleEngine, Condition

content = """---
name: block-rm
enabled: true
event: bash
action: block  # keep strict
conditions:
  - field: command, operator: regex_match, pattern: rm -rf
---

Blocked dangerous rm.
"""

fm, msg = extract_frontmatter(content)
naive = yaml.safe_load(content.split('---')[1])

# Assert divergence: config_loader keeps the trailing comment, safe_load strips it

assert fm['action'] == 'block  # keep strict'

rule = Rule.from_dict(fm, msg)
engine = RuleEngine()
result = engine.evaluate_rules(

)
# Expected (buggy) behavior: rule treated as warning, NOT blocking
assert "hookSpecificOutput" not in result  # would contain permissionDecision: deny if correctly blocked
assert "systemMessage" in result  # only a warning is shown, operation is NOT denied
```
