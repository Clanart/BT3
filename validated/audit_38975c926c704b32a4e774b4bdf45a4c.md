## Finding

The analog centers on `clone()` in [1](#0-0)  explicitly setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for every recursive clone performed by GitHub Desktop.

### Title
GitHub Desktop disables Git's built-in clone protection (`GIT_CLONE_PROTECTION_ACTIVE`) against malicious submodule/hook paths, re-opening remote code execution on simple "Clone" - (File: `app/src/lib/git/clone.ts`)

### Summary
Git upstream introduced `GIT_CLONE_PROTECTION_ACTIVE` as an internal safety gate during `git clone --recurse-submodules` to reject a maliciously crafted repository whose nested submodule/tree layout would let the checkout process write (or symlink) a path that collides with the top-level `.git` directory (e.g. `.git/hooks`), which is the mechanism behind the "arbitrary file write leading to hook execution during clone" class of Git vulnerabilities. GitHub Desktop's `clone()` function unconditionally forces this protection off for every clone the user performs, matching the external report's broken invariant: an attacker-controlled external input (here, a malicious repository/URL instead of a compromised LST) can, in a single unprivileged legitimate-looking action (cloning), immediately escalate to a far more dangerous state (writing outside the intended repo boundary / hook execution) with no cooldown, confirmation, or defensive gate in between.

### Finding Description
`clone()` builds its environment as:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
``` [2](#0-1) 

and always passes `--recursive` to `git clone`: [3](#0-2) 

The only mitigation present in this code path is `isClonePathSensitive()`, which merely blocks the *destination* directory from being certain sensitive host paths (home dir, `.ssh`, `.gnupg`, etc.) — it does nothing to validate the *contents* of the remote repository being cloned: [4](#0-3) 

That destination check does not stop a crafted upstream repository from containing nested submodules/paths engineered to collide (via case-folding on case-insensitive filesystems, or symlink tricks) with `.git/hooks` or similar sensitive locations inside the *newly created worktree itself*. Git's own protection for exactly this scenario is what `GIT_CLONE_PROTECTION_ACTIVE` gates, and Desktop disables it outright rather than only in a scoped, justified case.

Compare this to `updateSubmodulesAfterOperation`, which is far more careful — it only allows `protocol.file.allow=always` when the caller explicitly opts in via `allowFileProtocol`, showing the team is otherwise aware of the git-submodule threat model: [5](#0-4) 

`clone.ts`, however, applies its permissive override unconditionally to every "Clone repository" action in the app, including cloning of arbitrary/public repositories that the user does not control and has never inspected, satisfying the "attacker controls a cloned/fetched repository" impact criterion.

### Impact Explanation
If exploitable against the bundled Git/dugite version, a victim who simply clicks "Clone" on a malicious repository URL (e.g., pasted from a phishing link, forked/renamed repo, or malicious GitHub org) can trigger a write outside the intended repository tree — most critically, a Git hook file placed into `.git/hooks` of the freshly cloned repository. Because GitHub Desktop's clone flow runs `--recursive` and then the resulting repository is immediately usable, any subsequently triggered hook (e.g., `post-checkout`, run automatically as part of the same clone/checkout sequence) executes attacker-supplied code with the user's OS-level privileges. This is full local code execution triggered purely by cloning an untrusted repository — the strongest impact category listed (code execution / file write outside the repo) for the least amount of attacker effort (an unprivileged, remotely hosted git repo).

### Likelihood Explanation
Likelihood is high for the following reasons:
- Cloning arbitrary/untrusted repository URLs is a core, expected GitHub Desktop workflow (there's a dedicated `_clone`/`cloneAgain` flow and UI), so no unnatural user steps are required beyond the normal "paste URL and clone."
- `GIT_CLONE_PROTECTION_ACTIVE: 'false'` is applied unconditionally to *every* clone, not just trusted/first-party repos, so the protection is off exactly when it matters (cloning something the user has not yet vetted).
- `isClonePathSensitive` cannot detect this attack class since it only inspects the destination path chosen by the user/UI, not the malicious repository's internal tree/submodule structure.
- The equivalent, narrowly-scoped `protocol.file.allow`/`allowFileProtocol` pattern used elsewhere in the codebase (`submodule.ts`) shows the team already treats this general threat model as real elsewhere, making the blanket disablement in `clone.ts` an inconsistent, overlooked gap rather than an intentionally-reviewed tradeoff.

### Recommendation
Remove the blanket `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()`. Let Git's built-in clone protection remain active by default for all recursive clones of remote/untrusted URLs. If a legitimate need exists to disable it (e.g., for specific known-safe/local re-clone operations), scope the override narrowly and only after the repository has been validated, mirroring the `allowFileProtocol` opt-in pattern already used in `updateSubmodulesAfterOperation`. Add a regression test asserting that `clone()` does not set `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` for network/remote URLs.

### Proof of Concept
1. Attacker crafts and hosts a Git repository containing a submodule/tree structure designed to collide with `.git/hooks` on checkout (case-insensitive filesystem collision or symlinked submodule `.git` directory), with a malicious `post-checkout` (or similar) hook payload.
2. Victim opens GitHub Desktop and clones the attacker's repository URL via the normal "Clone repository" UI, which invokes `_clone()` → `cloningRepositoriesStore.clone()` → `clone()`.
3. `clone()` executes `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'` [6](#0-5) , disabling Git's own defense against the crafted layout.
4. During the recursive submodule checkout, the malicious hook file is written into `.git/hooks` inside the newly cloned working directory.
5. The hook subsequently executes automatically as part of normal Git/Desktop operations (checkout, commit, etc.), achieving code execution on the victim's machine with no further user action beyond the initial clone.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

    '-c',
