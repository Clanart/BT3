### Title
Reward tier bypass via mWomSV unlock/relock cycle drains finite MGP incentive pool - (File: wombat/ArbWomUp3.sol)

### Summary
`incentiveDeposit(_mode==2)` computes the vlMGP lock bonus from `mWomSV.getUserTotalLocked(_account)`, a mutable, decreasable balance, rather than a monotonic cumulative-deposit counter. Because `mWomSV` allows a user to `startUnlock`/`unlock` their locked mWom after a cooldown, an attacker can cycle lock → unlock → relock to repeatedly reset their tier baseline to zero and re-earn the low-tier `rewardMultiplier` bonus (doubled for mode 2) on capital that was never a genuine net-new deposit, draining the contract's finite `mgp` reward balance.

### Finding Description
`getRewardAmount`/`calDoubledCounted` derive the reward strictly from the account's currently locked balance in `mWomSV`: [1](#0-0) [2](#0-1) 

`_deposit` for mode 2 locks the freshly deposited mWom into `mWomSV` on behalf of the user via `lockFor`: [3](#0-2) 

`mWomSV` exposes unprivileged `startUnlock`/`unlock` functions that let the user withdraw previously locked mWom back to their wallet after a configurable `coolDownInSecs`: [4](#0-3) 

The `bracketRewarded` mapping, which appears to have been intended to track a monotonic per-account reward/tier state, is explicitly unused (`// not in use`): [5](#0-4) 

Exploit flow:
1. Attacker calls `incentiveDeposit(X, ratio, false, 2)` with `getUserTotalLocked == 0`. Reward is computed for the 0→X tier movement, doubled, and `vlMGP.lockFor` mints vlMGP to the attacker; `X/2` worth of mWom is locked into `mWomSV`.
2. Attacker calls `mWomSV.startUnlock(...)` for their locked mWom, waits `coolDownInSecs`, then calls `mWomSV.unlock(slotIndex)`, receiving the underlying mWOM back and reducing `getUserTotalLocked(attacker)` to 0.
3. Attacker calls `incentiveDeposit` again with new (or converted) WOM. Since `mWomSV.getUserTotalLocked(attacker)` is again 0, `calDoubledCounted` returns 0 and the full 0→X tier reward (doubled) is granted again via `vlMGP.lockFor`.
4. Repeating this loop lets the attacker extract the doubled low-tier bonus multiple times from the same effective capital, limited only by the cooldown period and the finite `mgp` balance held by `ArbWomUp3`.

Existing protections do not stop this: `nonReentrant`/`whenNotPaused` guard against reentrancy/pausing, not against sequential calls across blocks; there is no cumulative-deposit tracking, no per-account claim cap, and `bracketRewarded` (which could have served this purpose) is dead code.

### Impact Explanation
This results in theft/drain of the protocol's limited `mgp` reward reserve (Immunefi: theft of unclaimed yield / protocol funds). Legitimate depositors receive fewer or zero MGP rewards once the pool is exhausted by the exploit loop (`getRewardAmount` caps at `mgpleft`, so the impact is a redistribution of the whole incentive budget to the attacker instead of proportional distribution to genuine new depositors).

### Likelihood Explanation
No privileged role is required — any EOA holding WOM can lock/unlock/relock. The only cost is the `coolDownInSecs` delay per cycle and gas, so repeatability is bounded by time rather than any economic or access barrier, making this a low-cost, high-repeatability drain over the life of the contract's MGP reward allocation.

### Recommendation
Track a monotonic, non-decreasing cumulative-locked-via-this-contract counter per account (e.g., re-purpose `bracketRewarded` to store the highest tier/amount ever rewarded) and compute `calDoubledCounted`/tier rewards against that counter instead of the live, decreasable `mWomSV.getUserTotalLocked(_account)`. Only grant incremental reward for genuinely new cumulative deposits beyond the previous high-water mark.

### Proof of Concept
Foundry test outline:
1. Deploy `ArbWomUp3`, `mWomSV`, `MasterMagpie`, mock `mWom`/`wom`/`mgp` tokens, fund `ArbWomUp3` with `mgp`, set `rewardTier`/`rewardMultiplier`.
2. Attacker calls `incentiveDeposit(X, ratio, false, 2)`; record vlMGP minted (`R1`).
3. Attacker calls `mWomSV.startUnlock(mWomSV.getUserTotalLocked(attacker))`, warp `coolDownInSecs`, call `mWomSV.unlock(0)`.
4. Assert `mWomSV.getUserTotalLocked(attacker) == 0`.
5. Attacker calls `incentiveDeposit(X, ratio, false, 2)` again with fresh WOM; record vlMGP minted (`R2`).
6. Assert `R1 == R2` (full tier bonus re-earned) and `R1 + R2` exceeds the single-pass tier-schedule reward for total capital `X` locked once — demonstrating the reward pool is drained disproportionately relative to net capital contributed.
