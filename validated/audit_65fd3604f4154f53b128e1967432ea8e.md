### Title
Coinbase outputs are reported as spendable funds before maturity - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` scans every transaction in a Bitcoin block, including the coinbase transaction at `block.txdata[0]`. [1](#0-0)  Bitcoin coinbase outputs cannot be spent for 100 blocks, but `Scanner` returns them as ordinary `ReceivedOutput` values without recording coinbase status or maturity. [2](#0-1) [3](#0-2)  The resulting output can be passed directly to `SignableTransaction::new`, which treats it as immediately spendable input value. [4](#0-3) [5](#0-4) 

### Finding Description
`scan_transaction` emits a `ReceivedOutput` whenever an output's `script_pubkey` matches a registered scanner script. [6](#0-5)  `scan_block` applies that function to `block.txdata` without skipping index zero, so the block's coinbase transaction is classified using the same representation as normal spendable UTXOs. [1](#0-0)  The comment explicitly acknowledges that coinbase outputs are maturity-bound and requires callers to remove them separately. [3](#0-2) 

`ReceivedOutput` stores only an offset, a claimed `TxOut`, and an `OutPoint`; it has no coinbase, confirmation-height, or maturity field. [2](#0-1)  `SignableTransaction::new` then sums `input.output.value` as available input value and places every supplied `outpoint` into a transaction input without any maturity check. [5](#0-4)  During signing, the implementation validates that the configured offset derives the key expected by the declared previous output script, but still performs no coinbase-specific validation. [7](#0-6) 

This is the same boundary failure as the reported stake/prepayment issue: two asset categories with different spending rules are collapsed into one undifferentiated balance representation. [2](#0-1) [8](#0-7) 

### Impact Explanation
A miner, or another party able to cause a coinbase reward to pay a scanned address, can make `scan_block` report funds that cannot legally be spent for 100 blocks. [8](#0-7)  A downstream caller relying on the scanner result can report these funds as received and usable, construct a transaction consuming them, and obtain threshold signatures for a transaction Bitcoin consensus rejects as immature. [5](#0-4) [9](#0-8)  This concretely produces funds reported received that are not spendable and can cause an unnecessary signing round for an invalid transaction. [3](#0-2) 

### Likelihood Explanation
Coinbase outputs are present in every Bitcoin block, and any output paying a registered scanner script is returned by `scan_transaction`. [6](#0-5) [1](#0-0)  Producing such a coinbase requires mining a block or controlling where a mined block's reward pays, which is permissionless but carries the normal mining prerequisite. [3](#0-2)  No private key, validator privilege, malformed curve input, or malicious node response is required beyond causing the coinbase to pay a registered P2TR script. [10](#0-9) [6](#0-5) 

### Recommendation
Keep immature coinbase outputs out of the ordinary `ReceivedOutput` set by having `scan_block` skip `block.txdata[0]` or return a separately typed `ImmatureCoinbaseOutput` carrying the block height/maturity. [8](#0-7)  If immature outputs must be tracked, persist enough provenance to prevent `SignableTransaction::new` from accepting them before maturity; alternatively, give `SignableTransaction::new` an explicit spendability/maturity check so distinct funds cannot be silently treated as equivalent inputs. [4](#0-3) [5](#0-4) 

### Proof of Concept
1. Construct `Scanner::new(key)` for an even Taproot group key so the base P2TR script is registered. [10](#0-9) 
2. Mine or otherwise supply a valid block whose coinbase transaction contains an output paying that P2TR script.
3. Call `Scanner::scan_block(&block)`; `scan_block` iterates all transactions and therefore scans `txdata[0]`. [1](#0-0) 
4. `scan_transaction` returns the coinbase output as a normal `ReceivedOutput` with the registered offset and its outpoint. [6](#0-5) 
5. Pass that `ReceivedOutput` to `SignableTransaction::new`; its value contributes to `input_sat`, and its outpoint becomes a normal `TxIn`. [5](#0-4) 
6. `multisig` accepts the input when the offset-derived key matches the declared script, and `sign` produces the Taproot key-spend sighash for it. [7](#0-6) [11](#0-10) 
7. The signed transaction is invalid under Bitcoin consensus until the coinbase reaches maturity, despite the scanner having reported the output as received and the wallet having treated it as spendable. [3](#0-2)
