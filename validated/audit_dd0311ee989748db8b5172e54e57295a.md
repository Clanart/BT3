### Title
Attacker-controlled `n`/`t` in `ThresholdKeys::read` triggers quadratic Lagrange interpolation during `ThresholdKeys::new`, causing CPU-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes `t`, `n`, and `i` directly from untrusted bytes with no upper bound beyond `u16::MAX`, then reads `n` verification shares and calls `ThresholdKeys::new`. With `Interpolation::Lagrange` selected, `ThresholdKeys::new` computes the group key by calling `interpolation_factor` for each of `1..=t` participants, and each `interpolation_factor` call loops over all `t` included participants plus a field inversion. This is O(t²) field multiplications plus `t` inversions — work quadratically larger than the input bytes, directly analogous to CVE-2020-36311's amplification of a small trigger into an expensive teardown.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t` and `n` as raw `u16`s (lines 591–602), optionally reads `n` constant-interpolation scalars (lines 607–613), then reads `n` group elements as verification shares (lines 620–623) and passes everything to `ThresholdKeys::new` (lines 625–631). [1](#0-0) 

`ThresholdKeys::new` builds `t = participants 1..=t` and computes `group_key = Σ verification_shares[i] * interpolation_factor(i, t)` (lines 376–378). [2](#0-1) 

For `Interpolation::Lagrange`, `interpolation_factor` iterates over the entire `included` set performing two field multiplications per element, and finishes with a field inversion `denom.invert().unwrap()` (lines 229–247). [3](#0-2) 

Total work: `t` point scalar-multiplications plus `t` interpolation factors each costing O(t) field multiplications and one inversion — i.e. O(t²) field ops plus `t` inversions. With `t = n = 65535` (both valid under `ThresholdParams::new`, which only requires `0 < t <= n`, lines 166–178), that is ~4.3×10⁹ field multiplications and 65535 modular inversions, triggered by an input of only ~2 MB (65535 compressed points ≈ 32–33 bytes each). [4](#0-3) 

The `Participant::new` check on `i` and the `t <= n` check are the only validations; there is no cap on `n` anywhere in the read path or in `ThresholdKeys::new`.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (e.g. any code path that deserializes threshold keys from network messages, stored/relayed data, or IPC before sanity-checking params) can force the victim to perform billions of field operations and tens of thousands of inversions in a single synchronous call. This is a CPU-bound denial of service — the analog of the kernel soft-lockup in CVE-2020-36311 — stalling the signing/key-management thread handling the input. The amplification factor (~2 MB input → ~10⁹–10¹⁰ scalar ops) makes it practical, and the cost is paid before any cryptographic validity check on the shares could reject the input.

### Likelihood Explanation
Reachability requires a deployment feeding untrusted bytes into `ThresholdKeys::read`, which is exactly the documented untrusted-input surface for this format. No signature, proof, or honest-participant cooperation is needed — the cost is incurred purely in deserialization/parameter validation. Likelihood depends on deployment exposure, but within the stated scope (untrusted bytes fed to `ThresholdKeys::read`) the attack is fully deterministic and needs only a ~2 MB crafted buffer.

### Recommendation
Enforce a sane maximum on `n` (and hence `t`) in `ThresholdKeys::read` and/or `ThresholdParams::new` before reading the share vector or computing the group key — e.g. reject `n` above a protocol-bounded value (the protocol's real validator-set bound). Alternatively, compute `group_key` via a multiexp-friendly formulation or bound the interpolation work proportional to input size. At minimum, perform the `ThresholdParams::new` validation *before* reading `n` group elements so oversized `n` is rejected after 6 bytes.

### Proof of Concept
Conceptual byte stream fed to `ThresholdKeys::<Ristretto>::read`:

```text
u32 LE len(C::ID) || C::ID                      // curve ID check passes
u16 LE t = 0xFFFF                                // 65535
u16 LE n = 0xFFFF                                // 65535
u16 LE i = 0x0001                                // valid participant
u8     interpolation = 1                         // Lagrange
32B    secret_share                              // any valid scalar
65535 * 32B verification_shares                  // any valid compressed points
```

`ThresholdParams::new(65535, 65535, p1)` succeeds. `ThresholdKeys::new` then computes `group_key` as a sum of 65535 terms, each calling `interpolation_factor` which loops over 65535 participants (~2 field muls each) and performs one inversion — ~4.3 billion field multiplications and 65535 inversions from a ~2 MB input, blocking the calling thread.
