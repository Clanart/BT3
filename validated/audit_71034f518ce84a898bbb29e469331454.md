Confirmed: no check anywhere binds the `username` string parsed out of the ssh prompt to the actual host/remote the current git operation (`operationGUID`) is talking to — credential storage/lookup is keyed purely on that free-form string.

### Title
Stored SSH password disclosure via server-controlled password-prompt spoofing - (File: `app/src/lib/trampoline/trampoline-askpass-handler.ts`)

### Summary
`handleSSHUserPassword` treats the entire `user@host` string embedded in the ssh "password:" prompt as trusted input for looking up and auto-supplying a previously-stored SSH password, with no verification that this string actually corresponds to the host the current git operation is connecting to.

### Finding Description
`handleSSHUserPassword` extracts the `username` capture group from the prompt text via `/^(.+@.+)'s password: $/` [1](#0-0)  and immediately uses it as a lookup key: `getSSHUserPassword(username)`, returning the stored secret without prompting the user if found [2](#0-1) . That lookup goes straight to the OS credential store (`TokenStore.getItem(SSHUserPasswordTokenStoreKey, username)`) using `username` as the sole key [3](#0-2) .

This prompt text is not produced solely by the local ssh client from a value the client itself independently resolved — the trampoline/askpass mechanism forwards to Desktop whatever literal prompt text `ssh` is asked to display for a non-tty authentication challenge, including the single, non-echoed prompt strings from keyboard-interactive authentication, which are supplied by the remote SSH server. Because Desktop trusts any git remote (including one from a cloned repository's submodule URL) to reach an arbitrary SSH endpoint, a malicious or attacker-controlled SSH server can issue a keyboard-interactive challenge whose prompt text is crafted to exactly match the regex `^(.+@.+)'s password: $`, embedding an attacker-chosen "username" — e.g. the exact string previously used as the storage key for the user's real GitHub/GitLab SSH password (such as `git@github.com`).

Nothing in `handleSSHUserPassword`, `getSSHUserPassword`, or the credential-storage layer (`ssh-credential-storage.ts`) verifies that the claimed username/host in the prompt matches the actual remote/operation in progress [4](#0-3) . As a result, when the crafted prompt matches an existing storage key, Desktop will silently return the stored secret and feed it back into the ssh session — which is connected to the attacker's server, not the legitimate one the credential was originally created for.

### Impact Explanation
If a user has ever chosen to save an SSH password for a real host (e.g. `git@github.com`) via `promptSSHUserPassword`'s "store" option, that secret becomes retrievable by any subsequent SSH connection (to any attacker-controlled host reachable from a submodule URL, custom remote, or deep link that triggers a fetch/clone) as long as the malicious server can make its keyboard-interactive challenge text match the stored key. This is credential exfiltration of a real, reusable SSH password with no user interaction beyond Desktop performing a normal fetch/clone/push against the malicious remote.

### Likelihood Explanation
Requires (1) the victim to have previously stored an SSH password with Desktop for some host, and (2) the victim's Desktop to perform a git operation against an attacker-controlled SSH remote (trivially achievable via a malicious submodule URL in a cloned repo, or a maliciously configured remote reachable via a deep link/import flow). Both preconditions are realistic for users who use SSH password auth (common in enterprise/self-hosted Git setups) and interact with untrusted repositories, keeping likelihood moderate rather than trivial, since it also depends on the attacker guessing/knowing the exact key string (`user@host`) used previously — which is often predictable (`git@github.com`, `git@gitlab.com`, or the victim's own enterprise host).

### Recommendation
Bind the stored credential lookup/write to the actual expected remote host for the current operation (e.g. compare against the resolved host of the git remote associated with `operationGUID`/`trampolineToken`) rather than trusting the free-form string embedded in the ssh-emitted prompt. Reject or re-prompt (rather than silently auto-supplying a stored secret) when the prompt's claimed host does not match the operation's known target host.

### Proof of Concept
1. User has previously used Desktop to SSH-authenticate with password to `git@github.com` and chosen "remember password."
2. Attacker publishes a repository with a submodule pointing to `ssh://attacker.example.com/x`, running a modified OpenSSH server that offers keyboard-interactive auth with a single, non-echoed prompt whose text is exactly `git@github.com's password: `.
3. Victim clones/fetches the repository (or updates submodules) in Desktop, triggering the trampoline askpass flow against `attacker.example.com`.
4. `handleSSHUserPassword` parses `username = "git@github.com"`, calls `getSSHUserPassword("git@github.com")`, retrieves the victim's real stored GitHub password, and returns it as the keyboard-interactive response — which is sent to `attacker.example.com`, disclosing the victim's real GitHub SSH password to the attacker.

export async function getSSHUserPassword(username: string) {
  try {
    return TokenStore.getItem(SSHUserPasswordTokenStoreKey, username)
  } catch (e) {
    log.error('Could not retrieve passphrase for SSH key:', e)
    return null
  }
}
