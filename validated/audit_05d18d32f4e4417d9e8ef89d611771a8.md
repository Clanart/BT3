### Title
Stale Light Client Proof Returned Without Block-Height Validation Causes Operator Collateral Loss Under Reorg — (`File: core/src/citrea.rs`)

### Summary

`fetch_validate_and_store_lcp` caches the Light Client Proof (LCP) keyed only by `deposit_id` and, on every subsequent call, returns the cached receipt unconditionally — ignoring the `payout_block_height` argument entirely. The DB insert uses `ON CONFLICT (deposit_id) DO NOTHING`, making the stored LCP permanently immutable. After a Bitcoin reorg that moves the payout transaction into a different block, the operator's `send_asserts` path retrieves the stale LCP (anchored to the old block hash), feeds it into the bridge circuit alongside an SPV proof for the new block, and the circuit panics on the L1-block-hash mismatch check. The operator is unable to produce a valid assert proof, cannot defend against the open challenge, and forfeits their collateral.

### Impact Explanation

The operator cannot produce a valid Groth16 bridge-circuit proof. Without a valid proof, the operator cannot post the required assert transactions to defend against the open challenge. The challenger can then spend the burn connector and slash the operator's full collateral. This is a direct, material loss of operator collateral — an impact explicitly listed in the allowed-impact gate.

### Likelihood Explanation

Bitcoin reorgs of 1–2 blocks occur regularly on mainnet (several times per year). The window of vulnerability is the period between when the LCP is first stored (at kickoff time, via `PayoutCheckerTask` or `queue_relevant_txs_for_new_kickoff`) and when `send_asserts` is executed (which can be many blocks later, after all watchtower challenge timeouts expire). A challenger who monitors for reorgs and immediately challenges a kickoff whose payout block was reorganized can reliably trigger this path. The code has a scoped validation failure — it accepts `payout_block_height` as a parameter but never uses it on a cache hit — which is the in-scope trigger condition per the researcher guidelines ("honest external chain behavior unless scoped validation fails").

### Recommendation

1. Add `payout_block_height` (or `payout_block_hash`) as a column in `lcp_for_asserts` and include it in the primary key or a unique constraint.
2. Change `ON CONFLICT (deposit_id) DO NOTHING` to `ON CONFLICT (deposit_id) DO UPDATE SET lcp_receipt = EXCLUDED.lcp_receipt WHERE ...` when the stored block height differs from the requested one, or simply delete and re-insert.
3. In `fetch_validate_and_store_lcp`, after retrieving a cached LCP, deserialize it and assert that `latest_da_state.block_hash` matches the block hash at `payout_block_height` before returning it; if it does not match, fetch and store a fresh LCP.

### Proof of Concept

1. Operator fronts a withdrawal; payout transaction lands in Bitcoin block B₁ at height H₁.
2. `PayoutCheckerTask::run_once` fires, calls `fetch_validate_and_store_lcp(H₁, citrea_idx, ...)`. LCP for B₁ is fetched and stored in `lcp_for_asserts` with key `deposit_id = citrea_idx`.
3. A 1-block reorg occurs; the payout transaction is re-mined in block B₂ at height H₂ (H₂ ≠ H₁). The `bitcoin_syncer` updates `is_canonical` and the payout block hash in the operator's DB now resolves to B₂/H₂.
4. A challenger spends the challenge connector; the kickoff state machine transitions to `Challenged` and eventually dispatches `Duty::SendOperatorAsserts`.
5. `send_asserts` calls `get_full_block_from_hash(payout_block_hash)` → returns B₂, H₂.
6. `send_asserts` calls `fetch_validate_and_store_lcp(H₂, citrea_idx, ...)`. The function finds the existing row for `citrea_idx` and returns the LCP for B₁ without fetching a new one.
7. The bridge circuit input is assembled: SPV anchors to B₂ (`spv_l1_block_hash = hash(B₂)`), LCP carries `latest_da_state.block_hash = hash(B₁)`.
8. `bridge_circuit` panics: `"L1 block hash mismatch: expected hash(B₁), got hash(B₂)"`. Proof generation fails.

    /// Saves the light client proof for a deposit to be used while sending an assert.
    /// We save first before sending kickoff to be sure we have the LCP available if we need to assert.
    pub async fn insert_lcp_for_assert(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
        lcp: Receipt,
    ) -> Result<(), BridgeError> {
        let query = sqlx::query(
            "INSERT INTO lcp_for_asserts (deposit_id, lcp_receipt)
             VALUES ($1, $2)
             ON CONFLICT (deposit_id) DO NOTHING;",
        )
        .bind(i32::try_from(deposit_id).wrap_err("Failed to convert deposit id to i32")?)
        .bind(ReceiptDB(lcp));

        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
