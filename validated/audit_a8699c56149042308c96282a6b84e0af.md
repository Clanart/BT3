### Title
Missing lower-bound validation on `kip71.gastarget` causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: `kaiax/gov/param.go`, `params/kip71_config.go`)

### Summary
The external report's bug class is "a value that is used as a divisor is not validated to be non-zero, causing corrupted/undefined arithmetic results that are trusted downstream." The same class of bug exists in Kaia's KIP-71 governance parameter validation: `Kip71GasTarget` is the only KIP-71 numeric parameter that uses `noopFormatChecker` (no validation at all), while its sibling `Kip71BaseFeeDenominator` explicitly rejects zero. `GasTarget` is used unconditionally as a divisor in `NextMagmaBlockBaseFee`, so a governance-set value of `0` triggers a runtime division-by-zero panic on every node that computes the next base fee — which happens on every single block.

### Finding Description
In `kaiax/gov/param.go`, the parameter table validates `Kip71BaseFeeDenominator` to reject zero: [1](#0-0) 

But `Kip71GasTarget`, defined immediately below it, uses `noopFormatChecker`, which always returns `true` regardless of value: [2](#0-1) [3](#0-2) 

This means a governance vote (via headergov `kip71.gastarget` vote, or via the on-chain `GovParam` contract's `setParam`/`setParamIn`, callable by the contract owner) can set `GasTarget = 0` and pass all format-checking with no rejection.

That value is consumed directly as a divisor in `params/kip71_config.go`'s `NextMagmaBlockBaseFee`, which is the KIP-71 (Magma) dynamic base-fee calculation: [4](#0-3) 

Specifically, when `parentGasUsed > gasTarget` (which is true for essentially any block with `GasTarget == 0` and non-zero gas usage):
```
y := x.Div(x, new(big.Int).SetUint64(gasTarget))
```
`math/big.Int.Div` panics on division by zero. Since `gasTarget` comes straight from the unvalidated governance parameter, this line panics with `GasTarget = 0`.

This function is not an isolated utility — it is invoked in the header/state-transition hot path on every node for every block, including:
- `blockchain/block_validator.go` (header validation, calling `VerifyMagmaHeader` → `NextMagmaBlockBaseFee`)
- `blockchain/chain_makers.go`, `work/worker.go` (block assembly)
- `blockchain/tx_pool.go` (fee-based tx admission)
- `node/cn/gasprice/gasprice.go` and `node/cn/gasprice/feehistory.go` (gas price oracle / `eth_feeHistory`)

Because the panic occurs deterministically on identical input for every full node, once the parameter takes effect, *all* nodes computing/verifying the affected header would panic identically, halting block production and RPC service network-wide.

### Impact Explanation
This is a high-severity governance-parameter validation gap: a single malformed but syntactically "valid" governance parameter (`GasTarget = 0`) crashes core state-transition code paths (header verification, block building, gas price oracle, tx pool admission) on every Kaia node once the value becomes active. This constitutes a chain-wide denial of service / consensus halt reachable through the governance parameter surface explicitly listed as in-scope, directly analogous to the original report's theme of "missing validation of a value that later serves as a divisor, leading to unchecked arithmetic corruption trusted by downstream logic."

### Likelihood Explanation
Reaching this requires setting `GasTarget = 0` through the governance-parameter mechanism (headergov vote under the mode-appropriate approval process, or `GovParam.setParam`/`setParamIn` by the contract owner under KIP-81 contract governance). This is gated by governance permissions, not by an arbitrary unprivileged sender, but it is squarely within the "governance parameters" reachability category explicitly listed as in-scope for this analog search. Given `noopFormatChecker` performs zero validation (unlike the adjacent `BaseFeeDenominator` check), this is a straightforward, unintentional omission rather than a defense-in-depth gap — one governance action away from a full network panic.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0`, mirroring the existing check used for `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, as defense in depth, `NextMagmaBlockBaseFee` in `params/kip71_config.go` should guard against `gasTarget == 0` (e.g., treat it the same way `BaseFeeDenominator == 0` is defensively handled at line 71-76 of that file) so that a zero value cannot reach the `big.Int.Div` call regardless of how it entered the parameter set.

### Proof of Concept
1. Under contract governance (KIP-81), the `GovParam` contract owner calls `setParamIn("kip71.gastarget", true, <bytes for uint64(0)>, activation)` — this succeeds because `Kip71GasTarget`'s `FormatChecker` is a no-op and does not reject zero, unlike `Kip71BaseFeeDenominator`. [2](#0-1) 
2. Once the parameter's activation block is reached, `contractGovModule.GetParamSet` / `headergov` propagate `GasTarget = 0` into the effective `ParamSet`, which is converted via `ParamSet.ToKip71Config()`: [5](#0-4) 
3. On the next block after activation with any nonzero `GasUsed` (virtually guaranteed), `NextMagmaBlockBaseFee` executes the `parentGasUsed > gasTarget` branch and calls `x.Div(x, new(big.Int).SetUint64(0))`: [6](#0-5) 
4. `math/big.Int.Div` panics on divide-by-zero. Since this function is called from header verification (`blockchain/block_validator.go`), block assembly (`work/worker.go`), the gas price oracle (`node/cn/gasprice/gasprice.go`), and fee history (`node/cn/gasprice/feehistory.go`), every full node reaching this code path panics identically, resulting in a coordinated crash of block production/validation across the network — a chain halt.

Note: I was not able to directly view the full body of `blockchain/block_validator.go` to quote the exact call line to `VerifyMagmaHeader` (only confirmed its single reference via search) due to index size limits; a Devin session with full repository access could confirm and quote that exact call site for completeness.
