### Title
Untrusted `ReceivedOutput::read` bytes allow arbitrary offset/output pairing, producing deposits that are reported received but are unspendable or attacker-redirected - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) deserializes a scalar `offset`, a `TxOut`, and an `OutPoint` directly from attacker-controlled bytes, with no consistency check that `output.script_pubkey` equals `p2tr_script_buf(group_key + offset·G)` — the only condition under which the offset actually authorizes spending. Analogous to CVE-2021-23258, where an attacker-supplied expression is evaluated in a privileged context, here attacker-supplied bytes are interpreted as a privileged "this output belongs to the group key" assertion. The producer side (`Scanner::scan_transaction`, lines 199-214) guarantees that invariant by only emitting offsets looked up in `self.scripts`, but `read` re-establishes the object from raw bytes and silently drops the invariant.

### Finding Description

`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` (line 155) populated by `register_offset` (line 180), which documents that "Arbitrary offsets may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script" (lines 177-179). `scan_transaction` only creates a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` succeeds, i.e., the script was derived from the group's key plus a registered offset (lines 205-211).

`ReceivedOutput::read` performs no equivalent validation. It reads:
- `offset` via `Secp256k1::read_F` — an arbitrary scalar,
- `output` via `TxOut::consensus_decode` — an arbitrary `script_pubkey` and value,
- `outpoint` via `OutPoint::consensus_decode` — an arbitrary txid/vout (lines 123-131).

Any downstream consumer that reconstructs a `ReceivedOutput` from wire bytes (rather than trusting only `Scanner` output) therefore accepts three failure modes:

1. **Valid script_pubkey, wrong offset**: the derived spend key `group_key + offset·G` does not match the script's output key, so threshold signing produces a BIP-340 signature over the wrong key. Funds are reported received but can never be spent — a permanent loss-of-funds-lockup for that output.
2. **Valid real deposit output, fabricated outpoint or value**: `value()` (line 116) returns the attacker-claimed amount and `outpoint()` (line 110) the attacker-claimed UTXO. A claimed deposit can be inflated in value or pointed at a non-existent output.
3. **Mismatched key/script**: because `p2tr_script_buf` (line 80) uses `TweakedPublicKey::dangerous_assume_tweaked`, the output key position is interpreted as an already-tweaked Taproot key; an attacker who controls the (offset, script_pubkey) pair can encode a script path commitment into the claimed output key — precisely the script-path-spend hazard `register_offset`'s documentation warns about — while the Serai side believes the output is signature-spendable by the group key.

The SpEL analogy: untrusted input is treated as an already-authorized instruction ("this output is owned/spendable by the group") without the evaluation context re-checking it. The integrity guarantee exists only at construction time in `Scanner`, not at deserialization time.

### Impact Explanation

An unprivileged party who can feed bytes to `ReceivedOutput::read` (e.g., any channel that transports serialized `ReceivedOutput`s to a signer/processor rather than locally scanner-derived objects) can cause the Serai key set to be credited with outputs it cannot spend: incorrect offsets yield unspendable deposits (denial of spendability for real deposits whose records are substituted), fabricated `TxOut.value`/`OutPoint` fields misreport balances and reference non-existent UTXOs, and attacker-chosen script_pubkey/offset pairs can assert ownership of outputs under keys other than the group key. This satisfies "funds reported received that are not spendable."

### Likelihood Explanation

Reachability depends on the deployment deserializing `ReceivedOutput`s from untrusted bytes; the type exposes a public `read`/`serialize` pair intended for transport, and the audit scope explicitly designates `ReceivedOutput::read` as an untrusted-input sink. The defect requires no cryptographic attack — only byte-level control — matching the CVE's authenticated-attacker-to-RCE shape (low complexity once the input path exists). Impact is bounded to accounting/spendability rather than key extraction.

### Recommendation

Bind the offset to the output at use time. Either:
- Carry the expected `ScriptBuf` (or the owning `Scanner`) alongside deserialized `ReceivedOutput`s and assert `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)` before treating the output as spendable, or
- Have consumers re-derive the offset via `Scanner` (`scripts.get(&output.script_pubkey)`) and ignore the serialized `offset` field entirely, treating the wire form as `(TxOut, OutPoint)` only, or
- HMAC/sign serialized `ReceivedOutput`s so they are only accepted from the local scanner.

### Proof of Concept

```rust
// Attacker crafts ReceivedOutput bytes for a real deposit whose actual
// script_pubkey was produced by Scanner with offset o_real.
// They serialize: offset = o_real + 1 (or any scalar), the real TxOut, real OutPoint.
let mut bytes = Vec::new();
bytes.extend((real_offset + Scalar::ONE).to_bytes());       // wrong offset
bytes.extend(bitcoin::consensus::encode::serialize(&real_txout)); // real script_pubkey
bytes.extend(bitcoin::consensus::encode::serialize(&real_outpoint));

let claimed = ReceivedOutput::read(&mut &bytes[..]).unwrap();
// read() succeeds; claimed.offset() no longer maps group_key to real_txout.script_pubkey.
// Any signing attempt for `claimed` produces a signature under key + (o_real+1)·G,
// which does not satisfy the output's Taproot key spend -> deposit is bricked.
//
// Variant: claim TxOut{ value: 1_000_000_000, script_pubkey: <registered script> }
// with an outpoint that never appeared on-chain -> phantom balance reported.
```

The invariant enforced at line 205 (`self.scripts.get(&output.script_pubkey)`) is absent at line 122, letting attacker bytes fabricate the "scanned and owned" property.
