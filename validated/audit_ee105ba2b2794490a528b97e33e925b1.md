## Analysis

The external report's bug class is "a value that must go through exactly one transform ends up going through the wrong transform (or skipping it) because two different functions are used for what should be the same check," causing an invariant that holds in one code path to silently not hold in another. In `alchemix-v2-dao/FluxToken.sol` this was two multipliers wired incorrectly; in GitHub Desktop the closest analog is two different "is this ref name safe" functions being used inconsistently between the deep-link handler and the git-command builder, letting attacker-controlled strings that "look validated" reach `git checkout` as a leading argument.

### Title
Deep-link `branch` parameter bypasses leading-dash stripping and can be interpreted as a `git checkout` flag - (File: `app/src/lib/parse-app-url.ts`)

### Summary
GitHub Desktop registers an OS-level `x-github-client://openrepo/...` protocol handler. The `branch` query parameter of that URL is validated with `testForInvalidChars()` [1](#0-0)  and then propagated unmodified into `checkoutLocalBranch` via `openBranchNameFromUrl` [2](#0-1) . Unlike the sibling sanitizer `sanitizedRefName()`, which explicitly strips leading `-`/`+` characters before a ref name is used anywhere else in the app [3](#0-2) , `testForInvalidChars()` reuses the same `invalidCharacterRegex` but that regex contains no rule that rejects or strips a leading dash [4](#0-3) . The two "ref safety" functions are not equivalent, yet the deep-link path only calls the weaker one.

### Finding Description
`sanitizedRefName` is the function Desktop relies on everywhere a user types a branch name (create/rename branch dialogs) to guarantee the resulting string can't be confused with a CLI flag, explicitly via `.replace(/^[-\+]*/g, '')` [5](#0-4) . This is confirmed by the unit tests asserting `--but-can-still-keep-the-rest` becomes `but-can-still-keep-the-rest` [6](#0-5) .

`parseAppURL`, however, only *rejects* names containing `invalidCharacterRegex` matches via `testForInvalidChars`, it never strips or rejects a leading dash: [1](#0-0) . Since `invalidCharacterRegex` does not include `-` in its character class or as an anchored pattern [7](#0-6) , a branch value such as `--orphan` or any other dash-led git-checkout flag passes validation untouched and is stored as `action.branch`.

That value flows straight through `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl(url, branch)` → `this.checkoutLocalBranch(repository, branchName)` [8](#0-7) . Down in the git layer, `getBranchCheckoutArgs` places the branch name as a *positional argument before* the `--` pathspec separator: [9](#0-8) . The `--` only protects arguments that come after it; the branch/ref name itself is not defended by it. This means a dash-prefixed value reaching this point is parsed by `git` as an option to `checkout`, not as a ref.

The report's broken invariant maps directly here: `sanitizedRefName` (the "correct multiplier") is the intended single source of truth for "is this string safe to hand to git as a ref," but the deep-link parser applies a different, incomplete check (the "wrong multiplier"), so the protection that exists everywhere else in the app does not exist on this particular attacker-reachable path.

### Impact Explanation
An attacker who controls a link (e.g. embedded in a webpage, README, chat message, or GitHub Enterprise-hosted content) can craft a `x-github-client://openrepo/<url>?branch=<flag>` URI. When the victim clicks it, Desktop's own protocol handler (`handleAppURL`, reached via `handleCommandLineArguments` on Windows or the OS's URL scheme dispatch) invokes `checkoutLocalBranch` with attacker-controlled, dash-prefixed content that is fed as a positional argument to `git checkout`. This is exactly the "attacker controls...a link or deep link the user clicks" scenario in the Valid Impact criteria, and the consequence — corrupting the arguments of a git operation Desktop performs on the user's behalf — matches "silent corruption of what the user commits or pushes" / unintended local repository state changes triggered without further user action.

### Likelihood Explanation
No further user interaction beyond clicking the link is required; `handleAppURL`/`parseAppURL` runs automatically on protocol invocation and `checkoutLocalBranch` is called unconditionally once `branch` is non-null in the parsed action. The only gate is `testForInvalidChars`, and it demonstrably does not cover the dash-leading case that `sanitizedRefName` was written to cover, so the existing guard does not stop this path.

### Recommendation
Reuse `sanitizedRefName()` (or equivalently strip/reject leading `-`/`+`) in `parseAppURL`'s branch handling, or require `openBranchNameFromUrl`/`getBranchCheckoutArgs` to always prefix the branch positional argument with `--` before the ref (i.e., `git checkout -- <branch>` is not itself sufficient because checkout treats the token after `--` as a pathspec, not a ref — the actual fix should be validating/normalizing the string with the same canonical ref-sanitizer used elsewhere, or explicitly rejecting values starting with `-` at the point where they're accepted from an untrusted URL).

### Proof of Concept
1. Register/click a link: `x-github-client://openrepo/https://github.com/octocat/Hello-World?branch=--orphan`
2. `parseAppURL` returns `{ name: 'open-repository-from-url', branch: '--orphan', ... }` because `testForInvalidChars('--orphan')` is `false` (no character in `--orphan` matches `invalidCharacterRegex`) — confirmed by inspection of the regex at `app/src/lib/sanitize-ref-name.ts:5-6`, which is not tripped by `-`.
3. `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl(url, '--orphan')` → `checkoutLocalBranch(repository, '--orphan')`.
4. Downstream `getBranchCheckoutArgs` yields `['checkout', '--orphan', '--']`... (or similar assembly depending on the exact `checkoutLocalBranch` implementation, which I could not fully load before running out of tool iterations) causing `git` to interpret `--orphan` as a flag instead of a ref name.

**Caveat / unverified detail:** I was unable to load the body of `checkoutLocalBranch` in `app/src/ui/dispatcher/dispatcher.ts` before the tool budget ran out, so I cannot 100% confirm there is no additional sanitization step performed between `openBranchNameFromUrl` and the final `git` argv construction in `checkout.ts`. The two concrete facts I did verify are (a) `parseAppURL`'s `testForInvalidChars` check does not filter leading dashes while the sibling `sanitizedRefName` explicitly does, and (b) `getBranchCheckoutArgs` places the branch string before the `--` separator. If `checkoutLocalBranch` independently re-sanitizes with `sanitizedRefName` before calling `checkoutBranch`, this issue would be mitigated; this should be confirmed with a full read of that method (and of `_checkoutBranch`/`Branch` construction in `app-store.ts`) before treating this as a confirmed exploitable bug.

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
