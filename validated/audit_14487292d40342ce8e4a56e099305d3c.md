## Analysis

The H1 report's broken invariant is: **two independently-derived arrays from a single untrusted response are assumed to stay index-synchronized, and one is indexed/dereferenced (`.front()`) without checking the other's actual length**, causing an out-of-bounds/undefined dereference crash.

The closest analog in this codebase is `parseRawLogWithNumstat` in `app/src/lib/git/log.ts`, which parses the output of `git log`/`git diff --raw --numstat -z` for commits, stashes, and branch-comparison diffs (all data derived from a cloned/fetched repository, i.e. attacker-controllable).

### Title
Unchecked array index on assumed-synchronized `--raw`/`--numstat` git output causes crash when parsing an attacker-controlled repository's diff - (`app/src/lib/git/log.ts`)

### Summary
`parseRawLogWithNumstat` walks a single NUL-delimited token stream containing two logically separate sections produced by `git log/diff --raw --numstat -z`: a "raw" section (populating the `files` array) and a "numstat" section (only incrementing a separate counter `numStatCount`). The code assumes these two sections always contain the exact same number of entries, in the exact same order, and unconditionally indexes into `files[numStatCount]` while processing the numstat section: [1](#0-0) 

There is no bounds check on `numStatCount` against `files.length` before dereferencing `.status`. This is the same structural bug as the Monero report: it trusts that two representations of the same underlying data (`res.txs` vs `res.txs_as_hex`, here "raw" entries vs "numstat" entries) never desynchronize, and indexes/dereferences one based on a counter driven by the other, with zero verification.

### Finding Description
`getChangedFiles` (history view), `getStashedFiles` (stash view), `getBranchMergeBaseChangedFiles` and `getCommitRangeChangedFiles` (branch comparison/merge preview) all invoke `git log`/`git diff` with `--raw --numstat -z` against a repository the user has cloned or fetched, and pipe the resulting stdout — content whose shape is influenced by the commits/objects present in that repository — into `parseRawLogWithNumstat`: [2](#0-1) [3](#0-2) [4](#0-3) 

The parser's documented format assumption is a strict, ordered 1:1 pairing between raw entries and numstat entries: [5](#0-4) . If that pairing is violated — e.g. because the numstat block yields more logical entries than the raw block produced `CommittedFileChange` objects for (any case where git's numstat/raw counts diverge for a given diff, such as unusual type-change/submodule/conflict entries, or future git behavior changes) — `files[numStatCount]` evaluates to `undefined`, and `isCopyOrRename(files[numStatCount].status)` throws a `TypeError: Cannot read properties of undefined`. Note also the adjacent `oldPath` detection regex `/^R|C/` is itself buggy due to operator precedence (it matches "starts with R" **or** "contains C anywhere"), showing the parser's fragility around the same raw/numstat status field that drives the indexing logic: [6](#0-5) 

Just like the Monero code's guard `res.txs.size() != 1 && res.txs_as_hex.size() != 1` doesn't guarantee the two arrays describe the *same* transaction consistently, this parser's line-by-line `startsWith(':')` dispatch doesn't verify raw-entry count equals numstat-entry count before indexing `files[numStatCount]`.

### Impact Explanation
A crafted/malicious repository (fetched or cloned by the user) that produces a raw/numstat mismatch for one of its commits, stashes, or a branch being compared/merged will throw an unhandled `TypeError` deep inside `parseRawLogWithNumstat`. This directly affects the History view, Stash view, and the branch-compare/merge-preview flow that is used just before the user commits a merge — corrupting or aborting the exact data structure (`IChangesetData.files`) Desktop uses to show the user "what changed," which is the same class of trust violation called out as high-impact in the source report (crash triggered purely by untrusted repository/response content reaching an unguarded array/vector access).

### Likelihood Explanation
Reaching this code path requires nothing more than the victim cloning, fetching, or comparing against a repository controlled by an attacker — a completely natural, unprivileged Desktop workflow. No local access, credentials, or social engineering beyond "open/browse a repository" is required. The precondition (a raw/numstat count or ordering mismatch for some commit) is narrower than a guaranteed 100%-reliable trigger, since normally git emits both sections from the same diff computation, but the code contains **no defensive check at all** for the invariant it depends on, which is the exact same class of missing-guard flaw flagged as valid in the source report.

### Recommendation
Add an explicit bounds/length check before indexing `files[numStatCount]` (e.g., `if (numStatCount >= files.length) { throw/skip }`), and ideally validate up front that the total number of raw entries equals the total number of numstat entries before trusting the two counters to stay in lockstep, mirroring how the fix for the Monero issue would require checking `res.txs.size() === 1` before ever touching `res.txs.front()`. Additionally fix the `/^R|C/` regex to `/^[RC]/` so status-based branching doesn't silently mismatch entries.

### Proof of Concept
1. Craft/host a git repository containing a commit whose diff, when run through `git log -C -M -m -1 --first-parent --raw --format=format: --numstat -z`, produces a numstat section with more logical entries than the raw section (e.g. via edge-case type-change/submodule/rename-score combinations that cause git's raw vs numstat entry counts to diverge for that invocation).
2. Have the victim clone/fetch this repository and open its commit history (or compare/merge the branch) in GitHub Desktop, triggering `getChangedFiles` → `parseRawLogWithNumstat`: [7](#0-6) 
3. Observe the unhandled `TypeError` from `files[numStatCount].status` when `numStatCount` exceeds `files.length`, aborting the changed-files computation for that commit/comparison.

export async function getChangedFiles(
  repository: Repository,
  sha: string
): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)
  // this is equivalent to the user configuring 'diff.renames' to 'copies'
  // NOTE: order here matters - doing -M before -C means copies aren't detected
  const args = [
    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}

export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }

  return { files, linesAdded, linesDeleted }
}

export async function getBranchMergeBaseChangedFiles(
  repository: Repository,
  baseBranchName: string,
  comparisonBranchName: string,
  latestComparisonBranchCommitRef: string
): Promise<IChangesetData | null> {
  const baseArgs = [
    'diff',
    '--merge-base',
    baseBranchName,
    comparisonBranchName,
    '-C',
    '-M',
    '-z',
    '--raw',
    '--numstat',
    '--',
  ]

  const mergeBaseCommit = await getMergeBase(
    repository,
    baseBranchName,
    comparisonBranchName
  )

  if (mergeBaseCommit === null) {
    return null
  }

  const result = await git(
    baseArgs,
    repository.path,
    'getBranchMergeBaseChangedFiles'
  )

  return parseRawLogWithNumstat(
    result.stdout,
    `${latestComparisonBranchCommitRef}`,
    mergeBaseCommit
  )
}
