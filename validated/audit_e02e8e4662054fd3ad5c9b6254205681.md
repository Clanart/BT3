## Analysis

The reported bug class is a **boundary-comparison defect**: a security-relevant check that uses the wrong comparison operator/boundary condition, silently widening what is accepted. The closest analog in this codebase is not `>=`/`>` but the equivalent class of bug for path-containment checks: using `String.prototype.startsWith()` on a directory prefix **without** ensuring a trailing path-separator boundary. This makes a sibling directory whose name happens to share the root's prefix ("`/repo`" vs "`/repo-evil`") pass the "is contained within root" check — exactly the same broken-invariant shape as the `>=`/`>` bug (an inclusive/boundary check that admits one more value than intended).

### Title
Repository-containment check in `resolveWithin` accepts sibling directories due to missing path-separator boundary — (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin()` is the app's central guard used to confirm that a user- or remote-supplied relative path resolves to a location at or beneath a trusted root directory (e.g. the repository working directory) before that path is used to open, reveal, or read a file. The final containment check is a bare `startsWith` comparison with no separator boundary, so a resolved path in a sibling directory with a prefix-matching name is incorrectly treated as "inside" the root.

### Finding Description
`_resolveWithin` computes `realRoot` and `realResolved` via `realpath()` and then does: [1](#0-0) 

This is a plain string-prefix test with no check that the next character after `realRoot` in `realResolved` is a path separator (or that the strings are equal). If `realRoot` is e.g. `/Users/victim/Documents/GitHub/project` and an attacker can cause `realResolved` to become `/Users/victim/Documents/GitHub/project-evil-repo/secrets.txt`, the `startsWith` check passes even though `project-evil-repo` is a completely different, sibling directory outside `project`. This is the same class of bug as the reported `>=`/`>` discrepancy: an inexact boundary condition that admits one unintended extra case.

The function is exercised with attacker-influenced input via the `x-github-desktop://` deep-link handler: `filepath` from a deep link is passed straight into `resolveWithin(repository.path, filepath)`: [2](#0-1) 

and the parsed URL action's `filepath` originates from an untrusted URL (`x-github-desktop://openRepo/...&filepath=...`): [3](#0-2) 

The existing unit tests for `resolveWithin` only check `..`-traversal and symlink-traversal scenarios, not the sibling-prefix scenario, so this gap is not covered by the test suite: [4](#0-3) 

### Impact Explanation
`resolveWithin`'s only real guard against escaping the intended directory is this `startsWith` check. If `repository.path` happens to be a prefix of another directory name on disk (a realistic scenario — e.g. `.../GitHub/project` vs `.../GitHub/project-backup`, or a repository cloned into a directory adjacent to one with a longer, prefix-sharing name), a crafted deep link `filepath` parameter (`../project-backup/secret.txt`, normalized/resolved to the sibling) would be accepted as "within root" and passed to `shell.showItemInFolder`, revealing/opening a file outside of the trusted repository directory. This matches the "attacker controls ... a link or deep link the user clicks ... result is file read outside the repo" category.

### Likelihood Explanation
Exploitability depends on the victim having, or being made to have, a sibling directory whose name is a prefix-extension of the repository's directory name — this is not guaranteed to exist in every environment, so likelihood is moderate rather than certain. However, GitHub Desktop's default clone location (`~/Documents/GitHub/<repo-name>`) means many users routinely have multiple repositories cloned side-by-side under the same parent folder, and repo names differing only by a suffix (`foo`, `foo-fork`, `foo-old`, `foo2`) are common, making the precondition plausible without any special user action beyond clicking a link.

### Recommendation
Change the containment check in `_resolveWithin` to require an exact match or that the character immediately following the root in the resolved path is a path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add unit tests for the sibling-directory-prefix case (e.g. root `/a/b`, resolved `/a/b-evil`) to `app/test/unit/path-test.ts` to lock in the fix, mirroring the report's recommendation to explicitly verify which boundary semantics are correct.

### Proof of Concept
1. Victim has two repositories cloned under the same parent: `~/Documents/GitHub/project` (open in Desktop) and `~/Documents/GitHub/project-secret` (any directory, need not be a git repo, just needs to exist with a secret file inside, e.g. `~/Documents/GitHub/project-secret/secret.txt`).
2. Attacker sends the victim a link: `x-github-desktop://openRepo/<origin-url-of-project>?filepath=..%2Fproject-secret%2Fsecret.txt`.
3. `openRepositoryFromUrl` resolves/opens `project`, then calls `resolveWithin(repository.path, '../project-secret/secret.txt')`.
4. `resolve(normalizedRoot, normalizedRelative)` yields `~/Documents/GitHub/project-secret/secret.txt`; `realpath` of both root and resolved path are computed.
5. `realResolved.startsWith(realRoot)` evaluates true because `".../project-secret/secret.txt".startsWith(".../project")` is `true` in JavaScript (no separator boundary enforced).
6. `shell.showItemInFolder(resolved)` reveals/opens `secret.txt`, a file entirely outside of the `project` repository directory, purely by clicking a crafted link — no local access, admin rights, or prior compromise required. [5](#0-4) [6](#0-5)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }
```

```typescript
  describe('resolveWithin', () => {
    const root = process.cwd()

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
      assert((await resolveWithin(root, 'foo\0bar')) === null)
    })

    it('succeeds for absolute relative paths as long as they stay within the root', async () => {
      const parent = resolve(root, '..')
      assert.equal(await resolveWithin(parent, root), root)
    })

    if (!__WIN32__) {
```
