### Title
Zero slippage protection (`_minRec = 0`) in `ArbWomUp3._deposit` mode 2 enables sandwich-attack theft of depositor funds - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3._deposit` (mode 2) is reachable by any ordinary wallet that calls the contract's deposit entrypoint with `_mode == 2`. It swaps half of the user's deposited WOM through `SmartWomConvert.convert`, but hardcodes the slippage-protection parameter `_minRec` to `0`, exactly the "permissionless swap without slippage control" bug class described in the referenced report (`distributeMochi`).

### Finding Description
In `ArbWomUp3._deposit`, mode 2 splits the user's WOM 50/50: half is deposited directly into `mWom`, and the other half is routed through the converter with a hardcoded zero minimum-return: [1](#0-0) 

This calls `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)`, which forwards into `_convertFor` with `_minRec = 0`: [2](#0-1) 

Inside `_convertFor`, the actual on-chain swap against the WOM/mWOM pool via `IWombatRouter.swapExactTokensForTokens` is *also* called with a hardcoded `0` minimum-amount-out at the router level: [3](#0-2) 

The only after-the-fact guard is: [4](#0-3) 

Since `_minRec` was passed in as `0` from `ArbWomUp3`, this check `convertAmount + amountRec < 0` can never revert, so there is no effective slippage protection anywhere in this call path — mirroring the `distributeMochi` pattern where a swap/convert step lacks TWAP-based or caller-supplied minimum-return enforcement.

### Impact Explanation
Any user calling `ArbWomUp3`'s deposit flow with mode 2 has half of their WOM routed through an unprotected swap. An attacker can sandwich this transaction (front-run to skew the WOM/mWOM pool price, let the victim's swap execute at the manipulated rate, then back-run to restore the price and capture the difference), directly stealing value from the depositing user's funds. This is a direct theft-of-user-funds vulnerability reachable from an ordinary, unprivileged wallet interaction (a normal `deposit` call), not requiring any privileged role.

### Likelihood Explanation
Likelihood is high: the vulnerable path is triggered by a completely permissionless, common user action (depositing WOM in mode 2), the swap pool (WOM/mWOM) is a shallow, price-sensitive AMM pool, and MEV/sandwich bots routinely monitor mempools for exactly this zero-slippage pattern. No special privileges or preconditions are required from the attacker.

### Recommendation
Do not hardcode `_minRec` (and the underlying router `minAmountOut`) to `0`. Either:
1. Expose a genuine user-supplied `_minRec` parameter on `ArbWomUp3`'s public deposit function so depositors can set their own slippage tolerance, and thread it through unchanged to `SmartWomConvert.convert` and the router swap, or
2. Compute an on-chain minimum return from a TWAP/oracle-based fair price with a bounded slippage tolerance before invoking the swap.

### Proof of Concept
1. Attacker observes a pending call to `ArbWomUp3`'s deposit function with `_mode == 2` in the mempool.
2. Attacker front-runs by swapping a large amount of mWOM into the WOM/mWOM pool used at `womMWomPool`, skewing the price against WOM->mWOM conversion.
3. Victim's transaction executes `_deposit` → `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)` → `_convertFor`, whose router swap call has `minAmountOut = 0`: [5](#0-4) 
 The victim receives far less mWOM than fair value, and the post-check `convertAmount + amountRec < 0` cannot catch this since `_minRec` is `0`.
4. Attacker back-runs, reversing the price skew and pocketing the difference extracted from the victim's deposit.
