### Title
Fee/Dust Validation Computed on a Smaller Transaction Than the One Actually Signed - OP_RETURN Output Excluded From Weight/Fee Calculation - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` is the exact analog of the Rubicon `enforceReserveRatio` bug: a safety invariant (the fee must cover the transaction's actual size and pass the minimum relay fee) is validated against the *pre-action* state — the payment/output set — and never re-validated after the action mutates the transaction. Concretely, the OP_RETURN `data` output is pushed onto `tx_outs` *before* the weight calculation, but `calculate_weight_vbytes` is invoked with the `payments` slice, which never includes that output. The resulting `needed_fee` and the `TooLowFee` check are therefore computed on a transaction that is up to ~91 virtual bytes smaller than the real transaction that gets signed and broadcast. The transaction is emitted with the invariant already violated and no post-check catches it.

### Finding Description
In `SignableTransaction::new`:

1. `tx_outs` is populated with all payment outputs, then the OP_RETURN output is appended (`tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })`, send.rs ~L194-202).
2. The fee parameters are then computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs ~L204). `calculate_weight_vbytes` reconstructs a fresh `Transaction` whose `output` list is built *only* from `payments` (send.rs ~L85-93) — the OP_RETURN output and any change output are absent.
3. `needed_fee = fee_per_vbyte * vbytes` and the `TooLowFee` check (`needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000`, send.rs ~L206-213) both use this understated `vbytes`. The identical understatement applies to `fee_with_change` when a change output is added (`calculate_weight_vbytes(..., Some(&change))`, send.rs ~L225-234) — `payments` still excludes the OP_RETURN output.
4. The constructed `SignableTransaction` is returned containing `tx_outs` with the OP_RETURN output. The actual fee paid is `sum(prevouts) - sum(tx.output)` (`fee()`, send.rs ~L138-141), which equals `needed_fee`/`fee_with_change` — an amount priced for a smaller transaction. There is no post-check re-verifying that the final serialized transaction's weight satisfies the declared fee rate or the minimum relay fee.

`data` (the OP_RETURN payload, up to 80 bytes per the `TooMuchData` check at send.rs ~L171-173) originates from user-supplied instruction data routed through the scheduler/OutInstruction flow, so an unprivileged depositor controls the size of the omitted output.

### Impact Explanation
When `data` is non-empty, the signed transaction's real virtual size exceeds `vbytes`/`vbytes_with_change` by the size of the OP_RETURN output (~9–91 bytes). Because the fee was priced against the smaller size:

- The effective fee rate is strictly lower than `fee_per_vbyte`.
- If `fee_per_vbyte` is at/near the minimum relay threshold, the `TooLowFee` check passes while the actual transaction falls below `DEFAULT_MIN_RELAY_TX_FEE` for its true size. The resulting signed transaction is non-standard for mempool relay: it cannot be propagated or mined at the intended rate.

The consequence is that funds committed to a Plan — deposits scanned and slated for forwarding/payment/change — are placed into a transaction the network will not accept as broadcastable. The outputs remain under multisig control, but the completion cannot land on-chain as constructed, leaving the batch/plan's funds unspendable through the produced transaction and forcing the signer set to depend on re-attempt/eventuality recovery paths. Like the Rubicon case, a bound intended to be maintained at all times (fee ≥ minimum relay rate for the real transaction) is checked once before the mutation and silently violated by it.

### Likelihood Explanation
Any external user who can attach near-maximum `data` (up to the 80-byte cap) to an instruction that materializes as a Bitcoin output-bearing transaction triggers the understatement deterministically — no race or privileged access required. Whether it crosses the relay-fee boundary depends on the configured `fee_per_vbyte` being close to the minimum, so the user-visible failure (an unrelayable transaction) is conditional, but the invariant violation itself occurs on every transaction carrying OP_RETURN data.

### Recommendation
Mirror the Rubicon fix — re-run the check on post-state. Either:

- Pass the fully assembled `tx_outs` (payments + OP_RETURN + change) into the weight/vbyte calculation instead of the `payments` slice, so `needed_fee` reflects the real transaction; and/or
- After constructing `self.tx`, recompute `tx.weight()`/vsize and assert `fee() >= fee_per_vbyte * actual_vbytes` and `fee() >= (DEFAULT_MIN_RELAY_TX_FEE * actual_vbytes) / 1000` before returning `Ok`, analogous to calling `enforceReserveRatio` at the end of `placeMarketMakingTrades`.

### Proof of Concept
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new`:

```rust
// OP_RETURN output added to the real tx_outs ...
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(/* up to 80 bytes, checked at L171 */),
  })
}

// ... but the fee is priced on `payments`, which excludes that output
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
```

`calculate_weight_vbytes` (send.rs ~L62-127) builds its template `Transaction` solely from `payments` plus an optional change output — there is no parameter or code path that injects the OP_RETURN output, which already exists in `tx_outs`. With `data = vec![0u8; 80]` and `fee_per_vbyte` at the relay minimum, `new` returns `Ok` while the final `tx` (which includes the ~91-vbyte OP_RETURN output) has an actual fee rate below the minimum relay fee — a transaction the produced signature cannot get relayed, with no post-construction check detecting the violation. (Caveat I could not fully verify within the iteration budget: the exact processor call path feeding attacker-controlled `data` into `SignableTransaction::new` in `processor/src/networks/bitcoin.rs`, though the `data` parameter's purpose — embedding instruction payloads as OP_RETURN — is documented in the function's doc comment.)
