### Title
Path traversal via symlinked/untracked working-directory entries lets a malicious repository cause GitHub Desktop to delete, open, or reveal files outside the repository — ([File: app/src/lib/stores/git-store.ts], [File: app/src/lib/app-shell.ts])

### Summary
`git status` output (`file.path` / `file.status.oldPath`) is trusted as a repo-relative path throughout Desktop's UI and store code. Several call sites join this attacker-influenced path directly onto `repository.path` with plain `Path.join`/`Path.resolve` and then perform a filesystem side effect (delete via trash/`rm`, open in editor, reveal in Finder/Explorer) **without** the containment check (`resolveWithin`) that Desktop already uses elsewhere for exactly this class of attack (e.g. the `openrepo://` deep-link `filepath` handler). A repository that ships a symlink whose target points outside the working directory can make `git status --untracked-files=all` report paths like `evil-symlink/secret-file` that, once joined to `repository.path`, resolve through the symlink to a location outside the repo when the OS opens/deletes them.

### Finding Description
Desktop's own hardened path helper `resolveWithin` (`app/src/lib/path.ts:36-100`) explicitly defends against symlink-based escapes — its test suite proves this is a known, intentional threat model: [1](#0-0) 

Desktop applies this exact protection when handling the `x-github-client://openrepo/...?filepath=...` deep link, explicitly rejecting absolute paths and using `resolveWithin` before touching disk: [2](#0-1) 

However, the equivalent guard is **not** applied to paths that originate from `git status`/`git diff` for the *currently open* repository, which is the far more common code path and is driven entirely by data an attacker fully controls (the committed tree of a cloned/fetched repository). `parsePorcelainStatus` in `app/src/lib/status-parser.ts` captures the raw path field from `git status --porcelain=2 -z` with a permissive regex and no normalization/containment check: [3](#0-2) 

That path is stored verbatim on `WorkingDirectoryFileChange.path`/`CommittedFileChange.path` and then consumed by multiple UI/store call sites that do a raw `Path.join`/`Path.resolve` with no `resolveWithin` check before performing a filesystem action:

- Reveal in file manager (used from Changes list, History, PR files, conflict resolution dialogs): [4](#0-3) 

- Open with default program / external editor (Changes sidebar): [5](#0-4) 

- **Discard Changes**, which for untracked files performs an actual filesystem delete (`shell.moveItemToTrash`, falling back to `rm`) using `Path.resolve(this.repository.path, file.path)` / `Path.join(this.repository.path, file.path)`: [6](#0-5) 

Git's untracked-file scanner (`git status --untracked-files=all`, which Desktop always runs — `app/src/lib/git/status.ts:212-219`) follows symlinked directories that are part of the tracked tree and reports files found through them as untracked paths (e.g. `link-dir/some-file`). Because `Path.join`/`Path.resolve` are purely lexical and do not resolve symlinks, and because none of `revealInFileManager`, `_openInExternalEditor`, `onOpenItem`, or `discardChanges` call `resolveWithin` on the resulting path, the OS-level open/reveal/delete call transparently follows the symlink component and operates on a location outside `repository.path`.

### Impact Explanation
- **File deletion outside the repo**: "Discard Changes" on an untracked path reached through a malicious symlink results in `shell.moveItemToTrash` (or `rm` as a fallback) operating on a file outside the repository — an unprivileged, silent file-delete primitive triggered by a normal user action ("Discard changes").
- **File disclosure**: "Open in External Editor" / "Open with Default Program" on the same reported path opens an attacker-chosen file outside the repo (e.g. SSH keys, config files with tokens) in the user's editor, which can then be inadvertently pasted/committed/screen-shared, or read directly by the user believing it's a repo file.
- **Confusing/forced action**: "Reveal in Finder/Explorer" discloses the existence and location of files/directories outside the repo tree, aiding further targeted attacks.

This matches the required impact class: attacker (via a cloned/fetched repository) causes file read/write/delete outside the repo, with no additional user steps beyond ordinary Desktop usage (viewing the Changes list and clicking a normal context-menu action).

### Likelihood Explanation
Moderate-to-high. The attack requires only:
1. A crafted repository containing a symlink component pointing to a predictable/sensitive location (e.g. `~/.ssh`, `~/AppData/Roaming`, or a relative `..` escape) — this is a normal, unrestricted tracked blob type (`120000` symlink mode), not something git rejects.
2. The victim cloning/opening the repository in Desktop (a routine, expected action for any GitHub repository).
3. The victim performing an everyday action from the Changes/History/PR view — "Discard Changes", "Reveal in Finder", or "Open in External Editor" — on an entry that git's untracked-file scan surfaced through the symlink.

No admin rights, no pre-existing malware, and no unnatural steps are required; the vulnerable code paths are the default, most-used Desktop workflows (Changes tab, PR review, discard).

### Recommendation
Route every `file.path`/`file.status.oldPath` value through `resolveWithin(repository.path, file.path)` (the same helper already used for deep-link file opens) before any filesystem action is taken — specifically in:
- `app/src/lib/app-shell.ts` (`revealInFileManager`)
- `app/src/lib/stores/app-store.ts` (`_openInExternalEditor`/`_openInSelectedExternalEditor` when called with repo-relative status paths) and its UI callers (`app/src/ui/changes/sidebar.tsx`, `app/src/ui/changes/filter-changes-list.tsx`, `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`)
- `app/src/lib/stores/git-store.ts` `discardChanges` (both the `moveItemToTrash` and `rm` branches)

If `resolveWithin` returns `null`, abort the action and log/report an error, mirroring the existing behavior in `dispatcher.ts`'s `openRepositoryFromUrl`.

### Proof of Concept
1. Attacker creates a repository containing a symlink `pivot -> ../../../../` (or an absolute-path-equivalent traversal) committed as a normal tracked blob, alongside a `.gitignore` that does not exclude the target directory's contents.
2. Victim clones the repository with GitHub Desktop and opens it. Desktop runs `git status --untracked-files=all` (`app/src/lib/git/status.ts:212-219`), which follows the `pivot` symlink and lists files it can see on the other side (e.g. `pivot/.ssh/id_rsa`) as untracked entries in the Changes list.
3. Victim selects that entry and chooses **Discard Changes** (or **Reveal in Finder** / **Open in External Editor**) from the context menu (`app/src/ui/changes/filter-changes-list.tsx:790-800`, `app/src/ui/history/selected-commits.tsx:405-420`).
4. `git-store.ts`'s `discardChanges` calls `this.shell.moveItemToTrash(Path.resolve(this.repository.path, file.path))` — because `Path.resolve` is lexical, this resolves to `<repo>/pivot/.ssh/id_rsa`, which the OS follows through the symlink and deletes/trashes the real `~/.ssh/id_rsa`, entirely outside the cloned repository.
