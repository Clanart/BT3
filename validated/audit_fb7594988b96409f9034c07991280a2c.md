### Title
Spoofed `WWW-Authenticate` realm header from a malicious git remote forces GitHub Enterprise sign-in flow against attacker-controlled endpoint - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
The external report's core invariant break is: a component trusts a single classification signal to grant a sensitive capability (fund movement) that should require independently-verified authorization. The Desktop analog is `getEndpointKind()` in the git-credential-helper trampoline, which classifies a remote host as `'enterprise'` (a trusted GitHub Enterprise Server) purely because the HTTP response echoed a `WWW-Authenticate` header containing `realm="GitHub"` — a value fully controlled by the remote server, not verified against any GitHub-specific protocol handshake.

### Finding Description
When Git needs credentials for a remote, it invokes Desktop's credential-helper trampoline (`createCredentialHelperTrampolineHandler`) with a `get` request built from headers the *remote server itself* supplied, including any `wwwauth[N]` entries captured from the HTTP response. [1](#0-0) 

Specifically:
```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    ...
``` [2](#0-1) 

There is no cryptographic or protocol-level verification that the host is actually a GitHub Enterprise Server — the classification is entirely attacker-suppliable string matching on a header the git server returns in its 401 response. If the endpoint classifies as `'enterprise'` and no existing Desktop account matches that origin, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn` then begins a full GitHub Enterprise OAuth/device sign-in flow scoped to that attacker-controlled `endpoint`, showing the user a legitimate-looking Desktop sign-in dialog: [4](#0-3) 

This is the same broken-invariant shape as the report: a single, spoofable signal ("I appear to be a GitHub Enterprise Server") is trusted to authorize a sensitive, high-value action (initiating OAuth against a remote to obtain a token) instead of requiring corroborating proof (e.g., a successful call to a known GitHub API endpoint, TLS certificate pinning, or an out-of-band verification).

### Impact Explanation
A malicious or compromised git remote (e.g., a cloned/fetched repository whose `.git/config` or submodule points to an attacker HTTP(S) server, or a MITM/compromised proxy sitting on a legitimate-looking host) can return a 401 response with `WWW-Authenticate: Basic realm="GitHub"` for any URL. This causes Desktop to present its normal GitHub sign-in UI, scoped to the attacker's `origin`. If the user completes the OAuth/device flow (which is not itself abnormal-looking since it reuses Desktop's standard sign-in popup), the resulting session/token exchange is bound to `credentialHelperUrl: endpoint` set to the attacker's host, risking the OAuth device code / callback and, depending on `dispatcher.setSignInEndpoint`/`beginEnterpriseSignIn` behavior, potentially routing authentication material to that attacker endpoint. This matches the "unprivileged, attacker controls a git remote or proxy response, results in unauthorized OAuth/credential exfiltration" impact category.

### Likelihood Explanation
The trigger requires only that a user clone or fetch from an attacker-controlled or attacker-tampered HTTP(S) remote — no local access, no admin rights, and no prior malware are needed. The header value used for classification (`wwwauth[...]` containing `realm="GitHub"`) is trivial for any HTTP server to emit. The confusable UI (Desktop's own native sign-in dialog) increases realistic user completion of the flow, since it looks like Desktop's normal GHE onboarding rather than an unfamiliar phishing page.

### Recommendation
Do not rely on an attacker-controlled `WWW-Authenticate` header value as a trust signal for classifying a host as GitHub Enterprise. Before initiating the sign-in/OAuth flow, independently verify the endpoint by making a Desktop-initiated request to a known GitHub API path (e.g., `/api/v3/meta` or checking for the `x-github-enterprise-version` response header from a request Desktop controls) rather than trusting header content echoed from the credential-helper input. Fall back to the `'generic'` classification (username/password prompt, no OAuth) unless this independent verification succeeds.

### Proof of Concept
1. Stand up an HTTP git remote/proxy that returns, on any unauthenticated request:
   `WWW-Authenticate: Basic realm="GitHub"`
2. Add this URL as a remote in a repository and have the victim `fetch`/`pull`/`push` in GitHub Desktop.
3. Git invokes Desktop's credential helper with the captured `wwwauth[...]` header; `getEndpointKind` returns `'enterprise'` because of the string match at [5](#0-4) 
4. Since no existing account matches the attacker's origin, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, launching an Enterprise sign-in flow scoped to the attacker's host [6](#0-5) 
5. The victim, expecting a normal GHE sign-in prompt from Desktop, may proceed with authentication against the attacker-controlled endpoint.

**Note on confidence:** I was not able to fully trace `dispatcher.beginEnterpriseSignIn`/`setSignInEndpoint` and the downstream OAuth exchange implementation within the indexed portion of the codebase to confirm exactly what data (device codes, tokens) would be sent to the attacker endpoint versus GitHub.com — this would need to be verified by reading the full sign-in-store implementation, which may exceed what's available in the current index. I recommend a Devin session with full repo access to trace `SignInStore`/`beginEnterpriseSignIn` to confirm the exact exfiltration surface before treating this as a fully proven high-severity finding.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
