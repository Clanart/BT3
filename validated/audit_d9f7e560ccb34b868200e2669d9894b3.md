### Title
Unchecked out-of-bounds buffer indexing in CLVM canonical-encoding check can crash spend-bundle validation - (File: `chia/full_node/mempool_manager.py`)

### Summary
CVE-2019-20912 is a stack buffer overflow in GNU LibreDWG's `bit_read_TF` in `bits.c`, caused by trusting an attacker-controlled length/offset value without bounds-checking before reading from a buffer. The closest reachable analog in this repository is `is_atom_canonical()` / `is_clvm_canonical()` in `chia/full_node/mempool_manager.py`, which walks a CLVM solution buffer using an `offset` that is advanced purely from attacker-controlled length-prefix bits, with no check that `offset` stays within `len(clvm_buffer)` before each `clvm_buffer[offset]` read.

### Finding Description
`is_atom_canonical()` reads `b = clvm_buffer[offset]` and then, based on the top bits of `b`, determines a `prefix_len` (0–5) and increments `offset` that many times while OR-ing in each subsequent byte — all without ever verifying `offset < len(clvm_buffer)`: [1](#0-0) 

`is_clvm_canonical()` is the driver loop that calls `is_atom_canonical()` repeatedly while advancing `offset` by the returned `atom_len`, again with no upper bound check against the buffer length until the very end of the loop: [2](#0-1) 

This mirrors the LibreDWG bug class exactly: a length value taken from untrusted input is used to advance a cursor/read position with no validation that the read stays inside the allocated buffer. In C this manifests as a stack/heap overflow; in this Python codebase the same missing bounds-check manifests as an unhandled `IndexError` when a crafted length prefix or truncated buffer pushes `offset` past `len(clvm_buffer)`.

Per `.cursor/context/clvm-execution.md`, this check is invoked from `pre_validate_spendbundle()` when a spend is DEDUP-eligible, to ensure that its solution uses canonical serialization so identical solutions dedupe correctly: [3](#0-2) 

### Impact Explanation
A crafted, truncated, or malformed solution buffer submitted as part of a DEDUP-eligible spend in a spend bundle can drive `offset` out of bounds inside `is_atom_canonical()`/`is_clvm_canonical()`, raising an unhandled `IndexError` during mempool admission. If this exception is not caught by the caller, it would abort processing of that spend bundle path unexpectedly ("spend-triggered transaction-processing halt" per the validation criteria) rather than being rejected cleanly with a normal `MempoolInclusionStatus`/`Err` result. This is a data-integrity/availability concern for mempool processing rather than a memory-corruption vulnerability, since Python bounds-checks array access and raises an exception instead of overflowing memory.

### Likelihood Explanation
Likelihood is moderate: reaching this code requires the spend to be marked DEDUP-eligible and to include a solution whose bytes are crafted with an invalid/oversized length-prefix or are truncated relative to the declared prefix length. I was not able to fully confirm, within the scope of this analysis, whether the caller of `is_clvm_canonical()` wraps the call in a `try/except` that would gracefully convert this into a normal rejection (`Err.INVALID_SPEND_BUNDLE` or similar) rather than propagating an unhandled exception — I could not locate the exact call site with its surrounding exception-handling in the available context. This is a material uncertainty: if the call is wrapped in a broad exception handler, the practical impact is limited to a clean rejection (no vulnerability); if it is not wrapped, it is a legitimate spend-bundle-triggered crash/halt in that code path.

### Recommendation
Add an explicit bounds check in `is_atom_canonical()` before each `clvm_buffer[offset]` read (both the initial read and each byte consumed in the `for i in range(prefix_len)` loop), returning a definitive "non-canonical"/error result if `offset >= len(clvm_buffer)` rather than allowing the index expression to raise. Apply the same guard in `is_clvm_canonical()`'s main loop before every `clvm_buffer[offset]` access. Additionally, verify (or add, if absent) that the call site in `pre_validate_spendbundle()` treats any exception from this canonicality check as a spend-bundle validation failure rather than letting it propagate.

### Proof of Concept
Construct a spend bundle with a DEDUP-eligible coin spend whose solution bytes end with a truncated multi-byte atom length prefix, e.g. a final byte `0xFC` (which per the mask table implies `prefix_len = 5`, requiring 5 more length bytes) with fewer than 5 bytes remaining in the buffer:
```python
clvm_buffer = bytes([0xFC])  # signals prefix_len=5, but no following bytes exist
is_atom_canonical(clvm_buffer, 0)  # offset increments past len(clvm_buffer) -> IndexError
```
Submitting a spend bundle whose DEDUP-eligible solution serializes to end in such a truncated atom would trigger this same out-of-bounds access inside `pre_validate_spendbundle()`'s canonicality check.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
