## Title
Divergent conflict-marker parsing between prompt-building and file-reassembly lets a malicious merge/rebase payload corrupt AI-resolved commits - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot merge-conflict resolver parses a conflicted file's raw text **twice**, using two different, hand-written parsers that are supposed to agree on hunk boundaries:

1. `extractConflictHunks()` in `app/src/lib/copilot-conflict-context.ts` (lines 179-279) — used to build the prompt sent to Copilot, tracking ours/base/theirs sections as an explicit state machine.
2. `reassembleResolvedFile()` in `app/src/lib/copilot-conflict-resolution.ts` (lines 549-599) — used *after* the model responds, to splice the model's per-hunk `resolvedContent` back into the original on-disk file content, matched "by order, not by line number" (per the function's own doc comment, lines 535-536).

Just like the Trail-of-Bits Strategy report, where `burnForBase()` assumed the tracked "base token balance" would never be polluted by a differently-sourced balance (the reward token), this code assumes the second parser's notion of a "conflict block" will always line up with the first parser's. That invariant is not enforced and can be broken by attacker-controlled file content that flows through both parsers.

### Finding Description
`extractConflictHunks()` uses section-aware marker matching: while scanning the "ours" section it only checks for `baseMarker`/`separatorMarker`; it never checks for `theirsMarker` until it has already moved into the theirs-collection loop [1](#0-0) .

`reassembleResolvedFile()`, in contrast, does a single linear look-ahead from each `<<<<<<<` marker that treats **any** line matching the 7-character theirs-marker regex as the block's closing marker, regardless of which logical section it is in:
```
for (let j = i + 1; j < lines.length; j++) {
  if (reassemblySeparatorMarker.test(lines[j])) {
    hasSeparator = true
  } else if (reassemblyTheirsMarker.test(lines[j])) {
    closingIndex = j
    break
  }
}
``` [2](#0-1) 

If the "ours" (or "base") content of a genuine conflict block contains a line that is itself exactly seven `>` characters at column 0 (a value fully controlled by whatever text is in the attacker's branch/commit, e.g. an embedded diff, changelog snippet, or documentation example), the two parsers disagree:

- `extractConflictHunks()` ignores that fake marker (it only looks for `theirsMarker` after having already passed the separator) and correctly extracts one well-formed hunk that is sent to Copilot, gets a legitimate `resolvedContent`.
- `reassembleResolvedFile()`'s for-loop hits the fake `>>>>>>>` line **before** it has seen a real `=======` separator, so `hasSeparator` is still `false` when `closingIndex` is set → the block is classified as malformed (`!hasSeparator || closingIndex === -1`) and the code falls into the "copy through as regular content" branch, advancing `i` by only 1 line instead of skipping the whole block [3](#0-2) .

Because the outer loop only re-enters "block mode" on a genuine `<<<<<<<` line, all of the remaining lines of this "malformed" block — including the file's *real* `=======` and `>>>>>>> feature` markers — get copied through verbatim as ordinary content, and `hunkIndex` is never incremented for this block. Any subsequent, unrelated conflict block later in the same file then gets spliced with the **wrong** `hunkResolutions[hunkIndex]` entry (an off-by-one/index-shift), because pairing is done purely "by order" with no boundary cross-check.

The resulting corrupted content is written straight to disk and staged without further validation:
```
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
...
await git(['add', '--', ...pathsToStage], repository.path, 'copilotConflictResolution')
``` [4](#0-3) 

### Impact Explanation
This is a "silent corruption of what the user commits or pushes" scenario. A user merging/rebasing a branch or PR that an attacker controls (a normal, unprompted Desktop workflow — merging a fork, rebasing onto a colleague's branch, resolving a conflicting PR) and choosing to auto-resolve with Copilot conflict resolution can end up committing a file that:
- Still contains raw, unresolved conflict-marker text (`>>>>>>> feature`) left in place, which may silently change program behavior, break builds inconsistently, or leak internal branch names into shipped code; and/or
- Has one hunk's resolution applied to a completely different, unrelated hunk elsewhere in the file, since indices shift once the parsers diverge.

None of this is surfaced to the user — the whole point of the reassembly path is to produce a "clean" resolved file with no remaining markers, and the result dialog's UI trusts that Copilot's structured per-hunk output was faithfully applied.

### Likelihood Explanation
Triggering this requires only that the attacker control the text content of one side of a merge conflict — trivial for anyone who can push a branch/PR that the victim later merges or rebases with Copilot conflict resolution. No local access, no credentials, no unusual user steps beyond a normal merge that already has a conflict Copilot is invoked to resolve. Likelihood is moderate: it requires (a) the victim to use the Copilot-resolve feature, and (b) a conflict block whose "ours"/"base" content coincidentally or deliberately contains a line of exactly seven `>` characters at the start — easy for an attacker to engineer deliberately in a crafted conflicting file.

### Recommendation
- Make `reassembleResolvedFile()` re-derive block boundaries from the *exact same* state machine as `extractConflictHunks()` (same section-aware marker recognition), rather than an independent lookahead, so the two can never disagree on hunk count/boundaries for the same input.
- Add an explicit consistency check before writing: re-run `extractConflictHunks()` on `rawContent` immediately before reassembly and assert the extracted hunk count matches `hunkResolutions.length`; abort/flag the file for manual resolution on mismatch rather than silently splicing.
- After reassembly, verify the resulting content contains no remaining lines matching `oursMarker`/`separatorMarker`/`theirsMarker` before writing/staging it, and fail closed (skip auto-resolution, surface to the user) if any are found.

### Proof of Concept
1. Create a repo and two branches that will conflict on `file.txt`.
2. On "ours", make the conflicting hunk's content include a line consisting of exactly `>>>>>>>` (seven `>` characters) followed by nothing, e.g. as a quoted example inside a comment:
```
<<<<<<< HEAD
some real ours line
>>>>>>> not-a-real-marker
another ours line
=======
their real content
>>>>>>> feature
```
3. Merge the branches in Desktop, triggering a real conflict on `file.txt`, and invoke "Resolve with Copilot".
4. `extractConflictHunks()` treats this as one well-formed hunk (ours = the 3 lines above the real `=======`, theirs = `their real content`) and sends it to the model; the model returns one `IHunkResolution`.
5. `reassembleResolvedFile()` scans from the leading `<<<<<<< HEAD`, hits the embedded `>>>>>>> not-a-real-marker` line first (before any `=======` has been seen), sets `closingIndex` there with `hasSeparator === false`, and falls into the malformed branch — leaving the real `=======` / `>>>>>>> feature` markers as literal text in the file that gets written to disk and `git add`ed.
6. If the file has a second, unrelated conflict block further down, that block will now receive `hunkResolutions[0]` (meant for the corrupted first block) instead of its own resolution, due to the `hunkIndex` never having advanced correctly for the first block.

Note: I was not able to execute this scenario end-to-end in this environment (no test harness run), so the PoC is derived from static analysis of the two parsing functions and their call path; a Devin session with repo access could confirm by adding a unit test exercising `reassembleResolvedFile` alongside `extractConflictHunks` on the crafted input above.
