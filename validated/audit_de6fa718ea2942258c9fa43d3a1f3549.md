### Title
Stale `totalBoostFactor` / referrer `factor` after vlMGP unlock permanently inflates referral boost share and drains referral yield from active referrers - ([File: VLMGP.sol])

### Summary
`VLMGP.sol`'s `unlock()` and `forceUnLock()` functions never call `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)`, unlike `_lock()` and `startUnlock()` which do. As a result, once a referrer with an activated referral code fully withdraws their locked MGP, their boost `factor` remains permanently counted in `ReferralStorage.totalBoostFactor`, letting them keep siphoning a share of the shared `BoostPoint` referral bonus forever with zero remaining stake, at the expense of legitimate active referrers.

### Finding Description
`ReferralStorage.trigger()` computes a referrer's reward share partly from a "boosted" component: [1](#0-0) 

`_calBoosted` derives this boost from a user's `factor` relative to the global `totalBoostFactor`: [2](#0-1) 

`factor` is only synchronized via `updateTotalFactor`, which recomputes `factor = sqrt(currentLockedAmount)` and adjusts `totalBoostFactor` accordingly, but only runs when explicitly invoked: [3](#0-2) 

In `VLMGP.sol`, `updateTotalFactor` is correctly invoked on `_lock()` (deposit) and `startUnlock()` (entering cooldown): [4](#0-3) [5](#0-4) 

However, it is **never called** in `unlock()` (final withdrawal of MGP after cooldown) or `forceUnLock()` (early withdrawal with penalty) — both ordinary, unprivileged user-facing functions: [6](#0-5) [7](#0-6) 

This means once a user's locked MGP is fully removed from the system (`totalAmount`/`totalAmountInCoolDown` decremented via `_unlock`), their `userInfo.factor` in `ReferralStorage` still reflects the old, now-nonexistent locked balance, and `totalBoostFactor` is never reduced to remove it.

### Impact Explanation
Any ordinary wallet can: lock MGP, `registerCode()` to activate the referral/boost feature, wait for the `factor` to be added to `totalBoostFactor`, then run `startUnlock()` → `unlock()` (or `forceUnLock()`) to withdraw 100% of their MGP. After this, they retain a non-zero `factor` entry that is never purged from `totalBoostFactor`, so they continue collecting a share of `BoostPoint` in every future `trigger()` call triggered by anyone's harvest, indefinitely, with zero capital at risk or locked. This both (a) permanently steals a portion of the referral boost reward pool that should have accrued to real, currently-locked referrers, and (b) permanently dilutes/reduces (freezes) the correct boosted yield legitimate referrers should earn, since the denominator `totalBoostFactor` is inflated by phantom/stale entries that never decay. Repeating this lock/register/withdraw cycle with multiple addresses compounds the dilution over time, degrading the referral yield pool for all real participants indefinitely — this is a permanent freezing/theft of unclaimed referral yield belonging to unprivileged users.

### Likelihood Explanation
High likelihood: every step (`lock`, `lockFor`, `registerCode`, `startUnlock`, `unlock`, `forceUnLock`) is a normal, permissionless, unprivileged user action with no special preconditions, and the missing call is a straightforward code omission (present in `_lock`/`startUnlock` but absent in `unlock`/`forceUnLock`).

### Recommendation
Add `if (referralStorage != address(0)) IReferralStorage(referralStorage).updateTotalFactor(msg.sender);` at the end of both `unlock()` and `forceUnLock()` in `VLMGP.sol`, mirroring the pattern already used in `_lock()` and `startUnlock()`, so that `factor`/`totalBoostFactor` always reflect the user's current locked balance after any state-changing lock/unlock operation.

### Proof of Concept
1. Attacker calls `VLMGP.lock(amount)` to lock a large amount of MGP — this triggers `updateTotalFactor`, adding `sqrt(amount)` to `totalBoostFactor` once the attacker has an active referral code.
2. Attacker calls `ReferralStorage.registerCode(code)` to activate the referral/boost feature (`myCode` set).
3. Attacker calls `VLMGP.lock()` again (or any operation invoking `_lock`) so `updateTotalFactor` records their `factor` based on current full locked balance.
4. Attacker calls `startUnlock(fullAmount)` then, after cooldown, `unlock(slotIndex)` — MGP is fully withdrawn back to the attacker, `totalAmount`/`getUserTotalLocked` become 0 for them, but `updateTotalFactor` is never invoked in `unlock()`, so `userInfo.factor` and `totalBoostFactor` remain unchanged.
5. Attacker now has zero locked MGP but retains their `factor` share in `totalBoostFactor`. Any future `trigger()` call from any user's harvest still awards the attacker a slice of `BoostPoint` via `_calBoosted`, indefinitely, without any locked stake — verifiable directly from `ReferralStorage.sol:181-188,242-246` and the absence of the `updateTotalFactor` call in `VLMGP.sol:315-337,352-367`.

        UserInfo storage userInfo = userInfos[_account];
        if (userInfo.myCode == bytes32(0)) return; // user did not activate referral feature
        
        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
