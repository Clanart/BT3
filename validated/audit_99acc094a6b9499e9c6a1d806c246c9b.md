Based on my investigation, I found a concrete analog: GitHub Desktop's custom-protocol URL handler (`x-github-client://openRepo/...`) extracts an attacker-controlled remote URL from the deep link and passes it, effectively unvalidated, into the clone flow — mirroring the original bug class of "a value that should be validated/gated before being forwarded is silently dropped," except here the missing check is a URL/scheme allow-list rather than a `payable` modifier.

### Title
Deep-link `openRepo` action forwards an unvalidated remote URL into `git clone`, enabling argument/transport injection - ([File: app/src/lib/parse-app-url.ts])

### Summary
`parseAppURL` handles the `x-github-client://openRepo/<url>` custom-protocol action registered by the app on all platforms. It validates the `branch`, `pr`, and `filepath` query parameters with regexes, but the `url` field itself — the actual git remote that will be cloned — is passed through with no scheme allow-list and no rejection of values that don't look like a well-formed `http(s)/ssh/git` remote.

### Finding Description
`possibleProtocols` (`x-github-client`, `x-github-desktop-auth`, `github-mac`, `github-windows`) are registered as OS-level protocol handlers in `app/src/main-process/main.ts`, and both `open-url` (macOS) and the `--protocol-launcher` command-line path (Windows) route any URL matching these schemes straight to `handleAppURL` → `parseAppURL`. [1](#0-0) [2](#0-1) 

Inside `parseAppURL`, the `openrepo` branch validates `pr`, `branch`, but the `url` (`parsedPath`) that is returned as `IOpenRepositoryFromURLAction.url` — the value that later becomes the git remote to clone — undergoes no validation of its own: [3](#0-2) 

This action is dispatched via `dispatchURLAction` to `openRepositoryFromUrl`, which flows into `openOrCloneRepository(url)` in the dispatcher, ultimately reaching the git clone path (`app/src/lib/git/clone.ts`): [4](#0-3) [5](#0-4) 

Because this `url` string originates entirely from an external, attacker-controlled deep link (e.g., a link on a malicious webpage, an email, or a crafted GitHub comment that a user clicks), and is never checked against a scheme allow-list (`https:`, `ssh:`, `git:`) or checked for a leading `-` (which git argument parsers interpret as an option rather than a positional URL, the classic vector behind CVE-2017-1000117), this is structurally the same class of issue as the Sense report: a value that should be validated/gated before being used in a sensitive downstream call (there: attaching `msg.value`/protocol fee; here: sanitizing a remote URL before shelling out to git) is instead forwarded unchecked. Contrast this with `enterprise-validate-url.ts`, which *does* enforce an `https:`-only allow-list for the Enterprise sign-in flow — showing the project is aware of this class of check but did not apply the same discipline to the `openrepo` deep-link path. [6](#0-5) 

### Impact Explanation
If the value ultimately reaches git's CLI as a positional URL argument to `clone`/`fetch` (via dugite), an attacker-controlled string starting with `-` could be interpreted as a git option (e.g., `--upload-pack=<cmd>` for SSH transports, or `ext::<cmd>` for the `ext` transport if not blocked) rather than a remote location, potentially resulting in arbitrary command execution on the victim's machine the moment they click a link and confirm the clone. Even absent full RCE, an attacker can silently redirect users to clone from an attacker-controlled repository/host under the guise of a legitimate `openRepo` deep link, which affects what the user later commits/pushes.

### Likelihood Explanation
Moderate-to-high: this requires only that the victim click a link with one of the registered custom protocols (`x-github-client://`, `github-mac://`, `github-windows://`) — no local access, admin rights, or prior compromise needed. Whether this is fully exploitable end-to-end depends on how `app/src/lib/git/clone.ts` invokes dugite (e.g., whether it prepends `--` before the URL argument or validates the scheme before calling git) — I was not able to fully verify the contents of `clone.ts` within the available tool budget, so the presence/absence of a downstream mitigation in that specific file is unconfirmed.

### Recommendation
In `parseAppURL` (`app/src/lib/parse-app-url.ts`), validate the extracted `url` for the `openrepo` action against an explicit allow-list of expected remote schemes (`https:`, `ssh:`, `git:`, or a recognizable `user@host:path` SCP-like form) and reject values beginning with `-` before constructing `IOpenRepositoryFromURLAction`, mirroring the strict validation already implemented in `enterprise-validate-url.ts`.

### Proof of Concept
1. Register/observe that GitHub Desktop is the default handler for `x-github-client://`.
2. Host a link: `<a href="x-github-client://openRepo/-upload-pack=touch$IFS/tmp/pwned">Open in Desktop</a>` (or an equivalent SSH-transport payload).
3. Victim clicks the link; `main.ts`'s `open-url`/`--protocol-launcher` handling invokes `handleAppURL` → `parseAppURL`, which returns `{ name: 'open-repository-from-url', url: '-upload-pack=touch$IFS/tmp/pwned', ... }` with no rejection. [7](#0-6) 
4. The dispatcher's `openRepositoryFromUrl`/`openOrCloneRepository` path passes this string toward the clone invocation without an intervening scheme check. [5](#0-4)

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
