### Title
Wasm code-compile timeout leaves a background goroutine racing the CGO wasmvm cache instead of joining it - ([File: sei-wasmd/x/wasm/keeper/vm_wrapper.go])

### Summary
`VMWrapper.Create` guards calls into the CGO `wasmvm` engine with a mutex, but on timeout it returns while its background goroutine is still executing `w.WasmerEngine.Create(code)`. This mirrors the CVE-2021-47324 bug class: a "stop"/timeout path that does not wait (`del_timer` vs `del_timer_sync`) for an in-flight worker to actually finish before releasing the resource it was protecting, letting a new caller enter the protected region while the old worker is still touching shared state.

### Finding Description
`VMWrapper.Create` holds `w.mu` for the duration of the call and launches a goroutine to invoke the real, non-thread-safe compile call `w.WasmerEngine.Create(code)`, which is a CGO call into the Rust-side `wasmvm` cache (`api.StoreCode(vm.cache, code)`): [1](#0-0) 

If the compile takes longer than `CreateTimeout` (15s), the `select` takes the `timer.C` branch, sets `err`, and returns — the deferred `w.mu.Unlock()` fires immediately — but the goroutine started on line 33 is **not cancelled or joined**. It keeps running in the background, still writing to the named return variables `checksum`/`err` (a data race on function-local memory that has already been "returned"), and, more importantly, it keeps calling into the shared Rust `wasmvm` cache after the mutex has already been released to a new caller.

Since the mutex is the only serialization this wrapper provides around `WasmerEngine` (all other methods — `Instantiate`, `Execute`, `Migrate`, `Sudo`, `Reply`, `Pin`, `Unpin` — take the same lock), the intent is clearly to prevent concurrent CGO calls into the wasmvm cache. The timeout path defeats that guarantee: once it returns, any subsequent `Create`, `Pin`, `Unpin`, `Instantiate`, etc. can acquire `w.mu` and enter the CGO layer while the abandoned goroutine is still inside it, producing genuinely concurrent CGO calls into a cache that this wrapper was built specifically to serialize against. [2](#0-1) 

This is directly analogous to the CVE: `del_timer()` doesn't wait for the handler to finish before the caller proceeds to free/reuse the resource, causing use-after-free; here, the 15s timeout doesn't wait for the goroutine to finish before releasing the mutex that was supposed to make `WasmerEngine` calls mutually exclusive, allowing concurrent CGO access to the shared Rust-side wasm module cache.

### Impact Explanation
Concurrent calls into the wasmvm CGO cache (which manages Rust-owned memory, module compilation, and an in-process module/store cache) are outside Go's memory-safety guarantees. A slow-to-compile Wasm blob (e.g., deliberately large/expensive-to-instrument code submitted via `MsgStoreCode`) held past the 15s window combined with a subsequent overlapping `Create`/`Pin`/`Unpin` call on the same node can trigger concurrent/racing access to the Rust-side cache. Depending on the cache's actual internal locking, this can manifest as memory corruption or a crash in the CGO layer, i.e., a validator/node crash (chain halt) — this is a public/unprivileged CosmWasm code-upload path (`MsgStoreCode`), reachable by any transaction sender.

### Likelihood Explanation
Reaching the race requires only submitting a Wasm binary whose one-time compile step exceeds 15 seconds (attacker fully controls the bytecode complexity/size within the max code size) and then triggering another store/pin/unpin call before the first goroutine finishes. This is entirely within reach of an unprivileged wasm contract deployer with no special privileges, though it depends on actual compile times and on internal thread-safety assumptions of the vendored `wasmvm`/Wasmer cache that were not directly inspectable here.

### Recommendation
Make the timeout path actually cancel/join the worker before releasing the lock: either drop the timeout entirely and rely on gas/instruction metering to bound compile time, or keep holding `w.mu` until the goroutine signals completion via `done` (i.e., wait on `done` in a second, non-early-returning step, or use a proper context-cancelable compile API) so the mutex is never released while `WasmerEngine.Create` is still executing. At minimum, do not write to the shared named returns from the goroutine after the timeout branch has already returned.

### Proof of Concept
1. Submit `MsgStoreCode` with a Wasm binary engineered to take longer than 15 seconds to compile (e.g., very large module or one crafted to stress the Wasmer compiler).
2. `VMWrapper.Create` times out at 15s, returns an error, and releases `w.mu` — but the spawned goroutine is still executing `w.WasmerEngine.Create(code)` against the shared cache.
3. Immediately submit a second `MsgStoreCode`/`MsgPinCodes`/`MsgUnpinCodes` (or any op serialized by `w.mu`) targeting the same node; it acquires the now-free mutex and enters `WasmerEngine` concurrently with the still-running first goroutine.
4. Observe a data race / potential crash in the CGO wasmvm layer under `-race` or via repeated fuzzing with large payloads, confirming the two calls overlap in the underlying non-thread-safe cache. [3](#0-2) [4](#0-3)

```go
const CreateTimeout time.Duration = 15 * time.Second

type VMWrapper struct {
	types.WasmerEngine

	mu *sync.Mutex
}

func NewVMWrapper(inner types.WasmerEngine) types.WasmerEngine {
	return &VMWrapper{
		inner,
		&sync.Mutex{},
	}
}

func (w *VMWrapper) Create(code wasmvm.WasmCode) (checksum wasmvm.Checksum, err error) {
	w.mu.Lock()
	defer w.mu.Unlock()
	timer := time.NewTimer(CreateTimeout)
	done := make(chan struct{}, 1)
	go func() {
		checksum, err = w.WasmerEngine.Create(code)
		done <- struct{}{}
	}()
	select {
	case <-done:
		timer.Stop()
		return
	case <-timer.C:
		err = errors.New("create wasm code timed out")
		return
	}
}
```
