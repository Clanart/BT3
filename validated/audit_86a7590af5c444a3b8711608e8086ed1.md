### Title
Unchecked ERC20 Reward Transfer in ArbWomUp Airdrop Incentive Distribution Permanently Burns User's Claimable Reward - (File: wombat/ArbWomUp.sol, wombat/ArbWomUp2.sol)

### Summary
`ArbWomUp.incentiveDeposit()` and `ArbWomUp2.incentiveDeposit()` (both airdrop/incentive distribution contracts) perform an unchecked ERC20 `transfer()` of the USDT/BUSD incentive reward to the depositing user, while unconditionally recording the reward as claimed in `claimedReward[msg.sender]` before or regardless of the transfer's success. If the reward token behaves as a non-compliant ERC20 (returns `false` on failure instead of reverting), the transfer can silently fail while the accounting still marks the reward as delivered, permanently denying the user that portion of their incentive.

### Finding Description
In `_deposit`/`incentiveDeposit` in `wombat/ArbWomUp.sol`, the WOM deposit itself is transferred safely via `safeTransferFrom` [1](#0-0) , but the reward payout uses a raw, unchecked `transfer()`: [2](#0-1) 

The `claimedReward[msg.sender] += rewardToSend` bookkeeping happens before/independent of the transfer outcome, and `getRewardAmount()` computes future rewards by subtracting `claimedReward[_account]` from the tier-based entitlement [3](#0-2) . If `usdt.transfer()` returns `false` (as permitted by non-compliant ERC20 tokens such as historical USDT-style implementations) instead of reverting, the call still succeeds, the user's WOM deposit is taken, `claimedReward` is incremented as if payment succeeded, but no tokens actually reach the user.

The identical pattern exists in `wombat/ArbWomUp2.sol`: [4](#0-3) 
where `IERC20(busd).transfer(msg.sender, rewardToSend)` is unchecked while `claimedReward[msg.sender] += rewardToSend` is already recorded above it.

Because `claimedReward` is monotonically increasing and directly subtracted in the tiered reward formula, once it is incremented for a failed transfer, the user can never claim that specific reward amount again in any subsequent call — the entitlement is permanently and silently forfeited. This is the same unchecked-transfer root cause as the external report's `_performLoanRepayment` finding: assuming ERC20 `transfer`/`transferFrom` success without checking the return value, in a bug class explicitly cited in the analog rules (airdrop distribution) as in-scope.

### Impact Explanation
A user who calls `incentiveDeposit` deposits real WOM tokens (via `safeTransferFrom`) but, if the configured reward token (`usdt`/`busd`) is non-compliant, may receive nothing in return, while the contract's internal accounting treats the reward as fully paid. This is a permanent, protocol-level loss of the incentive/airdrop reward owed to the user — the user cannot re-claim it through any exposed function, since `claimedReward` has already been incremented. This matches "theft or permanent freezing of unclaimed yield" from an ordinary depositor's transaction, with no privileged role required to trigger it.

### Likelihood Explanation
Triggering requires only that the admin-configured reward token (`usdt`/`busd`) behaves as a non-compliant ERC20 that returns `false` rather than reverting on transfer failure (e.g., insufficient contract balance edge cases or blacklist/pausable token behavior), a well-documented and realistic class of ERC20 tokens in production. Any ordinary user calling `incentiveDeposit` under such conditions triggers the loss; no special privileges or governance actions are needed.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used elsewhere via `using SafeERC20 for IERC20;` in both files) for the reward payouts in `ArbWomUp.incentiveDeposit` and `ArbWomUp2.incentiveDeposit`, and only update `claimedReward` after (or atomically with) a verified successful transfer, e.g.:
```solidity
IERC20(usdt).safeTransfer(msg.sender, rewardToSend);
```
so a failed transfer reverts the entire transaction instead of silently burning the user's claimable reward.

### Proof of Concept
1. Owner deploys `ArbWomUp` and sets `usdt` to a non-compliant ERC20 that returns `false` on transfer failure instead of reverting (e.g., a token whose contract balance can be drained by other calls, or one with blacklist logic).
2. Contract's USDT balance becomes insufficient to cover a pending reward for a specific tier/user right at the moment `incentiveDeposit` executes (e.g. due to a race with `getRewardAmount`'s balance check being read before the actual transfer, or the token blacklists the recipient).
3. User calls `incentiveDeposit(_amount)`: WOM is pulled via `safeTransferFrom` (succeeds), `claimedReward[msg.sender] += rewardToSend` executes, then `IERC20(usdt).transfer(msg.sender, rewardToSend)` returns `false` without reverting.
4. Transaction completes successfully; user's WOM is now locked in the contract, `claimedReward[msg.sender]` reflects the reward as paid, but the user received zero USDT.
5. Any subsequent call to `incentiveDeposit`/`getRewardAmount` for this user subtracts the already-incremented `claimedReward`, permanently excluding the lost reward from all future entitlement calculations.

    function getRewardAmount(uint256 _amount, address _account) external view returns (uint256) {
        if (_amount == 0 || rewardMultiplier.length == 0) return 0;
        uint256 accumulated = _amount + userWOMDeposited[_account];

        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accumulated > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }
        rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];

        uint256 usdtReward = (rewardAmount / DENOMINATOR) - claimedReward[_account];
        uint256 usdtleft = IERC20(usdt).balanceOf(address(this));

        return usdtReward > usdtleft ? usdtleft : usdtReward;
    }
