### Title
Panic on unregistered participant's encryption key during blame verification allows unauthenticated node crash - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG encryption layer indexes internal `HashMap<Participant, C::G>` maps with `[]` instead of returning an error. `Decryption::decrypt_with_proof` and `Encryption::encrypt` will panic when the referenced participant was never registered. A participant who triggers the blame/decryption flow while naming a decryptor (or recipient) whose `EncryptionKeyMessage` was never registered causes an index-out-of-map panic, crashing the process. This is the Serai analog of CVE-2024-0746: attacker-reachable crash/DoS from untrusted input.

### Finding Description
`crypto/dkg/pedpop/src/encryption.rs` uses direct `HashMap` indexing on attacker-influenced participant indexes:

```rust
// Decryption::decrypt_with_proof — line ~388
&[self.enc_keys[&decryptor], *proof.key],

// Encryption::encrypt — line ~466
encrypt(rng, self.context, self.i, self.decryption.enc_keys[&participant], msg)
```

and an assertion on re-registration:

```rust
// Decryption::register — line ~356
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
```

`enc_keys` is populated only via `Decryption::register`, which is driven by the set of `EncryptionKeyMessage`s actually received/parsed (`EncryptionKeyMessage::read` at line 57 consumes untrusted bytes). The blame path (`decrypt_with_proof`) is reachable via `AdditionalBlameMachine::blame`, which is invoked when an accuser submits an `InvalidDkgShare` claim naming an `accuser`/`decryptor` participant. If the named decryptor participant never successfully registered an encryption key (e.g., they sent no commitments, malformed commitments rejected by `read`, or were excluded), `self.enc_keys[&decryptor]` panics rather than returning `DecryptionError`.

The same pattern in `Encryption::encrypt` fires if secret shares are generated for a participant list containing an index not present in the registered commitments map — the API takes a `HashMap<Participant, EncryptionKeyMessage>` keyed by attacker-chosen `Participant` values (any u16 from 1..=65535), and no validation ties the share-recipient set to the registered-key set before indexing.

### Impact Explanation
A panic in this code path aborts the calling thread/process. For a validator/processor running the DKG or blame-verification logic, a single crafted `InvalidDkgShare`/blame trigger naming an unregistered decryptor crashes the node — an unprivileged remote denial of service, matching the Medium-severity availability impact class of the source CVE (CVSS 6.5, A:H). There is no secret leakage, but availability of the signing node is lost mid-protocol.

### Likelihood Explanation
Reachable by any protocol participant able to submit a blame transaction or withhold their `EncryptionKeyMessage`: the map is keyed on `Participant` values taken from deserialized messages, and the indexing sites assume a completeness invariant (all participants registered) that is enforced nowhere in these functions. The panic requires no cryptographic work — just referencing an absent key.

### Recommendation
Replace `HashMap` indexing with `get()` plus an error path:

- In `decrypt_with_proof`: `let enc_key = self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?;`
- In `Encryption::encrypt`: return a `Result` or skip unregistered participants instead of panicking.
- In `Decryption::register`: replace `assert!` with a checked rejection (`io::Error`/dedicated error) so duplicate registrations are faults, not crashes.

### Proof of Concept
Conceptual trigger (no exploit code needed for a panic):

1. Complete a PedPoP DKG round where participant P never submits a valid `EncryptionKeyMessage` (or it is rejected by `EncryptionKeyMessage::read`), so `P` is absent from `Decryption.enc_keys`.
2. Submit an invalid-share accusation whose resolution calls `decrypt_with_proof(from, decryptor = P, msg, Some(proof))` with a PoP-valid `msg`.
3. `pop.verify` succeeds, the `proof` branch executes, and `self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388` panics (`HashMap` index on missing key), aborting the process.

Note: full confirmation of the blame call chain's argument mapping (which participant becomes `decryptor`) depends on `KeyMachine`/`AdditionalBlameMachine` internals I could not fully trace within the available context; the panic sites themselves are verified in `crypto/dkg/pedpop/src/encryption.rs` (lines ~356, ~388, ~466).
