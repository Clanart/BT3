Based on my investigation, I found a concrete authorization gap in the ISMP host-governance path that matches the "onlyPair"-style bug class: a check that authenticates at the wrong granularity (chain-level instead of module-level), allowing an entity that is not the intended privileged actor to be treated as authorized.

### Title
Missing module-identity binding in `HostManager.onAccept` allows any Hyperbridge-chain-originated message to trigger governance actions - (File: `evm/src/core/HostManager.sol`)

### Summary
`HostManager.onAccept` is the single entry point through which Hyperbridge cross-chain governance withdraws protocol/relayer revenue and updates `EvmHost` parameters (consensus client, fee token, admin, etc.) on every connected EVM chain. It only checks that the incoming request's **source chain** equals the configured `hyperbridge` state machine id — it never checks the request's **source module** (`from`), which is the actual identity of the pallet that is supposed to be authorized to issue these commands (`pallet-ismp-host-executive`, module id `b"hostexec"`).

### Finding Description
`HostManager.onAccept` authenticates only the chain, not the module: [1](#0-0) 

Compare this to how the legitimate caller is supposed to be identified. `pallet-ismp-host-executive` always sets `from: PALLET_ID.to_bytes()` when it dispatches `Withdraw`/`SetHostParam` actions: [2](#0-1) [3](#0-2) 

But nothing on the receiving side (`HostManager.onAccept`) verifies that `request.from == PALLET_ID.to_bytes()`. The outgoing `PostRequest.source` field is set automatically by the dispatcher to the chain's own `host_state_machine()` for *every* dispatched request, regardless of which pallet or account triggered the dispatch — it is not evidence of module-level authorization: [4](#0-3) 

The generic `IsmpDispatcher::dispatch_request` trait implementation copies the caller-supplied `from` field verbatim into the outgoing request without binding it to the calling pallet or account identity: [5](#0-4) 

This is architecturally analogous to the `BathToken` finding: `onlyPair` trusted `msg.sender == bathHouse`-controlled state without an independent binding to a specific, non-reassignable identity. Here, `HostManager.onAccept`'s `restrict(_params.host)` + `request.source == hyperbridge` checks only prove "this arrived from the Hyperbridge chain," not "this was dispatched by the host-executive governance pallet specifically." Any other pallet (existing or future) on the Hyperbridge/Nexus runtime that is permitted to call `IsmpDispatcher::dispatch_request` with a `to` matching a connected chain's `HostManager` address and a caller-controlled `from`/`body` would be indistinguishable from legitimate governance to `HostManager.onAccept`.

### Impact Explanation
If reachable, this allows `OnAcceptActions.Withdraw` (drain accrued protocol/relayer revenue to an arbitrary beneficiary via `EvmHost.withdraw`) or `OnAcceptActions.SetHostParam` (rewrite `feeToken`, `admin`, `handler`, `consensusClient`, `hostManager` on the target `EvmHost`) to be executed by an unintended module — i.e., unauthorized execution / fund loss / wrong-beneficiary transfer, and potentially a full hijack of the host's trust roots (consensus client, handler) on that connected chain. This falls squarely in "Bridged assets ... relayer rewards ... must move exactly once and only to the rightful beneficiary" and "Cross-chain admin or host-management effects must not be reachable through ... wrong module bindings."

### Likelihood Explanation
The missing `request.from` check is a concrete, verifiable gap in the code I reviewed — `HostManager.onAccept` genuinely never checks the module identity. However, I was not able to conclusively confirm, within the available context, an already-shipped, fully unprivileged (e.g., ordinary signed-origin) extrinsic in the current runtimes (`gargantua`, `nexus`, `demo`, `hyper-fungible-token`, `bandwidth`) that lets an arbitrary user freely choose `from`, `to`, and `body` and reach a target `HostManager` address; the examples I inspected (`pallet_ismp_demo::dispatch_to_evm`, `pallet_bandwidth::dispatch_withdraw`) either hardcode `from`/`body` or gate the call behind `AdminOrigin`. This means the exploitability today is contingent on some other pallet in the deployed runtime exposing unrestricted ISMP dispatch — which I could not fully rule out or confirm given tool-call limits. The underlying authorization gap in `HostManager.onAccept` itself is nonetheless real and should be treated as a defense-in-depth failure independent of which pallet ultimately triggers it.

### Recommendation
In `HostManager.onAccept`, add an explicit check that `request.from == HOST_EXECUTIVE_MODULE_ID` (the well-known `b"hostexec"` pallet module id), in addition to the existing `request.source` chain check, so that governance actions can only be triggered by the specific, expected module rather than any entity capable of dispatching from the Hyperbridge chain.

### Proof of Concept
1. Some pallet `P` on the Hyperbridge/Nexus chain (present now or added later) is permitted to call `IsmpDispatcher::dispatch_request` with a `DispatchPost { dest: <EvmChain>, from: <attacker-chosen-bytes>, to: <HostManager address>, body: [0x00, encode(WithdrawParams{ beneficiary: attacker, amount: <all fee token balance>, token: feeToken })] }`.
2. The pallet-ismp dispatcher sets `source = host_state_machine()` automatically (the Hyperbridge chain's own id) regardless of which pallet called it: `modules/pallets/ismp/src/dispatcher.rs:128-146`.
3. Once relayed and proven on the destination `EvmHost`, `HostManager.onAccept` is invoked. It checks only `restrict(_params.host)` and `request.source == hyperbridge()`, both of which pass: `evm/src/core/HostManager.sol:95-98`.
4. `action = OnAcceptActions.Withdraw` decodes and calls `IHostManager(_params.host).withdraw(withdrawParams)`, sending the host's accrued fee-token balance to the attacker-specified beneficiary: `evm/src/core/HostManager.sol:100-104`, `evm/src/core/EvmHost.sol:651-660`.
5. No check anywhere in this path verifies that the dispatching module on the Hyperbridge chain is actually `pallet-ismp-host-executive` (`b"hostexec"`).

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
