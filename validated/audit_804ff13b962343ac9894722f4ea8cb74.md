### Title
`Scanner::scan_block` reports immature coinbase outputs as immediately spendable `ReceivedOutput`s, enabling transactions that are consensus-invalid - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_block` iterates over `block.txdata` including `txdata[0]` (the coinbase transaction) and returns any matching outputs as `ReceivedOutput` with no maturity marker or height tracking. The bug class from the report — a state recorded at initiation time being treated as final even though the rule that governs it is time/height-dependent — maps directly: the scanner records "this output exists and is ours" as an absolute fact, while Bitcoin consensus says a coinbase output only becomes spendable 100 blocks later. Any consumer that feeds scanner results into `SignableTransaction`/FROST signing will build and sign a transaction the network rejects.

### Finding Description
`scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script, storing only `offset`, `output`, and `outpoint` — no block height, no coinbase flag (networks/bitcoin/src/wallet/mod.rs:199-214). `scan_block` calls it over all transactions in the block including the coinbase (mod.rs:221-227). The doc comment acknowledges the hazard ("This will also scan the coinbase transaction which is bound by maturity"), but the API returns `Vec<ReceivedOutput>` indistinguishable in type from spendable outputs, and nothing in `ReceivedOutput` lets a caller programmatically distinguish an immature coinbase output — they must re-derive which outpoints came from `txdata[0]` themselves.

An unprivileged miner can reach this path with public inputs: they mine a block whose coinbase pays to the scanner's registered script (a plain P2TR script is public knowledge for any registered offset, e.g. a known deposit address). The scanner then reports funds as received that cannot actually be spent.

### Impact Explanation
A downstream consumer (processor building a withdrawal/re-organization transaction) that trusts `scan_block` results will include the immature coinbase output as an input to `SignableTransaction`, run the full FROST signing ceremony over it, and produce a transaction that fails consensus validation (`bad-txns-premature-spend-of-coinbase`). This is "funds reported received that are not spendable": the protocol's accounting sees the output, but spending it is impossible for 100 blocks. It wastes a signing round at minimum, and if the output is co-spent with real inputs, the entire signed transaction is invalid — a liveness failure reachable purely by a miner's public transaction data.

### Likelihood Explanation
Low-to-moderate in practice: it requires a miner (or a pool) to deliberately direct coinbase payouts at a Serai-watched script, which costs them nothing extra if they already mine a block, but requires them to win one. It can also occur incidentally if a mining pool pays out to an address the protocol scans. The comment shows the authors were aware; the defect is that the safeguard is a non-enforced note rather than an API distinction (e.g., a `coinbase` flag or excluding `txdata[0]`).

### Recommendation
Have `scan_block` either skip `block.txdata[0]` entirely, or return coinbase-originated `ReceivedOutput`s tagged (e.g., `ReceivedOutput { .., immature: true }`) so consumers can enforce maturity. Since `scan_block` lacks height context, the cleanest fix is changing its signature to take the block height, or restricting it to `block.txdata[1 ..]` and exposing coinbase scanning via a separate, clearly-marked function.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
