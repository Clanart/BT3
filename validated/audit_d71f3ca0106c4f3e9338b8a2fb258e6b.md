### Title
Precompile signature verification cost is charged per declared signature count, not per byte hashed, allowing cheap-to-fee but expensive-to-verify secp256k1 payloads - (File: precompiles/src/secp256k1.rs)

### Summary
`agave_precompiles::secp256k1::verify` re-hashes an attacker-controlled `message_slice` of up to `message_data_size` (u16, max 65535) bytes via `solana_keccak_hasher::hash` once per signature entry, for up to `count` (u8, max 255) entries [1](#0-0) . Both the cost-model's pre-execution estimate and the actual in-SVM execution path charge cost only as a function of the *number* of signatures, not the number of bytes hashed, so the marginal cost of large `message_data_size` values is effectively free from a compute-budgeting perspective.

### Finding Description
The verify loop parses `offsets.message_data_size` directly from attacker-supplied instruction data and uses it, unclamped beyond `u16::MAX`, as the length of the slice passed to `solana_keccak_hasher::hash` [2](#0-1) . This repeats up to 255 times (`count` is a `u8`) per precompile instruction [3](#0-2) .

Two independent cost-accounting paths are relevant:

1. **Cost-model / fee estimation** (`cost-model/src/cost_model.rs::get_signature_cost`): charges `SECP256K1_VERIFY_COST` (a fixed constant, `223 * 30 = 6690` CU) multiplied only by `num_secp256k1_instruction_signatures`, which is simply `data[0]` (the declared signature count) [4](#0-3) [5](#0-4) . There is no term in this formula for `message_data_size`.

2. **Actual execution charge** (`program-runtime/src/invoke_context.rs::process_precompile`): when a top-level instruction targets a precompile, `process_message` dispatches to `process_precompile`, which calls the registered `epoch_stake_callback.process_precompile(...)` (ultimately `agave_precompiles::secp256k1::verify`) with **no call to `compute_meter.consume_checked`** anywhere in that path [6](#0-5) . This contrasts with ordinary builtins/syscalls, which always charge CUs proportional to work (e.g. `SyscallSecp256k1Recover` charges a fixed `secp256k1_recover_cost`, and CPI instruction-data translation charges `data.len() / cpi_bytes_per_unit`) [7](#0-6) [8](#0-7) . A dedicated test even documents that a precompile instruction "consume[s] 0 from CU-meter" during VM execution [9](#0-8) .

So regardless of whether `move_precompile_verification_to_svm` is active, the byte-proportional cost of hashing/verifying large messages is not reflected in either the pre-execution cost estimate used for block-cost accounting or the actual compute-unit meter consumed during execution.

**However**, actual exploitability is bounded by transaction-size limits that are outside the scope of `precompiles/src/secp256k1.rs` itself: `message_instruction_index`/`message_data_offset`/`message_data_size` must reference bytes that genuinely exist inside some instruction's data within the *same transaction* (`get_data_slice` bounds-checks `offset + size <= signature_instruction.len()`) [10](#0-9) . Transactions are constrained by the standard Solana wire/packet size limit (commonly referenced as `PACKET_DATA_SIZE`/1232 bytes) enforced elsewhere in the ingestion pipeline, which I was not able to fully trace within the available index in this session — I could not confirm the exact enforcement point or whether any code path (e.g. large `TransactionMessage`s in certain non-standard ingestion paths) could actually carry an instruction with ~64KB of data. Because of this, I cannot confirm the "255 signatures x 65535-byte message referencing one ~64KB instruction" scenario is reachable as literally described; the same large instruction's data can be reused by all signature offset entries (all pointing at the same `message_instruction_index`), which relaxes the requirement to just one large instruction rather than 255 separate ones, but the instruction's data itself is still bounded by the transaction's total wire size, which is typically far below 64KB.

Within the size that *is* reachable (an instruction data blob up to the maximum allowed by transaction size limits, referenced by up to 255 signature offset entries each declaring `message_data_size` equal to that maximum), the CU-cost-vs-real-work mismatch documented above still holds: cost scales only with `count`, not with `count * message_data_size`.

### Impact Explanation
This is a compute-cost-accounting deficiency (underpriced compute) rather than a memory-safety or privilege-escalation bug: an attacker can, within the actual maximum instruction-data size permitted by the transaction/packet-size limits, construct a secp256k1 precompile instruction with `count` up to 255, all referencing the same large instruction, to force up to 255 keccak hashes plus 255 libsecp256k1 recovery operations over the maximum permitted bytes per hash, while paying a fee proportional only to a fixed per-signature CU cost rather than to the bytes actually hashed. This falls into the "materially underpriced compute" category referenced by the rules, matching an Agave bounty category of compute-unit-accounting / DoS-amplification via cheap-to-encode-but-expensive-to-verify instructions. The severity is limited by the maximum transaction size (not 64KB as hypothesized in the question), which substantially reduces the amplification factor relative to the scenario as literally stated.

### Likelihood Explanation
- Preconditions: attacker needs only normal transaction-submission ability (unprivileged), no special account state, and can freely control the count and offsets fields of the secp256k1 instruction and craft an oversized companion instruction (bounded by max transaction size).
- The bug is deterministic and repeatable per transaction; it doesn't require racing, staking, or validator control.
- The real bottleneck is the maximum data size obtainable within one Solana transaction, which I could not fully verify within available index context (see caveat above) — this materially affects the achievable amplification and thus the practical severity/likelihood versus the question's u16::MAX-per-signature hypothesis.

### Recommendation
- Charge compute units in `process_precompile` (or in the callback that invokes `Precompile::verify`) proportional to the total bytes processed by all signature/message/eth-address slices referenced by the instruction (e.g., a per-byte keccak/secp256k1-recovery cost added via `compute_meter.consume_checked`), mirroring how `sha256_byte_cost`, `cpi_bytes_per_unit`, etc. already charge for other byte-proportional operations.
- Update `cost_model::get_signature_cost` (or introduce a companion cost term) to account for `message_data_size` summed across all `SecpSignatureOffsets` entries in secp256k1/ed25519/secp256r1 precompile instructions, not just the declared signature count.
- Add an explicit cap on `message_data_size` per signature entry independent of the surrounding instruction's actual length, to bound worst-case hashing work per precompile instruction regardless of future changes to transaction size limits.

    let max_len = 1200usize; // adjust to the actual enforced max instruction/transaction data size

            signature_instruction_index: 0,

fn get_data_slice<'a>(
    instruction_datas: &'a [&[u8]],
    instruction_index: u8,
    offset_start: u16,
    size: usize,
) -> Result<&'a [u8], PrecompileError> {
    let signature_index = instruction_index as usize;
    if signature_index >= instruction_datas.len() {
        return Err(PrecompileError::InvalidDataOffsets);
    }
    let signature_instruction = &instruction_datas[signature_index];
    let start = offset_start as usize;
    let end = start.saturating_add(size);
    if end > signature_instruction.len() {
        return Err(PrecompileError::InvalidSignature);
    }

    Ok(&instruction_datas[signature_index][start..end])
}
