### Title
JIT (Just-In-Time) Staking Attack on Instantaneous, Balance-Proportional Reward Distribution in BaseRewardPool - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool` (and its siblings `BaseRewardPoolV2`, `vlMGPBaseRewarder`, `mWOMSVBaseRewarder`) distribute newly harvested/donated reward tokens by instantly bumping `rewardPerTokenStored` in proportion to `totalStaked()` at the exact moment the reward is provisioned [1](#0-0) . Because deposits and withdrawals into the underlying pool (`MasterMagpie` / `WombatPoolHelperV2`) are permissionless, instant, and cost nothing beyond gas, and because `harvest()` that triggers the reward provisioning is also permissionless [2](#0-1) , an attacker can perform the same class of "JIT liquidity" manipulation described in the external report: inject a large, disposable stake immediately before the reward-triggering transaction, capture a disproportionate share of the just-harvested rewards, then withdraw right after — diluting the rightful yield of genuine long-term stakers.

### Finding Description
`BaseRewardPool._provisionReward` computes the reward-per-token increment using the pool's **current** `totalStaked()` balance, not a time-weighted or streamed average: [3](#0-2) 

`totalStaked()` is read live from the staking-token balance held by `MasterMagpie`: [4](#0-3) 

A user's earned amount is `balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid) / decimals + userRewards`, and `userRewardPerTokenPaid` is only reset on the account's own deposit/withdraw/harvest via `_updateFor`: [5](#0-4) [6](#0-5) 

Deposits and withdrawals of the receipt/staking token flow through `MasterMagpie._deposit`/`_withdraw`, which contain no lock, cooldown, or minimum holding period — a user can deposit and withdraw in the same transaction bundle: [7](#0-6) 

The entry point users interact with, `WombatPoolHelperV2`, exposes `deposit`, `depositFor`, `withdraw`, and `harvest` as unrestricted external functions with no access control and no fee: [8](#0-7) 

`harvest()` simply forwards to `WombatStaking.harvest(lpToken)`, which pulls in newly accrued WOM rewards from Wombat and calls `queueNewRewards` on the `BaseRewardPool`, instantly crediting `rewardPerTokenStored` based on whatever `totalStaked()` is at that instant.

**Attack flow (analog to the AntiSandwichHook JIT report):**
1. Attacker observes a large amount of pending harvestable reward (visible via `pendingWom()`).
2. Attacker calls `WombatPoolHelperV2.deposit()`/`depositFor()` with a large stake, instantly inflating `totalStaked()` in `MasterMagpie` for that pool.
3. In the same block (or immediately after), attacker (or anyone) calls `WombatPoolHelperV2.harvest()`, which triggers `WombatStaking.harvest(lpToken)` → `BaseRewardPool.queueNewRewards()`, bumping `rewardPerTokenStored` proportionally to the now-inflated `totalStaked()`.
4. Because the attacker's `userRewardPerTokenPaid` was only just set (at deposit, prior to the bump), `earned()` credits the attacker a large share of the newly distributed reward purely due to momentary balance size.
5. Attacker immediately calls `WombatPoolHelperV2.withdraw()` to unstake and claims the harvested reward, exiting with yield that should have accrued to genuine long-term stakers who held their position across the full reward-accrual period.

This exactly mirrors the reported bug class: a reward-distribution mechanism that (a) is proportional to point-in-time balance rather than time-weighted, and (b) allows costless, permissionless, same-block position changes — enabling value extraction from other unprivileged participants without any of the intended cost/penalty being borne.

### Impact Explanation
This constitutes theft of unclaimed yield from legitimate stakers: reward tokens (WOM/MGP-denominated rewards routed through `BaseRewardPool`/`vlMGPBaseRewarder`/`mWOMSVBaseRewarder`) that should accrue to long-term depositors are instead diverted to a transient, JIT depositor who contributes no meaningful time-weighted exposure to the pool. This degrades the reward economics for all real stakers across every pool that uses this reward-pool pattern (WombatStaking LP pools, vlMGP, mWomSV).

### Likelihood Explanation
Likelihood is high in economic terms whenever a large pending reward accrues and harvesting is permissionless and unthrottled: any address with sufficient capital (often flash-loanable, if the staking token or its underlying LP is available via flash loan/mint) can execute deposit → harvest → withdraw as a single atomic bundle with no cooldown blocking it, and no fee discourages the behavior.

### Recommendation
Introduce a time-weighted or streamed reward-release mechanism (e.g., a `rewardRate`/`periodFinish` streaming model as already used elsewhere in the codebase, see `WomUp.sol`'s `rewardPerToken()` streaming logic) instead of crediting the full donated/queued reward instantly to whatever balance is staked at the moment of `queueNewRewards`/`donateRewards`. Alternatively, enforce a minimum staking duration or decouple `harvest()` triggering from immediate deposit/withdraw eligibility (e.g., snapshot `totalStaked()`/`balanceOf` prior to the block in which the harvest is executed) so that same-block deposit-then-withdraw cannot capture freshly harvested rewards.

### Proof of Concept
Conceptual PoC (single transaction bundle / same block):
```solidity
// 1. Attacker deposits large stake right before harvest
WombatPoolHelperV2(helper).deposit(bigAmount, 0);

// 2. Trigger harvest — pulls pending WOM, credits rewardPerTokenStored
//    proportional to totalStaked() which now includes attacker's stake
WombatPoolHelperV2(helper).harvest();

// 3. Attacker withdraws immediately, claims disproportionate reward share
WombatPoolHelperV2(helper).withdraw(bigAmount, 0);
// harvest is auto-triggered on withdraw via MasterMagpie._withdraw -> _harvestBaseRewarder
```
This relies on `_provisionReward`'s use of live `totalStaked()` [9](#0-8)  combined with unrestricted, lock-free deposit/withdraw in `MasterMagpie._deposit`/`_withdraw` [10](#0-9) , and the permissionless `harvest()` entry point [2](#0-1) .

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
