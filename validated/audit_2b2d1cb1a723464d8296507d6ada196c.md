### Title
Unsafe `_mint` in `BridgeTransferERC721.handleERC721Transfer` can permanently lock bridged ERC721 tokens minted to non-receiving contracts - (File: contracts/service_chain/bridge/BridgeTransferERC721.sol)

### Summary
When the service-chain bridge operates in mint-burn mode, tokens crossing to the destination chain are (re)created via `ERC721MetadataMintable.mintWithTokenURI`, which calls the OpenZeppelin v2 `_mint` primitive instead of `_safeMint`. Because the destination address (`_to`) of the transfer is chosen by the unprivileged user who initiates the request on the source chain, any user can cause an ERC721 token to be minted to a contract address that does not implement `onERC721Received`, permanently locking it.

### Finding Description
An unprivileged holder calls the public, unauthenticated `requestERC721Transfer(address _tokenAddress, address _to, uint256 _tokenId, bytes _extraData)` function, transferring their own token into the bridge and emitting a cross-chain request with an attacker-controlled `_to` address. [1](#0-0) 

On the counterpart chain, once relayed, `handleERC721Transfer` is executed by the bridge operator based solely on the emitted request data. If the bridge runs in `modeMintBurn`, it mints the token directly to the user-supplied `_to` address via `ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI)`: [2](#0-1) 

`mintWithTokenURI` calls the internal `_mint`, not `_safeMint`: [3](#0-2) 

The underlying `_mint` implementation performs no receiver capability check whatsoever — it simply updates `_tokenOwner` and emits `Transfer`: [4](#0-3) 

Because the `_to` address that ultimately receives the minted token is fully controlled by the original (unprivileged) requester on the source chain, and the operator relays the request faithfully without validating that `_to` can receive the NFT, any contract address lacking `onERC721Received` support that becomes the destination will receive a token that can never be moved again by any transaction.

### Impact Explanation
Tokens bridged in mint-burn mode can become permanently and irrecoverably locked once minted to an incompatible contract address, resulting in an irreversible loss of the represented asset. This affects the `ServiceChainNFT` contract family and any other `ERC721MetadataMintable`-based token registered with the bridge in mint-burn mode. Because `requestERC721Transfer` lets the caller freely choose the destination `_to` on the other chain, this is not limited to self-inflicted mistakes: a malicious actor could deliberately target a known non-receiving smart-contract address (e.g., a victim's vault, multisig, or other on-chain contract) to grief/lock value belonging to protocol participants relying on the bridge, causing a permanent loss of the token's value.

### Likelihood Explanation
Likelihood is Medium: it requires the bridge to be configured in `modeMintBurn` and requires a destination address that does not implement `onERC721Received` (e.g., most non-ERC721Receiver-aware smart-contract wallets, DeFi vaults, or intentionally deployed griefing contracts). No special privileges are needed beyond owning a registered token and calling the standard public `requestERC721Transfer` entry point; the operator faithfully relays whatever `_to` was submitted.

### Recommendation
Replace the `_mint` call path with `_safeMint` (or add an explicit check for `onERC721Received` support before minting) in `ERC721MetadataMintable.mintWithTokenURI` / `ERC721Mintable.mint`, or have `BridgeTransferERC721.handleERC721Transfer` validate that `_to` is either an EOA or implements `IERC721Receiver` before invoking mint, falling back to holding the token in the bridge (similar to non-mint-burn mode) if the check fails.

### Proof of Concept
1. Deploy `ServiceChainNFT` (or `ServiceChainNFT_NoURI`) and configure the bridge in `modeMintBurn = true` between chain A and chain B.
2. On chain A, an unprivileged user owning `tokenId` calls `bridge.requestERC721Transfer(nftAddress, victimContract, tokenId, "0x")`, where `victimContract` is any deployed contract that does not implement `onERC721Received` (e.g., a plain multisig or vault contract). [1](#0-0) 
3. The bridge operator observes the `RequestValueTransferEncoded` event and calls `handleERC721Transfer` on chain B's bridge with the same `_to = victimContract`.
4. `handleERC721Transfer` executes `ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(victimContract, tokenId, tokenURI)`, which succeeds and mints the NFT to `victimContract`. [2](#0-1) 
5. Because `victimContract` cannot call `transferFrom`/`approve` logic for tokens it never expected to hold (or simply has no mechanism to move arbitrary ERC721s it did not explicitly integrate for), the token is permanently stuck with no code path to move it out, resulting in permanent loss.

    /**
     * @dev Internal function to mint a new token.
     * Reverts if the given token ID already exists.
     * @param to The address that will own the minted token
     * @param tokenId uint256 ID of the token to be minted
     */
    function _mint(address to, uint256 tokenId) internal {
        require(to != address(0), "ERC721: mint to the zero address");
        require(!_exists(tokenId), "ERC721: token already minted");

        _tokenOwner[tokenId] = to;
        _ownedTokensCount[to].increment();

        emit Transfer(address(0), to, tokenId);
    }
