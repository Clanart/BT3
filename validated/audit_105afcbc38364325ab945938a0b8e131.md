### Title
Automatic remote-URL rewrite trusts GitHub API `clone_url` without validating the target host, enabling silent redirection of `origin` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a repository's `origin` remote URL using the `clone_url` field of a `IAPIRepository` object fetched from the GitHub API/GitHub Enterprise Server, gating the write only on protocol-scheme equality and a lax `urlMatchesRemote` comparison — never confirming with the user or validating that the new host is trustworthy. This mirrors the `RizLendingPoolAddressesProvider` bug class: a value that is supposed to only be set through a trusted/validated path (the user explicitly changing the remote, or the initial clone) can instead be silently overwritten with an externally-supplied, less-trusted value that bypasses the intended validation.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  takes `apiRepo.clone_url` — a string that originates from a GitHub API response (`api.github.com` or, more importantly, a self-hosted GitHub Enterprise Server the user has added as an account) — and, if the URL "protocol" of the old and new remote match and a heuristic `urlMatchesRemote`/`remoteUrlUnchanged` check is satisfied, calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` directly.

That call flows to [2](#0-1)  and ultimately to `setRemoteURL` in [3](#0-2) , which runs `git remote set-url <name> <url>` with the attacker-influenced `url` used verbatim — no allowlist of hosts/protocols, no user prompt, and (unlike `clone.ts`, which explicitly guards against sensitive destinations at [4](#0-3) ) no equivalent safety backstop for remote-URL rewrites.

The only gate is `protocolsMatch` (both URLs must have the same `URL.parse` scheme, e.g. both `https:`) and `urlMatchesRemote`, which is a hostname/owner/name string comparison in [5](#0-4) . Because the check only compares scheme and repo path structure — never that the *hostname itself* is unchanged/expected — a GitHub Enterprise Server (an "API object" the report's threat model explicitly allows an attacker to control) can return a `clone_url` with the same protocol but pointing at a completely different, attacker-controlled host with a similarly-shaped owner/name path, and Desktop will silently repoint `origin` to it.

This is functionally identical to the report's root cause: **a canonical/trusted target (the validated proxy address / the user-configured remote) is overwritten through a side path that skips the invariant the primary path enforces**, because there is no check that the new value is "the same trustworthy target," only a shape/scheme check.

### Impact Explanation
If `origin` is silently repointed to an attacker-controlled remote with a matching URL "shape," subsequent user-initiated `git push` operations would send the user's commits (potentially private source code) to the attacker's repository instead of the intended one, and subsequent `git fetch`/`git pull` would silently merge attacker-controlled history into the user's working repository — both are explicitly listed as valid impacts ("silent corruption of what the user commits or pushes"). This requires no user awareness: there is no dialog, confirmation, or diff shown before the remote is rewritten; the change happens as part of routine background repository refresh.

### Likelihood Explanation
Exploitation requires the attacker to control the API server backing an account the victim has added to Desktop (most plausible via a malicious/compromised GitHub Enterprise Server, which is an explicitly in-scope "GitHub API object" attacker per the report's threat model) or a man-in-the-middle able to tamper with API responses. It does not require local/physical access, admin rights, prior malware, leaked credentials, or unusual user steps — the victim only needs to have the repository open in Desktop while it performs a normal background refresh against that account's API. The scheme-match requirement narrows but does not eliminate the attack surface, since the attacker fully controls the `clone_url` value returned and only needs to keep the scheme identical.

### Recommendation
- Do not auto-rewrite `origin` based on API-derived `clone_url` without also validating that the **hostname** of the new URL matches the hostname of the account's configured API endpoint (or the existing remote's hostname), not just the protocol scheme.
- Require explicit user confirmation before silently changing an existing remote URL to a different host.
- Apply the same "sensitive/expected target" validation used for clone destinations in `isClonePathSensitive` (`app/src/lib/git/clone.ts`) to remote-URL rewrites — i.e., add an equivalent guard in `setRemoteURL`/`updateRemoteUrl` that rejects host changes that weren't explicitly approved by the user.

### Proof of Concept
1. Victim adds a self-hosted GitHub Enterprise Server account (attacker-controlled) to GitHub Desktop and clones a repository from it, e.g. `https://ghe.evil-but-plausible.example/org/repo`.
2. Attacker's server later serves an API response for that repository where `clone_url` is `https://ghe.evil-but-plausible.example.attacker.net/org/repo` (or any other host under attacker control) — same `https:` scheme, same `owner/name` shape so `urlMatchesRemote`'s owner/name comparison can be satisfied while the hostname differs, depending on how the two are compared.
3. On the next background repository refresh, `updateRemoteUrl` ( [6](#0-5) ) calls `gitStore.setRemoteURL`, which runs `git remote set-url origin <attacker-url>` with no user prompt.
4. The victim's next `git push` (via Desktop) sends their commits to the attacker's remote unknowingly.

Note: I could not fully trace the exact call site(s) in `app-store.ts` that invoke `updateRemoteUrl` during automatic refresh (only 3 textual matches were found in that ~9000+ line file and their surrounding context was not retrievable within the remaining tool budget), so the precise trigger conditions (e.g., whether it runs on every foreground refresh vs. only after certain user actions) are based on the function's name/design and the existing unit tests in `app/test/unit/stores/updates/update-remote-url-test.ts`, not on directly-observed caller code. A full Devin session with file access would be needed to confirm the exact automatic-refresh trigger path and the precise behavior of `urlMatchesRemote` against a crafted cross-host payload before treating this as fully confirmed.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
