### Title
Division-by-zero on deduplicated mempool cost accounting halts block building - (File: `chia/full_node/mempool.py`)

### Summary
`Mempool.create_bundle_from_mempool_items()` computes `item_cost = cost - cost_saving` for every mempool item it considers for block inclusion, then immediately divides the item's fee by that value in a logging call: `fee / item_cost` [1](#0-0) . Unlike the mempool admission path (`mempool_manager.py`), which explicitly guards against `cost == 0` before computing `fees / cost` [2](#0-1) , this block-building code path performs no such guard on `item_cost` before dividing.

### Finding Description
`item_cost` is derived from `IdenticalSpendDedup.get_deduplication_info()`, which sums up the previously recorded cost of every coin spend in the item that is `eligible_for_dedup` and already has a matching entry (`cost_saving += dedup_coin_spend.cost`) [3](#0-2) . `dedup_coin_spend.cost` and `item.conds.cost` are computed from different, but overlapping, sources: the per-spend cost is `condition_cost + execution_cost` for that one coin spend [4](#0-3) , while the item's total `cost` property returns `conds.cost` — the Rust-computed total cost for the whole `SpendBundle` [5](#0-4) .

For a spend bundle that consists of exactly one coin spend and that coin spend is `ELIGIBLE_FOR_DEDUP`, the item's total `conds.cost` and the single spend's `condition_cost + execution_cost` are the same quantity (there is nothing else in the bundle contributing cost). If a second, later mempool item spends the identical coin with an identical solution (satisfying the dedup "same coin, same solution" check at line 208 of `eligible_coin_spends.py`) and is likewise a single-spend bundle, then:

```
item_cost = cost - cost_saving = conds.cost - dedup_coin_spend.cost = 0
```

This zero is then divided into during the diagnostic log call at `mempool.py:668`:
```python
log.info(
    "Cumulative cost: %d, fee per cost: %0.4f, item cost: %d", cost_sum, fee / item_cost, item_cost
)
```
Python evaluates the arguments to `log.info(...)` eagerly regardless of the configured log level, so `fee / item_cost` raises `ZeroDivisionError` even when logging is disabled. This exception is not caught anywhere in `create_bundle_from_mempool_items` [6](#0-5) , so it propagates out of block-generator creation.

### Impact Explanation
`create_bundle_from_mempool_items` is invoked by the full node whenever it attempts to build a candidate block from the mempool. An unhandled `ZeroDivisionError` here aborts the block-building call for every caller relying on that code path, directly matching the "spend-triggered transaction-processing halt" impact class accepted for this analog: an attacker who can get two crafted, minimal, single-spend, dedup-eligible spend bundles admitted into the mempool (spending the same coin with the same solution, which is explicitly a supported/expected mempool scenario, not a rejected one) can reliably crash the node's block-template generation whenever both are present together in the pool.

### Likelihood Explanation
Reaching `ELIGIBLE_FOR_DEDUP` and constructing a single-coin-spend bundle whose entire cost is attributable to that one spend requires knowledge of the dedup eligibility rules enforced in `chia_rs` (the `ELIGIBLE_FOR_DEDUP` condition flag) and of the exact cost components of `conds.cost` vs. per-spend `condition_cost + execution_cost`. I could not fully verify from the indexed Python sources whether `conds.cost` for a trivially minimal single-spend bundle always exactly equals `condition_cost + execution_cost` with zero remainder (e.g., whether a fixed base/byte cost is included in `conds.cost` that would make `item_cost` always strictly positive). This equality is enforced in the Rust condition-parsing layer (`chia_rs`), which is outside what I can inspect here. This uncertainty affects confidence in exploitability but not the code-review finding that the divide is unguarded, unlike the parallel, explicitly-guarded division in `mempool_manager.py`.

### Recommendation
Add a zero-check before the division in `create_bundle_from_mempool_items`, mirroring the guard already used in `MempoolManager.validate_spend_bundle` and `is_fee_enough` (`if cost == 0: ...`) [7](#0-6) , or simply avoid the eager division in the log statement (e.g., compute the fee-per-cost value only when `item_cost > 0`, or use a lazy/guarded logging expression). Also audit `create_block_generator2`'s equivalent cost-accounting logic for the same pattern.

### Proof of Concept
Conceptual PoC (requires confirming `ELIGIBLE_FOR_DEDUP` semantics in `chia_rs`, which was not directly inspectable here):
1. Submit spend bundle `A`: a single coin spend of coin `C` with solution `S`, structured so the spend is recognized `ELIGIBLE_FOR_DEDUP`, and admit it to the mempool.
2. Submit a second, independent spend bundle `B` that spends a *different* coin but is aggregated/duplicated such that it also contains a single-spend entry for coin `C` with the identical solution `S` (the standard "identical spend" dedup scenario the mempool explicitly supports, e.g., two competing offer-taker bundles settling the same offer coin).
3. Trigger block generation (`Mempool.create_bundle_from_mempool_items`); when the dedup logic processes the second item, `cost_saving` equals the full `item.cost`, producing `item_cost == 0` and raising `ZeroDivisionError` at `chia/full_node/mempool.py:668`, aborting block template creation.
