## Analog Found: Unbacked Referral Reward Liabilities in `ReferralStorage`

### Title
Referral rewards accrue as unbacked liabilities with no balance check, causing permanent freezing of user rewards - (File: `rewards/ReferralStorage.sol`)

### Summary
The reported bug describes admin-facing distribution functions (`setEthDistribution`/`setReachDistribution`) crediting users with rewards that may exceed the contract's actual token balance. The same root-cause pattern — off-chain/virtual accounting of "amount owed" that is never reconciled against real token balance — exists in `ReferralStorage.sol`, but here it is reachable entirely through ordinary, unprivileged user activity (harvesting rewards via `MasterMagpie`), not through any admin action.

### Finding Description
`MasterMagpie._harvestMGP` (or the relevant harvest path) sends MGP rewards directly to the claiming user/receiver, and only afterward calls `IReferralStorage(referral).trigger(_user, totalReward)` [1](#0-0)  purely to update referral bookkeeping — no MGP tokens are forwarded to `ReferralStorage` alongside this call.

Inside `trigger()`, the contract increments `refererInfo.rewardAmount` and `refereeInfo.rewardAmount` based on a percentage of `_amount`, with no cap or check against the contract's actual MGP balance: [2](#0-1) 

Later, `claimReward()` blindly transfers the full accrued `rewardAmount` without ever verifying that `MGP.balanceOf(address(this))` covers it: [3](#0-2) 

There is no function in `ReferralStorage.sol` that deposits/tops-up MGP into the contract in proportion to the liabilities being accrued by `trigger()` — the only MGP-related logic is the constructor's token reference and the unguarded `safeTransfer` in `claimReward()`. This means every call to `trigger()` (triggered by any ordinary user harvesting rewards through `MasterMagpie` with a referral code set) increases total outstanding liabilities without any corresponding increase in the contract's real token balance — mirroring exactly the audited bug class ("total amount to be distributed... exceeds the current balance of the contract").

### Impact Explanation
Because liability accrual (`trigger()`) is decoupled from actual balance funding, and is driven purely by normal user harvest activity (not an admin action), the sum of all referrers'/referees' `rewardAmount` can — and under sustained usage inevitably will — exceed the MGP token balance actually held by `ReferralStorage`. Users whose `claimReward()` call executes after the balance is exhausted by earlier claimants will have their transaction permanently revert (`safeTransfer` fails on insufficient balance), and since `rewardAmount` is only zeroed out on a successful transfer, their earned referral rewards become permanently unclaimable — a permanent freeze of unclaimed yield for those users.

### Likelihood Explanation
This requires no privileged or malicious action: any two ordinary users who set up a referral relationship and harvest MGP rewards through `MasterMagpie` will cause `trigger()` to accrue balances on their behalf indefinitely, with no built-in mechanism ensuring the pool is solvent at accrual time. The vulnerability is exposed as soon as accumulated referral liabilities across all users exceed whatever MGP the contract happens to hold, which is a foreseeable steady-state outcome given normal, sustained protocol usage.

### Recommendation
Reserve/transfer the corresponding MGP amount into `ReferralStorage` at the time `trigger()` is called (e.g., have `MasterMagpie` forward the referral-bonus portion of `totalReward` to `ReferralStorage` alongside the `trigger()` call), or add an explicit balance check/queued-rewards accounting (similar to `BaseRewardPool._provisionReward`) so that `rewardAmount` liabilities can never exceed the contract's actual token holdings.

### Proof of Concept
1. User A registers a referral code; User B uses A's code (`registerCode`/`useCode`).
2. User B harvests MGP rewards via `MasterMagpie`, which sends MGP directly to B and calls `ReferralStorage.trigger(B, totalReward)`, incrementing `refererInfo.rewardAmount` (A) and `refereeInfo.rewardAmount` (B) — with zero MGP actually transferred into `ReferralStorage`.
3. Repeat with many referrer/referee pairs harvesting over time; `ReferralStorage`'s recorded liabilities (`rewardAmount` sums) grow without bound while its real MGP balance stays at whatever amount (if any) was manually deposited by the owner.
4. Once cumulative `rewardAmount` claims exceed the actual MGP balance, any subsequent `claimReward()` call by a user whose turn comes after the balance is drained will revert permanently at `MGP.safeTransfer(msg.sender, userInfo.rewardAmount)` [3](#0-2) , freezing that user's earned referral rewards indefinitely.
