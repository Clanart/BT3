### Title
PedPoP accepts the identity point as a participant encryption key, making DKG secret shares world-decryptable — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The JumpServer bug class is "attacker-controlled input that skips validation and is consumed as trusted material." In Serai, the analogous shape is a DKG participant's `EncryptionKeyMessage`: the `enc_key` field is deserialized with `Ciphersuite::read_G`, which validates canonicity and torsion-freedom but does **not** reject the identity point. `Curve::read_G` in `crypto/frost/src/curve/mod.rs:125-131` explicitly rejects identity, but pedpop's `C: Ciphersuite` bound only reaches the permissive `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`). An identity `enc_key` makes every ECDH shared secret for that participant equal the identity point, so the ChaCha20 keystream is derived from a publicly known value.

### Finding Description
`EncryptionKeyMessage::read` reads `enc_key` with `C::read_G(reader)` (`crypto/dkg/pedpop/src/encryption.rs:57-59`), and `Decryption::register` stores it verbatim (`encryption.rs:351-361`) with no identity or proof-of-possession check — unlike per-message keys, which carry a PoP (`pop` field, `encryption.rs:83-91`).

On the encrypt side, `Encryption::encrypt` calls `encrypt(rng, context, i, self.decryption.enc_keys[&participant], msg)` (`encryption.rs:460-467`), which computes `ecdh(&key, to) = to * key` (`encryption.rs:95-97`). If `to` is the identity point, the shared secret is always the identity regardless of the ephemeral key. `cipher` then derives the ChaCha20 key solely from `context` and the identity encoding (`encryption.rs:101-126`, static IV `"DKG IV v0.2\0"`), a value any observer can recompute. For Ristretto/Ed25519, the identity encoding (all-zero 32 bytes) decompresses successfully, passes the `torsion_free` check (`crypto/dalek-ff-group/src/lib.rs:429-437`), and is canonical, so it is accepted.

### Impact Explanation
PedPoP assumes only an *authenticated* channel between DKG participants; the `EncryptedMessage` layer is what provides confidentiality of the secret shares (`spec/cryptography/Distributed Key Generation.md` states shares rely on this ECDH+ChaCha20 encryption). A participant who registers `enc_key = identity` causes every share `f_i(l)` encrypted to them by every other participant to be decryptable by anyone who observes the ciphertext — no private key required. This is passive secret-share/key-share material recovery by an unprivileged observer reachable purely through public DKG message bytes, the direct analog of validation-bypass-to-secret-exposure. It also defeats the blame protocol's confidentiality partitioning (per-message keys exist so revealed keys don't expose other messages; here the ECDH output is constant and known).

### Likelihood Explanation
A single malicious or compromised DKG participant broadcasts one `EncryptionKeyMessage` with `enc_key` set to the 32-byte identity encoding. Deserialization, `register`, and all subsequent encryptions succeed silently. Any party able to read the (authenticated, not necessarily confidential) share messages — e.g., a relay, coordinator, or passive network observer — recovers that participant's incoming shares. Likelihood is moderate-to-high within the DKG threat model (the protocol already assumes malicious participants; the PoP exists precisely because such attacks were anticipated for per-message keys, but the registration key was not equivalently hardened).

### Recommendation
Reject the identity point in `EncryptionKeyMessage::read` / `Decryption::register` (mirror `Curve::read_G`'s `is_identity` check), and consider binding a proof of possession to `enc_key` as is done for per-message keys.

let params = ThresholdParams::new(t, n, i).unwrap();

decryption.register(attacker_i, ekm);       // stored: enc_keys[attacker_i] = identity
