### Title
Distribution precompile `rewards()` accepts attached value with no refund path, permanently stranding funds - (File: precompiles/distribution/distribution.go)

### Summary
`PrecompileExecutor.rewards()` is dispatched from `Execute` without calling `pcommon.ValidateNonPayable(value)`, unlike every other query/view method in the same switch statement and unlike write methods that instead call `pcommon.HandlePaymentUsei` to refund the payer. Since the EVM has already credited the attached `value` (usei/wei) to the precompile's account balance before `Execute` runs, and `rewards()` never invokes `HandlePaymentUsei` or any other refund logic, any `usei`/`wei` sent alongside a `rewards()` call is permanently locked in the distribution precompile's Sei-side account.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute` dispatches methods based on `method.Name` [1](#0-0) . Non-payable state-changing methods explicitly call `pcommon.ValidateNonPayable(value)` to reject any attached value (e.g. `WithdrawValidatorCommissionMethod`) [2](#0-1) , and other view/query methods pass `value` through to helpers such as `params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, and `communityPool`, all of which are expected to validate non-payability via a shared input-validation helper [3](#0-2) . `RewardsMethod` is dispatched as `return p.rewards(ctx, method, args)` — `value` is not passed at all [4](#0-3) , and the `rewards` implementation itself never checks or handles `value` [5](#0-4) . This same pattern (missing guard on `rewards`) is present across every historical version of the precompile (`v562`, `v580`, `v605`, `v606`, `v610`, `v614`, `v620`, `v630`, `v640`, `v65`, `v66`, `v67`) [6](#0-5) .

The maintainers' own integration test explicitly documents this as a known quirk rather than a fix: "Guard quirk worth knowing: rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds), so this spec deliberately has no 'view rejects value' test." [7](#0-6) 

This is directly analogous to the reported `ZkSafeModule.sendZkSafeTransaction` bug: a function that is reachable with attached native value but has no code path to return or use that value, so it becomes permanently locked in the receiving contract/module's balance. Here the "module" is the distribution precompile's Sei account (`sdk.AccAddress` derived from the precompile's EVM address), and the missing counterpart to `execTransactionFromModule` is the missing `pcommon.HandlePaymentUsei` refund call that every payable write path (e.g. `delegate` in the staking precompile) uses to explicitly send the value back to the payer [8](#0-7) .

### Impact Explanation
Any EOA or contract calling `rewards(address)` on the distribution precompile (address `0x...1007`) with non-zero `msg.value` will have that value debited from the caller and credited to the precompile's account by the EVM's native value-transfer semantics, with no code path ever crediting it back. This is a direct, permanent, unrecoverable loss of `usei`/`wei` funds for any caller who mistakenly (or is tricked by a malicious front-end/contract into) attaching value to this call. Because `rewards` is a commonly-invoked read method (e.g. by wallets/dApps checking delegator rewards), the practical exposure is broad — any misconfigured integration that always attaches value defensively, or a malicious dApp designed to siphon value into this call, causes fund loss with no recovery mechanism.

### Likelihood Explanation
Likelihood is moderate: normal read-only tooling (e.g. ethers.js `staticCall`/view calls) does not attach value by default, so accidental triggering requires an explicit non-zero `value` on a non-static call to `rewards`, which is unusual but not prevented by any validation, and is trivially reachable by any single transaction from an unprivileged sender or by a malicious contract that funnels a user's funds into this call under the guise of "checking rewards."

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check to the `RewardsMethod` case in `Execute` (in `precompiles/distribution/distribution.go` and, for consistency, all legacy precompile versions still reachable in the currently deployed contract ABI), matching the pattern already used for `WithdrawValidatorCommissionMethod` and other non-payable paths, so that any transaction sending non-zero value to `rewards()` reverts instead of stranding funds.

### Proof of Concept
1. Call the distribution precompile at its fixed EVM address (`0x...1007`) with `data = abi.encodeWithSelector(rewards.selector, delegatorAddress)` and `value = 1 sei-wei` (or any non-zero amount) via a normal `eth_sendTransaction` (not a `staticcall`).
2. The EVM CALL semantics debit `value` from the caller and credit it to the precompile's account before `RunAndCalculateGas`/`Execute` is invoked.
3. `Execute` dispatches to `p.rewards(ctx, method, args)` without validating or handling `value` [4](#0-3) ; the call succeeds and returns the rewards data, with no refund performed.
4. The sent value remains in the precompile's Sei account balance permanently, since no other code path (nor any user-facing withdrawal function) can move funds out of the distribution precompile module account back to the original caller.
