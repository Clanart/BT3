## Finding

### Title
Order-Based Hunk Splicing With No Count Validation in `reassembleResolvedFile()` Enables Silent Corruption of Committed Merge Content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile()` splices each per-hunk model resolution into the original conflicted file purely by array *position* (`hunkIndex`), never verifying that the number of resolutions returned by the Copilot model equals the number of conflict blocks actually present in the file. This is the same broken-invariant class as the `getHigherLevelParents()` report: a positional/counted correspondence between two independently derived sequences (there, "hops found" vs. "expected parent levels"; here, "hunks returned by an LLM" vs. "hunks extracted from the file") that attacker-controlled structure can desynchronize, silently routing content to the wrong place instead of failing safe.

### Finding Description
`extractConflictHunks()` parses the working-directory file and produces the *ground-truth* ordered list of conflict blocks used to build the prompt (`app/src/lib/copilot-conflict-context.ts`, `buildConflictContext`). The Copilot model is then asked to return `hunks: [...]`, "one entry per conflict in the file, matching the ... order from the input" [1](#0-0) .

`reassembleResolvedFile()` walks the original file's marker blocks in order and consumes `hunkResolutions[hunkIndex]` for each one, incrementing `hunkIndex` regardless of whether a corresponding resolution exists: [2](#0-1) 

There is no check anywhere in `reassembleResolutions()` or `reassembleResolvedFile()` that `raw.hunks.length` equals the number of marker blocks found in `ctx.rawContent` [3](#0-2) . If the model's returned hunk array is short (e.g. truncated output, a malformed/dropped entry, or the model miscounting deeply nested/adjacent conflict blocks — all plausible with attacker-crafted merge content designed to have many small or visually ambiguous conflicts), every conflict block from that point onward is spliced with the *wrong* resolved content (or silently left empty), because matching is positional, not identity-based.

The resulting `resolvedContent` is written directly to disk and `git add`ed without further diffing/verification against the original conflict semantics: [4](#0-3) 

The only existing guards — `resolveWithin()` (path safety) and `getHunkSkipReason()`/`MAX_CONFLICT_FILE_READ_SIZE` (size bounds) — protect against path traversal and oversized payloads, not against a hunk-count mismatch between the extracted conflict list and the model's response. None of them detect or reject a shorter-than-expected `hunks` array.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits issue: the working tree file is overwritten with content that mixes unrelated conflict resolutions across blocks, and it is then staged (`git add`) as part of a merge/rebase/cherry-pick without the user being shown that the per-hunk correspondence broke. Because the file has no remaining conflict markers, `hasUnresolvedConflicts` will treat it as resolved, and the corrupted file is what gets committed and pushed — matching the "silent corruption of what the user commits or pushes" impact category. The attacker precondition is realistic and unprivileged: anyone contributing/merging a branch or PR that produces a set of conflicts structured (e.g., many adjacent or nested conflict markers in one file) to induce miscounted model output can trigger this; no local access, admin rights, or leaked credentials are required.

### Likelihood Explanation
Likelihood is bounded by relying on non-deterministic LLM output miscounting hunks, so it is not a deterministic 100%-reproducible bug the way the Solidity hop-limit issue is, but the code path has zero defensive validation for this specific mismatch, unlike the size/path guards that exist for other classes of bad output. Any parsing bug, truncation, or model confusion on a crafted multi-hunk file reaches the write path unguarded.

### Recommendation
In `reassembleResolutions()` / `reassembleResolvedFile()`, validate that the number of resolved hunks equals the number of conflict blocks detected in the original file before splicing; on mismatch, treat the file as unresolved (fall back to the skip/manual-resolution path used elsewhere) rather than silently misassigning content.

### Proof of Concept
1. Create a merge conflict in a single file containing several small, adjacent, or nested-looking `<<<<<<< / ======= / >>>>>>>` blocks (attacker crafts the branch/PR to maximize ambiguity, e.g. blocks separated by a single blank line, or with conflict markers appearing inside string/comment content elsewhere in the file to confuse a token-limited or careless parse).
2. User runs "Resolve with Copilot"; `buildConflictContext` extracts N hunks via `extractConflictHunks` [5](#0-4) .
3. The model returns fewer than N `hunks` entries (truncation/miscount) in `IRawFileResolution.hunks`.
4. `reassembleResolvedFile()` splices resolutions positionally: blocks after the shortfall receive the wrong resolved content or nothing, without any error [6](#0-5) .
5. `_applyCopilotConflictResolutions` writes this corrupted content to disk and `git add`s it [7](#0-6) , and the user commits/pushes the corrupted merge unaware anything went wrong.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
