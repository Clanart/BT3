### Title
Optional `aggregator_verification_address` Combined with Unauthenticated Aggregator Endpoint Allows Anyone to Force Operator Payout — (`core/src/rpc/operator.rs`, `core/src/rpc/aggregator.rs`, `core/src/servers.rs`)

---

### Summary

The operator's `Withdraw` RPC is intended to be called only by the aggregator after it has verified a withdrawal request. The sole caller-identity check beyond mTLS is the ECDSA `aggregator_verification_address` guard. That guard is entirely optional (`Option<Address>`) and is never enforced by `check_mainnet_requirements`. When it is absent (the default), the operator performs no caller-identity check at all. Because the aggregator server enforces no client certificates by design, any unauthenticated party can call `Aggregator::Withdraw`, which the aggregator forwards to the operator under its own mTLS certificate, satisfying the operator's `OnlyAggregatorAndSelf` interceptor. The result is that any external actor can force the operator to broadcast a payout transaction for any valid Citrea withdrawal at any time of their choosing.

---

### Finding Description

**Layer 1 — Aggregator has no client-certificate enforcement.**

`create_aggregator_grpc_server` calls `create_grpc_server` with the shared config. Inside `create_grpc_server`, the interceptor is set to `Noop` and the TLS config omits `client_ca_root` whenever `config.client_verification` is `false`:

```rust
// core/src/servers.rs
let tls_config = if config.client_verification {
    ServerTlsConfig::new()
        .identity(server_identity)
        .client_ca_root(client_ca)   // mTLS
} else {
    ServerTlsConfig::new().identity(server_identity)  // server-only TLS
};

let service = InterceptedService::new(
    service,
    if config.client_verification {
        OnlyAggregatorAndSelf { ... }
    } else {
        Noop   // ← no cert check on aggregator
    },
);
```

The documentation explicitly states: *"The aggregator does not enforce client certificates but does use TLS for encryption."* `client_verification` is not required to be `true` for the aggregator by `check_mainnet_requirements`. [1](#0-0) [2](#0-1) 

**Layer 2 — Aggregator's `withdraw` passes the caller-supplied payload straight through to operators.**

The aggregator's `withdraw` handler does not add any signature of its own. It clones `withdraw_params_with_sig` (which includes the caller-supplied, optional `verification_signature`) and sends it verbatim to each operator:

```rust
// core/src/rpc/aggregator.rs
let params = withdraw_params_with_sig.clone();
let mut request = Request::new(params);
request.set_timeout(WITHDRAWAL_TIMEOUT);
async move { (operator.withdraw(request).await, operator_xonly_pk) }
``` [3](#0-2) 

**Layer 3 — Operator's `Withdraw` skips the only caller-identity check when `aggregator_verification_address` is `None`.**

```rust
// core/src/rpc/operator.rs
// if verification address is set in config, check if verification signature is valid
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    // ... ECDSA check ...
}
// ← if None, execution falls through with no identity check
```

`aggregator_verification_address` is typed `Option<alloy::primitives::Address>` and is never required by `check_mainnet_requirements`. When absent, the entire ECDSA block is skipped and `operator.withdraw(...)` is called unconditionally. [4](#0-3) [5](#0-4) 

**Layer 4 — The operator's mTLS interceptor is satisfied by the aggregator's own certificate.**

The `OnlyAggregatorAndSelf` interceptor on the operator accepts any request whose leaf certificate equals `aggregator_cert` or `our_cert`. Because the aggregator is the one making the downstream call, it presents its own certificate, which passes the check. The attacker never needs to possess any certificate. [6](#0-5) 

---

### Impact Explanation

An unauthenticated external attacker can force the operator to broadcast a payout transaction for any withdrawal that is validly registered in Citrea. The operator fronts BTC for every payout and must wait for reimbursement through the kickoff/reimburse cycle. Consequences:

- **Liquidity exhaustion**: By replaying many valid withdrawal IDs in rapid succession, an attacker can drain the operator's available BTC balance, preventing it from servicing legitimate withdrawals and breaking bridge liveness.
- **Fee-rate griefing**: The attacker chooses the moment of broadcast; forcing payouts during high-fee periods increases the operator's costs and reduces reimbursement profitability.
- **Loss of payout-timing control**: The operator can no longer batch or sequence payouts optimally.

The operator's own validation (Citrea UTXO check, Schnorr signature verification, profitability check) prevents funds from being redirected to the attacker, so direct theft is not possible. The impact is unauthorized state transition in the payout flow with material fund-locking and liveness impact. [7](#0-6) [8](#0-7) 

---

### Likelihood Explanation

- The aggregator endpoint is reachable over the network with only a standard TLS connection (no client certificate required).
- `aggregator_verification_address` is `Option<Address>` with no enforcement in `check_mainnet_requirements`, so operators can and do run without it.
- The attack requires only knowledge of valid Citrea withdrawal IDs (publicly observable on-chain) and the corresponding withdrawal UTXO outpoints.
- No privileged key material is needed. [9](#0-8) 

---

### Recommendation

1. **Enforce `aggregator_verification_address` on mainnet.** Add a check in `check_mainnet_requirements` for `cli::Actor::Operator` that rejects startup when `aggregator_verification_address` is `None`.

2. **Have the aggregator sign the withdrawal params itself** before forwarding to operators, rather than passing through a caller-supplied signature. The aggregator holds its own key material and should attest that it has validated the request.

3. **Optionally, enforce client certificates on the aggregator** for the `Withdraw` and `OptimisticPayout` RPCs, restricting callers to a known backend service certificate.

### Proof of Concept

```
# Preconditions:
#   - Aggregator is reachable at agg.example.com:17000
#   - aggregator_verification_address is not set in operator config
#   - withdrawal_id=42 is a valid, unprocessed Citrea withdrawal

# Step 1: Connect to aggregator (server-only TLS, no client cert needed)
# Step 2: Call Aggregator::Withdraw with the valid withdrawal params

grpcurl -insecure \
  -d '{
    "withdrawal": {
      "withdrawal": {
        "withdrawal_id": 42,
        "input_signature": "<valid_taproot_sig_hex>",
        "input_outpoint": { "txid": { "txid": "<txid_bytes>" }, "vout": 0 },
        "output_script_pubkey": "<user_script_pubkey>",
        "output_amount": 99900000
      }
      // verification_signature omitted — field is optional
    }
  }' \
  agg.example.com:17000 clementine.ClementineAggregator/Withdraw

# Result: Aggregator forwards to operator using its own mTLS cert.
# Operator skips the aggregator_verification_address check (None).
# Operator validates the Citrea UTXO and Schnorr sig, then broadcasts the payout tx.
# Operator's BTC liquidity is consumed; attacker repeats for all pending withdrawals.
```

The attacker supplies no `verification_signature` (the field is `optional string` in the proto). The operator's guard at `core/src/rpc/operator.rs:210` is only entered when `aggregator_verification_address` is `Some`, so the missing signature causes no error. [10](#0-9) [4](#0-3) [11](#0-10)
