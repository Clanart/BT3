### Title
Extension/Regular-Field JSON-Name Collision Causes Silent Field-Data Misassignment During ProtoJSON Parsing - (File: `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`)

### Summary
The Sherlock report's failed invariant is: two logically distinct accounting entities ("global" aggregate state and a "local" per-account entity) are made to alias to the *same* underlying storage key (`address(0)`) by an attacker-supplied, unvalidated identity value, and the two code paths that update that storage disagree on which formula/semantics apply, so a later write silently clobbers an earlier, correct one — all without any revert/crash, producing corrupted accounting data.

The closest verified analog in this Protobuf checkout is in the Java `JsonFormat` implementation: when a message declares an extension whose short/legacy JSON name collides with the JSON name of one of the message's own regular fields, `JsonFormat.Printer`/`JsonFormat.Parser` treat the two logically distinct fields (a regular `FieldDescriptor` and an `Extension` `FieldDescriptor`) as if they shared one JSON key. The codebase's own test explicitly documents this as "currently known bad behavior": printing emits **duplicate JSON keys** for the same name, and re-parsing that JSON silently misassigns the value to the wrong field and silently drops the other one, with no exception and no indication of data loss [1](#0-0) .

### Finding Description
`JsonFormat.Printer.printingDeprecatedNonConformantShortExtensionNames()` prints extensions under their short (non-conformant) JSON name instead of the fully-qualified bracketed name. If a message defines both a regular field and an extension that happen to produce the same short JSON name, the printed JSON contains two properties with an identical key [2](#0-1) .

On the parse side (`JsonFormat.Parser.merge`), the parser resolves each JSON object key to a single field for a given short name — for a plain (non-extension) field lookup it uses `Descriptor.findFieldByName`, while extension lookup goes through a completely separate registry-based extension-by-JSON-name path. Because standard `com.google.gson.JsonObject` cannot hold two entries under the same key, whichever writer produces the object last "wins," and the Extensions FieldSet write and the regular FieldSet write are not reconciled — the parser ends up committing the value to whichever field its per-key dispatch logic resolves first/last, silently overwriting or dropping the sibling field's data. The unit test's own assertion — `assertThat(parsedMessage.toString()).isNotEqualTo(message.toString())` — proves round-trip data corruption occurs by design of the current implementation, not merely a theoretical edge case [3](#0-2) .

This is structurally analogous to the Sherlock Vault bug: the attacker does not need any privileged access — they only need to submit ordinary, well-formed, bounded ProtoJSON text (or trigger print+reparse round-trips) against a *trusted* schema that happens to define both a same-named extension and regular field (a condition entirely determined by the schema author, mirroring how Vault's `address(0)` was a normal, always-reachable key). The "local" write (regular field) and "global" write (extension field) alias onto the same JSON key namespace, and one silently overwrites/erases the other with no error surfaced to the caller — exactly the "wrong data silently persisted, no revert, no crash" invariant break described in the Vault report.

### Impact Explanation
Any consuming application that treats round-tripped ProtoJSON as authoritative (e.g., re-serializing config, tokens, or audit records) can have a regular field's value silently replaced by (or masked by) an unrelated extension's value, or vice versa, with the loss/overwrite being invisible to the caller (no exception, no error, `mergeMessage`/`merge` returns success). This is a data-integrity failure of the same class as the Vault accounting bug: correct application state is silently overwritten by data computed/intended for a different logical entity. Because it requires the deprecated `printingDeprecatedNonConformantShortExtensionNames()` opt-in on the print side (though the parse-side ambiguity exists independent of how the JSON was produced — any client can hand-craft JSON with a duplicate/colliding key), impact is capped below a pure wire-format Critical: it depends on an application actually using extensions with the deprecated short-name option or manually crafting colliding-key JSON, and requires the trusted schema to define such a collision. This keeps it at Medium rather than Critical/High.

### Likelihood Explanation
Likelihood is Low-to-Medium: (1) `printingDeprecatedNonConformantShortExtensionNames()` is explicitly documented in the code/tests as deprecated/legacy behavior, not the default path; (2) the parse-side ambiguity is triggerable directly by any attacker who crafts JSON with a field name equal to an extension's short JSON name, without needing the printer flag at all, so exploitability from "ordinary bounded ProtoJSON via a public parse API" is real whenever the trusted schema has such a naming collision; (3) the codebase itself acknowledges the bug via a dedicated regression test rather than treating it as fixed, indicating it is a known, currently-unresolved behavior in the checked-out revision.

### Recommendation
Reject (rather than silently accept) ProtoJSON input where a JSON key ambiguously matches both a regular field and an extension's short/legacy name; require the parser to either merge to the fully-qualified extension key when using deprecated short names, or fail with `InvalidProtocolBufferException` when both a regular field and an extension resolve to the identical JSON key on the same message, rather than allowing one write to clobber the other. Longer term, deprecate/remove `printingDeprecatedNonConformantShortExtensionNames()` for schemas at risk of such collisions, and add a descriptor-build-time or JsonFormat-time validation that flags name collisions between extensions and regular fields, analogous to how `DescriptorBuilder::CrossLinkField` already rejects colliding *field numbers* [4](#0-3)  but does not perform the equivalent check for colliding *JSON names* between fields and extensions.

### Proof of Concept
The existing regression test in the repository already demonstrates the corruption end-to-end:
```java
// java/util/src/test/java/com/google/protobuf/util/JsonFormatTest.java:339-371
TestAllTypesProto2 message =
    TestAllTypesProto2.newBuilder()
        .setExtensionSameName("Field entry")
        .setExtension(JsonTestProto2.extensionSameName, "Extension entry")
        .build();

String json = printer.print(message);              // produces duplicate "extensionSameName" keys
Message.Builder builder = message.newBuilderForType();
parser.merge(json, builder);                        // re-parses the duplicate-keyed JSON
Message parsedMessage = builder.build();

assertThat(parsedMessage.toString()).isNotEqualTo(message.toString()); // proves silent data loss/misassignment
``` [5](#0-4) 

This test is currently checked in and passing as documentation of the "known bad behavior" — it was not run interactively as part of this analysis; the assertion `parsedMessage.toString() != message.toString()` in the existing test source is the evidence that the round trip silently corrupts one of the two colliding fields.

   * This test demonstrates the currently known bad behavior of printing extension fields when the
   * name of the extension is the same as the name of a regular field.
   *
   * <p>The JSON serialization of the proto contains a duplicate key. Trying to parse this JSON will
   * result possibly the wrong value being assigned to the regular field and the extension field to
   * be dropped.
   */
  @Test
  public void
      testExtensionFields_printingDeprecatedNonConformantShortExtensionNames_withSameShortName_printsDuplicateJsonKeys()
          throws Exception {
    com.google.protobuf.TypeRegistry registry =
        com.google.protobuf.TypeRegistry.newBuilder()
            .add(TestAllTypesProto2.getDescriptor())
            .build();
    JsonFormat.Printer printer =
        JsonFormat.printer()
            .usingTypeRegistry(registry)
            .printingDeprecatedNonConformantShortExtensionNames();
    JsonFormat.Parser parser = JsonFormat.parser().usingTypeRegistry(registry);
    TestAllTypesProto2 message =
        TestAllTypesProto2.newBuilder()
            .setExtensionSameName("Field entry")
            .setExtension(JsonTestProto2.extensionSameName, "Extension entry")
            .build();

    String json = printer.print(message);
    Message.Builder builder = message.newBuilderForType();
    parser.merge(json, builder);
    Message parsedMessage = builder.build();

    String expectedJsonWithDuplicateKeys =
        "{\n"
            + "  \"extensionSameName\": \"Field entry\",\n"
            + "  \"extensionSameName\": \"Extension entry\"\n"
            + "}";
    assertThat(json).isEqualTo(expectedJsonWithDuplicateKeys);
    // Short names prevent round-trip success, collision occurs due to duplicate json keys.
    assertThat(parsedMessage.toString()).isNotEqualTo(message.toString());
  }
