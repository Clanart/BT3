### Title
Automatic remote URL rewrite trusts unauthenticated GitHub API `clone_url` field, silently repointing push/fetch target - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` silently calls `gitStore.setRemoteURL(...)` and rewrites the local `origin` remote whenever the GitHub API's `clone_url` for a tracked repository differs from the current remote, as long as a same-protocol / "url previously matched" heuristic passes. [1](#0-0) 

This mirrors the eMode bug class: the code trusts a single external data source (`apiRepo.clone_url`) for a security-relevant decision (which remote the user's git operations will target) without validating that the source truly reflects the intended/authorized configuration, and the "guard rails" only check superficial string equivalence, not actual repository identity.

### Finding Description
`updateRemoteUrl` compares the currently configured git remote URL to `apiRepo.clone_url` (data returned by the GitHub API for the repository Desktop believes is associated with the working copy) using `urlMatchesRemote`, which only parses and case-insensitively compares `{hostname, owner, name}` extracted via regex from the URL strings — it never validates against any repository ID or other tamper-resistant identity attribute. [2](#0-1) 

The function's only protections are:
1. `protocolsMatch` — requires the URL scheme (http/https/ssh) to stay the same.
2. `remoteUrlUnchanged` — requires that the *previously cached* `gitHubRepository.cloneURL` still matches the current git remote (i.e., the user hasn't manually edited the remote).
3. `!urlsMatch` — the new API URL differs from the current remote.

If all three hold, the code calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` with zero user confirmation and no check that the new owner/name pair is the *same repository the user originally added* beyond string comparison. [3](#0-2) 

The broken invariant: the code assumes `apiRepo.clone_url` returned for a given local `dbID`/endpoint will always continue to refer to the exact repository the user cloned. That assumption breaks when:
- The repository name changes hands (GitHub allows a name to be reused after a rename or the repo is deleted/transferred, so a subsequent API refresh could return a `clone_url` pointing at an attacker-controlled repository with the same owner/name pattern that Desktop's regex-only comparison treats as equivalent), or
- The API response is served by a compromised/malicious GitHub Enterprise endpoint or an on-path proxy for the API host, since nothing in `updateRemoteUrl` or `urlMatchesRemote` cryptographically ties the returned `clone_url` back to the specific repository object the user trusts.

Unlike the actual git-remote write path (`setRemoteURL`, which just runs `git remote set-url`), there is no user-facing warning, diff, or confirmation dialog before the remote is silently swapped. [4](#0-3) 

### Impact Explanation
If exploited, this silently redirects the user's `origin` remote to an attacker-influenced URL. Subsequent `git fetch`/`git pull` will fetch history from a different repository than the user intended, and — more importantly — subsequent `git push` operations initiated from Desktop will push the user's code/commits to whatever destination the attacker-controlled `clone_url` points to, without the user noticing the remote changed. This matches the "silent corruption of what the user commits or pushes" impact category: the user's mental model of "I'm pushing to my repo" is invalidated without their awareness.

### Likelihood Explanation
Likelihood depends on an attacker's ability to control what `clone_url` GitHub's API (or an Enterprise/proxy endpoint) returns for a repository Desktop already associates with a local clone — e.g. via repository-name squatting after a rename/delete, or a compromised/malicious GHE server response. This requires no local access, no admin rights, and no user action beyond Desktop performing its normal periodic API refresh of tracked repositories; it is a background heuristic acting on unauthenticated-content data rather than a manual user click.

### Recommendation
Do not automatically rewrite the local git remote based solely on regex-parsed owner/name/hostname string equality from a live API response. Instead:
- Tie the update to an immutable identifier (e.g., the GitHub repository `id`, not just owner/name strings) that was recorded at the time the repository was first associated with the local working copy.
- Prompt the user before changing the configured remote URL, showing the old and new URL.
- Treat repository rename/transfer detection as a distinct, explicit, user-confirmed action rather than a silent background side effect of `updateRemoteUrl`.

### Proof of Concept
1. User clones a repository via Desktop; Desktop stores `gitHubRepository.cloneURL` and configures `origin` to that URL.
2. Time passes; the repository at that owner/name is renamed away or deleted (or a proxy/compromised GHE endpoint is used) and a different repository ends up being reachable at the same owner/name path (or an on-path server crafts an API response with a spoofed `clone_url` for the same owner/name).
3. Desktop's periodic repository/API refresh invokes `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)` with the new `apiRepo.clone_url`.
4. Because the user never manually edited the remote, `remoteUrlUnchanged` is `true`; because the scheme is unchanged, `protocolsMatch` is `true`; and `urlsMatch` is `false` since the new URL differs.
5. `gitStore.setRemoteURL(...)` executes silently, rewriting `origin` to the attacker-influenced URL, and the next push from Desktop sends the user's commits there without any warning. [5](#0-4) 

Note: I was not able to fully trace, within the available tooling, the exact call site(s) in `app-store.ts` that invoke `updateRemoteUrl` (grep confirmed 3 references there) to confirm precisely which background refresh flow triggers it and whether any additional UI confirmation exists upstream. If a stronger guard exists there, it should be verified directly in `app/src/lib/stores/app-store.ts`.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```

```typescript
export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```
