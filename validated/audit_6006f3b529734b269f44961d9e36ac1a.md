### Title
Cached FROST nonce seed is reused across distinct `set_keys_message` signatures under the same DKG attempt, enabling validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The gzip bug class is "shared global state reused across different inputs within a single invocation without reinitialization". The Serai analog is `CachedPreprocesses`: a per-context FROST nonce seed stored in the DB, loaded by `preprocess_internal` (signing_protocol.rs:123-147) every time `preprocess()`, `share()`, or `complete()` runs for context `(b"DkgConfirmer", attempt)`. The seed deterministically derives the signing nonces (`seeded_preprocess`, crypto/frost/src/sign.rs:121-144) and is never deleted or rotated after a share is produced. Safety therefore rests entirely on every `share_internal` call under one context signing byte-identical `msg` and participant sets. That invariant is not enforced: `generated_key_pair` (coordinator/src/tributary/handle.rs:47-60) unconditionally overwrites `DkgKeyPair` and calls `share()` with whatever `key_pair` it is handed, and the signed message is `set_keys_message(set, removed, key_pair)` (signing_protocol.rs:296-301). Two invocations with distinct `key_pair` values under the same `attempt` produce two FROST signature shares over the same nonce with different challenges — classic nonce reuse, which the code comments themselves flag as "explicitly unsafe" (signing_protocol.rs:25) and whose acknowledged mitigation ("check the commitments generated from the decided nonces are in fact its commitments on-chain") is still a TODO (signing_protocol.rs:51).

### Finding Description
`preprocess_internal` creates the `CachedPreprocess` once per `context` and re-derives identical `nonces`/`commitments` on every subsequent call (signing_protocol.rs:137-147 → `AlgorithmSignMachine::from_cache` → `seeded_preprocess`). `share` and `complete` both funnel through `share_internal`, which signs `set_keys_message(...)` built from the caller-supplied `key_pair` and the `removed` set computed at call time (`removed_as_of_dkg_attempt`). Nothing in `handle.rs` or `signing_protocol.rs` binds the cached seed to the specific `key_pair`/`removed`/preprocess-set it first signed with, and `DkgKeyPair::set` (handle.rs:54) overwrites without comparing. A second call with different `key_pair` bytes yields a share `s' = d + e'·(ρ·share)` under the same nonce `d` — the exact stale-state-across-inputs pattern of the CVE.

### Impact Explanation
Two shares over one nonce with distinct challenges allow recovery of the coordinator's MuSig secret share — its validator private key — compromising the root-of-trust key used for `publish_set_keys`. Per the crate's own docs, "Reusing preprocesses would enable a third-party to recover your private key share" (spec/cryptography/FROST.md:51-55). This is key share recovery, a Critical-class outcome.

### Likelihood Explanation
Exploitation requires `share`/`complete` (or two `generated_key_pair` calls) to execute under one `attempt` with differing `msg` or participant sets. Within a single honest run inputs are deterministic, so divergence requires either (a) the processor emitting a distinct `key_pair` for the same attempt — possible because `generated_key_pair` has no idempotence guard and `DkgKeyPair::set` silently overwrites — or (b) a `removed`-set change / partial rebuild between the share and complete paths, which the file admits is only partially bounded ("This does set a bound preventing partial rebuilds which is accepted", signing_protocol.rs:47-48). Reachable but conditional; Medium likelihood.

### Recommendation
Bind the cached seed to the signed payload: store a hash of `(key_pair, removed, preprocess-set)` alongside `CachedPreprocesses` and refuse to sign if it differs; delete or rotate the entry after the first `share()`; and implement the noted TODO to verify our on-chain published preprocess matches the cached commitments before emitting a share.

Note: I could not fully verify whether coordinator main-loop code permits a second `generated_key_pair` invocation for the same attempt with a different `key_pair` (the caller in `main.rs` was not inspected). If the processor protocol guarantees a single `GeneratedKeyPair` per attempt, the residual risk reduces to the `share`/`complete` double-execution and partial-rebuild paths, which the code partially acknowledges but does not fully guard.
