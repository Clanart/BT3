### Title
`SignableTransaction::new` excludes the OP_RETURN `data` output from weight/vbytes, so `needed_fee` and the standardness checks are computed on a smaller transaction than the one actually signed — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Like the Arcadia finding where `previewMint`/`totalAssets` report a value that doesn't reflect what will actually happen, `SignableTransaction::new` builds the real output list (`tx_outs`, which includes the caller-supplied OP_RETURN output) but computes weight, vbytes, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check using only `payments` and `change`. The fee/weight "preview" therefore describes a transaction smaller than the one that gets signed.

### Finding Description
`SignableTransaction::new` pushes an OP_RETURN output carrying up to 80 bytes of caller-controlled `data` onto `tx_outs` at networks/bitcoin/src/wallet/send.rs:194-202. However, both fee-estimation calls pass `payments` — not `tx_outs` — into `calculate_weight_vbytes`:

- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` (send.rs:204)
- `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:226)

`calculate_weight_vbytes` builds its template transaction's `output` field solely from the `payments` argument plus an optional change output (send.rs:85-99), so the OP_RETURN output (~10 + up to 80 ≈ up to ~90 vbytes) is never counted. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) underestimates the fee required to hit the requested rate.
2. The `TooLowFee` minimum-relay check (send.rs:211) compares against the deflated `vbytes`, so a transaction that is actually below the relay minimum for its true size can pass.
3. The `weight > MAX_STANDARD_TX_WEIGHT` check (send.rs:241) uses the under-measured `weight`, so a transaction that is actually non-standard (over 400,000 WU) is accepted and signed.
4. Change is computed as `input_sat - payment_sat - fee_with_change` (send.rs:228-230) with the underestimated fee, so the change output absorbs the difference and the *actual* paid fee equals the underestimated `needed_fee` — the realized fee rate is strictly lower than the `fee_per_vbyte` the caller specified.

### Impact Explanation
`needed_fee()` is documented as "the fee necessary for this transaction to achieve the fee rate specified at construction" (send.rs:129-135), but the transaction that gets signed via `TransactionSignMachine::sign`/`complete` (send.rs:355-428) commits to `tx_outs` including the uncounted OP_RETURN output. Any consumer relying on `needed_fee` — e.g., a caller checking it against a minimum relay/mempool-acceptance fee rate, or an integrator presenting an estimated fee — is given false information, and the signed transaction will propagate at a lower effective fee rate than requested (potentially below `DEFAULT_MIN_RELAY_TX_FEE`, making it unrelayed) or exceed the standardness weight limit while passing the internal check. Up to ~90 vbytes of underpayment at the chosen fee rate is the direct consequence, mirroring the report's "preview functions return false info" impact.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is `Some`. `data` is a public, caller-supplied argument to `SignableTransaction::new`, so any integrator embedding arbitrary data (a supported, documented feature: "If data is specified, an OP_RETURN output will be added with it", send.rs:149) hits it. The Serai processor's own path passes `data: None` (processor/src/networks/bitcoin.rs:446-452), so the internal usage is unaffected — but the wallet library API itself produces the mis-estimate for any external caller, and the error grows with the size of `data` up to the 80-byte cap.

### Recommendation
Pass the actual outputs to the estimator. Either compute weight/vbytes over `tx_outs` (rebuilt once the change candidate is known), or extend `calculate_weight_vbytes` to take an additional `data: Option<&ScriptBuf>`/extra-output parameter so the OP_RETURN output is included in both the no-change and with-change estimates. Alternatively, add the fixed overhead of the OP_RETURN output (script length encoding plus the pushed data length) to the measured `vbytes` before computing `needed_fee`.

### Proof of Concept
```rust
// In networks/bitcoin: build a SignableTransaction with `data` and compare
// the reported needed_fee to the fee implied by the real transaction weight.

let data = vec![0xaa; 80]; // max allowed OP_RETURN payload
let tx = SignableTransaction::new(
    vec![input],                       // any ReceivedOutput with sufficient value
    &[(payment_script, payment_amt)],
    Some(change_script),
    Some(data.clone()),
    fee_per_vbyte,
).unwrap();

// The actual transaction includes the OP_RETURN output
let real_vbytes = tx.transaction().vsize() as u64; // includes ~90 extra bytes
// needed_fee was computed from a template WITHOUT the OP_RETURN output
assert!(tx.needed_fee() < fee_per_vbyte * real_vbytes);
// => the signed TX pays needed_fee yet is real_vbytes large,
//    so its effective fee rate < fee_per_vbyte (and can dip below
//    DEFAULT_MIN_RELAY_TX_FEE even though the TooLowFee check passed).
```
The discrepancy is visible directly in the source: `tx_outs` (send.rs:188-202) gains the OP_RETURN output, while both `calculate_weight_vbytes` invocations (send.rs:204, 226) are fed `payments`, which never contains it.
