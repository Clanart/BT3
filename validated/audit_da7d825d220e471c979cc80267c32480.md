### Title
Escrow withdrawal accounting is decremented even when the underlying token transfer silently fails, causing permanent loss of escrowed/dust funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports and uses `SafeERC20` (`using SafeERC20 for IERC20;`) for every escrow inflow (`safeTransferFrom` at lines 399, 453, 478), but on the outflow paths — `withdraw()` and the `SweepDust` handler in `onPostRequest` — it reverts to a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only inspects the low-level `success` boolean, never the ERC20 return data. [1](#0-0) [2](#0-1) 

### Finding Description
`withdraw()` decrements the escrow ledger `_orders[body.commitment][token] -= amount` unconditionally, and only guards against reverts via the low-level `success` flag from `.call`: [3](#0-2) 
For any ERC20 token that signals failure by returning `false` (a boolean, no revert) instead of reverting — a legitimate, still-in-use ERC20 pattern, exactly the class of behavior `SafeERC20` exists to guard against — the raw `.call` still returns `success = true` (the call executed without reverting), so `TransferFailed` never fires. The escrow accounting (`_orders[...] -= amount`, and for the fee path `delete _orders[body.commitment][TRANSACTION_FEES]`) is committed as if funds moved, while the beneficiary receives nothing. The same unchecked pattern is used for `TRANSACTION_FEES` payout and for the `SweepDust` admin-triggered token transfer in `onPostRequest`. [4](#0-3) [5](#0-4) 

This is the exact bug class from the external report (non-standard ERC20 return-value handling) but landing on the fund-release path rather than the fund-intake path: the contract already fixed intake (`safeTransferFrom`) but left release using the unsafe pattern, so any deployment on a chain/token pair where the output/fee/dust token returns `false` instead of reverting on failure will silently burn the escrowed balance — the ledger says released, but the beneficiary never receives the tokens, and the tokens remain stuck in the contract with no accounting path to reclaim them (since `_orders[...]` was already decremented to zero for that entry).

### Impact Explanation
This is a direct loss/lock of bridged/escrowed user funds: `withdraw()` is reachable both from a successful fill's cross-chain settlement callback and from the refund/timeout GET-response path (`onGetResponse`), so both the "solver got paid" and "user gets refunded" flows are exposed. Once the ledger entry is zeroed while the actual token balance sits untransferred in the contract, neither the beneficiary nor any code path can re-claim it — `UnknownOrder()` will now fire on any retry because `_orders[body.commitment][token]` is already zero.

### Likelihood Explanation
Requires only that one of the escrow's output/fee tokens is an ERC20 implementation that returns `false` on failure without reverting (rather than USDT's missing-return-value quirk, but the same non-standard-token category the report and `SafeERC20` target). No privileged actor, relayer misbehavior, or malformed proof is needed — any unprivileged order participant using such a token triggers it through the normal fill/refund lifecycle.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (escrow release and fee release) and in the `SweepDust` branch of `onPostRequest` with `IERC20(token).safeTransfer(...)`, consistent with how the same contract already handles inflow via `safeTransferFrom` and consistent with the mainline `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`, which already uses `safeTransfer`. [6](#0-5) 

### Proof of Concept
1. Deploy `IntentGatewayV2.sol` (Tron variant) with an output token `T` whose `transfer()` implementation returns `false` on insufficient balance/blacklist instead of reverting (a documented non-standard-but-real-world ERC20 behavior).
2. Create and fill an order whose output/input token is `T`; escrow accounting records `_orders[commitment][T] = amount`.
3. Trigger the cross-chain settlement/refund path so `withdraw(body, ...)` is invoked with `token = T`.
4. `T.transfer(beneficiary, amount)` returns `false` (e.g., beneficiary is blacklisted or contract is paused) but does not revert; `token.call(...)` therefore returns `success = true`.
5. `_orders[body.commitment][T]` is decremented to 0 and `EscrowReleased`/`EscrowRefunded` is emitted, even though the beneficiary's balance of `T` never increased — the tokens remain locked in `IntentGatewayV2` with no ledger entry left to reclaim them.
