### Title
Spoofable `WWW-Authenticate` realm lets a malicious git server trigger a fake "GitHub sign-in" prompt, enabling credential phishing - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The credential helper trampoline classifies a remote host as GitHub/GitHub Enterprise ("enterprise") based solely on the *content* of an attacker-controlled `WWW-Authenticate` HTTP header (`realm="GitHub"`), not on the actual hostname. This is the same class of bug as the report: a security-relevant classification/verification is declared to be based on one thing (the actual GitHub endpoint identity) but is actually implemented using a different, attacker-controllable field (an arbitrary header string), producing an inconsistent, spoofable standard.

### Finding Description
When git performs an HTTPS operation and receives a `401` with a `WWW-Authenticate` header, Desktop's credential helper receives the header as `wwwauth[]=...` entries in the credential protocol payload [1](#0-0) . `getEndpointKind` then determines the "kind" of endpoint like this: [2](#0-1) 

Note that the `wwwauth[...]` check happens *before* any hostname-based validation (`isGitHubHost`) and is matched purely against header text (`v.includes('realm="GitHub"')`), which git forwards to the helper verbatim from whatever server answered the HTTPS request — this is fully attacker-controlled if the remote server (or a MITM/malicious proxy sitting on a `http://` remote, or a compromised/attacker-operated git host the user added) chooses to send `WWW-Authenticate: Basic realm="GitHub"`.

Back in `getCredential`, if `endpointKind !== 'generic'` and no existing local account matches the (attacker-controlled) `apiEndpoint`, Desktop automatically opens a GitHub sign-in dialog for that endpoint: [3](#0-2) 

That in turn calls `promptForGitHubSignIn`, which — because the spoofed hostname isn't `github.com` — routes into the **Enterprise** sign-in flow using the attacker's own origin as the "GitHub Enterprise" endpoint: [4](#0-3) 

The enterprise sign-in flow only validates that the URL is syntactically valid HTTPS (`validateURL`), not that it's an actual GitHub Enterprise instance [5](#0-4) , then opens the user's browser to `${endpoint}/login/oauth/authorize` on the attacker's own domain, or — depending on the enterprise's login page — could otherwise be used to make the app request the user open/trust a phishing page under the pretext of an unavoidable "this repo requires GitHub sign-in" prompt that Desktop itself initiated during an ordinary `fetch`/`clone`/`push`.

### Impact Explanation
This is a no-privilege, remote-triggerable path: an attacker who controls (or has compromised/proxies) a git remote the victim has added can cause GitHub Desktop to spontaneously display what looks like a legitimate GitHub/Enterprise sign-in requirement during a routine git operation, using an endpoint the attacker fully controls. Because the classification (`getEndpointKind`) is driven by spoofable header text rather than actual host identity, the "existing guards" (endpoint-vs-account matching in `findGitHubTrampolineAccount`, which compares real recorded account origins) never get a chance to reject the request — the flow is routed to the sign-in *prompt* path specifically because no matching account exists. This is a credential/OAuth-phishing primitive: the victim did nothing more than clone/fetch/push to an attacker-supplied remote, and the dialog exists to normalize entering credentials for an arbitrary "GitHub Enterprise" host chosen by the attacker.

### Likelihood Explanation
Moderate-to-high. Any attacker who can stand up an HTTP git server, or MITM an `http://` remote, or get a victim to add a remote pointing at their infrastructure, can trigger this without any special git protocol tricks — a single crafted `401 WWW-Authenticate: Basic realm="GitHub"` response is sufficient. The main constraint is that the victim must actually notice and interact with the resulting sign-in dialog, but the entire point of the bug is that Desktop itself vouches for the prompt as "you need to sign in," lending it credibility.

### Recommendation
Do not classify a remote as GitHub/Enterprise based on `WWW-Authenticate` realm text alone. Require that the actual request hostname pass `isGitHubHost`/`isDotCom`/`isGHE`/`isGist` checks (i.e., verify the *URL*, not attacker-supplied header text) before treating an endpoint as `'enterprise'`, and prefer to fall through to the `generic` credential path (or a clearly-labeled "unknown host requested GitHub-style auth" warning) when the header claims a GitHub realm but the hostname doesn't match any recognized GitHub pattern.

### Proof of Concept
1. Host a minimal HTTPS git server (e.g., a dumb HTTP git backend) at `https://evil.example.com/victim/repo.git` that responds to authentication-required requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote/clone target in GitHub Desktop and performs a fetch/push.
3. Git invokes Desktop's credential helper trampoline; `parseCredential` captures the `wwwauth[]=Basic realm="GitHub"` line [6](#0-5) .
4. `getEndpointKind` matches the realm string and returns `'enterprise'` for `evil.example.com` [7](#0-6) .
5. No account matches `evil.example.com`, so `ui.promptForGitHubSignIn('https://evil.example.com')` is invoked, opening an "Enterprise sign-in" flow trusting the attacker's own domain [8](#0-7) .

Note: I was unable to fully inspect `isDotCom`/`isGHE`/`isGist`/`isGitHubHost` implementations in `app/src/lib/api.ts` and `app/src/lib/endpoint-capabilities.ts` before running out of tool iterations, so I cannot rule out an additional hostname check that might partially mitigate this specific branch. This should be verified directly in those files before treating this as fully confirmed.

export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (

    !accounts.some(a => a.endpoint === apiEndpoint)

      return undefined

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
