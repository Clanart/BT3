### Title
OOB panic on `Interpolation::Constant` coefficient slice — unvalidated length in `ThresholdKeys::new` crashes on attacker-controlled deserialized keys - (File: crypto/dkg/src/lib.rs)

### Summary
`Interpolation::Constant(Vec<F>)::interpolation_factor` indexes `c[i - 1]` for participant `i`, yet `ThresholdKeys::new` only checks `t == n` for constant interpolation and never validates `c.len() >= n`. `ThresholdKeys::new` then eagerly computes `group_key` by calling `interpolation_factor` for every `i` in `1..=t`, so a `Constant` coefficient vector shorter than `t` causes an immediate out-of-bounds panic. This is the same bug class as CVE-2014-10077 (`Hash#slice` crash when a requested key is absent): a container is queried for an element that was never proven present, and the lookup panics instead of erroring. Untrusted bytes routed through `ThresholdKeys::read`/`ThresholdKeys::new` trigger a reliable crash (denial of service) in any process deserializing them.

### Finding Description
`interpolation_factor` performs an unchecked slice index for the `Constant` variant:

```rust
// crypto/dkg/src/lib.rs:226-228
fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
  match self {
    Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
```

The constructor validates the `verification_shares` map (length `== n`, all keys `<= n`, which — since `Participant` rejects `0` at `Participant::new` and `BorshDeserialize` — forces the key set to be exactly `1..=n`), and checks `t == n` for `Constant` interpolation, but never checks that `c.len()` equals `n`/`t`:

```rust
// crypto/dkg/src/lib.rs:361-378
for participant in verification_shares.keys().copied() {
  if u16::from(participant) > params.n() {
    Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
  }
}
match &interpolation {
  Interpolation::Constant(_) => {
    if params.t() != params.n() {
      Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
    }
  }
  ...
}
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

`interpolation_factor` is invoked for `i` up to `t` (`= n`), indexing `c[0] .. c[t-1]`. A serialized `ThresholdKeys` carrying `Interpolation::Constant` with fewer than `t` coefficients (the vec length comes straight from the input bytes in the deserialization path) makes `c[i - 1]` panic with an index-out-of-bounds during `group_key` construction inside `ThresholdKeys::new` — i.e., during `ThresholdKeys::read` itself. The panic also fires later in `ThresholdKeys::view` (`crypto/dkg/src/lib.rs:496,505`) and in `ThresholdView::interpolation_factor`, but construction already crashes before those are reachable.

### Impact Explanation
Any code path that feeds attacker-supplied bytes into `ThresholdKeys::read` (key material relayed by peers during recovery/promotion flows, or any other deserialized `ThresholdKeys`) can be crashed deterministically with a short constant-coefficient vector. In Rust this is an unwind/abort at the indexing site, taking down the calling task — a denial-of-service identical in effect to the i18n advisory: the attacker supplies a collection missing elements the code assumes exist, and the missing-element lookup crashes the application. Per-scope impact is availability of the signing/key-management process; no secret leakage occurs.

### Likelihood Explanation
Reachability requires the attacker to supply bytes deserialized as `ThresholdKeys` where `params.t == params.n` (so the `Constant` arm is accepted) and `interpolation = Constant` with a coefficient count `< t`. `ThresholdParams::new` (`crypto/dkg/src/lib.rs:166-179`) accepts any `t <= n`, and nothing in `ThresholdKeys::new` ties the coefficient vector length to `n`, so a single crafted byte stream produces the panic 100% of the time. The constraint `t == n` is satisfiable with e.g. `t = n = 2`, so the payload is small and does not require controlling any other participant's honest messages — only the deserialized key bytes. Severity is bounded to availability (Medium-to-High DoS), matching the advisory's `A:H` impact class.

### Recommendation
In `ThresholdKeys::new`, extend the `Interpolation::Constant(c)` arm to reject `c.len() != usize::from(params.n())` with a `DkgError` before computing `group_key`. Additionally, make `interpolation_factor` defensive by returning `Option<F>` (or indexing via `c.get(i - 1)` and propagating an error) so no caller can panic on a length mismatch, and add a deserialization test asserting a truncated `Constant` vector yields a structured error, not a panic.

fn poc<C: Ciphersuite>() {

  let params = ThresholdParams::new(2, 2, Participant::new(1).unwrap()).unwrap();

  let _ = ThresholdKeys::new(

  );
}
