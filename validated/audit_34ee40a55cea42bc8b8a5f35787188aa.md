# Vulnerability Analog Found

### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub Enterprise classification, triggering unauthorized sign-in flow against a malicious host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The original finding is a "missing cross-check between two independently attacker-influenced inputs" bug (`_tokenFrom` type vs `msg.value`), causing the contract to act on unvalidated combined state. The Desktop analog is `getEndpointKind()` in the git credential-helper trampoline, which classifies a remote host as a trusted "GitHub" endpoint based solely on an HTTP response header that the *remote server itself* controls, before ever performing the real verification step, and that classification is then used to automatically launch the native "Sign in to GitHub Enterprise" flow.

### Finding Description
When Git performs an HTTPS authentication challenge against a remote, it captures any `WWW-Authenticate` response header and forwards it to Desktop's credential helper as a `wwwauth[]` field [1](#0-0) . `getEndpointKind()` uses the presence of `realm="GitHub"` in that attacker/server-controlled header as a shortcut ("happy path") to classify the endpoint as `'enterprise'`, explicitly to *avoid* making the real verification call: [2](#0-1)  The genuine verification (`isGitHubHost(endpoint)`, an actual network probe) is only reached as a fallback if the header trick doesn't fire [3](#0-2) .

This mirrors the smart-contract bug pattern exactly: two values that are supposed to be correlated (the *real* identity of the host vs. the *claimed* identity via an untrusted header) are never cross-checked before privileged logic acts on the claimed value.

Once `getEndpointKind()` returns `'enterprise'`/`'github.com'` for a host with no matching stored account, `getCredential()` unconditionally calls `ui.promptForGitHubSignIn(endpoint)` using the attacker's own remote URL as the "GitHub" endpoint [4](#0-3) . `promptForGitHubSignIn` then derives the origin from that same attacker-controlled URL and starts the Enterprise sign-in flow against it: [5](#0-4)  This leads into `SignInStore.setEndpoint()`/`authenticateWithBrowser()`, which opens the user's browser to an OAuth authorization URL built directly from the attacker's endpoint [6](#0-5) .

### Impact Explanation
A malicious/compromised git remote or a MITM proxy sitting in front of any HTTPS remote (no special user privileges, no local access needed — only requires the victim to run a normal git operation like clone/fetch/push against that remote) can force Desktop's native, trusted-looking "Sign in to GitHub" popup to appear and point it at the attacker's own server. This is a credential-phishing primitive baked into the trusted UI chrome of the app, and can also result in Desktop persisting an "account" bound to the attacker's fake endpoint (`AccountsStore`), i.e. unauthorized OAuth/account binding as called out in the valid-impact criteria. No file/RCE outside the sandbox is achieved, but the invariant broken is identical to the seed report: unauthenticated, attacker-supplied data is used to make a trust decision that existing "real" verification logic (`isGitHubHost`) was specifically designed to establish safely.

### Likelihood Explanation
Reachable purely through normal use: any user cloning/fetching/pushing to an HTTPS remote controlled by (or proxied by) an attacker will hit this code path whenever Git performs an auth challenge, since Git forwards `WWW-Authenticate` headers verbatim to the credential helper. The comment in the code confirms this was an intentional trade-off ("happy-path... without having to resort to making a request ourselves"), meaning the bypass of the authoritative check is by design, not an oversight, which increases confidence this path is exercised in practice, but I could not directly trace end-to-end whether `getIsBackgroundTaskEnvironment` suppresses the prompt for all automated/background fetches, which would reduce interactive exposure to explicit user-initiated git operations.

### Recommendation
Do not treat the `wwwauth[]` realm header as sufficient to classify a host as `'enterprise'`/trusted for the purposes of initiating a sign-in flow or looking up stored credentials. At minimum, require the authoritative `isGitHubHost(endpoint)` check (or an equivalent, already-established account/allowlist match) before short-circuiting to the "enterprise" classification, or require explicit user confirmation showing the literal endpoint hostname before opening the sign-in flow triggered by a header value that originates from the remote itself.

### Proof of Concept
1. Host a git-over-HTTPS server (or MITM proxy in front of any HTTPS remote) that, on any authentication challenge, replies with `WWW-Authenticate: Basic realm="GitHub"`.
2. Have the victim `git clone`/`fetch`/`push` against that remote in Desktop.
3. Git captures the header and forwards it to Desktop's credential helper trampoline as `wwwauth[0]=Basic realm="GitHub"`.
4. `getEndpointKind()` returns `'enterprise'` without ever calling `isGitHubHost()` [7](#0-6) .
5. Since no account matches this attacker endpoint, Desktop calls `promptForGitHubSignIn(endpoint)` and opens the "Sign in to GitHub Enterprise" flow against the attacker's own domain [8](#0-7) , eventually opening the system browser to an OAuth URL built from the attacker endpoint [9](#0-8) .

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
