### Title
Ed448 point deserialization accepts small-order (torsion) points because `is_torsion_free` is a vacuous check - (File: crypto/ed448/src/point.rs)

### Summary
The Ed448 implementation in `crypto/ed448/src/point.rs` attempts to reject non-prime-order points during decoding via `Point::is_torsion_free`, but the check computes `self * (Scalar::ZERO - Scalar::ONE) + self`, i.e. `(-P) + P`, which is the identity for **every** point. The result is that `GroupEncoding::from_bytes` (and therefore `Ed448::read_G`, `DLEqProof::read`, `Commitments::read`, `SchnorrSignature::read`, etc.) accepts any on-curve Ed448 point, including the order-2 and order-4 torsion points that Ed448's cofactor-4 group structure admits. The analogous classes upstream — `dalek-ff-group` (`crypto/dalek-ff-group/src/lib.rs:435`) and the ed448 negative-zero rejection in the same function — correctly enforce torsion-freeness, confirming this is a real defect and not a design choice.

### Finding Description
`from_bytes` decodes `y`, recovers `x`, rejects negative-zero encodings, and then requires `point.is_torsion_free()`:

- `crypto/ed448/src/point.rs:303-318` — `CtOption::new(point, not_negative_zero & point.is_torsion_free())`
- `crypto/ed448/src/point.rs:295-297` — `is_torsion_free` is `((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()`.

`Scalar::ZERO - Scalar::ONE = -1`, and scalar multiplication is modulo the group order, so `P * (-1) + P = identity` unconditionally. The intended check (multiply by the cofactor 4, or equivalently verify `q·P == 0` per RFC 8032's "multiplied by the cofactor" decode rule) never happens. Contrast with `crypto/dalek-ff-group/src/lib.rs:435`, where `$torsion_free(point)` is a real check, and with `crypto/ciphersuite/src/lib.rs:91-100` (`Ciphersuite::read_G`), which relies on `from_bytes` to enforce canonical prime-subgroup membership (`PrimeGroup` bound at `crypto/ciphersuite/src/lib.rs:37`).

Reachability: `Ed448` implements the FROST `Curve` trait (see `crypto/frost/src/tests/literal/ed448.rs:25-53` exercising `Ed448::read_G`/`read_F` on wire bytes). Any peer-supplied point — DKG commitments, FROST `Preprocess`/`Commitments` nonces, signature shares' `R`, `ThresholdKeys` verification shares — flows through `Ed448::read_G` → `from_bytes` → the broken check.

### Impact Explanation
An unauthenticated counterparty can submit Ed448 points carrying a torsion component where the protocol assumes prime-order-group elements:

- **FROST Ed448 signing** (`crypto/frost/src/sign.rs`): a participant's nonce commitment or verification share containing a torsion component breaks the `s·G = R + c·A` consistency between the aggregated signature check (`AlgorithmSignatureMachine::complete`, `crypto/frost/src/sign.rs:447-495`) and per-share `verify_share` blame — letting a malicious signer inject equivocating commitments, poison blame attribution, and force `InternalError`/abort conditions that honest shares cannot cause.
- **Small-subgroup confinement**: key shares/nonces multiplied against attacker-controlled torsion-bearing points leak the low-order residue (2 bits) of the scalar per interaction — a partial secret-leakage channel the `PrimeGroup` contract is supposed to exclude.
- The `PrimeGroup` marker (`crypto/ed448`, `impl PrimeGroup for Point`) is violated for deserialized values, invalidating downstream soundness assumptions in `DLEqProof`/`Schnorr` verification math that assume prime order.

This is a real memory-safety-adjacent correctness bug mapped onto Serai's shape: deserialization accepts semantically invalid inputs that corrupt subsequent group arithmetic (analogous bug class to CVE-2024-3864: attacker-controlled bytes inducing state the verifier assumed unreachable).

### Likelihood Explanation
Medium. Exploitation requires a counterparty in an Ed448 FROST/DKG session (or anything decoding Ed448 points from untrusted bytes) willing to submit non-subgroup encodings — no special privileges needed. The consequence is bounded by the small cofactor (4): at most 2 bits of scalar leakage per malicious point and denial-of-service/equivocation rather than direct full key recovery. That places it below a full-extraction Critical but well above informational, since it silently voids a security invariant the rest of the stack depends on.

### Recommendation
Replace the vacuous check with a real cofactor clearing test, e.g.:

```rust
// crypto/ed448/src/point.rs
fn is_torsion_free(&self) -> Choice {
  // Ed448 has cofactor 4: P is in the prime-order subgroup iff 4*P == identity
  self.double().double().is_identity()
}
```

or check `self * Scalar::from(4u64)` / the prime-subgroup order. Also add a regression test decoding each order-2/order-4 point and asserting `from_bytes` rejects it (mirroring `ff-group-tests` canonical-encoding tests), plus a `to_bytes`/`from_bytes` round-trip asserting decoded points always satisfy `is_torsion_free`.

### Proof of Concept
```rust
// Any Ed448 point of order 2 or 4 decodes successfully:
// Let T4 be a known order-4 point on Ed448 (e.g., a point with y = -1-style
// encodings resolvable on-curve). Then:
let enc = torsion_point_bytes; // 57-byte encoding of an order-4 point
let pt = Option::<ed448::Point>::from(
    <ed448::Point as group::GroupEncoding>::from_bytes(&enc)
);
assert!(pt.is_some()); // BUG: accepted, is_torsion_free() returned true
// because (-P) + P == identity for all P, including order-4 P.
```
Concretely: craft a FROST `Preprocess` for the `Ed448` ciphersuite whose `Commitments` nonce point is `R + T` where `T` has order 4. `SignMachine::read_preprocess` → `Commitments::read` → `Ed448::read_G` accepts it. The share then verifies inconsistently under the aggregated-vs-batch checks in `complete` (`crypto/frost/src/sign.rs:465-489`), demonstrating acceptance of input the `PrimeGroup` contract forbids — behavior impossible under a correct `is_torsion_free` (multiply-by-4) implementation.
