### Title
`EncryptedMessage::read` allocates an unbounded attacker-claimed ciphertext length, enabling memory-exhaustion DoS - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The DKG PedPoP `EncryptedMessage` deserialization reads a 4-byte length field for the ciphertext and immediately performs `vec![0; len]` on it — the same house-style pattern used throughout Serai (`vec![0; usize::try_from(u32::from_le_bytes(len)).unwrap()]`, e.g. `processor/src/plan.rs:56`, `coordinator/tributary/src/tests/transaction/mod.rs:59`). There is no cap on the claimed length and no chunked read, so a message declaring a ~4 GiB ciphertext forces a ~4 GiB allocation before a single ciphertext byte is checked. This is the direct analog of the referenced Coder advisory: a size field trusted without an aggregate bound, allocating an unbounded in-memory buffer from untrusted input.

### Finding Description
In the PedPoP DKG protocol, `EncryptedMessage::read` consumes: the `intended_for` participant index, the ephemeral ECDH `key` via `C::read_G`, a `u32` ciphertext length, the ciphertext buffer, and a `SchnorrSignature`. The ciphertext is an arbitrary-length `Vec<u8>` (it wraps the serialized encrypted share payload), so a length prefix is legitimately needed — but the claimed length is used to size the allocation outright. `read_exact` will only fail *after* the allocation succeeds, so the attacker pays 4 bytes to impose a multi-GiB allocation on the reader.

Every other Serai deserializer that was hardened shows the authors recognized this class: `networks/ethereum/src/machine.rs:51-60` explicitly comments "A valid DoS would be to claim a 4 GB data is present for only 4 bytes" and reads in 1 KB chunks; `coordinator/src/tributary/transaction.rs:286` enforces `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` before allocating; `coordinator/src/p2p.rs:264-270` bounds the claimed length by `MAX_LIBP2P_REQRES_MESSAGE_SIZE`. `EncryptedMessage::read` has no equivalent guard. (Note: the `DkgShares` variant of `Transaction::read` at `coordinator/src/tributary/transaction.rs:309-331` exhibits the identical missing-aggregate-limit shape — `share_quantity × key_share_quantity × share_len` up to ~4 GiB with no `TRANSACTION_SIZE_LIMIT` check, unlike the adjacent `DkgCommitments` branch — reinforcing that this class is real in Serai, though that file is outside the in-scope crates.)

### Impact Explanation
A single malformed DKG message claiming a near-`u32::MAX` ciphertext causes the receiving validator to attempt a ~4 GiB heap allocation and then block/zero it before `read_exact` discovers the payload is absent. With a modest number of concurrent messages, node memory is exhausted and the process is OOM-killed or aborts on allocation failure, taking down the DKG/signing process. Impact is availability only — no disclosure or code execution — matching the CVE's A:H-only CVSS vector.

### Likelihood Explanation
`EncryptedMessage` is exchanged between participants during PedPoP key generation, and `EncryptedMessage::read` is explicitly one of the deserialization entry points accepting untrusted bytes. Any party able to deliver a PedPoP message to a participant (or any integrator that reads a serialized `EncryptedMessage` from an untrusted buffer/file) triggers the allocation; the malicious bytes need only be ~10 bytes long (`participant || key || len=0xFFFFFFFF`) since the attack never requires the declared data to exist. Repeated submissions sustain the DoS.

### Recommendation
Mirror the chunked-read mitigation already present in `Call::read` (`networks/ethereum/src/machine.rs:51-60`): either reject ciphertext lengths above a sane bound (encrypted shares have a well-defined maximum size derivable from `ThresholdParams`/the ciphersuite), or read in small chunks so allocation tracks bytes actually transmitted. Alternatively, enforce an aggregate size limit on the whole PedPoP message before deserializing `EncryptedMessage`, analogous to the `TRANSACTION_SIZE_LIMIT` preflight used for `DkgCommitments`.

### Proof of Concept
Conceptual byte stream fed to `EncryptedMessage::read` (or to the PedPoP `commit`/`share` flow that calls it):

```text
01 00            // intended_for = Participant 1
<32-byte compressed G for key>   // any canonical point
ff ff ff ff      // ciphertext_len = u32::MAX (~4 GiB)
                 // <-- attacker sends nothing more
```

The deserializer executes `vec![0; ~4 GiB]` (allocation + zeroing) before `read_exact` returns `UnexpectedEof`. N such messages per allocation window yield ~N×4 GiB of transient memory pressure. By contrast, an honest `EncryptedMessage` ciphertext is bounded by the share size (a handful of scalars per `ThresholdParams`, plus the authenticated-encryption overhead), so a limit in the low kilobytes would preserve all legitimate traffic.
