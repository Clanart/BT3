### Title
`GIT_CLONE_PROTECTION_ACTIVE` explicitly disabled during recursive clone re-enables CVE-2024-32002 submodule hook RCE - (File: app/src/lib/git/clone.ts)

### Summary
GitHub Desktop's `clone()` function performs `git clone --recursive` while explicitly setting the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. This variable is the actual safety switch Git added upstream to fix CVE-2024-32002 — a vulnerability where a malicious repository with a crafted submodule (whose name/path collides with the superproject's `.git` directory, e.g. via case-folding, `8.3` short names on Windows, or symlink tricks) could cause Git to write attacker-controlled hook scripts into the superproject's `$GIT_DIR/hooks`, which then execute automatically. By hard-coding this flag to `false`, Desktop forces Git to skip the very check that was added to detect and block this collision, directly re-opening the RCE that upstream Git patched. [1](#0-0) 

### Finding Description
The broken invariant is: "Git's built-in submodule-collision protection is always active during automated/recursive clones." Desktop violates this invariant unconditionally for every clone it performs, because the `env` object passed into the `git()` invocation always contains `GIT_CLONE_PROTECTION_ACTIVE: 'false'` alongside the `--recursive` flag: [1](#0-0) 

```
const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }
  ...
  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
```

`--recursive` means every submodule referenced by the top-level, attacker-controlled repository is fetched and checked out automatically without further user confirmation. Git's post-CVE-2024-32002 code path uses `GIT_CLONE_PROTECTION_ACTIVE` to know when it is running inside a "protected" clone context so it can refuse to write into paths that would escape into `.git/`, `.git/hooks`, or `.git/modules` of the superproject via a maliciously named or symlinked submodule. Setting the value to `'false'` tells Git "protection is not currently active," which suppresses those checks for the entirety of the recursive clone/checkout, including all nested submodule operations.

Existing guards in the file do not stop this path: `isClonePathSensitive()` only validates the destination directory chosen by the *user* (e.g. rejects cloning into `~/.ssh`); it does nothing to validate the *contents* of the untrusted remote repository or its submodules, and it runs before the vulnerable `git clone --recursive` call even executes. [2](#0-1)  Similarly, `envForRemoteOperation(url)` only manages authentication/proxy environment for the operation and has no bearing on submodule path safety. None of the sanitization performed elsewhere in the codebase (e.g. `sanitizeCloneName` for the top-level clone directory name) touches submodule paths that Git itself writes during the recursive checkout. [3](#0-2) 

### Impact Explanation
An attacker who controls a public or shared repository (the classic "attacker controls a cloned/fetched repository" primitive) can craft a malicious submodule configuration designed to collide with the superproject's `.git` directory. When a victim uses GitHub Desktop's "Clone repository" feature (which always runs through this `clone()` function with `--recursive` and the protection disabled), Git will, without any additional confirmation prompt, write files into the victim's `.git/hooks` directory that get executed on subsequent Git operations (e.g. `post-checkout`, `pre-commit`) — resulting in arbitrary code execution on the victim's machine outside the scope of the repository content the user intended to trust. This satisfies the "code execution... from a cloned/fetched repository" impact category.

### Likelihood Explanation
Likelihood is high for any user who clones an attacker-supplied URL through Desktop's normal clone flow (Clone dialog, "Open in Desktop" deep links which internally reuse `clone()`, or CLI `--cli-clone`). No special local access, elevated privileges, or pre-existing malware is required — only that the user clone a URL the attacker controls, which is squarely within Desktop's supported and expected usage pattern. The `--recursive` flag guarantees submodules are processed automatically with zero additional user interaction, and the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` removes Git's own opt-in safety net for exactly this scenario.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Leave Git's default (protection enabled) in place for all clone operations, and if `--recursive` submodule initialization needs the protection temporarily relaxed for legitimate reasons, gate that decision behind an explicit, narrowly-scoped exception rather than unconditionally disabling it for every clone. At minimum, upgrade the bundled Git/dugite version to one containing the CVE-2024-32002 fix and remove this override entirely so the fix takes effect; if removed by mistake to work around a compatibility issue, that workaround should be reverted and replaced with a proper submodule-path validation step performed by Desktop itself before/after the clone.

### Proof of Concept
1. Attacker creates a repository containing a `.gitmodules` entry and worktree structure per the public CVE-2024-32002 write-up (a submodule directory name that, through case-insensitivity or short-name aliasing, resolves to the superproject's `.git` directory, embedding a hook script such as `post-checkout`).
2. Victim opens GitHub Desktop and clones the attacker's repository URL via the normal Clone dialog (or an "Open in Desktop" link), invoking `clone(url, path, options)` in [4](#0-3) .
3. Desktop runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment.
4. Git recursively initializes the malicious submodule; because protection is explicitly deactivated, Git does not detect/block the hook file being written into the superproject's `.git/hooks`.
5. The planted hook executes automatically on the next qualifying Git operation Desktop performs on the repository (e.g. checkout), achieving code execution on the victim's machine.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
