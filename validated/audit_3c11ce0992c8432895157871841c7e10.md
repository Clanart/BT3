Audit Report

## Title
Unrooted-slot remove/restore race panics `retry_to_get_account_accessor`, crashing the validator - (File: accounts-db/src/accounts_db.rs)

## Summary
`AccountsDb::retry_to_get_account_accessor` unconditionally panics whenever the accounts index returns the same `(slot, store_id)` tuple after a failed accessor lookup, without excluding `StorageLocation::Cached` entries. A benign race between `remove_unrooted_slots` (purging a slot's cache/index entries) and `store_accounts_unfrozen`/`store_for_tests` (re-populating the same slot) reproduces this exact same-slot/same-store-id condition through legitimate validator activity, triggering the panic and crashing the process.

## Finding Description
In `accounts-db/src/accounts_db.rs`, the retry branch checks only `new_slot == slot && new_storage_location.is_store_id_equal(&storage_location)` before entering an unconditional assert/panic path: [1](#0-0) 
Inside this branch, the code asserts `is_offset_equal`, then asserts `load_hint == LoadHint::Unspecified`, and finally calls `panic!` — none of these checks special-case a `Cached` storage location, contrary to the documented intent in the regression test's comment that the fix should "guard the bad-index-entry panic with `!new_storage_location.is_cached()`" [2](#0-1) . Because the guard is absent, any recurrence of `(slot, Cached)` — including the legitimate recurrence produced by a purge-then-restore race — falls into this branch and panics (either via the `is_offset_equal` assert, the `load_hint == Unspecified` assert failing for `FixedMaxRoot`, or the final unconditional `panic!`).

The accompanying regression test `test_load_after_remove_unrooted_and_restore_to_same_slot` [3](#0-2)  directly exercises this: a control thread alternates `remove_unrooted_slots` and `store_for_tests` for a fixed `(slot, pubkey)`, while a load thread repeatedly calls `AccountsDb::load` with `LoadHint::FixedMaxRoot`. This reproduces the sequence described in the comment — index/cache purge, re-population with a fresh `(slot, Cached)` entry, and a retry that observes the same slot/store-id tuple — and the test explicitly notes this panicked prior to the (missing) fix.

## Impact Explanation
A panic inside `AccountsDb::retry_to_get_account_accessor` (reached via `do_load`, on the hot path for transaction/account loading during replay and banking) is not caught during normal operation and results in thread/process termination of the validator, or a poisoned lock cascading into further panics. This is a crash of a single validator instance triggered by ordinary internal runtime activity (duplicate/unrooted slot cleanup racing with an in-flight load), not by attacker-supplied transaction or RPC payloads.

## Likelihood Explanation
The precondition — a duplicate/unrooted bank being purged (`remove_unrooted_slots`) and the same slot concurrently re-populated (`store_accounts_unfrozen`) while another thread loads an account from that slot — arises from the validator's own duplicate-block/fork-handling logic, not from attacker-controlled input. The regression test needed a tight, repeated race loop with a multi-second sleep to reliably reproduce it, indicating a narrow but real timing window rather than an input-driven, deterministically triggerable path.

## Recommendation
In `retry_to_get_account_accessor`, exclude `StorageLocation::Cached` entries from the bad-index-entry panic path (e.g., only enter the assert/panic branch when `!new_storage_location.is_cached()`), matching the intent documented in the regression test, so a benign cache remove-then-restore race is treated as a normal retry iteration instead of fatal index corruption.

## Proof of Concept
Run `test_load_after_remove_unrooted_and_restore_to_same_slot` in `accounts-db/tests/accounts_db.rs`: a control thread cycles `remove_unrooted_slots`/`store_for_tests` for a fixed `(slot, pubkey)` while a load thread calls `AccountsDb::load` with `LoadHint::FixedMaxRoot` in a tight loop for 5 seconds; absent the `is_cached()` guard, this reliably panics inside `retry_to_get_account_accessor`.

#[test]
fn test_load_after_remove_unrooted_and_restore_to_same_slot() {
    let slot = 402240429;
    let bank_id = 1;
    let pubkey = Pubkey::new_unique();
    let account = AccountSharedData::new(42, 0, AccountSharedData::default().owner());

    let db = Arc::new(AccountsDb::default_for_tests());
    let ancestors = Ancestors::from(vec![slot]);

    let exit = Arc::new(AtomicBool::new(false));

    // Control thread – performs the sequential remove-then-store cycle that mirrors
    // what happens in production when a duplicate bank is purged and the slot is
    // subsequently re-processed by the banking stage.
    let t_store = {
        let db = db.clone();
        let account = account.clone();
        let exit = exit.clone();
        std::thread::Builder::new()
            .name("control".to_string())
            .spawn(move || {
                loop {
                    if exit.load(Ordering::Relaxed) {
                        return;
                    }
                    // Step A: purge the slot (simulate remove_unrooted_slots).
                    if db.accounts_cache.slot_cache(slot).is_some() {
                        db.remove_unrooted_slots(&[(slot, bank_id)]);
                    }
                    // Step B: re-store the account (simulate store_accounts_unfrozen).
                    db.store_for_tests((slot, &[(&pubkey, &account)][..]));
                }
            })
            .unwrap()
    };

    // Load thread – continuously attempts to load the account.
    let t_do_load = {
        let db = db.clone();
        let exit = exit.clone();
        std::thread::Builder::new()
            .name("load".to_string())
            .spawn(move || {
                loop {
                    if exit.load(Ordering::Relaxed) {
                        return;
                    }
                    let _ = db.load(
                        &ancestors,
                        &pubkey,
                        LoadHint::FixedMaxRoot,
                        PopulateReadCache::False,
                    );
                }
            })
            .unwrap()
    };

    // Prior to the fix, it failed with a panic in 'retry_to_get_account_accessor' after ~1 second,
    // run long enough to catch the failure reliably.
    sleep(Duration::from_secs(5));
    exit.store(true, Ordering::Relaxed);
    t_store.join().unwrap();
    // Propagate any panic from the load thread in retry_to_get_account_accessor).
    t_do_load.join().map_err(std::panic::resume_unwind).unwrap();
}
