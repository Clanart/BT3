### Title
Permissionless `accumulate_fees` lets anyone strip a relayer's beneficiary redirect, permanently stranding fees at an unsignable `delivery_address` - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-ismp-relayer`'s `accumulate` credits fee balances either to a redirect `beneficiary_address` (chosen and signed by the relayer that delivered the message) or, absent that signed redirect, directly to the raw `delivery_address` decoded from the destination chain's request-receipt trie value. `accumulate_fees` is a fully unsigned/permissionless extrinsic (`ensure_none(origin)`), and once a batch of commitments is accumulated the underlying `RequestCommitments::claimed` flags are permanently set, so the same commitments can never be accumulated again. This mirrors the Euler/Berachain report's core defect: value gets attributed to an "account" whose true controller may be unable to ever claim it, and the write is irreversible.

### Finding Description
`WithdrawalProof::beneficiary_details` is an `Option<(Vec<u8>, Signature)>`. When present, `accumulate()` verifies a signature from the `delivery_address` over `(nonce, state_machine, beneficiary_address)` and credits `Fees[state_machine][beneficiary_address]` instead of the raw delivering account: [1](#0-0) 

When `beneficiary_details` is `None`, the fee is credited directly to `delivery_address` — the address extracted straight from the destination chain's `RequestReceipts` trie entry via `decode_receipt_relayer`, i.e. whatever `msg.sender`/signer actually submitted the delivery transaction on-chain: [2](#0-1) 

Crucially, `accumulate_fees` requires no signature or authorization from the relayer at all — it is dispatched with `ensure_none(origin)`, so **any address** holding the (publicly available) state proofs of the source request commitments and the destination delivery receipts can submit the batch: [3](#0-2) 

Once `accumulate` runs, every commitment resolved in the batch is marked `claimed = true` in `RequestCommitments`, unconditionally of who submitted it or whether a beneficiary redirect was included: [4](#0-3) 

The prior filter step also skips any commitment already flagged `claimed`, so this state transition is irreversible — the same commitment can never be accumulated a second time with a corrected beneficiary: [5](#0-4) 

Withdrawal of `Fees[state_machine][address]` is only possible by producing an EVM/sr25519/ed25519 signature that recovers to exactly that stored `address`: [6](#0-5) 

If the account that actually delivered the message on the destination chain (the value recorded in `RequestReceipts`, i.e. `msg.sender` there) is a smart-contract account — a multisig, an ERC-4337 smart account, or any relaying infrastructure that submits transactions via a contract rather than an EOA/keypair — that address can never produce a valid `Signature::Evm/Sr25519/Ed25519` that recovers to itself. Such an address is a completely normal, protocol-legal way to relay (Hyperbridge relayers are explicitly permitted to be "the account on which the given operation is performed"; no protocol invariant forbids contract-based delivery). The only mechanism that lets the true beneficiary escape this trap is the signed `beneficiary_details` redirect supplied at `accumulate` time — and because `accumulate_fees` is permissionless and the claim is a one-shot, irreversible state write, any unprivileged third party can submit the identical, publicly-derivable state proof first, with `beneficiary_details = None`, locking the reward onto the unsignable `delivery_address` before the legitimate relayer's own redirect-bearing accumulation reaches the chain.

### Impact Explanation
This is a direct fund-loss/fund-lock bug in the relayer reward-accounting path: legitimately-earned relayer fees (and, if relayer infra uses contract accounts, potentially the entire pool of accrued rewards for a delivery) can be permanently and irreversibly credited to an address that cannot pass the ECDSA/sr25519/ed25519 signature check required by `withdraw()`. There is no admin, governance, or fallback path in `withdraw()`/`accumulate()` to redirect funds already sitting under an unsignable `delivery_address`. This satisfies the bounty's "loss of funds" / "double-claim or logic attack on reward accounting" criteria in the fee-accumulation path.

### Likelihood Explanation
Exploitation requires no relayer collusion, no leaked keys, no admin/governance action, and no consensus-proof forgery — only that (a) the true delivering account for some request is a smart-contract address (a supported, common configuration for production relaying infrastructure, e.g. gas-abstracted / multisig-controlled relayers), and (b) an unprivileged observer submits the same state proofs via the permissionless `accumulate_fees` extrinsic without the optional beneficiary signature, ahead of the legitimate relayer's own redirect call. Because the request/receipt state proofs referenced by `accumulate` are public chain data (the docs describe them as "freely provided" by connected chains) and the call is `ensure_none`, any node operator can construct and submit this transaction. This is a race against the relayer's own redirect submission rather than a race against a competing benign application flow, but it requires no privileged access and permanently destroys value that the true relayer earned.

### Recommendation
- Do not allow `accumulate()` to permanently mark commitments `claimed` when no `beneficiary_details` is supplied and `delivery_address` cannot possibly satisfy a subsequent signature check (i.e., require an explicit opt-in/whitelisting mechanism for contract-based delivery addresses, or always require a signed beneficiary at accumulation time).
- Alternatively, support an ERC-1271/ERC-6492-style "contract signature" verification path in `withdraw()` so a delivering smart-contract account can authorize a beneficiary after the fact, instead of gating the beneficiary choice to a single, front-runnable accumulation call.
- At minimum, allow re-accumulation/reassignment of a `claimed` commitment's beneficiary via a follow-up signed message from the `delivery_address`'s controller (e.g., a contract-compatible ownership proof), rather than making the direct-credit path a permanent, unauthenticated dead end.

### Proof of Concept
1. Relayer R operates delivery infrastructure through a smart-contract account `C` (e.g., a Safe or AA wallet) that submits the delivery transaction to the destination chain's `IsmpHost`, so `RequestReceipts[commitment] = C`.
2. R's tooling plans to call `accumulate_fees` with a `WithdrawalProof` whose `beneficiary_details = Some((R_eoa, sig))`, redirecting the credit from `C` to an EOA `R_eoa` R actually controls (per `accumulate.rs` L106-147).
3. Before R's transaction lands, attacker A (any unprivileged party) observes the same publicly-available source/destination state proofs and submits `accumulate_fees` with an identical `WithdrawalProof` but `beneficiary_details = None`.
4. Pallet credits `Fees[state_machine][C] += fee` (accumulate.rs L140-147) and marks the commitment `claimed = true` (accumulate.rs L149-161).
5. R's subsequent (now-redundant) accumulation attempt for the same commitment is filtered out entirely because `leaf_meta.claimed == true` (accumulate.rs L58-69), so R can never redirect the fee.
6. R (as controller of contract `C`) can never produce a valid `Signature::Evm/Sr25519/Ed25519` in `withdraw()` (withdrawal.rs L81-115) that recovers to `C`'s own address, so `Fees[state_machine][C]` is permanently stuck and unwithdrawable.

Note: I was not able to fully verify within this session whether any off-chain relayer implementation (tesseract) in this repo currently uses contract-based delivery accounts in production, or whether an operational safeguard elsewhere restricts delivery submission to EOAs only; this would need to be confirmed with the full tesseract relayer configuration/deployment code, which is outside what I could exhaustively inspect here.
