### Title
Nested/recursive precompile calls cause double-application of bank balance events to EVM StateDB via stale `prevEventsLen` tracking - (File: precompiles/common/balance_handler.go)

### Summary
`BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` synchronize the Cosmos SDK bank module's balance-change events with the EVM `StateDB` by recording an event-slice offset (`prevEventsLen`) before a precompile executes and replaying `ctx.EventManager().Events()[prevEventsLen:]` afterward. When a precompile call is reentered (a contract calls a precompile whose execution itself triggers another precompile call on the same shared `ctx.EventManager()`), the inner call's `AfterBalanceChange` already applies the bank events it produced to the `StateDB`, but the outer call's `AfterBalanceChange` still replays events starting at its own earlier offset — reprocessing the same bank events a second time. This desynchronizes the EVM `StateDB` balance view from the actual `x/bank` balance, exactly mirroring the reported bug class of two "supposed to stay in sync" state machines being pushed out of sync by an unprivileged, interleaved call.

### Finding Description
The `BalanceHandler` design assumes precompile invocations complete atomically with respect to `ctx.EventManager()`: [1](#0-0) 

```
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
    bh.prevEventsLen = len(ctx.EventManager().Events())
}
```

and on exit it replays every event recorded since that offset onto the `StateDB`: [2](#0-1) 

Each precompile call obtains its own `BalanceHandler` instance from the factory in `runNativeAction`: [3](#0-2) 

The instance itself is not shared, but the underlying `ctx.EventManager()` **is** shared across the whole EVM transaction/call stack. If a precompile call's native action triggers a second (nested) precompile call — e.g. an ERC20 `_beforeTokenTransfer` hook calling `staking`/`distribution` precompiles, or a precompile issuing an EVM call that reenters another precompile — the following interleaving occurs:

1. Outer precompile call: `BeforeBalanceChange` records `prevEventsLen = N`.
2. Nested precompile call executes, emits bank events `[N..N+k]`, then its own `AfterBalanceChange` applies events `[N..N+k]` to `StateDB` (`AddBalance`/`SubBalance`).
3. Outer precompile call finishes any of its own bank-touching logic, then its `AfterBalanceChange` replays **all** events from its own recorded offset `N` onward — which now includes the events `[N..N+k]` that were already applied to `StateDB` by the nested call, plus any new outer events.
4. Result: the events generated by the nested call are applied to `StateDB.AddBalance`/`SubBalance` **twice**, producing an EVM balance that no longer matches the true `x/bank` balance for the affected accounts.

This is directly demonstrated and labeled as a known bug in the repository's own test suite: [4](#0-3)  and reproduced with a recursive debug precompile caller contract: [5](#0-4) . A related test explicitly documents the consequence for real precompiles (ICS20 + distribution) under recursive/nested precompile invocation from an ERC20 hook: [6](#0-5) , exercised via a contract that recursively calls staking/distribution precompiles from `_beforeTokenTransfer`: [7](#0-6) .

This is the direct Cosmos-EVM analog of the `PCVEquityMinter`/`BalancerLBPSwapper` bug: two components (the `x/bank` ledger and the EVM `StateDB`) are meant to stay perfectly synchronized via a shared, order-dependent bookkeeping cursor (`prevEventsLen`), but nothing prevents an unprivileged, ordinary transaction flow (any contract making nested/recursive precompile calls) from causing that cursor to be consumed/overlapped incorrectly, corrupting the derived state.

### Impact Explanation
Double-application of `CoinSpent`/`CoinReceived`/fractional-balance events onto `StateDB.AddBalance`/`SubBalance` means an EVM account's balance as seen by the EVM (and by any subsequent EVM logic, transfers, or `eth_getBalance` queries) can be inflated or deflated relative to its true, bank-module-backed balance. Since Cosmos EVM balances are 1:1 backed by `x/bank`/`x/precisebank` reserves, a mismatch here is an irreversible accounting-corruption / duplication-of-spendable-value condition — an attacker-influenced contract can cause EVM-visible balances to no longer be backed by real bank coins, enabling spend of value that does not exist in the bank ledger. This matches the "Critical unauthorized … duplication … of spendable user value across … EVM balances … or precompile-mediated assets" impact category.

### Likelihood Explanation
Triggering nested/nested-reentrant precompile calls only requires deploying and calling an ordinary smart contract — no privileged keys, validator, or relayer collusion is needed. The repository's own test suite already constructs such flows (ERC20 token with hooks that call staking/distribution precompiles, or recursive calls into a precompile) as a matter of course, confirming the pattern is reachable through standard, unprivileged EVM contract execution (`_beforeTokenTransfer` hooks, ICS20 transfers combined with token hooks, etc.).

### Recommendation
Track the event-consumption cursor globally per EVM call-frame/transaction rather than per precompile-call instance, or make `AfterBalanceChange` idempotent by marking/removing consumed events (or using a monotonically advancing shared cursor stored on the `StateDB`/journal) so nested precompile invocations cannot cause an outer call to re-process events already applied by an inner call. Alternatively, disallow nested precompile-to-precompile calls within the same EVM call stack, or have each precompile call snapshot and restore the shared cursor across nested boundaries (push/pop semantics) so that after a nested call returns, the outer handler's starting offset is advanced past everything the nested call already consumed.

### Proof of Concept
The repository already contains a reproducible PoC: `evmd/tests/integration/balance_handler/balance_handler_test.go` deploys `DebugPrecompileCaller.sol`, which recursively calls a debug precompile (`callback()` → nested precompile calls), and observes that the number of `debug_precompile` events counted does not match the expected count for the number of recursive precompile invocations, evidencing that event replay/consumption is not correctly scoped per call frame. [8](#0-7)  A second, real-precompile PoC uses an ERC20 token with a recursive `_beforeTokenTransfer` hook calling `claimRewards()` via the distribution precompile during an ICS20 transfer, and is explicitly commented as testing "the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated." [9](#0-8)

pragma solidity ^0.8.4;

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }
}
