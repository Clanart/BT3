### Title
Payout OP_RETURN operator attribution is unauthenticated, allowing a fronted withdrawal to be misattributed to an operator who never funded it - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The bridge determines which operator gets reimbursed for fronting a withdrawal purely by reading an unauthenticated `OP_RETURN` field on the confirmed `payout_tx`, without any cryptographic proof that the named operator actually supplied the funds. This mirrors the WJLP `wrap()` bug class: a value-moving action (fronting the payout) is decoupled from the credit-granting identity (`_rewardOwner`/here, `payout_payer_operator_xonly_pk`), because the binding between "who paid" and "who is credited" is never enforced.

### Finding Description
`create_payout_txhandler` builds the payout transaction with three outputs: the user's payout, an anchor, and an `OP_RETURN` output carrying the fronting operator's x-only pubkey, `op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()))`. [1](#0-0) 

The only witness on this transaction is `user_sig` set via `set_p2tr_key_spend_witness(&user_sig, 0)` — a single key-spend signature over the withdrawal input. [2](#0-1) 

The `operator_xonly_pk` argument itself carries no signature or proof of the operator's identity; `Operator::withdraw()` simply plugs in `self.signer.xonly_public_key` when it builds the tx. [3](#0-2) 

Later, when the payout confirms on-chain, `update_finalized_payouts` extracts the operator pubkey purely by parsing this `OP_RETURN` from the mined transaction — it performs no check that the named operator actually authorized or funded the transaction: [4](#0-3) 

This value is persisted as `payout_payer_operator_xonly_pk` and is the sole basis used by `PayoutCheckerTask` to decide which operator's reimbursement flow to trigger: [5](#0-4) [6](#0-5) 

`validate_payer_is_operator` / `get_reimbursement_txs` and `handle_finalized_payout` then drive the operator through kickoff → challenge-timeout → reimburse, ultimately spending the `MoveToVaultTx` deposit UTXO to reimburse whichever operator's key is named in that `OP_RETURN`: [7](#0-6) [8](#0-7) 

Because nothing ties the `OP_RETURN` content to a signature from the named operator, and because the withdrawal's actual payout amount typically must be supplied through an additional (fee-bumping) funding input rather than being fully covered by the withdrawal input itself (per the docstring "funding the withdrawal transaction using TxSender RBF option" / test helper naming it a "dust UTXO"), any party capable of constructing and confirming a valid payout transaction for the pending withdrawal (spending the same witness-bound input/output pair, but supplying its own funding input) can put an **arbitrary registered operator's x-only pubkey** into the `OP_RETURN`, rather than its own. The equality that should hold — "operator credited == operator that actually funded the payout" — is never checked anywhere in this pipeline.

### Impact Explanation
This breaks the binding "operator credited (payer_xonly_pk) == party that actually paid for the withdrawal", exactly the class of impact called out as Critical: *"an operator reimbursed for a payout it never funded."* A framed, honest operator would be automatically driven by `PayoutCheckerTask`/`handle_finalized_payout` into the kickoff/reimbursement flow for a withdrawal it never fronted, consuming one of its limited per-round kickoff connectors and eventually causing the bridge to release the `MoveToVaultTx` deposit funds to that operator's `reimburse_addr` — funds that operator did not front from its own balance. This is a genuine custody-attribution break (BTC leaving the move-to-vault UTXO is tied to the wrong/unverified funding party).

### Likelihood Explanation
I was unable to fully confirm within the available context whether the withdrawal input's presigned witness uses `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` (which would make this trivially exploitable by anyone observing a broadcast/mempool payout tx and rebroadcasting a variant with a different `OP_RETURN` and their own funding input) or a full-transaction-committing sighash (which would instead require access to the raw presigned data that is "given to operators off-chain," per the code's own documentation, effectively requiring operator-level access). This detail is essential to determine whether the attack is reachable by a fully unprivileged party or requires the kind of privileged/off-chain access this scan is instructed to exclude. Given this residual uncertainty about sighash flags and inability to conclusively verify the reachable attacker surface in the time available, I cannot assert this analog crosses the "unprivileged attacker" bar with full confidence.

### Recommendation
Regardless of the sighash detail, the reimbursement pipeline should not trust attacker-/operator-supplied `OP_RETURN` content as sole proof of who funded a payout. At minimum:
- Require the operator's `OP_RETURN` commitment to be covered by a signature that is bound to the *entire* transaction (`SIGHASH_ALL`) rather than allowing it to float outside of what the user's presigned witness commits to.
- Cross-check that the funding input(s) beyond the withdrawal UTXO are provably controlled/spent by the same operator whose pubkey appears in the `OP_RETURN` (e.g., require a signature from that operator's key over the full payout transaction, not just an unauthenticated data push).

### Proof of Concept
Not fully constructible without confirming the exact sighash flag used for `user_sig` in `create_payout_txhandler`; the conceptual PoC is:
1. Observe (or otherwise obtain) the presigned/broadcast payout transaction for a pending withdrawal, containing the withdrawal input and its committed payout output.
2. Construct an alternative transaction with the same input/committed output, add your own funding input to cover the full withdrawal amount, and add an `OP_RETURN` output naming an arbitrary registered operator's x-only pubkey (not your own).
3. Get this transaction confirmed (via RBF replacement, if the sighash allows adding uncommitted inputs/outputs, or otherwise).
4. `update_finalized_payouts` will record the named operator as `payout_payer_operator_xonly_pk`, and `PayoutCheckerTask` will subsequently drive that operator through kickoff/reimbursement for a withdrawal it never funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

                "Operator: Starting next round to be able to get reimbursement for the payout"

            // start the next round to be able to get reimbursement for the payout
            self.end_round(dbtx).await?;

    /// For a deposit_id checks that the payer for that deposit is the operator, and the payout blockhash and kickoff txid are set.
    async fn validate_payer_is_operator(
        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
    ) -> Result<(BlockHash, Txid), BridgeError> {
        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };

        tracing::info!(
            "Payer xonly pk, payout blockhash and kickoff txid found and valid for own operator for the requested deposit id: {}, payer xonly pk: {:?}, payout blockhash: {:?}, kickoff txid: {:?}",
            deposit_id,
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid
        );

        Ok((payout_blockhash, kickoff_txid))
    }

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
