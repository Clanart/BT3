### Title
Coinbase outputs reported as received and spendable despite being maturity-bound - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
The referenced Lend bug is a missing-registration flaw: collateral is supplied but never entered into `accountAssets`, so the later liquidity check counts zero collateral and a legitimate borrow fails — assets exist yet are unusable. The analog in Serai is `Scanner::scan_block`, which iterates `block.txdata` starting at index 0, thereby scanning the coinbase transaction. A miner can pay the multisig's `script_pubkey` in a coinbase output; the scanner returns it as an ordinary `ReceivedOutput`, and downstream code treats it as a spendable input even though Bitcoin consensus forbids spending it for 100 blocks.

### Finding Description
`scan_block` is defined in `networks/bitcoin/src/wallet/mod.rs`:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

`block.txdata[0]` is the coinbase. `scan_transaction` matches outputs purely by `script_pubkey` against `self.scripts`, with no coinbase/maturity check:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), outpoint: OutPoint::new(tx.compute_txid(), vout) });
}
```

The only acknowledgment is a doc comment stating "If received outputs must be immediately spendable, a post-processing pass is needed." No filter is implemented in the function itself, and `get_outputs` in `processor/src/networks/bitcoin.rs` funnels scanned outputs to the multisig scanner, which forwards anything with `balance >= N::DUST` to `ScannerEvent::Block` outputs — the same pipeline feeding `SignableTransaction::new` in `wallet/send.rs`, which will happily select the immature outpoint as an input.

Like the Lend report, the accounting of "what the user has" (scanned/spendable outputs) diverges from "what the protocol can actually use" (mature UTXOs), because a required state/membership check (coinbase maturity, analogous to `enterMarkets`) is omitted at the point funds are credited.

### Impact Explanation
Any miner (an unprivileged party crafting a valid Bitcoin transaction) can send a coinbase output to the multisig's external/branch/change/forward address. The processor reports it as received funds and may select it as a transaction input; the resulting transaction is consensus-invalid (`bad-txns-premature-spend-of-coinbase`) and will be rejected by the network, stalling signing/spending of the batch that included it — a denial of service on funds reported received that are not spendable.

### Likelihood Explanation
Requires a miner to mine a block paying the multisig script (moderately costly, but miners do this routinely for pool payouts, and any solo miner or pool can include such an output for free). Once present, the code path is deterministic — every scan of that block returns the immature output with no maturity filter anywhere in `scan_block`/`scan_transaction`/`get_outputs`.

### Recommendation
In `scan_block` (or in `get_outputs`/`scan_transaction`), skip `block.txdata[0]` or detect `tx.is_coinbase()` and either exclude such outputs entirely or track a maturity block on `ReceivedOutput` so `SignableTransaction::new` never selects inputs younger than 100 confirmations.

### Proof of Concept
Conceptual: on regtest, call `generatetoaddress 1 <multisig-p2tr-address>` (as the existing `send_and_get_output` test helper in `networks/bitcoin/tests/wallet.rs` already does — notably it then mines 100 extra blocks before scanning, implicitly working around this bug). Instead, scan the block containing the coinbase immediately:

```rust
let block = rpc.get_block(&rpc.get_block_hash(block_number).await.unwrap()).await.unwrap();
let outputs = scanner.scan_block(&block); // returns coinbase output
assert_eq!(outputs.len(), 1);
// outputs[0] is fed to SignableTransaction::new -> spends coinbase at height h
// broadcast fails: coinbase not mature until h+100
```

Caveat: I could not fully trace `processor/src/networks/bitcoin.rs::get_outputs` to confirm it does not filter coinbase outputs downstream; if it applies its own maturity check the impact is mitigated and this reduces to a latent footgun documented only in the `scan_block` doc comment.
