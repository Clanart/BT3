### Title
FROST signing accepts `Participant(0)` — attacker-controlled signer index bypasses the participant-validity check and is counted toward the threshold - (File: crypto/frost/src/sign.rs)

### Summary
`AlgorithmSignMachine::sign` builds the signing set `included` from attacker-controlled `HashMap<Participant, Preprocess>` keys (the `Participant` index is the user-controlled key). It enforces the documented invariant `0 < participant <= n` only on the upper bound (`included[included.len() - 1] > n`), and never rejects `Participant(0)`. Since `included` is sorted, index `0` lands in `included[0]`, passes the duplicate check, is counted in the `included.len() >= t` threshold check, is transcribed into the rho binding transcript, and is passed to `ThresholdKeys::view` for Lagrange interpolation. This is the direct analog of CVE-2022-46179: a security check conditioned on an attacker-supplied value where only part of the domain is validated, letting an out-of-domain value through.

### Finding Description
In `crypto/frost/src/sign.rs` (lines 290–313):

```rust
included.push(multisig_params.i());
for l in preprocesses.keys() { included.push(*l); }
included.sort_unstable();

if included.len() < usize::from(multisig_params.t()) { ... }
if u16::from(included[included.len() - 1]) > multisig_params.n() {
  Err(FrostError::InvalidParticipant(...))?;
}
for i in 0 .. (included.len() - 1) {
  if included[i] == included[i + 1] { Err(FrostError::DuplicatedParticipant(...))?; }
}

let view = self.params.keys.view(included.clone()).unwrap();
```

- `FrostError::InvalidParticipant` itself documents the invariant `0 < participant <= n` (crypto/frost/src/lib.rs:32), yet no code path checks `included[0] < Participant(1)` / `u16::from(included[0]) == 0`.
- An unauthenticated preprocess message — reached via `read_preprocess` → `Commitments::read` → `C::read_G`/`read_F` over untrusted bytes — keyed under `Participant(0)` is accepted into the signing set.
- The phantom signer is then appended to the rho transcript (`append_message(b"participant", ...)` for `l = 0`), assigned a binding factor via `B.calculate_binding_factors`, included in `B.bound(...)` during share verification in `complete`, and interpolated by `ThresholdKeys::view`/`ThresholdView`.

Consequences of admitting `Participant(0)`:
- **Threshold-policy bypass:** `included.len() >= t` is satisfied with only `t-1` real key holders. The t-of-n authorization policy is enforced against a set containing a non-existent member — the authorization check is bypassed by a user-controlled key.
- **Lagrange at index 0:** For set `S` containing `0`, the interpolation weight of every other member contains the factor `x_0 = 0` in its numerator (λ_i = Π_{j≠i} x_j/(x_j − x_i) evaluated at 0), so λ_i = 0 for all real participants, while λ_0 = 1 maps to the group-secret position (the verification share for index `0` is the group key itself). Honest participants emit shares `s_i = d_i + e_i·ρ_i + c·0·share_i` — i.e., shares over an attacker-shaped signing set carrying no threshold contribution — while `complete` still demands a share for index `0` equal to `nonce + c·x` (where `x` is the full group private key).
- **Offset misplacement:** `ThresholdView` applies any configured key offset (used by Serai's Taproot/schnorrkel integrations) to `included[0]`'s scalar. With `included[0] == 0`, the offset is assigned to the phantom instead of the legitimate lowest-indexed signer, so the honest shares are computed under a view whose authorization/offset layout does not match any real member set.

### Impact Explanation
An unprivileged party who can send a preprocess message to a signer (the normal FROST round-1 input surface) can cause honest participants to:

1. Treat a non-existent identity as a signer, satisfying `t` with fewer than `t` real participants — the signer-authorization check is bypassed.
2. Emit one-time signature shares bound to an unintended signer set (binding factors, Lagrange weights, and group-key offset placement all determined by the attacker's chosen index), burning the honest party's cached preprocess and forcing the session into a state where `complete` either fails on `InvalidShare(0)` or hits `InternalError`.

Because index `0`'s verification share is the group key, a full forgery additionally requires knowledge of the group secret; the concrete achieved primitive is induction of honest signature shares under an unauthorized/corrupted member set and disruption of the threshold policy — a bypass of the signer-set validity check that FROST's own error contract (`0 < participant`) promises.

### Likelihood Explanation
Reachable by any party able to deliver a round-1 preprocess to a FROST participant (the documented untrusted-bytes surface: `read_preprocess`/`Commitments::read`). The attacker needs no key material — only to key one preprocess under `Participant(0)`. Any session aggregating preprocesses by self-reported participant index accepts it, since only the maximum index is bounds-checked and duplicates/zero are never tested on the low end.

### Recommendation
In `AlgorithmSignMachine::sign` (and symmetrically anywhere `included`/participant indexes are validated), reject `Participant(0)` before sorting/interpolation:

```rust
if u16::from(included[0]) == 0 {
  Err(FrostError::InvalidParticipant(multisig_params.n(), included[0]))?;
}
```

Audit the same pattern in `dkg` (`ThresholdKeys::new`/`ThresholdView::new`, lagrange coefficient computation) to ensure `Participant(0)` is rejected at construction rather than silently interpolating to the group-secret position.
