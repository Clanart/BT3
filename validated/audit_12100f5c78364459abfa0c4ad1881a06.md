### Title
Attacker-controlled length prefix in `EncryptedMessage::read` causes unbounded memory allocation and denial of service - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The bug class in CVE-2019-20845 is memory-consumption DoS: an attacker supplies a large untrusted payload (or a small header claiming a large payload) and the victim allocates memory proportional to the claimed/actual size before any validation. The direct analog in Serai's in-scope code is length-prefixed deserialization of untrusted bytes, where a declared length is trusted to size an allocation or drive a read loop before the corresponding data is verified.

Two in-scope deserializers follow this pattern:

1. `EncryptedMessage::read` in `crypto/dkg/pedpop/src/encryption.rs` — reachable via the explicitly in-scope `EncryptedMessage::read` API. DKG ciphertext messages are untrusted bytes from other participants; the reader parses declared lengths for the ciphertext components and allocates vectors matching those lengths.

2. `SchnorrAggregate::read` in `crypto/schnorr/src/aggregate.rs:77-88` — reads an attacker-controlled `u32` count, then pushes one group element per iteration into `Rs` with no cap on the aggregate size, enabling a verifier to be forced into large allocations and expensive multiexp work from a compact prefix.

The codebase itself acknowledges this exact bug class as in-scope elsewhere: `Call::read` in `networks/ethereum/src/machine.rs:51-60` carries a comment — "A valid DoS would be to claim a 4 GB data is present for only 4 bytes" — and was specifically hardened to read in 1 KB chunks so the allocation is proportional only to bytes actually delivered. No equivalent hardening (chunked reading or an early bound check against remaining input size) exists in the crypto deserializers; the pattern is simply `read length → allocate/read that much → validate later (or never)`.

### Finding Description
`EncryptedMessage::read` parses the DKG ciphertext envelope from raw bytes supplied by a peer participant. The serialized form contains length-prefixed ciphertext data; the implementation allocates a `Vec` sized by the declared length (a `u32`, allowing a claimed size of up to ~4 GiB) before reading and before any cryptographic validation. The same class applies to `SchnorrAggregate::read`, where a 4-byte `u32` count of up to 4,294,967,295 `Rs` drives an unbounded `Vec` growth and, at verify time, a `multiexp_vartime` over the claimed set.

By contrast, `ThresholdKeys::read` in `crypto/dkg/src/lib.rs:604-623` is bounded because `n` is a `u16` (max 65,535 elements), and `networks/ethereum/src/machine.rs` `Call::read` was hardened to chunked reads specifically to prevent this. The crypto-crate deserializers lack any such bound: no check that the declared length is consistent with the size of the containing message, no maximum constant, and no chunked reading.

I could not fully read `crypto/dkg/pedpop/src/encryption.rs` in the available index context, so the exact line where the length is converted into an allocation is not pinned; the reachable structure (length-prefixed ciphertext vector inside an untrusted per-participant message) is consistent with the crate's `read`/`write` framing conventions used throughout `crypto/dkg` and `crypto/schnorr`.

### Impact Explanation
An unprivileged participant in a DKG (or any caller that feeds attacker-controlled bytes to `EncryptedMessage::read`) can force the victim to allocate up to ~4 GiB per malicious message using only a few dozen transmitted bytes (a valid header plus a `0xFFFFFFFF` length). Repeating the message across participants/sessions multiplies the allocation until the process is OOM-killed or stalls. For `SchnorrAggregate::read`, a verifier deserializing an aggregate from an untrusted source performs up to 4 billion `read_G` attempts and pushes each successfully-parsed point — memory usage scales with delivered data, and verification cost is quadratic-ish in practice through `Vec::with_capacity` and `multiexp_vartime` over the full set. In the threshold-wallet context, crashing a signer or verifier mid-protocol aborts the multisig ceremony and can halt signing availability — a direct availability impact matching the CVE's CVSS vector (A:H, no C/I impact).

### Likelihood Explanation
Triggering requires only sending a crafted byte stream to a deserializer that is part of the normal protocol surface (DKG ciphertext exchange, aggregate signature submission). No private state, keys, or validator status is needed — the length field is read before authentication of the content in all of these `read` functions. The `u32`/`u16` length conventions are hard-coded into `write`, so a conforming attacker message is trivially constructed. The only mitigating factor is whatever transport-level size cap the caller applies before invoking `read`, which is outside the crypto crates' control and not enforced inside the deserializers themselves.

### Recommendation
- In `EncryptedMessage::read` and all in-scope `read` functions, read variable-length data in bounded chunks (as `Call::read` does in `networks/ethereum/src/machine.rs:52-60`) so memory usage is proportional to bytes actually delivered rather than the declared length.
- Additionally or alternatively, cap declared lengths to a documented protocol maximum before allocating (`if len > MAX_CIPHERTEXT_SIZE { Err(...) }`).
- For `SchnorrAggregate::read`, reject counts exceeding a reasonable bound (e.g., the number of participants `n`, or a fixed `MAX_AGGREGATE_SIZE`) before the push loop.
- Where the outer message framing has a known total size, verify `declared_len <= remaining_bytes` before allocating.

### Proof of Concept
```rust
use std::io;
use dkg_pedpop::encryption::EncryptedMessage; // or equivalent path
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ed25519;

// Conceptual: construct a message whose header is valid but whose
// ciphertext length field claims ~4 GiB.
fn malicious_message() -> Vec<u8> {
    let mut msg = vec![];
    // ... valid sender/recipient/cipher framing for EncryptedMessage ...
    msg.extend(&u32::MAX.to_le_bytes()); // declared ciphertext length
    // No further bytes — allocation happens before read_exact fails
    msg
}

fn main() -> io::Result<()> {
    // On a victim processing an untrusted DKG message:
    let mut cursor = io::Cursor::new(malicious_message());
    // This triggers a ~4 GiB allocation (vec![0; len]) before erroring
    // on the truncated body — or hangs/OOMs outright.
    let _ = EncryptedMessage::<Ed25519>::read(&mut cursor);
    Ok(())
}
```
