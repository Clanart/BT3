### Title
ERC20-to-CW20 pointer's `send`/`send_from` reports a flat, unadjusted `amount` to the CosmWasm receiver hook, allowing fee-on-transfer or non-standard ERC20 tokens to desynchronize actual balance movement from the credited amount - (File: `example/cosmwasm/cw20/src/contract.rs`)

### Summary
The ERC20-to-CW20 pointer contract (the CosmWasm side of the ERC20↔CW20 bridge) implements `send`/`send_from` by delegatecalling the wrapped ERC20's `transfer`/`transferFrom` with the caller-supplied `amount`, and then unconditionally forwards that same `amount` inside a `Cw20ReceiveMsg` to the destination contract — without ever verifying that the pointer actually received/moved that amount of the underlying ERC20 token.

### Finding Description

`execute_send`/`execute_send_from` then take that exact `amount` and package it into a `Cw20ReceiveMsg` sent to the destination contract's `receive()` hook, asserting to the recipient that `amount` tokens were received: [2](#0-1) [3](#0-2) 

The helper that turns the `Cw20ReceiveMsg` into a `WasmMsg::Execute` performs no balance verification whatsoever — it just serializes the message and dispatches it: [4](#0-3) 

Crucially, the pointer's own `query_balance`/`erc20_balance` path queries the wrapped ERC20's real `balanceOf` live (no internal ledger) at query time: [5](#0-4) 

so the pointer contract itself never notices a fee-on-transfer discrepancy — but any downstream CosmWasm contract receiving the `Cw20ReceiveMsg` has no way to know it is being lied to about the amount, unless it separately queries the pointer's `balance` before and after. This is the direct sei-chain analog of the Timeswap Convenience bug: a bridging/wrapper layer forwards a flat, caller-specified amount as ground truth to a downstream consumer instead of verifying the amount actually moved, and any ERC20 with fee-on-transfer, deflationary burn-on-transfer, or rebasing behavior breaks the invariant that "amount transferred equals amount reported."

### Impact Explanation
Any CosmWasm contract (e.g. a CW20-aware AMM, vault, or lending market) that trusts the `amount` field of an incoming `Cw20ReceiveMsg` from an ERC20-to-CW20 pointer — rather than independently verifying its own balance delta of the pointer token — can be tricked into crediting a sender for more value than was actually transferred if the underlying ERC20 token is fee-on-transfer, deflationary, or otherwise non-standard. This is a direct path to fund loss/inflation of internal accounting for any protocol built to consume CW20 `Send`/`SendFrom` deposits through this specific pointer type, reachable by any unprivileged user who deploys a pointer for such a token and calls `send`/`send_from`.

### Likelihood Explanation
Likelihood is bounded by two things: (1) an attacker/user needs an ERC20 token with fee-on-transfer or similarly non-standard transfer semantics registered as a CW20 pointer — this is permissionless (any user can register a pointer for any deployed ERC20 via the `AddCW20` precompile path), and (2) a downstream CosmWasm contract must trust the `Cw20ReceiveMsg.amount` field without independently re-querying/verifying balances, which is a common (though not universal) pattern for CW20 deposit-accepting contracts. Given pointer registration is permissionless and this bridging contract is a first-class, documented mechanism in the codebase for wrapping arbitrary ERC20 tokens as CW20, the precondition is realistically reachable.

### Recommendation
In `execute_send`/`execute_send_from` (and analogous callback paths), do not trust the caller-supplied `amount` as the value reported to the recipient's receive hook. Instead, query the pointer's ERC20 balance (or the pre/post balance of the pointer contract on the wrapped ERC20) immediately before and after the delegatecall transfer, and use the observed balance delta as the `amount` forwarded in the `Cw20ReceiveMsg`. Alternatively, explicitly document (and ideally enforce via an allowlist or a standards-compliance check) that only fully ERC20-standard-compliant tokens (no transfer fees, no rebasing) may be wrapped via this pointer mechanism, and reject/flag pointer registration or `send` operations otherwise.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 token `FeeToken` on the EVM side of Sei (e.g., transfers deduct 5% and burn or redirect it).
2. Register an ERC20-to-CW20 pointer for `FeeToken` (permissionless, via the standard pointer registration precompile flow used in `contracts/test/ERC20toCW20PointerTest.js`).
3. Deploy a simple "vault" CosmWasm contract that implements the `Cw20ReceiveMsg` hook and credits `msg.amount` internally as a claim on its own token balance without independently checking its own live pointer balance.
4. Call `send { contract: vault, amount: 1000, msg: ... }` on the ERC20-to-CW20 pointer contract. The `transfer` delegatecall inside `transfer()`/`execute_send` (`example/cosmwasm/cw20/src/contract.rs:227-248`) moves only 950 actual tokens (5% fee deducted) into the vault's real ERC20 balance as tracked by the wrapped token, but the `Cw20ReceiveMsg` dispatched to the vault (`example/cosmwasm/cw20/src/contract.rs:95-114`) still reports `amount: 1000`.
5. The vault credits the sender for 1000 tokens' worth of claim, while only 950 tokens of real value were actually moved — a 50-token discrepancy the vault will eventually be unable to honor for all depositors, i.e., an insolvency/fund-loss condition.

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

/// Helper to convert a Cw20ReceiveMsg into an EvmMsg
pub fn cw20receive_into_cosmos_msg<T: Into<String>, C>(contract_addr: T, message: Cw20ReceiveMsg) -> StdResult<CosmosMsg<C>> 
where
    C: Clone + std::fmt::Debug + PartialEq + JsonSchema,
{
    let msg = message.into_binary()?;
    let execute = WasmMsg::Execute {
        contract_addr: contract_addr.into(),
        msg,
        funds: vec![],
    };

    Ok(execute.into())
}
