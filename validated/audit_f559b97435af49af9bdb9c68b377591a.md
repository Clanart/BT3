## Title
Stale line-selection indices are blindly re-applied against a freshly re-generated diff during partial commits, allowing silent corruption of committed content - (File: `app/src/lib/git/apply.ts`)

## Summary
The Superposition report's broken invariant is: a user approves an action based on an expected state, but the system executes the action against a different, unverified state at execution time, with no check that the outcome still matches what was approved. The GitHub Desktop analog is the "partial commit" (line/hunk selection) feature: the user selects specific diff lines to stage by numeric index against a diff snapshot rendered at time T1, but at commit time Desktop silently regenerates a brand-new diff and reapplies those same numeric indices to it without validating that the underlying content at those indices is unchanged.

## Finding Description
When a user selects individual lines/hunks of a file to include in a commit, the selection is stored as a set of absolute line indices tied to a specific diff object (`DiffSelection.isSelected(absoluteIndex)`), computed by `formatPatch` in [1](#0-0)  against `hunk.unifiedDiffStart + lineIndex`.

Critically, `applyPatchToIndex` does not reuse the diff the user actually reviewed and selected lines against. Instead, immediately before staging, it re-fetches a brand-new diff straight from disk: [2](#0-1) 

That freshly-fetched diff (not the one shown to the user) is passed into `formatPatch`, which reapplies the *old* `file.selection` indices to the *new* hunk structure: [3](#0-2) 

The generated patch is then applied with `git apply --cached --unidiff-zero`, i.e. with zero lines of context, so `git apply` performs no surrounding-context validation of the hunks: [4](#0-3) 

Desktop's own developers acknowledge this staleness problem exists for the UI-facing selection state, but only partially mitigate it (removing indices that are no longer selectable) rather than verifying content equivalence, and this mitigation only runs while the Changes view is actively refreshed — it is not re-checked immediately before `applyPatchToIndex` runs: [5](#0-4) 

If the working directory file is modified between the last diff/selection computed in the UI and the moment `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` executes (for example due to a repository-provided git hook such as `post-checkout`/`post-merge` that Desktop invokes when operating on a cloned/fetched malicious repository, or any other background process that touches tracked files), the same absolute line indices in the new diff can now correspond to entirely different content. Because `--unidiff-zero` disables context checking, `git apply` will not fail on a mismatch — it silently stages whatever content is now at those line offsets.

## Impact Explanation
This breaks the guarantee that "what the user selected in the diff viewer is what gets committed." An attacker who controls a cloned/fetched repository (e.g., via a malicious `post-checkout` or `post-merge` hook bundled in the repo) can cause content the user never reviewed or approved to be silently included in a commit that the user believes only contains their reviewed selection. This falls squarely into the allowed impact category of "silent corruption of what the user commits or pushes," analogous to the sandwich attack in the original report where the user's approved parameters (selected withdrawal amount / selected diff lines) do not match what is actually executed.

## Likelihood Explanation
Exploitation requires: (1) a partial/hunk-based commit workflow (a supported and common Desktop feature, tracked via `partialCommits` stats at [6](#0-5) ), and (2) a way for the attacker-supplied repository to trigger a file modification between diff display and commit execution — most plausibly via a git hook shipped in a cloned/fetched malicious repository. Desktop does invoke git hooks during normal operations (`noVerify` toggles specifically hook-skipping behavior for commits, implying hooks are otherwise honored). This makes the timing window realistic without requiring local/physical access, admin rights, or pre-existing malware — the malicious content originates entirely from the untrusted repository itself.

## Recommendation
- Do not re-fetch a brand-new diff at apply time; instead, use the exact diff object (and content hashes) that the selection was computed against, or
- Before calling `applyPatchToIndex`, re-verify that the freshly-fetched diff is content-identical (not just index-identical) to the diff the selection was derived from, and abort/re-prompt if it has changed.
- Consider using `git apply` with full context (not `--unidiff-zero`) for partial-commit patches so mismatched context causes a hard failure rather than a silent wrong-location apply.

## Proof of Concept
1. Clone an attacker-controlled repository containing a `post-checkout` (or similarly triggered) hook that rewrites a tracked file's content shortly after checkout/any git operation.
2. In Desktop, open the file's diff and select a subset of lines/hunks to commit (partial commit).
3. Before clicking "Commit," the malicious hook fires (or any other background write occurs) and alters the file at the same line offsets the user selected.
4. Click "Commit." `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` [7](#0-6)  and reapplies the stale `file.selection` indices via `formatPatch` [1](#0-0) , staging the attacker's substituted content instead of what the user reviewed, with `git apply --unidiff-zero` performing no context verification to catch the mismatch.
