### Title
Bridge `handleERC20Transfer` permanently reverts (and blocks nonce advancement) when a blacklisting ERC20 token's operator sends funds to a blacklisted recipient - (File: contracts/service_chain/bridge/BridgeTransferERC20.sol)

### Summary
`handleERC20Transfer` in `BridgeTransferERC20.sol` performs `IERC20(_tokenAddress).safeTransfer(_to, _value)` directly to the arbitrary recipient address `_to` extracted from the request, with no fallback if the transfer reverts. [1](#0-0) 

### Finding Description
`handleERC20Transfer` is called by bridge operators to fulfill a cross-chain ERC20 value-transfer request. Before the actual token movement, the function performs bookkeeping: it validates and records the nonce, marks the request tx hash as handled, updates `handleNoncesToBlockNums`, and advances `lowerHandleNonce`/`upperHandleNonce` via `_updateHandleNonce`, and only then attempts the transfer: [2](#0-1) 

`_updateHandleNonce` advances `lowerHandleNonce` sequentially, stopping at the first nonce whose `handleNoncesToBlockNums` entry is unset: [3](#0-2) 

If the underlying ERC20 token supports a blacklist (e.g. bridged USDC, as referenced by the analog report) and the request's `_to` address is blacklisted, `IERC20(_tokenAddress).safeTransfer(_to, _value)` will revert. Because Solidity transactions are atomic, this revert unwinds *all* the state changes made earlier in the same call — including the nonce bookkeeping, the handled-request-hash marking, and the vote registration performed inside `_voteValueTransfer`. The request can never be successfully "handled" as long as the recipient remains blacklisted, since every operator's attempt to call `handleERC20Transfer` for that request will hit the same revert.

This differs from the reported analog (`VestingEscrow.recoverERC20`) mainly in that this is not merely an admin recovery utility — it is the core bridge fulfillment path reachable by any bridge operator relaying a real user's cross-chain transfer request, and the sequential nonce design (`lowerHandleNonce`, `_lowerHandleNonceCheck`) means a stuck low nonce can hold back the housekeeping/pruning of the block-number recovery window used by `ValueTransferRecovery` (used to replay pending events after node restart), since `recoveryBlockNumber` is only advanced while iterating from `lowerHandleNonce` forward without gaps.

### Impact Explanation
- The specific value-transfer request to a blacklisted recipient can never be completed; the corresponding tokens locked/burned on the request side are permanently unfulfillable on the handle side (Medium: value gets stuck, denial of a specific user's cross-chain transfer, not a case of unauthorized value movement or supply inflation).
- Because `lowerHandleNonce` cannot advance past the stuck nonce, `recoveryBlockNumber` progression and pruning of `handleNoncesToBlockNums`/`closedValueTransferVotes` for nonces beyond the stuck one is degraded, which can affect the efficiency/correctness of `ValueTransferRecovery`'s event replay window over time, though this does not itself cause fund theft.

### Likelihood Explanation
Reaching this path requires: (1) the bridge being configured for an ERC20 token that implements an address blacklist (e.g., a bridged stablecoin like USDC), and (2) a `_to` recipient address becoming blacklisted by the token issuer (a third-party action outside the bridge). Given real-world stablecoin bridging is common and blacklisting events do occur, this is plausible but not attacker-controlled in the classic sense — it requires an external blacklist decision. It is reachable purely through the normal operator-submitted `handleERC20Transfer` transaction flow, with no special privilege beyond the existing `onlyOperators` role which is expected to process routine requests.

### Recommendation
Use a non-reverting/try-catch transfer pattern in `handleERC20Transfer` (e.g., an internal escrow-and-claim mechanism, or wrapping the `safeTransfer` call in a low-level call with failure handling that credits the recipient's balance for later withdrawal by an alternate address) so that a single blacklisted recipient cannot block nonce advancement or permanently strand the corresponding funds. Consider decoupling the nonce/vote bookkeeping success from the token transfer success, or allowing recovery/redirection of a stuck transfer to an alternate address.

### Proof of Concept
1. Deploy `Bridge` in non-mint-burn mode with a registered ERC20 token that supports blacklisting (e.g., mimic USDC's `isBlacklisted`/reverting `transfer`).
2. A user requests an ERC20 transfer to address `Bob` via `requestERC20Transfer`, emitting `RequestValueTransfer` with nonce `N`.
3. Before operators handle the request, the token issuer blacklists `Bob`.
4. An operator calls `handleERC20Transfer(...)` for nonce `N` targeting `Bob`; execution reaches `IERC20(_tokenAddress).safeTransfer(Bob, value)` at [4](#0-3) 
 which reverts because `Bob` is blacklisted, reverting the entire transaction and rolling back the nonce/vote bookkeeping performed at lines 45-54.
5. Every subsequent attempt by any operator to handle nonce `N` reverts identically; `lowerHandleNonce` can never advance past `N` per `_updateHandleNonce`'s sequential-scan logic at [5](#0-4) 
, permanently stalling the bridge's handled-nonce/recovery-block-number progression for this token's request stream.

    // _updateHandleNonce increases lower and upper handle nonce after the _requestedNonce is handled.
    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }

    function _lowerHandleNonceCheck(uint64 _requestedNonce) internal {
        require(lowerHandleNonce <= _requestedNonce, "removed vote");
    }
