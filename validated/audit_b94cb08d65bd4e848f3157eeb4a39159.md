Confirmed: `removeRepository` in `app/src/lib/stores/repositories-store.ts` only deletes the Dexie DB record and clears tags-to-push, and `_removeRepository`/`_relocateRepository` in `app-store.ts` never call any counterpart to `addSafeDirectory` to remove the path from Git's global `safe.directory` list. There is no `removeSafeDirectory`/`unsetSafeDirectory` function anywhere in the codebase — the trust decision, once granted, is permanent and keyed only by filesystem path, never revoked.

### Title
Removing/relocating an untrusted repository never revokes its `safe.directory` trust exception, allowing hook execution for any future repository placed at the same path - (File: app/src/lib/stores/app-store.ts)

### Summary
When Desktop encounters a repository whose ownership looks "unsafe" (Git's dubious-ownership check), the user can click "Trust Repository," which calls `addSafeDirectory` and permanently whitelists that absolute path in the user's global Git config via `safe.directory`. This trust is bound only to the **path string**, never to the specific repository content or ownership at the time of trust. Desktop provides no mechanism to revoke this trust when the repository is removed from Desktop, moved away, or replaced by different content at the same path.

### Finding Description
`addSafeDirectory` in `app/src/lib/git/config.ts` adds a path to Git's global `safe.directory` allow-list: [1](#0-0) 

This is invoked from two UI surfaces when the user trusts a directory: [2](#0-1) [3](#0-2) 

Once trusted, `getRepositoryType` will always classify that path as safe rather than `unsafe`, regardless of who now owns the directory contents: [4](#0-3) 

However, when a repository is removed from Desktop, only the Dexie database row is deleted — there is no call that removes the path from `safe.directory`: [5](#0-4) [6](#0-5) 

The same gap exists on relocation: if the user relocates a repository, the previously trusted path is simply dropped from Desktop's records, again without ever revoking the Git-level trust: [7](#0-6) 

A `grep` across the codebase confirms there is no `removeSafeDirectory` or equivalent `git config --global --unset safe.directory` call anywhere in the repo — trust is write-only.

This mirrors the oracle-quorum bug class exactly: a piece of "membership/trust state" (`safe.directory` entry) that should be atomically cleared when the trusted entity is removed/revoked is instead left intact, so a *new* untrusted entity that later occupies the same identifier (path) inherits the old trust and is treated as validated without re-verification.

### Impact Explanation
Git explicitly documents that `safe.directory` exists because working in a repository owned by another user can cause automatic execution of files (e.g., through configured hooks, `core.fsmonitor`, or other repo-controlled config values honored once a directory is deemed "safe"). Any attacker who can cause content to be written to a path a victim previously trusted and later abandoned in Desktop (shared machines, temp directories, network shares, CI runners reusing a workspace, USB/removable media reused across users, or a directory recreated after `rm -rf` + re-clone by another party) can plant a malicious repository there. Because Desktop never revokes the `safe.directory` entry, Git will silently treat the attacker's repository as trusted, bypassing the exact warning ("Adding untrusted repositories may automatically execute files in the repository") that the UI itself displays and enabling code execution outside the user's expectation — a direct violation of the "trusted-once-forever" invariant, comparable to the oracle bug's stale-report acceptance after revocation.

### Likelihood Explanation
Requires: (1) a user having trusted a repository path at some point, and (2) that same path later being repopulated with attacker-controlled Git content (shared/reused directories, CI agents, mounted/removable drives, multi-user machines) after the user removes/relocates the original repo in Desktop. This does not require local/physical access from the attacker beyond what's already in-scope (attacker controls content that ends up at that path, e.g., via a shared clone location, restored snapshot, or symlink), and no unnatural extra steps are needed from the victim beyond the one-time normal "Trust Repository" click that Desktop's own UI encourages.

### Recommendation
When a repository is removed from Desktop (`_removeRepository`) or relocated away from a trusted `unsafe`-flagged path (`_relocateRepository`), invoke a new `removeSafeDirectory(path)` helper that runs `git config --global --unset-all safe.directory <path>` (mirroring the existing `removeGlobalConfigValue` pattern already present in `app/src/lib/git/config.ts`) to revoke the trust exception. Additionally, re-validate ownership/trust at the time of use rather than relying solely on a persisted path-based allow-list.

### Proof of Concept
1. Clone/create a repository at a path on a shared or reusable location, e.g. `/shared/workspace/project`, where it is initially owned by a different user (or simulate via `GIT_TEST_ASSUME_DIFFERENT_OWNER=1`).
2. In Desktop, add it as an existing repository; Desktop reports it "unsafe" and shows "Trust Repository." Click it — `addSafeDirectory('/shared/workspace/project')` runs, permanently adding the path to the global `safe.directory` list.
3. Remove the repository from Desktop ("Remove…") or relocate it elsewhere. Desktop deletes the Dexie record via `repositoriesStore.removeRepository` but performs no `safe.directory` cleanup.
4. An attacker (a different local user/process/CI job with write access to that shared path) deletes the old contents and places a malicious Git repository at `/shared/workspace/project`, including a crafted hook or `core.*` config designed to execute on the next Git operation.
5. The victim (or another user relying on the same trust, or the same victim reopening/re-adding the path) performs any Desktop operation that invokes Git against that path. `getRepositoryType`/Git see the path is in `safe.directory` and skip the ownership warning entirely — the attacker's repository is treated as trusted and its hook/config content can execute, with no prompt ever shown to the user.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

  public async _relocateRepository(repository: Repository): Promise<void> {
    const path = await showOpenDialog({ properties: ['openDirectory'] })

    if (path === null) {
      return
    }

    const rt = await getRepositoryType(path)

    if (rt.kind === 'regular') {
      // The repository has moved, so any main worktree we recorded before now
      // points at where it used to be. Resolve it again from the new location.
      await this.repositoriesStore.updateRepositoryPath(
        repository,
        rt.topLevelWorkingDirectory,
        rt.gitDir,
        await this.findMainWorktreePath(rt.topLevelWorkingDirectory)
      )
    } else if (rt.kind === 'unsafe') {
      // Git refuses to run in a repository it considers unsafe, so there's no
      // resolving the main worktree here. Drop the recorded path rather than
      // keep one we know is stale.
      await this.repositoriesStore.updateRepositoryPath(
        repository,
        path,
        undefined,
        undefined,
        true
      )
    } else {
      this.emitError(new Error(this.getInvalidRepoPathsMessage([path])))
    }
  }

  public async _removeRepository(
    repository: Repository | CloningRepository,
    moveToTrash: boolean
  ): Promise<void> {
    try {
      if (moveToTrash) {
        try {
          await shell.moveItemToTrash(repository.path)
        } catch (error) {
          log.error('Failed moving repository to trash', error)

          this.emitError(
            new Error(
              `Failed to move the repository directory to ${TrashNameLabel}.\n\nA common reason for this is that the directory or one of its files is open in another program.`
            )
          )
          return
        }
      }

      if (repository instanceof CloningRepository) {
        this._removeCloningRepository(repository)
      } else {
        await this.repositoriesStore.removeRepository(repository)
      }
    } catch (err) {
      this.emitError(err)
      return
    }

    const allRepositories = await this.repositoriesStore.getAll()
    if (allRepositories.length === 0) {
      this._closeFoldout(FoldoutType.Repository)
    } else {
      this._showFoldout({ type: FoldoutType.Repository })
    }
  }
