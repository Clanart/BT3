### Title
Scanner reports immature coinbase outputs as spendable, causing the multisig to sign transactions that consensus will reject — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`Scanner::scan_block` iterates over **every** transaction in a block, including `block.txdata[0]` (the coinbase). Coinbase outputs are bound by Bitcoin's 100-block maturity rule and cannot be spent until then. Because the scanner reports them as ordinary `ReceivedOutput`s, the scheduler/signing pipeline will treat them as available balance, construct a `SignableTransaction` spending them, and produce a fully signed transaction that every node rejects as a consensus violation — the funds are effectively frozen until maturity, and the scheduled payments are blocked. This is the Serai analog of "the balance exists on paper but was never actually usable" (the Tokemak finding where `sellTokenBalance` can never cover the swap).

### Finding Description

`Scanner::scan_block` scans the coinbase transaction without any maturity check:

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

The doc comment at lines 216-220 acknowledges the issue ("This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed") but `ReceivedOutput` carries no height/maturity metadata — only `offset`, `output`, and `outpoint` (lines 89-97) — so no downstream consumer can distinguish an immature coinbase output from a normal one.

Downstream, `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` sums `input.output.value` into `input_sat` (line 175), builds `TxIn`s from the outpoints (lines 177-185), and only validates internal accounting (`input_sat < payment_sat + needed_fee` → `NotEnoughFunds`, lines 215-221). There is no consensus-maturity validation anywhere; a coinbase input passes all checks, gets signed via `sign`, and the broadcast transaction is rejected by the network. Unlike the Tokemak case where `InsufficientBalance` reverts cleanly, here the failure surfaces only at broadcast time — after threshold signatures have been produced — and the output remains in the scheduler's UTXO set.

### Impact Explanation

Funds reported received are not spendable. A coinbase output paying a Serai multisig script is registered in the scanner, counted in `self.utxos`/`balance` in `processor/src/multisigs/scheduler/utxo.rs` (`schedule`, lines 388-409), and selected as an input for pending payments. The resulting transaction is invalid for ~100 blocks. If the scheduler marks the UTXO as consumed (drained at line 358) and the payment as executed (`executing.push`, line 403), the burn/payment appears fulfilled while the TX can never confirm — payments stall and the accounting diverges from on-chain reality until manual intervention or re-scan logic kicks in. Severity: Medium-High (liveness/stuck-funds, recoverable after maturity but protocol-breaking in the interim).

### Likelihood Explanation

Any miner is an unprivileged party who can set their coinbase output `script_pubkey` arbitrarily. Paying a Serai multisig address in a coinbase requires no cooperation — it is exactly the "Bitcoin transaction they send" reachable-input class. Mining pools occasionally do pay third-party addresses from coinbase (e.g., pool payout schemes, "coinbase-to-address" donations), so this is not purely adversarial-only. `scan_transaction` matches solely on `script_pubkey` (line 205), so a coinbase output to any registered script is captured unconditionally.

### Recommendation

In `Scanner::scan_block`, skip `block.txdata[0]` (or better, scan it but tag the resulting `ReceivedOutput`s with a maturity height), and have the caller only release them to `get_outputs` once `block_height + 100 <= current_height`. Alternatively, extend `ReceivedOutput` with an `earliest_spendable_height` field populated at scan time, and filter in `SignableTransaction::new` / the scheduler's `add_outputs` so immature inputs never enter `self.utxos`.

### Proof of Concept

1. Register key `K` with the scanner (`Scanner::new(K)`).
2. Mine a regtest block whose coinbase pays `p2tr_script_buf(K)` 50 BTC (`block.txdata[0].output[0].script_pubkey == p2tr(K)`).
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` for that coinbase output — indistinguishable from a normal payment.
4. Call `SignableTransaction::new(vec![that_output], payments, change, None, fee)` — it succeeds (all balance checks pass since `input_sat` includes the 50 BTC).
5. Sign and broadcast: Bitcoin Core rejects with `bad-txns-premature-spend-of-coinbase`. The output was "received" yet the funds are not spendable, and any payment batched with it is stuck behind an invalid transaction.

Caveat: I could not fully verify whether `processor/src/networks/bitcoin.rs::get_outputs` applies its own coinbase filtering before returning outputs to the scheduler (the indexed snippet only shows it calling the scanner). If it filters `txdata[0]` itself, the bug is mitigated at that layer, but the primitive in `networks/bitcoin` remains unsafe-by-default, which is exactly the documented misuse pattern this analog class warns about.
