### Title
Recursive clone explicitly disables Git's anti-symlink clone protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), enabling file writes outside the repo - (`File: app/src/lib/git/clone.ts`)

### Summary
GitHub Desktop's `clone()` function builds the environment for every `git clone --recursive` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` [1](#0-0) . This variable is Git's own internal guard (added to fix the symlinked-`.git`-via-submodule attack class, CVE-2024-32002) that prevents a malicious repository/submodule from tricking Git into writing checkout files through a symlink that escapes the intended worktree. By forcing this flag to `false` on every clone, Desktop reintroduces exactly the class of bug Git's upstream protection was designed to close, for any repository URL the user clones (including URLs opened via `x-github-client://openRepo` deep links or "Clone" actions on a browsed GitHub repo).

### Finding Description
The `clone()` function first performs Desktop's own path-traversal backstop, `isClonePathSensitive()`, which only checks that the *destination directory* isn't a sensitive location on the local machine [2](#0-1) . That check says nothing about what happens *inside* the clone target after Git starts checking out attacker-controlled submodule trees. Immediately after that check, the function constructs the `env` object passed to the actual `git clone --recursive` invocation and explicitly disables Git's clone protection:

```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
...
args.push('--', url, path)
await git(args, __dirname, 'clone', opts)
``` [3](#0-2) 

`--recursive` means submodules are checked out as part of the same operation, which is precisely the scenario Git's protection targets: a malicious repository can define a submodule whose path collides (via case-folding, Unicode normalization, or a symlink placed in the tree) with the top-level `.git` directory, so that files Git subsequently writes for that submodule's checkout land through a symlink outside the intended working directory. Git's fix for this (CVE-2024-32002) is gated by an internal check that this env var, when explicitly set to `false`, disables. The `git()` helper in `core.ts` merges `opts.env` (which carries this value) into the final child-process environment and nothing downstream re-enables the protection [4](#0-3) .

This mirrors the root cause pattern in the source report: a protective check is computed/positioned correctly at a high level (`isClonePathSensitive` = "the liquidation/health check"), but a lower-level, more authoritative guard (`GIT_CLONE_PROTECTION_ACTIVE` = Git's own core anti-escape check, analogous to the delegation-slash step) is neutralized before the actual state-mutating operation (the recursive checkout / the slash), so the surface-level guard gives a false sense of safety while the underlying primitive is left exploitable.

### Impact Explanation
An attacker who controls a Git repository (or a fork/submodule reachable via a `x-github-client://openRepo`/"Clone" deep link, or a repository the victim is invited to clone) can craft a submodule tree that exploits the symlink checkout escape that `GIT_CLONE_PROTECTION_ACTIVE` exists to block. Because Desktop forces this protection off for every clone, a victim who simply clones the attacker's repository (the normal Desktop workflow) can have arbitrary files written outside the intended repository directory — potentially including startup files, shell profiles, or other locations reachable from the resolved clone path — resulting in file write outside the repo and a path to code execution on next shell/editor launch. This satisfies the "attacker controls a cloned/fetched repository ... result is code execution [or] file write ... outside the repo" impact criterion directly.

### Likelihood Explanation
No unnatural user interaction is required beyond the ordinary "Clone this repository" flow that Desktop is built around (including clone-from-URL/deep-link flows) [5](#0-4) . The disabling of the protection is unconditional and applies to every clone, not a rare edge case, and `--recursive` submodule cloning is the default behavior in `clone()` [6](#0-5) . The only mitigating factor is that the local, application-level `isClonePathSensitive()` check still blocks a small, fixed list of sensitive destinations, but it does not address symlink escapes originating from *within* the cloned tree/submodules, which is the exact gap `GIT_CLONE_PROTECTION_ACTIVE` closes.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override from `clone()` so Git's built-in anti-symlink clone protection remains active for recursive/submodule clones. If this override was added to work around a specific compatibility issue, it should instead be scoped narrowly (e.g., only for verified-safe recursive submodule paths) rather than globally disabling the guard for every clone of an arbitrary, potentially attacker-controlled URL.

### Proof of Concept
1. Attacker creates a public repository with a top-level submodule (or nested submodule) whose configured path is engineered to alias the `.git` directory on a case-insensitive or Unicode-normalizing filesystem (the same technique used in CVE-2024-32002 PoCs), and which contains a symlink pointing outside the working directory.
2. Attacker shares the repository URL, or a `x-github-client://openRepo?url=...` deep link, with the victim.
3. Victim clones the repository through Desktop's normal "Clone repository" UI or by opening the link, invoking `clone()` in `app/src/lib/git/clone.ts`.
4. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` in the spawned `git clone --recursive` process, Git's checkout-time symlink protection is skipped, and the attacker's submodule checkout writes a file through the symlink to a location outside the intended clone directory.
5. Depending on the target path chosen by the attacker (e.g., a shell rc file, editor config, or Git hook path reachable outside the repo), this results in a persistent file write outside the repository and a path to code execution the next time the victim opens a shell/editor or runs Git again.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
