### Title
Identity encryption key accepted in PedPoP `EncryptionKeyMessage`, exposing secret shares under a publicly computable ChaCha20 key - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG encrypts each secret share with a key derived from an ECDH between a fresh ephemeral scalar and the recipient's advertised `enc_key`. `EncryptionKeyMessage::read` accepts any canonical point — including the identity — because it uses `Ciphersuite::read_G`, which (unlike FROST's `Curve::read_G`) performs no identity rejection. An unprivileged DKG participant who registers `enc_key = identity` causes every honest sender to compute `ecdh(k, identity) = identity`, so the ChaCha20 key protecting that share is `H(context || identity_bytes)` — publicly computable. Anyone who obtains the transmitted `EncryptedMessage` can decrypt the share.

### Finding Description
`EncryptionKeyMessage::read` (encryption.rs:57-59) reads `enc_key` via `C::read_G`, which is `Ciphersuite::read_G` (ciphersuite/src/lib.rs:91-101). That decoder only enforces canonical encoding; the identity point passes. The identity-rejecting variant (`Curve::read_G` in frost/src/curve/mod.rs:125-131) exists but is not used here.

The key is stored unchecked in `Decryption::register` (encryption.rs:351-362) and consumed in `encrypt` (encryption.rs:135-168), where `ecdh::<C>(&key, to)` computes `to * k`. With `to` = identity, the result is always identity, and `cipher` (encryption.rs:101-133) derives the ChaCha20 keystream from `context || identity.to_bytes()` — no secret material. The share ciphertext to that participant is therefore encrypted under a key any third party can recompute. No other validation path (`verify_r1`, `generate_secret_shares`, `calculate_share` in pedpop/src/lib.rs) checks `enc_key` for identity either.

### Impact Explanation
Every `EncryptedMessage<C, SecretShare>` produced for the malicious participant is decryptable by anyone who observes it (authenticated channels protect against modification, not confidentiality of the payload to a public key). The secret share — meant to be known only to its recipient — is leaked publicly, recovering a participant's DKG key share to passive observers. This is precisely the "untrusted bytes reach a crypto path without sanitization" analog: attacker-supplied bytes (`enc_key`) flow unvalidated into ECDH.

### Likelihood Explanation
Requires only a malicious or compromised DKG participant (or a key-registration message forgery where channel authentication is weak). No brute force, no threshold collusion — a single participant registers identity as its key and all incoming shares become public. Reachable purely with public inputs to `EncryptionKeyMessage::read` / `EncryptedMessage::read`.

### Recommendation
Reject the identity point for `enc_key` in `EncryptionKeyMessage::read` (or in `Decryption::register`/`Encryption::encrypt`), mirroring the identity check in `Curve::read_G`. Similarly, reject identity `msg.key` in `EncryptedMessage::read`, since `ecdh` with an identity ephemeral key also yields a publicly known shared secret (for a message the sender knows the plaintext of, this additionally weakens the PoP-based blame design).
