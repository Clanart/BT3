Based on the investigation, I found a genuine analog to the CSP finding's underlying theme (missing isolation / shared state without proper boundaries leading to unauthorized cross-context effects). In Cosmos EVM this doesn't map to any CSP/CORS surface — those (`rpc/websockets.go` `checkOrigin`, `server/json_rpc.go` CORS handling) are properly gated. Instead, the analogous "improperly scoped shared context" defect exists in the precompile `BalanceHandler` used to bridge native bank events into the EVM `StateDB`.

Note: due to tool-call limits I was unable to view the exact body of `GetBalanceHandler()` in `precompiles/common/precompile.go` in this session, so the precise storage mechanism (field vs. factory-per-call) is inferred from the `BalanceHandlerFactory`/`BalanceHandler` code and from the project's own test suites, which explicitly name and describe this defect.

### Title
Shared BalanceHandler state across nested/recursive precompile calls causes bank-to-StateDB balance desync - (File: precompiles/common/balance_handler.go)

### Summary
`BalanceHandler.prevEventsLen` [1](#0-0)  is used as a single mutable "bookmark" into the SDK event log to determine which bank events (`coin_spent`, `coin_received`, fractional-balance-change) should be replayed into the EVM `StateDB` after a precompile call. The project's own integration tests confirm that this handler is shared across recursive/nested precompile invocations, causing the bookmark to be overwritten and balance-affecting bank events to be mis-attributed or dropped when reconciling `StateDB` balances with the native bank keeper.

### Finding Description
Every stateful precompile (`erc20`, `staking`, `distribution`, `gov`, `slashing`, `ics20`, `bank`, `werc20`, the test `debug` precompile) is built on `cmn.Precompile` and obtains a `BalanceHandler` via `BalanceHandlerFactory` [2](#0-1) . Before executing precompile logic, `BeforeBalanceChange` records `len(ctx.EventManager().Events())` into `prevEventsLen` [3](#0-2) ; after execution, `AfterBalanceChange` replays all bank events emitted *after* that index into `StateDB.AddBalance`/`SubBalance` [4](#0-3) .

The project's own test suite, `evmd/tests/integration/balance_handler/balance_handler_test.go`, is explicitly titled to document this defect: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [5](#0-4) . It demonstrates the issue via a contract (`DebugPrecompileCaller.sol`) that recursively re-enters the same precompile address [6](#0-5) , and a debug precompile whose `Call0` recursively re-invokes itself through `CallEVMWithData` before returning [7](#0-6) .

A second test suite independently documents the same root cause from a different trigger: `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` states it *"Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated"* [8](#0-7) , using an ERC20 contract with a reentrant `_beforeTokenTransfer` hook that triggers reverted nested calls during an ICS20 precompile transfer [9](#0-8) .

Because `prevEventsLen` is a single mutable counter shared by whatever object `GetBalanceHandler()` returns (rather than a fresh, call-frame-scoped instance), a nested/reentrant precompile invocation (same precompile called recursively, or one precompile call triggering another value-moving precompile) overwrites the outer call's bookmark. When the inner call finishes first and applies `AfterBalanceChange`, it consumes the shared event window; the outer call's subsequent `AfterBalanceChange` then either re-processes an already-consumed range (double-crediting/debiting `StateDB` balances for events that were already applied) or skips events emitted by the outer call because the bookmark index no longer matches the outer call's frame. Both outcomes break the 1:1 accounting invariant between the native bank keeper (source of truth) and EVM `StateDB` (visible to all EVM callers, including ERC20 `balanceOf`/transfer paths).

### Impact Explanation
This breaks the required invariant that "x/erc20, bank, ICS20, staking, distribution... flows must preserve 1:1 accounting between native coins, ERC20 views, escrows, and precompile-visible balances." A miscounted/duplicated event application can cause `StateDB.AddBalance` to credit an EVM account for value it never received from the bank keeper (inflating the EVM-visible balance beyond what is actually escrowed in the bank module), or cause `SubBalance` to be skipped/duplicated for the sender. Since token pair ERC20 precompiles, native EVM balance, and IBC/ICS20 transfer flows all route through this exact mechanism, an attacker who can trigger nested/reentrant precompile calls (e.g., via a token contract's transfer hook invoking a second value-moving precompile, or directly re-entering the same precompile address) can create a durable divergence between real bank balances and EVM-spendable balances — a form of unauthorized value duplication/extraction that is irreversible once committed to state.

### Likelihood Explanation
Both conditions needed to trigger this are reachable by an ordinary, unprivileged user: (1) deploying/calling a contract that re-enters a precompile address (directly demonstrated with `DebugPrecompileCaller.sol`, and generalizable to any real value-moving precompile with reentrant call paths, e.g., ERC20 token hooks calling into `distribution`/`staking`/`ics20`/`bank` precompiles), and (2) sending a standard EVM transaction. No privileged role, validator collusion, or governance action is required — the test suites reproduce it purely from a user-submitted transaction and contract.

### Recommendation
Make `BalanceHandler` strictly scoped per precompile call frame instead of a shared/cached instance: instantiate a new `BalanceHandler` from `BalanceHandlerFactory.NewBalanceHandler()` at the start of every `Run`/native-action invocation and pass it down the call stack (or otherwise maintain a stack/counter keyed by call depth) rather than storing `prevEventsLen` on a struct reused across nested precompile invocations. Add invariant checks (e.g., periodic reconciliation between `x/bank` total balances and aggregated `StateDB` balances for accounts touched by precompiles) to detect any residual desync.

### Proof of Concept
Use the existing repository test as the PoC: `evmd/tests/integration/balance_handler/balance_handler_test.go::TestRecursivePrecompileCallsWithDebugPrecompile` deploys `DebugPrecompileCaller.sol`, which recursively calls the debug precompile (`callback(0)` → `call1()` events + recursive `call0()` re-entry) [10](#0-9) ; and `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go::TestHandleMsgTransfer` ("test recursive precompile call with reverts") drives an ICS20 transfer of a recursive/reverting ERC20 token through the `ics20` precompile and inspects distribution reward/balance state afterward to show the aggregated event/balance mismatch [11](#0-10) . Both tests currently pass by asserting the observed (desynced) behavior rather than failing, indicating the underlying accounting bug is present and unaddressed as of this snapshot rather than being caught as a regression.

pragma solidity ^0.8.4;

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }
}
