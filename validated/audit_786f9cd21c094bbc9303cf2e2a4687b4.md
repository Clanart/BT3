### Title
Missing participant-key validation in `GeneratorPromotion::complete` allows out-of-bounds-map panic DoS - ([File: crypto/dkg/promote/src/lib.rs])

### Summary
`GeneratorPromotion::complete` iterates every participant index `1 ..= n` (excluding `self`) and blindly `unwrap()`s `proofs.get(&i)`. Its only validation is that the map has length `n - 1` and that no key exceeds `n`. A caller/peer that supplies a map containing `params.i()` (self) — or otherwise omitting any required participant while padding with a duplicate-index-free key ≤ `n` — causes a guaranteed panic.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` validates only:

- `proofs.len() == params.n() - 1` (line 125)
- every key `<= params.n()` (line 132-135)

It does **not** check that `proofs` excludes `params.i()` itself, nor that every participant in `1 ..= n` other than `i` is actually present. At line 140-146 it then does:

```rust
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();   // panics if participant j was skipped
```

Since `HashMap` keys are distinct, a map of size `n - 1` drawn from `1 ..= n` that contains `params.i()` must omit exactly one required participant `j ≠ i`. The `unwrap()` on `j` then panics. This is the same bug class as CVE-2025-65890: an index/identifier taken from external input is only partially range-checked, then used to index into a collection with an `unwrap`/`expect` that crashes the process.

### Impact Explanation
Denial of service. `GeneratorPromotion::complete` is invoked during generator-promotion ceremonies where the `proofs` map is assembled from `GeneratorProof` messages submitted by other participants (`GeneratorProof::read` accepts untrusted bytes). A single faulty/malicious participant-supplied set — or any pipeline that forwards a keyed map including the local participant — crashes the node mid-ceremony, aborting promotion and any dependent signing/recovery flow. Consistent with the CVSS 7.5 availability-only scoring of the source advisory.

### Likelihood Explanation
Reachable whenever promotion runs: the `proofs` map contents are attacker-influenced (each key is a `Participant` attached to a participant-supplied proof). The triggering condition is trivial — include `params.i()` in the map, or substitute a key while keeping `len() == n - 1`. No cryptographic correctness is needed to trigger it; it fires before any proof verification for the missing index.

### Recommendation
Before the `1 ..= n` loop, validate the key set exactly: reject if `proofs.contains_key(&params.i())`, and return `PromotionError` (e.g. `MissingParticipant`) instead of `unwrap()` when `proofs.get(&i)` returns `None`. Optionally use `validate_map`-style logic as in `pedpop`'s `calculate_share` (crypto/dkg/pedpop/src/lib.rs:468) which enforces exact key-set equality.

### Proof of Concept
```rust
// n = 5, our params.i() = Participant(1)
let mut proofs: HashMap<Participant, GeneratorProof<C>> = HashMap::new();
// Attacker-coordinated map includes self and omits participant 3
proofs.insert(Participant::new(1).unwrap(), proof_1); // self
proofs.insert(Participant::new(2).unwrap(), proof_2);
proofs.insert(Participant::new(4).unwrap(), proof_4);
proofs.insert(Participant::new(5).unwrap(), proof_5);
// len == 4 == n - 1, all keys <= 5: passes both checks
promotion.complete(&proofs); // panics at proofs.get(&Participant(3)).unwrap()
```
