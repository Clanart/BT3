### Title
Weak PRNG: `PREVRANDAO`/`block.difficulty` opcode is derived solely from the public, proposer-influenced block timestamp - (File: `x/evm/keeper/keeper.go`)

### Summary
Sei's EVM exposes the `DIFFICULTY`/`PREVRANDAO` opcode value to every Solidity contract via `vm.BlockContext.Random`. Instead of sourcing this from unpredictable validator/consensus entropy (as Ethereum's post-merge RANDAO mix does), `Keeper.GetVMBlockContext` computes it as `keccak256(blockTime)` — a value fully derivable from the block header timestamp, which is public, monotonic, and chosen by the block proposer.

### Finding Description
In `GetVMBlockContext`, the `Random` field of the EVM `BlockContext` (which backs the `DIFFICULTY`/`PREVRANDAO` opcode seen by every EVM contract) is computed as: [1](#0-0) 
```go
// Use hash of block timestamp as info for PREVRANDAO
r, err := ctx.BlockHeader().Time.MarshalBinary()
...
rh := crypto.Keccak256Hash(r)
```
and is then assigned directly to the block context: [2](#0-1) 

This is functionally identical to (and in fact weaker than) the exact bug class described in the external report: on Ethereum post-Merge, `block.difficulty`/`PREVRANDAO` is replaced by the beacon chain's `RANDAO` mix, which is at least derived from validator-contributed entropy accumulated over an epoch, even though it becomes fully known one slot ahead of proposal. On Sei, the substituted value is simply a hash of the current block's own timestamp — a value that is:
- Publicly visible in the block header at proposal time, before any transaction that depends on it is included in that same block, exactly mirroring the "value known ahead of block proposal" precondition in the report; and
- Directly influenced by the block proposer, who chooses the timestamp for a block (subject only to Tendermint's monotonicity constraint), giving the current proposer additional power beyond what even the reported EIP-4399 issue grants (an attacker in the report needed to only be a mempool-timing-aware user; here the block proposer can also bias the value they control).

Any Solidity contract deployed to Sei's EVM (games, raffles, loot boxes, on-chain randomness-dependent DeFi mechanisms, etc., exactly analogous to `DoomsdaySettlers.sol` in the report) that uses `block.difficulty`/`PREVRANDAO` as an entropy source is therefore trivially predictable and, worse, directly manipulable by whichever validator proposes the block containing the triggering transaction.

### Impact Explanation
Contracts deployed on Sei that rely on `PREVRANDAO`/`block.difficulty` for randomness (lotteries, gachas, settlement/asset-type assignment, etc.) can have their outcomes predicted or biased by (a) any observer who inspects the pending block's timestamp before submitting a triggering transaction, and (b) the block proposer, who can pick a timestamp that produces a favorable hash for themselves or a colluding party. This enables systematic fund extraction from randomness-dependent contracts and unfair reward distribution, mirroring the "fund loss via predictable settlement outcomes" impact validated in the original report, and is strictly easier to exploit on Sei than the analogous Ethereum PREVRANDAO scenario because the entropy source (timestamp) is directly proposer-controlled rather than being an accumulated validator-committee RANDAO mix.

### Likelihood Explanation
Any dApp developer using standard Solidity randomness idioms (`block.difficulty`/`block.prevrandao`) on Sei's EVM is automatically exposed; no special privileges are required beyond deploying/using a contract and observing/submitting ordinary EVM transactions, which is squarely within the unprivileged EVM-transaction-sender threat model.

### Recommendation
Do not derive `Random`/`PREVRANDAO` from the current block's own timestamp. Instead, source it from validator-set-derived entropy that is unknown until after commitment (e.g., use the previous block's Tendermint header hash/commit signatures aggregated over multiple blocks, or a delayed/future-epoch value), and clearly document in Sei's EVM compatibility notes that `PREVRANDAO` is not a secure randomness source, directing developers toward a verifiable randomness oracle for on-chain-random use cases.

### Proof of Concept
1. Observe the current or soon-to-be-proposed block's `BlockHeader().Time` via the public JSON-RPC (`eth_getBlockByNumber`/CometBFT block queries) before it is finalized, or, as a validator, choose the timestamp for the block you are proposing.
2. Compute `keccak256(time.MarshalBinary())` off-chain exactly as `GetVMBlockContext` does at `x/evm/keeper/keeper.go` lines 275-280.
3. Simulate the target randomness-dependent contract's logic (e.g., a settlement/reward contract using `block.difficulty`) locally with this precomputed value to determine whether the resulting outcome is favorable.
4. Only submit the triggering transaction (or, as proposer, only include it) when the outcome is favorable; otherwise wait for the next block/timestamp and repeat.
