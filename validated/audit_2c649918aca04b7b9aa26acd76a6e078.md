## Found: same-chain `cancelOrder` path reaches the unfixed CEI-violating `withdraw()` in the Tron IntentGatewayV2

### Title
Re-entrancy via CEI violation in `IntentGatewayV2.withdraw` (Tron variant) — external token transfer executes before escrow debit - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM `IntentsBase._withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-410`) was hardened with the CEI pattern: `_orders[body.commitment][token] = escrowed - amount;` is written **before** the external `.call`/`safeTransfer`, confirmed by the dedicated regression suite `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`. The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still has the pre-fix ordering in its `withdraw` function (lines 682-721): the external `token.call(...transfer...)` / native `.call{value: amount}` executes first, and `_orders[body.commitment][token] -= amount;` is only decremented afterward.

### Finding Description
`withdraw()` in the Tron contract is: [1](#0-0) 

Note the order of operations: the escrow amount is checked only via `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` (a non-zero check, not a sufficiency check against `amount`), then the external transfer is made, and only afterward is `_orders[body.commitment][token] -= amount;` executed. This is a direct analog of the external report's core defect: state (`tokenStorage`/escrow balance) is mutated **after**, not before, the external call/token transfer that can trigger attacker-controlled code (ERC777 `tokensReceived` hooks, or malicious/upgradeable ERC20 tokens with transfer callbacks).

This `withdraw` is reachable from a user-triggered, unprivileged entry point: `cancelOrder()` for same-chain orders calls it directly without any host restriction: [2](#0-1) 

Same-chain cancellation is caller-controlled (`order.user == msg.sender`) and requires no relayer, prover, or Hyperbridge involvement — it is a same-chain, single-transaction path (`isSameChain` branch, line 519-530) that calls `withdraw(body, true)` directly using order fields fully controlled by the caller (input token list, escrow amounts, beneficiary = `order.user`). If `order.inputs` contains a malicious token contract with a transfer hook (or the fee token / an unusual ERC20), the token's callback fires mid-`withdraw`, before `_orders[commitment][token]` is decremented for that token index and before the loop proceeds to subsequent tokens/fees in the same call.

Because `_orders[commitment][token]` for token `i` is still non-decremented at the moment the callback fires, and the loop continues to process *other tokens and fees for the same commitment* in the same external call before finishing, a malicious input token can re-enter another externally reachable function that reads/mutates `_orders[commitment][...]` (e.g. re-enter `cancelOrder` for the same order/commitment) while intermediate escrow entries for that commitment are still stale. This mirrors exactly the "state updated after external call → re-entrant drain" pattern from the reference report, just localized to the Intent Gateway's escrow bookkeeping instead of a `tokenStorage` mapping.

### Impact Explanation
This falls squarely within "stealing or loss of funds" and "logic attacks / double-settlement" categories: escrowed user funds held by the Intent Gateway contract are the custody target, and the CEI violation is the exact bug class the bounty scope calls out for bridge custody / intent settlement. A successful re-entrant call before `_orders[commitment][token]` is fully zeroed out for the commitment can allow a malicious token/beneficiary to trigger duplicate transfers out of the same escrow slot, or to interleave with other Intent Gateway operations (fee release, other token legs of the same order) while the commitment's bookkeeping is inconsistent.

### Likelihood Explanation
Likelihood is high for this specific code path: `cancelOrder` → same-chain branch → `withdraw` is directly callable by any order owner with no relayer/prover/admin dependency, using an order the owner constructs themselves (including choice of ERC20 input token). No malicious peer, relayer, or governance actor is required — only an attacker-controlled or ERC777-style token used as an order input, which the user fully controls.

### Recommendation
Apply the same CEI fix already present in `evm/src/apps/intentsv2/IntentsBase.sol` to the Tron `withdraw()`: decrement `_orders[body.commitment][token]` (and clear the fee entry) **before** making the external native/ERC20 transfer, for every branch (native, ERC20, and the fee-token payout). Add a reentrancy guard or `_filled`-style single-shot marker consistent with the fix validated by `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`, and port that regression test to the Tron contract.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) and a malicious ERC20/ERC777-style token `EvilToken` implementing a transfer-hook that, upon receiving tokens, calls back into `IntentGatewayV2.cancelOrder` for the same order/commitment (or any other function reading `_orders[commitment][...]`).
2. As `attacker`, place a same-chain `Order` with `order.inputs = [EvilToken: amount]` via `placeOrder`, escrowing `amount` of `EvilToken`.
3. Call `cancelOrder(order, options)` — enters the `isSameChain` branch, calls `withdraw(body, true)`.
4. Inside `withdraw`, the loop hits `token.call(transfer.selector, beneficiary, amount)` for `EvilToken` before `_orders[commitment][EvilToken] -= amount` executes.
5. `EvilToken`'s transfer hook re-enters `cancelOrder`/another gateway function for the same commitment while `_orders[commitment][EvilToken]` still shows the pre-debit escrow value, allowing a second, unintended withdrawal path to be taken against the stale escrow state.

Note: I was unable to fully trace within the available context whether the Tron contract exposes an additional re-entrant target beyond `cancelOrder` itself (e.g., a Tron-specific `fillOrder`) — the index does not surface a `fillOrder`/`_fillSameChain` function inside `evm/tron/contracts/apps/IntentGatewayV2.sol`, so the concrete double-spend requires re-entering through `cancelOrder` on the same or a related commitment, or a full protocol review of all callers of `_orders[commitment][...]`. A full audit of the Tron contract's complete function set (starting a Devin session with file access) would be needed to enumerate every re-entrant target precisely.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
