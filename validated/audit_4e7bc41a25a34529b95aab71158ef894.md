### Title
`depositFor()` in `WombatPoolHelperV2` hardcodes zero slippage protection, exposing depositors to front-run/sandwich value loss - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.depositFor()` forwards `_minimumLiquidity = 0` to `WombatStaking.deposit()` regardless of caller input, removing all slippage protection on the underlying Wombat pool deposit, unlike the normal `deposit()` path which lets the caller specify `_minimumLiquidity`.

### Finding Description
The `deposit()` function correctly exposes a caller-supplied minimum-liquidity parameter that is passed through to `WombatStaking.deposit()`: [1](#0-0) 

However, `depositFor()`, which is callable by any unprivileged wallet to deposit `depositToken` on behalf of an arbitrary `_for` address, hardcodes the minimum-liquidity argument to `0`: [2](#0-1) 

This value flows into `WombatStaking.deposit()`, which calls the Wombat pool's `deposit()` with that same `_minimumLiquidity` value as the slippage bound: [3](#0-2) 

The Wombat pool's deposit mints LP liquidity based on the pool's current `cash`/`liability` ratio (an AMM-style invariant), analogous to `router.getAmountsOut` spot pricing in the referenced report. Because `_minimumLiquidity` is unconditionally `0`, this call has no protection against the pool's liquidity-minting rate being skewed between transaction submission and execution — exactly the same bug class as the reported `BondingTax.swapForAsset` issue (an on-chain AMM-derived exchange rate used for a value-transfer operation with no effective minimum-output enforcement), except here it is not merely a manipulable formula but a complete absence of any check.

### Impact Explanation
Any user calling `depositFor()` (a fully unprivileged, externally callable function) receives an unbounded amount of LP/receipt tokens for their deposited stable tokens, with zero guaranteed minimum. An attacker can manipulate the pool's cash/liability ratio immediately before the victim's deposit executes (e.g., via a large withdraw/deposit in the same block or adjacent blocks) to reduce the liquidity minted to the depositor, capturing the difference. This is a direct, concrete loss of principal for the depositing wallet — value that should have gone to the depositor's LP/receipt-token balance is instead lost to the manipulated pool state, satisfying the "direct theft of user funds" bar.

### Likelihood Explanation
`depositFor()` is a normal user-facing entry point (no access control) intended for third-party/contract-assisted deposits (e.g., zappers), so it is reachable directly by any wallet in the course of ordinary usage. The absence of caller-supplied slippage protection means the exposure exists on every call, not just under adversarial conditions, making exploitation straightforward for any actor able to influence the Wombat pool's cash/liability ratio around the victim's transaction.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor()` (and thread it through analogous functions in `WombatPoolHelper.sol`/`AnkrBNBPoolHelper.sol` if they have similar hardcoded-zero paths) so callers can supply a real slippage bound instead of hardcoding `0`, consistent with the `deposit()` function's design.

### Proof of Concept
1. Attacker observes a pending `depositFor()` call for a large deposit into a Wombat pool via `WombatPoolHelperV2`.
2. Attacker front-runs with a transaction that skews the target pool's `cash`/`liability` ratio unfavorably (e.g., large withdrawal that shifts the coverage ratio down for the deposited asset).
3. Victim's `depositFor()` executes with `_minimumLiquidity = 0`, so `IWombatPool.deposit()` mints substantially fewer LP shares than expected for the deposited amount — the call cannot revert since there is no lower bound.
4. Attacker reverses their position (or benefits from the resulting pool skew), capturing the value difference at the depositor's expense. [2](#0-1) [4](#0-3)
