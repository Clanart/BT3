### Title
`CombineCoins` explicit `target_coin_ids` path bypasses `TXConfig` coin-selection restrictions (excluded/min/max coin filters) - ([File: chia/wallet/fungibility_manager.py])

### Summary
FreeScout's bug was that a customer-visibility restriction parameter (`limit_user_customer_visibility`) was enforced on normal customer access paths but silently skipped on the "merge customers" action, letting a restricted actor touch data the restriction was meant to keep off-limits. The same class of bug exists in Chia's wallet "combine coins" (merge) flow: `FungibilityManager.combine_coins()` enforces `TXConfig`/`CoinSelectionConfig` restrictions (`excluded_coin_ids`, `excluded_coin_amounts`, `min_coin_amount`, `max_coin_amount`) only on the automatic "fill-up" coin-selection branch, but completely skips them when coins are explicitly supplied via `target_coin_ids`.

### Finding Description
`FungibilityManager.combine_coins()` has two coin-gathering branches:
1. Explicit `target_coin_ids` branch — fetches coin records directly via `coin_store.get_coin_records(... coin_id_filter=HashFilter(target_coin_ids, mode=include))`, only rejecting already-spent coins, with **no application of `coin_selection_config`** at all (no `excluded_coin_ids`, `excluded_coin_amounts`, `min_coin_amount`, or `max_coin_amount` check). [1](#0-0) 
2. The automatic "fill-up" branch — which does apply `min_coin_amount`/`max_coin_amount` via `amount_range`, but still never applies `excluded_coin_ids`/`excluded_coin_amounts`. [2](#0-1) 

By contrast, the canonical coin-selection path used throughout the rest of the wallet (`select_coins()` in `chia/wallet/coin_selection.py`) fully enforces `excluded_coin_ids`/`excluded_coin_amounts`/`min`/`max` via `coin_selection_config.filter_coins()`. [3](#0-2) 

Per the wallet module's own documented mutation-ordering contract, `excluded_coin_ids` is not just a cosmetic UX filter — it is actively used as an authorization/reservation mechanism: `WalletActionConfig.adjust_for_side_effects()` feeds already-selected coin IDs back into `TXConfig.excluded_coin_ids` so that nested or multi-step spends (offers, tandem-fee transactions, CAT spends) do not re-select a coin that is already committed elsewhere in the same logical operation before any DB mutation has occurred. [4](#0-3) 

Because `CombineCoins` is a `TransactionEndpointRequest` that flows through the same `tx_endpoint()` gate as every other wallet RPC (auto-filling and validating a `TXConfig`), a caller/tool can legitimately construct a `TXConfig` with `excluded_coin_ids` set to protect specific coins (e.g., coins already reserved for a pending offer, a concurrent nested spend, or coins the caller wants to explicitly keep untouched) and pass it into `combine_coins`. If the caller (or the `--input-coin` CLI flag / `target_coin_ids` RPC field) also names one of those "excluded" coins explicitly, `FungibilityManager.combine_coins()` will happily combine and spend it anyway, since the exclusion list is never consulted in that code path. [5](#0-4) [6](#0-5) 

### Impact Explanation
Coin exclusion in this wallet's design is a state-consistency/authorization boundary, not merely a UX convenience — it is relied upon by nested action-scope spend construction (offers, CAT tandem-fee generation, multi-step spends) to guarantee a coin already staged for one purpose is not silently pulled into an unrelated spend before commit. Silently ignoring `excluded_coin_ids`/`excluded_coin_amounts` in the explicit-ID `combine_coins` path allows a coin that another in-flight operation depends on (e.g., a coin backing an outstanding offer, or a coin already staged in a concurrent nested action-scope spend within the same wallet) to be consumed by an unrelated "combine" transaction, invalidating that pending offer/trade or producing a coin-set/double-spend attempt against a coin the caller explicitly instructed the wallet not to touch. This is a concrete violation of the restriction contract the rest of the wallet code depends on for correctness, directly mirroring the FreeScout pattern of a merge operation silently ignoring the same restriction the rest of the application enforces.

### Likelihood Explanation
Exploitability requires only a single legitimate wallet RPC/CLI call: any caller (script, automation, remote wallet-RPC client, or `chia wallet coins combine --input-coin <id>`) that also has an `excluded_coin_ids`/`min_coin_amount`/`max_coin_amount`/`excluded_coin_amounts` restriction active for other reasons (protecting offer-locked coins, or relying on `adjust_for_side_effects()` inside a nested spend) will trigger this whenever `target_coin_ids` overlaps the restricted set. No special privilege beyond normal wallet-RPC access is needed, and existing regression tests only assert that the *fill-up* path respects `max_coin_amount` and rejects already-spent explicit IDs — they do not cover `excluded_coin_ids`/`excluded_coin_amounts` for the explicit-ID branch, confirming the gap is untested and live in this code path. [7](#0-6) 

### Recommendation
In `FungibilityManager.combine_coins()`, when `target_coin_ids` is provided, validate the fetched `target_records` against the active `action_scope.config.tx_config.coin_selection_config` (reject or filter coins whose ID is in `excluded_coin_ids`, whose amount is in `excluded_coin_amounts`, or that fall outside `[min_coin_amount, max_coin_amount]`) before adding them to `coins`, matching the enforcement already performed by `coin_selection.select_coins()` and `CoinSelectionConfig.filter_coins()`.

### Proof of Concept
1. Start a wallet and note two unspent coins, `A` and `B`.
2. Build a `TXConfig` with `excluded_coin_ids=[A.name()]` (e.g., because coin `A` is reserved for an outstanding offer or a concurrent nested action-scope spend that relies on `adjust_for_side_effects()`).
3. Call `combine_coins` (via RPC `CombineCoins` or CLI `chia wallet coins combine --input-coin <A> --input-coin <B>`) using that same `TXConfig`.
4. Observe that `FungibilityManager.combine_coins()` (`chia/wallet/fungibility_manager.py:101-111`) fetches and spends coin `A` despite it being listed in `excluded_coin_ids`, because the explicit `target_coin_ids` branch never calls `coin_selection_config.filter_coins()` or otherwise checks the exclusion list — unlike `select_coins()` in `chia/wallet/coin_selection.py`, which would reject/skip an excluded coin under the identical `TXConfig`.

    def filter_coins(self, coins: set[Coin]) -> set[Coin]:
        filtered_set = {
            coin
            for coin in coins
            if self.min_coin_amount <= coin.amount <= self.max_coin_amount
            and coin.amount not in self.excluded_coin_amounts
            and coin.name() not in self.excluded_coin_ids
        }
        necessary_coins = self.included_coin_ids + ([] if self.primary_coin is None else [self.primary_coin])
        if not set(necessary_coins).issubset({coin.name() for coin in filtered_set}):
            raise ValueError("Some coin selection restrictions eliminated coins specified for inclusion")
        return filtered_set

class CombineCoins(TransactionEndpointRequest):
    wallet_id: uint32
    number_of_coins: uint16 = uint16(500)
    largest_first: bool = False
    target_coin_ids: list[bytes32] = field(default_factory=list)
    target_coin_amount: uint64 | None = None
    coin_num_limit: uint16 = uint16(500)

    def __post_init__(self) -> None:
        if self.number_of_coins > self.coin_num_limit:
            raise ValueError(
                f"{self.number_of_coins} coins is greater then the maximum limit of {self.coin_num_limit} coins."
            )
        if self.number_of_coins < 2:
            raise ValueError("You need at least two coins to combine")
        if len(self.target_coin_ids) > self.number_of_coins:
            raise ValueError("More coin IDs specified than desired number of coins to combine")
