### Title
`ReceivedOutput::read` accepts an arbitrary offset/script_pubkey pair without consistency check, so a mismatched offset silently yields a wrong spendable key — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to `MinimalForwarder::execute` treating a call to an EOA as success (no check that `to` is actually a contract), `ReceivedOutput::read` treats any deserialized `(offset, TxOut, outpoint)` tuple as a valid received output without checking that the claimed `offset` actually corresponds to `output.script_pubkey`. The only place the two are bound together is `Scanner::scan_transaction`, which looks up the offset in `self.scripts` by script_pubkey [1](#0-0) . `read` performs no such binding [2](#0-1) .

### Finding Description
`ReceivedOutput::read` parses `offset` via `Secp256k1::read_F` and then consensus-decodes an arbitrary `TxOut`/`OutPoint` [2](#0-1) . Nothing verifies `output.script_pubkey == p2tr_script_buf(key + offset*G)`. Downstream, `Output::key` recovers the group key as `script_key - offset*G` [3](#0-2) . For a forged `ReceivedOutput` whose `TxOut` pays to `key + offset_A*G` but whose serialized offset field is `offset_B`, `key()` silently returns `key + (offset_A - offset_B)*G` — a key that does not correspond to the actual UTXO's spending conditions. The deserialization "succeeds" exactly like the forwarder call to an EOA: the absence of a semantic check produces a silently wrong result rather than an error.

### Impact Explanation
An unprivileged party supplying `ReceivedOutput` bytes (or an `Output` wrapping one via `Output::read`, which calls `ReceivedOutput::read` [4](#0-3) ) can cause funds to be reported as received under a group key that cannot spend them, or attributed to the wrong validator set/branch. Because `key()` asserts only `script.is_p2tr()` and then subtracts the attacker-chosen offset, the real deposit to `key + offset_A*G` is registered under `key + (offset_A - offset_B)*G`; the protocol's signing path for that output will produce signatures for a key unrelated to the on-chain UTXO, i.e., funds reported received that are not spendable.

### Likelihood Explanation
Reachable wherever `ReceivedOutput::read`/`Output::read` consume externally supplied bytes rather than `Scanner::scan_transaction` output. The attacker only needs a real P2TR output (any `TxOut`) and a freely chosen scalar — no collusion, no broken BFT, no leaked keys. Exploitability depends on integrators trusting serialized outputs rather than re-scanning, mirroring the report's "impact depends on applications that rely on `executeRequiringSuccess`".

### Recommendation
Bind the offset to the output at deserialization time (or make `ReceivedOutput` unconstructible except via `Scanner`): either store/verify `script_pubkey == p2tr_script_buf(key + offset*G)` inside `read` given the expected base key, or add a `verify(key)` method on `ReceivedOutput` that callers must invoke before `key()`/signing, so a mismatched offset fails loudly instead of silently producing a wrong key.

### Proof of Concept
1. Base key `key` is even-Y; honest deposit output pays to `p2tr_script_buf(key + offset_A*G)` for registered `offset_A`.
2. Attacker serializes `ReceivedOutput { offset: offset_B, output: <that TxOut>, outpoint: <that outpoint> }` with `offset_B != offset_A` (`ReceivedOutput` fields are private but `write`/`serialize` are constructible from a scanned output then re-encoded, or bytes are simply crafted: `F_le(offset_B) || consensus(TxOut) || consensus(OutPoint)`).
3. `ReceivedOutput::read` returns `Ok` — no error [2](#0-1) .
4. `Output::key()` parses the script's x-only key `K_A = key + offset_A*G` and returns `K_A - offset_B*G`, a key nobody holds shares for under this output's context [3](#0-2) . Any signing attempt for this "received" output targets the wrong key; the UTXO is unspendable through this path.

    let offset = Secp256k1::read_F(r)?;
    let output;

      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
