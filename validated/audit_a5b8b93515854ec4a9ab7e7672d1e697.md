## Analysis

The external report's core broken invariant is: **a function accepts `msg.value` intended to cover an exact required amount, but never validates that the supplied value equals (or refunds the excess over) that amount — so any overpayment is permanently stranded.**

Searching the Hyperbridge EVM contracts for the same pattern in fee-dispatch paths surfaces a direct analog in `EvmHost.dispatch()` combined with the cross-chain cancel flow in `ExtrinsicIntents.sol`.

### Title
Excess native `msg.value` sent to `EvmHost.dispatch()` for fee-token swaps is stranded in the host, not refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept native ETH and swap it for an exact amount of fee token via `swapETHForExactTokens(post.fee, ...)`, but discard the swap's return value and never refund the unspent portion of `msg.value` back to the caller.

### Finding Description
In `EvmHost.sol`: [1](#0-0) 

`swapETHForExactTokens` (e.g. `UniV3UniswapV2Wrapper.swapETHForExactTokens`) computes `spent` and refunds `msg.value - spent` — but that refund is sent to `msg.sender` of the swap call, which is `EvmHost` itself, not the original transaction sender: [2](#0-1) 

`EvmHost.dispatch()` never captures or forwards this refund to `_msgSender()`, so any native ETH sent in excess of the exact fee-token cost of `post.fee`/`get.fee` is absorbed into `EvmHost`'s own balance and is unrecoverable by the caller.

Most app-level callers protect against this by pre-computing the exact value needed and refunding leftovers *before* calling `dispatch`, e.g. `IntentGatewayV2.placeOrder` captures `amounts[0]` from its own swap and refunds `msgValue` explicitly: [3](#0-2) 

However, the cross-chain order-cancellation paths in `ExtrinsicIntents.sol` forward the *entire* `msg.value` straight into `IDispatcher(hostAddr).dispatch{value: msg.value}(request)` with no pre-check against `options.relayerFee` and no post-call refund: [4](#0-3) [5](#0-4) 

Since `cancelOrder` is `public payable`, any unprivileged caller (the order owner, or the public caller allowed after expiry) who overestimates the required native fee and sends excess ETH will have that excess permanently absorbed by `EvmHost`, with no code path that returns it.

### Impact Explanation
Any caller of the cross-chain cancel paths (`_cancelFromSource`, `_cancelFromDest`) who supplies `msg.value` greater than what is actually consumed by `swapETHForExactTokens` for the requested `relayerFee` loses that excess permanently — it is not credited to any user-controlled balance and there is no sweep path back to the original sender. This is a direct "loss of funds" outcome reachable by any unprivileged, honest user through normal use of a public entrypoint, matching the bounty's "stealing or loss of funds" / bridge custody category.

### Likelihood Explanation
Likelihood is moderate: it requires a caller to overestimate the exact fee-token amount needed (easy to do since the on-chain swap rate can shift between quote time and execution, or the caller simply pads value for safety, as is common practice). No malicious relayer, prover, or admin is needed — an honest user triggering `cancelOrder` cross-chain with any surplus ETH suffices.

### Recommendation
In `EvmHost.dispatch()` (both `DispatchPost` and `DispatchGet` overloads), capture the return value of `swapETHForExactTokens` (the actual amount spent) and refund `msg.value - spent` to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`. Alternatively, require callers to pass the exact expected value and revert on mismatch. Additionally, `ExtrinsicIntents._cancelFromSource`/`_cancelFromDest` should compute the exact swap cost before dispatching and refund any leftover `msg.value` to `msg.sender`, consistent with the refund logic already present in `_fillCrossChain`.

### Proof of Concept
1. User calls `IntentGatewayV2.cancelOrder(order, options)` on the destination chain with `order.deadline` already expired and `options.relayerFee = X`.
2. User sends `msg.value = Y` where `Y > (amount of ETH actually needed to buy X fee tokens)`.
3. `_cancelFromDest` forwards the full `msg.value` to `IDispatcher(hostAddr).dispatch{value: msg.value}(request)`.
4. `EvmHost.dispatch(DispatchPost)` swaps `msg.value` ETH for exactly `X` fee tokens via `swapETHForExactTokens`; the wrapper refunds the unspent ETH to `EvmHost` (its own `msg.sender` in that inner call), not to the user.
5. `EvmHost.dispatch` returns without ever forwarding that refund; the surplus ETH remains in `EvmHost`'s balance with no code path to return it to the user, i.e., permanently lost from the caller's perspective.
