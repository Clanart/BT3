### Title
Unsanitized tag name reaches `git tag -d` sink allowing argument injection - (File: app/src/lib/git/tag.ts)

### Summary
`deleteTag` in [1](#0-0)  builds `['tag', '-d', name]` and passes it straight to dugite/git without a `--` separator to stop `name` from being parsed as an option. `createTag` at [2](#0-1)  has the same pattern. This is inconsistent with most of the other git wrapper functions in this codebase (`checkout.ts`, `reset.ts`, `rm.ts`, `add.ts`, `diff.ts`, etc.), which use a literal `'--'` separator before user-controlled ref/path arguments to defend exactly against this class of argument injection — a pattern this repo already recognizes as necessary but did not apply to `tag.ts`.

### Finding Description
The tag name displayed/used in `DeleteTag.DeleteTag` in [3](#0-2)  is forwarded via `dispatcher.deleteTag(repository, tagName)` down to `GitStore`/`app-store.ts` and ultimately to `deleteTag()` in `tag.ts`. The tag names populating the UI originate from `getAllTags()`, which reads local tag refs via `git show-ref --tags -d` [4](#0-3) . Local tag refs include tags obtained via `git fetch` from a remote (git fetches tags by default), so a name chosen by a remote/attacker-controlled repository can, in principle, become the `name` argument passed unguarded into `['tag', '-d', name]`.

However, I could not confirm within this codebase (or via available tools) whether such attacker-crafted ref names (e.g. `-d`, `--force`, `--dry-run`) can actually survive `git`'s own ref-name validation (`check-ref-format`) during fetch/receive and end up as a literal local tag ref. This is a property of the git binary itself, not of GitHub Desktop's code, and I was not able to execute git or dugite in this environment to verify the proof-of-concept described in the question (creating a local tag literally named `--dry-run` and observing dugite's argv). The code-level facts I *can* confirm are:
- `tag.ts`'s `deleteTag`/`createTag` are missing the `--` separator used elsewhere in the codebase for the same class of untrusted input, an inconsistency.
- No sanitization/validation of `name` is done before it reaches the `git()` call in `tag.ts` or in `git-store.ts`/`dispatcher.ts`/`app-store.ts` along the path to `deleteTag`.

### Impact Explanation
If a ref name starting with `-` can indeed reach `git tag -d <name>` as `argv[2]`, it would be interpreted as a flag rather than a ref, e.g. `--force` combined with other flags in future git versions, or on some git versions the delete could target unrelated data or cause unexpected behavior. In the current code the only extra argument is `-d name`, so injecting a single following option is limited in the current git-tag surface (no such thing as multi-flag pipeline here), which somewhat limits impact compared to full command injection.

### Likelihood Explanation
Likelihood is uncertain and dependent on an external precondition outside GitHub Desktop's control — whether the git binary itself allows fetching/creating a local tag ref whose short name begins with `-`. Modern git's `check-ref-format` has historically rejected ref components that would be misinterpreted as options in several such fixes, so this may already be mitigated upstream by git itself, independent of Desktop's code.

### Recommendation
Regardless of whether git currently blocks such names, defense-in-depth is warranted: add a `'--'` separator before `name` in both `createTag` and `deleteTag` in `app/src/lib/git/tag.ts`, consistent with the pattern already used in `checkout.ts`, `reset.ts`, `rm.ts`, and `add.ts` in this codebase.

### Proof of Concept
Not verified in this environment — I do not have terminal/git execution access to reproduce the suggested PoC (creating a local tag literally named `--dry-run` and calling `GitStore.deleteTag` while inspecting dugite's `argv`). This would need to be confirmed with an actual git/dugite invocation to determine whether such a ref name can exist as a local tag at all, which is the crux of whether this is exploitable in practice.

**Caveat:** Given I could not conclusively verify (a) that an attacker-controlled remote can cause such a hyphen-prefixed tag ref to be created locally via fetch (git's own ref validation may block this), and (b) actual argv behavior via dugite, I cannot certify with confidence that this is fully exploitable end-to-end as described. The code-level inconsistency (missing `--` guard) is real and should be fixed, but I do not have enough certainty to assert unprivileged remote-triggered exploitability meets the "Valid Impact" bar without confirmation that git allows creating such tag refs from a fetch. If precise confirmation of the git-level behavior is required, that would need to be tested with an actual git/dugite execution environment, which is outside my current tool capabilities.

```typescript
export async function getAllTags(
  repository: Repository
): Promise<Map<string, string>> {
  const args = ['show-ref', '--tags', '-d']

  const tags = await git(args, repository.path, 'getAllTags', {
    successExitCodes: new Set([0, 1]), // when there are no tags, git exits with 1.
  })

  const tagsArray: Array<[string, string]> = tags.stdout
    .split('\n')
    .filter(line => line !== '')
    .map(line => {
      const [commitSha, rawTagName] = line.split(' ')

      // Normalize tag names by removing the leading ref/tags/ and the trailing ^{}.
      //
      // git show-ref returns two entries for annotated tags:
      // deadbeef refs/tags/annotated-tag
      // de510b99 refs/tags/annotated-tag^{}
      //
      // The first entry sha correspond to the blob object of the annotation, while the second
      // entry corresponds to the actual commit where the tag was created.
      // By normalizing the tag name we can make sure that the commit sha gets stored in the returned
      // Map of commits (since git will always print the entry with the commit sha at the end).
      const tagName = rawTagName
        .replace(/^refs\/tags\//, '')
        .replace(/\^\{\}$/, '')

      return [tagName, commitSha]
    })

  return new Map(tagsArray)
}
```
