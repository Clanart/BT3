## Confirmed: SinglePlusAnyoneCanPay signature enforced

This confirms the payout transaction's user signature must use `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) . Under BIP341, `SIGHASH_SINGLE | ANYONECANPAY` commits only to the single input being spent and the output at the matching index (index 0, the user's payout output) — it does **not** commit to any other outputs, including the anchor output or the OP_RETURN output that embeds the operator's x-only pubkey [2](#0-1) .

### Title
Malleable payout OP_RETURN allows misattribution of the fronting operator - (`core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The user's payout signature uses `SIGHASH_SINGLE|ANYONECANPAY`, which does not commit to the OP_RETURN output that records which operator fronted the withdrawal. Because that output is unsigned, any party that observes the user's signature (broadcast by one operator, or obtained off-chain) can rebuild an equivalent payout transaction embedding a *different* operator's x-only pubkey in the OP_RETURN output and get it confirmed instead, before the original operator's version lands. The bridge later treats the OP_RETURN content as authoritative proof of "the payer" for reimbursement purposes.

### Finding Description
`create_payout_txhandler` builds the payout tx with: (1) the user output (KeySpend input 0), (2) an anchor output, (3) an OP_RETURN output containing `operator_xonly_pk` [2](#0-1) . The witness is set with `set_p2tr_key_spend_witness(&user_sig, 0)`, and the parser enforces the user's signature sighash type must be `SinglePlusAnyoneCanPay` [1](#0-0) .

`SIGHASH_SINGLE|ANYONECANPAY` in Taproot only commits to input 0 and output 0; outputs 1 (anchor) and 2 (OP_RETURN with operator pubkey) are entirely unconstrained by the signature. Since operator identity is embedded only in output 2, any actor holding the raw signature+input data (e.g., another operator racing to front the same withdrawal, or anyone who intercepts the broadcast payout tx in the mempool before confirmation) can construct an alternate valid transaction spending the same input, with the same user output, but a different (their own) OP_RETURN pubkey — and get it mined first via fee bumping.

Downstream, `update_finalized_payouts` in `core/src/verifier.rs` extracts the operator pubkey strictly from this OP_RETURN and stores it as the "payer" of record [3](#0-2) . `validate_payer_is_operator` in `core/src/operator.rs` and `send_asserts`'s consistency check (`payout_op_xonly_pk != kickoff_data.operator_xonly_pk`) both rely on this same DB-recorded value to authorize which operator may claim reimbursement [4](#0-3) [5](#0-4) . Since the OP_RETURN is malleable relative to the signed data, the binding "party that fronted the withdrawal == operator credited in DB" can be broken by an unauthenticated third party who never funded the payout.

### Impact Explanation
This breaks the custody-attribution binding explicitly listed as Critical: "an operator reimbursed for a payout it never funded." If a malicious actor (who need not be an operator themselves, or a competing operator) replaces the OP_RETURN with an arbitrary operator's xonly pubkey and gets that version confirmed instead of the honest operator's broadcast, the honest operator who paid the user's withdrawal amount from `input_prevout`/off-chain funding effort ends up with `payer_xonly_pk` in the DB not matching them, permanently blocking their reimbursement path (`validate_payer_is_operator` rejects them), while a completely different, unfunding party gets attributed credit and can subsequently attempt `send_asserts`/kickoff to claim the reimbursement UTXO chain for a payout they never made.

### Likelihood Explanation
Exploitation requires only observing the user's `SinglePlusAnyoneCanPay` signature and the input UTXO/output details, both of which are transmitted to the acting operator over gRPC (`withdraw` RPC) and become visible immediately once the payout transaction is broadcast to the mempool (before confirmation). Any party monitoring the mempool, or any of the multiple operators contacted for a withdrawal, can race to substitute their own OP_RETURN and pay a competitive fee to get their version confirmed first — this requires no operator role privilege beyond being able to construct and broadcast a standard Bitcoin transaction, which fits the "unauthenticated state-changing/broadcasting call" impact category (High), potentially rising to Critical (permanent operator reimbursement loss) if it also causes an honest operator to be permanently unable to claim reimbursement.

### Recommendation
Change the sighash type required for the user's payout signature to `SIGHASH_ALL` (or at minimum `SIGHASH_SINGLE` without `ANYONECANPAY`, and ensure all outputs including OP_RETURN are covered), so the operator identity embedded in the OP_RETURN output is cryptographically bound to the user's authorization and cannot be substituted by any third party after the fact.

### Proof of Concept
1. User signs a payout authorization off-chain with `TapSighashType::SinglePlusAnyoneCanPay` for input `in_outpoint` and output `out_script_pubkey`/`out_amount`, and submits it (e.g., via `withdraw` RPC) to Operator A.
2. Operator A calls `create_payout_txhandler(input_utxo, output_txout, operator_A_xonly_pk, user_sig, network)` [2](#0-1) , producing tx `T_A` with OP_RETURN = `operator_A_xonly_pk`, and broadcasts `T_A`.
3. Before `T_A` confirms, an unauthorized third party (or competing Operator B) observes `T_A` in the mempool, extracts `in_outpoint`, `output_txout`, and `user_sig` (all publicly visible in the unconfirmed transaction), and constructs `T_B` = `create_payout_txhandler(input_utxo, output_txout, operator_B_xonly_pk, user_sig, network)`. Since `user_sig` only commits to input 0 and output 0 under `SinglePlusAnyoneCanPay`, `T_B` remains a valid signature verification for the taproot key-spend even with a different anchor amount/OP_RETURN content, as long as output 0 is unchanged.
4. Operator B broadcasts `T_B` with a higher fee (RBF) so it confirms in place of `T_A`.
5. `update_finalized_payouts` records Operator B's xonly pubkey as the payer for this withdrawal [3](#0-2) , even though Operator A funded the user's withdrawal via `T_A`'s (unconfirmed, replaced) transaction. Operator A can never satisfy `validate_payer_is_operator` for this deposit and is permanently locked out of reimbursement, while Operator B is credited without having funded anything of independent value (or, in a variant, may not have funded at all if it can produce output-0-identical construction without funding cost beyond fees).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
