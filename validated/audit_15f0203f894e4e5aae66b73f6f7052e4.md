### Title
Attacker-fronted `Payout` transaction can misattribute reimbursement to an arbitrary operator via the unverified OP_RETURN xonly-pubkey - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The BendDAO bug binds a value-moving action to the wrong actor identity by using `msg.sender` where `receiver` was intended. Clementine has an analogous unbound-identity issue: the operator credited for having "fronted" a withdrawal (and thus entitled to reimbursement from the vault) is derived purely from an OP_RETURN output inside the `Payout` transaction, not from any signature or spend-authorization proving that operator actually funded the payment.

### Finding Description
`create_payout_txhandler` builds the `Payout` transaction with the withdrawal UTXO as its only signed input (spent via the user's pre-signed `SinglePlusAnyoneCanPay` signature), and appends an OP_RETURN output containing an arbitrary `operator_xonly_pk` parameter supplied by whoever calls the function: [1](#0-0) 

Because the sighash type is `SinglePlusAnyoneCanPay`, the user's signature only commits to the single payout output and does not cover the OP_RETURN output or any other outputs/inputs added to the transaction. Anyone possessing the pre-signed withdrawal outpoint and signature (broadcast openly for operators to use) can therefore construct and broadcast the `Payout` transaction themselves while writing a victim operator's `xonly_pk` into the OP_RETURN output, fronting the withdrawal cost with their own funds/fee inputs (since anchor-output CPFP funding is external) but attributing the fronting to the victim operator.

On the verifier side, `update_finalized_payouts` reads this OP_RETURN value directly as the "payer" without any additional binding check: [2](#0-1) 

This value is persisted via `update_payout_txs_and_payer_operator_xonly_pk` into the `withdrawals.payout_payer_operator_xonly_pk` column: [3](#0-2) 

Later, `is_kickoff_malicious` only checks that the kickoff's `operator_xonly_pk` equals the value stored from the OP_RETURN — it never confirms that the credited operator's own signature or funds were used to broadcast the `Payout` tx: [4](#0-3) 

And `handle_finalized_payout`/`send_asserts` similarly trust the DB-recorded `payout_op_xonly_pk` to authorize kickoff/reimbursement for that operator: [5](#0-4) 

The binding that should hold is: `operator credited in OP_RETURN == operator who actually paid (funded) the withdrawal`. Because the OP_RETURN content is neither signed by the credited operator nor tied to who supplied the transaction's funding/fee inputs, this binding can be broken by anyone who obtains a user's pre-signed withdrawal payload (which operators exchange/relay to construct `Payout` txs, and which is also accepted directly via the unauthenticated `internal_withdraw`/`withdraw` gRPC on any operator).

### Impact Explanation
If an attacker broadcasts the `Payout` transaction with a victim operator's xonly-pubkey in OP_RETURN, the verifier network's Citrea-block scan will attribute that withdrawal to the victim operator. The victim operator becomes eligible (`get_first_unhandled_payout_by_operator_xonly_pk`) to submit a kickoff for reimbursement it never funded, or — more damagingly — a legitimate operator who actually paid the withdrawal amount could have their fronted payout attributed to a different xonly-pubkey (or a non-existent one), permanently preventing that honest operator from ever being reimbursed for BTC it genuinely paid out. This matches the Critical impact category: "an operator reimbursed for a payout it never funded" / "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
The withdrawal input UTXO and the user's `SinglePlusAnyoneCanPay` signature are, by design, shared off-chain with any operator to construct the payout transaction (`internal_withdraw`/`withdraw` RPCs accept these params from any caller per `core/src/rpc/operator.rs`). `SinglePlusAnyoneCanPay` explicitly allows adding/paying for extra inputs, meaning any party — not just operators — holding the signature and outpoint can complete and broadcast the transaction, and can freely choose the OP_RETURN payload. No unprivileged-attacker capability beyond observing/obtaining the shared signature is required.

### Recommendation
Cryptographically bind the OP_RETURN operator attribution to actual custody of the withdrawal funds — e.g., require the OP_RETURN output (or an equivalent additional output/witness) to be committed under the same signature that authorizes spending the withdrawal UTXO (use `AllPlusAnyoneCanPay`/`Default` sighash covering the OP_RETURN output, or have the credited operator co-sign the transaction), so that the identity recorded on-chain cannot be forged by a third party who merely relays the pre-signed payload.

### Proof of Concept
1. User signs a withdrawal payload (`input_outpoint`, `input_signature` with `SinglePlusAnyoneCanPay`, `output_script_pubkey`, `output_amount`) and this is available to any operator via the `withdraw`/`internal_withdraw` RPC flow, per `core/src/rpc/operator.rs:168-259`.
2. Attacker (not operator B) constructs a `Payout` transaction using `create_payout_txhandler` logic, spending the same withdrawal UTXO with the user's signature, but sets `operator_xonly_pk` = operator B's xonly pubkey in the OP_RETURN (`operator_reimburse.rs:407-436`), funding any extra fee inputs themselves.
3. Attacker broadcasts this transaction to Bitcoin.
4. Verifier's `update_finalized_payouts` scans the block, extracts operator B's pubkey from OP_RETURN, and records `payout_payer_operator_xonly_pk = operator B` in the `withdrawals` table (`verifier.rs:2283-2352`, `database/verifier.rs:198-251`).
5. Operator B — who never funded this payout — is now the operator whose kickoff will pass the `is_kickoff_malicious` check (`verifier.rs:1857-1890`) and can claim reimbursement (`operator.rs:1275-1296`), or conversely the true payer is unable to claim reimbursement because attribution went to operator B.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
