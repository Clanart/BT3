### Title
Attacker-controlled `WWW-Authenticate` header lets a malicious git remote spoof a trusted "GitHub Enterprise" identity and drive Desktop's native sign-in/OAuth flow to an arbitrary attacker domain - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The external report's broken invariant is: a single trust-determining value (`GOVERNANCE`) can be redirected by an untrusted party, and every privileged operation downstream blindly follows that value with no independent verification. The closest analog in GitHub Desktop is the git-credential-helper's host classification logic in `getEndpointKind()`, which decides whether a git remote should be treated as a first-class "GitHub"/"enterprise" host. That decision is derived, without further verification, from HTTP response metadata (`WWW-Authenticate` headers) that is fully controlled by the remote git server/proxy the user is cloning or fetching from.

### Finding Description
`getEndpointKind()` [1](#0-0)  classifies a credential request's target host in this order:
1. Known dotcom/GHE hostname checks (safe, based on Desktop's own constants).
2. **Any `wwwauth[...]` entry whose value contains `realm="GitHub"` is trusted immediately and the endpoint is classified `'enterprise'`** — no cross-check against a known account, no TLS validation beyond the fact HTTPS was used, and no confirmation that the server is actually a GitHub product.
3. Only if that heuristic fails does Desktop fall back to `isGitHubHost()`, which performs an actual network probe for `x-github-request-id`.

Git captures `WWW-Authenticate` challenge headers verbatim from whatever HTTP(S) server answers the clone/fetch/push request and forwards them to Desktop's credential helper as `wwwauth[]` entries [2](#0-1) . This value is attacker-controlled: any git remote (or a MITM/compromised proxy sitting in front of a legitimate-looking clone URL) can respond to the unauthenticated request with `WWW-Authenticate: Basic realm="GitHub"` and be instantly classified as an "enterprise" GitHub host by Desktop.

Once classified `'enterprise'`, `getCredential()` checks whether an account already exists for that host; if not, it invokes `ui.promptForGitHubSignIn(endpoint)` [3](#0-2) . That function calls `dispatcher.beginEnterpriseSignIn()` and `dispatcher.setSignInEndpoint(origin)` using the **attacker's own origin**, then shows the native `SignIn` popup [4](#0-3) . This drives Desktop's real `SignInStore` state machine into `SignInStep.Authentication` for that attacker-chosen endpoint and, when the user clicks continue, opens the system browser at `getOAuthAuthorizationURL(endpoint, csrfToken)` — a URL built directly from the attacker-controlled endpoint [5](#0-4) [6](#0-5) .

The corrupted value is the **host-trust classification (`endpointKind`) and, downstream, the sign-in `endpoint`**, both of which should only ever be derived from information Desktop itself controls (its known GitHub.com/GHE.com domain list, or a verified `/meta` probe), but are instead accepted from unauthenticated, attacker-suppliable HTTP metadata. Existing guards do not stop this path: the dotcom/GHE checks only rule out spoofing github.com/ghe.com's *known* names, they do not prevent an arbitrary third-party domain from being labeled "enterprise" via the header; the network-probe fallback (`isGitHubHost`) is only reached if the header heuristic doesn't fire first, meaning the "cheap" and stronger of the two checks is also the one an attacker fully controls.

### Impact Explanation
An attacker who controls the HTTP(S) server behind a git remote URL (a scenario squarely inside GitHub Desktop's threat model — "attacker controls a fetched/cloned repository's remote/proxy response") can cause Desktop to:
- Present its own trusted, native "Sign in to GitHub Enterprise" UI chrome for a domain the attacker fully controls, increasing the credibility of a phishing page opened in the user's system browser at that attacker domain.
- Persist a resulting "enterprise" `Account` (login/token/emails all served by the attacker's own OAuth endpoint responses) into `AccountsStore`, which is then treated as a legitimate account for all future trampoline credential lookups against that origin (`findGitHubTrampolineAccount`), and is exposed via `authenticated-image-filter.ts`'s per-origin token map for private-asset requests to that same origin.
- More broadly, this misclassification abuses a legitimate app-native trust surface (the GitHub-brand sign-in flow) purely by shaping a response header, with no user action beyond a normal `git clone`/`fetch` of an attacker-authored repository.

This does not directly exfiltrate a *different, pre-existing* account's token (matching for real accounts is scoped by exact origin), so it stops short of a full credential-theft primitive against unrelated GHE accounts, but it does allow spoofing a trusted first-party UI/OAuth surface driven entirely by attacker-controlled remote metadata — a real erosion of the trust boundary between "content served by an untrusted remote" and "Desktop's own security-sensitive sign-in chrome."

### Likelihood Explanation
Likelihood is Medium: any user who clones or fetches from a malicious/compromised remote (a common, unprivileged action) will trigger this path automatically the first time git challenges for credentials on that host, with no additional user interaction required to reach the spoofed sign-in prompt.

### Recommendation
Do not trust `WWW-Authenticate: realm="GitHub"` headers as sufficient evidence of a GitHub/Enterprise host. At minimum, require the network-based `isGitHubHost()` verification (which checks for `x-github-request-id` on a real `/meta` HEAD request) before ever classifying an unknown host as `'enterprise'`, or require both signals to agree. Additionally, surface a clear, non-dismissible UI indicator in the sign-in dialog when it was triggered implicitly by a credential request (as opposed to a user explicitly choosing "Sign in to Enterprise" from settings), showing the exact hostname being authenticated against.

### Proof of Concept
1. Attacker stands up an HTTPS server at `https://evil.example` that serves a valid git-smart-http response for `/info/refs?service=git-upload-pack`, but answers any unauthenticated request with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim runs `git clone https://evil.example/foo/bar.git` inside GitHub Desktop (or fetches an existing repo whose remote was changed to this URL).
3. Git forwards the `WWW-Authenticate` header to Desktop's credential helper trampoline as a `wwwauth[0]=Basic realm="GitHub"` field.
4. `getEndpointKind()` [2](#0-1)  returns `'enterprise'` for `evil.example` without any further check.
5. `getCredential()` finds no existing account for `apiEndpoint` and calls `ui.promptForGitHubSignIn('https://evil.example')` [3](#0-2) , which begins Desktop's native Enterprise sign-in flow bound to `evil.example`.
6. Desktop opens the system browser at `https://evil.example/login/oauth/authorize?...` [6](#0-5) , an attacker-controlled page indistinguishable in Desktop's own UI from a legitimate GHE sign-in, and any account data (`login`, `token`) the attacker's fake OAuth endpoint returns is accepted and stored via `AccountsStore.addAccount`.

Note: I was not able to fully verify how `AuthenticationForm` (`app/src/ui/lib/authentication-form.tsx`) renders for non-dotcom, non-browser sign-in (e.g., whether it ever solicits a raw username/password that could be phished directly rather than only supporting the browser-based OAuth handoff) — the index did not return that file's contents. Starting a full Devin session against the repo would allow inspecting that file to determine if a more direct credential-phishing variant (username/password entry) is also reachable through this same misclassification path.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }

export function getOAuthAuthorizationURL(
  endpoint: string,
  state: string
): string {
  const urlBase = getHTMLURL(endpoint)
  const scope = encodeURIComponent(oauthScopes.join(' '))

  return new window.URL(
    `/login/oauth/authorize?client_id=${ClientID}&scope=${scope}&state=${state}`,
    urlBase
  ).toString()
}
