### Title
Panic on unregistered participant index in PedPoP blame evaluation enables unprivileged denial of service - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `HashMap`s with caller-supplied `Participant` values (`self.enc_keys[&decryptor]`, `self.commitments[&sender]`) without validating that the indexes were registered. Since `Participant` accepts any nonzero `u16`, an accusation naming a sender or recipient outside `1 ..= n` causes an unconditional panic, aborting the process handling the blame proof — a denial of service reachable purely from attacker-chosen accusation fields, analogous to CVE-2017-6266's "improper access controls → unprivileged DoS".

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` take `sender`, `recipient`, the encrypted share message, and an optional `EncryptionKeyProof` — all derived from a public accusation. They call `blame_internal`, which calls `Decryption::decrypt_with_proof`. When a proof is provided, `decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` (encryption.rs:388), a `HashMap` index that panics if `decryptor` was never registered. `enc_keys` is only populated for participants `1 ..= n` (in `verify_r1` via `Encryption::register`, and in `AdditionalBlameMachine::new` at lib.rs:656-660). Likewise, `blame_internal` evaluates `self.commitments[&sender]` (lib.rs:599), panicking for a `sender` outside `1 ..= n`.

There is no bounds check on `sender`/`recipient` anywhere in the blame path: `Participant::new` permits any value `1 ..= u16::MAX`, so `recipient = Participant(n + 1)` (or `65535`) with `proof = Some(...)` deterministically panics. The blame API is explicitly designed to process accusations from arbitrary accusers ("the accuser") — this is untrusted input by construction.

### Impact Explanation
A panic inside `blame_internal` unwinds through `BlameMachine::blame` / `AdditionalBlameMachine::blame`, killing the thread/task evaluating the accusation. In a coordinator/validator context where blame transactions are evaluated by all honest nodes (e.g., an `InvalidDkgShare`-style accusation naming arbitrary `accuser`/`faulty` participants), a single crafted accusation can crash every node that evaluates it, halting DKG completion and any dependent signing. This is an availability-only impact matching the source CVE's C:N/I:N/A:H profile.

### Likelihood Explanation
Exploitation requires only the ability to submit a blame accusation — the exact unprivileged surface the API exists for. No threshold participation, valid signature on the encrypted share, or key knowledge is needed: the panic fires on the `HashMap` index before any cryptographic check on `recipient`/`sender` legitimacy, and `decrypt_with_proof` only requires `msg.pop` to verify (or reaches the index whenever `proof.is_some()` and the PoP check ordering allows). The accuser controls both the `sender`/`recipient` fields and whether `proof` is `Some`, making the crash deterministic.

### Recommendation
Validate `sender` and `recipient` at the top of `blame_internal` (or `blame`): return an error (or a defined blame result) when either is not present in `self.commitments`/`self.encryption.enc_keys`, instead of indexing. Replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor).ok_or(DecryptionError::...)` and `self.commitments[&sender]` with a checked `get`. Add a regression test calling `AdditionalBlameMachine::blame` with `sender`/`recipient` equal to `Participant(n + 1)` and `u16::MAX`.

### Proof of Concept
```rust
// crypto/dkg/pedpop context: n = 3 participants, blame evaluated by any party.
// Construct AdditionalBlameMachine from the public commitment messages:
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker-controlled accusation: recipient index beyond the participant set.
let recipient = Participant::new(4).unwrap(); // valid Participant, not in 1..=n
let sender = Participant::new(1).unwrap();

// Any EncryptionKeyProof (even garbage) suffices to reach the indexing panic,
// since `self.enc_keys[&decryptor]` panics regardless of proof validity.
let proof = Some(any_encryption_key_proof);
let msg = msg_with_valid_pop_for_sender_1; // pop.verify must pass to reach line 388

machine.blame(sender, recipient, msg, proof);
// decrypt_with_proof -> self.enc_keys[&Participant(4)] -> thread panics: "key not found"
```

Equivalently, `sender = Participant::new(4)` with a `recipient` in-range and a valid proof causes the panic at `self.commitments[&sender]` (lib.rs:599) once decryption succeeds. The root cause is missing access validation on map indexes for attacker-controlled `Participant` values — the direct analog of the CVE's improper-access-control denial of service.
