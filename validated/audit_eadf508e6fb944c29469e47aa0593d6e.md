### Title
Unvalidated `sender`/`recipient` participant indexes in PedPoP blame evaluation cause an index-out-of-map panic, giving any party a repeatable remote DoS - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `Decryption::decrypt_with_proof` all accept `Participant` values supplied by the accusing party (as part of the publicly submitted blame accusation, alongside the `EncryptedMessage` bytes parsed by `EncryptedMessage::read`) and index internal `HashMap`s with them without checking membership. A `Participant` index that is nonzero but not a member of the DKG set (e.g. `n + 1`, or any index absent from `commitments`/`enc_keys`) causes a `HashMap` indexing panic, crashing the process evaluating the blame. This mirrors the CVE-2019-2819 class: easily repeatable crash/DoS triggered over the protocol path, with a secondary integrity concern that a panic prevents the honest completion path of the DKG blame protocol.

### Finding Description
`blame_internal` is the single entry point used by both `BlameMachine::blame` and `AdditionalBlameMachine::blame`. It passes its arguments straight into `Decryption::decrypt_with_proof` and later into `self.commitments[&sender]`:

`crypto/dkg/pedpop/src/lib.rs` (`blame_internal`):

...
multiexp_vartime(&share_verification_statements::<C>(
  recipient,
  &self.commitments[&sender],   // panics if `sender` not in map
  ...

Inside `decrypt_with_proof`, the DLEq verify statement indexes the registered encryption keys with the accuser-supplied `decryptor` participant:

`crypto/dkg/pedpop/src/encryption.rs`:
```rust
&[C::generator(), msg.key],
&[self.enc_keys[&decryptor], *proof.key],
``` [2](#0-1) 

Neither `sender`, `recipient`, nor `decryptor` is checked against `1 ..= n` or against map membership. `Participant::new` only rejects zero (`crypto/dkg/src/lib.rs` lines 29–35), so `Participant::new(n + 1)` or any valid-but-foreign index is accepted. `commitments` and `enc_keys` are populated exclusively for `1 ..= n` (`verify_r1` iterates `all_participant_indexes()` at `pedpop/src/lib.rs:313`; `AdditionalBlameMachine::new` iterates `1 ..= n` at line 656), so any out-of-range or missing index unconditionally panics via `HashMap`'s `Index` impl. Additionally, if `proof` is `None`, `decrypt_with_proof` returns `InvalidProof` before the panic — but with a `Some(proof)` the `enc_keys[&decryptor]` panic fires, and regardless of proof, a valid-PoP `msg` reaches `self.commitments[&sender]` which panics.

Note the `blame` API is explicitly designed for untrusted input: the doc comments state the message "must have been authenticated as actually having come from the sender" but place no restriction on `sender`/`recipient` being members of the set, and `AdditionalBlameMachine::new` exists precisely so non-participants (e.g. coordinator/observer nodes) can evaluate arbitrary accusations — maximally exposed to attacker-chosen indexes.

### Impact Explanation
Any party able to submit a blame accusation (a DKG participant, or anyone whose accusations are relayed to validators/observers running `AdditionalBlameMachine`) can crash every node that evaluates it by naming a `sender`/`recipient` outside `1 ..= n`, or simply a `sender` whose commitments were never registered. The panic is deterministic and repeatable, matching "frequently repeatable crash (complete DOS)". For `BlameMachine::blame` this also aborts the protocol after consuming the machine, permanently preventing the honest party from completing DKG blame resolution for that session. A panicking validator mid-DKG can stall key generation or signer-set rotation network-wide.

### Likelihood Explanation
Triggering requires only constructing an accusation tuple `(sender, recipient, msg, proof)` where `sender` or `recipient` is a `Participant` value not present in the evaluator's maps. `msg` must carry a valid PoP signature for the `commitments[&sender]` path to be reached; an attacker who is themselves a DKG participant can produce a self-signed `EncryptedMessage` trivially, then accuse "sender = n+1". For the `enc_keys[&decryptor]` path, the accuser names a non-member `recipient`, which requires no PoP validity at all since the map lookup happens before decryption is attempted (the DLEq verify at `encryption.rs:383-390` indexes `enc_keys` before `apply_keystream`). Single-message, no collusion, no privileges beyond participating in or submitting accusations to the protocol.

### Recommendation
Validate `sender`, `recipient`, and `decryptor` against the registered participant set before indexing. In `blame_internal`, return the accusing party (or a dedicated error) when `sender`/`recipient` are not in `self.commitments`; in `decrypt_with_proof`, use `enc_keys.get(&decryptor)` and return `DecryptionError::InvalidProof` (or a new `InvalidParticipant` variant) on `None` instead of indexing. Also consider having `blame` return `Result`/`Option` rather than a bare `Participant` so malformed accusations can be rejected without state-machine consumption.

### Proof of Concept
```rust
// Evaluator side: completed DKG for params t=2, n=3 (any instantiation).
// Attacker submits a blame accusation naming a non-member participant.

let attacker = Participant::new(1).unwrap();
let ghost = Participant::new(4).unwrap(); // n = 3, so 4 is out of set

// Path 1: recipient out of range -> Decryption::decrypt_with_proof panics at
// `self.enc_keys[&decryptor]` (encryption.rs:388) before any share check.
blame_machine.blame(attacker, ghost, msg_with_valid_pop, Some(proof));

// Path 2: sender out of range -> blame_internal passes the PoP check, then
// `self.commitments[&sender]` (lib.rs:599) panics on the missing key.
blame_machine.blame(ghost, attacker, msg_with_valid_pop, Some(proof));

// Same crash for a third-party observer:
let mut observer = AdditionalBlameMachine::<C>::new(context, 3, commitment_msgs)?;
observer.blame(ghost, attacker, msg, Some(proof)); // panic: HashMap index
```

Each call deterministically hits a `HashMap` `Index` panic because `commitments`/`enc_keys` contain only keys `1 ..= n`, while `ghost` is a well-formed `Participant` (`new` only rejects 0). No validity checks on participant membership exist anywhere along the blame path.

Caveat: I was unable to inspect downstream callers (coordinator/processor blame-routing code is outside the in-scope crates), so exact deployment reachability of `blame()`/`AdditionalBlameMachine` — i.e., whether accusations with arbitrary indexes are relayed by honest nodes — could not be fully confirmed from the in-scope code alone. The library-level panic itself is unconditional.
