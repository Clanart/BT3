### Title
Trusting an "unsafe" (dubious-ownership) repository path is stored permanently and never re-validated - (File: `app/src/lib/git/config.ts`, `app/src/ui/add-repository/add-existing-repository.tsx`, `app/src/ui/missing-repository.tsx`)

### Summary
The report's broken invariant is: a security-relevant boolean/state (`lockCrv`) can be toggled, but the function that depends on it (`withdrawLock()`) never re-checks the current value of that state before acting, so the guard is effectively bypassed once the state has changed. The GitHub Desktop analog is the "untrusted/unsafe repository" gate: once a user clicks **Trust repository**, Desktop calls `addSafeDirectory()` [1](#0-0)  which permanently whitelists that filesystem path in git's global `safe.directory` config. From that point forward `getRepositoryType()` will always report the path as `regular` [2](#0-1)  regardless of whether the directory's ownership/content later changes — the app never re-verifies that the trust decision is still valid for whatever is actually on disk at that path when it re-opens it.

### Finding Description
`getRepositoryType()` asks git whether a path has "dubious ownership" and returns `{ kind: 'unsafe', path }` when it does [3](#0-2) . Desktop surfaces this in the UI (`AddExistingRepository`, `MissingRepository`) and offers a one-time **Trust repository** action that calls `addSafeDirectory(path)` to add the path to git's `safe.directory` allowlist [1](#0-0) [4](#0-3) .

Once a path is in `safe.directory`, git (and therefore `getRepositoryType`) will unconditionally treat *any future content* at that exact path as trusted — there is no re-check tying the trust decision to the ownership/content that existed at the moment the user clicked "Trust". `_addRepositories()` in the app store only special-cases the `unsafe` kind by marking the repository `missing: true` at add time [5](#0-4) ; there is no subsequent point where Desktop asks "did the owner/content of this path change since I trusted it?" before running git operations (fetch, checkout, hooks, LFS smudge filters, etc.) against it. This mirrors the `withdrawLock()` bug: the guard (`isRepositoryUnsafe`/ownership check) is bypassed forever after a single toggle, with no re-validation before subsequent privileged operations.

### Impact Explanation
An attacker who can cause content to be written to a path a victim previously trusted (e.g. a shared/removable drive, a reused clone destination, or a directory an attacker can later take ownership of or replace) can have arbitrary git config, hooks, and filters executed the next time Desktop opens that path — because Desktop/git no longer perform the ownership check that was the only gate. Given Desktop's own changelog states "Adding untrusted repositories may automatically execute files in the repository" [6](#0-5) , silently and permanently disabling that check for a path is a code-execution-adjacent trust bypass, not merely a UX nuisance.

### Likelihood Explanation
Exploitation requires a specific setup (the same path previously trusted by the victim later coming under attacker control/content), which is a narrower precondition than the arbitrary "attacker controls a cloned/fetched repository" primitive described as valid in this task. I could not find any per-directory or per-content re-validation logic anywhere in `app-store.ts`, `add-existing-repository.tsx`, or `missing-repository.tsx` beyond the initial ownership check, and I did not have visibility into the exact `addSafeDirectory` implementation in `app/src/lib/git/config.ts` (index coverage limits) to confirm whether it scopes the exception more narrowly (e.g., to a specific git-dir hash) — this should be verified in the full source.

### Recommendation
- Re-run the ownership/ "unsafe" check (`getRepositoryType`) each time a previously-trusted repository is opened rather than relying solely on git's persistent global `safe.directory` allowlist.
- Consider scoping trust to the specific git repository content (e.g., first-commit SHA or `.git` directory identity) instead of just the filesystem path, so that overwriting a trusted path with different content forces re-confirmation.
- Audit `app/src/lib/git/config.ts`'s `addSafeDirectory` to confirm it isn't unintentionally broader (e.g., via glob/`*`) than the single path the user approved.

### Proof of Concept
1. User opens directory `D` (owned by user A) in Desktop; git reports dubious ownership; user clicks "Trust repository", which calls `addSafeDirectory(D)` [1](#0-0) , permanently adding `D` to `safe.directory`.
2. Later, an attacker gains control of `D` (e.g., replaces its contents, or the directory is on a shared/removable volume and re-created by another user) with a malicious `.git` config/hooks.
3. Desktop (or the user) reopens `D`; `getRepositoryType(D)` now returns `kind: 'regular'` because the ownership check is bypassed by the earlier `safe.directory` entry [7](#0-6) , so no unsafe warning is shown and Desktop proceeds to run git operations (fetch/checkout/hooks) against the now-attacker-controlled repository content without any re-confirmation from the user.
