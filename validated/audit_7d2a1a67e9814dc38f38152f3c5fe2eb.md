### Title
Reentrancy in `withdraw()` allows double-release of escrowed funds via state update after external call - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2`'s escrow-release function violates checks-effects-interactions: it decrements the escrow accounting balance **after** performing the external value/token transfer, and its only guard is a non-zero check rather than a sufficiency check. This is the same broken-invariant class as the zkSync report — a limit/accounting value is checked against state that has not yet been updated to reflect the very operation in progress, allowing an operation to proceed on stale accounting.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 682-721) is the escrow-release routine invoked from `onAccept()` (RedeemEscrow / RefundEscrow) and `onGetResponse()` (source-side cancellation). For each token in the withdrawal request it:

1. Checks only `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` — not `escrowed < amount`.
2. Performs the external transfer (`beneficiary.call{value: amount}("")` for native token, or `token.call(transfer(...))` for ERC-20).
3. Only afterward executes `_orders[body.commitment][token] -= amount;`. [1](#0-0) 

Compare this to the canonical EVM implementation in `IntentsBase.sol`, which computes `escrowed - amount` and writes it to storage **before** the external call (`_orders[body.commitment][token] = escrowed - amount;` precedes `beneficiary.call{value: amount}("")` / `safeTransfer`): [2](#0-1) 

Because the Tron variant transfers value to `beneficiary` (attacker-controlled address for native-token orders) before mutating `_orders[...]`, a malicious beneficiary contract can reenter during the `.call{value: amount}("")` callback. If that reentrant path reaches `withdraw()` again for the same commitment/token — e.g. through a second in-flight ISMP message processed by the host before the first message's receipt is marked, or through any other execution path that reads `_orders[body.commitment][token]` — it will observe the pre-decrement (stale, still-full) escrow balance and pass the same `== 0` check, allowing a second transfer of the same escrowed amount before the first decrement ever lands.

This is structurally identical to the `_verifyWithdrawalLimit` bug: the guard is evaluated against `address(this).balance` (or, here, `_orders[...][token]`) that has not yet been updated for the withdrawal currently in flight, so a value that should already be "spent" is still counted as available.

### Impact Explanation
This falls squarely within the required impact set: "stealing or loss of funds" and "replay/double-claim/double-settlement." A successful reentrant call drains escrowed input tokens (or fee-token proceeds) for a commitment beyond what was actually escrowed, at the expense of either the protocol's held reserves or other users' commitments sharing storage/liquidity, without any relayer, prover, or admin compromise — only a malicious beneficiary/solver-controlled contract acting as the native-token recipient.

### Likelihood Explanation
Exploitability depends on whether the ISMP host on the Tron deployment can be re-entered mid-processing of a batch (i.e., whether the receipt/commitment for a request is marked "handled" before or after invoking the module's `onAccept`). This ordering could not be fully confirmed within available tool calls — the host-side receipt-marking logic (`HandlerV2.sol` / `EvmHost.sol`) was located but not read in enough detail to establish whether it commits the receipt before or after the external `onAccept` call, or whether the surrounding dispatch path carries a `nonReentrant` guard. Regardless of that host-level mitigation, the escrow-accounting function itself is written in an unsafe order (transfer-then-decrement) relative to the correct pattern used elsewhere in the same codebase, which is a genuine code defect independent of whether a currently-known reentrancy trigger exists.

### Recommendation
- Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to follow checks-effects-interactions: read `escrowed = _orders[body.commitment][token]`, revert if `escrowed < amount` (not just `== 0`), write `_orders[body.commitment][token] = escrowed - amount` **before** any external call, mirroring `IntentsBase.sol`'s `_withdraw`.
- Add an explicit `nonReentrant` guard to `withdraw()` (and to the entry points that call it: `onAccept`, `onGetResponse`) as defense in depth, matching the `nonReentrant` modifier already used in the current EVM `IntentGatewayV2.cancelOrder`.
- Audit the Tron host's message-processing/receipt-commit ordering to ensure a request's receipt is marked before the module callback executes, closing the underlying reentrancy window regardless of app-level ordering.

### Proof of Concept
Conceptual trace (native-token order, single commitment `C` with escrowed amount `A`):
1. Order settles; Hyperbridge dispatches a `RedeemEscrow`/`RefundEscrow` POST to the Tron `IntentGatewayV2`, `beneficiary` = attacker-controlled contract.
2. Host invokes `onAccept` → `withdraw(body, isRefund)`.
3. Loop iteration for the native-token entry: `_orders[C][0x0] == 0`? No (`A` is escrowed) → passes.
4. `beneficiary.call{value: A}("")` executes, transferring `A` and yielding control to attacker's `receive()`/fallback.
5. Attacker's fallback triggers a reentrant path back into a context that again reaches `withdraw()`/`_orders[C][0x0]` before step 6 runs — at this point `_orders[C][0x0]` is still `A` (unchanged), so the check again passes and a second transfer of `A` is dispatched.
6. Only after control returns does `_orders[C][0x0] -= A` execute (once, or twice if reentered twice), leaving total transferred = `2A` against a single escrowed `A`.

This trace could not be validated end-to-end against the live host dispatch code within the available exploration budget; the concrete reentrant entry point on the host side is the piece that needs confirmation to fully weaponize this, but the escrow function's unsafe ordering is directly observable in the cited code.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
