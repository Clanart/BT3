### Title
Clone operation explicitly disables Git's built-in clone-time exploit protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: `app/src/lib/git/clone.ts`)

### Summary
The Sherlock report's root cause is a protective guard that exists in the underlying protocol (AMM slippage bounds) being explicitly zeroed out by the calling code, removing the safety net the system relies on. The direct analog in GitHub Desktop is in the `clone()` function, which explicitly sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` for every clone, disabling a safety mechanism that Git itself uses internally to guard against hostile clone content (attacker-controlled repository).

### Finding Description
`clone()` builds the execution environment for every "git clone" invocation as: [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is a Git-internal environment variable that Git's own clone/recursive-submodule machinery uses to track and enforce hook/hidden-file protections while a clone is in progress (protecting against attacker-supplied repository content — e.g. symlinked or case-confusable paths under `.git`, or nested submodule hooks — attempting to execute or write files outside the intended target during a `--recursive` clone). Desktop always invokes with `--recursive`: [2](#0-1) 

By forcing this variable to `'false'` in the child process environment, Desktop is telling Git's own protection logic to treat the clone as already "protected"/inactive rather than letting Git set and manage the flag itself, which suppresses the internal re-entrancy/activation check Git performs when it recursively invokes itself for submodules. This is the exact same failure pattern as the Cork report: a value that is supposed to enforce a safety bound (slippage minimum / clone protection flag) is hard-coded to the value that disables the check (`0` / `'false'`), rather than left to be computed or enforced by the underlying system.

The attacker primitive matches the "Valid Impact" criteria: the attacker controls the cloned/fetched repository (a malicious remote a user is enticed to clone, e.g. via a crafted `x-github-client://openRepo/...` deep link handled in `app/src/lib/parse-app-url.ts` and `dispatcher.openOrCloneRepository`), and the corrupted value is the clone-time hook/hidden-path protection state that Git relies on to prevent code execution or file writes outside the intended clone target during recursive submodule processing.

### Impact Explanation
If Git's recursive-clone protection is meant to guard against untrusted submodule content triggering hook execution or writing outside the working tree (the class of issue covered by Git's `clone.protection`/`GIT_CLONE_PROTECTION_ACTIVE` mechanism), forcing it off for every Desktop-initiated clone removes that guard for all users, regardless of Git version or configuration, whenever they clone or fetch an attacker-controlled repository through Desktop. This maps to the "code execution / file write outside the repo" impact bucket in the Valid Impact criteria.

### Likelihood Explanation
Every clone performed through Desktop (via UI clone dialog, `x-github-client://openRepo` deep links, or CLI `github clone`) passes through this code path unconditionally, and `--recursive` is always appended, so any attacker who can get a victim to clone/open a malicious repository (a normal, expected Desktop workflow, not requiring local access or elevated privileges) exercises this disabled-protection path.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Either omit the variable entirely and let Git manage its own internal protection state during recursive clone, or set it to `'true'`/leave it unset so Git's built-in protections remain active for the full duration of the (recursive) clone.

### Proof of Concept
Exact code that disables the guard: [3](#0-2) 
1. A victim uses Desktop to clone or open (via `x-github-client://openRepo/<attacker-url>`) a malicious repository containing crafted submodules/hooks designed to be caught by Git's clone-time protection.
2. Desktop calls `clone()`, which sets `GIT_CLONE_PROTECTION_ACTIVE=false` and always passes `--recursive`.
3. Because the protection flag Git relies on internally is forced off, Git does not treat the recursive clone as protected, defeating the check the flag exists to enforce.
