## Analog Found

The external report's core issue is: *an external, attacker-influenced object (a token's proxy implementation) can silently change behavior after the protocol already trusted it, breaking safety invariants the protocol relied on.* The closest analog in GitHub Desktop is **submodule URLs**, which are attacker-controlled data embedded inside a cloned/fetched repository (`.gitmodules`), combined with a flag that re-enables Git's `file://` protocol for submodule operations — a protocol that upstream Git disables by default specifically because it allows a malicious repository to make Git read files from arbitrary local paths (the class of bug fixed upstream as `protocol.file.allow` hardening, CVE-2022-39253).

### Title
Submodule updates can re-enable `file://` protocol, letting an attacker-controlled repository read arbitrary local paths - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol` boolean that, when true, passes `-c protocol.file.allow=always` to `git submodule update --init --recursive`. [1](#0-0) 
This mirrors the TUSD scenario: the "implementation" here is the submodule URL declared inside `.gitmodules`, which is fully controlled by whoever authored the cloned/fetched repository (an untrusted, attacker-controlled GitHub object), and Desktop's guard (`protocol.file.allow`) can be selectively disabled for that operation.

### Finding Description
Git disables the `file://` transport for submodules by default because it lets a repository author redirect Git to clone from an arbitrary local filesystem path on the victim's machine during `submodule update`. Desktop's `submodule.ts` explicitly re-enables this via `protocol.file.allow=always` when `allowFileProtocol` is `true`. [2](#0-1) 
`.gitmodules` content is part of the repository tree, so it is fully attacker-controlled the moment a user clones, fetches, or checks out a branch/PR from an untrusted remote — exactly the "attacker controls a cloned/fetched repository" primitive called out as valid impact. If any checkout/PR flow invokes `updateSubmodulesAfterOperation` with `allowFileProtocol = true` for such untrusted content, a `.gitmodules` entry like:
```
[submodule "x"]
  path = x
  url = file:///Users/victim/.ssh
```
would cause Git to perform a local "clone" of that path into the submodule directory, and Git's local-clone fast path can hardlink/copy objects from the source directory into `.git/modules/...`, allowing the attacker to exfiltrate file contents into the working repository (which the user may then commit, push, or otherwise expose).

I could not fully trace, within the available iterations, every call site in `app/src/lib/git/checkout.ts` (7 references) to confirm the exact condition under which `allowFileProtocol` is passed as `true` versus `false` for a given checkout — that call path needs direct inspection to determine whether it can be triggered from an untrusted PR/branch checkout without user consent. This is the one piece of the chain I was unable to verify with certainty in this session.

### Impact Explanation
If reachable from an untrusted checkout (e.g., checking out a fork's PR branch that Desktop fetched automatically), this allows arbitrary local file/directory disclosure into the victim's repository purely by having the user clone/fetch/checkout an attacker-supplied repository or PR — no local access, admin rights, or social engineering beyond normal Desktop usage required.

### Likelihood Explanation
Likelihood depends entirely on whether any of the 7 call sites in `checkout.ts` pass `allowFileProtocol: true` for content originating from a remote/PR the user did not author (as opposed to only being enabled for the user's own already-trusted local repository operations). Without confirming those call sites, I can only establish the vulnerable primitive exists in `submodule.ts`, not the full end-to-end trigger.

### Recommendation
- Audit every caller of `updateSubmodulesAfterOperation` in `app/src/lib/git/checkout.ts` and ensure `allowFileProtocol` is never `true` when the checked-out ref/branch originates from an untrusted remote or PR fork.
- Prefer Git's default-safe `protocol.file.allow=user` (or leave unset) instead of `always`, and if `file://` submodules must be supported, restrict allowed paths to inside the repository's own directory tree.

### Proof of Concept
Conceptual (not executed, since I could not confirm the exact untrusted-trigger call site):
1. Attacker creates a public repository with `.gitmodules` containing `url = file:///path/to/victim/sensitive/dir`.
2. Victim uses Desktop to clone/fetch/checkout this repository (or a PR referencing it).
3. If the checkout path invokes `updateSubmodulesAfterOperation(..., allowFileProtocol: true)`, Git performs a local clone of the sensitive path into the submodule directory of the victim's now-local repository, exposing its contents. [1](#0-0)
