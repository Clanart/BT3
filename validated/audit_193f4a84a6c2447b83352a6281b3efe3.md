## Title
Unvalidated attacker-controlled clone URL from Pull Request API data is passed directly to `git remote add` / `git fetch`, allowing protocol-smuggled remote injection - ([File: app/src/lib/stores/app-store.ts])

## Summary
`_findPullRequestBranch` in `app-store.ts` takes a `headCloneUrl` string that ultimately originates from a GitHub API pull-request object (`pullRequest.head.repo.clone_url`, reachable via the "Open PR in Desktop" deep link / `openPullRequestInDesktop` flow) and, if no existing remote matches it, calls `addRemote(repository, forkRemoteName, headCloneUrl)` and later `this._fetchRemote(...)` on it, with no scheme/format validation performed anywhere in this path. [1](#0-0) 

## Finding Description
The broken invariant mirrors the report's pattern: a value that is supposed to be re-validated/derived safely (the liquidation edge price, tied to `info.funds`) is instead trusted stale/unchecked. Here, the "derived value" is the git remote URL used for `addRemote`/`fetch`, and the untrusted input is the `head.repo.clone_url` field of a PR object retrieved from the GitHub API (or GHES), which is attacker-influenced content when the PR is opened by a third party against a repository the victim has open in Desktop.

`_findPullRequestBranch` receives `headCloneUrl` and:
1. Searches existing remotes for a URL match via `urlMatchesRemote`.
2. If none match, calls `addRemote(repository, forkRemoteName, headCloneUrl)` directly - no validation that this is an `https://`/`ssh://`/`git://` GitHub URL.
3. Then calls `this._fetchRemote(repository, remote, ...)`, which invokes `git fetch` against that URL. [2](#0-1) 

`addRemote`/`setRemoteURL` in `app/src/lib/git/remote.ts` pass the URL straight to the `git remote add`/`git fetch` command line with no allow-listing of protocol (e.g. rejecting `ext::`, `fd::`, or other Git transport helpers that can execute arbitrary commands, per historical Git CVE classes around dangerous transport helpers). [3](#0-2) 

Existing guards that stop *some* remote-URL tampering (`updateRemoteUrl`) only check protocol consistency and that the remote hadn't been "manually changed" from the previously cached GitHub clone URL — they are applied to a different code path (refreshing the default `origin` remote when the associated GitHub repo's clone_url changes) and do not apply to the fork-remote-add path used when checking out a PR branch. [4](#0-3) 

Because the value flows from an external, attacker-influenced API object into a security-relevant git operation without being revalidated against an expected scheme/host allowlist, this is structurally the same "stale/unchecked derived value used for a security-relevant decision" bug as the `perp_withdraw`/`change_edge_px` report: a downstream consumer (`git fetch`/`git remote add`) trusts a value it never independently verified was safe.

## Impact Explanation
If Git (bundled with Desktop) supports any transport helper syntax such as `ext::` or similarly dangerous URL schemes, an attacker who can get a PR head repo's `clone_url` accepted unchanged into this code path could achieve command execution in the context of the Desktop process/user when the victim uses "Open in Desktop" / checks out a PR, satisfying the "attacker controls ... a GitHub API object ... result is code execution" impact category. At minimum, an attacker-controlled URL string reaching `git remote add`/`git fetch` without protocol restriction is a credential/token exfiltration and SSRF-adjacent risk (the URL could point at an attacker-controlled HTTP(S) endpoint capturing the victim's credential-helper/auth headers during fetch).

## Likelihood Explanation
I could not fully confirm within this session whether `pullRequest.head.repo.clone_url` as returned by the GitHub API is constrained server-side to `https://github.com/...` (which would significantly limit attacker control), nor could I trace every caller of `_findPullRequestBranch` (dispatcher/app.tsx call sites) to confirm the exact deep-link trigger and whether any earlier validation step filters the URL before it reaches `app-store.ts`. This uncertainty is significant, and without confirming that `clone_url` can be attacker-shaped (e.g., through GHES or a compromised/MITM API response) the exploitability is unproven — I could not access the full contents of `main-process/main.ts` and `dispatcher.ts` call sites within the available tool budget.

## Recommendation
- In `_findPullRequestBranch` (and any other call site that calls `addRemote`/`setRemoteURL` with a URL sourced from GitHub API responses), validate that the URL: uses an allow-listed scheme (`https`, `ssh`, `git`), and matches the expected host of the account's endpoint (dot-com or the configured GHES host) via `urlMatchesRemote`-style host checking, before ever passing it to `addRemote`/`fetch`.
- Apply the same protocol/host guard used in `updateRemoteUrl` uniformly across every code path that writes a remote URL derived from API/PR data, rather than only for the `origin` remote refresh flow.

## Proof of Concept
Not confirmed as exploitable from local code alone — this requires verifying (via a Devin session with full repo/tool access) that:
1. `pullRequest.head.repo.clone_url` can be made attacker-controlled (e.g., PR raised from a fork, GHES instance, or MITM'd API response).
2. Git's bundled version in Desktop treats such a URL string with a dangerous transport scheme as executable, when passed through `addRemote`/`git fetch` in `app/src/lib/git/remote.ts`.

If both conditions hold, the following flow reaches the vulnerable path: `dispatcher.ts` → `app.tsx` "Open PR in Desktop" handler → `app-store.ts:_findPullRequestBranch` (`headCloneUrl` untouched) → `addRemote(repository, forkRemoteName, headCloneUrl)` → `this._fetchRemote(...)`. [2](#0-1)

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
