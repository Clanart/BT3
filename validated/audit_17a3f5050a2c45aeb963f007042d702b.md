## Analysis

I found a strong analog. The aiohttp bug is fundamentally about a supported public parser accepting **Unicode digits/characters where only ASCII should be permitted**, because the underlying primitive (`\d` in regex, or a locale-aware conversion) is broader than the wire-format grammar requires. This exact bug class exists in `python/google/protobuf/json_format.py`'s `_ConvertInteger`, used by the pure-Python `Parse`/`ParseDict` ProtoJSON entry points.

### Title
Pure-Python ProtoJSON integer parser accepts non-ASCII Unicode digits via Python's locale-independent but Unicode-aware `int()`/`float()` conversion — (File: `python/google/protobuf/json_format.py`)

### Summary
`_ConvertInteger` in the pure-Python `json_format.py` converts JSON `string`-encoded 64-bit integer field values (and integer-valued floats) with the builtin `int(value)` / `float(value)`. Python's `int()` and `float()) builtins, when given a `str`, accept any Unicode code point in category Nd (decimal digit), not only ASCII `0`-`9`. This mirrors the aiohttp flaw: a text-based grammar element (HTTP version digits / here, a signed decimal integer per the ProtoJSON spec) is validated with a primitive that is more permissive than the JSON/proto3 JSON mapping spec (which requires the value to be composed only of ASCII digits `[0-9]` optionally preceded by `-`).

### Finding Description
`_ConvertInteger` ( [1](#0-0) ) does:
```python
if isinstance(value, str) and value.find(' ') != -1:
    raise ParseError(...)
...
try:
    return int(value)
except ValueError as e:
    try:
        f = float(value)
    ...
```
It only checks for embedded ASCII spaces before calling `int()`/`float()`. It performs no character-class validation that the string consists solely of ASCII digits. Python's `int(str)` and `float(str)` accept any Unicode decimal-digit codepoint (e.g., Arabic-Indic digits `١٢٣`, fullwidth digits `１２３`, Devanagari digits) and normalize them to the equivalent ASCII value. This is directly analogous to aiohttp's flaw #2, where "the HTTP version was permitting Unicode digits, where only ASCII digits are standards-compliant" — here, the proto3 JSON mapping spec for integral fields, and the conformance suite (`ExpectParseFailureForJson("Int32FieldStringValuePartiallyNumericUnicode", ..., R"({"optionalInt32": "12谷歌34"})")`, [2](#0-1) ) only tests CJK letters being rejected, not that *numeric* non-ASCII digit characters are also rejected — the conformance suite does not cover the Unicode-decimal-digit acceptance case at all.

Contrast this with the canonical/native paths: the upb-based JSON decoder (used by the C-extension/PHP/Ruby bindings) validates digits with an explicit ASCII range check `*d->ptr < '0' || *d->ptr > '9'` ( [3](#0-2) ), and the C++ `internal/parser.cc`/`internal/lexer.cc` JSON lexer also uses `absl::ascii_isdigit` for raw-number scanning ( [4](#0-3) ). Only the **pure-Python** upb-less fallback implementation of ProtoJSON parsing (`json_format.py`, used whenever the C++/upb Python extension is unavailable, e.g. pure-Python protobuf runtime) is exposed to this Unicode-digit leniency, because it hands the untrusted string directly to Python's Unicode-aware numeric conversion instead of doing char-class validation first.

### Impact Explanation
A client sending ProtoJSON such as `{"optionalInt64": "１２３"}` (fullwidth digits) or `{"optionalInt64": "١٢٣"}` (Arabic-Indic digits) to a service using the pure-Python protobuf runtime's `json_format.Parse`/`ParseDict` will have that string silently accepted and converted to the ASCII-equivalent integer `123`, even though it is not valid per the proto3 JSON encoding spec (which requires quoted 64-bit integers to be ASCII decimal digit strings). This is an input-validation/parser-differential issue: if the same payload is validated or logged upstream by an ASCII-only JSON schema validator/WAF (expecting rejection) and then parsed successfully downstream by this Python protobuf runtime, the differing acceptance behavior can be leveraged for validation bypass or smuggling of unexpected numeric values through supposed "reject invalid" boundaries — the same class of impact called out in the aiohttp advisory (proxy/parser disagreement enabling smuggling-like effects). It does not cause memory corruption or crash; the severity is bounded to input-validation/parser-differential (Medium), matching the aiohttp advisory's severity class and impact type (CWE-444 Inconsistent Interpretation of HTTP Requests → here, inconsistent interpretation of the proto3 JSON integer grammar).

### Likelihood Explanation
Any external, ordinary client of a service that exposes `Message.FromJson`/`json_format.Parse` on the pure-Python protobuf runtime can trigger this by simply sending Unicode decimal-digit characters in a quoted integer field — no privileges, no schema control, and no additional preconditions required. The pure-Python code path is the default fallback whenever the C++/upb accelerated implementation isn't installed (still shipped and reachable), so likelihood of exposure is non-trivial, though many deployments today use the upb-accelerated bindings where the issue does not reproduce (confirmed by inspecting `upb/json/decode.c` and `src/google/protobuf/json/internal/lexer.cc`, which correctly restrict to ASCII `0`-`9`).

### Recommendation
In `_ConvertInteger` (and analogously in `_ConvertFloat`), validate that `value`, when a `str`, matches an ASCII-only decimal pattern (e.g. `^-?[0-9]+$` for integers, `^-?[0-9]+(\.[0-9]+)?([eE][+-]?[0-9]+)?$` for floats) before calling `int()`/`float()`, rejecting any string containing non-ASCII digit characters, mirroring the explicit ASCII-range checks already used in `upb/json/decode.c` and `src/google/protobuf/json/internal/lexer.cc`. Add conformance test cases with Unicode decimal-digit characters (not just non-digit CJK letters) for quoted int32/int64/uint32/uint64 fields to close this test gap.

### Proof of Concept
Using the pure-Python protobuf runtime (`PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python`):
```python
from google.protobuf import json_format
import my_proto_pb2

msg = my_proto_pb2.TestAllTypes()
# Fullwidth Unicode digits, not ASCII 0-9
json_format.Parse('{"optionalInt64": "１２３"}', msg)
print(msg.optional_int64)  # prints 123, should have raised ParseError
```
This is expected to raise `ParseError` per the proto3 JSON integer grammar (ASCII digits only) but instead succeeds and silently normalizes to `123`, because `_ConvertInteger` ( [5](#0-4) ) delegates directly to Python's Unicode-aware `int()`.

**Uncertainty note:** I was not able to execute this PoC in this environment (read-only code index, no interpreter access), so the above reproduction is derived from static analysis of Python's documented `int()`/`float()` Unicode-digit behavior and the absence of any ASCII-only character-class check in `_ConvertInteger`, not from an actual test run. I recommend a Devin session with filesystem/interpreter access to confirm this behavior empirically and to check `_ConvertFloat` for the same issue.

```python
def _ConvertInteger(value):
  """Convert an integer.

  Args:
    value: A scalar value to convert.

  Returns:
    The integer value.

  Raises:
    ParseError: If an integer couldn't be consumed.
  """
  if isinstance(value, float) and not value.is_integer():
    raise ParseError("Couldn't parse integer: {0}".format(value))

  if isinstance(value, str) and value.find(' ') != -1:
    raise ParseError('Couldn\'t parse integer: "{0}"'.format(value))

  if isinstance(value, bool):
    raise ParseError(
        'Bool value {0} is not acceptable for integer field'.format(value)
    )

  try:
    return int(value)
  except ValueError as e:
    # Attempt to parse as an integer-valued float.
    try:
      f = float(value)
    except ValueError:
      # Raise the original exception for the int parse.
      raise e  # pylint: disable=raise-missing-from
    if not f.is_integer():
      raise ParseError(
          'Couldn\'t parse non-integer string: "{0}"'.format(value)
      ) from e
    return int(f)
```

```c
static bool jsondec_tryskipdigits(jsondec* d) {
  const char* start = d->ptr;

  while (d->ptr < d->end) {
    if (*d->ptr < '0' || *d->ptr > '9') {
      break;
    }
    d->ptr++;
  }

}
```
