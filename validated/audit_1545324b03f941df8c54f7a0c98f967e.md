### Title
Aggregator's `Internal*` RPCs (`InternalSendTx`, `InternalGetEmergencyStopTx`) are unauthenticated when `client_verification=false`, allowing anyone to broadcast attacker-chosen transactions - (File: core/src/servers.rs, core/src/rpc/interceptors.rs)

### Summary
When `BridgeConfig::client_verification` is `false`, `create_grpc_server` installs `Interceptors::Noop` instead of `Interceptors::OnlyAggregatorAndSelf`, and `Noop::call` unconditionally returns `Ok(req)` without ever invoking `is_internal` or checking peer certificates. Every RPC on the aggregator, including the `Internal*`-prefixed ones that are supposed to be restricted to the aggregator calling itself, is fully open to any unauthenticated caller who can reach the gRPC port.

### Finding Description
The binding this system is supposed to guarantee is: **a request accepted by the aggregator server for an `Internal*` method == a request whose leaf TLS certificate equals `our_cert`** (checked in `only_aggregator_and_self` at core/src/rpc/interceptors.rs:62-69). This binding is only enforced when the `OnlyAggregatorAndSelf` interceptor variant is installed.

In `core/src/servers.rs:106-138`, the choice of interceptor and TLS configuration is entirely driven by `config.client_verification`:
```
let tls_config = if config.client_verification {
    ServerTlsConfig::new().identity(server_identity).client_ca_root(client_ca)
} else {
    ServerTlsConfig::new().identity(server_identity)
};
...
if config.client_verification { OnlyAggregatorAndSelf {...} } else { Noop }
``` [1](#0-0) 

When `client_verification=false`:
- The TLS server config has no `client_ca_root`, so the server does not request or validate any client certificate during the handshake.
- The interceptor is `Interceptors::Noop`, whose `call` implementation is `Ok(req)` with no logic at all [2](#0-1) .
- `is_internal` (core/src/rpc/interceptors.rs:12-20) and the leaf-certificate comparison against `our_cert`/`aggregator_cert` are located inside `only_aggregator_and_self`, which is never called in this configuration.

Because of this, the left side of the binding ("request accepted") becomes true for literally any request reaching the port over plaintext or unauthenticated TLS, while the right side ("leaf cert == our_cert") is never evaluated. The two sides diverge completely for `Internal*` methods: the `AddMethodMiddlewareLayer` still tags the `grpc-method` header used by `is_internal`, but that header is irrelevant when `Noop` is in effect, so an attacker doesn't even need to forge or omit it — the check simply doesn't run.

### Impact Explanation
With `client_verification=false`, an unprivileged network attacker who can connect to the aggregator's gRPC port can call `InternalSendTx` and `InternalGetEmergencyStopTx` directly, without any certificate. These RPCs broadcast presigned or attacker-supplied Bitcoin transactions on behalf of the aggregator, so this is a direct **unauthenticated state-changing/broadcasting call** — matching the "High" impact category, and depending on what transactions can actually be pushed through these RPCs (e.g., forcing early broadcast of collateral-affecting or emergency-stop transactions), it can escalate to vault-affecting consequences. The blast radius is the entire aggregator instance and every operator/verifier that trusts its broadcasts, and the attack is trivially repeatable (no state consumed, no cost beyond a TCP connection).

### Likelihood Explanation
The precondition `client_verification=false` is required — this is a deployment/configuration setting present in `core/src/config/mod.rs` and set in the repo's own sample configs (`core/src/test/data/bridge_config.toml`, `scripts/docker/configs/testnet4/bridge_config.toml`). Given that precondition, exploitation costs nothing beyond opening a gRPC connection: no Bitcoin fees, no key material, no certificate. It is fully attacker-controlled and repeatable at will as long as the port is reachable and `client_verification` is off.

### Recommendation
Do not allow `Interceptors::Noop` to be selectable for any code path that services `Internal*` methods, or make `is_internal`'s authorization check unconditional regardless of `client_verification`. At minimum, the aggregator's TLS/interceptor setup should always enforce `OnlyAggregatorAndSelf` for its self-only endpoints (e.g. split routing so `Internal*` RPCs are only served on a loopback/Unix socket, or make `client_verification` non-optional for the aggregator).
