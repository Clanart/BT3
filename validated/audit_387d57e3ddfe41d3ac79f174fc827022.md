### Title
PedPoP encryption accepts the identity point as an ECDH public key, making all encrypted DKG secret shares decryptable by anyone — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2016-9606 (forcing deserialization of attacker-controlled objects), Serai's PedPoP DKG unmarshals attacker-controlled curve points (`enc_key` in `EncryptionKeyMessage::read` and `key` in `EncryptedMessage::read`) via `Ciphersuite::read_G`, which enforces canonical encoding but does **not** reject the identity point. Only `frost`'s `Curve::read_G` rejects identity (`crypto/frost/src/curve/mod.rs:125-131`), and PedPoP is generic over `Ciphersuite`, not `Curve`. An identity ECDH point collapses every shared secret to the publicly known identity, so the ChaCha20 keystream key becomes derivable by anyone — silently stripping confidentiality from the secret shares at the heart of the DKG.

### Finding Description
`EncryptionKeyMessage::read` reads `enc_key: C::read_G(reader)?` (`encryption.rs:57-58`) and `EncryptedMessage::read` reads `key: C::read_G(reader)?` (`encryption.rs:171-176`). `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only checks canonicality via `from_bytes`/`to_bytes` round-trip; identity encodings are canonical and pass. ECDH is then computed as `public * private` in `ecdh` (`encryption.rs:95-97`), so if `public` is identity, the shared point is identity regardless of the ephemeral scalar. `cipher` (`encryption.rs:101-133`) derives the ChaCha20 key solely from `transcript(context || identity_bytes)` — a publicly computable value. There is no `is_identity` check anywhere in `encryption.rs` or in `verify_r1`/`register` (`lib.rs:300-338`).

### Impact Explanation
Two attack directions exist:

1. **Malicious recipient** registers `enc_key = identity` in its broadcast `EncryptionKeyMessage`. Every honest sender's share to it is encrypted under the constant public key → any observer of the wire/relay (coordinator/tributary messages transport these ciphertexts) can decrypt all shares addressed to that participant.
2. **Malicious sender** crafts an `EncryptedMessage` with `key = identity` (the per-message public key). The recipient-side ECDH (`private_key * identity = identity`) again yields the public constant, so the share ciphertext to *every* recipient is publicly decryptable. Because shares are sent to all `n-1` other participants, an observer recovers the sender's polynomial evaluations for every index — and since the recipient shares sum into each victim's `self.secret` (`lib.rs:484`), collecting `t` victims' shares reconstructs the **full threshold group private key**, completely defeating the DKG.

The PoP signature does not prevent this: it proves knowledge of the DL of `key`, and identity has known DL `0`, so `SchnorrSignature::sign` over it is trivially producible. This is key-share/secret recovery reachable purely through untrusted bytes fed to `EncryptedMessage::read`/`EncryptionKeyMessage::read`, matching the "unmarshalling untrusted data" class of the CVE.

### Likelihood Explanation
The attack requires only submitting crafted bytes in the normal DKG message flow — a single malicious (or compromised) participant among `n`. No hash collisions or exotic conditions are needed; identity encodings are canonical and pass every existing check. Mitigating factor: the ciphertext must be observable by the attacker beyond its intended recipient (true when messages are relayed/broadcast by the coordinator, which is how blame traffic already exposes them publicly). Where channels are strictly pairwise-private, impact reduces to the malicious party's own shares — lowering severity — but the protocol intends ECDH confidentiality precisely because messages transit shared infrastructure.

### Recommendation
Reject the identity point for all ECDH public inputs in PedPoP: after `C::read_G` in `EncryptionKeyMessage::read` (`encryption.rs:58`) and `EncryptedMessage::read` (`encryption.rs:173`), check `bool::from(point.is_identity())` and return an error (mirroring `Curve::read_G` at `crypto/frost/src/curve/mod.rs:125-131`). Also reject identity in `Commitments::read` (`lib.rs:115-121`) so commitment coefficients cannot be the identity, and assert the computed ECDH result is non-identity in `ecdh`/`decrypt_with_proof` as defense-in-depth.

### Proof of Concept
```rust
// Malicious participant i_m registers an identity encryption key:
let mut msg = honest_commitments.serialize();
// Overwrite the trailing enc_key bytes with the canonical identity encoding:
let id_len = <C::G as GroupEncoding>::Repr::default().as_ref().len();
msg.truncate(msg.len() - id_len);
msg.extend(C::G::identity().to_bytes().as_ref());
// EncryptionKeyMessage::read accepts it; every sender computes
// ecdh(ephemeral, identity) == identity, so:
//   key = transcript("DKG Encryption v0.2" || context || identity_bytes).challenge(b"key")
// is publicly computable → ChaCha20 keystream is public → share plaintexts recoverable.
//
// Symmetrically, a malicious sender sets EncryptedMessage.key = identity
// (pop signs over DL=0), so victim-side ecdh(victim_priv, identity) == identity
// and every recipient's share ciphertext is decryptable by any observer.
```

*Caveat: I verified `encryption.rs` and `lib.rs` contain no identity rejection for these fields; I did not fully confirm the transport-layer visibility of share ciphertexts, which affects realized likelihood but not the missing-validation root cause.*
