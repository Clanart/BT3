No sanitization of `remote.name` exists anywhere in the codebase — `getRemotes` parses names straight out of `git remote -v` output via regex without validating the character set [1](#0-0) , and `push` interpolates that name directly as a positional argv element with no leading `--` separator to stop option parsing [2](#0-1) .

### Title
Argument Injection via Attacker-Controlled Remote Name in `git push` - (File: `app/src/lib/git/push.ts`)

### Summary
A remote name is not a free-form, sanitized value in GitHub Desktop — it is whatever text `git remote -v` reports for the `[remote "..."]` config section. Git's config-file syntax allows the quoted section name to contain characters that `git remote add` would normally reject (including a leading `--`). A crafted, cloned/fetched repository that ships a `.git/config` with a remote section such as `[remote "--upload-pack=./payload"]` (or any push-relevant flag) will cause `getRemotes()` to surface that string as `remote.name`, and `push()` then places it as the second positional argument to `git push` with no `--` separator to prevent it being parsed as an option.

### Finding Description
`getRemotes` builds `IRemote` objects purely from regex-parsed `git remote -v` stdout [3](#0-2) , with no allow-list/character validation on `name`. `push()` then constructs `args = ['push', remote.name, refspec]` [2](#0-1)  and executes it via `git(args, repository.path, 'push', opts)` [4](#0-3) . Because git's argv parser treats any leading `-`/`--` token as an option rather than the positional `<repository>` argument, a remote name beginning with `-` is not passed to git as "the remote to push to" as the code intends — it is interpreted as a `git push` flag. Compare with `clone.ts`, which defensively inserts a `--` separator before the URL/path to stop option parsing [5](#0-4) ; `push.ts` has no equivalent protection for `remote.name`.

Other remote-name call sites (`addRemote`, `removeRemote`, `setRemoteURL`, `getRemoteURL`, `updateRemoteHEAD`) have the same unsanitized-interpolation pattern [6](#0-5) , but `push.ts` line 59 is the most impactful because `git push` supports `--receive-pack=<program>`/`--exec=<program>`, which lets the caller choose the program git invokes to perform the receive-pack step. For local-filesystem or `ext::`-style remotes, this is executed directly by the local git process (not remotely over ssh), so a crafted config plus a companion script bundled inside the same repository (`cwd` is `repository.path`) gives the attacker a path to running an arbitrary program chosen by the "remote name" the moment the victim pushes.

### Impact Explanation
If exploitable end-to-end, this would allow a maliciously crafted repository to achieve local command execution when the victim performs an ordinary `push` action in Desktop against the poisoned remote, without any other suspicious action. That satisfies the "attacker controls a cloned/fetched repository" + "code execution" bar in scope.

### Likelihood Explanation
I could **not** fully verify exploitability within the tools available, and flag important open uncertainties that would need hands-on testing (which I don't have here):
1. Whether Desktop's UI ever presents/pushes to a remote whose `name` was sourced from a raw `.git/config` section without the user explicitly typing/choosing it (e.g., does the "Push" button pick the `currentRemote` derived from `getRemotes()` output, or does the user have to add the remote via Desktop's own `addRemote` UI, which would go through git's own name validation and reject invalid characters?).
2. Whether `--receive-pack=<value>`/`--exec=<value>` actually reaches local process execution for the transport types reachable from a cloned repo's `.git/config` (local path vs. `ext::` vs. ssh), and whether git's own argv parsing of `git push <flag> <refspec>` would still require a valid remote as a *second* non-option argument (it might error out instead of silently using a default), which needs confirmation against the exact dugite/git version bundled.
3. Whether the git version bundled with Desktop applies any additional constraints on remote-name/section syntax when writing/reading `.git/config` that would prevent a `-`-prefixed name from round-tripping through `git remote -v` at all.

Given these unresolved points, I can confirm the **code pattern is a real gap** (no sanitization, no `--` separator) relative to the safer pattern used in `clone.ts`, but I cannot confirm working end-to-end exploitation from this repo's index alone.

### Recommendation
- Insert a `--` separator (or `--end-of-options`) before `remote.name` in the `git push` argv, matching the mitigation already used in `clone.ts` for the URL/path arguments.
- Validate/allow-list `remote.name` (and other remote-derived values) coming from `getRemotes()` against git's own legal ref/remote name grammar, rejecting any name that starts with `-` before it is ever passed to `git`.
- Apply the same fix to `addRemote`, `removeRemote`, `setRemoteURL`, `getRemoteURL`, and `updateRemoteHEAD` in `app/src/lib/git/remote.ts`, all of which share the same unguarded-interpolation pattern.

### Proof of Concept
Conceptual PoC (not verified end-to-end due to tool limitations):
1. Attacker creates a repository whose `.git/config` contains:
```
[remote "--receive-pack=./evil.sh"]
    url = /tmp/some/local/path
    fetch = +refs/heads/*:refs/remotes/*
```
and bundles an executable `evil.sh` at the repository root.
2. Victim clones/opens this repository in GitHub Desktop.
3. `getRemotes()` reports a remote whose `name` is the literal string `--receive-pack=./evil.sh` [3](#0-2) .
4. Victim performs a normal `Push` action in Desktop; `push()` runs `git push --receive-pack=./evil.sh <localBranch>:<remoteBranch>` with `cwd = repository.path` [2](#0-1) , potentially invoking `evil.sh` instead of pushing to a normal remote.

export async function getRemotes(
  repository: Repository
): Promise<ReadonlyArray<IRemote>> {
  const result = await git(['remote', '-v'], repository.path, 'getRemotes', {
    expectedErrors: new Set([GitError.NotAGitRepository]),
  })

  if (result.gitError === GitError.NotAGitRepository) {
    return []
  }

  return [...result.stdout.matchAll(/^(.+)\t(.+)\s\(fetch\)/gm)].map(
    ([, name, url]) => ({ name, url })
  )
}

/** Removes an existing remote, or silently errors if it doesn't exist */
export async function removeRemote(
  repository: Repository,
  name: string
): Promise<void> {
  const options = {
    successExitCodes: new Set([0, 2, 128]),
  }

  await git(
    ['remote', 'remove', name],
    repository.path,
    'removeRemote',
    options
  )
}

/**
 * Get the URL for the remote that matches the given name.
 *
 * Returns null if the remote could not be found
 */
export async function getRemoteURL(
  repository: Repository,
  name: string
): Promise<string | null> {
  const result = await git(
    ['remote', 'get-url', name],
    repository.path,
    'getRemoteURL',
    { successExitCodes: new Set([0, 2, 128]) }
  )

  if (result.exitCode !== 0) {
    return null
  }

  return result.stdout
}

/**

    options
  )
}
