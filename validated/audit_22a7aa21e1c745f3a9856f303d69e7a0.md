Confirmed: `handleGetResponses` in `HandlerV2.sol` loops over every `GetResponseLeaf` in a relayer-submitted batch and calls `host.dispatchIncoming(leaf.response, _msgSender())` directly, with no per-item isolation. [1](#0-0) 

`EvmHost.dispatchIncoming(GetResponse,...)` delivers the response to the app via a low-level `.call` (failures there are isolated, receipt deleted for retry), but *after* a successful callback it unconditionally executes `IERC20(feeToken()).safeTransfer(relayer, fee)` **outside** any try/catch: [2](#0-1) 

`SafeERC20.safeTransfer` reverts on failure (insufficient host fee-token balance, a paused/blacklisting fee token, or any other transfer-level revert). Because this call sits inside `dispatchIncoming`, and `dispatchIncoming` is invoked directly (not wrapped in `try/catch`) from inside the `for` loop in `handleGetResponses`, a single failing fee transfer for **one** response in the batch bubbles up and reverts the **entire** `handleGetResponses` transaction — undoing delivery of every other `GetResponse` in that batch, for unrelated apps/users, and refunding no one their relayer fee either.

### Title
Single relayer-fee transfer failure inside a batched `GetResponse` can DoS delivery of all unrelated responses in the same batch - (File: evm/src/core/HandlerV2.sol / evm/src/core/EvmHost.sol)

### Summary
`HandlerV2.handleGetResponses` iterates a relayer-submitted batch of `GetResponseLeaf`s and calls `IHost.dispatchIncoming(GetResponse,...)` for each one without isolating failures. `EvmHost.dispatchIncoming` wraps the app callback (`onGetResponse`) in a low-level `.call` so a reverting app is safely retried later, but the subsequent relayer-fee `safeTransfer` is unprotected. If that transfer reverts for any single leaf in the batch, the revert propagates out of the loop and reverts the whole `handleGetResponses` call, blocking delivery of every other (unrelated) `GetResponse` bundled in the same multi-proof.

### Finding Description
`dispatchIncoming(GetResponse,...)` performs two side effects: (1) an isolated `.call` to the destination app's `onGetResponse`, whose failure is caught and simply causes the receipt to be deleted for retry [3](#0-2) , and (2) an unconditional relayer fee payout via `safeTransfer` once the callback succeeds [4](#0-3) . The second step has no failure containment.

`handleGetResponses` batches many `GetResponseLeaf`s under one Merkle multiproof and dispatches each one in a plain loop with no `try/catch` around `host.dispatchIncoming(...)` [1](#0-0) . This is unlike `handlePostRequests`'s underlying `dispatchIncoming(PostRequest,...)`, which isolates *all* of its failure modes internally and never reverts the outer batch [5](#0-4) .

Any of the following can make the `safeTransfer(relayer, fee)` step revert for one leaf:
- The `EvmHost`'s fee-token balance is insufficient to cover that request's escrowed `fee` (e.g. drained/mismatched accounting).
- The configured fee token is a non-standard/pausable/blacklist-capable ERC-20 and the relayer address is currently blocked.
- The fee token reverts for any other reason (`fee == 0` is the only value that skips the transfer).

Since a relayer batches responses to amortize proof-verification gas, and any user/app can influence whether their own GET response's `fee` accounting or associated relayer address triggers a revert, an attacker who can get one bad leaf into a relayer's otherwise-honest batch causes the whole batch to revert.

### Impact Explanation
This breaks the "requests/responses must be delivered independently" invariant expected of ISMP's batched delivery — one corrupted/failing leaf can indefinitely block delivery (and thus fund release, calldata execution, refunds, etc., depending on what the destination app's `onGetResponse` does) for every unrelated `GetResponse` bundled with it, and denies relayer fee payment for all of them in that attempt. This matches the "logic attack causing false state acceptance is avoided but honest cross-chain settlement is denied" class of impact: legitimate GET-response-driven settlements (e.g., intent cancellations/refunds via `onGetResponse` in `IntentGatewayV2`/`ExtrinsicIntents`) can be stalled by an unrelated response's fee-transfer failure in the same batch, at no cost beyond crafting one bad leaf.

### Likelihood Explanation
Likelihood is moderate: it requires a relayer to batch a "poisoned" response together with others (relayers are economically incentivized to batch for gas savings, and nothing here requires a malicious relayer — the poisoned leaf can be any legitimate GET response whose `fee` or token accounting is broken by a separate, unprivileged actor), and it requires the fee-token transfer to fail. It does not require a malicious peer, prover, or admin — only a state where the host's fee-token accounting/balance for one outstanding GET request is off, or the fee token itself is non-conforming.

### Recommendation
Isolate the relayer-fee transfer the same way the app callback is isolated: wrap the `safeTransfer` in a low-level call (or `try/catch` for ERC-20) and, on failure, emit an event / leave the fee claimable later instead of reverting the whole `dispatchIncoming` call. Additionally, wrap the per-leaf `host.dispatchIncoming(leaf.response, _msgSender())` invocation in `handleGetResponses` in a `try/catch` so that any leaf-level revert only skips that leaf instead of reverting the entire batch, matching the resilience already built into `dispatchIncoming(PostRequest,...)`/`handlePostRequests`.

### Proof of Concept
1. Attacker (or circumstance) causes the `EvmHost`'s fee-token balance to be insufficient for one outstanding GET request's `fee`, or gets the fee token to blacklist/pause the relayer address associated with that request's `requestCommitments` entry.
2. A relayer batches that `GetResponseLeaf` together with N other unrelated, healthy `GetResponseLeaf`s into a single `GetResponseMessage` and submits `handleGetResponses`.
3. The loop at `evm/src/core/HandlerV2.sol:241-246` processes leaves in order; when it reaches the poisoned leaf, `EvmHost.dispatchIncoming` succeeds in calling `onGetResponse` but then executes `IERC20(feeToken()).safeTransfer(relayer, fee)` at `evm/src/core/EvmHost.sol:844`, which reverts.
4. The revert is not caught anywhere in `handleGetResponses`, so the entire transaction reverts, rolling back delivery of all N healthy responses (and their relayer-fee payouts) even though only one leaf was faulty.
5. Repeating this whenever a relayer includes the poisoned leaf lets an attacker indefinitely stall settlement of other users' GET-response-driven flows bundled in the same batch.

        address destination = _bytesToAddress(request.to);

        }

            // instead of reverting the entire batch, early return here.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
