### Title
Malicious deep link silently triggers checkout of an attacker-chosen PR branch in a victim's existing repository - ([File: app/src/ui/dispatcher/dispatcher.ts])

### Summary
The C4 report's broken invariant is: a state-mutating function that should only fire as the side effect of a specific, authorized internal flow can instead be invoked directly by an unprivileged/external actor, causing an unwanted state change on a victim without their intended consent. The Desktop analog is the `x-github-client://openrepo/...?pr=N` deep-link handler, which lets *any* link (crafted by an attacker, e.g. in an email or a webpage) drive `Dispatcher.openRepositoryFromUrl` → `openPullRequestFromUrl` → `AppStore._checkoutPullRequest` → `_checkoutBranch`, and, depending on the victim's saved "uncommitted changes" preference, checks out an attacker-chosen PR head branch into the user's already-cloned local repository with **no confirmation dialog at all**.

### Finding Description
`parseAppURL` accepts the `openrepo` deep link scheme and extracts an unauthenticated `url` and `pr` query parameter with only superficial validation (`pr` must be numeric): [1](#0-0) 

`dispatchURLAction` routes any such link straight into `openRepositoryFromUrl` without any origin/consent check beyond "is this a well-formed protocol URL": [2](#0-1) 

`openPullRequestFromUrl` fetches the PR object from the GitHub API using attacker-supplied `owner/name/pr` values, matches it against a repository the victim *already has open in Desktop* (via origin/upstream HTML URL matching), and if found, immediately calls `_checkoutPullRequest` using the head clone URL/ref taken verbatim from the API response — i.e., values the PR author (who can be anyone with fork/PR rights on a public repo) controls: [3](#0-2) 

`_checkoutPullRequest` calls `_checkoutBranch` without an explicit strategy: [4](#0-3) 

`_checkoutBranch` only shows a confirmation popup when `explicitStrategy` is `undefined` **and** the user's saved `uncommittedChangesStrategy` preference is `AskForConfirmation`. If the user has instead set the (equally supported, non-default) preference to `MoveToNewBranch` or `StashOnCurrentBranch` (without an existing stash conflict), the checkout proceeds silently: [5](#0-4) 

The confirmation gate exists (`PopupType.StashAndSwitchBranch`, `ConfirmOverwriteStash`), but it is a *user preference*, not a per-action authorization check tied to the fact that this checkout was triggered by an unauthenticated external deep link rather than a deliberate UI click on "Checkout" for a PR the user explicitly opened. There is no distinction in `_checkoutBranch`/`_checkoutPullRequest` between "user clicked checkout in the PR list" and "an external protocol handler asked us to checkout this branch."

### Impact Explanation
Because the deep-link handler is reachable by anyone who can get the victim to click a link (a browser page, email, chat message, or even another local application invoking the registered `x-github-client://`/`github-mac://`/`github-windows://` protocol), an attacker can:
- Force Desktop to fetch and check out an arbitrary attacker-controlled branch of a PR against a repository the victim already has cloned, silently switching the victim's working directory HEAD if their uncommitted-changes preference is not `AskForConfirmation`.
- This corrupts what the victim's working directory represents at the moment they next commit or push — the "exact corrupted value" is the repository's checked-out branch/tip, which the user did not deliberately select. A user who resumes work without checking their current branch could commit on top of, or push, content originating from an attacker-supplied branch, or unknowingly build/run code from it.
- Because `filepath` handling is separately hardened (`isAbsolute`/`resolveWithin` checks), the remaining unguarded surface is specifically the automatic PR checkout path.

This does not require local/physical access, admin rights, prior malware, or leaked credentials — only a click on a link, which is the exact attacker primitive class this scan is scoped to accept (a link/deep link the user clicks).

### Likelihood Explanation
Existing guards (`testForInvalidChars` on branch names, numeric-only `pr` validation, `isAbsolute`/`resolveWithin` on `filepath`) validate the *shape* of link parameters but do nothing to gate the *authorization* of the resulting checkout action against the fact that the trigger source is untrusted. The only thing standing between the attacker and a silent checkout is a user preference (`uncommittedChangesStrategy`) that is unrelated to input trust and is commonly changed away from the default to reduce friction. No dialog specifically says "a link is asking to open PR #N in repository X — proceed?" before the PR/branch data is fetched and acted upon.

### Recommendation
Treat checkouts initiated via `dispatchURLAction`/CLI deep links as always requiring explicit confirmation, regardless of the user's saved `uncommittedChangesStrategy` preference — i.e., pass an explicit strategy through `openPullRequestFromUrl`/`openBranchNameFromUrl` that forces a `PopupType` confirmation naming the repository, PR number/branch, and its source URL/owner before invoking `_checkoutPullRequest`/`checkoutLocalBranch`, rather than relying solely on the generic preference-based gate in `_checkoutBranch`.

### Proof of Concept
1. Victim has GitHub Desktop installed with `uncommittedChangesStrategy` set to `MoveToNewBranch` (a supported, non-default option shown in Preferences) and already has `github.com/victim-org/repo` cloned. [6](#0-5) 
2. Attacker opens a PR (or uses an existing open PR) against `victim-org/repo` from their own fork, containing arbitrary commits.
3. Attacker sends the victim a link: `x-github-client://openrepo/https://github.com/victim-org/repo?pr=<attacker_pr_number>`.
4. Victim clicks the link. `parseAppURL` parses it into an `open-repository-from-url` action with `pr` set. [1](#0-0) 
5. `dispatchURLAction` → `openRepositoryFromUrl` → `openPullRequestFromUrl` locates the victim's already-open matching repository and calls `_checkoutPullRequest` with the attacker's fork clone URL/ref. [7](#0-6) 
6. `_checkoutBranch` sees `explicitStrategy === undefined` but `uncommittedChangesStrategy !== AskForConfirmation`, so no popup is shown, and the attacker's branch is checked out immediately. [8](#0-7) 

Note: I was unable to fully verify, from the indexed code alone, whether any additional gate exists elsewhere in the click-to-protocol-handler pipeline (e.g., an OS-level "open with GitHub Desktop?" prompt shown by the browser/OS before invoking the registered protocol) that might reduce likelihood; that prompt, where present, is an OS/browser-level mitigation outside this repository's code and was not something I could confirm in this codebase.

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }
