### Title
Threshold secret shares serialized and persisted to disk in plaintext - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2019-10430 (CWE-312) concerns a plugin writing credentials unencrypted into a global config file readable by anyone with filesystem access. The same bug class exists in Serai: `ThresholdKeys::write` serializes the FROST `secret_share` scalar in the clear, and the processor persists these serialized keys to its database via `GeneratedKeysDb::save_keys` / `KeysDb::confirm_keys` without any encryption.

### Finding Description
`ThresholdKeys::write` writes `self.core.secret_share.to_repr()` directly to the output stream in plaintext:

```rust
let mut share_bytes = self.core.secret_share.to_repr();
writer.write_all(share_bytes.as_ref())?;
``` [1](#0-0) 

On the consumer side, the processor's `GeneratedKeysDb::save_keys` concatenates `substrate_keys.serialize()` and `network_keys.serialize()` and commits the raw bytes into the node's local database under a key derived only from the public group keys; `KeysDb::confirm_keys` later re-stores the same plaintext blob keyed by the network key (`txn.put(Self::key(key_pair.1.as_ref()), keys_vec)`). [2](#0-1) 

There is no encryption layer, no keystore abstraction, and no access control beyond the filesystem permissions of the database directory — exactly the same exposure as the Jenkins plugin storing credentials in its global XML config.

### Impact Explanation
A `ThresholdKeys` value contains the validator's FROST secret share. Recovery of a validator's share (combined with t-1 other shares, or via ROS-style/preprocess reuse against that share) directly enables signing under the threshold key. Any party or process able to read the processor's on-disk database — backups, container volumes, snapshot exports, or a colocated service — obtains the plaintext secret share. This is "key share recovery", one of the accepted impact classes, and corresponds to Medium severity per the source advisory (local credential disclosure).

### Likelihood Explanation
Every Serai processor persists its generated threshold keys through this path (`save_keys` → `confirm_keys`), so the plaintext share is present on every validator's disk for the lifetime of the key. Exposure requires local/ filesystem-level access to the node, matching the advisory's `AV:L/PR:L` profile — an attacker who already fully controls the validator host gains nothing new, which caps the severity at Medium.

### Recommendation
Encrypt `secret_share` before persistence. Options:
- Add an authenticated encryption layer (e.g., AEAD keyed by an operator-supplied or HSM-held key) inside `ThresholdKeys::write`/`serialize`, or at the `GeneratedKeysDb`/`KeysDb` storage layer in `processor/src/key_gen.rs`.
- Alternatively, document that the DB directory must be encrypted at rest, and drop `secret_share` from serialization entirely in favor of an out-of-band keystore interface.
- Keep the existing `Zeroize`/drop hygiene for the in-memory representation regardless.

### Proof of Concept
1. `KeyGen` completes a DKG; `GeneratedKeysDb::save_keys` (processor/src/key_gen.rs:65-84) writes `substrate_keys.serialize() + network_keys.serialize()` into the DB.
2. `ThresholdKeys::write` (crypto/dkg/src/lib.rs:553-555) emits `secret_share.to_repr()` verbatim — a fixed-length field element at a known offset after `C::ID`, `t`, `n`, `i`, and the interpolation tag.
3. Any reader of the DB value (e.g., `KeysDb` entry keyed by the known public network key) slices out the share bytes and calls `F::from_repr` to recover the validator's secret signing share in the clear.
