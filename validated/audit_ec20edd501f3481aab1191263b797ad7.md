## Title
Unchecked ERC20 return-value in `IntentGatewayV2.withdraw()`/`SweepDust` permanently burns escrow accounting without transferring funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` imports and enables `SafeERC20` (`using SafeERC20 for IERC20;`) and its EVM sibling (`evm/src/apps/intentsv2/IntentsBase.sol`) consistently uses `safeTransfer`, but the Tron contract's `withdraw()` and `SweepDust` handler instead perform raw low-level calls and only check the outer call success, never decoding the returned boolean: [1](#0-0) [2](#0-1) 

This is exactly the ERC20 return-value pitfall the External Report warns about (some ERC20 implementations return `false` instead of reverting on failure), applied inversely: because the code only checks `success` from `.call(...)` (which is `true` as long as the token contract doesn't revert) and ignores the ABI-decoded return data, a token that signals failure by returning `false` (e.g. paused, blacklisted receiver, insufficient internal balance guard) will make the "transfer" appear successful while no tokens actually move.

### Finding Description
In `withdraw()`, escrowed balances are decremented and the order is marked filled *unconditionally* alongside the raw `call`: [3](#0-2) 

The same unchecked pattern is used for both the escrowed-token payout and the transaction-fee payout: [2](#0-1) 

and in the governance-triggered `SweepDust` branch of `onAccept`: [4](#0-3) 

`(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` only reflects whether the callee reverted; if the token contract returns `false` without reverting, `success` is still `true`, `revert TransferFailed()` is never triggered, and `_orders[commitment][token] -= amount` still executes. The beneficiary never receives the tokens, yet the protocol's internal accounting treats the order as filled/refunded (`_filled[body.commitment] = beneficiary`) with no remaining escrow to retry or recover the funds from.

By contrast, the canonical EVM `IntentsBase.sol` used by the main `IntentGatewayV2` correctly relies on OpenZeppelin's `safeTransfer`, which reverts on both call failure and `false` return values: [5](#0-4) 

The Tron contract's `using SafeERC20 for IERC20;` declaration is present but unused for these payout paths, indicating the raw-call pattern is an oversight/regression rather than an intentional design choice.

### Impact Explanation
Any order whose input/output token is a non-reverting ERC20 (a documented real-world token behavior class, not a contrived edge case) can have its escrow silently zeroed out by `withdraw()` while the intended beneficiary — solver, filler, or refund recipient — receives nothing. Because `_orders[commitment][token]` is already decremented and `_filled[commitment]` set, the withdrawal path cannot be safely retried, and the tokens become permanently stuck in the `IntentGatewayV2` contract with no on-chain recovery mechanism for the affected user/solver. This is a direct loss-of-funds condition reachable through the ordinary, unprivileged withdraw/response-and-timeout flow (`onGetResponse` → `withdraw`), requiring no malicious relayer, prover, or admin.

### Likelihood Explanation
Triggering this requires only that one of the order's input or fee tokens be an ERC20 implementation that returns `false` on failure instead of reverting (a known pattern among older/simplified token implementations, and achievable by a malicious order creator who deliberately selects such a token as the settlement asset). No privileged role or off-chain collusion is needed — the withdraw path is invoked automatically as part of normal ISMP response/timeout handling once a proof is verified by the host.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` invocations in `withdraw()` and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol` with `IERC20(token).safeTransfer(...)`, consistent with `IntentsBase.sol`, so that both call failure and a `false` return value revert the transaction and leave escrow accounting untouched until a real transfer succeeds.

### Proof of Concept
1. Deploy an ERC20-like token whose `transfer` function returns `false` when a condition fails (e.g., transfers to a "paused" or blacklisted address) instead of reverting.
2. Create an order in `IntentGatewayV2` (Tron) using this token as an input/output asset, escrowing funds via the normal deposit path.
3. Configure the beneficiary address to be one that triggers the token's `false`-return failure condition (or have the token globally paused after order creation but before settlement).
4. Trigger settlement so `onGetResponse`/`withdraw()` executes: `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (call didn't revert) even though the token's internal logic returned `false` and moved no funds.
5. Observe `_orders[commitment][token]` is decremented to zero and `_filled[commitment]` is set, while `token.balanceOf(beneficiary)` is unchanged — the escrowed funds are now unrecoverable.
