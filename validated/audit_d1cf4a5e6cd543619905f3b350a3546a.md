### Title
Use of Solidity `.transfer()` with fixed 2300-gas stipend in `WSEI.withdraw` can permanently freeze funds for smart-contract holders - (File: contracts/src/WSEI.sol)

### Summary
`WSEI.sol` is Sei's canonical wrapped-native-token contract, whose compiled bytecode/ABI is embedded and shipped as a genuine on-chain artifact via `x/evm/artifacts/wsei/artifacts.go` (used from `x/evm/client/cli/tx.go`) rather than existing purely as a test fixture. Its `withdraw` function sends the native asset back to the caller using the deprecated `.transfer()` pattern, which forwards a hard-coded 2300-gas stipend and reverts the entire call if the recipient's fallback/receive logic needs more gas.

### Finding Description
`withdraw()` computes the caller's balance and unconditionally calls `payable(msg.sender).transfer(wad)`: [1](#0-0) 

Because `.transfer()` hardcodes a 2300-gas stipend, any `msg.sender` that is a smart contract (multisig wallet, proxy, EIP-1271 wallet, or any contract whose `receive`/`fallback` performs more than trivial storage/logic work) will have its `receive()`/`fallback()` execution run out of gas and revert. Since `WSEI` provides no alternative withdrawal path (no `call`-based function, no pull-payment pattern), any contract-held WSEI balance whose owning contract has a non-trivial fallback becomes permanently unwithdrawable through this function. This mirrors exactly the bug class in the referenced report (`RewardDistributor.sol#L181` in the original code4rena finding), where `.transfer()` is flagged as unsafe because gas-stipend changes (already realized via EIP-1884 repricing of `SLOAD`) or complex receiving contracts can cause the call to unconditionally fail.

### Impact Explanation
Because `WSEI` deposits are recorded in `balanceOf` and the only redemption path is `withdraw()`, a contract wallet that deposited native SEI into `WSEI` (e.g., via `deposit()` or the `receive()`/`fallback()` auto-deposit hooks at [2](#0-1) ) and cannot receive plain value transfers under a 2300-gas stipend will have its funds permanently locked in the contract — satisfying the "permanent freezing of funds" impact bar. This is reachable by any ordinary EVM transaction sender/contract deployer interacting with the predeployed WSEI contract, with no special privilege required.

### Likelihood Explanation
Likelihood is moderate: it requires the withdrawing account to be a contract with a non-trivial `receive`/`fallback` (e.g. a Gnosis-Safe-style multisig, an account-abstraction wallet, or any DeFi vault/router contract that wraps/unwraps WSEI on behalf of users). Such contracts are common counterparties for a wrapped-native-token contract, and interaction with WSEI (wrap/unwrap flows) is a normal, expected usage pattern rather than an edge case, making accidental triggering plausible in production DeFi integrations.

### Recommendation
Replace the `.transfer()` call in `withdraw()` with a low-level `call` that forwards all available gas and explicitly checks the success return value, e.g.:
```solidity
(bool success, ) = msg.sender.call{value: wad}("");
require(success, "WSEI: withdraw failed");
```
Apply the standard checks-effects-interactions ordering (already followed here, since `balanceOf` is decremented before the external call) to prevent reentrancy after switching to `call`.

### Proof of Concept
1. Deploy a contract `C` with a `receive()` function that performs gas-intensive work (e.g., writes to several storage slots, consuming > 2300 gas).
2. From `C`, call `WSEI.deposit{value: X}()`, incrementing `balanceOf[C]`.
3. From `C`, call `WSEI.withdraw(X)`.
4. The internal `payable(msg.sender).transfer(wad)` call at [3](#0-2)  reverts due to out-of-gas in `C`'s `receive()`, reverting the whole `withdraw` transaction and leaving `C`'s WSEI balance permanently stuck (no alternative redemption function exists in the contract).
