Based on the investigation, here's the real Desktop analog to the ZetaChain "confirmation bypass via alternate/less-guarded code path" bug class.

The broken invariant in the original report is: a security check (block confirmation) that exists on the "normal"/primary path is silently skipped on a secondary, differently-coded path that handles equivalent data (`InboundTracker` vs `ObserveTxIn`). The Desktop analog with the same shape is `git checkout` (via `checkoutBranch`/`checkoutCommit`) enforcing `allowFileProtocol=false` by default when auto-updating submodules, while `git pull` and `git fetch` unconditionally pass `--recurse-submodules` without ever restricting `protocol.file.allow`, meaning a hostile submodule URL is only blocked on one of three equivalent "update submodules after a remote operation" code paths.

### Title
Inconsistent `protocol.file.allow` enforcement across submodule-update code paths (checkout vs. pull/fetch) - (File: `app/src/lib/git/pull.ts`, `app/src/lib/git/fetch.ts`, `app/src/lib/git/submodule.ts`)

### Summary
`checkoutBranch`/`checkoutCommit` call the shared `updateSubmodulesAfterOperation` helper with an explicit `allowFileProtocol` flag that defaults to `false`, which suppresses `-c protocol.file.allow=always` and thus relies on Git's built-in protections against `file://` submodule URLs (the fix for CVE-2022-39253/GHSA-related "arbitrary file read via submodule" class). `pull()` and `fetch()`, however, invoke `git pull --recurse-submodules` / `git fetch --recurse-submodules=on-demand` directly, bypassing `updateSubmodulesAfterOperation` entirely and never adding the `protocol.file.allow` restriction control at all, i.e. they simply rely on the ambient Git config's default (`user`) rather than an explicit, consistently-audited flag. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`updateSubmodulesAfterOperation` is the shared, security-aware primitive for submodule initialization: it takes an explicit `allowFileProtocol` boolean and only adds `-c protocol.file.allow=always` when the caller opts in. [5](#0-4) 
`checkoutBranch`/`checkoutCommit` route through this helper and both default `allowFileProtocol` to `false`, meaning ordinary checkouts do not relax Git's protocol restrictions for submodules. [6](#0-5) [7](#0-6) 

`pull()` and `fetch()` do not call `updateSubmodulesAfterOperation` at all — they pass `--recurse-submodules` / `--recurse-submodules=on-demand` straight to `git pull`/`git fetch`, so there is no code-level, auditable place enforcing `protocol.file.allow` restriction for these two operations; whatever the ambient (user or system-level) Git config allows for `protocol.file.allow` is what governs submodule fetching during pull/fetch. [8](#0-7) [9](#0-8) 

This mirrors the ZetaChain pattern exactly: one code path (`checkoutBranch`/`checkoutCommit`) has been hardened with an explicit, reviewed guard, while a second, semantically-equivalent path handling attacker-controlled remote content (`pull`, `fetch`) reimplements the same "recurse into submodules" operation independently and does not carry the same explicit guard. `.gitmodules` entries are fully attacker-controlled content coming from a cloned/fetched remote repository, satisfying the "attacker controls a fetched repository" impact criterion.

### Impact Explanation
If a user's Git installation has a permissive `protocol.file.allow`/`protocol.ext.allow` configuration (which is plausible on older Git for Windows, sanctioned corporate configs, or systems where users previously ran `git config --global protocol.file.allow always` to work around submodule issues — a common workaround documented in many Git/Submodule troubleshooting guides), a malicious `.gitmodules` entry pointing a submodule URL at `file:///` or `ext::` payloads would be honored on `git pull`/`git fetch` even though the equivalent `git checkout` path in this same codebase explicitly disables that behavior by default. This can result in local file disclosure or command execution via `ext::` transport helpers when a user pulls/fetches from an attacker-influenced remote, without any explicit trust prompt from Desktop (unlike the "unsafe directory"/ownership warnings shown for `add-existing-repository` and `missing-repository` flows). [10](#0-9) 

### Likelihood Explanation
Exploitability depends on the victim's global/system Git configuration already permitting `file://`/`ext::` protocols for submodules, which Git disabled by default starting with the 2022 security release; on a fully up-to-date, default Git install this is not exploitable. This is why it is best characterized as an **inconsistent, non-defense-in-depth implementation** rather than an unconditional bypass: Desktop clone (`clone.ts`) also does not set `protocol.file.allow`, and simply lets Git's own defaults apply. The residual risk is that Desktop's own code base treats checkout as needing an explicit application-level decision (`allowFileProtocol` parameter, defaulted safely) while pull/fetch make no equivalent application-level decision at all, leaving protection entirely to the ambient Git config with no compensating control in Desktop's own code, unlike the deliberate `isClonePathSensitive` backstop added for clone destinations. [11](#0-10) 

### Recommendation
Route `pull()` and `fetch()`'s submodule handling through the same `updateSubmodulesAfterOperation` abstraction used by `checkout.ts`, explicitly passing `allowFileProtocol=false` (or omitting `--recurse-submodules`/`-on-demand` and instead calling `updateSubmodulesAfterOperation` post-hoc), so there's a single, auditable code path enforcing the protocol restriction consistently for all three operations (checkout, pull, fetch), rather than relying on ambient Git configuration for two of the three.

### Proof of Concept
1. On a test machine, set a permissive submodule protocol config to simulate a legacy/misconfigured environment: `git config --global protocol.file.allow always`.
2. Create a malicious repository whose `.gitmodules` references a submodule URL of `file:///etc` (or another sensitive local path) with a fabricated gitlink SHA.
3. Have a Desktop user `git fetch`/`git pull` this repository via the Desktop UI. Because `fetch.ts`/`pull.ts` pass `--recurse-submodules(=on-demand)` without ever adding `-c protocol.file.allow=always`/`never` explicitly, the operation's submodule behavior is governed solely by the ambient config from step 1, and the submodule is fetched from the local filesystem path.
4. Compare against the same scenario via `checkoutBranch`: with `allowFileProtocol` defaulted to `false`, `updateSubmodulesAfterOperation` does not add `protocol.file.allow=always`, and (assuming Git's own compiled-in defaults) the checkout path additionally benefits from Git's built-in protections at a different, explicit code layer — demonstrating the inconsistency between the two "equivalent" submodule-init code paths in this codebase, as covered (for checkout only) by `app/test/unit/git/checkout-test.ts` lines 150-189, which has no pull/fetch equivalent test asserting the same protocol restriction. [12](#0-11)

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
