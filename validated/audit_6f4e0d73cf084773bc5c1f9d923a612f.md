### Title
Stale decimals in EVM native-token ERC20 pointers after tokenfactory admin updates bank denom metadata - (File: precompiles/pointer/pointer.go)

### Summary
The `AddNative` pointer-registration flow reads a tokenfactory/bank denom's `decimals` (derived from its `DenomUnit.Exponent` list) from the current bank `Metadata` at the moment the ERC20 pointer contract is deployed, and bakes that value immutably into the deployed native ERC20 pointer contract. A tokenfactory denom's admin (an ordinary, unprivileged tokenfactory denom creator — no governance or validator privilege required) can subsequently call `MsgSetDenomMetadata` to change the same denom's `DenomUnits`/`Exponent` (i.e., its effective decimals) at any time after the pointer has already been created. The already-deployed ERC20 pointer's cached `decimals()` never gets updated to reflect the new metadata, producing a permanent decimals mismatch between the CW/bank-side denom and its EVM ERC20 representation — the same bug class flagged in the Aave `LendingPoolConfigurator.setReserveDecimals` report, where changing decimals without propagating the change to dependent token representations/oracles causes mispricing.

### Finding Description
`PrecompileExecutor.AddNative` in `precompiles/pointer/pointer.go` computes `decimals` from the denom's registered `Metadata.DenomUnits` and passes it into `UpsertERCNativePointer`, which deploys (or reuses) a native ERC20 pointer contract with that `decimals` value hard-coded as part of its constructor arguments: [1](#0-0) 

`UpsertERCNativePointer` forwards the metadata (including `Decimals`) into the generic `UpsertERCPointer` constructor-argument path: [2](#0-1) 

The underlying `Metadata`/`DenomUnit` used to derive this decimals value is fully mutable after pointer creation: a tokenfactory denom admin can call `MsgSetDenomMetadata`, which is handled by `msgServer.SetDenomMetadata`. The only check performed is that `msg.Sender` matches the denom's own authority/admin — no interaction with, or invalidation of, any already-deployed EVM pointer contract: [3](#0-2) 

This ultimately calls the base bank keeper's `SetDenomMetaData`, which simply overwrites the stored `Metadata` (including `DenomUnits`/`Exponent`) with no propagation logic to any consumer that previously cached the value: [4](#0-3) 

Because the pointer contract's `decimals()` was baked in at deploy time (from the metadata snapshot taken during `AddNative`), it will silently diverge from the denom's true, current decimals once the admin updates the metadata. Any downstream EVM smart contract or off-chain integrator that trusts the pointer's `decimals()` — e.g., an AMM computing swap ratios, or a lending/DeFi protocol scaling collateral/oracle values by token decimals — will use the stale value, exactly mirroring the underlying Aave root cause: "changing the decimals... will not automatically change the decimals... additionally, the oracle must also be updated... otherwise mispricing and liquidations can occur."

### Impact Explanation
Any EVM protocol (AMM, lending market, custom pricing logic) integrating a native-token pointer as an ERC20 and relying on `decimals()` to normalize amounts will compute incorrect exchange ratios or collateral valuations once the underlying denom's metadata decimals are changed post-pointer-creation. This can lead to under/over-valuation of the token in AMMs or lending protocols, enabling mispriced swaps or improper liquidations/borrows — a concrete fund-loss vector consistent with the "Medium/High" impact bar (unauthorized value transfer/mispricing via a pointer), not merely a cosmetic display bug, since decimals feed directly into on-chain arithmetic in consuming contracts.

### Likelihood Explanation
The path is fully reachable by a normal, unprivileged actor: any account can create a tokenfactory denom (`MsgCreateDenom`), permissionlessly get an ERC20 pointer created for it via the pointer precompile (`add_native`), and, being the sole tokenfactory admin of their own denom, freely call `MsgSetDenomMetadata` at any later block to alter `DenomUnits`/`Exponent`. No governance, validator, or cross-party cooperation is required — likelihood is high for any token issuer who initially sets one exponent and later "corrects" or changes it after external protocols have already integrated the pointer.

### Recommendation
Either (a) disallow `MsgSetDenomMetadata` from changing `DenomUnits`/`Exponent` once an ERC20 pointer already exists for that denom (query the pointer registry in `SetDenomMetadata`/`SetDenomMetaData` and reject or require re-registration), or (b) make the pointer's `decimals()` a live query against current bank metadata (similar to how `CW20ERC20Pointer.decimals()` performs a live `token_info` query) rather than an immutable constructor-time value, so pointer callers always see the authoritative current decimals.

### Proof of Concept
1. Attacker creates a tokenfactory denom `factory/<attacker>/FOO` via `MsgCreateDenom`.
2. Attacker sets initial `Metadata` with a `DenomUnit` of exponent 18 (`MsgSetDenomMetadata`).
3. Anyone calls the pointer precompile `add_native(factory/<attacker>/FOO)`; `AddNative` reads the current metadata (exponent 18) and deploys a native ERC20 pointer with `decimals = 18`.
4. A third-party AMM/lending protocol is deployed and integrates this pointer, using `decimals()` (18) to normalize its accounting/pricing.
5. Attacker (still the denom admin) calls `MsgSetDenomMetadata` again, changing the `DenomUnit` exponent to, e.g., 2.
6. The already-deployed pointer's `decimals()` still returns 18 — a 10^16 discrepancy versus the "true" current decimals — while `bank_precompile` and any newly-deployed pointer would reflect the new value, creating an internally inconsistent decimals view that the integrated protocol continues to trust, resulting in a severely mispriced/miscalculated token amount within that protocol.

func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	contractAddr, err := p.evmKeeper.UpsertERCNativePointer(ctx, evm, token, utils.ERCMetadata{Name: name, Symbol: symbol, Decimals: decimals})
	if err != nil {
		return nil, 0, err
	}

func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
}
