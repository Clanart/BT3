### Title
Single unclaimable reward token permanently blocks claiming of all other reward tokens in `BaseRewardPool` - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool.getReward()` iterates over the full `rewardTokens` array and performs a `safeTransfer` for every token with a non-zero balance in a single loop, with no error handling. If any single reward token's transfer to the account reverts (e.g., the account is blacklisted on that token, the token is paused, or it reverts on a specific edge case), the entire call reverts, and the user cannot claim *any* of the reward tokens accrued in that pool — not just the problematic one. Unlike `vlMGPBaseRewarder`, `BaseRewardPool` provides no working fallback to claim a subset of tokens.

### Finding Description
`getReward` loops over all registered reward tokens and unconditionally calls `safeTransfer` for each one with a pending balance: [1](#0-0) 

If any single `IERC20(rewardToken).safeTransfer(_receiver, reward)` call reverts (blacklisted receiver on a token like USDC-style reward tokens, a paused token, or any ERC20 exhibiting reverting behavior), the whole transaction reverts due to Solidity's default revert-on-failure propagation in the loop — there is no `try/catch` or skip-and-continue logic, analogous to the `sweepTo` issue in the referenced report.

Critically, `BaseRewardPool` exposes no working alternative to selectively claim only the "good" tokens. The `getRewards` function, which is supposed to allow claiming a specific subset of reward tokens (and is called by `MasterMagpie._claimBaseRewarder` when a subset is requested), is an empty stub that does nothing: [2](#0-1) 

The claim entry point in `MasterMagpie` routes to either the all-or-nothing `getReward` or the no-op `getRewards`: [3](#0-2) 

So once one reward token becomes untransferable for a given account, that account has zero functioning code path to retrieve any of the other legitimately earned reward tokens from that pool.

Note that this does not block withdrawal of the principal stake, since `_harvestBaseRewarder` (called during deposit/withdraw) only calls `rewarder.updateFor(_account)`, which just updates accounting and performs no transfers: [4](#0-3) 
So the accrued-but-unclaimed reward balances for the affected user keep accumulating correctly in `userRewards`, but remain permanently unreachable.

### Impact Explanation
An ordinary staker whose address becomes non-transferable for just one of the pool's reward tokens (e.g., blacklisted on a USDC-like reward token used as a bribe/incentive, or that token becomes paused/upgraded to revert) permanently loses the ability to claim any and all reward tokens earned from that specific `BaseRewardPool`, including tokens they are otherwise fully entitled to and which are unaffected by the block. This is a permanent freeze of unclaimed yield for the affected user, with no available recovery path in the current contract, satisfying the "permanent freezing of unclaimed yield" impact category.

### Likelihood Explanation
This requires no privileged or malicious action from the protocol admin. It can occur passively any time a legitimately-added reward token (added via `queueNewRewards`, an `onlyManager` action independent of any individual staker) has blacklist/pause/weird-ERC20 semantics and the staker's own receiving address later becomes restricted on that specific token (e.g., regulatory blacklisting, which is outside the staker's and protocol's control). Given multiple reward tokens accumulate for popular pools over time, the probability that at least one becomes problematic for at least one address is non-trivial over the life of the protocol.

### Recommendation
Wrap each `safeTransfer` call inside `getReward`'s loop in a try/catch (or use low-level `call` and check success), and on failure, skip that specific token (optionally re-queuing it as unpaid, similar to `unpaidRewards` handling seen elsewhere in the codebase, e.g. `mocks/wombat/MultiRewarderPerSec.sol` lines 168-201) rather than reverting the whole batch. Additionally, implement `BaseRewardPool.getRewards` properly (rather than leaving it as a no-op) so that a user can explicitly select and claim only the reward tokens that are currently transferable for them.

### Proof of Concept
1. Pool `P` has reward tokens `[MGP, WOM, BadToken]` registered via `queueNewRewards`, where `BadToken` implements a blacklist (e.g., USDC-style) or is later paused/upgraded to always revert on transfer to a specific address.
2. User `Alice` stakes into pool `P` and accrues rewards in `MGP`, `WOM`, and `BadToken`.
3. `Alice`'s address becomes blacklisted on `BadToken` (a condition entirely outside her and the protocol's control, e.g. regulatory action on the stablecoin).
4. Alice calls `MasterMagpie.multiclaim([P])` → `_multiClaim` → `_claimBaseRewarder` → `BaseRewardPool(P).getReward(Alice, Alice)`. [5](#0-4) 
5. The loop in `getReward` reaches `BadToken`'s `safeTransfer` call and reverts, causing the whole `getReward` call (and thus the whole `multiclaim` transaction) to revert.
6. Alice tries `multiclaimSpec([P], [[MGP, WOM]])` to skip `BadToken`, but this routes to `getRewards`, which is an empty stub and silently transfers nothing. [2](#0-1) 
7. Alice has no remaining path to claim her legitimately earned `MGP` and `WOM` rewards from pool `P` — they are permanently frozen, even though her stake principal can still be withdrawn normally (since withdrawal only calls `updateFor`, not `getReward`).

            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier

        }

        return true;

    function _claimBaseRewarder(address _stakingToken, address _account, address _receiver, address[] memory _rewardTokens) internal {
        IBaseRewardPool rewarder = IBaseRewardPool(tokenToPoolInfo[_stakingToken].rewarder);
        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
                rewarder.getRewards(_account, _receiver, _rewardTokens);
            else
                // if not specifiying any reward token, just claim them all
                rewarder.getReward(_account, _receiver);
        }
    }
