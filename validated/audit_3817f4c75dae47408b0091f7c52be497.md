### Title
DkgConfirmer reuses deterministic nonces across `share` and `complete`, enabling secret share recovery when inputs differ - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The upstream bug class is a persistent mark/state that one path clears and another leaves stale, causing an inconsistent interpretation on the second pass. The Serai analog lives in `SigningProtocol::preprocess_internal`: the FROST preprocess seed is cached in `CachedPreprocesses` keyed only by `context` and is **never cleared after signing**. Every call to `share_internal` re-derives the *same* nonces from that seed via `AlgorithmSignMachine::from_cache`. `DkgConfirmer::share` signs once, and `DkgConfirmer::complete` calls `share_internal` **a second time** with freshly supplied `preprocesses` and `key_pair`. If either differs from the first call, the same nonces are used to produce a second signature share over different equations, which is the classic Schnorr/FROST nonce-reuse key-recovery condition.

### Finding Description
- `preprocess_internal` stores a ChaCha20 seed in `CachedPreprocesses` under `context = (b"DkgConfirmer", attempt)` and reuses it on every invocation for that attempt; nothing deletes it after a share is produced (`signing_protocol.rs:123-147`).
- `share_internal` rebuilds the machine from that cached seed and calls `machine.sign(preprocesses, msg)` (`signing_protocol.rs:150-178`).
- `DkgConfirmer::share` invokes `share_internal` with attacker-influenced `preprocesses` and `key_pair` (`signing_protocol.rs:288-310`).
- `DkgConfirmer::complete` invokes `share_internal` **again** — also with caller-supplied `preprocesses` and `key_pair` — to rebuild the machine (`signing_protocol.rs:312-327`).
- The message signed is `set_keys_message(&self.spec.set(), &removed, key_pair)` (`signing_protocol.rs:296-301`), so a different `key_pair` yields a different challenge `c` for the same nonce `k`. Alternatively, a different `preprocesses` map changes the binding factor `rho` and the included set / interpolation factor, again changing the share equation.
- With two shares `s1 = k + c1·x` and `s2 = k + c2·x` (same `k`, different effective equation), the MuSig secret share `x` is recoverable by any observer of the two published shares. FROST's own documentation states reuse of a preprocess "will enable third-party recovery of your private key share" (`frost/src/sign.rs:85-87`, `spec/cryptography/FROST.md:51-55`).
- The file's own header acknowledges the missing guard: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" (`signing_protocol.rs:50-54`). The BFT-ordering argument only covers ordering of *received* messages; it does not enforce that `share` and `complete` sign byte-identical `(preprocesses, msg)` inputs, and `complete` takes `preprocesses` from its caller rather than reusing the finalized set from `share`.

### Impact Explanation
Recovery of a validator's MuSig secret share for the validator-set key. Since this key is the root of trust used for on-chain DKG confirmation (per the file header), share recovery compromises the threshold signing key protecting validator set transitions. Reachable by any party able to submit the preprocesses/key_pair data that flows into `complete` (a participating validator or whoever can cause the confirmation transaction to be processed) with values differing from those used in `share` — no colluding threshold required, only a single unprivileged input divergence.

### Likelihood Explanation
Medium. Exploitation requires the two `share_internal` invocations to see differing inputs. `complete` accepts its `preprocesses` and `key_pair` as fresh arguments rather than caching the exact values `share` used, and the code explicitly notes the on-chain-preprocess-matches-presumed-preprocess check is a TODO. Whether a distinct finalized `complete` payload is actually routable depends on `coordinator/src/tributary/handle.rs` call sites (not fully verified), but the missing-identity-check between the two signing passes is exactly the stale-state pattern of the f2fs bug.

### Recommendation
- After `sign` succeeds, delete the `CachedPreprocesses` entry (or mark it consumed) so a second `share_internal` under the same context fails rather than re-signing.
- Persist the `preprocesses` map hash and `msg` hash alongside the cached seed on first `sign`, and reject any subsequent call whose inputs hash differently.
- Implement the noted TODO: verify the on-chain preprocesses equal the locally regenerated ones before publishing shares.

### Proof of Concept
Conceptual: assume `share(P1, K1)` is invoked and publishes share `s1`, then `complete(P2, K2, shares)` is invoked with `K2 ≠ K1` (or `P2 ≠ P1`). Both calls rebuild `AlgorithmSignMachine::from_cache` with the identical seed → identical nonces `d, e` → identical nonce commitments. `machine.sign` computes `s_i = d + (rho_i · e) + (c_i · λ_i · x)`; with `K2` changing `msg`, `c2 ≠ c1`, so `x = (s1 − s2) / (λ(c1 − c2))` (with `λ` the Lagrange factor), recovering the validator's secret share. The nonce determinism is confirmed by `seeded_preprocess` deriving nonces purely from `ChaCha20Rng::from_seed(*seed.0)` and the secret share (`frost/src/sign.rs:121-144`).

Unverified caveat: I could not inspect `coordinator/src/tributary/handle.rs` (the grep returned match counts only, not content), so the exact routing that feeds distinct `preprocesses`/`key_pair` into `complete` versus `share` is inferred from the function signatures and the documented TODO rather than confirmed at the call sites.
