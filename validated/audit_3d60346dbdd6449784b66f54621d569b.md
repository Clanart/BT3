### Title
Deterministic CachedPreprocess reuse across distinct `key_pair` messages enables FROST secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The DKG-confirmer signing path caches a FROST preprocess seed keyed only by `(b"DkgConfirmer", attempt)` and never deletes it. Both `share()` and `complete()` regenerate the identical nonces from that cached seed via `preprocess_internal`, while the signed message is a function of an attacker-influenced `key_pair`. Two signatures produced over different `key_pair` values under the same attempt reuse the same nonce, allowing a third party to recover the validator's private key share — the classic "use of a consumed one-time value" analog of a use-after-free.

### Finding Description
`SigningProtocol::preprocess_internal` stores a ChaCha20 seed as `CachedPreprocesses[context]` where `context = (b"DkgConfirmer", self.attempt)` (line 275). If a cached seed exists, it is decrypted and reused via `AlgorithmSignMachine::from_cache` → `seeded_preprocess`, which deterministically regenerates `nonces` and `commitments` from the seed (crypto/frost/src/sign.rs:127-135). The entry is only ever `get`/`set`; nothing removes it, so every `preprocess_internal` call under the same attempt produces identical nonces.

`DkgConfirmer::share` and `DkgConfirmer::complete` both call `share_internal` → `preprocess_internal`, and the message signed is `set_keys_message(&self.spec.set(), &removed, key_pair)` where `key_pair` is supplied per-call (lines 288-326). The FROST signature share is `s = d + b·rho + λ·share·c` where `d, b` are the nonces and `c` is the challenge over `(commitments, msg)`. Two executions with the same nonces but different `key_pair` yield shares `s₁, s₂` with different `λ_i·c_i` terms; with known `d + b·rho` recoverable from the shared commitments, the secret share is solvable.

Even the documented invariant is violated: `cache()`/`from_cache` docs state "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" (crypto/frost/src/sign.rs:218-219). The coordinator violates this MUST.

### Impact Explanation
Recovery of a validator's FROST/MuSig secret share reduces the threshold security of the DKG confirmation signatures for the validator set and, combined with shares recovered from other validators, enables forgery of `set_keys` confirmations — i.e., signing unintended messages as the validator set. This is a High-severity key-share-recovery path reachable entirely through public protocol inputs (`key_pair` / preprocess messages submitted to the tributary).

### Likelihood Explanation
An unprivileged participant who can cause `share()`/`complete()` to run for two distinct `key_pair` values within one DKG attempt (e.g., by submitting competing DKG confirmation data for the same attempt) triggers the reuse. The determinism makes exploitation reliable: no race or memory-safety primitive is needed, just two invocations with different messages under the same `(context, attempt)` key.

### Recommendation
Bind the cache context to the full message being signed (e.g., `context = (b"DkgConfirmer", attempt, hash(key_pair))`), or delete the `CachedPreprocesses` entry when the sign machine is consumed (`share()`/`complete()` must not regenerate a machine from a seed already used by `share()`). Alternatively, derive fresh nonces per `share_internal` call rather than resurrecting them from a persistent seed.

### Proof of Concept
```rust
// Attacker triggers within one attempt:
let share1 = confirmer.share(preprocesses.clone(), &key_pair_a)?; // msg_a signed
let share2 = confirmer.share(preprocesses.clone(), &key_pair_b)?; // SAME nonces, msg_b
// s1 - s2 = lambda * share * (c1 - c2) -> solve for `share`
```
Both calls hit `CachedPreprocesses::get` at signing_protocol.rs:137 and rebuild identical `nonces` via `seeded_preprocess` (sign.rs:127-141), while `msg` differs because `set_keys_message` commits to `key_pair` (lines 296-300).
