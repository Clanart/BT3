### Title
Zero-context patch application in `discardChangesFromSelection` can silently discard/corrupt unselected lines - ([File: app/src/lib/git/apply.ts])

### Summary
The External Report's core defect is a missing output safeguard: the contract computes and applies a monetary-effecting value (`outputAmount`) without ever validating that the value produced matches what the user actually intended, allowing a manipulated input state to silently produce a wrong (zero or reduced) result that the user has no way to reject. The closest verifiable analog in this GitHub Desktop codebase is `discardChangesFromSelection` in `app/src/lib/git/apply.ts`, which builds a client-synthesized unified diff patch from `formatPatchToDiscardChanges` (`app/src/lib/patch-formatter.ts`) and applies it with `git apply --unidiff-zero --whitespace=nowarn -` [1](#0-0) . Like the swap contract, this destructive, irreversible operation (permanently deleting uncommitted working-directory changes) is executed with no post-hoc verification that the effect on disk matches the user's selected line ranges.

### Finding Description
`formatPatchToDiscardChanges` reconstructs hunk headers purely from the parsed `DiffHunk.header.oldStartLine`/`newStartLine` values and locally recomputed `oldCount`/`newCount`, using the raw `line.text` content taken directly from `git diff` output of the working tree against `HEAD` [2](#0-1) . That patch is fed to `git apply` with `--unidiff-zero`, a flag that tells Git to match/apply hunks by line-number position rather than requiring the normal surrounding context lines Git usually uses to confirm the hunk is being applied to the right location [3](#0-2) . `--whitespace=nowarn` further suppresses any diagnostic output Git would otherwise surface.

Because the patch's line offsets are derived entirely from a `DiffHunk`/`DiffLine` model built by Desktop's own `DiffParser` (`app/src/lib/diff-parser.ts`), any mismatch between the parser's line/offset bookkeeping and the true state of the file on disk (for example a repository whose HEAD content is attacker-controlled — a hostile clone/fetch target — with unusual line-ending mixes, "no newline" markers, or the LF↔CRLF autocrlf rewriting Desktop already special-cases in `gitignore.ts` and warns about via `DiffContentsWarning`) can cause `git apply --unidiff-zero` to place the reconstructed hunk at the wrong offset. Unlike the normal (non-zero-context) `git apply` used in `applyPatchToIndex`, there is no context-line cross-check forcing Git to bail out if the surrounding lines don't match, so the operation can succeed while modifying/discarding content the user never selected. There is no verification step after `discardChangesFromSelection` runs that diffs the resulting file against the expected pre-image to confirm only the selected lines were affected.

This mirrors the report's broken invariant precisely: a value with real consequences (here, the working-directory file content that has not yet been committed) is computed from potentially attacker-influenced input and applied without any "expected vs. actual" guard, and the existing safeguards (Git's normal context-matching, size/line-ending warnings) are bypassed by the `--unidiff-zero` mode used specifically for this destructive operation.

### Impact Explanation
If triggered, this would silently corrupt the user's uncommitted working-directory changes — deleting or mangling lines the user did not choose to discard — with `discardChangesFromSelection` providing no recovery path, since discarded changes are not staged or otherwise recoverable through Desktop. This satisfies the "silent corruption of what the user commits or pushes" impact category: a user who believes they discarded one hunk may unknowingly lose or corrupt other, unrelated work, or, in the reverse, believe changes were discarded when they were not, and subsequently commit/push content they did not intend.

### Likelihood Explanation
This is a **low-confidence, unverified hypothesis** rather than a confirmed exploit path. I was not able to construct or observe a concrete crafted-repository input that reliably desyncs `DiffParser`'s line accounting from `git apply --unidiff-zero`'s positional matching within the scope of this analysis — the parser has explicit safeguards for the "no newline" marker (`app/src/lib/diff-parser.ts` lines 325-338) and hidden bidi characters are already flagged as a `DiffContentsWarning`. Triggering the mismatch would likely require an unusual combination of line-ending/`autocrlf` state changes, large/binary-adjacent diffs, or parser edge cases not covered by the existing unit tests (`app/test/unit/git/apply-test.ts`, `app/test/unit/patch-formatter-test.ts`). Without reproducing an actual desynchronization, likelihood should be treated as speculative.

### Recommendation
- After `git apply` succeeds in `discardChangesFromSelection`/`applyPatchToIndex`, re-diff the affected file (or the full index) and assert that only the intended hunk/line ranges changed before treating the operation as successful.
- Avoid `--unidiff-zero` for destructive discard operations where feasible, or add a minimal-context safety check (e.g., verifying context lines around the hunk before rewriting it) to prevent zero-context positional mis-application.
- Add fuzz/property tests that feed `DiffParser`-parsed hunks with adversarial line-ending, "no newline," and combining-character content through `formatPatchToDiscardChanges` → `git apply` and assert byte-for-byte equivalence between expected and actual post-discard file content.

### Proof of Concept
Not reproduced. This report is a structural analog derived from static code review of `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, and `app/src/lib/diff-parser.ts` rather than a demonstrated exploit; a concrete PoC would require constructing a specific repository/file state that desynchronizes the parser's hunk offsets from `git apply --unidiff-zero`'s positional application, which was not established during this analysis.

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}

```typescript
export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.newStartLine,
      newCount,
      hunk.header.oldStartLine,
      oldCount
    )
    patch += hunkBuf
  })
```
