### Title
Malicious repository can force Desktop's git-credential trampoline to erase a victim's unrelated stored credentials - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop registers itself as `git`'s credential helper (`credential.helper=desktop`) for every git invocation, and routes `get`/`store`/`erase` calls through `createCredentialHelperTrampolineHandler`. For any host that Desktop classifies as "generic" (non-GitHub.com/GHE), the `erase` command deletes the corresponding entry from `localStorage`/keychain purely based on the `host`/`username`/`protocol` fields that `git` sends on stdin, without verifying that this host/username pair is the one the user is actually authenticated to or intended to affect.

### Finding Description
`getCredentialUrl` builds the target identity strictly from the credential-helper protocol fields (`url`/`protocol`/`host`/`username`/`path`) supplied by `git` on stdin. [1](#0-0) 

`eraseCredential` then deletes the generic credential keyed by that host+username with no ownership or provenance check: [2](#0-1) 

`deleteGenericCredential` unconditionally wipes both the `localStorage` username entry and the keychain (`TokenStore`) entry for that endpoint: [3](#0-2) 

`git` itself decides when to call `erase` — it does so whenever an authentication attempt against a given remote URL fails after a `fill`. The remote URL that gets authenticated (and thus the host/username eventually pushed through `erase`) is not limited to the repository the user explicitly opened: it also includes URLs pulled in via `.gitmodules` submodule entries, `insteadOf`/URL rewrites, or any other remote reference embedded in a cloned/fetched repository's tracked content — all of which are attacker-controlled once the user clones or fetches a malicious repo. Nothing in `createCredentialHelperTrampolineHandler` or `eraseCredential` validates that the host being erased corresponds to the repository the user is currently working with or to a credential the user actually just tried to use in this session. [4](#0-3) 

This mirrors the `claimFees` flaw structurally: a state-mutating operation (`feeRecipientToTokenToAmount[to] = 0` / `deleteGenericCredential(endpoint, username)`) trusts an externally supplied identifier (`to` address / `host`+`username` derived from attacker-influenced repo data) instead of confirming it matches the actual party entitled to have that state changed (the fee recipient calling for itself / the account whose own failed authentication triggered the erase).

### Impact Explanation
An attacker who authors a public repository (or a submodule referenced by one) can point a submodule/remote URL at any arbitrary "generic" git host with a chosen username (e.g. a corporate Git server the victim already uses, or `github-enterprise-mirror.example.com`), configured to always fail authentication. When the victim clones/fetches this repository (including via `--recurse-submodules`, which Desktop performs), git will call the desktop credential helper's `erase` for that unrelated host+username, silently deleting the victim's previously stored generic-git credentials (username/password or PAT saved via the credential prompt) for that unrelated service — with no confirmation, warning, or link back to the repository the user actually opened. This is a real corruption/lockup of credentials the user rightfully stored, forcing them to re-authenticate (and, in constrained environments, potentially breaking unattended/CI-style clone flows that rely on cached generic credentials).

### Likelihood Explanation
Any repository the victim clones or fetches — including transitively via submodules — can embed a remote URL, so no special privileges, local access, or social engineering beyond "open/clone this repo" is required, consistent with the "attacker controls a cloned/fetched repository" threat model. The trigger is a normal Desktop operation (clone/fetch with submodules), and the erase path is reached automatically by git's own credential-helper protocol whenever authentication to the attacker-chosen host fails, which the attacker fully controls (e.g., serving a `401`).

### Recommendation
Scope credential `erase`/`store` operations to hosts/usernames that are actually relevant to the operation Desktop initiated for the currently tracked repository (e.g., cross-check against the repository's own configured remotes, or require the erased host to match one previously `fill`ed within the same trampoline token/session), rather than trusting the host/username fields verbatim from the credential-helper stdin for arbitrary submodule-introduced URLs.

### Proof of Concept
1. Create a public repo `victim-bait` whose `.gitmodules` contains a submodule URL such as `https://internal-git.company.com/whatever` (a generic, non-GitHub host the target is known/likely to use), configured server-side to return `401 Unauthorized`.
2. Victim, who has previously saved generic git credentials for `internal-git.company.com` in Desktop (via `setGenericCredential`), clones `victim-bait` with submodules in GitHub Desktop.
3. Git attempts to fetch the submodule, fails auth against `internal-git.company.com`, and invokes Desktop's registered credential helper with `erase` and `host=internal-git.company.com`, `username=<guessed/attacker-chosen>`.
4. `eraseCredential` → `deleteGenericCredential` wipes the victim's stored credential entry for that host/username, per [2](#0-1)  and [3](#0-2) , even though the victim never intended this unrelated repo to affect that host's stored credential.

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}

/** Implementation of the 'erase' git credential helper command */
async function eraseCredential(cred: Credential, store: Store, token: string) {
  if ((await getEndpointKind(cred, store)) !== 'generic') {
    return
  }

  return useExternalCredentialHelper()
    ? eraseExternalCredential(cred, token)
    : deleteGenericCredential(
        urlWithoutCredentials(getCredentialUrl(cred)),
        forceUnwrap(`credential missing username`, cred.get('username'))
      )
}

export const createCredentialHelperTrampolineHandler: (
  store: AccountsStore
) => TrampolineCommandHandler = (store: Store) => async command => {
  const firstParameter = command.parameters.at(0)
  if (!firstParameter) {
    return undefined
  }

  const { trampolineToken: token } = command
  const input = parseCredential(command.stdin)

  if (__DEV__) {
    debug(
      `${firstParameter}\n${command.stdin
        .replaceAll(/^password=.*$/gm, 'password=***')
        .replaceAll(/^(.*)$/gm, '  $1')
        .trimEnd()}`
    )
  }

  try {
    if (firstParameter === 'get') {
      const cred = await getCredential(input, store, token)
      if (!cred) {
        const endpoint = `${getCredentialUrl(input)}`
        info(`could not find credential for ${endpoint}`)
        setHasRejectedCredentialsForEndpoint(token, endpoint)
      }
      return cred ? formatCredential(cred) : undefined
    } else if (firstParameter === 'store') {
      await storeCredential(input, store, token)
    } else if (firstParameter === 'erase') {
      await eraseCredential(input, store, token)
    }
    return undefined
  } catch (e) {
    error(`${firstParameter} failed`, e)
    return undefined
  }
}

/** Delete a generic credential */
export function deleteGenericCredential(endpoint: string, username: string) {
  localStorage.removeItem(getKeyForUsername(endpoint))
  return TokenStore.deleteItem(getKeyForEndpoint(endpoint), username)
}
