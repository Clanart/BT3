### Title
Case-sensitive `contains`/`starts_with`/`ends_with`/`equals` operators silently diverge from `regex_match`'s `re.IGNORECASE` compilation, allowing case-varied dangerous commands to bypass hookify block rules - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._check_condition` implements `regex_match` via `compile_regex()`, which always compiles patterns with `re.IGNORECASE`, but implements `contains`, `starts_with`, `ends_with`, and `equals` using plain Python string operators, which are case-sensitive. A hookify block rule written to stop a dangerous command (e.g. `rm -rf`) using `contains`, `starts_with`, or `ends_with` will fail to match a case-varied form of the same command (e.g. `RM -RF`), while the identical pattern used with `regex_match` would match, because shells execute commands case-insensitively for many binaries/aliases but the rule engine does not normalize case consistently across operators.

### Finding Description
`_check_condition` dispatches on `condition.operator`: [1](#0-0) 
`regex_match` routes to `_regex_match`, which calls `compile_regex(pattern)`, and that function unconditionally applies `re.IGNORECASE`: [2](#0-1) 
In contrast, `contains` (`pattern in field_value`), `starts_with` (`field_value.startswith(pattern)`), and `ends_with` (`field_value.endswith(pattern)`) perform raw, case-sensitive Python string comparisons with no normalization step.

Attack flow: a rule author (project maintainer, not the attacker) writes a `PreToolUse`/`Bash` block rule intended to stop dangerous commands, e.g. `field="command", operator="contains", pattern="rm -rf"`. An unprivileged attacker who can influence the agent's command choice (e.g. via prompt injection from untrusted repository content, issue text, or tool output that Claude reads and then decides to execute) instructs the agent to run `RM -RF /path` or a mixed-case variant instead. Because Unix shells resolve `rm` and `RM` differently only if such a binary/alias exists, but many command wrappers, PowerShell contexts, or case-insensitive filesystems (and simply typo/obfuscation acceptance by users) make case variants plausible attacker-controlled forms; the `contains` check `"rm -rf" in "RM -RF /path"` evaluates to `False`, so `_rule_matches` returns `False` for that condition, and the block rule never fires. The same pattern under `operator="regex_match"` would match due to `re.IGNORECASE`, so the enforcement outcome differs purely based on which operator the rule author picked — a subtle, non-obvious footgun for defenders writing blocking rules who reasonably assume the engine's operators behave consistently with respect to case.

### Impact Explanation
This is a hook-enforcement bypass: a security-relevant `block` rule configured via `contains`/`starts_with`/`ends_with` (rather than `regex_match`) fails silently against case-varied attacker-influenced input, allowing a dangerous `Bash` command (or other tool action) to execute despite an administrator's intent to block it. This matches "unauthorized command execution due to bypassed hook enforcement" — a meaningful Claude Code trust-boundary/guardrail bypass, though its severity is bounded by the precondition that a defender must have chosen a case-sensitive operator for a security-critical rule instead of `regex_match`.

### Likelihood Explanation
Requires: (1) a hookify block rule using `contains`, `starts_with`, or `ends_with` against a lowercase (or fixed-case) dangerous-command pattern, and (2) an attacker able to influence the exact casing of the command the agent executes (e.g., via prompt injection). Both are realistic: `contains` is the most intuitive/commonly documented operator for simple substring blocking, and case variation is a trivial, repeatable obfuscation technique. No special privileges are needed by the attacker beyond typical prompt-injection reach already assumed in the Claude Code threat model.

### Recommendation
Normalize case consistently across all operators — either (a) apply `.lower()` to both `pattern` and `field_value` for `contains`/`starts_with`/`ends_with`/`equals` (and document this as case-insensitive by default), or (b) make `regex_match` case-sensitive by default and require an explicit flag/pattern prefix for `re.IGNORECASE`, and clearly document per-operator case-sensitivity in `plugins/hookify/skills/writing-rules/SKILL.md` and `README.md` so rule authors do not assume uniform behavior.

### Proof of Concept
Differential unit test in `plugins/hookify/core/rule_engine.py` test harness:
```python
engine = RuleEngine()
tool_input = {"command": "RM -RF /tmp/test"}
data = {"tool_name": "Bash", "tool_input": tool_input}

contains_cond = Condition(field="command", operator="contains", pattern="rm -rf")
regex_cond = Condition(field="command", operator="regex_match", pattern=r"rm\s+-rf")

assert engine._check_condition(contains_cond, "Bash", tool_input, data) is False   # bypass
assert engine._check_condition(regex_cond, "Bash", tool_input, data) is True       # would have blocked
```
This demonstrates that identical intent ("block rm -rf variants") produces divergent enforcement outcomes solely based on operator choice, confirming the bypass for `contains`-based block rules against case-varied dangerous commands.
