### Title
Copilot conflict resolution splices resolved hunks by positional order only, with no semantic tie to which lines are real git conflict markers - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` rebuilds a resolved file by scanning `rawContent` line-by-line for regex-matched marker syntax (`<{7}`, `={7}`, `>{7}`) and replacing each detected block with the *next* entry from the model's `hunkResolutions` array, matched purely by array order. [1](#0-0) 
The only safety check is `validateResolutionPaths`, which compares the *aggregate count* of hunks the model returned against the *aggregate count* recorded when the conflict context was first built - it never re-validates that those counts still correspond to the same actual marker positions at splice time. [2](#0-1) 

### Finding Description
This is the same bug class as the report: a downstream calculation (`_baseVestedAmount`/withdrawal math there, hunk-to-content assignment here) depends on an implicit invariant between two independently-derived values, and only one side of that relationship is checked.

- The expected hunk count (`expectedHunkCounts`) comes from whatever parsed `IFileConflictContext.hunks` at the time the conflict context/prompt was built.
- The actual splice points are re-derived independently inside `reassembleResolvedFile` by scanning `rawContent` for lines matching `^<{7}`, `^={7}$`, `^>{7}` at reassembly time.
- `validateResolutionPaths` only confirms `resolution.hunks.length === expectedCount` — a scalar equality check, not a structural/positional one. [3](#0-2) 

Because the two counts can be produced by different parsing passes over attacker-influenced file content, and because the splice logic explicitly documents "matched by order, not by line number" as its correspondence strategy, any drift between the two scans that nonetheless preserves the total count (e.g. a repository file that legitimately contains literal text resembling conflict-marker syntax, such as documentation about git conflicts, embedded patch/diff content, or a source file with `<<<<<<<`-looking string literals) will be spliced against the wrong block. `reassembleResolvedFile` itself acknowledges it treats any line matching the regex as a splice point regardless of whether it's a "real" conflict boundary, falling back to "copy through" only when the immediate look-ahead fails to also find a separator+closer. [4](#0-3) 

The reassembled content is written straight to disk and staged for commit with no further diffing against the original conflict set: [5](#0-4) 

### Impact Explanation
This satisfies the "silent corruption of what the user commits" impact class: the attacker only needs to control the *contents of a conflicting file* in a repository the victim clones/fetches (e.g. via a branch, PR, or merge target) — no local access, no admin rights, no credentials needed. If the crafted content causes a mismatch between where the model's resolved hunks are meant to land and where the naive regex-based splicer decides to land them, the user's "Continue Merge" action silently writes and stages incorrect content: legitimate authored lines that merely look like marker syntax can be deleted/replaced, or a real conflict resolution can be applied to the wrong location in the file, producing a corrupted commit that the user believes reflects Copilot's actual per-hunk resolution.

### Likelihood Explanation
Medium/Low, mirroring the original report's own downgrade rationale: the path requires the user to opt into Copilot-assisted conflict resolution and click "Continue Merge" on a conflicted file whose surrounding content happens to trigger the marker regex outside of genuine conflict blocks. It is not exploitable by an anonymous, unprompted network attacker without the victim performing a merge/rebase/cherry-pick against attacker-influenced content, and I could not fully verify (index limits) whether the initial hunk-count extraction routine that builds `IFileConflictContext.hunks` uses byte-for-byte the same marker-detection regex as `reassembleResolvedFile`, which would materially affect how easily the two counts can drift while still matching. Recommend a Devin session to confirm the exact extraction implementation the two counts derive from.

### Recommendation
Tie the splice position to the same marker-parse data structure used to build `IFileConflictContext.hunks` (e.g., persist line offsets or block boundaries at extraction time and reuse them for reassembly) instead of re-scanning `rawContent` independently. At minimum, validate that the *set of marker blocks* detected during reassembly matches — by count and by canonical content of `oursContent`/`theirsContent`, not just aggregate count — what was recorded at extraction time, and abort the write (falling back to manual conflict resolution) on any mismatch rather than silently splicing by best-effort order.

### Proof of Concept
1. Set up a merge where `some-file.md` has one real conflict block plus, elsewhere in the same file, literal text that matches the conflict-marker regex (e.g. a markdown snippet documenting `<<<<<<< ours` / `=======` / `>>>>>>> theirs` syntax as an example, which is common in contributor-guide or git-tutorial files).
2. Trigger Copilot conflict resolution; the model's per-hunk resolution array has exactly 1 entry for `some-file.md`'s 1 "real" hunk, matching `expectedHunkCounts`, so `validateResolutionPaths` passes. [3](#0-2) 
3. In `reassembleResolvedFile`, the line scan encounters the documentation snippet's marker-like lines first (well-formed per the look-ahead check for separator + closer) and splices the model's single resolved hunk into that block instead of the real conflict, while the real conflict block (now `hunkIndex >= hunkResolutions.length`) is silently dropped with no replacement content. [4](#0-3) 
4. `_applyCopilotConflictResolutions` writes this corrupted reassembly straight to disk and `git add`s it, so the user commits/pushes content that neither side of the merge intended. [6](#0-5)

/**
 * Validate that a parsed resolution response matches the expected set of
 * file paths and hunk counts. Throws CopilotValidationError on unexpected
 * paths, duplicates, missing files, or wrong hunk counts.
 */
export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
