## Title
Line-index-based partial-commit selection is silently re-applied to a freshly re-fetched (possibly changed) diff, causing commits to include unreviewed content - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop's partial-commit (line-by-line staging) feature builds a `DiffSelection` that is purely positional — it records selected/unselected *line indices*, with no binding to the actual line content or a diff/file hash. When the user actually commits, `applyPatchToIndex` re-fetches the diff from disk via `getWorkingDirectoryDiff` a second time and blindly re-applies those old positional indices to the new diff object to build the patch. If the working-tree file changes between the moment the diff was rendered/selected in the UI and the moment the commit is executed, the indices no longer refer to the same lines, so the resulting patch — and thus the commit — silently contains different content than what the user reviewed and selected. This mirrors the reported Solidity bug class: a value (`_errI`/state) is recomputed one way for display and a different way (stale/mismatched) for the actual state-changing operation, and the two are never reconciled or invalidated against each other.

### Finding Description
The UI flow is:
1. `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts` calls `getWorkingDirectoryDiff` to obtain the diff shown to the user [1](#0-0) .
2. The user selects specific lines to stage, which are stored as raw integer line indices inside `DiffSelection` (`withLineSelection`/`withRangeSelection`/`isSelected`) with **no correlation to line content**, only to a positional index within that diff snapshot [2](#0-1) .
3. When the user commits, `_commitIncludedChanges` passes the selected `WorkingDirectoryFileChange` objects (carrying the stale `DiffSelection`) straight into `createCommit` [3](#0-2) .
4. `createCommit` → `stageFiles` → `applyPatchToIndex` for any partially-selected file **re-fetches a brand-new diff** from the working directory rather than reusing the one the user actually looked at: `const diff = await getWorkingDirectoryDiff(repository, file)` [4](#0-3) .
5. `formatPatch(file, diff)` then walks the **new** diff's hunks and lines and asks `file.selection.isSelected(absoluteIndex)` using the **old** positional indices to decide what to include [5](#0-4) .

There is no check anywhere in this path that the diff used to build the selection is the same diff being patched (e.g., no hash/identity comparison between the diff rendered and the diff re-fetched at staging time). Contrast this with the `updateChangesWorkingDirectoryDiff` reload path, which explicitly re-validates state before applying loaded results (`isSameFile`, `arrayEquals` on selected IDs) before committing to state [6](#0-5) ; no equivalent guard exists between diff-selection time and `applyPatchToIndex`'s re-fetch.

### Impact Explanation
If the on-disk file content shifts between the diff render and the commit click — e.g. a build tool, linter/formatter-on-save, an editor autosave, a background `git` hook, or (per the report's threat model) a malicious script triggered upon opening/interacting with a cloned or fetched repository that modifies tracked files — the hunks/line offsets in the newly fetched diff no longer match those the user inspected. The same integer indices from `DiffSelection` will then point at unrelated lines in the new diff, so `formatPatch` builds a patch that stages/commits content the user never selected or even saw. This is silent corruption of what the user commits (and subsequently pushes), matching the "Valid Impact" category in the report (attacker controls repository content, result is silent corruption of what the user commits).

### Likelihood Explanation
The change window is real: `createCommit` performs `unstageAll` then `stageFiles` (which triggers the second `getWorkingDirectoryDiff` call) only after the user presses commit, so there is a non-trivial gap after the diff was rendered/selected in the Changes view. Any process capable of touching a working-tree file in that window — including tooling launched by opening/building a hostile cloned repository (e.g. `postinstall`/build scripts, IDE format-on-save, git hooks) — can trigger the mismatch without any unusual user action beyond normal editing/reviewing/committing.

### Recommendation
Bind the `DiffSelection` (or the `WorkingDirectoryFileChange`) to the exact diff it was computed against (e.g., diff/content hash or the diff object itself), and have `applyPatchToIndex`/`stageFiles` refuse to stage (or force a UI re-diff/re-confirmation) when the working-tree diff at staging time differs from the one the selection was derived from, analogous to the recommendation to make interest-rate view and mutating paths share one consistent, up-to-date computation rather than recomputing independently.

### Proof of Concept
1. Modify a tracked file with several disjoint edits and open it in GitHub Desktop's Changes view; only select (via line-level checkboxes) the addition on line 50.
2. Before clicking "Commit", have a background process (e.g., a save-on-format IDE plugin, a `postinstall`/watch script from a hostile cloned repo, or any process with normal write access to the working directory) insert/remove lines earlier in the same file, shifting subsequent line offsets.
3. Click "Commit". `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and `formatPatch` applies the old absolute index 50 to the new hunk layout (`app/src/lib/patch-formatter.ts:143-171`), producing a patch for a different line than the one the user selected.
4. Inspect the resulting commit: it contains a change the user never selected/reviewed, while the change they intended to commit may be silently left out or included unintentionally.
