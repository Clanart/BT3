## Analog Identified: Unauthenticated `CallDispatcher.dispatch()` lets anyone drain any balance the shared dispatcher holds

### Title
Unauthenticated arbitrary-call execution in `CallDispatcher.dispatch()` allows theft of any resident ETH/ERC20 balance — ([File: evm/src/utils/CallDispatcher.sol])

### Summary
The external report's core broken invariant is: *a trusted component blindly performs an outbound action (HTTP GET) to an attacker-chosen, unvalidated destination, and the destination can be a place where valuable side effects occur (a local dev API allowing code execution).* The local Hyperbridge analog is `CallDispatcher`, a shared utility contract used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute attacker/user-supplied `Call[]` batches (arbitrary `to`, `value`, `data`) during predispatch/postdispatch order execution and cross-chain token receipt. Its `dispatch()` entrypoint performs the equivalent of the SSRF's unauthenticated outbound request: it makes a call to a fully attacker-chosen `to` address with attacker-chosen `data`/`value`, and it has **no caller restriction whatsoever** — unlike every other privileged entrypoint in the codebase (`onlyHost`, `restrict(...)`, `AdminOrigin`, `_authenticate`), `CallDispatcher.dispatch()` can be invoked by any account, at any time. [1](#0-0) 

### Finding Description
`CallDispatcher` is designed to be a shared, persistent contract (one instance referenced from `_params.dispatcher` by `IntentGatewayV2`/`IntentsBase`, and from `_dispatcher` by `HyperFungibleToken`/`WrappedHyperFungibleToken`). It:

- Accepts ETH unconditionally via `receive() external payable {}`. [2](#0-1) 
- Exposes `dispatch(bytes memory encoded)` as a plain `external` function with **no access-control modifier at all** — no `onlyHost`, no owner check, no allow-listed caller set. It decodes an ABI-encoded `Call[]` and executes each call verbatim against `call.to` with `call.value` and `call.data`, the only guard being `extcodesize(to) > 0`. [3](#0-2) 

Every legitimate caller (`IntentGatewayV2._fillCrossChain/_fillSameChain/_execute`, `HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`) transfers real value (ERC20 tokens or native ETH) *into* the dispatcher immediately before calling `dispatch()`, expecting it to be swept back out afterward: [4](#0-3) [5](#0-4) 

Because `dispatch()` is unauthenticated, this design relies entirely on the assumption that the dispatcher never holds a balance except during the narrow legitimate window the gateway controls. That assumption is false in several code-verifiable ways:

1. `receive()` accepts native ETH from **anyone**, unconditionally — a stray or malicious direct transfer permanently deposits ETH into the shared contract.
2. The sweep logic in `IntentsBase._execute` and in `IntentGatewayV2`'s predispatch/postdispatch flows only sweeps the **specific tokens listed in the order** (`order.output.assets[i].token`, `order.inputs[i].token`). Any other token balance the dispatcher happens to hold (e.g. dust from rounding, a reward/airdrop token sent to it, or a token left over from an unrelated integrator's calldata) is never swept by the gateway and sits in the contract indefinitely.
3. Because `dispatch()` has no caller check, **any unprivileged external account** can call it directly with a `Call[]` that transfers out any ERC20 balance or ETH balance currently resident in the contract, to any address of their choosing — this is the exact SSRF analog: an unauthenticated, arbitrary "outbound request" (contract call) to a destination and with a payload fully controlled by the attacker, executed by a trusted component that happens to be holding value.

This differs from all the other cross-chain fund-movement paths in the repo (token gateway `teleport`, `HyperFungibleToken.onAccept`, `IntentsBase._withdraw`, `SimplexPaymaster`), all of which gate privileged/fund-moving actions behind `onlyHost`, `restrict(...)`, source/module authentication (`_authenticate`, `UnauthorizedSource`), or `AdminOrigin` — `CallDispatcher.dispatch()` has none of these.

### Impact Explanation
Any ETH or ERC20 balance transiently or accidentally resident in the shared `CallDispatcher` (dust from fee rounding, a token not part of an order's asset list, direct/accidental ETH transfers accepted by `receive()`) is stealable by any unprivileged address at will, with no relayer, prover, admin, or governance compromise required — this is a direct "stealing or loss of funds" / "unauthorized transaction or execution" impact matching the bounty scope. Because `CallDispatcher` is shared across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` production deployments, the blast radius extends to all products using it as `_params.dispatcher`/`_dispatcher`.

### Likelihood Explanation
Likelihood is high for the "stray dust" case: ETH sent directly to the contract's address (mistaken transfers, integrators assuming `dispatch()` is access-controlled, or partial/failed sweep paths under edge-case rounding) accumulates indefinitely and is trivially drainable by anyone monitoring the contract's balance — no privileged actor or race condition is needed, only a plain read of `address(dispatcher).balance` / `token.balanceOf(dispatcher)` followed by a call to `dispatch()`.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by an authorized set of caller contracts (e.g. `onlyAuthorizedCaller` mapping set at construction/governance, mirroring the `restrict(...)` pattern used in `EvmHost.sol`), or scope dispatcher instances 1:1 per calling contract so no cross-application balance mixing is possible. Additionally, add a sweep-everything path so any non-order-specific token/ETH balance left in the dispatcher can only be recovered by the legitimate owning contract/governance, not by an arbitrary caller.

### Proof of Concept
```solidity
// Any unprivileged EOA/contract, no prior setup required:

// 1. Cause (or wait for) any residual balance in the shared CallDispatcher,
//    e.g. send ETH directly — receive() accepts unconditionally:
(bool ok,) = address(callDispatcher).call{value: 1 ether}("");
require(ok);

// 2. Drain it — dispatch() has no access control at all:
Call ;
calls[0] = Call({
    to: attackerControlledOrAnyContract,
    value: 1 ether,
    data: ""            // or any calldata targeting an ERC20 `transfer` to attacker
});
callDispatcher.dispatch(abi.encode(calls));
// attackerControlledOrAnyContract now received the 1 ETH — no auth check was ever performed.
```
For the ERC20 dust case, replace the `Call` with `{to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, token.balanceOf(address(callDispatcher)))}` and call `dispatch()` directly — this succeeds identically since `dispatch()` never checks `msg.sender`.

Note: I was not able to fully verify from the available snippets whether any deployed instance of `CallDispatcher` is configured per-caller (i.e., whether production deployments always use a fresh, dedicated instance with zero standing balance between calls) versus a single shared singleton referenced by multiple apps' `_params.dispatcher`/`_dispatcher` fields — this distinction affects exploitability and should be confirmed against the actual on-chain deployment configuration before treating this as immediately live-exploitable.

```text
    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
