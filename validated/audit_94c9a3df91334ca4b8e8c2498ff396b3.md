### Title
Uncompensated ELF verification/JIT-compilation cost lets unprivileged users force cheap, unbounded validator CPU burn via program cache churn - (File: svm/src/transaction_processor.rs, program-runtime/src/program_cache_entry.rs)

### Summary
The reported bug class is: an attacker can cheaply "donate" a negligible input that flips a trigger condition, forcing a victim's automation to repeatedly perform expensive, gas-costing work that the victim cannot stop because the exit condition can never be satisfied. The Agave analog is that any unprivileged transaction that references a program not currently in the validator-global `ProgramCache` triggers real, uncompensated CPU work (ELF loading, bytecode verification, and JIT compilation), while the transaction's *charged* cost is fixed purely by its declared `compute_unit_limit`, independent of whether a cache miss/recompile actually occurred.

### Finding Description
`replenish_program_cache` calls `load_program_with_pubkey`, which performs `Executable::load`, `executable.verify::<RequisiteVerifier>()`, and `executable.jit_compile()` for every missing/evicted program [1](#0-0) , with the actual expensive work done in `ProgramCacheEntry::new_internal` [2](#0-1) . This loading/verification/compilation step happens completely outside of the transaction's compute meter — it is not part of `InvokeContext`/`compute_meter.consume_checked` accounting used by syscalls and instructions (contrast with e.g. `SyscallBigModExp`, which explicitly charges CU for real work [3](#0-2) ).

Meanwhile, the on-chain cost model that determines what a transaction is charged/allocated for block-inclusion purposes derives `programs_execution_cost` solely from the requested `compute_unit_limit` in the transaction's compute-budget instruction, not from any actual cache-miss/verification/compile cost incurred: [4](#0-3) .

Additionally, any transaction batch that causes a cache miss (`loaded_missing`) or modifies the cache (`merged_modified`) triggers a probabilistic eviction pass that shrinks the entire global program cache down to 90% of capacity every single time: [5](#0-4) . This is a routine, unprivileged, and cheap action — any transaction invoking a program that isn't presently resident in cache (which naturally happens with normal churn, or can be amplified by an attacker interleaving calls to many distinct large/complex on-chain programs) causes this eviction to run against the shared, validator-wide cache used by all other users' concurrent and subsequent transactions.

### Impact Explanation
Because verification and JIT compilation are real CPU-bound operations (parsing ELF sections, disassembly-based control-flow/relocation verification, and native code generation) whose cost scales with program complexity/size but is not metered or charged proportionally to the compute budget, an attacker can cheaply and repeatedly force cache churn (comparable to the report's "negligible donation" repeatedly re-triggering the victim's swap loop). Each forced reload/recompile consumes disproportionate validator CPU time relative to the CU fee paid, and — unlike the swap-loop analog which drains one victim's wallet — here the "victim" is the shared validator/cluster resource: repeated cheap cache-miss transactions can degrade block-production/replay throughput for all other participants, a materially underpriced-compute condition (`replenish_program_cache`/`load_program_with_pubkey` cost vs. the fixed CU-limit-based charge in `CostModel::get_estimated_execution_cost`).

### Likelihood Explanation
Any unprivileged user can submit ordinary transactions invoking on-chain programs; no special role, signature forgery, or privileged instruction is required. Cache misses/evictions occur as part of normal cache management (`evict_using_random_selection`) on nearly every batch containing a previously-uncached program [5](#0-4) , so the trigger condition is trivial and always available; the only variable is how consistently/severely an attacker can amplify churn (e.g., by round-robining calls across many sizeable deployed programs), which is inherently within attacker control since program invocation is permissionless.

### Recommendation
Charge compute units (or an equivalent fee) proportional to actual ELF load/verify/JIT-compile cost when a cache miss occurs (i.e., feed `LoadProgramMetrics`/compilation time back into the transaction's effective cost, similar to how the report's mitigation "fix DCA automation to only swap requested amount" bounded the attacker-triggerable work), and/or rate-limit or better protect frequently-used, expensive-to-recompile programs from eviction churn caused by low-value transactions (the `retention_score`/GDSF mechanism already tracks `compilation_time_ema` [6](#0-5)  but only informs *which* entries to keep, not whether the triggering transaction should pay for the churn it causes).

### Proof of Concept
Not independently reproducible from the index alone (no sandbox/terminal access). Conceptually: deploy several large/complex BPF programs; submit interleaved transactions invoking a rotating subset large enough to exceed the cache's "hot set," causing every transaction to be a `missing_programs` cache miss under `replenish_program_cache`; each such transaction pays only its declared `compute_unit_limit` while validators independently pay wall-clock cost for `Executable::load` + `verify::<RequisiteVerifier>` + `jit_compile` per miss. Confirming the real-world severity (whether this is already bounded elsewhere, e.g. by mempool/scheduler-level throttling not visible in this index) would require running this scenario against a live/local validator, which is outside the scope of this read-only analysis.

    fn get_estimated_execution_cost(
        transaction: &impl TransactionMeta,
        feature_set: &FeatureSet,
    ) -> (u64, u64) {
        // if failed to process compute_budget instructions, the transaction will not be executed
        // by `bank`, therefore it should be considered as no execution cost by cost model.
        let (programs_execution_costs, loaded_accounts_data_size_cost) =
            match transaction.transaction_configuration(feature_set) {
                Ok(config) => (
                    u64::from(config.compute_unit_limit),
                    Self::calculate_loaded_accounts_data_size_cost(
                        config.loaded_accounts_data_size_limit,
                        feature_set,
                    ),
                ),
                Err(_) => (0, 0),
            };

        (programs_execution_costs, loaded_accounts_data_size_cost)
    }
