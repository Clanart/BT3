### Title
Stale line-selection indices applied against a freshly re-computed diff cause partial commits to silently include/exclude the wrong lines - (File: `app/src/lib/patch-formatter.ts`, `app/src/lib/git/apply.ts`)

### Summary
When a user stages a *partial* file (selecting individual lines/hunks to commit), Desktop stores the selection as a `DiffSelection` keyed by **absolute line indices** computed from the diff that was rendered in the Changes view. At commit time, `applyPatchToIndex()` re-runs `git diff` to obtain a **brand new** diff object and then blindly re-applies the old, index-based selection to it via `formatPatch()`. If the working-tree content backing that diff changes between the moment the user made the selection and the moment the commit actually runs, the hunk/line layout (and therefore the absolute indices) can shift, causing the wrong lines to be included in — or excluded from — the generated patch, with no re-validation or user-visible warning.

### Finding Description
- `DiffSelection` tracks selected/unselected lines purely by integer index (`divergingLines: Set<number>`), computed from `hunk.unifiedDiffStart + lineIndex` of a specific diff snapshot: [1](#0-0) .
- `formatPatch()` builds the patch to `git apply --cached` purely by testing `file.selection.isSelected(absoluteIndex)` against the *current* diff's hunks, with zero validation that the diff's content matches the diff the selection was computed against: [2](#0-1) .
- `applyPatchToIndex()` — called for every partially-selected file during staging — fetches a fresh diff right before formatting the patch: [3](#0-2) .
- `stageFiles()` resets the whole index and then, for files with `DiffSelectionType.Partial`, calls `applyPatchToIndex` using the file object (and its `selection`) taken from `_commitIncludedChanges`'s in-memory state, not a freshly reconciled one: [4](#0-3) [5](#0-4) .
- The code base is itself aware that "the diff might have changed dramatically since last we loaded it," but the reconciliation logic that recomputes `selectableLines` and drops now-invalid indices only runs opportunistically inside the diff-loading callback used to refresh the UI's diff viewer (`_loadStatus`/diff-selection refresh path), not immediately before staging/commit: [6](#0-5) . This reconciliation only prunes lines that no longer exist as includeable lines; it does **not** protect against the more dangerous case where the new diff has a *different* hunk layout (e.g. added/removed context lines, different `unifiedDiffStart` offsets) so that indices from the old selection now point at semantically different lines that are still "includeable." In that case `isSelected(absoluteIndex)` returns a stale true/false answer for lines whose meaning has changed.
- There is no re-diff / re-validation performed between `_commitIncludedChanges` reading `state.changesState.workingDirectory.files` and `createCommit` → `stageFiles` → `applyPatchToIndex` re-diffing and applying that selection: [7](#0-6) [8](#0-7) .

This is the direct structural analog of the Cork Protocol bug: an accounting value (`psm.balances.ra.locked`) computed against one snapshot of state is reused/re-applied against a later, different snapshot of the same resource without reconciliation, silently corrupting the tracked value. Here, the "accounting value" is the set of line indices a user intended to commit, and the "later snapshot" is the freshly re-diffed working tree at staging time.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user who reviews a partial diff, selects specific lines, and then commits could have Desktop stage and commit different lines than reviewed — including lines the user explicitly deselected (potential secret/credential leakage, unintended code) or excluding lines the user wanted committed (silently dropping a fix). Because the corruption is silent (no error, `formatPatch` only throws on an *empty* patch, not a *wrong* one), the user has no signal that the commit content diverged from what they reviewed in the UI.

### Likelihood Explanation
The precondition is that the working-tree file content changes between the user making a line selection and the commit actually executing `git diff` inside `applyPatchToIndex`. This is realistic and does not require local/physical access, admin rights, or pre-existing malware:
- A cloned/fetched repository can legitimately include developer tooling (format-on-save scripts, lint-staged, file watchers, build scripts run via `npm run watch`, git smudge/clean filters declared in `.gitattributes`) that rewrites tracked files asynchronously while Desktop is open and a commit is in progress — this is normal repo-provided behavior, not social engineering.
- Desktop's own background refresh cycle (periodic `git status`/diff polling) plus a slow user (reviewing a diff, typing a commit message) creates a realistic window between diff-review and commit for external processes or file-system events to mutate the file.
- No special/unnatural user action is required beyond the ordinary "select lines → type message → click commit" workflow.

### Recommendation
Before formatting/applying the partial patch in `applyPatchToIndex` (and generally before `stageFiles`/`createCommit` proceeds), re-diff the file and verify the freshly obtained diff's structural fingerprint (e.g., hash of hunk headers/line content) matches what the selection was computed against. If it doesn't match, abort the partial-stage for that file and force the UI to refresh the diff and require the user to re-confirm the selection, rather than silently reapplying stale absolute-index selections to a structurally different diff.

### Proof of Concept
1. Open a repository in Desktop with a modified tracked file, e.g. `notes.md`.
2. In the Changes view, select only specific lines/hunks to include (partial selection), leaving the commit message box open (not yet clicking Commit).
3. While the commit box is still open, have an external process (e.g., a repo-provided `npm run watch` task, an editor's format-on-save, or simply another terminal) append/rewrite lines in `notes.md` so the hunk boundaries shift (e.g., add several new lines above the previously-selected hunk).
4. Click "Commit" without reopening the diff view (so Desktop does not recompute `selectableLines`/reconcile the selection).
5. Inspect the resulting commit with `git show`: the staged/committed lines correspond to the *old* absolute indices reapplied to the *new* diff, not the lines the user actually reviewed and intended to select — demonstrating silent corruption of commit content. This can be confirmed conceptually by tracing `formatPatch` (`app/src/lib/patch-formatter.ts:135-171`) being fed the diff freshly fetched in `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) together with the pre-existing `file.selection` object, with no equality/staleness check in between.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
