### Title
mWOMSVBaseRewarder._calExpireForfeit never applies rewardablePercentWAD, allowing full-cooldown mWomSV holders to claim 100% of rewards with zero forfeiture - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` hardcodes `rewardableAmount = _amount`, so `forfeitAmount` is always `0` regardless of the user's lock/cooldown state, unlike the equivalent `vlMGPBaseRewarder._calExpireForfeit` which scales `rewardableAmount` by `vlMGP.getRewardablePercentWAD(_account)`. Any mWomSV holder can move 100% of their stake into cooldown via `startUnlock()` and still receive full accrued rewards via `getReward()`/`getRewards()`, permanently stealing the yield share that should be forfeited and redistributed to fully-locked holders.

### Finding Description
`mWOMSVBaseRewarder.getReward()`/`getRewards()` are callable by `masterMagpie` on behalf of any account (reachable by the unprivileged holder through normal staking/claim flow) [3](#0-2) , and both route through `_sendReward`, which computes `forfeitAmount` via `_calExpireForfeit(_account, userRewards[_rewardToken][_account])` [4](#0-3) .

In `vlMGPBaseRewarder._calExpireForfeit`, the reward is scaled down by the fraction of the user's balance that is *not* in cooldown, obtained from `vlMGP.getRewardablePercentWAD(_account)`:
```
uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
``` [2](#0-1) 

In `mWOMSVBaseRewarder._calExpireForfeit`, this scaling is missing entirely:
```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
``` [5](#0-4) 

Since `rewardableAmount` is set equal to `_amount` unconditionally, `forfeitAmount = _amount - rewardableAmount` is always `0`. The `mWOM.getRewardablePercentWAD(_account)` function is fully implemented and available on the linked `mWOMSV` locker contract (identical logic to `VLMGP`'s), computing a reduced percentage while a user is in cooldown [1](#0-0) , but `mWOMSVBaseRewarder` never calls it. There is no other check (modifier, `updateReward`, receipt-token accounting) that reduces the payout for cooldown users — `_updateFor`/`updateReward` only track `rewardPerToken` accrual, not lock status [6](#0-5) .

Exploit flow:
1. Attacker calls `mWomSV.lock()`/`lockFor()` to deposit mWOM and receive mWomSV, staked in `masterMagpie`.
2. Rewards accrue over time to the attacker's `mWomSV` balance.
3. Attacker calls `mWomSV.startUnlock(fullAmount)`, moving 100% of their balance into cooldown (this itself triggers `multiclaimFor` but that's a routine claim, not the exploit).
4. Attacker calls `getReward()`/`getRewards()` (via `masterMagpie`) — `_calExpireForfeit` returns `0` forfeiture regardless of `fullyInLock == 0`, so the attacker receives 100% of `userRewards`.
5. The share that should have been forfeited (redistributed via `_queueNewRewardsWithoutTransfer` to remaining fully-locked holders) is instead paid out and permanently lost to those other holders.

### Impact Explanation
This is theft of unclaimed yield: fully-locked mWomSV holders are supposed to receive the forfeited share of rewards from users in cooldown (per the `vlMGPBaseRewarder` design pattern and the `ForfeitRewardAdded` event/`_queueNewRewardsWithoutTransfer` mechanism present in `mWOMSVBaseRewarder` itself) [7](#0-6) . Because forfeiture is always zero, that redistribution never happens, and the cooldown-initiating user keeps 100% of rewards they should have partially forfeited. This is a permanent, protocol-wide misallocation of yield affecting every mWomSV reward token, matching the "theft or permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
Trivial to trigger: any holder of mWomSV (obtained by locking mWOM, an ordinary permissionless action) can call `startUnlock()` for their full balance and then claim rewards normally through the standard `masterMagpie` claim path. No special capital, timing, or privileged role is required, and the bug is deterministic and repeatable for every reward distribution cycle.

### Recommendation
Mirror `vlMGPBaseRewarder._calExpireForfeit`: in `mWOMSVBaseRewarder._calExpireForfeit`, fetch `mWOMSV.getRewardablePercentWAD(_account)` and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before deriving `forfeitAmount`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWOM`, `mWomSV`, `masterMagpie`, `mWOMSVBaseRewarder` with a mock reward token.
2. Two users, A and B, each lock equal amounts of mWOM into `mWomSV`.
3. Queue a reward amount via `queueNewRewards` on `mWOMSVBaseRewarder`, let it accrue to both users.
4. User A calls `mWomSV.startUnlock(fullBalance)` to move 100% into cooldown; confirm `mWomSV.getRewardablePercentWAD(A) == 0`.
5. Call `mWOMSVBaseRewarder.calExpireForfeit(A, rewardToken)` (or directly `_calExpireForfeit` via a harness) and assert it returns `0`, while an equivalent `vlMGPBaseRewarder` setup (same cooldown state, same `getRewardablePercentWAD` value) returns `forfeitAmount == earnedAmount` (since `rewardablePercentWAD == 0` there).
6. Call `getReward(A, A)` and assert A receives the full `earned` amount, and no `ForfeitRewardAdded` event/added `rewardPerTokenStored` occurs from A's claim.
7. Assert User B (fully locked) receives no redistributed forfeited share, proving the yield meant for B was instead paid to A in full.

        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
