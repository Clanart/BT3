### Title
OP_RETURN Data Output Is Excluded From Fee Weight Calculation, So `SignableTransaction` Undercharges and Can Produce Transactions Below the Required Fee Rate - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The reported bug class is an accounting mismatch: a liability (referrer fees) is recorded/credited without the corresponding assets being deducted, leaving the protocol with a permanent shortfall. The analog in Serai's in-scope code is in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`: when arbitrary `data` is provided, an OP_RETURN output is appended to the transaction's outputs, yet `calculate_weight_vbytes` — which determines `needed_fee` and `fee_with_change` — is only ever called with `payments` (and optionally `change`), never with the data output. The OP_RETURN output's weight and value-field/script overhead is therefore accounted in the transaction (it occupies real vbytes on-chain) but never deducted from the fee budget, exactly mirroring "credited but not deducted" accounting.

### Finding Description
`SignableTransaction::new` builds `tx_outs` by pushing every payment output and then, if `data` is present, pushing an additional OP_RETURN `TxOut` carrying up to 80 bytes of attacker-influenced data [1](#0-0) . The fee computation, however, calls `calculate_weight_vbytes(tx_ins.len(), payments, None)` — a function which reconstructs a mock transaction whose `output` vector contains only the payment outputs plus an optional change output [2](#0-1) . There is no parameter or path by which the OP_RETURN output reaches `calculate_weight_vbytes`, so `needed_fee = fee_per_vbyte * vbytes` is computed on a vbytes figure that omits the data output entirely [3](#0-2) .

The same omission occurs in the change branch: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again excludes the OP_RETURN output, so `fee_with_change` is likewise undercounted, and the change value `input_sat - payment_sat - fee_with_change` absorbs only the undercounted fee [4](#0-3) . Consequently:

- The real transaction is larger than the measured `vbytes`/`vbytes_with_change` by the size of the OP_RETURN output (~11 bytes overhead + up to 80 bytes of data).
- The `TooLowFee` check against `DEFAULT_MIN_RELAY_TX_FEE` is evaluated against the underestimated vbytes [5](#0-4) , so a transaction whose *actual* fee rate is below the relay minimum can pass validation.
- `needed_fee()` returns a fee that does not achieve the caller-specified `fee_per_vbyte` on the transaction as it will actually be broadcast.

### Impact Explanation
When `data` is attached — in Serai's usage this is instruction data carried on-chain as an OP_RETURN, derived from externally supplied deposit/instruction data — the resulting transaction pays a fee rate strictly below the requested `fee_per_vbyte`, and can fall below the minimum relay fee while having passed the `TooLowFee` guard. The signed transaction is then rejected by relay policy or left unconfirmed, meaning outputs the scanner reported as spendable are locked in a transaction that cannot propagate — funds effectively unspendable and a shortfall between the declared and achieved fee, directly analogous to the protocol's uncollateralized referrer-fee liability. If the transaction does propagate, the excess simply burns into a higher-than-intended absolute fee or is absorbed from change, so the concrete harm is transactions failing relay/confirmation at low fee rates.

### Likelihood Explanation
The bug triggers deterministically whenever `SignableTransaction::new` is called with `Some(data)` — no race or special state is needed. The `data` parameter originates from untrusted instruction bytes supplied by an unprivileged depositor, so the trigger is publicly reachable. Exploitation severity is bounded: the fee deficit is at most ~91 vbytes times the fee rate, so at high fee rates the transaction still clears relay; at `fee_per_vbyte` near the minimum relay fee, however, a maximally sized data payload reliably pushes the true fee rate below the relay floor.

### Recommendation
Include the OP_RETURN output in the weight/vbytes calculation. Either extend `calculate_weight_vbytes` to accept the full output list (payments + data + change) or add a `data: Option<&[u8]>` parameter that appends a `ScriptBuf::new_op_return` output to the mock transaction, and use the resulting vbytes for `needed_fee`, `fee_with_change`, and the `TooLowFee` check at [6](#0-5)  and [7](#0-6) . Add a regression test asserting `tx.fee() >= fee_per_vbyte * tx.vsize()` when `data` is `Some`.

### Proof of Concept
```rust
// Conceptual PoC against SignableTransaction::new
let data = vec![0xaa; 80]; // max permitted
let tx = SignableTransaction::new(
    vec![input],                  // ReceivedOutput with sufficient value
    &[(payment_script, DUST)],
    Some(change_script),
    Some(data),
    1,                            // 1 sat/vbyte — near min relay
).unwrap();

// needed_fee was computed on a mock tx with no OP_RETURN output
let needed = tx.needed_fee();
// The real transaction contains the ~91 extra vbytes of the OP_RETURN output
let real_vsize = tx.transaction().vsize() as u64;
// Fee actually paid
let actual_fee = tx.fee();
// actual_fee == needed (change absorbs only the undercounted fee),
// but actual_fee < 1 * real_vsize, i.e. effective rate < requested rate
assert!(actual_fee < real_vsize);
// At the boundary, actual_fee < DEFAULT_MIN_RELAY_TX_FEE * real_vsize / 1000
// despite the TooLowFee check having passed — the tx will be rejected by relay.
```

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }

    let weight = tx.weight();

    // Now calculate the size in vbytes

    /*
      "Virtual transaction size" is weight ceildiv 4 per
      https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki

      https://github.com/bitcoin/bitcoin/blob/306ccd4927a2efe325c8d84be1bdb79edeb29b04
        /src/policy/policy.cpp#L295-L298
      implements this almost as expected, with an additional consideration to signature operations

      Signature operations (the second argument of the following call) do not count Taproot
      signatures per https://github.com/bitcoin/bips/blob/master/bip-0342.mediawiki#cite_ref-11-0

      We don't risk running afoul of the Taproot signature limit as it allows at least one per
      input, which is all we use
    */
    (
      weight.to_wu(),
      u64::try_from(bitcoin::policy::get_virtual_tx_size(
        i64::try_from(weight.to_wu()).unwrap(),
        0i64,
      ))
      .unwrap(),
    )
  }
