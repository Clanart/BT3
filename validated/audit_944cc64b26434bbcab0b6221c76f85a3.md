### Title
Zero-value `GaslessConfig.BalanceCheckLevel` silently disables all gasless swap/approve safety checks, enabling fund-draining swap bundles - (File: kaiax/gasless/config.go)

### Summary
`GaslessConfig.BalanceCheckLevel` is an `int` whose intended safe default is `BalanceCheckLevelAll` (3), but any zero-value `GaslessConfig{}` (constructed without calling `DefaultGaslessConfig()`) implicitly resolves to `BalanceCheckLevelStatic` (0) because it is the Go zero value and also `iota`'s first value. This exactly mirrors the `defaultScaledOfferFactor == 0` bug class: an unset/omitted configuration parameter silently degrades a financial safety gate to "no discount/no check", instead of failing safe.

This is structurally the same bug class as the `UniV3OracleImpl` report: a numeric configuration parameter whose unset/zero value silently disables the intended economic safeguard (there: 0% price ⇒ 100% discount; here: level 0 ⇒ 0 checks performed), and it is reachable by any unprivileged gasless-swap sender submitting a swap/approve transaction bundle once the node operator (or any code path) instantiates `GaslessConfig` without the documented default.

### Impact Explanation
With `BalanceCheckLevel == BalanceCheckLevelStatic` (0), a gasless-bundle sender can submit an approve+swap pair where the sender has no token balance, no allowance, and/or an `amountIn` insufficient for the claimed `minAmountOut`. Since only the "static" relation checks (deadline, `minAmountOut >= amountRepay`) remain, the consensus-node lender still fronts KAIA gas via the generated lend tx based on `swapTx.Fee()`, exposing the CN operator (fee-delegation counterparty) to a fund-drain: attacker submits many such swap bundles, the lender pays gas up front, and the swap subsequently reverts or fails to produce funds sufficient to repay, resulting in unrecoverable loss of the consensus node's KAIA balance. This is unauthorized value movement / fee-delegation abuse against the gasless module's lender, satisfying the Medium+ bar.

### Likelihood Explanation
Likelihood depends on whether the zero-value `GaslessConfig{}` (rather than `DefaultGaslessConfig()`) is ever the effective configuration in production, e.g. via `cmd/utils/config.go` / `node/cn/config.go` toml unmarshalling of a `[Gasless]` section that omits `BalanceCheckLevel`, or via any embedding path that does not call `SetGaslessConfig`/`DefaultGaslessConfig`. Given the test suite itself repeatedly constructs raw `&gasless.GaslessConfig{...}` literals without setting `BalanceCheckLevel` (e.g. `init_test.go`), the pattern of omitting this field is demonstrably easy to reproduce, making misconfiguration plausible for real deployments (e.g. TOML configs generated by hand or by older config templates that predate this field).

### Recommendation
- Make `BalanceCheckLevelAll` (or any explicit "safe" sentinel) the effective behavior when `BalanceCheckLevel` is unset, e.g. by reordering the `iota` constants so `0` means "all checks" and the least-safe level is a larger, explicitly-opted-in number, or by treating `0`/negative as "use default" inside `ShouldCheckToken`/`ShouldCheckSwapAmount`/`ShouldCheckSenderCode`.
- Alternatively, add a validation step in `GaslessModule.Init` that rejects or upgrades a `GaslessConfig` whose `BalanceCheckLevel` was not explicitly set (e.g., use a `*int` or explicit "IsSet" flag), forcing operators to opt into a reduced check level rather than silently falling back to the weakest one.
- Add regression coverage ensuring `GaslessConfig{}` (Go zero value) is never treated as a fully-checked (safe) configuration, and add a doc comment on `BalanceCheckLevel`/`GaslessConfig` making the unsafe zero-value behavior explicit for operators as the original report recommends doing for `defaultScaledOfferFactor`.
