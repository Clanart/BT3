### Title
`GaslessSwapRouter` accepts unrestricted native KAIA via `receive()` with no accounting, allowing accidental transfers to be swept by owner via `claimCommission()` - (File: contracts/bindings/kip247/GaslessSwapRouter.go)

### Summary
`GaslessSwapRouter` (bound in `contracts/bindings/kip247/GaslessSwapRouter.go`) exposes an unrestricted `receive()` payable function [1](#0-0)  alongside a `claimCommission()` method whose decompiled bytecode sweeps the contract's entire native balance (`SELFBALANCE`/`0x47`) to the owner and emits `CommissionClaimed` [2](#0-1) [3](#0-2) . Unlike `TreasuryRebalance.sol`, which explicitly reverts any incoming payment via a hardened fallback (`fallback() external payable { revert(...); }`) [4](#0-3) , `GaslessSwapRouter` has no equivalent safeguard: it accepts arbitrary native KAIA into its balance without tracking whose funds they are.

### Finding Description
The `GaslessSwapRouter` contract is part of Kaia's gasless-transaction module (`kaiax/gasless`), used by `SwapForGas` to let users swap ERC-20 tokens for native KAIA to repay a fee-delegation proposer [5](#0-4) . The contract declares an open `receive()` function that accepts any KAIA transfer from any sender, with no source validation and no attribution bookkeeping (no mapping of "who sent what") [6](#0-5) .

Separately, `claimCommission()` is implemented (per the visible init/runtime bytecode) to read `address(this).balance` in full and forward it to the owner via a low-level `call`, then emit `CommissionClaimed(amount)` [2](#0-1) . Because the contract does not separate "legitimate accrued commission" balance from "residual/accidental KAIA balance," any KAIA that lands in the contract — whether from an accidental EOA transfer, a stuck `swapForGas` residual, or a `SwappedForGas` settlement not yet forwarded — becomes indistinguishable native balance that the owner can claim in full on the next `claimCommission()` call.

This mirrors the reported bug class (missing fallback rejection allowing Ether to become "stuck"/misappropriated), but is worse here because there is an owner-privileged sweep path that can consume such funds rather than the funds merely sitting idle. Other Kaia system contracts explicitly reject unexpected value transfers with a reverting fallback (e.g., `TreasuryRebalance.sol`) or, for contracts intentionally holding funds like `CnStakingV4`/`ERC1967Proxy`, define `receive()` deliberately for expected value flows tied to specific accounted operations [7](#0-6) . `GaslessSwapRouter` instead combines an open payable receiver with an unrestricted "sweep entire balance" admin function and no rejection/refund path for unrelated transfers.

### Impact Explanation
Any unprivileged party (an ordinary transaction sender or the gasless-swap counterparties) that accidentally sends KAIA directly to the `GaslessSwapRouter` contract address has no path to recovery: the funds merge into the general balance and can be unilaterally withdrawn by the contract owner as "commission" via `claimCommission()`. This is a concrete value-misappropriation path — reachable by any public sender issuing a plain value transfer to the router address, and by the owner (a fee-delegation counterparty role within the gasless flow) draining it. It does not require any special privilege from the victim, satisfying the "unauthorized value movement" bar for this analog class.

### Likelihood Explanation
Likelihood is moderate: a user or bot sending KAIA to a known, published contract address (the swap router) by mistake is a realistic real-world occurrence (this is exactly the scenario the original StableSwap_V2 report flags), and the owner sweep function requires no coordination — it is a normal, expected admin call (`claimCommission`) that will incidentally capture any accidental balance the next time it is invoked.

### Recommendation
Add an explicit reject-by-default policy for unsolicited value transfers to `GaslessSwapRouter`: replace or guard the open `receive()` with a non-payable fallback/receive that reverts unless the caller is a recognized internal flow (e.g., only allow value transfers originating from `swapForGas`'s own internal accounting, or track incoming value per-transaction and exclude untracked residual balance from `claimCommission()`'s calculation). Emit an event/log on any rejected transfer as recommended in the original report, and ensure `claimCommission()` only transfers the portion of balance actually accrued as commission (tracked via a state variable updated during `swapForGas`), not `address(this).balance` in full.

### Proof of Concept
1. Deploy/observe `GaslessSwapRouter` at its known on-chain address (constructor takes `_wkaia`) [8](#0-7) .
2. As any unprivileged EOA, send a plain KAIA value transfer (no calldata) to the router address — it succeeds because `receive()` is `payable` and unguarded [1](#0-0) .
3. The owner (or any account with owner privileges under `Ownable`) calls `claimCommission()` [9](#0-8) ; per the bytecode this reads the full `address(this).balance` and forwards it to the owner, including the accidentally-sent KAIA from step 2.
4. The original sender has no recovery mechanism — the accidental transfer is permanently absorbed into owner-claimable commission, confirming stuck/misappropriated value.
