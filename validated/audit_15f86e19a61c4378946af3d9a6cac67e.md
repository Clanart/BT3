### Title
Empty aggregate signatures pass verification - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` accepts an aggregate containing zero signatures when `s = 0`. Because the verifier only requires `Rs.len() == keys_and_challenges.len()` and then checks whether the resulting multi-exponentiation is the identity, an empty `Rs` and empty `keys_and_challenges` reduce verification to `0 * G == identity`. A caller can therefore obtain `true` without any signer key, nonce, message, or Schnorr proof being involved. [1](#0-0) 

### Finding Description
`SchnorrAggregate::read` permits a serialized aggregate whose encoded `Rs` length is zero, then reads only a scalar `s` with no minimum-signature check. [2](#0-1) 

During verification, equal empty input lists satisfy the length check. The loop that would bind each nonce and public key challenge never executes, leaving only the pair `(-s, generator)`. For `s = 0`, that term is the identity, so `multiexp_vartime(&pairs).is_identity()` evaluates to true. [1](#0-0) 

The analogous missing boundary check is that an aggregate must contain at least one signature. `SchnorrAggregator::complete` already treats an empty aggregate as invalid by returning `None`, but this invariant is not enforced on the externally decodable `SchnorrAggregate` verification path. [3](#0-2) 

### Impact Explanation
An unprivileged caller can construct untrusted bytes representing an empty aggregate, deserialize them with `SchnorrAggregate::read`, and cause `verify(dst, &[])` to return true without a signature from any key. Any higher-level protocol that treats a successful aggregate verification as evidence that at least one signature existed accepts a vacuously valid proof. This is an incorrect verifier formula because the aggregate equation permits the empty statement. [2](#0-1) [1](#0-0) 

### Likelihood Explanation
The attack requires no private state, malformed cryptographic point, timing condition, or cooperation from another party. The public deserialization API directly accepts the zero-length aggregate, and the public verifier receives the matching empty `keys_and_challenges` slice. Exploitation depends only on an integration calling `verify` without separately requiring a non-empty signature/key list. [2](#0-1) [4](#0-3) 

### Recommendation
Reject empty aggregates in both `SchnorrAggregate::read` and `SchnorrAggregate::verify`. At minimum, `verify` should return `false` when `keys_and_challenges.is_empty()` or `self.Rs.is_empty()` before evaluating the multi-exponentiation. Enforcing the check during deserialization as well prevents semantically invalid values from being propagated. [2](#0-1) [1](#0-0) 

### Proof of Concept
For any supported `C: Ciphersuite` whose zero scalar has its canonical serialized representation:

```rust
use ciphersuite::group::ff::Field;
use schnorr::SchnorrAggregate;

let aggregate = SchnorrAggregate::<C> {
    Rs: vec![],
    s: C::F::ZERO,
};

assert!(aggregate.verify(b"example aggregation dst", &[]));
```

Equivalently, serialized input can consist of `00 00 00 00` for the `Rs` length followed by the canonical encoding of scalar zero. `read` accepts it, `verify` finds zero nonce/key pairs to check, and the sole `(-ZERO) * G` term is the identity. [2](#0-1) [1](#0-0)

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
