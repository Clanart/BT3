### Title
`SignableTransaction::new` accepts inputs it can never sign for — `multisig` rejects them — mirroring the `payoutFor`/`purchaseBond` inconsistency - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` (the "preview"/planning path) validates structural properties of a spend — non-empty inputs, dust-free payments, sufficient funds, size/weight limits — and returns a `SignableTransaction` reporting a `needed_fee` and a spendable-looking `transaction()`. It never verifies that each supplied `ReceivedOutput` is actually spendable by the threshold keys, i.e. that `p2tr_script_buf((keys + offset).group_key()) == output.script_pubkey`. That check is deferred to `SignableTransaction::multisig` (the "execution" path), which silently returns `None`. This is the same class as the reported bug: a query function green-lights an action that the state-changing function will reject.

### Finding Description
In `send.rs`, `SignableTransaction::new` consumes `Vec<ReceivedOutput>` and performs every feasibility check except ownership/spendability of the inputs:

- It checks `NoInputs`, `NoOutputs`, `DustPayment`, `TooMuchData`, `TooLowFee`, `NotEnoughFunds`, and `TooLargeTransaction` (send.rs:157-243).
- It builds `prevouts` directly from the attacker-influenceable `ReceivedOutput.output` (send.rs:253).

Only later does `multisig` re-derive the output key and compare:

```rust
// networks/bitcoin/src/wallet/send.rs:273-282
pub fn multisig(self, keys: &ThresholdKeys<Secp256k1>) -> Option<TransactionMachine> {
    for i in 0 .. self.tx.input.len() {
      let offset = keys.clone().offset(self.offsets[i]);
      if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
        None?;
      }
      ...
```

`ReceivedOutput` is deserializable from untrusted bytes via `ReceivedOutput::read` (mod.rs:122-134), which performs no consistency check between `offset`, `output.script_pubkey`, and `outpoint`. A `ReceivedOutput` can therefore carry:

1. A `script_pubkey` that does not match `key + offset*G` (or matches an odd-Y point for which `p2tr_script_buf` returns `None`).
2. A fabricated `output.value`, inflating `input_sat` so `NotEnoughFunds` passes while the real prevout pays less — producing a transaction whose committed fee/input amounts are wrong (the sighash commits to `Prevouts::All(&self.tx.prevouts)` at send.rs:375, so an honest signer signs for false prevout values and the resulting transaction is invalid on-chain).

Because `new`/`needed_fee`/`transaction()`/`txid()` all report a viable plan, any caller that relies on them (e.g. a planner deciding a payment can be fulfilled at a fee rate) obtains a false positive; `multisig` then returns `None` and no transaction can be produced — exactly the "view says yes, action reverts" inconsistency, with the addition that the signed transaction, if prevout values were forged but keys consistent, commits to incorrect input amounts under `Prevouts::All`.

### Impact Explanation
An unprivileged party feeding untrusted bytes to `ReceivedOutput::read` can cause the planner to report an output as spendable (nonzero `value()`, accepted by `SignableTransaction::new`) that is not spendable — either because `multisig` rejects it (DoS of the signing plan, analogous to the report's missed-opportunity/delay impact) or because the reported prevout value is fictitious, yielding a signed transaction committing to amounts that don't exist on-chain. This satisfies the "funds reported received that are not spendable" and inconsistent-state impact classes.

### Likelihood Explanation
Reachable wherever `ReceivedOutput`s are transported/deserialized between components rather than produced exclusively by a local `Scanner::scan_transaction` (which does set `offset` consistently with `script_pubkey`). The moment serialized `ReceivedOutput`s cross a trust boundary — the explicitly in-scope `ReceivedOutput::read` path — `new`'s missing consistency check is triggerable with fully attacker-controlled fields. No timing, collusion, or validator misbehavior required.

### Recommendation
Perform the ownership/spendability check at construction (or deserialization) time rather than at `multisig`:

- In `SignableTransaction::new` (or a verified-constructor on `ReceivedOutput`), require a proof that `output.script_pubkey` equals `p2tr_script_buf(group_key + offset*G)` for the intended keys — or, at minimum, return an error from a fallible validation method instead of deferring to `Option` in `multisig`.
- Alternatively, make `ReceivedOutput` unforgeable: only constructible via `Scanner::scan_transaction`, with `ReceivedOutput::read` re-verifying `script_pubkey == p2tr_script_buf(key + offset*G)` for a bound key before yielding the struct.
- Also consider a dust/immaturity check on inputs in `new` so reported plans don't include unspendable or non-standard inputs.

### Proof of Concept
```rust
// Untrusted bytes -> ReceivedOutput::read
let mut bytes = vec![];
bytes.extend(Scalar::ZERO.to_bytes());               // offset = 0 (key + 0*G)
let fake_txout = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_p2tr_tweaked(
    TweakedPublicKey::dangerous_assume_tweaked(attacker_xonly),
  ),                                                  // NOT p2tr(key + 0)
};
bytes.extend(serialize(&fake_txout));
bytes.extend(serialize(&OutPoint::new(real_txid, 0)));

let ro = ReceivedOutput::read(&mut &bytes[..]).unwrap();
assert_eq!(ro.value(), 100_000);                       // reported as spendable funds

// Planning path accepts it: all checks pass, needed_fee reported
let st = SignableTransaction::new(
  vec![ro], &payments, None, None, fee_per_vbyte,
).unwrap();                                            // no error — inconsistency
st.needed_fee(); st.transaction(); st.txid();          // looks viable

// Execution path rejects it
assert!(st.multisig(&keys).is_none());                 // silent None — purchaseBond-style revert
```
The serialized `ReceivedOutput` passes every check in `new` yet can never be signed for, matching the `payoutFor`/`purchaseBond` divergence where the view path omits a constraint enforced only at execution.
