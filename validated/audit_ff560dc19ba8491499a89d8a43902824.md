### Title
Line-selection index desync after diff hunk expansion can silently corrupt partial commits - (File: app/src/ui/diff/text-diff-expansion.ts, app/src/models/diff/diff-selection.ts)

### Summary
The external report describes a broken invariant: an index (`Emission.index`) computed over a **subset** of the domain (staked tokens) is reused to calculate rewards for the **whole** domain (staked + unstaked/treasury tokens), producing silently wrong allocations. The Desktop analog is a structurally identical class of bug: `DiffSelection` stores which lines are "included" for a partial commit as a `Set<number>` of **absolute line indices** computed against a specific diff hunk layout [1](#0-0) . When a diff hunk is expanded (`expandTextDiffHunk`), hunks located after the expansion point are shifted by `numberOfNewDiffLines`, changing what absolute index each underlying diff line occupies, while the previously recorded `divergingLines` selection set is not recomputed against the new layout [2](#0-1) . `formatPatch`, which builds the exact patch applied to the git index for a partial commit, blindly trusts `file.selection.isSelected(absoluteIndex)` against the current (possibly expanded/shifted) hunk indices [3](#0-2) . If the index base used to build the selection state (pre-expansion layout) no longer matches the index base used to evaluate it (post-expansion layout), the resulting patch can include or drop the wrong lines — an analog of "index calculated on the wrong denominator/basis and reused elsewhere."

### Finding Description
`DiffSelection` is an index-based abstraction: it has no notion of what a given index "means," it only remembers which absolute line indices diverge from the default selection state [4](#0-3) . The correctness of the whole partial-commit feature depends on the invariant that the absolute index space used to set selection state is the same index space used later to read it back when generating the patch.

`expandTextDiffHunk` violates this invariant for hunks that come after the expansion point: it recomputes `unifiedDiffStart`/`unifiedDiffEnd` for "following hunks" by adding `numberOfNewDiffLines`, which shifts every line in those hunks to a new absolute index [5](#0-4) . There is a partial reconciliation path (`withSelectableLines`) invoked when the working directory diff is reloaded from git status after a file changes on disk [6](#0-5) , but this only prunes selections for lines that are no longer *selectable* (e.g. turned into context) — it does not detect or correct the case where a previously selected line's underlying content has moved to a different absolute index because of a hunk merge/expansion, and a *different* line has now taken over that old index. In that scenario `isSelected(absoluteIndex)` in `formatPatch`/`applyPatchToIndex` will silently report the wrong line as selected/unselected [7](#0-6) , [8](#0-7) .

This is directly analogous to the reported bug: the `index`/selection state was computed for one basis (a specific hunk layout / staked-token supply) and is later applied against a different basis (an expanded/shifted hunk layout / total token supply) without recalculation, so the attribution of "what belongs to what" becomes wrong.

### Impact Explanation
If an attacker controls the content of a tracked file that the victim is about to partially stage/commit (e.g., a large file in a cloned/fetched repository, or a file touched by a build/generator triggered as part of normal workflow), they can craft content such that expanding a hunk (a routine UI action, e.g. "Load more lines" clicked by the user while reviewing a large diff) causes hunks to merge/shift. If the victim then finishes selecting/deselecting lines and commits only a subset, the final patch produced by `formatPatch`/`applyPatchToIndex` can differ from what the UI displayed as selected — i.e., **silent corruption of what the user commits**, which matches the "Valid Impact" criteria (unauthorized modification of committed content due to attacker-influenced repository state, no local/physical access or malware required).

### Likelihood Explanation
This requires: (1) a file large enough or diffed in a way that triggers hunk expansion/merging (a documented, common UI feature, `DefaultDiffExpansionStep = 20` [9](#0-8) ), and (2) the user performing partial line selection before or after expanding a hunk whose position is later than the expansion point. This is a normal workflow (reviewing large diffs, selectively staging), not requiring unnatural steps. However, I was unable to confirm from the code read so far whether the `side-by-side-diff.tsx` component's `expandHunk`/`onExpandHunk` handlers actually feed the shifted diff back into `onIncludeChanged`/`DiffSelection` in a way that re-syncs indices, or whether they leave the existing `DiffSelection` object entirely untouched against the new hunk layout — this needs direct inspection of `expandHunk` in `app/src/ui/diff/side-by-side-diff.tsx`, which I could not complete due to running out of tool iterations.

### Recommendation
Ensure that any operation which changes hunk boundaries/line-index layout (`expandTextDiffHunk`, `mergeDiffHunks`, `expandWholeTextDiff`) also remaps or invalidates the `DiffSelection`'s `divergingLines` set so that indices always refer to the current layout — analogous to recalculating the reward index against total supply instead of reusing a stale, subset-based index. At minimum, `formatPatch` and `applyPatchToIndex` should validate that the diff passed in matches the exact hunk layout the `DiffSelection` was built against (e.g., via a layout/version fingerprint) before trusting `isSelected()` results, rather than silently trusting index correspondence between two potentially different hunk revisions.

### Proof of Concept
Conceptual PoC (needs confirmation in a live Devin session against `side-by-side-diff.tsx`):
1. Clone/fetch a repository containing a large tracked file with multiple separated change hunks positioned such that expanding one hunk (`DefaultDiffExpansionStep = 20` lines) will merge it with, or push forward, a subsequent hunk (per `shouldMergeWithAdjacent` logic) [10](#0-9) .
2. In Desktop, open the diff for that file, select only lines within the second hunk (population index range depends on original layout) for partial commit, and select "Load more lines" to expand the first hunk.
3. Because the second hunk's `unifiedDiffStart`/`unifiedDiffEnd` shift by `numberOfNewDiffLines` [5](#0-4) , the `DiffSelection`'s previously recorded absolute-index selections now line up with different underlying diff lines.
4. Commit the partial selection; inspect the actual git patch applied via `applyPatchToIndex`/`formatPatch` versus what was visually indicated as selected in the UI before expansion, to confirm the mismatch.
