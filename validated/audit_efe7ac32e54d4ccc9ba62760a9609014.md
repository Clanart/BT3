### Title
Attacker-controlled `WWW-Authenticate` realm header spoofs a git remote as a trusted "GitHub Enterprise" endpoint, triggering GitHub sign-in against the attacker's host - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
GitHub Desktop's credential-helper trampoline classifies an unknown git remote as GitHub, GitHub.com, GitHub Enterprise (`ghe.com`), or "generic" before deciding whether to hand out a stored OAuth token or prompt the user to sign in. One classification path trusts the `wwwauth[]` values that git forwards from the remote server's HTTP `WWW-Authenticate` response header, treating any host that returns `realm="GitHub"` as an "enterprise" GitHub host - even though that value is fully controlled by whoever answers the HTTP request for that remote. This is the same broken-invariant pattern as the report: Desktop assumes a "controlled/legitimate" identity (a GitHub endpoint) can be inferred from attacker-suppliable data (an HTTP response field from an arbitrary remote), and then acts (initiating a sign-in/credential flow) as if that inference were trustworthy.

### Finding Description
`getEndpointKind()` determines how the credential helper responds to a `git credential get/store/erase` request: [1](#0-0) 

Note the loop:
```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
```
The `wwwauth[]` entries in `cred` come from git's credential helper protocol, which git populates from the actual `WWW-Authenticate` HTTP header returned by whatever server answers the request for the configured remote URL [2](#0-1) . That server is entirely under the control of whoever operates the remote (a malicious "git clone"/"add remote" URL, a malicious HTTP proxy, or a man-in-the-middle on a plain HTTP remote) - the same "attacker-supplied object" class the task requires (a git remote/proxy response).

Once `getEndpointKind` returns `'enterprise'` for an attacker's arbitrary host, `getCredential()` uses that classification directly: [3](#0-2) 

Since the attacker's host has never been added as an account, `accounts.some(a => a.endpoint === apiEndpoint)` is false, so Desktop calls `ui.promptForGitHubSignIn(endpoint)` with `endpoint` set to the attacker's own host. This mirrors the report's broken invariant exactly: Desktop assumes that a remote responding like "GitHub" is in fact a GitHub identity it can safely authenticate against, the same way the audited contract assumed an address was controlled identically across chains. The `isDotCom`/`isGHE` checks earlier in the same function use strict hostname equality/suffix checks and are not the weak point [4](#0-3) ; the weak point is specifically the `wwwauth[]`/`realm="GitHub"` heuristic, which relies purely on attacker-controlled response content with no relationship to an actual GitHub-owned hostname.

### Impact Explanation
If a user adds or fetches from a malicious remote (e.g. a spoofed "clone URL" shared via a README, deep link, or fork), the attacker's server can respond with `WWW-Authenticate: Basic realm="GitHub"` to any authenticated git request. This causes Desktop's credential helper to believe the remote is a genuine GitHub Enterprise endpoint and surface a "sign in to GitHub" prompt scoped to the attacker's host. A user who completes that sign-in flow risks authenticating (and potentially exchanging OAuth/device-flow secrets) against an endpoint the attacker controls, which can lead to credential/token exfiltration and an account binding that is not what the user intended - directly matching the class of harm called out as valid (unauthorized OAuth/account binding, credential exfiltration) via an attacker-controlled git remote/proxy response.

### Likelihood Explanation
Medium. It requires the victim to interact with a remote whose HTTP responses are attacker-controlled (a spoofed/malicious clone URL, or an on-path proxy for an HTTP(S) git remote) and to actually complete an ensuing GitHub sign-in prompt. No local access, admin rights, or pre-existing malware is required, and the trigger (setting a benign-looking `WWW-Authenticate` header) requires no unnatural steps from the attacker's side - only that the user perform a normal `fetch`/`clone`/`push` against the attacker's remote, which is within scope as an "attacker controls...git remote/proxy response."

### Recommendation
Do not derive trust/classification of a git endpoint from response content the remote itself supplies (the `wwwauth[]`/`realm=` heuristic). Base the "enterprise" classification only on: (1) hostnames that match an already-registered/known account endpoint, or (2) an explicit, server-verified handshake (e.g., the existing `isGitHubHost()` API probe) that Desktop performs itself rather than trusting a header echoed back by git. If a heuristic based on `WWW-Authenticate` must be kept for UX reasons, it should only ever be used to *offer* an opt-in "does this look like a GitHub Enterprise server?" prompt, never to short-circuit account/credential flows, and the resulting sign-in UI must prominently display the actual raw hostname being authenticated against.

### Proof of Concept
1. Attacker hosts a git-over-HTTP(S) server (or a MITM proxy for a plain-HTTP remote) at `https://evil.example.com/x.git`.
2. Victim adds this as a remote in GitHub Desktop and performs a fetch/pull/push that requires authentication.
3. Git issues an HTTP request; the attacker's server responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this as a `wwwauth[0]=Basic realm="GitHub"` field in the credential-fill request to Desktop's trampoline.
5. `getEndpointKind()` matches `v.includes('realm="GitHub"')` and returns `'enterprise'` for `evil.example.com` [5](#0-4) .
6. `getCredential()` finds no existing account for `evil.example.com` and calls `ui.promptForGitHubSignIn('https://evil.example.com')`, prompting the user to authenticate against the attacker's host as if it were a legitimate GitHub Enterprise server [6](#0-5) .

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

import { exec as git } from 'dugite'

export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}

export const isDotCom = (ep: string) => {
  if (ep === getDotComAPIEndpoint()) {
    return true
  }

  const { hostname } = new URL(ep)
  return hostname === 'api.github.com' || hostname === 'github.com'
}

export const isGist = (ep: string) => {
  const { hostname } = new URL(ep)
  return hostname === 'gist.github.com' || hostname === 'gist.ghe.io'
}

/** Whether or not the given endpoint URI is under the ghe.com domain */
export const isGHE = (ep: string) => new URL(ep).hostname.endsWith('.ghe.com')
