### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-shop request forgery - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` authenticates an inbound webhook solely by validating the raw request body against an HMAC computed with the app's shared secret. The shop identity for the request (`shop_domain`) is read directly from the `X-Shopify-Shop-Domain` header, which is **not part of the HMAC-signed data**. Any party able to obtain one validly-signed webhook body/HMAC pair for their own shop can replay that exact body+signature to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. Verification still passes because the header is never checked against, or bound into, the signed payload.

### Finding Description
`hmac_valid?` computes `OpenSSL::HMAC.digest(digest, secret, data)` only over `request.raw_post` and compares it to the `HTTP_X_SHOPIFY_HMAC_SHA256` header: [1](#0-0) 

`WebhookVerification#verify_request` gates the controller action purely on that check, and the separate `shop_domain` accessor simply trusts the unauthenticated header: [2](#0-1) 

Because the app's client secret is shared across every shop that has the app installed (it is not per-shop), any merchant who has installed the app can obtain a legitimately-signed webhook (body + valid `X-Shopify-Hmac-Sha256`) for events in their *own* store — e.g. by registering an app-scoped webhook subscription pointing at a server they control. They can then take that exact `raw_post`/HMAC pair and POST it directly to the target app's public webhook receiver endpoint (`ShopifyApp::WebhooksController#receive`, mounted at a predictable path), substituting the `X-Shopify-Shop-Domain` header value with a victim shop's domain: [3](#0-2) 

`hmac_valid?` still returns true (the body/secret pair is genuine), so the forged shop-domain association is accepted and passed downstream into the job pipeline. This mirrors the report's root cause exactly: a caller-supplied identifier (`_aToken` in the report, `X-Shopify-Shop-Domain` here) is used to determine *whose* resource/record is affected, without validating that identifier against the entity that was actually cryptographically authenticated (the underlying reserve in the report; the shop that actually produced the signed payload here).

The gem's own generator templates propagate this unauthenticated value straight into background jobs keyed by `shop_domain`, e.g.: [4](#0-3) 

and the doc explicitly states the job is queued with `shop_domain` and the webhook body as the two parameters, with `shop_domain` sourced from the header path shown above.

### Impact Explanation
An attacker (any merchant who has installed the app, i.e. an "unrelated merchant") can inject forged webhook events attributed to a victim shop's domain into the app's processing pipeline, without possessing the victim's own webhook secret or session — because the secret is shared, not per-shop. Depending on what the app's webhook jobs do with `shop_domain` (e.g. `app/uninstalled` cleanup, `shop/redact`, `customers/redact`, or app-specific business logic keyed by shop), this can lead to:
- Cross-shop data corruption/injection (writing attacker-controlled payload data under a victim shop's identity).
- Triggering privileged shop-scoped side effects (e.g. uninstall/redaction flows, session/session-data destruction) for a shop the attacker does not own.
- Denial of service / data integrity issues for the victim merchant.

### Likelihood Explanation
Moderate-to-high for apps that mount `ShopifyApp::WebhookVerification`/`WebhooksController` at a discoverable, static path (the webhook path is typically fixed and often documented/predictable), combined with the fact that the app's HMAC secret is shared across all installations. The prerequisite — becoming a merchant who installs the app and can obtain one genuinely-signed webhook — is low-effort, since any developer can install most public/development apps.

### Recommendation
- Short term: Do not trust the `X-Shopify-Shop-Domain` header as an identity source for anything security-relevant. Cross-check it against the shop bound to the currently-authenticated session/token, or against a shop identifier embedded in and covered by the HMAC-signed payload (e.g. use `ShopifyAPI::Webhooks::Registry`/`Request` parsing that ties shop identity to the verified webhook subscription, and reject requests where the header shop doesn't match the webhook's registered/expected shop).
- Additionally, mitigate replay by validating the `X-Shopify-Webhook-Id`/timestamp uniqueness so a captured valid body+HMAC cannot be resent later for a different header context.
- Long term: Add unit/integration tests that simulate a same-secret cross-shop replay (valid HMAC, mismatched shop-domain header) and assert the request is rejected.

### Proof of Concept
1. Attacker installs the target app on shop `attacker.myshopify.com` (or on any shop they control) and, using their store's Admin API access token, registers a webhook subscription (e.g. `orders/create`) pointing at a server they control, receiving genuinely `X-Shopify-Hmac-Sha256`-signed payloads that use the app's shared client secret.
2. Attacker captures one such request's raw body and its valid `X-Shopify-Hmac-Sha256` value.
3. Attacker sends this exact body + HMAC header directly to the target app's real webhook endpoint (e.g. `POST /webhooks/orders_create`), but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` → `hmac_valid?(request.raw_post)` succeeds (body/secret pair is genuine), so the request is accepted; `shop_domain` resolves to `victim-shop.myshopify.com` and is forwarded to the app's webhook job with the attacker's payload, as shown in the documented job invocation pattern: [4](#0-3)

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```ruby
module ShopifyApp
  class WebhooksController < ActionController::Base
    include ShopifyApp::WebhookVerification

    def receive
      params.permit!

        ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h),
      )

    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
```
