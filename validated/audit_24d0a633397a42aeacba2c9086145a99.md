This confirms the vulnerability exactly as described. `mWOMSVBaseRewarder._calExpireForfeit` at [1](#0-0)  sets `rewardableAmount = _amount` unconditionally, never calling `mWOMSV.getRewardablePercentWAD()`, so `forfeitAmount` is always `_amount - _amount = 0`. This contrasts with the parallel `vlMGPBaseRewarder._calExpireForfeit` at [2](#0-1)  which correctly reads `vlMGP.getRewardablePercentWAD(_account)` and applies the pro-rated percentage — confirming the mWOMSV version is a broken/incomplete copy that dropped the pro-ration logic.

The reachable path is real: `getReward`/`getRewards` are `onlyMasterMagpie`-gated [3](#0-2) , but any unprivileged user can trigger them via `MasterMagpie.multiclaim`, and `_sendReward` calls `_calExpireForfeit` to determine forfeiture [4](#0-3) . `mWomSV.getRewardablePercentWAD` at [5](#0-4)  exists and correctly pro-rates based on `startUnlock`/cooldown state, but it is simply never invoked from the mWOMSV rewarder.

### Title
mWOMSVBaseRewarder never applies pro-rated forfeiture, allowing users in cooldown to claim 100% of bonus rewards - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` unconditionally and never queries `mWOMSV.getRewardablePercentWAD(_account)`, so `forfeitAmount` is always zero regardless of a user's lock/cooldown state. Any user who has started `startUnlock()` (partially or fully in cooldown) can call `getReward()`/`getRewards()` through `MasterMagpie.multiclaim` and receive 100% of accrued bonus rewards instead of the pro-rated share, with nothing forfeited back to remaining lockers.

### Finding Description
The sibling contract `vlMGPBaseRewarder._calExpireForfeit` correctly computes `rewardableAmount = _amount * vlMGP.getRewardablePercentWAD(_account) / 1e18` [2](#0-1) , showing the intended design: users who have moved tokens into cooldown (`startUnlock`) should only be rewarded proportionally to their still-fully-locked share plus time-decayed cooldown share, as computed by `getRewardablePercentWAD` in `mWomSV.sol` [5](#0-4) .

In `mWOMSVBaseRewarder.sol`, the equivalent function omits this calculation entirely:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    ...
}
``` [1](#0-0) 

Since `rewardableAmount` always equals `_amount`, `forfeitAmount` is always `0`, and `_sendReward` sends the user's full `userRewards[...]` balance regardless of their cooldown status [4](#0-3) .

Exploit flow: attacker calls `mWomSV.lock()` to obtain `mWomSV` balance credited in `MasterMagpie`, then calls `startUnlock(amount)` to move all or part of the balance into a cooldown slot [6](#0-5) . Their `balanceOf()` as tracked by `mWOMSVBaseRewarder` (via `MasterMagpie.stakingInfo`) still includes the cooldown amount, so rewards continue to accrue via `rewardPerToken`. When the rewarder's manager calls `queueNewRewards`, accrued rewards increase. The attacker (or anyone) then triggers `getReward`/`getRewards` via `MasterMagpie.multiclaim`, and `_sendReward`/`_calExpireForfeit` grants 100% of `earned()` with zero forfeiture, even though the user is fully or partially in cooldown and should only receive the pro-rated `getRewardablePercentWAD` share. No modifier, `nonReentrant` guard, or reward-index update prevents this since the bug is a pure logic/calculation omission, not an access-control or reentrancy issue.

### Impact Explanation
This is theft of unclaimed yield: bonus rewards that should be forfeited from a partially/fully-cooling-down user and redistributed to remaining fully-locked stakers (via `_queueNewRewardsWithoutTransfer`) are instead paid out in full to the departing user. This directly harms remaining lockers who lose their expected pro-rata share of forfeited rewards, and breaks the Conservation invariant intended by the protocol's design (as evidenced by the correct implementation existing in the parallel `vlMGPBaseRewarder` contract).

### Likelihood Explanation
High likelihood and trivially repeatable: it requires no special capital beyond acquiring mWOM to lock, no privileged role, and no complex conditions — simply lock, call `startUnlock()` for any nonzero amount, wait for rewards to accrue, and call `getReward`/`getRewards` through `MasterMagpie`. This can be repeated by any/every user with a cooldown slot, systematically draining the pro-ration mechanism's intended protective effect for the entire pool.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`: compute `rewardableAmount = _amount * mWOMSV.getRewardablePercentWAD(_account) / 1e18` instead of `rewardableAmount = _amount`.

### Proof of Concept
Foundry test outline:
1. Deploy `mWomSV`, `MasterMagpie`, `mWOMSVBaseRewarder`, and a reward token; register rewarder in `MasterMagpie`.
2. User A calls `mWOM.approve` + `mWomSV.lock(1000e18)`, crediting 1000e18 mWomSV in `MasterMagpie`.
3. User A calls `mWomSV.startUnlock(1000e18)` (moves 100% into cooldown; `getRewardablePercentWAD` should return < 1e18 since fully in cooldown and not yet past `endTime`).
4. Manager calls `mWOMSVBaseRewarder.queueNewRewards(rewardAmount, rewardToken)`.
5. Before `endTime`, User A (or via `MasterMagpie.multiclaim`) calls `getReward(userA, userA)`.
6. Assert: `IERC20(rewardToken).balanceOf(userA)` equals full `earned(userA, rewardToken)` computed pre-claim, rather than `earned() * mWomSV.getRewardablePercentWAD(userA) / 1e18`, proving zero forfeiture occurred despite the user being fully in cooldown. Compare against `vlMGPBaseRewarder` behavior under an analogous setup, where forfeiture is correctly non-zero.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
