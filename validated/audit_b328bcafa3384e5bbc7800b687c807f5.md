### Title
Attacker-controlled `n` in `ThresholdKeys::read` forces disproportionate heap allocation before any input validation - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a `u16` `n` from untrusted bytes and immediately calls `Vec::with_capacity(usize::from(n))` when the interpolation tag is `0` (`Interpolation::Constant`). A ~10-byte input therefore forces an allocation proportional to 65535 field elements (≈2–3.7 MB depending on the curve), mirroring CVE-2021-35517's small-input/large-allocation DoS class.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, and `i` as raw `u16`s from the reader (lines 591–602). `n` is not validated until `ThresholdParams::new` is called at the very end (line 626). Before that, when the interpolation byte is `0`, the code executes:

```rust
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
})
``` [1](#0-0) 

`Vec::with_capacity(n)` commits `n * size_of::<C::F>()` bytes of heap based solely on two attacker-supplied bytes, regardless of how much data actually follows. With `n = 0xFFFF`, each ~11-byte prefix (4-byte ID len + ID + 6 bytes of params + 1 tag byte) forces allocation of 65535 scalars — ≈2.1 MB for a 32-byte field, ≈3.7 MB for ed448's 56-byte scalar. The subsequent `read_F` loop fails on EOF, but the oversized allocation is transiently committed per call; an unprivileged peer repeatedly feeding such inputs to a service that deserializes `ThresholdKeys` (the listed `ThresholdKeys::read` entry point) amplifies a trivial bandwidth spend into large memory churn/pressure.

Note `ThresholdParams::new(t, n, i)` (lines 166–179) would reject `t > n`/invalid `i`, but it is only invoked *after* the allocation and reads, so it does not gate the allocation.

### Impact Explanation
A remote party able to submit serialized `ThresholdKeys` bytes (key-exchange/reshare flows, coordinator RPCs that deserialize threshold keys) can force each request to allocate megabytes while sending only bytes, enabling memory-exhaustion denial of service against the node — the same impact class as CVE-2021-35517, where a tiny archive forces Compress to allocate unbounded memory.

### Likelihood Explanation
Exploitation requires the deployment to call `ThresholdKeys::read` on unauthenticated/untrusted bytes, which is the documented public deserialization API. No key material, collusion, or protocol privilege is needed — only the ability to deliver ~11 crafted bytes repeatedly. No invalid proof or signature is needed; the OOM pressure occurs purely at parse time.

### Recommendation
Cap the pre-allocation: replace `Vec::with_capacity(usize::from(n))` with either no pre-allocation (push-bounded-by-input growth), or validate `n`/`t`/`i` against sane bounds via `ThresholdParams::new` *before* the match arm, and/or use `reader.take(limit)`-style reading so allocation can never exceed bytes actually supplied. At minimum, order the reads so capacity is bounded by observed input length rather than the declared field.

### Proof of Concept
```rust
// Constructed bytes (conceptual), C = any in-scope Ciphersuite:
//   [u32 LE: C::ID.len()] || C::ID || t=1 || n=0xFFFF || i=1 || tag=0
// Only ~11 bytes after the header; reaching the interpolation arm calls
// Vec::with_capacity(65535) => ~2-3.7 MB committed per call.
let mut bytes = vec![];
bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(1u16.to_le_bytes());      // t
bytes.extend(0xFFFFu16.to_le_bytes()); // n
bytes.extend(1u16.to_le_bytes());      // i
bytes.push(0u8);                       // Interpolation::Constant tag
// ThresholdKeys::<C>::read(&mut bytes.as_slice()) allocates ~n*sizeof(F)
// before failing on read_F EOF.
```
