### Analysis

The concern in the question is real as a mathematical observation: `RecoverPolynomialCoefficients` in `internal/erasure_code/erasure_code.go` performs the Reed–Solomon-style recovery and then unconditionally truncates:

```go
polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]
return polyCoeff, nil
``` [1](#0-0) 

without ever checking that `cosetQuotientEval[dr.numScalarsInDataWord:]` is all-zero. This is correct-by-construction *only* when the input data is truly evaluations of some degree-<4096 polynomial at the non-erased points; for adversarial/inconsistent cell data this is not guaranteed.

However, this does **not** constitute a valid, in-scope finding for this repo, for several reasons:

1. **`RecoverCellsAndComputeKZGProofs(cellIDs, cells, ...)` takes no commitment argument at all** [2](#0-1) . There is nothing for the function to verify the cells against. It is documented/designed as a pure erasure-decoding routine, to be used only on cells that have *already* been verified via `VerifyCellKZGProofBatch` against a commitment as a separate protocol step. This matches the c-kzg / consensus-spec API contract exactly (`recover_cells_and_kzg_proofs` also has no commitment parameter). So there is no way for this function to "reject" inconsistent cells that c-kzg would reject — c-kzg's `recover_cells_and_kzg_proofs` has the identical contract and the identical blind truncation behavior (it performs the same FFT-based erasure decoding without a "check upper coefficients are zero" step, since the spec assumes pre-validated inputs).

2. Consequently, feeding inconsistent cells into `RecoverCellsAndComputeKZGProofs` produces a deterministic function of the algorithm as specified — both this Go implementation and c-kzg/consensus-spec would compute the exact same coset-FFT-based quotient and truncate it the same way, given the same field arithmetic. There is no client-split: nothing here is "accepted here / rejected there" or "different output for the same input" relative to the spec, because the *spec itself* defines this exact truncation behavior with no additional consistency check.

3. The test suite (`consensus_specs_test.go` `TestRecoverCellsAndKZGProofs`) validates outputs byte-for-byte against official test vectors generated from c-kzg [3](#0-2) , and no such "inconsistent cells produce a divergent result" test vector exists in the official spec's own test suite, because this is expected, specified behavior, not an implementation bug.

4. The stated invariant ("recovered polynomial has degree < ScalarsPerBlob, else an error") is not actually part of the function's contract — the function's contract is "given ≥50% honestly-generated cells (already verified elsewhere), recover the rest," not "detect and reject arbitrary attacker-chosen cell values." Rejecting the premise that such a check is missing-and-required is exactly what the `Reject anything requiring ... a client developer wiring the library wrongly` and `theoretical findings` exclusions in the rules cover — using this function directly on unverified attacker cells without a prior proof-verification step is a misuse of the API, not a vulnerability in it.

func (ctx *Context) RecoverCellsAndComputeKZGProofs(cellIDs []uint64, cells []*Cell, numGoRoutines int) ([CellsPerExtBlob]*Cell, [CellsPerExtBlob]KZGProof, error) {
