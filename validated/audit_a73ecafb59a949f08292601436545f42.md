### Title
Committed symlinks let a malicious repo redirect "Open File"/"Reveal in Finder"/"Open in External Editor" actions outside the repository - (File: app/src/lib/app-shell.ts)

### Summary
GitHub Desktop already contains a dedicated safeguard, `resolveWithin()`, whose explicit purpose is to reject any repository-relative path that — once symlinks are resolved via `realpath` — escapes the repository root [1](#0-0) . This guard is used for deep-link file opens and for the AI conflict-resolution file reader [2](#0-1) [3](#0-2) . However, the much more commonly used code path — the context-menu actions "Open in External Editor", "Open with Default Program", and "Reveal in Finder/Explorer" on files in Changes, History, Pull Request diffs, and Merge-conflict resolution — never calls `resolveWithin`. They instead build the target path with a bare `Path.join(repository.path, file.path)` and hand it straight to Electron's `shell`, exactly the same "broken invariant enforced on one path but not another" pattern as the FighterFarm transfer bug (a restriction implemented via `_ableToTransfer()` on some functions but missing on the inherited `safeTransferFrom(...,data)`).

### Finding Description
`revealInFileManager()` computes the full path with plain `Path.join` and immediately calls `shell.showItemInFolder`, with no symlink/traversal check: [4](#0-3) 

The same unguarded pattern appears at every other file-open call site:
- Changes list context menu ("Open in External Editor"/"Reveal in Finder"/"Open with Default Program") [5](#0-4) [6](#0-5) 
- Commit history file context menu [7](#0-6) 
- Pull request file list context menu [8](#0-7) 
- Merge/rebase conflict resolution UI [9](#0-8) [10](#0-9) 
- `openFile()`, which passes the raw path to `shell.openExternal('file://...')` [11](#0-10) 
- `launchExternalEditor`/`launchCustomExternalEditor`, which `spawn` the editor binary with the raw path as an argument [12](#0-11) 

Git tracks symlinks as first-class blob objects (mode `120000`) and checks them out as real OS symlinks on macOS/Linux (and on Windows when symlink support is enabled). A malicious/compromised repository can therefore commit a tracked symlink such as `notes.txt -> ../../../../../.ssh/id_rsa` or `notes.txt -> /etc/passwd`. After the victim clones/fetches/checks out this repository, `git status`/commit history will list `notes.txt` as a normal repository-relative path. None of the guards above resolve the real, symlink-followed location before acting — they only check the *unresolved* `Path.join` string. The `resolveWithin` helper exists precisely to close this gap (it calls `realpath` and verifies the result still starts with the real, resolved repo root) [13](#0-12) , but it is applied to only two entry points in the codebase (`dispatcher.ts`'s `openRepositoryFromUrl` and `copilot-conflict-context.ts`), not to the interactive file-open/reveal/edit actions.

### Impact Explanation
When the victim right-clicks the attacker-controlled file entry and chooses "Open in External Editor," "Open with Default Program," or "Reveal in Finder/Explorer," GitHub Desktop resolves the symlink transparently through the OS/editor and reveals, opens, or (depending on the editor/program) allows editing of an arbitrary file outside the repository working directory — e.g., private SSH keys, shell config, other repositories' files, or OS files. This is a file-read/disclosure and potential silent-corruption primitive fully attacker-controlled via the contents of a fetched repository, matching the "attacker controls a cloned/fetched repository ... result is file write or read outside the repo" impact category. If the resolved target is itself an editable document that the default program can save back to (e.g., a text editor), the user could also unknowingly overwrite content outside the repo.

### Likelihood Explanation
This does not require local/physical access, admin rights, prior malware, or leaked credentials — only that the victim opens/clones a hostile repository (a normal desktop-app trust boundary: fetching/cloning third-party repos is a core supported workflow) and performs a completely ordinary, expected action (right-click → "Open in External Editor"/"Reveal in Finder"/"Open with Default Program" on a listed changed/committed file, something users routinely do to inspect diffs). Git checking out tracked symlinks is default behavior on macOS/Linux. The codebase's own existing `resolveWithin` guard and its accompanying tests (`clone-path-safety-test.ts`, `path-test.ts`) demonstrate the maintainers are already aware of and actively defending against exactly this symlink-escape class in other locations, but the coverage is incomplete.

### Recommendation
Route every file path derived from repository-relative entries (Changes, History, Pull Request diffs, conflict resolution UI) through `resolveWithin`/`resolveWithinPosix` before calling `shell.showItemInFolder`, `shell.openExternal`, `shell.openPath`, or spawning an external editor. If resolution fails (returns `null`), refuse the action and surface an error, mirroring the pattern already used in `copilot-conflict-context.ts` and `dispatcher.ts`'s `openRepositoryFromUrl`. Centralize this check inside `revealInFileManager()`, `openFile()`, and `_openInExternalEditor()`/`launchExternalEditor` so all current and future call sites are protected automatically instead of relying on each UI call site to remember to validate.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink, e.g.:
   ```
   git symlink-add: notes.txt -> ../../../../../../.ssh/id_rsa   (git mode 120000)
   git add notes.txt && git commit -m "add notes"
   ```
2. Victim clones this repository with GitHub Desktop, or the attacker gets it merged/fetched into an existing repo the victim has open.
3. Victim opens the "Changes"/"History" tab and sees `notes.txt` listed as a normal file.
4. Victim right-clicks `notes.txt` and selects "Reveal in Finder" or "Open in External Editor."
5. `Path.join(repository.path, 'notes.txt')` resolves at the OS level through the symlink to the victim's `~/.ssh/id_rsa`, which is now shown in Finder/opened in the configured editor — disclosing (or, if the editor allows saving, corrupting) a file entirely outside the repository, with no `resolveWithin`/`realpath` check ever performed by `revealInFileManager()` [14](#0-13)  or `openFile()` [15](#0-14) .

Note: I was not able to execute this against a running Desktop build (no filesystem/terminal access in this environment); the finding is based on static code review of the exact call sites shown above and the documented purpose of `resolveWithin`. Confirming exact OS-level behavior (e.g., interaction with `core.symlinks`, macOS Gatekeeper prompts for `shell.openPath` on certain file types) would benefit from dynamic testing in a live Desktop session.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
```

```typescript
/**
 * Open a given file or folder in the desired custom external editor.
 *
 * @param fullPath A folder or file path to pass as an argument when launching the editor.
 * @param customEditor The external editor to launch.
 */
export const launchCustomExternalEditor = (
  fullPath: string,
  customEditor: ICustomIntegration
) => {
  const argv = parseCustomIntegrationArguments(customEditor.arguments)

  // Replace instances of RepoPathArgument with fullPath in customEditor.arguments
  const args = expandTargetPathArgument(argv, fullPath)

  // In macOS we can use `open` if it's an app (i.e. if we have a bundleID),
  // which will open the right executable file for us, we only need the path
  // to the editor .app folder.
  const spawnAsDarwinApp = __DARWIN__ && customEditor.bundleID !== undefined
  const editorName = `custom editor at path '${customEditor.path}'`

  return launchEditor(customEditor.path, args, editorName, spawnAsDarwinApp)
}
```
