### Title
`updateRemoteUrl` rewrites the local git remote to an attacker-controlled host from an unvalidated GitHub API `clone_url` field - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
Analogous to the Chainlink oracle bug (blindly trusting an external price feed value with no sanity/bounds check before using it), `updateRemoteUrl` blindly trusts the `clone_url` field returned by the GitHub API for a repository and rewrites the user's local `origin` remote to that URL as soon as it differs from the current remote — without ever checking that the new URL's **hostname** matches a trusted endpoint (`github.com` / the configured GHE host). The only checks performed are protocol equality and "did the user manually change the remote", neither of which constrain the destination host.

### Finding Description
`updateRemoteUrl` computes: [1](#0-0) 

- `protocolsMatch` only compares the URL *scheme* (`https:` vs `https:`), not host.
- `remoteUrlUnchanged` only verifies the user hasn't manually repointed the remote away from the previously-known GitHub clone URL.
- `urlsMatch` is expected to be `false` precisely so that legitimate repository renames/transfers propagate to the local remote.

None of these three conditions validate that the **hostname** of the new `apiRepo.clone_url` matches the hostname of the existing remote / the account's endpoint: [2](#0-1) 

If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, Desktop calls `gitStore.setRemoteURL(...)` with the attacker-supplied URL, silently rewriting `origin` — this is confirmed by the test suite, which explicitly validates that the remote is rewritten purely because "the github url changes", with no host allow-list assertion: [3](#0-2) 

The comparison helper `urlMatchesRemote` only returns `false`/`true` for match/no-match — it is used here purely as a "did anything change" signal, not as a trust boundary: [4](#0-3) 

This is the same class of bug as the oracle report: a value obtained from an external, potentially adversarial source (`AggregatorV3Interface.latestRoundData()` ↔ GitHub API `repos/{owner}/{name}` response `clone_url`) is consumed and acted upon without a bounds/allow-list check (`minPrice`/`maxPrice` ↔ "is this still the expected host"), so an out-of-range/malicious value silently propagates into a security-relevant sink (oracle price feed ↔ the local git remote used for future fetch/push).

### Impact Explanation
If the `clone_url` returned by the GitHub API for a repository can be attacker-influenced — e.g. via a compromised or malicious GitHub Enterprise Server, a network-positioned attacker/proxy able to tamper with the unauthenticated portions of API responses, or a GHE admin-controlled endpoint the victim has added as an account — Desktop will silently repoint the user's `origin` remote to an attacker-chosen host that merely shares the same URL scheme. Consequences:
- Future `git push` operations from the user silently go to the attacker's server, exfiltrating proprietary source code.
- Future `git fetch`/`pull` bring in attacker-controlled history/content that the user may merge or check out, risking downstream code execution in build/dev tooling.
- This is a silent corruption of what the user pushes/fetches — no prompt, no diff shown, no confirmation dialog is present in this code path.

### Likelihood Explanation
The trigger only requires the attacker to control (or MITM) one API response field (`clone_url`) for a repository the user already has connected to a `GitHubRepository` record, while the user has not manually customized their remote URL. This matches the report's allowed attacker model ("attacker controls ... a GitHub API object ... or a git remote/proxy response") and requires no local access, no admin rights, and no unnatural user steps — the rewrite happens automatically as part of routine repository metadata refresh.

### Recommendation
Add an explicit hostname/allow-list check before accepting `apiRepo.clone_url` as an update target: the new URL's hostname must equal the hostname of the account's API endpoint (or `github.com`) that the `GitHubRepository` was already associated with. Reject (or require explicit user confirmation for) any `clone_url` whose hostname differs from the previously trusted host, even if protocol and "unchanged" heuristics pass — mirroring the recommended Chainlink fix of enforcing bounds (`minPrice`/`maxPrice`) rather than accepting any returned value at face value.

### Proof of Concept
Using the existing test harness pattern in `app/test/unit/stores/updates/update-remote-url-test.ts`:
1. Set up a repository whose `origin` remote is `https://github.com/my-user/my-repo`, matching `gitHubRepository.cloneURL` (so `remoteUrlUnchanged === true`).
2. Simulate an API response (attacker-controlled/MITM'd) where `apiRepo.clone_url = 'https://evil.example.com/my-user/my-repo'` (same scheme, different host).
3. Call `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)`.
4. Observe `gitStore.currentRemote.url` is now `https://evil.example.com/my-user/my-repo` — no host validation blocked it, matching the behavior demonstrated by the existing "updates the repository's remote url when the github url changes" test but with a hostile host substituted for the legitimate `github.com` one. export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
