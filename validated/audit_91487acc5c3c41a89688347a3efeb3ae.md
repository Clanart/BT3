## Analysis

Comparing the four `argv` builders in `app/src/lib/git/checkout.ts`:

**Path-based functions correctly place `--` before the tainted argument:**
```ts
// checkoutPaths
['checkout', 'HEAD', '--', ...paths]
// checkoutConflictedFile
['checkout', `--${resolution}`, '--', file.path]
``` [1](#0-0) 

**Ref-based functions do not:**
```ts
async function getBranchCheckoutArgs(branch: Branch) {
  return [
    branch.name,
    ...(branch.type === BranchType.Remote
      ? ['-b', branch.nameWithoutRemote]
      : []),
    '--',
  ]
}
``` [2](#0-1) 

`checkoutBranch` assembles `['checkout', branch.name, '-b', nameWithoutRemote, '--']` — the `--` end-of-options marker trails the tainted `branch.name`/`nameWithoutRemote` tokens instead of preceding them. [3](#0-2) 

`checkoutCommit` has no `--` guard at all: `['checkout', ...progressArgs, commit.sha]`. [4](#0-3) 

So the answer to the literal question is **yes**: `checkoutBranch` and `checkoutCommit` never place `--` before the variable ref token, while `checkoutPaths` and `checkoutConflictedFile` do place it before the variable path token. A `branch.name` beginning with `-` (e.g. `-b`, `--orphan`, `--detach`) sits in argv **before** any `--` separator, so `git`'s option parser sees it as a flag candidate rather than a literal ref.

## Caveats / uncertainty

I could not fully verify inside this environment whether Desktop applies any ref-name sanitization before a fetched/remote branch reaches `checkoutBranch` (I located `app/src/lib/sanitize-ref-name.ts` and validation helpers in `app/src/lib/git/branch.ts` / `for-each-ref.ts` but did not have remaining iterations to trace whether those are applied to remote-tracking branch names surfaced from `git for-each-ref`/`packed-refs`, as opposed to only to user-typed new-branch names). Git's own `check-ref-format` rules do not forbid a ref name from starting with `-`, so a malicious repository can legitimately contain a ref like `refs/heads/-orphan` or `refs/remotes/origin/-b` in its `packed-refs`/loose-ref files, which would be enumerated and offered by Desktop's branch list/autocomplete without ever going through `git checkout -b <name>` CLI parsing (where such a name would normally be rejected/quoted). If no sanitization filters this before it reaches `checkoutBranch`, the branch token is attacker-controlled and injectable, since `checkout` accepts flags such as `--orphan`, `--detach`, `-b`, `-B`, `-t`, `--ignore-skip-worktree-bits`, `--recurse-submodules`, etc. Given `git checkout`'s option surface (unlike `clone`/`fetch`, which expose dangerous options like `--upload-pack`), the realistic worst case here is behavior manipulation (e.g. forcing an orphan/detached checkout, unexpected local-branch creation) rather than direct RCE — this maps to the "silent corruption of what the user commits or pushes" impact bucket in scope, not arbitrary code execution.

### Title
Missing `--` end-of-options guard before ref argument in `checkoutBranch`/`checkoutCommit` enables argv-flag injection via malicious branch/commit names - (File: app/src/lib/git/checkout.ts)

### Summary
`getBranchCheckoutArgs` and `checkoutCommit` build `git checkout` argv with the ref token placed before (or with no) `--` separator, unlike `checkoutPaths`/`checkoutConflictedFile`, which correctly place `--` before their variable path argument.

### Finding Description
`getBranchCheckoutArgs` returns `[branch.name, ...(remote ? ['-b', nameWithoutRemote] : []), '--']`, so the final argv for `checkoutBranch` is `['checkout', branch.name, '-b', nameWithoutRemote, '--']` — the tainted tokens precede the separator. `checkoutCommit` omits the separator entirely: `['checkout', ...progressArgs, commit.sha]`. Branch names originate from repository ref data (local/remote branches enumerated for the branches list and autocompletion), which is attacker-influenced repository content; git's ref-name grammar does not prohibit a leading `-`, so a crafted repository can ship a ref whose name is itself a flag string. [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
If such a ref reaches these functions unsanitized, `git checkout`'s own flags (e.g. `--orphan`, `--detach`, `-b`) can be triggered instead of a plain ref checkout, silently altering the resulting working tree/branch state that the user subsequently commits/pushes from. This falls under "silent corruption of what the user commits or pushes" in the valid-impact scope. `git checkout` exposes no flag equivalent to `clone`'s `--upload-pack` remote-command execution vector, so code execution is not directly reachable through this specific sink.

### Likelihood Explanation
Exploitability depends on whether Desktop performs any ref-name filtering/sanitization between reading refs from a cloned/fetched repository and passing `branch.name` into `checkoutBranch`; I was unable to confirm this within the available iterations (see caveats above). Without that confirmation, this should be treated as a plausible but unverified argv-injection surface rather than a confirmed, end-to-end exploit chain.

### Recommendation
Mirror the pattern already used in `checkoutPaths`/`checkoutConflictedFile`: place `--` immediately before the ref token (e.g. `['checkout', ...(progress), '--', branch.name, ...]` and `['checkout', ...(progress), '--', commit.sha]`), and/or validate that ref names do not start with `-` before using them as CLI arguments.

### Proof of Concept
```
checkoutBranch argv (branch.name = "-orphan"):
['checkout', '-orphan', '--']          // '-orphan' precedes '--', parsed as an option token

checkoutCommit argv (commit.sha starting with '-', hypothetical):
['checkout', '-b']                      // no '--' guard at all

checkoutPaths argv (path = "-orphan"):
['checkout', 'HEAD', '--', '-orphan']  // '--' precedes the tainted token, treated literally
```
