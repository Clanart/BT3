### Title
Silent Line-Index Mismatch Between Expanded Diff View and Freshly-Fetched Staging Diff Causes Wrong Lines to be Committed - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
GitHub Desktop lets a user expand hidden context around a hunk in the diff viewer (`expandTextDiffHunk`). Expansion re-numbers the `unifiedDiffStart`/`unifiedDiffEnd` offsets of every hunk that follows the expanded one by adding the number of newly injected context lines. Partial-line selection for staging (`DiffSelection`) is recorded purely as a set of these absolute line indices [1](#0-0) . When the file is actually staged, `applyPatchToIndex` ignores whatever expanded diff is on screen and re-fetches a brand-new, unexpanded diff straight from `git diff` [2](#0-1) , then builds the patch by reinterpreting the stored absolute indices against that unexpanded hunk structure [3](#0-2) . Because the two numbering schemes diverge as soon as any expansion happened, the same integer index can point at two different physical lines, so the patch actually applied to the index/commit can silently differ from what the user visually selected — the same “N small steps ≠ 1 big step” invariant break described in the funding-index report, here manifesting as index-based state that is not renormalized when the underlying structure (diff hunks) is regenerated.

### Finding Description
`expandTextDiffHunk` computes `numberOfNewDiffLines` for the hunk being expanded and then shifts every subsequent hunk's `unifiedDiffStart`/`unifiedDiffEnd` by that amount: [4](#0-3) 

This shift exists **only** in the client-side `ITextDiff` object held by the UI (built up incrementally, one “load more” click — i.e. one `DefaultDiffExpansionStep = 20` — at a time, or all at once via `expandWholeTextDiff`) [5](#0-4) .

When the user then drags to select/deselect lines in the (expanded) diff, `side-by-side-diff.tsx` computes the absolute index from `hunk.unifiedDiffStart` of the currently rendered (expanded) hunk and stores it into `DiffSelection`: [6](#0-5) 

`DiffSelection` itself is a bare set of integers with no notion of which diff object it was computed against [7](#0-6) .

At commit/stage time, `applyPatchToIndex` never uses the expanded diff that produced the selection — it always calls `getWorkingDirectoryDiff` fresh: [8](#0-7) 

`formatPatch` then walks the hunks of this fresh, unexpanded diff and asks `file.selection.isSelected(absoluteIndex)` using `hunk.unifiedDiffStart + lineIndex` computed from the *new*, unshifted numbering: [9](#0-8) 

Because the unexpanded hunks after the expansion point have smaller `unifiedDiffStart` values than the expanded UI diff had, the same stored index number now resolves to a different, earlier line in the real diff. `formatPatch`/`formatPatchToDiscardChanges` will therefore include or exclude the wrong add/delete line when generating the unified-diff text fed to `git apply --cached` [10](#0-9) . `git apply` has no way to detect this — it just applies whatever hunk/line content it is handed with `--whitespace=nowarn --unidiff-zero`, so there is no guard rail catching the mismatch.

The `updateChangesWorkingDirectoryDiff` reconciliation logic that runs on refresh only *intersects* the stored diverging-line indices with the new diff's selectable-line set; it does not remap indices to account for a structural renumbering, so a stale index simply survives and is silently reinterpreted against the new hunk layout [11](#0-10) , [12](#0-11) .

### Impact Explanation
This falls under “silent corruption of what the user commits or pushes”: a user can expand context in the diff viewer, select what they believe is a specific line to stage (or exclude), and have Desktop actually stage/commit a different line — potentially re-including a change the user explicitly deselected, or omitting one they wanted included, with no error or warning. Because the mismatch is purely numeric/index-based and the git apply step succeeds without complaint, the corrupted commit looks completely normal to the user.

### Likelihood Explanation
No attacker access or special privileges are required — this is triggered by ordinary application use: expand a hunk’s context (“load more” one or more times) in a file with multiple hunks, then partially select lines in a hunk that follows the expansion point, and commit. The larger the diff and the more expansion steps performed, the larger the accumulated offset and the more likely a selection lands on the wrong physical line. This is a plausible, easily reachable UI workflow rather than an edge case requiring unnatural steps.

### Recommendation
1. Make `DiffSelection` (or the selection-carrying `WorkingDirectoryFileChange`) aware of, and tied to, the exact diff/hunk structure it was computed against, rather than bare absolute integers that are reinterpreted against whatever hunk layout happens to exist later.
2. When `applyPatchToIndex`/`formatPatch` operate on a freshly fetched diff, translate any prior selection recorded against an expanded diff into the new (unexpanded) hunk coordinate space before applying it — e.g., by matching on hunk header ranges/line content instead of raw unified-diff line index — or invalidate/re-derive the selection whenever the underlying diff structure changes due to expansion.
3. Add regression tests asserting that “expand hunk in N small steps then partially select a line in a later hunk” produces an identical staged patch to “select the same logical line without any expansion,” mirroring the “1×10h == 10×1h” path-independence test recommended in the original report.

### Proof of Concept
1. Open a modified file with at least two hunks separated by more than `DefaultDiffExpansionStep` (20) unchanged lines.
2. In the diff viewer, click “Expand” on the first hunk one or more times so that the second hunk’s `unifiedDiffStart` is shifted forward relative to what it would be in a freshly fetched diff (see the offset math in `expandTextDiffHunk`, `app/src/ui/diff/text-diff-expansion.ts:356-387`).
3. Partially select (for staging) a single added/deleted line inside the second hunk. The absolute index recorded into `DiffSelection` is computed from the shifted `unifiedDiffStart` of the expanded diff (`app/src/ui/diff/side-by-side-diff.tsx:1335-1354`).
4. Commit the file. `applyPatchToIndex` re-fetches a fresh, unexpanded diff (`app/src/lib/git/apply.ts:60`) whose second hunk has a smaller `unifiedDiffStart`. `formatPatch` looks up `file.selection.isSelected(absoluteIndex)` against this new numbering (`app/src/lib/patch-formatter.ts:143-145`), resolving the same index to a different line than the one visually selected.
5. Inspect the resulting commit: the staged/committed line differs from the line the user selected in the UI, with no error surfaced by Desktop or `git apply`.
