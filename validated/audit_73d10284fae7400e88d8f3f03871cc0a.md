### Title
Attacker-controlled `t`/`n` in serialized `ThresholdKeys` causes quadratic interpolation loop and CPU exhaustion - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, and `i` directly from untrusted bytes, then `ThresholdKeys::new` computes the group key by calling `Interpolation::interpolation_factor` for every participant in `1..=t`. The Lagrange branch of `interpolation_factor` loops over the entire `included` set (size `t`) per call, making group-key derivation O(t²) in field operations. A crafted serialized `ThresholdKeys` with `t = n = 65535` forces ~4.3 billion scalar multiplications plus 65535 field inversions during deserialization, mirroring the large-loop/CPU-consumption class of CVE-2017-9256.

### Finding Description
`ThresholdKeys::read` reads `t` and `n` as raw `u16`s and then validates them via `ThresholdParams::new`, which only enforces `t <= n` and `t, n != 0`, capping both at 65535 [1](#0-0) [2](#0-1) . It then reads `n` scalars and `n` verification-share points (each a fixed-width read, so the payload only needs ~n·64 bytes) and calls `ThresholdKeys::new` [3](#0-2) .

`ThresholdKeys::new` computes `group_key` as `sum over i in 1..=t of verification_shares[i] * interpolation_factor(i, t)` [4](#0-3) . Under `Interpolation::Lagrange` (a single attacker-controlled byte in the stream), each `interpolation_factor` call iterates all `t` entries of `included`, performing two field multiplications per entry plus a field inversion [5](#0-4) . The same quadratic blow-up recurs on every `view()` call, which computes an interpolation factor per included participant [6](#0-5) .

### Impact Explanation
An unprivileged party who can feed serialized bytes to `ThresholdKeys::read` (e.g., loading keys or reconstituting keys from externally supplied data) causes the host to burn CPU proportional to t². With the maximum `t = n = 65535`, a ~4 MB payload triggers ~4.3·10⁹ field multiplications and 65535 inversions — orders of magnitude more work than the input size — blocking the process handling the deserialization, a remote denial of service matching the CVE-2017-9256 pattern of an attacker-controlled iteration count driving a large loop.

### Likelihood Explanation
Reachability requires the attacker to supply the `ThresholdKeys` bytes. This is medium likelihood: the read API is explicitly in scope for untrusted input, and the payload is small (~4 MB for maximum effect; meaningful slowdowns occur at far smaller `t`, e.g. `t = 8192` needs only ~0.5 MB and yields ~67 million multiplications). No special privileges, collusion, or valid key material are needed — `new` doesn't check shares against the secret, it only counts them.

### Recommendation
Enforce a sane upper bound on `t`/`n` in `ThresholdKeys::read` before the O(t²) work (e.g., a `MAX_PARTICIPANTS` consistent with protocol limits such as `MAX_KEY_SHARES_PER_SET`), and/or compute `group_key` via a single multiexponentiation with precomputed Lagrange coefficients so the cost is O(t) multiexp rather than t independent O(t) interpolation loops.

### Proof of Concept
Serialize a `ThresholdKeys` for a prime-field ciphersuite (e.g., `Ristretto`) with `C::ID` valid, `t = n = 65535`, `i = 1`, interpolation byte `1` (`Lagrange`), one scalar for the secret share, and 65535 arbitrary valid point encodings for the verification shares. Feeding this ~4 MB buffer to `ThresholdKeys::<Ristretto>::read` reaches `ThresholdKeys::new`, which performs 65535 × 65535 field multiplications in `interpolation_factor` plus 65535 inversions, consuming CPU disproportionate to the input size.
