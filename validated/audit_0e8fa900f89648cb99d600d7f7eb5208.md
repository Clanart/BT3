## Analysis

I found a directly analogous bug in the CW20-to-ERC20 pointer contract used to make native ERC20 tokens claimable/transferable from CosmWasm. The Rust pointer's `transfer` and `transfer_from` handlers build a `DelegateCallEvm` message targeting the underlying ERC20's `transfer`/`transferFrom` selector, but never inspect the ABI-encoded `bool` return value that these functions produce. They only construct the message and add it to the response — success is assumed purely from the call not reverting. [1](#0-0) [2](#0-1) 

This mirrors the report's root cause exactly: standard ERC20 functions that return `false` instead of reverting on failure (non-standard/old tokens, paused tokens, blacklists, etc.) will cause the CosmWasm-side message to be treated as successful because only the outer call's revert-or-not status is checked, not the packed `bool` return data.

On the EVM-execution side, `HandleInternalEVMDelegateCall` → `CallEVM` in `x/evm/keeper/evm.go` only treats `res.Err` (an EVM revert/exceptional halt) as failure; a normal `RETURN` of ABI-encoded `false` is passed back as `ReturnData` without any inspection, and the CosmWasm message succeeds: [3](#0-2) [4](#0-3) 

By contrast, the analogous EVM-side pointer (`CW20ERC20Pointer.sol`, which lets ERC20 holders interact with a CW20 token) is implemented defensively: its `_execute` helper explicitly `require(success, "CosmWasm execute failed")`, so a WASM execution failure reverts the whole EVM transaction: [5](#0-4) 

This asymmetry confirms the gap is specifically on the CW-side wrapper for ERC20 tokens (`example/cosmwasm/cw20`), which never checks the packed boolean.

### Title
CW20-pointer-for-ERC20 `transfer`/`transfer_from` ignore ERC20 `bool` return value, allowing silent transfer failures to be reported as success - (`example/cosmwasm/cw20/src/contract.rs`)

### Summary
The CosmWasm CW20 pointer contract that wraps a native ERC20 token (used so CosmWasm contracts/users can move ERC20 balances) issues an `EvmMsg::DelegateCallEvm` carrying the ABI-encoded `transfer`/`transferFrom` calldata for the underlying ERC20, but never checks the returned `bool` from that call. Any ERC20 that returns `false` on failure instead of reverting (non-standard tokens, paused/blacklisting tokens, tokens with post-condition checks) will make the transfer silently no-op while the CW20 pointer's execute message still succeeds.

### Finding Description
`execute_transfer` and `transfer_from` in `example/cosmwasm/cw20/src/contract.rs` build the transfer payload via `EvmQuerier::erc20_transfer_payload`/`erc20_transfer_from_payload`, wrap it in `EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload }`, and return a `Response` with `add_message(msg)` — no callback, no `reply` handling, and no decoding of the message's return data. [1](#0-0) [2](#0-1) 

On the chain side, this message is routed to `HandleInternalEVMDelegateCall`, which calls `CallEVM`. `CallEVM` only surfaces failure when `res.Err != nil` (an EVM revert/exceptional halt); it returns `res.ReturnData` (which for a token returning `false` is simply ABI-encoded `false`, not an error) as a success value. [3](#0-2) 

Because the CosmWasm message handler chain only cares whether the message execution errored (not what data it returned), a `transfer` call that returns `false` completes the whole `MsgExecuteContract`/CW20-pointer transaction as a success, from both the wasm module's and the caller's perspective, without ever moving the ERC20 balance.

This is the same bug class as the reported `FootiumPrizeDistributor.claimERC20Prize` issue: unchecked ERC20 return value causes the caller to believe a transfer succeeded when it silently failed.

### Impact Explanation
Any user/contract using the CW20-pointer-for-ERC20 interface to move balances of an ERC20 token that returns `false` on failure (rather than reverting) can be told the `transfer`/`transfer_from` succeeded (no error returned, event optimistically emitted from the wrapper's execution response) while funds never moved. This can desynchronize application-level accounting built on top of the CW20 pointer (e.g., escrow/vault contracts assuming a successful `transfer` moved funds), leading to fund-loss or fund-freezing scenarios for CosmWasm applications built to interoperate with ERC20 tokens through this documented pointer mechanism.

### Likelihood Explanation
Reachable directly by any CosmWasm user/contract holding an ERC20-pointer CW20 token and calling `transfer`/`transfer_from` against a non-standard ERC20 (there are many widely used non-reverting ERC20 tokens historically, e.g. older USDT-style tokens). No special privilege is required — a single wasm `MsgExecuteContract` transaction is sufficient to trigger the code path.

### Recommendation
Have `CallEVM`/`HandleInternalEVMDelegateCall`, or the CW20 pointer contract itself, decode the ABI-encoded return value of ERC20 `transfer`/`transferFrom` calls and treat a `false` result as a failure (return an error from `execute_transfer`/`transfer_from` instead of blindly succeeding), consistent with how `CW20ERC20Pointer.sol`'s `_execute` treats WASM execution failures as reverting failures.

### Proof of Concept
1. Deploy an ERC20 token whose `transfer` function returns `false` on failure instead of reverting (e.g., paused-token semantics or an insufficient-balance branch that returns `false`).
2. Register a CW20 pointer for this ERC20 using the `example/cosmwasm/cw20` contract (`ERC20_ADDRESS` set to the token).
3. From a CosmWasm account, call `ExecuteMsg::Transfer { recipient, amount }` where `amount` exceeds available balance or the token is paused, so the underlying ERC20 `transfer` call returns `false`.
4. Observe that `execute_transfer` still returns `Ok(Response)` with `add_message` succeeding (delegatecall did not revert), the wasm `MsgExecuteContract` transaction is recorded as successful, but the recipient's ERC20 balance is unchanged — a silent failed transfer reported as success.

}

func (k *Keeper) HandleInternalEVMDelegateCall(ctx sdk.Context, req *types.MsgInternalEVMDelegateCall) (*sdk.Result, error) {
	var to *common.Address
	if req.To != "" {
		addr := common.HexToAddress(req.To)
		to = &addr
	} else {
		return nil, errors.New("cannot use a CosmWasm contract to delegate-create an EVM contract")
	}
	addr, _, exists := k.GetAnyPointerInfo(ctx, types.PointerReverseRegistryKey(common.BytesToAddress([]byte(req.FromContract))))
	if !exists || common.BytesToAddress(addr).Cmp(*to) != 0 {
		return nil, errors.New("only pointer contract can make delegatecalls")
	}
	zeroInt := sdk.ZeroInt()
	senderAddr, err := sdk.AccAddressFromBech32(req.Sender)
	if err != nil {
		return nil, err
	}
	// delegatecall caller must be associated; otherwise any state change on EVM contract will be lost
	// after they asssociate.
	senderEvmAddr, found := k.GetEVMAddress(ctx, senderAddr)
	if !found {
		err := types.NewAssociationMissingErr(req.Sender)
		evmKeeperMetrics.associationError.Add(ctx.Context(), 1, otelmetric.WithAttributes(attribute.String("scenario", "evm_handle_internal_evm_delegate_call"), attribute.String("type", err.AddressType())))
		return nil, err
	}
	ret, err := k.CallEVM(ctx, senderEvmAddr, to, &zeroInt, req.Data)
	if err != nil {
		return nil, err
	}
	return &sdk.Result{Data: ret}, nil
}
