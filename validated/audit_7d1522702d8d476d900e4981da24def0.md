## Title
Webhook shop attribution is not covered by HMAC verification, enabling cross-shop webhook forgery - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

## Summary
`ShopifyApp::WebhookVerification` authenticates a webhook request purely by recomputing an HMAC over the raw POST body and comparing it to the `X-Shopify-Hmac-Sha256` header. The shop identity used to attribute the processed payload — exposed via the `shop_domain` helper — is read straight from the unsigned `X-Shopify-Shop-Domain` header, which is never bound to the HMAC-verified body. This mirrors the GachaToken issue: an unverified identity/actor field (`by` in the report, `shop_domain` here) can be supplied independently of the piece of data that was actually authenticated, letting the caller dictate whose "account" the verified action applies to.

## Finding Description
`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` only authenticates `request.raw_post` against the shared app secret: [1](#0-0) 

`WebhookVerification` uses this same body-only check as its sole gate, and separately exposes `shop_domain`, sourced from a header that is not part of what was signed: [2](#0-1) 

The app secret (`ShopifyApp.configuration.secret`) is a single shared app-level secret, not a per-shop secret — it's the same value used for every merchant that installs the app. Any merchant who has installed the app therefore can, through legitimate webhook deliveries to their own store, obtain valid `(body, HMAC)` pairs for arbitrary body content they control (e.g. by editing their own product/cart/order data to shape the webhook body). Because `X-Shopify-Shop-Domain` is not part of the signed material, that same merchant can then replay the body+HMAC pair to the app's webhook endpoint while substituting a different shop's domain in the header. `hmac_valid?` still returns true (the body/secret pair is untouched), so the request is accepted, and `shop_domain` reports the attacker-chosen victim domain.

This is the direct analog of the GachaToken bug: the verification step (`hmac_valid?` / `_burn`'s permission model) authenticates one thing (the payload/that the caller is `msg.sender`), while a separate, attacker-controlled field (`shop_domain` / `by`) is trusted for identity attribution without being covered by that same verification.

The gem's own documentation instructs custom webhook controllers to use exactly this unverified value to key downstream, shop-scoped work: [3](#0-2) 

The built-in `WebhooksController` and generator template follow the same pattern, forwarding `shop_domain`/`webhook_request.shop` (header-derived) directly into background jobs that operate on shop-scoped models: [4](#0-3) [5](#0-4) 

## Impact Explanation
A merchant with any installation of the app (an "unrelated merchant" from the perspective of any other shop) can forge a webhook whose signature validates, but whose declared `shop_domain` names a different, victim shop. Any job/controller logic keyed on `shop_domain` (installing/removing data, updating shop-scoped records, triggering shop-specific side effects such as uninstall cleanup or subscription state changes) can be invoked under the wrong tenant's identity, since the app's `WebhookVerification` concern gives developers no signal that `shop_domain` is unauthenticated. This is a cross-shop/cross-tenant data integrity and access issue directly enabled by the gem's verification design.

## Likelihood Explanation
Exploitation only requires installing the app once (any developer/merchant account) to obtain a valid signed body/HMAC pair, then replaying it with a modified `X-Shopify-Shop-Domain` header value pointing at a different, arbitrary shop domain — no secret material, no privileged access, and no interaction with the victim shop is required.

## Recommendation
Do not trust `X-Shopify-Shop-Domain` (or any other header) as an authenticated identity signal. Either:
1. Include the shop domain in the HMAC-covered material (compute/verify HMAC over `shop_domain + body`, or require the shop domain to be embedded in and derived from the signed webhook body itself), or
2. Cross-check the header-derived `shop_domain` against a shop domain independently recovered from the verified payload (e.g., the webhook's `id`/resource lookup scoped to a session already tied to that shop) before using it for any shop-scoped action, and document/enforce that `shop_domain` must never be used as a sole tenant key without such a check.

## Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a real webhook (e.g. by updating one of their own products), capturing the request body `B` and its valid header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which only checks `B` against the shared secret — it passes.
5. The controller/job reads `shop_domain` (or `webhook_request.shop`), which now returns `victim-shop.myshopify.com`, and performs shop-scoped processing under the victim shop's identity despite the payload actually originating from, and being valid for, the attacker's own shop. [6](#0-5)

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

# frozen_string_literal: true

module ShopifyApp
  module WebhookVerification
    extend ActiveSupport::Concern
    include ShopifyApp::PayloadVerification

    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_request
    end

    private

    def verify_request
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end

    def shop_domain
      request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]
    end
  end
end
