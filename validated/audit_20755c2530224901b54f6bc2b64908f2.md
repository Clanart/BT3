### Title
`ThresholdKeys::read` performs no consistency validation between the secret share, verification shares, and interpolation data, allowing attacker-crafted serializations to bind a victim to an attacker-known group key - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to CVE-2024-22369 (deserialization of untrusted data producing object states the program assumes impossible), `ThresholdKeys::read` deserializes t/n/i, an `Interpolation` method, a `secret_share`, and `verification_shares` purely structurally, then hands them to `ThresholdKeys::new`. `ThresholdKeys::new` only checks share count, participant bounds, and that `t == n` for `Interpolation::Constant`; it never checks that `secret_share * C::generator() == verification_shares[params.i()]`, nor that the constant coefficients actually interpolate the verification shares. `group_key` is derived exclusively from the verification shares. A crafted byte stream therefore produces `ThresholdKeys` whose group key is fully attacker-controlled while the embedded secret share is unrelated.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads the curve ID, `(t, n, i)`, an interpolation tag (`0` = `Constant` with `n` scalars via `C::read_F`, `1` = `Lagrange`), a `secret_share` scalar via `C::read_F`, and `n` verification-share points via `C::read_G`. All field/point reads are canonical (crypto/ciphersuite/src/lib.rs:74-101), so the bug is not encoding-level malleability but the absence of semantic validation. `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) validates only:

- `verification_shares.len() == n` and all keys `<= n` (lines 355-365)
- `t == n` when interpolation is `Constant` (lines 367-374)

It then computes `group_key = sum(verification_shares[l] * interpolation_factor(l))` over `l = 1..=t` (lines 376-378) with no check whatsoever on `secret_share`. The codebase itself acknowledges the resulting state: `AlgorithmSignatureMachine::complete` ends with `InternalError("everyone had a valid share yet the signature was still invalid")` and comments that "the only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:491-494).

Concretely, an attacker who feeds crafted bytes to `ThresholdKeys::read` can choose `verification_shares[1..=t]` as points with known discrete logarithms (e.g., `g*x_1, ..., g*x_t` with `Interpolation::Lagrange` so the interpolation factors are public and computable), making `group_key` a key whose discrete log the attacker knows, while `secret_share` is arbitrary garbage. The victim's `group_key()`, `tweak_keys`, `Scanner::new`, and FROST `view()`/`sign()` all proceed normally on this object.

### Impact Explanation
If a victim deserializes the attacker-supplied bytes (e.g., a key file/blob transported or restored rather than produced by a verified DKG transcript), the resulting `group_key` — including after `tweak_keys` Taproot adjustment in `networks/bitcoin/src/wallet/mod.rs:46-75` — is a key whose spend path the attacker fully controls. `Scanner`/`scan_transaction` will report outputs paying that key as received funds, but the victim's `secret_share` corresponds to no valid threshold signing relation, so the funds are unspendable by the victim and spendable by the attacker. Alternatively, with honestly-derived shares but a tampered `interpolation` byte or reordered/mismatched share/scalar fields, all participants produce "valid" shares under the crafted verification shares yet `complete()` fails, hitting the documented `InternalError` path — persistent signing failure (DoS) indistinguishable from a library bug.

### Likelihood Explanation
The attack requires an attacker to cause the victim to deserialize attacker-controlled bytes via `ThresholdKeys::read` rather than keys produced by the local DKG — i.e., untrusted serialized key material (backup restore, cross-node transfer, or any channel where serialized keys are accepted). Within that documented input surface this is deterministic and trivial: no cryptanalytic work is needed since `group_key` is a linear, public combination of attacker-chosen points. Severity is bounded by the fact that canonical encodings and `ThresholdParams` bounds are enforced, and that the attack does not leak an existing honest secret share.

### Recommendation
In `ThresholdKeys::new` (or at the end of `ThresholdKeys::read`), verify `secret_share * C::generator() == verification_shares[&params.i()]`. For `Interpolation::Constant`, additionally verify the coefficients are consistent with the verification shares (e.g., that each share satisfies the committed coefficients, or restrict `Constant` to known-good constructions). Consider authenticating serialized key material (MAC or transcript-hash binding to the DKG session) so deserialization cannot silently substitute semantically invalid keys.

### Proof of Concept
```rust
// C = Secp256k1 ciphersuite, t = n = 2, victim i = 1
// Attacker picks known scalars x1, x2 and builds a serialization:
let x1 = random_scalar();
let x2 = random_scalar();

let mut bytes = vec![];
bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(2u16.to_le_bytes()); // t
bytes.extend(2u16.to_le_bytes()); // n
bytes.extend(1u16.to_le_bytes()); // i
bytes.push(1);                    // Interpolation::Lagrange
bytes.extend(arbitrary_scalar.to_repr()); // secret_share: unrelated garbage
bytes.extend((G::generator() * x1).to_bytes()); // verification_shares[1]
bytes.extend((G::generator() * x2).to_bytes()); // verification_shares[2]

let keys = ThresholdKeys::<C>::read(&mut bytes.as_slice()).unwrap(); // succeeds

// group_key = x1*L1(0)*G + x2*L2(0)*G => attacker knows its discrete log
// victim's secret_share does not correspond to verification_shares[1]
// Deposits to Scanner::new(group_key).p2tr address are spendable by attacker,
// unspendable by victim; FROST complete() hits InternalError.
```

The `InternalError` arm at crypto/frost/src/sign.rs:491-494 confirms this state is reachable only through deserialization of semantically invalid keys.
