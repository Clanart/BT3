### Title
Attacker-controlled `.gitmodules` can force `protocol.file.allow=always` during checkout, re-enabling git's local-submodule file-protocol trust issue - ([File: app/src/lib/git/submodule.ts], [File: app/src/lib/git/checkout.ts])

### Summary
The gogopool bug is a "broken trust boundary at first use" issue: an attacker seeds a shared piece of state (share price) before a legitimate actor interacts with it, and no guard prevents the attacker-controlled value from being trusted. The closest analog in GitHub Desktop is the `allowFileProtocol` flag that is threaded from `checkoutBranch`/`checkoutCommit` into `updateSubmodulesAfterOperation`, which conditionally re-enables `protocol.file.allow=always` for `git submodule update --init --recursive` [1](#0-0) . Git disables the `file://` submodule protocol by default specifically because a malicious repository's `.gitmodules` can point a submodule at an arbitrary local path and, via git's local-clone hardlink optimization, exfiltrate or corrupt files outside the intended repository. If Desktop's checkout path ever calls into this with `allowFileProtocol=true` for a repository whose `.gitmodules` content is attacker-controlled (i.e., came from a clone/fetch, not from the user's own local creation), that trust check is silently defeated the same way the first-depositor exchange rate is silently corrupted in the ERC4626 bug: a single attacker-supplied value (`.gitmodules` submodule URL) reaches a privileged execution path (`git -c protocol.file.allow=always ...`) with no independent verification of provenance.

### Finding Description
`checkoutBranch` and `checkoutCommit` accept a boolean `allowFileProtocol` and pass it straight through to `updateSubmodulesAfterOperation` [2](#0-1) [3](#0-2) . Inside `updateSubmodulesAfterOperation`, when the flag is `true`, Git is invoked with `-c protocol.file.allow=always` before running `submodule update --init --recursive` [1](#0-0) . `protocol.file.allow=always` is the exact override that disables the upstream Git mitigation for CVE-class issues where a submodule's URL in `.gitmodules` (fully attacker-controlled content of a cloned repo) references a `file://` path. With the restriction lifted, `git submodule update --init --recursive` will clone/checkout whatever local path the attacker names — including paths outside the working tree — and Git's local-clone optimization can hardlink files from that path into the new submodule's `.git` objects, exposing or corrupting file contents (and, depending on hook/config content reachable that way, execute arbitrary code on subsequent Git operations).

### Impact Explanation
If any call site reaches `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true` while operating on a freshly cloned or fetched (i.e., attacker-authored) repository, the attacker's `.gitmodules` entry is the sole input that decides which local filesystem path Git touches. This satisfies the report's core impact class — an attacker-controlled repository object silently corrupting what the app does with local files, potentially leading to code execution or file read/write outside the intended repository — without requiring any social engineering beyond the user opening/cloning the malicious repo and performing an ordinary checkout.

### Likelihood Explanation
I was not able to fully trace, within this session, every call site in `app-store.ts` and `dispatcher.ts` that decides the concrete value of `allowFileProtocol` passed into `checkoutBranch`/`checkoutCommit` [4](#0-3) . The sink (`protocol.file.allow=always` in `submodule.ts`) and the plumbing (`checkout.ts`) are confirmed from local code; whether the flag is gated on "this repository/submodule was locally authored by the user" versus "any repository being checked out" is the deciding factor for exploitability and needs to be verified against the actual condition used in `app-store.ts`/`dispatcher.ts` before treating this as a confirmed, currently-reachable bug versus a previously-mitigated one.

### Recommendation
- Verify all call sites that set `allowFileProtocol=true` and ensure it is only ever true for repositories/submodules whose origin is fully trusted by the user (e.g., a repository the user created locally themselves), never for a repository that was cloned/fetched from a remote or whose `.gitmodules` content could have been supplied by a third party.
- Prefer leaving Git's default (`protocol.file.allow=user` or unset) for any checkout/submodule-update path triggered on cloned/fetched content, and only opt into `always` after an explicit, per-submodule-URL user confirmation dialog, similar to how other trust-sensitive git config overrides are surfaced.

### Proof of Concept
Conceptual PoC (requires confirming the exact trust gate before it can be demonstrated end-to-end):
1. Attacker publishes a repository containing a `.gitmodules` file with a submodule URL such as `file:///some/local/path/that/exists/on/many/machines` (or a relative `file://../../..` path).
2. Victim clones or fetches this repository in Desktop and performs a normal branch/commit checkout.
3. If the checkout path that runs invokes `updateSubmodulesAfterOperation` with `allowFileProtocol=true` for this repository [1](#0-0) , Git executes `git -c protocol.file.allow=always submodule update --init --recursive`, cloning the attacker-specified local path into the submodule directory using Git's local hardlink optimization, exposing or corrupting files outside the intended repository boundary.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
