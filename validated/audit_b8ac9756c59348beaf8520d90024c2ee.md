## Summary

The Covalent report's core broken invariant: a share/ownership accounting value (`totalGlobalShares`) is mutated as a byproduct of one operation (`disableValidator`) while a *different* operation (reward distribution) still depends on it being scoped correctly, and when the two get out of sync, funds meant for one party get released to/locked from the wrong party.

The closest local analog is in `IntrinsicIntents._fillSameChain` [1](#0-0) , where per-leg fill progress is tracked by **output token address only** (`_partialFills[commitment][outputToken]`), not by output-leg index, while escrow release on a full-leg fill reads the **entire remaining balance of the input token for the whole order** rather than the leg-proportional amount.

### Finding Description

`_partialFills` is keyed as `mapping(commitment => mapping(outputToken => filled))` [2](#0-1) . Inside `_fillSameChain`, the loop iterates output legs by index `i`, but reads/writes cumulative fill progress keyed only by `outputToken = order.output.assets[i].token` [3](#0-2) . If an order has two output legs that specify the *same* output token (e.g. two legs both paying out in USDC, backed by two different escrowed input tokens/amounts at `order.inputs[0]` and `order.inputs[1]`), filling leg 0 writes `_partialFills[commitment][token] = fillAmount0`. When the loop reaches leg 1, `alreadyFilled` is read from the *same* key and already reflects leg 0's progress, so `remaining = totalRequired(leg1) - alreadyFilled(from leg0)` is corrupted — the solver can be assessed less than leg 1 actually requires, or the subtraction can revert depending on magnitude.

Worse, on the "leg complete" path the code does not compute a proportional escrow release; it instead reads the **whole remaining order-wide escrow balance for that input token**:

```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [4](#0-3) 

`_orders[commitment][token]` is a single running balance per `(commitment, token)` pair [5](#0-4) , decremented in `_withdraw` [6](#0-5) . If two output legs are backed by the *same* input token (a legitimate configuration — nothing in `_fillSameChain`/`IntentsBase` rejects duplicate `order.inputs[i].token` across indices), completing the first leg pulls the *entire* remaining escrow for that token via `_orders[commitment][token]`, not just that leg's proportional share. The solver who completes leg 0 first receives escrow that was meant to also cover leg 1. When leg 1 is later filled, `_withdraw` finds `_orders[commitment][token] == 0` and reverts with `UnknownOrder()` [7](#0-6) , permanently blocking that leg's completion — the user's remaining input tokens for that leg were already drained to the first solver, and the second output the user was owed can never be paid out through this path.

### Impact Explanation

An ordinary solver (unprivileged actor, no relayer/prover/admin trust assumed) can, on an order containing duplicate output-token legs, capture escrow value that exceeds their proportional entitlement for the leg they filled, while permanently locking the remaining leg (denial of completion, and locked/misdirected user funds). This is a direct "wrong beneficiary or amount" / fund-loss condition inside the escrow settlement path that the bounty scope explicitly covers ("bridged assets, order escrow ... must move exactly once and only to the rightful beneficiary and amount").

### Likelihood Explanation

This requires only a normally-placed order with two output legs sharing an output token address and backed by the same input token — a plausible, non-malicious order shape (e.g. a user requesting output split across two beneficiary-side legs, or a partial-fill auction scenario) — plus an ordinary solver calling `fillOrder`. No relayer, prover, or governance compromise is needed; it is reachable purely through public entrypoints. I was unable to fully verify (due to no further tool budget) whether `placeOrder`/order-hash validation elsewhere in `evm/src/apps/IntentGatewayV2.sol` or `IntentsBase._validateParams` explicitly forbids duplicate tokens across `order.output.assets` or requires `order.inputs.length == order.output.assets.length` — if such a check exists, it would need to be confirmed to entirely rule out this path.

### Recommendation

Key `_partialFills` (and the escrow-release computation on full-leg completion) by **leg index** rather than by token address alone — e.g. `_partialFills[commitment][i]` — and always compute the escrow release for a leg as the proportional share of `order.inputs[i].amount`, never as the raw remaining balance of `_orders[commitment][token]`, even on the "fully filled" branch. Additionally, validate at order-placement time that `order.inputs.length == order.output.assets.length` and consider rejecting orders where the same output token appears in multiple legs (or handle it explicitly with a separate per-leg escrow accounting scheme) so that fill progress for one leg can never influence the escrow computed for another leg with a shared token.

### Proof of Concept

1. User places a same-chain order with two output legs: leg 0 = `{token: USDC, amount: 100}` backed by `order.inputs[0] = {token: DAI, amount: 100}`; leg 1 = `{token: USDC, amount: 50}` backed by `order.inputs[1] = {token: DAI, amount: 50}` (same input token DAI across both legs, escrowed total 150 DAI under `_orders[commitment][DAI] = 150`).
2. Solver A calls `fillOrder` supplying `solverAmount = 100` USDC only for leg 0. Loop processes `i=0`: `alreadyFilled=0`, `remaining=100`, `fillAmount=100`, `amountFilled=100=totalRequired` → takes the "fully filled" branch: `escrowedAmount = _orders[commitment][DAI] = 150` (the *entire* pool, not the 100 owed for leg 0). This 150 DAI is queued into `escrowedInputs[0]` and released via `_withdraw`, zeroing `_orders[commitment][DAI]`.
3. Loop processes `i=1` in the same call (since `options.outputs[1].amount` was 0, code skips it via the `solverAmount==0` branch, leaving leg 1 unresolved and `isFullyFilled=false`), so the transaction emits `PartialFill` while having already drained all 150 DAI to Solver A for satisfying only leg 0's 100 USDC requirement.
4. Solver B later attempts to fill leg 1 (50 USDC) expecting to receive the remaining 50 DAI; `_withdraw` reads `_orders[commitment][DAI] == 0` and reverts with `UnknownOrder()`, permanently preventing leg 1 from ever settling — the 50 DAI meant for leg 1's solver was already misdirected to Solver A in step 2.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
