## Analysis

The stake bug's core invariant: a deposit gets irreversibly committed against a target entity, is escrowed pending an asynchronous cross-chain confirmation message, and if that target/binding changes (validator inactive) before the message lands, the deposit is permanently stuck with no cancel path.

The closest local analog is in the Intent Gateway's cross-chain settlement, specifically in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `evm/src/apps/intentsv2/IntentsBase.sol`.

### Title
Stale `_instances` binding after gateway redeployment permanently strands cross-chain escrow — (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`_fillCrossChain` and `_cancelFromDest` dispatch `RedeemEscrow`/`RefundEscrow` messages whose `to` field is resolved via `_instance(order.source)` — a mutable, governance-controlled mapping — at *settlement* time, not at *order-placement* time. If Hyperbridge governance re-registers the source-chain gateway address (`_addDeployment`, triggered by a `NewDeployment` message) between order placement and fill, the settlement message is routed to the *new* gateway contract, which has no `_orders[commitment]` entry for that order. The escrow remains locked in the *old* gateway contract forever, since the dispatched message's `to` field is baked in at dispatch time and any retry targets the same (wrong) contract.

### Finding Description
- `_instance()` (`evm/src/apps/intentsv2/IntentsBase.sol:358-362`) is a pure lookup into `_instances[keccak256(stateMachineId)]`, updated at any time by `_addDeployment` (`IntentsBase.sol:521-524`), itself driven by an inbound `NewDeployment` request that only Hyperbridge can send (`ExtrinsicIntents.sol:297-300`).
- At fill time, the destination gateway builds the settlement message using the *current* value of `_instance(order.source)` as the `to` address: [1](#0-0) 
- Likewise for destination-initiated cancellation: [2](#0-1) 
- On the source chain, `onAccept` authenticates the *sender* (`request.from`) against `_instance(request.source)`, and then calls `_withdraw`, which requires `_orders[commitment][token] != 0`: [3](#0-2) [4](#0-3) 
- The order's escrow (`_orders[commitment][token]`) lives permanently at the *original* source-chain gateway contract address used at `placeOrder` time. There is no mechanism binding the dispatched settlement message's destination address to that specific contract — it is resolved dynamically via `_instance()` at settlement time.
- If governance issues a `NewDeployment` for `order.source` between placement and fill/cancel (e.g., a routine contract upgrade/migration, or address rotation), `_instance(order.source)` now points to the new gateway. The RedeemEscrow/RefundEscrow message lands on the new (empty) contract, `_orders[commitment][token] == 0` there, and `_withdraw` reverts with `UnknownOrder()`. Because the message's `to` was fixed at dispatch, every retry (per the documented ISMP retry-until-timeout semantics, and the dispatch uses `timeout: 0`, i.e., it never expires) keeps hitting the same wrong, empty contract — the failure is not transient, it is deterministic and permanent.
- Meanwhile, on the destination side the order is already marked filled/cancelled (`_filled[commitment]` set) and, for a fill, the solver has already delivered real output tokens to the beneficiary. The source-side escrow can never be released: `cancelOrder` on the (old) source gateway still checks `_filled[commitment] != address(0)` — that's still zero there (never got set because the wrong contract received the message), so a user retry of cancellation is theoretically possible, but only through a fresh `_cancelFromSource`/`_cancelFromDest` path, which is itself routed through the *same* stale `_instance()` binding and hits the same wrong address, so the round trip can never authenticate/settle either.

### Impact Explanation
This is a direct loss/lock of bridged assets: escrowed input tokens (and any accrued relayer fee) become permanently unrecoverable in the old gateway contract once a source-chain redeployment occurs while an order is in flight. No admin sweep function exists for `_orders` balances (only `_sweepDust` for protocol-owned dust, which is a distinct storage slot). This matches the "stealing or loss of funds" and "wrong beneficiary or amount" impact classes in the bounty scope — value is stuck with no rightful beneficiary ever receiving it.

### Likelihood Explanation
This requires no malicious actor — governance redeploying/rotating a gateway is a normal, expected operational event (contract upgrades, security patches, chain migrations). Any order placed shortly before such a rotation and filled/cancelled after it lands is at risk. Given the intent-gateway's multi-chain, long-lived order model (deadlines can span many blocks) and that gateway redeployments are a documented governance capability, the race window is realistic and not contrived.

### Recommendation
Bind the settlement message's destination address to the gateway instance that was active for `order.source` at **order-placement time**, not at settlement time — e.g., snapshot and store the source gateway address (or a version/epoch id) in the order/commitment record at `placeOrder`, and use that stored value (not a live `_instance()` lookup) when constructing the `RedeemEscrow`/`RefundEscrow` dispatch `to` field. Alternatively, retain old gateway addresses in an append-only registry so `_authenticate`/dispatch can route to any historically valid instance for in-flight orders, and add an explicit emergency-withdrawal path for orders stranded by a redeployment.

### Proof of Concept
1. User places a cross-chain order on chain A (source) via `IntentGatewayV2.placeOrder`, escrowing input tokens; `order.source = A`, `order.destination = B`. `_orders[commitment][token]` is set on gateway A₁ (the currently deployed source gateway).
2. Before the order is filled, Hyperbridge governance dispatches a `NewDeployment` for chain A pointing to a new gateway address A₂ (e.g., as part of a routine contract upgrade/migration) — this updates `_instances[keccak256(A)]` on the destination gateway (chain B) via `_addDeployment`.
3. A solver fills the order on chain B via `fillOrder` → `_fillCrossChain`. The dispatched `RedeemEscrow` message uses `to: abi.encodePacked(_instance(order.source))`, which now resolves to A₂, not A₁.
4. The message is delivered and accepted on chain A, hitting gateway A₂'s `onAccept` → `_authenticate` (passes, since A₂ trusts B's registered instance) → `_withdraw`, which looks up `_orders[commitment][token]` on A₂ — this is `0` because the actual escrow lives on A₁. `withdraw` reverts with `UnknownOrder()`.
5. Every retry of this (or a freshly dispatched) settlement message targets A₂ again since `_instance(A)` still resolves to A₂. The escrow on A₁ can never be released to the solver, and the user cannot use `cancelOrder`'s destination-triggered path either, since it routes through the same stale binding. The funds are permanently stranded on A₁. [5](#0-4) [6](#0-5)
