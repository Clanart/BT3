### Title
Underestimated transaction weight when an OP_RETURN output is present allows creating transactions below the required fee rate or over the standard weight limit — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The reported bug class is an inconsistency between the value used to *compute* a bound (fees, rounded up per-output) and the value used to *validate* that bound (max fee, rounded down on the aggregate), so that a valid-looking operation produces a result the protocol then rejects — a fulfillment DoS. The same shape exists in Serai's `bitcoin-serai` wallet: `SignableTransaction::new` builds the final transaction from `tx_outs` (which includes the OP_RETURN `data` output), but computes `weight`, `vbytes`, `needed_fee`, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which is passed `payments` — a list that does **not** include the `data` output. The estimation and the constructed transaction are inconsistent, exactly as in the report where the two code paths disagree.

### Finding Description
`SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` before estimating size:

```rust
// networks/bitcoin/src/wallet/send.rs:194-204
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) });
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (send.rs:62-127) synthesizes a `Transaction` whose outputs are only `payments` (+optional change). The OP_RETURN output (up to 80 bytes of data, ~90 vbytes) is therefore excluded from:

- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206)
- the minimum relay fee check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (send.rs:211)
- the change feasibility check and `fee_with_change` (send.rs:225-233), so the change output's value is set such that the *actual* fee paid equals the underestimated `fee_with_change`
- the `weight > MAX_STANDARD_TX_WEIGHT` standardness check (send.rs:241)

Because the actual fee is fixed by `sum(inputs) - sum(outputs)` at construction time (not re-derived from real `tx.vsize()`), a transaction created with `data.is_some()` pays a fee computed against a smaller virtual size than it actually has. With `fee_per_vbyte = 1` and a change output, the real feerate is `vbytes_est / vbytes_actual < 1 sat/vbyte`, below `DEFAULT_MIN_RELAY_TX_FEE`, so the signed transaction is rejected by relay policy despite `TooLowFee` not being returned. Likewise, a transaction with vsize at the boundary passes the `MAX_STANDARD_TX_WEIGHT` check while the real transaction (with the extra output) is non-standard and unbroadcastable. This mirrors the report: a quantity is computed on one representation (fee/vsize of a smaller tx) and the resulting artifact fails validation against the real representation (network policy / weight limit), so otherwise-valid spends cannot be fulfilled.

### Impact Explanation
A caller using `SignableTransaction::new` with `data` can produce a signed transaction that the Bitcoin network will not relay (sub-minimum feerate or over-standard-weight). For a threshold-wallet setting (the intended consumer, e.g. a coordinator preparing transactions for FROST signing), this produces a plan whose signed transaction is unbroadcastable — a fulfillment DoS with the same flavor as the reported revert-on-fill, and it can also silently underpay the feerate relative to the caller's request even when still relayable.

Reachability caveat: in `processor/src/networks/bitcoin.rs`, `make_signable_transaction` passes `None` for `data`, so this path is only exposed to direct consumers of the `bitcoin-serai` wallet API, not via the in-tree processor flow. Severity is bounded accordingly (Medium/low-Medium).

### Likelihood Explanation
Any `SignableTransaction::new` call with `Some(data)` and either a low `fee_per_vbyte`, a change output, or a near-boundary total size triggers the discrepancy deterministically — no adversarial timing required.

### Recommendation
Compute weight/vbytes over the exact output set that will be serialized. Either build `tx_outs` fully (including the OP_RETURN output) before calling `calculate_weight_vbytes`, or change `calculate_weight_vbytes` to take the final `Vec<TxOut>`/`tx_outs` instead of `payments`, so `needed_fee`, `fee_with_change`, the min-relay check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the real transaction.

### Proof of Concept
Conceptual reproduction against `networks/bitcoin/src/wallet/send.rs`:

```rust
// 1 input ReceivedOutput with value V; one payment of DUST; change address C;
// data = vec![0; 80]; fee_per_vbyte = 1.
let tx = SignableTransaction::new(vec![input], &[(payment_script, DUST)],
                                Some(change_script), Some(vec![0; 80]), 1).unwrap();
// Internally: vbytes_est excludes the ~89-vbyte OP_RETURN output.
// Change is set to V - DUST - vbytes_est, so actual fee == vbytes_est.
// Actual vsize = vbytes_est + ~89  =>  feerate ≈ 0.99... sat/vb < 1 sat/vb.
assert!(tx.fee() < u64::try_from(/* signed tx */ vsize_actual).unwrap()); // below min relay
```

The signed transaction serializes with the OP_RETURN output (present in `tx.output`), so `bitcoin::policy::get_virtual_tx_size` on the real `Transaction` exceeds the estimate used for `needed_fee`; broadcasting to a node with default policy fails `min relay fee not met`. The analogous boundary case replaces the large `data`/`payments` with enough outputs so that `weight_est <= 400_000 < weight_actual`, passing `TooLargeTransaction` while producing a non-standard transaction.
