### Title
`RecoverCellsAndComputeKZGProofs` performs no post-recovery consistency check, allowing inconsistent input cells to silently produce a corrupted (non-matching) recovered polynomial - (`api_eip7594.go`)

### Summary
`recoverPolynomialCoeffs` in `api_eip7594.go` reconstructs a degree-`< numScalarsInDataWord` polynomial from supplied cells using a zero-polynomial erasure-decoding technique in `internal/erasure_code/erasure_code.go`, then blindly truncates the result to `numScalarsInDataWord` coefficients without ever re-checking that the recovered polynomial reproduces the caller-supplied cells at the caller-supplied `cellIDs`. When the number of supplied cells exceeds the strict minimum (`NumBlocksNeededToReconstruct`), or when all 128 cells are supplied with zero "missing" blocks, the true quotient polynomial `q(x)` computed internally can have degree higher than `numScalarsInDataWord-1` if the input cells do not originate from a single low-degree polynomial (e.g., cells stitched together from two unrelated valid extended blobs). Truncating this higher-degree `q(x)` silently drops nonzero high-order coefficients, so `computeCellsFromPolyCoeff` on the truncated result no longer reproduces the original input cells at the given indices, and no error is returned.

### Finding Description
The claimed invariant is: for every `i`, `recovered[cellIDs[i]] == cells[i]`, where `recovered` is the output of `computeCellsFromPolyCoeff` on the polynomial returned by `RecoverPolynomialCoefficients`.

Code path:
- `recoverPolynomialCoeffs` (`api_eip7594.go:97-146`) deserializes each cell with `deserializeCell` (canonical scalar check only, no consistency check), places it into `extendedBlob` at `cellID*scalarsPerCell`, bit-reverses, and calls `ctx.dataRecovery.RecoverPolynomialCoefficients(extendedBlob, missingCellIds)`. [1](#0-0) 
- `RecoverPolynomialCoefficients` (`internal/erasure_code/erasure_code.go:110-148`) builds the vanishing polynomial `z(x)` over the *missing* block indices, computes `g(x) = e(x)*z(x)` via a full-domain FFT/IFFT round trip, divides by `z` on a coset to obtain `q(x) = g(x)/z(x)`, and then truncates: `polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]`. [2](#0-1) 

Algebraically, `q(x_i) = e(x_i)` exactly at every non-erased domain point `x_i` — this holds unconditionally, regardless of whether `e` is a valid low-degree Reed–Solomon codeword — because `g(x)` is the exact interpolation of `e(x)*z(x)` and `z` divides `g` exactly at the roots of `z`. However, this identity only survives the *truncation* to `numScalarsInDataWord` coefficients when `deg(q) < numScalarsInDataWord`. The degree bound `deg(q) <= N-1-deg(z)` is only guaranteed to fall below `numScalarsInDataWord` when the number of missing blocks equals the *maximum* allowed (i.e., exactly `NumBlocksNeededToReconstruct` cells supplied — the minimum case). When strictly more cells than the minimum are supplied (fewer "missing" blocks, so `deg(z)` is smaller than the enforced maximum), and the supplied cell data does not correspond to any single degree-`<numScalarsInDataWord` polynomial (attacker-crafted inconsistency, e.g., cells 0–63 taken from one valid extended blob and cells 64–127 taken from a different valid extended blob), the true `q(x)` can have degree well above `numScalarsInDataWord-1`. The blind truncation then discards nonzero high-order terms, and the resulting `polyCoeff`, when fed to `computeCellsFromPolyCoeff` inside `RecoverCellsAndComputeKZGProofs` (`api_eip7594.go:148-165`), evaluates to values that generically diverge from the originally supplied `cells[i]` at the corresponding `cellIDs[i]`. [3](#0-2) 

None of the existing guards catch this: `deserializeCell` only enforces canonical scalar encoding (no cross-cell consistency); `isAscending` and the `cellID < CellsPerExtBlob` checks only validate index formatting; `NumBlocksNeededToReconstruct` only enforces a minimum count, not a maximum, so supplying more than the minimum (or all 128) is permitted and is exactly the regime where the bug manifests; there is no final "re-evaluate polynomial at the given indices and compare to input cells" assertion anywhere in `recoverPolynomialCoeffs`, `RecoverCellsAndComputeKZGProofs`, or `RecoverCells` (`api_eip.go:7-15`). [4](#0-3) 

### Impact Explanation
If a caller feeds `RecoverCellsAndComputeKZGProofs` with `cellIDs`/`cells` that are individually well-formed (canonical field elements, ascending indices, sufficiently many cells) but collectively inconsistent with any single low-degree polynomial, the function returns a full `[CellsPerExtBlob]*Cell` array and a matching `[CellsPerExtBlob]KZGProof` array with **no error**, even though the recovered data does not match the input at the supplied indices. This is a genuine "recovered data does not match supplied data" defect inside the reconstruction routine itself. Because `RecoverCellsAndComputeKZGProofs` does not take or check against a KZG commitment, its output would still need to pass a downstream `VerifyCellKZGProofBatch` against the real blob commitment before being accepted elsewhere, which would very likely fail for corrupted data — this limits the blast radius to "false reconstruction data that a subsequent proof check should reject" rather than an "accepted forged opening." Whether this is exploitable in a live network depends entirely on whether callers invoke this function with cells that were not already proof-verified against a single commitment (per the standard EIP-7594 flow, peers verify individual cell proofs against the block's commitment before using them in reconstruction).

### Likelihood Explanation
Exploiting this specific code path requires: (1) an over-determined call — more cells supplied than the strict minimum `NumBlocksNeededToReconstruct` — and (2) cell contents that are individually canonical but jointly inconsistent with a single low-degree polynomial. If the calling code first validates each cell's KZG proof against a single common commitment (as intended by the protocol) before ever calling `RecoverCellsAndComputeKZGProofs`, such inconsistent inputs cannot arise from honest per-cell verification against one commitment, and this scenario becomes a "wrong caller usage" issue rather than a directly attacker-reachable one through the intended protocol path. I was not able to fully verify from the available code/tests whether any caller in this repository or a consuming client is required to perform that pre-verification, nor whether the c-kzg-4844 reference implementation performs an equivalent post-recovery consistency check (which would make this a spec-matching non-issue rather than a divergence). The embedded test suite (`tests/recover_cells_and_kzg_proofs/...`) includes cases for non-canonical bytes and out-of-order indices but I found no test exercising "canonical, ascending, sufficient cells that are jointly inconsistent," so this exact scenario appears untested.

### Recommendation
After computing `polyCoeff` in `recoverPolynomialCoeffs`, re-derive `computeCellsFromPolyCoeff(polyCoeff, ...)` and assert that `recovered[cellIDs[i]] == cells[i]` for every supplied index before returning; return an error (e.g., a new `ErrRecoveredCellsMismatch`) if any mismatch is found. This closes the gap regardless of caller behavior and matches the "recovered data must equal supplied data" invariant implied by the API contract.

func (ctx *Context) RecoverCellsAndComputeKZGProofs(cellIDs []uint64, cells []*Cell, numGoRoutines int) ([CellsPerExtBlob]*Cell, [CellsPerExtBlob]KZGProof, error) {
	polyCoeff, err := ctx.recoverPolynomialCoeffs(cellIDs, cells)
	if err != nil {
		return [CellsPerExtBlob]*Cell{}, [CellsPerExtBlob]KZGProof{}, err
	}

	recoveredCells, err := ctx.computeCellsFromPolyCoeff(polyCoeff, numGoRoutines)
	if err != nil {
		return [CellsPerExtBlob]*Cell{}, [CellsPerExtBlob]KZGProof{}, err
	}

	proofs, err := ctx.computeKZGProofsFromPolyCoeff(polyCoeff, numGoRoutines)
	if err != nil {
		return [CellsPerExtBlob]*Cell{}, [CellsPerExtBlob]KZGProof{}, err
	}

	return recoveredCells, proofs, nil
}

func (dr *DataRecovery) RecoverPolynomialCoefficients(data []fr.Element, missingIndices []BlockErasureIndex) ([]fr.Element, error) {
	zX := dr.constructVanishingPolyOnIndices(missingIndices)

	// Compute zX evaluations without mutating zX since we need zX later for a coset FFT
	zXForEval := make([]fr.Element, len(zX))
	copy(zXForEval, zX)
	dr.domainExtended.FftFr(zXForEval)
	zXEval := zXForEval

	if len(zXEval) != len(data) {
		return nil, errors.New("length of data and zXEval should be equal")
	}

	eZEval := make([]fr.Element, len(data))
	for i := 0; i < len(data); i++ {
		eZEval[i].Mul(&data[i], &zXEval[i])
	}

	dr.domainExtended.IfftFr(eZEval)
	dzPoly := eZEval

	dr.domainExtendedCoset.CosetFFtFr(zX)
	cosetZxEval := zX
	dr.domainExtendedCoset.CosetFFtFr(dzPoly)
	cosetDzEVal := dzPoly

	cosetQuotientEval := make([]fr.Element, len(cosetZxEval))
	cosetZxEval = fr.BatchInvert(cosetZxEval)

	for i := 0; i < len(cosetZxEval); i++ {
		cosetQuotientEval[i].Mul(&cosetDzEVal[i], &cosetZxEval[i])
	}

	dr.domainExtendedCoset.CosetIFFtFr(cosetQuotientEval)

	// Truncate the polynomial coefficients to the number of scalars in the data word
	polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]
	return polyCoeff, nil
}

// RecoverCells will compute the extended blob that is associated with the given `cells` if we have more than 50% of the `cells`
func (ctx *Context) RecoverCells(cellIDs []uint64, cells []*Cell, numGoroutines int) ([CellsPerExtBlob]*Cell, error) {
	polyCoeff, err := ctx.recoverPolynomialCoeffs(cellIDs, cells)
	if err != nil {
		return [CellsPerExtBlob]*Cell{}, err
	}

	return ctx.computeCellsFromPolyCoeff(polyCoeff, numGoroutines)
