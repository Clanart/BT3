## Title
Missing finalized-order guard in `onAccept` allows a stale/duplicate cross-chain settlement message to overwrite an already-finalized order's beneficiary - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The reported bug class is: a settlement-status check that is too lenient allows a state that should be immutable (a finalized/settled position) to be reprocessed and its accounting corrupted. The direct local analog is in Hyperbridge's `IntentGatewayV2` cross-chain intent settlement path. The same-chain entrypoint `cancelOrder()` explicitly enforces `if (_filled[commitment] != address(0)) revert Filled();` before allowing any state change, but the cross-chain settlement callback `onAccept()` — which processes both `RedeemEscrow` (fill payout) and `RefundEscrow` (cancel payout) messages arriving from Hyperbridge — never performs this check before calling `_withdraw(..., finalize: true)`.

### Finding Description
`onAccept` dispatches directly into `_withdraw` for both terminal message kinds without checking whether the order commitment has already been finalized: [1](#0-0) 

Compare this to the local, same-chain path (`IntentGatewayV2.cancelOrder`, documented in `docs/content/developers/evm/intent-gateway/cancelling-orders.mdx:39-56`), which explicitly derives the commitment and rejects it if `_filled[commitment] != address(0)` *before* dispatching anything. `onAccept` has no equivalent guard — it relies entirely on two incidental protections instead of an explicit invariant check on `_filled[commitment]`:

1. ISMP's one-time request delivery/receipt semantics (a given request commitment is only supposed to be delivered once), and
2. The escrow-balance check inside `_withdraw`, which reverts with `UnknownOrder` only when `_orders[commitment][token] == 0` for a **non-zero-amount** token: [2](#0-1) 

The per-token loop explicitly skips the balance check whenever a token entry's `amount == 0`:
```solidity
if (amount == 0) continue;
```
Since `body.tokens` is always `order.inputs` — a field fully controlled by the order's creator at placement time, with no validation that all entries are non-zero — an order can be constructed where the escrow-balance check that is the *only* remaining backstop against a second finalize call never fires for one or more "input" entries. In that case, a second (stale, duplicated, or maliciously re-dispatched) `RedeemEscrow`/`RefundEscrow` message for an already-settled commitment reaches `_withdraw` with `finalize=true`, which unconditionally:
- overwrites `_filled[body.commitment] = <new beneficiary>` (silently redefining who the protocol considers to have settled the order), and
- unconditionally re-reads and drains `_orders[body.commitment][TRANSACTION_FEES]` to the new beneficiary if it is non-zero, and re-emits `EscrowReleased`/`EscrowRefunded`.

This is architecturally identical to the reported issue: `checkTradeExpiry`/`onAccept` accepts a state transition (`Traded`/`Zombie` → `TradeExpired`/`Settled`) without first asserting the object is still in an eligible pre-settlement status, relying instead on incidental, best-effort guards that a second, contradictory message can bypass.

### Impact Explanation
If the escrow-zero guard is bypassed for the reason above, an attacker- or relayer-controlled duplicate settlement message can re-finalize an already-settled order, redirecting `_filled[commitment]` (the protocol's canonical settlement/beneficiary record used by `isOrderFilled`/`isOrderRefunded` off-chain checks and by `cancelOrder`'s guard) to an address of the attacker's choosing, and can drain any residual `_orders[commitment][TRANSACTION_FEES]` balance to that address — a wrong-beneficiary/double-settlement outcome directly within the bounty's "logic attacks / double-settlement / false state acceptance" category.

### Likelihood Explanation
This is a public-entrypoint path (order creation is fully attacker-controlled; the `onAccept` handler itself only checks `_authenticate` against the registered peer gateway, not against the order's finalize state) and does not require a compromised relayer, prover, or admin — the ordinary intent flow (place → fill/cancel) is sufficient to construct the zero-amount input entry. The main uncertainty is whether Hyperbridge's ISMP delivery guarantees plus `dedup_requests`/receipt uniqueness (seen in `modules/ismp/core/src/handlers/timeout.rs` and `modules/pallets/testsuite`) fully prevent a second delivery of the *same* request commitment in practice; if so, the attacker would need a second, distinct request (e.g., from a second `cancelOrder` call racing a fill, or a relayer re-submission bug) to trigger the second `onAccept` invocation. I was not able to fully verify from local code whether such a second distinct message for the same order commitment is reachable end-to-end (e.g., via `_cancelFromDest` being callable again after a fill if `_filled` were not checked at that layer — but that check *is* present in `cancelOrder`, so the destination-side origin of a second message is currently blocked). The core, concretely verified defect is the missing invariant check in `onAccept`/`_withdraw`; the full exploit chain to a second real message depends on whether any other path (e.g., a second GET-based source cancellation replay, or a message resubmission bug in the relayer) can produce a second finalize-triggering message for the same commitment, which I could not fully confirm.

### Recommendation
Add an explicit guard in `onAccept` (and in `onGetResponse`) mirroring `cancelOrder()`'s check, e.g. `require(_filled[body.commitment] == address(0), "Filled");` before invoking `_withdraw(..., finalize: true)`, so that `_filled` transitions are enforced at the point of finalization itself rather than relying on the incidental combination of ISMP delivery uniqueness and the escrow-loop's `amount == 0` skip. Additionally, either reject zero-amount entries in `order.inputs` at `placeOrder` time, or make the escrow check in `_withdraw` unconditional (checked once per commitment rather than per non-zero token) so a crafted order cannot suppress the only remaining state-transition guard.

### Proof of Concept
1. User places a cross-chain order whose `order.inputs` includes at least one entry with `amount == 0` alongside a normal, real-value input token (or, in the degenerate case, an order whose only "value" is the Hyperbridge relayer fee accumulated in `_orders[commitment][TRANSACTION_FEES]`).
2. The order is legitimately filled: `_fillCrossChain` on the destination sets `_filled[commitment] = solver` and dispatches `RedeemEscrow`; `onAccept` on the source processes it, calling `_withdraw(body, false, true)`, which sets `_filled[commitment] = solver`, releases the real (non-zero) input token(s), and drains any then-current `TRANSACTION_FEES` balance to `solver`.
3. A second `RedeemEscrow`/`RefundEscrow` message referencing the same commitment (obtained via message re-delivery, a relayer bug, or any path that produces a duplicate deliverable request for the same commitment) is processed by `onAccept` again.
4. Inside `_withdraw`, the loop over `body.tokens` hits `continue` for the zero-amount entry and never reaches the `escrowed == 0` revert check for that entry; if this is the only entry actually iterated (or if any residual `TRANSACTION_FEES` has been re-populated in the interim, e.g. via a relayer paying `order.fees` again), the call does not revert.
5. `_filled[commitment]` is overwritten with the second message's beneficiary, and any non-zero `_orders[commitment][TRANSACTION_FEES]` is transferred to that beneficiary and the wrong `EscrowReleased`/`EscrowRefunded` event is emitted — a double-settlement/wrong-beneficiary outcome for an order that should already be immutably finalized.     function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
