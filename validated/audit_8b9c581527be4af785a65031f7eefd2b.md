### Title
`SignableTransaction::new` allows payments to unspendable Bitcoin outputs - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` accepts caller-controlled payment outputs as arbitrary `ScriptBuf` values and only validates that their amounts meet the dust threshold. A caller can therefore create a transaction containing a positive-value `OP_RETURN` or otherwise provably unspendable output, permanently burning the transferred bitcoin.

### Finding Description
`SignableTransaction::new` receives `payments` as `&[(ScriptBuf, u64)]`. The only validation applied to each payment is `amount >= DUST`; the destination script itself is never checked for spendability or conformance to a supported address type. Each supplied script is then copied directly into a transaction output.

The function handles the intentional `data` argument safely by creating an `OP_RETURN` output with `Amount::ZERO`, but it does not prevent the same unspendable script pattern from being supplied through `payments` with a positive amount.

Relevant flow:

```rust
pub fn new(
  mut inputs: Vec<ReceivedOutput>,
  payments: &[(ScriptBuf, u64)],
  change: Option<ScriptBuf>,
  data: Option<Vec<u8>>,
  fee_per_vbyte: u64,
) -> Result<SignableTransaction, TransactionError> {
  for (_, amount) in payments {
    if *amount < DUST {
      Err(TransactionError::DustPayment)?;
    }
  }

  let mut tx_outs = payments
    .iter()
    .map(|payment| TxOut {
      value: Amount::from_sat(payment.1),
      script_pubkey: payment.0.clone(),
    })
    .collect::<Vec<_>>();
}
```

A payment script such as `OP_RETURN <data>` is consensus-valid but can never be spent. The returned `SignableTransaction` can subsequently be signed normally, causing the assigned amount to become permanently inaccessible.

### Impact Explanation
Any funds assigned to an unspendable payment output are irrevocably burned once the transaction is signed and confirmed. This is analogous to allowing a zero-address reward receiver: the API permits a destination encoding for which no private key or valid spending witness can exist.

The issue is particularly dangerous for withdrawal/payment construction because `payments` is attacker- or user-controlled transaction data, while `SignableTransaction` presents the result as a valid transaction ready for signing.

### Likelihood Explanation
The bug is reachable by any caller able to control a payment destination passed to `SignableTransaction::new`. No malformed encoding, cryptographic assumption, race, or miner cooperation is required. Supplying a standard `OP_RETURN` script with a positive amount is sufficient.

### Recommendation
Validate every payment and change script before constructing the transaction. At minimum:

- Reject `script_pubkey.is_op_return()` and other provably unspendable scripts for positive-value payments.
- Restrict payment scripts to the supported spendable address forms, such as P2PKH, P2SH, P2WPKH, P2WSH, and P2TR.
- Prefer accepting a typed Bitcoin address rather than a raw `ScriptBuf`.
- Continue allowing an `OP_RETURN` only through the dedicated `data` parameter, where the value is fixed to zero.
- Apply equivalent validation to the optional `change` script.

### Proof of Concept
The following conceptual code creates a positive-value payment to an unspendable `OP_RETURN` output:

```rust
use bitcoin::{
  script::{PushBytesBuf, ScriptBuf},
  Amount,
};

let input = scanner.scan_transaction(&funding_tx).remove(0);
let input_value = input.value();

let burn_amount = 10_000;
let fee_per_vbyte = 10;

let unspendable_payment = ScriptBuf::new_op_return(
  PushBytesBuf::try_from(b"burn".to_vec()).unwrap(),
);

let signable = SignableTransaction::new(
  vec![input],
  &[(unspendable_payment.clone(), burn_amount)],
  None,
  None,
  fee_per_vbyte,
).unwrap();

assert_eq!(
  signable.tx.output[0].script_pubkey,
  unspendable_payment,
);
assert_eq!(
  signable.tx.output[0].value,
  Amount::from_sat(burn_amount),
);
assert!(signable.tx.output[0].script_pubkey.is_op_return());
```

`SignableTransaction::new` accepts this output even though no Bitcoin script execution can spend an `OP_RETURN` output. Signing and broadcasting the transaction permanently destroys `burn_amount` satoshis.
