### Title
VerifyBlame passes `accuser`/`accused` in swapped order to `BlameMachine::blame`, causing every valid blame report to fatally blame the honest accuser and exonerate the faulty sender - (File: processor/src/key_gen.rs)

### Summary
`CoordinatorMessage::VerifyBlame` is supposed to verify a PedPoP blame statement identifying which of two parties was faulty in the DKG. The processor calls `AdditionalBlameMachine::blame(accuser, accused, share, blame)` at processor/src/key_gen.rs:549 and :556, but `BlameMachine::blame`/`blame_internal` is defined as `blame(sender, recipient, msg, proof)` (crypto/dkg/pedpop/src/lib.rs:575-629), where `sender` must be the party that *sent* the accused share (the `accused`) and `recipient` must be the party that received and decrypted it (the `accuser`). The processor passes them inverted. As a result, `blame_internal` is executed with `sender = accuser` and `recipient = accused`, and the only possible verdicts are `accuser` (PoP signature fails) or `accused` (only when the proof decrypts a *valid* share under the *accused's* encryption key — unreachable for a legitimately generated proof). Every real accusation therefore resolves to `Blame { participant: accuser }`.

### Finding Description
`blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609) evaluates blame in this order:

1. `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` — inside, `msg.pop.verify(msg.key, pop_challenge::<C>(context, msg.pop.R, msg.key, from, msg.msg))` (crypto/dkg/pedpop/src/encryption.rs:374-379). The PoP `SchnorrSignature` challenge binds the message to `from`, i.e., the participant who created the `EncryptedMessage`. When the processor calls `blame(accuser, accused, ...)`, `from` is bound to the *accuser*, while the share message was signed by the *accused*. Any authentically-produced share message (which is what the accuser relays) therefore fails `pop.verify` → `DecryptionError::InvalidSignature` → `blame_internal` returns `sender`, which under the swapped call is the **accuser**.
2. Even if the PoP check were bypassed, the DLEq is verified against `self.enc_keys[&decryptor]` — with the swap, the *accused's* encryption public key (encryption.rs:383-390) — while the accuser's `EncryptionKeyProof` was produced for the accuser's `enc_key`/`enc_pub_key` (encryption.rs:487-499). No legitimate proof can satisfy this, so `InvalidProof` returns `recipient` = the accused only for proofs that were actually valid for a different binding — which cannot happen.

Back in key_gen.rs:559-563, the code blames `accused` if either verdict equals `accused`, otherwise blames `accuser`. Since the swapped call can only return `accuser` (InvalidSignature) or — for a false accusation that would otherwise correctly return `recipient` — an `accused` verdict only when the *accused* is proven honest under their own key (impossible since the decryptor binding is wrong), the outcome is: **the accuser is blamed in every reachable case**.

This is a verifier-formula/attribution error: the on-chain blame arbitration returns the wrong party for 100% of accusations, including the `blame: None` path for malformed ciphertexts (a `None` proof yields `InvalidProof` → returns `recipient` = `accused` — wait, only reached if the PoP passes, which it cannot; the PoP failure dominates and returns `accuser`).

### Impact Explanation
Blame resolution is how Serai decides who is "fatally slashed" after a DKG fault (see the comment at key_gen.rs:535-537: "this being called means *someone* is getting fatally slashed"). A malicious validator can send a corrupt secret share to an honest participant during key generation. The honest participant emits `ProcessorMessage::InvalidShare { accuser: self, faulty: attacker, blame }` (key_gen.rs:420-425). When the network arbitrates via `VerifyBlame`, the swapped arguments force the verdict onto the **honest accuser**, who is fatally slashed, while the malicious sender escapes attribution entirely and can repeat the attack across attempts. This both confiscates honest validators' stake and makes DKG fault-attribution completely ineffective — an unprivileged DKG participant reaches this purely by sending malformed `EncryptedMessage<SecretShare>` bytes and waiting for the victim to accuse them.

### Likelihood Explanation
Certain, not probabilistic: the argument order is inverted unconditionally in both `AdditionalBlameMachine::new(...).blame(accuser, accused, ...)` invocations (key_gen.rs:549, 556). `blame_internal`'s first check — the per-message PoP `SchnorrSignature` whose challenge transcript includes `from` (encryption.rs:374-377, and `pop_challenge` binds `from` at signing time in `encrypt`, encryption.rs:161-165) — fails for every honestly relayed share because `from` is bound to the wrong participant. Any `InvalidShare` report during any DKG triggers it; DKG faults are a normal occurrence the blame path was built for.

### Recommendation
Swap the arguments so the sender of the accused message is first:

```rust
.blame(accused, accuser, substrate_share, substrate_blame);
.blame(accused, accuser, network_share, network_blame);
```

in processor/src/key_gen.rs:549 and :556. Optionally, rename the parameters of `BlameMachine::blame`/`blame_internal`/`AdditionalBlameMachine::blame` in crypto/dkg/pedpop/src/lib.rs from `(sender, recipient)` to `(accused, accuser)` (or add doc-comments making the order explicit) to prevent recurrence, and add a processor-level test asserting `VerifyBlame` blames `accused` for a corrupted share and `accuser` for a false accusation — mirroring `invalid_share_value_blame`/`invalid_ecdh_blame` in crypto/dkg/pedpop/src/tests.rs but exercising the coordinator message handler.

### Proof of Concept
1. Run the PedPoP DKG (as in `commit_enc_keys_and_shares`, crypto/dkg/pedpop/src/tests.rs).
2. Participant `A` (malicious) sends participant `B` a share message `m` with a corrupted ciphertext or an invalid scalar (e.g., via `invalidate_msg`/`invalidate_share_value`).
3. `B`'s `KeyMachine::calculate_share` returns `PedPoPError::InvalidShare { participant: A, blame: Some(proof) }` (lib.rs:493-499), and `B` reports `InvalidShare { accuser: B, faulty: A, blame }` (key_gen.rs:420-425).
4. On `CoordinatorMessage::VerifyBlame { accuser: B, accused: A, share: m, blame }`, the processor executes `AdditionalBlameMachine::blame(B, A, m, proof)`.
5. Inside `decrypt_with_proof`, `pop_challenge(context, m.pop.R, m.key, from = B, msg)` is verified against a PoP that `A` signed with `from = A` — verification fails, `Err(InvalidSignature)`, and `blame_internal` returns `sender = B` (lib.rs:583-585).
6. key_gen.rs:559-563 concludes `Blame { participant: B }` — the honest accuser is fatally slashed and `A`, who sent the invalid share, is exonerated.

This holds even though `proof` is a perfectly valid `EncryptionKeyProof`: the swapped `decryptor` binding (encryption.rs:388 uses `enc_keys[&accused]` instead of `enc_keys[&accuser]`) guarantees no legitimate accusation can ever resolve against the accused.
