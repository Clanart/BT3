### Title
Integer overflow in transaction accounting allows signing an underfunded transaction - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` uses unchecked `u64` summation, multiplication, and addition when calculating total inputs, total payments, and required fees. [1](#0-0) [2](#0-1)  An attacker who can influence requested payment amounts can make `payment_sat + needed_fee` wrap below the available input total in builds without overflow checks, bypassing the `NotEnoughFunds` check. [3](#0-2)  The resulting underfunded transaction is still returned, passed into FROST signing machines, and each input is signed. [4](#0-3) [5](#0-4) 

### Finding Description
The constructor sums untrusted input and payment amounts with `sum::<u64>()`, without bounding the totals to `u64::MAX` or Bitcoin’s maximum money supply. [1](#0-0)  It then calculates `needed_fee` using unchecked multiplication and performs the solvency test with unchecked `payment_sat + needed_fee`. [2](#0-1)  If `payment_sat` alone wraps, or if `payment_sat + needed_fee` wraps, the comparison can evaluate as though the outputs are affordable even though the encoded transaction spends far more than the inputs. [3](#0-2)  The change path repeats the same unchecked addition inside `checked_sub`, so wrapping `payment_sat + fee_with_change` can also produce an artificial change value. [6](#0-5) 

### Impact Explanation
This causes the threshold signing flow to sign a transaction whose Taproot sighashes commit to an output set violating the wallet’s invariant that inputs cover payments plus fees. [5](#0-4)  The completed machine attaches valid Schnorr signatures to that malformed transaction, producing an unintended signed transaction rather than rejecting it during construction. [7](#0-6)  Because Bitcoin consensus will reject outputs exceeding the money supply or spending more than the referenced inputs, the direct impact is a validly signed but non-broadcastable transaction and failure of the wallet’s accounting/safety boundary. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
The vulnerable path is reachable through the public `SignableTransaction::new` API using attacker-influenced `(ScriptBuf, u64)` payment entries. [10](#0-9)  Exploitation requires a service to place attacker-controlled payment amounts in the transaction and to build without integer-overflow checks; debug builds will panic instead of producing the malformed transaction. [11](#0-10)  No malicious validator, leaked key, invalid curve input, or colluding signer is required because the arithmetic flaw occurs before signing. [12](#0-11) 

### Recommendation
Use checked arithmetic for every monetary total and retain explicit Bitcoin maximum-money validation. [1](#0-0)  In particular, replace the sums and products with `try_fold`/`checked_add`/`checked_mul`, compare using `input_sat < payment_sat.saturating_add(needed_fee)` or a checked equivalent, and reject each output and aggregate output amount above Bitcoin’s consensus maximum. [13](#0-12)  Also change `fee()` to use checked subtraction so a malformed or overflowed `SignableTransaction` cannot silently wrap to a large fee value. [14](#0-13) 

### Proof of Concept
In a build without overflow checks, select two payments whose sum is congruent modulo `2^64` to `input_sat - needed_fee`, while individually remaining at or above the dust threshold. [15](#0-14)  For example, with `input_sat = 1_000_000` and `needed_fee = 1_000`, use payment amounts `u64::MAX - 499_000` and `1_498_000`, whose sum wraps to `999_000`. [16](#0-15)  The check evaluates `1_000_000 < 999_000 + 1_000` as false, so construction succeeds even though the serialized outputs request approximately `2^64` satoshis. [3](#0-2)  Calling `multisig`, `preprocess`, `sign`, and `complete` then produces Schnorr witnesses committing to those exact outputs through `taproot_key_spend_signature_hash`. [17](#0-16) [5](#0-4) [7](#0-6)
