### Title
Unauthenticated `OP_RETURN` operator attribution lets any funder-of-record steal payout credit for another operator — ([File: `core/src/verifier.rs`])

### Summary
`update_finalized_payouts` attributes a payout's `payout_payer_operator_xonly_pk` purely from the raw bytes of whichever transaction happens to be confirmed spending the tracked `withdrawal_utxo`, with zero cryptographic binding between the OP_RETURN pubkey and whoever actually contributed the funding inputs. Because the user's authorization signature is `SinglePlusAnyoneCanPay`, it only commits to input 0 and output 0, so any party (not just the intended operator) can copy that input/witness/output0, add their own funding inputs, insert an arbitrary operator's xonly pubkey into a new OP_RETURN output, and win the race to get it confirmed — causing the DB, and subsequently that operator's own automation, to credit a reimbursement to an operator that never funded or broadcast anything.

### Finding Description
The binding the system relies on is:
`payout_payer_operator_xonly_pk == xonly_pk of the party whose transaction actually funded/paid output 0`

In reality the code only guarantees:
`payout_payer_operator_xonly_pk == whatever bytes appear in the OP_RETURN of the confirmed transaction that spends withdrawal_utxo`

The relevant path:
- `create_payout_txhandler` builds the payout tx with input 0 = user's withdrawal UTXO (`SpendPath::KeySpend`, signed with the user's `SinglePlusAnyoneCanPay` signature covering only input 0 + output 0), output 0 = user payout, output 2 = OP_RETURN with `operator_xonly_pk` [1](#0-0) .
- `calculate_pubkey_spend_sighash`/`calculate_sighash_txin` computes `Prevouts::One` for `SinglePlusAnyoneCanPay`, confirming the signature only binds input 0's prevout and (via SIGHASH_SINGLE) output 0 — nothing else in the transaction, including the OP_RETURN output, is committed by the user's signature [2](#0-1) .
- `get_payout_txs_for_withdrawal_utxos` finds the payout txid purely by joining on which confirmed transaction spent the tracked `withdrawal_utxo_txid`/`withdrawal_utxo_vout` — i.e. whichever transaction wins the race to spend that specific outpoint [3](#0-2) .
- `update_finalized_payouts` then parses the first OP_RETURN of that confirmed transaction and stores its bytes as `operator_xonly_pk` with no check that the signer/funder of the extra inputs corresponds to this pubkey [4](#0-3) .
- `is_kickoff_malicious` only checks that the OP_RETURN pubkey equals the kickoff's operator pubkey — it never validates that the operator who owns that pubkey actually contributed the payout funding [5](#0-4) .
- `PayoutCheckerTask::run_once` blindly trusts `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and proceeds straight to `handle_finalized_payout`/`mark_payout_handled` [6](#0-5) .

Exploit flow: honest operator B constructs and broadcasts a fully-funded payout tx (input 0 = withdrawal UTXO + user's signature, output 0 = user payout, extra funding inputs signed by B, OP_RETURN = B's pubkey). Before it confirms, an unprivileged attacker observes the broadcast (mempool-visible), copies input 0 (with its reusable `SinglePlusAnyoneCanPay` witness) and output 0, discards B's funding inputs/OP_RETURN (which the attacker cannot reuse since they're signed with a different sighash and would require B's key to preserve), and constructs a competing transaction: same input 0/output 0, attacker's own funding inputs (attacker pays real BTC + fees) to cover output 0, and a new OP_RETURN containing operator A's xonly pubkey. If this attacker transaction confirms first (a normal same-UTXO confirmation race, no hashrate majority or protocol violation needed), `update_finalized_payouts` records `payout_payer_operator_xonly_pk = A`. Operator A's own `PayoutCheckerTask` then legitimately (from A's code's perspective) treats this as its own unhandled payout, calls `handle_finalized_payout`, builds and sends its Kickoff, and eventually claims a Reimburse — crediting A for a payout A never funded, signed, or broadcast. B's original transaction, having lost the confirmation race, never gets accepted, and B can never obtain credit for that withdrawal index.

No existing guard (`is_kickoff_malicious`, `SECP.verify_schnorr` on the user's signature, or the DB schema) checks that the OP_RETURN's pubkey corresponds to the party who supplied the transaction's additional funding inputs — the attribution is purely self-declared plaintext in a transaction output not covered by any signature.

### Impact Explanation
This matches the Critical category "an operator reimbursed for a payout it never funded": operator A's collateral/round funds are used to claim a Reimburse output from the move-to-vault UTXO for a withdrawal A did not fund, while the actual funder (the attacker) receives no credit and B, who genuinely attempted to front the payout, is permanently unable to claim reimbursement for that withdrawal index since it is already marked handled/spent. This is repeatable across any withdrawal for which a `SinglePlusAnyoneCanPay`-signed payout transaction is broadcast but not yet confirmed, and across any pair of operators, since the root cause (unauthenticated OP_RETURN attribution field) is systemic rather than instance-specific.

### Likelihood Explanation
The attacker needs no privileged role — only the ability to observe a broadcast/mempool transaction, construct a competing transaction reusing the copyable `SinglePlusAnyoneCanPay` witness, fund output 0 from their own wallet, and get it mined ahead of the original (a standard fee-race, not a hash-power or consensus attack). The economic cost to the attacker is real: they must front the full withdrawal amount plus fees, so this only makes practical sense as a deliberate griefing/wrong-attribution move (e.g., to sabotage operator B and gift unearned credit to A, or as a demonstration), not as a profit-seeking attack for the attacker themselves. Nonetheless it is fully reproducible with a `cargo test` harness and does not require any privileged role, mainnet, or live Citrea.

### Recommendation
Bind the OP_RETURN operator attribution to the party who actually supplied the payout transaction's funding, e.g., by requiring the operator to sign a commitment (e.g. via `ANYONECANPAY`-safe extra output/witness or an aggregated N-of-N-verifiable claim) that provably ties the funding inputs to the claimed `operator_xonly_pk`, rather than trusting free-form OP_RETURN bytes on a transaction whose signature does not cover those bytes at all.

### Proof of Concept
1. In a `cargo test` two-operator harness (A, B configured with distinct xonly pubkeys), fund a withdrawal on Citrea and have B build+sign a fully funded `Payout` tx (input 0 = withdrawal UTXO with user's `SinglePlusAnyoneCanPay` signature, extra inputs from B's wallet, OP_RETURN = B's pubkey) but not yet broadcast it.
2. Have the test harness (as an "attacker") construct a second transaction: same input 0 (with the same witness copied from B's constructed tx) and same output 0, but with new attacker-funded inputs and OP_RETURN = A's `operator_xonly_pk`.
3. Broadcast the attacker's transaction first and mine it; then attempt to broadcast B's transaction and confirm it fails (double-spend).
4. Assert, after the block syncer processes the block, that `get_payout_info_from_move_txid` / `withdrawals.payout_payer_operator_xonly_pk` equals A's pubkey (`payout_payer_operator_xonly_pk == A`, not B), even though B never funded output 0.
5. Run A's `PayoutCheckerTask::run_once` and assert it returns `Ok(true)`, having called `handle_finalized_payout` and `mark_payout_handled` for that withdrawal index — confirming A is credited for a payout it never funded, while B's payout is never marked handled.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()

    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
