## Finding: CR-CAT `authorized_providers` list is not validated to be non-empty, permanently freezing minted assets

### Title
Missing validation of `authorized_providers` in `CRCAT.launch()` / `construct_cr_layer()` allows minting Credential-Restricted CATs that can never be spent - ([File: chia/wallet/vc_wallet/cr_cat_drivers.py])

### Summary
The reported Solidity bug is that `Timelock::constructor()` accepts an `admin` parameter without checking it is non-zero, and once deployed with a zero admin the contract becomes permanently non-functional because every privileged function gates on `msg.sender == admin`. The analogous Chia pattern is a CR-CAT (Credential Restricted CAT), whose spendability is entirely gated on a coin owner producing a proof from a provider contained in a curried, immutable `authorized_providers` list. Just like the zero admin bricking the Timelock, an empty (or otherwise unauthorizable) `authorized_providers` list bricks the CR-CAT permanently, because the list is baked into the puzzle hash at launch time and can never be updated afterward.

### Finding Description
`construct_cr_layer()` curries `authorized_providers` directly into the `CREDENTIAL_RESTRICTION` puzzle with no validation that the list is non-empty or contains reachable/legitimate provider identities: [1](#0-0) 

`CRCAT.launch()`, the entry point used to mint a new CR-CAT from an XCH coin, forwards `authorized_providers` straight into `construct_cr_layer()` and the eve spend's remark condition, again with zero validation: [2](#0-1) 

On the wallet side, `CRCATWallet.get_or_create_wallet_for_cat()` (invoked both when creating a new CR-CAT wallet and when reconstructing one `create_from_puzzle_info`) only checks that the parameter is not `None`, never that the list is non-empty: [3](#0-2) 

Because `authorized_providers` is curried into the puzzle (hence the puzzle hash / coin identity) at launch time, it is immutable for the life of that CR-CAT lineage — there is no "admin update" mechanism, mirroring the Timelock where `admin` is set once in the constructor and used forever after via `if msg.sender != admin`. Once a coin of this asset type exists on-chain with an empty (or unreachable) provider list, spending logic (`CRCATWallet.claim_pending_approval_balance`, `VCWallet.add_vc_authorization`) can never find a valid VC to authorize the spend, since they explicitly search `self.info.authorized_providers` / `crcat_spend.crcat.authorized_providers` for a matching VC: [4](#0-3) [5](#0-4) 

If `authorized_providers` is empty, `get_vc_records_by_providers(crcat_spend.crcat.authorized_providers)` (called with an empty list) can never return a matching VC, and the code explicitly raises rather than proceeding — the transaction-processing path for that coin halts permanently. This is reachable by any unprivileged wallet user who mints a CR-CAT (via a spend bundle they build/submit) supplying an empty or bogus `authorized_providers` list — no special privilege needed, exactly analogous to any deployer being able to pass a zero `admin` to `Timelock`.

### Impact Explanation
Any funds sent into a CR-CAT minted with an empty/unreachable `authorized_providers` list become permanently unspendable — a spend-triggered transaction-processing halt for that asset. This is a concrete, irreversible loss-of-funds condition for whoever owns coins of that asset type (self-inflicted misconfiguration is the most direct route, but nothing in the code prevents a malicious minter from advertising the asset to counterparties in an offer, where the taker would only discover after settlement that the received CR-CATs can never move again).

### Likelihood Explanation
Medium: this requires either an honest mistake (passing an empty list, a common "no restriction" default elsewhere in the code) or a malicious minter deliberately building a CR-CAT with an unreachable provider set. There is no validation anywhere in `construct_cr_layer`, `CRCAT.launch`, or `CRCATWallet.get_or_create_wallet_for_cat`/`create_from_puzzle_info` that would catch this before the coin is created on-chain.

### Recommendation
Add validation, analogous to rejecting a zero `admin`, at the points where `authorized_providers` is accepted to construct or launch a CR-CAT:
- In `construct_cr_layer()` / `CRCAT.launch()` in `chia/wallet/vc_wallet/cr_cat_drivers.py`, reject an empty `authorized_providers` list before curry/launch.
- In `CRCATWallet.get_or_create_wallet_for_cat()` / `create_from_puzzle_info()` in `chia/wallet/vc_wallet/cr_cat_wallet.py`, raise a clear error if `authorized_providers` is empty, rather than only checking for `None`.
- Consider warning/blocking wallet UX (e.g., in offer-acceptance flows) when a counterparty-provided CR-CAT's `authorized_providers` set contains no providers the taker has any way of ever obtaining a VC from.

### Proof of Concept
1. Call `CRCAT.launch(origin_coin, payment, tail, tail_solution, authorized_providers=[], proofs_checker)` — no exception is raised (`chia/wallet/vc_wallet/cr_cat_drivers.py:181-222`).
2. The eve spend and resulting `CRCAT` are broadcast and confirmed on-chain with `authorized_providers == []` curried into the puzzle.
3. Any later attempt to move the coin, e.g. via `VCWallet.add_vc_authorization`, calls `get_vc_records_by_providers(crcat_spend.crcat.authorized_providers)` with an empty list, finds zero results, and raises `ValueError("No VC available with provider in [])")` (`chia/wallet/vc_wallet/vc_wallet.py:479-483`), and `CRCATWallet.claim_pending_approval_balance` has the identical failure mode (`chia/wallet/vc_wallet/cr_cat_wallet.py:713-718`).
4. The coin's value is permanently stranded — no future transaction can ever satisfy the CR-CAT's spend requirements.
