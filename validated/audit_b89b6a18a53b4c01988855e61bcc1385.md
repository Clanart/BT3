### Title
`SignableTransaction::new` omits the OP_RETURN output from fee/weight accounting, inflating the change output and underpaying the miner fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report's class is "actual value moved exceeds value deducted from tracked accounting: only the net amount is deducted while a separately-tracked component also leaves the pool." The analog in `bitcoin-serai` is `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`: when a caller supplies `data`, an OP_RETURN `TxOut` is appended to `tx_outs` (lines 194–202), but the transaction weight used to compute `needed_fee` is derived from `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which rebuilds a transaction containing only `payments` (plus optional change) — never the OP_RETURN output (lines 62–99, 204, 225–226). The fee accounting therefore reflects a smaller transaction than the one actually constructed and signed.

### Finding Description
`SignableTransaction::new` builds the real output list `tx_outs` including the OP_RETURN data output, then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) and, if change exists, `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (lines 225–226). `calculate_weight_vbytes` reconstructs a `Transaction` solely from `payments` and `change` (lines 68–99); the `data`/`tx_outs` argument is never threaded in. Consequently `vbytes`/`vbytes_with_change` — and hence `needed_fee`/`fee_with_change` — exclude the OP_RETURN output's ~9 + len(data) bytes (up to ~90 bytes).

The change output is then credited as `value = input_sat - (payment_sat + fee_with_change)` (lines 228–230): because `fee_with_change` is understated, the change output absorbs value that should have been paid as the fee for the OP_RETURN's vbytes. `fee()` (lines 138–141) correctly computes `sum(inputs) - sum(outputs)`, so the transaction "pays" exactly `needed_fee` — i.e., a per-vbyte fee rate below the caller-specified `fee_per_vbyte`, by `fee_per_vbyte * (OP_RETURN output size)`. Additionally, the `TooLowFee` minimum-relay check (line 211) and the `MAX_STANDARD_TX_WEIGHT` check (lines 101, 241) are evaluated against the understated weight, so a transaction can pass `TooLowFee`/`TooLargeTransaction` while the real signed transaction is larger/heavier than accounted.

### Impact Explanation
An unprivileged caller who controls the `data` argument (public input to `SignableTransaction::new`) causes the signing machine to produce a transaction whose effective fee rate is strictly lower than the requested `fee_per_vbyte`, while the change output is credited the difference — the accounting understates the cost of what actually leaves in the transaction, mirroring the reported "tracked balance inflated by the un-deducted component" pattern. For fee rates near relay minimums or large `data` payloads, the signed transaction can fall below the network's effective minimum relay fee or the intended confirmation target, rendering the transaction unconfirmable/mempool-rejected and the spent inputs effectively unspendable until replaced — while `needed_fee()` reports a value never actually achieved per-vbyte. Conversely, a weight-边界 case can produce a transaction exceeding `MAX_STANDARD_TX_WEIGHT` in reality while passing the check.

### Likelihood Explanation
The divergence occurs deterministically on every `SignableTransaction::new` call with `data: Some(_)`, requiring no collusion, no internal state access, and no malformed encodings — only the documented public `data` parameter. Whether it reaches Medium depends on deployment usage of `data` and prevailing fee rates; the miscalculation itself is unconditional and unambiguous in code.

### Recommendation
Pass the OP_RETURN output (or the full `tx_outs` list) into `calculate_weight_vbytes` so `weight`/`vbytes` reflect the transaction actually being built — e.g., compute weight over `tx_outs` after the OP_RETURN push, and for the change path recompute over `payments + OP_RETURN + change`. This makes `needed_fee` cover the real virtual size, so `fee()` equals `fee_per_vbyte * actual_vbytes` and the change output is not inflated by uncharged size.
