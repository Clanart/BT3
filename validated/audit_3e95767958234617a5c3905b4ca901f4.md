### Title
Partial `on_accept` Execution Followed by Receipt Deletion Enables Duplicate Minting on Calldata Decode Failure - (File: `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/ismp/core/src/handlers/request.rs`)

### Summary
`HftError::CalldataDecodeError` can be triggered by attacker-controlled `message.data` bytes *after* the token mint/transfer to the beneficiary has already been executed. Because the ISMP core request handler stores the request receipt **before** invoking the module's `on_accept`, and only deletes that receipt when `on_accept` returns an `Err` (to permit timeout processing), a message with a valid transfer body but malformed `SubstrateCalldata` causes: (1) funds minted/transferred to the beneficiary, (2) an `Err` returned due to calldata decode failure, (3) the request receipt deleted by the core handler. This clears the duplicate-request guard for that exact commitment, letting the same request be resubmitted (with the same still-valid source-chain proof) and reprocessed, repeating the mint/transfer each time.

### Finding Description
In `modules/pallets/hyper-fungible-token/src/module.rs`, `on_accept` performs the asset mint/transfer at lines 93-117 **before** attempting to decode the optional calldata at lines 120-122: [1](#0-0) 

If `message.data` is non-empty but does not decode as `SubstrateCalldata`, the function returns `Err(HftError::CalldataDecodeError(...))` *after* the mint/transfer already succeeded and was applied to storage.

In `modules/ismp/core/src/handlers/request.rs`, the request receipt is stored **before** the module callback runs, and only deleted if the callback errors, explicitly to allow the request to be timed out: [2](#0-1) 

The overall `handle()` function does not propagate this per-request error as a failure of the whole extrinsic — it maps each request's outcome (`Ok`/`Err`) into a `MessageResult::Request` events vector and returns `Ok(...)` regardless: [3](#0-2) 

Because the extrinsic as a whole succeeds, any storage mutations already committed inside `on_accept` (the asset mint/transfer to the beneficiary) are not rolled back by FRAME's default transactional dispatch machinery — that mechanism only reverts storage on failure of the *entire* dispatched call, not on an inner per-request `Err` that is caught and converted to an event. The receipt for that specific request commitment is deleted, clearing the `host.request_receipt(&req).is_some()` duplicate-guard checked earlier at line 58, so the same request (same commitment, same source-chain proof) is no longer recognized as already processed. Since it's the same commitment/message that already exists on the source chain, it can be relayed again (relaying is a permissionless action) and, since the calldata is deterministically malformed, this failure/mint/delete cycle can repeat, producing unbounded duplicate minting for a single escrowed transfer.

This breaks the "one-time settlement per request commitment" invariant called out in the review's Hyperbridge Pivots: request/response/timeout paths must bind commitment uniqueness and one-time receipt handling.

### Impact Explanation
Unauthorized, unbounded duplicate minting/transfer of bridged funds to an attacker-chosen beneficiary is one of the most severe classes of bridge bugs (direct loss of funds from custody/treasury), matching the bounty's "stealing or loss of funds" and "duplicate settlement" impact categories.

### Likelihood Explanation
The precondition is simple and fully attacker-controlled: register/use an already-mapped `ContractToAsset` asset (a normal bridged asset, not privileged), and craft the transfer message with a valid `amount`/`to` but garbage bytes in the optional `data` field. No privileged role, malicious relayer, or malicious node is required — the message is only relayed with a standard valid source-chain membership proof, which is the normal/expected relaying flow.

### Recommendation
Perform calldata decoding/validation of `message.data` **before** executing the mint/transfer, so that any failure occurs prior to mutating balances. Alternatively, wrap the entire `on_accept` module callback in an explicit `frame_support::storage::with_transaction` (or equivalent transactional storage layer) in `modules/ismp/core/src/handlers/request.rs` so that any `Err` returned by the callback atomically rolls back all storage changes made during that callback before the receipt is deleted, guaranteeing that receipt deletion only ever corresponds to a fully no-op callback.

### Proof of Concept
1. Register an asset in `ContractToAsset` for source chain/contract, configure `Precisions`.
2. Construct a `Message` with a valid `to`/`amount` (mints funds) but `data` set to bytes that fail `SubstrateCalldata::decode`.
3. Call `on_accept` directly (or via the full `handle()` path) — observe the beneficiary balance increases (mint/transfer at lines 93-117 succeeds) while the function ultimately returns `Err(HftError::CalldataDecodeError)`.
4. In the `handle()` request path, observe `host.delete_request_receipt(&wrapped_req)` executes because `res.is_err()`.
5. Resubmit the identical `RequestMessage` (same commitment, same/refreshed proof) — `host.request_receipt(&req).is_some()` is now `false`, so it passes the duplicate check and `on_accept` executes again, minting the funds a second time to the same beneficiary for what is logically the same escrowed transfer.
