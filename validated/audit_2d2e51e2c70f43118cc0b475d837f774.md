### Title
Unchecked balance deduction `amount.0 -= 2 * COST_TO_AGGREGATE` credits instructions with more value than received — (File: processor/src/multisigs/mod.rs)

### Summary
Analog to fee-on-transfer accounting bugs (credited amount ≠ actually received amount): in `processor/src/multisigs/mod.rs`, `instruction_from_output` blindly decrements the scanned output's balance by `2 * N::COST_TO_AGGREGATE` without verifying the output actually carried enough value to cover that deduction. The resulting `InInstructionWithBalance` is then reported to the chain as having a `balance` derived from a subtraction performed on an unchecked input — the same "trusted declared value rather than actual received value" flaw as the Allo report.

### Finding Description
`instruction_from_output` (processor/src/multisigs/mod.rs:84-92) takes any scanned `Output` of `OutputType::External`, decodes the shorthand, and unconditionally executes `balance.amount.0 -= 2 * N::COST_TO_AGGREGATE`. The balance is taken directly from `output.balance()` (`Amount(self.output.value())`, processor/src/networks/bitcoin.rs:128-130). The upstream filter in `processor/src/multisigs/scanner.rs:564` only requires `output.balance().amount.0 >= N::DUST`. If `N::DUST < 2 * N::COST_TO_AGGREGATE`, an attacker sending an external output with a value in `[DUST, 2*COST_TO_AGGREGATE)` triggers a u64 underflow: panic in debug builds (DoS of the processor), or a wrapped, astronomically-large `amount` in release builds, causing the runtime to credit a `Balance` vastly exceeding the BTC actually received — "funds reported received that are not spendable," and value not backed by the transfer.

I was unable to confirm the exact values of `N::DUST` and `N::COST_TO_AGGREGATE` for `Bitcoin` in the indexed snippet of `processor/src/networks/mod.rs` / `bitcoin.rs`, so whether the underflow is reachable depends on `DUST < 2 * COST_TO_AGGREGATE`. Even if the constants currently prevent underflow, the second leg of the analog stands independently at processor/src/multisigs/mod.rs:883-884: when forwarding, `instruction.balance.amount.0 -= tx.0.fee()` rewrites the instruction's balance to the post-fee amount but `ForwardedOutputDb::save_forwarded_output` records the instruction whose amount was decremented under an assumed fee — if the actual created output differs (dropped/dust-adjusted output, fee drift between `prepare_send` simulation and mining), the on-chain credited amount diverges from what was actually moved, mirroring the "deducted wrong values from underlying state variables" root cause.

### Impact Explanation
A wrapped or mismatched `balance.amount` causes Serai's Substrate runtime to mint/credit liquidity against BTC that was never received, draining pool value; alternately, a debug-panic halts the processor's multisig pipeline (availability loss of the whole bridge).

### Likelihood Explanation
Reachable by any unprivileged party who sends a Bitcoin transaction to a Serai multisig address with an attached instruction shorthand — purely public on-chain input.

### Recommendation
Use `checked_sub`/`saturating_sub` (or reject outputs below `2 * COST_TO_AGGREGATE` at scan time) in `instruction_from_output`, and only save forwarded instructions after confirming the created output's actual amount via `created_output`-style post-fee accounting.

### Proof of Concept
Send a P2TR output of value `v` where `N::DUST <= v < 2 * N::COST_TO_AGGREGATE` to the active multisig's Taproot key with OP_RETURN/script data encoding a valid `RefundableInInstruction` shorthand; on scanning, `instruction_from_output` computes `v - 2*COST_TO_AGGREGATE`, underflowing the credited balance.
