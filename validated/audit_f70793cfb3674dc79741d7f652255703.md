### Title
Unbounded attacker-controlled allocation in `ThresholdKeys::read` enables memory-consumption DoS — (File: crypto/dkg/src/lib.rs)

### Summary
The CVE-2013-1753 class is "attacker-controlled size parameter causes disproportionate memory consumption before input is validated." In Serai, `ThresholdKeys::read` deserializes an attacker-supplied `n` (u16) from the wire and immediately performs `Vec::with_capacity(usize::from(n))` and a `HashMap` built over `1 ..= n` entries — allocating and iterating proportionally to a declared length rather than to bytes actually present.

### Finding Description
In `ThresholdKeys::read`, `t`, `n`, and `i` are read directly from the reader with no bound beyond `Participant::new` for `i` [1](#0-0) . When the interpolation byte selects `Interpolation::Constant`, the code executes `Vec::with_capacity(usize::from(n))` — a heap allocation of `n × size_of::<C::F>()` bytes — before reading a single scalar [2](#0-1) . It then unconditionally loops `1 ..= n` calling `read_G` into a `HashMap` [3](#0-2) . Crucially, `ThresholdParams::new(t, n, i)` validation happens only *after* these allocations/reads [4](#0-3) , so a crafted 8-byte prefix (`id_len` + id + `t`/`n`/`i` + interpolation tag `0x00`) forces a `with_capacity(65535)` allocation (~2 MiB for 32-byte scalars) even when the stream ends immediately and `read_F` fails on the first element. The same pattern repeats across other deserialization paths: pedpop `Commitments::read` allocates `Vec::with_capacity(params.t())` from machine params (bounded) [5](#0-4) , but `Transaction::DkgShares::read` allocates `share_quantity × key_share_quantity` inner vectors of attacker-declared `share_len` from u8/u16 fields with no size cap on the product before allocation [6](#0-5) .

### Impact Explanation
An unprivileged party feeding bytes to `ThresholdKeys::read` (explicitly a supported reachability surface for this audit) can trigger repeated large short-lived allocations: each ~8-byte header claims `n = 65535`, producing a ~2 MiB `Vec::with_capacity` plus a 65535-iteration `read_G` loop. Even though the loop fails fast on missing bytes, the capacity reservation and per-call HashMap churn allow an amplification attack that exhausts memory or triggers allocator pressure/OOM in a long-running validator/processor process — directly mirroring the CVE's memory-consumption DoS, which has CVSS A:H.

### Likelihood Explanation
Reachability requires the host to pass untrusted bytes into `ThresholdKeys::read` (e.g., loading key material from RPC-fetched or peer-supplied data). `n` is a u16 so per-request amplification is capped at ~65k×, and the `read_G`/`read_F` failures abort before data-dependent allocation exceeds input in the worst sustained case — but the up-front `with_capacity` and HashMap structure inserts still yield a high amplification-per-byte transient allocation. Medium likelihood: it depends on integrators deserializing untrusted `ThresholdKeys`, but the deserialization ordering defect (allocate-then-validate) is unconditional once reached.

### Recommendation
Validate `ThresholdParams::new(t, n, i)` *before* any allocation or loop in `ThresholdKeys::read`, reject `t > n` / `n == 0` early, and avoid `Vec::with_capacity(n)` — grow the vector while reading so allocated memory never exceeds bytes actually delivered. Apply the same fix to `Transaction::DkgShares::read` by bounding `share_quantity * key_share_quantity * share_len` against `TRANSACTION_SIZE_LIMIT` prior to allocation, as is already done for `DkgCommitments` [7](#0-6) .

### Proof of Concept
```rust
use std::io;
use dkg::{ThresholdKeys, Interpolation}; // crypto/dkg
use ciphersuite::Ciphersuite;

fn poc<C: Ciphersuite>() {
    let mut bytes = Vec::new();
    bytes.extend((C::ID.len() as u32).to_le_bytes());
    bytes.extend(C::ID);
    bytes.extend(1u16.to_le_bytes());       // t = 1
    bytes.extend(u16::MAX.to_le_bytes());   // n = 65535 (attacker-controlled)
    bytes.extend(1u16.to_le_bytes());       // i = 1
    bytes.push(0);                          // Interpolation::Constant
    // Stream ends here; ThresholdKeys::read still performs
    // Vec::with_capacity(65535) and enters a 1..=65535 read_G loop
    let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
}
```
Each invocation of this ~40-byte input forces a multi-megabyte reservation and a 65k-iteration loop; concurrent invocations compound into memory exhaustion.

Caveat: I was unable to inspect `crypto/dkg/pedpop/src/encryption.rs` (`EncryptedMessage::read`) in the available iterations; if it applies a similar length-prefixed allocation to ciphertext payloads, it would be an equivalent or stronger analog worth checking.
