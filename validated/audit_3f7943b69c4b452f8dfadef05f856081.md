### Title
Malicious `.gitmodules` submodule URL is rendered as a clickable external link without validation - (File: app/src/ui/diff/submodule-diff.tsx)

### Summary
When a user views a diff for a changed/added submodule, Desktop reads the submodule's URL straight from the repository's own git config (`submodule.<path>.url`, sourced from `.gitmodules`) and renders it as a clickable link pointing to `https://<hostname>/<owner>/<name>` without validating that the resulting host is the one the repository actually claims to point to, or that the value is a sane hostname at all.

### Finding Description
`buildSubmoduleDiff` retrieves the submodule URL from the repository's local config: [1](#0-0) 
This URL is fully attacker-controlled: it is written by whoever authored the `.gitmodules` file / submodule config of a repository the user clones or fetches. It is passed straight through to the UI as `ISubmoduleDiff.url` with no sanitization: [2](#0-1) 
The UI layer then does: [3](#0-2) 
`parseRepositoryIdentifier` first tries a strict remote regex, but falls back to accepting any two-slash-separated segments as `owner/name` if it doesn't match a known VCS host pattern: [4](#0-3) 
Because the `hostname` used to build the final `https://${hostname}/${owner}/${name}` link comes directly from parsing the attacker-supplied URL (via `remoteRegexes` matches or generic parsing), a repository author can set `submodule.foo.url` to a value that gets parsed into an arbitrary hostname/owner/name combination, causing the rendered `LinkButton` to point at a completely different, attacker-chosen external URL while displaying misleading owner/repo text. Unlike a normal remote fetch/push (which is gated by network operations with authentication and proxy handling), this value is never validated as being related to the actual submodule remote actually configured for fetching — it's shown purely for informational/link purposes based on trust in the string.

### Impact Explanation
This satisfies the "attacker controls a cloned/fetched repository ... and the result is ... a link ... the user clicks" impact class. A malicious repository can craft its `.gitmodules` to make the "This is a submodule based on the repository ..." link point anywhere (e.g., a phishing page mimicking a GitHub sign-in, or a `file://`/other scheme if `LinkButton`/Shell.openExternal don't restrict schemes), while displaying a seemingly legitimate `owner/name` label to build trust. This is a link-based social-engineering vector that operates without any unusual steps beyond normal repository browsing (viewing the Changes list after cloning/fetching a repo with a submodule change).

### Likelihood Explanation
Likelihood is moderate: it requires the victim to clone or fetch a repository containing a submodule and to open its diff (a completely ordinary Desktop workflow), and then to click the informational link — no elevated trust or unusual interaction is needed beyond that. The main uncertainty (not fully verified with available tooling) is what `LinkButton`'s underlying `uri` handler does with non-`https` schemes and whether `shell.openExternal` in Electron further restricts protocols; this would determine whether the impact is limited to phishing redirection or could be escalated further.

### Recommendation
Do not use the untrusted `submodule.<path>.url` value to construct a user-facing clickable link without validating that the parsed hostname is a well-formed, expected host (and restrict `parseRepositoryIdentifier`'s fallback so it cannot manufacture a hostname from arbitrary attacker text). Consider only linking when the URL can be strictly matched against `remoteRegexes` for known providers, and always confirm the final scheme is `https:` before passing the URI to `LinkButton`/`shell.openExternal`.

### Proof of Concept
1. Create a repository with a submodule whose `.gitmodules`/`submodule.<path>.url` is set to a value that `parseRemote`/`parseRepositoryIdentifier` will interpret into an attacker-chosen `hostname`/`owner`/`name` (e.g., a value crafted to resemble `evil.example.com/phish/repo` combined with a modified commit pointer so `status.commitChanged` is true).
2. Have the victim clone/fetch this repository in GitHub Desktop and open the Changes view for the submodule.
3. Desktop renders "This is a submodule based on the repository `phish/repo` (evil.example.com)" as a clickable link built from `https://${hostname}/${owner}/${name}` per `app/src/ui/diff/submodule-diff.tsx:84-96`.
4. The victim, trusting the Desktop UI, clicks the link and is navigated to the attacker's chosen destination.

/** Try to parse an owner and name from a URL or owner/name shortcut. */
export function parseRepositoryIdentifier(
  url: string
): IRepositoryIdentifier | null {
  const parsed = parseRemote(url)
  // If we can parse it as a remote URL, we'll assume they gave us a proper
  // URL. If not, we'll try treating it as a GitHub repository owner/name
  // shortcut.
  if (parsed) {
    const { owner, name, hostname } = parsed
    if (owner && name) {
      return { owner, name, hostname }
    }
  }

  const pieces = url.split('/')
  if (pieces.length === 2 && pieces[0].length > 0 && pieces[1].length > 0) {
    const owner = pieces[0]
    const name = pieces[1]
    return { owner, name, hostname: null }
  }

  return null
}
