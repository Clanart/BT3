### Title
App Proxy signature verification does not validate request `timestamp` freshness, allowing indefinite replay of leaked/intercepted signed proxy requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` verifies that the HMAC `signature` query parameter matches a signature computed over the other query parameters (which include `timestamp`), but it never checks that `timestamp` is recent. This is the same bug class as the referenced oracle report: a signed value (a price round / a signed request) is accepted without checking that it is fresh, so stale/old signed data is treated as if it were current.

### Finding Description
`verify_proxy_request` calls `query_string_valid?(request.query_string)`, which:
1. Parses the query string into a hash.
2. Extracts and removes `signature`.
3. Recomputes the HMAC over the remaining sorted params (which includes `timestamp`) and does a `secure_compare` against the supplied `signature`. [1](#0-0) 

Nowhere in this flow is the `timestamp` parameter's value compared to the current time. Shopify's app-proxy signing scheme embeds a `timestamp` in the signed payload specifically so that a receiving app can reject requests that are too old, but this gem's implementation only proves that the signature is valid for whatever `timestamp` was originally issued — it does not enforce a freshness/staleness window. Once a valid signed app-proxy URL (with its query string) is observed by anyone (e.g., logged in browser history, proxy logs, shared links, browser extensions, network intermediaries), it remains a permanently valid, replayable request against `AppProxyVerification`-protected controllers, since the secret-derived signature never expires and no server-side check tests the age of the request. This mirrors `PriceOracle.getPrice` accepting stale Chainlink round data because it never inspected the round timestamp. [2](#0-1) 

The generated app proxy controller and docs both directly rely on this concern with no additional freshness enforcement layered on top. [3](#0-2) [4](#0-3) 

### Impact Explanation
Any captured/leaked app-proxy signed query string can be replayed forever to reach the app's `AppProxyVerification`-protected endpoints as an authenticated-looking storefront proxy request, even long after the shop context, session, or intended action window has expired. Because `ShopifyApp::AppProxyVerification` is the mechanism apps use to trust that a request truly originated from Shopify's app proxy for a specific shop at a specific time, the missing freshness check undermines that trust guarantee and enables cross-time replay of forged/stolen signed requests. This is a genuine authentication/verification-bypass class weakness, analogous to accepting a stale price feed as current in the referenced report.

### Likelihood Explanation
Exploitation requires obtaining a previously valid signed app-proxy query string (via logs, browser history, referrer leakage, shared/cached URLs, or network capture). This is a realistic threat model since these URLs travel over storefront-embedded requests and can be logged by many intermediate systems (CDNs, browser extensions, proxies, analytics tools). No secret material needs to be compromised — only an old signed URL, which is inherently less sensitive-looking and thus more likely to leak or be retained than a password/token.

### Recommendation
Include an explicit freshness check on the `timestamp` query parameter in `query_string_valid?`/`verify_proxy_request`, rejecting requests whose `timestamp` is older than a configurable tolerance (e.g., a few minutes), similar to Shopify's own guidance for app-proxy signature verification. This closes the indefinite-replay window without requiring any change to how requests are signed.

### Proof of Concept
1. A merchant's storefront customer (or any network intermediary) captures a legitimately signed app-proxy request URL, e.g.:
   `GET /apps/my-app?shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid-sig>`
2. Using the exact same query string, an attacker replays this request at any point in the future (months/years later).
3. `query_string_valid?` recomputes the same HMAC over the same params and it matches `signature`, so `verify_proxy_request` allows the request through unconditionally, exactly as demonstrated by the passing test using a fixed historical `timestamp=1466106083`. [5](#0-4)

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
