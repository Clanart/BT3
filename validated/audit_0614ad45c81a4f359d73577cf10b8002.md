# Q3484: Analysis — Duplicate Signature Amplification in BEEFY Participation-Threshold Check

## Title
Participation Threshold Computed From Raw Signature Count Instead of Unique Authority Indices - (File: modules/consensus/beefy/verifier/src/lib.rs)

## Summary
The BEEFY consensus verifier's supermajority check is evaluated against the raw length of the attacker-supplied `signed_commitment.signatures` array rather than the count of *distinct* authority indices actually proven against the keyset commitment. No code path was found that deduplicates `authority_indices` before (or as part of) the threshold check.

## Finding Description
In `verify_mmr_update_proof` [1](#0-0) , the participation gate is:

```rust
let signatures_length = mmr.signed_commitment.signatures.len();
...
if !check_participation_threshold(signatures_length as u32, authority_set.len) {
    return Err(Error::SuperMajorityRequired);
}
```

`signatures_length` is simply `Vec::len()` on an attacker-controlled `Vec<Signature>` decoded from the unsigned `Message::Consensus` proof submitted through `pallet_ismp::handle_unsigned` [2](#0-1) . Nothing at this point has checked that each signature corresponds to a *distinct* authority.

Only afterward does the code recover each signature's signer and build `authority_indices`/`authority_leaves`, one entry per signature (including duplicates), and pass them into `rs_merkle::MerkleProof::verify` against the keyset commitment: [3](#0-2) 

No sort/dedup/uniqueness assertion is applied to `authority_indices` anywhere in this function, in `verify_mmr_leaf`, or in `verify_parachain_headers` [4](#0-3) . The EVM counterpart (`EcdsaBeefy.sol`) has the identical structure: `sigLen` (raw array length) feeds `checkParticipationThreshold`, and `authorities[i]` is populated per-signature without a uniqueness check before calling `MerkleMultiProof.VerifyProof`. [5](#0-4) 

The unresolved question is whether `rs_merkle::MerkleProof::verify` (and the Solidity `MerkleMultiProof.VerifyProof`) tolerate repeated `(index, hash)` leaf entries and still return `true`. Both are third-party/external library code not present in this repository's index, so I could not directly confirm their exact handling of duplicate indices in a multiproof. If either library treats duplicate `(index, hash)` pairs as consistent (since the hash at a given index is always the same for the same authority), the missing uniqueness check on `authority_indices`/`signatures_length` becomes exploitable: an attacker could take one or a minority of genuine validator signatures over a malicious commitment, duplicate the ECDSA signature entries in the submitted proof to artificially inflate `signatures_length` past `check_participation_threshold`, and thereby get `verify_mmr_update_proof` to accept a BEEFY commitment that was never actually signed by supermajority of the authority set.

## Impact Explanation
If the underlying multiproof verification does not reject duplicate leaf indices, this would let an unprivileged caller of `handle_unsigned` push forged MMR roots / consensus state updates with less than supermajority signer participation, which cascades into false parachain header/state acceptance and, ultimately, unauthorized cross-chain execution — matching the "Critical: false state acceptance" impact class.

## Likelihood Explanation
Uncertain/Medium. It depends entirely on undocumented behavior of the `rs_merkle` crate's multiproof `verify` (and the Solidity equivalent) with duplicate `(index, leaf)` entries, which is not part of this codebase and could not be verified with available tools. Notably: I did not find any test in `modules/consensus/beefy/verifier/src/test.rs` that specifically exercises duplicate-signature/duplicate-index submissions (the existing tests cover stale height, sub-supermajority from named set, and stale MMR leaves, but not duplicated indices), so this exact scenario appears untested in this repo.

## Recommendation
- Add an explicit dedup check: sort `authority_indices`, verify no repeated index, and derive `signatures_length` from the count of *unique* indices (not raw `Vec::len()`) before calling `check_participation_threshold`, in both `modules/consensus/beefy/verifier/src/lib.rs` and `evm/src/consensus/EcdsaBeefy.sol`.
- Add a unit test that submits a proof with N signatures where fewer than the supermajority threshold of authority indices are distinct (duplicating one or more valid signatures) and assert `Error::SuperMajorityRequired` (or `SuperMajorityRequired()` on EVM) is returned.
- Independently confirm, via a Devin session with terminal access to build/test the `rs_merkle` and Solidity `MerkleMultiProof` verification paths with deliberately duplicated `(index, hash)` inputs, whether the multiproof `verify` calls currently accept or reject such duplicates — this determines whether the missing dedup check is merely defense-in-depth or an actively exploitable gap.

## Proof of Concept
Not fully constructible from static analysis alone since it hinges on `rs_merkle`/`MerkleMultiProof` behavior under duplicate indices, which requires running code (unavailable in ask-only/read-only mode). The fast-validation approach suggested in the question — submitting a batch with `signed_commitment.signatures` containing one honest authority signature duplicated N times, and asserting `check_participation_threshold` is computed on unique indices — is the correct next step and should be executed in a Devin session with repository/test access.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

/// Verifies the inclusion of parachain headers in the parachain heads root via a merkle multi proof
pub fn verify_parachain_headers<H: Keccak256>(
	heads_root: H256,
	parachain_proof: ParachainProof,
) -> Result<Vec<ParachainHeader>, Error> {
	if parachain_proof.parachains.is_empty() {
		return Ok(vec![]);
	}

	let mut indexed_leaf_hashes = Vec::with_capacity(parachain_proof.parachains.len());

	for para_header in &parachain_proof.parachains {
		let leaf = (para_header.para_id, para_header.header.clone());
		let hash: [u8; 32] = H::keccak256(&leaf.encode()).into();
		indexed_leaf_hashes.push((para_header.index as usize, hash));
	}

	indexed_leaf_hashes.sort_by_key(|(index, _)| *index);

	let (leaf_indices, leaf_hashes): (Vec<usize>, Vec<[u8; 32]>) =
		indexed_leaf_hashes.into_iter().unzip();
	let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(parachain_proof.proof.clone());
	let valid = merkle_proof.verify(
		heads_root.0,
		&leaf_indices,
		&leaf_hashes,
		parachain_proof.total_leaves as usize,
	);

	if !valid {
		Err(Error::InvalidParachainProof)?;
	}

	Ok(parachain_proof.parachains)
}
