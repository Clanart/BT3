### Title
CW20ERC20Pointer.approve() is vulnerable to the ERC20 approve front-running race condition, enabling unauthorized over-spend via the pointer's CW20 bridge - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
`CW20ERC20Pointer` is the Solidity ERC20 pointer contract that Sei deploys to expose a CW20 token as an ERC20 token to EVM users, with its bytecode embedded in `x/evm/artifacts/cw20/artifacts.go` and instantiated by `x/evm/keeper/pointer.go`. Its `approve` function [1](#0-0)  does not overwrite the CW20 allowance directly; instead it reads the current on-chain allowance and issues a delta `increase_allowance`/`decrease_allowance` CosmWasm execute message to reach the new target amount.

### Finding Description
When an owner wants to change a spender's allowance from `A` to `B`, `approve()` first queries `currentAllowance` via `allowance(msg.sender, spender)` [2](#0-1) , then computes the delta and issues either an `increase_allowance` or `decrease_allowance` message on the underlying CW20 contract [3](#0-2) . Because `currentAllowance` is only re-read at the moment this transaction actually executes (not at signing time), a spender can front-run the owner's `approve(spender, B)` transaction: the spender first calls `transferFrom` to fully consume the existing allowance `A`, so when the owner's transaction executes, `currentAllowance` reads as `0` and the pointer issues an `increase_allowance` for the full `B`. The spender ends up having received `A` (already transferred) plus a freshly granted allowance of `B`, i.e. `A + B` total instead of the intended `B`. This is the exact ERC20 approve race-condition class described in the referenced report (classic "set" semantics being exploited via front-running), except here it manifests through the increase/decrease delta calculation instead of a direct overwrite — the delta calculation does not protect against a spender consuming the allowance in between the query and the mutating call within the same pointer transaction execution path.

### Impact Explanation
A spender that races an owner's `approve` call against a Sei CW20↔ERC20 pointer can obtain unauthorized extra token allowance and transfer tokens beyond what the owner intended to grant, resulting in unauthorized transfer of value via the pointer contract. Since pointer contracts are the canonical bridge exposing CW20/bank assets to EVM-side DeFi integrations, any protocol relying on `approve()` to reset allowances against a `CW20ERC20Pointer` is exposed to fund loss for the token owner.

### Likelihood Explanation
Exploitation requires an interested spender (already approved for some non-zero allowance) to observe a pending `approve` transaction changing their allowance and front-run it with a `transferFrom` before it lands in a block — a well-known, practically achievable MEV/mempool-ordering technique, and Sei's public mempool/RPC exposes pending transactions to any client capable of monitoring and submitting competing transactions.

### Recommendation
Change `CW20ERC20Pointer.approve()` semantics to require setting the allowance to zero before setting it to a new non-zero value (matching common ERC20 safe-approve guidance), or expose explicit `increaseAllowance`/`decreaseAllowance` functions atomic with a check on the currently observed allowance (similar to OpenZeppelin's deprecated safe-approve pattern), and document that integrators should use these instead of naive `approve` overwrites.

### Proof of Concept
1. Owner has granted spender an allowance of `A` on a CW20 pointer via `approve(spender, A)`.
2. Owner decides to reduce the allowance and submits `approve(spender, B)` with `B < A`.
3. Spender observes the pending transaction in the mempool and front-runs it with `transferFrom(owner, spender, A)`, fully consuming the existing allowance so `currentAllowance` becomes `0` on-chain.
4. Owner's `approve(spender, B)` transaction executes next: `currentAllowance` (now `0`) is less than `B`, so the pointer issues `increase_allowance` for `B`, granting the spender a fresh allowance of `B`.
5. Spender now controls `A` (already transferred) + `B` (new allowance) = `A + B`, exceeding the owner's intended total exposure of `B`. [1](#0-0)

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
