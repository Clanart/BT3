### Title
NFT Royalty Amount Truncates to Zero for Low-Value Trades, Allowing Creator Royalty to Be Silently Skipped - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
The wallet-side royalty computation used when building NFT offers performs integer division of `amount * percentage / MAX_ROYALTY_BASIS_POINTS (10000)` with no minimum-amount check. For any trade price/royalty-split combination where `amount * percentage < 10000`, the computed royalty rounds down to `0`, and the code explicitly treats this as "no royalty owed" — it both drops the royalty payment condition and omits the corresponding `trade_prices_list` entry that would otherwise force the taker's spend to acknowledge/pay the royalty. This mirrors the reported Cooler bug class: a percentage-based amount calculation rounds to zero for sufficiently small inputs, and the code has no floor/minimum enforcement, so the intended payment is bypassed entirely instead of failing or rounding up.

### Finding Description
Two functions perform this unguarded division: [1](#0-0) 

```
def compute_royalty_amount(offered_amount, royalty_split, percentage):
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    ...
    return royalty
``` [2](#0-1) 

Both use `// royalty_split * percentage // 10000` — integer division truncates toward zero, so for a sufficiently small `offered_amount` (or a large `royalty_split` from bundling many royalty-enabled NFTs in one offer) the result is `0`, exactly as in the Cooler `collateralFor` bug where `amount_ * decimals / loanToCollateral_` rounds to `0`.

This zero result is not treated as an error; instead `make_nft1_offer` uses it to explicitly skip the royalty payment and skip requiring the on-chain assertion of that payment: [3](#0-2) 

The `trade_prices_list` passed into the `-10` (ownership-layer transfer) condition only includes entries where `price[0] * offered_royalty_percentages[asset] // MAX_ROYALTY_BASIS_POINTS != 0` — zero-royalty trade prices are filtered out of the list that the transfer condition uses.

And separately, when constructing the actual `CreateCoin` payments for the offer bundle: [4](#0-3) 

```
# Skip it if we're paying 0 royalties
payments = royalty_payments[asset] if asset in royalty_payments else []
if sum(p.amount for _, p in payments) == 0:
    continue
```

So a maker (or counterparty) can construct a legitimate offer for a royalty-enabled NFT with a low enough trade price (or by bundling multiple royalty NFTs to inflate `royalty_split`) such that the computed royalty is `0`, and the code path simply omits the royalty payment/announcement rather than enforcing any minimum.

### Impact Explanation
An NFT creator's configured royalty (`royalty_percentage` on the singleton's ownership/transfer-program layer) can be silently bypassed for low-value trades or multi-NFT batched offers, diverting value that should go to the royalty address away from the rightful recipient — a form of offer-settlement value diversion reachable by any wallet user constructing or accepting an NFT offer, no privileged access required.

### Likelihood Explanation
High likelihood of occurrence: any wallet user (maker or taker) constructing an NFT offer through `NFTWallet.make_nft1_offer` / `TradeManager.check_for_special_offer_making` can trivially trigger the zero-rounding condition by picking a sufficiently small `offered_amount` relative to `royalty_percentage`, or by batching multiple royalty NFTs in one offer to increase `royalty_split`. No special privileges, malicious peers, or network-level manipulation are needed — it is purely a function of offer amounts chosen by an ordinary offer counterparty.

### Recommendation
Enforce a minimum computed royalty threshold (or round up / reject trades where `amount * percentage < MAX_ROYALTY_BASIS_POINTS`) in both `compute_royalty_amount` and `NFTWallet.royalty_calculation`, and remove the implicit "skip if zero" behavior in `make_nft1_offer`/the `trade_prices_list` filter so that any nonzero royalty percentage always results in either a nonzero payment or an explicit rejection of the trade, rather than silently omitting the payment.

### Proof of Concept
1. A creator sets an NFT's royalty to a nonzero `royalty_percentage` (e.g., `1` basis point = 0.01%).
2. A maker creates an offer via `NFTWallet.make_nft1_offer` requesting a small `xch_requested`/`amount` such that `amount * royalty_percentage // 10000 == 0` (e.g., `amount = 500`, `percentage = 1` → `500*1//10000 = 0`), demonstrated directly by: [5](#0-4) 
3. `compute_royalty_amount` / `royalty_calculation` return `0`.
4. `make_nft1_offer` excludes this asset from `trade_prices_list` (line 1027-1031) and skips creating the royalty `CreateCoin`/announcement (line 1043-1046).
5. The taker accepts the offer paying only the agreed (low) amount; the NFT creator receives no royalty despite the NFT having a configured nonzero royalty percentage, and no on-chain condition required them to pay it.

Note: I was unable to locate/verify the compiled on-chain royalty transfer-program CLVM puzzle (`NFT_TRANSFER_PROGRAM_DEFAULT`'s compiled `.clsp.hex`) in the indexed codebase to confirm whether the singleton ownership layer independently re-validates a minimum royalty on `-10` conditions; my analysis is based on the Python-side trade construction logic which explicitly special-cases and skips zero-rounded royalties. A full on-chain-puzzle-level review would be needed to confirm whether any additional enforcement exists there.

def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
