### Title
Unsanitized GitHub API `pull_request.head.ref` flows into `git branch <name> <start-point>` without an option-terminator, allowing a malicious fork owner to corrupt the branch created for a checked-out PR - (File: `app/src/lib/git/branch.ts`)

### Summary
When a GitHub Desktop user checks out an incoming pull request, the PR's `head.ref` (the name of the source branch, taken verbatim from the GitHub API and therefore fully controlled by whoever owns the forked repository the PR came from) is concatenated into a `start-point` string and handed to `git branch` as a raw command-line argument, with no `--` end-of-options marker and no ref-name sanitation. This mirrors the SeaDrop pattern: a semi-trusted external party (a PR author from a fork, analogous to an "allowed signer") controls a parameter (`head.ref`) that a downstream consumer implicitly trusts to be a well-formed value, and that value is used unguarded in a security-relevant operation, bypassing the invariant that the argument must be a valid commit-ish rather than an option flag.

### Finding Description
`app/src/ui/dispatcher/dispatcher.ts` reads the PR's head ref straight off the API model and passes it down unmodified: [1](#0-0) 

`app/src/lib/stores/app-store.ts` uses it to build a remote-qualified ref string with plain string interpolation: [2](#0-1) 

That composed string (`remoteRef`) is then passed as the `startPoint`/commit-ish argument when the local `pr/<num>` branch is created: [3](#0-2) 

`_createBranch` ultimately calls `createBranch`, which builds a raw `git` argv array with `name` and `startPoint` as adjacent positional arguments and never inserts a `--` separator before them: [4](#0-3) 

Contrast this with the deep-link ("Open in Desktop") branch handling, where the *same class* of value (a branch name) **is** validated against `testForInvalidChars`/`sanitizedRefName` before use: [5](#0-4) [6](#0-5) 

and with `clone()`, which explicitly appends `--` before the attacker-influenced `url` argument specifically to defend against this exact class of argument-injection bug: [7](#0-6) 

No equivalent protection (neither a `--` terminator nor a ref-format check) exists on the path that turns `pullRequest.head.ref` into the `startPoint` passed to `git branch`. Git ref names are permitted to begin with `-` (git's `check-ref-format` does not forbid a leading hyphen the way it forbids leading `.`), and a ref with such a name can be created and pushed directly via the git protocol even though GitHub's web UI blocks it, so a PR author fully controls this string via their own fork's branch name.

### Impact Explanation
Because `git branch <name> <start-point>` has no `--` boundary here, a `start-point` value beginning with `-` can be parsed by git as an option to `branch` (e.g., `-t`/`--track`, `--set-upstream-to=...`, etc.) instead of the intended commit-ish. This breaks the invariant that "the local `pr/<num>` branch is created from the PR's actual head commit," which is exactly the "silent corruption of what the user commits/pushes" impact category: the victim believes they are reviewing/building on top of the pull request's real content, while the local branch may silently be created from an unintended base (e.g., current `HEAD`) or with attacker-influenced tracking/upstream configuration, all without any error being surfaced to the user. This is triggered purely by the victim checking out a PR from an unprivileged, attacker-controlled fork — no local access, credentials, or unnatural user steps are required beyond the normal "check out this PR" action Desktop is designed for.

### Likelihood Explanation
Any GitHub user can fork the target repository, push a branch with a crafted ref name via `git push`, and open a PR from it — this requires no special privileges. The victim only needs to check out that PR in Desktop, which is a completely ordinary workflow (checking out community/contributor PRs is a core Desktop feature). Because the field flows through the API model deserializer with no validation applied anywhere between `IAPIPullRequest.head.ref` and `git branch`'s argv construction, the likelihood of the tainted value reaching the vulnerable sink is high whenever a PR from an attacker-controlled fork is checked out.

### Recommendation
- Insert a `--` end-of-options separator in `createBranch()` (`app/src/lib/git/branch.ts`) before `name` and `startPoint`, mirroring the pattern already used in `clone.ts`.
- Additionally validate/reject `pullRequest.head.ref` (and any other externally-sourced ref-like fields) with `testForInvalidChars`/`sanitizedRefName` (or an explicit "does not start with `-`" check) before using them to build git command arguments or composed ref strings such as `remoteRef`.

### Proof of Concept
1. Attacker forks the target repository on GitHub.
2. In the fork, attacker creates a git ref whose name begins with a dash (e.g. `-t`) and pushes it directly with the git CLI: `git push origin HEAD:refs/heads/-t` (bypassing the GitHub web UI, which normally disallows creating such names through its own branch-creation form).
3. Attacker opens a pull request from `-t` against the target repository; the GitHub API now returns `head.ref === "-t"`.
4. The victim, using GitHub Desktop with access to the target repository, opens/checks out this PR (via the PR list or an "Open in Desktop" style flow) which calls `dispatcher.checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch`.
5. `_findPullRequestBranch` builds `remoteRef = "<forkRemoteName>/-t"` and calls `_createBranch(repository, "pr/<num>", remoteRef, false)`, which calls `createBranch(repository, "pr/<num>", "<forkRemoteName>/-t")`.
6. `createBranch` executes `git(['branch', 'pr/<num>', '<forkRemoteName>/-t'])` — with no `--` separator, git may interpret the `-t`-suffixed positional argument as an option rather than a commit-ish, causing the new local branch to be created from an unintended base or with unintended flags rather than failing safely or matching the PR's real head commit.

**Uncertainty / what remains unverified:** I was not able to execute git directly in this environment to confirm precisely how a given installed `dugite`/git version parses `git branch <name> <value-starting-with-dash>` in every case (some flag combinations will simply error out rather than silently succeed). The exact exploitable flag set for `git branch` is narrower than for commands like `clone`/`fetch` (which have far more dangerous options such as `--upload-pack`), so this should be validated experimentally (e.g., via a Devin session with git available) to confirm which specific corrupted/silent-success scenario is reachable versus which attempts simply produce a git error.

export async function createBranch(
  repository: Repository,
  name: string,
  startPoint: string | null,
  noTrack?: boolean
): Promise<void> {
  const args =
    startPoint !== null ? ['branch', name, startPoint] : ['branch', name]

  // if we're branching directly from a remote branch, we don't want to track it
  // tracking it will make the rest of desktop think we want to push to that
  // remote branch's upstream (which would likely be the upstream of the fork)
  if (noTrack) {
    args.push('--no-track')
  }

  await git(args, repository.path, 'createBranch')
}

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
