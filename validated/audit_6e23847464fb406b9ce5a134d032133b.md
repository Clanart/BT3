### Title
Scanner reports same-block spent and immature coinbase outputs as spendable `ReceivedOutput`s - (networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block`/`scan_transaction` turn any matching P2TR `script_pubkey` into a `ReceivedOutput` without checking whether the outpoint is spent later in the same block or whether it is an immature coinbase output, despite `ReceivedOutput` being documented as “A spendable output.” [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The bug class is authorization/accounting based on a balance that is only transiently present. In the Bitcoin wallet scanner, transient presence is literal: `scan_transaction` emits a `ReceivedOutput` solely because `self.scripts.get(&output.script_pubkey)` matches, then records `OutPoint::new(tx.compute_txid(), vout)`. [4](#0-3)  `scan_block` runs this over every transaction in `block.txdata`, including `txdata[0]`, and never inspects `tx.input`/`previous_output` to remove outputs already consumed inside the same block. [5](#0-4)  The only caveat is a comment saying coinbase outputs are “bound by maturity” and need an external post-processing pass; the function still returns them as `ReceivedOutput`s. [6](#0-5)  Downstream, `SignableTransaction::new` trusts those `ReceivedOutput`s as inputs: it sums `input.output.value`, builds `TxIn`s from `input.outpoint`, and stores `input.output` as `prevouts` for signing. [7](#0-6) [8](#0-7)  The multisig constructor only checks that each stored prevout `script_pubkey` matches `keys.offset(offset).group_key()`; it does not prove the outpoint remains unspent or mature. [9](#0-8) 

### Impact Explanation
An unprivileged party can cause Serai’s Bitcoin scanner to report funds as received that are not spendable at the block end: send transaction A paying a scanned P2TR script, then transaction B later in the same block spending A’s output back to the attacker. `scan_block` still returns A’s output because it never subtracts same-block spends. This is the Bitcoin analog of flashloan-voting-power bypass: a value is temporarily observable during the block/transaction context, is consumed before it becomes a durable UTXO, yet is classified as a spendable `ReceivedOutput`. If an in-scope consumer treats `scan_block` output as confirmed/spendable per its API contract, this can produce incorrect received-funds accounting and a signing attempt for an invalid input. Coinbase outputs are similarly returned before maturity, with the test itself mining 100 blocks before spending and then calling `scan_block` on the coinbase block. [10](#0-9) 

### Likelihood Explanation
Reachability is high from public Bitcoin transaction data: the attacker only needs to get two transactions ordered in one block, which Bitcoin permits for intra-block dependencies. The trigger is entirely inside `Scanner::scan_block`, which explicitly chooses to scan `block.txdata` wholesale rather than `block.txdata[1 ..]` or a spentness-aware pass. [3](#0-2)  Exploitability for theft depends on consumers above this crate crediting scan results before a final UTXO/maturity check; within this crate the concrete failure is that `ReceivedOutput` is labeled spendable while it can be already spent or immature.

### Recommendation
Make `scan_block` spendability-aware or stop claiming its results are spendable. Track all `tx.input[*].previous_output` while scanning a block and suppress/remove matching `ReceivedOutput`s created earlier in that same block; skip `block.txdata[0]` or return a flag for coinbase immaturity; and have `SignableTransaction::new`/`multisig` reject inputs whose prevouts are not known-unspent and mature. If scanning must remain purely script-based, rename/document `scan_block` as a raw matcher and require callers to pass only mature, final UTXOs into `ReceivedOutput` consumers.

### Proof of Concept
```rust
// Attacker gets two txs ordered in one Bitcoin block:
// A: creates output paying Serai's scanned P2TR script.
// B: spends A:0 back to attacker via a valid input.
let mut scanner = Scanner::new(tweaked_group_key).unwrap();

// scan_block sees A's script_pubkey and emits ReceivedOutput(A:0).
let reported = scanner.scan_block(&block);
assert!(reported.iter().any(|o| o.outpoint() == &OutPoint::new(A.txid(), 0)));

// But B.input[*].previous_output == A:0 later in the same block, so A:0 is not
// a spendable UTXO at block end. scan_block never checks block inputs.
assert!(block.txdata.iter().skip(1).any(|tx|
  tx.input.iter().any(|i| i.previous_output == OutPoint::new(A.txid(), 0))
));
```
The same primitive reports coinbase outputs from `block.txdata[0]` before maturity while documenting that an extra pass is required to remove them. [3](#0-2)

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
