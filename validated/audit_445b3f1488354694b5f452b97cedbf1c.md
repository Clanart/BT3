### Title
Zest's zUSDH vault reports an incorrect `DECIMALS` constant that feeds the market's USD-normalization math, producing wrong collateral/debt values - (File: `mainnet/contracts/vault/v0-vault-usdh.clar`)

### Summary
`v0-vault-usdh.clar` hardcodes `(define-constant DECIMALS u8)` [1](#0-0)  for the zUSDH vault share token, while the protocol's own documentation states that every non-BTC vault (including USDH) uses 6 decimals: "Accounts for different decimal precision across vaults: sBTC uses 8 decimals (Bitcoin standard); All others use 6 decimals" [2](#0-1) . This is directly analogous to the Tokemak `LMPStrategy` finding: a hardcoded/assumed decimals value diverging from the token's real decimal precision, which is then consumed downstream by USD value math.

### Finding Description
When any asset (including a zToken vault-share) is registered, `assets.clar`/`v0-assets.clar` `insert` calls `call-get-decimals`, which invokes the FT contract's `get-decimals` and stores the returned value verbatim into the registry entry used for all subsequent pricing math: [3](#0-2) [4](#0-3) 

For the zUSDH vault, `get-decimals` returns the contract's local `DECIMALS` constant, which is hardcoded to `u8` [1](#0-0) , even though the protocol documentation/design expects 6-decimal precision for every non-BTC vault token [2](#0-1) .

This registered `decimals` value is later used, unmodified, as the divisor in the core USD-notional calculation for both collateral and debt legs of every health check, borrow, and liquidation: [5](#0-4) 
and in the liquidation-specific value conversions: [6](#0-5) [7](#0-6) 

If the actual zUSDH share amounts are minted/transferred at 6-decimal scale (mirroring the true USDH underlying, matching the documented design) while the registry believes the token has 8 decimals, then `normalize (* amount price) decimals` divides by `10^8` instead of `10^6` — a 100x under-scaling of the USD value attributed to any zUSDH position, on both the collateral and debt sides.

### Impact Explanation
This is a decimals-normalization mismatch feeding directly into the health/liquidation verdict, matching the in-scope bug class. Depending on which side of a position holds zUSDH:
- If zUSDH is used as **debt**, its USD value is undercounted 100x, making an actually-unhealthy position appear healthy (`is-healthy` returns true when it should be false), allowing users to over-borrow against collateral or evade liquidation entirely — this is a path to insolvency/theft of protocol funds.
- If zUSDH is used as **collateral**, its USD value is undercounted 100x, causing healthy positions to be misclassified as unhealthy, triggering unwarranted (temporary) freezing/liquidation of user funds.

Either direction lands squarely on the in-scope impact classes (protocol insolvency / theft of funds, or temporary freezing of funds), matching the "wrong health verdict from decimals normalization" analog class permitted by the rules.

### Likelihood Explanation
The bug is not conditional on any external oracle misbehavior or DAO misconfiguration — it is a static, hardcoded contract constant that is used unconditionally by every asset-registration and every subsequent notional-value computation for zUSDH. Every borrow, health check, and liquidation involving zUSDH would be affected once the asset is registered with this decimals value, making exploitation deterministic rather than probabilistic.

### Recommendation
Verify the actual decimal precision minted by `v0-vault-usdh.clar`'s tokenized-vault logic (deposit/withdraw share math) against the real USDH underlying token's decimals, and correct the `DECIMALS` constant (and any dependent `PRECISION`/scaling constants) to match. Add a registration-time or CI-level invariant check comparing each vault's declared `DECIMALS` against its underlying asset's decimals (accounting for intended 1:1 share-decimal parity) to prevent this class of mismatch from silently propagating into `normalize()`-based USD math in `v0-4-market.clar`.

### Proof of Concept
1. Register the zUSDH vault via `v0-assets.insert`, which calls `call-get-decimals` on `v0-vault-usdh`, returning the hardcoded `u8` [1](#0-0)  and storing `decimals: 8` in the registry entry.
2. A user deposits USDH and receives zUSDH shares minted at the vault's true (6-decimal) internal scale — e.g., `1,000,000` units representing "1.0" zUSDH.
3. The user opens a borrow position using zUSDH as collateral/debt. `calculate-asset-notional-value` computes `normalize (* 1,000,000 price) 8 ...` [8](#0-7) , dividing by `10^8` instead of the correct `10^6`, yielding a USD notional 100x smaller than actual.
4. `is-healthy` [9](#0-8)  then evaluates the position against a debt or collateral figure that is off by 100x, permitting over-borrowing (if zUSDH is debt) or improper liquidation (if zUSDH is collateral).

Note: I could not fully confirm, within the available indexed content, the exact decimal precision minted by `v0-vault-usdh.clar`'s deposit/mint logic nor the real on-chain decimals of the `usdh-token-v1` underlying contract (only the local mock `local-testing/contracts/utility/token/usdh.clar` was located, not read). The finding is grounded in the explicit contradiction between the hardcoded `DECIMALS u8` constant in the mainnet vault contract and the protocol's own documented design that "all [non-BTC] vaults use 6 decimals." A Devin session with full repo access should verify the vault's actual mint/burn decimal scale and the real USDH token decimals to confirm exploitability before remediation.
