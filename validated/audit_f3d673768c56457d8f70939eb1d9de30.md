### Title
OP_RETURN data output excluded from fee/weight calculation causes underpaid, potentially non-standard transactions - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/Annirich/serai--021/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends the user-supplied `data` as an OP_RETURN `TxOut` to the actual transaction's outputs, but computes `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` bound via `calculate_weight_vbytes`, which only accounts for `inputs`, `payments`, and `change` — never the data output. Transactions carrying data therefore pay less than the requested fee rate and can pass the standard-weight check while actually exceeding it. [1](#0-0) 

### Finding Description
The external report describes a function that accepts a user-supplied parameter (`quote`), produces a real side effect (burning PT/YT for Target), but then fails to account for/transfer the actual resulting asset, so the user loses funds. The Serai analog is in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`:

- At lines 194–202, if `data` is `Some`, an OP_RETURN output of up to ~91 bytes (9-byte script overhead + up to 80 bytes of data, allowed by the `TooMuchData` check at line 171) is pushed onto `tx_outs`, which becomes the real transaction's `output` list.
- At line 204, the fee/vbyte and weight basis is computed as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — `payments` does not include the OP_RETURN output (it is built from the `payments` slice only, lines 85–93). The same omission occurs in the change path at line 226.
- Consequently `needed_fee = fee_per_vbyte * vbytes` is short by `fee_per_vbyte * ~23` vbytes (the OP_RETURN output's serialized size / 4), and the `DEFAULT_MIN_RELAY_TX_FEE` floor check at line 211 and the `MAX_STANDARD_TX_WEIGHT` check at line 241 are evaluated against a weight that excludes the data output. [2](#0-1) 

An unprivileged user supplies the `data` bytes (the Serai InInstruction / OP_RETURN payload path in `processor/src/networks/bitcoin.rs` uses `extract_serai_data` on these outputs, confirming `data` is attacker-influenced transaction data). Because signing commits to the real `tx.output` via `Prevouts::All` in `TransactionSignMachine::sign` (line 375), the produced signature is valid for the under-priced/oversized transaction — the multisig signs and broadcasts a transaction that miners will reject or that pays below the intended rate. [3](#0-2) 

### Impact Explanation
- The transaction's effective fee rate is below both the requested `fee_per_vbyte` and possibly the relay minimum, so it may never confirm while the protocol believes the plan was executed and the inputs are consumed (the plan/output bookkeeping treats the signed TX as spending those `ReceivedOutput`s).
- A transaction whose true weight exceeds `MAX_STANDARD_TX_WEIGHT` (100k WU) passes the check whenever the omitted OP_RETURN output is what pushes it over, yielding a permanently non-standard, unrelayable transaction signed by the threshold key — funds are stuck pending manual intervention. As in the source report, the protocol produces a valid-looking result while the actual economic output (confirmed spend) is not delivered.

### Likelihood Explanation
Medium. Any transaction carrying a `data` payload triggers the underpayment deterministically; whether it causes a relay failure depends on how close the signed TX is to the min-fee floor or the standard-weight cap. The weight-check bypass requires an already-large transaction (many inputs/payments plus ~91 bytes of uncounted output), which is reachable since `payments` can contain up to thousands of entries before `TooLargeTransaction` fires — and that check itself uses the understated weight.

### Recommendation
Include the OP_RETURN output in the size/fee accounting: extend `calculate_weight_vbytes` to accept the optional `data` (or build `tx_outs` first and measure the full output set) so that `needed_fee`, the min-relay floor, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction actually being signed.

### Proof of Concept
```rust
// Conceptual: any data-bearing transaction is undercharged.
let inputs = vec![output];            // ReceivedOutput with ample value
let payments = vec![(addr(), 1000)];
let data = vec![0u8; 80];             // user-supplied InInstruction payload

let tx = SignableTransaction::new(inputs, &payments, None, Some(data), FEE).unwrap();
// tx.needed_fee() == FEE * vbytes(inputs + payments)  -- missing the OP_RETURN output
// actual size is larger by ~91 bytes, so effective rate < FEE
// effective fee rate = (inputs - outputs) / actual_vsize < FEE
```
With `payments` large enough that `weight + OP_RETURN_weight > MAX_STANDARD_TX_WEIGHT >= weight`, the constructor returns `Ok` and produces a transaction no node will relay, even though `sign()`/`complete()` will validly sign it.
