## Finding [1](#0-0) 

### Title
Stale line-selection indices are trusted without re-validation against a freshly-fetched diff during partial commit staging - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets users stage a subset of lines in a file ("partial commit") by recording *absolute line indices* in a `DiffSelection` object that was computed against the diff shown in the UI. When the commit is actually staged, `applyPatchToIndex` re-fetches a **new** diff of the working directory and blindly reuses those same absolute indices against it, with no check that the new diff's line indexing still matches the one the selection was built from.

### Finding Description
The invariant "selection indices are only meaningful relative to the diff they were computed from" is enforced in exactly one place: `AppStore`'s diff-refresh handler recomputes `selectableLines` and prunes stale divergent lines whenever the UI reloads a diff [2](#0-1) . That code even acknowledges the risk in its own comment:

> "The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines..."

However, this reconciliation only happens on the UI's periodic diff-refresh path. It is **not** re-run at the point where the selection is actually consumed to build the patch that gets applied to the git index. `applyPatchToIndex` fetches a brand-new diff right before formatting the patch: [3](#0-2) 

```
const diff = await getWorkingDirectoryDiff(repository, file)
...
const patch = await formatPatch(file, diff)
await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })
```

`formatPatch` then walks the hunks of *this newly-fetched* diff and, for every non-context line, decides inclusion purely via `file.selection.isSelected(absoluteIndex)` where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` [4](#0-3) . `DiffSelection.isSelected()` performs no bounds or structural check at all — it simply asks whether the numeric index is present in `divergingLines`, with no reference to which diff produced that index [5](#0-4) .

This is the same bug class as the audited Solana proof: a length/consistency check (`bit_lengths.len() <= MAX_COMMITMENTS`, analogous to "selection indices match diff structure") is enforced at one call site (proof generation / UI diff-refresh) but is silently assumed — never re-verified — at the consumption site (proof verification / patch application against a freshly loaded diff). `formatPatch`'s own comment underscores this trust assumption: *"If we get into this state we should never have been called in the first place. Someone gave us a faulty diff and/or faulty selection state."* [6](#0-5)  — i.e., the function relies entirely on an invariant that is maintained elsewhere and unverifiable at the point of use.

### Impact Explanation
If the working-directory file's diff structure changes (hunk boundaries/line counts shift) between the moment the user's partial-selection UI state was built and the moment `applyPatchToIndex` re-diffs the file, the numeric indices no longer line up with the same source/target lines. Because `isSelected` has zero structural awareness, this can cause the wrong lines to be staged/committed — lines the user never selected get included, or lines they selected get silently dropped — without any error being raised (`formatPatch` only throws if the *entire* patch is empty, not if the *wrong* content was chosen). This is exactly the "silent corruption of what the user commits or pushes" impact category: a user could believe they excluded a secret, credential, or unrelated hunk from a commit, while the tool silently includes different content instead, or vice versa.

### Likelihood Explanation
An attacker who controls a cloned repository (e.g., ships an automated file-formatter/build hook, a watch-mode generator, or any tooling — even one the victim runs themselves as part of a normal dev workflow, such as `webpack --watch`, codegen, or `git filter` — that rewrites a tracked file's content) can cause the working file to change between the time Desktop renders the diff for the user to select lines from and the time the user clicks "Commit" and the code path in `apply.ts` re-diffs the file. Desktop does not re-validate or re-map the selection against the new diff at that consumption point, so mismatched line inclusion is a realistic outcome for anyone editing/staging partial changes concurrently with any background process modifying the same file — a common and natural (not contrived) Desktop usage pattern.

### Recommendation
Before calling `formatPatch`/`formatPatchToDiscardChanges`, re-validate that the just-fetched diff structurally matches the diff the `DiffSelection` was computed against (e.g., compare hunk headers/line counts, or recompute `selectableLines` and diff it against the selection's `selectableLines`), and abort/refresh the selection instead of silently proceeding when a mismatch is detected — mirroring, at the point of use, the reconciliation logic that today only runs in `app-store.ts`'s diff-refresh handler.

### Proof of Concept
1. Open a repository in Desktop, modify `file.md`, and in the Changes view deselect a specific added line (building a `DiffSelection` keyed to the currently rendered diff's `hunk.unifiedDiffStart` offsets).
2. Before clicking "Commit," have an external process (e.g., a watch-mode formatter/build script, or simply editing the file in another editor) change `file.md` such that the hunk structure shifts (e.g., add/remove a line earlier in the file so line offsets change), without refreshing/re-rendering Desktop's diff view.
3. Click "Commit." `applyPatchToIndex` calls `getWorkingDirectoryDiff` again [7](#0-6) , producing hunks with different `unifiedDiffStart` offsets than what the selection was built from, then `formatPatch` applies the stale absolute-index selection to these new hunks [4](#0-3) .
4. Inspect the resulting commit: it contains different line inclusions/exclusions than what was visibly selected in the UI, with no error surfaced to the user.

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
