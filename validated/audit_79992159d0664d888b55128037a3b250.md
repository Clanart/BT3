### Title
`ThresholdKeys::read` does not enforce that the encoded secret share matches its verification share - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts attacker-controlled threshold key material whose `secret_share` is unrelated to the supplied `verification_shares[i]`. `ThresholdKeys::new` validates the participant indices and derives a group key from the first `t` verification shares, but it never checks that the local secret corresponds to the local verification share. The result is a semantically inconsistent signing key accepted as structurally valid. This mirrors the reported bug class: a declared policy/value is serialized and used without enforcing the required consistency invariant at the point of acceptance.

### Finding Description
`ThresholdKeys::read` parses:

- `t`, `n`, and participant index `i`;
- an interpolation method;
- one secret scalar;
- `n` verification shares.

It then calls `ThresholdKeys::new` with those independent fields. `ThresholdKeys::new` checks the number of verification shares and that all participant indices are in range, and it derives `group_key` from verification shares `1..=t`. However, it never checks:

```rust
C::generator() * secret_share == verification_shares[&i]
```

or otherwise proves that the encoded secret belongs to the encoded verification-share polynomial.

The inconsistency is acknowledged indirectly by the FROST completion path: after all signature shares verify individually, an aggregate failure is described as possible when a “semantically invalid FrostKeys” value was deserialized.

### Impact Explanation
An attacker who can feed crafted `ThresholdKeys` bytes into an operator, service, migration path, or recovery/import routine can cause it to accept key material that appears valid but cannot produce a valid threshold signature. Every participant may produce an individually valid share for the attacker-selected verification-share map while the aggregate signature still fails, causing the signing operation to abort at completion.

This is a funds-availability failure for threshold-controlled assets: the deserialized object reports a group key and can start signing, but the inconsistent secret prevents successful finalization. It can also misattribute blame or repeatedly trigger signing attempts because the inconsistency is detected only after the full signing interaction rather than at deserialization.

### Likelihood Explanation
The malformed state is reachable entirely through public/untrusted bytes supplied to `ThresholdKeys::read`: all scalar and point encodings can be independently selected. The parser accepts them if they are canonical and the participant indices satisfy the coarse bounds checks.

Exploitation requires a reachable path where an unprivileged party can submit or replace serialized threshold-key material, or where untrusted backup/recovery data is imported without a stronger authenticity layer. If `ThresholdKeys::read` is used only on trusted internal storage, the practical exposure is lower; the vulnerability is still a missing invariant in a public deserialization API.

### Recommendation
Enforce the semantic relation during `ThresholdKeys::new`, or at least during `ThresholdKeys::read`, by checking:

```rust
C::generator() * secret_share == verification_shares[&params.i()]
```

Prefer doing this in `ThresholdKeys::new` so all constructors, not only deserialization, reject inconsistent key material. If supporting algorithms where the verification share intentionally differs from `generator * secret_share`, the constructor should require an explicit semantic proof from the caller instead of silently accepting inconsistent state.

### Proof of Concept
Conceptually, for any supported ciphersuite:

1. Pick valid `t`, `n`, and `i`, such as `t = n = 2`, `i = 1`.
2. Pick arbitrary canonical `secret_share`.
3. Pick any `verification_shares[1]` not equal to `C::generator() * secret_share`, and arbitrary valid points for the remaining shares.
4. Serialize those fields using `ThresholdKeys`’s documented wire format.
5. `ThresholdKeys::read` succeeds because only structural bounds and point canonicity are checked.
6. Attempting to sign reaches `complete`; individual share verification can pass for the supplied verification shares, while aggregate verification fails, reaching the internal error case reserved for semantically invalid deserialized keys.
