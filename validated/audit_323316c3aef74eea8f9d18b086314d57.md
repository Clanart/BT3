### Title
Gasless swap `minAmountOut` slippage protection is enforced only at tx-pool admission, not atomically at execution, enabling sandwich attacks - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The `kaiax/gasless` module lets an unprivileged sender submit a `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` transaction that is expected to protect the user from excessive slippage via `minAmountOut`. However, that check (`checkBalanceForSwap`) is performed only once, off-chain, when the transaction is admitted to the tx pool, using the AMM price/state at that moment. The `GaslessModule` implements `kaiax.ExecutionModule` (only `PostInsertBlock`) but not `kaiax.TxProcessModule` (`PreRunTx`/`PostRunTx`), so there is no atomic on-chain re-check of `minAmountOut` at the time the swap is actually executed. If the underlying DEX price used by `GaslessSwapRouter.GetAmountIn` moves between admission and execution — e.g., because an auction bidder's bid transaction (which KIP-249 explicitly allows to be inserted immediately adjacent to a target transaction) trades against the same pool — the swap still executes and returns fewer tokens than the user intended, exactly the sandwich scenario the external report describes, but here manifesting as a race between mempool admission-time slippage validation and actual execution-time settlement.

### Finding Description
`GaslessModule.GetCheckBalance()` returns `checkBalanceForSwap`, which is the only place `minAmountOut` is validated: [1](#0-0) 

This check requires `minAmountOut >= amountRepay` and `amountIn >= router.GetAmountIn(token, minAmountOut)` computed against the *current* on-chain state at the moment the check runs (`bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)`), which is invoked from `PreAddTx`/`GetCheckBalance` in the `TxPoolModule` lifecycle: [2](#0-1) 

Crucially, `GaslessModule` does not implement `kaiax.TxProcessModule`'s `PreRunTx`/`PostRunTx` hooks, which are the mechanism kaiax provides for per-transaction checks that run atomically during actual EVM execution: [3](#0-2) 

Instead, `GaslessModule`'s only execution-lifecycle hook is `PostInsertBlock`, which merely refreshes cached state/addresses after a block is inserted — it performs no re-validation of pending swap transactions' slippage bounds relative to the state at actual execution time: [4](#0-3) 

Because the `swapForGas` call itself, once it reaches the EVM, is not shown anywhere to independently enforce `minAmountOut` against the realized output (the only place that string "insufficient minAmountOut" is produced is the Go-level `checkBalanceForSwap`, and the test confirms the rejection happens at `SendTransaction`/pool admission, not via an execution revert): [5](#0-4) 

Meanwhile, KIP-249 auctions are explicitly designed to let a searcher's bid execute immediately adjacent to a target transaction in the same block: [6](#0-5) 

Put together, this is structurally the same weakness as the reported Proteus issue: a slippage-protection parameter (`minAmountOut`) exists in the interface, but it is not tied atomically to the swap's actual on-chain settlement. Here it is checked once, off-chain, at an earlier point in time (pool admission) against a state that can differ from the state at execution.

### Impact Explanation
An unprivileged auction bidder (searcher) can submit a bid whose payload trades against the same underlying DEX pool that `GaslessSwapRouter` quotes from, targeting a pending gasless swap transaction that has already passed the mempool's stale `minAmountOut` check. Because there is no atomic on-chain enforcement of `minAmountOut` at execution time, the victim's `swapForGas` transaction executes at the manipulated (worse) price rather than reverting, and the searcher captures the spread. This is a concrete value-extraction/theft primitive against gasless-swap users, consistent with "unauthorized value movement" via slippage abuse.

### Likelihood Explanation
The precondition — a time/state gap between admission-time price check and execution-time settlement — is structural, not incidental: KIP-249's entire design intentionally inserts bid transactions adjacent to targets, and gasless swap transactions can also simply sit in the pool across blocks before being promoted/executed. No special privilege is required; any bidder or trader interacting with the underlying pool can trigger the price movement. The only mitigating factor is that the mempool check does approximate a slippage bound, reducing (but, due to the timing gap, not eliminating) the attack surface, hence Medium likelihood.

### Recommendation
Enforce `minAmountOut` atomically at execution time rather than only at admission time. Concretely, add `PreRunTx`/`PostRunTx` handling (via `kaiax.TxProcessModule`) for gasless swap transactions that re-verifies the realized output against `minAmountOut` using the state immediately before/after the swap executes within the same EVM transaction, and reverts if the bound is violated — mirroring what an on-chain AMM's `require(outputAmount >= minAmountOut)` would provide. Alternatively/additionally, ensure the `GaslessSwapRouter` contract itself enforces `minAmountOut` against the actual computed output inside `swapForGas`, so slippage protection does not depend solely on a point-in-time mempool policy check.

### Proof of Concept
1. Alice signs and submits a `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` transaction; it passes `checkBalanceForSwap` because, at submission time, `router.GetAmountIn(token, minAmountOut)` is satisfied by the current pool price (`kaiax/gasless/impl/tx_pool.go:107-141`).
2. Before Alice's transaction is included/executed, a searcher submits an auction bid (KIP-249) whose bundled transaction trades against the same underlying pool that the `GaslessSwapRouter` prices from, moving the exchange rate unfavorably for Alice. The auction module places this bid transaction immediately adjacent to (before) Alice's swap in block construction (`kaiax/auction/README.md:26-33`).
3. Alice's `swapForGas` transaction is executed at the new, worse price. Since `GaslessModule` has no `PreRunTx`/`PostRunTx` re-validation of `minAmountOut` (`kaiax/gasless/impl/execution.go:24-33`, `kaiax/interface.go:128-145`), and the mempool-level check already passed and is not re-run, the swap does not revert.
4. Alice receives fewer tokens than her declared `minAmountOut`, while the searcher profits from the price spread — the same outcome described in the sandwich-attack report, reproduced here via the timing gap between admission-time and execution-time state.

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}

// TxProcessModule intervenes how transactions are executed.
// Tx processing can happen on temporary states (e.g. eth_call),
// or run on states before confirmation (e.g. miner),
// therefore these methods MUST NOT modify any persistent states.
type TxProcessModule interface {
	// Additional actions to perform before EVM execution.
	// Optionally transform the tx to a regular Eth tx.
	// Optionally populate VM envs e.g. feepayer
	PreRunTx(evm *vm.EVM, tx *types.Transaction) (*types.Transaction, error)

	// Additional actions to perform after EVM execution.
	PostRunTx(evm *vm.EVM, tx *types.Transaction) error
}

// Any component or module that accommodate tx process modules.
type TxProcessModuleHost interface {
	RegisterTxProcessModule(modules ...TxProcessModule)
}
