### Title
Global `safe.directory` trust grants are never revoked, letting an attacker-controlled repository silently inherit "trusted" status at a reused path - (File: app/src/lib/git/config.ts)

### Summary
When Desktop encounters a repository owned by a different user, it warns the user and, only on explicit click, calls `addSafeDirectory(path)` which appends that literal path to the user's **global** `safe.directory` git config [2](#0-1) . This call is idempotent-add only (`addGlobalConfigValueIfMissing`) [1](#0-0) , and nothing in the codebase ever calls the corresponding `removeGlobalConfigValue`/`removeConfigValueInPath` to revoke it [3](#0-2) . Meanwhile, removing a repository from Desktop (`RepositoriesStore.removeRepository`) only deletes the Dexie DB row — it does nothing to the global git config [4](#0-3) .

### Finding Description
This is the structural analog of the audit's "must approve 0 first" class: a security-relevant allow-list entry is *added* without ever being properly reset/cleared, so stale trust silently combines with a new, attacker-controlled object at the same identifier.

Concretely:
1. A user adds/clones a repository at path `P` owned by another OS user (e.g. shared machine, mounted network drive, extracted archive, Docker volume, CI runner reused across jobs). Desktop's `getRepositoryType` flags it `unsafe` and shows a warning: "appears to be owned by another user... Adding untrusted repositories may automatically execute files in the repository" [5](#0-4) .
2. The user clicks "Trust Repository" once, calling `onTrustDirectory` → `addSafeDirectory(P)` [6](#0-5) [7](#0-6) . This permanently writes `P` into the user's global `~/.gitconfig` `[safe] directory=P` list.
3. The user later removes that repository from Desktop (`_removeRepository` → `repositoriesStore.removeRepository`), which never touches `safe.directory` [8](#0-7) [4](#0-3) .
4. Any future directory that ends up at the identical path `P` — because it's a shared/reused mount point, a symlink target, a scratch/tmp path, a re-cloned folder with the same name, or a directory an attacker (with only filesystem-write access to that shared location, not the user's machine as "admin") repopulates with a malicious `.git` — is now automatically treated as trusted by Git with **no new prompt**, because Git's ownership check is satisfied purely by path membership in `safe.directory`, and Desktop's guard (`getRepositoryType` returning `unsafe`) is bypassed by design once the path is in that list.
5. Since a "trusted" (non-unsafe) repository is one where Git will execute repo-controlled configuration (hooks path via `core.hooksPath`, `.gitattributes` filters, submodule commands, etc. — the whole point of the ownership check Git added in CVE-2022-24765 environments), an attacker who can place content at a previously-trusted path regains the ability to trigger code execution without the user ever re-approving that specific repository/content.

### Impact Explanation
This corrupts the invariant "the user consciously reviewed and trusted *this* directory's current owner/content" into "the user trusted *this path string*, forever, regardless of what occupies it later." That silently re-grants Git's unsafe-directory protection bypass to arbitrary future content dropped at a previously-approved path, which can lead to unprompted execution of repository-controlled Git machinery (hooks/filters) — i.e., code execution outside of any explicit per-repository consent, satisfying the report's impact bar (result of a fetched/opened repository object leading to code execution without renewed authorization).

### Likelihood Explanation
Requires: (a) the user having trusted a directory once (already a documented, common flow for network shares/shared machines per the changelog: "Support trusting repositories on network shares (Windows)"), and (b) that same path later being repopulated by different/attacker content — realistic for shared drives, CI agents, container volumes, or removable media, none of which require local/physical/admin access to the user's own machine or leaked credentials. It is a plausible, if not everyday, occurrence for users who work with shared/mounted paths, matching a "medium" likelihood similar to the original finding's non-trivial-but-real occurrence for USDT-like tokens.

### Recommendation
- When a repository is removed from Desktop (`RepositoriesStore.removeRepository` / `AppStore._removeRepository`), also revoke the corresponding `safe.directory` grant added via `addSafeDirectory`, e.g. call `removeGlobalConfigValue('safe.directory', repository.path)` (mirroring `removeConfigValueInPath` in `app/src/lib/git/config.ts:266-283`) if Desktop was the one that added it.
- Alternatively/additionally, re-verify repository identity (e.g., compare a stored fingerprint of the initial commit/remote) before silently reusing a prior trust grant, rather than trusting by path alone.
- At minimum, warn users that "Trust Repository" grants are permanent and path-based, and provide a UI to review/revoke previously trusted directories.

### Proof of Concept
1. On a machine where directory `/shared/proj` is owned by user B.
2. User A clones/opens `/shared/proj` in Desktop, sees the "owned by another user" warning, clicks "Trust Repository" → `addSafeDirectory('/shared/proj')` is called, adding it to global `safe.directory` [6](#0-5) .
3. User A removes the repository from Desktop's list (`Remove` button) — `repositoriesStore.removeRepository` deletes only the DB entry [4](#0-3) ; global git config `safe.directory=/shared/proj` remains.
4. Attacker (who has write access to the shared location, e.g. another legitimate user of the shared drive) deletes and recreates `/shared/proj` with a malicious `.git` (e.g. containing a `core.hooksPath`-triggering config or malicious hook once made executable via a subsequent commit/checkout).
5. User A re-opens `/shared/proj` in Desktop. `getRepositoryType` no longer reports `unsafe` (because the path is already allow-listed), so no warning is shown and Git treats the malicious repository as fully trusted, running its hooks/config without any new user consent. /**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

/** Set the global config value by name. */
export async function addGlobalConfigValueIfMissing(
  name: string,
  value: string
): Promise<void> {
  const { stdout, exitCode } = await git(
    ['config', '--global', '-z', '--get-all', name, value],
    __dirname,
    'addGlobalConfigValue',
    { successExitCodes: new Set([0, 1]) }
  )

  if (exitCode === 1 || !stdout.split('\0').includes(value)) {
    await addGlobalConfigValue(name, value)
  }
}
