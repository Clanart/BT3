### Title
Negative EVM ante/tx "surplus" (usei/wei accounting shortfall) is silently dropped in `EndBlock`, causing supply-invariant panics or unrecovered accounting debt - ([File: x/evm/keeper/abci.go])

### Summary
Sei's EVM StateDB tracks a per-transaction usei/wei reconciliation value called "surplus" that must be swept into the EVM module account at `EndBlock`. The current code only handles the case where the aggregated surplus is positive; if it is negative, nothing is done to reconcile it, which is structurally the same defect described in the external report: a computed shortfall ("debt") that the system fails to settle. A prior real-world occurrence of this exact class of bug required a manual migration (`FixTotalSupply`) to repair a corrupted total-supply value.

### Finding Description
Every `AddBalance`/`SubBalance` call in the EVM `StateDB` accumulates a `surplus` value representing the usei/wei precision remainder for that transaction: [1](#0-0) [2](#0-1) 

This per-tx surplus is finalized and stored via `AddAnteSurplus` during ante handling: [3](#0-2) 

At `EndBlock`, the keeper sums all per-tx surpluses (`GetAnteSurplusSum` plus each `deferredInfo.Surplus`) and reconciles them into the EVM module account — but only for the positive branch: [4](#0-3) 

There is no corresponding branch to subtract/burn from the module account (or otherwise account for) a negative aggregate surplus. This mirrors the PoolTemplate.resume() pattern in the referenced report: a computed shortfall (`_shortage`/negative surplus) is calculated but only one direction of settlement is implemented, leaving the opposite-sign case as unhandled "system debt."

Corroborating this is a migration explicitly written to repair the consequences of this exact gap: [5](#0-4) 

The comment states plainly: "This migration is to fix total supply mismatch caused by mishandled ante surplus" — i.e., this bug class has already manifested in production/historical state and corrupted the `usei` total supply, requiring a manual, one-off correction rather than a systemic fix in the accrual path itself.

The invariant checker (`LightInvarianceTotalSupply`), which is enabled by default (`SupplyEnabled: true`), independently validates that `useiDiff` (computed from the surplus/wei/supply deltas) is exactly zero every block and `panic`s otherwise: [6](#0-5) [7](#0-6) 

So if any reachable EVM execution path (an unprivileged transaction sender constructing balance mutation patterns, precompile calls that move value, or pointer/CW-EVM bridging operations) causes the aggregated per-block surplus to go negative in a way not fully offset elsewhere, the un-swept negative surplus is dropped in `EndBlock` (accounting debt is not recorded, not repaid, not burned), and on the very next invariance pass this manifests as a nonzero `useiDiff`, causing a node-wide `panic`.

### Impact Explanation
Because `LightInvarianceChecks`/`LightInvarianceTotalSupply` runs by default and `panic`s on any nonzero `useiDiff`, an unhandled negative surplus stemming from ordinary EVM transaction execution can crash every validator running with default config, producing a chain halt (validator halt) — one of the explicitly accepted impacts. Absent the invariant check (e.g., disabled by an operator), the same defect degrades into a silent, permanent total-supply mismatch (supply inflation/deflation), which is also an accepted impact class. The existence of `fix_total_supply.go` demonstrates this is not theoretical — the exact failure mode ("mishandled ante surplus" corrupting total supply) has previously occurred, and the root-cause code path in `EndBlock` (only handling `surplus.IsPositive()`) has not visibly changed to close the negative-surplus gap.

### Likelihood Explanation
The surplus mechanism is driven entirely by ordinary EVM balance mutations that any unprivileged transaction sender can trigger (regular value transfers, precompile calls with value forwarding, pointer-contract operations bridging usei/wei). The precise sequence of `AddBalance`/`SubBalance` calls that yields a net-negative aggregate surplus for a block is state- and ordering-dependent and was not proven end-to-end within this repo (no fully reachable, minimal PoC was located in the available index; the exact conditions producing a negative sum were not verified line-by-line beyond the accounting code and the historical migration evidence). Given that this exact defect already corrupted supply once in production history (per the migration's own description), likelihood is assessed as real but conditional on triggering the negative-sum case, which the code review could not fully reproduce from the indexed contents alone.

### Recommendation
Add explicit handling for the negative branch of the aggregated `surplus` in `x/evm/keeper/abci.go`'s `EndBlock`: when `surplus.IsNegative()`, deduct/burn the corresponding usei/wei from the EVM module account (mirroring the positive-branch mint), and if the module account balance is insufficient to cover it, treat this as a hard invariant violation with clear diagnostics (module, block height, offending tx hashes) rather than allowing it to silently propagate into total-supply corruption. Additionally, add a dedicated unit test analogous to `TestAnteSurplus` that exercises a negative aggregate surplus and asserts the module account balance is correctly decremented (or the appropriate error/handling path executes), to guarantee this class of accounting shortfall can never again require a manual `FixTotalSupply`-style migration.

### Proof of Concept
Not independently reproduced from the indexed codebase; a concrete PoC would require constructing an EVM transaction sequence (or precompile-driven usei/wei crossing) that yields a net-negative aggregate `surplus` value in `k.GetAnteSurplusSum(ctx)` combined with `deferredInfo.Surplus`, then observing that `x/evm/keeper/abci.go`'s `EndBlock` (lines 106–148) performs no compensating action, followed by `app.LightInvarianceTotalSupply` panicking on the resulting `useiDiff` mismatch. The historical existence of `x/evm/migrations/fix_total_supply.go`, whose sole purpose is to repair total-supply corruption "caused by mishandled ante surplus," is used as evidence that this condition has been previously producible in this codebase's history.

// This migration is to fix total supply mismatch caused by mishandled
// ante surplus
func FixTotalSupply(ctx sdk.Context, k *keeper.Keeper) error {
	balances := k.BankKeeper().GetAccountsBalances(ctx)
	correctSupply := sdk.ZeroInt()
	for _, balance := range balances {
		correctSupply = correctSupply.Add(balance.Coins.AmountOf(sdk.MustGetBaseDenom()))
	}
	totalWeiBalance := sdk.ZeroInt()
	k.BankKeeper().IterateAllWeiBalances(ctx, func(aa sdk.AccAddress, i sdk.Int) bool {
		totalWeiBalance = totalWeiBalance.Add(i)
		return false
	})
	weiInUsei, weiRemainder := bankkeeper.SplitUseiWeiAmount(totalWeiBalance)
	if !weiRemainder.IsZero() {
		logger.Error("wei total supply has been compromised as well; rounding up and adding to reserve")
		if err := k.BankKeeper().AddWei(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName), bankkeeper.OneUseiInWei.Sub(weiRemainder)); err != nil {
			return err
		}
		weiInUsei = weiInUsei.Add(sdk.OneInt())
	}
	correctSupply = correctSupply.Add(weiInUsei)
	currentSupply := k.BankKeeper().GetSupply(ctx, sdk.MustGetBaseDenom()).Amount
	if !currentSupply.Equal(correctSupply) {
		k.BankKeeper().SetSupply(ctx, sdk.NewCoin(sdk.MustGetBaseDenom(), correctSupply))
	}
	return nil
