### Title
`get_first_op_return_output` Accepts Attacker-Injected OP_RETURN in Payout Tx, Causing Honest Operator Collateral Slash - (File: `circuits-lib/src/bridge_circuit/mod.rs`, `core/src/verifier.rs`)

---

### Summary

The bridge circuit and the verifier's payout-detection logic both call `get_first_op_return_output` on the payout transaction to extract the operator's x-only public key. Because the payout transaction's user input is signed with `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`, any third party can attach additional outputs — including a fake OP_RETURN — to the transaction before it is mined. If a fake OP_RETURN is inserted at output index 1 (before the legitimate one at index 2), both the verifier and the bridge circuit silently consume the attacker-controlled key. This causes the verifier to flag the honest operator's kickoff as malicious and triggers a challenge the operator cannot win, resulting in permanent loss of their collateral.

---

### Finding Description

**Payout transaction structure (canonical)**

`create_payout_txhandler` builds the payout transaction with a fixed output layout:

| Index | Content |
|-------|---------|
| 0 | User payout output (covered by user's `SinglePlusAnyoneCanPay` signature) |
| 1 | Ephemeral anchor (CPFP) |
| 2 | `OP_RETURN` embedding the honest operator's x-only public key | [1](#0-0) 

The user's Taproot key-path signature covers only input 0 and output 0. Outputs 1 and 2 are **not** covered by the signature.

**`SinglePlusAnyoneCanPay` allows third-party output injection**

The parser enforces `TapSighashType::SinglePlusAnyoneCanPay` on every withdrawal signature: [2](#0-1) 

Under `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`, any party can create a competing transaction that keeps output 0 intact and inserts new outputs at positions 1, 2, … without invalidating the user's signature. The attacker broadcasts this competing transaction with a higher fee; if it is mined, the on-chain payout transaction has:

| Index | Content |
|-------|---------|
| 0 | User payout output (unchanged) |
| **1** | **Attacker-controlled fake `OP_RETURN`** |
| 2 | Anchor (shifted) |
| 3 | Honest operator's `OP_RETURN` (shifted) |

**`get_first_op_return_output` returns the fake output**

Both the verifier and the bridge circuit call `get_first_op_return_output` without checking the output index:

*Verifier (off-chain payout detection):* [3](#0-2) 

*Bridge circuit (zkVM, on-chain proof):* [4](#0-3) 

*Host-side deposit constant calculation:* [5](#0-4) 

In all three call sites the attacker's fake key is silently accepted.

**Downstream consequences**

1. **Verifier stores wrong operator key in DB.** `update_finalized_payouts` writes `(withdrawal_idx, payout_txid, fake_operator_pk, block_hash)` to the `withdrawals` table. [6](#0-5) 

2. **`is_kickoff_malicious` returns `true` for the honest operator.** When the honest operator later sends a kickoff transaction, the verifier compares the kickoff's embedded operator key against the stored (fake) key and concludes the kickoff is malicious. [7](#0-6) 

3. **Bridge circuit proof is unrecoverable.** The `deposit_constant` committed inside the kickoff transaction (via WOTS) is computed with the honest operator's key. The bridge circuit recomputes `deposit_constant` using the fake key from the payout tx's first OP_RETURN, producing a mismatched journal hash. The proof fails verification; the operator cannot disprove the challenge. [8](#0-7) 

---

### Impact Explanation

The honest operator:
- Has their kickoff transaction challenged by every verifier (all see the fake key).
- Cannot generate a valid bridge circuit proof (wrong `deposit_constant`).
- Loses their full operator collateral — a bridge-amount-sized UTXO — permanently.

The attacker can additionally insert their own operator key as the fake OP_RETURN. The verifier then accepts the attacker's kickoff as legitimate, allowing the attacker to claim the bridge-amount reimbursement that belongs to the honest operator. This constitutes direct theft of bridged BTC.

---

### Likelihood Explanation

- The payout transaction is broadcast to the public Bitcoin mempool before confirmation.
- `SinglePlusAnyoneCanPay` is explicitly enforced by the protocol, making the transaction structurally open to third-party output injection.
- The attacker only needs to pay a marginally higher miner fee to displace the honest operator's transaction.
- Any party (competing operator, watchtower, or external observer) can execute this with no privileged access.

---

### Recommendation

1. **Pin the OP_RETURN to a fixed output index.** Replace `get_first_op_return_output` with a direct index lookup (e.g., `payout_tx.output[2]`) in both the verifier and the bridge circuit, matching the canonical layout produced by `create_payout_txhandler`.

2. **Validate output count and structure.** Before extracting the operator key, assert that the payout transaction has exactly the expected number of outputs and that output 2 is an OP_RETURN containing exactly 32 bytes.

3. **Reject payout transactions with unexpected OP_RETURN outputs.** In `update_finalized_payouts`, if the transaction contains more than one OP_RETURN output, treat the payout as invalid (equivalent to an optimistic payout with `operator_xonly_pk = None`) rather than silently accepting the first one.

---

### Proof of Concept

1. Honest operator calls `withdraw(withdrawal_id=0, …)`. The operator constructs and broadcasts a payout transaction with outputs `[user_payout, anchor, OP_RETURN(honest_pk)]`.

2. Attacker observes the transaction in the mempool. Attacker constructs a competing transaction that keeps output 0 (`user_payout`) and inserts `OP_RETURN(attacker_pk)` at index 1, shifting the anchor to index 2 and the honest OP_RETURN to index 3. The user's `SinglePlusAnyoneCanPay` signature remains valid. Attacker adds their own input to pay a higher fee and broadcasts.

3. Attacker's transaction is mined. `update_finalized_payouts` calls `get_first_op_return_output`, receives the output at index 1 (`OP_RETURN(attacker_pk)`), and stores `attacker_pk` as `payout_payer_operator_xonly_pk` in the `withdrawals` table. [9](#0-8) 

4. Honest operator sends kickoff transaction (embedding `honest_pk` via WOTS). `is_kickoff_malicious` compares `honest_pk` against the stored `attacker_pk` — mismatch — returns `true`. Verifier challenges the kickoff. [10](#0-9) 

5. Honest operator attempts to generate a bridge circuit proof. The circuit calls `get_first_op_return_output` on the SPV-proven payout transaction, extracts `attacker_pk`, and computes `deposit_constant(attacker_pk, …)`. This does not match the `deposit_constant(honest_pk, …)` committed in the kickoff WOTS. Proof verification fails. [11](#0-10) 

6. Honest operator cannot disprove the challenge. Their collateral is burned. If the attacker used their own key, they can send a valid kickoff and claim the bridge-amount reimbursement.
