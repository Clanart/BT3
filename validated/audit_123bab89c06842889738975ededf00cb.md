### Title
Unchecked u64 arithmetic overflow bypasses the `NotEnoughFunds` check and produces a signed consensus-invalid transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
CVE-2020-14363 is an integer overflow that cascades into memory corruption. The analog in Serai is unchecked integer arithmetic on attacker-influenced 64-bit amounts inside `SignableTransaction::new`, where sums and additions of payment/input/fee values can overflow `u64` (wrapping in release builds, panicking in debug), defeating the solvency check that guards transaction construction.

### Finding Description
`SignableTransaction::new` computes three values with plain `u64` arithmetic:

- `input_sat`: `inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>()` (send.rs:175)
- `payment_sat`: `payments.iter().map(|payment| payment.1).sum::<u64>()` (send.rs:187)
- `needed_fee`: `fee_per_vbyte * vbytes` (send.rs:206)

The solvency guard is then evaluated with `input_sat < (payment_sat + needed_fee)` (send.rs:215), and the change path uses `input_sat.checked_sub(payment_sat + fee_with_change)` (send.rs:228). Both `payment_sat + needed_fee` and `payment_sat + fee_with_change` can wrap. If `payment_sat` alone exceeds `u64::MAX` (e.g., multiple payments near `u64::MAX`), the wrapped sum becomes small, `NotEnoughFunds` is not returned, `checked_sub` succeeds, and a transaction is constructed whose declared outputs exceed the inputs — and exceed Bitcoin's 21M-coin consensus cap. This transaction flows into `TransactionSignMachine::sign`, which produces Schnorr shares over `taproot_key_spend_signature_hash` and ultimately a fully signed `Transaction` that no Bitcoin node will ever accept (send.rs:373-397). In debug builds the same overflow panics, crashing the processor.

Payment amounts reach this code from `make_signable_transaction`, which maps `payment.balance.amount.0` (an arbitrary `u64` from a `Plan` derived from on-chain instructions) directly into `BSignableTransaction::new` (processor/src/networks/bitcoin.rs:433-452), so an unprivileged party who can get payment amounts into a plan (e.g., via burn/withdrawal instructions) controls the overflowing operands.

### Impact Explanation
The protocol signs and broadcasts a transaction that is consensus-invalid (outputs exceed the 21M BTC limit and/or the inputs). The plan is treated as signed yet can never confirm, so the associated inputs and the plan are effectively stuck: Serai reports/drives a completion path for funds that are not spendable on-chain, and repeated attempts burn operating costs. In debug/panic-on-overflow configurations it is a direct processor crash (liveness). This maps to the "funds reported received / transaction driven that is not spendable" and "signing of an unintended (invalid) message" classes.

### Likelihood Explanation
Requires a plan whose payments sum to more than `u64::MAX` sats (~1.8×10^19). Such amounts are not backed by real BTC supply, so exploiting the wrap for profit is limited — the realistic outcome is a signed, permanently-unconfirmable transaction and stuck/retried plans, i.e., a liveness/accounting-integrity failure rather than theft. Fee-rate overflow (`fee_per_vbyte * vbytes`) is not attacker-controlled since the fee comes from `median_fee`. Severity: Medium.

### Recommendation
Use checked/saturating arithmetic throughout `SignableTransaction::new`:

- `input_sat = inputs.iter().try_fold(0u64, |a, i| a.checked_add(i.output.value.to_sat()))`
- Same for `payment_sat`, and reject with a new error variant on overflow.
- Replace `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`, and treat overflow as `NotEnoughFunds`.
- Similarly bound `fee_per_vbyte * vbytes` via `checked_mul`/`saturating_mul`.

This mirrors the upstream fix pattern for CVE-2020-14363 (validate arithmetic before allocation/use).
