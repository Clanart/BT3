### Title
`ThresholdKeys::read` deserializes persisted key state without verifying the secret share matches the verification shares or group key - (File: crypto/dkg/src/lib.rs)

### Summary
The external report describes a state update that blindly trusts new data, breaking internal accounting because no consistency check is performed between the migrated representation and the semantics it encodes. The same class exists in Serai's DKG crate: `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574) reconstructs a full threshold key - parameters, interpolation, secret share, and the map of verification shares - purely from untrusted bytes, and `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349) validates only *shape* (counts, index ranges, interpolation applicability). It never checks the one invariant that gives the structure meaning: `C::generator() * secret_share == verification_shares[params.i()]`, nor that the verification shares lie on a consistent polynomial.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, `i`, an `Interpolation` discriminant, a `secret_share` scalar, and `n` verification-share points, then calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:625). `ThresholdKeys::new` only verifies that the number of shares equals `n` (crypto/dkg/src/lib.rs:355), that each participant index is `<= n` (crypto/dkg/src/lib.rs:361), and that `Constant` interpolation is only used when `t == n` (crypto/dkg/src/lib.rs:367). It then derives `group_key` from verification shares `1..=t` (crypto/dkg/src/lib.rs:376) and stores the attacker-controlled `secret_share` unchanged (crypto/dkg/src/lib.rs:384).

Two exploitable consequences follow:

1. **Secret share decoupled from verification share.** A serialized blob whose `secret_share` does not equal the discrete log of `verification_shares[i]` is accepted. On `view()` (crypto/dkg/src/lib.rs:463), the node interpolates the bogus scalar, and in `sign` produces signature shares that fail verification against the interpolated verification share - or, worse, pass verification under a mutated view the attacker constructed, since the attacker controls *all* fields including `t`, `n`, and the verification-share map.

2. **Attacker-chosen group key.** Because `group_key` is recomputed solely from the attacker-supplied verification shares, an attacker who can feed serialized `ThresholdKeys` to a consumer (a documented untrusted-bytes sink per scope) causes the victim to adopt an arbitrary group key whose discrete log the attacker knows, while the victim believes it holds a share of a DKG output. Any downstream component that registers or scans for this `group_key()` attributes funds/signing authority to a key the victim's real key shares do not back.

The missing check is a single scalar multiplication: after `ThresholdKeys::new`, `read` should assert `C::generator() * secret_share == verification_shares[&params.i()]` (adjusted for the interpolation combination for `Constant` mode) and reject otherwise.

### Impact Explanation
An attacker supplying a crafted serialization can make a consumer operate under a group key fully controlled by the attacker (key-import with attacker-known secret), or silently corrupt a node's share so it emits shares that either fail or satisfy only attacker-constructed verification data. For deployments that persist `ThresholdKeys` (e.g., `GeneratedKeysDb::read_keys` in processor/src/key_gen.rs:57 deserializes stored blobs via `ThresholdKeys::read`), any channel that can inject or corrupt these bytes - backup restore, migration, or an import API - yields keys that "load successfully" yet do not correspond to the real DKG, directly breaking the accounting invariant the external report describes.

### Likelihood Explanation
Likelihood depends on an untrusted byte path into `ThresholdKeys::read`; the format is explicitly exposed as a deserialization API and consumed by processor key-storage code. Within the accepted model (untrusted bytes to `ThresholdKeys::read`), the attack is deterministic: no consistency check exists, so any well-formed encoding is accepted. Severity is bounded to Medium because exploiting it requires reaching the deserialization path rather than a consensus-facing message, and honest-but-corrupted shares are largely detected at signing time rather than silently forging signatures.

### Recommendation
In `ThresholdKeys::read` (or `ThresholdKeys::new`), verify the secret share against its claimed verification share: for `Lagrange`, require `C::generator() * secret_share == verification_shares[&params.i()]`; for `Constant`, require `C::generator() * (secret_share * c[i-1]^{-1})` equals the share (or equivalently verify the interpolated relation). Additionally, when reconstructing keys whose shares were produced under a known polynomial, verify all `verification_shares` lie on the committed polynomial degree `t-1`. Return an `io::Error` on mismatch so inconsistent storage cannot migrate into an operational `ThresholdKeys`.

// Conceptual PoC against crypto/dkg/src/lib.rs ThresholdKeys::read
// (format mirrors crypto/frost/src/tests/vectors.rs:118-131)
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(1u16.to_le_bytes());            // t = 1
blob.extend(1u16.to_le_bytes());            // n = 1
blob.extend(1u16.to_le_bytes());            // i = 1
blob.push(1);                               // Interpolation::Lagrange
blob.extend(C::F::ONE.to_repr().as_ref());  // secret_share = 1
// verification share for participant 1 = G * 2  (MISMATCHED with secret_share)
blob.extend((C::generator() * C::F::from(2)).to_bytes().as_ref());

// Accepted: ThresholdKeys::new never checks G*1 == G*2
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
// group_key is attacker-chosen (G*2); the node's share signs as scalar 1
assert_eq!(keys.group_key(), C::generator() * C::F::from(2));
// Every signature share produced from view() will be inconsistent with
// the advertised verification share, or valid only under attacker views.
