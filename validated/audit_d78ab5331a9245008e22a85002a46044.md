### Title
Stale deadline validation in gasless swap admission allows delayed, price-manipulated execution - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The gasless swap transaction (`GaslessSwapTx`, KIP-247) deadline check performed in `checkBalanceForSwap` validates `swapArgs.Deadline` against `g.Chain.CurrentBlock().Time()` at the time the transaction is admitted to the mempool, not against the timestamp of the block the transaction is ultimately mined in.

### Finding Description
`checkBalanceForSwap` in [1](#0-0)  performs the deadline check only once when the transaction is inserted into the tx pool via `GetCheckBalance()` [2](#0-1) . Once a `GaslessSwapTx` passes this check it is tracked and can remain in the pool for up to `PendingTimeout`/`QueueTimeout` before being dropped, per `PreReset` [3](#0-2) . There is no re-validation of the deadline against the timestamp of the block that will actually include and execute the transaction (i.e., at block-building/`ExtractTxBundles` time in `kaiax/gasless/impl/builder.go` or on-chain inside `GaslessSwapRouter.SwapForGas`), unlike the reported Solidity anti-pattern where `block.timestamp` (or a stale/derived value) is used as the swap deadline instead of independently verifying freshness at the moment of execution. This mirrors the underlying root cause of the external report: a "deadline" is checked against a point-in-time value that is not guaranteed to correspond to the block of execution, allowing a block proposer to consciously delay execution.

### Impact Explanation
A block proposer/builder controls when a validated `GaslessSwapTx` is actually bundled and executed (via `ExtractTxBundles`/`FilterTxs` in `kaiax/gasless/impl/builder.go` and `kaiax/auction/impl/builder.go`). Because the deadline is enforced only at admission time using the then-current block time, a proposer can strategically hold a gasless swap in the pool and execute it in a later block after price movement, extracting value from the user's `minAmountOut`/`amountRepay` parameters set at signing time — the classic MEV/deadline-manipulation impact described in the external report, but realized through the node's transaction-admission logic rather than the Solidity contract itself.

### Likelihood Explanation
Any block proposer on Kaia (a role reachable simply by being an active consensus node in normal operation, not requiring any privileged compromise) can withhold already-pool-admitted, already-validated gasless swap transactions up to the pool's timeout windows, making this reachable purely through the proposer's routine block-assembly decisions on transactions submitted by ordinary users.

### Recommendation
Re-validate `swapArgs.Deadline` at the moment of block building/inclusion (e.g., in `ExtractTxBundles`/bundle generation) against the timestamp of the block actually being assembled, not just at pool-admission time, and consider re-checking again as part of `IsReady`/`PostInsertBlock` execution paths so a transaction whose deadline has elapsed while sitting in the pool is dropped rather than executed.

### Proof of Concept
1. User signs and submits a `GaslessSwapTx` with `deadline = currentBlockTime + 300`.
2. `checkBalanceForSwap` [1](#0-0)  passes since `deadline >= currentBlock.Time()`.
3. The tx is added to `knownTxs`/pending pool and remains valid for up to `PendingTimeout` [4](#0-3)  without deadline re-check.
4. A malicious/opportunistic proposer withholds the tx from immediate inclusion, waits for favorable price movement on the Uniswap pool backing `GaslessSwapRouter`, then includes it once `minAmountOut` is still (barely) satisfiable but the user receives worse execution than at submission time — with no on-chain or off-chain re-check ever comparing `deadline` to the actual inclusion block's timestamp.

// PreReset removes timed out tx from the tx pool and knownTxs.
func (g *GaslessModule) PreReset(oldHead, newHead *types.Header) []common.Hash {
	g.knownTxsMu.Lock()
	defer g.knownTxsMu.Unlock()

	drops := make([]common.Hash, 0)

	for hash, knownTx := range *g.knownTxs {
		// remove pending timed out tx from tx pool
		if knownTx.status == TxStatusPending && knownTx.elapsedPromotedTime() >= PendingTimeout {
			drops = append(drops, hash)
		}
		// remove queue timed out tx from tx pool
		if knownTx.status == TxStatusQueue && knownTx.elapsedAddedTime() >= QueueTimeout {
			drops = append(drops, hash)
		}
		// remove known timed out tx from knownTxs
		if knownTx.elapsedPromotedOrAddedTime() >= KnownTxTimeout {
			g.knownTxs.delete(hash)
		}
	}

	return drops
}
