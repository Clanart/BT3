### Title
Unauthorized ERC20 drain via shared `CallDispatcher` and unrestricted arbitrary-call `order.predispatch.call` / `order.output.call` - (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The IntentGateway's predispatch/postdispatch calldata feature routes arbitrary attacker-supplied `Call[]` through a single, permissionless, shared `CallDispatcher` contract. Any user placing or filling an order controls the `to`/`data` of the calls the dispatcher executes. Since users must grant the `dispatcher` contract itself an ERC20 allowance to use the predispatch swap-then-escrow feature, that lingering allowance is not scoped to any specific order — it is a blanket approval on a shared contract that any other, unrelated order's calldata can invoke.

### Finding Description
This mirrors the ApeCoinStaking "split pair" bug's core invariant break: a shared custodial primitive (there, the `NTokenBAYC` reserve pool that indiscriminately forwards its *entire* balance to whoever triggers the withdraw path; here, the shared `CallDispatcher` that indiscriminately executes whatever calldata whoever triggers `placeOrder`/`fillOrder` supplies) does not bind the beneficiary/amount to the specific actor whose funds are involved.

`CallDispatcher.dispatch` is a bare `external` function with zero caller restriction [1](#0-0) . It is invoked by `IntentGatewayV2`/`IntentsBase` for:
- `order.predispatch.call` during `placeOrder` — before assets are escrowed, executed via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [4](#0-3) 
- `order.output.call` during `_execute`, executed via `ICallDispatcher(dispatcher).dispatch(order.output.call)` after a fill [5](#0-4) 

Both `order.predispatch.call` and `order.output.call` are attacker/order-placer-controlled bytes with no validation of which contracts/functions they may target — `CallDispatcher` only checks that `to` has code, not that `to`/`data` relate to the caller's own order [1](#0-0) .

Because the predispatch flow requires the order placer to have an ERC20 approval **on the dispatcher address itself** (`IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` in the tron/EVM `IntentGatewayV2.placeOrder` path) [6](#0-5) , any user who has ever approved the shared `dispatcher` contract for a token leaves that allowance live and usable by **anyone else's** order. A malicious actor can place (or fill) an order whose `predispatch.call`/`output.call` encodes `Call({to: token, data: abi.encodeWithSelector(IERC20.transferFrom.selector, victim, attacker, amount)})`. When `CallDispatcher.dispatch` executes this, `msg.sender` as seen by the ERC20 is the `CallDispatcher` contract, so the transfer succeeds against `allowance[victim][dispatcher]` regardless of which order or user triggered it — exactly the "unrelated third party sweeps funds belonging to someone else via a shared custodial account" pattern from the ApeCoin BAKC report.

### Impact Explanation
Any ERC20 tokens a legitimate IntentGateway user has approved to the shared `CallDispatcher` (a prerequisite for using the documented predispatch swap-then-escrow feature) can be drained by an unrelated, unprivileged attacker simply by placing or filling a different order with malicious `predispatch.call`/`output.call` bytes. This is unauthorized execution and fund theft with an arbitrary attacker-chosen beneficiary and amount — squarely within the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" / "transaction manipulation" categories, requiring no relayer, prover, or admin compromise.

### Likelihood Explanation
Likelihood is driven entirely by how many users leave a standing ERC20 approval on the dispatcher after using predispatch once (typical ERC20 UX approves a generous or infinite amount, and nothing in the flow instructs users to revoke it after their order settles). No special timing, race condition, or privileged role is needed — the attack is a single `placeOrder`/`fillOrder` call with crafted calldata.

### Recommendation
- Scope every allowance a user grants for predispatch strictly per-order (e.g., have `IntentGatewayV2` pull tokens to itself and only forward the exact needed amount to `CallDispatcher` for that single call, rather than requiring a standing approval on the shared dispatcher).
- Have `CallDispatcher` accept only calls from the registered `IntentGatewayV2` instance (`onlyGateway`), and additionally restrict callable targets to a per-call allowlist supplied by the gateway (e.g., router/token addresses relevant to the order being processed), never an unconstrained attacker-chosen `to`.
- Consider deploying a fresh, ephemeral dispatcher (e.g., via `CREATE2` per order/commitment) so no shared allowance state persists across unrelated orders.

### Proof of Concept
1. Alice places an order using the predispatch feature (e.g., swap ETH→DAI) which requires her to `approve(dispatcher, largeAmount)` on DAI so the gateway can `safeTransferFrom(alice, dispatcher, amount)` per `evm/tron/contracts/apps/IntentGatewayV2.sol:392-400`. Her order completes, but the DAI allowance to `dispatcher` remains (e.g. `type(uint256).max` from a typical approve-once UX).
2. Attacker (Mallory) crafts a new order whose `predispatch.call` is `abi.encode([Call({to: DAI, value: 0, data: abi.encodeWithSelector(IERC20.transferFrom.selector, alice, mallory, aliceRemainingAllowanceOrBalance)})])`.
3. Mallory calls `placeOrder`. `IntentGatewayV2` invokes `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` per `evm/src/apps/IntentGatewayV2.sol:203-227`.
4. `CallDispatcher.dispatch` executes the call with no restriction on `to`/`data` [1](#0-0) ; since `msg.sender` inside the DAI contract is `dispatcher`, `transferFrom(alice, mallory, amount)` succeeds against Alice's standing allowance.
5. Mallory's DAI balance increases by Alice's funds, entirely outside any order/commitment accounting — a direct, unauthorized fund transfer analogous to Ben sweeping Jimmy's staked ApeCoin out of the shared `NTokenBAYC` pool.
