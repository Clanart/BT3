### Title
Cached FROST preprocess seed is never deleted after `sign`, so re-execution/reset reuses the same nonce and leaks the MuSig private key share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug is a stale-state/use-after-release flaw: an error path releases a resource, yet a later call dereferences the stale pointer because the released state was not invalidated. The Serai analog is in the coordinator's MuSig signing protocol: `preprocess_internal` persists a `CachedPreprocess` seed in `CachedPreprocesses` keyed only by `context`, and `share_internal` rebuilds the signing machine from that *same* seed every time it runs. Because the seed deterministically regenerates the identical nonce commitments, any second invocation of `sign` under the same context — after a reboot, re-execution, or a repeated/reattempted signing round — reuses the nonce, which FROST's own documentation states enables recovery of the private key share.

### Finding Description
`preprocess_internal` stores a seeded preprocess in the DB the first time a context is seen and then reloads it on every subsequent call:

`share_internal` then calls `self.preprocess_internal(participants).0` again and feeds the reconstructed machine into `machine.sign(preprocesses, msg)`: [2](#0-1) 

The entry is never removed or invalidated — there is no `CachedPreprocesses::del`/delete anywhere in the codebase (only the four references in this file). This mirrors the kernel flaw exactly: state that must be consumed-once survives the "release" (completion/failure/reset of a signing attempt) and is silently reused on the next access.

Serai's own comments concede the danger and pin safety entirely on the assumption that the BFT layer will never present distinct inputs for the same context: "it is explicitly unsafe to reuse nonces across signing sessions… In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" [3](#0-2) . The same comment block explicitly flags partial rebuilds and re-execution as an unresolved bound ("This does set a bound preventing partial rebuilds", plus a TODO to check that on-chain commitments match the presumed preprocess) [4](#0-3) .

The FROST library is unambiguous about the consequence: "This cached preprocess MUST only be used once. Reuse of it enables recovery of your private key share" [5](#0-4) , and `spec/cryptography/FROST.md` repeats that "the only way for this seeded RNG to fail is if a preprocess is loaded multiple times" — which is precisely what this code does on every `share_internal` call and on any post-reset re-execution.

Contrast with the processor signers, which deliberately *don't* persist nonces across reboots for this reason ("While we could apply similar tricks as the DKG (a seeded RNG)… it's not worth the complexity when messing up here leaks our secret share") [6](#0-5) .

### Impact Explanation
If `share_internal` (or `preprocess_internal` via a second signing round for the same `context`) executes twice with different counterparties' preprocesses or a different message, the coordinator produces two Schnorr signature shares under the same secret nonce. With the aggregate nonce `R` fixed and the challenge varying via the other inputs, two shares `(s, s')` satisfying `s = k + c·x` let anyone observing both published shares solve for the key share `x = (s − s') / (c − c')`. Since this is the coordinator-side MuSig over validator keys (`musig(...)` with the validator set context), recovery of this share compromises the validator root-of-trust key used for DKG confirmation — a full key-share recovery, the highest-impact outcome in scope.

### Likelihood Explanation
Triggering does not require a malicious validator or broken BFT in the rejected sense — it requires only that the same context be signed for twice with differing inputs. Reachable paths include: (a) a coordinator reboot or crash between `preprocess` and `share` phases, after which re-execution rebuilds from the identical seed (the file's own header acknowledges re-execution is the design and that partial rebuilds are an unhandled bound); (b) any logical flaw letting new finalized messages overwrite prior ones, which the comments explicitly list as a residual risk rather than ruling out. The unprivileged-party angle: the differing input is a set of `preprocesses`/`msg` bytes supplied by counterparties through `read_preprocess`/`sign`, i.e., public protocol data the attacker causes to be signed — matching the reachability rules. Likelihood is moderate (requires a retry/reset race or a tributary-level duplicate round), keeping this at High rather than Critical.

### Recommendation
Consume the cached seed exactly once: delete `CachedPreprocesses` for the context in a `Drop`/post-`sign` step inside `share_internal` (or before broadcasting shares), so a second call fails closed instead of regenerating the nonce. Additionally implement the already-noted TODO: before publishing a share, verify that the commitments implied by the rebuilt preprocess match the commitments actually finalized on-chain for this context, aborting if they differ — this converts any double-sign attempt into a detectable no-op rather than a key-leak.

### Proof of Concept
Conceptual, from the code paths above:

1. Coordinator runs `preprocess_internal(ctx)` → stores seed `S` under `CachedPreprocesses[ctx]`, broadcasts `Preprocess` with nonce commitments `R_ours = g^d, g^(b·e)` derived from `S`.
2. Signing round 1: `share_internal` rebuilds machine from `S` → `sign(preprocesses_A, msg_A)` → publishes share `s_1 = d + b·e + c_1 · λ·x` (simplified; `c_1` binds `msg_A` and the aggregate nonce).
3. Trigger: reboot/re-execution or a second finalized round for `ctx` with different inputs `preprocesses_B`/`msg_B` (e.g., a different participant subset or a different `set_keys_message`).
4. `share_internal` again loads `S` (never deleted) → same `d, e` → publishes `s_2` with the same local nonce but new challenge `c_2`.
5. Observer computes `λ·x = (s_1 − s_2) / (c_1 − c_2)`, recovering the coordinator's interpolated private key share — matching exactly the "reuse of cached preprocess leaks the private key share" warning in `crypto/frost/src/sign.rs:211-213`.
