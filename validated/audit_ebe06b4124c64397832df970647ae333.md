Based on the strongest analog found in the codebase, the OAuth `state`/CSRF flow in `sign-in-store.ts` is correctly validated (state token is compared before minting an account), so that isn't a viable finding. The better structural analog to the report's core flaw — *a security-relevant value gets silently reset/rewritten based on an identity change, without confirming with the entity relying on it, and without validating the new value strongly enough* — is the automatic remote-URL rewrite logic driven by GitHub API data.

### Title
Automatic remote URL rewrite trusts attacker-influenced GitHub API `clone_url` without validating the destination host - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` silently rewrites a repository's `origin` remote URL whenever the GitHub API reports a different `clone_url` than what Desktop has cached, as long as the URL protocol is unchanged and the user hasn't manually diverged the remote from the previously-cached API URL. The check does not verify that the new `clone_url` points to the same host/owner/name the user originally trusted — it only requires the URL scheme to match.

### Finding Description [1](#0-0) 

The function computes:
- `urlsMatch` — whether the current remote already matches the new API `clone_url`.
- `protocolsMatch` — whether the URL *scheme* (http/ssh) of the old and new URLs match.
- `remoteUrlUnchanged` — whether the currently configured remote still matches the previously cached `gitHubRepository.cloneURL`.

If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, Desktop calls `gitStore.setRemoteURL(...)` and rewrites `origin` to the new `clone_url` [2](#0-1) , without any user prompt or confirmation dialog.

Crucially, `protocolsMatch` only compares `URL.parse(...).protocol` (e.g., `"https:"` vs `"https:"`), not hostname, owner, or repository name [3](#0-2) . This is analogous to the report's broken invariant: a security-relevant value (nonce / here, the push-fetch destination) is reset/updated as a side effect of an "identity" change (account/repo transfer as reported by the API) without a strong integrity check tying the new value to the same trusted entity.

### Impact Explanation
If the `clone_url` returned by the GitHub API (or GitHub Enterprise instance, or any proxy/gateway in front of it) can be influenced by an attacker — for example, a compromised/malicious GHE server, a MITM on an internal network for an Enterprise install, or a `clone_url` field controlled through a repository-rename/transfer race — Desktop will silently repoint the user's `origin` remote to the attacker's URL as long as the scheme matches (e.g., `https://` to `https://`), with zero host/owner verification and zero user confirmation. Any subsequent `git push` or `git fetch` from Desktop will then target the attacker-controlled remote, which is a silent corruption of what the user pushes — the exact class of "silent corruption of what the user commits or pushes" called out as valid impact.

### Likelihood Explanation
This requires the attacker to control (or spoof) a GitHub API response object (`clone_url`) for a repository the user has already added to Desktop, and the change must occur while `remoteUrlUnchanged` is still true (i.e., the user hasn't manually edited the remote since the last cached value). This is plausible for GitHub Enterprise Server deployments behind a compromised/malicious proxy, or scenarios where API responses can be tampered with, matching the report's "External API object attacker control" primitive rather than requiring local access or credential theft.

### Recommendation
- Before silently rewriting `origin`, verify that the new `clone_url` still resolves to the *same* trusted host (and ideally warn/prompt on owner/name changes, e.g., repository transfer), not merely that the URL scheme is unchanged.
- Require explicit user confirmation (similar to the "unsafe directory" trust prompt pattern already used elsewhere in Desktop, e.g. `app/src/ui/missing-repository.tsx`) before automatically changing a remote that will be used for push/fetch and credential resolution.
- Log/audit remote URL auto-rewrites so users can detect unexpected changes.

### Proof of Concept
1. User has a repository in Desktop tracking `origin` = `https://github.example.com/org/repo.git`, matching the cached `gitHubRepository.cloneURL`.
2. An attacker who can influence the API response served to Desktop (compromised GHE instance / proxy) returns `clone_url: "https://attacker.example.com/org/repo.git"` for the same repository object.
3. On the next repository refresh, `updateRemoteUrl` sees `protocolsMatch` (both `https:`) and `remoteUrlUnchanged` (user hadn't manually edited remote), and `!urlsMatch`, so it silently calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/org/repo.git')` [4](#0-3) .
4. The user's next push goes to `attacker.example.com` without any warning.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
