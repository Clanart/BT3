## Title
Rewards queued during zero-`totalStaked` periods can be captured entirely by an attacker who deposits and calls the permissionless `donateRewards` right after, stealing previously-queued yield - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool` (and its clones `BaseRewardPoolV2.sol`, `mWOMSVBaseRewarder.sol`, `vlMGPBaseRewarder.sol`, `DelegateVoteRewardPool.sol`) defer reward accounting into a `queuedRewards` bucket whenever `totalStaked() == 0` at the time a reward is provisioned. This mirrors the reported bug class: an accounting-skip condition ("zero coverage" ↔ "zero totalStaked") causes value to sit un-distributed in the contract until a later, unrelated provisioning call sweeps the *entire* accumulated amount into the *current* `rewardPerTokenStored`, based on whoever is staked at that later moment rather than who accrued it.

### Finding Description
`_provisionReward` in [1](#0-0)  checks `this.totalStaked() == 0` and, if true, adds the incoming reward to `rewardInfo.queuedRewards` instead of updating `rewardPerTokenStored`. On the next call where `totalStaked() > 0`, all outstanding `queuedRewards` are added to the new `_amountReward` and distributed via `rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked()` — using `totalStaked()` measured at that later moment.

`totalStaked()` itself simply reads `IERC20(stakingToken).balanceOf(operator)` [2](#0-1) , i.e., MasterMagpie's total staked balance for that token — with no accrual-window tracking of who was staked while the reward sat queued.

Critically, `donateRewards` is a **public, unprivileged** entry point into `_provisionReward`: [3](#0-2) . This means any wallet can trigger the flush of accumulated `queuedRewards` at a time of their choosing.

Attack flow (unprivileged wallet only):
1. Wait for (or induce, e.g., by being among the last to withdraw) a period where `totalStaked() == 0` for a pool, while the manager continues to `queueNewRewards` (a normal periodic emission/fee operation) — these all get parked in `queuedRewards`.
2. Deposit a small stake via `MasterMagpie.deposit` so the attacker becomes effectively the sole staker (`totalStaked() > 0`), see deposit path in [4](#0-3) .
3. Call the permissionless `donateRewards` with a trivial amount (even 1 wei) on the reward pool. This flips the `else` branch in `_provisionReward`, flushing the entire `queuedRewards` bucket into `rewardPerTokenStored`, computed against the attacker's own (currently dominant) stake.
4. Claim/withdraw, capturing rewards that accrued while other, unrelated stakes/withdrawals were happening — value never contributed by the attacker.

### Impact Explanation
This lets an ordinary wallet redirect previously-queued (deferred) reward-token yield to itself instead of it being fairly distributed based on actual staking time/proportion, constituting theft of otherwise-unclaimed yield reachable purely through public `deposit`/`withdraw`/`donateRewards` calls — no privileged role required.

### Likelihood Explanation
Requires the pool to pass through a `totalStaked() == 0` state while a manager is queuing rewards (plausible during low-TVL periods, pool bootstrapping, or after mass withdrawal), and then requires only a normal deposit plus a call to the public `donateRewards` function — both fully permissionless actions available to any wallet.

### Recommendation
Do not flush the full historical `queuedRewards` proportionally to `totalStaked()` measured only at the next provisioning call. Instead, either (a) route rewards accrued while `totalStaked() == 0` to a separate destination (e.g., protocol treasury/fee collector) rather than back into `rewardPerTokenStored`, or (b) require a minimum bootstrapping delay / snapshot mechanism so newly-deposited stakers cannot immediately capture previously queued rewards, similar to the report's suggested mitigation of not routing zero-coverage-period funds into the same accounting path used for active-period rewards.

### Proof of Concept
1. Pool P has zero stakers (`totalStaked() == 0`).
2. Manager calls `queueNewRewards(1000, rewardToken)` several times over time → `rewards[rewardToken].queuedRewards` accumulates to a large value; none of it is reflected in `rewardPerTokenStored`.
3. Attacker calls `MasterMagpie.deposit(stakingToken, 1)` — now `totalStaked() == 1` (attacker only).
4. Attacker calls `donateRewards(1, rewardToken)` on `BaseRewardPool` — triggers `_provisionReward`, `totalStaked() != 0`, so all `queuedRewards` + the 1 wei donation are folded into `rewardPerTokenStored`, entirely attributed to the attacker's stake of `1`.
5. Attacker calls `MasterMagpie.withdraw` then claims via `getReward`, receiving the entire previously-queued reward pot instantaneously.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```
