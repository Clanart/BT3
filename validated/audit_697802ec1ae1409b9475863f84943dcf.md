### Title
Coinbase (immature) outputs reported as spendable received funds by `Scanner::scan_block` - (networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class from the external report is "an irreversible action completes (transfer/burn) while the dependent downstream step can silently fail, leaving funds locked." In `serai--020`, the analogous shape is "funds reported received that are not spendable." `Scanner::scan_block` in `networks/bitcoin/src/wallet/mod.rs` iterates over `block.txdata` including `txdata[0]` (the coinbase transaction) and returns matching outputs as ordinary `ReceivedOutput`s. Coinbase outputs are consensus-immature for 100 blocks, so any spend built from them via `SignableTransaction::new` produces a transaction that can never be included, while the scanner and upstream accounting treat the funds as received.

### Finding Description
`Scanner::scan_transaction` (wallet/mod.rs:199-214) matches transaction outputs purely on `output.script_pubkey` against the registered script set, with no check on the containing transaction type. `Scanner::scan_block` (wallet/mod.rs:221-227) calls it on every transaction in the block, including the coinbase. A `ReceivedOutput` carries only `{ offset, output, outpoint }` (wallet/mod.rs:90-97) — there is no field distinguishing an immature coinbase output from a normal spendable one, and no way for a downstream consumer holding only a `ReceivedOutput` to detect immaturity.

Downstream, `SignableTransaction::new` (wallet/send.rs:150-256) accepts any `Vec<ReceivedOutput>` and constructs a transaction spending their `outpoint`s; `TransactionSignMachine::sign` (wallet/send.rs:355-398) then produces valid BIP-340 signature shares over `Prevouts::All` for a transaction that is consensus-invalid until maturity. Nothing in the spend path re-checks whether an input outpoint refers to a coinbase output. The only mitigation is a doc comment on `scan_block` (wallet/mod.rs:217-220) noting that a post-processing pass "is needed" — the API itself performs no filtering and exposes no flag enabling callers who don't perform the pass to detect the condition.

The reachable trigger: a miner (an unprivileged party relative to the multisig) can include a coinbase output paying the multisig's P2TR script — or any registered offset script — in a block they mine. The scanner emits it identically to a normal deposit.

### Impact Explanation
- Funds are reported as received/owned while they are not yet spendable, corrupting the balance/planning view for up to 100 blocks.
- `SignableTransaction::new` will select the immature output as an input, and the threshold signing flow will produce signatures for a transaction that is rejected by the network (immature coinbase spend). Because `complete` only assembles witnesses (wallet/send.rs:413-428) without validating spendability, the failure surfaces only at broadcast, after the full signing round completed — mirroring the reported class where the burn/lock succeeds and the dependent action fails.
- Repeated replanning can keep selecting the same immature input, repeatedly burning signing rounds on transactions that cannot confirm.

### Likelihood Explanation
Low-to-moderate. It requires a miner to direct coinbase rewards to the multisig script (or a registered offset script). No economic benefit to the miner is needed — it can be done intentionally to pollute the scanner's output set, and pools with vanity/donation payouts could do so incidentally. The window of exposure is the 100-block maturity period per affected output.

### Recommendation
Have `scan_block` skip `block.txdata[0]` (or check `tx.is_coinbase()` and exclude its outputs), since the scanner's outputs feed directly into spend planning. If scanning coinbase transactions must be supported, add a maturity flag to `ReceivedOutput` and have `SignableTransaction::new` reject immature inputs rather than relying on callers to post-filter.

### Proof of Concept
1. A miner mines a block whose coinbase transaction pays `p2tr_script_buf(group_key)` an amount ≥ `DUST`.
2. `Scanner::new(key)` + `scan_block(&block)` returns a `ReceivedOutput` for the coinbase output — indistinguishable from a normal deposit.
3. Construct `SignableTransaction::new(vec![coinbase_output], &payments, change, None, fee)` — it succeeds; `sign`/`complete` produce a fully signed transaction.
4. Broadcasting the transaction fails with "bad-txns-premature-spend-of-coinbase" — the funds were reported received and a signing round was consumed, yet the spend can never confirm until maturity, with no in-band signal of why.
