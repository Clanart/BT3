Key finding: `multiclaimOnBehalf` is protected by `_onlyCompounder` [1](#0-0) , meaning only the address set as `compounder` in `MasterMagpie` (presumably the `ManualCompound` contract itself, set via `setCompounder`) can call it. This directly contradicts the premise of the question, which requires an "unprivileged EOA or attacker-deployed contract" to invoke `compound()` and have `multiclaimOnBehalf` execute — but `ManualCompound.compound()` itself calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(...)` internally at line 125 [2](#0-1) , using `msg.sender` as the account being claimed for. Since `ManualCompound` is presumably the registered `compounder`, this call succeeds regardless of who calls `compound()` externally — `compound()` itself has no access control.

However, the actual scenario premised in the question — "another user's `multiclaimOnBehalf` is pending in the mempool and will land in the same block" — is not possible for an unprivileged attacker to set up, because `multiclaimOnBehalf` cannot be called directly by any other user; it can only be triggered through `ManualCompound.compound()` (assuming `ManualCompound` is the sole `compounder`). So the "victim's pending multiclaimOnBehalf" would actually be another user's call to `compound()`, which itself calls `multiclaimOnBehalf` on their behalf.

Now examining the actual sweeping logic: the second loop in `compound()` sweeps the **entire contract balance** of each configured reward token via `IERC20(_tokenAddress).balanceOf(address(this))` at line 144, not a delta scoped to what the current caller's claim produced [3](#0-2) . This full-balance-sweep pattern is a real and serious anti-pattern: if a victim's `multiclaimOnBehalf`-mediated `compound()` call is pending and lands in the same block after an attacker's `compound()` call (or vice versa — the attacker's call lands after the victim's tokens have been transferred to `ManualCompound` but before the victim's own sweep completes), the attacker's second loop will scoop up the victim's unclaimed reward tokens sitting in the contract and route them to `msg.sender` (the attacker) via `convertFor`, `lockFor`, `depositFor`, or `safeTransfer` — all using `msg.sender` as the recipient [4](#0-3) .

This is a genuine reentrancy/interleaving risk grounded in balance-based accounting rather than claim-scoped delta accounting, and it is theoretically triggerable by two calls to `compound()` racing in the same block — no privileged role is needed to call `compound()` itself. But note: this requires the victim's `compound()` transaction to be mined **before** the attacker's, and the attacker's transaction to execute in the same block after the victim's tokens have arrived at `ManualCompound` but before the victim's second loop runs — which is not achievable purely via mempool ordering within a single block unless the attacker can insert their transaction between the victim's `multiclaimOnBehalf` call and the victim's own sweep loop, which are not two separable transactions (they occur within the same call in the same transaction, atomically). Since `multiclaim` and the sweep both happen within one atomic `compound()` transaction call by the victim, there is no way for an attacker's separate transaction to be interleaved *between* the victim's internal `multiclaimOnBehalf` and the victim's internal sweep loop — a single Solidity call executes without interruption from other transactions. Thus, the "front-run inside a single tx" premise described in the question does not hold under EVM's non-interleaving transaction execution model.

The only viable race is: attacker's `compound()` transaction executes **after** the victim's full transaction completes but the victim's transaction somehow left funds in `ManualCompound` — but `compound()`'s second loop already fully sweeps every reward token's `balanceOf(address(this))` down to zero (or up to whatever transfer succeeded) within the same transaction, so there is no leftover balance for the next caller to sweep, **unless** the reward's disposition path (`convertFor`, `lockFor`, `depositFor`) reverts/leaves dust or if the reward token is not registered in `rewards[]` (in which case the caller doesn't receive it via the second loop, but it's returned in the first loop already, scoped to `_rewards[i][j]`) [5](#0-4) . For tokens that ARE in `compoundableRewards`, the full balance is swept every time by the caller — meaning if two transactions (attacker's and victim's) both claim into `ManualCompound` and are mined in the same block in sequence, whichever transaction's sweep loop runs *last* (in block order) will collect the combined balance of both claims and route the whole sum to that transaction's `msg.sender`. Since transaction ordering within a block is determined by the miner/builder (which the attacker cannot fully control, but MEV searchers commonly can via same-block bundling or priority gas auctions), an attacker who front-runs is not the one guaranteed to receive the surplus — the second-executing transaction receives the surplus, meaning the attacker must **back-run**, not front-run.

Given the premise states the victim's `multiclaimOnBehalf`-triggering call is already pending and will land in the same block, an attacker (as an unprivileged EOA) could submit a `compound()` call with high gas price to execute immediately after the victim's transaction in the same block, and because the second sweep loop uses `balanceOf(address(this))` rather than a per-call delta, the attacker's sweep would capture and forward the victim's unclaimed reward balance to the attacker's own address via `_convertor.convertFor(..., msg.sender, ...)`, `_locker.lockFor(..., msg.sender)`, `_helperAddress.depositFor(..., msg.sender)`, or `safeTransfer(msg.sender, ...)`.

This is a plausible and serious vulnerability matching the balance-based sweep root cause described. I cannot fully verify preconditions such as whether front-running/backrunning bots on the target chain make this reliably exploitable, or whether `ManualCompound` is guaranteed to be the sole registered `compounder` in every deployment — that would require checking deployment scripts, which are outside what I found. Based on the code available, however, the vulnerability is real and matches the finding.

### Title
`ManualCompound.compound` sweeps full contract token balance instead of caller-scoped rewards, enabling theft via same-block backrunning - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()`'s second loop distributes reward tokens based on `IERC20(_tokenAddress).balanceOf(address(this))` rather than the amount actually produced by the caller's own claim [3](#0-2) . If a victim's `compound()` call lands earlier in a block and any downstream disposition step leaves tokens un-swept, or more directly, if an attacker's `compound()` transaction is mined immediately after a victim's in the same block, the attacker's sweep can capture and route the victim's claimed rewards to the attacker via `convertFor`/`lockFor`/`depositFor`/`safeTransfer` calls that all use `msg.sender` as the recipient.

### Finding Description
`compound()` has no access control and can be called by any unprivileged address [2](#0-1) . It calls `multiclaimOnBehalf(_lps, _rewards, msg.sender)` on `MasterMagpie`, which is restricted to `compounder` only, but this restriction is satisfied because `ManualCompound` itself is presumably registered as `MasterMagpie.compounder` [1](#0-0) . After claiming, the function's second loop iterates all registered `rewards[]` tokens and reads `IERC20(_tokenAddress).balanceOf(address(this))` as the amount to convert/lock/deposit/transfer to `msg.sender`, rather than tracking a per-call delta tied to the caller's own claim [6](#0-5) . Any reward token balance sitting in the contract at the time this loop executes — including balances belonging to a different user's pending or recently-completed claim — is swept to the current caller.

### Impact Explanation
Direct theft of another user's claimed but not-yet-fully-disposed reward tokens, matching "Direct theft of user funds." The magnitude equals the reward token balance present in the contract at loop execution time.

### Likelihood Explanation
Requires an attacker to submit a `compound()` transaction that executes immediately after a victim's `compound()`/claim transaction within the same block (a backrun), which is technically and economically feasible for MEV-aware actors without needing capital beyond gas, and is repeatable across blocks whenever victim claims occur. Note: strict front-running (attacker's tx before victim's, within the same atomic sequence) cannot interleave with the victim's single-transaction internal execution, so the exploitable ordering is specifically "attacker backruns victim's claim transaction," not "attacker front-runs."

### Recommendation
Track reward token balances immediately before and after the `multiclaimOnBehalf` call within the same transaction (delta accounting) rather than using the raw `balanceOf(address(this))`, so that only tokens produced by the current caller's own claim are distributed to that caller.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, register `ManualCompound` as `compounder`, add pools/rewarders emitting a compoundable reward token, and configure `ManualCompound.addReward` for that token with `convertor = address(0)`, `locker = address(0)`, `tokenHelper = address(0)` so the token defaults to `safeTransfer(msg.sender, receivedBalance)`.
2. Victim stakes into a pool, accrues claimable reward.
3. Victim calls `compound(...)`; before its second-loop sweep executes, have attacker's transaction land immediately after in the same block (simulate via Hardhat's manual mining / same-block tx ordering) calling `compound(...)` with an empty/no-op claim (`_lps=[]`, `_rewards=[]]`) so no reward is transferred to the contract by the attacker's own claim.
4. Assert: attacker's balance of the reward token increases by an amount equal (or partially equal, depending on execution order) to the victim's claimed reward, while the victim receives zero, violating "settlement scoped to the reward tokens the caller's claim actually produced."
