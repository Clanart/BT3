### Title
Untrusted offset in deserialized `ReceivedOutput` silently re-derives an inconsistent spend key, causing funds to be reported received that are not spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
CVE-2016-10151's class is: *a comparison between an attacker-influenced value and a privileged value decides whether attacker-supplied configuration is trusted* (EUID vs. UID gating `HESIOD_CONFIG`). The analog in Serai is `ReceivedOutput::read` / `Scanner::scan_transaction`: a `ReceivedOutput` carries an `offset` scalar that is trusted to reconstruct the spendable key (`script_key - offset*G` in `Output::key`, or `keys.offset(offset)` in `SignableTransaction::multisig`), yet nothing in the deserialization path verifies the offset is consistent with the output's `script_pubkey`. An attacker who supplies serialized output bytes can claim an arbitrary offset for an output, causing the processor to attribute funds to a key that does not match the on-chain script.

### Finding Description
`ReceivedOutput::read` reads `offset = Secp256k1::read_F(r)` straight from the input stream and stores it unvalidated alongside the `TxOut`/`OutPoint` ([mod.rs:122-134](networks/bitcoin/src/wallet/mod.rs)). The offset is the secret-free "configuration" needed to spend: `Scanner::register_offset` establishes the invariant `p2tr_script_buf(key + offset*G) == script_pubkey` only for offsets it registers internally ([mod.rs:180-196](networks/bitcoin/src/wallet/mod.rs)). That invariant is *assumed* downstream but never re-verified at the trust boundary where untrusted bytes enter:

- `Output::key()` in `processor/src/networks/bitcoin.rs:112-122` computes `read_G(script_key) - GENERATOR * output.offset()` — pure attacker arithmetic if `offset` is attacker-controlled. The returned "group key" can be made equal to any point, attributing the output to the wrong multisig.
- `SignableTransaction::multisig` in `networks/bitcoin/src/wallet/send.rs:273-285` applies `keys.offset(self.offsets[i])` and only *then* compares `p2tr_script_buf(offset.group_key())` to `prevouts[i].script_pubkey`, returning `None` on mismatch — meaning a tampered offset converts a genuinely-received output into an unspendable one, while a crafted offset shifts the derived key away from the set's actual key.

This mirrors the Hesiod bug exactly: the offset functions like `HESIOD_CONFIG` — ambient data treated as authoritative about which key/privilege applies — and the equality between "claimed key" and "actual key" is only enforced (if at all) far downstream of where the data is trusted.

### Impact Explanation
An unprivileged party feeding `ReceivedOutput`/`Output` bytes (the rules explicitly allow untrusted input to `ReceivedOutput::read`) can:

1. Report an output as received under a *wrong* group key — `Output::key()` misattributes the UTXO to a different multisig/offset, corrupting scheduler decisions (`processor/src/multisigs/scheduler/utxo.rs` consumes `key()`).
2. Render real funds unspendable — `multisig()` returns `None` when the offset-derived script doesn't match, so an output the set genuinely owns can be permanently stuck in signing (the scanner believed it received it, but no machine can sign for it).

This satisfies "funds reported received that are not spendable" — Medium.

### Likelihood Explanation
Reachability requires the attacker to control the serialized `ReceivedOutput`/`Output` bytes consumed by a processor (e.g., a malicious peer or a forged output record propagated through the protocol). The offset is a single 32-byte scalar with no binding to the script; no proof of consistency is requested. The failure mode is deterministic once such bytes are accepted.

### Recommendation
Bind the offset to the output at the trust boundary. Either:
- In `Output::key()` / when a `ReceivedOutput` is accepted from untrusted bytes, verify `p2tr_script_buf(key() + GENERATOR * offset) == output.script_pubkey` and reject otherwise; or
- Make `ReceivedOutput::read` take the `Scanner` (or the key + registered-offsets map) and look the offset up by `script_pubkey` instead of trusting the embedded scalar, mirroring how `scan_transaction` derives the offset internally.

### Proof of Concept
Conceptual: construct bytes for `ReceivedOutput::read` as `offset' || TxOut { script_pubkey: <group's p2tr script>, value } || outpoint` where `offset'` is any scalar ≠ the registered offset. `read` succeeds. Then:
- `Output::key()` returns `script_key - offset'*G`, an arbitrary point — the output is attributed to a key the set doesn't hold at that offset.
- `SignableTransaction::new(...).multisig(keys)` computes `keys.offset(offset')`, producing `p2tr_script_buf(group_key') != prevout.script_pubkey`, returns `None` — the received funds cannot be signed for despite appearing in the wallet's balance via `Output::balance()`.
