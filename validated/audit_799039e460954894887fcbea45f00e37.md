### Title
Unauthenticated Admin API call triggered by attacker-supplied `shop` param bypasses identity verification - ([File: app/controllers/concerns/shopify_app/ensure_installed.rb])

### Summary
`EnsureInstalled#validate_non_embedded_session` makes a live `ShopifyAPI::Clients::Rest::Admin` GET request using `installed_shop_session`, which is derived solely from the attacker-controlled `params[:shop]`, whenever the request is not flagged as `embedded=1`. No proof of caller identity (session cookie, JWT, HMAC) is required, allowing any anonymous requester to trigger outbound calls using a victim shop's stored offline access token and use the response (success vs. 401-redirect) as an oracle for session validity.

### Finding Description
`before_action :check_shop_known` sets `@shop = installed_shop_session`, which resolves via `SessionRepository.retrieve_shop_session_by_shopify_domain(current_shopify_domain)` where `current_shopify_domain` is `ShopifyApp::Utils.sanitize_shop_domain(params[:shop])` [1](#0-0) . This only validates domain format, not requester identity — any attacker can name a real installed shop. If a session exists, `check_shop_known` does not redirect [2](#0-1) , and the next `before_action`, `validate_non_embedded_session`, runs:

```ruby
def validate_non_embedded_session
  return if loaded_directly_from_admin?

  client = ShopifyAPI::Clients::Rest::Admin.new(session: installed_shop_session)
  client.get(path: "shop")
rescue ShopifyAPI::Errors::HttpResponseError => error
  ...
end
``` [3](#0-2) 

`loaded_directly_from_admin?` only checks `ShopifyApp.configuration.embedded_app? && params[:embedded] == "1"` [4](#0-3) . This is purely a self-reported request parameter that any anonymous caller can omit or manipulate — it does not verify the caller is actually inside Shopify Admin (no HMAC, JWT, or signed token check). When absent, the code proceeds to instantiate a real Admin API client using the victim shop's stored access token and issues a live outbound `GET /admin/api/.../shop.json` request, without any check that the requester possesses a valid session token or cookie proving their identity.

The gem's own documentation and comments confirm this is a known design limitation: "This concern does not authenticate the request... `installed_shop_session` resolves the session from the user-controllable `shop` query parameter — it does not verify who is making the request. Do not use `EnsureInstalled` or `installed_shop_session` for any action that accesses shop data or makes Shopify API calls" [5](#0-4) . Yet `validate_non_embedded_session` itself — part of the `EnsureInstalled` concern — violates this exact guidance by making an Admin API call gated only by the `shop` param and the self-reported `embedded` flag.

The existing repo tests explicitly exercise and expect this behavior without any authentication setup: `test "returns :ok if the shop is installed"` performs `get :index, params: { shop: shopify_domain }` with a stubbed session and asserts `ShopifyAPI::Clients::Rest::Admin.expects(:new).with(session: session)` and `client.expects(:get)` fire [6](#0-5) , confirming no token/identity check gates the call.

### Impact Explanation
An anonymous attacker naming any known/guessed `*.myshopify.com` domain can force the app server to issue live Shopify Admin REST calls using that shop's stored offline access token, and infer session validity from the response (200 vs. redirect-on-401), i.e., a shop-installation/session-validity oracle. It also allows unauthenticated triggering of arbitrary outbound API traffic using a victim's access token/credentials, which maps to Shopify's "Improper Authentication" / "Broken Access Control" impact class — using a shop's credentials without the requester proving their own identity.

### Likelihood Explanation
Fully feasible and repeatable: it requires only `use_new_embedded_auth_strategy?` to be `false` (the pre-token-exchange/legacy `EnsureInstalled` flow, still supported and used by generator templates such as `unauthenticated_home_controller.rb` and `dummy_home_controller.rb`) [7](#0-6) , a victim shop with a stored offline session, and a simple unauthenticated GET request with the `shop` param and no `embedded=1`. No secrets, tokens, or special access are needed.

### Recommendation
`validate_non_embedded_session` should not be reachable/should not make a live Admin API call based solely on an unauthenticated `shop` param. Either remove this API-call-based validation entirely from `EnsureInstalled` (as the docs already instruct: use `EnsureHasSession` for anything that calls the Shopify API), or require the request to already carry a verified session token/HMAC/cookie proving the caller's identity before allowing this validation call to run — not merely `params[:embedded] == "1"`, which is attacker-controlled and unverified.

### Proof of Concept
Using the existing test scaffold in `test/controllers/concerns/ensure_installed_test.rb`:
```ruby
test "makes an unauthenticated Admin API call using only the shop param" do
  session = mock
  ShopifyApp::SessionRepository.stubs(:retrieve_shop_session_by_shopify_domain).returns(session)

  client = mock
  ShopifyAPI::Clients::Rest::Admin.expects(:new).with(session: session).returns(client)
  client.expects(:get).with(path: "shop") # <-- fires with zero proof of caller identity

  # No cookies, no Authorization header, no JWT, no embedded=1
  get :index, params: { shop: "victim-shop.myshopify.com" }

  assert_response :ok
end
```
This reproduces the exact flow already present at [6](#0-5) : the client call fires solely because `params[:shop]` names an installed shop, with no verification that the requester is that shop's authenticated user.
