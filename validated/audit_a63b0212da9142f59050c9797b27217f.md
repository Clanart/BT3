`SignableTransaction::new` omits the `OP_RETURN` data output from the weight/fee calculation, underpaying the fee and overfunding change - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an `OP_RETURN` output into `tx_outs` whenever `data` is specified, but both calls to `calculate_weight_vbytes` are made over `payments` only — never over the final output list. The analogue of the `pendingWithdrawals` bug: an accounting quantity (the transaction's serialized weight used to derive `needed_fee` and the change value) is not updated after an output is added, so every downstream computation (`TooLowFee` check, `fee_with_change`, change amount) operates on a stale, understated size.

### Finding Description
At send.rs:194-202 the `OP_RETURN` `TxOut` is appended to `tx_outs`. At send.rs:204, `calculate_weight_vbytes(tx_ins.len(), payments, None)` computes `weight`/`vbytes` — but `calculate_weight_vbytes` (send.rs:62-99) builds its template transaction's `output` vector *solely* from the `payments` argument plus an optional change output. The `OP_RETURN` output (~11–92 bytes: a 0-value `TxOut` plus the `OP_RETURN` script and pushdata) is therefore absent from `vbytes`.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) is too small by `fee_per_vbyte * sizeof(OP_RETURN output)`.
- The `TooLowFee` check (send.rs:211) validates against the understated `vbytes`, so a transaction whose *actual* feerate falls below `DEFAULT_MIN_RELAY_TX_FEE` is accepted.
- The change arm recomputes with `vbytes_with_change` (send.rs:226-228), also excluding the data output, so `value = input_sat - (payment_sat + fee_with_change)` over-credits the change output by exactly the undercharged fee.

The tx actually broadcast is larger than measured, so its real feerate is `fee / (vbytes + ~10–90)` — lower than the caller requested, and potentially below the relay minimum despite the explicit check.

### Impact Explanation
Reachable via public input: the `data` field originates from `OutInstruction`/`InInstruction` data that external users attach to burns/deposits (plans built in `processor` call `SignableTransaction::new(..., data, ...)`). Any such withdrawal produces a transaction paying less than the intended feerate. If the underpayment pushes the effective rate below the mempool minimum, the signed multisig transaction will not relay/confirm — multisig funds become stuck until the situation is manually resolved. This is the same class as the Fairside finding: a stale accumulator silently corrupts downstream value computations (`change` amount, fee adequacy check) that callers rely on being exact.

### Likelihood Explanation
Triggered whenever a Bitcoin plan carries non-empty `data` (an arbitrary-data burn/instruction), which is a normal, externally-influenced code path. Not contingent on validator misbehavior. Whether the fee dips below relay minimum depends on `fee_per_vbyte` and data length, but the miscalculation occurs on every data-bearing transaction.

### Recommendation
Include the `OP_RETURN` output in the weight/fee computation — e.g., extend `calculate_weight_vbytes` to take the `data: Option<&[u8]>` (or the full `tx_outs` list), and call it after the data output is known, at both send.rs:204 and the change branch at send.rs:226. Additionally derive the change amount as `input_sat - payment_sat - needed_fee` computed against the *final* output set.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_rate)`:
- `tx_outs` gains an ~92-byte `OP_RETURN` output at send.rs:194-202.
- `calculate_weight_vbytes` at send.rs:204/226 never sees it, so `needed_fee` and the `TooLowFee` check ignore ~92 bytes.
- The resulting `tx` (send.rs:245-255) includes the data output while paying only for the payment/change outputs; `fee() / actual_vsize < fee_rate`, and change is over-valued by the shortfall. Setting `fee_rate` at exactly the relay minimum yields a transaction that passes `TooLowFee` yet is actually under the minimum once the real size is measured. [1](#0-0) [2](#0-1) [3](#0-2)
