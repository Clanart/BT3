### Title
DataLayer mirror-URL SSRF via unrestricted `http_download`/`get_downloader` fetch of attacker-published mirror URLs - (File: `chia/data_layer/download_data.py`)

### Summary
Chia's DataLayer subscription/sync path fetches delta/full-tree files from server URLs that come from on-chain "mirror" coins, which any wallet controlling a DataLayer singleton can publish with arbitrary URL strings. When a local DataLayer client subscribes to (or auto-owns) a store advertised by another party, `DataLayer.update_subscriptions_from_wallet()` copies those attacker-supplied URLs verbatim into the local subscription table, and `DataLayer.fetch_and_validate()` / `download_data.http_download()` later issue outbound HTTP requests to them with no host/scheme allow-list, matching the CVE-2024-51242 bug class (unvalidated user-controlled URL/host used server-side to issue outbound requests).

### Finding Description
`Mirror` records are created on-chain by anyone owning a DataLayer singleton launcher (`DataLayerWallet.create_new_mirror()`), and their `urls` field is free-form text taken from a spend's memos with no validation against SSRF-sensitive targets: [1](#0-0) 

When another node's DataLayer wallet sees the mirror coin get added, it stores those URLs verbatim in the local DL store: [2](#0-1) 

The DataLayer service pulls these URLs straight from wallet RPC and writes them into its local subscription table without any validation (no scheme restriction, no private/loopback/link-local IP filtering): [3](#0-2) 

During the periodic sync loop, `fetch_and_validate()` iterates these server URLs and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs a plain `aiohttp` GET against `server_info.url + "/" + filename` with no destination checks: [4](#0-3) [5](#0-4) 

`get_downloader()` similarly POSTs a `store_id`/`url` payload to configured plugin URLs, but the `url` value that gets forwarded to the plugin (and, for the S3 plugin, parsed and used to pick a bucket) also originates from the same untrusted mirror list: [6](#0-5) 

There is no allow-list, scheme restriction (`http`/`https` only would still allow SSRF to internal hosts), or private-network/loopback/link-local exclusion anywhere in this chain, unlike the peer-discovery path which does validate hosts (`chia/server/node_discovery.py`, `_add_peers_common`) or `chia/util/network.py`'s `is_in_network`/`is_trusted_cidr` helpers — those protections are not applied to DataLayer mirror URLs.

### Impact Explanation
A malicious DataLayer store owner can publish mirror URLs pointing at internal-only services (e.g., `http://127.0.0.1:<port>/...`, `http://169.254.169.254/...`, or other RFC1918 addresses reachable from the DataLayer host) as part of on-chain mirror coins. Any local DataLayer client that subscribes to that store id — a normal, unprivileged Data Layer client action — will have its DataLayer service issue outbound HTTP GET requests to those internal targets during background sync (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`), potentially probing/interacting with internal infrastructure (cloud metadata endpoints, local RPC ports, other services bound to localhost) from the node operator's network. This is a genuine SSRF primitive triggered by attacker-controlled on-chain data, consistent with CVSS 6.5 Medium severity (network-reachable, low complexity, requires the victim to subscribe, no direct confidentiality/integrity impact on chain state but real internal network reconnaissance/request forgery capability).

### Likelihood Explanation
Likelihood is Medium: exploitation requires the victim to actively subscribe to (or otherwise track) a store id controlled by the attacker, which is a normal DataLayer user workflow (subscribing to third-party DataLayer stores is an advertised feature), and the attacker only needs to publish an on-chain mirror coin with crafted URLs — no privileged access or protocol-level manipulation is required.

### Recommendation
Validate mirror/server URLs before they are persisted as subscription servers and before any HTTP request is issued: restrict scheme to `http`/`https`, resolve the hostname and reject private/loopback/link-local/multicast ranges (reusing `chia.util.network.is_in_network`/`ip_address` style checks already used for peer validation), and apply the same validation to `get_downloader()`'s plugin URL forwarding and to `DataStore.update_subscriptions_from_wallet()` inputs. Consider allowing operators to opt into an explicit mirror-host allow-list.

### Proof of Concept
1. Attacker creates a DataLayer store and calls `add_mirror` (CLI: `chia data add_mirror -u http://127.0.0.1:<internal-port>/ -u http://169.254.169.254/latest/meta-data/ ...`), which is accepted with no URL validation (`chia/data_layer/data_layer.py:965-970`, `add_mirror` RPC).
2. This creates an on-chain mirror coin with those URLs, tracked by `DataLayerWallet.coin_added()` for any node syncing that singleton.
3. Victim runs `chia data subscribe -i <attacker_store_id>`, causing their DataLayer service to call `update_subscriptions_from_wallet()`, which copies the attacker URLs into the local `subscriptions`/`servers_info` table verbatim (`chia/data_layer/data_layer.py:979-985`).
4. On the next `periodically_manage_data()` cycle, `fetch_and_validate()` selects one of these `server_info.url` values and calls `http_download()`, which performs `session.get(server_info.url + "/" + filename, ...)` (`chia/data_layer/download_data.py:298-319`) — issuing an outbound HTTP request to the attacker-chosen internal host/port from the victim's DataLayer process.

    async def get_downloader(self, store_id: bytes32, url: str) -> PluginRemote | None:
        request_json = {"store_id": store_id.hex(), "url": url}
        for d in self.downloaders:
            async with aiohttp.ClientSession() as session:
                try:
                    async with session.post(
                        d.url + "/handle_download",
                        json=request_json,
                        headers=d.headers,
                        timeout=self.client_timeout,
                    ) as response:
                        res_json = await response.json()
                        if res_json["handle_download"]:
                            return d
                except Exception as e:
                    self.log.error(f"get_downloader could not get response: {type(e).__name__}: {e}")
        return None

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
