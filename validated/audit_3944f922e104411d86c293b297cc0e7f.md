### Title
Out-of-order/missing-registration dereference: blame processing panics when the accused or accuser never registered an encryption key — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2015-4054 is a state-ordering bug: PgBouncer dereferenced a connection object that was only initialized by a startup packet when a password packet arrived first. The Serai analog lives in PedPoP's blame path: `Decryption::decrypt_with_proof` dereferences `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` dereferences `self.commitments[&sender]` — both `HashMap` indexing operations that panic when the named participant never "started up" (never registered an `EncryptionKeyMessage` / has no entry in the map). Neither `blame` nor `decrypt_with_proof` validates that `sender`/`recipient` are registered participants before indexing.

### Finding Description
`Encryption::register` is the only function that inserts into `enc_keys`, and it is only invoked while processing round-1 commitment messages (`SecretShareMachine::verify_r1`, `AdditionalBlameMachine::new`). Later, `blame_internal` accepts caller-supplied `sender`/`recipient` `Participant` values plus an attacker-influenced `msg`/`proof`, and:

- calls `decrypt_with_proof`, which evaluates `self.enc_keys[&decryptor]` — panics if `decryptor` was never registered (encryption.rs:388), and
- evaluates `self.commitments[&sender]` — panics if `sender` isn't in the commitments map (lib.rs:599).

The panic on the `decryptor` index is gated only by `msg.pop.verify(...)`, which the accuser can satisfy: the PoP challenge binds `from`, but the accuser (or whoever relays the blame package) chooses the ephemeral key and signs a valid PoP for whatever `from` they claim. There is no check equivalent to "did a startup packet arrive" before dereferencing the per-participant state.

`AdditionalBlameMachine::new` registers `1..=n`, so it survives for in-range indexes — but `blame()` takes arbitrary `Participant` values, and a `Participant` index `> n` (or one filtered out of `commitment_msgs`) has no entry, hitting the same panic. Similarly, `Encryption::encrypt` indexes `enc_keys[&participant]` (encryption.rs:466), which would panic for any participant whose registration message was absent if the caller didn't pre-validate the map — `verify_r1`'s `validate_map` currently saves that path, but the invariant is implicit, not enforced by the indexing itself.

### Impact Explanation
A panic in `blame`/`blame_internal`/`decrypt_with_proof` aborts the calling thread. Since blame evaluation is invoked while arbitrating accusations, a single malformed accusation naming an unregistered participant crashes the arbitrator/validator process — a remote denial of service, exactly the impact class of CVE-2015-4054 (crash before initialized state). This is not a correctness or fund-loss bug; the impact is availability of the node processing blame.

### Likelihood Explanation
Reachability requires an accusation flow where the accusing party supplies `sender`/`recipient`/`msg`/`proof`. `blame`/`AdditionalBlameMachine::blame` are the documented public API for exactly this, and their inputs are participant-controlled. `Participant::new` only enforces non-zero, so indexes outside the registered set are constructible. The constraint is that the attacker must be a DKG participant (or control what gets passed to `blame`), which bounds the surface to a malicious validator in the deployed protocol — hence Medium rather than High.

### Recommendation
Replace `HashMap` indexing with checked lookups in the blame/decrypt path:

- In `Decryption::decrypt_with_proof`, use `self.enc_keys.get(&decryptor)` and return `DecryptionError::InvalidProof` (or a new `UnregisteredParticipant` variant) on `None`.
- In `BlameMachine::blame_internal`, validate `sender`/`recipient` membership in `self.commitments`/`enc_keys` before use, returning a defined error or blaming the accuser.
- In `Encryption::encrypt`, use `.get(&participant)` and propagate an error instead of relying on callers to have pre-registered every index.

### Proof of Concept
Conceptual, using the public API (`crypto/dkg/pedpop`):

```rust
// n = 2, t = 2 context; only participants 1 and 2 register via
// AdditionalBlameMachine::new(context, 2, commitment_msgs).
let mut machine = AdditionalBlameMachine::<C>::new(context, 2, commitment_msgs).unwrap();

// Attacker submits a blame statement naming a participant who never registered
// (or an out-of-range index such as Participant::new(7)).
let ghost = Participant::new(7).unwrap();

// Forge a valid PoP: choose arbitrary scalar k, set key = G*k, and Schnorr-sign
// the challenge bound to `ghost` as `from` — verify() passes since the signer
// controls the ephemeral key.
let msg: EncryptedMessage<C, SecretShare<C::F>> = forge_pop_for(ghost, bytes);

// machine.blame(sender, ghost, msg, Some(proof)) reaches
// decrypt_with_proof -> self.enc_keys[&ghost] -> panic! (no entry for key)
// or, with proof = None bypass, blame_internal -> self.commitments[&sender] -> panic!
```

Any call to `blame()` where `recipient` was never inserted via `register()` (e.g., index > `n`, or a participant omitted from `commitment_msgs` in a manually constructed `Decryption`) panics on `enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388`, mirroring the packet-before-startup dereference.
