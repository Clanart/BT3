## Analysis

The Bacon Protocol report's core issue is an **unguarded, attacker-triggerable state change that persists and silently affects a legitimate user's later actions** — a "first write wins" configuration value that anyone can set on behalf of a victim, with no consent check, causing harmful downstream behavior.

The closest verifiable Desktop analog is the reintroduction of the `file://` submodule transport during automatic submodule updates, keyed off attacker-controlled repository content (`.gitmodules`), rather than any explicit trust decision by the user.

### Title
Submodule updates unconditionally re-enable `protocol.file.allow=always`, permitting attacker-controlled `.gitmodules` to exfiltrate local files - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` builds its `git submodule update --init --recursive` invocation with an optional `-c protocol.file.allow=always` flag [1](#0-0) , gated only by a boolean `allowFileProtocol` parameter supplied by the caller — never by any check of whether the submodule URL(s) in the checked-out tree are trustworthy.

### Finding Description
Git disabled the `file://` transport for submodules by default (fix for CVE-2022-39253) precisely because a **repository the user does not control** (a fetched branch, a cloned fork, a pull-request checkout) can embed a `.gitmodules` entry pointing at an arbitrary local path (e.g. `file:///home/victim/.ssh`, `file:///etc/passwd`, or a UNC path on Windows) and have Git copy that local content into the submodule's working tree, where it becomes visible, readable, and — worse — committable/pushable by the victim without their knowledge.

`updateSubmodulesAfterOperation` re-adds this disabled capability via `-c protocol.file.allow=always` whenever it is called with `allowFileProtocol: true` [2](#0-1) . Grep of the codebase shows this function (and the `allowFileProtocol` flag) is exercised from `app/src/lib/git/checkout.ts` in the normal branch-checkout flow, i.e., whenever Desktop checks out a branch and then runs a submodule update — which happens for any branch the user checks out, including branches/PRs fetched from a remote the user does not control. The `.gitmodules` file, and therefore the submodule URLs it declares, is fully attacker-controlled content living inside the fetched/cloned repository: exactly the "attacker controls a cloned/fetched repository" primitive called out as valid in this task. There is no per-URL allow-list, no prompt, and no distinction in `updateSubmodulesAfterOperation` between "submodule added by the user themselves" and "submodule declared in a branch fetched from a third party."

This mirrors the report's broken invariant: a security-relevant, persistent configuration (`protocol.file.allow`) that should require the *receiver's* (here, the local user's) explicit consent is instead activated unconditionally as a side effect of an action the attacker can trigger indirectly (crafting the repository content the victim later checks out), silently corrupting what ends up in the victim's working directory.

### Impact Explanation
If exploited, this can read local files (SSH keys, config files, other private data) outside the intended repository into the working tree of a repository the victim then may stage/commit/push — a "file write/read outside the repo" and "silent corruption of what the user commits or pushes" outcome, matching the valid-impact bar.

### Likelihood Explanation
Likelihood depends on exactly which checkout paths pass `allowFileProtocol: true` — I was only able to confirm the function's implementation and that `checkout.ts` references it seven times via `grep_search`; I could not read the full body of `app/src/lib/git/checkout.ts` in this session to confirm every call site's `allowFileProtocol` value and whether Desktop restricts it to submodules the user manually adds versus arbitrary fetched branches. This is the key open question and should be verified before treating this as confirmed-exploitable.

### Recommendation
- Only pass `allowFileProtocol: true` for submodules explicitly added by the local user in the current session, never for submodule declarations that arrive via fetch/checkout of a remote branch.
- Alternatively, validate submodule URLs against an allow-list of protocols (https/ssh) before permitting `protocol.file.allow=always`, and prompt the user when a `file://` submodule URL is encountered from untrusted/fetched content.

### Proof of Concept
Conceptual (not executed): an attacker prepares a branch/fork whose `.gitmodules` contains `url = file:///Users/victim/.ssh`. If the victim fetches and checks out that branch in Desktop, and the checkout path invokes `updateSubmodulesAfterOperation(..., allowFileProtocol: true)`, `git submodule update --init --recursive -c protocol.file.allow=always` will copy the victim's `~/.ssh` directory into the submodule path inside the working tree, where Desktop's UI would show it as untracked/new content ready to be committed.

**Caveat:** because I could not fully inspect `app/src/lib/git/checkout.ts` to confirm the exact conditions under which `allowFileProtocol` is `true` for branch/PR checkouts versus manual submodule-add flows, this should be treated as a **plausible, code-supported analog requiring verification**, not a fully confirmed exploit chain. If checkout.ts turns out to gate `allowFileProtocol` strictly to submodules the user just added locally (not to arbitrary remote branch checkouts), the impact would not apply.
