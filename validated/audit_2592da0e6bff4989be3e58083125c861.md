## Title
Unhandled index/undefined crash when parsing malformed `git log --raw --numstat` output from an attacker-controlled repository - (File: `app/src/lib/git/log.ts`)

## Summary
The Celestia report is a crash in header/p2p server code caused by insufficiently validated assumptions about the shape of peer-supplied data (a known-format response that could deviate from expectations and cause a fault). The closest analog in GitHub Desktop is `parseRawLogWithNumstat`, which parses `git log -z --raw --numstat` output line-by-line while assuming the `--raw` file-entry section and the `--numstat` section are always in 1:1 positional correspondence, then indexes into an array built from the first section using a counter maintained from the second section. [1](#0-0) 

## Finding Description
`parseRawLogWithNumstat` builds a `files` array while iterating `--raw` lines (those starting with `:`), then separately iterates `--numstat` lines and increments `numStatCount` for every non-`:` line, using that counter to index back into `files`: [2](#0-1) 

The code trusts that the number/order of raw entries always equals the number/order of numstat entries for a given commit's diff. This assumption is implicit and unenforced — there is no bounds check on `files[numStatCount]` before `.status` is accessed. If the two sections ever diverge (e.g., due to combined/merge-diff raw formats using a different leading-colon convention, or unusual rename/copy detection edge cases produced by a crafted commit in a cloned/fetched repository), `files[numStatCount]` will be `undefined`, and `.status` access throws an uncaught `TypeError`. This is functionally the same bug class as the Celestia issue: code that dereferences/derefs an index into a peer/attacker-influenced data structure without validating that the structure actually has the expected shape, leading to a runtime crash rather than a graceful parse failure.

This function is invoked by `getChangedFiles` (used to view a commit's file changes) and `getStashedFiles`, both of which take a `sha` that can point to a commit that was fetched/cloned from a remote the user doesn't control. [3](#0-2) [4](#0-3) 

Existing guards elsewhere in the file (`forceUnwrap`) explicitly convert `undefined`/`null` into a controlled fatal error with a descriptive message for other fields in the same function, but this particular array-index access at line 326 has no equivalent guard. [5](#0-4) 

## Impact Explanation
If reachable, this causes an uncaught exception while rendering a commit's diff/changed-files list for a commit or stash that originated from a repository the user cloned or fetched (i.e., attacker-influenced input), consistent with the "attacker controls a cloned/fetched repository... result is ... renderer-sandbox... crash" impact category. Whether this surfaces as a caught, user-visible error or an unhandled process crash depends on whether the call sites in `app-store.ts` wrap this call in error handling — I was not able to fully confirm from the available index whether the specific call path from `app-store.ts` (`getChangedFiles`) is wrapped in a try/catch or `performFailableOperation`-style guard, so the ultimate severity (recoverable error vs. renderer crash) is uncertain.

## Likelihood Explanation
Likelihood is uncertain/low-to-moderate: normal, well-formed `git log --raw --numstat -z` output for standard commits keeps the two sections in sync, so triggering the divergence requires a specifically crafted commit (e.g., exploiting merge/combined-diff raw formatting, unusual renames, or copy-detection edge cases) inside a repository the victim clones or fetches. I could not verify from the index a concrete git invocation that reliably produces a raw/numstat count mismatch, so this should be treated as a plausible-but-unconfirmed reachable path rather than a proven exploit.

## Recommendation
Add an explicit bounds/shape check before indexing `files[numStatCount]` (mirroring the `forceUnwrap` pattern already used for other fields in this function), and fail gracefully (e.g., return a partial/well-defined error) instead of allowing an uncaught `TypeError` if the raw and numstat sections do not match in count for a given parsed commit.

## Proof of Concept
Not verified end-to-end against real git output; the concrete PoC would be a git repository containing a commit (e.g. a merge/combined-diff commit or one exercising rename/copy detection) that produces `--raw`/`--numstat` sections whose entry counts diverge when run through `git log -m -C -M --raw --numstat -z`, then having the victim clone/fetch that repository and view the commit's changed files in Desktop, causing `parseRawLogWithNumstat` to throw when accessing `files[numStatCount]`.

export async function getChangedFiles(
  repository: Repository,
  sha: string
): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)
  // this is equivalent to the user configuring 'diff.renames' to 'copies'
  // NOTE: order here matters - doing -M before -C means copies aren't detected
  const args = [
    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}

export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }

  return { files, linesAdded, linesDeleted }
}
