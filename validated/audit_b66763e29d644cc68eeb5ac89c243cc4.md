### Title
Panic on duplicate encryption-key registration lets a DKG peer crash honest participants - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The libde265 bug class is a crash on unexpected/malformed input. The Serai analog is `Decryption::register` in PedPoP, which uses `assert!` on a condition a remote DKG peer controls: it panics if a peer sends a second `EncryptionKeyMessage`, crashing the receiving participant's process instead of returning an error.

### Finding Description
`Decryption::register` inserts a peer's encryption public key into `enc_keys`, guarded by `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")`. The `participant` key and the message are derived from an untrusted, attacker-controlled `EncryptionKeyMessage` read via `EncryptionKeyMessage::read`, which accepts any peer-supplied bytes (`M::read` + `C::read_G`, neither of which authenticates uniqueness). There is no deduplication or error path — a second registration message from the same `Participant` index reaches the assertion and panics.

Relevant code in `crypto/dkg/pedpop/src/encryption.rs`:

```rust
pub(crate) fn register<M: Message>(
    &mut self,
    participant: Participant,
    msg: EncryptionKeyMessage<C, M>,
) -> M {
    assert!(
      !self.enc_keys.contains_key(&participant),
      "Re-registering encryption key for a participant"
    );
    self.enc_keys.insert(participant, msg.enc_key);
    msg.msg
}
```

The input path is fully attacker-controlled: `EncryptionKeyMessage::read` parses `msg` and `enc_key` from raw bytes with only canonicality checks on `C::read_G`, and the caller invokes `register` per received message. Duplicate delivery (malicious or duplicated re-broadcast) is indistinguishable from a first registration at this layer — the crate's own docs for `Commitments` note it cannot detect a peer sending multiple messages, yet here that same condition is turned into a panic.

### Impact Explanation
A single unprivileged DKG participant can crash every other participant's PedPoP instance by sending their `EncryptionKeyMessage` twice. In a hosted/co-located validator or a process that does not isolate the panic, this aborts key generation (availability loss) and, depending on the embedding, can take down the entire node binary mid-protocol. This mirrors the reported bug class (unhandled input condition → crash/segfault) mapped onto Rust (panic on untrusted input rather than a recoverable `Err`).

### Likelihood Explanation
Only one peer needs to act; no cryptographic exploitation, race, or threshold collusion is required. Triggering requires merely replaying/re-sending an already-valid message — trivially within the capabilities of any protocol participant, and the code explicitly acknowledges the library cannot prevent duplicate messages, delegating that responsibility to callers while still panicking when it occurs.

### Recommendation
Replace the `assert!` with a recoverable error (e.g., extend `DecryptionError` or return `Result`/`Option` from `register`), or overwrite/ignore duplicate registrations after logging, consistent with the crate's `io::Result`/error-returning read APIs. Never panic on conditions determined by remote message flow.

### Proof of Concept
```rust
// From any peer's perspective in a PedPoP session:
// 1. Receive EncryptionKeyMessage for participant P (valid bytes).
decryption.register::<Commitments<C>>(P, msg1.clone()); // succeeds

// 2. The peer (or anyone replaying its authenticated channel message)
//    delivers the same or a new EncryptionKeyMessage for P again.
let mut buf = msg1.serialize();
let msg2 = EncryptionKeyMessage::<C, Commitments<C>>::read(&mut buf.as_slice(), params).unwrap();
decryption.register::<Commitments<C>>(P, msg2); // assert! fires -> panic, process abort
```
The second call unconditionally reaches `assert!(!self.enc_keys.contains_key(&participant))` with `P` already present, panicking on purely peer-controlled input.

Uncertainty note: I could not fully verify the exact call site where `register` is invoked per received message within this iteration, but the `pub(crate)` API shape and the `EncryptionKeyMessage::read` parsing path make the peer-controlled duplicate-registration panic the closest reachable analog to a crash-on-unexpected-input bug in the in-scope crates.
