Missing HTML/JavaScript-context escaping (`<`, `>`) in upb's native JSON encoder used by Ruby, PHP, and upb-backed Python bindings — inconsistent with C++, Java, and C# ProtoJSON encoders - ([File: upb/json/encode.c])

### Summary
The GoCD CVE's failed invariant is: attacker-controlled string data is serialized into a document that is later interpreted in a browser/JavaScript context without escaping characters that are meaningful there (`<`, `>`), enabling script injection. Protobuf's own ProtoJSON encoders in C++, Java, and C# implement exactly this defense-in-depth invariant — deliberately escaping `<`, `>`, and several other Unicode "JavaScript-dangerous" code points as `\uXXXX` even though the JSON spec does not require it, specifically to make ProtoJSON output safe to embed in `<script>` blocks or HTML documents. However, the analog upb-based native JSON encoder — shared by the Ruby extension, the PHP extension, and used as the backend for Python's `upb`-based C extension — does not implement this same protection.

### Finding Description
- C++'s canonical JSON writer explicitly escapes `<`/`>` and a list of other Unicode code points "to prevent security bugs in JavaScript," per `MustEscape` in `src/google/protobuf/json/internal/writer.cc:239-251`. This is exercised by `JsonTest.HtmlEscape` in `src/google/protobuf/json/json_test.cc:1583-1589` (`</script>` → `\u003c/script\u003e`) and by the dedicated `TestEvilJson` message with `json_name = "</script>"` and `"\"<script>alert('hello!);</script>"` fixtures in `src/google/protobuf/util/json_format_proto3.proto:199-207`.
- Java's `JsonFormat.java` mirrors this: `replacementChars` explicitly escapes `<`, `>`, `&`, `=`, `'` "to prevent XSS risks" at `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java:1583-1591`, verified by `testHtmlEscape` in `java/util/src/test/java/com/google/protobuf/util/JsonFormatTest.java:2016-2035`.
- C#'s `JsonFormatter.cs` does the same via its `CommonRepresentations` table, escaping `<`/`>` "required for HTML security" (`csharp/src/Google.Protobuf/JsonFormatter.cs:68-72`) plus additional invisible/format Unicode ranges in `WriteString` (`csharp/src/Google.Protobuf/JsonFormatter.cs:717-745`).
- In contrast, the upb native JSON encoder's character-escaping routine, `jsonenc_put_escaped_char`, only escapes the JSON-mandatory control characters (`\n`, `\r`, `\t`, `"`, `\f`, `\b`, `\\`, and bytes `< 0x20`); all other bytes, including `<` and `>`, fall through to the `default` branch and are written raw via `jsonenc_putbytes`. This same function/logic is duplicated verbatim in:
  - `upb/json/encode.c:268-301` (canonical upb source)
  - `php/ext/google/protobuf/php-upb.c:6807-6840` (PHP extension's vendored upb)
  - `ruby/ext/google/protobuf_c/ruby-upb.c:5560-5593` (Ruby extension's vendored upb)

The upb encoder's own test suite (`upb/json/encode_test.cc`) covers control-character and quote escaping but contains no test analogous to C++'s `JsonTest.HtmlEscape`, confirming the gap is not merely undocumented but untested.

### Impact Explanation
Any consuming application that calls the public `MessageToJson`/`to_json`/`serializeToJsonString`-style ProtoJSON API on the Ruby or PHP native extension (or Python's upb-backed extension) and embeds the resulting JSON string into an HTML page or inline `<script>` block — a common pattern for bootstrapping client-side application state — will fail to get the `\u003c`/`\u003e` escaping that the C++/Java/C# implementations guarantee. If an attacker controls any string field value that flows into such a message (e.g., a user-supplied string field bounded and validly encoded per a trusted schema), a payload like `</script><script>alert(1)</script>` set in a `string` field would be re-encoded verbatim (`</script>...`) instead of `\u003c/script\u003e...`, and could break out of an inline `<script>` context to execute in the victim's browser — the same class of impact as the original GoCD stored XSS, mediated through protobuf's cross-language JSON output inconsistency rather than through protobuf's own UI.

### Likelihood Explanation
This is a High-likelihood, direct analog for consuming applications using Ruby, PHP, or upb-backed Python bindings: the vulnerable code path is on the standard public `ToJson`/`to_json` API, requires no special configuration, and reaching it only requires an attacker-controlled string value (bounded, valid per schema) — exactly the threat model specified. The bug is a straightforward omission (missing `case '<': case '>':` branches) present identically across three vendored copies of the same upb source, meaning it is a systemic gap rather than an isolated typo, and it is easily confirmed by diffing against the intentionally-hardened C++/Java/C# `MustEscape`/`replacementChars` tables.

### Recommendation
Add the same JavaScript/HTML-context-dangerous character escaping used in C++'s `MustEscape` (`src/google/protobuf/json/internal/writer.cc`) to upb's `jsonenc_put_escaped_char` in `upb/json/encode.c`, at minimum escaping `<` and `>` as `\u003c`/`\u003e`, and propagate the fix into the vendored copies in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c` (these appear to be generated/vendored from the same upb source and should be regenerated). Add a regression test mirroring `JsonTest.HtmlEscape` to `upb/json/encode_test.cc`.

### Proof of Concept
Using a trusted schema with a `string` field (e.g. upb's own `TestMessage` used in `upb/json/encode_test.cc`), set the field to `"</script><script>alert(1)</script>"` and call the public JSON-encoding entry point (`upb_JsonEncode`, reachable from Ruby's `Message#to_json` or PHP's `serializeToJsonString`):
- Expected (matching C++/Java/C# behavior): `{"stringValue":"\u003c/script\u003e\u003cscript\u003ealert(1)\u003c/script\u003e"}`
- Actual (per `jsonenc_put_escaped_char` default branch in `upb/json/encode.c:291-300`, `php-upb.c:6830-6839`, `ruby-upb.c:5583-5592`): `{"stringValue":"</script><script>alert(1)</script>"}`

This can be locally verified by adding a test case identical in structure to `TEST(JsonTest, EncodeEnumCustomStringWithEscapedQuotes)` (`upb/json/encode_test.cc:141-148`), but asserting on a string field containing `<`/`>`, and observing it fails to match the escaped form that the equivalent C++ `JsonTest.HtmlEscape` test (`src/google/protobuf/json/json_test.cc:1583-1589`) asserts and passes.   @Test
  public void testHtmlEscape() throws Exception {
    TestAllTypes message = TestAllTypes.newBuilder().setOptionalString("</script>").build();

        .isEqualTo("{\n  \"optionalString\": \"\\u003c/script\\u003e\"\n}");
