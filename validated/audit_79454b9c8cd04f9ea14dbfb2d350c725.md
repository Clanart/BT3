### Title
PedPoG/PedPoP encryption key is not validated, allowing a participant to register the identity point and expose all secret shares addressed to them to any observer - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`EncryptionKeyMessage::read` deserializes `enc_key` via `C::read_G` and `Decryption::register` stores it with no validation — no identity check, no proof of possession, no binding to the participant's commitments. A malicious participant can register `enc_key = identity`. Every honest dealer then computes `ecdh(per_message_key, identity) = identity`, so the ChaCha20 keystream protecting that participant's secret shares is derived entirely from public data (`context` and the identity encoding). Any passive observer of the DKG traffic can decrypt every share addressed to the malicious participant, recovering that participant's secret share of the generated threshold key — a credential/secret-exposure analog of the reported CORS credential leak.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`:

- `EncryptionKeyMessage::read` (lines 57–59) reads `enc_key: C::read_G(reader)?` with no canonicality, identity, or torsion rejection at this layer.
- `Decryption::register` (lines 351–362) only asserts non-duplicate registration and inserts `msg.enc_key` into `enc_keys` unchecked.
- `Encryption::encrypt` (lines 460–467) encrypts shares to a participant via `encrypt(rng, context, i, self.decryption.enc_keys[&participant], msg)`, and `encrypt`/`ecdh`/`cipher` (lines 95–133, 154) derive the ChaCha20 key from a transcript of `context` and `ecdh = recipient_pub * ephemeral_priv`.
- The only proof-of-possession is on the *per-message* key (`pop` field, lines 83–91); the registered long-term `enc_key` has no proof of possession or validity check at all.

If a participant registers `enc_key = C::G::identity()` (a valid encoding for both `RistrettoPoint` and `EdwardsPoint`), then for every dealer's message to them `ecdh = identity * k = identity`. The keystream is `transcript("DKG Encryption v0.2" | context | "encryption_key" | shared_key=identity_bytes)` — computable by anyone who knows `context` (which is public/session-derived). `AdditionalBlameMachine::new` (lib.rs lines 649–662) likewise registers the identity key without complaint, so blame machinery still functions and nothing detects the weak key.

### Impact Explanation
All `EncryptedMessage<C, SecretShare<C::F>>` ciphertexts addressed to the malicious participant are effectively plaintext to any observer. Each decrypted share is `f_i(j)` for dealer `i`; summing them yields participant `j`'s secret share of the threshold key. An unprivileged party who merely observes the (publicly relayed/coordinator-visible) share distribution phase recovers a full secret share of the group key, reducing the effective threshold against external attackers by one and violating the DKG's confidentiality guarantee — analogous to credentials being readable by untrusted origins in the reference advisory. Note the attacker does not even need to know the discrete log of the registered key, since decryption is also performed with the publicly derivable keystream.

### Likelihood Explanation
The attack requires only that a participant submit a malformed `EncryptionKeyMessage` during the commitments round — an unprivileged input fully within the attacker's control. No honest party rejects it: no code path validates `enc_key` against identity, and the protocol continues normally (the shares decrypt "correctly" for the attacker, so no blame event is ever raised). It is reliably exploitable in every DKG session the attacker joins.

### Recommendation
In `EncryptionKeyMessage::read` or `Decryption::register`, reject `enc_key` values that are identity (and, for cofactored curves like `EdwardsPoint`, non-prime-order/torsion points). Preferably also require a Schnorr proof of possession of `enc_key` bound to `context` and the participant index, matching the treatment already given to `commitments[0]` in `verify_r1`, so a participant cannot register a key whose discrete log is unknown or degenerate.

### Proof of Concept
Using the existing test harness shape in `crypto/dkg/pedpop/src/tests.rs`:

```rust
// Malicious participant TWO forges its registration message
let mut forged = honest_commitments_msg_for_TWO; // EncryptionKeyMessage<Ristretto, Commitments>
// Serialize with enc_key replaced by the identity encoding (32 zero bytes for Ristretto)
let mut bytes = forged.serialize();
// enc_key is the last 32 bytes written by EncryptionKeyMessage::write
let len = bytes.len();
bytes[len - 32 ..].copy_from_slice(&[0u8; 32]);
let forged = EncryptionKeyMessage::<Ristretto, Commitments<Ristretto>>::read(
    &mut bytes.as_slice(), params,
).unwrap();

// Every honest participant calls verify_r1 -> encryption.register(TWO, forged)
// register() accepts identity enc_key without error.

// Dealer ONE then runs generate_secret_shares -> Encryption::encrypt(rng, TWO, share)
// ecdh(ephemeral_key, identity) == identity
// keystream = ChaCha20(key = transcript("DKG Encryption v0.2", context,
//              "encryption_key", shared_key = identity.to_bytes()))
```

An observer who sees the broadcast `EncryptedMessage` from any dealer `i` to `TWO` recomputes the same keystream (only `context` and the identity bytes are inputs), XORs it against `msg`, and recovers `SecretShare` `f_i(2)`. Repeating for all `n` dealers and summing yields participant TWO's secret share of the generated `ThresholdKeys` group secret, with no fault ever being attributed to TWO.
