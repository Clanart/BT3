### Title
Git submodule `file://` protocol re-enabled during branch/commit checkout, bypassing Git's own local-clone exfiltration protection - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` conditionally prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` command whenever it is invoked with `allowFileProtocol=true`: [1](#0-0) 

This flag is threaded through `checkoutBranch` and `checkoutCommit` in `app/src/lib/git/checkout.ts`, both of which default the parameter to `false` but accept a caller-supplied `true`: [2](#0-1) [3](#0-2) 

The unit test suite confirms `true` is a real, exercised value for this parameter, specifically for the case of "initializing an uninitialized submodule when checking out a branch": [4](#0-3) 

### Finding Description
Since Git 2.38 (and backports to 2.35.5+, addressing CVE-2022-39253), `git submodule update`/`clone` refuses `file://` submodule URLs by default (`protocol.file.allow=user`, not `always`) precisely because a `.gitmodules` entry with a local path can be used to have Git "clone" (i.e., hardlink/copy) an arbitrary local directory on the victim's disk into the working tree of an untrusted repository, from where the contents become visible/exfiltratable to whoever controls that repository (e.g., via the next `git add`/commit/push, or simply by the file being read locally).

`.gitmodules` is repository content — an attacker who controls a cloned/fetched repository (or a branch/PR within it) fully controls the submodule `url` field. If GitHub Desktop's checkout flow calls `updateSubmodulesAfterOperation` with `allowFileProtocol=true`, it explicitly re-opens the exact path Git's maintainers closed by default, using the `-c protocol.file.allow=always` override on `git submodule update --init --recursive`. That command will happily follow an attacker-supplied `file:///Users/victim/.ssh` (or any other absolute/relative local path reachable from the victim's filesystem, including via `../../` traversal or symlinks) and materialize its contents inside the checked-out repository's submodule directory.

The broken invariant mirrors the audit source finding: a supposedly narrow, "just in case" override (`getFunds()` bypassing normal withdrawal rules once killed) is instead reachable through an ordinary, expected user action (checking out a branch) and is driven by data the untrusted party controls (`.gitmodules`), silently disabling a safety guard that exists specifically to stop this class of abuse.

### Impact Explanation
If reachable with `allowFileProtocol=true` on an untrusted/attacker-supplied branch or PR, this allows:
- Reading files outside the intended repository's directory tree (the core "Valid Impact" criterion: attacker controls a cloned/fetched repository; result is file read outside the repo).
- Potential credential/token exfiltration if the local path points at SSH keys, `.netrc`, other repositories' `.git/config` with embedded credentials, or GitHub Desktop's own config/cache directories, since the materialized submodule content becomes visible/committable by the app.

This is exactly the class of attack Git 2.38 defused; if GitHub Desktop force-re-enables it on a normal "check out this branch" action, no additional local access, admin rights, or social engineering beyond checking out a branch/PR (an expected, unprivileged Desktop workflow) is required.

### Likelihood Explanation
Confirmed facts:
- The `protocol.file.allow=always` override exists in code and is wired to a boolean parameter on the checkout path (`app/src/lib/git/checkout.ts`, `app/src/lib/git/submodule.ts`).
- A unit test exercises `checkoutBranch(..., true)` for the "uninitialized submodule" scenario, so `true` is a genuine, supported runtime value, not dead code.

Not fully confirmed from the available index: I was unable to inspect the exact call sites in `app/src/lib/stores/app-store.ts` (8 matches found via `grep_search`, but content not retrieved before the tool budget was exhausted) that decide, at the point of a real user-initiated checkout, whether `allowFileProtocol` is set to `true`. It is therefore unverified whether the production trigger condition is generic ("any branch with an uninitialized submodule") or is scoped narrowly (e.g., only for repositories/remotes already trusted as first-party GitHub repositories, or only for submodules whose URL matches the parent's own trusted host). This distinction determines whether the issue is exploitable end-to-end via an untrusted repo/PR checkout, or is a benign internal implementation detail scoped to safe cases.

### Recommendation
- In `app/src/lib/stores/app-store.ts` (and any other caller), verify exactly when `allowFileProtocol=true` is passed to `checkoutBranch`/`checkoutCommit`.
- Never pass `allowFileProtocol=true` based solely on the presence of an uninitialized submodule; instead validate each submodule URL in `.gitmodules` against an allow-list (e.g., only `https`/`ssh` GitHub-hosted URLs, matching the same host/owner trust model already used in `app/src/lib/remote-parsing.ts` and `app/src/lib/repository-matching.ts`) before permitting `protocol.file.allow=always`, mirroring Git's own upstream fix instead of blanket-overriding it.
- If `file://` submodules must be supported (e.g., for legitimate local-fixture/test workflows), gate this behind an explicit, user-visible confirmation dialog rather than an implicit flag flipped during normal checkout.

### Proof of Concept
Conceptual PoC (based on confirmed code paths, pending confirmation of the exact app-store trigger condition):
1. Attacker creates a public repository/branch/PR with a `.gitmodules` file containing:
   ```
   [submodule "leak"]
       path = leak
       url = file:///Users/victim/.ssh
   ```
2. Victim opens this repository/PR in GitHub Desktop and checks out the branch — an entirely ordinary, unprivileged action.
3. If the checkout path reaches `checkoutBranch(..., allowFileProtocol=true)` → `updateSubmodulesAfterOperation` → `git -c protocol.file.allow=always submodule update --init --recursive` (as shown in `app/src/lib/git/submodule.ts:44-51`), Git clones/copies the victim's `~/.ssh` directory into the `leak/` submodule path inside the checked-out working tree, exposing its contents to the attacker's repo (e.g., visible via `git status`, stageable, and potentially pushed back if the attacker later fetches the victim's fork/PR branch).

Verification of the exact conditions under which the app passes `allowFileProtocol=true` in production (as opposed to only in the test harness) requires a full read of `app/src/lib/stores/app-store.ts`, which was not completed due to tool-call limits; a follow-up session with unrestricted file access should confirm this before treating the finding as fully proven end-to-end.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
