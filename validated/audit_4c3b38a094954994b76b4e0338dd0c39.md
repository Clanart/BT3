### Title
Quadratic Lagrange interpolation in `ThresholdKeys::new` enables DoS via crafted `ThresholdKeys::read` input - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n`/`t` (both `u16`, up to 65535) and immediately calls `ThresholdKeys::new`, which computes the group key by evaluating a Lagrange `interpolation_factor` for each of the `t` participants. Each `interpolation_factor` call iterates over all `t` included participants, yielding O(t²) field multiplications — up to ~4.3 billion operations — triggered purely by deserializing untrusted bytes. This is the Serai analog of unvalidated-input algorithmic-complexity DoS (CVE-2026-16270 class): no bound or validation limits the superlinear work implied by the input.

### Finding Description
In `crypto/dkg/src/lib.rs`:

- `ThresholdKeys::read` reads `t`, `n`, `i` as raw `u16`s from the reader, then reads `n` group elements and calls `ThresholdKeys::new` (lines 591–632). `n` is only constrained to be nonzero and `t <= n`.
- `ThresholdKeys::new` builds `t = (1..=params.t())` and computes `group_key = Σ verification_shares[i] * interpolation_factor(i, &t)` (lines 376–378).
- `interpolation_factor` for `Interpolation::Lagrange` loops over every element of `included` performing field multiplications (lines 234–242).

So parsing a serialized `ThresholdKeys` with `t = n = 65535` and `Interpolation::Lagrange` performs 65535 × 65535 ≈ 4.3×10⁹ scalar-field multiplications during `ThresholdKeys::new` alone — before any caller even uses the key. The same quadratic blowup reoccurs in `ThresholdKeys::view` (lines 494–507), which calls `interpolation_factor` once for the local share and once per included signer.

There is no cap on `t`/`n` anywhere in the read path, and no cheaper validation performed before the quadratic computation. The mitigations that exist elsewhere in Serai for resource exhaustion (e.g., chunked reads in `networks/ethereum/src/machine.rs` `Call::read`, `MAX_LIBP2P_REQRES_MESSAGE_SIZE` in `coordinator/src/p2p.rs`) do not apply here.

### Impact Explanation
Any component that feeds untrusted bytes to `ThresholdKeys::<C>::read` — e.g., a processor/coordinator rehydrating key material received or synced from an untrusted source, or any service accepting serialized key material — can be stalled for minutes to hours of single-threaded CPU time on a ~2 MB input. Per the rules, `ThresholdKeys::read` is an explicitly in-scope untrusted-bytes sink. This is an availability-only impact (no secret leakage or forgery), matching a Medium severity DoS.

### Likelihood Explanation
The attacker needs only to cause the victim to deserialize a crafted blob; no threshold collusion, no valid key material, and no protocol participation is required — `ThresholdKeys::new` performs the quadratic work during construction/validation itself, before semantic checks on the shares would matter. Exploitation requires the victim to actually call `ThresholdKeys::read` on attacker-controlled data; deployments that only read locally-generated keys are not exposed. Cost to the attacker is ~2 MB of bandwidth; cost to the victim is billions of field operations, a strong asymmetry.

### Recommendation
- Enforce a sane maximum on `n`/`t` (e.g., the protocol's real maximum validator-set size) inside `ThresholdParams::new` or at the top of `ThresholdKeys::read`, before any work proportional to `t` is performed.
- Alternatively/also, compute `group_key` incrementally or bound `included.len()` in `view()` and reject interpolation workloads above a fixed budget.
- Perform the `verification_shares.len() == n` and participant-range checks before reading all `n` points / before `interpolation_factor` is invoked.
