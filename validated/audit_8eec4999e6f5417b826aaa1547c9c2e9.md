## Analysis

**Binding claimed broken:** `payout_payer_operator_xonly_pk(withdrawal i) == operator whose own funds funded payout(withdrawal i)`.

Tracing the payout attribution path: `verifier.rs::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) extracts the attributed operator purely from `get_first_op_return_output`/`parse_op_return_data` on the on-chain payout transaction [1](#0-0) , with no check that the named operator contributed any funds to the transaction. The same unauthenticated extraction is repeated in `bridge_circuit::mod.rs::bridge_circuit` for `deposit_constant` [2](#0-1) .

Crucially, the user's payout-authorizing signature uses `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params` [3](#0-2) . `SIGHASH_SINGLE` commits only to input 0 (the withdrawal UTXO) and output 0 (the user's own payout output); `ANYONECANPAY` lets anyone add further inputs/outputs freely. The OP_RETURN operator-attribution output (added in `create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:418-433`) is **not covered by any signature at all** [4](#0-3) . This means whoever completes/broadcasts the transaction — including the withdrawer themselves, who already possesses their own valid `SinglePlusAnyoneCanPay` signature — can put **any bytes**, including an arbitrary honest operator's x-only pubkey, into that OP_RETURN, without invalidating the user's signature.

Downstream, `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) polls `get_first_unhandled_payout_by_operator_xonly_pk` filtered only on `payout_payer_operator_xonly_pk = self.operator.signer.xonly_public_key` [5](#0-4) ; it has no mechanism to verify that the named operator actually paid anything. It then calls `Operator::handle_finalized_payout`, which consumes the operator's own pre-signed kickoff connector and queues `Kickoff`/`Reimburse` transactions [6](#0-5) , ultimately leading to a `Reimburse` transaction that pays the operator the deposited bridge amount from the deposit's collateral/round path — independent of whether that operator ever funded the withdrawal payout.

None of the guards listed in the audit rules close this gap: `verify_storage_proofs` only checks that the payout tx's referenced input matches the committed withdrawal outpoint/index [7](#0-6) ; `SECP.verify_schnorr` only authenticates the user's spend of their own withdrawal UTXO output-0 spend [8](#0-7) ; neither constrains OP_RETURN content. `Verifier::is_deposit_valid`, `Operator::is_profitable`, and `only_aggregator_and_self` are not on this code path at all (attribution happens post-hoc from on-chain data, not through a gRPC-privileged call). This is a genuine, unauthenticated attribution vulnerability rooted in the deliberate lack of signature coverage over the OP_RETURN field, combined with zero verification that the named operator's funds/inputs appear anywhere in the payout transaction.

### Title
Unauthenticated OP_RETURN operator attribution allows crediting reimbursement to an operator who never funded the payout - (`core/src/verifier.rs`, `circuits-lib/src/bridge_circuit/mod.rs`)

### Summary
The withdrawer's `SinglePlusAnyoneCanPay` payout signature commits only to the withdrawal input and the user's own output, leaving the OP_RETURN "payer operator" field completely unsigned and attacker-controllable. Since `update_finalized_payouts` and the `bridge_circuit`'s `deposit_constant` both trust this OP_RETURN byte string as ground truth for "which operator funded this payout," an attacker can complete their own presigned withdrawal, self-pay their own output, and stamp an arbitrary honest operator's x-only pubkey into the OP_RETURN, triggering that operator's `PayoutCheckerTask` to kick off reimbursement for a payout it never funded.

### Finding Description
Binding: `payout_payer_operator_xonly_pk(w) == funder_of_output0(w)`. Before the attack, for a legitimate payout these are equal because the operator constructs and broadcasts the transaction, adding the operator's own funding input and its own OP_RETURN pubkey via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`). After the attack, they diverge: the withdrawer (or anyone in possession of the withdrawer's `SinglePlusAnyoneCanPay` signature) builds a self-spend of the withdrawal UTXO, keeps output 0 exactly as signed (paying themselves — required, since SIGHASH_SINGLE commits it), and appends an OP_RETURN naming a targeted honest operator's pubkey, without that operator contributing any funds or signature to the transaction.

Root cause: `parse_op_return_data`/`get_first_op_return_output` (`circuits-lib/src/bridge_circuit/mod.rs:608-692`) is used both by verifiers (`update_finalized_payouts`, `core/src/verifier.rs:2283-2353`) and inside `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:206-229`, `deposit_constant`) as the sole source of operator attribution, with no cryptographic binding between the OP_RETURN content and the actual funding/signing party of the transaction. `SinglePlusAnyoneCanPay` (enforced in `core/src/rpc/parser/operator.rs:161-203`) intentionally leaves this output — and any additional funding inputs — outside signature coverage so operators can complete the transaction, but this also permits the withdrawer to complete it themselves and forge the attribution.

Exploit flow: attacker calls Citrea `withdraw()`/obtains a withdrawal UTXO and produces (or reuses) a `SinglePlusAnyoneCanPay` signature over output-0 = attacker's own address; broadcasts a raw transaction spending the withdrawal UTXO to their own output-0, with an OP_RETURN containing operator O's public x-only pubkey. `update_finalized_payouts` records `payout_payer_operator_xonly_pk = O`. O's `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) finds this unhandled payout attributed to itself and calls `handle_finalized_payout`, which signs and broadcasts `Kickoff`/`Reimburse` transactions using O's own presigned kickoff connector (`core/src/operator.rs:839-969`), and a `bridge_circuit` proof is generated attributing `deposit_constant` to O's pubkey (parsed the same unauthenticated way), which can reach `Reimburse`.

### Impact Explanation
Operator O is credited/reimbursed the full bridge/deposit amount for a withdrawal it never funded — matching the Critical category "an operator reimbursed for a payout it never funded." Because the attacker's own output-0 already returns their funds to themselves (self-payment, no net attacker loss/gain there), the net effect is that the deposit's bridge amount is paid out twice: once implicitly (the withdrawer's own money moving to their own address) and again to operator O via the on-chain reimbursement path, at the bridge's/depositors' expense. This is repeatable for every withdrawal an attacker can register and complete themselves, and for any operator whose public x-only pubkey is known (all operator pubkeys are public), so the blast radius spans all operators and all withdrawals.

### Likelihood Explanation
Preconditions are minimal and fully within the stated unprivileged attacker capability set: ability to call Citrea `withdraw()`, choose the withdrawal UTXO bytes, produce a `SinglePlusAnyoneCanPay` signature over their own chosen output, and broadcast a Bitcoin transaction with a crafted OP_RETURN. No verifier/operator/aggregator privilege, key share, or collateral is required. Cost is limited to Bitcoin transaction fees and the attacker's own withdrawal amount (which returns to themselves). The attack is deterministic and repeatable across deposits/withdrawals and against any operator, since operator identity attribution requires no proof of funding.

### Recommendation
Bind operator attribution cryptographically to the transaction: require the OP_RETURN-attributed operator to actually sign the payout transaction (e.g., include the operator's funding input/signature as a mandatory, sighash-covered element), or otherwise require verifiers to independently confirm — before recording `payout_payer_operator_xonly_pk` — that the named operator's own input/signature/participation appears in the payout transaction, rather than trusting an unauthenticated OP_RETURN field. Alternatively, remove the operator's ability to be attributed passively and instead require an explicit, authenticated claim/reservation step (e.g., an operator-signed commitment prior to broadcast) that verifiers cross-check against the broadcast transaction.
