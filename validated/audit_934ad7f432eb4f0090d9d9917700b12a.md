### Title
Permanent freeze of deposits, withdrawals, and harvests for an entire WombatStaking pool if any fee recipient becomes blacklisted by an ERC20 token - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.deposit`, `depositLP`, `withdraw`, and `harvest` are all unprivileged, user-callable entry points that internally invoke `_toMasterWomAndSendReward`, which unconditionally calls `_sendRewards` for both the `wom` reward and any bonus tokens. `_sendRewards` iterates over the admin-configured `feeInfos` array and performs a hard `safeTransfer` (or `queueNewRewards`) to each `feeInfo.to` address for every single deposit/withdraw/harvest transaction. If any one of these fixed fee-recipient addresses is blacklisted by a blacklist-capable ERC20 (e.g. USDC-style tokens), every future call to `deposit`, `depositLP`, `withdraw`, and `harvest` for that pool reverts, permanently freezing funds and rewards for every user of the pool — not just one participant.

### Finding Description
`deposit` [1](#0-0)  and `withdraw` [2](#0-1)  both call `_toMasterWomAndSendReward`, and `harvest` calls it directly as well: [3](#0-2) .

`_toMasterWomAndSendReward` unconditionally calls `_sendRewards` for the wom reward and each bonus token balance change: [4](#0-3) .

`_sendRewards` loops through every entry of the `feeInfos` array and, for any active fee whose `isAddress` flag is set, performs a `safeTransfer` to `feeInfo.to`: [5](#0-4) . The `feeInfos` array and its `to` addresses are configured via `setFee`/`addFee` [6](#0-5)  and stored using the `Fees` struct [7](#0-6) .

Because `IERC20.safeTransfer` will revert if the underlying token (e.g. USDC) has blacklisted the recipient `feeInfo.to`, and this transfer is unconditionally executed on every single user's deposit, withdrawal, or harvest call in the pool (not gated behind any try/catch or pull-based accounting), a single blacklisted fee recipient bricks the entire pool's core functionality for all stakers — a much broader blast radius than the original Escrow.sol finding, where blacklisting only affected the blacklisted party.

### Impact Explanation
Once a `feeInfo.to` address is blacklisted by the reward or bonus token being harvested, every `deposit`, `depositLP`, `withdraw`, and `harvest` call on that pool will revert unconditionally, since `_sendRewards` is called on every such action. This locks all depositors' principal (they cannot withdraw) and all pending rewards (harvest cannot succeed) for that pool indefinitely, until governance removes the blacklisted fee entry via `removeFee`/`setFee` — meaning ordinary users have no way to unstick their own funds and are fully dependent on an admin intervention, satisfying "permanent freezing of funds" for a large class of unprivileged users.

### Likelihood Explanation
The trigger event (blacklisting) is entirely outside the control of stakers or the protocol and can occur at any time to any of the configured fee-recipient addresses if the harvested/bonus token has blacklist functionality (e.g. USDC-style tokens as bonus rewards, per the project's own token support goals). Given that `feeInfos` entries are static addresses reused across every transaction in the pool, a single blacklist event is sufficient to freeze the whole pool, making the likelihood non-trivial once such tokens are configured as bonus rewards or fee tokens.

### Recommendation
Do not perform direct `safeTransfer` calls to fee recipients inline within the deposit/withdraw/harvest critical path. Instead:
1. Use a pull-based accounting pattern: credit `feeInfo.to`'s claimable balance in a state mapping within `_sendRewards`, and expose a separate `claimFee`/`withdrawFee` function that fee recipients call themselves to pull their tokens.
2. Wrap any unavoidable inline transfers in a try/catch (or a low-level call with success check) so a revert on transfer to one recipient does not block the entire deposit/withdraw/harvest flow, e.g. skip and queue the failed transfer for a later separate claim path.
3. Allow updating a fee recipient's payout address if it becomes blacklisted, without needing to remove/re-add the whole fee configuration (which would already require an owner call anyway, but at minimum should not require unwinding funds stuck mid-flight).

### Proof of Concept
1. Owner calls `setFee`/`addFee` on `WombatStaking` to add a fee entry with `isAddress = true`, `to = feeRecipient`, for a pool where the bonus/reward token is a blacklist-capable stablecoin (e.g. USDC-like bonus token) — see `addBonusRewardForAsset` [8](#0-7) .
2. The stablecoin issuer blacklists `feeRecipient` (independent external event, e.g. due to sanctions/Tornado Cash usage/spite).
3. Any user calls `PoolHelper.deposit(...)` -> `WombatStaking.deposit(...)`, which triggers `_toMasterWomAndSendReward` -> `_sendRewards`, which attempts `IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend)` to the now-blacklisted `feeRecipient` and reverts [9](#0-8) .
4. Every subsequent `deposit`, `depositLP`, `withdraw`, and `harvest` call for that pool now reverts identically, freezing all users' principal and rewards until an owner transaction removes or changes the fee entry.

        uint256 bonusTokensLength = bonusTokens.length;

        uint256 womBeforeBalance = IERC20(wom).balanceOf(address(this));

        uint256 womRewards = IERC20(wom).balanceOf(address(this)) - womBeforeBalance;
        _sendRewards(_lpToken, wom, poolInfo.rewarder, womRewards);

                _sendRewards(_lpToken, bonusTokens[i], poolInfo.rewarder, bonusBalanceDiff);
            }
        }

    function _sendRewards(
        address _lpToken,
        address _rewardToken,
        address _rewarder,
        uint256 _amount
    ) internal {
        if (_amount == 0) return;
        uint256 originalRewardAmount = _amount;

        if (!isPoolFeeFree[_lpToken]) {
            for (uint256 i = 0; i < feeInfos.length; i++) {
                Fees storage feeInfo = feeInfos[i];

                if (feeInfo.isActive) {
                    address rewardToken = _rewardToken;
                    uint256 feeAmount = (originalRewardAmount * feeInfo.value) / DENOMINATOR;
                    _amount -= feeAmount;
                    uint256 feeTosend = feeAmount;

                    if (feeInfo.isMWOM && rewardToken == wom) {
                        if (smartWomConverter != address(0)) {
                            IERC20(wom).safeApprove(smartWomConverter, feeAmount);
                            uint256 beforeBalnce = IMWom(mWom).balanceOf(address(this));
                            IConverter(smartWomConverter).smartConvert(feeAmount, 0);
                            rewardToken = mWom;
                            feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce;
                        } else {
                            IERC20(wom).safeApprove(mWom, feeAmount);
                            uint256 beforeBalnce = IMWom(mWom).balanceOf(address(this));
                            IMWom(mWom).deposit(feeAmount);
                            rewardToken = mWom;
                            feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce;
                        }
                    }

                    if (!feeInfo.isAddress) {
                        IERC20(rewardToken).safeApprove(feeInfo.to, 0);
                        IERC20(rewardToken).safeApprove(feeInfo.to, feeTosend);
                        IBaseRewardPool(feeInfo.to).queueNewRewards(feeTosend, rewardToken);
                    } else {
                        IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend);
                        emit RewardPaidTo(feeInfo.to, rewardToken, feeTosend);
                    }
                }
            }
        }
