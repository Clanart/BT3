### Title
SchnorrSignature::verify accepts a universal forgery (R = identity, s = 0) whenever the public key is the identity, which attacker-controlled `ThresholdKeys::read` bytes can induce - (File: crypto/schnorr/src/lib.rs)

### Summary
`SchnorrSignature::verify` validates the equation `R + cA - sG == 0` via `multiexp_vartime` but never rejects an identity public key `A` or identity nonce commitment `R`. When `A` is the identity, the forged signature `(R = identity, s = 0)` satisfies the equation for every challenge `c`, i.e. it "verifies" for any message. `read_G`/`read_F` accept the canonical identity/zero encodings, and `ThresholdKeys::read` ingests attacker-controlled `verification_shares` from which `ThresholdKeys::new` derives `group_key` — an unprivileged party can therefore craft bytes whose deserialized `group_key` is the identity, then pass the trivial forged signature under it.

### Finding Description
In `crypto/schnorr/src/lib.rs:88-110`, `batch_statements`/`verify` compute `multiexp_vartime([(ONE, R), (c, A), (-s, G)])` and check it is the identity. If `A = identity` and the signature is `R = identity, s = 0`, the sum is `identity + c*identity - 0*G = identity` for **any** challenge `c`, so verification succeeds regardless of the message. There is no identity check on `public_key`, `R`, or a nonzero check on `s`.

The public key and signature reach this code from untrusted bytes: `C::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only enforces canonical encoding — the identity encoding is canonical and accepted — and `SchnorrSignature::read` (`crypto/schnorr/src/lib.rs:51-53`) reads `R` and `s` verbatim. Meanwhile `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) reads `t`, `n`, `i`, a secret share, and `n` verification shares directly from the byte stream and passes them to `ThresholdKeys::new`, which interpolates the group key from the supplied shares. An attacker who supplies verification shares whose interpolation over participants `1..=t` sums to the identity obtains a `ThresholdKeys`/`ThresholdView` whose `group_key()` is the identity. (Not fully verified: whether `ThresholdKeys::new` performs a non-identity sanity check on the resulting group key — no such check was found in the indexed code, and none of the `read`/`new` paths inspect `is_identity`.)

### Impact Explanation
Under a group key equal to the identity, `SchnorrSignature { R: identity, s: 0 }` is a universal forgery: it verifies for every message and every challenge. Any downstream consumer that verifies a FROST/Schnorr output signature against `view.group_key()` (e.g., to accept a signed transaction or to confirm key ownership) can be made to accept signatures on arbitrary messages that no private key produced — a concrete forged signature reachable entirely from public bytes fed to `ThresholdKeys::read` + `SchnorrSignature::read`/`verify`. Analogous to CVE-2022-21334's class: attacker-supplied input to a trusted component yields takeover of the security decision (signature validity) rather than a crash or resource flaw.

### Likelihood Explanation
Medium. Exploitation requires the attacker to influence the deserialized threshold key material or the verification key used (e.g., a serialized `ThresholdKeys`/`ThresholdView` or signer-supplied key in a MuSig/PedPoP-style flow). This is a realistic precondition — these structures cross trust boundaries — but it is not a purely remote unauthenticated trigger against an already-initialized honest participant, hence not High.

### Recommendation
- In `SchnorrSignature::verify` and `batch_statements` consumers, reject `public_key.is_identity()` and `self.R.is_identity()` (and consider rejecting `s == 0`).
- In `ThresholdKeys::new` / `ThresholdView` construction, assert the interpolated `group_key` is non-identity, and reject identity verification shares in `ThresholdKeys::read`.
- Optionally reject identity `R`/points in `read_G` call sites where identity has no legitimate meaning (or add a `read_nonidentity_G` helper in `Ciphersuite`).

### Proof of Concept
```rust
// Requires: ciphersuite, schnorr, dalek-ff-group (or any in-scope Ciphersuite)
use zeroize::Zeroizing;
use group::Group;
use ciphersuite::Ciphersuite;
use dalek_ff_group::{Ed25519, Scalar};
use schnorr::SchnorrSignature;

#[test]
fn identity_key_universal_forgery() {
    // Attacker-controlled key material: ThresholdKeys::read bytes whose
    // verification shares interpolate to the identity group key.
    let group_key = <Ed25519 as Ciphersuite>::G::identity();

    // The trivial forgery: R = identity, s = 0.
    let forged = SchnorrSignature::<Ed25519> {
        R: <Ed25519 as Ciphersuite>::G::identity(),
        s: Scalar::ZERO,
    };

    // Any challenge => batch_statements sum is identity + c*identity - 0*G = identity.
    for msg in [&b"transfer all funds"[..], b"arbitrary message"] {
        let c = Ed25519::hash_to_F(b"any-challenge-dst", msg);
        assert!(forged.verify(group_key, c)); // forged signature "valid" for any message
    }

    // The same forgery round-trips through the untrusted-byte readers:
    // SchnorrSignature::read accepts canonical identity/zero encodings, and
    // read_G/read_F impose no non-identity / non-zero checks.
    let mut bytes = Vec::new();
    forged.write(&mut bytes).unwrap();
    let decoded = SchnorrSignature::<Ed25519>::read(&mut bytes.as_slice()).unwrap();
    assert!(decoded.verify(group_key, Scalar::ONE));
}
```

Root cause: `verify` treats the verification equation as sufficient while omitting the standard identity-key exclusion, and the deserialization paths (`ThresholdKeys::read`, `read_G`) permit the identity element into the public-key position.
