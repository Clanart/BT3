## Finding: Cross-function signature replay between `withdraw()` and `accumulate()` beneficiary redirection

Both are legitimate, locally-provable bugs but the strongest, most concrete one is the shared, undomained message format between `pallet-relayer`'s `withdraw()` and `accumulate()` beneficiary-redirect paths.

### Title
Signature reuse across `Relayer::withdraw` and `Relayer::accumulate` due to identical, undomained signed payload - (`modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-relayer` authorizes two distinct, high-impact operations — an immediate fee withdrawal (`withdraw`) and a beneficiary redirect during batch proof accumulation (`accumulate`) — using signatures over structurally identical payloads: `keccak256((nonce: u64, state_machine: StateMachine, beneficiary: Vec<u8>).encode())`. Neither payload includes a domain tag, function selector, or any value that distinguishes "authorize a withdraw" from "authorize an accumulate-time beneficiary redirect." Because both functions key their nonce off the same `Nonce<T>` storage map `(address, state_machine)`, a signature crafted by a relayer for one of these two calls is a valid signature for the other, exactly the "arbitrary data as signature" class described in the source report (no domain separator, no purpose/type binding).

Both hash a SCALE-encoded `(u64, StateMachine, Vec<u8>/&[u8])` tuple with no additional context, so for identical `(nonce, state_machine, beneficiary)` the two functions produce byte-identical digests and thus accept the same signature. Both consume the relayer's nonce from the same map: [3](#0-2) [4](#0-3) 

Both `withdraw` and `accumulate` are public, unsigned extrinsics validated only by signature recovery — there is no `ensure_signed`/origin binding to the relayer, so anyone observing a previously broadcast/on-chain signature can resubmit it into the *other* function while the nonce is still unconsumed. `withdraw()` immediately dispatches the full currently-accumulated `Fees[dest_chain][address]` balance and zeroes it: [5](#0-4) 
while `accumulate()`'s beneficiary path only redirects the fee delta from the batch being proven in that call: [6](#0-5) 

These are semantically very different actions with different amounts at stake, yet share one undomained signature format — the exact "no type hash / no domain separator" flaw the external report calls out for `Factory.sol`.

### Impact Explanation
An attacker who captures a relayer's signature intended for one of these calls (visible on-chain the instant it is submitted, since these are unsigned extrinsics with no other replay protection besides this shared nonce) can resubmit it into the other function before the relayer's own transaction consumes the nonce. This lets a third party:
- Force an immediate, full `withdraw()` of a relayer's entire accumulated `Fees` balance to a beneficiary the relayer only meant to authorize for a single, smaller `accumulate()` batch, or
- Force an `accumulate()` beneficiary redirect using a signature the relayer only meant for a one-time `withdraw()`, redirecting fees from unrelated newly-proven delivery batches.

Either way this is unauthorized execution of a state-mutating, fund-moving action beyond what the relayer's signature was intended to authorize — a logic/replay attack reachable by any unprivileged observer, matching the "unauthorized transaction or execution" / "logic attacks" impact categories.

### Likelihood Explanation
Moderate. It requires a legitimate relayer signature to exist for either call and for that signature to be observed before the nonce is consumed (e.g., in the transaction pool, or from a prior block if the legitimate call was never included). No malicious relayer, prover, or admin is needed — only an ordinary chain observer replaying public data, which the task's gate explicitly allows.

### Recommendation
Bind each signed payload to its specific call with a domain/context tag (e.g., a distinct byte prefix such as `b"withdraw"` vs `b"accumulate-beneficiary"`, or separate the nonce spaces), analogous to adopting an EIP-712-style domain/type-hash separation as recommended in the source report, so a signature for one entrypoint can never be replayed into the other.

### Proof of Concept
1. Relayer `R` (EVM) with nonce `N` on `state_machine = X` signs `msg = keccak256((N, X, B).encode())` intending to call `accumulate()` to redirect one small proven batch's fee to `B`.
2. Before that extrinsic executes, an unprivileged attacker submits `withdraw({ signature: sig(msg), dest_chain: X, beneficiary: Some(B) })`. `Nonce::<T>::get(R, X) == N` still, so `message(N, X, Some(B))` matches `msg`, verification passes, and the *entire* `Fees[X][R]` balance is dispatched to `B` and zeroed, and `Nonce[R][X]` becomes `N+1` — an action `R` never separately authorized at this magnitude/timing.
3. `R`'s originally intended `accumulate()` call, now reading `Nonce[R][X] == N+1`, fails signature verification (since it was signed for `N`), demonstrating the cross-function confusion and consequent griefing/forced-withdrawal. [1](#0-0) [2](#0-1)
