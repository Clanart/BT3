### Title
Native CPI path (`native_invoke_signed`) skips the base `invoke_units` compute charge applied to BPF syscall CPIs, underpricing compute for builtin-triggered cross-program invocations - (File: program-runtime/src/invoke_context.rs)

### Summary
The BPF syscall CPI path (`cpi_common`) charges a flat `invoke_units` compute fee before performing any cross-program invocation work, but the builtin/native CPI path (`native_invoke_signed`) — used by native programs (e.g. bpf_loader, vote program) to CPI into other programs on behalf of a user transaction — never charges this same base cost. This is structurally analogous to the Putty finding where one code path (calls) correctly deducted fees while the parallel path (puts) omitted the deduction entirely.

### Finding Description
In the syscall-driven CPI implementation, every cross-program invocation begins by charging the `invoke_units` compute cost before doing any translation or invocation work: [1](#0-0) 

This cost is defined as "Number of compute units consumed by an invoke call (not including the cost incurred by the called program)" [2](#0-1) , and is a base overhead intentionally charged per invocation regardless of the actual work performed.

However, `InvokeContext::native_invoke_signed`, the equivalent entrypoint "for a cross-program invocation from a builtin program", never calls `compute_meter.consume_checked` for `invoke_units` (or any base cost) at all — it only derives signer PDAs, calls `prepare_next_cpi_instruction`, and then `process_instruction`: [3](#0-2) 

This function is invoked by builtin programs such as `bpf_loader` (during upgrade/program-management CPIs), the `vote` program, and other core builtins during ordinary, unprivileged user-triggered transactions: [4](#0-3) [5](#0-4) 

Contrast this with the syscall path, where the equivalent base fee is unconditionally deducted up front (`program-runtime/src/cpi.rs:785-786`) before the callee is even invoked. The two paths implement the same conceptual operation (dispatching a cross-program invocation) but only one of them pays the base "invoke" overhead — the native path is "free of any fee" relative to the syscall path, mirroring the put-vs-call asymmetry in the referenced report.

### Impact Explanation
Every unit of `invoke_units` skipped on the native CPI path represents underpriced compute: a transaction that repeatedly drives builtins to perform CPI via `native_invoke_signed` (e.g. through repeated builtin instructions that internally CPI, such as bpf_loader management instructions or vote program operations that recurse into System Program) pays strictly less compute than an SBF program performing the equivalent number of `invoke_signed` syscalls for the same underlying dispatch overhead. This is a case of "materially underpriced compute" for a reachable, unprivileged-user code path, since it lets certain transaction shapes obtain proportionally more actual work (multiple internal CPI dispatches through builtins) per compute unit purchased than the fee-market/compute-budget model assumes, and it creates an inconsistency in the accounting model that cost/compute-unit calibration for CPI overhead is meant to capture uniformly.

### Likelihood Explanation
This is a deterministic, code-inherent gap — not a proof-of-concept or theoretical edge case: any current call site of `native_invoke_signed` (builtin-to-program CPI) unconditionally skips the `invoke_units` charge on every invocation, and these call sites are reachable by ordinary, unprivileged transactions that exercise the relevant builtin program instructions (no special privilege or validator role required).

### Recommendation
Charge the same base `invoke_units` compute cost in `native_invoke_signed` that `cpi_common` charges for syscall-driven CPI, i.e. call `self.compute_meter.consume_checked(self.get_execution_cost().invoke_units)?` at the start of `native_invoke_signed`, before `prepare_next_cpi_instruction`/`process_instruction`, so both CPI entrypoints are priced consistently.

### Proof of Concept
Not independently executed; the analysis is based on direct code comparison between the two CPI entrypoints:
- `cpi_common` (syscall path) charges `invoke_units` unconditionally at entry: [1](#0-0) 
- `native_invoke_signed` (builtin/native path) performs the equivalent dispatch (`prepare_next_cpi_instruction` + `process_instruction`) with no corresponding charge: [6](#0-5) 

I was not able to fully trace every current call site of `native_invoke_signed` (e.g. exact reachability/frequency within `bpf_loader` and `vote` program logic) within the available tool budget; a background Devin session with full repository access would be needed to enumerate all call sites and construct a concrete transaction-level compute-unit measurement confirming the discrepancy end-to-end.

```rust
    /// Entrypoint for a cross-program invocation from a builtin program.
    ///
    /// Takes signer seeds and derives PDAs internally via
    /// `create_program_address`, mirroring the SBF CPI path. This makes
    /// it structurally impossible for a builtin to vouch for a non-PDA
    /// address (e.g. a user wallet) as a signer.
    pub fn native_invoke_signed(
        &mut self,
        instruction: Instruction,
        signer_seeds: &[&[&[u8]]],
    ) -> Result<(), InstructionError> {
        let caller_program_id = *self
            .transaction_context
            .get_current_instruction_context()?
            .get_program_key()?;
        // The conversion from `PubkeyError` to `InstructionError` through
        // num-traits is incorrect, but it's the existing behavior.
        let signers = signer_seeds
            .iter()
            .map(|seeds| Pubkey::create_program_address(seeds, &caller_program_id))
            .collect::<Result<Vec<Pubkey>, solana_pubkey::PubkeyError>>()
            .map_err(|e| e as u64)?;
        self.prepare_next_cpi_instruction(instruction, &signers)?;
        let mut compute_units_consumed = 0;
        self.process_instruction(&mut compute_units_consumed, &mut ExecuteTimings::default())?;
        Ok(())
    }
```
