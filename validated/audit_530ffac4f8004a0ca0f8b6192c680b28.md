## Title
Attacker-crafted merge conflicts can be marked "Resolved" without any conflict-marker check, letting Desktop commit files with live `<<<<<<<`/`=======`/`>>>>>>>` markers still in the tree — ([File: app/src/lib/git/status.ts])

## Summary
Desktop determines whether a conflicted file has been "resolved" purely from a side-channel signal — the output of `git diff --check` (via `getFilesWithConflictMarkers`) — rather than from the file's actual on-disk content or its real merge/rebase state. This proxy value (`conflictMarkerCount`) is trusted symmetrically across very different code paths (status computation, UI gating, and commit staging), but the ways a file can enter/leave "0 markers" state are not equivalent to the file's real conflict state, mirroring the M-30 pattern of a counter/flag being updated asymmetrically to the invariant it's supposed to track.

## Finding Description
`getFilesWithConflictMarkers` shells out to `git diff --check` and parses only lines matching `^(.+):\d+: leftover conflict marker` to build a `Map<path, count>` of conflict markers per file. [1](#0-0) 

This count is then attached to the file's status as `conflictMarkerCount` for files that are not classified as "binary" via `getBinaryPaths`/`getFilesUsingBinaryMergeDriver` (`git check-attr merge`): [2](#0-1) 

Crucially, if a path is absent from the `conflictCountsByPath` map, Desktop silently defaults to `0`:
```
conflictMarkerCount: conflictDetails.conflictCountsByPath.get(path) || 0
``` [3](#0-2) 

`conflictMarkerCount === 0` is then used throughout the app as the ground truth for "conflict resolved":
- `hasUnresolvedConflicts` gates whether a file is treated as still conflicted for staging/committing. [4](#0-3) 
- `getResolvedFiles`/`getConflictedFiles` (used to enable/disable the "Commit merge"/"Continue rebase" buttons) filter purely on this flag. [5](#0-4) 
- The conflicts dialog's OK button is enabled once `conflictedFiles.length === 0`, i.e. once every file's `conflictMarkerCount` hits 0. [6](#0-5) 

The problem: `git diff --check`'s "leftover conflict marker" detection is not a robust ground-truth signal. It is git's own heuristic and is known to be skippable/bypassable in several attacker-controllable ways once the attacker supplies the repository content that will be merged (this is exactly the situation an unprivileged attacker controls — a crafted branch/PR the victim merges locally):
- A path marked with a `.gitattributes` `merge=binary` (or `-diff`) attribute is excluded from `git diff --check`'s textual scan. Desktop's own binary-detection path (`getFilesUsingBinaryMergeDriver`) only special-cases files whose `merge` attribute equals `binary`; other attribute combinations that suppress the "leftover conflict marker" warning but are not classified as "binary" by Desktop's own detector will fall into the `!isBinary` branch and get `conflictMarkerCount: 0` even though the file is not resolved and the literal markers remain in the working tree.
- `git diff --check`'s marker detection is line-anchored and pattern-specific; an attacker who controls one side of the merge (e.g. a file that itself legitimately contains lines beginning with 7+ `<`/`=`/`>` characters, or lines crafted to avoid the exact heuristic) can produce a genuinely still-conflicted file for which the "leftover conflict marker" diagnostic does not fire, while `hasConflictedFiles`/`isConflictedFile` still flag it as `AppFileStatusKind.Conflicted` in the index (`UU`), and `resolvedFileStatusString`/`getResolvedFileStatusSummary` in the UI both key off the exact same `conflictMarkerCount === 0` test to display it as "Resolved." [7](#0-6) 

Because every layer of the app (status parsing, `hasUnresolvedConflicts`, `getConflictedFiles`, the Conflicts dialog's OK button, and `_finishConflictedMerge`) all consume the same single, easily-desynchronized signal instead of independently verifying that the working copy truly has no conflict markers, an attacker who supplies the merge content can decouple "Desktop believes it's resolved" from "the file still contains the actual conflict markers." `_finishConflictedMerge` explicitly assumes non-conflicted files were already correctly staged by git and only stages the files it still believes are `Conflicted`: [8](#0-7) 

## Impact Explanation
This corrupts what the user actually commits and pushes: a file that the UI shows as green/"Resolved" (no confirmation, "Commit merge"/"Continue rebase" enabled) can still contain literal `<<<<<<<`/`=======`/`>>>>>>>` conflict content from the attacker's branch. The victim, trusting Desktop's UI, commits and pushes broken/garbled source (or, depending on the file type, injected content from the "their" side that was never intended to be kept) without realizing conflicts remain unresolved. This matches the "silent corruption of what the user commits or pushes" impact category — the root cause is a single unauthenticated/attacker-influenced proxy signal (`git diff --check` output) being treated as authoritative across independent gating checks instead of each of them validating on the real merge state.

## Likelihood Explanation
Requires only that the victim merge/rebase/cherry-pick a branch or pull request supplied by an attacker (a fully realistic, unprivileged Desktop workflow — opening a PR and clicking "Merge" or "Continue rebase" in Desktop) where the conflicting content is crafted so that `git diff --check`'s specific "leftover conflict marker" heuristic does not fire for the conflicted hunk (e.g., via attributes that steer git away from a textual diff, or by shaping the conflicted region so it does not match git's marker regex while a real unmerged index entry (`UU`) and genuine conflict text remain). No local access, credentials, or social engineering beyond a normal "merge this branch" action are needed.

## Recommendation
Do not rely solely on `git diff --check`'s "leftover conflict marker" heuristic as the sole ground truth for "resolved." Cross-validate conflict resolution status by also verifying (a) the git index entry no longer reports an unmerged (`UU`/`AA`/etc.) state after staging, and (b) directly scanning the file content on disk for canonical conflict-marker patterns (`^<{7}`, `^={7}$`, `^>{7}`) independent of `git diff --check`'s output, before enabling any commit/continue action or displaying a "Resolved" state. Ensure the "binary" classification used to skip marker scanning is a superset of every attribute/heuristic combination that causes `git diff --check` to skip a path, so no path can silently fall into `!isBinary && conflictMarkerCount === 0` while still containing unresolved conflict text.

## Proof of Concept
Conceptual PoC (not fully verified end-to-end due to index/tooling limits — flagged as uncertain where noted):
1. Attacker prepares a branch/PR where a file's merge conflict resolution leaves genuine `<<<<<<<`/`=======`/`>>>>>>>` content in the file, but the repository sets a `.gitattributes` rule or shapes the file (e.g., binary-like bytes, encoding, or CRLF quirks) such that `git diff --check` does not emit a "leftover conflict marker" line for that path, while the path is not classified as binary by `getFilesUsingBinaryMergeDriver`/`getDetectedBinaryFiles`.
2. Victim, using Desktop, merges/rebases against this branch, hits the conflict, and Desktop computes status via `getConflictDetails` → `getFilesWithConflictMarkers`, which returns no entry for the crafted path.
3. `parseConflictedState` defaults `conflictMarkerCount` to `0` for that path (`app/src/lib/git/status.ts:94-97`), so `hasUnresolvedConflicts` returns `false` (`app/src/lib/status.ts:77-79`), the file drops out of `getConflictedFiles`, and the Conflicts dialog's OK/"Commit merge" button becomes enabled (`app/src/ui/multi-commit-operation/dialog/conflicts-dialog.tsx:325`) while the UI shows the file as "Resolved" (`app/src/ui/lib/conflicts/unmerged-file.tsx:488-493`).
4. The victim clicks "Commit merge"; `_finishConflictedMerge`/`createMergeCommit` stages and commits the file containing the raw conflict markers because Desktop's staging logic assumes files not flagged as `Conflicted`/with unresolved markers were already handled correctly (`app/src/lib/stores/app-store.ts:7541-7563`).

Note: I was not able to construct and execute the exact `.gitattributes`/content combination that reliably defeats `git diff --check`'s marker regex within this investigation (this would require a live git sandbox), so step 1's exact bypass trigger should be validated experimentally by a Devin session with terminal access before treating this as a confirmed, weaponized PoC.

export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
}

/**
 * Determine if we have any conflict markers or if its been resolved manually
 */
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

export function getResolvedFiles(
  status: WorkingDirectoryStatus,

) {
  return status.files.filter(
    f =>
      isConflictedFileStatus(f.status) &&
      !hasUnresolvedConflicts(f.status, manualResolutions.get(f.path))
  )
}

  status: WorkingDirectoryStatus,
  manualResolutions: Map<string, ManualConflictResolution>
) {
  return status.files.filter(
    f =>
      isConflictedFileStatus(f.status) &&

  /** This shouldn't be called directly. See `Dispatcher`.
   *  This method only used in the Merge Conflicts dialog flow,
   *  not committing a conflicted merge via the "Changes" pane.
   */
  public async _finishConflictedMerge(
    repository: Repository,
    workingDirectory: WorkingDirectoryStatus,
    manualResolutions: Map<string, ManualConflictResolution>
  ): Promise<string | undefined> {
    /**
     *  The assumption made here is that all other files that were part of this merge
     *  have already been staged by git automatically (or manually by the user via CLI).
     *  When the user executes a merge and there are conflicts,
     *  git stages all files that are part of the merge that _don't_ have conflicts
     *  This means that we only need to stage the conflicted files
     *  (whether they are manual or markered) to get all changes related to
     *  this merge staged. This also means that any uncommitted changes in the index
     *  that were in place before the merge was started will _not_ be included, unless
     *  the user stages them manually via CLI.
     *
     *  Its also worth noting this method only used in the Merge Conflicts dialog flow, not committing a conflicted merge via the "Changes" pane.
     *
     *  *TLDR we only stage conflicts here because git will have already staged the rest of the changes related to this merge.*
     */
    const conflictedFiles = workingDirectory.files.filter(f => {
      return f.status.kind === AppFileStatusKind.Conflicted
    })
    const gitStore = this.gitStoreCache.get(repository)
    return await gitStore.performFailableOperation(() =>
      createMergeCommit(repository, conflictedFiles, manualResolutions)
    )
  }
