### Title
Shared `BalanceHandler` Instance in Recursive/Nested Precompile Calls Causes Stale `prevEventsLen` and StateDB/Bank Balance Corruption - (File: `precompiles/common/balance_handler.go`)

### Summary
The FunC bug describes a stale-cache class of vulnerability: a value snapshotted at one point in time (`success_amount`, `service_fee`) is consumed later, after the underlying source of truth has changed, without revalidation. The Cosmos EVM analog is the `BalanceHandler`'s `prevEventsLen` cursor used to synchronize bank-module events with the EVM `StateDB`. When precompile calls are recursive/nested (a precompile call that internally triggers another call into the same precompile, or the shared handler instance is reused across nested calls), the inner call's `BeforeBalanceChange` overwrites the same `prevEventsLen` field that the outer call is relying on, causing the outer call's `AfterBalanceChange` to compute over the wrong "before" event-index. The repository itself contains a dedicated regression test explicitly describing this defect: [1](#0-0) .

### Finding Description
`BalanceHandler` records the event log length before a precompile-triggered bank operation, then reprocesses only the events appended after that index to synchronize the `StateDB`'s cached balances (`AddBalance`/`SubBalance`) with the real bank-keeper balance change caused by the precompile: [2](#0-1) [3](#0-2) .

`prevEventsLen` is a single mutable field on the handler struct: [4](#0-3) . If the same `BalanceHandler` instance is reused/shared for nested or reentrant precompile invocations within one EVM transaction (e.g. via `p.GetBalanceHandler()` returning a handler stored on the precompile struct rather than a fresh instance per call, as used by the debug precompile and by staking/distribution/gov/ics20/slashing/erc20 precompiles per the `GetBalanceHandler`/`BalanceHandler` usages), the inner call's `BeforeBalanceChange` invocation resets `prevEventsLen` to a later index than the outer call originally captured: [5](#0-4) .

When the outer call's `AfterBalanceChange` subsequently runs, it slices `events[bh.prevEventsLen:]` using the corrupted (now stale-relative, but effectively “too-high”/wrong) cursor, meaning some bank `coin_spent`/`coin_received`/precisebank fractional-balance events emitted by the outer precompile operation are silently skipped and never applied to the `StateDB`, while events already consumed by the inner call could also be reprocessed depending on ordering: [6](#0-5) . This is architecturally identical to the FunC bug: a cached index/parameter captured at one point is silently invalidated by a later, unrelated state-changing event, and the consuming code proceeds without revalidating it, corrupting downstream accounting. The `Precompile.RunNativeAction`/`runNativeAction` path shows a partially-hardened alternative that constructs a *new* handler per call via a factory, confirming that the shared/reused-handler pattern is the defective one still present elsewhere: [7](#0-6) .

The codebase's own reproduction test explicitly demonstrates that recursive precompile calls share a `BalanceHandler` instance and overwrite `prevEventsLen`, and states this "leads to balance desync between native bank keeper and EVM stateDB": [8](#0-7) .

### Impact Explanation
The `StateDB` balance for native/EVM-visible accounts is the value ultimately committed back into keeper state at the end of the transaction via `Commit`/`commitWithCtx`, which persists the `stateObject`'s account/balance data: [9](#0-8) . If `AfterBalanceChange` drops or double-applies bank events due to the stale `prevEventsLen`, the `StateDB`'s view of an account balance diverges from the bank module's actual ground-truth balance for that account. This is a direct instance of the allowed impact class "irreversible accounting corruption of spendable user value across native balances, EVM balances ... or precompile-mediated assets" — funds can appear duplicated (unauthorized inflation of a balance visible to the EVM and subsequently spendable) or silently lost/frozen (a legitimate credit never reflected in the EVM-visible balance), both of which are Critical-severity outcomes reachable purely through ordinary unprivileged smart-contract calls that trigger nested/recursive precompile invocations (e.g., a caller contract that calls a precompile, which itself calls back into a precompile, as demonstrated by the debug/caller pattern in the regression test).

### Likelihood Explanation
The trigger path is fully reachable by an unprivileged user: it only requires deploying a contract that invokes one of the stateful precompiles (staking, distribution, gov, ics20, slashing, erc20, or a caller pattern like the debug precompile) in a manner that produces nested/recursive precompile calls within a single EVM transaction. The codebase's maintainers have already written a dedicated integration test to reproduce this exact scenario, which strongly indicates it is a known, reachable behavior in production precompile code paths, not a hypothetical or already-fully-mitigated one for every precompile (only the newer `RunNativeAction`/factory-based construction appears hardened).

### Recommendation
Never share a single `BalanceHandler` (and its `prevEventsLen` cursor) across nested/recursive precompile invocations within the same EVM call stack. Every precompile entry point should construct a fresh `BalanceHandler` per invocation (as done in `precompiles/common/precompile.go`'s `runNativeAction` via `BalanceHandlerFactory.NewBalanceHandler()`), and this pattern must be applied uniformly to all precompiles that currently obtain the handler via `p.GetBalanceHandler()` returning a struct-level shared field (staking, distribution, gov, ics20, slashing, erc20, and the debug precompile). Additionally, consider maintaining a call-stack-aware (or event-index-diff-based, not absolute-length-based) accounting mechanism so that concurrent/nested handlers cannot clobber each other's starting index, analogous to the FunC report's recommendation of a versioned/snapshotted state check rather than a single mutable shared cursor.

### Proof of Concept
The repository's own test demonstrates the mechanics: a caller contract invokes the debug precompile recursively (`callback` recursion), and the shared `BalanceHandler`/`prevEventsLen` field is overwritten across the nested calls: [10](#0-9) . To weaponize this against a real balance-affecting precompile (e.g. `erc20`/`staking`/`distribution`), an attacker would deploy a contract that:
1. Calls a stateful precompile method that transfers/mints/burns bank coins (emitting `coin_spent`/`coin_received` events) and internally shares/reuses the same `BalanceHandler`.
2. From within that first precompile call (or via an immediately nested contract call), triggers a second call into a precompile that also invokes `BeforeBalanceChange`, resetting `prevEventsLen`.
3. Observes that the outer call's `AfterBalanceChange` then fails to apply (or double-applies) the bank balance-change events to `StateDB`, producing a persistent divergence between the bank keeper's true balance and the EVM-visible/committed balance for the involved accounts.

I was unable to fully trace, within the available iterations, the exact code path connecting `StateDB.Commit()`/native-balance handling back to bank-keeper minting/burning for every account type, which would be needed to give an exact numeric PoC of fund duplication vs. fund freezing; this should be verified with a live reproduction (extending the existing `balance_handler_test.go` to also assert on final bank-keeper vs. `StateDB` balance equality, which the current test does not check).

// commitWithCtx writes the dirty states to keeper
// using the provided context
func (s *StateDB) commitWithCtx(ctx sdk.Context) error {
	for _, addr := range s.journal.sortedDirties() {
		obj := s.stateObjects[addr]
		if obj.selfDestructed {
			if err := s.keeper.DeleteAccount(ctx, obj.Address()); err != nil {
				return errorsmod.Wrapf(err, "failed to delete account %s", obj.Address())
			}
		} else {
			if obj.code != nil && obj.dirtyCode {
				if len(obj.code) == 0 {
					s.keeper.DeleteCode(ctx, obj.CodeHash())
				} else {
					s.keeper.SetCode(ctx, obj.CodeHash(), obj.code)
				}
			}
			if err := s.keeper.SetAccount(ctx, obj.Address(), obj.account); err != nil {
				return errorsmod.Wrap(err, "failed to set account")
			}

			for _, key := range obj.dirtyStorage.SortedKeys() {
				valueBytes := obj.dirtyStorage[key].Bytes()
				if len(valueBytes) == 0 {
					s.keeper.DeleteState(ctx, obj.Address(), key)
				} else {
					s.keeper.SetState(ctx, obj.Address(), key, valueBytes)
				}
			}
		}
	}
	return nil
