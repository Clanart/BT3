## Title
`aptos move verify-package` never compares on-chain bytecode, only self-reported source metadata, so verification can be spoofed - ([File: aptos-move/cli/src/commands.rs])

### Summary
The `VerifyPackage` CLI command is documented and named as a bytecode verifier, but its implementation only diffs `PackageMetadata` fields (name, deps, `ModuleMetadata` source/source_map/name, manifest, upgrade policy, source digest). It never fetches or compares the actual deployed Move bytecode. This breaks the "verified bytes must match committed module bytes" invariant that the tool exists to enforce.

### Finding Description
The doc comment on `VerifyPackage` states it "Downloads the package from onchain and verifies the bytecode matches a local compilation of the Move code": [1](#0-0) 

Its `execute()` builds the package locally, extracts `PackageMetadata`, then fetches the on-chain registry with `CachedPackageRegistry::create(client, self.account, false)` — note the `false` for `with_bytecode` — and calls `package.verify(&compiled_metadata)`: [2](#0-1) 

`CachedPackageRegistry::create` only populates its `bytecode: BTreeMap` when `with_bytecode` is `true`; here it is hard-coded `false`, so `bytecode` stays empty: [3](#0-2) 

`CachedPackageMetadata::verify()` then only compares `PackageMetadata` fields — `name`, `deps`, `modules` (which is `ModuleMetadata`: name/source/source_map/extension — self-reported gzipped Move source, not bytecode), `manifest`, `upgrade_policy`, `extension`, `source_digest`: [4](#0-3) 

On-chain, `code::publish_package_txn` accepts `metadata_serialized` and `code` (the actual bytecode bundle) as two independent, uncorrelated arguments — the Move framework's `validate_publish_request` only checks that module *names* declared in the metadata match module names found in the bytecode bundle, and performs dependency/compatibility/verifier checks on the bytecode itself: [5](#0-4) [6](#0-5) 

Nothing on-chain or in `verify-package` binds the human-readable `source`/`source_digest` fields inside `PackageMetadata` to the actual compiled bytecode that gets executed. A publisher can submit accurate-looking source metadata (matching a benign, publicly reviewed source tree) together with entirely different, malicious compiled bytecode. Since the CLI's `verify-package` never downloads or diffs the real bytecode, it will report "Successfully verified source of package" for this malicious deployment as long as the attacker-supplied metadata's source text and digest match what a reviewer's local build produces.

### Impact Explanation
This is a code-integrity/verification-bypass bug: the primary developer-facing safeguard documented in `third_party/move/documentation/book/src/cli-deploy.md` ("For code review and reproducibility, `verify-package` checks that on-chain bytecode matches a local source tree") and in the dependency security guidance ("it is highly recommended you know and understand the entity publishing the package"/verify code before depending on it) is not actually performed: [7](#0-6) [8](#0-7) 

A downstream integrator relying on `aptos move verify-package` to gate whether they trust/depend on a third-party package could be led to believe deployed bytecode matches known-good source, when the executed code is actually different and potentially malicious (e.g., backdoored, draining funds, or bypassing intended access control), since it is the actual bytecode — not the metadata's `source` blob — that runs on mainnet.

### Likelihood Explanation
Any package publisher fully controls both the `metadata_serialized` and `code` arguments passed to `code::publish_package_txn`/`request_publish[_with_allowed_deps]`; there is no on-chain requirement that `ModuleMetadata.source`/`source_digest` be derived from, or consistent with, the actual bytecode blobs being published — deterministic compilation is assumed but never enforced. Exploiting the CLI's false sense of assurance requires only that a victim runs `aptos move verify-package` against the malicious account and trusts the "Successfully verified" result, which is exactly the documented use case for the command.

### Recommendation
Make `VerifyPackage::execute` always fetch bytecode (`CachedPackageRegistry::create(client, self.account, true)`), compile the local package to bytecode, and additionally compare each module's on-chain bytecode bytes (via `registry.get_bytecode(module_name)`) against the locally compiled bytecode (`pack.extract_code()`), failing verification on any mismatch — not just on metadata/source differences.

### Proof of Concept
1. Attacker prepares a benign Move source tree `S` and compiles it to produce metadata `M` (name, deps, module sources, manifest, `source_digest`).
2. Attacker separately crafts malicious bytecode `B` (e.g., adds a backdoor function or bypasses an authorization check) whose module names match those declared in `M`, satisfying `validate_publish_request`'s name-matching check.
3. Attacker calls `code::publish_package_txn(owner, bcs(M), B)` (directly, or via `object_code_deployment::publish`/`resource_account::create_resource_account_and_publish_package`), which succeeds because on-chain checks only validate module names, dependency policy, and bytecode-level compatibility/verifier rules — never that `B` corresponds to `M`'s declared source.
4. A reviewer runs `aptos move verify-package --account <attacker>` against a locally rebuilt copy of source `S`.
5. `VerifyPackage::execute` calls `CachedPackageRegistry::create(client, account, false)` (no bytecode fetched) and `package.verify(&compiled_metadata)`, which only diffs `PackageMetadata` fields — all of which match, since the attacker published the honest `M` alongside malicious `B`.
6. The tool prints `"Successfully verified source of package"`, giving the reviewer false confidence that the deployed, executable bytecode `B` matches trusted source `S`, when in fact it does not.
