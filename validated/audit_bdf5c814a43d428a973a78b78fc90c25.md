### Title
Unbounded input-token array in `placeOrder` allows permanent escrow lock via out-of-gas withdrawal loop - (File: evm/src/apps/IntentGatewayV2.sol / evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder` only checks that `order.inputs.length != 0`; it never bounds the *upper* size of the input-token array. [1](#0-0) 
Every subsequent settlement path (fill redemption, refund, cross-chain cancellation) redeems escrow by iterating over `body.tokens`, which is populated directly from `order.inputs`, with no chunking or gas-bounded batching: [2](#0-1) [3](#0-2) 

This is a direct structural analog of the Moloch `_ragequit` bug: an attacker-controlled unbounded loop over a whitelist-like set (here, order input tokens) that runs during the fund-release path, where exceeding the block gas limit reverts *every* attempt to unlock the escrowed funds, permanently freezing them.

### Finding Description
`placeOrder` lets the caller supply an arbitrarily long `order.inputs` array (bounded only by what fits in one transaction for escrow deposit), and there is no `MAX_INPUT_TOKENS`-style cap anywhere in the codebase (`grep` for `MAX_TOKENS`/length caps returns none in `IntentGatewayV2.sol`).

The order's `inputs` array is committed into the order hash and is echoed back verbatim in every downstream `WithdrawalRequest.tokens` that is used to release escrow:
- On successful cross-chain fill: destination gateway dispatches a `RedeemEscrow` request whose body embeds `order.inputs`; the source chain's `onAccept` decodes it and calls `withdraw(body, false)` / `_withdraw(body, false, true)`, iterating over every token to `safeTransfer`/`call` it out of escrow. [4](#0-3) 
- On cancellation: `RefundEscrow` triggers the same per-token loop with `isRefund=true`. [5](#0-4) 
- Same-chain path uses `_withdraw` in `IntentsBase.sol`, which also iterates unconditionally over `body.tokens.length`. [2](#0-1) 

Unlike `placeOrder` (where the attacker pays their own escrow-deposit gas and can size the array to just fit), the withdrawal loop is invoked later — inside a relayer- or solver-submitted transaction (`onAccept`/`onGetResponse`, called by the Hyperbridge host as part of handling an incoming cross-chain message) — and does strictly more per-token work than deposit (existence check + external transfer + storage write, plus surrounding proof-verification/dispatch overhead in the same transaction). If the attacker sizes `order.inputs` so that the *withdraw* loop, not the deposit loop, exceeds the destination transaction's available gas (e.g., by using many distinct token addresses, including cheap self-deployed ERC20 contracts, to maximize the number of unique storage slots touched), the withdrawal call will always revert with out-of-gas, regardless of who submits it or how much gas they provide up to the block limit.

Because `_orders[commitment][token]` balances are only ever decremented inside this same unconditionally-executing loop, and there is no partial/incremental withdrawal mechanism for the cross-chain paths (`RedeemEscrow`/`RefundEscrow` are all-or-nothing, single-shot `onAccept` calls), the escrowed input tokens become permanently unretrievable: fill can't complete (destination fill already happened, but the source-side `withdraw` that pays the solver reverts every time) and refund/cancel can't complete either.

### Impact Explanation
This is a real fund-loss/fund-lock vector matching the bounty scope ("stealing or loss of funds"). An unprivileged user who calls the public `placeOrder` entrypoint can construct an order whose `inputs` array is large enough that the mandatory settlement-time loop in `IntentsBase._withdraw` / `IntentGatewayV2.withdraw` cannot fit in a single EVM transaction. The escrowed tokens (which can include real value tokens mixed in among filler tokens, since only `inputs.length == 0` is rejected) are then permanently locked in the gateway contract — no path exists to ever call `withdraw`/`_withdraw` successfully once created, since it always executes the same unbounded loop. No malicious relayer, prover, or admin action is required — the attacker alone, using only `placeOrder`, creates a state that guarantees the loss.

### Likelihood Explanation
Likelihood is moderate-to-high: any user can call `placeOrder` directly, there is no fee-per-token cap or `MAX_INPUT_TOKENS` guard, and the number of distinct token contracts needed to blow an EVM block's gas budget in a loop doing `SLOAD` + external `call`/`safeTransfer` + `SSTORE` per token is on the order of a few hundred — well within reach of a single `placeOrder` transaction that a determined attacker can afford (especially by pre-deploying minimal ERC20 stand-ins). The only friction is the attacker must also fund escrow deposits for each token in `placeOrder`, but this is a bounded, self-paid cost and does not require any privileged actor.

### Recommendation
- Enforce an explicit `MAX_ORDER_INPUTS` (and/or `MAX_ORDER_OUTPUTS`) cap in `placeOrder`, chosen conservatively so the corresponding `withdraw`/`_withdraw` loop — which does strictly more gas-per-token work and runs inside a transaction that also pays proof/dispatch overhead — provably fits within the block gas limit with margin.
- Alternatively/additionally, make settlement idempotent and chunkable: allow `withdraw` to be called repeatedly with a bounded slice of `body.tokens`, tracking per-token completion so a large order can be unwound over multiple transactions instead of requiring one atomic all-or-nothing loop.

### Proof of Concept
1. Attacker deploys N (e.g., 300+) trivial ERC20 tokens (or reuses N distinct existing tokens they hold a nonzero balance of), each with a nominal balance.
2. Attacker calls `placeOrder` with `order.inputs` containing all N tokens (each with a small amount, distinct addresses so the duplicate-token check in `placeOrder` passes), escrowing them into `_orders[commitment][token]`. [6](#0-5) 
3. A solver fills the order on the destination chain (or the attacker himself immediately cancels it), triggering dispatch of `RedeemEscrow`/`RefundEscrow` back to the source-chain gateway.
4. The Hyperbridge host delivers the message and calls `onAccept`, which internally calls `withdraw(body, ...)`/`_withdraw(body, ...)`, looping over all N tokens to transfer them out of escrow. [3](#0-2) 
5. Because N was sized so the loop's gas cost (transfer + storage writes per token) exceeds the block gas limit when combined with the surrounding message-verification overhead, the transaction reverts with out-of-gas on every retry attempt by any relayer.
6. The escrowed tokens in `_orders[commitment][*]` remain forever unspendable — no other function can drain or reset that mapping entry.

    /**
     * @notice Withdraws the escrowed tokens for a request body.
     * @dev This function is marked as internal.
     * @param body The request body containing commitment, tokens, and beneficiary.
     * @param isRefund Whether this is a refund (true) or a successful fill (false).
     */
    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
