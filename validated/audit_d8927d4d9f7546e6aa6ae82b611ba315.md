### Title
Unhandled `TypeError` in `parsePorcelainStatus` on malformed/truncated rename-or-copy status records - (File: `app/src/lib/status-parser.ts`)

### Summary
`parsePorcelainStatus` iterates over NUL-separated tokens from `git status --porcelain -z` and, for rename/copy entries (`kind '2'`), unconditionally consumes an extra token as the old path via `tokens[++i].toString()` without checking that a token actually exists at that index.

### Finding Description
In the loop over tokens, when a field starts with `2` (the `RenamedOrCopiedEntryType`), the code does: [1](#0-0) 
`tokens[++i].toString()` assumes the next array slot is always populated. If the `'2 ...'` record happens to be the last token produced by `splitBuffer`, `tokens[++i]` evaluates to `undefined`, and calling `.toString()` on it throws an uncaught `TypeError`. This mirrors the exact bug class in the report: a deserializer/handler that indexes into attacker-influenceable structured data without a bounds check before dereferencing.

Downstream, `parsedRenamedOrCopiedEntry` does have a guard for `!oldPath` [2](#0-1)  — but that guard is unreachable for this case because the crash happens one line earlier, at the `tokens[++i].toString()` call site itself, before `oldPath` is even passed in.

### Impact Explanation
If reached, this throws an unhandled exception during `git status` parsing, which is invoked on nearly every user action (branch switch, refresh, commit, etc.) via `getStatus` in `app/src/lib/git/status.ts`. This is a crash/DoS on the status pipeline, not code execution, file write, or credential exfiltration.

### Likelihood Explanation
I could not confirm a concrete way for an attacker who merely controls repository content (files, refs, or a malicious remote) to force git itself to emit a `-z`-formatted rename/copy record as the very last NUL-terminated token without its paired old-path field — under normal operation, `git status --porcelain -z` always emits path pairs for rename/copy entries as an atomic unit, so this field pairing is normally guaranteed by git's own output format, not by Desktop. I looked for a truncation path (Desktop is known to cap large stdout, per changelog entry "Cap output from git at string max length - #19724") that might sever a record mid-stream, but I was not able to locate the actual truncation implementation or confirm that it interacts with `parsePorcelainStatus`/`getStatus` in this codebase within the available context. Without demonstrating a concrete attacker-controlled trigger (e.g., a crafted repository, oversized status output, or a git wrapper/proxy response that truncates output), I cannot substantiate that this is externally reachable rather than a purely defensive/theoretical code-quality issue.

### Recommendation
Add an explicit bounds/undefined check before consuming the paired token, e.g.:
```ts
} else if (entryKind === RenamedOrCopiedEntryType) {
  const oldPathToken = tokens[++i]
  if (oldPathToken === undefined) {
    log.debug(`parsePorcelainStatus: missing old path for renamed/copied entry: ${field}`)
    continue
  }
  entries.push(parsedRenamedOrCopiedEntry(field, oldPathToken.toString()))
}
```
This converts a potential unhandled crash into a graceful skip/error, consistent with the pattern already used in `parseChangedEntry`/`parseUnmergedEntry`/`parsedRenamedOrCopiedEntry`.

### Proof of Concept
I was unable to construct or verify a concrete external trigger (crafted repo/remote/proxy input) that causes git to emit a truncated or unpaired `'2 ...'` record as the last token reaching `parsePorcelainStatus`, given available context. A synthetic unit-test-level PoC (not an attacker-reachable one) would be calling `parsePorcelainStatus(Buffer.from('2 R. N... 0 0 0 abc123 abc123 R100 newpath\0'))` — i.e., a buffer whose only content is a rename/copy header with no following old-path token — which throws `TypeError: Cannot read properties of undefined (reading 'toString')` instead of returning gracefully or throwing the existing, more descriptive `Error` used elsewhere in the file.

**Note:** Because I could not confirm attacker-controllable reachability of the exact malformed-token condition (this requires either a corrupted/truncated git stdout stream or a scenario where git itself deviates from its documented `-z` porcelain format), this finding should be treated as **unconfirmed/low-confidence** rather than a verified externally-triggerable vulnerability meeting the report's "Valid Impact" bar. If you need deeper verification (e.g., examining the git-output truncation code referenced in changelog #19724, or `splitBuffer`'s behavior on truncated streams), I'd recommend a full Devin session with file-system access to trace the exact truncation/parsing interaction.
