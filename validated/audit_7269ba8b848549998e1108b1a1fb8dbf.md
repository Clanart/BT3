### Title
Unchecked `u64` additions in Bitcoin fee/funds math allow overflow past the `NotEnoughFunds` check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` computes funds sufficiency and change with unchecked `u64` addition on attacker-influenced amounts (`payment_sat + needed_fee`, `payment_sat + fee_with_change`). This is the same bug class as CVE-2018-25020: arithmetic on sizes/amounts that can overflow when the operands are large, producing a wrapped result that bypasses the guard it was meant to enforce. In release builds (`overflow-checks` off), the additions wrap silently; in debug builds they panic.

### Finding Description
In `SignableTransaction::new`:

- Line 187: `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` — each `payment.1` is only checked to be `>= DUST` (line 165-169); there is no upper bound. Two payments of `u64::MAX / 2 + 1` sum to `>= u64::MAX`, wrapping.
- Line 215: `if input_sat < (payment_sat + needed_fee)` — if `payment_sat` is near `u64::MAX`, `payment_sat + needed_fee` wraps to a small value, so `input_sat < wrapped` is false and `NotEnoughFunds` is never raised.
- Line 228: `input_sat.checked_sub(payment_sat + fee_with_change)` — the `checked_sub` guards the subtraction, but the inner `payment_sat + fee_with_change` still overflows *before* the checked subtraction sees it, wrapping to a tiny value.

The result: `checked_sub` succeeds and `value ≈ input_sat`, so a change `TxOut` worth nearly the entire input sum is appended (line 230) alongside payment outputs whose nominal values exceed `input_sat`. `SignableTransaction::new` returns `Ok`, and `TransactionSignMachine::sign` / `TransactionSignatureMachine::complete` (lines 355-428) proceed to produce threshold Schnorr signatures over the sighashes of this transaction.

### Impact Explanation
The threshold multisig signs a transaction whose declared outputs sum to far more than its inputs. Two concrete harms:

1. **Signing of an economically invalid transaction**: the FROST machine produces valid BIP-340 signatures committing to output values the inputs cannot fund. Depending on how callers interpret `needed_fee`/`fee()`, the reported fee (`fee()` at line 138-141 computes `sum(inputs) - sum(outputs)`, which itself underflows to a huge `u64`) is garbage — a "fee" of ~`u64::MAX` is reported while the real construction is corrupt.
2. **DoS / fund-locking**: the coordinator-signed plan transaction is unbroadcastable (rejected by Bitcoin's `CheckTransaction` since outputs exceed inputs), burning a signing attempt and stalling the affected inputs/plan.

Because payment amounts originate from scheduler/instruction data ultimately driven by externally submitted instructions (untrusted transaction data the multisig is asked to sign), an unprivileged party who can influence payment amounts reaches this path.

### Likelihood Explanation
Requires the ability to place near-`u64::MAX` amounts into the `payments` list passed to `SignableTransaction::new` (i.e., influence over the payment set of a plan being signed). No cryptographic assumptions needed — pure arithmetic. In builds compiled with overflow checks the wrap becomes a panic (crash/DoS); in release builds it silently produces the malformed transaction. Medium likelihood given the requirement to steer payment values, but no malicious-validator or collusion assumptions are required.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`:
- `payment_sat`: `payments.iter().try_fold(0u64, |a, p| a.checked_add(p.1))` and reject on `None`.
- Line 215: `payment_sat.checked_add(needed_fee)` and compare against `input_sat`, erroring `NotEnoughFunds` on overflow.
- Line 228: `payment_sat.checked_add(fee_with_change).and_then(|v| input_sat.checked_sub(v))`.
- Line 139-140 `fee()`: compute via `checked_sub` and treat underflow as an error/invariant violation.

### Proof of Concept
```rust
// release build (overflow-checks = off)
let input = ReceivedOutput { /* output.value = 1_000_000 sats */ .. };
let payments = vec![
    (script.clone(), u64::MAX - 10),   // passes `>= DUST`
];
// payment_sat = u64::MAX - 10
// payment_sat + needed_fee wraps to (needed_fee - 11), tiny
// -> `input_sat < wrapped` is false, NotEnoughFunds skipped
// -> change branch: input_sat.checked_sub(wrapped) ≈ 1_000_000,
//    emits change output ~ input_sat while payment output is u64::MAX - 10
// -> SignableTransaction::new returns Ok; sign() produces a valid FROST
//    signature over a transaction whose outputs vastly exceed its inputs.
let stx = SignableTransaction::new(vec![input], &payments, Some(change_script), None, fee);
assert!(stx.is_ok()); // should have been NotEnoughFunds
```
