### Title
Out-of-bounds read via unclamped length in `RepeatedField#[]` slice accessor exposing adjacent arena memory - ([File: ruby/ext/google/protobuf_c/repeated_field.c])

### Summary
The Ruby extension's `RepeatedField#[beg, len]` accessor (backed by `upb_Array`) did not clamp `len` to the number of elements actually present in the array before reading, allowing a read past the end of the underlying `upb_Array` buffer. This mirrors the SANE CVE-2020-12863 pattern: an out-of-bounds read driven by a caller/attacker-influenced length value that returns adjacent heap/arena bytes to the caller instead of failing safely.

### Finding Description
The regression test [1](#0-0)  documents the bug directly in its comment: `RepeatedField#[beg, len]` with `len > size` "used to read past the end of the underlying `upb_Array` buffer, returning adjacent arena bytes (info disclosure on numeric fields) or crashing the process (string/message fields)." The fix requires that behavior "match Ruby `Array#[beg, len]`: clamp `len` to what is available and never read OOB" [1](#0-0) . The subarray logic lives in `ruby/ext/google/protobuf_c/repeated_field.c`, which contains the "subarray" implementation referenced by this test, but I was unable to load the full function body in this session (the `read_file` call did not complete before the tool budget was exhausted), so I cannot confirm from source here whether the fix (clamping) is actually present in this checkout versus only present in the test expectations.

The invariant that fails in the SANE case — "attacker supplies a length that is used to read data beyond the bounds of an allocated buffer, and the excess bytes (which may contain sensitive adjacent memory, e.g. heap metadata or ASLR-relevant pointers) are returned to the attacker" — transfers cleanly to this Ruby case: a `len` argument larger than the array's actual element count is used to compute a read region into the underlying `upb_Array` storage without first clamping to the populated size, and the result (for numeric field types) is copied directly into a Ruby array returned to the caller, disclosing adjacent arena bytes.

### Impact Explanation
For repeated numeric fields, an out-of-bounds slice read discloses adjacent arena heap contents to the calling code as legitimate-looking values (analogous to disclosing ASLR offsets in the SANE case) — a confidentiality (`C:L`) impact with no integrity/availability impact, consistent with the CVSS vector of the source advisory (`AV:A/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N` conceptually maps to a local, low-complexity confidentiality leak). For string/message-typed repeated fields, the same OOB read instead dereferences invalid pointers taken from beyond the array bounds, which can crash the process — a lower-severity availability concern that is explicitly excluded from scope here as an unbounded/resource issue.

### Likelihood Explanation
Likelihood is **not fully established from this checkout**: the presence of a purpose-written regression test with a detailed comment describing exactly this OOB read strongly suggests the vulnerability existed and a fix was authored, but I could not verify from the `repeated_field.c` source in this session whether:
1. This fix is actually present/active in the code paths reachable from the public `RepeatedField#[]` Ruby API, or
2. The vulnerable code path is reachable via attacker-controlled data only when the *host application* (not protobuf itself) passes an untrusted, attacker-derived `len` value to the accessor after parsing a message — which is consistent with this exercise's "ordinary client sending bounded protobuf, consuming application trusted" threat model only if the length originates from parsed field data (e.g., a length taken from an `int32` field in the message) rather than being hardcoded by the application.

Given the CVE analogy is strong but source verification of the current fix state is incomplete, I flag this with **Medium** confidence rather than asserting confirmed unpatched status.

### Recommendation
1. Confirm in `ruby/ext/google/protobuf_c/repeated_field.c` that the subarray/slice implementation clamps `len` to `upb_Array_Size(array) - beg` (and rejects negative `beg`/`len`) before performing any memory read, matching Ruby's native `Array#[]` semantics, exactly as asserted by the test in `ruby/tests/repeated_field_test.rb`.
2. Apply the same audit to the JRuby (`RubyRepeatedField.java`) and FFI (`ruby/lib/google/protobuf/ffi/repeated_field.rb`) backends, since they implement equivalent subarray/slice semantics against the same underlying `upb_Array` and may not share the C extension's fix.
3. Add sanitizer-based (ASan) regression coverage that programmatically constructs a `RepeatedField` from parsed message data and then probes `[]` with a range of `beg`/`len` combinations exceeding the real element count, to catch any future regression at the C level rather than relying solely on behavioral test assertions.
