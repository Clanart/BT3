### Title
Scanner credits dust outputs that cannot be economically spent, reporting unspendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`Scanner::scan_transaction` registers every output paying to a registered script as a `ReceivedOutput` with no minimum-value check, and `SignableTransaction::new` accepts any `ReceivedOutput` as an input without verifying its value covers the marginal fee cost of spending it. An unprivileged party can send tiny/dust-valued Taproot outputs to a scanned address; these are reported to the protocol as received, spendable funds even though each such input costs more in fee (~57 vbytes × feerate) than it contributes — the analog of the reference bug where vault accounting treats a balance as available while a downstream operation cannot actually be performed with it.

### Finding Description

`scan_transaction` matches only on `output.script_pubkey` and pushes a `ReceivedOutput` for any matched output regardless of `output.value` (networks/bitcoin/src/wallet/mod.rs:199-214). There is no filter against `DUST` (546 sats, defined at send.rs:32) or against the ~57-vbyte marginal weight a Taproot key-spend input adds (documented in processor/src/networks/bitcoin.rs:606-637).

On the spend side, `SignableTransaction::new` computes `input_sat` as the naive sum of all input values and only checks the aggregate `input_sat < payment_sat + needed_fee` (send.rs:175, 215-221). Each included input raises `needed_fee` via `calculate_weight_vbytes` (send.rs:62-127), so a dust input contributes negative net value. If the scheduler selects a set consisting only of dust inputs (e.g., the multisig was drained of large outputs, leaving only attacker-sent dust — mirroring the reference scenario where all shares are withdrawn leaving an unpayable fee), `new` returns `NotEnoughFunds` and no transaction can be constructed, while the scanner continues to report those outputs as received balance.

### Impact Explanation

- Funds reported received that are not spendable: `scan_transaction`/`scan_block` emit `ReceivedOutput`s whose value is below the fee cost of spending them. Balance accounting that consumes the scanner overstates available funds.
- Permanent dust accumulation: an attacker can cheaply grind the wallet's effective balance by sending many sub-cost outputs, forcing either fee loss (inputs whose spend cost exceeds value get subsidized by other inputs in the same tx) or `NotEnoughFunds` failures in `SignableTransaction::new` when only dust remains.
- Unlike a relay-level dust rejection (which only blocks outputs < 546 sats), the unspendable threshold here is feerate-dependent (~57 × fee_per_vbyte sats), so outputs well above consensus dust are still economically unspendable yet credited.

### Likelihood Explanation

Any party that learns a scanned `script_pubkey` (publicly visible on-chain once used, or derivable for the base key) can send outputs of arbitrary value to it with an ordinary Bitcoin transaction — no privilege required. The wallet provides no mechanism to reject or ignore them, and `register_offset`-derived change addresses are equally affected.

### Recommendation

- In `Scanner::scan_transaction` (or a post-processing pass over its results, mirroring the existing coinbase-maturity caveat at mod.rs:216-220), drop outputs below a configurable spendability threshold (at least `DUST`, ideally `57 × current_fee_rate`).
- In `SignableTransaction::new`, reject or skip inputs whose value is below the marginal fee they add (`fee_per_vbyte * 57`), rather than only checking the aggregate.

### Proof of Concept

1. Construct `Scanner::new(group_key)`; note `s = p2tr_script_buf(group_key)`.
2. Send a Bitcoin tx with an output `{ value: 600, script_pubkey: s }` (above the 546 relay dust floor, below spend cost at any feerate ≥ ~11 sat/vb).
3. `scanner.scan_transaction(&tx)` returns a `ReceivedOutput` with `value() == 600` — reported as received funds.
4. Call `SignableTransaction::new(vec![that_output], &payments, None, None, fee)` — either `NotEnoughFunds`, or the input is included while contributing less than its own marginal fee, silently burning other inputs' value.
