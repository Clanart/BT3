### Title
`host_deposit_constant` Passes `deposit_value_bytes` Instead of `move_txid` to `deposit_constant`, Causing Bridge Circuit Proof Verification to Always Fail — (`File: bridge-circuit-host/src/structs.rs`)

---

### Summary

The host-side helper `host_deposit_constant` in `bridge-circuit-host/src/structs.rs` calls the shared `deposit_constant` function with `deposit_value_bytes` (the raw EVM storage value of the deposit storage proof) as the fourth argument. The zkVM guest circuit (`circuits-lib/src/bridge_circuit/mod.rs`) calls the same function with `*move_txid` (the move-to-vault transaction ID extracted from the storage proof). Because the two callers pass semantically different 32-byte values for the same parameter, the `DepositConstant` computed on the host will never match the one committed inside the circuit's journal, causing every bridge-circuit proof verification to fail.

---

**Host-side call** (`bridge-circuit-host/src/structs.rs` lines 505–515):

```rust
let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    deposit_value_bytes,  // ← WRONG: EVM storage slot value, not move_txid
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,

```

`deposit_value_bytes` is the big-endian encoding of the EVM `uint256` value stored in the deposit storage slot (`deposit_storage_proof.value`). `move_txid` is the 32-byte Bitcoin transaction ID of the move-to-vault transaction, returned by `verify_storage_proofs`. These are entirely different 32-byte quantities.

The `DepositConstant` is SHA-256 hashed into the circuit's final `journal_hash` (committed to the zkVM journal). The host recomputes this hash in `SuccinctBridgeCircuitPublicInputs::new` → `host_journal_hash()` and compares it against the receipt journal to validate the proof. Because the host's `deposit_constant` is computed with the wrong input, the two journal hashes will never match. [1](#0-0) [2](#0-1) [3](#0-2) 

---

### Impact Explanation

`prove_bridge_circuit` calls `SuccinctBridgeCircuitPublicInputs::new(bridge_circuit_input)` and then checks the host-computed `journal_hash` against the receipt journal bytes. Because `host_deposit_constant` feeds the wrong value into the hash, this check always fails, and `prove_bridge_circuit` returns an error before the Groth16 proof is returned to the caller. [4](#0-3) 

Downstream consequences:

1. The operator's `send_asserts` path cannot produce a valid bridge-circuit proof.
2. Without a valid proof, the operator cannot post correct Assert transactions.
3. A challenger can then post a Disprove transaction and burn the operator's collateral.
4. Every challenged deposit is permanently unresolvable: the operator loses collateral and the bridge's liveness is broken for those deposits. [5](#0-4) 

---

### Likelihood Explanation

The bug is triggered unconditionally whenever an operator is challenged and attempts to generate a bridge-circuit proof. No special attacker input is required; the mismatch is structural. Any honest operator running the production code path will hit this failure on every challenged withdrawal.

---

### Recommendation

Replace `deposit_value_bytes` with the actual `move_txid` extracted from the deposit storage proof in `host_deposit_constant`. The host must mirror exactly what `verify_storage_proofs` returns inside the guest:

```rust
// Correct host-side call:
Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    move_txid_bytes,   // ← derive from deposit_storage_proof the same way
                       //   verify_storage_proofs does inside the circuit
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
```

Add a unit test that runs `host_deposit_constant` and the guest `deposit_constant` on the same `BridgeCircuitInput` and asserts they produce identical `DepositConstant` values.

---

### Proof of Concept

1. Construct a valid `BridgeCircuitInput` with a real deposit storage proof whose `value` field differs from the move-to-vault txid (which is always the case in production).
2. Call `host_deposit_constant(&input)` → observe `deposit_value_bytes` is used.
3. Call the guest `deposit_constant` path with `*move_txid` from `verify_storage_proofs`.
4. Compare the two `DepositConstant` outputs — they will differ.
5. Feed both into `journal_hash` — the host hash will not match the circuit's committed journal bytes.
6. `prove_bridge_circuit` returns `Err("Journal hash mismatch")` before returning the proof. [6](#0-5) [7](#0-6)

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}
```
