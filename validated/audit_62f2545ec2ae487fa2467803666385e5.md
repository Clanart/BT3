## Title
Malicious commit content in a fetched/cloned repository crashes the app via unhandled `fatalError()` in `parseRawLogWithNumstat` - (File: `app/src/lib/git/log.ts`)

### Summary
`getChangedFiles` in `app/src/lib/git/log.ts` runs `git log --raw --numstat -z` against a commit taken from a cloned/fetched repository and feeds the raw, attacker-influenced stdout into `parseRawLogWithNumstat`, which assumes a rigid line structure and calls `forceUnwrap()` on each parsed field.<cite repo="Annirich/desktop--021" path="app/src/lib/git/log.ts" start="219="244" /> `forceUnwrap` throws via `fatalError()` whenever a field is `null`/`undefined`, i.e. whenever the assumed structure doesn't hold. [1](#0-0)  This is conceptually the same class of bug as the Stellar report: a failure mode of parsing externally-supplied data isn't handled defensively, and instead of returning an error to the caller it throws an unhandled/fatal exception that propagates up and crashes the process (the Desktop equivalent of a "core node" crashing).

### Finding Description
`parseRawLogWithNumstat` walks the `\0`-delimited output of `git log --raw --numstat -z` line by line, splitting each `--raw` line on spaces and asserting a fixed number of columns with `forceUnwrap('Invalid log output (...)', ...)`: [2](#0-1) 

For numstat lines it does the same via a regex match and `forceUnwrap('Invalid numstat line', match)`. [3](#0-2) 

`forceUnwrap` is not a soft validation helper — it calls `fatalError()`, which unconditionally `throw`s a plain `Error`: [4](#0-3) [5](#0-4) 

This function is invoked synchronously from `getChangedFiles`, which just returns whatever `git` produced for a given `sha` with no `try/catch` around the parse call: [6](#0-5) 

Because `-M`/`-C` (rename/copy detection), quoted paths, and edge cases such as merge commits with `-m` can all change the expected line layout that this hand-rolled parser assumes, a repository crafted with adversarial tree/commit content (e.g., filenames or a commit topology that produces an atypical `--raw`/`--numstat` pairing, unexpected ordering, or truncated fields for a given mode/status combination) can make one of the `forceUnwrap` calls receive `undefined`. The same parser is reused by `app/src/lib/git/diff.ts` and `app/src/lib/git/stash.ts`, both of which are reachable purely by viewing history/diffs or refreshing a stash in a repository the user cloned or fetched from an attacker-controlled remote — no local access, admin rights, or social engineering beyond "clone/fetch this repo" is required.

### Impact Explanation
The thrown `Error` is not one of the expected/handled Git errors — it's a plain JS exception from application code running inside the normal `git()` control flow, in a context Desktop does not wrap with the standard `Dispatcher.postError` machinery. If it isn't caught by any intervening `try/catch`, it becomes an uncaught exception. In the main process this is caught by `process.on('uncaughtException', ...)` in `app/src/main-process/main.ts`, which destroys the main window and shows a full crash/relaunch UI via `showUncaughtException`. [7](#0-6)  In the renderer the equivalent handler in `app/src/ui/index.tsx` reports and effectively treats it as fatal. [8](#0-7)  The net effect: viewing a commit's diff/changed-files list in a maliciously crafted cloned/fetched repository can force an application-wide crash and forced relaunch — a remote, unprivileged, repository-content-triggered crash, directly analogous to the Stellar advisory's "core node randomly crashed" scenario, including the same "recovers by restarting" profile.

### Likelihood Explanation
Likelihood is moderate: it requires constructing raw/numstat output that desynchronizes the parser's index bookkeeping (`i`, `++i` skips for rename/copy old-path lines, `numStatCount` used to index into `files[]`). This is plausible given known edge cases in `git --raw --numstat -z` output (e.g., interaction between `-m` for merge commits, `-C`/`-M` copy/rename thresholds, and submodule/mode-change lines), but it has not been dynamically reproduced here — it is a structural/defensive-programming weakness inferred from the code, not a confirmed exploit with a concrete payload.

### Recommendation
Replace the `forceUnwrap`-based fatal assertions in `parseRawLogWithNumstat` with graceful validation that returns a partial/degraded result (or a typed parse error) instead of throwing, and wrap `getChangedFiles`/its callers in `try/catch` so malformed data from an untrusted repository degrades to an error banner instead of an application-wide crash — consistent with how other Desktop git-output parsers (e.g., `createLogParser`, `GitRebaseParser`, `GitProgressParser`) already return `null`/empty results on unexpected input instead of throwing.

### Proof of Concept
Not independently reproduced. A concrete PoC would require crafting a commit (e.g., with a rename/copy plus a mode-change or submodule entry, combined with `-m` merge-commit parsing) whose `--raw --numstat -z` output desynchronizes the fixed-shape parsing loop in `parseRawLogWithNumstat`, causing one of the `forceUnwrap` calls at [9](#0-8)  to receive `undefined` and throw. This should be validated by a Devin session with test-repo/dugite access before treating it as confirmed-exploitable.

export async function getChangedFiles(
  repository: Repository,
  sha: string
): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)
  // this is equivalent to the user configuring 'diff.renames' to 'copies'
  // NOTE: order here matters - doing -M before -C means copies aren't detected
  const args = [
    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}

export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }
