### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` allows a spend-triggered wallet-sync crash / DoS - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs nested `MofN` custody structures from an attacker-controlled CLVM memo `Program` with no depth limit, mirroring the CVE-2026-49941 bug class (unvalidated/unbounded recursive parsing of untrusted input leading to indefinite/excessive recursion and a crash). This function is reachable purely from passive wallet sync: any unprivileged party can submit a spend bundle that creates a coin whose puzzle mimics a PlotNFT singleton and whose `CREATE_COIN` memo encodes a deeply/maliciously nested `MofN` hint, causing the memo parser to recurse until Python's recursion limit is hit.

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses an untrusted `Program` (the memo attached to a `CREATE_COIN` condition) and, whenever the memo signals "further branching" (an `MofN` node), recurses once per member: [1](#0-0) 

There is no cap on nesting depth, no limit on the number of `MofN` members, and no bound on total memo size before recursing. Each recursive call is driven directly by attacker-supplied `Program` structure (`memo.at(...)`, `MofNHint.from_program(...)`), so a spend bundle author fully controls how deep the recursion goes.

This code path is reachable from ordinary, passive wallet sync, not from any privileged or operator-only action:
- `WalletStateManager.determine_coin_type()` calls `PlotNFT2Wallet.identify()` for any observed coin whose puzzle uncurries to the singleton mod, purely because the wallet is watching chain state: [2](#0-1) 
- `PlotNFT2Wallet.identify()` calls `PlotNFT.get_next_from_coin_spend()` for every such coin spend it observes: [3](#0-2) 
- `PlotNFT.get_next_from_coin_spend()` falls through to `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` whenever the created coin's puzzle hash cannot be matched via cheap heuristics, i.e., exactly the case a malicious spend would trigger: [4](#0-3) 

Because a `CREATE_COIN` memo is just quoted/constant data output by the puzzle, an attacker can cheaply produce a serialized program with many levels of `MofN` nesting (encoding nested lists is only a couple of bytes per level) without materially raising CLVM execution cost, then submit that spend bundle to the mempool. When any full node's wallet (or any wallet client syncing coin states, trusted or untrusted) later observes this coin's spend and tries to classify it, `from_memo()`'s recursion explodes proportionally to memo nesting depth.

### Impact Explanation
An attacker-crafted, cheaply-produced spend bundle can drive `PuzzleWithRestrictions.from_memo()` into deep/unbounded recursion purely through wallet sync classification logic that every syncing wallet runs automatically and unconditionally on observed coin states. This can raise a Python `RecursionError` (or in constrained environments a native stack overflow) inside wallet coin-state processing (`WalletStateManager._add_coin_state` / `add_coin_states`), which is a broadly reachable transaction-processing path for any wallet client. This matches the "spend-triggered transaction-processing halt" impact category: a single unprivileged spend can degrade or crash coin-state processing for wallets that later observe it, without requiring any signature, key compromise, or victim interaction beyond normal sync.

### Likelihood Explanation
Likelihood is high for wallets that watch/sync generic chain coin state (any wallet, since `determine_coin_type()` runs for every observed coin uncurrying to the singleton mod, not just wallets that already own a PlotNFT). The attacker needs only to submit an ordinary spend bundle creating a coin with a crafted memo; no privileged access, peer compromise, or leaked keys are required — this is exactly the "single submitted spend bundle" threat model in scope.

### Recommendation
Add an explicit recursion/nesting depth limit (and/or member-count limit) to `PuzzleWithRestrictions.from_memo()` and `MofNHint.from_program()` before recursing, raising a `ValueError` (which callers like `PlotNFT.get_next_from_coin_spend()` already catch) once a safe bound is exceeded. Alternatively, convert the recursive descent into an explicit iterative worklist (as is already done for CLVM tree hashing in `chia/types/blockchain_format/tree_hash.py`) so pathological memo shapes cannot exhaust the Python call stack.

### Proof of Concept
1. Construct a spend whose puzzle uncurries as a `SINGLETON_TOP_LAYER_MOD` puzzle (matching `PlotNFT.singleton_puzzles.singleton_mod`) so `WalletStateManager.determine_coin_type()` routes it to `PlotNFT2Wallet.identify()`.
2. Have that spend's solution produce exactly one `CREATE_COIN` condition whose `memo_blob` is `(spec_namespace, [nonce, [], 1, (M, [nested_memo, nested_memo, ...])])`, where `nested_memo` is itself recursively built the same way to a depth of tens of thousands of levels (cheap in bytes since it's constant/quoted data).
3. Broadcast the spend bundle; it does not need to be a genuine PlotNFT — it only needs to pass the cheap early checks in `get_next_from_coin_spend()` (singleton mod/launcher hash match, exactly one `CREATE_COIN`) before falling through to `PuzzleWithRestrictions.from_memo(memo_blob.rest())`.
4. Any wallet (attacker's own test node, or later any full node/light wallet that syncs this coin state) calls `from_memo()` on the crafted memo, causing recursion depth to scale with attacker-chosen nesting and raising `RecursionError` inside `_add_coin_state`, disrupting that wallet's coin-state processing for the batch containing this coin.

    @classmethod
    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
            puzzle=puzzle,
            additional_memos=additional_memos,
        )
