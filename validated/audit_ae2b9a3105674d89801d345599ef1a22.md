Confirmed: `CallDispatcher.dispatch()` has **no access control** — it's a fully public, unrestricted `external` function that any address can call directly, at any time, independent of the ISMP flow. This is the concrete local analog to the external report's "unvalidated external payload" bug class, and it produces a real fund-theft primitive rather than just a DoS/gas issue.

### Title
Unrestricted public `CallDispatcher.dispatch()` allows theft of tokens/ETH left in the shared dispatcher by cross-chain calldata-execution messages - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`HyperFungibleToken.onAccept()`, `WrappedHyperFungibleToken.onAccept()`, and their upgradeable variants mint/unlock bridged tokens to a `beneficiary` address (which callers are told to set to the `CallDispatcher` address when the payload needs to spend the bridged funds) and then forward attacker/sender-controlled `message.data` to `ICallDispatcher(_dispatcher).dispatch(message.data)` for arbitrary execution. `CallDispatcher.dispatch()` itself has no caller restriction, so this "temporary custody" contract is a shared, permissionless executor that any unrelated address can invoke.

### Finding Description
`HyperFungibleToken.onAccept` decodes a fully attacker-controlled ISMP message body and, when `message.data.length > 0`, mints tokens to `beneficiary` and immediately calls the dispatcher: [1](#0-0) 

The dispatcher itself performs no access control on who may call `dispatch()`: [2](#0-1) 

The documented usage pattern instructs integrators to bridge tokens directly `to` the `CallDispatcher` address so that the subsequent `Call[]` (e.g., `approve` + `swap`) can spend them: [3](#0-2) 

Because `dispatch()` is a public entrypoint with no `onlyHost`/`onlyModule`/reentrancy guard and no restriction tying a call to a specific ISMP message, the dispatcher is a **shared, stateful custodian** across every HFT/WrappedHFT deployment and every sender that uses the "bridge-then-execute" pattern. Any of the following windows create fund-loss opportunities that existing guards do not stop:

1. **Cross-call residual balance theft.** If a `Call[]` sequence in one message leaves any token/ETH balance in the dispatcher (e.g., an approve amount larger than what the swap consumes, a swap that reverts a downstream step in a *future* transaction with fixed slippage but partial fills, or a call ordering bug), that balance sits in a public shared contract. Any unprivileged actor can then call `CallDispatcher.dispatch()` directly (bypassing the Host/ISMP module entirely — `dispatch()` doesn't check `msg.sender == host`) with a `Call[]` that transfers out the dispatcher's ERC-20 balance or ETH balance to themselves. There's no "belongs to this bridge message" scoping — the funds are fungible dispatcher-owned assets the moment they land there.
2. **No atomicity between mint-to-dispatcher and the intended spend.** The mint happens inside `onAccept`, and the same transaction also runs the attacker-controlled `Call[]`, but because `dispatch()` is public and unguarded, a malicious relayer/user could front-run or interleave a directly-submitted `dispatch()` call (via a separate transaction in the same block, or exploiting mempool ordering) targeting dust/leftover balances from *any other* HFT deployment that shares the same `CallDispatcher` instance (the docs confirm one canonical `CallDispatcher` is reused across mainnet/testnet deployments, see `contract-addresses` docs), draining balances that were only transiently supposed to belong to a specific bridging user.
3. **The `Call[]` payload is never validated for target/allowance safety** — the recipients of "temporary custody" (the dispatcher) rely entirely on integrators using "exact amounts rather than unlimited allowances" per the docs' own security caveat, which is an unenforced convention, not a code-level guard. This exactly matches the external report's core theme: unvalidated externally-supplied payloads executed on the destination chain with no protocol-level restriction on what they can do or who can trigger dispatcher execution.

### Impact Explanation
Funds (bridged ERC-20 tokens or native ETH) intended for the `to`/`beneficiary` address of an intent settlement (bridge-and-swap) can end up permanently or transiently owned by the shared, permissionless `CallDispatcher` contract. Because `dispatch()` has no access control, any third party can seize that balance by submitting their own `Call[]` before the legitimate downstream consumer (or the original bridging transaction's own multi-call sequence) claims it. This is a direct loss/theft of bridged funds routed through a bridge-provided execution primitive — matching the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories.

### Likelihood Explanation
Exploitability requires no privileged role, malicious relayer, or governance actor — only an ordinary EOA calling the public `dispatch()` function once any balance is observably sitting in the `CallDispatcher` (e.g., after an approve-then-swap sequence with any slippage/rounding, or simply during the brief window between minting tokens `to` the dispatcher and the dispatcher successfully executing every `Call[]` step in the same top-level tx before a later related but distinct ISMP message also targets the dispatcher). Since the same dispatcher address is reused across all HFT/WrappedHFT deployments per the published contract-addresses list, it is a persistent shared target, not a one-off race.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to be callable only by the specific `IApp` contract that received the corresponding ISMP message (e.g., `onlyHost`-style check or a caller allow-list), or make the dispatcher a single-use, per-message clone/proxy so no cross-message balance can accumulate.
- Sweep any residual token/ETH balance back to the intended beneficiary (or revert) at the end of `dispatch()` instead of leaving dust in a shared, permissionless contract.
- Add reentrancy/ordering guards so `dispatch()` cannot be invoked out-of-band from the `onAccept` flow that funded it.

### Proof of Concept
1. Alice bridges 100 USDC cross-chain with `to = CALL_DISPATCHER`, `data = [approve(router, 100 USDC), swapExactTokensForTokens(100 USDC → min 99 WETH-equivalent, recipient = Alice)]`.
2. Due to slippage/rounding, the swap only consumes 99.5 USDC of the 100 USDC approved allowance, or the approve step approves a fixed round amount leaving a small remainder unspent inside `CallDispatcher`.
3. Because `CallDispatcher.dispatch()` has no access control, Mallory (any address) immediately calls `CallDispatcher.dispatch(encodedCalls)` with `calls = [ {to: USDC, data: transferFrom(dispatcher-held-balance...)} ]` or simply `IERC20(USDC).transfer` if the dispatcher itself holds a stray balance from a prior message — since the dispatcher's balance is fungible and not tied to any specific sender, Mallory drains any leftover balance belonging to Alice's (or any other user's) cross-chain settlement.
4. No proof, relayer collusion, or privileged role is required — only calling the public `dispatch()` entrypoint directly.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```
