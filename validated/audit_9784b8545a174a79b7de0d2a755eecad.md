### Title
Reward-pool sandwiching via instant, uncapped `_provisionReward` and lock-free deposit/withdraw in `BaseRewardPool` / `MasterMagpie` - (File: `rewards/BaseRewardPool.sol`, `rewards/MasterMagpie.sol`, `wombat/WombatStaking.sol`)

### Summary
The external report describes sandwiching a discrete, instantaneous price/value update (rETH price submission) by depositing right before the update and withdrawing right after to capture value that should have accrued to long-term holders. The same pattern applies to this codebase's reward accounting: reward tokens harvested from Wombat (or donated) are applied to `rewardPerTokenStored` in one atomic, un-streamed step, and staking positions in `MasterMagpie`/pool helpers can be entered and exited with no cooldown or vesting. This lets an attacker front-run a harvest/reward-injection transaction with a large deposit, claim a full pro-rata share of the newly injected rewards, and withdraw immediately afterward, diluting the yield that should belong to existing long-term stakers.

### Finding Description
`BaseRewardPool._provisionReward` (and the equivalent in `BaseRewardPoolV2`) updates `rewardPerTokenStored` for the *entire currently staked supply* the instant new rewards arrive: [1](#0-0) 

This is invoked either by `queueNewRewards` (called during Wombat harvest, see `WombatStaking._sendRewards`) or by the permissionless `donateRewards`: [2](#0-1) 

Reward computation is a simple point-in-time snapshot (`rewardPerToken(_rewardToken) - userRewardPerTokenPaid`) multiplied by the caller's current balance — there is no time-weighting, streaming, or minimum holding period: [3](#0-2) 

Meanwhile, `MasterMagpie._deposit`/`_withdraw` (and the pool-helper wrappers such as `WombatPoolHelper.deposit`/`withdraw`) allow instant, uncapped stake and unstake in the same block with no lock-up, unlike the vesting/cooldown slots used for `VLMGP`/`mWomSV`: [4](#0-3) [5](#0-4) 

Harvest of Wombat rewards into the reward pool is itself externally triggerable (`WombatPoolHelper.harvest()` → `IWombatStaking.harvest(lpToken)`), making the "price/value update" event publicly observable and predictable in the mempool, exactly like the `submitPrices` transaction in the original report: [6](#0-5) 

An attacker can therefore:
1. Observe a pending `harvest()`/`donateRewards()` transaction (or trigger `harvest()` themselves) in the mempool.
2. Front-run it with a large `deposit()` into the corresponding pool via the pool helper (no cooldown, no minimum stake duration).
3. Let the harvest/reward-provision transaction execute, which instantly inflates `rewardPerTokenStored` for all current stakers, including the attacker's freshly deposited (undeserved) balance.
4. Call `getReward` (via `MasterMagpie.multiclaim`) to collect a full pro-rata share of the newly injected rewards.
5. Immediately `withdraw()` the principal, with no exit penalty or lock.

This extracts yield that should have accrued only to stakers who were staked during the period the rewards were earned, directly diluting/stealing from genuine long-term LPs.

### Impact Explanation
This is a direct theft of unclaimed yield from legitimate long-term stakers in the `WombatStaking`/`BaseRewardPool` reward system. Every harvest cycle is subject to this extraction, and because `donateRewards` is fully permissionless, the attack can be self-triggered without waiting for organic harvests, making the drain continuous and repeatable. Given that harvest amounts scale with protocol TVL, the stolen value scales similarly, and it can be automated as a bot strategy with essentially the same profile as the rETH sandwich (single-block acquire-then-release position with no market risk).

### Likelihood Explanation
Likelihood is high: deposit/withdraw in `MasterMagpie` and the pool helpers are unrestricted, uncapped, and have no cooldown (unlike `VLMGP`/`mWomSV` unlock slots), `harvest()` is externally callable and its resulting reward transaction is visible pre-confirmation in the mempool, and `donateRewards` gives an attacker a way to force the value-increasing event on demand rather than waiting to observe one. No privileged role is required at any step.

### Recommendation
Introduce a reward-streaming mechanism (e.g., linear vesting of newly queued rewards over a fixed duration, as in Synthetix-style `StakingRewards`) instead of applying `_amountReward` to `rewardPerTokenStored` atomically, and/or enforce a minimum holding period (analogous to the rETH fix's ~1 day deposit delay) between deposit and reward claim/withdrawal in `MasterMagpie` for pools with active reward flows.

### Proof of Concept
1. Attacker monitors mempool for a `WombatStaking.harvest()` call (or calls it directly) that will route WOM rewards to a pool's `BaseRewardPool` via `queueNewRewards`, or attacker simply calls `BaseRewardPool.donateRewards()` themselves after step 2.
2. Attacker calls `WombatPoolHelper.deposit()` with a large amount just prior, which calls `MasterMagpie.depositFor` — no lock, instant stake: [7](#0-6) 
3. Harvest/reward-provisioning transaction executes, instantly bumping `rewardPerTokenStored` for the full `totalStaked()` including the attacker's fresh deposit: [8](#0-7) 
4. Attacker calls `MasterMagpie.multiclaim`/`multiclaimFor` to harvest their pro-rata share of the newly injected rewards.
5. Attacker calls `WombatPoolHelper.withdraw()` to exit the position immediately, with no penalty: [9](#0-8) 

The net effect: the attacker earns yield proportional to a stake held for a single block, diluting rewards owed to genuine stakers who held their position throughout the reward-accrual period.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
}
