### Title
Trampoline credential helper trusts an attacker-controlled `WWW-Authenticate` header to classify an arbitrary remote host as GitHub, driving credential lookups toward stored account tokens - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`PolicyBook`'s bug was that the contract delegated broad, hard-to-audit trust to external actors (blanket DAI allowance) instead of mediating every transfer itself, so the invariant "only the contract decides where its balance goes" was broken. The closest analog in this codebase is in the Git credential-helper trampoline: the classification of *which* class of secret Desktop is allowed to hand back for a given remote URL (`github.com` / GHE-`enterprise` / `generic`) is decided using data supplied by the remote server itself (the `wwwauth[]` credential fields, which come verbatim from a `WWW-Authenticate` response header returned by whatever host/proxy Git is talking to), rather than being derived solely from data Desktop itself controls (the account's own endpoint). This hands part of the "who gets which token" decision to an attacker-controlled input instead of keeping it fully internal to Desktop, which is exactly the broken-invariant pattern described in the report (control delegated externally instead of mediated internally).

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` (lines 137-179) decides whether a credential request is for `'github.com'`, `'ghe.com'`, `'enterprise'`, or `'generic'`. After the safe, Desktop-controlled hostname checks (`isDotCom`, `isGHE`), it falls back to trusting server-supplied authentication metadata: [1](#0-0) 

The comment itself states the intent: "When Git attempts to authenticate with a host it captures any `WWW-Authenticate` headers and forwards them to the credential helper." That header value is fully controlled by whatever server (or proxy sitting in front of it - explicitly a valid attacker-controlled surface per the report scope) answers the unauthenticated HTTPS request Git makes when cloning/fetching/pushing. If an attacker-controlled remote or MITM-capable proxy returns `WWW-Authenticate: Basic realm="GitHub"`, `getEndpointKind` returns `'enterprise'` for a host that is not `github.com`/`*.ghe.com` and not associated with any account.

This classification then feeds `getCredential` (lines 93-135), which is invoked for every `git credential get` call issued by the trampoline (wired globally for the whole process tree via `GIT_CONFIG_PARAMETERS` in `withTrampolineEnv`): [2](#0-1) 

Once `endpointKind !== 'generic'`, the code takes the GitHub-specific branch instead of the plain generic-credential branch, and if the attacker's URL happens to resolve to an `apiEndpoint` matching an account Desktop already trusts, `credWithAccount` will hand back that account's real login/token straight into the credential response given to Git for the attacker's host: [3](#0-2) 

The broken invariant is: *which stored account token is eligible for a given remote should be determined only by data Desktop itself has verified (the account's configured endpoint origin)*, but here the "GitHub-ness" gate that decides whether that lookup path is even taken is influenced by header content originating from the remote/proxy being talked to.

### Impact Explanation
If exploitable to the point of an exact `apiEndpoint` collision (e.g., via a compromised/attacker-run proxy configured for the user, or a malicious mirror whose URL happens to match a previously trusted enterprise endpoint string), this results in Desktop's stored GitHub personal token/OAuth token for that endpoint being sent as Basic-auth credentials to a host the attacker controls - i.e., unauthorized token exfiltration during an otherwise ordinary `clone`/`fetch`/`push` against an attacker-supplied remote, matching the report's "credential/token exfiltration" impact class.

### Likelihood Explanation
This is a narrower, harder-to-exploit analog than the original DAI-allowance bug: the fallback in `getEndpointKind` only changes behavior when `wwwauth[]` matches `realm="GitHub"` for a *non*-dotcom/non-ghe host, and the actual leak only materializes if `getAPIEndpoint(endpoint)` string-matches an existing account's stored endpoint - which normally requires the attacker's URL to be identical to (or normalize to) a host the user already trusts (e.g., via a malicious proxy interposed in front of the real enterprise endpoint, which the report's valid-impact list explicitly allows as an attacker primitive: "a git remote/proxy response"). Absent that endpoint collision, the same header spoof only reaches the `promptForGitHubSignIn` phishing-dialog branch, which requires the user to actively enter credentials and is out of scope per the report's exclusions. I could not fully verify, within the available exploration budget, whether `getAPIEndpoint`/`getEnterpriseAPIURL` normalization has any additional bug that would make such a collision easier to engineer (e.g., trailing slash, casing, or scheme normalization mismatches) - this remains unverified and would need direct inspection of `app/src/lib/api.ts`'s endpoint-URL builders.

### Recommendation
Do not let server-supplied `WWW-Authenticate` realm strings promote a host's classification to `'enterprise'`/`'github.com'` on their own; only use Desktop-owned data (account endpoints resolved via `findGitHubTrampolineAccount`, or an explicit, previously-verified enterprise host list) to decide eligibility for handing back a stored token, and never treat a `wwwauth[]` value as sufficient by itself to select which account's credentials may be considered for a URL that doesn't already match a trusted account's origin.

### Proof of Concept
1. User has an existing GitHub Enterprise account configured in Desktop for `https://github.company.com`.
2. Attacker sets up (or MITMs via a configured proxy) a host reachable at a URL that Desktop's `getAPIEndpoint` normalizes to the same string as the trusted enterprise account's endpoint (unverified whether such a normalization collision is achievable without further inspection of `api.ts`).
3. User adds/clones this attacker-controlled remote in Desktop and performs a fetch/push; Git issues an unauthenticated HTTPS request, and the attacker's server responds with `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this header to the trampoline credential helper as a `wwwauth[]` field; `getEndpointKind` classifies the host as `'enterprise'`; `getCredential` matches the spoofed `apiEndpoint` against the existing account and returns that account's real token to Git, which sends it to the attacker's server as Basic-auth credentials.

Because step 2's exact collision condition was not independently confirmed in the code available to me, this should be treated as a plausible but not fully proven exploit chain, and a Devin session with full repository access (including `app/src/lib/api.ts`'s `getAPIEndpoint`/`getEnterpriseAPIURL` implementations) would be needed to confirm or rule out the normalization collision.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
