## Title
Copilot conflict resolution can silently splice mismatched hunk content into unrelated conflict blocks when the reassembled file content diverges from the working-tree file used to build the prompt - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` matches AI-provided per-hunk resolutions to conflict-marker blocks **by ordinal position only**, not by content or line number, and then the store applies the reassembled text to disk unconditionally once it decides the file is still "conflicted."

### Finding Description
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` walks a conflicted file and produces a `hunks` array in file order, which is the content sent to the model. [1](#0-0)  Later, `reassembleResolvedFile` walks the same on-disk `rawContent` again and, for the `n`‑th `<<<<<<<`…`>>>>>>>` block it encounters, blindly substitutes `hunkResolutions[n]` — matched purely by index, never by comparing the hunk's `oursContent`/`theirsContent` against what was actually sent to the model. [2](#0-1) 

`validateResolutionPaths` only checks that the returned hunk **count** per path equals the count originally extracted; it does not verify that the *content* of each hunk still matches what was sent (a resilience check against the underlying file changing between context capture and resolution apply). [3](#0-2) 

The actual write-to-disk path, `_applyCopilotConflictResolutions`, only re-checks whether the file is still reported as "conflicted" by git status (to avoid clobbering a resolution the user made manually in an editor) — it does not re-extract/re-diff the current hunks against the ones the model resolved before writing `resolution.resolvedContent` to the file and staging it. [4](#0-3) 

Because the attacker controls one side of the merge/rebase/cherry-pick (a remote branch, PR, or fetched ref the user merges/rebases against), they can craft conflicting hunks so that, combined with normal user activity (e.g. resolving another conflicting hunk in the same file manually while the Copilot dialog is open, or a subsequent fetch/rebase step reordering hunks in the file between context-capture and apply), the ordinal-only splice pairs an AI resolution meant for hunk *k* with the on-disk marker block at position *k*, even though the underlying conflict at that position has since changed. The system does not verify hunk *content* identity before splicing — only hunk *count*.

This is structurally analogous to the ERC4626 bug: the code uses one value (`hunkIndex`/position) to select what gets substituted while the actual authoritative accounting anchor should be hunk *content* — a mismatch between the "index" used and the "identity" that should be used, leading to silently wrong data being written where the user believes it corresponds to the reviewed AI suggestion.

### Impact Explanation
If exploited, this results in **silent corruption of what the user commits** — the core sensitive-value class this scan targets. A resolved-conflict file can end up containing code that was never reviewed/approved for that specific conflict region (e.g., an attacker's payload spliced into a block the user believed was resolved differently), and the corrupted content is staged with `git add` and then committed as part of the merge/rebase, without any additional prompt. [5](#0-4) 

### Likelihood Explanation
Exploitation requires: (1) the user runs Desktop's Copilot conflict-resolution feature in a merge/rebase/cherry-pick where the attacker controls one side, and (2) the on-disk hunk sequence used during context capture (`buildConflictContext`) and the sequence walked during reassembly diverge, e.g. via a manual edit in the results dialog window (the code explicitly acknowledges "the user resolved this file externally... while the result dialog was open"). [6](#0-5)  That comment shows the developers anticipated *file-level* drift but only guarded against the "no longer conflicted" case, not against reordering/count-preserving content drift within a still-conflicted file. This narrows likelihood to a specific timing window and is not a trivial one-click exploit, so I rate it as a plausible but non-trivial condition-dependent path rather than a guaranteed-repro bug.

### Recommendation
- In `reassembleResolvedFile`/`validateResolutionPaths`, bind each AI-returned hunk resolution to its source hunk by content hash (of `oursContent`/`theirsContent`/`baseContent`) captured at context-build time, not by positional index alone.
- Before writing in `_applyCopilotConflictResolutions`, re-extract conflict hunks from the current on-disk file and confirm they exactly match (count and content) the hunks that were sent to the model; abort/re-prompt if they differ instead of splicing positionally.

### Proof of Concept
Conceptual (I could not execute this against a live Desktop build; based on static code review of the cited functions):
1. Attacker pushes a branch that produces a multi-hunk conflict when merged (hunks A, B, C in that file order).
2. User starts "Resolve with Copilot"; `buildConflictContext`/`extractConflictHunks` captures hunks [A, B, C] and sends them to the model, which returns resolutions [rA, rB, rC]. [7](#0-6) 
3. While the result dialog is open (before "Continue Merge" is clicked), the user manually resolves hunk B in an editor, removing that marker block but leaving A and C still conflicted (git still reports the file as conflicted overall because A/C remain).
4. On "Continue Merge", `_applyCopilotConflictResolutions` sees the file is still `isConflictedFileStatus` with `hasUnresolvedConflicts`, so it proceeds to call `reassembleResolvedFile(currentRawContent, [rA, rB, rC])`. [8](#0-7) 
5. Because only two marker blocks (A, C) now exist on disk but three resolutions exist, `reassembleResolvedFile` pairs the first on-disk block with `rA` (still correct) but pairs the **second** on-disk block (which is actually C) with `rB` (meant for the now-removed B) — silently writing the wrong resolution into the C conflict region and discarding `rC` entirely, all without any warning to the user. [9](#0-8) 
6. The mis-spliced content is then staged and committed as part of the merge.

  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
