### Title
OP_RETURN `data` output is excluded from weight/vbyte/fee and size checks, so data-carrying transactions are undercharged and can exceed the standard weight limit - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to `executeProposal()` failing to forward `msg.value`, `SignableTransaction::new` creates an extra transaction output (the OP_RETURN `data` output) after the transaction's weight, virtual size, and required fee have already been computed, and never re-runs those calculations with it. The `data` payload — a caller-supplied value that must be "carried" by the transaction — is not accounted for by `calculate_weight_vbytes`, `needed_fee`, or the `MAX_STANDARD_TX_WEIGHT` check.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`), the outputs are assembled in `tx_outs`, and if `data` is `Some`, an additional `TxOut` with `script_pubkey: ScriptBuf::new_op_return(...)` is pushed at lines 194-202. However:

- Line 204: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` — the size estimation is built solely from `tx_ins` and `payments` (and later `change`), with no parameter for the data output. `calculate_weight_vbytes` (lines 62-127) only constructs outputs from `payments` plus an optional `change`.
- `needed_fee = fee_per_vbyte * vbytes` (line 206) therefore prices a transaction that does not include the OP_RETURN output (up to ~80 bytes of payload plus output overhead).
- The change check at lines 224-235 recomputes with `Some(&change)` — but still without the data output — so `fee_with_change` is also understated.
- The standardness bound `weight > MAX_STANDARD_TX_WEIGHT` (line 241) uses `weight` that never includes the data output, so a transaction whose real weight exceeds the limit passes the `TooLargeTransaction` check.
- The `NotEnoughFunds` check (line 215) only ensures `input_sat >= payment_sat + needed_fee`; since `needed_fee` is understated, a transaction can be constructed whose true required fee exceeds the inputs' margin, even though callers rely on `needed_fee()`/`fee()` (lines 133-141) to decide funding.

This is the exact structural analog: a caller-supplied value (`data`) is accepted into the produced artifact but never forwarded into the computation that determines whether the transaction is payable/valid — just as `msg.value` is received at the call site but unusable because `executeProposal` isn't payable.

### Impact Explanation
- The fee actually paid (`inputs - outputs`, see `fee()`) can be below the fee rate the caller specified, because `needed_fee` excluded the OP_RETURN output's vbytes. For an 80-byte payload plus output overhead (~11 vbytes serialized, ~ up to ~130 wu of weight), the shortfall is small in absolute terms, but the transaction may fall below the minimum relay fee rate in the regime where `needed_fee` was only marginally above it — the `TooLowFee` guard at line 211 validates the *understated* size, not the real one.
- More concretely, a transaction with a maximal `data` payload and many payments/inputs can exceed `MAX_STANDARD_TX_WEIGHT` (400,000 wu) in reality while `weight` (computed without the OP_RETURN output) stays under the bound. Such a transaction is produced by `SignableTransaction`/`TransactionMachine`, will be fully signed by the FROST machines, and then be rejected as non-standard by relaying nodes — the signed Bitcoin transaction spends outputs that cannot actually be relayed, i.e., funds that appear spendable are not.
- Reachability: `data` is a public caller input to `SignableTransaction::new`, and the same `data`/`Payment` plumbing is used by the processor's Bitcoin transaction builder.

### Likelihood Explanation
Any caller constructing a `SignableTransaction` with `data: Some(_)` hits the miscalculation deterministically; no adversarial participant is needed. The undersized-fee effect occurs on every data-carrying transaction; the non-standard-weight outcome additionally requires a transaction near the weight bound, which is realistic since transactions can aggregate many inputs/outputs.

### Recommendation
Include the OP_RETURN output in `calculate_weight_vbytes` — pass the constructed `tx_outs` (or an explicit `data` length parameter) into the size estimation so `weight`, `vbytes`, `needed_fee`, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction actually produced. Equivalently, compute weight/vbytes once over the final `tx_outs` (payments + data + change) rather than over a synthetic reconstruction that omits the data output.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Line 194-202: a data output is appended to tx_outs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data).expect("data didn't fit"),
    ),
  })
}
// Line 204: weight/vbytes computed only from tx_ins.len() and `payments`
// (and later `change` at line 226) -- the OP_RETURN output is never included
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;        // understated
// Line 241: standardness check uses the data-less `weight`
if weight > u64::from(bitcoin::policy::MAX_STANDARD_TX_WEIGHT) { ... }
```
`calculate_weight_vbytes` (lines 62-127) builds its dummy transaction's `output` vector exclusively from `payments` plus an optional `change`; it has no way to account for the data output, so every quantity derived from it (`vbytes` → `needed_fee`, `fee_with_change`, `weight` vs. `MAX_STANDARD_TX_WEIGHT`) reflects a transaction smaller than the one stored in `SignableTransaction.tx` and ultimately signed by `TransactionSignMachine::sign` (lines 373-397).
