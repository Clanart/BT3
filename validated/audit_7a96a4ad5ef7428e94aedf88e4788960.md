### Title
Memory exhaustion via per-input duplication of the full participant preprocess map - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the CKB dep-group bug (attacker-supplied references each resolved into separately-allocated objects with no deduplication), `TransactionSignMachine::sign` in `networks/bitcoin/src/wallet/send.rs` rebuilds the entire `HashMap<Participant, Preprocess>` once per transaction input. Because every input of a spend references the same set of participant preprocesses, the same t preprocesses are cloned `inputs` times, giving O(inputs × t) live heap allocations for a single signature operation. The number of inputs is attacker-influenced: an unprivileged party can dust the Serai multisig's Bitcoin address with many small outputs, which the wallet later includes as `ReceivedOutput` inputs. `TransactionSignatureMachine::complete` additionally performs `shares.remove(0)` per input, giving O(inputs²) copying on top of the O(inputs × t) map rebuild.

### Finding Description
`SignableTransaction::new` accepts an arbitrary-length `Vec<ReceivedOutput>` and creates one FROST `AlgorithmMachine` per input (`multisig`, lines 273–285). When signing, `TransactionSignMachine::sign` executes:

```rust
// networks/bitcoin/src/wallet/send.rs:364-371
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone()))
      .collect::<HashMap<_, _>>()
  })
  .collect::<Vec<_>>();
```

This materializes `sigs.len()` (i.e. input-count) separate `HashMap<Participant, Preprocess<Secp256k1, ()>>` structures, each containing a full clone of every participant's preprocess. This matches the CKB pattern: N references (inputs) each cause the resolution/copying of the same t-entry data set, with no deduplication or sharing — the amplification happens at resolve time, before any signature math.

Completion repeats the pattern: for each input, `complete` builds a fresh `HashMap` and calls `shares.remove(0)` on each participant's share vector (lines 417–419), an O(n) shift per element, yielding O(inputs²) byte movement plus another O(inputs × t) map allocation.

The preprocesses themselves are parsed from each participant's serialized preprocess message by `read_preprocess` (lines 351–353), so the data being multiplied is exactly the untrusted per-participant bytes a signing round carries.

### Impact Explanation
An attacker who sends K outputs to the multisig's Taproot address causes every honest processor to allocate `K × t` preprocess objects in memory simultaneously during the next spend attempt, and to do O(K²) work plus O(K × t) map construction when completing. With t on the order of the validator count (up to ~150) and each `Preprocess` plus `HashMap` entry costing on the order of hundreds of bytes, even a modest K (tens of thousands of dust outputs, each costing the attacker only dust-level value) multiplies into multiple GB of RAM and substantial CPU, exhausting the validator process — the same "small input → large resident memory" shape as GHSA-j35p-q24r-5367, where ~26 KB of attacker data yielded ~19 GB amplification per repeated transaction. This is reachable purely through Bitcoin transactions the attacker sends; no validator status, collusion, or leaked key is required.

### Likelihood Explanation
- Reachability: outputs received by the multisig address become `ReceivedOutput`s and are candidate inputs to `SignableTransaction::new`; nothing in `new` bounds the input count or deduplicates outpoints (the only size check is `MAX_STANDARD_TX_WEIGHT` at line 241, which permits tens of thousands of inputs in a single standard-weight transaction and does not prevent repeated sign attempts across attempts/payments).
- The amplification occurs inside `sign` before signature verification, so invalid or uneconomical inputs still cost the memory.
- Cost to attacker is bounded only by the dust/output cost on Bitcoin — cheap relative to the O(K·t) memory inflicted on every validator simultaneously.
- Additionally, duplicate `previous_output`s are not deduplicated at input ingestion (lines 175–185), so the same outpoint can be counted multiple times, worsening the multiplier where upstream code doesn't filter.

### Recommendation
- Avoid materializing `sigs.len()` full `HashMap` clones: share the preprocess table (e.g., `Rc`/reference-indexed views) or restructure `SignMachine::sign` to accept `&HashMap` borrows so the per-input maps are views, not copies.
- Deduplicate `previous_output`s when constructing `tx_ins`/`prevouts` in `SignableTransaction::new` (reject duplicate outpoints outright).
- In `complete`, replace `shares.remove(0)` with an iterator/`VecDeque` drain to eliminate the O(inputs²) shift.
- Impose an explicit upper bound on input count before allocation, independent of transaction weight.

### Proof of Concept
Conceptual reproduction (no code execution performed — read-only analysis):

1. Attacker creates K small-value outputs paying to the Serai multisig's `p2tr_script_buf(group_key)` address via ordinary Bitcoin transactions (public input surface).
2. Processor scanner registers them as `ReceivedOutput`s; on the next spend, `SignableTransaction::new(inputs: Vec<ReceivedOutput>, …)` is invoked with all K outputs, creating K `AlgorithmMachine`s (`multisig`, lines 273–285).
3. Each participant publishes `Vec<Preprocess>` of length K (`read_preprocess`, lines 351–353). On `sign`, the code at lines 364–371 constructs K `HashMap`s each cloning all t preprocesses:

   Memory ≈ K × t × (sizeof(Preprocess) + HashMap overhead)

   For K = 50,000 inputs and t = 150: ≈ 50,000 × 150 × ~200 B ≈ 1.5 GB resident for a single `sign` call, replicated on every validator in the set, before any share verification.
4. `complete` then performs K HashMap constructions and `K × t` `Vec::remove(0)` calls (lines 417–419), an additional O(K²) byte-shift cost (~2.5 × 10⁹ element moves for the above parameters), amplifying CPU exhaustion even if memory is not exhausted.

Root cause is confirmed in `networks/bitcoin/src/wallet/send.rs`: unconditional per-input cloning of the shared preprocess map (lines 364–371), no input deduplication at construction (lines 175–185), and quadratic share removal (lines 417–419).
