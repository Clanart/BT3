### Title
Cross-shop webhook identity spoofing via unsigned `HTTP_X_SHOPIFY_SHOP_DOMAIN` header trusted by `shop_domain` - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#shop_domain` returns the raw, unsigned `HTTP_X_SHOPIFY_SHOP_DOMAIN` request header without any cryptographic binding to the verified HMAC. Because the HMAC in `hmac_valid?` is computed only over `request.raw_post` using the app's shared client secret (not per-shop, and not covering headers), any actor holding one valid `(body, hmac)` pair for their own shop can replay it against the app's public webhook endpoint with a forged shop-domain header, causing downstream code that trusts `shop_domain` to attribute the payload to a different (victim) shop.

### Finding Description
`verify_request` only validates the raw POST body against a shared secret: [1](#0-0) [2](#0-1) 

`ShopifyApp.configuration.secret`/`old_secret` are the app's client secret(s), shared across every shop that installs the app — they are not per-shop keys. The HMAC digest is computed over `data` (the raw body) only; no header, including `HTTP_X_SHOPIFY_SHOP_DOMAIN`, is included in the signed material.

`shop_domain` then reads that unauthenticated header directly and is treated as the verified shop identity for the request: [3](#0-2) 

This is the exact documented/intended usage pattern of the library: both the docs and the generator templates instruct app developers to pass `shop_domain` straight into a background job that looks up a `Shop` record and acts under that shop's session: [4](#0-3) [5](#0-4) 

Exploit flow:
1. Attacker installs the target app on their own (unprivileged) shop and triggers/receives a legitimate webhook, capturing a valid `(raw_post, X-Shopify-Hmac-Sha256)` pair. Because the HMAC secret is the app-wide client secret, this pair is valid for the app regardless of shop.
2. Attacker sends a POST directly to the app's public webhook route (bypassing Shopify) with the same `raw_post` and `hmac`, but sets `HTTP_X_SHOPIFY_SHOP_DOMAIN` to the victim shop's domain.
3. `hmac_valid?` passes because it only checks body+secret, never the header.
4. `shop_domain` returns the attacker-forged victim domain, unverified.
5. Downstream job code (`Shop.find_by(shopify_domain: shop_domain)` then `shop.with_shopify_session`) processes attacker-controlled webhook data under the victim shop's identity/session.

None of the existing safeguards stop this: there is no `ActiveSupport::SecurityUtils.secure_compare` on the shop-domain header (it isn't compared to anything), no ID-token/JWT session binding is involved (webhooks are server-to-server, not embedded-session requests), and `ShopifyApp::Utils.sanitize_shop_domain` is not invoked in this path.

### Impact Explanation
This enables cross-shop confusion in webhook processing: an attacker can cause the app to run webhook-triggered business logic (data request/redact flows, order/cart update handlers, custom job logic) attributed to a shop they do not control, using data they fully control. Depending on what the job does with `shop.with_shopify_session`, this can range from data integrity/logic-confusion issues up to unauthorized actions being taken against a victim shop's session using attacker-supplied webhook payload content. This maps to Shopify's "cross-shop data access / forged webhook request accepted" impact class.

### Likelihood Explanation
Feasibility is high and requires no privileged access: any actor able to install the app on an unrelated (attacker-owned) development/trial shop can capture a valid signed webhook and replay it with a forged header directly to the app's endpoint, since the client secret is shared across all installs and the header is never bound to the signature. Repeatable for any topic/body the attacker's own shop can trigger.

### Recommendation
Do not trust `HTTP_X_SHOPIFY_SHOP_DOMAIN` as authenticated shop identity. Either:
- Derive/verify the shop domain from data that is inside the signed payload where the topic guarantees it (and validate it belongs to a shop actually registered/installed for this app), or
- Include the shop domain in the HMAC-signed material (e.g., verify it against Shopify's registered webhook delivery for that specific shop's per-shop stored access token/session, cross-checking that the shop is an installed shop before trusting the header), and reject if the shop record's stored webhook secret/config doesn't match.
At minimum, downstream consumers should treat `shop_domain` as untrusted input and re-validate it (e.g., confirm the shop is installed and require additional shop-specific verification) before acting with elevated privileges.

```ruby
class WebhookVerificationController < ActionController::Base

class WebhookVerificationSpoofTest < ActionController::TestCase
  tests WebhookVerificationController

  setup do
    ShopifyApp.configure { |c| c.secret = "secret" }
  end

  test "hmac validates independent of shop-domain header, allowing spoofing" do
    with_routing do |set|
      set.draw { post "/webhook_action" => "webhook_verification#webhook_action" }

      params = { foo: "anything" }
      valid_hmac = "yCGX/RrK4fcuNtr3ztk5tQGsOBjcAzHpGLdMUrbV8yI=" # valid for this body+secret regardless of shop

      @request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"] = valid_hmac
      @request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"] = "victim-shop.myshopify.com" # attacker-forged

      post :webhook_action, params: params

      assert_response :ok
      assert_equal "victim-shop.myshopify.com", @response.body # unverified, attacker-controlled
    end
  end
end
```
This demonstrates that a body/HMAC pair valid for the attacker's own shop is accepted while an arbitrary, unverified `shop_domain` value is returned to downstream callers.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
