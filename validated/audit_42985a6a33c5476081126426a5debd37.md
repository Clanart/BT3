### Title
Once a local repository is matched to a GitHub repo, the association is never cleared, letting an attacker-controlled remote pin the wrong endpoint/credentials permanently - (File: `app/src/lib/stores/app-store.ts`)

### Summary
GitHub Desktop's `repositoryWithRefreshedGitHubRepository` in `app-store.ts` matches a local repository's `origin` remote against known GitHub accounts (`matchGitHubRepository`) and, once a match is found, persists a `GitHubRepository` association (endpoint, owner, name) on the `Repository` record. The code contains an explicit acknowledgment that this association is **never cleared**, mirroring the reported bug class: a trust/whitelist entry that can be added but has no corresponding removal path.

### Finding Description
`repositoryWithRefreshedGitHubRepository` calls `this.matchGitHubRepository(repository)`, which resolves the remote URL to a GitHub `(owner, name)` pair via `matchGitHubRepository` in `app/src/lib/repository-matching.ts`. If a match is found, the code explicitly states it will never unset this association: [1](#0-0) 

```
    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }
```

This binding determines which authenticated `Account` (and its OAuth token) is used for git operations, GitHub API calls (branch protection, PR checks, commit status), and proxy resolution: [2](#0-1) 

The matching logic itself only compares the remote's hostname against a known account's endpoint hostname, without pinning to a specific owner/name the user explicitly trusted: [3](#0-2) 

Because the resulting `GitHubRepository` association is persisted and, per the TODO, is never cleared, an attacker who can transiently control the `origin` remote URL of a repository the victim has open in Desktop (e.g., by supplying a malicious clone target, briefly redirecting a fork's remote, or via a crafted `x-github-client://openRepo` deep link handled by `parseAppURL`/`handleAppURL` that opens/clones an attacker repository) can cause the local `Repository` record to bind permanently to the attacker's GitHub repository/owner. Even after the remote URL is subsequently corrected by the user, the stale `gitHubRepository` association — including its `endpoint` used by `getAccountForRepository` and `getFallbackUrlForProxyResolve` — persists, since there is no "remove/clear association" feature analogous to the missing `blacklist()`/`removeFromWhitelist()` function in the audited contract.

The deep-link entry point that can drive this binding without local access is `parseAppURL`, which accepts an arbitrary `url` for the `open-repository-from-url` action: [4](#0-3) 

### Impact Explanation
A persistent, un-removable binding between a local repository and an attacker-influenced GitHub repository/endpoint means:
- The wrong `Account`/token could continue to be selected for authenticated operations against that repository (`getAccountForRepository`), potentially exposing credentials to git operations, commit-status/CI-check API calls, or proxy resolution tied to the attacker's endpoint (`getFallbackUrlForProxyResolve` in `app/src/lib/git/environment.ts`).
- Downstream features (branch protection refresh, PR checks, notifications) keep referencing metadata sourced from the attacker-influenced `GitHubRepository` record even after the user "fixes" the remote, because there's no path to unset it.
- This matches the core of the reported bug class: a trust association can be created but never revoked, forcing the user into unnatural workarounds (e.g., deleting and re-adding the entire local repository from Desktop) to fully break the stale binding.

### Likelihood Explanation
Moderate. The binding is created automatically any time Desktop refreshes GitHub metadata for a repository whose remote resolves to a known account's hostname — this happens routinely (e.g., after clone, fetch, or opening via the `x-github-client://openRepo` protocol handler). No explicit user consent step vets the specific owner/repo being bound, unlike the SSH host-key trust flow which prompts before persisting trust (`AddSSHHost` dialog). The attack requires the attacker's remote to have been present at some point when Desktop performed this refresh, which is plausible via a deep-link-driven clone/open action or a maliciously repointed remote in a shared/forked repository workflow.

### Recommendation
Implement an explicit way to clear or reset a repository's `GitHubRepository` association (analogous to the missing `blacklist()`/removal function recommended in the source report), e.g., a "Disassociate from GitHub" action in Repository Settings, and re-validate/require the association to match the *current* remote's owner/name on every refresh rather than persisting a stale match indefinitely. Resolve the tracked TODO/issue referenced in the code (`desktop/desktop#1144`).

### Proof of Concept
1. Have Desktop track a repository whose `origin` remote temporarily points to an attacker-controlled fork on the same GitHub host (e.g., via a crafted `x-github-client://openRepo/<attacker-repo-url>` link handled by `parseAppURL`, or by an attacker with transient write access to a shared remote configuration).
2. Trigger a metadata refresh (fetch, opening the repo, or automatic background refresh) so `repositoryWithRefreshedGitHubRepository` runs `matchGitHubRepository` and persists a `GitHubRepository` record bound to the attacker's owner/repo/endpoint via `repoStore.setGitHubRepository`.
3. Restore `origin` to the legitimate URL.
4. Observe that `repository.gitHubRepository` still reflects the attacker-controlled repository/endpoint (per the explicit "never clear" TODO), and that `getAccountForRepository`/`getFallbackUrlForProxyResolve` continue to make decisions based on that stale association, with no in-app control to remove it — only manually removing and re-adding the repository from Desktop root out the record.

**Note on completeness:** I could not fully trace the entire lifecycle of `setGitHubRepository`/`upsertGitHubRepository` in `repositories-store.ts` (only the top of the file was inspected) to confirm there is truly no hidden "clear" method elsewhere in that store; the explicit code comment and referenced upstream issue (`desktop/desktop#1144`) are the primary evidence for this finding.

```typescript
export function getAccountForRepository(
  accounts: ReadonlyArray<Account>,
  repository: Repository
): Account | null {
  const gitHubRepository = repository.gitHubRepository
  if (!gitHubRepository) {
    return null
  }

  return getAccountForEndpoint(accounts, gitHubRepository.endpoint)
}
```

```typescript
/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
```
