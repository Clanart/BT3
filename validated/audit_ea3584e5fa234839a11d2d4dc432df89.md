### Title
PedPoP `calculate_share` returns the ECDH-revealing blame proof before verifying the message's proof-of-possession, letting a copied per-message key decrypt someone else's secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts each received `EncryptedMessage` and produces an `EncryptionKeyProof` (the raw ECDH shared point plus a DLEq) inside `Encryption::decrypt` before the message's `pop` Schnorr proof — which is only *queued* into the batch verifier — has actually been checked. If the decrypted bytes fail `C::F::from_repr`, the function returns `PedPoPError::InvalidShare { blame: Some(blame) }` immediately, skipping `batch.verify_with_vartime_blame()` entirely. An attacker can therefore obtain a blame proof revealing the ECDH secret for a message whose per-message key they do not own, resurrecting the exact share-disclosure attack the per-message PoP was added to prevent.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `EncryptedMessage` carries a `pop` Schnorr signature precisely so that an attacker copying Alice's per-message key `X` cannot induce victim Bob to publish the ECDH key `b·X`, which would also decrypt Alice's real message to Bob (comments at lines 84-90). The `pop` is only checked inside `Encryption::decrypt` via `msg.pop.batch_verify(rng, batch, batch_id, ...)` — i.e., it is *queued*, not verified — while `decrypt` immediately computes and returns `key = ecdh(enc_key, msg.key)` wrapped in an `EncryptionKeyProof` (`encryption.rs:479-499`).

In `crypto/dkg/pedpop/src/lib.rs:476-491`, `calculate_share` iterates over attacker-supplied shares, calls `decrypt`, and then performs `Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| PedPoPError::InvalidShare { blame: Some(blame.clone()) })?`. The `?` early-returns from the function *before* `batch.verify_with_vartime_blame()` at line 493 is ever reached. The returned `blame` (a `Some(EncryptionKeyProof)` containing `key = enc_priv_bob · msg.key` and a DLEq binding it to Bob's registered encryption key) is designed to be published so third parties can resolve blame — publishing it exposes the shared key for `msg.key`.

Exploit path: Eve observes Alice's honest `EncryptedMessage` to Bob, which uses per-message key `X`. Eve copies `X` as her own `msg.key` and fills `msg`/`pop` with arbitrary bytes. Because Eve does not know the ChaCha keystream derived from `b·X`, the "decrypted" `share_bytes` are effectively uniform 32 bytes. For ed25519/Ristretto (l ≈ 2^252.4), ~92% of random 32-byte strings are non-canonical, so `from_repr` fails with overwhelming probability, causing Bob's `calculate_share` to return `blame: Some(EncryptionKeyProof{ key = b·X, dleq })` for a message whose `pop` was never verified. Once that blame is published (the protocol's intended handling of `PedPoPError::InvalidShare`), `b·X` decrypts Alice's genuine `EncryptedMessage`, leaking the secret share Alice sent to Bob.

### Impact Explanation
This is secret share disclosure leading to key share recovery, the same impact class the code comments describe as "a massive side effect which could break some protocols, in the worst case" (`encryption.rs:86-88`). The published `EncryptionKeyProof.key` is the exact ChaCha20 seed material (`cipher(context, ecdh)`) for every message encrypted under Alice's per-message key `X` to Bob, so Alice's secret share to Bob is recovered by anyone who sees the blame. Compromised shares undermine the threshold key produced by the DKG (an attacker harvesting shares across rounds/sessions can approach reconstructing participants' shares).

### Likelihood Explanation
An unprivileged DKG participant can reach this path with purely public inputs: an `EncryptedMessage` is read via `EncryptedMessage::read` (public bytes) and fed to `calculate_share`. The attacker does not need the discrete log of the copied key. The trigger probability per attempt is ~92% (probability a uniform 32-byte string exceeds the scalar modulus), and the attack can be retried across DKG invocations. The only requirement is the DKG's assumed authenticated broadcast channel, which is a baseline assumption of the protocol rather than an elevated capability.

### Recommendation
Verify the `pop` before returning or emitting the blame proof. Concretely, in `calculate_share`, do not return `blame: Some(...)` on the `from_repr` failure until the decryption batch has been verified — e.g., treat a share whose `pop` fails as `BatchId::Decryption` (blame `None`), and only attach the `EncryptionKeyProof` once `batch.verify_with_vartime_blame()` has confirmed the PoP for that message. Alternatively, have `Encryption::decrypt` verify the `pop` synchronously (or return the proof lazily, only materializing `EncryptionKeyProof` after batch verification succeeds).

### Proof of Concept
1. Run a PedPoP DKG with participants Alice (1), Eve (2), Bob (3).
2. Capture `shares[Alice][Bob]` (`EncryptedMessage { key: X, pop, msg }`) as broadcast.
3. Eve constructs `EncryptedMessage { key: X, pop: arbitrary SchnorrSignature, msg: arbitrary bytes }` addressed as her share to Bob, and delivers it via `EncryptedMessage::read` → `calculate_share`.
4. Inside `calculate_share`, `decrypt` queues the invalid `pop` into the batch but returns `EncryptionKeyProof { key: b·X, dleq }` immediately.
5. `C::F::from_repr` on the pseudo-random decrypted bytes fails with ~92% probability, returning `PedPoPError::InvalidShare { participant: Eve, blame: Some(proof) }` — emitted before `batch.verify_with_vartime_blame()` ever checks Eve's forged `pop`.
6. Bob publishes the blame per protocol; any observer computes `cipher(context, b·X)` and decrypts Alice's real message, recovering Alice's secret share to Bob.
