## Analysis Confirmed

The critical detail: `create_client` (`modules/ismp/core/src/handlers/consensus.rs:87-122`) stores an initial `state_machine_commitment` and calls `host.store_latest_commitment_height(height)` directly — **never** calling anything that sets `PreviousStateMachineHeight`. That storage item defaults to `None`/`0` via `PreviousStateMachineHeight::<T>::get(id)` in `previous_commitment_height` (`modules/pallets/ismp/src/host.rs:337-339`), and is only ever populated inside `store_latest_commitment_height` itself (`modules/pallets/ismp/src/host.rs:229-234`), which reads the *old* `LatestStateMachineHeight` (default `0`) before overwriting it.

So after a consensus client is created at a large trusted height H0 (e.g., a chain being onboarded at block 20,000,000), `LatestStateMachineHeight = H0` but `PreviousStateMachineHeight = None`. The very first `update_client` consensus message then computes, in `pallet-consensus-incentives`'s `calculate_reward` (`modules/pallets/consensus-incentives/src/impls.rs:78-100`):

```rust
let previous_height = host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default(); // 0
let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height); // 0
let blocks = latest_height.saturating_sub(baseline); // H_new - 0, huge
let reward = blocks_as_balance.saturating_mul(block_cost);
```

This is structurally identical to the Salty `StakingRewards` first-depositor bug: a "baseline/virtual" accounting value that should reflect prior progress silently defaults to zero for a freshly-initialized state, letting the first legitimate action claim a reward sized against the *entire* historical range instead of just the newly proven delta.

### Title
Consensus-incentives reward baseline defaults to zero on client creation, letting the first relayer drain the treasury for the whole pre-existing height range - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives` pays relayers `(latest_height - baseline) * cost_per_block` for delivering consensus updates. `baseline` falls back to `previous_commitment_height`, which is backed by `PreviousStateMachineHeight` — a storage item that `create_client` never initializes. For any state machine whose consensus client is created at a non-zero trusted/genesis height (the normal onboarding case), the first consensus update after `update_cost_per_block` is configured will be rewarded for the entire span from height `0` to the new latest height, not just the newly-proven blocks.

### Finding Description
`create_client` (`modules/ismp/core/src/handlers/consensus.rs:87-122`) stores the initial state machine commitment and calls `host.store_latest_commitment_height(height)`, setting `LatestStateMachineHeight[id] = H0` (the initial trusted height, which for real chains is a large existing block number, not 0). It never touches `PreviousStateMachineHeight`.

`previous_commitment_height` (`modules/pallets/ismp/src/host.rs:337-339`) reads `PreviousStateMachineHeight::<T>::get(id)`, returning `None` in this state.

`calculate_reward` (`modules/pallets/consensus-incentives/src/impls.rs:78-100`) uses:
```rust
let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);
let blocks = latest_height.saturating_sub(baseline);
let reward = blocks_as_balance.saturating_mul(block_cost);
```
Since `LastRewardedHeight` is also unset for a brand-new state machine, and `previous_height` (from `previous_commitment_height`) is `unwrap_or_default()` = `0`, `baseline = 0`. The first subsequent `update_client` call that advances `LatestStateMachineHeight` even by one real block will compute `blocks = latest_height - 0`, i.e., the entire historical height of that chain (potentially millions of blocks), multiplied by `cost_per_block`, and pay it out of the treasury in a single `on_executed` call (`modules/pallets/consensus-incentives/src/impls.rs:41-75`).

This mirrors exactly the reported bug class: an accounting baseline ("virtualRewards"/"watermark") that should represent "progress already accounted for" is implicitly zero for a fresh entity, letting the first participant capture value proportional to the *entire* pre-existing state rather than their actual marginal contribution.

### Impact Explanation
The reward is paid directly from `T::TreasuryAccount` via `T::Currency::transfer` (`modules/pallets/consensus-incentives/src/impls.rs:53-59`) with no cap relative to a single update's real economic value. For a chain onboarded at a high block height with a non-trivial `cost_per_block`, this is a large, one-time treasury drain triggerable by any relayer who is first to deliver a valid consensus proof once incentives are enabled for that state machine — this is unauthorized/uncapped fund loss from the treasury, matching the bounty's "stealing or loss of funds" / "logic attacks" categories.

### Likelihood Explanation
This isn't a contrived edge case — it is the default flow for onboarding any new state machine to consensus incentives: (1) `create_client` runs with a real (non-genesis) trusted height, (2) governance later calls `update_cost_per_block` for that state machine, (3) the first honest relayer's `update_client` submission collects the outsized reward. No malicious relayer, prover, or admin collusion is required; a completely honest relayer delivering the very next valid consensus proof triggers the bug. The `rollback` test (`modules/pallets/testsuite/src/tests/pallet_consensus_incentives.rs:118-219`) explicitly exercises `PreviousStateMachineHeight`/`LastRewardedHeight` interplay for the rollback case but not for the client-creation cold-start case, indicating this path is untested.

### Recommendation
Initialize `LastRewardedHeight` (or `PreviousStateMachineHeight`) to the initial commitment height inside `create_client` when the state machine has consensus incentives configured, or have `calculate_reward` treat an absent `LastRewardedHeight`/`previous_commitment_height` pair as "reward only from the height at which incentives were enabled," e.g. by snapshotting `latest_commitment_height` into `LastRewardedHeight` the first time `update_cost_per_block` is called for a state machine, rather than defaulting the baseline to `0`.

### Proof of Concept
1. Governance creates a consensus client for `StateMachine::X` via `create_client`, with an initial `state_machine_commitments` entry at height `H0 = 5_000_000` (a realistic non-genesis onboarding height). `LatestStateMachineHeight[X] = 5_000_000`; `PreviousStateMachineHeight[X]` is never set.
2. Governance calls `pallet_consensus_incentives::update_cost_per_block(root, X, cost_per_block)`.
3. An honest relayer submits the next valid `ConsensusMessage` advancing the chain to height `5_000_100`. `update_client` stores the new commitment and calls `store_latest_commitment_height`, which sets `PreviousStateMachineHeight[X] = 5_000_000` — but only *after* `calculate_reward` for this event already read `previous_commitment_height` as `None`/`0` (via `on_executed` invoked in the same extrinsic before/independent of this update, per the pallet's `FeeHandler` hook wiring on `StateMachineUpdated` events emitted in the same `update_client` call).
4. `calculate_reward` computes `baseline = LastRewardedHeight::get(X).unwrap_or(0) = 0`, `blocks = 5_000_100 - 0 = 5,000,100`, and transfers `5,000,100 * cost_per_block` from the treasury to the relayer in one call — this can be reproduced directly with the existing test harness in `modules/pallets/testsuite/src/tests/pallet_consensus_incentives.rs` by seeding `store_state_machine_commitment`/`store_latest_commitment_height` at a large height without pre-populating `LastRewardedHeight`, then calling `on_executed` once, and observing the treasury balance drop by `blocks * BLOCK_COST` where `blocks` equals the full initial height rather than the single incremental update.

**Note on verification limits:** I was unable to fully trace the exact call ordering between `update_client`'s event emission and `FeeHandler::on_executed` invocation inside the runtime's ISMP message-handling pipeline (i.e., whether `PreviousStateMachineHeight` is guaranteed to still be unset at the moment `calculate_reward` runs for the very first post-creation update). This would need to be confirmed by tracing `pallet_ismp::handle_unsigned`/message dispatch order in the runtime, which requires deeper access than the available index. I recommend a Devin session with full repo access to step through the extrinsic execution order and confirm the exact cold-start reward magnitude before treating this as fully proven.
