## Title
Stale line-index selection allows a race-window file mutation to silently corrupt partial commits — (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user "partially" stage a file by selecting individual diff lines. The selection is stored as a set of **absolute line indices** into a diff that was fetched at render time. When the commit actually executes, Desktop re-fetches a brand-new diff and blindly re-applies those same indices to it, with no check that the new diff's line-for-line shape still matches the one the user reviewed. This is the same "predefined parameter vs. state that can move before use" flaw as the Mellow `amount` bug: an index/amount computed against one snapshot of mutable state is consumed against a different, later snapshot, and nothing guards the gap.

### Finding Description
When a user selects a subset of lines to commit, `WorkingDirectoryFileChange.selection` stores `isSelected(absoluteIndex)` bookkeeping produced from the diff that was on screen at the time [1](#0-0) . Desktop is aware this diff can go stale relative to a previous render and only reconciles it by pruning indices that no longer point at an "includeable" line — it explicitly does **not** verify the line content is unchanged: [2](#0-1) 

That reconciliation only runs opportunistically whenever the Changes-tab diff viewer refreshes. It is never re-run immediately before staging. At commit time, `_commitIncludedChanges` takes whatever `file.selection` currently sits in the state cache and hands it straight to `createCommit` → `stageFiles` [3](#0-2) [4](#0-3) .

For any file with a partial selection, `stageFiles` calls `applyPatchToIndex`, which **independently re-fetches the diff from disk right before formatting the patch**: [5](#0-4) 

`formatPatch` then walks the hunks of this freshly-fetched diff and decides what to keep purely by `file.selection.isSelected(absoluteIndex)` — a numeric index carried over from the old diff, with no cross-check that hunk boundaries, line counts, or content still line up: [6](#0-5) 

If the working-tree file changes between the moment the user made their line selection (based on the diff they were shown) and the moment `applyPatchToIndex` re-diffs and re-applies indices, the indices silently point at different content in the new diff. `git apply --cached` then stages whatever lines happen to sit at those offsets in the new hunks — not the lines the user reviewed and checked. Existing guards do not stop this:
- The "selectable lines" pruning in `updateChangesWorkingDirectoryDiff` only fires on the async diff-panel refresh path, is throttled/best-effort, and only drops indices that are no longer includeable — it does not re-validate that a *still-includeable* index still corresponds to the *same* line the user selected.
- `applyPatchToIndex` re-diffs completely independently of that reconciliation pass, with zero staleness check against the diff the selection was derived from.

### Impact Explanation
The result is silent corruption of what the user commits (and subsequently pushes): text the user never reviewed can end up staged and committed under a commit message the user wrote for entirely different content, while unrelated hunks the user explicitly deselected can be included. This maps directly to the report's "Impact" category (`silent corruption of what the user commits or pushes`). Because this happens inside the normal commit flow with no error, the user has no signal that the committed diff differs from what they approved in the review pane.

### Likelihood Explanation
The race window is the interval between the last diff render/selection reconciliation and the user clicking "Commit" — realistically seconds during which Desktop itself runs background repository refreshes (`_refreshRepository`, periodic status/diff updates) or any external process (editor autosave, build/watch tool, a filter/smudge driver invoked by git for a cloned repository, or another git client) can touch the same file. A hostile/compromised repository can maximize the odds of hitting this window by shipping content or tooling (e.g. clean/smudge filters, generated files that a build step rewrites on checkout) designed to mutate tracked files shortly after checkout/fetch, precisely while a developer is reviewing and partially staging that file in Desktop.

### Recommendation
Before applying a partial-selection patch in `applyPatchToIndex`/`stageFiles`, re-validate that the diff fetched at staging time is structurally identical (or hash-equal per hunk) to the diff the selection was derived from; if it differs, abort the partial stage for that file and force the user to re-review/re-select rather than silently remapping indices onto new content. At minimum, track a content fingerprint (e.g. hash of the diff text) alongside `DiffSelection` and compare it in `applyPatchToIndex` before calling `formatPatch`.

### Proof of Concept
1. Modify a tracked file so it has two hunks; open it in Desktop's Changes view and select only the lines of hunk 1 (leave hunk 2 unselected).
2. Before clicking "Commit", have another process (e.g. a script, a `git checkout`/filter, or a background job the repository is designed to trigger) rewrite the file so hunk boundaries/line offsets shift while keeping some lines "includeable" at the same absolute indices (e.g. insert lines above hunk 1, or replace hunk 1's content with different but same-length additions).
3. Click "Commit" in Desktop. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-diffs the now-changed file and `formatPatch` (`app/src/lib/patch-formatter.ts:143-168`) applies the old absolute indices to the new hunks.
4. Inspect the resulting commit: it contains lines the user never selected/reviewed (from the new content at the old indices), while the message/description still reflects the originally reviewed change — demonstrating silent corruption of the committed content.
