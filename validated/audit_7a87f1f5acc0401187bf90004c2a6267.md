### Title
Fee and minimum-relay check ignore the OP_RETURN data output's weight, producing under-priced transactions - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/bsaldua/serai--019))

### Summary
`SignableTransaction::new` appends a caller-supplied OP_RETURN output (up to 80 bytes) to `tx_outs`, but computes `vbytes`, `needed_fee`, the minimum-relay-fee check, and the change amount via `calculate_weight_vbytes(tx_ins.len(), payments, …)` — which only receives `payments`, not the data output. The signed transaction therefore carries more weight than the fee calculation accounted for, so its real fee rate is lower than `fee_per_vbyte` and can fall below the relay minimum even though the `TooLowFee` check passed. This mirrors the reported bug class: a user-supplied quantity (here, `data` length; there, `shareAmount`) is included in one side of the operation but excluded from the fee computed on it.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- The OP_RETURN output is pushed onto `tx_outs` at lines 194–202, *before* the fee math.
- The fee math at lines 204–232 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, …)`, which builds a dummy `Transaction` whose `output` list is built solely from `payments` (lines 85–93) plus optional change (lines 95–99). The `data` output is never represented.
- Consequently `needed_fee = fee_per_vbyte * vbytes` (line 206) and the minimum-relay check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (line 211) are evaluated against a vbyte count up to ~92 weight units (~23 vbytes) too small (1-byte OP_RETURN prefix + push opcode + up to 80 bytes data, plus output overhead of ~9 bytes for value+script length — roughly 90+ bytes, i.e. ~23+ vbytes, though the exact delta depends on push-opcode encoding).
- The change computation at line 228 (`input_sat - payment_sat - fee_with_change`) uses the same understated fee, so the *satoshi* fee paid is `fee_with_change` while the *actual* transaction is larger than `vbytes_with_change`.

### Impact Explanation
Any caller that passes `data` gets a transaction whose effective fee rate is strictly below the `fee_per_vbyte` they requested — the exact analogue of "fee calculated on a smaller amount than what is actually transacted." At boundary values (low `fee_per_vbyte`, or change just above `DUST`), the signed transaction's true fee rate can drop below `DEFAULT_MIN_RELAY_TX_FEE`, meaning the transaction the protocol produces and signs is non-standard/non-relayable and will not confirm: the change output (and thus the funds) are reported/spent in a transaction that cannot enter the mempool, stalling the funds until the plan is retried. Unlike the HardVault case the user profits nothing directly, but the correctness invariant "`needed_fee` achieves `fee_per_vbyte`" is violated by user-supplied input.

### Likelihood Explanation
Reachable by any caller of the public `SignableTransaction::new` API supplying a non-empty `data` — no privileged position needed. Within Serai's own processor (`processor/src/networks/bitcoin.rs` `make_signable_transaction`), `data` is hardcoded to `None`, so the deployed processor does not trigger it; the defect affects library users/wallets built on `bitcoin-serai` that embed OP_RETURN data and rely on `needed_fee()`/`fee()` accuracy. Severity is bounded (fee mispricing up to ~23 vbytes worth), so Medium at most.

### Recommendation
Include the data output in the size estimation: build the weight-calculation transaction from the actual `tx_outs` (payments + OP_RETURN + optional change) rather than only `payments`. Concretely, pass the already-constructed `tx_outs` (or the serialized `data` length) into `calculate_weight_vbytes` so that `vbytes`, `needed_fee`, the `TooLowFee` check, and `fee_with_change` all account for the OP_RETURN output.

### Proof of Concept
```rust
// networks/bitcoin/tests/wallet.rs style reproduction
// Given: one ReceivedOutput `output`, address `addr`, FEE sat/vbyte.
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
  vec![output.clone()],
  &[(addr(), 10_000)],
  None,
  Some(data.clone()),
  FEE,
).unwrap();
// tx.needed_fee() was computed WITHOUT the ~90-byte OP_RETURN output.
// Actual fee paid = input - outputs = needed_fee (no change, leftover = needed_fee),
// but the real vsize is ~23+ vbytes larger than needed_fee / FEE.
// => effective fee rate = needed_fee / real_vsize < FEE.
// With FEE = 1 sat/vbyte the constructed TX's actual rate can fall below
// DEFAULT_MIN_RELAY_TX_FEE even though the TooLowFee check passed.
```
The weight/vbyte computation at `send.rs:62–127` only materializes `payments` and `change`; the `data` output pushed at `send.rs:194–202` is absent from every fee-related quantity derived afterward (`send.rs:204–235`).
