## Title
GHE Enterprise sign-in flow can be triggered against an attacker-controlled endpoint via a spoofed `WWW-Authenticate` realm, leading to credential/OAuth phishing - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind` in the Git credential-helper trampoline classifies a remote endpoint as GitHub Enterprise (`'enterprise'`) based on a `WWW-Authenticate` header value the remote server itself supplies, and that classification is later used to launch the real GitHub Enterprise sign-in UI (`promptForGitHubSignIn`) pointed at that attacker-controlled origin.

### Finding Description
When Git needs credentials for a remote, it forwards any `WWW-Authenticate` response headers into the credential-helper input. `getEndpointKind` treats this as a trusted signal: [1](#0-0) 

If the header contains `realm="GitHub"`, the endpoint is classified `'enterprise'` — with no verification that the host is actually a GitHub Enterprise instance (no TLS pinning, no `/meta` probe, nothing beyond a substring match on attacker-supplied header text). This value entirely comes from the remote server the user is cloning/fetching/pushing to, i.e. it's attacker-controlled input analogous to the "custom contract only implementing one interface" in the Optimism report: the classifier's OR-style heuristic (`isDotCom` OR `isGHE` OR header match OR known account OR HTTPS probe) lets a value pass a "looks like GitHub" check that downstream code treats as if it had the full guarantee of being a real, verified GitHub/GHE endpoint.

That misclassification is then consumed in `getCredential`: [2](#0-1) 

Since `endpointKind !== 'generic'` and no stored account matches this made-up endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which opens the real "Sign in to GitHub Enterprise" popup and points the actual OAuth/enterprise sign-in flow at the attacker's `origin`: [3](#0-2) 

The check that decides whether to trust a header-derived host as "enterprise" is only a substring test (`v.includes('realm="GitHub"')`) with no additional verification step before the sign-in UI is invoked, so the "existing guard" (the OR-chain of `isDotCom`/`isGHE`/header-match/known-account/`isGitHubHost` probe) does not stop a spoofed `WWW-Authenticate` header from being treated as equivalent to a verified GitHub Enterprise host — exactly the class of bug in the report, where a partial/loose interface/heuristic match is treated as if the full trusted interface were satisfied.

### Impact Explanation
A malicious git server/proxy that the user clones, fetches from, or is redirected to (e.g., via a malicious remote URL, a compromised git proxy, or MITM on plain HTTP that gets upgraded implicitly by git's auth negotiation) can respond to an authentication challenge with `WWW-Authenticate: realm="GitHub"`. Desktop will then present its legitimate-looking "Sign in to GitHub Enterprise" dialog pointed at that attacker origin. Depending on the underlying enterprise sign-in implementation (browser-based OAuth redirect or basic auth prompt), this can be used to phish the user's GitHub Enterprise session/OAuth token by presenting a trusted-looking Desktop UI while directing the authentication flow to the attacker's server. This matches the requested impact category of unauthorized OAuth flow / credential exfiltration driven by an attacker-controlled git remote/proxy response.

### Likelihood Explanation
This requires no local access, no prior malware, and no unusual user action beyond the normal step of adding/cloning from a remote and encountering an authentication prompt — a legitimate and expected user flow when authenticating to any Enterprise-like remote. The attacker only needs to control the HTTP response headers of a git server the victim is already interacting with (self-hosted git server, malicious fork host, or MITM/proxy), which is within the "attacker controls a git remote/proxy response" bracket explicitly allowed by the task's validity criteria.

### Recommendation
Do not let a self-reported `WWW-Authenticate` realm string alone elevate an endpoint to `'enterprise'` classification for the purposes of launching the real sign-in flow. At minimum, corroborate the header hint with the same verification used elsewhere (`isGitHubHost`'s `/meta` HEAD request and `x-github-request-id` check) before invoking `promptForGitHubSignIn`, and/or surface the actual target hostname prominently in the sign-in popup so users can recognize an unexpected/unfamiliar host before entering credentials.

### Proof of Concept
1. Set up a git-served HTTP endpoint (e.g., a proxy in front of a benign git repo) that, on an authentication challenge for `git fetch`/`clone`, returns `WWW-Authenticate: realm="GitHub"`.
2. Add this URL as a remote in GitHub Desktop and trigger a fetch/push that requires credentials.
3. The trampoline credential helper receives the `wwwauth[...]` header, matches `realm="GitHub"` in `getEndpointKind` [4](#0-3) , classifies the endpoint as `'enterprise'`, and since no account matches, calls `ui.promptForGitHubSignIn(endpoint)` [5](#0-4) .
4. `promptForGitHubSignIn` opens the genuine "Sign in to GitHub Enterprise" dialog with `setSignInEndpoint(origin)` set to the attacker's origin [6](#0-5) , so any credentials/tokens the user provides during that flow are sent to the attacker-controlled origin.

**Uncertainty note:** I could not fully trace the downstream `beginEnterpriseSignIn` / `setSignInEndpoint` implementation (e.g., whether it performs any additional origin validation, uses an embedded browser with OAuth device flow, or a basic-auth form) because those files were not returned by the index — this is the piece needed to confirm exactly what gets exposed to the attacker origin (raw username/password vs. an OAuth code/token) and would need to be verified in a full checkout of the repository.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
