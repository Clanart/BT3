### Title
`ThresholdKeys::read` accepts attacker-declared structure (params, interpolation, secret share, verification shares) without checking internal consistency, yielding semantically invalid keys - (File: crypto/dkg/src/lib.rs)

### Summary
The XXE bug class — a parser that trusts attacker-declared structure embedded in untrusted bytes — maps onto `ThresholdKeys::<C>::read`. The deserializer reads `t`, `n`, `i`, an interpolation variant, a `secret_share`, and `n` verification shares entirely from the input stream, then hands them to `ThresholdKeys::new`, which validates only counts and index ranges — never that `C::generator() * secret_share == verification_shares[i]`, and never that the interpolation factors are consistent with the verification shares. The result is a `ThresholdKeys` object that deserializes "successfully" yet is semantically meaningless, exactly like an XML parser expanding an attacker-declared entity into unintended content. Serai's own FROST code acknowledges this state exists: `AlgorithmSignatureMachine::complete` reaches `InternalError("everyone had a valid share yet the signature was still invalid")` only via "a semantically invalid FrostKeys" [1](#0-0) .

### Finding Description
`ThresholdKeys::read` parses all semantic fields from the reader [2](#0-1) :

- `t`, `n`, `i` are attacker-chosen u16s (bounds-checked only by `ThresholdParams::new`: `t <= n`, `i <= n`, nonzero) [3](#0-2) .
- The interpolation byte selects `Constant` (which reads `n` arbitrary scalars used later as per-participant interpolation factors) or `Lagrange` [4](#0-3) .
- `secret_share` and the `n` verification shares are read with no relation enforced between them.

`ThresholdKeys::new` only checks `verification_shares.len() == n`, participant indexes `<= n`, and `t == n` for `Constant`. It then derives `group_key` as `sum(verification_shares[i] * interpolation_factor(i))` over `1..=t` — a pure function of attacker-supplied points and attacker-supplied Constant factors [5](#0-4) . There is no check that `verification_shares[i] == C::generator() * secret_share`, so the stored secret is disconnected from the declared public structure.

Consequences when such keys are used:

- `view()` interpolates the (arbitrary) `secret_share` against the (arbitrary) verification shares, so the node produces FROST signature shares for a group key unrelated to its share — shares that fail `verify_share`, corrupting the aggregated signature while the key object itself was accepted [6](#0-5) .
- `group_key` is fully attacker-defined via `Constant` factors and verification shares, so anything keyed on `group_key()`/`original_group_key()` (e.g., address derivation, the `register_offset`/scanner path in `networks/bitcoin`) can attribute outputs to a group key whose corresponding secret distribution the holder does not possess — funds reported received that are not spendable.
- For `Interpolation::Constant`, the attacker supplies the binding coefficients outright; with Lagrange, `interpolation_factor` divides by `(share - i_f)` which is invertible for distinct participants, but nothing ties the resulting `group_key` back to the secret share.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (a listed reachable sink) causes the victim to adopt keys whose public identity (`group_key`, verification shares) is decoupled from its private share. Depending on downstream use this yields signatures that cannot verify under the apparent group key, or outputs credited to a `group_key`-derived address that the key material cannot spend — the "funds reported received that are not spendable" / "semantically invalid keys" impacts the exercise accepts.

### Likelihood Explanation
Reachability is gated on the deployment actually deserializing `ThresholdKeys` from an attacker-influenced source (the format is a network/restoration serialization). When reachable, exploitation is deterministic — no races, no probabilistic elements — since every field is directly attacker-controlled and the only validations are range checks. Severity is bounded by the fact that the attacker cannot recover the honest secret share (they would already need it), so the practical impact is integrity/availability of the key group rather than key theft: Medium.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), reject semantically invalid input:
1. Require `C::generator() * secret_share == verification_shares[&params.i()]` — every honest construction path (`dealer::key_gen`, `pedpop::calculate_share`, `musig`) satisfies this [7](#0-6) .
2. For `Interpolation::Constant`, either verify the coefficient vector length/consistency against the shares or document and check the invariant that `sum(share_i * c_i) * G == group_key` for a known-consistent subset.
3. Optionally reject `secret_share == 0` on read, since no honest path produces it.

### Proof of Concept
```rust
// crypto/dkg: construct a ThresholdKeys blob whose secret share
// does not match its own verification share — read() accepts it.
use dkg::{ThresholdKeys, Participant, ThresholdParams, Interpolation};
use ciphersuite::{Ciphersuite, group::ff::Field};
use dalek_ff_group::Ristretto;
use zeroize::Zeroizing;
use rand_core::OsRng;

let mut bytes = vec![];
// curve ID header
bytes.extend(&(Ristretto::ID.len() as u32).to_le_bytes());
bytes.extend(Ristretto::ID);
// t = 1, n = 1, i = 1
bytes.extend(&1u16.to_le_bytes());
bytes.extend(&1u16.to_le_bytes());
bytes.extend(&1u16.to_le_bytes());
// Interpolation::Lagrange
bytes.push(1);
// secret_share = random s1
let s1 = <Ristretto as Ciphersuite>::F::random(&mut OsRng);
bytes.extend(s1.to_repr().as_ref());
// verification_shares[1] = G * s2 for an unrelated s2
let s2 = <Ristretto as Ciphersuite>::F::random(&mut OsRng);
bytes.extend((Ristretto::generator() * s2).to_bytes().as_ref());

let keys = ThresholdKeys::<Ristretto>::read(&mut bytes.as_slice()).unwrap();
// group_key == G * s2, but the stored secret is s1.
assert_eq!(keys.group_key(), Ristretto::generator() * s2);
assert_eq!(*keys.original_secret_share(), s1);
// Any view()/signing operation now produces shares inconsistent with
// the group key — the "semantically invalid FrostKeys" state sign.rs
// admits can only come from deserialization.
```

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }
