### Title
Reward Misattribution via Multi-Message Batch in `pallet-consensus-incentives::on_executed` - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`on_executed` derives the reward beneficiary solely from the first `Message::Consensus` entry in a batch, then pays that single account for the state advancement of every state machine touched anywhere in the batch — including state machines whose consensus proof was actually submitted by a different signer's message later in the same batch.

### Finding Description
`Pallet::execute` (`modules/pallets/ismp/src/impls.rs:40-79`) processes an arbitrary `Vec<Message>` supplied by the caller of the unsigned `handle_unsigned` extrinsic, batches the resulting events, and hands the *entire* event list plus the *entire* message list to `T::FeeHandler::on_executed` in one call. Nothing constrains a submitted batch to messages from a single signer or a single state machine — the ISMP router is designed to process arbitrary heterogeneous message batches for efficiency.

`consensus-incentives::on_executed` (`modules/pallets/consensus-incentives/src/impls.rs:108-157`) recovers `relayer_account` by decoding the signature on `messages[0]` only:
```rust
let maybe_relayer_account = messages.get(0).and_then(|first_message| { ... });
```
It then builds `highest_per_state_machine` by scanning **all** `IsmpEvent::StateMachineUpdated` events in the batch — regardless of which message produced them — and pays `relayer_account` (the signer of message 0) for every one of those state-machine advances via `process_message`, which performs an unconditional treasury `Currency::transfer`.

If a batch contains `Message::Consensus` proofs for state machine A signed by relayer X and state machine B signed by relayer Y, relayer X (whose message happens to occupy index 0) collects the reward for *both* A's and B's advancement, while Y receives nothing despite having supplied the valid proof and signature for B. This is a direct fund-misdirection: the wrong beneficiary receives the treasury payout, and the actual submitting relayer for the other messages is never even inspected.

This is a local structural analog to the reported external bug class: a shared "pool" of reward computation (here, "whichever signer happens to be at position 0") is applied indiscriminately across multiple independent units of work batched together, decoupling the party that did the work from the party that gets paid — the same disconnect the external report described between the fee charged for one rollup/batch and the reward paid out from the shared pool.

### Impact Explanation
This is a real fund-misdirection in a production reward-distribution pallet: treasury funds are transferred to an account that did not necessarily produce all (or in the adversarial case, any) of the state advancements being rewarded. An unprivileged, unsigned extrinsic submitter fully controls the batch composition (message ordering and count), so they can structure a batch to route rewards for other relayers' consensus updates to their own account, provided they can also supply one valid signed `Message::Consensus` at index 0 for any state machine. Because the extrinsic is unsigned (`ensure_none` semantics via `handle_unsigned`) and rewards are paid unconditionally from the treasury based on batch content, this directly satisfies "unauthorized transaction manipulation" / "wrong beneficiary" per the bounty scope.

### Likelihood Explanation
Likelihood depends on how the off-chain relayer/tesseract client normally batches messages — if it typically never batches multiple `Message::Consensus` from different state machines/signers together, this may rarely trigger organically. However, nothing in the on-chain `execute`/`on_executed` path enforces single-signer or single-state-machine batches, and the extrinsic is unsigned and permissionlessly submittable, so a malicious actor can deliberately construct such a batch (bundling their own valid proof at index 0 with any other relayer's already-broadcast/mempool-visible consensus proof for a different chain) to redirect that other relayer's reward to themselves.

### Recommendation
Recover and reward the signer per individual `Message::Consensus` entry rather than using only `messages[0]`. Pair each `StateMachineUpdated` event with the specific message/signer that produced it (e.g., by tracking message index or embedding the state_machine_id → signer mapping while iterating `messages`), and pay each relayer only for the updates their own signed message produced.

### Proof of Concept
1. Relayer Y broadcasts a valid signed `Message::Consensus` proof for `state_machine_id = B` (visible in mempool / previously submitted).
2. Attacker X crafts their own valid `Message::Consensus` for `state_machine_id = A` and submits `handle_unsigned([X's message for A, Y's message for B])` as a single unsigned extrinsic, placing their own message at index 0.
3. `Pallet::execute` processes both messages, producing `StateMachineUpdated` events for both A and B, and calls `on_executed(messages, events)` with both messages/events combined.
4. `on_executed` recovers only X's signature from `messages[0]`, then iterates `highest_per_state_machine` covering both A and B, calling `process_message` for each with `relayer_account = X`.
5. Treasury pays X for both A's and B's block-span reward; Y receives nothing despite having authored B's proof.

Note: I was unable to fully trace whether the off-chain tesseract client or on-chain mempool validation ever prevents such cross-relayer batch construction (e.g., via `validate_unsigned` tagging) — this would need direct verification in a live/test environment (e.g., `modules/pallets/testsuite`) to confirm no additional guard rejects heterogeneous-signer batches before `on_executed` is reached.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
