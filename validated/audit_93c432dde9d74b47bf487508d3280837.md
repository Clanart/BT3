## Analog Found: Balance Handler `prevEventsLen` Caching Bug in Precompile-Recursion Path

### Title
Cached `prevEventsLen` in `BalanceHandler` causes double- or missed-application of bank balance-change events to the EVM StateDB during nested/recursive precompile calls - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
This is the same bug class as the Arcadia Uniswap issue: a value is snapshotted (`assetToLiquidity` in Arcadia; `prevEventsLen` here) at one point in execution, and used later to reconcile state — but an intervening nested/recursive call can invalidate the assumption behind the cached value before it's consumed, producing state that diverges from ground truth. In Cosmos EVM, `BalanceHandler.BeforeBalanceChange` records `len(ctx.EventManager().Events())` as `prevEventsLen`, and `AfterBalanceChange` later replays `events[prevEventsLen:]` to apply `AddBalance`/`SubBalance` deltas onto the EVM `StateDB` [1](#0-0) . Because the underlying `ctx.EventManager()` event log is shared and monotonically growing across nested precompile executions (all derived from the same cache context chain on the `StateDB`), a nested/recursive precompile call occurring inside another precompile's native action can cause the outer call's post-processing window to overlap with the inner call's already-processed window — or, in the shared-handler variant, cause `prevEventsLen` itself to be silently overwritten by the inner call before the outer call reads it.

### Finding Description
`BalanceHandler` is a stateful helper that translates `x/bank` `EventTypeCoinSpent`/`EventTypeCoinReceived` events into `StateDB.AddBalance`/`SubBalance` calls, so that native-currency movements performed by a precompile (via `bank.SendCoins`) are reflected in the EVM statedb view of balances [2](#0-1) .

The reconciliation window is computed purely from array-length bookkeeping:
- `BeforeBalanceChange` sets `bh.prevEventsLen = len(ctx.EventManager().Events())` [3](#0-2) .
- `AfterBalanceChange` later iterates `events[bh.prevEventsLen:]` and applies each spent/received amount to the stateDB [4](#0-3) .

In the current mainline (`precompiles/common/precompile.go`), each call to `RunNativeAction`/`runNativeAction` allocates a fresh handler via `p.BalanceHandlerFactory.NewBalanceHandler()` immediately before calling `BeforeBalanceChange`, and calls `AfterBalanceChange` immediately after the native `action(ctx)` returns [5](#0-4) . This mitigates the *shared mutable field* variant of the bug (where a single `BalanceHandler` instance field on a precompile struct is reused and thus overwritten across recursive/reentrant calls into the *same* precompile object). That older, more direct variant is preserved and exercised by the repository's own `debug` test precompile, which fetches the handler via `p.GetBalanceHandler()` on a shared struct rather than a per-call factory instance [6](#0-5) , and the repo carries a dedicated regression test explicitly documenting this class of bug: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync between native bank keeper and EVM stateDB"* [7](#0-6) .

Critically, even with the "fresh handler per call" fix in `precompiles/common/precompile.go`, the underlying reconciliation mechanism is still fragile against nesting: the event log (`ctx.EventManager().Events()`) that `prevEventsLen` indexes into is never truncated or partitioned per call — it is a single, ever-growing slice shared across the whole call stack for the transaction. If a precompile's native action (`action(ctx)`) itself triggers another precompile call before returning (precompile-to-precompile reentrancy, e.g. through IBC/EVM callback flows or contract calls made mid-execution of a bank `Send`), the inner call's `AfterBalanceChange` will consume and apply events generated by the inner call. When control returns to the outer call and its own `AfterBalanceChange` runs, its window `events[outerPrevEventsLen:]` still includes those same inner-call events (since indices are never advanced/consumed, only read), causing the outer handler to re-apply `AddBalance`/`SubBalance` deltas that were already applied by the inner handler.

### Impact Explanation
Re-application of `AddBalance`/`SubBalance` deltas duplicates or erases native-coin balance changes on the EVM `StateDB` relative to the actual `x/bank` ledger, i.e., an unauthorized duplication or corruption of spendable value between the native bank balances and their EVM-visible representation — the exact "keep balances... consistent across recursive execution" invariant called out for the `x/vm` statedb/journal path. Depending on event direction (spent vs received) this can either mint phantom EVM-visible balance (attacker can spend value never actually escrowed/backed by bank state) or destroy balance (funds become inconsistent/frozen relative to bank truth), both of which map to the Critical impact gate (unauthorized duplication/accounting corruption of spendable value, or unauthorized extraction/freezing of funds).

### Likelihood Explanation
Reachability depends on whether an unprivileged user can force one precompile's native action to trigger another precompile call (or a re-entry into the same precompile) within the same top-level EVM call before the outer `AfterBalanceChange` executes. The repository's own recursion test suite (`evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`, `evmd/tests/integration/balance_handler/balance_handler_test.go`) confirms that recursive precompile-call chains involving distribution/staking/bank precompiles are an exercised, real code path in this system (via contract-level `_beforeTokenTransfer` hooks calling back into precompiles, and ICS20 transfer callbacks) [8](#0-7) . This strongly indicates the trigger surface (recursive/nested precompile calls from ordinary contract code) is genuinely reachable by unprivileged callers; however, I could not fully verify from the indexed code alone whether, in the *current* per-call-factory implementation, the specific overlapping-event-window double-application still produces an exploitable discrepancy in all precompile combinations, or whether some other guard (e.g., event slice truncation, per-call isolated context) elsewhere fully neutralizes it. This uncertainty should be resolved by a Devin session with full repository access and the ability to run the existing `balance_handler_test.go`/`ics20_recursive_precompile_calls_test.go` suites (and variants using the production `BalanceHandlerFactory`, not just the `debug` test precompile) to confirm whether balances diverge after nested calls.

### Recommendation
Make balance-event reconciliation robust to nesting: either (a) truncate/consume the event slice as it is processed so no two handlers can read overlapping windows, (b) track a monotonic global cursor on the shared event log rather than a per-handler snapshot length, or (c) perform the bank-event-to-stateDB reconciliation directly against the coin deltas returned by `SendCoins`/`MsgServer.Send` rather than by re-parsing the shared event manager, eliminating index-based cache invalidation entirely — directly mirroring the Arcadia fix of validating post-state rather than trusting a value cached before an intervening external/nested call.

### Proof of Concept
A minimal reproduction path (already partially scaffolded in-repo) is:
1. Deploy a contract exposing a `_beforeTokenTransfer`/callback hook that, mid-transfer, invokes a second precompile call (as done in `contracts/solidity/ERC20RecursiveNonRevertingPrecompileCall.sol`'s `claimRewards()` calling the distribution precompile mid-`_beforeTokenTransfer`) [9](#0-8) .
2. Trigger a transfer that causes bank `SendCoins` events to be emitted by an outer precompile call, then reenters another precompile (or the same one) before the outer `AfterBalanceChange` runs, as exercised by `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` [10](#0-9) .
3. Compare `bankKeeper.GetBalance` (ground truth) against `evmKeeper.GetBalance`/StateDB balance after the transaction to confirm divergence — mirroring the existing `balance_handler_test.go` methodology which already asserts on event counts as a proxy for this desync [11](#0-10) .

Full confirmation that this divergence still manifests in the production `BalanceHandlerFactory` path (rather than only the `debug` test precompile's shared-instance variant) requires running these tests with full repository/tooling access, which is beyond what static indexing can verify with certainty here.

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.Wrap(errors2.ErrUnauthorized, "could not create statedb in debug precompile")
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	err = stateDB.AddPrecompileFn(p.Address(), snapshot, events)
	if err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	// Start the balance change handler before executing the precompile.
	p.GetBalanceHandler().BeforeBalanceChange(ctx)
