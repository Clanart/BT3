Based on my investigation, I found a valid analog to the ExecuteSwap bug: the payout transaction's operator attribution mechanism relies entirely on unauthenticated OP_RETURN data that anyone can set, not on cryptographic proof that the named operator actually funded the payout.

### Title
Payout tx operator attribution via unsigned OP_RETURN allows crediting reimbursement to an operator who never fronted the withdrawal - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the on-chain payout transaction with an OP_RETURN output that simply encodes an `operator_xonly_pk` [1](#0-0) . This OP_RETURN byte string is never signed or cryptographically bound to the payer of the transaction. The user's signature only covers input 0 and output 0 via `SinglePlusAnyoneCanPay` [2](#0-1) , so any additional inputs (which fund the fee) and the OP_RETURN output are unauthenticated and can be freely substituted by whoever broadcasts the transaction. Verifiers later parse this OP_RETURN to decide which operator "paid" for the withdrawal [3](#0-2) , and this attribution is used to gate which operator is allowed to claim reimbursement [4](#0-3) [5](#0-4) .

### Finding Description
The binding that should hold is: `operator credited for reimbursement == party whose BTC actually funded the payout to the withdrawing user`. The payout transaction structure is:
- Input 0: user's withdrawal UTXO, signed by the user with `SIGHASH_SINGLE|ANYONECANPAY`
- Output 0: user's payout (covered by the signature)
- Additional input(s): fee-funding UTXO(s), added later via `fund_raw_transaction` [6](#0-5) 
- OP_RETURN output: raw bytes of an `operator_xonly_pk`, added by whoever assembles the final transaction, and NOT covered by the user's `SinglePlusAnyoneCanPay` signature.

Because `SinglePlusAnyoneCanPay` only commits to input 0 and output 0, an attacker (or any of the several operators racing to front the same withdrawal — see the concurrent-withdrawal test at `core/src/test/deposit_and_withdraw_e2e.rs:2091-2168`) can take the user-signed input/output, fund the transaction fee themselves via a *different* funding input, and place *any* `operator_xonly_pk` bytes in the OP_RETURN — including one belonging to a completely different operator who never funded anything.

`update_finalized_payouts` in `core/src/verifier.rs` blindly trusts this OP_RETURN content as "the payer" [7](#0-6) , and this value gates downstream reimbursement flow: `is_kickoff_malicious` treats a kickoff as valid only if `kickoff_data.operator_xonly_pk` matches this untrusted OP_RETURN value [8](#0-7) , and `send_asserts`/`validate_payer_is_operator` use the same DB-recorded "payer" to authorize an operator's reimbursement path [5](#0-4) [9](#0-8) .

This exactly parallels the ExecuteSwap flaw: a value-moving action (the swap / the payout) lacks a check binding the recorded party (token-from address / operator xonly pk) to the party that actually supplied the corresponding value (msg.value / the payout funding UTXO).

### Impact Explanation
If exploited, an operator (or any third party who observes the pending user-signed withdrawal input and races to complete it) can insert a *different, honest* operator's `xonly_pk` into the OP_RETURN of a payout they fund themselves. The verifier network will then record that honest operator as the "payer" for the withdrawal. When that honest operator later sends a kickoff for a different, legitimate deposit reimbursement, `is_kickoff_malicious`/`validate_payer_is_operator` binds its reimbursement eligibility to this falsely-recorded payout, which can starve the honest operator of the ability to claim its own reimbursement path (its kickoff windows/collateral tied to a payout it never made) or let the malicious broadcaster attempt to draft off legitimate infrastructure. This matches "an honest operator permanently unable to be reimbursed" from the rules' Critical impact list, and, at minimum, is an unauthenticated broadcasting/attribution issue that breaks the custody-binding required by the protocol.

### Likelihood Explanation
Likelihood is constrained by the fact that the attacker still must actually pay the user's withdrawal output in full (the `SIGHASH_SINGLE` output is fixed), so this is not a way to steal BTC directly — it is a mis-attribution/DoS vector against a *specific named operator*, requiring the attacker to front real capital equal to the withdrawal amount. Exploitation is straightforward for anyone who can observe an in-flight, user-signed withdrawal request (via the aggregator/operator RPC flow) and race to broadcast a variant with someone else's `xonly_pk` in the OP_RETURN before the legitimate operator's own payout confirms.

### Recommendation
Bind the OP_RETURN operator attribution to something the payer actually controls — e.g., require the payout transaction's *funding* input(s) to be spendable only by the claimed operator's key (so the operator's own signature authorizes the OP_RETURN content), or otherwise cryptographically tie the `operator_xonly_pk` claim to a signature made by that operator over the specific payout txid/outpoint before verifiers accept it as the recorded payer.

### Proof of Concept
1. User signs the withdrawal payout output/input with `SinglePlusAnyoneCanPay` off-chain as documented in `generate_withdrawal_transaction_and_signature` [10](#0-9) .
2. Attacker (or a racing operator) constructs a full transaction using this signed input/output, adds its own fee-funding input, and sets the OP_RETURN to Operator B's `xonly_pk` (not their own), then broadcasts it.
3. `update_finalized_payouts` parses the OP_RETURN and records Operator B as `payout_payer_operator_xonly_pk` for that withdrawal [11](#0-10) .
4. Operator B's subsequent kickoff for this deposit is checked against this falsely-recorded attribution in `is_kickoff_malicious`, potentially causing it to be treated as legitimate/malicious incorrectly, and `validate_payer_is_operator` gates Operator B's `get_reimbursement_txs` flow on this same falsified record [12](#0-11) , even though Operator B never funded the payout.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()

fn sign_withdrawal_output(
    config: &BridgeConfig,
    dust_utxo: &UTXO,
    withdrawal_address: &bitcoin::Address,
    withdrawal_amount: bitcoin::Amount,
) -> (bitcoin::TxOut, taproot::Signature) {
    let signer = Actor::new(config.secret_key, config.protocol_paramset().network);
    let txin = builder::transaction::input::SpendableTxIn::new(
        dust_utxo.outpoint,
        dust_utxo.txout.clone(),
        vec![],
        None,
    );
    let txout = bitcoin::TxOut {
        value: withdrawal_amount,
        script_pubkey: withdrawal_address.script_pubkey(),
    };
    let unspent_txout = builder::transaction::output::UnspentTxOut::from_partial(txout.clone());

    let tx = builder::transaction::TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            builder::transaction::DEFAULT_SEQUENCE,
        )
        .add_output(unspent_txout.clone())
        .finalize();

    let sighash = tx
        .calculate_sighash_txin(0, sighash::TapSighashType::SinglePlusAnyoneCanPay)
        .expect("Failed to calculate sighash");

    let sig = signer
        .sign_with_tweak_data(sighash, builder::sighash::TapTweakData::KeyPath(None), None)
        .expect("Failed to sign");

    let sig = taproot::Signature {
        signature: sig,
        sighash_type: sighash::TapSighashType::SinglePlusAnyoneCanPay,
    };

    (txout, sig)
}
