### Title
Unprivileged sender impersonates internal output classes (branch/change/forward) via script_pubkey-only scanning - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`Scanner` attributes every received output to an offset class purely by matching `output.script_pubkey` against a `HashMap<ScriptBuf, Scalar>` (mod.rs:199-214). Because Taproot script pubkeys are deterministic functions of the group key and publicly derivable offset scalars, anyone who observes the multisig's addresses can compute the branch/change/forward `script_pubkey`s and pay them directly. The scanner then reports a `ReceivedOutput` carrying the internal offset as if the protocol itself had produced that output. This is the Serai analog of hardware-address impersonation: an unauthenticated party crafts inputs that are accepted under an identity (output class) they do not legitimately hold.

### Finding Description
`Scanner::new`/`register_offset` populate `self.scripts` keyed only by `ScriptBuf` (mod.rs:155, 185-190). `scan_transaction` performs `self.scripts.get(&output.script_pubkey)` and emits a `ReceivedOutput` with the registered offset for *any* transaction output paying to that script, with no check of provenance (mod.rs:205-210).

The offsets are not secret. In the downstream consumer (`processor/src/networks/bitcoin.rs`, out of scope but showing intended usage), `BRANCH_OFFSET`, `CHANGE_OFFSET`, and `FORWARD_OFFSET` are computed as `Secp256k1::hash_to_F(KEY_DST, b"branch" | b"change" | b"forward")` with the public constant `KEY_DST = b"Serai Bitcoin Output Offset"`. Given the (public) group key `key`, anyone computes `p2tr_script_buf(key + G*offset)` — modulo the documented even-Y increment in `register_offset` — and obtains the exact script the scanner watches for.

When such a payment is scanned, the caller (`processor` `get_outputs`) classifies it via `kinds[offset]` as `OutputType::Branch` / `OutputType::Change` / `OutputType::Forwarded`. An attacker therefore:

- impersonates a **Forwarded** output — downstream logic treats attacker dust as a deposit requiring forwarding, causing the threshold multisig to produce `SignableTransaction`s and sign spends it never should have made (fee drain: the forwarding transaction costs more in fees than the dust is worth);
- impersonates a **Change** output — an output is reported as protocol-created change that the protocol never constructed, corrupting the change-output accounting model that assumes a change-class output corresponds to a prior spend;
- impersonates a **Branch** output similarly.

Additionally, `TransactionSignMachine::sign` indexes signer-supplied preprocess vectors via `commitments[c]` (send.rs:364-369); a participant supplying a shorter vector triggers a panic — reachable but only a DoS from a signing participant.

### Impact Explanation
An unprivileged network party (anyone able to broadcast a Bitcoin transaction) can force the scanner to emit outputs misattributed to internal offset classes. The concrete, in-scope consequence chain is: attacker sends dust to the forward/change script → `ReceivedOutput` emitted with the internal offset → downstream treats it as authentic protocol output → `SignableTransaction`/`multisig` (send.rs:273-285) happily accepts it since `keys.offset(offset)` yields the correct spending key → the multisig signs an unintended transaction, paying fees out of real funds to move attacker-controlled dust. Impact is bounded (fee loss, accounting confusion, no key/share recovery), hence Medium rather than High.

### Likelihood Explanation
High reachability: requires only a standard Bitcoin payment to a publicly computable address; no cryptographic break needed. Exploitation cost is one dust-sized UTXO per attempt. However, the attacker gains nothing directly except forcing fee expenditure and bookkeeping corruption, which tempers severity.

### Recommendation
`Scanner`/`ReceivedOutput` cannot prevent payments to public scripts, so the distinction must be made by the consumer: outputs classified as `Change` (and arguably `Forwarded`) should only be accepted when they appear in transactions the protocol itself created (e.g., match `tx.compute_txid()`/vout against records of broadcast transactions), rather than trusting `script_pubkey` equivalence alone. Document on `Scanner` that `scan_transaction` reports *any* payment to a registered script and that internal-class outputs require provenance checks.

### Proof of Concept
```rust
// Attacker knows the multisig group key (public) and the public offset constants.
// Reproduce the internal offsets used by processor::scanner():
let branch  = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch");
let change  = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change");
let forward = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward");

// Compute the exact script_pubkey the Scanner watches for (incrementing the
// offset until p2tr_script_buf returns Some, mirroring register_offset).
fn script_for(key: ProjectivePoint, mut offset: Scalar) -> ScriptBuf {
    loop {
        if let Some(s) = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * offset)) {
            return s;
        }
        offset += Scalar::ONE;
    }
}

// Attacker broadcasts a transaction paying dust to, e.g., the forward script:
//   TxOut { value: Amount::from_sat(546), script_pubkey: script_for(key, forward) }
//
// Scanner::scan_transaction (mod.rs:199-214) emits:
//   ReceivedOutput { offset: forward_offset, output, outpoint }
//
// Downstream get_outputs classifies it as OutputType::Forwarded, and the
// multisig proceeds to sign a forwarding spend — an unintended signature —
// funded by protocol fees, even though no forward was ever requested.
```

Evidence: `Scanner` keyed solely by `ScriptBuf` and matched with no provenance check (`mod.rs:155, 185-190, 205-210`); offsets publicly derivable (`processor/src/networks/bitcoin.rs:308-344`); the spoofed output is trivially spendable by the multisig via `keys.offset(offset)` (`send.rs:273-285`), so the "funds" are accepted as genuine internal outputs.
