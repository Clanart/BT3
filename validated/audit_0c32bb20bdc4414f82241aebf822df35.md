### Title
Unchecked u64 accumulation overflow in payment/input sums bypasses the insufficient-funds check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums attacker-influenced `u64` amounts with `Iterator::sum` and plain `+`, which silently wraps in release builds. A wrapped `payment_sat` defeats the `NotEnoughFunds` check, producing (and subsequently threshold-signing) a Bitcoin transaction whose outputs exceed its inputs — an invalid transaction that can never confirm.

### Finding Description
The upstream bug class is an unchecked accumulator that can overflow when incremented by attacker-influenced amounts (`records[beneficiary].claimed += claimableAmount`). The analogous shape in Serai's in-scope code is the satoshi accounting in `SignableTransaction::new`:

- `input_sat` accumulates each `ReceivedOutput`'s value via `.sum::<u64>()` (`networks/bitcoin/src/wallet/send.rs:175`).
- `payment_sat` accumulates each caller-supplied payment amount via `.sum::<u64>()` (`send.rs:187`).
- The funds check computes `payment_sat + needed_fee` with a plain `u64` addition (`send.rs:215`).

Each individual output is serialized via `Amount::from_sat(payment.1)` (`send.rs:190`), so every payment value is independently a valid `u64` — but their *sum* is unchecked. With enough large payments, `payment_sat` wraps to a small residue, `input_sat < payment_sat + needed_fee` evaluates false, and `NotEnoughFunds` is bypassed. The same wrap applies to `fee_per_vbyte * vbytes` (`send.rs:206`) and to `payment_sat + fee_with_change` in the change branch (`send.rs:228`).

The resulting `SignableTransaction` is then passed to `multisig()` (`send.rs:273`) and each input's sighash is signed via `taproot_key_spend_signature_hash` (`send.rs:386`), so the threshold group produces signatures for a transaction Bitcoin consensus will reject (output value > input value).

`SignableTransaction::fee()` (`send.rs:139`) has the twin bug: `sum(inputs) - sum(outputs)` subtracts with plain `-` on `u64` and wraps rather than reporting a negative fee.

### Impact Explanation
The coordinator/processor constructs payments from scheduled withdrawals, i.e. data ultimately driven by untrusted withdrawal requests. If crafted payments drive the sum over `u64::MAX`, the node signs a transaction that is permanently unconfirmable. Any downstream logic treating the broadcast txid as a fulfilled payment would report funds sent that can never arrive, and the inputs are effectively locked until the plan is discarded — the same "incorrect accounting" consequence as the reference finding. At minimum this is a signing of an unintended (invalid) transaction: the signers' intent bound to the sighash was "spend inputs covering these payments," which the arithmetic wrap falsified.

### Likelihood Explanation
Triggering requires sum(payments) or the wrapped check arithmetic to cross `u64::MAX` satoshis (~1.8e19 sats, ~1.8e11 BTC), which exceeds the Bitcoin money supply for pure value, but the multiplication `fee_per_vbyte * vbytes` (`send.rs:206`) and the change-path addition can wrap with far smaller inputs if `fee_per_vbyte` is attacker-influenced, and the bug needs only one malicious payment set in the payment queue. Reachability is constrained to whoever can inject payments into the plan, making this a Medium rather than High.

### Recommendation
Use `checked_add`/`checked_sub`/`checked_mul` (or `u128` accumulators) for `input_sat`, `payment_sat`, `needed_fee`, the change-branch `payment_sat + fee_with_change`, and `fee()`. Reject with `NotEnoughFunds`/`TooLowFee` on any overflow instead of wrapping, mirroring the upstream recommendation for range-checked accumulation.

### Proof of Concept
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

```rust
let input_sat: u64 = /* e.g. */ 1_000_000;
let payments = vec![(script_a, u64::MAX - 10), (script_b, 1_000u64)];
let payment_sat = payments.iter().map(|p| p.1).sum::<u64>();
// release build: payment_sat wraps to 989
assert!(input_sat < payment_sat + needed_fee); // check bypassed -> no NotEnoughFunds
```

The function then emits two `TxOut`s totaling ~`u64::MAX` sats against `1_000_000` sats of inputs, `multisig()` accepts the offsets, `sign()` produces valid BIP-340 shares for `Prevouts::All` sighashes, and `complete()` returns a fully-signed transaction that Bitcoin Core rejects with `bad-txns-in-belowout`. `fee()` on the same object wraps to a huge `u64` rather than reporting the negative fee.
