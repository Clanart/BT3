## Analysis

The external report's core primitive — an unauthenticated, unrestricted arbitrary-call executor whose *own* address can be pre-loaded with a persistent ERC20/ERC777 approval by an attacker, then drained when a victim's tokens later pass through that same shared execution context — has a direct, local analog in Hyperbridge's `CallDispatcher`.

`CallDispatcher.dispatch()` is a plain `external` function with **no access control and no reentrancy guard**, executing an attacker-supplied `Call[]` with the dispatcher itself as `msg.sender`: [1](#0-0) 

This single `CallDispatcher` instance is shared across all apps and all orders — `IntentGatewayV2` references it via `_params.dispatcher` for both predispatch and postdispatch execution, and it repeatedly receives, holds, and forwards tokens belonging to unrelated orders/users in the same call: [2](#0-1) [3](#0-2) 

The documentation itself confirms the dispatcher is intended to *hold tokens temporarily during execution* and recommends (as a mitigation that depends on user diligence, not a contract-enforced guarantee) using exact approvals rather than unlimited ones — implicitly acknowledging the dispatcher's approval state persists beyond a single call: [4](#0-3) 

Because `dispatch()` has no caller restriction, anyone can invoke it directly (not only via `IntentGatewayV2`/HFT flows) to plant an `approve(attacker, type(uint256).max)` call on any ERC20 (including ERC777-compatible) token from the `CallDispatcher`. This grants a durable, standing allowance that is never revoked by the protocol. Any subsequent transaction — from any other user's `placeOrder`/`fillOrder` predispatch/postdispatch flow, or an HFT `send()` with `to = CallDispatcher` — that causes the dispatcher to (even momentarily, or as unswept "dust") hold a balance of that token is then drainable by the attacker via a plain `token.transferFrom(dispatcher, attacker, amount)`, or — mirroring the report's ERC777 vector exactly — via a `tokensReceived` reentrant hook fired the instant tokens land on the dispatcher mid another user's transaction, since `dispatch()` carries no reentrancy lock.

The sweep logic that is supposed to clear residual balances only sweeps tokens explicitly listed in `order.output.assets` / `order.inputs` for the *current* order: [5](#0-4) 

Any token balance left on the dispatcher that isn't part of that specific order's listed token set (e.g., an intermediate routing token from a multi-hop swap, or dust from a different app's flow) is never swept and remains permanently exposed to any address holding a pre-planted approval.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows an attacker to plant persistent token approvals and drain funds that transit the shared dispatcher via other users' orders - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` executes arbitrary attacker-supplied calls with no caller restriction and no reentrancy guard, and the same `CallDispatcher` instance is reused across all `IntentGatewayV2` orders (and other apps such as `HyperFungibleToken`) as a temporary holder of user funds during predispatch/postdispatch execution and calldata-driven bridging.

### Finding Description
Because `dispatch()` is `external` with no `onlyGateway`/caller check, any address can call it directly to make the `CallDispatcher` itself execute `token.approve(attacker, type(uint256).max)` for an arbitrary ERC20/ERC777 token. This is not a call made *through* an order — it requires no escrow, no order placement, and no interaction with `IntentGatewayV2` at all. The resulting allowance is stored in the token contract, keyed by the fixed, shared `CallDispatcher` address, and persists indefinitely.

Because the same `CallDispatcher` is the designated temporary holder for:
- `predispatch.assets` transferred in during `placeOrder` before being swept back per `order.inputs`,
- `order.output.call` execution during fills, swept only per `order.output.assets`,
- HFT/WrappedHFT `send()` flows that mint/unlock tokens directly to the dispatcher for calldata execution,

any token balance that lands on the dispatcher outside the specific token list an order's sweep logic checks for (e.g., an intermediate token from a multi-hop postdispatch swap, or any dust not accounted for) is retrievable by the attacker using the pre-planted approval — with no relation to whose order caused the balance to appear. For ERC777-class tokens, the attacker does not even need to wait: a `tokensReceived` hook registered via ERC1820 fires synchronously the moment any other user's order transfers that token into the dispatcher, and since `dispatch()` has no reentrancy guard, the attacker's hook can reenter `CallDispatcher.dispatch()` to `transferFrom` the dispatcher's current balance to themselves before the victim transaction's own sweep/forward call executes.

### Impact Explanation
This allows an unprivileged attacker to steal tokens belonging to unrelated users/orders that transiently or persistently sit on the shared `CallDispatcher`, without compromising any relayer, prover, or admin key, and without needing a malicious peer. This is a direct fund-loss/theft vector matching the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories.

### Likelihood Explanation
The precondition (calling `dispatch()` with an `approve` call) is trivially available to anyone at any time since the function is unauthenticated — no order placement or privileged role is required. The victim-side trigger (any order/app routing a token that leaves dust, or any ERC777 transfer into the dispatcher) occurs routinely as part of normal predispatch/postdispatch composability that the protocol explicitly documents and tests (e.g., multi-step Uniswap swaps through the dispatcher).

### Recommendation
- Restrict `CallDispatcher.dispatch()` to authorized callers only (e.g., an `onlyAuthorized` modifier allowing only registered gateway/app contracts), or deploy a fresh, single-use dispatcher/proxy per order/transfer instead of a long-lived shared singleton.
- Add a reentrancy guard to `dispatch()`.
- After every use, explicitly revoke (`approve(_, 0)`) any allowances the dispatcher granted during that call, or forbid `approve` calls entirely from within `dispatch()`'s executed `Call[]` targeting tokens other than the one being swept in the same transaction.
- Sweep *all* token balances the dispatcher holds after each use (not just tokens present in `order.inputs`/`order.output.assets`), so no residual balance can persist across transactions.

### Proof of Concept
1. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: approve(attacker, type(uint256).max)})]))` directly — no order, no escrow, succeeds because `dispatch()` has no access control.
2. Later, any user places/fills an `IntentGatewayV2` order (or bridges via `HyperFungibleToken.send()`) whose predispatch/postdispatch calldata routes `token` through the dispatcher (e.g., a multi-hop swap leaving `token` as an untracked intermediate, or `token` implementing ERC777 with a `tokensReceived` hook registered by the attacker).
3. For the ERC777 case, the attacker's hook fires synchronously when `token` is transferred into the dispatcher mid-transaction; the attacker's hook calls `CallDispatcher.dispatch()` again with `token.transferFrom(dispatcher, attacker, dispatcher.balanceOf(token))`, executing before the victim transaction's own sweep/forward completes.
4. For the dust case, the attacker simply calls `token.transferFrom(dispatcher, attacker, amount)` in a later transaction once `token` balance accumulates on the dispatcher from any order whose sweep list doesn't include `token`. [1](#0-0)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
