### Title
Lock restriction in `AnkrBNBPoolHelper.withdraw()` is bypassable via direct `MasterMagpie.withdraw()` call - (File: wombat/AnkrBNBPoolHelper.sol)

### Summary
`AnkrBNBPoolHelper.withdraw()` enforces `unlockTime`/`lockedAmount[msg.sender]` only inside its own code path, after unstaking from `MasterMagpie` via `withdrawFor` [1](#0-0) . The locked user's position, however, is simply a normal balance in `MasterMagpie`'s `userInfo[stakingToken][user]` mapping, created by `depositFor` when `batchDepositLPFor` assigns `lockedAmount[_for[i]]` [2](#0-1) . Because `MasterMagpie` exposes a completely separate, unrestricted `withdraw(address _stakingToken, uint256 _amount)` entrypoint that any holder of that pool's staking token can call directly, a locked user can withdraw their staking/receipt token from `MasterMagpie` without ever going through `AnkrBNBPoolHelper.withdraw()`, and thus without the `unlockTime`/`lockedAmount` check ever being evaluated.

### Finding Description
`MasterMagpie.withdraw` is a plain external function, gated only by `whenNotPaused`/`nonReentrant`, that lets `msg.sender` withdraw their own `available` balance for any registered `_stakingToken` pool: [3](#0-2) . This is distinct from `withdrawFor`, which is restricted with `_onlyPoolHelper(_stakingToken)` and is the function `AnkrBNBPoolHelper._unstake` calls on behalf of the pool helper [4](#0-3) , [5](#0-4) .

A user whose funds were locked via `batchDepositLPFor` (which sets `lockedAmount[_for[i]] += amount` and then calls `depositFor` on `MasterMagpie`) still has a normal, unrestricted `available`/`amount` balance recorded under `userInfo[stakingToken][user]` in `MasterMagpie` [2](#0-1) . Nothing in `MasterMagpie` is aware of `AnkrBNBPoolHelper`'s `lockedAmount`/`unlockTime` state — that state lives only in the helper contract and is checked only inside the helper's own `withdraw()` function [6](#0-5) .

Consequently, the locked user can simply call `MasterMagpie.withdraw(stakingToken, amount)` directly, which internally calls `_withdraw` → `_harvestAndUnstake`, checks only `user.available < _amount` (no time-lock semantics at all), decrements the user's `amount`/`available`, and transfers the raw `stakingToken` (the WombatStaking receipt token) to the caller [7](#0-6) . This completely bypasses the "1-year lock compensation" mechanism the helper contract was designed to enforce, since the check at `AnkrBNBPoolHelper.sol:171` is never reached.

### Impact Explanation
This breaks the core invariant that the Ankr 1-year-lock compensation restricts early withdrawal of the compensation stake. A locked user can obtain the underlying receipt/staking token early via `MasterMagpie.withdraw()`, and from there redeem/trade/use that token outside of the intended lock window, defeating the purpose of the lock mechanism entirely. This is a fund-access-control bypass (early release of funds that were meant to remain locked), matching a Critical-severity "bypass of a security control leading to unauthorized access to locked funds" class of impact, though it is more precisely a lock-bypass than outright "theft from other users" — no other user's principal is directly stolen, but the attacker (a locked holder) can access funds they should not yet be entitled to.

### Likelihood Explanation
No special privileges are required: any address that received a locked deposit through `batchDepositLPFor` (called by `ankrOperator` on their behalf) can immediately call the standard, permissionless `MasterMagpie.withdraw()` function for the same `stakingToken` pool. No capital, flash loans, or complex sequencing are needed — it is a single direct call available at any time after the locked deposit is registered, and is fully repeatable per locked account.

### Recommendation
Move the lock enforcement into `MasterMagpie` itself (e.g., a per-user/per-pool "locked until" or "locked amount" field checked inside `_harvestAndUnstake`/`_withdraw`), or restrict the affected `stakingToken` pool so that `MasterMagpie.withdraw()` cannot be called directly for locked users (e.g., route ordinary withdrawals for this pool exclusively through `withdrawFor`, disabling the public `withdraw` path for pools that have an associated lock, or store `lockedAmount`/`unlockTime` in `MasterMagpie.userInfo` and check it in `_harvestAndUnstake`). A time-based restriction on a position must be enforced at the layer where the position's balance/state lives (`MasterMagpie`), not solely in an optional front-end contract (`AnkrBNBPoolHelper`).

### Proof of Concept
Hardhat test outline:
1. Deploy `MasterMagpie`, `WombatStaking`, `AnkrBNBPoolHelper` (with `unlockTime` set in the future), register the pool via `MasterMagpie.add(...)` with `helper = AnkrBNBPoolHelper` address.
2. As `ankrOperator`, call `batchDepositLPFor` to lock `amount` for `victim`/`attacker`, verifying `lockedAmount[attacker] == amount` and `MasterMagpie.stakingInfo(stakingToken, attacker)` shows the equivalent `available` balance.
3. From `attacker` (no special role), directly call `MasterMagpie.withdraw(stakingToken, amount)`.
4. Assert the call succeeds (no revert) and `attacker` receives `stakingToken` balance equal to `amount`, despite `block.timestamp < unlockTime`.
5. Assert that calling `AnkrBNBPoolHelper.withdraw(amount, minAmount)` in the same scenario (before unlock) reverts with `NotAllowed`, proving the lock is enforced only in the helper and is fully bypassed via `MasterMagpie.withdraw`.

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
