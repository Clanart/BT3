### Title
Path-based `safe.directory` trust exception is permanent and never revoked, letting an attacker who later controls the same path bypass Git's untrusted-repository protection - (File: `app/src/lib/git/config.ts`)

### Summary
Git's ownership-mismatch protection ("dubious ownership") is meant to stop Desktop from treating a directory owned by another user as trusted, because doing so can lead to automatic execution of repository-controlled content (hooks, filters, etc.). Desktop's "Trust Repository" flow permanently allow-lists the *path* in the user's global git config via `addSafeDirectory`, and never removes that allow-list entry — not when the repository is removed from Desktop, not when it goes missing, and not when its identity/ownership changes later. This mirrors the reported bug class exactly: a one-time "unlock" action (`unlock()` never resetting `unlockBlock`) leaves a security gate permanently open, except here the gate is "this filesystem path is trusted forever."

### Finding Description
When Desktop detects that a repository is "unsafe" (owned by a different user than the current process), it prompts the user to "Trust Repository". Accepting this calls `addSafeDirectory`, which appends the path to the global `safe.directory` config: [1](#0-0) 

This is invoked from both the "add existing repository" flow and the "missing repository" recovery flow: [2](#0-1) [3](#0-2) 

Once written, this exception is keyed purely on the filesystem *path string* (`safe.directory=<path>`), not on any repository identity (e.g., remote URL, first commit SHA, or a fingerprint of the `.git` directory). Git itself, and Desktop's own `getRepositoryType` check, will treat *anything* later found at that same path as trusted, regardless of whether it is still the repository the user originally reviewed: [4](#0-3) 

There is no corresponding "untrust"/"remove safe directory" call anywhere in the codebase — `removeConfigValue`/`removeGlobalConfigValue` exist generically in `config.ts` but are never wired to the repository-removal (`removeRepository`) or missing-repository flows. So the exception is written once and persists in the user's global `~/.gitconfig` indefinitely, exactly analogous to `unlockBlock` never being reset to `0` after `withdraw()`.

### Impact Explanation
This breaks the invariant Git's ownership check is designed to enforce: "only execute repository-controlled logic (hooks, `core.fsmonitor`, filters configured via `.git/config`, submodule commands, etc.) for paths whose ownership/trust has been explicitly and *currently* verified." Because the trust decision is bound to a path rather than to the specific repository content reviewed at the time of the decision, any later attacker who can place a different Git repository at that same path (e.g., a shared/synced folder, a container mount, a multi-user workstation, or simply a path Desktop reuses after the user removes and reclones/relocates a repo) inherits full trust with no re-prompt. That can lead to automatic execution of attacker-controlled repository content the next time Desktop or the user's git operations touch that path — satisfying the "code execution via attacker-controlled cloned/fetched repository" impact category.

### Likelihood Explanation
Requires the specific, but realistic, sequence: (1) the user legitimately trusts a path once (already anticipated flow, not requiring unnatural steps), (2) that same path is later reused by different repository content under attacker control (plausible on shared machines, network drives, CI/build directories reused by Desktop's "clone again" or "relocate" flows, or simply cloning at a path where a prior, now-removed, unsafe repo was trusted). No admin rights, malware, or leaked credentials are needed — the only "special" precondition is a reused path, which is a normal filesystem event, not an attack requiring physical/local privileged access.

### Recommendation
Do not rely solely on a path-keyed, permanent global `safe.directory` entry:
- Re-validate repository identity (e.g., remote URL / initial commit) whenever a trusted path is reopened, and re-prompt if the content at the path appears to have changed.
- Remove the `safe.directory` exception when the corresponding repository is removed from Desktop (`removeRepository`) or when the user explicitly untrusts it, mirroring how `withdraw()` should reset `unlockBlock` to `0`.
- Consider scoping trust decisions more narrowly (e.g., tie to a hash of `.git` metadata) rather than a mutable filesystem path.

### Proof of Concept
1. On a shared/multi-user path (or any path Desktop will reuse, such as via "Clone Again" after removing a repo), clone/open a benign repo `R1` owned by another OS user; Desktop flags it "unsafe" per `getRepositoryType`.
2. User clicks "Trust Repository" → `onTrustDirectory` → `addSafeDirectory(path)` writes `safe.directory=<path>` to the global gitconfig permanently. [5](#0-4) 
3. User later removes `R1` from Desktop (no code path clears the `safe.directory` entry).
4. Attacker (or the user unknowingly) places a different, attacker-controlled repository `R2` at the exact same path (e.g., re-clone target, shared mount reused, CI workspace path reuse).
5. Desktop's `getRepositoryType(path)` no longer reports `unsafe` for `R2`, because the global config exception matches on path only — no new trust prompt is shown, and any hooks/config in `R2` are treated as already vetted.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```
