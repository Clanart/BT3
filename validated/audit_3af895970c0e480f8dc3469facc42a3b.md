### Title
`ReceivedOutput::read` accepts an arbitrary `TxOut`/`offset` pair without verifying the script corresponds to the scanned key — unspendable outputs reported as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class is "inconsistent/unchecked success signalling on external calls": the Buffer issue was that `transfer`/`approve` return values were either unchecked or checked in a way incompatible with some tokens, causing failed operations to be treated as successful (and vice versa). The Serai analog lives in deserialization of externally supplied data: `ReceivedOutput::read` treats the three fields (`offset`, `TxOut`, `OutPoint`) as self-consistent evidence of a received payment, but performs no semantic validation whatsoever — it never checks that `output.script_pubkey` is even a P2TR output, nor that it equals `p2tr_script_buf(key + G * offset)`. Like the ZRX case in the report (a `false` return silently accepted), a malformed/mismatched `ReceivedOutput` is silently accepted as a spendable receipt.

### Finding Description
`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) parses:
- `offset` via `Secp256k1::read_F` — any scalar, unchecked against anything;
- `output` via `TxOut::consensus_decode` — any script_pubkey, including non-P2TR scripts the wallet can never sign for;
- `outpoint` via `OutPoint::consensus_decode` — any txid/vout pair.

None of the three fields are cross-validated. The invariant that makes a `ReceivedOutput` meaningful — `output.script_pubkey == p2tr_script_buf(group_key + G * offset)` for a `scripts`-registered offset — is only ever established inside `Scanner::scan_transaction` (mod.rs:199-214), which constructs `ReceivedOutput`s itself and therefore guarantees consistency. `read` bypasses `Scanner` entirely: it re-derives nothing and re-checks nothing, so bytes which were never produced by `scan_transaction` deserialize "successfully" into a semantically invalid object. There is also no check that `script_pubkey.is_p2tr()` or that the embedded x-only key lifts to the expected point (contrast `Output::<Bitcoin>::key` in processor/src/networks/bitcoin.rs:112-122, which *does* re-derive `key + G*offset` from the script — proving the codebase knows this invariant must hold, and `assert!(script.is_p2tr())` panics when it doesn't).

### Impact Explanation
A `ReceivedOutput` deserialized from attacker-controlled bytes claiming e.g. `offset = 0` with a script paying `key + G*5`, or a non-P2TR script, will be treated by downstream code as a confirmed, spendable input. When a `SignableTransaction`/signing plan is built over it, the produced Schnorr signature corresponds to `key + offset`, which does not match the output's actual locking key — the input is unspendable, and any batch/plan containing it fails or produces an invalid transaction. This matches the report's "impact type 1": the failure passes unnoticed at the boundary and surfaces only as unspendable "received" funds — i.e., funds reported received that are not spendable.

### Likelihood Explanation
`ReceivedOutput::read` is explicitly a sink for untrusted serialized bytes (it round-trips through `serialize()`/`write()` onto the wire and disk, and is reachable wherever a peer or stored record supplies an output claim rather than the node scanning the chain itself). An unprivileged counterparty able to supply or corrupt such bytes can inject an inconsistent output at negligible cost — no key material or collusion required. Reachability depends on a caller trusting `ReceivedOutput::read` output without re-scanning the chain, which is the design assumption encoded by exposing `read` as a public constructor-equivalent.

### Recommendation
Either make `ReceivedOutput` construction private (remove/deprecate the public `read`, or have `read` take the `Scanner`/`ProjectivePoint` and verify `self.scripts.get(&output.script_pubkey) == Some(&offset)`), or at minimum validate in `read`/at every consumption site that:
1. `output.script_pubkey.is_p2tr()` and its x-only key lifts to a valid point;
2. the script equals `p2tr_script_buf(key + G * offset)` for the intended key;
3. the outpoint references an output actually confirmed on-chain before the output enters scheduling.

The same "check the semantic result, not just decoding success" fix pattern as the report's SafeERC20 recommendation applies.

### Proof of Concept
```rust
// Attacker crafts bytes: offset = 0, but script_pubkey pays key + G*5 (or a non-P2TR script)
let mut buf = vec![];
buf.extend(Scalar::ZERO.to_bytes());                       // offset = 0
let fake = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: p2tr_script_buf(key + ProjectivePoint::GENERATOR * Scalar::from(5u64)).unwrap(),
  // or: ScriptBuf::new_p2pkh(...) — anything consensus-decodable
};
buf.extend(serialize(&fake));
buf.extend(serialize(&OutPoint::new(real_txid, 0)));        // any outpoint

// ReceivedOutput::read accepts it without complaint — no scanner consistency check
let ro = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // succeeds
// ro is now indistinguishable from a genuinely scanned output; signing for it
// produces a BIP-340 signature under `key + 0`, which cannot unlock `key + G*5`'s script.
```
