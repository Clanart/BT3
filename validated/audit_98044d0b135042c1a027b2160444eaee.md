### Title
Unauthenticated broadcast of a payout-shaped transaction lets anyone frame an arbitrary operator as payer, causing reimbursement for a payout it never funded - ([File: core/src/verifier.rs])

### Summary
The user's `SinglePlusAnyoneCanPay` (S+AP) signature only commits to the withdrawal input and the single payout output; every other part of the transaction — extra fee inputs, the anchor output, and critically the OP_RETURN carrying the "fronting operator" xonly pubkey — is completely unsigned. `update_finalized_payouts` in `core/src/verifier.rs` trusts the OP_RETURN bytes of *whatever transaction first spends the withdrawal UTXO* as the identity of the fronting operator, with no check that this party is the operator, holds any key, or is even a gRPC-authenticated caller. Anyone possessing the S+AP signature (e.g., the withdrawer themselves) can construct and broadcast their own transaction embedding an arbitrary (real) operator's xonly pubkey, causing that operator's node to autonomously believe it fronted the payout and proceed to claim reimbursement it never earned.

### Finding Description
The broken binding: `withdrawals.payout_payer_operator_xonly_pk` (as recorded by `update_finalized_payouts`) should equal the xonly pubkey of the party that the protocol authorized to submit the payout via `Operator::withdraw`/`Aggregator::withdraw` (i.e., an operator who actually spent its own funds to front the withdrawal). In reality it equals whatever pubkey bytes appear in the OP_RETURN of the first transaction observed on-chain spending the registered `withdrawal_utxo`.

Trace:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds a payout tx with input 0 = withdrawal UTXO (key-spend with the user's S+AP sig), output 0 = user payout (committed by the sighash), output 1 = anchor, output 2 = OP_RETURN(`operator_xonly_pk`).
- `Operator::withdraw` (`core/src/operator.rs:560-637`) verifies the user's signature only against `sighash = calculate_sighash_txin(0, SinglePlusAnyoneCanPay)`. Because the sighash type is `SinglePlusAnyoneCanPay`, it only commits to input 0 and output 0 — the fee inputs, anchor output, and OP_RETURN output are unsigned and freely choosable by anyone in possession of the signature.
- Any party (including the withdrawer who legitimately created this signature themselves via `Aggregator::withdraw`/`WithdrawParams.input_signature`) can independently build a transaction reusing this exact signature: their own fee-paying inputs, the same signed output 0, and an OP_RETURN of their choosing — including a real, currently-registered operator's public xonly pubkey — then broadcast it directly to the Bitcoin network via any node, with no gRPC call to any Clementine entity.
- `bitcoin_syncer`/`Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) picks up the first tx spending the tracked withdrawal UTXO, extracts the OP_RETURN via `get_first_op_return_output`/`parse_op_return_data`, and unconditionally writes it as `payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`) — with no signature check tying that pubkey to the actual broadcaster.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) on the framed operator's own node polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and, finding this attacker-attributed row, calls `Operator::handle_finalized_payout` (`core/src/operator.rs:839-...`), which allocates a kickoff connector and proceeds toward reimbursement — entirely automatically, without ever having called `Operator::withdraw`.
- Even without automation, `Operator::get_reimbursement_txs` → `validate_payer_is_operator` (`core/src/operator.rs:1686-1740`) only checks that the DB-recorded `payer_xonly_pk == self.signer.xonly_public_key`; it performs no check that the operator itself broadcast or funded the payout transaction.
- `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) only checks that the DB-recorded `operator_xonly_pk` matches `kickoff_data.operator_xonly_pk` and that the committed blockhash matches — both trivially satisfied since they derive from the same unauthenticated DB value. No guard anywhere validates that the named operator's own key or funds were actually involved in the payout transaction.

### Impact Explanation
This lets an unprivileged party (the withdrawer, using a signature they legitimately obtained for their own withdrawal) name any real operator as the fronting party, causing that operator's automation (or manual reimbursement flow) to claim a kickoff/reimbursement cycle for a payout it never funded. This directly matches the Critical category "an operator reimbursed for a payout it never funded": the bridge's move-to-vault UTXO for this deposit is ultimately spent to reimburse an operator who put up no capital, while the withdrawer already paid themselves using their own funds. The attack is repeatable for every withdrawal and against any operator whose xonly pubkey is publicly known (operator pubkeys are not secret; they are shared, e.g. via `operator_xonly_pks` in withdraw requests). Blast radius: every deposit/withdrawal pair and every registered operator.

### Likelihood Explanation
The attacker only needs to be a normal withdrawer: deposit, call Citrea `withdraw`, obtain/construct the S+AP signature over their own withdrawal output (which they can do unilaterally, since it's their own signature over their own intended payout), then build and broadcast a transaction with extra self-funded fee inputs and an OP_RETURN naming a target operator's public xonly pubkey. No aggregator/operator/verifier gRPC call, no key compromise, and no elevated privilege is required — only normal Bitcoin fee costs to pay for the transaction's confirmation, which is small and fully reusable at scale (repeatable per withdrawal).

### Recommendation
Do not derive payer attribution solely from an unauthenticated OP_RETURN. Either require the payout transaction's fee-paying inputs/witness to include a verifiable commitment/signature from the named operator (e.g., an operator signature over the whole transaction or a separate attestation channel), or otherwise cross-check that the operator actually initiated/funded the broadcast (e.g., via an operator-signed record created at `Operator::withdraw` time and matched against the on-chain payout before crediting `payout_payer_operator_xonly_pk`), before allowing `handle_finalized_payout`/`get_reimbursement_txs` to proceed to kickoff/reimbursement for that operator.

### Proof of Concept
`cargo test` under `core/src/test`:
1. Run a normal deposit + withdrawal registration (as in `deposit_and_withdraw_e2e.rs`), generating `withdrawal_utxo`, `payout_txout`, and the user's S+AP `sig`.
2. Do NOT call `Operator::withdraw`/`Aggregator::withdraw`. Instead, manually construct a transaction: input 0 = `withdrawal_utxo` with witness = `sig`; output 0 = exact signed `payout_txout`; add an attacker-controlled funding input/output for fees; add an OP_RETURN output containing `operator0`'s real xonly pubkey (from `actors.get_operator_client_by_index(0)`'s known pubkey).
3. Broadcast this transaction directly via `rpc.send_raw_transaction`, mine to finality.
4. Assert `db.get_payout_info_from_move_txid(...)` returns `payout_payer_operator_xonly_pk == operator0_xonly_pk` and `payout_txid == attacker_tx.compute_txid()`, even though `Operator::withdraw` was never invoked for operator0.
5. Assert `operator0.get_reimbursement_txs(deposit_outpoint)` (or the `PayoutCheckerTask`) succeeds and returns a Kickoff transaction, demonstrating operator0 proceeding toward reimbursement for a payout it never funded.
