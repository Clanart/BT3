## Finding: Relayer reward misattribution via batch consensus-message reward aggregation

### Title
Consensus-incentive reward theft: `on_executed` attributes the entire batch's height-advance reward to the signer of message[0] only - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::FeeHandler::on_executed` computes relayer rewards from the *globally persisted* `latest_commitment_height` after an entire batch of messages has been applied, but attributes the *whole* reward to whichever account signed `messages[0]`. This is the same bug class as the reported `Goldilocks._getProposalState()` issue: a payout/state decision is derived from a value that mutates as a side effect of the very same call (or of other actors' work), rather than being bound to the specific unit of work the caller performed.

### Finding Description
In `on_executed` [1](#0-0) , the relayer credited for the *whole* batch is derived only from `messages[0]`:

```rust
let maybe_relayer_account = messages.get(0).and_then(|first_message| {
    if let Message::Consensus(consensus_msg) = &first_message.message {
        ...decode signer of message[0]...
    } else { None }
});
```

But the reward amount is computed from **every** `StateMachineUpdated` event produced by the **entire** batch, collapsed to the single highest height per state machine: [2](#0-1) 

`calculate_reward` then reads the *current, global* `latest_commitment_height` (not anything tied to `messages[0]`'s own proof) and diffs it against the persisted watermark `LastRewardedHeight`: [3](#0-2) 

Because `latest_commitment_height` is a chain-wide value that advances from *any* consensus message processed in the batch — not just the one belonging to the credited signer — the reward paid to `messages[0]`'s signer is sized by the total height span the whole batch advanced, exactly like `totalSupply` in the original report being a live, externally-mutable quantity that a state-transition function trusted as if it were locally scoped.

### Impact Explanation
An unprivileged relayer can bundle their own trivial/self-signed `Message::Consensus` as `messages[0]` alongside one or more substantive consensus proofs (contributed by other messages in the same extrinsic/batch — consensus/finality proofs are public data, not privileged secrets) and collect the **entire** treasury payout (`T::Currency::transfer` from `TreasuryAccount` plus `ReputationAsset::mint_into`) for height-span work that was actually verified by other messages in the batch: [4](#0-3) 

This is a direct "wrong beneficiary" fund-diversion from the Hyperbridge treasury: the honest relayer who supplied the substantive proof gets nothing (their own `LastRewardedHeight` watermark is now advanced past their work by the attacker's claim), while the attacker collects BRIDGE plus reputation tokens for negligible/no verification effort of their own.

### Likelihood Explanation
The pallet's own comment acknowledges that a single call to `on_executed` can legitimately contain "multiple `StateMachineUpdated` events for the same `state_machine_id`" within one batch [5](#0-4) , confirming multi-message batches are a normal, reachable code path — not a hypothetical edge case. Constructing such a batch requires no special privilege, key, or relayer trust assumption: only that the attacker can include an additional valid `Message::Consensus` in the same submitted set as their own trivially-signed message, which any permissionless message submitter can do.

### Recommendation
Bind the reward calculation to the specific message/proof credited to each signer instead of the mutable global `latest_commitment_height`:
- Track and reward per-message (or per-signer) height deltas rather than collapsing to one global watermark comparison paid to `messages[0]`'s signer.
- Extract the relayer/signer independently for every `Message::Consensus` in the batch and pay each the reward corresponding to the height span *their own* message actually advanced (verified before/after values captured at that message's own processing step, not read from shared mutable storage after the whole batch has executed).

### Proof of Concept
1. Prepare a batch/extrinsic containing two `Message::Consensus` items:
   - `messages[0]`: a message signed with the attacker's key, wrapping any consensus proof that the consensus client accepts without error (may be a no-op / minimal proof).
   - `messages[1..]`: a substantive, publicly-obtainable consensus proof (e.g., copied from another relayer's pending/broadcast submission) that legitimately advances `latest_commitment_height` for some `state_machine_id` by many blocks.
2. Submit the batch. `pallet_ismp` processes all messages, applying state machine commitment updates for every message, then calls `FeeHandler::on_executed(messages, events)`.
3. `on_executed` extracts `maybe_relayer_account` solely from `messages[0]` (the attacker) at [6](#0-5) .
4. It aggregates `StateMachineUpdated` events across the **whole batch** into `highest_per_state_machine`, then calls `process_message`/`calculate_reward` using the post-batch `latest_commitment_height` versus `LastRewardedHeight` watermark.
5. The full reward for the entire height span (attacker's message + the other message(s)) is transferred to the attacker's account and reputation is minted to them, while `LastRewardedHeight` is advanced so the actual proof contributor can never claim that span.
