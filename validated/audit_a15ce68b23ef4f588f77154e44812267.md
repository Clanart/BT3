## Analysis

The ZENO report's root cause is a **precision/scaling arithmetic bug in a value used for a security-critical financial decision** — an inexact numeric representation used where an exact one was required. Searching Agave for the equivalent class of bug (inexact arithmetic used for a critical fund/consensus-safety decision) surfaces the stake-threshold percentage checks in the legacy Tower consensus code, which still use raw `f64` division/multiplication instead of the exact `Fraction` type Agave itself introduced (and documents as fixing this exact defect) for the Alpenglow path. [1](#0-0) [2](#0-1) 

Agave's own test explicitly proves that `stake as f64 / total_stake.get() as f64` at realistic stake magnitudes (`10^17`-scale, i.e., lamport-denominated total network stake) can round to the **wrong side of an exact percentage boundary** (`60_000_000_000_000_001` / `100_000_000_000_000_000` — mathematically just over 60% — evaluates as `<= 0.6` in `f64`).

Meanwhile, the legacy (non-Alpenglow) Tower BFT threshold checks that gate safety-critical decisions still use the same unfixed pattern:

- `check_vote_stake_threshold` (vote lockout threshold, prevents voting for a slot without sufficient tower stake support): `let lockout = *fork_stake as f64 / total_stake as f64; ... lockout > threshold_size` [3](#0-2) 
- `make_check_switch_threshold_decision` (switch-fork safety proof, explicitly meant to prevent a network split where honest validators abandon a fork without enough proof that lockouts are safely broken elsewhere): `if (locked_out_stake as f64 / total_stake as f64) > SWITCH_FORK_THRESHOLD` [4](#0-3) [5](#0-4) 
- `VoteStakeTracker::add_vote_pubkey` (supermajority/optimistic-confirmation threshold crossing detection): `let threshold_stake = (total_stake as f64 * threshold) as u64;` [6](#0-5) 
- `CommitmentAggregationData::get_lockout_count` (confirmation-count/rooted commitment level): `if (sum as f64 / self.total_stake as f64) > minimum_stake_percentage` [7](#0-6) 

The switch-threshold comment in `core/src/consensus/fork_choice.rs` makes explicit why exactness matters here: an incorrect threshold decision that lets validators switch away from a fork without sufficient proof "the network halts because 90% of validators can't vote." [8](#0-7) 

None of these call sites use `checked_mul`/`u128` exact cross-multiplication the way `Fraction::cmp` does — they are the exact unfixed instance of the bug class Agave's own developers found necessary to patch for Alpenglow.

### Title
Floating-point precision loss in legacy Tower stake-threshold comparisons can misjudge safety-critical switch/vote/commitment thresholds - (File: `core/src/consensus.rs`, `core/src/consensus/vote_stake_tracker.rs`, `runtime/src/commitment.rs`)

### Summary
Several safety-critical stake-percentage threshold checks in the Tower BFT consensus path compute `stake_amount as f64 / total_stake as f64` (or the multiplicative inverse) and compare the result against a fixed threshold (`SWITCH_FORK_THRESHOLD`, `VOTE_THRESHOLD_SIZE`, arbitrary confirmation-count percentages). At the lamport-scale magnitudes involved in real total network stake (~10^17), `f64`'s 52-bit mantissa cannot exactly represent the ratio, and Agave's own test in `votor-messages/src/fraction.rs` demonstrates that a stake value that is mathematically *just above* a percentage boundary can be computed by `f64` division as being at or below it. This is precisely the class of defect in the ZENO report: using an inexact arithmetic representation for a value that must be exact for correctness of a fund/consensus decision.

### Finding Description
`Tower::check_vote_stake_threshold` and `Tower::make_check_switch_threshold_decision` both perform the comparison `some_stake as f64 / total_stake as f64 > threshold` where `threshold` is a fixed `f64` constant (`SWITCH_FORK_THRESHOLD`, `self.threshold_size`). [9](#0-8) [10](#0-9) 
`VoteStakeTracker::add_vote_pubkey` and `CommitmentAggregationData::get_lockout_count` perform the analogous multiplication/division for supermajority and confirmation-count thresholds. [11](#0-10) [12](#0-11) 

Total activated stake on mainnet is on the order of hundreds of millions of SOL, i.e. ~10^17-10^18 lamports — well beyond `f64`'s exact-integer range (`2^53 ≈ 9×10^15`). Agave's own regression test for the newly-introduced `Fraction` type proves that at this exact magnitude, `f64` division of a stake value that is mathematically 1 lamport over a 60% boundary rounds to `<= 0.6`, i.e. the comparison result flips relative to the true rational value. [2](#0-1) 

Because a validator's own self-delegated/other stake amounts (and thus the lamport values summed into `fork_stake`/`locked_out_stake`/`sum`) are attacker-influenced (stake account balances are set by the staker), an attacker can tune the exact lamport amount of a stake account so the aggregate crosses a rounding boundary such that the `f64` comparison evaluates opposite to the true fraction, at the exact percentage threshold that gates:
- whether a vote is allowed past the tower lockout depth check (`check_vote_stake_threshold`),
- whether a fork-switch is permitted without a full/legitimate switch proof (`make_check_switch_threshold_decision`, guarding `SWITCH_FORK_THRESHOLD`),
- whether a slot is deemed to have crossed a given commitment/confirmation level (`get_lockout_count`).

Existing guards do not stop this path: there is no `checked_mul`/exact-integer cross-multiplication anywhere in these call sites (unlike `Fraction::cmp`, which Agave itself added specifically to eliminate this defect for Alpenglow-era code, implying the legacy Tower code was never back-ported to use exact arithmetic). [13](#0-12) 

### Impact Explanation
The `SWITCH_FORK_THRESHOLD` check exists specifically to prevent honest validators from abandoning a fork (thus permanently losing votes cast there) without cryptographic-equivalent proof that enough stake is safely locked out elsewhere; the surrounding comment states that an incorrect switch decision at scale "the network halts because 90% of validators can't vote." [14](#0-13) 
A misjudged vote-stake threshold or commitment-lockout count similarly affects rooting/optimistic-confirmation correctness — i.e., "false execution/rooting/acceptance, consensus halt," which is within the requested valid-impact scope.

### Likelihood Explanation
The magnitude of the defect (ULP-level rounding error at 10^17-scale values) is real and proven by Agave's own test, but triggering an *externally consequential* threshold flip requires the aggregated stake to land within roughly one ULP (a handful of lamports out of ~10^17) of an exact threshold boundary. This is a narrow, low-probability condition to hit organically, and an attacker would need fine control over the exact lamport-level stake amounts contributing to the sum at the moment of evaluation — feasible in principle (stake amounts are attacker-chosen) but requiring precise engineering of a specific, hard-to-guarantee coincidence, making practical exploitation low-likelihood even though the underlying arithmetic defect is unconditionally present.

### Recommendation
Replace the raw `f64` stake-ratio comparisons in `core/src/consensus.rs` (`check_vote_stake_threshold`, `make_check_switch_threshold_decision`), `core/src/consensus/vote_stake_tracker.rs` (`add_vote_pubkey`), and `runtime/src/commitment.rs` (`get_lockout_count`) with the same exact-integer `Fraction`-style cross-multiplication comparison already used for Alpenglow in `votor-messages/src/fraction.rs`, eliminating the floating-point precision gap for these safety-critical checks.

### Proof of Concept
Agave's own unit test demonstrates the underlying arithmetic flaw directly: [2](#0-1) 
The same pattern (`stake_value as f64 / total_stake as f64` compared against a fixed threshold) is reachable from `Tower::check_vote_stake_threshold` and `Tower::make_check_switch_threshold_decision` using attacker-controlled stake-account lamport balances chosen to land within one ULP of `VOTE_THRESHOLD_SIZE`/`SWITCH_FORK_THRESHOLD` at realistic total-stake magnitudes, causing the boundary comparison to evaluate opposite to the true rational stake fraction.
