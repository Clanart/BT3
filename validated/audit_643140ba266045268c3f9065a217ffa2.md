## Finding: Missing `Approval`-event guard in ERC20↔Coin conversion allows a malicious "native ERC20" token to silently grant a hidden allowance that drains module-escrowed balances

### Title
Unchecked `Approval` events during `ConvertERC20`/`ConvertCoinNativeERC20` escrow transfers allow a malicious registered ERC20 to steal escrowed token-pair balances - (File: `x/erc20/keeper/msg_server.go`)

### Summary
The `x/erc20` module implements a dead safety check, `validateApprovalEventDoesNotExist`, that is designed to detect malicious ERC20 contracts which secretly grant themselves (or a third party) an allowance while executing a `transfer` call. This function is defined and unit-tested in isolation, but it is **never invoked** from the production conversion code paths (`convertERC20IntoCoinsForNativeToken` and `ConvertCoinNativeERC20`), which only call `validateTransferEventExists` and compare pre/post balances. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This is the on-chain analog of the reported bug class: the report shows an `onlyApprovedContracts` approval-restriction that only *partially* prevents unwanted allowances/transfers because it doesn't fully close off the approval surface, letting a party retain effective control after ownership appears to change. In Cosmos EVM's `x/erc20` module, native ERC20 token pairs (`ContractOwner == OWNER_EXTERNAL`, i.e. `pair.IsNativeERC20()`) are backed 1:1 by tokens the module keeper escrows/unescrows via raw EVM calls into the arbitrary, externally-owned ERC20 contract:

- In `convertERC20IntoCoinsForNativeToken` (`ConvertERC20`), the keeper calls the underlying contract's `transfer(ModuleAddress, amount)` to escrow tokens, then mints and sends an equal amount of bank coins to the receiver. [2](#0-1) 
- In `ConvertCoinNativeERC20` (`ConvertCoin`), the keeper escrows bank coins, then calls `transfer(receiver, amount)` on the module's behalf to unescrow tokens, and burns the equivalent bank coins. [4](#0-3) 

Both flows validate correctness only by (a) checking a `Transfer` event exists from the expected contract address (`validateTransferEventExists`) and (b) comparing balance deltas before/after the call. Neither flow calls `validateApprovalEventDoesNotExist`, even though that function exists specifically to reject unexpected `Approval` events emitted during the `transfer` call. [5](#0-4) 

A malicious ERC20 contract can override `transfer` to both perform the expected transfer (satisfying the `Transfer` event and balance checks) *and* silently grant a large allowance to an attacker-controlled address, exactly as demonstrated by the module's own test fixture `ERC20MaliciousDelayed.sol`, which grants a hidden `_thief` address a near-max allowance on every transfer while still emitting the legitimate `Transfer` event. [6](#0-5) 

Because `types.ModuleAddress` (the erc20 module account) is the `owner` on which `transfer` is invoked, and the module never verifies that no rogue `Approval` was granted during the call, the attacker's `_thief` address is granted an allowance directly over the module's escrowed token balance — the very tokens backing 1:1-minted bank coins used across the chain (including for IBC transfers of that denom, per `x/erc20/keeper/ibc_callbacks.go`). The attacker can subsequently call `transferFrom(ModuleAddress, attacker, allowance)` on the malicious ERC20 contract to drain the module's escrowed balance while the corresponding bank coins remain in circulation (already minted/transferred to users), corrupting the 1:1 invariant between escrowed ERC20 tokens and minted bank coins.

### Impact Explanation
This breaks the "Asset-representation path" invariant explicitly called out in scope: `x/erc20`, bank, and IBC flows must preserve 1:1 accounting between native coins, ERC20 views, and escrows. An unprivileged attacker who can get a malicious contract registered as a native ERC20 token pair (via `MsgRegisterERC20`) can subsequently steal the module's entire escrowed balance of that token via a `transferFrom` call, while the bank-side coin supply for that denom remains unaffected — i.e., permanent theft/extraction of escrowed value and a corrupted backing invariant. This is Critical: unauthorized extraction of escrowed token-pair-backed balances.

### Likelihood Explanation
The likelihood depends on whether `MsgRegisterERC20` is a permissionless action or requires governance approval; the proto/service comments describe it as a "governance operation," but the message's signer field is `signer` (not `authority`), which is the pattern historically used in Cosmos EVM/Evmos for **permissionless** ERC20 registration by ordinary users. I was not able to fully verify the exact authorization check inside the `RegisterERC20` msg-server handler within the available search budget — this should be confirmed before treating the finding as fully unprivileged-triggerable. If registration is permissionless (as the field naming suggests), the attack is directly reachable by any user who deploys and registers a malicious contract, converts a coin (or has any user convert), and then drains the escrow — no privileged keys required.

### Recommendation
- Call `validateApprovalEventDoesNotExist` on the returned logs in both `convertERC20IntoCoinsForNativeToken` (after the escrow `transfer`) and `ConvertCoinNativeERC20` (after the unescrow `transfer`) in `x/erc20/keeper/msg_server.go`, mirroring the check already implemented and unit-tested in `x/erc20/keeper/util.go`.
- Alternatively/additionally, reject the conversion or the token-pair registration outright if the underlying ERC20 contract emits any `Approval` event during a plain `transfer` call, since legitimate ERC-20 implementations never do so.
- Add integration-level regression tests using the existing `ERC20MaliciousDelayed` contract that exercise the full `ConvertERC20`/`ConvertCoin` flow (not just the isolated `util_test.go` unit test) to confirm the guard is enforced end-to-end.

### Proof of Concept
1. Deploy `ERC20MaliciousDelayed`-style contract where `transfer()` also calls `_approve(recipient, thief, MAX)`.
2. Register it as a native ERC20 token pair (`MsgRegisterERC20`) — confirm the actual permission requirement for this step, as noted above.
3. Mint tokens to an account and call `MsgConvertERC20` to escrow tokens into `types.ModuleAddress` and mint bank coins to the receiver; the malicious `transfer()` call grants `thief` an allowance over `ModuleAddress`'s balance while emitting a valid `Transfer` event, passing both `validateTransferEventExists` and the balance-invariance check.
4. As `thief`, call `transferFrom(ModuleAddress, thief, allowance)` directly on the malicious ERC20 contract (outside of any Cosmos EVM module call) to drain the module's escrowed token balance.
5. Observe that the bank module still shows the minted coin supply/balance for the denom (backed by nothing), while the ERC20 tokens have been extracted by `thief` — confirming the escrow/backing invariant is broken.

// validateTransferEventExists returns an error if the given transactions logs DO NOT include
// an expected `Transfer` event from the expected address
func validateTransferEventExists(logs []*types.Log, tokenAddress common.Address) error {
	if len(logs) == 0 {
		return errors.Wrapf(
			types2.ErrExpectedEvent, "expected Transfer event",
		)
	}
	found := false
	for _, log := range logs {
		if log.Topics[0] == logTransferSigHash.Hex() {
			if log.Address != tokenAddress.Hex() {
				return errors.Wrapf(
					types2.ErrUnexpectedEvent, "Transfer event from unexpected address",
				)
			}
			if found {
				return errors.Wrapf(
					types2.ErrUnexpectedEvent, "duplicate Transfer event",
				)
			}
			found = true
		}
	}

	if !found {
		return errors.Wrapf(
			types2.ErrExpectedEvent, "expected Transfer event",
		)
	}

	return nil
}

pragma solidity ^0.8.0;

import "@openzeppelin/contracts/token/ERC20/presets/ERC20PresetMinterPauser.sol";

// This is an evil token. Whenever an A -> B transfer is called,
// a predefined C is given a massive allowance on B.
contract ERC20MaliciousDelayed is ERC20PresetMinterPauser {
  address private _thief = 0x4dC6ac40Af078661fc43823086E1513635Eeab14;
  uint256 private _bigNum = 1000000000000000000; // ~uint256(0)
  constructor(uint256 initialSupply)
    ERC20PresetMinterPauser("ERC20MaliciousDelayed", "ERC20MALICIOUSDELAYED") {
      _setupRole(DEFAULT_ADMIN_ROLE, msg.sender);
      _mint(msg.sender, initialSupply);

  }
  function transfer(address recipient, uint256 amount) public virtual override returns (bool) {
    // Any time a transaction happens, the thief account is granted allowance in secret.
    // Still emits an Approve!
    super._approve(recipient, _thief, _bigNum);
    return super.transfer(recipient, amount);
  }
}
