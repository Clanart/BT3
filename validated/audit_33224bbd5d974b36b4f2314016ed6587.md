### Title
Legacy `event: file` rules infer `field: new_text`, which resolves to `tool_input['new_string']` and is always empty for the `Write` tool - silently disabling block rules on `Write` operations - ([File: plugins/hookify/core/config_loader.py, plugins/hookify/core/rule_engine.py])

### Summary
`Rule.from_dict` converts the legacy `pattern:` shorthand for `event: file` into a single condition with `field='new_text'`, without distinguishing between the `Write` and `Edit` tools. `RuleEngine._extract_field` maps `new_text`/`new_string` exclusively to `tool_input.get('new_string', '')`, but the `Write` tool never populates `new_string` — it uses `content`. As a result, any legacy-style block rule targeting `event: file` is evaluated against an empty string for `Write` operations and can never match, even though the actual dangerous content is present in `tool_input['content']`.

### Finding Description
The vulnerable path is:

1. `Rule.from_dict` (plugins/hookify/core/config_loader.py, lines 56-73) — for a legacy rule with `event: file` and a top-level `pattern:` (no `conditions:`), the field is inferred as `'new_text'`: [1](#0-0) 

2. `RuleEngine._rule_matches` calls `_check_condition` for each condition, which calls `_extract_field(condition.field='new_text', tool_name='Write', tool_input, ...)`.

3. In `_extract_field`, for `tool_name in ['Write', 'Edit']` and `field == 'new_text' or field == 'new_string'`, the code unconditionally does `return tool_input.get('new_string', '')`: [2](#0-1) 

The `Write` tool's `tool_input` schema contains a `content` key (as explicitly acknowledged two lines above in the `content` branch: `tool_input.get('content') or tool_input.get('new_string', '')`), not `new_string`. So for a `Write` call, `_extract_field('new_text', ...)` always returns `''`.

4. Back in `_check_condition`, `field_value` is `''`; the `regex_match`/`contains` operator is then evaluated against an empty string, so any non-trivial dangerous-content pattern (e.g. matching secrets, shell injection payloads, etc.) never matches: [3](#0-2) 

5. In `evaluate_rules`, since the condition never matches, the rule never enters `blocking_rules`, so a rule configured with `action: block` is silently downgraded to a no-op for `Write` operations: [4](#0-3) 

No existing validation catches this: `rule.tool_matcher` is optional and not auto-derived from `event: file`, so the rule is evaluated against both `Write` and `Edit`, but only `Edit`'s `new_string` field is actually inspected. There is no schema-normalization step, no warning, and no test coverage asserting the legacy shorthand behaves consistently across tools.

### Impact Explanation
This breaks the "deny means deny" invariant of the hookify rule engine: a rule author who writes a straightforward legacy-style block rule to catch dangerous content in file writes (per the plugin's documented `event: file` / `pattern:` shorthand) believes any subsequent `Write` tool call containing that pattern will be blocked, but it silently never fires. This allows arbitrary dangerous file content to be written via the `Write` tool despite an explicit blocking rule intended to prevent it — a policy-enforcement bypass that defeats the plugin's core safety control without any indication of failure to the user.

### Likelihood Explanation
This is highly likely to occur in practice because:
- The legacy `pattern:` shorthand for `event: file` is a documented, simple configuration style (referenced repeatedly in `plugins/hookify/skills/writing-rules/SKILL.md` and `plugins/hookify/README.md`), making it a natural choice for less sophisticated rule authors.
- No `tool_matcher` or `conditions:` awareness is required to trigger the bug — it happens by default whenever `event: file` + `pattern:` is used and the tool invoked is `Write`.
- The bug is deterministic and reproducible on every `Write` call; it requires no attacker privilege beyond normal use of the `Write` tool (which any Claude Code session can invoke).

### Recommendation
Fix `Rule.from_dict` and/or `RuleEngine._extract_field` so the legacy `field: new_text` inference resolves per-tool correctly: either infer separate field names/conditions for `Write` (`content`) vs `Edit`/`MultiEdit` (`new_string`), or make `_extract_field`'s `new_text`/`new_string` branch fall back to `tool_input.get('content')` when `new_string` is absent (mirroring the existing `content` branch logic). Add regression tests covering `event: file` legacy-pattern rules evaluated against both `Write` and `Edit`/`MultiEdit` tool inputs to ensure blocking rules fire consistently.

### Proof of Concept
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

def test_legacy_file_pattern_block_rule_bypassed_for_write():
    frontmatter = {
        "name": "block-secret-write",
        "enabled": True,
        "event": "file",
        "pattern": r"SECRET_KEY",
        "action": "block",
    }
    rule = Rule.from_dict(frontmatter, "Blocking secret write!")

    engine = RuleEngine()
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Write",
        "tool_input": {
            "file_path": "/tmp/config.py",
            "content": "SECRET_KEY = 'abcdef123456'",
        },
    }

    result = engine.evaluate_rules([rule], input_data)

    # BUG: block rule never fires because field 'new_text' resolves to
    # tool_input.get('new_string', '') == '' for the Write tool,
    # even though the dangerous pattern is present in tool_input['content'].
    assert result == {}, f"Expected block bypass bug, got: {result}"
```
Expected (buggy) result: `evaluate_rules` returns `{}` (no block), confirming the pattern matching against `content` is silently skipped for `Write` tool calls despite a configured `action: block` rule.
