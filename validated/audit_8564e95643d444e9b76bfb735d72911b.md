### Title
Tier-reward telescoping can be broken via `mWomSV.startUnlock`/`cancelUnlock` manipulation of `getUserTotalLocked` between `incentiveDeposit` calls - (File: wombat/ArbWomUp3.sol)

### Summary
`incentiveDeposit` computes the marginal tier-based MGP reward for a lock deposit as `f(currentLocked + newAmount) - f(currentLocked)`, where `currentLocked = mWomSV.getUserTotalLocked(_account)` [1](#0-0)  and the subtracted term is `calDoubledCounted(_account)` [2](#0-1) . Because `getUserTotalLocked` excludes any amount the user has parked into cooldown via `mWomSV.startUnlock` (and that cooldown can be instantly reversed with `cancelUnlock` without waiting out the cooldown period), an attacker can transiently and reversibly lower the "base" used for the marginal-reward calculation between two `incentiveDeposit` calls, without ever reducing their real backing stake in `MasterMagpie`.

### Finding Description
`getUserTotalLocked` is defined as the amount staked in `MasterMagpie` minus `getUserAmountInCoolDown` [3](#0-2) . `startUnlock` moves part of a user's locked balance into a cooldown slot without withdrawing anything from `MasterMagpie` (the actual withdrawal only happens later in `unlock`) [4](#0-3) . `cancelUnlock` reverses this instantly (no wait required, only requires the slot still be “in cooldown”) [5](#0-4) .

The reward formula in `ArbWomUp3` is only correct (i.e., path-independent/telescoping across multiple deposits) if each successive call's baseline `getUserTotalLocked` equals the actual cumulative amount previously locked. By calling `mWomSV.startUnlock(c)` before a second `incentiveDeposit` call, the attacker artificially reports a lower baseline `L1 - c` instead of the true `L1`, so `calDoubledCounted` under-subtracts, and the marginal reward for the second deposit is computed as `f(L1 - c + y) - f(L1 - c)` instead of the correct `f(L1 + y) - f(L1)`. The attacker then calls `cancelUnlock` to restore `c` back into the locked balance, ending in the same final state (`L1 + y`) as if no manipulation had occurred, but having collected a different (and, depending on curvature of the tier/multiplier schedule, potentially inflated) total reward across the two calls versus what a single continuous computation would have paid.

This is not literally "claiming the same reward twice" for the same `x` (each call is calculated against the state at that time), but it does break the intended additivity of the tiered reward formula since the baseline used in the second call no longer reflects the user's real, unreduced locked amount.

### Impact Explanation
If `rewardMultiplier` is configured with diminishing (concave) marginal rewards per tier bracket (i.e., earlier/smaller tranches rewarded more per unit than later/larger ones — a plausible loyalty-program design), this manipulation lets the attacker extract more total `vlMGP`-backing MGP for the same net final `mWomSV` lock than a straightforward single deposit would yield, at no capital cost. This is theft of unclaimed MGP yield reserved in the `ArbWomUp3` contract (`IERC20(mgp).balanceOf(address(this))`) [6](#0-5) , drawing down the program's finite reward pool at a rate faster than intended.

### Likelihood Explanation
This is conditional and cannot be confirmed purely from the contract code: the actual profitability of the manipulation depends entirely on the `rewardMultiplier`/`rewardTier` values chosen by the owner via `setMultiplier` [7](#0-6) , which are not defined or constrained (monotonic increasing or decreasing) anywhere in the contract. If the multiplier increases with tier size (rewarding larger locks more per unit — arguably the more natural design to encourage bigger commitments), the described manipulation would actually *reduce* the attacker's reward rather than inflate it, making the exploit self-defeating. I could not verify the deployed/intended multiplier schedule, so I cannot confirm the direction of curvature needed for the described exploit to be net-profitable.

### Recommendation
Regardless of multiplier configuration, the reward baseline should not be manipulable via reversible cooldown actions. Use a value that cannot be altered without an actual, irreversible change in stake — e.g. `getUserTotalLocked(_account) + getUserAmountInCoolDown(_account)` (i.e., `balanceOf`, the true `MasterMagpie` staking balance) as the baseline for both `accumulated` in `getRewardAmount` and `accuIn1` in `calDoubledCounted`, so that `startUnlock`/`cancelUnlock` cycles cannot change the computed tier baseline between successive `incentiveDeposit` calls.

### Proof of Concept
Cannot be conclusively demonstrated as a profitable exploit without knowing the actual/intended `rewardMultiplier` schedule, since the sign of the effect (reward inflation vs. reward reduction) flips depending on whether the schedule is concave or convex. A Hardhat PoC would need to: deploy `ArbWomUp3` with a concretely concave `setMultiplier` schedule, fund it with MGP, have the attacker (a) call `incentiveDeposit(x, ratio, true, 2)`, (b) call `mWomSV.startUnlock(c)`, (c) call `incentiveDeposit(y, ratio, true, 2)`, (d) call `mWomSV.cancelUnlock(slot)`, and compare total `vlMGP` locked for the attacker against the reward a single continuous `incentiveDeposit` sequence (without the cooldown trick) would have produced for the same final `mWomSV` balance — asserting the manipulated path yields strictly more `vlMGP`. Given this is contingent on an as-yet-unverified admin-configured curvature and not a self-contained code-level guarantee, I flag this finding with reduced confidence pending confirmation of the actual `rewardMultiplier` ordering used in production.

    function calDoubledCounted(address _account) public view returns (uint256) {
        uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accuIn1 > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }

        rewardAmount += (accuIn1 - rewardTier[i - 1]) * rewardMultiplier[i - 1];
        return rewardAmount / DENOMINATOR;
    }
