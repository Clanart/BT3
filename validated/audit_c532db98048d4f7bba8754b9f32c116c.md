### Title
Attacker can hijack donated/queued rewards on an empty pool via a dust deposit that inflates `rewardPerTokenStored` at a near-zero `totalStaked()` denominator - (File: `rewards/BaseRewardPool.sol` / `rewards/BaseRewardPoolV2.sol`)

### Summary
`donateRewards` and `queueNewRewards` both route through `_provisionReward`, which stores incoming rewards in `queuedRewards` whenever `totalStaked() == 0`, and only folds `queuedRewards` into `rewardPerTokenStored` (dividing by `totalStaked()`) the next time `_provisionReward` runs. Because `donateRewards` is fully permissionless and `_provisionReward` divides by whatever the pool's current `totalStaked()` is at that instant, an attacker can stake a 1-wei dust amount and immediately trigger the fold-in itself (even with a zero-value donation), causing the entire queued reward to be credited to the dust position before any real depositor arrives.

### Finding Description
`donateRewards` has no access control beyond requiring the token be a registered reward token: [1](#0-0) 

It calls `_provisionReward`, which branches on `totalStaked()`: [2](#0-1) 

`totalStaked()` simply reads the staking token's balance held by `MasterMagpie`: [3](#0-2) 

Exploit flow:
1. While the pool has zero stakers (`totalStaked()==0`), any caller (the attacker, or a legitimate third party wanting to pre-fund an about-to-launch pool) calls `donateRewards(largeAmount, rewardToken)`. Since `totalStaked()==0`, the full amount goes into `rewards[rewardToken].queuedRewards` and `rewardPerTokenStored` is left untouched.
2. The attacker calls `MasterMagpie.deposit(stakingToken, 1)` to stake 1 wei. In `_deposit`, `_harvestBaseRewarder` (which snapshots `userRewardPerTokenPaid` via `rewarder.updateFor`) runs *before* the staking-token transfer, so the attacker's checkpoint is taken while `rewardPerTokenStored` is still unchanged: [4](#0-3) 
3. The attacker then calls `donateRewards(0, rewardToken)` again — a zero-cost, permissionless call. Now `totalStaked()` is nonzero (the attacker's 1 wei), so the `else` branch executes: it folds the entire pre-existing `queuedRewards` into `rewardPerTokenStored`, dividing by the attacker's own dust `totalStaked()` — inflating `rewardPerTokenStored` by a factor of roughly `largeAmount / 1 wei`.
4. Because the attacker holds effectively 100% of `totalStaked()` at the exact moment of the fold-in, `earned()` — computed as `balanceOf(account) * (rewardPerToken - paid) / 10**decimals + userRewards` — resolves to essentially the entire donated amount for the attacker: [5](#0-4) 
5. The attacker calls `withdraw`/`multiclaim`, which invokes `getReward`/`getRewards` on the rewarder and actually transfers the reward tokens out: [6](#0-5) 
6. Any legitimate depositor who stakes afterward has their `userRewardPerTokenPaid` checkpointed at the now-already-inflated `rewardPerTokenStored` (via the same `_harvestBaseRewarder`/`updateFor` path executed *before* their balance is counted), so they receive nothing from the reward that was queued for the pool — it has already been drained to the dust staker.

No existing modifier prevents this: `donateRewards` has no `onlyManager`/`onlyMasterMagpie` restriction (unlike `queueNewRewards`), `MasterMagpie.deposit` has no minimum-stake requirement, and the reward-index update logic assumes `totalStaked()` at fold-in time fairly represents "who was staked when the reward accrued," which is false when the entire historical `queuedRewards` accrued while stake was zero and is folded in against a manipulated near-zero denominator.

### Impact Explanation
Direct theft of funds intended for legitimate stakers: rewards that should be distributed proportionally to actual stake-time are instead captured almost entirely by an attacker who staked a dust amount for an instant, at the expense of the real depositor(s) who arrive afterward and receive none of the pre-funded/queued reward they were entitled to. This matches the "theft of unclaimed yield" / "direct theft of user funds" Immunefi impact class, since it breaks the conservation invariant `earned <= own accrual share`.

### Likelihood Explanation
- Requires no privileged role: `donateRewards`, `MasterMagpie.deposit`, `withdraw`/`multiclaim` are all public/external and unrestricted.
- Requires the pool to have `totalStaked()==0` at some point with queued rewards pending — this is a normal, expected state for a newly created pool or one whose stakers have all fully withdrawn while a reward manager or donor tries to pre-seed incentives.
- Capital needed is minimal: 1 wei of the staking token plus gas; the fold-in trigger call (`donateRewards(0, token)`) costs nothing beyond gas.
- Fully repeatable any time a pool transitions from zero to nonzero `totalStaked()` while `queuedRewards` is outstanding.

### Recommendation
Do not let a single block/transaction sequence allow an attacker's just-deposited dust balance to capture the entire backlog of `queuedRewards`. Options: (1) accrue `queuedRewards` gradually over time (streaming) rather than an instantaneous full fold-in on the next `_provisionReward` call; (2) require a minimum stake or minimum-duration checkpoint before a wallet's balance can be used as the `totalStaked()` divisor for folding in queued rewards; (3) snapshot/timestamp `queuedRewards` and distribute pro-rata based on stake held over the queued period rather than stake held at the single moment `_provisionReward` happens to be called next.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, a mock staking ERC20, and register a pool with `BaseRewardPool`/`BaseRewardPoolV2` as rewarder; register a mock reward ERC20 via `queueNewRewards` (or constructor) so `isRewardToken[rewardToken]==true`.
2. Ensure `totalStaked()==0` for the pool (no deposits yet).
3. As `attacker`, mint/approve `largeAmount` of `rewardToken` and call `rewarder.donateRewards(largeAmount, rewardToken)`; assert `rewards[rewardToken].queuedRewards == largeAmount` and `rewardPerTokenStored == 0`.
4. As `attacker`, approve 1 wei of `stakingToken` and call `MasterMagpie.deposit(stakingToken, 1)`.
5. As `attacker`, call `rewarder.donateRewards(0, rewardToken)`; assert `queuedRewards == 0` and `rewardPerTokenStored` jumped to `largeAmount * 10**decimals / 1`.
6. As `victim`, deposit `largeStakeAmount` (e.g., 1000e18) into the same pool.
7. Have `attacker` call `MasterMagpie.multiclaim`/`withdraw` and assert `attacker`'s received `rewardToken` balance ≈ `largeAmount` (vastly more than their proportional stake-time share, which is ~0).
8. Have `victim` accrue rewards over time and call `multiclaim`; assert `victim` receives 0 (or near 0) from the pre-existing `largeAmount`, proving the donated reward was misappropriated instead of distributed to legitimate future stakers.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
