## Finding: `placeOrder` in IntentGatewayV2 Escrows Tokens for Arbitrary/Unsupported `destination` Chains With No Whitelist Check

### Title
Missing destination-chain whitelist in `IntentGatewayV2.placeOrder` permanently locks escrowed user funds - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder()` accepts an arbitrary, user-supplied `order.destination` byte string and immediately escrows the user's input tokens against it, with **no check that the destination chain is a supported/registered Hyperbridge state machine**. This is the exact bug class from the FBTC report: user funds are moved into custody based on an unvalidated destination identifier, and if that destination is not a real, connected chain (typo, unsupported network, or a misleading frontend), the escrowed tokens have no valid recovery path.

### Finding Description
`placeOrder` overwrites `order.user`, `order.source`, and `order.nonce`, but performs **no validation of `order.destination`** before transferring/escrowing the caller's tokens: [1](#0-0) [2](#0-1) 

Compare this to `HyperFungibleToken.sol`, where the equivalent send path explicitly whitelists the destination before burning/locking any tokens: [3](#0-2) [4](#0-3) 

`IntentGatewayV2` has no analogous `_supportedChains`/whitelist gate in `placeOrder`. The only chain-validity check happens later, and only on the *fill* and *cancel* paths, which compare `order.destination`/`order.source` against the *current* chain's own identity (`currentChain == orderDest` / `currentChain == orderSource`), not against a registry of chains that Hyperbridge actually connects to: [5](#0-4) [6](#0-5) 

If a user (or a misleading frontend) submits an order with `order.destination` set to a chain ID Hyperbridge does not actually support, `placeOrder` escrows the input tokens unconditionally. Because no real chain corresponds to that destination:
- No solver can ever call `fillOrder`, because there is no live `IntentGatewayV2` deployment on that "chain" to accept the fill and dispatch the `RedeemEscrow` message back.
- Cancellation from the source chain (`_cancelFromSource`, cross-chain path) needs to resolve the peer gateway/module identity for `order.destination` (via the module's `instance()`/deployment registry, populated only through `NewDeployment` messages authenticated from Hyperbridge) in order to build and dispatch its cross-chain verification/cancel request. For an unregistered destination this registry lookup has no entry, so this path either reverts or can never receive the required confirming message, leaving cancellation unresolvable.

The existing test suite even documents that unrecognized/mismatched chain identifiers are only checked at `fillOrder`/`cancelOrder` time (reverting with `WrongChain`) and that unregistered destinations are tolerated at `placeOrder` time (escrow succeeds, only a fee-lookup fallback is exercised), confirming there is no upfront whitelist: [7](#0-6) [8](#0-7) 

The same missing-whitelist pattern exists identically in the Tron variant of `placeOrder`: [9](#0-8) 

### Impact Explanation
An unprivileged user who places an order with an unsupported/incorrect `order.destination` (whether by mistake, typo, or because a compromised/misleading frontend supplies it) has their input tokens escrowed by the contract with no whitelist rejection. Because no counterpart gateway exists on that destination, the order can never be legitimately filled, and the cross-chain cancellation/refund flow depends on resolving that same unsupported destination's registered module — which does not exist. This causes **permanent loss/lock of the user's escrowed tokens** inside `IntentGatewayV2`, directly matching the "stealing or loss of funds" and "cross-chain admin/host-management effects... unauthenticated message flow" impact categories in the bounty scope.

### Likelihood Explanation
This requires no privileged actor, relayer, or prover — any ordinary user calling the public `placeOrder` entrypoint with a malformed or unsupported `destination` value triggers the loss. This is precisely the medium-severity condition described in the referenced FBTC report ("user specifies an unsupported network or the project's frontend is misleading"), and the guard that FBTC was advised to add (destination whitelist check before locking/burning funds) is present in Hyperbridge's own `HyperFungibleToken` contracts but absent from `IntentGatewayV2.placeOrder`.

### Recommendation
Add an explicit destination-chain whitelist check in `placeOrder` (and the Tron variant) before escrowing any tokens — e.g., validate `order.destination` against the module's registered deployments/instance mapping (the same registry used by `instance()`/`_instance()` for fill and cancel), and revert with an `UnsupportedChain`-style error if the destination has no registered counterpart gateway, mirroring the pattern already used in `HyperFungibleToken._buildDispatchPost`.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder(order, graffiti)` with `order.destination = bytes("FAKE_CHAIN")` (a chain ID with no registered `IntentGatewayV2` deployment/instance anywhere in Hyperbridge).
2. `placeOrder` computes `order.source`, increments nonce, computes the commitment, and unconditionally escrows `order.inputs` from the user (see `evm/src/apps/IntentGatewayV2.sol:191-343`) — no check against a supported-chain registry occurs.
3. No solver can ever call `fillOrder` for this commitment because there is no real deployment on `"FAKE_CHAIN"` to receive the fill and dispatch the settlement message.
4. The user (or anyone after deadline) attempts `cancelOrder`; since `orderSource != orderDest`, execution routes to `_cancelFromSource` (`evm/src/apps/IntentGatewayV2.sol:483-484`), which must resolve/dispatch based on the unsupported `order.destination` — this path cannot complete because no counterpart module/instance is registered for `"FAKE_CHAIN"`.
5. The escrowed input tokens remain permanently stuck in the `IntentGatewayV2` contract with no fill and no cancel path — total loss of the user's escrowed funds.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
