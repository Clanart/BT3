### Title
`VLMGP.cancelUnlock()` never calls `ReferralStorage.updateTotalFactor`, permanently desynchronizing `totalBoostFactor` from real locked balances - (File: VLMGP.sol / rewards/ReferralStorage.sol)

### Summary
`VLMGP.lock`, `lockFor`, and `startUnlock` all call `IReferralStorage(referralStorage).updateTotalFactor(...)` after changing a user's real locked balance, but `cancelUnlock()` does not, even though it immediately increases `getUserTotalLocked` by moving MGP out of cooldown back into the "locked" bucket. Any user can exploit this asymmetry to leave their own `userInfo.factor` (and hence the global `totalBoostFactor` denominator) stale and understated relative to their true locked balance, which inflates `_calBoosted()` results used in `ReferralStorage.trigger()` for every referrer.

### Finding Description
`updateTotalFactor` is the only function that keeps `totalBoostFactor` (the sum of every user's `sqrt(getUserTotalLocked)` factor) in sync with reality: [1](#0-0) 

It is invoked from `VLMGP._lock` (used by `lock`/`lockFor`) and from `VLMGP.startUnlock`: [2](#0-1) [3](#0-2) 

However `cancelUnlock()` reduces `slot.amountInCoolDown` to zero, which directly increases `getUserTotalLocked(_user)` (since `getUserTotalLocked = amountInMasterMagpie - getUserAmountInCoolDown`), but never calls `updateTotalFactor`: [4](#0-3) [5](#0-4) 

Because the user's `userInfo.factor` in `ReferralStorage` is left stale (computed from the pre-cancel, smaller locked amount) while `totalBoostFactor` is the running sum of all such factors, `totalBoostFactor` permanently understates the true aggregate participation until that specific user happens to call `lock`/`lockFor`/`startUnlock` again. Any referrer (including the caller themselves) can repeat a `lock -> startUnlock -> cancelUnlock` cycle to keep widening this gap indefinitely, since `cancelUnlock` has no cooldown/rate limit beyond needing an active cooldown slot.

This directly corrupts `_calBoosted`, which is the shared boost calculation used for every referrer's reward cut: [6](#0-5) [7](#0-6) 

Since `totalBoostFactor` is the shared denominator across all referrers, artificially depressing it (by never refreshing one user's factor after `cancelUnlock`) inflates `boostesd` for every `_calBoosted(referer)` call, which inflates both `refererPercentage` and `refereePercentage` in `trigger()`, and thus the `rewardAmount` credited on every referee-triggered claim across the whole system - not just for the manipulating account.

No existing modifier prevents this: `cancelUnlock` only checks `whenNotPaused` and `_checkInCoolDown`; there is no reentrancy guard requirement here nor any factor-sync check.

### Impact Explanation
`trigger()` only increments an internal `rewardAmount` accounting entry; it does not check that `MGP.balanceOf(address(this))` covers all outstanding `rewardAmount` obligations. If accrued `rewardAmount` values (inflated via the deflated `totalBoostFactor`) exceed the actual MGP token balance held by `ReferralStorage`, later callers of `claimReward()` will find `MGP.safeTransfer` failing/reverting, or earlier claimants draining the pool such that legitimate referrers/referees can no longer redeem their rightfully accrued rewards. This is a concrete, quantifiable loss of unclaimed yield for honest participants, caused entirely by an unprivileged user repeatedly cycling `lock → startUnlock → cancelUnlock`, matching the "Theft of unclaimed yield" impact class.

### Likelihood Explanation
- Fully permissionless: `lock`, `startUnlock`, and `cancelUnlock` on `VLMGP` require no special role.
- Low capital requirement: only needs enough MGP to lock and unlock in a slot; the cycle can be repeated as often as desired (subject to `coolDownInSecs` gating how quickly a slot can be reused, but repeatable indefinitely over time or across multiple slots up to `maxSlot`).
- No code change to state variables outside normal contract functions is needed; this is a pure logic gap (missing call), always present, not dependent on a race condition or front-running.
- The larger the number of active referrers and the longer the drift persists, the larger the cumulative over-payment, making the insolvency precondition increasingly easy to reach over time.

### Recommendation
Add a call to `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)` inside `cancelUnlock()` (and any other function in `VLMGP` that changes `getUserTotalLocked`, e.g. `unlock`/`forceUnLock` already change cooldown but should be checked too), mirroring the pattern used in `_lock` and `startUnlock`:

```solidity
function cancelUnlock(uint256 _slotIndex) external override whenNotPaused {
    _checkIdexInBoundary(msg.sender, _slotIndex);
    UserUnlocking storage slot = userUnlockings[msg.sender][_slotIndex];
    _checkInCoolDown(msg.sender, _slotIndex);

    totalAmountInCoolDown -= slot.amountInCoolDown;
    slot.amountInCoolDown = 0;

    if (referralStorage != address(0)) IReferralStorage(referralStorage).updateTotalFactor(msg.sender);

    emit ReLock(msg.sender, _slotIndex, slot.amountInCoolDown);
}
```
Additionally, consider adding a solvency check in `ReferralStorage.trigger()`/`claimReward()` (e.g., capping `rewardAmount` accrual to available MGP or requiring reconciliation) as defense in depth against any future factor-sync gaps.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `VLMGP`, `ReferralStorage`, `MasterMagpie` mocks/fixtures wired together (`vlMGP.setReferralStorage`, referralStorage initialized with `vlMGP`).
2. Attacker registers a referral code (`registerCode`) and sets tier via owner (`setTier(1, X)`), or reuse default tier 1.
3. Attacker calls `MGP.approve` + `vlMGP.lock(amount)` — assert `updateTotalFactor` fired and `totalBoostFactor == sqrt(amount)`.
4. Attacker calls `vlMGP.startUnlock(halfAmount)` — assert `totalBoostFactor` drops to `sqrt(amount-halfAmount)` (factor refreshed correctly here).
5. Attacker calls `vlMGP.cancelUnlock(0)` — assert `getUserTotalLocked(attacker) == amount` again (real lock restored), but `totalBoostFactor` (and `userInfos[attacker].factor` in `ReferralStorage`) still equals `sqrt(amount-halfAmount)` — i.e., stale/understated versus the refreshed value that `updateTotalFactor` would compute (`sqrt(amount)`).
6. Have a second, uninvolved referrer (victim) with an existing referee call `trigger()` (simulate via `masterMagpie`) before and after step 5, and show `boosted(victim)` / resulting `refererAmount` computed in `trigger()` is strictly larger after the attacker's `cancelUnlock()`, purely due to the deflated `totalBoostFactor`, despite the victim's own real locked/factor being unchanged.
7. Repeat the lock/startUnlock/cancelUnlock cycle to accumulate enough drift/`rewardAmount` inflation that `sum(rewardAmount)` across referrers exceeds `MGP.balanceOf(referralStorage)`; assert that a legitimate referrer's `claimReward()` call reverts (`InsufficientRewardBalance` from insufficient MGP transfer) despite having a nonzero, previously-accrued `rewardAmount`.
