### Title
BIP-340 FROST algorithm verifies signatures against the non-normalized (odd-Y) group key, producing signatures invalid on-chain - (File: networks/bitcoin/src/crypto.rs)

### Summary
The Bitcoin `Schnorr` algorithm wrapping `IetfSchnorr<Secp256k1, Hram>` computes the BIP-340 challenge over the x-coordinate of the group key (`x(A)`), but verifies the aggregate signature equation `sG == R + cA` against the full `group_key` point as-is. When the threshold group key has an odd Y coordinate, BIP-340 requires the secret/public key to be effectively negated (the x-only key corresponds to `lift_x(x) = -A`), yet `sign_share` never negates `params.secret_share()` and `verify` never normalizes `group_key`. The internal verification in `complete` therefore accepts a signature that no BIP-340 verifier (Bitcoin consensus) will accept.

### Finding Description
- `Hram::hram` (networks/bitcoin/src/crypto.rs:59-73) hashes `x(R) || x(A) || m` (x-coordinates only) and conditionally negates the challenge when `R` is odd-Y, correctly handling nonce parity per BIP-340.
- However, no equivalent normalization exists for `A`. In `Schnorr::sign_share` the secret share is used verbatim via `self.0.sign_share(params, ...)` (crypto.rs:128-136), which signs `s = r + c·a` where `a·G = A` exactly, not `-a`.
- In `Schnorr::verify` (crypto.rs:139-150), `self.0.verify(group_key, nonces, sum)` calls `SchnorrSignature::verify(group_key, c)` which checks `R + cA - sG == 0` (crypto/schnorr/src/lib.rs:88-109) against the literal `group_key`. Only `s` is negated for an odd `R` (crypto.rs:146).
- An external BIP-340 verifier reconstructs `P = lift_x(x(A))`, which equals `-A` when `A` is odd-Y, and checks `sG = R_even + c·P`. The produced signature satisfies `sG = -R + cA` (after s-negation), so the verifier computes `R' = sG - c·(-A) = -R + 2cA ≠ ±R`, and rejects.
- `ThresholdKeys`/`ThresholdView` (`crypto/dkg/src/lib.rs:414-447`, `:518-521`) apply scalar/offset tweaks that freely change the group key's Y parity with no parity normalization, so an odd-Y `group_key` occurs for roughly half of all tweaked keys.

### Impact Explanation
For any signing session whose (tweaked) group key is odd-Y, every signer’s internal integrity check in `AlgorithmSignatureMachine::complete` (crypto/frost/src/sign.rs:465) reports success and returns a signature that is invalid under BIP-340. Transactions signed for such outputs cannot be broadcast — funds are provably unspendable via this path despite the threshold protocol completing "successfully", i.e., improper signature validation yields signatures no valid verifier accepts.

### Likelihood Explanation
Deterministic for any key with odd-Y `group_key`; parity is effectively random across TapTweak/offset applications, so ~50% of distinct keys are affected. No malicious participant is required — honest execution triggers it.

### Recommendation
Normalize the effective key before use: in `sign_share`, conditionally negate `params.secret_share()` (or equivalently incorporate a parity-fixing offset into `ThresholdView`) when `needs_negation(group_key)`; in `verify`, verify against `conditional_select(&group_key, &-group_key, needs_negation(&group_key))` so the internal check matches the BIP-340 verifier’s equation.

### Proof of Concept
1. Build `ThresholdKeys<Secp256k1>` and apply `.offset(delta)` chosen so `group_key()` has odd Y (try deltas until `needs_negation` is true).
2. Run `AlgorithmMachine::new(Schnorr::new(), keys)` for `t` participants through `preprocess`/`sign`/`complete` on any 32-byte `msg`.
3. `complete` returns `Ok(sig)` (internal `verify` passes, crypto/frost/src/sign.rs:465-467).
4. Verify `(x(group_key), sig)` with any BIP-340 implementation (e.g., `bitcoin::secp256k1` `verify_schnorr`): verification fails, since `lift_x(x(A)) = -A` while the signature satisfies `sG = -R + cA`.
