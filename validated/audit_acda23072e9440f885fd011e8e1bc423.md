### Title
Push-sweep permanently marks capped/dropped-risk commits as "reviewed," letting an attacker-sized diff evade future security re-scans - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The reported CDPVault bug is a **fail-open state-drift pattern**: a partial remediating action (partial liquidation) is treated as sufficient to flip a security-relevant state (unsafe → safe), permanently suppressing further enforcement even though the underlying risk was never fully addressed. The closest reachable analog in this repository is in the `security-guidance` plugin's commit/push security-review gate, which has the same shape: a **partial review is recorded as a complete review**, which then durably suppresses future scanning of the un-reviewed portion.

### Finding Description
`handle_push_sweep_posttooluse` (and the analogous `handle_commit_review_posttooluse`) enforces a hard cap `MAX_DIFF_FILES`/`MAX_PUSH_SWEEP_FILES` on the number of files sent to the LLM security reviewer per fire [1](#0-0) . When a diff/push range exceeds the cap, `_prioritize_diff_files` selects only the top-N files by a heuristic risk score and silently drops the rest [2](#0-1) . After the (partial) review runs, the push-sweep path advances the "reviewed" watermark and appends the **entire commit range** (`tail`) to the persistent `reviewed_shas` cache via `_append_reviewed_shas`, even though a subset of files in that range were never actually sent to the reviewer [3](#0-2) . The code comments acknowledge this tradeoff directly: "We still mark `tail` reviewed afterward — the dropped files are by construction the low-risk ones... Per-commit review remains the primary surface for those files" [4](#0-3) . Once a SHA is recorded in `reviewed_shas`, `_compute_push_sweep_base` treats everything up to that SHA as already covered and will not re-diff or re-review it on subsequent pushes [5](#0-4) (module referenced but not directly inspectable in this session — see Likelihood note).

The risk-scoring heuristic (`_SECURITY_RISK_PATH_TOKENS`) is a static substring allowlist over file paths (e.g. `auth`, `route`, `handler`, `exec`) [6](#0-5) . A file that introduces a genuine vulnerability but whose path doesn't match any risk token (e.g. `utils/helpers.py`, `lib/formatter.py`) scores low and is deprioritized/dropped whenever a commit or push range exceeds the file-count cap. This is structurally identical to the CDPVault bug: a bounded, partial corrective action (reviewing only the top-N riskiest-looking files) is accepted as equivalent to full coverage, and the state (`reviewed_shas`) is updated to reflect "fully checked," permanently foreclosing the backstop (per-commit `Stop` hook re-review) that the comments themselves say is needed to cover the gap.

### Impact Explanation
If an attacker (or a compromised/malicious contributor, or Claude itself under prompt injection) structures a push/commit so that a genuinely dangerous file is bundled alongside many low-risk-scoring files exceeding `MAX_PUSH_SWEEP_FILES`/`MAX_DIFF_FILES`, the dangerous file can be scored low by the path-token heuristic, get dropped from the reviewed set, and the SHA range is nonetheless marked fully reviewed. Because `reviewed_shas` gates all *future* push-sweep re-scans of that range, the vulnerable file is never surfaced by this security control, unless the earlier per-commit `Stop`/`PostToolUse` hook happened to catch it in a smaller diff. This weakens (but does not fully eliminate, since `Stop`-hook review is a separate code path) the plugin's security-review guarantee for large or intentionally-padded changesets. This is a defense-in-depth/detection-gate bypass in an optional guidance plugin, not a core Claude Code approval/sandbox/tool-authorization bypass — impact is limited to reduced detection coverage in `security-guidance`, not to unauthorized command execution or credential disclosure.

### Likelihood Explanation
The bug requires a large diff/push (more files than `MAX_DIFF_FILES`, default 30, or `MAX_PUSH_SWEEP_FILES`) that includes at least one dangerous file whose path doesn't match the static risk-token list — a plausible but not trivial condition to engineer, especially adversarially (e.g., padding a push with many innocuous file touches to force the cap). The per-commit `Stop` hook is a partial mitigating backstop that the push-sweep authors call out explicitly, so real-world exploitability depends on that backstop having already missed the same file (e.g., if the file was introduced across many separate commits each individually under the per-commit cap, or if per-commit review was skipped/rate-limited via `atomic_check_rate_limit`, which is also fail-open on state read errors [7](#0-6) ). I could not fully verify `_compute_push_sweep_base`'s exact base/advance logic (in `diffstate.py`) within this session due to tool-call limits, so I cannot confirm with certainty whether the marked-reviewed range is later fully skipped on all subsequent sweeps or only partially. This uncertainty should be resolved by reading `diffstate.py` in full before treating this as confirmed.

### Recommendation
1. When `_prioritize_diff_files` drops files due to the cap, do not advance/record `reviewed_shas` for the full range; only mark the SHAs whose files were actually all reviewed, or persist a marker that the range was partially reviewed so a later sweep with a smaller effective diff (or a raised cap) can complete coverage of the dropped files.
2. Alternatively, always guarantee eventual coverage: track dropped-file identities (not just SHAs) in state and prioritize them first on the next sweep, rather than relying solely on the "the per-commit Stop hook already covers it" assumption.
3. Expand or complement the static risk-token heuristic with a cheaper structural signal (e.g., new function/class additions, changed control-flow) so genuinely risky but non-conventionally-named files are not systematically deprioritized.
4. Add telemetry alerting when `diff_files_dropped > 0` and the corresponding SHAs are being marked reviewed, so operators can audit how often full coverage is being silently skipped.

### Proof of Concept
Conceptual reproduction (not run against a live instance):
1. In a repo with the `security-guidance` plugin's push-sweep hook enabled, prepare a push containing `MAX_PUSH_SWEEP_FILES + 1` (e.g. 31+) changed files.
2. Ensure 1 of those files introduces a real vulnerability (e.g., `subprocess.run(cmd, shell=True)` with tainted input) but is named something that doesn't match any token in `_SECURITY_RISK_PATH_TOKENS` (e.g. `app/format_output.py`) [6](#0-5) .
3. Ensure the other 30 files have paths matching risk tokens (e.g. `app/auth_handler.py`, `app/api_client.py`, etc.) so they outrank the vulnerable file in `_prioritize_diff_files`'s scoring and get sent to the LLM reviewer instead [8](#0-7) .
4. Push. `handle_push_sweep_posttooluse` runs, caps the reviewed set to the 30 higher-scoring files, and the vulnerable file is dropped (`diff_files_dropped` incremented) [9](#0-8) .
5. The full push range (`tail`) is nonetheless recorded in `reviewed_shas`, so a future push-sweep will treat this SHA range as already covered and will not re-diff/re-review the vulnerable file [4](#0-3) .

Note: I was not able to fully trace `diffstate.py`'s `_compute_push_sweep_base`/`_append_reviewed_shas` internals in this session (tool-call budget exhausted), so step 5's exact persistence semantics should be independently verified against that file before treating this as a confirmed, exploitable finding rather than a design-comment-supported hypothesis.

```python
    """Rolling-window rate limit: allow at most `max_per_window` calls per
    `window_s` seconds, per (session_id, key).

    Returns (allowed: bool, count_in_window: int). count_in_window is the
    post-decision count (i.e., includes this call if allowed) so callers can
    emit it directly as a telemetry gauge.

    Replaces session-lifetime `atomic_check_counter` for commit-review and
    push-sweep. Telemetry showed a small but persistent share of sessions hit
    the lifetime cap, and those were multi-day persistent sessions that then
    lost coverage for many subsequent commits — not burst abusers. A rolling
    hour keeps the same cost ceiling for any 1h window while letting long
    sessions regain coverage.

    State key: rate_limits: {"<key>": [ts, ts, ...]}. Timestamps are pruned
    on every call so the list is bounded by max_per_window; no migration
    needed from the old `counters` dict — different key.
    """
    import time as _time
    now = _time.time()
    cutoff = now - window_s

    def _check(state):
        buckets = state.setdefault("rate_limits", {})
        ts_list = buckets.get(key, [])

            return False, len(ts_list)

        buckets[key] = ts_list
        return True, len(ts_list)
```

```python
def _prioritize_diff_files(diff_files, cap):
    """When `diff_files` exceeds `cap`, return the top-`cap` by security
    relevance plus the count dropped. Otherwise return (diff_files, 0).

    Score = (risk_tokens_in_path, not_low_priority, added_lines). The
    added-lines proxy is `content.count('\\n+')` which counts diff additions
    cheaply without re-parsing hunks. This is a heuristic, not a guarantee —
    the goal is to review the likely-dangerous subset of an over-cap diff
    instead of reviewing nothing. Diffs that exceed the cap are typically
    large multi-file scaffolds, and the cross-file source→sink vulnerabilities
    in them concentrate in a handful of api/client/route files.
    """
    if len(diff_files) <= cap:
        return diff_files, 0

    def _score(item):
        fp, content = item
        low = fp.lower()
        # Prepend "/" so leading-slash patterns in _LOW_PRIORITY_PATH_TOKENS
        # match top-level dirs (git diff paths are repo-root-relative, e.g.
        # `migrations/001.py` not `/migrations/001.py`). Same trick as
        # _is_reviewable_source.
        low_slashed = "/" + low
        risk = sum(1 for t in _SECURITY_RISK_PATH_TOKENS if t in low)
        low_prio = (
            fp.endswith(_LOW_PRIORITY_SUFFIXES)
            or any(t in low_slashed for t in _LOW_PRIORITY_PATH_TOKENS)
        )
        # added_lines: count('\n+') over-counts by including '+++' header and
        # any literal '+' at line start in context, but it's a consistent
        # ordinal across files in the same diff which is all we need.
        added = content.count("\n+")
        return (risk, not low_prio, added)

    ranked = sorted(diff_files, key=_score, reverse=True)
    return ranked[:cap], len(diff_files) - cap
```
