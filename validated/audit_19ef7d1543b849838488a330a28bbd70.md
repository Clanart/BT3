## Analysis: Local Hyperbridge Analog Found

**Core broken invariant in the external report:** an attacker with more capital can force an honest party's *correct* stake/claim out of a bounded, shared resource by flooding it with cheap, independent entries until the honest party's slot is evicted/exhausted — the honest party loses something they legitimately paid for, purely due to a capacity-based eviction rule with no per-payer authorization check.

**Local Hyperbridge analog:** `pallet-bandwidth`'s FIFO subscription queue combined with `BandwidthManager.sol`'s unauthenticated cross-tenant sponsorship purchase path.

### Title
Unauthenticated cross-tenant bandwidth purchases let a funded attacker evict a victim app's paid subscription via FIFO cap eviction - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` stores prepaid byte allowances per `(app_chain, app)` key in a FIFO list capped at 1024 entries (`MAX_SUBSCRIPTIONS`). Any purchase — from any payer, on any registered source chain — can target an arbitrary `(chain, app)` pair because the sponsorship design intentionally decouples the payer's chain from the credited app: "a buyer on Ethereum can credit an app on Base." Nothing checks that the purchaser is the app owner, a partner, or otherwise authorized for that specific `(chain, app)`. When the FIFO list is full, the oldest entry is silently evicted and its remaining, already-paid-for bytes are permanently lost (`SubscriptionEvicted`). A well-funded attacker can repeatedly call `purchase()` targeting a victim app's `(chain, app)` key with the cheapest tier until the queue reaches capacity, then continue purchasing to push out the victim's legitimately purchased (and possibly much larger/expensive) subscription before it is consumed.

### Finding Description
The purchase flow: [1](#0-0) 

is implemented on-chain with no allowlist/ownership check on who may credit a given `(app_chain, app)`: [2](#0-1) 

Every purchase appends unconditionally through `push_subscription`, which evicts the oldest entry once the list is at its 1024 cap, discarding its `remaining_bytes` permanently and only emitting an event — no compensation, no refund path: [3](#0-2) 

The only actor-level gate in the whole flow is that `request.from` must equal the registered `BandwidthManager` contract address for the *source chain* the purchase message arrived from — it does **not** constrain which `(app_chain, app)` the purchase body targets: [4](#0-3) 

Because `Allowance` is keyed by `msg.chain`/`msg.app` taken straight from the purchase body (not from `request.source`), and the manager contract's `purchase()` is permissionlessly callable by anyone who can pay the tier price, any account can push subscriptions into any other app's queue on any chain the attacker chooses to buy from.

### Impact Explanation
This satisfies the required impact class of "stealing or loss of funds" against the pivot that "bridged assets... bandwidth balances must move exactly once and only to the rightful beneficiary and amount." Here, a victim's already-paid bandwidth balance can be destroyed by a third party who never should have had write access to that specific `(chain, app)` bucket. The victim app effectively loses money it spent on a `BandwidthManager.purchase()` call (fee token pulled at purchase time is non-refundable — see purchase mechanics) and loses byte allowance it is entitled to, with the funds unrecoverable once evicted. For an app that has few live subscriptions (the common case — most apps do not carry hundreds of queued tiers), an attacker only needs to push enough purchases to reach the 1024 cap and then a handful more to specifically evict the victim's entries, i.e., far fewer than 1024 total transactions if the attacker interleaves purchases before the victim tops up, or exactly enough to roll the FIFO past the victim's position. This is a bounded-cost griefing attack purely funded by capital, with no relayer/prover/admin compromise required.

### Likelihood Explanation
The path is fully permissionless and public: `BandwidthManager.purchase()` on any registered EVM source chain, dispatched as an ISMP POST to `pallet-bandwidth`'s `on_accept`. No governance, relayer misbehavior, or malicious node is required — only capital to pay tier prices (the cheapest tier is $50/100KB per the docs). The eviction logic in `push_subscription` unconditionally evicts on cap regardless of who owns the entries being evicted, so the mechanism is deterministic and reliable once the attacker has funded enough purchases.

### Recommendation
Scope subscription capacity or eviction protection per payer/purchase-origin, or require that credits to a given `(chain, app)` only be creditable by the app itself (or an explicitly allowlisted sponsor list per app), rather than by any arbitrary payer on any chain. Alternatively, remove the hard FIFO eviction in favor of rejecting new purchases when the list is full (forcing the new purchaser to wait/consolidate) so no party's paid allowance can be destroyed by a third party's purchase.

### Proof of Concept
1. Victim app `V` legitimately purchases the $1000/8MB tier for `(EVM-8453, V)` via `BandwidthManager.purchase()` — one entry lands in `Allowance[(EVM-8453, V)]`.
2. Attacker, with no relationship to `V`, calls `BandwidthManager.purchase()` (on any chain with a registered manager) repeatedly with the cheapest $50/100KB tier, setting the purchase message's `app = V`, `chain = EVM-8453` each time.
3. Each call lands on `pallet-bandwidth::on_accept`, which calls `push_subscription(&EVM-8453, &V, ...)` — see [5](#0-4) .
4. Once `Allowance[(EVM-8453, V)]` reaches 1024 entries, each subsequent attacker purchase evicts the oldest entry — see `push_subscription`'s `list.remove(0)` at [6](#0-5) .
5. Once the attacker's purchases roll past `V`'s legitimate $1000-tier entry, it is evicted with `SubscriptionEvicted { lost_bytes }`, permanently destroying the bytes `V` paid for, with no recourse.

### Purchase messages skip the gate

The router uses `Pallet::is_purchase_message(request)` to identify a purchase from a registered manager (`request.source` is managed _and_ `request.from` matches the registered manager address). Purchase messages bypass the gate — otherwise a depleted app couldn't ever recharge.

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
