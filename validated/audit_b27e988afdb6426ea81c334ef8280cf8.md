### Title
Unbounded Attacker-Controlled `royalty_percentage` in NFT Transfer Program Causes Unhandled Exception / DoS When Building Offers - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`NFTWallet.make_nft1_offer()` reads the `royalty_percentage` value directly out of the curried transfer-program puzzle of an NFT and casts it to `uint16` without any prior bounds validation. Because the transfer program is arbitrary CLVM data chosen entirely by the NFT's creator (there is no consensus rule constraining `royalty_percentage` to a sane basis-point range), a malicious NFT can be minted with a wildly out-of-range percentage value (e.g. `2**64`). Any wallet that later tries to include this NFT in an offer via `make_nft1_offer` will hit an unhandled `ValueError` while constructing the `uint16`, aborting the offer-creation flow — the same "extreme externally-supplied value breaks arithmetic/casting and DoSes the caller" bug class described in the report, just manifesting as a type-cast overflow instead of a Solidity multiplication overflow.

### Finding Description
`royalty_percentage` for an NFT is uncurried straight from the NFT's own puzzle reveal in `TransferProgramPuzzle.match()`: [1](#0-0) 

`percentage.as_int()` performs no range check — the value is whatever the NFT minter curried into the puzzle. This raw value flows into `NFTWallet.make_nft1_offer`, where it is parsed and then coerced to `uint16` with no prior validation: [2](#0-1) 

If `royalty_percentage` exceeds the `uint16` range, `uint16(royalty_percentage)` raises, which propagates out of `make_nft1_offer` uncaught. The same unguarded pattern also affects `NFTWallet.royalty_calculation`, exposed via the `nft_calculate_royalties` RPC, which performs the percentage arithmetic (`abs(amount) // len(...) * percentage // MAX_ROYALTY_BASIS_POINTS`) without checking `percentage` bounds at all: [3](#0-2) 

This is directly analogous to the reported `getVestedAmount()` issue: an externally/attacker-supplied numeric field (there: `amount` from a Merkle leaf; here: `royalty_percentage` from an NFT's curried puzzle) is fed into arithmetic/casting logic without an upper-bound check, and extreme values cause the function to fail for any legitimate caller trying to interact with that data (there: claim/query; here: build an offer or query royalties for that NFT).

By contrast, `compute_royalty_amount()` (used only in the offered/fungible-asset royalty payout branch) already validates `percentage <= MAX_ROYALTY_BASIS_POINTS` and raises a clear error, showing the team was aware of this bug class in one code path but did not apply the same guard to `royalty_percentage` parsing in `make_nft1_offer`/`royalty_calculation`: [4](#0-3) 

### Impact Explanation
Any wallet (offer counterparty) that attempts to build a trade offer involving a maliciously crafted NFT — one whose transfer program was curried with an out-of-range `royalty_percentage` — will hit an unhandled exception in `make_nft1_offer`, aborting that transaction-building flow. The same NFT will also break the `nft_calculate_royalties` RPC used by CLI/GUI clients to preview royalty amounts before creating an offer. This effectively bricks trading (offer creation) for that specific NFT for every user who tries to interact with it, which matches the report's "spend-triggered halt of the affected operation for that user/asset" impact class, though scoped to the wallet's offer-construction logic rather than block-level consensus.

### Likelihood Explanation
Minting an NFT with an arbitrary curried value in its transfer program puzzle requires no special privilege — any unprivileged user can mint/deploy such an NFT and distribute or offer it to a counterparty. Since `royalty_percentage` is never constrained on-chain, this is trivially reachable by any NFT creator, making likelihood high for any wallet that agrees to trade with an attacker-supplied NFT.

### Recommendation
Validate `royalty_percentage` immediately after uncurrying it from the transfer program (in `TransferProgramPuzzle.match()` and/or in `NFTWallet.make_nft1_offer`/`royalty_calculation`), rejecting or clamping values greater than `MAX_ROYALTY_BASIS_POINTS` (10000) with a clear, catchable error before any `uint16()` cast or arithmetic is performed — mirroring the bound check already present in `compute_royalty_amount()`.

### Proof of Concept
1. Mint an NFT whose transfer program (`NFT_TRANSFER_PROGRAM_DEFAULT`) is curried with `royalty_puzzle_hash` and a `percentage` value far outside `uint16` range (e.g. `2**64`), since `puzzle_for_transfer_program` performs no validation on `percentage` at construction time.
2. Have any wallet call `NFTWallet.make_nft1_offer` (or the `nft_calculate_royalties` RPC) to build/query an offer that includes this NFT.
3. `royalty_percentage = int(royalty_percentage_raw)` reads the oversized value, and `uint16(royalty_percentage)` raises `ValueError`, which is unhandled and aborts offer creation for that NFT.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
