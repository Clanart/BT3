### Title
Malformed preprocess/share vector causes panic abort in Bitcoin transaction signing - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary

`TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` trust the length of attacker-controlled `Vec<Preprocess>` / `Vec<SignatureShare>` values. A participant who supplies a shorter vector than the number of transaction inputs causes an out-of-bounds index / `remove(0)` on an empty vector, panicking every honest signer mid-protocol — an unauthenticated-party-triggered denial of service analogous to CVE-2019-5061's "trigger state-changing processing before authentication completes".

### Finding Description

In `TransactionSignMachine::sign`, the per-participant preprocess map is split into per-input maps by blindly indexing `commitments[c]` for `c in 0 .. self.sigs.len()` (send.rs:364-371). `Self::Preprocess` is `Vec<Preprocess<Secp256k1, ()>>`, deserialized from untrusted bytes by `read_preprocess` (send.rs:351-353), which calls `sig.read_preprocess(reader)` per signer machine but never validates that the resulting per-participant vector length equals `self.tx.input.len()`.

Symmetrically, `TransactionSignatureMachine::complete` calls `shares.remove(0)` on each participant's `Vec<SignatureShare>` once per input (send.rs:417-419), panicking if a participant supplied an empty or short share vector.

The panic occurs *after* honest signers have already consumed their FROST nonces in `sig.sign(...)` (send.rs:383-390), mirroring the CVE pattern: the unauthenticated message triggers irreversible processing (nonce commitment consumption and a panic abort of the whole signing attempt) before any verification establishes that the peer's data is well-formed.

### Impact Explanation

Any threshold participant (or anyone able to feed bytes to `read_preprocess` / `read_share`) can abort every Bitcoin signing session it joins at negligible cost, repeatedly, preventing the multisig from ever producing a transaction. This is a liveness/DoS failure against the wallet: fees, withdrawals, and batch transactions depending on `TransactionMachine` signing are blocked. Because each honest signer consumes its preprocess/nonces in the failed `sign` call, retries require a fresh preprocess round, letting a single faulty participant starve the protocol indefinitely — matching the CVE's "traffic flapping" style repeated-disruption DoS.

### Likelihood Explanation

The trigger is fully within attacker-controlled input: the participant's preprocess/share messages are the public, expected inputs to `sign`/`complete`. No collusion, leaked keys, or broken assumptions are needed — one participant encoding `n-1` (or zero) preprocesses instead of `n` panics all honest signers. The absence of any length check makes it trivially reachable.

### Recommendation

Validate lengths before processing: in `TransactionSignMachine::sign`, check `commitments.len() == self.sigs.len()` for every participant and return a `FrostError` variant identifying the faulty participant instead of indexing blindly. Likewise, in `complete`, check each participant's share vector length equals the number of inputs before calling `remove(0)`, and report the mismatch as a blameable error rather than panicking.

### Proof of Concept

```rust
// Build a SignableTransaction with 2 inputs, obtain TransactionMachine via
// signable.multisig(&keys), then preprocess to get TransactionSignMachine.
// A malicious participant i submits a preprocess Vec with only 1 element:

let mut preprocesses: HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>> = ...;
// honest participants send sigs.len() == 2 preprocesses;
// attacker sends:
preprocesses.insert(attacker, vec![attacker_preprocess_for_input_0]); // len 1, not 2

// Honest signer calls:
sign_machine.sign(preprocesses, b"")
// panics at send.rs `commitments[c]` with index out of bounds when c == 1.

// Same for complete(): attacker sends SignatureShare vec of length 0,
// `shares.remove(0)` at send.rs:419 panics.
```
