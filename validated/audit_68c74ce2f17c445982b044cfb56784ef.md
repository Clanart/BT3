### Title
Silent transfer failures in Tron IntentGatewayV2 escrow withdrawal cause fund loss — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of `IntentGatewayV2` releases escrowed order tokens using a raw low-level `.call` with `IERC20.transfer.selector`, checking only that the external call did not revert — it never decodes/validates the ERC20 boolean return value. This is the same root-cause bug class as the referenced report ("Lack of USDT support due to use of `transfer`"): unchecked/blindly-trusted token transfer results in the accounting engine believing a transfer succeeded when the token silently failed. Note that the canonical EVM version of the same logic (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`) already uses `SafeERC20.safeTransfer`, but the Tron variant was not updated to match.

### Finding Description
In `withdraw()` (escrow release for both order fills and refunds, and fee redemption) and in the `SweepDust` handler within `onAccept()`, the Tron `IntentGatewayV2.sol` performs: [1](#0-0) [2](#0-1) [3](#0-2) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```

The `success` flag from a low-level `.call` only indicates that the callee did not revert — it says nothing about the ERC20 function's own boolean return value. Any non-standard-compliant ERC20 that returns `false` on failure instead of reverting (a widely-known real-world token behavior class, the same family the referenced USDT report is about) will make this call return `success = true` even though no tokens moved. Since the code never decodes `returndata` into a `bool`, it treats this as a completed transfer and immediately decrements `_orders[commitment][token]`.

This directly contrasts with the hardened, already-shipped EVM implementation in `IntentsBase.sol::_withdraw`, which uses `SafeERC20.safeTransfer` (validates both call success and boolean return, and supports tokens with no return value like USDT): [4](#0-3) 

`withdraw()` is reachable through multiple unprivileged, public paths: same-chain `cancelOrder` refunds by the order owner, cross-chain `RedeemEscrow`/`RefundEscrow` message delivery via `onAccept`, all of which operate on tokens chosen freely at order-placement time (per the intents design, "any token" can be used as input/output), exactly mirroring the conditions in the original report.

### Impact Explanation
Once escrow accounting is decremented without the underlying tokens actually leaving the contract, the intended beneficiary (a solver expecting fill payout, or a user expecting a cancellation refund) permanently loses their claim to those tokens — the `_orders` mapping no longer reflects any escrow for that commitment/token, so a legitimate retry is impossible (`UnknownOrder` will now revert on any subsequent attempt). The tokens remain unaccounted for inside the contract, effectively a silent loss of funds for the rightful beneficiary. This satisfies the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" impact classes, since escrow state (a value that must move exactly once to the rightful beneficiary and amount) is corrupted without an actual matching transfer.

### Likelihood Explanation
This requires a token used as order input/output that returns `false` on transfer failure rather than reverting — a real, non-adversarial token behavior class (distinct from USDT's "no return value" quirk, but from the same "non-standard-return-handling" bug family). Because the intents system is explicitly designed to accept arbitrary tokens for input/output (as in the original report's context), an order creator or solver choosing such a token (intentionally or not) triggers the flaw without needing any relayer, prover, or admin compromise — purely through normal `placeOrder`/`fillOrder`/`cancelOrder` usage.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()`, the `SweepDust` handler, and the dispatcher-transfer-back logic) with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, matching the pattern already used correctly in `evm/src/apps/intentsv2/IntentsBase.sol`. This validates both call success and, when present, the returned boolean, reverting on either a false return or empty non-contract call.

### Proof of Concept
1. Order creator places a cross-chain order with a `TokenInfo.token` pointing at an ERC20 that returns `false` (rather than reverting) when a `transfer` would fail (e.g., due to an internal blacklist, paused state, or insufficient allowance edge case reachable during withdrawal window).
2. Escrow succeeds initially via `safeTransferFrom` at `placeOrder` time (lines 453/399), so `_orders[commitment][token]` is correctly credited.
3. Later, order is cancelled (`cancelOrder`, same-chain path) or filled cross-chain, triggering `withdraw()`.
4. Inside `withdraw()`, `token.call(...)` returns `success = true` (no revert) but the token's internal transfer logic returns `false` and moves no funds.
5. `if (!success) revert TransferFailed();` does not fire; `_orders[body.commitment][token] -= amount;` proceeds, permanently clearing the escrow record.
6. Beneficiary receives zero tokens; the escrowed tokens remain stuck in the `IntentGatewayV2` contract with no accounting path to recover them, and any retry reverts with `UnknownOrder`.
