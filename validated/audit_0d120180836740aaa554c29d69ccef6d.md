### Title
`mWOMSVBaseRewarder._calExpireForfeit` never computes a forfeit, permanently withholding the cooling-down-lock yield penalty from remaining lockers - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWomSV.getRewardablePercentWAD` exists and correctly computes a reduced rewardable percentage for accounts with tokens in cooldown (unlocking) slots [1](#0-0) , exactly mirroring the sibling `vlMGPBaseRewarder._calExpireForfeit`, which calls `vlMGP.getRewardablePercentWAD(_account)` to derive the forfeit [2](#0-1) . However, `mWOMSVBaseRewarder._calExpireForfeit` never calls `mWOMSV.getRewardablePercentWAD(_account)` (or any equivalent) — it sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount = _amount - rewardableAmount` is always `0` [3](#0-2) .

### Finding Description
`getReward(account, receiver)` is called by MasterMagpie (via multiclaim) with `onlyMasterMagpie` and `updateReward` modifiers, then loops over reward tokens calling `_sendReward` [4](#0-3) . `_sendReward` computes `forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account])`, sends `toSend = userRewards - forfeitAmount` to the receiver, zeroes `userRewards`, and if `forfeitAmount > 0` routes it via `_queueNewRewardsWithoutTransfer` to top up `rewardInfo.queuedRewards`/`rewardPerTokenStored` for remaining lockers [5](#0-4) .

The bug is in `_calExpireForfeit`: `rewardableAmount` is initialized to `_amount` and never adjusted by the account's lock/cooldown state before the `if (rewardableAmount > _amount) revert` check, so `forfeitAmount = _amount - rewardableAmount` is always `0`, regardless of how much of the account's `mWOMSV` balance is in cooldown [3](#0-2) . This is unlike the vlMGP counterpart, which multiplies `_amount` by `vlMGP.getRewardablePercentWAD(_account)` (a value strictly `< 1e18` for accounts with cooling-down slots) before computing the difference [2](#0-1) . Since `mWomSV.getRewardablePercentWAD` is fully implemented and correctly reduces the percent for cooldown/unlocking amounts [1](#0-0) , the omission of this call in `mWOMSVBaseRewarder._calExpireForfeit` is a functional bug, not by design.

Any unprivileged account holding `mWOMSV` that has started `startUnlock` (a cooldown slot) can simply call `getReward`/`claim` through MasterMagpie's multiclaim path and receive their **full** accrued reward with zero forfeiture, whereas the intended design (mirrored by vlMGP) is to forfeit a proportional share of rewards for tokens sitting in cooldown, and redistribute that forfeited share to the remaining, fully-locked stakers via `_queueNewRewardsWithoutTransfer`.

Existing modifiers (`onlyMasterMagpie`, `updateReward`) do not stop this — they only gate caller identity and refresh reward accounting, they do not enforce forfeiture logic. There is no `nonReentrant` issue here since `getReward` doesn't need reentrancy protection to trigger this — the bug is purely in the forfeit math being a no-op.

### Impact Explanation
This causes theft/permanent loss of unclaimed yield for other `mWomSV` lockers: the forfeit amount that should be redistributed to remaining locked stakeholders (via `queuedRewards`/`rewardPerTokenStored` top-up) is instead paid out in full to the cooling-down account, permanently denying that yield to the remaining lockers. This matches the Immunefi impact class "theft or permanent freezing of unclaimed yield." The loss is real but scoped to the "yield distribution fairness" mechanism — it does not touch principal, but each `getReward` call by a partially-cooling-down account is an economic transfer of the withheld forfeit percentage of the reward token to that account, from what should have gone to other lockers.

### Likelihood Explanation
Preconditions are trivial and permissionless: any user who locked `mWOMSV`, called `startUnlock` for part of their balance (still keeping `userRewards[_rewardToken][_account] > 0` unclaimed), and then calls `getReward`/claims via MasterMagpie multiclaim will trigger this. No special capital, front-running, or privileged role is required — it happens on every single claim by any account with an active cooldown slot. This is directly and repeatably exploitable (or rather, silently occurs by design flaw) on every reward claim for any account with a nonzero cooldown amount.

### Recommendation
Fix `_calExpireForfeit` in `rewards/mWOMSVBaseRewarder.sol` to mirror `vlMGPBaseRewarder._calExpireForfeit`: call `mWOMSV.getRewardablePercentWAD(_account)` (add this to `ILocker`/relevant interface if not already exposed) and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before computing `forfeitAmount`, e.g.:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
}
```

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie` with a reward token.
2. Have two users, A and B, each lock equal amounts of `mWOMSV` (e.g., 1000 tokens).
3. Manager calls `queueNewRewards`/`donateRewards` to accrue rewards for both A and B.
4. Have A call `startUnlock` on half their balance (500 tokens go into cooldown), leaving `userRewards[token][A] > 0` unclaimed.
5. Immediately (while still in cooldown, before `endTime`), have A call `getReward(A, A)` via MasterMagpie multiclaim.
6. Assert: `rewardInfo.queuedRewards` (or `rewardPerTokenStored`) before the call vs. after the call — expected: nonzero forfeit amount queued (since `getRewardablePercentWAD(A) < 1e18`), but observed: `queuedRewards` unchanged (forfeit == 0), and A receives their entire full unforfeited reward despite having 50% of balance in cooldown.
7. Compare against `vlMGPBaseRewarder` equivalent test (locker in cooldown claiming via `queueMGP`/`getReward`) where `queuedRewards` correctly increases by the forfeited amount, confirming the mWOMSV implementation is missing this behavior.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
