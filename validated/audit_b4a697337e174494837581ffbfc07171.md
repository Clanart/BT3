### Title
Git's recursive-clone RCE protection is explicitly disabled during clone, and submodule `file://` protocol is unconditionally re-enabled during checkout/pull - (File: `app/src/lib/git/clone.ts`, `app/src/lib/git/submodule.ts`)

### Summary
The escrow report's broken invariant is: a safety check that should gate access based on current trust/ownership is bypassed or left disabled, letting an untrusted party (the ex-owner / attacker) act as if the check never existed. The closest verifiable analog in GitHub Desktop is that Desktop explicitly turns off a Git-level anti-RCE guard when cloning attacker-supplied repositories, and separately unconditionally allows the `file://` submodule protocol during submodule initialization — both of which are guards Git itself ships specifically to stop a hostile repository from executing code or reading files outside the working tree.

### Finding Description
In `clone()` [1](#0-0) , Desktop builds the clone environment as:

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
```

`GIT_CLONE_PROTECTION_ACTIVE` is a Git-native safeguard for recursive/`--recursive` clones (the clone always includes `--recursive`, see `args.push('clone', '--recursive', ...)` in the same function) that Git added to defend against maliciously crafted repositories that use symlinked `.git` directories/nested submodules and hooks to escape the intended clone target and execute code or write files during the clone (the class of bug fixed upstream as CVE-2024-32004/CVE-2024-32020-class hardening). Desktop sets this to `'false'` for every clone it performs, i.e. it deliberately opts out of Git's own mitigation for exactly the attacker model this task cares about — an attacker who controls the cloned repository.

Compounding this, `updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` flag which, when true, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation [2](#0-1) . Git disabled `file://` submodules by default specifically because a submodule URL controlled by a hostile top-level repository could point at an arbitrary local path (e.g. another user's already-cloned repo, or a path containing hooks/config) and be silently checked out. Re-enabling it via `protocol.file.allow=always` removes that guard for repositories where this code path is exercised (e.g. checkout of a branch with an uninitialized `file://` submodule).

Both of these are "approvals" (Git's built-in trust decisions) that are supposed to be scoped to the operator's own intent, but Desktop unconditionally clears/overrides them for content it does not control — i.e., the untrusted, attacker-authored repository content (its `.gitmodules`, nested repos, symlinks) gets to run with Git's protections turned off.

### Impact Explanation
If either guard is load-bearing on the currently embedded Git version (rather than fully superseded by an upstream fix), a maliciously crafted repository — supplied via clone URL, or fetched/checked out with a submodule reference an attacker controls — can leverage the disabled `GIT_CLONE_PROTECTION_ACTIVE` or `protocol.file.allow=always` to write/execute outside the intended clone directory, or to have a submodule silently pull from an arbitrary local `file://` path. This lands squarely in the requested impact categories: code execution or file write/read outside the repo, driven purely by content in a cloned/fetched repository.

### Likelihood Explanation
Both code paths are hit on ordinary, unprivileged user actions — cloning any repository (`_clone`/`clone()`), and checking out a branch or pulling that references an uninitialized submodule — with zero unusual user steps and no local/admin access, credential leakage, or social engineering required. The only unresolved uncertainty is which specific Git CVE(s) `GIT_CLONE_PROTECTION_ACTIVE` corresponds to in the exact `dugite`/Git version Desktop bundles, and whether that CVE is otherwise mitigated by version alone; this could not be confirmed from the indexed code (the embedded Git binary/version file was not available to inspect in this pass).

### Recommendation
- Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (or scope it strictly to only the specific benign case it was added for, with a code comment justifying why bypassing the protection is safe), so recursive clones benefit from Git's own anti-RCE hardening.
- Restrict `-c protocol.file.allow=always` in `updateSubmodulesAfterOperation` to submodules whose URL has been explicitly reviewed/approved by the user (or drop it entirely and let Git's default `protocol.file.allow=user` semantics apply), rather than enabling it broadly for submodule init triggered by content from an untrusted repository.
- Add regression tests asserting that cloning/checking out a repository with a `file://`-protocol submodule pointing outside the intended directory fails by default.

### Proof of Concept
1. Attacker publishes a Git repository containing a `.gitmodules` entry (or nested submodule structure) crafted per the known recursive-clone RCE technique that `GIT_CLONE_PROTECTION_ACTIVE` is designed to block, or a submodule URL of the form `file:///absolute/path/to/sensitive/or/other/local/repo`.
2. Victim clones the repository in GitHub Desktop via `_clone()` → `clone()` in `app/src/lib/git/clone.ts`, which always runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false`, or checks out a branch that triggers `updateSubmodulesAfterOperation(..., allowFileProtocol=true)` in `app/src/lib/git/submodule.ts`.
3. Because Git's protective checks are disabled/overridden by Desktop's own environment/flag injection, the malicious submodule reference or nested-repo structure is processed without the guard that would normally reject or warn about it, allowing the attacker's payload to execute or to pull in file content from outside the intended repository.

Note: I could not directly execute or fully trace this end-to-end against Desktop's bundled Git version in this pass (no terminal/filesystem access here), so exploitability specifically depends on whether the bundled Git version still relies on `GIT_CLONE_PROTECTION_ACTIVE` for the relevant mitigation and whether any callers set `allowFileProtocol` to `true` for genuinely untrusted content — this would need to be validated on a running checkout of the repo.
