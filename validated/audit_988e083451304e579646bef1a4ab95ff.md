### Title
Cached FROST preprocess reused across distinct messages leaks the validator's MuSig secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to CVE-2019-16910 (insufficient entropy/context in deterministic nonce usage enabling key recovery via repeated signing), the coordinator's DKG-confirmation signing protocol deterministically re-derives its FROST nonces from a single cached 32-byte seed keyed only by `(b"DkgConfirmer", attempt)`. The signed message — `set_keys_message(set, removed, key_pair)` — is not part of that context. Every call to `share` or `complete` calls `share_internal` → `preprocess_internal` → `AlgorithmSignMachine::from_cache` → `sign`, producing a fresh signature share with the *same* `(d, e)` nonces whenever the peer preprocesses are identical. If two invocations within one attempt sign different `msg` bytes (different `key_pair` or `removed` set), the same effective nonce `d + e·ρ` is bound to two different Schnorr challenges, and the signer's MuSig secret key share is recoverable by simple algebra.

### Finding Description
`preprocess_internal` stores/loads a `CachedPreprocess` under `CachedPreprocesses` keyed solely on `self.context = (b"DkgConfirmer", self.attempt)` (lines 123–145). The seed drives `ChaCha20Rng::from_seed(*seed.0)` in `seeded_preprocess`, making both nonce scalars `d, e` fully deterministic per context (`crypto/frost/src/sign.rs:121-133`, `crypto/frost/src/curve/mod.rs:94-121`). In `sign`, the effective nonce is `d + e·ρ_i` where `ρ_i` is the binding factor computed over `group_key`, `hash_msg(msg)`, and the transcript of all preprocesses (`crypto/frost/src/sign.rs:361-396`).

Critically, `share()` (line 304) and `complete()` (line 312) both invoke `share_internal` → `machine.sign(preprocesses, msg)`. `complete` even expects a prior `share` to have occurred ("trying to complete a machine which failed to preprocess"). The message is built inside `share_internal` from `set_keys_message(&self.spec.set(), &self.removed…, key_pair)` (lines 296–301) — none of which is committed in the cache context. The header comment itself concedes the design is only safe because "the received nonce commitments (or the message to be signed)" must not be distinct across calls (lines 25–48); the message-binding assumption is enforced nowhere in code.

Two shares `s₁ = r + c₁·x` and `s₂ = r + c₂·x` over identical nonce `r` yield `x = (s₁ − s₂)/(c₁ − c₂)`. Since `c` in the Schnorrkel path commits to `R`, `group_key`, and `msg` (`crypto/frost/src/algorithm.rs:208`, `crypto/schnorrkel/src/lib.rs:110-129`), any change to `key_pair` or the removed set under the same attempt produces `c₁ ≠ c₂` while `r` is identical (same peer preprocesses → same `ρ`).

### Impact Explanation
Recovery of the validator's MuSig secret share — the key that is the root of trust for validator-set operations — from publicly observed signature shares. Unlike ordinary FROST share leakage (which reveals only a threshold share), this key underlies the coordinator's on-chain signing authority.

### Likelihood Explanation
Requires two `sign` calls within one `(DkgConfirmer, attempt)` context over the same peer preprocess set but a different `msg` — e.g., a re-derived or updated `KeyPair`/removed-set between the `share` and `complete` invocations, or re-execution after partial state. The code comments explicitly rely on BFT ordering rather than cryptographic binding for this invariant, so it cannot occur under arbitrary peer messages; it is a latent fragility rather than a guaranteed remote exploit — consistent with Medium severity, mirroring the source CVE.

### Recommendation
Include the message (or `key_pair`/`removed` hash) in the cache context so any distinct message derives a distinct seed, or record the signed `msg` hash alongside `CachedPreprocesses` and abort if a subsequent `sign` under the same context sees a different message. Persist the generated `AlgorithmSignMachine` (or a "consumed" flag) instead of regenerating it per call.

### Proof of Concept
1. Within attempt `N`, peers' preprocesses `P` are finalized; `share(P, key_pair_A)` emits `s₁` over nonce `r = d + e·ρ` and challenge `c₁ = H(R, group_key, msg_A)`.
2. `complete(P, key_pair_B, …)` (or a second `share` after the confirmed key pair changes within the same attempt) emits `s₂` over the same `r` but `c₂ = H(R, group_key, msg_B)`.
3. Compute `x = (s₁ − s₂)·(c₁ − c₂)⁻¹ mod l`, recovering the MuSig secret share; verify `Ristretto::generator() * x ==` the validator's public key.

Uncertainty: I did not read `coordinator/src/tributary/handle.rs` to confirm whether `share`/`complete` can actually be driven with divergent `key_pair` in one attempt; the finding stands on the code's own stated safety invariant (lines 34–35) not being enforced at the crypto layer.
