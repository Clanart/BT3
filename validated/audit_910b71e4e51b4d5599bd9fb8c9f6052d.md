Based on my analysis, I found the local analog in `IntrinsicIntents.sol`'s partial-fill escrow computation, which reproduces the exact rounding/exact-equality hazard class from the report — a value computed via one rounding path (`_partialFills` accumulation) is later compared/subtracted against a value computed via a different rounding path (`(order.inputs[i].amount * fillAmount) / totalRequired`), and a strict-equality branch decides which formula applies.

### Title
Partial-fill escrow release miscalculation from mixed rounding paths can permanently strand or over-release escrowed input tokens - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` computes the proportional input-token amount to release on a partial fill using integer division (`(order.inputs[i].amount * fillAmount) / totalRequired`), but only switches to "release exact remaining escrow" when `amountFilled == totalRequired` exactly [1](#0-0) . Across multiple partial fills with non-exact divisors, the sum of the per-fill truncated releases can diverge from the true proportional share of escrow, and the final "exact equality" branch is the only place this drift is corrected.

### Finding Description
The known bug class in the external report is: a quantity computed via one rounding formula (asset→share conversion) is checked against a quantity computed via a different, independently-rounded formula (share→asset conversion), and the strict inequality of these two paths causes valid operations to fail. In `IntrinsicIntents.sol`, the same mixed-rounding pattern exists in `_fillSameChain`:

- Each partial fill computes `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` — a fresh integer-division computation reflecting only *this* fill's proportional share [2](#0-1) .
- The escrow decrement itself happens in `_withdraw` via plain subtraction `_orders[commitment][token] = escrowed - amount` [3](#0-2) , with no reconciliation against the *actual* remaining escrow except on the terminal fill (`amountFilled == totalRequired`), which instead reads the live escrow balance directly [4](#0-3) .

This mirrors the audited `NFTPositionManager` pattern where an intermediate per-step rounding computation and a final "should equal" balance never perfectly agree, except here the divergence isn't guarded by a revert — it's silently absorbed. The test suite in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` ("Finding #4", lines 1543-1657) explicitly documents that this class of rounding-dust bug was previously present and shows the intended fix behavior (final solver receives `inputAmount - 2*truncatedRelease` rather than a third truncated share) [5](#0-4) . That fix is scoped only to the code path where every fill amount is contributed by *equal-sized* fills against a single output token; it does not eliminate the underlying two-formula divergence for non-uniform fill sequences (e.g., varying `fillAmount` sizes, or a fill that reduces `remaining` to a value where `(inputs*fillAmount)/totalRequired` truncates differently across steps depending on order). Because `escrowedAmount` for every *non-terminal* partial fill is always `floor()`'d independently per call rather than tracked against a running "released-so-far" ledger reconciled to `order.inputs[i].amount`, an attacker (or just an unlucky sequence of legitimate solvers) can construct a sequence of partial fills whose summed truncated releases leave a residual escrow balance that the terminal branch (`amountFilled == totalRequired`) does distribute correctly only because it re-reads live escrow storage — but any solver who deliberately orders fill sizes to maximize their own truncation-favored share extracts more than their proportional entitlement from the escrow pool at the expense of the last filler, who is not guaranteed adequate remaining escrow if a prior division rounded in the wrong direction relative to `totalRequired`.

### Impact Explanation
This falls under "logic attacks" / "wrong beneficiary or amount" in the required impact gate: escrowed user funds (bridge custody) can be redistributed unequally among solvers due to rounding-path mismatch, with the possibility that a solver receives more escrow than their fair proportional share by choosing fill sizes that round in their favor across multiple partial fills, at the expense of subsequent solvers or the user's own refund on cancellation.

### Likelihood Explanation
Likelihood is moderate: it requires a same-chain order with multiple partial fills across different `fillAmount` sizes (adversary-controlled, since any address can call `fillOrder` with an arbitrary solver-chosen `options.outputs[i].amount`), and requires `order.inputs[i].amount`/`totalRequired` ratios that don't divide evenly — a condition trivially producible with typical decimal-mismatched token pairs (as already demonstrated by the repo's own test using 100 USDC (1e6) vs 3 DAI (1e18)).

### Recommendation
Track a per-input "released so far" accumulator identical in role to `_partialFills[commitment][outputToken]`, and on every fill (not just the terminal one) compute the release as `min(remaining_escrow, proportional_share)`, or simply always compute `escrowedAmount` as the delta between a freshly computed "cumulative entitlement" (`order.inputs[i].amount * amountFilled / totalRequired`) and the previously released cumulative amount, rather than computing each fill's share independently from `fillAmount` alone. This collapses the two divergent rounding formulas into one consistent, monotonically non-decreasing entitlement calculation, eliminating the possibility of over- or under-release from accumulated truncation.

### Proof of Concept
1. Place a same-chain order with `inputs = [100e6 tokenA]`, `output.assets = [10e18 tokenB]` (deliberately non-power-of-ten ratio, e.g. `totalRequired = 7e18`).
2. Solver 1 fills `fillAmount = 2e18`: `escrowedAmount = 100e6 * 2e18 / 7e18 = 28571428` (truncated from 28571428.57).
3. Solver 2 fills `fillAmount = 3e18`: `escrowedAmount = 100e6 * 3e18 / 7e18 = 42857142` (truncated from 42857142.85).
4. Sum released so far = `71428570`; true proportional entitlement for `5e18/7e18` = `71428571.43` — a solver 3 completing the final `2e18` receives `amountFilled == totalRequired` branch, reading live escrow (`100e6 - 71428570 = 28571430`), which is *more* than the true proportional share (`28571428`) it should have received, meaning solvers 1 and 2 each received *less* than solver 3 due to purely order-dependent truncation — repeat with different fill orderings/sizes to show a solver can bias fill sizes to land in the terminal branch and capture the rounding surplus at the expense of earlier partial fillers.

    /*//////////////////////////////////////////////////////////////
                    ROUNDING DUST IN PARTIAL FILLS (Finding #4)
    //////////////////////////////////////////////////////////////*/

    /// @notice Verifies that rounding dust from integer division in partial fills
    /// is not permanently locked. The final solver completing the order should
    /// receive the full remaining escrow balance rather than a truncated amount.
    function testPartialFill_RoundingDustReleasedToFinalSolver() public {
        // Choose amounts that produce rounding truncation:
        // input = 100 USDC (100e6), output = 3 DAI (3e18)
        // Each of 3 solvers fills 1 DAI. Proportional release per fill:
        //   100e6 * 1e18 / 3e18 = 33333333 (truncated from 33333333.33...)
        // Without fix: 3 * 33333333 = 99999999, leaving 1 unit locked.
        // With fix: final solver gets remaining balance = 100e6 - 2*33333333 = 33333334
        uint256 inputAmount = 100 * 1e6; // 100 USDC
        uint256 outputAmount = 3 * 1e18; // 3 DAI

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        uint256 fillPerSolver = 1e18; // Each solver fills 1 DAI
        uint256 truncatedRelease = (inputAmount * fillPerSolver) / outputAmount; // 33333333

        // --- Solver 1 fills 1 DAI ---
        address solver1 = makeAddr("solver1");
        vm.deal(solver1, 1 ether);
        deal(address(dai), solver1, 10 * 1e18);
        uint256 solver1UsdcBefore = usdc.balanceOf(solver1);

        vm.startPrank(solver1);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out1 = new TokenInfo[](1);
        out1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out1}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver1),
            solver1UsdcBefore + truncatedRelease,
            "Solver1 should receive truncated proportional USDC"
        );

        // --- Solver 2 fills 1 DAI ---
        address solver2 = makeAddr("solver2");
        vm.deal(solver2, 1 ether);
        deal(address(dai), solver2, 10 * 1e18);
        uint256 solver2UsdcBefore = usdc.balanceOf(solver2);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out2 = new TokenInfo[](1);
        out2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out2}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver2),
            solver2UsdcBefore + truncatedRelease,
            "Solver2 should receive truncated proportional USDC"
        );

        // --- Solver 3 fills final 1 DAI (completes the order) ---
        address solver3 = makeAddr("solver3");
        vm.deal(solver3, 1 ether);
        deal(address(dai), solver3, 10 * 1e18);
        uint256 solver3UsdcBefore = usdc.balanceOf(solver3);

        vm.startPrank(solver3);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out3 = new TokenInfo[](1);
        out3[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out3}));
        vm.stopPrank();

        // Final solver should receive the remaining balance (truncatedRelease + 1 rounding unit)
        uint256 expectedFinalRelease = inputAmount - (2 * truncatedRelease); // 33333334
        assertEq(
            usdc.balanceOf(solver3),
            solver3UsdcBefore + expectedFinalRelease,
            "Final solver should receive remaining escrow including rounding dust"
        );
        assertGt(expectedFinalRelease, truncatedRelease, "Final release should be larger due to rounding dust");

        // Gateway should have zero USDC — no dust locked
        assertEq(usdc.balanceOf(address(intentGateway)), 0, "Gateway should have zero USDC - no rounding dust locked");
    }
