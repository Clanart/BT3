### Title

Bitcoin coinbase outputs are credited before consensus maturity and scheduled as spendable - (File: processor/src/networks/bitcoin.rs)

### Summary

Serai’s Bitcoin output-processing path treats a coinbase output like any other confirmed UTXO, even though Bitcoin coinbase outputs cannot be spent until they are 100 blocks deep. `Scanner::scan_block` explicitly includes `block.txdata[0]`, the coinbase transaction, and documents that a post-processing pass is required if outputs must be immediately spendable. [1](#0-0)  The processor accepts every output returned by `Bitcoin::get_outputs` once the ordinary `N::CONFIRMATIONS` gate has passed, filtering only by `N::DUST`; it does not distinguish an immature coinbase output from a mature spendable output. [2](#0-1) [3](#0-2) 

### Finding Description

`Scanner::scan_transaction` constructs a `ReceivedOutput` solely from a matching `script_pubkey`, storing its offset, `TxOut`, and outpoint without checking whether the containing transaction is a coinbase or whether that coinbase is mature. [4](#0-3)  `Scanner::scan_block` then applies that logic to every transaction in `block.txdata`, including index zero, which is the coinbase transaction in a valid Bitcoin block. [1](#0-0) 

The processor’s scanner processes blocks only after the normal confirmation threshold and submits all returned non-dust outputs to the multisig scheduler; there is no additional check requiring a coinbase output to have 100 confirmations. [2](#0-1) [3](#0-2)  The scheduler records scanned outputs as UTXOs, sums their reported balances, removes them from the available set when planning, and generates a spending plan. [5](#0-4) [6](#0-5) 

`SignableTransaction::new` converts each reported `ReceivedOutput` into a transaction input using its claimed outpoint and stores its claimed `TxOut` as the corresponding Taproot prevout. [7](#0-6) [8](#0-7)  The transaction signer then produces signatures committing to all those prevouts through `Prevouts::All`. [9](#0-8)  A transaction spending a coinbase output before depth 100 is consensus-invalid, regardless of whether its Taproot signatures are valid.

### Impact Explanation

A coinbase payout to a Serai-controlled external or offset address can be reported as received balance before it is legally spendable. The scheduler may consume that UTXO in a plan, obtain valid threshold signatures for it, and produce a transaction that Bitcoin nodes reject until the coinbase reaches maturity. Because scheduling drains the selected UTXOs from `self.utxos`, an unsuccessful spend can also remove the output from normal scheduler accounting even though the actual funds remain on-chain. [10](#0-9) 

This creates a “funds reported received that are not spendable” condition analogous to accepting an ERC20 transfer whose effective deposited value or transfer semantics differ from what the protocol assumes. It can stall payments, strand scheduler state, and require manual recovery or explicit rescanning to reintroduce the mature coinbase UTXO.

### Likelihood Explanation

Any miner or mining pool can create a coinbase output paying Serai’s P2TR script; this does not require access to Serai’s private key, cooperation from validators, a malicious RPC result, or control of an existing Serai UTXO. `Scanner::new` maps the base group key to a P2TR script, while `register_offset` maps deterministic offsets to additional P2TR scripts. [11](#0-10) [12](#0-11) 

The attack requires the miner to win a block, which makes arbitrary triggering costly, but coinbase payouts to externally supplied addresses are a normal Bitcoin mechanism and can also occur accidentally through mining-pool payout configuration. Once included, the output only needs to survive Serai’s ordinary confirmation threshold to enter scheduler state, while Bitcoin requires 100 confirmations before it can be spent. [2](#0-1) 

### Recommendation

Track coinbase maturity separately from ordinary deposit confirmations. In the Bitcoin `get_outputs` implementation, skip `block.txdata[0]` or mark its outputs as immature until `block_height + 100` has been reached. Do not rely on `N::CONFIRMATIONS` unless it is guaranteed to be at least Bitcoin’s 100-block coinbase-maturity rule.

`ReceivedOutput` or the processor-level `Output` should expose whether it came from a coinbase transaction and the height at which it appeared, since the txid/vout and `TxOut` alone do not encode maturity. Scheduler admission should reject or defer `OutputType::External`, branch, change, and forwarded outputs whose source transaction is an immature coinbase. A regression test should confirm that a valid block containing a coinbase payment to the threshold key produces no spendable scheduler UTXO before depth 100.

### Proof of Concept

A miner constructs a valid block whose coinbase contains an output paying the base threshold key:

```rust
let script = p2tr_script_buf(group_key).unwrap();

let coinbase = Transaction {
  version: Version(2),
  lock_time: LockTime::ZERO,
  input: vec![TxIn {
    previous_output: OutPoint::null(),
    script_sig: coinbase_script,
    sequence: Sequence::MAX,
    witness: Witness::new(),
  }],
  output: vec![TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: script,
  }],
};

let block = Block {
  header: valid_header,
  txdata: vec![coinbase],
};

let outputs = Scanner::new(group_key).unwrap().scan_block(&block);
assert_eq!(outputs.len(), 1);
```

`scan_block` returns the coinbase `ReceivedOutput`, containing the coinbase txid, vout, amount, and zero offset. [3](#0-2)  The scheduler then uses it as a plan input and generates signatures over the claimed prevout, but Bitcoin consensus rejects the resulting spend until the coinbase is 100 blocks old.     let mut res = Vec::new();
