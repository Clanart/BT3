Based on my investigation, I found a plausible structural analog in GitHub Desktop's diff/patch line-selection machinery, though I want to be explicit that I could not fully trace a dynamic exploit chain (no terminal/test execution available) — the finding below is based on static code-path analysis of the referenced files.

### Title
Selection-index desync when expanding/merging diff hunks can cause wrong lines to be committed - (File: app/src/ui/diff/text-diff-expansion.ts)

### Summary
GitHub Desktop tracks which diff lines a user has selected for a partial commit using a single flat "absolute index" space computed as `hunk.unifiedDiffStart + lineIndex` [1](#0-0) . This index space is recomputed by `expandTextDiffHunk` and `mergeDiffHunks` whenever a user expands hidden context lines around a hunk (e.g. clicking "Load more lines"), including shifting/merging existing hunks [2](#0-1) . The user's previously-recorded `DiffSelection` (which stores selections keyed by these same absolute indices) is not migrated when hunks are merged/renumbered, so after an expansion the same numeric index can refer to a semantically different diff line than when the user selected it. `formatPatch`/`formatPatchToDiscardChanges` then blindly trust `selection.isSelected(absoluteIndex)` [3](#0-2)  to decide what to include in the generated patch that is fed to `git apply`.

### Finding Description
The invariant the app relies on is: "a given absolute line index always identifies the same diff line for as long as a `DiffSelection` bitmap built against it is alive." This invariant is analogous to the ZapMathLib bug's assumption that a raw numeric value can be reinterpreted across different unit/decimal domains without conversion — here the "domain" is the hunk-line index space before vs. after an expansion/merge.

- `expandTextDiffHunk` recomputes `unifiedDiffStart`/`unifiedDiffEnd` for the hunk being expanded and for hunks *after* it, offsetting by `numberOfNewDiffLines` [4](#0-3) .
- When `shouldMergeWithAdjacent` is true, two hunks (with two separate header lines) become one hunk via `mergeDiffHunks`, which drops one header line and concatenates the rest [5](#0-4) . This changes which line occupies each index within and after the merged hunk.
- Nothing in this path touches or invalidates the file's existing `DiffSelection` (`file.selection`), which is a UI-level object separate from the diff/hunks data structure. The next time the user commits, `formatPatch` re-derives `absoluteIndex` from the *new* hunk layout and looks it up in the *old* selection bitmap [6](#0-5) .
- Because the new content lines pulled into the expansion come from the working-tree file (`newContentLines`), an attacker who controls the content of a fetched/cloned/checked-out file (e.g. via a crafted upstream commit) controls exactly how many lines get inserted and whether a merge occurs, giving them influence over how far the index space shifts.

Existing guards do not stop this: there is no re-validation step in `formatPatch` verifying that the selection bitmap and the hunk list it was built from are still in sync (no versioning/generation check on `DiffSelection` vs. the diff object). The only "check" is the empty-patch guard at the end [7](#0-6) , which does not detect a shifted-but-nonempty selection.

### Impact Explanation
**Medium** — If exploitable end-to-end, a user reviewing a diff, expanding context around a change, and then partially staging/committing lines could silently commit or discard the wrong lines (e.g. commit an unintended change while believing they excluded it, or vice versa). This falls under "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories. It requires no elevated privileges and is triggered by ordinary diff review/partial-commit UI interaction on a repository the user already has open.

### Likelihood Explanation
**Medium-Low** — Triggering it requires a specific UI sequence (expand hunk context → partially (de)select lines → commit) and specific file layouts (gaps between hunks close enough to trigger a merge, per `DefaultDiffExpansionStep`/`getHunkHeaderExpansionType` [8](#0-7) ). I was not able to execute the app or its test suite in this environment to confirm the selection bitmap is not remapped elsewhere (e.g. in `diff-explorer.ts` or the React diff component), so this should be treated as a code-level risk requiring dynamic confirmation, not a proven exploit.

### Recommendation
Whenever hunks are expanded or merged (`expandTextDiffHunk`, `mergeDiffHunks`, `getTextDiffWithBottomDummyHunk`), remap the associated `DiffSelection` bitmap using the same index-shift/merge arithmetic applied to the hunks (shift ranges by `numberOfNewDiffLines`, and correctly interleave selection bits when two hunks are merged) instead of leaving the selection object untouched. Alternatively, key `DiffSelection` by a stable per-line identity (e.g. old/new line-number pair) rather than a positional index that is invalidated by any hunk mutation.

### Proof of Concept
Not independently executed (no terminal access in this session). Suggested reproduction for a background engineer to confirm/refute:
1. Create a repo with a file containing two separate hunks separated by more than `DefaultDiffExpansionStep` (20) unchanged lines.
2. In Desktop, open Changes, select the second hunk's added line for commit (leave everything else unselected).
3. Expand the gap between hunks until the two hunks merge (`shouldMergeWithAdjacent` true) via repeated "Expand" clicks.
4. Commit only the previously selected line and inspect the resulting commit via `git show` to verify whether the actually-selected physical line still matches the originally intended one, or whether an unintended line was included/excluded due to index shift.

export function getHunkHeaderExpansionType(
  hunkIndex: number,
  hunkHeader: DiffHunkHeader,
  previousHunk: DiffHunk | null
): DiffHunkExpansionType {
  const distanceToPrevious =
    previousHunk === null
      ? Infinity
      : hunkHeader.oldStartLine -
        previousHunk.header.oldStartLine -
        previousHunk.header.oldLineCount

  // In order to simplify the whole logic around expansion, only the hunk at the
  // top can be expanded up exclusively, and only the hunk at the bottom (the
  // dummy one, see getTextDiffWithBottomDummyHunk) can be expanded down
  // exclusively.
  // The rest of the hunks can be expanded both ways, except those which are too
  // short and therefore the direction of expansion doesn't matter.
  if (hunkIndex === 0) {
    // The top hunk can only be expanded if there is content above it
    if (hunkHeader.oldStartLine > 1 && hunkHeader.newStartLine > 1) {
      return DiffHunkExpansionType.Up
    } else {
      return DiffHunkExpansionType.None
    }
  } else if (distanceToPrevious <= DefaultDiffExpansionStep) {
    return DiffHunkExpansionType.Short
  } else {
    return DiffHunkExpansionType.Both
  }
}
