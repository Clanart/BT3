## Finding Analysis

I verified the flow across `wombat/WombatStaking.sol` and `wombat/SmartWomConvert.sol`. The core mechanism described is real, but one part of the question's framing does not match the code: the "bonus reward token registered for the asset is also one of the fee currencies" precondition is **not** actually required. The `smartConvert` revert is only triggered on the `wom` fee leg (`feeInfo.isMWOM && rewardToken == wom` at [1](#0-0) ), not on the bonus-token loop, which only calls `_sendRewards` for whatever bonus token differs (never routed through `smartConvert` unless the bonus token itself is `wom`, an unlikely/unsupported registration). So that specific precondition described in the question is a mismatch with the actual code.

That said, the underlying root cause it's pointing at is real and doesn't need that precondition:

### Title
Hardcoded `_minRec == _amountIn` in `SmartWomConvert.smartConvert` causes harvest-path reverts that permanently block deposit/depositLP/withdraw - (File: wombat/SmartWomConvert.sol, wombat/WombatStaking.sol)

### Summary
`SmartWomConvert.smartConvert` always calls `_convertFor` with `_minRec = _amountIn` [2](#0-1) , requiring the WOM->mWom conversion to return at least 1:1 in value. Because `_sendRewards`/`smartConvert` is invoked unconditionally inside `_toMasterWomAndSendReward`, which is on the call path of every `deposit`, `depositLP`, `withdraw`, and `harvest` for any pool with an active `isMWOM` fee [3](#0-2) [4](#0-3) , a revert in `smartConvert` bricks user-facing principal operations for that pool.

### Finding Description
`smartConvert` computes `currentRatio()` from the `womMWomPool` and, if it is below `buybackThreshold` (default 9000/10000), swaps a portion of the WOM fee through the router for mWom while depositing the rest 1:1 [5](#0-4) . It then unconditionally requires `_minRec == _amountIn`, i.e., the combined swap+deposit output must be >= the full input amount, even though the AMM swap leg is executed precisely because the pool price is unfavorable (`mWomToWom < buybackThreshold`) — a swap under those conditions will typically return less mWom than WOM put in, causing `convertAmount + amountRec < _minRec` and reverting with `MinRecNotMatch()` [6](#0-5) .

This call is reached from `_sendRewards`, which every `deposit`, `depositLP`, `withdraw`, and `harvest` call runs through via `_toMasterWomAndSendReward` [7](#0-6) [8](#0-7) , as long as `smartWomConverter != address(0)`, the pool isn't marked fee-free (`isPoolFeeFree[_lpToken]`), an active `isMWOM` fee exists, and any nonzero WOM reward was harvested from `masterWombat`. None of `nonReentrant`, `whenNotPaused`, or `_onlyActivePoolHelper` prevent this — they gate caller identity/pause state, not the internal revert from a failed conversion.

An attacker (unprivileged) can push `womMWomPool`'s cash/liability ratio so that `currentRatio() < buybackThreshold` by swapping through the public router, and keep it depressed; every subsequent `deposit`/`withdraw`/`depositLP` call across the affected pool(s) will then revert as long as WOM rewards are non-zero at harvest time — this can be sustained without any theft, purely to grief/freeze principal deposits and withdrawals.

### Impact Explanation
This blocks legitimate users from depositing or withdrawing principal for any pool where the `isMWOM` fee is active and `smartWomConverter` is set, for as long as the manipulated ratio (or naturally depegged ratio) persists — matching "Temporary freezing of funds for at least 24 hours" if the attacker (or market conditions) keep the ratio below `buybackThreshold` for that duration. There is no direct fund theft; the impact is availability/DoS on principal movement.

### Likelihood Explanation
Feasibility depends entirely on the attacker's ability to move/hold `womMWomPool`'s price ratio below `buybackThreshold` (90%) for a sustained window, which requires capital proportional to the pool's liquidity and is subject to third-party arbitrage correcting it back. This is a real design flaw (a hardcoded, non-slippage-tolerant `_minRec` in a mandatory harvest-fee path) rather than a contrived edge case, but exploiting it deliberately (vs. it happening from natural depeg) requires meaningful capital and is not permanent — arbitrageurs or `smartWomConverter.owner()` (via `buybackThreshold`/`ratio` setters) can restore normal operation, capping the "freeze" window's certainty.

### Recommendation
Do not hardcode `_minRec = _amountIn` in `smartConvert`; instead compute a realistic minimum output that accounts for the AMM swap leg's expected slippage (e.g., using `estimateTotalConversion` with an acceptable tolerance), or make the fee-conversion step non-blocking — e.g., wrap the `smartConvert` call in a try/catch (or a low-level call) inside `_sendRewards` so that a fee-conversion failure degrades gracefully (e.g., falls back to direct `mWom.deposit()` or skips the WOM fee for that harvest) rather than reverting the entire deposit/withdraw transaction.

### Proof of Concept
Foundry fork test plan:
1. Fork BSC/mainnet at a block where `WombatStaking.smartWomConverter` is set and an `isMWOM` fee is active and non-fee-free for a target pool.
2. Use the router to swap WOM into the `womMWomPool` (or mWom out) in size sufficient to push `SmartWomConvert.currentRatio()` below `buybackThreshold`.
3. Call `deposit(...)` (or `withdraw(...)`) via the pool's `WombatPoolHelper` as a normal unprivileged user with a nonzero pending WOM harvest amount.
4. Assert the transaction reverts with `MinRecNotMatch()` bubbled up from `SmartWomConvert._convertFor`, and that repeating the call while the ratio stays depressed always reverts — demonstrating deposits/withdrawals are blocked, not merely a one-off failure.
5. Restore the pool ratio and confirm deposit/withdraw succeed again, confirming the causal link. [9](#0-8) [10](#0-9) [2](#0-1)

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
