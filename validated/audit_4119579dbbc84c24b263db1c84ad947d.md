### Title
Fee/vsize accounting omits the OP_RETURN data output, so `SignableTransaction` pays an internal rate that diverges from the transaction's actual on-chain cost - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Usual incident — a protocol computing value at a fixed internal rate while the externally-settled quantity differs — `SignableTransaction::new` computes its vsize (and therefore its fee and change) using only the declared `payments`, never accounting for the OP_RETURN output it appends when `data` is supplied. The internally-priced transaction is smaller than the transaction actually signed and broadcast, so the effective feerate is lower than the caller-specified `fee_per_vbyte`, the minimum-relay check is applied against an undercounted size, and the change amount is computed against an underpriced fee.

### Finding Description
`SignableTransaction::new` builds `tx_outs` including the OP_RETURN data output at `send.rs:194-202`, but the size estimator `calculate_weight_vbytes` is invoked with only `payments` — it reconstructs a transaction whose `output` field contains just the payment TxOuts (and optionally change), with no `data` output included. Both call sites pass `payments`, not the real output list:

- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` at `send.rs:204`, then `needed_fee = fee_per_vbyte * vbytes` at `send.rs:206`.
- `let (weight_with_change, vbytes_with_change) = Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));` at `send.rs:225-227`, with the change value set to `input_sat - (payment_sat + fee_with_change)` at `send.rs:228-230`.

The data is attacker-influenced: the Bitcoin network path embeds an up-to-80-byte `InInstruction`/`Shorthand` payload as the OP_RETURN (`data.as_ref().map_or(0, Vec::len) > 80` bound at `send.rs:171`), so an unprivileged external sender who triggers a protocol transaction carrying data causes a size undercount of roughly `9 + len(data)` bytes (up to ~89 real bytes / weight units).

Consequences of the divergence between the priced size and the actual size:

- `needed_fee` and the change calculation assume the smaller transaction, so the effective feerate of the signed transaction is `fee_per_vbyte * vbytes_priced / vbytes_actual`, strictly below the requested rate whenever `data` is non-empty.
- The minimum-relay guard `if needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` at `send.rs:211` is checked against the undercounted `vbytes`, so a transaction can pass validation while actually paying below the node's min relay feerate — it will be silently rejected by relay, while the processor treats the outputs as spent (they remain committed to `Prevouts::All` and the `prevouts`/`offsets` bookkeeping).
- `fee()` at `send.rs:138-141` reports `sum(inputs) - sum(outputs)`, which will differ from `needed_fee()` whenever this undercount applies, breaking the documented invariant that the achieved fee equals the needed fee. [1](#0-0) [2](#0-1) 

### Impact Explanation
External users can attach up to 80 bytes of data that flows into the OP_RETURN output while the fee machinery prices a transaction without it. The resulting transaction either pays a meaningfully lower feerate than configured — degrading confirmation reliability for every Serai Bitcoin send carrying data — or, when `fee_per_vbyte` is chosen near the minimum relay bound, produces a transaction the network will not relay at all even though `SignableTransaction::new` accepted it and the multisig signs it (`send.rs:373-397`). Inputs committed to such a transaction are effectively frozen pending out-of-band recovery, and the discrepancy between `needed_fee()` and `fee()` corrupts any accounting that trusts the internal estimate. This is the same economic shape as the Usual bug: a quantity settled internally at one rate while the external system settles the larger actual quantity.

### Likelihood Explanation
Any transaction constructed with `data: Some(..)` triggers the undercount — this is a deterministic arithmetic mismatch, not a probabilistic one. The data path is exercised by normal InInstruction-bearing transfers into Serai, so the condition arises from ordinary unprivileged usage rather than exotic adversary positioning. Severity is Medium: it does not directly steal funds (the difference accrues to change or to a slightly-larger-than-priced fee), but it produces incorrect verifier/accounting output and can brick payments at the relay boundary.

### Recommendation
Pass the fully-constructed `tx_outs` (including the OP_RETURN output) into the size estimation — e.g., extend `calculate_weight_vbytes` to take the actual `Vec<TxOut>` rather than rebuilding from `payments`, or add the OP_RETURN output's serialized size (`8 + compact_size(len) + script len`) to the weight computation in `SignableTransaction::new`. Apply the same corrected size to both the no-change and with-change fee computations and to the minimum-relay guard.

### Proof of Concept
1. Construct `inputs` worth `payment_sat + fee_per_vbyte * vbytes_with_change + DUST` exactly.
2. Call `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)`.
3. The returned `SignableTransaction`'s `tx` has outputs `payments + OP_RETURN(80 bytes) + change`, but `needed_fee` equals `fee_per_vbyte * vbytes(payments + change)` — undercounting by ~89 bytes of witness/base weight. `tx.fee()` therefore equals a feerate of `fee_per_vbyte * vbytes_priced / vbytes_actual < fee_per_vbyte`.
4. Set `fee_per_vbyte` such that `needed_fee` exactly equals `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` for the priced size; the real transaction then pays less than 1 sat/vbyte of its actual size and is rejected by `sendrawtransaction`, while the inputs' `prevouts` were already consumed by the signing flow (`send.rs:375`).

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
