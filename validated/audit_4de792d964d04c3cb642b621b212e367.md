### Title
Malicious repository with a broken/hostile submodule permanently DoS's `checkoutBranch`/`checkoutCommit` even though the top-level ref switch already succeeded - (File: `app/src/lib/git/checkout.ts`)

### Summary
`checkoutBranch` and `checkoutCommit` run `git checkout` first and then unconditionally call `updateSubmodulesAfterOperation`, which shells out to `git submodule update --init --recursive` over *all* submodules in one command. There is no per-submodule error isolation and no way to skip a single bad submodule, so a repository (cloned/fetched, i.e. attacker-controlled content) that contains one broken or hostile submodule reference will make every future checkout of that branch/commit fail, even though the primary branch/commit switch already succeeded.

### Finding Description
`checkoutBranch` performs the ref switch first, then submodule sync as a second, all-or-nothing step: [1](#0-0) 

The submodule step is a single git invocation covering every submodule in the tree, with no per-entry try/catch or skip list: [2](#0-1) 

`resetSubmodulePaths`, used elsewhere for discard, at least accepts a path array, but `updateSubmodulesAfterOperation` has no equivalent granularity - if any one of N submodules fails to initialize/update (e.g., its recorded commit is unreachable, its URL is unresolvable, or `protocol.file.allow`/proxy restrictions block it), the whole `git submodule update --init --recursive` process exits non-zero and the error propagates out of `checkoutBranch`/`checkoutCommit`: [3](#0-2) 

This mirrors the report's broken invariant exactly: a batch operation over multiple independent sub-items (strategies in EigenLayer, submodules in Desktop) is treated as atomic even though the sub-items are logically independent, and a single attacker-controlled/broken entry can revert/fail the whole batch. In Desktop's case the "queue" step (the `git checkout` ref move) has already committed - HEAD and the top-level working tree are already switched - but the "completion" step (submodule materialization) fails and throws, surfacing an error to the user on every retry since the bad submodule reference is baked into the committed tree.

`_checkoutBranch` in `app-store.ts` treats any failure the same way regardless of whether it originated from the ref switch or the submodule step, wrapping it in `CheckoutError` and offering a generic retry, which will deterministically fail again for the same reason: [4](#0-3) [5](#0-4) 

The same all-or-nothing pattern exists in `pull`, which runs `git pull ... --recurse-submodules` as one call - a bad submodule reference introduced by a remote/fetched branch can make every subsequent pull of that branch fail as well: [6](#0-5) 

and in `clone`, which always passes `--recursive`, so cloning a repository containing one broken submodule reference will always fail even though the top-level repository content is otherwise perfectly fine: [7](#0-6) 

### Impact Explanation
An attacker who controls a repository, fork, or branch a victim clones/fetches/pulls (e.g., a malicious PR branch, a compromised remote, or a repo with a corrupted `.gitmodules`/gitlink entry) can render that branch permanently un-checkoutable in Desktop: every attempt to switch to it (via UI checkout, PR checkout, or `git pull --recurse-submodules`) will throw and retry endlessly, since the failing submodule reference is committed history and does not change between attempts. This is analogous to the report's "permanently DoS all currently pending withdrawals": here it is "permanently DoS checkout/pull/clone of the affected branch." Users on Desktop's default UI (no terminal access assumed) have no built-in workaround (no skip-submodule option), unlike the raw git CLI where `--no-recurse-submodules` or manual `git submodule deinit` could route around it.

### Likelihood Explanation
Any contributor with push/PR access to a shared repo, or the operator of any remote a user adds, can trivially add a submodule entry pointing at an unreachable commit/URL, or point `.gitmodules` at a hostile/oversized/slow-cloning target - no privileged or local access is required, matching the "unprivileged attacker controls a cloned/fetched repository" criterion in scope. Because Desktop always passes `--recursive`/`--init --recursive`/`--recurse-submodules` with no partial-failure handling, the condition triggers on the very first checkout/pull/clone attempt against the poisoned branch.

### Recommendation
- In `updateSubmodulesAfterOperation`, iterate submodules individually (or parse per-submodule failures from git's output) and continue updating the remaining ones, collecting/reporting failures without aborting the whole operation.
- Do not let a submodule-update failure mask the fact that the primary `git checkout`/`git pull` ref move already succeeded; surface a distinct, actionable error ("branch switched, but N submodules failed to update") rather than a generic `CheckoutError` that implies the whole operation failed.
- Consider offering `--no-recurse-submodules` as a fallback/retry path when submodule sync fails, so the user isn't permanently blocked from using the rest of the repository.

### Proof of Concept
1. Attacker creates a branch on a repo that adds a submodule entry (`.gitmodules` + gitlink) whose recorded commit does not exist in the referenced remote, or whose URL is unreachable/blocked.
2. Victim uses GitHub Desktop to fetch and check out that branch (`checkoutBranch`), or `git pull` while on it.
3. `git checkout` succeeds, moving HEAD/working tree; `updateSubmodulesAfterOperation` then runs `git submodule update --init --recursive`, which fails for the single bad submodule and returns non-zero: [8](#0-7) 
4. The error propagates to `_checkoutBranch`, which reports `CheckoutError` and offers "Retry" via `RetryActionType.Checkout`; retrying repeats the same failure indefinitely because the bad submodule reference is permanent commit data, with no per-submodule skip mechanism available in the UI. [9](#0-8)

export async function updateSubmodulesAfterOperation<T extends Progress>(
  repository: Repository,
  remote: IRemote | null,
  progressCallback: ((progress: T) => void) | undefined,
  progressKind: T['kind'],
  title: string,
  targetOrRemote: string,
  allowFileProtocol: boolean

  const opts: IGitStringExecutionOptions = {
    env: await envForRemoteOperation(
      getFallbackUrlForProxyResolve(repository, remote)
    ),
    expectedErrors: AuthenticationErrors,
  }

  const args = [
    ...(allowFileProtocol ? ['-c', 'protocol.file.allow=always'] : []),
    'submodule',
    'update',
    '--init',
    '--recursive',
  ]

  if (!progressCallback) {
    await git(args, repository.path, 'updateSubmodules', opts)
    return
  }
