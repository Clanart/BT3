### Title
Path-containment bypass in `resolveWithin` via unanchored `startsWith` prefix check allows deep-link `filepath` to escape the repository root - (File: `app/src/lib/path.ts`)

### Summary
The path-containment helper `resolveWithin` (and its `posix`/`win32` variants) validates that a resolved path stays inside a root directory by doing `realResolved.startsWith(realRoot)` with no trailing path-separator anchor. [1](#0-0)  This is the classic unanchored-prefix path-containment bug: a resolved path in a *sibling* directory whose name merely starts with the same characters as the root directory’s basename (e.g. root `.../Projects/app` vs sibling `.../Projects/app-secrets`) will incorrectly pass the check. This helper is the sole containment guard used when handling the attacker-controlled `filepath` parameter of the `x-github-client://openRepo/...` deep link. [2](#0-1) 

### Finding Description
`parseAppURL` extracts `filepath` from the deep-link query string with no sanitization beyond leaving it as a raw string (unlike `branch`, which is checked with `testForInvalidChars`). [3](#0-2) 

`dispatcher.ts`’s `openRepositoryFromUrl` then applies two guards before calling `shell.showItemInFolder`:
1. `isAbsolute(filepath)` — rejects only absolute paths, not `..` traversal segments.
2. `resolveWithin(repository.path, filepath)` — the real containment check. [2](#0-1) 

Inside `resolveWithin`, the final containment decision is:
```
return realResolved.startsWith(realRoot) ? resolved : null
``` [4](#0-3) 

Because `startsWith` performs a raw string-prefix comparison with no trailing separator, `realRoot = "/Users/victim/Documents/GitHub/app"` will match `realResolved = "/Users/victim/Documents/GitHub/app-secrets/token.txt"` even though the latter is a completely different, sibling directory. An attacker who knows (or guesses) the local clone directory’s name — trivial, since GitHub Desktop clones repos using the GitHub repo name by default (e.g. `octocat/app` → folder `app`) — can craft a `filepath` such as `../app-secrets/token.txt` (or any other sibling folder that happens to share the root’s name as a prefix, e.g. `.bak`, `-old`, `_v2`, `.git-old` naming conventions common in developer machines) to have `resolveWithin` return a non-null resolved path outside the actual repository.

The unit test suite for this function only covers full-escape cases (`..`, `../..`, symlink escapes) and never exercises the sibling-prefix collision, which is exactly the kind of test coverage gap described in the source report (“the testing scripts do not cover all contract functionality” / insufficiently faithful checks on side-effects). [5](#0-4) 

### Impact Explanation
A successful bypass causes `shell.showItemInFolder(resolved)` to be invoked with a path outside the cloned repository, revealing/opening an arbitrary file on disk in the user’s file manager merely because the user clicked an attacker-supplied `x-github-client://openRepo/...` link — an unprivileged, remote-triggerable action fitting the “link/deep link the user clicks” attacker model and resulting in file read/disclosure outside the repo. The same `resolveWithin` helper also guards file reads in the Copilot merge-conflict context builder, so any other caller relying on it for containment inherits the same weakness. [6](#0-5) 

### Likelihood Explanation
Exploitation requires only that the victim click a maliciously crafted `x-github-client://` link (standard Desktop deep-link mechanism registered in `main.ts`) and that a sibling directory exists whose name shares the repo folder’s name as a prefix — a very common occurrence given typical developer folder naming (`repo`, `repo-old`, `repo.bak`, `repo_v2`, `repo-private`). [7](#0-6)  No local access, admin rights, or prior malware is needed — only normal use of the OS-registered protocol handler.

### Recommendation
In `_resolveWithin` (`app/src/lib/path.ts`), replace the unanchored prefix check with a boundary-aware comparison, e.g.:
```ts
return (
  realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
) ? resolved : null
```
Add regression tests for the sibling-prefix case (e.g. root `/tmp/app`, target `/tmp/app-evil/file`) to close the exact coverage gap that allowed this to go undetected, consistent with the report's recommendation to make path/side-effect containment tests exhaustive rather than only covering trivial `..`/symlink escapes.

### Proof of Concept
1. Victim has cloned `https://github.com/acme/app` into `~/Documents/GitHub/app`, and separately has an unrelated folder `~/Documents/GitHub/app-secrets` containing sensitive files.
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/acme/app?filepath=..%2Fapp-secrets%2Ftoken.txt`
3. Desktop’s protocol handler invokes `handleAppURL` → `parseAppURL` → `openRepositoryFromUrl`. [7](#0-6) 
4. `filepath = "../app-secrets/token.txt"` passes `isAbsolute` (false) and is passed to `resolveWithin("~/Documents/GitHub/app", "../app-secrets/token.txt")`.
5. Inside `_resolveWithin`, `resolved` becomes `~/Documents/GitHub/app-secrets/token.txt`; `realResolved.startsWith(realRoot)` is `true` because `"...GitHub/app-secrets/token.txt".startsWith("...GitHub/app")` — the function returns the escaped path instead of `null`. [4](#0-3) 
6. `shell.showItemInFolder(resolved)` reveals `token.txt` from outside the repository to the attacker-controlled workflow, despite the code’s explicit intent to “Refus[e] to open absolute path” and “Prevent[] attempt to open path outside of the repository root”. [2](#0-1)
