### Title
Permanent freeze of yield via unprivileged `donateRewards()` overflow in BaseRewardPool reward accounting - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`donateRewards()` in `BaseRewardPoolV2.sol`, `BaseRewardPool.sol`, and `mWOMSVBaseRewarder.sol` is callable by **any wallet**, with no minimum-amount, cooldown, or `totalStaked()` sanity check, and feeds directly into `_provisionReward()`, which stores an attacker-controlled value into `rewardInfo.rewardPerTokenStored` scaled by `10**decimals / totalStaked()`. Because Solidity 0.8's built-in overflow checks revert (rather than wrap) on overflow, an attacker who is a very small/first depositor of a pool (so `totalStaked()` is tiny) can call `donateRewards()` with a large raw amount of an already-registered reward token to push `rewardPerTokenStored` close to `type(uint256).max`. Any subsequent addition to that value (future `queueNewRewards`/`donateRewards` calls, which occur during normal harvest/bribe-casting flows) will then overflow and revert permanently, freezing yield distribution for that reward token across the entire pool.

### Finding Description
`_provisionReward()` unconditionally adds to a persisted state variable: [1](#0-0) 

```
function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
    ...
    if (totalStaked() == 0) {
        rewardInfo.queuedRewards += _amountReward;
    } else {
        ...
        rewardInfo.rewardPerTokenStored =
            rewardInfo.rewardPerTokenStored +
            (_amountReward * 10**stakingTokenDecimals) /
            totalStaked();
    }
    emit RewardAdded(_amountReward, _rewardToken);
}
```

This is reachable by any unprivileged wallet through: [2](#0-1) 

```
function donateRewards(uint256 _amountReward, address _rewardToken) external {
    if (!isRewardToken[_rewardToken])
        revert MustBeRewardToken();

    _provisionReward(_amountReward, _rewardToken);
}
```

Note the absence of `onlyManager` here (unlike `queueNewRewards`), and no restriction on `_amountReward` relative to `totalStaked()`. The identical unprotected pattern also exists in: [3](#0-2) [4](#0-3) 

If `totalStaked()` is small (e.g., a newly-created pool before significant deposits, or a `BribeRewardPool`/`vlMGPBaseRewarder` where `totalStaked()` tracks voted/locked amounts that can be minimal early on), the division `(_amountReward * 10**decimals) / totalStaked()` can be made arbitrarily large by simply choosing a large `_amountReward` of a cheap, high-supply, or self-minted ERC20 token that is already a registered `rewardToken` for that pool (e.g., a bribe token added through the `WombatBribeManager` flow, which accepts arbitrary reward tokens chosen by whoever adds the bribe — see `WombatStaking.vote()` calling `IBaseRewardPool(_rewarders[i]).queueNewRewards(...)` for arbitrary bribe tokens): [5](#0-4) 

Once `rewardInfo.rewardPerTokenStored` is pushed near `type(uint256).max`, the *next* call that adds to it — whether a legitimate `queueNewRewards()` from harvesting/bribe-casting or another `donateRewards()` — will overflow the `+` operation and revert under Solidity ≥0.8's checked arithmetic. This is the same root-cause pattern as the referenced Moloch report: an attacker-inflated value flowing into an accounting variable causes all future arithmetic on it to permanently revert, unlike the recommended "allow overflow" fix Moloch applied.

### Impact Explanation
Once `rewardPerTokenStored` is corrupted, every future `_provisionReward()` call for that specific reward token in that pool reverts. Since `queueNewRewards` is invoked from the bribe-casting/harvest path (`WombatStaking.vote` → `IBaseRewardPool.queueNewRewards`) and from `WombatBribeManager.castVotes()`/`harvestSinglePool()`, this permanently blocks distribution of that reward token to all stakers/voters of the affected pool — a permanent freeze of unclaimed yield for every user in that pool, satisfying the "theft or permanent freezing of unclaimed yield" impact bar. Depending on how `castVotes()` aggregates reward forwarding across all pools in a single transaction, a single poisoned pool/rewarder could also revert-block the shared `castVotes()` call for all pools, amplifying the DoS protocol-wide.

### Likelihood Explanation
The attack requires no privileged role. Any wallet can:
1. Become a (small) depositor/voter in a target pool to make `totalStaked()` small, or wait for a pool with naturally low activity.
2. Get a cheap/self-minted token registered as a reward token for that pool's rewarder (feasible via the bribe-token mechanism, which does not restrict token choice) or target a pool where the desired reward token (e.g., WOM/MGP) already has low `totalStaked()`.
3. Call `donateRewards()` with a large raw amount of that token (cost is only the token amount itself — trivial for a self-minted token, or for a legitimate token if `totalStaked()` is small enough that even a modest donation pushes the stored value close to the overflow boundary given `stakingTokenDecimals` scaling).

Feasibility depends on real-world `totalStaked()` sizes at attack time, but is straightforward on any newly deployed or thinly-used pool/bribe rewarder, which is common shortly after protocol or new-pool launches.

### Recommendation
- Remove or restrict `donateRewards()` to authorized managers, or add a cap/sanity check ensuring the added `rewardPerTokenStored` increment cannot approach overflow bounds (e.g., bound `_amountReward` relative to a reasonable multiple of `totalStaked()`, or require a minimum `totalStaked()` before allowing large donations).
- Consider using a `try/catch` or saturating-add pattern (explicit `unchecked` with a cap, analogous to Moloch's `unsafeAddToBalance`) so that a single malicious/inflated token cannot permanently brick reward accounting for legitimate tokens/pools — while clearly documenting that any resulting reward-per-token inaccuracy is isolated to the poisoned token and does not halt the system.
- Alternatively, track `rewardPerTokenStored` growth increments and reject donations that would push the value beyond a safe threshold, reverting only the malicious donation instead of allowing state to be poisoned for future legitimate calls.

### Proof of Concept
1. Deploy/identify a `BribeRewardPool` (or any `BaseRewardPoolV2`/`mWOMSVBaseRewarder` derivative) for a pool where `totalStaked()` is small (e.g., pool just created, `totalStaked() == 1`).
2. Attacker mints a large supply of a custom ERC20 (`EvilToken`), gets it added as a bribe reward token for that pool through the normal bribe flow (any briber can specify token), making `isRewardToken[EvilToken] = true`.
3. Attacker calls `donateRewards(hugeAmount, EvilToken)` where `hugeAmount * 10**decimals / totalStaked()` is close to `type(uint256).max` (trivial since `totalStaked()` is 1 and `EvilToken` supply/decimals are attacker-controlled).
4. `rewardInfo.rewardPerTokenStored` for `EvilToken` is now near `type(uint256).max`.
5. Any subsequent legitimate `queueNewRewards(amount, EvilToken)` call (e.g., triggered from `WombatBribeManager.castVotes()` forwarding a future bribe in the same token, or another `donateRewards`) executes `rewardInfo.rewardPerTokenStored + (...)`, overflows, and reverts — permanently blocking further reward provisioning of `EvilToken` for that pool and potentially reverting the shared `castVotes()` transaction that batches multiple pools' reward forwarding.

                rewardInfo.rewardPerTokenStored +
