### Title
Liquidation reverts on stale/invalid oracle price instead of falling back, allowing undercollateralized positions to escape liquidation - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `liquidate()` public function resolves collateral and debt prices through `price-resolve`, which hard-reverts via `ERR-ORACLE-INVARIANT` whenever the price fails a staleness or positivity check, and also through an `unwrap-panic` on `price-resolve` for disabled collateral. Liquidation should never be blocked by transient oracle-freshness issues; instead it currently aborts entirely, mirroring the H-37 pattern where the liquidation path (`BigBang.liquidate` → `Market.updateExchangeRate`) reverts on `rate == 0` rather than falling back to a usable value.

### Finding Description
`liquidate()` calls `get-notional-evaluation`, which walks the position's assets and calls `get-asset-value` for each, which in turn calls `price-resolve`: [1](#0-0) 

`price-resolve` performs a hard `asserts!` on both price legality and timestamp freshness, reverting the entire transaction with `ERR-ORACLE-INVARIANT` if either check fails — there is no fallback to a previously known good price: [2](#0-1) 

The same hard-failure mode also exists directly inside the liquidation code path itself: when the seized collateral asset is a "disabled" collateral (not in the pre-fetched `assets` list), `process-collateral-asset` calls `price-resolve` and immediately `unwrap-panic`s the result — an even stricter, non-recoverable failure mode than a `try!`/`asserts!`: [3](#0-2) 

`liquidate()` itself has no try/catch or fallback around any of these price resolutions — a stale or momentarily invalid feed (e.g. `oracle-timestamp-fresh` failing because the feed hasn't been pushed within `max-staleness`, or a `confidence` check failing for Pyth) anywhere in the position's collateral/debt asset set makes the entire liquidation call abort: [4](#0-3) [5](#0-4) 

This is the same bug class as H-37: a staleness/confidence gate that unconditionally reverts, reached from the liquidation entrypoint, with no override for the "must-not-fail" liquidation path.

### Impact Explanation
If any relevant price feed becomes momentarily stale (network congestion, Pyth/DIA update delay, exceeding `max-staleness`) or fails the confidence check while a position is deeply underwater, `liquidate()` reverts unconditionally for that position and — since `price-resolve` failures are asset/feed-specific rather than tx-specific — potentially for every position sharing that asset. During exactly the volatile market conditions where liquidations are most needed (fast price moves causing feed lag or wide confidence intervals), liquidators are blocked from acting. Debt keeps accruing against insufficient collateral, pushing the protocol toward bad debt / insolvency once liquidation does eventually succeed (if the position hasn't already gone further underwater). This lands on protocol insolvency (Critical) per the impact taxonomy.

### Likelihood Explanation
Staleness thresholds (`max-staleness`) are finite and per-asset, and Pyth confidence intervals widen during high volatility — precisely the periods when large price swings drive positions into liquidation range. It does not require any third-party bad data or DAO misconfiguration to trigger: a normal, honest oracle update simply arriving a few seconds late relative to `max-staleness`, or a normal wide-confidence quote during a volatile market, is sufficient. This makes the condition plausibly reachable in production without any attacker action, similar to the original report's PoC.

### Recommendation
In the liquidation code path specifically, do not hard-revert on stale/low-confidence price data. Either:
- Allow `liquidate()` to fall back to the last known-good price (`last-update` map value / cached price) when `price-resolve`'s freshness or confidence check fails, instead of using `asserts!` to abort; or
- Introduce a liquidation-specific price resolution function that tolerates staleness/confidence failures (using the last valid cached price) while still enforcing the normal strict checks for all other market operations (borrow, withdraw, etc.).
Also replace the `unwrap-panic` on `price-resolve` in `process-collateral-asset` with a graceful fallback rather than an unconditional panic, since disabled-collateral price resolution is on the critical liquidation path.

### Proof of Concept
1. A borrower's position collateral value drops such that `current-ltv >= ltv-liq-partial` (liquidatable).
2. Simultaneously, the price feed for one of the position's collateral or debt assets fails `oracle-timestamp-fresh` (feed not updated within `max-staleness`) or `check-confidence`/`oracle-price-legal`.
3. A liquidator calls `liquidate()`; execution reaches `get-notional-evaluation` → `get-asset-value` → `price-resolve`, which hits `(asserts! ... ERR-ORACLE-INVARIANT)` and reverts the whole transaction (or, for disabled collateral, hits `unwrap-panic` in `process-collateral-asset` and panics). [6](#0-5) 
4. The liquidation cannot proceed until the feed is refreshed/becomes confident again, during which time the undercollateralized position continues to accrue debt, worsening the shortfall that must eventually be socialized as bad debt.

```text
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
