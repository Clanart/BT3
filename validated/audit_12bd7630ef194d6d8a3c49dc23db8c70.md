### Title
Unauthenticated bandwidth-subscription griefing via unbounded FIFO eviction in `pallet-bandwidth` - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`purchase()` on `BandwidthManager.sol` is callable by **anyone** for **any `(chain, app)` pair** — it is an explicit multi-tenant "sponsorship" feature [1](#0-0) . On the Hyperbridge side, `pallet-bandwidth::on_accept` appends every accepted purchase to a `BoundedVec<Subscription, 1024>` FIFO queue keyed only by `(app_chain, app)`, and once the queue hits the 1024-entry cap, the **oldest entry is unconditionally evicted regardless of whether it has been consumed or is close to expiry** [2](#0-1) . This is the direct structural analog of the `maxRecordsPerTransaction` report: a per-unit protection ("cap the list, evict oldest") that looks like a safety bound but is trivially defeated by an attacker who splits their spend across many independent purchase transactions (or many sponsor calls) instead of one, destroying bandwidth another party legitimately paid for.

### Finding Description
Any address on any registered source chain can call `BandwidthManager.purchase(app, tier, months, chain)` and credit — or, by extension, flood — the subscription list of an **arbitrary app on an arbitrary chain**, because the pallet keys `Allowance` storage purely by `(app_chain, app)` taken from the message body, not by payer identity [3](#0-2) . The docs confirm this is intentional "Sponsorship": *"a buyer on Ethereum can credit an app on Base... The pallet keys allowance storage by (app_chain, app)... not by request.source."*

`push_subscription` enforces the 1024 cap purely as a size limit, not a fairness or ownership-aware limit:
```
let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
    let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
        Some(list.remove(0))
    } else { None };
    let _ = list.try_push(new_sub);
    evicted
});
``` [4](#0-3) 

There is no check that the entry being evicted belongs to the same payer, has been (mostly) consumed, or is near expiry — eviction is pure FIFO-by-insertion-order, and the event itself documents the fund-loss framing: `"lost_bytes" is what the user paid for and won't get to use` [5](#0-4) .

The minimum purchase unit is one tier-month at the cheapest configured tier (e.g. the documented $50/100 KB tier) [6](#0-5) , and `purchase()` places no restriction on repeat calls, minimum `months`, or per-address rate — an attacker can script 1,024 sequential cheap purchases against the *same* `(app_chain, app)` pair that a legitimate sponsor already funded, evicting the victim's still-unconsumed (or even brand-new, large-tier) subscription entirely out of the FIFO before a single byte of it is drained by the gate. The only "protection" — the 1024-slot bound — is exactly the kind of check the external report describes: it caps storage growth, but gives a false sense of protecting subscription content, because an attacker's ability to submit many independent purchase transactions (the on-chain analog of "many wallets") lets them dominate and evict the entire queue.

### Impact Explanation
This falls squarely within the Hyperbridge bounty's "loss of funds" and "logic attack" categories: a legitimate sponsor pays real fee-token value for bandwidth (`BandwidthManager.purchase` pulls ERC-20 from `msg.sender` [7](#0-6) ) that can be permanently destroyed — with zero governance or app-owner involvement — purely by an unprivileged third party who is not required to be the app, the app's owner, or even hold any relationship with it. The victim's ISMP messages will then also start reverting at the gate (`GateError::NoAllowance` / `Insufficient`) because their credited bytes vanished, causing denial of service for the app's cross-chain traffic on top of the direct fund loss.

### Likelihood Explanation
Medium-to-High: `purchase()` is a fully public, unauthenticated entrypoint with no per-app rate limiting, no minimum-purchase-size floor relative to the queue cap, and no ownership binding between payer and app. The attack requires only enough of the cheapest configured fee-token amount for up to 1024 minimum-tier purchases plus relayer fees to deliver each cross-chain message — an attacker only needs to grief a specific high-value app they want to disrupt (e.g. a competitor), making the cost/benefit favorable in a targeted-griefing scenario, closely mirroring the original report's "script + bundled repeat calls" primitive.

### Recommendation
- Track subscriptions per-payer (or reserve a portion of queue slots per source/payer) rather than a single shared FIFO per `(app_chain, app)`, so one payer cannot evict another payer's unconsumed allowance.
- Alternatively, disallow eviction of subscriptions that are not yet substantially expired/consumed (e.g. only evict entries whose `remaining_bytes` is fully drained or `expires_at` has passed), forcing new purchases to fail (or queue) rather than silently destroying paid-for value.
- Add a minimum economic cost per queue slot (e.g. scale the 1024 cap or minimum tier price so that filling the queue costs materially more than the value being protected), and/or rate-limit purchases per `(source, payer, app)` triple.

### Proof of Concept
1. Victim (or a legitimate sponsor) calls `BandwidthManager.purchase(app="0xVictimApp", tier=TierFour, months=12, chain="EVM-1")`, crediting a large, long-duration subscription to `pallet-bandwidth`'s `Allowance[EVM-1]["0xVictimApp"]` FIFO [8](#0-7) .
2. Attacker, from any address, repeatedly calls `BandwidthManager.purchase(app="0xVictimApp", tier=TierOne, months=1, chain="EVM-1")` 1024 times (any source chain registered with a `BandwidthManager`), each dispatching a valid `BandwidthPurchaseMsg` that `on_accept` happily processes because `is_purchase_message`/`on_accept` only checks `request.from == manager`, not payer identity [9](#0-8) .
3. Each attacker purchase triggers `push_subscription`, and once the list length reaches `MAX_SUBSCRIPTIONS = 1024`, subsequent pushes evict the oldest entry — eventually reaching and evicting the victim's large TierFour subscription, emitting `SubscriptionEvicted { lost_bytes: <victim's bytes> }` [10](#0-9) .
4. The victim app's dispatches now fail at `BandwidthGate::try_consume` with `GateError::NoAllowance`/`Insufficient` [11](#0-10) , despite having paid in full — funds are lost and the app is denied service, all without requiring any relayer, prover, or governance compromise.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
