### Title
Unauthenticated `BandwidthManager.purchase()` lets any unprivileged caller force-evict another app's paid-for bandwidth subscription - ([File: evm/src/apps/BandwidthManager.sol], [File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`BandwidthManager.purchase()` accepts an arbitrary `app` and `chain` identifier from any caller with no ownership or authentication check tying the purchase to the app being credited. On the Hyperbridge side, `pallet-bandwidth` stores each `(chain, app)` allowance as a FIFO list capped at 1024 entries; when a new subscription is credited to a full list, the pallet unconditionally evicts and discards the **oldest** entry (`SubscriptionEvicted`), regardless of who paid for it or how much unexpired bandwidth it still holds. Because `app`/`chain` are free-form attacker-controlled bytes and nothing restricts who may top up a given `(chain, app)` bucket, an unprivileged third party can flood cheap purchases against a victim's `(chain, app)` key to push the FIFO list to capacity and force-evict the victim's legitimately paid, unexpired, higher-value subscription — resulting in an on-chain, irreversible loss of the fee tokens the victim spent.

### Finding Description
The bandwidth model intentionally allows "sponsorship" — any buyer can credit bandwidth for any `app`/`chain` pair without ownership checks, by design (`purchase()` in [1](#0-0) ). This is documented as a feature for treasuries sponsoring apps on other chains.

However, the pallet caps each `(chain, app)` FIFO subscription list at 1024 entries and, on overflow, evicts the *oldest* entry unconditionally to make room for the new purchase, as documented:

"Pushing onto a full list (1024 entries) evicts the **oldest** entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain." [2](#0-1) 

There is no restriction that limits who may push into a given `(chain, app)` bucket, nor any weighting/priority given to subscriptions by remaining value, expiry, or purchaser identity — eviction is purely FIFO-by-insertion-order:

"Each `(chain, app)` row holds a FIFO list of subscriptions, capped at **1024** entries. Every purchase appends a new subscription — same-tier repurchases don't stack, they queue." [3](#0-2) 

The gate's drain/sweep logic in `pallet_bandwidth::Pallet::try_consume` confirms the list is a simple ordered `Vec<Subscription>` mutated only by index-0 pops and appends, with no special-casing for eviction priority: [4](#0-3) 

Combined with the unauthenticated `purchase()` entrypoint that lets anyone target an arbitrary `(app, chain)` key [1](#0-0) , and the on-chain credit path that only verifies `request.from` equals the registered manager (not that the purchaser has any relationship to `app`) — "The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`" [5](#0-4)  — an attacker can:

1. Observe (or predict) that a victim app has purchased a large/long-duration Tier (e.g. the $1000/8MB tier) for `(chain=EVM-8453, app=victim)`.
2. Repeatedly call `purchase()` with the cheapest available tier (Tier One), targeting the same `(app=victim, chain=EVM-8453)` key, until the FIFO list reaches the 1024-entry cap.
3. One additional purchase evicts the victim's legitimate, unexpired subscription, permanently destroying the bytes/duration the victim paid for — the funds spent by the victim are gone with no recourse, no refund path, and no way for the victim to prevent it since there is no access control on who can write into their bucket.

### Impact Explanation
This is a direct on-chain loss of funds reachable through a fully public, unprivileged entrypoint (`BandwidthManager.purchase()`), requiring no malicious relayer, prover, governance actor, or leaked key. The victim's already-paid bandwidth allocation — real value locked as ERC-20 fee tokens transferred to the manager contract at purchase time — is destroyed by a third party's unrelated purchases, purely due to the absence of any ownership/ACL binding between the purchaser and the `(chain, app)` bucket being written to, and the unconditional oldest-first eviction policy with a fixed, attacker-reachable 1024 cap.

### Likelihood Explanation
The attack requires no privileged position: any address holding the local fee token can call `purchase()` repeatedly. The `app` and `chain` fields are fully attacker-controlled bytes with no validation against the caller's identity [6](#0-5) . The only cost is the cheapest tier's price multiplied by however many purchases are needed to fill the remaining FIFO capacity to 1024 — bounded and entirely attacker-controllable, especially against low-activity `(chain, app)` buckets that don't yet have many entries queued.

### Recommendation
- Bind bandwidth purchases to the target `app`'s authorization (e.g. require a signed authorization from the app, or restrict `purchase()`'s effective beneficiary to `msg.sender` by default, gating third-party sponsorship behind an explicit allow-list or app-side opt-in).
- Change eviction policy so unexpired, high-value subscriptions cannot be displaced by cheap, unrelated purchases — e.g. evict only same-purchaser entries, or refuse credit (revert) if the FIFO is full for that bucket instead of silently discarding value.
- Consider a minimum per-purchase price floor and/or a maximum purchase rate per `(chain, app)` bucket per block/period to make griefing economically prohibitive.

### Proof of Concept
1. Victim calls `BandwidthManager.purchase(app=victimApp, tier=TierFour, months=12, chain="EVM-8453")`, paying the $1000-tier price; `pallet-bandwidth` credits an unexpired, large `Subscription` into `(EVM-8453, victimApp)`'s FIFO list.
2. Attacker (any unrelated address) repeatedly calls `BandwidthManager.purchase(app=victimApp, tier=TierOne, months=1, chain="EVM-8453")` — the cheapest tier — enough times to bring the FIFO list for `(EVM-8453, victimApp)` to 1024 entries.
3. Attacker calls `purchase()` one more time. Per the documented eviction rule, `pallet-bandwidth::on_accept` appends the new subscription and evicts index 0 — the victim's Tier-Four subscription purchased in step 1 (assuming it's the oldest remaining entry, which it is if the attacker's flood entries were inserted after it) — emitting `SubscriptionEvicted` and permanently discarding the victim's paid-for, unexpired bandwidth allocation, with no way for the victim to recover the spent fee tokens or the bandwidth.

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}
