### Title
Cached FROST preprocess seed is never invalidated, permitting deterministic nonce reuse and private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The cifs bug class is a one-time identifier ("xid") allocated, then not freed/released on a path where it must be retired, causing reuse/leak. Serai's analog: `SigningProtocol::preprocess_internal` allocates a one-shot FROST preprocess seed into `CachedPreprocesses` keyed by `context`, but the seed is **never deleted or rotated** after the machine consumes it. Every subsequent `share_internal`/`complete_internal` under the same context deterministically regenerates the *identical* nonces and commitments via `AlgorithmMachine::seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)` [1](#0-0) . The cached seed therefore acts exactly like the leaked xid: a one-time resource that survives across returns and is silently reused.

### Finding Description
In `preprocess_internal` (coordinator/src/tributary/signing_protocol.rs), the seed is written with `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` only when `CachedPreprocesses::get` is `None`, then read back and fed to `AlgorithmSignMachine::from_cache` [2](#0-1) . There is no `del`/`remove` call on `CachedPreprocesses` anywhere in the codebase (grep for `CachedPreprocesses::(del|take|remove)` returns nothing), so the seed persists for the lifetime of the DB.

`share_internal` calls `self.preprocess_internal(participants).0`, which reconstructs the `AlgorithmSignMachine` from the same cached seed [3](#0-2) . `DkgConfirmer::share` and `DkgConfirmer::complete` both funnel through `share_internal`, with `complete` re-invoking it on the caller-supplied `preprocesses`/`key_pair` [4](#0-3) . The signed message is `set_keys_message(&self.spec.set(), &removed, key_pair)` — i.e., it varies with `key_pair` while the FROST nonces stay fixed under the same `(b"DkgConfirmer", attempt)` context [5](#0-4) .

The FROST docs state the invariant violated here: a preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share" [6](#0-5) , and "Reusing preprocesses would enable a third-party to recover your private key share" [7](#0-6) . Because `from_cache` re-derives `nonces`/`commitments` from the seed, two `share_internal` invocations over distinct messages produce two Schnorr signature shares `s = d + b·e·ρ + c·λ·x` with identical `(d + b·e·ρ)` but different challenges `c` — a textbook nonce-reuse equation system yielding the secret share `x`.

### Impact Explanation
An honest validator's MuSig/Schnorrkel secret key share over Ristretto is recoverable by any party that obtains two signature shares produced under the same `context` over distinct `set_keys_message` payloads. Since the substrate key backs the validator set's signing authority (`musig_context(self.spec.set())` [8](#0-7) ), recovery of one share degrades the threshold, and combined with the deterministic regeneration means every re-entry under that context leaks more of the same nonce. This is key share recovery — the highest-impact class in scope (Critical/High).

### Likelihood Explanation
The persistence half of the bug is fully confirmed: the seed is written once and never invalidated, and `from_cache` deterministically reproduces nonces. The trigger requires the validator to execute `share_internal` (via `share` or `complete`) twice under the same `(context, attempt)` with differing `key_pair` or differing preprocess sets (which changes `rho`/challenge). `complete` unconditionally re-runs `share_internal` on network-supplied `preprocesses`, so a second execution is part of the normal protocol flow; whether a distinct `key_pair` can reach `share`/`complete` for the same attempt depends on the DKG-confirmation call sites in `coordinator/src/tributary/handle.rs`, which I could not fully enumerate in this session. Even absent a differing `key_pair`, `complete` re-signs with a potentially different preprocess set than `share` used, changing `included` and thus the challenge while nonces remain fixed — same leak. Severity is provisional High pending confirmation of the distinct-message trigger.

### Recommendation
Delete or tombstone `CachedPreprocesses` after the first successful `sign`/`share` consumption (e.g., `CachedPreprocesses::del(txn, &context)` once the share is produced), or bind the cached seed into a one-shot state machine that refuses to serve a second distinct message set under the same context. At minimum, record the exact `msg`/`preprocesses` hash alongside the cached seed and `assert` equality on re-entry, so a second invocation with different inputs cannot silently reuse the nonces.

### Proof of Concept
Conceptual reproduction by code inspection (execution not performed):
1. `DkgConfirmer::share(preprocesses_A, key_pair_1)` → `preprocess_internal` stores seed `S` under `(b"DkgConfirmer", attempt)`; machine rebuilt from `ChaCha20Rng::from_seed(S)` yields nonces `N`; share `s1 = N_share + c1·λ·x` emitted for `msg1 = set_keys_message(set, removed, key_pair_1)`.
2. `DkgConfirmer::complete(preprocesses_B, key_pair_2, shares)` (or a second `share` for a retried/conflicting confirmation under the same attempt) → `CachedPreprocesses::get` still returns `S` (never deleted); `from_cache` regenerates the same `N`; `sign` produces `s2 = N_share + c2·λ·x` with `c2 ≠ c1` (different `key_pair`/`included` changes `hash_msg`/binding).
3. Solve the two linear equations: `x = (s1 − s2) / (λ·(c1 − c2))` — recovery of the validator's secret key share from two public shares, matching the documented "third-party recovery of your private key share" consequence of preprocess reuse.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))

# Caching

modular-frost supports caching a preprocess. This is done by having all
preprocesses use a seeded RNG. Accordingly, the entire preprocess can be derived
from the RNG seed, making the cache just the seed.

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
