### Title
Queued rewards can be entirely captured by a 1-wei staker when `totalStaked()` transiently hits zero - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`_provisionReward` diverts newly queued rewards into `queuedRewards` whenever `totalStaked() == 0`, and flushes that entire backlog into `rewardPerTokenStored` the next time the function runs with a non-zero `totalStaked()`, dividing by whatever `totalStaked()` is at that moment. Because `totalStaked()` is simply `IERC20(stakingToken).balanceOf(operator)` and the flush can be triggered by anyone via the permissionless `donateRewards(0, token)` call, a staker who empties the pool, waits for rewards to queue, then re-stakes a trivial amount can redirect the whole queued reward balance to themselves.

### Finding Description
`_provisionReward` at [1](#0-0)  branches on `totalStaked() == 0`: if true, the incoming reward is only added to `rewardInfo.queuedRewards`; if false, any accumulated `queuedRewards` is added to the current `_amountReward` and the whole sum is divided by the *current* `totalStaked()` to update `rewardPerTokenStored`.

`totalStaked()` is defined as the staking-token balance currently held by the operator (MasterMagpie) [2](#0-1) , so it can genuinely be zero if the pool has no active stakers (e.g., a newly created pool, or one where the last staker withdrew).

The flush is not limited to the manager's `queueNewRewards`: `donateRewards`, an unauthenticated external function, also calls `_provisionReward` and only requires that the token is a registered reward token [3](#0-2) . Calling it with `_amountReward = 0` still executes the `totalStaked() != 0` branch and flushes `queuedRewards` into `rewardPerTokenStored`, divided by the caller-controllable `totalStaked()`.

Exploit flow when an attacker can arrange (or observe) `totalStaked() == 0` at the moment a large reward is queued:
1. Pool is empty (`totalStaked() == 0`) — either because the attacker is the sole staker and withdraws, or the pool is freshly deployed/temporarily empty.
2. A manager calls `queueNewRewards(largeAmount, token)`. Since `totalStaked() == 0`, the whole amount goes into `queuedRewards` and `rewardPerTokenStored` is untouched.
3. Attacker deposits a minimal amount (e.g., 1 wei) via MasterMagpie, making themselves the only staker, so `totalStaked() == 1`.
4. Attacker calls the permissionless `donateRewards(0, token)`. This re-enters `_provisionReward` with `totalStaked() != 0`, flushing all of `queuedRewards` into `rewardPerTokenStored`, scaled by `10**stakingTokenDecimals / totalStaked()` — with `totalStaked() == 1`, the attacker's tiny stake captures the reward-per-token increase almost entirely.
5. Attacker calls `getReward`, receiving virtually the entire queued reward pool for a 1-wei stake.

No modifier in the contract (`onlyManager`, `onlyMasterMagpie`, `updateReward`) prevents this: `donateRewards` is intentionally open to anyone, and the reward-index math has no floor or minimum-stake safeguard, no time-weighting, and no check that the staker who caused the flush actually contributed proportionally to the reward period during which it accrued.

### Impact Explanation
This is a direct theft of user/protocol funds: legitimate rewards intended to be distributed pro-rata to stakers over the period(s) they were staked are instead captured entirely by an attacker holding a negligible (1 wei) position at the instant of the flush. This matches the "direct theft of user funds" / "theft of unclaimed yield" Immunefi impact class.

### Likelihood Explanation
The likelihood is conditional and depends on being able to force or catch `totalStaked() == 0`: this is realistic for freshly deployed pools, low-TVL pools, or any pool where all current stakers withdraw at the same time (attacker is the sole staker, or briefly coincides with everyone else withdrawing). Triggering the flush itself requires no privilege — `donateRewards(0, token)` is public and callable by the attacker directly, removing any dependency on waiting for the manager's next `queueNewRewards` call, and making exploitation immediately actionable as soon as the zero-totalStaked queuing occurs. Capital requirement is minimal (1 wei of staking token plus gas).

### Recommendation
- Prevent reward flush division by a "fresh"/negligible `totalStaked()` that did not exist during reward accrual, e.g., track a reward-accrual timestamp/epoch and require a minimum bonded amount or time-locked stake before a staker qualifies to receive queued rewards.
- Alternatively, don't allow `queuedRewards` to be flushed based on instantaneously fetched `totalStaked()`; instead accumulate reward-per-share increments only against verified stake history (e.g., checkpointed total supply), or hold `queuedRewards` until a minimum total-staked threshold/time delay is met.
- Restrict `donateRewards` from being able to trigger the flush path with `_amountReward == 0`, or require `_amountReward > 0` and add a cooldown/timelock between re-staking after `totalStaked()==0` and eligibility for previously queued rewards.

### Proof of Concept
Foundry test plan (using `BaseRewardPoolV2` + a mock `MasterMagpie`/staking token):
1. Deploy `BaseRewardPoolV2` with reward token `RWD`; deploy mock `MasterMagpie` as `operator` that reports `balanceOf`/`stakingInfo` from an internal staking ledger.
2. `staker1` deposits `100e18` staking tokens; confirm `totalStaked() == 100e18`.
3. `staker1` withdraws all `100e18`; confirm `totalStaked() == 0`.
4. As `manager`, call `queueNewRewards(1_000e18, RWD)`; assert `rewards[RWD].queuedRewards == 1_000e18` and `rewardPerTokenStored` unchanged.
5. Attacker deposits `1` wei of staking token; confirm `totalStaked() == 1`.
6. Attacker calls `donateRewards(0, RWD)` (requires attacker to hold/approve 0 tokens, trivially satisfied); assert `rewards[RWD].queuedRewards == 0` and `rewardPerTokenStored` increased by `1_000e18 * 10**decimals / 1`.
7. MasterMagpie calls `getReward(attacker, attacker)`; assert attacker receives (close to) the full `1_000e18` `RWD`, despite having staked only 1 wei for a negligible duration — demonstrating disproportionate capture of rewards meant for the prior staking period.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
