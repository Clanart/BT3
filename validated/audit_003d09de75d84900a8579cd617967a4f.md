### Title
Vault share-price preview (`calc-treasury-lp-preview`) can underflow and permanently disrupt deposits/withdrawals when unrealized interest accrual makes `reserve-inc` exceed `ta-preview` - ([File: mainnet/contracts/vault/v0-vault-sbtc.clar])

### Summary
Every Zest v0 vault (`v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) computes the "treasury LP" fee-share dilution with a subtraction pattern structurally identical to Basket.sol's `handleFees()`: a time-accrual-derived fee amount (`reserve-inc`) is subtracted from a base value (`ta-preview`) with no clamp, so an unbounded accrual (from a long-idle vault plus a normal, protocol-set `fee-reserve`) can make the subtrahend exceed the minuend and revert the whole preview path with a Clarity uint underflow.

### Finding Description
`calc-treasury-lp-preview` [1](#0-0)  computes:

```
old-debt   = mul-div-down(scaled-principal, index,      PRECISION)
new-debt   = mul-div-down(scaled-principal, next-index,  PRECISION)
debt-delta = new-debt - old-debt (clamped at 0)
reserve-inc = debt-delta * fee-reserve / BPS
ta-preview  = total-assets-preview()
result = reserve-inc * total-supply / (ta-preview - reserve-inc)
```

`ta-preview - reserve-inc` is an unchecked Clarity subtraction that panics if `reserve-inc > ta-preview`. `next-index` grows with elapsed time since `last-update` multiplied by the current `interest-rate`, exactly like Basket's `timeDiff * licenseFee` term [2](#0-1) . `total-assets-preview` bases its "unrealized interest" term on `debt-preview - total-borrowed`, a value tracked independently of the treasury computation's own `old-debt`/`new-debt`, and the two paths use different rounding functions (`calc-cumulative-debt` uses `mul-div-up`, while `calc-treasury-lp-preview` uses `mul-div-down` directly) [3](#0-2) . This means `reserve-inc` is not provably bounded by `ta-preview` for all elapsed times and `fee-reserve` values, particularly when the vault has been left un-accrued for an extended period (large `time-delta`) while `current-assets` is low (most liquidity borrowed out), analogous to Basket being "left inactive for two months."

Because `calc-treasury-lp-preview` feeds `total-supply-preview`, which in turn feeds `convert-to-shares-preview`/`convert-to-assets-preview` [4](#0-3) , any revert here blocks the vault's deposit/mint/withdraw/redeem accounting - the same "disruption of minting and burning" impact described in the Basket report.

### Impact Explanation
If triggered, users cannot deposit, mint, withdraw, or redeem vault shares until the underlying condition (accrued but unrealized interest relative to `fee-reserve`) is resolved by an accrual-triggering transaction or admin parameter change. This is a temporary freezing of funds/yield on the affected vault, matching the in-scope "temporary freezing of funds" impact category.

### Likelihood Explanation
Likelihood is uncertain without confirming the exact bounds enforced on `fee-reserve` (must be `<= BPS`) and the precise synchronization semantics between `total-borrowed` and the vault's `index`/`next-index`. Under the normal invariant that `fee-reserve <= BPS` and `total-borrowed` is synced to `total-debt()` at every real accrual, `reserve-inc` should stay below `ta-preview`. However, the rounding mismatch (`mul-div-down` vs `mul-div-up` for conceptually the same debt figure) and the unclamped subtraction mean there is no explicit on-chain guarantee, unlike Basket's report, which explicitly recommends capping `feePct`. I could not fully trace where `fee-reserve` is set/bounded within the available index, so likelihood should be treated as low-to-moderate and requires further verification of `fee-reserve`'s enforced maximum and `total-borrowed`'s update cadence.

### Recommendation
Clamp `reserve-inc` to be strictly less than `ta-preview` (e.g., `min(reserve-inc, ta-preview - 1)`) before using it as a denominator term, and/or unify the rounding direction used for `old-debt`/`new-debt` in `calc-treasury-lp-preview` with the rounding used in `calc-cumulative-debt`/`total-assets-preview` so the two debt computations cannot diverge. Additionally, enforce and document an explicit protocol-level maximum on `fee-reserve` (e.g., `<= BPS`).

### Proof of Concept
1. Let a vault accrue no transactions for an extended period so `next-index` grows substantially relative to `index` (large `time-delta * interest-rate`).
2. Ensure most of `current-assets` is lent out (`total-borrowed` close to `total-assets`), so `ta-preview` is dominated by the "interest" term rather than idle liquidity.
3. Call any function that triggers `calc-treasury-lp-preview` (via `total-supply-preview`, reachable from deposit/withdraw/mint/redeem preview paths).
4. If `reserve-inc` (a `fee-reserve`-scaled portion of `debt-delta`) equals or exceeds `ta-preview`, `(- ta-preview reserve-inc)` underflows and the transaction reverts, blocking the vault's core operations - mirroring the Basket.sol PoC of leaving the contract inactive and then having `mint`/`burn` revert in `handleFees()`.

Note: I was not able to locate and verify the exact bounds/setter for `fee-reserve` or the precise update points for `total-borrowed` within the indexed codebase, which limits full certainty on exploitability; a background engineer should confirm these invariants directly in the full contract source before treating this as confirmed-exploitable versus theoretically-unreachable.

        (idx (var-get index))

        (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
        u0)))
