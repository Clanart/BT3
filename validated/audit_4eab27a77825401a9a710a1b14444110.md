### Title
Signature Replay Enables Forced Cross-Context Address Association and Premature Balance Migration in `addr` Precompile / `AssociateTx` - (File: `precompiles/addr/addr.go`, `app/ante/evm_checktx.go`, `utils/helpers/address.go`, `utils/helpers/associate.go`)

### Summary
The `associate` method of the `addr` precompile and the equivalent `AssociateTx` ante-handler path (`HandleAssociateTx`) recover a signer's EVM address, Sei address, and pubkey purely from `crypto.Keccak256Hash([]byte(customMessage))` plus a raw `(v, r, s)` triple, with no chain-ID, contract-address, or domain-specific binding baked into the hash by the protocol itself [1](#0-0) . This mirrors the ERC1271 EOA-signature issue in the report: "there are no restrictions on how the hash is constructed" and no `_hashTypedDataV4`-style binding of chain ID/verifier contract, so any signature the victim produced for an unrelated purpose can be replayed here as long as the attacker also supplies the matching plaintext bytes as `customMessage`.

### Finding Description
`GetAddresses`/`RecoverPubkey` in `utils/helpers/address.go` perform raw ECDSA recovery against `crypto.Keccak256Hash([]byte(customMessage))` with no chain ID or contract address mixed in [2](#0-1) . The only length restriction is `MaxAssociateCustomMessageLength = 64` [3](#0-2) ; there is no fixed, chain-specific prefix enforced in the Go code (the `ASSOCIATE_MESSAGE` / EIP-191 envelope constant only exists in the TS test helper, not as an on-chain constraint) [4](#0-3) .

Both entry points are reachable directly by an unprivileged sender:
- `precompiles/addr/addr.go` `associate()` — a plain EVM contract call [4](#0-3) .
- `app/ante/evm_checktx.go` `HandleAssociateTx()` — invoked from the stateless/CheckTx path for `AssociateTx` messages, gated only by "already associated" and a positive-balance check, not by any signer authentication tying the message to the submitter [5](#0-4) .

Because the recovered `(evmAddr, seiAddr, pubkey)` triple is accepted as long as ECDSA recovery succeeds against attacker-supplied `(v, r, s, customMessage)`, an attacker who has ever observed a victim's personal-sign-style ECDSA signature (a common, publicly visible signing scheme not unique to Sei — e.g., any dApp login message, any other-chain message) can resubmit that exact `(v, r, s, message)` pair through `associate`, forcing the association and consequent `AssociateAddresses` → `MigrateBalance` execution on the victim's behalf and on the attacker's chosen timing [6](#0-5) .

Critically, `MigrateBalance` only moves bank balances (usei/wei/spendable coins) from the cast address to the pubkey-derived Sei address and then removes the cast account if `LockedCoins` is zero — it does not migrate or account for staking delegations, unbonding entries, or distribution rewards tied to the cast address [7](#0-6) . The codebase's own comment on the analogous EIP-7702 pre-association path explicitly documents this exact hazard: forced/unexpected association "migrating their direct-cast balance and orphaning staking/distribution state" [8](#0-7) . That EIP-7702 path was hardened with a mandatory chain-ID check (`auth.ChainID.IsZero() || auth.ChainID.CmpBig(k.ChainID(ctx)) != 0`) specifically to stop cross-chain replay causing this outcome [9](#0-8) , but the `customMessage`-based `associate`/`AssociateTx` path has no equivalent chain-ID/domain binding, leaving it exposed to the same class of forced, attacker-timed association.

### Impact Explanation
An attacker can force premature/unwanted association of a victim's cast address (`sdk.AccAddress(evmAddr[:])`) to their pubkey-derived Sei address at a time of the attacker's choosing, using a signature never intended for Sei association. This triggers automatic balance migration while leaving staking delegations, unbonding queues, and distribution reward positions attached to the now-orphaned cast address, since `MigrateBalance` never touches those modules. This is a form of permanent freezing/loss of access to staking-related value for the victim (the same impact the codebase's own comment attributes to this bug class), reachable by any transaction sender or contract caller with no special privilege, matching the accepted "permanent freezing" impact category.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to already possess a valid ECDSA signature `(v, r, s)` from the victim over some byte string ≤64 bytes (e.g., a `personal_sign`/EIP-191-wrapped message used for login on another dApp or another chain) plus the plaintext. Such signatures are commonly exposed (mempools, other chains' explorers, application backends) and are trivially replayable here since Sei's `associate` path performs no chain-ID or purpose binding, unlike the hardened EIP-7702 authority pre-association path in the same codebase.

### Recommendation
Bind the association hash to Sei-chain-specific domain data before hashing (e.g., include chain ID and a fixed Sei-only prefix/purpose tag, mirroring EIP-712/ERC-7739-style domain separation, or the chain-ID check already applied to `AuthorityToPreAssociate`). Additionally, before performing `MigrateBalance`, verify or block migration whenever the cast address has active staking delegations, unbonding entries, or distribution positions, or extend the migration to include or explicitly reject those cases, so a forced association cannot orphan staking/distribution state.

### Proof of Concept
1. Attacker observes (via mempool, another chain's explorer, or an unrelated dApp) a victim's already-used ECDSA signature `(v, r, s)` over a plaintext message `M` (≤64 bytes) that was never intended for Sei association.
2. Attacker calls `addr.associate(v, r, s, M)` on the `addr` precompile (`0x...1004`) or submits an `AssociateTx` with `CustomMessage = M` [4](#0-3) .
3. `helpers.GetAddresses` recovers the victim's real EVM address, Sei address, and pubkey from `keccak256(M)` and `(v,r,s)` [2](#0-1) .
4. Since the victim's cast address was not previously associated and holds ≥1 wei, the association succeeds and `AssociateAddresses`/`MigrateBalance` executes, moving bank balances and removing the cast account while leaving any staking delegations at the cast address orphaned [6](#0-5) , at a time chosen entirely by the attacker rather than the victim.

func HandleAssociateTx(ctx sdk.Context, ek *evmkeeper.Keeper, atx *ethtx.AssociateTx, readOnly bool) (sdk.Context, error) {
	V, R, S := atx.GetRawSignatureValues()
	V = new(big.Int).Add(V, utils.Big27)
	// Hash custom message passed in
	customMessageHash := crypto.Keccak256Hash([]byte(atx.CustomMessage))
	evmAddr, seiAddr, seiPubkey, err := helpers.GetAddresses(V, R, S, customMessageHash)
	if err != nil {
		return ctx, err
	}
	_, isAssociated := ek.GetEVMAddress(ctx, seiAddr)
	if isAssociated {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInvalidRequest, "account already has association set")
	}
	if !IsAccountBalancePositive(ctx, ek, seiAddr, evmAddr) {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInsufficientFunds, "account needs to have at least 1 wei to force association")
	}
	if !readOnly {
		if err := AssociateAddress(ctx, ek, evmAddr, seiAddr, seiPubkey); err != nil {
			return ctx, err
		}
	}
	return ctx.WithPriority(antedecorators.EVMAssociatePriority), nil
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
