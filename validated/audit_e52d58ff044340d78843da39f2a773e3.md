### Title
`ReceivedOutput::read` accepts an offset inconsistent with the output's `script_pubkey`, letting crafted bytes report unspendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in CVE-2019-13672 is content spoofing: untrusted input is presented as if it were authenticated/consistent, so the user sees a state that does not reflect reality. The Serai analog lives in `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122-134`, which deserializes the three fields (`offset`, `output`, `outpoint`) completely independently and never checks that `offset` actually derives `output.script_pubkey` under the wallet's group key. A forged `ReceivedOutput` therefore reports a balance the wallet can never spend.

### Finding Description
`Scanner::scan_transaction` (mod.rs:199-214) produces `ReceivedOutput`s where `offset` is guaranteed consistent: it is looked up in `self.scripts`, a map keyed by `p2tr_script_buf(key + G*offset)` (mod.rs:185-190). That invariant is only enforced on the scan path.

`ReceivedOutput::read` (mod.rs:122-134) reconstructs the same struct from raw bytes with zero validation:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

Any byte string encoding `(arbitrary scalar, arbitrary TxOut, arbitrary OutPoint)` is accepted as a "received output". The only place consistency is checked downstream is `SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs:277`), which returns `None` when `p2tr_script_buf(offset.group_key()) != prevouts[i].script_pubkey` — i.e., it silently refuses to sign rather than flagging the output as fraudulent. Nothing ever rejects the malformed `ReceivedOutput` itself: `value()`, `output()`, `outpoint()` (mod.rs:100-118) all report attacker-chosen data as genuine.

### Impact Explanation
An unprivileged party who can feed bytes into `ReceivedOutput::read` (the explicit untrusted-bytes entry point) can cause the wallet/processor to report funds as received that are not spendable:

- A crafted `ReceivedOutput` pairing a real scanned `script_pubkey`/`outpoint` with a wrong `offset` is indistinguishable from a genuine deposit at the `value()`/`balance()` layer, but `multisig()` returns `None` at send.rs:277, so the output can never be included in a `SignableTransaction`. Balance is credited; the funds are permanently unspendable and any spend attempt silently fails.
- Combined with a fabricated `TxOut`/`OutPoint`, arbitrary "deposits" of arbitrary value can be reported, corrupting accounting (`fee()`, `input_sat` summation at send.rs:175,175) until signing fails.

This mirrors the CVE: the deserialization layer presents spoofed content (a claimed deposit) without the consistency proof the scan path normally provides.

### Likelihood Explanation
Reachability depends on whether `ReceivedOutput::read` is applied to data an attacker can influence (serialized outputs crossing process/network/storage boundaries, which is the documented use of `write`/`serialize`/`read`). Given the library explicitly exposes `read` for untrusted streams, and the impact is limited to false-positive balance reporting plus signing refusal (no key leakage, no unauthorized spend — the send.rs:277 check prevents signing a mismatched input), this is Medium severity: integrity impact on reported state, no confidentiality loss.

### Recommendation
Either make the inconsistency impossible or fail loudly:

1. Give `ReceivedOutput::read` access to the expected group key (e.g., a `read_with_key(key, r)` constructor) and reject inputs where `p2tr_script_buf(key + G*offset) != output.script_pubkey`.
2. Alternatively, store the script→offset invariant check in `SignableTransaction::new`/`multisig` as a hard error (not a silent `None`), so a spoofed output is surfaced at receipt time rather than at spend time.
3. Document that `ReceivedOutput::read` must only consume bytes produced by the local `Scanner`, if that is the intended trust boundary.

### Proof of Concept
```rust
// Given a Scanner-derived genuine output `real: ReceivedOutput`,
// craft bytes claiming the same script but a wrong offset:
let mut buf = Vec::new();
(Scalar::ONE).write(&mut buf).unwrap();          // wrong offset (real uses e.g. ZERO)
buf.extend(serialize(real.output()));            // genuine script_pubkey + value
buf.extend(serialize(real.outpoint()));

let spoofed = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// Reports as received:
assert_eq!(spoofed.value(), real.value());
// ...but cannot ever be spent:
assert!(SignableTransaction::new(vec![spoofed], &payments, None, None, fee)
        .unwrap()
        .multisig(&keys)
        .is_none()); // send.rs:277 rejects silently
```
The mismatch is only discovered at signing time; every balance/reporting path treats the forged output as a genuine received deposit.
