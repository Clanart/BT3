Based on the evidence gathered, I found a concrete local-code analog: a Time-of-Check/Time-of-Use (TOCTOU) mismatch between the diff a user reviews and selects lines from, and the diff GitHub Desktop actually re-fetches when staging the patch — exactly parallel to the Sherlock finding where the *preview* calculation diverges from the *actual* mint calculation, silently giving the user something different from what they expected.

### Title
Stale diff/selection mismatch causes silent corruption of partially-staged commits - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user select individual lines/hunks to stage from a diff rendered in the UI. That selection is stored as a `DiffSelection` object keyed purely by **absolute line index**, not by line content or hunk identity [1](#0-0) . When the commit is actually created, `applyPatchToIndex` re-fetches a **brand-new** diff of the working directory rather than reusing the diff the user reviewed, and then re-applies the old, index-based selection against that new diff to build the patch: [2](#0-1) 

`formatPatch` then walks the (new) diff’s hunks and asks `file.selection.isSelected(absoluteIndex)` for each line, where `absoluteIndex` is computed purely from `hunk.unifiedDiffStart + lineIndex` of the **new** diff: [3](#0-2) 

If the file content changes between the moment the UI computed the diff the user based their selection on and the moment `applyPatchToIndex` re-diffs the file, the hunk boundaries/line offsets shift. The old selection indices are then blindly reinterpreted against the new hunk layout, so `formatPatch` can select/deselect lines that are semantically unrelated to what the user actually clicked.

### Finding Description
The broken invariant is: *"the set of lines the user visually selected in the reviewed diff == the set of lines that end up in the generated patch."* This invariant only holds if the diff used to render the UI and build the selection is identical to the diff used at staging time. Desktop does not enforce this — `getWorkingDirectoryDiff` is called once for rendering (`updateChangesWorkingDirectoryDiff` in `app-store.ts`) and independently a second time in `applyPatchToIndex` right before staging [4](#0-3) . There is no hash/oid comparison, no re-validation, and no abort when the two diffs disagree; `DiffSelection` has no concept of "this index is only valid for diff X."

This is analogous to the Notional bug: `_previewDeposit`/preview logic used one code path (NotionalV2) while the actual mint path (`_mintInternal`) used different, inconsistent logic, and the code never reconciled the discrepancy — leading to silently wrong output. Here, the "preview" (diff shown to the user, from which the selection is built) and the "actual" (diff re-fetched at staging/apply time) can diverge, and Desktop has no code to detect or reconcile that divergence — it just blindly re-uses stale integer offsets.

### Impact Explanation
This falls squarely under "silent corruption of what the user commits or pushes" from the accepted impact list. If the working tree file is mutated between diff rendering and commit execution (e.g. by an editor's auto-format/auto-save on file-system events, a linter/build watcher, another concurrently running git operation, or a slow git hook invoked as part of the same commit flow), the resulting partial commit can:
- Include lines the user explicitly deselected (never intended to commit), or
- Exclude lines the user explicitly selected (silently dropped), or
- Apply the patch to a materially different file body, since `formatPatch` operates purely on index-derived hunk headers, not content-anchored context.

No error is raised in the common case — `formatPatch` only throws when the resulting patch is completely empty (`patch.length === 0`) [5](#0-4) ; a shifted-but-non-empty patch is applied silently. Since this happens during the write path (git index/commit), the corrupted result is exactly what the user later pushes.

### Likelihood Explanation
This requires no admin rights, no leaked credentials, and no local malware — only a normal race between the working-tree state at diff-render time and at commit-time, both entirely inside Desktop's control flow (a genuine TOCTOU). It's realistically triggerable in everyday workflows (auto-formatters, background build tools, slow filesystem events, or another Desktop-triggered git command running between selection and staging), and Desktop performs no reconciliation step to prevent it. The exact probability of hitting a visible corruption depends on how much the file changes in that narrow window, so likelihood is moderate rather than certain, but the guard that "should" exist (verifying the diff hasn't changed since it was rendered/selected) simply does not exist anywhere in `applyPatchToIndex`, `stageFiles`, or `formatPatch`.

### Recommendation
Before staging, `applyPatchToIndex` should verify that the diff it's about to apply the selection against is the same diff (by content hash or by full-file OID) the user actually selected lines from, and abort/re-prompt if it has changed — rather than silently re-diffing and reapplying stale, purely positional selection state. Alternatively, `DiffSelection` should anchor selections to diff/hunk identity (e.g., content-hash of the hunk) rather than raw absolute line indices, so a mismatch is detectable instead of silently misapplied.

### Proof of Concept
1. Modify a tracked file with several distinct hunks; open it in GitHub Desktop's Changes view so the diff is rendered and hunk offsets (`unifiedDiffStart`) are computed for the *first* version of the diff.
2. In the UI, deselect a specific line/hunk (e.g., hunk #2) via `withRangeSelection` — this stores absolute indices from diff v1 in `DiffSelection` (see selection construction pattern used in tests) [6](#0-5) .
3. Before clicking "Commit," have another process (editor auto-save, formatter, or a manual `echo >> file` in a terminal) append/modify lines earlier in the file, shifting hunk boundaries — producing diff v2 with different `unifiedDiffStart` values for the same logical hunks.
4. Click "Commit." `applyPatchToIndex` calls `getWorkingDirectoryDiff` again, obtaining diff v2, and calls `formatPatch(file, diffV2)` using the selection built against diff v1's indices [7](#0-6) .
5. Inspect the resulting commit: it will include/exclude lines that no longer correspond to what the user saw and selected in step 2, since `absoluteIndex` in `formatPatch` is now computed relative to diff v2's (shifted) hunks [8](#0-7) .

**Caveat:** I was unable to fully trace `_commitIncludedChanges` in `app-store.ts` end-to-end (tool budget exhausted) to confirm whether any intermediate refresh/guard exists between UI selection and `stageFiles`/`applyPatchToIndex`; based on `stageFiles`'s doc comment ("the job of this function is to set up the index in such a way that it reflects what the user has selected") and its direct call into `applyPatchToIndex` with a fresh diff fetch, no such guard is evident [9](#0-8) . A Devin session with full repo access would be needed to conclusively verify whether any staleness check exists elsewhere in the commit dispatch path before this is treated as fully confirmed.

  /**
   * @param divergingLines Any line numbers where the selection differs from the default state.
   * @param selectableLines Optional set of line numbers which can be selected.
   */
  private constructor(
    private readonly defaultSelectionType:
      | DiffSelectionType.All
      | DiffSelectionType.None,
    private readonly divergingLines: Set<number> | null = null,
    private readonly selectableLines: Set<number> | null = null
  ) {}

  /** Returns a value indicating the computed overall state of the selection */
  public getSelectionType(): DiffSelectionType {
    const divergingLines = this.divergingLines
    const selectableLines = this.selectableLines

    // No diverging lines, happy path. Either all lines are selected or none are.
    if (!divergingLines) {
      return this.defaultSelectionType
    }
    if (divergingLines.size === 0) {
      return this.defaultSelectionType
    }

    // If we know which lines are selectable we need to check that
    // all lines are divergent and return the inverse of default selection.
    // To avoid looping through the set that often our happy path is
    // if there's a size mismatch.
    if (selectableLines && selectableLines.size === divergingLines.size) {
      const allSelectableLinesAreDivergent = [...selectableLines].every(i =>
        divergingLines.has(i)
      )

      if (allSelectableLinesAreDivergent) {
        return this.defaultSelectionType === DiffSelectionType.All
          ? DiffSelectionType.None
          : DiffSelectionType.All
      }
    }

    // Note that without any selectable lines we'll report partial selection
    // as long as we have any diverging lines since we have no way of knowing
    // if _all_ lines are divergent or not
    return DiffSelectionType.Partial
  }

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

/**
 * Stage all the given files by either staging the entire path or by applying
 * a patch.
 *
 * Note that prior to stageFiles the index has been completely reset,
 * the job of this function is to set up the index in such a way that it
 * reflects what the user has selected in the app.
 */
export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
