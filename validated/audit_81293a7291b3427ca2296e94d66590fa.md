### Title
Panic on point-at-infinity in BIP-340 `Hram::hram` crashes signing on attacker-chosen preprocesses — ([File: networks/bitcoin/src/crypto.rs])

### Summary
The Jettison advisory is a crash-on-untrusted-input DoS (parser stack overflow). The analog in Serai is not recursion but an `expect` panic on the point at infinity inside the Bitcoin `Hram` implementation, reachable via attacker-supplied FROST preprocess bytes fed to `read_preprocess`. A counterparty preprocess whose nonce commitments force the binding-weighted nonce sum `R` to the identity makes `x(&R)` panic, aborting the signing process.

### Finding Description
`x(key)` calls `key.to_encoded_point(true)` and then `.expect("point at infinity")` on `encoded.x()` [1](#0-0) . `Hram::hram` calls `x(R)` on the aggregate nonce point and `x(A)` on the group key [2](#0-1) , and `verify` additionally calls `needs_negation(&sig.R)`, which runs `to_encoded_point(true).tag()` on the computed `R` [3](#0-2) [4](#0-3) .

`R` is the sum over all participants of the binding-weighted nonce commitments (`D + rho·E`) taken from each `Preprocess.commitments` [5](#0-4) . Because preprocesses are broadcast before the challenge is known, a signing counterparty sees every other participant's commitments, computes `rho`, and submits commitments `D', E'` such that `D' + rho·E'` equals the negation of the honest partial sum. The aggregate `R` is then the identity. When `AlgorithmMachine::sign`/`complete` invokes `Schnorr::verify` → `Hram::hram(R, A, m)` → `x(R)`, `to_encoded_point` on the identity yields no x-coordinate and the `expect` fires [6](#0-5) . The code itself acknowledges this: "If either `R` or `A` is the point at infinity, this will panic" and "MAY panic ... even with malicious participants present" [7](#0-6) .

There is no upstream guard rejecting identity nonce sums: `Commitments`/preprocess parsing accepts any `read_G`-decodable point, and nothing in the shown `verify` path checks `R.is_identity()` before `x(R)`/`needs_negation(R)` is evaluated (unlike `Signed::read`, which does reject an identity signature nonce, showing the pattern exists but is absent here) [8](#0-7) .

### Impact Explanation
Any single threshold participant in a Bitcoin multisig signing session can force a panic in every honest signer (and the coordinator task driving `complete`) at the moment the aggregate signature is computed. A panic unwinds/aborts the executing task, killing the signing attempt and — depending on the host runtime — the process handling it. This is a reachable availability failure driven purely by bytes an unprivileged counterparty submits (`read_preprocess`), with no key leakage required: a medium-severity DoS matching the Jettison class (crash on maliciously structured public input). It also forces a re-attempt, letting the adversary repeatedly stall a Bitcoin payout/signing plan.

### Likelihood Explanation
Reachability requires only a valid DKG slot in the signing set — the same trust level already assumed for `read_preprocess`/`read_share` inputs. The attack is deterministic: preprocesses are public commitments, `rho` is a deterministic function of the preprocess set and message (`hash_msg`/binding transcript), so the attacker can compute a cancelling commitment pair with certainty on every attempt they join. Cost is one preprocessing round; no guesswork, no races.

### Recommendation
Reject the identity early: after computing each weighted nonce sum `R`, check `bool::from(R.is_identity())` and return `FrostError`/`None` instead of proceeding, mirroring the identity check already applied to `signature.R` in `Signed::read`. Concretely, in `Schnorr::verify` (and inside `Hram::hram` as defense-in-depth), return `None` when `R` or `A` is the point at infinity rather than letting `x()`/`x_only()` `expect` fire [9](#0-8) .

### Proof of Concept
1. Honest participants broadcast preprocess commitments; the attacker observes all `D_i, E_i` and the message.
2. Attacker computes the binding factors `rho_i` (public transcript) and the honest partial nonce sum `S = Σ (D_i + rho_i·E_i)` for the relevant nonce index.
3. Attacker picks any scalar `k`, sets their commitments `D' = -S - rho'·(k·G)`, `E' = k·G` so their contribution `D' + rho'·E' = -S`, making aggregate `R = S + (-S) = identity`.
4. During `complete`/`verify`, `Hram::hram` calls `x(&R)` → `to_encoded_point` returns a point with no `x()` → `expect("point at infinity")` panics (equivalently `needs_negation(&sig.R)` panics on the identity `R`) [10](#0-9) [4](#0-3) .

Note on scope/confidence: I verified the panic sites and the preprocess→`R` data flow, but did not fully trace `IetfSchnorr::verify`'s internal ordering in `crypto/frost/src/algorithm.rs`; the documented "may panic ... even with malicious participants present" contract confirms the authors consider the identity-`R` path reachable rather than guarded.

  #[derive(Clone, Copy, Debug)]
  pub struct Hram;
  #[allow(non_snake_case)]
  impl HramTrait<Secp256k1> for Hram {
    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
  }
