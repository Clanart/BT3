Confirmed finding: `RewardMintingAmount` has no upper bound validation.

### Title
Unbounded `reward.mintingamount` governance parameter allows unlimited KAIA inflation via minting reward - ([File: kaiax/gov/param.go])

### Summary
The `reward.mintingamount` governance parameter, which directly determines the amount of native KAIA token minted every block as validator/fund reward, has no upper-bound (or sanity) validation in its `FormatChecker`. Unlike other numeric parameters, it accepts any non-negative (or even arbitrary) `*big.Int` value with no cap.

### Finding Description
The parameter table in `kaiax/gov/param.go` defines `RewardMintingAmount` with `FormatChecker: noopFormatChecker`, which always returns `true` regardless of the value: [1](#0-0) [2](#0-1) 

Compare this to `RewardMinimumStake`, which at least checks `v.Sign() >= 0`, and to `RewardRatio`/`RewardKip82Ratio`, which validate percentile sums to exactly 100. `RewardMintingAmount` has no such check — any value that parses into a `*big.Int` is accepted.

This value flows directly into block reward computation via `RewardConfig.MintingAmount`, which is minted every block regardless of transaction fees: [3](#0-2) [4](#0-3) 

The value is set through a governance vote via the `governance_vote` RPC/API and applied to the header at ratification. The consistency check performed for `RewardMintingAmount` votes in `checkConsistency` is a no-op that simply returns `nil` without validating the magnitude: [5](#0-4) 

The `NewVoteData`/format-check tests confirm any value is accepted, including `"0"` all the way to arbitrarily large values, with the only rejected inputs being those that fail to parse as a `*big.Int` (e.g., `"many"`, `false`): [6](#0-5) [7](#0-6) 

### Impact Explanation
Once ratified, this value is minted into the block reward every single block and distributed to the proposer, stakers, and funds (KIF/KEF/KPF) — this is a genuine, unbounded native-token supply inflation vector, matching "supply inflation" in the accepted-impact list. Since the value has no cap, a malicious or compromised governing node (single-mode governance, which is what Mainnet/Kairos actually use per `kaiax/gov/headergov/README.md`) could vote an astronomically large `reward.mintingamount`, and after ratification every block would mint that amount, causing catastrophic and immediate devaluation of KAIA. There is no consensus-level circuit breaker preventing this; the format checker is the only gate and it is a no-op.

### Likelihood Explanation
The likelihood is bounded by the fact that only the governing node (in `single` governance mode, used by Mainnet/Kairos) or GC council members (in `none` mode) can cast a ratified vote — this is not reachable by a fully unprivileged externally-owned account. However, the governing node is a single key controlled by the foundation/operator; if that key is compromised or misconfigured (e.g., a large placeholder value accidentally submitted, or governance transitions to a malicious governing node under the "none" mode dynamics), there is zero protocol-level defense against setting an economically absurd minting amount, unlike every other bounded numeric parameter (`RewardRatio`, `RewardKip82Ratio`, `Kip71*` bounds, `RewardMinimumStake`). This is a missing-defense-in-depth issue rather than a directly user-triggerable one.

### Recommendation
Add a `FormatChecker` for `RewardMintingAmount` that enforces a sane upper bound (e.g., relative to a maximum reasonable per-block inflation, consistent with historical Mainnet/Kairos values), in addition to the existing non-negativity implicitly required. Consider also validating in `checkConsistency` at `kaiax/gov/headergov/impl/header.go` that a newly voted `reward.mintingamount` does not deviate excessively (e.g., by more than an order of magnitude) from the currently effective value, to prevent catastrophic single-vote misconfiguration.

### Proof of Concept
1. Governing node (or GC member in "none" mode) calls `governance_vote("reward.mintingamount", "999999999999999999999999999999")` via the `governance_vote` API described in `kaiax/gov/headergov/README.md` (lines 206-225).
2. `NewVoteData` accepts the value because `RewardMintingAmount`'s `Canonicalizer` (`bigIntCanonicalizer`) successfully parses any big integer string, and `FormatChecker` is `noopFormatChecker` which always returns `true`.
3. `checkConsistency` in `kaiax/gov/headergov/impl/header.go` (case `gov.RewardMintingAmount`, lines 217-219) performs no additional validation and returns `nil`.
4. The vote is embedded in `header.Vote`, verified by `VerifyVote` (which checks voter/proposer identity but not the value's magnitude), and ratified at the next epoch boundary into `header.Governance`.
5. From the next epoch onward, `RewardConfig.MintingAmount` (`kaiax/reward/config.go` line 62) is set to this value every block, and `FinalizeState`/`getDeferredReward` mints and distributes this absurd amount as block reward every block, inflating KAIA supply without limit.
