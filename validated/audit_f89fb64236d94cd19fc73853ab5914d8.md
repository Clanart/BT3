## Analysis

I found a concrete analog. The CLOB bug's core primitive is: **attacker-controlled entries reuse an identity/slot in a bounded index keyed on coarse attributes (price/side), and the system's local bookkeeping (order tree membership) silently diverges from the "real" intended economic state.** The Desktop equivalent is `applyPatchToIndex` / `formatPatch` in `app/src/lib/patch-formatter.ts`, which builds the git-apply patch for a *partial* commit by re-fetching the diff fresh right before staging [1](#0-0) , but the line-selection object (`DiffSelection`) that decides which lines get included was computed against a *previous* diff and is only keyed by absolute line index, not by file content/hash.

`WorkingDirectoryFileChange.id` is `${status.kind}+${path}` (no content hash) [2](#0-1) , and `updateChangedFiles` merges each new status-scan file with any *existing* file sharing that same id, carrying over `existingFile.selection` verbatim onto the new file object regardless of whether the underlying diff content changed [3](#0-2) . The comment in `app-store.ts` explicitly acknowledges this is a known soft spot: *"The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines"* — and that recomputation of `selectableLines` only happens when the file is the one actively selected/rendered in the Changes view [4](#0-3) . Files that are *not* currently selected/visible never get their `selectableLines` refreshed even though their stale `DiffSelection` (line indices) is retained across status refreshes.

`formatPatch` then walks the **freshly-fetched diff's** hunks and, for each non-context line, calls `file.selection.isSelected(absoluteIndex)` [5](#0-4)  — using stale index-based selection state against new hunk content to decide what to include/exclude in the patch that gets `git apply --cached`'d.

### Attack scenario
1. User has a file `X` with `Modified` status and a **partial** selection (e.g., they deliberately excluded a sensitive line at diff line index 40, keeping other hunks selected).
2. User leaves that file unselected in the Changes list (viewing a different file) and performs an operation that updates the working tree from attacker-controlled content — e.g. `git pull`/checkout after a `fetch` from an attacker-controlled/compromised remote, or a merge — where file `X` still ends up `Modified` (same `id`) but with completely different diff hunks/line layout (attacker inserted/removed lines earlier in the file, shifting hunk boundaries).
3. `updateChangedFiles` matches on the stale `id` and reuses the old `DiffSelection` untouched [6](#0-5) .
4. User commits (selecting "commit all" or having previously left the file in a partially-included state that they trust reflects "exclude line 40"). `applyPatchToIndex` re-fetches the diff fresh, but reuses `file.selection` for index-based inclusion [7](#0-6) .
5. Because the attacker shifted hunk boundaries, the same numeric line index now maps to a *different* line (e.g. now includes attacker-injected content the user never reviewed, or silently drops a line the user meant to keep) — this is silent corruption of what gets staged/committed, driven entirely by remote-provided content, with no attacker requiring local access.

### Uncertainty
I could not fully trace every intermediate call path (e.g., whether `_refreshRepository`/pull flows always go through `updateChangedFiles` before commit, or whether some paths force-clear partial selection on refresh via `clearPartialState`). The `clearPartialState` flag does reset partial selections in some flows [8](#0-7) , which may mitigate certain refresh paths (e.g. post-commit) but not all (e.g. background status polling, fetch-without-checkout, or refreshes that don't set that flag). Confirming exactly which caller paths set `clearPartialState=true` vs `false` would require deeper tracing of `app-store.ts` callers of `updateChangedFiles`, which I could not fully complete in the available iterations.

### Title
Stale line-index diff selection reused across content-changed working-directory refreshes causes silent mis-staging of committed content - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateChangedFiles` keys working-directory file identity purely on `status.kind + path` (no content hash) and blindly reuses the previous `DiffSelection` (an index-based line selection) whenever a file with the same id reappears in a new git status scan, even if the underlying diff hunks have completely different content/line offsets.

### Finding Description
`WorkingDirectoryFileChange.id` is derived only from status kind and path [2](#0-1) . On every working-directory refresh, `updateChangedFiles` matches new files to old ones by this id and carries the old `selection` object forward unconditionally (`return file.withSelection(existingFile.selection)`) [6](#0-5) . `DiffSelection` tracks "diverging lines" purely by absolute numeric index within a specific diff's hunks [9](#0-8) . The only place that reconciles selection indices against a genuinely fresh diff is `updateChangesWorkingDirectoryDiff`, and even that only recomputes `selectableLines` (to drop indices that no longer exist) for the *currently selected* file [4](#0-3) ; it does not re-validate what each surviving index actually points to content-wise, and it never runs for files that aren't the active selection. When `stageFiles`/`applyPatchToIndex` later builds the commit patch, `formatPatch` re-fetches the diff fresh but applies the (potentially stale) `file.selection.isSelected(absoluteIndex)` against the new hunks' line indices [5](#0-4) , [10](#0-9) .

### Impact Explanation
This can cause a user to commit or push content they did not review or intend, because index-based inclusion/exclusion decisions silently apply to a different diff than the one the user actually looked at when making the selection. Since remote/fetched content directly determines hunk layout, an attacker controlling a remote/branch the victim merges/checks out from can engineer this divergence, resulting in unreviewed lines being silently staged (or reviewed exclusions being silently dropped) — matching the "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
Requires: (1) the victim to have a partially-selected (not all/none) file, (2) a working-directory content update for that same path/status-kind (e.g., via checkout/merge/pull from attacker-influenced remote) that shifts hunk boundaries while the file remains unselected in the UI, and (3) the victim then committing without re-reviewing that file's diff. This is a plausible but multi-step scenario dependent on normal Desktop usage patterns (partial staging + background/refresh timing), so likelihood is moderate rather than trivial.

### Recommendation
Bind `DiffSelection` (or the merge logic in `updateChangedFiles`) to a content-derived identity (e.g., blob OID / diff hash) rather than only `path + status.kind`, and invalidate/re-derive partial selections whenever the underlying diff content changes for *any* file, not only the currently selected one. Alternatively, have `formatPatch`/`applyPatchToIndex` validate that the diff used to build the selection matches the diff being patched (e.g., by hash) and fail closed (forcing full review) rather than silently reapplying stale indices.

### Proof of Concept
Not independently executed; derived from static code-path tracing of `updateChangedFiles` → `updateChangesWorkingDirectoryDiff` → `formatPatch`/`applyPatchToIndex` shown above. A full end-to-end reproduction (checkout sequence producing hunk-shifting content under an unselected partially-staged file, followed by commit) would need to be run in a live Desktop instance to confirm the exact conditions under which `clearPartialState` is or isn't set on the relevant refresh path.
