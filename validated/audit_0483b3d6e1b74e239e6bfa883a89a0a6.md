## Title
`resolveWithin`'s missing path-separator boundary check lets an attacker-controlled deep-link `filepath` escape the repository root - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin` (the shared containment check used to keep file operations inside a repository) validates containment with a bare `String.prototype.startsWith()` comparison instead of checking for a trailing path separator boundary. This is the same bug class as the reported Solidity finding: a comparison intended to bound a value to a valid range/containment is missing the correct boundary condition, so it silently accepts values that should be rejected (rather than rejecting valid ones, as in the report, but the root cause — an incomplete boundary check on a string/numeric comparison — is identical).

### Finding Description
`resolveWithin` is the single security boundary GitHub Desktop relies on to guarantee a user-influenced relative path stays inside a given root directory: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`startsWith(realRoot)` only checks that `realResolved` begins with the exact characters of `realRoot`. It does **not** verify that the next character after that prefix is a path separator (or that the strings are equal). This means any sibling directory whose name textually begins with the root directory's name is incorrectly treated as "inside" the root, e.g.:

- `realRoot` = `/Users/victim/Documents/GitHub/myrepo`
- `realResolved` = `/Users/victim/Documents/GitHub/myrepo-backup/secret.txt`

`realResolved.startsWith(realRoot)` is `true` even though `myrepo-backup` is a completely different, sibling directory. This is the exact bug-class from the report: a comparison that is supposed to bound a value strictly within a range (`proposalId` between `initialProposalId` and `proposalCount`; here, a path between the root and its descendants) is missing the correct boundary operator/condition, causing it to accept inputs it should reject.

This function is consumed with fully attacker-controlled input coming from a deep link. `parseAppURL` extracts a `filepath` query string parameter from `x-github-client://openrepo/...` URLs and passes it through **unsanitized** (unlike `branch`, which is validated with `testForInvalidChars`): [2](#0-1) 

The dispatcher then only rejects absolute paths before calling `resolveWithin`: [3](#0-2) 

```
if (filepath !== null) {
  if (isAbsolute(filepath)) { ... return }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } ...
}
```

A relative `filepath` such as `../myrepo-backup/secret.txt` (or any string that, after `path.resolve`, lands in a sibling directory whose name has the current repository's directory name as a literal prefix) will pass the `resolveWithin` check and be handed to `shell.showItemInFolder`.

`resolveWithin` is also used to bound write targets when applying Copilot conflict resolutions to the working directory: [4](#0-3) 

so the same boundary flaw is reachable from any code path that trusts `resolveWithin` to keep a write inside the repository.

### Impact Explanation
Existing tests for `resolveWithin` only cover `..`-traversal and symlink-traversal cases, not the sibling-prefix case, so this gap is unguarded: [5](#0-4) 

Because the check is a raw string prefix comparison and not a proper path-boundary comparison, an attacker who controls a deep link a user clicks (`x-github-client://openrepo/...&filepath=...`) can cause Desktop to resolve and act on paths outside the intended repository whenever the user's local clone layout happens to contain a sibling directory sharing the repository's directory name as a prefix (a very common real-world pattern — forks, backups, or renamed copies such as `repo`, `repo-old`, `repo2`, `repo.bak`, `repo (copy)`). The `openRepositoryFromUrl` path leads to `shell.showItemInFolder`, an information-disclosure/path-confusion primitive; the same broken primitive underlies the write path used for Copilot conflict-resolution content, which is a stronger "silent corruption of content outside the intended file" primitive if `resolution.path` can ever be shaped to hit a sibling directory (this reachability from an attacker-controlled repo could not be fully confirmed in this review — Git normally rejects tracked paths containing `..`, which limits, but does not necessarily eliminate depending on how the conflict path is derived, that specific chain).

### Likelihood Explanation
The most concretely exploitable and verifiable path is the deep-link `filepath` parameter: it requires only that the user click a crafted link (a recognized Desktop attack surface — deep links are explicitly listed as unprivileged and attacker-controlled), no admin rights, no pre-existing malware, and no credentials. The only precondition is a plausible directory-naming coincidence on the victim's machine, which is common but not guaranteed, making this a real but conditional (Medium-likelihood) issue rather than a universally reliable one.

### Recommendation
Fix the containment check in `_resolveWithin` to require an exact match or a boundary separator immediately after the prefix:
```ts
return realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Additionally, sanitize/validate the `filepath` query parameter in `parseAppURL` the same way `branch` is validated (e.g., reject invalid characters and any path that is not a clean relative path) before it ever reaches `resolveWithin`.

### Proof of Concept
1. Attacker hosts (or gets a victim to click) a link:
   `x-github-client://openrepo/https://github.com/victim-org/myrepo?filepath=..%2Fmyrepo-backup%2Fsecret.txt`
2. `parseAppURL` (`app/src/lib/parse-app-url.ts:98-124`) returns `filepath = "../myrepo-backup/secret.txt"` unsanitized.
3. `dispatcher.openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1957-1972`) confirms `filepath` isn't absolute, then calls `resolveWithin(repository.path, filepath)` where `repository.path` is `.../GitHub/myrepo`.
4. Inside `_resolveWithin` (`app/src/lib/path.ts:64-71`), `resolved` becomes `.../GitHub/myrepo-backup/secret.txt`. `realResolved.startsWith(realRoot)` evaluates `true` because `myrepo-backup` textually starts with `myrepo`, even though it is a different directory.
5. `resolveWithin` returns the out-of-root path instead of `null`, and `shell.showItemInFolder(resolved)` reveals a file that lives entirely outside `myrepo`.

      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {

    })

    it('fails for paths containing null bytes', async () => {

    })
