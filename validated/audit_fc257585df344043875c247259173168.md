### Title
Fee calculation omits the OP_RETURN output's weight, producing transactions below the intended (and possibly minimum-relay) fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes `needed_fee` by estimating the transaction's virtual size with `calculate_weight_vbytes`, which reconstructs the transaction from `tx_ins` and `payments` only. However, when `data` is provided, an extra OP_RETURN `TxOut` is pushed onto `tx_outs` *before* the weight estimation, and that output is never included in the estimated transaction. The resulting fee delta is therefore computed from the wrong set of terms — analogous to the Hyperdrive bug where `shareCurveDelta` was adjusted by the wrong combination of fee components, corrupting the reserve update.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is added to `tx_outs` at lines 194-202, but the weight/vbyte estimates at lines 204 and 225-227 call `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which builds its throwaway `Transaction` solely from `payments` (lines 85-93) plus an optional change output (lines 95-99). The `data` output is never part of the estimated transaction, so:

- `vbytes` (line 204) is underestimated by the serialized size of the OP_RETURN output (up to ~89 bytes for 80 bytes of data plus output overhead).
- `needed_fee = fee_per_vbyte * vbytes` (line 206) is proportionally too small.
- `fee_with_change` (line 227) inherits the same underestimate, so the change amount at line 228-230 is computed against an incorrect fee.
- The `TooLowFee` check at line 211 validates `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes` using the underestimated `vbytes`, so it can pass even though the real transaction is larger and its effective sat/vbyte is below the minimum relay fee.

The formula that determines how much value is burned as fee (`needed_fee`) versus returned as change is thus derived from terms that do not match the transaction actually constructed and signed — the same class of error as `shareCurveDelta -= curveFee` instead of `shareCurveDelta -= (curveFee - governanceCurveFee)`.

### Impact Explanation
A caller who constructs a `SignableTransaction` with `data` gets a signed transaction whose absolute fee equals the underestimated `needed_fee`, while its real vsize is larger. Consequences:

- The effective fee rate is lower than the requested `fee_per_vbyte`, potentially causing the transaction to be evicted or never confirm under contention.
- When the estimate pushes the real fee rate below the Bitcoin minimum relay fee, the transaction is rejected by relay policy despite passing the internal `TooLowFee` check — funds become temporarily unspendable (stuck in the inputs / returned only after constructing a replacement), i.e., outputs the wallet believes were created with a valid fee are not actually broadcastable.
- Accounting that relies on `needed_fee()` / `fee()` as the authoritative cost of the spend is systematically wrong whenever `data` is present.

### Likelihood Explanation
Triggering requires only calling the public API `SignableTransaction::new` with a non-`None` `data` argument — an ordinary, documented use of the library (the `data` parameter exists precisely for OP_RETURN metadata). No malicious counterparty, validator collusion, or leaked key material is needed; any embed-data transaction deterministically mis-computes its fee. The divergence grows with `data` length (up to 80 bytes).

### Recommendation
Include the OP_RETURN output in the weight estimate. Either pass the fully-built `tx_outs` (or `payments` plus a flag/length for the data output) into `calculate_weight_vbytes`, or compute the weight once `tx_outs` is finalized, e.g. change the signature to accept `outputs: &[TxOut]` and call it after the OP_RETURN push. Apply the same fix to the `fee_with_change` estimation path. Add a test asserting `tx.fee()`/`vsize()` equals `fee_per_vbyte` when `data` is specified.

### Proof of Concept
```rust
// networks/bitcoin: with one P2TR input worth `input_sat`,
// and 80 bytes of OP_RETURN data:
let payments = [(script, 1000u64)];
let data = vec![0xaa; 80];

let tx_no_data = SignableTransaction::new(
    inputs.clone(), &payments, None, None, fee_per_vbyte).unwrap();
let tx_data = SignableTransaction::new(
    inputs, &payments, None, Some(data.clone()), fee_per_vbyte).unwrap();

// The OP_RETURN output adds ~89 serialized bytes to the real tx,
// yet needed_fee is identical for both transactions:
assert_eq!(tx_no_data.needed_fee(), tx_data.needed_fee());
// Therefore tx_data's true sat/vbyte is strictly below fee_per_vbyte:
//   tx_data.fee() / real_vsize  <  fee_per_vbyte
// With fee_per_vbyte near the min-relay boundary, the TooLowFee check at
// send.rs:211 passes while the real transaction is non-standard for relay.
```
