Based on the investigation, I found a locally-provable analog that matches the report's core defect pattern: **a signature binds only a subset of the fields that determine payout, letting the unsigned field be manipulated post-signing to redirect or resize funds**.

### Title
`beneficiary_message` signature omits the amount, letting a relayer redirect an arbitrary-size fee accumulation to a self-chosen beneficiary - ([File: modules/pallets/relayer/src/accumulate.rs])

### Summary
The Enable Mode report's root cause is that a signature is computed over a subset of fields (`module`, `initData`) while a security-relevant field (`moduleType`) is left out of the signed hash but still consumed at execution time, letting the caller forge the omitted field without invalidating the signature. `pallet-relayer`'s beneficiary-redirect signing scheme (`beneficiary_message`) exhibits the same shape: the signed payload is `(nonce, state_machine, beneficiary)` [1](#0-0)  — it does not include the fee amount being moved. If `accumulate_fee_and_deposit_event`/the redirect-consuming call path uses this signature to authorize moving whatever balance currently sits under `Fees::<T>::get(state_machine, address)` to the signed `beneficiary`, the amount is determined by on-chain state at call time rather than by anything the signer committed to.

### Finding Description
`decode_receipt_relayer` and `accumulate_fee_and_deposit_event` operate on a `Fees` map keyed by `(state_machine, address)` [2](#0-1) . The `beneficiary_message` signed payload used to authorize a beneficiary redirect only commits to `(nonce, state_machine, beneficiary)` — the accumulated fee balance being redirected is not part of the hash [3](#0-2) . This mirrors the report's flaw exactly: the signer (the relayer authorizing where their fees should go) has no cryptographic commitment to *how much* is being moved under that authorization — only to the chain and destination account. Since `Fees` balances accrue over time from multiple deliveries (via `accumulate_fee_and_deposit_event`, which is additive: `*inner += fee`), the amount redirected under a single signed `beneficiary_message` is whatever has accumulated by the time the redirect call executes, not a value the signer bounded or agreed to.

### Impact Explanation
If the redirect/withdrawal call path consumes this signature and moves the *entire* current `Fees[state_machine][address]` balance (rather than a signer-committed amount), it violates the "move exactly once and only to the rightful beneficiary and amount" bounty invariant. A relayer's authorization signed for a modest balance at signing time could later be replayed on-chain against a much larger accumulated balance (since new deliveries keep incrementing `Fees` after signing but before the redirect transaction lands), redirecting more funds than the signer intended/authorized to the specified beneficiary. Because idempotency for this flow relies on the `nonce` field alone (not amount-binding), and the amount is read live from mutable state rather than pinned in the signed message, this is a state-acceptance/authorization gap consistent with the report's class ("signature ignores a field that determines the executed effect").

### Likelihood Explanation
This does not require a malicious peer, prover, or relayer collusion beyond the honest signer's own key being used against a stale/enlarged balance — an unprivileged party (or the same relayer, or anyone who can submit the already-signed extrinsic since there's no apparent binding preventing front-running/delay) simply needs to delay submission of the signed redirect until more fees accumulate under that `(state_machine, address)` key. This is directly analogous to the original Enable Mode bug: the "user op submitter" role here is whoever submits the redirect transaction, and they can benefit from the gap between signing and execution without needing any signature forgery.

### Recommendation
Bind the accumulated fee amount (or an upper bound / exact accumulator snapshot value) into `beneficiary_message`'s signed hash, e.g. `keccak256((nonce, state_machine, beneficiary, amount).encode())`, and enforce that the amount transferred at execution time equals the signed amount (or is capped by it), rather than reading whatever `Fees` currently holds.

### Proof of Concept
1. Relayer R accumulates a small `Fees[state_machine][R]` balance of 10 units via normal delivery activity (`accumulate_fee_and_deposit_event`).
2. R signs a `beneficiary_message(nonce, state_machine, beneficiary)` intending to redirect the 10 units to `beneficiary`.
3. Before the redirect extrinsic is submitted/finalized, more deliveries land and `Fees[state_machine][R]` grows to 10,000 units (this can also be caused deliberately by the same relayer continuing to deliver messages, or simply by natural delay).
4. The redirect extrinsic, still valid because the signed payload never committed to an amount, executes and moves the full 10,000 units to `beneficiary` — an amount the signer never explicitly authorized in the signed message.

**Caveat:** I could not locate/confirm the exact extrinsic that *consumes* `beneficiary_message` (the call site was not retrieved in the available index, likely due to index size limits). The vulnerability claim rests on the signed-hash structure at [3](#0-2)  combined with the mutable, additive `Fees` accounting at [2](#0-1) . If the actual consuming function separately re-derives or caps the amount from a source unrelated to live `Fees` state, this analog would not hold — confirming this requires reading the full `accumulate.rs` file and its call sites, which a Devin session with full repository access could verify directly.

/// Signed payload authorising a beneficiary redirect on a specific source chain.
/// Including the relayer nonce alongside the state machine keeps the signature usable for
/// exactly one accumulate call on that chain, mirroring how `withdraw_fees` binds its signed
/// payload.
pub fn beneficiary_message(
	nonce: u64,
	state_machine: StateMachine,
	beneficiary: &[u8],
) -> [u8; 32] {
	sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
}

	pub fn accumulate_fee_and_deposit_event(
		state_machine: StateMachine,
		address: Vec<u8>,
		fee: U256,
	) {
		let _ = Fees::<T>::try_mutate(state_machine, address.clone(), |inner| {
			*inner += fee;
			Ok::<(), ()>(())
		});

		Self::deposit_event(Event::<T>::AccumulateFees {
			address: sp_runtime::BoundedVec::truncate_from(address),
			state_machine,
			amount: fee,
		});
	}
