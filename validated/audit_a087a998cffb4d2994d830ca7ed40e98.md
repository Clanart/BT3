### Title
Payout tx's `SinglePlusAnyoneCanPay` signature lets a third party strip the operator-attribution OP_RETURN, permanently blocking honest-operator reimbursement - ([File: core/src/verifier.rs])

### Summary
The payout transaction created by `create_payout_txhandler` is authorized by a user signature restricted to `TapSighashType::SinglePlusAnyoneCanPay`, which only commits to input[0] and output[0]. The anchor output and the OP_RETURN output that carries `operator_xonly_pk` are *not* covered by the signature, so anyone who observes the operator's broadcast payout transaction in the mempool can rebuild a conflicting transaction with the same signed input and the same output[0] but a stripped/corrupted OP_RETURN. If that malleated transaction confirms instead of the operator's original, `Verifier::update_finalized_payouts` records `payout_payer_operator_xonly_pk = NULL`, and `is_kickoff_malicious`'s `let Some(operator_xonly_pk) = operator_xonly_pk_opt else { return Ok(true) }` then marks *any* subsequent kickoff for that deposit malicious, permanently denying reimbursement to the operator who actually funded the payout.

### Finding Description
Binding claimed to be broken: `payout_payer_operator_xonly_pk (DB) == the xonly_pk of the operator that actually funded the withdrawal`.

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds output[0] = user payout, output[1] = anchor, output[2] = OP_RETURN(`operator_xonly_pk`), and signs input[0] with the user's `taproot::Signature`. [1](#0-0) 
- The user's signature is enforced to use `TapSighashType::SinglePlusAnyoneCanPay` in `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:161-187`), and this sighash flag is entirely attacker-controllable per the threat model ("a Schnorr signature and its sighash flag"). [2](#0-1) 
- `SinglePlusAnyoneCanPay` only commits to the spent input and the single corresponding output (index 0); the anchor and OP_RETURN outputs are unauthenticated by the signature. `operator.rs::withdraw` even verifies the signature over exactly this restricted sighash. [3](#0-2) 
- `update_finalized_payouts` derives `operator_xonly_pk` purely from whatever transaction is found to have spent the withdrawal outpoint in the confirmed block, extracting the OP_RETURN from that specific on-chain transaction; if none/invalid, it sets the DB column to NULL and logs it as an "optimistic payout or wrong payout tx" case, with no distinction from a maliciously-malleated payout. [4](#0-3) 
- `is_kickoff_malicious` treats a NULL payer as unconditionally malicious for *any* kickoff, without any per-operator fallback: `let Some(operator_xonly_pk) = operator_xonly_pk_opt else { ...; return Ok(true) }`. [5](#0-4) 

Exploit flow: an honest operator broadcasts the correctly-formed payout tx (with valid OP_RETURN). Before it confirms, the attacker — who can observe the mempool and craft their own transactions/sighash flags — reuses the exact signed input (witness) from the operator's tx and constructs a conflicting transaction with an identical output[0] but no/garbage OP_RETURN and a different output[1]. Since only input[0]/output[0] are signature-committed, this alternate transaction carries a valid signature and a different txid, directly double-spending the withdrawal outpoint against the operator's original. If the attacker's version is the one that gets mined (a mempool/miner-policy dependent race, feasible via fee-bumping or full-RBF-enabled relay/miners, which do not require any special privilege), the chain permanently records that a payout for this withdrawal happened with no attributable operator. The verifier's `is_kickoff_malicious` then always answers "malicious" for that deposit's kickoff, regardless of which operator (including the one who genuinely funded it) submits it — there is no code path that re-attributes or reimburses that operator.

Existing guards do not close this gap: `Verifier::is_deposit_valid`, `SECP.verify_schnorr`, and `verify_storage_proofs` validate signature/proof correctness but never validate that the OP_RETURN output is itself covered by the payout signature, and nothing enforces that only the intended operator's exact txid (rather than "whichever tx spent the outpoint") is treated as authoritative.

### Impact Explanation
An operator that has genuinely fronted a user's withdrawal (spending its own BTC to pay the user) can be permanently and unrecoverably denied reimbursement, because the on-chain record of "who paid" is corrupted by a third party exploiting the intentionally weak sighash used for the user's authorization signature. This is a Critical-severity impact per the given rubric ("an honest operator permanently unable to be reimbursed"). The attack is repeatable across every withdrawal/deposit that uses the standard (non-optimistic) payout path, since every payout tx uses the same `SinglePlusAnyoneCanPay` construction, and it is independent of which operator services the withdrawal.

### Likelihood Explanation
The attacker needs no privileged role, key, or collateral — only the ability to observe the Bitcoin mempool (public), construct a Bitcoin transaction reusing an already-public witness, and get it relayed/mined ahead of or in place of the operator's original transaction (e.g., via higher fee-rate replacement on nodes/miners that accept conflicting/full-RBF transactions). This exactly matches the granted attacker capabilities ("broadcast Bitcoin transactions and pay fees ... a Schnorr signature and its sighash flag"). The main uncertainty is whether the specific mempool/miner policy in effect at exploitation time will accept the conflicting malleated transaction over the original (this depends on RBF signaling/policy, which is outside this repository's control) — but this is a realistic and increasingly common network condition, not a purely theoretical one, and the code offers no in-protocol defense against it regardless of network policy.

### Recommendation
Bind the operator-attribution data into the part of the transaction that is committed by the user's signature, e.g.:
- Change the payout transaction structure so the OP_RETURN (or an equivalent operator-attribution commitment) is included at output index 0 or otherwise placed under `SIGHASH_ALL`/`SIGHASH_SINGLE` coverage that cannot be altered without invalidating the user's signature, or
- Require the user's payout authorization signature to use a sighash flag that commits to all outputs (`SIGHASH_ALL` with `ANYONECANPAY` restricted only to inputs, or use a full commitment scheme instead of trusting a solely-user-signed transaction to carry operator attribution), and
- Track payouts in the DB by the specific `payout_txid` the operator originally broadcast (failing closed / re-evaluating rather than silently accepting whichever conflicting tx happens to confirm), and add a reconciliation path so that if the outpoint was spent by a different, unattributed transaction, the true funding operator can still prove funding (e.g., via off-chain signature records) and be reimbursed instead of being unconditionally treated as malicious.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
