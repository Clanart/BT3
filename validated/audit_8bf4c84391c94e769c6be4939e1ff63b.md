### Title
Consensus Liquidity reward share computed from CLPool's raw wrapped-KAIA `balanceOf()` allows unstaked-donation reward theft - ([File: kaiax/staking/impl/getter.go])

### Summary
The KIP-226 consensus liquidity (CL) staking amount that feeds directly into validator/staker reward proportions is obtained by calling `MultiCallDPStakingInfo` → `CLRegistry.getAllCLs()`, which reports each CL pool's stake as `WrappedKaia.balanceOf(clPool)` — i.e., the pool's **spot wrapped-KAIA balance** — rather than an internally tracked, deposit-accounted share ledger. This mirrors the Spartan Protocol root cause: LP/stake value derived from `balanceOf()` spot state instead of protected internal accounting, letting anyone move value into the tracked address to manipulate the derived quantity used in a monetary calculation.

### Finding Description
`getFromState` in `kaiax/staking/impl/getter.go` calls `contract.MultiCallDPStakingInfo(callOpts)` to fetch `(nodeIds, clPools, stakingAmounts)` for CL nodes: [1](#0-0) 

These amounts are copied verbatim (only unit-divided by `params.KAIA`) into `CLStakingInfo.CLStakingAmount`, which is the exact value used later for reward math: [2](#0-1) 

The staking module's own test/mock illustrates the underlying computation: the mock `WrappedKaia.balanceOf(account)` simply returns `account.balance` (the pool address's raw native/wrapped balance), and the resulting `CLStakingAmount` in the expected `StakingInfo` is set 1:1 to the CLPool address's KAIA balance: [3](#0-2) [4](#0-3) 

`CLStakingAmount` is then used directly in reward-eligibility and reward-splitting math in `kaiax/reward`: [5](#0-4) [6](#0-5) 
and in the CN/CL reward split: [7](#0-6) 

Because Kaia's staking-info sourcing rule uses the **previous block** state (`SourceNum(num) = num - 1` post-Kaia hardfork): [8](#0-7) 

an unprivileged sender (or a staker) can send a plain native-KAIA transfer (or wrap and transfer WKAIA) directly to a registered CLPool address in block `N`. This transfer requires no interaction with the CL pool's deposit function and grants the sender no shares — but it inflates `WrappedKaia.balanceOf(clPool)` observed when computing StakingInfo for block `N+1`, exactly as the Spartan exploit donated tokens directly to the pool contract to distort a balance-derived accounting value used in a subsequent computation (`removeLiquidity`/reward split) without going through the proper share-minting path.

### Impact Explanation
`CLStakingAmount` directly determines: (1) reward eligibility thresholds (`cn.StakingAmount + CLStakingAmount > threshold/minStake`), and (2) the proportional split of staking rewards between the CN validator's own staking amount and the CL pool address via `consolidatedNode.Split()`. Inflating a pool's reported balance via a bare donation can:
- Push a CN over `MinimumStake`/`StakingRewardThreshold` that it would not otherwise meet, making it (and its stakers) reward-eligible when it should not be.
- Skew `assignStakingRewards`/`assignStakingRewardsFlex`'s proportional allocation, redirecting minted staking-reward budget away from other honest validators/CL pools toward the manipulated CN's reward address and CL pool address.
This is a concrete reward-redirection/value-movement vulnerability reachable purely by submitting a native transfer transaction targeting a public address (the CLPool), satisfying "unauthorized value movement / reward redirection" criteria.

### Likelihood Explanation
Medium-High. No special privilege is needed beyond having spendable KAIA and knowledge of a CLPool address (which is public, exposed via `kaia_getStakingInfo`). Because staking info for block `N+1` is drawn from block `N`'s state, and each block re-derives `StakingInfo` from the *live* balance rather than a checkpointed deposit ledger, the manipulation window recurs every block, making it cheap to repeat opportunistically before each reward-distributing block. The main mitigating factor (uncertain from index) is whether the production `CLRegistry`/`CLPool` contracts (not available in the indexed mock) restrict `getAllCLs()`'s amount field to an internally tracked deposited-and-locked balance rather than delegating to `WrappedKaia.balanceOf`. This could not be fully verified since only the `CLRegistryMock.sol`/`WrappedKaiaMock.sol` test doubles are present in the index; the real KIP-226 `CLPool`/`CLRegistry` contract source was not found in this repo (likely lives in a separate contracts repo), so it is uncertain whether production code guards this balance with deposit accounting or withdrawal locks that would neutralize a bare donation.

### Recommendation
Have `CLRegistry.getAllCLs()` (and any staking-amount getter it relies on) report a value derived from an internally tracked deposit/share ledger (mint/burn accounting on `deposit`/`withdraw`) rather than the pool contract's live `balanceOf()`. If `balanceOf()` must be used for compatibility, reconcile it against the tracked "shares outstanding" and cap the reward-eligible amount at the tracked principal, ignoring any balance surplus that did not arise from a recognized deposit call (mirroring the standard fix pattern for donation/inflation attacks — track `totalDeposited` internally instead of trusting spot balance).

### Proof of Concept
Not executable against production code from this index, since the real `CLPool`/`CLRegistry` implementation is not present (only mocks). Conceptually, mirroring the Spartan exploit’s donation step:
1. Identify a CLPool address `P` for CN validator `V` via `kaia_getStakingInfo`.
2. At block `N`, submit a plain value-transfer transaction (or a WKAIA `transfer`) sending `X` KAIA to `P`, without calling any deposit/stake function on the CL pool.
3. At block `N+1`, `kaiax/staking` reads `StakingInfo` sourced from block `N`, calling `MultiCallDPStakingInfo` → `WrappedKaia.balanceOf(P)`, which now includes the donated `X`.
4. `kaiax/reward`'s `assignStakingRewards`/`assignStakingRewardsFlex` computes `V`'s reward share using the inflated `CLStakingAmount`, redirecting a larger fraction of the block's staking reward to `V`'s reward address and pool `P`, at the expense of other validators/CL pools — without the depositor ever receiving withdrawable shares for `X`.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
