### Title
`EvmHost.dispatch()` / `fundRequest()` swap native token via `swapETHForExactTokens{value: msg.value}` with no excess refund to caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept native token payment and swap the *entire* `msg.value` for an exact amount of `feeToken` via the local Uniswap V2 router, but never account for or refund the unspent remainder back to the original caller. This is the structural mirror of the external report's core defect: a function silently treats "value sent" as "value spent" instead of tracking the actual cost, with the excess ending up somewhere other than the payer.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 
and `dispatch(DispatchGet)`: [2](#0-1) 
and `fundRequest`: [3](#0-2) 

all call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee_or_amount, path, address(this), block.timestamp)`, sending the entire `msg.value` into the swap rather than a bounded amount, and never check/store/refund the leftover.

By contrast, callers built on top of `EvmHost` that go through the same swap-for-fee pattern (`IntentGatewayV2.placeOrder`, `ExtrinsicIntents`) explicitly track a local `msgValue` variable, decrement it by the router's actual reported spend (`amounts[0]`), and refund the remainder to `msg.sender` at the end of the call: [4](#0-3) 

`EvmHost.dispatch`/`fundRequest` do not perform this bookkeeping at all: the return value of `swapETHForExactTokens` (which reports `amounts[0]`, the actual ETH spent) is discarded, and no refund path exists to return unspent ETH to `_msgSender()`. Standard Uniswap V2 routers refund unspent ETH to `msg.sender` of the swap call — but that caller is `EvmHost` itself (since `EvmHost` is the one invoking the router), not the original external caller of `dispatch()`/`fundRequest()`. The refunded ETH therefore lands in `EvmHost`'s own balance, not back with the user who overpaid.

This exactly matches the external report's broken invariant: **the function conflates "amount sent" with "amount spent"** — except here the consequence is worse than an inflated accounting field: the excess native token is not returned to the payer at all, and `EvmHost` exposes no `withdraw`/`sweep` mechanism visible in this function region for that stray native balance, so a caller who overpays via `dispatch{value: X}()` where `X` exceeds the fee-swap cost permanently loses the difference.

### Impact Explanation
Any unprivileged app or user calling `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with native token payment and even a small margin above the exact swap cost (which is unknowable in advance since it depends on live AMM price/slippage) will have that margin siphoned into the host contract with no path to recovery through these functions. This is a direct, unrecoverable loss of user funds triggered by ordinary use of a public, unprivileged entrypoint — no malicious relayer, prover, or admin involvement required.

### Likelihood Explanation
Likelihood is high: any integrator dispatching a POST/GET request with a native-token fee, or funding an existing request, who does not compute the exact AMM-quoted input amount (which changes with every block due to price movement) will overpay and lose the difference. This is the default/expected usage pattern documented in `post-requests.mdx`, which shows `dispatch{value: msg.value}(post)` being called directly with a caller-supplied native amount.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder`/`ExtrinsicIntents`: capture the router's returned `amounts[0]` (actual native token spent), and refund `msg.value - amounts[0]` back to `_msgSender()` at the end of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`.

### Proof of Concept
1. Caller calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires 0.1 ether worth of ETH via the configured Uniswap V2 router.
2. `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` executes; the router spends ~0.1 ether and refunds ~0.9 ether — to `EvmHost` (the `msg.sender` of the swap call), not the original caller.
3. `dispatch()` returns; the 0.9 ether excess is now stranded inside `EvmHost`'s balance.
4. No line in `dispatch()`/`fundRequest()` checks `address(this).balance` before/after the swap or transfers any leftover back to `_msgSender()`, so the caller has permanently lost 0.9 ether relative to what was actually required.
