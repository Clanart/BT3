### Title
Schnorr half-aggregation weights do not bind to the nonce commitments or public keys, allowing a malicious aggregator to substitute attacker-chosen `R` points - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives per-signature weights `z_i` solely from the externally-supplied challenges. The transcript that produces each weight commits only to the sequence of `challenge` scalars (`digest.append_message(b"challenge", ...)`), never to the aggregate's `Rs` or to the public keys. In the half-aggregation scheme of ePrint 2021/350 this code cites, the weight must be a hash bound to the full signature list (all `(R_i, A_i)` pairs) — precisely to prevent the weighted `R` values from being malleable. An unprivileged party supplying the aggregate bytes (the `read`/`serialize` path accepts arbitrary `R_i` points and `s`) can therefore fabricate an aggregate whose per-signer nonce commitments were never produced by the signers, while verification still passes.

### Finding Description
Verification computes (`crypto/schnorr/src/aggregate.rs:127-146`):

- `digest` = `DigestTranscript(dst) || "signatures" || challenge_0 || ... || challenge_{n-1}`
- `z_i` = `weight(&mut digest)` — a function of the challenges only
- Accept iff `Σ z_i·R_i + Σ z_i·c_i·A_i − s·G = identity`

Because `z_i` is a deterministic public function of `(c_0..c_{n-1})` and is completely independent of `Rs` and `keys`, the attacker knows every weight before choosing any point. For any honestly-aggregated set of signatures `(R_i, s_i)` where `s = Σ z_i·s_i`, an attacker can pick an arbitrary point `X` and rewrite e.g.:

- `R'_0 = X`
- `R'_1 = R_1 + (z_0/z_1)·(R_0 − X)`
- `R'_i = R_i` for `i ≥ 2`, `s' = s`

Then `Σ z_i·R'_i = z_0·X + z_1·R_1 + z_0·(R_0 − X) + Σ_{i≥2} z_i·R_i = Σ z_i·R_i`, so `verify` accepts an aggregate in which signer 0's nonce commitment is replaced by an attacker-controlled point. The verifier formula is incorrect relative to the referenced scheme: `weight()` lacks binding to `R_i`/`A_i`, so the `Rs` field is unauthenticated.

### Impact Explanation
Any consumer that treats `SchnorrAggregate.Rs[i]` as the authenticated nonce commitment of signer `i` — e.g., nonce-reuse detection, per-input audit, blame, or matching `R` to a recorded commitment — can be deceived: funds/output checks or accountability decisions would be made against nonce points the signer never committed to. More fundamentally, this deviates from the proof of the cited scheme: unforgeability of half-aggregation relies on `z_i` being unpredictable *after* the adversary commits to the `R` values; here the adversary commits to `R` values *after* learning all `z_i`, breaking the linearization argument and permitting a class of forged aggregates. This is reachable with purely public inputs: the attacker controls the aggregate byte stream fed to `SchnorrAggregate::read` (network/substrate message data) and only needs knowledge of the public challenges.

### Likelihood Explanation
Exploitation requires only that an attacker can submit or relay a `SchnorrAggregate` (or influence aggregation in `SchnorrAggregator`) for challenges it can compute — all public data. Crafting a malleated aggregate is elementary algebra once `z_i` are computed; no secret material is needed. Realization of concrete harm depends on whether downstream code consumes `Rs` for identification/authentication, but the verifier formula itself is demonstrably incorrect versus the scheme it implements.

### Recommendation
Bind the weight transcript to the data being weighted: before deriving `z_i`, append each `R_i` and public key `A_i` (and the index `i`) to `digest` — i.e., `z_i = H(dst || all (R_j, A_j, c_j) || i)` per ePrint 2021/350, or equivalently append `R_i`/`A_i` to the digest inside the loop in both `verify` and `SchnorrAggregator::complete` so both sides stay consistent. Then `z_i` is fixed once the aggregate is committed, and the cancellation trick becomes impossible.

### Proof of Concept
```
// Given two valid Schnorr signatures (R0,s0) under (A0,c0), (R1,s1) under (A1,c1),
// honest aggregate: Rs = [R0, R1], s = z0*s0 + z1*s1 (z_i from challenges only).
// Attacker picks arbitrary X on the curve and computes:
//   R0' = X
//   R1' = R1 + (z0 * z1^{-1}) * (R0 - X)
//   s'  = s
// verify() computes  z0*R0' + z0*c0*A0 + z1*R1' + z1*c1*A1 - s'*G
//   = z0*X + z1*R1 + z0*R0 - z0*X + z0*c0*A0 + z1*c1*A1 - s*G
//   = z0*R0 + z1*R1 + z0*c0*A0 + z1*c1*A1 - s*G = 0   // ACCEPTS
// Signer 0's nonce commitment is now attacker-chosen X; signature still verifies.
```

Root cause is that `weight` (`aggregate.rs:22-65`) and the digest construction in `verify`/`complete` (`aggregate.rs:132-136`, `aggregate.rs:169-183`) commit only to `challenge.to_repr()` values, never to `Rs` or `keys`. Note: I was unable to fully trace all downstream consumers of `SchnorrAggregate::Rs()` within the iteration budget, so the concrete protocol-level consequence beyond the invalid verifier formula itself (e.g., which call site trusts the returned `Rs`) is not fully verified.
