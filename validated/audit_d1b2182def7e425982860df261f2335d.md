## Analysis

The seed bug (`hedgePositions` omitting `queuedPerpSize`) is a class of bug where a function captures a "snapshot" baseline before an operation, but nested/concurrent state added during that operation is silently double-counted (or lost) when the baseline is later reused to compute a delta. I found a directly analogous, already-partially-documented bug in Cosmos EVM's precompile `BalanceHandler` machinery.

`BalanceHandler.BeforeBalanceChange` snapshots `prevEventsLen` (the event-log length) before native precompile logic runs, and `AfterBalanceChange` replays only the events emitted after that snapshot (`events[bh.prevEventsLen:]`) into the EVM `StateDB` via `AddBalance`/`SubBalance`: [1](#0-0) [2](#0-1) 

The per-call wiring in `runNativeAction` creates the handler, records the baseline, runs `action(ctx)`, then replays events since that baseline: [3](#0-2) 

If `action(ctx)` itself triggers a **nested** precompile invocation (e.g. via `evmKeeper.CallEVMWithData` re-entering the EVM, which then calls back into a stateful precompile), the inner call's own `runNativeAction`/`Run` records its own `prevEventsLen` snapshot (correctly starting from the current event-log length) and consumes+applies its slice of events to `stateDB` in its own `AfterBalanceChange`. Execution then returns to the outer call, whose `bh.prevEventsLen` still points to the *original* (older) baseline recorded before the inner call happened. The outer `AfterBalanceChange` then re-processes `events[outerPrevEventsLen:]`, which **includes the same bank events the inner call already applied to `stateDB`**, causing a second `AddBalance`/`SubBalance` for the same underlying bank transfer — exactly the "missing accounting for pending/nested amount already consumed" pattern from the seed report.

This exact scenario is already reproduced in the repo's own test suite, which explicitly documents it as a balance-handler desync bug caused by nested/recursive precompile calls: [4](#0-3) 

The test uses a debug precompile whose `Call0` recursively re-enters the EVM (`CallEVMWithData`) to reproduce the nested-call condition: [5](#0-4) 

### Important caveat on scope

I could not fully confirm from the indexed code whether the production stateful precompiles (`erc20`, `ics20`, `staking`, `distribution`, `gov`, `slashing`) actually exercise a nested-call path through `runNativeAction` (each call there does create a *fresh* `BalanceHandler` via `BalanceHandlerFactory.NewBalanceHandler()`, so same-instance sharing itself is not the flaw — the flaw is the **stale baseline in the outer call** once an inner nested call has already consumed/applied a shared suffix of the event log). The debug precompile used in the test is explicitly marked "not for use in production," and I did not find a concrete production call path (e.g., ERC20 transfer triggering an IBC hook or ICS20 transfer re-entering another precompile within the same native action) confirmed in the indexed files. Due to index size limits, some file contents (particularly `precompiles/ics20/ics20.go`, `precompiles/erc20/methods.go`, and any hook/callback dispatch code that could establish a genuine nested-precompile production trigger) were not available to me. Starting a full Devin session with complete repository access would be needed to confirm whether an unprivileged user can actually construct a production transaction that nests two `BalanceHandler`-guarded precompile calls within one EVM call frame.

### Title
Nested precompile calls cause stale `BalanceHandler.prevEventsLen` baseline, leading to double-application of bank events to EVM StateDB - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
`BalanceHandler` snapshots the event-log length before running native precompile logic and replays only newly-emitted bank events into `StateDB` afterward. If a native action nests another `BalanceHandler`-guarded precompile call (self-reentry via `CallEVMWithData` or a cross-precompile call within the same action), the inner call applies and effectively "consumes" a suffix of the event log to `StateDB`, but the outer call's baseline was recorded before the inner call started. The outer call's replay window therefore overlaps with events already applied by the inner call, causing the same `CoinSpent`/`CoinReceived`/fractional-balance event to be applied to `StateDB` twice.

### Finding Description
`BeforeBalanceChange` records `prevEventsLen = len(ctx.EventManager().Events())` [1](#0-0) . `AfterBalanceChange` iterates `events[bh.prevEventsLen:]` and calls `stateDB.AddBalance`/`SubBalance` for each `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` event [6](#0-5) . This mirrors `_getTotalPerpPosition()` in the seed bug: it is a "baseline" measurement that must include everything already pending/consumed to avoid double counting. When a nested precompile call occurs inside `action(ctx)` (per `precompiles/common/precompile.go` lines 99-123), the inner call's own `AfterBalanceChange` already drains and applies its own event slice to `StateDB`. The outer call's stale `prevEventsLen`, however, still spans across the inner call's event range, so the outer `AfterBalanceChange` re-applies those same balance-changing events a second time.

### Impact Explanation
Re-application of `AddBalance`/`SubBalance` for the same underlying bank movement duplicates value in the EVM-visible `StateDB` balance without a corresponding second real bank transfer, producing a persistent, irreversible mismatch between native bank balances and EVM balances — i.e., unauthorized duplication/minting of spendable value in the EVM balance view. This matches the Critical "unauthorized minting/duplication/accounting corruption of spendable user value across native balances, EVM balances" impact class.

### Likelihood Explanation
This requires a call path where a precompile's native action itself triggers a re-entrant call to a `BalanceHandler`-protected precompile (self-recursion or cross-precompile) within a single top-level EVM transaction. The repository's own test (`evmd/tests/integration/balance_handler/balance_handler_test.go`) demonstrates this is mechanically achievable using `CallEVMWithData` from within a precompile's execution, though I was unable to confirm from indexed files that any *production* precompile (erc20/ics20/staking/etc.) has a naturally reachable nested-call trigger for an unprivileged EVM caller. Confirming exploitability in production precompiles requires deeper repository access than the index provides.

### Recommendation
Ensure `prevEventsLen` accounting accounts for nested calls, e.g., by re-reading the current event count immediately after the nested action returns (rather than only at entry), or by having inner calls advance/report their consumed event-range so outer calls resume exactly where the inner one left off — analogous to including `queuedPerpSize` in the seed fix so no window of already-settled state is double-counted.

### Proof of Concept
Conceptual sequence (as reproduced by the existing test, generalized to a value-duplication scenario):
1. Contract calls precompile A's transfer method, entering `runNativeAction`, which snapshots `prevEventsLenOuter = N`.
2. Inside the native action, the code re-enters the EVM (e.g., via `CallEVMWithData`) to call precompile A/B again, which internally performs a bank `SendCoins` emitting `CoinSpent`/`CoinReceived` events, then runs its own `AfterBalanceChange`, applying `SubBalance`/`AddBalance` to `StateDB` for that transfer, consuming events `[N:M]`.
3. Control returns to the outer call; the outer native action finishes with no additional relevant events beyond `M`.
4. Outer `AfterBalanceChange` runs against `events[N:]`, which still includes the inner's `[N:M]` `CoinSpent`/`CoinReceived` events, and reapplies `SubBalance`/`AddBalance` for the same transfer — doubling the balance change in `StateDB` relative to the actual bank ledger movement.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
