### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub Enterprise trust classification, triggering an unwarranted OAuth/PAT sign-in prompt for an arbitrary remote - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The external report's broken invariant is that several independently-supplied "trust" values (contract addresses) are combined without cross-validation, letting an attacker-influenced input desynchronize the system and cause unsafe behavior. The Desktop analog is `getEndpointKind()` in the credential-helper trampoline: it classifies a Git remote as `'enterprise'` (a GitHub host) based on an unauthenticated, attacker-controlled `WWW-Authenticate` HTTP header forwarded by Git, without cross-checking that classification against any independently-verified source of truth (e.g. an actual signed API response or a known account record).

### Finding Description
When Git performs an HTTP(S) operation against a remote and receives a `401`, it forwards any `WWW-Authenticate` response headers to the configured credential helper as `wwwauth[N]=...` fields. `getEndpointKind` trusts the content of that header verbatim to decide whether the remote "looks like GitHub": [1](#0-0) 

If `v.includes('realm="GitHub"')` the function immediately returns `'enterprise'`, short-circuiting the rest of the logic (including the `isGitHubHost(endpoint)` network probe that would otherwise provide some independent confirmation) — this header is emitted by whatever server (or MITM proxy, in the case of a plain-HTTP remote, or a malicious/compromised Git hosting server) the operation is talking to, so it is fully attacker-controlled and is not synchronized with any of the trusted state the app already holds (the accounts store, the configured API endpoints, `isDotCom`/`isGHE` checks based on real hostnames).

This classification feeds directly into `getCredential`: [2](#0-1) 

Because `endpointKind !== 'generic'` and no existing `Account` matches the attacker's `apiEndpoint`, Desktop calls `ui.promptForGitHubSignIn(endpoint)` with `endpoint` set to the attacker-controlled URL, presenting the user a "Sign in to GitHub Enterprise" flow for a host that was never independently verified to be a GitHub instance — the only "proof" was a header value the remote chose to send.

This mirrors the audit report's exact bug class: multiple normally-synchronized trust inputs (`isDotCom`, `isGHE`, `isGist`, an existing-account lookup, an HTTPS-only heuristic, and the network-probed `isGitHubHost`) are supposed to agree before Desktop treats a host as GitHub, but the `wwwauth[]` header path lets a single attacker-supplied value bypass all of them and desynchronize the decision from the actual configured endpoints.

### Impact Explanation
An attacker who controls the Git server for a clone/fetch/push URL a victim adds (or who can inject `WWW-Authenticate: realm="GitHub"` on an HTTP MITM path for a plain-`http://` remote) can force GitHub Desktop's credential helper to treat that arbitrary endpoint as a legitimate GitHub Enterprise instance, triggering `ui.promptForGitHubSignIn` for that endpoint. This is an "unauthorized account binding" style primitive: the user is asked to authenticate/authorize an account against a host the app itself never verified through the normal `isGitHubHost` corroboration path, opening a phishing surface where a look-alike "Sign in to GitHub Enterprise" dialog is shown for an untrusted server. It also demonstrates that `getEndpointKind`'s heuristics are not mutually consistent/synchronized, matching the "misconfiguration due to unsynchronized trust inputs" class from the original report.

### Likelihood Explanation
The victim only needs to perform an ordinary, expected Desktop action — cloning/fetching/pushing to a remote whose server the attacker controls (or is capable of intercepting, e.g. an `http://` remote on an untrusted network) — no local access, admin rights, or pre-existing malware is required. The `WWW-Authenticate` header is a standard part of the HTTP Basic-auth challenge/response flow that Git already forwards, so no unnatural interaction is needed beyond the credential prompt that Git triggers normally during authentication.

### Recommendation
Do not let the `wwwauth[]` realm string alone elevate an endpoint to `'enterprise'` classification. Require it to be corroborated by the independent `isGitHubHost(endpoint)` probe (or a TLS/host-based check) before short-circuiting, so a single attacker-supplied header cannot desynchronize the trust decision from Desktop's own verified endpoint list.

### Proof of Concept
1. Attacker stands up an HTTP(S) Git server at `https://attacker.example/victim-repo.git`, or intercepts a plain `http://` remote used by the victim.
2. Victim adds the remote in GitHub Desktop and performs a `fetch`/`push`.
3. Git issues the HTTP request; the attacker's server responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this as `wwwauth[0]=Basic realm="GitHub"` to the `desktop` credential helper.
5. `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`) matches `realm="GitHub"` and returns `'enterprise'` without ever calling `isGitHubHost`.
6. `getCredential` (lines 101-125) finds no matching account for `attacker.example` and calls `ui.promptForGitHubSignIn('https://attacker.example/...')`, presenting the user a GitHub Enterprise sign-in prompt for the attacker's domain.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
