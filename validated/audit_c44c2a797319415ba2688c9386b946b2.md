### Title
EIP-7702 authority address remapping can orphan validator/staking identity and halt the chain - (File: `x/evm/ante/preprocess.go`)

### Summary
The FOSUserBundle advisory describes an identity-validation flaw where a user was re-resolved by a mutable identifier (primary key reuse across identity changes) instead of validating that the resolved identity still matches the expected principal, allowing identity confusion after the identifier changes. The closest reachable analog in sei-chain is the Sei↔EVM address association system in `x/evm/keeper/address.go`, where `SetAddressMapping` unconditionally overwrites the bidirectional `EVMAddressToSeiAddressKey`/`SeiAddressToEVMAddressKey` mapping without validating that the EVM address wasn't already tied to a different, already-in-use Sei identity.

### Finding Description
`SetAddressMapping` writes both directions of the mapping without checking whether the EVM address already resolves to a different Sei address: [1](#0-0) 

The `associateAddresses` helper used by the `addr` precompile only guards against the *Sei* address already being associated, not against the *EVM* address already being tied to a different Sei identity: [2](#0-1) 

The ante-handler code itself documents a known instance of this class of bug for EIP-7702 `SetCode` authorities: a direct-cast EVM→Sei mapping created when `SetCode` installs delegation code for an authority is *mutable*, and a later `associatePubKey` call can remap that authority's identity, orphaning any staking/distribution state that had been created under the direct-cast identity — which the comment states "can halt the chain via the distribution validator-removal hook": [3](#0-2) 

This is explicitly the same bug class as the FOSUserBundle advisory: a stable identifier (the EVM/authority address, analogous to the DB primary key) is used to re-resolve or re-establish account identity, and a later mutable-identity update (`associatePubKey`, analogous to a username change) is not properly reconciled against previously-established state tied to the old identity, allowing an identity to be silently reassigned out from under state that depended on it.

### Impact Explanation
If the mitigation coded in `associateAuthorizationAuthorities` (referenced by the comment) is incomplete or bypassable in some code path, an attacker could use `SetCode` (EIP-7702) to install delegation code for an authority address, allow the direct-cast Sei address to accumulate protocol state (e.g., become associated with staking/distribution records), and then issue an `associatePubKey`/`associate` transaction that remaps the authority's true Sei identity — orphaning the previous direct-cast identity's state. Per the module's own comment, this can halt the chain via the distribution validator-removal hook, which is a validator-halt/chain-availability impact, and could also strand or misdirect funds tied to the orphaned identity.

### Likelihood Explanation
The general mapping-overwrite pattern (`SetAddressMapping` with no reverse-mapping conflict check) is reachable directly from a public precompile call (`addr.associate`/`associatePubKey`) and from ordinary EVM transaction preprocessing, so it is trivially reachable by any transaction sender. Whether it is currently *exploitable* depends on the completeness of the guard already added in `associateAuthorizationAuthorities` in `preprocess.go` — the fix comment in the ante-handler indicates the team is already aware of this exact bug class and added a targeted mitigation, but the general `SetAddressMapping`/`associateAddresses` code path still lacks a symmetric check preventing an EVM address from being silently rebound to a different Sei address outside of that one guarded call site.

### Recommendation
- Add a symmetric check in `associateAddresses` (and in `Keeper.SetAddressMapping`) verifying that the EVM address is not already mapped to a different Sei address before overwriting the mapping, mirroring the existing "already associated" check for the Sei address.
- Ensure the EIP-7702 authority protection in `associateAuthorizationAuthorities` covers all code paths that can create a direct-cast EVM→Sei mapping (not just the `SetCode` preprocessing path), including future precompile or wasm-bridge callers of `SetAddressMapping`.
- Add explicit regression tests that create staking/distribution state under a direct-cast authority identity, then attempt to remap that authority via `associatePubKey`, asserting the operation is rejected or the prior state is properly migrated instead of orphaned.

### Proof of Concept
Conceptual reproduction (constrained by index limits — the full `associateAuthorizationAuthorities` implementation could not be retrieved in this session to confirm whether the mitigation fully closes the gap):
1. Submit an EIP-7702 `SetCode` transaction naming an authority address `A` that has no prior Sei association; this creates/uses a direct-cast Sei address for `A`.
2. Cause `A`'s direct-cast Sei address to accrue protocol state (e.g., delegate stake or trigger distribution bookkeeping tied to that identity).
3. Submit an `addr.associatePubKey`/`associate` transaction with a signature proving control of `A`'s private key, causing `evmKeeper.SetAddressMapping` to rebind `A` to a new "true" Sei address per `precompiles/addr/addr.go` lines 239-251.
4. Observe whether the previously accrued state under the old direct-cast identity becomes orphaned/unreachable, and, per the code's own comment, whether this can trigger the distribution validator-removal hook and halt the chain.

Because the exact contents of `associateAuthorizationAuthorities` (the function referenced in the comment as the fix) could not be fully read in this session due to a tool error, I cannot confirm with certainty whether this path is already fully mitigated or remains partially exploitable — a Devin session with full file access would be needed to verify the completeness of that guard.

```go
func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}
```

```go
func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}
```
