### Title
Invalid proof-of-possession messages can leak a victim’s ECDH decryption key and secret share - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Encryption::decrypt` decrypts an `EncryptedMessage` and constructs an `EncryptionKeyProof` before the message’s Schnorr proof-of-possession has actually been verified. The PoP is only queued in a `BatchVerifier`, while the ECDH result is immediately used and returned as part of the proof. [1](#0-0)  `KeyMachine::calculate_share` can return that proof before the queued PoP verification runs whenever the decrypted bytes are not a canonical scalar. [2](#0-1) 

### Finding Description
The code explicitly relies on the per-message PoP to prevent an attacker from reusing another participant’s encryption key and inducing the recipient to reveal the corresponding ECDH result. [3](#0-2)  However, `Encryption::decrypt` calls `msg.pop.batch_verify`, which only queues the signature statement, then immediately computes `ecdh(enc_key, msg.key)`, decrypts the ciphertext, and returns `EncryptionKeyProof { key, dleq }`. [1](#0-0) 

`calculate_share` then calls `C::F::from_repr` on the decrypted bytes and returns `PedPoPError::InvalidShare { blame: Some(blame) }` before `batch.verify_with_vartime_blame()` is reached. [4](#0-3)  Because a random invalid ciphertext decrypts to effectively random bytes, a 32-byte result is non-canonical for a 252-bit scalar field with high probability, causing this early return and exposing the ECDH result despite the forged PoP.

The ECDH result is the complete shared secret input to the ChaCha20 transcript: `cipher` transcripts the context and `shared_key`, then uses a fixed IV. [5](#0-4)  Consequently, revealing `bX` for victim key `X` allows anyone who knows the protocol context to reconstruct the keystream and decrypt the original victim ciphertext.

### Impact Explanation
A malicious DKG participant can copy the `key` field from another participant’s encrypted share, submit it in their own malformed `EncryptedMessage`, and cause the recipient to publish the ECDH key for that victim message. The attacker can then decrypt the victim’s original ciphertext and recover the enclosed `SecretShare`.

The processor propagates this decryption key material inside the reported `InvalidShare` blame payload, making the secret available outside the intended recipient. [6](#0-5)  This defeats the exact isolation property described for per-message encryption keys and can expose threshold-secret material that was meant to remain encrypted. [7](#0-6) 

### Likelihood Explanation
The attacker only needs to supply untrusted bytes later passed to `EncryptedMessage::read` and `calculate_share`. `EncryptedMessage::read` accepts the attacker-controlled `key`, `pop`, and ciphertext fields. [8](#0-7)  The PoP does not need to be valid because its batch verification is deferred until after decryption and may never run before the early blame return. [9](#0-8) 

For Ristretto and other 255-bit-group scalars, most random 32-byte decodings are non-canonical, so a randomly selected forged ciphertext is likely to trigger the vulnerable early-return path.

### Recommendation
Do not produce an `EncryptionKeyProof` until the PoP has been positively verified. Either verify `msg.pop` synchronously inside `Encryption::decrypt` before computing or returning the ECDH result, or restructure `calculate_share` so scalar parsing, share validation, and blame disclosure are gated on the completed batch verification.

If batch verification must be retained, separate proof creation from disclosure: decrypt locally, but do not expose `EncryptionKeyProof` unless the corresponding PoP has succeeded. Additionally, consider explicitly rejecting identity points for encryption keys, although that does not address this specific deferred-verification flaw.

### Proof of Concept
1. Alice sends Bob an encrypted share `M_A` containing per-message public key `X`, PoP `σ_A`, and ciphertext `C_A`.
2. Mallory observes `M_A` and constructs `M_E` for the same recipient with:
   - `key = X`
   - arbitrary parseable `pop`
   - arbitrary ciphertext `C_E`
3. Bob calls `EncryptedMessage::read` followed by `calculate_share` with `M_E` attributed to Mallory.
4. `Encryption::decrypt` queues Mallory’s invalid PoP, but immediately computes `K = bX`, where `b` is Bob’s private encryption key, and creates an `EncryptionKeyProof` containing `K`. [10](#0-9) 
5. With high probability, `C_E XOR ChaCha20(K)` is not a canonical scalar, so `calculate_share` returns `InvalidShare { blame: Some(proof) }` before validating the invalid PoP. [11](#0-10) 
6. Mallory reads `K` from the published blame, reconstructs `cipher(context, K)`, and applies it to Alice’s original ciphertext `C_A`, recovering Alice’s secret-share plaintext.

/// An encrypted message, with a per-message encryption key enabling revealing specific messages
/// without side effects.
#[derive(Clone, Zeroize)]
pub struct EncryptedMessage<C: Ciphersuite, E: Encryptable> {
  key: C::G,
  // Also include a proof-of-possession for the key.
  // If this proof-of-possession wasn't here, Eve could observe Alice encrypt to Bob with key X,
  // then send Bob a message also claiming to use X.
  // While Eve's message would fail to meaningfully decrypt, Bob would then use this to create a
  // blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob.

  // While Eve can still reuse their own keys, causing Bob to leak all messages by revealing for
  // any single one, that's effectively Eve revealing themselves, and not considered relevant.

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
