### Title
Out-of-range `Participant` index in a blame accusation panics the DKG blame machine (DoS) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP `BlameMachine`/`AdditionalBlameMachine` resolve a blame accusation by indexing `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with the `sender`/`recipient` arguments, without first checking those indexes are within `1 ..= n`. `Participant::new` only rejects `0`, so any `Participant` with index `> n` (e.g. `Participant(0xffff)`) is a well-formed value that deserializes cleanly, yet causes a panic when used as a `HashMap` key lookup. This mirrors CVE-2018-7334's bug class: an unhandled/reserved value in attacker-influenced input crashes the process instead of being rejected.

### Finding Description
`AdditionalBlameMachine::new` registers exactly the participants `1 ..= n` into `encryption.enc_keys` and `commitments` [1](#0-0) . `blame` then calls `blame_internal`, which invokes `decrypt_with_proof` with the caller-supplied `recipient` [2](#0-1) .

Inside `decrypt_with_proof`, once the attacker supplies a message whose `pop` Schnorr signature verifies (they can produce this for their own key since `pop_challenge` binds `from`, `key`, and the ciphertext, and `from` here is whatever index they claim), the code executes:

```rust
// crypto/dkg/pedpop/src/encryption.rs
&[self.enc_keys[&decryptor], *proof.key],
```

`self.enc_keys[&decryptor]` panics (indexing `HashMap` with an absent key) when `decryptor`/`recipient` is a `Participant` with index `> n` [3](#0-2) . Symmetrically, even with a valid `recipient`, `self.commitments[&sender]` in `blame_internal` panics when `sender` has index `> n` [4](#0-3) .

The input path is real: blame accusations are constructed from messages carrying serialized `Participant` values (e.g. the `InvalidDkgShare`-style transactions that `Participant::new`-parse accuser/faulty fields), and `Participant::new` accepts every nonzero `u16` [5](#0-4) . No validation in `blame`, `blame_internal`, or `decrypt_with_proof` bounds the supplied indexes against `n`.

### Impact Explanation
An unprivileged party can crash any node evaluating a blame proof by naming a participant index outside `1 ..= n` (a "reserved value" the protocol never rejected). The panic aborts the DKG blame-handling path — and, since this runs inside the validator/processor call stack, it halts the process rather than returning a `PedPoPError`. This is a remote denial of service, the same impact class as the Wireshark dissector crash (A:H).

### Likelihood Explanation
Triggering requires only submitting a blame accusation whose `sender`/`recipient` index is a nonzero `u16` greater than the session's `n`, plus an `EncryptedMessage`/`EncryptionKeyProof` the accuser controls or replays. Nothing in the serialization (`Participant::new`), the API (`blame`), or the internals rejects such indexes before the `HashMap` indexing panics.

### Recommendation
In `blame`/`blame_internal` (crypto/dkg/pedpop/src/lib.rs) and `decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs), validate that `sender` and `recipient`/`decryptor` are registered participants (`<= n`, i.e. `enc_keys.contains_key` / `commitments.contains_key`) before indexing; return a `PedPoPError`/`DecryptionError` instead of using `map[&key]` on untrusted-derived indexes. The same fix pattern as the upstream CVE: reject the reserved value rather than letting it reach a crashing access.

### Proof of Concept
Conceptual (library-level):

```rust
// n = 3 session; AdditionalBlameMachine built from all three commitment messages
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker submits a blame accusation naming a non-existent participant index.
// Participant::new accepts any nonzero u16, so this deserializes fine.
let sender = Participant::new(0xffff).unwrap();          // > n, never registered
let recipient = Participant::new(1).unwrap();

// msg: an EncryptedMessage whose `pop` is a valid Schnorr PoP over the
// attacker's chosen ephemeral key (they can construct this honestly for
// their own key/pop_challenge, or replay one from another sender field).
// proof: a valid EncryptionKeyProof for msg.key under recipient's enc_key.
machine.blame(sender, recipient, msg, Some(proof));
// -> decrypt_with_proof indexes self.enc_keys[&decryptor] (ok here),
//    then blame_internal evaluates self.commitments[&sender] -> panic
// (or symmetrically: recipient = Participant(0xffff) panics directly on
//  self.enc_keys[&decryptor])
```

Root cause: `self.enc_keys[&decryptor]` and `self.commitments[&sender]` index `HashMap`s keyed only by participants `1 ..= n`, while the `Participant` inputs are unconstrained nonzero `u16`s [6](#0-5) [4](#0-3) .

One caveat worth noting: I verified the panic sites and the absence of bounds checks in `blame_internal`/`decrypt_with_proof`, but could not fully trace the production call chain that feeds deserialized `Participant` values into `blame` (coordinator code is out of scope), so the library-level reachability is certain while the exact production caller is inferred.

  pub fn new(
    context: [u8; 32],
    n: u16,
    mut commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<Self, PedPoPError<C>> {
    let mut commitments = HashMap::new();
    let mut encryption = Decryption::new(context);
    for i in 1 ..= n {
      let i = Participant::new(i).unwrap();
      let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
      commitments.insert(i, encryption.register(i, msg).commitments);
    }
    Ok(AdditionalBlameMachine(BlameMachine { commitments, encryption, result: None }))
  }
