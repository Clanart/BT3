### Title
`SignableTransaction` omits the OP_RETURN data output from weight/vbytes estimation, underpaying the intended fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an OP_RETURN output carrying caller-supplied `data` into `tx_outs`, but both fee/size estimations (`calculate_weight_vbytes`) are computed only over `payments` and the optional `change` output. The OP_RETURN output's serialized size (up to ~90 bytes for the 80-byte cap plus output overhead) is never counted, so the produced transaction is larger than estimated and its effective sat/vbyte rate is lower than `fee_per_vbyte` — potentially below the minimum relay fee despite the `TooLowFee` check passing.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the size estimation:

- `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })` at lines 194-202.
- The estimation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, and the change-path estimation at lines 225-227 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`.

Inside `calculate_weight_vbytes` (lines 62-127), the synthetic `Transaction` is built only from `payments` and `change`; there is no parameter or path that includes the OP_RETURN output. Consequently:

- `vbytes` / `vbytes_with_change` exclude the OP_RETURN output (`8` bytes value + compactsize length + script bytes, roughly 12-95 vbytes depending on data length, with script length pushing into a 2-byte compactsize at >252 bytes total script).
- `needed_fee = fee_per_vbyte * vbytes` (lines 206, 227-232) is therefore smaller than `fee_per_vbyte * actual_vsize`.
- The `TooLowFee` check (line 211) compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`, so a transaction whose true fee rate is below the relay minimum can be accepted.
- The change amount `input_sat - payment_sat - fee_with_change` (lines 228-230) is correct in value terms (OP_RETURN carries 0 value) but the change output itself is sized against the wrong total fee target.

The result: `tx.fee()` (`prevouts - outputs`) equals `needed_fee`, but the signed transaction broadcast has a strictly lower sat/vbyte than requested and can be below `minRelayTxFee`, making it non-relayable.

### Impact Explanation
An unprivileged party who can cause a Bitcoin transaction to be signed with a `data` payload (e.g., via a protocol path that embeds `data` in a `SignableTransaction` for the FROST multisig) causes the threshold group to produce a transaction paying a lower fee rate than specified — and possibly an un-relayable one, stalling the associated funds until a new signing round is coordinated. Because `needed_fee` is treated as authoritative ("The actual fee this transaction will use is `sum(inputs) - sum(outputs)`"), there is no later check that catches the shortfall before signing. This is a deterministic accounting error reachable purely through public inputs (`data`, `payments`, `change`) fed to `SignableTransaction::new`.

### Likelihood Explanation
Any call to `SignableTransaction::new` with `data: Some(_)` and a near-minimum `fee_per_vbyte` triggers an underpayment of `(OP_RETURN output vsize) * fee_per_vbyte` sats, and a transaction that falls under the default minimum relay fee when `data` is large. No attacker secret or collusion is required — only the ability to supply the `data` field of a transaction the multisig signs.

### Recommendation
Include the OP_RETURN output in the size estimate: either pass the fully-built `tx_outs` (or the `data` length) into `calculate_weight_vbytes`, or compute the OP_RETURN output's serialized size and add it to `weight`/vbytes before deriving `needed_fee`. The change-path estimation must include it as well so `fee_with_change` reflects the true transaction size.

### Proof of Concept
`networks/bitcoin/src/wallet/send.rs`:

- Line 194-202: OP_RETURN pushed to `tx_outs` unconditionally before estimation.
- Line 204: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` — `data` not passed.
- Lines 68-99: synthetic `tx` contains only `payments` (+ `change`); OP_RETURN never represented.
- Line 206: `let mut needed_fee = fee_per_vbyte * vbytes;` — fee computed on the too-small vbytes.
- Line 211: `TooLowFee` check also uses the underestimated `vbytes`.

Concrete scenario: `fee_per_vbyte = 1` (just above relay minimum), `data` of 80 bytes → OP_RETURN output adds ~93 serialized bytes (~93 vbytes, all non-witness). Estimated `vbytes` misses it, so `needed_fee` passes `needed_fee >= 1000 * vbytes_est / 1000 = vbytes_est` while the true requirement is `vbytes_est + ~93`. The signed transaction broadcasts at `< 1 sat/vbyte` effective rate and is rejected by standard relay policy, yet `SignableTransaction` was already signed by `TransactionMachine`/`TransactionSignMachine` (lines 355-398) with `Prevouts::All` committing to the underpaid outputs.
