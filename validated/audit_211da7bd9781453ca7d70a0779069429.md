### Title
Cached preprocess lets `sign` be invoked repeatedly on the same FROST nonces, defeating the consuming-self nonce-reuse lock - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The audit bug class: a guard meant to prevent a dangerous combination of operations in one flow is bypassed by re-entering through a path the guard doesn't cover (there, `multicall`; here, re-instantiation from a persisted deterministic seed). In Serai, FROST's protection against nonce reuse relies on `SignMachine::sign` consuming `self` (`crypto/frost/src/sign.rs:283`). The coordinator bypasses this protection structurally: `share_internal` calls `preprocess_internal`, which rebuilds an identical `AlgorithmSignMachine` — identical nonces and identical broadcast commitments — from the `CachedPreprocesses` DB seed every time it is invoked (`signing_protocol.rs:137-148`, `156`, `170`). Two invocations under the same context with different preprocess sets or a different `msg` produce two signature shares over the same nonce pair `(d, e)`, enabling recovery of the validator's secret share.

### Finding Description
`preprocess_internal` stores a 32-byte seed in `CachedPreprocesses` keyed by `context` and, on every call, decrypts it and calls `AlgorithmSignMachine::from_cache` (`signing_protocol.rs:123-148`). `from_cache` routes to `seeded_preprocess`, which derives the nonces deterministically via `ChaCha20Rng::from_seed(*seed.0)` (`crypto/frost/src/sign.rs:127-133`). So the nonces are a pure function of the seed — the same nonces every call, forever, for that context.

`DkgConfirmer` fixes `context = (b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:275`), so all calls within one DKG attempt share one nonce pair. `share` and `complete` both accept caller-provided `preprocesses` and a `key_pair`; `key_pair` flows into `msg` via `set_keys_message(...)` (`signing_protocol.rs:296-300`), and `complete` re-runs `share_internal` internally (`signing_protocol.rs:321-324`). Any call reaching `share_internal` with a different `msg` or a different set of peer preprocesses than a prior call causes the same `(d, e)` to be bound under a different `rho`/challenge — the classic ROS/parallel-session nonce-reuse condition. Given two shares `s₁ = d + ρ₁e + λ·x·c₁` and `s₂ = d + ρ₂e + λ·x·c₂` (ρ derivable publicly from the transcripts, since `rho_transcript` commits to public data only — `crypto/frost/src/sign.rs:361-379`), the secret share `x` is recoverable.

The file's own header acknowledges this is only safe because received messages are BFT-finalized identically, and explicitly flags the missing guard: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" and "We also need to review how we're handling Processor preprocesses and likely implement the same on-chain-preprocess-matches-presumed-preprocess check before publishing shares" (`signing_protocol.rs:50-54`). That check is unimplemented — nothing binds the published share to a specific preprocess set or `key_pair`, so the "lock" (consuming `self`) is trivially circumvented by re-execution, exactly as `multicall` circumvented the per-function lock in the original report.

### Impact Explanation
Recovery of a validator's MuSig/FROST secret share under the validator-set key (`musig(...)` keys, `signing_protocol.rs:118-121`). A recovered share weakens the root-of-trust key used to confirm DKG results on Substrate; combined with threshold-many compromised shares this enables forging `set_keys` signatures. It also enables signing an unintended message: an attacker who can supply a `key_pair`/preprocess combination the victim has not actually committed to obtains a valid share for it.

### Likelihood Explanation
Exploitation requires two `share`-producing paths under one `attempt` to diverge in `msg` or preprocess set. Divergence sources are reachable: `key_pair` is an input parameter (`signing_protocol.rs:307`), and the peer preprocess map is attacker-supplied bytes via `read_preprocess`. The defense rests entirely on BFT ordering; the code itself documents gaps (unverified on-chain preprocess matching, processor-side preprocess handling as an open TODO). Because the missing binding check is acknowledged-but-absent rather than merely hypothetical, the analog stands. However, whether an unprivileged party can concretely cause `share`/`complete` to run twice with divergent inputs in a single attempt could not be fully verified from the indexed code — the tributary message handlers in `coordinator/src/tributary/handle.rs` would need review to confirm.

### Recommendation
Bind each published share to the exact session state: before signing, verify that the local machine's commitments match the preprocess recorded on-chain for this context, and record the `msg`/`key_pair` and preprocess set alongside `CachedPreprocesses`, refusing to sign if a subsequent call disagrees. Implement the documented TODO (`signing_protocol.rs:50-54`). Alternatively, scope `context` to include a hash of the message and preprocess set so divergent inputs deterministically yield fresh nonces.

  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
