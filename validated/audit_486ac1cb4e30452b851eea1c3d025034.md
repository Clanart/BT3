## Title
Block-reward proportional split can miscalculate when `stake` exceeds `total_active_stake` during recalculation - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The C4 report describes `shareChange()` in `vToken.sol` computing `newShares = (_amountInAsset * (_totalSupply - oldShares)) / (_assetBalance - availableAssets)`, which silently zeroes out or misallocates the minted amount whenever `oldShares` (a value already counted inside `_totalSupply`) equals or exceeds the "total" it is subtracted from — an invariant the code assumes but does not enforce. The Agave analog is `calculate_block_reward()`, which distributes a vote account's `pending_delegator_rewards` to each delegating stake account proportionally to `stake / total_active_stake`, where `total_active_stake` is a *snapshot* denominator (`reward_epoch_delegated_stakes`) that can become stale/inconsistent relative to the numerator `stake` fetched from a different point in the recalculation flow.

### Finding Description
`calculate_block_reward()` computes each stake's share of a vote account's block-revenue-sharing pool: [1](#0-0) 

```rust
let total_active_stake = reward_epoch_delegated_stakes
    .delegated_stakes
    .get(&vote_pubkey)
    .copied()
    .unwrap_or(0);
if total_active_stake == 0 {
    0
} else {
    let stake = delegation_effective_stake(...);
    // During recalculation, if stake account has already received rewards,
    // it's possible to have `stake > total_active_stake`. If
    // `pending_delegator_rewards` is a huge number, we could potentially
    // overflow a `u64`. We can also have individual rewards look greater
    // than the pending rewards. This is harmless in practice, but we
    // clamp it just to be safe
    (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
        .try_into()
        .unwrap_or(u64::MAX)
        .min(pending_delegator_rewards)
}
```

The code's own comment acknowledges the exact broken invariant: `total_active_stake` (the denominator, a fixed snapshot captured in `RewardEpochDelegatedStakes` for the rewarded epoch) is supposed to represent the sum of all `stake` values (the numerators) computed via `delegation_effective_stake()` for every delegation to that vote account. When recalculation happens (e.g., replaying/adjusting rewards after some stake accounts have already had their delegation increased by previously distributed rewards, similar to the vToken scenario where `oldShares` is already folded into `totalSupply`), an individual `stake` can end up computed as *larger* than the `total_active_stake` snapshot it is being divided by. This is structurally the same defect class as the vToken bug: a value that should represent "this entity's share of the total" is computed independently from, and inconsistently with, the total denominator used to normalize it, so the ratio `stake / total_active_stake` no longer reflects the actual proportional ownership.

The existing guard — `.min(pending_delegator_rewards)` — does not fix the invariant; it only prevents wraparound/overflow in the `u64` conversion, exactly like Phuture's dismissal of the report as "impossible" without actually correcting the arithmetic. If `stake > total_active_stake` for one delegator, that delegator is over-paid (capped only by the entire pool), while the denominator sum across all other delegators to the same vote account no longer sums to 1, meaning the total amount handed out across all stake accounts delegated to that vote pubkey can exceed `pending_delegator_rewards` in aggregate (bounded per-call, but not bounded in sum across all calls for that vote account within the same reward calculation pass).

### Impact Explanation
If the per-delegator clamp is insufficient to prevent aggregate over-distribution across all stakers of a given vote account, this results in lamports being minted/paid out beyond what `pending_delegator_rewards` intends — a fund-issuance/accounting bug in the reward distribution path (`runtime/src/bank/partitioned_epoch_rewards/`), which underpins `bank`/`runtime` reward correctness relied upon for consensus-relevant state (bank hash / capitalization). Incorrect capitalization or over/under-paid stake rewards is exactly the class of "false execution/rooting/acceptance" impact called out as valid.

### Likelihood Explanation
The likelihood is low/uncertain: the trigger condition ("during recalculation, if stake account has already received rewards") is explicitly called out by the code authors as a known, narrow edge case, and the code comment states the observed effect is "harmless in practice" because of the clamp. I was not able to fully trace, within the available tool budget, the exact caller path that performs this "recalculation" (e.g., `redeem_delegation_rewards` / ledger-tool inflation recalculation) to confirm whether the aggregate (not just per-delegator) payout is bounded elsewhere, or whether `total_active_stake` and `stake` can actually diverge under any externally-triggerable, unprivileged transaction sequence rather than only in internal tooling/recalculation utilities. This uncertainty should be resolved before treating this as a confirmed, exploitable bug — the current evidence supports it only as a structural analog of the reported bug class, with the same "invariant asserted in a comment but not enforced in code" pattern as the original finding.

### Recommendation
Do not rely on `.min(pending_delegator_rewards)` alone to bound this calculation. Either:
1. Recompute `total_active_stake` at the same point in time / same pass as `stake`, so the denominator always reflects the sum of the exact numerators being divided by it (mirroring the C4 recommendation of using `_totalSupply - oldShares` — i.e., keep numerator and denominator mutually consistent), or
2. Explicitly assert/track that `sum(stake for all delegations to vote_pubkey) <= total_active_stake` before using it as a divisor, and fail loudly (not silently clamp) if the invariant is violated, so silent misallocation cannot occur undetected in production reward accounting.

### Proof of Concept
Conceptual PoC (could not be executed within available tooling/time budget):
1. Set up a vote account with `pending_delegator_rewards = R` and two stake delegations, A and B, delegated at differing epochs such that `reward_epoch_delegated_stakes.delegated_stakes[vote_pubkey] = total_active_stake` is computed from a stale snapshot (e.g., before a reward-driven increase to A's delegation is reflected).
2. Trigger the "recalculation" code path (as referenced in the inline comment) so that `delegation_effective_stake()` for A returns a `stake_A` value larger than `total_active_stake` (because A's delegation grew due to already-applied rewards not reflected in the snapshot).
3. Observe `calculate_block_reward()` for A returning a reward close to/at `pending_delegator_rewards` (via the `.min()` clamp) while B independently also receives its proportional share based on the same stale `total_active_stake`, causing the sum of A's and B's block rewards to exceed `pending_delegator_rewards`.
4. Confirming step 3 requires running the actual recalculation harness (e.g., `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` tests such as `get_block_reward_for_test`, seen at lines 4246-4318) with deliberately mismatched `individual_stake`/`total_stake` values exceeding the snapshot, which I was unable to execute in this read-only investigation.
