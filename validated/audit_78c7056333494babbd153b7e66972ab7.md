### Title
Unbounded recursive RLP decoding of nested AccountKeyRoleBased account keys enables stack-overflow DoS crash - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each of its sub-keys by calling `rlp.DecodeBytes` on nested byte blobs, and if a sub-key is itself an `AccountKeyRoleBased`, this repeats without any depth limit. The check that rejects nested role-based keys (`ErrNestedCompositeType`) is only enforced later, during `CheckInstallable`/`CheckUpdatable`, which run *after* decoding has already completed. A single crafted `AccountUpdate`-type transaction (or an RLP blob passed to `DecodeAccountKey`) with sufficiently deep nesting can drive unbounded Go call-stack recursion during decode, before any semantic validation occurs.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a `[][]byte`, then for every element calls `rlp.DecodeBytes(b, &serializer)`, where `serializer` is an `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` determines the key type from the encoded bytes and dispatches to `s.Decode(serializer.key)`, which — if `keyType == AccountKeyTypeRoleBased` — invokes `AccountKeyRoleBased.DecodeRLP` again: [2](#0-1) 

This recursion is not bounded by any depth counter in the decode path. The only depth/composite-type enforcement exists in `CheckInstallable`/`CheckUpdatable`, i.e., strictly *after* the entire nested structure has already been fully decoded via the recursive `DecodeRLP` calls: [3](#0-2) 

Since transaction decoding (RLP unmarshalling of an incoming raw transaction) is performed unconditionally whenever a transaction is received (via `eth_sendRawTransaction`, p2p broadcast, or `kaia_decodeAccountKey`/`kaia_encodeAccountKey` RPC calls) — long before `TxPool.validateTx`/`tx.Validate()` runs — the decode-time recursion executes irrespective of whether the transaction would ultimately be rejected as invalid: [4](#0-3) [5](#0-4) 

Each recursion level requires reflect-based RLP decoding (`Stream.Decode`, `makeStructDecoder`, `decodeListSlice`, etc.), which consumes non-trivial stack space per call: [6](#0-5) 

In Go, exceeding the maximum goroutine stack size during unbounded recursion results in a **fatal, unrecoverable runtime error** ("goroutine stack exceeds ... limit") that crashes the entire process — this cannot be caught by `recover()`, unlike an ordinary panic. This is functionally analogous to the referenced MongoDB CVE-2021-32040: a bounded but sufficiently large/nested structure causes stack frames to overflow the stack during a single operation, crashing the whole server process.

### Impact Explanation
Any unprivileged party who can submit a transaction or raw RLP bytes to a node — via `eth_sendRawTransaction`, p2p transaction gossip, or the `kaia_decodeAccountKey`/`kaia_encodeAccountKey` JSON-RPC endpoints — can craft a deeply nested `AccountKeyRoleBased` byte structure to trigger unbounded recursive decoding. If depth is sufficient to exceed Go's max stack size, this crashes the node process (denial of service), independent of whether the resulting transaction/account key would ever be considered valid by subsequent business-logic checks.

### Likelihood Explanation
The attack requires no special privileges, keys, gas payment beyond constructing the RLP bytes, or prior on-chain state — only the ability to submit a transaction/RPC call whose bytes decode before any signature or semantic validation occurs. The `AccountKeyRoleBased` field itself is not otherwise size-restricted at decode time (only post-decode `len(*a) > RoleLast` bounds the top-level list length, not the nesting depth of encoded byte blobs it wraps).

### Recommendation
Enforce a maximum recursion/nesting depth check inside `AccountKeyRoleBased.DecodeRLP` (or in `AccountKeySerializer.DecodeRLP`) that rejects composite/RoleBased sub-keys immediately at decode time, rather than deferring the check to `CheckInstallable`/`CheckUpdatable`. This mirrors the effect of MongoDB's `internalPipelineLengthLimit` workaround — bound the recursive structure size before performing expensive/stack-heavy recursive work.

### Proof of Concept
1. Construct nested `AccountKeySerializer` RLP blobs: start with a leaf `AccountKeyPublic`, wrap it in an `AccountKeyRoleBased([leaf])`, then repeatedly wrap the resulting serialized bytes in another `AccountKeyRoleBased` layer, for N levels (N large, e.g. tens of thousands, achievable within normal tx size limits since only wrapper overhead is required per level).
2. Encode the final structure as the `Key` field of an `AccountUpdate` transaction (or pass it directly as the argument to `kaia_decodeAccountKey`).
3. Submit the transaction via `eth_sendRawTransaction` / p2p gossip, or call `kaia_decodeAccountKey` via RPC.
4. Observe that `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recurses N times before any `CheckInstallable`/`ErrNestedCompositeType` rejection can occur, exhausting the goroutine stack and crashing the node process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
