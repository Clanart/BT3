### Title
`ManualCompound.compound` sweeps the contract's entire reward-token balance to `msg.sender`, letting anyone steal residual/dust reward tokens left by other users - (File: `rewards/ManualCompound.sol`)

### Summary
`compound(address[] _lps, address[][] _rewards, uint256 _convertRatio, uint256 _minRec, bool _lockMgp)` claims rewards through `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` and then, for every configured reward token, converts/locks/deposits `IERC20(_tokenAddress).balanceOf(address(this))` (the contract's *total* balance) entirely to `msg.sender`. Because the conversion loop is driven by the contract's raw token balance rather than by an amount actually attributable to the caller, any balance of a compoundable reward token that happens to sit on the contract from a prior transaction is credited in full to whoever calls `compound` next.

### Finding Description
`compound` performs two loops:
1. A "non-compoundable reward" sweep that only processes tokens present in the caller-supplied `_rewards` arrays.
2. The compoundable-rewards loop at [1](#0-0)  which iterates over `rewards` (the full, permanent list of configured reward tokens, independent of what `_lps`/`_rewards` were passed this call) and, for each, reads `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))` and forwards **all of it** to `msg.sender` via `convertFor(..., msg.sender, 2)`, `lockFor(..., msg.sender)`, `depositFor(..., msg.sender)`, or a plain transfer.

The claiming step, `multiclaimOnBehalf`, is gated with `_onlyCompounder` on `MasterMagpie` [2](#0-1) , so it does correctly attribute the *claimed* amount to the actual caller (`_account` = the compound-function caller, receiver = `ManualCompound`). However, the subsequent conversion step does not use the amount that was just claimed — it re-reads the contract's live balance. There is no accounting structure (no per-user pending balance, no "amount claimed this tx" tracking) tying `receivedBalance` to the specific caller's entitlement.

Consequently, if any residual balance of a configured reward token remains on the contract from an earlier transaction — e.g., dust from a previous compound where the amount consumed by `convertFor`/`lockFor`/`depositFor` did not exactly equal the approved/transferred amount, rounding remainders in the underlying conversion/staking logic, or tokens sent to the contract outside the exact claim-then-convert sequence — the very next unprivileged caller of `compound` (even one who calls it with empty `_lps`/`_rewards`, or with LPs/rewards unrelated to the leftover token, since the loop is keyed on `rewards[i].tokenAddress` and not on what was passed in) will have that residue swept into their own conversion/lock output. This breaks the invariant that converted value must be attributed to the account that earned it.

No modifier, reentrancy guard, or balance-tracking exists in `ManualCompound` to prevent this: `compound` is `external` with no access restriction beyond what `multiclaimOnBehalf`'s `_onlyCompounder` enforces on the `ManualCompound` contract itself (satisfied automatically since `ManualCompound` is the caller of `MasterMagpie`), and any EOA can call `ManualCompound.compound` directly.

### Impact Explanation
Any residual balance of a compoundable reward token accumulated on `ManualCompound` — belonging in aggregate to prior compounders whose conversion left dust, or resulting from rounding in the downstream `convertFor`/`lockFor`/`depositFor` calls — can be redirected entirely to an unrelated, unprivileged caller. This is a direct diversion of value that rightfully belongs to other users into the attacker's locked position (`mWomSV`/`vlMGP`), matching "theft of user funds"; however, the loss is bounded by whatever residue accumulates, not by draining live user deposits or actively-staked principal, since `multiclaimOnBehalf` itself does correctly gate claims to the caller's own stake.

### Likelihood Explanation
Exploitation requires no special privileges — any EOA can call `compound` with arbitrary/empty `_lps` and `_rewards` arrays and still trigger the second loop over all configured `rewards`, since that loop is independent of the calldata-supplied `_lps`/`_rewards`. The precondition is that some residue of a configured reward token exists on the contract at call time. Whether the underlying `convertFor`/`lockFor`/`depositFor` implementations reliably consume exactly `receivedBalance` (leaving zero dust) could not be fully confirmed from the portions of `wombat/SmartWomConvert.sol` and `wombat/mWomSV.sol` retrieved in this session; this materially affects how often/how large residues can realistically be, and should be checked directly in the repository (full contents of these files were not available through the indexed search).

### Recommendation
Track and convert only the amount actually claimed for the caller in the current transaction (e.g., have `multiclaimOnBehalf` return per-token claimed amounts, or snapshot `balanceOf(address(this))` before and after the claim call and only process the delta) instead of relying on the live `balanceOf(address(this))`, which can include residue from other users' transactions. Any leftover dust from the delta calculation should be swept by the contract owner/treasury, not left ambiguous, or accounted for in a persistent global "owed to distribute" pool rather than blindly attributed to the next caller.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, `ManualCompound`, a reward token (e.g., mock WOM), and a mock `IConverter` implementing `convertFor`.
2. Configure `ManualCompound.addReward(rewardToken, helper=0, convertor=mockConverter, locker=0)`.
3. Simulate residue: directly `rewardToken.transfer(manualCompound, dustAmount)` to emulate a leftover from a prior imperfect compound (or, if reachable, run one real `compound()` call by user A that leaves `dustAmount` unconverted due to convertor rounding).
4. From an unrelated address B (no stake, no claims), call `compound([], [], 0, 0, false)`.
5. Assert: `mockConverter` received `convertFor(dustAmount, ..., B, 2)` — i.e., B's locked `mWomSV`/converted balance increased by `dustAmount` despite B never having earned that reward.
6. Assert: `rewardToken.balanceOf(manualCompound)` dropped to 0 and the value is now attributed to B instead of the original earner (user A or the protocol).
