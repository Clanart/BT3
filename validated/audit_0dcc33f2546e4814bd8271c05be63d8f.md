### Title
Instant, non-time-weighted bribe distribution in `BribeRewardPool`/`WombatBribeManager.castVotes` allows front-running voters to steal accrued yield - (File: wombat/WombatBribeManager.sol, rewards/BribeRewardPool.sol, rewards/BaseRewardPoolV2.sol)

### Summary
`WombatBribeManager.vote()` calls `BribeRewardPool.stakeFor()`, which credits the caller's balance and `totalSupply` immediately, with no minimum holding period or time-weighting. `castVotes()`/`voteAndCast()` then harvests bribes and forwards them into the same pool via `_provisionReward()`, which instantaneously stretches `rewardPerTokenStored` over the *current* `totalStaked()`. An attacker can front-run a pending `castVotes` transaction (or bundle `vote()`+`castVotes()` via `voteAndCast()`) to insert their vlMGP vote weight one block/instruction before the bribe is queued, capturing a full proportional share of the harvested bribe despite that vote weight never having been registered on Wombat for the period that earned the bribe, and then immediately `unvote()` to reclaim their vlMGP.

### Finding Description
- `vote()` increases `pool.totalVoteInVlmgp` and calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, delta)` [1](#0-0) .
- `BribeRewardPool.stakeFor` is wrapped in `updateRewards(_for, rewardTokens)`, which checkpoints the caller's `userRewardPerTokenPaid` to the *current* `rewardPerToken` *before* `totalSupply`/`_balances[_for]` are incremented in the function body [2](#0-1) [3](#0-2) .
- `castVotes()` immediately after calls `wombatStaking.vote(...)` which harvests bribes and (via `_forwardRewards`/pool rewarder `queueNewRewards`) triggers `_provisionReward`, which computes `rewardPerTokenStored += amountReward * scale / totalStaked()` using the **instantaneous** `totalStaked()` — no duration, no streaming, no time-weighting [4](#0-3) ; [5](#0-4) .
- Because the attacker's `userRewardPerTokenPaid` was checkpointed *before* the reward bump but their balance was already added to `totalStaked()` (the denominator) at the time the bump occurred, `earned = balance * (rewardPerTokenStored_after - checkpoint) / scale` gives the attacker a full proportional share of the whole harvested bribe, diluting the share owed to voters who actually held vote weight through the period that generated the bribe on Wombat.
- `voteAndCast()` makes this composable in a single transaction, and `unvote()` allows immediate exit with `claim=true`, so exposure is limited to essentially one block [6](#0-5) [7](#0-6) .
- No modifier, cooldown, or time-weighted accounting exists anywhere in this path to prevent a last-instant staker from claiming a full epoch's bribe share.

### Impact Explanation
This is a real, code-supported yield-theft/dilution bug: an attacker with real (non-flash-loanable) vlMGP voting power can systematically capture a disproportionate share of bribes relative to the time their vote was actually reflected on Wombat, at the expense of long-term voters, every time a `castVotes`/`voteAndCast` transaction is pending. This matches the "theft of unclaimed yield" impact category. It does **not** put user principal (staked vlMGP/underlying LP) at risk — `stakeFor`/`unvote` correctly track vote accounting (`getVoteForLp` vs `poolInfos[lp].totalVoteInVlmgp` reconciliation is not broken by this, since votes pushed to Wombat are computed from `poolInfos[lp].totalVoteInVlmgp` correctly at cast time), so the "Critical — direct theft of user funds" classification claimed in the prompt is overstated; the concretely demonstrable impact is repeatable theft/dilution of bribe yield, not principal.

### Likelihood Explanation
Feasible for any holder of real vlMGP (no flash loan possible since vote power is not a transferable flash-borrowable asset), requiring only the ability to front-run or bundle a transaction ahead of a pending `castVotes` call — a capability explicitly permitted to the attacker in this assessment. It is fully repeatable every time bribes are cast, scaling with the attacker's own vlMGP holdings relative to total votes for that pool.

### Recommendation
Introduce time-weighting or a minimum lock/cooldown before newly staked vote weight is eligible to receive bribes queued in the same or an adjacent block (e.g., checkpoint rewards using a duration-based streaming model like Synthetix's `StakingRewards`, or snapshot eligible balances prior to `castVotes` execution rather than using live `totalStaked()`/`balanceOf` at the moment of `_provisionReward`).

### Proof of Concept
Hardhat test plan:
1. Deploy `WombatBribeManager`, `BribeRewardPool`, and mock `wombatStaking`/`Voter` returning a fixed bribe amount on `vote()`.
2. Set up two vlMGP holders: `Alice` (long-term voter, votes N-1 blocks earlier) and `Attacker` (no prior vote).
3. Simulate a keeper `castVotes()` transaction sitting in the mempool (do not mine it yet).
4. Have `Attacker` call `vote()` with a large delta for the same pool, mined in the same block right before the keeper's `castVotes()`.
5. Mine the keeper's `castVotes()` — bribe is harvested and queued into `BribeRewardPool`.
6. Assert: `Attacker.earned(rewardToken)` is proportional to `Attacker`'s just-added balance / total balance at harvest time, i.e., non-zero and comparable to `Alice`'s despite `Attacker` never having voted for a full epoch, while `Alice.earned` is reduced compared to a baseline run without `Attacker`'s front-run vote.
7. Have `Attacker` immediately call `unvote()` with `claim=true` to withdraw the reward and reclaim vlMGP voting power in the same test, showing full capital efficiency and repeatability.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
