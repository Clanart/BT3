### Title
`SignableTransaction::new` uses wallet `DUST` (546 sat) instead of the processor's `N::DUST` (10,000 sat) when deciding to emit a change output, creating change the scanner will permanently ignore - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
The reported bug class is a validation check performed against the wrong (far smaller) constant, admitting values the protocol intends to reject. In Serai, `SignableTransaction::new` gates both payments and the change output on the wallet-level constant `DUST = 546`, while the processor's scanner only registers received outputs whose value is `>= N::DUST`, where `Bitcoin::DUST = 10_000`. A change output in `[546, 10_000)` sats is therefore constructed, signed, broadcast, and then silently dropped by Serai's own scanner, stranding the funds.

### Finding Description
`networks/bitcoin/src/wallet/send.rs` defines `pub const DUST: u64 = 546` (the Bitcoin relay dust limit) and uses it for two distinct checks:

- Payment validation: `if *amount < DUST { Err(TransactionError::DustPayment)? }` (`send.rs:165-169`).
- Change emission: `if value >= DUST { tx_outs.push(...) }` (`send.rs:228-234`).

Meanwhile, the processor defines a much larger economic dust threshold `const DUST: u64 = 10_000` (`processor/src/networks/bitcoin.rs:638`), deliberately chosen as an order of magnitude above the spend-fee estimate so that tracked outputs are always worth spending. The scanner enforces exactly this bound when deciding which on-chain outputs belong to Serai:

```rust
// processor/src/multisigs/scanner.rs:562-567
for output in network.get_outputs(&block, key).await {
  assert_eq!(output.key(), key);
  if output.balance().amount.0 >= N::DUST {
    outputs.push(output);
  }
}
```

The change address is a Serai-owned key (`N::change_address`, used in `scheduler/utxo.rs:261,382,429`), so any change output comes back to an address the scanner watches — but with the `>= N::DUST` filter. Whenever `input_sat - (payment_sat + fee_with_change)` lands in `[546, 10_000)`, `SignableTransaction::new` happily adds the change output (since `value >= 546`), while the scanner will never emit it (since `value < 10_000`). The only relationship enforced anywhere is the compile-time test `Bitcoin::DUST >= bitcoin_serai::wallet::DUST` (`processor/src/tests/literal/mod.rs:53`), which guarantees consistency for *payments the processor itself originates* but does nothing for the change path, where the wallet's smaller constant is the sole gate.

### Impact Explanation
Any change output created with value in `[546, 10_000)` sats is confirmed on-chain to a Serai change address yet is never delivered via `ScannerEvent::Block`, never added to `self.utxos` in `Scheduler::schedule`, and never reported to the coordinator as a received output. The funds are effectively burned: the multisig cannot spend an output it does not track, and the discrepancy permanently desynchronizes the scheduler's accounting (`self.utxos` / `balance` computations in `scheduler/utxo.rs:388-409`) from the real on-chain UTXO set. This is "funds sent to the protocol that are not spendable/credited" — a concrete loss-of-funds class rather than a policy nit, since the protocol's own constants disagree about which outputs exist.

### Likelihood Explanation
An unprivileged user influences the residual through public inputs only: the payment amounts they request (withdrawals) and the deposit amounts they send determine `input_sat`, `payment_sat`, and hence the change residual `input_sat - payment_sat - fee_with_change`. Since inputs and payments are attacker-influenced u64 amounts, hitting the 9,454-sat window `[546, 10_000)` is straightforward across the many transactions the scheduler produces (payments TXs, aggregation TXs, and forced spends all carry change to `N::change_address`). No validator misbehavior, collusion, or RPC compromise is required — ordinary deposits/withdrawals suffice. Severity: Medium.

### Recommendation
Gate the change-output decision on the processor's economic dust bound rather than the relay bound. Concretely, in `SignableTransaction::new` (`send.rs:224-235`) compare `value` against a threshold that is `>= N::DUST` for the network the transaction targets — e.g., have the caller (the processor's `Plan` → `SignableTransaction` construction path) supply the minimum acceptable change value, or raise the wallet `DUST` used for the change check so that any emitted change is guaranteed to be re-scanned. Alternatively, fold sub-`N::DUST` residuals into the fee unconditionally and assert consistency between the wallet-level and network-level dust constants in the same compile-time test that already relates them.

### Proof of Concept
1. A user arranges inputs and payments such that for a processor-built transaction, `input_sat - payment_sat - fee_with_change = 5_000` sats (feasible via choice of deposit amount and withdrawal amount).
2. `SignableTransaction::new` evaluates `5_000 >= DUST (546)` at `send.rs:229` and appends a 5,000-sat `TxOut` to `N::change_address`.
3. The transaction is signed by `TransactionSignMachine::sign` (`send.rs:355-398`) and broadcast.
4. Once confirmed and scanned (`scanner.rs:562-567`), the scanner computes `output.balance().amount.0 = 5_000 < N::DUST = 10_000` and drops the output; it never enters `self.utxos` in `Scheduler::schedule` (`scheduler/utxo.rs:295,388`).
5. The 5,000 sats remain at a Serai-controlled change address permanently untracked and unspendable, while the scheduler's internal balance accounting no longer matches the on-chain UTXO set.

I was unable to verify the exact call site that converts a `Plan` into `SignableTransaction::new`'s `payments`/`change` arguments (the `processor` transaction-building path beyond `scheduler/utxo.rs`); confirming that no additional `N::DUST` clamp is applied to change there would strengthen the finding, but the constant mismatch between `send.rs:229` and `scanner.rs:564` is directly evidenced above.
