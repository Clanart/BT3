## Analog Identified: Missing XSS-Hardening Escape of `<`/`>` in upb-based ProtoJSON Encoder (PHP/Ruby/Python)

### Title
Attacker-controlled string values are not escaped for `<`/`>` when serialized to JSON via the upb JSON encoder, unlike the C++/Java/C# JSON writers — (`upb/json/encode.c`)

### Summary
The RabbitMQ CVE's failed invariant is: user-influenced string data must be sanitized before it reaches a context where it can be interpreted as executable markup (HTML/`<script>`). Protobuf's C++, Java, and C# ProtoJSON writers implement exactly this safety invariant by additionally escaping `<` and `>` (and a few Unicode look-alikes) beyond what the JSON spec requires, explicitly to prevent JavaScript/XSS injection when JSON output is later embedded in an HTML page. The upb-based JSON encoder — which backs PHP's `google/protobuf` extension, Ruby's `protobuf_c` extension, and can back Python's `_message` implementation — does not apply this same escaping, creating an inconsistency where the exact same attacker-controlled `string` field, serialized via `Message.serializeToJsonString`-equivalent calls in these languages, will contain a raw, unescaped `<`/`>`.

### Finding Description
In the C++ core JSON writer, `MustEscape()` explicitly treats `<` and `>` as must-escape characters "to prevent security bugs in JavaScript": [1](#0-0) 

The Java `JsonFormat` printer independently implements the identical hardening, escaping `<>&='` with the comment "escaped to prevent XSS risks": [2](#0-1) 

The C# `JsonFormatter` also escapes `<`/`>` to `\u003c`/`\u003e` "required for HTML security": [3](#0-2) 

In contrast, the upb C JSON encoder's character-escaping routine — shared verbatim across `upb/json/encode.c`, `php/ext/google/protobuf/php-upb.c`, and `ruby/ext/google/protobuf_c/ruby-upb.c` — only escapes `\n \r \t \" \f \b \\` and raw control bytes `< 0x20`. It has no `case '<':`/`case '>':` branch at all: [4](#0-3) 

This routine (`jsonenc_stringbody`/`jsonenc_string`) is used for ordinary string field values, map keys, and `Any`/type_url output: [5](#0-4) 

So a string field value like `</script><script>alert(1)</script>`, set by an ordinary client through a public message-building/setter API and then serialized via the language's normal "to JSON string" call, comes out of PHP's or Ruby's upb-backed JSON serializer with those characters completely literal, whereas the same value serialized by the C++, Java, or C# ProtoJSON writer would have them converted to `\u003c`/`\u003e`.

### Impact Explanation
This is a direct binary-encoded-then-ProtoJSON-re-encoded analog of the RabbitMQ bug: an attacker-controlled string (the RabbitMQ "consumer tag" analog is any Protobuf `string` field) flows through a *trusted, schema-conformant* serialization path and reaches JSON output without the same sanitization invariant that upstream Protobuf itself considers a required security control elsewhere in the very same codebase (evidenced by the explicit "prevent XSS risks"/"prevent security bugs in JavaScript" comments). If a consuming web application takes this JSON (a common integration pattern: server serializes a protobuf message to JSON and embeds it directly in an HTML `<script>` block to bootstrap client-side state — the same failure mode the C++/Java/C# code was hardened against), an attacker-controlled `<`/`>` sequence can break out of the intended JSON/script context and inject script, i.e. reflected/stored XSS in the consuming application, mirroring the RabbitMQ management UI's unescaped consumer-tag rendering.

### Likelihood Explanation
Likelihood is Medium: exploitation requires a consuming application to embed upb-encoded ProtoJSON output directly into HTML without its own separate escaping — the exact "consuming-application exposure assumption" pattern from the RabbitMQ report, not a Protobuf RPC endpoint by itself. No privileged access, hostile schema, or unbounded resource use is needed; the only precondition is passing an ordinary, valid string through a supported public ProtoJSON serialization API on the PHP/Ruby/Python-upb backends. Because the analogous protection already exists (and is explicitly documented as a security control) in the C++, Java, and C# implementations, its absence in the upb encoder is a genuine, provable divergence rather than an allowed cross-implementation formatting difference.

### Recommendation
Add the same `<`/`>` (and, for full parity, the Unicode zero-width/format-character) escaping to `jsonenc_put_escaped_char` in `upb/json/encode.c`, and regenerate/sync the copies embedded in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`, so all Protobuf JSON writers uniformly escape these characters as documented security hardening.

### Proof of Concept
Conceptual reproduction (schema and API are trusted/valid; only the string payload is attacker-controlled):
1. Define any proto message with a `string` field, e.g. `message M { string s = 1; }`.
2. In PHP or Ruby (upb-backed), set `s = "</script><script>alert(1)</script>"` and call the standard `serializeToJsonString()`/`to_json` API.
3. Observe the output JSON contains the literal substring `</script><script>alert(1)</script>` unescaped, i.e. `{"s":"</script><script>alert(1)</script>"}`.
4. Perform the equivalent serialization in Java (`JsonFormat.printer().print(...)`) or C++ (`json_util`) with the same string value and observe `<`/`>` are converted to `\u003c`/`\u003e` per `MustEscape()`/`getReplacementOrNull()`, confirming the divergence exists specifically in the upb encoder's `jsonenc_put_escaped_char`.

**File:** upb/json/encode.c (L268-301)
```c
static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}
```

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
