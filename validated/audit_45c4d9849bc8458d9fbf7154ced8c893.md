### Title
Missing identity/zero validation of verification shares in `ThresholdKeys::new`/`ThresholdKeys::read` yields an identity group key with universally forgeable signatures - (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class is failure to validate that a security-critical value is non-zero before installing it. In Serai, `ThresholdKeys::new` computes the group key by interpolating the first `t` verification shares, and `ThresholdKeys::read` deserializes those shares with `Ciphersuite::read_G`, which validates canonical encoding but does **not** reject the identity (zero) point. As a result, untrusted bytes fed to `ThresholdKeys::read` can construct a `ThresholdKeys` whose `group_key` is the identity point. Any Schnorr/FROST signature verification against the identity public key is trivially forgeable by an unprivileged party, so funds "secured" by such a key are spendable by anyone, and recovery succeeds while returning a false sense of validity.

### Finding Description
`Ciphersuite::read_G` enforces canonical encodings only; it explicitly permits the identity point (`crypto/ciphersuite/src/lib.rs:91-101`). `ThresholdKeys::read` uses `C::read_G` (the `Ciphersuite` impl, not the identity-rejecting `Curve::read_G`) for each verification share (`crypto/dkg/src/lib.rs:620-623`), then calls `ThresholdKeys::new`. `ThresholdKeys::new` only checks the count of verification shares and that each participant index is `<= n` (`crypto/dkg/src/lib.rs:355-365`); it never checks that a share is non-identity. The group key is then computed as `sum(verification_shares[i] * interpolation_factor(i))` over `i in 1..=t` (`crypto/dkg/src/lib.rs:376-378`). If the first `t` serialized shares are all identity (a trivially encodable input: the all-zero/`0x01`-prefixed canonical identity encoding per curve), the resulting `core.group_key` is `G::identity()`.

Downstream, `group_key()` returns `(identity * scalar) + (generator * offset)`, which is identity when no offset is applied (`crypto/dkg/src/lib.rs:445-447`). `SchnorrSignature::verify` checks `R + cA - sG == 0` via `batch_statements` (`crypto/schnorr/src/lib.rs:88-110`). With `A = identity`, the statement reduces to `R - sG == 0`, which any attacker satisfies by choosing arbitrary `s` and `R = sG` — a forged signature against the group key with no secret knowledge. `recover_key` (`crypto/dkg/recovery/src/lib.rs:80`) even accepts these keys since `generator * res == group_key` holds for `res = 0`-consistent interpolations, confirming the corrupt state is silently accepted.

Note that elsewhere the codebase does enforce this check where it matters: `Curve::read_G` rejects identity (`crypto/frost/src/curve/mod.rs:125-131`), which protects FROST nonce commitments, and `Curve::random_nonce` rejects zero nonces. The gap is specifically that `ThresholdKeys::new`/`read` trust verification shares to be non-identity when deriving the group key.

### Impact Explanation
An identity group key is a key whose secret is 0, controlled by no one and therefore effectively by everyone: any unprivileged party can produce valid Schnorr signatures for it (choose `s`, set `R = sG`). If a node loads crafted `ThresholdKeys` bytes (e.g., restored key material, or keys reconstructed from untrusted inputs), every subsequent FROST signing session produces signatures for an identity key — outputs credited to that key (e.g., a Bitcoin output paying the identity tweaked key) are immediately stealable by any observer, and shares contributed are effectively wasted. This matches the report's impact: a zero-value assignment silently transfers control of the resource.

### Likelihood Explanation
The attack requires an attacker to cause malicious bytes to reach `ThresholdKeys::read` — a documented untrusted-input surface. `Participant` index 0 is already rejected (`Participant::new` at `crypto/dkg/src/lib.rs:600`), and `ThresholdParams::new` bounds `t`/`n`/`i`, but nothing blocks the all-identity share vector. Exploitation additionally requires the victim to treat the resulting identity group key as authoritative (no on-chain confirmation of a non-identity key). Because honest DKG output can never produce identity shares, this is a Medium-severity deserialization-input hardening gap rather than a routine-path forgery.

### Recommendation
Reject the identity point when reading or accepting verification shares: either call an identity-rejecting point reader inside `ThresholdKeys::read`/`ThresholdKeys::new` (mirroring `Curve::read_G`'s `is_identity` check), and/or assert `!group_key.is_identity()` after interpolation in `ThresholdKeys::new` (before `crypto/dkg/src/lib.rs:380`), returning a `DkgError`. Additionally consider rejecting a zero `secret_share` for consistency, since a zero share under an identity-adjacent key provides no security.

### Proof of Concept
```rust
// For any in-scope ciphersuite C (e.g., Ristretto / Secp256k1)
let id_bytes = C::G::identity().to_bytes();

// Build a serialized ThresholdKeys buffer with t = n = 2, i = 1
let mut serialized = vec![];
serialized.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
serialized.extend(C::ID);
serialized.extend(2u16.to_le_bytes()); // t
serialized.extend(2u16.to_le_bytes()); // n
serialized.extend(1u16.to_le_bytes()); // i
serialized.push(1);                    // Interpolation::Lagrange
serialized.extend(C::F::ZERO.to_repr().as_ref()); // secret_share = 0
for _ in 0 .. 2 {
    serialized.extend(id_bytes.as_ref());         // identity verification shares
}

let keys = ThresholdKeys::<C>::read::<&[u8]>(&mut serialized.as_ref()).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // accepted: group key is identity

// Universal forgery against the identity group key:
// SchnorrSignature::verify checks R + cA - sG == 0; with A = identity, pick any s, R = sG.
let s = C::F::random(&mut OsRng);
let forged = SchnorrSignature::<C> { R: C::generator() * s, s };
assert!(forged.verify(keys.group_key(), arbitrary_challenge)); // verifies with no secret
```
