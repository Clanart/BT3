## Confirmed local analog: Tron `IntentGatewayV2.placeOrder` escrows the fee-reduced amount but uses `IERC20.safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` for the *nominal* (pre-transfer) amount, never checking what the contract actually received

### Title
Escrow ledger overstates actual token balance for fee-on-transfer / deflationary ERC-20 inputs in Tron `IntentGatewayV2.placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Sherlock report's core invariant break is: a ledger entry (`UnbondingDelegationEntry.initial_balance` in `UNSTAKING_QUEUE`) records a value that can legitimately diverge from the value the contract actually ends up holding (`balance`, reduced by slashing), and the withdraw path spends against the recorded value instead of the actual balance, causing reverts/blocking. The same pattern exists in `evm/tron/contracts/apps/IntentGatewayV2.sol`: `_orders[commitment][token]` is credited with `reducedInputs[i].amount` (nominal amount minus protocol fee) rather than the token amount the contract actually received via `safeTransferFrom`, which for fee-on-transfer/deflationary/rebasing ERC-20s is smaller than requested.

### Finding Description
In the no-predispatch branch of `placeOrder`: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then immediately credits escrow with `reducedInputs[i].amount`, which is derived purely from `order.inputs[i].amount` minus the protocol fee bps — no balance-before/balance-after check is performed anywhere in this function.

Compare this with the mainline (non-Tron) `IntentGatewayV2.sol`, which explicitly measures actual received balance and mutates `order.inputs[i].amount` to the real transferred amount before computing fees and escrow: [2](#0-1) 
and the fee-on-transfer regression tests that assert `_orders[commitment][token]` must equal actually-received balance, not the nominal amount: [3](#0-2) 

The Tron contract has no equivalent "measure actual received" step for either the plain-transfer or predispatch path, so for any ERC-20 with a transfer fee, rebase-on-transfer, or a taxed/deflationary supply mechanic, `_orders[commitment][token]` will be strictly larger than `IERC20(token).balanceOf(address(this))` attributable to that commitment.

This directly mirrors the M-7 defect: the ledger (`_orders[commitment][token]`, analogous to `UnbondingDelegationEntry.initial_balance`) records more than what is actually custodied (analogous to `UnbondingDelegationEntry.balance` after slashing).

### Impact Explanation
When a fill/redeem/refund is later settled, `withdraw()` (or `_withdraw()` in the base contract used elsewhere) attempts to transfer `amount` (equal to the over-recorded escrow) to the beneficiary: [4](#0-3) 
Since the actual token balance held by the contract for that order is smaller than the ledger says, the outbound `token.call(...transfer...)` will fail (insufficient balance) or, because multiple orders share the same contract-wide token balance, the shortfall can be silently paid out of tokens escrowed for *other, unrelated orders* — draining their custody and causing their own later withdrawals to fail. This is:
- Loss/lock of user or solver funds (order withdrawal permanently reverts, exactly like the M-7 "failure due to insufficient balance").
- Cross-order fund misappropriation: a legitimate order's `withdraw()` can consume ERC-20 balance that rightfully belongs to a different order's escrow, since `_orders[commitment][token]` is only an internal accounting variable, not a real balance guarantee — this is a wrong-beneficiary/wrong-amount fund movement, which matches the bounty's "stealing or loss of funds" / "transaction manipulation" categories.
- Blocks the queue/settlement path exactly as described in the source report (subsequent order withdrawals against the same token pool can fail once the pool is depleted below what the ledger promises).

### Likelihood Explanation
This is reachable by any unprivileged user placing an order (`placeOrder`) with a fee-on-transfer, deflationary, or rebase-on-transfer ERC-20 token as `order.inputs[i].token` — no relayer, prover, admin, or governance action is required. Such tokens are common in production DeFi (fee-on-transfer tokens, reflection tokens). Because the mainline `IntentGatewayV2.sol` had to be patched specifically for this class of token (as evidenced by the dedicated fee-on-transfer test suite), the Tron variant appears to be an un-ported/regressed copy that reintroduces the exact defect the mainline contract fixed.

### Recommendation
Mirror the mainline contract's fix in the Tron deployment: measure `balanceOf(address(this))` before and after each `safeTransferFrom` (and after the predispatch sweep), and use the actually-received delta — not `order.inputs[i].amount` — as the basis for both the commitment hash and the amount credited to `_orders[commitment][token]`. Additionally, in `withdraw()`, replace the `escrowed == 0` sentinel check with `escrowed < amount` before decrementing, so an under-collateralized escrow reverts cleanly and cannot silently draw down a different order's balance.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a 1% fee-on-transfer ERC-20 as the input token, `protocolFeeBps = 0` for simplicity so `reducedInputs[i].amount == order.inputs[i].amount`.
2. User calls `placeOrder` with `order.inputs[0].amount = 1000e18`.
   - `safeTransferFrom` moves `1000e18` nominal, but the gateway actually receives `990e18` (1% fee).
   - `_orders[commitment][token] += 1000e18` (not `990e18`).
3. Gateway's real `balanceOf(address(this))` for this token is `990e18`, but the ledger says `1000e18`.
4. On solver `fillOrder`/cross-chain redeem, `withdraw()` attempts to transfer `1000e18` to the beneficiary using `_orders[commitment][token] -= amount` bookkeeping — this either reverts (insufficient balance) if this is the only order for that token, or succeeds by consuming `10e18` that belongs to a different, unrelated order's escrow if the pool holds enough from concurrent orders, corrupting that other order's future withdrawal.

Note: this analysis is scoped to the Tron contract copy in `evm/tron/contracts/apps/IntentGatewayV2.sol`; I was not able to fully verify whether Tron-network TRC-20 tokens commonly exhibit fee-on-transfer behavior in production (this affects likelihood but not the code-level correctness of the defect), and a Devin session with repo access would be needed to check whether this Tron contract is actually deployed/used in production versus being a reference/test artifact.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
