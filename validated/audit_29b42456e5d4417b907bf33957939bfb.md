## Title
Spoofed `WWW-Authenticate` realm on a malicious remote/proxy tricks the credential helper into launching a GitHub Enterprise sign‑in flow against the attacker's own host, capturing user credentials - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind()` in the git credential trampoline classifies an unknown remote host as `'enterprise'` (a GitHub Enterprise Server) purely by inspecting the `WWW-Authenticate` header that the remote server returned to git, without any cryptographic or independent verification. This classification is attacker-controlled input from the remote git server itself. When the host is classified as `'enterprise'`, `getCredential()` triggers `promptForGitHubSignIn(endpoint)`, which — for any hostname other than `github.com` — calls `dispatcher.setSignInEndpoint(origin)` using the **attacker's own origin**, i.e. it points the "GitHub Enterprise sign‑in" dialog directly at the malicious server. A user who adds/clones from a malicious remote (or is MITM'd via a proxy) and is prompted to "sign in" will have their entered username/password/PAT sent straight to the attacker.

### Finding Description
The classification chain is:

1. `getEndpointKind()` [1](#0-0)  inspects `wwwauth[...]` credential fields (which git populates from the server's `WWW-Authenticate` response header) and returns `'enterprise'` if it contains `realm="GitHub"`.
2. `getCredential()` uses this classification: if `endpointKind !== 'generic'` and no existing account matches the endpoint, it calls `ui.promptForGitHubSignIn(endpoint)` [2](#0-1) .
3. `promptForGitHubSignIn()` in `TrampolineUIHelper` checks only `hostname === 'github.com'`; for any other hostname (including the attacker's) it calls `beginEnterpriseSignIn(cb)` and `setSignInEndpoint(origin)` with the **attacker-controlled origin** [3](#0-2) .

The `origin` passed to `setSignInEndpoint` is derived directly from `getCredentialUrl(cred)`, which is built from git's credential protocol fields (`url`/`host`/`protocol`) supplied by the git subprocess talking to the untrusted remote [4](#0-3) . Nothing in this path verifies that the host claiming to be "GitHub" actually is GitHub — it is purely a self-reported HTTP header from the party attempting to authenticate the connection, i.e. the attacker. This is the same class of bug as the GMX `EmptyFeedPrice` issue: a classification helper (`isEmptyPriceError()` / `getEndpointKind()`) has an allow-listed branch that is trusted to gate a consequential action (skip-cancel-order / skip-generic-prompt-and-launch-enterprise-signin) without verifying the underlying condition is genuine, letting attacker-supplied data steer the branch into the unsafe path.

By contrast, the code does have a legitimate independent verification mechanism, `isGitHubHost()`, which performs an actual network probe checking for the `x-github-request-id` response header from a real GitHub host [5](#0-4) , and this is used as a fallback later in `getEndpointKind()`. However, the `wwwauth[]` realm check is evaluated *before* that safer heuristic and short-circuits it entirely, so a malicious server can bypass the network-probe check simply by returning `WWW-Authenticate: Basic realm="GitHub"` on the initial authentication challenge.

### Impact Explanation
If exploited, a user cloning/adding an attacker-controlled remote (or going through a malicious/compromised proxy) who is prompted to authenticate can end up entering real credentials or a Personal Access Token into what appears to be (and dispatches as) a "GitHub Enterprise sign-in" flow, but which is configured with `setSignInEndpoint()` pointed at the attacker's own origin. Any username/password/PAT authentication attempted against that endpoint is sent to the attacker, resulting in full account credential/token exfiltration — a direct violation of the "unauthorized OAuth or account binding, credential/token exfiltration" impact category from an untrusted git remote/proxy response.

### Likelihood Explanation
The trigger requires only that a user perform a normal git operation (clone/fetch/push) against an attacker-controlled or MITM'd remote that returns a crafted `WWW-Authenticate: ... realm="GitHub"` response — no local access, no admin rights, and no unnatural steps beyond the credential prompt a user would ordinarily see and complete when connecting to a new git host. This is squarely within the "attacker controls ... a git remote/proxy response" threat model in the task's valid-impact definition.

### Recommendation
Do not trust the `realm="GitHub"` string from `WWW-Authenticate` as sufficient evidence that a host is a genuine GitHub Enterprise instance. At minimum:
- Remove or de-prioritize the `wwwauth[]` realm heuristic in `getEndpointKind()`, relying instead on the network-verified `isGitHubHost()` check (or requiring it as confirmation before returning `'enterprise'`).
- In `promptForGitHubSignIn()`, never point `setSignInEndpoint`/`beginEnterpriseSignIn` at an arbitrary attacker-supplied origin without the user explicitly confirming they intend to add a new GitHub Enterprise account for that host (as is already done through the normal "Add Enterprise Account" UI flow), rather than auto-launching it transparently from a credential-helper callback.

### Proof of Concept
Note: this could not be dynamically executed/verified in this environment (no filesystem/terminal access); the following is derived purely from static code-path analysis and should be validated by a developer with a running build.

1. Attacker stands up an HTTPS git server (or MITM proxy) at `https://evil.example.com/attacker/repo.git`.
2. Server is configured so that, when git attempts to authenticate (e.g., on `git fetch`), it responds with HTTP 401 and header `WWW-Authenticate: Basic realm="GitHub"`.
3. Victim adds this remote in GitHub Desktop and performs a fetch/pull. Git invokes the desktop credential helper (`credential-helper.ts get`), which parses the `wwwauth[...]` field from the credential protocol input.
4. `getEndpointKind()` sees `realm="GitHub"` and returns `'enterprise'` [6](#0-5) .
5. Since the victim has no existing account for `evil.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com')` [2](#0-1) .
6. `promptForGitHubSignIn` sees `hostname !== 'github.com'`, calls `beginEnterpriseSignIn` and `setSignInEndpoint('https://evil.example.com')` [7](#0-6) .
7. The victim, believing they are signing into a legitimate GitHub Enterprise instance related to the repo they just cloned, enters credentials/PAT which are submitted to `evil.example.com`, exfiltrating them to the attacker.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}

/**
 * Attempts to determine whether or not the url belongs to a GitHub host.
 *
 * This is a best-effort attempt and may return `undefined` if encountering
 * an error making the discovery request
 */
export async function isGitHubHost(url: string) {
  const { hostname } = new window.URL(url)

  const endpoint =
    hostname === 'github.com' || hostname === 'api.github.com'
      ? getDotComAPIEndpoint()
      : getEnterpriseAPIURL(url)

  if (isDotCom(endpoint) || isGHE(endpoint)) {
    return true
  }

  if (isKnownThirdPartyHost(hostname)) {
    return false
  }

  // github.example.com,
  if (/(^|\.)(github)\./.test(hostname)) {
    return true
  }

  // bitbucket.example.com, etc
  if (/(^|\.)(bitbucket|gitlab)\./.test(hostname)) {
    return false
  }

  if (getEndpointVersion(endpoint) !== null) {
    return true
  }

  // Add a unique identifier to the URL to make sure our certificate error
  // supression only catches this request
  const metaUrl = `${endpoint}/meta?ghd=${crypto.randomUUID()}`

  const ac = new AbortController()
  const timeoutId = setTimeout(() => ac.abort(), 2000)
  suppressCertificateErrorFor(metaUrl)
  try {
    const response = await fetch(metaUrl, {
      headers: { 'user-agent': getUserAgent() },
      signal: ac.signal,
      credentials: 'omit',
      method: 'HEAD',
      redirect: 'error',
    })

    tryUpdateEndpointVersionFromResponse(endpoint, response)

    return response.headers.has('x-github-request-id')
  } catch (e) {
    log.debug(`isGitHubHost: failed with endpoint ${endpoint}`, e)
    return undefined
  } finally {
    clearTimeout(timeoutId)
    clearCertificateErrorSuppressionFor(metaUrl)
  }
}
