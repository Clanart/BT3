### Title
Unauthenticated OP_RETURN operator-attribution byte range in `create_payout_txhandler` allows anyone to hijack payout credit via a competing SIGHASH_SINGLE|ANYONECANPAY spend - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` places `operator_xonly_pk.serialize()` in an OP_RETURN output that lies outside the coverage of the single required input signature when that signature uses `SIGHASH_SINGLE|ANYONECANPAY` [6](#0-5) . The operator's code does not force a specific sighash type — it verifies whatever `sighash_type` the withdrawing user chose [7](#0-6) . Because attribution is looked up purely by "who spent the withdrawal outpoint in the confirmed chain" rather than by a pre-committed txid, any party who can construct a second, independently fully-signed transaction spending the same withdrawal input (reusing the leaked user signature, which is valid under `SIGHASH_SINGLE|ANYONECANPAY`) can substitute an arbitrary OP_RETURN payload and win the race to have it be the one that gets attributed.

### Finding Description
The broken binding claimed by the question is: `OP_RETURN.operator_xonly_pk (as read by update_finalized_payouts) == kickoff_data.operator_xonly_pk (of the operator who actually fronted the withdrawal)`.

Tracing the path: `Operator::withdraw` builds the payout tx via `create_payout_txhandler`, whose input is the pre-committed `withdrawal_utxo` (owned by the withdrawing user's key) spent with a user-supplied Schnorr signature and *user-chosen* sighash flag [8](#0-7) . If that sighash flag is `SIGHASH_SINGLE|ANYONECANPAY` (the flag documented/expected for this flow, per the error message on line 637 and the proto comment), the signature commits only to input 0's outpoint/sequence and to output 0 (the user payout) — not to the anchor or the OP_RETURN outputs added later in the same builder [9](#0-8) .

Any party who obtains this signature (trivially, once the operator broadcasts the payout tx to the mempool, since witness data is public) can build an entirely new, independently valid transaction that reuses input 0 with the same valid signature, keeps output 0 identical (required by the commitment), and freely chooses their own additional fee input(s) (signed with their own key) and an arbitrary OP_RETURN value. Because Bitcoin only allows one spend of a given outpoint to confirm, this constitutes a legitimate double-spend race, not a signature forgery — no bridge secret is required, matching the "SIGHASH_SINGLE|ANYONECANPAY" composability by design of the sighash flag, but weaponized here because the OP_RETURN carries protocol-critical semantics (payer attribution) that nothing else re-affirms.

Once such a substitute transaction confirms, `update_finalized_payouts` blindly parses the OP_RETURN of *whichever* transaction is found to have spent the recorded withdrawal outpoint in the canonical block and stores it as `payout_payer_operator_xonly_pk`, with no check that this pubkey corresponds to any operator who actually participated in constructing/funding the transaction [10](#0-9) . The attribution lookup itself is outpoint-based, not txid-based, confirmed by `bitcoin_syncer_spent_utxos`/`BlockCache::get_tx_of_utxo`, so whichever transaction wins the confirmation race is unconditionally treated as "the" payout tx [5](#0-4) .

Downstream, `Verifier::is_kickoff_malicious` treats any mismatch between the stored `payout_payer_operator_xonly_pk` and the actual `kickoff_data.operator_xonly_pk` presented by an operator's kickoff as malicious, and treats an unparseable/absent OP_RETURN the same way [11](#0-10) . Consequently, the honest operator that genuinely fronted/broadcast the payout can be permanently blocked from proving they are entitled to reimbursement, because the DB row that `is_kickoff_malicious` and `send_asserts` consult was overwritten by a stranger's chosen bytes [12](#0-11) . No existing guard (`SECP.verify_schnorr`, `is_profitable`, `is_kickoff_malicious`, or a DB uniqueness constraint) checks that the OP_RETURN pubkey corresponds to whoever actually constructed/funded the confirmed transaction — they only check self-consistency between the stored value and the kickoff, which is exactly the value an outsider can already have corrupted before confirmation.

### Impact Explanation
The user's payout output (index 0) is unaffected — funds still reach the withdrawing user at the correct address/amount, since that output is covered by the signature. What is destroyed is the operator-crediting/attribution record: the legitimate fronting operator can be rendered permanently unable to prove their kickoff is non-malicious and thus unable to claim reimbursement (`is_kickoff_malicious` returns `true`), which is the Critical category "an honest operator permanently unable to be reimbursed." Alternatively, if the attacker instead substitutes a *different, legitimately registered* operator's xonly pubkey (rather than garbage bytes), that uninvolved operator's kickoff could pass the `payout_op_xonly_pk == kickoff_data.operator_xonly_pk` check in `send_asserts` and proceed to be reimbursed for a payout it never funded — the Critical category "an operator reimbursed for a payout it never funded." This is repeatable for every withdrawal/payout tx that is broadcast with a permissive sighash flag, across any deposit and any operator.

### Likelihood Explanation
The precondition is that the payout tx's sole required signature uses `SIGHASH_SINGLE|ANYONECANPAY` (which the code's own error message explicitly expects/instructs users to use, and which `Operator::withdraw` does not reject in favor of `SIGHASH_ALL`) [13](#0-12) . Given that, the attacker only needs to observe the broadcast tx in the mempool (or, if the attacker is the withdrawing user themselves, they already hold the signature), construct their own transaction with their own fee-paying input, and win a normal fee-based mempool/RBF race — no key compromise, no majority hashrate, and no bridge-specific secret is required. This is fully reproducible on regtest.

### Recommendation
Bind the OP_RETURN operator identity to the same signature that authorizes the spend: either require the withdrawal input signature to use `SIGHASH_ALL` (or `SIGHASH_ALL|ANYONECANPAY`, which still commits to `hashOutputs`) so the OP_RETURN and anchor outputs are covered, or otherwise commit the operator pubkey/attribution into a value that the user's signature covers (e.g., include the operator's pubkey hash in the sighash-committed output 0's script or an explicit annex commitment validated by the verifier), so no output outside the signature's protection can be substituted by any third party.

### Proof of Concept
`cargo test` (regtest, no mainnet/live Citrea) plan:
1. Set up a deposit and withdrawal via the existing e2e harness (as in `core/src/test/deposit_and_withdraw_e2e.rs`) so that a legitimate `Operator::withdraw` payout tx is broadcast, capturing its raw bytes and the witness signature/sighash type for input 0.
2. Assert `in_signature.sighash_type == SIGHASH_SINGLE|ANYONECANPAY` and that output 2 (OP_RETURN) is not covered by `sighash` per `calculate_sighash_txin(0, sighash_type)`.
3. Construct a second transaction reusing input 0 (same outpoint, same witness signature) and output 0 unchanged, but with a fresh, attacker-funded fee input (signed by a locally-generated test key) and a mutated OP_RETURN containing an attacker-chosen 32-byte value.
4. Submit the attacker transaction via `sendrawtransaction` before the legitimate one confirms (e.g. with a higher fee), and assert Bitcoin Core accepts it into the mempool/mines it (`testmempoolaccept`/`generatetoaddress`).
5. Run the block-sync path (`handle_finalized_block` → `update_finalized_payouts`) and assert `payout_payer_operator_xonly_pk` in the `withdrawals` table now equals the attacker-chosen value, not the honest operator's `signer.xonly_public_key`.
6. Call `is_kickoff_malicious` (or trigger the honest operator's kickoff flow) and assert it now returns `true`/errors for the honest operator despite them having legitimately relayed the payout, proving the mis-attribution and reimbursement denial.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
