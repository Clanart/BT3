### Title
GET request can be both fulfilled and timed-out, double-invoking the app's settlement callback - (File: `evm/src/core/EvmHost.sol`, `evm/src/core/HandlerV2.sol`)

### Summary
`dispatchIncoming(GetResponse,...)` pays the relayer fee out of `_requestCommitments[commitment]` on a successful `onGetResponse` callback but never deletes that commitment. `handleGetRequestTimeouts` only rejects a timeout claim if `_requestCommitments[commitment]` is empty. Because the commitment is left intact after a successful response, the same GET request commitment can later be submitted through the timeout path, causing `onGetTimeout` to also fire on the source app for a request that already received `onGetResponse`.

### Finding Description
On a successful response: `_requestCommitments[commitment]` is read but never cleared. [3](#0-2) 

`handleGetRequestTimeouts`'s only "known request" guard is that `meta.sender != address(0)` in `_requestCommitments`, which stays true forever after a successful response. [4](#0-3) 

The only other defense is a non-membership proof that the destination's `_responseReceipts[commitment]` slot is empty **at the specific historical height chosen for the proof**. Since state commitments are stored per-height and never pruned, an attacker (permissionless caller) can pick any already-verified destination height whose `state.timestamp >= request.timeout()` but which predates the block where the response was actually recorded on the destination. At that earlier height the response-receipt slot is genuinely empty, so the non-membership proof is valid, even though the response was later delivered and processed on the source chain. [5](#0-4) 

This mirrors the report's core defect class exactly: a storage location (`_requestCommitments[commitment]`) is left holding stale data after the value it protects is no longer relevant, because the code path that consumes/settles it fails to write (clear) it — the same "write/no-write discipline" bug, just manifesting as a missing invalidation rather than a redundant write. The Rust ISMP timeout handler for the same case explicitly documents the analogous pattern and its danger, confirming this is a load-bearing invariant elsewhere in the codebase: the commitment must be deleted (or otherwise invalidated) as soon as one terminal outcome (accept or timeout) has occurred, precisely to block this class of double-processing. [6](#0-5) 

### Impact Explanation
Any `IApp` module that implements both `onGetResponse` and `onGetTimeout` with mutually exclusive settlement logic (e.g., an intents/escrow app that releases funds to a beneficiary on `onGetResponse` and refunds the payer on `onGetTimeout`) can be forced to execute both, causing double-settlement / duplicate execution of privileged application logic from a single GET dispatch. This is unauthorized execution and potential loss/duplication of funds at the app layer, triggered purely by a permissionless call to `handleGetRequestTimeouts` with a proof constructed from already-public, already-verified chain state — no malicious relayer, prover, or admin required.

### Likelihood Explanation
`handleGetRequestTimeouts` is explicitly documented as permissionless. The attacker needs only (a) a `GetResponse` that was already delivered/processed, and (b) any previously-stored destination state commitment whose timestamp is past the request's timeout but whose block predates the response's inclusion — a condition that can occur naturally whenever state commitments and response delivery race, and can be engineered by simply waiting for/selecting an appropriate historical height that Hyperbridge already committed. No privileged role or protocol-level compromise is needed, only standard construction of a state-trie non-membership proof against a real, already-accepted state commitment.

### Recommendation
In `dispatchIncoming(GetResponse,...)`, delete `_requestCommitments[commitment]` (mirroring what `dispatchTimeOut` does) once the response has been successfully dispatched and the fee paid, so `handleGetRequestTimeouts`'s `UnknownMessage` check correctly rejects any later timeout claim for an already-settled GET request — matching the invariant already enforced (and documented) in the Rust `timeout.rs` handler.

### Proof of Concept
1. App `A` on chain `S` dispatches a `GetRequest` with `timeout_timestamp = T`.
2. Destination processes the request; at destination block height `H_late` (with `H_late.timestamp` slightly `< T` or shortly after) the response is committed into `_responseReceipts`.
3. A relayer submits `handleGetResponses` on `S` using a state commitment at height `H_late`; `dispatchIncoming(GetResponse)` calls `A.onGetResponse(...)` (e.g., releases escrow), pays the relayer fee, and **does not delete `_requestCommitments[commitment]`**.
4. Later, `state.timestamp` for some earlier already-verified height `H_early < H_late` (with `H_early.timestamp >= T`, i.e., already "timed out" by that snapshot) is used, and at `H_early` the response-receipts slot for `commitment` is still empty (because it was written at `H_late > H_early`).
5. Attacker calls `handleGetRequestTimeouts` with height `H_early` and a valid non-membership proof; `meta.sender != address(0)` still holds (never cleared), so the check passes and `host.dispatchTimeOut(GetRequestTimeout(...))` is invoked, calling `A.onGetTimeout(...)` (e.g., refunds the same escrow) — a second, conflicting settlement on the same request.     /**
     * @dev Dispatch an incoming GET response to source module
     * @param response - get response

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
