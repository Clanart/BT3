### Title
Explicit zero-fee governance overrides for a destination chain are silently discarded and replaced with the global default `protocolFeeBps` - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` resolves the protocol fee for an order by reading `_destinationProtocolFees[destinationHash]` and, if that value is `0`, falling back to the global default `_params.protocolFeeBps`. Because Solidity mappings return `0` both for "never configured" and for "governance explicitly configured this destination to `0` fee," the contract cannot distinguish an intentional fee waiver from an unset entry. This is the same broken invariant as the `SecondSwap_VestingManager.setSellable` bug: a deliberate zero value is silently reinterpreted as "not initialized" and replaced with a non-zero default, overriding the explicit intent of governance.

### Finding Description
`_updateParams` in `evm/src/apps/intentsv2/IntentsBase.sol` allows Hyperbridge governance to set a per-destination protocol fee override, including explicitly setting it to `0` bps to waive fees for a given destination chain: [1](#0-0) 

Nothing in this write path records "this destination has been configured," it only writes `feeBps` (which can legitimately be `0`) into the mapping. Later, `placeOrder` reads that same mapping and treats a stored `0` as equivalent to "no override configured," falling back to the global default fee: [2](#0-1) 

The same pattern exists in the Tron fork of the contract: [3](#0-2) 

This mirrors exactly the reported `maxSellPercent` bug class: a value of `0` is overloaded to mean both "uninitialized/default" and "explicitly set to zero by the privileged configurer," and the read path always collapses the latter into the former.

### Impact Explanation
Once governance sets `_destinationProtocolFees[destinationHash] = 0` for a given destination chain (e.g., to run a promotional zero-fee route, or because that route was intentionally exempted from protocol fees), every subsequent `placeOrder` call to that destination silently reverts to charging `_params.protocolFeeBps` instead of `0`. The protocol fee is deducted directly from the user's escrowed input tokens: [4](#0-3) 

and the deducted amount is emitted as `DustCollected`, eventually swept to a beneficiary via `_sweepDust` (in `IntentsBase.sol`). This results in users being charged a fee that governance explicitly disabled for that destination — an unauthorized transaction manipulation and loss of user funds without any authorization for the outcome, fully consistent with the required "stealing or loss of funds" / "transaction manipulation" impact categories. No malicious peer, relayer, or governance actor is needed — the bug is triggered purely by the intersection of a completely legitimate governance action (waiving a fee) and the normal, unprivileged `placeOrder` entrypoint.

### Likelihood Explanation
This requires no attacker at all — it is a systemic logic defect that fires automatically the first time governance uses the zero-fee-waiver feature that the `_updateParams`/`DestinationFeeOverride` mechanism explicitly supports (the code allows `feeBps == 0` with no special casing to reject it or distinguish it). Since destination-specific fee waivers are a normal governance operation intended to be supported (the mapping accepts any `feeBps < 10_000`, including `0`), this is a "guaranteed to trigger" class of bug the moment the feature is used, not an edge-case attacker scenario.

### Recommendation
Add an explicit "configured" flag per destination (e.g., `mapping(bytes32 => bool) hasDestinationFeeOverride`, or store `feeBps + 1` internally, or use a sentinel value like `type(uint256).max` for "no override") so that `placeOrder` can distinguish "never configured, use global default" from "explicitly configured to 0." Only fall back to `_params.protocolFeeBps` when the destination truly has no override recorded.

### Proof of Concept
1. Governance calls `_updateParams` with `destinationFees = [{chain: <destB>, destinationFeeBps: 0}]` to waive protocol fees for `destB`, intending users routing to `destB` to pay no protocol fee. This sets `_destinationProtocolFees[keccak256(destB)] = 0`.
2. A user calls `placeOrder(order, graffiti)` with `order.destination = destB`.
3. In `placeOrder`:
   - `protocolFeeBps = _destinationProtocolFees[keccak256(destB)]` reads `0`.
   - Because `protocolFeeBps == 0`, the code executes `protocolFeeBps = _params.protocolFeeBps;`, silently substituting the global default fee (e.g., 30 bps) instead of respecting governance's explicit `0`.
4. The user's escrowed input is reduced by `originalAmount * _params.protocolFeeBps / 10_000`, and a `DustCollected` event fires for a fee the user was told/promised would be `0`, extracting funds from the user that governance had explicitly waived. [5](#0-4)
