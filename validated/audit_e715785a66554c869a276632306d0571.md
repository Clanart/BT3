### Title
Unverified PedPoP ciphertexts can trigger premature ECDH blame proof disclosure - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts an untrusted `EncryptedMessage`, deserializes its plaintext share, and may return the sender’s ECDH blame proof before the message’s proof-of-possession has actually been verified. This matches the reported bug class: a protection/validation scope ends before the protected object is safely used.

### Finding Description
`EncryptedMessage::read` accepts the ephemeral ECDH public key, Schnorr proof-of-possession, and encrypted payload from untrusted bytes. [1](#0-0)  `Encryption::decrypt` only queues the proof-of-possession into a `BatchVerifier`; it then immediately performs ECDH, decrypts the payload, and constructs an `EncryptionKeyProof` revealing the shared ECDH point. [2](#0-1) 

`KeyMachine::calculate_share` then calls `C::F::from_repr` on that decrypted plaintext before the queued proof-of-possession is verified. If the plaintext is non-canonical, it returns `PedPoPError::InvalidShare` with `blame: Some(blame)`, exposing the ECDH proof immediately. [3](#0-2)  The deferred batch verification that would reject the forged proof-of-possession only happens afterward. [4](#0-3) 

The protocol explicitly recognizes why this ordering is unsafe: without proof-of-possession enforcement, an observer can reuse Alice’s ephemeral key, cause Bob to reveal `bX`, and thereby decrypt Alice’s original message to Bob. [5](#0-4) 

### Impact Explanation
An unprivileged participant or observer can copy the ephemeral public key from another participant’s encrypted share and submit forged ciphertexts under that key. For fields such as Ristretto/ed25519-order scalars, random 32-byte plaintext has a substantial probability of being non-canonical. Once one forged ciphertext decrypts to a non-canonical scalar, `calculate_share` returns the ECDH proof before discovering that the proof-of-possession was invalid.

That proof contains the shared ECDH point used by `cipher`, allowing the attacker to derive the ChaCha20 keystream and decrypt the previously observed legitimate `EncryptedMessage` using the copied ephemeral key. This leaks another participant’s PedPoP secret-share value, a concrete secret/key-material disclosure.

### Likelihood Explanation
Likelihood is moderate to high where the PedPoP field’s canonical scalar range is meaningfully smaller than its fixed-width encoding, such as Ristretto. Each forged ciphertext acts as a decryption attempt; when the result is non-canonical, the early error path leaks the proof. The attack only requires observed protocol bytes and the ability to submit an untrusted encrypted share, both public-input paths contemplated by the API.

On fields whose order is extremely close to `2^256`, randomly obtaining a non-canonical scalar is negligible, so the practical reachability depends on the deployed ciphersuite. The ordering bug itself is unconditional.

### Recommendation
Do not create, return, or publish an `EncryptionKeyProof` until after the message proof-of-possession has been verified. In particular:

- Queue all message proof-of-possession statements first.
- Run `batch.verify_with_vartime_blame()` before deriving or returning blame proofs for decrypted plaintext.
- Alternatively, make `Encryption::decrypt` synchronously verify `msg.pop` before ECDH decryption.
- Treat non-canonical plaintext from a message with an unverified/invalid PoP as a signature/authentication failure with `blame: None`, not as a share fault with an ECDH disclosure.
- Avoid adding decrypted bytes to `self.secret` until all authentication and share-verification statements have succeeded.

### Proof of Concept
Conceptual exploit against the Ristretto PedPoP flow:

1. Alice sends Bob a valid `EncryptedMessage<Ristretto, SecretShare<_>>` with ephemeral key `X`, PoP `pop_A`, and ciphertext `C_A`.
2. Eve observes that serialized message and extracts `X`.
3. Eve serializes a forged message:
   - `key = X`
   - `pop = arbitrary invalid SchnorrSignature`
   - `msg = random ciphertext`
4. Eve submits that message to Bob through `EncryptedMessage::read` and `KeyMachine::calculate_share`.
5. Bob queues PoP verification but decrypts immediately, producing random plaintext. On Ristretto-order fields, approximately 1/16 of uniformly random 32-byte encodings are non-canonical.
6. When the plaintext is non-canonical, `calculate_share` returns `InvalidShare { blame: Some(proof) }` before calling batch verification.
7. Eve uses `proof.key` as the ECDH point for `cipher(context, &proof.key)`, derives the keystream, and decrypts Alice’s original `C_A`, recovering Alice’s PedPoP secret-share bytes.

The decisive bug is the ordering in `calculate_share`: plaintext deserialization and the `Some(blame)` return occur at lines 477–482, while proof-of-possession verification is deferred to lines 493–499. [6](#0-5)
