### Title
Materially underpriced compute in CPI instruction/account-meta translation cost calculation due to integer-division rounding to zero - (File: program-runtime/src/cpi.rs)

### Summary
Both `translate_instruction_rust` and `translate_instruction_c` in `program-runtime/src/cpi.rs` compute the compute-unit cost of translating cross-program-invocation (CPI) instruction data and account metas by dividing the byte length by `cpi_bytes_per_unit` with no minimum-charge floor, unlike the analogous pattern used elsewhere in the syscall cost model.

### Finding Description
The analog report describes a defi vault that computes `tokenAmount = shares * pricePerShare / totalShares`-style pull amount using integer division; when the amount rounds to zero, no tokens are pulled but shares are still minted, letting an attacker accumulate value for free across repeated small operations.

The structurally equivalent pattern in agave is compute-unit charging via integer division that can legitimately round down to zero, effectively giving the operation for free. In `translate_instruction_rust`:

```
let mut total_cu_translation_cost: u64 = (data.len() as u64)
    .checked_div(invoke_context.get_execution_cost().cpi_bytes_per_unit)
    .unwrap_or(u64::MAX);
``` [1](#0-0) 

and the account-meta cost:
```
let account_meta_translation_cost =
    (account_metas.len().saturating_mul(size_of::<AccountMeta>()) as u64)
        .checked_div(invoke_context.get_execution_cost().cpi_bytes_per_unit)
        .unwrap_or(u64::MAX);
``` [2](#0-1) 

The identical pattern (with the same missing floor) also exists in `translate_instruction_c`: [3](#0-2) 

If `data.len()` (CPI instruction data) and `account_metas.len() * size_of::<AccountMeta>()` are both smaller than `cpi_bytes_per_unit`, both divisions round to `0`, and `total_cu_translation_cost` becomes `0`. Compare this to every other cost-charging site that performs the same style of byte-cost division elsewhere in the syscall/runtime code, which uses an explicit `.max(mem_op_base_cost)` (or equivalent) floor to guarantee a non-zero minimum charge for any operation performed, e.g.:
- `mem_op_consume` in `syscalls/src/mem_ops.rs`: `compute_cost.mem_op_base_cost.max(n.checked_div(...).unwrap_or(u64::MAX))` [4](#0-3) 
- `SyscallHash` per-value cost: `mem_op_base_cost.max(hash_byte_cost.saturating_mul(...))` [5](#0-4) 
- `SyscallGetSysvar`/sysvar fetch cost: `std::cmp::max(sysvar_buf_cost, mem_op_base_cost)` [6](#0-5) 

`translate_instruction_rust`/`translate_instruction_c` do not apply any such floor, so a CPI carrying small instruction data and few account metas is translated (VM memory reads, bounds checks, pubkey/bool validation, `Vec` allocation and copies) essentially for a charge of `0` compute units for that portion of the operation, in contrast to the established convention elsewhere in the same cost model.

### Impact Explanation
This is a compute-cost underpricing bug in the CPI path: a program can issue a very large number of CPIs with small instruction payloads (few bytes of data, few or zero account metas) and pay effectively nothing (0 CUs) for the per-CPI translation work that this code performs (memory-mapping translation, bounds checks, per-account-meta unsafe pointer reads, allocation). Since CPI is a common hot path and this cost line item is one of several charged per invoke (there are additional costs elsewhere, e.g. in `cpi_common`), the practical severity is that this specific charge can be zeroed out, which is a genuine instance of "materially underpriced compute" for the translation step, analogous to the report's rounding-to-zero cost bypass, though it does not directly enable unbounded free execution since other CPI-related costs (instruction cost accounting, base CPI cost, called program's own compute-unit charges) are charged separately.

### Likelihood Explanation
`cpi_bytes_per_unit` is a fixed protocol constant (not attacker-controlled) and CPI instruction data/account-meta sizes are fully attacker-controlled by any unprivileged BPF program performing CPI. Triggering the zero-cost condition only requires crafting a CPI with instruction data and account-meta byte length both under the `cpi_bytes_per_unit` threshold, which is trivial and requires no special privileges — any on-chain program can call `invoke`/`invoke_signed` with minimal instruction payloads.

### Recommendation
Apply a minimum-charge floor (e.g., `.max(mem_op_base_cost)`, mirroring the convention used in `mem_op_consume`, `SyscallHash`, and `SyscallGetSysvar`) to the `total_cu_translation_cost` computation in both `translate_instruction_rust` and `translate_instruction_c`, so translation work with small payloads is never charged `0` compute units.

### Proof of Concept
Conceptual PoC (cannot be executed in this environment):
1. Deploy a BPF program that repeatedly performs `invoke()` CPIs to a no-op target program, using an instruction with `data.len()` and `accounts.len() * size_of::<AccountMeta>()` both smaller than the current `cpi_bytes_per_unit` value (see `execution_budget.rs` for the constant value).
2. Instrument/observe the compute meter before and after `translate_instruction_rust` executes for such a call — per the code at lines 560-568 of `program-runtime/src/cpi.rs`, `total_cu_translation_cost` evaluates to `0` for both terms, so `invoke_context.compute_meter.consume_checked(0)` is called, i.e., no CUs are charged for the translation step regardless of how many such CPIs are issued.
3. Compare against `mem_op_consume` (syscalls/src/mem_ops.rs) or `SyscallGetSysvar` (syscalls/src/sysvar.rs), which apply an explicit minimum floor and never reach a zero charge for equivalent small-input operations — confirming the inconsistency/bug in the CPI translation cost path.
