### Title
Attacker can flood Serai's Bitcoin vault with economically-unspendable dust outputs, permanently growing the tracked-input set and DoS-ing fee-solvent spends - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the Tunnl report — where anyone can create unbounded zero-value offers that accumulate in `s_offersToUpkeep` and stall upkeep — anyone can send unbounded numbers of minimum-relayable P2TR outputs to Serai's Bitcoin deposit address. `Scanner::scan_transaction` matches purely on `script_pubkey` and returns every matching output with no value check, and `SignableTransaction::new` in `send.rs` applies the `DUST` check only to outgoing *payments*, never to whether an *input* is worth more than the fee required to spend it. The result is a permanently growing set of reported-received outputs that cost more to spend than they are worth.

### Finding Description
`Scanner::scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for every output whose `script_pubkey` is in `self.scripts` — there is no amount filter at all in the in-scope wallet code (networks/bitcoin/src/wallet/mod.rs:199-214).

On the spending side, `SignableTransaction::new` enforces `DUST = 546` only against `payments` (send.rs:165-169), sums all inputs blindly (send.rs:175), and only fails with `NotEnoughFunds` if the *aggregate* input value can't cover payments + fee (send.rs:215-221). A P2TR key-path input adds ~57.5 vbytes to a transaction (fixed-size `TxIn` + 64-byte witness, per `calculate_weight_vbytes` at send.rs:71-82). At a fee rate of ~10 sat/vB, spending one input costs ~575 sats — more than the 546-sat minimum output value an attacker can create. There is no per-input viability check, and no bound on the number of inputs a `SignableTransaction` may carry other than `MAX_STANDARD_TX_WEIGHT` (send.rs:241).

So an attacker broadcasts transactions paying, e.g., 546-600 sat outputs to `p2tr_script_buf(key)` (the external deposit script). Each one is returned by `scan_transaction` as a legitimate `ReceivedOutput`, tracked forever, and must eventually be merged/spent — at a net loss, or never, since spending it costs more than it yields. This mirrors the report: cheap, non-beneficial-to-anyone "offers" (here, dust deposits) accumulate in the tracked set and degrade/DoS the queue that must process them.

### Impact Explanation
- Funds are reported received (via `ScannerEvent` / `ReceivedOutput`) yet are not economically spendable — spending a 546-600 sat input at normal fee rates burns more in fees than the input contributes, and `SignableTransaction` provides no mechanism to refuse or skip such inputs.
- The tracked input set grows unboundedly at attacker cost of only the dust amount per output; the aggregation/merge burden (and its transaction fees) falls on Serai.
- Analogous medium-severity DoS: no direct profit to the attacker, but protocol throughput and solvency for processing outputs are degraded. Severity: **Medium**.

### Likelihood Explanation
Any unprivileged Bitcoin user can do this with standard transactions — no validator status, collusion, or leaked material needed. Cost is linear (546+ sats per output, partially recoverable since the attacker loses only the fee if outputs are never spent — actually fully lost to them, which limits sustained attack, consistent with the original report's "medium, no direct economic benefit" assessment). During fee spikes, even substantially larger "spam" outputs become net-negative to spend.

### Recommendation
- In `scan_transaction`/`ReceivedOutput` handling, ignore outputs below a *spend-viability* threshold computed as `DUST` + the marginal fee to spend one input (≈ `fee_per_vbyte * ~58` vB), not merely the relay dust limit.
- In `SignableTransaction::new`, drop or refuse inputs whose `value` is less than their marginal spend cost, so the aggregate `NotEnoughFunds` check isn't poisoned by unprofitable inputs.
- Cap/limit total pending inputs tracked per key and charge received-output handling costs against the minted amount, as the spec itself contemplates (spec/processor/UTXO Management.md:143-155).

```rust
// At fee_per_vbyte >= ~10, each input costs more to spend than it contributes:

```

Root cause locations: unfiltered output acceptance in `Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214), and the absence of a per-input economic check in `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-243, `DUST` enforced only on payments at send.rs:32,165-169).
