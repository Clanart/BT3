### Title
Unsafe UTF-8 construction from attacker-controlled cross-chain payload can produce a corrupted `String` and crash the node — `pallet-ismp-demo::on_accept` (Gargantua runtime) - (File: modules/pallets/demo/src/lib.rs)

### Summary
`IsmpModuleCallback::on_accept` in `pallet-ismp-demo` builds an event field from an incoming ISMP `PostRequest.body` using `String::from_utf8_unchecked`, without validating that the bytes are valid UTF-8. `PostRequest.body` for `StateMachine::Evm(_)` sources is fully attacker-controlled (any contract on any registered EVM source chain can dispatch a `PostRequest` targeting this module with arbitrary bytes), and the resulting value is a `String` that does not actually satisfy Rust's UTF-8 validity invariant — the exact same class of "trust an unchecked conversion of externally supplied bytes" bug the seed report flags for `MustAccAddressFromBech32`.

### Finding Description
`pallet-ismp-demo` is wired into the live Gargantua runtime's ISMP router (`parachain/runtimes/gargantua/src/ismp.rs`), where `ProxyModule::on_accept` dispatches any incoming `PostRequest` addressed to `pallet_ismp_demo::PALLET_ID` straight to `IsmpModuleCallback::<Runtime>::default().on_accept(request)`: [1](#0-0) 

Inside that handler, for any EVM-sourced request the body is converted to a `String` with an `unsafe` unchecked call: [2](#0-1) 

`String::from_utf8_unchecked` skips UTF-8 validation entirely; its safety contract requires the caller to *guarantee* the input is valid UTF-8. `request.body` here comes straight from an ISMP `PostRequest` dispatched by an arbitrary contract on any EVM state machine that Hyperbridge/Gargantua accepts requests from — nothing about the ISMP request path (module resolution via `ModuleId::from_bytes(&request.to)`, bandwidth gate, receipt/duplicate checks in `modules/ismp/core/src/handlers/request.rs`) validates or restricts the byte content of the body. An attacker only needs to dispatch a `PostRequest` with `to == ismp-ast` module id and a non-UTF-8 body from any EVM chain; the message is delivered through the normal, permissionless relayer flow with a perfectly valid consensus/membership proof — no malicious relayer, prover, or admin is required.

This produces a `String` instance whose backing bytes are not valid UTF-8, violating Rust's core invariant for `String`/`str`. This is undefined behavior at the language level: any subsequent safe code that treats this value as a `str` (e.g. `.chars()`, `.len()` combined with slicing at a byte boundary, string comparison optimizations, or even the standard library's own internal assumptions) can panic, produce corrupted state, or in the worst case be exploited by the compiler's UB-based optimizations. Because this event field is stored in a pallet event via `deposit_event` and encoded/decoded across `frame_system` event storage, RPC subscriptions, and various tooling that treats `Event::Request.data: String` as legitimate UTF-8, a downstream panic on a corrupted `String` inside consensus-critical execution (event deposit/finalization) is a very plausible route to a runtime panic that halts block production — structurally identical to the seed bug where an unchecked/panicking conversion of externally supplied data is reached from live message-processing code.

### Impact Explanation
If any downstream consumption of the `Event::Request { data, .. }` field (event decoding for RPC, indexers reading the raw String and calling `.chars()`/`.split()`, or any future safe-Rust code path touching this field in-runtime) triggers on invalid UTF-8 content, it produces either a runtime panic (halting the parachain, matching the seed report's "Chain Halt" impact) or memory-safety UB depending on how the compiler exploits the invariant violation. This falls squarely within the bounty's "unauthorized execution / logic attack" and false-invariant categories: an unprivileged sender on any connected EVM chain can force a Substrate `String` to hold non-UTF-8 bytes purely through the normal, permissionless ISMP delivery path.

### Likelihood Explanation
High likelihood of reachability: `pallet-ismp-demo` is registered as a first-class module in the Gargantua runtime's production `ProxyModule::on_accept` dispatch table, reachable by any `PostRequest` with a matching module id and an EVM source, requiring no special relayer or admin privilege — only a normal consensus/membership proof, which any dispatching application legitimately obtains. The only open question is exactly how far downstream the corrupted `String` is consumed before a panic is triggered (event codec paths for `String` typically just serialize length + raw bytes without re-validating UTF-8, so the immediate `deposit_event` call itself may not panic) — this is the main uncertainty, since I could not trace every consumer of `frame_system::Event` string fields (RPC subscription serializers, indexer clients) in this pass.

### Recommendation
Replace `String::from_utf8_unchecked(request.body)` with a checked conversion, e.g. `String::from_utf8_lossy(&request.body).into_owned()` or `String::from_utf8(request.body).map_err(|_| IsmpError::Custom("invalid utf8 in request body".into()))?`, so a malformed payload is rejected or safely lossy-converted instead of producing a `String` that violates Rust's UTF-8 invariant.

### Proof of Concept
1. On a registered EVM source chain, have any contract dispatch an ISMP `PostRequest` with `to = ModuleId::Pallet(PalletId(*b"ismp-ast")).to_bytes()` (the demo pallet's module id) and `body` containing an invalid UTF-8 byte sequence, e.g. `vec![0xFF, 0xFE, 0xFD]`.
2. Deliver the request to Gargantua through the standard relayer flow with a valid consensus/membership proof (no relayer collusion needed — the proof is genuine, only the payload content is malicious).
3. `ProxyModule::on_accept` (`parachain/runtimes/gargantua/src/ismp.rs:406-418`) routes to `pallet_ismp_demo::IsmpModuleCallback::on_accept`, which executes `String::from_utf8_unchecked(request.body)` on the malformed bytes (`modules/pallets/demo/src/lib.rs:375`), producing a `String` that does not hold valid UTF-8 — an invariant violation that downstream consumers of the deposited event are not expected to handle safely.

impl<T: Config> IsmpModule for IsmpModuleCallback<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		let source_chain = request.source;

		match source_chain {
			StateMachine::Evm(_) => Pallet::<T>::deposit_event(Event::Request {
				source: source_chain,
				data: unsafe { String::from_utf8_unchecked(request.body) },
			}),
			StateMachine::Polkadot(_) | StateMachine::Kusama(_) => {
				let payload =
					<Payload<T::AccountId, <T as Config>::Balance> as codec::Decode>::decode(
						&mut &*request.body,
					)
					.map_err(|_| IsmpError::Custom("Failed to decode request data".to_string()))?;
				<T::NativeCurrency as Mutate<T::AccountId>>::mint_into(
					&payload.to,
					payload.amount.into(),
				)
				.map_err(|_| IsmpError::Custom("Failed to mint funds".to_string()))?;
				Pallet::<T>::deposit_event(Event::<T>::BalanceReceived {
					from: payload.from,
					to: payload.to,
					amount: payload.amount,
					source_chain,
				});
			},
			source => Err(IsmpError::Custom(format!("Unsupported source {source:?}")))?,
		}

		Ok(weight())
	}
