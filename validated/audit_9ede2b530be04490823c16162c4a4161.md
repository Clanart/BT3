### Title
Reachable panic in PedPoP blame evaluation via unvalidated participant indexes - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The Dire Wolf report describes a reachable assertion: an attacker-controlled field (empty MIC-E comment) trips an `assert` that terminates the process. The Serai analog is in PedPoP's blame evaluation: `BlameMachine::blame_internal` indexes `self.commitments[&sender]` and `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with `Participant` values that are never validated against the protocol's `1..=n` range. Any blame request naming a participant index that wasn't registered causes a `HashMap` indexing panic. The in-tree consumer, `processor/src/key_gen.rs` `CoordinatorMessage::VerifyBlame`, passes `accuser`/`accused` straight from the network message into `blame(...)` with no bounds check.

### Finding Description
`AdditionalBlameMachine::new` only registers encryption keys and commitments for participants `1 ..= n`: [1](#0-0) 

`blame` then calls `blame_internal`, which calls `decrypt_with_proof`, which performs `self.enc_keys[&decryptor]` — a `HashMap` index that panics on a missing key: [2](#0-1) 

and, if the PoP signature and proof happen to pass or the code path is reached, `blame_internal` likewise does `self.commitments[&sender]`: [3](#0-2) 

`Participant::new` only enforces non-zero, so any index in `1..=u16::MAX` is representable, but only `1..=n` were inserted. In `processor/src/key_gen.rs`, the `VerifyBlame` handler builds `AdditionalBlameMachine::new(context, params.n(), commitment_msgs)` and calls `.blame(accuser, accused, share, blame)` with `accuser`/`accused` taken verbatim from the coordinator/processor message: [4](#0-3) 

So a remote participant can send a blame request with `accuser` (or `accused`) set to a valid nonzero `Participant` outside `1..=n` (e.g., `Participant(0xffff)`), and the victim node panics inside `decrypt_with_proof`/`blame_internal` on the missing `HashMap` entry.

### Impact Explanation
A single attacker-supplied message deterministically panics the validator/processor task handling blame verification. In deployments where a task panic aborts the process (the codebase's own relayer installs a panic hook that calls `std::process::exit(1)`), this is an unauthenticated remote denial of service against a DKG node — the same severity class as the referenced assertion-failure DoS. Repeated crashes during a key-generation session can stall or prevent multisig establishment.

### Likelihood Explanation
The trigger is a single malformed message; it requires no valid proof, no threshold collusion, and no signature — only a `Participant` index outside the registered set. `blame`/`blame_internal` perform no membership check on `sender`/`recipient` before indexing (`decrypt_with_proof` does verify `msg.pop` first, but the `self.enc_keys[&decryptor]` lookup in the DLEq verify arguments is evaluated *before* `dleq.verify` can fail, so an out-of-range `decryptor`/`recipient` panics unconditionally). Caveat: I verified the panic paths inside `crypto/dkg/pedpop`, but could not fully trace upstream message validation in `processor`/coordinator to confirm no earlier guard rejects out-of-range `accuser`/`accused` values; the `VerifyBlame` handler shown performs none.

### Recommendation
In `crypto/dkg/pedpop/src/lib.rs`, `blame_internal` should validate `sender` and `recipient` (e.g., `self.commitments.get(&sender)` / `self.encryption.enc_keys.get(&decryptor)`) and return an error/verdict instead of indexing. Callers passing externally supplied `Participant` values should reject indexes `> params.n()` before invoking `blame`.

### Proof of Concept
```rust
// Setup: AdditionalBlameMachine::new(context, n, msgs) with participants 1..=n.
// Attacker-controlled blame request:
let attacker_chosen_recipient = Participant::new(u16::MAX).unwrap(); // nonzero, valid type, > n
// Any sender message/proof; decrypt_with_proof evaluates:
//   self.enc_keys[&decryptor]
// as an argument to dleq.verify before any check rejects it -> HashMap index panic.
machine.blame(sender, attacker_chosen_recipient, msg, Some(proof)); // panic: index not found
```
The same applies to `self.commitments[&sender]` in `blame_internal` for an out-of-range `sender` once the PoP signature verifies.
