### Title
Cross-domain signature replay between `withdraw_fees` and `accumulate_fees` beneficiary redirection due to identical signed payloads and shared nonce - ([File: modules/pallets/relayer/src/withdrawal.rs], [File: modules/pallets/relayer/src/accumulate.rs])

### Summary
`pallet-relayer` has two independent signed actions that both authorize where a relayer's accrued fees end up: `withdraw()` (a relayer withdrawing fees to itself or a designated beneficiary) and `accumulate()`'s beneficiary-redirect path (a relayer proving delivery and redirecting the freshly accumulated fee to a beneficiary). Both build their signed message by hashing `(nonce, state_machine, beneficiary_bytes)` and both consume the exact same `Nonce<T>` counter keyed by `(address, state_machine)`. Because the SCALE encodings of `Vec<u8>` and `&[u8]` are identical, the two message-construction functions produce byte-for-byte identical hashes for the same `(nonce, chain, beneficiary)` tuple. A signature the relayer produced to authorize one action is therefore also a valid signature for the other action — exactly the same bug class as the reported `CommunityRound.reserve()` issue, where a signed authorization intended for one specific use could be reused/replayed for an unintended state mutation.

### Finding Description
`withdrawal.rs::message()` computes:
```rust
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
    if let Some(beneficiary) = beneficiary {
        return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
    }
    sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
``` [1](#0-0) 

`accumulate.rs::beneficiary_message()` computes:
```rust
pub fn beneficiary_message(nonce: u64, state_machine: StateMachine, beneficiary: &[u8]) -> [u8; 32] {
    sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
}
``` [2](#0-1) 

Both functions concatenate the SCALE encoding of `nonce`, `StateMachine`, and the beneficiary byte sequence in the same order; `Vec<u8>` and `&[u8]` encode identically. So `message(n, chain, Some(b)) == beneficiary_message(n, chain, &b)` for identical inputs — there is no domain separator (no discriminant byte identifying "this signs a withdrawal" vs. "this signs an accumulate beneficiary redirect").

Both consumers read and later mutate the *same* `Nonce<T>` storage keyed by `(address, state_machine)`:
- `withdraw()`: `let nonce = Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain);` ... later `Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, |value| *value += 1 ...)` [3](#0-2) [4](#0-3) 
- `accumulate()`: `let nonce = Nonce::<T>::get(&delivery_address, state_machine);` ... later `Nonce::<T>::try_mutate(&delivery_address, state_machine, |value| *value += 1 ...)` [5](#0-4) 

Because the message format collides and the nonce namespace is shared, a signature the relayer signs for one call is a fully valid signature for the other call **at the same nonce value**. Both entry points are permissionless/unsigned extrinsics (`ensure_none` origin) — `accumulate_fees` and `withdraw_fees` are both submitted via `validate_unsigned`, so any observer can lift a signature+beneficiary pair off one pending/broadcast extrinsic and resubmit it as the other call type before the originating nonce is consumed.

### Impact Explanation
If exploited, an attacker can cause a relayer's fee to be redirected to an unintended beneficiary through either:
- Capturing a `withdraw_fees` beneficiary-designation signature and replaying it into `accumulate_fees`'s `beneficiary_details`, redirecting freshly-provable fee accumulation to the same address the relayer only authorized for a withdrawal, or
- The reverse direction, causing `withdraw_fees` to be triggered/consumed using a signature the relayer only meant to authorize an `accumulate` redirect.

Either way this is unauthorized manipulation of relayer fund flow and directly matches "unauthorized transaction or execution / logic attacks / wrong beneficiary" impact categories, because the two code paths were never intended to be interchangeable — the destination effects differ (one dispatches a cross-chain withdrawal request draining the relayer's fee balance to zero, the other redirects credit for a newly-proven delivery).

### Likelihood Explanation
Exploitation requires the attacker's replayed extrinsic to be included in a block before the legitimate extrinsic consumes the shared nonce — i.e., it depends on transaction-pool ordering/timing for the specific `(address, state_machine)` nonce slot to still be unconsumed. This narrows practical exploitation to a race window, but the underlying defect (missing domain separation causing two structurally different authorizations to hash identically) is a genuine cryptographic/protocol flaw independent of any privileged actor, malicious relayer, or prover assumption — any address that produces a normal, honestly-signed message for either call is at risk of cross-use.

### Recommendation
Add an explicit domain separator (a distinct discriminant constant/enum tag such as `b"withdraw"` vs. `b"accumulate-beneficiary"`) as the first encoded field in both `message()` and `beneficiary_message()` before hashing, so the two payload types can never collide regardless of nonce or field values. Additionally, consider giving `withdraw()` and `accumulate()`'s beneficiary redirect independent nonce namespaces (e.g., separate storage maps or an action-tag component in the `Nonce` key) rather than sharing a single `Nonce<T>` per `(address, state_machine)`.

### Proof of Concept
1. Relayer R has previously delivered messages on `dest_chain = X` and has current `Nonce::<T>::get(R, X) == n`.
2. R broadcasts a `withdraw_fees` extrinsic with `WithdrawalInputData { beneficiary: Some(B), dest_chain: X, signature: sig }`, where `sig` is R's signature over `message(n, X, Some(B))`.
3. Before R's extrinsic is included, an attacker observes the pending/broadcast extrinsic (transaction data is public in the mempool) and extracts `(B, sig)`.
4. The attacker independently proves (via a legitimate destination state proof, which any observer can construct once delivery happened) that R delivered some other unrelated request on chain `X`, and submits `accumulate_fees` with `beneficiary_details = Some((B, sig))`.
5. Because `beneficiary_message(n, X, B) == message(n, X, Some(B))` bytewise, and `Nonce::<T>::get(R, X)` is still `n` (R's tx not yet applied), the signature verification in `accumulate()` succeeds, crediting the newly-proven fee to `B` and incrementing the shared nonce to `n+1` — consuming R's nonce and redirecting funds to `B` under an authorization R only intended for the withdrawal call.
6. R's original `withdraw_fees` extrinsic, still carrying nonce `n`, is now rejected as replayed/stale even though R never authorized this outcome, and future accumulate/withdraw semantics for R at that chain are permanently confused with the attacker's substitution.
