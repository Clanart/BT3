### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s, enabling a consensus-invalid threshold-signed transaction - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the external report is a permissionless, cost-free trigger that pushes an unintended/incorrect object into a downstream pipeline that acts on it without re-validation. In Serai, the analog is `Scanner::scan_block`, which unconditionally scans `block.txdata[0]` — the coinbase transaction — and emits `ReceivedOutput`s for any outputs paying to a registered script. Coinbase outputs are consensus-immature for 100 blocks, yet the returned `ReceivedOutput` is indistinguishable from a mature one and feeds directly into `SignableTransaction::new` → `multisig` → the FROST `TransactionMachine`, which will produce a fully signed transaction spending an immature coinbase output. That transaction is invalid under Bitcoin consensus rules and will be rejected by every node.

### Finding Description
`scan_block` iterates over every transaction in the block, including the coinbase, and defers to `scan_transaction`, which matches only on `output.script_pubkey` and constructs a `ReceivedOutput` with no maturity or coinbase flag.

`ReceivedOutput` (mod.rs:90-97) carries only `offset`, `output`, and `outpoint` — nothing marks the output as coinbase-derived or immature. `SignableTransaction::new` (send.rs:150-256) accepts `Vec<ReceivedOutput>` and builds inputs from each `outpoint` without any maturity check, and `TransactionSignMachine::sign` (send.rs:373-397) signs each input with `Prevouts::All` and `TapSighashType::Default`, producing a validly signed yet consensus-invalid transaction once completed by `TransactionSignatureMachine::complete` (send.rs:413-428).

The doc comment on `scan_block` acknowledges the issue ("This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed"), but the library provides no marker on `ReceivedOutput` to perform that pass other than re-correlating the txid against `block.txdata[0]`, and nothing in the type system or `SignableTransaction` enforces it.

### Impact Explanation
A miner (an unprivileged external party) can include a coinbase output paying to any script registered in the `Scanner` — including the base tweaked group key script. `scan_block` then reports funds as received that are not spendable for 100 blocks. If a downstream consumer selects that `ReceivedOutput` as an input, the threshold signing round produces a transaction spending an immature coinbase output, which is invalid per consensus (COINBASE_MATURITY = 100). Broadcast fails, the consumed inputs/plan must be reconstructed, and repeated selection of the immature output stalls the signing pipeline. This is the "funds reported received that are not spendable" impact class.

### Likelihood Explanation
Likelihood is Medium. The trigger requires mining a block (or influencing a miner), which has real cost, but requires no protocol privileges, no validator status, and no cooperation from Serai participants — the coinbase output just needs to pay to a scanned `script_pubkey`. Any block containing such an output that is fed to `scan_block` deterministically produces the unspendable `ReceivedOutput`. Whether it is then spent depends on consumer-side input selection, which the library does not guard.

### Recommendation
Track coinbase status/maturity in `ReceivedOutput` (e.g., an `immature` flag or separate type), and/or change `scan_block` to skip `block.txdata[0]` by default — matching the suggestion already in its doc comment of scanning `block.txdata[1 ..]` — with an explicit opt-in variant for scanning the coinbase that returns clearly-marked immature outputs. Additionally, `SignableTransaction::new` could reject immature inputs defensively.

### Proof of Concept
1. A miner mines a block whose coinbase transaction contains an output with `script_pubkey = p2tr_script_buf(scanner.key)` (the script registered by `Scanner::new`, mod.rs:162-166).
2. The consumer calls `Scanner::scan_block(&block)`. `scan_transaction` matches the coinbase output's `script_pubkey` and returns `ReceivedOutput { offset: Scalar::ZERO, output, outpoint: OutPoint::new(coinbase_txid, vout) }` (mod.rs:205-210).
3. The consumer passes this `ReceivedOutput` to `SignableTransaction::new` (send.rs:150), which accepts it — there is no coinbase/maturity validation anywhere in `new`, `multisig` (send.rs:273-285), or `TransactionSignMachine::sign` (send.rs:355-398).
4. The FROST signing round completes via `TransactionSignatureMachine::complete` (send.rs:413-428), yielding a signed transaction spending an immature coinbase output, which any Bitcoin node rejects under `COINBASE_MATURITY` — burned effort on a provably unspendable input, with the scanner still reporting the funds as received.   /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
