### Sub-dust change is silently dropped and permanently burned as miner fees - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` treats a requested change output below `DUST` (546 satoshis) as if no change output exists. The transaction still consumes the entire input amount, so the residual is neither withdrawn nor represented as an output; it is implicitly converted into transaction fees. This is the Bitcoin-wallet analogue of a sub-unit withdrawable amount being rounded to zero.

### Finding Description
Payments below `DUST` are rejected up front, but change is handled differently. When a change address is supplied, `input_sat - payment_sat - fee_with_change` is only added as an output if it is at least 546 satoshis [1](#0-0) . If the remainder is between 1 and 545 satoshis, no change output is pushed and no error is returned. The signed transaction consequently contains only the payment outputs, while `fee()` computes the fee as all inputs minus all outputs [2](#0-1) .

The discrepancy also makes accounting misleading: `needed_fee` remains based on the transaction without a change output when the change is dropped [3](#0-2) . The actual fee can therefore exceed `needed_fee()` by both the dropped remainder and the extra cost of the would-be change output.

### Impact Explanation
An unprivileged party who can influence the requested payment amount or script can choose a payment such that the remainder is 1–545 satoshis. The wallet then produces and threshold-signs a transaction that permanently gives that remainder, plus the marginal fee reserved for the change output, to miners rather than returning it to the requested change address.

The loss is bounded per transaction, but it is deterministic and does not require key access or a malicious validator: it follows solely from attacker-influenced transaction parameters processed by `SignableTransaction::new`.

### Likelihood Explanation
The trigger is straightforward whenever an input, payment amount, fee rate, and change address are externally supplied or assembled from untrusted order/payment data. The attacker only needs to arrange the arithmetic so the residual falls under `DUST`; no race, malformed encoding, or cryptographic assumption is required.

The issue cannot trigger if the remainder is zero, if no change address is requested, or if all transaction parameters are generated by a trusted wallet policy that explicitly prevents near-dust change.

### Recommendation
When a change address is provided and the computed change is non-zero but below `DUST`, reject transaction construction with an explicit error. Alternatively, expose an explicit policy choice allowing the caller to donate sub-dust change to fees; it should not happen silently merely because an optional change address was supplied.

The check should account for `fee_with_change`, since adding the change output increases the transaction size and required fee.

### Proof of Concept
For a transaction with one input, one payment, and a requested change output, choose values satisfying:

```text
input_sat = payment_sat + fee_with_change + 1
```

where `fee_with_change` is calculated at `networks/bitcoin/src/wallet/send.rs:227`.

Then:

```rust
let tx = SignableTransaction::new(
  vec![input],                       // input_sat
  &[(payment_script, payment_sat)],  // payment_sat >= DUST
  Some(change_script),               // caller expects change if possible
  None,
  fee_per_vbyte,
).unwrap();
```

At `networks/bitcoin/src/wallet/send.rs:228-230`, the computed change is `1`, so the condition `value >= DUST` fails and no change output is added. Construction still succeeds. The resulting transaction consumes `input_sat` but outputs only `payment_sat`, making:

```text
actual_fee = fee_with_change + 1
tx.fee() = input_sat - payment_sat
```

The 1-satoshi change amount—and the additional fee reserved for the omitted change output—is irreversibly paid to miners once the transaction is signed and broadcast. Using any residual `1..=545` produces the same silent loss pattern.
