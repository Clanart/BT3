### Title
Scanner::scan_block reports immature coinbase outputs as spendable ReceivedOutputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external finding is an incorrect "maximum available" calculation: `maxWithdraw` returned a bound computed from the wrong quantity, so users could act on funds that were not actually available. The analog in Serai's in-scope code is `Scanner::scan_block` in `networks/bitcoin/src/wallet/mod.rs`, which scans `block.txdata` including `txdata[0]` — the coinbase transaction — and returns its outputs as ordinary `ReceivedOutput`s indistinguishable from spendable ones, even though coinbase outputs are immature and unspendable for 100 blocks.

### Finding Description
`scan_block` iterates every transaction in the block and feeds them to `scan_transaction`, which matches `output.script_pubkey` against registered scripts and wraps matches into `ReceivedOutput` (mod.rs lines 221-227, 199-214). The coinbase transaction pays to arbitrary scripts chosen by the miner; if the miner (or any unprivileged party who mines a block, or whose coinbase coincidentally pays to a watched script — e.g., a pool payout paying a registered offset script) pays to a script in `self.scripts`, the resulting `ReceivedOutput` is returned with no maturity marker. `ReceivedOutput` carries only `offset`, `output`, and `outpoint` (lines 90-97); there is no field or flag distinguishing immature coinbase outputs from confirmed spendable ones.

The returned `ReceivedOutput`s are consumed directly by `SignableTransaction::new` (send.rs lines 150-256), which sums `input.output.value` as available funds (`input_sat`, line 175) and constructs/signs a transaction spending them. Any transaction built from an immature coinbase output is consensus-invalid and will be rejected by the network — i.e., the "available balance" computed from scanning is incorrect, exactly the bug class of the reference finding.

### Impact Explanation
Funds are reported received and spendable that are not spendable. An integrator relying on `scan_block` to compute available balance will overstate it by the immature coinbase amount, and the FROST `TransactionMachine` will produce signatures committing to a transaction (`Prevouts::All`, send.rs line 375) that the Bitcoin network rejects. This wastes a threshold-signing round and can wedge automated withdrawal pipelines that assume scanned outputs are spendable.

### Likelihood Explanation
Reachable by an unprivileged party: any miner can direct a coinbase payout to a watched P2TR script. More realistically, mining pools routinely pay out to arbitrary addresses in the coinbase, so a registered offset script receiving a pool coinbase payout is plausible rather than adversarial-only. The doc comment acknowledges maturity but provides no way for the caller to identify which `ReceivedOutput`s are immature without re-scanning the block — and the API does not enforce the suggested post-processing.

### Recommendation
Either exclude `block.txdata[0]` inside `scan_block` (matching the documented alternative of scanning `txdata[1 ..]`), or extend `ReceivedOutput` with an `immature`/`coinbase` flag so callers can distinguish outputs subject to the 100-block maturity rule, and have `SignableTransaction::new` reject immature inputs.

### Proof of Concept
```rust
// A block whose coinbase pays to a registered script
let mut scanner = Scanner::new(group_key).unwrap();
let script = p2tr_script_buf(group_key).unwrap();

let block: Block = /* block where txdata[0] is a coinbase with an output
                      whose script_pubkey == script */;

let received = scanner.scan_block(&block);
// received contains a ReceivedOutput for the coinbase output.
// It is indistinguishable from spendable outputs and can be fed to:
let tx = SignableTransaction::new(received, &payments, change, None, fee_rate);
// The produced transaction spends an immature coinbase output and is
// consensus-invalid (BIP-34/COINBASE_MATURITY = 100), yet scan_block
// reported the funds as received and available.
```
Root cause is `scan_block` iterating `block.txdata` unfiltered (mod.rs lines 221-227) while `ReceivedOutput` (lines 90-97) cannot express maturity.
