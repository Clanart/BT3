### Title
Deterministic cached preprocess reused across distinct messages/preprocess sets enables validator secret-share recovery and signing a "corrected" message - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically regenerates the same FROST nonces for a given `context` (e.g., `(b"DkgConfirmer", attempt)`) from a seed cached in the DB. `share_internal` rebuilds the sign machine from that cache every time it is invoked, then calls `sign(preprocesses, msg)`. Because both `preprocesses` (attacker-submitted serialized preprocess bytes) and `msg` (derived from `key_pair` via `set_keys_message`) are inputs to each call, any second invocation with different values produces a second signature share under the same seed-derived nonces, recovering the validator's secret share — and letting an attacker obtain a share over a message different from the one originally intended (the Gajim "message correction" analog).

### Finding Description
- `preprocess_internal` stores a 32-byte seed under `CachedPreprocesses[context]` once, then every call does `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`, which feeds the seed into `ChaCha20Rng` and regenerates identical nonces/commitments (`seeded_preprocess`).
- `share_internal` calls `preprocess_internal` then `machine.sign(preprocesses, msg)` with `preprocesses` parsed from caller-supplied bytes via `read_preprocess` and `msg` supplied by the caller.
- In `DkgConfirmer`, `share(preprocesses, key_pair)` builds `msg = set_keys_message(set, removed, key_pair)`, and `complete(preprocesses, key_pair, shares)` internally calls `share_internal(preprocesses, key_pair)` *again* — re-signing with the same nonces.
- In FROST, each share is `s_i = d_i + e_i·ρ_i + c·λ_i·share_i` where `c = Hram(R, group_key, msg)` and `ρ_i` is the binding factor over `group_key || hash_msg(msg) || commitments`. The raw `d_i, e_i` are fixed by the cached seed. Two `sign` executions with either a different `msg` (different `key_pair`) or a different preprocess set (different `ρ_i`) yield two linear equations in the same unknowns, letting an attacker solve for the validator's secret key share — or obtain a valid share for a message the signer never agreed to.

### Impact Explanation
Recovery of a validator's MuSig/FROST secret key share breaks the validator-level root of trust used to confirm DKG results on Substrate. It also produces signature shares over attacker-chosen ("corrected") key-confirmation messages, mirroring CVE-2022-39835's class: material authenticated under a message that was not the one actually presented.

### Likelihood Explanation
The triggering inputs are unprivileged-reachable: `preprocesses` are `HashMap<Participant, Vec<u8>>` received from other validators' tributary transactions, and `key_pair` flows from DKG/tributary data the attacker influences. The nonce-reuse safety argument in the file's header comment depends on BFT finality and "complete rebuild re-decides nonces," but the code re-executes `sign` in `complete` unconditionally — any divergence between the `key_pair`/preprocess sets seen by `share` vs `complete` (or across repeated calls within one attempt, since `context` is just `(b"DkgConfirmer", attempt)`) produces the second share. No protocol-level check binds the cached seed to a single `(msg, preprocesses)` tuple.

### Recommendation
Bind the cached preprocess to the exact signing inputs: store `H(msg || serialized preprocesses)` alongside the seed on first `sign`, and refuse to sign (or panic) if a subsequent `share_internal` call for the same context presents different inputs. Alternatively, record that `share` already emitted a share for the context and make `complete` reuse the produced share rather than re-executing `sign`.

### Proof of Concept
1. In a `DkgConfirmer` attempt, cause `share(preprocesses_A, key_pair_A)` to run: `preprocess_internal` caches seed `S` under `("DkgConfirmer", attempt)` and signs `msg_A = set_keys_message(..., key_pair_A)`, emitting `s_1 = d + e·ρ_A + c_A·λ·share`.
2. Trigger `complete(preprocesses_B, key_pair_B, shares)` (or a second `share` call) with `key_pair_B ≠ key_pair_A` or a different preprocess set: `from_cache` regenerates identical `d, e` from `S`; `sign` emits `s_2 = d + e·ρ_B + c_B·λ·share`.
3. With `ρ_A, ρ_B, c_A, c_B` computable from public inputs, solve the two-equation system for `d`, `e`, and `λ·share` — recovering the validator's secret share and a share valid over `msg_B`, a message never shown during the original sign.
