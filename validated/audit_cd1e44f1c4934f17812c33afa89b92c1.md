### Title
Duplicate inputs inflate `input_sat`, letting the wallet sign a transaction that spends funds it does not have - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` sums the value of every supplied `ReceivedOutput` into `input_sat` and uses that sum as the "available balance" for both the `NotEnoughFunds` check and the change calculation, without checking that the inputs' outpoints are distinct. A duplicated `ReceivedOutput` (two entries with the same `OutPoint`) is counted twice, exactly mirroring the Rio bug where `availableShares` failed to subtract shares already owed to pending withdrawals: the balance check validates against funds that are already committed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the available-funds figure is computed as a plain sum over all inputs:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>(); // line 175
...
if input_sat < (payment_sat + needed_fee) {          // line 215
  Err(TransactionError::NotEnoughFunds { ... })?;
}
```

No deduplication on `input.outpoint` is performed anywhere in `new`, and the inputs are then copied verbatim into `tx_ins` (lines 177-185). The same overcounted `input_sat` is used to size the change output (line 228: `input_sat.checked_sub(payment_sat + fee_with_change)`), so a phantom second copy of a UTXO can create a change output paying satoshis that do not exist.

The crafted inputs are reachable through `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` (lines 122-134), which deserializes `offset`, `TxOut`, and `OutPoint` from untrusted bytes with no consistency checks. Two decoded `ReceivedOutput`s can carry the identical `outpoint`, and `SignableTransaction::new` will accept both. `multisig()` (lines 273-285) only verifies that each offset's tweaked key matches that input's `script_pubkey` — a duplicated honest input passes that check — after which `TransactionSignMachine::sign` produces valid FROST signature shares committing to the self-double-spending transaction via `taproot_key_spend_signature_hash` with `Prevouts::All` (lines 373-397).

### Impact Explanation
The threshold signer group produces cryptographically valid BIP-340 signatures for a transaction that is consensus-invalid (the same outpoint appears twice in `tx.input`, so every node rejects it, and the change/payment amounts may exceed the real input total). This is the Serai analog of the Rio finding: an obligation (the first claim on a UTXO) is not subtracted from the availability check, so a later claim is admitted against non-existent balance, and the downstream settle/sign step completes "successfully" while producing a transaction that can never be broadcast — burning a signing round and leaving the corresponding payment/withdrawal permanently unexecutable until the inputs are corrected. Depending on ordering, the inflated `input_sat` can also push a fabricated change output above `DUST`, emitting a `SignableTransaction` whose stated `fee()`/`needed_fee()` accounting is wrong.

### Likelihood Explanation
Reachability requires only that an attacker influence the byte stream deserialized by `ReceivedOutput::read` or the input vector passed to `SignableTransaction::new` — e.g., by replaying/duplicating a legitimately received output's serialized form. No key material, validator collusion, or privileged position is needed; the same outpoint legitimately exists on-chain, so the duplicated entries individually pass all internal checks (`offset` validity at `multisig()`, `DUST`, `NotEnoughFunds`). The defect is a missing invariant (unique outpoints per transaction), not an edge case requiring exotic values.

### Recommendation
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), collect inputs into a set keyed by `outpoint` (or sort/dedup `tx_ins` by `previous_output`) and reject any duplicate with a new `TransactionError` variant before computing `input_sat`. This enforces the invariant that each claimed UTXO contributes to the available balance exactly once, analogous to the recommended `sharesOwedTotal` subtraction in the original report. `ReceivedOutput::read` may additionally reject outpoints with `Txid::all_zeros()`/`u32::MAX` sentinel values to harden the deserialization surface.

### Proof of Concept
```rust
// Two ReceivedOutputs referencing the SAME on-chain outpoint.
// Each individually passes multisig()'s script_pubkey check since the
// offset is the real offset for that deposit.
let dup = output_a.clone(); // same outpoint, offset, TxOut
let inputs = vec![output_a, dup];

// input_sat = 2 * value(output_a), so this passes NotEnoughFunds and may
// mint a change output for satoshis that don't exist:
let stx = SignableTransaction::new(
    inputs,
    &[(payment_script, value_almost_2x)],   // > real single-UTXO value
    Some(change_script),
    None,
    fee_per_vbyte,
).unwrap();                                  // succeeds — bug

let machine = stx.multisig(&keys).unwrap();  // script check passes for both copies
// ... FROST signing completes, yielding valid signatures for a tx whose
// input list contains the same outpoint twice => rejected by every node.
```

A transaction containing a duplicated `previous_output` is consensus-invalid (BIP/Bitcoin Core `CheckTransaction` rejects duplicate inputs), so the signed result is unbroadcastable and the intended payment is never made, despite the availability check having "verified" sufficient funds.
