## Analog Found: NFT royalty amount computed with premature integer division, causing underpaid/zero royalties in offers

### Title
Premature integer division in `compute_royalty_amount` truncates NFT royalty payments to less than the mathematically correct amount (or zero) - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
The reported TwapOracle bug stems from dividing before multiplying enough decimals, which can cause `getRate` to truncate to zero. The same bug class exists in Chia's NFT offer royalty math: `compute_royalty_amount` divides `abs(offered_amount)` by `royalty_split` *before* multiplying by `percentage`, instead of multiplying first and dividing once at the end. This ordering discards precision unnecessarily and can produce a royalty of `0` (or a smaller-than-correct nonzero value) in cases where the mathematically correct floor-divided royalty would be nonzero (or larger).

### Finding Description
`compute_royalty_amount` is defined as: [1](#0-0) 

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(...)
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```

The correct integer-precision-preserving formula is `abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)` (multiply first, single division at the end). Instead, the code divides by `royalty_split` first (`abs(offered_amount) // royalty_split`), which discards a fractional remainder before the multiplication by `percentage` even happens. This is the same root cause as the TwapOracle finding — an early division truncates a value that should have remained fractional until the final division, producing an incorrect (too-low, sometimes zero) result.

For example, with `offered_amount=-150`, `royalty_split=101`, `percentage=9999` (99.99%):
- Buggy order: `150 // 101 = 1`; `1 * 9999 // 10000 = 0`
- Correct order: `150 * 9999 // (101 * 10000) = 1499850 // 1010000 = 1`

The same division-before-multiplication pattern is duplicated in `NFTWallet.royalty_calculation`, used by the `nft_calculate_royalties` RPC to preview expected royalties: [2](#0-1) 

This function is reachable by any wallet user/offer counterparty constructing or evaluating an NFT offer, via `NFTWallet.make_nft1_offer`, which calls `compute_royalty_amount` once per required royalty NFT when building royalty payments for the offered fungible asset: [3](#0-2) 

### Impact Explanation
`compute_royalty_amount` determines the `CreateCoin` amount paid to the NFT royalty address (`address`) when an offer is settled through `OFFER_MOD`. An offer maker (who is not the royalty recipient) controls both `offered_amount` and, indirectly, `royalty_split` (by choosing how many royalty-bearing NFTs to request in the same offer), and can therefore construct offers where the resulting royalty is unnecessarily rounded down to a smaller value — or to zero — than the correct floor computation would yield, at the expense of the third-party royalty recipient (the NFT creator/collection). This is a value-extraction / offer-settlement-shortfall issue: the counterparty who should receive royalties on a settled trade receives less than intended by protocol design, purely due to arithmetic operation ordering rather than the NFT creator's declared percentage.

### Likelihood Explanation
Any wallet user creating an NFT offer that requests multiple royalty-enabled NFTs (increasing `request_side_royalty_split`) while offering a relatively small fungible amount can trigger this rounding-down behavior without any special privileges — it only requires normal offer-creation RPC calls (`make_nft1_offer` path), which is reachable by any offer maker.

### Recommendation
Reorder the arithmetic in `compute_royalty_amount` (and the equivalent expression in `royalty_calculation`) to perform all multiplications before the final division, e.g. `abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`, matching the TwapOracle mitigation of multiplying by enough decimals/values before dividing, so intermediate truncation does not discard precision that the correct single final division would have preserved.

### Proof of Concept
Using `compute_royalty_amount` directly (as exercised by `chia/_tests/wallet/nft_wallet/test_nft_royalty.py`, e.g. `test_small_amount_truncates_to_zero`):
```python
compute_royalty_amount(offered_amount=-150, royalty_split=101, percentage=9999)
# buggy order: 150 // 101 = 1; 1 * 9999 // 10000 = 0
# correct order: 150 * 9999 // (101 * 10000) = 1
```
This demonstrates the royalty recipient receiving `0` mojos instead of the `1` mojo that correct floor-division arithmetic would yield — reachable by any offer maker structuring `royalty_split` and `offered_amount` in `make_nft1_offer`. [1](#0-0) [3](#0-2)
