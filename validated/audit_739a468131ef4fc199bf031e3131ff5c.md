### Title
Unbounded Sequential RPC Loop in `collect_deposit_move_txids` / `collect_withdrawal_utxos` Stalls Verifier Block Processing — (`File: core/src/citrea.rs`)

---

### Summary

`CitreaClient::collect_deposit_move_txids` and `CitreaClient::collect_withdrawal_utxos` in `core/src/citrea.rs` iterate over every new deposit or withdrawal entry in the Citrea bridge contract with one sequential RPC call per entry and no upper bound on iterations. These functions are called on every finalized Bitcoin block inside `Verifier::handle_finalized_block`. An unprivileged actor who floods the bridge contract with many deposits or withdrawals in a single sync window forces the verifier to issue an unbounded number of sequential network calls, stalling block processing indefinitely. A stalled verifier cannot challenge malicious operators, breaking bridge safety and liveness with material fund impact.

---

### Finding Description

`collect_deposit_move_txids` starts at `last_deposit_idx + 1` and loops, issuing one `eth_call` to `depositTxIds(i)` per iteration, breaking only when the contract reverts (array out of bounds):

```rust
// core/src/citrea.rs:432-454
loop {
    let deposit_txid = self
        .contract
        .depositTxIds(U256::from(start_idx))
        .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
        .call()
        .await;
    match deposit_txid {
        Err(e) if e.to_string().contains("execution reverted") => { break; }
        Err(e) => return Err(e.into()),
        Ok(_) => {}
    }
    // ...
    start_idx += 1;
}
```

`collect_withdrawal_utxos` is structurally identical (lines 470–494), iterating over `withdrawalUTXOs(i)` with the same pattern.

Both functions are called unconditionally from `update_citrea_deposit_and_withdrawals`:

```rust
// core/src/verifier.rs:2218-2227
let new_deposits = self
    .citrea_client
    .collect_deposit_move_txids(last_deposit_idx, l2_height_end)
    .await?;

let new_withdrawals = self
    .citrea_client
    .collect_withdrawal_utxos(last_withdrawal_idx, l2_height_end)
    .await?;
```

Which is called from `handle_finalized_block` on every finalized Bitcoin block:

```rust
// core/src/verifier.rs:3082-3088
self.update_citrea_deposit_and_withdrawals(
    dbtx,
    l2_height_start,
    l2_height_end,
    block_height,
)
.await?;
```

`handle_finalized_block` is the `BlockHandler::handle_new_block` implementation for `Verifier`, invoked by `LcpSyncerTask` / `FinalizedBlockFetcherTask` on every finalized block:

```rust
// core/src/task/lcp_syncer.rs:59-74
impl<C> crate::bitcoin_syncer::BlockHandler for Verifier<C> {
    async fn handle_new_block(...) -> Result<(), BridgeError> {
        self.handle_finalized_block(dbtx, block_id, height, ..., None).await
    }
}
```

There is no overall timeout on `handle_finalized_block` itself, and no cap on the number of iterations in either loop. The per-request timeout (60 s default) applies only to individual RPC calls, not to the loop as a whole.

---

### Impact Explanation

If an attacker creates N new deposits or withdrawals in a single sync window (i.e., between two consecutive verifier sync cycles), the verifier must issue N sequential RPC calls before it can commit the block and advance. With N = 1 000 entries and a 1-second average RPC latency, the verifier is blocked for ~17 minutes per Bitcoin block. With N = 10 000, it is blocked for ~2.8 hours per block.

A blocked verifier:
- Cannot process new finalized Bitcoin blocks.
- Cannot detect or challenge malicious operator behavior (kickoff fraud, invalid assert, etc.).
- Cannot dispatch `lcp_processed` events to the state manager, halting the entire state machine.
- Cannot process new deposits or withdrawals for legitimate users.

If a malicious operator initiates a fraudulent kickoff while the verifier is stalled, no challenge transaction is issued within the challenge window, allowing the operator to claim collateral or drain bridge-controlled UTXOs without contest. This constitutes a material loss of bridged BTC and operator collateral.

---

### Likelihood Explanation

The Citrea bridge contract's `withdraw()` function is callable by any holder of bridge tokens. A single actor who previously deposited bridge_amount × N BTC can register N withdrawals in rapid succession within one Citrea block, forcing the verifier to process all N entries in the next sync cycle. The cost scales linearly with N but the DoS effect is permanent until the verifier catches up (which it never does if new entries keep arriving). The attack surface is entirely unprivileged and reachable from the public Citrea RPC.

---

### Recommendation

1. **Use the contract's count getter before looping.** The test code already calls `getWithdrawalCount()` (visible in `core/src/test/withdraw.rs:150-156`). Read the total count once at `to_height` and iterate only up to that index — eliminating the need for the error-based termination heuristic and bounding the loop.

2. **Batch or paginate RPC calls.** Use `eth_call` multicall patterns or a single storage-proof read (the `UTXOS_STORAGE_INDEX` / `DEPOSIT_STORAGE_INDEX` constants already exist in `core/src/citrea.rs:46-49`) to fetch all entries in one round-trip instead of N sequential calls.

3. **Apply an overall timeout** to `update_citrea_deposit_and_withdrawals` so that a slow or adversarial RPC node cannot stall the verifier indefinitely.

4. **Process entries incrementally with a per-block cap.** Limit the number of new entries processed per `handle_finalized_block` invocation and carry the remainder to the next block, preventing any single block from monopolizing the verifier's processing loop.

---

### Proof of Concept

**Setup:** Attacker holds sufficient bridge tokens on Citrea (obtained via prior legitimate deposits).

**Step 1 — Flood the contract:** In a single Citrea block, the attacker calls `withdraw()` N times (e.g., N = 5 000), each with a distinct UTXO, registering 5 000 entries in `withdrawalUTXOs`.

**Step 2 — Verifier sync triggered:** The next finalized Bitcoin block causes `LcpSyncerTask` to call `Verifier::handle_new_block` → `handle_finalized_block` → `update_citrea_deposit_and_withdrawals`.

**Step 3 — Unbounded loop executes:** `collect_withdrawal_utxos(last_withdrawal_idx=None, to_height=T)` starts at index 0 and issues 5 000 sequential `eth_call` requests to `withdrawalUTXOs(0)` … `withdrawalUTXOs(4999)`. At 200 ms average latency per call, this takes ~17 minutes. At 1 s latency (congested node), ~83 minutes.

**Step 4 — Verifier stalled:** During this period, no new Bitcoin blocks are processed. If a malicious operator broadcasts a fraudulent kickoff transaction during this window, the verifier issues no challenge. The operator's assert/disprove window expires unchallenged.

**Step 5 — Permanent liveness failure:** The attacker continuously registers new withdrawals each block, keeping `last_withdrawal_idx` perpetually behind the contract's count, ensuring the verifier never catches up.

**Corrupted value:** The verifier's `next_finalized_height` counter in `FinalizedBlockFetcherTask` never advances past the block where the flood occurred, and `StateManager::dispatch_lcp_processed` is never called for subsequent heights, permanently halting the state machine.     async fn collect_deposit_move_txids(
        &self,
        last_deposit_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, Txid)>, BridgeError> {
        let mut move_txids = vec![];

        let mut start_idx = match last_deposit_idx {
            Some(idx) => idx + 1,
            None => 0,
        };

        loop {
            let deposit_txid = self
                .contract
                .depositTxIds(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match deposit_txid {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Deposit txid not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            tracing::info!("Deposit txid found for index: {:?}", deposit_txid);

            let deposit_txid = deposit_txid.expect("Failed to get deposit txid");
            let move_txid = Txid::from_slice(deposit_txid._0.as_ref())
                .wrap_err("Failed to convert move txid to Txid")?;
            move_txids.push((start_idx as u64, move_txid));
            start_idx += 1;
        }
        Ok(move_txids)
    }

    async fn collect_withdrawal_utxos(
        &self,
        last_withdrawal_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, OutPoint)>, BridgeError> {
        let mut utxos = vec![];

        let mut start_idx = match last_withdrawal_idx {
            Some(idx) => idx + 1,
            None => 0,
        };

        loop {
            let withdrawal_utxo = self
                .contract
                .withdrawalUTXOs(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match withdrawal_utxo {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Withdrawal utxo not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            let withdrawal_utxo = withdrawal_utxo.expect("Failed to get withdrawal UTXO");
            let txid = withdrawal_utxo.txId.0;
            let txid =
                Txid::from_slice(txid.as_ref()).wrap_err("Failed to convert txid to Txid")?;
            let vout = withdrawal_utxo.outputId.0;
            let vout = u32::from_le_bytes(vout);
            let utxo = OutPoint { txid, vout };
            utxos.push((start_idx as u64, utxo));
            start_idx += 1;
        }
        Ok(utxos)
    }

    pub async fn handle_finalized_block(
        &self,
        mut dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_height: u32,
        block_cache: Arc<block_cache::BlockCache>,
        light_client_proof_wait_interval_secs: Option<u32>,
    ) -> Result<(), BridgeError> {
        tracing::info!("Verifier handling finalized block height: {}", block_height);

        // before a certain number of blocks, citrea doesn't produce proofs (defined in citrea config)
        let max_attempts = light_client_proof_wait_interval_secs.unwrap_or(TEN_MINUTES_IN_SECS);
        let timeout = Duration::from_secs(max_attempts as u64);

        let (l2_height_start, l2_height_end) = self
            .citrea_client
            .get_citrea_l2_height_range(
                block_height.into(),
                timeout,
                self.config.protocol_paramset(),
            )
            .await
            .inspect_err(|e| tracing::error!("Error getting citrea l2 height range: {:?}", e))?;

        tracing::debug!(
            "l2_height_start: {:?}, l2_height_end: {:?}, collecting deposits and withdrawals...",
            l2_height_start,
            l2_height_end
        );
        self.update_citrea_deposit_and_withdrawals(
            dbtx,
            l2_height_start,
            l2_height_end,
            block_height,
        )
        .await?;

        self.update_finalized_payouts(dbtx, block_id, &block_cache)
            .await?;

        #[cfg(feature = "automation")]
        {
            // Save unproven block cache to the database
            self.header_chain_prover
                .save_unproven_block_cache(Some(&mut dbtx), &block_cache)
                .await?;
            while (self.header_chain_prover.prove_if_ready().await?).is_some() {
                // Continue until prove_if_ready returns None
                // If it doesn't return None, it means next batch_size amount of blocks were proven
            }
            // notify that lcp was processed for this height to state manager
            StateManager::<Self>::dispatch_lcp_processed(&self.db, dbtx, block_height).await?;
        }

        Ok(())
    }
