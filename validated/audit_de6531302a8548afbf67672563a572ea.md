### Title
Native-BNB bribe rewards become permanently unclaimable via `claimAllBribes` due to `address(0)`/`wbnb` token-identity mismatch - (File: `wombat/WombatBribeManager.sol`)

### Summary
`WombatBribeManager.claimAllBribes` determines whether a user has bribe rewards to harvest by calling `earned(_for, rewardTokens[i])` where `rewardTokens[i]` is read directly from the raw Wombat bribe contract's `rewardTokens()` list [1](#0-0) . For native-BNB bribes this raw token is `address(0)`. However, `WombatStaking.vote()` — the function that actually harvests bribes and funds the `IBribeRewardPool` rewarder — converts `address(0)` (BNB) into `wbnb` before queuing the reward into the pool's internal accounting [2](#0-1) . This is the exact same class of bug as the referenced Swapper report: a discount/config/lookup keyed on the "converted" token identity (`wbnb`) does not match the "unconverted" identity (`address(0)`/native) used elsewhere in the system.

### Finding Description
When a bribe pool distributes rewards in native BNB, the `IWombatBribe` contract represents that reward token as `address(0)`. When `castVotes`/`WombatStaking.vote()` harvests these rewards, it explicitly detects the zero address and wraps the native asset into `wbnb`, then queues the rewards into the `IBaseRewardPool`/`IBribeRewardPool` under the **`wbnb`** key [3](#0-2) . From that point forward, the reward pool's internal reward-token bookkeeping (its `rewardTokens` array and `rewards[token]` mapping) is keyed by `wbnb`, not `address(0)`.

`claimAllBribes`, however, independently re-derives the reward token to query by calling the bribe contract directly: `rewardTokens[i] = address(IWombatBribe(bribesContract).rewardTokens()[0])`, which still returns `address(0)` for native BNB bribes [4](#0-3) . It then uses that raw, unconverted key to check `earned(_for, rewardTokens[i])` and gates the actual reward transfer on the result:
```solidity
earnedRewards[i] = IBribeRewardPool(pool.rewarder).earned(_for, rewardTokens[i]);
if (earnedRewards[i] > 0) {
    IBribeRewardPool(pool.rewarder).getReward(_for, _for);
}
``` [5](#0-4) 

Since the pool never queued rewards under key `address(0)` (they were queued under `wbnb`), `earned(_for, address(0))` returns 0 even when real, unclaimed `wbnb` rewards are sitting in the pool for that user. As a result, `getReward` — the call that would actually transfer the user's rewards — is never invoked through this code path for native-BNB bribe pools.

### Impact Explanation
Any vlMGP voter who calls the unprivileged, public `claimAllBribes` function to harvest bribes from a pool whose bribe reward token is native BNB will have that portion of their harvest silently skipped, even though real `wbnb` balance is already accrued to them inside the `IBribeRewardPool`. Because the check is keyed on the wrong address every single time `claimAllBribes` is used, this is not a one-off race but a structural, permanent inability to harvest native-BNB bribe rewards via this entry point — a permanent freezing of unclaimed yield for affected pools/users, consistent with the accepted impact class in the referenced report (config/lookup keyed on the converted vs. unconverted native-asset identity).

### Likelihood Explanation
Likelihood is high wherever a bribe pool's incentive is denominated in native BNB, which the codebase explicitly anticipates and handles (`WombatStaking.vote()` has dedicated logic to wrap native BNB rewards) [6](#0-5) . No privileged action or misconfiguration by the user is required — any ordinary vlMGP holder calling `claimAllBribes` (directly, or via `castVotesAndClaimBribes`/`voteAndCast` flows) for such a pool will trigger the mismatch every time.

### Recommendation
`claimAllBribes` should not re-derive the reward token from the raw `IWombatBribe.rewardTokens()` list. Instead it should use the token identity that `IBribeRewardPool` actually tracks internally (i.e., normalize `address(0)` to `wbnb` the same way `WombatStaking.vote()` does before calling `earned`), or better, avoid the pre-check entirely and always call `getReward(_for, _for)` and let the reward pool report actual rewards paid, mirroring the safer pattern already used by `claimBribe`/`claimBribeFor` [7](#0-6) .

### Proof of Concept
1. A Wombat pool's `veWom.infos(lp).bribe` bribe contract lists its sole reward token as `address(0)` (native BNB), consistent with the handling in `WombatStaking.vote()` [8](#0-7) .
2. A vlMGP holder votes for that pool (`WombatBribeManager.vote`) and someone calls `castVotes`, which calls `WombatStaking.vote()`; native BNB bribes are wrapped to `wbnb` and `queueNewRewards(rewardAmount, wbnb)` is called on the pool's rewarder [9](#0-8) . The rewarder's internal accounting now tracks earned rewards under `wbnb`.
3. The voter calls `claimAllBribes(_for)`. For this pool, `rewardTokens[i]` is set from `IWombatBribe(bribesContract).rewardTokens()[0]`, i.e., `address(0)` [10](#0-9) .
4. `earned(_for, address(0))` on the rewarder returns 0 (no rewards were ever recorded under that key), so `getReward` is never invoked, and the user's real `wbnb` bribe reward remains stuck in the pool, unreachable through this claim path.
