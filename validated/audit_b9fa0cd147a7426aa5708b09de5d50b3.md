### Title
Cubic-complexity coin-dependency scan in `Offer.get_cancellation_coins()` causes wallet transaction-processing halt via malicious offer - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_cancellation_coins()` and its helper `detect_dependent_coin()` in `chia/wallet/trading/offer.py` re-scan the entire set of an offer's coin spends with nested loops and list-membership tests instead of set lookups, mirroring the exact bug class in the Absinthe advisory (an O(N) linear scan performed once per item, embedded inside outer loops, turning a linear problem into a polynomial one). Because the number of coins in an offer and the number of announcement conditions per coin are attacker-controlled and only bounded by overall CLVM cost (the announcement-count cap was removed at hard-fork 3.0), a malicious offer counterparty can craft an offer that makes this routine perform a very large amount of work when the victim's wallet attempts to compute cancellation coins for that offer.

### Finding Description
`detect_dependent_coin()` walks every coin name, then every dependency of that coin, then every `(coin, announces)` pair in the announcement dictionary, and tests `dependency in announces` — a full linear scan of the `announces` list — for every dependency of every coin: [1](#0-0) 

`get_cancellation_coins()` builds `dependencies` and `announcements` maps from every non-addition coin spend in the offer bundle by actually running each puzzle (`run_with_cost`) and scanning its output conditions: [2](#0-1) 

It then repeatedly calls `detect_dependent_coin()` in an outer `while True:` loop, removing one dependent coin (and everything that depends on it) per outer iteration, and restarts the full triple-nested scan from scratch on the remaining coin set each time: [3](#0-2) 

This is structurally identical to the Absinthe `UniqueFragmentNames` flaw: a per-item `Enum.count`/list-scan (`dependency in announces`) is nested inside loops over all items (`names`, `deps[name]`, `announcement_dict.items()`), and the whole scan is repeated once per removed item in the outer `while` loop — yielding complexity on the order of O(N² · A) per outer pass and O(N) outer passes (N = coin count, A = average announcements per coin), i.e., roughly cubic in the attacker-controlled offer size. Both `N` (number of coin spends in the offer) and `A` (announcement conditions per coin) are controlled entirely by the untrusted offer's CLVM programs, and per the test suite the per-puzzle CREATE_COIN_ANNOUNCEMENT/ASSERT_COIN_ANNOUNCEMENT limit was removed post hard-fork 3.0, so only the aggregate CLVM cost budget bounds these counts: [4](#0-3) 

Because announcement conditions are cheap relative to `MAX_BLOCK_COST_CLVM`/offer max-cost checks (see `ConditionCost`), and coin generation itself can be made cheap using a CLVM-side counter (as shown by `CREATE_UNIQUE_COINS`, which emits thousands of coins under a small fixed cost budget), a crafted offer can pack many thousands of coins each carrying many announcement conditions while still passing `Offer`'s own cost checks: [5](#0-4) [6](#0-5) 

### Impact Explanation
`get_cancellation_coins()` is invoked from `chia/wallet/trade_manager.py` when a wallet needs to determine which coins to spend in order to cancel a pending/received offer. Chia's wallet node runs on a single asyncio event loop; a synchronous, CPU-bound call of this complexity blocks that event loop for the duration of the computation, halting all other wallet transaction processing (sending, receiving, RPC calls) for that wallet process while it is stuck evaluating the malicious offer's dependency graph. This matches the "spend-triggered transaction-processing halt" impact category: the attacker does not need to compromise anything beyond sending a specially-crafted offer to the victim.

### Likelihood Explanation
Medium-to-High. Any wallet user who loads an offer from an untrusted counterparty (a common offer-marketplace workflow) and whose wallet subsequently computes cancellation coins for it is affected. No signature forgery, special privileges, or race conditions are required — only the ability to construct an offer whose CLVM output emits many coins and many `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions, which is well within reach of a crafting party given documented cost-efficient CLVM patterns already present in the test suite.

### Recommendation
Rewrite `detect_dependent_coin()`/`get_cancellation_coins()` to avoid repeated linear scans:
- Build an inverted index (announcement value → coin name) once, using a `dict`/`set`, so `dependency in announces` becomes an O(1) lookup instead of an O(len(announces)) list scan.
- Avoid restarting the full scan over all remaining names after each removal; maintain and update dependency/announcement state incrementally (e.g., process removals via a worklist/queue) so the overall algorithm is close to linear in the number of coins and conditions.
- Consider bounding the total number of coin spends and/or announcement conditions examined by this cancellation-coin computation, independent of the raw CLVM cost limit, since cost alone does not proportionally limit the number of extractable conditions.

### Proof of Concept
Conceptual PoC (mirroring the Absinthe PoC's approach of timing a specific validation phase against a maliciously-shaped input):
1. Construct an `Offer` whose underlying `WalletSpendBundle` contains a large number of coin spends (e.g., several thousand), generated cheaply via a CLVM counter idiom analogous to `CREATE_UNIQUE_COINS` so the aggregate CLVM cost stays under `Offer`'s max-cost check.
2. Have each coin spend's puzzle emit a large number of `CREATE_COIN_ANNOUNCEMENT` and `ASSERT_COIN_ANNOUNCEMENT` conditions referencing announcements from many other coins in the same bundle, forming a dense dependency graph (uncapped post hard-fork 3.0 per `test_announce_conditions_limit`).
3. Call `Offer.get_cancellation_coins()` (the same call path `TradeManager` uses to cancel an offer) on this crafted `Offer` and measure wall-clock time; the nested-loop/list-membership structure in `detect_dependent_coin()` predicts runtime growing much faster than linearly with the number of coins/conditions, analogous to the 15-second stall demonstrated for Absinthe's `UniqueFragmentNames` phase with 20,000 fragments.

Note: I was not able to execute this PoC (no code execution tooling available in this environment); the finding is based on static analysis of the nested-loop/list-membership structure in `chia/wallet/trading/offer.py` and the related test evidence about uncapped announcement counts and cheap large-N coin generation. A background Devin session with code-execution access would be needed to run and time the concrete PoC.

def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
