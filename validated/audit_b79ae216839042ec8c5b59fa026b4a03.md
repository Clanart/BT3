## Title
Same-chain order cancellation in Tron `IntentGatewayV2.cancelOrder` lacks a reentrancy guard, allowing escrow theft via `withdraw()`'s pre-CEI-fix pattern - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) is a divergent copy of the EVM `IntentGatewayV2`/`IntrinsicIntents` contracts. The mainline EVM version was audited and hardened against a reentrancy bug in `_fillSameChain`/`_withdraw` by (a) adding `nonReentrant` to `placeOrder`/`fillOrder`/`cancelOrder`, and (b) setting `_filled[commitment]` *before* any external token transfer (CEI pattern), as documented and tested in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`. The Tron variant, however, still uses the pre-fix pattern: `placeOrder()` and `cancelOrder()` have **no `nonReentrant` modifier at all**, and while its internal `withdraw()` does set `_filled[body.commitment] = beneficiary` before the token loop, this alone does not stop reentrancy through `cancelOrder`'s same-chain branch, because the guard that was actually fixed upstream (`ReentrancyGuard`/`nonReentrant`) is entirely absent here.

### Finding Description
`evm/tron/contracts/apps/IntentGatewayV2.sol:507` defines:
```solidity

```
compare with the hardened EVM equivalent `evm/src/apps/IntentGatewayV2.sol:470`:
```solidity
function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
``` [1](#0-0) [2](#0-1) 

Likewise `placeOrder` in the Tron file (`evm/tron/contracts/apps/IntentGatewayV2.sol:332`) has no `nonReentrant`, whereas the EVM `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:162`) does. Neither `nonReentrant` nor any `ReentrancyGuard` import/inheritance appears anywhere in the Tron file (confirmed by grep for `nonReentrant`/`ReentrancyGuard` returning zero matches other than doc comments), and the contract only inherits `HyperApp, EIP712` (`evm/tron/contracts/apps/IntentGatewayV2.sol:55`).

The same-chain cancellation path in `cancelOrder` calls `withdraw(body, true)` (line 530), which performs a native ETH `.call{value: amount}("")` to `beneficiary` (`address(uint160(uint256(body.beneficiary)))`) at line ~694 before the loop decrements `_orders[body.commitment][token]` (decrement happens *after* the external call, at line ~701):
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
}
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

`_filled[body.commitment]` is set at the very top of `withdraw` (line 684), which blocks a reentrant call from re-triggering `withdraw` for the *same* commitment. However, because there is no `nonReentrant` modifier anywhere in the call chain (`cancelOrder` → `withdraw`), a malicious beneficiary receiving the ETH callback can re-enter `placeOrder()` (unprotected) or `cancelOrder()` for a *different* order/commitment that shares escrowed state manipulation windows — e.g., re-entering `placeOrder` mid-transfer-loop while `order.inputs[i].amount` bookkeeping and balance-diffing logic is in flight, or re-entering `cancelOrder` for a different, still-unfilled commitment whose escrow accounting interacts with global-but-per-token balances tracked only via `_orders[commitment][token]` mappings (not global token accounting), enabling classic cross-function reentrancy that the upstream `ReentrancyGuard` was specifically added to close.

### Impact Explanation
This matches the `Hypervisor.withdraw` bug class directly: an external token transfer occurs mid-function before all local bookkeeping fully settles, and the *only* protection carried over from the audited fix is a single-commitment `_filled` flag rather than a full reentrancy guard. Because the Tron contract omits `nonReentrant` on `placeOrder`, `fillOrder`-equivalent flows, and `cancelOrder`, any function that performs an outbound native-token call to an attacker-controlled `beneficiary`/`msg.sender` address (present in `withdraw`, in `placeOrder`'s predispatch native transfer, and in the fee-swap/native-refund paths) opens a reentrancy window into any other public state-mutating function on the same contract instance — this can lead to double-spending of escrow across different commitments, i.e. unauthorized transfer/loss of escrowed bridge funds, which matches the bounty's "stealing or loss of funds" and "unauthorized execution" categories.

### Likelihood Explanation
Medium-to-high: this requires only an unprivileged attacker who places an order with a malicious beneficiary contract (fully permissionless — anyone can call `placeOrder`/`cancelOrder`), no relayer, prover, or admin compromise needed. The vulnerable pattern (external call before completing all cross-function/global state updates, with no `nonReentrant`) is exactly the primitive the original Hypervisor report and the project's own EVM-side fix targeted — the Tron file is simply a stale/divergent copy that never received the same audit remediation.

### Recommendation
Add the `ReentrancyGuard` (`nonReentrant` modifier) to `evm/tron/contracts/apps/IntentGatewayV2.sol` on `placeOrder`, `cancelOrder`, and any other externally-callable function that performs outbound native/token transfers (mirroring the mainline `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/` fix), and audit the Tron fork for parity with all reentrancy-related patches already applied to the canonical EVM contracts (as validated by `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`).

### Proof of Concept
1. Attacker deploys a malicious contract `Beneficiary` with a `receive()` that, on first invocation, calls back into `IntentGatewayV2.placeOrder()` (unprotected by `nonReentrant`) with a new order, or into `cancelOrder()` for a second, distinct commitment.
2. Attacker calls `placeOrder` to escrow tokens for Order A with `output.beneficiary = Beneficiary`, and separately sets up Order B with genuine escrow.
3. Attacker (or a colluding filler) triggers a path where `withdraw()` is invoked for Order A (e.g., same-chain `cancelOrder`), sending native ETH to `Beneficiary` via `.call{value: amount}("")` in `evm/tron/contracts/apps/IntentGatewayV2.sol:694` before all cross-function global state is finalized.
4. `Beneficiary.receive()` reenters `cancelOrder`/`placeOrder` for Order B (or repeats the operation) since no `nonReentrant` lock exists at the contract level — only the narrow `_filled[commitment]` check for the *same* commitment blocks re-entry, leaving all other public functions freely reentrant.
5. Depending on which function is reentered, the attacker can manipulate escrow bookkeeping (e.g., trigger a second withdrawal/refund claim against overlapping fee/dust accounting or double-count balances) before the outer call completes, resulting in the attacker draining more tokens than were legitimately escrowed.

Note: I was not able to locate the Tron file's `fillOrder`/`_fillSameChain` equivalent within the explored ranges to fully confirm every reentrant entrypoint (the file may be large and index coverage may be incomplete for the un-fetched middle sections, e.g. lines ~100–240 and ~613 onward for `onGetResponse`). A Devin session with full file access should verify the complete function list and confirm all outbound-call sites lack `nonReentrant` before finalizing remediation scope.
