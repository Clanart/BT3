### Title
Operator/Verifier `secret_key` Exposed in Debug Logs via Unprotected `BridgeConfig` and `TxSenderConfig` Debug Derivation — (`core/src/config/env.rs`, `core/src/config/mod.rs`, `crates/clementine-tx-sender/src/config.rs`)

---

### Summary

`BridgeConfig` and `TxSenderConfig` both derive `Debug` and store the actor's secp256k1 `secret_key` (and `private_da_key`) as bare `SecretKey` fields — not wrapped in `secrecy::Secret<>`. A `tracing::debug!` call in the production config-loading path unconditionally formats the entire `BridgeConfig` struct, including the raw private key, into the log stream. Other sensitive fields in the same struct (`bitcoin_rpc_password`, `db_password`, `db_user`, `bitcoin_rpc_user`) are correctly wrapped in `SecretString` and are redacted in Debug output; `secret_key` is not, creating an inconsistency that is a code bug, not an operator configuration mistake.

---

### Finding Description

`BridgeConfig` is declared with `#[derive(Debug, Clone, Deserialize)]` and contains:

```rust
pub secret_key: SecretKey,   // bare secp256k1 key — no secrecy wrapper
pub bitcoin_rpc_user: SecretString,   // correctly redacted
pub bitcoin_rpc_password: SecretString, // correctly redacted
pub db_user: SecretString,            // correctly redacted
pub db_password: SecretString,        // correctly redacted
``` [1](#0-0) 

At the end of `BridgeConfig::from_env()`, the entire struct is emitted to the tracing log at DEBUG level:

```rust
tracing::debug!("BridgeConfig from env: {:?}", config);
``` [2](#0-1) 

`bitcoin::secp256k1::SecretKey`'s `Debug` implementation outputs the key material as hex (via `display_secret()`). Because `secret_key` is not wrapped in `secrecy::Secret<SecretKey>`, the `{:?}` format expands to the full 32-byte private key in hex.

The same pattern exists in the standalone tx-sender:

```rust
#[derive(Clone, Debug)]
pub struct TxSenderConfig {
    pub secret_key: SecretKey,
    pub private_da_key: Option<SecretKey>,
    ...
}
``` [3](#0-2) 

---

### Impact Explanation

The `secret_key` in `BridgeConfig` is the secp256k1 private key used by operators and verifiers to:

- Sign Bitcoin transactions controlling the operator's **collateral UTXO** and **reimbursement outputs** (bridge-controlled UTXOs).
- Participate in MuSig2 deposit signing sessions that produce the move-to-vault transaction.

For the tx-sender, `secret_key` controls the **tx-sender-managed UTXO pool** used to fund and CPFP bridge transactions; `private_da_key` signs Citrea DA blobs.

If an attacker gains access to log output while DEBUG logging is active (e.g., during incident response, log aggregation misconfiguration, or a developer enabling `RUST_LOG=debug` on a production node), they obtain the raw private key and can:

1. Spend the operator's collateral UTXO directly on Bitcoin.
2. Redirect reimbursement outputs.
3. Drain the tx-sender's UTXO pool.
4. Impersonate the operator/verifier in future signing sessions.

---

### Likelihood Explanation

Requires `RUST_LOG=debug` (or equivalent) to be active and log output to be accessible to an attacker. Default production deployments use `RUST_LOG=info` (confirmed in docker configs), so the debug line does not fire under normal conditions. However, the code bug is latent and unconditional: any operator who enables debug logging for troubleshooting — a common operational action — immediately exposes their signing key. The inconsistency with `SecretString` usage for other credentials makes this a code defect, not a configuration mistake.

---

### Recommendation

1. Wrap `secret_key` in `secrecy::Secret<SecretKey>` (or a newtype that implements `Debug` as `[REDACTED]`) in both `BridgeConfig` and `TxSenderConfig`, consistent with how `bitcoin_rpc_password`, `db_password`, etc. are handled.
2. Remove or gate the `tracing::debug!("BridgeConfig from env: {:?}", config)` call; if config logging is needed, implement a custom `Debug`/`Display` that explicitly redacts all key material.
3. Audit all other `tracing::debug!` / `tracing::trace!` / `println!` / `eprintln!` call sites that format `BridgeConfig`, `TxSenderConfig`, or any struct containing `SecretKey` fields.

---

### Proof of Concept

1. Start any Clementine actor (verifier, operator, aggregator, or standalone tx-sender) with `RUST_LOG=debug` and `READ_CONFIG_FROM_ENV=1`.
2. Observe the log line emitted by `core/src/config/env.rs:255`:
   ```
   DEBUG clementine_core::config::env: BridgeConfig from env: BridgeConfig { secret_key: SecretKey(<hex of private key>), bitcoin_rpc_user: Secret([REDACTED]), ... }
   ```
3. The 32-byte secp256k1 private key appears in plaintext hex in the log stream while all `SecretString`-wrapped fields are correctly redacted. [4](#0-3) [2](#0-1) [3](#0-2)
