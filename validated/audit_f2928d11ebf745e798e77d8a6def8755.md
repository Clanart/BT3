## Title
Bounded state-commitment queue can evict a still-unchallenged `StateCommitment` before its `challenge_period` elapses, permanently blocking proof verification for in-flight requests/responses/timeouts - (File: `modules/pallets/ismp/src/lib.rs`, `modules/pallets/ismp/src/host.rs`)

### Summary
`pallet-ismp` retains state machine commitments per state machine in a bounded, FIFO-evicted queue (`StateCommitmentQueue` / `BoundedStateCommitments` / `BoundedStateMachineUpdateTime`), capped at `MAX_STATE_MACHINE_COMMITMENTS` (or an admin override via `update_commitment_caps`). New consensus updates push new heights and evict the oldest ones once the cap is exceeded, independent of whether the evicted height's `challenge_period` has elapsed yet. [1](#0-0) 

This is a structural analog to the external report's blockhash-256-block problem: a time-bounded on-chain invariant (`challenge_period` must elapse before a commitment can be used) depends on a piece of state (`BoundedStateCommitments`/`BoundedStateMachineUpdateTime`) whose retention window is independent of, and can be shorter than, the time-bound itself.

### Finding Description
`verify_delay_passed` / `validate_state_machine` gate every request, response, and timeout handler on the `challenge_period` configured for a state machine, reading the recorded `state_machine_update_time` for the specific proof height: [2](#0-1) 

Both the commitment and its update time for a given height are stored via the same bounded, per-chain FIFO queue and are evicted together once the configured cap is exceeded: [3](#0-2) [4](#0-3) [5](#0-4) 

`update_client` stores a `StateMachineUpdated` commitment for *every* intermediate height reported by a consensus update, one insertion (and one potential eviction) per height: [6](#0-5) 

If the counterparty chain's finality cadence produces more than `cap` new heights within the configured `challenge_period` window (i.e. `challenge_period_seconds / average_finality_interval > cap`), a height's `BoundedStateCommitments`/`BoundedStateMachineUpdateTime` entry gets evicted from the queue *before* the challenge period for that height has actually elapsed. This can happen through completely honest, permissionless consensus updates — no fraud proof, malicious relayer, or governance action is required; only enough legitimate chain progress on the counterparty.

Once evicted, `state_machine_commitment()` and `state_machine_update_time()` both return `Err(StateCommitmentNotFound)` / `Custom("Update time not found")` for that height, so:
- Any relayer holding a valid, fee-paid `PostRequest`/`GetResponse` whose commitment/proof was anchored to that specific height can never again pass `validate_state_machine`/`verify_membership` for it, even though the height was never vetoed and no fraud was ever proven.
- Any `PostRequestTimeoutMessage`/`GetTimeoutMessage` also depends on `stateMachineCommitmentUpdateTime`/`state_machine_commitment` at a (possibly different, but still boundable) height to prove non-membership — the same eviction race applies there.

The code comments in `insert_bounded_state_commitment` and `update_commitment_caps` acknowledge the cap must be "sized to the chain's finality cadence" but there is no on-chain enforcement tying `cap` to `challenge_period`; they are configured independently (`ChallengePeriod::<T>` vs `StateMachineCommitmentCap::<T>`), so a mismatched pair of parameters (including plausible defaults for a fast-finality chain paired with a long, deliberately conservative `challenge_period`) silently breaks the protocol's core "wait challenge_period, then trust the state" invariant.

### Impact Explanation
This breaks the core cross-chain trust invariant that a `StateCommitment`, once past its `challenge_period`, must remain usable to prove membership/non-membership of the requests/responses committed against it. When eviction races the challenge period:
- Paid relayer fees for legitimate, already-dispatched requests become undeliverable through the normal request-handling path; the only recovery is waiting for the request's own `timeout_timestamp` and processing a timeout (assuming a *later*, live commitment can still prove non-membership on the destination), which delays settlement and can leave funds locked in escrow far longer than intended, or indefinitely if the destination chain processed the request in the meantime (making later timeout/non-membership proofs impossible without a surviving commitment at the right height) — exactly mirroring the "transaction will fail" outcome of the reported bug-class, applied to Hyperbridge's request/timeout settlement pipeline rather than a slashing dispute window.
- This is a pure liveness/fund-lock failure, not a validator- or relayer-trust bypass, and requires no privileged or malicious actor — only ordinary fast finality on the counterparty chain combined with the deployment's own configured `challenge_period`/cap pairing.

### Likelihood Explanation
Likelihood depends entirely on runtime configuration (cap vs. challenge period vs. counterparty finality rate), which is set by governance/admin, not by an attacker. I was not able to confirm from the indexed code what the deployed defaults are for `MAX_STATE_MACHINE_COMMITMENTS`, `ChallengePeriod`, and per-chain finality intervals in production (gargantua/nexus runtimes), so I cannot certify this fires under current mainnet parameters — this is a latent configuration-dependent bug rather than a demonstrated exploit with today's settings. It requires no attacker action, only normal operation with an unfavorable configuration.

### Recommendation
- Enforce an on-chain invariant when `update_commitment_caps` or `ChallengePeriod` is set: reject configurations where `cap * average_finality_interval < challenge_period`, or dynamically size the retention window from the configured `challenge_period` rather than a fixed commitment count.
- Alternatively, do not evict a height until `verify_delay_passed` for it would return `true` (i.e., never evict inside the active challenge window), falling back to unlimited growth (bounded by wall-clock pruning) rather than count-based FIFO eviction.
- Document explicitly (as the original report recommends for its own case) that `MAX_STATE_MACHINE_COMMITMENTS`/per-chain caps must be provisioned for `challenge_period_seconds / finality_interval_seconds`, and add a runtime/CI check that the deployed genesis/config values satisfy this for every registered state machine.

### Proof of Concept
Deterministic PoC available in-repo showing eviction of a live commitment purely from normal `store_state_machine_commitment` calls, no attacker or admin action required to trigger the eviction mechanic: [7](#0-6) 

To reproduce the challenge-period race conceptually:
1. Configure `challenge_period` for state machine `S` to `T` seconds.
2. Configure (or leave default) `StateMachineCommitmentCap`/`MAX_STATE_MACHINE_COMMITMENTS` for `S` such that `cap * finality_interval(S) < T`.
3. Dispatch a `PostRequest` whose commitment is anchored at height `H` on `S`.
4. Let honest consensus updates for `S` advance past `H + cap` heights before `T` seconds elapse (this occurs naturally if `S` finalizes faster than `T/cap`).
5. Attempt `handlePostRequests`/`handle_incoming_message` with a proof at height `H` after `T` seconds: `host.state_machine_commitment(H)` / `state_machine_update_time(H)` now return `Err` (evicted), exactly as `commitment_queue_evicts_oldest_when_cap_is_reached` demonstrates for heights `1..=2` after only 5 insertions with `cap=3` — no fraud, veto, or malicious relayer involved.

		/// Insert a state commitment into the bounded map. ISMP does not allow
		/// duplicate state updates so we don't have an overwrite path.
		///
		/// Appends the height to the per-chain [`StateCommitmentQueue`] and, once
		/// the chain's cap is exceeded, evicts oldest-first from the queue head.
		/// Evictions are limited to [`MAX_COMMITMENT_EVICTIONS_PER_INSERT`] per
		/// call so a lowered cap drains over many insertions rather than in one.
		pub fn insert_bounded_state_commitment(
			height: StateMachineHeight,
			commitment: StateCommitment,
		) {
			let cap = Self::state_machine_commitment_cap(height.id).max(1) as u64;
			let mut state = CommitmentQueueStates::<T>::get(height.id);

			StateCommitmentQueue::<T>::insert(height.id, state.tail, height.height);
			state.tail += 1;

			let excess = (state.tail - state.head)
				.saturating_sub(cap)
				.min(MAX_COMMITMENT_EVICTIONS_PER_INSERT as u64);
			for _ in 0..excess {
				if let Some(old) = StateCommitmentQueue::<T>::take(height.id, state.head) {
					BoundedStateCommitments::<T>::remove(height.id, old);
					BoundedStateMachineUpdateTime::<T>::remove(height.id, old);
				}
				state.head += 1;
			}

			CommitmentQueueStates::<T>::insert(height.id, state);
			BoundedStateCommitments::<T>::insert(height.id, height.height, commitment);
		}

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

#[test]
fn commitment_queue_evicts_oldest_when_cap_is_reached() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 3)]),
		)
		.unwrap();

		for height in 1..=5u64 {
			let at = StateMachineHeight { id, height };
			host.store_state_machine_commitment(at, queue_test_commitment()).unwrap();
			host.store_state_machine_update_time(at, Duration::from_secs(height)).unwrap();
		}

		for height in 1..=2u64 {
			let at = StateMachineHeight { id, height };
			assert!(host.state_machine_commitment(at).is_err());
			assert!(host.state_machine_update_time(at).is_err());
		}
		for height in 3..=5u64 {
			let at = StateMachineHeight { id, height };
			assert!(host.state_machine_commitment(at).is_ok());
			assert!(host.state_machine_update_time(at).is_ok());
		}
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 2, tail: 5 }
		);
	})
}
