## Title
Unvalidated "first OP_RETURN" scan lets an attacker spoof payout attribution via a spurious leading OP_RETURN output - (File: circuits-lib/src/bridge_circuit/mod.rs, core/src/verifier.rs)

## Summary
`get_first_op_return_output` simply returns the first `TxOut` in a transaction whose `script_pubkey.is_op_return()`, with no check that it is the *only* OP_RETURN output or that it appears at any specific position. [1](#0-0)  Both the bridge circuit's `deposit_constant` computation and `core/src/verifier.rs`'s `update_finalized_payouts` rely on this function's output to determine which operator xonly-pubkey funded a payout, so an attacker who controls the outputs of a broadcast `payout_tx` (constrained only by a `SIGHASH_SINGLE|ANYONECANPAY` user signature) can prepend a fake OP_RETURN naming an arbitrary xonly-pubkey.

## Finding Description
The binding this system relies on is: `operator_xonly_pk` parsed by `get_first_op_return_output(payout_tx)` == the xonly-pk of the party who actually funded/broadcast the payout to the withdrawing user.

`get_first_op_return_output` is defined as:
```rust
pub fn get_first_op_return_output(tx: &CircuitTransaction) -> Option<&TxOut> {
    tx.output.iter().find(|out| out.script_pubkey.is_op_return())
}
``` [1](#0-0) 

It is invoked in `bridge_circuit` to derive `operator_xonlypk`, which feeds directly into `deposit_constant` (and therefore the zkVM `journal_hash` that the bridge circuit commits and that is later used to prove/disprove a claim):
```rust
let first_op_return_output = get_first_op_return_output(&input.payout_spv.transaction)
    .expect("Payout transaction must have an OP_RETURN output");
...
let operator_xonlypk: [u8; 32] = parse_op_return_data(&first_op_return_output.script_pubkey)
    .expect("Invalid operator xonlypk")
    .try_into()
    .expect("Invalid xonlypk");

let deposit_constant = deposit_constant(operator_xonlypk, ...);
``` [2](#0-1) 

`core/src/verifier.rs` imports and calls the same `get_first_op_return_output` in `update_finalized_payouts` to determine which operator is credited for a confirmed payout in the verifier's own bookkeeping (per the grep match count of exactly two occurrences — one `use` import, one call site — consistent with reuse of the circuits-lib implementation with no additional index/position validation added on the core side).

Attack flow:
1. A user (who is, per the threat model, an unprivileged attacker) requests a withdrawal via the Citrea Bridge contract, producing a public `WithdrawParams` (withdrawal UTXO, `output_script_pubkey`, `output_amount`, and a `SinglePlusAnyoneCanPay` signature over that single input/output pair).
2. Because the sighash type is `SIGHASH_SINGLE|ANYONECANPAY`, the signature commits *only* to: the signed input's outpoint/value/scriptPubKey/sequence, and the output at the *same index* as that input. It commits to nothing about outputs at other indices, their count, or their order.
3. The attacker (anyone who can broadcast Bitcoin transactions) constructs a `payout_tx` that spends the registered withdrawal UTXO with the valid user signature, places the required output (`output_script_pubkey`/`output_amount`) at the signed input's index so the signature check passes, but inserts an extra, attacker-controlled OP_RETURN output at an earlier index than wherever the true funding operator would place its own attribution OP_RETURN.
4. Once this transaction confirms and is later scanned/proven, both `get_first_op_return_output` call sites blindly pick the attacker's spurious first OP_RETURN and parse its 32-byte push as `operator_xonlypk`, attributing funding of the payout to whatever xonly-pubkey the attacker chose — not the entity that actually funded the user's withdrawal output.

No existing guard prevents this: `SECP.verify_schnorr` only validates the signature under `SinglePlusAnyoneCanPay`, which by design does not commit to the full output set or output ordering; `get_first_op_return_output` has no uniqueness or position check; and there is no cross-check elsewhere in the traced code that the credited xonly-pk corresponds to whichever party's funds actually left an output funding the user.

## Impact Explanation
This breaks the ATTRIBUTION binding used to decide which operator is deemed to have fronted a withdrawal. If `update_finalized_payouts` (verifier bookkeeping) or the bridge-circuit `deposit_constant`/journal attribution feeds into which operator's kickoff/round transaction graph is trusted for reimbursement, an attacker-chosen operator identity can be falsely credited for a payout it never funded — matching the Critical category "an operator reimbursed for a payout it never funded." The attack is repeatable per withdrawal, since every `SinglePlusAnyoneCanPay`-signed withdrawal request is independently malleable in this way, and the root-cause function is shared between the zkVM bridge circuit and the verifier's off-chain accounting, so the blast radius spans all deposits/withdrawals and all operators.

## Likelihood Explanation
Preconditions are minimal and fully within the stated attacker capability set: the attacker only needs to observe/obtain the public withdrawal signature (created by calling `withdraw` themselves, or reusing a public one) and construct/broadcast an alternate `payout_tx` before, or in place of, the legitimate operator's version, paying the ordinary Bitcoin fee. No verifier, operator, or aggregator privilege, key share, or collateral is required. This is directly and repeatably demonstrable with a crafted transaction in a `cargo test`.

## Recommendation
Do not select attribution by "first OP_RETURN found." Require exactly one OP_RETURN output in the payout transaction (reject transactions with more than one), or require the attribution OP_RETURN to be at a fixed, protocol-defined index relative to the withdrawal output (e.g., immediately following the required withdrawal output, or the last output), and enforce that check both in `circuits-lib`'s `get_first_op_return_output`/`bridge_circuit` path and in `core/src/verifier.rs`'s `update_finalized_payouts`.

## Proof of Concept
`cargo test` plan (to be written under a non-excluded location, since `core/src/test/**` is out of scope for this repo's audit rules but the described reproduction target is a unit test against `get_first_op_return_output`/`update_finalized_payouts` logic directly):
1. Build a `CircuitTransaction`/`Transaction` with: input spending the registered withdrawal UTXO, output[0] = attacker's spurious OP_RETURN containing an arbitrary attacker-chosen 32-byte xonly-pk, output[1] = the required `output_script_pubkey`/`output_amount` from `WithdrawParams` at the signed input index, output[2] = the true operator's real OP_RETURN with the legitimate funding operator's xonly-pk.
2. Assert `get_first_op_return_output(&tx)` returns `output[0]` (the attacker's fake OP_RETURN), not `output[2]`.
3. Assert `parse_op_return_data` extracted from that result equals the attacker-chosen pubkey, not the true operator's pubkey — i.e., assert `operator_xonly_pk_recovered != true_funding_operator_xonly_pk` while `operator_xonly_pk_recovered == attacker_chosen_xonly_pk`.
4. If reachable in a unit-test harness, call `update_finalized_payouts` with this transaction and assert the DB/record it writes for the payout stores the attacker-chosen pubkey rather than the true funding operator's, demonstrating the binding `operator_xonly_pk == true funder` is violated both before (true) and after (false) the crafted transaction is processed.
