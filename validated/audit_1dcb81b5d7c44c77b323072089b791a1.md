## Title
Same-chain partial fills can round the released escrow to zero while still consuming fill progress, letting a later filler capture escrow owed to an earlier filler — (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the escrow to release on a partial fill with integer division that can truncate to zero, exactly mirroring the reported `MozStaking.redeem()` pattern: an amount-scaling calculation that can legitimately return zero for a valid, non-zero input, silently consuming state while releasing nothing. Because `_withdraw` skips zero-amount line items without decrementing the escrow ledger, the truncated amount is never subtracted from `_orders`, and it later gets swept in full to whichever filler happens to complete the order.

### Finding Description
In `_fillSameChain`, the proportional escrow released for a partial fill is: [1](#0-0) 

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

When `order.inputs[i].amount * fillAmount < totalRequired`, `escrowedAmount` truncates to `0`. This is entirely plausible whenever the input and output tokens differ in decimals or price ratio (e.g. `inputs[i].amount = 1e6`, `totalRequired = 1e24`) — a filler supplying a legitimate, non-trivial `fillAmount` (well above "dust") can still be rounded down to zero escrow.

Despite `escrowedAmount == 0`:
- `_partialFills[commitment][outputToken]` is already updated to `amountFilled = alreadyFilled + fillAmount` before the escrow is computed [2](#0-1) , permanently advancing fill progress.
- The filler still pays the full `beneficiaryTotal` in output tokens to the beneficiary [3](#0-2) .
- The resulting `TokenInfo{amount: 0}` is passed into `_withdraw`, which explicitly skips zero-amount entries without touching `_orders`: [4](#0-3) 

So the escrow balance for that token is **never decremented** for this fill — it remains available in full. The next filler who completes the order (`amountFilled == totalRequired`) reads `escrowedAmount = _orders[commitment][token]`, i.e. the *entire remaining, undiminished* balance, and receives it — including the share that rightfully belonged to the earlier filler whose contribution rounded to zero. The recommended mitigation in the source report ("revert if the derived amount is zero") is exactly what's missing here: there is no `if (escrowedAmount == 0) revert` guard before consuming `_partialFills` and taking the filler's payment.

### Impact Explanation
An unprivileged filler can lose the input-token entitlement that should correspond to output tokens they legitimately paid to the beneficiary, and that lost value is captured by whichever filler happens to complete the order afterward — not the protocol, not governance, just ordinary fill-order callers. This is a direct "loss of funds" / "wrong beneficiary or amount" outcome on a public, permissionless entrypoint (`fillOrder` → `_fillSameChain`), matching the bounty's fund-loss and logic-attack categories. No malicious relayer, prover, or admin is required — it is triggerable purely through the order's own token-decimal/ratio parameters and multiple ordinary `fillOrder` calls.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: any order pairing a low-decimal/low-unit-price input token against a high-decimal/high-unit-price output token (a routine configuration for cross-token intents) creates a wide truncation window where meaningful `fillAmount` values still round `escrowedAmount` to zero. No privileged setup or race condition is needed — a single filler can even self-trigger this by choosing an unfavorable `fillAmount`, and a second, unrelated filler completing the order automatically absorbs the undecremented balance.

### Recommendation
Before consuming `_partialFills` progress and pulling the filler's payment, compute `escrowedAmount` and revert (or reject the fill) if it is zero for a non-zero `fillAmount`, the same fix accepted for the `MozStaking.redeem()` report. Alternatively, use a rounding scheme (e.g. always round up, or track released/unreleased escrow explicitly per filler) so truncation cannot leave value unaccounted for and later harvested by an unrelated party.

### Proof of Concept
1. Place a same-chain order with `order.inputs[0].amount = 1_000_000` (a 6-decimal token) and `order.output.assets[0].amount = 1_000_000_000_000_000_000_000_000` (a high-decimal output token), no output calldata.
2. Filler A calls `fillOrder` with `options.outputs[0].amount = fillAmount_A` such that `1_000_000 * fillAmount_A < 1_000_000_000_000_000_000_000_000` (e.g. `fillAmount_A = 1e20`, i.e. 10% of `totalRequired`) — a normal, non-dust partial fill.
   - `_partialFills[commitment][outputToken]` advances to `fillAmount_A`.
   - `escrowedAmount = (1_000_000 * 1e20) / 1e24 = 0` due to truncation.
   - Filler A pays `fillAmount_A` in output tokens to the beneficiary and receives `0` escrowed input tokens. `_orders[commitment][inputToken]` is untouched (still `1_000_000`).
3. Filler B calls `fillOrder` with the remaining `fillAmount_B = totalRequired - fillAmount_A`, completing the order.
   - `amountFilled == totalRequired`, so `escrowedAmount = _orders[commitment][inputToken] = 1_000_000` — the *full* original escrow, even though Filler A already contributed 10% of the output payment.
4. Filler B receives all `1_000_000` input tokens for paying only 90% of `totalRequired`; Filler A's 10% payment yielded nothing. The escrow that should have been split 10/90 between A and B is entirely captured by B.
