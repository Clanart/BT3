## Analysis

The report's core broken invariant: an external round/epoch counter that the codebase assumes increments by exactly 1, but which can legitimately jump by more than 1 (Chainlink's `phaseId` bump shifts `roundId` by `2**64`). Code that derives "the previous round" from the latest counter value then permanently misses the skipped values, causing state that is never retrievable through the normal path (DoS in the original report).

The direct local analog is in Hyperbridge's **outbound consensus delivery reward** attribution, which layers the same "assume +1" logic on top of BEEFY authority-set rotation.

**How the rotation can jump by more than 1:** `EcdsaBeefy.verifyMmrUpdateProof` / `SP1Beefy.verifyConsensus` perform only a single-step rotation per consensus update, regardless of how far the submitted MMR leaf's `nextAuthoritySet.id` has advanced beyond the client's currently tracked `nextAuthoritySet.id`: [1](#0-0) 

If the relay chain has advanced through several session/epoch changes between two consensus submissions to Hyperbridge (e.g. relayers are offline or catching up), the latest available leaf's `nextAuthoritySet.id` can be many greater than the trusted state's `nextAuthoritySet.id`. `currentAuthoritySet` <- old `nextAuthoritySet`, `nextAuthoritySet` <- new leaf value: every id strictly between the old and new `nextAuthoritySet.id` is skipped and never becomes "current" or "next" in the light client at all.

**How that gap propagates to reward accounting:** `HandlerV2.handleConsensus` derives the "just-ended" epoch purely by subtracting 1 from whatever `nextAuthoritySetId` the verifier returns, and only guards against going backwards, not against skipping forward: [2](#0-1) 

`EvmHost.recordEpoch` then writes exactly one `_epochs[epoch]` slot per call and permanently forecloses any lower id: [3](#0-2) 

Because `_currentEpoch` is monotonically advanced to the *post-jump* epoch value in a single call, every intermediate epoch id between the old and new value gets `_epochs[id] == address(0)` forever — `authoritySetId <= _currentEpoch` will always be true for them from that point on, so no future call can ever populate them.

**Where this becomes a fund-loss issue:** the reward pallet's whole claim mechanism is keyed off `EvmHost._epochs[set_id]`: [4](#0-3) 

For every skipped `set_id` in the gap, `decode_epochs_slot_address` will always resolve to `address(0)` / `None`, so `process_outbound_consensus_delivery_claim` will always fail with `OutboundDeliveryNotProven`: [5](#0-4) 

The `OutboundConsensusDeliveryReward` configured for that destination is thus permanently unclaimable for every skipped epoch — not merely delayed, but foreclosed forever, since `_currentEpoch` never revisits a lower value and there is no mechanism to backfill `_epochs[id]` for ids strictly less than `_currentEpoch`.

### Title
Authority-set epoch jumps in BEEFY rotation permanently orphan skipped `EvmHost._epochs[id]` slots, foreclosing `OutboundConsensusDeliveryReward` forever - ([File: evm/src/core/HandlerV2.sol])

### Summary
`HandlerV2.handleConsensus` attributes relayer credit for BEEFY authority-set rotations by computing `epoch = nextAuthoritySetId - 1` and writing a single `EvmHost._epochs[epoch]` slot. But the BEEFY consensus clients (`EcdsaBeefy`, `SP1Beefy`) perform only a single-step rotation per proof no matter how many authority-set ids the relay chain actually advanced through since the last update. Every authority-set id strictly between the previous and new `nextAuthoritySet.id` is skipped, `EvmHost._currentEpoch` jumps straight past them, and `_epochs[id]` for those ids can never be set again (`authoritySetId <= _currentEpoch` is enforced permanently). Any legitimate `claim_outbound_consensus_delivery_reward` for those skipped `set_id`s will always fail proof verification (`_epochs[set_id]` decodes to the zero address), so the configured `OutboundConsensusDeliveryReward` for those epochs is permanently unclaimable by anyone.

### Finding Description
- `EcdsaBeefy.verifyMmrUpdateProof` / `SP1Beefy.verifyConsensus` rotate `currentAuthoritySet <- nextAuthoritySet`, `nextAuthoritySet <- leaf.nextAuthoritySet` in one step per proof, regardless of the numeric gap between the old and new `nextAuthoritySet.id` [1](#0-0) .
- `HandlerV2.handleConsensus` blindly computes `epoch = nextAuthoritySetId - 1` from whatever id the verifier returns and calls `recordEpoch(epoch, relayer)` [2](#0-1) .
- `EvmHost.recordEpoch` only guards against non-increasing ids (`authoritySetId <= _currentEpoch`) — it has no notion of "gap" and cannot backfill lower, skipped ids once `_currentEpoch` has advanced past them [6](#0-5) .
- The reward-claim pallet trusts `_epochs[set_id]` as the sole source of truth for who delivered a given rotation, and rejects the claim outright if the slot is empty [5](#0-4) .

This is the structural analog of the Chainlink `phaseId`/`roundId` bug: an external counter (authority set id) is assumed to advance one step at a time for indexing purposes ("the previous id" derived by subtracting one from the latest id), but the real underlying system can legitimately leap several steps in a single update, permanently orphaning the skipped indices in code that never re-checks or backfills them.

### Impact Explanation
Every authority-set id skipped by a "catch-up" BEEFY consensus update becomes permanently unattributable: `_epochs[id]` stays `address(0)` forever, and the governance-configured `OutboundConsensusDeliveryReward` for that destination cannot be claimed for those epochs by anyone — not the relayer who submitted the catch-up proof (who is credited only for the final, non-skipped epoch), and not any other relayer (no on-chain evidence of a real deliverer for the skipped ids even exists). This is a permanent, non-recoverable loss of intended relayer compensation, silently triggered any time the relayer network falls behind by more than one authority-set rotation before the next consensus update lands — a routine liveness condition, not an attack requiring a malicious actor.

### Likelihood Explanation
High under ordinary operating conditions: BEEFY epoch rotations occur every relay-chain session, and any period where Hyperbridge's light client for a given EVM destination misses more than one rotation before the next update (relayer downtime, backpressure, fee-driven throttling, etc.) triggers this gap deterministically. No malicious relayer, prover, or governance action is required — a single normal "catch-up" consensus submission after a delay is sufficient.

### Recommendation
Do not derive epoch attribution solely from `nextAuthoritySetId - 1`. Either:
1. Return the full range of authority-set ids traversed by a single consensus proof from the verifier (e.g., `(oldNextAuthoritySetId, newNextAuthoritySetId)`), and have `handleConsensus` record every intermediate id (not just the last one) attributed to the delivering relayer, or
2. Change `EvmHost.recordEpoch`/`_currentEpoch` semantics so that skipped ids can still be later proven/backfilled (e.g., track a "claimable range" rather than a single monotonic pointer), or
3. At minimum, emit an event/flag when a jump `> 1` occurs so the reward pallet or governance can compensate the gap out of band instead of silently losing it forever.

### Proof of Concept
1. Deploy `EvmHost` + `HandlerV2` + `EcdsaBeefy` for a destination chain; initialize `BeefyConsensusState` with `currentAuthoritySet.id = 4`, `nextAuthoritySet.id = 5`.
2. Governance sets `OutboundConsensusDeliveryReward[destination] = R` on Hyperbridge.
3. Simulate relayer downtime: on the relay chain, let 5 session rotations occur (ids 5→6→7→8→9→10) with no intervening consensus proof submitted to the EVM destination.
4. Submit a single BEEFY consensus proof carrying the latest MMR leaf, whose `nextAuthoritySet.id == 10`.
   - `verifyMmrUpdateProof` sets `currentAuthoritySet.id = 5`, `nextAuthoritySet.id = 10` in one step [1](#0-0) .
   - `handleConsensus` computes `epoch = 10 - 1 = 9`, calls `recordEpoch(9, relayer)` → `_currentEpoch = 9`, `_epochs[9] = relayer` [2](#0-1) .
5. Any relayer (including the honest one who actually processed rotation 6, 7, or 8 off-chain via BEEFY prover state) attempts `claim_outbound_consensus_delivery_reward` with `set_id = 6` (or 7, 8): `EvmHost._epochs[6]` decodes to the zero address (never written, and `recordEpoch(6, …)` will now always no-op since `6 <= _currentEpoch(9)`), so the claim reverts with `OutboundDeliveryNotProven` [5](#0-4) , permanently and irrecoverably, for the lifetime of the contract.

    /**
     * @dev Record the relayer that first submitted a consensus proof for a new authority set epoch.
     * Only callable by the configured handler. Stale or duplicate epoch IDs are ignored.
     * @param authoritySetId the new authority set / epoch ID
     * @param relayer the relayer that delivered the consensus proof
     */
    function recordEpoch(uint256 authoritySetId, address relayer) external restrict(_hostParams.handler) {
        if (authoritySetId <= _currentEpoch) return;
        _currentEpoch = authoritySetId;
        _epochs[authoritySetId] = relayer;
        emit NewEpoch({authoritySetId: authoritySetId, relayer: relayer});
    }
