### Title
Taking an offer can silently lock CR-CAT funds to `authorized_providers` the recipient has no Verified Credential for, permanently freezing the received assets - (File: `chia/wallet/vc_wallet/vc_wallet.py`)

### Summary
When a wallet takes an offer that delivers Credential-Restricted CATs (CR-CATs), `VCWallet.add_vc_authorization` approves any CR-CAT output that is "coming to us" purely by checking that the destination puzzle hash belongs to one of our wallets — it never checks that we actually hold a Verified Credential (VC) issued by one of that asset's `authorized_providers`. Because every future CR-CAT spend (including simply melting/moving the coins) requires a VC from one of the curried-in `authorized_providers`, a taker can end up owning CR-CAT coins that are permanently unspendable if they don't (and can never) obtain a VC from those specific providers.

### Finding Description
`CRCAT` puzzles curry in an `authorized_providers` list and a `proofs_checker` at mint time via `construct_cr_layer`, and this data becomes part of the coin's puzzle hash/identity forever [1](#0-0) . Note that "it's coming to us" is satisfied merely because `get_wallet_identifier_for_puzzle_hash` recognizes the destination inner puzzle hash as belonging to one of our wallets — there is no check that we hold, or can ever obtain, a VC issued by `crcat_spend.crcat.authorized_providers`. This same gap exists in `check_for_requested_payment_modifications`, which validates VC availability only for the *maker* requesting CR-CATs, not for CR-CATs a *taker* passively receives as change or as the traded asset [6](#0-5) .

As a result, a taker's wallet will happily accept and record ownership of CR-CAT coins whose `authorized_providers` reference DIDs the taker has no relationship with. The coin shows up as "pending approval"/spendable balance in the wallet, but any subsequent attempt to move, melt, or claim it will fail forever, since `_generate_unsigned_spendbundle` and `claim_pending_approval_balance` both hard-require a VC matching those specific providers [7](#0-6) .

This mirrors the reported bug class precisely: just as `PrivateChainBridge::lockTokens` let users lock funds against a `DestinationChain` enum value that had no configured chain ID (permanently stranding funds with zero on-chain validation), the Chia wallet lets a taker accept CR-CAT value against an `authorized_providers` set for which they hold no configured VC, with no pre-acceptance validation to prevent it.

### Impact Explanation
Funds received via an offer as CR-CATs can become permanently unspendable if the recipient never holds (or cannot obtain) a VC from any of the coin's `authorized_providers`. Since CR-CAT credential providers are typically controlled by a specific issuer/DID chosen by the asset's original minter, a counterparty offering such assets in a trade can cause the taker to receive value that the taker's wallet will never be able to move — a real loss of funds with no remediation path other than obtaining an out-of-band VC from the correct issuer (which may not be possible for an adversarial or defunct provider).

### Likelihood Explanation
Any wallet user who takes an offer that includes CR-CAT payments is exposed; no malicious peer, node, or privileged access is required — an ordinary offer counterparty can construct an offer whose CR-CAT `authorized_providers` list points to a DID the taker cannot get proofs from, and the taker's own wallet code approves the swap without warning or blocking it.

### Recommendation
Before `VCWallet.add_vc_authorization` (or the offer-taking flow more generally) approves a CR-CAT output that is "coming to us," verify that the receiving wallet already holds, or can plausibly obtain, a VC issued by one of that CR-CAT's `authorized_providers` (e.g., by calling the same `get_vc_with_provider_in_and_proofs`/`store.get_vc_records_by_providers` check used elsewhere) and reject/warn on the trade if not, mirroring the existing check already performed for the maker in `check_for_requested_payment_modifications`.

### Proof of Concept
1. Maker mints a CR-CAT with `authorized_providers = [some_did_taker_has_no_vc_for]` (as in `mint_cr_cat`/`CRCATWallet.get_or_create_wallet_for_cat`) [8](#0-7) .
2. Maker creates an offer sending these CR-CATs to the taker in exchange for XCH/other assets.
3. Taker's wallet calls `check_for_final_modifications` → `VCWallet.add_vc_authorization`, which approves the incoming CR-CAT purely because the destination puzzle hash resolves to the taker's own wallet, without checking VC compatibility [9](#0-8) .
4. Trade completes; taker now owns CR-CAT coins.
5. Taker attempts to spend/claim these coins; `CRCATWallet._generate_unsigned_spendbundle` raises `RuntimeError("CR-CATs cannot be spent without an appropriate VC")` because the taker has no VC issued by `some_did_taker_has_no_vc_for` [2](#0-1) , and can never obtain one if that DID is unreachable/adversarial — funds are permanently stuck.

def construct_cr_layer(
    authorized_providers: list[bytes32],
    proofs_checker: Program,
    inner_puzzle: Program,
) -> Program:
    first_curry: Program = CREDENTIAL_RESTRICTION.curry(
        CREDENTIAL_STRUCT,
        authorized_providers,
        proofs_checker,
    )
    return first_curry.curry(first_curry.get_tree_hash(), inner_puzzle)
