### Title
Uncaught crash from unchecked `checkRun.app` dereference when processing malformed GitHub Check Run API responses - (File: app/src/lib/ci-checks/ci-checks.ts)

### Summary
`apiCheckRunToRefCheck` unconditionally accesses `checkRun.app.name` and `checkRun.check_suite.id` when converting a GitHub Checks API check-run object into Desktop's internal `IRefCheck` model, with no null-check on `app` or `check_suite`, mirroring the deposit-transaction bug where `dec.Gas` was dereferenced without a nil check.

### Finding Description
`apiCheckRunToRefCheck(checkRun: IAPIRefCheckRun)` builds an `IRefCheck` by reading `checkRun.app.name` and `checkRun.check_suite.id` directly: [1](#0-0) 

The GitHub Checks API documents `app` as nullable (a check run's associated GitHub App can be `null`, e.g. for check runs created by certain integrations, deleted apps, or third-party/GHES-compatible services). `checkRun` objects originate from the network response of `fetchRefCheckRuns`/similar API calls in `app/src/lib/api.ts`, which are simply JSON-deserialized (`parsedResponse<T>`) without runtime shape validation — the TypeScript interface `IAPIRefCheckRun` is a compile-time-only assumption, not enforced at runtime. Any GHES server, a MITM proxy on an HTTP(S) connection, or a compromised/malicious GitHub-compatible endpoint that Desktop is configured to talk to can therefore return a check-run object where `app` is `null` (or omitted), causing `checkRun.app.name` to throw a `TypeError: Cannot read properties of null (reading 'name')`.

Unlike several other API accessors in `api.ts` that wrap `parsedResponse` calls in `try/catch` and degrade gracefully (e.g. `fetchProtectedBranches`, `fetchAllRepoRulesets`), `apiCheckRunToRefCheck` itself contains no defensive check, and its callers (`commit-status-store.ts`, `notifications-store.ts`) invoke it while mapping arrays of check runs — a single malformed entry in the array will throw synchronously and propagate up through the caller's call stack.

### Impact Explanation
This function is invoked from `commit-status-store.ts` and `notifications-store.ts` while refreshing commit statuses / CI check results, a background/periodic process that runs automatically for any repository with GitHub Enterprise/GitHub.com metadata. An uncaught `TypeError` thrown mid-mapping in the renderer process can crash the status refresh pathway and, depending on how far up the stack it propagates, disrupt in-progress UI state (commit status polling, PR checks notifications) — a denial-of-service against Desktop's CI status/notifications feature triggered purely by a malicious or compromised server response, without any local access, credentials, or user action beyond having added the account/repository.

### Likelihood Explanation
Likelihood is moderate: it requires a network response (from a GHES instance, a malicious/compromised endpoint, or a MITM position) containing a check run with `app: null`, which is a real, spec-permitted GitHub Checks API value (not merely a contrived malformed field), making this more likely to occur naturally than a fully invalid JSON payload.

### Recommendation
Add a defensive null check before dereferencing `checkRun.app` and `checkRun.check_suite` in `apiCheckRunToRefCheck`, e.g.:
```ts
appName: checkRun.app?.name ?? '',
checkSuiteId: checkRun.check_suite?.id ?? null,
```
and audit other direct property accesses on API-response-typed objects (`IAPIRefCheckRun`, `IAPIWorkflowRun`, etc.) throughout `ci-checks.ts` and its callers for the same unguarded-dereference pattern.
