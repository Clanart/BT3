### Title
Duplicate Citrea withdrawal registrations sharing one on-chain payout UTXO let an operator be reimbursed twice for a single fronted payout - ([File: circuits-lib/src/bridge_circuit/storage_proof.rs])

### Summary
`verify_storage_proofs` (circuits-lib/src/bridge_circuit/storage_proof.rs:44-133) only checks that the `(txid, vout)` read from the contract at `storage_proof.index` matches a valid Merkle/JMT proof against the committed `state_root`; it never checks that this `(txid, vout)` pair is unique across withdrawal/deposit indices. Because a withdrawing user (an unprivileged Citrea/Bitcoin actor) chooses the raw bytes of the withdrawal outpoint when calling the Bridge contract's `withdraw()` (see `core/src/test/withdraw.rs:133-138`, `core/src/citrea.rs:458-496`), the same physical Bitcoin outpoint can legitimately be registered by the attacker at two different Citrea withdrawal indices, each tied to a different deposit's `move_txid` (`DEPOSIT_STORAGE_INDEX` array keyed by the same `index`). A single Bitcoin payout transaction that spends that outpoint then satisfies `verify_storage_proofs`/`bridge_circuit` for **both** indices, producing two independently valid bridge-circuit journals/`deposit_constant`s pointing at two different deposits' presigned kickoff graphs, while only one payout ever occurred on Bitcoin L1.

### Finding Description
The binding this circuit is supposed to enforce is: *for withdrawal index i, the payout owed equals exactly one on-chain payout transaction that specifically fronts index i's registered withdrawal UTXO, counted once*. In code:

- `verify_storage_proofs(storage_proof, state_root)` (circuits-lib/src/bridge_circuit/storage_proof.rs:44-133) derives `wd_outpoint`/`vout` purely from `storage_proof.index` via `storage_address + index*2` / `index*2+1`, and `move_txid` from `storage_address_deposit + index`. It only validates the JMT storage proof (`storage_verify`) — it does **not** check that `(wd_outpoint, vout)` hasn't already been consumed by a different index's claim.
- `bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs:182-204) then only checks that the SPV-proved payout transaction's referenced input (`payout_input_index`) matches this index's `(wd_outpoint, vout)` — again with no cross-index uniqueness check.
- `deposit_constant`/`journal_hash` (circuits-lib/src/bridge_circuit/mod.rs:634-684) bind the claim to a specific deposit (`move_txid`) and kickoff (`round_txid`, `kickoff_round_vout`), but nothing binds the *payout transaction itself* to only one deposit.

The root cause is that the on-chain source of truth for "which UTXO funds withdrawal index i" (`withdrawalUTXOs[i]` on the Citrea Bridge contract) is populated with attacker-chosen bytes at `withdraw()` time (`core/src/citrea.rs:458-496`, `core/src/test/withdraw.rs:133-138`), and no code in this repo (neither `verify_storage_proofs`, nor `Operator::withdraw` at core/src/operator.rs:560-627, nor the verifier DB join `get_payout_txs_for_withdrawal_utxos` at core/src/database/verifier.rs:170-196) enforces that a given `(txid, vout)` pair can only be registered/consumed for a single withdrawal index.

Exploit flow:
1. Attacker deposits twice, obtaining deposit N and deposit M (each entitled to `bridge_amount`).
2. Attacker owns Bitcoin UTXO_A. They call Citrea `withdraw(UTXO_A.txid, UTXO_A.vout)` registering withdrawal index N with UTXO_A, and separately call `withdraw(UTXO_A.txid, UTXO_A.vout)` again registering withdrawal index M with the same UTXO_A.
3. An operator (honest) receives the withdrawal request for index N, verifies `in_outpoint == withdrawal_utxo` from Citrea (core/src/operator.rs:589-596), fronts payout transaction P spending UTXO_A once.
4. Off-chain bookkeeping (`get_payout_txs_for_withdrawal_utxos`, core/src/database/verifier.rs:170-196) joins `bitcoin_syncer_spent_utxos` on `(txid, vout)` against the `withdrawals` table; because both index N and index M rows store the identical `(UTXO_A.txid, UTXO_A.vout)`, this query (and the corresponding storage-proof-based `bridge_circuit` verification for index M) resolves payout tx P as the fronting payout for index M as well.
5. The operator submits/gets validated Reimburse claims for both deposit N's and deposit M's presigned kickoff graphs, each backed by an independently valid `bridge_circuit` journal (different `deposit_constant` per deposit, same underlying payout SPV proof), each entitling the operator to reimbursement from that deposit's move-to-vault UTXO.

Existing guards (`Verifier::is_deposit_valid`, `Operator::is_profitable`, `SECP.verify_schnorr`, `SPV::verify`, `lc_proof_verifier`) all pass because each individual check operates only within the scope of a single index/deposit and never cross-references other indices' recorded outpoints.

### Impact Explanation
Two different deposits' move-to-vault UTXOs get released to reimburse the operator, while only one payout transaction (fronting one withdrawal's worth of BTC) ever left the operator's wallet. This is "an operator reimbursed for a payout it never funded" (Critical) for the second deposit — its withdrawing party (which is the same attacker, so no honest user directly loses BTC in this specific narrow instantiation, but any honest operator processing these claims is drained of collateral/UTXOs disproportionate to what they actually fronted, and if the two colliding indices belonged to two different withdrawing users, one of them would simply never receive their payout while the operator still gets reimbursed for both). This is repeatable for every pair of deposits an attacker can register with a duplicated outpoint, scaling the blast radius across all deposits/operators that process the corresponding withdrawal indices.

### Likelihood Explanation
Preconditions: the attacker must be able to make two deposits (paying `bridge_amount` twice) and call Citrea's `withdraw()` twice with an identical, attacker-controlled outpoint — both actions are explicitly enumerated as available to an unprivileged attacker. No verifier/operator/aggregator privilege, key compromise, or majority hashrate is needed. The cost is bounded by the price of making the extra deposit(s) (recoverable if the attack succeeds since the double reimbursement compensates the second deposit's cost). This is feasible and repeatable across any number of deposit pairs, limited only by the requirement that the Citrea Bridge contract does not itself reject duplicate `(txid, vout)` withdrawal registrations across indices (a Solidity-level design choice not enforced anywhere in this repository).

### Recommendation
In `verify_storage_proofs`/`bridge_circuit`, or in the operator/verifier off-chain tracking (`get_payout_txs_for_withdrawal_utxos`, `Operator::withdraw`), enforce a one-to-one binding between a spent payout outpoint and a single withdrawal/deposit index — e.g., persist and check a uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table (or reject a second Reimburse/kickoff claim once a given payout txid has already been credited to one deposit), and additionally include the withdrawal `index` (not just `move_txid`) inside `deposit_constant`/`journal_hash` so that the committed journal cannot be reused to satisfy a second index's claim.

### Proof of Concept
```rust
// circuits-lib/src/bridge_circuit/storage_proof.rs (new test)
#[test]
fn test_two_indices_same_outpoint_both_pass() {
    // Construct StorageProof A with index = N, whose storage_proof_utxo/vout resolve
    // (via storage_key_utxo = storage_address + N*2, storage_key_vout = storage_address + N*2+1)
    // to (UTXO_A.txid, UTXO_A.vout), and storage_proof_deposit_txid resolving to move_txid_N.
    let sp_n = StorageProof { index: N, /* proofs crafted at slots N*2, N*2+1, and deposit slot N */ ... };

    // Construct StorageProof B with index = M (M != N), whose storage_proof_utxo/vout
    // resolve (via slots M*2, M*2+1) to the SAME (UTXO_A.txid, UTXO_A.vout),
    // and storage_proof_deposit_txid resolving to a DIFFERENT move_txid_M.
    let sp_m = StorageProof { index: M, /* proofs crafted at slots M*2, M*2+1 = same UTXO_A value, deposit slot M */ ... };

    let (wd_outpoint_n, vout_n, move_txid_n) = verify_storage_proofs(&sp_n, state_root);
    let (wd_outpoint_m, vout_m, move_txid_m) = verify_storage_proofs(&sp_m, state_root);

    // Binding under test: two distinct withdrawal indices should not both resolve
    // to the same funding outpoint from a single payout.
    assert_eq!(*wd_outpoint_n, *wd_outpoint_m, "same payout outpoint claimed by two indices");
    assert_eq!(vout_n, vout_m);
    assert_ne!(*move_txid_n, *move_txid_m, "but they belong to two different deposits");
    // -> demonstrates a single payout tx (spending wd_outpoint_n == wd_outpoint_m)
    //    would independently satisfy bridge_circuit's checks for BOTH deposit N and deposit M,
    //    yielding two valid, distinct journal_hash/deposit_constant outputs from one payout.
}
```
Running this against `cargo test -p circuits-lib test_two_indices_same_outpoint_both_pass` (crafting the two `StorageProof`s from a real JMT tree with slots N and M pointing at the same UTXO value, following the pattern of the existing `test_verify_storage_proofs` fixture) shows both calls succeed and yield differing `move_txid`, confirming the double-counting is possible with no additional guard in this code path.
