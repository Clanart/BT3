## Title
Attacker-controlled `meta.sender` can permanently block batched POST/GET-timeout processing for unrelated users via a reverting fee refund — `dispatchTimeOut` (File: `evm/src/core/EvmHost.sol`)

## Summary
`EvmHost.dispatchTimeOut` (both the `PostRequestTimeout` and `GetRequestTimeout` overloads) pushes the refunded relayer fee directly to `meta.sender` — the original requester, an address fully chosen by whoever dispatched the timed-out request — with a plain `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` call that is not isolated from the rest of the batch. `HandlerV2.handlePostRequestTimeouts` / `handleGetRequestTimeouts` iterate over an array of independent, unrelated timeouts and call `host.dispatchTimeOut(...)` for each one in a plain loop with no per-item try/catch, and the whole call can additionally be folded into `HandlerV2.batchCall`, which is explicitly atomic ("if any call fails, the entire batch reverts"). This reproduces the exact structural bug from the referenced NFTLoanFacilitator report: an attacker who is the ultimate recipient of a pushed token transfer inside a shared multi-party transaction can revert that transfer on demand and thereby revert everyone else's legitimate operation bundled in the same call.

## Finding Description
`dispatchTimeOut` deletes the request commitment for replay protection, invokes the destination app's `onPostRequestTimeout`/`onGetTimeout` hook, and — importantly — the app-hook failure path is defensively guarded (restores `_requestCommitments[commitment] = meta` on failure "so that it can be retried"), but the **fee-refund transfer that follows a successful app callback is not guarded at all**: [1](#0-0) 

Contrast this with `dispatchIncoming` for POST requests, which deliberately wraps the destination call in a low-level `.call` and treats failure as a no-op/retry rather than reverting the batch: [2](#0-1) 

That defensive pattern (catch failures so one bad actor can't sink the whole batch) is applied to the *app callback* but not to the *fee transfer*. `HandlerV2.handlePostRequestTimeouts` loops over an arbitrary batch of unrelated timed-out requests and calls `dispatchTimeOut` directly, unguarded, per item: [3](#0-2) 

This handler call can itself be included in `IHandlerV2.batchCall`, which is atomic by design — "any failure reverts the entire batch": [4](#0-3) 

`meta.sender` is the value stored in `_requestCommitments[commitment]` at the time the original request was dispatched — fully attacker-controlled, since anyone can dispatch a POST/GET request paying an arbitrary fee and naming themselves (or any contract they deploy) as `payer`/`sender`. If `feeToken()` is an ERC-777-compatible token (or any token whose transfer triggers recipient-side code, e.g., via ERC-1363-style hooks wired to `transfer`), the attacker's contract can implement a hook that inspects on-chain state (e.g., whether other unrelated commitments in the same batch have already been processed) and reverts precisely when it wants to sabotage a shared batch, exactly as described in the source report's `_callTokensReceived` manipulation.

This is the identical primitive as the source finding: a party who is due to *receive* a pushed token transfer as a side effect of someone else's transaction can weaponize a transfer-triggered callback to revert the shared transaction, blocking unrelated participants (in this case, every other request's timeout being processed together in the same `handlePostRequestTimeouts`/`batchCall` invocation) from ever settling through that path.

## Impact Explanation
This falls squarely under "transaction manipulation / logic attacks" and "request/response/timeout paths must bind ... one-time receipt handling" from the bounty scope: an unprivileged attacker can force other users' legitimate `PostRequestTimeout`/`GetRequestTimeout` deliveries to permanently fail whenever a relayer batches them together with the attacker's poisoned timeout, since the relayer has no way to selectively drop just the attacker's item without resubmitting the entire remaining batch, and any resubmission that still contains the attacker's timeout will fail again. In the worst case this can be used to indefinitely delay refunds/timeout notifications for other users' requests bundled in the same delivery, and — combined with the commitment-restore-on-hook-failure logic already present for the app callback but *not* present after a successful callback — can leave `_requestCommitments[commitment]` deleted for the attacker's own request (since `delete` happens up front and is only restored if the *app-hook* call fails, not if the later fee transfer fails) while the transaction as a whole still reverts, since a revert unwinds all state changes made in that call including the `delete`. Practically the primary damage is repeated, attacker-triggered denial of settlement for other users' bundled requests, which matches the Medium-severity classification the original report ultimately received (no direct fund loss, but forced default/DoS of a shared settlement path).

## Likelihood Explanation
The attack requires the fee token configured via `feeToken()` to be an ERC-777 (or otherwise hook-triggering) token; if the deployed fee token is a standard, non-hooked ERC-20 (as is typical for stablecoins), a plain `transfer()` call cannot execute attacker code and this path is not exploitable. I was not able to locate an explicit restriction in `EvmHost.sol` preventing governance from configuring an ERC-777-style `feeToken` (unlike `StreamingYieldVault`, which the codebase documentation explicitly warns must use a "standard ERC-20 ... without automatic transfer callbacks"). Given this repo has no comparable guard or documentation warning on the ISMP host's `feeToken`, and the exact push-transfer-to-attacker-controlled-address-inside-shared-batch pattern reproduces the source report's root cause precisely, this is a locally provable structural analog, though its real-world triggerability depends on the specific fee-token deployment choice, which I could not fully verify from the available index (some `HostParams`/token-registration code may be outside what was indexed).

## Recommendation
Isolate the fee-refund transfer from the batch's atomicity the same way the app-hook call is isolated: wrap `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` in a try/catch (or a low-level `.call`) and, on failure, credit the fee to a claimable/pull-based balance for `meta.sender` instead of reverting the enclosing `dispatchTimeOut`/batch call. This converts the push transfer into a pull-based redemption pattern (mirroring the mitigation recommended in the original report) and prevents one attacker-controlled `meta.sender` from being able to sabotage other unrelated requests' timeout processing when batched together.

## Proof of Concept
1. Attacker deploys a custom ERC-777-compatible token or otherwise arranges for `feeToken()` to be a hook-triggering token (precondition: governance has configured such a token as the ISMP host's fee token).
2. Attacker dispatches a POST request from their own contract, paying a fee, so that `_requestCommitments[commitment] = FeeMetadata { sender: attackerContract, fee: X }` is recorded.
3. Attacker lets the request time out (never delivers it to the destination, or it's rejected there).
4. A relayer collects several unrelated users' timed-out requests plus the attacker's timed-out request into a single `PostRequestTimeoutMessage` (or wraps `handlePostRequestTimeouts` inside `HandlerV2.batchCall` along with other handler calls) and submits it.
5. `HandlerV2.handlePostRequestTimeouts` iterates the timeouts; for each it calls `host.dispatchTimeOut(...)`. For the attacker's entry, the app callback (`onPostRequestTimeout`) succeeds, then `IERC20(feeToken()).safeTransfer(attackerContract, X)` triggers the attacker's `tokensReceived` hook, which the attacker programs to always `revert()`.
6. Because there is no try/catch around this transfer and (if used) `batchCall` is atomic, the entire transaction reverts — the other unrelated users' timeouts in the same batch are never processed, and the relayer must retry, only to have the attacker repeat the same sabotage on every subsequent batch that includes their poisoned commitment.     function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});

     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
