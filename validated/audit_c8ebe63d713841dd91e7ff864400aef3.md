## Title
Stale manual conflict resolutions ("ours"/"theirs") from a prior merge/rebase are silently reused for a new, unrelated merge/rebase against attacker-controlled refs, causing wrong content to be auto-staged and committed - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
In the SecondSwap report, `SecondSwap_StepVesting` copies a stale `stepsClaimed` value into a brand-new listing whenever the destination bucket looks "empty" (`totalAmount == 0`), instead of verifying that the incoming allocation actually corresponds to the same underlying position. This causes state from one allocation to be silently inherited by an unrelated one, corrupting how much a buyer can claim.

`updateConflictState` in Desktop's `changes-state.ts` has the same broken-invariant shape: it carries `manualResolutions` (a path → `ours`/`theirs` map) forward from `prevConflictState` into the freshly computed `newConflictState` based only on whether a `prevConflictState` object of a matching *kind* (`merge`/`rebase`/`cherryPick`) currently exists - it never verifies that the new conflict is the *same* operation (same `currentTip`/base commit) as the one the resolutions were recorded against.

### Finding Description
`updateConflictState` computes the resolutions map before it even knows what the new conflict looks like: [1](#0-0) 

`getConflictState` then attaches this possibly-stale map to the new state purely by kind, with no identity check against the actual git object graph (commit/branch) that produced it: [2](#0-1) 

The only place a mismatch is even detected is `performEffectsForMergeStateChange`/`performEffectsForRebaseStateChange`, and that check exists solely to increment telemetry counters (`mergeAbortedAfterConflictsCount`, etc.) - it explicitly does **not** clear `manualResolutions`: [3](#0-2) 

Once carried forward, these resolutions are trusted as authoritative decisions by the rest of the app:
- `_updateManualConflictResolution` merges into the existing map without any tie to the specific merge/rebase attempt that produced it: [4](#0-3) 
- `stageManualConflictResolution` executes `git checkout --ours/--theirs` and stages the file based purely on the resolution value, with no verification that the conflict is the one the user actually reviewed: [5](#0-4) 
- The conflicts dialog computes "resolved" vs "conflicted" counts directly from this map and lets the user commit once `conflictedFiles.length === 0`, hiding files whose resolution was inherited rather than freshly chosen: [6](#0-5) 

**Attacker path:** a user aborts (or the tool detects as aborted) a merge/rebase against branch `B` after manually picking `ours`/`theirs` for a set of paths. The user then starts a *new* merge/rebase into a branch also named `B` (e.g., because a remote/proxy served an updated ref, or the attacker force-pushed `B` to a different commit, or a fetched/cloned repo already ships a `B` whose tip differs from what was previously resolved against). `getConflictState` only compares `currentBranch`/`currentTip` for telemetry purposes; the `manualResolutions` map keyed by file **path** is reused verbatim for the new conflict. If the new commit graph reintroduces conflicts on the same paths but with materially different (attacker-controlled) content, Desktop treats those paths as already resolved and will `git checkout --ours/--theirs` + stage them without ever presenting them to the user in the conflicts dialog.

### Impact Explanation
This corrupts the exact value the SecondSwap bug corrupts: not "what the user is shown" but "what actually gets committed/pushed." A path that the user resolved in a prior, unrelated merge attempt can be auto-resolved and staged with content dictated by whichever side ("theirs") is attacker-influenced (a remote branch, a fetched ref, or a repo cloned from an untrusted source), without the user ever reviewing the new diff for that file. This is a silent-corruption-of-what-the-user-commits bug class, matching the report's impact category, reachable purely by normal use of Desktop against attacker-controlled remotes/refs - no local access, admin rights, or prior compromise needed.

### Likelihood Explanation
Requires a realistic but non-trivial sequence: an aborted/failed merge or rebase against a given branch name followed immediately by a second merge/rebase into a same-named branch whose tip has moved (force-push, re-fetch, or a maliciously crafted repository/remote that resolves the same branch name to different content across two fetches). Desktop's own telemetry logic in `performEffectsForMergeStateChange`/`performEffectsForRebaseStateChange` demonstrates the authors already anticipated tip/branch changes across conflict states but only used that signal for stats, not for invalidating stale resolutions - indicating the guard that would prevent this exists in spirit but was never wired to the security-relevant path.

### Recommendation
Tie `manualResolutions` to the specific conflict identity (e.g., `currentTip`/`originalBranchTip`/`baseBranchTip` plus `currentBranch`) rather than just "a `prevConflictState` of matching kind exists." When `getConflictState` detects that the underlying commits differ from what produced the stored resolutions, discard the map (mirroring what `RepositoryStateCache` already does for `commitToAmend`, which is invalidated when identity conditions no longer hold): [7](#0-6) 

### Proof of Concept
1. Clone/fetch a repository where branch `feature` currently points to commit `A`.
2. Start a merge of `feature` into `main` in Desktop; it conflicts on `file.txt`. Manually resolve `file.txt` as "theirs" (choosing `A`'s content) but do not finish - abort the merge.
3. Have the attacker-controlled remote force-push `feature` to point to a different commit `B` whose version of `file.txt` contains malicious/altered content, then fetch.
4. Start a new merge of `feature` (now at `B`) into `main`. `getConflictState` recomputes `currentTip`/`currentBranch` but `updateConflictState` still passes through the old `manualResolutions` map keyed by `file.txt`.
5. Desktop's conflicts dialog shows `file.txt` as already resolved ("theirs") from the stale map; the user commits, and Desktop runs `checkout --theirs` + stage against the new (attacker-controlled) `B` content without ever showing the actual new diff for review.

  public _updateManualConflictResolution(

    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }
