### Title
Empty aggregate Schnorr signatures are accepted as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` accepts an aggregate containing zero nonces and `s = 0` whenever the caller supplies an empty `keys_and_challenges` list. The aggregator refuses to produce an empty aggregate, but deserialization and verification still accept this fail-open edge case. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`SchnorrAggregate::read` permits a zero nonce count and reads the following scalar without requiring a nonzero signer count. During verification, matching zero lengths passes, no signer statements are queued, and the verifier only checks `(-s)G == 0`. A forged object with `s = 0` therefore verifies. This mirrors the reported class: an absent/empty authentication value is treated as valid instead of being rejected before dispatch.

### Impact Explanation
An unprivileged party who can submit serialized aggregate signatures and cause verification over an empty signer list can forge an aggregate signature without any private key or participant approval. Protocols that treat successful aggregate verification as evidence that every listed signer authorized the message receive a true result despite there being no signer, nonce, key, or challenge statement to verify.

### Likelihood Explanation
The attack requires the surrounding protocol to reach `verify` with an empty `keys_and_challenges` list. That precondition limits applicability where a separate quorum/nonempty-signer check always runs first. Within the exposed crypto API, however, deserialization and verification are directly reachable with public bytes, and the local aggregator explicitly distinguishes empty aggregation as invalid, making the verifier acceptance inconsistent.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::read`, `SchnorrAggregate::verify`, or both. Verification should return `false` when `self.Rs.is_empty()` or `keys_and_challenges.is_empty()`, matching `SchnorrAggregator::complete`'s refusal to produce such an object. Add a regression test asserting that serialized `len = 0, s = 0` never verifies.

### Proof of Concept
```rust
use schnorr::SchnorrAggregate;
use dalek_ff_group::Ristretto;

// Aggregate encoding: u32 nonce count = 0, followed by scalar s = 0.
let mut encoded = 0u32.to_le_bytes().to_vec();
encoded.extend_from_slice(&[0u8; 32]);

let aggregate =
  SchnorrAggregate::<Ristretto>::read(&mut encoded.as_slice()).unwrap();

// No signers or challenges are supplied; verification still succeeds.
assert!(aggregate.verify(b"example-dst", &[]));
```
