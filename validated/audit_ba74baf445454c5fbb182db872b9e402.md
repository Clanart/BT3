### Title
Quadratic (and inversion-heavy) Lagrange interpolation in `ThresholdKeys::read`/`ThresholdKeys::new` enables CPU-exhaustion DoS from untrusted bytes - (File: crypto/dkg/src/lib.rs)

### Summary
The referenced advisory (GHSA-h9mq-f6q5-6c8m, CWE-770) concerns a parser/validator that fails to account for attacker-influenced work items when bounding denial of service. The Serai analog is `ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs`: it trusts a 16-bit `n` and `t` from the byte stream, then `ThresholdKeys::new` derives `group_key` by evaluating a Lagrange `interpolation_factor` for every one of `t` participants, where each evaluation is itself an `O(t)` loop with a field inversion. An attacker who feeds crafted bytes to `ThresholdKeys::read` obtains `O(t²)` field multiplications plus `t` field inversions from a linear-size input, with no cap on `n`/`t` beyond `u16::MAX` (65,535).

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` as raw u16s [1](#0-0) , reads `n` scalars/points (Lagrange mode reads none for interpolation, then `n` verification shares) [2](#0-1) , and calls `ThresholdKeys::new`, which validates only `t <= n`, not magnitude [3](#0-2) . It then computes `group_key` as the sum over participants `1..=t` of `verification_shares[i] * interpolation.interpolation_factor(*i, &t)` [4](#0-3) .

For `Interpolation::Lagrange`, `interpolation_factor` loops over the entire `included` set (`t` elements), performing two field multiplications per element, and finishes with a modular inversion [5](#0-4) . Setting `t = n = 65,535` in the crafted input therefore triggers ~4.3×10⁹ field multiplications and 65,535 field inversions (each inversion itself an ~256-bit exponentiation chain) during a single `read` call — from an input of only ~`n × 32` bytes for the verification shares (~2 MB). The work is quadratic in attacker-controlled input size, exactly the unaccounted-resource-consumption class of the advisory.

The same quadratic pattern exists in `ThresholdKeys::view`, which evaluates `interpolation_factor` for each of `included.len()` participants, each evaluation `O(included.len())` [6](#0-5)  — but there the signing set is bounded by the honest `n` of real keys, whereas `read` lets the attacker choose `n` arbitrarily.

### Impact Explanation
An unprivileged party who can cause a node/validator to deserialize attacker-supplied bytes via `ThresholdKeys::read` — listed as an in-scope untrusted-bytes entry point — can stall the deserializing thread for an unbounded period: ~4 billion field multiplications plus tens of thousands of inversions per 2 MB input. Repeated submissions amplify this into a full denial of service of the signing/coordinator process, preventing DKG completion and signature production (availability failure, matching the advisory's A:H impact).

### Likelihood Explanation
Likelihood is moderate: it requires a code path where `ThresholdKeys::read` (or borsh/scale decoding of `ThresholdKeys`, which has no length bound either) consumes attacker-influenced bytes rather than only locally-generated keys. No authentication, secret knowledge, or collusion is needed — only the ability to supply ~2–4 MB of well-formed field/point encodings. The cost asymmetry (megabytes of input → billions of field ops) makes each request cheap for the attacker and expensive for the victim.

### Recommendation
- Enforce a protocol-level maximum on `n`/`t` inside `ThresholdKeys::read` and `ThresholdParams::new` (e.g., the same `MAX_KEY_SHARES_PER_SET` bound used elsewhere), rather than allowing up to `u16::MAX`.
- Replace the per-participant `O(t)` Lagrange factor computation with the standard `O(t)` total product/denominator-prefix technique, or compute all factors in one pass.
- Reject `Interpolation`/`ThresholdParams` combinations that are semantically invalid early (before `ThresholdKeys::new` performs the `group_key` sum), and bound deserialization work proportionally to input size.

### Proof of Concept

```rust
// Conceptual PoC against crypto/dkg ThresholdKeys::read
// Craft: id_len || C::ID || t=0xFFFF || n=0xFFFF || i=1 || interp=1 (Lagrange)
//        || secret_share || n * valid point encodings
// ThresholdKeys::new then runs t = 65535 iterations of interpolation_factor,
// each iterating over 65535 included participants and performing a field invert:
// ~4.3e9 field multiplications + 65535 inversions, CPU-bound for a ~2MB input.

let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&u16::MAX.to_le_bytes()); // t
buf.extend(&u16::MAX.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes());     // i
buf.push(1);                         // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref()); // secret_share
for _ in 0 .. u16::MAX {
  buf.extend(C::generator().to_bytes().as_ref()); // verification_shares
}
// ThresholdKeys::<C>::read(&mut &buf[..]) // hangs in group_key computation
```
