### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/fee calculation, undercharging the transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The reported bug class is a total/reserve aggregation that forgets an accrued component (unclaimed fees omitted from the Bunni position's total value). The Serai analog lives in the Bitcoin wallet's transaction constructor: `SignableTransaction::new` pushes the optional OP_RETURN `data` output into `tx_outs`, but computes the transaction weight and vbytes — and therefore `needed_fee` — from a mock transaction containing only `payments`. The OP_RETURN output (up to ~92 serialized bytes for an 80-byte payload plus output overhead) is a component of the final transaction that is left out of the "total size" calculation, exactly mirroring a fee component left out of a "total value" calculation.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the fee is computed: [1](#0-0) 

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ... })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` rebuilds a mock `Transaction` whose `output` vector is constructed **only** from `payments` — `data` is never passed in: [2](#0-1) 

The same omission propagates to the change path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` also lacks the OP_RETURN output, so `fee_with_change` is understated and the change output is credited with `input_sat - payment_sat - fee_with_change`, i.e., the sats that should have paid for the OP_RETURN bytes are instead swept into change. [3](#0-2) 

Additionally, the `weight > MAX_STANDARD_TX_WEIGHT` check uses the underestimated `weight`, so a transaction can be accepted while its actual weight exceeds the standardness limit. [4](#0-3) 

### Impact Explanation
Any caller of this in-scope wallet API that supplies `data` (the API explicitly supports up to 80 bytes, checked at line 171) produces a transaction whose real fee rate is lower than `fee_per_vbyte` and lower than the reported `needed_fee()`. Concretely:

- `needed_fee` is understated by `fee_per_vbyte * ceil(4*(9 + 2 + data_len)/4)` ≈ `fee_per_vbyte * ~85` vbytes for a maximal payload.
- The change output is over-credited by the same amount, so the effective fee paid is less than the intended rate — the transaction can fall below the mempool's minimum relay/eviction thresholds and never confirm, stalling funds in-flight (the coins sit in an unconfirmed transaction the wallet considers correctly priced).
- The `MAX_STANDARD_TX_WEIGHT` guard can be bypassed by up to the OP_RETURN output's weight, producing a non-standard transaction that relays reject.

This is an incorrect fee formula derived from reachable public inputs (`data` bytes supplied to the constructor), not integrator misuse — the API contract ("any leftover funds will be sent to change... needed_fee achieves the specified fee rate") is violated internally.

### Likelihood Explanation
The bug triggers deterministically whenever `data.is_some()`. The in-tree processor currently passes `None` for `data` on Bitcoin (`processor/src/networks/bitcoin.rs` line 450), so the practical exploit path is any consumer of `bitcoin-serai`'s wallet that uses the OP_RETURN feature — e.g., embedding Inscriptions/bridging memos, which is the documented purpose of the `data` parameter. Since the OP_RETURN path is explicitly supported and bounded (80 bytes), it is a first-class reachable input, not a corner case.

### Recommendation
Include the OP_RETURN output in the mock transaction used for weight/vbyte estimation. The cleanest fix is to compute the size from the already-built `tx_outs` (plus the prospective change output) rather than from `payments` alone — e.g., pass `&tx_outs` (or the constructed output list) into `calculate_weight_vbytes`, and use the same data-inclusive size for `fee_with_change`, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs semantics
let data = vec![0u8; 80];
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(data), FEE).unwrap();

// Real vsize includes the OP_RETURN output (~92 extra bytes)
let real_vbytes = tx.clone().sign(...).vsize(); // > vbytes used internally

// needed_fee was computed on vbytes excluding the OP_RETURN output:
assert!(tx.needed_fee() < FEE * real_vbytes);
// Change output absorbed the difference: actual paid fee < intended fee rate
assert_eq!(tx.fee(), tx.needed_fee()); // fee paid equals understated needed_fee
```
The discrepancy is `fee_per_vbyte` times the serialized size of `TxOut { value: 0, script_pubkey: OP_RETURN <data> }`, which `calculate_weight_vbytes` never accounts for because it only iterates `payments`.

```rust
  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
```
