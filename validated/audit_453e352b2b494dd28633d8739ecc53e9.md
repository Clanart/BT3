### Title
Server-Side Request Forgery (SSRF) via unrestricted Data Layer mirror URLs - (File: `chia/data_layer/download_data.py`)

### Summary
Any user who owns a DataLayer store can publish arbitrary mirror URLs on-chain via the `add_mirror` RPC/wallet flow. Any other DataLayer node that subscribes to that store id will automatically and periodically issue outbound HTTP requests to those attacker-chosen URLs from its background sync loop, with no validation of scheme, host, or address (no blocking of loopback/link-local/internal ranges). This is a classic SSRF: an unprivileged store owner forces a victim's DataLayer service to make requests to internal hosts/services from within the victim's network.

### Finding Description
`DataLayer.add_mirror()` accepts a caller-supplied list of URLs and publishes them on-chain through the wallet without any validation: [1](#0-0) 

Any node that discovers this mirror (e.g. because a local wallet user subscribed to that `store_id`) pulls the mirror URLs directly into its subscription table via `update_subscriptions_from_wallet()`, again without validating the URL: [2](#0-1) 

The background service loop (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`) then randomly selects one of these attacker-controlled URLs and issues an HTTP request to it without any scheme/host allow-listing: [3](#0-2) 

The actual request is performed by `http_download()`, which does a plain `aiohttp` GET to `server_info.url + "/" + filename` — `server_info.url` is fully attacker-controlled (it can point to `http://127.0.0.1:<port>/...`, `http://169.254.169.254/...`, or any other internal address reachable from the victim's host): [4](#0-3) 

There is no validation anywhere in this chain (`add_mirror`, `update_subscriptions_from_wallet`, `get_available_servers_for_store`, `http_download`) that restricts the URL to a public/allow-listed host or blocks private/loopback/link-local ranges. The project's own module notes explicitly acknowledge that "Plugin and mirror URLs are external trust inputs," but the trust boundary is only enforced on the *downloaded content* (validated against the wallet-advertised Merkle root), not on *where the request is sent*: [5](#0-4) 

Because the response body is fed into `insert_from_delta_file()`/`DataStore.insert_into_data_store_from_file()` for parsing, and error/success behavior (timing, HTTP status, exceptions such as `ClientConnectorError`) is distinguishable by the store owner (via retry/backoff bookkeeping and eventual on-chain publication success/failure), this also creates a blind SSRF oracle that can be used to probe internal network topology (open ports, service banners via timing/behavior) even without leaking full response bodies.

### Impact Explanation
Any wallet user can create a DataLayer store, publish a mirror URL pointing at an internal-only address, and get any subscriber's full node/DataLayer service to make outbound requests to that address from within the subscriber's private network. This can be used to:
- Probe/port-scan internal infrastructure reachable from a DataLayer node's host (cloud metadata endpoints, internal admin panels, other services on localhost/private IPs) with a repeated, persistent trigger (the sync loop retries automatically).
- Trigger side effects on internal HTTP services that act on GET requests.
- Potentially exfiltrate response timing/availability signals about internal network state to the attacker (who fully controls the mirror URL and knows when/whether their target reacted).

This matches CWE-918 (SSRF) directly and is reachable purely through a normal, unprivileged DataLayer/wallet action (owning a store and calling `add_mirror`), satisfying the "wallet user / Data Layer client" reachability requirement of the report.

### Likelihood Explanation
High likelihood: creating a DataLayer store and adding mirrors is a standard, unauthenticated (from the DataLayer server's perspective) user action requiring no special privilege beyond owning any store. Any other user who chooses to subscribe to that store id (a normal, expected DataLayer usage pattern for consuming public/shared data stores) is automatically exposed — the fetch happens unconditionally in the periodic background loop, requiring no additional victim interaction beyond subscribing.

### Recommendation
- Validate/allow-list mirror URLs at ingestion (`add_mirror` in `chia/data_layer/data_layer.py` and/or the wallet-side mirror creation path) and again at fetch time in `download_data.py`/`http_download()`.
- Reject or require explicit opt-in for URLs resolving to loopback, link-local (169.254.0.0/16), private RFC1918 ranges, and other non-routable/internal addresses, resolving DNS before connecting to prevent DNS-rebinding bypass.
- Consider disabling redirects (or re-validating destination after redirect) in the `aiohttp` client used by `http_download()`.
- Document and enforce that subscribing to third-party store ids implies trusting their mirror URLs only to the extent of an explicit network egress policy, and provide a config option to restrict DataLayer network egress to an allow-list of hosts.

### Proof of Concept
1. Attacker runs a normal Chia wallet + DataLayer node, creates a DataLayer store (`create_data_store`), and calls `add_mirror` with a URL pointing at a victim-reachable internal service, e.g. `http://169.254.169.254/latest/meta-data/` or `http://127.0.0.1:8555/some_internal_rpc`, via:
   - `DataLayer.add_mirror(store_id, urls=["http://169.254.169.254/latest/meta-data/"], amount=1, fee=0)` (`chia/data_layer/data_layer.py:965`).
2. The mirror URL is published on-chain through `dl_new_mirror`.
3. Victim's DataLayer node subscribes to attacker's `store_id` (a normal DataLayer usage flow, e.g. via `subscribe` CLI/RPC to follow a public dataset).
4. Victim's `periodically_manage_data()` loop calls `update_subscriptions_from_wallet()` (`chia/data_layer/data_layer.py:979`), pulling the attacker's URL into its local subscription table with no validation.
5. On the next `fetch_and_validate()` cycle (`chia/data_layer/data_layer.py:642`), the victim node picks the attacker's server info and calls `insert_from_delta_file()` → `download_file()` → `http_download()` (`chia/data_layer/download_data.py:298`), which performs `session.get("http://169.254.169.254/latest/meta-data/" + "/" + filename, ...)` directly from the victim's process — an outbound request to an internal-only resource fully chosen by the attacker.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
```
