### Title
Silent Truncation/Padding of Fixed-Size WOTS Key Arrays Corrupts BitVM Disprove Scripts — (`File: core/src/bitvm_client.rs`)

### Summary

`ClementineBitVMPublicKeys::vec_to_array` and `vec_slice_to_nested_array` silently truncate or pad with dummy sentinel bytes (`[255u8; 20]`) when the supplied inner `Vec` length does not match the expected compile-time constant `N`. The only length guard in the deposit flow checks the *outer* count of 381 Winternitz key vectors, but never validates the *inner* digit count of each individual key. A malicious operator can therefore submit 381 outer vectors that each pass the outer-count check while carrying wrong inner lengths, causing the verifier to derive a completely different Taproot disprove-script tree and assert-address set than the one the operator actually embeds in its on-chain assert transactions. The verifier then cannot construct a valid disprove transaction, and the operator wins the BitVM challenge game unchallenged.

---

### Finding Description

**`vec_to_array` — silent truncation and dummy-padding** [1](#0-0) 

```rust
pub fn vec_to_array<const N: usize>(vec: &[[u8; 20]]) -> [[u8; 20]; N] {
    let mut result = [[255u8; 20]; N];   // ← pre-filled with dummy sentinel
    for (i, item) in vec.iter().enumerate() {
        if i < N {
            result[i] = *item;           // ← silently drops items beyond N
        }
    }
    result                               // ← silently pads with [255u8;20] if vec.len() < N
}
```

`vec_slice_to_nested_array` delegates to `vec_to_array` for every inner slice and carries the same flaw. [2](#0-1) 

**`from_flattened_vec` — calls `vec_to_array` for every key group without inner-length validation** [3](#0-2) 

Expected inner sizes are:
- `payout_tx_blockhash_pk` / `latest_blockhash_pk` / `challenge_sending_watchtowers_pk` → 43 digits
- `bitvm_pks.0[i]` / `bitvm_pks.1[i]` → 67 digits
- `bitvm_pks.2[i]` → 35 digits

None of these are validated.

**The only guard in `set_operator_keys` checks the outer count (381), not inner lengths** [4](#0-3) 

After the outer-count check passes, `from_flattened_vec` is called directly on the unchecked inner vectors, producing a `ClementineBitVMPublicKeys` whose digit arrays may contain trailing `[255u8; 20]` sentinels or be silently truncated.

**The corrupted keys are immediately used to compute and persist the disprove-script Taproot root and assert-tx addresses** [5](#0-4) 

The `root_hash` (Taproot root of all disprove scripts) and `assert_tx_addrs` (leaf hashes of assert transactions) derived from the corrupted keys are stored in the `bitvm_setups` table. These are the values the verifier uses later to construct and broadcast a disprove transaction.

**The corrupted keys are also used at transaction-build time** [6](#0-5) 

---

### Impact Explanation

When the verifier later observes an operator's on-chain assert transaction, it retrieves the stored `root_hash` and `assert_tx_addrs` to construct the disprove transaction. Because those values were derived from malformed keys (with wrong inner lengths), they do not match the actual Taproot tree the operator embedded in the assert transaction (which uses the operator's real keys). The verifier's disprove transaction references a non-existent script path and is therefore invalid on-chain. The operator wins the BitVM challenge game without a valid proof, and can claim the bridged BTC collateral or prevent reimbursement of honest withdrawals.

---

### Likelihood Explanation

The attack requires a registered operator (who has posted collateral) to deliberately send 381 outer Winternitz key vectors where one or more inner vectors have a length other than the expected digit count. The outer-count check at line 1770 passes; no other validation rejects the submission. The operator then uses their actual (correctly-sized) keys in the assert transaction. The mismatch is never detected at key-ingestion time.

---

### Recommendation

Add an explicit inner-length check inside `vec_to_array` (or at the call sites in `from_flattened_vec`) and return an error instead of silently truncating or padding:

```rust
pub fn vec_to_array_checked<const N: usize>(
    vec: &[[u8; 20]],
) -> Result<[[u8; 20]; N], BridgeError> {
    if vec.len() != N {
        return Err(eyre::eyre!(
            "Expected inner Winternitz key length {N}, got {}",
            vec.len()
        ).into());
    }
    Ok(vec.try_into().expect("length already checked"))
}
```

Apply the same check inside `vec_slice_to_nested_array`. Propagate the `Result` through `from_flattened_vec` and reject the `set_operator_keys` RPC call if any inner vector has the wrong digit count.

---

### Proof of Concept

1. A malicious operator calls `set_operator_keys` with 381 outer vectors (passes the count check at line 1770), but sets `flattened_wpks[0]` (the `payout_tx_blockhash_pk` group) to a vector of length 42 instead of 43.
2. `vec_to_array::<43>` fills `result[42]` with `[255u8; 20]` — the dummy sentinel — without error.
3. The verifier computes `assert_tx_addrs` and `root_hash` from this corrupted key set and stores them in `bitvm_setups`.
4. The operator later broadcasts an assert transaction whose Taproot tree is built from their actual 43-digit key. The Taproot root differs from the stored `root_hash`.
5. The verifier's disprove transaction references the wrong script path and is rejected by Bitcoin consensus.
6. The operator's fraudulent assertion stands unchallenged; the BitVM game resolves in the operator's favor.
