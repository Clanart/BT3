### Title
Unsynchronized `task.Status` reads race with mutex-protected `SetStatus` writes in the OCC scheduler - (File: sei-cosmos/tasks/scheduler.go)

### Summary
`sei-cosmos/tasks/scheduler.go` defines `deliverTxTask.Status` as a field protected by an `mx sync.RWMutex`, with `IsStatus()` and `SetStatus()` taking the lock correctly. However, `shouldRerun()` and `findFirstNonValidated()` read `task.Status` directly (`switch task.Status` / `if t.Status != statusValidated`) without acquiring `mx`, while concurrently executing goroutines mutate the very same field through the locked `SetStatus()` path (e.g., `statusAborted` / `statusExecuted` in `executeTask()`, `statusWaiting` / `statusValidated` in `shouldRerun()` itself). This is the same "marked-vs-unmarked access" pattern described in the fuse-uring advisory: some accesses to a shared flag are synchronized (mutex/`WRITE_ONCE`-equivalent) and others are plain loads, which the Go memory model does not guarantee to observe a consistent, up-to-date value for. ### Finding Description
The `Scheduler` used by `ProcessTXsWithOCCV2` (the Cosmos-side OCC parallel-execution path that processes every block's non-EVM/mixed transactions) runs execution and validation work across many worker goroutines fed through `s.executeCh` / `s.validateCh` (`start`, `executeAll`, `validateAll`). Task status transitions are guarded by `deliverTxTask.mx`:

- `IsStatus()` takes `mx.RLock()` before reading `Status`.
- `SetStatus()` takes `mx.Lock()` before writing `Status`.

But `shouldRerun()`, which is invoked from every validation goroutine, reads the field with a bare `switch task.Status` instead of calling `IsStatus()`. Likewise `findFirstNonValidated()`, which is invoked both from the main scheduling loop and from `executeTask()` in the synchronous fallback path, iterates `s.allTasks` and reads `t.Status` directly rather than through the locked accessor. [4](#0-3) 

Because `executeTask()` writes `Status` via the locked `SetStatus()` (`statusAborted`, `statusExecuted`) while `shouldRerun()`/`findFirstNonValidated()` elsewhere read it unlocked, the compiler and runtime are free to reorder or cache these accesses independently on each goroutine — exactly the class of bug the referenced advisory fixes by promoting a bare `WRITE_ONCE`/plain-load pair to `smp_store_release()`/`smp_load_acquire()` (or, in the KCSAN case, wrapping the load in `READ_ONCE()`). In Go terms this is an unsynchronized read racing a mutex-protected write on the same memory location, which under `go test -race` is a reportable data race and, on the actual production build (built without the race detector), gives no correctness guarantee that a goroutine observing an aborted/executed/waiting task will see the fully-formed side effects that accompanied that status transition (e.g., `task.Abort`, `task.Response`, or the dependency set populated in `AppendDependencies`, all of which are set right before/after the unlocked-vs-locked `Status` write).

### Impact Explanation
`ProcessTXsWithOCCV2` runs for every block containing transactions that are not eligible for (or fall back from) the Giga path, so this scheduler is on the hot path for ordinary Cosmos-message and mixed-tx blocks reachable by any transaction sender. A torn/stale view of `task.Status` can cause the scheduler to make an incorrect scheduling decision (e.g., treat a task as validated when its dependency accounting or abort bookkeeping has not yet become visible, or vice versa), which can produce non-deterministic per-validator execution outcomes depending on the host architecture's memory ordering and Go runtime scheduling. Since OCC's output (execution order/results) must be bit-identical across all validators to keep AppHash consensus, a data race that manifests differently across nodes is a path to a **permanent chain split** — the impact category explicitly listed as in-scope for this class of bug.

### Likelihood Explanation
The race requires no attacker privilege beyond submitting ordinary transactions that populate a block with enough non-EVM/mixed transactions to trigger `ProcessTXsWithOCCV2` with `workers > 1` and at least one conflict/abort/rerun cycle, which is routine on validators running with `ConcurrencyWorkers() > 1`. Because Go's memory model offers no ordering guarantee for unsynchronized reads racing mutex-protected writes, the probability of an observable divergence is architecture- and load-dependent (higher on weakly-ordered platforms or under high validator load) but not exotic — it is the same class of latent race the fuse-uring CVE assigned High severity for, since exploitation only needs concurrent access, not a malicious actor.

### Recommendation
Route every read of `deliverTxTask.Status` through the existing locked `IsStatus()` accessor instead of the raw field, in both `shouldRerun()` (the `switch task.Status` dispatch) and `findFirstNonValidated()`/`executeTask()`'s synchronous fallback checks. Where a single locked snapshot is needed for a multi-way switch, capture it once via a small locked getter (e.g., `dt.GetStatus() status`) rather than re-entering `IsStatus()` per branch, mirroring the kernel fix's approach of wrapping unmarked loads in `READ_ONCE()`/acquire semantics to match the marked stores.

### Proof of Concept
1. Build the scheduler with `-race` and drive `ProcessTXsWithOCCV2`/`scheduler.ProcessAll` with `workers > 1` on a block containing several transactions that write/read the same state key (forcing at least one abort → `SetStatus(statusAborted)` → dependency-driven rerun → `SetStatus(statusWaiting)`/`SetStatus(statusValidated)` transitions), as already exercised by `giga/tests/giga_test.go`'s `TestGigaOCCVsGigaSequential_Conflicting`-style conflicting-transfer workload (the equivalent sei-cosmos OCC path shares the identical `scheduler.go` status-field pattern). 2. Run under `go test -race ./sei-cosmos/tasks/...` (or add a targeted concurrency test analogous to `sei-db/state_db/sc/memiavl/tree_race_test.go`'s pattern of concurrent readers/writers) and observe the race detector flag concurrent unlocked reads of `task.Status` in `shouldRerun`/`findFirstNonValidated` against the mutex-guarded writes in `SetStatus`, confirming the same "marked vs. unmarked access" defect class as CVE-2026-64588.

func (s *scheduler) executeTask(task *deliverTxTask) {
	dCtx, dSpan := s.traceSpan(task.Ctx, "SchedulerExecuteTask", task)
	defer dSpan.End()
	task.Ctx = dCtx

	// in the synchronous case, we only want to re-execute tasks that need re-executing
	if s.synchronous {
		// even if already validated, it could become invalid again due to preceding
		// reruns. Make sure previous writes are invalidated before rerunning.
		if task.IsStatus(statusValidated) {
			s.invalidateTask(task)
		}

		// waiting transactions may not yet have been reset
		// this ensures a task has been reset and incremented
		if !task.IsStatus(statusPending) {
			task.Reset()
			task.Increment()
		}
	}
