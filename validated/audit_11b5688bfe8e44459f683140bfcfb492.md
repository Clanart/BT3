## Title
Warning-dedup key collision via unescaped string concatenation causes suppressed security warnings (DoS on security-guidance plugin) - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

## Summary
The `security-guidance` plugin's `PostToolUse` handler builds a deduplication key for security warnings by concatenating two independently-controlled, variable-length strings with a single literal `-` separator instead of an unambiguous encoding. This is the same class of bug as the Trail of Bits finding in `StorageUtils.sol`: concatenating multiple dynamic-length values without an injective encoding lets an attacker move a delimiter-shaped substring across the boundary and produce two different `(file_path, rule_name)` pairs that hash/compare to the identical key, causing the dedup logic to treat unrelated findings as duplicates.

## Finding Description
In `handle_..._posttooluse` processing of `Edit`/`Write`/`MultiEdit`/`NotebookEdit` tool calls, for every pattern match the code computes: [1](#0-0) 

```python
for rule_name, reminder in pattern_matches:
    warning_key = f"{file_path}-{rule_name}"
    if atomic_check_and_mark_warning(session_id, warning_key):
        all_guidance.append(reminder)
```

`file_path` comes directly from `tool_input.file_path`/`notebook_path` (fully attacker/model-influenced — Claude, potentially guided by prompt injection, chooses the path of files it writes/edits), and `rule_name` is either a built-in pattern id or a project-defined custom rule name loaded via `extensibility.load_for_session` (also attacker-influenced if the project's `.claude` config or CLAUDE.md is untrusted/injected). Both are variable-length strings joined with a single `-` character that can also legitimately appear inside either field (paths routinely contain hyphens; rule names are free-form strings including user-defined `user:*` patterns).

Because `-` is not escaped or length-prefixed, two semantically distinct pairs can produce an identical `warning_key`:
- `file_path = "notes-b"`, `rule_name = "c"` → `"notes-b-c"`
- `file_path = "notes"`, `rule_name = "b-c"` → `"notes-b-c"`

`atomic_check_and_mark_warning` (built on the same `with_locked_state` session-state primitive used elsewhere in the plugin) is a "have we already shown this warning" gate — the same idempotency-style used by the on-chain `storeSubscription`/`subscriptionId` mechanism in the ToB report. A collision lets an earlier, unrelated (file, rule) warning "consume" the dedup slot for a later, genuinely new finding, so the later finding is silently dropped from `all_guidance` and never surfaces to the user.

## Impact Explanation
This is a Denial-of-Service on the security-guidance plugin's own protective signal rather than a permission/authorization bypass: a security warning that should be shown to the user for a specific dangerous edit can be silently suppressed because its dedup key collided with an already-seen, unrelated warning. Since this plugin's entire purpose is to flag risky edits (secrets, insecure patterns, etc.) as they happen, silently dropping a genuine new finding is a direct analog of the "Airnode no longer reports API results to Alice" scenario — the intended recipient (the user) is denied the intended notification because of an attacker-craftable identifier collision. It does not by itself grant unauthorized tool execution, but it undermines the tool's safety-net function and could mask a real vulnerability introduced by a prior or concurrent edit.

## Likelihood Explanation
Exploitability requires an attacker (or a model acting on injected instructions) to control both operands feeding the key: the edited/written `file_path` (fully attacker-influenced) and a `rule_name` that can be made to contain a `-`. Built-in rule names are fixed identifiers (would need to already contain a hyphen matching the crafted split), but project-defined custom patterns loaded through `extensibility.py` allow arbitrary rule names, making the collision straightforward to engineer in any repo where custom security patterns are configurable (including via a compromised/malicious CLAUDE.md or repo config, similar in spirit to the report's "user-controlled parameters" trust boundary). Given file paths are attacker-chosen and one collision partner only needs a matching custom rule name, this is a Low-difficulty, deterministic collision — matching the report's stated "Low" difficulty rating.

## Recommendation
- **Short term:** Build `warning_key` from a structured tuple/encoding that cannot collide across field boundaries, e.g. `(file_path, rule_name)` used directly as a dict/tuple key, or a length-prefixed/JSON-encoded key such as `json.dumps([file_path, rule_name])`, instead of `f"{file_path}-{rule_name}"`.
- **Long term:** Audit the codebase for any other place where multiple variable-length, potentially attacker-controlled strings are concatenated with a plain separator to form an identifier used for security-relevant deduplication, caching, or authorization decisions (e.g., other `f"{a}-{b}"`/`f"{a}_{b}"` patterns in `security_reminder_hook.py`, `diffstate.py`, and `hookify`), and replace them with collision-safe encodings (tuple keys, `abi.encode`-style length-prefixed serialization, or hashing each field separately before combining).

## Proof of Concept
1. Configure a project-level custom security pattern (via the plugin's extensibility mechanism) with `rule_name = "b-c"` that matches some benign content.
2. Have Claude (or a prompt-injected instruction) `Write`/`Edit` a file at path `notes` such that the custom rule `"b-c"` fires. This computes `warning_key = "notes-b-c"` and marks it as warned via `atomic_check_and_mark_warning`.
3. Separately, have Claude `Write`/`Edit` a genuinely dangerous file at path `notes-b` that triggers a real, distinct built-in rule `"c"` (e.g., a hard-coded-secret or insecure-pattern rule). This computes the same `warning_key = "notes-b-c"`.
4. Because the key already exists in session state from step 2, `atomic_check_and_mark_warning` returns "already warned," so the genuine finding from step 3 is dropped from `all_guidance` and the user is never shown the warning for the actual vulnerable edit in `notes-b`.
