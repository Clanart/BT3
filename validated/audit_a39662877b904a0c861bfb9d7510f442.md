## Analysis

The external finding's broken invariant is: **an action is taken on an object based only on a coarse condition (expired/removable) without re-validating that the object's precise identity/state still matches what the caller intended**, allowing state to be mutated based on stale or attacker-influenced identifiers. The closest analogous invariant gap in this GitHub Desktop codebase is in the Copilot-assisted merge-conflict resolution flow, where file writes are keyed off an AI-supplied `path` string that is never re-validated against the actual set of conflicted files gathered for that operation before being written to disk and staged.

### Title
Copilot conflict resolution writes/stages files by AI-supplied path without verifying the path was part of the original conflict set - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`AppStore._applyCopilotConflictResolutions` iterates over `copilotResolutions` (model output) and, for each entry, validates only that the path stays inside the repository (`resolveWithin`) and that a *currently conflicted* file with that exact path isn't already externally resolved. It never checks that `resolution.path` was actually a member of the file set that was sent to the model in `buildConflictContext`/`ICopilotConflictContext.files`. If the model returns a `path` for a file that was never part of the conflict (e.g. an ordinary tracked file elsewhere in the working tree), Desktop still writes the AI-generated content to that file and stages it.

### Finding Description
`_applyCopilotConflictResolutions` [1](#0-0)  loops over `copilotResolutions` and:
1. Skips only paths present in `manualResolutions` (user overrides).
2. Handles `deleteConflictAction` cases by looking up the file in `workingDirectory.files`.
3. For ordinary text resolutions, calls `resolveWithin(repository.path, resolution.path)` — a directory-traversal guard only, not a membership check [2](#0-1) .
4. Looks up `onDiskFile` by path in `workingDirectory.files`; it only *skips* the write when the file **is** found, is conflicted, and has no remaining unresolved conflicts (meaning the user resolved it externally) [3](#0-2) . If `onDiskFile` is `undefined` — i.e., the path is not a currently conflicted (or even changed) file at all — none of these guard conditions apply, and execution falls through to the unconditional write:
```
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
``` [4](#0-3) 
5. All staged paths are then `git add`-ed automatically [5](#0-4) .

The only place the "real" list of conflicted files is established is `buildConflictContext`, which builds `ICopilotConflictContext.files` from the caller-supplied conflicted-file list [6](#0-5) . That gathered file list, however, is not threaded through to `_applyCopilotConflictResolutions` for cross-checking; the apply step trusts whatever `path` values come back embedded in `copilotResolutions` (populated from the model's JSON result in `_startCopilotConflictResolution` at [7](#0-6) ). The conflict content sent to the model — hunks of `oursContent`/`theirsContent` from a merge, rebase, or cherry-pick — originates directly from the incoming/attacker-controllable branch or PR being merged (fetched from a remote), so prompt-injection text embedded in that content could induce the model to emit an out-of-scope `path` referring to an unrelated tracked file, and Desktop would still write and stage it, matching the report's core failure mode of "acting on an object without re-checking the invariant that should have governed the action."

### Impact Explanation
This can silently corrupt a file the user never intended to touch and never reviewed as part of the conflict, then stage it (`git add`) so that it is included in the next commit/push — i.e. "silent corruption of what the user commits or pushes," which is an explicitly valid impact category. Because the write path resolves the file inside the repository (`resolveWithin` prevents `../` escape), this isn't an arbitrary filesystem write outside the repo, but it is an unauthorized write to a tracked file inside the repo that bypasses the review the Copilot conflicts dialog is meant to provide.

### Likelihood Explanation
The trigger requires the attacker to control content that ends up in the "theirs" side of a merge/rebase/cherry-pick (a normal, expected attacker capability for this class per the valid-impact rules: "attacker controls a cloned/fetched repository"/git remote), plus a model response that includes prompt-injected paths outside the requested set. The actual reachability of that final step (whether `_startCopilotConflictResolution`/`_resolveConflictsWithCopilot` filters the model's response against the requested files before populating `copilotResolutions`) could not be fully confirmed — the SDK-calling implementation of `_resolveConflictsWithCopilot` was not inspected in this pass. This is the main uncertainty in the analysis: if that function already filters resolutions to only the requested conflict paths, the missing check in `_applyCopilotConflictResolutions` would be dead code from a security standpoint. Based on the code actually reviewed, no such filtering exists at the point where files are written.

### Recommendation
In `_applyCopilotConflictResolutions`, thread through (or re-derive) the original set of conflicted file paths that were sent to the model, and explicitly reject/skip any `resolution.path` not present in that set before calling `writeFile`/staging it, rather than relying solely on `resolveWithin` and the "already externally resolved" heuristic.

### Proof of Concept
Not independently reproduced end-to-end (would require confirming `_resolveConflictsWithCopilot`'s response handling, which was not fully inspected). Based on code inspection:
1. Trigger a merge/rebase where the incoming ("theirs") side contains conflict-marker content engineered to prompt-inject the model.
2. Start Copilot conflict resolution; the model returns a `resolutions` array including an entry whose `path` points to a tracked file outside the actual conflicted set.
3. `_applyCopilotConflictResolutions` finds no matching `onDiskFile` for that path, so the "skip if already externally resolved" guard never triggers, and it unconditionally writes `resolution.resolvedContent` to that file and stages it via `git add`.
