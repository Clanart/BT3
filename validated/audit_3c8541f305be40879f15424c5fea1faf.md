### Title
Blind SSRF via arbitrary attacker-published DataLayer mirror URLs consumed by `fetch_and_validate`/`download_file` - ([File: chia/data_layer/download_data.py])

### Summary
Any wallet holder can publish an arbitrary URL on-chain as a DataLayer "mirror" for a store id they don't even need to own visibility restrictions on. Any other DataLayer client that subscribes/tracks that store (a normal, low-privilege DL operation) will automatically pull the attacker-controlled URL out of chain state and issue an outbound HTTP GET/POST to it with no destination validation (scheme, host, private-IP/loopback/link-local checks), mirroring the unauthenticated blind SSRF pattern in Audiobookshelf's `Auth.js` (CVE-2023-51665).

### Finding Description
1. Any user can create a mirror coin with arbitrary URL strings via the wallet RPC `dl_new_mirror` (`chia/wallet/wallet_rpc_api.py` `dl_new_mirror`, wrapping `DataLayerWallet.create_new_mirror`), or via the DataLayer RPC `add_mirror` (`chia/data_layer/data_layer.py:965-970`, `chia/data_layer/data_layer_rpc_api.py:468-475`). The URLs are stored on-chain in the mirror coin's solution with no format/host restriction. [1](#0-0) 
2. When any other node tracks/subscribes to that same store, `coin_added` in `DataLayerWallet` parses the mirror coin spend and records the raw attacker-supplied URLs into local wallet state (`dl_wallet_store.add_mirror`), with no validation of the URL content. [2](#0-1) 
3. `DataLayer.update_subscriptions_from_wallet` copies these mirror URLs directly into the subscription table used for downloads: `urls += mirror.urls` then persisted via `DataStore.update_subscriptions_from_wallet`. [3](#0-2) 
4. The periodic sync loop `fetch_and_validate` iterates these `servers_info` URLs and calls `insert_from_delta_file` → `download_file`, which — when no downloader plugin handles the URL — calls `http_download` directly against the raw URL taken from chain-derived mirror data, with only filename validation (`is_filename_valid`), not URL/host validation. [4](#0-3) [5](#0-4) 
5. No code path checks the URL's scheme or resolved host against a denylist of private/loopback/link-local/metadata-service ranges before the aiohttp request is issued. This is confirmed by the test at `test_mirrors` which happily stores `http://127.0.0.1/8000`-style URLs as valid mirrors with no rejection. [6](#0-5) 

Because the mirror-publishing coin spend is just an ordinary spend bundle (no special authorization beyond paying a fee to create the mirror coin), any unprivileged spend-bundle submitter/wallet user can plant a malicious URL that other, unrelated DataLayer nodes will fetch — this is the "blind SSRF triggered by unauthenticated/low-trust input" bug class described in the Audiobookshelf advisory, transposed to DataLayer's mirror/subscription mechanism.

### Impact Explanation
A malicious actor can cause any DataLayer node that later chooses to track/subscribe to their store to issue outbound HTTP requests to attacker-chosen internal or otherwise restricted endpoints (e.g., internal admin panels, cloud metadata endpoints, local loopback services on other ports) with attacker-influenced JSON bodies (`store_id`) in the plugin-download case, or plain GET requests in the plain HTTP-download case. This can be used to probe internal network topology, hit internal APIs, or abuse services that trust localhost/other-listener input — a classic SSRF impact. It does not directly cause coin-set divergence, unauthorized asset movement, or consensus-level harm, keeping severity at Medium, consistent with the referenced CVE's CVSS rating.

### Likelihood Explanation
Likelihood is moderate: exploitation requires a victim operator to deliberately subscribe/track the attacker's store (an intentional, low-privilege DataLayer action), but no further authorization, signature, or special trust is needed from the attacker beyond publishing a normal spend bundle that creates a mirror coin. The URLs are never sanitized/validated at any point along the chain-to-fetch pipeline.

### Recommendation
- Validate and restrict mirror/server URLs before storing and before use in `http_download`/`download_file`: enforce an allow-listed scheme (e.g., `https://` only), resolve and reject requests targeting private, loopback, link-local, and other reserved IP ranges (RFC1918/RFC6598/RFC4193/169.254.0.0/16, etc.), similar to standard SSRF mitigations.
- Apply this validation both when persisting mirror URLs (`DataLayerWallet.coin_added`, `DataStore.update_subscriptions_from_wallet`) and immediately before issuing the HTTP request in `download_file`/`http_download`, so validation isn't bypassed if URLs are injected via any other code path.
- Consider requiring operator opt-in / an explicit allow-list of trusted mirror domains rather than trusting arbitrary on-chain-published URLs.

### Proof of Concept
1. Attacker (any wallet holder) creates a DataLayer store and calls `dl_new_mirror`/`add_mirror` with `urls=["http://169.254.169.254/latest/meta-data/", "http://internal-admin.local/trigger"]`. [7](#0-6) 
2. The mirror coin is confirmed on-chain.
3. A victim node calls `dl_track_new`/subscribes to the attacker's `store_id` (a normal, low-trust DataLayer client action).
4. The victim's `DataLayerWallet.coin_added` records the malicious URLs, `DataLayer.update_subscriptions_from_wallet` copies them into the subscription table. [3](#0-2) 
5. On the next sync cycle, `fetch_and_validate` → `insert_from_delta_file` → `download_file` → `http_download` issues an outbound HTTP request to the attacker-chosen URL from the victim's server, with no host/IP validation. [8](#0-7) 

**Note on completeness:** I could not retrieve the exact body of `http_download` (its definition wasn't returned within available line ranges I queried), so I cannot confirm whether it performs any lower-level SSRF mitigation (e.g., custom DNS resolution/IP filtering) inside that specific function beyond what is visible in `download_file`'s call site and the `is_filename_valid` check. This is a gap that should be verified directly in `chia/data_layer/download_data.py`'s `http_download` implementation before treating the recommendation as fully novel (i.e., confirm no existing IP allow/deny-list logic exists there).

```python
async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True
```
