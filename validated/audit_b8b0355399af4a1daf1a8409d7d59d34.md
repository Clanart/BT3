### Title
Attacker-controlled preprocess/share vector length causes out-of-bounds indexing panic during FROST signing - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to GoAccess's `parse_browser` — which assumed a fixed structure (`"Opera" + version`) on attacker-controlled bytes and then indexed/moved memory at a fixed offset past the allocation — `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` in `bitcoin-serai` assume attacker-supplied vectors have a fixed structure matching the number of inputs/participants, then index them without any length check. Peer's serialized preprocesses/shares reach these paths through `read_preprocess` / `read_share`, both listed reachable entry points for untrusted bytes.

### Finding Description
`TransactionSignMachine::sign` rebuilds per-input commitment maps by indexing each participant's `Vec<Preprocess>` at input index `c`:

- `networks/bitcoin/src/wallet/send.rs:351-353` — `read_preprocess` collects `self.sigs.len()` preprocesses per `sig.read_preprocess(reader)`, but each participant's `Self::Preprocess` is `Vec<Preprocess<Secp256k1, ()>>` whose element count is whatever the sender serialized (it is deserialized element-by-element; nothing forces it to equal `self.sigs.len()`).
- `networks/bitcoin/src/wallet/send.rs:364-371` — `commitments.iter().map(|(l, commitments)| (*l, commitments[c].clone()))` indexes `commitments[c]` for `c in 0 .. self.sigs.len()`. A peer whose preprocess vector is shorter than `self.sigs.len()` causes a panic on out-of-bounds indexing.

Similarly, in `complete` at `networks/bitcoin/src/wallet/send.rs:417-420`, `shares.remove(0)` is called per input on `Vec<SignatureShare>` values deserialized via `read_share` (`send.rs:409-411`); a share vector shorter than the input count (including empty) panics.

### Impact Explanation
A single participant in a FROST signing session can abort the signing process of every node that consumes their preprocess/share bytes: sending a truncated preprocess vector (or a truncated signature-share vector to the aggregator) causes an unhandled panic rather than a `FrostError`. This is a reachable, remotely-triggered crash of the threshold signing pipeline — the direct Rust analog of the GoAccess heap corruption/crash (panic instead of OOB write). Repeated submissions prevent completion of Bitcoin spend signing for the multisig, stalling aggregation/forwarding transactions.

### Likelihood Explanation
Any party able to submit a preprocess or signature share to a participant/aggregator — i.e., a session participant or anyone whose bytes are routed through `read_preprocess`/`read_share` — can trigger it with a trivially malformed serialization (fewer elements than inputs). No collusion or validator privileges are required beyond being a signer in the round; it costs nothing and deterministically panics on every victim that indexes the vector.

### Recommendation
Validate deserialized vector lengths before indexing:
- In `sign`, check `commitments.len() == self.sigs.len()` for each participant and return `FrostError` instead of indexing blindly.
- In `complete`, pop shares with a length check (`if shares.is_empty() { return Err(...) }`) rather than `remove(0)`.
- Preferably enforce element-count equality inside `read_preprocess`/`read_share` so malformed peer data is rejected at deserialization.
