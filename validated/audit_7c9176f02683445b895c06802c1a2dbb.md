### Title
Side-by-side diff line-selection uses the same column for both "before" and "after" lookups, causing wrong line to be staged/discarded - ([File: app/src/ui/diff/side-by-side-diff.tsx])

### Summary
The reported Hanji bug is a case where a single value is applied twice to two conceptually distinct accounting slots that should have been computed independently, corrupting state. The closest verified analog in this codebase is in `onLineNumberCheckedChanged`, where the "before" and "after" line numbers for a diff row checkbox click are both derived from the exact same call, `this.getDiffLineNumber(row, column)`, instead of one call per column (`DiffColumn.Before` / `DiffColumn.After`). [1](#0-0) 

### Finding Description
`onLineNumberCheckedChanged` is the handler invoked when the user (un)checks a line-selection checkbox in the side-by-side diff view, in order to stage or discard an individual line:

```
const lineBefore = this.getDiffLineNumber(row, column)
const lineAfter = this.getDiffLineNumber(row, column)

if (lineBefore !== null) {
  selection = selection.withLineSelection(lineBefore, isSelected)
}

if (lineAfter !== null) {
  selection = selection.withLineSelection(lineAfter, isSelected)
}
``` [2](#0-1) 

Both `lineBefore` and `lineAfter` are computed with the identical `column` argument that was passed into the handler, rather than explicitly querying `DiffColumn.Before` and `DiffColumn.After` respectively. Elsewhere in the same file, `Modified` rows are known to carry two distinct line numbers — one for the "before" side and one for the "after" side (`r.beforeData.lineNumber` vs `r.afterData.lineNumber`), which are tracked and applied separately: [3](#0-2) 

Given that structure, `getDiffLineNumber(row, column)` is expected to resolve to different underlying diff-line numbers for `Before` vs `After` on a `Modified` row. Because `onLineNumberCheckedChanged` invokes it twice with the *same* `column`, `lineBefore` and `lineAfter` collapse to the same underlying line number. This mirrors the structural flaw in the reported Hanji issue: a value that should have been derived independently for two separate accounting slots is instead derived once and reused, corrupting the second slot's semantics — here, the "opposite" side of a modified line's selection state.

### Impact Explanation
On a `Modified` row (an added and a deleted line rendered together), the "before" (deleted) and "after" (added) lines are two independent diff-line entries that can be independently included/excluded from a partial commit via `DiffSelection` and later turned into a unified diff by `formatPatch`/`applyPatchToIndex`. If checking/unchecking one checkbox erroneously also (or instead of) toggles the line-selection state of the sibling line on the same row, the resulting partial-commit patch generated by `formatPatch` will silently include or drop a line the user did not intend — i.e., it corrupts what the user actually commits or discards, without any error or warning. This falls squarely into the "silent corruption of what the user commits or pushes" impact category, since the same selection-state bit ends up applied to a line the user never selected. [4](#0-3) 

### Likelihood Explanation
This path is reachable purely through normal, unprivileged UI interaction: any user staging changes line-by-line in the side-by-side diff view on a file with `Modified` rows (interleaved add/delete pairs) exercises `onLineNumberCheckedChanged`. No attacker-controlled repository content is strictly required to trigger the bug itself (it is a client-side logic defect), which weakens its fit against the "attacker controls a cloned/fetched repository" framing in the Valid Impact criteria — the bug manifests for any modified-line diff, not specifically an attacker-crafted one. This is the main uncertainty in mapping it to the required threat model: I could not fully verify `getDiffLineNumber`'s implementation in this session (the file location was returned by search but its body wasn't inspected before the tool budget ended), so I cannot confirm with certainty whether the duplicated call actually produces two different values that get silently discarded, or whether it's cosmetically redundant but functionally harmless. This should be verified against `getDiffLineNumber`'s definition before treating this as confirmed-exploitable.

### Recommendation
Verify `getDiffLineNumber`'s signature/behavior for `DiffColumn.Before` vs `DiffColumn.After`. If it does return distinct values per column (consistent with the `beforeData`/`afterData` split seen elsewhere), fix `onLineNumberCheckedChanged` to call `getDiffLineNumber(row, DiffColumn.Before)` for `lineBefore` and `getDiffLineNumber(row, DiffColumn.After)` for `lineAfter`, matching the pattern already used in `getRowSelectableGroupStaticData`. Add a regression test that toggles the checkbox on only the "after" (added) side of a `Modified` row and asserts that only the added line's selection state changes, not the paired deleted line's.

### Proof of Concept
Conceptual reproduction (pending confirmation of `getDiffLineNumber`'s exact semantics):
1. Modify a file such that a hunk contains a `Modified` row (one deleted line immediately followed by one added line), producing a side-by-side row with independent `beforeData.lineNumber` and `afterData.lineNumber`.
2. In the Changes view, side-by-side diff enabled, click the checkbox for only the "after" (added) column on that row to unstage it while leaving the "before" (deleted) column selected.
3. Inspect the actual `DiffSelection` passed to `onIncludeChanged`/the generated patch via `formatPatch` and confirm whether the deleted line's selection state was unexpectedly altered alongside (or instead of) the added line's, due to `lineBefore`/`lineAfter` resolving to the same value.

This could not be fully executed/confirmed within the current session due to tool-call limits; a Devin session with code execution should trace `getDiffLineNumber`'s implementation and run the above scenario to confirm exploitability before treating this as a confirmed vulnerability.

```typescript
export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })
