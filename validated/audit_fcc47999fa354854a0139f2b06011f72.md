### Title
Cached FROST preprocess is keyed only by signing context, not the signing set — nonce reuse across distinct preprocess sets enables validator key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class in the reference report — an authorization/ownership check that fails to bind an object identifier to the security context it is used under — maps onto `SigningProtocol::preprocess_internal`/`share_internal`. A cached FROST nonce seed (`CachedPreprocesses`) is stored and retrieved under `context` alone, while the FROST machine built from it is parameterized by the caller-supplied `participants`/`preprocesses` signing set. Two `sign()` invocations under the same context but with different preprocess sets reuse the same underlying nonces `(d, e)` with different binding factors and challenges, which is the classic parallel-session nonce-reuse condition that allows recovery of the signer's secret share.

### Finding Description
`preprocess_internal` fetches the nonce seed exclusively by context:

```rust
// coordinator/src/tributary/signing_protocol.rs:123-145
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  let (machine, _) = AlgorithmMachine::new(algorithm.clone(), keys.clone()).preprocess(&mut OsRng);
  ...
  CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
...
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

The seed is *not* bound to `participants`, the preprocess map, or the message. `share_internal` then calls `machine.sign(preprocesses, msg)` on whatever attacker-influenced preprocess map was supplied:

```rust
// coordinator/src/tributary/signing_protocol.rs:150-180
let machine = self.preprocess_internal(participants).0;
...
let (machine, share) = machine.sign(preprocesses, msg)...
```

`sign()` derives the effective nonce as `actual = base + rho * nonce_share` where `rho` depends on the entire preprocess set (participant list, commitments, addenda) and the challenge `c` depends on the resulting nonce sum and message (crypto/frost/src/sign.rs:361-398, crypto/frost/src/nonce.rs:161-211). The emitted share is `z = d + rho·e + c·λ·s` with `d, e` fixed by the cached seed and `s` the secret share.

Crucially, `DkgConfirmer::share()` and `DkgConfirmer::complete()` are independent entry points over the *same* context `(b"DkgConfirmer", attempt)` (lines 274-327). `complete` internally re-runs `share_internal` — a second `sign()` over the same cached seed. The preprocess maps passed to `share` and to `complete` need not be identical: they are built from whatever (threshold-indexed) preprocess messages the coordinator has accumulated at that stage via `threshold_i_map_to_keys_and_musig_i_map`. If the included set or any commitment bytes differ between the two calls — e.g., a participant's preprocess arrives before `complete` but after `share`, or a removed-validator change alters the index mapping — the coordinator publishes two distinct shares `z1, z2` over identical `(d, e)` with different `(rho, c, λ)`. A third distinct signing set under the same context yields a solvable linear system for `e` and the secret share `s`.

This is exactly the AppFlowy shape: the object (nonce seed) is looked up by an identifier (`context` = attempt) that is not verified to belong to the workspace-equivalent (the specific `participants`/preprocess set and message it is actually used to sign for).

### Impact Explanation
Recovery of the validator's Ristretto secret share `s`. In the MuSig/t-of-n confirmation protocol, recovering a validator's signing key lets an attacker forge that validator's confirmation shares for arbitrary `set_keys_message` payloads, undermining the DKG-confirmation root of trust. More generally, any caller of `SigningProtocol` that triggers `sign` twice under one context with differing preprocess sets leaks the share. This matches the acceptance criterion of key-share recovery driven by untrusted preprocess bytes fed to `read_preprocess`/`sign`.

### Likelihood Explanation
Medium. Exploitation requires two `sign` executions under the same `(context)` with distinct preprocess maps. The design comments acknowledge nonce reuse is catastrophic and lean on BFT finality, but nothing in `share_internal` or the `CachedPreprocesses` schema enforces that the seed belongs to the supplied set — the code explicitly notes the on-chain preprocess-matches-presumed check is a TODO (lines 50-54). A `share()`-then-`complete()` path, a retry with an enlarged preprocess quorum, or a second signing protocol instance reusing a context encoding all reach the same seed. Three total shares under one seed fully recover `s`; each additional distinct set strengthens the linear system.

### Recommendation
Bind the cached preprocess to its usage: store `CachedPreprocesses` under a key that commits to `(context, participants, serialized preprocess map, msg)` — or record alongside the seed the exact `preprocesses`/`msg` it was signed with and panic/abort if a later `share_internal` call presents a different set. Alternatively, derive the seed deterministically as `H(context || participants || preprocesses || msg || key)` so distinct sessions can never collide, and mark the DB entry consumed after first use.

### Proof of Concept
```rust
// Conceptual: same SigningProtocol context, two different preprocess maps.

// 1) share() executes:
let (m1, share1) = sp.share_internal(&participants, preprocesses_A, msg).unwrap();
//    z1 = d + rho_A * e + c_A * λ_A * s        (seed = CachedPreprocesses[context])

// 2) complete() executes share_internal again with a different included set
//    (an extra participant's preprocess arrived, or index remapping changed):
let (m2, share2) = sp.share_internal(&participants, preprocesses_B, msg).unwrap();
//    z2 = d + rho_B * e + c_B * λ_B * s        (SAME seed: d, e identical)

// rho_A, rho_B, c_A, c_B, λ_A, λ_B are all publicly computable from the
// preprocess bytes and msg (crypto/frost/src/sign.rs:361-398).
// z1 - z2 = (rho_A - rho_B) * e + (c_A λ_A - c_B λ_B) * s
// A third session (preprocesses_C) yields a second independent equation:
//   solve 2x2 system -> e, and then s = secret share.
// Then d = z1 - rho_A*e - c_A*λ_A*s and any share over this seed is forgeable.
```

The same seed persisting under `context` regardless of the signing set is the root cause; `AlgorithmSignMachine::from_cache` happily regenerates identical `nonces` for every call since `seeded_preprocess` is deterministic in `cache`.
