### Title
Cross-transaction instruction contamination lets a later Bitcoin transaction hijack an earlier Serai deposit - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
`Bitcoin::get_outputs` reuses one `outputs` vector across all transactions in a block. Whenever a later transaction contains any scanned output, it writes that transaction’s `presumed_origin` and embedded Serai instruction to every previously accumulated output, including outputs created by earlier unrelated transactions. An attacker can therefore overwrite the instruction belonging to another depositor and redirect the resulting minted funds. [1](#0-0) 

### Finding Description
The scanner collects matching outputs into a block-level `outputs` vector at lines 689–700. After processing each transaction, the condition at lines 702–704 tests whether this cumulative vector is empty rather than whether the current transaction produced outputs. It then calculates `presumed_origin` from the current transaction’s first input, extracts the current transaction’s Serai data, and assigns both values to every entry in `outputs` at lines 730–735. [1](#0-0) 

`extract_serai_data` accepts instruction bytes from an `OP_RETURN` output or from a specially shaped witness input. [2](#0-1)  These bytes are decoded as a `Shorthand`, converted into a `RefundableInInstruction`, and paired with each output’s own balance. [3](#0-2)  The multisig scanner then queues each resulting `InInstructionWithBalance` for inclusion in a batch. [4](#0-3) 

Consequently, transaction `B` can replace the instruction and presumed origin previously assigned to a Serai output from earlier transaction `A` in the same block. No external callback or malformed encoding is required; the attacker only needs to submit ordinary Bitcoin transaction data. [1](#0-0) 

### Impact Explanation
A deposit can be credited under an instruction supplied by a different transaction. For example, a victim transaction can specify `Transfer(victim_serai_address)`, while a later attacker transaction specifies `Transfer(attacker_serai_address)`. The later assignment overwrites the victim output’s `data`, causing the victim’s Bitcoin amount to be paired with the attacker’s destination instruction. [5](#0-4) [6](#0-5) 

The balance itself remains the victim output’s amount because `instruction_from_output` reads `output.balance()` separately from the instruction bytes. [7](#0-6)  This produces an unauthorized transfer/mint of the deposited value to the attacker-selected instruction rather than merely corrupting metadata.

### Likelihood Explanation
Any party capable of submitting Bitcoin transactions can supply the malicious transaction and its instruction data. [2](#0-1)  The attack requires the malicious transaction to be scanned after the victim transaction in the same block.

Block ordering does not necessarily require miner control. If the victim transaction also creates an output spendable by the attacker—for example, a payment or attacker-controlled change output—the attacker can broadcast a child transaction spending that output and paying the Serai external address while carrying the malicious `OP_RETURN` instruction. Consensus transaction ordering requires the child to appear after its parent. [1](#0-0) 

The attacker’s added output only needs to satisfy the processor’s Bitcoin dust threshold of `10_000` satoshis so it is retained by the multisig scanner. [8](#0-7) [9](#0-8) 

### Recommendation
Track scanned outputs on a per-transaction basis. Populate `data` and `presumed_origin` immediately after scanning each transaction and move only that transaction’s outputs into the block-level result, or store the producing transaction index on each `Output` and refuse to mutate metadata belonging to other transactions. [1](#0-0) 

For example, replace the cumulative mutation with a local `tx_outputs` vector:

```rust
// processor/src/networks/bitcoin.rs
for tx in &block.txdata[1..] {
  let mut tx_outputs = vec![];

  for output in scanner.scan_transaction(tx) {
    // construct Output and push it into tx_outputs
  }

  if tx_outputs.is_empty() {
    continue;
  }

  let presumed_origin = /* current transaction's origin */;
  let data = Self::extract_serai_data(tx);

  for output in &mut tx_outputs {
    // assign only this transaction's metadata
  }

  outputs.extend(tx_outputs);
}
```

Add a regression test containing two Serai-paying transactions in one block with different instructions and origins, asserting that each returned `Output` retains the instruction from its own transaction.

### Proof of Concept
Construct a block containing:

1. `tx_victim`, which creates:
   - one output paying the Serai external scanner address;
   - an `OP_RETURN` encoding `Shorthand::transfer(None, victim_serai_address)`;
   - one output spendable by the attacker.
2. `tx_attacker`, which spends the attacker-controlled output from `tx_victim`, ensuring it follows `tx_victim` in the block, and creates:
   - one output of at least `10_000` satoshis paying the same Serai external scanner address;
   - an `OP_RETURN` encoding `Shorthand::transfer(None, attacker_serai_address)`.

During `get_outputs`, `tx_victim` first inserts its output with the victim instruction. `tx_attacker` then inserts its own output, sees the cumulative vector as non-empty, and executes the mutation loop over both entries. Both `Output` objects leave `get_outputs` carrying `attacker_serai_address`; `instruction_from_output` subsequently emits two instructions using their respective output balances. [10](#0-9) [11](#0-10) 

The behavioral assertion is:

```rust
assert_eq!(outputs[0].data(), attacker_instruction);
assert_eq!(outputs[1].data(), attacker_instruction);
```

The expected result is instead that `outputs[0].data()` remains `victim_instruction`.
