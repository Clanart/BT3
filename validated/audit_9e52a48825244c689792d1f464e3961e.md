### Title
Unauthenticated panic in PedPoP blame evaluation via unregistered participant index (`enc_keys[&decryptor]` / `commitments[&sender]`) - (crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2019-10207 is a crash bug: a crafted ioctl lets a local attacker panic the kernel. The direct analog in Serai is an attacker-controlled panic in the PedPoP DKG blame path. `Decryption::decrypt_with_proof` verifies an attacker-supplied message/proof and then indexes `self.enc_keys[&decryptor]` — a `HashMap` index that panics if the `decryptor` participant was never registered. The same pattern exists for `self.commitments[&sender]` in `blame_internal`. Both `sender` and `recipient` (`decryptor`) are plain `Participant` values passed to the public `BlameMachine::blame` / `AdditionalBlameMachine::blame` APIs, and `Participant::new` accepts any non-zero `u16`, so indexes outside the DKG set are representable.

### Finding Description
`blame` → `blame_internal` → `decrypt_with_proof(sender, recipient, msg, proof)` at `crypto/dkg/pedpop/src/lib.rs:582`. Inside `decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs`):

```rust
if !msg.pop.verify(msg.key, pop_challenge::<C>(..., from, ...)) {
  Err(DecryptionError::InvalidSignature)?;   // line ~374-379
}
if let Some(proof) = proof {
  proof.dleq.verify(&mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key])  // line ~388: PANIC if decryptor unregistered
```

Two reachable panic sites from untrusted input:

1. `self.enc_keys[&decryptor]` (encryption.rs:388). For a `BlameMachine` produced by `KeyMachine::calculate_share`, `enc_keys` is populated by `encryption.register` only for *other* participants during `verify_r1` (`lib.rs:313-315`); the machine's own index `params.i()` is never inserted (own key lives in `Encryption::enc_pub_key`, dropped by `into_decryption`). Any blame statement — honest or malicious — naming `recipient == params.i()` with a validly-signed `msg.pop` and `Some(proof)` panics the process.
2. `self.commitments[&sender]` (`lib.rs:599`) and `enc_keys[&decryptor]` again for `AdditionalBlameMachine`: `AdditionalBlameMachine::new` registers only participants `1..=n`, but `blame(sender, recipient, …)` accepts arbitrary `Participant` indexes (e.g., 65535), panicking on the map index.

The attacker needs the `msg`'s Schnorr PoP to verify to reach the indexing line — trivially satisfiable since they can sign a PoP for a key they generated (as `encrypt` does). `msg` and `proof` are untrusted bytes via `EncryptedMessage::read` / `EncryptionKeyProof::read`.

### Impact Explanation
Any node evaluating blame — either the accused/accuser participant's `BlameMachine`, or an arbiter's `AdditionalBlameMachine` — panics (process abort / unwound async task) when presented with a blame statement whose `recipient` (or `sender`, on the deeper path) is a participant index lacking a registered encryption key. This is a remote, input-triggered denial of service of the DKG fault-resolution path: a single crafted `(sender, recipient, EncryptedMessage, EncryptionKeyProof)` tuple crashes the evaluator, mirroring the CVE's "specially crafted call crashes the system". A malicious DKG participant can also deliberately name the victim's own index as `recipient` with a well-formed message to crash the victim's blame handling.

### Likelihood Explanation
Reachable whenever blame evaluation is invoked on attacker-influenced `(sender, recipient)` values and attacker-controlled message/proof bytes — both are public inputs in the blame protocol (the message is a relayed `EncryptedMessage`, the proof is supplied by the accuser). The only gate is a Schnorr PoP verification the attacker can legitimately satisfy. Triggering requires the blame path to run, which happens after a DKG fault, so frequency is moderate; severity is a clean panic, matching Medium.

### Recommendation
Replace `HashMap` indexing with fallible lookups in `Decryption::decrypt_with_proof` and `blame_internal`: use `enc_keys.get(&decryptor)` / `commitments.get(&sender)` and map `None` to a defined outcome (e.g., treat unregistered `sender`/`recipient` as faulty, or return an error). Also validate `sender`/`recipient` against `all_participant_indexes` at the top of `BlameMachine::blame` and `AdditionalBlameMachine::blame` before any verification work.

### Proof of Concept
```rust
// AdditionalBlameMachine path (crypto/dkg/pedpop)
let machine = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();

// Attacker submits a blame claim naming a participant index outside 1..=n,
// e.g. Participant(0xffff), as the recipient/decryptor.
let bogus_recipient = Participant::new(u16::MAX).unwrap();

// msg: EncryptedMessage with attacker-chosen key k, pub_key = G*k, and a
// SchnorrSignature::sign(k, r, pop_challenge(context, R, pub_key, sender, ciphertext))
// -> msg.pop.verify(...) passes, so execution reaches `enc_keys[&decryptor]`.
// proof: Some(attacker-crafted EncryptionKeyProof) (only needs to reach the indexing line)
machine.blame(sender, bogus_recipient, msg, Some(proof));
// -> panic: "key not found" at encryption.rs (`self.enc_keys[&decryptor]`)
```
The equivalent `BlameMachine::blame(sender, params.i(), msg, Some(proof))` panics even in fully honest operation, since `enc_keys` never contains the local participant's own index (it is registered only for the *other* participants in `verify_r1`).
