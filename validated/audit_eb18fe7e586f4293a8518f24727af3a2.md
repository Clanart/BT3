## Title
Stale line-index diff selection is silently reapplied to a freshly-fetched diff during partial commit staging, corrupting committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
This is the same "stale cached value combined with fresh state" bug class as the `svTokenValue` issue: a value (`totalSupply`) computed at one point in time is used to make a calculation (`equityValue / totalSupply`) without validating that it still reflects the current state (`pendingFee`). In GitHub Desktop, the analogous corrupted value is `WorkingDirectoryFileChange.selection` — a `DiffSelection` object that records *line indices* the user selected in a previously rendered diff. When a partial commit is staged, Desktop re-fetches a brand-new diff for the file and blindly re-applies the old, index-based selection to it, without verifying the new diff has the same hunk layout.

### Finding Description
`applyPatchToIndex` re-fetches the diff at staging time rather than using the diff the user actually reviewed: [1](#0-0) 

That freshly-fetched diff is then handed to `formatPatch`, which decides what to include using `file.selection.isSelected(absoluteIndex)` — an index computed against the diff that existed when the user made their line/hunk selection, not the diff that was just re-fetched: [2](#0-1) 

`_commitIncludedChanges` takes the `WorkingDirectoryFileChange[]` snapshot straight out of `repositoryStateCache` and passes it into `createCommit` → `stageFiles` → `applyPatchToIndex` without any revalidation step that the selection is still consistent with current file content: [3](#0-2) 

The only place Desktop reconciles a selection against a changed diff is `updateChangesWorkingDirectoryDiff`, and it explicitly narrows its guarantee to "updating the selectable lines" for the *single currently displayed* file — it does not assert the previously selected line positions still correspond to the same content, and it is not invoked as part of the commit path at all: [4](#0-3) 

Likewise, `updateChangedFiles` (run on every background status refresh) simply carries the old `existingFile.selection` object forward onto the new file object whenever a file with the same id still exists, again without checking hunk-shape compatibility: [5](#0-4) 

Because `DiffSelection.isSelected` operates purely on absolute line-index arithmetic, not content hashes or hunk anchors, if the working tree file's diff shape changes between when the user made a partial line selection and when the commit is actually staged (e.g., the file is edited again, reformatted, or touched by a build tool/git filter while Desktop's background status refresh hasn't caught up), the indices from the old selection now point at completely different lines in the new diff. `formatPatch` will happily construct a patch that includes/excludes lines the user never reviewed or intended.

### Impact Explanation
The result is silent corruption of what the user commits: the staged/committed patch can differ from what was shown and selected in the UI, with no error or warning, exactly matching the "silent corruption of what the user commits or pushes" impact category. Since partial (line-level) commit selection is a core, heavily used Desktop feature, this can lead to unintended lines being committed or omitted — data that the user explicitly chose to exclude could end up in a commit (or vice versa), all without any indication in the UI.

### Likelihood Explanation
This does not require local/admin access or pre-existing malware — it only requires the working tree content to change between the diff render and the click of "Commit", which is a completely ordinary occurrence: external editors autosaving, linters/formatters running, file watchers, or git attribute-driven smudge/clean filters triggered by content in a cloned repository. Desktop's own architecture (async status refresh, separate diff-fetch call at staging time) creates the race window; no unnatural user steps are needed.

### Recommendation
Before calling `formatPatch`/`applyPatchToIndex`, re-validate that the newly fetched diff has the same hunk/line layout the selection was computed against (e.g., compare hunk headers or line content hashes), and if it has changed, abort the partial-stage and force the user to re-review the diff — analogous to adding the missing "pending" delta into the calculation instead of using the stale value outright.

### Proof of Concept
1. Modify a tracked file and open it in Desktop's Changes view; select only specific lines/hunks for the commit (partial selection), leaving other hunks unselected.
2. Before pressing "Commit", externally modify the same file in a way that shifts hunk boundaries (e.g., insert/remove a line above the previously selected hunk) without Desktop's background diff view being manually refreshed for that specific pending selection object.
3. Click "Commit". `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3681`) passes the stale `WorkingDirectoryFileChange` (with old-index selection) into `createCommit` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`), which fetches a new diff and calls `formatPatch` using the stale `isSelected(absoluteIndex)` (`app/src/lib/patch-formatter.ts:157`).
4. Inspect the resulting commit: it contains different lines than what was visually checked/unchecked by the user in step 1, with no warning surfaced.
