### Title
CW20-wrapped-ERC20 pointer contract silently discards `IncreaseAllowance`/`DecreaseAllowance` expiration, giving spenders a perpetual, un-revocable-by-time allowance the owner cannot bound - (File: example/cosmwasm/cw20/src/contract.rs)

### Summary
The CW20 pointer contract that wraps a Sei EVM ERC20 token accepts the standard CW20 `IncreaseAllowance { spender, amount, expires }` / `DecreaseAllowance { spender, amount, expires }` messages but explicitly discards the `expires` field before forwarding the approval to the underlying ERC20 contract, and `query_allowance` always reports `Expiration::Never{}` regardless of what the owner specified.

### Finding Description
In the CW20-ERC20 pointer contract's `execute` entrypoint, both allowance-mutating variants pattern-match the `expires` field only to drop it: [1](#0-0) 

The corresponding handlers only ever forward `spender`/`amount` to the ERC20 `approve` call via the EVM delegatecall payload, with no expiration logic at all: [2](#0-1) 

and the query path hardcodes the expiration as `Never`, matching the fact that ERC20 `approve` has no expiry concept: [3](#0-2) 

This mirrors the Cooler `roll()` bug class exactly: the CW20 standard exposes a parameter (`expires`) that a token owner (the "lender" analog) uses to bound how long a permission granted to another account (the "borrower"/spender analog) remains valid. The implementation accepts that parameter, silently ignores it, and grants an allowance that is functionally unbounded in time — the owner has no way, through the CW20 interface, to cap the spender's window of use, just as the Cooler lender has no way to cap the number of `roll()` extensions. The owner believes they set a time-bounded allowance (as CW20/ CW20 clients generally assume, since `AllowanceResponse.expires` is a first-class, relied-upon field across the CW20 ecosystem), but the spender can call `TransferFrom`/`SendFrom` against that allowance indefinitely, long after the owner's intended expiration, until the owner notices and manually revokes it.

### Impact Explanation
Any CosmWasm caller/integrator that relies on the standard CW20 `expires` semantics to auto-expire a spending permission (e.g., a DEX router, escrow, or automated allowance granted for a single session/campaign) will have that allowance persist forever on this pointer contract. If the owner does not proactively call `DecreaseAllowance` after the intended expiry, the previously-authorized spender retains an unauthorized, indefinite ability to pull funds via `TransferFrom`, resulting in unauthorized transfer / fund loss for the owner — directly analogous to the "lender cannot bound duration" impact in the source report.

### Likelihood Explanation
Likelihood requires that (a) a user actually supplies a non-`Never` `expires` value expecting it to be honored, and (b) they do not manually clean up the allowance afterward. Because CW20 tooling and many contracts pass `expires` routinely, this is a plausible, non-adversarial usage pattern rather than a contrived edge case. I could not fully confirm from the indexed code whether this specific contract under `example/cosmwasm/cw20/` is the exact canonical, production-deployed CW20↔ERC20 pointer contract instantiated by the live pointer-creation flow, or purely a reference/sample contract shipped for documentation/testing purposes — grep only found self-references within this same directory, with no wiring found from the Go-side pointer-factory code in the indexed portion of the repo. This should be verified against the actual deployed pointer contract bytecode/instantiation path before treating this as confirmed production-exploitable.

### Recommendation
Either (1) implement real expiration tracking (store `expires` per `(owner, spender)` in contract state and check it in `transfer_from`/`send_from`/`query_allowance`, rejecting/zeroing allowances past their expiry), or (2) if expiration truly cannot be supported due to ERC20's limitations, reject `IncreaseAllowance`/`DecreaseAllowance` calls that specify a non-`Never` `expires` value with `ContractError::NotSupported`, rather than silently accepting and discarding the parameter.

### Proof of Concept
1. Owner calls `IncreaseAllowance { spender, amount: X, expires: Expiration::AtTime(T) }` on the CW20 pointer, expecting the spender's rights to lapse at time `T`.
2. The contract calls `execute_increase_allowance`, which never looks at `expires` and issues an ERC20 `approve(spender, X)` with no expiry: [4](#0-3) 
3. After time `T` passes, `query_allowance` still reports `expires: Expiration::Never{}` and the ERC20 allowance is unchanged: [3](#0-2) 
4. The spender calls `TransferFrom`/`SendFrom` for up to `X` tokens at any point after `T`, which succeeds because the underlying ERC20 allowance was never revoked: [5](#0-4)

// Increase the allowance of spender by amount.
// Expiration does not work here since it is not supported by ERC20.
pub fn execute_increase_allowance(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    spender: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&spender)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);

    // Query the current allowance for this user
    let current_allowance = querier.erc20_allowance(erc_addr.clone(), info.sender.clone().into_string(), spender.clone())?.allowance;

    // Set the new allowance as the sum of the current allowance and amount specified
    let new_allowance = current_allowance + amount;

    // Send the message to approve the new amount
    let payload = querier.erc20_approve_payload(spender.clone(), new_allowance)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };

    let res = Response::new()
        .add_attribute("action", "increase_allowance")
        .add_attribute("spender", spender)
        .add_attribute("amount", amount)
        .add_attribute("new_allowance", new_allowance)
        .add_attribute("by", info.sender)
        .add_message(msg);

    Ok(res)
}

pub fn query_allowance(deps: Deps<EvmQueryWrapper>, owner: String, spender: String) -> StdResult<Binary> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&spender)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let allowance = querier.erc20_allowance(erc_addr, owner, spender)?;
    to_json_binary(&AllowanceResponse{allowance: allowance.allowance, expires: Expiration::Never{}})
}
