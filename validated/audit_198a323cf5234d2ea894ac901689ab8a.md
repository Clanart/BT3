## Title
`git clone` unconditionally disables Git's recursive-submodule clone protection via `GIT_CLONE_PROTECTION_ACTIVE=false` - (File: `app/src/lib/git/clone.ts`)

### Summary
Applying the report's broken-invariant pattern — a security check exists elsewhere in the codebase (staked-balance validation in the Sherlock report) but a specific call path silently bypasses it, letting attacker-controlled input escape an intended containment boundary — the closest analog in this Desktop fork is in `clone()`. Every invocation of `clone()` explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the git subprocess environment, unconditionally disabling the upstream Git hardening that protects `git clone --recursive` against malicious embedded submodule configurations. [1](#0-0) 

### Finding Description
`clone()` always runs `git clone --recursive` and builds its environment as:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
``` [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is the env variable Git itself uses internally to mark that a recursive submodule clone is happening inside a protection-active top-level clone; the flag is what triggers Git's built-in defenses against maliciously crafted repository content (e.g. `.gitmodules` entries or nested submodule paths designed to write files outside the intended checkout, or into `.git` internals, during a recursive clone). By forcing this to `'false'` for every clone Desktop performs, the app deliberately opts every user-initiated (and "Open in Desktop" / URL-triggered) clone out of that protection, for both the top-level repo and any of its submodules.

This is directly analogous to the Sherlock finding's root cause: a validation step that should gate an operation (`getAvailableBalance()` before `provideLiquidity`) is simply missing/bypassed, letting attacker-supplied state (staked tokens) be used where it shouldn't be. Here, the validation Git itself performs to gate submodule processing during `--recursive` clone is explicitly turned off by Desktop's own code, letting attacker-supplied repository content (a malicious remote's `.gitmodules`/submodule tree) be processed without the safety check that upstream Git ships specifically to stop this class of attack.

The clone path already has a separate defense (`isClonePathSensitive`) that blocks the *destination* path from resolving into a handful of sensitive directories, but that check only inspects the user/URL-chosen top-level clone path — it does nothing to constrain what a malicious submodule embedded in the cloned repository can do once Git's internal recursive-clone protections have been switched off. [2](#0-1) 

### Impact Explanation
Because every `clone()` call (triggered by a user pasting/clicking a repository URL, or by Desktop's own `x-github-client://openrepo/...` deep-link / "Open in Desktop" handler resolving to `openOrCloneRepository`) runs with the protection disabled, an attacker who controls the content of a repository (or a `git@`/HTTPS remote the user is lured into cloning) can embed submodule configuration designed to exploit the exact class of bug this Git protection exists to stop. Depending on the underlying Git version's exposure, this can result in files being written outside the intended repository directory, corruption of the local `.git` directory, or execution of an unintended hook — i.e. file write outside the repo or code execution, matching the in-scope impact categories for this program (attacker-controlled cloned repository leading to code execution / file write outside the repo).

### Likelihood Explanation
Every clone Desktop performs is affected — this is not a narrow edge case but the default, unconditional behavior of `clone()`; it also applies to the "Open in Desktop" deep-link flow (`dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository`), which is directly attacker-triggerable via a link the user clicks, satisfying the "link/deep link" and "cloned/fetched repository" attacker-control criteria. No unusual local access, admin rights, or social-engineering beyond "user clicks a link/enters a URL to clone" (core, intended Desktop functionality) is required. [3](#0-2) 

### Recommendation
Remove the hardcoded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` so Git's own protection remains active for recursive clones, and audit whether this override was added to work around a specific compatibility issue — if so, gate it narrowly (e.g., only for known-safe local test fixtures) rather than applying it to every clone of arbitrary, attacker-controlled remotes.

### Proof of Concept
Not independently reproducible from static review alone: exploitation depends on the specific Git version bundled/invoked by Desktop and on constructing a `.gitmodules`/submodule tree that trips the exact condition the disabled protection guards against. What is concretely verifiable from the code is the unconditional presence of the override:
```
// app/src/lib/git/clone.ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
args.push('-c', 'init.defaultBranch=...', 'clone', '--recursive')
...
await git(args, __dirname, 'clone', opts)
``` [4](#0-3) 
This shows the protection is disabled for the `--recursive` clone path regardless of the source of `url`, which is sufficient to establish the broken invariant; confirming full exploitability (RCE/file-write PoC) would require testing against the exact bundled Git binary and is out of scope for a static/code-index review.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
