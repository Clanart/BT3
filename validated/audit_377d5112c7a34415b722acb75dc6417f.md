### Title
Race condition in `CW20ERC20Pointer.approve()` allows a spender to consume more than the intended allowance via a read-then-diff approve pattern - ([File: contracts/src/CW20ERC20Pointer.sol])

### Summary
`CW20ERC20Pointer.approve()` implements the standard `IERC20.approve(spender, amount)` interface on top of a CW20 contract that only exposes `increase_allowance`/`decrease_allowance` messages. To do this, it reads the *current* allowance at execution time and issues a CW20 `increase_allowance` or `decrease_allowance` message for the *delta* between the current and requested allowance. [1](#0-0) 

Because the delta is computed from the allowance value observed at the moment the `approve()` EVM transaction executes (not from a value fixed when the owner decided/queued the change), a spender can front-run the owner's `approve()` call by first draining the existing allowance via `transferFrom`, and then let the owner's `approve()` transaction land afterward. The pointer will see the (now-drained) allowance and compute a delta that effectively grants the spender the *full new amount on top of* what was already transferred, rather than replacing it — exactly the same "sum exceeds any single intended cap" failure mode described in the reported Teller `updateCommitment`/`acceptCommitment` race.

### Finding Description
`approve()` is implemented as:
```solidity
function approve(address spender, uint256 amount) public override returns (bool) {
    ...
    uint256 currentAllowance = allowance(msg.sender, spender);
    if (currentAllowance > amount) {
        // decrease_allowance by (currentAllowance - amount)
    } else if (currentAllowance < amount) {
        // increase_allowance by (amount - currentAllowance)
    }
    return true;
}
``` [1](#0-0) 

The `currentAllowance` is read live from the CW20 contract's state (via `WasmdPrecompile.query`) at the time the `approve()` transaction executes on-chain, not from a value the caller assumed when constructing/submitting the transaction. This means the actual allowance mutation is a function of whatever the on-chain allowance happens to be at execution time, which an adversarial spender fully controls by choosing when to call `transferFrom` relative to the owner's pending `approve()` transaction — this is precisely the classic ERC20 approve front-running/race condition, here made concrete and exploitable through Sei's CW20↔ERC20 pointer bridge.

Concrete scenario:
1. Owner has granted spender an allowance of 10 (via CW20 `increase_allowance`).
2. Owner decides to reduce the allowance to 8 and submits `pointer.approve(spender, 8)`.
3. Spender sees this pending transaction and front-runs it with `transferFrom(owner, spender, 10)`, draining the full existing allowance to 0 and receiving 10 tokens.
4. Owner's `approve(spender, 8)` transaction now executes: it reads `currentAllowance = 0` (already drained), and since `0 < 8`, it issues `increase_allowance(spender, 8)`.
5. Final state: spender has already received 10 tokens AND now has a fresh allowance of 8 — a total exposure of 18, exceeding both the original (10) and the intended new (8) limits, exactly mirroring the Teller `maxPrincipal` race where the borrower ends up consuming more than either the old or new cap.

### Impact Explanation
This allows an unauthorized/excess transfer of the pointed CW20 asset beyond any allowance limit the token owner ever intended to be in effect at one time, i.e., direct fund loss for the owner through the CW20↔ERC20 pointer contract. Since `CW20ERC20Pointer` is a bridge contract wrapping arbitrary CW20 tokens for EVM consumption, this is reachable by any EVM account interacting with a CW20 pointer and constitutes concrete unauthorized transfer via a pointer contract.

### Likelihood Explanation
Any spender who has been granted a nonzero allowance and observes (via public mempool/RPC) that the owner is about to change that allowance can trivially front-run with a `transferFrom` call. No special privileges are required — only a standard EVM transaction from the spender's own account, reachable by any public JSON-RPC client.

### Recommendation
Do not compute the increase/decrease delta from the allowance value read live during `approve()` execution. Instead, follow the well-known safe-approve mitigation: require the caller to reset the allowance to zero before setting a new nonzero value (revert if `currentAllowance != 0 && amount != 0`), or expose explicit `increaseAllowance`/`decreaseAllowance` functions that operate on an amount specified by the caller rather than a value derived from a diff against on-chain state read at execution time.

### Proof of Concept
1. Owner calls `pointer.approve(spender, 10)` → CW20 allowance(owner, spender) = 10.
2. Owner submits `pointer.approve(spender, 8)` intending to lower the allowance.
3. Spender detects the pending tx and submits `pointer.transferFrom(owner, spender, 10)` with higher gas price to front-run it; this succeeds because current allowance is still 10, draining it to 0 and moving 10 tokens to spender.
4. Owner's `approve(spender, 8)` executes next: `currentAllowance` (read live) = 0, so it issues CW20 `increase_allowance(spender, 8)`, resulting in a final allowance of 8.
5. Net effect: spender obtained 10 tokens via `transferFrom` plus a fresh 8-token allowance — 18 total exposure versus the owner's intended maximum of 8 (or original 10).

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
