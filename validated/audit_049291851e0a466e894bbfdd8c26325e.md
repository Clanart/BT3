### Title
Unauthenticated `InternalSendTx` broadcast bypass via `Noop` interceptor - ([File: core/src/servers.rs], [File: core/src/rpc/interceptors.rs])

### Summary
The `is_internal()` authorization check that is supposed to gate all `Internal*`-prefixed RPCs (including `internal_send_tx`) is only invoked inside `only_aggregator_and_self`, never inside `Noop`. When `client_verification=false`, `create_grpc_server` installs `Noop` as the interceptor, so every RPC — including `internal_send_tx` — is reachable by any unauthenticated caller on the gRPC port.

### Finding Description
The intended binding is: `caller of Internal* RPC == aggregator/self (leaf_cert == our_cert)`. This is enforced only in `only_aggregator_and_self`: [1](#0-0) 

`Noop`, used whenever `config.client_verification` is `false`, performs no such check at all — it unconditionally forwards the request: [2](#0-1) 

`create_grpc_server` selects between the two interceptors purely based on `config.client_verification`, with no fallback enforcement of the internal-method restriction when TLS/mTLS is disabled: [3](#0-2) 

As a result, when `client_verification=false`, an attacker with plain network access to the aggregator's gRPC port can call `InternalSendTx` directly, with no certificate, no `is_internal` gate, and no other authorization layer between the transport and the handler.

### Impact Explanation
This qualifies as the "High - an unauthenticated state-changing or broadcasting call" category by itself: `internal_send_tx` forwards a transaction into the tx-sender/broadcast pipeline, and reaching it requires no authentication under this configuration. I could not retrieve the body of `internal_send_tx` in `core/src/rpc/aggregator.rs` to confirm whether it accepts a fully attacker-controlled raw transaction or only re-broadcasts/tracks a transaction already known to the tx-sender (e.g., validated against DB-stored, previously-signed transactions). That distinction determines whether this escalates to Critical (unauthorized spend of a bridge-controlled UTXO) or remains bounded to the High "unauthenticated broadcast" category. Absent that confirmation, I can only substantiate the High-severity claim: unauthenticated access to an `Internal*` state-changing/broadcasting RPC.

### Likelihood Explanation
The exploit requires the deployment to run with `client_verification=false`. I was not able to confirm in the available time whether this is the actual default value of `BridgeConfig::client_verification` (the field's default is set in `core/src/config/mod.rs`/`core/src/config/env.rs`, which I could not fully inspect before running out of iterations) or whether production configs (e.g., `scripts/docker/configs/testnet4/bridge_config.toml`) explicitly enable client verification. If mTLS/client verification is enabled by default and in real deployments, this path does not exist since `OnlyAggregatorAndSelf` (which does enforce `is_internal`) would be used instead.

### Recommendation
Enforce the `is_internal()` restriction unconditionally, independent of `client_verification`/interceptor choice — e.g., check `is_internal(&req)` inside `Noop::call` too and reject internal-prefixed methods when there is no way to verify caller identity, or move the internal-method check into a layer that always runs regardless of the configured `Interceptors` variant.

### Proof of Concept
Not fully substantiated: verifying the exploit requires (1) confirming the actual default/deployed value of `client_verification`, and (2) reading the `internal_send_tx` handler body in `core/src/rpc/aggregator.rs` to determine whether it broadcasts an attacker-supplied raw transaction or only operates on already-tracked/signed transactions. I could not retrieve either within the available tool budget, so I cannot provide a concrete `cargo test` proof with confirmed assertions on both sides of the binding. This should be treated as a structurally-confirmed authorization gap (interceptor code) pending confirmation of the two open items above before filing at Critical severity.
