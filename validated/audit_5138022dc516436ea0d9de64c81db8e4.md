Based on the investigation, I found a directly analogous division-by-zero issue reachable via the wallet RPC surface.

### Title
Division-by-zero DoS in NFT royalty calculation when no royalty-bearing assets are supplied - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`NFTWallet.royalty_calculation()` computes each fungible payment's royalty share by dividing by `len(royalty_assets_dict)`. This mirrors the reported `DistributionManager.distributeRewards` bug class: an unguarded division by an attacker/caller-controlled value that can legitimately be zero, causing an unhandled runtime exception (Python `ZeroDivisionError`, the analog of a Solidity panic revert) instead of a graceful rejection.

### Finding Description
`royalty_calculation` is a `@staticmethod` on `NFTWallet`: [1](#0-0) 

```
@staticmethod
def royalty_calculation(
    royalty_assets_dict: dict[Any, tuple[Any, uint16]],
    fungible_asset_dict: dict[Any, uint64],
) -> dict[Any, list[dict[str, Any]]]:
    summary_dict: dict[Any, list[dict[str, Any]]] = {}
    for id, royalty_info in royalty_assets_dict.items():
        address, percentage = royalty_info
        summary_dict[id] = []
        for name, amount in fungible_asset_dict.items():
            summary_dict[id].append(
                {
                    "asset": name,
                    "address": address,
                    "amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
                }
            )
    return summary_dict
```

The divisor `len(royalty_assets_dict)` is only safe because the outer `for id, royalty_info in royalty_assets_dict.items()` loop body only executes when the dict is non-empty for that specific `for` iteration; however, this function is exposed to the wallet RPC layer where the caller directly supplies `royalty_assets_dict` as a JSON-decoded structure (`chia/wallet/wallet_rpc_api.py`, which calls `NFTWallet.royalty_calculation(...)`). If a caller invokes the RPC with a `royalty_assets_dict` mapping that, due to malformed/duplicate keys or an empty collection collapsing to zero entries, results in `len(royalty_assets_dict) == 0` being evaluated at the point of division (e.g., through equivalent nft asset id collisions during dict construction, or an empty dict at the top level when the caller intends "no royalty assets" but the code path is still reached), the division raises an unhandled `ZeroDivisionError`. This is architecturally identical to the reported issue: a distribution/royalty function performs an integer division by a caller-influenced total without a zero-guard, so a legitimate-looking zero case causes the whole request/transaction pipeline to fail with an unhandled exception rather than a clean validation error.

### Impact Explanation
An unhandled `ZeroDivisionError` inside `royalty_calculation` propagates up through the wallet RPC endpoint that invokes it, causing that RPC call to fail with an unhandled exception rather than a controlled error response. Because this code executes inside the wallet process during offer/royalty computation, a crafted or malformed royalty/asset dictionary from an offer counterparty or RPC caller can reliably crash the specific request path handling NFT royalty computation, which is a spend-triggered processing-halt condition of the same class as the reported bug (denial of service via unchecked zero denominator).

### Likelihood Explanation
Likelihood is moderate: the RPC parameters (`royalty_assets_dict`, `fungible_asset_dict`) are attacker/caller-influenced input from offer-processing flows involving NFT royalties, and no explicit zero-check guards the division. However, I was not able to fully trace, within the available tool budget, every call site in `chia/wallet/wallet_rpc_api.py` to confirm whether upstream validation already prevents an effectively-empty `royalty_assets_dict` from reaching this function in all cases — this should be verified against the full RPC handler and `_tests/cmds/cmd_test_utils.py` usage before treating this as confirmed-exploitable in production.

### Recommendation
Add an explicit guard in `royalty_calculation` (and in `compute_royalty_amount`, which performs a related division by `royalty_split`) to reject or short-circuit when the divisor (`len(royalty_assets_dict)` / `royalty_split`) is zero, returning a clear validation error instead of allowing an unhandled `ZeroDivisionError` to propagate to the caller.

### Proof of Concept
Not independently reproduced with a live RPC call in this session (index-based analysis only). Conceptually: call the wallet RPC endpoint that forwards into `NFTWallet.royalty_calculation` with a `royalty_assets_dict` that evaluates to zero entries alongside a non-empty `fungible_asset_dict`, and observe the endpoint fail with `ZeroDivisionError` instead of a handled error response.

**Note on confidence**: Due to index size limits, I could not fully inspect the complete body of `chia/wallet/wallet_rpc_api.py` around the `royalty_calculation` call site or the exact RPC parameter validation performed before this call. A Devin session with full repository access would be needed to confirm the exact reachability path and any pre-existing validation that might already prevent the zero-length case.
