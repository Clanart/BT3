### Title
Division by zero in `consolidatedNode.Split` when proposer's CN staking amount and consensus-liquidity staking amount are both zero - ([File: kaiax/staking/staking_info.go])

### Summary
`consolidatedNode.Split()` divides a reward amount by `totalAmount = StakingAmount + CLStakingAmount` without checking that this sum is nonzero. This function is invoked for the block proposer inside the reward-distribution finalization path (`specWithProposerAndFunds`/`specWithProposerAndFundsFlex`) whenever the proposer has a registered `CLStakingInfo`, regardless of whether either staking amount is actually nonzero. If a proposer's CN staking-contract balance and its consensus-liquidity (CL) pool balance are both reported as zero at the same time, this causes a runtime division-by-zero panic during deterministic block finalization (`FinalizeState`), which every honest node executes identically for that block.

### Finding Description
`Split` computes:
```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)
	...
}
``` [1](#0-0) 

`totalAmount` is only guaranteed non-zero when the caller has already filtered by `StakingAmount >= minStake` (as done in `assignStakingRewards`/`assignStakingRewardsFlex`). However, the proposer-specific paths call `Split` unconditionally, gated only on `cn.CLStakingInfo != nil`, with no minimum-stake or non-zero check:
```go
newSpec.Proposer = proposer
if !config.Rules.IsPrague || si.CLStakingInfos == nil {
    newSpec.IncRecipient(config.Rewardbase, proposer)
    return newSpec
}
cns := si.ConsolidatedNodes()
for _, cn := range cns {
    if cn.RewardAddr != config.Rewardbase {
        continue
    }
    if cn.CLStakingInfo == nil {
        break
    }
    cnAmount, clAmount := cn.Split(proposer)
    ...
}
``` [2](#0-1) 
The same unguarded pattern exists in `specWithProposerAndFundsFlex`. [3](#0-2) 

`StakingInfo` is built from the live AddressBook/CLRegistry state without filtering out zero-balance entries: any registered CN node ID is kept in `NodeIds`/`StakingAmounts` regardless of its current staking-contract balance, and CL entries are similarly derived from live pool balances rounded to whole KAIA. [4](#0-3) [5](#0-4) 

Under `RoundRobin`/`Sticky` proposer policies (or any scenario where stake is not required for council membership/proposer eligibility), a council member can be selected as proposer even with zero CN staking balance. If that same validator has a registered but fully-withdrawn CL pool (`CLStakingAmount == 0`), then for that proposer `StakingAmount == 0` and `CLStakingInfo.CLStakingAmount == 0`, so `totalAmount == 0`, and `clAmount.Div(clAmount, totalAmount)` panics.

This mirrors the reported bug class: a value that is assumed to always be nonzero (an admin/state-mutable divisor) becomes zero because the code path that produced the guarantee (minimum-stake filtering) is bypassed by another code path (unconditional proposer handling), leading to division by zero.

### Impact Explanation
Because `FinalizeState` is executed deterministically by every node processing the block (both `TransitionDb`/`FinalizeState` reward crediting path is part of core consensus state transition), a panic here would crash block processing across all honest nodes at the same block height, halting the chain (denial of service on the core state-transition/reward-distribution logic, not a network-layer DoS). This falls squarely within the in-scope "state transition and gas/burn accounting" and "reward redirection" categories, since it directly breaks the reward distribution guarantee described in the reward module's own design (Kore/Prague/Flex rules assume `totalAmount > 0` whenever `CLStakingInfo` is present).

### Likelihood Explanation
Triggering requires: (1) `istanbul.policy` not requiring stake for proposer eligibility (RoundRobin/Sticky), or a WeightedRandom validator whose CNStaking balance later drops to zero while remaining a qualified validator through other means; (2) the same validator having a CL registration with a balance that later reaches zero (a legitimate operation — withdrawing consensus-liquidity stake); and (3) that validator being selected/allowed to propose a block. Registering and withdrawing CL stake is a normal user-facing (staker) operation, and node de-staking while remaining briefly in the council is plausible during churn. This makes the precondition reachable through ordinary reachable actions (staking/unstaking transactions) without requiring any privileged or malicious-node behavior.

### Recommendation
In `consolidatedNode.Split`, guard against `totalAmount.Sign() == 0` (return the full `amount` to the CN side, matching the "no CL" fallback), mirroring the existing safety checks already applied in `assignStakingRewards`/`assignStakingRewardsFlex`. Additionally, `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` should apply the same eligibility/minimum-stake and nonzero-total checks before calling `Split` for the proposer, rather than relying solely on `cn.CLStakingInfo != nil`.

### Proof of Concept
1. Configure `istanbul.policy = RoundRobin` (or otherwise arrange for a council member to be proposer without meeting `minimumstake`).
2. Register the validator's CL pool via CLRegistry, then fully withdraw the CL stake so `CLStakingAmount` reads as 0 while the CL registration entry persists.
3. Ensure the validator's CNStaking contract balance is also 0 (e.g., withdrawn) while it remains in the council.
4. Let this validator be selected as the block proposer under Prague rules with `reward.deferredtxfee = true`.
5. During `FinalizeState`, `getDeferredRewardFullKore`/`Flex` → `specWithProposerAndFunds(Flex)` finds this proposer's `consolidatedNode` with `CLStakingInfo != nil`, calls `cn.Split(proposer)`, and `totalAmount = 0 + 0 = 0` triggers a `big.Int` division-by-zero panic, crashing block finalization for every node processing this block.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

func specWithProposerAndFundsFlex(spec *reward.RewardSpec, config *reward.RewardConfig, proposer, kif, kef, kpf *big.Int, si *staking.StakingInfo) *reward.RewardSpec {
	newSpec := spec.Copy()

	// If KIF, KEF, or KPF address is not set, proposer takes it.
	if common.EmptyAddress(si.KIFAddr) {
		newSpec.KIF = common.Big0
		proposer.Add(proposer, kif)
	} else {
		newSpec.KIF = kif
		newSpec.IncRecipient(si.KIFAddr, kif)
	}

	if common.EmptyAddress(si.KEFAddr) {
		newSpec.KEF = common.Big0
		proposer.Add(proposer, kef)
	} else {
		newSpec.KEF = kef
		newSpec.IncRecipient(si.KEFAddr, kef)
	}

	if common.EmptyAddress(si.KPFAddr) {
		newSpec.KPF = common.Big0
		proposer.Add(proposer, kpf)
	} else {
		newSpec.KPF = kpf
		newSpec.IncRecipient(si.KPFAddr, kpf)
	}

	newSpec.Proposer = proposer
	if !config.Rules.IsPrague || si.CLStakingInfos == nil {
		newSpec.IncRecipient(config.Rewardbase, proposer)
		return newSpec
	}

	// Handle CLStakingInfo for proposer after Prague
	cns := si.ConsolidatedNodes()
	for _, cn := range cns {
		if cn.RewardAddr != config.Rewardbase {
			continue

			// Early exit if there's no CL for proposer
			break
		}

		newSpec.IncRecipient(cn.RewardAddr, cnAmount)
		newSpec.IncRecipient(cn.CLStakingInfo.CLPoolAddr, clAmount)
		return newSpec
	}

	newSpec.IncRecipient(config.Rewardbase, proposer)
	return newSpec
