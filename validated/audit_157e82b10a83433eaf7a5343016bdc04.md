Based on the code I reviewed, there is a solid Desktop analog: the trampoline credential-helper trusts *any* request made under a single valid `DESKTOP_TRAMPOLINE_TOKEN` for the whole duration of one Git operation, without binding that token to the specific host/endpoint the user actually intended to talk to — analogous to HealthRegion allowing multiple unrelated instructions once "unlocked" until a final check.

### Title
Credential helper trampoline grants stored/host credentials to any endpoint requested during a single Git operation, enabling cross-host credential leakage via attacker-controlled submodules/LFS - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
`withTrampolineEnv` issues one `DESKTOP_TRAMPOLINE_TOKEN` that stays valid for the entire duration of a single Git invocation (e.g. `git clone --recursive`), and configures `credential.helper=desktop` globally via `GIT_CONFIG_PARAMETERS` so that it propagates to child processes such as submodule fetches and Git LFS filters [1](#0-0) . The trampoline server only validates that the token is *currently active* — `isValidTrampolineToken` — it does not validate that the credential request's host matches the original remote URL that the operation was started for [2](#0-1) . This mirrors the HealthRegion flaw: a single "begin/end" trust window in which multiple, unrelated sub-operations are allowed to execute without re-validating against the original intent.

### Finding Description
When Desktop clones or fetches a repository, `envForRemoteOperation`/`withTrampolineEnv` sets up credential handling scoped only to a `token`, not to the target remote URL [3](#0-2) . The comment in `withTrampolineEnv` explicitly acknowledges that `GIT_CONFIG_PARAMETERS` is used (instead of `-c` args) specifically so that "commands invoked by filters (i.e. Git LFS)" also pick up the `credential.helper=desktop` configuration [4](#0-3) . Because `git clone --recursive` is used [5](#0-4) , an attacker-controlled repository can define a `.gitmodules` entry (or an LFS `.gitattributes` filter) pointing to a *different* host than the one the user is cloning.

During that single "clone" trust window (one token, one `credential.helper=desktop` for the whole process tree), Git will invoke the credential helper for the submodule's/LFS's host. `getCredential` in `trampoline-credential-helper.ts` resolves the endpoint purely from the credential request's `url`/`host` fields supplied by that sub-invocation, with no comparison to the original clone/fetch URL [6](#0-5) . If that host matches a GitHub endpoint the user is already signed into, `getGitHubCredential`/`findGitHubTrampolineAccount` will hand back that stored account's token to the credential helper (i.e. to the attacker-controlled subprocess) without any prompt, since an account for that endpoint exists [7](#0-6) . If it's a generic host, `getGenericCredential`/`findGenericTrampolineAccount` similarly returns stored credentials scoped only by the trampoline `token`+endpoint, again with no origin/url binding to the clone target [8](#0-7) .

The existing guard, `isValidTrampolineToken`, only checks that the token hasn't been revoked yet — it is exactly the kind of "still inside the health region" check that the Mango bug shows is insufficient: it authorizes *any* instruction (credential request) issued while the region is open, regardless of whether that instruction matches the operation the region was opened for [2](#0-1) .

### Impact Explanation
If exploitable, a malicious repository (cloned or fetched by an unsuspecting user) could use a submodule URL or LFS smudge/clean filter to trigger the trampoline credential helper for an arbitrary host (e.g. `github.com`, or a corporate GHE instance the victim is signed into) while riding on the trust window opened for cloning the "top-level" repo. This would exfiltrate the user's stored OAuth token/credentials to the attacker's server for that host — a credential exfiltration issue matching the "unprivileged … attacker controls a cloned/fetched repository … credential/token exfiltration" impact category in scope.

### Likelihood Explanation
This requires no local access or existing malware — only that the victim clones/fetches an attacker-supplied repository containing a submodule or LFS configuration pointing to a host for which the victim already has stored credentials in Desktop. The comment in the code explicitly documents that filters/submodules are intentionally allowed to reuse the trampoline's credential helper configuration, which is the exact condition needed. I was not able to fully verify at what points `isBackgroundTaskEnvironment`/prompt suppression apply for submodule-triggered requests versus top-level requests, nor whether Git itself restricts which credential fields (`host`/`url`) a submodule fetch can present to the helper — this would need to be confirmed by tracing dugite/Git's actual submodule-fetch credential-helper invocation behavior, which the indexed code does not fully show.

### Recommendation
Bind the trampoline's credential lookup (and the askpass handler) to the specific remote URL(s) legitimately associated with the top-level operation (the primary clone/fetch/push URL and any URLs explicitly declared as trusted submodule/LFS remotes), rather than trusting any request that merely presents a currently-valid token. Concretely: pass the intended remote host(s) into `withTrampolineEnv`/`trampolineEnvironmentPath`, and have `getCredential`/`getGenericCredential`/`getGitHubCredential` reject (or explicitly re-prompt for) credential requests whose endpoint doesn't match one of the expected hosts for that operation, similar to how the Mango patch now explicitly allowlists only the instructions that legitimately belong inside the HealthRegion.

### Proof of Concept
Conceptual PoC (not executed against a live Desktop build):
1. Attacker publishes a public repository `evil/repo` containing a `.gitmodules` file with a submodule URL of `https://github.com/<victim-relevant-path>` or configures `.gitattributes`/LFS filters that shell out and invoke `git credential fill` for `host=github.com`.
2. Victim, already signed into `github.com` in Desktop, clones `evil/repo` via Desktop's UI, which runs `git clone --recursive` under a single `DESKTOP_TRAMPOLINE_TOKEN` with `credential.helper=desktop` set globally via `GIT_CONFIG_PARAMETERS`.
3. During the recursive submodule fetch (still inside the same trust window/token), Git invokes the credential helper for the submodule's/LFS's `github.com` endpoint.
4. `trampoline-credential-helper.ts`'s `getGitHubCredential` finds the victim's existing stored account for `github.com` and returns the token to the credential helper — silently, with no prompt — because the endpoint check only compares against stored accounts, not against the URL the user actually intended to clone.
5. The attacker's submodule/hook/filter process, receiving these credentials via its own credential-helper flow, exfiltrates them.

```typescript
export async function withTrampolineEnv<T>(
  fn: (env: object) => Promise<T>,
  path: string,
  isBackgroundTask = false,
  customEnv?: Record<string, string | undefined>
): Promise<T> {
  const sshEnv = await getSSHEnvironment()

  return withTrampolineToken(async token => {
    isBackgroundTaskEnvironment.set(token, isBackgroundTask)
    trampolineEnvironmentPath.set(token, path)

    const existingGitEnvConfig =
      customEnv?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    // The code below assumes a few things in order to manage SSH key passphrases
    // correctly:
    // 1. `withTrampolineEnv` is only used in the functions `git` (core.ts)
    // 2. Those two functions always thrown an error when something went wrong,
    //    and just return a result when everything went fine.
    //
    // With those two premises in mind, we can safely assume that right after
    // `fn` has been invoked, we can store the SSH key passphrase for this git
    // operation if there was one pending to be stored.
    try {
      return await fn({
        DESKTOP_PORT: await trampolineServer.getPort(),
        DESKTOP_TRAMPOLINE_TOKEN: token,
        GIT_ASKPASS: '',
        // This warrants some explanation. We're configuring the
        // credential helper using environment variables rather than
        // arguments (i.e. -c credential.helper=) because we want commands
        // invoked by filters (i.e. Git LFS) to be able to pick up our
        // configuration. Arguments passed to git commands are not passed
        // down to filters.
        //
        // We're using the undocumented GIT_CONFIG_PARAMETERS environment
        // variable over the documented GIT_CONFIG_{COUNT,KEY,VALUE} due
        // to an apparent bug either in a Windows Python runtime
        // dependency or in a Python project commonly used to manage hooks
        // which isn't able to handle the blank environment variables we
        // need when using GIT_CONFIG_*.
        //
        // See https://github.com/desktop/desktop/issues/18945
        // See https://github.com/git/git/blob/ed155187b429a/config.c#L664
        GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'credential.helper=' 'credential.helper=desktop'`,

        GIT_USER_AGENT: await GitUserAgent(),
        ...sshEnv,
      })
```

```typescript
    ...envForAuthentication(),
```

```typescript
/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}
```
