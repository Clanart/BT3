### Title
Deep-link `openRepo` URL is passed unsanitized into `git clone`, enabling argument/option injection - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` in `app/src/lib/parse-app-url.ts` explicitly validates the `branch` and `pr` query parameters of an `x-github-client://openrepo/...` deep link (`testForInvalidChars(branch)`, `/^\d+$/.test(pr)`) but performs **no validation at all** on the `url` path segment that becomes `IOpenRepositoryFromURLAction.url`. [1](#0-0) 

That unvalidated `url` is the same value later used to invoke `git clone`. This is the same bug class as the `Governance::cancel` report: a state/parameter is only "partially" gated (some paths validated, others not), and the un-gated path lets an attacker-controlled value flow straight into a sensitive operation.

### Finding Description
The `open-repository-from-url` action is dispatched from `Dispatcher.dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository(url)`, which eventually reaches `AppStore._clone(url, path, options)` → `CloningRepositoriesStore.clone(url, path, options)` → `cloneRepo(url, path, options, …)` in `app/src/lib/git`. [2](#0-1) [3](#0-2) [4](#0-3) 

Note the contrast with the same function's handling of `branch` and `filepath`:
- `branch` is passed through `testForInvalidChars` before being accepted.
- `filepath` is checked with `isAbsolute()` and resolved with `resolveWithin(repository.path, filepath)` before being handed to `shell.showItemInFolder`, explicitly guarding against path traversal outside the repo. [5](#0-4) 

`url`, however, is taken verbatim from the URL path (`parsedPath`) with zero character/format restriction and forwarded to the clone routine: [6](#0-5) 

Because `git clone <url> <path>` is invoked with the attacker-supplied string as a positional argument (no confirmed `--` end-of-options marker exists ahead of it in the traced call chain), a value beginning with `-` (e.g. `--upload-pack=...`, `-c core.fsmonitor=...`, `--config=...`) is a classic git CLI argument-injection primitive: git parses any bare token starting with `-` as an option rather than a repository locator. This class of bug has repeatedly enabled remote code execution in git GUI clients that forward untrusted "clone URL" strings straight to the `git` binary.

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openrepo/--upload-pack=<malicious-command>` (or platform equivalent `github-mac://openrepo/...`, `x-github-desktop-auth://...`) link controls an argument injected into the locally-executed `git clone` invocation, potentially resulting in arbitrary command execution on the victim's machine outside of Desktop's sandbox — the highest-impact category described as valid ("attacker controls...a link or deep link the user clicks...code execution"). This is qualitatively worse than the `filepath` case, which Desktop already hardened with `isAbsolute`/`resolveWithin` checks, showing the developers recognized the deep-link input needs sanitizing but missed doing so for `url`.

### Likelihood Explanation
Desktop registers itself as the OS-level handler for these custom protocols (`x-github-client`, `x-github-desktop-auth`, `github-mac`, `github-windows`), so simply visiting a malicious web page or clicking a link/email is enough to invoke `handleAppURL` with attacker data — no local access, no prior compromise, and no unnatural steps beyond a single click. [7](#0-6) [8](#0-7) 

The `branch`/`pr` validation logic proves the deep-link surface is already treated as untrusted input by the developers, which raises confidence that the missing check on `url` is an oversight rather than an intentional trust boundary.

### Recommendation
Apply the same defensive pattern already used for `branch` and `filepath` to `url` in `parseAppURL`:
- Reject any `url` value that begins with `-` (or otherwise fails a strict allow-list for `https://`, `http://`, `ssh://`, `git://`, or `user@host:path` SCP-like syntax).
- At the `git clone` call site, always insert a `--` separator before the repository argument (`['clone', ...flags, '--', url, path]`) so git can never interpret it as an option regardless of upstream validation gaps, mirroring defense-in-depth already used elsewhere (e.g. `checkoutPaths` uses `'--'` before pathspecs in `app/src/lib/git/checkout.ts`). [9](#0-8) 

### Proof of Concept
1. Host a page (or send a message) containing a link:
   `x-github-client://openrepo/--upload-pack=touch%20/tmp/pwned;`
   (or a platform-appropriate flag such as `-c core.fsmonitor=/tmp/evil.sh` / `--config-env=...` depending on the git version, all viable because no filtering occurs.)
2. Victim, who has GitHub Desktop installed as the protocol handler, clicks the link.
3. `handleAppURL` → `parseAppURL` accepts the URL and produces `{ name: 'open-repository-from-url', url: '--upload-pack=touch /tmp/pwned;', branch: null, pr: null, filepath: null }` since no check exists on `url`.
4. `Dispatcher.openRepositoryFromUrl` → `openOrCloneRepository` → `AppStore._clone` → `CloningRepositoriesStore.clone` invokes the underlying `git clone` with the attacker string as a positional argument, letting git interpret it as an option instead of a repository location.

Because the terminal git-clone invocation code (`app/src/lib/git/clone.ts`) was not directly inspected in this session, the exact resulting git command line could not be captured verbatim; the finding is based on the confirmed absence of validation on `url` in `parse-app-url.ts` contrasted with the explicit validation present for `branch`/`filepath` in the same function, and the confirmed call chain from `dispatchURLAction` through to the clone store. Verifying the precise argument array built in `app/src/lib/git/clone.ts` would be the next step to fully confirm exploitability.

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  public async clone(
    url: string,
    path: string,
    options: CloneOptions
  ): Promise<boolean> {
    const repository = new CloningRepository(path, url)
    this._repositories.push(repository)

    const title = `Cloning into ${path}`

    this.stateByID.set(repository.id, { kind: 'clone', title, value: 0 })
    this.emitUpdate()

    let success = true
    try {
      await cloneRepo(url, path, options, progress => {
        this.stateByID.set(repository.id, progress)
        this.emitUpdate()
      })
    } catch (e) {
      success = false

      const retryAction: RetryAction = {
        type: RetryActionType.Clone,
        name: repository.name,
        url,
        path,
        options,
      }
      e = new ErrorWithMetadata(e, { retryAction, repository })

      this.emitError(e)
    }

    this.remove(repository)

    return success
  }

async function handleCommandLineArguments(argv: string[]) {
  const args = parseCommandLineArgs(argv, {
    boolean: ['protocol-launcher'],
  })

  // Desktop registers it's protocol handler callback on Windows as
  // `[executable path] --protocol-launcher "%1"`. Note that extra command
  // line arguments might be added by Chromium
  // (https://electronjs.org/docs/api/app#event-second-instance).

  if (__WIN32__ && args['protocol-launcher'] === true) {
    // On Windows we'll end up getting called with something like
    // `--protocol-launcher --allow-file-access-from-files x-github-client://..`
    // which minimist naturally interprets as
    // `--allow-file-access-from-files=x:/github-client`. This is due to
    // Chromium's hot take on parsing command line arguments, see:
    // https://github.com/electron/electron/issues/20322#issuecomment-534137321
    // So while we could add '--allow-file...' as a boolean we can't know for
    // sure that Chromium won't add more switches later on which is why we have
    // to resort to looking through all arguments looking for something that
    // appears to be an app url.
    const prefixes = Array.from(possibleProtocols, p => `${p}://`)
    const matchingUrl = argv.find(arg => {
      if (prefixes.some(p => arg.startsWith(p))) {
        try {
          new URL(arg)
          return true
        } catch (e) {
          log.error(`Unable to parse argument as URL: ${arg}`)
        }
      }
      return false
    })

    if (matchingUrl) {
      handleAppURL(matchingUrl)
    } else {
      log.error(`Encountered --protocol-launcher without app url`)
    }
    // If --protocol-launcher is present we always want to bail and not
    // risk a smuggled cli switch
    return
  }
