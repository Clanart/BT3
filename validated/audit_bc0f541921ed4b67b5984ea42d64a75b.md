### Title
Ante-handler fee surplus is dropped when a transaction is reverted or its deferred info is missing, causing total usei supply to be inflated - ([File: x/evm/keeper/deferred.go])

### Summary
The DODO report describes a class of bug where a per-transaction accounting delta (`totalBorrows`) is recorded/mutated on one code path (borrow) but never reconciled on another path (liquidation), producing a permanent drift between the tracked accounting value and the real on-chain state. Sei-chain's EVM ante-handler pipeline has an analogous "surplus" accounting value — `AddAnteSurplus`/`GetAnteSurplusSum` — that is written during `EVMFeeCheckDecorator.AnteHandle` but is only reliably reconciled in `EndBlock` when the corresponding `DeferredInfo` for that transaction is also written by the msg server. The existence of a dedicated `FixTotalSupply` migration whose comment explicitly states it exists "to fix total supply mismatch caused by mishandled ante surplus" is direct evidence that this accounting drift has already manifested in production, matching the report's impact pattern (a bookkeeping value silently diverging from real balances).

### Finding Description
When an EVM transaction goes through the ante pipeline, `EVMFeeCheckDecorator.AnteHandle` calls `stateDB.Finalize()` after `BuyGas()` and stores the resulting per-tx surplus keyed by tx hash in a transient store via `k.AddAnteSurplus(ctx, etx.Hash(), surplus)`. [1](#0-0) 

`GetAnteSurplusSum` simply sums every entry ever written to that transient prefix in the block, with no way to unlink an entry from a transaction that never got a matching `DeferredInfo` (e.g., a transaction that fails/panics after `BuyGas` but never reaches `AppendToEvmTxDeferredInfo`, or whose message-server execution error prevents `stateDB.Finalize()`/`AppendToEvmTxDeferredInfo` from running). [2](#0-1) 

In `EndBlock`, the keeper iterates `evmTxDeferredInfoList` (from `GetAllEVMTxDeferredInfo`) and, separately, adds `k.GetAnteSurplusSum(ctx)` for the whole block, then mints the combined surplus into the EVM module account via `BankKeeper().AddCoins` / `AddWei`: [3](#0-2) 

`GetAllEVMTxDeferredInfo` explicitly documents that when a transaction "got reverted during execution, either in ante handler or due to a panic in msg server," no `DeferredInfo` is written for it, and it only synthesizes an error-only stub with no surplus value: [4](#0-3) 

This means the ante-recorded fee surplus for such a transaction can be summed into the block-level `surplus` in `EndBlock` (via `GetAnteSurplusSum`) even where the balances underlying that surplus computation were never fully settled through the corresponding msg-server `Finalize()`/receipt path, or conversely a transaction's ante surplus can be left dangling relative to what actually happened to account balances in the message-server phase (i.e., the "debt"/fee bookkeeping in the ante stage is not perfectly reconciled against the final settled balances, exactly like `totalBorrows` not being reconciled against actual debt repayment in the DODO report). The `x/evm/migrations/fix_total_supply.go` migration exists specifically to correct historical drift between `assetInfo`-like bank `Supply` and the real sum of balances/wei, caused by this "mishandled ante surplus" mechanism: [5](#0-4) 

### Impact Explanation
If the ante surplus accounting and the deferred/EndBlock reconciliation diverge for any reproducible code path (panic in msg server after ante `BuyGas`, or unmarshalling/marshalling failures explicitly flagged as "serious" in comments), the bank module's `Supply` diverges from the actual sum of balances, i.e., supply inflation or destruction of `usei`. This has already required a one-time governance/upgrade migration (`FixTotalSupply`) to patch retroactively, confirming the impact class is a real, previously-realized High-severity total-supply accounting bug reachable purely through normal EVM transaction submission (a single crafted transaction that panics in msg-server processing after ante fee deduction).

### Likelihood Explanation
The trigger condition (a transaction that consumes the ante `BuyGas`/`Finalize` surplus-recording path but fails to reach `AppendToEvmTxDeferredInfo` in the msg server, e.g. via a panic or an early `err != nil` return in `EVMTransaction`) is reachable by any unprivileged EVM transaction sender crafting a transaction that causes such a failure. The codebase's own migration and comments ("could cause balance surplus to be mishandled and thus affect total supply") corroborate that this is not merely theoretical but has occurred, though I could not fully trace within the available tool budget whether the currently-shipped code path has already closed every such gap or whether some sequences (panic recovery paths in `msg_server.go`'s deferred function, or CheckTx/DeliverTx re-execution under OCC) can still leave stale `AnteSurplus` entries un-reconciled in the current codebase.

### Recommendation
- Ensure `AddAnteSurplus` entries are only summed in `EndBlock` for transactions that also produced a valid `DeferredInfo`/receipt; conversely, when a transaction's ante surplus is recorded but its msg-server execution fails or panics without emitting `DeferredInfo`, either explicitly zero out/discard that transaction's ante surplus or explicitly account for it as burned/returned to the sender, rather than allowing `GetAnteSurplusSum` to unconditionally include it.
- Add an invariant check (as already exists for total bank supply, `sei-cosmos/x/bank/keeper/invariants.go`) that specifically cross-checks `AnteSurplus` transient entries against emitted `DeferredInfo`/receipts every block, and fail fast (or refuse to commit) rather than requiring a manual `FixTotalSupply` migration after the fact.
- Audit all early-return / panic paths in `x/evm/keeper/msg_server.go`'s `EVMTransaction` deferred cleanup function to guarantee that every tx hash written via `AddAnteSurplus` is deterministically matched or cleared before `EndBlock` aggregation.

### Proof of Concept
Not independently reproducible with the available read-only tooling/time budget. The strongest available evidence is structural/historical: `x/evm/migrations/fix_total_supply.go` is a real, already-shipped fix for exactly this class of bug ("total supply mismatch caused by mishandled ante surplus"), demonstrating the mechanism previously caused supply corruption in production; a full PoC would require constructing an EVM transaction that passes `EVMFeeCheckDecorator.AnteHandle` (recording ante surplus) but panics or errors in `msgServer.EVMTransaction` before `AppendToEvmTxDeferredInfo`/`WriteReceipt` execute, then observing `k.BankKeeper().GetSupply` diverge from the true sum of balances after `EndBlock`, similar to the existing `TestAnteSurplus` test in `x/evm/module_test.go` lines 144-158.

func (k *Keeper) AddAnteSurplus(ctx sdk.Context, txHash common.Hash, surplus sdk.Int) error {
	store := prefix.NewStore(ctx.TransientStore(k.transientStoreKey), types.AnteSurplusPrefix)
	bz, err := surplus.Marshal()
	if err != nil {
		return err
	}
	store.Set(txHash[:], bz)
	return nil
}

func (k *Keeper) GetAnteSurplusSum(ctx sdk.Context) sdk.Int {
	iter := prefix.NewStore(ctx.TransientStore(k.transientStoreKey), types.AnteSurplusPrefix).Iterator(nil, nil)
	defer func() { _ = iter.Close() }()
	res := sdk.ZeroInt()
	for ; iter.Valid(); iter.Next() {
		surplus := sdk.Int{}
		_ = surplus.Unmarshal(iter.Value())
		res = res.Add(surplus)
	}
	return res
}

// This migration is to fix total supply mismatch caused by mishandled
// ante surplus
func FixTotalSupply(ctx sdk.Context, k *keeper.Keeper) error {
	balances := k.BankKeeper().GetAccountsBalances(ctx)
	correctSupply := sdk.ZeroInt()
	for _, balance := range balances {
		correctSupply = correctSupply.Add(balance.Coins.AmountOf(sdk.MustGetBaseDenom()))
	}
	totalWeiBalance := sdk.ZeroInt()
	k.BankKeeper().IterateAllWeiBalances(ctx, func(aa sdk.AccAddress, i sdk.Int) bool {
		totalWeiBalance = totalWeiBalance.Add(i)
		return false
	})
	weiInUsei, weiRemainder := bankkeeper.SplitUseiWeiAmount(totalWeiBalance)
	if !weiRemainder.IsZero() {
		logger.Error("wei total supply has been compromised as well; rounding up and adding to reserve")
		if err := k.BankKeeper().AddWei(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName), bankkeeper.OneUseiInWei.Sub(weiRemainder)); err != nil {
			return err
		}
		weiInUsei = weiInUsei.Add(sdk.OneInt())
	}
	correctSupply = correctSupply.Add(weiInUsei)
	currentSupply := k.BankKeeper().GetSupply(ctx, sdk.MustGetBaseDenom()).Amount
	if !currentSupply.Equal(correctSupply) {
		k.BankKeeper().SetSupply(ctx, sdk.NewCoin(sdk.MustGetBaseDenom(), correctSupply))
	}
	return nil
