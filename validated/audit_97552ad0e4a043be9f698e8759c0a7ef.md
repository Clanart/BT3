### Title
Silent hijack of a repository's git remote URL from an unauthenticated GitHub API field - ([File: app/src/lib/stores/updates/update-remote-url.ts](app/src/lib/stores/updates/update-remote-url.ts))

### Summary
`updateRemoteUrl` automatically rewrites a user's local git remote (`git remote set-url`) to whatever `clone_url` the GitHub/GHES API returns for the linked repository, gating the change only on protocol equality and "did the remote match the *previous* API url", but never validating that the new URL still points at the same hostname/host trust boundary as before. [1](#0-0) 

### Finding Description
`updateRemoteUrl` is the mechanism used to keep the local `origin` remote in sync when a repository is renamed on GitHub (or GHES). It:
1. Compares the current remote URL against the incoming `apiRepo.clone_url` (`urlsMatch`).
2. Compares the current remote URL against the previously known `gitHubRepository.cloneURL` (`remoteUrlUnchanged`) — i.e. verifies the user hasn't manually customized the remote.
3. Checks that the URL *protocol* (`https:`/`ssh:`) hasn't changed.
4. If unchanged-protocol and the remote still matches the old API-known URL, it calls `gitStore.setRemoteURL(...)` with the **new** `apiRepo.clone_url` verbatim — with no check that the hostname of the new URL is the same as the hostname of the old one. [2](#0-1) 

`setRemoteURL` then invokes `git remote set-url <name> <url>` unconditionally, accepting any string as long as it's syntactically a URL. [3](#0-2) 

`clone_url` is an attacker-influenceable field: it originates from the API response for the GitHub repository object (`IAPIRepository`/`IAPIFullRepository`), which is fetched from whatever endpoint the repository is bound to (dotcom or a GitHub Enterprise Server instance the user has added). A malicious/compromised GHES instance, or an on-path party abusing Desktop's "Untrusted Server" continue-anyway certificate flow, can serve an API response whose `clone_url` points at a completely different host while keeping the same protocol scheme, e.g. changing `https://github.example.com/org/repo.git` to `https://git-mirror.attacker.tld/org/repo.git`. `urlMatchesRemote`, which is used only to detect "did anything change", explicitly returns `false` for differing hostnames — but the code path that fires when hostnames differ is exactly the one that performs the update, not one that blocks it. [4](#0-3) 

The existing unit tests confirm the update happens purely based on URL string comparison and protocol matching, with no host allow-listing: [5](#0-4) 

Note that the test at line 96-112 shows a protocol mismatch is blocked, but there is no equivalent test or code path blocking a same-protocol/different-host swap — the invariant "the remote must keep pointing at the same host" is never enforced. [6](#0-5) 

This differs from the clone-time protections that exist elsewhere in the codebase (`isClonePathSensitive`, `sanitizeCloneName` in `app/src/lib/remote-parsing.ts` and `app/src/lib/git/clone.ts`), which defend against path traversal from attacker-controlled URLs but do nothing for remote-URL rewriting after the repository is already on disk. [7](#0-6) 

### Impact Explanation
Once the local `origin` remote silently points at an attacker-controlled host, every subsequent `git push`/`git fetch` triggered by Desktop (and by the user's own git CLI usage of that remote) is redirected there:
- Push operations transmit the user's code (and, depending on credential helper configuration, may trigger credential-helper HTTP Basic prompts/POSTs to the new host) to an attacker-controlled endpoint.
- Fetch/pull will pull attacker-supplied history into the "same" repository, silently corrupting what the user believes is their upstream state.
- This matches the requested impact class "credential/token exfiltration" and "silent corruption of what the user commits or pushes" without requiring local access, admin rights, or leaked credentials — only a compromised/malicious API response for a repository the user already has added (GHES admin compromise, DNS hijack + accepted "Untrusted Server" dialog, or a malicious enterprise proxy).

### Likelihood Explanation
Requires the attacker to control the API response for a repository already tracked by Desktop (e.g., a compromised or malicious GitHub Enterprise Server the user is signed into, or a MITM position combined with the user accepting the "Untrusted Server" dialog shown in `app/src/ui/untrusted-certificate/untrusted-certificate.tsx`). This is a plausible, low-interaction path for GHES users and does not require prior host compromise, admin rights, or leaked secrets, making it a realistic Medium-likelihood analog of the original "compromised admin can rug funds via unrestrained privileged action" pattern — here the "privileged action" is an unrestrained remote-URL rewrite driven by an unauthenticated data field.

### Recommendation
In `updateRemoteUrl`, before calling `gitStore.setRemoteURL`, additionally require that the hostname of `apiRepo.clone_url` matches the hostname of the existing remote (or the repository's known API endpoint host). Reject/log-and-skip the update if the hostname changes, and only allow such cross-host moves via an explicit, user-confirmed prompt.

### Proof of Concept
1. User adds a GitHub Enterprise Server account in Desktop and clones `org/repo` from `https://ghes.company.com/org/repo.git`; `origin` is set to that URL and `gitHubRepository.cloneURL` is cached as the same.
2. The GHES instance (or an on-path attacker who gets the user to accept the untrusted-certificate dialog) is compromised and starts returning, for the same repository ID, `clone_url: "https://ghes.attacker-controlled.tld/org/repo.git"` (same `https` scheme).
3. On the next repository refresh, `updateRemoteUrl` computes `urlsMatch = false`, `remoteUrlUnchanged = true` (previous cached URL still matches origin), `protocolsMatch = true`, and calls `gitStore.setRemoteURL('origin', 'https://ghes.attacker-controlled.tld/org/repo.git')`.
4. `origin` now silently points at the attacker's host; the next push in Desktop sends the user's commits (and potentially credential-helper Basic-auth attempts) to `ghes.attacker-controlled.tld` with no warning shown to the user, as demonstrated by the passing test at [5](#0-4)  which shows exactly this class of unrestricted URL swap succeeding when only the hostname differs.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```

```typescript
export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```

```typescript
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
```
