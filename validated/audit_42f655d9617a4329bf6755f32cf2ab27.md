### Title
Automatic remote-URL rewrite from unverified GitHub API `clone_url` silently repoints `origin` to an attacker-controlled repository - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Solidity report's broken invariant is: a piece of authoritative state (`primeRate`) is overwritten directly from external input (`newPrimeRate`) and immediately trusted to recompute dependent accounting, without first validating/settling the effects the *old* state should have had — so stale/incorrect state silently propagates forward. The closest Desktop analog is `updateRemoteUrl()`, which takes a `clone_url` value returned by the GitHub API (an "attacker-controlled GitHub API object" per the allowed impact list) and, if a handful of loose heuristics pass, directly overwrites the local Git `origin` remote URL with no user confirmation — silently changing where the user's next `push`/`fetch`/`pull` goes.

### Finding Description
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` compares the locally configured remote against `apiRepo.clone_url` (data returned by `api.fetchRepository`) and, if the protocol matches and the existing remote is unchanged from the last known association, calls `gitStore.setRemoteURL(...)` to rewrite `origin` to the new URL: [1](#0-0) [2](#0-1) 

This is invoked from `repositoryWithRefreshedGitHubRepository`, which is part of the routine background repository-refresh flow (triggered by periodic indicator/repository refresh, not an explicit user action such as "change remote"): [3](#0-2) 

The actual mutation happens in `GitStore.setRemoteURL`, which runs `git remote set-url` and emits an update — there is no dialog, confirmation, or diffable notice to the user before the remote changes: [4](#0-3) 

The guard rails that exist (`protocolsMatch`, `remoteUrlUnchanged`, `!urlsMatch`) only protect against the case where the *user* has manually customized the remote away from the last-known GitHub clone URL. They rely on `urlMatchesRemote`, which only compares hostname/owner/name strings, not any cryptographic or ownership-continuity check: [5](#0-4) 

None of these checks verify that the `owner/name` pair returned by the API still corresponds to the same underlying repository the user originally added — they only prevent overriding a *manually* customized remote. If a repository is renamed/transferred/deleted-and-reclaimed on the GitHub side (an "attacker controls a GitHub API object" scenario within the report's allowed threat model — e.g. a malicious actor claiming a vacated `owner/name` slug, or a compromised GHES/API response under MITM), the API's `clone_url` for the association Desktop is tracking becomes attacker-controlled while `protocolsMatch`/`remoteUrlUnchanged` still hold trivially true (since the user never touched their remote). Desktop will then automatically retarget `origin` in the background, with zero prompt, exactly matching the report's "silently commit/push corruption" impact category — the invariant that "origin still points at the repository the user cloned" is broken by an unvalidated external write.

### Impact Explanation
Once `origin` is silently rewritten, every subsequent `git push`/`git fetch`/`git pull` the user performs from Desktop's UI is directed at the attacker-controlled repository without any visual difference in the app (the UI generally reflects `gitHubRepository`/remote state that was itself just updated to match). This can result in:
- The user unknowingly pushing proprietary commits/branches to a repository the attacker controls (data exfiltration of source code).
- The user fetching/pulling attacker-supplied history into their local repo under the belief it's the original project.

This satisfies the report's named "silent corruption of what the user commits or pushes" impact category, driven by an attacker-influenced GitHub API object, without requiring local access, admin rights, or social engineering beyond the pre-existing repository/API-manipulation primitive.

### Likelihood Explanation
This requires a specific precondition to be attacker-reachable: the attacker must be able to get the GitHub API endpoint that Desktop already trusts (based on the account whose host matches the remote) to return a `clone_url` for the tracked repository that points to attacker infrastructure — via repo-slug reclaiming after a rename/deletion, or a compromised/MITM'd GitHub Enterprise API endpoint. This is a narrower likelihood than a pure client-side bug, and I could not verify from the indexed code whether additional out-of-band protections exist elsewhere (e.g. GitHub-side repo ID pinning checks) that might mitigate the reclaimed-slug scenario before `fetchRepository` is even called — this is a genuine gap in my analysis given index limitations.

### Recommendation
Before automatically rewriting `origin`, verify repository identity continuity beyond string matching — e.g., compare a stable repository ID returned by the API (not just `owner/name`/hostname) against a previously stored ID, and/or require explicit user confirmation (similar to the existing `UpstreamAlreadyExists` dialog pattern already used for the `upstream` remote in `app/src/ui/upstream-already-exists/upstream-already-exists.tsx`) before silently changing `origin`'s URL.

### Proof of Concept
Conceptual PoC (not fully verifiable from the index without the API/server-side repo-slug behavior, flagged as uncertain above):
1. Attacker deletes/relinquishes ownership so that a public repository at the same `owner/name` the victim originally cloned becomes claimable, or compromises a GHES API response in transit.
2. Attacker (re)creates a repository at that same `owner/name` slug, controlling `clone_url`.
3. Desktop's periodic background refresh calls `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository(owner, name)`, obtaining the attacker's `clone_url`.
4. `updateRemoteUrl` sees `protocolsMatch = true`, `remoteUrlUnchanged = true` (victim never touched `origin`), `urlsMatch = false` (URL now differs at the git-object level, e.g. different underlying host/IP even though owner/name strings match) and calls `gitStore.setRemoteURL('origin', attackerCloneUrl)` with no prompt, confirmed by the test suite's automatic-update expectation: [6](#0-5) 
5. Victim's next push in Desktop silently goes to the attacker's repository.

    repository: Repository

    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
