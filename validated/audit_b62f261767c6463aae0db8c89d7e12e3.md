## Title
Line-index–based partial commit selection is silently re-applied to a changed diff, allowing on-disk content changes to be committed without user review - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop tracks partial-commit line selections purely by numeric line index (`DiffSelection.divergingLines`), not by line content. When the diff for the currently selected file is refreshed asynchronously (`updateChangesWorkingDirectoryDiff`), the code only prunes indices that are no longer "selectable" (e.g. turned into context/hunk-header lines) — it never verifies that a still-selectable index still refers to the *same content* the user originally selected. This mirrors the FlywheelV2 pattern of a locally cached/derived value (`storedCycle` / here, `divergingLines`) drifting out of sync with the authoritative source of truth (`gaugeCycle` / here, the freshly-fetched diff), with an incomplete guard (`==` check / here, index-existence check) that fails to detect the mismatch, leading to silent, incorrect data being carried forward.

### Finding Description
`DiffSelection` stores which lines are "diverging" from the default selection as raw absolute line indices (`unifiedDiffStart + index`), with no reference to the actual text/hash of the line: [1](#0-0) [2](#0-1) 

When the working-directory diff for the selected file is reloaded (e.g. after a background refresh, hook execution, or any process that changes the file on disk between renders), `updateChangesWorkingDirectoryDiff` re-derives only the *set of selectable line indices* from the new diff and calls `withSelectableLines`, explicitly acknowledging that it does not validate whether previously selected lines still correspond to the same content: [3](#0-2) 

`withSelectableLines` merely intersects the old diverging-line index set with the new selectable-line index set — it keeps an index "selected" as long as that index is still an includeable line in the new diff, regardless of whether the content at that index changed: [4](#0-3) 

Finally, when the user commits, `formatPatch` builds the actual patch strictly from `file.selection.isSelected(absoluteIndex)`, i.e. index membership, with no content cross-check against what was originally selected: [5](#0-4) 

The broken invariant: the UI's `divergingLines` set is supposed to track "the specific lines of content the user decided to include," but it actually only tracks "line indices," which is a different, weaker invariant. Existing guards (`arrayEquals(selectedFileIDs, ...)`, `selectedFileID !== selectedFileIdBeforeLoad`) in `updateChangesWorkingDirectoryDiff` only check that the same *file* is still selected — they do nothing to detect that the *diff content backing those indices* has changed: [6](#0-5) 

### Impact Explanation
If a file's on-disk diff shifts (lines inserted/removed above the previously-selected hunk, or content otherwise mutated) between the time the user makes a partial line selection and the time the commit is created, the same line indices can now correspond to entirely different content. Because selection state survives purely by index, the user can end up silently committing/staging content they never reviewed or explicitly approved (or omitting content they did intend to commit). This is a silent corruption of what the user commits — the app's own comment concedes the validation gap ("the diff might have changed dramatically...we'll settle on just updating the selectable lines"). This satisfies the "silent corruption of what the user commits or pushes" impact category from a value the user did not knowingly review.

### Likelihood Explanation
This requires the working directory file to change underneath an in-progress partial selection while Desktop is still showing/refreshing that diff — plausible via any concurrent write to the file (external editor autosave, a git hook, a background `checkout`/`stash pop` triggered by another Desktop action, or a submodule/LFS smudge filter driven by fetched remote content) landing between `_selectWorkingDirectoryFiles`/diff-refresh cycles. It does not require admin rights or local malware beyond content the user is already interacting with (a repository whose hooks or filters run automatically on checkout/fetch can produce this race without any unnatural user action), but it does depend on timing, so it is a real but not trivially deterministic condition to hit reliably.

### Recommendation
Bind the `divergingLines` selection state to diff content, not just index position — e.g., invalidate (or attempt to remap by content/hash) selections when the underlying hunk lines at those indices have changed text, rather than only checking whether the index remains "selectable." At minimum, when `updateChangesWorkingDirectoryDiff` detects that hunk boundaries/content differ from the previous diff, it should clear the partial selection for the affected lines/hunks and force the user to re-review before allowing a commit, similar to the fix pattern from the FlywheelV2 report (always keep derived caches in sync with the authoritative source rather than doing a shallow existence check).

### Proof of Concept
1. Open GitHub Desktop on a repository, select a file with modifications, and select a subset of lines in a hunk in the Changes view (Partial `DiffSelectionType`), without committing yet.
2. While Desktop is idle on this screen, have an external process (e.g., an editor autosave, a `post-checkout`/`post-merge` hook, or another Desktop-triggered refresh from a background fetch) rewrite the file so that lines are inserted/removed above the previously selected hunk, shifting line numbers but keeping the file "modified" (still triggers `updateChangesWorkingDirectoryDiff`).
3. Desktop reloads the diff via `getWorkingDirectoryDiff` and calls `withSelectableLines` on the existing selection — the same numeric indices remain "selectable" in the new diff (since the new diff also has includeable lines at those positions) and are therefore still marked selected, even though they now point to different content: [7](#0-6) 
4. Without re-inspecting the diff, the user commits via `_commitIncludedChanges`, which stages only files that still have a non-`None` selection: [8](#0-7) 
5. `formatPatch`/`applyPatchToIndex` build the patch strictly from the stale index-based selection, committing content at those indices that the user never actually reviewed post-change: [5](#0-4)

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

  /**
   * Returns a copy of this selection instance with a specified set of
   * selectable lines. By default a DiffSelection instance allows selecting
   * all lines (in fact, it has no notion of how many lines exists or what
   * it is that is being selected).
   *
   * If the selection instance lacks a set of selectable lines it can not
   * supply an accurate value from getSelectionType when the selection of
   * all lines have diverged from the default state (since it doesn't know
   * what all lines mean).
   */
  public withSelectableLines(selectableLines: Set<number>) {
    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))
      : null

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
      selectableLines
    )
  }
