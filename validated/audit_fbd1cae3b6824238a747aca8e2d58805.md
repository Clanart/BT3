### Title
Attacker-controlled prev-txid forces unbounded server-side RPC fetch, stalling output scanning - (File: processor/src/networks/bitcoin.rs)

### Summary
Analogous to the SSRF report (attacker-supplied input causes the server to issue a request to an attacker-chosen target), `get_outputs` derives an RPC request target entirely from an attacker's confirmed Bitcoin transaction and retries that request forever on any failure.

### Finding Description
When a block contains any transaction paying to a scanned multisig script, `get_outputs` reads `tx.input[0].previous_output` — a fully attacker-chosen `(txid, vout)` — and calls `self.rpc.get_transaction(&spent_tx)` inside a `while tx.is_err()` loop with no bound, only sleeping between attempts [1](#0-0) . The fetched prevout is used only to populate the informational `presumed_origin` field, yet its retrieval is placed on the critical path of crediting the deposit [2](#0-1) . `get_outputs` is invoked from the block-scanning loop before outputs are emitted, so a stuck call blocks all crediting for that key [3](#0-2) . The triggering condition is realistic: a Bitcoin node without `txindex=1`, or a pruned node, returns an error for arbitrary historical prev-txids, so the loop never exits.

### Impact Explanation
Any external party who sends a deposit transaction whose first input's prevout is not retrievable via the node's `gettransaction` RPC (no txindex, pruned, or non-wallet tx) causes the processor to loop indefinitely. No `ScannerEvent::Block` is emitted for that block or any later block, so deposits are never credited and the multisig is effectively frozen — a liveness failure on the deposit path reachable by an unprivileged on-chain actor.

### Likelihood Explanation
Triggering requires only broadcasting a normal, valid transaction paying to a published Serai deposit/forward address, choosing which input is `input[0]`. The cost is a standard transaction fee. Whether it succeeds depends on the RPC node's configuration, which is a common deployment variation rather than a malicious-RPC assumption — the loop's unbounded retry converts a routine RPC error into a permanent stall.

### Recommendation
Bound or remove the retry loop: fetch the prevout a bounded number of times, and on persistent failure emit the `Output` with `presumed_origin: None` rather than blocking. Alternatively, tolerate a missing origin entirely, since `presumed_origin` is informational and not required for spendability.

### Proof of Concept
1. Obtain a deposit address for a multisig key (`external_address` / `forward_address` use `scanner(key)` offsets, `processor/src/networks/bitcoin.rs:671-674`, `314-347`).
2. Craft a Bitcoin transaction whose `input[0].previous_output` references a txid the processor's node cannot serve via `get_transaction` (e.g., node without txindex where the prev tx is old/unrelated), with an output paying the scanned script_pubkey.
3. `scan_transaction` matches the output by `script_pubkey` [4](#0-3) , so `get_outputs` enters the `while tx.is_err()` loop and never returns; the deposit is never credited and scanning halts.
