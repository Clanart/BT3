## Title
Diff-Selection Index Desync Between Whitespace-Hidden Preview and Patch Generation Silently Corrupts Partial Commits - (File: `app/src/lib/git/apply.ts`)

## Summary
GitHub Desktop's partial-commit ("stage selected lines") feature encodes the user's line selection as absolute integer offsets into a specific `IDiff` hunk layout (`DiffSelection.isSelected(absoluteIndex)`). The diff structure the user actually reviews in the Changes view can be computed with `git diff -w` (whitespace hidden) when the user has "Hide Whitespace Changes" enabled, which produces a different hunk layout (fewer hunks, different `unifiedDiffStart`/`unifiedDiffEnd` offsets, whitespace-only lines collapsed to context) than the diff computed without `-w`. However, the code path that actually builds the git patch to stage/commit, `applyPatchToIndex` in `app/src/lib/git/apply.ts`, always calls `getWorkingDirectoryDiff(repository, file)` fresh, without forwarding the `hideWhitespaceInDiff` flag, and then reuses the *same* `file.selection` (line indices) against this newly-fetched, structurally different diff.

## Finding Description
`applyPatchToIndex` is the function that turns a user's line selection into the actual patch applied to the git index (and thus into the commit): [1](#0-0) 

It re-fetches the diff via `getWorkingDirectoryDiff(repository, file)` with no whitespace option, then hands that diff straight to `formatPatch`, which walks the diff's hunks and decides inclusion/exclusion purely by absolute line index: [2](#0-1) 

The `DiffSelection` object being consulted (`file.selection`), however, is built and maintained relative to whatever diff was rendered in the Changes/diff UI — a UI path that is threaded through the app with a `hideWhitespaceInDiff` toggle (referenced pervasively in `app-store.ts`, `changes.tsx`, `diff/index.tsx`, `side-by-side-diff.tsx`, etc.). `git diff -w` and `git diff` (without `-w`) do not produce line-index-compatible hunk structures: whitespace-only changes are turned into context lines (or removed) under `-w`, shifting `unifiedDiffStart`/`unifiedDiffEnd` for every subsequent hunk. `app-store.ts` itself acknowledges that a diff "might have changed dramatically since last we loaded it" and only reconciles *selectable* lines, not the semantic meaning of a given absolute index: [3](#0-2) 

The broken invariant: a `DiffSelection`'s absolute line indices are only meaningful with respect to the exact hunk layout of the diff they were computed against. Nothing in `applyPatchToIndex`/`stageFiles` verifies that the diff it fetches at staging time has the same hunk layout as the diff the user actually selected lines against. If the two differ (which happens whenever the whitespace-hide flag differs between the review-time diff and the stage-time diff, or more generally whenever the working tree changed between viewing and staging), `formatPatch` will interpret the stored indices against the wrong lines — silently including lines the user never selected and/or excluding lines the user did select.

## Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user reviewing a diff with whitespace hidden (common when reviewing a file from a repository the attacker controls that mixes reformatting/whitespace churn with a small malicious change) could deliberately deselect the small set of suspicious lines, believe they excluded them, and yet have `applyPatchToIndex` include them in the resulting commit anyway because the line indices it re-derives from the non-`-w` diff no longer line up with the indices the UI recorded. Conversely, intended changes could be silently dropped. Because staging happens through `stageFiles`/`applyPatchToIndex` with no re-validation or diff-identity check against the diff the selection was made from, there is no guard that stops this mismatch, and the user gets no warning — they only discover the discrepancy (if ever) by inspecting the resulting commit diff after the fact.

## Likelihood Explanation
The precondition is realistic and unprivileged: an attacker-controlled repository can be engineered to contain files with heavy interleaving of whitespace-only and content changes (e.g., reformatted/re-indented source with a small backdoored line mixed in), which naturally motivates a victim to toggle "Hide Whitespace Changes" while reviewing before committing/amending. I was not able to fully trace, within the remaining tool budget, the exact call chain that threads the UI's `hideWhitespaceInDiff` setting into the specific `WorkingDirectoryFileChange`/diff object rendered for partial selection in the Changes list (as opposed to History/PR review views, where `hideWhitespaceInDiff` is also heavily used) — this is the piece needed to fully confirm that the *same* selection UI that feeds `applyPatchToIndex` can be shown with `-w` enabled. What is confirmed directly from code is that `applyPatchToIndex` unconditionally recomputes the diff without any whitespace flag and blindly reuses `file.selection`'s absolute indices, and that the codebase's own comment in `app-store.ts` acknowledges diffs can "change dramatically" between when a selection was made and when it's consumed, with no correctness guarantee beyond filtering out now-nonexistent indices.

## Recommendation
- Persist an identity/fingerprint of the diff (e.g. hash of hunk headers/line count) alongside `DiffSelection`, and have `applyPatchToIndex`/`stageFiles` refuse to reuse a selection whose diff fingerprint doesn't match the diff it just fetched — forcing a full re-diff and re-render for user reconfirmation instead of silently proceeding with mismatched indices.
- Ensure `applyPatchToIndex`/`getWorkingDirectoryDiff` used for staging always uses the exact same diff options (notably `hideWhitespaceInDiff`) as whatever diff last produced the currently-active `DiffSelection`, or better, never allow partial-line staging while a non-default diff view (whitespace hidden) is active without normalizing selection back to the canonical (non-`-w`) line space first.
- Add a pre-commit consistency check that compares the actual staged patch content against what the UI selection implies, surfacing a warning if they diverge.

## Proof of Concept
1. Attacker publishes/pushes a repository file containing alternating whitespace-only and one substantive line change per hunk (crafted so that `git diff -w` merges/removes several hunks relative to plain `git diff`).
2. Victim clones/fetches this repo in GitHub Desktop, edits nothing further, but toggles "Hide Whitespace Changes" while reviewing the file in the Changes view, and deselects the hunk(s) containing the substantive change based on the whitespace-hidden hunk layout shown.
3. Victim clicks Commit. `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) calls `getWorkingDirectoryDiff(repository, file)` again, this time without the `-w` flag, producing a diff with different `unifiedDiffStart` offsets per hunk.
4. `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) evaluates `file.selection.isSelected(absoluteIndex)` against the new (non-`-w`) hunk/line indices, which no longer correspond to the lines the user intentionally deselected.
5. The resulting commit silently contains the "excluded" substantive change (or excludes an intended one), with no warning shown to the user before or after commit/push.
