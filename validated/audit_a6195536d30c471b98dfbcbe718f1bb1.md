## Analysis

`getBranchCheckoutArgs` builds the checkout argv as: [1](#0-0) 

and it is concatenated after the base `checkout`/`--progress` args in `checkoutBranch`: [2](#0-1) 

So the final argv is `['checkout', ('--progress'), branch.name, ('-b', branch.nameWithoutRemote), '--']`. Because `--` sits at the **end**, every token before it — including `branch.name` and `branch.nameWithoutRemote` — is still eligible for git's normal option parsing. A ref name that begins with `-` (e.g. `--orphan`, `--force`, `-p`) is therefore interpreted by `git checkout` as a flag rather than as a literal revision/branch name.

`branch.name` and `branch.nameWithoutRemote` are not developer-controlled constants; for remote-tracking branches they come straight from `git for-each-ref %(refname:short)` output in `getBranches`, with no sanitization applied on the read path: [3](#0-2) [4](#0-3) 

The only leading-dash stripping that exists in the codebase, `sanitizedRefName`, is applied when the *user* types a new branch name in the UI, not to names parsed from a fetched/cloned repository's refs: [5](#0-4) 

Git's own `check-ref-format` rules (mirrored in the comment above `invalidCharacterRegex`) do **not** forbid a leading `-` in a ref name, so a malicious remote can advertise/carry a ref such as `refs/heads/--orphan` or similar, and Desktop will happily list it via `getBranches` and later hand `branch.name` to `getBranchCheckoutArgs` unsanitized.

**On the proposed fix ("just move `--` earlier"):** This does not cleanly close the hole. The trailing `--` here is git's documented idiom `git checkout <branch> --`, used to disambiguate a branch name from a pathspec — it must come *after* the branch name for checkout-branch semantics to work at all; moving it *before* `branch.name` would turn the command into `git checkout -- <name>` (restore path from index) instead of "switch to branch," breaking normal checkouts. It also can't be inserted between `branch.name` and the hardcoded `-b`/`nameWithoutRemote` pair without breaking the `-b` flag's own argument-parsing. So reordering `--` alone is not a safe, semantics-preserving fix; the correct fix is to reject/validate any branch name/nameWithoutRemote that starts with `-` before building argv (or use git's `--end-of-options` marker, supported since git 2.24, placed immediately after `checkout`, which terminates option scanning without changing checkout's path-vs-revision semantics).

**On the test coverage:** `checkout-test.ts` only tests:
- invalid character `'..'` [6](#0-5) 
- a valid branch name checkout [7](#0-6) 
- multi-remote branch-name collision [8](#0-7) 
- submodule checkout scenarios [9](#0-8) 

There is **no** test case using a dash-prefixed branch name (e.g. `-b`, `--orphan`, `--force`). This confirms the argv-injection surface via leading-dash branch names is currently untested.

### Title
Argument injection via dash-prefixed branch names in `getBranchCheckoutArgs` - (File: app/src/lib/git/checkout.ts)

### Summary
`checkoutBranch` places the branch name (and, for remote branches, `-b <nameWithoutRemote>`) before the pathspec-terminating `--`, so a ref name beginning with `-` fetched from a malicious remote can be parsed by `git checkout` as an option rather than a revision, and no code path sanitizes leading dashes on names sourced from `for-each-ref`.

### Finding Description
`getBranchCheckoutArgs` [1](#0-0)  returns `[branch.name, ('-b', nameWithoutRemote), '--']`, concatenated onto `['checkout', ...]` in `checkoutBranch` [10](#0-9) . Both `branch.name` and `branch.nameWithoutRemote` originate, for remote-tracking branches, from `%(refname:short)` values returned by `getBranches`/`for-each-ref` [4](#0-3) , and no leading-dash stripping (unlike `sanitizedRefName`, which is UI-input-only) is applied to those parsed names. Because they sit before the trailing `--`, git's own argv parser can interpret a dash-leading branch name as a checkout flag instead of a revision.

### Impact Explanation
An attacker who controls a git remote (in scope per the review's "remote/proxy response" category) can publish a ref whose short name begins with `-` (e.g. mimicking `--orphan`, `-f`/`--force`, `--recurse-submodules`, etc.). When a victim clones/fetches that repository and Desktop lists/checks out that branch, the crafted name is injected as a flag into the `git checkout` invocation, altering checkout behavior — e.g. forcing overwrite of the working tree/uncommitted local changes, or creating an orphan branch — which fits the "silent corruption of what the user commits or pushes" impact category in scope.

### Likelihood Explanation
Requires the victim to clone/fetch from, and then attempt to check out a branch from, a repository controlled by the attacker — a normal, expected Desktop workflow, not requiring unnatural user steps. The main uncertainty (not verifiable without running git/dugite directly) is whether git's transport layer will actually advertise/accept a ref name starting with `-` during a standard fetch/clone versus rejecting it as unsafe at a lower layer; `check-ref-format` itself does not prohibit a leading dash, but this could not be confirmed against the exact dugite/git version pinned in this repo without executing it.

### Recommendation
Do not rely on argument reordering of `--` (it cannot be moved without breaking the intended `<branch> --` and `-b <name>` semantics). Instead, validate `branch.name` and `branch.nameWithoutRemote` in `getBranchCheckoutArgs`/`checkoutBranch` and reject/refuse checkout (or prefix with `./`/use git's `--end-of-options` marker right after `checkout`) whenever either value starts with `-`, mirroring the leading-dash stripping already done by `sanitizedRefName` for user-typed branch names, but applied uniformly to remote-sourced ref names too.

### Proof of Concept
1. Craft a malicious remote repository containing a ref, e.g. `refs/heads/--orphan` (or via `refs/remotes/origin/--force`), created via low-level plumbing (`git update-ref`) or a hand-edited `packed-refs` file, bypassing the porcelain `git branch` name checks.
2. Victim clones/fetches this repository in GitHub Desktop; `getBranches` lists a `Branch` whose `name`/`nameWithoutRemote` is `--orphan` (or similar).
3. Victim checks out that branch in the UI, triggering `checkoutBranch` → `getBranchCheckoutArgs` → `git(['checkout', '--orphan', '--'], ...)` (or with `-b --force` for a remote branch), causing git to execute the injected flag instead of switching to a literal branch named `--orphan`.
4. Confirm no existing test in `app/test/unit/git/checkout-test.ts` exercises this case (only `'..' ` and multi-remote collision are tested) [6](#0-5) .

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}
