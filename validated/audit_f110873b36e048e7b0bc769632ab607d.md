## Title
Relayer's accrued `Fees` balance is zeroed before disbursement is guaranteed, while the disbursement message itself carries zero relayer fee — permanently stranding withdrawn funds - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`pallet-ismp-relayer::withdraw` (the function the `withdraw_fees` extrinsic calls) reads a relayer's `Fees` balance, dispatches an ISMP POST request instructing the destination chain to pay it out, and **immediately zeros the `Fees` entry once dispatch succeeds** — before the destination chain has actually executed the payout. The dispatched request is sent with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }`, i.e. zero relayer fee, so no third-party relayer is economically incentivized to deliver it, and `timeout: 0` means it never expires to trigger any recovery/refund path. If nobody ever delivers this message, the relayer's balance has already been erased on Hyperbridge with no way to reclaim it — mirroring the reported class of "call A zeroes claimable value before B (the actual payout) is guaranteed," which permanently strands user funds.

### Finding Description
In `Pallet::withdraw` [1](#0-0) , the flow is:

1. Read `available_amount = Fees::<T>::get(dest_chain, address)`.
2. Dispatch a `DispatchPost` to the destination's `HostManager` (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate) carrying `WithdrawalParams`/`WithdrawRelayerFees` with the full `available_amount`.
3. On successful dispatch (`dispatch_request(...).map_err(...)`), **unconditionally zero** `Fees::<T>::insert(dest_chain, address, U256::zero())` — this happens as soon as the request is queued in `pallet_ismp::child_trie::RequestCommitments`, not after the destination actually executes the transfer.

The dispatch itself uses:
```rust
dispatcher.dispatch_request(
    DispatchRequest::Post(post),
    FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
)
``` [2](#0-1) 

This zero-fee, zero-payer pattern for hyperbridge-originated system messages is explicitly documented as an unsolved problem elsewhere in the repo: relayers "have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism," and it names `modules/pallets/relayer/src/lib.rs:638` (the withdrawal dispatch call site) as one of the affected paths [3](#0-2) . The withdrawal request also uses `timeout: 0`, meaning it can never time out to trigger any refund/re-credit logic — the module comment itself notes "This request will not timeout, allowing it to be submitted to the destination chain at any time" [4](#0-3) .

Because `Fees` is zeroed the moment `dispatch_request` returns `Ok` — which only means the commitment was recorded locally, not that the destination chain executed the payout — there is no on-chain record left of how much was owed if delivery never happens. Unlike the on-EVM inbound-failure-retry pattern seen in `EvmHost.dispatchIncoming` (which deletes the request receipt on a reverting `onAccept` "so that it can be retried" [5](#0-4) ), retrying the *delivery* of this message does not help: the amount value has already been consumed from `Fees` and does not exist anywhere else to be reconstructed if the request is dropped, censored, or simply never relayed due to lacking any fee incentive.

### Impact Explanation
This is a direct, protocol-level loss-of-funds bug: an honest relayer's entire accrued cross-chain fee balance for a chain is erased from Hyperbridge storage as soon as `withdraw_fees` dispatches successfully, while the actual settlement depends on an unincentivized (zero relayer fee), never-timing-out message reaching the destination `HostManager`/`HYPERBRIDGE_MODULE_ID`. If that delivery never happens — because no relayer bothers to pick up a zero-fee message, or the destination call reverts and is simply never retried by anyone — the funds are permanently lost with no recovery path, since `Fees` no longer records the amount and there is no timeout-triggered refund.

### Likelihood Explanation
Medium-to-high. This isn't a contrived edge case requiring a malicious actor: it is the *documented default behavior* of every hyperbridge-originated system message including this exact withdrawal path, as acknowledged in `docs/outbound-request-incentivization.md`, which explicitly calls out `modules/pallets/relayer/src/lib.rs:638` (the withdrawal dispatch) as relying purely on relayer "altruism" today. Any relayer who calls `withdraw_fees` is exposed to this — it requires no admin/relayer misbehavior, malformed proof, or malicious peer.

### Recommendation
Do not zero `Fees` until the destination-side execution is confirmed (e.g. via a receipt/ack proof, similar to `accumulate_fees`'s proof-based crediting), or alternatively attach a real relayer fee to the withdrawal `DispatchPost` (funded from the treasury/relayer's own balance) so delivery is economically guaranteed, and/or give the request a bounded timeout with an `on_timeout` handler that re-credits `Fees` if delivery fails, exactly the same pattern already implemented for user-originated request timeouts.

### Proof of Concept
1. A relayer accumulates fees via `accumulate_fees`, populating `Fees::<T>::get(dest_chain, address)` with a nonzero balance [6](#0-5) .
2. The relayer calls `withdraw_fees` with a valid signature. `Pallet::withdraw` reads `available_amount`, dispatches the POST request with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }` and `timeout: 0`, and on `Ok` immediately sets `Fees::<T>::insert(dest_chain, address, U256::zero())` [7](#0-6) .
3. Because the dispatched request carries zero fee, no relayer in the permissionless network is compensated to deliver it to the destination `HostManager`/`HYPERBRIDGE_MODULE_ID`; because `timeout: 0`, it never expires to trigger a refund.
4. If the message is never delivered (or delivery reverts, e.g. `HostManager.onAccept`'s `IHostManager(host).withdraw` failing on insufficient/locked treasury balance, as shown to be a real revert path in `test_host_manager_insufficient_balance` [8](#0-7) ), the relayer's balance is permanently zero on Hyperbridge with no corresponding payout ever landing on the destination chain.

A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.
