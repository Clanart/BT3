### Title
Aggregator gRPC accepts any self-signed TLS certificate (no client identity check) when `client_verification=false`, allowing an unauthenticated `SendMoveToVaultTx` call - (File: core/src/servers.rs)

### Summary
In `create_grpc_server`, when `config.client_verification` is `false`, the `ServerTlsConfig` is built with only `.identity(server_identity)` and no `.client_ca_root(...)`, and the interceptor applied is `Noop` instead of `OnlyAggregatorAndSelf`. `.tls_config(tls_config)` is still applied to the `tonic::transport::Server` regardless of `client_verification`, so a fully plaintext (non-TLS) connection is rejected at the handshake layer. However, since no client CA root is configured, the server never requests/verifies a client certificate — any TLS-capable client presenting an arbitrary, freely-generated (self-signed, never registered) certificate, or even no client certificate at all, completes the handshake successfully and reaches the `Noop`-intercepted service.

### Finding Description
Binding claimed to hold: `client presenting cert C` `==` `client authorized as aggregator/self` should be enforced whenever a caller reaches a state-changing RPC such as `SendMoveToVaultTx`. In the `client_verification=false` branch this binding is broken: the equality reduces to `possesses ANY TLS certificate == authorized caller`, because:

- `let tls_config = ... else { ServerTlsConfig::new().identity(server_identity) };` — no `client_ca_root` is set [1](#0-0) .
- The interceptor becomes `Noop` rather than `OnlyAggregatorAndSelf` (which checks peer certs against `aggregator_cert`/`our_cert`) [2](#0-1) .
- `.tls_config(tls_config)` is unconditionally applied to the `Server::builder()` [3](#0-2) .

Because `tls_config` still carries the server `identity` (its own cert+key) even in the `else` branch, `tonic`/`rustls` still performs a server-side TLS handshake (ServerHello + certificate) for every connection — a plaintext HTTP/2 connection with no ClientHello is rejected at the TLS layer, as the question's premise states. But since `client_ca_root` is unset, rustls' `ServerConfig` is built without client-cert verification (`.with_no_client_auth()`-equivalent path in tonic), so the server accepts the TLS handshake from a client presenting any certificate — including a locally-generated, never-registered, self-signed certificate — or from a client presenting no certificate. Once the handshake completes, the only gate left is the `Noop` interceptor, which performs no identity check, and `SendMoveToVaultTx` on the aggregator service is dispatched to the handler.

### Impact Explanation
This is exactly the "unauthenticated state-changing or broadcasting call" category. Any caller possessing nothing more than an ordinary TLS client library and a self-generated certificate — i.e., an unprivileged network attacker with no key share, no operator/verifier role, and no legitimate TLS certificate — can invoke `SendMoveToVaultTx` (and any other aggregator RPC) as if it were an authorized caller. This does not directly move BTC or forge signatures by itself (the aggregator's downstream logic — musig2 sessions, deposit validation, etc. — still gates what can actually be broadcast), but it removes the intended caller-authority boundary at the transport layer for every aggregator RPC, which is the precondition the rest of the system's authorization design (`OnlyAggregatorAndSelf`) relies on. Severity matches the "unauthenticated state-changing or broadcasting call" bucket (High), scoped precisely to "any TLS cert accepted, not caller identity checked" rather than "no TLS required at all."

### Likelihood Explanation
This requires `client_verification=false` in the deployed `BridgeConfig` — a config-driven precondition, not a code path that is always active. Where this flag is `false` (e.g., as shown for the `client_verification=false` matches in `core/src/test/data/bridge_config.toml` and `scripts/docker/configs/testnet4/bridge_config.toml`), the attacker only needs to generate an ephemeral self-signed certificate and initiate a standard TLS 1.2/1.3 handshake against the public aggregator port — no fees, no BTC, no privileged role required. This is fully repeatable and trivially automatable.

### Recommendation
Always configure `ServerTlsConfig` with `.client_ca_root(...)` and require client certificate verification (mTLS) regardless of `client_verification`, or otherwise gate every RPC handler with an authenticated-caller check that does not depend solely on transport-layer TLS client-cert presence. At minimum, do not allow a `Noop` interceptor path to be reachable on any externally-exposed aggregator port; the `OnlyAggregatorAndSelf` check (or equivalent) should be mandatory, independent of the `client_verification` toggle for production configs.
