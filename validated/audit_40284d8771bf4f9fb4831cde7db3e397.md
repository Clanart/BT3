### Title
OP_RETURN data is omitted from transaction weight and fee accounting - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Medium: `SignableTransaction::new` adds an attacker-supplied OP_RETURN output to the signed transaction, but calculates transaction weight, virtual size, required fee, and the maximum-standard-weight check using only the payment outputs. This mirrors an undersized-accounting bug: an optional output contributes bytes to the final transaction without being included in its size calculation. [1](#0-0) 

### Finding Description
`calculate_weight_vbytes` models a transaction containing the requested inputs, payment outputs, and optional change output. [2](#0-1)  Its output list is built only from `payments`, with change optionally appended afterward. [3](#0-2) 

`SignableTransaction::new` accepts up to 80 bytes of public transaction data and appends it as a zero-value OP_RETURN output to `tx_outs`. [4](#0-3) [5](#0-4)  However, the first fee and weight calculation still passes only `payments` and `None` for change, omitting the OP_RETURN output entirely. [6](#0-5)  The change-aware calculation repeats the same omission when deciding whether a change output can be funded. [7](#0-6)  Finally, the standard-weight check uses the underestimated `weight`, so a transaction whose actual weight exceeds `MAX_STANDARD_TX_WEIGHT` can pass validation. [8](#0-7) 

### Impact Explanation
Any call using `Some(data)` produces a transaction with a lower fee rate than the requested `fee_per_vbyte`, because the OP_RETURN output's serialized size is not priced. For the maximum 80-byte payload, the omitted output contributes roughly 91 non-witness bytes, or approximately 364 weight units and 91 vbytes, so the transaction under-reserves approximately `fee_per_vbyte * 91` satoshis. [9](#0-8) [6](#0-5) 

More significantly, transaction data can push the actual transaction over the standard transaction-weight limit while the flawed estimate remains below it. The signing path then produces signatures for a transaction that the API should have rejected as `TooLargeTransaction`, making this a concrete signing of an unintended Bitcoin transaction rather than merely an inaccurate quote. [8](#0-7) [10](#0-9) 

### Likelihood Explanation
The miscalculation is deterministic whenever `data` is `Some`, because `data` is appended to `tx_outs` but never represented in either call to `calculate_weight_vbytes`. [1](#0-0)  An unprivileged party only needs to cause an OP_RETURN-bearing transaction to be signed; no malformed cryptographic input, malicious validator, leaked key, or invalid curve point is required. Exploiting the standardness bypass additionally requires the estimated weight to be close enough to `MAX_STANDARD_TX_WEIGHT` for the omitted output to cross the limit. [7](#0-6) [8](#0-7) 

### Recommendation
Include the OP_RETURN output in the transaction model used by `calculate_weight_vbytes`, either by adding `data` as a parameter and constructing its `TxOut` there, or by calculating weight and virtual size from the complete `tx_outs` list. Recalculate both the no-change and with-change cases after all outputs, including `data`, have been assembled. [11](#0-10) [6](#0-5) 

The final `SignableTransaction` should also be validated against the actual transaction's `weight()` before returning it, rather than relying on a separately reconstructed transaction that can omit fields. [12](#0-11) 

### Proof of Concept
Construct two otherwise identical transactions, one without data and one with 80 bytes of OP_RETURN data:

```rust
let inputs = vec![funded_received_output];
let payments = vec![(payment_script, DUST)];
let data = vec![0u8; 80];

let without_data = SignableTransaction::new(
    inputs.clone(),
    &payments,
    Some(change_script.clone()),
    None,
    fee_per_vbyte,
)
.unwrap();

let with_data = SignableTransaction::new(
    inputs,
    &payments,
    Some(change_script),
    Some(data),
    fee_per_vbyte,
)
.unwrap();

// The fee estimate is unchanged despite the extra output.
assert_eq!(without_data.needed_fee(), with_data.needed_fee());

// The actual transaction contains the additional OP_RETURN output.
assert_eq!(
    with_data.transaction().output.len(),
    without_data.transaction().output.len() + 1,
);
assert!(with_data.transaction().weight() > without_data.transaction().weight());
```

The equality succeeds because `needed_fee` is derived from a model containing only `payments`, while the actual transaction returned for signing contains the extra OP_RETURN output. [11](#0-10) [6](#0-5)
