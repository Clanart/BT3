### Title
Partial-commit patch application re-reads the working-tree diff at apply time, allowing staged/committed content to diverge from what the user reviewed and selected - ([File: app/src/lib/git/apply.ts])

### Summary
The Frontier fix addressed a race where `eth_getTransactionReceipt` looked up data by number using an index that could be updated between the initial reference (block number) being formed and the mapping actually being resolved, returning a receipt inconsistent with what the caller expected. The structural analog in Desktop is `applyPatchToIndex` in [1](#0-0) , which re-fetches the working-directory diff from disk at *stage/commit* time and then re-applies the user's line-selection indices (`file.selection`, computed against the diff shown to the user earlier in the UI) to this freshly-fetched diff.

### Finding Description
When a user stages a partial selection of lines/hunks for a modified file, GitHub Desktop stores a `DiffSelection` keyed by absolute line index into a diff object that was rendered earlier in the UI. When the commit actually executes, `stageFiles` calls `applyPatchToIndex` for every partially-selected file [2](#0-1) , and `applyPatchToIndex` calls `getWorkingDirectoryDiff(repository, file)` again, right before formatting the patch: [3](#0-2) 

`formatPatch` then walks the **newly fetched** diff's hunks and lines, and decides what to include based solely on `file.selection.isSelected(absoluteIndex)` [4](#0-3)  — i.e., it trusts that the index positions in the old (UI-time) diff still correspond to the same lines in the new (apply-time) diff. There is no check that the diff used to build the selection is the same diff being patched, and no re-validation of file content/hash between the two reads.

If the tracked file's contents change on disk between the moment the diff/selection was created in the UI and the moment `createCommit`/`applyPatchToIndex` runs (e.g. due to a build/watch tool, an editor auto-save, an npm script, or a git clean/smudge filter defined in `.gitattributes` of a cloned/fetched repository that mutates the file asynchronously), the hunk boundaries and absolute line indices can shift. `formatPatch` will then apply the "selected" indices to the wrong lines of the new diff, producing a patch that stages/commits different content than what the user reviewed and explicitly selected in the Changes view.

### Impact Explanation
This is a silent corruption of what the user commits: content the user did not review or intended to exclude can end up staged and committed (and subsequently pushed), while content the user explicitly selected can be silently dropped. Because `.gitattributes`-driven clean/smudge filters and other repository-defined hooks can be attacker-controlled in a cloned/fetched repository, this creates a path for the "attacker controls a cloned/fetched repository" primitive to influence what a victim unknowingly commits/pushes — matching the class of "silent corruption of what the user commits or pushes" in the stated impact criteria.

### Likelihood Explanation
Exploitation requires a window between diff computation (shown to the user) and patch application (at commit time) during which the tracked file's on-disk content changes in a way that shifts hunk boundaries, and it depends on filters/tools that mutate tracked files without direct, deliberate user action. This is a narrower race than the Frontier bug (which affected essentially all callers on every block), but the underlying invariant break — reusing position-based selection state against re-fetched, potentially different data — is directly analogous, and no code path in `applyPatchToIndex`/`formatPatch` guards against it.

### Recommendation
Capture and reuse the exact diff object (or its content hash) that was used to build the `DiffSelection` when generating the patch in `applyPatchToIndex`, instead of re-fetching a new diff from disk at apply time. If the working-tree content has changed since the diff was generated, fail the partial stage/commit operation (or force a diff refresh and selection re-validation) rather than silently applying stale selection indices to new diff content.

### Proof of Concept
Not independently reproduced; based on static code-path analysis of `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) and `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`), which show the diff is fetched twice (once for UI display/selection, once for the actual patch) with no consistency check between the two reads. Verifying live exploitability (e.g., using a `.gitattributes` clean filter to mutate a tracked file between diff-render and commit) would require running Desktop end-to-end, which is outside the scope of static analysis here.

export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })
