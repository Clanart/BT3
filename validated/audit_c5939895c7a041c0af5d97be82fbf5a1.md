### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class is an access/reachability boundary that is broader than the pre-defined safe subset: OnionShare's sandbox granted read access to the entire home directory instead of only OnionShare folders. The Serai analog is `Scanner::scan_block`, which scans *all* transactions in a block — including the coinbase — and emits `ReceivedOutput`s for coinbase outputs paying to the multisig's P2TR script. Coinbase outputs are consensus-immature (COINSTAKE_MATURITY = 100 blocks), so the scanner reports funds as received that cannot yet be spent.

### Finding Description
`Scanner::scan_block` iterates `block.txdata` from index 0 and forwards each transaction to `scan_transaction`, which matches `output.script_pubkey` against the registered `scripts` map and returns a `ReceivedOutput` { offset, output, outpoint } (mod.rs lines 199-227). A `ReceivedOutput` produced this way is indistinguishable from a normally spendable UTXO: `SignableTransaction::new`/`multisig` will happily build and threshold-sign a transaction spending it via `Prevouts::All` + `taproot_key_spend_signature_hash` (send.rs lines 373-397). Broadcast then fails because the coinbase is immature.

Serai's own processor acknowledges the problem: `Bitcoin::get_outputs` explicitly skips `block.txdata[0]` (`processor/src/networks/bitcoin.rs:691`), proving the coinbase was meant to be excluded from the spendable set. But the in-scope `bitcoin-serai` `Scanner` — the API integrators (and other networks' send paths) rely on — performs no such restriction, and the only mitigation is a doc comment telling callers to post-filter.

### Impact Explanation
Any unprivileged party capable of mining a block (or getting a coinbase template mined) can pay directly to Serai's external P2TR address or to any registered offset script. The scanner then reports the output as received; downstream code that treats `ReceivedOutput` as spendable constructs and signs a transaction that the network rejects. This matches the accepted impact "funds reported received that are not spendable": balance accounting credits an input that `SignableTransaction`/`TransactionMachine` will sign but that cannot confirm for ~100 blocks. Repeated deposits (one per mined block) can continually inject phantom spendable outputs.

### Likelihood Explanation
Requires an attacker to control a coinbase output paying to the target script — feasible for miners/mining pools with no cooperation from Serai participants. Severity is Medium: no secret leakage or theft, but the scanner's output contract ("a spendable output") is violated with real accounting/DoS consequences, and the library-level fix (skipping `txdata[0]` in `scan_block`, as the processor already does) is unambiguously correct.

### Recommendation
Restrict `Scanner::scan_block` to `block.txdata[1 ..]`, or add a `mature`/`coinbase` flag on `ReceivedOutput` so consumers cannot treat immature coinbase outputs as spendable inputs. At minimum, mirror the processor's exclusion inside the library rather than relying on caller-side filtering.
