### Title
`resolveWithin` sandbox check uses a bare string-prefix comparison, allowing writes/reads to escape the repository root - ([File: app/src/lib/path.ts])

### Summary
The bug in the external report is a broken numeric-boundary invariant: a conversion constant was silently wrong by a factor of 10, so a value that was supposed to be constrained to a safe range (bps→decimal) slipped through validation and was trusted downstream. The equivalent flaw in GitHub Desktop is in the sandbox/containment check `_resolveWithin()` in `app/src/lib/path.ts`, which is supposed to guarantee "this resolved path is inside the repository root," but implements that guarantee with a bare string `startsWith()` comparison instead of a proper path-boundary comparison: [1](#0-0) 

Because `startsWith` has no notion of a path separator, any sibling directory whose name happens to begin with the same characters as the repository's folder name will incorrectly be treated as "inside" the repository.

### Finding Description
`resolveWithin(rootPath, ...pathSegments)` is Desktop's general-purpose guard used across the codebase to stop path-traversal from untrusted input (URL deep links, AI-generated file paths, etc.) before performing filesystem operations: [2](#0-1) 

The final containment check is:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
This is the exact "wrong-constant" class of bug: the invariant *"resolved path must be a descendant of root"* is encoded as a raw prefix string comparison with no separator boundary. If `realRoot` is `/Users/joe/GitHub/desktop` and an attacker-influenced path segment resolves (via `..` traversal) to `/Users/joe/GitHub/desktop-secrets/config.json`, the check passes because `"/Users/joe/GitHub/desktop-secrets/config.json".startsWith("/Users/joe/GitHub/desktop")` is `true`, even though `desktop-secrets` is a completely different, sibling directory. The correct check should require `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`.

This primitive is then used to gate a real write in the AI/Copilot conflict-resolution flow, which writes model-influenced content to disk: [3](#0-2) 

Critically, the write is *not* additionally validated against the actual list of conflicted files before writing — the `onDiskFile` lookup only short-circuits the write when the file **is** found and already resolved; if `resolution.path` doesn't match any real working-directory entry at all, execution falls through to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` anyway. So the only thing standing between an attacker-influenced `resolution.path` (Copilot conflict resolutions are derived from the contents of the cloned/fetched repository, a known prompt-injection vector for AI merge/conflict features) and an out-of-repo file write is the `resolveWithin` boundary check — and that check is broken exactly the way the report describes: a boundary/limit comparison that silently admits values it should reject.

The same broken primitive also backs the deep-link `filepath` handling, where `openRepositoryFromUrl` (reachable via `x-github-client://openrepo/...?filepath=...`, a link a user can be induced to click) uses `resolveWithin` before calling `shell.showItemInFolder`: [4](#0-3) 

### Impact Explanation
The broken boundary check causes `resolveWithin` to silently approve destinations outside the intended repository sandbox whenever a sibling directory shares a name prefix with the repository directory (a very common real-world pattern: `repo`/`repo2`, `app`/`app-old`, `project`/`project-backup`, etc.). Where this guard backs a `writeFile` (Copilot conflict resolution), the practical impact is silent corruption/creation of files outside the user's repository — content the user did not intend to write, potentially staged and committed/pushed without their knowledge, matching the report's core impact theme ("silent corruption of what the user commits") applied to the filesystem instead of a price calculation. Where it backs `shell.showItemInFolder`, it allows revealing/opening files outside the repo root via a crafted deep link.

### Likelihood Explanation
Exploitability does not require any local/physical access, admin rights, or pre-existing malware: the attacker only needs (a) control over content in a repository the user clones/fetches (feeding paths into the Copilot conflict-resolution pipeline) or (b) the ability to get the user to click a crafted `x-github-client://openrepo/...` deep link, plus a plausible sibling directory name — both are realistic given common folder-naming conventions on developer machines. The root cause is a single, easily reachable comparison (`startsWith`) shared by every call site of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`, so no other guard in the call chain currently enforces the separator boundary.

### Recommendation
Fix the invariant at its source in `_resolveWithin` (app/src/lib/path.ts):
```diff
- return realResolved.startsWith(realRoot) ? resolved : null
+ const sep = options === Path.posix ? '/' : Path.sep
+ return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
+   ? resolved
+   : null
```
Additionally, in `app-store.ts`'s Copilot conflict-resolution loop, require that `resolution.path` match an actual conflicted entry in `state.changesState.workingDirectory.files` before ever calling `writeFile`, rather than only using that list to skip already-resolved files.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdir } from 'fs/promises'

// Setup: two sibling directories sharing a prefix, as commonly exists on disk
// /tmp/work/repo         <- the trusted repository root
// /tmp/work/repo-secrets <- an unrelated sibling directory
await mkdir('/tmp/work/repo', { recursive: true })
await mkdir('/tmp/work/repo-secrets', { recursive: true })

// A traversal segment ("../repo-secrets/pwned.txt") resolves outside root,
// but the prefix check in _resolveWithin incorrectly approves it because
// "/tmp/work/repo-secrets/pwned.txt".startsWith("/tmp/work/repo") === true
const result = await resolveWithin('/tmp/work/repo', '../repo-secrets/pwned.txt')

console.log(result)
// Expected: null (path escapes the repository root)
// Actual:   '/tmp/work/repo/../repo-secrets/pwned.txt' resolved and returned,
//           i.e. the guard fails to reject the escape.
```
This confirms the boundary check is broken independent of any specific caller; the Copilot conflict-resolution write path and the deep-link `filepath` open path both rely on this same faulty primitive to keep filesystem operations confined to the repository.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
