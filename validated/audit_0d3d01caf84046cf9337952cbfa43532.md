### Title
Stale diff reuse via content-insensitive file ID allows silent commit of unreviewed content - (File: app/src/lib/stores/updates/changes-state.ts)

### Summary
The Chaos Labs bug pattern is a "broken invariant": a `previousValue` cache was keyed too coarsely (by update type only, not type+market), so a value computed for one context was silently reused for a different context. GitHub Desktop has the same class of bug in `updateChangedFiles`, which decides whether to keep or invalidate a cached working-directory diff purely by comparing `WorkingDirectoryFileChange.id` values, not by any content fingerprint.

### Finding Description
When Desktop refreshes the working directory status, `updateChangedFiles` decides whether the previously loaded diff for the selected file can be reused:

```ts
const diff =
  selectedFileIDs.length === 1 &&
  state.selection.selectedFileIDs.length === 1 &&
  state.selection.selectedFileIDs[0] === selectedFileIDs[0]
    ? state.selection.diff
    : null
``` [2](#0-1) 

The same "still the same file, so keep the cached diff" pattern is used by `updateChangesWorkingDirectoryDiff` in `app-store.ts` when comparing pre-load and post-load selection state (`arrayEquals(... selectedFileIDs ...)` and `selectedFileID !== selectedFileIdBeforeLoad`). [3](#0-2) 

Both checks rely entirely on `WorkingDirectoryFileChange.id`, which is computed as `${status.kind}+${path}` (or with `oldPath` for renames/copies) — a value derived only from the file's status kind and path, never from its actual content, size, or mtime. [4](#0-3) 

This means the "identity" of a file, from the diff-caching perspective, is indistinguishable across two different revisions of on-disk content as long as the path and status kind (e.g. `Modified`) stay the same. If the on-disk content of the selected file changes between the time Desktop starts computing/rendering a diff and the time the next status refresh completes (e.g. because a git hook, a build tool, an editor auto-save, or another process invoked as part of a checkout/merge/rebase/LFS smudge triggered by the cloned/fetched malicious repository rewrites the file after `git status` classifies it as `Modified` but before the diff render or the next status poll), Desktop will treat the file as "the same file" and either reuse the stale in-memory diff or fail to reload a fresh one, all while the working tree content has already changed underneath the user.

### Impact Explanation
This directly maps to the "silent corruption of what the user commits or pushes" impact category: the user reviews a diff in the Changes view, believes it accurately represents what will be committed, checks the box, and commits — but git actually stages/commits the *current* on-disk content, which may differ from what was displayed if it was altered by a hook or background process triggered by attacker-controlled repository content (e.g. `post-checkout`, `smudge`/`clean` filters, LFS pointers, or a build script invoked from `package.json`/CI config in the fetched repo) between the diff render and the commit action. Because Desktop's periodic background status refresh (`gitStore` polling) runs independently of the diff render, there's a real window where the UI and the actual working tree diverge without any indication to the user, since the guard only checks `id` equality, not content equality.

### Likelihood Explanation
The likelihood is moderate: it requires a git repository or fetched content that can trigger a file rewrite through legitimate Desktop-invoked git machinery (hooks, LFS filters, submodule updates) shortly after a status refresh but before the user commits, without changing the file's classified status kind or path. This is plausible in cloned/fetched repositories that ship hooks or LFS smudge filters (both are things an attacker fully controls when the victim clones/fetches their repository), and does not require local/physical access, admin rights, or social engineering beyond the normal "user clones/fetches a repository" action already covered by the valid-impact scope.

### Recommendation
Include a content fingerprint (e.g., blob hash or `mtime`+`size` from the `git status`/`lstat` result) as part of the cache-validity check in `updateChangedFiles` and `updateChangesWorkingDirectoryDiff`, rather than relying solely on the path/status-derived `id`. Alternatively, always re-fetch the diff on every status refresh for the currently selected file rather than conditionally reusing the previous `diff` object, and explicitly reload the diff immediately before staging/committing to guarantee that what's shown to the user matches what's committed.

### Proof of Concept
1. Attacker publishes a repository containing a `post-checkout` hook (or a Git LFS smudge filter / build script commonly auto-run by tooling) that rewrites a tracked file's content after checkout without changing its path.
2. Victim clones the repository in Desktop and makes an edit to that file so it is classified `Modified`; Desktop computes and displays a diff, caching it against `id = "Modified+<path>"`.
3. The hook/filter/background process rewrites the file's content on disk (still `Modified` status, same path) after Desktop's diff is displayed but before the user commits.
4. On the next background status refresh, `updateChangedFiles` sees the same `selectedFileIDs` (`"Modified+<path>"` unchanged) and reuses `state.selection.diff` per the check at `app/src/lib/stores/updates/changes-state.ts:90-95`, so the UI continues to show the stale diff.
5. The user commits, believing they reviewed the change, but the committed content is the version rewritten by the hook — not what was displayed.

*Note: I was not able to directly trace the exact hook/filter invocation timing relative to the periodic status-refresh interval within the indexed portion of the codebase, so the precise race window size is not fully verified from local code alone — this would benefit from a live Desktop session to confirm exact timing behavior.*
