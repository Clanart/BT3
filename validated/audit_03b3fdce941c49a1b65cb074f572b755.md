### Title
`unvote()` reverts for deactivated pools due to an inverted `pool.isActive` check, permanently trapping a voter's vlMGP votes and blocking `VLMGP.startUnlock()` - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager.unvote()` is documented as the mechanism to "Unvote from an inactive pool" so that deleting a pool doesn't trap users, but the implementation reverts with `PoolNotActive()` precisely when `pool.isActive` is `false` — the opposite of the intended behavior. Once the owner sets `poolInfos[lp].isActive = false` for a pool a user previously voted on, that user can never zero out `userVotedForPoolInVlmgp`/`userTotalVotedInVlmgp` for that pool, since both `vote()` and `unvote()` require `pool.isActive == true`.

### Finding Description
`vote()` requires `pool.isActive` for every pool touched (including negative deltas used to reduce a vote): [1](#0-0) 

`unvote()` carries the NatSpec "Unvote from an inactive pool. This makes it so that deleting a pool ... doesn't block users from withdrawing," yet its guard reverts precisely when the pool is inactive: [2](#0-1) 

Because both entry points into reducing a user's vote (`vote()` with negative delta and `unvote()`) require `pool.isActive == true`, once the pool is flipped to `isActive = false`, neither function can be used to reduce `userVotedForPoolInVlmgp[msg.sender][pool]` or `userTotalVotedInVlmgp[msg.sender]` for that pool. There is no other public/external function in `WombatBribeManager.sol` that clears these mappings independent of the `isActive` flag.

This inflated `userTotalVotedInVlmgp[msg.sender]` is read by `VLMGP.startUnlock()`: [3](#0-2) 
If a user's entire locked balance (or enough of it) was voted on the now-deactivated pool, `totalLockAfterStartUnlock < userTotalVotedInVlmgp(msg.sender)` will be true for any unlock amount that would bring the user below their frozen "voted" total, causing `startUnlock()` to revert with `NotEnoughLockedMPG`.

### Impact Explanation
This is a permanent freezing-of-funds bug from the perspective of an unprivileged voter: their locked MGP cannot enter the unlock queue at all (or only partially, if some non-deactivated votes exist) because the stale vote accounting can never be reduced. This matches the "permanent freezing of user funds" / "freezing for ≥24 hours" impact class, since `coolDownInSecs` cooldown periods in `VLMGP` are typically long, and here the user cannot even *start* the cooldown. Root cause is a state-inconsistency (inverted condition) reachable purely through normal user actions (`vote`) plus an admin operational action (deactivating a pool) that is a legitimate, expected admin action per the code's own design intent (the NatSpec explicitly anticipates pool deactivation/removal as a normal event, not malicious governance).

### Likelihood Explanation
Preconditions are minimal and realistic: (1) attacker/victim locks MGP in `VLMGP`, (2) votes on any pool via `WombatBribeManager.vote()`, (3) pool owner later deactivates that pool (a normal, expected lifecycle event explicitly anticipated by the contract's NatSpec, not a malicious/adversarial admin action) . No special capital or flash loans are needed; any voter on a pool that is later deactivated is affected. This is highly likely to occur over the protocol's lifetime since pools are expected to be deactivated periodically.

### Recommendation
Invert the condition in `unvote()` so it does not require the pool to be active (or removes the check altogether, since the function's entire purpose is to allow exit from inactive pools), while retaining any necessary rewarder/withdraw safety accounting. E.g., only branch on `pool.isActive` when deciding whether to call `IBribeRewardPool(pool.rewarder).withdrawFor(...)` (skip or handle failures gracefully if the rewarder is also being deprecated), but do not revert `unvote()` merely because `isActive == false`.

### Proof of Concept
Foundry test outline:
1. Deploy/wire `WombatBribeManager`, `VLMGP`, a bribe rewarder, and register a pool `lp` as active.
2. User locks `X` MGP into `VLMGP` via `lock(X)`.
3. User calls `vote([lp], [+X])` — assert `userVotedForPoolInVlmgp[user][lp] == X` and `userTotalVotedInVlmgp[user] == X`.
4. Owner deactivates the pool (set `poolInfos[lp].isActive = false` via whatever admin setter exists, e.g. re-adding with isActive=false or a dedicated setter).
5. User calls `unvote(lp)` — assert it reverts with `PoolNotActive()`.
6. User calls `VLMGP.startUnlock(X)` — assert it reverts with `NotEnoughLockedMPG` because `totalLockAfterStartUnlock (0) < userTotalVotedInVlmgp(user) (X)`.
7. Assert the user's entire locked MGP balance is permanently unable to enter the unlock cooldown, demonstrating fund freezing beyond 24 hours (the cooldown period itself cannot even begin). [2](#0-1) [4](#0-3)

```text
    /// @notice Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing
    function unvote(address _lp) public {
        Pool storage pool = poolInfos[_lp];
        uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
        if(!pool.isActive)
            revert PoolNotActive();
        
        pool.totalVoteInVlmgp -= uint256(currentVote);
        userTotalVotedInVlmgp[msg.sender] -= uint256(currentVote);
        userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] = 0;
        if (msg.sender != delegatedPool) {
            totalVlMgpInVote -= currentVote;
        }
        
        IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(currentVote), true);
    }
```
