Audit Report

## Title
Unauthenticated `DepositDelegatorRewards` allows any signer to inflate `pending_delegator_rewards` and lock/grief a vote account's withdrawable balance - (File: programs/vote/src/vote_state/mod.rs)

## Summary
The `deposit_delegator_rewards` instruction only verifies that the depositing/source account signs its own lamport transfer via `verify_authorized_signer(&source_address, signers)`; it performs no check that the caller is related to the target vote account (not the withdraw authority, node identity, or block-revenue collector). Any unprivileged account can therefore call it against an arbitrary V4 vote account, uncapped by `add_pending_delegator_rewards` (bounded only by `u64` overflow), and that inflated `pending_delegator_rewards` value is subsequently treated by `withdraw()` as a mandatory reserve that reduces the withdrawable balance and blocks account closure.

## Finding Description
`deposit_delegator_rewards` checks only that `source_address` (the sender of the deposit) is a signer, with no relationship required to the vote account's authorized withdrawer or identity: [1](#0-0) 

It then CPIs a System transfer and unconditionally calls `add_pending_delegator_rewards`, which only guards against `u64` overflow, not authorization or a maximum: [2](#0-1) 

`withdraw()` subsequently reads `pending_delegator_rewards` directly and (a) rejects full-balance withdrawal/closure whenever it is nonzero, and (b) adds it to the mandatory `min_balance` reserve for partial withdrawals — with no path in this function to distinguish attacker-injected value from legitimately-collected block revenue: [3](#0-2) 

The only existing guard is the signature check on the depositor's own funds (`verify_authorized_signer`), which is insufficient because it authorizes the *transfer of the depositor's own lamports*, not authorization to modify the *target* vote account's reserved-rewards accounting.

## Impact Explanation
This does not directly steal funds, but it lets an unprivileged, unrelated party unilaterally reduce a vote account withdrawer's control over their own funds: the withdrawer's withdrawable balance is reduced by an attacker-chosen amount, and the vote account can be rendered non-closeable purely via `withdraw()`'s `pending_delegator_rewards > 0` check. This falls under fund lock / loss-of-control impact in the accounts/runtime category.

## Likelihood Explanation
Feasibility is high and repeatable: any account can sign a small self-transfer and invoke `DepositDelegatorRewards` against any V4 vote account, at a cost proportional only to the attacker's own deposit (which is not burned, but forcibly redirected into the target's reward accounting). The precondition is that `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` are all active, as gated in `vote_processor.rs`: [4](#0-3) 

## Recommendation
Restrict `deposit_delegator_rewards` to require the deposit to be attributable to an authorized party for that vote account (e.g., the designated block-revenue commission collector), mirroring the `verify_authorized_signer` pattern already used for `update_commission_collector`; alternatively, decouple `withdraw()`'s mandatory reserve/close-block logic from a field any outside party can inflate, e.g. by capping growth per epoch or only honoring deposits routed through an authorized collector path.

## Proof of Concept
Existing unit tests demonstrate the unrestricted deposit and its downstream effect on withdrawal: [5](#0-4) [6](#0-5) 

Steps: (1) attacker signs a `VoteInstruction::DepositDelegatorRewards { deposit }` naming itself as `source_address` and an arbitrary victim vote account as the target; (2) the call succeeds since only the attacker's own signature is checked; (3) `pending_delegator_rewards` in the victim account increases; (4) the victim's authorized withdrawer's subsequent `Withdraw` call is now constrained by this attacker-controlled value, per `withdraw()`.
