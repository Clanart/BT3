### Title
Deterministic preprocess seed reuse lets `share`/`complete` sign divergent messages with identical nonces — validator key recovery - (File: `coordinator/src/tributary/signing_protocol.rs`)

### Summary
The Linux bug (CVE-2021-47162) appends private data into an skb `frag_list` that was cloned and shared by other skbs — one buffer ends up "seen" by multiple consumers although it was only meant for one. The Serai analog is the `CachedPreprocess` design in `SigningProtocol::preprocess_internal`: a single nonce seed is persisted in the DB keyed only by `context`, and every subsequent call — `preprocess()`, `share()`, and the internal `share_internal` inside `complete()` — regenerates the *same* secret nonces via `seeded_preprocess`. The seed is shared across all signing calls for a context, but each `sign()` call consumes it as if it were fresh. If two calls bind to different `msg`/preprocess sets, the identical nonce pair signs twice — classic FROST nonce reuse enabling private key share recovery.

### Finding Description
`preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148) generates a `ChaCha20Rng` seed once per `context`, stores it XOR-encrypted in `CachedPreprocesses`, and on every call decrypts it and runs `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (crypto/frost/src/sign.rs:121-144, 268-274), which deterministically regenerates identical `nonces` and `commitments`. There is no "consumed" flag: the cache entry is never cleared or versioned. `share_internal` (line 156) calls `preprocess_internal` then `machine.sign(preprocesses, msg)`, so *every* share/complete operation reuses the same nonce seed.

The danger materializes in `DkgConfirmer`:
- `generated_key_pair` (coordinator/src/tributary/handle.rs:47-60) calls `.share(preprocesses, key_pair)` where `key_pair` is whatever the processor reported — and `DkgKeyPair::set`/`KeyToDkgAttempt::set` unconditionally overwrite any prior pair for `(genesis, attempt)`. There is no guard against a second, distinct `KeyPair` being recorded for the same attempt.
- Later, `DkgConfirmed` handling (handle.rs:526-535) loads `DkgKeyPair::get` — the *latest stored* pair — and calls `confirmer.complete(...)`, which internally calls `share_internal` again (signing_protocol.rs:321-326), re-signing under the same context `("DkgConfirmer", attempt)` and therefore the same nonces.

`msg` in `share_internal` is `set_keys_message(&self.spec.set(), &removed, key_pair)` (signing_protocol.rs:296-300) — it commits to `key_pair`. If the stored key pair changed between the published `share` and `complete` (e.g., processor reported a distinct pair after blame/re-execution for the same attempt), the same nonce pair `d, e` produces two shares `s_i = d + ρ·e + λ·c_i·x` with different challenges `c_i` bound to different messages. Since `ρ`, `λ`, `c_i` and both shares are public (the share is published in `Transaction::DkgConfirmed`), anyone solves `x = (s_1 − s_2) / (λ·(c_1 − c_2))` — recovering the validator's Ristretto secret key, the root of trust for DKG confirmation.

The header comment (lines 25-48) claims safety from "the nonces being context-bound under a BFT protocol" and explicitly notes a TODO to check that published shares match the presumed preprocess — which is exactly the un-guarded gap: the *message* signed is derived from mutable DB state (`DkgKeyPair`), not bound into the nonce context.

### Impact Explanation
Reuse of a FROST/Schnorr nonce across two distinct challenges yields the signer's secret scalar directly. Here the secret is the coordinator validator's Ristretto private key used for MuSig confirmation of DKG results — i.e., a root-of-trust key whose compromise lets an attacker forge `set_keys` confirmations or equivocate undetectably. Both shares are published on the public tributary chain, so recovery is passive and requires no further interaction.

### Likelihood Explanation
Triggering requires `generated_key_pair` to be invoked more than once with a distinct `KeyPair` for the same `attempt`, or `share` inputs to differ between the public share call and `complete`. There is no `assert` preventing overwrite of `DkgKeyPair`/`KeyToDkgAttempt`, and processor re-execution after blame events (`InvalidDkgShare` flows) is the designed path for producing a different key pair within one attempt. The precondition is a divergence in BFT-finalized inputs rather than direct attacker control, which lowers likelihood to Medium — matching the source CVE's severity — but the cryptographic consequence is total key exposure.

### Recommendation
- Bind the message (or at least `key_pair` / a digest of `set_keys_message`) into the `CachedPreprocesses` key, or store the first `msg` hash alongside the seed and `assert_eq!` it on reuse, analogous to `FirstPreprocessDb::save_first_preprocess`'s `assert_eq!(&existing, preprocess)` (coordinator/src/db.rs:90-93).
- Guard `DkgKeyPair::set`/`KeyToDkgAttempt::set` in `generated_key_pair` against a second distinct write for the same attempt.
- Delete or tombstone the cached seed after first `sign()` and regenerate via `AlgorithmMachine::preprocess(&mut OsRng)` for any repeated call under the same context.

### Proof of Concept
```
1. Attempt a: all validators publish DkgShares; coordinator accumulates
   ConfirmationNonces and calls generated_key_pair(key_pair=KP1)
   -> DkgKeyPair[genesis, a] := KP1
   -> share(preprocesses, KP1) signs msg1 = set_keys_message(set, removed, KP1)
      with nonces (d, e) derived from cached seed S(context=("DkgConfirmer", a))
   -> share s1 = d + rho*e + lambda*c1*x published via Transaction::DkgConfirmed.

2. A blame/re-execution path causes the processor to report a distinct
   valid KeyPair KP2 for the same attempt -> generated_key_pair(KP2)
   overwrites DkgKeyPair[genesis, a] := KP2 (no assertion prevents this).

3. DkgConfirmed accumulation completes; handler loads DkgKeyPair::get = KP2
   and calls confirmer.complete(preprocesses, &KP2, shares)
   -> share_internal re-derives identical nonces (d, e) from S
   -> produces s2 = d + rho*e + lambda*c2*x with c2 bound to
      msg2 = set_keys_message(set, removed, KP2).

4. Both s1, s2 and all public values are on-chain. Attacker computes
      x = (s1 - s2) * (lambda*(c1 - c2))^-1
   recovering the validator's private key.
```
