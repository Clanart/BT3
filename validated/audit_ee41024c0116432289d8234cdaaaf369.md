## Finding

### Title
Uncontrolled recursion in `AccountKeyRoleBased.DecodeRLP` allows stack exhaustion via deeply nested account keys - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively RLP-decodes each embedded key by re-invoking `AccountKeySerializer.DecodeRLP` → `NewAccountKey` → (potentially) `AccountKeyRoleBased.DecodeRLP` again, with no depth limit, mirroring the CVE-2017-9616 pattern of unbounded recursive box/child parsing in `dissect_mp4_box`.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of RLP-encoded sub-keys and, for each entry, calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is an `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type and then decodes into a freshly constructed `AccountKey` of that type via `s.Decode(serializer.key)`: [2](#0-1) 

If the declared type is again `AccountKeyTypeRoleBased`, this calls back into `AccountKeyRoleBased.DecodeRLP`, and the cycle repeats for every nesting level present in the encoded bytes. There is no recursion-depth guard anywhere in this decode path. The only protection against nested `RoleBasedKey` values — `IsCompositeType()`/`CheckInstallable`/`CheckUpdatable` returning `kerrors.ErrNestedCompositeType` — is applied *after* the object graph has already been fully constructed by decoding: [3](#0-2) [4](#0-3) 

This is confirmed by the existing test that documents the intended rejection of nested role-based keys, which only rejects the tx during pool/apply validation, i.e., strictly after decoding has completed: [5](#0-4) 

Similarly, `api_kaia.go`'s `checkAccountKeyZeroValues` only prevents one level of nesting for the JSON path (`EncodeAccountKey`), and does so after the key object already exists, not during decode: [6](#0-5) 

Because the semantic "no nested composite type" rule is enforced post-decode, an attacker can supply an `AccountKeyRoleBased`-typed key whose encoded byte string embeds another `AccountKeyRoleBased` (which embeds another, etc.) many thousands of times. Decoding such a value recurses through `DecodeRLP` → `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → `NewAccountKey`/`s.Decode` → back into `DecodeRLP`, consuming a stack frame per level with no bound other than available process stack, exactly analogous to `dissect_mp4_box`'s unbounded recursion on nested "chunks" in the referenced Wireshark CVE.

### Impact Explanation
This account key structure is decoded on any node processing an `AccountUpdate`/`FeeDelegatedAccountUpdate` (and variants) transaction that carries an RLP-encoded `AccountKey` payload — reachable from a single submitted transaction via the public RPC (`eth_sendRawTransaction`) or transaction pool ingestion, and again during block validation by every node in the network. A crafted deeply-nested key can exhaust the goroutine stack and crash the node process (Go runtime `fatal error: stack overflow` is not recoverable via `recover()`), producing a denial-of-service that can be triggered repeatedly and affects all nodes that receive/relay/validate the transaction — a state-divergence/liveness risk to the network rather than a "resource-only" issue, since a crashed validating node stops producing/validating blocks.

### Likelihood Explanation
Likelihood is high for any attacker capable of submitting a transaction: constructing nested RLP `AccountKeyRoleBased` bytes requires no special privilege, no valid signature verification is needed before decode occurs (RLP decoding of the tx body happens prior to/along with signature/pool validation), and the vulnerable code path (`DecodeRLP`) is unconditionally exercised whenever an `AccountUpdate`-type transaction with a `RoleBased` key type field is decoded, including during raw-tx submission and block/tx-pool relaying.

### Recommendation
Add an explicit recursion-depth (or total-size) limit inside `AccountKeyRoleBased.DecodeRLP` (and more generally in `AccountKeySerializer.DecodeRLP`), rejecting a `RoleBased` key type nested inside another `RoleBased` key type *during decode* rather than only after decode completes in `CheckInstallable`/`CheckUpdatable`. This can be done by threading a depth counter/context through decoding, or by pre-scanning the type byte before recursing when the type equals `AccountKeyTypeRoleBased` inside an already-`RoleBased` context, returning `kerrors.ErrNestedCompositeType` immediately instead of recursively decoding it.

### Proof of Concept
Construct nested `AccountKeyRoleBased` values with the existing test helper pattern (which currently nests only one level for the negative test) and increase the nesting depth to thousands of levels, e.g. extending: [7](#0-6) 
by repeatedly wrapping: `NewAccountKeyRoleBasedWithValues([]AccountKey{ prevRoleBasedKey })` many times, then RLP-encode via `AccountKeySerializer.EncodeRLP` and feed the resulting bytes to `rlp.DecodeBytes(data, &accountkey.AccountKeySerializer{})` (the same call used by `KaiaAPI.DecodeAccountKey` and internally by transaction decoding) to trigger unbounded recursion and stack exhaustion before any `CheckInstallable`/`ErrNestedCompositeType` check can run.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (a *AccountKeyRoleBased) CheckUpdatable(newKey AccountKey, currentBlockNumber uint64) error {
	if newKey, ok := newKey.(*AccountKeyRoleBased); ok {
		lenOldKey := len(*a)
		lenNewKey := len(*newKey)
		// If no key is to be replaced, it is regarded as a fail.
		if lenNewKey == 0 {
			return kerrors.ErrZeroLength
		}
		// Do not allow undefined roles.
		if lenNewKey > (int)(RoleLast) {
			return kerrors.ErrLengthTooLong
		}
		for i := range lenNewKey {
			switch {
			// A composite key is not allowed.
			case (*newKey)[i].IsCompositeType():
				return kerrors.ErrNestedCompositeType
			// If newKey is longer than oldKey, init the new attributes.
			case i >= lenOldKey:
				if err := (*newKey)[i].CheckInstallable(currentBlockNumber); err != nil {
					return err
				}
			// Do nothing for AccountKeyTypeNil
			case (*newKey)[i].Type() == AccountKeyTypeNil:

			// Check whether the newKey is replacable or not
			default:
				if err := CheckReplacable((*a)[i], (*newKey)[i], currentBlockNumber); err != nil {
					return err
				}
			}
		}
		return nil
	}
	// Update is not possible if the type is different.
	return kerrors.ErrDifferentAccountKeyType
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
