## Confirmed: No containment check exists

`saveGitIgnore` builds the destination path and writes to it with no `lstat`/`realpath` verification: [1](#0-0) 

Compare this to the containment-checking utility that already exists elsewhere in the codebase (`resolveWithin`, which explicitly calls `realpath` on both root and resolved path and rejects anything that escapes root): [2](#0-1) 

`gitignore.ts` does not use `resolveWithin`/`resolveWithinPosix` or any `fs.lstat` call before `readGitIgnoreAtRoot`'s `FS.readFile` or `saveGitIgnore`'s `writeFile`/`FS.unlink`, so both operations transparently follow symlinks.

### Title
Symlinked `.gitignore` in a malicious repository allows write outside the working tree via `saveGitIgnore` - (File: `app/src/lib/git/gitignore.ts`)

### Summary
`saveGitIgnore` resolves the .gitignore path as `Path.join(repository.path, '.gitignore')` and passes it directly to `fs/promises.writeFile` (and `FS.unlink` for the empty-text case) without any `lstat`/`realpath` check to ensure the resolved file is a real, non-symlinked path inside `repository.path`.

### Finding Description
The filename segment (`'.gitignore'`) is fixed, so there's no traditional path-traversal via a crafted string. The exposure instead comes from the working tree content itself: git checks out symlinks verbatim on macOS/Linux (assuming `core.symlinks` is enabled, the default). A malicious repository can therefore contain a tracked symlink at path `.gitignore` pointing to an arbitrary absolute path outside the repository (e.g., `~/.bashrc`, `~/.ssh/authorized_keys`, or another project's file). When the victim clones/fetches this repository, `Path.join(repository.path, '.gitignore')` still resolves lexically inside `repository.path`, but the filesystem-level target that `writeFile`/`FS.unlink` actually touches is whatever the symlink points to, because Node's `fs` calls follow symlinks by default and no `lstat` is performed first to detect/reject this. This breaks the working-tree containment invariant: writes intended for the repo root can land anywhere the OS user has write permission.

`saveGitIgnore` is reached through normal, expected user actions: [3](#0-2) 
- Editing ignored files in Repository Settings (`app/src/ui/repository-settings/repository-settings.tsx`)
- Right-clicking a changed file in the Changes list and choosing "Ignore file" / "Ignore file (all `.ext`)" (`app/src/ui/changes/sidebar.tsx`, routed through `dispatcher.ts` → `appendIgnoreFile`/`appendIgnoreRule` → `saveGitIgnore`)

### Impact Explanation
An attacker who controls repository content can pre-plant a symlinked `.gitignore` so that a completely ordinary user action (viewing repo settings' ignore list, or ignoring any single changed file) causes GitHub Desktop to write (or delete, in the empty-text branch) an out-of-repo file the OS user can write to. This is a file-write-outside-the-repo primitive stemming from attacker-controlled cloned repository content, matching the in-scope impact category.

### Likelihood Explanation
Requires: (1) victim clones/fetches the malicious repo, (2) the target filesystem/OS honors the symlink on checkout (true by default on macOS/Linux; Windows without symlink privileges typically materializes it as a plain text placeholder instead, reducing risk there), and (3) the victim performs a very common, natural action — opening Repository Settings' "Ignored Files" tab or using the standard "Ignore file" context-menu entry. No unnatural steps are required beyond normal repository interaction.

### Recommendation
Before `readGitIgnoreAtRoot`'s read and `saveGitIgnore`'s write/unlink, `lstat` the target path (or use the existing `resolveWithin`/`resolveWithinPosix` helper in `app/src/lib/path.ts`) and refuse to operate if the path is a symlink or resolves outside `repository.path`.

### Proof of Concept
1. Create a repository where `.gitignore` is a symlink to `../../.bashrc` (or any file outside the clone directory), committed as a tracked symlink.
2. Victim clones the repository on macOS/Linux with default `core.symlinks=true`; the checkout materializes `.gitignore` as a real symlink pointing outside the repo.
3. Victim opens Repository Settings → Ignored Files (or right-clicks any changed file and selects "Ignore file").
4. `saveGitIgnore` calls `writeFile(ignorePath, fileContents)` where `ignorePath` still lexically resolves under `repository.path`, but the OS follows the symlink and writes into the attacker-chosen target file outside the repository — confirmed by inspecting `app/src/lib/git/gitignore.ts:40-60` and the absence of any `lstat`/`resolveWithin` guard compared to `app/src/lib/path.ts:36-72`.

export async function saveGitIgnore(
  repository: Repository,
  text: string
): Promise<void> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  if (text === '') {
    return new Promise<void>((resolve, reject) => {
      FS.unlink(ignorePath, err => {
        if (err) {
          reject(err)
        } else {
          resolve()
        }
      })
    })
  }

  const fileContents = await formatGitIgnoreContents(text, repository)
  await writeFile(ignorePath, fileContents)
}
```

/** Add the given pattern or patterns to the root gitignore file */
export async function appendIgnoreRule(
  repository: Repository,
  patterns: string | string[]
): Promise<void> {
  const text = (await readGitIgnoreAtRoot(repository)) || ''

  const currentContents = await formatGitIgnoreContents(text, repository)

  const newPatternText =
    patterns instanceof Array ? patterns.join('\n') : patterns
  const newText = await formatGitIgnoreContents(
    `${currentContents}${newPatternText}`,
    repository
  )

  await saveGitIgnore(repository, newText)
}
```
