### Title
CR-CAT recipients whose Verified Credential is revoked (or who never possess an authorized VC) permanently lose access to CR-CAT funds sent to them, with no path to redirect payment to a different address - (File: `chia/wallet/vc_wallet/cr_cat_drivers.py`, `chia/wallet/vc_wallet/cr_cat_wallet.py`)

### Summary
Credential-Restricted CATs (CR-CATs) are Chia's analog of tokens with "blacklist"/permissioned-transfer functionality (e.g. USDC). Just like the reported LooksRare bug where a blacklisted USDC winner can never claim rewards, a CR-CAT payment sent to a recipient is locked to that recipient's specific `inner_puzzle_hash` via `construct_pending_approval_state()`, and can only be released by that same recipient presenting a valid Verified Credential (VC) from an `authorized_providers` list. If the provider revokes that VC (the on-chain "blacklist" mechanism, `VerifiedCredential.activate_backdoor` / `vc_revoke`) — or the recipient simply never obtains one — the CR-CAT funds already committed to them become permanently frozen, with no built-in mechanism to redirect the coin to a different, still-authorized address.

### Finding Description
CR-CATs gate all transfers behind a `CREDENTIAL_RESTRICTION` puzzle layer curried with `authorized_providers` and a `proofs_checker`, constructed in `construct_cr_layer()`: [1](#0-0) 

When a payment's recipient is not a wallet with a known VC of its own, the wallet wraps the destination in a "pending approval" state that is permanently keyed to the recipient's original `puzzle_hash`: [2](#0-1) 

Releasing coins out of this pending state requires the *specific* recipient to hold a VC matching the CR-CAT's `authorized_providers`/`proofs_checker`; `claim_pending_approval_balance` fails outright if no such VC exists: [3](#0-2) 

VCs are themselves revocable at any time by the `proof_provider` (the DID acting as credential issuer) via a "backdoor" spend path — functionally identical to a blacklist: [4](#0-3) [5](#0-4) 

Because `construct_pending_approval_state` bakes the target `puzzle_hash` directly into the puzzle used to lock the coin, and `claim_pending_approval_balance`/`generate_signed_transaction` for `CRCATWallet` always re-derive that same `inner_puzhash` from wallet metadata (not an alternate address), there is no supported path in the wallet code for the affected recipient — or anyone else — to redirect a stuck pending CR-CAT balance to a different, still-VC-authorized puzzle hash: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any CR-CAT balance (including offer settlement proceeds routed through `check_for_requested_payment_modifications` in `trade_manager.py`, which wraps CR-CAT requested payments in the pending-approval state) sent to a recipient becomes irrecoverable once that recipient's VC is revoked by the issuer or if the recipient never manages to obtain an authorized VC that satisfies the `proofs_checker` flags. This is a direct, on-chain-permanent loss of funds for a legitimate counterparty in an offer/trade — matching the "funds frozen forever" impact class from the reference report, not merely a resource/availability issue. [8](#0-7) 

### Likelihood Explanation
This requires no attacker action beyond normal, permitted protocol use: any wallet user offering/paying CR-CATs to a counterparty, combined with the CR-CAT issuer/provider later revoking that counterparty's VC (a supported, documented feature of the credential system) or the counterparty simply lacking a valid VC at claim time. Both revocation and pending-approval routing are first-class, reachable wallet/RPC flows (`vc_revoke`, `crcat_approve_pending`, offer-taking with CR-CAT driver checks), so likelihood is not purely theoretical — it is an inherent structural gap in the CR-CAT/VC design rather than a rare edge case.

### Recommendation
Provide a supported recovery path for CR-CAT coins stuck in the pending-approval state, analogous to the LooksRare fix recommendation: allow the coin's true owner (or the CR-CAT wallet on their behalf) to redirect a pending-approval CR-CAT to a different destination puzzle hash once authorized by *any* currently-valid VC they control, rather than hard-locking the pending puzzle to the original `puzzle_hash` forever. At minimum, document and/or add tooling so that CR-CAT senders/recipients understand that revocation of the target's VC can permanently freeze already-sent funds, and consider adding a puzzle-level escape hatch (e.g., an alternate authorized-provider override or a timeout-based reclaim by the original sender) for this scenario.

### Proof of Concept
1. Provider (DID) mints/authorizes a VC for Alice's puzzle hash; Alice's wallet is set up as a `CRCATWallet` requiring that provider in `authorized_providers`.
2. Bob (offer counterparty) creates/accepts a trade sending CR-CAT funds to Alice. Because trade_manager routes CR-CAT requested payments through `construct_pending_approval_state(payment.puzzle_hash, ...)`, Alice's incoming CR-CAT coin is locked into the pending-approval puzzle keyed to her `puzzle_hash`. [9](#0-8) 
3. Before Alice calls `crcat_approve_pending` (RPC → `claim_pending_approval_balance`), the provider revokes Alice's VC via `vc_revoke`/`activate_backdoor`. [10](#0-9) 
4. Alice (or anyone) now calls `crcat_approve_pending`; `claim_pending_approval_balance` cannot find any VC matching `authorized_providers`/`proofs_checker` and raises `RuntimeError`, permanently preventing the pending CR-CAT coin from ever leaving the pending-approval puzzle hash. [11](#0-10) 
5. No other code path exists to move the coin to a new destination, so the funds are frozen forever — the same end state described in the reference USDC-blacklist report.

def construct_cr_layer(
    authorized_providers: list[bytes32],
    proofs_checker: Program,
    inner_puzzle: Program,
) -> Program:
    first_curry: Program = CREDENTIAL_RESTRICTION.curry(
        CREDENTIAL_STRUCT,
        authorized_providers,
        proofs_checker,
    )
    return first_curry.curry(first_curry.get_tree_hash(), inner_puzzle)

    async def vc_revoke(
        self,
        request: VCRevoke,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> VCRevokeResponse:
        """
        Revoke an on chain VC provided the correct DID is available
        :param request: required 'vc_parent_id' for the VC coin. Standard transaction params 'fee' & 'reuse_puzhash'.
        :return: a list of all relevant 'transactions' (TransactionRecord) that this spend generates (VC TX + fee TX)

        vc_wallet: VCWallet = await self.service.wallet_state_manager.get_or_create_vc_wallet()

        await vc_wallet.revoke_vc(
            request.vc_parent_id,
            self.service.get_full_node_peer(),
            action_scope,
            request.fee,
            extra_conditions=extra_conditions,
        )

        return VCRevokeResponse(unsigned_transactions=[], transactions=[])  # tx_endpoint takes care of filling this out
