### Title
`Interpolation::Constant` panics on participant index 0, enabling remote denial of service during signing - (File: crypto/dkg/src/lib.rs)

### Summary
The FROST signing path validates that every included `Participant` is `<= n`, but never enforces the documented lower bound `0 < participant`. A `Participant(0)` admitted into the signing set causes `Interpolation::interpolation_factor` to compute `u16::from(i) - 1`, i.e. `0 - 1`, which panics (underflow in debug builds, wrap to 65535 followed by an out-of-bounds vector index in release builds). Either way the signing process crashes. This is a direct analog of the CVE-2016-9819 bug class: undefined/invalid arithmetic on attacker-influenced values producing a crash.

### Finding Description
`FrostError::InvalidParticipant` documents the invariant `0 < participant <= n` at `crypto/frost/src/lib.rs:32`. However, `AlgorithmSignMachine::sign` in `crypto/frost/src/sign.rs` only checks the upper bound:

- `sign.rs:302-304`: `if u16::from(included[included.len() - 1]) > multisig_params.n()` — since `included` is sorted ascending at `sign.rs:295`, `Participant(0)` sorts first and evades this check entirely.
- `sign.rs:312`: `self.params.keys.view(included.clone()).unwrap()` — the `included` set containing 0 flows into `ThresholdView` construction.
- `crypto/dkg/src/lib.rs:228`: `Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)]` — for `i == 0` this computes `0 - 1`. In debug builds `u16` subtraction underflows and panics; in release builds it wraps to `65535`, and `c[65535]` panics on the out-of-bounds index (the coefficient vector has `n` entries).

`Interpolation::Constant` is used for keys produced via promotion/recovery flows (`crypto/dkg` promote/dealer paths), where each participant's share carries a constant coefficient vector indexed by `i - 1`. Signed messages and signing sets in these flows are reachable by participants in the threshold protocol.

### Impact Explanation
A single `Participant(0)` appearing in the signing set crashes every honest signer that calls `sign()` on those preprocesses, aborting the signing session (denial of service of the threshold signing operation), exactly the crash-impact class of CVE-2016-9819. The panic occurs before any share is produced, so no key material leaks; the impact is availability of the signing protocol.

### Likelihood Explanation
The `preprocesses: HashMap<Participant, Preprocess>` keys are assigned externally by the message-collection layer rather than read from attacker bytes directly, so reaching `Participant(0)` requires the routing/mapping layer to admit a zero index — `Participant` is a thin `u16` newtype and nothing in `frost` itself rejects 0 at parse or sign time (the enum explicitly anticipates "0 < participant" violations). The bug is a missing validation against a documented invariant; any caller that accepts participant indices from the wire without its own `>= 1` check exposes the panic.

### Recommendation
Enforce the documented invariant in `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs`, after the `included` sort): reject `included[0] == Participant(0)` — or more generally `u16::from(included[0]) < 1` — with `FrostError::InvalidParticipant`. Additionally, make `Participant`'s constructor/deserialization reject 0 at the `dkg` crate boundary, and use `checked_sub(1)`/`get(i-1)` in `Interpolation::Constant`'s indexing as defense in depth.

### Proof of Concept
```rust
// crypto/frost: with keys using Interpolation::Constant (promoted keys),
// and a SignMachine for participant i = 1:

let mut preprocesses = HashMap::new();
// A zero-indexed entry admitted into the signing set:
preprocesses.insert(Participant::try_from(0u16).unwrap(), malicious_preprocess);
// plus enough valid preprocesses to reach threshold t...

// included = [0, 1, ...]; sort puts 0 first.
// sign.rs:302 only rejects included.last() > n, so 0 passes.
// sign.rs:312 -> ThresholdView::new -> interpolation_factor(0, included)
// dkg/src/lib.rs:228: c[u16::from(0) - 1] -> panic (underflow / OOB index)
let _ = sign_machine.sign(preprocesses, msg); // thread panic, DoS
```

The panic site is `crypto/dkg/src/lib.rs:228` (`u16::from(i) - 1`), reached because the sole bound check at `crypto/frost/src/sign.rs:302` tests only the maximum element of the sorted `included` vector.
