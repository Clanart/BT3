## Title
Stale index-based diff selection can silently commit unintended content when the working-tree diff shifts between selection and patch generation - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/models/diff/diff-selection.ts`)

### Summary
`DiffSelection` tracks which lines a user wants to commit purely by **absolute numeric index** into a unified diff, not by line content or identity. When the working-directory diff is recomputed after the user made their selection (which happens routinely, and can be forced by attacker-controlled content in a fetched repository), the same indices can now point at completely different lines. The commit path (`applyPatchToIndex` → `formatPatch`) re-fetches the diff independently right before building the patch and blindly applies the old index-based selection to the new diff, so the resulting patch can silently include or exclude content the user never actually reviewed/selected.

### Finding Description
The selection model deliberately has "no notion of how many lines exist or what it is that is being selected" and only stores line *indices*: [1](#0-0) 

The application itself acknowledges the invariant is fragile. In `updateChangesWorkingDirectoryDiff`, after reloading the diff for the currently selected file, the comment explicitly states the reconciliation is incomplete: [2](#0-1) 

It only prunes indices that are no longer selectable at all - it never verifies that an index which *remains* selectable still refers to the same diff line/content it did when the user made the selection.

The real breakage happens at commit time. `stageFiles` calls `applyPatchToIndex` for every partially-selected file: [3](#0-2) 

`applyPatchToIndex` fetches a **brand new** diff of the working directory (independent of whatever diff was rendered/selected against in the UI) and hands it, together with the *old* `file.selection`, straight to `formatPatch`: [4](#0-3) 

`formatPatch` then walks the *new* diff's hunks and, for each line, calls `file.selection.isSelected(absoluteIndex)` using indices that were computed against the *old* diff: [5](#0-4) 

If the working-tree file's diff shape changes between the moment the user picked which lines to include and the moment `applyPatchToIndex` re-diffs the file (e.g. line count grows/shrinks due to a git clean/smudge filter, a `.gitattributes`-driven text transform, an eol/whitespace normalization pass, or any process that rewrites the tracked file), the index numbers no longer correspond to the same content. `isSelected(absoluteIndex)` will then mark different lines as "selected" than the user intended - possibly including attacker-authored content the user explicitly deselected, or dropping content the user meant to commit - and `git apply --cached` will write that mismatched patch straight into the index.

### Impact Explanation
This breaks the invariant "the commit contains exactly the lines the user selected in the diff view," which is the security-relevant integrity guarantee GitHub Desktop makes for partial/line-level staging. Since a repository under attacker control can define content-rewriting mechanics (e.g., filters declared in `.gitattributes`) or otherwise cause the tracked file to be rewritten between the two diff computations, this becomes a path for **silent corruption of what the user commits and subsequently pushes** - the user reviews and deselects malicious lines in the Changes view, but the actual committed/pushed content can differ from what was shown and approved, without any error or warning surfaced to the user.

### Likelihood Explanation
The window is real but narrow: it requires the diff of the specific staged file to change shape (hunk/line count) between the UI's diff load and Desktop's second, independent diff fetch during staging. This can be triggered by repository-declared file filters/normalization or a background process touching the file while Desktop is mid-commit - it does not require local/admin access, prior malware, or leaked credentials, only an attacker-controlled repository whose content or filter behavior can shift diff line indices at an opportune moment. Because Desktop performs no re-validation of selection content (only of selectability) before applying the patch, there is no existing guard that would catch or block the mismatch.

### Recommendation
- Re-validate (or re-derive) the user's line selection against the diff that is actually used to build the patch in `applyPatchToIndex`, rather than trusting index-based selection computed against a possibly stale diff.
- Prefer content-anchored selection (e.g., hashing/line-content fingerprints) over pure numeric indices, or abort/re-prompt the user if the working-directory diff has materially changed since the selection was captured.
- Fail the commit (rather than silently proceeding) when the diff used for patch generation differs from the diff the selection was computed against.

### Proof of Concept
1. Clone/create a repository containing a tracked text file and a `.gitattributes` filter (or any workflow tool) that measurably changes the file's line count when the file is touched/read.
2. In Desktop, open the file's diff and deselect a specific set of lines (e.g., lines added by the "attacker") via `DiffSelection`, leaving other lines selected.
3. Before Desktop finalizes the commit, trigger the filter/process so the working-tree file's diff shape shifts (insert/remove lines) - this happens naturally through git's own clean/smudge machinery on repositories that declare such filters.
4. Commit. `applyPatchToIndex` (`app/src/lib/git/apply.ts`) re-diffs the file and `formatPatch` (`app/src/lib/patch-formatter.ts`) applies the stale index-based selection against the new hunk layout.
5. Inspect the resulting commit: it contains lines the user never selected (or omits lines the user did select), demonstrating silent corruption of the committed content relative to what was reviewed in the UI.
