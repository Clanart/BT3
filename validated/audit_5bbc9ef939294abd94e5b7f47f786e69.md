### Title
Unbounded Python-side quadratic-scan DoS when processing an untrusted offer's coin/announcement dependency graph in `Offer.get_cancellation_coins()` - (File: chia/wallet/trading/offer.py)

### Summary
CVE-2023-21920 is a MySQL "optimizer" bug class: attacker-supplied input drives the query planner into a pathological, disproportionately expensive execution path relative to the resources the attacker actually spent, causing a hang/crash (availability DoS) without any privilege beyond issuing a query. The reachable Chia analog is in wallet-side offer processing: `Offer.get_cancellation_coins()` (and its helper `detect_dependent_coin()`) walks a coin/announcement dependency structure built entirely from the coin spends embedded in an offer file. This computation runs in pure Python, outside of any CLVM cost metering, and its cost is driven only by the *shape* (number of coins and cross-announcement dependencies) of the untrusted offer's spend bundle, not by any consensus-priced resource an attacker has to pay for.

### Finding Description
`Offer.get_cancellation_coins()` builds, for every non-addition coin spend in the offer bundle, a `dependencies` map (coins pointed to by `ASSERT_COIN_ANNOUNCEMENT`, opcode 61) and an `announcements` map (messages created by `CREATE_COIN_ANNOUNCEMENT`, opcode 60): [1](#0-0) 

It then repeatedly calls `detect_dependent_coin()`, which for every outer loop iteration scans **all coin names × all of that coin's dependencies × all coins' announcement lists** (triple nested loop) to find one dependent coin to remove, then loops again over the *entire remaining* `dependencies`/`announcements` maps to propagate the removal: [2](#0-1) [3](#0-2) 

Each call to `detect_dependent_coin()` costs `O(N × D × C)` (names × per-coin deps × all coins' announcement lists), and it is called once per removal in an outer `while True` loop, and the propagation inner `while True` loop again rescans every remaining coin's dependency set against a shrinking `removed_announcements` list. With `N` coins each declaring multiple `ASSERT_COIN_ANNOUNCEMENT`/`CREATE_COIN_ANNOUNCEMENT` conditions (up to the per-spend condition count that CLVM cost can afford), the overall algorithmic complexity is quadratic-to-worse in the number of coins/conditions in the offer, and this cost is paid entirely on the Python side of the *receiving* wallet — it is not gated by `MAX_BLOCK_COST_CLVM`, `max_tx_clvm_cost`, or any of the mempool duration/atom/pair guards described in `mempool_manager.py`'s `pre_validate_spendbundle()` (`validation_timeout`, `ns/cost` timeout, atom/pair bounds).

This is structurally analogous to the MySQL optimizer bug: a low-privileged actor (an offer counterparty who crafts and sends an `.offer` file, or a peer who lists such an offer that a user's wallet later inspects/cancels) submits input that is cheap for them to construct but disproportionately expensive for the receiving node to process, because the vulnerable code path is not priced by the same cost model that governs the rest of consensus-facing input.

### Impact Explanation
A wallet operator who receives or imports a maliciously crafted offer (e.g., via `take_offer`/`get_offer_summary`/cancel-offer flows in `trade_manager.py`, which calls `get_cancellation_coins()`) can have their wallet process hang or become unresponsive for an extended period while performing this quadratic/super-linear scan, since it is unbounded pure-Python work with no cost ceiling, timeout, or size cap on the number of coins/announcements in an offer. This is a local availability impact on the wallet process, matching the CVSS profile of the source CVE (`C:N/I:N/A:H`) — no confidentiality or integrity impact, but a transaction/offer-processing hang triggered by attacker-supplied (offer) input.

### Likelihood Explanation
Likelihood is moderate: constructing an offer with many coin spends and many announcement conditions requires paying for the corresponding puzzle-reveal/solution size and (if actually pushed on-chain) CLVM execution cost, but `get_cancellation_coins()` operates on `self._bundle.coin_spends` directly from a *received, not-yet-validated-on-chain* offer object — a counterparty can hand a wallet user an offer file with a large but not consensus-invalid conditions set purely to trigger this local processing path, without ever needing it to be admitted to the mempool at all (offers are exchanged off-chain before being taken/pushed).

### Recommendation
Bound the work done in `detect_dependent_coin()`/`get_cancellation_coins()`: cap the number of coins/announcements considered, replace the linear announcement-dict scan with a reverse index (`announcement_msg -> coin`) built once in `O(N)`, and add an explicit iteration/size limit (or wall-clock guard, consistent with the `validation_timeout` pattern already used in `mempool_manager.py`) before this Python-only computation is allowed to run against attacker-supplied offer data.

### Proof of Concept
1. Craft an `Offer` object (not necessarily broadcastable/spendable on-chain, just constructible as a `WalletSpendBundle`) containing `N` coin spends, each with several `CREATE_COIN_ANNOUNCEMENT` and `ASSERT_COIN_ANNOUNCEMENT` conditions forming a long dependency chain/dense cross-reference graph among the coins (e.g., coin `i` asserts an announcement created by coin `i+1`, and vice versa in overlapping cycles).
2. Send this offer file to a victim wallet (as one normally shares `.offer` files) or otherwise get it loaded via `TradeManager`.
3. Trigger `Offer.get_cancellation_coins()` (reachable from `trade_manager.py`, e.g. during offer cancellation/inspection flow) with `N` scaled up (hundreds to low thousands of coins/announcements, within CLVM byte/cost limits for constructing the puzzle reveals).
4. Observe wall-clock time of the wallet's RPC call scale super-linearly with `N`, hanging the wallet's processing of that call while it repeatedly rescans the full dependency/announcement maps in `detect_dependent_coin()`. [4](#0-3)

def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
