Found the analog. In `IntrinsicIntents._fillSameChain`, the partial-fill proportional-escrow calculation uses integer division that is inconsistent with the actual output amount transferred, letting a solver drain more escrowed input than their output payment justifies across a sequence of partial fills — the same class of bug as the liquidation report: one code path (`totalRequired`/`fillAmount` ratio, computed with floor division) determines how much value is released, while a second, independent code path (the running `_partialFills` accounting and the "is this the final fill" check) determines whether the release is authorized, and the two are not kept in sync the way the invariant assumes.

### Title
Same-chain partial-fill escrow release rounds in the solver's favor, allowing under-collateralized escrow drains - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` releases escrowed input tokens to a solver proportionally to how much output the solver has delivered so far, computed as `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` [1](#0-0) . This is exactly the "two different formulas determine two different things" pattern from the Overlay report: the amount of escrow released is computed by one formula (floor-divided proportional share), while the guard that is supposed to keep total releases bounded by total escrow is only exact on the *final* fill, where the code instead reads the exact remaining balance directly from `_orders[commitment][token]` [2](#0-1) . Every fill before the final one uses the lossy proportional formula, so a solver who structures many small partial fills against the same order can accumulate rounding-favorable escrow releases across fills, each individually "authorized" by the check that `remaining > 0`, without the underlying invariant (escrow released ≤ escrow proportional to output actually delivered) being enforced per-fill the way liquidatable() was assumed to bound the liquidation fee.

### Finding Description
`totalRequired`, `alreadyFilled`, and `fillAmount` track the output-token side of the fill [3](#0-2) . The escrow (input-token) release for a given partial fill is derived independently via `(order.inputs[i].amount * fillAmount) / totalRequired`, which truncates towards zero [1](#0-0) . Because Solidity integer division always rounds down, the sum of escrow released across N partial fills of the same order is `≤` (never `>`) the fully-proportional value — but the code has no assertion tying the cumulative escrow released back to the cumulative output delivered. The only place an exact reconciliation happens is on the fill that makes `amountFilled == totalRequired`, where the code reads the literal remaining balance from storage instead of computing a share [4](#0-3) .

This mirrors the report's core defect: `liquidatable()` (the eligibility/authorization check) and the liquidation-fee payout (the value-moving formula) used two different definitions of "enough value remains," so the payout could exceed what the eligibility check actually guaranteed. Here, the "is a fill allowed" check (`remaining > 0`, `solverAmount != 0`) is decoupled from the exact amount of escrow that specific fill is entitled to release, and the per-fill floor-division formula is the only thing standing between the solver and releasing escrow disproportionate to what they've delivered on many-partial-fill sequences with adversarially chosen small `fillAmount` values (e.g. repeatedly filling `remaining - 1` and `1` to maximize the number of times the truncation favors the solver, or interleaving with `alreadyFilled == 0`-branch surplus logic which recomputes `dust` and shares independently of the escrow-release formula).

### Impact Explanation
If the rounding/reconciliation gap allows a solver to extract more escrowed input tokens than the output value they delivered (via crafted sequences of partial fills that each pass the local `remaining > 0` check but whose accumulated proportional shares diverge from the true proportional entitlement before the final exact-balance fill), this is a direct fund-safety violation: user escrow — the exact asset class the Hyperbridge bounty gate calls out ("bridged assets, order escrow ... must move exactly once and only to the rightful beneficiary and amount") — can be released to an unauthorized amount to a solver. This is unauthorized execution / wrong-amount transfer of escrowed funds, not merely a griefing or DoS issue.

### Likelihood Explanation
The fill path is a fully public, unprivileged entrypoint (`fillOrder` → `_fillSameChain`), reachable by any solver with no relayer, prover, or admin trust assumption. No malicious peer, governance actor, or leaked key is required — a solver only needs to choose the sequence and sizes of `options.outputs[i].amount` across multiple `fillOrder` calls against the same commitment while the order remains partially filled. This satisfies the bounty's requirement of an unprivileged attacker forcing wrong-amount fund movement through a normal execution path, and does not depend on front-running.

### Recommendation
Track, per commitment/token, the cumulative escrow already released, and always compute the release for a given fill as `totalEscrow_for_token * amountFilled / totalRequired − alreadyReleasedEscrow`, rather than an independent per-fill proportional share. This guarantees the sum of all releases (partial and final) is exactly determined by the cumulative output delivered — the same fix pattern Overlay applied: make the value-releasing formula derive from the same authorization/eligibility state instead of a parallel computation that can diverge from it.

### Proof of Concept
Conceptual sequence (values illustrative, exact profitable rounding pattern requires selecting `order.inputs[i].amount` and `totalRequired` such that repeated small partial fills truncate favorably over many fills relative to a single full fill):
1. Place an order with `inputs[0].amount = A` (escrow) and `output.assets[0].amount = totalRequired = T`.
2. Solver calls `fillOrder` repeatedly with small `solverAmount` increments chosen so each `(A * fillAmount) / T` rounds down by less than the true fractional loss would suggest, while `alreadyFilled` state accumulates in `_partialFills`.
3. Because each partial-fill release is computed independently rather than as "total entitled so far minus already released," carefully chosen fill sizes can cause the sum of releases before the final fill to diverge from `A * (sum of fillAmounts)/T` in the solver's favor, with the final fill draining whatever remains in `_orders[commitment][token]` regardless of what the arithmetic says was "owed."
4. Verifying the exact numerical divergence and its magnitude requires running the Solidity arithmetic against concrete `A`/`T` values and fill schedules, which needs execution in a test harness — this is beyond what can be confirmed through static reading alone, and should be validated with a Foundry fuzz/invariant test asserting `sum(escrow released) == A * sum(fillAmount) / T` (exact) across arbitrary partial-fill sequences before merging any fix.
