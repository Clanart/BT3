I found a valid analog: `MultiSender.sol`, which reproduces the exact bug class from the report — a `payable` function that accepts native token in excess of what's strictly required for the operation, with no refund mechanism, permanently trapping the surplus.

### Title
Excess native token sent to `MultiSender` batch-transfer functions is permanently stuck with no refund path - ([File: contracts/src/MultiSender.sol])

### Summary
`MultiSender.batchTransferEqualAmount()` and `MultiSender.batchTransfer()` are `payable` functions that only `require(msg.value >= totalAmount, ...)` — a greater-than-or-equal check — rather than requiring an exact match, and they never return, forward, or account for the difference between `msg.value` and `totalAmount`. Any native token sent above the exact required amount stays trapped in the contract balance indefinitely, matching the reported `BreederTimeLockPool.crossChainClaimReward()` pattern of accepting more native token than needed and providing no refund mechanism.

### Finding Description
Both payable entry points compute the exact amount needed to fulfill the batch send (`totalAmount`), then only assert `msg.value` is *sufficient*, not *exact*: [1](#0-0) [2](#0-1) 

After the `require` check, the functions loop and `send()` exactly `amount`/`amounts[i]` to each recipient — never touching or returning any `msg.value` surplus. The contract holds no `withdraw()`, `receive()`-forwarding, or refund logic of any kind, so `msg.value - totalAmount` accumulates as native token balance owned by the `MultiSender` contract with no function capable of extracting it. This is structurally identical to the reported bug: a function that computes a required amount from user-controlled/external inputs, accepts `msg.value` that may exceed that requirement, and has no path to return the difference.

### Impact Explanation
Any user who miscalculates or intentionally overpays `msg.value` when calling `batchTransferEqualAmount` or `batchTransfer` permanently loses the excess amount — it becomes unrecoverable native token, permanently frozen in the contract with no owner, admin, or user-facing withdrawal function. This is a direct, concrete loss of user funds satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood is user-driven but plausible: because the check is `>=` instead of `==`, any wallet/UI that pads gas/value estimates, or any user who provides a slightly-too-large `msg.value` (e.g. rounding, buffer for future recipients, or copy-paste from a different call), silently overpays with no error and no recovery, unlike an exact-match `require` which would at least surface the mistake via a revert.

### Recommendation
Change the `require` to an exact-match check (`msg.value == totalAmount`) so any mismatch reverts loudly, or alternatively add explicit refund logic that returns `msg.value - totalAmount` to `msg.sender` at the end of each function before completing execution.

### Proof of Concept
1. Deploy `MultiSender`.
2. Call `batchTransferEqualAmount([recipientA, recipientB], amount)` with `msg.value = 2*amount + 1 wei` (or any value strictly greater than `totalAmount`).
3. The `require(msg.value >= totalAmount, ...)` check passes; the loop sends exactly `amount` to each of the two recipients.
4. The leftover `1 wei` (or any larger surplus) remains in the `MultiSender` contract's balance.
5. Inspect the contract's native balance post-call: it holds the surplus permanently since no function in the contract can move it out.

  function batchTransferEqualAmount(
    address[] calldata recipients,
    uint256 amount
  ) external payable {
    uint256 totalAmount = amount * recipients.length;
    require(msg.value >= totalAmount, "Insufficient amount sent");

    for (uint256 i = 0; i < recipients.length; i++) {
      bool success = payable(recipients[i]).send(amount);
      require(success, "Failed to send Ether");
      emit SendSuccessful(msg.sender, recipients[i], amount);
    }
  }

  function batchTransfer(
    address[] calldata recipients,
    uint256[] calldata amounts
  ) external payable {
    require(
      recipients.length == amounts.length,
      "Recipients and amounts do not match"
    );
    uint256 totalAmount = 0;
    for (uint256 i = 0; i < amounts.length; i++) {
      totalAmount += amounts[i];
    }

    require(msg.value >= totalAmount, "Insufficient amount sent");

    for (uint256 i = 0; i < recipients.length; i++) {
      bool success = payable(recipients[i]).send(amounts[i]);
      require(success, "Failed to send Ether");
      emit SendSuccessful(msg.sender, recipients[i], amounts[i]);
    }
  }
}
