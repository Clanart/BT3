### Title
`SinglePlusAnyoneCanPay` in `create_payout_txhandler` leaves the anchor amount and OP_RETURN operator pubkey unsigned, allowing a payout-attribution race - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` signs the Payout transaction's single withdrawal input with `TapSighashType::SinglePlusAnyoneCanPay`, which under BIP341 only commits to input 0 and output 0 (the user payout). The anchor output (`NON_EPHEMERAL_ANCHOR_AMOUNT`) and the OP_RETURN output carrying `operator_xonly_pk` are unsigned and can be freely rewritten by anyone holding the same user signature, as long as no other input in the final broadcast tx is signed with a full-coverage sighash (e.g. `SIGHASH_ALL`) tying down the whole transaction.

### Finding Description
The broken binding: `withdrawals.payout_payer_operator_xonly_pk` (written in `update_finalized_payouts`, [1](#0-0) ) is claimed to equal the operator that actually funded output 0 of the confirmed Payout tx. In reality it equals whatever bytes are found in the first OP_RETURN output of whichever *conflicting* transaction happens to confirm for that input, with **no cross-check** against who supplied the value.

`create_payout_txhandler` builds outputs `[user_payout, anchor(NON_EPHEMERAL_ANCHOR_AMOUNT), OP_RETURN(operator_xonly_pk)]` and signs only input 0 with the user's `SinglePlusAnyoneCanPay` signature: [2](#0-1) . That sighash type, per BIP341, commits to input 0's outpoint/value/script and to output 0 only — outputs 1 (anchor) and 2 (OP_RETURN) and any other inputs are outside the signed message, confirmed by the test helper that computes this exact sighash: [3](#0-2) .

`Operator::withdraw` verifies the *user's* signature against this same sighash before broadcasting [4](#0-3) , then funds/signs/broadcasts via `fund_raw_transaction`/`sign_raw_transaction_with_wallet` [5](#0-4) . If the withdrawal input UTXO's value already covers `output0 + anchor + minimal fee` (a realistic configuration, since `is_profitable` only guarantees `net_profit >= operator_withdrawal_fee_sats`, not that additional wallet funding is required) [6](#0-5) , `fund_raw_transaction` adds **no extra inputs**, leaving the entire broadcast transaction protected by only the single `SinglePlusAnyoneCanPay` signature.

Under the stated threat model, the attacker is the withdrawing user (or intercepts the off-chain `in_signature`) and therefore already possesses this exact signature. Before the honest operator's transaction confirms, the attacker rebuilds a transaction with the identical input 0 and output 0 (both signed/committed, so unchanged), but a different anchor value and a different OP_RETURN payload (an arbitrary/attacker-chosen `operator_xonly_pk`), and broadcasts it with a competitive fee (by shrinking the anchor value, which is unsigned, to raise the implicit fee) using RBF. Because both transactions spend the same input 0, they conflict; whichever gets mined determines the outcome.

`update_finalized_payouts` blindly parses the OP_RETURN of whichever transaction actually confirms and writes it to `payout_payer_operator_xonly_pk` [1](#0-0) , with no validation that the named operator funded anything. This value is later trusted as ground truth by `Verifier::is_kickoff_malicious`, which flags a kickoff as malicious purely by comparing `kickoff_data.operator_xonly_pk` against the DB value [7](#0-6) , and by `Operator::send_asserts`, which errors out if they mismatch [8](#0-7) . None of `is_deposit_valid`, `verify_storage_proofs`, `SPV::verify`, or the presigned tx graph validate *who funded the withdrawal output*, only that a payout tx with a valid OP_RETURN-encoded pubkey exists for the withdrawal UTXO — so this specific gap is not otherwise covered.

### Impact Explanation
If the attacker's variant confirms instead of the honest operator's, the withdrawal's DB attribution (`payout_payer_operator_xonly_pk`) points to a pubkey that did not fund the payment. Consequences:
- If the attacker names a bogus/unregistered key, the true operator's later kickoff for that deposit will fail `is_kickoff_malicious`'s equality check and be treated as malicious, exposing the honest operator's kickoff to challenge/disprove — potentially burning their collateral and permanently blocking their legitimate reimbursement.
- If the attacker instead names a *different real* operator's key, that operator could subsequently be routed into the reimbursement flow for a payout they never funded once its kickoff is checked (`payout_op_xonly_pk == kickoff_data.operator_xonly_pk` would match for that operator, not the true payer).

Either outcome matches the Critical impact categories: "an honest operator permanently unable to be reimbursed" / "an honest operator's collateral burned" / "an operator reimbursed for a payout it never funded." The blast radius is per-withdrawal and repeatable across any deposit/withdrawal where the withdrawal UTXO already fully funds the payout without additional operator-wallet inputs.

### Likelihood Explanation
Requires: (1) an honest Payout tx broadcast but unconfirmed, (2) the payout tx's only witness-bearing input signed with `SinglePlusAnyoneCanPay` (i.e., no additional wallet-funded input was needed) — plausible depending on the configured `operator_withdrawal_fee_sats` margin versus anchor/fee costs, and (3) the attacker (as the withdrawing user, who legitimately possesses the `in_signature`) winning an RBF fee race, which only costs the marginal fee difference (the anchor value, e.g. hundreds/low-thousands of sats, is fungible into fee). This is a low-cost, deterministic mempool race requiring no privileged access — matching the "Preconditions/Call sequence" the question describes. Its feasibility is contingent on operator funding not adding extra committed inputs, which cannot be verified as always/never true from the repo alone without live deployment parameters, but nothing in the code prevents this configuration.

### Recommendation
Change the payout input's sighash to commit to all outputs and reject `ANYONECANPAY`/`SINGLE` for this input — e.g. sign with `SIGHASH_ALL` (or at minimum `SIGHASH_ALL|ANYONECANPAY` if additional operator-funded inputs must remain flexible) so that the anchor value and OP_RETURN payload are covered by the same signature as output 0. Alternatively/additionally, have `update_finalized_payouts` cross-validate that the confirming payout transaction's structure (inputs, anchor amount) matches the operator's own signed template, rather than trusting the OP_RETURN payload in isolation.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

fn sign_withdrawal_output(
    config: &BridgeConfig,
    dust_utxo: &UTXO,
    withdrawal_address: &bitcoin::Address,
    withdrawal_amount: bitcoin::Amount,
) -> (bitcoin::TxOut, taproot::Signature) {
    let signer = Actor::new(config.secret_key, config.protocol_paramset().network);
    let txin = builder::transaction::input::SpendableTxIn::new(
        dust_utxo.outpoint,
        dust_utxo.txout.clone(),
        vec![],
        None,
    );
    let txout = bitcoin::TxOut {
        value: withdrawal_amount,
        script_pubkey: withdrawal_address.script_pubkey(),
    };
    let unspent_txout = builder::transaction::output::UnspentTxOut::from_partial(txout.clone());

    let tx = builder::transaction::TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            builder::transaction::DEFAULT_SEQUENCE,
        )
        .add_output(unspent_txout.clone())
        .finalize();

    let sighash = tx
        .calculate_sighash_txin(0, sighash::TapSighashType::SinglePlusAnyoneCanPay)
        .expect("Failed to calculate sighash");

    let sig = signer
        .sign_with_tweak_data(sighash, builder::sighash::TapTweakData::KeyPath(None), None)
        .expect("Failed to sign");

    let sig = taproot::Signature {
        signature: sig,
        sighash_type: sighash::TapSighashType::SinglePlusAnyoneCanPay,
    };

    (txout, sig)
}

    fn is_profitable(
        input_amount: Amount,
        withdrawal_amount: Amount,
        bridge_amount_sats: Amount,
        operator_withdrawal_fee_sats: Amount,
    ) -> bool {
        // Use checked_sub to safely handle potential underflow
        let withdrawal_diff = match withdrawal_amount
            .to_sat()
            .checked_sub(input_amount.to_sat())
        {
            Some(diff) => Amount::from_sat(diff),
            None => {
                // input amount is greater than withdrawal amount, so it's profitable but doesn't make sense
                tracing::warn!(
                    "Some user gave more amount than the withdrawal amount as input for withdrawal"
                );
                return true;
            }
        };

        if withdrawal_diff > bridge_amount_sats {
            return false;
        }

        // Calculate net profit after the withdrawal using checked_sub to prevent panic
        let net_profit = match bridge_amount_sats.checked_sub(withdrawal_diff) {
            Some(profit) => profit,
            None => return false, // If underflow occurs, it's not profitable
        };

        // Net profit must be bigger than withdrawal fee.
        // net profit doesn't take into account the fees, but operator_withdrawal_fee_sats should
        net_profit >= operator_withdrawal_fee_sats
    }
