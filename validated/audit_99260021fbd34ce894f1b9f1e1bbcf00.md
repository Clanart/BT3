### Title
Permanent, unscoped `safe.directory` trust exception never revoked after repository removal - ([File: app/src/lib/git/config.ts])

### Summary
The bug class described in the external report is "a permission granted to interact with an object is left permanently active after the triggering action completes, and nothing in the normal user flow revokes it." The GitHub Desktop analog is the `safe.directory` trust mechanism: when a user encounters a Git-detected "dubious ownership" (unsafe) repository and clicks "Trust repository," Desktop permanently whitelists that exact filesystem path in the user's **global** `.gitconfig`, and there is no code path anywhere in the app that ever removes it again — not even when the user removes/deletes the repository from Desktop.

### Finding Description
When Desktop detects an "unsafe" repository (owned by a different user, e.g. after cloning into a shared/removable/network path, or importing a repo whose ownership doesn't match the current user), the UI offers a "Trust repository" action in `AddExistingRepository.onTrustDirectory` and `MissingRepository.onTrustDirectory`: [1](#0-0) 

Both call `addSafeDirectory(path)`: [2](#0-1) 

which unconditionally appends the path to the global `safe.directory` config list via `addGlobalConfigValueIfMissing`, using `git config --global --add`: [3](#0-2) 

This is a **global**, machine-wide, permanent Git configuration change — it is not scoped to the current Desktop session, not tied to the specific repository record in Desktop's database, and not attached to any expiring token/permission object. I searched the codebase for any counterpart "revoke"/"remove" logic (`removeSafeDirectory`, cleanup of `safe.directory` on `removeRepository`) and found none — `RepositoriesStore` and the `removeRepository` flows in `app-store.ts` / `dispatcher.ts` only affect Desktop's internal repository list/database, never touching the Git global config.

This mirrors exactly the reported smart-contract flaw: the "workflow" (Desktop) performs a whitelisting action (`setBatchPermissionFor` ≈ `git config --global --add safe.directory`) to accomplish one atomic task (letting a specific, one-time-flagged path be treated as safe), but the resulting permission persists indefinitely regardless of what happens afterward to the object it was granted for.

### Impact Explanation
Once a path is added to `safe.directory`, any Git repository under that exact path — even one an attacker later plants/replaces at the same path (e.g. a shared machine, a removable drive, a network share, a temp/downloads folder that gets reused, or a path where a prior test/demo repo was removed and a new one owned by another user is dropped in) — will silently bypass Git's "dubious ownership" protection for **every Git client and IDE on the machine**, not just Desktop, since `safe.directory` is a global Git config entry, not an application-scoped setting. Git's dubious-ownership check exists specifically to prevent automatic execution of repository-controlled hooks/config (e.g. `core.fsmonitor`, `.git/hooks/*`) when a repo is owned by another user — the exact attack the warning text in `add-existing-repository.tsx` references ("Adding untrusted repositories may automatically execute files in the repository"). A permanently whitelisted path re-opens this exact risk for any future untrusted content placed at that path, with no user-visible indication that the exception is still active. [4](#0-3) 

### Likelihood Explanation
Trusting a repository is a common, low-friction one-click action any Desktop user performs whenever cloning to removable media, shared/multi-user machines, or CI-mounted paths, or when repository ownership metadata is unusual (a scenario common on Windows with WSL-mounted drives and on shared network drives, which the changelog shows was explicitly a repeated pain point: "Support trusting repositories on network shares (Windows)"). Because there is no UI to view or revoke previously-trusted directories, and `removeRepository` never cleans it up, stale trust entries accumulate silently and indefinitely on every user's machine, making the exploitation window (attacker later placing/regaining control of content at a previously-trusted path) realistic rather than theoretical. [5](#0-4) 

### Recommendation
Scope the trust decision instead of writing a permanent global exception: prefer per-invocation `-c safe.directory=<path>` command-line/environment scoping for the specific Git operations Desktop needs to run, or at minimum track trusted paths in Desktop's own repository record so that `removeRepository` (and periodic housekeeping) can call a corresponding `removeSafeDirectory` to prune the global `safe.directory` list when Desktop no longer manages that repository. Surface currently-trusted directories in Settings so users can audit and manually revoke them.

### Proof of Concept
1. On a shared/multi-user machine (or a machine where a removable/network drive is later reused by another user), clone or add a repository at path `P` that Git flags as "dubious ownership."
2. In Desktop, click "Trust repository" (`AddExistingRepository.onTrustDirectory` / `MissingRepository.onTrustDirectory`), which calls `addSafeDirectory(P)` → `git config --global --add safe.directory P`.
3. Remove the repository from Desktop (`dispatcher.removeRepository`), or simply delete the folder at `P`.
4. At a later time, an attacker (a different OS user, or content restored from removable media) places a malicious Git repository — including hostile hooks/config — at the exact same path `P`.
5. Any Git operation on `P`, from Desktop or any other Git client on that machine, silently skips the dubious-ownership warning and proceeds to read/execute repo-controlled config/hooks, because `safe.directory` still contains `P` from step 2 and nothing ever removed it.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```

```typescript
/** Set the global config value by name. */
export async function addGlobalConfigValueIfMissing(
  name: string,
  value: string
): Promise<void> {
  const { stdout, exitCode } = await git(
    ['config', '--global', '-z', '--get-all', name, value],
    __dirname,
    'addGlobalConfigValue',
    { successExitCodes: new Set([0, 1]) }
  )

  if (exitCode === 1 || !stdout.split('\0').includes(value)) {
    await addGlobalConfigValue(name, value)
  }
}
```
