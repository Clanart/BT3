### Title
Automatic silent rewrite of the local git remote URL from an unauthenticated GitHub API field - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl()` compares the previously cached `GitHubRepository.cloneURL` against the API-fetched `apiRepo.clone_url` and, if the local remote still matches the old cached value, automatically calls `gitStore.setRemoteURL()` to rewrite the user's `origin` (or default) remote — with no user confirmation dialog. [1](#0-0)  This is invoked from `repositoryWithRefreshedGitHubRepository`, a routine background-refresh path that runs `api.fetchRepository(owner, name)` and feeds the resulting API object directly into `updateRemoteUrl`. [2](#0-1) 

### Finding Description
The invariant that should hold is: *the local git remote URL — which determines where the user's credentials, pushes, and fetches go — must only change with explicit user awareness/consent*, analogous to the SophonFarming invariant that shared accounting state (`totalAllocPoint`) must not be mutated without first settling everything that depends on it. Here, the "accounting state" is the trust relationship between the locally configured remote and the GitHub-hosted repository.

`updateRemoteUrl` breaks this invariant by treating a GitHub API response (`IAPIRepository.clone_url`) as authoritative and silently pushing it into the local git config via `setRemoteURL`, which shells out to `git remote set-url`: [3](#0-2) 

The only guards are:
- `gitStore.defaultRemote !== null`
- `protocolsMatch` (same scheme, e.g. https vs https)
- `remoteUrlUnchanged` — the *current* local remote still equals the *previously cached* `gitHubRepository.cloneURL`
- `!urlsMatch` — the new API url differs from the current remote

None of these guards validate that the *newly reported* `clone_url` actually still refers to the same underlying repository the user originally added. They only check that the user hasn't manually customized their remote away from what Desktop remembers. If the API begins returning a different `clone_url` for what Desktop believes is "the same" `GitHubRepository` record (e.g., because the repo was renamed/transferred, or because whoever controls the account/repo name changes ownership after the original repo is deleted — a squatting scenario), Desktop will happily rewrite the remote to point wherever the API says, without ever asking the user. Existing guards (protocol/hostname sanity, user prompts) exist elsewhere in the app for explicit remote edits (e.g. `RepositorySettings` calls `dispatcher.setRemoteURL` only from a user-typed text box [4](#0-3) , and there's even a dedicated confirmation dialog, `UpstreamAlreadyExists`, for changing the *upstream* remote [5](#0-4) ) — but this automatic sync path bypasses all of that.

### Impact Explanation
If exploited, the next `git push`/`git fetch`/`git pull` the user performs silently targets a URL the user never approved of. Over HTTPS this can exfiltrate the stored git credential/token to an attacker-controlled host during authentication, and for SSH it can leak which key material is offered. It can also silently corrupt what the user pushes (into a repo the user does not actually control) or what they later pull/merge into their working tree (arbitrary attacker-supplied content), matching the "silent corruption of what the user commits or pushes" and "credential/token exfiltration" categories in the valid-impact list. This is entirely unprivileged from the attacker's perspective — no local access, no malware, and no unusual user action is required, since the update happens as part of the routine background repository refresh (`_refreshRepository` → `repositoryWithRefreshedGitHubRepository`).

### Likelihood Explanation
`repositoryWithRefreshedGitHubRepository` runs during normal, frequent app operations, not on a rare admin action — this happens as part of standard refresh flows tied to the repository model. The precondition (`remoteUrlUnchanged`) is the *common* case, since most users never manually edit the remote URL that Desktop configured for them. The main open question — which I could not fully verify given remaining tool budget — is exactly how `matchGitHubRepository` resolves which `GitHubRepository`/account to re-fetch (by persisted database ID vs. by re-parsing owner/name from the current remote each time), which determines whether a rename/ownership-transfer/squatting scenario can actually substitute a different underlying repository. This should be confirmed by inspecting `matchGitHubRepository` (`app-store.ts`) and `find-account.ts` before treating this as fully proven, so I present it with that caveat.

### Recommendation
Never let automatic background sync rewrite a git remote without an explicit user prompt (mirroring the existing `UpstreamAlreadyExists` dialog pattern already used for upstream remotes). At minimum, require confirmation before calling `setRemoteURL` from `updateRemoteUrl`, and additionally cross-check `apiRepo.id`/`node_id` against the persisted `GitHubRepository.dbID`'s originally-associated repository identity (not just owner/name string matching) before considering two API responses "the same repository."

### Proof of Concept
1. User adds/clones a repository and Desktop stores `GitHubRepository.cloneURL` matching the current `origin` remote.
2. On a subsequent background refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository(owner, name)` [6](#0-5)  and obtains an `IAPIRepository` object whose `clone_url` now differs from what's cached (e.g., due to a rename/transfer, or a re-registered owner/name after the original repo was deleted).
3. `updateRemoteUrl` sees `protocolsMatch = true`, `remoteUrlUnchanged = true` (local remote still equals the old cached clone URL), `urlsMatch = false`, and calls `gitStore.setRemoteURL(name, updatedRemoteUrl)` without any prompt. [7](#0-6) 
4. The next `git push`/`fetch` from Desktop now silently targets the new, unverified URL.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
