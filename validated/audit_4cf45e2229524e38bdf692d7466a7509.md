## Title
Pharos consensus client accepts an unbounded `header.timestamp` that is used to prematurely satisfy request timeout checks - ([File: modules/consensus/pharos/verifier/src/lib.rs])

### Summary
The Berachain report's core defect is that a proposer-supplied `Timestamp` field is trusted without being bounded against real time before it becomes part of accepted state, letting a single proposer corrupt a value that downstream logic assumes is monotonic and roughly accurate. The Pharos ISMP consensus client has the same defect: `verify_pharos_block` validates block hash, epoch continuity, and BLS signature thresholds, but never validates `update.header.timestamp` against the previously trusted timestamp or against the host's own wall-clock/bounds. That unvalidated timestamp is copied verbatim into the `StateCommitment` that is later used by the generic ISMP request-timeout handler to decide whether outstanding `PostRequest`s have expired.

### Finding Description
`verify_pharos_block` performs block-number, hash, epoch, and BLS-signature checks, but has no check on `update.header.timestamp` at all: [1](#0-0) [2](#0-1) 

The `PharosClient::verify_consensus` then takes that unvalidated `update.header.timestamp` and stores it directly as the `StateCommitment.timestamp` for the tracked EVM chain, with no sanity bound against `host.timestamp()`: [3](#0-2) 

Contrast this with the Tendermint/Polygon light client, which explicitly enforces a `HeaderFromFuture` bound via the cometbft verifier's clock-drift check before accepting a header's time as trusted: [4](#0-3) [5](#0-4) 

No equivalent bound exists for Pharos. Once this inflated `StateCommitment.timestamp` is stored, it becomes `state.timestamp()` in the generic ISMP `PostRequest` timeout handler, which uses it to decide whether any pending `PostRequest` destined to/from that Pharos-tracked chain has timed out: [6](#0-5) 

`PostRequest::timed_out` simply compares the supplied timestamp against the request's `timeout_timestamp`: [7](#0-6) 

The equivalent EVM-side handler makes the same unguarded comparison against `state.timestamp` when processing timeouts: [8](#0-7) 

Because a single block proposer/producer of a Pharos block controls the header's `timestamp` field (as in the original report, most PoS/EVM-style chains only require the timestamp to be monotonically increasing from the parent, not bounded from above), that proposer can set an extreme future timestamp in an otherwise valid, properly-signed block. The BLS signers validate hash/state/epoch continuity, not the timestamp's plausibility, so a supermajority can legitimately co-sign a block carrying a bogus far-future timestamp.

### Impact Explanation
Once such a state commitment is accepted, `state.timestamp()` for that height becomes far larger than any pending request's `timeout_timestamp`. Any party can then submit `handle_timeouts`/`handlePostRequestTimeouts` referencing that height: `post.timed_out(state.timestamp())` returns true trivially, and the accompanying non-membership proof for the (not-yet-delivered) request against the real, unforged state root will genuinely succeed since the request legitimately has not yet been processed on the destination. This lets an attacker force premature timeout of requests that have not actually expired — deleting the request commitment and firing `on_timeout` (refunding fees/escrow to the sponsor) on the source chain — while the request remains deliverable and can still be legitimately executed later on the destination via `handlePostRequests`/`handle` request path. The result is duplicate settlement: the source-side timeout path releases funds/state as if the request failed, while the destination-side delivery path can still execute the original intent, producing a double payout / loss of protocol funds. This satisfies the bounty's explicit "double-claim/double-settlement" and "loss of funds" impact categories.

### Likelihood Explanation
This does not require a malicious relayer, prover, or admin — only a single Pharos block proposer setting an implausible timestamp in an otherwise valid block, which the BLS-signing validator set has no mechanism to reject since timestamp plausibility is never checked in `verify_pharos_block`. Any unprivileged actor holding the resulting consensus proof can then submit the ordinary, public `handle_timeouts`/`handlePostRequestTimeouts` entrypoints to trigger the premature timeout — no privileged role is needed to exploit it once such a block exists.

### Recommendation
Add an explicit bound check in `verify_pharos_block` (or in `PharosClient::verify_consensus`) rejecting headers whose `timestamp` is not greater than the previously trusted state's timestamp and not more than a small allowed drift beyond the host's own `host.timestamp()`, mirroring the `HeaderFromFuture`-style bound already enforced by the Tendermint/Polygon verifier path.

### Proof of Concept
1. A Pharos block is produced (and gets ≥2/3 BLS-stake signatures) with a valid state root/hash but with `header.timestamp` set to a large future value (e.g., `u64::MAX` or timestamp far beyond any pending request's `timeout_timestamp`).
2. Submit this block via `ConsensusMessage`/`update_client` — `verify_pharos_block` accepts it because it never checks `header.timestamp`; `PharosClient::verify_consensus` stores it as `StateCommitment.timestamp` at `modules/ismp/clients/pharos/src/lib.rs:120-127`.
3. For any legitimately pending `PostRequest` targeting/originating from this Pharos-tracked chain (not actually expired), submit `TimeoutMessage::Post` (or EVM `handlePostRequestTimeouts`) referencing this height. `post.timed_out(state.timestamp())` in `modules/ismp/core/src/handlers/timeout.rs:75` returns true trivially, and the non-membership proof against the real (unforged) state root succeeds because the request genuinely hasn't been delivered yet.
4. The request commitment is deleted and `on_timeout` fires (refund/unwind) on the source chain, while the request remains valid and deliverable to the destination via the normal request-handling path, enabling duplicate settlement.

pub fn verify_pharos_block<C: Config, H: Keccak256 + Send + Sync>(
	trusted_state: VerifierState,
	update: VerifierStateUpdate,
) -> Result<VerifierState, Error> {
	let update_block_number = update.block_number();
	let current_block_number = trusted_state.finalized_block_number;

	if update_block_number <= current_block_number {
		return Err(Error::StaleUpdate {
			current: current_block_number,
			update: update_block_number,
		});
	}

	let computed_hash = Header::from(&update.header).hash::<H>();

	if computed_hash != update.block_proof.block_proof_hash {
		return Err(Error::BlockProofHashMismatch {
			computed: computed_hash,
			provided: update.block_proof.block_proof_hash,
		});
	}
