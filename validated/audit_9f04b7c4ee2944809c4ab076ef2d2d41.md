### Title
CW20ERC20Pointer.transferFrom always dispatches a CW20 `transfer_from` execute message even when spender == from, breaking ERC20 pull-only compatibility - ([File: contracts/src/CW20ERC20Pointer.sol])

### Summary
`CW20ERC20Pointer.transferFrom` (the Sei EVM pointer contract that wraps a native CW20 token as an ERC20, deployed on-chain via `x/evm/artifacts/cw20`) unconditionally forwards every `transferFrom` call to the underlying CW20 contract's `transfer_from` execute message, regardless of whether `msg.sender == from`. This is the same class of bug as Sherlock issue M-8 in Surge Protocol's `Pool#transferFrom`: the ERC20 standard (and OZ's base `ERC20` that this contract inherits and overrides) only consults/consumes the allowance when `spender != owner`; when the owner calls `transferFrom` on themselves, no allowance should be required.

### Finding Description
`transferFrom` in the pointer contract builds a `transfer_from` CosmWasm execute message using `from` as owner and `msg.sender` implicitly as the CW20 message sender, with no branch checking `from == msg.sender`: [1](#0-0) 

Compare this with `transfer`, which correctly always uses `msg.sender` as the mover of funds without any allowance dependency: [2](#0-1) 

The underlying CW20 contract's `transfer_from`/`ExecuteMsg::TransferFrom` handler (standard cw20-base semantics, reachable via `WasmdPrecompile.execute`) always looks up and decrements the `ALLOWANCES` map keyed by `(owner, spender)`, and errors if no allowance record exists — it does not special-case `owner == spender`. Because `CW20ERC20Pointer.transferFrom` never distinguishes the self-call case, any EVM caller who invokes `transferFrom(self, to, amount)` without having first called `approve(self, amount)` will have the call revert with `"CosmWasm execute failed"` (visible in the contract's `_execute` helper): [3](#0-2) 

This directly mirrors the ERC20 standard deviation identified in the referenced report: `transferFrom` should bypass the allowance mechanism when `spender == from`.

### Impact Explanation
Many DeFi protocols and routers exclusively use `transferFrom` (pull-only pattern) instead of ever calling `transfer` directly, including in first-party flows where the token owner itself is `msg.sender` (e.g., a contract pulling its own tokens for accounting reasons, or a wallet/router calling `transferFrom(user, user, amount)`-style self-moves). Because the pointer contract requires an allowance even in the owner-is-caller case, tokens routed through the CW20↔ERC20 pointer can become stuck/unusable in any integration that relies on this ERC20 compatibility guarantee, exactly as described in the analog report ("tokens becoming irreversibly stranded across different protocols"). Given the CW20 pointer is a core, generally reachable mechanism for exposing native/CW20 tokens to the EVM ecosystem on Sei, this breaks a fundamental interoperability assumption for any composing protocol.

### Likelihood Explanation
This is directly and trivially reachable by any EVM transaction sender: any account can deploy or interact with an existing CW20 pointer, and any protocol integrating with the pointer under the pull-only pattern will hit this immediately without any special preconditions, elevated privileges, or unlikely victim behavior.

### Recommendation
In `CW20ERC20Pointer.transferFrom`, special-case `from == msg.sender` by invoking the underlying CW20 `transfer` execute message (as `transfer` already does) instead of `transfer_from`, bypassing the allowance requirement entirely when the caller is the token owner — mirroring the ERC20 standard and the fix accepted in the referenced Surge Protocol report.

### Proof of Concept
1. Deploy/point a `CW20ERC20Pointer` at an existing CW20 denom with account `A` holding a balance and no allowance set for itself.
2. From account `A`, call `transferFrom(A, B, amount)` on the pointer without calling `approve(A, amount)` first.
3. The call reverts with `"CosmWasm execute failed"` because the underlying CW20 `transfer_from` message requires a pre-existing allowance record for `(A, A)`, which does not exist — despite `A` being both the owner and the caller, exactly as in the referenced `Pool#transferFrom` bug. [4](#0-3)

```text
    function transferFrom(address from, address to, uint256 amount) public override returns (bool) {
        require(to != address(0), "ERC20: transfer to the zero address");
        string memory sender = _formatPayload("owner", _doubleQuotes(AddrPrecompile.getSeiAddr(from)));
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount)));
        string memory req = _curlyBrace(_formatPayload("transfer_from", _curlyBrace(_join(_join(sender, recipient, ","), amt, ","))));
        _execute(bytes(req));
        return true;
    }

    function _execute(bytes memory req) internal returns (bytes memory) {
        (bool success, bytes memory ret) = WASMD_PRECOMPILE_ADDRESS.delegatecall(
            abi.encodeWithSignature(
                "execute(string,bytes,bytes)",
                Cw20Address,
                bytes(req),
                bytes("[]")
            )
        );
        require(success, "CosmWasm execute failed");
        return ret;
    }
```
