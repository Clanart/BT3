### Title
Buffer over-read via missing bounds checks in `is_atom_canonical` CLVM length-prefix parsing - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` parse a CLVM-serialized buffer (a coin spend's `solution` bytes, from an attacker-controlled spend bundle) byte-by-byte to decide dedup eligibility, but unlike every other length-prefixed buffer parser in this codebase, they never validate that `offset` stays within `len(clvm_buffer)` before indexing into it. This mirrors the CVE-2019-7572 class of bug: a decoder that trusts an internal length/index field and reads past the end of an attacker-supplied buffer.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads the atom's tag byte, determines a `prefix_len` (0–5 additional bytes), and then loops `prefix_len` times doing: [1](#0-0) 
incrementing `offset` and indexing `clvm_buffer[offset]` on every iteration with no check that `offset < len(clvm_buffer)`. `is_clvm_canonical()` drives this in a loop over the whole buffer, likewise indexing `clvm_buffer[offset]` without a bounds check before each read: [2](#0-1) 

Contrast this with the rest of the codebase's untrusted-buffer parsers, e.g. `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list`, which explicitly check `n > len(buf)` and raise `ValueError` before slicing: [3](#0-2) 

A truncated or crafted atom-length prefix (e.g., a buffer ending immediately after a multi-byte length-prefix tag byte such as `0xFC`–`0xFE` variants, so the follow-up length bytes are missing) causes `is_atom_canonical` to index past the end of `clvm_buffer`, raising an uncaught `IndexError` inside the mempool's per-spend eligibility computation rather than returning a controlled parse failure.

### Impact Explanation
This function is invoked during mempool spend-bundle processing (per `.cursor/context/clvm-execution.md`, `is_clvm_canonical()` at `mempool_manager.py:185` gates DEDUP eligibility for a submitted spend's solution). An `IndexError` raised out of this pure-Python parsing routine during spend-bundle admission is not a validated/typed error like the other `ValueError`s the mempool code otherwise raises and expects; it is reachable by any unprivileged party who submits a spend bundle with a malformed solution buffer. Depending on where the exception is caught in the call chain, this can manifest as an unhandled exception during mempool item construction, which the "Validate" acceptance criteria explicitly recognizes as a "spend-triggered transaction-processing halt."

### Likelihood Explanation
High: this code path is reached for every spend bundle that goes through mempool admission and dedup-eligibility scoring; the malformed byte sequence needed to trigger the read is trivial for a submitter to construct in a `CoinSpend.solution`.

### Recommendation
Add explicit bounds checks in `is_atom_canonical` before each `clvm_buffer[offset]` access (mirroring the `len(buf) < n` guards used in `skip_bytes`/`skip_list` in `chia/full_node/full_block_utils.py`), and have `is_clvm_canonical` treat an out-of-range parse as "not canonical" (return `False`) instead of letting an `IndexError` propagate.

### Proof of Concept
Construct a CLVM buffer ending in a multi-byte atom length-prefix tag with no trailing length bytes, e.g. `bytes([0b11111100])` (5-byte-prefix tag, `prefix_len = 5`, `min_value` set) followed by fewer than 5 bytes, then call:
```python
from chia.full_node.mempool_manager import is_clvm_canonical
is_clvm_canonical(bytes([0b11111100]))  # buffer of length 1, prefix_len=5 required
```
`is_atom_canonical` will attempt `clvm_buffer[offset]` for `offset` beyond the 1-byte buffer, raising `IndexError` instead of a handled validation failure.

**Note on verification limits**: due to the size of the tool-call budget available, I was not able to trace the exact call site that invokes `is_clvm_canonical`/dedup eligibility scoring on a submitted `CoinSpend.solution`, nor confirm whether an outer `try/except` in `MempoolManager` catches generic exceptions during that specific step. The parsing bug itself (missing bounds checks) is confirmed directly from source, but whether it currently crashes mempool processing versus being silently swallowed by a broader exception handler is unconfirmed. I recommend a Devin session with full repo access to trace `is_clvm_canonical`'s caller(s) and confirm exception-handling behavior before treating this as certain.

def skip_bytes(buf: memoryview) -> memoryview:
    if len(buf) < 4:
        raise ValueError(f"byte length prefix requires 4 bytes, remaining buffer {len(buf)}")
    n = int.from_bytes(buf[:4], "big", signed=False)
    buf = buf[4:]
    if n > len(buf):
        raise ValueError(f"byte length {n} exceeds remaining buffer {len(buf)}")
    return buf[n:]
