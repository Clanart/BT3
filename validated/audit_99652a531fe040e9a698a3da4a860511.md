### Title
Integer overflow in payment/fee summation bypasses the insufficient-funds check and produces an unspendable transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums attacker-influenced `u64` payment amounts and multiplies the fee rate by vbytes using unchecked `u64` arithmetic. Overflow of `payment_sat` (or `fee_per_vbyte * vbytes`) wraps to a small value, bypassing the `input_sat < payment_sat + needed_fee` check, so the multisig produces threshold signatures on a transaction whose outputs exceed its inputs and which the Bitcoin network will reject. This is the direct analog of CVE-2023-5849's integer-overflow class: untrusted numeric inputs are aggregated without checked arithmetic, corrupting the security-critical invariant (fee/output conservation) the function exists to enforce.

### Finding Description
In `SignableTransaction::new`, untrusted amounts are aggregated with plain `u64` ops:

- `payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>()` (`send.rs:187`) — no checked add.
- `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) — no checked mul.
- Insufficient-funds check: `if input_sat < (payment_sat + needed_fee)` (`send.rs:215`) — `payment_sat + needed_fee` itself can also overflow.

If `payment_sat` wraps to a small value, the check passes even though the actual `tx_outs` (built independently at `send.rs:188-191` with the true per-payment `u64` amounts) total far more than `input_sat`. Note the individual amounts are only validated against `DUST` (`send.rs:165-169`); there is no per-payment upper bound or total-supply bound. Likewise `fee_per_vbyte * vbytes` overflow wraps `needed_fee` to near-zero, bypassing both `TooLowFee` and `NotEnoughFunds`, producing a transaction paying essentially no fee.

`fee()` at `send.rs:138-141` performs `sum(inputs) - sum(outputs)`; with a wrapped `payment_sat` the actual output sum exceeds the input sum, so this subtraction underflows and panics (debug and release both panic on `-` overflow? — underflow panics in debug, wraps in release, yielding an absurd fee value). Either way the returned `SignableTransaction` is internally inconsistent.

The subsequent flow — `multisig()` → `preprocess()` → `sign()` → `complete()` (`send.rs:273-428`) — has no second conservation check: participants threshold-sign `taproot_key_spend_signature_hash` over the malformed prevouts/outputs, producing valid BIP-340 signatures for a transaction Bitcoin consensus rejects (outputs exceed inputs; or fee below relay minimum).

### Impact Explanation
The threshold set is induced to sign a transaction that can never confirm. Consequences:

- Burned signing session / preprocesses and a permanently stuck withdrawal requiring manual intervention (each FROST signing session is a real coordination cost).
- If an attacker can influence the `payments` list (e.g., withdrawal amounts sourced from user requests) or `fee_per_vbyte`, they can reliably force the multisig to produce invalid transactions — a liveness/DoS against the bridge's Bitcoin outputs, and a griefing vector that wastes nonce commitments and may complicate nonce reuse guarantees.
- In debug builds (tests, some deployments) the `sum::<u64>()` overflow panics outright, crashing the signing path.

This is a Medium: no direct theft (an outputs>inputs transaction can't be mined), but a reachable arithmetic-integrity failure that defeats the function's own validation and wastes/aborts threshold signing on demand.

### Likelihood Explanation
Reachability requires influencing `payments` amounts or `fee_per_vbyte`. In Serai's architecture, withdrawal payment amounts originate from user-initiated requests processed by the scheduler, and `fee_per_vbyte` from fee estimation — so an unprivileged user submitting crafted withdrawal amounts can plausibly reach the sum. Exploitation requires making the `u64` sum exceed `u64::MAX` (needs ~1.8e19 cumulative sats across the payment list — practically infeasible for `payment_sat` itself given BTC supply), BUT the same wrapping applies to `payment_sat + needed_fee` and `fee_per_vbyte * vbytes`: a malicious or erroneous `fee_per_vbyte` (e.g., `u64::MAX / vbytes + 1`) makes `needed_fee` wrap small with modest real payments, fully bypassing both checks. Whether `fee_per_vbyte` is attacker-reachable depends on the processor's fee-source, which is outside the in-scope crates — so likelihood is gated on that integration detail.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`:

- `payments.iter().try_fold(0u64, |a, p| a.checked_add(p.1))` and the same for `input_sat`.
- `fee_per_vbyte.checked_mul(vbytes)` and `payment_sat.checked_add(needed_fee)`, mapping `None` to `TooLowFee`/`NotEnoughFunds`.
- Bound each `payment.1` to `<= 21_000_000 * 1e8` (MoneyRange) as Bitcoin Core does.
- Make `fee()` use `checked_sub` and return `Option<u64>` or assert the invariant established at construction.

### Proof of Concept
```rust
// Conceptual: with attacker-influenced fee_per_vbyte chosen so the multiply wraps.
let vbytes = /* e.g. 200 */;
let fee_per_vbyte = u64::MAX / vbytes + 1; // wraps needed_fee to a small value

let stx = SignableTransaction::new(
    vec![received_output_1000_sats],
    &[(script, 600)],            // legitimate payment
    Some(change_script),
    None,
    fee_per_vbyte,
).unwrap(); // should be TooLowFee/NotEnoughFunds, but passes

// stx.needed_fee() ~= fee_per_vbyte*vbytes mod 2^64 (tiny)
// The resulting tx pays ~0 fee -> never relays; FROST session consumed.
// Or, in a debug build, the sum/mul panics -> signing crash.
```
For `payment_sat` wrapping specifically, the attacker would need cumulative payment amounts exceeding `u64::MAX` across the payment list — only feasible if the integrator fails to bound amounts, but the arithmetic flaw is identical.

Caveat: I could not fully verify who controls `payments`/`fee_per_vbyte` upstream (processor scheduler is partially in-scope but I ran out of search budget); the overflow itself at `send.rs:187`, `:206`, `:215` is confirmed in-file.
