### Title
`SignableTransaction` omits the OP_RETURN data output from the fee/weight calculation, underpaying the fee and inflating change owed to the sender — (`networks/bitcoin/src/wallet/send.rs`)

### Summary
Analogous to the reported bug class — a value computed and accounted for (here, the fee) is never actually charged, while a value owed to a party (the change) is paid out as if the charge had been applied — `SignableTransaction::new` computes transaction weight and the change amount using `payments` only, ignoring the OP_RETURN `data` output that was already pushed into `tx_outs`. The result is a transaction that pays a lower effective feerate than requested/reported by `needed_fee()`, and hands the uncharged difference to the change output's claim on funds rather than to the fee the network requires.

### Finding Description
In `SignableTransaction::new`, an OP_RETURN output is appended to `tx_outs` when `data` is provided (`send.rs:194-202`). However, both weight estimates are computed from `payments`, not `tx_outs`:

- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` (`send.rs:204`)
- `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` for `fee_with_change` (`send.rs:225-227`)

`calculate_weight_vbytes` builds a transaction whose outputs are only `payments` plus the optional change output; the OP_RETURN output (up to 80 bytes of payload plus ~10 bytes of output overhead) is excluded. Therefore `needed_fee` and `fee_with_change` are both under-estimated. The change amount is then computed as `input_sat - payment_sat - fee_with_change` (`send.rs:228`), so the change output absorbs sats that should have covered the fee for the OP_RETURN output's weight.

The transaction's actual paid fee is `sum(inputs) - sum(outputs)` (`fee()`, `send.rs:138-141`), which equals the under-estimated `fee_with_change`. The real feerate is below the caller's `fee_per_vbyte`, and can fall below `DEFAULT_MIN_RELAY_TX_FEE` even though the constructor's `TooLowFee` check passed — because that check also used the underestimated vbytes.

### Impact Explanation
An unprivileged caller supplying `data` (transaction data they cause to be signed) produces a signed transaction whose effective feerate is lower than the `needed_fee()` the code reports and lower than the requested rate. Depending on `fee_per_vbyte` and data size, the transaction can be non-relayable or left unconfirmed indefinitely, so the payments are never delivered while inputs may be marked spent — and the change output is credited an amount inconsistent with the promised feerate. This is a funds-liveness/accounting mismatch reachable purely from public inputs (`data` bytes, `fee_per_vbyte`).

### Likelihood Explanation
Any invocation of `SignableTransaction::new` with `Some(data)` and a `change` address triggers the discrepancy on every build; it is deterministic, not adversary-dependent beyond supplying the data. Whether the underpayment crosses a relay/confirmation threshold depends on data length and the fee rate.

### Recommendation
Pass `&tx_outs` (or an equivalent list including the OP_RETURN output) into `calculate_weight_vbytes` instead of `payments` at both call sites, so `vbytes`, `needed_fee`, `fee_with_change`, and the change amount all account for every output actually included in the transaction.

### Proof of Concept
In `networks/bitcoin/src/wallet/send.rs`:

- `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })` for `data` (lines 194-202).
- Weight/vbytes computed over `payments` only, excluding that output: lines 204 and 225-227 in `calculate_weight_vbytes` (lines 62-99, which only iterates `payments` and the optional `change`).
- Change credited as `input_sat - payment_sat - fee_with_change` (lines 228-233), so the missing OP_RETURN weight is paid to change instead of the fee.

Construct `SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0; 80]), fee_per_vbyte)`: the returned `needed_fee()` and the transaction's real feerate are short by the OP_RETURN output's vbytes × `fee_per_vbyte`, and the change output is inflated by that same amount.
