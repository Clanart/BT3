Based on my research, the closest structural analog to the ToyBox report — "one code path has protective handling that a similar, attacker-reachable code path lacks" — is the asymmetry between the codebase's string/name sanitization functions (which are used defensively in several places) and the **remote URL** value that is passed straight into `git remote add` / `git remote set-url` without any equivalent validation, even though that value can originate from the GitHub API (attacker-influenced: a PR fork's `clone_url`, or a repo's `clone_url` fetched by a GHE/API server).

I was not able to fully verify (ran out of tool iterations) whether `app/src/lib/git/clone.ts` applies a `--` end-of-options separator before the clone URL, so I cannot confirm the full downstream exploitation chain into `git clone`. I'm presenting the concretely-verified analog below and flagging that gap explicitly.

### Title
Attacker-controlled remote URLs from the GitHub API are passed unsanitized as positional git arguments to `remote add`/`remote set-url` - (File: `app/src/lib/git/remote.ts`)

### Summary
GitHub Desktop has multiple internal utilities (`sanitizeCloneName`, `sanitizedRefName`, `sanitizedRepositoryName`, `testForInvalidChars`) that defensively strip dangerous characters from user- or remote-derived strings before they are used in file paths or git ref names. However, no equivalent validation exists for the remote **URL** value itself before it is spliced into git command argv arrays in `addRemote` and `setRemoteURL`. Several call sites feed these functions strings that originate directly from the GitHub API and are effectively attacker-controlled (a pull request author's fork clone URL, or a repository's `clone_url`).

### Finding Description
`addRemote` and `setRemoteURL` build the git command directly from the caller-supplied `url` with no leading-character or shape validation: [1](#0-0) [2](#0-1) 

These are invoked with values sourced from the GitHub API in at least three places:
- `_findPullRequestBranch` adds a fork remote using `headCloneUrl`, which comes from the PR's head repository metadata (controlled by the PR/fork author): [3](#0-2) 
- `ensureUpstreamRemoteURL` / `addUpstreamRemoteIfNeeded` add/update the upstream remote from `parent.cloneURL`: [4](#0-3) 
- `updateRemoteUrl` rewrites the default remote's URL using `apiRepo.clone_url` fetched from the API, gated only by a protocol-match/heuristic check that says nothing about argument-injection characters: [5](#0-4) 

By contrast, elsewhere in the same codebase, comparably attacker-influenced strings (repo names, branch names, clone directory names) are explicitly sanitized before use: [6](#0-5) [7](#0-6) 

This is the same "missing setter/guard on one path, present on the sibling path" pattern as the ToyBox report: the codebase demonstrably has the pattern and tooling to validate untrusted strings, but the remote-URL path — which is reachable purely by an attacker crafting a PR from a fork or controlling API/GHE response data — has no such guard before the value is handed to git as a positional argument.

### Impact Explanation
If a value beginning with `-`/`--` is accepted as a "URL" and later treated by git's argument parser as an option rather than a positional operand (a well-known class of git argument-injection issues affecting many git GUI clients), this could allow an unprivileged remote/PR-fork attacker to inject git options into subsequent git invocations on the victim's machine, corrupting repository configuration or, depending on which subcommand ultimately consumes the raw string as argv, potentially achieving unintended git behavior against the user's local checkout. This matches the "attacker controls a fetched repository / GitHub API object" threat model called out as valid impact.

### Likelihood Explanation
Likelihood is **uncertain/moderate** rather than confirmed high, because:
- I confirmed the missing validation at the `addRemote`/`setRemoteURL` layer and confirmed attacker-controlled call sites reach it.
- I was **not** able to verify in this session whether `git remote add <name> <url>` in the git version bundled via `dugite`, or the downstream `git clone`/`git fetch` invocations, actually mis-parse a leading-dash "URL" as an option (some git subcommands stop option parsing after the first non-option token, which would neutralize this). I also could not confirm the exact argv construction in `app/src/lib/git/clone.ts`.
- This uncertainty should be resolved by a background agent inspecting the dugite/git version behavior and `clone.ts` before treating this as a confirmed exploitable path.

### Recommendation
Add an explicit validator (mirroring `sanitizeCloneName`/`testForInvalidChars`) that rejects or normalizes remote URLs beginning with `-` (or otherwise not matching an expected URL/SSH-remote shape) before they reach `addRemote`, `setRemoteURL`, and any `git clone`/`git fetch` invocation that takes a raw URL argument. Alternatively, always pass `--` before the URL argument in these git invocations to force git to treat it strictly as a positional operand.

### Proof of Concept
Not independently confirmed end-to-end due to inability to verify the dugite/git argument-parsing behavior and `clone.ts` implementation in this session. Conceptually: an attacker opens a pull request from a fork whose repository/clone URL (as returned by the GitHub API) begins with `-` (e.g., `--upload-pack=...`); when GitHub Desktop calls `_findPullRequestBranch` → `addRemote(repository, forkRemoteName, headCloneUrl)`, the crafted string is passed unchecked into `git remote add` argv at [8](#0-7) . A background agent should verify whether this or the subsequent fetch/clone step causes git to parse the string as an option.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
