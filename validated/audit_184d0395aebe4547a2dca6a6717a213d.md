### Title
Unhandled `IndexError` in `get_mirror_info` on a crafted mirror-coin spend halts wallet-side Data Layer coin processing - ([File: chia/wallet/db_wallet/db_wallet_puzzles.py])

### Summary
The reported CVE is a denial-of-service caused by a parsing function that does not validate the structure of a crafted input before indexing into it. The analogous pattern exists in `chia`'s Data Layer wallet mirror-coin handling: `get_mirror_info()` blindly indexes into an attacker-supplied CLVM condition payload (`memos`) without checking that it has the minimum required length, and its caller, `DataLayerWallet.coin_added()`, does not guard the call with exception handling.

### Finding Description
`get_mirror_info()` in `chia/wallet/db_wallet/db_wallet_puzzles.py` runs the parent puzzle/solution and, upon finding a `CREATE_COIN` condition whose puzzle hash matches the DL mirror puzzle hash (`create_mirror_puzzle().get_tree_hash()`), reads the memo list from the condition and immediately does: [1](#0-0) 
```
memos: list[bytes] = condition.at("rrrf").as_python()
launcher_id = bytes32(memos[0])
return launcher_id, [url for url in memos[1:]]
```

The puzzle hash used for matching (`create_mirror_puzzle().get_tree_hash()`) is a public constant `MIRROR_PUZZLE_HASH`, so any unprivileged spender can create a coin whose `puzzle_hash` equals it, with an accompanying parent spend that emits a `CREATE_COIN` condition to that puzzle hash but with an **empty memo list** (or a memo list missing the launcher id). Because CLVM conditions are attacker-controlled data emitted by an arbitrary puzzle/solution pair (the "parent puzzle" run here is just whatever the spender chooses, not necessarily the real mirror puzzle), the memo list shape is entirely under attacker control.

This function is invoked from `DataLayerWallet.coin_added()`, which is called by the wallet's coin-sync path whenever a wallet observes a new coin whose puzzle hash equals the mirror puzzle hash: [2](#0-1) 
```
async def coin_added(
    self, coin: Coin, height: uint32, peer: WSChiaConnection, coin_data: object | None, sync_scope: WalletSyncScope
) -> None:
    if coin.puzzle_hash == create_mirror_puzzle().get_tree_hash():
        parent_state: CoinState = (
            await self.wallet_state_manager.wallet_node.get_coin_state([coin.parent_coin_info], peer=peer)
        )[0]
        parent_spend = await fetch_coin_spend(height, parent_state.coin, peer)
        assert parent_spend is not None
        launcher_id, urls = get_mirror_info(parent_spend.puzzle_reveal, parent_spend.solution)
```

There is no `try/except` around `get_mirror_info(...)` here, so an `IndexError` raised when `memos` is empty (or too short) propagates up through the wallet's coin-added processing pipeline for any wallet that has a Data Layer wallet configured and is syncing coin state that includes such a coin.

### Impact Explanation
Any wallet user (or offer counterparty / anyone whose wallet syncs the chain) that has a DataLayer wallet active can be forced to process a mirror-shaped coin created by an unprivileged spender. Once such a coin confirms on-chain and the victim wallet syncs it, `coin_added()` raises an uncaught `IndexError`, halting further coin processing for that sync callback. This is a spend-triggered denial-of-service against wallet transaction/coin processing — directly analogous to the reported CVE's "crafted payload causing DoS in a parsing function."

### Likelihood Explanation
Likelihood is Medium: it requires a victim to run a DataLayer wallet (not the default for all users) and for the malicious coin to be included in a confirmed block (subject to normal mempool acceptance, but the spend itself is valid CLVM and does not violate any consensus rule, so it should be minable/includable). No special privileges beyond normal spend-bundle submission are needed to construct the crafted parent spend.

### Recommendation
In `get_mirror_info()`, validate that `memos` is non-empty (and ideally that all subsequent items are `bytes`) before indexing, raising the existing `ValueError("The provided puzzle and solution do not create a mirror coin")` instead of letting an `IndexError` escape. Additionally, wrap the `get_mirror_info` call in `DataLayerWallet.coin_added()` in a try/except that logs and returns instead of propagating, mirroring how the function already documents an expected `ValueError` failure path for non-mirror coins.

### Proof of Concept
1. Craft a coin-spend whose puzzle, when run with a given solution, emits: `(CREATE_COIN <MIRROR_PUZZLE_HASH> <amount> (() ))` — i.e. a `CREATE_COIN` condition targeting `MIRROR_PUZZLE_HASH` with a memo field set to an empty list (or a single-element list without a launcher id).
2. Submit this as part of a spend bundle from an unprivileged wallet; it creates a child coin with `puzzle_hash == MIRROR_PUZZLE_HASH`.
3. Once confirmed, any node/wallet with a `DataLayerWallet` configured that syncs this coin state calls `coin_added()` → `get_mirror_info(parent_spend.puzzle_reveal, parent_spend.solution)` → `memos[0]` raises `IndexError` because `memos` is empty, which is not caught anywhere in the call chain, halting that wallet's coin-added processing for the sync batch.
