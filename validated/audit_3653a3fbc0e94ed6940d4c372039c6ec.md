### Title
Zero-amount escrow entries can revert `withdraw()` in the Tron IntentGatewayV2, permanently freezing bridged escrow - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the Intent Gateway's `withdraw()` function iterates `body.tokens[]` and unconditionally attempts an ERC-20 `transfer` for every entry, including entries whose `amount == 0`. The canonical EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`) explicitly guards against this with `if (amount == 0) continue;`, but that guard is absent from the Tron contract's `withdraw()`. This is the exact bug class from the Notional report: a code path that always attempts a deposit/transfer of a value that can legitimately be zero, against an external asset that may revert on a zero-value operation.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 682-721) is the single settlement function used for both `RedeemEscrow` (fill settlement) and `RefundEscrow` (cancellation) cross-chain messages, and it is also invoked from `onGetResponse` for GET-based cancellation: [1](#0-0) 

For each `body.tokens[i]`, the code:
1. Checks `_orders[body.commitment][token] == 0` (the *escrow balance*, not the transfer `amount`) and reverts `UnknownOrder` if so.
2. Executes `token.call(transfer(beneficiary, amount))` (or a raw native `.call{value: amount}("")`) unconditionally, even when `amount == 0`.
3. Subtracts `amount` from the escrow.

Compare this to the fixed/canonical logic in the EVM app (`IntentsBase.sol::_withdraw`), which explicitly skips zero-amount entries before touching the token: [2](#0-1) 

The Tron `withdraw()` never applies this `if (amount == 0) continue;` guard. As long as the escrow entry for that token is non-zero overall (satisfying the `UnknownOrder` check), a `WithdrawalRequest.tokens[i].amount` of `0` for one of the multiple input tokens in an order still results in an actual zero-value `transfer` call to the token contract. Per the well-documented "revert on zero-value transfers" behavior of several real ERC-20 tokens (BNB, and others noted in the weird-erc20 catalogue referenced in the source report), this call can revert, which reverts the entire `withdraw()` transaction — and thus the entire `onAccept`/`onGetResponse` handler, since `onAccept`/`onGetResponse` are `external` entry points called directly by the trusted host with no try/catch around `withdraw()`.

Because `WithdrawalRequest.tokens` is built directly from `order.inputs` (the multi-token input array a user supplies at `placeOrder` time) and is dispatched cross-chain as part of `RedeemEscrow`/`RefundEscrow`, an order with more than one input token where one input's `amount` field ends up `0` for a given withdrawal path is enough to trigger this. This can occur naturally for RefundEscrow paths that recompute per-token remaining escrow (partial state) or for orders deliberately structured with a zero-value leg among multiple `inputs`, and no explicit check anywhere in the placement or settlement path rejects a zero `TokenInfo.amount` entry in `order.inputs`.

### Impact Explanation
If the settlement message reverts, the ISMP host's `onAccept` call for a `RedeemEscrow` (solver payout) or `RefundEscrow` (user refund/cancellation) never completes. The escrow funds for that commitment become permanently unredeemable through the normal flow: the solver that legitimately filled the order cannot be paid, and/or the user cannot recover a cancelled/expired order's escrow. This is direct loss/lock of bridged funds in escrow custody — squarely inside the bounty's "stealing or loss of funds" / "transaction manipulation" impact category, since it is a reachable, non-privileged path (any user placing an order, or the deterministic cross-chain settlement message flow) that causes funds to become stuck in the gateway with no retry path other than a token-specific workaround, if one exists at all.

### Likelihood Explanation
The trigger requires only a token that reverts on zero-value transfers being used as one of multiple `order.inputs` in a placed order, or any code path that produces a zero `amount` entry inside `WithdrawalRequest.tokens` reaching `withdraw()`. No relayer collusion, admin action, or malicious prover is required — the order itself is user-supplied data, and the withdrawal path is driven entirely by an authenticated but attacker/user-influenced `WithdrawalRequest.tokens` array. The absence of the `amount == 0` guard (present in the sibling EVM contract) indicates this is a real divergence/regression in the Tron port rather than an intentional design choice, making it a genuine, locally provable analog of the Notional zero-amount revert bug.

### Recommendation
Add the same `if (amount == 0) continue;` guard used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, skipping both the native-token `.call` and the ERC-20 `transfer` call for zero-amount entries, while still allowing the loop and escrow-accounting decrement (which is a no-op for `amount == 0`) to proceed.

### Proof of Concept
1. User calls `placeOrder` on the Tron chain with `order.inputs` containing two `TokenInfo` entries: one normal ERC-20 input with a non-zero amount, and one entry referencing a token known to revert on zero-value `transfer` calls (e.g., certain BSC-style tokens), with `amount` effectively contributing a zero-value leg to a later withdrawal computation (or crafted directly if any code path allows a zero `TokenInfo.amount` to be included in `order.inputs`).
2. The order proceeds through the normal cross-chain fill/cancel flow; a `WithdrawalRequest` is constructed from `order.inputs`/escrow state and dispatched as `RedeemEscrow` or `RefundEscrow` to the source chain.
3. On the source chain, the trusted host delivers the message and calls `IntentGatewayV2.onAccept`, which calls `withdraw(body, isRefund)`.
4. Inside `withdraw()`, the loop reaches the zero-value token leg and calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, 0))`.
5. Because the token reverts on a zero-value transfer, `success` is `false`, and `withdraw()` reverts with `TransferFailed`.
6. The entire `onAccept` call reverts. No escrow is released — not even for the other, non-zero-amount input token in the same order — leaving the whole order's escrow permanently stuck since there's no alternate path around `withdraw()` for that commitment. [3](#0-2) [4](#0-3)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
