### Title
Mempool fee calculation can raise an unhandled `ValueError` on spend bundles where total addition amount exceeds total removal amount, halting transaction processing - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` computes the transaction fee as `fees = uint64(removal_amount - addition_amount)` [1](#0-0)  without first verifying that `addition_amount <= removal_amount`. This mirrors the Taurus `_calcLiquidation()` bug class: an unchecked subtraction that is expected to always be non-negative in normal cases, but is not actually constrained to be so by any prior check, causing a revert/exception under an edge-case input that an attacker or even an honest-but-buggy client fully controls.

### Finding Description
While assembling `bundle_coin_spends`, the method sums `addition_amount` from each spend's `create_coin` outputs [2](#0-1)  and separately sums `removal_amount` from the coin records of the spent coins [3](#0-2) . Nowhere in this pipeline is there a check that `removal_amount >= addition_amount` before the subtraction. The only validations performed on `create_coin` amounts at this stage are per-condition bounds checks (non-negative, ≤ `MAX_COIN_AMOUNT`), as shown by the mempool-level tests `test_negative_addition_amount` and `test_valid_addition_amount` [4](#0-3) ; there is no aggregate check across all spends in a bundle that outputs do not exceed inputs.

That aggregate "minting" check (`Err.MINTING_COIN`) only exists in block-level validation, not in mempool admission: [5](#0-4) 

The `uint64()` constructor is known to raise `ValueError` (`"does not fit into uint64"`) for negative inputs, as demonstrated by `test_compute_block_fee` in the consensus test suite [6](#0-5) . Therefore, if a submitted spend bundle spends coins whose puzzles reveal `CREATE_COIN` conditions summing to more value than the coins being spent (each individual `CREATE_COIN` amount remaining within valid bounds), `removal_amount - addition_amount` is negative and `uint64(...)` at line 814 raises an unhandled `ValueError`.

`FullNode.add_transaction()` only wraps the earlier `pre_validate_spendbundle()` call in a `try/except ValueError`/`ValidationError` block [7](#0-6) ; `validate_spend_bundle()` (containing the vulnerable line) is invoked later, in the code path calling `add_spend_bundle`, which is not shown to be wrapped by the same protective handling. This mirrors exactly the reported bug class: an unchecked subtraction assumed safe by the surrounding business logic, but not actually guaranteed to be non-negative, causing a revert/exception in a specific, attacker-reachable edge case (not requiring any privileged access — any spend-bundle submitter can trigger it by crafting the puzzle reveal and solution for coins they control).

### Impact Explanation
An unprivileged spend-bundle submitter can craft a bundle where a spent coin's puzzle emits `CREATE_COIN` conditions whose total value exceeds the coin's own amount, while staying within individual per-condition bounds. This causes `validate_spend_bundle()` to throw an unhandled `ValueError` at the fee computation step instead of returning a structured `Err`. If this exception is not caught by the caller (unlike the `pre_validate_spendbundle` path, which is explicitly protected), it results in a spend-triggered halt of that transaction's processing path in the full node, rather than a clean `MempoolInclusionStatus.FAILED` rejection. This matches the "spend-triggered transaction-processing halt" impact class.

### Likelihood Explanation
The condition is fully attacker-controlled: any submitter can construct a `CoinSpend` whose puzzle reveal creates outputs of value greater than the coin's own amount (each individual output still within `MAX_COIN_AMOUNT`), without needing any private information about network state or victims. This requires no malicious peer/node behavior, no leaked keys, and no privileged role — only crafting a spend bundle from an owned/controlled coin. The exact downstream exception-handling behavior around `validate_spend_bundle()`/`add_spend_bundle()` in `full_node.py` beyond what was inspected could not be fully confirmed within the available exploration, so whether this specific path is caught gracefully elsewhere remains somewhat uncertain.

### Recommendation
Add an explicit guard before the fee subtraction in `validate_spend_bundle()`:
```python
if addition_amount > removal_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This mirrors the recommendation from the source report — validate the potentially negative operand before performing the subtraction/cast, rather than relying on the operation to fail safely.

### Proof of Concept
1. Create a coin `C` with amount `1` owned by the attacker, using a custom puzzle (not necessarily a standard puzzle) that the attacker fully controls the reveal/solution for.
2. Craft `coin_spend` for `C` whose solution causes the puzzle to run and emit a single condition: `CREATE_COIN(some_puzzle_hash, 1000)`.
3. Submit this as a `SpendBundle` (with any required/absent signature satisfying `AGG_SIG` conditions, or none if the puzzle requires none) via `respond_transaction`/`add_transaction`.
4. In `MempoolManager.validate_spend_bundle()`, `removal_amount = 1`, `addition_amount = 1000`, so `fees = uint64(1 - 1000)` raises `ValueError: does not fit into uint64`.
5. Confirm whether this exception propagates uncaught through `add_spend_bundle`/`add_transaction` (unlike the explicitly-caught `pre_validate_spendbundle` path) to validate the full impact.
