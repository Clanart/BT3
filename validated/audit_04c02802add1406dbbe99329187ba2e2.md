### Title
Unprotected legacy transactions bypass chain-ID validation, enabling cross-chain transaction replay - (File: `blockchain/tx_pool.go`)

### Summary
Kaia's transaction pool only enforces chain-ID matching for "protected" (EIP-155) legacy transactions. A legacy transaction signed without EIP-155 replay protection (`V = 27/28`) is accepted with no chain-ID check at all, and is verified via `HomesteadSigner`, which has no concept of chain ID. This mirrors the root cause of CVE-2021-25835 in Ethermint: because the chain does not unconditionally require/verify a chain-ID-bound signature, a validly-signed transaction from one chain (or one with no chain ID specified) can be replayed on Kaia.

### Finding Description
In `blockchain/tx_pool.go`'s `validateTx`, the chain-ID check is conditioned on `tx.Protected()`: [1](#0-0) 

`Transaction.Protected()` explicitly returns `false` for any legacy transaction whose signature `V` is `27` or `28` (i.e., an unprotected, pre-EIP-155 style signature): [2](#0-1) 

When such an unprotected transaction reaches `EIP155Signer.Sender` (used via `LatestSignerForChainID` → `modernSigner.legacy`), it is explicitly delegated to `HomesteadSigner{}.Sender(tx)`: [3](#0-2) 

`HomesteadSigner` has no chain ID at all (`ChainID()` returns `nil`) and its `Sender` recovers the address purely from `(r, s, v)` with no chain binding whatsoever: [4](#0-3) 

Because `validateTx` skips the chain-ID comparison entirely for these unprotected transactions (`tx.Protected()` is `false`), such a transaction is accepted into the pool as long as it has a valid nonce/balance/signature, is included in a block, and passes consensus-level checks the same way. A separate comment in the block-assembly worker code confirms the assumption that "Kaia is always in EIP155" was relied upon to skip additional replay-protection enforcement, and that code path was disabled/commented out rather than replaced with an equivalent check: [5](#0-4) 

This is structurally the same bug class as CVE-2021-25835: the protocol does not universally require chain-ID-bound signatures, so a signature that is valid without reference to a specific chain ID can be reused/accepted on a different network than the signer intended, defeating the purpose of chain-ID-based replay protection.

### Impact Explanation
An unprotected legacy transaction signed by a user for one purpose/chain (e.g., signed without EIP-155 chainId parameter by a wallet, hardware signer, or an intentionally crafted transaction meant for another EVM chain that also permits homestead-style signatures) is accepted into Kaia's pool and can be mined, without Kaia ever verifying the signer intended it for the Kaia chain ID. This allows unauthorized replay of a transaction (e.g., a token transfer, contract call, or approval) across chains where the same private key is used, potentially causing unintended value movement / duplicate execution of an action the user only authorized once. This qualifies as concrete unauthorized value movement / acceptance of a transaction that should have been rejected due to missing chain binding.

### Likelihood Explanation
Reachable directly by any unprivileged transaction sender: simply craft/sign a legacy transaction with `V ∈ {27, 28}` (unprotected) and submit it via public RPC (`eth_sendRawTransaction`) or `txpool.AddRemote`. No special privileges, node compromise, or consensus/validator role is required — this is a single-transaction submission path (`AddRemote` → `validateTx`).

### Recommendation
Remove the `tx.Protected()` gate in `blockchain/tx_pool.go`'s `validateTx` chain-ID check (or reject unprotected/legacy pre-EIP-155 transactions outright once EIP-155 is always active on Kaia, consistent with the intent documented in `work/worker.go`'s comment). Concretely, always require `tx.ChainId().Cmp(pool.chainconfig.ChainID) == 0` for legacy transactions, and reject any transaction where `Protected()` is false given that Kaia asserts it is "always in EIP155."

### Proof of Concept
1. Generate a legacy transaction (nonce, to, value, data, gas, gasPrice) and sign it using `HomesteadSigner` (or equivalently produce `V = 27/28` without EIP-155 chainId encoding) — this is possible using `types.SignTx(tx, types.HomesteadSigner{}, key)` per the signer implementation cited above.
2. Submit the resulting raw transaction to a Kaia node via public RPC/`AddRemote`.
3. Observe that `validateTx`'s chain-ID branch (`blockchain/tx_pool.go:828`) is skipped because `tx.Protected()` returns `false` (`blockchain/types/transaction.go:491-497`), and the transaction is accepted/mined despite carrying no chain-specific binding — the same transaction bytes would also validate on any other homestead-compatible chain using the same key/nonce, demonstrating replay potential.

func isProtectedV(V *big.Int) bool {
	if V.BitLen() <= 8 {
		v := V.Uint64()
		return v != 27 && v != 28 && v != 1 && v != 0
	}
	// anything not 27 or 28 is considered protected
	return true
}

// Protected says whether the transaction is replay-protected.
func (tx *Transaction) Protected() bool {
	if tx.IsLegacyTransaction() {
		v := tx.RawSignatureValues()[0].V
		return v != nil && isProtectedV(v)
	}
	return true
}
