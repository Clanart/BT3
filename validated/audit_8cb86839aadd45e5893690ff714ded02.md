Based on the investigation, I found a concrete analog in the trampoline credential helper. The bug-class from the report — a function that trusts a caller-supplied identity ("caller" address) instead of deriving it from the actual authenticated context ("msg.sender") — maps to how GitHub Desktop's git-credential trampoline decides which stored account token to hand back to a git subprocess: it trusts whatever endpoint/host the credential request claims, rather than restricting it to the host of the remote the user actually initiated the operation against.

### Title
Credential helper hands the signed-in account's token to any host requested by a git subprocess spawned during a clone/fetch, enabling confused-deputy token misuse via malicious submodules - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
`git credential.helper=desktop` is configured globally for the whole git process tree via `GIT_CONFIG_PARAMETERS`, explicitly so that subprocesses spawned by git (e.g. submodule fetches, LFS filters) can also use it. [1](#0-0)  When any such subprocess asks for credentials, `getCredential`/`getGitHubCredential` simply looks up an account whose `endpoint` matches whatever host string is embedded in the credential request, with no check that this host is the one the user actually intended to interact with (e.g. the top-level repository's own remote). [2](#0-1) [3](#0-2) 

### Finding Description
`findGitHubTrampolineAccount` accepts any `endpoint` string derived from the credential request and returns the first stored account whose endpoint's origin matches it: [4](#0-3) 

```
export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
```

There is nothing tying this lookup back to the repository/remote that the user actually asked Desktop to clone, fetch, or push. The only "authorization" performed is a hostname match against the account list — exactly the same class of bug as the report: instead of scoping the action to a value derived from a trusted context (the actual initiating remote/operation, analogous to `msg.sender`), the code trusts an attacker-influenceable input (the credential request's target host, analogous to the user-supplied `caller` address).

Because Desktop deliberately propagates the credential-helper config to child processes so that git filters like LFS can use it, any subprocess git itself spawns while operating inside a repository the user cloned — most notably a `git submodule update` triggered by a malicious `.gitmodules` file — can trigger a brand-new credential request for a completely different host than the one the user is fetching from. If that host happens to match one of the user's stored GitHub.com/GHE account endpoints, Desktop's trampoline will silently hand over the real account token to authenticate that unrelated request, with no confirmation that the user intended to touch that second host/repository at all.

### Impact Explanation
An attacker who gets a victim to clone/open a repository (or add it as a remote/submodule) can embed a `.gitmodules` entry (or any nested remote reachable through recursive submodule fetch) pointing at an arbitrary path on `github.com` or the victim's GHE instance. When Desktop performs the top-level clone/fetch and git recurses into the submodule, the credential helper will authenticate that request using the victim's real, stored token — without ever prompting the user or verifying this second host/path matches the operation the user authorized. This is a confused-deputy primitive: the attacker's repository content (not the attacker directly) controls which credentialed request gets fired, letting them probe private-repo existence/content the victim can access, or trigger authenticated requests to endpoints the user never chose to interact with, entirely because the credential/token hand-off is keyed off a request-supplied host rather than the trusted operation context.

### Likelihood Explanation
Likelihood is high for the trigger condition (any repo with a submodule is enough — no unusual user action beyond a normal clone/fetch with submodules, which Desktop performs automatically for repos that declare them), though the blast radius depends on the victim already having a stored account for the targeted host, which is the common case for github.com. The `GIT_CONFIG_PARAMETERS` comment in `trampoline-environment.ts` confirms this global propagation is intentional, and hook-spawned processes are the only place where trampoline env vars are explicitly filtered out (`safePrefixes`/hooks-proxy) — submodule/filter subprocesses spawned directly by git are not filtered. [5](#0-4) 

### Recommendation
Scope credential lookups to the operation's declared/trusted endpoint(s) instead of accepting any host the credential request names. Concretely: pass the expected endpoint(s) for the current git operation into the trampoline token context (similar to how `trampolineEnvironmentPath`/`isBackgroundTaskEnvironment` are already tracked per-token in `trampoline-environment.ts`), and in `getGitHubCredential`/`getCredential`, reject or prompt-confirm any credential request whose host doesn't match the endpoint(s) associated with that token's operation, rather than matching purely against the full account list.

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitmodules` file with a submodule URL such as `https://github.com/some-org/private-target.git` (any path on a host the victim has a stored Desktop account for).
2. Victim clones the attacker's repository in GitHub Desktop with "recurse submodules" behavior (or later runs a submodule update inside it).
3. Git, spawned by Desktop with the global `credential.helper=desktop` config, attempts to fetch the submodule and issues a `git credential fill` request for `github.com`.
4. `getCredential` → `getGitHubCredential` → `findGitHubTrampolineAccount` matches the victim's real GitHub.com account purely by hostname and returns the stored token, authenticating the submodule fetch with the victim's real credentials without any confirmation that the user intended to touch `private-target`. [3](#0-2)
