### Title
Gas-griefing on relayers via unbounded native-ETH push to attacker-controlled `order.user`/beneficiary during cross-chain escrow settlement - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_withdraw()` releases escrowed native tokens to `beneficiary` (derived from `body.beneficiary`) using `beneficiary.call{value: amount}("")` with **no gas limit**. This function is reached from `onAccept()` (RedeemEscrow/RefundEscrow) and `onGetResponse()` — both of which are triggered exclusively by a relayer submitting a valid cross-chain proof to Hyperbridge. Since `order.user` is a raw `bytes32` chosen entirely by the order creator when the order is placed, an attacker can set it to a contract with a gas-consuming fallback, forcing whichever relayer eventually delivers the settlement/refund/cancel proof to pay for that execution out of their own transaction gas.

### Finding Description
- `Order.user` is attacker-supplied and copied verbatim into `WithdrawalRequest.beneficiary` in `_cancelFromSource` and `_cancelFromDest` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:203`, `:249`).
- `_withdraw()` in `IntentsBase.sol` performs `(bool sent,) = beneficiary.call{value: amount}("")` for the native-token branch (`evm/src/apps/intentsv2/IntentsBase.sol:405-406`) with the full remaining gas forwarded (no `gas:` stipend). [1](#0-0) 
- `_withdraw()` is invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages and from `onGetResponse()` for cancellation — both callbacks are `onlyHost` and execute only when a relayer submits the ISMP proof that drives message delivery. [2](#0-1) 
- Because the beneficiary address comes straight from `order.user` with no validation that it is an EOA or a well-behaved contract, and no gas cap bounds the sub-call, a malicious order creator can register `order.user` as a contract whose `receive()`/`fallback()` deliberately burns gas (e.g., a loop, or returning an oversized payload that the caller must pay to receive via return-data copying/ABI decode). The relayer who is required to deliver the corresponding settlement/refund message then pays this excess gas, with no way to predict or bound it beforehand since the call forwards essentially all available gas (63/64 rule).
- This differs from the wrapped-token paths (`WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`) which at least fall back to an ERC20 transfer if the native push fails — `IntentsBase._withdraw()` has no such fallback: if the push fails or is deliberately made maximally expensive, the transaction still completes (assuming `sent` is eventually returned `true`) but at attacker-dictated cost to the relayer, or reverts entirely with `InsufficientNativeToken()` if the attacker's contract deliberately reverts, permanently blocking that beneficiary's settlement path and forcing relayers to keep re-attempting (or refuse) delivery for that order.

### Impact Explanation
This is a fund-flow-adjacent griefing vector against the relayer network that Hyperbridge intent settlement depends on: an attacker can economically deter relayers from delivering RedeemEscrow/RefundEscrow/cancellation messages for their own maliciously crafted orders, since the delivery cost becomes attacker-controlled and can be made arbitrarily larger than the relayer fee paid for the job. Because relayers are needed to move the protocol's escrowed funds to completion, this can stall or economically discourage settlement of specific escrows, and in the worst case (attacker's fallback intentionally reverts) permanently locks the escrowed native tokens for that order since `_withdraw` has no non-reverting fallback path for native transfers.

### Likelihood Explanation
The order creator fully controls `order.user` at order-placement time with zero restriction (no check that it's an EOA, no code-size check, no gas cap on delivery). Any unprivileged user can place such an order and does not need a malicious relayer, prover, or admin — only a normal relayer performing its expected job. This makes the attack trivially and repeatably exploitable by an unprivileged attacker.

### Recommendation
- Cap the gas forwarded to `beneficiary.call{value: amount, gas: <fixed_stipend>}("")` (e.g., 3000–30000 gas, enough for standard `receive()`), and treat failure as expected (queue the funds for pull-based withdrawal) rather than reverting the whole settlement.
- Alternatively, switch to a pull-payment pattern for native ETH release to the `beneficiary` (record an internal claimable balance and let the beneficiary withdraw it themselves), removing the relayer's exposure to arbitrary fallback gas consumption entirely — mirroring the mitigation direction used in `WrappedHyperFungibleToken`, which already falls back to an ERC20-style transfer when the native push fails.

### Proof of Concept
1. Attacker deploys `EvilBeneficiary` with a `receive()` function containing an expensive loop (or that returns a huge payload sized to maximize `RETURNDATACOPY` cost in the caller).
2. Attacker calls the source-chain `IntentGatewayV2`/`IntentsV2` order-placement flow, setting `order.user = bytes32(uint256(uint160(address(EvilBeneficiary))))` and funding/escrowing a native-token order.
3. Attacker lets the order expire and calls `_cancelFromDest`/`_cancelFromSource` (as itself, since it is the order owner) to trigger the cross-chain `RefundEscrow`/GET-response cancellation flow, which builds `WithdrawalRequest{ beneficiary: order.user, ... }`.
4. A relayer, doing its normal job, submits the corresponding ISMP proof, causing the destination-chain contract's `onAccept()`/`onGetResponse()` to invoke `_withdraw()`. [3](#0-2) 
5. `_withdraw()` executes `beneficiary.call{value: amount}("")` with unbounded gas; `EvilBeneficiary`'s expensive fallback consumes gas at the relayer's expense (or reverts to permanently block `_withdraw` for that commitment, since there's no fallback path for the native branch), demonstrating gas griefing/fund-lock against the relayer for a beneficiary the attacker fully controls.
