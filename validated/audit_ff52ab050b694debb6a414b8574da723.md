### Summary
The kernel bug (CVE-2017-16525) is a use-after-free: stale state is reused after a failed/disconnected setup. The Serai analog is state reuse in signing: `SigningProtocol::preprocess_internal` derives FROST nonces deterministically from a DB-cached seed keyed only on `context`, and `share_internal`/`complete` regenerate the identical nonces on every call for the same context. A co-signer who causes the node to run `sign` twice for the same attempt with different preprocess sets obtains two signature shares using the same nonce under different binding factors/challenges, enabling algebraic recovery of the signer's FROST secret share.

### Finding Description
`preprocess_internal` stores a 32-byte ChaCha seed under `CachedPreprocesses::set(self.txn, &self.context, ...)` and, on every subsequent call, reads it back and rebuilds the machine with `AlgorithmSignMachine::from_cache` — never deleting or rotating the entry [1](#0-0) . `share_internal` then calls `preprocess_internal` again and immediately `machine.sign(preprocesses, msg)` with caller-supplied preprocesses [2](#0-1) . `DkgConfirmer::share` and `DkgConfirmer::complete` each invoke `share_internal` with independently supplied `preprocesses` maps for the same `(b"DkgConfirmer", attempt)` context [3](#0-2) .

In `crypto/frost/src/sign.rs`, `seeded_preprocess` regenerates `nonces` deterministically from the cached seed [4](#0-3) , and `sign` computes the effective nonce as `base + rho * actual` where `rho` (the per-signer binding factor) is derived from the transcript of the `included` participant set and `hash_msg(msg)` [5](#0-4) . Two `sign` calls with the same seed but different `preprocesses` (different included sets, hence different `rho` values, different challenge, and different Lagrange coefficients for the signer's share) yield shares `s_i = base + rho_j·a + c_j·λ_j·x`, giving two linear equations in the secret share `x` — solving it directly. The FROST spec and in-code comments acknowledge this: "Reusing preprocesses would enable a third-party to recover your private key share" [6](#0-5) .

### Impact Explanation
Recovery of the validator's FROST secret share for the MuSig-of-FROST key used to confirm DKG key sets. Combined with threshold-1 cooperating (or compromised) shares, or used in parallel-session attacks, this degrades the threshold security of the validator-set key that authorizes `set_keys` — i.e., it undermines the security of every threshold signature the set produces, potentially enabling signature forgery for key rotation.

### Likelihood Explanation
Reachability requires the confirmer to execute `share`/`complete` for the same `attempt` with a different included-set map than an earlier invocation — e.g., a retry or a competing block carrying a different preprocess subset for the same attempt. I was not able to fully verify the call sites in `coordinator/src/tributary/handle.rs` (grep showed `DkgConfirmer`/`share` usage but the surrounding gating logic was not read), so it is unconfirmed whether a second `share` with a divergent preprocess set is practically triggerable, or whether the attempt counter rolls on any disagreement. Medium likelihood: no nonce-seed deletion or single-use guard exists in `signing_protocol.rs`, so any path that reaches `share_internal` twice with differing inputs leaks the share.

### Recommendation
Delete or rotate the `CachedPreprocesses` entry after the first `share_internal` consumption, or bind the cached-seed usage to a hash of the preprocess set and abort (fresh seed / error) if a second `sign` is attempted under the same context with different inputs. Alternatively, track a `used` flag per context and panic/err rather than re-deriving nonces.

### Proof of Concept
1. Node runs `DkgConfirmer::share(preprocesses_A, key_pair)` for `attempt = a`, producing share `σ1 = d + ρ_A·e + c_A·λ_A·x` (Schnorrkel share form; binding factor `ρ_A` and challenge `c_A` depend on the included set in `preprocesses_A`).
2. The same context `(b"DkgConfirmer", a)` still holds the seed; a second `share_internal` call (e.g., `complete` or a retried `share`) with `preprocesses_B` where the included participant set differs regenerates the identical `(d, e)` nonces from `CachedPreprocess` but computes `ρ_B`, `c_B`, `λ_B`.
3. From shares `σ1`, `σ2` and public `ρ_A, ρ_B, c_A, c_B, λ_A, λ_B` plus the public commitments `D = d·G, E = e·G` (broadcast in the preprocess), solve the two-share linear system for `x` after eliminating `d + ρ·e`: `x = ((σ1 − σ2) − (ρ_A − ρ_B)·e) / (c_A·λ_A − c_B·λ_B)`, or more robustly with `e` eliminated first via the commitment relation. Recover the Ristretto secret share `x`.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
