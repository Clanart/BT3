## Title
Escrow decrement occurs after the external transfer in `IntentGatewayV2.withdraw` (Tron fork), reintroducing the CEI violation already fixed on the main EVM contracts - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report flags Nucypher's `PoolingStakingContractV2.sol` for calling `transfer` before finishing bookkeeping, recommending the transfer be moved to the last line of each affected function. Hyperbridge's EVM Intent Gateway had exactly this class of bug in escrow release/refund and fixed it (see `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` and the corrected `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`, which decrements `_orders[...]` *before* transferring). The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still has the pre-fix ordering: it performs the native/ERC-20 `.call()` transfer first and only decrements the escrow accounting (`_orders[body.commitment][token] -= amount`) afterward, and its public `cancelOrder` entrypoint is missing the `nonReentrant` guard that the mainline contract has.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw` (lines 682-721): [1](#0-0) 
the function sets `_filled[body.commitment] = beneficiary` first, then loops over `body.tokens`, and for each token performs the external transfer (`beneficiary.call{value: amount}("")` or `token.call(transfer(...))`) **before** decrementing `_orders[body.commitment][token] -= amount`.

Compare this to the mainline EVM contract `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` (lines 390-410): [2](#0-1) 
where `_orders[body.commitment][token] = escrowed - amount` is executed **before** the transfer — the correct checks-effects-interactions (CEI) ordering that the project's own reentrancy test suite documents as a deliberate fix: [3](#0-2) 

Additionally, `evm/tron/contracts/apps/IntentGatewayV2.sol::cancelOrder` is declared `public payable` with **no `nonReentrant` modifier**: [4](#0-3) 
whereas the documented mainline signature is `function cancelOrder(...) public payable nonReentrant`.

For the same-chain cancel path, `cancelOrder` sets `beneficiary = order.user`, and only `order.user` (i.e., `msg.sender`) may call it. If `order.user` is a contract, its fallback/receive logic runs during the native-token leg of `withdraw`'s transfer loop while `_orders[commitment][token]` for tokens not yet processed in the loop (in a multi-input order) is still un-decremented, and the missing `nonReentrant` modifier on `cancelOrder` removes the outer safety net that the mainline contract relies on in addition to the `_filled` check.

### Impact Explanation
This falls under "stealing or loss of funds" via double-settlement of escrowed bridge/intent funds — a directly in-scope impact. The vulnerable ordering means the escrow ledger (`_orders[commitment][token]`) does not reflect a token's payout until after control has already been handed to an attacker-controlled address, which is exactly the invariant violation the external report calls out ("place `transfer` on the last line" / update state before external calls).

### Likelihood Explanation
Exploitability is constrained: `_filled[commitment]` is set at the top of `withdraw`, before the transfer loop, which blocks a trivial re-entrant re-cancel of the *same* commitment via `cancelOrder`'s `_filled` guard even without `nonReentrant`. I was not able to fully trace, within the remaining tool budget, whether the Tron fork's `fillOrder`/`_fillSameChain` path applies the `_filled[commitment] = msg.sender` write **before** its output-transfer loop (the way the fixed mainline `IntrinsicIntents.sol` does) or after it (the documented pre-fix behavior that enabled `testReentrancy_FeeTheft`-style escrow theft on the mainline contract before its CEI fix). Given that this Tron file otherwise mirrors the *pre-fix* `withdraw`/`cancelOrder` code and is missing `nonReentrant`, it is uncertain but plausible that the fill path has the same unfixed ordering, which would make the multi-output escrow-theft/fee-theft scenario from `IntrinsicIntentsReentrancyTest.sol` directly reproducible on this fork.

### Recommendation
1. In `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, move `_orders[body.commitment][token] -= amount;` (and the fee decrement) to before the external `.call()`/transfer, matching `IntentsBase.sol::_withdraw`.
2. Add the `nonReentrant` modifier to `cancelOrder` (and any other externally reachable entrypoint that ends in a token/native transfer) to match the mainline contract.
3. Audit and, if necessary, port the `_filled[commitment] = msg.sender` before-transfer CEI fix to the Tron fork's `fillOrder`/same-chain-fill path — confirm whether `IntrinsicIntentsReentrancyTest.sol`'s scenarios reproduce against this file specifically.
4. Add a Tron-specific reentrancy regression test (a `ReentrantBeneficiary`-style contract as `order.user`/beneficiary) exercising `cancelOrder` and `fillOrder` with multi-token orders.

### Proof of Concept
Conceptual PoC (native-token, same-chain order, multiple inputs):
1. Attacker contract `Evil` places a same-chain order with two inputs: `input[0] = 1 ETH` (native) and `input[1] = 1000 USDC`, with `order.user = address(Evil)`.
2. `Evil.cancelOrder(order, options)` is called (no `nonReentrant` blocks re-entry at the outer call).
3. Inside `withdraw`, `_filled[commitment]` is set, then the loop processes `input[0]` first: `_orders[commitment][ETH]` is still non-zero, so the check passes, and `beneficiary.call{value: 1 ether}("")` triggers `Evil.receive()`.
4. Because `_orders[commitment][USDC]` has **not yet been decremented** (the loop hasn't reached index 1), if any other publicly reachable function keyed by the same `commitment`/`token` pair reads `_orders` without going through the `_filled` guard (e.g., a future/alternate withdrawal path, or a duplicate-token entry in `order.inputs`), it would observe stale escrow accounting during the reentrant call.
5. Given tool-call limits, this PoC step was not fully validated against the Tron fork's `fillOrder` implementation; a Devin session with repo access should write a Foundry test analogous to `IntrinsicIntentsReentrancyTest.sol` targeting `evm/tron/contracts/apps/IntentGatewayV2.sol` to confirm whether a concrete double-payout is achievable end-to-end.
