### Title
Scanner reports immature coinbase outputs as spendable received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over `block.txdata` including `txdata[0]`, the coinbase transaction, and emits any coinbase outputs paying to a registered script as `ReceivedOutput`s. Coinbase outputs are unspendable until they reach 100 confirmations of maturity (Bitcoin consensus rule). Because the scanner performs no maturity check — the analog of the missing CRL-staleness check in CVE-2020-16162 — funds are reported as received that cannot actually be spent, and downstream code (`SignableTransaction::new`, `Output::balance`, scheduler planning) treats them as ordinary spendable inputs.

### Finding Description
`scan_transaction` matches outputs purely by `script_pubkey` membership in `self.scripts` and builds a `ReceivedOutput` recording only `{offset, output, outpoint}` — no notion of the output's origin or maturity state is stored. [1](#0-0) 

`scan_block` then feeds the coinbase transaction through the same path, with only a comment noting that "a post-processing pass is needed" to remove immature outputs — the check itself is absent from the API: [2](#0-1) 

Nothing in `ReceivedOutput`, `Output::read`, or the scheduling path re-validates maturity: [3](#0-2) [4](#0-3) 

If a validator set's threshold key is the miner of a block (or a coinbase pays a registered script — anyone can mine a block paying an arbitrary P2TR script), the resulting `ReceivedOutput` is accepted, persisted via `ScannerDb::save_outputs`, scheduled, and signed for. The produced spend transaction will be rejected by the Bitcoin network (invalid coinbase spend), burning a signing attempt and stalling the payment queue until the "received" output matures or is ejected.

### Impact Explanation
An unprivileged external party (any miner) can craft a coinbase output paying to Serai's registered P2TR script, causing the coordinator to report received funds that are not spendable for 100 blocks. The wallet will construct and threshold-sign a transaction spending an immature coinbase, which is consensus-invalid — wasting signing rounds and causing funds-accounting/skew between "scanned balance" and "actually spendable balance". This matches the report's class: a missing freshness/validity check lets stale/invalid credential-equivalent state (an unspendable UTXO) be accepted as valid.

### Likelihood Explanation
Requires a mined block whose coinbase pays the multisig's script — feasible for any miner, including via public mining pools paying arbitrary addresses, and guaranteed whenever Serai itself or an allied miner includes such output. Not exploitable on demand by a non-miner, hence Medium rather than High.

### Recommendation
In `scan_block`, either skip `block.txdata[0]` entirely or mark coinbase-derived `ReceivedOutput`s with a maturity height and exclude them from spending paths until confirmed 100+ blocks deep. Alternatively, enforce the check inside `SignableTransaction::new`/`multisig` by rejecting inputs whose outpoint refers to an unmatured coinbase (requires tracking coinbase-ness on `ReceivedOutput`). At minimum, perform the documented "post-processing pass" inside the library rather than delegating it to every caller.

### Proof of Concept
```rust
// networks/bitcoin/tests/wallet.rs style
let key = /* even group key */;
let mut scanner = Scanner::new(key).unwrap();

// Construct a block whose coinbase pays directly to our P2TR script
let coinbase = Transaction {
  version: Version(2),
  lock_time: LockTime::ZERO,
  input: vec![TxIn {
    previous_output: OutPoint::null(),          // coinbase marker
    script_sig: ScriptBuf::from_bytes(vec![0x01]),
    sequence: Sequence::MAX,
    witness: Witness::default(),
  }],
  output: vec![TxOut {
    value: Amount::from_sat(50_0000_0000),
    script_pubkey: p2tr_script_buf(key).unwrap(), // pays to the multisig
  }],
};
let block = Block { header: /* valid header */, txdata: vec![coinbase] };

let outputs = scanner.scan_block(&block);
assert_eq!(outputs.len(), 1);                    // reported as received
// outputs[0] is a coinbase output: unspendable for 100 blocks,
// yet SignableTransaction::new(vec![outputs[0]], ...) will accept it
// and TransactionSignMachine will sign a consensus-invalid spend.
```

Root cause is that `scan_block` never distinguishes `txdata[0]` from ordinary transactions, and `ReceivedOutput` carries no field recording coinbase provenance, so no later stage can detect the violation either.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
