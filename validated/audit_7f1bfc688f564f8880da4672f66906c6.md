### Title
`ThresholdKeys::new` derives the committed `group_key` from only participants `1..=t`, so a key can be "committed" whose actual shares cannot produce valid signatures - ([File: crypto/dkg/src/lib.rs])

### Summary
Analogous to `enableUniswapV3Launch` gating launch on the proxy `unitPrice >= thresholdPrice` instead of the actual ETH raised, `ThresholdKeys::new` "commits" the group key — the identity under which funds are later received and signatures must verify — by interpolating only the verification shares of participants `1..=t`, while validating the remaining `n - t` shares only by count and index range. If the `n` verification shares do not lie on a single degree `(t-1)` polynomial, the committed `group_key` is only consistent with the subset `{1, ..., t}`; any other quorum produces signature shares that individually verify yet aggregate to a signature that fails verification under `group_key`. The result is a key which is treated as established but which cannot actually sign — funds received under it are unspendable, the same "insolvency" outcome as a premature Uniswap launch.

### Finding Description
`ThresholdKeys::new` checks only that `verification_shares.len() == n` and that no participant index exceeds `n`. It then computes the group key by Lagrange-interpolating the shares of participants `1..=t` only:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [1](#0-0) [2](#0-1) 

There is no check that the remaining shares `t+1..=n` are consistent with the polynomial implied by the first `t`. At signing time, `ThresholdKeys::view` interpolates each included participant's verification share and offset independently, so every individual FROST share still passes its per-share check, and `AlgorithmSignatureMachine::complete` sums the shares and calls `verify(view.group_key(), ...)` — which fails because `sum(s_i)` corresponds to the key interpolated from the *actual* signing set, not the key interpolated from `1..=t`. The protocol committed a group key without "enough backing" to guarantee signability by arbitrary quorums — precisely the launch-without-sufficient-ETH shape.

Untrusted bytes reach this constructor via `ThresholdKeys::read`, which deserializes `n` arbitrary group elements as verification shares and calls `ThresholdKeys::new` with no consistency check: [3](#0-2) 

and it is used on externally supplied key material in `processor/src/key_gen.rs`.

### Impact Explanation
A `ThresholdKeys` accepted with inconsistent verification shares yields a `group_key` that equals the secret interpolated only for the subset `{1..=t}`. Any quorum missing even one of those participants produces a signature for a *different* interpolated key, so `complete` returns `FrostError` after blame, or worse, every honest quorum believes it holds a share of `group_key` while funds addressed to `group_key` are only spendable by that single fixed subset — an effective loss/lock of funds matching the report's "contract becomes insolvent" outcome. [4](#0-3) 

### Likelihood Explanation
Reachability requires feeding crafted verification shares through `ThresholdKeys::read`/`ThresholdKeys::new` or a key-generation path that skips share-consistency verification. Honest PedPoP output is consistent, so the bug is latent rather than triggered by well-formed inputs — but the gate (count + index bounds) is formally insufficient, exactly as `unitPrice >= thresholdPrice` was insufficient for `token1Amount` raised, and any deserialization path accepting externally supplied `ThresholdKeys` exposes it.

### Recommendation
As the report recommends gating launch on `totalSupply` rather than the price proxy, `group_key` should not be derived from a privileged subset. Either compute `group_key` from all `n` verification shares in a way that detects inconsistency (e.g., verify that every subset's interpolation agrees, or require callers to supply the group key/commitment-0 separately and check `group_key == sum_i in any t-subset`), or document/enforce that `ThresholdKeys` may only be built from verified VSS output and have `read` reject keys where participants `t+1..=n` are inconsistent with the committed polynomial.

### Proof of Concept
```rust
// t = 2, n = 3. Honest polynomial would give verification shares on one line.
// Construct shares where Y1, Y2 lie on a polynomial with constant term A,
// but Y3 is arbitrary — i.e., inconsistent.
let y1 = C::generator() * s1;
let y2 = C::generator() * s2;
let y3 = C::generator() * C::F::random(rng); // not on the same polynomial

let keys = ThresholdKeys::new(
  ThresholdParams::new(2, 3, Participant::new(1).unwrap()).unwrap(),
  Interpolation::Lagrange,
  Zeroizing::new(s1),
  HashMap::from([(p1, y1), (p2, y2), (p3, y3)]),
).unwrap();

// group_key was interpolated ONLY from {1, 2}
assert_eq!(keys.group_key(), interpolate([y1, y2]));

// A quorum of {2, 3} (or {1, 3}) passes ThresholdKeys::view and FROST per-share
// verification, but the summed share verifies against interpolate({Y2, Y3})
// or interpolate({Y1, Y3}) != group_key:
//   AlgorithmSignatureMachine::complete -> algorithm.verify(view.group_key(), Rs, sum) -> None
// The committed group key cannot be signed for by most quorums: funds locked.
```

The asymmetry is visible directly in the constructor: `group_key` uses only `1..=t` [2](#0-1) , while `view` happily builds a `ThresholdView` for any valid `included` set [5](#0-4) , and the aggregate is checked against the `1..=t`-derived key [4](#0-3) .
