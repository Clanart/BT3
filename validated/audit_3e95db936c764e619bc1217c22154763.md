### Title
Scanner reports dust-value outputs as received that the wallet can never spend - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` accepts any output paying to a registered script_pubkey regardless of its value, including outputs below the dust threshold (`DUST = 546` sats). `SignableTransaction::new` enforces `DustPayment` on outgoing payments but performs no minimum-value check on inputs, so a dust output can be recorded by the vault as received yet is permanently unspendable — spending it costs more in fees than its value, and any attempt that does include it will fail `NotEnoughFunds` or produce a transaction relay rejects.

### Finding Description
In the Y2K report, a deposit accepted under an old `relayerFee` becomes unprocessable after the fee increases, freezing the queue because the queue-processing loop never re-validates the stored amount. The analogous shape in `bitcoin-serai`: outputs are accepted/registered into the "received" set based solely on `script_pubkey` matching, while the spendability constraint (minimum economic value) is only enforced on a different side of the flow.

`Scanner::scan_transaction` matches `self.scripts.get(&output.script_pubkey)` and pushes a `ReceivedOutput` unconditionally — there is no `output.value >= DUST` (or fee-viability) check:

```rust
// networks/bitcoin/src/wallet/mod.rs
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

`SignableTransaction::new` only checks dust for `payments` (`if *amount < DUST { Err(DustPayment) }`), never for `inputs`. An attacker can send an output of e.g. 1 sat (or any amount below the fee needed to spend a Taproot input, ~ 57.5 vB × fee rate) to the vault's registered address. The scanner reports it as received funds; the wallet either cannot spend it economically or, if blindly included in a batch spend, causes `NotEnoughFunds`/`TooLowFee` or an unrelayable transaction — a per-input analogue of the halted-queue/frozen-funds condition, with no rejection path in the scanner.

### Impact Explanation
Any unprivileged party can permanently poison the vault's UTXO set with dust outputs credited to it. These outputs are counted as received (e.g., credited to a depositor on Serai) yet can never be spent without burning more value than they contain — funds reported received that are not spendable. If the coordinator naively aggregates all scanned inputs into a `SignableTransaction`, inclusion of dust inputs reduces the effective fee/change and can abort transaction construction entirely.

### Likelihood Explanation
Sending dust to a known Taproot address is cheap, permissionless, and repeatable. Vault deposit addresses are public, so any user (or attacker grieving the protocol) can trigger this with a single on-chain transaction.

### Recommendation
In `Scanner::scan_transaction` (or in a post-processing pass, as is already done conceptually for coinbase maturity), filter out outputs whose `value` is below `DUST` or below the marginal fee required to spend a Taproot input at a reference fee rate. Alternatively, have `SignableTransaction::new` reject or skip inputs where `input.output.value < DUST`, so unscannable-value outputs never enter the spend path.

### Proof of Concept
1. Attacker obtains a vault deposit script_pubkey (any registered offset address).
2. Attacker broadcasts a Bitcoin transaction with an output paying 100 sats (< `DUST`) to that script.
3. `Scanner::scan_transaction` returns a `ReceivedOutput` for it; the protocol credits it as received.
4. `SignableTransaction::new` either errors with `NotEnoughFunds` when the dust input can't cover its own spend weight (~57.5 vB × `fee_per_vbyte`), or constructs a transaction whose fee is insufficient for relay — the "deposit" is frozen, mirroring the halted queue in the original report.
