### Title
Unhandled `IndexError` in CLVM canonical-encoding check causes spend-bundle-triggered mempool processing crash - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` in `chia/full_node/mempool_manager.py` parses an attacker-supplied CLVM atom length prefix and reads follow-on bytes from `clvm_buffer` without ever checking that the buffer actually contains that many bytes, directly analogous to the Linux RSVP classifier's unchecked-offset read in CVE-2023-42755 (reading past the end of an untrusted buffer because a length/pointer field is trusted without a bounds check).

### Finding Description
`is_atom_canonical()` decodes the CLVM atom-length prefix from `clvm_buffer[offset]` and then loops `prefix_len` times, incrementing `offset` and reading `clvm_buffer[offset]` each time to build `atom_len`, with **no check that `offset` stays within `len(clvm_buffer)`**: [1](#0-0) 

This function is invoked from `is_clvm_canonical()`, which walks an entire CLVM-serialized buffer token by token, again without validating that `offset` is in range before indexing `clvm_buffer[offset]`: [2](#0-1) 

`is_clvm_canonical()` is called directly on **untrusted, attacker-controlled** data — the `puzzle_reveal` and `solution` of every coin spend in a submitted `SpendBundle` — inside `MempoolManager.validate_spend_bundle()`, the core mempool-admission path reachable by any unprivileged spend-bundle submitter: [3](#0-2) 

A crafted buffer such as a single byte `0xF0` (which signals a 3-byte trailing length prefix per the bit-pattern table in `is_atom_canonical`) but with no following bytes will cause the loop to index past the end of the buffer, raising an unhandled `IndexError` instead of returning `False`/`(atom_len, False)` gracefully. No `try/except` wraps this call in `validate_spend_bundle()`, so the exception propagates out of mempool validation.

### Impact Explanation
This is directly analogous to the CVE's bug class: an out-of-bounds read caused by trusting a length/pointer field derived from untrusted input without validating it against the actual buffer bounds. Here the "buffer" is the coin spend's `puzzle_reveal`/`solution` bytes and the "pointer" is the running `offset` in `is_atom_canonical`/`is_clvm_canonical`. Since this code path executes for every coin spend of every submitted spend bundle during mempool admission, a single malicious spend bundle can raise an unhandled `IndexError` during `validate_spend_bundle()`, which is exactly the "spend-triggered transaction-processing halt" impact category called out in scope (denial of service against mempool processing, matching the kernel bug's "local user can crash the system" DoS characterization).

### Likelihood Explanation
High reachability: any unprivileged spend-bundle submitter (wallet client, RPC caller, or peer relaying a transaction) can trigger this by constructing a `CoinSpend` with a deliberately truncated/malformed puzzle_reveal or solution buffer whose trailing bytes are shorter than the atom length prefix claims. The check happens unconditionally for every coin spend before any other validation short-circuits it, so the crafted payload does not need to pass any other check first.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (raising/returning a "non-canonical"/error result rather than indexing out of range), and add a bounds check in `is_clvm_canonical()`'s main loop before reading `clvm_buffer[offset]`. Alternatively, wrap the entire `is_clvm_canonical()` call site in `validate_spend_bundle()` with an explicit `try/except IndexError` that treats it as `Err.INVALID_COIN_SOLUTION`, matching how other malformed-encoding cases are already rejected.

### Proof of Concept
1. Construct a `CoinSpend` whose `solution` (or `puzzle_reveal`) bytes are exactly `b"\xf0"` (a single byte). Per the bit pattern in `is_atom_canonical`, `0xF0 & 0b11111000 == 0b11110000`, selecting the branch with `prefix_len = 3`.
2. Wrap it in a `SpendBundle` and submit it via `MempoolManager.add_spend_bundle()` (e.g., through the wallet RPC "push_tx" or peer transaction relay path) with matching `SpendBundleConditions`.
3. `validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.solution))`, which calls `is_atom_canonical(clvm_buffer, 0)`.
4. Inside `is_atom_canonical`, the loop executes `offset += 1; atom_len |= clvm_buffer[offset]` — on the first iteration `offset` becomes `1`, but `len(clvm_buffer) == 1`, so `clvm_buffer[1]` raises `IndexError: index out of range`.
5. Because no exception handler wraps this call in `validate_spend_bundle()`, the `IndexError` propagates out of the mempool-admission coroutine, disrupting spend-bundle processing for that call path. [1](#0-0) [2](#0-1) [3](#0-2)

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
