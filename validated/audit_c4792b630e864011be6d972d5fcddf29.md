Confirmed: `CW721ERC721Pointer.sol`'s `transferFrom`, `approve`, and `setApprovalForAll` never check that `msg.sender` is the token owner or an approved operator before calling `_execute`. The underlying CosmWasm `transfer_nft`/`approve`/`approve_all` execute call runs with the pointer contract's own module-level authority — the CW20/CW721 pointer's `_execute` uses the EVM caller association just to build the payload, but the actual authorization check that should gate "is `msg.sender` allowed to move this specific token" is entirely absent in the Solidity wrapper.### Title
`CW721ERC721Pointer` transferFrom/approve/setApprovalForAll allow any caller to move or approve tokens they don't own — missing operator/owner check (IDOR) - (File: `contracts/src/CW721ERC721Pointer.sol`)

### Summary
The ERC721-compatible pointer contract that wraps a CosmWasm CW721 collection does not validate that `msg.sender` is the token owner or an approved operator before executing state-changing NFT actions. This is the same bug class as the AVideo IDOR: an authenticated actor (any EVM account) can act on a resource (an NFT owned by someone else) because the code checks that the *target resource* is in the expected state, but never checks that the *caller* is authorized to act on it.

### Finding Description
`transferFrom` in `contracts/src/CW721ERC721Pointer.sol` only verifies that the `from` argument actually owns the token: [1](#0-0) 
It never checks `msg.sender == from`, `msg.sender == getApproved(tokenId)`, or `isApprovedForAll(from, msg.sender)` — the standard ERC721 authorization checks. Compare this with the reference/local `ERC721.sol` implementation used elsewhere in the repo, which explicitly gates `transferFrom` behind `_isApprovedOrOwner(from, msg.sender, id)`: [2](#0-1) 

Because `CW721ERC721Pointer.transferFrom` omits this, any EVM account can call `pointer.transferFrom(victimAddress, attackerAddress, tokenId)` for any token owned by `victimAddress`, and it will succeed as long as `from == ownerOf(tokenId)` (which it trivially is, since `from` is attacker-supplied and just needs to match the real owner).

The call is routed through the wasmd precompile's `execute`, which derives the CosmWasm `Sender` from the pointer contract's own association (not from a per-token permission check), so the CW721 contract executes `transfer_nft` as if it were an authorized call: [3](#0-2) 

The same missing-authorization pattern also affects `approve` (any address can grant itself/anyone approval over any tokenId without being the owner or an approved operator) and `setApprovalForAll` operates on the caller's own address so it is not directly exploitable, but `approve` is: [4](#0-3) 

The existing unit tests only exercise the happy path where the pranked caller happens to be the real owner, and never test that a third-party attacker is rejected, so this gap is not covered: [5](#0-4) 

### Impact Explanation
Any EVM transaction sender can steal or move any NFT pointed to by a `CW721ERC721Pointer` contract by calling `transferFrom(victim, attacker, tokenId)`, and can also self-grant `approve` rights over tokens they do not own/control. This is a direct unauthorized-transfer vulnerability via a CW↔EVM pointer contract, resulting in permanent, uncompensated loss of NFT ownership for any victim whose CW721 collection has been wrapped by this pointer — a critical fund/asset loss scenario reachable by any public EVM RPC client submitting a single transaction.

### Likelihood Explanation
Trivially reachable: any address can call `transferFrom` on a deployed `CW721ERC721Pointer` for any `tokenId`/owner pair without any special privilege, funds, or setup other than knowing (or discovering on-chain, which is public) the current owner and token id. No governance, validator collusion, or race condition is required.

### Recommendation
Add explicit ERC721 authorization checks in `CW721ERC721Pointer.sol` mirroring `ERC721._isApprovedOrOwner`: in `transferFrom`, require that `msg.sender == from || msg.sender == getApproved(tokenId) || isApprovedForAll(from, msg.sender)`. In `approve`, require that `msg.sender == ownerOf(tokenId) || isApprovedForAll(ownerOf(tokenId), msg.sender)` before calling `_execute`.

### Proof of Concept
1. Victim owns `tokenId=1` in a CW721 collection wrapped by `CW721ERC721Pointer` at address `P`.
2. Attacker (unrelated EOA, no approval) calls `P.transferFrom(victim, attacker, 1)`.
3. `require(from == ownerOf(tokenId), ...)` passes because `from` is set to the real owner (`victim`), and no check exists on `msg.sender`.
4. `_execute` delegatecalls the wasmd precompile's `execute("transfer_nft", {recipient: attacker, token_id: "1"})` against the underlying CW721 contract, transferring the NFT to the attacker without the victim's consent.

    function _isApprovedOrOwner(
        address owner,
        address spender,
        uint id
    ) internal view returns (bool) {
        return (spender == owner ||
        isApprovedForAll[owner][spender] ||
            spender == _approvals[id]);
    }

    function transferFrom(address from, address to, uint id) public {
        require(from == _ownerOf[id], "from != owner");
        require(to != address(0), "transfer to zero address");

        require(_isApprovedOrOwner(from, msg.sender, id), "not authorized");

        _balanceOf[from]--;
        _balanceOf[to]++;
        _ownerOf[id] = to;

        delete _approvals[id];

        emit Transfer(from, to, id);
    }
