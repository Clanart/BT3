### Title
Confidence Interval Check Not Applied to DIA Oracle Feeds in Price Resolution Pipeline - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
### Finding Description
The oracle price-resolution pipeline in `v0-4-market.clar` applies confidence-interval validation only to one of the two supported price-feed types. `resolve-pyth` explicitly calls `check-confidence` on every price it returns: [1](#0-0) 

but `resolve-dia`, used for USDH/zUSDH pricing, returns its value directly with no equivalent confidence gate at all: [2](#0-1) 

Both feed types converge into the same `resolve-price-feed` dispatcher and then into the shared `price-resolve` function, which only enforces `oracle-price-legal` (price > 0) and `oracle-timestamp-fresh` (staleness/monotonicity) — neither of which substitutes for a confidence check: [3](#0-2) [4](#0-3) 

This mirrors the reported bug class exactly: a validator (`check-confidence`, analogous to `inputValidatorMiddleware()`) is applied to one code path (Pyth-sourced handlers) but silently absent from a structurally parallel path (DIA-sourced handlers) that feeds into the same downstream pricing/health logic used for collateral valuation and LTV checks.

### Impact Explanation
`ERR-PRICE-CONFIDENCE-LOW` (`check-confidence`) exists specifically to reject prices whose uncertainty band exceeds `max-confidence-ratio` (10% by default), guarding against using an unreliable/wide-confidence price for USD valuation: [5](#0-4) 

Since USDH/zUSDH pricing bypasses this gate entirely, a low-confidence (high-uncertainty) DIA value would still be accepted as long as it is positive and passes the staleness/monotonic timestamp check, and would be used directly in USD-denominated collateral/debt valuation for borrow, health-factor, and liquidation calculations. If the DIA-reported value diverges from the true market price during a period of high uncertainty, that stale/uncertain value directly changes the computed health factor: it could permit undercollateralized borrows against USDH/zUSDH collateral (theft of funds at rest) or trigger/avoid liquidations at a wrong price. This lands in the Critical impact class — direct theft of user funds via mispriced USDH collateral/debt.

### Likelihood Explanation
This does not require any DAO misconfiguration or third-party price manipulation of Pyth's data — the root cause is Zest's own code path structure: the same protective check that was deliberately added for Pyth was never mirrored for DIA in the same file. It would trigger whenever a DIA-sourced USDH price update has abnormal uncertainty (e.g., during a market-stress event or depeg-adjacent volatility), which is a realistic, non-adversarial-dependent occurrence given USDH is a stablecoin subject to depeg risk. Likelihood is Medium-to-High given USDH/zUSDH are active collateral/debt assets in the market.

### Recommendation
Since DIA's oracle interface (`get-value`) does not expose a confidence/uncertainty field, either: (1) integrate a DIA oracle variant that reports confidence and apply the equivalent of `check-confidence` to it inside `resolve-dia`, mirroring `resolve-pyth`; or (2) if no confidence data is available from DIA, compensate by tightening `max-staleness` for the USDH feed and/or adding a maximum deviation check against a secondary reference price before accepting a DIA value in `price-resolve`, so DIA-sourced prices receive validation parity with Pyth-sourced prices rather than only the generic staleness/positivity checks.

### Proof of Concept
1. DIA's storage returns `{ value, timestamp }` for `USDH/USD` with a value that has drifted from spot due to elevated market uncertainty, but is still positive and has a fresh/monotonic timestamp.
2. A user calls `market.borrow` (or `collateral-add`) with USDH/zUSDH; `price-resolve` invokes `resolve-price-feed` → `resolve-dia`, which returns the value unchecked for confidence: [6](#0-5) 
3. `price-resolve`'s only gates (`oracle-price-legal`, `oracle-timestamp-fresh`) pass, so the uncertain price is accepted as authoritative: [7](#0-6) 
4. The health-factor/LTV computation downstream uses this value directly, producing a wrong (favorable-to-borrower or unfairly liquidatable) health verdict for USDH/zUSDH positions — whereas the same scenario for a Pyth-priced asset would have been rejected by `ERR-PRICE-CONFIDENCE-LOW`.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
