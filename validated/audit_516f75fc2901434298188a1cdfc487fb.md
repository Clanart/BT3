### Title
Copilot conflict-resolution reassembly trusts unverified hunk count from AI response, silently deleting unresolved conflict regions - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
`reassembleResolvedFile` is designed to be called only when the model's `hunks` array corresponds 1:1, in order, with every conflict marker block found in the original file. However, nothing in the pipeline — not `parseCopilotConflictResolution`, not `buildConflictContext`, not `reassembleResolutions` — verifies that the number of hunks the model returned matches the number of conflict blocks `extractConflictHunks` found on disk. If the AI response contains fewer hunks than actual conflicts (e.g., due to model truncation, context-window pressure from attacker-supplied content, or a model that "merges" what it perceives as duplicate conflicts), later conflict blocks in the file are silently stripped of their markers with no replacement content, deleting both `ours` and `theirs` sides of that conflict without warning.

### Finding Description
`extractConflictHunks` ( [1](#0-0) ) independently scans the on-disk file and produces the hunk list sent to Copilot as context. Separately, `parseCopilotConflictResolution` validates the model's JSON response but only checks per-hunk `resolvedContent` for leftover conflict markers [2](#0-1)  — it never checks `rawHunks.length` against the number of conflicts actually present in that file.

`reassembleResolvedFile` then walks the raw file looking for marker blocks and replaces each one with `hunkResolutions[hunkIndex]`, advancing `hunkIndex` for every block encountered, matching purely by order: [3](#0-2) 
When `hunkIndex >= hunkResolutions.length` (fewer AI-provided hunks than actual conflict blocks), the `if (hunkIndex < hunkResolutions.length)` branch is skipped entirely — the conflict marker lines are still stripped out (via `i = closingIndex + 1`), but *no* content is spliced in for that block, silently deleting both sides of that unresolved conflict from the final file.

This mirrors the reported bug class exactly: a downstream function (`reassembleResolvedFile`) is invoked under an assumption (hunk-count parity with the source file) that its caller never enforces, and the guard that does exist (`parseCopilotConflictResolution`'s marker-in-resolvedContent check) operates at the wrong granularity (per returned hunk) to catch this class of drift (missing hunks).

### Impact Explanation
Because the merge/rebase/cherry-pick source content comes from a fetched/cloned remote branch that an attacker can fully control (e.g., a malicious upstream branch designed to produce many, large, or adversarially-formatted conflicts against the user's local changes), an attacker can increase the likelihood of hitting model truncation or miscounting on a specific file, causing entire hunks of legitimate code (potentially including the user's own security-relevant changes) to vanish from the file with no error surfaced to the user. The result dialog only tracks files Copilot explicitly reports as "skipped" [4](#0-3)  — it has no way to detect a *partial*, silent hunk drop inside a file it believes was fully resolved. The corrupted content is then written to disk and staged/committed [5](#0-4) , meaning the user's commit silently loses code without their awareness — matching the "silent corruption of what the user commits" impact category.

### Likelihood Explanation
This requires no local access, malware, or credentials — only that the user runs the built-in Copilot-assisted conflict resolution feature against a branch/repository the attacker influences (a normal collaboration or upstream-merge scenario). It depends on the AI model actually miscounting hunks, which is a plausible but non-deterministic failure mode (large/complex conflict sets, prompt-injection-style content in commit messages/PR bodies also included in context, or model quirks) rather than a guaranteed 100%-reliable trigger, so likelihood is moderate rather than certain — I could not directly execute the Copilot integration to observe live model behavior, so this analysis is based on static code review of the validation and reassembly logic.

### Recommendation
In `reassembleResolutions` (or before calling `reassembleResolvedFile`), assert that `raw.hunks.length` equals `ctx.hunks.length` (the count independently computed by `extractConflictHunks` for that file) and throw a `CopilotValidationError` on mismatch instead of silently truncating. Additionally, `reassembleResolvedFile` should track whether every discovered conflict block received a corresponding resolution and fail loudly (or fall back to leaving the original markers) rather than dropping content when `hunkIndex >= hunkResolutions.length`.
