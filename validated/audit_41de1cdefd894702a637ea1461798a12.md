### Title
Deterministic preprocess reuse across validator sets enables recovery of the coordinator's MuSig/FROST private key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches the FROST preprocess seed in the coordinator database under a key derived solely from `context`. For `DkgConfirmer`, the context is `(b"DkgConfirmer", self.attempt)` — it does **not** include the tributary's genesis, the validator set, the participant list, or the message being signed. Consequently, whenever the same validator key signs for DKG confirmation attempt `N` under two distinct `TributarySpec`s (e.g., before and after a validator-set rotation / new genesis, or any second tributary sharing the coordinator DB), the identical 32-byte ChaCha seed is reloaded via `AlgorithmSignMachine::from_cache`, regenerating the *identical* nonces, which are then used to sign a *different* `set_keys_message` (the message embeds the set). Two published signature shares with the same nonce over different challenges yield the private key — which here is the validator's root-of-trust MuSig key. [1](#0-0) 

### Finding Description
The cached preprocess is stored under `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` and reloaded with `CachedPreprocesses::get(self.txn, &self.context)` where `context = (b"DkgConfirmer", attempt: u32)` [2](#0-1) . The `DkgConfirmer::signing_protocol` constructor defines the context as `(b"DkgConfirmer", self.attempt)` only [3](#0-2) .

`AlgorithmSignMachine::from_cache` feeds the cached seed into `seeded_preprocess`, which instantiates `ChaCha20Rng::from_seed(*seed.0)` and derives the nonces deterministically via `Commitments::new(rng, params.keys.original_secret_share(), ...)` [4](#0-3) . The nonce scalars are `C::random_nonce(secret_share, rng)` = `hash_to_F(b"nonce", seed_bytes || secret_repr)` [5](#0-4) . For MuSig, `original_secret_share` is the validator's own private key, so the same seed + same key produces the same nonces regardless of which set/participants are being signed for.

The signed message is `set_keys_message(&self.spec.set(), removed, key_pair)` [6](#0-5) , which differs per set. The safety argument in the module doc-comment claims "nonces being context-bound under a BFT protocol" prevents reuse [7](#0-6)  — but the context only binds the *attempt counter*, not the set/genesis, so the binding fails across specs. Note also that `spec`, `removed`, `participants`, and `key_pair` are all absent from the cache key even though all of them feed into the machine construction.

### Impact Explanation
An observer who sees two Schnorr signature shares (or the two completed MuSig signatures, published to Substrate) produced with the same nonce `k` over different challenges `c1, c2` recovers the private scalar via `s = (s1 - s2) / (c1 - c2)`. Since `DkgConfirmer` signs with `self.key` — the validator's long-lived Ristretto secret key used as the coordinator's root of trust — this is full private-key recovery, not merely a leaked ephemeral share. Compromise of this key enables forging DKG confirmations and subverting the validator set's trust root. Per the accepted-impact criteria this is "key share recovery" / secret leakage from publicly observable outputs. Severity: High.

### Likelihood Explanation
The collision requires the same validator key to produce a `DkgConfirmer` preprocess/share for the same `attempt` value under a different `TributarySpec` sharing the same coordinator DB. This happens naturally whenever a second tributary (new validator set, new genesis) runs a DKG confirmation — attempt numbering restarts at 0 while `CachedPreprocesses` rows persist. The doc-comment's own safety analysis only considers re-execution within one BFT context and acknowledges (TODO, lines 50–54) that commitment-matching checks are not yet implemented. No attacker action is needed beyond observing on-chain data; an attacker who can influence DKG re-attempts or set rotation timing can actively induce the collision. Caveat: I could not fully confirm that all `TributarySpec`s share one coordinator DB namespace for `CachedPreprocesses` — if each spec has an isolated DB, the collision would require a spec reuse path I did not identify.

### Recommendation
Bind the full signing context into the cache key: include `self.spec.genesis()` (or `self.spec.set()`), the participant set digest, and the intended `key_pair`/message digest in `context`, e.g. `(b"DkgConfirmer", spec.genesis(), attempt, msg_hash)` in `coordinator/src/tributary/signing_protocol.rs:275`. Additionally, before publishing a share, verify on-chain that the preprocess commitments match the presumed preprocess (the code's own TODO at lines 50–54), and clear/regenerate the cached preprocess when `participants` or `removed` differ from the set under which it was created.

### Proof of Concept
1. Coordinator participates in tributary A (genesis `G_A`), DKG confirmation attempt 0. `signing_protocol()` builds context `("DkgConfirmer", 0)`; `CachedPreprocesses::get` is empty, so a fresh `OsRng` seed `S` is XOR-encrypted and stored under `("DkgConfirmer", 0)` (lines 123–135). `share()` signs `msg_A = set_keys_message(set_A, removed_A, key_pair_A)` with nonce `k = hash_to_F(nonce, chacha(S) || key)`; share `s_A` is published.
2. Later, the same coordinator (same `key`) runs tributary B (genesis `G_B`, rotated set), DKG confirmation attempt 0. Context is again `("DkgConfirmer", 0)` → cached seed `S` is loaded (line 137), `from_cache` regenerates the same `k` (`crypto/frost/src/sign.rs:127–132`), and `share()` signs `msg_B = set_keys_message(set_B, removed_B, key_pair_B)` ≠ `msg_A`; share `s_B` is published with the same nonce commitments.
3. From the two public shares/signatures: `key = (s_A − s_B) · (c_A − c_B)⁻¹ mod ℓ` where `c_A, c_B` are the respective Schnorr challenges — direct private-key recovery via textbook nonce reuse. No tool execution was possible; derivation rests on `signing_protocol.rs:88,123–145,274–301` and `crypto/frost/src/sign.rs:121–145,268–274`.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }

  fn random_nonce<R: RngCore + CryptoRng>(
    secret: &Zeroizing<Self::F>,
    rng: &mut R,
  ) -> Zeroizing<Self::F> {
    let mut seed = Zeroizing::new(vec![0; 32]);
    rng.fill_bytes(seed.as_mut());

    let mut repr = secret.to_repr();

    // Perform rejection sampling until we reach a non-zero nonce
    // While the IETF spec doesn't explicitly require this, generating a zero nonce will produce
    // commitments which will be rejected for being zero (and if they were used, leak the secret
    // share)
    // Rejection sampling here will prevent an honest participant from ever generating 'malicious'
    // values and ensure safety
    let mut res;
    while {
      seed.extend(repr.as_ref());
      res = Zeroizing::new(<Self as Curve>::hash_to_F(b"nonce", seed.deref()));
      res.ct_eq(&Self::F::ZERO).into()
    } {
      seed = Zeroizing::new(vec![0; 32]);
      rng.fill_bytes(&mut seed);
    }
    repr.as_mut().zeroize();

    res
  }
