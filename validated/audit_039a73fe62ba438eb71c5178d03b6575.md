### Title
Insecure prefix-only path-containment check in `resolveWithin` allows escaping the intended root directory - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin` (and its `resolveWithinPosix`/`resolveWithinWin32` variants) is Desktop's shared guard for "keep this resolved path inside this root directory," used to sandbox file access derived from repository-relative paths coming from git/AI-conflict-resolution flows and from deep-link file paths. The containment check uses a bare string `startsWith` comparison between the resolved real path and the real root path, with no trailing separator boundary check. This is structurally the same class of bug as the reported `pricePerShare` issue: a calculation/comparison is performed against the wrong basis (a raw string prefix instead of a path-segment-bounded root), so it silently produces a wrong result for a specific, predictable class of inputs.

### Finding Description
`_resolveWithin` computes: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`realResolved.startsWith(realRoot)` treats `realRoot` as a literal string prefix rather than a path segment boundary. If `realRoot` is e.g. `/Users/victim/Documents/GitHub/project`, then a resolved path of `/Users/victim/Documents/GitHub/project-secrets/config.json` **passes** the check, even though `project-secrets` is a completely different, sibling directory outside `project`. No `path.sep` (or root+sep) check is performed after `startsWith`, so any sibling directory whose name happens to have the repo's directory name as a string prefix is treated as "inside the root."

This directly parallels the reported bug: the correct invariant ("stay within this exact directory") is checked using the wrong granularity (raw string prefix vs. directory-boundary-aware prefix), producing systematically wrong results for a predictable input shape — just as `pricePerShare` used vault decimals instead of asset decimals and produced systematically wrong results whenever the two differed.

Two real call sites make attacker-influenced paths reach this check:
- `openRepositoryFromUrl` resolves a deep-link `filepath` (attacker-controlled, arrives via `x-github-client://openRepo/...` style URLs a user clicks) against the repository root and, if within, calls `shell.showItemInFolder(resolved)`: [2](#0-1) 
- `buildConflictContext` resolves each conflicted file's repository-relative `path` (sourced from git conflict/merge state, i.e., content that traces back to a remote/collaborator-controlled commit) against `workingDirectory`, and on success reads the file's full content into `rawContent`, which is later sent to the Copilot API as conflict-resolution context: [3](#0-2) 

Existing guards do not stop this: the null-byte check and `isAbsolute` rejection in `openRepositoryFromUrl` only block absolute paths, not relative paths that resolve (via `..` segments, which `path.resolve` legitimately collapses) into a sibling directory whose name shares the root's name as a prefix. The symlink-based tests in the test suite (`app/test/unit/path-test.ts`) only cover cases where `realpath` escapes to an unrelated directory tree that does *not* share a string prefix with the root — they do not cover the "sibling directory with shared name prefix" case, so this bypass is not exercised or caught by current tests.

### Impact Explanation
- Via `openRepositoryFromUrl` → `shell.showItemInFolder`: a crafted deep link opened by the user can make Desktop reveal/select a file located in a sibling directory outside the intended repository (e.g. `.../GitHub/myrepo-private/secret.txt` when the repo is `.../GitHub/myrepo`), disclosing the existence and location of files the attacker should not be able to probe from a link click.
- Via `buildConflictContext` → Copilot conflict resolution: if a maliciously crafted git history/merge presents a conflicted-file path that, after `resolveWithin` incorrectly succeeds, points to a file in a sibling directory outside the repository working tree, that file's full contents (`rawContent`) are read from disk and passed into the AI conflict-resolution context that is sent to an external service — i.e., an out-of-repo file read plus exfiltration of that content to a third party.

This corrupts the specific value the guard is supposed to protect — "the path is guaranteed to stay within the repository root" — for any target whose directory name has the repository directory name as a prefix, which is a common and easily-guessable naming pattern (`repo`, `repo-old`, `repo-backup`, `repo-private`, `repo2`, etc.).

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or guess a sibling directory name sharing the root's name as a prefix, and requires no local access, admin rights, or pre-existing malware — only a user clicking a deep link (for the `openRepositoryFromUrl` path) or the presence of a maliciously-shaped conflict path reaching `buildConflictContext`. The prefix-collision naming pattern (`project`, `project-backup`, `project2`) is common enough in real developer environments that this is a plausible, not merely theoretical, bypass. The `buildConflictContext` path's reachability depends on whether git's own path-safety rules for indexed/worktree entries can ever produce a `file.path` that, after joining with `workingDirectory`, resolves outside the working directory into a same-prefix sibling — this specific reachability was not fully confirmed within the available tooling and would need dynamic verification.

### Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to compare on path-segment boundaries rather than raw string prefix, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
```
(using the appropriate `sep` for the `posix`/`win32` variant), and add a regression test with a sibling directory whose name shares the root directory's name as a string prefix.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
