## Title
Unhandled `ValueError` in `determine_coin_type` when syncing a revoked/cleared Verified Credential permanently halts wallet coin-state processing - (File: `chia/wallet/wallet_state_manager.py`)

### Summary
`WalletStateManager.determine_coin_type` calls `VerifiedCredential.get_next_from_coin_spend(coin_spend)` with no exception handling whenever an incoming coin's parent puzzle is identified as a VC via `VerifiedCredential.is_vc()`: [1](#0-0) 

This mirrors the report's root cause exactly: a piece of on-chain identity/ownership state (there, `ownerOf()`; here, the reconstructed `VerifiedCredential`) is derived by a function that unconditionally reverts/raises once the underlying singleton has been "burned" (self-revoked or backdoor-revoked by its DID provider), and that function is called from a shared processing path with no fallback, instead of the safe pattern used elsewhere in the same codebase.

### Finding Description
`VerifiedCredential.get_next_from_coin_spend` is documented as failing specifically when a VC has been revoked: [2](#0-1) 

It explicitly raises `ValueError` in two revocation-related cases — when the metadata layer indicates the credential was cleared, and when the reconstructed VC puzzle hash doesn't match (which is exactly what happens after `activate_backdoor`/self-revoke spends): [3](#0-2) [4](#0-3) 

The self-revoke and backdoor-revoke (provider "yoink") spends are first-class, intentionally reachable actions any VC holder or its DID provider can submit as an ordinary spend bundle: [5](#0-4) 

The codebase already recognizes that `get_next_from_coin_spend` must be defensively wrapped when syncing, and does so correctly in `VCWallet.coin_added`: [6](#0-5) 

However, `WalletStateManager.determine_coin_type` — which is the dispatcher used to classify every newly-seen coin during coin-state sync (CATs, NFTs, DIDs, clawback coins, VCs, PlotNFTs, in this order) — calls the same method with no try/except: [1](#0-0) 

Because `is_vc()` only validates the *puzzle structure* of the parent spend (it does not simulate whether the spend actually produced a valid child VC), any coin whose parent spend used the VC puzzle framework but revoked/cleared the credential will pass `is_vc() == True` and then cause `get_next_from_coin_spend` to raise, uncaught, inside `determine_coin_type`.

### Impact Explanation
This is directly analogous to the reported bug class: a party who legitimately holds a VC-based singleton (either the VC owner via self-revoke, or the DID "authorized provider" via the backdoor) can produce a valid, minimal-cost spend that is trivially recognized as a VC-shaped puzzle but that deterministically raises inside the wallet's coin-classification code path. If `determine_coin_type` is invoked without an enclosing try/except somewhere in the coin-state processing loop (as is the pattern for every other coin type handled in this function, none of which wrap their `identify`/parsing calls at this level either), the unhandled exception aborts processing of the batch of coin states being synced, which can include unrelated coins belonging to the user (their own XCH, CATs, NFTs, DIDs). This can prevent the wallet from advancing its sync state and thus from being able to select coins or push new spends until the batch is manually worked around, which is the same "spend-triggered transaction-processing halt" category called out as an acceptable analog for the reported bug (funds become practically unspendable because syncing itself throws).

### Likelihood Explanation
Likelihood is limited by two factors that could not be fully confirmed from the index: (1) whether the specific loop that invokes `determine_coin_type` for a batch of `CoinState` updates has a surrounding try/except that isolates per-coin failures (this determines whether the blast radius is "one wallet's whole sync" vs. just "one coin's classification"), and (2) whether an attacker can cheaply cause an *unrelated* victim wallet to receive/observe such a revoked-VC coin as part of the same state batch (e.g., via a shared subscription, an offer counter-party, or a hinted/interested coin). Because VC coin hints/subscriptions are typically wallet-specific (the coin's inner puzzle hash must belong to the wallet, per `VCWallet.identify`), this is likely most exploitable by a VC-holding party against their own wallet, or by a DID "provider" against the sync of a wallet that is tracking VCs it authorized — a narrower blast radius than the original UniV3 report, but still a legitimate wallet-side denial-of-service triggered purely by an on-chain spend.

### Recommendation
Wrap the `VerifiedCredential.get_next_from_coin_spend(coin_spend)` call in `WalletStateManager.determine_coin_type` in the same defensive `try/except Exception` pattern already used in `VCWallet.coin_added`, logging the revocation and returning `(None, None)` (treating it as "not a trackable VC" for classification purposes) rather than letting the exception propagate out of the coin-classification dispatcher.

### Proof of Concept
Not independently reproduced in this session (no execution environment available); the analysis is based on static code tracing:
1. Attacker/VC holder creates a VC and later spends it via `VerifiedCredential.activate_backdoor(...)` (self-revoke or provider-revoke), producing a `CoinSpend` whose puzzle reveal still uncurries as a VC-shaped singleton (`is_vc()` returns `True`) but whose child does not.
2. When a wallet's sync path processes this coin via `WalletStateManager.determine_coin_type`, `VerifiedCredential.get_next_from_coin_spend(coin_spend)` raises `ValueError` (per [3](#0-2)  or [4](#0-3) ), matching the test assertions that explicitly expect this exception after a yoink/clear spend: [7](#0-6)  and [8](#0-7) .
3. Whether this propagates further and halts a larger sync batch (as opposed to being caught by an outer handler not covered in the excerpts reviewed) would need to be confirmed by tracing the caller of `determine_coin_type`; this could not be fully verified with the tools available and should be validated in a Devin session with full repository access.
