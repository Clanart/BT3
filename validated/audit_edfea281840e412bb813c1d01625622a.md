### Title
Cached FROST/MuSig preprocess seed is keyed only by `(b"DkgConfirmer", attempt)` and reused across validator sets, causing nonce reuse and validator key-share recovery — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically regenerates FROST nonces from a 32-byte seed stored in `CachedPreprocesses`, whose DB key is the SCALE encoding of `context = (b"DkgConfirmer", self.attempt)` only. The DB key format (`serai_db_key` = `db_dst || item_dst || encode(args)`) contains no tributary/genesis/validator-set qualifier. When the coordinator confirms a DKG for a different validator set (new `TributarySpec`, different `participants`, different `removed`, different `set` in `set_keys_message`) at the same `attempt` value (e.g. `attempt = 0`), the identical nonce seed is loaded and `AlgorithmSignMachine::from_cache` re-derives the identical nonces. Each execution publishes a signature share `s = d + b·e + c·λ_i·x_i` with the same nonce `d + b·e` but a different binding factor `b`, different aggregate-key context, and different challenge `c`, because `participants`/`msg` differ. Two published shares therefore suffice to solve for and recover the validator's private MuSig key share — the classic one-time-nonce reuse ("stale-state use-after-free") analog of CVE-2019-5850.

### Finding Description
- `DkgConfirmer::signing_protocol` builds `context = (b"DkgConfirmer", self.attempt)` at coordinator/src/tributary/signing_protocol.rs:275, omitting `spec.genesis()`, the validator set, and `removed`.
- `CachedPreprocesses::get(self.txn, &self.context)` at line 123/137 loads any previously stored seed for that context; `create_db!` keys are `serai_db_key("SigningProtocolDb", "CachedPreprocesses", context.encode())` (common/db/src/create_db.rs:2-10, 39-70), so two distinct tributaries processed by the same coordinator DB collide on identical `(label, attempt)` keys.
- `AlgorithmSignMachine::from_cache` (crypto/frost/src/sign.rs:268-274) → `seeded_preprocess` (lines 121-144) seeds `ChaCha20Rng` with the cached seed, regenerating identical `nonces` and identical published `commitments`.
- `share_internal` (lines 150-181) rebuilds `keys`/`participants` from the *current* `spec` and calls `machine.sign(preprocesses, msg)` where `msg = set_keys_message(&self.spec.set(), &removed, key_pair)` (lines 296-300) — different per set.
- In `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:283-410), binding factors come from `B.calculate_binding_factors` over a rho transcript containing `group_key`, `hash_msg(msg)` and the preprocess hash (lines 362-371), and the effective nonce is `base + rho·actual` (lines 386-396). With the same raw nonces but different `group_key`/`msg`/participants, each share is `s = k + c·λ·x` with the same `k` and different public `c`, `R`, so `x = (s1 − s2) / ((c1−c2)·λ)` leaks the validator's key share.

### Impact Explanation
Signature shares are published in tributary `Transaction`s, so they are public. Anyone observing shares for two DKG confirmations performed under the same `attempt` counter for different validator sets recovers a validator's MuSig secret share, enabling forgery of that validator's share in future DKG confirmations — undermining the on-chain root-of-trust confirmation for arbitrary key pairs. This is key-share recovery, the highest-impact outcome class.

### Likelihood Explanation
Triggering requires the coordinator to process two `DkgConfirmer` flows with the same `attempt` but different `spec`/`participants`/`removed` or a different `KeyPair`, which occurs naturally across validator-set rotations (each new set starts attempts at 0) sharing one `raw_db`. No malicious validator is needed; an unprivileged observer of the published shares performs the recovery offline. One caveat I could not fully verify within the iteration budget: whether the coordinator ever runs two distinct `TributarySpec`s against the same `CachedPreprocesses` table, and whether `complete`'s second `share_internal` call can be reached with a differing `key_pair`. The header comment (lines 25-54) explicitly acknowledges the nonce-reuse danger but only analyzes same-chain message divergence, not cross-context key collision.

### Recommendation
Bind the cached-preprocess context to everything that parameterizes the signing session: include `spec.genesis()` (or `spec.set()`), the full `participants` list hash, and `removed` in `context`. Additionally, track a "consumed" flag: once `share_internal` runs for a context, refuse to sign again unless the `(participants, msg)` hash matches the first use, enforcing the documented single-use invariant of `CachedPreprocess`.

### Proof of Concept
```
1. Coordinator confirms DKG for validator set A (attempt 0):
   context = ("DkgConfirmer", 0) → seed S stored; nonce commitments C_A, share
   s_A = (d + b_A·e) + c_A·λ_i·x_i  published.
2. Validator set rotates; new TributarySpec B (different participants,
   different genesis). DKG attempt 0 runs again:
   context encodes identically → CachedPreprocesses::get returns S.
   from_cache regenerates d, e. New keys/participants ⇒ different aggregate
   key, different msg = set_keys_message(set_B, removed_B, key_pair_B).
   Share s_B = (d + b_B·e) + c_B·λ_i·x_i published with the same raw nonces.
3. Observer computes the effective nonce K_A = D + b_A·E from public
   commitments and binding factors; verifies R share equations, then solves
   x_i = (s_A − s_B − (K_A − K_B)) / ((c_A − c_B)·λ_i) mod l — or, when
   participants are identical (only key_pair differs), K_A = K_B so
   x_i = (s_A − s_B) / ((c_A − c_B)·λ_i).
   Result: validator's private MuSig share recovered.
```
