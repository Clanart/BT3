## Title
Global (non-per-IP) DoS of QUIC connection-tracker capacity via slow-handshake burst — (File: `streamer/src/nonblocking/quic.rs`)

## Summary
An unprivileged, unstaked attacker can open a burst of QUIC connections and deliberately withhold handshake-completion packets, holding each `ClientConnectionTracker` slot for the full `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) before it is released and immediately repeating the cycle. Because both the overall and per-IP rate limiters only debit tokens on the *success* path, an attacker who never completes the handshake evades both, letting them monopolize the global `max_concurrent_connections` headroom.

## Finding Description
In `run_server`, before a `ClientConnectionTracker` slot is granted, the code checks `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0)  and `rate_limiter.is_allowed(&incoming.remote_address().ip())` [2](#0-1) . Both are peek-only reads — `current_tokens()` merely loads the bucket state without consuming [3](#0-2) , and `is_allowed` returns `true` whenever no record exists yet for the IP [4](#0-3) .

Tokens are only actually consumed inside `setup_connection`, and only after the handshake succeeds: `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` are called solely inside the `Ok(new_connection)` branch of the awaited `connecting` result [5](#0-4) .

The only gate that bounds concurrent in-flight (incomplete) handshakes is `ClientConnectionTracker::new`, which compares a single global `open_connections` counter against `max_concurrent_connections`, with no per-IP partitioning [6](#0-5) . Once granted, the slot is held for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2 seconds) via `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await` [7](#0-6) , with the timeout constant fixed at 2s [8](#0-7) . `max_concurrent_connections` is sized with only 25% headroom above the steady-state cap, specifically to accommodate in-flight handshakes: `self.config.max_staked_connections * 5 / 4` [9](#0-8) . This headroom is global, not per-IP.

The in-code comment acknowledges the intended design ("shed fast", "global rate-limiter", "rate-limit abusive peers by ... ip") [10](#0-9) , but as shown, neither limiter is actually exercised against attempts that never complete the handshake — they only throttle the rate of *successful* completions, not the count of concurrently outstanding, stalled attempts.

## Impact Explanation
This falls within the "QUIC/TPU ... non-RPC remote exhaustion/degradation" scope. A single unprivileged, unstaked attacker can occupy a meaningful fraction of the shared, global `max_concurrent_connections` pool indefinitely by repeatedly reserving slots for ~2s and re-triggering as soon as each times out, degrading the server's ability to admit genuinely new (staked or unstaked) connections during the attack window. The severity is bounded — it is a slot-holding/exhaustion issue at the connection-admission layer, not a crash, and per-peer/stream-level protections (`max_connections_per_peer`, stream throttling) still apply to established connections — but it is a real resource-exhaustion/availability degradation, not fund loss or consensus impact.

## Likelihood Explanation
Likelihood is moderate-to-high. No authentication, stake, or special network position is required; the attacker only needs to send valid-looking QUIC Initial packets (causing quinn to yield `Incoming` objects) and then withhold subsequent handshake packets. No IP spoofing is required — a client that simply stalls after the Initial flight suffices. As demonstrated by tracing the code, neither `overall_connection_rate_limiter` nor the per-IP `rate_limiter` is ever debited for such stalled attempts, since both consumption calls (`consume_tokens`, `register_connection`) live only on the post-handshake success path [11](#0-10) , while the pre-admission checks are non-mutating peeks [3](#0-2) [4](#0-3) . The attack is repeatable indefinitely, bounded only by the attacker's ability to generate new `Incoming` streams.

## Recommendation
- Consume/reserve tokens (or otherwise account for in-flight attempts) from the per-IP and/or overall rate limiters at admission time (before/at `ClientConnectionTracker::new`), not only on handshake success, so stalled attempts are throttled the same as completed ones.
- Introduce a per-IP cap on concurrent outstanding (`ClientConnectionTracker`-held) connection attempts, independent of the existing per-IP completed-connection rate limiter.
- Consider shrinking `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` or making it adaptive under load, and/or dynamically scaling handshake headroom based on observed abuse.

## Proof of Concept
Using the existing test harness pattern (`test_client_connection_tracker`), spin up `setup_quic_server`, then repeatedly open QUIC client endpoints/raw UDP sockets that send only an Initial-shaped datagram and never let `connecting.await` resolve, in bursts sized close to `qos.max_concurrent_connections()`. Concurrently attempt a normal legitimate `endpoint.connect(...).await`. Measure `stats.refused_connections_too_many_open_connections` increasing and legitimate-connection latency/failure rate rising while the attacker's stalled attempts occupy slots for the ~2s `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` window, and confirm `stats.connection_rate_limited_per_ipaddr` / `stats.connection_rate_limited_across_all` remain at 0 for the attacker's stalled attempts, proving the rate limiters were never triggered — consistent with the code paths at [12](#0-11)  and [13](#0-12) .
