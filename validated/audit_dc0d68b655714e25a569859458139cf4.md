### Title
IBC receive-packet callback treats an unpacked-return `approve()` failure as fatal, permanently freezing user funds at an unrecoverable isolated address - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`ContractKeeper.IBCReceivePacketCallback` calls `approve()` on the ERC20 contract behind a registered token pair and strictly requires the return data to ABI-decode into a `bool`. Non-standard ERC20 tokens (e.g., USDT-style tokens that omit the boolean return value on `approve`, the exact bug class from the referenced report) will make this decode fail, aborting the callback after the underlying IBC transfer has already credited the deterministically-derived, key-less "isolated address."

### Finding Description
In `IBCReceivePacketCallback` [1](#0-0) , the destination-callback flow:

1. Computes an `isolatedAddr` deterministically from `packet.GetDestChannel()` and `data.Sender` via `types.GenerateIsolatedAddress` and requires the packet receiver to equal it [2](#0-1) . This address has no known private key — it exists purely so the callback-executed contract can be authorized to pull the funds via `transferFrom`.
2. By the time this callback runs, the underlying ICS-20 transfer has already unescrowed/minted the tokens to that `receiver` address (this is standard ibc-go callback-middleware ordering: the callback executes *after* the transfer completes, and a callback failure does not roll back the transfer).
3. The keeper then calls `approve()` on `tokenPair.GetERC20Contract()` on behalf of the isolated address and unconditionally requires the return value to decode as `bool`: [3](#0-2) 

If the registered ERC20 contract for that token pair does not return a value from `approve` (the exact "missing return value" weird-ERC20 behavior described in the source report, e.g. USDT-style contracts), `res.Ret` will be empty and `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` will fail, causing `IBCReceivePacketCallback` to return an error at line 207. Because the transfer already completed before this point, the tokens sitting at `isolatedAddr` cannot be moved: nobody holds the isolated address's private key, and the only intended path to spend those funds (approve + `transferFrom` executed inside this same callback) is permanently and deterministically blocked for that token, for every future receive on that channel/sender pair.

This is the direct analog of the Sherlock M-1 finding: `approve()` is called and its return value is trusted/required in a strict ABI-typed way without accounting for tokens that don't return a boolean, causing the call path to permanently fail instead of gracefully degrading.

### Impact Explanation
Unlike the original Sentiment V2 bug (which merely prevented a SuperPool from being *created*, a availability/DoS-level issue), the Cosmos EVM analog results in **permanent loss of user funds**: the IBC transfer has already delivered value to `isolatedAddr` before the approve step runs, and once the approve-decode fails there is no code path or key that can ever move those tokens out. This matches the allowed Critical impact class of "permanent freezing, locking ... of user funds ... or token-pair-backed balances," since it affects ERC20-representation balances that are 1:1 backed by IBC-escrowed/minted coins.

### Likelihood Explanation
Triggering requires only that:
- A token pair's underlying ERC20 contract (registered, e.g., via the native ERC20 registration proposal path) is a non-standard token that omits the `approve` return value — a real-world, common pattern (USDT and USDT-like forks), not a contrived/malicious contract requirement.
- Any unprivileged user sends an ICS-20 transfer with IBC callback middleware memo (`dest_callback`) targeting a contract, for that token.

No privileged actor, malicious relayer, or governance misconfiguration beyond ordinary token-pair registration is needed; a legitimately whitelisted "weird" ERC20 is sufficient, mirroring the exact conditions called out in the referenced report (USDT-class tokens explicitly stated to be supported).

### Recommendation
- Do not require ABI-decoding a `bool` from `approve`'s return data. Treat a successful (non-reverting) EVM call as success regardless of return payload length, similar to `SafeERC20.forceApprove` semantics (treat empty return data as success, only decode when data is present and use it if valid).
- More importantly, decouple the fund-transfer-in step from the callback so that callback failure cannot leave funds unrecoverably stranded at `isolatedAddr` — e.g., validate the destination contract/token pair "approve-compatibility" ahead of finalizing the transfer, or provide a governance/permissionless recovery/sweep path for `isolatedAddr` balances when the destination callback errors.

### Proof of Concept
1. Register a native ERC20 token pair whose contract implements `approve` in the USDT style (updates storage/emits `Approval` but returns no data, i.e., function signature `approve(address,uint256)` with no `returns (bool)`).
2. A user submits an ICS-20 transfer to this chain carrying a `dest_callback` memo targeting some receiving contract, with `receiver` set to the correctly derived isolated address.
3. IBC transfer completes: `coin` is unescrowed/minted to `isolatedAddr`.
4. `IBCReceivePacketCallback` runs, calls `approve` on the token contract; `res.Ret` is empty.
5. `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` returns an error, so the function returns `ErrAllowanceFailed` and the destination-callback logic (and thus the `transferFrom` pulling funds into the target contract) never executes.
6. The tokens remain permanently held by `isolatedAddr`, which has no corresponding private key and is not reachable by any subsequent user-initiated transaction, since the only intended pathway to spend from it is the just-failed callback logic.
