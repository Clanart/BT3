### Title
Divergent royalty-fee formulas in `NFTWallet` can miscalculate royalty amounts, mirroring Overlay's liquidation/fee split bug - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
Chia's NFT offer/royalty logic contains two independent implementations for computing the royalty due on a trade: `compute_royalty_amount()` (used when the *maker* actually constructs on-chain royalty payments in `make_nft1_offer`) and the static `royalty_calculation()` (used by the RPC endpoint `nft_calculate_royalties` and by taker-side tooling/tests to determine what should be paid). Like the Overlay `liquidatable()` vs `liquidationFeeRate` split — one formula gates eligibility/expectation, a different formula performs the actual value movement — these two chia formulas can diverge.

### Finding Description
`compute_royalty_amount()` is the authoritative, "safe" implementation used to build the actual `CreateCoin` royalty outputs in `NFTWallet.make_nft1_offer`: [1](#0-0) 
It performs integer division as `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`, and validates `percentage <= MAX_ROYALTY_BASIS_POINTS` and `royalty < abs(offered_amount)`, raising `ValueError` otherwise. It is invoked when actually constructing royalty payment conditions: [2](#0-1) 

By contrast, `royalty_calculation()` — used for the wallet RPC `nft_calculate_royalties` (surfaced to CLI/offer-preview tooling that a taker relies on to know what to pay) — uses the *same* division formula but has none of the same guard rails: [3](#0-2) [4](#0-3) 

The two functions can produce different results in edge cases (e.g., percentages at or above `MAX_ROYALTY_BASIS_POINTS`, or amounts where `royalty >= abs(offered_amount)`), because `royalty_calculation()` performs no bounds checks and silently returns a raw computed integer while `compute_royalty_amount()` rejects the same inputs outright. This is analogous to the Overlay bug where `liquidatable()` used `maintenanceMarginFraction` to gate an action while the actual value transferred used the independent `liquidationFeeRate`.

### Impact Explanation
This does not directly enable unauthorized coin movement on its own: the actual conditions enforced on-chain during offer settlement (`trade_prices_list`, `CreateCoin` outputs) are still generated exclusively via `compute_royalty_amount()` in `make_nft1_offer`, and any CLVM-level settlement mismatch would simply cause the trade solution to fail rather than let value leak silently. The primary exposure is that RPC/CLI tooling (`nft_calculate_royalties`, `calculate_nft_royalty_amount` in `wallet_funcs.py`) that a taker relies on to preview "how much do I need to pay" can present an inconsistent (unbounded) figure compared to what the maker's actual offer construction logic would compute/require, which could mislead a taker into constructing an incorrect take-offer amount or trusting a bad estimate for a malicious offer that exploits a boundary percentage the safe function would have rejected.

### Likelihood Explanation
Low–moderate. It requires an NFT with an edge-case royalty percentage or amount near the guard-rail boundaries encoded only in `compute_royalty_amount`. Since CLVM-level settlement is still gated by the correct calculation path in `make_nft1_offer`, a mismatch is more likely to manifest as a confusing/incorrect preview or a failed take-offer rather than fund loss — I could not find a code path where `royalty_calculation()`'s output is fed directly into an unguarded on-chain spend, so I cannot confirm concrete fund loss from the codebase alone.

### Recommendation
Consolidate on a single royalty-calculation function (`compute_royalty_amount`) for both the RPC preview (`NFTWallet.royalty_calculation` / `nft_calculate_royalties`) and the actual offer-construction path, so that eligibility/preview calculations and actual value-moving calculations can never diverge — mirroring the Overlay fix, which unified how liquidation eligibility and liquidation-fee amounts are derived from the same accounting basis.

### Proof of Concept
Not independently verifiable from static analysis alone. A concrete PoC would require constructing an NFT offer with a royalty `percentage` at/above `MAX_ROYALTY_BASIS_POINTS` (10000) or an `amount`/`royalty_split` combination where `compute_royalty_amount` raises `ValueError`, then calling `nft_calculate_royalties` (which uses `royalty_calculation`) to observe it return a non-error, differing numeric result — demonstrating that RPC-reported expected royalty and actually-enforceable royalty are computed by different, non-equivalent code paths.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```

```python
    def royalty_calculation(
        royalty_assets_dict: dict[Any, tuple[Any, uint16]],
        fungible_asset_dict: dict[Any, uint64],
    ) -> dict[Any, list[dict[str, Any]]]:
        summary_dict: dict[Any, list[dict[str, Any]]] = {}
        for id, royalty_info in royalty_assets_dict.items():
            address, percentage = royalty_info
            summary_dict[id] = []
            for name, amount in fungible_asset_dict.items():

                    {
                        "asset": name,
                        "address": address,
                        "amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
                    }
                )

        return summary_dict
```
