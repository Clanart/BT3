### Title
Silent re-association and remote URL rewrite of a tracked `GitHubRepository` based on mutable owner/name instead of a stable identity - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The Sherlock report's broken invariant is that `GoatV1Pair.takeOverPool()` identifies "the legitimate pool" purely by loosely-checked, attacker-influenced parameters instead of a value that can't be forged, letting an attacker silently take over state that belongs to someone else. The same class of bug exists in GitHub Desktop's GitHub-repository association logic: Desktop re-binds a tracked local repository's `GitHubRepository` metadata — and can silently rewrite the local `origin` remote URL — by matching on the mutable `owner/name` path parsed out of the existing remote URL, never checking GitHub's stable numeric repository id. If that owner/name path is later claimed by a different GitHub repository (a classic "repo/account name recycling" scenario, e.g. the legitimate owner renames or deletes their account/repo and someone else claims the freed name), Desktop's background refresh logic will happily adopt the new repository as if it were the same one the user has been working with, with no prompt to the user.

### Finding Description
`matchGitHubRepository` in `app/src/lib/repository-matching.ts:29-46` derives `{ owner, name, account }` purely by parsing the current git remote URL string (`parseRemote(remote)`), it never consults or validates against any persisted, stable repository identifier. [1](#0-0) 

`AppStore.repositoryWithRefreshedGitHubRepository` uses this owner/name match to call `api.fetchRepository(owner, name)` and — as long as the API call succeeds — unconditionally re-associates the local `Repository` with whatever repo the API now returns for that path, via `repoStore.upsertGitHubRepository(endpoint, apiRepo)` and `repoStore.setGitHubRepository(repository, ghRepo)`. There is no comparison of the previously-known GitHub repository id (`repository.gitHubRepository.dbID`/API `id`) against the freshly fetched `apiRepo.id` before accepting the swap. [2](#0-1) 

Compounding this, `updateRemoteUrl` will also silently rewrite the tracked git remote's URL — no user confirmation dialog — whenever the old `gitHubRepository.cloneURL` still matches the current remote (i.e. the user hasn't manually customized it) and the new `apiRepo.clone_url` differs but keeps the same protocol: [3](#0-2) 

Notably, Desktop *does* have a user-facing guard for a related case — when an upstream (fork-parent) remote unexpectedly points elsewhere, it shows the `UpstreamAlreadyExists` dialog asking the user to confirm before updating: [4](#0-3) 

But no equivalent confirmation exists for the *default/origin* remote's GitHub repository association being silently swapped to a different underlying repository object that just happens to share the same `owner/name` string. This mirrors the audit finding: L481/L496 in `GoatV1Pair` check *some* parameters (token amounts) but omit the value (virtual ETH) that actually defines pool identity/ownership; here Desktop checks *some* things (protocol, URL string shape) but omits the value that actually defines repository identity (the immutable numeric GitHub repo id).

### Impact Explanation
Once the local repository's `gitHubRepository` metadata is repointed to an attacker-controlled repository that has reclaimed the old `owner/name` path:
- `refreshBranchProtectionState` and permission checks (`hasWritePermission`) start reflecting the attacker's repository rather than the user's actual project, which can cause Desktop's push-safety UI (e.g. protected-branch warnings) to reflect the wrong repository's rules.
- Notifications, PR/issue metadata (`fetchIssues`, PR checks) sourced via `fetchRepository`/related API calls will surface attacker-controlled content inside Desktop's UI for what the user believes is their own project, including links and PR branches — if the user then fetches/checks out a PR ref from what Desktop presents as "their" repository, they can pull attacker-authored commits into their working copy believing it's trusted upstream content.
- Because `updateRemoteUrl` can rewrite the actual `git remote set-url` value without any prompt, the local git configuration itself — the thing that determines where the user's next `push`/`fetch` actually goes — can be altered silently in the background refresh path, not just Desktop's own bookkeeping.

This matches the "silent corruption of what the user commits or pushes" / "attacker controls a GitHub API object or git remote response" impact bucket, since the trigger is entirely the content of `api.fetchRepository()`'s response for a reused owner/name path.

### Likelihood Explanation
This requires an external precondition equivalent to a well-documented "repo/account name recycling" (repojacking) scenario: the legitimate owner must first rename/delete the account or repository, freeing the `owner/name` path, and an attacker must then claim that same path with their own repository before Desktop's periodic `repositoryWithRefreshedGitHubRepository` refresh runs again for the affected local clone. This is a real, externally-triggerable condition (GitHub allows username/repo-name reuse after deletion or rename) but is not something Desktop itself creates — Desktop's bug is that once this condition occurs, it has zero defenses (no id-based identity check, no user prompt) against silently trusting the new owner of that path, unlike the analogous fork-upstream-mismatch case which does prompt the user.

### Recommendation
Before accepting a refreshed `apiRepo` as the "same" GitHub repository in `repositoryWithRefreshedGitHubRepository`/`upsertGitHubRepository`, compare the previously stored numeric GitHub repository `id` against the newly fetched `apiRepo.id`. If they differ, treat this the same way the existing `UpstreamAlreadyExists` flow does — surface a warning dialog to the user before updating `_repositoryWithRefreshedGitHubRepository`'s association or calling `updateRemoteUrl`'s `setRemoteURL`, rather than silently repointing local state and the local git remote to a different underlying repository.

### Proof of Concept
1. User A creates `github.com/alice/project`, clones it in Desktop; Desktop stores its `GitHubRepository` (id=123, owner=alice, name=project) and `origin` remote `https://github.com/alice/project.git`.
2. Alice renames her GitHub account to `alice2` (or deletes the repo/account). The `alice` login/`alice/project` path becomes available.
3. Attacker registers the `alice` login and creates a repository named `project` (`github.com/alice/project`, a different repo id, e.g. 999).
4. On Desktop's next background refresh of user A's repository list, `repositoryWithRefreshedGitHubRepository` (`app-store.ts:4874`) parses the still-unchanged remote URL, extracts `owner=alice, name=project` via `matchGitHubRepository`, and calls `api.fetchRepository('alice', 'project')`, which now returns the attacker's repo (id 999).
5. Because there's no `id` comparison, `repoStore.upsertGitHubRepository`/`setGitHubRepository` silently re-associates the local repository's `gitHubRepository` field with the attacker's repo, and `updateRemoteUrl` may rewrite `origin` to the attacker's `clone_url` if it differs in string form — all with no dialog shown to user A, who continues working believing nothing changed.

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
