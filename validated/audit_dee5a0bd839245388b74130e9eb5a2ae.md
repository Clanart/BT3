### Title
Unbounded quadratic sibling-data construction in `Offer.to_valid_spend()` lets a crafted offer exhaust a counterparty's memory/CPU - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.to_valid_spend()` builds, for every offered coin of a given non-XCH asset, a "siblings" data set describing *every other* offered coin of that same asset, including a full hex serialization of each sibling's `CoinSpend`. This is done eagerly for all coins before any CLVM execution or cost check, giving `O(n^2)` string construction (each element itself proportional to spend size) with no upper bound on `n`, the number of coins offered for one asset in an `Offer`. This mirrors the `Ash.Filter.Runtime` bug class (CVE-2026-82742): eager, unbounded cross-expansion over a "to-many" collection (here, offered coins per asset) performed before any short-circuiting validation, driven entirely by attacker-controlled input (an offer file).

### Finding Description
`Offer.to_valid_spend()` iterates the offered coins per requested asset and, for CAT/CR-CAT-style assets (`asset_id` truthy), constructs `siblings`, `sibling_spends`, `sibling_puzzles`, and `sibling_solutions` strings by nested-looping over all other offered coins of that asset: [1](#0-0) 

For each `coin` in `offered_coins`, the inner loop iterates `offered_coins` again and, for every non-matching `sibling_coin`, appends the full hex-encoded serialization of that sibling's `CoinSpend` (`bytes(coin_to_spend_dict[sibling_coin]).hex()`) plus its disassembled puzzle and solution strings: [2](#0-1) 

This happens inside `to_valid_spend`, which is invoked before any CLVM execution/cost accounting takes place for the final combined spend bundle, and there is no cap anywhere in `chia/wallet/trading/offer.py` on the number of coins that can be offered for a single asset in an `Offer` (`get_offered_coins()` simply collects every matching addition per asset with no size limit): [3](#0-2) 

`to_valid_spend()` is reachable purely from processing an externally supplied offer — i.e., `respond_to_offer()` (taking a maker's offer) calls it on the aggregated `complete_offer` after decompressing/aggregating both sides' spend bundles, prior to broadcasting anything: [4](#0-3) 

Because a maker fully controls the shape of an offer they publish (including how many small CAT/CR-CAT coins they choose to offer for the same asset id, and how large the individual `CoinSpend` puzzle reveals/solutions are, e.g. via CR-CAT proof-of-inclusion data), a taker who calls `take_offer`/`respond_to_offer` on a maliciously crafted offer triggers `O(n^2)` string concatenation and hex-encoding of spend bytes purely as a side effect of accepting/validating the offer locally, well before mempool cost limits would ever bound the resulting spend bundle.

### Impact Explanation
An attacker (an untrusted offer counterparty) can publish/share an offer with a very large number of offered coins for the same CAT/CR-CAT asset id (each carrying a substantial puzzle reveal/solution, e.g. large CR-CAT proof-of-inclusion programs). When a victim wallet processes that offer via `take_offer`/`respond_to_offer`, `to_valid_spend()` performs unbounded quadratic work (CPU for repeated hex/disassembly and memory for the resulting large `siblings`/`sibling_spends`/`sibling_puzzles`/`sibling_solutions` strings) before any spend is ever pushed to the mempool or subjected to CLVM cost limits. This can stall or crash the victim's wallet process (denial of service against wallet state processing), matching the "spend-triggered transaction-processing halt" impact category. It does not directly move funds, but it is a concrete resource-exhaustion vector triggered by a single attacker-controlled offer, analogous in mechanism to the reported `Ash.Filter.Runtime` combinatorial blow-up.

### Likelihood Explanation
Likelihood is moderate: constructing an offer with many small coins for one asset (and, to maximize per-sibling cost, CR-CAT coins carrying large proof data) is straightforward for any wallet user/offer creator, and no consensus or mempool limit constrains offer construction before a taker processes it locally. The taker only needs to call `take_offer` (a common, expected wallet action) on the malicious offer to trigger the unbounded work.

### Recommendation
Bound the number of offered coins per asset that `to_valid_spend()` will process (reject/flag offers exceeding a sane per-asset coin count before building sibling data), and/or restructure the sibling construction to avoid `O(n^2)` full-spend serialization — e.g., precompute/cache each coin's hex-encoded spend once and reuse it across iterations instead of iterating pairs, and enforce an early size/cost estimate on the aggregate offer before deep processing, mirroring the fix pattern in the referenced CVE (lazy/streamed evaluation with short-circuiting rather than eager full materialization).

### Proof of Concept
1. Craft an `Offer` (via `Offer.notarize_payments` + a `WalletSpendBundle`) that requests a small payment but offers e.g. 5,000 distinct CAT coins for the same CAT asset id, each backed by a `CoinSpend` whose solution is padded to be large (e.g., a CR-CAT spend with a sizeable `proof_of_inclusions` program).
2. Encode this as a bech32 offer string and send it to a victim.
3. Victim calls the wallet RPC `take_offer` with this offer string, which routes to `TradeManager.respond_to_offer()` and ultimately `Offer.to_valid_spend()`. [5](#0-4) 
4. Observe that `to_valid_spend()`'s nested loop over `offered_coins` (~5,000² ≈ 25,000,000 iterations, each doing hex-encoding/disassembly of a sizeable `CoinSpend`) consumes excessive CPU/memory on the victim's node before any CLVM execution or mempool cost check occurs. [1](#0-0) 

*Note: I was unable to independently verify (within this session) any hard system-level cap on offer file size or coin count enforced earlier in the RPC path (e.g., in `take_offer` request parsing) that might reduce practical severity; a full assessment would benefit from tracing the complete `take_offer` RPC entry point in a Devin session with file access to confirm no such cap exists before `to_valid_spend()` is reached.*

    def _get_offered_coins(self) -> dict[bytes32 | None, list[Coin]]:
        offered_coins: dict[bytes32 | None, list[Coin]] = {}

        cost_left = INFINITE_COST
        for parent_spend in self._bundle.coin_spends:
            coins_for_this_spend: list[Coin] = []

            parent_puzzle: UnknownPuzzle = UnknownPuzzle(known_program=parent_spend.puzzle_reveal)
            parent_solution = Program.from_serialized(parent_spend.solution)
            additions: list[Coin] = self._additions[parent_spend.coin]

            puzzle_driver = match_puzzle(parent_puzzle)
            if puzzle_driver is not None:
                asset_id = create_asset_id(puzzle_driver)
                inner_puzzle: Program | None = get_inner_puzzle(puzzle_driver, parent_puzzle, parent_solution)
                inner_solution: Program | None = get_inner_solution(puzzle_driver, parent_solution)
                assert inner_puzzle is not None and inner_solution is not None

                # We're going to look at the conditions created by the inner puzzle
                puzzle_cost, conditions = inner_puzzle.run_with_cost(cost_left, inner_solution)
                assert cost_left >= puzzle_cost
                cost_left -= puzzle_cost
                expected_num_matches: int = 0
                offered_amounts: list[int] = []
                for condition in conditions.as_iter():
                    if condition.first() == 51 and condition.rest().first() == OFFER_MOD_HASH:
                        expected_num_matches += 1
                        offered_amounts.append(condition.rest().rest().first().as_int())

                # Start by filtering additions that match the amount
                matching_spend_additions = [a for a in additions if a.amount in offered_amounts]

                if len(matching_spend_additions) == expected_num_matches:
                    coins_for_this_spend.extend(matching_spend_additions)
                # We didn't quite get there so now lets narrow it down by puzzle hash
                else:
                    # If we narrowed down too much, we can't trust the amounts so start over with all additions
                    if len(matching_spend_additions) < expected_num_matches:
                        matching_spend_additions = additions
                    matching_spend_additions = [
                        a
                        for a in matching_spend_additions
                        if a.puzzle_hash == construct_puzzle(puzzle_driver, OFFER_MOD).get_tree_hash()
                    ]
                    if len(matching_spend_additions) == expected_num_matches:
                        coins_for_this_spend.extend(matching_spend_additions)
                    else:
                        raise ValueError("Could not properly guess offered coins from parent spend")
            else:
                # It's much easier if the asset is bare XCH
                asset_id = None
                coins_for_this_spend.extend([a for a in additions if a.puzzle_hash == OFFER_MOD_HASH])

            # We only care about unspent coins
            coins_for_this_spend = [c for c in coins_for_this_spend if c not in self._bundle.removals()]

            if coins_for_this_spend != []:
                offered_coins.setdefault(asset_id, [])
                offered_coins[asset_id].extend(coins_for_this_spend)
        return offered_coins
