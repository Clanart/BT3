### Title
Automatic silent remote-URL rewrite from unauthenticated GitHub API `clone_url` field can redirect a user's push destination - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically refreshes GitHub repository metadata from the API and, if it detects that the API's `clone_url` no longer matches the local `origin` remote, it will silently rewrite the local git remote URL to the new value — with no user prompt or confirmation — as long as a same-protocol/"unchanged since last known" heuristic passes.

### Finding Description
`updateRemoteUrl()` compares the locally configured `origin` remote against the `clone_url` returned by the GitHub API for the associated `GitHubRepository`. If the current remote still matches the *previously cached* `gitHubRepository.cloneURL` (i.e. the user hasn't manually customized it) and the URL scheme/protocol of old vs. new value matches, the code calls `gitStore.setRemoteURL(...)` and rewrites `origin` to the new `apiRepo.clone_url` without any user confirmation: [1](#0-0) 

The only integrity checks performed are protocol matching and "did the remote still match what we last cached" — mirroring the smart-contract bug's structural flaw: state is refreshed/overwritten using a trusted-by-default external value (there, GMX's `stakedGmxTracker()`; here, the GitHub API's `clone_url` field) without validating that the *new* value is safe to adopt, and without any owner/user confirmation gate before the mutation takes effect. `urlMatchesRemote()` only checks hostname/owner/repo-name structurally; it does not otherwise validate provenance of the `clone_url` string that arrives in the API response object: [2](#0-1) 

This is invoked from the periodic GitHub repository metadata refresh path in `app-store.ts` (three call sites reference `updateRemoteUrl`), which is driven purely by data returned from the GitHub API for that repository — an object whose fields (including `clone_url`) can change due to a repository rename, transfer, or (in the enterprise/GHES case) a compromised or MITM'd API endpoint.

### Impact Explanation
If the `clone_url` field an attacker can influence (e.g., via a compromised GHES instance, a malicious repository transfer/rename sequence, or a man-in-the-middle on an API response for a self-hosted GHES server) differs from the current remote but still resolves the "unchanged since last cache" and "protocol matches" heuristics, GitHub Desktop will automatically point the user's `origin` remote at a new host/owner/repo without any dialog. Subsequent `git push`/`git fetch` operations — and any credential helper handshake performed by the trampoline (`app/src/lib/trampoline/trampoline-credential-helper.ts`) for that new remote host — would be silently redirected, risking exfiltration of push credentials/tokens to an attacker-controlled endpoint and/or corruption of what gets pushed (pushing to the wrong destination transparently). This matches the report's "silent corruption of what the user commits or pushes" and "credential exfiltration" impact classes.

### Likelihood Explanation
Likelihood is limited: for github.com the `clone_url` is normally stable and the app's own upstream fork/rename dialogs (`UpstreamAlreadyExists`) generally do prompt for known fork-upstream scenarios. However, `updateRemoteUrl` bypasses any such prompt for the *default* (`origin`) remote specifically, and the trust boundary is the raw API response body — which is attacker-influenced in a compromised/MITM GHES scenario or via a maliciously orchestrated rename/transfer chain that satisfies the "previously unchanged" heuristic. This is a plausible but not trivially exploitable path, and it requires a scenario where the attacker can influence the `clone_url` returned by the configured GitHub API endpoint.

### Recommendation
Do not perform automatic, silent remote URL rewrites for `origin` based purely on the GitHub API's `clone_url` field. At minimum, prompt the user for confirmation before changing `origin` (as is already done for the `upstream` remote via `UpstreamAlreadyExists`), and validate that the new URL's host is one the user has already authenticated against, rather than blindly trusting `apiRepo.clone_url`.

### Proof of Concept
1. User has cloned a repository from a GitHub Enterprise Server instance; `origin` is `https://ghe.example.com/org/repo.git` and matches the app's cached `gitHubRepository.cloneURL`.
2. Attacker compromises the GHES instance (or performs a MITM against its API endpoint) and causes the repository API object's `clone_url` field to instead read `https://attacker-controlled-host/org/repo.git` (same protocol, `https`).
3. On the next periodic metadata refresh, `updateRemoteUrl()` finds `remoteUrlUnchanged === true` (matches previously cached `cloneURL`) and `protocolsMatch === true`, so it calls `gitStore.setRemoteURL('origin', 'https://attacker-controlled-host/org/repo.git')` with no user prompt: [3](#0-2) .
4. The user's next `git push` (and the trampoline credential helper flow for that new host) silently targets the attacker-controlled remote, risking token/credential exposure and misdirected pushes.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
