### Title
Argv/flag injection into external-editor invocation via attacker-controlled file/repo paths — ([File: app/src/lib/editors/launch.ts])

### Summary
`FoundEditor` itself (`app/src/lib/editors/shared.ts`) is just a data type (`editor` name + `path`); it carries no attacker-controlled data — the editor `path` values come exclusively from local, hard-coded discovery lists on the user's machine (e.g. `app/src/lib/editors/linux.ts`, `win32.ts`, `darwin.ts`). [1](#0-0) [2](#0-1)  So the specific claim that a ref/branch/tag/remote URL flows *into* `FoundEditor` does not hold — those values never touch this type or the editor-launch code path.

However, the actual sink that consumes a `FoundEditor` — `launchExternalEditor` in `app/src/lib/editors/launch.ts` — does have a real, narrower issue: it spawns the editor binary with the repository/file path as a raw, unguarded argv element, with no `--` separator and no check for a leading `-`/`+`.

```ts
// app/src/lib/editors/launch.ts
export const launchExternalEditor = (fullPath: string, editor: FoundEditor) =>
  launchEditor(editor.path, [fullPath], `'${editor.editor}'`, __DARWIN__)
``` [3](#0-2) 

`launchEditor` then calls Node's `child_process.spawn(editorPath, args, opts)` directly (no shell), so classic shell-metacharacter injection is not possible — `args` are passed as literal execve arguments, not parsed by a shell. [4](#0-3) 

### Finding Description
`fullPath` is built by joining `repository.path` with a file's relative path taken directly from git tree/working-directory entries — i.e., attacker-controlled repository content (a committed file name). [5](#0-4) [6](#0-5)  That value is forwarded unmodified to `launchExternalEditor`/`launchEditor`, which places it as the sole positional argument to the external editor binary, with nothing to stop the operating-system-level parser of that binary (not GitHub Desktop's own parsing) from treating a leading-special-character filename as an option rather than a path.

This is a known class of argv-injection risk for certain editors: e.g. Vim/Neovim (both are entries in GitHub Desktop's built-in editor list) treat an argument beginning with `+` as a startup `:ex` command to execute before opening any file, unless preceded by `--`. A repository could contain a committed file literally named e.g. `+:!touch pwned` or `+:!curl ... | sh`; if the user selects "Open in \<editor\>" for that file while Vim/Neovim is the configured editor, the spawned command becomes effectively `nvim '+:!touch pwned'`, which Vim would interpret as an ex-command to run rather than a filename to open. [7](#0-6) 

### Impact Explanation
If exploitable against the user's configured editor (Vim/Neovim being the clearest case), this results in local command execution triggered simply by a user opening a maliciously-named file from a cloned/fetched repository in their external editor — a genuine RCE vector originating from repository content the attacker controls, consistent with the program's "unprivileged repository content" attacker model. Impact is editor-dependent, however: most GUI editors (VS Code, Sublime, Atom, etc.) do not have similarly dangerous flag-parsing behavior for a bare filename, so this is not universally "Critical" across all supported editors — it's conditioned on the user's editor choice and that editor's specific CLI parsing semantics.

### Likelihood Explanation
Requires: (1) attacker commits/pushes a file with a crafted name into a repo the victim clones/fetches, (2) the victim has a vulnerable editor (e.g. Vim/Neovim) configured as their external editor, and (3) the victim explicitly right-clicks and chooses "Open in external editor" on that specific file (or opens the whole repository, which also passes `repository.path` — less useful for filename-based tricks but the same missing `--` guard applies). This requires a non-trivial, specific user action (choosing to open a suspiciously-named file), which lowers likelihood relative to a fully automatic/silent exploit.

### Recommendation
In `launchEditor`/`launchExternalEditor` (`app/src/lib/editors/launch.ts`), insert a `--` argument-terminator before the path argument when spawning the editor directly (i.e. `spawn(editorPath, ['--', fullPath], opts)`), and/or reject/normalize file and repository paths that begin with `-` or `+` before passing them as argv. The same treatment should be applied to `launchCustomExternalEditor`'s expanded `%TARGET_PATH%` argument in `app/src/lib/custom-integration.ts` for consistency, since it also lacks any leading-character check.

### Proof of Concept
1. Clone a repository containing a file literally named `+:!touch /tmp/pwned` (or the Windows/PowerShell equivalent).
2. Configure Neovim as the external editor in GitHub Desktop preferences.
3. Right-click the file in the Changes/History list and select "Open in Neovim".
4. Observe that `spawn('/usr/bin/nvim', ['/path/to/repo/+:!touch /tmp/pwned'], ...)` is invoked, and Neovim executes the embedded `:!touch /tmp/pwned` ex-command on startup instead of (or in addition to) opening a file, because the argument was not passed after a `--` separator.

Note: this finding concerns `launch.ts`, not `shared.ts` — `shared.ts` contains no logic that processes or forwards untrusted input, so as literally scoped to "`FoundEditor` in `app/src/lib/editors/shared.ts`," there is nothing exploitable in that file itself.
