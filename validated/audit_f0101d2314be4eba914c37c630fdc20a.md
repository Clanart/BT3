### Title
Unhandled division by zero in KIP-71 base fee calculation when `GasTarget` governance parameter is set to zero - ([File: params/kip71_config.go])

### Summary
The `Kip71GasTarget` governance parameter can be set to `0` because its validation uses a no-op format checker, unlike the sibling `Kip71BaseFeeDenominator` parameter which explicitly rejects zero. When `GasTarget` is `0` and a block's gas usage is non-zero, `NextMagmaBlockBaseFee` performs an unguarded `big.Int` division by the zero `gasTarget`, which panics.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the next block's base fee using `gasTarget` as a divisor in both the "gas used above target" and "gas used below target" branches: [1](#0-0) [2](#0-1) 

The only protection against a zero divisor exists for `BaseFeeDenominator` (`baseFeeDenominator = 64` fallback when zero): [3](#0-2) 

No equivalent fallback exists for `gasTarget := kc.GasTarget`, used directly as the divisor a few lines later: [4](#0-3) 

Crucially, the governance parameter registry validates `Kip71BaseFeeDenominator` with a checker that rejects `0`, but validates `Kip71GasTarget` with `noopFormatChecker`, which accepts any `uint64` value including `0`: [5](#0-4) 

This means a governance vote (via the governance module's vote/param mechanism) can legitimately set `GasTarget = 0` and have it accepted into the `ParamSet`, which then flows into `ChainConfig.Governance.KIP71.GasTarget` and is used by every node to compute and verify the next block's base fee (`VerifyMagmaHeader` / `NextMagmaBlockBaseFee`), called during block validation (`blockchain/block_validator.go`) and block assembly (`work/worker.go`), as well as `gasprice`/`feehistory` estimation paths.

If `parentGasUsed` (capped by `MaxBlockGasUsedForBaseFee`) is anything other than `0` while `gasTarget == 0`, the code takes the `parentGasUsed > gasTarget` branch and executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, which panics in Go's `math/big` package.

### Impact Explanation
Since `NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is invoked on every full node during block processing and header verification, and in the block-building path, a `GasTarget=0` governance parameter would cause a panic on all nodes attempting to process any block with non-zero gas usage after the parameter takes effect. This halts block production/verification network-wide once the parameter is active, which is a severe consensus-availability impact reachable purely through the in-scope governance-parameter update mechanism (no privileged node/peer/consensus-message access required beyond the standard governance vote flow).

### Likelihood Explanation
Likelihood depends on a governance vote successfully setting `GasTarget` to `0` (or on any other future feature that could zero this value), but the code path itself provides no defense-in-depth despite the adjacent `BaseFeeDenominator` parameter explicitly guarding against exactly this class of misconfiguration. This asymmetry (deliberate zero-check for one KIP-71 parameter, `noopFormatChecker` for the other) strongly suggests the omission is unintentional and reachable.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (mirroring `Kip71BaseFeeDenominator`), and/or add a defensive zero-check/fallback for `gasTarget` inside `NextMagmaBlockBaseFee`, similar to the existing `baseFeeDenominator == 0` fallback, before performing the division.

### Proof of Concept
1. Submit/pass a governance vote setting `kip71.gastarget` to `0` (accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`): [6](#0-5) 
2. Once the parameter becomes active at the target block, any subsequent block with `GasUsed > 0` triggers `NextMagmaBlockBaseFee` with `gasTarget = 0`: [7](#0-6) 
3. `parentGasUsed > gasTarget (0)` is true, and `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` divides by zero, panicking every node that verifies or builds this block.
