### Title
Fee and standardness checks computed on a transaction that omits the OP_RETURN data output — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying `data` to the transaction's output list, yet computes `weight`/`vbytes` (used for the `needed_fee` and `TooLowFee` checks) and the later `MAX_STANDARD_TX_WEIGHT` standardness check via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which only accounts for `payments` and an optional change output. The data-bearing output pushed to `tx_outs` is never included in the size the checks are applied to. This mirrors the referenced bug class: a bound check is evaluated against the wrong variable (a different, smaller transaction than the one actually produced), so the real transaction escapes the intended fee/size bound.

### Finding Description
In `SignableTransaction::new`:

- The OP_RETURN output is added to `tx_outs` before any sizing is performed (`tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })`), so the final `Transaction` always includes it.
- The initial sizing call is `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` which internally builds a scratch `Transaction` whose `output` is constructed only from `payments` (plus optional change). The `data` output is absent.
- `needed_fee = fee_per_vbyte * vbytes` and the `TooLowFee` check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` therefore use a vbyte count that is short by the size of the OP_RETURN output (~9 bytes of `TxOut` overhead plus the pushdata-encoded script, up to ~83 bytes for the maximum allowed 80-byte payload).
- The change branch recomputes via `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`, again omitting the data output, so `fee_with_change` is also underestimated.
- The final check `if weight > MAX_STANDARD_TX_WEIGHT` uses the same undersized `weight`, so a transaction that exceeds the standardness limit once the data output is included can pass the check.

The resulting `SignableTransaction` contains the OP_RETURN output, so `fee() = sum(inputs) - sum(outputs)` is correct (the fee itself is not stolen or miscalculated in the tx — inputs minus outputs is unchanged), but it is `fee_per_vbyte * (actual_vbytes - estimated_vbytes)` short of the requested rate, and it may fall below `DEFAULT_MIN_RELAY_TX_FEE` even though the `TooLowFee` check "passed".

### Impact Explanation
A `SignableTransaction` constructed with `data` pays a lower effective fee rate than `fee_per_vbyte` requested and can dip under the minimum relay fee or the standard weight cap while every guard returns success. When such a transaction is signed and broadcast, it is rejected by relay policy (non-standard / insufficient fee), leaving the payment unconfirmed and the consumed `ReceivedOutput`s effectively locked until the transaction is reconstructed or bumped — funds the wallet believes it spent that never reach their destination. If `needed_fee()` is consumed by callers (e.g., `processor::networks::bitcoin::needed_fee` amortizes `signable.needed_fee()` over payments), the amortization math operates on a fee below what the real transaction requires.

### Likelihood Explanation
The bug triggers deterministically whenever `data.is_some()` — no adversarial timing or coordination is needed, only a caller exercising the documented OP_RETURN feature. Within this repository, the production caller (`Bitcoin::make_signable_transaction`) currently passes `None` for `data`, so the live processor path is unaffected today; the defect exists in the public `bitcoin-serai` wallet API and manifests for any integrator that supplies OP_RETURN data, which is the supported, documented purpose of the parameter. Severity is bounded to correctness/liveness of the produced transaction rather than theft: Medium.

### Recommendation
Include the OP_RETURN data output in the size estimation. Extend `calculate_weight_vbytes` to accept the data length (or the fully-formed `TxOut` list) and pass `data` through at both call sites (the no-change estimate and the change estimate), so `needed_fee`, the `TooLowFee` check, the change-amount `checked_sub`, and the `MAX_STANDARD_TX_WEIGHT` check are all evaluated against the exact transaction that will be emitted. Alternatively, build the scratch transaction from `tx_outs` directly instead of re-deriving outputs from `payments`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs logic trace
// With data = Some(vec![0u8; 80]) and fee_per_vbyte chosen so that
// fee_per_vbyte * vbytes_no_data >= MIN_RELAY * vbytes_no_data / 1000
// but fee_per_vbyte * (vbytes_no_data + ~91) >= MIN_RELAY * (vbytes_no_data + ~91) / 1000 fails:

let data = Some(vec![0u8; 80]);
// Passes: dust loop only inspects payments; data length check passes (<= 80).
let tx = SignableTransaction::new(inputs, &payments, change, data.clone(), fee_per_vbyte).unwrap();

// tx.tx.output contains the extra OP_RETURN output, so actual vsize is larger
// than the vbytes used internally:
//   actual_vsize = vbytes_no_data + sizeof(TxOut{value, len, OP_RETURN push(80)})
//                ≈ vbytes_no_data + 91
// tx.needed_fee() == fee_per_vbyte * vbytes_no_data  <  actual relay minimum
// tx.fee() == input_sat - sum(tx_outs) which still equals needed_fee (change branch
//   used the same underestimation), so fee_rate_actual < fee_per_vbyte and the TX
//   can be below DEFAULT_MIN_RELAY_TX_FEE despite TooLowFee not firing.
```
Concretely: pick `fee_per_vbyte = 1` sat/vB (the default minimum relay rate). `needed_fee = vbytes_no_data`. The check requires `vbytes_no_data >= vbytes_no_data` (min relay is 1000 sat/kvB = 1 sat/vB), which passes. The emitted transaction is ~91 vB larger, so its true fee rate is `vbytes_no_data / (vbytes_no_data + 91) < 1` sat/vB — below the minimum relay fee — while `SignableTransaction::new` returned `Ok` and `needed_fee()` reports the underestimated value. A test asserting `tx.needed_fee() == tx.fee()` with `fee_per_vbyte` such that the real vsize is used (i.e., `needed_fee == fee_per_vbyte * tx.vsize()`) fails today whenever `data` is present; the existing test `test_send` only exercises `data = None`/`Some` in error paths, never asserting fee correctness for a data-bearing transaction.
