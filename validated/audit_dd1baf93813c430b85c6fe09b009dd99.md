### Title
Untrusted length fields in `ThresholdKeys::read` cause attacker-driven memory exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes threshold parameters (`t`, `n`, `i`) directly from an untrusted byte stream and uses the attacker-controlled `n` to size allocations and read loops before any bounds validation. A small crafted buffer forces `Vec::with_capacity(n)` and a `HashMap` of `n` verification-share reads, so an unprivileged peer repeatedly feeding truncated or hostile encodings to `ThresholdKeys::read` can force large speculative allocations per message, exhausting memory (a remote denial of service analogous to CVE-2014-0219's reachable DoS via an unvalidated input path).

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), the reader first pulls a curve ID, then three `u16` values `(t, n, i)` straight from the stream with no upper bound check: [1](#0-0) 

`n` then drives two unbounded structures before `ThresholdParams::new` gets a chance to reject it:

1. `Interpolation::Constant` preallocates `Vec::with_capacity(usize::from(n))` and reads `n` scalars (`crypto/dkg/src/lib.rs:604-613`). The capacity reservation happens *before* the read loop, so a ~50-byte input claiming `n = 65535` reserves `65535 * sizeof(F)` (~2 MiB for 32-byte fields) and then immediately errors on EOF — the allocation cost is paid regardless.
2. `verification_shares` inserts `n` `read_G` decodes into a `HashMap` for `l in 1..=n` (`crypto/dkg/src/lib.rs:620-623`), again honoring the attacker-chosen count.

Only after these attacker-sized allocations/reads does `ThresholdParams::new(t, n, i)` run and reject invalid combinations (`crypto/dkg/src/lib.rs:625-631`). Compare with other deserializers in-tree that do bound lengths up front — e.g., `Transaction::read` rejects `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` before allocating (`coordinator/src/tributary/transaction.rs:275-297`), and `SlashReport` caps `len` against `MAX_KEY_SHARES_PER_SET` (`coordinator/src/tributary/transaction.rs:424-433`). `ThresholdKeys::read` performs no equivalent pre-validation.

### Impact Explanation
`ThresholdKeys::read` is an explicitly listed public input sink: any place that ingests peer/coordinator-supplied serialized key material (key-rotation payload, reshare messages, recovery blobs) passes raw bytes here. Each hostile packet of only tens of bytes forces a multi-MiB allocation plus `n` failed point-deserialization iterations. Repeated submissions scale linearly in memory churn and CPU spent in `read_G` canonicality checks (`crypto/ciphersuite/src/lib.rs:91-101`), degrading or crashing the signing node — availability loss with no keys or signatures forged. Medium severity: local-equivalent DoS reachable from unauthenticated bytes, matching the CVE-2014-0219 pattern (unvalidated input → shutdown/DoS, CVSS A:H only).

### Likelihood Explanation
The trigger is trivial: `u16` fields mean a 21-byte prefix (4-byte ID len + ID + 6 bytes of params + interpolation tag `0`) claiming `n = 0xFFFF` reaches the vulnerable allocation. No proof-of-possession, signature, or participant authorization is checked inside `read` — validation is entirely deferred to `ThresholdParams::new`, which runs too late. Exploitability depends on an integrator exposing `ThresholdKeys::read` to untrusted input; within Serai's threat model (these read APIs are documented ingestion points for network messages) that is the expected deployment.

### Recommendation
Validate `t`/`n`/`i` against `ThresholdParams`'s limits immediately after reading them and before any allocation:

```rust
// crypto/dkg/src/lib.rs, inside ThresholdKeys::read, after reading (t, n, i):
ThresholdParams::new(t, n, i).map_err(io::Error::other)?; // reject before allocating
// additionally cap n at a hard maximum (e.g., MAX_PARTICIPANTS) and
// only reserve capacity after confirming the input actually contains n elements
```

Also replace `Vec::with_capacity(n)` with incremental `push` (or a `min(n, remaining_len_hint)` bound) so allocation size can never exceed actual input size.

### Proof of Concept
```rust
use std::io::Cursor;
use dkg::{ThresholdKeys};
use frost::curve::Secp256k1;
use ciphersuite::Ciphersuite;

// Attacker-controlled bytes: valid curve ID, then t=1, n=0xFFFF, i=1,
// interpolation = Constant (0), then EOF — no scalar/point data at all.
let mut buf = vec![];
buf.extend((Secp256k1::ID.len() as u32).to_le_bytes());
buf.extend(Secp256k1::ID);
buf.extend(1u16.to_le_bytes());        // t
buf.extend(0xFFFFu16.to_le_bytes());   // n = 65535
buf.extend(1u16.to_le_bytes());        // i
buf.push(0u8);                         // Interpolation::Constant

// Returns Err quickly, but only after Vec::with_capacity(65535) reserves
// ~2 MiB of C::F and the HashMap loop begins. Repeated calls exhaust memory.
let _ = ThresholdKeys::<Secp256k1>::read(&mut Cursor::new(buf));
```

Caveat: I confirmed the allocation-before-validation ordering from `crypto/dkg/src/lib.rs`; I did not trace every upstream caller, so the exact network path feeding `ThresholdKeys::read` in a live deployment is assumed from the documented status of these `read` APIs as untrusted-input sinks.
