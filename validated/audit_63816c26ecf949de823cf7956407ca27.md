### Title
Reward-rate freezing via direct-transfer lpSupply inflation - (rewards/MasterMagpie.sol)

### Summary
`_calLpSupply()` uses `IERC20(_stakingToken).balanceOf(address(this))` as the denominator for accMGPPerShare accrual on every non-vlMGP/non-mWomSV pool, instead of an internally tracked sum of `UserInfo.amount`. Because any external account can push staking tokens directly to `MasterMagpie` with a plain `transfer()` (no `deposit()` call, no `UserInfo.amount` credited), the denominator used in `updatePool()` can be inflated arbitrarily, permanently degrading — and via integer-division truncation, potentially fully zeroing — future MGP accrual for every legitimate staker in that pool.

### Finding Description
`_calLpSupply()` at [1](#0-0)  returns the raw token balance of the contract for all pools other than vlMGP/mWomSV. `updatePool()` divides the period's `mgpReward` by this value to grow `accMGPPerShare`: [2](#0-1) .

`updatePool()` is invoked from every user-facing entrypoint that touches a pool, including `_multiClaim` (used by `multiclaimSpec`, `multiclaim`, `multiclaimFor`, `multiclaimOnBehalf`), `_deposit`, and `_harvestAndUnstake`: [3](#0-2) .

An unprivileged attacker who holds the pool's staking token can call `stakingToken.transfer(masterMagpieAddress, hugeAmount)` directly — no `deposit()`, no `UserInfo.amount` update, no allowance/role required. This inflates `balanceOf(address(this))`, which is what `_calLpSupply()` reports on the next `updatePool()` call (triggered, for example, by any account calling `multiclaimSpec`). Since `pool.allocPoint` is the only non-zero allocation, the entire `mgpPerSec` stream is routed through this diluted division. If the donated amount is large enough relative to `mgpReward * 1e12`, `(mgpReward * 1e12) / lpSupply` truncates to `0` on every subsequent call, and `accMGPPerShare` stops increasing permanently — freezing all future MGP accrual for every staker in the pool, regardless of their `UserInfo.amount`.

Note that the per-account bookkeeping invariant (`unClaimedMgp[_stakingToken][user]` vs `userInfo[_stakingToken][user].rewardDebt`) is *not* broken by `_multiClaim` itself — it correctly zeroes `unClaimedMgp` and resets `rewardDebt = user.amount * accMGPPerShare / 1e12` each time: [4](#0-3) . The real break is upstream, in the shared reward-rate denominator that `updatePool()` (and hence `multiclaimSpec`) consumes: `accMGPPerShare` is divided by donated-and-uncredited balance rather than staked-and-credited supply, so the emitted-MGP-must-equal-sum-of-distributable-shares invariant is violated at the pool level.

### Impact Explanation
This permanently and irreversibly reduces (up to fully zeroing, via integer-division truncation) the MGP yield accrual rate for every legitimate staker of the affected pool, with no compensating benefit to anyone (the donated tokens are not MGP and are not returned to the attacker). Since the pool holds the entire `totalAllocPoint`, this effectively halts protocol-wide future MGP emission distribution to stakers — matching High: permanent freezing of (future/unclaimed) yield.

### Likelihood Explanation
No privileged role is required — any EOA holding (or able to cheaply acquire) the staking token can perform a raw `transfer()` to the contract. The only capital constraint is the amount of staking token needed to make `mgpReward * 1e12 / lpSupply` truncate to zero, which depends on the staking token's price/decimals and the pool's `mgpPerSec` allocation; for low-decimal or already-large-supply staking tokens this can be a modest, one-time, irreversible donation. The attack is trivially repeatable and requires no reentrancy, flash loan repayment, or timing precision — it is a static state change that persists.

### Recommendation
Do not use `balanceOf(address(this))` as the reward-rate denominator. Track an internal `totalStaked[_stakingToken]` counter, incremented in `_deposit`/`depositFor` and decremented in `_withdraw`/`withdrawFor`/`emergencyWithdraw`, and use that in `_calLpSupply()` instead of the raw ERC20 balance for non-vlMGP/non-mWomSV pools.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, register one pool `X` with the only non-zero `allocPoint`, set a realistic `mgpPerSec`.
2. Have user A `deposit()` a normal amount into pool `X`.
3. From an unprivileged address, call `stakingTokenX.transfer(masterMagpie.address, largeDonation)` directly (no `deposit()`).
4. Advance time, then call `masterMagpie.multiclaimSpec([X], [[]])` (or any other function that triggers `updatePool(X)`).
5. Assert `tokenToPoolInfo(X).accMGPPerShare` did not increase (or increased by far less than it would have absent the donation) despite the elapsed `mgpPerSec` interval, demonstrating that emitted MGP is permanently under-distributed/frozen relative to `UserInfo.amount` staked in the pool.
6. Repeat with a donation sized to make `(mgpReward * 1e12) / lpSupply == 0` to demonstrate full, permanent freezing of the pool's MGP accrual.

    function _calLpSupply(address _stakingToken) internal view returns (uint256) {
        if (_stakingToken == address(vlmgp)) {
            return IERC20(address(vlmgp)).totalSupply();
        }
        if (_stakingToken == address(mWomSV)) {
            return IERC20(address(mWomSV)).totalSupply();
        }
