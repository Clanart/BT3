## Analog Found

### Title
Copilot conflict-resolution apply step writes AI-resolved content using a stale working-directory snapshot, silently clobbering a user's own conflict resolution - ([File: app/src/lib/stores/app-store.ts])

### Summary
The Sherlock report's broken invariant is: a security-relevant check (`is this position liquidable?`) is evaluated against a debt value that was cached before the check, instead of being refreshed immediately before the guarded action (`remove_margin`), letting a stale read authorize an action that should have been blocked.

The same "stale-snapshot-guards-a-destructive-write" pattern exists in `_applyCopilotConflictResolutions`, which decides whether to overwrite a conflicted file on disk with AI-generated content based on a `RepositoryState` snapshot captured once at function entry, rather than a freshly read git status taken right before the write.

### Finding Description
`_applyCopilotConflictResolutions` captures `state` a single time at the top of the function: [1](#0-0) 

Later, for each Copilot-generated resolution, it consults that same stale `state.changesState.workingDirectory.files` snapshot to decide whether the user has already manually resolved the file (e.g., in an external editor) since the resolution was generated, and skips the write if so: [2](#0-1) 

The comment at line 7241 explicitly documents the intended guard ("If the user resolved this file externally... while the result dialog was open, git status will report it with no remaining conflict markers... skip it and let their resolution stand"), but the implementation only works if `state.changesState.workingDirectory.files` is current. That state is populated by the periodic/background `_loadStatus` refresh cycle rather than being force-refreshed immediately before this apply step runs. Between the moment Copilot resolutions are generated (`_startCopilotConflictResolution`, which can take up to two minutes based on the timing telemetry recorded around it) and the moment the user clicks "Continue Merge" (an arbitrary amount of time, gated only by user interaction with the result dialog), the cached working-directory snapshot can go stale relative to the actual file contents on disk.

This mirrors M-1 exactly: a value (`total_debt_shares` / `workingDirectory.files`) is read once and reused to gate a state-changing action (removing collateral / overwriting a file) instead of being re-derived immediately before the action, so the guard (`is liquidable?` / `did the user already resolve this file?`) can pass based on data that no longer reflects reality.

### Impact Explanation
If the stale snapshot still reports the file as containing unresolved conflict markers (because the periodic refresh hasn't caught up with the user's external edit), the guard at line 7250-7256 fails to trigger, and the AI-generated resolution is written over the user's manual resolution via `writeFile` and staged with `git add`. This is a silent corruption of what the user subsequently commits — the user believes their manually resolved content will be kept, but Desktop overwrites it without any further confirmation, and the corrupted content is what ultimately gets committed/pushed. Because the conflicting branches can originate from any fetched/merged remote (including forks or third-party branches an attacker controls), an attacker who can influence conflicting content merged from their branch has some influence over what an AI model produces as a "resolution," compounding the risk of unnoticed content substitution.

### Likelihood Explanation
This requires: (1) the user enabling Copilot conflict resolution during a merge/rebase/cherry-pick, (2) editing a conflicted file externally while the Copilot result dialog is open, and (3) Desktop's background status refresh not having caught up to that edit by the time "Continue Merge" is clicked. This is a plausible but narrow timing window rather than a trivially reproducible race, so likelihood is moderate-to-low, similar in spirit to how the original debt-staleness bug required the position to become liquidable in the gap between the stale read and the guarded action.

### Recommendation
Before comparing `onDiskFile.status` to decide whether to skip a write in `_applyCopilotConflictResolutions`, re-run `_loadStatus(repository)` (or otherwise re-read the file's conflict-marker state directly from disk) immediately prior to the loop, so the "already resolved externally" check is evaluated against current state rather than a snapshot that may predate the Copilot round-trip and user review time.

### Proof of Concept
1. Start a merge/rebase with conflicts and enable "Resolve with Copilot."
2. While Copilot resolution is generating results (or while the result dialog is open, before Desktop's background status refresh has re-run), manually resolve one of the conflicted files in an external editor and save it.
3. Click "Continue Merge" quickly, before Desktop's next periodic `_loadStatus` refresh completes.
4. Observe that `_applyCopilotConflictResolutions` reads `onDiskFile.status` from the stale `state` captured at function entry, still finds `isConflictedFileStatus === true`, does not detect the file's manual resolution, and overwrites it with the Copilot-generated content — silently discarding the user's manual fix before it is committed.

Note: I was unable to fully trace the exact debounce/refresh cadence of `_loadStatus` relative to focus/idle events within the indexed portion of the codebase, so the precise reproducibility window (how often the race is actually hittable in practice) is uncertain and would need runtime verification.
