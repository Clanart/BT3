Based on my investigation, I found a legitimate analog in GitHub Desktop's AI-assisted merge-conflict resolution feature. It shares the exact root cause pattern from the report — validation logic that doesn't actually enforce the invariant it claims to check — but the impact category is different (silent commit corruption instead of a disabled test flag).

### Title
Weak conflict-marker validation lets attacker-influenced Copilot output silently corrupt resolved merge files - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
`parseCopilotConflictResolution` is supposed to reject any hunk resolution that still contains leftover Git conflict markers before it is spliced back into the user's file and written to disk/staged for commit. The regex used for that check is narrower than the marker-detection regex used elsewhere in the same file, so a resolution that contains a malformed/incomplete conflict marker can pass validation, get reassembled into the "resolved" file, and be silently written to disk and staged.

### Finding Description
The validation gate that is supposed to catch leftover conflict markers in a hunk's `resolvedContent` is: [1](#0-0) 

This requires **both** an opening marker followed by whitespace (`/^<{7}\s/m`) **and** a separate `=======` line (`/^={7}$/m`) to be present before it throws `CopilotValidationError`. Compare this to the marker-detection regexes actually used during reassembly: [2](#0-1) 

The reassembly regex `/^<{7}(?:\s|$)/` matches a bare `<<<<<<<` line with nothing after it (end of line), but the validation regex requires a trailing space/character after the 7 `<`s. A hunk resolution containing a stray `<<<<<<<` (no trailing text) without an accompanying `=======` line therefore passes `parseCopilotConflictResolution` unflagged, gets spliced verbatim into the file by `reassembleResolvedFile`, and is written to disk and staged via `_applyCopilotConflictResolutions`: [3](#0-2) 

The system prompt explicitly feeds untrusted, repository-controlled content — commit messages and PR titles/descriptions from a possibly malicious remote/collaborator — into the same conversation context used to steer the model's decision: [4](#0-3) 

This is a text-injection surface: repository content an attacker controls (commit messages, PR descriptions encountered during a merge/rebase against a malicious branch/fork) is passed as model input that influences the resolution text, and the weak-marker check does not fully validate the model's structured output before it is trusted and persisted.

Note: the file-path write path itself is properly guarded — `_applyCopilotConflictResolutions` calls `resolveWithin(repository.path, resolution.path)` and skips any path that resolves outside the repo, so this is not a directory-traversal / arbitrary-file-write bug: [5](#0-4) 

### Impact Explanation
Impact is limited to data integrity, not remote code execution or credential exfiltration: a malformed/incomplete conflict-marker fragment (or attacker-steered incorrect merge resolution) can be silently written into the user's working tree file and staged for commit without the user reviewing the raw diff, because the app's own "no leftover markers" safety check does not actually cover all marker shapes it should. This falls in the "silent corruption of what the user commits or pushes" bucket, since the file content the user ultimately commits/pushes may differ from what they believe was validated.

### Likelihood Explanation
Requires the user to invoke "Resolve with Copilot" on a merge/rebase/cherry-pick that involves attacker-influenced content (a malicious fork/branch/PR with crafted commit messages or PR description) and for the model's structured JSON output to include a resolution whose `resolvedContent` field contains a marker shape not covered by the check (e.g., `<<<<<<<` with no trailing text on that line). This depends on model behavior which is probabilistic, so likelihood is moderate/low, but it does not require any unnatural user steps beyond normal use of a shipped feature.

### Recommendation
Use the same (or a stricter, superset) marker-detection regex in `parseCopilotConflictResolution` as is used in `reassembleResolvedFile` (e.g., reuse `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` constants), and also check for stray `=======`/`>>>>>>>` lines independently, not only as a conjunction with a matching open marker. Consider running a final `git diff --check`-style validation pass on the fully reassembled file before it is written and staged, so any leftover marker syntax blocks the write instead of relying solely on the model's structured-field validation.

### Proof of Concept
1. Trigger a merge/rebase/cherry-pick against a branch containing attacker-crafted commit messages/PR description designed to bias the model.
2. Invoke "Resolve with Copilot" (`attemptCopilotConflictResolution` → `startCopilotConflictResolution`).
3. If the model's JSON response contains a hunk `resolvedContent` value such as `"foo\n<<<<<<<\nbar"` (bare `<<<<<<<` line, no separator), `parseCopilotConflictResolution`'s check `/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)` evaluates to `false` (missing the required trailing whitespace and missing `=======`) and does not throw.
4. `reassembleResolvedFile` splices this content into the file.
5. `_applyCopilotConflictResolutions` writes it to disk via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and runs `git add`, staging the corrupted content without further marker validation.
