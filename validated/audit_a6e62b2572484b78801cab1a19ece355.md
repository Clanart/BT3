### Title
`unvote()` incorrectly reverts with `PoolNotActive` when the pool IS active, contradicting NatSpec, permanently stranding vote weight once a pool is deactivated - ([File: wombat/WombatBribeManager.sol])

### Summary
`unvote(address _lp)` is documented as the mechanism to "Unvote from an inactive pool" so that deactivating a pool or changing its rewarder does not block users from withdrawing their vlMGP voting weight. However the implemented guard is inverted: it reverts with `PoolNotActive()` when `!pool.isActive`, i.e., it only succeeds while the pool is still active and always reverts once the pool is deactivated - exactly the opposite of its stated purpose.

### Finding Description
`vote()` guards every pool touched in a batch with `if (!pool.isActive) revert PoolNotActive();` [1](#0-0) , meaning once the owner sets `pool.isActive = false` for a pool `P`, no user can submit a negative delta for `P` through `vote()` to withdraw their stake there.

The escape hatch is supposed to be `unvote()`, whose NatSpec explicitly states: "Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing" [2](#0-1) . But the actual guard is:

```solidity
function unvote(address _lp) public {
    Pool storage pool = poolInfos[_lp];
    uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
    if(!pool.isActive)
        revert PoolNotActive();
    ...
}
``` [3](#0-2) 

This check reverts precisely in the case the function is meant to handle (an inactive pool), and only allows execution while the pool remains active - a condition under which the user could already exit via `vote()` with a negative delta. As a result, once `P.isActive` becomes `false`, both exit paths (`vote()` and `unvote()`) revert with `PoolNotActive()` for any user holding a nonzero `userVotedForPoolInVlmgp[user][P]` balance, and there is no other public/external function in `WombatBribeManager` that lets a user reduce `userVotedForPoolInVlmgp`/`userTotalVotedInVlmgp` for a specific pool. Since `userTotalVotedInVlmgp[msg.sender]` is checked against `getUserVotable(msg.sender)` in `vote()` [4](#0-3) , this stranded allocation also permanently consumes part of the user's votable vlMGP capacity, preventing them from reallocating that weight to any other pool.

### Impact Explanation
This is a permanent freezing-of-funds/voting-weight condition: any unprivileged voter who had allocated vlMGP weight to a pool that is later deactivated by the owner becomes unable to reclaim or reallocate that weight through any public function in the contract, since the only two withdrawal paths (`vote()` and `unvote()`) both require `pool.isActive == true`. Matches Immunefi's "permanent freezing of funds/voting weight" impact class.

### Likelihood Explanation
No special capital is required beyond having voted for a pool. The only precondition is a pool deactivation, which is a normal, expected admin/lifecycle action (deleting a pool or changing its rewarder) explicitly anticipated by the NatSpec of `unvote()`. This is not a malicious-admin scenario — deactivating pools is routine protocol operation, and the resulting freeze is a straightforward logic-inversion bug reachable by any voter.

### Recommendation
Invert the condition in `unvote()` so it succeeds when `!pool.isActive` (or removes the `isActive` check entirely and relies on other invariants), matching the documented intent, e.g.:
```solidity
function unvote(address _lp) public {
    Pool storage pool = poolInfos[_lp];
    if (pool.isActive) revert PoolStillActive(); // or simply drop the check
    ...
}
```

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, add pool `P` with `isActive = true`, and a mock `IBribeRewardPool` rewarder.
2. As attacker, lock MGP to obtain vlMGP voting power, then call `vote([P], [+X])`; assert `userVotedForPoolInVlmgp[attacker][P] == X` and `userTotalVotedInVlmgp[attacker] == X`.
3. As owner, deactivate `P` (set `poolInfos[P].isActive = false`).
4. As attacker, call `vote([P], [-X])` and assert it reverts with `PoolNotActive()`.
5. As attacker, call `unvote(P)` and assert it also reverts with `PoolNotActive()` (this is the bug — NatSpec says this should succeed).
6. Assert `userTotalVotedInVlmgp[attacker]` remains `X` indefinitely, and attacker cannot vote for any other pool up to their full `getUserVotable(attacker)` capacity, demonstrating the frozen/stuck voting weight for at least 24 hours (or indefinitely, until the bug is fixed).
