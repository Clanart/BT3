### Title
Temp git index created via `shutil.copy2` inherits and widens permissions in a world-accessible temp directory - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`_temp_index` creates the throwaway index with `tempfile.mkstemp`, which Python guarantees is opened `0600` regardless of umask, but then immediately calls `shutil.copy2(real_index, tmp_index)`. `shutil.copy2` also copies file metadata (via `copystat`), including the source's permission bits, so the temp file's mode is overwritten to match `real_index`'s mode rather than staying at the safe `0600` that `mkstemp` established. Since the temp file lives in a shared, world-listable directory (`/tmp`), this can expose index contents to local users who otherwise could never reach the real `.git/index` (e.g., because it sits under a `700` home directory).

### Finding Description
The relevant code is: [1](#0-0) 

```
tmp_fd, tmp_index = tempfile.mkstemp(prefix="security_hook_idx_")
os.close(tmp_fd)
try:
    shutil.copy2(real_index, tmp_index)
    env = {**os.environ, "GIT_INDEX_FILE": tmp_index}
```

`tempfile.mkstemp` opens the descriptor with mode `0600` unconditionally (it does not rely on the process umask), which is the safe baseline. However `shutil.copy2` is explicitly documented to copy "as much metadata as possible" including permission bits via `shutil.copystat`, which calls `os.chmod(dst, src_mode)`. This means immediately after the copy, `tmp_index`'s mode is whatever `real_index`'s mode is — commonly `0644` on POSIX systems where the process umask is `022`, since git creates the index file according to the umask at the time it was written.

The temp file is placed directly in the system temp directory (`tempfile.mkstemp` defaults to `tempfile.gettempdir()`, typically `/tmp`), which is world-listable/readable (mode `1777`) on most Linux/macOS systems. In the original location, the real index is often protected by restrictive parent-directory permissions (e.g., a `700` home directory), so its own `644` file mode is not exploitable by other local users. Copying it into `/tmp` with the same permissive mode removes that protection layer for the duration between `shutil.copy2` and the `os.unlink` in the `finally` block: [2](#0-1) 

An unprivileged local user who cannot read the real repository (no access to the home directory) but can list/read `/tmp` could, during that window, `open()` the temp index and read its entries — repo-relative paths and blob SHA-1s for every staged file, including the identity of staged secret files (e.g., filenames like `aws_credentials.json`) and their content-hashes. Nothing in `_temp_index` restores or enforces `0600` after the `copy2` call, so the mode divergence is real and not merely theoretical.

### Impact Explanation
This is a local information-disclosure issue: the identity (paths) and SHA-1 hashes of staged files become readable to unprivileged local users who otherwise have no access to the victim's repository, for the brief window the temp index exists in `/tmp`. Full secret *content* reconstruction additionally requires access to the corresponding loose objects in `.git/objects`, which is not copied here, so the scoped impact is disclosure of staged file paths/hashes rather than full secret bytes in the common case — still a trust-boundary violation matching a local information-disclosure class bounty impact.

### Likelihood Explanation
Exploitability requires: (1) a shared multi-user host where `/tmp` (or `tempfile.gettempdir()`) is world-readable/listable — the common default; (2) the attacker lacking direct read access to the victim's repository directory but having `/tmp` read access — a realistic and common local-attacker configuration; (3) winning a narrow race between `shutil.copy2` and `os.unlink`, repeatable by polling `/tmp` for files matching the `security_hook_idx_*` prefix while the hook runs repeatedly (this hook fires on ordinary git diff/status flows in the plugin, so the window recurs often). No privilege escalation or code execution is needed — only a filesystem read race.

### Recommendation
After `shutil.copy2`, explicitly re-`os.chmod(tmp_index, 0o600)` (or use `shutil.copyfile` instead of `copy2`, which does not copy permission bits and preserves the `mkstemp`-created destination mode), so the mode never diverges from the safe baseline `mkstemp` established, independent of the source index's mode or the destination directory's exposure.

### Proof of Concept
Integration test:
1. Create a temp "repo" dir with restrictive permissions (`0700`) containing a `.git/index` file with mode `0644` (simulating default umask).
2. Monkeypatch/call `_temp_index(cwd)` and, inside the `with` block (before the `finally` cleanup), call `os.stat(tmp_index).st_mode & 0o777`.
3. Assert the mode is `0o600` (or stricter) — the test should currently **fail**, showing the mode is `0o644` (matching `real_index`), demonstrating the divergence.
4. As a secondary check, assert that a second unprivileged process (or `os.access(tmp_index, os.R_OK)` under a different simulated UID) cannot read the file when running with the fix, but can without it.
