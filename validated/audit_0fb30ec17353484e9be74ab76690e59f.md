## Finding: Valid

### Title
Signature threshold check counts raw vector length instead of unique authority indices, allowing quorum bypass via duplicated `(signature, index)` entries - (File: `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
`verify_mmr_update_proof` computes `signatures_length = mmr.signed_commitment.signatures.len()` and passes that raw count into `check_participation_threshold`, without ever deduplicating by `SignatureWithAuthorityIndex.index`. An attacker who can obtain fewer than `2/3+1` genuine signatures for a round (e.g. harvested from the public BEEFY gossip network before finalization, which anyone can observe) can pad the `signatures` vector with repeated `(signature, index)` pairs for the *same* already-owned authorities to inflate the raw length past the quorum threshold. [1](#0-0) 

### Finding Description
`check_participation_threshold` is a pure arithmetic check on a `u32` length: [2](#0-1) 

It has no knowledge of, and does not deduplicate against, the actual `index` field carried by each `SignatureWithAuthorityIndex`: [3](#0-2) 

Downstream, the loop that builds `authority_indices`/`authority_leaves` for the merkle multi-proof also iterates the raw (possibly duplicated) `signatures` vector without deduplication: [4](#0-3) 

Because the two derived vectors (`authority_indices`, `authority_leaves`) contain the same repeated `(index, leaf)` pair positioned identically, any standard merkle multi-proof algorithm treats the duplicate as a no-op — it supplies no new information beyond the single unique leaf at that index and requires no additional proof material. In other words, padding the signature list with repeats of already-recovered, already-included authorities does not require the attacker to forge anything against `authority_set.keyset_commitment`; the multi-proof for the true minority subset of unique signers still verifies. This lets `signatures_length` (the raw vector length used for the threshold check) diverge arbitrarily from the true number of *unique* signing authorities, defeating the supermajority invariant the function is supposed to enforce.

Note: I was not able to directly inspect the vendored `rs_merkle` crate source in this repository (it is an external dependency, see `Cargo.toml`), so the exact duplicate-index handling of `MerkleProof::verify` could not be confirmed line-by-line. However, the vulnerability's root cause is independent of that detail: `check_participation_threshold` is checking the wrong quantity (`Vec::len()`) regardless of how the merkle library later processes duplicates — a correct implementation must count unique authority indices before comparing against the 2/3+1 bound.

### Impact Explanation
If exploited, an attacker with only a sub-quorum set of genuine authority signatures (obtainable, in a BEEFY round, from the public gossip network before finalization completes — no validator collusion or private key compromise required) can get `verify_mmr_update_proof` to `Ok` a forged/incomplete commitment. This corrupts `ConsensusState.mmr_root_hash` and advances `latest_beefy_height` based on a commitment that never actually reached network-wide supermajority finality. Since all downstream parachain header and state-proof verification is anchored to this `mmr_root_hash`, an attacker could subsequently present forged parachain state commitments to mint, unlock, or redirect bridged assets, escrowed funds, or relayer rewards — matching the "false proof/state acceptance" and "stealing or loss of funds" impact categories in scope.

### Likelihood Explanation
Exploitation requires the attacker to acquire genuine authority signatures for the round below the quorum threshold. BEEFY validators broadcast partial round votes over a public P2P gossip network as part of normal protocol operation, so an unprivileged observer (not a validator, not a relayer, not requiring any compromise) can collect these without any privileged access. The remaining steps — padding the signature vector with duplicates and constructing a merkle multi-proof for only the unique leaves actually held — require no cryptographic breaks, only correctly using existing library functions the way an honest prover already does (as seen in `build_authority_proof` in the prover).

### Recommendation
Deduplicate by `sig.index` before computing the threshold count and before building the merkle multi-proof inputs, e.g.:
- Collect signatures into a `BTreeSet`/`BTreeMap` keyed by `index`, rejecting the proof outright (or simply ignoring duplicates) if the same index appears more than once.
- Use the size of this deduplicated set, not `mmr.signed_commitment.signatures.len()`, as the input to `check_participation_threshold`.
- Reject proofs containing duplicate `index` values outright, since a well-formed prover never needs to submit more than one signature per authority.

### Proof of Concept
1. Attacker observes the public BEEFY gossip network during a round and collects genuine `(signature, index)` votes from `k` authorities, where `k < (2/3)*total + 1`.
2. Attacker builds `signed_commitment.signatures` by repeating each of the `k` genuine `SignatureWithAuthorityIndex` entries enough times so that `signatures.len() >= (2/3)*total + 1` (e.g. duplicate each entry ~2-3x).
3. Attacker builds `authority_proof` as the standard merkle multi-proof for the `k` unique authority indices (exactly as `build_authority_proof` in the honest prover does), since the duplicated entries add no new leaves to prove.
4. Attacker submits this `MmrProof` via `verify_consensus`/`verify_mmr_update_proof`.
5. `check_participation_threshold(signatures_length, authority_set.len)` passes because `signatures_length` counts duplicates.
6. `merkle_proof.verify(...)` passes because the duplicated `(index, leaf)` pairs are redundant and the proof correctly attests to the `k` unique real leaves.
7. `verify_mmr_update_proof` returns `Ok`, updating `ConsensusState` from only `k < 2/3+1` unique real signers.
