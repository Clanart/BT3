### Title
Algorithmic complexity DoS in `Offer.get_cancellation_coins()` via crafted announcement-dependency chains - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_cancellation_coins()` and its helper `detect_dependent_coin()` process the `ASSERT_COIN_ANNOUNCEMENT`/`CREATE_COIN_ANNOUNCEMENT` conditions of every coin spend in an offer file to determine which coins to cancel. The nested-loop structure is driven entirely by data (coin count and dependency chains) that an untrusted offer counterparty fully controls, mirroring the Envoy HTTP/2-stream-reset bug class: attacker-controlled input drives a super-linear amount of local CPU work in a single call.

### Finding Description
`detect_dependent_coin()` iterates `names × deps[name] × announcement_dict.items()` — a triple nested loop over all coins in the offer for every invocation: [1](#0-0) 

`get_cancellation_coins()` builds `dependencies`/`announcements` maps from every non-addition coin spend's conditions, then calls `detect_dependent_coin()` inside an outer `while True` loop that only removes coins one dependency-chain-step at a time, plus an inner `while True` loop performing `set` intersections over `dependencies.items()` for every removed coin: [2](#0-1) 

Because the outer loop can iterate up to N times (removing at most a handful of coins per pass in adversarial chains) and each iteration re-scans the full `detect_dependent_coin()` triple loop plus the inner set-based sweep over all remaining `dependencies`, the combined cost scales far worse than linearly with the number of coin spends and announcement dependencies in the offer — worse than the O(N²) class described in the Envoy report.

This computation is not part of core consensus validation; it runs client-side whenever a wallet inspects/cancels a trade offer, via `TradeManager`'s cancellation flow, which calls into `Offer.get_cancellation_coins()`: [3](#0-2) 

### Impact Explanation
An offer counterparty can craft a `SpendBundle`-backed offer file with a large number of coin spends whose puzzles emit long chains of `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions referencing each other. When the recipient wallet loads the offer and later attempts to cancel it (a normal wallet operation reachable by any user who received such an offer), `get_cancellation_coins()` is invoked and can consume excessive CPU on the recipient's wallet process, stalling wallet responsiveness — a spend-triggered transaction-processing halt local to the victim's wallet.

### Likelihood Explanation
Any offer counterparty can construct and send such an offer file; no privileged access or network-layer exploitation is required, and offers are a normal, expected data structure a wallet user is meant to load and potentially cancel. The complexity is entirely driven by the coin/announcement structure the attacker controls in the spend bundle.

### Recommendation
Bound or pre-validate the number of coin spends / dependency edges processed by `get_cancellation_coins()` before running the removal loop, and replace the repeated linear/triple-nested scans in `detect_dependent_coin()` and the inner `while True` set-intersection sweep with a single-pass graph traversal (e.g., building an announcement→dependent-coin index once, then doing a linear BFS/DFS over dependencies) to keep the overall complexity near O(N) or O(N log N) in the number of coin spends.

### Proof of Concept
Construct an offer `SpendBundle` with `N` coin spends where each coin `i` asserts an announcement created by coin `i+1` (a linear or branching dependency chain among `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions) and no coin is in `additions()`. Call `Offer(...).get_cancellation_coins()` (as triggered by the wallet's offer-cancellation RPC path) and observe CPU time growing much faster than linearly as `N` increases, due to the repeated `detect_dependent_coin()` triple-nested scan combined with the inner `while True` set-intersection loop over `dependencies.items()` executed once per removed coin.

**Note:** I was not able to fully trace the exact RPC entry point (`cancel_offer(s)` in `wallet_rpc_api.py`) that calls into `TradeManager`'s cancellation path due to tool-call limits reached before finishing that lookup — this should be verified to confirm the precise externally-triggerable call chain, though `get_cancellation_coins()`'s only production caller found is within `chia/wallet/trade_manager.py`.

```python
def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
```

```python
    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
```
