### Title
A single invalid offset aborts signing for every input in `SignableTransaction::multisig` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::multisig` builds one `AlgorithmMachine` per input. While doing so it uses `None?` early-return semantics: if any single input's offset produces a group key whose `p2tr_script_buf` is `None` (i.e., an odd Y coordinate), the entire function returns `None`, abandoning the machines already built for all other, perfectly valid inputs. There is no partial path — one bad input DoSes the whole transaction.

### Finding Description
The analog to the PureTokenAdapter bug is structural: a multi-item operation is designed to iterate over independent items, but a failure in one item propagates as a hard abort of the whole operation instead of a per-item failure.

In `multisig` (networks/bitcoin/src/wallet/send.rs:273-285):

```rust
pub fn multisig(self, keys: &ThresholdKeys<Secp256k1>) -> Option<TransactionMachine> {
  let mut sigs = vec![];
  for i in 0 .. self.tx.input.len() {
    let offset = keys.clone().offset(self.offsets[i]);
    if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
      None?;
    }
    sigs.push(AlgorithmMachine::new(Schnorr::new(), keys.clone().offset(self.offsets[i])));
  }
  Some(TransactionMachine { tx: self, sigs })
}
```

`self.offsets` comes verbatim from `ReceivedOutput::offset`, and `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) accepts an arbitrary `Scalar` from untrusted bytes with no validation that `key + G*offset` is an even-Y point. `p2tr_script_buf` (mod.rs:80-86) returns `None` precisely for odd keys, and `register_offset` (mod.rs:180-196) documents that not every offset is usable — offsets that produce odd points are incremented until even.

So an attacker-supplied `ReceivedOutput` whose `offset` yields an odd `offset.group_key()` (≈50% of arbitrary scalars) causes `None?` to fire inside the loop. The function then returns `None` for the *entire* transaction, discarding the valid inputs' machines — exactly as the adapter's revert discarded the partial withdrawal the AssetManager was designed to allow.

### Impact Explanation
Any party able to feed a `ReceivedOutput` (e.g., through `ReceivedOutput::read` bytes, or an out-of-band offset that was never normalized through `Scanner::register_offset`) can insert one poisoned input into `SignableTransaction::new` and make `multisig` return `None`. All other legitimate, spendable inputs in that transaction become unsignable through this machine — funds received are not spendable via the intended path, and there is no error distinguishing which input failed, so the caller cannot even identify and drop the bad input.

### Likelihood Explanation
Requires an unprivileged party to get one `ReceivedOutput` with a non-normalized offset included in a multi-input `SignableTransaction`. Each such offset has ~50% chance of producing an odd point, so essentially any unchecked scalar works. The failure is deterministic once the input set is fixed.

### Recommendation
Do not use `None?` inside the per-input loop. Either validate each offset at `SignableTransaction::new` time (reject inputs whose `p2tr_script_buf` is `None` or whose script doesn't match `prevouts[i].script_pubkey`, reporting the index), or have `multisig` skip/diagnose the failing input rather than returning `None` for the whole transaction — mirroring the recommendation that the adapter return `false` instead of reverting so partial operations remain possible.

### Proof of Concept
1. Construct two `ReceivedOutput`s spending to the same key. Give the second one an `offset` scalar (writable via `ReceivedOutput::write`/`read`) such that `key + G*offset` has odd Y — trivially found by trying offsets `1, 2, 3, ...` (`register_offset` itself notes half of all offsets are odd).
2. Build `SignableTransaction::new(vec![good, bad], payments, change, None, fee)` — succeeds, since `new` never validates offsets.
3. Call `.multisig(&keys)`. The loop reaches `i = 1`, `p2tr_script_buf(offset.group_key())` returns `None`, `None?` fires, and the function returns `None` — the valid first input can no longer be signed either.
