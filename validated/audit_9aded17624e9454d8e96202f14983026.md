### Title
Zero-Operator Deposit Bypasses All NofN and Operator Signature Requirements, Permanently Locking Bridged BTC — (`core/src/verifier.rs`, `core/src/builder/sighash.rs`)

### Summary

When the operator set is empty (zero operators), `get_num_required_nofn_sigs` returns 0, causing the entire MuSig2 signing pipeline to complete trivially with no signatures collected or verified. A deposit finalizes successfully, the move-tx is broadcast, and BTC is transferred to the vault UTXO — but with no operator to ever front a withdrawal, the BTC is permanently locked. No existing guard in `is_deposit_valid` or the aggregator's `new_deposit` rejects a zero-operator deposit.

### Finding Description

**Root cause 1 — `get_num_required_nofn_sigs` collapses to zero:**

```rust
pub fn get_num_required_nofn_sigs(&self, deposit_data: &DepositData) -> usize {
    deposit_data.get_num_operators()          // ← 0 when no operators
        * self.protocol_paramset().num_round_txs
        * self.protocol_paramset().num_signed_kickoffs
        * self.get_num_required_nofn_sigs_per_kickoff(deposit_data)
}
``` [1](#0-0) 

With `get_num_operators() == 0`, the product is 0. Every downstream check that compares `total_sigs == needed_nofn_sigs` (0 == 0) passes vacuously.

**Root cause 2 — `is_deposit_valid` has no minimum-operator guard:** [2](#0-1) 

The function checks uniqueness, watchtower limits, security council, and script correctness — but never asserts `deposit_data.get_num_operators() > 0`. When both `operators_in_db` and `operators_in_deposit_data` are empty, both loops are no-ops and the function returns `Ok(())`.

**Execution trace with 0 operators:**

1. **Aggregator `new_deposit`** — `fetch_operator_keys()` returns `Ok(vec![])` when `operator_clients` is empty (zero endpoints configured, or all operators have exited and their keys are absent). `DepositData.actors.operators` is `vec![]`. [3](#0-2) 

2. **`nonce_aggregator`** — `needed_nofn_sigs = 0`; the `while let Some(msg) = sighash_stream.next()` loop never executes; the sanity check `total_sigs != needed_nofn_sigs` → `0 != 0` → false; function returns `Ok(...)`. [4](#0-3) 

3. **`collect_operator_sigs`** — `operator_clients.clients()` is empty; `timed_try_join_all` over an empty iterator returns `Ok(vec![])` immediately; the per-operator signature check loop never executes; returns `Ok(vec![])`. [5](#0-4) 

4. **Verifier `deposit_sign`** — `num_required_sigs = 0`; the `agg_nonce_rx.recv()` loop never fires; the nonce count check `num_required_sigs + 2 != session.nonces.len()` → `2 != 2` → false; returns successfully. [6](#0-5) 

5. **Verifier `deposit_finalize`** — `num_required_nofn_sigs = 0`; `num_required_total_op_sigs = 0 * 0 = 0`; both verification loops are no-ops; the verifier signs the move-tx and returns a valid partial signature. [7](#0-6) [8](#0-7) 

6. **Move-tx broadcast** — The aggregator aggregates verifier partial signatures, constructs the move-tx, and broadcasts it. BTC moves from the deposit UTXO to the vault UTXO. [9](#0-8) 

**Result:** BTC is now in the vault UTXO controlled by the verifiers' NofN key. No operator exists to call `withdraw`, front a payout, or initiate a kickoff/reimburse cycle. The BTC is permanently locked with no protocol-level recovery path.

### Impact Explanation

Bridged BTC is permanently locked in the vault UTXO. No operator can front a withdrawal (none exist), no kickoff/reimburse cycle can be initiated, and no payout transaction can be created. This is a permanent, irrecoverable loss of user funds — equivalent to the H-04 scenario where depositors' funds are transferred to the counterparty vault and they receive nothing back.

### Likelihood Explanation

Two realistic triggers exist:

1. **All operators exit the protocol** — Operators spend their collateral (legitimate exit). The verifier's `is_deposit_valid` check allows deposits with 0 active operators because the collateral-usability loop only rejects operators that are *in the deposit data but have spent collateral*, not the case where the deposit data has 0 operators and all DB operators have spent collateral. [10](#0-9) 

2. **Aggregator configured with 0 operator endpoints** — `fetch_operator_keys()` returns an empty vec without error when `operator_clients` is empty. [11](#0-10) 

### Recommendation

Add an explicit minimum-operator guard in `is_deposit_valid` in `core/src/verifier.rs`:

```rust
if deposit_data.get_num_operators() == 0 {
    return Err(BridgeError::InvalidDeposit(
        "Deposit must include at least one operator".to_string()
    ));
}
```

Additionally, add the same guard in the aggregator's `new_deposit` before constructing `DepositData`, and add a non-zero assertion in `get_num_required_nofn_sigs` or its callers to prevent silent zero-signature acceptance.

### Proof of Concept

1. Deploy Clementine with verifiers but zero operator endpoints (or wait until all operators spend their collateral).
2. Submit a deposit via `aggregator.new_deposit(...)`.
3. Observe: `fetch_operator_keys()` returns `[]`; `get_num_required_nofn_sigs` returns 0; `nonce_aggregator`, `signature_aggregator`, and `collect_operator_sigs` all complete with 0 items; `is_deposit_valid` returns `Ok(())`; verifiers sign the move-tx.
4. The move-tx is broadcast and confirmed on Bitcoin. BTC is now in the vault UTXO.
5. Attempt any withdrawal — no operator exists to call `withdraw` or `get_reimbursement_txs`. The BTC is permanently locked. [12](#0-11) [1](#0-0) [13](#0-12)
