## Analysis

I traced the exact path: `x/erc20/ibc_middleware.go:53-67` (`IBCMiddleware.OnRecvPacket`) first calls the wrapped ICS20 transfer app via `im.Module.OnRecvPacket` [1](#0-0) , which unescrows/mints the bank `Coin` to the recipient directly against the live `sdk.Context` (no `CacheContext` boundary is used around this call). Only if that succeeds does it hand off to `k.OnRecvPacket` in `x/erc20/keeper/ibc_callbacks.go` [2](#0-1) .

For the "native ERC20" case (`pair.IsNativeERC20()`), if `k.MintingEnabled` fails after the underlying transfer already unescrowed/minted funds to the recipient, the middleware discards the original success ack and returns a brand-new `channeltypes.NewErrorAcknowledgement(err)` [3](#0-2) . Because there is no `ctx.CacheContext()`/`writeFn()` pattern wrapping the initial transfer + conversion attempt (unlike the pattern correctly used elsewhere, e.g. `x/ibc/callbacks/keeper/keeper.go:129-227` which does use `CacheContext`/`writeFn` to make state changes conditional), the already-completed unescrow to the recipient is **not rolled back** when the error ack is produced.

The test suite itself documents this exact behavior: `evmd/tests/ibc/ibc_middleware_test.go:728-808` sets `SendEnabled=false` on the native ERC20 denom (which is precisely what makes `MintingEnabled`'s `IsSendEnabledCoin` check fail at `x/erc20/keeper/mint.go:60-64`), sends a packet, and the comment states plainly: *"SendEnabled=false will cause the conversion of bank tokens to erc20 tokens to fail, but not send them back to escrow"* [4](#0-3) . This confirms the destination-chain unescrow persists despite the error acknowledgement.

Reviewing `MintingEnabled`'s failure conditions [5](#0-4) , the `BlockedAddr` check cannot be abused by an attacker because all blocked addresses correspond to module accounts that are pre-instantiated at genesis via `maccPerms`, and are already filtered out earlier by `types.IsModuleAccount(receiverAcc)` at `x/erc20/keeper/ibc_callbacks.go:65-70`. However, the `IsSendEnabledCoin` failure is realistically reachable: native-ERC20-backed token pairs commonly have `SendEnabled=false` on their bank denom by design (to force transfers through the ERC20/precompile path), meaning an **ordinary, unprivileged user** performing a standard IBC round-trip transfer of such a token back to its origin chain will hit this exact failure path — no governance or validator collusion required.

The consequence: the origin chain unescrows/releases the collateral to the recipient's bank balance (permanent, uncommitted state change that isn't reverted), while the error acknowledgement causes the counterparty chain to refund/re-mint the burned voucher back to the original sender — resulting in the same value existing simultaneously on both chains, i.e., unauthorized duplication of escrowed value.

### Title
Unrolled-back unescrow on ERC20 minting-check failure causes double-crediting across IBC chains - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
`IBCMiddleware.OnRecvPacket` lets the underlying ICS20 transfer complete (unescrowing/minting bank coins to the recipient) before invoking `erc20keeper.OnRecvPacket`. When `MintingEnabled` subsequently fails for a native-ERC20 token pair (e.g. bank `SendEnabled=false` for that denom — a routine/default configuration), the code converts the outcome into an error acknowledgement without reverting the already-completed unescrow, because no `CacheContext`/`writeFn` boundary protects the combined operation.

### Finding Description
`x/erc20/ibc_middleware.go:53-67` calls `im.Module.OnRecvPacket` (the standard ICS20 transfer callback) directly against the live context, then conditionally calls `k.OnRecvPacket`. Inside `x/erc20/keeper/ibc_callbacks.go:118-139`, for `pair.IsNativeERC20()`, a `MintingEnabled` failure (routinely triggered by `IsSendEnabledCoin` returning false, per `x/erc20/keeper/mint.go:60-64`) results in `channeltypes.NewErrorAcknowledgement(err)` being returned — overriding the prior successful transfer ack — while the unescrow performed moments earlier by the wrapped transfer module remains committed to state. [2](#0-1) 

### Impact Explanation
When the counterparty chain receives this error acknowledgement, it will refund/re-mint the burned voucher tokens back to the original sender, per standard ICS20 semantics. Combined with the un-reverted unescrow on the receiving chain, the same collateral value now exists concurrently on both chains — an unauthorized duplication of spendable value, which is a Critical accounting-corruption impact.

### Likelihood Explanation
High. This does not require any privileged actor. It is triggered by an ordinary user performing a standard IBC transfer of a native-ERC20-backed token back to its origin chain when that denom has `SendEnabled=false` (a routine/default state for such pairs, as demonstrated directly in `evmd/tests/ibc/ibc_middleware_test.go:728-754`).

### Recommendation
Wrap the underlying transfer callback and the erc20 conversion/`MintingEnabled` check in a single `ctx.CacheContext()` region, only calling `writeFn()` once the entire flow (unescrow + ERC20 conversion) is confirmed final, or explicitly revert the unescrow before returning an error acknowledgement in `x/erc20/keeper/ibc_callbacks.go`.

### Proof of Concept
1. Register a native-ERC20 token pair and disable `SendEnabled` for its bank denom (as done in `evmd/tests/ibc/ibc_middleware_test.go:733`).
2. Send that token's IBC voucher from chain B back to origin chain A.
3. On chain A, `im.Module.OnRecvPacket` unescrows the coin to the recipient (verify non-zero recipient balance / zero escrow balance).
4. `k.MintingEnabled` fails due to `SendEnabled=false`; `IBCMiddleware.OnRecvPacket` returns an error ack.
5. Simulate chain B processing the error ack via `OnAcknowledgementPacket`/refund logic, re-minting the voucher to the original sender.
6. Assert total value across both chains now exceeds the original escrowed amount (chain A recipient balance + chain B refunded balance > original transfer amount).

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}

func (k Keeper) MintingEnabled(
	ctx sdk.Context,
	receiver sdk.AccAddress,
	token string,
) (types.TokenPair, error) {
	if !k.IsERC20Enabled(ctx) {
		return types.TokenPair{}, errorsmod.Wrap(
			types.ErrERC20Disabled, "module is currently disabled by governance",
		)
	}

	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	if !pair.Enabled {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrERC20TokenPairDisabled, "minting token '%s' is not enabled by governance", token,
		)
	}

	if k.bankKeeper.BlockedAddr(receiver.Bytes()) {
		return types.TokenPair{}, errorsmod.Wrapf(
			errortypes.ErrUnauthorized, "%s is not allowed to receive transactions", receiver,
		)
	}

	// NOTE: ignore amount as only denom is checked on IsSendEnabledCoin
	coin := sdk.Coin{Denom: pair.Denom}

	// check if minting to a recipient address other than the sender is enabled
	// for for the given coin denom
	if !k.bankKeeper.IsSendEnabledCoin(ctx, coin) {
		return types.TokenPair{}, errorsmod.Wrapf(
			banktypes.ErrSendDisabled, "minting '%s' coins to an external address is currently disabled", token,
		)
	}

	return pair, nil
