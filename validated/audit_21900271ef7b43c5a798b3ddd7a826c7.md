## Title
Stale line-index diff selection allows silent commit/push of unreviewed content on working-tree change (TOCTOU) - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop tracks a user's partial-commit line selection as a set of **absolute line indices** into a previously loaded diff (`DiffSelection`), not as content-addressed selections. When staging a partially-selected file, `applyPatchToIndex` re-fetches a **fresh** diff from disk and reuses the **stale** selection indices to build the patch that is actually applied to the index and eventually committed/pushed. If the working-directory file content changes between the moment the user reviewed/selected lines in the UI and the moment staging occurs, the indices silently point to different lines than what the user reviewed, so the wrong hunks/lines get committed without any warning.

### Finding Description
The selection model is purely index-based: `DiffSelection` stores selected line numbers, and `formatPatch` decides what to include solely via `file.selection.isSelected(absoluteIndex)` against whatever diff is handed to it. [1](#0-0) 

`applyPatchToIndex` — invoked from `stageFiles` for every file with a partial selection — re-fetches the diff from the working directory at staging time and hands it to `formatPatch` together with the file's (already computed) `.selection`: [2](#0-1) 

That selection, however, was computed earlier by the UI against a *different* diff snapshot that was rendered when the user made their choice. The app's own refresh logic acknowledges this gap but only patches over part of it: when the diff changes it removes lines that are no longer "includeable" (turned into context/removed), but it explicitly does **not** validate that surviving selected indices still correspond to the same content: [3](#0-2) 

`updateChangedFiles`, called on every `_loadStatus`, further compounds this by unconditionally re-attaching the old `existingFile.selection` object onto the newly-fetched file/diff pairing, with no check that line offsets still line up with the new diff's hunks: [4](#0-3) 

Because line numbering shifts whenever lines are inserted/removed above a given hunk, an index that was valid ("select line 42 = the malicious payload line") can, after an external edit, silently refer to a completely unrelated line (e.g. a legitimate comment) — and vice versa: a line the user explicitly deselected can shift into becoming a still-"includeable" and still-marked-selected index, causing it to be silently included.

### Impact Explanation
This breaks the core invariant of the partial-commit ("selective staging") feature: what git actually stages/commits must be exactly what the user visually selected in the diff viewer. Because indices are the source of truth and are never re-validated for *content* equality (only for “is this offset still includeable”), a background process that legitimately modifies files in the working directory between the user's selection and the click on "Commit" (a file watcher-triggered formatter, linter --fix, IDE autosave, a build/lint script from `package.json`, or a git hook such as `post-checkout`/`pre-commit` invoked from an untrusted cloned repository) can cause Desktop to commit and push content the user never selected/reviewed — i.e., silent corruption of what the user commits, without any error or confirmation dialog. This can be used to smuggle attacker-controlled content into a commit the user believes only contains their reviewed lines, or to drop an intended security-relevant hunk (e.g. a line the user selected to include) from the final commit.

### Likelihood Explanation
Requires no elevated privileges: it only requires that some process with normal write access to the working directory (a build tool, watcher, formatter, or a script defined inside the cloned repository itself and invoked by ordinary developer workflows like running `npm install`/`npm run build` while Desktop is open) touches the file being partially staged during the window between diff-render and stage/commit. Desktop already re-fetches status/diff on file-system events, so this window is realistically reachable in normal day-to-day usage rather than a purely theoretical race, and the code comment in `app-store.ts` shows the team is aware selection re-validation is incomplete ("Ideally we would be more clever about validating that any partial selection state is still valid... but for now we'll settle on just updating the selectable lines").

### Recommendation
Do not key the persisted selection purely by hunk-relative absolute line index across diff reloads. Instead, when a new diff is loaded for a file with an existing partial selection, remap the selection based on line *content* (e.g., diff the old and new hunks and translate previously selected line content into new indices, dropping any that no longer exist), and re-validate/re-diff the file immediately before `applyPatchToIndex` builds and applies the patch (fail/prompt the user if the diff used for staging differs from the diff last rendered) rather than silently reusing indices computed against a stale diff.

### Proof of Concept
1. In a repo with a modified text file, open the Changes view; partially select only certain lines (line-based diff selection) but do not commit yet.
2. While the commit is pending, have an external process (e.g. a save-on-change formatter, an npm script, or a git hook from the cloned repo) insert/remove lines above the hunk in that same file, shifting line numbers but not necessarily triggering a fresh review by the user (the UI diff may auto-refresh but the stale in-memory `DiffSelection` indices are carried over per `updateChangedFiles`/`app-store.ts:3478-3497`).
3. Click "Commit selected changes." `stageFiles` → `applyPatchToIndex` fetches the now-current diff via `getWorkingDirectoryDiff` and calls `formatPatch(file, diff)` using the old selection indices.
4. Inspect the resulting commit: it contains lines at those indices from the *new* diff content, not the lines the user actually selected/reviewed, demonstrating silent corruption of the committed content.
