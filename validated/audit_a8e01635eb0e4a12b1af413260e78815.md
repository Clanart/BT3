## Analysis

The bug report's core invariant: a **prepaid entitlement created earlier can be nullified by unrelated activity happening later, before the entitlement holder ever gets to use what they paid for** — the vlPenpie user locked tokens, then a later config/action retroactively made their existing lock harder to exit without extra unprivileged actions from others.

The strongest local analog is `pallet-bandwidth`'s FIFO subscription list. Any unprivileged relayer can trigger `on_accept` by delivering purchase messages, and the eviction logic runs purely on user-triggered purchase volume — no admin action needed, unlike the `set_manager`/`set_tier` paths (which I ruled out as they require `AdminOrigin`, matching the gate's exclusion of governance-actor scenarios). ### Title
Bandwidth Subscription FIFO Eviction Destroys Unconsumed Prepaid Bytes Before Expiry - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth` credits every purchase as a new `Subscription` appended to a per-`(app_chain, app)` `BoundedVec` capped at `MAX_SUBSCRIPTIONS = 1024`. Once the cap is hit, `push_subscription` unconditionally evicts index `0` (the oldest, still-unspent subscription) to make room for the new one — regardless of whether that oldest subscription has any `remaining_bytes` left or how long until it naturally expires.

### Finding Description
`push_subscription` is invoked from `on_accept` for every incoming purchase message from the registered `BandwidthManager`, with no privileged gating: any account able to fund a purchase on the source EVM chain can drive purchase volume for a given `(app_chain, app)` key. When the 1024-slot cap is reached, the function evicts `list.remove(0)` — the earliest unconsumed subscription — and deposits `SubscriptionEvicted { lost_bytes: old.remaining_bytes }` as the only record. [3](#0-2) 

This mirrors the reported invariant break exactly: an app that legitimately locked in bandwidth (paid for and not yet consumed) can lose that entitlement purely because *other, unrelated* purchases for the same `(app_chain, app)` key accumulated past the cap first — the victim did nothing wrong and had no chance to consume their allowance before it was silently destroyed. The `try_consume` gate itself only drains from the front and never protects against this eviction path; the only remediation available to the app is to "purchase more" to requeue, exactly the "lock more to unlock" unfairness pattern from the source report. [4](#0-3) 

Because `AppKey` is a 32-byte value keyed only by `(app_chain, app)`, and the pallet doc itself states "any deployment can sponsor any app on any chain," an attacker (or just heavy legitimate traffic) purchasing many small, cheap tiers for the *same* `(app_chain, app)` pair can rapidly fill the 1024-slot FIFO and evict all prior purchasers' unconsumed byte balances — a griefing/fund-loss vector reachable by any unprivileged account with enough fee-token balance to buy the cheapest tier repeatedly. [5](#0-4) 

### Impact Explanation
This is a loss-of-funds vector: bandwidth is a prepaid asset (paid for via `BandwidthManager.sol` in real fee tokens), and legitimately purchased-but-unconsumed bytes are irrecoverably destroyed once evicted — there is no refund path, only an audit event. A high-traffic app or a griefer targeting a specific `(app_chain, app)` pair can force premature eviction of another purchaser's paid allowance well before its `expires_at`, causing direct financial loss without needing any relayer, prover, or admin compromise.

### Likelihood Explanation
Likelihood is bounded by the cost of buying 1024 cheap-tier purchases to force the wraparound, and by the fact that `AppKey` collisions require targeting the exact same `(app_chain, app)` pair as the victim, which is knowable on-chain via `BandwidthCredited` events. For high-volume or shared app identifiers this is realistically triggerable with normal purchase activity alone, not requiring intentional griefing.

### Recommendation
Do not silently evict subscriptions with nonzero `remaining_bytes`; either grow the bound dynamically, merge/compact same-tier entries instead of queuing them, refund the fee-token equivalent of `lost_bytes` back to the evicted purchaser via a cross-chain `Withdraw` message, or reject new purchases once the cap is reached (forcing the buyer to wait rather than destroying someone else's balance).

### Proof of Concept
1. Governance configures a cheap `TierIndex` via `set_tier` (long-lived duration, minimal bytes) — a normal setup step, not an exploit.
2. Victim purchases bandwidth for `(app_chain=X, app=Y)`; a `Subscription` is appended at some index `k`.
3. Attacker (or organic traffic) repeatedly triggers purchase messages for the identical `(app_chain=X, app=Y)` key until `Allowance::<T>::get(X, Y).len()` reaches `MAX_SUBSCRIPTIONS = 1024`.
4. The next purchase for `(X, Y)` calls `push_subscription`, which executes `list.remove(0)`, evicting the victim's still-unconsumed subscription (assuming it is now at the front due to FIFO drain order) and emitting `SubscriptionEvicted { lost_bytes: victim_remaining }`.
5. Victim's `remaining()`/`allowances()` no longer reflects the paid-for bytes, and no on-chain mechanism refunds the loss. [6](#0-5)

//! # pallet-bandwidth
//!
//! Prepaid `(chain, app)` byte balances credited by tier purchases
//! from `BandwidthManager.sol`. Each purchase carries its own
//! `app_chain`, so any deployment can sponsor any app on any chain.
//!
//! Each `(chain, app)` row holds a FIFO list of [`Subscription`]s

//! subscription with a fixed `expires_at`; expiry never extends and
//! same-tier repurchases don't stack — they queue. The gate drains
//! the oldest live subscription first; once empty it moves to the
//! next. Subscriptions that aren't reached before their expiry are
//! swept silently — what you paid for is yours only until it expires.
//! Pushes onto a full list evict the oldest entry and emit

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
