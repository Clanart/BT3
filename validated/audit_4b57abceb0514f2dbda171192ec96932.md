### Title
PedPoP blame proof reveals the ECDH shared key before the message's proof-of-possession is verified, letting a malicious sender leak another participant's encrypted secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` returns an `EncryptionKeyProof` (containing the ECDH shared point `enc_key_b * msg.key`) inside `PedPoPError::InvalidShare` when the decrypted share bytes fail `from_repr`, **before** the queued PoP `SchnorrSignature` batch verification ever runs. A malicious participant can copy an honest sender's per-message encryption key `X` into their own `EncryptedMessage` (without knowing `x`, so the PoP is invalid), and the victim still produces and publishes a valid blame proof revealing `b·X`. Because the PoP exists specifically to prevent this co-option of keys, leaking the blame proof anyway lets anyone decrypt the original honest message that used `X`, exposing an encrypted DKG secret share. This is the exact bug class of GHSA-v7x3-7hw7-pcjg: secret material leaked into a public artifact (blame proof / `ProcessorMessage::InvalidShare`) during an error-handling path.

### Finding Description
In `calculate_share`, each incoming `EncryptedMessage` is processed by `Encryption::decrypt`, which queues the PoP into the batch verifier and *eagerly* computes an `EncryptionKeyProof` containing the raw ECDH point [1](#0-0) . If `C::F::from_repr(share_bytes.0)` fails, the function returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` immediately, without calling `batch.verify_with_vartime_blame()` [2](#0-1) . The PoP is the sole defense against key co-option — the code comments state that without it, Eve can reuse Alice's `key` field `X`, Bob's blame would reveal `bX`, "revealing Alice's message to Bob" and calling it "a massive side effect" [3](#0-2) . But because the blame proof (a valid DLEq over `enc_key_b`) is produced and returned prior to PoP verification, the protection is bypassed on this error path. The processor then publishes the blame: `blame: Some(blame.map(|blame| blame.serialize())).flatten()` inside `ProcessorMessage::InvalidShare` [4](#0-3) , and `VerifyBlame` accepts it since `decrypt_with_proof` only checks the DLEq, which is legitimately generated [5](#0-4) .

### Impact Explanation
An unprivileged DKG participant Eve sends Bob a `EncryptedMessage` whose `key` field is copied from Alice's encrypted share to Bob (`X = aG`) with arbitrary ciphertext and an invalid PoP. Bob's ECDH `b·X` is identical to the shared key protecting Alice's share. The blame proof Bob publishes reveals `b·X` (verifiably correct via the DLEq), so every observer can derive the ChaCha20 keystream via `cipher(context, b·X)` and decrypt Alice's secret share `f_alice(bob)` — a share of the threshold secret key the DKG is meant to keep private. Even though the DKG aborts after blame, a leaked share weakens future/related uses (e.g., the same share bytes re-checked by `AdditionalBlameMachine`, or retries), and the spec itself classifies this side effect as "massive" [6](#0-5) .

### Likelihood Explanation
Eve only needs to submit one malformed share message — something she already does legitimately each DKG round. Random garbage decrypts to a non-canonical scalar with overwhelming probability (≈ 1 − l/2^256 for Ristretto), so the early-return error path is reliably reached in a single attempt; if it lands canonical, the batch verifier catches the bad PoP and no blame key is leaked, letting her retry on a later attempt. Reachable purely with public/protocol inputs: an `EncryptedMessage` she authors.

### Recommendation
Do not attach an `EncryptionKeyProof` to `PedPoPError::InvalidShare` until the PoP for that message has been verified. Options: verify `msg.pop` eagerly (non-batch) before computing/returning the proof in `Encryption::decrypt`, or hold the `blames` map unpublished and only release a proof once `batch.verify_with_vartime_blame()` confirms the PoP passed (e.g., return `blame: None` whenever the message never survived PoP verification, including the `from_repr` early return).

### Proof of Concept
1. Run a PedPoP DKG with participants including Alice (1), Bob (2), Eve (3).
2. Alice encrypts her share to Bob: `encrypt(rng, ctx, Alice, Bob.enc_pub_key, share)` producing `EncryptedMessage { key: X, pop, msg: CT }` (`encryption.rs:135-168`).
3. Eve constructs `EncryptedMessage { key: X, pop: <invalid signature>, msg: <random bytes> }` and sends it to Bob as her share.
4. Bob's `KeyMachine::calculate_share` calls `self.encryption.decrypt(...)`: PoP is queued (not verified), ECDH `b·X` is computed, `CT_eve` decrypts to garbage, `from_repr` fails → `InvalidShare { participant: Eve, blame: Some(proof) }` with `proof.key = b·X`.
5. Bob emits `ProcessorMessage::InvalidShare { blame: proof.serialize() }`, publicly revealing `b·X`.
6. Anyone computes `cipher(context, b·X)` and applies the keystream to Alice's `CT`, recovering Alice's secret share — precisely the leak the PoP was added to prevent, bypassed because the blame proof escaped before PoP verification.

While key reuse by a participant is considered as them revealing the messages
themselves, and therefore out of scope, there is an attack where a malicious
adversary claims another participant's encryption key. They'll fail to encrypt
their message, and the recipient will issue a blame statement. This blame
statement, intended to reveal the malicious adversary, also reveals the message
by the participant whose keys were co-opted. To resolve this, a
proof-of-possession is also included with encrypted messages, ensuring only
those actually with per-message keys can claim to use them.
