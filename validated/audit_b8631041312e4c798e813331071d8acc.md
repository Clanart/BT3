Confirmed: `txpool_content` (`TxPoolAPI`) is registered unconditionally on the public HTTP RPC in `NewEVMHTTPServer` [1](#0-0) , is not gated behind the `debug` namespace or any admin/auth check, and its `Content` handler pulls every unconfirmed transaction straight from the mempool via `tmClient.UnconfirmedTxs` and returns full transaction bodies (from, to, value, gas, input calldata, nonce, signature) keyed by sender [2](#0-1) .

### Title
Public `txpool_content` RPC discloses full pending-transaction contents, enabling front-running/MEV extraction - (File: `evmrpc/txpool.go`)

### Summary
The `txpool` namespace is registered on the default, unauthenticated public EVM JSON-RPC HTTP server alongside `eth`, `net`, and `web3` [1](#0-0) . Any remote, unprivileged client can call `txpool_content` and receive the decoded contents (sender, recipient, value, calldata, gas price fields, nonce, raw signature) of every mempool transaction not yet included in a block [2](#0-1) .

### Finding Description
`Content` iterates `t.tmClient.UnconfirmedTxs`, decodes each pending EVM transaction, recovers the sender address, and serializes the transaction (`export.NewRPCPendingTransaction`) into the response, including calldata and value [3](#0-2) . This is registered without any restriction in the default HTTP RPC API set [4](#0-3) , and the test suite confirms the response includes full transaction fields (from, to, value, input, gas, signature) for any observer [5](#0-4) . This mirrors the CWE-200 pattern in the referenced advisory: a component that should keep operational/internal data private inadvertently discloses it to unauthenticated remote callers.

Full visibility into pending transaction contents (not just hashes) before block inclusion allows any observer to decode a victim's swap/arbitrage/liquidation transaction and construct a competing transaction to front-run or sandwich it (classic MEV extraction), directly causing fund loss to the original sender through worse execution price or a stolen arbitrage/liquidation opportunity.

### Impact Explanation
This satisfies the "concrete fund loss" bar in the validation criteria: exposing the exact calldata and value of a pending swap, liquidation, or arbitrage transaction lets an adversary construct and submit a transaction that captures the value (front-running/sandwiching) at the expense of the original sender, or steals a time-sensitive liquidation/arbitrage opportunity. This is worse than typical Ethereum mempool exposure because Sei's block cadence and instant-finality design compress the response window, but the fundamental exposure is that the full transaction body — not merely existence/hash — is available to any public RPC caller pre-inclusion.

### Likelihood Explanation
High likelihood: no authentication, no rate limiting specific to this method beyond generic RPC limits, and it is enabled by default in `NewEVMHTTPServer`'s API list. Any address broadcasting a transaction through `eth_sendRawTransaction` has its full pending transaction visible to competitors via a single unauthenticated `txpool_content` call before the transaction lands on-chain.

### Recommendation
Restrict `txpool_content` (and any equivalent `txpool_*` method) so it does not leak calldata/value/from for transactions belonging to other senders, or gate the namespace behind an explicit opt-in/authenticated admin flag (similar to how `debug` and `test` namespaces are already conditionally enabled). At minimum, mask/redact calldata and value for transactions not originating from the caller, or restrict the endpoint to local-only listeners.

### Proof of Concept
1. Have victim submit a profitable transaction (e.g., a DEX swap or liquidation call) via `eth_sendRawTransaction`.
2. Before the transaction is included, call `txpool_content` on the public RPC endpoint:
   ```
   curl -X POST -d '{"jsonrpc":"2.0","method":"txpool_content","params":[],"id":1}' http://<node>:8545
   ```
3. The response returns the victim's full transaction — `from`, `to`, `value`, `input` (calldata), `gas`, `nonce`, and signature — as demonstrated by the integration test assertions [5](#0-4) .
4. An attacker decodes the calldata, constructs a competing transaction with higher priority, and submits it ahead of/around the victim's transaction to capture the value (front-run/sandwich), resulting in direct fund loss to the victim.

```go
// Content returns the content of the txpool.
// for now, we put all unconfirmed txs in pending and none in queued.
func (t *TxPoolAPI) Content(ctx context.Context) (result map[string]map[string]map[string]*export.RPCTransaction, returnErr error) {
	startTime := time.Now()
	defer func() {
		recordMetricsWithError(ctx, "sei_content", t.connectionType, startTime, returnErr, recover())
	}()
	content := map[string]map[string]map[string]*export.RPCTransaction{
		"pending": make(map[string]map[string]*export.RPCTransaction),
		"queued":  make(map[string]map[string]*export.RPCTransaction),
	}

	total := t.txPoolConfig.maxNumTxs
	resUnconfirmedTxs, err := t.tmClient.UnconfirmedTxs(ctx, nil, &total)
	if err != nil {
		return nil, err
	}

	sdkCtx := t.ctxProvider(LatestCtxHeight)
	for _, tx := range resUnconfirmedTxs.Txs {
		ethTx := getEthTxForTxBz(tx, t.txConfigProvider(LatestCtxHeight).TxDecoder())
		if ethTx == nil { // not an evm tx
			continue
		}
		fromAddr, err := rpcutils.RecoverEVMSenderWithContext(sdkCtx, ethTx)
		if err != nil {
			return nil, err
		}
		nonce := ethTx.Nonce()
		chainConfig := types.DefaultChainConfig().EthereumConfig(t.keeper.ChainID(sdkCtx))
		res := export.NewRPCPendingTransaction(ethTx, nil, chainConfig)
		nonceStr := strconv.FormatUint(nonce, 10)
		if content["pending"][fromAddr.String()] == nil {
			content["pending"][fromAddr.String()] = map[string]*export.RPCTransaction{
				nonceStr: res,
			}
		} else {
			content["pending"][fromAddr.String()][nonceStr] = res
		}
	}
	return content, nil
```
