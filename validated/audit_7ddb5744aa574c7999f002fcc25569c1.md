### Title
Hard 8000-char truncation of `diff_text` in `build_refute_prompt` lets a padded diff push a genuine finding's evidence out of the adversarial-verifier's view, causing a false REFUTE - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` embeds the diff into the stage-2 adversarial-verifier prompt with a raw `diff_text[:8000]` slice and no truncation marker, unlike the properly-capped/annotated diff used at investigate stage (`cap_diff_for_prompt` in `build_investigate_prompt`). An attacker who controls diff size/ordering (e.g. via many touched files or a large earlier hunk) can push the actual vulnerable `+` lines past byte 8000, so the refute-stage model — which is explicitly instructed to refute as "PRE-EXISTING" any cited code that "does NOT appear on any + line in the DIFF block above" — sees a DIFF block that no longer contains that evidence, and can validly conclude REFUTE for a genuinely newly-introduced vulnerability.

### Finding Description
`build_refute_prompt` at [1](#0-0)  constructs the stage-2 prompt as:
```
"\n\nDIFF:\n" + diff_text[:8000]
```
This is a hard string slice with no per-file cap, no total-byte accounting, and — critically — no truncation marker of the kind `cap_diff_for_prompt` inserts ("... [truncated by security-guidance: ...]") at [2](#0-1) . The investigate-stage prompt (`build_investigate_prompt`, [3](#0-2) ) runs the full diff through `cap_diff_for_prompt` first, so its truncation is per-file, bounded, and explicitly flagged to the model. The refute-stage instead concatenates the same full multi-file `diff_text` and blindly truncates the combined string at a fixed 8000-character boundary.

The refute system prompt then instructs the verifier to treat absence from the visible DIFF block as proof of non-introduction: `"PRE-EXISTING: the cited vulnerableCode does NOT appear on any + line in the DIFF block above — it is unchanged context in a touched file. The diff did not introduce it."` ( [4](#0-3) ). If the genuinely offending `+` line falls after the 8000-character cut, this rule fires incorrectly — the model has no way to distinguish "not in the diff" from "diff was truncated before this point," because no truncation marker is present in the refute prompt to warn it.

Because `diff_text` is assembled by joining per-file diff blocks (`"=== DIFF: {fp} ===\n{content}"`) in file order, an attacker who controls the diff content (i.e., the code change being reviewed, whether authored directly or produced by an agent acting on attacker-influenced instructions/repo content) can pad earlier files or hunks with large benign-looking diff content to push their actual malicious hunk past the 8000-character window that reaches the refute stage, while the investigate stage (using the properly capped, larger `DIFF_TOTAL_BYTES=400000`/`DIFF_PER_FILE_BYTES=80000` budget) still correctly flags it as a candidate. The candidate then survives to stage 2 with genuine content, but stage 2 cannot see the corroborating diff evidence and can legitimately mark it REFUTED per the PRE-EXISTING rule, silently dropping the finding from the developer-facing output.

### Impact Explanation
This breaks the stated invariant that "prompt assembly must not let untrusted repo content suppress review of dangerous changes." A successfully refuted candidate is dropped entirely — `agentic_review` returns `(None, [], metrics)` if all candidates are refuted ( [5](#0-4) ) — meaning the developer/user never sees the guidance for a real vulnerability that the investigate stage did correctly detect. This matches "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries": the security-guidance plugin's own review pipeline can be made to suppress its own finding via diff size/ordering, independent of any LLM prompt-injection risk (i.e., it is a deterministic formatting/truncation defect, not merely a model-susceptibility concern).

### Likelihood Explanation
Reachability requires only that the attacker (whoever authors or causes the diff content — a malicious/careless contributor, or an agent acting on attacker-influenced task content) can control the size and ordering of the diff being reviewed, which is normal, unprivileged repo-content control. No local shell access, credentials, or special privilege is needed. The trigger condition (moving the malicious hunk past 8000 characters into the combined diff string) is easy to engineer deterministically by padding an earlier touched file's diff. The remaining variable is whether the refute-stage LLM, when explicitly told the vulnerable code doesn't appear in the visible DIFF block, actually returns REFUTE — this is a model-behavior dependency, but the prompt's own explicit PRE-EXISTING rule instructs exactly this outcome, making it a reasonably likely, repeatable effect. The 1 ≤ candidates ≤ 2 iterative-investigate re-check in `llm.py` does not mitigate this, since it operates on the same untruncated-vs-truncated split.

### Recommendation
- Apply the same `cap_diff_for_prompt` per-file/total-byte capping (with explicit truncation markers) to the diff embedded in `build_refute_prompt`, instead of a bare `diff_text[:8000]` slice.
- If a global length budget is still needed for the refute stage, truncate per-file after joining, inserting an explicit `[... diff truncated by security-guidance ...]` marker so the model knows content is missing, and never truncate mid-file in a way that could hide a candidate's own touched file.
- Alternatively, guarantee that all files referenced by any surviving candidate are included in full in the refute-stage diff text before applying any length budget to the remaining, non-candidate-referenced files.

### Proof of Concept
Unit test in `plugins/security-guidance/hooks/review_api.py` test suite:
1. Construct `diff_files` with two files: `noise.py` containing >8000 characters of benign filler diff, and `victim.py` containing a small `+`-line diff hunk with a clearly attacker-controlled dangerous pattern (e.g. `+ os.system(user_input)`).
2. Build `diff_text = "\n\n".join(f"=== DIFF: {fp} ===\n{content}" for fp, content in [("noise.py", noise_diff), ("victim.py", victim_diff)])` matching how callers assemble it before calling `build_refute_prompt`.
3. Construct a `candidates` list containing one dict citing `filePath="victim.py"`, `vulnerableCode="os.system(user_input)"`.
4. Call `prompt = build_refute_prompt(candidates, diff_text)`.
5. Assert that `"os.system(user_input)"` (the dangerous line) is **not** present in `prompt` (demonstrating it was truncated out of the visible DIFF block) while it **is** present in the full `diff_text` — proving the refute-stage prompt loses the evidence needed to correctly evaluate the candidate.
6. Additionally assert that no truncation marker (e.g. `"truncated"`) appears anywhere in the generated prompt, confirming the model receives no signal that content was cut, unlike `cap_diff_for_prompt`'s explicit markers ( [2](#0-1) ).

Expected result (current code): assertions in step 5/6 pass, confirming the vulnerable evidence is silently dropped from the refute prompt with no truncation warning — validating the finding without requiring any live LLM call.

def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,
    context_note: str = "",
) -> str:
    capped, _ = cap_diff_for_prompt(diff_files)
    diff_text = "\n\n".join(
        f"=== DIFF: {fp} ===\n{content}" for fp, content in capped
    )
    return (
        "Review this change for security vulnerabilities.\n\n"
        "Changed files (you may Read these and any other file in the repo):\n"
        + "\n".join(f"  - {p}" for p in touched_paths[:50])
        + context_note
        + "\n\nUnified diff (only + lines are new):\n\n"
        + diff_text
        + extensibility.guidance_block()

    )
