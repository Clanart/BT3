### Title
`SignableTransaction::new` computes weight/fee before the OP_RETURN output is appended, so the real fee rate is lower than requested - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class in the external report is *state read for a computation, then mutated before the computation's result is used* — the reward index is computed against a stale token supply. In `SignableTransaction::new`, the same shape exists: the transaction's weight and `needed_fee` are computed via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which only accounts for the *payment* outputs — the OP_RETURN data output was already pushed to `tx_outs` (lines 194–202) but is never included in the weight calculation at lines 204 and 225–226. The fee is therefore priced against a stale transaction shape.

### Finding Description
`SignableTransaction::new` builds the final output list (`tx_outs`) including an OP_RETURN output of up to 80 bytes of caller-supplied `data` plus script overhead [1](#0-0) . However, the vbyte estimate used to derive `needed_fee` calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which constructs the dummy transaction from `payments` only and never models the OP_RETURN output [2](#0-1) . The change-output decision repeats the same omission: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again excludes the data output [3](#0-2) .

The fee actually paid is `sum(inputs) - sum(outputs)`, which equals the `needed_fee` derived from the understated vbytes [4](#0-3) . The real transaction is larger than estimated by the full serialized OP_RETURN output (roughly 9 + up to ~83 script bytes). Additionally, the minimum-relay sanity check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` uses the same understated `vbytes`, so a `fee_per_vbyte` chosen exactly at the relay minimum produces a real transaction whose effective rate falls below the minimum relay fee [5](#0-4) .

### Impact Explanation
Any `SignableTransaction` carrying an OP_RETURN data output — used by Serai's Bitcoin processor for `InInstruction`-bearing transactions — pays a fee rate strictly lower than the `fee_per_vbyte` requested. When the requested rate is at or near the minimum relay fee, the signed transaction's effective rate falls below `DEFAULT_MIN_RELAY_TX_FEE` and will be rejected by peer mempools, leaving the transaction unable to propagate or confirm. Funds are not stolen, but a threshold-signed transaction becomes unbroadcastable/stalls, and the entire FROST signing round must be redone with corrected parameters. This is a Medium-severity liveness/fee-accounting flaw directly reachable through the normal transaction-construction path.

### Likelihood Explanation
Deterministic whenever `data.is_some()` — the OP_RETURN is always added to `tx_outs` and never counted in either weight calculation. The underpayment is capped at the size of one ~90-byte output, so impact materializes only when `fee_per_vbyte` is close to the relay minimum; with comfortable fee margins the transaction still confirms, merely overpaying relative to intent rather than underpaying.

### Recommendation
Include the OP_RETURN output in the weight estimation. Either pass the fully constructed `tx_outs` (payments + OP_RETURN, plus optionally change) into `calculate_weight_vbytes`, or add the serialized size of the OP_RETURN `TxOut` to the computed weight/vbytes before deriving `needed_fee`. The same fix must apply to the `fee_with_change` computation so the change/dust decision accounts for the data output as well.

### Proof of Concept
```rust
// In networks/bitcoin, construct a tx with an OP_RETURN payload:
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
    vec![output],                       // one input worth enough
    &[(payment_script, 1000)],
    Some(change_script),
    Some(data),
    1,                                  // 1 sat/vbyte, at relay minimum
).unwrap();

// tx.transaction() contains the OP_RETURN output (~90 extra bytes),
// yet needed_fee() == vbytes(payments + change) * 1, which does not
// cover the real vsize. tx.fee() / tx.transaction().vsize() < 1 sat/vb,
// below DEFAULT_MIN_RELAY_TX_FEE -> rejected by mempools.
```
The existing test `test_send` only exercises `data: None` [6](#0-5) , which is why the discrepancy is unobserved: `assert_eq!(input_value - output_value, needed_fee)` holds because `needed_fee` is defined against the understated vbytes — the assertion compares the paid fee to the wrong estimate, not to the real vsize of the transaction that includes an OP_RETURN.
