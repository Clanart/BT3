## Analysis

The Tokemak report's core broken invariant is: **a monotonically-updated "high mark" accounting structure can be manipulated by an unprivileged actor into a state that irrecoverably destroys or freezes value already earned/paid for**, with no path to recovery once the mutation happens.

The closest local analog in Hyperbridge is in `pallet-bandwidth`'s FIFO subscription ledger, where the eviction rule that fires once the per-`(chain, app)` list hits its 1024-entry cap always removes **index 0 — the actively-draining, oldest-inserted subscription** — rather than a stale or expired one. Any unprivileged caller can pay to fill someone else's queue and force-evict their live, still-funded allowance.

### Title
Unprivileged `purchase()` calls can evict a victim's live, still-funded bandwidth subscription instead of an expired one, permanently destroying prepaid balance — (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`BandwidthManager.purchase()` is a fully public entrypoint [1](#0-0)  that lets *any* caller credit bandwidth to *any* `(chain, app)` pair by paying the tier price — the pallet only checks that the dispatching contract is the registered manager for its source chain, never who the buyer is or who the app belongs to [2](#0-1) . Each purchase appends a `Subscription` to a `BoundedVec` capped at 1024 entries via `push_subscription`. When the cap is reached, the pallet unconditionally evicts `list.remove(0)` — the oldest-inserted entry — with no check for whether that entry is expired or still has `remaining_bytes` actively being drained [3](#0-2) . Because the gate (`try_consume`) also drains strictly from index 0 [4](#0-3) , index 0 is by construction the app's *currently in-use* allowance, not a stale one.

### Finding Description
`push_subscription` is:
```rust
let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
    let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
        Some(list.remove(0))
    } else {
        None
    };
    let _ = list.try_push(new_sub);
    evicted
});
``` [5](#0-4) 

There is no expiry sweep or "is this entry still valuable" check before the eviction — the pick is purely capacity-based FIFO by insertion order. The drain path in `try_consume` confirms index 0 is the live head being consumed on every non-purchase request [4](#0-3) .

Since `purchase()` is unauthenticated with respect to the target `app`/`chain` — it only requires paying `tierPrice × months` in the fee token, and the pallet's `on_accept` keys the credit purely off the message body's `chain`/`app` fields [6](#0-5)  — any attacker can:
1. Observe a victim app's `(chain, app)` and current queue depth (public chain state).
2. Buy the cheapest tier (`TierOne`, e.g. $50/month) repeatedly, targeting the victim's `(chain, app)` pair, until the list reaches 1024 entries.
3. Every purchase beyond the cap evicts `list[0]` — the victim's oldest live subscription, which is exactly the one the gate is actively draining and which may still hold a large `remaining_bytes` balance the victim already paid real money for.
4. The event `SubscriptionEvicted { lost_bytes }` fires, confirming the loss is unrecoverable — there is no refund path, and eviction is irreversible.

Existing guards do not stop this: the allowlist bypass (`Allowlist`) only exempts specific `(source, app)` pairs from the gate and does not protect against eviction; `is_purchase_message` only checks the manager identity, not the payer or the beneficiary app; and the "sponsorship" design (any chain can credit any app) is explicitly intended to be permissionless, which is precisely what removes the barrier to this attack.

### Impact Explanation
This is a direct loss-of-funds vector against `pallet-bandwidth`'s core ledger: prepaid, still-live bandwidth balance — real value paid for in ERC-20/native fee tokens on the source chain — is permanently destroyed and never reaches or benefits the app that paid for it. This maps to "Bridged assets... and bandwidth balances must move exactly once and only to the rightful beneficiary and amount" in the Hyperbridge Pivots: here the balance moves to nobody — it is destroyed by a third party with no economic claim on it. Any app relying on the bandwidth gate to keep its cross-chain messages flowing can be starved out entirely by a well-funded attacker without needing to compromise a relayer, prover, or admin key.

### Likelihood Explanation
High relative to the audit's "unprivileged public entrypoint" bar: the attack requires only calling a public Solidity function (`purchase()`) repeatedly against a chosen victim `(chain, app)` pair — no special timing, no front-running, no relayer/prover collusion, no governance action. The only cost is the cheapest tier price × the number of purchases needed to reach/exceed the 1024 cap (which can be primed once and then topped up incrementally as the victim's queue naturally grows via their own legitimate purchases). The attacker does not need to match or exceed the victim's total prepaid value — they only need to keep the queue at 1024 and repeatedly nudge index 0 out, which is cheap relative to the value an app may have locked into a single large multi-month purchase.

### Recommendation
Before evicting on a full list, sweep expired entries first (the same filter `try_consume` already applies) and only evict an entry if no expired one exists to remove instead. If eviction of a live entry is unavoidable, evict the entry with the least remaining value (smallest `remaining_bytes` relative to its `expires_at`), not simply the oldest by insertion index. Consider additionally gating `purchase()`'s beneficiary `(chain, app)` behind an allow-list or a minimum-purchase-size proportional to the target's existing queue depth to prevent cheap queue-stuffing.

### Proof of Concept
1. Governance configures `TierOne` with a low price (per docs, $50/100KB) and registers a `BandwidthManager` for chain `EVM-8453` [7](#0-6) .
2. Victim app buys a large, long-duration subscription (e.g., `TierFour`, 8MB, several months) — this lands at some position `i` in `Allowance[(EVM-8453, victimApp)]`.
3. Attacker calls `BandwidthManager.purchase(victimApp, TierOne, 1, "EVM-8453")` repeatedly (any `msg.sender`, no relationship to `victimApp` required) until the list reaches 1024 entries, each dispatching a `BandwidthPurchaseMsg` credited by `on_accept` via `push_subscription` [8](#0-7) .
4. Once at cap, each further attacker purchase evicts `list.remove(0)` [5](#0-4)  — since the victim's earlier large purchase is now the oldest surviving (and actively-draining) entry, it gets evicted, emitting `SubscriptionEvicted { lost_bytes: <victim's remaining bytes> }`.
5. The victim's app is now unable to send messages through the bandwidth gate (`GateError::NoAllowance` / reduced allowance) despite having paid for a large, unexpired subscription, and has no way to reclaim the destroyed balance.

        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();

        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});
