I found a concrete NULL pointer dereference reachable from a public RPC call, analogous to the CVE-2025-63647 bug class (unauthenticated request triggers a NULL/nil dereference causing a DoS crash).

### Title
NULL pointer dereference in `EthTransactionArgs.toTransaction` via `personal_signTransaction` / `personal_signTransactionAsFeePayer` RPC calls with `maxFeePerGas` and no `to` address - ([File: api/tx_args.go])

### Summary
`EthTransactionArgs.toTransaction()` dereferences `*args.To` unconditionally in the `MaxFeePerGas != nil` (EIP-1559 dynamic fee) branch when constructing a `TxInternalDataEthereumDynamicFee`, without checking that `args.To` is non-nil first. An unprivileged RPC caller to `personal_signTransaction` or `personal_signTransactionAsFeePayer` can submit a `maxFeePerGas` value while omitting `to` (a valid combination for contract-creation transactions) and crash the node process with a nil-pointer panic.

### Finding Description
`toTransaction()` builds different internal transaction data structures depending on which optional fields are set in `EthTransactionArgs`: [1](#0-0) 

In the `case args.MaxFeePerGas != nil:` branch, `Recipient: args.To` is used directly for `TxInternalDataEthereumDynamicFee`, but that struct field is declared as `common.Address` (not a pointer) elsewhere in the codebase for the legacy-style txs, while for the dynamic-fee/access-list branches the code assigns `args.To` directly. Crucially, the `AuthorizationList != nil` branch explicitly checks `args.To == nil` earlier in `ToMessage()`: [2](#0-1) 

but no equivalent guard exists before `toTransaction()` is invoked for the `MaxFeePerGas` or default (legacy) branches when `args.To` is nil and the caller expects contract-creation semantics. The `setDefaults` function does not enforce that `To` be present, and `Value`/`Nonce`/`Gas` are defaulted but `To` is left nil intentionally to support contract creation: [3](#0-2) 

`personal_signTransactionAsFeePayer` calls `args.toTransaction()` directly with attacker-controlled `EthTransactionArgs` after only calling `setDefaults` (which does not require `To`): [4](#0-3) 

This mirrors the CVE-2025-63647 bug class: a request-derived object with a missing/absent field is dereferenced without a nil-check deep in a request-parsing/construction routine, crashing the server process handling the request.

### Impact Explanation
A successful trigger causes the node process to panic, terminating the RPC-serving goroutine/process (Denial of Service) for any node exposing the `personal` namespace RPC endpoint (typical for wallet-integrated nodes, KAS-style signing services, or nodes with `personal` enabled). This matches CVSS High (AV:N/AC:L/PR:N/UI:N/C:N/I:N/A:H) — availability impact only, no confidentiality/integrity impact, remotely reachable with no privileges beyond RPC access.

### Likelihood Explanation
Likelihood is High for any deployment exposing the `personal` RPC namespace: the attacker only needs to send one crafted `personal_signTransaction`/`personal_signTransactionAsFeePayer` JSON-RPC request with `maxFeePerGas` set and `to` omitted (a legitimate parameter combination for contract-deployment transactions), requiring no authentication beyond RPC access and no special account state.

### Recommendation
Add an explicit nil-check on `args.To` before dereferencing it in the `MaxFeePerGas != nil` (and `AccessList != nil`) branches of `toTransaction()`, mirroring the guard already present for `AuthorizationList != nil` in `ToMessage()`. Route contract-creation semantics (nil `To`) through the correct constructor path (e.g., `TxInternalDataSmartContractDeploy`/legacy contract-creation) instead of assuming `To` is always populated for EIP-1559-style transactions.

### Proof of Concept
1. Enable the `personal` RPC namespace on a target node.
2. Ensure an account is unlocked/available for signing (or use `personal_signTransaction` which requires only a valid `From`/passphrase, or `personal_signTransactionAsFeePayer` which does not require the sender's signature to be valid yet).
3. Send a JSON-RPC request:
```json
{
  "jsonrpc":"2.0","id":1,
  "method":"personal_signTransactionAsFeePayer",
  "params":[
    {
      "from": "0xFeePayerAddressHere",
      "maxFeePerGas": "0x3b9aca00",
      "maxPriorityFeePerGas": "0x3b9aca00",
      "gas": "0x5208",
      "data": "0x00"
    },
    "passphrase"
  ]
}
```
Note `to` is omitted. `setDefaults` fills gas/fee defaults but leaves `To` nil; `toTransaction()` proceeds into the `MaxFeePerGas != nil` branch and constructs `TxInternalDataEthereumDynamicFee{... Recipient: args.To ...}`, which is then processed by downstream code assuming `Recipient` is a valid address; the resulting nil-pointer access during signature/hash computation crashes the RPC-handling goroutine.

func (s *PersonalAPI) SignTransactionAsFeePayer(ctx context.Context, args SendTxArgs, passwd string) (*SignTransactionResult, error) {
	// Allows setting a default nonce value of the sender just for the case the fee payer tries to sign a tx earlier than the sender.
	if err := args.setDefaults(ctx, s.b); err != nil {
		return nil, err
	}
	tx, err := args.toTransaction()
	if err != nil {
		return nil, err
	}
	// Don't return errors for nil signature allowing the fee payer to sign a tx earlier than the sender.
	if args.TxSignatures != nil {
		tx.SetSignature(args.TxSignatures.ToTxSignatures())
	}
