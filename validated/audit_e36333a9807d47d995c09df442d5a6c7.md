### Title
`SignableTransaction` omits the OP_RETURN data output from its weight, fee, and standardness calculations - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying attacker-supplied `data` (up to 80 bytes) to the transaction's outputs, but computes the transaction weight, the derived `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check via `calculate_weight_vbytes`, which is only passed `inputs` and `payments`. The data output is never included in the weight model, so the signed transaction is larger and heavier than accounted for — analogous to the CVE-2022-21539 class of a low-privileged network party inducing integrity- and availability-affecting misbehavior in data they cause to be processed.

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256):

- When `data` is `Some`, a zero-valued OP_RETURN `TxOut` is pushed onto `tx_outs` containing up to 80 arbitrary bytes (lines 193-202).
- `calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) builds a model transaction whose `output` list is populated *only* from `payments` and the optional `change` (lines 85-99). It has no awareness of `data` at all — the OP_RETURN output's ~12 bytes of output envelope plus the script payload is missing from both `weight` and `vbytes`.
- `needed_fee = fee_per_vbyte * vbytes` (line 206) and the minimum-relay-fee check (line 211) are therefore computed on a vbyte count that is too small by the full size of the OP_RETURN output (~90+ WU ≈ ~23+ vbytes).
- The change-branch calculation at lines 224-235 re-runs `calculate_weight_vbytes` with the change script but again without the data output, so `fee_with_change` is undercharged identically.
- The standardness guard `weight > MAX_STANDARD_TX_WEIGHT` (line 241) uses the under-counted `weight`, so a transaction whose *actual* weight exceeds 400,000 WU is admitted and signed.

The resulting `SignableTransaction.tx` does contain the OP_RETURN output (line 250), and `TransactionSignMachine::sign` (send.rs:373-397) signs `taproot_key_spend_signature_hash` over the real transaction, so the FROST multisig produces a validly-signed transaction that is bigger than what was priced and size-checked.

### Impact Explanation
- **Underpaid fee / stuck transaction (partial DoS):** The multisig signs a transaction whose actual feerate is lower than the requested `fee_per_vbyte`, and potentially below the mempool minimum relay fee even though the `TooLowFee` check passed against the smaller virtual size. The broadcast transaction may be rejected or sit unconfirmed indefinitely, stalling the associated plan/branch.
- **Standardness bypass (partial DoS):** With many inputs/payments near the boundary, including `data` can push the true weight past `MAX_STANDARD_TX_WEIGHT`, producing a signed transaction no default node will relay — permanently unbroadcastable despite having consumed a signing round.
- **Integrity skew:** `needed_fee()` and `fee()` report inconsistent values relative to caller intent: callers budgeting change via `input_sat - payment_sat - fee_with_change` hand the shortfall to miners invisibly mixed into the change calculation, corrupting the accounting between what was requested and what was signed.

### Likelihood Explanation
An unprivileged party who can cause the wallet to embed `data` into a transaction (e.g., an InInstruction-style payload accompanying a payment routed through this construction) triggers the undercount deterministically — no race, no collusion, no privileged access needed. Whether the delta is fatal depends on the configured fee rate's margin above relay minimums and how close the transaction is to the weight cap, matching a Medium (partial impact) profile.

### Recommendation
Pass the serialized OP_RETURN `TxOut` (or a worst-case 80-byte placeholder) into `calculate_weight_vbytes` so `weight`, `vbytes`, `needed_fee`, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check all account for the data output. Ideally, build the model transaction from the final `tx_outs` list rather than a separately reconstructed output set, eliminating the possibility of future divergence.
