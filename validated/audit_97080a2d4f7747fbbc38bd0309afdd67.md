### Title
AnkrBNBPoolHelper lock bypass via direct MasterMagpie.withdraw - ([File: wombat/AnkrBNBPoolHelper.sol])

### Summary
`AnkrBNBPoolHelper.withdraw` enforces the `unlockTime`/`lockedAmount` gate at line 171, but `MasterMagpie.withdraw(_stakingToken, _amount)` is a public, unrestricted function that lets any staker withdraw their own `stakingToken` balance directly from `MasterMagpie` without ever routing through `AnkrBNBPoolHelper`. Because `depositFor` (called during `batchDepositLPFor`) credits `user.amount`/`user.available` in `MasterMagpie` under the recipient's own address, the batch-deposit beneficiary can call `MasterMagpie.withdraw` themselves and receive their `stakingToken` back before `unlockTime`, completely bypassing the helper's lock check.

### Finding Description
In `AnkrBNBPoolHelper.batchDepositLPFor` (wombat/AnkrBNBPoolHelper.sol:113-135), the operator deposits LP on behalf of beneficiaries via `IMasterMagpie(masterMagpie).depositFor(stakingToken, amount, _for[i])`, and separately records `lockedAmount[_for[i]] += amount`. The lock is enforced only inside `AnkrBNBPoolHelper.withdraw` (wombat/AnkrBNBPoolHelper.sol:160-177):
```solidity
uint256 rest = this.balance(msg.sender);
if (unlockTime > block.timestamp && lockedAmount[msg.sender] > rest) revert NotAllowed();
```
This check lives entirely in the helper contract and is never consulted by `MasterMagpie` itself.

`MasterMagpie.withdraw` (rewards/MasterMagpie.sol:344-346) is a plain, unrestricted external function:
```solidity
function withdraw(address _stakingToken, uint256 _amount) external whenNotPaused nonReentrant {
    _withdraw(_stakingToken, msg.sender, _amount, false);
}
```
Unlike `withdrawFor` (line 364-370), which is gated by `_onlyPoolHelper(_stakingToken)`, `withdraw` has no such gate — any address with `user.available > 0` for that `stakingToken` in `MasterMagpie` can call it for themselves. `_withdraw` → `_harvestAndUnstake` only checks `user.available < _amount` (line 521), decrements accounting, and then directly transfers the raw `stakingToken` (the Wombat LP receipt/asset token used by `WombatStaking`) to `msg.sender` (line 512):
```solidity
IERC20(tokenToPoolInfo[_stakingToken].stakingToken).safeTransfer(address(msg.sender), _amount);
```
Since a batch-deposit beneficiary's `user.available[stakingToken][beneficiary]` was incremented by `depositFor` during `batchDepositLPFor`, this balance is fully withdrawable via the public `MasterMagpie.withdraw` path with zero reference to `AnkrBNBPoolHelper.lockedAmount` or `unlockTime`. The attacker thereby receives the `stakingToken` directly (bypassing `WombatStaking.withdraw`/`burnReceiptToken` and the helper's lock check entirely), defeating the intended 1-year Ankr compensation lock.

### Impact Explanation
This allows early unlock/theft of funds intended to remain locked until `unlockTime` for the Ankr compensation program (Exit safety / lock integrity invariant). A beneficiary who received an allocation via `batchDepositLPFor` can extract the underlying value before the lock period ends, which can create insolvency/unfair distribution among other allocation recipients relying on the locked-until-`unlockTime` guarantee. This matches Immunefi's "theft of user funds" / "permanent freezing... circumvented lock" impact class, scoped specifically to the Ankr lock program funds routed through `AnkrBNBPoolHelper`.

### Likelihood Explanation
- Preconditions: attacker must be a `batchDepositLPFor` beneficiary (`lockedAmount[attacker] > 0`), and `unlockTime` must not yet have passed. This requires the `ankrOperator` to have deposited on the attacker's behalf, but the attacker themselves needs no special privilege beyond being a normal `msg.sender` calling public functions.
- No capital is required beyond normal transaction gas; the exploit is a single direct call to `MasterMagpie.withdraw(stakingToken, amount)`.
- Fully repeatable for every beneficiary address with a locked allocation, at any time before `unlockTime`.

### Recommendation
Enforce the lock invariant at the `MasterMagpie` layer (or equivalently in `WombatStaking`) rather than only in `AnkrBNBPoolHelper`. Options: (1) restrict the general `MasterMagpie.withdraw` from operating on pools with an associated lock/helper unless called via the registered pool helper (similar to `withdrawFor`'s `_onlyPoolHelper` gate), or (2) track `lockedAmount` and `unlockTime` inside `MasterMagpie` (or a shared registry) and check it inside `_withdraw`/`_harvestAndUnstake` for any staking token subject to a lock, so the check cannot be bypassed by calling `MasterMagpie` or `WombatStaking` directly.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `WombatStaking`, and `AnkrBNBPoolHelper` with `unlockTime = block.timestamp + 365 days`.
2. As `ankrOperator`, call `AnkrBNBPoolHelper.batchDepositLPFor(lpAmount, [attacker], [100000])`, which sets `lockedAmount[attacker] = lpAmount` and calls `MasterMagpie.depositFor(stakingToken, lpAmount, attacker)`.
3. From `attacker` EOA, directly call `MasterMagpie.withdraw(stakingToken, lpAmount)` (not via `AnkrBNBPoolHelper.withdraw`).
4. Assert: the call succeeds (does not revert with `NotAllowed`), `IERC20(stakingToken).balanceOf(attacker) == lpAmount`, and `block.timestamp < unlockTime`, proving the lock was bypassed.
5. Compare with control case: calling `AnkrBNBPoolHelper.withdraw(lpAmount, minAmount)` from `attacker` before `unlockTime` reverts with `NotAllowed()`, confirming the helper's own gate works but is trivially bypassable via `MasterMagpie`.
