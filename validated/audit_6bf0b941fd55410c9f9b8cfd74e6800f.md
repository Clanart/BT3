### Title
Untrusted `ReceivedOutput` bytes can forge a non-spendable deposit - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary

`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without proving that the `OutPoint` refers to a transaction which actually contains that output. This removes the provenance guarantee provided by `Scanner::scan_transaction`, which derives the `OutPoint` from the scanned transaction after matching its script. [1](#0-0) [2](#0-1) 

### Finding Description

`ReceivedOutput` is documented as “a spendable output” and exposes its claimed Bitcoin value through `value()`. [3](#0-2) 

The legitimate scanner establishes that claim by matching `output.script_pubkey` against registered scripts and constructing `OutPoint::new(tx.compute_txid(), vout)` from the containing transaction. [2](#0-1) 

Deserialization does not preserve that binding: it reads an attacker-controlled offset, output, and outpoint as three independent fields. [1](#0-0)  Consequently, an attacker who knows the public group key can encode an output paying that key, but pair it with an unrelated or nonexistent outpoint.

The spending path then trusts those fields directly: `SignableTransaction::new` uses `input.outpoint` as the transaction input and stores `input.output` as the claimed prevout. [4](#0-3) [5](#0-4) 

`SignableTransaction::multisig` only checks that the claimed prevout script equals the key derived from the claimed offset. [6](#0-5)  It does not check that the outpoint exists on-chain or resolves to that `TxOut`. Signing then commits to `Prevouts::All(&self.tx.prevouts)`, so the fabricated output metadata is incorporated into the Taproot signature request. [7](#0-6) 

This is analogous to the reported path-lookup flaw: the scanner’s transaction-derived outpoint acts as the rooted lookup, while deserialization permits an attacker-supplied outpoint to escape that root and refer to an unrelated object.

### Impact Explanation

A malicious party can cause Serai to report or attempt to spend funds that are not actually spendable by the threshold group. The forged object can carry an arbitrary amount and outpoint while using a script controlled by the public group key and offset zero.

If such bytes are persisted, relayed, or otherwise accepted as a `ReceivedOutput`, the resulting `SignableTransaction` can reach FROST signing and produce signatures for a transaction that Bitcoin consensus will reject because its input does not reference the claimed prevout. This creates false balance accounting, failed spends, and potential operational disruption; it does not require knowledge of any threshold key share.

### Likelihood Explanation

The required inputs are only public data: the group P2TR script, an amount, and an arbitrary serialized `OutPoint`. The attack succeeds whenever untrusted `ReceivedOutput` bytes can cross a trust boundary and be treated with the same authority as scanner-produced outputs.

No malformed encodings or cryptographic break are needed. A canonical scalar, a valid consensus-encoded `TxOut`, and a valid consensus-encoded `OutPoint` are sufficient.

### Recommendation

Do not treat deserialized `ReceivedOutput` values as proof of spendability. Either:

- Require `ReceivedOutput` construction through `Scanner::scan_transaction`/`scan_block`, and remove or clearly mark `ReceivedOutput::read` as trusted-state deserialization.
- Include and validate the containing transaction or a trusted UTXO proof: verify `tx.compute_txid() == outpoint.txid`, `outpoint.vout < tx.output.len()`, and that the referenced output equals `output`.
- Before constructing `SignableTransaction`, reload the prevout from trusted chain state and compare it with the claimed `TxOut`.
- Authenticate scanner-produced outputs before storing or accepting them from another process.

### Proof of Concept

The following conceptual test constructs a canonical `ReceivedOutput` claiming a nonexistent UTXO. `group_key` must be an even-y Taproot key.

```rust
use frost::{curve::Secp256k1, ThresholdKeys};
use group::ff::PrimeField;
use k256::Scalar;
use bitcoin::{
  consensus::serialize,
  transaction::OutPoint,
  Amount, TxOut,
};
use bitcoin_serai::wallet::{
  ReceivedOutput, SignableTransaction, p2tr_script_buf,
};

fn forged_received_output(
  keys: &ThresholdKeys<Secp256k1>,
  payment_script: bitcoin::ScriptBuf,
) {
  // Public group key; no private share is needed.
  let group_script = p2tr_script_buf(keys.group_key()).unwrap();

  // The output claims to pay Serai, but the outpoint is unrelated/nonexistent.
  let fake_txout = TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: group_script,
  };
  let fake_outpoint = OutPoint::default();

  // ReceivedOutput format:
  // scalar || consensus TxOut || consensus OutPoint.
  let mut bytes = Scalar::ZERO.to_bytes().to_vec();
  bytes.extend(serialize(&fake_txout));
  bytes.extend(serialize(&fake_outpoint));

  let forged =
    ReceivedOutput::read(&mut bytes.as_slice()).expect("canonical forged output");

  // The fabricated deposit is reported as received value.
  assert_eq!(forged.value(), 100_000);

  let signable = SignableTransaction::new(
    vec![forged],
    &[(payment_script, 50_000)],
    None,
    None,
    20,
  )
  .unwrap();

  // The script matches offset zero, so the multisig machine accepts it.
  let _machine = signable.multisig(keys).unwrap();
}
```

The produced transaction can be signed, but Bitcoin will reject it because `fake_outpoint` does not resolve to the claimed group-controlled `TxOut`.
