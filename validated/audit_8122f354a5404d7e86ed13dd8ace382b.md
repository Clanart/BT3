## Analysis

The GitHub Desktop analog to this bug class (a security check that omits a necessary term in its comparison, exactly as the LoopFi code omitted the `protocolFee` term from `loanAmount`) is the containment check in `_resolveWithin`.

### Title
Prefix-based path containment check in `resolveWithin` allows sibling-directory escape via crafted deep-link `filepath` - (File: app/src/lib/path.ts)

### Summary
`_resolveWithin()` is the central guard used throughout the app to guarantee that a user- or attacker-influenced relative path cannot escape a repository's root directory. Its final decision is a bare string `startsWith` comparison between the resolved real path and the real root path, with no check that the character following the root prefix is a path separator. This is the same class of defect as the reported issue: a formula that should include one more term (here, a path-separator boundary; there, the protocol fee) but doesn't, so the guard silently accepts values it should reject.

### Finding Description [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`realRoot` has no guaranteed trailing separator. If `realRoot` is `/Users/victim/Documents/GitHub/repo` and a sibling directory exists named `/Users/victim/Documents/GitHub/repo-secrets`, then `realResolved.startsWith(realRoot)` evaluates to `true` even though `repo-secrets` is a completely different directory outside the intended repo — it merely shares a string prefix. The correct check needs an additional term, e.g. `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`, exactly analogous to how the LoopFi formula needed to subtract the fee term.

This function is used as the sole traversal guard for handling a `filepath` parameter delivered via the app's custom URL scheme deep link: [2](#0-1) 

```
if (isAbsolute(filepath)) {
  log.error(`Refusing to open absolute path: ${filepath}`)
  return
}
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
} else {
  log.error(...)
}
```

Only absolute paths are rejected; a *relative* traversal payload (e.g. `../repo-secrets/config.json`) is passed straight to `resolveWithin`, which resolves it to a sibling directory and then wrongly treats it as "within" the repo because of the prefix bug.

The same primitive is reused for reading file contents that get sent to an external Copilot API: [3](#0-2) 

### Impact Explanation
An attacker who controls a deep link the user clicks (`x-github-client://openRepo?url=...&pr=...&filepath=../<sibling>-secrets/...`) can cause GitHub Desktop to reveal (`shell.showItemInFolder`) a file that resides outside the target repository, as long as a sibling directory happens to share the repo's name as a string prefix (a very common situation — forks, related repos, or GitHub Desktop's own default per-owner clone layout make prefix collisions likely, e.g. `desktop` / `desktop-i18n`, `repo` / `repo-old`, `repo` / `repo2`). This matches the explicitly valid impact category "a link or deep link the user clicks ... result is ... file write or read outside the repo."

### Likelihood Explanation
The precondition (a sibling directory whose name is a superstring of the repo's directory name) is common in real developer working-copy layouts, and no local/physical access, admin rights, or prior malware is required — only a single click on a maliciously crafted `x-github-client://` link, which is the exact "unprivileged" trigger this task requires.

### Recommendation
Fix the boundary check in `_resolveWithin` (app/src/lib/path.ts:71) to require an exact match or a path-separator boundary after the root prefix, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply the same fix consistently across all consumers of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`.

### Proof of Concept
1. User has cloned two repositories side by side: `~/Documents/GitHub/repo` and `~/Documents/GitHub/repo-secrets` (the latter containing sensitive files, e.g. `.env`).
2. Attacker sends the user a link: `x-github-client://openRepo?url=https://github.com/org/repo&filepath=../repo-secrets/.env`
3. `openRepositoryFromUrl` (app/src/ui/dispatcher/dispatcher.ts:1940-1972) resolves/opens `repo`, then calls `resolveWithin(repository.path, '../repo-secrets/.env')`.
4. `_resolveWithin` computes `resolved = /Users/.../GitHub/repo-secrets/.env`, and `realResolved.startsWith(realRoot)` returns `true` because `"repo-secrets"` starts with `"repo"`.
5. `shell.showItemInFolder(resolved)` reveals `.env` from the sibling repo, outside the opened repository, without any warning.
