Confirmed finding: the `x/erc20` IBC receive path auto-registers a new token pair for **every** unrecognized `ibc/...` denom with no permission check [1](#0-0) , calling `RegisterERC20Extension` → `CreateNewTokenPair` unconditionally for any unprivileged relayer/sender who moves a new denom over IBC [2](#0-1) . This means the number of registered token pairs `n` is attacker-controllable and unbounded (limited only by ordinary IBC transfer fees, not by EVM gas).

The `bank` precompile's `Balances`/`totalSupply` queries iterate over token pairs, and the documented cost model scales with `n` (`2,851 + 2,851×(n-1)`) [3](#0-2) , but `RequiredGas` — the value actually charged by the EVM before `Run` executes — returns a **flat constant** (`GasBalances = 2_851`) regardless of `n` [4](#0-3) [5](#0-4) . Additionally, the precompile is constructed with an empty `KvGasConfig{}` "to avoid extra gas costs during the run execution" [6](#0-5) , so the SDK-gas-metered path inside `RunNativeAction` that would normally true-up the flat estimate with real KV-store gas usage [7](#0-6)  also charges near-zero for the iteration. In other words there is no mechanism anywhere in this call path that scales the actual gas debited to the caller with the actual number of token pairs iterated.

This is structurally the same bug class as the reported zkEVM issue: a size-dependent cost (word-count for calldata/code copy there; token-pair count here) is computed with an unconstrained/uncharged variable instead of being tied to a metered, bounded value, allowing execution work to grow unboundedly while the gas charged stays fixed.

However, I was not able to fully confirm within available tool budget:
- Whether `p.Balances`/`p.TotalSupply` implementations (not retrieved in full) actually iterate over *all* registered token pairs versus only pairs relevant to the queried address (this determines whether the attack scales per call or is bounded per-account).
- The exact per-pair cost of the iteration (bank keeper balance lookups, ERC20 address derivation) to estimate how many pairs are needed to cause meaningfully unbounded work within a single block's gas limit.
- Whether `permissionless_registration`/governance params could gate this path in the deployed configuration (the proto shows a `permissionless_registration` param [8](#0-7) , but the IBC-triggered auto-registration in `OnRecvPacket` appears unconditional and not gated by that param based on the code I reviewed).

Given these open questions — particularly whether the impact rises to a genuine Critical, unbounded-work / chain-halt-class DoS as opposed to a bounded, per-block-limited cost increase — I can't assert with full confidence that this clears the bar required by the "Critical chain halt ... that an unprivileged user can trigger" impact gate. I'd recommend a Devin session to pull the full `Balances`/`TotalSupply` implementations and measure real gas-vs-work scaling before filing this as a confirmed Critical finding.

// It derives the ERC-20 address from the token denomination and registers the

	pair, err := k.CreateNewTokenPair(ctx, denom)
	if err != nil {
		return nil, err
	}

	// Add to existing EVM extensions
	if err := k.EnableDynamicPrecompile(ctx, pair.GetERC20Contract()); err != nil {
		return nil, err
	}

	return &pair, err

// RequiredGas calculates the precompiled contract's base gas rate.
func (p Precompile) RequiredGas(input []byte) uint64 {
	// NOTE: This check avoid panicking when trying to decode the method ID
	if len(input) < 4 {
		return 0
	}

	methodID := input[:4]

	method, err := p.MethodById(methodID)
	if err != nil {
		// This should never happen since this method is going to fail during Run
		return 0
	}

	switch method.Name {
	case BalancesMethod:
		return GasBalances
	case TotalSupplyMethod:
		return GasTotalSupply
	case SupplyOfMethod:
		return GasSupplyOf
	}

	return 0
}
