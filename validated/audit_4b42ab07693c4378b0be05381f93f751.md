Confirmed: `filepath` in `x-github-desktop://openRepo` deep links comes directly from an unsanitized querystring value (only checked with `isAbsolute()` in `dispatcher.ts`), and is passed straight to `resolveWithin()`, whose containment check has a boundary-prefix bug identical in spirit to the reported `rescue()` flaw — a check that looks correct but has a second "entry point" that satisfies the raw comparison without satisfying the intended invariant.

### Title
Deep-link `filepath` parameter escapes the repository root via string-prefix bypass in `resolveWithin()` - ([File: app/src/lib/path.ts])

### Summary
`resolveWithin()` is the guard used throughout Desktop to keep an attacker-influenced relative path pinned inside a trusted root directory [1](#0-0) . Its final containment check is a plain string `startsWith()` comparison with no trailing path-separator check, so any resolved path whose absolute string merely begins with the root's string (e.g. a sibling folder `myrepo-evil` next to `myrepo`) is incorrectly treated as "inside" the root, exactly as the `rescue()` bug allowed a token with an aliased address to slip past an `!=` identity check.

### Finding Description
`_resolveWithin()` computes `resolved = resolve(normalizedRoot, normalizedRelative)`, then validates containment with: [2](#0-1) 

`realResolved.startsWith(realRoot)` returns `true` whenever `realResolved` textually begins with `realRoot`, regardless of whether the next character is a path separator. If the trusted root is `/Users/victim/Documents/GitHubDesktop/myrepo` and a sibling directory `/Users/victim/Documents/GitHubDesktop/myrepo-secrets` exists (a completely different, unrelated directory — the "second entry point"), then a relative segment such as `../myrepo-secrets/notes.txt` resolves to a path that starts with the string `.../myrepo` but is not actually inside it. The guard passes even though the invariant ("resolved path is at or under root") is violated.

This guard is invoked directly on attacker-controlled input in `dispatcher.ts`: [3](#0-2) 

The only prior check is `isAbsolute(filepath)`, which does nothing to stop a relative traversal string like `../sibling-name-with-shared-prefix/secret.txt`. The `filepath` value itself is taken verbatim from the deep-link query string with no character filtering (unlike `branch`, which is validated with `testForInvalidChars`): [4](#0-3) 

Because `x-github-desktop://openrepo?...&filepath=...` links are handled by clicking an "Open in Desktop" link (attacker-controlled web page/GitHub API response), and Desktop clones/derives the repository root path from attacker-supplied repo `url`/owner/name, an attacker can craft a link whose destination repository name is chosen so that a plausible sibling directory name (existing from a prior clone, another project, or a name the attacker can also get the user to create via the same clone flow) shares the vulnerable prefix.

### Impact Explanation
Successful exploitation directs `shell.showItemInFolder(resolved)` to reveal/select an arbitrary file outside the intended repository directory (path confinement bypass, reads/exposes file locations outside the repo root) [5](#0-4) . The same `resolveWithin()` primitive is reused by `copilot-conflict-context.ts` to decide which on-disk files are safe to read and forward to the Copilot backend as merge-conflict context [6](#0-5) , so the identical prefix-bypass logic, if reachable with attacker-influenced relative segments there, would broaden from "reveal in folder" to "read file contents and exfiltrate them to an external API." This matches the report's classification: the checked invariant ("not a pool/repo-protected asset") is bypassed via an aliasing/second-entry-point condition the check doesn't account for.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires (a) the user to click a crafted `x-github-desktop://openrepo` link, and (b) a sibling directory whose name shares the root directory's name as a string prefix to already exist on disk (or be creatable through the same clone flow, since the attacker also controls the `url`/repo name used to derive the root). This is analogous to the original report's "Low likelihood, High impact" rating, since it depends on a specific naming coincidence but is fully realizable without any local/admin access — purely through a link click and remote repository metadata the attacker controls.

### Recommendation
Fix `_resolveWithin()` to require an exact match or a match followed by the platform path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply this everywhere `startsWith(realRoot)`-style containment checks exist, and add a regression test for the sibling-directory-with-shared-prefix case in `app/test/unit/path-test.ts` (alongside the existing symlink-escape tests) [7](#0-6) .

### Proof of Concept
1. Ensure two directories exist side by side: `/Users/victim/Documents/GitHubDesktop/myrepo` (the trusted root, e.g. cloned via the deep link's `url`) and `/Users/victim/Documents/GitHubDesktop/myrepo-secrets/notes.txt` (any pre-existing or attacker-inducible sibling).
2. Attacker publishes/serves a link: `x-github-desktop://openrepo?url=<attacker-or-any-repo-url-that-clones-to-myrepo>&filepath=..%2Fmyrepo-secrets%2Fnotes.txt`.
3. Victim clicks the link; Desktop calls `openRepositoryFromUrl` → `isAbsolute('../myrepo-secrets/notes.txt')` is `false`, so the check is skipped [8](#0-7) .
4. `resolveWithin(repository.path, '../myrepo-secrets/notes.txt')` resolves to `/Users/victim/Documents/GitHubDesktop/myrepo-secrets/notes.txt`, whose string starts with `/Users/victim/Documents/GitHubDesktop/myrepo` (no separator check), so the guard returns the path instead of `null` [2](#0-1) .
5. `shell.showItemInFolder(resolved)` opens/selects `notes.txt` from the sibling directory outside the cloned repo, confirming the containment bypass.

  describe('resolveWithin', () => {
    const root = process.cwd()

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
      assert((await resolveWithin(root, 'foo\0bar')) === null)
    })

    it('succeeds for absolute relative paths as long as they stay within the root', async () => {
      const parent = resolve(root, '..')
      assert.equal(await resolveWithin(parent, root), root)
