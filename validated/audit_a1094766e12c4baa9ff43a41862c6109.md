### Title
Gasless `MsgAssociate`/Associate transactions allow zero-cost spam that forces the chain to do real work without any fee compensation - (File: app/ante/evm_checktx.go, x/evm/ante/preprocess.go)

### Summary
The reported LooksRare bug is a game-theoretic fee-griefing pattern: an attacker can force the protocol to perform costly work (VRF request/callback) while paying a fee that is far smaller than the cost incurred, because the fee model does not scale with the actual cost of the triggered work. Sei-chain has an analogous asymmetry in its EVM/Cosmos ante pipeline: transactions that associate a Sei address with an EVM address are classified as **gasless** as long as the sender is not yet associated, requiring no `--fees`/gas price and only a nominal 1-wei balance, yet each such transaction still causes real state writes, ECDSA recovery, and bank-keeper balance migration.

### Finding Description
Sei's ante pipeline explicitly special-cases unassociated `MsgAssociate`/`AssociateTx` transactions as gasless:
- `HandleAssociateTx` in `app/ante/evm_checktx.go` only requires `IsAccountBalancePositive` (≥1 wei) rather than a fee, before calling `AssociateAddress`. [1](#0-0) 
- `EVMPreprocessDecorator.AnteHandle` in `x/evm/ante/preprocess.go` performs the association work (ECDSA-derived address checks and `AssociateAddresses`, which is a state-mutating bank/keeper operation) for an unassociated sender **before** any fee validation step even runs, and short-circuits the chain (`return ctx.WithPriority(...), nil`) without calling `next`, i.e. without ever reaching the fee-charging decorator. [2](#0-1) 
- The repository's own review notes confirm this is a deliberate but broad gasless classification: "a single-message `MsgAssociate` ... whose sender is not yet associated ... the sender only needs a nonzero balance (at least 1 wei), not a fee." [3](#0-2) 
- The EVM ante pipeline documentation confirms that "Preprocessing... Associate transactions are handled here" as step 2, ahead of "Fee validation" (step 6), for the general EVM tx flow. [4](#0-3) 

This mirrors the YoloV2 bug class: the cost the protocol incurs to service the request (signature verification, keeper writes, gas metering setup) is decoupled from what the requester pays (zero fee, 1 wei balance). Unlike the LooksRare case where the attacker needs two colluding addresses per round, here an attacker only needs to generate a fresh, never-before-associated keypair (trivial and free off-chain) and fund it with 1 wei, then broadcast an unassociated `MsgAssociate`/Associate-type transaction. Because the address is guaranteed to be new every time, this gasless path can be repeated indefinitely, unlike genuine one-time association by legitimate users.

### Impact Explanation
Every gasless associate transaction still consumes block space, requires the proposer/validators to execute ECDSA signature recovery and to perform on-chain state writes (`AssociateAddresses` touches address-mapping stores and, per `x/evm/AGENTS.md`, potentially bank-keeper balance migration between Sei and EVM balance representations), yet the protocol collects zero fee revenue for the work. An attacker with a large but cheap supply of fresh keypairs (each funded with a negligible 1 wei = effectively free) can flood blocks with association transactions that pass CheckTx/DeliverTx for free, degrading throughput available to fee-paying users and consuming validator compute/storage for no revenue — the same "attacker pays near-zero, protocol pays real cost" imbalance flagged in the original report. This is a fee/resource-abuse (griefing) issue rather than a direct fund-loss bug, so it is scoped as Medium severity consistent with the analog report's own Medium rating.

### Likelihood Explanation
Likelihood is high for the mechanics (generating fresh keypairs and funding each with 1 wei is trivial and essentially free), but the practical severity depends on whether validators/relayers implement any additional mempool-level anti-spam (e.g., minimum balance requirements beyond 1 wei, per-IP/per-account rate limiting) outside of the code paths reviewed. No such additional gate was found in the reviewed ante/preprocess code, and the repository's own `REVIEW.md` documents this gasless behavior as an accepted, intentional design choice rather than flagging any additional spam mitigation.

### Recommendation
Add a rate limit or a minimal-but-nonzero explicit fee (distinct from the 1-wei balance existence check) for association transactions, or bound the number of gasless association transactions per block/per proposer, so that the aggregate cost of processing spam-associate transactions cannot exceed what an attacker pays. Alternatively, meter and charge gas for the ECDSA-recovery and state-write work performed in `HandleAssociateTx`/`EVMPreprocessDecorator.AnteHandle` even when the transaction is otherwise "gasless," ensuring cost scales with the amount of on-chain work the network is asked to perform.

### Proof of Concept
1. Generate N fresh EVM keypairs off-chain (free).
2. Fund each with the minimum required balance (1 wei) via a single low-cost setup transaction, satisfying `IsAccountBalancePositive` in `app/ante/evm_checktx.go`. [5](#0-4) 
3. Broadcast N unassociated `MsgAssociate` (or `AssociateTx`) transactions, one per fresh address.
4. Each transaction passes `EvmStatelessChecks`/`Preprocess` and is handled entirely inside `HandleAssociateTx` / `EVMPreprocessDecorator.AnteHandle`, which perform state writes and short-circuit before fee validation, so `EvmCheckAndChargeFees` is never invoked for these messages. [6](#0-5) 
5. Repeat with N new addresses per block indefinitely, at near-zero attacker cost, while the chain performs the association state-write work for every transaction with zero fee revenue collected.

func HandleAssociateTx(ctx sdk.Context, ek *evmkeeper.Keeper, atx *ethtx.AssociateTx, readOnly bool) (sdk.Context, error) {
	V, R, S := atx.GetRawSignatureValues()
	V = new(big.Int).Add(V, utils.Big27)
	// Hash custom message passed in
	customMessageHash := crypto.Keccak256Hash([]byte(atx.CustomMessage))
	evmAddr, seiAddr, seiPubkey, err := helpers.GetAddresses(V, R, S, customMessageHash)
	if err != nil {
		return ctx, err
	}
	_, isAssociated := ek.GetEVMAddress(ctx, seiAddr)
	if isAssociated {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInvalidRequest, "account already has association set")
	}
	if !IsAccountBalancePositive(ctx, ek, seiAddr, evmAddr) {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInsufficientFunds, "account needs to have at least 1 wei to force association")
	}
	if !readOnly {
		if err := AssociateAddress(ctx, ek, evmAddr, seiAddr, seiPubkey); err != nil {
			return ctx, err
		}
	}
	return ctx.WithPriority(antedecorators.EVMAssociatePriority), nil
}

```markdown
The EVM ante chain performs, in order:

1. **Cosmos field rejection** — EVM txs must not use Cosmos-specific fields (memo, timeout, fees, etc.).
2. **Preprocessing** — unpacks the inner Ethereum tx, recovers the sender via ECDSA, populates derived metadata. Associate transactions are handled here.
3. **Address derivation** — for Cosmos-signed txs, derives the EVM address from the public key and sets up mappings.
4. **Basic validation** — init code size, non-negative value, intrinsic gas.
5. **Signature/nonce verification** — validates chain ID and nonce. CheckTx uses pending nonce logic for mempool ordering; DeliverTx requires exact match.
6. **Fee validation** — checks against base fee and minimum fee, executes gas purchase, stores any fee surplus.
7. **Gas metering** — sets the Sei gas meter using the converted EVM gas limit.
```
