### Title
OP_RETURN `data` output omitted from transaction weight/vbytes calculation, undercharging the fee below the requested rate - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` pushes an OP_RETURN output for caller-supplied `data` onto `tx_outs`, but both calls to `calculate_weight_vbytes` pass only `payments` (not `tx_outs`) as the output list. The OP_RETURN output's size is therefore never counted in `vbytes`, so `needed_fee` (and `fee_with_change`) are computed on a smaller transaction than the one actually signed and broadcast. This is the same bug class as the reference finding: an optional input variant (decaying bond / `data` payload) takes a cost-calculation path that silently drops a term, producing a mispriced result.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the weight is computed:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds its template `Transaction` solely from `payments` plus the optional `change` script — it never sees the OP_RETURN output (`send.rs:85-99`). The same omission occurs in the change branch:

```rust
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
let fee_with_change = fee_per_vbyte * vbytes_with_change;
```

The final `Transaction` includes the OP_RETURN output (`tx.output: tx_outs`, line 250), so its real vbytes exceed `vbytes`/`vbytes_with_change` by roughly the serialized size of the OP_RETURN output — up to ~90 vbytes for the maximum 80-byte payload (8-byte value + ~83-byte script + output overhead). Two consequences:

1. `needed_fee()` is documented as "the fee necessary for this transaction to achieve the fee rate specified at construction", yet it under-reports by up to `fee_per_vbyte * ~90` sats whenever `data` is set.
2. With no change output, the actual paid fee (`sum(inputs) - sum(outputs)`) is whatever is left over, so the effective feerate may still be adequate by accident. With a change output, the change is sized by the undercounted `fee_with_change`, so the transaction deterministically pays a lower feerate than `fee_per_vbyte` requested — and the `TooLowFee` check at line 211 is also evaluated against the undercounted `vbytes`, so a transaction can pass the check while actually falling below `DEFAULT_MIN_RELAY_TX_FEE` once the OP_RETURN output is included.

### Impact Explanation
Any `SignableTransaction` built with `data` (Serai uses this to commit metadata/refunds in Bitcoin sends) silently pays less than the requested `fee_per_vbyte`. At modest fee rates the shortfall of up to ~90 vbytes worth of fee can push the transaction below the minimum relay feerate or below the rate needed for timely confirmation, causing the signed transaction to be rejected by peers or stuck in the mempool. Because the multisig commits to these exact outputs via `Prevouts::All`, correcting the fee requires a new signing round; the produced transaction is mispriced at signing time with no in-band way to fix it.

### Likelihood Explanation
The bug triggers deterministically whenever `data: Some(_)` is passed — the size of the discrepancy grows with payload length, worst case at the 80-byte `TooMuchData` limit. It requires no adversarial behavior beyond supplying an OP_RETURN payload, which is a supported code path. Exploitation/loss is indirect (stuck or underpriced transactions rather than theft), consistent with a Medium severity mispricing analog.

### Recommendation
Include the OP_RETURN output in the weight template — e.g., compute `calculate_weight_vbytes(tx_ins.len(), &tx_outs-scripts, None)` or pass the full `tx_outs` (value-independent since only `script_pubkey` affects size), and likewise when computing `weight_with_change`/`vbytes_with_change`. Also evaluate the `TooLowFee` check against the vbytes figure that includes the OP_RETURN output.

### Proof of Concept
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

1. Call `new(inputs, payments, None, Some(vec![0u8; 80]), fee_per_vbyte)`.
2. `tx_outs` gains a ~91-byte OP_RETURN output at lines 194-202.
3. `calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) constructs a `Transaction` containing only `payments` — the OP_RETURN is absent — so `vbytes` excludes ~91 vbytes.
4. `needed_fee = fee_per_vbyte * vbytes` and the min-relay check at line 211 both use this undercounted size.
5. With `change = Some(..)`, `fee_with_change` (line 227) has the same omission, and the change output is sized to leave exactly that underestimated fee, so the signed transaction's real feerate is strictly below `fee_per_vbyte`.

Comparing `needed_fee()` against `tx.weight()`/`get_virtual_tx_size` of the returned `transaction()` (which does contain the OP_RETURN output) demonstrates the discrepancy directly.
