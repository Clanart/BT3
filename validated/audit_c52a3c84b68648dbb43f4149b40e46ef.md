### Title
Unbounded allocation on attacker-controlled `n` in `ThresholdKeys::read` before parameter validation - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` in `crypto/dkg/src/lib.rs` trusts an attacker-controlled 16-bit `n` field and immediately performs `Vec::with_capacity(usize::from(n))` plus `n` sequential `read_F`/`read_G` deserializations, before `ThresholdParams::new(t, n, i)` is validated at the end of the function. This is the same bug class as GHSA-m9gh-vj53-gvh9 (CWE-770): attacker-supplied input controls memory allocation without a maximum-size check at the point of allocation.

### Finding Description
The deserialization order is:

1. Read and check the curve ID (`crypto/dkg/src/lib.rs:575-589`).
2. Read `t`, `n`, `i` as raw `u16`s (`crypto/dkg/src/lib.rs:591-602`). No validation occurs here — `n` may be up to 65535.
3. If the interpolation byte is `0` (Constant), execute `Vec::with_capacity(usize::from(n))` and push `n` results of `C::read_F` (`crypto/dkg/src/lib.rs:606-613`). This allocates `n * size_of::<C::F>()` (~2 MB for a 32-byte scalar at `n = 65535`) and performs `n` scalar reads.
4. Read one `secret_share` scalar (`crypto/dkg/src/lib.rs:618`).
5. Loop `(1..=n)` inserting `read_G` results into a `HashMap` (`crypto/dkg/src/lib.rs:620-623`) — `n` point decompressions plus `n` hash-map entries.
6. Only now call `ThresholdParams::new(t, n, i)` (`crypto/dkg/src/lib.rs:625-626`), the first point at which `n` is checked for sanity relative to `t`.

Because validation happens last, an unprivileged party feeding bytes to `ThresholdKeys::read` can claim `t = 1, n = 65535` and force either (a) a ~2 MB up-front `with_capacity` allocation after sending only ~11 bytes (if the stream then truncates, the work/allocation was still performed), or (b) ~4 MB of retained allocations and 65535 point decompressions if they actually stream the body — with `ThresholdParams` still accepting the parameters since `t <= n <= u16::MAX` is satisfiable.

### Impact Explanation
Any component that deserializes `ThresholdKeys` from unauthenticated bytes (e.g., key material transmitted during DKG/reshare/recovery flows before the sender is authenticated as a legitimate participant) can be driven to allocate memory and perform group-decompression work disproportionate to what the attacker sends. The header-only variant gives an amplification of roughly 2 MB allocation per ~11 input bytes per call; repeated parallel calls cause memory pressure and CPU burn (each `read_G` is an elliptic-curve decompression) without requiring a large upload, matching the advisory's "unnecessary memory allocations" impact.

### Likelihood Explanation
Reachability requires a call path feeding attacker-controlled bytes into `ThresholdKeys::read` prior to authenticating the sender — the same precondition class as the engine.io advisory (payload read before the peer is confirmed known). The amplification factor is bounded by `u16` (~2–4 MB per message rather than unbounded), which caps per-message impact, but there is no transaction/message size gate inside the crate itself; enforcement is delegated entirely to callers. Severity: Medium — real resource-consumption asymmetry, but bounded and transient per call.

### Recommendation
Validate `t`/`n`/`i` via `ThresholdParams::new` immediately after reading them (before any allocation), reject `n` values inconsistent with the expected set size, and replace the `Vec::with_capacity(n)` + eager `read_F`/`read_G` loops with incremental reads so allocation grows only as data actually arrives — mirroring the upstream fix of deferring body loading until limits are confirmed.

### Proof of Concept
Feed `ThresholdKeys::read` a buffer containing: valid `C::ID` length + `C::ID`, `t = 0x0001`, `n = 0xFFFF`, `i = 0x0001`, interpolation byte `0x00`, then truncate. The call executes `Vec::with_capacity(65535)` (~2 MB) and begins `read_F` before any parameter validation or authentication occurs:

```rust
// crypto/dkg/src/lib.rs:606-613
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n)); // n = 0xFFFF, unvalidated
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
```

versus the validation only at `crypto/dkg/src/lib.rs:625-626`:

```rust
ThresholdKeys::new(
  ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
  ...
)
```

A minimal PoC: `let mut bytes = id_len_bytes ++ C::ID ++ [1,0] ++ [0xFF,0xFF] ++ [1,0] ++ [0]; ThresholdKeys::<C>::read(&mut bytes.as_slice())` — observe the 65535-element capacity allocation with ~11 bytes of attacker input.
