### Title
Payout attribution (`payout_payer_operator_xonly_pk`) is derived solely from attacker-controlled OP_RETURN data with no signature/funding proof - ([File: core/src/verifier.rs])

### Summary
`Verifier::update_finalized_payouts` (core/src/verifier.rs:2283-2352) attributes a confirmed payout to whichever xonly pubkey appears in the first OP_RETURN output of the payout transaction, using `get_first_op_return_output` and `parse_op_return_data` with no check that the named operator co-signed, funded, or otherwise authorized that payout. Because anyone can broadcast a transaction spending the withdrawal UTXO with an arbitrary OP_RETURN, an attacker can frame a victim operator by naming their xonly pubkey.

### Finding Description
The binding that should hold is: `payout_payer_operator_xonly_pk[idx] == xonly_pk(party whose collateral funded payout output[idx])`. Instead, the code sets it to whatever bytes are found in the payout tx's first OP_RETURN output: [1](#0-0) 

There is no `SECP.verify_schnorr`, no check that the transaction's inputs originate from the named operator's known funding path, and no requirement that the operator co-signed the transaction. The only "guard" is that `operator_xonly_pk` becomes `None` if OP_RETURN is missing or malformed — but a syntactically valid 32-byte xonly pubkey belonging to an unrelated (victim) operator passes trivially. This value is committed straight to the DB via `update_payout_txs_and_payer_operator_xonly_pk` and later read by `Database::get_first_unhandled_payout_by_operator_xonly_pk`, which is polled by each operator's own `PayoutCheckerTask` filtered on `self.operator.signer.xonly_public_key`: [2](#0-1) 

If a victim operator's pubkey is forged into the OP_RETURN, the victim's own automated `PayoutCheckerTask` will see this "unhandled payout" as attributed to itself and will automatically call `handle_finalized_payout`, which drives that operator's real kickoff/round transaction flow (spending its own real collateral) for a payout it never made and was never asked to make. There is no code path in `update_finalized_payouts` or `get_first_unhandled_payout_by_operator_xonly_pk` that re-validates the payer's identity against the transaction's actual funding inputs or a signature.

### Impact Explanation
This lets an unprivileged attacker unilaterally trigger a victim operator's kickoff/reimbursement flow for a withdrawal the victim never paid, by broadcasting any transaction that spends the withdrawal UTXO with a forged OP_RETURN. Depending on downstream checks inside `handle_finalized_payout` (not fully inspectable within the tool budget here), this can result in the victim operator burning collateral/fees initiating a kickoff for a payout it did not make, or being made a target for Challenge/Disprove flows tied to a payout it never funded — matching the Critical category "an honest operator's collateral burned" / "operator reimbursed for a payout it never funded." The attack is repeatable per withdrawal and requires no special privileges beyond broadcasting one Bitcoin transaction and paying its fee.

### Likelihood Explanation
Any withdrawal that becomes available on Bitcoin can be front-run: the attacker only needs to construct a payout transaction that spends the withdrawal UTXO correctly (satisfying the withdrawal contract/output requirements) and append an OP_RETURN with an arbitrary 32-byte value (a victim operator's known public xonly pubkey — operator identities are public). No signature, key share, or collateral is required from the attacker to control the OP_RETURN payload. This is inexpensive (one transaction + fee) and fully reproducible.

### Recommendation
Do not trust OP_RETURN content alone for payer attribution. Require the payout transaction to be signed/authorized by the named operator (e.g., verify a Schnorr signature from that operator's key over the payout transaction, or require that the payout's funding input(s) originate from that operator's known operator wallet/output before recording `payout_payer_operator_xonly_pk`, and additionally require an explicit consent step by the operator itself before `handle_finalized_payout` acts on an attributed payout).

### Proof of Concept
Not fully verifiable within this session — I could not inspect `Operator::handle_finalized_payout` to confirm whether it independently re-derives/re-checks funding authorization before spending the operator's collateral, which is necessary to determine whether this reaches a bridge-value-moving outcome or is merely a benign DB misattribution. A `cargo test` proof would need to:
1. Set up a deposit/withdrawal in test harness, broadcast a payout tx spending the withdrawal UTXO funded by an unrelated key but with OP_RETURN containing victim operator B's xonly pubkey.
2. Run `update_finalized_payouts` and assert `payout_payer_operator_xonly_pk` for that withdrawal equals B's pubkey while B never signed/funded the transaction.
3. Trigger operator B's `PayoutCheckerTask::run_once` and assert whether `handle_finalized_payout` proceeds to spend B's real collateral for a payout B never made.

Given the inability to confirm step 3's downstream guard within this investigation, this should be treated as a probable but not fully confirmed finding — recommend a follow-up session with full repo access to trace `Operator::handle_finalized_payout` before finalizing severity.
