## Title
Stale line-selection indices are silently reapplied to a freshly-fetched diff when creating partial commits, allowing unreviewed content to be staged and committed - (`File: app/src/lib/git/apply.ts`)

### Summary
The Ronin fix addressed unsynchronized reads of mutable `Consortium` signer fields that could be read while another goroutine was mutating them, producing an inconsistent view of state used for security-relevant decisions. The GitHub Desktop analog is a TOCTOU-style inconsistency between the diff a user visually reviewed/selected lines from and the diff that is actually used to build the commit: `WorkingDirectoryFileChange.selection` stores only line-index bitmasks (`DiffSelection`), not the diff content itself, and staging re-fetches a brand-new diff from disk at commit time rather than validating it against the diff the indices were computed from.

### Finding Description
When a user makes a partial selection of lines in the Changes view, the UI computes an `absoluteIndex`-based `DiffSelection` against the `ITextDiff` that was loaded and displayed at that moment (see `app/src/ui/changes/changes.tsx` and `isSelected(absoluteIndex)` usage in `app/src/lib/patch-formatter.ts:157`).

When the user commits, `_commitIncludedChanges` captures the current `WorkingDirectoryFileChange[]` (with their existing `selection` field) synchronously from `repositoryStateCache` [1](#0-0) , then calls `createCommit` → `stageFiles` → `applyPatchToIndex` for any file with a partial selection [2](#0-1) .

Critically, `applyPatchToIndex` does **not** reuse the diff the user reviewed. It fetches a fresh diff straight from the working directory at staging time: [3](#0-2) 

That fresh diff is then combined with the *old* selection bitmap via `formatPatch(file, diff)`, which walks the new diff's hunks and simply asks, for each line, `file.selection.isSelected(absoluteIndex)` [4](#0-3) . There is no check comparing the diff that produced the selection to the diff being patched — no hash, no line-count/hunk-shape validation, no re-fetch-and-compare guard analogous to the read-lock the Ronin fix introduced.

If the tracked file's on-disk content changes between the time the diff was displayed (and the user made a line selection) and the time `applyPatchToIndex` runs, the hunk layout and `absoluteIndex` numbering shift. The stale bitmask is then applied against unrelated lines in the new diff, so `formatPatch` can silently select/deselect the wrong lines. Repository-attacker-controllable triggers for such a mid-review file mutation include tooling that the repository can cause to run against the working tree in the background (e.g., project-configured watch/build/format tasks, lint-staged/husky style hooks wired via `package.json` scripts that Desktop or an IDE the user has open executes on file save/checkout), all of which are "attacker controls a cloned/fetched repository" scenarios in scope.

### Impact Explanation
This can cause **silent corruption of what the user commits** — the review the user performed no longer corresponds to what is actually staged and recorded in the commit, because the line-selection bitmap is blindly reapplied to a diff it was never computed against. Depending on the divergence, this can result in unintended lines being included (leaking content the user meant to exclude) or intended lines being dropped (silently discarding a fix/check), all inside a Desktop-generated commit that the user then pushes, believing it matches what they reviewed.

### Likelihood Explanation
This requires a narrow timing window (a file mutation occurring between diff display/selection and the click-to-commit → `applyPatchToIndex` call) and a mechanism to mutate a tracked file in that window without the user's explicit action — realistic in developer workflows where build/format/watch tooling from the opened repository runs in the background. It does not require local/physical access, admin rights, or pre-existing host compromise, matching the "in-scope" criteria, but the exploitation window is small and non-deterministic, which limits reliability compared to a guaranteed win.

### Recommendation
Before applying a stored `DiffSelection` to a newly fetched diff in `applyPatchToIndex` (`app/src/lib/git/apply.ts`), validate that the diff hasn't changed since the selection was made — e.g., by comparing the diff's hunk structure/line count or a content hash captured at selection time, and refusing/re-prompting the commit (similar in spirit to the stale-state re-checks already used elsewhere, such as `_selectStashedFile`'s comparison in `app/src/lib/stores/app-store.ts:3661-3668`) rather than silently reapplying possibly-mismatched line indices.

### Proof of Concept
1. Open a repository in Desktop containing a file with a background process (e.g., a watch/build script the repo instructs the user to run, or an editor auto-format-on-save hook) that periodically rewrites a tracked file.
2. In the Changes view, open the diff for that file and select only specific lines for a partial commit.
3. While the commit dialog/message is being composed (a natural user delay), let the background process rewrite the file, changing its line layout without altering the file's overall "modified" status.
4. Click Commit. `_commitIncludedChanges` uses the old `WorkingDirectoryFileChange.selection` object [5](#0-4) , and `applyPatchToIndex` fetches the new diff and applies that stale selection to it [6](#0-5) .
5. Inspect the resulting commit: it contains a hunk selection that does not match what was visually selected in step 2, demonstrating the corrupted commit content.
