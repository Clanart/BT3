### Title
`SignableTransaction::new` omits the OP_RETURN output when estimating weight/vbytes, so the transaction pays a lower fee than accounted and may fall below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

Analogous to the Allo fee-on-transfer issue — where the contract credits `amountAfterFee` even though the actual amount delivered is less — `SignableTransaction::new` accounts a fee (`needed_fee`) computed from a vsize estimate that does not include the OP_RETURN output it actually adds to the transaction. The transaction commits to a fee smaller than the fee rate requires for its true size, and the minimum-relay-fee check is also performed against the underestimated vsize, so a transaction that will not relay can be produced and signed.

### Finding Description

`SignableTransaction::new` accepts an optional `data` argument, which it turns into a real `TxOut` (OP_RETURN) pushed onto `tx_outs`:

```rust
// networks/bitcoin/src/wallet/send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}
```

However, both fee/size estimates call `calculate_weight_vbytes` with `payments` — not `tx_outs` — so the synthetic transaction used for weight calculation contains only the payment outputs (plus the optional change output), never the OP_RETURN output:

- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` (send.rs:204)
- `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:226)
- Inside `calculate_weight_vbytes`, outputs are built solely from `payments` (send.rs:85-93) plus change (send.rs:95-99).

The result is `vbytes`/`vbytes_with_change` underestimated by the serialized size of the OP_RETURN output (8-byte value + script length + 1-byte opcode + pushdata prefix + up to 80 bytes of data, roughly 10–90+ vbytes). `needed_fee = fee_per_vbyte * vbytes` (send.rs:206, 227) is therefore smaller than the fee the chosen rate actually requires.

Two accounting mismatches follow, mirroring the Allo bug where `increasePoolAmount` records more than was delivered:

1. The min-relay check compares the under-computed `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes` (send.rs:211). When `fee_per_vbyte` is at/near the minimum, the real transaction's fee rate falls below the relay minimum once the OP_RETURN output is included.
2. The change path computes `fee_with_change` from `vbytes_with_change` (also missing the OP_RETURN output) and sets `needed_fee = fee_with_change` (send.rs:227-232), so even when change is created the paid fee is below the intended rate, while `needed_fee()` reports it as correct.

This is reachable with public inputs: the `data` payload comes from the plan/payment data derived from user-supplied `InInstruction` data (forwarded/refund flows embed arbitrary data), so an unprivileged user who submits a transfer carrying data causes the multisig to produce an under-fee'd transaction.

### Impact Explanation

- The signed transaction pays `sum(inputs) - sum(outputs) = needed_fee`, which is less than `actual_vsize * fee_per_vbyte`. For low fee rates this can be below Bitcoin's default minimum relay fee, so the transaction will not propagate to miners; the funds it spends (multisig inputs) are effectively locked until a replacement is produced — "funds reported sent that are not spendable/confirmable".
- `needed_fee()` and the recorded accounting overstate the delivered fee rate, analogous to `increasePoolAmount(amountAfterFee)` recording more than the strategy actually received. When change is dropped (`value < DUST`), the excess becomes additional fee, further diverging actual from accounted fee without any size-based justification.
- Severity: Medium — requires the OP_RETURN path plus a marginal fee rate, but is triggerable by unprivileged transaction data.

### Likelihood Explanation

Any plan that attaches `data` (user-controlled instruction payloads up to 80 bytes, send.rs:171-173) produces a systematically underestimated fee. Whether the transaction actually fails to relay depends on `fee_per_vbyte` being near the relay minimum, but the accounting is wrong in every case where `data.is_some()`.

### Recommendation

Include the OP_RETURN output in the size estimation. Either build the weight-estimation transaction from `tx_outs` (which already contains the OP_RETURN output) rather than `payments`, or pass the data output into `calculate_weight_vbytes` so both the no-change and with-change estimates account for it. Additionally, re-run the min-relay-fee check against the final, correctly sized vbytes, and consider checking `self.fee()` against `actual_vsize * DEFAULT_MIN_RELAY_TX_FEE` post-construction as a sanity assertion.

### Proof of Concept

```rust
// Conceptual: in networks/bitcoin, construct a SignableTransaction with data
let data = Some(vec![0u8; 80]); // max allowed per the <= 80 check
let tx = SignableTransaction::new(inputs, &payments, Some(change), data, fee_per_vbyte).unwrap();

// The real transaction has one more output than the estimate used:
assert_eq!(tx.transaction().output.len(), payments.len() + 2); // payments + OP_RETURN + change

// Actual vsize exceeds the estimated vsize by ~90 bytes, so:
// tx.fee() (= needed_fee) < tx.transaction().vsize() as u64 * fee_per_vbyte
// With fee_per_vbyte == 1 and vsize crossing the min-relay threshold,
// the real feerate is < 1 sat/vb and the TX will not be relayed,
// even though the TooLowFee check at send.rs:211 passed.
```

The fix is to feed the OP_RETURN-bearing output set into `calculate_weight_vbytes` so `needed_fee` reflects the transaction's true size.
