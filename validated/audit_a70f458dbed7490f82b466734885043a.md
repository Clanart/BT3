## Title
Delimiter-less Concatenation in App Proxy Signature Verification Allows Hash Collision / Forged Signature Reuse - (`File: lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

## Summary
`ShopifyApp::AppProxyVerification#calculated_signature` builds the HMAC input by concatenating `"key=value"` strings for every query parameter with **no delimiter between pairs** (`.sort.join` with the default empty separator). This is the same root cause described in the referenced report: multiple dynamic-length values are packed together with no boundary marker before hashing/signing, so an attacker who can influence how the raw query string is split into key/value pairs can shift bytes across the `key`/`value` boundary of different parameters while producing the exact same concatenated string — and therefore the exact same signature — for a semantically different parameter set. [1](#0-0) 

## Finding Description
`verify_proxy_request` accepts an app-proxy request only if `query_string_valid?` returns true, which recomputes the signature from all query params except `signature` and compares it to the supplied one: [2](#0-1) 

The signature input is built as:
```ruby
sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join
``` [3](#0-2) 

There is no separator between different `"key=value"` segments once they are joined. This is structurally identical to `abi.encodePacked(a, b)` with two dynamic-length arguments: the byte boundary between `key` and `value`, and between one pair and the next, is not fixed, so distinct parameter maps can serialize to the identical byte string that gets HMAC'd.

Concretely: `{"a" => "1", "b" => "2"}` serializes to `"a=1" + "b=2"` = `"a=1b=2"`. A different, unrelated parameter map `{"a=1b" => "2"}` (a single parameter whose *key* is the literal string `a=1b`) serializes to `"a=1b=2"` — the identical byte string. Since `Rack::Utils.parse_query` URL-decodes keys before building the hash, a raw request query string containing `a%3D1b=2` is parsed into the key `"a=1b"` mapped to value `"2"`, i.e., exactly the collided map. Both parameter sets produce the same `sorted_params` value and therefore the same HMAC digest under the same secret, meaning a signature that Shopify computed and issued for one query string will validate an entirely different query string constructed by an attacker.

## Impact Explanation
An app proxy request routed through Shopify to a merchant's storefront (e.g. `.../apps/my-app?shop=...&path_prefix=...&timestamp=...&logged_in_customer_id=...&signature=...`) is something any visitor — including an anonymous, unauthenticated user — can trigger legitimately and capture, since app proxy signing does not require merchant credentials, only a storefront visit. Because the signature only binds the ambiguous concatenated byte string rather than an unambiguous encoding of the parameter map, an attacker who has captured one genuine `(query_string, signature)` pair can re-encode the query string (moving `=` characters into percent-encoded key names) to change which values are attributed to which parameter, or to merge/split params such as `shop`, `path_prefix`, or `logged_in_customer_id`, while the recomputed signature stays valid. This can be used to forge acceptance of a query string whose actual semantic content (e.g., which shop, which logged-in customer id) differs from what Shopify actually signed, defeating the purpose of `query_string_valid?` as an authenticity check for app-proxy traffic — the exact "signedOnly bypass via hash collision" pattern from the source report.

## Likelihood Explanation
Exploitation requires the attacker to first obtain one legitimately signed app-proxy query string (trivial, since any storefront visitor can generate one) and then craft a colliding re-encoding that both (a) produces an identical `sorted_params` byte string and (b) results in a parameter map useful to the attacker (e.g., a different `logged_in_customer_id` or additional trusted-looking parameter). Because the concatenation has no separators at all between the fields as well as between the values of multi-valued params (joined with `,`), an attacker has significant freedom to shift characters across key/value and pair boundaries, making practical collisions constructible rather than merely theoretical, matching the medium-severity classification of the original bug class.

## Recommendation
Do not build the value to be HMAC'd by naive string concatenation of dynamic-length fields. Instead:
- Insert an unambiguous delimiter between every `key` and `value`, and between successive pairs, that cannot itself appear (or is escaped) in keys/values (e.g. length-prefix each field, or use a structured/canonical encoding such as escaping `=`, `,`, and the pair separator before joining).
- Alternatively, compute the HMAC over a canonical, unambiguous serialization (e.g. JSON with sorted keys) instead of ad-hoc string concatenation, mirroring the EIP-712-style fix referenced in the source report.

## Proof of Concept
```ruby
require "openssl"
require "rack/utils"

secret = "secret"

def calculated_signature(secret, query_hash_without_signature)
  sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join
  OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), secret, sorted_params)
end

# "Genuine" query string as would be produced/signed for a real app-proxy request
genuine_hash = { "a" => "1", "b" => "2" }
sig = calculated_signature(secret, genuine_hash)

# Attacker-crafted query string: single param whose *key* literally contains "1b"
# Raw query string sent to the app: "a%3D1b=2&signature=<sig>"
colliding_hash = Rack::Utils.parse_query("a%3D1b=2")
# => {"a=1b" => "2"}

puts calculated_signature(secret, colliding_hash) == sig # => true, forged/colliding acceptance
```
Both `genuine_hash` and `colliding_hash` are semantically different parameter maps, yet `calculated_signature` returns the same digest for both because `.collect { ... }.sort.join` provides no delimiter between concatenated fields, allowing `query_string_valid?` in `AppProxyVerification` to accept the attacker's crafted request as if it carried the originally-signed parameters.
