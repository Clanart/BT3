Confirmed: `handle_unsigned` is a fully unauthenticated, `ensure_none`-gated extrinsic, and `handle_get_requests` places no restriction on the `address` field beyond a 32-byte-length check before minting.

### Title
Unbounded/self-declared `address` beneficiary in `handle_get_requests` allows reputation-reward theft from the actual delivering relayer - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`pallet-state-coprocessor::handle_unsigned` is dispatched via `ensure_none(origin)` [1](#0-0) , so *any* unsigned caller can submit a `GetRequestsWithProof` payload once they observe a valid, still-unclaimed `GetRequest` + state proof pair (which is public information relayed cross-chain). The payload carries a self-declared `address: Vec<u8>` field described only as "Address that should be credited with fees" [2](#0-1) . Nothing in the verification pipeline binds `address` to the entity that actually did the proof-fetching/relaying work — it is neither derived from a signature nor checked against any relayer registry.

### Finding Description
The external report's "unbounded/uncontrolled request field" bug class maps here to an **unbounded trust field**: `address` is copied verbatim into the reputation-minting and response-receipt logic without provenance checks.

- `handle_get_requests` mints `ReputationAsset` to `address` proportional to `total_bytes` (the "work paid for") [3](#0-2) .
- It also stores `address` as the `response_receipt` signer and as the relayer credited in `Event::GetRequestHandled` [4](#0-3) [5](#0-4) .
- `validate_unsigned` re-executes `handle_get_requests` purely to check it doesn't error, and its only anti-replay defense is a `provides` tag derived from the *request commitments*, not from `address` [6](#0-5) .

Because the actual expensive/trusted work (fetching source+destination state proofs and constructing `GetRequestsWithProof`) is done off-chain by the legitimate relayer in `tesseract/messaging/messaging/src/get_requests.rs`, and the finished payload (including proofs) is visible on the wire/mempool before inclusion, any third party can copy an honest relayer's `GetRequestsWithProof`, swap in their own `address`, and resubmit it (front-running is explicitly out of scope per the impact gate, but this is not front-running of a *pending* on-chain transaction — it is copying a fully-formed, valid payload and substituting the payee before either version lands, i.e., a race the protocol itself does not adjudicate by relayer identity at all). The protocol has zero binding between "who fetched/verified the proof" and "who gets the reputation payout" — the field is unauthenticated data, exactly the unbounded/unchecked-input pattern flagged in the external report.

### Impact Explanation
This directly causes **wrong-beneficiary fund/reward diversion**: the relayer that did the real off-chain work (querying and assembling state proofs across two chains) can be preempted by any observer who resubmits the same message with a different `address`, stealing the `ReputationMinted` payout [7](#0-6) . Reputation tokens are minted via `ReputationAsset::mint_into`, i.e., real value is created and assigned to the wrong account — this is loss of relayer earnings / unauthorized value transfer, not merely a griefing/DoS concern.

### Likelihood Explanation
High. No privileged role, relayer key, or governance action is required — only visibility into a submitted (or about-to-be-submitted) `GetRequestsWithProof` and an unsigned transaction to the public mempool. The whole flow (`handle_unsigned`) is explicitly `ensure_none` and open to any submitter [8](#0-7) ; the batches are also visible off-chain since the relayer streams them from a public receiver channel [9](#0-8) .

### Recommendation
Bind the reputation/receipt beneficiary to a verifiable identity instead of an unauthenticated field: require `address` to be a signature-recovered public key/account over the batch's commitment set (mirroring the `Signature` pattern already used in `RequestMessage`/`ResponseMessage`), or replace `ensure_none` + free-form `address` with `ensure_signed(origin)` and use the transaction signer as the reward recipient, exactly as `outbound_request_delivery_message`/`OutboundRequestDeliveryClaim` already do for the analogous relayer-reward flow [10](#0-9) .

### Proof of Concept
1. Relayer A builds a legitimate `GetRequestsWithProof` for a real, unclaimed `GetRequest` (valid source/dest state proofs) and broadcasts it via `handle_unsigned` with `address = relayer_A_pubkey`.
2. Attacker B observes this payload in the transaction pool/gossip before/while it is included, copies `requests`, `source`, `response` verbatim, and resubmits an identical extrinsic with `address = attacker_B_pubkey`.
3. Whichever transaction lands first in the block succeeds; `dedup_requests` / `response_receipt` checks only prevent the *second* one from double-processing the same `GetRequest` — they do not restrict *who* may claim credit for the first successful one [11](#0-10) .
4. If B's transaction is included first (trivial via higher tip/priority or by resubmitting faster), B receives the `ReputationMinted` payout and is recorded as the relayer in `GetRequestHandled`, while A did all the off-chain proof-fetching work and receives nothing.
