### Title
`client_verification = false` Silently Disables Role-Based gRPC Method Access Control in Addition to mTLS Client-Cert Enforcement — (`core/src/servers.rs`)

### Summary

`create_grpc_server` uses a single boolean flag, `client_verification`, to control two independent security layers: (1) whether the TLS stack demands a client certificate, and (2) whether the `OnlyAggregatorAndSelf` interceptor enforces role-based method access control. Setting `client_verification = false` — which is explicitly allowed for the Aggregator on mainnet and for all actors on non-mainnet networks — silently replaces the `OnlyAggregatorAndSelf` interceptor with a `Noop` interceptor, removing all role-based access control. Any network-reachable caller can then invoke `Internal*` gRPC methods that are supposed to be callable only by the entity itself.

### Finding Description

In `core/src/servers.rs`, `create_grpc_server` branches on `config.client_verification` for both the TLS configuration and the interceptor selection:

```rust
// TLS layer
let tls_config = if config.client_verification {
    ServerTlsConfig::new().identity(server_identity).client_ca_root(client_ca)
} else {
    ServerTlsConfig::new().identity(server_identity)   // no client-cert requirement
};

// Interceptor layer — coupled to the same flag
let service = InterceptedService::new(
    service,
    if config.client_verification {
        OnlyAggregatorAndSelf { aggregator_cert, our_cert: client_cert }
    } else {
        Noop   // ← all role checks silently removed
    },
);
``` [1](#0-0) 

`OnlyAggregatorAndSelf` enforces two distinct rules:
- **Public methods**: only the aggregator cert or the entity's own cert may call them.
- **Internal methods** (those whose gRPC path starts with `Internal`): only the entity's own cert may call them. [2](#0-1) 

When `client_verification = false`, `Noop` is substituted and both rules vanish. Any caller — no certificate required — can invoke every method, including:

- **Operator**: `InternalEndRound`, `InternalFinalizedPayout`, `InternalCreateSignedTxs`, `InternalCreateAssertCommitmentTxs`
- **Aggregator**: `InternalSendTx`, `InternalGetEmergencyStopTx` [3](#0-2) 

`check_mainnet_requirements` blocks `client_verification = false` for Verifier and Operator on mainnet, but **the Aggregator is explicitly excluded from this guard**:

```rust
if matches!(actor_type, cli::Actor::Verifier | cli::Actor::Operator)
    && !self.client_verification
{
    misconfigs.push("CLIENT_VERIFICATION=false".to_string());
}
``` [4](#0-3) 

The Aggregator is therefore permitted to run on mainnet with `client_verification = false`, and `create_aggregator_grpc_server` even emits only a `warn!` (not an error) when client verification is enabled, implying the disabled state is the expected default:

```rust
if config.client_verification {
    tracing::warn!("Client verification is enabled on aggregator gRPC server");
}
``` [5](#0-4) 

The config field's own doc-comment further misrepresents the situation: it states "Client certificates are always validated against the CA certificate according to mTLS regardless of this setting," which is false — when `client_verification = false`, no client certificate is demanded at all. [6](#0-5) 

### Impact Explanation

With `client_verification = false` on the Aggregator (mainnet-permitted) and the gRPC port reachable:

- **`InternalSendTx`**: An unauthenticated caller can submit any raw transaction bytes to the Aggregator's Bitcoin broadcast path. If the attacker has obtained a valid pre-signed transaction (e.g., from mempool observation, a prior broadcast, or a leaked kickoff/payout tx), they can replay or front-run it at will, potentially disrupting the bridge's transaction sequencing or triggering premature state transitions.
- **`InternalGetEmergencyStopTx`**: An attacker can enumerate emergency-stop transactions for arbitrary move-txids, leaking internal bridge state.

On non-mainnet deployments (testnet4, regtest) where `client_verification = false` is common and `check_mainnet_requirements` does not run, the same bypass applies to Verifier and Operator servers, exposing `InternalEndRound` and `InternalFinalizedPayout` — methods that advance the bridge's round and payout state machine — to any network-reachable caller.

This is an **authentication/authorization bypass in gRPC actor roles** that grants privileged bridge actions to the wrong party, matching the allowed impact gate.

### Likelihood Explanation

The Aggregator's `client_verification = false` is the documented default (the code warns when it is *enabled*, not when it is disabled). Any operator following the standard deployment guide will run the Aggregator without client verification. If the Aggregator's gRPC port is reachable from outside the operator's private network — a realistic scenario for testnet deployments and possible for mainnet deployments that expose the Aggregator endpoint for backend integration — the bypass is immediately exploitable with no special tooling beyond a standard gRPC client.

### Recommendation

Decouple the two security mechanisms. The `client_verification` flag should control only whether a client certificate is *required* by the TLS layer. Role-based method access control (`OnlyAggregatorAndSelf`) should be applied independently and unconditionally for all TCP servers. Specifically:

1. Always install `OnlyAggregatorAndSelf` for Verifier and Operator TCP servers, regardless of `client_verification`.
2. For the Aggregator, apply a separate interceptor that at minimum restricts `Internal*` methods to callers presenting the Aggregator's own certificate.
3. Correct the doc-comment on `client_verification` to accurately describe its actual effect.
4. Add a mainnet guard for the Aggregator analogous to the existing Verifier/Operator guard.

### Proof of Concept

**Preconditions**: Aggregator running on mainnet (or any actor on testnet) with `client_verification = false` (the default) and gRPC port reachable.

**Steps**:

1. Connect to the Aggregator's gRPC endpoint with any TLS client (no client certificate needed — the server does not request one):
   ```
   grpcurl -insecure <aggregator_host>:<port> clementine.ClementineAggregator/InternalSendTx
   ```
2. Supply a `SendTxRequest` containing the raw bytes of any previously observed signed Bitcoin transaction (e.g., a kickoff or payout tx captured from the mempool).
3. The Aggregator accepts the call (no `UNAUTHENTICATED` status returned) and forwards the transaction to the Bitcoin network.

**Expected (correct) behavior**: The server rejects the call with `Status::unauthenticated("Unauthorized call to internal method (not self)")`.

**Observed behavior**: The `Noop` interceptor passes the request unconditionally; the handler executes. [7](#0-6) [8](#0-7)
