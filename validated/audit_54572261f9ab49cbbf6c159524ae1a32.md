### Title
CW20ERC20Pointer.approve() implements a read-then-delta allowance update, amplifying the classic ERC20 approve/transferFrom front-running race into unauthorized token extraction - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
`CW20ERC20Pointer.sol` is the ERC20-compatible wrapper contract Sei deploys as a pointer over a native CW20 token, letting EVM clients interact with CW20 balances through the standard ERC20 interface [1](#0-0) . Its `approve()` does not simply overwrite the spender's allowance like standard ERC20 tokens; instead it reads the current on-chain (CW20) allowance and issues a CosmWasm `increase_allowance` or `decrease_allowance` message for the *difference* between the new and current amount [2](#0-1) . This makes the well-known ERC20 approve/transferFrom front-running race worse than in a standard `approve(spender, amount)` implementation, because a spender who front-runs the owner's `approve` transaction with a `transferFrom` can cause the owner's transaction to compute a larger increase than intended, letting the spender extract more tokens than the owner ever approved in total.

### Finding Description
In standard ERC20 contracts (e.g. the vulnerability class in the external report), `approve(spender, amount)` unconditionally overwrites the allowance mapping, so the well-known race is: spender front-runs with `transferFrom` for the old allowance, then the owner's `approve` transaction still lands and grants the new allowance, letting the spender ultimately claim `old + new` tokens instead of just `new`.

`CW20ERC20Pointer.approve()` reproduces this exact race, but with an added complication: it computes `currentAllowance = allowance(msg.sender, spender)` at execution time and issues a *delta* update (`increase_allowance`/`decrease_allowance`) rather than an absolute set [3](#0-2) . The underlying CW20 pointer's `increase_allowance`/`decrease_allowance` handlers themselves also read-then-write the CW20 allowance state via a query followed by a delegatecall-based approve payload [4](#0-3) [5](#0-4) .

Exploit flow:
1. Alice has approved Bob (spender) for 100 tokens via the pointer.
2. Alice decides to change Bob's allowance to 150 and submits `approve(bob, 150)`.
3. Bob observes this pending transaction and front-runs it (via a higher gas price / EVM mempool ordering) with `transferFrom(alice, bob, 100)`, draining the full existing allowance down to 0.
4. Alice's `approve(bob, 150)` transaction is then included. It calls `allowance(alice, bob)`, which now returns `0` because Bob already consumed it. The contract computes `amount - currentAllowance = 150 - 0 = 150` and issues `increase_allowance(bob, 150)`.
5. Bob's allowance is now 150 (fresh), on top of the 100 he already extracted in step 3 — a total of 250 tokens moved for an intended 150-token approval, exactly matching the classic front-running exploit scenario described in the report, but reachable through the Sei EVM<->CW20 pointer bridge rather than a bespoke token contract.

This is directly reachable by any unprivileged EVM transaction sender interacting with a CW20 pointer contract — no validator, node, or governance privilege is required, only normal mempool/gas-price front-running of a public transaction, which is squarely in scope per the allowed EVM/pointer transaction surface.

### Impact Explanation
This results in unauthorized transfer of CW20-token-backed pointer assets via the pointer contract: a spender can extract more tokens than the owner ever intended to approve in total, directly causing fund loss to the token owner. Because the amount extracted scales with however many times the owner updates an existing nonzero allowance, an attacker can repeat this pattern with every `approve` call from a victim, extracting the full sum of every allowance ever granted rather than just the final approved amount.

### Likelihood Explanation
Likelihood is elevated relative to the standard ERC20 version of this bug because the pointer's delta-based `approve()` logic actively computes a fresh increase based on a manipulable `currentAllowance` read, rather than a simple overwrite — meaning the attacker doesn't need the owner to reduce an allowance to zero first (as in the classic scenario); any subsequent `approve` call to update an existing nonzero allowance is exploitable. Any spender who is a counterparty in an allowance relationship and who monitors the mempool for the owner's `approve` transactions can perform this attack with a simple front-run, requiring no special privileges.

### Recommendation
- Modify `CW20ERC20Pointer.approve()` to not read/derive a delta from the current allowance; either revert if `currentAllowance != 0 && amount != 0` (à la mitigations for classic ERC20 front-running), or expose separate `increaseAllowance`/`decreaseAllowance` functions and discourage direct absolute `approve` calls when a nonzero allowance already exists.
- Avoid computing allowance deltas based on a same-transaction read of mutable, front-runnable state; if delta semantics are required, source the "current" allowance from a value the caller explicitly commits to (e.g., an `expectedCurrentAllowance` parameter) so the transaction reverts rather than silently amplifying if state changed.
- Document that pointer-contract allowance owners should always set allowance to 0 before setting a new nonzero value, consistent with standard ERC20 hardening.

### Proof of Concept
1. Deploy/point a `CW20ERC20Pointer` at a CW20 token; Alice approves Bob for 100 tokens via `pointer.approve(bob, 100)` [2](#0-1) .
2. Alice submits `pointer.approve(bob, 150)` to update the allowance.
3. Bob, monitoring the mempool, submits `pointer.transferFrom(alice, bob, 100)` with a higher gas price so it lands first [6](#0-5) .
4. Alice's `approve(bob, 150)` executes afterward; `allowance(alice, bob)` returns 0 (fully drained by Bob's transfer), so the contract issues `increase_allowance(bob, 150)` [3](#0-2) .
5. Bob now holds the 100 tokens already transferred plus a fresh 150-token allowance — 250 tokens total moved/available versus the 150 Alice intended, confirming the fund-loss impact.

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }

// Increase the allowance of spender by amount.
// Expiration does not work here since it is not supported by ERC20.
pub fn execute_increase_allowance(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    spender: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&spender)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);

    // Query the current allowance for this user
    let current_allowance = querier.erc20_allowance(erc_addr.clone(), info.sender.clone().into_string(), spender.clone())?.allowance;

    // Set the new allowance as the sum of the current allowance and amount specified
    let new_allowance = current_allowance + amount;

    // Send the message to approve the new amount
    let payload = querier.erc20_approve_payload(spender.clone(), new_allowance)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };

    let res = Response::new()
        .add_attribute("action", "increase_allowance")
        .add_attribute("spender", spender)
        .add_attribute("amount", amount)
        .add_attribute("new_allowance", new_allowance)
        .add_attribute("by", info.sender)
        .add_message(msg);

    Ok(res)
}

// Decrease the allowance of spender by amount.
// Expiration does not work here since it is not supported by ERC20.
pub fn execute_decrease_allowance(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    spender: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&spender)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    // Query the current allowance for this spender
    let querier = EvmQuerier::new(&deps.querier);
    let current_allowance = querier.erc20_allowance(erc_addr.clone(), info.sender.clone().into_string(), spender.clone())?.allowance;

    // If the new allowance after deduction is negative, set allowance to 0.
    let new_allowance = match current_allowance.checked_sub(amount)
    {
        Ok(new_amount) => new_amount,
        Err(_) => Uint128::MIN,
    };
    
    // Send the message to approve the new amount.
    let payload = querier.erc20_approve_payload(spender.clone(), new_allowance)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };

    let res = Response::new()
        .add_attribute("action", "decrease_allowance")
        .add_attribute("spender", spender)
        .add_attribute("amount", amount)
        .add_attribute("new_allowance", new_allowance)
        .add_attribute("by", info.sender)
        .add_message(msg);

    Ok(res)
}
