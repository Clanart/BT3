### Title
Permanently locked vlMGP unlock/cooldown due to reverting reward-token transfer in `getReward()` - ([File: VLMGP.sol])

### Summary
`VLMGP.startUnlock()` and `VLMGP.unlock()` both unconditionally call `IMasterMagpie(masterMagpie).multiclaimFor(...)` before allowing the user's principal MGP to move to/from cooldown. That call chain ends in `BaseRewardPool`/`BaseRewardPoolV2.getReward()`, which loops over **all** registered reward tokens of the vlMGP rewarder and performs a `safeTransfer` for each one with a non-zero balance. If any single reward token transfer reverts, the entire `getReward()` call reverts, which bubbles up and reverts `multiclaimFor`, which in turn reverts `startUnlock()`/`unlock()` — permanently blocking the user from starting or completing the unlock of their own locked MGP.

### Finding Description
`startUnlock()` and `unlock()` each build a single-element `lps` array containing `address(this)` (the vlMGP token) and call: [1](#0-0) [2](#0-1) 

`multiclaimFor` routes to `_multiClaim`, which for each staking token calls `_claimBaseRewarder`: [3](#0-2) 

Because `vlMGPrewards` is passed as an empty inner array, `_claimBaseRewarder` takes the `rewarder.getReward(_account, _receiver)` branch, which iterates every registered reward token of the vlMGP rewarder and calls `safeTransfer` unconditionally for any non-zero pending amount: [4](#0-3) 

If any one reward token in that loop reverts on transfer (e.g., the rewarder's tracked balance for a token has drifted above its actual token balance due to accounting edge cases, or the receiving account is blacklisted/paused on that specific ERC20), the whole `getReward()` call reverts — there is no `try/catch` or per-token isolation. Since `unlock()`/`startUnlock()` have no way to bypass the `multiclaimFor` call, this makes it impossible for the affected user to ever unlock or start unlocking their MGP, regardless of how much time has passed in cooldown.

This is the same architectural pattern as the referenced report: a core, fund-releasing operation (`unstake`) is composed with unrelated external calls (`deposit`/`withdraw` on each derivative) in a way that a single failure anywhere in the loop reverts the entire operation and locks user principal. Here, the "principal-releasing" operation (`unlock`) is coupled to a reward-distribution loop over an unbounded/growing list of reward tokens (`rewardTokens.length`, appended over time via `queueNewRewards`), any one of which can permanently block the unlock.

### Impact Explanation
The impact is a permanent freeze of user principal: once a reward token tied to the vlMGP rewarder becomes untransferable (for any reason — insufficient real balance vs. tracked `userRewards`, a blacklist, or a paused/reverting token) all users of that rewarder lose the ability to `startUnlock()` or `unlock()` their MGP forever, since there is no owner/admin recovery path shown that removes a stuck reward token from the `getReward()` loop for affected users. This satisfies the "permanent freezing of funds" criterion.

### Likelihood Explanation
Likelihood is moderate: it does not require a malicious admin action — it can be triggered by ordinary reward-token behavior over time (e.g., accounting drift between `userRewards` bookkeeping and the rewarder's actual on-hand balance across many reward tokens accumulated via `queueNewRewards`/`donateRewards`), and is reachable purely from an ordinary user's own `unlock()`/`startUnlock()` transactions, which are core, frequently-used flows for every vlMGP holder.

### Recommendation
Decouple principal release from reward distribution:
- Wrap the reward-claim loop (or the whole `multiclaimFor` call inside `startUnlock`/`unlock`) in a `try/catch` so a failing reward token cannot block the unlock/cooldown flow.
- Alternatively, give users a way to skip claiming or specify which reward tokens to claim (already supported via `_rewardTokens` parameter for `getRewards`) so `unlock()`/`startUnlock()` can call `multiclaimFor` with an intentionally empty reward set to skip the loop.
- Add an admin/emergency function to deactivate or skip a specific stuck reward token in the rewarder's `rewardTokens` array without affecting other tokens.

### Proof of Concept
1. A vlMGP rewarder accumulates multiple reward tokens via `queueNewRewards`/`donateRewards` over time.
2. Due to accounting drift (e.g., rounding in `_earned`/`_updateFor`, or a reward token being paused/blacklisted for a specific receiver), a `safeTransfer` inside `getReward()` for one of these reward tokens begins to revert for a given user.
3. That user calls `startUnlock()` or `unlock()`:
   - [5](#0-4) 
   - [6](#0-5) 
4. Both functions unconditionally call `multiclaimFor`, which reaches `getReward()`, which reverts on the bad reward token transfer.
5. The entire `startUnlock()`/`unlock()` transaction reverts, and the user's MGP remains locked/in-cooldown indefinitely with no way to bypass the reward claim step.
