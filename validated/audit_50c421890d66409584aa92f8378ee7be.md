## Analog Identified: Missing upper-bound / component-range validation in upb's ProtoJSON `Timestamp` decoder

The external report's core pattern — an externally-supplied value (`newTimestamp`) that feeds a downstream computed value (`periodIndex`) with **no validation**, where the invalid case is explicitly known but silently accepted — has a direct, currently-reproducible analog in protobuf's own ProtoJSON `google.protobuf.Timestamp` well-known-type decoder in the upb runtime (used by Ruby, PHP, and Python-upb bindings).

### Title
Missing range validation on parsed date/time components and upper Timestamp bound in `jsondec_timestamp` - (File: `ruby/ext/google/protobuf_c/ruby-upb.c`, `php/ext/google/protobuf/php-upb.c`)

### Summary
`jsondec_timestamp()` parses a RFC 3339 string supplied via ProtoJSON into `google.protobuf.Timestamp.seconds`/`nanos`. It computes `seconds` from raw digit groups (year/month/day/hour/min/sec) via `jsondec_unixtime()` without validating that month is 1–12, day is valid for the month, hour is 0–23, minute/second are in range, or that the final computed `seconds` does not exceed the documented maximum (`kTimestampMaxSeconds = 253402300799`, i.e. `9999-12-31T23:59:59Z`). Only the lower bound is checked.

### Finding Description [1](#0-0) 

The function reads each date/time component with `jsondec_tsdigits()`, which only enforces digit count and delimiter characters — it performs no semantic range check (e.g. month ≤ 12, day ≤ 31, hour ≤ 23). After computing `seconds.int64_val`, the code only checks:
```
if (seconds.int64_val < -62135596800) {
    jsondec_err(d, "Timestamp out of range");
}
```
There is no corresponding check against the documented maximum, `253402300799`, defined in `timestamp.proto`: [2](#0-1) 

By contrast, the C++ core JSON parser (`ParseTimestamp` in `json/internal/parser.cc`) explicitly rejects zero/invalid `year`, `month`, `day` values, though it too accepts out-of-range `hour`/`minute`/`second` in some cases: [3](#0-2) 

The gap is *known and accepted* — it is explicitly enumerated in the project's own conformance "known failing" lists across multiple language backends, mirroring the "explicitly stated to cause problems, but chosen to be ignored" pattern in the external report: [4](#0-3) [5](#0-4) [6](#0-5) 

These lists show that `TimestampJsonInputDayTooLarge`, `TimestampJsonInputMonthTooLarge`, `TimestampJsonInputHourTooLarge`, `TimestampJsonInputHourTooLarge25`, `TimestampJsonInputMinuteTooLarge`, `TimestampJsonInputSecondTooLarge`, `TimestampJsonInputNonLeapFeb29`, and `TimestampJsonInputOffsetBoundaryOverflow` are all documented as "should have failed to parse, but didn't" for the C++, Python (upb backend), and Ruby (upb backend) implementations.

### Impact Explanation
An ordinary client sending a bounded ProtoJSON payload with a syntactically well-formed but semantically invalid timestamp string (e.g. `"1970-13-99T99:99:99Z"`) will have it silently accepted and converted into an internally-inconsistent `Timestamp` message (out-of-range `seconds`, or a `seconds` value that does not correspond to any real calendar date). Any consuming application that treats a successfully-parsed `Timestamp` as trustworthy (e.g. for expiry checks, ordering, indexing by day/period, as in the original oracle bug) inherits silently-corrupted data — an integrity failure directly analogous to the original report's `periodIndex` corruption from an unchecked `newTimestamp`. This is a data-integrity/validation-bypass issue, not a memory-safety issue.

### Likelihood Explanation
High likelihood of being triggered by ordinary, non-malicious ProtoJSON traffic (malformed but not malicious inputs, e.g. buggy upstream clients), and trivially reachable through the standard public JSON parse API with no special privileges. The issue is already reproducible today per the project's own conformance suite, and reproduces consistently for the upb-backed bindings (Ruby, PHP, Python-upb) and, for a subset of cases, the C++ implementation.

### Recommendation
In `jsondec_timestamp` (and shared upb logic used by Ruby/PHP/Python bindings), validate each parsed component before computing `seconds`:
- `1 <= mon <= 12`
- `1 <= day <= days_in_month(year, mon)` (accounting for leap years)
- `0 <= hour <= 23`, `0 <= min <= 59`, `0 <= sec <= 59`
- After combining offsets, check `seconds.int64_val <= kTimestampMaxSeconds` (253402300799) in addition to the existing minimum check.

Apply the equivalent hardening to `src/google/protobuf/json/internal/parser.cc`'s `ParseTimestamp` for the hour/minute/second components that are not currently checked for validity ranges, aligning behavior with the `RunValidJsonTest`/`ExpectParseFailureForJson` conformance expectations already defined in `conformance/binary_json_conformance_suite.cc`.

### Proof of Concept
Sending the following ProtoJSON payload to a message containing a `google.protobuf.Timestamp` field, parsed via the upb-backed Ruby/PHP bindings (or affected C++ paths per the failure list):
```json
{"optionalTimestamp": "1970-01-01T25:00:00Z"}
```
or
```json
{"optionalTimestamp": "2001-02-29T00:00:00Z"}
```
is expected to fail parsing per the conformance suite's `TimestampJsonInputHourTooLarge` / `TimestampJsonInputNonLeapFeb29` test cases [7](#0-6) , but is documented to be accepted without error by the affected backends per `conformance/failure_list_ruby.txt`, `conformance/failure_list_python_upb.txt`, and `conformance/failure_list_cpp.txt` cited above — confirming the invariant bypass is real and currently unaddressed in this checkout.

  return (int64_t)jsondec_epochdays(y, m, d) * 86400 + h * 3600 + min * 60 + s;
}

static void jsondec_timestamp(jsondec* d, upb_Message* msg,
                              const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  upb_MessageValue seconds;
  upb_MessageValue nanos;
  upb_StringView str = jsondec_string(d);
  const char* ptr = str.data;
  const char* end = ptr + str.size;

  if (str.size < 20) goto malformed;

  {
    /* 1972-01-01T01:00:00 */
    int year = jsondec_tsdigits(d, &ptr, 4, "-");
    int mon = jsondec_tsdigits(d, &ptr, 2, "-");
    int day = jsondec_tsdigits(d, &ptr, 2, "T");
    int hour = jsondec_tsdigits(d, &ptr, 2, ":");
    int min = jsondec_tsdigits(d, &ptr, 2, ":");
    int sec = jsondec_tsdigits(d, &ptr, 2, NULL);

    seconds.int64_val = jsondec_unixtime(year, mon, day, hour, min, sec);
  }

  nanos.int32_val = jsondec_nanos(d, &ptr, end);

  {
    /* [+-]08:00 or Z */
    int ofs_hour = 0;
    int ofs_min = 0;
    bool neg = false;

    if (ptr == end) goto malformed;

    switch (*ptr++) {
      case '-':
        neg = true;
        /* fallthrough */
      case '+':
        if ((end - ptr) != 5) goto malformed;
        ofs_hour = jsondec_tsdigits(d, &ptr, 2, ":");
        ofs_min = jsondec_tsdigits(d, &ptr, 2, NULL);
        ofs_min = ((ofs_hour * 60) + ofs_min) * 60;
        seconds.int64_val += (neg ? ofs_min : -ofs_min);
        break;
      case 'Z':
        if (ptr != end) goto malformed;
        break;
      default:
        goto malformed;
    }
  }

  if (seconds.int64_val < -62135596800) {
    jsondec_err(d, "Timestamp out of range");
  }

  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 1),
                                   seconds, d->arena));
  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 2),
                                   nanos, d->arena));
  return;

malformed:
  jsondec_err(d, "Malformed timestamp");
}

message Timestamp {

  // be between -62135596800 and 253402300799 inclusive (which corresponds to

  // the nanosecond portion of the duration, not an alternative to seconds.
  // Negative second values with fractions must still have non-negative nanos
