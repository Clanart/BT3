### Title
Unbounded chunk-row amplification via unauthenticated `send_citrea_tx` with `chunk_size=1` drains tx-sender wallet and locks bridge UTXOs — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`, `crates/clementine-tx-sender/src/client.rs`)

### Summary
The `send_citrea_tx` JSON-RPC endpoint accepts a `CitreaTxRequest::BatchProof` with a caller-controlled `chunk_size`. The validation clamps `chunk_size` from above (to `MAX_CHUNK_SIZE = 390_000`) and resets `0` to `MAX_CHUNK_SIZE`, but any value in `1..MAX_CHUNK_SIZE` is accepted without a lower-bound check. With `chunk_size=1` and a large `bytes` payload (up to the 50 MB server limit), the handler inserts O(bytes.len()) rows into `tx_sender_citrea_raw_tx_queue`, each of which the tx-sender background loop will attempt to commit-reveal on Bitcoin, consuming wallet funds for every row.

### Finding Description
In `TxSenderClient::send_citrea_tx` (`crates/clementine-tx-sender/src/client.rs`):

```rust
let mut chunk_size = chunk_size.unwrap_or(MAX_CHUNK_SIZE);
if chunk_size == 0 {
    chunk_size = MAX_CHUNK_SIZE;
}
if chunk_size > MAX_CHUNK_SIZE {
    chunk_size = MAX_CHUNK_SIZE;
}
// chunk_size = 1 passes all checks above
let chunk_size = chunk_size as usize;

if bytes.len() <= chunk_size {
    // single row
} else {
    let chunks: Vec<Vec<u8>> = bytes.chunks(chunk_size)  // O(bytes.len()) chunks
        .map(|chunk| borsh::to_vec(&DataOnDa::Chunk(chunk.to_vec()))...)
        .collect();
    self.db.insert_citrea_raw_tx_chunks(&mut dbtx, &chunks, &full_body_hash).await?
    // inserts N chunk rows + 1 aggregate row
}
```

The JSON-RPC server exposes this method with no authentication (`ServerBuilder::default()`, no middleware) and a 50 MB request body limit. An attacker submitting `{ bytes: [0u8; 50_000_000], chunk_size: Some(1) }` creates 50 million DB rows. Each non-aggregate row with a `body` is picked up by the tx-sender background loop, which constructs and broadcasts a Bitcoin commit-reveal transaction pair for it, spending wallet funds.

The `UNIQUE (body_hash)` deduplication guard only covers the aggregate row (which stores `SHA256(full_bytes)`). Chunk rows have `body_hash = NULL` and are not deduplicated. Repeated calls with different `bytes` payloads bypass even the aggregate-level guard.

### Impact Explanation
- **Wallet drain**: Each of the O(bytes.len()) chunk rows triggers a Bitcoin commit-reveal transaction pair. At 50 MB / 1 byte per chunk, this is ~50 million Bitcoin transactions, exhausting the tx-sender's wallet.
- **Bridge UTXO lock**: Once the wallet is drained, the tx-sender cannot pay fees for legitimate bridge transactions (kickoff, payout, reimbursement, collateral), permanently locking bridge-controlled UTXOs.
- **No recovery path**: The queue rows persist in the DB; the background loop will keep retrying until funds are gone.

### Likelihood Explanation
The default bind is `127.0.0.1`, which requires local access. However, the code contains no authentication mechanism whatsoever. In containerized deployments (same pod, shared network namespace, or a widened bind address), any process can reach the endpoint. The attack requires only a single HTTP POST with a crafted JSON body — no keys, no credentials, no privileged role.

### Recommendation
1. **Enforce a minimum `chunk_size`**: Add `if chunk_size < MIN_CHUNK_SIZE { return Err(...) }` (e.g., `MIN_CHUNK_SIZE = 1024` or enforce `chunk_size >= bytes.len() / MAX_CHUNKS`).
2. **Add authentication to the JSON-RPC server**: Require a shared secret, mTLS, or restrict callers to a known allowlist at the code level, not just via deployment convention.
3. **Cap the total number of chunks per request**: Reject requests where `bytes.len() / chunk_size > MAX_CHUNKS` (e.g., `MAX_CHUNKS = 1000`).
4. **Rate-limit the `send_citrea_tx` endpoint** at the server layer.
