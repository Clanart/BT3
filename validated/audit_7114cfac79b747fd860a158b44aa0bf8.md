### Title
Attacker-controlled `WWW-Authenticate` realm header spoofs GitHub identity and triggers a real Sign-in-to-GitHub prompt against an arbitrary git host - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
`getEndpointKind()` in the git credential-helper trampoline treats a bare `realm="GitHub"` substring inside an attacker-controllable `WWW-Authenticate` header as sufficient proof that an arbitrary git remote is a genuine "enterprise" GitHub host, with no verification of hostname, TLS identity, or an actual API round-trip. This is structurally the same bug class as the Nethermind report: a narrow, context-specific signal (there, a V-value; here, a header substring) is accepted as universally valid trust evidence without the additional checks that should gate it, letting an attacker who fully controls a response (fetch/clone/push target or a MITM/proxy sitting in front of it) force Desktop into GitHub-authentication UX for a non-GitHub host.

### Finding Description
`getEndpointKind()` classifies a credential-helper request's target host in order to decide whether to treat it as `'generic'` (plain git host credentials) or as a GitHub identity (`'github.com'`/`'ghe.com'`/`'enterprise'`): [1](#0-0) 

The hostname-based checks (`isGist`, `isDotCom`, `isGHE`) are legitimate allow-list checks against fixed domains, defined in: [2](#0-1) 

But when none of those match, the function falls back to trusting a value copied straight from the server's HTTP response: [3](#0-2) 

`cred` originates from the git credential-fill protocol, whose `wwwauth[N]` entries are populated verbatim by git from any `WWW-Authenticate` response header the remote server (or a proxy/MITM in the network path) sends back on an authentication challenge. There is no check that the header actually came from `github.com`/`*.ghe.com`, no TLS/cert pinning, and no live API call to confirm the claim — the string match `realm="GitHub"` alone is enough to flip the classification to `'enterprise'`, exactly analogous to how `signature.V is 27 or 28` alone was enough to flip Nethermind's validator to `return true` regardless of transaction type.

Once `getEndpointKind` returns `'enterprise'` for an attacker's host, `getCredential()` — because there is no existing stored account for that host — calls `ui.promptForGitHubSignIn(endpoint)`: [4](#0-3) 

which opens the real GitHub-Desktop "Sign in" popover, wiring it directly to the attacker's `origin` as if it were a genuine GitHub Enterprise Server: [5](#0-4) 

`beginEnterpriseSignIn`/`setSignInEndpoint` will subsequently drive OAuth/basic-auth flows against that attacker-chosen `origin`.

### Impact Explanation
An attacker who controls (or can respond as) a git remote — e.g. a self-hosted git server, a compromised/malicious proxy in the push/fetch path, or a MITM on a plain-`http`/misconfigured `https` connection — can send a 401 response with `WWW-Authenticate: Basic realm="GitHub"` during any git operation (clone, fetch, push) that Desktop performs through the trampoline credential helper. This causes Desktop to present a "Sign in to GitHub" dialog bound to the attacker's host. A user who completes that sign-in (enters PAT/basic-auth credentials, or is redirected through OAuth to the attacker's domain) will have their credentials sent to, or an OAuth exchange brokered by, the attacker's server — i.e., unauthorized GitHub credential/token phishing driven entirely by unprivileged, attacker-controlled server responses that Desktop's own UI vouches for as "GitHub." This falls squarely in the reported valid-impact category: "attacker controls … a git remote/proxy response, and the result is … credential/token exfiltration [or] unauthorized OAuth."

### Likelihood Explanation
Reaching this code only requires the victim to add/use a remote pointing at attacker infrastructure (or be MITM'd on an insecure connection) and perform any git network operation; git's own credential protocol automatically forwards `WWW-Authenticate` headers into `wwwauth[N]` entries with no Desktop-side filtering, so the attacker payload is trivial to produce (a single HTTP header). The remaining requirement is a plausible one — the user must click through the resulting sign-in prompt — but this is materially different from the "social engineering" the scope excludes, since the trigger is a legitimate-looking, Desktop-generated "Sign in to GitHub" system dialog rather than a phishing message crafted by the attacker.

### Recommendation
Do not derive trust from response headers alone. Either:
- Require a successful authenticated API call (e.g. `/meta` or a version probe) against the endpoint before classifying it as `'enterprise'`, instead of trusting `wwwauth[N]` header content, or
- At minimum, corroborate the `realm="GitHub"` header with an independent signal (valid TLS certificate for a known-Enterprise-style pattern, or a follow-up `x-github-enterprise-version` check as already done elsewhere in `tryUpdateEndpointVersionFromResponse`) before invoking `promptForGitHubSignIn`, and clearly surface the actual host in the sign-in UI so users are not misled into thinking they're authenticating to a vetted GitHub instance.

### Proof of Concept
1. Stand up a plain HTTP(S) git server (e.g. via `git http-backend`) on `https://evil.example.com/victim/repo.git`.
2. Configure it to respond to unauthenticated smart-HTTP requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. In GitHub Desktop, clone or add `https://evil.example.com/victim/repo.git` as a remote and trigger a fetch/push.
4. Git invokes Desktop's credential-helper trampoline; `getEndpointKind` sees no `isDotCom`/`isGHE` match, then finds the `wwwauth[...]` entry containing `realm="GitHub"` and returns `'enterprise'`.
5. Since no stored account exists for `evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com')`, and Desktop shows a "Sign in to GitHub Enterprise" dialog bound to `evil.example.com`.
6. Any credentials/OAuth flow the user completes there is directed at the attacker's server.

Note: I could not find any additional server-authenticity check (e.g., certificate pinning or an authenticated API probe) gating this specific fallback path elsewhere in the codebase — the mitigations that do exist (`isDotCom`, `isGHE`, `findGitHubTrampolineAccount`) are all bypassed for a first-contact attacker host, which is the exact scenario this PoC exercises.

```typescript
const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
```

```typescript
export const isDotCom = (ep: string) => {
  if (ep === getDotComAPIEndpoint()) {
    return true
  }

  const { hostname } = new URL(ep)
  return hostname === 'api.github.com' || hostname === 'github.com'
}

export const isGist = (ep: string) => {
  const { hostname } = new URL(ep)
  return hostname === 'gist.github.com' || hostname === 'gist.ghe.io'
}

/** Whether or not the given endpoint URI is under the ghe.com domain */
export const isGHE = (ep: string) => new URL(ep).hostname.endsWith('.ghe.com')
```

```typescript
  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
```
