## Title
Recursive clone explicitly disables Git's clone protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-opening symlink/hook-planting attacks in malicious repositories - (`File: app/src/lib/git/clone.ts`)

### Summary
GitHub Desktop's `clone()` function performs `git clone --recursive` against an attacker-supplied URL and explicitly forces the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` for the entire operation, unconditionally, for every clone. `GIT_CLONE_PROTECTION_ACTIVE` is the internal switch Git itself uses to guard the working-tree/`.git`-directory collision checks that were hardened after the class of clone-time arbitrary-hook-execution vulnerabilities (crafted submodules/paths that collide with `.git` on case-insensitive or symlink-following filesystems, letting an attacker plant executable hooks that fire automatically during a recursive clone/submodule checkout). By forcing this flag to `'false'`, Desktop is deliberately turning that protection off for a `--recursive` clone driven entirely by attacker-controlled remote content (URL + repository/submodule tree), which is exactly the trust boundary the guard exists to protect.

### Finding Description
The corrupted value is the `GIT_CLONE_PROTECTION_ACTIVE` environment variable passed to the underlying `git` invocation: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

Unlike other operations in the same codebase that recognize the trust risk of hook execution and route it through Desktop's own sandboxing/interception layer (`interceptHooks` + the hooks proxy in `app/src/lib/hooks/with-hooks-env.ts` and `app/src/lib/hooks/hooks-proxy.ts`), `clone()` neither sets `interceptHooks` nor otherwise mediates hook execution — it just disables the git-side collision/hook-planting protection outright and runs a fully recursive clone (which also recursively initializes and checks out any submodules) straight from the network.

This mirrors the report's broken invariant: in the CNumaToken case, the protocol assumed a "trusted" collateral token but let an attacker substitute one, defeating the reentrancy guard; here, Desktop assumes clone targets are "safe enough" and pre-emptively strips out Git's own defense-in-depth guard before ever inspecting the remote content, even though `--recursive` immediately walks into submodules and hooks whose paths and content are fully attacker-controlled.

### Impact Explanation
If Git's clone protection exists specifically to stop maliciously-crafted repository trees (e.g., submodules whose worktree/gitdir paths collide with `.git`, or symlinked `.git` contents) from causing hooks to be written into a location where they get executed during checkout, then forcing `GIT_CLONE_PROTECTION_ACTIVE=false` removes that backstop for every single clone Desktop performs. Combined with `--recursive` (which auto-initializes and checks out every submodule without prompting the user), a crafted repository could plant an executable hook (e.g., `post-checkout`) that runs automatically as part of the clone with no interception, no confirmation dialog, and no path validation from Desktop's own hook-proxy machinery — resulting in arbitrary code execution on the victim's machine purely from cloning a URL/repository the attacker controls.

### Likelihood Explanation
The attack surface matches the "Valid Impact" criteria precisely: the attacker only needs to control the cloned repository (including its submodules/hooks) — no local access, no prior compromise, no social engineering beyond getting the victim to clone the repo (a completely ordinary, expected Desktop action). Desktop calls `clone()` for every repository cloned through the UI, so the disabled protection is unconditionally active on the primary "clone from URL" code path.

### Recommendation
Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` and let Git's built-in clone protections run. If there is a legitimate compatibility reason to disable it (e.g. a specific Git version incompatibility), gate it narrowly and route the recursive submodule/hook handling through the same `interceptHooks` sandbox already used for `pull`, `push`, `merge`, and `commit` (see `app/src/lib/hooks/with-hooks-env.ts`) so that any hooks discovered during clone are proxied and subject to the same user-visible controls rather than executing directly.

### Proof of Concept
1. Attacker crafts a public repository containing a submodule whose configured path/worktree is engineered to collide with the top-level `.git` directory (case-insensitive filename tricks / symlink tricks), with a payload hook (e.g. `post-checkout`) staged to be written into that colliding path.
2. Victim clones the attacker's repository URL via Desktop's "Clone repository" UI, which calls `clone()` in `app/src/lib/git/clone.ts:68-126` with `--recursive` and `GIT_CLONE_PROTECTION_ACTIVE: 'false'`.
3. Because Git's own clone-time collision/protection check is disabled by this environment variable, and Desktop does not intercept hooks for the `clone` operation (no `interceptHooks` passed to `opts`), the planted hook is written to the real hooks directory and executed automatically as part of the recursive checkout — achieving code execution on the victim's machine with no additional user action beyond the normal "Clone" click.
```typescript
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
```
