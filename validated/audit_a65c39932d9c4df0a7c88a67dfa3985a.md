## Analysis

The Sherlock bug is a broken-invariant class: several sibling functions perform the same class of operation (removing/moving a resource across a security boundary), but only *some* of them apply the safety check that keeps state consistent — the missing check on one sibling silently lets corrupted state leak into what happens afterward.

The GitHub Desktop codebase has an internal, established pattern for exactly this kind of check: `resolveWithin()` in `app/src/lib/path.ts`, which resolves a repository-relative path and verifies (via `realpath`) that it does **not** escape the repository root, explicitly guarding against symlink-based traversal (`app/src/lib/path.ts:36-72`, tested in `app/test/unit/path-test.ts:65-100`). This guard is correctly applied to file paths coming from git data by `buildConflictContext()` in `app/src/lib/copilot-conflict-context.ts:390-407` and to the deep-link `filepath` handler in `dispatcher.ts:1957-1972`.

However, `revealInFileManager()` — the sibling function that also turns a repository-relative, git-derived path into a filesystem path for a shell action — does **not** apply this check: [1](#0-0) 

This function is called throughout the UI with `file.path` values taken directly from `git status`/diff parsing (attacker-influenced tree/working-directory content), e.g.: [2](#0-1) [3](#0-2) 

### Title
Missing path-containment check in `revealInFileManager`/`openFile` lets a malicious repo symlink escape the repo root via git-status paths - (File: `app/src/lib/app-shell.ts`)

### Summary
`resolveWithin()` is the codebase's sanctioned invariant check for turning an untrusted, repository-relative path into a safe absolute path before it is handed to a shell/file operation. It is applied for conflict-context file reads and for the `x-github-client://openrepo` deep-link `filepath` parameter, but the analogous "reveal in file manager" / "open with default program" code paths join the path with `Path.join()` only, with no `resolveWithin()`/`realpath` containment check.

### Finding Description
`revealInFileManager()` builds the target path with a plain `Path.join(repository.path, path)` and passes it straight to `shell.showItemInFolder()`: [1](#0-0) 

The `path` argument originates from `WorkingDirectoryFileChange.path`/`CommittedFileChange.path`, which are populated from `git status --porcelain=2 -z` output parsed by `parsePorcelainStatus()` in `app/src/lib/status-parser.ts:105-182`, and from diff/log output. These values are not restricted to safe, traversal-free relative paths at the type level — the only real protection against escaping the repository root, when a working-tree symlink is involved, is `resolveWithin()`'s `realpath`-based comparison (`app/src/lib/path.ts:36-72`), which is deliberately *not* invoked here.

Sibling code that handles the same class of git-derived, repository-relative path treats this as a real security boundary and calls `resolveWithin`:
- `buildConflictContext()` explicitly comments "Guard against path traversal and symlink escapes (cross-platform)" before calling `resolveWithin` (`app/src/lib/copilot-conflict-context.ts:390-407`).
- `openRepositoryFromUrl()` rejects absolute `filepath` values and calls `resolveWithin(repository.path, filepath)` before calling `shell.showItemInFolder` (`app/src/ui/dispatcher/dispatcher.ts:1957-1972`).

`revealInFileManager` and `openFile`/`onOpenItem` (`app/src/ui/lib/open-file.ts:4-17`, `app/src/ui/changes/sidebar.tsx:282-285`, `app/src/ui/changes/filter-changes-list.tsx:602-655`, `app/src/ui/history/selected-commits.tsx:371-425`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx:154-211`) do the exact same class of operation on the exact same class of untrusted input, but omit that check — this is the "sibling function has the guard, this one doesn't" pattern from the seed report.

**Attacker primitive**: a cloned/fetched repository can contain a symlink (a legitimate git object type) pointing outside the repository (e.g. `evil -> /` or `evil -> C:\`). Once checked out, any subsequently created/tracked path underneath that symlink (e.g. `evil/Documents/secrets.txt`) is reported by `git status` with a path string like `evil/Documents/secrets.txt`. `Path.join(repository.path, path)` faithfully reconstructs that string, and the OS resolves the symlink component at open time — landing outside the repository root. `resolveWithin`'s own symlink test (`app/test/unit/path-test.ts:65-78`) demonstrates this exact traversal is possible and is the reason the function exists.

### Impact Explanation
- `revealInFileManager` reveals an arbitrary filesystem path chosen by the crafted symlink in the OS file manager — an unprivileged repository/PR/commit can point Desktop's UI at files outside the repo (e.g. the user's home directory or SSH/config files), disclosing their existence/location and enabling the user to be misled about what they are viewing/committing.
- The more severe sibling, `openFile()` (`app/src/ui/lib/open-file.ts:4-17`), calls `shell.openExternal('file://' + fullPath)`, i.e. asks the OS to open the resolved path with its default handler. If the symlink-escaped path resolves to an attacker-plantable or attacker-known file outside the repo (e.g. a downloaded document, `.desktop`/`.lnk`/`.url` file, or another OS-handler-exploitable file type), this becomes a path-controlled "open arbitrary file with the OS default handler" primitive outside the intended repo sandbox — this is invoked from `onOpenItem` handlers throughout the Changes/History/PR UI (`app/src/ui/changes/sidebar.tsx:282-285`, `app/src/ui/changes/filter-changes-list.tsx:648-655`).

### Likelihood Explanation
Requires no local access, admin rights, or prior compromise: an attacker only needs to get the victim to clone/fetch/checkout a repository (or open a PR/commit) containing a symlink, and then interact with the "Reveal in Finder/Explorer" or "Open with default program" context menu action on a file whose reported path traverses through that symlink — an ordinary, expected user interaction with Desktop's own UI, not an "unnatural" step. Git fully supports storing symlinks as tree entries, and Desktop already treats this exact scenario as attacker-reachable elsewhere (the `resolveWithin` symlink-escape test and its use in `copilot-conflict-context.ts` and the deep-link handler).

### Recommendation
Route `revealInFileManager()` (and the `onOpenItem`/`openFile` call chain) through `resolveWithin(repository.path, path)` the same way `buildConflictContext` and `openRepositoryFromUrl` do, refusing to reveal/open the item (and logging, as the deep-link handler does) when the resolved real path does not stay under the repository root.

### Proof of Concept
1. On a non-Windows platform, create a git repository containing a symlink entry `evil -> /` (git supports storing symlinks; e.g. `ln -s / evil && git add evil && git commit`).
2. Have the victim clone this repository in Desktop and check it out.
3. Have the victim (or an automated helper file) create/modify a file that appears under the symlink in the working tree, e.g. `evil/Users/victim/.ssh/id_rsa` becomes visible as a tracked/untracked path `evil/Users/victim/.ssh/id_rsa` in `git status`.
4. In Desktop's Changes list, right-click that file and choose "Reveal in Finder/Explorer" (`revealInFileManager`, `app/src/lib/app-shell.ts:61-64`) or "Open with default program" (`openFile`, `app/src/ui/lib/open-file.ts:4-17`).
5. Because `Path.join(repository.path, path)` is used with no `resolveWithin` containment check, the OS resolves the symlink and reveals/opens the real filesystem path `/Users/victim/.ssh/id_rsa`, outside the cloned repository — reproducing the exact traversal that `resolveWithin`'s own test suite (`app/test/unit/path-test.ts:65-78`) demonstrates is otherwise blocked when the guard is used.

/**
 * Reveals a file from a repository in the native file manager.
 *
 * @param repository The currently active repository instance
 * @param path The path of the file relative to the root of the repository
 */
export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
