### Title
Missing upper-bound check on oracle timestamps lets a future-dated price corrupt the monotonic `last-update` tracker and permanently freeze price resolution - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` is the staleness/freshness gate used by every price resolution call in `v0-4-market.clar`. It caps how *old* a price timestamp may be, but it has no upper bound on how far in the *future* a timestamp may be. Any timestamp greater than `stacks-block-time` is treated as automatically "fresh" (delta forced to `u0`), and it is then written into the monotonic `last-update` map. Once a future timestamp is recorded, every subsequent legitimate update — whose real timestamp is necessarily smaller — fails the monotonic check `(>= ts prev)` and reverts, permanently blocking all price resolution (and therefore borrow/withdraw/liquidate/health-check logic) for that asset until real chain time catches up to the erroneous future value.

### Finding Description
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
``` [1](#0-0) 

When `ts > stacks-block-time`, `delta` is forced to `u0`, so the `(<= delta max-staleness)` check always passes regardless of how far in the future `ts` is. This function is invoked from `price-resolve`:
```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let (...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
``` [2](#0-1) 

If a price update with a `publish-time` far in the future is ever accepted (e.g. clock skew from the Pyth/DIA feed relative to `stacks-block-time`, or a malformed/adversarial feed value that still satisfies upstream oracle checks), this future timestamp:
1. Passes `oracle-timestamp-fresh` unconditionally (`delta = u0`).
2. Gets persisted into `last-update` because `timestamp > last-update-time`.

From that point forward, every subsequent (correct) price update has `ts < prev` (since `prev` is now an inflated future value), so `(>= ts prev)` fails and `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for that feed key — indefinitely, until the chain's `stacks-block-time` naturally advances past the erroneous future value. There is no admin function found in `v0-4-market.clar` to reset or override the `last-update` map entry, so recovery depends purely on waiting out the bogus future timestamp.

This is structurally the same class of bug as the referenced report: the code fails to bound a time-related input from above, and that missing bound permanently locks a resource (there: staked tokens in a stream; here: the price feed and everything gated by it) rather than merely producing a temporary/expected condition.

### Impact Explanation
Once triggered, `price-resolve` for the affected asset reverts on every call. Since `price-resolve`/`price-multi-resolve` back all health-factor, borrow, withdraw, and liquidation checks in the market, this results in the affected asset (and any position depending on its price) being unusable — deposits/collateral become inaccessible for borrowing/withdrawal and cannot be liquidated even if undercollateralized, until the bogus far-future timestamp is naturally surpassed by chain time. This is a temporary (bounded by how far in the future the timestamp was set, potentially very long) freezing of user funds tied to that asset, matching the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
Likelihood depends on how the upstream oracle-writing path (`pyth-storage-v4`) bounds `publish-time`. It enforces a lower bound (staleness threshold) and monotonicity per price identifier, but does **not** enforce that `publish-time` cannot exceed current chain time by an arbitrary amount:
```clarity
(asserts! (>= publish-time (+ (- latest-stacks-timestamp stale-price-threshold) STACKS_BLOCK_TIME)) ERR_STALE_PRICE)
``` [3](#0-2) 
There is no corresponding upper-bound check anywhere in that pipeline, so a feed value with a timestamp ahead of `stacks-block-time` (whether from legitimate clock skew or a malformed but properly-signed VAA) can reach `market.clar`'s `oracle-timestamp-fresh` and trigger the freeze. The root cause of the DoS itself, however, is `oracle-timestamp-fresh`'s own missing upper bound in `market.clar` — the code that is supposed to gate staleness silently disables the check for any future timestamp.

### Recommendation
Add an explicit upper bound in `oracle-timestamp-fresh` (and/or at the oracle-write layer) rejecting any timestamp that is more than a small, configurable tolerance ahead of `stacks-block-time`, instead of forcing `delta` to `u0` for future timestamps:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   (- ts stacks-block-time)   ;; measure the "future" drift too
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```
Additionally, consider providing a governance/admin function to reset a corrupted `last-update` entry for a given feed key so the protocol is not permanently reliant on waiting out an erroneous timestamp.

### Proof of Concept
1. Upstream oracle write path accepts a price update for asset `X` with `publish-time = stacks-block-time + N` (N large), because `pyth-storage-v4.write-batch-entry` only checks a lower staleness bound and monotonicity, not an upper future bound [3](#0-2) .
2. `market.clar`'s `price-resolve` calls `oracle-timestamp-fresh(timestamp=stacks-block-time+N, prev=old_ts, max-staleness)`; since `ts > stacks-block-time`, `delta` is forced to `u0`, the check passes, and `last-update` is set to `stacks-block-time + N` [4](#0-3) .
3. Any later legitimate price update for asset `X` has `ts (real, ≈ current time) < prev (stacks-block-time+N)`, so `(>= ts prev)` is `false`, `oracle-timestamp-fresh` returns `false`, and `price-resolve` reverts with `ERR-ORACLE-INVARIANT`.
4. All market operations that need `X`'s price (borrow against it, withdraw it as collateral, liquidate positions using it) revert until `stacks-block-time` naturally exceeds `stacks-block-time + N`, freezing user funds tied to asset `X` for that entire duration.
