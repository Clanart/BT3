### Title
Tron `IntentGatewayV2.placeOrder` credits escrow with the declared amount instead of the actual token balance received, letting fee-on-transfer/deflationary input tokens create a shortfall that lets one order's withdrawal consume another order's escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
On the Tron variant of `IntentGatewayV2`, `placeOrder`'s non-predispatch escrow path calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits `_orders[commitment][token] += reducedInputs[i].amount`, using the *declared* transfer amount rather than measuring the contract's actual balance delta. [1](#0-0)  The mainline EVM `IntentGatewayV2.sol` avoids exactly this class of bug by measuring `balanceOf(address(this))` before/after the transfer and crediting only the actually-received amount. [2](#0-1)  The Tron contract lacks this check, so the internal escrow ledger (`_orders[commitment][token]`) can diverge from the pool of tokens actually held by the contract — the same broken invariant as the Lido report (accounting believes it holds more than it actually does).

### Finding Description
`_orders[commitment][token]` is a per-order bookkeeping entry, but the actual ERC-20 balance backing all orders' escrow is a single shared pool inside the contract. `withdraw()` never checks the contract's real token balance before paying out — it only checks `_orders[body.commitment][token] != 0` and then unconditionally attempts `token.call(transfer, beneficiary, amount)`, decrementing the ledger afterward. [3](#0-2) 

If any input token used across orders is fee-on-transfer, rebasing, or otherwise delivers less than `amount` on `transferFrom` (a very common ERC-20 pattern on Tron/TRC-20 forks of standard tokens), the ledger is over-credited relative to what the contract actually received. Every order placed with such a token inflates the *booked* escrow beyond the *real* token balance. Because withdrawals for any order draw from the shared token balance rather than a segregated per-order balance, this shortfall means later legitimate withdrawals (for that token, potentially across unrelated orders/users) can fail or — combined with the fact that `withdraw()`'s `TransferFailed()`/`InsufficientNativeToken()` guards only catch failed calls, not partial insufficiency — silently pay out of a pool that was funded in part by other users' escrow, effectively letting one inflated/faulty accounting entry consume real tokens that back a different commitment.

This mirrors the cited Lido issue precisely: the contract's internal accounting (`_readyToClaim` / `_orders[commitment][token]`) can exceed the actual token balance held by the contract, and there is no guard ensuring sufficient balance exists before a transfer is attempted or allowed to succeed against the wrong backing funds.

### Impact Explanation
This is a fund-safety issue in the bridge's escrow custody logic (`IntentGatewayV2`/intents settlement path). A ledger/balance mismatch on a shared escrow pool means:
- Legitimate users can be unable to withdraw their rightful escrow (fund lock) once the pool is drained below the sum of outstanding ledger entries.
- Because `_orders` per-order entries are logically independent claims on one shared token balance, whichever order withdraws first drains real tokens that other orders' ledger says they are entitled to, i.e. wrong-beneficiary/wrong-amount fund flow once the pool runs dry — a direct violation of "bridged assets ... must move exactly once and only to the rightful beneficiary and amount."

### Likelihood Explanation
Triggering this requires only placing an order (an unprivileged, public entrypoint) using an ERC-20/TRC-20 input token that charges a fee-on-transfer or otherwise delivers less than the nominal `amount` — no relayer, prover, or admin compromise is needed. The intent-gateway design explicitly supports arbitrary registered tokens as inputs, and the mainline EVM contract was already hardened against this exact scenario (balance-delta accounting), indicating the underlying risk is known and real, but the fix was not carried over to the Tron contract.

### Recommendation
Mirror the mainline EVM contract's fix in the Tron `IntentGatewayV2.placeOrder`: measure `balanceOf(address(this))` immediately before and after each `safeTransferFrom`, and credit `_orders[commitment][token]` with the actual delta received rather than the caller-declared `order.inputs[i].amount`. Additionally, consider adding a balance-sufficiency check inside `withdraw()` (i.e., verify `IERC20(token).balanceOf(address(this)) >= amount` prior to transfer) so any residual accounting drift fails safely instead of silently consuming another order's backing funds.

### Proof of Concept
1. Governance/owner deploys or a user places an order with `token` = a TRC-20 that takes, e.g., a 2% transfer fee (delivers 98% of `amount` to the recipient).
2. Attacker calls `placeOrder` with `order.inputs[0] = {token, amount: 1_000_000}`. `safeTransferFrom` moves only 980_000 units into the gateway, but `_orders[commitment][token] += reducedInputs[i].amount` credits the full (fee-adjusted-for-protocol-fee, but not for transfer-fee) `amount`, e.g. 1_000_000 (assuming zero protocol fee) — a 20,000-unit deficit versus real balance is now baked into the ledger. [4](#0-3) 
3. A second, unrelated user places a normal order with the same `token`, correctly delivering the full amount, growing the shared pool.
4. When the first (deficit) order is cancelled/filled and `withdraw()` runs, it pays out the full booked `1_000_000` from the shared pool — this either reverts (if pool is short) causing a temporary/lasting fund lock for the second user, or succeeds by consuming part of the second user's real escrowed balance, so the second user's later withdrawal fails or returns less than owed, since the pool is now short of what their own `_orders` entry claims.
5. This is exactly the "contract has less than the recorded claimable amount" condition described in the reference Lido report, transplanted onto Hyperbridge's cross-chain intent escrow.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
