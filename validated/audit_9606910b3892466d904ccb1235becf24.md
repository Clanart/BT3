### Title
Sybil self-referral via two attacker-controlled EOAs allows extraction of extra MGP referral yield with no genuine referee - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage.useCode()` only blocks a user from referring themselves with the exact same address (`Circled()` check on `codeOwners[_code] == msg.sender`), but does nothing to prevent one attacker who controls two EOAs from having EOA2 use a code registered by EOA1. Because `MasterMagpie._multiClaim()` calls `IReferralStorage.trigger()` for every claim, any staking/harvest activity by EOA2 automatically mints extra `refererAmount` credited to EOA1's `rewardAmount`, funded from ReferralStorage's own MGP balance rather than from any independent third party.

### Finding Description
- `useCode()` (rewards/ReferralStorage.sol:134-145) sets `myReferer[msg.sender] = codeOwners[_code]` and only rejects the case `codeOwners[_code] == msg.sender`. It has no check preventing `msg.sender` and `codeOwners[_code]` from being two different addresses controlled by the same entity. [1](#0-0) 
- Once EOA2 stakes/claims MGP through `MasterMagpie`, `_multiClaim()` computes `totalReward` and unconditionally calls `IReferralStorage(referral).trigger(_user, totalReward)`. [2](#0-1) 
- `trigger()` looks up `myReferer[_referee]` (EOA1), computes `refererAmount`/`refereeAmount` as percentages of `_amount` based on the referer's tier and boosted factor, and adds `refererAmount` to `refererInfo.rewardAmount` (EOA1) and `refereeAmount` to `refereeInfo.rewardAmount` (EOA2) — both amounts additive on top of the MGP the referee already received directly from `MasterMagpie`. [3](#0-2) 
- EOA1 later calls `claimReward()` to pull `rewardAmount` in MGP from the contract's balance. [4](#0-3) 

Since there is no identity/KYC linkage or anti-Sybil mechanism beyond the trivial same-address check, and no requirement that the referee be economically independent from the referrer, an attacker with two wallets earns `refererAmount` extra MGP for every harvest of EOA2, purely by routing self-owned stake volume through a code they registered on EOA1. This bypasses the evident intent of the `Circled()` check (self-referral prevention), which only catches the degenerate single-address case.

### Impact Explanation
Every harvest by the Sybil wallet (EOA2) mints extra MGP `rewardAmount` for the attacker's other wallet (EOA1), paid out of ReferralStorage's held MGP balance. This is uncompensated protocol-funded yield extracted with no genuine independent referee, diluting the pool of MGP set aside for referral rewards / diverting protocol-funded yield to the attacker — matching the "theft of unclaimed yield" impact class. The loss scales with however much stake/volume the attacker routes through MasterMagpie and is entirely repeatable.

### Likelihood Explanation
Trivial and cheap to execute: attacker needs only two EOAs (no privileged role), some MGP to stake in each wallet, and standard calls (`registerCode`, `useCode`, `deposit`, `multiclaim`). No flash loans, no timing tricks, no reentrancy needed — fully repeatable on every harvest cycle for as long as the attacker keeps staking through EOA2.

### Recommendation
Add Sybil-resistance to the referral linkage, e.g.:
- Require a minimum time delay / cooldown between wallet creation (stake history) and code usage, or
- Cap total referral reward accrual per referrer relative to independently-verifiable metrics, or
- Restrict `trigger()`-driven rewards to referees whose staked capital did not originate from the same referrer address (e.g., disallow if referer and referee share funding provenance), or at minimum
- Introduce a governance-configurable per-referrer reward cap and monitoring/flagging of self-dealing patterns, since fully eliminating Sybil self-referral in an on-chain permissionless system is not possible without off-chain identity, but bounding exposure limits the drain on protocol-held MGP.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `ReferralStorage`, `MGP` token, and a staking pool; fund `ReferralStorage` with MGP (as would occur in production via admin funding) and set a tier with `rewardPercentage` via `setTier`/`setReferrerTier`.
2. `vm.prank(EOA1)`; `referralStorage.registerCode("CODE1")`.
3. `vm.prank(EOA2)`; `referralStorage.useCode("CODE1")` — succeeds since `codeOwners["CODE1"] == EOA1 != EOA2`.
4. `vm.prank(EOA2)`; `masterMagpie.deposit(stakingToken, amount)` then advance time and call `masterMagpie.multiclaim([stakingToken])` — this triggers `_multiClaim` -> `IReferralStorage.trigger(EOA2, totalReward)`.
5. Assert `referralStorage.userInfos(EOA1).rewardAmount > 0` even though EOA1 never staked or was harvested directly.
6. `vm.prank(EOA1)`; `referralStorage.claimReward()`; assert MGP balance of EOA1 increased by `rewardAmount`.
7. Compare against a baseline scenario where EOA2 stakes without using any referral code — total attacker-controlled MGP (EOA1 + EOA2) in the Sybil scenario should exceed the baseline by exactly `refererAmount`, demonstrating net profit from self-referral with no genuine third-party referee.

        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
