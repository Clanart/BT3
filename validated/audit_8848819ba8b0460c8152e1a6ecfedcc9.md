## Analysis

The report's broken invariant is: **a value computed under one denomination is consumed as if it were in another**, and this happens *inconsistently* between two code paths that should treat the same input the same way — one path applies the correct conversion/guard, a sibling path doesn't, and the divergence is exploitable.

In `bsaldua/desktop--019` the closest structural analog is a **path-sandboxing inconsistency in the Copilot merge-conflict UI**. When Desktop resolves conflicts (via Copilot, or via `git status`), it produces a list of conflicted `file.path` values that ultimately originate from data reported for a repository the app just fetched/merged against (i.e. attacker-influenced content, since the conflicting branch/remote can be hostile).

- The **write path** (`buildConflictContext` and `_resolveWithin`-backed application of resolutions) explicitly guards every one of these paths through `resolveWithin`, which normalizes and `realpath`-checks the result before touching disk: [1](#0-0) [2](#0-1) [3](#0-2) 

- The **context-menu / "open" path** in the same conflict-resolution dialog instead joins the identical untrusted `path` value directly onto the repository root with plain `path.join`, with no `resolveWithin`/`realpath` check at all, before handing it to "Open with default program", "Open in \<editor\>", and "Reveal in File Manager": [4](#0-3) 

This is the same class of bug as the Compound report: the collateral-value function (`getCollBalance`) applies the correct base/scale, while the borrow-value function (`getBorrowBalanceInBase`) reuses the same underlying quantity without the equivalent conversion — a value that is safe in one context is silently reused unsafely in a sibling context that looks like it should follow the same rule. Here, `resolveWithin` is the "conversion/guard" that the write path applies and the open/reveal path omits for the exact same class of attacker-influenced `path` string.

### Title
Untrusted conflict file path bypasses repository sandbox in Copilot conflict context menu ("Open"/"Reveal") - (File: app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx)

### Summary
`onOverflowMenuClick` in the Copilot conflicts dialog builds the target path for "Open with default program", "Open in \<editor\>", and "Reveal in File Manager" using plain `path.join(repository.path, path)`, while the functionally identical write-side consumer of the same `path` values (`buildConflictContext` / conflict resolution application in `AppStore`) is guarded by `resolveWithin`, which resolves symlinks and rejects any path escaping the repo root.

### Finding Description
Conflict file paths shown in the dialog come from the working tree's unmerged/conflicted files, produced after a merge/rebase/cherry-pick against a branch or remote the user does not control (the “attacker-controlled cloned/fetched repository” scenario). These path strings flow into two sinks in this feature:
1. Content read/write sink (`buildConflictContext`, resolution application) — sandboxed via `resolveWithin`, which normalizes, rejects null bytes, and requires the `realpath` of the resolved target to be nested under the repo root.
2. UI action sink (`onOverflowMenuClick`) — **not** sandboxed; it simply does `join(repository.path, path)` and passes the result to `openFile`, `openFileInExternalEditor`, and `revealInFileManager`.

Because the two sinks consume the exact same untrusted string but apply different validation, any crafted conflicted-path value that would be rejected by `resolveWithin` (e.g. one designed to normalize/resolve outside the repository root, including via symlinked intermediate directories or platform path-separator confusion) is still accepted by the unguarded `join()` call used for the "Open"/"Reveal" actions.

### Impact Explanation
If the working-directory conflict listing can contain (or be made to contain, via symlinked directory components inside the repo, or platform-specific separator handling) a path segment that escapes the repository root, the unguarded sink allows the app to open or reveal an arbitrary file outside the cloned repository through a user click that appears to be a normal "open this conflicted file" action. This is a file-read/reveal-outside-repo primitive triggered by content originating from an untrusted remote/branch, and it corrupts the invariant the write-side code explicitly documents as its purpose ("Guard against path traversal and symlink escapes (cross-platform)") by simply not applying it consistently.

### Likelihood Explanation
Medium: exploitation requires the attacker to get a conflicted file entry whose relative path, when joined naively, resolves outside the working directory (e.g. through a symlinked subdirectory committed in the malicious branch, since git permits symlinks as tree entries and Desktop does not appear to specifically block symlinked directory components in this particular sink). The action further requires the user to open the conflict-resolution context menu and click "Open"/"Reveal" — a single, unmodified, expected user interaction rather than an unnatural extra step. It does not require local/physical access, admin rights, or pre-existing malware.

### Recommendation
Route the path used in `onOverflowMenuClick` (and any other consumer of conflicted `file.path`/`resolution.path` values used for filesystem actions) through the same `resolveWithin` (or `resolveWithinWin32`/`resolveWithinPosix` as appropriate) check already used in `copilot-conflict-context.ts` and `app-store.ts`, and refuse to open/reveal when the check returns `null`, mirroring the `log.warn('Copilot resolution skipped: path outside repository...')` pattern already established elsewhere in the codebase.

### Proof of Concept
1. Attacker prepares a branch/remote that, when merged/rebased/cherry-picked by the victim, produces a conflict on a path whose resolution (via a symlinked directory checked into the malicious branch, or an equivalent path-separator trick) points outside the repository root.
2. Victim opens GitHub Desktop's Copilot conflict-resolution dialog for the resulting conflict.
3. Victim right-clicks the conflicted entry and selects "Open with default program" / "Reveal in File Manager" — `onOverflowMenuClick` computes `absolutePath = join(repository.path, path)` with no `resolveWithin` check: [5](#0-4) 
4. Contrast with the equivalent, correctly-guarded write path, showing the same class of input is validated there but not in the menu handler: [1](#0-0) 

Note: I was not able to fully confirm from the indexed code alone the exact upstream mechanism that would let a hostile repository place such an escaping path into the unmerged-file listing (e.g. whether Desktop's own `git status` parsing additionally normalizes/rejects symlinked path components before this point) — this would need to be verified against the full `app/src/lib/status.ts` / git status parsing implementation in a live session, since the indexer's coverage of that file was incomplete.
