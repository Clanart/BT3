### Title
`SimplexPaymaster._getOraclePrice()` accepts stale Chainlink prices during Arbitrum/Optimism/Base sequencer downtime, mispricing gas and draining paymaster funds - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` is deployed on Arbitrum, Optimism and Base [1](#0-0) , and prices every gas-payment token conversion through `_getOraclePrice()`, which only checks `answer <= 0` and a timestamp-based `maxOracleAge` staleness bound, without ever checking the Chainlink L2 sequencer-uptime feed [2](#0-1) . This is the exact bug class from the external report: on Arbitrum/Optimism/Base, when the sequencer is down, `latestRoundData()` keeps returning the last price the feed had before the outage together with its old (but still within `maxOracleAge`) `updatedAt`, so the staleness check alone cannot detect the outage.

### Finding Description
`_getOraclePrice()` is the sole gate protecting every price-dependent code path in the paymaster:

```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
``` [3](#0-2) 

`maxOracleAge` is deliberately configured with large buffers (24h on Base/Ethereum, up to 90,000s per deploy script) to tolerate normal heartbeat delays [4](#0-3) . This wide tolerance is precisely the window in which a sequencer-downtime stale price passes validation: the sponsor's own resolution of the original Sherlock issue explains that during sequencer downtime "the new price won't be reported to the chain... the feed on the L2 will return the value it had when it went down," and that value can still be well inside a multi-hour/day threshold window if the market moved before the outage window closes on `updatedAt`.

This stale/frozen price feeds directly into:
- `_tokenPrice()` → `_fetchDetails()` → `PaymasterERC20._erc20Cost` — determines exactly how many ERC-20 tokens are pulled from the UserOp sender to cover gas [5](#0-4) , [6](#0-5) .
- `swapAndDeposit()` — uses the same oracle price to compute `amountOutMin` for swapping accrued stablecoins to native asset, gating the router's execution price [7](#0-6) .

No path in the contract queries an `L2SequencerUptimeFeed`-style oracle, so there is no guard that rejects pricing during/immediately after a sequencer outage — the same missing check flagged in the external Chainlink/Arbitrum report.

### Impact Explanation
If the real asset price diverges from the frozen oracle price while the sequencer is down (and the outage lasts long enough for the market to move meaningfully but not long enough to exceed `maxOracleAge`), UserOps processed once the sequencer resumes will be charged the stale price:
- If the stale price undercharges relative to real market value, users drain paymaster-subsidized value: the paymaster/EntryPoint deposit pays real gas cost while receiving too little token value, directly bleeding protocol funds (loss of funds to the treasury/paymaster).
- If `swapAndDeposit()` executes with a stale `amountOutMin`, the treasury-triggered swap can settle at a wrong minimum output relative to true market price, again causing fund loss for the protocol side.

This matches the bounty's "stealing or loss of funds" / "false proof or state acceptance"-style category: an unprivileged party (any UserOp sender) can trigger `_fetchDetails`/`_getOraclePrice` with no privileged action, causing wrong-amount fund movement whenever the sequencer glitches on Arbitrum, Optimism, or Base — all live deployment targets of `SimplexPaymaster`.

### Likelihood Explanation
Arbitrum and Optimism-stack sequencers have historically experienced multi-minute to multi-hour outages. Because `maxOracleAge` is intentionally set large (24h class buffers) to avoid false-positive reverts on legitimate heartbeat delays, the exploitable window (outage duration where the price is stale but still "fresh enough" per the threshold) is realistically achievable without any privileged actor — any user submitting a normal ERC-20-gas UserOp during/after such a window triggers the mispriced path automatically.

### Recommendation
Integrate the Chainlink L2 sequencer uptime feed (`0xFdB631F5EE196F0ed6FAa767959853A9F217697` type feeds per chain) into `_getOraclePrice()`: revert if the sequencer is currently down, and require a grace period after it comes back up before accepting prices again — mirroring Chainlink's documented `example-code` pattern for L2 feeds, exactly as recommended in the referenced report and as implemented in `Bond-Protocol/bonds` PR #53.

### Proof of Concept
1. Deploy/observe `SimplexPaymaster` on Arbitrum with `maxOracleAge` set to its production value (large buffer for heartbeat tolerance).
2. Simulate sequencer downtime: the underlying Chainlink aggregator's `latestRoundData()` stops advancing `updatedAt`/`answer`, freezing at the pre-outage price, while `block.timestamp` keeps advancing normally via L1 batch posting.
3. During the outage (and shortly after, while `block.timestamp - updatedAt` is still `<= maxOracleAge`), submit a UserOp with `paymasterData` referencing a registered token; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` returns the frozen price without reverting (compare to `testStaleOracleReverts` in the test suite, which only tests the case where `updatedAt` exceeds `maxOracleAge`, not the sequencer-down/frozen-but-fresh case) [8](#0-7) .
4. Token amount charged to the UserOp sender is computed from the stale price, diverging from the true market price once the sequencer resumes and price catches up — resulting in wrong-amount fund transfer between user and paymaster/treasury.

    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
