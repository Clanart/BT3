### Title
`_calExpireForfeit` never applies `getRewardablePercentWAD`, so `getRewards`/`getReward` always pay 100% of accrued rewards to users with expired unwithdrawn unlock slots - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` is intended to forfeit part of a user's accrued reward when that user holds mWomSV weight coming from an expired-but-unwithdrawn unlocking slot (per `mWomSV.getRewardablePercentWAD`), redistributing the forfeited share to other stakers. Instead, the function is a no-op that always returns `forfeitAmount = 0` because it never reads `getRewardablePercentWAD` and instead sets `rewardableAmount = _amount` unconditionally, making `forfeitAmount = _amount - rewardableAmount == 0` by construction.

### Finding Description
`calExpireForfeit`/`_sendReward` in `rewards/mWOMSVBaseRewarder.sol` are the enforcement point for reducing rewards owed to users whose mWomSV balance weight includes amounts sitting in expired (fully unlocked but unwithdrawn) cooldown slots: [1](#0-0) 

The forfeiture calculation itself is broken: [2](#0-1) 

`rewardableAmount` is initialized to `_amount` and never modified based on `mWomSV.getRewardablePercentWAD(_account)` (the function that computes the actual rewardable share, weighted down for stale expired-cooldown balances) — despite `mWomSV.sol` implementing exactly that logic: [3](#0-2) 

Because `rewardableAmount = _amount` always holds, `forfeitAmount = _amount - rewardableAmount` is always `0`, and the subsequent "smaller than 0.1%" branch is dead code that can never trigger meaningfully (it only zeroes an already-zero value). Consequently `_sendReward` always computes `toSend = userRewards[token][account] - 0 = userRewards[token][account]`, i.e., 100% of `earned()`, regardless of whether the user's mWomSV weight partially derives from a fully expired, unwithdrawn cooldown slot.

The `getRewards`/`getReward` external entry points invoked by `MasterMagpie` (the only caller, `onlyMasterMagpie`) do not add any additional scaling and rely entirely on `_sendReward`: [4](#0-3) 

No modifier, reentrancy guard, or reward-index update compensates for this — `updateRewards`/`updateReward` only refresh `userRewards` via `_earned`, which itself has no forfeiture logic applied at accrual time either: [5](#0-4) 

So the intended mechanism (reduce payout to the rewardable percentage, redistribute the rest via `_queueNewRewardsWithoutTransfer`) never fires in practice.

### Impact Explanation
This is theft/misallocation of unclaimed yield: a user who has started `startUnlock` and let a slot fully expire without calling `unlock()` (so `amountInCoolDown > 0` and `endTime < block.timestamp`) still receives their full accrued reward via `MasterMagpie.multiclaimFor`/`getRewards` → `mWOMSVBaseRewarder.getRewards`/`getReward`, instead of the reduced share implied by `getRewardablePercentWAD`. The forfeited difference, which should be redistributed pro-rata to other mWomSV stakers via `_queueNewRewardsWithoutTransfer`, is never generated — permanently denying that redistribution to honest stakers and effectively letting the expired-slot holder capture rewards they should not be entitled to. This matches the "theft or permanent freezing of unclaimed yield" impact class, since honest stakers permanently lose the redistribution share that never gets queued.

### Likelihood Explanation
No special privilege, capital, or timing race is required beyond normal protocol usage: any staker can lock mWOM into `mWomSV`, call `startUnlock`, wait for cooldown to expire without withdrawing, keep accruing rewards on the still-counted balance, and then claim through the ordinary `MasterMagpie` claim path. This is 100% reachable by any unprivileged user, deterministic (the arithmetic bug is unconditional), and repeatable on every claim.

### Recommendation
Fix `_calExpireForfeit` to actually scale by the account's rewardable percentage from the locker, e.g.:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = (_amount * rewardablePercentWAD) / 1e18;
    uint256 forfeitAmount = _amount - rewardableAmount;

    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
    }
    return forfeitAmount;
}
```
Ensure `ILocker`/`mWOMSV` exposes `getRewardablePercentWAD` in the interface used by `mWOMSVBaseRewarder` and that it's called with up-to-date balances.

### Proof of Concept
Hardhat test plan:
1. Deploy `mWomSV`, `MasterMagpie`, `mWOMSVBaseRewarder` with a cooldown period (e.g., 7 days).
2. User A and User B each lock equal amounts of mWOM into `mWomSV`.
3. Queue reward tokens into `mWOMSVBaseRewarder` via `queueNewRewards` so both users accrue rewards over time.
4. User A calls `startUnlock` for their full balance; advance time past `coolDownInSecs` so the slot is expired but User A does **not** call `unlock()`.
5. Continue to advance time / queue more rewards so `earned(userA, token) > 0` continues to accrue.
6. Compute expected `rewardablePercentWAD = mWomSV.getRewardablePercentWAD(userA)` (should be < 1e18 since a portion is in an expired, unwithdrawn slot).
7. Call `MasterMagpie.multiclaimFor`/`getRewards(userA, ...)` and record the actual amount transferred to User A.
8. Assert: actual claimed amount == `earned(userA, token)` (full amount), not `earned(userA, token) * rewardablePercentWAD / 1e18` (the reduced, correct amount) — proving forfeiture never occurs and User A captures rewards beyond their `getRewardablePercentWAD`-implied entitlement.
9. Additionally assert that `rewards[token].rewardPerTokenStored` was never incremented via `_queueNewRewardsWithoutTransfer` as a result of this claim, confirming no forfeited amount was redistributed to User B.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
