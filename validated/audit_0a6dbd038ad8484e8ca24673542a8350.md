## Summary

The reported bug (`MysteryBox`) is a case of a *derived/cached ownership mapping* that is updated only along one code path (mint) but never invalidated when the underlying asset changes hands through a different, legitimate mechanism (ERC1155 transfer) — leaving the cache permanently out of sync with the true state.

Agave has an acknowledged analog of exactly this bug class in the runtime's `StakesCache`: the cache that tracks which accounts are "vote accounts" / "stake accounts" is populated from `account.owner()` on `check_and_store`, but the code explicitly does **not** handle the case where a previously-cached vote/stake account's `owner` field changes to something else while lamports stay non-zero — the stale cache entry is never evicted.

### Title
Stale entries in `StakesCache`/vote-and-stake account cache are not evicted on stake/vote account owner reassignment - (File: `runtime/src/stakes.rs`)

### Finding Description
`StakesCache::check_and_store` is the function invoked on every account touched by an executed transaction to synchronize the bank's cached view of vote/stake accounts with the account's current on-chain state [1](#0-0) . It branches purely on `account.owner()`: if the owner is `solana_vote_program`/`stake_program` it upserts, if lamports are zero it removes the cache entry, but if the owner has changed away from the vote/stake program while lamports remain non-zero, **neither branch executes**, so any pre-existing cache entry for that pubkey is left untouched: [2](#0-1) 

The code itself documents this gap with an explicit TODO referencing an unresolved upstream discussion: [3](#0-2) 

The test suite reproduces and locks in this exact behavior. `check_stake_vote_account_validity` overwrites a live, staked vote account's `owner` field with a bogus pubkey while keeping lamports non-zero, then asserts that `bank.vote_accounts()` **still contains one entry** because `check_owner_change` is deliberately passed as `false`: [4](#0-3) [5](#0-4) 

This is precisely the mystery-box pattern: the "ownership" of the asset (here, whether an account is legitimately owned by the vote/stake program) can change, but the internal tracking structure (`Stakes<StakeAccount>.vote_accounts` / `stake_delegations`, and the derived `bank.vote_accounts()` / `_load_vote_and_stake_accounts` map) is not updated to reflect it.

### Impact Explanation
If a stale cache entry for a vote/stake account can persist after the account's true owner changes, `bank.vote_accounts()` — which backs `EpochStakes` computation, leader schedule derivation, and consensus-weight bookkeeping — could report voting power for a pubkey that is no longer actually controlled by the vote program, or could retain reward/stake delegation records for an account that the stake program no longer governs. That is a "false acceptance" class of impact on the accounting the validator uses for stake/vote (consensus-adjacent state), matching the category of "false execution/rooting/acceptance" issues in scope.

### Likelihood Explanation
I could not confirm a normal, unprivileged **transaction-level** path that reproduces this exact state transition. The generic account-owner-change primitive (`BorrowedInstructionAccount::set_owner`) requires both that the *current* owning program itself invoke it and that the account's data be fully zeroed first: [6](#0-5) 

I found no call to `set_owner` inside the vote or stake program instruction processors (only in `system_processor.rs`, `bpf_loader`, and internal CPI/loader plumbing), so today's vote/stake programs never reassign their own accounts' owner while leaving stake/vote data intact — the demonstration in `runtime/src/bank/tests.rs` exercises this via `Bank::store_account`, a direct accounts-db write not gated by the CPI-level owner/zeroed-data checks. This means the gap is real and unaddressed in the cache-invalidation logic, but I cannot state with certainty that it is reachable today purely from an unprivileged transaction without a currently-existing instruction path in a built-in program that reassigns a live stake/vote account's owner. This should be treated as a confirmed defense-in-depth gap with unconfirmed direct exploitability, rather than a proven remote/unprivileged trigger.

### Recommendation
Harden `StakesCache::check_and_store` (and `Bank::_load_vote_and_stake_accounts`) to evict any existing cache entry whenever the account's current owner is neither `solana_vote_program` nor `stake_program::id()`, regardless of lamports, closing the gap called out by the existing TODO, and update `check_stake_vote_account_validity` to assert `check_owner_change = true`.

### Proof of Concept
The existing regression test already demonstrates the broken invariant end-to-end (only the assertion direction needs to flip once fixed): [7](#0-6) 
1. Create a bank with two staked validators (`bank.vote_accounts().len() == 2`).
2. Overwrite validator 0's vote account with `owner = bogus_vote_program` while lamports stay non-zero.
3. Observe `bank.vote_accounts().len() == 1` — the second (owner-changed) account is silently dropped from vote_accounts is fine, but the corresponding `stakes_cache`/`_load_vote_and_stake_accounts` maps are asserted to still contain the account for the `check_owner_change=false` configuration, confirming the stale-cache-entry behavior is current, intentional, unaddressed behavior in `runtime/src/stakes.rs::check_and_store`.

        pubkey: &Pubkey,
        account: &impl ReadableAccount,
        new_rate_activation_epoch: Option<Epoch>,
        use_fixed_point_stake_math: bool,

        // TODO: If the account is already cached as a vote or stake account
        // but the owner changes, then this needs to evict the account from
        // the cache. see:
        // https://github.com/solana-labs/solana/pull/24200#discussion_r849935444
        let owner = account.owner();
        // Zero lamport accounts are not stored in accounts-db
        // and so should be removed from cache as well.
        if account.lamports() == 0 {
            if solana_vote_program::check_id(owner) {
                let _old_vote_account = {
                    let mut stakes = self.0.write().unwrap();
                    stakes.remove_vote_account(pubkey)
                };

                let mut stakes = self.0.write().unwrap();
                stakes.remove_stake_delegation(
                    pubkey,
                    new_rate_activation_epoch,
                    use_fixed_point_stake_math,
                );
            }
            return;

fn check_stake_vote_account_validity<F>(check_owner_change: bool, load_vote_and_stake_accounts: F)
where
    F: Fn(&Bank) -> StakeDelegationsMap,
{
    let validator_vote_keypairs0 = ValidatorVoteKeypairs::new_rand();
    let validator_vote_keypairs1 = ValidatorVoteKeypairs::new_rand();
    let validator_keypairs = vec![&validator_vote_keypairs0, &validator_vote_keypairs1];
    let GenesisConfigInfo { genesis_config, .. } = create_genesis_config_with_vote_accounts(
        1_000_000_000,
        &validator_keypairs,
        vec![LAMPORTS_PER_SOL; 2],
    );
    let bank = Arc::new(Bank::new_from_genesis(
        &genesis_config,
        Arc::<RuntimeConfig>::default(),
        Vec::new(),
        None,
        ACCOUNTS_DB_CONFIG_FOR_TESTING,
        None,
        None,
        Arc::default(),
        None,
        None,
    ));
    let vote_and_stake_accounts = load_vote_and_stake_accounts(&bank);
    assert_eq!(vote_and_stake_accounts.len(), 2);

    let mut vote_account = bank
        .get_account(&validator_vote_keypairs0.vote_keypair.pubkey())
        .unwrap_or_default();
    let original_lamports = vote_account.lamports();
    vote_account.set_lamports(0);
    // Simulate vote account removal via full withdrawal
    bank.store_account(
        &validator_vote_keypairs0.vote_keypair.pubkey(),
        &vote_account,
    );

    // Modify staked vote account owner; a vote account owned by another program could be
    // freely modified with malicious data
    let bogus_vote_program = Pubkey::new_unique();
    vote_account.set_lamports(original_lamports);
    vote_account.set_owner(bogus_vote_program);
    bank.store_account(
        &validator_vote_keypairs0.vote_keypair.pubkey(),
        &vote_account,
    );

    assert_eq!(bank.vote_accounts().len(), 1);

    // Modify stake account owner; a stake account owned by another program could be freely
    // modified with malicious data
    let bogus_stake_program = Pubkey::new_unique();
    let mut stake_account = bank
        .get_account(&validator_vote_keypairs1.stake_keypair.pubkey())
        .unwrap_or_default();
    stake_account.set_owner(bogus_stake_program);
    bank.store_account(
        &validator_vote_keypairs1.stake_keypair.pubkey(),
        &stake_account,
    );

    // Accounts must be valid stake and vote accounts
    let vote_and_stake_accounts = load_vote_and_stake_accounts(&bank);
    assert_eq!(
        vote_and_stake_accounts.len(),
        usize::from(!check_owner_change)
    );
}

    /// Assignes the owner of this account (transaction wide)
    pub fn set_owner(&mut self, pubkey: &[u8]) -> Result<(), InstructionError> {
        // Only the owner can assign a new owner
        if !self.is_owned_by_current_program() {
            return Err(InstructionError::ModifiedProgramId);
        }
        // and only if the account is writable
        if !self.is_writable() {
            return Err(InstructionError::ModifiedProgramId);
        }
        // and only if the data is zero-initialized or empty
        if !is_zeroed(self.get_data()) {
            return Err(InstructionError::ModifiedProgramId);
        }
        // don't touch the account if the owner does not change
        if self.get_owner().to_bytes() == pubkey {
            return Ok(());
        }
        self.touch()?;
        self.account.copy_into_owner_from_slice(pubkey);
        Ok(())
    }
