## Title
Unprivileged callers can drain any non-registered ERC20 token balance held by `ManualCompound` via the `compound()` function - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` lets any caller supply an arbitrary list of "reward token" addresses (`_rewards`) and then sweeps the contract's **entire current balance** of any token in that list that is not flagged `compoundableRewards[token]`, sending it to `msg.sender`. Because the sweep amount is derived from `IERC20(token).balanceOf(address(this))` rather than the amount actually claimed for the caller in that transaction, any stray/leftover balance of a non-registered token sitting in the contract can be swept in full by any wallet, even one with zero stake in any Magpie pool.

### Finding Description
In `compound()`, after calling `multiclaimOnBehalf` (which routes the actual claimed rewards to the `ManualCompound` contract as `_receiver`), the contract sweeps back "non-compoundable" rewards using the caller-supplied `_rewards` array: [1](#0-0) 

The check `!compoundableRewards[_rewards[i][j]]` only gates tokens that the owner has explicitly registered via `addReward` as compoundable (locked/converted). Any other address supplied in `_rewards` is treated as sweepable, and the **full current balance** of that token in the contract is transferred to `msg.sender`: [2](#0-1) 

This mirrors the referenced bug class exactly: the amount transferred is not tied to what the caller actually earned/deposited in this call — it's whatever balance the contract happens to hold for that token address at call time. `_rewards` is fully attacker-controlled `calldata`, and `_claimBaseRewarder`/`getRewards` in `BaseRewardPool`/`BaseRewardPoolV2` will simply no-op (transfer 0) for tokens that aren't real registered rewards for the pool (`userRewards[token][account]` defaults to 0), so an attacker does not need any real stake or claim to trigger the sweep: [3](#0-2) [4](#0-3) 

Any wallet can therefore call `compound()` with a `_lps`/`_rewards` combination naming any ERC20 address it wants (e.g. a token that ended up in the contract from convertor rounding remainders, a reward token that a base rewarder distributes but that the owner hasn't yet registered via `addReward`, or tokens accidentally sent to the contract) and receive the entire balance, regardless of whether that balance belongs to other users' pending compounds or the protocol.

### Impact Explanation
This allows direct, permissionless theft of ERC20 token balances held by `ManualCompound` that are not on the `compoundableRewards` allow-list — including reward tokens that legitimately belong to other users but happen to be resident in the contract (e.g., left over from conversion/locking steps, or reward tokens distributed by a `BaseRewardPool` that the owner hasn't yet wired into `rewards[]`). This is theft of user/protocol funds with no privileged role required, satisfying the "concrete direct theft of user funds" bar.

### Likelihood Explanation
Likelihood is high once any balance accumulates in the contract for a token not flagged `compoundableRewards`: it requires no special permissions, no timing dependency beyond the token balance being non-zero, and can be triggered by any ordinary wallet in a single transaction by simply choosing an appropriate `_lps`/`_rewards` argument.

### Recommendation
Track the actual amount received by `ManualCompound` for each entry in `_rewards` during the current call (e.g., balance-before/balance-after delta scoped to this transaction, or have `multiclaimOnBehalf`/`getRewards` return exact amounts transferred) and only forward that delta to `msg.sender`, instead of sweeping `IERC20(token).balanceOf(address(this))`.

### Proof of Concept
1. Assume the `ManualCompound` contract currently holds a non-zero balance of token `X` that is not in `compoundableRewards` (e.g., a remainder from `IConverter.convertFor` for a previous caller, or a reward token distributed by a `BaseRewardPool` pool but not yet added via `addReward`).
2. An attacker with no stake in any Magpie pool calls `compound(_lps, _rewards, 0, 0, false)` where `_lps = [somePoolStakingToken]` and `_rewards = [[X]]`.
3. `multiclaimOnBehalf` claims nothing meaningful for the attacker (their earned amount for `X` is 0), but the subsequent sweep loop executes:
   `rewardBalance = IERC20(X).balanceOf(address(this))` → full balance
   `IERC20(X).safeTransfer(msg.sender, rewardBalance)` → sent entirely to the attacker.
4. The attacker receives the entire stray/pending balance of token `X`, which may include funds owed to other users or the protocol, at zero cost. [1](#0-0)

    function compound(address[] calldata _lps, address[][] calldata _rewards, uint256 _convertRatio, uint256 _minRec, bool _lockMgp) external {
        uint256 rewardTokensLength = rewards.length;        
        IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
        // send none compoundable reward back to caller
        for(uint256 i; i < _lps.length; i++) {
            uint256 rewardLength = _rewards[i].length;
            if (rewardLength > 0) {
                for (uint j; j < rewardLength; j++) {
                    if (!compoundableRewards[_rewards[i][j]]) {
                        uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
                        if (rewardBalance > 0)
                            IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
                    }
                }
            }
        }
