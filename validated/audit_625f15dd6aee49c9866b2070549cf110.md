Based on the investigation, the closest structural analog to the "split-transaction" bug class (a multi-step operation that is not atomic, where content can shift between the "what the user approved" step and the "what gets executed" step) is the commit-staging pipeline in `createCommit()`.

### Title
Stale-diff TOCTOU in partial-commit staging can silently commit content the user never reviewed - ([File: app/src/lib/git/update-index.ts](), [File: app/src/lib/git/apply.ts]())

### Summary
`executePayroll()`'s flaw was that a "single" batch operation was actually a sequence of independent, non-atomic sub-transactions, so an attacker able to act between sub-steps could make the final on-chain state diverge from what was authorized. GitHub Desktop has a structurally identical pattern in the commit-staging code path: `createCommit()` → `stageFiles()` loops over files and, for every partially-selected file, performs a *separate*, freshly re-computed diff/patch/apply sequence, instead of reusing the diff the user actually reviewed and selected hunks from.

### Finding Description
When a user stages a partial selection of a file's changes and clicks "Commit," the flow is:
1. `_commitIncludedChanges` in `app/src/lib/stores/app-store.ts` (around line 3681-3711) passes the currently `selectedFiles` (each carrying a `DiffSelection` computed from a *previously rendered* diff) into `createCommit`.
2. `createCommit` (`app/src/lib/git/commit.ts:15-72`) calls `unstageAll` then `stageFiles`.
3. `stageFiles` (`app/src/lib/git/update-index.ts:109-169`) partitions files and, for every file with a partial selection, awaits `applyPatchToIndex` **one file at a time in a sequential loop** (line 166-168).
4. `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`) does **not** reuse the diff object the UI already rendered/selected against. It re-invokes `getWorkingDirectoryDiff(repository, file)` (line 60) to get a brand-new diff from the current on-disk state, then builds a patch (`formatPatch`) by re-applying the old `DiffSelection` line/hunk indices to this *new* diff, and finally runs `git apply --cached` with that patch.

This is the same "broken invariant" as `executePayroll()`: a decision made against one snapshot (the diff the user visually reviewed and hand-picked lines from) is executed against a different, later snapshot (the working-directory content re-read at staging time), across a sequence of independently-awaited git subprocess calls (`add --update`, `ls-tree`, `update-index`, `apply --cached`) with real async gaps between them — not one atomic operation.

Notably, the codebase elsewhere explicitly guards against exactly this kind of staleness: `updateChangesStashDiff` in `app/src/lib/stores/app-store.ts:3661-3668` checks "Something has changed during our async getCommitDiff, bail" before committing UI state. No equivalent staleness check exists on the commit-staging path (`stageFiles`/`applyPatchToIndex`), so the recognized hazard pattern is unmitigated specifically where it matters most — what actually gets written into the repository's history.

### Impact Explanation
If the working-directory content for a file changes between (a) the moment the user reviewed the diff and selected specific lines/hunks to include, and (b) the moment `stageFiles` iterates to that file and calls `applyPatchToIndex`, the line-selection indices are applied to the wrong content. Depending on how the content changed (e.g., a checked-out working tree modified via a smudge/clean filter declared in an attacker-supplied `.gitattributes` of the cloned repository, a concurrent background operation touching the same file, or a symlinked path being swapped between review and staging), the resulting staged/committed blob can differ from what the user saw and approved — this is "silent corruption of what the user commits," one of the explicitly valid impact classes, and it can also be leveraged to smuggle unexpected byte content (e.g., via symlink retargeting) into a commit that later gets pushed.

### Likelihood Explanation
The likelihood is moderate and conditional: it requires an attacker-controlled repository or filter mechanism (e.g., `.gitattributes`-declared filters, or a symlinked path within the repo) to be able to alter working-directory bytes for a specific file inside the narrow window between UI-diff rendering and the sequential per-file staging loop in `stageFiles`. I was not able to fully confirm within the indexed code a concrete, single-step trigger that reliably lands a write inside that exact window (e.g., a specific smudge-filter hook invoked automatically during that gap) — this would need to be validated dynamically (e.g., with a crafted fixture repository and a slow/large diff to widen the timing window) to convert this from a structural weakness into a fully reproducible exploit.

### Recommendation
Do not recompute the diff at staging time from scratch. Either:
- Capture and persist the exact diff object (or its content hash) that was shown to the user at selection time, and use it — not a freshly re-read one — when building the patch in `applyPatchToIndex`; or
- Before running `git apply --cached`, verify that the file's current on-disk content/hash matches what it was when the selection was made, and abort/re-prompt the user if it has changed (mirroring the "bail if something changed" pattern already used in `updateChangesStashDiff`).

### Proof of Concept
Not fully verified end-to-end from static analysis alone. The structural PoC sketch is:
1. Open a repository with a large/slow-to-diff file that has both `.gitattributes`-declared content filters (or is a symlink target) and unrelated modifications.
2. In Desktop's Changes view, select only specific lines/hunks of that file for a partial commit.
3. Immediately after selection (during the async gap before `stageFiles` reaches that file in its per-file loop, e.g. by having other files ahead of it in the commit selection to lengthen the loop), trigger something that rewrites the file's on-disk bytes (e.g., a background git filter run, or a symlink swap of the path).
4. Click "Commit." Because `applyPatchToIndex` re-reads the working directory at staging time (`app/src/lib/git/apply.ts:60`) rather than reusing the reviewed diff, the resulting commit can contain content that was never shown to or approved by the user.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
}
