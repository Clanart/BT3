## Title
Malicious `tokenIn` in IntentGatewayV2/IntentsBase permanently locks escrowed funds and blocks Hyperbridge cross-chain refund settlement — (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` accepts any address as `order.inputs[i].token` with no allowlist, exactly like the `tokenIn` in the referenced `OracleLess` report. An attacker can escrow a malicious ERC-20 that reverts on `transfer`/`safeTransfer` to the gateway itself. Every code path that releases that escrow — same-chain cancel, cross-chain source cancel, and critically the cross-chain `onAccept` handler that processes `RedeemEscrow`/`RefundEscrow` Hyperbridge messages — calls `_withdraw`, which unconditionally does `IERC20(token).safeTransfer(beneficiary, amount)`. Because the token always reverts, the withdrawal can never succeed, and because the associated `DispatchPost` uses `timeout: 0` (no timeout), there is no protocol-level recovery path. The escrowed funds (which can include legitimate co-escrowed assets in the same order, not just the malicious token) become permanently stuck.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` (lines 181-300) pulls arbitrary `order.inputs[i].token` via `IERC20(token).safeTransferFrom` with no whitelist check [1](#0-0) .

The single token-release function used by every settlement/refund path is `_withdraw` in `IntentsBase.sol`: [2](#0-1) 

For cross-chain orders, `_cancelFromDest` marks the order as finalized locally (`_filled[commitment] = ...`) and dispatches a `RefundEscrow` POST with `timeout: 0`, i.e. it can never expire/time out: [3](#0-2) 

When that message reaches the source chain, `onAccept` decodes it and calls `_withdraw(body, kind == RequestKind.RefundEscrow, true)`: [4](#0-3) 

If any `token` in `body.tokens` is the malicious contract, `IERC20(token).safeTransfer(beneficiary, amount)` inside `_withdraw` reverts, causing the whole `onAccept` callback to revert. Since the `DispatchPost` had `timeout: 0`, ISMP will keep re-attempting delivery of the same message indefinitely without a timeout fallback, and every attempt reverts identically — the escrow can never be released. The same non-recoverable revert applies to `RedeemEscrow` (solver trying to claim a fill) and to the same-chain `_cancelSameChain`/`withdraw` path (Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 682-721), which is the direct analog of the `OracleLess._cancelOrder` revert-on-refund bug.

Because a single order can escrow multiple `TokenInfo` entries (`order.inputs`), an attacker can pair one malicious, always-reverting token with other legitimate tokens in the same order; when `_withdraw` iterates the token list, the malicious entry's revert blocks the release of every other legitimate token in that same order as well.

### Impact Explanation
This is a real, unprivileged fund-lock primitive on the live IntentGateway escrow logic, not a generic gas-DoS: escrowed value (attacker's own tokens, and any co-escrowed legitimate tokens in the same order) becomes permanently irrecoverable because (1) there is no token allowlist at `placeOrder`, (2) `_withdraw`/`withdraw` has no per-token try/catch or skip-and-continue fallback, and (3) the cross-chain refund/redeem dispatches use `timeout: 0`, removing the only other recovery mechanism (a timeout handler) that exists elsewhere in the codebase (e.g., `WrappedHyperFungibleTokenUpgradeable.onPostRequestTimeout`). This directly matches the bounty's "loss/lock of funds" and "logic attack via unauthenticated flow" categories — no malicious relayer, prover, or admin is needed, only a normal user placing an order with a self-deployed token.

### Likelihood Explanation
High. Any account can call `placeOrder` with a self-crafted ERC-20 (revert-on-transfer-to-gateway) as `order.inputs[i].token`; this requires no special privileges, no race condition, and no cooperation from relayers or provers — a single transaction suffices to create an unrefundable/unredeemable order.

### Recommendation
- Add a token allowlist (or at minimum a code-existence + standard-compliance check) enforced at `placeOrder` for all `order.inputs[i].token` values, mirroring the mitigation recommended for the `OracleLess` report.
- Make `_withdraw`/`withdraw` resilient to a reverting token: use low-level `call` with try/catch per token so a single malicious token cannot block release of co-escrowed legitimate tokens or the overall finalize/emit logic, and mark the order/beneficiary as owed a claimable balance instead of reverting the entire call.
- Set a real `timeout` (not `0`) on `RedeemEscrow`/`RefundEscrow` `DispatchPost` dispatches so a permanently-reverting withdrawal path degrades to a timeout-handled fallback instead of an unrecoverable revert loop.

### Proof of Concept
1. Attacker deploys `EvilToken` implementing `IERC20` whose `transfer`/`transferFrom` succeeds when pulled into the gateway (`placeOrder`'s `safeTransferFrom`) but always reverts when the gateway attempts to send it out (`safeTransfer` inside `_withdraw`).
2. Attacker calls `IntentGatewayV2.placeOrder` with a cross-chain order whose `order.inputs` includes `EvilToken` (and optionally a legitimate token, e.g. USDC, in the same order) — escrow succeeds since inbound transfer is not reverted.
3. Order goes unfilled past `order.deadline`. Anyone calls `cancelOrder` → `_cancelFromDest`, which sets `_filled[commitment]` and dispatches `RefundEscrow` with `timeout: 0`.
4. When the relayer delivers the message, `onAccept` → `_withdraw` attempts `IERC20(EvilToken).safeTransfer(beneficiary, amount)`, which reverts, reverting the whole `onAccept` call.
5. Because `timeout` was `0`, there is no timeout path to fall back to; the message delivery will keep failing on every retry. Both the `EvilToken` amount and any co-escrowed USDC in the same `WithdrawalRequest.tokens` array remain locked in the source-chain gateway forever, with `_filled[commitment]` already set on the destination chain, so the order can never be re-processed through any other path either.

            to: abi.encodePacked(_instance(order.source)),

            payer: msg.sender
