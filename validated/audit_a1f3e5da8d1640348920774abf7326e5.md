### Title
Silent fast-forward failures after fetch/pull are masked by an overly-broad success exit code, leaving local tracking refs stale without detection - (File: app/src/lib/git/fetch.ts)

### Summary
The report's core defect is a broken invariant: after an external operation partially completes, cached/derived state that assumes full completion is never corrected. `LienToken.sol` decremented `yIntercept` only in the full-payout branch, so a partial Seaport payout left the vault's accounting stale. The closest structural analog in GitHub Desktop is `fastForwardBranches` in `app/src/lib/git/fetch.ts`, which fast-forwards *all* local tracking branches in one `git fetch . --stdin` call but accepts exit code `1` as blanket success, without inspecting which of the individual `refPairs` actually updated.

### Finding Description
`fastForwardBranches` batches every stale local tracking branch into one `git fetch` invocation and passes `successExitCodes: new Set([0, 1])` because, per the inline comment, "Fetch exits with an exit code of 1 if one or more refs failed to update which is what we expect will happen": [1](#0-0) 

This call is treated as an atomic success/failure unit — there is no per-ref parsing of stderr/stdout to determine *which* of the `refPairs` (`branch.upstreamRef:branch.ref`) actually fast-forwarded and which silently failed (e.g., because the remote-tracking branch history diverged, as would happen if the remote returned rewritten/forced history that can't be fast-forwarded, or a race with a concurrent local update). The caller (`performPush`/`performPull` in `app-store.ts`) unconditionally proceeds to refresh branch protection state and the whole repository as if all tracking refs are now current: [2](#0-1) [3](#0-2) 

The corrupted value here is the local tracking branch's stored SHA/ahead-behind counters (`branchesState`, `aheadBehind`) — analogous to `yIntercept`: it's a cached quantity that is supposed to always reflect the true post-operation state, but after a partial failure of the underlying operation it is left pointing at the pre-fetch value while the rest of the app (branch list, "ahead/behind" badges, force-push warnings) treats it as authoritative.

### Impact Explanation
GitHub Desktop uses these tracking-branch positions to compute ahead/behind counts and to decide whether a push needs to be a force-push (`confirmOrForcePush`/`performForcePush` in `dispatcher.ts`) and whether to show "branch already up to date" banners. If one ref among many silently fails to fast-forward — e.g. because a remote returned history that diverges from what Desktop's local tracking ref expects, which is exactly the kind of "attacker controls a git remote/proxy response" scenario allowed by this exercise's valid-impact criteria — Desktop will still report success for the whole operation and refresh the UI as if the tracking branch is current. This can cause the user to make commit/push decisions (e.g., deciding a force-push is unnecessary, or committing on top of what they believe is the latest upstream state) based on stale, silently-wrong local state, i.e., a form of "silent corruption of what the user commits or pushes" without any error being surfaced.

### Likelihood Explanation
The likelihood is moderate to low: the batched fast-forward runs against `.` (the local repo, refspecs sourced from already-fetched remote-tracking refs), so it is one hop removed from directly attacker-controlled network content, and Desktop's own comment ("which is what we expect will happen") indicates the exit-1 case is a known, common occurrence (any single branch failing to fast-forward is treated as expected noise for the whole batch). This is a plausible everyday occurrence with multiple stale local branches, not requiring any unusual local/physical access or credentials — it is triggered purely by a repository's ordinary branch divergence, which an attacker with control of a fetched remote can engineer by advertising rewritten history for a given ref.

### Recommendation
Parse per-ref outcome (git fetch with `--stdin` reports individual ref update results on stderr, similar to how `getFilesWithConflictMarkers`/`fetchTagsToPush` parse porcelain output elsewhere in this codebase) instead of relying on the aggregate exit code. Update only the tracking-branch entries confirmed to have fast-forwarded, and explicitly surface/log (or refresh) the ones that didn't, so downstream ahead/behind and force-push logic never treats an unresolved ref as up to date.

### Proof of Concept
I could not build a concrete, verified end-to-end PoC within the available tool budget — I found and confirmed the vulnerable pattern (`successExitCodes: new Set([0, 1])` with no per-ref result parsing in `fastForwardBranches`, `app/src/lib/git/fetch.ts:103-140`) and its unconditional-success call sites in `performPush`/`performPull` (`app/src/lib/stores/app-store.ts`), but I was unable to trace, within the remaining budget, the exact downstream code path in `ahead-behind-store.ts` / `git-store.ts` that consumes the stale tracking ref to confirm precisely which UI/force-push decision becomes wrong when one ref among many fails silently. A background Devin session with terminal access could reproduce this by fast-forwarding two tracking branches in one `fastForwardBranches` call where one is unable to fast-forward, confirming that the function returns without error and that the failing branch's cached SHA is not refreshed/flagged anywhere in `IBranchesState`.

```typescript
export async function fastForwardBranches(
  repository: Repository,
  branches: ReadonlyArray<ITrackingBranch>
): Promise<void> {
  if (branches.length === 0) {
    return
  }

  const refPairs = branches.map(branch => `${branch.upstreamRef}:${branch.ref}`)

  await git(
    [
      'fetch',
      '.',
      // Make sure we don't try to update branches that can't be fast-forwarded
      // even if the user disabled this via the git config option
      // `fetch.showForcedUpdates`
      '--show-forced-updates',
      // Prevent `git fetch` from touching the `FETCH_HEAD`
      '--no-write-fetch-head',
      // Take branch refs from stdin to circumvent shell max line length
      // limitations (mainly on Windows)
      '--stdin',
    ],
    repository.path,
    'fastForwardBranches',
    {
      // Fetch exits with an exit code of 1 if one or more refs failed to update
      // which is what we expect will happen
      successExitCodes: new Set([0, 1]),
      env: {
        // This will make sure the reflog entries are correct after
        // fast-forwarding the branches.
        GIT_REFLOG_ACTION: 'pull',
      },
      stdin: refPairs.join('\n'),
    }
  )
```
