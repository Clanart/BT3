This confirms the mechanism: when a CR-CAT is transferred to a recipient who cannot immediately present a valid VC satisfying the `authorized_providers`/`proofs_checker` requirements, the payment is routed to a "pending approval" state via `construct_pending_approval_state` [1](#0-0)  rather than directly to the recipient's inner puzzle hash. The only way to move the coin out of this pending state is `CRCATWallet.claim_pending_approval_balance`, which requires locating a VC that satisfies `self.info.authorized_providers` and `self.info.proofs_checker.flags`; if no such VC exists, it raises `RuntimeError` and the funds simply remain in the pending-approval puzzle indefinitely [2](#0-1) . There's no mechanism in this puzzle/wallet flow to return the value to the sender if the recipient can never obtain a compliant VC — structurally the same "destination-side authorization/cap gate blocks finalization, no fallback to sender" pattern as the sUSX `mintCap` bug.

### Title
CR-CAT funds sent to recipients without a qualifying VC become permanently stuck in the "pending approval" state with no fallback to the sender - (File: chia/wallet/vc_wallet/cr_cat_wallet.py)

### Summary
Credential-Restricted CATs (CR-CATs) route any payment whose destination cannot be immediately authorized by a matching Verified Credential (VC) into an intermediate on-chain "pending approval" puzzle instead of the recipient's real inner puzzle. Claiming out of that pending state requires the recipient to independently obtain a VC issued by one of the CAT's `authorized_providers` and containing proofs satisfying the `proofs_checker` flags. If the recipient's wallet can never obtain such a VC (e.g., no provider will issue one, the requirement set is impossible for them to satisfy, or the provider set/flags configured by the sender do not match anything the recipient can get), the CR-CAT amount is permanently locked in the pending-approval coin with no path back to the original sender — mirroring the sUSX `mintCap` bug where a destination-side gating check (mint cap there, VC authorization here) blocks finalization of a transfer and leaves funds stuck pending a third party (there: the admin raising the cap; here: a credential provider issuing a VC).

### Finding Description
`construct_pending_approval_state` wraps a payment's real destination puzzle hash in `PENDING_VC_ANNOUNCEMENT`, which is used as the CR-CAT inner puzzle whenever the sender/taker-side logic (in `VCWallet.add_vc_authorization` and `TradeManager.check_for_requested_payment_modifications`) cannot immediately confirm a valid VC for the recipient [1](#0-0) [3](#0-2) . The corresponding coin is tracked client-side as `CoinType.CRCAT_PENDING` [4](#0-3) .

The only exit from this state is `CRCATWallet.claim_pending_approval_balance`, which calls `vc_wallet.get_vc_with_provider_in_and_proofs(self.info.authorized_providers, self.info.proofs_checker.flags)`. If no VC satisfies both the provider list and proof flags, the call raises `RuntimeError` and no spend is produced [2](#0-1) . There is no code path in `cr_cat_wallet.py`, `vc_wallet.py`, or `trade_manager.py` that allows the pending-approval coin to be redirected back to the sender, refunded, or claimed through any means other than presenting a compliant VC. Because `authorized_providers` and `proofs_checker` are fixed parameters of the CR-CAT asset (curried into the puzzle at mint time, mirrored in `CRCATInfo`), a recipient who is unable to obtain a VC from any of the configured providers — analogous to an admin never raising the destination `mintCap` in the sUSX report — has no recourse; the coin is spendable only by a VC that may never materialize.

### Impact Explanation
Funds transferred as CR-CATs to a destination that cannot obtain an authorizing VC become permanently non-spendable by the intended recipient and unrecoverable by the sender, since the CR-CAT has already left the sender's control and the pending-approval puzzle has no sender-reclaim branch. This is a direct fund-lock analogous to the reported bug: value moves out of the sender's coin set but never resolves into spendable value for anyone, absent third-party (credential-provider) action outside the protocol's control.

### Likelihood Explanation
This can be triggered in ordinary usage: any CR-CAT payment, offer settlement, or `claim_pending_approval_balance`/`crcat_approve_pending` RPC flow that targets a recipient lacking (and unable to obtain) a VC from the `authorized_providers` set with the required `proofs_checker` flags will land in this state, and it will stay there indefinitely since raising the issue requires an off-chain credential provider action, not a protocol-level fallback.

### Recommendation
Add a puzzle-level or wallet-level fallback path for `pending approval` CR-CAT coins allowing the original sender (or a designated timeout/refund puzzle branch) to reclaim the value if no qualifying VC becomes available within a bounded window, similar to how `clawback` puzzles allow the sender to reclaim funds after a timelock via `create_merkle_puzzle`/`create_merkle_solution` [5](#0-4) . At minimum, wallet UX and documentation should surface pending-approval balances that cannot currently be claimed due to lack of an authorizing VC, and `claim_pending_approval_balance`/`add_vc_authorization` should distinguish "VC not yet available" from "no VC will ever satisfy this configuration" where possible.

### Proof of Concept
1. Mint a CR-CAT with `authorized_providers = [DID_A]` and a `ProofsChecker` requiring flag `"kyc"`, using `CRCATWallet.get_or_create_wallet_for_cat` [6](#0-5) .
2. Send CR-CAT payment to Bob's puzzle hash, e.g. via an offer where the taker cannot supply a matching VC; `TradeManager.check_for_requested_payment_modifications` rewrites the requested payment's destination to `construct_pending_approval_state(bob_ph, amount).get_tree_hash()` [3](#0-2) .
3. Confirm the spend; Bob's wallet records the coin as `CoinType.CRCAT_PENDING` [4](#0-3) .
4. Bob never obtains a VC issued by `DID_A` with a `"kyc"` proof (e.g., `DID_A` refuses, is defunct, or requires unmeetable conditions). Bob calls `crcat_approve_pending` / `claim_pending_approval_balance`; `vc_wallet.get_vc_with_provider_in_and_proofs` returns `None` and the call raises `RuntimeError`, leaving the coin permanently unspent by Bob and unreachable by the original sender [2](#0-1) .
