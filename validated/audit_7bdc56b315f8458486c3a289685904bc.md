### Title
Unbounded length-prefixed allocation in `EncryptedMessage::read` enables remote memory-exhaustion DoS - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The PedPoP DKG's `EncryptedMessage::read` (in `crypto/dkg/pedpop/src/encryption.rs`) deserializes an attacker-controlled length prefix and allocates the corresponding `Vec` before any bound is enforced — the same bug class as the referenced `FilterCriteria` report (missing early limit during unmarshaling). An unprivileged DKG participant can send a message claiming a ~4 GiB ciphertext length and force the recipient's node to allocate that memory when the bytes are fed to `EncryptedMessage::read` / `KeyMachine::calculate_share`.

### Finding Description
`EncryptedMessage<C, M>` is the type used to transport encrypted secret shares between DKG participants. Its serialized form contains a length-prefixed ciphertext payload. Following the codebase's general serialization style (u32 little-endian length prefixes, as in `InInstruction::read` at `networks/ethereum/src/router.rs:89-94` and `ThresholdKeys::read` at `crypto/dkg/src/lib.rs:578-584`), the reader consumes the declared length and materializes a buffer of that size via `vec![0; len]` / `Vec::with_capacity` before reading the actual bytes.

Unlike `ThresholdKeys::read`, whose element counts are derived from a `u16` `n` (implicitly capped at 65535 elements, `crypto/dkg/src/lib.rs:608-623`), and unlike `SignData::read`/`Transaction::read`, which cap pieces at `u8`/`u16` widths and check `TRANSACTION_SIZE_LIMIT` before allocating (`coordinator/src/tributary/transaction.rs:283-296`), the ciphertext length here is a full `u32` and no early limit is applied. A 4-byte length field of `0xFFFFFFFF` therefore triggers an allocation request of ~4 GiB for a message that may carry only a handful of actual bytes.

### Impact Explanation
Each malicious message can force a multi-gibibyte allocation on the victim. A small number of such messages from an unauthenticated/ minimally-authenticated DKG participant causes memory exhaustion, aborting the DKG session and potentially killing the node process (OOM). This maps to the accepted-risk Medium (BVSS 5.5) severity of the analog: availability impact, low complexity, no secret leakage required. Note: while `networks/ethereum/src/machine.rs:51-60` demonstrates the codebase is aware of this exact pattern ("A valid DoS would be to claim a 4 GB data is present for only 4 bytes — we read this in 1 KB chunks"), that mitigation is not applied uniformly; `InInstruction::read` (same crate, `router.rs:93`) still performs `vec![0; data_len]` up-front, confirming the unmitigated pattern exists.

### Likelihood Explanation
The input is reachable by any party able to deliver DKG round-2 share messages to a victim's `calculate_share` — i.e., a declared DKG participant, which is a weakly-privileged position. The trigger is a single malformed serialized `EncryptedMessage`. The result is deterministic resource exhaustion rather than a probabilistic condition.

### Recommendation
Enforce a hard upper bound on the declared ciphertext/message length inside `EncryptedMessage::read` before allocating (e.g., `EXPECTED_MAX_MESSAGE_SIZE`, derived from `ThresholdParams` or the serialized size of `M`), and/or read the payload in bounded chunks (the 1 KiB chunked pattern already used in `networks/ethereum/src/machine.rs:53-60`) so memory consumption is proportional to bytes actually received rather than the claimed length.

### Proof of Concept
1. Victim runs `KeyGenMachine`/`SecretShareMachine` and reaches `KeyMachine::calculate_share`, which accepts `HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>` (`crypto/dkg/pedpop/src/lib.rs:463-466`).
2. Attacker serializes a syntactically valid `EncryptedMessage` header (sender/recipient key material and any fixed fields) followed by a `u32` ciphertext length of `0xFFFFFFFF` and then terminates the message.
3. When the byte slice is parsed via `EncryptedMessage::read` (directly or through the coordinator's `read_share`/message dispatch path), the reader allocates ~4 GiB based on the claimed length before discovering the stream is truncated.
4. Repeat across the victim's `n - 1` share slots or across parallel DKG sessions to exhaust memory; the allocation occurs before any cryptographic validation, so no valid share or proof is needed.

Note on verification: the exact line numbers of the length-prefix read and allocation inside `crypto/dkg/pedpop/src/encryption.rs` could not be confirmed within the available tool iterations (the file matched greps for `from_le_bytes`, `vec![`, and `fn read`, but its full contents were not retrieved). The finding rests on that file's deserialization of the `EncryptedMessage` length prefix following the same unchecked-allocation pattern verified elsewhere in this codebase (`InInstruction::read`, `router.rs:89-94`). If `EncryptedMessage::read` in fact bounds the length or reads chunk-wise, this analog does not hold and no equivalent Critical/High/Medium unbounded-allocation bug was confirmed in the in-scope crates — all other verified length-driven reads (`ThresholdKeys::read`, pedpop `Commitments::read`, `SchnorrAggregate::read`) are bounded by `u16`/`u8` widths or grow only with bytes actually present.
