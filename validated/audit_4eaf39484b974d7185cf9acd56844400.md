### Title
Unauthenticated OP_RETURN operator-credit tag in Payout tx allows front-running via SIGHASH_SINGLE|ANYONECANPAY malleability - ([File: core/src/verifier.rs])

### Summary
`update_finalized_payouts` attributes a withdrawal's reimbursement credit purely to whatever xonly-pubkey bytes are present in the first OP_RETURN output of whichever transaction is first observed spending the tracked withdrawal outpoint, with no signature covering that OP_RETURN output. Because the payout tx's input-0 witness is a `SIGHASH_SINGLE|ANYONECANPAY` Schnorr signature that only commits to input 0 and output 0, any outputs beyond index 0 (including the OP_RETURN carrying the operator's identity) are unauthenticated and freely rewritable by anyone who observes the signature.

### Finding Description
The binding under test: `withdrawals.payout_payer_operator_xonly_pk` for index `i` should equal the operator whose funds actually settled the withdrawal. In practice the code establishes a weaker binding: `payout_payer_operator_xonly_pk == whatever OP_RETURN bytes appear in the first tx observed by bitcoin_syncer spending withdrawal index i's tracked outpoint`.

`Verifier::update_finalized_payouts` fetches the payout txid tied to a withdrawal, locates the mined transaction, and reads the operator identity solely from `get_first_op_return_output` / `parse_op_return_data` with no signature check: [1](#0-0) 
It then persists this untrusted value directly: [2](#0-1) 

The persisted value is written via `update_payout_txs_and_payer_operator_xonly_pk`, which simply overwrites the `withdrawals` row for the matched `idx`: [3](#0-2) 

The only path back to a real operator's ability to claim reimbursement is `get_first_unhandled_payout_by_operator_xonly_pk`, which is a strict equality match on `payout_payer_operator_xonly_pk`: [4](#0-3) 
and `PayoutCheckerTask::run_once` only proceeds if that lookup returns a row for the operator's own key: [5](#0-4) 

Since the OP_RETURN content is not covered by the `SIGHASH_SINGLE|ANYONECANPAY` signature (which per the question's own description covers only input 0 and output 0), an attacker who observes the honest operator's Payout transaction (e.g., in the mempool, or by extracting the signature/outpoint from any publicly visible source) can reuse the same witness on input 0 and the same output 0, discard/replace all other outputs (specifically the OP_RETURN in output 2), and append their own chosen xonly pubkey bytes. If this attacker-modified transaction is mined first for that withdrawal outpoint, `update_finalized_payouts` will record the attacker-chosen pubkey as the payer, permanently orphaning the withdrawal for the real operator (whose key never again satisfies the equality check in `get_first_unhandled_payout_by_operator_xonly_pk`).

I was not able to fully verify from the index the precise source of BTC funding output 0 in `create_payout_txhandler` (i.e., whether input 0 alone fully funds the withdrawal amount, versus the honest operator supplying additional funding inputs) because repeated attempts to read `core/src/builder/transaction/operator_reimburse.rs` and `Operator::withdraw` in `core/src/operator.rs` failed in this session. This detail affects the attacker's cost: if input 0 alone (a pre-funded/bridge-controlled UTXO) covers output 0, the attack costs only Bitcoin fees; if the operator's own extra inputs fund the payout, an attacker would need to match that funding to win the race. Either way, the OP_RETURN's lack of cryptographic binding to input-0's signer is a genuine gap, but the exact attacker cost and full reproducibility could not be conclusively confirmed against the unread source in this pass.


### Impact Explanation
If exploited, the legitimate operator that fronted the withdrawal amount can never satisfy `get_first_unhandled_payout_by_operator_xonly_pk` for its own key for that withdrawal index, since the DB row is permanently stamped with the attacker's (unregistered) xonly pubkey; `is_payout_handled` never flips because no operator process polls for the attacker's key. This matches the "honest operator permanently unable to be reimbursed" Critical category, and is repeatable per withdrawal for any withdrawal transaction the attacker can observe before it confirms. [5](#0-4) 

### Likelihood Explanation
Preconditions are that the attacker observe the Payout transaction (mempool or otherwise) before it confirms and be able to get an alternative transaction confirmed first (a standard fee/mempool race), requiring no privileged role, key share, or collateral. The exact BTC cost to the attacker (whether they must also supply the withdrawal amount as funding, or only pay a competitive tx fee) could not be confirmed due to unread source files (`operator_reimburse.rs`, `Operator::withdraw`) in this session, which materially affects feasibility and should be re-verified with full file access.

### Recommendation
Bind the OP_RETURN operator-identity output to the same signature that authorizes input 0, e.g. by using `SIGHASH_ALL` (or `SIGHASH_SINGLE` covering an output index reserved for the OP_RETURN as well) so the operator claiming credit cannot be rewritten independently of the authorized input/output pair, or otherwise cryptographically bind the claimed operator identity to a signature the withdrawing party actually produced for that specific operator.

### Proof of Concept
Given the incomplete verification of `operator_reimburse.rs` in this session, a definitive PoC cannot be finalized here. It would require:
1. Constructing a deposit + withdrawal on regtest.
2. Having an honest operator produce and broadcast its Payout tx (capturing the mempool tx, input-0 witness, and output-0 details).
3. Building an attacker tx reusing input 0's witness and output 0 verbatim, replacing the OP_RETURN in output 2 with an attacker-chosen `XOnlyPublicKey`, and mining it first via `bitcoin_syncer`.
4. Asserting `Verifier::update_finalized_payouts` sets `withdrawals.payout_payer_operator_xonly_pk` to the attacker's key (not the honest operator's), and that `PayoutCheckerTask::run_once` for the honest operator returns `Ok(false)` indefinitely for that withdrawal index.

This should be re-confirmed against the actual contents of `core/src/builder/transaction/operator_reimburse.rs::create_payout_txhandler` and `core/src/operator.rs::Operator::withdraw` before treating the finding as fully proven.
