### Title
Silent, single-step rewrite of a repository's default remote URL from unverified GitHub API data - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
GitHub Desktop's `updateRemoteUrl()` will overwrite a local repository's `origin` (default) remote URL automatically, in a single step, whenever a background/foreground refresh of the associated `GitHubRepository` detects that the API's `clone_url` differs from what Desktop last cached — with no user confirmation, review, or opportunity to reject the change. This mirrors the "lack of a two-step process" bug class from the external report: a single privileged/irreversible action (repointing where a user's commits and pushes go) is executed immediately based on external, potentially attacker-influenced input, instead of being staged and requiring explicit user acceptance.

### Finding Description
`updateRemoteUrl()` compares the repository's current git remote URL against the `clone_url` field of an `IAPIRepository` object fetched from the GitHub/GHES API, and if the protocol matches and the previously-cached URL matches the remote, it directly calls `gitStore.setRemoteURL()` to rewrite `origin` — no dialog, no diff view, no opt-in: [1](#0-0) 

This function is invoked from `repositoryWithRefreshedGitHubRepository()`, which is exercised as part of ordinary repository refresh flows (e.g., selecting a repository, or fetching): [2](#0-1) 

The `apiRepo` object passed in comes straight from `api.fetchRepository(owner, name)`, i.e. the GitHub.com or GitHub Enterprise Server response for that repo: [3](#0-2) 

The underlying git operation, `setRemoteURL`, is a raw `git remote set-url` with no additional safety net: [4](#0-3) 

The existing guard rails (`protocolsMatch`, `remoteUrlUnchanged`, `!urlsMatch`) are heuristics meant to avoid clobbering a *manually* customized remote — they do not authenticate or validate that the new `clone_url` is trustworthy. Since GitHub Enterprise Server endpoints are user/organization-controlled hosts, and repository rename/transfer/ownership-change events (or a compromised/malicious GHES instance, or a MITM'd/spoofed API response for an untrusted GHES host) can change `clone_url` freely, this path silently redirects the local `origin` remote to a new destination the moment those three conditions line up. There is no analog to "propose, then accept" — the rewrite is unilateral and immediate, exactly the pattern the external report calls out as the root cause (`transferOwnership()` completing in one call with no owner-verifies-target step).

### Impact Explanation
If a `clone_url` served by an attacker-influenced source (a malicious/compromised GHES server the user has already added as an account, or an API response manipulated in transit for such a non-pinned enterprise endpoint) differs from Desktop's cached URL but keeps the same protocol, Desktop will silently repoint `origin` to that URL. Because the corrupted value is exactly what a user's next `git push`/`git fetch`/`git pull` targets, this is a silent corruption of where the user's commits go: subsequent pushes could be silently redirected to an attacker-controlled repository (leaking private code, or making it look like a push succeeded when it went elsewhere), and subsequent fetches/pulls could pull attacker-controlled history into the user's working copy without any warning banner beyond what a normal remote change would show (which is none, since no UI surfaces this).

### Likelihood Explanation
This requires the user to have already added a GitHub Enterprise account whose API responses are attacker-influenced (compromised/malicious GHES host, or a network position able to tamper with that host's TLS-terminated responses) — no local access, no admin rights, and no unusual user action beyond Desktop's normal background repository refresh/fetch behavior, which happens automatically. The three-condition gate (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`) narrows but does not eliminate the window: an attacker who controls the API response merely needs to keep the scheme identical (e.g. `https`) and ensure the currently-cached `cloneURL` still matches the local remote (the common, unmodified case) to trigger the rewrite.

### Recommendation
- Short term: Convert this from an automatic rewrite into a two-step, user-confirmed action — surface a prompt/dialog showing the old and new remote URLs and require explicit user acceptance before calling `gitStore.setRemoteURL()`, mirroring the transferOwnership recommendation of "propose, then accept."
- Additionally, treat `clone_url` from non-dotcom (GHES) endpoints with extra scrutiny (e.g., require the same host, or flag any URL that doesn't already match `gitHubRepository.htmlURL`'s host) rather than relying solely on protocol-equality heuristics.
- Long term: Document and audit all locations where Desktop mutates local git configuration (remotes, upstreams, HEAD refs) automatically based on API data, and require explicit consent for state changes that affect where a user's data is pushed.

### Proof of Concept
1. User adds a GitHub Enterprise Server account in Desktop for `https://ghes.attacker-influenced.example` and clones/opens a repository whose `origin` matches the API's `clone_url` at that time (satisfies `remoteUrlUnchanged`).
2. The GHES server (compromised, or an admin turned malicious, or intercepted for an endpoint the client trusts) begins returning a modified `clone_url` for `repos/{owner}/{name}` — same `https` scheme, but pointing at a different repository path/host under the attacker's control.
3. On the next background repository refresh or fetch (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`), Desktop detects `protocolsMatch === true`, `remoteUrlUnchanged === true`, `urlsMatch === false`, and calls `gitStore.setRemoteURL('origin', <attacker_clone_url>)` with no prompt.
4. The user's next `git push`/`fetch` silently targets the attacker-specified remote.

Note: I could not fully trace `withRefreshedGitHubRepository`'s exact caller list within the tool budget (only found matches within `app-store.ts`, but not the full body/definition); however, `repositoryWithRefreshedGitHubRepository` is directly invoked from `_selectRepositoryRefreshTasks`, confirming the automatic (non-user-gated) trigger path is real.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  /** Fetch a repo by its owner and name. */
  public async fetchRepository(
    owner: string,
    name: string
  ): Promise<IAPIFullRepository | null> {
    try {
      const response = await this.ghRequest('GET', `repos/${owner}/${name}`)
      if (response.status === HttpStatusCode.NotFound) {
        log.warn(`fetchRepository: '${owner}/${name}' returned a 404`)
        return null
      }
      return await parsedResponse<IAPIFullRepository>(response)
    } catch (e) {
      log.warn(`fetchRepository: an error occurred for '${owner}/${name}'`, e)
      return null
    }
  }

/** Changes the URL for the remote that matches the given name  */
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
