## Finding

### Title
Payout tx OP_RETURN operator attribution is unauthenticated, letting an attacker self-fund a withdrawal and credit an operator that never fronted it - ([File: core/src/verifier.rs], [File: core/src/operator.rs])

### Summary
The `Payout` transaction's `OP_RETURN` output (the only artifact used to decide which operator gets reimbursed) is not bound by any signature from the named operator. Because the withdrawal input is signed by the user with `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`, an attacker who owns the withdrawal (or who can observe the signature) can build and broadcast their own version of the payout tx — funding it entirely with their own UTXOs and writing an arbitrary operator's x-only pubkey into the `OP_RETURN` — completely bypassing `Operator::withdraw`'s profitability/verification checks. The verifier's Bitcoin sync (`update_finalized_payouts`) blindly trusts this `OP_RETURN` and attributes the payout to that operator, whose own automation (`PayoutCheckerTask` → `send_asserts`) will then proceed to claim reimbursement for a payout it never funded.

### Finding Description
The broken binding: `payout_op_xonly_pk` (parsed from the `Payout` tx's `OP_RETURN`, as read by `get_payout_info_from_move_txid` and compared in `Operator::send_asserts`) should equal *"the operator that actually fronted this specific withdrawal via a `withdraw()` call it signed"*. In the current code these two values are never actually bound together.

- `create_payout_txhandler` [1](#0-0)  builds the `Payout` tx with input 0 = the user's withdrawal UTXO (spent with `KeySpend`, using only the user's own signature) and appends an `OP_RETURN` containing an arbitrary `operator_xonly_pk` parameter — nothing cryptographically ties that pubkey to the actual funder of the transaction.
- The user's signature on input 0 uses `SinglePlusAnyoneCanPay` [2](#0-1) , meaning it commits only to output index 0 and does not cover any additional funding inputs, the anchor output, or the `OP_RETURN` output. Any party holding this signature can freely assemble a different transaction with their own funding inputs and their own choice of `OP_RETURN` payload.
- `Operator::withdraw` performs `is_profitable`, signature and verification-address checks [3](#0-2)  only inside the gRPC code path. None of these checks exist on-chain, so an attacker who constructs and broadcasts the tx directly bypasses all of them.
- Bitcoin sync (`update_finalized_payouts`) accepts whatever `OP_RETURN` pubkey is present in the tx that spends the registered `withdrawal_utxo` and records it verbatim: `let operator_xonly_pk = op_return_output.and_then(...).and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());` followed by `update_payout_txs_and_payer_operator_xonly_pk` [4](#0-3) .
- The victim/beneficiary operator's own automation (`PayoutCheckerTask`) picks up *any* unhandled payout attributed to its own key with no further validation of who paid it [5](#0-4) , then proceeds through `handle_finalized_payout` and eventually `Operator::send_asserts`, which only re-checks `payout_op_xonly_pk != kickoff_data.operator_xonly_pk` [6](#0-5)  — i.e., it checks that the OP_RETURN matches the kickoff's own operator, which trivially succeeds since the attacker wrote that operator's key into the OP_RETURN.
- `Verifier::is_kickoff_malicious` performs the same check and nothing more [7](#0-6)  — it validates the OP_RETURN-vs-kickoff match and the committed payout blockhash, but never validates the actual source of the payout tx's funding inputs.

Exploit flow: the attacker calls `withdraw()` on the Citrea bridge contract for their own withdrawal, signs the dust UTXO input with `SIGHASH_SINGLE|ANYONECANPAY`, then constructs a raw transaction (never touching any operator's gRPC endpoint) that: spends that dust UTXO to themselves (output 0), adds their own funding input(s) to cover fees/amount, and appends an `OP_RETURN` containing operator O's x-only pubkey. They broadcast it directly to the Bitcoin network. Bitcoin sync records `payout_payer_operator_xonly_pk = O`. O's automation observes the unhandled payout attributed to itself and proceeds through kickoff, asserts, and eventual `Reimburse`, crediting O with bridge collateral for a withdrawal O never fronted.

### Impact Explanation
This directly matches the Critical category "an operator reimbursed for a payout it never funded." The operator's collateral round proceeds normally and nothing is burned, but the operator (or a colluding operator working with the withdrawing user) is credited reimbursement funds without ever having fronted real liquidity to the withdrawing user, bypassing `is_profitable`/fee/verification checks entirely. This is repeatable per withdrawal and per operator: any withdrawing user can pick any registered operator to receive the false credit, and a colluding operator can systematically avoid ever fronting capital for withdrawals while still collecting the reimbursement, undermining the core economic assumption that operators risk their own BTC to earn reimbursement.

### Likelihood Explanation
No privileged role is required. The attacker only needs to be the withdrawing user (or possess/observe the user's `SinglePlusAnyoneCanPay` signature) and be able to broadcast a Bitcoin transaction with additional self-funded inputs — capabilities explicitly granted to "unprivileged attackers" per the threat model. The attack requires no majority hashrate, key compromise, or verifier/operator collusion beyond the passive, automatic behavior of the target operator's existing automation (`PayoutCheckerTask`), which unconditionally trusts DB-recorded OP_RETURN attribution. Cost to the attacker is just their own funding of the withdrawal output plus fees — fully repeatable across all deposits/withdrawals and any operator.

### Recommendation
Bind the OP_RETURN operator attribution to an authenticated action by that operator, e.g., require the operator to co-sign the `Payout` tx (or a commitment covering all inputs/outputs including the OP_RETURN) rather than relying purely on an unauthenticated OP_RETURN payload; alternatively, require verifiers/operators to additionally validate that the payout tx's non-withdrawal-input funding traces back to the claimed operator (e.g., via a known operator-controlled UTXO or a signature from the operator's key over the full transaction) before treating a payout as attributable to that operator for reimbursement purposes.

### Proof of Concept
`cargo test` plan (regtest, no mainnet/live Citrea, using existing e2e harness in `core/src/test`):
1. Run a normal deposit + Citrea withdrawal registration (as in `deposit_and_withdraw_e2e.rs`) to obtain a `withdrawal_utxo`, `dust_utxo`, and user signature (`sig`) with `SinglePlusAnyoneCanPay`, targeting Operator O.
2. Instead of calling `operator0.withdraw(...)` (the gRPC path), directly build a raw transaction using `create_payout_txhandler`-equivalent construction: input 0 = `dust_utxo` with the user's `sig`, additional funding input(s) taken from a separate wallet/key not belonging to O, output 0 = payout to the user, `OP_RETURN` = O's `xonly_public_key`.
3. Broadcast this transaction via the regtest RPC directly (bypassing `Operator::withdraw`), and mine blocks to finality depth.
4. Assert `db.get_payout_info_from_move_txid(...)` returns `Some(O.xonly_public_key)` for this move txid.
5. Assert O's `PayoutCheckerTask`/kickoff automation proceeds (kickoff tx broadcast, `send_asserts` succeeds without error) — i.e., assert `payout_op_xonly_pk == kickoff_data.operator_xonly_pk` holds and reimbursement eventually completes — while asserting O never called `withdraw()` nor funded any input of the payout transaction (verify none of O's known UTXOs/wallet keys were spent as inputs).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
