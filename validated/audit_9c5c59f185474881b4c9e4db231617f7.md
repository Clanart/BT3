Based on the code, this is a legitimate finding, but with an important technical correction to the premise: `Path.join` itself does not resolve symlinks (it's a purely lexical string operation), so `Path.join(repository.path, file.path)` will not "resolve through" a symlink on its own. The actual risk is that once this lexically-joined path is handed to filesystem/OS calls (`pathExists`, `spawn`, shell "open"), the **OS** transparently follows any symlink present in a leading path component on disk. Since none of the code in this call chain validates that the resolved real path stays under `repository.path`, a pre-existing tracked symlink directory can redirect these operations outside the repo.

## Finding Description

`PullRequestFilesChanged.onFileContextMenu` builds `fullPath` by simple string concatenation: [1](#0-0) 

It only gates the "Open in External Editor" / "Reveal in File Manager" / "Open with Default Program" menu items on `pathExists(fullPath)`: [2](#0-1) 

`fullPath` is then passed straight to `dispatcher.openInExternalEditor(fullPath)`, which eventually calls `launchExternalEditor`: [3](#0-2) [4](#0-3) 

`launchEditor`'s only existence check is on the **editor binary path** (`editorPath`), not on `fullPath`/containment of `fullPath` under `repository.path`. `fullPath` (potentially escaping the repo through a symlink) is passed as a raw `spawn` argument to the editor.

Critically, the `files`/`CommittedFileChange[]` shown in this dialog come from `getBranchMergeBaseChangedFiles`, which is a pure `git diff --merge-base` computation between two refs — **it does not check out the PR branch onto disk**: [5](#0-4) 

This means `file.path` strings shown/operated on in this dialog are taken from the PR branch's git tree, but `pathExists`/`fullPath` are evaluated against whatever is *actually checked out* in the working directory at `repository.path`. If the currently checked-out working tree already contains a tracked symlinked directory (e.g., previously merged/checked out from an earlier malicious commit) whose name matches a leading path segment referenced by the PR diff (e.g. `link/secret.txt`), then `Path.join(repository.path, "link/secret.txt")` produces a path that is lexically inside the repo, but which the OS will resolve through the on-disk `link` symlink to a location outside `repository.path` when `pathExists`, `spawn`, or the shell "open" handler actually touches it.

Git's own checkout-time symlink protections (`has_symlink_leading_path` in `unpack-trees.c`) only guard actual `git checkout`/`read-tree` operations that would *write* a new file through a symlinked path; they do not apply here because Desktop is not invoking git to materialize this path — it's doing its own `Path.join` + Node `fs`/`spawn` access on a path that was never validated for containment.

## Impact Explanation

If exploited, GitHub Desktop can be induced to open (via the configured external editor, the OS "open with default program" handler, or reveal-in-file-manager) an arbitrary file located outside the repository whose relative-to-symlink-target name is attacker-chosen (the attacker names it after known sensitive files, e.g. SSH keys, cloud credential files, `.netrc`, etc.). This is an out-of-repo file read/disclosure to the user's own tooling and, depending on the OS default-handler behavior for the chosen extension, could have further consequences. `isSafeFileExtension` mitigates the most direct "double-click executes" risk for `OpenWithDefaultProgramLabel` since it only inspects the extension of the attacker-controlled `file.path` string: [6](#0-5) 

## Likelihood Explanation

Exploitation requires two attacker-controllable conditions to line up:
1. A tracked symlinked directory pointing outside the repo must already exist on disk in the user's currently checked-out working tree (achievable if the same attacker previously got a symlink-adding commit merged/checked out, since git legitimately supports tracked symlinks and normal checkout of them is not itself blocked).
2. The PR being previewed (via "Open Pull Request" dialog, without requiring the reviewer to actually check it out) must reference a file path with that same leading directory name.

This is a real, non-trivial gap (missing path-containment validation on `fullPath` before all disk operations in `pull-request-files-changed.tsx` and `launch.ts`), but requires a specific setup (a previously checked-out malicious symlink) rather than being exploitable purely by a single fetched/previewed PR branch in isolation.

## Recommendation

- After constructing `fullPath` in `pull-request-files-changed.tsx`, resolve it with `fs.realpath`/`fs.realpathSync` and verify the resolved path still starts with the resolved `repository.path` before enabling any of `RevealInFileManagerLabel`, `openInExternalEditor`, or `OpenWithDefaultProgramLabel` actions.
- Add the same containment check as a defense-in-depth guard in `launchExternalEditor`/`launchCustomExternalEditor` in `app/src/lib/editors/launch.ts`, rejecting any `fullPath` that resolves outside the intended repository root.

## Proof of Concept

1. Create a test repository at `/tmp/repo` and commit a tracked symlink `/tmp/repo/link -> /tmp/outside` (`/tmp/outside` exists and contains `secret.txt`), then check this commit out (making `link` a real on-disk symlink).
2. Simulate a PR "files changed" list containing a `CommittedFileChange` with `path: 'link/secret.txt'` (as would come from `getBranchMergeBaseChangedFiles` diffing against a branch that has `link/secret.txt` in its tree, without checking that branch out).
3. Call the same logic as `onFileContextMenu`: `Path.join(repository.path, 'link/secret.txt')` → `/tmp/repo/link/secret.txt`.
4. Confirm `pathExists()` returns `true` (following the symlink) and that `fs.realpathSync('/tmp/repo/link/secret.txt')` resolves to `/tmp/outside/secret.txt`, outside `repository.path`.
5. Confirm `launchExternalEditor` would spawn the editor with this out-of-repo real path as its argument, with no containment check performed anywhere in the call chain.

export async function getBranchMergeBaseChangedFiles(
  repository: Repository,
  baseBranchName: string,
  comparisonBranchName: string,
  latestComparisonBranchCommitRef: string

  const baseArgs = [
    'diff',
    '--merge-base',
    baseBranchName,
    comparisonBranchName,
    '-C',
    '-M',
    '-z',
    '--raw',
    '--numstat',
    '--',
  ]

  const mergeBaseCommit = await getMergeBase(
    repository,
    baseBranchName,
    comparisonBranchName
  )

  if (mergeBaseCommit === null) {
    return null
  }

  const result = await git(
    baseArgs,
    repository.path,
    'getBranchMergeBaseChangedFiles'
  )

  return parseRawLogWithNumstat(
    result.stdout,
    `${latestComparisonBranchCommitRef}`,
    mergeBaseCommit
  )
}
