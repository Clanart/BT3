### Title
Git-hooks sandbox is silently disabled because `GIT_CONFIG_PARAMETERS` from the hooks proxy is clobbered by the trampoline environment, letting repo-controlled hooks run with the full, unfiltered process environment - (File: app/src/lib/git/core.ts)

### Summary
Desktop's "hooks environment" feature is meant to run Git hooks (`pre-commit`, `post-checkout`, `post-merge`, etc.) through an isolated proxy that strips sensitive variables (`GIT_ASKPASS`, `GIT_SSH_COMMAND`, `GIT_USER_AGENT`) before handing an explicitly-curated `safeEnv` to the hook process. This isolation is implemented by redirecting `core.hooksPath` to a temp directory of stub hooks via `GIT_CONFIG_PARAMETERS`, computed in `withHooksEnv`. However, in `git()` (app/src/lib/git/core.ts) the final environment is assembled as `{ TERM, ...opts.env, ...hooksEnv, ...env }` where `env` comes from `withTrampolineEnv`, which is invoked without the `customEnv` parameter and therefore computes its own, independent `GIT_CONFIG_PARAMETERS` value (only containing `credential.helper=...`) based on `process.env`, not on `hooksEnv`. Because `env` is spread last, its `GIT_CONFIG_PARAMETERS` key overwrites the one produced by `hooksEnv`, silently discarding the `core.hooksPath=<tmpHooksDir>` override that was supposed to redirect hook execution into the sandboxed proxy.

### Finding Description
- `withHooksEnv` (app/src/lib/hooks/with-hooks-env.ts:29-96) builds a `GIT_CONFIG_PARAMETERS` string of the form `'core.hooksPath=<tmp>'` (optionally prefixed with any pre-existing `GIT_CONFIG_PARAMETERS`) so that the actual `git` invocation runs hooks through `tmpHooksDir`, where stub binaries forward execution to `createHooksProxy` (app/src/lib/hooks/hooks-proxy.ts).
- `hooks-proxy.ts` explicitly filters the environment handed to the real hook process down to `GIT_`/`GITHEAD_`-prefixed variables minus an `excludedEnvVars` set (`GIT_ASKPASS`, `GIT_SSH_COMMAND`, `GIT_USER_AGENT`, `GIT_CONFIG_PARAMETERS`-leaking vars, etc.) — this is the actual "guard" the feature provides against untrusted, repository-supplied hook scripts.
- `withTrampolineEnv` (app/src/lib/trampoline/trampoline-environment.ts:93-147) independently computes its own `GIT_CONFIG_PARAMETERS` (adding `credential.helper=` / `credential.helper=desktop`), reading only `customEnv?.['GIT_CONFIG_PARAMETERS'] ?? process.env['GIT_CONFIG_PARAMETERS']`.
- In `git()` (app/src/lib/git/core.ts:276-296), `withTrampolineEnv` is called as `withTrampolineEnv(async env => {...}, path)` — with **no `customEnv` argument** — so it never sees `hooksEnv`'s value. The final env object is built as:
```
env: { TERM: 'dumb', ...opts.env, ...hooksEnv, ...env }
```
Since object spread makes later keys win, the trampoline-produced `GIT_CONFIG_PARAMETERS` (credential helper only) overwrites the hooks-produced `GIT_CONFIG_PARAMETERS` (which contained `core.hooksPath=<tmp>`), for every single `git` invocation that both hooks *and* trampoline are active for (i.e., essentially all of them, since `withHooksEnv` wraps `withTrampolineEnv` in the same call chain). [1](#0-0) [2](#0-1) [3](#0-2) 

As a result, the `core.hooksPath` redirection never reaches the real `git` process, so Git falls back to invoking hooks from the repository's *actual* hooks directory (its normal `.git/hooks`, or a `core.hooksPath` value the repository's own config might set) directly — bypassing the isolated proxy and its `safeEnv` filtering entirely. The hook then inherits the full process environment used for the top-level Git command, including `GIT_ASKPASS`, `GIT_SSH_COMMAND`, `GIT_USER_AGENT`, and the actual `GIT_CONFIG_PARAMETERS` describing `credential.helper=desktop` — precisely the values `excludedEnvVars` in `hooks-proxy.ts` was designed to keep away from hook scripts. [4](#0-3) [5](#0-4) 

This mirrors the report's bug class exactly: a security-relevant guard (`whenNotPaused` in the original report; here, "route hook execution through the restricted-env proxy") exists on the "normal" path but is silently absent/overwritten on the actual execution path, so the protected operation (running a Git hook found in a repository) proceeds without the intended restriction.

### Impact Explanation
Git hooks are executable content that can be delivered inside a repository the user opens or has already cloned (via `.git/hooks/*` in a repository archive/bundle, a bare/local clone, a repository template, or a repo whose `.git/config` already sets `core.hooksPath` to an in-tree directory of scripts). Desktop's hooks-proxy feature exists specifically to sandbox that execution and keep credential/auth-related environment variables (`GIT_ASKPASS`, `GIT_SSH_COMMAND`, `GIT_USER_AGENT`) away from these scripts. Because the intended override is clobbered, a hook script from such a repository instead runs with the full unrestricted environment of the invoking `git` process, including the credential-helper configuration Desktop injects for authentication (`credential.helper=desktop`) and (depending on other env inheritance) askpass/SSH command paths. A malicious hook could invoke `git credential fill`/the `desktop` credential helper, or otherwise leverage the unrestricted environment, to obtain credentials or otherwise act outside the sandboxed context the feature promises, undermining the confidentiality guarantee the feature was built for.

### Likelihood Explanation
The bug is deterministic and unconditional: it triggers on every `git()` call that has both `interceptHooks` set and hooks present, since `withTrampolineEnv` is always called without `customEnv` in `core.ts`. Any repository with hooks (planted via cloning a bare/mirror repo, opening a pre-existing local clone, or via `core.hooksPath` set in a tracked/opened `.git/config`) is affected — no special user action beyond opening/using such a repository in Desktop is required, making this a reliable, repository-controlled bypass rather than a race condition or edge case.

### Recommendation
Ensure the `GIT_CONFIG_PARAMETERS` values produced by `withHooksEnv` and `withTrampolineEnv` are composed instead of overwritten — e.g., pass `hooksEnv` as the `customEnv` argument to `withTrampolineEnv` (so its `existingGitEnvConfig` calculation includes the hooks-path config), or merge the two `GIT_CONFIG_PARAMETERS` strings explicitly before constructing the final `env` object in `git()`. Add a regression test asserting that the final environment passed to `exec()` contains both the `core.hooksPath=<tmp>` and `credential.helper=desktop` config fragments simultaneously.

### Proof of Concept
1. In app/src/lib/git/core.ts, instrument (or log) the `env` object right before `exec(args, path, { ...opts, env: {...} })` for any command that goes through `withHooksEnv`/`withTrampolineEnv` with hooks present in the target repo (e.g. `createCommit`, which sets `interceptHooks: ['pre-commit', ...]`).
2. Observe that `GIT_CONFIG_PARAMETERS` in the logged env only contains `'credential.helper=' 'credential.helper=desktop'` and does **not** contain `'core.hooksPath=<tmpHooksDir>'`, confirming the hooksEnv value was overwritten by the trampoline-computed value.
3. Confirm empirically: place an executable `pre-commit` hook directly in a test repository's `.git/hooks/pre-commit` that dumps `env` to a file, then trigger a commit from Desktop. The dumped environment will contain the full, unfiltered process environment (e.g. `GIT_ASKPASS`, real `GIT_CONFIG_PARAMETERS` with credential helper config) rather than the reduced `safeEnv` the proxy (`hooks-proxy.ts`) is designed to hand to hooks — demonstrating the sandbox never engaged for that invocation.

Note: I could not execute this against a live build to directly capture stdout logs (sandboxed to static code reading), but the control-flow evidence — the unconditional key-overwrite via object spread order in `app/src/lib/git/core.ts:276-295` combined with the independent, non-composing `GIT_CONFIG_PARAMETERS` computations in `with-hooks-env.ts` and `trampoline-environment.ts` — is unambiguous and directly supports the finding.

      customEnv?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    // The code below assumes a few things in order to manage SSH key passphrases
    // correctly:
    // 1. `withTrampolineEnv` is only used in the functions `git` (core.ts)
    // 2. Those two functions always thrown an error when something went wrong,
    //    and just return a result when everything went fine.
    //
    // With those two premises in mind, we can safely assume that right after
    // `fn` has been invoked, we can store the SSH key passphrase for this git
    // operation if there was one pending to be stored.
    try {
      return await fn({
        DESKTOP_PORT: await trampolineServer.getPort(),
        DESKTOP_TRAMPOLINE_TOKEN: token,
        GIT_ASKPASS: '',
        // This warrants some explanation. We're configuring the
        // credential helper using environment variables rather than
        // arguments (i.e. -c credential.helper=) because we want commands
        // invoked by filters (i.e. Git LFS) to be able to pick up our
        // configuration. Arguments passed to git commands are not passed
        // down to filters.
        //
        // We're using the undocumented GIT_CONFIG_PARAMETERS environment
        // variable over the documented GIT_CONFIG_{COUNT,KEY,VALUE} due
        // to an apparent bug either in a Windows Python runtime
        // dependency or in a Python project commonly used to manage hooks
        // which isn't able to handle the blank environment variables we
        // need when using GIT_CONFIG_*.
        //
        // See https://github.com/desktop/desktop/issues/18945
        // See https://github.com/git/git/blob/ed155187b429a/config.c#L664
        GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'credential.helper=' 'credential.helper=desktop'`,

        GIT_USER_AGENT: await GitUserAgent(),
        ...sshEnv,
      })
