### Title
Unauthenticated third-party payments to deterministic internal offset addresses are misclassified as Change/Branch/Forwarded outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the external report is "a security-relevant field is validated only for format (http/https scheme), never for provenance against the server's own origin, so attacker-supplied data steers a sensitive flow." The analog in Serai's Bitcoin wallet is output classification: `Scanner` decides whether a received output is `External`, `Branch`, `Change`, or `Forwarded` purely by whether the `script_pubkey` exists in its `scripts` map keyed on registered offsets — it never validates that a Change/Branch/Forwarded output was actually created by Serai itself. Since the offsets for the internal output types are deterministic, publicly computable constants, any unprivileged party can send a Bitcoin transaction paying to an internal-type address and have it reported under the wrong `OutputType`.

### Finding Description
`Scanner::new`/`register_offset` build a `HashMap<ScriptBuf, Scalar>` from offset to script (`networks/bitcoin/src/wallet/mod.rs:153-196`). `scan_transaction` matches incoming outputs solely on `self.scripts.get(&output.script_pubkey)` and returns a `ReceivedOutput` carrying that offset (`mod.rs:199-214`). In `processor/src/networks/bitcoin.rs`, the internal offsets are fixed public values: `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch" | b"change" | b"forward")` (`bitcoin.rs:308-344`). Given the group key (which is necessarily public — it appears in every multisig output on-chain), anyone can compute `key + G*offset`, adjust to an even Y point exactly as `register_offset` does (`mod.rs:180-195`), and derive the Branch/Change/Forwarded P2TR addresses. `get_outputs` then labels the attacker-created output via `kinds[offset_repr]` (`bitcoin.rs:687-699`). Only `External` outputs get `data`/instruction processing (`bitcoin.rs:730-735`), so a payment crafted to land on an internal-type script is reported as received yet is processed under internal semantics rather than as a crediting deposit.

### Impact Explanation
Outputs an attacker causes to be classified as `Change`/`Branch`/`Forwarded` bypass the `External` instruction/extraction path. A victim/integration that relies on `OutputType::External` for deposit crediting will report the funds as received (they are scanned and emitted) but never generate the crediting instruction — i.e., funds reported received that are not spendable/creditable under the expected flow. Conversely, an attacker can inject a `Forwarded`-typed output to interfere with forwarding/rotation bookkeeping in the processor. This mirrors the Grav flaw: the address format is "valid" (it is in the scripts map), but the provenance — who created the output — is never checked.

### Likelihood Explanation
Reachable by any unprivileged party: all inputs are public — the group key from the chain, the fixed DST `KEY_DST`, and the deterministic `hash_to_F` offsets. The attacker only needs to send an ordinary Bitcoin transaction to the derived P2TR script; no collusion, no malicious validator, and no integrator misuse is required.

### Recommendation
Authenticate provenance, not just the script: e.g., bind internal-type outputs to Serai-created change (only accept `Change`/`Forwarded` outputs in transactions the multisig itself signed, tracked by prevout/txid), or require an explicit internal marker/witness commitment for non-External classifications. At minimum, document and enforce that outputs to internal offset scripts arriving in transactions not authored by the multisig are treated as `External` (or quarantined).

### Proof of Concept
1. Observe any multisig P2TR output on-chain to learn `group_key` (x-only, even-Y).
2. Compute `offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change")`, increment until `group_key + G*offset` is even (matching `register_offset`'s loop in `mod.rs:184-195`), and derive `p2tr_script_buf(group_key + G*offset)`.
3. Send a transaction paying that script. `scan_transaction` matches it (`mod.rs:205`), `get_outputs` classifies it as `OutputType::Change` and attaches no `data` (`bitcoin.rs:695,732-735`). The output is emitted as a received internal-change output despite being attacker-created, corrupting deposit accounting.

Uncertainty note: the processor-side consequences (exact Plan construction for mislabeled outputs) live outside the in-scope files; the in-scope code provably performs the misclassification, and `get_outputs`'s `kinds[offset]` lookup plus the External-only data path demonstrate the divergent handling.
