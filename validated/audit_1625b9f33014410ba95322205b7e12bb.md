## Title
`revealInFileManager` performs unguarded `Path.join` with attacker‑influenced file paths, unlike the sibling `resolveWithin` guard in `dispatcher.ts` - (File: `app/src/lib/app-shell.ts`)

### Summary
This is the same *"fix applied to one code path but not to the sibling path"* pattern as the Sherlock report (fix landed for `CurveSpell` but not `ConvexSpell`). GitHub Desktop has a dedicated path‑traversal guard, `resolveWithin`, that is explicitly used when opening a file coming from a URL‑triggered action, but the much more commonly used file‑reveal helper `revealInFileManager` still does a raw `Path.join(repository.path, path)` with no traversal check at all.

### Finding Description
`app/src/ui/dispatcher/dispatcher.ts`'s `openRepositoryFromUrl` treats a filepath coming from an `x-github-client://` deep link as untrusted: it rejects absolute paths and resolves the remainder with `resolveWithin`, which normalizes the path, resolves symlinks with `realpath`, and rejects anything that escapes the repository root: [1](#0-0) 

The `resolveWithin` helper itself is careful to defend against `..` traversal, null bytes, and symlink escapes: [2](#0-1) 

However, `revealInFileManager` — the function invoked from numerous UI surfaces (changes list, commit history, unmerged/conflicted files, PR "Files changed" view, and Copilot conflict dialog context menus) — never uses this guard. It simply joins the repository root with a caller‑supplied relative path and hands the result to the OS shell: [3](#0-2) 

The `path` argument here originates from file entries that are not necessarily constrained by a real git checkout: e.g. the "Files changed" list for an open pull request is built directly from GitHub API diff data, and diff/tree entries can in principle contain path separators or `..` segments that never actually get materialized on disk by `git checkout` (git's own tree/index validation only protects real checkouts, not string-only file lists surfaced through the API or through unmerged/conflict metadata). Because `revealInFileManager` performs no normalization or root‑containment check, a crafted `path` value ending in `..\..\..\AppData\Roaming\evil.exe`‑style segments would resolve outside the repository and be handed to `shell.showItemInFolder`, the exact same class of "escape via unguarded `Path.join`" that `resolveWithin` was written to close in the dispatcher.

### Impact Explanation
`shell.showItemInFolder` reveals (and on some platforms pre‑selects/executes shell integration for) an arbitrary filesystem location chosen by the attacker-controlled string, rather than the intended repository file. This is a "file read/interaction outside the repo" primitive driven by attacker‑controlled data (a malicious PR's file list, or a maliciously crafted conflict/status entry), matching the "file write or read outside the repo" impact category. It does not require local/physical access, admin rights, or any credential.

### Likelihood Explanation
The guard (`resolveWithin`) already exists and is proven to be considered necessary by the Desktop team for exactly this kind of attacker‑supplied path — but it was only wired up for the deep‑link path‑opening flow, not for the much broader `revealInFileManager` surface that is reachable from six+ different UI components (`filter-changes-list.tsx`, `selected-commits.tsx`, `unmerged-file.tsx`, `pull-request-files-changed.tsx`, `copilot-conflicts-dialog.tsx`). This mirrors the audited bug precisely: the mitigation exists and was applied to one call site (`ConvexSpell`/dispatcher) while an analogous call site (`CurveSpell`/`app-shell.ts`) was missed.

### Recommendation
Route `revealInFileManager` (and any other consumer that joins `repository.path` with an externally sourced relative path) through `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` before calling `shell.showItemInFolder`, rejecting (and logging) any path that resolves outside the repository root, exactly as `dispatcher.ts`'s `openRepositoryFromUrl` already does.

### Proof of Concept
1. Open a pull request (or any UI list rendered from `IStatusEntry`/PR file JSON) whose file list contains an attacker‑controlled entry such as `"..\\..\\..\\..\\AppData\\Roaming\\Microsoft\\Windows\\Start Menu\\Programs\\Startup\\evil.lnk"`.
2. User right‑clicks the entry and selects "Show in Explorer/Finder", which calls `revealInFileManager(repository, path)`. [3](#0-2) 
3. `Path.join(repository.path, path)` resolves to a location entirely outside the repository (no `resolveWithin`/root‑containment check is performed, unlike the dispatcher's equivalent flow), and the OS file manager reveals/interacts with that external path instead of a repository file.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
