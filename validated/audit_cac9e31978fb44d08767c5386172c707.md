### Title
Blame proofs publicly disclose the ECDH decryption key, letting any third party recover the DKG secret share in the blamed message — ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The PedPoP DKG encrypts each secret share under a per-message key combined with ECDH against the recipient's published encryption key. When a recipient accuses a sender, it emits an `EncryptionKeyProof` that contains `key` — the raw ECDH shared secret for that message — plus a DLEq proving it is well formed. Because `AdditionalBlameMachine::new` / `decrypt_with_proof` are explicitly designed to be evaluable by anyone ("regardless of if the caller was a member of the DKG protocol"), the blame proof is a self-contained, publicly verifiable decryption oracle: any unprivileged observer who sees the blame proof and the (already public, on-protocol) encrypted share can decrypt the plaintext `SecretShare<C::F>` themselves. This mirrors the reported class: a resource intended for a restricted party (the blamed share's intended recipient) is exposed to unauthenticated parties alongside the data needed to use it.

### Finding Description
`Encryption::decrypt` constructs the blame artifact as `EncryptionKeyProof { key, dleq }`, where `key = ecdh::<C>(&self.enc_key, msg.key)` is the shared secret for that message [1](#0-0) . `Decryption::decrypt_with_proof` then verifies the DLEq against the decryptor's registered public key and directly applies `cipher::<C>(context, &proof.key)` to recover the plaintext share [2](#0-1) . `AdditionalBlameMachine::new` builds this `Decryption` context purely from the participants' public commitment messages and states it can be run by non-members [3](#0-2) . In the processor, the blame proof is serialized into `ProcessorMessage::InvalidShare` and later re-parsed from untrusted bytes by any node evaluating `CoordinatorMessage::VerifyBlame` [4](#0-3) [5](#0-4) . Nothing authenticates or restricts who may read `proof.key`; `EncryptionKeyProof::read` accepts it verbatim [6](#0-5) . The code itself acknowledges the blast radius of revealing `bX` (the ECDH product): "When they do, they'd reveal bX, revealing Alice's message to Bob" [7](#0-6)  — the per-message PoP only prevents framing a third party's key as the sender's; it does not prevent disclosure of the plaintext share to the public.

### Impact Explanation
Every published blame event permanently discloses one honest-party secret share `f_sender(recipient)` of the DKG dealing, to the entire observer set — not just to the disputing parties. Since blame proofs are propagated in public coordinator/processor messages for third-party adjudication, a passive attacker harvesting blame traffic accumulates valid secret shares and the ECDH keys protecting them without participating in the DKG at all. This is unauthorized disclosure of threshold-key material (key share recovery as a publicly reachable side effect), and a malicious recipient can deliberately trigger it by falsely accusing an honest sender — the accusation is "free" in the sense that the honest sender's valid share is the data being decrypted and broadcast, while the recipient alone decides whether to publish. Each leaked share reduces the effective secrecy of that sender's contribution.

### Likelihood Explanation
Reachability is high: the disclosure path uses only public inputs — the `EncryptedMessage` blamed and the `EncryptionKeyProof` bytes broadcast in `ProcessorMessage::InvalidShare`/`VerifyBlame` — and `AdditionalBlameMachine::new` + `decrypt_with_proof` perform the decryption for any caller. Triggering requires an in-protocol blame event, which any single malicious DKG participant can cause at will by accusing an honest sender of an invalid share. Impact is bounded to the shares of messages actually blamed, so this rates Medium: it is real secret-material disclosure reachable by an unprivileged party, but it does not by itself recover a full threshold secret in a single event.

### Recommendation
Do not place the raw ECDH secret in a publicly transmissible structure. Two options:
- Replace `EncryptionKeyProof.key` with a reveal-then-verify flow where blame verification happens inside the protocol by a party holding the decryptor's `enc_key`, and publish only the verdict plus a non-decrypting attestation.
- If third-party verifiability is required, encrypt the revealed `key` to the verifier set (e.g., a designated blame-arbiter key) instead of serializing it in cleartext, so observers who see the public proof cannot decrypt the share.

At minimum, document and gate `AdditionalBlameMachine::new`/`blame` so the leaked-share disclosure is an acknowledged, opt-in consequence of running blame publicly.

### Proof of Concept
Any observer that sees a blame event can decrypt the blamed share:

```rust
// Given, from public protocol traffic:
//   context ([u8;32] DKG context), n participants,
//   every EncryptionKeyMessage<C, Commitments<C>> (broadcast),
//   the blamed EncryptedMessage<C, SecretShare<C::F>> for (sender -> recipient),
//   the accuser's serialized EncryptionKeyProof<C> (contains the ECDH key in cleartext)
let machine = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();

// blame() internally calls decrypt_with_proof, which does:
//   cipher::<C>(context, &proof.key).apply_keystream(msg.msg)
// proof.key is the raw ECDH secret; the observer now has the plaintext share.
let _faulty = machine.blame(sender, recipient, blamed_msg, Some(proof));

// Equivalently, directly:
let mut msg = blamed_msg;
let proof: EncryptionKeyProof<C> = EncryptionKeyProof::read(&mut blame_bytes).unwrap();
let decryption = Decryption::<C>::new(context);
// after registering enc_keys from public commitment msgs:
let plaintext = decryption
  .decrypt_with_proof(sender, recipient, msg, Some(proof))
  .unwrap(); // plaintext.0 is the sender's secret share to recipient
```

The cleartext `key` field in `EncryptionKeyProof` (encryption.rs:261-263, 491-492) plus the publicly constructible `Decryption` context (encryption.rs:348-362, lib.rs:649-661) make this a pure offline computation over already-broadcast bytes — no DKG membership, authentication, or secret input is required.
