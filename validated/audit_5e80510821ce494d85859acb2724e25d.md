Based on my investigation, the strongest local analog to the Mellow "aggregate-without-checking-support" DoS pattern is in the same-chain intent fill logic of `IntrinsicIntents.sol`.

### Title
Uninitialized/zero-address escrow slots in partial same-chain fills can brick order withdrawal - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain()` builds a fixed-size `escrowedInputs` array indexed in lockstep with `order.output.assets`, but for any output index where the fill is skipped (`remaining == 0 || solverAmount == 0`), the corresponding `escrowedInputs[i]` slot is left completely unpopulated by the `continue` statement, defaulting to `TokenInfo{token: 0, amount: 0}`. This zero-address, zero-amount entry is then passed unfiltered into `_withdraw()` as part of `body.tokens`, exactly mirroring the Mellow bug where balances/entries from an unchecked/unsupported source are blindly aggregated and handed to a settlement routine that assumes every entry is a legitimate, backed record.

### Finding Description
In `_fillSameChain` [1](#0-0) , the loop iterates `outputsLen` times and calls `continue` without writing to `escrowedInputs[i]`/`outputFills[i]` whenever an output has already been fully filled by a prior partial fill (`remaining == 0`) or the solver supplies nothing for that leg (`solverAmount == 0`). Because `escrowedInputs` is a fixed-length memory array allocated up front [2](#0-1) , any skipped index retains Solidity's default struct value: `token = bytes32(0)` (i.e. `address(0)`, the sentinel this codebase uses for the native asset — see the `token == address(0)` native-asset branches throughout the file) and `amount = 0`.

This array is then submitted as `body.tokens` to `_withdraw()` [3](#0-2) . The Tron sibling contract's equivalent withdrawal routine shows the expected per-token contract for this shared code path: it iterates every entry in `body.tokens` and reverts the *entire* withdrawal if any single token's escrow record is unset — `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` [4](#0-3) . If `IntentsBase._withdraw` follows the same per-entry-must-be-valid pattern (its signature and call sites strongly suggest it does, though I was unable to read its full body before the tool budget was exhausted), then any multi-output order that is filled leg-by-leg — a normal, expected usage pattern the contract explicitly supports via `_partialFills` — will inject a phantom `address(0)`/`amount:0` entry into `body.tokens`, and the withdrawal will incorrectly revert on that entry (`_orders[commitment][address(0)]` is `0` whenever the order has no genuine native-asset input), even though every real escrow entry is fully valid and available for release.

The root cause mirrors M-7 precisely: an aggregation routine (`escrowedInputs`) is constructed without verifying that every slot corresponds to a "supported"/populated record before handing it to a downstream all-or-nothing settlement function that assumes uniform validity across the whole array.

### Impact Explanation
If confirmed against `IntentsBase._withdraw`'s actual logic, this permanently blocks escrow release for any multi-output order that receives sequential/partial fills where legs complete at different times — a normal, intended flow (`_partialFills` mapping exists specifically to support this). Once the withdrawal reverts, the filler who supplied real assets to the beneficiary cannot claim their escrowed input tokens, and the order's escrow state (`_filled`, `_orders`) is left in an inconsistent, unresolvable position, since `_fillSameChain` has already performed the token transfers to the beneficiary and deleted `_filled[commitment]` for the non-full-fill branch before the revert would surface — meaning a retried call sees stale/duplicated state. This can lock filler funds and desynchronize the order's on-chain fill accounting, a fund-loss/lock condition matching the bounty's "loss of funds" / "logic attack" categories.

### Likelihood Explanation
Any solver filling a multi-output order in more than one transaction (a normal usage pattern for large orders that get filled incrementally by liquidity-constrained solvers) triggers the skip path deterministically — no malicious peer, relayer, or governance actor is required, only a routine partial fill against a multi-asset order. This is a public-entrypoint, unprivileged-attacker-reachable condition (or even purely accidental for legitimate solvers).

### Recommendation
Do not rely on default-initialized array slots as an implicit "no-op" marker. Either (a) size `escrowedInputs`/`outputFills` dynamically to only the entries actually filled in this call and pass that reduced array to `_withdraw`, or (b) have `_withdraw` skip zero-amount/zero-token entries instead of treating an unset `_orders[commitment][token]` as a hard revert for the whole batch. Confirm the exact behavior of `IntentsBase._withdraw` (not fully reviewed here due to tool-call exhaustion) and add a regression test that partially fills a two-output order across two separate transactions, verifying the second fill's escrow withdrawal does not revert on the phantom entry.

### Proof of Concept
1. Place an order with two output assets, `A` and `B`, and corresponding escrowed inputs.
2. Solver calls `_fillSameChain` supplying `solverAmount` for output `A` only, leaving `options.outputs[1].amount = 0` for `B`.
3. In the loop, index `1` (output `B`) hits `solverAmount == 0` and `continue`s, leaving `escrowedInputs[1] = TokenInfo(0, 0)` and `outputFills[1] = TokenInfo(0,0)`.
4. `isFullyFilled = false`; `_withdraw(body, false, false)` is called with `body.tokens = escrowedInputs` containing the phantom zero entry.
5. If `_withdraw` reverts on any `_orders[commitment][token] == 0` (as the Tron sibling's `withdraw()` does for `address(0)`, since this order has no native-asset input), the whole partial-fill transaction reverts, even though the real escrowed amount for output `A`'s input token is fully valid and should have been released to the solver.

**Note on completeness:** I could not retrieve the full body of `IntentsBase._withdraw()` before the tool budget ran out, so the exact revert condition on the EVM-mainline contract is inferred from the confirmed-analogous logic in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`. This should be verified directly against `evm/src/apps/intentsv2/IntentsBase.sol` before treating this as fully confirmed.
