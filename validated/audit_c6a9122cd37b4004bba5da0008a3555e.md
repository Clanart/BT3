### Title
SignableTransaction computes vbytes/weight from `payments` only, excluding the OP_RETURN `data` output — fee and size checks use the wrong quantity, like `convertToAssets` being fed one asset instead of one share — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report's bug class is "a value is computed by feeding the wrong object/units into a conversion function, silently producing a wrong result when the two differ." In `SignableTransaction::new`, the transaction's weight and virtual size — the denominator for the entire fee calculation — are computed by passing `payments` to `calculate_weight_vbytes` instead of the actual output list `tx_outs`, which by that point already contains an additional OP_RETURN output carrying up to 80 bytes of caller-supplied `data`.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202`, if `data` is specified, an extra `TxOut` (an OP_RETURN output of up to ~90 serialized bytes) is pushed onto `tx_outs`. Immediately after, at line 204, the fee is derived from:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` (lines 62-127) builds a template `Transaction` whose `output` field is populated **only** from `payments` (plus optional `change`). The OP_RETURN output is therefore omitted from the weight/vbytes measurement. The same wrong input is used for the with-change variant at lines 224-227 (`payments` again, not `tx_outs`).

Consequences, all flowing from the one wrong argument:
- `needed_fee = fee_per_vbyte * vbytes` is computed on a smaller transaction than the one actually built and signed, so the real feerate is below the requested `fee_per_vbyte`.
- The minimum-relay-fee guard at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) is evaluated on the same understated `vbytes`, so a transaction that is actually below the ~1 sat/vB relay minimum can pass the check.
- The `TooLargeTransaction` check at line 241 compares the understated `weight` against `MAX_STANDARD_TX_WEIGHT`, so a transaction that exceeds the standardness weight limit can pass.

This is a direct analog: a measurement function is handed the wrong input (the pre-OP_RETURN payment list rather than the real output set), and every downstream economic check silently computes on the wrong quantity — exactly the "one asset instead of one share" shape, where the discrepancy only materializes when the two differ (i.e., when `data` is present).

### Impact Explanation
An unprivileged party able to cause a transaction with `data` to be produced (the `data` parameter of `SignableTransaction::new` is attacker-influenced transaction content) obtains a signed transaction whose effective feerate is lower than intended and potentially below the mempool minimum relay feerate. The result is a transaction that is rejected on broadcast or that stalls unconfirmed while still committing the inputs (and their `offsets`/`prevouts` to the signing session), degrading into a funds-availability failure: the multisig produces signatures for a spend that cannot reliably confirm, and UTXOs are tied up. This is a Medium impact: no direct theft or key/share recovery, but a concrete, attacker-reachable miscalculation that can prevent funds from being spendable as intended.

### Likelihood Explanation
The discrepancy exists whenever `data` is non-empty, which is a normal (not malformed) input. The magnitude is bounded (~20-25 vbytes for an 80-byte payload), so it only crosses the relay-minimum boundary when `fee_per_vbyte` is near 1 sat/vB — precisely the regime the code itself targets (`median_fee` clamps to `fee.max(1)` in `processor/src/networks/bitcoin.rs:414`). The in-tree processor caller currently passes `None` for `data` (`processor/src/networks/bitcoin.rs:450`), which reduces present-day exploitability inside Serai's own pipeline; the flaw is still real in the in-scope `bitcoin_serai::wallet` API for any caller supplying data.

### Recommendation
Pass the actual output set to `calculate_weight_vbytes`, not `payments`. Either move the OP_RETURN push after the measurement while adding an equivalent placeholder output to the measured transaction, or change `calculate_weight_vbytes` to take `&[TxOut]`/the real `tx_outs` (including the data output) so weight, vbytes, `needed_fee`, the minimum-fee check, and the max-weight check all evaluate the exact transaction that will be signed.

### Proof of Concept
```rust
// Conceptual: build a transaction whose only "output" is data plus change
let inputs = vec![received_output];            // e.g., 10_000 sats
let data = vec![0u8; 80];                      // max allowed
let tx = SignableTransaction::new(
    inputs, &[], Some(change_addr), Some(data), 1 /* sat/vB */,
).unwrap();

// vbytes was measured WITHOUT the ~90-byte OP_RETURN output.
// needed_fee = 1 * vbytes(no-data) but the signed tx is ~22 vbytes larger,
// so actual feerate < 1 sat/vB and it can fail DEFAULT_MIN_RELAY_TX_FEE
// in practice even though the TooLowFee check passed.
assert_eq!(tx.tx.output.len(), 2); // OP_RETURN + change, both committed by sighash
```
Root cause: `networks/bitcoin/src/wallet/send.rs:204` and `:226` measure `payments` while `tx_outs` (lines 188-202) already includes the extra OP_RETURN output; `needed_fee`, the min-fee check at line 211, and the weight check at line 241 all consume the understated measurement.
