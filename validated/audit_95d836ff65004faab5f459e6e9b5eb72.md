### Title
App Proxy Request Verification Accepts Signed Requests With No Freshness Check on `timestamp` - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` validates only that the HMAC signature over the query string (which includes a `timestamp` parameter) matches, but it never checks that `timestamp` is recent. Any previously valid, correctly-signed app proxy request — including a decade-old one — is accepted indefinitely. This mirrors the reported oracle bug class: a value/signature can be legitimate at issuance but is accepted forever because there is no check that it was produced "within a reasonable time window."

### Finding Description
`query_string_valid?` extracts the `signature` parameter, recomputes the HMAC over the remaining sorted query parameters (including `timestamp`), and does a constant-time comparison — nothing else: [1](#0-0) 

`calculated_signature` simply HMACs the sorted params (which include `timestamp`) with the app secret, with no separate freshness validation of that timestamp value: [2](#0-1) 

The `before_action :verify_proxy_request` gate is the only check standing between an anonymous request and the proxied controller action: [3](#0-2) 

The repo's own test suite proves this: a request carrying `timestamp: "1466106083"` (year 2016) with its correct signature is accepted with `:ok`, demonstrating no expiry/freshness enforcement whatsoever: [4](#0-3) 

This is the direct structural analog of the oracle report: the report's `Oracle` contracts stored manually-set prices with no way to check "if they were last updated within a reasonable time window," so stale data could be treated as current. Here, `timestamp` is present in the signed payload (analogous to a "last updated" value) but is never compared against current time, so a captured, leaked, or logged app-proxy URL (e.g., from browser history, server logs, a referrer header, or a shared link) remains a valid, acceptable "signed request" forever.

The same missing-freshness-check pattern exists in `ShopifyApp::PayloadVerification#hmac_valid?`, used by `WebhookVerification`, which likewise validates only the HMAC digest with no replay/timestamp window enforcement: [5](#0-4) 

### Impact Explanation
An attacker who obtains a single previously-valid, Shopify-signed app proxy URL (via logs, referrer leakage, browser history, shared support tickets, etc.) can replay it against the app indefinitely, since there is no expiry check on `timestamp`. Because `verify_proxy_request` is the sole authorization gate for app-proxy controllers, this allows an unrelated party to invoke proxy actions as if they were a live, legitimate Shopify-forwarded storefront request at any point in the future — a stale, previously-authorized signed request is accepted as current.

### Likelihood Explanation
Exploitation requires the attacker to have observed one valid signed app-proxy request at some point (from logs, browser history, referrer headers, or similar exposure) but no ongoing secret compromise or elevated access is needed. Once obtained, replay works unconditionally and indefinitely, since it is purely a passive check-omission (no rate limiting, no timestamp comparison) rather than a targeted brute force.

### Recommendation
Enforce a freshness window on the `timestamp` parameter in `query_string_valid?` (and equivalently add nonce/timestamp replay protection to webhook HMAC verification in `payload_verification.rb`): reject requests whose `timestamp` deviates from the current time by more than a small tolerance (e.g., a few minutes), mirroring the audit's own recommendation to only accept values "updated within a reasonable time window."

### Proof of Concept
Using the existing test fixture, a request with `timestamp: "1466106083"` (a 2016 Unix timestamp) and its matching signature is accepted as `:ok` by `AppProxyVerificationController#basic` today, exactly as shown in the test: [4](#0-3) 

Since `query_string_valid?` never inspects `Time.now` relative to `timestamp`, this same request — or any other historically valid signed app-proxy request captured by a third party — will continue to pass `verify_proxy_request` and reach the protected action at any future date, with no code path added to reject it based on age.

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
