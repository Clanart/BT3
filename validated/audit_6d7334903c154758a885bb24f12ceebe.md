### Title
Attacker-controlled FROST preprocess can force the aggregate nonce `R` to the point at infinity, panicking `x()`/`x_only()` during BIP-340 signing — (File: networks/bitcoin/src/crypto.rs)

### Summary
The external bug class is "a protocol function trusts attacker-supplied length/structure and crashes" (Suricata's `ftp_pasv_response` parsing). The reachable analog in Serai is in the Bitcoin Schnorr `Hram`: `x(key)` and `x_only(key)` unconditionally `expect` the point is not infinity, yet the aggregate nonce `R` hashed by `Hram::hram` is a linear combination of per-participant `Commitments` that are read verbatim from untrusted preprocess bytes via `read_preprocess` / `Commitments::read`. A signer participating in a FROST session can choose its nonce commitments so the summed `R` is the identity point, causing a panic (node crash) whenever `sign_share`/`verify` runs over the BIP-340 algorithm — a remote DoS of the signing processor.

### Finding Description
`networks/bitcoin/src/crypto.rs` defines helpers that panic on the point at infinity:

```rust
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
``` [1](#0-0) 

`x_only` likewise `expect`s a non-infinity, even point: [2](#0-1) 

`Hram::hram` calls `x(R)` on the aggregate nonce `R` and `x(A)` on the group key: [3](#0-2) 

On the FROST side, `AlgorithmSignMachine::read_preprocess` deserializes `Commitments` and the addendum directly from attacker-controlled bytes with no non-identity-sum constraint on the aggregate: [4](#0-3) 

`sign` validates participant indexes and duplicates, but performs no check that the summed nonce `R` (or any nonce sum entering `Hram`) is non-identity before `sign_share`/`verify` evaluate `hram`: [5](#0-4) 

Even if `read_G`/`Commitments::read` rejects an identity *individual* commitment, an attacker in the signing set sees the other preprocesses and can set its own commitments `D_i = -(sum of others)` so the aggregate `R` equals the identity — every individual commitment is a valid non-infinity encoding. The doc comment on `Schnorr` acknowledges it "may panic if called with nonces ... which are the point at infinity", relying only on the assumption that the probability is "negligible ... even with malicious participants" — which is incorrect, since a malicious participant can force it deterministically.

### Impact Explanation
An unprivileged counterparty in a threshold signing session (any participant able to submit a preprocess, e.g., a validator submitting `Transaction::Sign`/`SignCompleted` data or preprocess bytes consumed via `read_preprocess`) can deterministically crash the signer/coordinator process at `x()`'s `expect` on secp256k1 during a Bitcoin signing attempt. This halts signing availability — the same "crash on unvalidated protocol input" class as CVE-2019-10055 (CVSS 7.5, A:H). Per the rules this maps to availability loss reachable with public inputs; severity is Medium–High (panic in production signing path, not merely an error return).

### Likelihood Explanation
Any participant in the `included` set can compute the honest aggregate commitment sum and submit `Commitments` encoding its negative before `sign`/`complete` computes `R` and invokes `Hram::hram`. No cryptographic assumption is needed — it is pure group arithmetic over public preprocess bytes. The only mitigation is the claim that identity nonces are improbable, which does not hold for a deliberate adversary. (Uncertainty: I could not fully confirm `Commitments::read`'s per-point identity rejection within the index, but it is irrelevant to the exploit since the attack works with all-valid encodings.)

### Recommendation
In `frost`'s `sign`/`verify` path (and/or `Schnorr::sign_share`/`verify` in `networks/bitcoin/src/crypto.rs`), explicitly check that every aggregate nonce point (the `R` fed to `Hram`) and the group key are not the identity before calling `x()`, and return a `FrostError::InvalidPreprocess(p)` instead of panicking. Alternatively make `x`/`x_only` return `Option`/`io::Error` and propagate blame to the submitting participant.

### Proof of Concept
1. Honest participants publish preprocesses with nonce commitments `C_1..C_{t-1}`; the attacker computes `S = Σ C_j`.
2. Attacker submits its preprocess (via `read_preprocess`-consumed bytes) with commitments `C_t = -S` (negate each generator commitment). Each point is a valid, non-infinity secp256k1 encoding.
3. `sign` computes nonce sums; the aggregate `R = S + (-S) = O` (identity).
4. `Hram::hram` calls `x(&R)` → `encoded.x().expect("point at infinity")` panics (`crypto.rs:15`), crashing the signing process. Same crash applies in `verify`/`complete` when reconstructing `R` from `nonce_sums`.
