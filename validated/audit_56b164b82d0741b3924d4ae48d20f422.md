## Analysis

This is a real local analog to the Aave "decimals not propagated" bug, found in `pallet-hyper-fungible-token`.

### The core issue

The pallet's cross-chain amount conversion (`send`, `on_accept`, `on_timeout`) relies on two independently-sourced decimal values:

1. **`erc_decimals`** — the remote-chain ERC20 decimals, fixed once in the `Precisions` storage map at `register_token`/`update_token` time.
2. **`local_decimals`** — read **live** on every call from the underlying `pallet-assets` metadata via `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(asset_id)`, e.g. in `send` [1](#0-0) , in `on_accept` [2](#0-1) , and in `on_timeout` [3](#0-2) .

The only place the relationship between these two values is validated is at `register_token`/`update_token` time, where `config.decimals >= local_decimals` is enforced [4](#0-3) [5](#0-4) . Once registered, `local_decimals` is **never re-checked** — the pallet just trusts the live value from `pallet-assets` on every send/receive/timeout call, exactly the same class of bug as the Aave report: decimals are changeable in one component (the asset's own metadata) without any propagation/re-validation in the component that depends on the invariant (the bridge's amount scaling).

The actual scaling logic makes this exploitable rather than just theoretical, because of `saturating_sub` in `convert_to_erc20`/`convert_to_balance`:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
	let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
``` [6](#0-5) 

These only compute a *one-directional* exponent (`erc_decimals - local_decimals`, floored at 0 via `saturating_sub`). If `local_decimals` ever exceeds `erc_decimals` — the exact inequality the registration-time check exists to prevent — the exponent silently becomes `0`, and the amount is passed through **completely unscaled** instead of being scaled correctly in the other direction.

### Why the guard doesn't stop it

`local_decimals` is not a value the pallet owns or freezes; it is pulled live from the asset's own `pallet-assets` metadata (`decimals()`), which is mutable by that asset's Issuer/Admin via `pallet-assets::set_metadata`, an entity entirely separate from the bridge's `CreateOrigin`. Once a legitimate asset is registered into the bridge with `config.decimals >= local_decimals` satisfied, nothing prevents that asset's own metadata decimals from later being raised (e.g. by its issuer) above the recorded `erc_decimals` in `Precisions`. The bridge never re-validates this invariant on `send`, `on_accept`, or `on_timeout` — it just recomputes `local_decimals` fresh and feeds it straight into the unscaled-fallback conversion functions.

### Impact

Once `local_decimals > erc_decimals` for a registered asset:
- `send()` computes `erc20_amount = convert_to_erc20(amount, erc_decimals, local_decimals)` with no scale-down, so the message dispatched to the remote `HyperFungibleToken`/`WrappedHyperFungibleToken` contract carries an amount many orders of magnitude larger than intended relative to what was actually escrowed/burned locally [7](#0-6) . The remote contract will mint/release that inflated amount to the recipient — a direct fund-inflation/loss vector for the bridge's custody.
- Conversely, on `on_accept`/`on_timeout`, the same broken conversion under-credits or over-credits the beneficiary relative to the actual escrowed/burned amount, corrupting the one-to-one custody accounting the pallet is supposed to preserve [8](#0-7) .

### Title

### Summary
`pallet-hyper-fungible-token` fixes `erc_decimals` in the `Precisions` map at registration time but reads `local_decimals` live from `pallet-assets` metadata on every `send`/`on_accept`/`on_timeout` call, mirroring the Aave `setReserveDecimals` bug: a decimals change in one place (asset metadata) is never propagated to the dependent bridge logic. The conversion helpers `convert_to_balance`/`convert_to_erc20` compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`, which silently collapses to `0` (no scaling at all) once `local_decimals` exceeds `erc_decimals` — exactly the condition the registration-time `ensure!(config.decimals >= local_decimals, ...)` check exists to prevent, but which is never re-enforced afterward.

### Finding Description
The registration-time invariant `config.decimals >= local_decimals` is a one-time check in `register_token`/`update_token` [4](#0-3) . It assumes `local_decimals` (derived from `pallet-assets` metadata) stays fixed. But `local_decimals` is recomputed dynamically on every subsequent `send`, `on_accept`, and `on_timeout` call rather than being snapshotted at registration [1](#0-0) [9](#0-8) [3](#0-2) . If the asset's decimals metadata is later increased (via `pallet-assets::set_metadata`, controlled by that asset's Issuer/Admin — independent of the bridge's `CreateOrigin`), the invariant silently breaks, and `saturating_sub` masks the violation by producing a zero exponent instead of erroring or scaling in the correct direction [6](#0-5) .

### Impact Explanation
This corrupts the amount encoded in cross-chain `Message.amount` on `send` relative to the amount actually escrowed/burned locally, and corrupts the amount credited locally on `on_accept`/`on_timeout` relative to the amount encoded in the incoming/refunded message. Both directions break the bridge's fund-conservation invariant (custody escrowed/burned must equal custody released/minted), directly matching the bounty's "stealing or loss of funds" / "logic attacks" category.

### Likelihood Explanation
Requires only a change to the local asset's own `decimals` metadata after bridge registration — a routine, permissionless-relative-to-the-bridge action available to whatever account controls that asset's `pallet-assets` Issuer/Admin role, with no bridge governance or CreateOrigin action needed to trigger the mismatch.

### Recommendation
Snapshot `local_decimals` in the `Precisions`/registration storage at `register_token` time rather than reading it live on every call, and reject `send`/`on_accept`/`on_timeout` (or re-derive scaling correctly in both directions, without `saturating_sub` collapsing to zero) if the live decimals no longer match the recorded value — analogous to the Aave recommendation of only allowing decimals changes for inactive reserves and propagating the change everywhere it's consumed.

### Proof of Concept
1. Register asset `X` with `local_decimals = 6` and `erc_decimals = 18` via `register_token` (passes the `config.decimals >= local_decimals` check).
2. Asset `X`'s Issuer calls `pallet_assets::set_metadata` to raise the asset's decimals to `24` (no bridge-side validation on this call).
3. User calls `send` with `amount = 1_000_000` (i.e., 1 token at old 6-decimal precision). `local_decimals` is now read live as `24`; `erc_decimals.saturating_sub(local_decimals) = 18.saturating_sub(24) = 0`, so `convert_to_erc20` returns `1_000_000` unscaled instead of the intended `1_000_000 * 10^12`.
4. The remote `HyperFungibleToken` contract receives a message amount that is `10^12` times smaller/larger than intended (depending on direction), releasing/minting an incorrect amount relative to what was actually escrowed on the source chain, breaking the bridge's 1:1 custody guarantee.
