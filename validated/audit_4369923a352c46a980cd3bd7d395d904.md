### Title
Live pruning marks recorded during a reverted/failed transaction bundle are never rolled back, causing later deletion of trie nodes still referenced by the canonical state — ([File: storage/statedb/trie.go], [File: blockchain/blockchain.go])

### Summary
Kaia's live-pruning trie implementation records "pruning marks" for trie nodes whenever a node is superseded during `Update`/`Delete` (via `markPrunableNode`), and those marks are persisted on every `Trie.Commit`/`CommitExt` (`commitPruningMarks`). A background goroutine (`pruneTrieNodeLoop`) later deletes the marked nodes permanently from disk based only on block number retention, with no re-validation that the node is actually obsolete on the canonical chain. When a transaction bundle is executed, partially committed, and then reverted/aborted (e.g. because a later bundled tx fails a nonce check), the pruning marks already generated by the intermediate trie mutations are **not undone**, even though the corresponding state mutation itself is discarded. This is functionally analogous to the Firefox CVE-2024-7527 pattern ("unexpected marking work at the start of sweeping... use-after-free"): work done during the "marking" phase (pruning-mark bookkeeping) races ahead of / diverges from the eventual "sweeping" phase (async node deletion), leaving nodes that are still live on the canonical trie scheduled for physical deletion.

### Finding Description
- `Trie.markPrunableNode` is invoked from `Trie.Update`/`Trie.delete` whenever a node is replaced/removed inside the in-memory trie mutation path, and the accumulated marks are staged in `t.pruningMarksCache`. [1](#0-0) 
- These marks are only flushed to `db.pruningMarks` (and eventually the disk `MiscDB`) when `Trie.CommitExt` is called, which happens on every `state.Commit()` for account/storage tries, not just at final block finalization: [2](#0-1) 
- `BlockChain.writeStateTrie` schedules the actual pruning of previously marked nodes via `bc.chPrune <- block.NumberU64()` after a block's state trie is committed, and a separate loop (`pruneTrieNodeLoop`) later calls `bc.db.PruneTrieNodes(marks)` to permanently delete the marked nodes from disk, driven purely by block-number retention distance — not by whether the mutation that produced the mark was ultimately part of the canonical chain: [3](#0-2) [4](#0-3) 
- The existing test scenario `makeTestTxBundleLivePruningScenario` explicitly documents this exact failure mode: when live pruning is enabled and a tx bundle is reverted because one of the bundled transactions fails (nonce too high), the state db becomes broken because nodes marked for pruning while executing the (ultimately reverted) bundle are left in place, i.e. the pruning marks are never rolled back with the state: [5](#0-4) 

The root cause is that pruning-mark bookkeeping (`markPrunableNode`/`commitPruningMarks`) is tied to trie mutation/commit calls that can occur speculatively (per-transaction `IntermediateRoot`/`Commit` calls during block building and bundle simulation), while the actual physical deletion (`PruneTrieNodes`) happens asynchronously and unconditionally based on those recorded marks, with no reconciliation step to confirm the marked node is genuinely superseded on the finally-accepted canonical state.

### Impact Explanation
On any full node running with live pruning enabled (`LivePruningRetention`/`chPrune`), an attacker-triggerable sequence — a transaction bundle that partially executes then fails/reverts (e.g. via a bundle where a later transaction has an invalid nonce, as demonstrated in the existing test) — can cause trie nodes that are still referenced by the canonical (post-revert) state to be marked for pruning. Once the async `pruneTrieNodeLoop` catches up past the retention window, those nodes are permanently deleted from disk even though they are still part of the live canonical trie. Subsequent access to that state (`StateAt`, `PrunableStateAt`) returns `statedb.MissingNodeError`, corrupting that node's local view of historical/canonical state. This can produce state divergence between nodes with differing pruning configurations (archive vs. live-pruning nodes), inability to serve state for affected accounts/blocks, and node crashes/service disruption for any client relying on the affected node's state — reachable purely from a public transaction/bundle submission, no privileged access required.

### Likelihood Explanation
The precondition (live pruning enabled) is an operator configuration choice, not attacker-controlled, so this only affects a subset of deployments. However, given that condition, the trigger itself — submitting or causing a bundle that gets partially applied and then reverted — is directly reachable by any transaction sender or bundle submitter, and is already reproduced deterministically by the repository's own test (`makeTestTxBundleLivePruningScenario(true)` asserts an error/broken state db). This indicates the bug is not a theoretical corner case but an already-observed, reproducible condition in the codebase.

### Recommendation
- Defer committing pruning marks (`commitPruningMarks` / `insertPruningMark`) until the enclosing block (and all bundles within it) is fully finalized and confirmed canonical, rather than at every intermediate `Trie.Commit` call during speculative/bundle execution.
- Alternatively, make pruning-mark application transactional with block insertion: buffer marks per candidate block/bundle attempt and discard them if the block/bundle is discarded, mirroring how state changes themselves are rolled back on failure.
- Add a reconciliation/safety check in `pruneTrieNodeLoop`/`PruneTrieNodes` to verify a marked node is not reachable from the current canonical root before physically deleting it, or gate live pruning to only mark nodes once the state that produced the mark has been committed as part of an accepted block.

### Proof of Concept
The existing repository test already demonstrates the bug end-to-end: [5](#0-4) 
1. Enable live pruning (`bcdata.db.WritePruningEnabled()`).
2. Submit a bundle of two transactions from the same sender where the second transaction uses a nonce far ahead of the correct one, guaranteeing `nonceTooHigh` failure and causing the bundle to be reverted after partial execution.
3. Observe (as asserted by the test) that `GenABlockWithTransactionsWithBundle` returns an error tied to state db corruption — nodes marked for pruning during the reverted bundle's execution remain scheduled for deletion, breaking the state db, whereas the same sequence with live pruning disabled succeeds without error.

// Mark the node for later pruning by writing PruningMark to database.
func (t *Trie) markPrunableNode(n node) {
	// Mark nodes only if both conditions are met:
	// - t.pruning: database has pruning enabled, i.e. nodes are stored with ExtHash
	// - t.PruningBlockNumber: requested pruning through state.New -> OpenTrie -> NewTrie.
	if !t.pruning || t.PruningBlockNumber == 0 {
		return
	}

	if hn, ok := n.(hashNode); ok {
		// If a node exists as a hashNode, it means the node is either:
		// (1) lives in database but yet to be resolved - subject to pruning,
		// (2) collapsed by Hash or Commit - may or may not be in database, add the mark anyway.
		t.pruningMarksCache[common.BytesToExtHash(hn)] = t.PruningBlockNumber
	} else if hn, _ := n.cache(); hn != nil {
		// If node.flags.hash is nonempty, it means the node is either:
		// (1) loaded from database - subject to pruning,
		// (2) went through hasher by Hash or Commit - may or may not be in database, add the mark anyway.
		t.pruningMarksCache[common.BytesToExtHash(hn)] = t.PruningBlockNumber
	}
}

func (bc *BlockChain) pruneTrieNodeLoop() {
	// ReadPruningMarks(1, limit) is very slow because it iterates over the most of MiscDB.
	// ReadPruningMarks(start, limit) is much faster because it only iterates a small range.
	startNum := uint64(1)

	bc.wg.Go(func() {
		for {
			select {
			case num := <-bc.chPrune:
				if num <= bc.cacheConfig.LivePruningRetention {
					continue
				}
				limit := num - bc.cacheConfig.LivePruningRetention // Prune [1, latest - retention]

				startTime := time.Now()
				marks := bc.db.ReadPruningMarks(startNum, limit+1)
				bc.db.PruneTrieNodes(marks)
				bc.db.DeletePruningMarks(marks)
				bc.db.WriteLastPrunedBlockNumber(limit)

				logger.Info("Pruned trie nodes", "number", num, "start", startNum, "limit", limit,
					"count", len(marks), "elapsed", time.Since(startTime))

				startNum = limit + 1
			case <-bc.quit:
				return
			}
		}
	})
}

func makeTestTxBundleLivePruningScenario(livePruningEnabled bool) func(*testing.T, *BCData, *TestAccountType, *TestAccountType, *TestAccountType, *AccountMap, *profile.Profiler, []kaiax.TxBundlingModule) {
	return func(t *testing.T, bcdata *BCData, rewardBase, validator, anon *TestAccountType, accountMap *AccountMap, prof *profile.Profiler, txBundlingModules []kaiax.TxBundlingModule) {
		if livePruningEnabled {
			bcdata.db.WritePruningEnabled()
		}

		bcdata.EnableMiner()

		signer := types.LatestSignerForChainID(bcdata.bc.Config().ChainID)
		gasPrice := new(big.Int).SetUint64(bcdata.bc.Config().UnitPrice)

		// 1. Transfer (rewardBase -> anon) using a legacy transaction.
		{
			amount := new(big.Int).Mul(big.NewInt(10000), new(big.Int).SetUint64(params.KAIA))
			tx := types.NewTransaction(rewardBase.Nonce, anon.Addr, amount, gasLimit, gasPrice, []byte{})
			rewardBase.Nonce += 1
			err := tx.SignWithKeys(signer, rewardBase.Keys)
			assert.Equal(t, nil, err)
			if err := bcdata.GenABlockWithTransactions(accountMap, []*types.Transaction{tx}, prof); err != nil {
				t.Fatal(err)
			}
		}

		// 2. Transfer (anon -> validator) using a legacy transaction two times.
		{
			txs := []*types.Transaction{}
			for i := range 2 {
				amount := new(big.Int).Mul(common.Big1, new(big.Int).SetUint64(params.Kei))
				nonce := anon.Nonce
				if i == 1 {
					nonce += 100
				}
				tx := types.NewTransaction(nonce, validator.Addr, amount, gasLimit, gasPrice, []byte{})
				err := tx.SignWithKeys(signer, anon.Keys)
				assert.Equal(t, nil, err)
				txs = append(txs, tx)
			}
			// tx0 and tx1 are bundled, and then tx1 fails due to nonceTooHigh, so it is reverted.
			expectedFailTxHashes := []common.Hash{txs[0].Hash(), txs[1].Hash()}
			err := bcdata.GenABlockWithTransactionsWithBundle(accountMap, txs, expectedFailTxHashes, prof, txBundlingModules)

			if livePruningEnabled {
				// State db will be broken because nodes marked as pruning during executing the bundle will be left in state db
				// even though the bundle will be reverted.
				assert.Error(t, err)
			} else if err != nil {
				t.Fatal(err)
			}
		}
