### Title
`Scanner::scan_block` reports coinbase outputs as received even though they are not spendable until maturity - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external finding describes an availability bug: a capability the documentation promises (EOA role providers) is unusable because the code unconditionally requires a property (the `IRoleProvider` interface) that a legitimate input does not have. The analogous pattern in Serai's in-scope `networks/bitcoin` crate is `Scanner::scan_block`, which scans `block.txdata[0]` (the coinbase transaction) alongside normal transactions and reports any matching outputs as ordinary `ReceivedOutput`s, even though coinbase outputs are consensus-unspendable for 100 blocks. Funds are reported received that are not spendable, and downstream code (e.g., `ReceivedOutput::read`/`write`, scheduler integration) has no maturity marker to distinguish them.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs:221-227`, `scan_block` iterates over all of `block.txdata` including index 0:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

`scan_transaction` (lines 199-214) matches only on `output.script_pubkey`, so a coinbase output paying to a registered scanner script produces a `ReceivedOutput` indistinguishable from a normal payment. The `ReceivedOutput` type (lines 88-149) carries only `offset`, `output`, and `outpoint` — no coinbase/maturity flag — and its serialized form read by `ReceivedOutput::read` (lines 122-134) equally has no way to encode maturity. The doc comment acknowledges the limitation ("This will also scan the coinbase transaction which is bound by maturity... a post-processing pass is needed"), but the API itself hands unspendable outputs to any caller that does not implement the suggested workaround. Notably, the production path in `processor/src/networks/bitcoin.rs:691` had to special-case this by iterating `block.txdata[1 ..]` — confirming the library function returns data its own primary consumer cannot safely use.

This mirrors M-07's shape: the code treats a class of external input (coinbase transaction / EOA provider) as interchangeable with inputs possessing a required property (spendability / `IRoleProvider`), when it is not. The result is availability loss: a scan incorporating a coinbase output yields a `ReceivedOutput` that any spend attempt will fail on at consensus (immature coinbase), and which a scheduler or wallet treating `scan_block` results as spendable UTXOs will select, producing transactions the network rejects.

### Impact Explanation
An unprivileged party — any Bitcoin miner — can create a block whose coinbase pays the multisig's P2TR script (or any registered offset script). Any downstream user of `scan_block` (the documented way to scan whole blocks) receives a `ReceivedOutput` that cannot be spent for 100 confirmations. Since `ReceivedOutput` and its serialization carry no maturity information, there is no recoverable signal: funds are reported received that are not spendable, and transactions built spending them will be rejected by consensus. This is a concrete availability/integrity failure of the wallet scanning API, matching the accepted impact class "funds reported received that are not spendable."

### Likelihood Explanation
Coinbase outputs paying arbitrary P2TR scripts require miner cooperation, so triggering this is less common than an ordinary payment — but miners are unprivileged third parties, merge-mined/pool payouts and miner donations to known addresses do occur, and the library exposes `scan_block` as a public API explicitly intended to scan blocks (per its docs and its use in `networks/bitcoin/tests/wallet.rs:65-66` where it is asserted equivalent to scanning `txdata[0]`). The availability impact is marginal but tangible: at most the coinbase value and one scheduler attempt per occurrence. Medium is consistent with the source finding's "marginal but tangible availability impact" reasoning.

### Recommendation
Skip the coinbase transaction inside `scan_block` (scan `block.txdata[1 ..]`), or add an explicit maturity/coinbase flag to `ReceivedOutput` (including its `read`/`write` encoding) so callers cannot mistake an immature coinbase output for a spendable input. The current doc-only warning places a consensus-critical invariant on every caller; the fix belongs in the library, as demonstrated by the processor already special-casing `txdata[1 ..]` in `processor/src/networks/bitcoin.rs:691`.

use secp256kfun::marker::*;
use bitcoin_serai::wallet::{Scanner, p2tr_script_buf};

// A miner crafts a block whose coinbase pays the scanner's external address.
fn poc_coinbase_reported_unspendable() {
  let key = /* even group key */;
  let mut scanner = Scanner::new(key).unwrap();
  let script = p2tr_script_buf(key).unwrap();

  // Coinbase tx paying the multisig script
  let coinbase = Transaction {
    version: Version::TWO,
    lock_time: LockTime::ZERO,
    input: vec![TxIn {
      previous_output: OutPoint::null(), // coinbase
      ..Default::default()
    }],
    output: vec![TxOut { value: Amount::from_sat(50_0000_0000), script_pubkey: script }],
  };

  let block = /* a Block whose txdata[0] == coinbase */;

  let outputs = scanner.scan_block(&block);
  // outputs[0] is a ReceivedOutput, indistinguishable from a spendable UTXO,
  // yet consensus forbids spending it until 100 confirmations elapse.
  assert_eq!(outputs.len(), 1);
  // ReceivedOutput carries no maturity flag; serialization round-trip loses nothing
  // because there is nothing to lose — the unspendability is never represented.
}
