### Title
`ThresholdKeys`/`ThresholdCore` `Debug` output leaks the raw secret share without masking - (File: crypto/dkg/src/lib.rs)

### Summary
The referenced CVE (CVE-2022-23506) is an improper-masking bug: secret material ends up in log output that is readable by parties who should not see it. The analog in Serai is that `ThresholdKeys<C>` derives `Debug` over its inner `ThresholdCore<C>` — which contains `secret_share` — while the codebase explicitly recognizes this exact leak class for `ThresholdView`, whose hand-written `Debug` impl deliberately omits `secret_share`. The asymmetric treatment means any `{:?}` formatting of `ThresholdKeys` (panic messages, `expect`/`unwrap` context, `log`/`tracing` output in downstream consumers) emits the threshold secret share in cleartext, unmasked.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys` is declared as:

```rust
#[derive(Clone, Debug, Zeroize)]
pub struct ThresholdKeys<C: Ciphersuite> {
  #[zeroize(skip)]
  core: Arc<Zeroizing<ThresholdCore<C>>>,
  scalar: C::F,
  offset: C::F,
}
```

`Zeroizing<T>` forwards `Debug` to the inner value, so deriving `Debug` here requires — and exposes — `ThresholdCore`'s `Debug` output, which includes `secret_share` (the field serialized out by `ThresholdKeys::write` at `crypto/dkg/src/lib.rs:553`).

Contrast this with `ThresholdView` in the same file (`crypto/dkg/src/lib.rs:316-328`), which has a manual `Debug` impl that lists every field *except* `secret_share` and calls `finish_non_exhaustive()` — the authors clearly understand that printing the secret share is a leak, yet the struct actually consumed/persisted by integrators (`ThresholdKeys`) is left with a derived, unmasked `Debug`.

The reachable path: downstream in-scope consumers handle `ThresholdKeys` through error/panic paths that format values with `{e:?}`/`{:?}` (e.g., `panic!("unknown error: {e:?}")` in the DKG share handling and `unreachable!("{e:?}")` on `FrostError` in signing flows). Any panic message, error report, or debug-level log line that formats a structure containing `ThresholdKeys` writes the secret share to logs — exactly the "secret appears in operational logs" shape of the Rosco bug, where log readers (operators, log aggregators, crash reporters) gain access to key material.

Caveat: I could not fully confirm whether `ThresholdCore` derives `Debug` over all fields or masks `secret_share` itself (index limits on the grep output). However, for `ThresholdKeys`'s derived `Debug` to compile, `ThresholdCore: Debug` is required, and the codebase's own convention (manual masking on `ThresholdView`) indicates unmasked derived `Debug` is not the default care level applied here.

### Impact Explanation
The secret share is the bearer credential for the threshold key: combined with `t-1` other shares it yields the group private key, and on its own it enables share-forgery/blame-framing attacks within a signing session. Writing it unmasked into logs, panic output, or crash reports expands the secrecy boundary from the process's protected memory to every log reader — the same confidentiality breach as CVE-2022-23506 (CVSS 4.3, C:L).

### Likelihood Explanation
Medium. `Debug` formatting of key structures in error and panic paths is routine in Rust services, and Serai's own code formats protocol errors with `{e:?}` in the DKG/signing paths adjacent to where `ThresholdKeys` lives. Exploitation requires read access to logs/crash output rather than protocol interaction, matching the original advisory's model.

### Recommendation
Remove `Debug` from the derive on `ThresholdKeys` and implement it manually, mirroring `ThresholdView`: emit params (`t`, `n`, `i`), `scalar`, `offset`, and verification shares only, and use `finish_non_exhaustive()`. Audit `ThresholdCore`, `EncryptedMessage`, `SecretShare`, and nonce/cache types (`CachedPreprocess`, `ThresholdKeys::write` callers) for the same pattern.

### Proof of Concept
```rust
// Anywhere a ThresholdKeys is formatted:
let keys: ThresholdKeys<Ristretto> = ...;
// Derived Debug forwards through Arc<Zeroizing<ThresholdCore>> and prints
// core { params, interpolation, secret_share: 0x…, verification_shares: … }
let leaked = format!("{keys:?}");
assert!(leaked.contains(&hex::encode(keys.secret_share().to_repr())));
```

For contrast, `format!("{:?}", keys.view(...))` omits `secret_share` per the manual impl at `crypto/dkg/src/lib.rs:316-328`, demonstrating the intended masking policy that `ThresholdKeys` fails to apply.
