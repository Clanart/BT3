### Title
Unbounded CLVM execution cost in `Offer.get_cancellation_coins()` bypasses the cost limits enforced elsewhere in `Offer` - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer` normally bounds CLVM execution against `MAX_BLOCK_COST_CLVM` when computing additions and conditions, but `get_cancellation_coins()` runs the same untrusted puzzle reveals with `INFINITE_COST`, with no limit at all. This mirrors the Starlette bug class: a resource limit (max cost / bounded parsing) that is correctly enforced on one code path but silently omitted on a sibling path operating on the same untrusted input.

### Finding Description
When an `Offer` object is constructed from untrusted, counterparty-supplied bytes, `Offer.__post_init__` runs every `CoinSpend`'s puzzle through `compute_spend_hints_and_additions` with an explicit `max_cost` initialized to `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`, decrementing it per spend and raising `ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, ...)` if exceeded: [1](#0-0) 

Similarly, `Offer.conditions()` also runs `run_with_cost` with a `max_cost` budget derived from `MAX_BLOCK_COST_CLVM` and raises `ValidationError` on overflow: [2](#0-1) 

However, `Offer.get_cancellation_coins()` — which iterates over the same untrusted `self._bundle.coin_spends` — calls `run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)` with no cost bound whatsoever: [3](#0-2) 

`INFINITE_COST` is imported directly from `chia.types.blockchain_format.program` and used to intentionally skip cost accounting: [4](#0-3) 

Because the puzzle reveal and solution in a `CoinSpend` come directly from the offer file (attacker/counterparty-controlled), and `get_cancellation_coins()` executes them with no cost ceiling, an attacker can craft a puzzle whose execution cost is enormous (deep recursion / large loops permitted by CLVM), causing the CLVM interpreter to run essentially unbounded inside the wallet process — exactly the resource-limit-bypass pattern described in the Starlette advisory (a limit is enforced in one parser/path but not the sibling path handling the same untrusted payload).

### Impact Explanation
This is a spend-triggered/offer-triggered synchronous computation with no upper bound, executed inside the wallet's request-handling flow. A single malicious offer (or offer file) can force the wallet to spend a large amount of CPU time (or effectively hang) evaluating an oversized CLVM program, blocking the wallet service from handling other work — a Denial-of-Service condition directly analogous to CWE-770 in the source report. It does not directly cause coin theft or inflation, but it can render the local wallet RPC/service unusable while processing an untrusted offer, which is exactly the class of impact the report describes (resource exhaustion via un-enforced limits).

### Likelihood Explanation
Reachable by any offer counterparty who can hand the victim's wallet an offer file/bytes to be loaded into an `Offer` object and subsequently have its cancellation coins computed. Because `__post_init__` already tolerates spends that raise generic `Exception` (only re-raising `ValidationError` for the max_cost case) and other paths already impose a `MAX_BLOCK_COST_CLVM` ceiling, this is very likely an accidental omission (same bug pattern as Starlette: the limit exists elsewhere but wasn't threaded through to this call site) rather than an intentional design choice.

### Recommendation
Replace `INFINITE_COST` in `get_cancellation_coins()` with a bounded `max_cost` (e.g., `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`, decremented across spends and enforced the same way as in `__post_init__`/`conditions()`), raising `ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, ...)` if exceeded, so that the same protection consistently applies to every code path that executes untrusted puzzle reveals from an `Offer`.

### Proof of Concept
1. Craft an offer whose non-addition `CoinSpend` puzzle reveal is a CLVM program designed to consume extremely high cost when run without a ceiling (e.g., deep recursive apply/quote expansion) while still being cheap enough, or engineered, to pass the bounded checks in `__post_init__`/`conditions()` (or simply exploit that `__post_init__` swallows generic exceptions from `compute_spend_hints_and_additions` for non-`ValidationError` cases via its `except Exception: continue`).
2. Deliver this offer file to a victim wallet (e.g., via the offer-import/trade flow).
3. Trigger `Offer.get_cancellation_coins()` (invoked from the trade-cancellation flow in `chia/wallet/trade_manager.py`) on this `Offer` instance.
4. Observe that `run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)` executes without any cost ceiling, consuming disproportionate CPU/time and blocking the wallet process — unlike the equivalent, correctly-bounded call in `conditions()`/`__post_init__`, which would raise `ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, ...)` instead.

Note: I was not able to fully trace, within the available tool budget, the exact caller path in `chia/wallet/trade_manager.py` that invokes `get_cancellation_coins()` (e.g., whether it fires automatically upon receiving/processing an offer versus only on explicit user-initiated cancellation of a trade). This affects how directly an unauthenticated counterparty can trigger the unbounded execution without user interaction, and should be verified against `chia/wallet/trade_manager.py` before treating this as fully unauthenticated-reachable.
