### Title
Missing participant-index validation in `BlameMachine::blame` / `AdditionalBlameMachine::blame` causes panic on unbounded `sender`/`recipient` indexes - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
The iccDEV bug class (a `Validate()` routine that trusts attacker-controlled index/length fields and performs unchecked indexing, yielding UB) maps onto Serai's PedPoP blame-evaluation path: `BlameMachine::blame` and `AdditionalBlameMachine::blame` accept caller-supplied `sender`/`recipient` `Participant` values and index internal `HashMap`s with them (`self.commitments[&sender]`, `self.enc_keys[&decryptor]`) without checking that the participant is within `1..=n`. `Participant::new` accepts any non-zero `u16`, so an index like `n+1` (or 65535) passes encoding validation upstream and reaches these APIs. The result is a panic that aborts the DKG blame/handling path — the same "missing bounds check on untrusted identifier" shape as `CIccTagLutAtoB::Validate()`.

### Finding Description
`Participant` wraps a non-zero `u16` with no upper bound (`crypto/dkg/src/lib.rs:121-126` only rejects zero). In the blame path:

- `BlameMachine::blame` → `blame_internal` does `&self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`) and `self.encryption.decrypt_with_proof(...)` which does `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`).
- `AdditionalBlameMachine::new` builds `commitments`/`enc_keys` only for `1..=n` (`crypto/dkg/pedpop/src/lib.rs:656-660`), and its `blame` forwards arbitrary `sender`/`recipient` to `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:674-682`).
- `Decryption::register` additionally `assert!`s on re-registration (`crypto/dkg/pedpop/src/encryption.rs:356-359`), another panic reachable if duplicate participants are submitted upstream.

Upstream, blame claims are transported as `InvalidDkgShare` tributary transactions whose `accuser`/`faulty` fields are deserialized with only `Participant::new` (non-zero) validation (`coordinator/src/tributary/transaction.rs:346-353`), so any non-zero `u16` index — including ones beyond the validator set size `n` — can reach `blame`.

### Impact Explanation
A single crafted blame transaction naming a `faulty`/`accuser` index outside `1..=n` (or a duplicated commitment registration) panics every validator evaluating blame. This aborts the key-generation/rotation attempt and, depending on panic handling, crashes the processor — a consensus-affecting denial of service reachable by any party able to submit the blame message (the accused need not even be a real participant). This mirrors the iccDEV class: a validation routine performing unchecked indexing on attacker-controlled identifiers, here causing guaranteed abort rather than memory-unsafe reads (Rust converts the UB into a panic, but the availability impact is equivalent).

### Likelihood Explanation
Triggering requires only submitting an `InvalidDkgShare`-style message with an out-of-range or inconsistent participant index — no key material, no valid signature from the victim set beyond the accuser's own, and no collusion. The crash is deterministic (`HashMap` indexing on an absent key panics unconditionally). Cost to the attacker is minimal; the abort forces DKG restart/halt, making repeated triggering trivially easy.

### Recommendation
- In `blame_internal`/`decrypt_with_proof`, replace `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with `.get()`-based lookups that return a defined fault result (e.g., blame the out-of-range accuser) instead of panicking.
- Validate `sender`/`recipient` against `1..=n` at the `blame` API boundary in `BlameMachine`/`AdditionalBlameMachine`.
- Turn `Decryption::register`'s `assert!` on duplicate registration into a returned error, since duplicate commitments are an expected malicious-party behavior per the crate's own docs.
- Belt-and-suspenders: validate `accuser`/`faulty` are in `1..=n` when parsing `InvalidDkgShare` transactions.

### Proof of Concept
```rust
// crypto/dkg/pedpop PoC sketch (Ristretto)
use dkg::{Participant, ThresholdParams};
use dkg_pedpop::*;
use ciphersuite::dalek_ff_group::Ristretto;
use rand_core::OsRng;
use std::collections::HashMap;

// Setup: n = 3 participants complete round 1 honestly
// Build an AdditionalBlameMachine over their valid commitment messages
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker submits a blame statement naming a non-existent participant (index 4..=65535)
let bogus = Participant::new(4).unwrap();
// Any well-formed EncryptedMessage bytes parsed via EncryptedMessage::read
machine.blame(bogus, Participant::new(1).unwrap(), msg, None);
// ^ panics at crypto/dkg/pedpop/src/lib.rs:599 on `self.commitments[&sender]`
//   because `commitments` only contains Participants 1..=3.
```
The same panic occurs in `Decryption::decrypt_with_proof` (`self.enc_keys[&decryptor]`, `crypto/dkg/pedpop/src/encryption.rs:388`) when `recipient` is out of range and a proof is supplied, since `enc_keys` is populated only for `1..=n`.

Note: I could not inspect the coordinator-side call site that feeds parsed `accuser`/`faulty` values into `blame` (outside the listed in-scope files), so the reachability claim rests on `Participant::new` accepting any non-zero `u16` at parse time and the library API imposing no bound check itself.
