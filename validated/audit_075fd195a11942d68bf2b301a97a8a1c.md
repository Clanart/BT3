### Title
Deep-link `branch` parameter validation (`testForInvalidChars`) fails to reject leading-hyphen branch names, enabling git argument injection at checkout — (File: `app/src/lib/sanitize-ref-name.ts`, `app/src/lib/parse-app-url.ts`, `app/src/lib/git/checkout.ts`)

### Summary
`parseAppURL` validates the deep-link `branch` query parameter with `testForInvalidChars` before constructing an `IOpenRepositoryFromURLAction`. That validator's regex catches control characters, `@{`, consecutive dots, and other ref-format issues, but it never rejects a name that starts with `-`. The sibling function `sanitizedRefName` in the same file explicitly strips leading `-`/`+` as a second pass, proving the authors know leading dashes are dangerous — but that second pass is not applied to deep-link input. Separately, the actual `git checkout` invocation in `getBranchCheckoutArgs` places the branch name *before* the `--` end-of-options marker, so even the `--` guard does not protect against a hyphen-prefixed branch name being parsed as a flag.

### Finding Description
`app/src/lib/parse-app-url.ts` only calls `testForInvalidChars(branch)` on the `branch` deep-link parameter: [1](#0-0) 

`testForInvalidChars` is backed by a regex designed for `git check-ref-format` compliance, but it has no clause rejecting a leading `-`: [2](#0-1) 

Contrast this with `sanitizedRefName` in the very same file, which performs an *additional* `.replace(/^[-\+]*/g, '')` pass specifically to strip leading dashes/pluses — confirming the maintainers are aware that a leading `-` is unsafe for a ref/branch name used as a CLI token, yet `testForInvalidChars` (the function actually gated on deep-link input) omits this check.

The tainted `branch` string flows to `Dispatcher.openBranchNameFromUrl`, which calls `this.checkoutLocalBranch(repository, branchName)` directly with the raw string: [3](#0-2) 

Ultimately, when a `Branch` object is checked out, `checkoutBranch` in `app/src/lib/git/checkout.ts` builds the git argv via `getBranchCheckoutArgs`: [4](#0-3) 

Note the ordering: `branch.name` is placed **before** the trailing `'--'`. Git parses options left-to-right until it hits `--`; because the branch name token appears prior to that separator, a name like `--force` (or `-b`, `--orphan`, etc.) is interpreted as an option flag rather than a literal ref argument, defeating the purpose of the `--` guard entirely.

### Impact Explanation
If an attacker can get a `branch` value beginning with `-` through `parseAppURL`'s check (which it can, since only `@{`, `..`, control chars, etc. are blocked — not leading `-`), and that value ends up as `Branch.name` reaching `checkoutBranch`, the resulting `git checkout <attacker-string> --` invocation can have the attacker string parsed as a git option instead of a ref name. Depending on which option string is chosen, this creates the potential for unintended git behavior (argument/flag injection) rather than a benign "branch not found" error, which is a classic argument-injection class bug in wrappers that don't defensively place `--` before the untrusted value.

### Likelihood Explanation
Reduced/uncertain: I was not able to fully trace, within this session, whether `Dispatcher.checkoutLocalBranch` (or the underlying `AppStore` method) constructs a `Branch` object directly from the raw deep-link string when no matching branch exists, or whether it requires the name to match a branch actually present after `_fetch` (in which case the attacker would need to control the remote and pre-create a ref literally named e.g. `--force`, which itself may be rejected by `git check-ref-format`/`git branch` naming rules on typical git servers). This piece of the chain (exact `checkoutLocalBranch`/`_checkoutBranch` implementation in `app/src/lib/stores/app-store.ts`) could not be retrieved before the iteration budget ran out, so the end-to-end exploitability (does a hyphen-prefixed value actually survive to becoming `Branch.name` passed into `checkoutBranch`) is not fully confirmed.

### Recommendation
- Update `testForInvalidChars` in `app/src/lib/sanitize-ref-name.ts` to also reject names with a leading `-`/`+`, mirroring the stripping logic already present in `sanitizedRefName`.
- Independently, fix `getBranchCheckoutArgs` in `app/src/lib/git/checkout.ts` so the branch name is emitted only *after* the `--` separator (or otherwise ensure all untrusted ref-like tokens passed to `git` are guarded by a preceding `--`), so that even if a malformed name slips through validation it cannot be parsed as a flag.
- Confirm and, if necessary, harden the `checkoutLocalBranch` path in `app/src/lib/stores/app-store.ts` to reject/sanitize any branch/ref value before it is wrapped into a `Branch` object used for a real `git` invocation.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
