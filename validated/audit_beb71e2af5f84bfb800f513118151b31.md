### Title
Unauthenticated encryption key registration allows MITM substitution of `enc_key`, leaking DKG secret shares — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP DKG authenticates each participant's `Commitments` via a Schnorr proof of knowledge whose challenge binds only the participant index, nonce, and commitment bytes — it never covers `enc_key`, the ephemeral ECDH public key carried in the same `EncryptionKeyMessage`. `Decryption::register` stores whatever `enc_key` arrives with no proof of possession and no identity/non-identity check. A party relaying the protocol transcript (or any unprivileged party able to feed crafted bytes to `EncryptionKeyMessage::read`/`Commitments::read`) can swap `enc_key` for a key whose discrete log they know (e.g., `k*G`, or even the identity). Every secret share later "encrypted to" that participant uses `ecdh(enc_key_attacker, msg_key)`, so the attacker derives the same ChaCha20 keystream and reads the victim's FROST secret shares in the clear — a direct analog of a MITM reading credentials when a weak/unauthenticated parameter is silently accepted.

### Finding Description
- `challenge` at `crypto/dkg/pedpop/src/lib.rs:86-94` binds `context`, `participant`, `nonce` (`R`), and `commitments` (`Am`) — `enc_key` is absent. The `EncryptionKeyMessage` is produced at `crypto/dkg/pedpop/src/lib.rs:190-191` via `encryption.registration(...)`, which just wraps the raw `enc_pub_key` with no signature or PoP over it.
- `Decryption::register` (`crypto/dkg/pedpop/src/encryption.rs:351-362`) inserts `msg.enc_key` into `enc_keys` unconditionally — the only check is a duplicate-registration assert. No PoP, no identity rejection.
- In `verify_r1` (`lib.rs:323-329`), the batch Schnorr verification uses `msg.sig.R` and `msg.cached_msg`, which excludes `enc_key` (note `Commitments::read` rebuilds `cached_msg` only from the commitment encodings, `lib.rs:109-128`). A tampered `enc_key` passes all verification.
- `Encryption::encrypt` (`encryption.rs:460-467`) then calls `encrypt(rng, self.context, self.i, self.decryption.enc_keys[&participant], msg)`, and `encrypt` (`encryption.rs:153-167`) computes `cipher(context, ecdh(key, to))` where `to` is the attacker's substituted key. Because ChaCha20's key/IV derive solely from `transcript(context || shared_key)` and a fixed IV (`encryption.rs:101-133`), anyone holding the discrete log of `to` reconstructs the exact keystream and XOR-decrypts the `SecretShare` bytes.
- The per-message Schnorr PoP (`pop`, `encryption.rs:83-91`) does not help: it only proves the sender knew the ephemeral `key` scalar — it does not bind the destination `enc_key` to the victim's identity.

### Impact Explanation
An attacker who replaces participant `v`'s `enc_key` learns every `SecretShare` sent to `v` (`lib.rs:369`). The victim's resulting private share is the sum of those shares (`lib.rs:484`), so the attacker recovers `v`'s threshold key share outright — key-share recovery. If the attacker performs the substitution against `t` participants' registrations, they recover `t` shares and can reconstruct/forge the group key's signing capability entirely. The DKG may later fail blame attribution (the victim can't decrypt and will be flagged faulty via `DecryptionError::InvalidProof` → `blame_internal` returns `recipient`, `lib.rs:586-587`), but the credential material has already been read — identical in shape to CVE-2018-1139 where weak accepted authentication let a MITM read credentials in transit.

### Likelihood Explanation
Any unprivileged relay/observer who can alter the `EncryptionKeyMessage` bytes — which are parsed by `EncryptionKeyMessage::read` / `Commitments::read` from untrusted input (`encryption.rs:57-59`, `lib.rs:109-128`) — can substitute `enc_key` without invalidating any verification performed in `verify_r1`. No collusion, no broken BFT, and no leaked keys are required; the missing authentication is purely a protocol-level gap.

### Recommendation
Bind `enc_key` into the `challenge` transcript in `generate_coefficients`/`verify_r1` (append `enc_key.to_bytes()` alongside `commitments`), or attach a Schnorr proof of possession for `enc_key` to `EncryptionKeyMessage`. Additionally, reject identity/non-canonical group elements in `Decryption::register` so a substituted key cannot be the public identity point.

### Proof of Concept
1. Victim `v` broadcasts `EncryptionKeyMessage { msg: Commitments{..}, enc_key: E_v }`.
2. Attacker rewrites the message to `enc_key: E_a = k*G` (or the identity) and forwards it to sender `s`. `Commitments::read` accepts it; `verify_r1`'s batch PoK check passes because `cached_msg`/`challenge` never include `enc_key`; `register` stores `E_a`.
3. `s` runs `generate_secret_shares` → `encrypt(rng, v, share)` → `cipher(context, ecdh(key, E_a))` and sends `EncryptedMessage { key: K = r*G, pop, msg: share ⊕ keystream }`.
4. Attacker computes `shared = k*K`, rebuilds `ChaCha20` via `cipher(context, shared)` (fixed IV `"DKG IV v0.2\0"`), and XOR-decrypts `msg` to recover `v`'s `SecretShare` scalar bytes — while the unmodified `pop` remains valid since it only attests to `K`.
