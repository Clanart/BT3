### Title
Diff-hunk "Expand Up" desynchronizes line-selection indices, causing wrong lines to be silently included/excluded from a commit - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
This is the closest Desktop analog to the "hidden unit/index-scale mismatch propagated through chained calls without re-validation" bug class from the Yield report. In `CompositeMultiOracle`, a price was scaled once and then re-used downstream under an implicit decimals assumption that was never re-checked. In Desktop, `expandTextDiffHunk` inserts new diff lines *before* the existing lines of a hunk when the user clicks "Expand Up," but leaves `hunk.unifiedDiffStart` for that hunk unchanged, while the per-line "absolute index" (`unifiedDiffStart + lineIndex` used everywhere for partial-commit line selection) silently shifts for every pre-existing line in that hunk. The `DiffSelection` object is a bare set of integer indices with no dependency on the diff it was computed against, so after an "expand up" the same integers now point at different lines.

### Finding Description
Line selection for partial commits is implemented as a `Set<number>` of "diverging" absolute line indices inside `DiffSelection` (`app/src/models/diff/diff-selection.ts`), and `isSelected(lineIndex)` simply checks membership against that set: [1](#0-0) 

Both the UI (`side-by-side-diff.tsx`) and the patch generator (`patch-formatter.ts`) compute the "absolute index" of a line the same way: `hunk.unifiedDiffStart + lineIndex`: [2](#0-1) 

When a hunk is expanded upward, `expandTextDiffHunk` builds the new line array by *prepending* the newly revealed context lines ahead of all the pre-existing lines of the hunk: [3](#0-2) 

But the resulting hunk keeps the same `unifiedDiffStart` as before the expansion (only `unifiedDiffEnd` grows): [4](#0-3) 

Because `lineIndex` for every pre-existing line inside that hunk has now increased by `numberOfNewDiffLines` (the count of newly inserted lines), while `unifiedDiffStart` did not change, the absolute index of every pre-existing Add/Delete line in that hunk shifts forward by `numberOfNewDiffLines`. The `DiffSelection` set, however, still contains the *old* absolute indices from before the expansion — nothing in `expandTextDiffHunk`, `onExpandHunk`, or the `DiffSelection` API remaps or invalidates those indices when a hunk is expanded (the only remap path found, `withSelectableLines` in `app-store.ts`, only prunes/keeps *membership* against a newly computed `selectableLines` set — it does not shift the stored indices to follow moved lines): [5](#0-4) 

The net effect: after "Expand Up," the old absolute-index integers in the user's selection now resolve to different lines than the ones the user actually selected/deselected. When `formatPatch`/`formatPatchToDiscardChanges` later call `file.selection.isSelected(absoluteIndex)` to build the commit/discard patch, they use the *new* diff's line layout with the *stale* selection indices: [6](#0-5) 

This is structurally the same defect pattern as the audited bug: a value (there, a scaled price; here, a line-selection index) is computed once under one set of assumptions (decimals / hunk layout) and reused later without re-deriving it under the new context (oracle decimals / post-expansion layout), and no guard exists to catch the mismatch.

### Impact Explanation
If the mapping is off, `git apply`/commit creation can silently stage or discard the wrong hunk lines relative to what the user visually selected in the diff viewer after expanding context — i.e., "silent corruption of what the user commits or pushes," one of the explicitly valid impact classes for this scan. A user could unknowingly commit a change they had intentionally deselected (e.g., a secret, a debug statement, or an unwanted line) or fail to commit a change they believed was selected, without any error being surfaced, because `formatPatch` never fails for a valid-looking (but mismatched) selection — it just emits a different but structurally valid patch.

### Likelihood Explanation
Requires no attacker control over content, and no local/privileged access beyond the ordinary GitHub Desktop partial-commit workflow: any user viewing a diff with more than the default context (i.e., using "Expand Up" on a hunk that isn't already fully expanded — a first-class, easily discoverable UI feature) and then adjusting the individual add/delete line selection is exposed. This is a normal, single-user workflow interacting with local repository content, not an exotic or multi-step attack chain, which raises likelihood, though exploiting it for a specific malicious outcome (rather than encountering it as a correctness bug) would need the user to combine it with attacker-supplied file content designed to be near a hunk boundary.

### Recommendation
- When a hunk is expanded (up or down) or merged with an adjacent hunk, remap all previously-diverging selection indices in the corresponding `DiffSelection` by the same `numberOfNewDiffLines`/merge offset used to shift the hunk boundaries in `expandTextDiffHunk`, instead of leaving the selection's raw indices untouched.
- Alternatively, key `DiffSelection` off a stable per-line identity (e.g., old/new line numbers, which are diff-content-derived and unaffected by hunk-boundary bookkeping) rather than a positional "absolute index" that is only valid for one specific snapshot of `diff.hunks`.
- Add a regression test that: selects specific Add/Delete lines, expands the hunk containing them upward, and asserts that `formatPatch` still includes exactly the originally-selected lines.

### Proof of Concept
1. Open a file in Desktop with a diff that has more than the default context lines above a change (so "Expand Up" is available), e.g. hunk header `@@ -50,10 +50,12 @@`.
2. In the side-by-side diff, deselect a single `+` line inside that hunk (via `withLineSelection`/`onEndSelection`), leaving the rest selected — `absoluteIndex = hunk.unifiedDiffStart + lineIndex` for that line is recorded in `DiffSelection`'s diverging set (`app/src/models/diff/diff-selection.ts:121-135`, `app/src/ui/diff/side-by-side-diff.tsx:1335-1354`).
3. Click "Expand Up" on that hunk, triggering `expandTextDiffHunk(diff, hunk, 'up', ...)`. New context lines are prepended ahead of the existing lines (`app/src/ui/diff/text-diff-expansion.ts:302-309`), while `hunk.unifiedDiffStart` for the (now larger) hunk stays the same (`text-diff-expansion.ts:318-325`) — shifting the internal `lineIndex` of the deselected `+` line forward by the number of newly added lines.
4. Commit the file. `formatPatch` recomputes `absoluteIndex = hunk.unifiedDiffStart + lineIndex` against the *new*, expanded hunk and checks it against the *unshifted* selection set (`app/src/lib/patch-formatter.ts:143-157`). The index that used to point at the deselected `+` line now points at one of the newly-added context lines (a no-op for context, per lines 153-156), while the actual `+` line the user deselected sits at a new index that is *not* in the diverging set — so it reverts to the default ("all selected") behavior and gets silently committed even though the user deselected it in the UI.

Note: I could not fully trace the top-level `expandHunk`/`onExpandHunk` call chain in `side-by-side-diff.tsx` beyond the code shown (tool budget exhausted before reaching its full body), so I have not confirmed whether some other, unseen code path re-synchronizes the selection object immediately after an expansion completes. If such a remap exists elsewhere and is not visible in the excerpts reviewed, it would mitigate this finding; based on all `DiffSelection`/`withSelectableLines` code found, no such remap exists.
