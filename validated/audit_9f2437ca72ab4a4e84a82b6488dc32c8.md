## Analysis

The external report's core issue — allowances being tracked across multiple, disjoint stores/contracts with no reconciling invariant — maps directly onto how Cosmos EVM's native-ERC20 token pairs handle allowances in two independent places:

1. The actual deployed `ERC20MinterBurnerDecimals` Solidity contract's own OpenZeppelin-style storage-backed `allowance` mapping [1](#0-0) .
2. The `x/erc20` keeper's separate, precompile-facing allowance KV store (`GetAllowance`/`SetAllowance`/`DeleteAllowance`) [2](#0-1)  which is only consumed by the ERC20 precompile's `Approve`/`Allowance`/`TransferFrom` [3](#0-2) [4](#0-3) .

While investigating consumers of the on-contract allowance path, I found the IBC callbacks module uses `approve()` on the native ERC20 contract to grant a target contract spend rights over funds held by a deterministic "isolated address" during `IBCReceivePacketCallback`, then invokes arbitrary attacker-supplied bytecode, and only afterward checks that the isolated address balance is zero to prevent stuck funds [5](#0-4) .

### Title
Premature state commit before fund-safety invariant check in `IBCReceivePacketCallback` permanently locks user funds - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`IBCReceivePacketCallback` grants an ERC20 allowance to an arbitrary attacker-supplied contract on behalf of a non-custodial "isolated address," executes that contract's arbitrary calldata, and only *after* calling `writeFn()` to commit the cached EVM state checks whether the isolated address still holds a nonzero token balance.

### Finding Description
The function builds a cached context (`cachedCtx, writeFn := ctx.CacheContext()`) to run two EVM calls: an `approve()` granting the destination contract an allowance over the isolated address's tokens, and then an arbitrary call into the destination contract using `cbData.Calldata` [6](#0-5) [7](#0-6) .

Immediately after the arbitrary contract call succeeds, the code calls `writeFn()`, which commits *all* cached state changes (the allowance grant, the destination contract's calls, and any state mutation the contract performed with its allowance) into the real `ctx` — and only afterward evaluates the invariant that is supposed to prevent stuck funds:

```go
// Write cachedCtx events back to ctx.
writeFn()

// Check that the sender no longer has tokens after the callback.
receiverTokenBalance := k.erc20Keeper.BalanceOf(ctx, erc20.ABI, tokenPair.GetERC20Contract(), receiverHex)
if receiverTokenBalance.Cmp(big.NewInt(0)) != 0 {
    return errorsmod.Wrapf(erc20types.ErrEVMCall,
        "receiver has %d unrecoverable tokens after callback", receiverTokenBalance)
}
``` [8](#0-7) 

The isolated address is deterministically derived from `(destChannel, sender)` and has no private key [9](#0-8) ; the module's own doc comment for this check explicitly states its purpose is to prevent funds from becoming irretrievable there. However, because `writeFn()` runs before the check, the commit to state is unconditional on the destination contract actually draining the isolated address's balance. If the destination contract's calldata deliberately (or due to a bug) leaves any nonzero token balance behind — e.g., by only partially calling `transferFrom`, or not calling it at all while still returning success — the function returns an error, but the tokens have already been moved into the destination contract's allowance-controlled/spent state and the isolated address's leftover dust is permanently stranded, since:
- The isolated address has no key to ever move the leftover balance.
- Returning an error at this point cannot undo the `writeFn()` that already ran, because `writeFn()` writes into the shared `ctx`, not into any context still under this function's control.

### Impact Explanation
This falls under the "Critical permanent freezing/locking of user funds" impact class. Any unprivileged user can trigger an IBC transfer with `destination_callback` memo pointing to a contract (their own or a buggy/malicious third-party contract) for a native-ERC20 token pair. If that destination contract does not consume 100% of the approved allowance/balance in its callback execution, the remainder becomes permanently and irrecoverably locked at the isolated address — with no reconciling mechanism, since the "safety" balance check runs only after the corrupting state is already durably committed via `writeFn()`, making the check a no-op with respect to actually preventing the loss it claims to prevent.

### Likelihood Explanation
Any user can initiate an ordinary IBC transfer (`MsgTransfer`) to a registered native-ERC20 token pair with an IBC-callbacks `destination_callback` memo referencing a contract that under-consumes its allowance (whether intentionally malicious or simply buggy). No privileged role, validator collusion, or relayer misbehavior is required — the trigger is a standard, unprivileged transaction/packet flow through the production IBC-callbacks + `x/erc20` integration path.

### Recommendation
Move the `receiverTokenBalance` invariant check to before `writeFn()` is invoked, evaluating it against `cachedCtx` (the state as it would be if committed) rather than against `ctx` after the fact. If the invariant fails, discard the cached context entirely (do not call `writeFn()`), returning an error so that the outer IBC callback middleware can appropriately handle failure without any partial, irreversible state commit having occurred.

### Proof of Concept
1. Register a native ERC20 token pair (`ERC20MinterBurnerDecimals`).
2. Deploy an attacker-controlled "callback target" contract whose function invoked by `cbData.Calldata` does nothing (or only partially calls `transferFrom`), returning success without draining the isolated address's balance to zero.
3. Submit an ordinary `MsgTransfer` (as any user, no special privileges) with an IBC-Go `destination_callback` memo pointing at this contract and a nonzero token amount for the registered denom.
4. During `OnRecvPacket` processing, `IBCReceivePacketCallback` approves the contract, invokes it, and calls `writeFn()` — committing the approval/allowance state — before checking `receiverTokenBalance`.
5. Because the contract left a nonzero balance, the function returns `ErrEVMCall` ("receiver has %d unrecoverable tokens after callback"), but the isolated address's tokens remain stuck at an address with no corresponding private key, permanently unrecoverable by the sender or the protocol.

func (k Keeper) GetAllowance(
	ctx sdk.Context,
	erc20 common.Address,
	owner common.Address,
	spender common.Address,
) (*big.Int, error) {
	allowanceKey := types.AllowanceKey(erc20, owner, spender)
	store := prefix.NewStore(ctx.KVStore(k.storeKey), types.KeyPrefixAllowance)

	var allowance types.Allowance
	bz := store.Get(allowanceKey)
	if bz == nil {
		return common.Big0, nil
	}

	k.cdc.MustUnmarshal(bz, &allowance)

	return allowance.Value.BigInt(), nil
}

	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
	method *abi.Method,
	args []interface{},
) ([]byte, error) {
	spender, amount, err := ParseApproveArgs(args)
	if err != nil {
		return nil, err
	}

	owner := contract.Caller()

	// TODO: owner should be the owner of the contract
	allowance, err := p.erc20Keeper.GetAllowance(ctx, p.Address(), owner, spender)
	if err != nil {
		return nil, sdkerrors.Wrap(err, fmt.Sprintf(ErrNoAllowanceForToken, p.tokenPair.Denom))
	}

	switch {
	case allowance.Sign() == 0 && amount != nil && amount.Sign() < 0:
		// case 1: no allowance, amount 0 or negative -> error
		err = ErrNegativeAmount
	case allowance.Sign() == 0 && amount != nil && amount.Sign() > 0:
		// case 2: no allowance, amount positive -> create a new allowance
		err = p.setAllowance(ctx, owner, spender, amount)
	case allowance.Sign() > 0 && amount != nil && amount.Sign() <= 0:
		// case 3: allowance exists, amount 0 or negative -> remove from spend limit and delete allowance if no spend limit left
		err = p.erc20Keeper.DeleteAllowance(ctx, p.Address(), owner, spender)
	case allowance.Sign() > 0 && amount != nil && amount.Sign() > 0:
		// case 4: allowance exists, amount positive -> update allowance
		err = p.setAllowance(ctx, owner, spender, amount)
	}
