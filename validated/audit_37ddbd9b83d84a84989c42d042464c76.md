### Title
Forged `ReceivedOutput` records make unspendable inputs appear spendable - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts the spending-key offset, claimed `TxOut`, and `OutPoint` as three independent attacker-controlled fields without checking that the `OutPoint` references a real UTXO containing that `TxOut`. [1](#0-0)  Although `SignableTransaction::multisig` verifies that the claimed output script equals `key + offset * G`, it does not verify the referenced outpoint or its on-chain contents. [2](#0-1)  The transaction builder then uses the claimed output value for balance accounting and the attacker-selected outpoint as the transaction input. [3](#0-2) 

### Finding Description
`Scanner::scan_transaction` creates internally consistent `ReceivedOutput` values by pairing a recognized `script_pubkey` with its registered offset and the real transaction outpoint. [4](#0-3)  `ReceivedOutput::read` provides no equivalent validation: it accepts any scalar, any serialized `TxOut`, and any serialized `OutPoint`. [5](#0-4) 

When the forged record reaches `SignableTransaction::new`, its declared `output.value` is included in `input_sat`, while `outpoint` is copied directly into the unsigned transaction. [3](#0-2)  The later signing setup only compares `prevouts[i].script_pubkey` with the script derived from the threshold key and supplied offset; the `OutPoint` itself remains unauthenticated. [2](#0-1) 

The signing digest commits to the forged prevout list through `Prevouts::All`, so participants produce signatures for a transaction whose declared input does not correspond to the alleged spendable UTXO. [6](#0-5)  Completion places the signatures into every input and returns the transaction as successfully completed. [7](#0-6) 

### Impact Explanation
An untrusted serialized `ReceivedOutput` can inflate the reported input balance and satisfy the key/script check while naming a nonexistent or unrelated outpoint. [3](#0-2)  This permits funds to be represented as received and available for spending when they are not actually spendable. [8](#0-7)  A completed transaction can still be rejected by Bitcoin consensus because its input references no matching UTXO, turning the false balance into an invalid or stalled spend. [9](#0-8) 

### Likelihood Explanation
The attacker only needs to supply bytes accepted by `ReceivedOutput::read`; obtaining a matching script is straightforward because `p2tr_script_buf(key + GENERATOR * offset)` is public and deterministic. [10](#0-9)  No private key, validator privilege, malformed signature, or control over consensus state is required. [5](#0-4)  Successful exploitation requires the consumer to deserialize untrusted `ReceivedOutput` records rather than exclusively using objects returned by `Scanner`. [4](#0-3) 

### Recommendation
Treat `ReceivedOutput` deserialization as untrusted input and bind it to authenticated scan state before balance accounting or signing. [5](#0-4)  At minimum, resolve each `outpoint` against the blockchain, require the returned UTXO to equal `output`, and require its script to equal the scanner-derived script for the claimed offset before constructing `SignableTransaction`. [2](#0-1)  Prefer a checked constructor that accepts a scanner plus consensus-verified UTXO over exposing an unchecked tuple deserializer for spending decisions. [11](#0-10) 

### Proof of Concept
```rust
use bitcoin::{
  absolute::LockTime, transaction::Version, Amount, OutPoint, ScriptBuf,
  Transaction, TxIn, TxOut, Txid,
};
use bitcoin::consensus::encode::serialize;
use bitcoin::hashes::Hash;
use frost::curve::{Ciphersuite, Secp256k1};
use k256::{ProjectivePoint, Scalar};
use std::collections::HashMap;
use std::io::Write;

// `group_key` is the even-Y threshold key used by Scanner::new.
let offset = Scalar::ZERO;
let script = p2tr_script_buf(group_key).unwrap();

// Claim a large prevout controlled by the threshold key.
let claimed_prevout = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: script.clone(),
};

// Name an outpoint which does not exist, or which references unrelated data.
let fake_outpoint = OutPoint {
  txid: Txid::from_byte_array([0x41; 32]),
  vout: 0,
};

// ReceivedOutput::read format:
//   32-byte scalar || consensus TxOut || consensus OutPoint
let mut forged = Vec::new();
forged.write_all(&offset.to_bytes()).unwrap();
forged.extend(serialize(&claimed_prevout));
forged.extend(serialize(&fake_outpoint));

let received = ReceivedOutput::read(&mut forged.as_slice()).unwrap();
assert_eq!(received.value(), 1_000_000);

// The script/offset consistency check succeeds because claimed_prevout uses
// p2tr_script_buf(group_key + GENERATOR * offset).
let tx = SignableTransaction::new(
  vec![received],
  &[(ScriptBuf::new_op_return(&[] as &[_]), 546)],
  None,
  None,
  1,
).unwrap();

// This returns Some because it validates only the claimed script against the
// offset-derived group key, not whether fake_outpoint contains that prevout.
let machine = tx.multisig(&threshold_keys).unwrap();
```

The forged record passes the local consistency check and is counted as one million satoshis of input, while the resulting transaction references `fake_outpoint` rather than a proven UTXO containing `claimed_prevout`. [12](#0-11)  Signing commits the participant set to the forged prevout through `Prevouts::All`, and `complete` returns a fully witnessed transaction that consensus cannot accept if the outpoint is absent or contains different output data. [13](#0-12)
