### Title
Nil-pointer dereference in legacy `HandlePrecompileError` (missing nil-check on `GetDBImpl`) - ([File: precompiles/common/legacy/v605/precompiles.go])

### Summary
The historical/legacy precompile-common packages `v605`, `v606`, and `v610` implement `HandlePrecompileError` without checking whether `state.GetDBImpl(evm.StateDB)` returned `nil` before calling a method on it, unlike every later version of the same helper.

### Finding Description
`state.GetDBImpl` performs a type assertion against `vm.StateDB` and explicitly returns `nil` when the underlying `StateDB` is neither `*DBImpl` nor `*state.HookedStateDB`: [1](#0-0) 

In the legacy packages `v605`, `v606`, and `v610`, the deferred error handler dereferences that possibly-nil pointer unconditionally: [2](#0-1) 

This is structurally identical to the CVE-2021-47652 pattern: a resource pointer that is not guaranteed to be initialized (`GetDBImpl` can legitimately return `nil`) is dereferenced unconditionally in an error/cleanup path (`HandlePrecompileError`), rather than being checked first. Every later revision of the same helper (`v66`, `v67`, `v630`, `v640`, and the current `precompiles/common/precompiles.go`) fixed exactly this by adding a nil guard: [3](#0-2) 

Both `Prepare()` in the same legacy files already anticipate a nil `GetDBImpl` result and return an error instead of crashing: [4](#0-3) 
but `HandlePrecompileError`, which is invoked from every versioned precompile's `Run`/`RunAndCalculateGas` deferred error handler (staking, gov, distribution, bank, pointer, wasmd, addr, oracle, json, p256, pointerview), was left unpatched in these three legacy snapshots.

### Impact Explanation
If any code path passes a `vm.StateDB` that is not a `*state.DBImpl`/`*state.HookedStateDB` into one of these frozen legacy precompile implementations (which are dispatched by block height for historical-consistency reasons, per `app/upgrades.go` / `app/app.go` version wiring), and that call returns a non-nil `err`, the deferred `HandlePrecompileError` will panic with a nil-pointer dereference. Because this runs inside EVM precompile execution reached from `eth_call`/`debug_traceCall`/transaction replay at the pinned historical heights, a crafted call that trips any precompile error condition at one of these frozen versions can crash the node process handling it — satisfying "crash of default-configuration RPC nodes."

### Likelihood Explanation
Medium. The crash requires (a) execution routed through one of the three legacy precompile versions (height-gated, used for replay/historical-state consistency) and (b) a `vm.StateDB` value that fails the `*DBImpl`/`*HookedStateDB` type assertion at that call site while a precompile method also returns an error. I could not fully confirm from the index which exact call path supplies a non-DBImpl `StateDB` to these specific legacy versions (e.g., an alternate simulation/tracing wrapper) — this is the main gap in the analysis and would need to be validated with a live reproduction or fuller call-graph trace than the index allows.

### Recommendation
Apply the same nil-guard used in the newer versions to the legacy `HandlePrecompileError` implementations in `precompiles/common/legacy/v605/precompiles.go`, `precompiles/common/legacy/v606/precompiles.go`, and `precompiles/common/legacy/v610/precompiles.go`:
```go
func HandlePrecompileError(err error, evm *vm.EVM, operation string) {
	if err != nil {
		if sdb := state.GetDBImpl(evm.StateDB); sdb != nil {
			sdb.SetPrecompileError(err)
		}
		metrics.IncrementErrorMetrics(operation, err)
	}
}
```

### Proof of Concept
Not independently reproduced within Ask-mode (no code execution available). The theoretical trigger: invoke any EVM precompile (e.g. staking, gov, bank) at a historical block height that routes to the `v605`/`v606`/`v610` legacy implementation, with an `evm.StateDB` that is not `*state.DBImpl`/`*state.HookedStateDB` (e.g., via a call/trace path using an alternate `vm.StateDB` wrapper), and cause the precompile method to return a non-nil error — the deferred `HandlePrecompileError` then dereferences a nil `*DBImpl`. Confirming the exact caller that supplies a non-`DBImpl` `StateDB` to these legacy paths would require deeper call-graph tracing than available here; flagged as unverified but structurally consistent with the CVE's root cause and with the fix later applied elsewhere in the same codebase.
