### Title
Stale cached working-directory status lets Copilot conflict-resolution overwrite user's own conflict edits - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_applyCopilotConflictResolutions` decides whether to write Copilot's resolved file content to disk based on a single snapshot of `state.changesState.workingDirectory.files` taken at the very start of the function. This mirrors the Notional bug pattern: a "healthy/unhealthy" (here, "resolved/unresolved") check is performed once, and then an action (writing files) is taken later, without re-validating the condition against current on-disk reality at the moment of the write.

### Finding Description
`_applyCopilotConflictResolutions` fetches `state` once via `this.repositoryStateCache.get(repository)` and then, for every file in `copilotResolutions`, uses that single stale `state.changesState.workingDirectory.files` snapshot to decide if the file "was resolved externally" before overwriting it: [1](#0-0) [2](#0-1) 

The comment at lines 7241-7246 explicitly acknowledges the race being guarded against ("If the user resolved this file externally ... while the result dialog was open") but the guard only checks a cached status object, not a freshly recomputed git status immediately before `writeFile`. The `state.changesState.workingDirectory.files` used here is whatever was last pushed into the `repositoryStateCache` by a background status refresh — it is not re-queried inside this function, and there's no `await getStatus(...)` call before the write loop. Given the dialog can remain open for a long time (the user reviews per-file summaries, opens files in an external editor via `onOverflowMenuClick`/`openFileInExternalEditor`, resolves conflicts manually, and only then clicks "Continue"), the cached snapshot captured at populate-time (or at whatever the last background refresh happened to catch) can be arbitrarily stale relative to the moment `_applyCopilotConflictResolutions` actually executes and writes.

The dialog itself relies on the same kind of state (`this.props.workingDirectory` passed as a prop) to render "resolved externally" rows and to gate the Continue button (`hasUnresolvedSkippedFiles`) via `isFileResolvedExternally`/`isSkippedFileResolved`: [3](#0-2) [4](#0-3) 

But `onContinue` immediately dispatches `applyCopilotConflictResolutions` without triggering (or awaiting) any fresh status refresh, so both the UI decision and the actual write use whatever `workingDirectory`/`changesState` snapshot happened to be cached — there is no explicit re-stat/re-status call guaranteeing the write-time check reflects the current file contents.

### Impact Explanation
If a user manually finishes resolving a conflicted file in their editor (removing markers, saving) in the window between when the last background status refresh occurred and when they click "Continue", but before another status refresh lands in the cache, `onDiskFile`'s cached status can still show it as unresolved/conflicted. The stale guard then fails to detect the external resolution, and `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` silently overwrites the user's manually resolved content with Copilot's earlier-computed resolution, and the file is then staged with `git add`. This is a silent corruption of what the user commits/pushes — exactly one of the explicitly accepted impact categories (silent corruption of what the user commits) — with no error, warning, or diff shown to the user before the overwrite.

### Likelihood Explanation
This requires only a normal, unprivileged workflow: a user resolving conflicts with Copilot conflict resolution enabled, editing a file externally while the result dialog is open (a documented, intended UI affordance via the "Open in <editor>" / overflow menu action at lines 212-237 of `copilot-conflicts-dialog.tsx`), and clicking Continue before any status refresh happens to re-sync the cache. No git remote/API manipulation, admin rights, or malware is needed — the race window is inherent to how long conflict-resolution dialogs typically stay open (users reviewing multiple files, reading reasoning, or context-switching to an editor).

### Recommendation
Before writing each resolution (or at minimum before the write loop), re-fetch actual on-disk/git status instead of relying on the cached `state.changesState.workingDirectory.files`. Concretely, call `getStatus(repository, ...)` (or equivalent) immediately prior to the loop in `_applyCopilotConflictResolutions`, and re-check `hasUnresolvedConflicts`/`isConflictedFileStatus` against that fresh result rather than the value obtained from `this.repositoryStateCache.get(repository)` at function entry. This closes the check-then-act gap by ensuring the "is this file still actually conflicted on disk" check happens atomically (as close as possible) to the write, analogous to re-validating `isExternalLendingUnhealthy` right before executing the rebalance rather than trusting a stale precomputed value.

### Proof of Concept
1. Trigger a merge/rebase/cherry-pick with conflicts and enable Copilot conflict resolution so the app populates `copilotResolutions` and shows `CopilotConflictsDialog`.
2. While the dialog is open, use the overflow menu to "Open in <editor>" for one of the conflicted files (`onOverflowMenuClick` → `openFileInExternalEditor`), manually resolve the conflict in the external editor, and save the file — without triggering an app-visible status refresh event beforehand.
3. Immediately click "Continue" in the dialog, invoking `onContinue` → `dispatcher.applyCopilotConflictResolutions(repository)` → `_applyCopilotConflictResolutions`.
4. Because `state.changesState.workingDirectory.files` still reflects the pre-edit status snapshot, `onDiskFile` at line 7247 is evaluated against the stale conflicted status, `hasUnresolvedConflicts(onDiskFile.status)` returns true, and the guard at lines 7250-7256 does not `continue`.
5. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` at line 7258 overwrites the user's manually resolved content with Copilot's resolution, then the file is staged via `git add`, silently discarding the user's edits.
