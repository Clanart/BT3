## Analysis

The reported Solana bug is a **boundary/containment validation function that appears to enforce a limit but has a logic gap allowing the checked value to "escape" the intended boundary** (`level == MAX_LEVEL` instead of `level >= MAX_LEVEL`). The closest verified analog in the GitHub Desktop codebase is a path-containment check that uses raw string-prefix comparison instead of a path-boundary-aware comparison, in `_resolveWithin` in `app/src/lib/path.ts`.

### Title
Path containment check in `_resolveWithin` uses unsafe string-prefix comparison, allowing deep-link-controlled paths to escape the intended repository root - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin` is the shared guard used across Desktop to guarantee that a caller-supplied relative path resolves to a location "at, or underneath" a given root path (e.g. a repository directory) before that path is used for filesystem operations. Its final check is a plain `String.prototype.startsWith` comparison rather than a path-segment-aware comparison, so a resolved path that merely shares a string prefix with the root (e.g. a sibling directory) is incorrectly treated as being contained within the root.

### Finding Description
The containment decision is made here: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` has no concept of path separators. If `realRoot` is `/Users/x/repo`, any real path beginning with the literal characters `repo` will pass, including a sibling directory such as `/Users/x/repo-secrets` or `/Users/x/repository-backup`. This is the same class of flaw as the reported bug: the function's job is to enforce "path must remain inside the boundary," but the actual comparison only checks a necessary-but-insufficient condition (equal-or-prefix as raw characters) rather than the real invariant (equal, or prefix immediately followed by a path separator). Just as `calculate_points_for_level` silently permits `level > MAX_LEVEL` because it never generalizes its `==` check, `_resolveWithin` silently permits `realResolved` outside `realRoot` because it never checks for a trailing separator boundary.

This helper is consumed directly by an attacker-reachable, deep-link-driven code path: [2](#0-1) 

```
private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
  const { url, pr, branch, filepath } = action
  ...
  if (filepath !== null) {
    if (isAbsolute(filepath)) {
      log.error(`Refusing to open absolute path: ${filepath}`)
      return
    }
    const resolved = await resolveWithin(repository.path, filepath)
    if (resolved !== null) {
      shell.showItemInFolder(resolved)
    } else {
      log.error(`Prevented attempt to open path outside of the repository root: ${filepath}`)
    }
  }
}
```

The absolute-path check (`isAbsolute`) is not a substitute for the `resolveWithin` boundary check — it only rejects one bypass technique (absolute paths) while leaving the prefix-collision technique (`../repo-sibling/...`) unaddressed, because `resolveWithin` is expected to be the actual gate.

`_resolveWithin` is also used from `app/src/lib/copilot-conflict-context.ts` and `app/src/lib/stores/app-store.ts` as a general-purpose "keep this path inside that root" primitive, so any caller relying on it for a security boundary inherits the same weakness. [3](#0-2) 

### Impact Explanation
`openRepositoryFromUrl` is triggered by GitHub Desktop's custom URL/deep-link protocol handler (`x-github-client://openRepo?...&filepath=...`), i.e. it is invoked purely by a link the user clicks — matching the "link or deep link the user clicks" attacker-controlled entry point. A crafted `filepath` value such as `../repo-secrets/some-file` can cause `resolveWithin` to resolve to, and validate as "within", a directory outside the actual repository (e.g. `<repoParent>/repo-secrets`) as long as the sibling name shares the repository directory name as a string prefix. `shell.showItemInFolder` is then called on that out-of-repo path, revealing to the OS shell (and thus to the user's screen/Finder/Explorer) the existence and location of files/folders outside the repository that the attacker predicted or probed for — a file/path disclosure outside the intended repository root, consistent with the accepted impact class "file write or read outside the repo."

### Likelihood Explanation
Exploitation requires the victim to click a maliciously crafted `x-github-client://` deep link (no local access, no admin rights, and no prior malware needed) and requires the attacker to have some knowledge or guess of a sibling directory name near the target repository that shares a prefix with the repository's directory name (e.g. common patterns like `repo`, `repo-old`, `repo.bak`, `repository`). This makes it a plausible but not universally-reliable path-disclosure primitive — it depends on directory naming coincidences on the victim's disk, which lowers likelihood compared to a fully deterministic traversal bug, but the underlying validation defect itself is deterministic and always present.

### Recommendation
Replace the raw `startsWith` string comparison in `_resolveWithin` (`app/src/lib/path.ts:71`) with a boundary-aware check, e.g. verify `realResolved === realRoot || realResolved.startsWith(realRoot + path.sep)`, so that only genuine descendants of `realRoot` are considered "within" it.

### Proof of Concept
1. Victim has a repository open at `/Users/victim/projects/repo` and, elsewhere on disk, a directory `/Users/victim/projects/repo-secrets` containing sensitive files.
2. Attacker sends the victim a link: `x-github-client://openRepo?url=<repo-url>&filepath=..%2Frepo-secrets%2Fnotes.txt`.
3. Victim clicks the link; Desktop's protocol handler invokes `openRepositoryFromUrl`, which calls `resolveWithin(repository.path, "../repo-secrets/notes.txt")`.
4. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/projects/repo-secrets/notes.txt`; `realResolved.startsWith(realRoot)` evaluates true because `"/Users/victim/projects/repo-secrets/notes.txt".startsWith("/Users/victim/projects/repo")` is true, even though the file is outside `repo`.
5. `shell.showItemInFolder(resolved)` opens the OS file browser directly at the out-of-repository file, disclosing its existence/location to whatever is rendered on screen (and to any subsequent action the victim takes there).

Note: I was unable to inspect the exact contents of `copilot-conflict-context.ts` and `app-store.ts`'s use of `resolveWithin` within the available iterations; if those call sites feed resolved paths into read/write operations (rather than just UI navigation), the impact could be more severe (arbitrary file read/write) and should be verified separately.
