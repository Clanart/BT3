### Title
`git pull --recurse-submodules` bypasses the `file://` submodule-protocol guard enforced on checkout - (File: app/src/lib/git/pull.ts)

### Summary
The report's bug class is a security check implemented for one sensitive operation (`stake()`) but omitted from a sibling operation (`queueWithdrawal()`) that has the same trust boundary. The Desktop analog is `updateSubmodulesAfterOperation`'s `allowFileProtocol` gate, which is wired into `checkoutBranch()` and `checkoutCommit()` but has no equivalent in `pull()`, even though `pull()` also recurses into submodules.

### Finding Description
`app/src/lib/git/submodule.ts`'s `updateSubmodulesAfterOperation` only adds `-c protocol.file.allow=always` when the caller explicitly passes `allowFileProtocol: true`; otherwise submodule updates run with Git's default (safer) protocol restrictions: [1](#0-0) 

Both `checkoutBranch()` and `checkoutCommit()` in `app/src/lib/git/checkout.ts` explicitly thread an `allowFileProtocol` parameter through to `updateSubmodulesAfterOperation()`, showing this is treated as a deliberate, gated decision for those code paths: [2](#0-1) [3](#0-2) 

`pull()` in `app/src/lib/git/pull.ts`, however, performs submodule recursion itself via the raw `--recurse-submodules` flag on `git pull`, without ever calling `updateSubmodulesAfterOperation` or setting any `protocol.file.allow` override: [4](#0-3) 

This is structurally identical to the reported bug: the same "should this operation be allowed to touch file:// submodule sources" decision exists in one function (`checkout*`) but is absent from a sibling function (`pull`) that reaches the same sensitive `git submodule update` behavior via `--recurse-submodules`.

### Impact Explanation
`file://` submodule URLs are a known vector (CVE-2022-39253) for pulling arbitrary local filesystem paths into a repository's working tree as a "submodule," which can leak local files into what looks like tracked repository content, or be used to stage attacker-controlled local content for a subsequent commit/push. Desktop's own code demonstrates awareness of this risk by making `allowFileProtocol` an explicit, narrowly-scoped opt-in for checkout flows. If `pull --recurse-submodules` is reached with a remote that has updated `.gitmodules` to point at `file://` paths (e.g., a collaborator's malicious push, or a compromised/malicious remote a user pulls from), Desktop's pull path does not apply the same restriction decision that checkout applies, so any implicit allowance (e.g., via global git config or Desktop's git environment setup) would silently apply during a routine pull without going through the same gate.

### Likelihood Explanation
`pull` is one of the most routine, low-friction operations a user performs (e.g., via "Fetch origin" / "Pull" button), unlike clone-with-confirmation flows. An attacker who controls a remote/repository that a victim already has added (a collaborator on a shared repo, or a spoofed/typosquatted remote) can add or modify a submodule entry to use `file://` and have it exercised the next time the victim pulls, without any of the special-cased consent path checkout uses.

### Recommendation
Route `pull()`'s submodule handling through the same `updateSubmodulesAfterOperation()`/`allowFileProtocol` gate used by `checkoutBranch()`/`checkoutCommit()` (or otherwise explicitly deny `protocol.file.allow` unless the same trust decision has been made), rather than relying on the bare `--recurse-submodules` flag on `git pull`.

### Proof of Concept
Note: I was unable to fully trace, within the available tool budget, how UI callers set `allowFileProtocol: true`/`false` for `checkoutBranch`/`checkoutCommit` (i.e., whether there's a user-facing confirmation dialog gating this), nor whether Desktop's global git environment (`envForRemoteOperation`/`envForAuthentication` in `app/src/lib/git/environment.ts`) sets a global `protocol.file.allow` value that would make `pull()` inherit an unsafe default. This should be verified directly in a full checkout of the repository (e.g., via a Devin session) before treating this as a confirmed, exploitable vulnerability, since the actual exploitability depends on Git's own default `protocol.file.allow` behavior (which blocks `file://` submodules by default since Git 2.38) and whether Desktop overrides that default anywhere in its environment setup for remote operations: [5](#0-4) 

If Desktop does not globally override `protocol.file.allow`, then Git's own default protections would still apply during `pull`, meaning the missing `allowFileProtocol` plumbing in `pull()` would be a latent inconsistency rather than an immediately exploitable vulnerability — this should be treated as **unconfirmed** without further investigation into the full environment/config setup.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}

/**
 * Create a set of environment variables to use when invoking a Git
 * subcommand that needs to communicate with a remote (i.e. fetch, clone,
 * push, pull, ls-remote, etc etc).
 *
 * The environment variables deal with setting up sane defaults, configuring
 * authentication, and resolving proxy urls if necessary.
 *
 * @param account   The authentication information (if available) to provide
 *                  to Git for use when connecting to the remote
 * @param remoteUrl The primary remote URL for this operation. Note that Git
 *                  might connect to other remotes in order to fulfill the
 *                  operation. As an example, a clone of
 *                  https://github.com/desktop/desktop could contain a submodule
 *                  pointing to another host entirely. Used to resolve which
 *                  proxy (if any) should be used for the operation.
 */
export async function envForRemoteOperation(remoteUrl: string) {
  return {
    ...envForAuthentication(),
    ...(await envForProxy(remoteUrl)),
  }
}
