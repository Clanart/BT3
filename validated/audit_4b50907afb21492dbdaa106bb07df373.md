### Title
Data Layer server-side HTTP fetch of attacker-published mirror URLs enables SSRF against internal network / cloud metadata - ([File: chia/data_layer/download_data.py])

### Summary
Any wallet user can publish an on-chain "mirror" record for a DataLayer store containing arbitrary attacker-chosen URL strings via `DataLayerWallet.create_new_mirror()`. These URLs are stored as coin memos on-chain (unrestricted, free-form strings), later read back by any DataLayer node/client that syncs that store, and are automatically dereferenced with server-side outbound HTTP GET requests with no validation that the target host is not localhost, an RFC1918 address, or a cloud metadata endpoint. This mirrors the Flowise HTTP-Node SSRF bug class: user-controlled URL → unrestricted server-side HTTP fetch.

### Finding Description
`DataLayerWallet.create_new_mirror()` lets a wallet (any spend-bundle submitter with a DL wallet) create a mirror coin whose puzzle hash is the fixed `create_mirror_puzzle()` hash and whose memos encode `[launcher_id, *urls]` with no format or host validation: [1](#0-0) 

The `Mirror` dataclass simply UTF-8 encodes/decodes whatever URL strings are supplied, again with no scheme/host restriction: [2](#0-1) 

These mirror URLs are readable by any wallet RPC caller/DataLayer client via `dl_get_mirrors` and are fed directly into `DataStore.update_subscriptions_from_wallet(store_id, urls)`: [3](#0-2) 

When a DataLayer service (or any peer subscribing to that store id) later syncs, `fetch_and_validate()` selects one of these attacker-supplied server URLs and passes it straight into the delta-file download path: [4](#0-3) 

`insert_from_delta_file()`/`download_file()` then perform an unrestricted `aiohttp` GET (via `http_download`) directly against `server_info.url`, with no allow-list, no private-IP/localhost blocking, and only an optional user-configured `proxy_url`: [5](#0-4) 

There is no SSRF-hardening anywhere in this path (no check against `127.0.0.1`, `169.254.169.254`, RFC1918 ranges, etc.). The only "validation" performed is on the downloaded *filename* format (`is_filename_valid`) and the response *size*, not on the destination host of the request itself.

### Impact Explanation
A malicious store owner who mints/updates a DL mirror to point at `http://127.0.0.1:<port>`, `http://169.254.169.254/latest/meta-data/...`, or any internal-only host will cause every honest node/operator running a DataLayer service that subscribes to (or owns/mirrors) that store to issue outbound HTTP GET requests to that internal target from the DataLayer server process. This can be used to probe or exfiltrate data from internal services reachable from the DataLayer host, including cloud instance-metadata credential endpoints, replicating the "read" impact of the Flowise SSRF (impact is limited to GET requests in this HTTP client, unlike Flowise's arbitrary-method HTTP node, so write/RCE-via-method abuse does not directly apply here). This satisfies the "coin-set/consistency divergence" bar loosely (peers can be steered to fetch from attacker infrastructure and diverge on file availability/backoff state) but more directly it is a genuine SSRF against operator-only infrastructure triggered purely by a normal DL mirror-creation spend that any wallet holder can submit — no privileged access is required to publish the malicious URL.

### Likelihood Explanation
Likelihood is Medium: the attacker needs only to run `create_new_mirror`/`dl_new_mirror` (a standard wallet RPC/CLI operation, `chia data add_mirror`) with a spend anyone can construct and get accepted into the mempool; no special permission is required. The victim side requires that some other operator's DataLayer service subscribes to (or is a mirror server candidate for) the attacker's store, which is a normal/expected DataLayer usage pattern (subscribing to third-party stores is the whole point of the mirror mechanism).

### Recommendation
Add SSRF protections to the DataLayer HTTP download path (`chia/data_layer/download_data.py: http_download`) and mirror-URL acceptance path (`chia/data_layer/data_layer_wallet.py: Mirror`/`create_new_mirror`):
- Validate/resolve mirror URLs before use and reject (or require explicit operator opt-in for) loopback, link-local (`169.254.0.0/16`), and RFC1918 private ranges.
- Enforce an allow-list/deny-list configuration option (default deny private ranges) analogous to the suggested Flowise fix.
- Consider validating scheme (`http`/`https` only) and disallowing credentials-in-URL or unusual ports commonly used for internal services, and log/flag mirrors whose URLs resolve to non-routable addresses.

### Proof of Concept
1. Attacker creates/owns a DataLayer store and calls `dl_new_mirror` (`chia/wallet/wallet_rpc_api.py` `dl_new_mirror`, backed by `DataLayerWallet.create_new_mirror`) with `urls=["http://127.0.0.1:8000/", "http://169.254.169.254/latest/meta-data/iam/security-credentials/"]`. This is a normal signed spend bundle, accepted by mempool rules like any other spend.
2. A victim operator's DataLayer service subscribes to the attacker's `store_id` (a supported, expected DataLayer workflow) — `update_subscriptions_from_wallet` pulls the attacker's URLs from `dl_get_mirrors` into the local subscription's server list (`chia/data_layer/data_layer.py:979-985`).
3. On the victim's next sync cycle, `fetch_and_validate()` (`chia/data_layer/data_layer.py:642-706`) picks the attacker's URL and calls `insert_from_delta_file` → `download_file` → `http_download` (`chia/data_layer/download_data.py:298-324`), issuing an unrestricted GET from the victim's DataLayer host to the attacker-chosen internal/loopback/metadata address, with the response content parsed as delta-file bytes (failure is silently logged, but the request itself is fully executed server-side against the internal target).

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
