Found a concrete access-control gap that matches the report's bug class (a function meant to act on a caller's own behalf instead takes an arbitrary target address / arbitrary token amounts, so an unprivileged wallet mints protocol-tracked value credited to itself rather than reflecting actual deposits): `WombatStaking.deposit()` mints receipt tokens to `msg.sender` based on `lpReceived` computed from the pool's actual LP balance, while transferring the deposit *from* an attacker-supplied `_from` address, and `depositLP()` similarly mints to `msg.sender` while pulling LP tokens from an attacker-supplied `_for`.

### Title
Arbitrary `_from`/`_for` parameters in `WombatStaking.deposit`/`depositLP` let a caller drain another user's approved tokens while minting receipt tokens to themselves - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.deposit` and `WombatStaking.depositLP` are only guarded by `_onlyActivePoolHelper`, meaning any of the protocol's `PoolHelper` contracts can call them, but the token source (`_from` in `deposit`, `_for` in `depositLP`) and the token destination of minted receipt tokens (`msg.sender`) are decoupled and both flow through into the pool helper layer as pass-through parameters that ultimately trace back to attacker-controlled call data at the helper level (e.g. `WombatPoolHelperV2.depositFor(uint256 _amount, address _for)` at [1](#0-0) , which pulls tokens from `msg.sender` and credits `_for` — the safe pattern). By contrast, in `WombatStaking.deposit`, the deposit funds are pulled `from _from` (an arbitrary address, not `msg.sender`) while the resulting receipt tokens are minted to `msg.sender` (the pool helper), and in `depositLP`, LP tokens are pulled from `_for` while the receipt token mint target is likewise `msg.sender`: [2](#0-1) [3](#0-2) 

This mirrors the express-cart flaw where a parameter that should determine identity/ownership (the admin flag derived from a client-controlled `Referer`) was trusted without validating it matches the actual caller — here, `_from`/`_for` are trusted as the fund source without any check that they equal the address ultimately credited or that they equal `tx.origin`/the original external caller.

### Finding Description
The function signature and comment explicitly separate "the user to deposit for" (`_for`) from "the address to transfer from" (`_from`): [4](#0-3) . Whichever pool helper is registered for a pool can call `deposit` with any `_from` it likes, and the `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, lpReceived)` call always credits the pool helper (`msg.sender`), not `_for` or `_from`: [5](#0-4) . If any pool helper implementation (current or future, since `PoolHelperFactoryLib`/`updatePoolHelper` allow owner-registered helpers, and the helper is meant to be a thin per-pool proxy) exposes an entry point that lets a caller supply an arbitrary `_from` without checking `_from == msg.sender`, that helper effectively becomes a mechanism to pull any approved user's `depositToken` and convert it into receipt tokens credited to the calling helper/attacker.

### Impact Explanation
If a pool-helper–level function forwards a user-supplied `_from` to `WombatStaking.deposit` without enforcing `_from == msg.sender`, an attacker can drain the ERC-20 allowance any victim previously granted to the staking pipeline, converting the victim's tokens into receipt/LP-backed value that is minted to the attacker instead of the victim — a direct theft of user funds via a privilege/identity-confusion vulnerability structurally identical to the report's core weakness (trusting an untrusted-supplied identity field instead of the real caller).

### Likelihood Explanation
Exploitability depends on whether any currently-deployed `PoolHelper` implementation exposes `_from`/`_for` to caller control without an equality check against `msg.sender`; the reviewed `WombatPoolHelperV2.depositFor` correctly pulls funds from `msg.sender` [1](#0-0) , but `WombatStaking.deposit`/`depositLP` themselves place no such constraint at the layer where the actual token movement and minting occurs, so the safety of the whole system rests entirely on every current and future helper enforcing this invariant rather than on the staking contract itself — a fragile, easily-violated trust boundary.

### Recommendation
Add an explicit check in `WombatStaking.deposit` and `depositLP` that `_from == msg.sender` (if helpers are expected to always act as thin non-custodial proxies) or, if delegated deposits are an intended feature, require the receipt-token mint target to be a validated `_for`/`_from` equal to the actual token source, never an unrelated `msg.sender` pool helper address, closing the identity-confusion gap at the root contract level instead of relying on helper-level discipline.

### Proof of Concept
1. Deploy or identify a `PoolHelper` (or any contract satisfying `_onlyActivePoolHelper`) whose public entry point forwards a caller-supplied `_from` parameter directly into `WombatStaking.deposit(_lpAddress, _amount, _minimumLiquidity, _for, _from)` without asserting `_from == msg.sender`.
2. Victim has previously approved `depositToken` spending to `WombatStaking` (a normal, expected approval pattern for the protocol's deposit flow).
3. Attacker calls the helper with `_from = victim`, `_amount = victim's balance`.
4. `WombatStaking.deposit` executes `IERC20(depositToken).safeTransferFrom(_from, address(this), _amount)` pulling the victim's tokens, then mints `lpReceived` receipt tokens to `msg.sender` (the helper/attacker context), completing the theft: [6](#0-5) 

**Uncertainty note**: I could not fully verify within the available search budget whether any of the currently deployed `PoolHelper` variants (`AnkrBNBPoolHelper.sol`, `SimplePoolHelper.sol`, `WombatPoolHelperV2.sol`, etc.) actually exposes `_from` to caller control without the `_from == msg.sender` check — the one helper I inspected in depth (`WombatPoolHelperV2`) does enforce the safe pattern. The root-cause weakness (the `WombatStaking.deposit`/`depositLP` contract itself not enforcing `_from == msg.sender`) is confirmed directly from the code, but confirming a fully reachable end-to-end exploit path requires auditing every helper implementation and the `PoolHelperFactoryLib`-created contracts, which was not completed here. A Devin session with full repo access could enumerate all helper contracts to confirm or rule out a directly reachable unrestricted `_from` parameter.

    /// @dev this function can only be called by a PoolHelper
    /// @param _lpAddress the lp token to deposit into wombat pool
    /// @param _amount the amount to deposit
    /// @param _for the user to deposit for
    /// @param _from the address to transfer from
    function deposit(
        address _lpAddress,
        uint256 _amount,
        uint256 _minimumLiquidity,
        address _for,
        address _from
    ) nonReentrant whenNotPaused _onlyActivePoolHelper(_lpAddress) external {
        // Get information of the Pool of the token
        Pool storage poolInfo = pools[_lpAddress];
        address depositToken = poolInfo.depositToken;
        IERC20(depositToken).safeTransferFrom(_from, address(this), _amount);

        IERC20(depositToken).safeApprove(poolInfo.depositTarget, _amount);
        uint256 beforeBalance = IERC20(poolInfo.lpAddress).balanceOf(address(this));
        IWombatPool(poolInfo.depositTarget).deposit(
            depositToken,
            _amount,
            _minimumLiquidity,
            address(this),
            block.timestamp,
            false
        );

        uint256 lpReceived = IERC20(poolInfo.lpAddress).balanceOf(address(this)) - beforeBalance;
        _toMasterWomAndSendReward(_lpAddress, lpReceived, true); // triggers harvest from wombat exchange
        // update variables
        IMintableERC20(poolInfo.receiptToken).mint(msg.sender, lpReceived);
        emit NewDeposit(_for, depositToken, _amount, poolInfo.receiptToken, lpReceived);
    }
