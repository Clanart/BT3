### Title
Zero-slippage WOM→mWom buyback swap in `smartConvert` can be sandwiched via Wombat pool price manipulation - ([File: wombat/SmartWomConvert.sol])

### Summary
`SmartWomConvert.smartConvert()` is invoked by `WombatStaking._sendRewards()` on every permissionless `harvest()` call whenever the harvested WOM fee is configured to be converted into mWom [1](#0-0) . It reads a live spot price from the WOM/mWom Wombat pool via `currentRatio()` and then executes an internal buyback swap with **zero minimum output** (`amountOutMin = 0`), making the swap fully exposed to price manipulation/sandwiching within the same transaction context.

### Finding Description
`currentRatio()` computes the mWom→WOM exchange rate by directly querying `IWombatRouter(router).getAmountOut(...)` against the live `womMWomPool` reserves (`cash`/`liability`) — a spot-price read with no time-weighting or manipulation resistance [2](#0-1) .

This ratio decides `convertRatio`, i.e., how much of the incoming WOM fee should be swapped for mWom on the open pool versus minted 1:1 via `IMWom.deposit` [3](#0-2) .

The actual swap in `_convertFor` calls `IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` — the `amountOutMin` parameter is hardcoded to `0`, i.e., no slippage protection whatsoever on this leg of the trade [4](#0-3) . The only downstream check is `convertAmount + amountRec < _minRec` [5](#0-4) , but in the `smartConvert` path `_minRec` is set to `_amountIn` itself [6](#0-5) , which is a very loose bound (mWom is expected to be worth roughly WOM 1:1 already) and does not prevent the buyback leg from executing at an artificially bad rate as long as the total output stays marginally above `_amountIn`.

This whole flow is reachable by any unprivileged wallet: `WombatStaking.harvest(_lpToken)` is an external function gated only by `whenNotPaused` and `_onlyActivePool(_lpToken)` (i.e. the pool must be active, not caller-privileged) [7](#0-6) , and it internally triggers `_toMasterWomAndSendReward` → `_sendRewards` → `smartConvert` [8](#0-7) [1](#0-0) .

An attacker can, in the same transaction (or via back-to-back transactions/flash swap against the WOM/mWom pool), skew the pool's cash/liability ratio, then call `harvest()` to force the fee buyback swap to execute at the manipulated price with zero slippage protection, then restore the pool to its prior state, capturing the value difference at the expense of the protocol fee amount that was meant to be converted into mWom for stakers/treasury.

### Impact Explanation
The WOM fee amount routed through `smartConvert`'s buyback leg is protocol revenue meant to be converted into mWom (ultimately benefiting stakers/treasury holdings of mWom). Because the buyback swap has no real slippage protection, an attacker sandwiching the swap can extract value from this conversion, permanently reducing the mWom obtained by the protocol on each harvest that triggers a buyback. This is a repeatable theft of protocol/user yield each time `harvest()` is called while `mWomToWom < buybackThreshold`.

### Likelihood Explanation
Likelihood is moderate-to-high: `harvest()` is permissionless and can be called by anyone, and the vulnerable path only activates when `currentRatio() < buybackThreshold` (default 9000, i.e. mWom trading below 90% of WOM), which is a plausible pool state, especially since an attacker can force this condition using the same manipulation. The Wombat WOM/mWom pool is a purpose-built, likely lower-liquidity pool compared to major AMM pairs, making price manipulation within a single block cheaper.

### Recommendation
Never hardcode `amountOutMin = 0` on the `swapExactTokensForTokens` call in `_convertFor`; instead pass a real minimum output computed from an independent/manipulation-resistant reference (e.g., a TWAP-style average or a conservative bound derived off-chain and validated on-chain), and enforce a tight per-leg slippage bound rather than only bounding the aggregate `convertAmount + amountRec` against `_minRec`. Additionally, consider adding a maximum acceptable deviation check between `currentRatio()` and a longer-window reference price before deciding `convertRatio`, so a single-block price excursion cannot skew the buyback/mint split.

### Proof of Concept
1. Attacker observes `SmartWomConvert.buybackThreshold` (default 9000) and the current `womMWomPool` cash/liability state.
2. Attacker performs a large swap against `womMWomPool` (via `IWombatRouter`) to push `currentRatio()` below `buybackThreshold`, and/or to otherwise skew cash/liability so that the subsequent buyback swap executes at a favorable rate for the attacker.
3. In the same transaction (or immediately after, same block), attacker calls `WombatStaking.harvest(_lpToken)` for an active pool with WOM rewards and `isMWOM` fee configured, triggering `_sendRewards` → `SmartWomConvert.smartConvert(feeAmount, 0)` [1](#0-0) .
4. `smartConvert` computes `convertRatio` from the manipulated `currentRatio()` [9](#0-8)  and executes `swapExactTokensForTokens(..., 0, ...)` with zero slippage protection [10](#0-9) , receiving a manipulated/unfavorable `amountRec` of mWom.
5. Attacker reverses their initial swap against `womMWomPool`, restoring the pool and pocketing the difference extracted from the protocol's buyback swap, at the cost of the WOM fee amount that should have converted into more mWom for the protocol.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
