### Title
`ThresholdKeys::read` accepts identity verification shares, yielding an identity group key for which anyone can forge Schnorr signatures - (File: crypto/dkg/src/lib.rs)

### Summary
The Iron Bank issue is missing sanity checks on externally returned data (Chainlink accepting a structurally-valid but semantically-invalid price). The Serai analog is in `ThresholdKeys::read`: it deserializes `n` verification shares via `<C as Ciphersuite>::read_G`, which only enforces canonical point encoding — it does not reject the identity point. If every verification share is the identity, `ThresholdKeys::new` computes `group_key` as the identity point (the sum of interpolated identity shares). A Schnorr signature against an identity public key is trivially forgeable: `verify` checks `R + c·A − s·G == 0`, and with `A = identity` any `(R = s·G, s)` pair passes. FROST's `Curve::read_G` does reject identity, but `ThresholdKeys::read` calls the ciphersuite-level `read_G` directly and bypasses that check.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `n` verification shares with `<C as Ciphersuite>::read_G(reader)?` (lines 620-623), then passes them to `ThresholdKeys::new`. `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101) rejects only non-canonical encodings — the identity point is a canonical encoding and is accepted. Contrast with `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131), which explicitly rejects identity; that wrapper is not used here.

`ThresholdKeys::new` (lines 376-378) computes `group_key` as `Σ verification_shares[i] · interpolation_factor(i, {1..=t})` over participants `1..=t`. With all shares set to identity, `group_key = identity` and no check anywhere validates that the group key, or any verification share, is non-identity.

`SchnorrSignature::verify` (crypto/schnorr/src/lib.rs:88-109) checks `multiexp_vartime([(1, R), (c, A), (-s, G)]).is_identity()`. For `A = identity`, the `c·A` term vanishes, so any `(R, s)` with `R = s·G` verifies — a complete forgery requiring no secret knowledge.

Additionally, `read` never validates that `secret_share · G == verification_shares[i]`, but the identity-shares path is the sharper issue since it yields a key whose signatures anyone can forge.

### Impact Explanation
Any consumer that loads `ThresholdKeys` from attacker-influenced bytes (the `read` path is an explicit untrusted-byte entry point) can end up with a `group_key` of identity. For that key, an unprivileged party produces valid Schnorr signatures `(R = s·G, s)` for arbitrary challenges — a forged signature under the threshold group's reported key. Downstream systems treating `group_key()` as the multisig identity would accept attacker-forged signatures as if produced by the threshold set. The same deserialization also permits selectively zeroed verification shares (identity share for specific participants), corrupting `group_key` and per-participant share validation without any deserialization-time detection.

### Likelihood Explanation
Reachability depends on untrusted bytes reaching `ThresholdKeys::read` — which is within the defined attack surface (deserialization of persisted or transmitted key material). Crafting the payload is trivial: the encoder only needs valid headers (`C::ID`, `t`, `n`, `i`), a Lagrange interpolation tag, any canonical scalar, and `n` canonical identity point encodings. No cryptographic hardness stands in the way — the exploit is purely a missing-validation issue, matching the Medium severity of the reference report.

### Recommendation
- In `ThresholdKeys::read` (or `ThresholdKeys::new`), reject identity verification shares and a resulting identity `group_key`.
- Verify `C::generator() * secret_share == verification_shares[&params.i()]` on deserialization so the secret share is bound to the share map.
- Consider using the identity-rejecting point-read semantics (as `Curve::read_G` does) wherever group elements represent keys/shares rather than arbitrary points.
