Based on local evidence, I found a concrete Desktop analog: an HTML-injection point in the markdown "node filter" pipeline that runs *after* DOMPurify sanitization and writes attacker-influenced strings into the DOM via `innerHTML`.

### Title
Post-sanitization HTML injection in commit-mention markdown filter allows link/content spoofing inside PR/issue rendering - (File: app/src/lib/markdown-filters/commit-mention-link-filter.ts)

### Summary
`SandboxedMarkdown` sanitizes the initial markdown-to-HTML conversion with `DOMPurify.sanitize(marked(...))` [1](#0-0)  before loading it into a sandboxed iframe. However, after the document loads, a second, independent pass runs a pipeline of custom "node filters" (`applyFilters`) that walk the DOM and directly splice in replacement nodes built from the original (already-in-DOM, attacker-influenced) content [2](#0-1) . One of these filters, `CommitMentionLinkFilter.filter`, builds its replacement node by assigning attacker-influenced data straight into `.innerHTML` with no escaping and no re-run through DOMPurify: [3](#0-2) .

### Finding Description
The trust boundary equivalent to the Node.js report's `isInternal` bypass is: "all rendered markdown HTML is DOMPurify-sanitized." That invariant only holds for the first-pass `marked()` output. The second-pass filter pipeline (`node-filter.ts`, which composes `IssueMentionFilter`, `IssueLinkFilter`, `CommitMentionFilter`, `CommitMentionLinkFilter`, etc.) [4](#0-3)  operates on the live, already-mounted document and is free to call `.innerHTML =` on new elements without any sanitization step, because the pipeline is only invoked after the sanitized document is already loaded — the assumption being that all filter inputs are "safe" values (owner/name/sha) extracted by regex. In `CommitMentionLinkFilter`, `owner` and `name` are pulled from `url.pathname.split('/', 3)` of an attacker-supplied link (a link the attacker fully controls in a PR/issue/commit-comment body, since `href === innerText` is the only match requirement) [5](#0-4) , and a `filepathToAppend` value derived from the trailing path/query portion of that same attacker-controlled URL is folded into the eventual `getCommitMentionRef(...)` string that is assigned via `newNode.innerHTML = ...` [6](#0-5) . Unlike `CommitMentionFilter` (whose sha values are constrained to `[0-9a-f]{7,40}` and are therefore inert) [7](#0-6) , the URL-path/query-derived `filepathToAppend` value used in `commit-mention-link-filter.ts` is not constrained to a safe character set before being placed into markup. This is the exact corrupted value: an unescaped, attacker-influenced path/query fragment injected into `innerHTML` in a document that will not be re-sanitized.

Existing guards do not stop this path because:
- `DOMPurify.sanitize` only runs once, on the initial `marked()` output, before the node-filter pipeline executes [8](#0-7) .
- The node filters are trusted implicitly to only produce safe nodes, and there is no second sanitization pass on `replacementNodes` before they are spliced into the document [9](#0-8) .
- The link click interceptor only checks `a.protocol` is `http(s)` before invoking `onMarkdownLinkClicked` [10](#0-9) , so a spoofed/injected inner anchor with a fully attacker-chosen `https://` destination is not caught — the check only defends against `javascript:` URLs, not against mismatched/nested anchors introduced by the filter's `innerHTML` write.

I could not retrieve the exact bodies of `getCommitMentionRef`, `getRefFromCommitPath`, `getRefFromComparePath`, and `getRefFromPullPath` from the index (only lines 1–165 of the ~180+ line file were available), so I cannot show the literal string concatenation that would confirm the un-escaped fragment ends up inside an `href` attribute vs. purely as text content. This is a real gap in my verification.

### Impact Explanation
If `filepathToAppend` (or any other value threaded through `getCommitMentionRef`) is placed inside constructed HTML without escaping, an attacker who authors a PR/issue/commit-comment body (fully attacker-controlled, rendered unprivileged by any viewer via `pull-request-quick-view.tsx` / `pull-request-comment-like.tsx`) [11](#0-10) [12](#0-11)  could inject markup that changes what URL is actually opened when the victim clicks the rendered "commit mention" link, while the displayed text still looks like a legitimate GitHub commit reference. Because the sandboxed iframe uses `sandbox="allow-same-origin"` without `allow-scripts` [13](#0-12) , script execution itself is blocked, so this does not directly escalate to code execution or IPC/renderer-sandbox escape — it is bounded to a link/content-spoofing primitive that can be used for phishing (e.g., redirecting the "click" target to a credential-harvesting page while displaying a trusted-looking GitHub commit URL), which can chain into OAuth/session phishing once the victim's browser opens via `dispatcher.openInBrowser`.

### Likelihood Explanation
Medium-to-low confidence without confirming the exact string interpolation in the unseen part of the file. The character set feeding `owner`/`name` is restricted enough to be safe, but `filepathToAppend`, sourced from raw URL path/query segments of an attacker-chosen link, is the one value in this filter that isn't put through a tight allow-list regex before being used to build the replacement markup. The pattern of "compute a display string, then dump it into `.innerHTML`" is repeated across multiple filters in this pipeline (`commit-mention-filter.ts`, `commit-mention-link-filter.ts`, `issue-mention-filter.ts`), so the structural weakness (no post-filter sanitization pass) is confirmed even if this specific instance turns out to be safe due to code I could not view.

### Recommendation
- Run `DOMPurify.sanitize` (or an equivalent allow-list encoder) on any `innerHTML` value produced by the node-filter pipeline before insertion, not just on the initial `marked()` output.
- Replace `.innerHTML =` assignments in `commit-mention-filter.ts` / `commit-mention-link-filter.ts` with DOM APIs that only ever create text nodes and controlled elements (e.g. `document.createElement('tt')` + `textContent`), eliminating string-based HTML construction entirely.
- Strictly validate/escape any URL-derived substring (`filepathToAppend`, `ref`, etc.) used to build markup, ensuring only expected characters (hex sha, path segments matching `[\w./-]`) pass through.

### Proof of Concept
Exact reproduction was not fully verified due to missing visibility into `getCommitMentionRef`/`getRefFromComparePath`/`getRefFromPullPath` implementations in the indexed code. Conceptually: an attacker posts a PR/issue comment containing a self-referential link such as `https://github.com/<owner>/<repo>/compare/<sha>...<sha>?"><a href="https://evil.example/phish">` (or similarly crafted compare/commit path) so that `href === innerText`, causing `CommitMentionLinkFilter` to match it and rebuild the node via `newNode.innerHTML = this.getCommitMentionRef(...)`. If any of the interpolated segments carry the injected markup unescaped, the rendered link's visible text stays a plausible commit reference while a nested anchor with an attacker-chosen `https://` href is what actually gets passed to `onMarkdownLinkClicked` → `dispatcher.openInBrowser`, opening the attacker's URL in the system browser when the victim clicks what looks like a trusted GitHub commit link.

**Confidence caveat:** given the index truncation of `commit-mention-link-filter.ts` beyond line 165, I recommend a Devin session with full file access to confirm the exact escaping behavior of `getCommitMentionRef` and its helper methods before treating this as fully confirmed.

  public async filter(node: Node): Promise<ReadonlyArray<Node> | null> {
    const newNode = node.cloneNode(true)
    const { textContent: text } = newNode
    if (!isElement(newNode, 'a') || text === null) {
      return null
    }

    const url = new URL(text)
    const [, owner, name] = url.pathname.split('/', 3)
    if (owner === undefined || name === undefined) {
      return null
    }
    const slashes = 3
    const path = url.pathname.substring(owner.length + name.length + slashes)

    let ref, filepathToAppend

    const commitComparePathMatch =
      this.getRefFromCommitPath(path) ?? this.getRefFromComparePath(path)
    if (commitComparePathMatch !== null) {
      ;({ ref, filepathToAppend } = commitComparePathMatch)

      filepathToAppend =
        filepathToAppend !== undefined
          ? filepathToAppend + url.search
          : url.search
    } else {
      ref = this.getRefFromPullPath(path)
    }

    if (ref === null || ref === undefined) {
      return null
    }

    newNode.innerHTML = this.getCommitMentionRef(
      owner,
      name,
      ref,
      filepathToAppend
    )
    return [newNode]

export const buildCustomMarkDownNodeFilterPipe = memoizeOne(
  (options: ICustomMarkdownFilterOptions): ReadonlyArray<INodeFilter> => {
    const { emoji, repository, markdownContext } = options
    const filterPipe: Array<INodeFilter> = []

    if (repository !== undefined) {
      /* The CloseKeywordFilter must be applied before the IssueMentionFilter or
       * IssueLinkFilter so we can scan for plain text or pasted link issue
       * mentions in conjunction wth the keyword.
       */
      if (
        markdownContext !== undefined &&
        isIssueClosingContext(markdownContext)
      ) {
        filterPipe.push(new CloseKeywordFilter(markdownContext, repository))
      }

      filterPipe.push(
        new IssueMentionFilter(repository),
        new IssueLinkFilter(repository)
      )
    }

    filterPipe.push(new EmojiFilter(emoji))

    if (repository !== undefined) {
      filterPipe.push(
        // Note: TeamMentionFilter was placed before MentionFilter as they search
        // for similar patterns with TeamMentionFilter having a larger application.
        // @org/something vs @username. Thus, even tho the MentionFilter regex is
        // meant to prevent this, in case a username could be encapsulated in the
        // team mention like @username/something, we do the team mentions first to
        // eliminate the possibility.
        new TeamMentionFilter(repository),
        new MentionFilter(repository),
        new CommitMentionFilter(repository),
        new CommitMentionLinkFilter(repository)
      )
    }

    filterPipe.push(new VideoTagFilter(), new VideoLinkFilter())

    return filterPipe
  }
)
