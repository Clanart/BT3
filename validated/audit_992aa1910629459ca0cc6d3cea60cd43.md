### Title
Escrow withdrawal accepts a false `transfer()` return value as success, permanently locking funds while marking orders as filled - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed tokens using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the *external call itself* did not revert (`success`), never decoding and validating the boolean return value that `IERC20.transfer`/`transfer` is supposed to return. Any ERC20/TRC20 implementation that returns `false` on failure instead of reverting will cause the gateway to believe the transfer succeeded, finalize the order (`_filled`), decrement escrow accounting, and emit `EscrowReleased`/`EscrowRefunded`/`DustSwept` — while the beneficiary never actually receives the tokens.

### Finding Description
In `withdraw()` [1](#0-0)  the token payout path is:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

Here `success` only reflects whether the low-level call reverted, not whether the token's `transfer` function returned `true`. Per the ERC20 standard, tokens are permitted to signal failure by returning `false` without reverting (this is precisely the bug class described in the referenced report for `token.transfer()`/`transferFrom()`). The same unchecked pattern repeats for the fee payout [2](#0-1)  and for the `SweepDust` handler [3](#0-2) .

Notably, the contract already imports and enables OpenZeppelin's `SafeERC20` (`using SafeERC20 for IERC20;`) [4](#0-3)  and correctly uses `safeTransferFrom` when *collecting* escrow on `placeOrder` [5](#0-4) , but the payout paths (`withdraw`, `SweepDust`) bypass `safeTransfer` in favor of the raw, unchecked `.call`.

Because `withdraw()` unconditionally decrements `_orders[body.commitment][token]` and, on finalize, marks `_filled[body.commitment] = beneficiary` regardless of whether the token payout actually moved value [6](#0-5) , a token that returns `false` on `transfer` failure causes:
- The order to be irreversibly marked filled/refunded.
- The escrow bookkeeping decremented as if funds were paid out.
- No revert, so no retry path — the tokens remain stuck in the contract while the on-chain state says the beneficiary was paid.

This is reachable via the normal cross-chain settlement flow: `onAccept` dispatches `RedeemEscrow`/`RefundEscrow` bodies straight into `withdraw()` after only checking the message came from the expected source module [7](#0-6) ; no additional privileged actor is needed beyond the normal hyperbridge message flow that any user's order settlement triggers.

### Impact Explanation
This causes real loss of user/solver funds: escrowed tokens that fail the low-level `transfer` (return `false` instead of reverting — a documented, non-malicious ERC20 behavior class, e.g. legacy/pausable/blacklist tokens) become permanently locked in the `IntentGatewayV2` contract while the protocol's internal state (`_orders`, `_filled`) records the escrow as already released/refunded/settled. The beneficiary has no recourse since the commitment is finalized and cannot be retried or re-triggered, matching the "false state acceptance" / fund-loss impact class for the bounty.

### Likelihood Explanation
This is a direct function of token behavior, not an attacker requirement — no malicious relayer, prover, or admin is needed. Any listed/allow-listed token (or one added later via governance/params update) that returns `false` rather than reverting on transfer failure (insufficient balance edge cases, blacklists, paused states) will trigger this on ordinary escrow settlement, cancellation, or dust-sweep paths that already run in production.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)` (already imported and used elsewhere in the same file for `safeTransferFrom`), so both call-failure and false-return-value cases revert deterministically instead of silently finalizing.

### Proof of Concept
1. Protocol allow-lists (or a user selects) a token whose `transfer` implementation returns `false` instead of reverting when it cannot move funds (a standards-compliant but non-strict ERC20).
2. User places a cross-chain order with that token as input escrow via `placeOrder`, which uses `safeTransferFrom` correctly and escrows the tokens [8](#0-7) .
3. Order settles/refunds; `onAccept` routes into `withdraw()` [7](#0-6) .
4. The token's `transfer` call returns `false` (no revert) under the triggering condition (e.g., temporary blacklist/pause). `success` from the outer `.call` is `true` because the call itself did not revert, so `withdraw()` proceeds to decrement escrow, mark `_filled`, and emit `EscrowReleased` [9](#0-8) .
5. Beneficiary never receives tokens; funds are stuck in the contract with no retry mechanism since `_filled`/`_orders` already reflect completion.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
