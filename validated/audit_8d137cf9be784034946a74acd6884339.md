### Title
PedPoP `Encryption::decrypt` decrypts attacker-controlled ciphertexts and returns an ECDH key proof before the per-message proof-of-possession is verified - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

The Arcane bug class is "attacker-controlled indirection resolved and returned before the containment check that exists elsewhere runs" (`GetProjectFileContent` returns include content before `IsSafeSubdirectory`). The Serai analog lives in PedPoP's share-encryption layer: `Encryption::decrypt` performs ECDH with the recipient's *static* decryption scalar against an attacker-supplied point, applies the ChaCha20 keystream to the attacker-supplied ciphertext, and returns the plaintext together with an `EncryptionKeyProof` — while the only authentication of the message (the Schnorr proof-of-possession over `key`, `sender`, and `msg`) is merely *queued* into a `BatchVerifier` whose result is produced later and out of this function's control.

### Finding Description

In `crypto/dkg/pedpop/src/encryption.rs`, `Encryption::decrypt` (lines 469–501):

```rust
pub(crate) fn decrypt<...>(
  &self, rng, batch, batch_id, from, mut msg: EncryptedMessage<C, E>,
) -> (Zeroizing<E>, EncryptionKeyProof<C>) {
  msg.pop.batch_verify(rng, batch, batch_id, msg.key,
    pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.as_ref()));
  let key = ecdh::<C>(&self.enc_key, msg.key);                 // s * attacker-chosen P
  cipher::<C>(self.context, &key).apply_keystream(msg.msg.as_mut().as_mut());
  (msg.msg, EncryptionKeyProof { key, dleq: DLEqProof::prove(...) })
}
```

Three properties combine:

1. `EncryptedMessage::read` (lines 171–177) accepts fully untrusted bytes: `key` (any non-identity point via `C::read_G`), `pop`, and the raw ciphertext `msg` — no validation at parse time.
2. `decrypt` unconditionally computes `ecdh(enc_key, msg.key)` — a static-Diffie-Hellman evaluation under the victim's long-lived `enc_key` on an *attacker-chosen* point — and decrypts the ciphertext, returning the plaintext.
3. It also returns `EncryptionKeyProof { key }`, disclosing the ECDH result `s·P` for the attacker-chosen `P` (with a DLEq proof binding it to `msg.key` and the victim's `enc_pub_key`). The PoP that would prove the sender knew `P`'s discrete log is verified only later inside the shared `BatchVerifier`; nothing in `decrypt` gates its outputs on that result.

The contrast with the sibling function mirrors the Arcane create-vs-update asymmetry: `Decryption::decrypt_with_proof` (lines 366–397) verifies `msg.pop` **synchronously** (`Err(DecryptionError::InvalidSignature)?` at line 378) before any keystream is applied — so the blame path validates before disclosing, while the hot path discloses before validating.

### Impact Explanation

This is a static-ECDH decryption oracle reachable by any unauthenticated DKG participant (`Participant` index is attacker-claimed bytes in the message stream). Concretely:

- **Decryption oracle / key-share recovery**: an attacker submits `(P, C)` pairs where `C` is ciphertext intercepted from honest share messages addressed to the victim. `decrypt` returns `C` XOR `ChaCha20(H(context ‖ s·P))` plus `s·P` itself — the attacker learns the plaintext of any message encrypted to the victim regardless of PoP validity. In PedPoP these plaintexts are Feldman/Pedersen secret shares; recovering `t` participants' shares yields the threshold private key.
- **Pre-verification secret disclosure**: `EncryptionKeyProof.key` is `s·P` for attacker-chosen `P`. Beyond oracle decryption, this is precisely the "revealing ECDH keys" hazard the module comments (lines 84–90) warn breaks protocols — except here it is emitted before the message authenticates, not only during blame.
- The PoP's `batch_verify` failure only helps if the caller aborts *all* use of the returned plaintext/proof on batch failure; the values have already been computed and returned, and `InvalidShare`-style blame for a bad PoP uses `decrypt_with_proof`, whose own decryption of the accused message further reveals content.

### Likelihood Explanation

Reachability is high: `EncryptedMessage::read` consumes untrusted peer bytes and `decrypt` is invoked on every received share message in the DKG. Exploitation requires no collusion beyond the attacker's own participation — a single malicious participant submitting messages with a forged/random `pop` and chosen `key` point gets oracle service before the batch rejects the PoP. Severity is High (not Critical) because the primitive is a decryption/DH oracle rather than direct scalar extraction; converting it into the threshold key requires collecting `t` victims' shares across the round.

### Recommendation

Verify the PoP synchronously inside `decrypt` (or return a handle that withholds the plaintext/proof until the batch resolves) before computing `ecdh` and `apply_keystream`, matching `decrypt_with_proof`'s ordering: check `msg.pop.verify(msg.key, pop_challenge(...))` first, `Err` on failure, and only then decrypt and construct `EncryptionKeyProof`. If batching must be kept for performance, delay disclosure: decrypt into a sealed buffer and release `msg.msg`/`EncryptionKeyProof` only after the batch verifier confirms the PoP.
