### Title
SignableTransaction weight bound check omits the OP_RETURN data output, permitting over-weight transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes the OP_RETURN `data` output onto `tx_outs` before computing the transaction weight, but `calculate_weight_vbytes` is invoked with `payments` — which excludes the data output. The `MAX_STANDARD_TX_WEIGHT` boundary check therefore runs against a weight that was never adjusted for the added output, exactly the "check boundary, then forget to re-check after modification" class of the vivid advisory.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202`, the OP_RETURN output (up to 80 bytes of attacker-influenced data plus output overhead, ~360+ weight units) is appended to `tx_outs`. The weight used for both the minimum-fee check (line 211) and the standard-weight check (line 241) comes from `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, whose reconstructed `Transaction` contains only `payments` (lines 85-93) — the data output is never represented. When change is added, `weight` is correctly updated to `weight_with_change` (line 231), but there is no equivalent path for the data output. A caller can thus construct a `SignableTransaction` whose real weight exceeds `MAX_STANDARD_TX_WEIGHT` while passing every check.

### Impact Explanation
The resulting transaction is non-standard and will be rejected by Bitcoin relay policy, yet it is fully formed and will be signed by the FROST multisig path (`multisig()`, `sign()`/`complete`). The inputs consumed are locked into an unbroadcastable transaction, requiring manual reconstruction to recover — funds committed to a transaction that cannot be mined. Additionally, `needed_fee` and the `TooLowFee` minimum-fee check are computed from under-counted vbytes, so the produced TX can also underpay relative to its true size.

### Likelihood Explanation
Reachable by any party able to supply `data` (e.g., an instruction payload) and payments sized near the weight limit to the transaction-construction path; no collusion or key material is required. The omission is deterministic — any `data.is_some()` construction bypasses ~360 weight units of accounting.

### Recommendation
Include the data output in the transaction used for weight/vbytes accounting — e.g., build `calculate_weight_vbytes` from `tx_outs` (or pass the data length) rather than `payments`, and recompute/re-check `weight` after pushing the OP_RETURN output, mirroring the `weight_with_change` handling.

### Proof of Concept
Conceptually: call `SignableTransaction::new(inputs, payments, None, Some(vec![0; 80]), fee)` where `payments` are chosen so the no-change/no-data weight is just below `MAX_STANDARD_TX_WEIGHT`. The check at line 241 passes against the payments-only weight, but the returned `tx` — which includes the ~89-vbyte OP_RETURN output — exceeds the standard weight limit and fails `testmempoolaccept`/relay on a live node.
