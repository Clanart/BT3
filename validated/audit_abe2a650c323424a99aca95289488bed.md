### Title
Distribution precompile `rewards()` accepts `msg.value` with no refund path, permanently stranding sent funds - (File: precompiles/distribution/distribution.go)

### Summary
The `distribution` precompile at address `0x0000000000000000000000000000000000001007` dispatches its `rewards` method without validating that `msg.value` is zero and without ever forwarding or refunding any value sent along with the call. Any EVM caller that sends native funds (usei/wei) together with a call to `rewards(address)` will have those funds irrecoverably locked in the precompile's associated Sei account, since `rewards` is a pure query that never touches the payment and no other precompile method exists to sweep or withdraw a stray balance from that account.

### Finding Description
In `Execute`, every other state-mutating or payable-sensitive method either performs `pcommon.ValidateNonPayable(value)` to reject value, or explicitly consumes the value via `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` (as seen in the `withdrawValidatorCommission` case and in the analogous `staking.delegate` pattern). The `RewardsMethod` case is the one dispatch branch that does neither: [1](#0-0) 

```
case RewardsMethod:
    return p.rewards(ctx, method, args)
```

`value` is not even passed into `p.rewards`, and the query body itself only reads delegation-reward data and packs a response — it never inspects or moves `value`: [2](#0-1) 

Because Sei's EVM `CALL` semantics transfer `msg.value` into the callee's balance at the EVM/state layer *before* the precompile's Go executor even runs (the same mechanism that funds `HandlePaymentUsei`-consuming methods), any non-zero `value` sent to `rewards` is credited to the precompile's associated Sei address (`DistrAddress = 0x0000...1007`, mapped to a Cosmos account) regardless of what the Go handler does afterward. Since `rewards` performs no debit/refund and no other distribution-precompile method exists to withdraw an arbitrary balance sitting on that association account, the funds become permanently stuck.

This is confirmed directly by the project's own integration-test documentation, which flags this as a known guard gap rather than something hypothetical: [3](#0-2) 

```
 * Guard quirk worth knowing: rewards() is the one phase-2 view WITHOUT a
 * non-payable check (a value-bearing call would succeed and strand the funds),
 * so this spec deliberately has no "view rejects value" test.
```

and in the suite README: [4](#0-3) 

This is the structural analog of the reported `StakeManager.sol` issue: a payable-reachable entry point accepts native currency in exchange for nothing, with no corresponding withdraw/refund mechanism, so the deposited value is locked forever — except here the "deposit" happens implicitly via EVM `CALL` value-forwarding into a precompile-associated account rather than via an explicit `payable` Solidity function.

### Impact Explanation
Any unprivileged EVM transaction sender can call `rewards(address)` on the distribution precompile with a non-zero `value` and have that value silently accepted and stranded — a real, permanent loss of the sender's native funds with no code path to recover them (no other distribution-precompile method allows withdrawing an arbitrary balance held by the precompile's associated address, and it is not a normal delegator/validator/withdraw-address flow). This meets the "permanent freezing/fund loss" bar for a valid analog, though the value at risk per call is capped by whatever `msg.value` an unaware or buggy caller happens to attach.

### Likelihood Explanation
Likelihood is moderate: a careful caller who reads the ABI (`view`/non-payable) would not normally attach value, so this is unlikely to be triggered by routine usage. However, it is trivially triggerable by any transaction sender who crafts a raw call to the precompile address with the `rewards` selector and non-zero `value` (bypassing ABI-level mstate mutability hints), or by a contract/dApp that unintentionally forwards `msg.value` when batching a `rewards` view call with a payable transaction.

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` guard used by the other `distribution` precompile view methods (e.g., `withdrawValidatorCommission`) to the `RewardsMethod` dispatch branch in `Execute`, rejecting any call to `rewards` that carries non-zero value, consistent with all other view/query methods in this precompile.

### Proof of Concept
1. Associate an EVM account with a Sei address (`associateViaTx`).
2. Send a raw EVM transaction (or `eth_call`/tx via low-level `call`) to `0x0000000000000000000000000000000000001007` encoding the `rewards(address)` selector with the delegator's address, setting `value` to a non-zero amount (e.g., `1000000000000` wei = 1 usei).
3. Observe the transaction succeeds (status 1) and returns the rewards data as expected.
4. Query the bank balance of the distribution precompile's associated Sei account (`p.evmKeeper.GetSeiAddressOrDefault(ctx, DistrAddress)`) before and after — the balance increases by the sent value.
5. Confirm no distribution-precompile method exists that can withdraw this balance back to any user; the funds remain stuck under the precompile's account indefinitely.

```go
func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
```
