### Title
Incorrect Assumption That `block_height - 1` Always Has a Light Client Proof in `get_citrea_l2_height_range` Causes Verifier to Permanently Fail Processing Finalized Blocks — (`File: core/src/citrea.rs`)

---

### Summary

`CitreaClient::get_citrea_l2_height_range` unconditionally fetches the Citrea Light Client Proof (LCP) for `block_height - 1` to derive the L2 height range start. Citrea explicitly does not produce LCPs for every L1 block height — the code itself acknowledges this with the comment *"before a certain number of blocks, citrea doesn't produce proofs"*. When `block_height - 1` has no LCP (e.g., at bridge startup when the first provable L1 block is processed), the function returns a hard error. This propagates to `Verifier::handle_finalized_block`, which fails to collect deposits and withdrawals for that block, breaking the verifier's ability to track bridge state and challenge fraudulent operators.

---

### Finding Description

In `core/src/citrea.rs`, `get_citrea_l2_height_range` computes the L2 height range for a given L1 block by fetching two LCPs: one for `block_height` (with retry/timeout) and one for `block_height - 1` (no retry, immediate hard failure):

```rust
// core/src/citrea.rs lines 579-585
let proof_previous = self
    .get_light_client_proof(block_height - 1, paramset)
    .await?
    .ok_or(eyre::eyre!(
        "Light client proof not found for block height: {}",
        block_height - 1
    ))?;
``` [1](#0-0) 

The function assumes `block_height - 1` always has a valid LCP. However, Citrea's light client prover does not produce proofs for every L1 block height. The comment in `handle_finalized_block` explicitly acknowledges this:

```rust
// core/src/verifier.rs line 3063
// before a certain number of blocks, citrea doesn't produce proofs (defined in citrea config)
``` [2](#0-1) 

This means there exists a concrete first L1 block height `H` for which Citrea produces an LCP, but `H - 1` has no LCP. When the verifier processes block `H`, `get_citrea_l2_height_range(H, ...)` will:
1. Successfully wait for and retrieve the LCP for `H`
2. Immediately fail with `"Light client proof not found for block height: H-1"`

This error propagates directly out of `handle_finalized_block`:

```rust
// core/src/verifier.rs lines 3067-3075
let (l2_height_start, l2_height_end) = self
    .citrea_client
    .get_citrea_l2_height_range(
        block_height.into(),
        timeout,
        self.config.protocol_paramset(),
    )
    .await
    .inspect_err(|e| tracing::error!("Error getting citrea l2 height range: {:?}", e))?;
``` [3](#0-2) 

When `handle_finalized_block` fails, `update_citrea_deposit_and_withdrawals` is never called, so deposits (move txids) and withdrawals (UTXOs) from that block are never collected into the verifier's database:

```rust
// core/src/verifier.rs lines 3082-3088
self.update_citrea_deposit_and_withdrawals(
    dbtx,
    l2_height_start,
    l2_height_end,
    block_height,
)
.await?;
``` [4](#0-3) 

The analog to the Chainlink bug is exact: just as `_getPrevChainlinkResponse` blindly uses `roundId - 1` assuming it always contains valid data, `get_citrea_l2_height_range` blindly uses `block_height - 1` assuming it always has a valid LCP — and both assumptions are false by design of the external system.

---

### Impact Explanation

When `handle_finalized_block` fails for block `H`:

1. **Deposits not registered**: Move txids from Citrea for deposits finalized in that L2 range are never stored in the verifier's DB via `upsert_move_to_vault_txid_from_citrea_deposit`. The verifier permanently loses awareness of those deposits.

2. **Withdrawals not registered**: Withdrawal UTXOs from Citrea for that range are never stored via `update_withdrawal_utxo_from_citrea_withdrawal`. The verifier cannot validate payouts against those withdrawals.

3. **Verifier stuck or skipping**: Depending on state machine retry behavior, the verifier either loops indefinitely on block `H` (complete liveness failure) or skips it (permanent state gap). Either outcome breaks the verifier's ability to challenge fraudulent operator payouts for deposits/withdrawals in that block.

4. **Operator fraud goes unchallenged**: If the verifier does not know about a withdrawal UTXO, it cannot validate whether an operator's payout is legitimate. A fraudulent payout for a withdrawal the verifier missed would go unchallenged, enabling operator theft of bridged BTC.

---

### Likelihood Explanation

This is triggered deterministically at bridge startup. The bridge `start_height` is configured to the first L1 block the bridge monitors. Citrea's light client prover begins producing proofs only after some initial block count (explicitly noted in the code). The first block `H` for which an LCP exists will have `H - 1` without an LCP. This is not a rare edge case — it is the normal startup sequence of every Clementine deployment.

---

### Recommendation

Instead of unconditionally fetching `block_height - 1`, search backwards for the most recent L1 block height that has a valid LCP, analogous to the Chainlink fix of looping through previous roundIds:

```rust
async fn get_citrea_l2_height_range(...) -> Result<(u64, u64), BridgeError> {
    // ... wait for proof_current at block_height ...

    // Search backwards for the nearest previous block with an LCP
    let mut prev_height = block_height.saturating_sub(1);
    let proof_previous = loop {
        if prev_height == 0 {
            // No previous proof exists; l2_height_start = 0
            break None;
        }
        if let Some(proof) = self.get_light_client_proof(prev_height, paramset).await? {
            break Some(proof);
        }
        prev_height = prev_height.saturating_sub(1);
    };

    let l2_height_end: u64 = proof_current.2;
    let l2_height_start: u64 = proof_previous.map(|p| p.2).unwrap_or(0);
    Ok((l2_height_start, l2_height_end))
}
```

Additionally, the `start_height` paramset value should be validated at startup to ensure `start_height - 1` either has an LCP or is handled as a genesis case.

---

### Proof of Concept

1. Deploy Clementine with `start_height = H` where `H` is the first L1 block for which Citrea produces an LCP (i.e., `H - 1` has no LCP).
2. The Bitcoin syncer finalizes block `H` and calls `Verifier::handle_finalized_block(H)`.
3. `get_citrea_l2_height_range(H, ...)` successfully retrieves the LCP for `H`.
4. It then calls `get_light_client_proof(H - 1, ...)`, which returns `None` because Citrea has no proof for `H - 1`.
5. The `.ok_or(...)` at line 582 converts `None` to `Err("Light client proof not found for block height: H-1")`.
6. `handle_finalized_block` returns this error.
7. `update_citrea_deposit_and_withdrawals` is never called for block `H`.
8. All deposits and withdrawals finalized in the L2 range corresponding to block `H` are permanently absent from the verifier's database.
9. Any operator payout for a withdrawal from that range proceeds without verifier challenge.
