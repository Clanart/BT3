## Title
Malformed/reverting source-chain callback in `IBCOnAcknowledgementPacketCallback` permanently blocks packet acknowledgement and freezes escrowed refund - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
This is the Cosmos-EVM analog of the Connext `PromiseRouter.process()` griefing bug (C4 M-19): an external, attacker/user-controlled callback contract can revert during a critical settlement step, and instead of the failure being isolated, the error propagates up and aborts the entire state transition, permanently blocking finalization of the underlying protocol action.

### Finding Description
`ContractKeeper.IBCOnAcknowledgementPacketCallback` invokes the sender-specified EVM contract's `onPacketAcknowledgement` via `k.evmKeeper.CallEVM(...)`, and if that call errors (contract reverts, runs out of the caller-chosen `gas_limit`, is deleted/self-destructed, etc.), it wraps and **returns the error**: [1](#0-0) 

This error propagates through `transferStack.OnAcknowledgementPacket`, causing the entire `MsgAcknowledgement` handler to fail. In Cosmos SDK, a failing message handler discards **all** state writes made during that message, including the transfer app's already-computed refund for an error-acknowledgement (i.e. tokens that should be released from escrow back to the sender when the destination chain reports a failed transfer). This is confirmed by the module's own test matrix: a callback pointed at an empty/no-code address makes the whole acknowledgement processing fail with a propagated error: [2](#0-1) 

Critically, the equivalent `IBCOnTimeoutPacketCallback` path (same file) has the identical fragile pattern — returning the wrapped error on any EVM callback failure: [3](#0-2) 

yet the test suite explicitly documents that the *timeout* refund must always occur **regardless of callback failure** ("Even if callback fails, the timeout refund should still happen"): [4](#0-3) 

This shows the intended invariant of the module (established by its own tests) is that a failing/reverting source-side callback must **never** block base IBC settlement (refunds/escrow release), matching IBC-go's ADR-008 design principle that callback failures on the packet-sending chain must not affect the underlying packet lifecycle. The acknowledgement path violates this invariant: unlike the timeout path, a reverting `onPacketAcknowledgement` implementation directly aborts the acknowledgement transaction, discarding the refund that the transfer application already computed for error acks.

The callback target contract address, and the gas limit given to it, are both attacker/sender-controlled via the packet `memo` (`src_callback.address`, `src_callback.gas_limit`), and only the IBC packet sender needs to set it: [5](#0-4) 

A relayer (unprivileged, permissionless) delivering the acknowledgement proof cannot avoid triggering this call — `CallEVM` is invoked unconditionally whenever `src_callback` is present and calldata validation passes.

### Impact Explanation
Because `MsgAcknowledgement` for this packet can never succeed while the callback contract keeps reverting/running out of gas (e.g. a contract that later self-destructs, is bricked, deliberately reverts, or was given too small a `gas_limit`), the packet commitment on the source channel is never cleared and the corresponding refund for an error-acknowledged transfer is **never released from escrow**. There is no other code path to reclaim these tokens once the destination has already rejected the transfer (error ack) — the packet cannot be independently timed out since it was already acknowledged by the counterparty. This results in permanent, irreversible freezing of escrowed user funds through ordinary, unprivileged transaction flow (submitting a `MsgTransfer` with a `src_callback` memo, then any relayer delivering the resulting error acknowledgement), matching the "Critical permanent freezing/locking of escrowed assets" impact category.

### Likelihood Explanation
Triggering requires only: (1) a sender using the (documented, encouraged) source-callback feature of ICS-20 transfers with a contract whose acknowledgement handler can fail (easy to occur unintentionally via insufficient `gas_limit`, a contract bug, or a subsequently self-destructed/upgraded contract; or deliberately by a malicious actor griefing their own or a shared contract), and (2) the destination chain returning an error acknowledgement (a completely ordinary occurrence, e.g., receiver-side transfer failures). No privileged access or validator collusion is needed, and the trigger is a normal relayer action.

### Recommendation
Mirror the isolation already partially present conceptually for the timeout path (or make it actually effective): execute the EVM callback in `IBCOnAcknowledgementPacketCallback` (and `IBCOnTimeoutPacketCallback`) on the already-used cached context, and if the callback call fails (revert, out-of-gas, no-code, etc.), **do not propagate the error to the caller of `OnAcknowledgementPacket`/`OnTimeoutPacket`**. Instead, log/emit a failure event, discard only the callback's own cached-context writes (skip `writeFn()`), and return `nil` so the underlying transfer app's refund/escrow-release logic is committed unconditionally, decoupling settlement finality from arbitrary user-controlled contract execution — consistent with the "callback must not block packet lifecycle" invariant already asserted by this repo's own test suite for timeouts.

### Proof of Concept
1. Sender submits `MsgTransfer` on chain A with `memo` containing `src_callback` pointing to a contract that always reverts in `onPacketAcknowledgement` (or is given an insufficient `gas_limit`), per the format in `x/ibc/callbacks/README.md`.
2. Destination chain B rejects the transfer, producing an error acknowledgement.
3. A relayer submits `MsgAcknowledgement` on chain A with this error ack.
4. `IBCOnAcknowledgementPacketCallback` calls the sender's contract via `CallEVM`; the call reverts/fails, and the function returns `errorsmod.Wrapf(types.ErrCallbackFailed, ...)` as shown in `x/ibc/callbacks/keeper/keeper.go` lines 324-330.
5. The error propagates up through `OnAcknowledgementPacket`; the entire `MsgAcknowledgement` message fails and all its state changes (including the transfer app's computed refund) are rolled back, exactly as reproduced in the "failure - callback to empty address" test case (`evmd/tests/ibc/ibc_middleware_test.go` lines 932-947), which asserts `expError: "ABCI code: 4"` for the whole acknowledgement call.
6. Since the packet is already acknowledged by the counterparty (error ack), there is no alternative timeout path to reclaim the escrowed tokens — every future relay attempt of the same acknowledgement will fail identically, permanently freezing the sender's tokens in the escrow account.

#### Callback information in memo

For the callback to be processed, the transfer packet's `memo` should contain the following in its JSON:

```json
"memo": {
    "src_callback": {
        "address": "evm_contract_addr",
        "gas_limit": "1000000",
    }
}
```

NOTE: For the source callbacks, the calldata **must** be empty since we do not support custom calldata and
instead expect to call a specific entrypoint with the packet information and acknowledgement.
