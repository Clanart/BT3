### Title
Blind SSRF via unvalidated on-chain DataLayer mirror URLs causing outbound GET requests from any subscribing node - ([File: chia/data_layer/download_data.py])

### Summary
Any wallet user can create a DataLayer "mirror" coin advertising an arbitrary URL for a store, and every full node running a DataLayer service that later subscribes to or tracks that store will automatically issue outbound `aiohttp` GET requests to that attacker-chosen URL, with no validation of scheme, host, or destination network range. This is directly analogous to CVE-2021-32698 (eLabFTW), where user-controlled input caused the server to make blind GET requests to attacker-chosen locations.

### Finding Description
A mirror is created on-chain by spending funds through `DataLayerWallet.create_mirror()`/the `add_mirror` RPC, which places attacker-controlled `urls` directly into the coin's memo field and calls `dl_new_mirror` with no URL validation: [1](#0-0) .

Any node syncing coins recognizes the `create_mirror_puzzle()` puzzle hash, extracts `launcher_id, urls` from `get_mirror_info()`, and — if that launcher/store id is already tracked by the local wallet (`is_launcher_tracked`) — persists the mirror and its URLs into `dl_store` without any host/scheme filtering: [2](#0-1) .

The DataLayer service periodically pulls these wallet-tracked mirror URLs via `update_subscriptions_from_wallet()` and merges them into the local subscription server list: [3](#0-2) .

`fetch_and_validate()` then randomly picks one of these attacker-supplied URLs and passes it into `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs a plain `aiohttp.ClientSession().get(server_info.url + "/" + filename, ...)` request without any check that the URL points to a legitimate DataLayer mirror server (no scheme allow-list, no private/link-local IP block, no DNS-rebinding protection): [4](#0-3) [5](#0-4) .

Grepping the DataLayer module confirms no URL/scheme/host validation exists anywhere in the sync path (`data_layer.py`, `data_store.py`, `download_data.py`, `data_layer_wallet.py`) — the only scheme check in the whole module lives in the unrelated `s3_plugin_service.py`, which merely checks for `scheme == "s3"` before doing its own plugin-specific download and is not reachable from ordinary HTTP mirror URLs.

### Impact Explanation
Because the request-triggering user only needs to be tracked as owning/subscribing to a store (which any node operator can arrange simply by running `dl_track_new`/`subscribe`, or automatically if `auto_subscribe_to_local_stores` is enabled), an attacker can force arbitrary Chia full nodes running DataLayer to issue GET requests to attacker-chosen hosts, including internal-network addresses, localhost services, or cloud metadata endpoints (e.g. `169.254.169.254`). This qualifies as a blind SSRF: the requesting node does not return response contents to the attacker, but the attacker fully controls the destination and can use it to port-scan or trigger side effects against internal infrastructure reachable from the victim's DataLayer service host, exactly mirroring the CVE-2021-32698 bug class ("attacker cannot see the result of the request").

### Likelihood Explanation
Likelihood is high for any node operator who subscribes to third-party DataLayer stores (a normal, documented DataLayer workflow) since the mirror-adding party can be any wallet holder able to fund a mirror coin — no special privilege is required to create the malicious mirror. The victim node automatically performs periodic syncing (`periodically_manage_data()`) without operator interaction once subscribed.

### Recommendation
Validate mirror/server URLs before storing and before making outbound requests: restrict to `http`/`https` schemes, resolve and reject requests to private, loopback, and link-local IP ranges (including via DNS resolution, to prevent DNS-rebinding), and consider making outbound mirror fetches opt-in per-store or via an explicit allow-list, consistent with the mitigation approach used by the upstream eLabFTW fix referenced in CVE-2021-32698.

### Proof of Concept
1. Attacker wallet creates a DataLayer store/launcher and calls `add_mirror` (or `dl_new_mirror`) with `urls=["http://169.254.169.254/latest/meta-data/"]` and pushes the mirror-coin spend on chain (see `chia/data_layer/data_layer_rpc_api.py` `add_mirror` handler and `data_layer.py:965-970`).
2. A victim operator's DataLayer service tracks/subscribes to the attacker's store id (e.g., via `subscribe` RPC or via `auto_subscribe_to_local_stores`).
3. On the victim's next `coin_added()` sync of the mirror coin, the malicious URL is written into `dl_store` (`data_layer_wallet.py:775-800`), then pulled into local subscriptions by `update_subscriptions_from_wallet()`.
4. On the next `periodically_manage_data()` cycle, `fetch_and_validate()`/`insert_from_delta_file()`/`download_file()`/`http_download()` issues an outbound GET to the attacker's URL from the victim node's process, with no host/scheme restriction (`data_layer.py:642-694`, `download_data.py:298-320`).
