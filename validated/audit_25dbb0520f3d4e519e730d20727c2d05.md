### Title
Stale `userRewardPerTokenPaid` checkpoint lets a staker retroactively claim rewards on a balance increase, since `balanceOf()` is externally fetched and no atomic checkpoint is enforced on stake changes - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder` has no `stake()`/`withdraw()` function of its own; `balanceOf(_account)` is fetched live from `IMasterMagpie(masterMagpie).stakingInfo(stakingToken, _account)` [1](#0-0)  rather than tracked internally on stake/withdraw. Because the reward index (`userRewardPerTokenPaid`) is only checkpointed when someone explicitly calls the permissionless `updateFor`/`getReward` entrypoints [2](#0-1) , an account whose underlying staked balance increases between two checkpoints will have the *entire* pending `rewardPerToken` delta multiplied by its **new, larger** balance in `_earned`, instead of the balance that was actually staked while the reward accrued.

### Finding Description
`_earned` computes rewards as:
```
(_userMWOMSVShare * (rewardPerToken(_rewardToken) - userRewardPerTokenPaid[_rewardToken][_account])) / 1e18 + userRewards[_rewardToken][_account]
``` [3](#0-2) 

This is only correct if `userRewardPerTokenPaid[_account]` is checkpointed (via `_updateFor`) at the exact moment the account's balance changes, using the *pre-change* balance. In this contract, `_updateFor` is only invoked by:
- `updateFor(address _account)` — external, permissionless, callable by anyone at any time [2](#0-1) 
- the `updateReward`/`updateRewards` modifiers on `getReward`/`getRewards` [4](#0-3) 

None of these are wired atomically into the balance-changing action itself, because that action (locking/staking mWOMSV) lives entirely outside this contract, in `MasterMagpie`/the locker whose `stakingInfo` this contract reads. If a checkpoint is not forced synchronously with every balance change on this specific rewarder, the sequence described is exploitable:
1. Attacker holds a small balance; `userRewardPerTokenPaid[attacker]` is checkpointed at that small-balance time.
2. `queueNewRewards` (manager) increases `rewardPerTokenStored` for the pool [5](#0-4) , based on the total supply at the time — attacker's fair share of the accrual is proportional to their small balance.
3. Attacker increases their staked balance dramatically (through the locker/`MasterMagpie` staking flow) without an intervening checkpoint on this rewarder.
4. Attacker calls `updateFor(self)`/`getReward` — `_updateFor` reads the **new large** `balanceOf(_account)` and multiplies it by the **entire** `rewardPerToken` delta accrued since the old checkpoint, crediting far more reward than the attacker actually earned while holding the small balance.

Existing guards do not prevent this: `onlyMasterMagpie` only gates `getReward`, not `updateFor`; there is no `nonReentrant`/timing guard preventing a large stake increase from happening between the last checkpoint and the next `updateFor` call; and reward accounting has no time-weighting, only a per-token-index snapshot that must be kept in sync with balance changes by external code this file does not control.

### Impact Explanation
Direct theft of yield from other genuine long-term stakers: the excess reward paid to the attacker (`newBalance - actualStakedBalanceDuringAccrual) * rewardPerTokenDelta / 1e18`) comes out of the same finite `rewardPerTokenStored` pool that should have been shared only among stakers who held balance during that period — a permanent, unrecoverable transfer of value away from honest stakers. This matches Immunefi's "direct theft of user funds" / "theft of unclaimed yield" impact class.

### Likelihood Explanation
Exploitability depends entirely on whether the actual staking/locking flow (in `MasterMagpie`, `VLMGP.sol`, or `mWomSV.sol`, none of which I was able to fully inspect within the available tool budget) synchronously calls `mWOMSVBaseRewarder.updateFor(account)` before mutating `stakingInfo`. I could not confirm from the retrieved code whether that atomic checkpoint is enforced elsewhere in the protocol. The vulnerable accounting pattern in this file (`_earned`/`_updateFor`/permissionless `updateFor`) is confirmed and is inherently unsafe unless every balance-changing call site elsewhere in the codebase disciplined enforces the checkpoint-before-mutate ordering. Given I cannot verify that discipline exists for every code path that can change `stakingInfo(stakingToken, account)` (deposits, MGP locks converted to mWOMSV, etc.), I cannot state with certainty that this is exploitable end-to-end, only that the local contract logic contains the necessary precondition for the described attack.

### Recommendation
Do not rely on `balanceOf()` being externally synchronized. Either (a) have this rewarder maintain its own internal balance ledger with `stake`/`withdraw` entrypoints restricted to `onlyMasterMagpie`, checkpointing rewards via the `updateReward` modifier atomically with every balance mutation (as `BaseRewardPool.sol`/`BaseRewardPoolV2.sol` appear to do), or (b) if balance must stay externally sourced, require every contract capable of mutating `stakingInfo(stakingToken, account)` to call `mWOMSVBaseRewarder.updateFor(account)` in the same transaction, before the mutation, and add an explicit check/invariant test verifying no balance-changing call path can bypass this checkpoint.

### Proof of Concept
Cannot be made fully concrete without confirming the exact call path in `MasterMagpie.sol`/`VLMGP.sol`/`mWomSV.sol` that mutates `stakingInfo(stakingToken, account)`, which was not retrievable within the available tool budget. A Foundry/Hardhat PoC would need to:
1. Deploy `mWOMSVBaseRewarder`, `MasterMagpie` mock, and the actual locker.
2. Have attacker stake a small amount, call `updateFor(attacker)` to checkpoint.
3. Manager calls `queueNewRewards` to accrue `rewardPerTokenStored`.
4. Attacker increases stake to a large amount via whatever code path mutates `stakingInfo` (e.g., `VLMGP.lock`) — assert whether `updateFor` was NOT called as part of that path.
5. Attacker calls `updateFor(attacker)`/`getReward` and assert `userRewards[token][attacker]` reflects `largeBalance * fullRewardDelta`, exceeding the attacker's fair pro-rata share, and that other stakers' claimable rewards are correspondingly reduced/insufficient (`rewardInfo` no longer able to pay out all legitimate claims).

Given the uncertainty about the exact staking call path, I flag this as a structural finding requiring confirmation against `MasterMagpie.sol`/`VLMGP.sol`/`mWomSV.sol` rather than a fully proven, reproducible exploit at this time.
