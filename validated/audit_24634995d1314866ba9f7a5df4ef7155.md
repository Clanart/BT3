### Title
Vesting/locked coins stranded at the direct-cast address after EVM address re-association become permanently unspendable - ([File: utils/helpers/associate.go])

### Summary
The bug report's core pattern — a deposit/bond is moved into an on-chain account that later has no way to be reclaimed once the associated lifecycle transition happens — has a direct analog in Sei's EVM↔Cosmos address-association flow. When an EVM address is associated with a *different* true `sei1…` address (e.g. via `MsgAssociate`/`associatePubKey`, reachable by any unprivileged EVM/Cosmos transaction sender), `AssociationHelper.MigrateBalance` only migrates the direct-cast address's **spendable** coins and wei balance to the newly associated Sei address. Any **locked** coins (e.g. a vesting account funded at the direct-cast address before association) are left behind, and the direct-cast account is only deleted if `LockedCoins` is zero.

### Finding Description
`AssociationHelper.AssociateAddresses` and `MigrateBalance` implement the balance-migration logic run whenever an EVM address becomes associated (or re-associated) with a Sei address: [1](#0-0) [2](#0-1) 

`MigrateBalance` moves `SpendableCoins` and the wei balance from `castAddr` (`sdk.AccAddress(evmAddr[:])`) to the real `seiAddr`, and only removes the `castAddr` account entirely `if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero()`. Locked coins (e.g. vesting coins that were sent to the cast address before the true owner associated their pubkey with a *different* Sei address) are never migrated and the account persists at `castAddr` holding them.

This is confirmed by the unit test, which explicitly shows 1 `usei` staying `LockedCoins` at the cast address after migration while the rest is moved: [3](#0-2) 

Once association has occurred, `GetSeiAddress`/`GetEVMAddress` mappings route all future EVM-signed activity from that private key to the *true* `seiAddr`, never to `castAddr` again: [4](#0-3) 

And `CanAddressReceive` explicitly marks the cast address as unable to receive new funds once it is associated to a different address, formalizing that `castAddr` is a dead-end identity going forward: [5](#0-4) 

Because `castAddr` is a raw 20-byte cast of the EVM address (not a normal secp256k1 pubkey hash), and the account created there via `NewAccountWithAddress` has no pubkey set, there is no way to natively sign a Cosmos `MsgSend` from `castAddr` to move out coins once they eventually finish vesting and become spendable — the only path that could have moved them (this same `MigrateBalance`/`AssociateAddresses` flow) has already run and will not run again for coins that arrive at `castAddr` afterward or that were locked at the time of association. There is no other code path in the module (checked `x/evm/migrations/migrate_cast_address_balances.go`, which performs the identical incomplete migration for all mapped addresses, and again only migrates spendable coins and wei, never locked coins) that reclaims this locked balance: [6](#0-5) 

This mirrors the reported bug class precisely: value is deposited (vesting-locked) at an address tied to a lifecycle state (an EVM address not yet associated to its final identity), a state transition occurs (association is set/changed, the ExManager analog of "unwind"), and afterward there is no burn/redeem/withdraw mechanism to recover the locked value — it is permanently orphaned in the account.

### Impact Explanation
Any usei (or other locked-denom coins, e.g., via a vesting grant, airdrop, or governance-created vesting account) that end up locked at the *direct-cast* Sei address of an EVM address before that EVM address is associated to a different true Sei address become permanently frozen. No key can ever author a valid Cosmos signature for `castAddr` (it's not a pubkey-derived address), and the only code that historically moves coins out of `castAddr` (`MigrateBalance`) already ran and does not re-run for coins locked at/after that point. This is a fund-freezing bug (Medium/High depending on how commonly cast addresses receive vesting grants prior to association), matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Reachable by an ordinary user: any account can receive a vesting grant (or other locked-coin credit) to the direct-cast Sei address corresponding to an EVM address before that EVM address/private key holder submits an `Associate`/`SetCode`/normal EVM tx that maps the EVM address to a *different* true Sei address (e.g. reusing a previously airdropped/vesting cast identity while operating from a fresh HD-wallet-derived Sei key). This requires no privileged access — only a standard EVM transaction from an unassociated address plus a prior deposit of locked coins to its cast address, both of which are normal, expected chain operations documented and tested in the codebase itself.

### Recommendation
Extend `AssociationHelper.MigrateBalance` (and the analogous `x/evm/migrations/migrate_cast_address_balances.go`) to also migrate locked/vesting balances from `castAddr` to the real `seiAddr` (e.g., by transferring the underlying vesting schedule/`BaseVestingAccount` state to the new address, or by unlocking and forwarding the coins), instead of leaving the account in place only when `LockedCoins` is non-zero. Alternatively, provide an explicit, permissionless message that lets the holder of the EVM private key claim any residual locked balance at their cast address into their associated Sei address once the lock matures.

### Proof of Concept
1. Create (e.g., via governance/vesting genesis or a vesting-account-creating message) a `ContinuousVestingAccount`/`DelayedVestingAccount` at `castAddr = sdk.AccAddress(evmAddr[:])` for an EVM address `evmAddr` that has not yet been associated on-chain, funding it with locked `usei`.
2. From the private key controlling `evmAddr`, submit a normal EVM transaction (or `MsgAssociate`) that is *not* the direct-cast identity's own preimage but is signed such that `AssociateAddresses` maps `evmAddr` to a different true `seiAddr` (this is the standard flow the ante handler performs automatically the first time an EVM tx is processed for an unassociated sender, as seen in `x/evm/ante/preprocess.go`).
3. Observe (as in `TestMigrateBalance`) that `k.BankKeeper().LockedCoins(ctx, castAddr)` remains non-zero after association and `SpendableCoins(ctx, seiAddr)` does not include it.
4. Wait for the vesting schedule to mature; attempt to spend from `castAddr` via a normal Cosmos `MsgSend` — no key exists that can produce a valid signature for `castAddr` (it is not a secp256k1-pubkey-derived address), and no further association/migration call moves these matured coins, leaving them permanently stranded.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

func TestMigrateBalance(t *testing.T) {
	k := &testkeeper.EVMTestApp.EvmKeeper
	ctx := testkeeper.EVMTestApp.GetContextForDeliverTx(nil)
	admin, _ := testkeeper.MockAddressPair()

			k.AccountKeeper().NewAccountWithAddress(ctx, sdk.AccAddress(evmAddr[:])).(*authtypes.BaseAccount),

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}

func (k *Keeper) DeleteAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Delete(types.EVMAddressToSeiAddressKey(evmAddress))
	store.Delete(types.SeiAddressToEVMAddressKey(seiAddress))
}

func (k *Keeper) GetEVMAddress(ctx sdk.Context, seiAddress sdk.AccAddress) (common.Address, bool) {
	store := ctx.KVStore(k.storeKey)
	bz := store.Get(types.SeiAddressToEVMAddressKey(seiAddress))
	addr := common.Address{}
	if bz == nil {
		return addr, false
	}
	copy(addr[:], bz)
	return addr, true
}

func (k *Keeper) GetEVMAddressOrDefault(ctx sdk.Context, seiAddress sdk.AccAddress) common.Address {
	addr, ok := k.GetEVMAddress(ctx, seiAddress)
	if ok {
		return addr
	}
	return common.BytesToAddress(seiAddress)
}

// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

func MigrateCastAddressBalances(ctx sdk.Context, k *keeper.Keeper) (rerr error) {
	k.IterateSeiAddressMapping(ctx, func(evmAddr common.Address, seiAddr sdk.AccAddress) bool {
		castAddr := sdk.AccAddress(evmAddr[:])
		if balances := k.BankKeeper().SpendableCoins(ctx, castAddr); !balances.IsZero() {
			if err := k.BankKeeper().SendCoins(ctx, castAddr, seiAddr, balances); err != nil {
				logger.Error("error migrating balances from cast to real for address", "address", evmAddr, "err", err)
				rerr = err
				return true
			}
		}
		if wei := k.BankKeeper().GetWeiBalance(ctx, castAddr); !wei.IsZero() {
			if err := k.BankKeeper().SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), wei); err != nil {
				logger.Error("error migrating wei from cast to real for address", "address", evmAddr, "err", err)
				rerr = err
				return true
			}
		}
		return false
	})
	return
}
