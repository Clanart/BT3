### Title
Unvalidated `Participant` index causes panic (node crash) when evaluating PedPoP blame proofs - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2024-35989 — a cleanup/fault-handling path dereferences a target that was never validated to exist — `Decryption::decrypt_with_proof` (invoked by `BlameMachine::blame` / `AdditionalBlameMachine::blame` when resolving an accusation of an invalid DKG secret share) indexes `self.enc_keys[&decryptor]` directly. `decryptor` is the `recipient` `Participant` supplied by the caller alongside attacker-controlled message/proof bytes. No check ensures the recipient actually registered an encryption key, so a `Participant` value outside the registered set causes a HashMap-index panic, crashing the blame-evaluation path.

### Finding Description
`Decryption::register` only inserts an entry per participant that actually submitted an `EncryptionKeyMessage` (`crypto/dkg/pedpop/src/encryption.rs:351-362`, and `AdditionalBlameMachine::new` at `crypto/dkg/pedpop/src/lib.rs:649-662` which only registers indexes `1..=n` that supplied messages). In `decrypt_with_proof`, when the accuser supplies `proof: Some(...)`, the code evaluates:

```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],
)
```

at `encryption.rs:383-390`. `self.enc_keys[&decryptor]` is evaluated as part of building the argument array *before* any DLEq verification, so the panic occurs regardless of whether the proof is valid. The only gate beforehand is `msg.pop.verify(...)` at lines 374-379, a Schnorr proof-of-possession over `msg.key` with challenge `pop_challenge(context, R, key, from, msg)` — trivially satisfiable by any sender who picks their own ephemeral key and signs.

The same pattern exists at `crypto/dkg/pedpop/src/lib.rs:599` where `blame_internal` indexes `self.commitments[&sender]` with a caller-supplied `sender`, panicking if that participant's commitments aren't in the map.

Both `BlameMachine::blame` (`lib.rs:623-632`) and `AdditionalBlameMachine::blame` (`lib.rs:674-682`) accept `sender` and `recipient` as free `Participant` arguments and neither validates them against `enc_keys`/`commitments` membership before indexing. `AdditionalBlameMachine` is explicitly designed to be usable by an external evaluator who "was not a member in the DKG protocol," so these inputs are untrusted.

### Impact Explanation
Any party able to submit a blame claim (a DKG participant, or anyone feeding an `AdditionalBlameMachine` evaluator) can crash the process evaluating blame by naming a `recipient`/`sender` `Participant` index that was never registered. This aborts fault attribution and, in a running processor, is a remote, unprivileged-input-triggered denial of service — matching the availability impact class of the reference advisory. Note that blame evaluation determines *which* party is faulty; a crash means honest validators cannot complete blame attribution, forcing DKG/protocol abort without accountability.

### Likelihood Explanation
The attacker needs only:
1. A `msg` whose `pop` Schnorr signature verifies — they generate the ephemeral key themselves, so this is free.
2. `proof: Some(...)` with any `EncryptionKeyProof` (contents never reached).
3. A `recipient` `Participant` index not present in `enc_keys` — e.g., an index `> n`, or a legitimate index for a participant whose `EncryptionKeyMessage` was absent.

`Participant` is any nonzero `u16`, so out-of-range values are representable and reachable through the public `blame`/`AdditionalBlameMachine` API and through `EncryptedMessage::read`/`EncryptionKeyProof` deserialization of attacker bytes.

### Recommendation
Replace the indexing operations with fallible lookups: `self.enc_keys.get(&decryptor)` and `self.commitments.get(&sender)`, returning `DecryptionError::InvalidProof` / a defined `PedPoPError` (or blaming the accuser/requester) when the participant is unregistered. Also explicitly bound-check `sender`/`recipient` against `1..=n` in `BlameMachine::blame` and `AdditionalBlameMachine::blame` before use.

### Proof of Concept
```rust
// Context: an AdditionalBlameMachine built over n registered participants,
// or a BlameMachine from a completed calculate_share.
let additional = AdditionalBlameMachine::<Ristretto>::new(CONTEXT, n, commitment_msgs).unwrap();

// Attacker crafts an EncryptedMessage with a self-signed pop:
// pick ephemeral scalar r, key = G*r, R = G*k, s = k + H(context,R,key,from,msg)*r
let msg: EncryptedMessage<Ristretto, SecretShare<_>> = /* valid pop, arbitrary ciphertext */;

// Recipient index that was never registered (n+1 is still a valid nonzero Participant)
let unregistered = Participant::new(n + 1).unwrap();

// Passing proof: Some(any EncryptionKeyProof) reaches
//   &[self.enc_keys[&decryptor], *proof.key]
// before DLEq verification -> HashMap index panic -> process abort.
additional.blame(sender, unregistered, msg, Some(proof));
```

Equivalently, within `blame_internal`, a `sender` whose commitments were never stored panics at `self.commitments[&sender]` (lib.rs:599) once decryption succeeds.
