## Analysis

The Sherlock/OtterSec findings describe a common Solana/Anchor pattern: an instruction validates that account `A` was signed/approved by its rightful controller (`governor.smart_wallet == smart_wallet` signer), but never checks that the *relationship* between the two accounts that are supposed to be bound together (`locker.governor == governor`) actually holds. This lets an attacker substitute a self-consistent-but-unrelated account and bypass the intended per-resource authorization.

The closest analog reachable from an anonymous/unrelated-merchant HTTP request in `shopify_app` is in webhook verification. `ShopifyApp::WebhookVerification` (and the identical pattern documented for custom controllers) verifies only that the **request body** is HMAC-signed with the app's shared secret, but the **shop identity** used to route/process the webhook is read from an unsigned header and is never bound into that verification: [1](#0-0) [2](#0-1) 

The `hmac_valid?` check only covers `request.raw_post`; `shop_domain` is pulled straight from `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]`, which is not part of the signed material at all. The gem's own documentation instructs developers to build custom controllers on exactly this trust boundary, passing the unverified `shop_domain` directly into job dispatch: [3](#0-2) 

### Title
Webhook HMAC verification does not bind shop identity to the signed payload, allowing cross-shop webhook spoofing - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only validates that `request.raw_post` was HMAC-signed with the app's client secret via `PayloadVerification#hmac_valid?`. The `shop_domain` value that downstream code uses to attribute/scope the webhook to a specific merchant (`shop_domain` method, and the value passed to jobs like `perform_later(shop_domain: shop_domain, ...)`) is read from the `X-Shopify-Shop-Domain` header, which is **not covered by the HMAC**. This is directly analogous to the audited bug: the signer/secret is validated (like `governor.smart_wallet == smart_wallet`), but the binding between that valid signature and the specific tenant resource it should apply to (`locker.governor == governor`) is never checked.

### Finding Description
The app's HMAC secret (`ShopifyApp.configuration.secret`) is a single shared secret for the whole app, not per-shop. Any merchant who has installed the app can trigger legitimate webhook deliveries for their own shop (e.g. by updating a cart/product), thereby obtaining a valid `(body, HMAC)` pair signed by the app's secret. Because the shop-domain header is excluded from the signed content, that same merchant can replay the captured request to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g., a competitor's shop domain). `verify_request` will still pass since it only checks `hmac_valid?(data)`: [4](#0-3) 

Any controller/job built per the documented pattern will then process attacker-controlled data as if it belongs to the spoofed `shop_domain`: [5](#0-4) 

### Impact Explanation
Depending on what the app's webhook job does with `shop_domain` (e.g., updating shop-scoped records, invalidating caches, triggering shop-specific business logic, writing data keyed by shop), this allows a malicious but legitimately-installed merchant to inject attacker-controlled webhook payloads attributed to an unrelated shop, causing cross-tenant data corruption or unauthorized state changes scoped to a shop the attacker does not control.

### Likelihood Explanation
Requires the attacker to be an installed (but otherwise unprivileged/unrelated) merchant able to trigger a real webhook delivery for their own shop and then replay it with a modified header against the app's public webhook endpoint. No secret leakage or special access is required beyond normal app installation, which is a realistic "unrelated-merchant HTTP request" threat model.

### Recommendation
Bind the trusted shop identity into the verification step rather than trusting the `X-Shopify-Shop-Domain` header independently of the signed payload — e.g., derive/verify the shop from the signed webhook body content (Shopify webhook payloads include shop-identifying fields) or otherwise cryptographically bind the shop domain to the HMAC computation, and reject requests where the header-provided domain doesn't match the domain embedded in the verified payload.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`.
2. Trigger a real webhook event (e.g., update a cart) to receive a legitimate `(raw_post, X-Shopify-Hmac-Sha256)` pair signed by the app's shared secret, along with header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Resend the identical `raw_post` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim.myshopify.com`.
4. `WebhookVerification#verify_request` passes because `hmac_valid?(raw_post)` only checks the body signature; the controller/job then processes the payload as if it originated from `victim.myshopify.com`.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

  end

  def webhook_params
