### Title
SignableTransaction omits the OP_RETURN output from its size/fee calculation, systematically underpaying the requested fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

The reported bug class is "an action is committed before all of its effects are accounted for" — in the original report, a transaction executes before being deleted, so a second confirmation re-executes it. The structural analog in Serai is `SignableTransaction::new`: the OP_RETURN data output is pushed into `tx_outs` (the committed transaction) at `send.rs:194-202`, *before* the weight/vbytes used for `needed_fee` are computed at `send.rs:204`, and `calculate_weight_vbytes` is only ever passed `payments` and `change` — never the OP_RETURN output. The fee therefore covers a smaller transaction than the one actually produced, so the signed transaction pays a lower effective fee rate than `fee_per_vbyte`, and can fall below the mempool's minimum relay fee even though `TooLowFee` was checked.

### Finding Description

`SignableTransaction::new` builds the output list as:

- `send.rs:188-191`: `tx_outs` = payments
- `send.rs:194-202`: `tx_outs.push(OP_RETURN output)` when `data` is supplied
- `send.rs:204`: `(weight, vbytes) = calculate_weight_vbytes(tx_ins.len(), payments, None)`
- `send.rs:225-226`: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`

`calculate_weight_vbytes` (`send.rs:62-99`) constructs a template `Transaction` whose `output` is built only from `payments` plus the optional change output. The OP_RETURN output added at line 195 is never included in the template, so `vbytes` underestimates the real virtual size by roughly `9 + 1 + script_len` bytes (an OP_RETURN output with up to 80 bytes of data ≈ ~90+ vbytes) on every call.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is smaller than `fee_per_vbyte * actual_vsize`. The caller's requested fee rate is silently not achieved whenever `data` is present.
2. The `TooLowFee` guard at `send.rs:211` compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`. A caller-specified `fee_per_vbyte` that exactly meets minimum relay for the *template* tx produces a final transaction whose real feerate is below minimum relay, causing Bitcoin nodes to reject it from the mempool.
3. The change branch (lines 224-235) computes `fee_with_change` on the same underestimated size, so the change output's value is also slightly wrong (change absorbs the error, keeping `sum(inputs) - sum(outputs) = needed_fee`, but the effective feerate is still low).

Note that `fee()` (line 138) correctly reports `sum(prevouts) - sum(outputs)`, so the discrepancy is only detectable after construction by comparing `fee()` to `needed_fee * actual_vsize / vsize` — the committed state (the built `tx` inside `SignableTransaction`) does not match the fee accounting that was performed before it was finalized.

### Impact Explanation

Any `SignableTransaction` created with non-empty `data` pays a strictly lower effective feerate than requested. For a near-minimum `fee_per_vbyte`, the produced transaction is below `DEFAULT_MIN_RELAY_TX_FEE` in real terms and will be rejected by relaying nodes — the threshold signature ceremony completes and produces witnesses for a transaction the network will not accept, stalling the spend and forcing a full re-sign with corrected parameters. For higher fee rates, the transaction still confirms more slowly than the caller intended, which is a correctness violation of the `fee_per_vbyte` contract rather than a mere rounding error (the missing size is up to ~90 vbytes of an OP_RETURN, not sub-byte dust). Since `data` is attacker/user-influenced (in the wider system it carries `InInstruction` payloads supplied by external depositors), the underpayment is reachable from untrusted inputs to the transaction-building path.

### Likelihood Explanation

The bug triggers deterministically on every `SignableTransaction::new` call where `data: Some(_)` is supplied — no race, no malicious counterparty, no edge-case inputs required. Whether it becomes an *exploitable/observable* failure depends on how close `fee_per_vbyte` is to the minimum relay threshold: transactions built with comfortable fee margins merely confirm slower than intended, while minimally-priced transactions are outright unrelayable. The size gap scales with `data` length (up to 80 bytes allowed by the `TooMuchData` check at line 171), so maximal-length data maximizes the underpayment.

### Recommendation

Include the OP_RETURN output in the size calculation, either by:

- Passing the fully-built `tx_outs` (payments + OP_RETURN) into `calculate_weight_vbytes` instead of `payments`, so the template transaction matches the real output set before change is considered; or
- Computing `vbytes` after `tx_outs` is finalized (payments + OP_RETURN), then adding the change output's marginal size when the change branch is taken.

After the fix, `needed_fee` should satisfy `needed_fee >= fee_per_vbyte * final_tx_vsize` and `needed_fee >= DEFAULT_MIN_RELAY_TX_FEE * final_tx_vsize / 1000` for the transaction actually produced, and the `TooLowFee` check should be evaluated against that final size.

### Proof of Concept

```rust
// networks/bitcoin context; Secp256k1 keys from frost
let mut scanner = Scanner::new(key).unwrap();
let output: ReceivedOutput = /* any scanned output */;

let payments = [(p2tr_script_buf(dest_key).unwrap(), 100_000u64)];
let data = vec![0xAA; 80]; // max permitted by TooMuchData check
let fee_rate = 1; // sat/vbyte

let tx = SignableTransaction::new(
    vec![output],
    &payments,
    None,
    Some(data.clone()),
    fee_rate,
).unwrap();

let real_vsize = tx.transaction().vsize() as u64;
// needed_fee was computed as fee_rate * vbytes where vbytes EXCLUDES the OP_RETURN output
assert!(tx.needed_fee() < fee_rate * real_vsize); // underpaid vs. requested rate

// The actual fee equals needed_fee (change-less), so the real feerate is < fee_rate:
assert_eq!(tx.fee(), tx.needed_fee());

// For a fee_rate that only just clears the min-relay check at send.rs:211 on the
// underestimated vsize, tx.fee() / real_vsize < DEFAULT_MIN_RELAY_TX_FEE/1000,
// and the fully-signed transaction is rejected by Bitcoin Core mempool policy.
```

The relevant lines: OP_RETURN pushed at `send.rs:194-202`, weight computed from `payments` only at `send.rs:204` and `send.rs:225-226`, and `calculate_weight_vbytes` building the template from `payments`/`change` only at `send.rs:85-99`.
