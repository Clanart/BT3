### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/vbytes used for fee calculation, producing under-funded transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report's bug class is a limit/accounting check computed on an aggregate that silently omits contributions from a second path (mint limit measured on `totalSupply` which also counts claims). The Serai analog is in `SignableTransaction::new`: the fee and change math is computed from `calculate_weight_vbytes`, which is only passed `payments` — the `data` OP_RETURN output (up to 80 bytes of user-supplied data, pushed to `tx_outs` at send.rs:194-202) is never included in the weight used to derive `needed_fee`, nor in the change computation.

### Finding Description
`SignableTransaction::new` (send.rs:150) builds `tx_outs` including an OP_RETURN output for `data` (send.rs:194-202). However, `calculate_weight_vbytes(tx_ins.len(), payments, None)` at send.rs:204 and `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at send.rs:226 only serialize payment outputs (and optionally change) — never the OP_RETURN output (send.rs:85-99). Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) under-counts the transaction's real vsize by roughly 11–90+ bytes (8-byte value + script length + up to 80 bytes of pushed data).
- The minimum-relay-fee check at send.rs:211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`, so a transaction can pass this check yet actually pay below the node's minimum relay fee once the data output is added.
- When a change output is created, its value `input_sat - payment_sat - fee_with_change` (send.rs:228-230) is computed with the same underestimated fee, so the *actual* fee paid (`inputs - outputs`) equals `fee_with_change`, which still under-covers the real vsize.

In the processor, `Bitcoin::make_signable_transaction` calls `BSignableTransaction::new` with `data: None` for out-instructions (processor/src/networks/bitcoin.rs:446-451), but `needed_fee` (bitcoin.rs:803-815) drives `prepare_send`'s amortization (processor/src/networks/mod.rs:442-495); any caller passing `data` (the constructor explicitly supports it, and `extract_serai_data`/InInstruction flows attach data to external outputs) produces a plan whose fee assumptions are wrong. The accepted-impact analog: a transaction is constructed and signed whose effective fee rate is below what was specified — potentially below `DEFAULT_MIN_RELAY_TX_FEE` — so the network rejects or stalls the broadcast, leaving funds unspendable/unforwarded despite the plan being treated as fulfillable.

### Impact Explanation
An unprivileged user controls the `data` bytes attached to Bitcoin transactions that reach this constructor (InInstruction data, capped at 80 bytes per the `TooMuchData` check at send.rs:171). The signed transaction's true fee rate is `fee_per_vbyte * vbytes_underestimated / vbytes_actual`, which is strictly less than `fee_per_vbyte`. When `fee_per_vbyte` is at or near the minimum relay fee, the transaction fails `sendrawtransaction` mempool acceptance (bad-txns rejection or silent non-propagation), so the associated eventuality/forwarded funds never complete — an availability failure indistinguishable from "funds reported as sent that are not". Even when relayable, the system systematically under-pays fees by up to ~90 vbytes × fee rate per data-carrying transaction, contradicting `needed_fee()`'s documented contract (send.rs:129-135).

### Likelihood Explanation
Reachable whenever `data` is `Some` and the chosen fee rate is near the relay minimum — exactly the regime the `TooLowFee` guard exists for. The user only needs to supply 80 bytes of data; no validator collusion or privileged role is required. The discrepancy is deterministic (not probabilistic): the OP_RETURN output is always excluded from the weight estimate.

### Recommendation
Include the OP_RETURN output in the weight estimation. Either pass the final `tx_outs` (or a synthetic `TxOut` with the OP_RETURN script) into `calculate_weight_vbytes`, or add its serialized size to the computed weight before deriving `vbytes`/`needed_fee`, at both call sites (send.rs:204 and send.rs:226). Additionally, re-check `TooLowFee` against the final transaction weight rather than the pre-data estimate.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
