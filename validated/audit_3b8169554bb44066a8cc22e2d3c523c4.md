Based on my investigation, I found a valid analog of this bug class in `WombatStaking.depositLP`.

### Title
Fee-on-transfer LP tokens cause over-minting of receipt tokens and protocol insolvency in `depositLP` - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.depositLP` transfers LP tokens from a caller with `safeTransferFrom` using the caller-supplied `_lpAmount`, but never checks how many tokens were actually received before staking that same `_lpAmount` to Master Wombat and minting `_lpAmount` receipt tokens. [1](#0-0)  If the underlying LP/deposit token charges a fee on transfer, the contract receives less than `_lpAmount` yet still stakes and mints as if it received the full amount.

### Finding Description
In `depositLP`, the flow is:
```
IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);
_toMasterWomAndSendReward(_lpAddress, _lpAmount, true);
IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);
``` [2](#0-1) 

`_toMasterWomAndSendReward` with `_isStake = true` calls `_stakeToWombatMaster(_lpAddress, lpAmount)`, which approves and deposits exactly `lpAmount` into Master Wombat without verifying the contract's actual token balance beforehand: [3](#0-2) 

This is the same root-cause pattern as the referenced report: the contract trusts the nominal transfer amount instead of measuring the actual balance delta. Notably, the sibling function `deposit` (non-LP path) in the same file *does* correctly measure the LP balance delta before minting receipt tokens (`lpReceived = balanceOf(after) - balanceOf(before)`), [4](#0-3)  showing the developers were aware of this pattern but did not apply it consistently to `depositLP`.

### Impact Explanation
If any registered pool's `lpAddress` (the Wombat LP/asset token) implements a transfer fee, a depositor calling `depositLP` (or via `WombatPoolHelper.depositLP`/`AnkrBNBPoolHelper.depositLP`, which forward user-supplied `_lpAmount` to this function) [5](#0-4)  would receive receipt tokens for the full `_lpAmount`, while Master Wombat only received the post-fee amount actually held by the contract (the `_stakeToWombatMaster` call would attempt to deposit `_lpAmount`, exceeding what was received, causing either a revert due to insufficient balance during the internal transferFrom in Master Wombat, or if Master Wombat also has slack/tolerance, an under-collateralized stake). This creates a permanent accounting mismatch between receipt token supply and actual staked assets, leading to insolvency: later withdrawers would be unable to redeem their proportional share because assets backing them never fully entered the system.

### Likelihood Explanation
This path is reachable by any ordinary wallet holding registered LP tokens via `depositLP`, `WombatPoolHelper.depositLP`, or `AnkrBNBPoolHelper.depositLP` — no privileged role is required. [5](#0-4) [6](#0-5)  Exploitability depends on whether any pool's registered `lpAddress` token has a transfer fee; this is a protocol-level design/config risk rather than a certainty for all current pools, since Wombat pool LP tokens are typically standard ERC20s. However, given `registerPool` is admin-controlled but the code itself lacks defense-in-depth against fee-on-transfer tokens (unlike the `deposit` function which is correctly balance-checked), this is a legitimate root-cause finding independent of any specific token currently registered.

### Recommendation
In `depositLP`, measure the actual LP token balance received before and after the `safeTransferFrom` call (as already done correctly in `deposit`), and use that measured amount for both `_toMasterWomAndSendReward` staking and receipt-token minting, instead of trusting the caller-supplied `_lpAmount`.

### Proof of Concept
1. Admin registers a pool whose `lpAddress` implements a fee-on-transfer (e.g., 1% fee) — plausible for third-party or wrapped LP tokens.
2. A user calls `depositLP(_lpAddress, 1000e18, user)` (directly or through `WombatPoolHelper.depositLP`).
3. `safeTransferFrom` moves 1000e18 nominally but the contract only receives 990e18 due to the fee. [7](#0-6) 
4. `_toMasterWomAndSendReward` attempts to stake the full 1000e18 to Master Wombat via `_stakeToWombatMaster`, which will either revert (insufficient balance) or, in pools without strict checks, leave the staking under-collateralized. [8](#0-7) 
5. If it does not revert, `receiptToken` is minted for the full 1000e18 to the user despite only 990e18 actually being staked, permanently over-inflating claims against the pool's real assets. [9](#0-8)
