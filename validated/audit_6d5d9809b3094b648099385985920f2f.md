### Title
Remote denial of service via infinity-inducing nonce commitments in BIP-340 `Hram` - ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
The Squid CVE is a DoS triggered by a plausibly-occurring, attacker-supplied value reaching a parser/verifier. The Serai analog lives in the bitcoin-serai FROST glue: `Hram::hram` calls `x(R)`, which panics when `R` is the point at infinity. An unprivileged cosigner can supply preprocess bytes (read via `Commitments::read`/`read_G`, which accept the canonical identity encoding) chosen so the aggregate nonce sum is infinity, causing `expect("point at infinity")` to abort the process during `sign_share`/`verify`.

### Finding Description
- `x()` unconditionally unwraps the x-coordinate: `(*encoded.x().expect("point at infinity")).into()` at `networks/bitcoin/src/crypto.rs:13-16`.
- `Hram::hram` (lines 59-73) calls `x(R)` and `x(A)` on the aggregate nonce `R` and group key `A`.
- `R` is the sum over per-participant nonce commitments, which arrive as serialized group elements. `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-100`) only enforces canonicality — the identity point is a valid canonical encoding and is accepted.
- A participant sending preprocess `Preprocess` bytes whose `Commitments` points are chosen to negate the honest sum forces `R = identity` (or contributes `identity` directly where sums aren't checked before `hram`). `verify`/`sign_share` then reach `hram(R, A, m)` → `x(R)` → panic.
- The same panic path exists in `x_only`/`needs_negation` callers (`crypto.rs:21-28`), and the code itself documents the panic: "If either `R` or `A` is the point at infinity, this will panic" (lines 54, 78-83). The assumption that infinity has "negligible probability even with malicious participants present" is wrong: a malicious participant deterministically forces it via their public commitment bytes.

### Impact Explanation
A single untrusted preprocess message deterministically panics the signing process (which, as elsewhere in Serai, is configured to `std::process::exit(1)` on task panic — see `networks/ethereum/relayer/src/main.rs:13-19` for the codebase's panic policy). Repeated submissions permanently deny signing. This is an availability-only impact, matching the Medium severity of the source CVE.

### Likelihood Explanation
The trigger requires only that the attacker be a signing participant able to send a preprocess — no key material, no race, no special privileges beyond submitting bytes to `read_G`/`Commitments::read`. Identity encodings pass all canonicality checks. One-shot, deterministic, cost-free to the attacker.

### Recommendation
Before computing `hram`, reject infinity: check `R.is_identity()` (and each nonce commitment sum) in `FrostSchnorr::sign_share`/`verify`/`verify_share` and return a `FrostError`/abort the session gracefully instead of panicking. Additionally, reject identity points in `Commitments::read` for FROST preprocesses, or at minimum make `x()`/`x_only()` return `Option`/`io::Error` rather than `expect`ing.

### Proof of Concept
1. Attacker (participant `i`) runs a FROST sign session using `Schnorr` from `networks/bitcoin/src/crypto.rs`.
2. In the preprocess round, the attacker broadcasts a `Preprocess` whose `Commitments` (parsed via `read_G`, so identity is accepted) are chosen as the negation of the honest participants' expected commitment sums — e.g., after seeing honest commitments, send commitments `C_i = -Σ_{j≠i} C_j` so `R = identity`.
3. During `sign_share`, `FrostSchnorr` computes `R`, calls `Hram::hram(&R, &A, msg)` → `x(&R)` → `to_encoded_point` on infinity yields `x() == None` → `expect("point at infinity")` panics → process abort.
4. Any `verify`/`verify_share` evaluation of the same aggregate hits the identical panic path.

// networks/bitcoin/src/crypto.rs
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into() // panic when key == identity
}
