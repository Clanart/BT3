### Title
`SignableTransaction::new` computes weight/vbytes (and therefore fee and the standardness check) over `payments` only, omitting the OP_RETURN `data` output — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the LoopFi bug where `loss` was computed against a total that included a component it shouldn't have (principal + interest instead of principal only), `SignableTransaction::new` computes the transaction's weight, virtual size, `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check using a reconstructed transaction that contains *only* the `payments` outputs — even though the real transaction also includes a zero-value OP_RETURN output when `data` is provided. The result is an internally consistent but mispriced transaction: the fee charged corresponds to a smaller transaction than the one actually produced.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the size/fee calculation:

- `tx_outs.push(TxOut { value: ZERO, script_pubkey: new_op_return(data) })` — lines 194–202
- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` — line 204

`calculate_weight_vbytes` builds its template transaction exclusively from `payments` (lines 85–93), plus an optional `change` output (lines 95–99). The `data` output is never represented. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) underpays by `fee_per_vbyte * (vsize of the OP_RETURN output)` — roughly 10 + script_len vbytes.
2. The minimum-relay-fee check (lines 211–213) is evaluated against the understated `vbytes`, so it can pass while the *actual* fee rate of the final transaction is below `DEFAULT_MIN_RELAY_TX_FEE` when `change` is not added, and below the intended `fee_per_vbyte` in all cases.
3. The `MAX_STANDARD_TX_WEIGHT` check (lines 241–243) uses `weight` that excludes the OP_RETURN output, so a transaction that is genuinely non-standard can pass the check.
4. The `NotEnoughFunds` check (line 215) and the change computation `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228, where `fee_with_change` is derived from `calculate_weight_vbytes(..., payments, Some(&change))`, line 226) all consistently use the understated size, so the error is silent — no panic, just a wrong fee.

The `data` argument is an untrusted/public input supplied by whoever constructs the transaction (in the processor this path is used for data-carrying transactions), making this reachable by an unprivileged party feeding bytes into `SignableTransaction::new`.

### Impact Explanation
The signed transaction pays a lower fee rate than requested. Concretely:

- A caller can craft `data` such that the resulting transaction's *real* fee rate is below the minimum relay fee: choose inputs/payments so that `fee_per_vbyte * vbytes_without_opreturn` passes the check at line 211 while `fee_per_vbyte * actual_vsize` would not be met, or simply so that the absolute fee is below what relays require for the actual vsize. The multisig then signs and broadcasts a transaction that is dropped or stuck, freezing the involved UTXOs/outputs (DoS on the vault's outputs).
- Combined with many inputs/payments near the weight limit, the OP_RETURN pushes the real weight above `MAX_STANDARD_TX_WEIGHT` while the check at line 241 passes, producing a non-standard, unrelayable transaction carrying threshold-signed inputs.

This maps to the accepted impact class of an incorrect accounting/subtraction formula producing a wrong fee — funds are not directly stolen, but threshold-controlled outputs can be committed to transactions that cannot confirm.

### Likelihood Explanation
Any code path that calls `SignableTransaction::new` with `data: Some(_)` produces a mispriced transaction deterministically — no race or special conditions needed. Exploitability depends on whether transaction construction with OP_RETURN data is exposed to untrusted input selection (amounts/`data`); where the `data` is fixed-size and honest, the bug only causes a slight fee underpayment, so severity is bounded. Medium is appropriate: reliable miscalculation, impact limited to DoS/mispricing rather than direct theft.

### Recommendation
Build the template transaction in `calculate_weight_vbytes` from the actual `tx_outs` (or pass `data` through and include the OP_RETURN `TxOut` in the weight/vsize calculation). Specifically, change the signature to accept the full output list, e.g. `calculate_weight_vbytes(tx_ins.len(), &tx_outs, change)`, and perform the min-relay-fee check and `MAX_STANDARD_TX_WEIGHT` check against the complete output set.

### Proof of Concept
```rust
// In SignableTransaction::new (networks/bitcoin/src/wallet/send.rs):

// tx_outs now contains payments + OP_RETURN(data)
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(/* data, up to 80 bytes */),
  });
}

// ...but the fee template is built from `payments` only:
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
// `payments` does NOT include the OP_RETURN output -> vbytes understated.

let mut needed_fee = fee_per_vbyte * vbytes; // underpaying fee

// With change:
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
let fee_with_change = fee_per_vbyte * vbytes_with_change; // still omits data
// change output value = input_sat - payment_sat - fee_with_change
// -> actual fee of broadcast TX = fee_with_change, applied to a LARGER tx,
//    so the effective sat/vbyte rate is below fee_per_vbyte.
```
Concrete instance: `data` of 80 bytes adds ~89 vbytes unaccounted. With `fee_per_vbyte` chosen so `needed_fee` just clears `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` at line 211, the real transaction's fee rate falls below the relay minimum and the transaction is rejected by the mempool after being threshold-signed.
