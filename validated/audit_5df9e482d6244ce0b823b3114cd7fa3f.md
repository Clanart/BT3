## Analysis

Reducing the report to its broken invariant: a program keeps a **locally-cached value** (`total_collateral`, `base_balance`) that is trusted for a *critical, irreversible operation* (withdrawal), while the *real* value (actual vault balance) can drift out from under it because an outside actor can directly modify the real value. The fix was to stop trusting the cache and re-derive from the real source before the critical action.

GitHub Desktop has the structurally identical pattern in its partial-commit ("stage individual lines") feature: the UI caches a `DiffSelection` (a set of absolute line indices the user chose to include) against one snapshot of a file's diff, but the actual patch that gets applied to the index at commit time is built from a **freshly re-fetched diff**. The reconciliation code that is supposed to keep the cached selection valid only runs on one narrow code path, not on the path used after routine repository refreshes such as a pull.

### Title
Stale line-index-based commit selection is silently re-applied to a changed file after a pull, corrupting partial commits - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`WorkingDirectoryFileChange.selection` (a `DiffSelection` keyed by *absolute diff line index*) is treated as ground truth when building the patch that is staged and committed, but it is only a locally cached snapshot of "which lines looked interesting in a previous diff." `updateChangedFiles`, which runs on every status refresh (including after a `pull`/`fetch`/merge), blindly re-attaches this stale selection to the newly-refreshed file object with no validation that the indices still correspond to the same content.

### Finding Description
When a file has a partial (line-level) selection pending, `updateChangedFiles` merges the new `git status` result with the previous UI state like this: [1](#0-0) 

Note `return file.withSelection(existingFile.selection)` — the old `DiffSelection` (a `Set<number>` of "diverging" absolute line indices, see [2](#0-1)  ) is copied onto the *new* `WorkingDirectoryFileChange`, which represents the file's *post-refresh* content, without any check that those indices still point at the same lines.

This function is invoked from `_loadStatus`, which is the generic status-refresh path used after routine operations (fetch/pull, periodic background refresh, branch switch, etc.): [3](#0-2) 

There *is* a reconciliation routine that tries to keep a selection valid against a changed diff, `updateChangesWorkingDirectoryDiff`, but it only fires when the currently-viewed file's diff is explicitly reloaded, and even then it admits it is only a heuristic: [4](#0-3) 

It narrows the *set of selectable lines* by size/identity of includeable lines, not by verifying content — so if intervening changes preserve the same count/shape of addable/removable lines (a very plausible outcome after a merge/rebase touching the same region of a text file), a previously-selected index will silently be treated as still valid even though it now refers to different content.

At commit time, `_commitIncludedChanges` takes exactly this cached `file.selection` and hands it to `createCommit`: [5](#0-4) 

`createCommit` → `applyPatchToIndex` then fetches a **brand-new** diff of the current on-disk file and builds the patch by testing `file.selection.isSelected(absoluteIndex)` against that new diff's lines: [6](#0-5) [7](#0-6) 

So the "vault balance" here (the true, current diff) and the "tracked state" (the cached `DiffSelection`) are two different snapshots in time, and nothing at the moment of patch construction confirms they still agree — precisely the discrepancy class described in the report.

### Impact Explanation
This is silent corruption of what the user commits: after a routine pull/merge changes a file the user had already partially staged (a completely ordinary Desktop workflow — stage some lines, then pull to sync before finishing), the subsequent commit can:
- include lines the user never selected (attacker-authored content from the remote merged into the file, picked up because it now sits at an index the user had marked "selected"), or
- omit lines the user explicitly intended to commit.

No error, warning, or diff re-confirmation is shown; the commit dialog shows the (stale) diff the user reviewed earlier, not what is actually staged into the index. Because the attacker only needs control of a git remote/shared branch (one of the explicitly in-scope primitives) and the corruption happens without any additional unnatural step by the victim, this satisfies the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The trigger requires two ordinary, expected actions from the victim: (1) select specific lines of a modified file for a partial commit, then (2) pull/fetch/merge before finishing/clicking "Commit" — a common pattern ("sync, then finish my in-progress commit"). No admin rights, local access, or pre-existing malware are needed; the only thing the attacker needs is write access to a branch/remote the victim pulls from (compromised or malicious collaborator/remote), which is within the accepted "git remote/proxy response" threat class. The only limiting factor is the reconciliation heuristic in `updateChangesWorkingDirectoryDiff`, which is a rough, non-content-aware check and only applies to the actively-viewed file's diff — the generic `updateChangedFiles` path used by ordinary refreshes has none.

### Recommendation
Treat `DiffSelection` as ephemeral UI state tied to the exact diff snapshot it was derived from, not as durable per-file state that survives an underlying content change:
- Tag each cached selection with an identifier/hash of the diff it was computed against (e.g., a hash of the diff hunks or the blob OID), and invalidate (reset to "none"/prompt the user) any selection whose diff identifier doesn't match the file's current content when `updateChangedFiles` runs.
- Alternatively, at commit time (`applyPatchToIndex`/`formatPatch`), re-fetch the diff *before* the selection is finalized and compare it against the diff the selection was made from; if they differ, refuse to build the patch and force the UI to show the new diff for re-confirmation instead of silently applying stale indices.
- Extend the `clearPartialState`-style invalidation used after a user's own commit to also apply whenever the underlying diff for a file with a partial selection changes for any reason (pull, checkout, stash pop, external edit).

### Proof of Concept
1. Victim has file `shared.md` tracked in a repository whose remote is attacker-controlled/compromised.
2. Victim edits `shared.md`, opens the Changes view, and selects only lines 10–12 for inclusion (leaving other modified lines unselected) — `file.selection` now diverges at those absolute indices (see [8](#0-7) ).
3. Before clicking "Commit", the victim clicks "Pull" to sync with the remote. The attacker's branch contains a commit that edits `shared.md` in a way that preserves the same number of changed lines in that region but swaps their content (e.g., replacing benign config lines with malicious ones) so the merge/fast-forward succeeds without conflict.
4. Desktop's post-pull refresh calls `_loadStatus` → `updateChangedFiles`, which reattaches the victim's untouched `DiffSelection` (still indices 10–12) to the new `WorkingDirectoryFileChange` for the merged file (`app/src/lib/stores/updates/changes-state.ts:56`), with no content check.
5. Victim clicks "Commit". `_commitIncludedChanges` → `createCommit` → `applyPatchToIndex` fetches the fresh, post-pull diff and calls `formatPatch`, which stages whatever now sits at indices 10–12 in the *new* diff — the attacker's injected lines — as if the victim had reviewed and selected them (`app/src/lib/patch-formatter.ts:129-161`).
6. The resulting commit (and any subsequent push) silently contains attacker-chosen content the victim never selected or saw at commit time.
