### Title
Same-chain partial-fill escrow release pays a completing output's solver from the *entire* shared token balance, not just that output's reserved share - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
The bug-class seed is "burn/pay from the wrong balance bucket instead of the amount actually owed." The local analog is in `_fillSameChain()` in `IntrinsicIntents.sol`: when an output leg reaches full completion, the escrow released to that solver is read directly from the aggregate `_orders[commitment][token]` balance rather than the amount specifically reserved for that output index. Because `_orders` is keyed only by `(commitment, token address)` and not by output index, any order whose `inputs` array references the same token for more than one leg lets whichever leg completes first drain the token's *entire* remaining escrow — including the portion earmarked for a still-open leg.

### Finding Description
`_orders[commitment][token]` in `IntentsBase.sol` is a flat `mapping(bytes32 => mapping(address => uint256))` [1](#0-0) . It aggregates escrow per token across the whole order, with no per-output-index partition.

In `_fillSameChain()`, when a fill causes `amountFilled == totalRequired` for a given output leg `i`, the code does not compute the proportional remaining share for leg `i` — it reads whatever is currently sitting in `_orders[commitment][token]` for that token and releases all of it:

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [2](#0-1) 

This value is then handed straight to `_withdraw()`, which decrements `_orders[commitment][token]` by exactly that amount and transfers it to the completing solver:

```solidity
_orders[body.commitment][token] = escrowed - amount;
...
IERC20(token).safeTransfer(beneficiary, amount);
``` [3](#0-2) 

If `order.inputs` contains the same token address at two different indices (e.g. two output legs both settled in the same ERC20), both legs' escrow accumulates into one shared counter. Whichever leg is filled to completion first empties that whole counter for the solver who completed it — not just the fraction that was reserved for that leg. A second solver who later (or concurrently) supplies output tokens for the other leg finds the shared escrow already zeroed and receives `UnknownOrder()` on `_withdraw` (escrowed == 0) or a truncated payout, while having already irrevocably transferred output tokens to the beneficiary (`IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` happens before the escrow accounting check) [4](#0-3) .

### Impact Explanation
This is the same broken invariant as the credit-token report: value is released from an aggregate holding pool instead of the specific allotment tied to the action that unlocked it, so one party's completion siphons funds owed to another. Here the practical effect is fund loss for an honest solver who fills a distinct order leg but never receives the input tokens they were promised, because a different leg's "full completion" branch swept the shared per-token escrow balance to itself first. Depending on ordering, part of the user's escrow can end up paid entirely to one solver while a second solver's output delivery goes uncompensated — an unauthorized reallocation of escrowed funds to the wrong beneficiary/amount.

### Likelihood Explanation
No entrypoint in `IntentsBase`/`IntrinsicIntents` shown here validates that `order.inputs` token addresses are unique across indices, and `order.inputs`/`order.output.assets` are attacker (order-creator) controlled fields fixed at `placeOrder` time. Constructing an order with a repeated input token across two output legs requires no privileged access — any user placing an order can create this layout, and any unsuspecting solver racing to fill either leg is exposed. The path is reachable by an ordinary, unprivileged caller (`fillOrder`/`_fillSameChain`) with no relayer, prover, or admin involvement, matching the required "public entrypoint, unprivileged attacker" bar. I was not able to fully inspect `placeOrder`'s validation logic before the tool budget ran out, so I cannot rule out an explicit anti-duplicate-token check existing elsewhere in the placement path — this is the main residual uncertainty in this finding.

### Recommendation
Track escrow per `(commitment, outputIndex)` (or per `(commitment, inputIndex)`) rather than aggregating purely by token address, so that completion of one leg can only ever release the amount specifically escrowed for that leg. Alternatively, at `placeOrder` time, reject orders whose `inputs` array contains duplicate token addresses, or explicitly document/enforce a strict 1:1, non-aggregating mapping between `inputs[i]` and `output.assets[i]` so that `_orders[commitment][token]` unambiguously represents exactly one leg's balance.

### Proof of Concept
1. User places a same-chain order with two output legs, `output.assets[0]` and `output.assets[1]`, both requiring input token `USDC` at `order.inputs[0].token` and `order.inputs[1].token` (same address, e.g., 100 USDC each) — `_orders[commitment][USDC] = 200`.
2. Solver A fully fills leg 0 (matching `order.output.assets[0]`'s required output). In `_fillSameChain`, `amountFilled == totalRequired` for leg 0, so `escrowedAmount = _orders[commitment][USDC]` = 200 (the full remaining balance, not the 100 reserved for leg 0) [2](#0-1) .
3. `_withdraw` sets `_orders[commitment][USDC] = 200 - 200 = 0` and pays Solver A the full 200 USDC [3](#0-2) .
4. Solver B, who separately delivers output tokens to complete leg 1, calls fill; the escrow lookup for `USDC` is now 0, so `_withdraw` reverts with `UnknownOrder()` — Solver B has already sent output tokens to the beneficiary but receives no input tokens in return, a direct loss of funds caused by the wrong-bucket withdrawal.
