### Title
Nested/embedded conflict-marker text causes silent corruption of committed files during Copilot conflict resolution - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` and `extractConflictHunks` are two independent, line-based parsers that both scan a conflicted file for `<<<<<<<` / `=======` / `>>>>>>>` markers using near-identical greedy logic. When the "ours"/"theirs" side of a real conflict block itself contains lines that *look like* conflict markers (e.g. documentation, a test fixture, or any text that legitimately uses `<<<<<<<`, `=======`, `>>>>>>>` as literal content — common in files that discuss Git conflict resolution), both parsers latch onto the *first* embedded marker they encounter as the closing delimiter of the outer hunk, rather than the real one. This causes the two independently-invoked scanners to consume different spans of the file, and the remainder of the file — which still contains genuine, unresolved `=======` / `>>>>>>>` marker lines — is silently copied through as ordinary content by the `else` branch at [1](#0-0)  of `reassembleResolvedFile`.

### Finding Description
`extractConflictHunks` in `copilot-conflict-context.ts` collects "ours" content by scanning forward until it sees a `baseMarker` or `separatorMarker` line — it does **not** guard against an embedded `<<<<<<<`/`>>>>>>>` pair appearing inside that content: [2](#0-1) 

`reassembleResolvedFile` performs the equivalent scan when splicing model output back into the file, again only checking for a separator and a closing marker without verifying there isn't a nested marker pair first: [3](#0-2) 

Both functions independently, but consistently, treat the *first* `>>>>>>>`-looking line as the close of the *first* `<<<<<<<`-looking line, ignoring the intervening literal marker-like lines. This means:
1. `extractConflictHunks` produces a hunk count that under-counts real conflicts (the true second conflict block that started right after the false close is skipped entirely because the outer `while` loop's cursor `i` has already moved past it without re-scanning for a following `<<<<<<<`).
2. `reassembleResolvedFile`, using the same greedy first-match logic, splices the model's resolution into the same wrong location, and then falls through to the `else` branch that copies subsequent lines — including the genuine `=======` and `>>>>>>>` markers of the real second conflict — through **verbatim**, since those lines don't start with `<{7}` and are therefore never inspected as conflict markers again.

The comment at [4](#0-3)  claims malformed markers are safely copied through "to avoid data loss," but this guard only covers the case where a `<<<<<<<` has **no** matching close at all — it does not detect or reject the nested-marker misattribution case, so the guard does not stop this path.

The only content-level validation performed on the model's output is a regex check that a single hunk's `resolvedContent` doesn't itself contain `<{7}`/`={7}` lines: [5](#0-4) 
This check operates on the model's own hunk text, not on the final reassembled file, so it cannot catch leftover real marker lines that were never captured into any hunk to begin with.

### Impact Explanation
An attacker who controls a branch/PR the victim merges, rebases, or cherry-picks (a normal, unprivileged workflow — pulling a colleague's or contributor's branch) can craft a file whose conflicting content contains marker-like literal text (e.g., a README/doc explaining Git conflict syntax, or a test fixture with embedded `<<<<<<<`/`=======`/`>>>>>>>` strings). When the victim resolves the resulting merge conflict using the Copilot conflict-resolution feature, the reassembled file that gets written to disk and staged/committed can:
- silently retain genuine `=======` / `>>>>>>>` marker lines from a real, unresolved conflict block that was never sent to the model or spliced correctly, and
- have Copilot's resolution spliced into the wrong location relative to the surrounding code.

This is silent corruption of what the user commits/pushes: the file is presented as "resolved" (no error, no warning), yet the code that lands in the commit/push can contain broken syntax, dropped changes, or literal Git conflict markers that later break builds or reintroduce a bug from either side.

### Likelihood Explanation
This requires: (a) the victim to use the Copilot conflict-resolution feature (an opt-in but normal flow) and (b) a conflicting file where one side's legitimate content contains marker-like lines. This is not an exotic prerequisite — files that document or test Git conflict-marker handling (this very repository's own `app/test/unit/copilot-conflict-resolution-test.ts` contains literal `<<<<<<<`/`=======`/`>>>>>>>` strings as fixture data) are a realistic and attacker-triggerable target, since the attacker only needs to introduce such content on a branch that will later conflict with the victim's branch. No local/physical access, credentials, or social engineering beyond a normal PR/branch merge is required.

### Recommendation
Make both parsers reject (rather than silently absorb) nested marker sequences: when scanning for the closing `=======`/`>>>>>>>` of a hunk, also detect an intervening `<<<<<<<` line and treat the whole region as malformed (skip / flag for manual resolution) rather than picking the first matching close. Additionally, add a final integrity check after `reassembleResolvedFile` that reassembled output contains zero lines matching the conflict-marker regexes before it is treated as fully resolved and written/staged; if any remain, fail closed and route the file to manual resolution instead of silently committing it.

### Proof of Concept
Given a conflicted file on disk (post-merge, still containing markers) with the following content:

```
<<<<<<< HEAD
See below for an example conflict:
<<<<<<< inner-example
foo
=======
bar
>>>>>>> inner-example
=======
real theirs content
>>>>>>> feature
```

1. `extractConflictHunks` scans from the first `<<<<<<< HEAD`, collects `"See below..."`, `"<<<<<<< inner-example"`, `"foo"` as `oursContent` (none of these match `baseMarker`/`separatorMarker`), then hits the literal `=======` and treats it as the real separator, then collects `"bar"` as `theirsContent` until it hits `>>>>>>> inner-example`, closing the hunk there (`hunks.length === 1`). The real trailing `=======` / `real theirs content` / `>>>>>>> feature` lines are never parsed into a hunk. [6](#0-5) 
2. Copilot receives only one conflict ("Conflict 1 of 1") built from the wrong span and returns a single `resolvedContent`.
3. `reassembleResolvedFile` performs the same greedy scan, splices the model's single resolution in place of the `HEAD ... inner-example` span, then resumes at `i = closingIndex + 1` — the loop's `else` branch at line 592-595 copies the leftover `=======`, `"real theirs content"`, and `>>>>>>> feature` lines straight into `resultLines` because they don't start with `<{7}`. [7](#0-6) 
4. The resulting `resolvedContent` returned to the caller (and ultimately written to the working tree / staged for commit) still contains a stray `=======` / `>>>>>>> feature` block — a corrupted, half-resolved file that the UI reports as fully resolved.

Note: I was not able to fully trace the exact write/staging call site in `app-store.ts`/`copilot-store.ts` (only found the reference matches, not the full write path) to confirm whether any later validation step exists there beyond what's shown above; if such a check does exist, it would need to be verified to see whether it inspects the final reassembled text for stray markers before staging.
