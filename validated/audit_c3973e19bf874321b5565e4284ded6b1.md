## Analog Found: Missing Uniqueness Check on `ContractToAsset` Binding in `hyper-fungible-token` Pallet

### Title
Unchecked overwrite of `ContractToAsset` reverse mapping in `register_token`/`update_token` lets a new asset registration hijack an existing EVM contract binding - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
The Linea bug is that `setCustomContract` lets the owner bind a native token to a `_targetContract` without checking whether that target is already bound to a *different* native token, allowing an existing bridge binding to be silently repointed. The exact same missing-uniqueness invariant exists in Hyperbridge's `hyper-fungible-token` pallet: `register_token` and `update_token` write into `TokenContracts` and its reverse index `ContractToAsset` without ever checking whether the supplied `token_contract` address is already bound to a *different* `AssetId`. `ContractToAsset` is the sole authentication mechanism used by `on_accept` to decide which local asset (and therefore which mint/transfer path and beneficiary funds) an incoming cross-chain message resolves to.

`register_token` iterates over the caller-supplied `chains` map and inserts: [1](#0-0) 

Note there is no lookup of `ContractToAsset::<T>::get(chain, &token_contract)` before this insert to verify the contract bytes aren't already claimed by a different `AssetId`. `update_token`'s `add_chains` loop has the same gap — it only removes the *old* contract mapping for the asset being updated, never checks whether the *new* `token_contract` is already claimed by some other asset: [2](#0-1) 

This reverse mapping is not cosmetic — it is the pallet's entire authentication mechanism for incoming ISMP messages. `on_accept` trusts `ContractToAsset` unconditionally to resolve `local_asset_id` from the `(source_chain, from_address)` pair, and then mints/transfers funds to whatever beneficiary the message specifies using that asset: [3](#0-2) [4](#0-3) 

The same lookup also drives refunds on timeout: [5](#0-4) 

Because the mapping can be repointed after the fact by a later `register_token`/`update_token` call targeting the same `(chain, token_contract)` pair, whichever `AssetId` last wrote to `ContractToAsset` becomes the authoritative asset for all future incoming messages from that EVM contract address — exactly mirroring the Linea flaw where `setCustomContract` let the owner rebind an already-used `_targetContract` to a new native token, causing bridged funds to be minted against the wrong bridge target.

### Impact Explanation
If `CreateOrigin` is configured such that more than one asset can be registered independently over time (the pallet's own documentation configures `CreateOrigin = frame_system::EnsureSigned<AccountId>` for `register_token`), any later registration/update call that reuses a `token_contract` address already bound to an existing asset silently reassigns that EVM contract's incoming message stream to the new `AssetId`. Genuine incoming transfers from the real EVM contract would then be minted/transferred as the wrong asset to the recipient — wrong-asset minting, potential fund loss for the original asset's users, and a path to mint an unrelated asset "for free" against an EVM contract that was never configured to back it. This matches the required impact classes: unauthorized execution/state acceptance and wrong asset/beneficiary settlement, since `on_accept`'s sole authentication (`ContractToAsset`) becomes attacker/registrant-controlled.

### Likelihood Explanation
The likelihood depends entirely on how `CreateOrigin` is configured in the concrete runtime. Per the pallet's own developer documentation the intended configuration example uses `EnsureSigned<AccountId>`, i.e. any signed account, making this trivially exploitable by an unprivileged caller in that configuration. Even under a more restrictive origin (e.g., a governance/root origin), the underlying invariant violation is real: there is no code-level guard preventing a second registration from clobbering an existing `ContractToAsset` entry, so the flaw is present regardless of who holds `CreateOrigin`.

### Recommendation
Before inserting into `TokenContracts`/`ContractToAsset` in both `register_token` and `update_token`, check `ContractToAsset::<T>::get(chain, &token_contract)`; if it exists and resolves to a different `AssetId` than the one being registered/updated, reject the call (e.g., a new `Error::TokenContractAlreadyBound`). This mirrors the Linea fix's `isNewToken` modifier check on the target contract.

### Proof of Concept
1. Authority (whatever origin `CreateOrigin` permits) calls `register_token` with `local_id = ASSET_A`, `chains = { Evm(1): { token_contract: 0xCONTRACT } }`. `TokenContracts[(Evm(1), ASSET_A)] = 0xCONTRACT` and `ContractToAsset[(Evm(1), 0xCONTRACT)] = ASSET_A` are set, per [1](#0-0) .
2. Later, the same/another call to `register_token` (or `update_token`) registers `local_id = ASSET_B` reusing the identical `token_contract: 0xCONTRACT` for `Evm(1)`. No check rejects this; `ContractToAsset[(Evm(1), 0xCONTRACT)]` is overwritten to `ASSET_B`.
3. Any subsequent legitimate ISMP `PostRequest` arriving from `source = Evm(1)`, `from = 0xCONTRACT` is now resolved by `on_accept` via `ContractToAsset::<T>::get(source, &from)` to `ASSET_B` instead of `ASSET_A`, per [3](#0-2) , causing the pallet to mint/transfer `ASSET_B` to the beneficiary instead of `ASSET_A` — silently redirecting bridged value to the wrong asset.
