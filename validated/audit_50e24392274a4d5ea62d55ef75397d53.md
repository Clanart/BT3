### Title
`ThresholdKeys::read` trusts the attacker-declared participant count `n` to drive allocation and `n` point decodings before any bound/validity check — a claimed-length deserialization over-consumption — (File: crypto/dkg/src/lib.rs)

### Summary
The Nextcloud bug (CVE-2024-52520) is a "declared size trusted, actual size unbounded" flaw: a pre-flight HEAD response's declared length is used for the size decision while the subsequent GET body can be arbitrarily larger. In Serai, `ThresholdKeys::read` exhibits the analogous pattern inside the byte stream itself: the `n` field embedded in attacker-controlled bytes is trusted to size a `Vec::with_capacity` allocation and to drive `n` scalar reads plus `n` group-element decodings, before `ThresholdParams::new` / `ThresholdKeys::new` ever validates `t`, `n`, `i`, or the interpolation mode. An unprivileged party feeding bytes to `ThresholdKeys::read` can therefore make the peer allocate memory and burn CPU proportional to a claimed `n` up to 65535, regardless of the multisig's real size. [1](#0-0) 

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, and `i` directly from the input stream, then:

1. If the interpolation byte is `0` (`Constant`), it immediately executes `Vec::with_capacity(usize::from(n))` and loops `0..n` calling `C::read_F(reader)` — before checking that `t == n` (required for `Constant`) or that `n` is sane.
2. It then unconditionally loops `1..=n` calling `read_G` to fill `verification_shares`.
3. Only after all of this does it call `ThresholdParams::new(t, n, i)` and `ThresholdKeys::new(...)`, which is where `ZeroParameter`, `InvalidThreshold`, `InvalidParticipant`, and `InapplicableInterpolation` are raised.

So the declared `n` in the byte stream — not the real, protocol-established participant count — controls both memory allocation and `O(n)` elliptic-curve decompression work. Just as Nextcloud's link previewer trusted the HEAD `Content-Length` and then streamed a far larger body, `ThresholdKeys::read` trusts the embedded count and consumes resources sized by it before the post-hoc validation rejects the parameters. The same pattern of reading a declared quantity of elements before semantic validation also appears in `Commitments::<C>::read` in `crypto/dkg/pedpop/src/lib.rs` (lines 110-128), which reads `params.t()` points — bounded by local params there — whereas `ThresholdKeys::read` is driven purely by attacker bytes. [2](#0-1) [3](#0-2) 

### Impact Explanation
An unprivileged party who can cause a validator/processor to run `ThresholdKeys::read` on bytes they supply (e.g., during multisig/key-rotation message handling) can craft a blob with `interpolation = 0` and `n = 65535`. This forces an immediate ~`65535 * sizeof(F)` capacity allocation plus up to 65535 scalar reads and 65535 `read_G` point decompressions (each a full decoding/subgroup check) — all before the blob is rejected. Repeated submissions yield a CPU- and memory-exhaustion denial of service, matching the availability-only impact profile of the reference advisory (CVSS A:H, no confidentiality/integrity impact). The work is bounded by `u16`, so the severity is medium rather than high, mirroring the reference.

### Likelihood Explanation
The flaw is deterministic and requires no cryptographic advantage — only the ability to get attacker bytes into `ThresholdKeys::read`. It does require a call path where serialized `ThresholdKeys` come from an untrusted source; if the deployment only ever reads locally-written keys, reachability drops. However, the format is explicitly a serialization/deserialization API (`write`/`read`/`serialize`) exposed for interchange, and DKG/threshold flows are precisely where untrusted peers' bytes are deserialized.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` immediately after reading them, before any allocation or element decoding; reject `n` values inconsistent with the interpolation tag (`Constant` requires `t == n`) up front; and avoid `Vec::with_capacity(n)` — use incremental `push` so allocation is proportional to bytes actually present (the same chunked-read defense used in `networks/ethereum/src/machine.rs`'s `Call::read`, which explicitly documents this exact DoS class). Optionally impose a protocol-level max `n`. [4](#0-3) 

### Proof of Concept
```rust
// Feeding ThresholdKeys::<C>::read a blob with interpolation=Constant and n=65535:
let mut blob = vec![];
blob.extend(&(C::ID.len() as u32).to_le_bytes());
blob.extend(C::ID);
blob.extend(&1u16.to_le_bytes());      // t = 1 (valid-looking)
blob.extend(&u16::MAX.to_le_bytes());  // n = 65535 -- attacker-declared
blob.extend(&1u16.to_le_bytes());      // i = 1
blob.push(0);                          // Interpolation::Constant
// No further bytes needed: Vec::with_capacity(65535) is allocated immediately,
// then read_F/read_G churn until EOF. With a fully populated blob the peer
// performs 65535 point decompressions before ThresholdParams::new rejects it.
let res = ThresholdKeys::<C>::read(&mut blob.as_slice());
```

Note: I verified the pre-validation allocation and unvalidated-count loops directly in `crypto/dkg/src/lib.rs`. The exact production call sites that hand untrusted bytes to `ThresholdKeys::read` could not be fully enumerated within the available iterations; if every call site already enforces a strict outer message length or a trailing-bytes check, the practical severity would be lower.

  fn read<R: Read>(reader: &mut R, params: ThresholdParams) -> io::Result<Self> {
    let mut commitments = Vec::with_capacity(params.t().into());
    let mut cached_msg = vec![];

    #[allow(non_snake_case)]
    let mut read_G = || -> io::Result<C::G> {
      let mut buf = <C::G as GroupEncoding>::Repr::default();
      reader.read_exact(buf.as_mut())?;
      let point = C::read_G(&mut buf.as_ref())?;
      cached_msg.extend(buf.as_ref());
      Ok(point)
    };

    for _ in 0 .. params.t() {
      commitments.push(read_G()?);
    }

    Ok(Commitments { commitments, cached_msg, sig: SchnorrSignature::read(reader)? })
