### Title
Duplicate outpoints in deserialized `ReceivedOutput`s can be signed as distinct inputs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`ReceivedOutput::read` accepts an arbitrary `(offset, TxOut, OutPoint)` tuple, and `SignableTransaction::new` trusts each decoded outpoint without checking whether it was already supplied. An attacker who can feed untrusted serialized outputs into the wallet can submit the same Bitcoin outpoint multiple times, inflate the apparent input total, and cause the multisig flow to sign a transaction Bitcoin rejects for duplicate inputs. [1](#0-0) [2](#0-1) 

### Finding Description
`ReceivedOutput::read` parses the spending offset, claimed previous output, and outpoint entirely from caller-controlled bytes, with no ownership or uniqueness validation. [1](#0-0) 

`SignableTransaction::new` then:

1. Sums every supplied `ReceivedOutput.output.value` as spendable input value.
2. Copies every supplied `ReceivedOutput.outpoint` into a distinct `TxIn`.
3. Stores every supplied `ReceivedOutput.offset`.
4. Performs the balance check against the duplicated, attacker-controlled input total. [2](#0-1) [3](#0-2) 

During multisig setup, the only consistency check is that `group_key + offset` produces the claimed output's `script_pubkey`; it does not check whether the outpoint was duplicated or exists with the claimed value. [4](#0-3) 

Finally, `TransactionSignMachine::sign` commits to all claimed prevouts and generates a signature share for every input, including inputs sharing the same outpoint. [5](#0-4) 

### Impact Explanation
A wallet or coordinator accepting serialized `ReceivedOutput`s from an untrusted source can be induced to treat one UTXO as multiple inputs. This can bypass `NotEnoughFunds` and produce a fully signed transaction whose inputs cannot actually be spent. The resulting transaction is invalid under Bitcoin consensus because duplicate inputs are forbidden, causing funds accounted as spendable to become unspendable by that transaction path. [2](#0-1) [6](#0-5) 

### Likelihood Explanation
The attack requires an attacker to control or corrupt serialized `ReceivedOutput` bytes consumed by the wallet. That reachability is exposed through the public `ReceivedOutput::read` API; once duplicate bytes are supplied, no subsequent deduplication prevents them from becoming transaction inputs. A signer using scanner-generated outputs exclusively is not exposed through this path. [7](#0-6) [8](#0-7) 

### Recommendation
Reject duplicate `ReceivedOutput.outpoint` values in `SignableTransaction::new` before calculating balances or constructing `TxIn`s. For example:

```rust
// networks/bitcoin/src/wallet/send.rs
use std::collections::HashSet;

let mut seen_outpoints = HashSet::with_capacity(inputs.len());
for input in &inputs {
    if !seen_outpoints.insert(input.outpoint) {
        return Err(TransactionError::DuplicateInput);
    }
}
```

Add a `DuplicateInput` variant to `TransactionError`. Inputs should also be accepted only from an authenticated scanner/database path unless the caller has independently verified that each `OutPoint` exists and contains the claimed `TxOut`.

### Proof of Concept
```rust
// Conceptual Rust PoC

let real = ReceivedOutput::read(&mut attacker_controlled_bytes).unwrap();
let duplicate = real.clone();

// The same outpoint is counted twice, doubling the apparent balance.
let tx = SignableTransaction::new(
    vec![real, duplicate],
    &[(destination_script, payment_larger_than_real_utxo)],
    None,
    None,
    fee_rate,
).unwrap();

// Both duplicated inputs pass the script/offset check.
let machine = tx.multisig(&keys).unwrap();

// The threshold protocol signs both inputs, producing a transaction
// Bitcoin rejects because both TxIns reference the same OutPoint.
```
