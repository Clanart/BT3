Unauthenticated `InternalGetEmergencyStopTx` leaks pre-signed emergency-stop transaction when `client_verification=false` - ([File: core/src/rpc/interceptors.rs])

### Summary
When `client_verification` is disabled, the aggregator's gRPC server uses `Interceptors::Noop`, which performs no authentication whatsoever, so the `OnlyAggregatorAndSelf` check that is supposed to restrict `Internal*` methods to the aggregator itself is not applied at all. This lets any unprivileged network client call `InternalGetEmergencyStopTx` for a known `move_to_vault_txid` and retrieve the pre-signed (only encrypted at rest, not access-controlled) emergency-stop transaction, which is a premature disclosure of a protocol commitment.

### Finding Description
The binding the system is supposed to enforce is: `caller_of(InternalGetEmergencyStopTx) == aggregator_process_itself`, enforced by `only_aggregator_and_self` via `Interceptors::OnlyAggregatorAndSelf` [1](#0-0) . That binding is only wired in when `config.client_verification` is `true`; the server construction code explicitly falls back to `Interceptors::Noop`, which passes every request through unchanged, when `client_verification` is `false`: [2](#0-1) 

`is_internal` itself only inspects a `grpc-method` header injected by middleware and does not perform any cryptographic authentication — the entire security boundary for `Internal*` RPCs rests on the peer-certificate check inside `only_aggregator_and_self`, which is skipped entirely under `Noop`: [3](#0-2) 

The emergency-stop transaction is generated during deposit finalization and stored (encrypted with `emergency_stop_encryption_public_key`) keyed by `move_to_vault_txid` in `verify_and_save_emergency_stop_sigs`, which any observer of the deposit's Bitcoin transactions can learn (the move-to-vault txid is public on-chain once broadcast): [4](#0-3) 

With `client_verification=false`, an attacker who knows a `move_to_vault_txid` (trivially obtainable by watching the chain or by being the depositor themselves, since the attacker profile explicitly includes someone who can "deposit into the bridge") can send an `InternalGetEmergencyStopTx` gRPC request directly to the aggregator's port with no certificate, no key share, and no prior authorization, and the request will pass through `Noop` uncontested and reach the handler.

### Impact Explanation
This matches the High-impact category "premature disclosure of a protocol commitment": the emergency-stop transaction is meant to be held by the aggregator/security council and only revealed/broadcast under a defined operational trigger. Uncontrolled disclosure lets an attacker learn ahead of time exactly what the pre-committed emergency-stop transaction looks like (its structure, and if the RPC returns decrypted bytes, the fully valid N-of-N signed transaction itself), which could let an unauthenticated party broadcast it to freeze a move-to-vault UTXO at a time of their choosing — an outcome the design intends to reserve for authorized security-council action. This is repeatable across every deposit that has completed finalization, since each has its own emergency-stop tx recoverable by its own `move_to_vault_txid`. Note: I was not able to fully confirm from available context whether the RPC handler for `internal_get_emergency_stop_tx` itself decrypts the stored ciphertext before returning it, or returns the encrypted blob as-is — the function body was not located within the searchable index (the file was too large to fully read and grep did not resolve the exact handler body beyond its declaration). This materially affects severity: if only the encrypted blob is returned, the impact is confidentiality/commitment-disclosure (High, as scoped); if it's decrypted server-side and returned in the clear, the impact escalates toward Critical (an unauthenticated party obtaining a broadcastable N-of-N-signed transaction).

### Likelihood Explanation
The precondition is a specific, opt-in deployment misconfiguration: `client_verification=false` in `BridgeConfig`. This is a supported configuration (not merely a test artifact) — it is explicitly branched on in production server-construction code with only a `tracing::warn!` log, no hard failure, in `create_aggregator_grpc_server`: [5](#0-4) 
Given this configuration, exploitation costs the attacker nothing beyond knowing a public `move_to_vault_txid` and sending one gRPC request; no BTC, fees, or special access are required. Likelihood is entirely contingent on operators choosing to run with TLS client verification disabled.

### Recommendation
Do not allow `Interceptors::Noop` to apply to `Internal*`-prefixed methods regardless of `client_verification` setting; either (a) always enforce a minimal internal-only check (e.g., loopback-address restriction, a shared internal secret, or mandatory mTLS specifically for internal methods) independent of the general `client_verification` toggle, or (b) refuse to start the aggregator gRPC server with internal methods exposed on a public listener when `client_verification=false`, forcing internal RPCs onto a separate local-only transport (e.g., Unix socket) as already exists for tests.

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
}
