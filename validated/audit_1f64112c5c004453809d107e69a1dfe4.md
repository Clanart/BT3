### Title
Stack overflow via unbounded recursive RLP decoding of nested `AccountKeyRoleBased` keys - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes its inner `AccountKey` elements through `AccountKeySerializer`, and `AccountKeySerializer.DecodeRLP` dispatches back into `AccountKeyRoleBased.DecodeRLP` when the encoded inner key type is itself `AccountKeyTypeRoleBased`. Nothing bounds this recursion depth during decoding, so an attacker can submit a single `TxTypeAccountUpdate`/`TxTypeAccountCreation` (or fee-delegated variant) transaction whose `AccountKey` payload is an arbitrarily deep chain of nested `RoleBased` keys, causing the Go call stack to overflow while the node merely decodes the transaction — exactly the same bug class as CVE-2026-40612 (unbounded recursion on attacker-controlled nested structure with no depth limit).

### Finding Description
`AccountKeySerializer.DecodeRLP` reads a `keyType`, constructs the concrete `AccountKey` via `NewAccountKey`, and then decodes into it: [1](#0-0) 

When `keyType == AccountKeyTypeRoleBased`, this recurses into `AccountKeyRoleBased.DecodeRLP`, which reads a list of raw byte-strings and, for each element, decodes a fresh `AccountKeySerializer` from those bytes — which can again be `AccountKeyTypeRoleBased`: [2](#0-1) 

The only protection against nested composite keys is `IsCompositeType()`/`CheckInstallable`/`CheckUpdatable`, which reject a `RoleBased` key whose members are themselves composite: [3](#0-2) 

and the API-layer `checkAccountKeyZeroValues` check with its `isNested` flag: [4](#0-3) 

Both of these checks run only *after* the RLP structure has been fully decoded into a semantic `AccountKey` value tree. They do nothing to stop the `DecodeRLP`/`rlp.DecodeBytes` recursion itself from running to whatever depth the raw bytes describe. Because `AccountKeyRoleBased.DecodeRLP` calls `rlp.DecodeBytes` on each sub-element (a new decoding pass, not tail-call optimized), an attacker-crafted transaction with N levels of nested `RoleBased` wrapping (encoded entirely client-side, bypassing any constructor invariant) drives N stack frames of mutually recursive Go decoding functions. This is decoded the moment the transaction is parsed — during `Transaction.DecodeRLP` at tx-pool ingestion (`AddRemote`/p2p broadcast) or block/RLP transaction-list decoding — well before any execution-time nested-composite-type validation occurs.

### Impact Explanation
A single external, unprivileged party can submit (via `eth_sendRawTransaction`/`klay_sendRawTransaction` or p2p tx propagation) a `TxTypeAccountUpdate`/`TxTypeAccountCreation` transaction containing a deeply nested `AccountKeyRoleBased` blob. When any node attempts to RLP-decode that transaction — which happens unconditionally as part of ingesting the raw transaction bytes, prior to any account-key semantic validation — the recursive decode drives the Go goroutine stack to exhaustion, causing an unrecoverable process crash (`fatal error: stack overflow` is not a normal Go `panic` and cannot be `recover()`-ed). This is a remotely triggerable node crash/DoS reachable from a single crafted transaction submitted by any unprivileged sender, directly analogous to the jq `jv_contains` unbounded-recursion stack overflow.

### Likelihood Explanation
High likelihood of triggerability: constructing the malicious RLP bytes requires no special privileges, no valid signature validation is needed before the vulnerable decode path executes (the decode of the `AccountKey` field happens as part of the generic `Transaction.DecodeRLP`/`s.Decode(serializer)` call chain used for every incoming transaction), and the depth required to exhaust a typical goroutine stack (a few thousand nested `RoleBased` layers, each contributing multiple stack frames across `DecodeRLP` → `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → `NewAccountKey`/`s.Decode`) is easily encodable in a modest-size RLP payload.

### Recommendation
Add an explicit recursion/nesting-depth counter (or a maximum key-tree depth check) to `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` that is enforced *during* decoding (not only post-hoc in `CheckInstallable`), rejecting any `AccountKeyRoleBased` payload whose encoded nesting exceeds a small fixed bound (e.g., 1, since nested composite keys are never semantically valid). Alternatively, plumb the existing `IsCompositeType` restriction into the decoder itself so that decoding a `RoleBased`-typed element inside another `RoleBased` list immediately errors out instead of recursing.

### Proof of Concept
Conceptually:
1. Construct `innerKey := AccountKeyPublic{...}` (or any leaf key).
2. Repeatedly wrap: `k := NewAccountKeyRoleBasedWithValues([]AccountKey{k})` for N ≈ tens of thousands of iterations, RLP-encoding at each nesting level using `AccountKeySerializer.EncodeRLP` (bypassing the semantic constructors/validators that normally would run only at execution time).
3. Embed the resulting deeply-nested `AccountKey` bytes into the `Key` field of a `TxTypeAccountUpdate` (or `TxTypeAccountCreation`) transaction and RLP-encode the full transaction.
4. Submit the raw transaction via `eth_sendRawTransaction`/p2p broadcast to a Kaia node.
5. The node's `Transaction.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recursion runs to depth N before any `CheckInstallable`/`ErrNestedCompositeType` rejection can occur, crashing the node with a stack overflow.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
}
